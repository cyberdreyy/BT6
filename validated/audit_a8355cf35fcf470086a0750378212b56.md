### Title
Marginfi account migration allows transferring account authority to the zero address, permanently freezing user funds - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
The `transfer_to_new_account` / `transfer_to_new_account_pda` instructions let a user migrate their `MarginfiAccount` to a freshly-created account under a new authority. The `new_authority` account is accepted as a completely unchecked `UncheckedAccount` with no validation against the Solana system default (zero) pubkey. The only such check exists client-side in the CLI helper, not in the on-chain program, so nothing prevents the new account's `authority` field from being set to `Pubkey::default()`.

### Finding Description
`TransferToNewAccount` (and the PDA variant `TransferToNewAccountPda`) explicitly documents the account as unchecked: [1](#0-0) 

`transfer_to_new_account` calls `initialize_migrated_account(&mut new_account, &old_account, ctx.accounts.new_authority.key(), ...)` directly with whatever pubkey was supplied, with no `check!`/`check_eq!` guarding against `Pubkey::default()`: [2](#0-1) 

After migration, the old account is disabled and marked as migrated to the new account, and all lending positions are moved to the new account: [3](#0-2) [4](#0-3) 

This is the same bug class described in the external report: a transfer/ownership-assignment routine that should reject the zero address but doesn't, causing the underlying value (here, the entire `MarginfiAccount`, its balances/collateral, and any accrued health) to become permanently associated with an address no one controls.

Notably, the developers were clearly aware zero-address transfers are dangerous, because the CLI helper enforces this check purely client-side: [5](#0-4) 

That check is trivially bypassable by anyone building the `TransferToNewAccount`/`TransferToNewAccountPda` instruction directly (any wallet, SDK, or malicious frontend), since the on-chain program performs no equivalent validation.

### Impact Explanation
Once migrated, `authority = Pubkey::default()` on the new `MarginfiAccount`. All subsequent operations on that account (`lending_account_deposit`, `withdraw`, `borrow`, `repay`, `close_balance`, further transfers, order placement, etc.) require a matching `Signer` for the account authority, enforced via `is_signer_authorized`/`has_one = authority` type checks used across the account's instruction handlers. Since no keypair exists for the all-zero pubkey, nobody can ever sign as that authority again. All collateral/positions moved into the new account become permanently frozen/unrecoverable — a durable, unrecoverable financial loss for the user, fully analogous to the "assets stuck forever" and "no owner can ever act on the position" impact in the external report.

### Likelihood Explanation
This requires only a single permissionless call by the account's own current authority (or anyone who can trick a user's wallet/frontend into constructing this instruction with `new_authority = Pubkey::default()`), reachable in one instruction with no privileged role required. Because the protection existing today lives only in an off-chain CLI, any other client (dApp frontend, SDK, malicious dApp, or a bug in tooling) that composes this instruction directly bypasses it entirely, making accidental or malicious triggering plausible.

### Recommendation
Add an on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` (and any other future migration/transfer-of-authority instruction) rejecting `new_authority == Pubkey::default()`, mirroring the check already present in the CLI:
```rust
check!(
    ctx.accounts.new_authority.key() != Pubkey::default(),
    MarginfiError::InvalidAuthority // or a new dedicated error
);
```
This should be enforced identically in `TransferToNewAccount` and `TransferToNewAccountPda` account validation/handler logic.

### Proof of Concept
1. User creates a `MarginfiAccount` via `marginfi_account_initialize` and deposits collateral.
2. User (or an attacker who convinces the wallet to sign) submits `transfer_to_new_account` (or `transfer_to_new_account_pda`) with `new_authority = Pubkey::default()`.
3. Instruction succeeds: old account is flagged `ACCOUNT_DISABLED` and `migrated_to` is set; new account is initialized with `authority = Pubkey::default()`, holding all migrated lending positions. [6](#0-5) 
4. Any attempt to interact with the new account (withdraw, repay, borrow, transfer again) requires a `Signer` matching `authority == Pubkey::default()`, which is unobtainable — the deposited collateral is permanently frozen.
