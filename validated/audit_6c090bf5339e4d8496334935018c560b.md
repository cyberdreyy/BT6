Based on my investigation, I found a genuine local analog of this bug class in `staking_contract.move` and `vesting.move`, both of which route payouts through `aptos_account::deposit_coins`, a function with an explicit "recipient may reject the deposit" guard that is functionally equivalent to the missing `receive()`/`fallback()` problem in the Solidity report.

### Title
Unprivileged shareholder can permanently DoS `staking_contract::distribute` / `vesting::distribute` for all co-shareholders by disabling direct coin acceptance - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move, aptos-move/framework/aptos-framework/sources/vesting.move)

### Summary
`aptos_account::deposit_coins` aborts if the recipient is not registered for the coin and has not opted in to receive arbitrary direct coin transfers [1](#0-0) . `staking_contract::distribute_internal` and `vesting::distribute` both iterate over *all* shareholders of a shared distribution pool in a single atomic transaction and call `aptos_account::deposit_coins` for each one [2](#0-1) [3](#0-2) . If any single shareholder in the loop cannot accept the deposit, the entire transaction aborts, so nobody in that distribution round is paid — this is the same "cannot receive funds → revert → stuck value" pattern flagged in the external report about `L1Migrator`/`BridgeMinter`.

### Finding Description
`deposit_coins` explicitly guards against pushing coins to an account that has not registered a `CoinStore<CoinType>` and has disabled direct transfers via `set_allow_direct_coin_transfers`: [4](#0-3) 

In `staking_contract::distribute_internal`, the function withdraws the entire inactive/pending-inactive balance from the stake pool and then loops over `distribution_pool.shareholders()` (which includes the staker and the operator, redirected to the operator's beneficiary via `beneficiary_for_operator`), calling `aptos_account::deposit_coins` for each recipient inside a `while` loop with no per-recipient failure isolation: [5](#0-4) 

The equivalent path exists in `vesting::distribute`, which iterates `grant_pool.shareholders()` and calls `aptos_account::deposit_coins(recipient_address, share_of_coins)` for every shareholder, where `recipient_address` may be a beneficiary set independently by the admin: [3](#0-2) 

Because `distribute` (in both modules) is a permissionless `public entry fun` callable by anyone, and because Move transactions are all-or-nothing, any single shareholder — the staker, the operator/beneficiary, or a vesting shareholder/beneficiary — can unilaterally make themselves unable to accept a direct `AptosCoin` deposit (by never registering `CoinStore<AptosCoin>`, or by calling `set_allow_direct_coin_transfers(account, false)`), which then blocks the entire `distribute` call for **every other** shareholder sharing that pool, not just themselves.

### Impact Explanation
This breaks the invariant that "unlock, reactivate, withdraw, synchronize, and beneficiary-update paths must not redirect value or strand it permanently" required for the stake/vesting gate. A single uncooperative or malicious co-shareholder (e.g., an operator who disputes a commission, or a vesting shareholder with a grudge against a co-shareholder) can trap the withdrawable/inactive stake for the entire pool indefinitely — the staker's own already-unlocked stake becomes undistributable as long as the griefing party keeps direct-transfer acceptance disabled, since the withdrawal from `stake::withdraw_with_cap` and the distribution attempt happen atomically and are rolled back on abort.

### Likelihood Explanation
This requires no privileged role: any shareholder of an existing `staking_contract` or `vesting` distribution pool (staker, operator, beneficiary, or vesting shareholder) can trigger it against themselves and, by extension, against every other party who shares that same distribution pool, using only the standard `aptos_account::set_allow_direct_coin_transfers` entry function [6](#0-5)  — no exploit of a separate bug is needed to reach the block, only ordinary account configuration.

### Recommendation
Do not let one recipient's inability/refusal to accept a direct deposit abort payouts to unrelated shareholders. Isolate failures per-recipient (e.g., catch/skip a failing deposit and route the amount to an escrow/claimable balance the recipient can pull later), or split distribution into independent, per-recipient claim calls rather than a single atomic loop that pays out to all shareholders in one transaction.

### Proof of Concept
Conceptually (not fully verified in this pass due to tool-call limits — see caveats below):
1. Staker creates a `staking_contract` with `operator`. Both accounts exist and are registered for `AptosCoin`.
2. `operator` calls `aptos_account::set_allow_direct_coin_transfers(operator_signer, false)`, then (if their `AptosCoin` balance is zero) unregisters their `CoinStore<AptosCoin>` via `coin::unregister` (not directly located in the reviewed slice — needs confirmation this API exists and permits zero-balance unregistration).
3. Rewards accrue and become inactive/pending-inactive on the shared stake pool.
4. Anyone calls `staking_contract::distribute(staker_address, operator_address)`.
5. The loop reaches the operator's/beneficiary's share and calls `aptos_account::deposit_coins`, which asserts `can_receive_direct_coin_transfers(operator)` and aborts, reverting the whole transaction — the staker's already-unlocked stake becomes stuck until the operator changes their transfer settings back.

**Caveats / what I could not fully verify with the remaining tool budget:**
- I could not confirm the exact default value of `can_receive_direct_coin_transfers` when no `DirectTransferConfig` resource exists (i.e., whether an account must actively opt out, or whether unregistered/new accounts default to rejecting direct transfers already).
- I could not locate/confirm a `coin::unregister` entry function and its zero-balance precondition in this pass, which affects whether an already-registered shareholder can revert to an unregistered state.
- I did not confirm whether a *former* operator remains a shareholder in `staking_contract`'s `distribution_pool` after `switch_operator` (which calls `distribute_internal` first), which would matter for whether a departed, uncooperative operator can still grief a pool they no longer manage.

Given these open items, I'm presenting this as the strongest candidate found, but recommend a follow-up focused specifically on confirming the default `DirectTransferConfig` behavior and the `coin::unregister` semantics before treating this as fully proven.
