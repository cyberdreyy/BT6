## Analysis

The report's bug class — an ERC20 `transfer()`/`transferFrom()` that can fail without reverting, leaving accounting out of sync with actual token movement — maps onto NEAR's async `Promise::transfer` semantics. In this repo, every custodial withdrawal path that burns an internal balance before sending NEAR out via a `Promise` follows a strict pattern elsewhere: attach a `.then()` callback that calls `is_promise_success()` and rolls back the ledger update if the transfer failed. This is the pattern used throughout `lockup/src/owner_callbacks.rs` and `lockup/src/foundation_callbacks.rs` (e.g. `on_staking_pool_withdraw`, `on_withdraw_unvested_amount`).

`w-near/src/w_near.rs`'s `near_withdraw` breaks this pattern.Confirmed: `near_withdraw` in `w-near/src/w_near.rs` L38-46 is the only place in scope where an internal ledger balance is decremented and then a bare `Promise::new(...).transfer(...)` is fired with no `.then()` callback to confirm the transfer landed — unlike every other outgoing-NEAR path in this codebase (`lockup/src/owner_callbacks.rs` L102-145, `lockup/src/foundation_callbacks.rs` L143-241), which all attach a callback that calls `is_promise_success()` and reverts the internal accounting if the transfer failed.

### Title
Unhandled NEAR transfer failure in `near_withdraw()` permanently burns wNEAR without guaranteeing delivery of native NEAR - (File: `w-near/src/w_near.rs`)

### Summary
`near_withdraw()` calls `self.ft.internal_withdraw(&account_id, amount)`, permanently reducing the caller's wNEAR balance and the token's total supply, and only afterward schedules `Promise::new(account_id).transfer(amount + 1)`. No `.then()` callback is attached to verify the transfer succeeded. If the outgoing `Transfer` action fails for any reason, the ledger burn is never rolled back.

### Finding Description
`near_withdraw` in [1](#0-0)  performs the balance-reducing state change (`internal_withdraw`) synchronously and then issues the native NEAR transfer as a detached `Promise` with no result-checking callback. This is the exact bug class described in the external report: a value-moving call whose outcome is not verified, so the recorded claim (wNEAR balance / total supply) can diverge from the value actually delivered.

Contrast this with every other custodial-transfer code path in the same set of contracts, which explicitly binds the accounting update to promise success:
- [2](#0-1) 
- [3](#0-2) 

Both of those only finalize/keep the balance decrement when `is_promise_success()` returns true, and otherwise restore the pre-withdrawal state. `near_withdraw` has no equivalent — the burn in `internal_withdraw` is unconditional and irreversible the moment the method returns, regardless of what happens to the subsequently scheduled `Promise::transfer`.

The equality this breaks: `sum(ft.accounts balances)` (recorded wNEAR claims) should equal the NEAR value the contract is obligated to deliver on redemption. After `internal_withdraw`, the claim is already reduced by `amount`, but the corresponding NEAR has not yet been confirmed as delivered to `account_id`. If the transfer receipt fails, the claim reduction still stands.

### Impact Explanation
This is a value-debited-versus-value-delivered custody break: the wNEAR ledger decreases and total supply drops immediately, but the matching native NEAR is only conditionally, asynchronously sent. If the transfer fails, the affected NEAR remains stranded in the contract's balance with no accounting entry pointing back to the account that was debited, and no retry/refund path exists in this method. This falls under the Critical impact category — a wrongly-tracked claim exceeding/diverging from assets actually held, and effectively funds permanently frozen for the affected account, since `internal_withdraw` already removed their only record of entitlement.

### Likelihood Explanation
The failure path for a native `Transfer` action is narrow (primarily `AccountDoesNotExist`), and `account_id` here is the transaction predecessor, so it normally exists at call time. The trigger condition is a receiver account being removed between the call and the asynchronous execution of the transfer receipt (e.g., a `delete_account` action landing on the same account in the interim). This is a low-frequency edge case, but it requires no privileged actor, no redeploy, and no cross-account victim — it is exercised purely by the withdrawing account's own sequence of actions/timing, which fits the "unprivileged attacker" bar, even though the "gain" here manifests as an unrecoverable loss/freeze rather than a profit extraction.

### Recommendation
Do not call `internal_withdraw` before the transfer is confirmed. Instead, schedule the `Promise::transfer` first, attach a `.then()` callback (mirroring `on_staking_pool_withdraw` / `on_withdraw_unvested_amount`) that checks `is_promise_success()`, and only call `internal_withdraw` (or leave the balance debited) when the callback confirms success; otherwise leave the balance untouched. Alternatively, keep the debit but add a resolution callback that re-credits the account via `internal_deposit` if the transfer promise fails.

### Proof of Concept
1. Register and deposit NEAR via `near_deposit` to mint wNEAR to `account_id`.
2. `account_id` calls `near_withdraw(amount)` with 1 yoctoNEAR attached.
3. `self.ft.internal_withdraw(&account_id, amount)` executes synchronously, reducing `account_id`'s wNEAR balance and total supply by `amount`.
4. `Promise::new(account_id).transfer(amount + 1)` is scheduled but not awaited/checked; if `account_id` is deleted before this receipt executes (e.g., via a concurrently submitted `delete_account`), the transfer receipt fails.
5. No callback exists to detect step 4's failure or restore the wNEAR balance — the ledger permanently reflects the burn with no corresponding NEAR delivered, and no code path allows recovery of the stranded amount. [1](#0-0)
