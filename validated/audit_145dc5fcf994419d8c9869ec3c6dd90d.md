### Title
Miner-controlled reorg permit (`check_parent_tenure_choice`) lets a single sortition winner void a signer's own equivocation guard, opening the door to signing conflicting blocks - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
The external report's bug class is an unguarded, unilaterally-triggerable admin action (`changeController`) that silently rewrites trusted state and lets the caller drain funds via `sendTokens`. The reachable analog in this codebase is `SortitionData::check_parent_tenure_choice` [1](#0-0) : a single miner who wins a sortition can, purely by choosing to build off something other than the prior sortition and by controlling the timing of its own tenure's proposal, cause each signer to unilaterally rewrite its own conflict-tracking state (`mark_tenure_superseded`) — voiding the very equivocation guard meant to stop a signer from endorsing two conflicting chains.

### Finding Description
`check_parent_tenure_choice` is called from `SortitionState::is_tenure_valid` [2](#0-1)  for every new sortition/tenure a miner proposes. If the new tenure's parent is not the prior sortition (i.e. it is reorging one or more tenures), the signer independently asks the node for forking info and decides, per-signer and without any peer coordination, whether the reorg is "valid behavior." The decisive branch is the timing check:

```
if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
    ...
    superseded_tenures.push(tenure);
    continue;
}
``` [3](#0-2) 

`proposal_to_sortition` is derived from `local_block_info.approved_time`, which is populated by this signer's own DB records of when it saw/approved the reorged tenure's first block — timing that is downstream of the (single) miner's own message pacing during its previous tenure, not of any multi-party agreement. `first_proposal_burn_block_timing` is a fixed config duration [4](#0-3) , so a miner that simply delays sending its first proposal in a tenure close enough to the next burn block transition can make every signer independently conclude the reorged tenure was "poorly timed" and thus reorg-eligible.

Once every reorged tenure clears this per-tenure check, the whole reorg is "permitted," and each superseded tenure is recorded via `record_superseded_tenure` → `SignerDb::mark_tenure_superseded`, keyed to the *new* (reorging) sortition's consensus hash [5](#0-4) . The doc comment for this mechanism states explicitly the intended effect: "a signature we already placed on one of its blocks must stop counting as a conflict while `self`'s sortition remains canonical" [6](#0-5) . That is precisely the signer's own equivocation guard being turned off — analogous to the `changeController` pattern where a single privileged actor rewrites trusted state (here, "which blocks I may safely have signed") that other logic (`sendTokens`/here, "am I allowed to sign a conflicting block") then trusts unconditionally.

This decision is made per-signer, locally, and is entirely miner-triggerable: it requires no majority of signers, no other signer's key, and no node-consensus acceptance to occur first — it only requires the local signer's own recorded proposal timing plus the node's `get_tenure_forking_info` response, both of which are consequences of what the single sortition-winning miner chose to broadcast and when.

### Impact Explanation
If the reorg permit is granted too liberally (e.g., because the miner deliberately delayed/timed its previous tenure's first proposal to land inside the loophole window), the signer's conflict-detection logic (which normally prevents signing two blocks that could both end up in the chain, as described for `get_signed_conflicts`/`has_signed_block_in_tenure` in the flow docs) is told to disregard a signature it already placed on the reorged tenure. This is a "signer signing an invalid/non-canonical/conflicting block" class breakage: the safety property that a signer never signs two blocks that could both land in the canonical chain at the same height is exactly the equality this mechanism is meant to protect, and it is voided based on evidence entirely under the proposing miner's control. Because the permit is recorded per-signer and keyed to the new sortition's own canonicity [7](#0-6) , a miner who can influence the "poorly timed" classification across the signer set can get many signers to independently drop their guard against the same conflicting chain, which is the concrete safety break this analog reaches without needing a majority of signers or any signer's private key.

### Likelihood Explanation
This requires only the block-proposing miner (a single "slot" actor) to control ordinary parameters already within its control — when and how it proposes its first block in a tenure relative to the next burn block — and does not require compromising any signer key, achieving majority collusion, or performing StackerDB-level attacks. The relevant thresholds (`first_proposal_burn_block_timing`) are static config values known/inferable ahead of time, making the timing window something a motivated miner can target deliberately rather than accidentally.

### Recommendation
Treat the reorg-permit decision the same way block signatures are treated: require it to be corroborated by the group's own agreed pre-commit/signature state (e.g., anchored to `signed_self`/`signed_group` timestamps rather than `approved_time`, which is stamped at pre-commit and is not a signature) before allowing `mark_tenure_superseded` to null out a prior signature's conflict status; alternatively, gate the superseded-tenure recording on a global-state / multi-signer agreement input (similar to `GlobalStateEvaluator`) rather than purely local, miner-influenced timing so a single miner cannot unilaterally cause many independent signers to void their own equivocation guard via the same maneuver.

### Proof of Concept
1. Miner M mines tenure T1 and, in T1, deliberately proposes its first (and only) block late — timed such that `sortition_state_received_time - approved_time < first_proposal_burn_block_timing` will hold for the *next* tenure's evaluation, per the check at [3](#0-2) .
2. In the next sortition, M (or a colluding miner) proposes tenure T2 whose parent is the sortition *before* T1 (a reorg of T1), instead of building on T1.
3. Each signer independently runs `check_parent_tenure_choice`: `tenures_reorged` includes T1; `get_globally_accepted_block_count_in_tenure(T1) <= 1` (satisfied if only one block was ever signed in T1); the timing check classifies T1 as "poorly timed," so T1 is pushed into `superseded_tenures` and the reorg is permitted [8](#0-7) .
4. `record_superseded_tenure` marks T1 superseded by T2's sortition in each signer's local DB [9](#0-8) , so a signature the signer already gave on T1's block no longer counts as a conflict for as long as T2's sortition is canonical — even though the signer already signed a block in T1 that could still separately propagate and be accepted by peers who never saw the reorg attempt.
5. This yields multiple signers now willing to sign a competing/conflicting block on T2's branch despite having previously signed a block on T1's branch, breaking the "never sign two blocks that could both land in the chain" guarantee without any signer's key being compromised and without requiring a majority coordinated attack — only the proposing miner's control over proposal timing.

    /// Note that we have sanctioned `self`'s tenure replacing whatever `tenure` built, so a
    /// signature we already placed on one of its blocks must stop counting as a conflict while
    /// `self`'s sortition remains canonical.
    ///
    /// A failure to record only costs a delayed replacement -- the conflict keeps blocking until
    /// the signature goes stale -- so it is logged rather than propagated.
    fn record_superseded_tenure(&self, signer_db: &mut SignerDb, tenure: &TenureForkingInfo) {
        if let Err(e) = signer_db.mark_tenure_superseded(
            &tenure.consensus_hash,
            tenure.burn_block_height,
            &self.consensus_hash,
            &self.burn_block_hash,
        ) {
            warn!("Failed to record a tenure whose reorg we permitted: {e}";
                "superseded_tenure_id" => %tenure.consensus_hash,
                "superseded_by" => %self.consensus_hash,
            );
        }
    }
