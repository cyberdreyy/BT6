### Title
Signer weight double-counted across accept/reject tallies in `StackerDBListener`, producing a false "block cannot reach quorum" signal - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
In the mining-node's StackerDB message-processing loop, a single malicious signer can cause its weight to be simultaneously recorded in both `total_weight_rejected` and `total_weight_approved` for the same block proposal by first sending a `Rejected` response and later a valid `Accepted` response for the same `signer_signature_hash`. The `Accepted` branch only guards against double counting via `gathered_signatures.contains_key(&slot_id)`, never checking whether that slot already contributed weight on the `responded_signers`/rejected side. This breaks the intended invariant that a signer's weight is exclusively attributed to one side of the tally, and can trigger the "no-quorum-possible" liveness check with stale/incorrect data.

### Finding Description
`BlockStatus` tracks `total_weight_approved`, `total_weight_rejected`, and `responded_signers` per block hash [1](#0-0) .

When a `Rejected` message arrives, the code adds the signer's weight to `total_weight_rejected` guarded by `block.responded_signers.insert(slot_id)`: [2](#0-1) 

When an `Accepted` message later arrives for the *same* block hash from the *same* slot, the guard used is `!block.gathered_signatures.contains_key(&slot_id)` — not `responded_signers`: [3](#0-2) 

Because the slot was never present in `gathered_signatures` (only in `responded_signers`, added by the earlier rejection), the later accept passes this check and adds the signer's weight to `total_weight_approved` as well. The signer's weight is now counted on both sides simultaneously — `total_weight_rejected` still contains it (nothing subtracts it), and `total_weight_approved` now also contains it.

This directly feeds the liveness/no-quorum heuristic: [4](#0-3) 
`total_weight_rejected.saturating_add(weight_threshold) > total_weight` is meant to detect "even in the best case, remaining unresponded weight cannot push this block over threshold." With one signer's weight double-booked, this arithmetic becomes wrong: the same weight is counted as "used up on the reject side" while it is *also* legitimately present on the approve side, understating the pool of weight that can still contribute to quorum and causing the check to fire earlier than it mathematically should.

The asymmetric handling is reinforced by `reset_rejections`, which explicitly documents that approvals are never cleared ("an old approval could always be used to make a block reach the approval threshold") but wipes `total_weight_rejected` and `responded_signers`, re-seeding `responded_signers` only from `gathered_signatures`: [5](#0-4) 
This shows the code author intended `responded_signers`/`gathered_signatures` to be reconciled so a signer can only occupy one side of the tally at a time — but the live message-processing loop for `Accepted` fails to enforce that, since it checks the wrong set (`gathered_signatures` instead of `responded_signers`).

### Impact Explanation
This is a liveness-class issue affecting the mining node's own bookkeeping of quorum progress, not a cryptographic forgery: the actual block push still requires real, verified signer signatures reaching `weight_threshold` via `gathered_signatures`, so no invalid/non-canonical block can be signed through this bug alone. The consequence is that a single Byzantine signer, by sending a `Rejected` message and later an `Accepted` message for the same proposal (both are legitimate, individually-valid StackerDB gossip messages, requiring no majority or extra privileges), can corrupt the coordinator's rejected/approved weight bookkeeping so the "block cannot possibly reach quorum" condition fires prematurely/incorrectly. Depending on how `signer_coordinator.rs` consumes this signal (abandoning/retrying the proposal), this can degrade block-production liveness for the affected proposal, forcing unnecessary re-proposals. It does not rise to "signer signing an invalid block" but matches a liveness-degradation profile.

### Likelihood Explanation
Likelihood is moderate-to-high: any single signer (no majority required) can trigger the double count merely by sending two StackerDB chunk messages (Reject then Accept) for the same block hash — an action fully within a rogue signer's normal message-sending capability, requiring only a valid signature over the block sighash (which a legitimate/eligible signer always can produce for a block it processes). No majority collusion, no auth token, and no node compromise is needed.

### Recommendation
In the `Accepted` branch, guard the weight addition using the same `responded_signers` set (or check `responded_signers.contains(&slot_id)` in addition to `gathered_signatures`) before adding weight to `total_weight_approved`, and ensure a signer's weight cannot be counted on both `total_weight_approved` and `total_weight_rejected` simultaneously — e.g., if a signer previously rejected, either reject the late accept for tallying purposes or explicitly subtract the previously-counted reject weight before adding to the approved tally.

### Proof of Concept
1. Node proposes block `B` with `signer_signature_hash = H`.
2. Malicious signer `S` (weight `W`) sends `BlockResponse::Rejected` for `H`. `StackerDBListener` records: `responded_signers += {S}`, `total_weight_rejected += W` (per lines 515-518 above).
3. Enough real weight has already rejected such that `total_weight_rejected + weight_threshold` is close to `total_weight` (or attacker repeats with several colluding-but-independent rejecting signers to approach the boundary).
4. Signer `S` then sends a legitimately-signed `BlockResponse::Accepted` for the same `H`. Since `gathered_signatures` does not yet contain `S`'s slot, the code adds `W` to `total_weight_approved` too (lines 443-465), while `S`'s weight remains counted in `total_weight_rejected` from step 2 (never removed).
5. Now `total_weight_rejected` includes `W` that is also present in `total_weight_approved`. The no-quorum-possible check (`total_weight_rejected + weight_threshold > total_weight`) can trip using this double-booked weight, even though the actual remaining unresponded weight might still be sufficient to reach `weight_threshold`, causing the coordinator to prematurely treat the block as unreachable for quorum.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
