### Title
Second withdraw request resets `lastWithdrawRequest`, letting a loss-haircutted receipt be re-claimed at par and draining unfunded basis - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.claimWithdrawRequest` applies a `stopEpochWithDuration` loss haircut only when `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` is set. Because `requestWithdraw` unconditionally overwrites `lastWithdrawRequest[_user]` with the *latest* request epoch and merges all pending receipts into the aggregate `withdrawsRequests[_user]`, a user who holds a receipt haircutted in an earlier epoch can simply file a second withdraw request in a later healthy epoch. The loss-adjusted path is then skipped entirely and `_claimFundedWithdrawRequest` pays the full aggregate — including the haircutted receipt — at par, even though the strategy only collected the reduced `pendingToFund` amount for that epoch. The attacker is paid the unfunded loss portion out of underlying reserved for other claimants.

### Finding Description
In `requestWithdraw`, every new request sets `lastWithdrawRequest[_user] = currentEpoch` and adds `_amount` to both `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` (IdleCreditVault.sol ~L282-293).

When `stopEpochWithDuration` realizes a loss on pending receipts, `previewLossAdjustedWithdrawFunds` reduces the amount pulled from the borrower to `pendingToFund`, `collectWithdrawFunds` sets `pendingWithdraws = 0` and stores `lossRecoveryPriceByEpoch[epochNumber] = funded/basis` (IdleCreditVault.sol L411-430, L440-460). The receipt's full basis remains in `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][lossEpoch]`.

On claim, `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest(_user)` first, which looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (L789-792). If the user made a second request after the loss epoch, `lastWithdrawRequest[_user]` is the *new* epoch, whose `lossRecoveryPriceByEpoch` entry is `0`, so the function returns early and the old receipt is never cleared via `_clearWithdrawClaimForEpoch` for the loss epoch. Execution falls through to `_claimFundedWithdrawRequest`, which after the epoch-wait gate pays `amount = withdrawsRequests[_user] + apr0 buckets` in full via `_transferFundedClaim` (L319-349) — paying the loss-epoch receipt at par.

The only guard in `_transferFundedClaim` protects `defaultRecoveryReserve`, not ordinary funded liquidity (L897-907), so the overpayment succeeds as long as the strategy holds any underlyings (e.g., funds pulled for other users' pending receipts).

### Impact Explanation
Direct theft / insolvency: the attacker extracts `claimBasis_lossEpoch - fundedAmount_lossEpoch` more than the haircutted receipt entitles them to. That shortfall is borne by other pending claimants or the vault's liquidity — later honest claims revert on insufficient balance or the pool's receipts become undercollateralized. Quantified loss equals the pro-rata loss share assigned to that receipt (`_lossAmount * pendingBasis / totalBasis` per receipt fraction), which can be a large fraction of a pending receipt when the manager passes a large legitimate `_lossAmount` at `stopEpochWithDuration`.

### Likelihood Explanation
Exploitable by any unprivileged tranche-token holder who files a normal withdraw request in an epoch that ends with a `stopEpochWithDuration(_lossAmount > 0)` (a supported partial-loss flow distinct from hard default — no privileged role needed; the loss parameter is an honest manager input reflecting borrower underpayment), then files a second request in the next epoch and waits one epoch. The merge-and-wait behavior is explicitly supported (`NOTE`: "if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests"), so no guard blocks the sequence. No skim, flag, or KYC check prevents it; `epochEndDate != 0 && epochNumber <= lastWithdrawRequest` only enforces the waiting period, which the attacker satisfies.

### Recommendation
Track loss-adjusted basis per request epoch rather than keying the haircut lookup solely on `lastWithdrawRequest`. Options:
- In `_claimLossAdjustedWithdrawRequest`, iterate/derive the loss epoch from `withdrawsRequestsByEpoch` (e.g., store `lossEpoch` per user or a per-epoch `lossRecoveryPriceByEpoch` flag consulted for each epoch with nonzero `withdrawsRequestsByEpoch[_user][e]`), clearing each loss-epoch receipt at its stored price before the funded claim pays the remainder.
- Alternatively, in `requestWithdraw`, revert if the user has an unclaimed receipt in an epoch with a nonzero `lossRecoveryPriceByEpoch` (forcing them to claim the haircutted receipt first), mirroring the existing post-default `postDefaultRequests` guard that requires claiming open prior receipts.

### Proof of Concept
Foundry fork PoC outline (against `IdleCDOEpochVariant` + `IdleCreditVault`, e.g., extending `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossReceiptReclaimedAtParViaSecondRequest() external {
    uint256 amount = 10_000 * ONE_SCALE;
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, amount, true);      // AA deposit, KYC'd test user

    // Epoch 0: normal epoch, stop with gain so request is instant/normal
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // Attacker files withdraw request -> receipt in epoch 1
    vm.prank(attacker);
    uint256 lossEpochClaim = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Epoch 1: manager stops with a partial loss (borrower underpays) via stopEpochWithDuration
    _startEpochAndCheckPrices(1);
    uint256 lossBasis = IdleCreditVault(address(strategy)).pendingWithdraws();
    // fund only pendingToFund + interest; compute pendingToFund via previewLossAdjustedWithdrawFunds
    (uint256 pendingToFund, ) = IdleCreditVault(address(strategy))
        .previewLossAdjustedWithdrawFunds(lossBasis / 2);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest() + pendingToFund);
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), type(uint256).max);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), lossBasis / 2);

    // Attacker files a SECOND request in epoch 2 (any small amount / remaining tranche balance)
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // overwrites lastWithdrawRequest -> epoch 2

    _startEpochAndCheckPrices(2);
    _stopEpochAndCheckPrices(2, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // Claim: lossRecoveryPriceByEpoch[2] == 0, so _claimLossAdjustedWithdrawRequest skips;
    // _claimFundedWithdrawRequest pays withdrawsRequests[attacker] (incl. epoch-1 basis) at par.
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balPre;

    // Expected entitlement for the epoch-1 receipt is lossEpochClaim * lossRecoveryPrice / 1e18.
    // Assert overpayment: paid exceeds sum of haircutted epoch-1 claim + par epoch-2 claim,
    // i.e. the strategy transferred underlying it never collected for the epoch-1 loss.
    assertGt(paid, lossEpochClaim * IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(1) / 1e18);
}
```

Caveat: I could not fully read `requestWithdraw`'s entry guard (lines ~250-282) to confirm it permits a second request while a loss-epoch receipt is unclaimed; the code comments explicitly document merge-and-wait semantics for repeated requests, and no per-epoch loss guard was observed, but the PoC should verify the second `requestWithdraw` does not revert in this configuration.
