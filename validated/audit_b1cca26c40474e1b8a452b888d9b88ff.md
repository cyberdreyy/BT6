### Title
Loss-adjusted withdrawal haircut applied only to the user's last request epoch — earlier pending receipts are paid at par, draining funded underlyings and freezing later claimants — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The `stopEpochWithDuration` loss path in `collectWithdrawFunds` computes a single `lossRecoveryPrice` over the **global** `pendingWithdraws` aggregate, i.e. every pending receipt in every request epoch is haircut. But `_claimLossAdjustedWithdrawRequest` only applies that haircut to the user's receipts recorded under `withdrawsRequestsByEpoch[_user][lastWithdrawRequest[_user]]`. Any earlier-epoch pending receipt of the same user stays in `withdrawsRequests[_user]` and is paid **at par** by `_claimFundedWithdrawRequest` in the very same call. The "one receipt one payout" / loss-waterfall invariant is broken, so the first claimer can extract more underlying than the strategy actually received, leaving insufficient funds for the remaining claimants (insolvency / permanent freeze of their claims).

### Finding Description
Relevant flow in `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` lets a user accumulate pending receipts across multiple epochs: `withdrawsRequests[_user] += _amount` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, while `lastWithdrawRequest[_user]` is overwritten with the *latest* request epoch (lines 282–293). The in-code comment at line 323 explicitly acknowledges this: "if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests."
- On a shortfall stop, `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` where `pendingBasis` is the **entire** `pendingWithdraws`, then sets `pendingWithdraws = 0` and stores `lossRecoveryPriceByEpoch[epochNumber]` (lines 411–429). Only `_amount` underlyings (the haircut total) are transferred in.
- On claim, `claimWithdrawRequest` runs `_claimLossAdjustedWithdrawRequest` then `_claimFundedWithdrawRequest` (lines 312–313). `_claimLossAdjustedWithdrawRequest` uses `lossEpoch = lastWithdrawRequest[_user]` and clears only `withdrawsRequestsByEpoch[_user][lossEpoch]` via `_clearWithdrawClaimForEpoch`, which subtracts just that epoch's amount from `withdrawsRequests[_user]` and resets `lastWithdrawRequest[_user] = 0` (lines 789–837).
- `_claimFundedWithdrawRequest` then passes its epoch gate (since `lastWithdrawRequest` is now 0) and pays the *remaining* `withdrawsRequests[_user]` — the older-epoch receipts — at full par via `_transferFundedClaim`, even though those receipts were included in the haircut basis and only funded at `lossRecoveryPrice` (lines 319–350, 897–907).

Net result: the user's payout is `lastEpochBasis * lossRecoveryPrice + olderBasis * 1.0`, while the strategy only received `totalBasis * lossRecoveryPrice`. The overpayment `olderBasis * (1 - lossRecoveryPrice)` is taken from underlyings earmarked for other claimants.

### Impact Explanation
Direct theft plus insolvency/permanent freezing. A user holding pending receipts in two or more epochs when a loss-adjusted `stopEpoch` occurs is overpaid by `(sum of his older-epoch pending basis) * (1 - lossRecoveryPrice)`. Because the strategy only holds `totalBasis * lossRecoveryPrice` underlying for all claimants of that epoch, every overpaid unit is a unit some other claimant cannot withdraw — their `claimWithdrawRequest` reverts in `_transferFundedClaim` once the balance is drained (the `balance - reserve < _amount` / `safeTransfer` path). For a pool with, say, 10M pending basis haircut to 70%, an attacker who staged 30% of the aggregate basis as "older-epoch" receipts extracts ~0.3 * 0.3 * 10M = 900k underlyings beyond his entitlement and freezes an equivalent amount of honest claims.

### Likelihood Explanation
- No privileged attacker is required. Any KYC-passing lender holding tranche tokens can create multi-epoch pending receipts by calling `requestWithdraw` in two different epochs without claiming in between — ordinary, documented user behavior.
- The trigger is a partial repayment at `stopEpoch`/`stopEpochWithDuration` (borrower returns less than owed without a full default). This is the designed loss path, not an edge case; the attacker does not need to cause it, only have staged receipts when it happens. Even without staging, any user who naturally accumulated receipts across epochs is overpaid at others' expense.
- The guard at lines 263–271 only blocks a *new* request while a previous **loss-adjusted** receipt is unclaimed; it does nothing for the first loss event, where multi-epoch receipts can already exist.
- The guard in `_transferFundedClaim` (reserve check) does not stop the first overpayment — it only causes later victims' claims to revert.

### Recommendation
Apply the loss haircut to the user's **entire** pending basis at the time of the loss epoch, not only the `lastWithdrawRequest` epoch. Concretely:

- In `_claimLossAdjustedWithdrawRequest`, when `lossRecoveryPriceByEpoch[lossEpoch] != 0`, compute `claimBasis` over all of the user's pending receipts (i.e. `withdrawsRequests[_user]` plus open APR0 principal/interest, or iterate/zero all `withdrawsRequestsByEpoch` entries) and burn the corresponding full receipt amount; or
- Record per-user pending basis snapshots at loss time (e.g. `lossAdjustedClaimsByEpoch[user][epoch] = withdrawsRequests[_user]` captured in `collectWithdrawFunds`-adjacent accounting) so the claim is unambiguous; and
- Alternatively, disallow new `requestWithdraw` while the user still has any unclaimed pending receipt (`_hasWithdrawRequest`), collapsing multi-epoch receipts entirely so `lastWithdrawRequest` is a safe sole index.

### Proof of Concept
Foundry fork sketch (extends the existing harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossAdjustedClaimPaysOldEpochAtPar() external {
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    address attacker = makeAddr('multi-epoch-user');
    address victim   = makeAddr('victim-user');
    uint256 amount = 10_000 * ONE_SCALE;

    _depositWithUser(attacker, amount, true);
    _depositWithUser(victim,   amount, true);

    // Epoch 0 runs and stops normally
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // Attacker: first request in epoch 1 buffer
    uint256 bal = IERC20Detailed(AAtranche).balanceOf(attacker);
    vm.prank(attacker);
    uint256 req1 = cdoEpoch.requestWithdraw(bal / 2, address(AAtranche));
    // Victim also requests, fully in the loss epoch
    vm.prank(victim);
    uint256 victimReq = cdoEpoch.requestWithdraw(IERC20Detailed(AAtranche).balanceOf(victim), address(AAtranche));

    _startEpochAndCheckPrices(1);   // epochNumber becomes 1
    _stopEpochAndCheckPrices(1, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // Attacker: second request in epoch 2 buffer (first still unclaimed -> allowed)
    vm.prank(attacker);
    uint256 req2 = cdoEpoch.requestWithdraw(IERC20Detailed(AAtranche).balanceOf(attacker), address(AAtranche));

    _startEpochAndCheckPrices(2);   // epochNumber becomes 2

    // Honest manager stops epoch 2 with a partial repayment: loss haircut on ALL pendingWithdraws
    // (stopEpochWithDuration / borrower returns _amount < pendingBasis -> collectWithdrawFunds sets
    //  lossRecoveryPriceByEpoch[2] = price < RECOVERY_FULL, pendingWithdraws = 0)
    // ... trigger loss stop via existing _stopEpochWithDuration-style helper ...

    uint256 price = creditVault.lossRecoveryPriceByEpoch(2);
    assertLt(price, RECOVERY_FULL);

    // Attacker claims: req2 is haircut, req1 is paid AT PAR -> overpaid vs funded amount
    uint256 pre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = IERC20Detailed(defaultUnderlying).balanceOf(attacker) - pre;
    assertApproxEqAbs(paid, req1 + req2 * price / RECOVERY_FULL, 5); // req1 at par = theft

    // Victim's claim now reverts / is underfunded: insolvency
    vm.expectRevert();
    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest();
}
```

The key assertions are: (a) the attacker's earlier-epoch receipt `req1` is paid at par despite being inside the haircut basis, and (b) a later claimant's `claimWithdrawRequest` reverts because the strategy no longer holds the funded underlyings.
