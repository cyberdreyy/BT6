### Title
EIP-8130 builder-time `WatchManifest` revalidation omits authorization-time code reads, allowing execution against post-approval bytecode drift - ([File: crates/execution/txpool/src/manifest.rs])

### Summary
Base's EIP-8130 admission path authorizes a transaction once at pool-validation time and snapshots the state it depended on into a `WatchManifest`, which the payload builder later replays with `manifest.revalidate()` immediately before folding the transaction into a block. That replay only re-checks storage slots (`config_slots`), payer balance, and expiry — it does not re-check the contract *bytecode* that `TransactionAuthorizer::authorize_and_apply` reads via `with_account_code` (e.g., for delegation-target validation). The pool's separate `watch_set` does track `InvalidationKey::CodeHash` entries for async re-validation, but the synchronous, authoritative gate that runs right before execution (`manifest.revalidate`) does not carry that information at all. This is the same bug class as GHSA-8g75-q649-6pv6: an approval decision is bound to only part of the mutable operand set, so a caller can get a shape approved and then let the unbound part (code content) drift before execution consumes it.

### Finding Description
`OverlayPrecompileStorage::with_account_code` records every address whose code is read during authorization into `self.code_reads` [1](#0-0) . In `validate_eip8130_full`, this set is captured as `authorization_code_reads` right after `TransactionAuthorizer::authorize_and_apply` runs [2](#0-1) , and it is folded only into the pool's `watch_set` as `InvalidationKey::CodeHash(address)` entries [3](#0-2) .

However, the `WatchManifest` that the builder actually gates on before execution is constructed from `config_reads` (storage slots) plus payer/expiry data only — `authorization_code_reads` is never passed into it [4](#0-3) . `WatchManifest::revalidate` correspondingly only checks `config_slots`, payer balance, and expiry; it has no notion of a code-hash predicate [5](#0-4) .

This manifest is the actual "approval binding" enforced immediately before a transaction is folded into a block: both the flashblocks context and the payload builder call `manifest.revalidate(...)` right before executing an EIP-8130 transaction, and rely on it to drop transactions whose authorization has gone stale [6](#0-5) [7](#0-6) . Since code reads are excluded from this predicate set, any authorization decision that depended on the bytecode at an address (for example, delegation-target validation performed via `with_account_code` during `authorize_and_apply`) is not re-verified at the point of actual execution.

### Impact Explanation
The pool's `watch_set` (async re-validation) does track code-hash changes, but that mechanism is best-effort/eventual — the payload builder's `manifest_precheck` is the synchronous, authoritative check run at the moment of inclusion, and it silently permits code-dependent authorization to go stale. An attacker who controls or can influence the bytecode at an address consulted during EIP-8130 authorization (e.g., a delegation target, or any address inspected via `with_account_code` in the authorization path) can:
1. Submit an EIP-8130 transaction that is authorized/admitted while that address's code satisfies whatever invariant the authorizer enforces.
2. Change that address's code (e.g., via a preceding transaction in the same block, or a race between pool admission and block building) before the transaction is executed.
3. Rely on the builder's `manifest.revalidate` to pass anyway, since it never inspects code hashes — resulting in the transaction being executed and its account-configuration effects (e.g., delegation install) applied against bytecode different from what was actually approved.

Depending on what invariant the authorization's code read enforces (this could not be fully confirmed from the available index — `crates/execution/eip8130/src/apply.rs`'s `with_account_code` call needs review), this can lead to an account-configuration/delegation installed under conditions the authorizer was supposed to prevent, i.e., an unauthorized account-configuration change — a concrete violation of the access-control guarantee EIP-8130 authorization is meant to provide.

### Likelihood Explanation
Reachable by any unprivileged transaction sender able to submit an EIP-8130 transaction whose authorization path touches code at an address they can also cause to change before block inclusion (e.g., via a same-block preceding transaction). No special privileges beyond normal transaction submission are required. The gap is structural (the manifest type simply has no field for code-hash predicates), not a narrow edge case, so it reproduces deterministically whenever authorization depends on code content.

### Recommendation
Extend `WatchManifest` to carry the authorization-time code-hash read-set (mirroring `ConfigSlot` for storage), populate it from `authorization_code_reads` in `validate_eip8130_full`, and have `WatchManifest::revalidate` reject the transaction if any watched address's code hash differs from what was observed at authorization time — symmetric to how `config_slots` and `payer_max_cost` are already handled. Audit `crates/execution/eip8130/src/apply.rs`'s `with_account_code` usage to confirm exactly what invariant it enforces, and verify no other authorization-relevant mutable read (nonce/account-info reads outside `config_reads`) is similarly excluded from the manifest.

### Proof of Concept
1. Submit EIP-8130 transaction `T` whose account-configuration change (e.g., a `Delegation`) causes `TransactionAuthorizer::authorize_and_apply` to read the code at address `X` via `with_account_code`, and which is admitted to the pool because `X`'s code currently satisfies the authorizer's invariant. The pool captures `T`'s `WatchManifest` with only `config_slots`/payer/expiry, omitting the read of `X`'s code.
2. Before `T` is included, get a different transaction included earlier in the same block (or race pool admission vs. block building) that changes the code at `X` (redeploy/self-destruct+recreate, or any account-configuration path that alters code) to a state that would have caused `T`'s authorization to fail or behave differently.
3. When the builder considers `T` for inclusion, `manifest.revalidate` only checks `config_slots`/payer/expiry — none of which reflect `X`'s code change — so `T` passes the precheck and is executed against the new, different code state, applying its account-configuration/delegation effect under conditions that would not have passed authorization against the current state.

    pub fn revalidate<DB: Database>(&self, db: &mut DB, now: u64) -> Result<(), ManifestStale> {
        if self.effective_expiry != u64::MAX && now > self.effective_expiry {
            return Err(ManifestStale::Expired { deadline: self.effective_expiry, now });
        }

        for slot in &self.config_slots {
            if let Ok(current) = db.storage(slot.address, slot.slot)
                && current != slot.expected
            {
                return Err(ManifestStale::ConfigSlotChanged {
                    address: slot.address,
                    slot: slot.slot,
                });
            }
        }

        if !self.payer_max_cost.is_zero()
            && let Ok(info) = db.basic(self.payer)
        {
            let available = info.map_or(U256::ZERO, |info| info.balance);
            if available < self.payer_max_cost {
                return Err(ManifestStale::PayerUnderfunded {
                    payer: self.payer,
                    required: self.payer_max_cost,
                    available,
                });
            }
        }

        Ok(())
    }
