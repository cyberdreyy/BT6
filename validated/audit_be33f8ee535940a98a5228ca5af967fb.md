### Title
BB tranche holders can dodge first-loss absorption by front-running a loss-bearing `stopEpochWithDuration` with a withdraw request — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`stopEpochWithDuration(_lossAmount)` applies a realized loss in two buckets: pending withdraw receipts take a **pro-rata** share via `previewLossAdjustedWithdrawFunds`, while the remainder hits active tranches through the **BB-first** waterfall. Because pending receipts do not retain tranche identity, a BB holder who calls `requestWithdraw` during the buffer phase converts a first-loss position into a blended-loss receipt, escaping subordination and shifting the avoided loss onto AA holders.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch`, when a `_lossAmount` is passed, the strategy computes the split: [1](#0-0) 

`pendingLoss = _lossAmount * pendingBasis / totalBasis` — every receipt in `pendingWithdraws` is haircut equally, regardless of whether it came from an AA or BB tranche. The leftover `activeLoss` is then burned and applied via `_forceUpdateAccounting()`, which uses the ordinary BB-first waterfall: [2](#0-1) 

Withdraw requests are only allowed while the epoch is **not** running — `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are set `false` in `startEpoch` and re-enabled after a successful `stopEpoch`: [3](#0-2) 

This creates the front-running window: during the buffer phase, a BB holder observes (or anticipates) borrower distress that will lead the manager to call `stopEpochWithDuration` with a `_lossAmount`. They call `requestWithdraw`, burning their BB tranches into a pending receipt. When the loss lands, their receipt only bears `pendingBasis / totalBasis` of it instead of absorbing it first. Loss-adjusted receipts are then claimed at `lossRecoveryPriceByEpoch`, which is identical for all receipts of that epoch: [4](#0-3) 

Concrete example: TVL 100 (90 AA / 10 BB), loss = 10. If the BB holder stays active, BB takes the full 10 loss and AA is untouched. If the BB holder requests withdraw first, `pendingBasis = 10`, `totalBasis = 100`, so the pending bucket takes only 1 of the loss; the remaining 9 falls on active positions BB-first — i.e., onto the 90 AA NAV once the (now smaller) active BB tranche is exhausted, or onto remaining BB holders who didn't front-run. The front-running BB holder loses 1 instead of 10.

Additionally, **AA holders who requested withdraw are harmed**: their receipts are haircut pro rata even though, had the loss been applied correctly, BB subordination should have absorbed it entirely.

### Impact Explanation
Direct redistribution of loss from subordinated BB holders to senior AA holders and other pending receipts. The broken invariant is the loss waterfall: tranche seniority is silently discarded the moment a position enters the pending bucket. Loss up to `pendingBasis * lossAmount / totalBasis` is misallocated per lossy stop epoch; if multiple BB holders do this, the effective BB buffer shrinks toward zero while nominally still existing.

### Likelihood Explanation
- Withdraw requests are open to any KYC'd tranche holder during every buffer phase — no privilege needed.
- The trigger is a predictable `_lossAmount` at `stopEpochWithDuration`. Manager honesty is assumed, but losses correlate with observable borrower distress (late repayment in prior epochs, off-chain credit events), so anticipatory withdrawal is realistic — the same reasoning the Celo report uses (rational actors shed exposed balances ahead of time).
- Partial mitigation: the attacker must hold BB exposure at request time, and pro-rata sharing means they still take some loss, so the dodge is a fraction rather than total. It is a repeatable value-transfer rather than a one-shot exploit.

### Recommendation
Record tranche class per pending receipt (e.g., `pendingWithdrawsAA`/`pendingWithdrawsBB` or per-epoch per-class bases) so `previewLossAdjustedWithdrawFunds` can apply the loss BB-first across the combined active+pending basis: BB pending receipts absorb loss before AA pending receipts and AA active positions. Alternatively, charge an estimated worst-case haircut at `requestWithdraw` time and refund at claim, or disallow BB withdraw requests while a loss is pending resolution.

### Proof of Concept
Foundry fork PoC sketch (mirroring `test/foundry/IdleCDOEpochQueue.t.sol:789-858` loss-adjusted claim setup):

```solidity
function testBBDodgesLossViaPendingWithdraw() public {
    // Setup: AA = 90e18, BB(attacker) = 10e18, epoch running normally.
    // 1. Epoch stops, buffer phase opens (allowBBWithdrawRequest == true).
    vm.prank(manager); cdoEpoch.stopEpoch(10e18, 0);
    // 2. Attacker converts BB position into a pending receipt during buffer.
    vm.prank(BB_USER); cdoEpoch.requestWithdraw(BB_USER_TRANCHES, address(bbTranche));
    // 3. Manager starts next epoch, then stops it with a loss of 10e18.
    vm.prank(manager); cdoEpoch.startEpoch();
    vm.warp(cdoEpoch.epochEndDate() + 1);
    // fund borrower for loss-adjusted repayment
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 activeBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(10e18);
    deal(address(underlying), strategy.borrower(), cdoEpoch.expectedEpochInterest() + pendingToFund);
    vm.prank(strategy.borrower()); underlying.approve(address(cdoEpoch), type(uint256).max);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, duration, 10e18);
    // 4. Assert: attacker receipt only lost pendingBasis/totalBasis of 10e18,
    //    while an AA pending/active holder absorbed loss meant for BB.
    uint256 price = strategy.lossRecoveryPriceByEpoch(strategy.epochNumber());
    assertGt(price, 0); // attacker haircut ≈10% instead of ~100% BB-first loss
}
```

Expected result: the attacker's claim pays out at the shared `lossRecoveryPriceByEpoch` (~90% recovery) instead of ~0%, and AA NAV/receipts carry the displaced loss — violating the BB-first invariant.
