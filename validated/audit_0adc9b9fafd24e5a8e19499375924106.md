Based on my research across the transaction-processing paths reachable by an unprivileged sender (RPC transaction decoding, wincode/packet deserialization, account loading/CPI data growth, and syscall memory translation), agave already enforces size limits before or incrementally during allocation rather than buffering unbounded attacker-controlled data first:

- `rpc/src/rpc.rs`'s `decode_and_deserialize` checks encoded and decoded lengths against `MAX_BASE58_SIZE`/`MAX_BASE64_SIZE`/`PACKET_DATA_SIZE`/`v1::MAX_TRANSACTION_SIZE` before calling `wincode::deserialize`. [1](#0-0) 
- `perf/src/packet.rs` configures wincode with a fixed `PACKET_DATA_SIZE` preallocation limit for all packet deserialization. [2](#0-1) 
- Account data growth during CPI/realloc is bounded per-account by `MAX_ACCOUNT_DATA_LEN`/`MAX_PERMITTED_DATA_LENGTH` and per-transaction by `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`, checked in `can_data_be_resized` before any resize occurs. [3](#0-2) 
- `svm/src/account_loader.rs`'s `load_transaction_accounts` accumulates `loaded_accounts_data_size` and calls `increase_calculated_data_size` after each account load, erroring out with `MaxLoadedAccountsDataSizeExceeded` as soon as the requested limit is exceeded, rather than deferring the check until an entire batch is fully materialized.

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }
