### Title
Unbounded job-controlled `CACHE_CHUNK_SIZE`/`CACHE_CONCURRENCY`/`CACHE_TRANSFER_BUFFER_SIZE` enable memory/connection exhaustion via cache-archiver/extractor - (File: `commands/helpers/cache_defaults.go`, `commands/helpers/cache_archiver.go`)

### Summary
`validateCacheTransferTuning` only rejects negative/zero values but places no upper bound on `TransferBufferSize`, `ChunkSize`, or `Concurrency`, all of which are settable by job-level CI variables (`CACHE_TRANSFER_BUFFER_SIZE`/`CACHE_CHUNK_SIZE`/`CACHE_CONCURRENCY`) per the documented feature. An unprivileged pipeline author can set these to very large values to force large buffer allocations (`buf := make([]byte, c.TransferBufferSize)`) and high multipart/range fan-out (`writerOpts.MaxConcurrency`, `ParallelRangeDownload` concurrency), consuming memory in the job's own process/container and opening many concurrent connections to the shared cache backend.

### Finding Description
`CacheArchiverCommand`/`CacheExtractorCommand` expose `TransferBufferSize`, `ChunkSize`, `Concurrency` as CLI flags with `env:"CACHE_TRANSFER_BUFFER_SIZE"`/`env:"CACHE_CHUNK_SIZE"`/`env:"CACHE_CONCURRENCY"` tags [1](#0-0) . These are documented as job-tunable variables that the `cache-archiver`/`cache-extractor` helpers read directly from the environment: "You can tune parallelism with these job environment variables" [2](#0-1) . The shell generator exports job variables into the script environment before invoking `cache-archiver`/`cache-extractor` as a subprocess [3](#0-2) , so a job's `variables:` block (fully attacker/pipeline-author controlled) reaches these fields.

`validateCacheTransferTuning` only checks for non-positive/negative values, with no upper bound: [4](#0-3) 

Downstream, `ChunkSize` becomes `writerOpts.BufferSize` and `Concurrency` becomes `writerOpts.MaxConcurrency` passed straight to `b.NewWriter`, and `TransferBufferSize` sizes a `make([]byte, ...)` copy buffer: [5](#0-4) 

Similarly on download, `Concurrency` and `ChunkSize` drive `transfer.ParallelRangeDownload` fan-out for both presigned-URL range GETs and GoCloud range reads [6](#0-5) , and the sequential path also allocates `make([]byte, c.TransferBufferSize)` [7](#0-6) .

No existing check caps these to sane maximums (e.g., a few hundred MiB / a few dozen concurrent connections); only negative/zero rejection exists, confirmed by the unit test which never exercises upper-bound rejection [8](#0-7) .

### Impact Explanation
A job can set e.g. `CACHE_CHUNK_SIZE=1073741824` (1 GiB) and `CACHE_CONCURRENCY=1000` with `FF_USE_PARALLEL_CACHE_TRANSFER=true`, causing the `cache-archiver`/`cache-extractor` helper to attempt allocation on the order of `ChunkSize * Concurrency` (potentially many GiB) and to open up to `Concurrency` simultaneous multipart-upload parts or range requests against the shared object storage backend (S3/GCS/Azure) used by the shared runner fleet. This can OOM-kill the helper/job container or, on shell executors, degrade the shared runner host process; simultaneously it produces a large connection/request fan-out against the shared cache bucket, which can throttle or degrade cache availability for other tenants sharing that backend and its per-account rate limits.

### Likelihood Explanation
High feasibility: the attacker only needs to set CI/CD job `variables` (a normal pipeline author capability, no special runner or project privileges beyond ability to define/modify `.gitlab-ci.yml` or protected/unprotected pipeline variables) and enable `FF_USE_PARALLEL_CACHE_TRANSFER`, which is itself a feature flag settable via job variables in many runner configurations. Reproducible on every job run that defines a cache and these variables; no race conditions or timing dependency involved.

### Recommendation
Add upper-bound clamping/rejection in `validateCacheTransferTuning` (or `normalizeArgs`/`normalizeExtractorArgs`) for all three parameters — e.g., cap `TransferBufferSize`/`ChunkSize` to a fixed maximum (such as 64–128 MiB) and `Concurrency` to a fixed maximum (such as 32–64), rejecting or clamping values beyond that instead of passing arbitrary job-supplied integers straight into `blob.WriterOptions`/`transfer.ParallelRangeDownload`.

### Proof of Concept
```go
func TestValidateCacheTransferTuning_RejectsExcessiveValues(t *testing.T) {
    // Currently these all pass validation with no upper bound — expected: should error.
    err := validateCacheTransferTuning(1<<30, 1<<30, 100000)
    require.Error(t, err, "expected huge transfer tuning values to be rejected, but validateCacheTransferTuning accepted them")
}
```
Integration PoC: run a job with `variables: {FF_USE_PARALLEL_CACHE_TRANSFER: "true", CACHE_CHUNK_SIZE: "1073741824", CACHE_CONCURRENCY: "1000"}` and a `cache:` block on a GoCloud-backed shared cache; observe the `cache-archiver` process's RSS and outbound connection count spike proportionally to `ChunkSize * Concurrency`, and assert (via memory/connection monitoring) that it exceeds a safe bound that a single tenant should not be able to trigger.

```go
func validateCacheTransferTuning(transferBufferSize, chunkSize, concurrency int) error {
	if transferBufferSize <= 0 {
		return fmt.Errorf("invalid cache transfer buffer size %d (CACHE_TRANSFER_BUFFER_SIZE / --transfer-buffer-size): must be positive; use 0 for default %d bytes",
			transferBufferSize, defaultCacheTransferBufferSize)
	}
	if chunkSize < 0 {
		return fmt.Errorf("invalid cache chunk size %d (CACHE_CHUNK_SIZE / --chunk-size): must be non-negative; use 0 for default %d bytes",
			chunkSize, defaultCacheChunkSize)
	}
	if concurrency < 0 {
		return fmt.Errorf("invalid cache concurrency %d (CACHE_CONCURRENCY / --concurrency): must be non-negative", concurrency)
	}
	return nil
```

```go
func TestValidateCacheTransferTuning(t *testing.T) {
	t.Parallel()

	require.NoError(t, validateCacheTransferTuning(
		defaultCacheTransferBufferSize,
		defaultCacheChunkSize,
		defaultCacheConcurrency,
	))

	require.NoError(t, validateCacheTransferTuning(1, 0, 0))

	err := validateCacheTransferTuning(0, defaultCacheChunkSize, defaultCacheConcurrency)
	require.Error(t, err)
	require.Contains(t, err.Error(), "transfer buffer size")

	err = validateCacheTransferTuning(-1, defaultCacheChunkSize, defaultCacheConcurrency)
	require.Error(t, err)
	require.Contains(t, err.Error(), "transfer buffer size")

	err = validateCacheTransferTuning(defaultCacheTransferBufferSize, -1, defaultCacheConcurrency)
	require.Error(t, err)
	require.Contains(t, err.Error(), "chunk size")

	err = validateCacheTransferTuning(defaultCacheTransferBufferSize, defaultCacheChunkSize, -1)
	require.Error(t, err)
	require.Contains(t, err.Error(), "concurrency")
}
```
