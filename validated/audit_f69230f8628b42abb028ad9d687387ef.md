### Title
Stale confirmations from a deleted multisig key are still counted toward `num_confirmations`, allowing execution of a request below the live-key threshold - (File: `multisig/src/lib.rs`)

### Summary
The `DeleteKey` action in `multisig/src/lib.rs` removes a public key from the multisig's `num_requests_pk` map and revokes the on-chain access key, but it only purges `confirmations` for requests that were *originally created* by the deleted key. It never scrubs the deleted key from the `confirmations` set of *other* pending requests that key had merely confirmed. Because `confirm` counts entries in that stale `HashSet<PublicKey>` without checking key liveness, a request can later be executed after receiving fewer live confirmations than `num_confirmations` actually requires — mirroring the reported analog where a recorded voting/confirmation credit no longer matches the entity actually holding that power.

### Finding Description
`add_request`/`confirm` store confirmations as a `HashSet<PublicKey>` keyed only by request id: [1](#0-0) 

`confirm` simply checks `confirmations.len() as u32 + 1 >= self.num_confirmations` and executes once threshold is reached — there is no re-validation that the public keys already present in the set are still active multisig members.

The `DeleteKey` action, however, only cleans up requests whose *original signer* (`r.signer_pk`) is the deleted key, and removes only *those* requests' confirmation sets: [2](#0-1) 

Confirmations that the deleted key placed on *other* requests (i.e., requests it did not create but merely confirmed) are never removed from `self.confirmations`. `num_requests_pk` and the on-chain access key are cleaned up, but the stale entry inside another request's `confirmations` `HashSet<PublicKey>` persists indefinitely.

The equality that should hold is:
`confirmations counted for request X == number of currently-live members who approved X`

After a `DeleteKey` action removes a member who had confirmed some other still-pending request X, this becomes:
`confirmations counted for request X > number of currently-live members who approved X`

### Impact Explanation
This lets a request execute (transfer funds, add/delete keys, deploy code, arbitrary `FunctionCall`) with fewer live confirmations than `num_confirmations` mandates, effectively lowering the k-of-n threshold without any of the remaining members explicitly re-approving. This is a Critical-class impact per the rules ("a multisig request executed below threshold"), since it can be leveraged to move funds or grant a new key with weaker-than-configured authorization.

### Likelihood Explanation
Requires two members' worth of ordinary multisig activity (creating/confirming requests, and later removing a member) — no privileged role beyond being an existing key holder, and no protocol misconfiguration. Key removal (e.g., off-boarding a member, or rotating a compromised key) is a normal, expected multisig operation, and any request left pending with a partial confirmation from that key at removal time becomes exploitable this way.

### Recommendation
When executing `DeleteKey`, iterate over all pending requests (not just those originated by the deleted key) and remove the deleted public key from every request's `confirmations` set. Alternatively, when counting confirmations in `confirm`, filter the stored set against the current valid key set (e.g., cross-check against `num_requests_pk` or an explicit active-keys collection) before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig` with `num_confirmations = 2` and keys `A`, `B`, `C`.
2. Key `C` calls `add_request` to create request `X` (e.g., a `Transfer`). `confirmations[X] = {}`.
3. Key `B` calls `confirm(X)`. Since `len()+1 (1) < 2`, it just records: `confirmations[X] = {B}`.
4. Separately, members reach threshold on a `DeleteKey { public_key: B }` request/action (via the normal `add_request_and_confirm`/`confirm` flow), executing `execute_request` with the `DeleteKey` branch shown above — this removes `B`'s own originated requests (none exist) and calls `promise.delete_key(B)`, but does **not** touch `confirmations[X]`.
5. Key `A` calls `confirm(X)`. `confirmations[X].len() (1) + 1 = 2 >= num_confirmations (2)` → `execute_request(X)` runs, even though `B` is no longer a valid key and only one live member (`A`) actually approved `X`. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
