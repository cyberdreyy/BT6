### Title
Rebasing underlying rewards are swept to `feeReceiver` as "donations" and permanently lost to depositors - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
`IdleCDOEpochVariant` deliberately treats the entire raw `token` balance held by the CDO as a donation and sweeps it to `feeReceiver` via `_skimDonatedAssets()` on every user interaction (`_deposit`, `requestWithdraw`, `depositDuringEpoch`, `startEpoch`, `stopEpoch`, `finalizeDefault`, `updateAccounting`). Tranche NAV and mint/burn pricing only account strategy tokens plus managed underlyings, so if the vault's `token` is a positive-rebasing asset (stETH, aToken-style, yield-accruing pool currency), every rebase that lands on the CDO between interactions is silently confiscated to `feeReceiver`, and rebase that accrues inside `IdleCreditVault` is stranded because claims and receipts pay fixed tracked amounts.

### Finding Description
The credit vault is the direct analog of the reported `EnjoyoorsVaultDeposits._deposit` bug: user value is tracked internally (strategy tokens minted 1:1, tranche shares priced off `lastNAV*`/`getContractValue`) while the real ERC20 balance can grow independently via rebases.

Key mechanics:

- `getContractValue()` counts `strategyToken` balance plus raw `token` balance minus `unclaimedFees`, but `virtualPrice`/`tranchePrice` price tranches off managed value; raw underlying is intentionally excluded from what users can claim (`contracts/IdleCDOCreditVault.sol:125-137`).
- `_skimDonatedAssets()` moves *the whole* `token` balance of the CDO to `feeReceiver` (`contracts/IdleCDOEpochVariant.sol:794-796`), and it is invoked at the top of `_deposit`, `requestWithdraw`, `depositDuringEpoch`, `startEpoch`, `stopEpoch`, `updateAccounting`, and `finalizeDefault` (`IdleCDOEpochVariant.sol:644-649, 739-747, 656-679, 233-242, 353-355, 157-161, 194-197`).
- There is no way to distinguish "unsolicited donation" from "positive rebase on users' in-flight underlying". Any balance growth while underlying transits the CDO (buffer phase between user `transferFrom` and `strategy.deposit()`, the `stopEpoch` pull from the borrower before redispatch, instant-withdraw funding) is classified as a donation.
- On the strategy side, `IdleCreditVault` mints/burns receipts at fixed tracked amounts (`withdrawsRequests`, `apr0Users`, `defaultRecoveryReserve`); `_transferFundedClaim`/`_transferDefaultRecovery` pay exact amounts, so rebase that accrues on `underlyingToken.balanceOf(strategy)` is never credited to any user or receipt (`contracts/strategies/idle/IdleCreditVault.sol:897-917`). Only the owner `transferToken` rescue can move it, i.e., it never reaches users through any protocol path.

Broken invariant: fair mint/burn / donation isolation. The skim mechanism assumes raw `token` balance is only ever "donations"; for a rebasing pool currency it is users' accrued yield, and it is permanently redirected to `feeReceiver` (CDO side) or stranded (strategy side). The protocol cannot detect or distribute it proportionally — exactly the "track shares, not absolute amounts" failure of the report.

### Impact Explanation
Permanent loss/theft of unclaimed yield for all depositors whenever the configured `token` rebases upward. Quantified loss per sweep = `rebaseDelta = token.balanceOf(cdo)` accrued since the last interaction; over an epoch this is `principal * rebaseRate * timeInContract`, repeating every buffer/epoch cycle. Depositors receive only the fixed-APR interest the borrower pays; the asset's native yield is fully expropriated to `feeReceiver` with no recovery path for users (owner `transferToken` exists only on the strategy, not the CDO, and routed donations are already gone).

### Likelihood Explanation
Medium. It requires the vault to be deployed with a rebasing pool currency — a plausible configuration since `initialize()` accepts any ERC20 (`IdleCreditVault.sol:124-140`). Once configured, no attacker action is needed; the loss is systematic and occurs on every interaction, identical in nature to the reported bug (the report itself recommends "explicitly prohibit rebasing tokens" — this codebase has no such prohibition or wrapped-token guard).

### Recommendation
Either prohibit rebasing underlyings at factory/initialization time (or document and enforce wrapped variants such as wstETH), or credit raw-balance growth to users: snapshot the expected underlying balance attributable to in-flight deposits/repayments and sweep only `balance - expected` to `feeReceiver`, folding the remainder into NAV (`getContractValue`/tranche price) so rebases distribute pro rata. On the strategy, periodically fold `underlyingToken.balanceOf(this) - (fundedClaims + defaultRecoveryReserve)` into claimable value instead of stranding it.

### Proof of Concept
```solidity
// test/foundry/RebaseSkim.t.sol — fork of the existing IdleCreditVault.t.sol harness
// using a rebasing mock as `defaultUnderlying` (mint extra balance = positive rebase).

function testRebaseOnCDOIsSweptToFeeReceiver() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // User deposits during buffer; underlying sits on the CDO before startEpoch forwards it
    idleCDO.depositAA(amount);

    // Simulate a positive rebase while funds sit on the CDO:
    // rebasing token credits +1% to every holder
    uint256 rebase = amount / 100;
    rebasingToken.rebase(address(cdoEpoch), rebase); // mock: mints rebase to holder

    uint256 feeBalPre = underlying.balanceOf(cdoEpoch.feeReceiver());
    uint256 pricePre  = cdoEpoch.virtualPrice(address(AAtranche));

    // Any unprivileged user interaction sweeps the rebase
    idleCDO.depositAA(ONE_SCALE);

    // The rebase went entirely to feeReceiver; users got nothing
    assertEq(underlying.balanceOf(cdoEpoch.feeReceiver()) - feeBalPre, rebase,
        "rebase confiscated as donation");
    // virtualPrice unchanged: the yield is gone from user NAV permanently
    assertEq(cdoEpoch.virtualPrice(address(AAtranche)), pricePre);
}

function testRebaseInStrategyIsStranded() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);           // CDO forwards to IdleCreditVault.deposit -> mints 1:1
    rebasingToken.rebase(address(strategy), amount / 100);

    // User requests full withdraw; claimable amount is the fixed tracked basis
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertEq(requested, amount);         // rebase not credited

    // After funding + claim, the rebase delta remains in the strategy with no
    // user-accessible path; only owner transferToken can extract it
    // ... (stopEpoch funding, claimWithdrawRequest)
    assertGt(underlying.balanceOf(address(strategy)),
             strategy.pendingWithdraws() + strategy.defaultRecoveryReserve());
}
```
