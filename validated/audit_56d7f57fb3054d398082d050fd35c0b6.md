### Title
Loss-adjusted withdraw receipts keyed to wrong epoch: first claimant over-paid at par, later claimants permanently frozen - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` stores the haircut ratio under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` is incremented inside `deposit()` while the epoch is still running (`epochNumber += 1` at lines 607–611), which happens during `stopEpochWithDuration` *before* the strategy collects the funded amount. A user who called `requestWithdraw` during the running epoch has `lastWithdrawRequest[user]` set to the pre-bump epoch. At claim time `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` — the old epoch key — finds 0, and skips the haircut. The receipt then falls through to `_claimFundedWithdrawRequest` and is paid at par, even though the strategy only received the loss-reduced aggregate. The first claimant drains the haircut pool; subsequent claimants' `safeTransfer` reverts on insufficient balance, permanently freezing their receipts.

### Finding Description
The bug chain:

1. During a running epoch (epochNumber = E), a lender calls `IdleCDOEpochVariant.requestWithdraw` → `IdleCreditVault.requestWithdraw`. This mints a strategy-token receipt, increases `pendingWithdraws`, and records `lastWithdrawRequest[_user] = E` and `withdrawsRequestsByEpoch[_user][E] += amount` (lines 259–294).

2. The honest manager calls `stopEpochWithDuration(apr, 0, duration, lossAmount)` after the borrower under-repays. Inside the stop flow, the CDO deposits received funds via `strategy.deposit()` while `isEpochRunning()` is still true, so `epochNumber` becomes E+1 (lines 607–611).

3. The CDO then calls `collectWithdrawFunds(pendingToFund)` where `pendingToFund < pendingBasis`. The recovery price is stored under the *new* epoch: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice`, i.e. key E+1, and `pendingWithdraws` is zeroed (lines 411–421). The strategy now holds only `pendingToFund`, less than the aggregate receipt basis.

4. When the user calls `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` computes `lossEpoch = lastWithdrawRequest[_user] = E` and reads `lossRecoveryPriceByEpoch[E]` = 0 → returns 0 (lines 789–795). The claim falls through to `_claimFundedWithdrawRequest`, whose freshness check `epochNumber <= lastWithdrawRequest[_user]` passes because E+1 > E (line 326). It pays `withdrawsRequests[_user]` in full at par (lines 338–349).

Because total `withdrawsRequests` exceeds the funded balance, claims are paid FCFS at par until the strategy balance is exhausted; the last claimant's `underlyingToken.safeTransfer` reverts with no recovery path — `withdrawsRequests` is never reduced for unclaimed users and no other function re-keys the stored price to epoch E.

Broken invariant: loss waterfall / fair burn — haircut loss is socialized only in the preview/accounting layer but never enforced on epoch-E receipts, producing over-payment for early claimants and permanent insolvency-driven freeze for the remainder.

Note on certainty: I verified `deposit()` bumps `epochNumber` while running and that the queue test (`testProcessWithdrawalClaimsWithZeroRoundedQueuePayout`) treats `strategy.epochNumber()` *after* stop as the claim epoch, consistent with the E+1 keying. I was not able to read `IdleCDOEpochVariant.stopEpochWithDuration` directly to confirm `collectWithdrawFunds` is invoked strictly after the epoch-bumping deposit, though the CDO must deposit repaid funds before collecting withdraw funding, so the ordering follows from the deposit flow.

### Impact Explanation
Direct theft plus permanent freezing. With e.g. 1000 USDC of epoch-E pending receipts and a 50% loss, the strategy receives 500 USDC but owes 1000 USDC of par-payable claims. Early claimants receive up to 2× their entitled recovery (theft of the recovery pool); the last claimant's `claimWithdrawRequest` always reverts, permanently freezing their receipt (~500 USDC unclaimable in this example, scaling with pending basis).

### Likelihood Explanation
Requires only a `stopEpochWithDuration` loss event with non-zero pending withdrawals — a designed-for code path (`previewLossAdjustedWithdrawFunds`, `collectWithdrawFunds`) — and at least one `requestWithdraw` opened during the running epoch rather than the buffer period. The attacker/victim needs no privileges; the borrower default or partial loss is the trigger, and no existing guard (`requestWithdraw`'s loss-epoch check reads the same wrong key, so it doesn't even block new requests) mitigates it.

### Recommendation
Key `lossRecoveryPriceByEpoch` to the epoch in which the receipts were created (the pre-bump epoch, e.g. `epochNumber - 1` or an explicit parameter from the CDO), or alternatively record `lastWithdrawRequest`/`withdrawsRequestsByEpoch` against the post-stop epoch. Add a consistency check in `collectWithdrawFunds` that all outstanding `withdrawsRequestsByEpoch` entries resolve to a non-zero recovery price.
