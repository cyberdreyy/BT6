### Title
Unbounded `Content-Range` total length causes memory-exhaustion DoS via `parallelDownloadRanges` chunk-slice construction - (File: helpers/transfer/parallel_download.go)

### Summary
`ParseContentRangeTotal` (helpers/transfer/content_range.go) parses the server-supplied `Content-Range` total into an `int64` with no upper bound other than `int64` range and `>0`. This value flows unchecked from `tryPresignedParallelDownload` into `downloadParallel` → `transfer.ParallelRangeDownload` → `parallelDownloadRanges`, which eagerly builds a slice of one `byteRange` entry per chunk before any goroutine runs, so a malicious/compromised cache backend returning `Content-Range: bytes 0-0/<huge N>` forces the runner process to allocate and iterate over hundreds of billions of slice entries, exhausting host memory/CPU.

### Finding Description
`ParseContentRangeTotal` only rejects malformed values, `*`, and `<=0`; any positive `int64` up to `math.MaxInt64` is accepted as valid `contentLength`: [1](#0-0) 

`tryPresignedParallelDownload` uses this value directly as `contentLength` for `downloadParallel` when `FF_USE_PARALLEL_CACHE_TRANSFER` is on and `Concurrency > 1`: [2](#0-1) 

`downloadParallel` passes `contentLength` straight into `transfer.ParallelRangeDownload` with the configured `chunkSize`: [3](#0-2) 

`ParallelRangeDownload` normalizes only `chunkSize`/`concurrency` (never caps `contentLength`), then calls `parallelDownloadRanges`, which loops `for offset := 0; offset < contentLength; offset += chunkSize` and appends a `byteRange` to a slice on every iteration — with no cap on iteration count: [4](#0-3) [5](#0-4) 

With `contentLength` near `math.MaxInt64` and a 16 MiB default chunk size, this loop produces on the order of 5.7×10^11 chunks. Even though the semaphore (`sem := make(chan struct{}, concurrency)`) throttles concurrent goroutine execution, the `chunks` slice itself is built to completion **before** the dispatch loop starts (`chunks := parallelDownloadRanges(contentLength, chunkSize)` at line 96, prior to the `for _, cnk := range chunks` loop), so the unbounded allocation/CPU cost of slice growth happens unconditionally regardless of concurrency, before any semaphore-based throttling can take effect. There is no existing check anywhere in this path (`ParseContentRangeTotal`, `tryPresignedParallelDownload`, `downloadParallel`, `normalizeParallelDownloadInputs`, `parallelDownloadRanges`) that bounds `contentLength` or the resulting chunk count against a sane maximum (e.g., available disk/memory, or a hard cap like a few million chunks).

### Impact Explanation
A crafted/attacker-influenced HTTP response feeding a fabricated `Content-Range` header can cause the runner (or its helper) process handling `cache-extractor` to attempt to allocate a slice with hundreds of billions of elements, consuming gigabytes of memory and CPU cycles just to build the loop, before any network chunk fetch occurs. This is a denial-of-service against the runner host process that executes `cache-extractor` (typically the job's execution context/helper), potentially crashing or severely degrading it — impacting the current job at minimum, and depending on execution model (shared runner host resources), other concurrently-running jobs on the same host.

### Likelihood Explanation
This requires: (1) `FF_USE_PARALLEL_CACHE_TRANSFER=true`, (2) `Concurrency > 1` (both are runner/job configuration values, not strictly restricted to admin-only settings — `Concurrency`/`ChunkSize` are exposed as CLI/env-configurable fields of `CacheExtractorCommand`), and (3) the ability to control or intercept the HTTP response feeding the primary or alternate cache URL. I was unable to fully verify, within the available index, whether `AlternateURL`/`AlternateGoCloudURL` values are ever derived from data an unprivileged pipeline author can influence (e.g., via job/cache configuration) versus being strictly set by trusted GitLab backend/runner-side logic — the search only surfaced these fields' definitions and test usage in `commands/helpers/cache_extractor.go`, not their origin/wiring from job payloads. This is the key precondition gap that determines whether this bug is remotely reachable by an unprivileged CI job author versus only by whoever controls the primary cache backend URL (which in the presigned case is the "primary" URL itself, already treated as trusted infrastructure in the GitLab backend). If the primary/alternate cache URLs are entirely GitLab-backend-controlled and not attacker-influenceable inputs, this finding would not meet the "job-controlled/attacker-reachable" bar and would be out of scope (external service compromise only). Given this uncertainty, likelihood is assessed as **plausible only under confirmed attacker control of the responding cache endpoint**, which was not conclusively established from the code inspected.

### Recommendation
Bound `contentLength`/derived chunk count defensively regardless of source trust: e.g., in `ParallelRangeDownload`/`parallelDownloadRanges`, cap the number of chunks (compute `numChunks := (contentLength + chunkSize - 1) / chunkSize` and reject/clamp if it exceeds a sane maximum, such as a few hundred thousand), and/or cap `contentLength` itself against a configured maximum cache size before entering the parallel path in `tryPresignedParallelDownload` and `handleGoCloudURL`. Preallocate the `chunks` slice with `make([]byteRange, 0, numChunks)` only after validating `numChunks` against the cap, and return an explicit error instead of silently proceeding to an unbounded loop.

```go
func TestParallelRangeDownload_RejectsHugeContentLength(t *testing.T) {

	})

		t.Fatal("expected ParallelRangeDownload to reject unbounded contentLength, but it proceeded")
	}

func FuzzParseContentRangeTotal(f *testing.F) {
	f.Add("bytes 0-0/9223372036854775807")
	f.Fuzz(func(t *testing.T, totalStr string) {
		n, ok := ParseContentRangeTotal("bytes 0-0/" + totalStr)
		if ok && n > 0 {
			// Assert that feeding n into ParallelRangeDownload does not attempt
			// to build an unbounded chunk slice; expect a bounds error instead.
			err := ParallelRangeDownload(n, 16<<20, 16, nil, func(offset, length int64) (io.ReadCloser, error) {
				return nil, nil
			})
			if n > (1<<40) && err == nil { // arbitrary large threshold
				t.Fatalf("ParallelRangeDownload accepted unbounded contentLength=%d without a cap", n)
			}
		}
	})
}
```
Expected assertion: `ParallelRangeDownload` (and by extension `downloadParallel`/`tryPresignedParallelDownload`) must reject or clamp `contentLength` values that would produce an excessive chunk count, before allocating the `chunks` slice in `parallelDownloadRanges`.

```go
func normalizeParallelDownloadInputs(contentLength int64, chunkSize int64, concurrency int) (int64, int, error) {
	if chunkSize <= 0 {
		return 0, 0, fmt.Errorf("transfer: chunk size must be positive")
	}
	if chunkSize > contentLength {
		chunkSize = contentLength
	}
	if concurrency < 1 {
		concurrency = 1
	}
	return chunkSize, concurrency, nil
}

func parallelDownloadRanges(contentLength, chunkSize int64) []byteRange {
	var chunks []byteRange
	for offset := int64(0); offset < contentLength; offset += chunkSize {
		length := chunkSize
		if offset+length > contentLength {
			length = contentLength - offset
		}
		chunks = append(chunks, byteRange{offset, length})
	}
	return chunks
}
```

```go
func ParallelRangeDownload(contentLength, chunkSize int64, concurrency int, dest io.WriterAt, fetchChunk FetchChunk) error {
	chunkSize, concurrency, err := normalizeParallelDownloadInputs(contentLength, chunkSize, concurrency)
	if err != nil {
		return err
	}
	chunks := parallelDownloadRanges(contentLength, chunkSize)

	worker := &parallelRangeWorker{dest: dest, fetchChunk: fetchChunk}
	sem := make(chan struct{}, concurrency)
	var wg sync.WaitGroup

	for _, cnk := range chunks {
		wg.Add(1)
		sem <- struct{}{}
		go func(offset, length int64) {
			defer wg.Done()
			defer func() { <-sem }()
			worker.downloadChunk(offset, length)
		}(cnk.offset, cnk.length)
	}
	wg.Wait()
	return worker.firstErr
```
