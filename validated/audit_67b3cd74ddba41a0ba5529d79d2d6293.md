### Title
Missing zero-address validation in B-20 token `grantRole` allows the sole DefaultAdmin to be irrecoverably locked out - ([File: crates/common/precompiles/src/b20_asset/logic/v2.rs])

### Summary
The B-20 token precompile logic's `grant_role` / `grant_role_unchecked` functions accept an arbitrary `account: Address` and never reject `Address::ZERO`, unlike the token's transfer path which explicitly type-checks addresses via `NonZeroAddress`. This mirrors the reported NFTCollection.sol issue where ownership transfer is not validated against an invalid new owner, and lets a legitimate `DefaultAdmin` accidentally (or via a single crafted transaction) assign the role-admin capability to an address nobody controls.

### Finding Description
`grant_role_unchecked` sets the role bit and, for `DefaultAdmin`, bumps `role_member_count` for whatever `account` is passed, with no zero-address guard: [1](#0-0) 

The public `grant_role` entry point (reachable by any account holding the role-admin for the target role — by default `DefaultAdmin` for the `DefaultAdmin` role itself) only checks role-admin authorization, not the target account: [2](#0-1) 

Compare this to the transfer path, which explicitly wraps `from`/`to` in `NonZeroAddress` and rejects `Address::ZERO` before any state mutation: [3](#0-2) 

The same unguarded pattern exists in the asset V1 logic, and in both the stablecoin V1 and V2 logic: [4](#0-3) [5](#0-4) [6](#0-5) 

Once `DefaultAdmin` is granted to `Address::ZERO`, `role_member_count(DefaultAdmin)` becomes `2`. The "last admin" safety checks in `revoke_role` and `renounce_last_admin` only block a renounce/revoke when the count is exactly `1`: [7](#0-6) [8](#0-7) 

Because the zero address is counted as a "member" for these purposes, the real admin can now freely `revoke_role`/`renounce_role` their own `DefaultAdmin` membership (count is `2`, not `1`), leaving `Address::ZERO` as the sole holder of `DefaultAdmin`. Since no transaction can ever originate from `Address::ZERO`, the role-admin function (`set_role_admin`), all `grant_role`/`revoke_role` calls gated by `DefaultAdmin`, and `update_supply_cap` (also gated by `DefaultAdmin`) become permanently unreachable for that token: [9](#0-8) [10](#0-9) 

Notably, the factory itself is aware that a zero admin is meaningless and guards against it at creation time: [11](#0-10) 

but that same guard is absent from the general-purpose `grant_role` entry point used post-deployment, so the vulnerable path remains open for the entire life of a deployed token.

### Impact Explanation
If `Pause`/`Unpause` role administration also traces back to `DefaultAdmin` (the default role-admin for all roles unless reassigned via `set_role_admin`), losing the last functioning `DefaultAdmin` permanently forecloses the ability to grant/revoke/re-admin any role on that token — including `Unpause`. A token already paused for `TRANSFER`/`MINT`/`BURN` at the time of the mistake can never be unpaused again, and no new privileged accounts (mint, burn, seize, metadata) can ever be appointed. This is a permanent freeze of core token functionality (and potentially of user funds if transfers are paused), reachable from a single unprivileged-relative-to-protocol but privileged-relative-to-token transaction sequence (`grantRole(DEFAULT_ADMIN_ROLE, address(0))` followed by `revokeRole`/`renounceRole` of the real admin).

### Likelihood Explanation
This requires the current `DefaultAdmin` to submit two transactions (or be tricked/scripted into doing so): a `grantRole` call with `account = address(0)` and a subsequent self-revoke/renounce. This is analogous to the original ownership-transfer report's "can happen due to user error" framing — a straightforward operational mistake with no built-in guard, unlike the codebase's own transfer path which does defend against it via `NonZeroAddress`.

### Recommendation
Reject `Address::ZERO` as the `account` parameter in `grant_role` / `grant_role_unchecked` for all B-20 asset and stablecoin logic versions (V1 and V2), consistent with the `NonZeroAddress` pattern already used for `transfer`/`transferFrom`. Additionally, consider excluding `Address::ZERO` from `role_member_count` accounting entirely so it can never satisfy or subvert the "last admin" safety checks.

### Proof of Concept
1. Deploy a B-20 asset/stablecoin token via the factory with `initialAdmin = ADMIN` (grants `DefaultAdmin` to `ADMIN`, `role_member_count(DefaultAdmin) == 1`).
2. `ADMIN` calls `grantRole(DEFAULT_ADMIN_ROLE, address(0))` — succeeds because `grant_role_unchecked` performs no zero-address check; `role_member_count(DefaultAdmin)` becomes `2`.
3. `ADMIN` calls `renounceRole(DEFAULT_ADMIN_ROLE, ADMIN)` — succeeds because `role_member_count != 1` at check time (see `renounce_role`/`revoke_role_unchecked` in [12](#0-11) ), leaving `Address::ZERO` as the sole `DefaultAdmin`.
4. Any subsequent call requiring `DefaultAdmin` (e.g., `setRoleAdmin`, `grantRole`/`revokeRole` for other roles, `updateSupplyCap`) reverts with `AccessControlUnauthorizedAccount` for every real caller, and can never succeed again since no one can transact as `address(0)`.

    fn grant_role_unchecked(
        &self,
        token: &mut B20AssetToken<S, A>,
        role: B256,
        account: Address,
        sender: Address,
    ) -> Result<()> {
        if token.accounting().has_role(role, account)? {
            return Ok(());
        }
        token.accounting_mut().set_role(role, account, true)?;
        if role == B20TokenRole::DefaultAdmin.id() {
            let current = token.accounting().role_member_count(role)?;
            let next =
                current.checked_add(U256::ONE).ok_or_else(BasePrecompileError::under_overflow)?;
            token.accounting_mut().set_role_member_count(role, next)?;
        }
        token
            .accounting_mut()
            .emit_event(IB20::RoleGranted { role, account, sender }.encode_log_data())
    }

    fn renounce_last_admin(&self, token: &mut B20AssetToken<S, A>, caller: Address) -> Result<()> {
        let admin_role = B20TokenRole::DefaultAdmin.id();
        B20Guards::ensure_role(token, caller, admin_role)?;
        if token.accounting().role_member_count(admin_role)? != U256::ONE {
            return Err(BasePrecompileError::revert(IB20::NotSoleAdmin {}));
        }
        self.revoke_role_unchecked(token, admin_role, caller, caller)?;
        token
            .accounting_mut()
            .emit_event(IB20::LastAdminRenounced { previousAdmin: caller }.encode_log_data())
    }

    fn update_supply_cap(
        &self,
        token: &mut B20StablecoinToken<S, A>,
        caller: Address,
        new_cap: U256,
        privileged: bool,
    ) -> Result<()> {
        if !privileged {
            B20Guards::ensure_token_role(token, caller, B20TokenRole::DefaultAdmin)?;
        }
        let supply = token.accounting().total_supply()?;
        if new_cap < supply || new_cap > B20_MAX_SUPPLY_CAP {
            return Err(BasePrecompileError::revert(IB20::InvalidSupplyCap {
                currentSupply: supply,
                proposedCap: new_cap,
            }));

        let old = token.accounting().supply_cap()?;
        token.accounting_mut().set_supply_cap(new_cap)?;
        token.accounting_mut().emit_event(
            IB20::SupplyCapUpdated { updater: caller, oldSupplyCap: old, newSupplyCap: new_cap }
                .encode_log_data(),
        )
    }
