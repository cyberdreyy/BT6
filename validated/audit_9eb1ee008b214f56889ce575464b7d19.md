### Title
Incomplete secret redaction blacklist causes sensitive credentials to be logged in plaintext - (File: core/web/router.go)

### Summary
Chainlink's HTTP request logging middleware (`loggerFunc`) sanitizes JSON request bodies before writing them to the node's debug logs, but the redaction filter only matches keys containing the substring `"password"`. Any other sensitive field name (e.g. `secret`, `token`, `apiKey`, `clientSecret`, embedded credentials inside a job spec TOML blob, etc.) is written to the log stream unredacted. This mirrors the pattern in the external report — sensitive credentials being persisted/exposed in an insecure, unencrypted store (there, `QSettings`; here, the node's debug log file) — because the protection mechanism does not cover all classes of secrets.

### Finding Description
`loggerFunc` reads every incoming request body and passes it to `readBody` → `readSanitizedJSON`, which redacts only keys present in a hardcoded `blacklist` map or containing the substring `"password"`: [1](#0-0) 

The same `isBlacklisted` function is also used to redact query-string values via `redact`: [2](#0-1) 

This logging wrapper is applied globally to authenticated web-server routes, and the sanitized request body is written at `Debug` level along with method, path, and client IP: [3](#0-2) 

Because the blacklist enumerates only password-related keys (`password`, `newpassword`, `oldpassword`, `current_password`, `new_account_password`), any JSON field named `secret`, `token`, `apiKey`, `apiSecret`, `clientSecret`, `outgoingToken`, or any nested/embedded secret value inside a larger blob field (such as the `toml` job-spec body accepted by `jobs_controller.go`, or fields on `bridge_types_controller.go` / `external_initiators_controller.go`) passes through `readSanitizedJSON` untouched and is written to the node's log file or log-shipping pipeline in cleartext.

This is directly analogous to the reported issue: sensitive material (there, an RPC password; here, API/bridge/job secrets) is captured by a general-purpose persistence/output mechanism (`QSettings` vs. the node's log sink) that was not designed with confidentiality guarantees, and the allow/deny-list approach to redaction is incomplete rather than a deny-by-default (redact-everything-except-known-safe-fields) approach.

### Impact Explanation
Any authenticated node-API user (not necessarily an admin — e.g. an `edit` or `run` role user submitting a job spec, bridge, or external-initiator request) who includes a non-password-named secret in a request body will have that secret written to the node's plaintext debug logs. Chainlink node logs are frequently shipped to centralized logging/observability infrastructure (e.g., via `AuditLogger.ForwardToUrl`, log files, or third-party log aggregation), widening the blast radius beyond the local machine. This is analogous to, but broader than, the original report's plaintext-QSettings issue, since it affects any log consumer rather than just local filesystem access.

### Likelihood Explanation
Any endpoint using `c.ShouldBindJSON` with a field not literally containing "password" is affected. Concretely, `core/web/jobs_controller.go` accepts a raw `toml` job spec string that can embed API keys/tokens for external adapters or bridges, and `core/web/bridge_types_controller.go` / `core/web/external_initiators_controller.go` accept structured request bodies that could carry secret-like fields in future or custom deployments. Because the middleware runs unconditionally on all matched routes, exploitation only requires an authenticated user (of any role permitted to hit these endpoints) submitting a request containing a non-"password" secret field — no special privilege escalation is required to trigger the disclosure into logs.

### Recommendation
- **Short term:** Change `isBlacklisted` to a deny-by-default policy: redact any field whose value looks like a secret/URL-with-credentials, or redact everything except an explicit allow-list of known-safe field names, rather than matching only "password"-like keys. At minimum, extend the blacklist to include `secret`, `token`, `apikey`, `clientsecret`, `authorization`, and recursively sanitize nested objects/arrays.
- **Long term:** Avoid logging raw request bodies altogether for endpoints that can carry credentials (jobs, bridges, external initiators); instead, log a structured summary omitting free-form/opaque blobs (e.g., `toml`), and rely on the existing `logger/audit` package for auditable, field-scoped events rather than full-body debug logs.

### Proof of Concept
1. As an authenticated node-API user with `edit`/`run` role, send a request whose JSON body contains a key not covered by the blacklist, e.g.:
   ```
   POST /v2/bridge_types
   {"name":"myadapter","url":"http://adapter.local","secret":"super-secret-api-key"}
   ```
2. With `Log.Level = 'debug'` (a supported, non-default but legitimate node configuration), the node's log output will contain the full sanitized-but-unredacted body, e.g.:
   ```
   "body":"{\"name\":\"myadapter\",\"url\":\"http://adapter.local\",\"secret\":\"super-secret-api-key\"}"
   ```
   because `"secret"` does not match `isBlacklisted` in [4](#0-3) .
3. Anyone with access to the node's log files or log-aggregation pipeline (which may be a broader audience than those with direct database/API access) can recover the plaintext secret.

**Note on confidence:** I was unable to locate a currently shipped, first-party API field literally named `secret`/`token` accepted via `ShouldBindJSON` on a truly unprivileged-reachable endpoint (existing bridge/external-initiator/job request DTOs largely avoid such field names, and password-named fields are already covered). The root-cause gap in the redaction logic is concretely verified in code, but the concrete end-to-end "secret disclosed via logs" scenario depends on either (a) a job spec TOML embedding a credential, or (b) any future/custom field not literally containing "password" — this should be validated against the currently deployed request/response DTOs before treating it as a confirmed, exploitable-today vulnerability rather than a defense-in-depth gap.

func redact(values url.Values) string {
	cleaned := url.Values{}
	for k, v := range values {
		if isBlacklisted(k) {
			cleaned[k] = []string{"REDACTED"}
			continue
		}
		cleaned[k] = v
	}
	return cleaned.Encode()
}

// NOTE: keys must be in lowercase for case insensitive match
var blacklist = map[string]struct{}{
	"password":             {},
	"newpassword":          {},
	"oldpassword":          {},
	"current_password":     {},
	"new_account_password": {},
}

func isBlacklisted(k string) bool {
	lk := strings.ToLower(k)
	if _, ok := blacklist[lk]; ok || strings.Contains(lk, "password") {
		return true
	}
	return false
}
