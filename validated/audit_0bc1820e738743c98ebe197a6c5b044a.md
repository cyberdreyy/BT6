### Title
Nested VM image allowlist check runs on unexpanded image string, bypassed via CI variable expansion - (File: executors/internal/autoscaler/acquisition.go)

### Summary
The `instance` executor validates `options.Build.Image.Name` against `Instance.AllowedImages` before variable expansion, but `acquisitionRef.createVMTunnel` later expands that same string with `options.Build.GetAllVariables().ExpandValue(image)` and uses the *expanded* value to request a nested VM from the nesting daemon, with no second allowlist check. A pipeline author can set `image: $SOME_VAR` and define `SOME_VAR` as a normal (unprotected) CI/CD variable to make the runner boot a nested VM image that was never validated against `allowed_images`.

### Finding Description
`executors/instance/instance.go` `Prepare()` performs the allowlist check like this: [1](#0-0) 

Note `Image: options.Build.Image.Name` — the **raw, unexpanded** job image string is checked with `common.VerifyAllowedImage` (`doublestar.Match` glob matching) against `Instance.AllowedImages`.

Immediately after this check passes, `Prepare()` calls `environment.Prepare(...)` → `acquisitionRef.Prepare` → `acquisitionRef.createVMTunnel`: [2](#0-1) 

Here `image` is set from `options.Build.Image.Name` again (same raw string, since `mapJobImageToVMImage` is `true` for the instance executor per `executors/instance/instance.go` `NewProvider` config), but it is then expanded with job-controlled CI/CD variables via `ExpandValue`, and the **expanded** result is passed directly to `nc.Create(ctx, image, &slot)` — the nesting daemon RPC that actually creates/attaches the nested VM. There is no re-validation of the expanded string against `AllowedImages` anywhere in this path.

Because glob matching in `VerifyAllowedImage` operates on the literal (unexpanded) string, an attacker only needs the literal placeholder (e.g. `$INJECTED_IMAGE`) to satisfy the configured pattern — which is trivial for common configurations such as `allowed_images = ["*"]` (shown as the documented example in `docs/executors/instance.md` for nested-VM setups), and is possible for many other single-segment/glob patterns as well, since `$` is not treated specially by `doublestar.Match`.

Exploit flow:
1. Runner configured with `executor = "instance"`, `autoscaler.vm_isolation.enabled = true`, and some `instance.allowed_images` list.
2. Pipeline author (unprivileged, controls `.gitlab-ci.yml` and job-level `variables:`) sets `image: "$INJECTED_IMAGE"` and defines `INJECTED_IMAGE` to any string of their choosing.
3. `instance.go` `Prepare()` validates the literal string `"$INJECTED_IMAGE"` against `AllowedImages` — passes trivially for wildcard/generic patterns.
4. `acquisitionRef.createVMTunnel` expands `image` using `options.Build.GetAllVariables().ExpandValue(image)`, producing the attacker-chosen value, with zero further allowlist enforcement.
5. `nc.Create(ctx, image, &slot)` requests that arbitrary, unvalidated image name from the nesting daemon.

### Impact Explanation
This is a real allowlist bypass: the operator-configured `allowed_images` restriction that is supposed to constrain which nested VM images a job can request is checked against the wrong (pre-expansion) string, so it does not actually constrain the image ultimately used to create the nested VM. If the nesting host has other VM images/snapshots available to the nesting daemon (e.g., other configured or cached images that were not intended to be job-selectable), a job can request them despite `allowed_images` being configured to deny that image name. This breaks the "runner-enforced restrictions on images ... must hold against user-controlled input" invariant.

### Likelihood Explanation
Preconditions are narrow but realistic and fully within scope: `executor = "instance"` with `vm_isolation.enabled = true` (a documented, supported configuration for GitLab Runner on macOS/Apple Silicon and other nested-virtualization setups), and a job author able to set CI/CD variables and the `image:` keyword — both of which are standard unprivileged pipeline-author capabilities. No admin compromise or leaked credentials are required. The bypass is deterministic and repeatable for any `allowed_images` pattern that matches the literal placeholder text.

### Recommendation
Perform the `VerifyAllowedImage` check against the **expanded** image value (after `options.Build.GetAllVariables().ExpandValue(...)`), not the raw `Image.Name`, and ideally re-validate inside/near `createVMTunnel` right before calling `nc.Create`, so the value actually sent to the nesting daemon is the one that was checked. Alternatively, disallow variable expansion of `Image.Name` entirely for `vm_isolation`-enabled instance-executor configurations if a match-before-expand ordering can't be changed without wider refactors.

### Proof of Concept
Go unit test idea for `executors/instance/instance_test.go` (or as an autoscaler package test):
```go
func TestInstanceAllowedImages_BypassViaVariableExpansion(t *testing.T) {
    options := common.ExecutorPrepareOptions{
        Config: common.RunnerConfig{
            RunnerSettings: common.RunnerSettings{
                Instance: &common.InstanceConfig{
                    AllowedImages: []string{"*"}, // typical nested-VM config
                },
                Autoscaler: &common.AutoscalerConfig{
                    VMIsolation: common.VMIsolation{Enabled: true},
                },
            },
        },
        Build: &common.Build{
            JobResponse: common.JobResponse{
                Image: common.Image{Name: "$INJECTED_IMAGE"},
                Variables: common.JobVariables{
                    {Key: "INJECTED_IMAGE", Value: "forbidden/other-tenant-image", Public: true},
                },
            },
        },
    }

    // Step 1: allowlist check as done in instance.go Prepare — passes.
    err := common.VerifyAllowedImage(common.VerifyAllowedImageOptions{
        Image:         options.Build.Image.Name, // "$INJECTED_IMAGE"
        AllowedImages: options.Config.Instance.AllowedImages,
    }, logger)
    assert.NoError(t, err) // passes even though the real image was never vetted

    // Step 2: simulate acquisitionRef.createVMTunnel's expansion.
    expanded := options.Build.GetAllVariables().ExpandValue(options.Build.Image.Name)
    assert.Equal(t, "forbidden/other-tenant-image", expanded)

    // Assert: the actually-used image was never re-checked against AllowedImages,
    // proving the allowlist can be bypassed.
}
```
Expected assertions: the pre-expansion check passes for an attacker-supplied variable placeholder, and the post-expansion value used by `nc.Create` differs from what was validated and is not itself checked against `AllowedImages`, confirming the bypass.
