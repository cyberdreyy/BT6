### Title
Response cache key omits workflowID, causing cross-workflow HTTP response cache poisoning/staleness in Gateway HTTP capability - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The Gateway's HTTP Action response cache (`responseCache`) is documented as being workflow-scoped ("Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" per `core/services/gateway/handlers/capabilities/v2/README.md`), but the actual cache key derived from `OutboundHTTPRequest.Hash()` excludes `WorkflowID` entirely, keying only on method, URL, headers, body, and `WorkflowOwner`. Combined with the fact that `Set()` refuses to refresh an entry that has not yet expired, this reproduces the same bug class as the "outdated interest rate" report: a value (the cached HTTP response) that should be refreshed/validated per logical unit (workflow) is instead served stale/shared across units, because the code path that should scope/refresh it does not do so.

### Finding Description
`responseCache.Fetch` and `responseCache.Set` both key the cache purely off `req.Hash()`: [1](#0-0) [2](#0-1) 

The comment on the struct states the hash covers "method, URL, headers, body, workflowOwner" — notably omitting `WorkflowID`: [3](#0-2) 

This is confirmed by the test suite, which explicitly asserts that two requests differing only by `WorkflowID` produce the *same* hash, while differing `WorkflowOwner` produces different hashes: [4](#0-3) [5](#0-4) 

Yet the package README documents the opposite invariant — that caching is workflow-scoped to prevent cross-workflow leakage: [6](#0-5) [7](#0-6) 

The gateway path that reaches this cache is triggered by `HandleNodeMessage` → `makeOutgoingRequest`, processing an `OutboundHTTPRequest` unmarshalled directly from the DON node's message and passed straight into `Fetch`/`Set` without any workflow-scoping being added: [8](#0-7) 

Because `Set()` only writes into the cache when the existing entry `isExpiredOrNotCached` (i.e., it will not overwrite a live, unexpired entry even when the caller explicitly requested a fresh fetch and store), any workflow belonging to the same owner that hits the same method/URL/headers/body combination during the TTL window will receive the response captured by whichever workflow (potentially a different, unrelated workflow instance) populated the cache first — mirroring the reported bug class where a computed value is served without validating/refreshing the underlying state that should have invalidated it.

### Impact Explanation
Multiple concurrently-running workflow instances belonging to the same `WorkflowOwner` (a legitimate, real-world scenario — an owner deploying several distinct workflows) can silently share HTTP Action responses that were intended to be workflow-specific. A workflow with different logic/URLs generally won't collide, but any workflow issuing structurally identical outbound requests (same method/URL/headers/body — e.g., calling a shared internal API, webhook, or third-party endpoint with a fixed payload) will receive another workflow's cached response instead of its own fresh fetch, and vice versa. This breaks the documented workflow-isolation guarantee, degrading data integrity/response confusion for legitimate workflows and enables one workflow (compromised or by design) to populate a cache entry that is then served, unrefreshed, to a co-owned but independent workflow within the TTL window (default 10 minutes).

### Likelihood Explanation
Likelihood is moderate: it requires (a) two or more workflows under the same owner, (b) issuing outbound HTTP Action requests with identical method/URL/headers/body, and (c) `CacheSettings` enabling caching (`Store`/`MaxAgeMs`). This is plausible for owners running multiple workflow versions/instances that call the same fixed external endpoint (a common pattern for polling shared APIs), making accidental cross-workflow response reuse realistic even without adversarial intent, and requiring no privileged access beyond normal workflow node operation on the gateway.

### Recommendation
Include `WorkflowID` (or another workflow-execution-scoped identifier consistent with the documented isolation guarantee) in the cache key computed by `OutboundHTTPRequest.Hash()`, so entries are correctly isolated per workflow as the README specifies. Additionally, reconsider the `isExpiredOrNotCached` guard in `Set()` so that an explicit fresh-fetch-and-store request can update the cache entry rather than being silently dropped in favor of stale data.

### Proof of Concept
1. Workflow A (owner `0xOwner`) issues an `OutboundHTTPRequest{Method: "GET", URL: "https://svc/api", CacheSettings: {Store: true, MaxAgeMs: 600000}}` via the Gateway HTTP Action; the gateway fetches and caches the response under a key derived from method+URL+headers+body+`0xOwner` (no `WorkflowID`), per `response_cache.go`.
2. Workflow B (also owner `0xOwner`, but a different `WorkflowID`) issues the identical `OutboundHTTPRequest` shortly after.
3. Per `TestRequestHash`'s "having different workflowID results in same Hash" behavior, Workflow B's request hashes to the same cache key as Workflow A's, so `Fetch` returns Workflow A's cached response to Workflow B without making a new HTTP call — demonstrating the cross-workflow cache sharing that contradicts the documented workflow-scoped isolation.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

	var req gateway_common.OutboundHTTPRequest

	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{

		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
