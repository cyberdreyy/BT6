### Title
Loss-adjusted withdraw receipts bypass the haircut and claim at par because `collectWithdrawFunds` keys `lossRecoveryPriceByEpoch` to the post-increment `epochNumber` while receipts are keyed to the pre-increment `lastWithdrawRequest` epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The CVE bug class is a verification step (tag recomputation) that is silently skipped when an input-processing step is omitted (empty ciphertext), letting an unauthenticated value pass. The analog in `IdleCreditVault` is the partial-loss haircut for pending withdraw receipts: the loss price is stored under `lossRecoveryPriceByEpoch[epochNumber]` at `collectWithdrawFunds` time, but it is looked up under `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` at claim time. `epochNumber` is incremented inside `deposit()` during `stopEpoch` ("deposit done on stopEpoch ... epochNumber += 1", IdleCreditVault.sol:607-611), so a receipt created in the buffer of epoch N is haircutter under epoch N+1. `_claimLossAdjustedWithdrawRequest` reads price 0 for the user's epoch, returns early, and `_claimFundedWithdrawRequest` then pays the full un-haircut basis.

### Finding Description
- `requestWithdraw` stores `lastWithdrawRequest[_user] = currentEpoch` where `currentEpoch = epochNumber` read *before* the epoch ends (IdleCreditVault.sol:260-282).
- During `stopEpoch`, the strategy's `deposit()` callback runs while `isEpochRunning()` is still true and executes `epochNumber += 1` (IdleCreditVault.sol:607-611).
- `collectWithdrawFunds(_amount)` records a shortfall as `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` using the *already-incremented* epoch (IdleCreditVault.sol:411-421), and zeroes `pendingWithdraws` while only transferring `_amount` of underlying.
- At claim time, `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest`, which computes `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the pre-increment epoch — gets 0, and returns without applying the haircut (IdleCreditVault.sol:789-795).
- Execution falls through to `_claimFundedWithdrawRequest`, whose only gate is `epochNumber <= lastWithdrawRequest[_user]`; since `epochNumber` is now N+1 > N, it passes and pays `withdrawsRequests[_user]` in full via `_transferFundedClaim` (IdleCreditVault.sol:326-349).

The guard in `requestWithdraw` that blocks re-requesting while a loss-adjusted receipt is pending (IdleCreditVault.sol:263-271) also reads `lossRecoveryPriceByEpoch[lossEpoch]` and gets 0, so it does not stop anything — the same skipped-verification shape as the CVE.

### Impact Explanation
Direct theft from the strategy's funded withdraw reserve: the borrower funded only `pendingBasis * lossRecoveryPrice / 1e18`, yet the first claimer(s) to call `claimWithdrawRequest` receive the full pre-loss basis. Later claimants' receipts become unfundable (permanent freezing of unclaimed yield / insolvency for the remainder). Loss magnitude is `pendingBasis - fundedAmount` (the intended pending-receipt share of the realized loss), up to the entire pending bucket.

### Likelihood Explanation
Requires a `stopEpoch` with realized loss where `pendingWithdraws > 0` and the funded amount is below basis — i.e., the `stopEpochWithDuration`/loss path that is explicitly supported by `previewLossAdjustedWithdrawFunds` and `collectWithdrawFunds`. No attacker privilege is needed: any receipt holder simply calls `claimWithdrawRequest()` first after the epoch stops. The one assumption I could not fully verify within my iteration budget is the exact ordering of `deposit()` vs `collectWithdrawFunds` inside `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration`; if `collectWithdrawFunds` executes *before* the incrementing `deposit()`, the key matches and the bug does not trigger. The PoC below confirms or refutes this ordering.

### Recommendation
Key `lossRecoveryPriceByEpoch` to the epoch the receipts belong to rather than the mutated counter: capture `epochNumber` at the start of `stopEpoch` (before `deposit()` increments it), or store `lastWithdrawRequest` consistently against the same post-increment numbering. Alternatively, track an explicit `lossEpoch` for pending receipts at `collectWithdrawFunds` time using the request-epoch value recorded when the receipts were created, and have both `_claimLossAdjustedWithdrawRequest` and the `requestWithdraw` guard read that epoch.

### Proof of Concept
```solidity
// Foundry fork test (extend test/foundry/IdleCreditVault.t.sol helpers)
function testLossAdjustedReceiptClaimsAtPar() external {
    // deposit, start epoch 0, then requestWithdraw during buffer of epoch 0
    cdoEpoch.requestWithdraw(amount, address(AAtranche));      // lastWithdrawRequest[user] = 0
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();

    _startEpochAndCheckPrices(1);

    // borrower funds only part of pending: realized loss path
    uint256 funded = pending / 2;
    deal(defaultUnderlying, borrower, funded);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // or stopEpochWithDuration path that calls collectWithdrawFunds(funded < pending)

    // epochNumber is now 1; lossRecoveryPriceByEpoch[1] = 0.5e18
    // but user's lastWithdrawRequest is 0 -> price lookup misses
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 balPost = underlying.balanceOf(address(this));

    // BUG: receives full `pending` instead of `pending * 0.5e18 / 1e18`
    assertEq(balPost - balPre, pending);
}
```
Run against a mainnet fork; the assertion showing par payout (instead of the haircutted `pending/2`) confirms the skipped verification.
