### Title
Unprivileged APR=0 withdraw request permanently bricks `stopEpoch` once the manager sets a non-zero APR, freezing all vault funds - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external bug (CVE-2019-5163) is a FATAL-exit DoS: arbitrary attacker input triggers a hard-fail code path that kills the service. The closest idle-tranches analog is `prepareStopEpochWithApr0` in `IdleCreditVault`, which hard-reverts whenever `apr0TotalPrincipal != 0 && unscaledApr != 0`. Any KYC-passing lender can create `apr0TotalPrincipal` dust with a tiny `requestWithdraw` during an APR=0 epoch; after the honest manager later sets a normal non-zero APR via `setAprs`/`setAprsWithBuffer`, every `stopEpoch` call reverts — the epoch can never close and all LP funds are frozen.

### Finding Description
- `requestWithdraw` routes requests into the APR0 bucket whenever `unscaledApr == 0` and the pool is not closed: `if (unscaledApr == 0 && !isClosed) _requestWithdrawApr0(_amount, _user)` — this increments `apr0TotalPrincipal` by an arbitrary, attacker-chosen `_amount` with no minimum (`IdleCreditVault.sol:285-286`, `567-577`).
- `prepareStopEpochWithApr0`, invoked by the CDO inside `stopEpoch`, reverts unconditionally when `apr0TotalPrincipal != 0 && unscaledApr != 0` (`IdleCreditVault.sol:502-508`). `apr0TotalPrincipal` is only reset to 0 inside that same function (`line 540`), so the revert is self-reinforcing: while APR ≠ 0 the bucket can never be cleared.
- The attacker needs only a funded tranche position (a KYC-passing lender), then calls `requestWithdraw` during an epoch whose `unscaledApr == 0`. APR=0 epochs are a supported operating mode (the whole `apr0Users`/`apr0RateByEpoch` flow exists for them), and switching APR between epochs is routine manager behavior.
- Existing guards do not stop it: the `NotAllowed` revert is the vulnerability itself; KYC only gates deposits, not this path; there is no skim/flag that skips the stale bucket.

### Impact Explanation
All `stopEpoch` calls revert → the epoch cannot close → every active LP's funds and every pending withdraw receipt are frozen (the borrower also cannot be repaid/refinanced). Recovery requires the manager to detect the issue and call `setAprs(0, 0)` (or `setApr(0)` after `setAprs`), forcing `unscaledApr` back to 0 for a stop, then re-set the real APR — so this is a temporary freeze, not permanent loss, but it halts the entire vault for at least one forced-APR=0 stop cycle and can be repeated any time APR returns to 0.

### Likelihood Explanation
Requires a pool operating an APR=0 epoch (a real supported mode) plus a manager APR change — both normal operations. Attacker cost is one deposit + one dust `requestWithdraw` (a few wei of underlying). Medium likelihood.

### Recommendation
Decouple the stale-bucket guard from `stopEpoch`: when `unscaledApr != 0`, treat the APR0 bucket as settled at zero rate (clear `apr0TotalPrincipal` without reverting) or lazily migrate it into normal `withdrawsRequests`. Alternatively, cap `requestWithdraw` APR0 bookkeeping so the revert condition can't be reached, and always allow `stopEpoch` to proceed.

### Proof of Concept
Foundry fork PoC outline:
1. Deploy/fork `IdleCDOEpochVariant` + `IdleCreditVault` with `unscaledApr = 0` (APR=0 mode).
2. `vm.prank(kycLender)` → `idleCDO.depositAA(1e6)`, then `cdoEpoch.requestWithdraw(1, AATranche)` → `apr0TotalPrincipal == 1`.
3. Manager starts next epoch and calls `vault.setAprs(5e18, 5e18)` (honest APR change).
4. `vm.warp(epochEndDate + 1)`; `vm.prank(manager); vm.expectRevert(NotAllowed.selector); cdoEpoch.stopEpoch(0, 0)` → reverts on every call while `unscaledApr != 0`, freezing all deposited funds until the manager is forced to set APR back to 0.

Uncertainty: I could not view the full `stopEpoch` body in `IdleCDOEpochVariant.sol` to confirm `prepareStopEpochWithApr0` is called unconditionally in all variants (prefunded/programmable paths may skip it), and I could not rule out that this guard is a previously acknowledged design decision in audit notes.
