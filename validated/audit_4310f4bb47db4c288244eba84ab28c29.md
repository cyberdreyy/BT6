### Title
Unbounded activity-refresh via repeated same-height pre-commit conflicts stalls miner-inactivity fallback - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_latest_block_in_tenure` credits "miner activity" (`update_last_activity_time`) whenever an incoming proposal conflicts with a block the signer has only *pre-committed* to, and unlike the analogous credit for conflicts with a fully *signed* block, this pre-commit-conflict branch has no `reorg_attempts_activity_timeout`-style cap. A miner who keeps submitting fresh, distinct, same-height (or lower) candidate blocks faster than `tenure_last_block_proposal_timeout` can keep every signer's `last_activity_time` perpetually fresh, so `is_timed_out`/`check_miner_inactivity` never fires and `make_miner_state` fallback to the prior tenure never triggers, even though `has_signed_block_in_tenure` correctly reports no signature was ever produced.

### Finding Description
`SortitionState::is_timed_out` (v1: `stacks-signer/src/chainstate/v1.rs:55-94`, v2: `stacks-signer/src/chainstate/v2.rs:48-89`) correctly excludes pre-committed-only blocks from "signed" status via `SignerDb::has_signed_block_in_tenure` (`stacks-signer/src/signerdb.rs:1511-1516`) — this is the fix the regression tests (`stacks-signer/src/signerdb.rs:4093-4148`, `stacks-signer/src/chainstate/tests/v2.rs:717-746`) pin down, and it works as intended: a tenure with only pre-commits is correctly eligible to time out.

However, `is_timed_out` also gates on `elapsed > block_proposal_timeout` measured from `get_last_activity_time`, which is written only by `update_last_activity_time` (`stacks-signer/src/signerdb.rs:2249-2257`), called from exactly two branches inside `check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:376-478`):

1. Conflict with a **signed** tip (lines 390-419): activity credit is explicitly bounded — `info.signed_group.is_none_or(|signed_time| signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs())`. Once `reorg_attempts_activity_timeout` elapses past the signed block, further conflicting proposals stop refreshing activity.
2. Conflict with a **pre-committed-only** block (lines 422-448): activity credit is gated only by `is_fresh_pre_commit`, i.e. whether the *existing* pre-commit's `approved_time` is still within `tenure_last_block_proposal_timeout`. There is no overall cap analogous to `reorg_attempts_activity_timeout`.

Because `mark_pre_committed` (`stacks-signer/src/signerdb.rs:272-277`) stamps a *fresh* `approved_time` on each new distinct block that reaches pre-commit (`self.approved_time.get_or_insert(get_epoch_time_secs())` on a brand-new `BlockInfo`), an attacker-miner who repeatedly proposes new, distinct, valid-looking blocks at the same (or lower) chain height in the same tenure — each one individually validated OK by the node and pre-committed by each signer per `handle_block_validate_ok` (`stacks-signer/src/v0/signer.rs:1946-1984`) — keeps `is_fresh_pre_commit` true forever. Each such conflicting proposal reruns `check_latest_block_in_tenure`, hits branch 2, and calls `update_last_activity_time` with no long-run cap. As long as the attacker submits a new competing proposal more often than `tenure_last_block_proposal_timeout` (default 30s), every signer's `last_activity_time` for that tenure is refreshed indefinitely, so `is_timed_out` never returns `true`, `check_miner_inactivity` (`stacks-signer/src/v0/signer_state.rs:284-374`) never falls into the fallback branch, and `make_miner_state` is never invoked to switch to the prior tenure — this matches exactly the wedge the question describes, and existing guards (`has_signed_block_in_tenure` correctly excluding pre-commits, the `reorg_attempts_activity_timeout` cap on the *signed*-conflict path) do not cover this pre-commit-conflict path.

This requires no signer collusion: each signer independently validates the miner's proposal against its own node and its own signer DB; a legitimately-signed, correctly-extending competing block will independently pass validation and reach `PreCommitted` state on every honest signer, satisfying `pre_committed_block_does_not_veto_replacement` (`stacks-signer/src/chainstate/tests/v2.rs:958-1040`), which explicitly documents that a same-height competing proposal both passes the check and updates activity time — confirming the mechanism is intentional for a single "slow" proposal, but the code contains no bound preventing indefinite repetition.

### Impact Explanation
This breaks the liveness guarantee that a stalled tenure (never producing a globally/locally signed block) must eventually time out and fall back to the prior valid tenure. A single unprivileged miner, holding the winning sortition slot, can indefinitely deny the fallback path by feeding a steady stream of distinct, individually-valid competing block proposals, keeping the tenure alive from the signers' point of view while never producing a signable/canonical block. This matches the High-severity category: "a signer wedged into never signing valid blocks (liveness)." It is repeatable indefinitely as long as the attacker keeps mining/submitting proposals within the `tenure_last_block_proposal_timeout` cadence.

### Likelihood Explanation
Preconditions: attacker wins a single sortition (normal, unprivileged cost — win their own BTC-block bid), and gossips a stream of distinct, well-formed `BlockProposal`s at the current tenure height (or below), each needing to pass real stacks-node block validation (real cost, but ordinary miner capability, no special access). No majority-signer control, no compromised keys, no auth_token needed — only gossip of proposals a signer normally consumes. The attack is bounded practically by proposal-construction/validation throughput but not by any protocol-level cap, since the pre-commit-conflict activity-credit path has no `reorg_attempts_activity_timeout`-style ceiling. This is straightforwardly reproducible in a unit/integration test driving `check_latest_block_in_tenure` and `is_timed_out` in a loop.

### Recommendation
Apply an overall cap to the pre-commit-conflict activity-credit branch in `check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:422-448`) analogous to `reorg_attempts_activity_timeout` used for the signed-conflict branch — e.g., bound the credit relative to the *first* pre-commit's timestamp for the tenure (or the burn-block-received time), not the most recently refreshed `approved_time`, so that a sequence of never-completing pre-commits cannot indefinitely extend the inactivity window.

### Proof of Concept
Rust test plan (extends existing `stacks-signer` chainstate/signer_state test harness):
1. Set up a `SignerDb` and `ProposalEvalConfig` with small `tenure_last_block_proposal_timeout` (e.g. 2s) and `block_proposal_timeout` (e.g. 5s), as in `check_miner_inactivity_timeout` (`stacks-signer/src/tests/signer_state.rs:1021-1096`).
2. Insert a burn block / sortition and an initial `BlockInfo` marked `PreCommitted` for the tenure.
3. Loop: every `tenure_last_block_proposal_timeout / 2` interval, construct a new distinct `NakamotoBlock` at the same `chain_length`, wrap in `BlockProposal`→`BlockInfo`, call `SortitionData::check_latest_block_in_tenure` (asserting it returns `Ok(true)` — "not vetoed"), then `mark_pre_committed()` + `insert_block`.
4. After each iteration, assert `signer_db.get_last_activity_time(&tenure_id)` keeps advancing and `SortitionState::is_timed_out(...)` returns `false`, even though wall-clock elapsed time since the tenure's original burn-block receipt now exceeds `block_proposal_timeout`.
5. As a control, stop looping and assert that once refresh stops, `is_timed_out` eventually returns `true` — proving the wedge is caused specifically by the unbounded refresh, not a general timeout bug.
6. Recommend the same test be re-run after adding the proposed `reorg_attempts_activity_timeout`-style cap to branch 2, asserting `is_timed_out` becomes `true` despite continued spam once the cap elapses, and `check_miner_inactivity` then calls `make_miner_state` to fall back to the prior tenure.
