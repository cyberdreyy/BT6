### Title
pprof debug endpoints reachable by any authenticated user (including 'view' role), no admin-role check - (File: core/web/router.go)

### Summary
The `/v2/debug/pprof/*` routes (cmdline, heap, goroutine, profile, trace, symbol, allocs, block, mutex, threadcreate) are registered via `metricRoutes(authv2)` inside the `authv2` group that only requires `auth.Authenticate` (token or session), with no `auth.RequiresAdminRole`/`RequiresEditRole` wrapper applied, unlike every other sensitive admin-only route in the same file. This allows any authenticated node user, including one holding only the `view` role, to dump goroutine stacks, heap contents, and the process command line.

### Finding Description
In `core/web/router.go`, `v2Routes` builds `authv2` as a group requiring only `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` [1](#0-0) . Sensitive actions in that same group are explicitly locked down with role wrappers, e.g. `auth.RequiresAdminRole(uc.Index)` for `/v2/users`, `auth.RequiresAdminRole(ets.Create)` for `/v2/transfers`, and `auth.RequiresEditRole(...)` for bridge/external-initiator mutation routes [2](#0-1) .

However, the debug/metrics routes are mounted with a comment claiming this is intentional — `// Debug routes accessible via authentication` — and calling `metricRoutes(authv2)` with no role check at all: [3](#0-2) .

`metricRoutes` itself registers the standard Go `net/http/pprof` handlers directly with no additional guard: [4](#0-3) . These handlers include `pprof.Cmdline` (process argv, which for `chainlink node start -p <password>` can leak the literal keystore password argument, as documented in CLI usage/tests: [5](#0-4) ), `pprof.Handler("heap")` (memory contents, potentially private key material or decrypted secrets resident in memory), `pprof.Handler("goroutine")` (full stack traces, which can reveal argument values including secrets passed through function calls), and `pprof.Profile`/`pprof.Trace` (CPU/exec traces).

Because `authv2` accepts any of the four session roles (`view`, `run`, `edit`, `admin`) as long as authentication succeeds, and there is no per-route `RequiresAdminRole`/`RequiresEditRole`/`RequiresRunRole` wrapper on the `metricRoutes` group, a session or API token issued to a `view`-only user is sufficient to reach every pprof endpoint. This contradicts the pattern established for every other privileged action in the file and the stated design intent that debug endpoints should require the highest role.

Separately, `debugRoutes` (serving `/debug/vars` via `expvar`) is also gated by session authentication only, with no role check [6](#0-5) .

### Impact Explanation
A `view`-role authenticated user (the lowest privilege level in the RBAC model, intended only for read-only access per `auth.RequiresEditRole`'s explicit exclusion of `UserRoleView` [7](#0-6) ) can retrieve full heap dumps, goroutine stack traces, and CPU/execution traces of the running node process, and the process command line via `pprof.Cmdline`. Depending on how the node/CLI was started (e.g., `-p <password>` on the command line as shown in the txtar test fixtures), this can leak the plaintext master keystore password, which in turn can be used offline to decrypt exported key files, and heap/goroutine dumps can incidentally contain decrypted private key material or in-flight secrets. This maps to the "server credential/key theft" bounty impact class since it discloses secrets from a running node to a user who should only have read access to job/run resources.

### Likelihood Explanation
Low precondition: any valid session or API token with `UserRoleView`, the weakest role grantable, is sufficient — no operator/admin/edit/run privileges are needed. The routes are always registered when the node's web server starts (`v2Routes` is unconditionally called from `NewRouter`), so this is reachable on every deployed node without any special configuration. The attack is trivially repeatable — simple authenticated GET requests to `/v2/debug/pprof/cmdline`, `/v2/debug/pprof/heap`, `/v2/debug/pprof/goroutine`, etc.

### Recommendation
Wrap all handlers registered in `metricRoutes` (and the `/debug/vars` route in `debugRoutes`) with `auth.RequiresAdminRole`, consistent with other sensitive/administrative endpoints in `v2Routes`. Alternatively, move debug/pprof endpoints out of the general authenticated API surface entirely and bind them only to a separate internal-only listener/port not exposed to ordinary API clients, matching the deliberate separation already used for the internal LOOP plugin pprof proxy (`loop_registry.go`) which forwards to a plugin-only port.

### Proof of Concept
Go handler-level integration test plan (extending the existing RBAC test pattern in `core/web/auth/auth_test.go`):
1. Add `/v2/debug/pprof/cmdline`, `/v2/debug/pprof/heap`, `/v2/debug/pprof/goroutine`, `/v2/debug/pprof/profile?seconds=0`, `/v2/debug/pprof/trace?seconds=0` entries to the `routesRolesMap` table (or a new dedicated test) with `viewOnlyAllowed: false` (the expected/secure value).
2. In `TestRBAC_Routemap_ViewOnly`, create a `cltest.User{Role: sessions.UserRoleView}`, obtain an authenticated HTTP client via `app.NewHTTPClient(u)`.
3. Issue `GET` requests to each pprof path.
4. Assert expected (secure) behavior: `resp.StatusCode == http.StatusForbidden`.
5. Run against current code: assert this fails — the actual current behavior returns `http.StatusOK` (or 200 with data payload) instead of `403`, proving the view-role user can reach the debug data, confirming the vulnerability.
6. Optionally add a byte-content assertion decoding the pprof cmdline response and confirming it contains process `os.Args` content, to demonstrate concrete secret/command-line disclosure.

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
