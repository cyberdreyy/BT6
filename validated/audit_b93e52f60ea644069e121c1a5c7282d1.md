### Title
Every sync deposit/mint relocks a receiver's entire unit balance, allowing indefinite re-freezing of already-vested funds - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2._syncDeposit` unconditionally overwrites `userUnitsRefundableUntil[receiver]` to `block.timestamp + depositRefundTimeout` on every `deposit`/`mint` call, regardless of the receiver's pre-existing (already fully-unlocked) unit balance. Because `MultiDepositorVault._update` and the `redeem`/`withdraw` sync-exit paths gate on this single global timestamp rather than on a per-deposit amount, a small, repeated deposit can keep relocking a user's entire, previously-unlocked unit balance forever — the same "unlock delayed infinitely by normal interaction" root cause as the disclosed Flat Money `PointsModule._setMintUnlockTime` finding.

### Finding Description
`deposit()`/`mint()` in `v3/src/core/ProvisionerV2.sol` (lines 170-229) both call `_syncDeposit(token, tokensIn, unitsOut, receiver)`, which does:
```solidity
uint256 refundableUntil = block.timestamp + depositRefundTimeout;
...
userUnitsRefundableUntil[receiver] = refundableUntil;
``` [1](#0-0) 

This mapping is not scoped to the newly minted units; it is a single per-user timestamp checked globally:
- `MultiDepositorVault._update` blocks *any* outgoing transfer for `from` while `areUserUnitsLocked(from)` is true [2](#0-1) 
- `areUserUnitsLocked` simply checks `userUnitsRefundableUntil[user] >= block.timestamp` [3](#0-2) 
- `redeem()`/`withdraw()` (sync exits) also gate on `userUnitsRefundableUntil[msg.sender] < block.timestamp` before allowing any exit [4](#0-3) [5](#0-4) 

Because the timeout is reset on every call, not accumulated/weighted by amount as in the referenced report, the effect is even stronger: a single 1-wei-equivalent deposit fully re-locks 100% of a user's pre-existing, already-unlocked balance for another full `depositRefundTimeout` period. As long as new small deposits keep arriving before the previous lock expires, the timestamp is perpetually pushed forward and the user's older units — which had already cleared the refund window and should be freely transferable/redeemable — are locked again. This mirrors exactly the broken invariant in the referenced report: "points/units that have already passed their unlock condition become locked again due to routine, expected user interaction," rather than being scoped per-tranche.

This can occur purely from the receiver's own repeated deposits (self-inflicted, but a normal, expected interaction with no privileged role required), or from any depositor address a user has approved via `setDepositReceiverApproval` (also a normal, non-privileged permission) repeatedly depositing tiny amounts on the user's behalf.

### Impact Explanation
Users' entire unit balance (not just the newest tranche) can be kept perpetually non-transferable and non-sync-redeemable by an unprivileged party (self or an approved depositor) performing trivial-cost deposits before each `depositRefundTimeout` window expires. This is a temporary/indefinite freeze of already-vested user funds — matching Immunefi Medium severity for temporary freezing of user funds, since the async redeem path (`requestRedeem`/`solveRequestsVault`/`solveRequestsDirect`) is not gated by this lock and remains available, capping worst-case severity at Medium (temporary freeze) rather than permanent loss.

### Likelihood Explanation
No privileged role, oracle, guardian, or solver collusion is required. The trigger is calling the plain, publicly reachable `deposit`/`mint` functions repeatedly with minimal token amounts before the existing `depositRefundTimeout` elapses — an ordinary, low-cost transaction sequence any depositor (self, or an address approved via `setDepositReceiverApproval`) can execute indefinitely.

### Recommendation
Scope the refund lock to the specific deposited tranche instead of overwriting a single global per-user timestamp — e.g., track locked amount alongside the unlock timestamp (similar fix as recommended for the referenced report), or only extend the lock proportionally/only for the newly deposited units, so that once a portion of a user's balance has crossed its own `depositRefundTimeout`, it becomes permanently transferable regardless of subsequent unrelated deposits.

### Proof of Concept
1. On a local fork, deploy/borrow existing `ProvisionerV2` + `MultiDepositorVault` with a nonzero `depositRefundTimeout` (e.g., 1 day).
2. `deposit()` a normal amount as `receiver = alice`. Note `userUnitsRefundableUntil[alice] = t0 + 1 day`.
3. Warp to `t0 + 23 hours` (before lock expiry) and call `deposit()` again with a trivial `tokensIn` (e.g., smallest unit that clears `minUnitsOut`), receiver `alice`. Assert `userUnitsRefundableUntil[alice]` is now `t0 + 23h + 1day`, i.e., pushed forward again.
4. Repeat step 3 every ~23 hours indefinitely; assert `MultiDepositorVault.transfer` from `alice` always reverts with `Aera__UnitsLocked` and `redeem/withdraw` from `alice` always revert, even though alice's original deposit is far past its original 1-day window.
5. Contrast with a scenario where no further deposits occur: after `t0 + 1 day`, transfers/redeem succeed — demonstrating the lock is trivially perpetuated by routine deposit activity rather than tied to the specific vested tranche.

        // Requirements: deposit hash is not set

        // Effects: set receiver's refundable until timestamp
