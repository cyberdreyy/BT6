### Title
ProgrammableBorrower accepts zero-value ERC4626 shares, allowing vault share inflation to steal pool principal - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower._depositToVault` deposits underlying into the configured ERC4626 vault but accepts the returned share amount without validating that it represents the deposited assets. If the vault is exposed to first-depositor/share-inflation rounding, an unprivileged vault user can make the borrower adapter deposit pool principal for zero or nearly worthless shares and then redeem the pool’s underlying.

### Finding Description
`onStartEpoch` parks all available underlying in `vault` through `_depositToVault` and records the pre-deposit total as `epochStartVaultAssets`. [1](#0-0)  `_depositToVault` calls `vault.deposit(_assetAmount, address(this))` and only emits the returned `shares`; it never checks `shares != 0`, compares it with `previewDeposit`, or verifies that `convertToAssets(shares)` covers the deposit. [2](#0-1) 

An attacker who is also a user of the external ERC4626 vault can first mint one share for one unit, then directly transfer `D` underlying to the vault. When `ProgrammableBorrower` subsequently deposits `D`, a floor-rounding vault mints `D / (D + 1) == 0` shares. The adapter still considers the operation successful, while `_currentVaultAssets()` later returns zero because the adapter holds no vault shares. [3](#0-2) 

The loss is then interpreted as vault PnL: `_vaultNetInterest` compares the recorded principal baseline with current vault assets plus withdrawals and reports a loss equal to the stolen deposit. [4](#0-3)  In minted-interest mode, `IdleCDOEpochVariant` does not pull principal at a normal stop, so the CDO’s strategy-token balance can continue to represent principal that the external vault has already paid to the attacker. [5](#0-4) 

### Impact Explanation
The attacker directly steals the deposited pool principal from the ERC4626 vault. A deposit of `D` underlying can be converted into zero adapter shares, after which the attacker redeems their inflated share for their donation plus the adapter’s `D`.

The vault accounting does not remove the corresponding CDO strategy-token exposure during a normal minted-interest epoch. When LPs later request withdrawals or the pool attempts to close, `onStopEpoch` cannot source the shortfall because the adapter’s vault position is zero. [6](#0-5)  The eventual `transferFrom` fails and the CDO enters its borrower-default path, leaving active LPs and pending receipts to share an unbacked claim basis. [7](#0-6) 

The broken invariant is fair external-asset custody: one unit of pool principal transferred to the borrower adapter must remain represented by economically equivalent vault shares or cash.

### Likelihood Explanation
The attack requires the configured ERC4626 vault to use integer rounding without inflation protection and to be accessible to other depositors. It is most feasible before the borrower adapter’s first material vault deposit, when a prospective attacker can establish and inflate the vault share supply.

No privileged vault role is required for the exploit itself: the attacker only performs an ordinary ERC4626 deposit, a direct asset donation, and a later redemption. Existing CDO guards do not detect the condition because `_depositToVault` treats a zero-share deposit as successful and the CDO continues tracking exposure through strategy tokens rather than the adapter’s realized vault assets.

### Recommendation
Validate every vault deposit with an explicit minimum-share or minimum-credited-asset bound. At minimum:

- derive `expectedShares = vault.previewDeposit(_assetAmount)`;
- call `vault.deposit` with a caller-controlled `minShares` equivalent;
- revert if `shares == 0` or `vault.convertToAssets(shares)` is materially below `_assetAmount`;
- preferably require the configured vault to use virtual shares/assets or another inflation-resistant ERC4626 implementation;
- seed or enforce a minimum vault share supply before allowing pool funds to be deposited;
- apply the same check to deposits made during repayment as well as epoch-start parking.

A backwards-compatible patch could make `_depositToVault` revert when `shares == 0` or when `convertToAssets(shares)` differs from `_assetAmount` by more than a bounded rounding allowance.

### Proof of Concept
A Foundry fork test can reproduce the loss with a rounding ERC4626 vault:

```solidity
// Attacker prepares the public vault before ProgrammableBorrower's deposit.
deal(address(asset), attacker, D + 1);

vm.startPrank(attacker);
asset.approve(address(vault), type(uint256).max);

// Mint one share for one unit.
vault.deposit(1, attacker);

// Inflate the price of that single share to D + 1 assets.
asset.transfer(address(vault), D);
vm.stopPrank();

// Honest manager starts the epoch. ProgrammableBorrower deposits D and gets:
// shares = D * 1 / (D + 1) = 0.
vm.prank(manager);
cdo.startEpoch();

assertEq(vault.balanceOf(address(programmableBorrower)), 0);
assertEq(asset.balanceOf(address(programmableBorrower)), 0);

// The attacker redeems the only share and receives donation + adapter deposit.
vm.prank(attacker);
vault.redeem(1, attacker, attacker);

assertGe(asset.balanceOf(attacker), 2 * D + 1);

// At the next stop, the recorded principal baseline becomes a vault loss.
vm.warp(cdo.epochEndDate() + 1);
assertEq(programmableBorrower.vaultLoss(), D);
assertEq(programmableBorrower.totalInterestDueNow(), 0);

// A subsequent withdrawal request cannot be funded because the vault principal is gone.
vm.prank(lender);
cdo.requestWithdraw(0, AAtranche);

vm.prank(manager);
cdo.startEpoch();

vm.warp(cdo.epochEndDate() + 1);
vm.prank(manager);
cdo.stopEpoch(0, 0);

assertTrue(cdo.defaulted());
```

The critical assertion is that `vault.deposit` returns/mints zero shares while `_depositToVault` completes successfully; the adapter then owns no claim over the `D` underlying it transferred.
