### Title
Stale confirmations from a deleted member still count toward `num_confirmations`, allowing execution below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` only purges requests that were *created* by the removed member; it never scans other pending requests' `confirmations` sets for entries belonging to that member. A confirmation string left behind by a now-deleted member is still counted by `confirm()`, so a request can reach `num_confirmations` and execute with fewer *live* members having actually approved it than the threshold requires.

### Finding Description
The invariant that should hold is: for every request `R`, `confirmations[R].len()` (as counted in `confirm`) should equal the number of *current* members who approved `R`. In `confirm`: [1](#0-0) 

the check is purely `confirmations.len() as u32 + 1 >= self.num_confirmations`, with no filtering of the stored strings against `self.members`.

`delete_member` is the only place that mutates the multisig's member set at runtime: [2](#0-1) 

It iterates `self.requests` and removes only the requests whose **creator** (`r.member`) equals the member being deleted (`self.requests.iter().filter_map(|(k, r)| if r.member == member ...)`), then calls `self.confirmations.remove(&request_id)` for those specific requests. It never inspects the `confirmations` `HashSet<String>` of *other* requests to strip out an entry matching `member.to_string()`. `assert_valid_request` also does not re-validate that stored confirmers are still members: [3](#0-2) 

Exploit flow (attacker is any current multisig member acting inside otherwise-normal multisig operation, no privileged foundation/owner role needed beyond being one of the multisig's own members, which is attainable by any account added via a legitimate `AddMember` request or already a member):
1. Multisig has members `{A, B, C, D}` with `num_confirmations = 3`.
2. Member `A` creates request `R` (e.g., `Transfer` draining funds to an attacker-controlled account).
3. Member `B` confirms `R` -> `confirmations[R] = {B}` (len 1).
4. Member `D` confirms `R` -> `confirmations[R] = {B, D}` (len 2, still below 3, not yet executed).
5. Separately, a `DeleteMember { member: D }` request is confirmed and executed (this only requires the normal multisig quorum and is a legitimate governance action, e.g., rotating out a compromised or departing member). `delete_member` removes `D` from `self.members` and only cleans up requests *created by* `D`; `R` (created by `A`) is untouched, so `confirmations[R]` still contains `D`.
6. Member `C` (the only remaining live member who hasn't confirmed) confirms `R` -> `confirmations[R].len() + 1 == 3 == num_confirmations`, so `execute_request` fires and the transfer executes.

Only `B` and `C` are live members who actually confirmed; `D`'s stale confirmation is counted as if it were a third live approval. The request executes with `2` live confirmations against a stated `num_confirmations = 3`, i.e., below the required live-member threshold — matching the Critical category "a multisig request executed below `num_confirmations` live members."

None of the existing guards prevent this: `assert_valid_request` only checks the request and confirmation map entries exist, not that confirmers are current members; `confirm` never re-validates set membership of the `HashSet<String>` contents; `delete_member`'s cleanup loop is scoped to requests keyed by creator, not by confirmer.

### Impact Explanation
Funds (or any other multisig action, including `AddKey`/`AddMember`/`DeployContract`) can be authorized and executed by fewer live, currently-authorized members than `num_confirmations` mandates, because a removed member's stale confirmation persists and is silently counted. This directly moves NEAR (or triggers other privileged actions) out of the multisig account without the entitled quorum's consent — Critical severity, matching "a multisig request executed below `num_confirmations` live members." The condition is repeatable any time a member who has confirmed an outstanding request is later removed while that request remains pending, and reusable across any multisig contract instance deployed from the same code.

### Likelihood Explanation
This requires only normal multisig usage: an outstanding, not-yet-fully-confirmed request plus a subsequent, legitimate `DeleteMember` execution — both are routine multisig operations available to the multisig's own members (no foundation/owner privilege, no key compromise). No special attacker resources are needed beyond being (or colluding with) an existing multisig member, and the sequence can be triggered opportunistically or engineered by a malicious/soon-to-be-removed member who pre-confirms sensitive requests before being removed.

### Recommendation
When deleting a member, iterate all pending requests' `confirmations` sets (not just requests created by that member) and remove the deleted member's `to_string()` entry from each. Alternatively (and more robustly), have `confirm` (and any confirmation-count check) filter `confirmations.get(&request_id)` against `self.members` at read time, so stale/removed-member confirmations never count toward `num_confirmations`.

### Proof of Concept
```rust
// multisig2/src/lib.rs - new test in mod tests
#[test]
fn test_stale_confirmation_after_delete_member_counts_toward_threshold() {
    // Members: alice (Account), bob (Account), key1 (AccessKey), key2 (AccessKey/TEST_KEY)
    // num_confirmations = 3
    let amount = 1_000;
    testing_env!(context_with_account(alice(), amount)); // A creates request
    let mut c = MultiSigContract::new(members(), 3);

    let request = MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    };
    let request_id = c.add_request(request);

    // B confirms
    testing_env!(context_with_account(bob(), amount));
    c.confirm(request_id);
    assert_eq!(c.confirmations.get(&request_id).unwrap().len(), 1);

    // key2 (TEST_KEY, a distinct member "D") confirms
    testing_env!(context_with_key(
        PublicKey::try_from(TEST_KEY.to_vec()).unwrap(),
        amount
    ));
    c.confirm(request_id);
    assert_eq!(c.confirmations.get(&request_id).unwrap().len(), 2); // still below 3, not executed

    // A separate request deletes member "D" (TEST_KEY) - executed via required quorum
    testing_env!(context_with_account(alice(), amount));
    let delete_req_id = c.add_request(MultiSigRequest {
        receiver_id: alice(), // self request, current_account_id is alice per context
        actions: vec![MultiSigRequestAction::DeleteMember {
            member: MultisigMember::AccessKey {
                public_key: PublicKey::try_from(TEST_KEY.to_vec()).unwrap(),
            },
        }],
    });
    testing_env!(context_with_account(bob(), amount));
    c.confirm(delete_req_id);
    testing_env!(context_with_key(
        PublicKey::from("Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy".parse().unwrap()),
        amount
    ));
    c.confirm(delete_req_id); // reaches 3 confirmations, executes DeleteMember

    // Assert: D is no longer a member
    assert!(!c.get_members().contains(&MultisigMember::AccessKey {
        public_key: PublicKey::try_from(TEST_KEY.to_vec()).unwrap(),
    }));

    // BUT: original request_id's confirmations still contain D's stale entry
    assert_eq!(c.confirmations.get(&request_id).unwrap().len(), 2); // BROKEN INVARIANT:
    // should be 1 (only B, a live member) since D was removed, but D's entry persists

    // C (key1) confirms - only the 2nd *live* confirmation, but 3rd counted overall
    testing_env!(context_with_key(
        PublicKey::from("Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy".parse().unwrap()),
        amount
    ));
    c.confirm(request_id); // executes: confirmations.len()+1 == 3 == num_confirmations

    // Assert: request executed (removed) despite only 2 live-member confirmations (B and C)
    assert_eq!(c.requests.len(), 0); // Transfer executed with only 2/3 live confirmations
}
```
This demonstrates the binding `live_confirmations(R) == confirmations[R].len()` is false after a `DeleteMember` execution, and that `execute_request` fires with fewer live confirmations than `num_confirmations` requires.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
