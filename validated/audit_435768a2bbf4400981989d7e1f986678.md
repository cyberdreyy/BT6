### Title
Time-of-check-to-time-of-use race in `jwtReplayCache.isReplay`/`recordUsage` allows single-use trigger JWT to authorize concurrently - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks `jwtCache.isReplay(claims.ID)` and only marks the jti as used via `jwtCache.recordUsage(claims.ID)` after several more steps, with no lock held across the two calls. Two concurrent `Authorize` invocations carrying the same `jti` can both pass the `isReplay` check before either calls `recordUsage`, defeating the single-use guarantee the cache is meant to enforce.

### Finding Description
`isReplay` takes an `RLock`, reads the map, and releases the lock [1](#0-0) . `recordUsage` is only called much later in `Authorize`, after the authorized-key lookup succeeds, using a separate `Lock` acquisition [2](#0-1) . Between these two calls in `Authorize`, no mutex is held [3](#0-2) , so this is a classic check-then-act race: two goroutines calling `Authorize` with an identical `jti` can both observe `isReplay == false`, both pass the authorized-key check, and both call `recordUsage` — i.e., the same signed trigger JWT is accepted twice instead of the intended single use.

`Authorize` is reachable from the gateway's HTTP trigger path via `httpTriggerHandler.authorizeRequest`, which is called for every inbound `MethodWorkflowExecute` trigger request before rate limiting and dispatch [4](#0-3) . An attacker holding one valid signed trigger JWT (e.g., a legitimate workflow trigger credential) can fire it concurrently to win this race at the authorization layer.

However, actual dispatch to DON nodes (the real "pipeline trigger") is additionally gated by `setupCallback`, which performs an atomic check-and-insert of the JSON-RPC `requestID` into `h.callbacks` under a single critical section (`callbacksMu.Lock()`) [5](#0-4) . Because this check-and-insert happens atomically (unlike the JWT cache), two concurrent requests carrying the identical `req.ID` will have only one of them proceed to `sendWithRetries` (actual pipeline dispatch); the other is rejected with `"in-flight request ID... has already been used"`. The existing test suite confirms replay of the same token+requestID is rejected via this path, and that duplicate requestID alone is rejected via the atomic map check [6](#0-5) .

The residual, confirmed exploitable defect is at the `Authorize`/`jwtReplayCache` layer itself: the anti-replay control it implements is not atomic and can be bypassed by concurrency, regardless of what downstream request-ID deduplication exists. Whether this defect can be escalated to an actual double pipeline dispatch depends on whether `utils.VerifyRequestJWT` cryptographically binds the signature to the specific JSON-RPC `req.ID` (which would force the two racing requests to share the same `req.ID`, and thus be caught by the atomic `setupCallback` dedup) — this binding could not be fully verified from `core/utils/jwt.go` within the available investigation. If the JWT signature does not bind to `req.ID` (only to `jti`/payload), an attacker could attach the same token to two JSON-RPC requests with distinct `req.ID`s, race `Authorize`, and get both dispatched via `setupCallback` (distinct requestIDs → distinct map entries → no dedup), achieving a genuine double pipeline trigger.

### Impact Explanation
At minimum, this is a broken single-use enforcement in a security control explicitly documented as "prevent replay attacks" — the cache can record a jti as used only after two racing callers already treated it as unused, meaning the anti-replay guarantee does not hold under concurrency. If (as could not be fully confirmed) the JWT signature does not bind to the specific `req.ID`, this becomes an unauthorized duplicate job/pipeline execution using a single signed credential — matching Chainlink's "unauthorized job run" impact class.

### Likelihood Explanation
No special privilege is needed beyond possessing one legitimately signed (or otherwise obtained) trigger JWT for a workflow — a capability already available to a legitimate signer/external-initiator credential holder. Winning the race only requires firing near-simultaneous requests, which is trivially reproducible with concurrent goroutines/HTTP clients; no timing tricks beyond ordinary concurrency are needed.

### Recommendation
Make the check-and-record operation atomic: acquire a single write lock, perform the `isReplay` existence check and the `recordUsage` insert inside that one critical section (compare-and-swap semantics), and return "already used" if the entry already existed — analogous to `sync.Map.LoadOrStore`. Additionally, verify (and if missing, add) that `utils.VerifyRequestJWT` cryptographically binds the token to the exact JSON-RPC `req.ID`, so that the atomic `setupCallback` requestID dedup functions as a defense-in-depth backstop.

### Proof of Concept
Unit test directly against `jwtReplayCache`/`Authorize`:
```go
func TestJWTReplayCache_ConcurrentAuthorize_TOCTOU(t *testing.T) {
    h, ... := createTestWorkflowMetadataHandler(t) // register a workflow + authorized signer
    token, req := createTestJWTToken(t, ..., privateKey) // single jti

    var successCount atomic.Int32
    var wg sync.WaitGroup
    for i := 0; i < 50; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            if _, err := h.Authorize(workflowID, token, req); err == nil {
                successCount.Add(1)
            }
        }()
    }
    wg.Wait()
    // Expect exactly 1 with correct locking; race allows > 1
    require.LessOrEqual(t, successCount.Load(), int32(1), "JWT replay cache TOCTOU allowed multiple successful authorizations for same jti")
}
```
Run with `go test -race` to surface the concurrent map access and confirm `recordUsage` is invoked more than once for the same `jti`. A follow-up integration test should assert whether `httpTriggerHandler.HandleUserTriggerRequest`, when fed two requests with distinct `req.ID`s but the same JWT, results in more than one `SendToNode` dispatch — this determines whether the flaw escalates to actual double pipeline execution and depends on confirming the `req.ID`-binding behavior of `VerifyRequestJWT`.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

	// Build one response aggregator per shard the workflow is assigned to.
	assigned := h.workflowMetadataHandler.WorkflowShards(workflowID)
	if len(assigned) == 0 {
		// this shouldn't happen because we checked it in authorizeRequest()
		h.handleUserError(ctx, requestID, jsonrpc.ErrInternal, fmt.Sprintf("Workflow %s is not assigned to any DONs", workflowID), callback)
		return nil, errors.New("workflow is not assigned to any shards")
	}
