### Title
Stale confirmations from removed multisig members remain counted toward the confirmation threshold - ([File: multisig2/src/lib.rs])

### Summary
In `multisig2`, `delete_member` removes a member from the multisig's member set and from *its own* outstanding requests, but it never purges that member's confirmation from the `confirmations` set of *other* pending requests (created by different members) that it had already confirmed. `confirm()` later counts these stale entries toward `num_confirmations`, letting a request execute with fewer than `num_confirmations` *live* member confirmations — the same "stale entry not removed on reassignment/removal" bug class as the referenced `delegate`/`delegatedTokenIds` finding, applied to the confirmation-count vs. live-member-set binding.

### Finding Description
The contract's core invariant is:
```
number of DISTINCT LIVE members in confirmations[request_id] >= num_confirmations
```
before a request is executed via `confirm`: [1](#0-0) 

`delete_member` is responsible for removing a member from the system. It only cleans up requests whose creator (`r.member`) equals the deleted member, and removes that member's `num_requests_pk` entry — it never scans/cleans the `confirmations` map of requests created by *other* members that the deleted member may have already confirmed: [2](#0-1) 

Because `confirmations` is a `LookupMap<RequestId, HashSet<String>>` keyed independently of the live `members: UnorderedSet<MultisigMember>` set, an entry recorded there for a member who has since been deleted is never invalidated. `confirm()` blindly counts `confirmations.len()` without cross-checking that every entry still belongs to a current member: [3](#0-2) 

This is structurally identical to the report's bug class: an old relationship (`delegatedTokenIds` entry / here, a confirmation entry) is not removed when the underlying membership changes, so it keeps contributing to a count it should no longer be part of.

### Impact Explanation
This lets a `MultiSigRequest` (e.g. a `Transfer`, `FunctionCall`, `AddKey`/`AddMember` granting full access) execute with fewer live confirmations than `num_confirmations` requires, i.e. **a multisig request executed below threshold** — explicitly listed as Critical impact. Funds can be moved, or full-access keys/members added, by a coalition smaller than the configured K-of-N threshold, defeating the entire security model of the multisig.

### Likelihood Explanation
No privileged actor, redeploy, or foundation action is required. Any legitimate member sequence — (1) member confirms a pending request, (2) that member is later removed via a normal, threshold-approved `DeleteMember` request (a routine operational action, e.g. offboarding), (3) the original request is later pushed over the threshold by other members — reproduces the issue. It requires the ordinary lifecycle event of removing a member while other requests are pending, which is a realistic and unprivileged-attacker-exploitable ("stale confirmation") condition rather than a contrived edge case.

### Recommendation
When deleting a member in `delete_member`, iterate over all entries in `confirmations` and remove the deleted member's identifier from every request's confirmation set (not just requests it created), or alternatively re-validate at `confirm()`/execution time that every address present in a request's confirmation set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]`, `num_confirmations = 3`.
2. `B` calls `add_request_and_confirm(R)` → `confirmations[R] = {B}`.
3. `D` calls `confirm(R)` → `confirmations[R] = {B, D}` (2 confirmations, below threshold, `R` stays pending).
4. Members separately pass a threshold-approved request executing `DeleteMember { member: D }` (this only touches requests created by `D`, not `R`, since `R.member == B`) — `D` is removed from `members`, but `confirmations[R]` still equals `{B, D}`.
5. `A` calls `confirm(R)`: `confirmations.len()` is `2`, `+1 = 3 >= num_confirmations(3)` → `R` executes.
6. Result: `R` executed with confirmations from only `{A, B}` as live members plus the stale, no-longer-valid `D`, i.e. only 2 live-member confirmations satisfied a 3-of-N policy. [4](#0-3) [1](#0-0)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
