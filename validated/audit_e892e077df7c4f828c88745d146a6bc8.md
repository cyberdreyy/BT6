This confirms the vulnerability. Both `lockup-factory` and `staking-pool-factory` implement a `.then()` callback (`on_lockup_create` / `on_staking_pool_create`) that checks `is_promise_success()` and explicitly refunds the deposit to `predecessor_account_id` on failure. `multisig-factory::create` at [1](#0-0)  has no such `.then()` callback — it just returns the bare `Promise::new(account_id).create_account().deploy_contract(...).transfer(...).function_call(...)` with no failure handling whatsoever.

### Title
Multisig factory `create` has no failure callback, silently consuming deposit on failed deployment - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` at [1](#0-0)  schedules a single batched promise (`create_account` → `deploy_contract` → `transfer` → `function_call`) and returns it directly to the caller with no `.then()` callback to self. If the batch receipt fails (e.g., because `create_account` fails since the derived `account_id` already exists), the attached deposit is never returned to the original caller, unlike the sibling `lockup-factory` and `staking-pool-factory` contracts which both implement explicit refund callbacks (`on_lockup_create`, `on_staking_pool_create`).

### Finding Description
The broken binding: `balance_refunded_to(predecessor_account_id)` should equal `attached_deposit` whenever the deployment `Promise` batch fails, exactly as enforced in the sibling factories via `is_promise_success()` checks in their callbacks (`lockup-factory/src/lib.rs` lines 171-198, `staking-pool-factory/src/lib.rs` lines 200-239). In `multisig-factory/src/lib.rs`, `create` builds `account_id = format!("{}.{}", name, env::current_account_id())` and issues one promise batch containing `create_account`, `deploy_contract`, `transfer(env::attached_deposit())`, and `function_call("new", ...)`, then returns that `Promise` directly — there is no `.then(ext_self::...)` and no callback function defined anywhere in the file [2](#0-1) .

Exploit flow: an unprivileged attacker first creates (or otherwise causes to exist) an account at the exact derived path `name.multisig-factory-account`, e.g. by calling `create` once successfully for a given `name`, or by directly creating that account another way and funding it with a balance. The attacker then calls `create` again with the same `name` and a fresh deposit. The `create_account` action in the new batch fails (`AccountAlreadyExists`), which causes the entire batched receipt to fail atomically — `deploy_contract`, `transfer`, and `function_call` never execute. Because there is no callback checking `is_promise_success()`, the factory contract never learns about the failure and never issues a refund `Promise::new(predecessor_account_id).transfer(...)`. The attached deposit that was already deducted from the caller's balance and forwarded to the receipt is refunded by the NEAR protocol's automatic receipt-failure refund mechanics back to the *predecessor of that failed receipt* — which is the `multisig-factory` contract account itself, not the original transaction signer. The deposit is thus absorbed into the factory contract's own balance rather than returned to the caller who paid it, silently and permanently (from the caller's perspective) diverting funds with no on-chain acknowledgment of failure beyond the returned-but-unhandled Promise.

No existing guard prevents this: `create` performs no `env::is_valid_account_id`-based existence check, no `assert_self()`/`is_promise_success()` gate (there is nothing to gate, since there is no callback), and no `assert_one_yocto()` or similar. The sibling factories' pattern of `.then(ext_self::on_X_create(...))` with explicit refund-on-failure logic is entirely absent here.

### Impact Explanation
Any caller whose `create` call targets an already-existing derived account id loses their attached deposit — it ends up credited to the `multisig-factory` contract's own account balance instead of being returned to the payer. This is an accounting divergence: the payer's ledger (their wallet) shows the deposit spent on a multisig they never got, while the "another party" (the factory contract/its operator) ends up holding a balance increase it did not legitimately earn and has no code path to disburse. This is repeatable by any attacker for any `name` value they can cause to collide (including their own previous multisig or an account they create themselves), and matches the High severity category: "an accounting value diverging from reality where another party settles on it."

### Likelihood Explanation
The precondition — a derived account already existing at `name.multisig-factory-account` — is trivially attacker-controlled: the attacker can simply call `create` once to legitimately create `name.multisig-factory-account`, then call `create` again with the same `name` and a new deposit to trigger the failure path. No privileged role, foundation approval, or victim cooperation is required; the attack costs only the deposit and gas of two ordinary transactions and is fully repeatable across arbitrary `name` values.

### Recommendation
Add a `.then(ext_self::on_create(...))` callback to `MultisigFactory::create`, mirroring `lockup-factory`/`staking-pool-factory`: check `is_promise_success()` in the callback, and if the deployment failed, issue `Promise::new(predecessor_account_id).transfer(attached_deposit)` to refund the original caller instead of letting the protocol-level refund land on the factory account.
