### Title
Unbounded chunk-count allocation from attacker-controlled `Content-Range` total causes cache-extractor OOM/DoS - ([File: helpers/transfer/parallel_download.go])

### Summary
`ParseContentRangeTotal` in `helpers/transfer/content_range.go` accepts any positive int64 up to `math.MaxInt64` from a server-supplied `Content-Range` header with no upper bound check. This value flows unvalidated into `ParallelRangeDownload`, where `parallelDownloadRanges` eagerly builds a full `[]byteRange` slice sized `contentLength/chunkSize`, allowing a malicious/compromised cache backend to force the runner helper process to allocate an astronomically large slice and exhaust host memory before any goroutine or network I/O even begins.

### Finding Description
`ParseContentRangeTotal` only validates that the parsed total is a valid int64 `> 0`; it imposes no maximum [1](#0-0) . In `commands/helpers/cache_extractor.go`, `tryPresignedParallelDownload` issues a 1-byte probe `Range` request and takes `contentLength` directly from this parser's return value with no sanity/max check before calling `downloadParallel` [2](#0-1) . The GoCloud path similarly takes `attrs.Size` from the bucket backend and passes it to `downloadParallel` [3](#0-2) .

`downloadParallel` forwards `contentLength` straight into `transfer.ParallelRangeDownload` [4](#0-3) . Inside `ParallelRangeDownload`, `normalizeParallelDownloadInputs` only clamps `chunkSize` down to `contentLength` if `chunkSize > contentLength`, but does nothing to bound the resulting number of chunks when `contentLength` is huge relative to `chunkSize` [5](#0-4) . `parallelDownloadRanges` then loops `contentLength/chunkSize` times, appending a `byteRange` struct on every iteration, fully materializing the chunk list in memory before any worker goroutine is spawned [6](#0-5) .

With the default chunk size (16 MiB) and an attacker-returned total near `math.MaxInt64` (~9.22×10^18), the loop count is on the order of 5.76×10^11 iterations, and the `chunks` slice growth (Go slice doubling with 16-byte `byteRange` elements) alone requires terabytes of memory — enough to OOM-kill the process (and, depending on cgroup/host configuration, put memory pressure on the whole node) long before any `ParallelRangeDownload` goroutine limit or `io.LimitReader` protection in `downloadChunk` (lines 52-79) ever comes into play. Those existing protections only bound per-chunk read size, not the total chunk count derived from the attacker-controlled total.

The attack path requires the runner to have `FF_USE_PARALLEL_CACHE_TRANSFER` enabled and `Concurrency > 1` (checked in `presignedParallelDownloadEligible`, line 248-251, and inline for GoCloud at line 491), and requires the presigned/alternate URL or GoCloud bucket the runner fetches from to be attacker-influenced infrastructure (e.g., an `AlternateURL`/`AlternateGoCloudURL` pointing at a server the attacker controls) that returns a crafted `Content-Range`/object-size response.

### Impact Explanation
A crafted response causes the `cache-extractor` helper process (running inside/alongside the job's isolation boundary but on the runner host) to attempt a multi-terabyte memory allocation, resulting in an OOM kill or severe memory pressure. On shared runners or hosts running multiple concurrent jobs, this can starve or crash sibling job processes, producing a denial-of-service that disrupts other tenants' workloads on the same host — matching the scoped impact of host resource exhaustion enabling cross-tenant disruption.

### Likelihood Explanation
Preconditions (`FF_USE_PARALLEL_CACHE_TRANSFER=true` and `Concurrency>1`) are non-default but are legitimate, documented runner configuration options that operators may enable for performance. Given those preconditions, the exploit requires the runner to fetch cache metadata from an attacker-influenced endpoint (e.g., the alternate URL/GoCloud path), which is a job-configuration-dependent factor and not something an unprivileged pipeline author can universally control without infrastructure influence — this dependency is inherited from the question's stated precondition and was not independently verified in this review (the exact mechanism by which a job author supplies `--alternate-url`/`--alternate-gocloud-url` values was not traced). Given that precondition, the bug itself is trivially and repeatably triggerable: a single crafted HTTP response is sufficient, no timing races or complex state needed.

### Recommendation
Add an explicit upper bound in `ParseContentRangeTotal` (or at the call sites in `cache_extractor.go`) rejecting/clamping totals larger than a sane maximum (e.g., a configurable max cache size). Additionally, in `helpers/transfer/parallel_download.go`, bound the number of chunks computed by `parallelDownloadRanges`/`normalizeParallelDownloadInputs` — e.g., cap `contentLength/chunkSize` to a maximum chunk count and increase `chunkSize` automatically (or return an error) when the computed count would exceed that cap, rather than allocating the full chunk slice unconditionally.

### Proof of Concept
```go
// helpers/transfer/parallel_download_test.go
func TestParallelRangeDownload_HugeContentLengthDoS(t *testing.T) {
    // Simulates an attacker-controlled Content-Range total near math.MaxInt64.
    hugeTotal := int64(math.MaxInt64 - 1)
    chunkSize := int64(16 * 1024 * 1024) // default 16MiB

    f, err := os.CreateTemp(t.TempDir(), "parallel-range")
    require.NoError(t, err)
    t.Cleanup(func() { _ = f.Close() })

    fetchChunk := func(offset, length int64) (io.ReadCloser, error) {
        t.Fatal("fetchChunk must not be called before chunk-count is bounded")
        return nil, nil
    }

    done := make(chan struct{})
    go func() {
        _ = ParallelRangeDownload(hugeTotal, chunkSize, 4, f, fetchChunk)
        close(done)
    }()

    select {
    case <-done:
        // Expected: should return quickly with an error (rejecting excessive chunk count),
        // not attempt to build ~5.7e11-element slice.
    case <-time.After(5 * time.Second):
        t.Fatal("ParallelRangeDownload did not bound/reject an oversized contentLength; " +
            "likely stuck allocating an unbounded chunk slice")
    }
}
```
Expected assertion after a fix: `ParallelRangeDownload` (or an added guard in `normalizeParallelDownloadInputs`/`parallelDownloadRanges`) returns an error such as `"transfer: chunk count exceeds maximum"` immediately, rather than attempting to allocate/iterate hundreds of billions of chunks. Currently, no such guard exists, so the only bound is process OOM.

```go
func parallelDownloadRanges(contentLength, chunkSize int64) []byteRange {
	var chunks []byteRange
	for offset := int64(0); offset < contentLength; offset += chunkSize {
		length := chunkSize
		if offset+length > contentLength {
			length = contentLength - offset
		}
		chunks = append(chunks, byteRange{offset, length})
	}
	return chunks
}
```
