### Title
Truncated per-epoch APR0 rate permanently strands accrued interest inside `pendingWithdraws` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `prepareStopEpochWithApr0` finalizes the APR0 interest bucket, it credits the full `_apr0NetInterest` to `pendingWithdraws` but distributes it to users through a double-truncated rate (`apr0RateByEpoch` then per-user `_principal * _rate / 1e18`). The division remainders are added to the liability counter but can never be claimed by anyone, exactly mirroring the MultiRewards bug where `leftover % rewardsDuration` was lost instead of being added back into `rewardResidual`.

### Finding Description
In `prepareStopEpochWithApr0`, the pro-rata APR0 share is computed and the full net amount is pushed onto the claimable liability:

- `pendingWithdraws += _apr0NetInterest;` (contracts/strategies/idle/IdleCreditVault.sol:535)
- `apr0RateByEpoch[epochNumber] = (_apr0NetInterest * 1e18) / _principal;` (contracts/strategies/idle/IdleCreditVault.sol:537)

The first truncation loses `(_apr0NetInterest * 1e18) % _principal`, i.e. up to `_principal / 1e18` underlying units of rate that were already counted in `pendingWithdraws`. Then each user settles via `_settleApr0`:

- `_apr0User.settledInterest += (_principal * _rate) / 1e18;` (contracts/strategies/idle/IdleCreditVault.sol:561)

which truncates again per user. The sum of all `settledInterest` credited is strictly less than `_apr0NetInterest` whenever either division has a remainder, but `pendingWithdraws` (the basis used by `collectWithdrawFunds`, `previewLossAdjustedWithdrawFunds`, and `defaultPendingClaimBasis`) keeps the full amount. The residual is not re-added anywhere — there is no `rewardResidual` equivalent — so the dust becomes a permanently unclaimable liability that inflates the pending-receipt bucket.

Concretely: with `_apr0NetInterest` and `_principal` chosen such that `_apr0NetInterest * 1e18 % _principal != 0`, after all APR0 users settle and claim, `pendingWithdraws` is decremented by less than the credited amount, leaving `pendingWithdraws > sum(claimable)`. That residual still participates as `pendingBasis` in `previewLossAdjustedWithdrawFunds` (line 441-459) and in `defaultPendingClaimBasis` (line 644-649), so during a subsequent `stopEpochWithDuration(_lossAmount)` or default finalization it receives a pro-rata loss/recovery allocation for funds no one can claim, slightly diluting real LPs and real receipt holders.

### Impact Explanation
**Low** per event — the stranded amount is bounded by roughly `_principal / 1e18 + nUsers` wei per epoch — but it is a permanent freeze of credited yield and a small, permanent accounting inconsistency in `pendingWithdraws` that skews subsequent loss/recovery haircuts against honest users.

### Likelihood Explanation
**High** — the rounding is hit on every `stopEpoch` in which APR0 withdraw requests exist and realized interest is nonzero. An unprivileged lender can also shape `apr0TotalPrincipal` (by splitting deposits/requests so `_principal` is not a divisor of `_apr0NetInterest * 1e18`) to maximize the stranded residual each epoch; it requires no privileged action.

### Recommendation
Track the undistributed remainder explicitly: after computing `apr0RateByEpoch[epochNumber]`, compute `uint256 distributed = _principal * apr0RateByEpoch[epochNumber] / 1e18;` (or accumulate per-user remainders) and credit `pendingWithdraws` only with the actually-claimable sum, or store the remainder in a residual variable that is folded into the next epoch's APR0 distribution — the same fix pattern as MultiRewards' `rewardResidual`.
