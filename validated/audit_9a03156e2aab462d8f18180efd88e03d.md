### Title
Unfunded instant-withdraw receipts are paid from other users' funded balances due to missing funded-amount limit check - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` in `IdleCreditVault` pays out the entire `instantWithdrawsRequests[_user]` receipt balance via `_transferFundedClaim`, which only guards against spending `defaultRecoveryReserve`. It never checks whether the request was actually funded (i.e., whether `pendingInstantWithdraws` was reduced via `collectInstantWithdrawFunds` and the corresponding underlying was pulled from the CDO). This mirrors CVE-2019-18425's missing descriptor-table limit check: a privileged-path access (the instant-withdraw claim) is performed without respecting the limit that should bound it (the funded instant-withdraw amount). An unprivileged tranche holder can therefore withdraw unfunded instant receipts against underlying belonging to funded withdraw claimants, APR0 claimants, or deposits not yet sent to the borrower.

### Finding Description
Instant withdrawals follow a two-step flow: `requestInstantWithdraw` mints a strategy-token receipt to the user and increases `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (lines 356-375). The CDO is expected to later fund the request via `collectInstantWithdrawFunds`, which decreases `pendingInstantWithdraws` and pulls underlying into the strategy (lines 398-403).

However, `claimInstantWithdrawRequest` (lines 380-393) burns the full `instantWithdrawsRequests[_user]` amount and calls `_transferFundedClaim(_user, amount)` unconditionally:

```
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`_transferFundedClaim` (lines 897-907) only enforces `balance - defaultRecoveryReserve >= _amount` when a recovery reserve exists. There is no check that `amount <= (instantWithdrawsRequests basis that was actually funded)`, i.e. no check against `pendingInstantWithdraws` or a funded-balance limit. Contrast with normal withdraws, which are gated by epoch (`epochNumber <= lastWithdrawRequest` reverts at line 326) and are only paid after `collectWithdrawFunds` moved real underlying. Instant claims skip the funding/limit check entirely.

Concrete attack (unprivileged lender, running epoch):
1. Strategy holds underlying backing previously funded normal withdraw receipts (`collectWithdrawFunds` already ran) and/or deposits held before `sendInterestAndDeposits`/borrower send.
2. Attacker calls `requestInstantWithdraw(X)` through the CDO (KYC-passed lender path), receiving receipt tokens and `instantWithdrawsRequests[attacker] = X`, `pendingInstantWithdraws += X`. No underlying moves.
3. Before anyone funds the instant queue, attacker calls `claimInstantWithdrawRequest(attacker)` via the CDO. The function burns the receipt and transfers `X` underlying from the strategy's existing balance — underlying that was reserved for other users' funded claims or pending deposits.
4. `pendingInstantWithdraws` remains nonzero, so the honest flow still expects the CDO/borrower to fund `X`, but the tokens are already gone — the loss is socialized onto the funded claimants whose withdrawals now revert on insufficient balance.

### Impact Explanation
Direct theft / temporary freezing of funds: the attacker extracts underlying equal to their unfunded instant receipt, up to the strategy's liquid balance (`balance - defaultRecoveryReserve`). Funded withdraw claimants and instant claimants are left unable to claim until new funds arrive (insolvency-style freeze), and if the borrower later defaults the shortfall is permanent. The broken invariant is "one receipt, one funded payout": a receipt minted without any underlying transfer is redeemed against a communal funded pool with no funded-limit check.

### Likelihood Explanation
Attackable by any unprivileged user able to call the instant-withdraw request path (a KYC-passed lender / tranche holder) during a running epoch, whenever the strategy holds underlying for other purposes — a common state after `collectWithdrawFunds` or during deposit windows. It requires no privileged role and no borrower misbehavior. The only mitigation is if the calling CDO context blocks claims while `pendingInstantWithdraws` is nonzero or fully funds requests atomically at request time; the strategy code itself contains no such guard, and the docstring for `defaultPendingClaimBasis` (lines 636-640) explicitly documents that `pendingInstantWithdraws != 0` means current-epoch instant receipts "were not fully funded" — confirming unfunded instant receipts coexist with claimable state by design. If the CDO does enforce atomic funding at the call site, the issue degrades to defense-in-depth; I was unable to fully verify the CDO-side `claimInstantWithdrawRequest`/`requestInstantWithdraw` wrappers within the available iterations.

### Recommendation
Track funded vs. unfunded instant receipts separately, e.g. maintain `fundedInstantWithdraws` incremented in `collectInstantWithdrawFunds` and cap each claim at the user's funded portion, or simply gate `claimInstantWithdrawRequest` so a user can only claim amounts backed by collected funds (`require(pendingInstantWithdraws == 0)`-style epoch accounting). Alternatively, extend `_transferFundedClaim`'s reserve check to exclude underlying owed to other pending claimant classes, so instant claims cannot spend the funded-withdraw pool.

// Fork test: instantiate a real epoch CDO + IdleCreditVault on mainnet fork
// (see test/foundry for existing fixture patterns).
contract UnfundedInstantWithdrawPoC is Test {

    IERC20Detailed underlying;

    address attacker; // KYC-passed lender / tranche holder
    address victim;   // funded normal-withdraw claimant

    function test_claimUnfundedInstantReceipt() public {
        // Setup: vault holds 1000e6 USDC backing victim's funded withdraw receipt
        // (collectWithdrawFunds already pulled funds into the strategy).
        uint256 fundedPool = underlying.balanceOf(address(vault));
        assertGt(fundedPool, 0);

        uint256 attackerUnderlyingBefore = underlying.balanceOf(attacker);

        // 1. Attacker requests instant withdraw of amount <= fundedPool via CDO.
        vm.prank(attacker);
        // CDO.requestInstantWithdraw(amount) -> vault.requestInstantWithdraw(amount, attacker)
        // mints receipt, sets instantWithdrawsRequests[attacker], pendingInstantWithdraws += amount.

        // 2. Nobody calls collectInstantWithdrawFunds: pendingInstantWithdraws is still unfunded.
        assertGt(vault.pendingInstantWithdraws(), 0);

        // 3. Attacker immediately claims; _transferFundedClaim only checks
        //    defaultRecoveryReserve (== 0), so the full amount is paid from
        //    victim's funded pool.
        // CDO.claimInstantWithdrawRequest(attacker) -> vault.claimInstantWithdrawRequest(attacker)

        assertGt(underlying.balanceOf(attacker), attackerUnderlyingBefore);

        // 4. Victim's claim now reverts / is underpaid: strategy balance < funded claims.
        // vault.claimWithdrawRequest(victim) -> _transferFundedClaim underflows or pays less.
    }
}
