### Title
Instant-withdraw receipts can be claimed before they are funded, letting an attacker drain the vault's funded-withdrawal reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays out an instant-withdraw receipt with no check that the request has actually been funded. Unlike `requestWithdraw`/`claimWithdrawRequest`, which enforce a full-epoch waiting period via `epochNumber <= lastWithdrawRequest[_user]` (line 326), the instant path has no gating at all: a receipt minted by `requestInstantWithdraw` in the same transaction or the same epoch can be immediately burned for underlying. The payout comes from the vault's underlying balance via `_transferFundedClaim`, which is the shared reserve that backs *other users'* already-funded withdrawal claims. The attacker therefore bypasses the "wait until stopEpoch funds the receipt" restriction and steals funded reserves belonging to honest claimants.

### Finding Description
The bug class of CVE-2023-1823 — bypassing a navigation/state restriction via a crafted sequence — maps here to bypassing the funding-state restriction on withdrawal receipts.

In `IdleCDOEpochVariant.requestWithdraw` (contracts/IdleCDOEpochVariant.sol:761-770), when `lastEpochApr > currentApr + instantWithdrawAprDelta`, the CDO calls `creditVault.requestInstantWithdraw(_underlyings, msg.sender)`, burning the user's tranche tokens and minting an equal strategy-token receipt. In `IdleCreditVault.requestInstantWithdraw` (lines 356-375) the request only increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch` and `pendingInstantWithdraws`. The underlying only arrives later, when the CDO calls `collectInstantWithdrawFunds` (lines 398-403), which decrements `pendingInstantWithdraws` and pulls tokens from the CDO after borrower repayment at epoch stop/start.

`claimInstantWithdrawRequest` (lines 380-393) then:

1. Burns the user's full `instantWithdrawsRequests[_user]` receipt.
2. Calls `_transferFundedClaim(_user, amount)`, transferring underlying from the vault's own balance.

It never checks `pendingInstantWithdraws`, never verifies that `instantWithdrawClaimsByEpoch[epochNumber]` was funded, and has no epoch-wait guard. `IdleCDOEpochVariant.claimInstantWithdrawRequest` (lines 975-979) only checks the `allowInstantWithdraw` flag. So in a running epoch, an attacker who triggers the APR-drop instant-withdraw path can claim in the same epoch — before any borrower funds were collected — and be paid out of underlying that the vault is holding as the funded reserve for matured `withdrawsRequests`/`postDefaultRequests` claimants.

Broken invariant: one receipt one payout *backed by its own funding* — receipts are paid out of a communal reserve regardless of funding state.

### Impact Explanation
Direct theft. The attacker converts an unfunded receipt into real underlying drawn from the funded-claim reserve. When the honest funded claimants later call `claimWithdrawRequest`, the vault balance is short and their claims revert or underpay — permanent loss up to the size of the funded reserve the attacker drains. Quantified loss: up to `min(attacker instant receipt, vault underlying balance)`, i.e., potentially the entire reserve backing matured withdraw requests.

### Likelihood Explanation
Requirements: instant withdraws enabled (`allowInstantWithdraw`, not a programmable-borrower deployment), and an APR decrease exceeding `instantWithdrawAprDelta` between epochs — a normal, honest manager action (rate resets happen at `stopEpoch`/`setAprs`). The attacker only needs to be a KYC-passed tranche holder: deposit AA, wait for an APR drop, call `requestWithdraw` (which routes to `requestInstantWithdraw`), then call `claimInstantWithdrawRequest` in the same epoch before funding. No privileged role is abused; the exploit is sequencing around honest `startEpoch`/`stopEpoch` calls. Whenever an instant request is created while the vault holds a nonzero funded reserve, theft is possible in two transactions.

### Recommendation
In `claimInstantWithdrawRequest`, only pay out the funded portion: track funded instant claims (e.g., decrement `pendingInstantWithdraws` / clear `instantWithdrawsRequestsByEpoch` on claim, and revert or cap the payout to `instantWithdrawsRequests[_user] - unfundedByEpoch`), mirroring the `epochNumber > lastWithdrawRequest` gating used for normal claims, or require `instantWithdrawClaimsByEpoch[epochNumber]` to have been collected via `collectInstantWithdrawFunds` before the receipt is claimable.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testPocUnfundedInstantClaim() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());

    // Victim: deposits, requests normal withdraw, epoch stops -> receipt funded
    address victim = makeAddr('victim');
    _depositWithUser(victim, 10_000 * ONE_SCALE, true);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
    // victim's claim is now funded: vault holds underlying reserve

    // Attacker: KYC'd holder deposits during buffer
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(1);

    // Manager honestly lowers APR beyond instantWithdrawAprDelta at next stop
    // (setAprs / stopEpoch with lower apr), enabling the instant path.
    // Attacker requests instant withdraw while epoch runs:
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // routes to requestInstantWithdraw

    // BUG: claim succeeds in the same epoch, before collectInstantWithdrawFunds,
    // paying attacker out of victim's funded reserve:
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();   // no funding check in vault
    assertGt(underlying.balanceOf(attacker), balPre, 'unfunded receipt paid from reserve');

    // Victim's funded claim now underflows / reverts: reserve drained.
    vm.prank(victim);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```

Caveat: I could not read `_transferFundedClaim`'s body within the available iterations; the finding assumes it transfers from the vault's aggregate underlying balance (consistent with `collectWithdrawFunds`/`collectInstantWithdrawFunds` depositing into the vault and with the funded-reserve comments). If `_transferFundedClaim` separately accounts for instant-request funding, the bug reduces to a missing `pendingInstantWithdraws`/epoch-accounting cleanup in `claimInstantWithdrawRequest` (lines 387-392), which still desyncs `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` used by default finalization.
