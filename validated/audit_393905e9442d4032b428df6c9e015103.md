### Title
EI credentials can trigger `RunJobV2` for arbitrary int-ID jobs not bound to that EI - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates the int32 job-ID run-trigger path on `auth.GetAuthenticatedUser(c)` returning `true`, intending (per its own comment) to restrict this path to logged-in users and exclude External Initiators. However, `AuthenticateExternalInitiator` in `core/web/auth/auth.go` sets the same `SessionUserKey` context value to a synthetic `clsessions.User{Role: clsessions.UserRoleRun}` for any successfully authenticated EI, so `GetAuthenticatedUser` returns `true` for EI callers as well, defeating the intended restriction.

### Finding Description
`Create()` checks:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser { ... prc.App.RunJobV2(ctx, jobID, nil) ... }
``` [1](#0-0) 

But `AuthenticateExternalInitiator` explicitly assigns the same session key used by `GetAuthenticatedUser`:
```go
c.Set(SessionExternalInitiatorKey, ei)
// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
// of 'run' (required to trigger job runs)
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [2](#0-1) 

`GetAuthenticatedUser` simply reads `SessionUserKey` without regard to whether it originated from a real user session/API-token or from EI middleware:
```go
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	...
}
``` [3](#0-2) 

Consequently, if the `/v2/jobs/:ID/runs` route's authentication middleware chain includes `AuthenticateExternalInitiator` (alongside session/token auth, as is standard pattern for job-run endpoints, illustrated by the EI-authenticated POST to `/v2/jobs/<uuid>/runs` in `TestRunner_WebhookJobRemoved`) [4](#0-3) , a successfully authenticated EI will pass the `isUser` gate and reach `prc.App.RunJobV2(ctx, jobID, nil)`.

`RunJobV2` itself performs no EI-to-job binding check — it only looks up the job by ID:
```go
func (app *ChainlinkApplication) RunJobV2(ctx context.Context, jobID int32, meta map[string]any) (int64, error) {
	if build.IsProd() {
		return 0, errors.New("manual job runs not supported on secure builds")
	}
	jb, err := app.jobORM.FindJob(ctx, jobID)
	...
}
``` [5](#0-4) 

So there is no code path anywhere in `Create()` → `RunJobV2()` that verifies the calling EI is associated with the target job (`bridges.ExternalInitiator` binding to `job.WebhookSpec.ExternalInitiatorWebhookSpecs`). Any authenticated EI can trigger a run for any int-ID job as long as `isUser` is satisfied by the synthetic Run-role user.

### Impact Explanation
Cross-job run triggering: an EI credential scoped/intended for job A can trigger pipeline execution of job B, potentially causing unauthorized on-chain side effects (e.g. Ethereum transactions, VRF fulfillment simulation, etc., depending on job type) or unwanted resource consumption/DoS via repeated triggering of unrelated jobs. This falls under "unauthorized job run" / authorization bypass in the Chainlink bounty impact classes.

### Likelihood Explanation
Important caveat: `RunJobV2` is explicitly gated by `build.IsProd()`, returning an error on secure/production builds [6](#0-5) . This significantly limits real-world exploitability to non-production builds (dev/testnet nodes not compiled with the "prod" build flag). On any node where this manual-run path is reachable, the precondition is minimal: any valid EI `AccessKey`/`Secret` pair (which can belong to an EI not associated with the target job) is sufficient, and no user-role escalation or extra secrets are needed — the bypass is deterministic and repeatable.

### Recommendation
In `PipelineRunsController.Create`, do not rely solely on `auth.GetAuthenticatedUser`; explicitly reject requests where `auth.GetAuthenticatedExternalInitiator(c)` returns `true` (i.e., distinguish real user sessions/API tokens from EI-derived synthetic users), matching the existing code comment's intent ("EIs not allowed"). Alternatively, introduce a distinct context key/flag set only by real user authentication methods (`AuthenticateBySession`/`AuthenticateByToken`) rather than reusing `SessionUserKey` for EI's synthetic run-role user.

### Proof of Concept
1. Handler-level integration test in `core/web/pipeline_runs_controller_test.go`:
   - Build a non-prod test `Application` (as done elsewhere in the test file) with two jobs having int IDs, `jobA` and `jobB`, and one EI `foo` bound to `jobA` via a webhook spec's `ExternalInitiatorWebhookSpecs`.
   - Authenticate as EI `foo` using `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers (mirroring `TestRunner_WebhookJobRemoved`'s pattern) [4](#0-3) .
   - POST to `/v2/jobs/<jobB.ID>/runs` (int ID, not `jobA`) using the EI's credentials.
   - Assert the response is NOT 200/201 with a created pipeline run (expected: 401/403 rejection) — currently it will succeed and call `RunJobV2(ctx, jobB.ID, nil)`, proving the bypass.
2. Unit test on `auth.GetAuthenticatedUser` combined with `AuthenticateExternalInitiator`: construct a `gin.Context`, invoke `AuthenticateExternalInitiator`, then call `GetAuthenticatedUser(c)` and assert it returns `(user, true)` with `user.Role == clsessions.UserRoleRun`, demonstrating that `isUser` cannot distinguish EI callers from real users.
