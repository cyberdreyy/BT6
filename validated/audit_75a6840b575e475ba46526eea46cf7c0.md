### Title
Node-side signer weight aggregator double-counts a single signer's weight when it flips a Rejected vote to Accepted on the same block, letting stale rejection weight coexist with fresh acceptance weight - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` tallies `BlockStatus.total_weight_approved` and `total_weight_rejected` from `BlockResponse` messages published by signers. The `Rejected` branch guards against double counting by checking `block.responded_signers.insert(slot_id)` before adding weight, so an `Accepted` sent first and a later `Rejected` from the same signer will *not* add rejection weight. But the `Accepted` branch does not perform the equivalent check against `responded_signers`; it only dedupes against `gathered_signatures` (which is specific to the accept path). If a signer first sends `Rejected` (weight added to `total_weight_rejected`, slot recorded in `responded_signers`) and later sends `Accepted` for the same block (a supported, one-signer-triggered scenario — the signer protocol explicitly allows reconsidering certain rejections, see `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs`), the `Accepted` branch adds that signer's weight into `total_weight_approved` as well, without removing/adjusting the earlier `total_weight_rejected` contribution.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`:

- Rejected handling (guarded, correct): [1](#0-0) 
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block
        .total_weight_rejected
        .saturating_add(signer_entry.weight);
```
This only adds rejection weight the first time this signer's slot is seen for the block (across accept/reject).

- Accepted handling (unguarded against a prior rejection): [2](#0-1) 
```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block
        .total_weight_approved
        .saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
```
This checks only `gathered_signatures` (which is empty the first time an `Accepted` message from this signer for this block is seen), not whether the same slot already contributed weight to `total_weight_rejected` via `responded_signers`. So a Reject→Accept transition from a single signer for the same block causes that signer's weight to be counted in **both** `total_weight_approved` and `total_weight_rejected` simultaneously.

This asymmetry is directly analogous to the reported bug class: one code path (`Reject` after `Accept`) is correctly guarded, but the mirror path (`Accept` after `Reject`) silently produces an incorrect aggregate value (an inflated/`stale` weight persists in the wrong bucket) because the check used doesn't actually verify the *current* true state of that signer's vote — the same category of "half of the invariant reads stale/incorrect data" defect as `raw_call`'s asymmetric `MLOAD` bug.

This double count breaks the safety invariant relied on by `stacks-node/src/nakamoto_node/signer_coordinator.rs`, which assumes `total_weight_approved` and `total_weight_rejected` are mutually exclusive per-signer contributions bounded by `self.total_weight`: [3](#0-2) 
The rejection-threshold check (`total_weight_rejected + weight_threshold > total_weight`) is evaluated before the acceptance-threshold check (`total_weight_approved >= weight_threshold`). With the double count, a signer that legitimately reconsidered and voted `Accepted` still leaves its earlier `Rejected` weight "alive" in `total_weight_rejected`, artificially pushing the rejection tally toward/over the 30% blocking-minority threshold using weight that should have been retracted, even while the true, live votes have crossed the 70% acceptance threshold.

### Impact Explanation
This can cause the miner (`signer_coordinator.rs`) to erroneously treat a validly, sufficiently-signed block as globally rejected (`SignersRejected`) due to phantom double-counted rejection weight from a single signer who actually switched its vote to acceptance — i.e., an accepted vote gets miscounted as (also) a rejection, corrupting the aggregated-weight-vs-verified-accepts equality that block finalization depends on. This is a liveness wedge: legitimately signed blocks can be discarded and retried, and because the underlying trigger (a signer reconsidering one of the re-evaluable reject reasons) is a normal protocol occurrence that can recur across proposals, this can repeatedly stall block production for a given miner/tenure.

### Likelihood Explanation
No majority or malicious behavior is required — a single, honest signer legitimately reconsidering its own earlier rejection (a feature explicitly supported since changelog entry "3.1.0.0.8.0: For some rejection reasons, a signer will reconsider a block proposal that it previously rejected") triggers the Reject→Accept sequence for the same block. The bug is purely a bookkeeping defect in the node-side StackerDB listener aggregation and is reachable by ordinary protocol operation, one signer, and gossip of two consecutive StackerDB chunks.

### Recommendation
In the `Accepted` branch of `stackerdb_listener.rs`, check `block.responded_signers` (or otherwise detect a prior `Rejected` contribution from the same `slot_id`) before adding to `total_weight_approved`; if the signer previously contributed to `total_weight_rejected`, subtract/retract that contribution (symmetric to how the `Rejected` branch already guards against a prior `Accepted`). Ensure a single signer's weight is counted in exactly one of `total_weight_approved` / `total_weight_rejected` at any time, mirroring the fix already applied on the signer side (CHANGELOG: "Do not count both a block acceptance and a block rejection for the same signer/block").
