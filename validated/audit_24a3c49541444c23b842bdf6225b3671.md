### Title
Unprivileged "view" role user can bypass `RequiresEditRole` job-creation authorization by using the GraphQL `createJob` mutation instead of `POST /v2/jobs` - ([File: core/web/router.go], [File: core/web/resolver/mutation.go])

### Summary
The REST endpoint for creating jobs is explicitly gated behind an edit-role check, but the GraphQL mutation that performs the same job-creation action is reachable through a separate code path (`/query`) that only requires session authentication, with no equivalent role check found in the mutation resolver. This mirrors the reported Crestal bug class: a protected creation action (`createAgentWithWhitelistUsers`) has an alternate, unguarded creation function (`createAgentWithNFT`) that achieves the same effect without the intended access-control check.

### Finding Description
`core/web/router.go` registers the REST job-creation route with an explicit role guard: [1](#0-0) 

This wraps `jc.Create` with `auth.RequiresEditRole`, which rejects any authenticated user whose role is `UserRoleView`: [2](#0-1) 

However, the GraphQL endpoint `/query` is wired up with only `auth.AuthenticateGQL` (session authentication), and no separate role-based middleware: [3](#0-2) 

Searching `core/web/resolver/mutation.go` (which contains the `CreateJob` mutation resolver referenced by the GraphQL schema) for any of `RequiresEditRole`, `RequiresAdminRole`, `GetAuthenticatedUser`, or `SessionUserKey` returned no matches, indicating the mutation resolver does not perform its own role check before creating a job. This means a session-authenticated user with only the `view` role — who is explicitly blocked from `POST /v2/jobs` by `RequiresEditRole` — could still call the `createJob` GraphQL mutation over `/query` and have the job created, bypassing the intended edit-role restriction, in the same way `createAgentWithNFT` bypassed the whitelist check that `createAgentWithWhitelistUsers` enforced.

Note: I was not able to fully read the body of `CreateJob` inside `core/web/resolver/mutation.go` within the available tool budget to conclusively confirm there is no role check performed via a different mechanism (e.g., inside a shared resolver helper or middleware in `loader.Middleware`). This should be verified directly against the full resolver and `loader` middleware source before treating this as confirmed.

### Impact Explanation
If confirmed, a low-privileged `view`-role user (or any credential intended to be read-only) could create arbitrary job specs (webhook, cron, direct request, OCR, etc.) via the GraphQL API, which is a significant authorization bypass — job creation can trigger fund-moving transactions, external HTTP calls, and other privileged node behavior that the `view` role is specifically meant to be excluded from.

### Likelihood Explanation
Likelihood depends entirely on whether the GraphQL resolver independently enforces role checks elsewhere (e.g. a wrapping directive, or checks inside individual resolver functions not visible in the searched file). Given that the REST controller relies on router-level middleware (`RequiresEditRole`) rather than a check inside the controller method itself, and no equivalent middleware exists on the `/query` route, there's a strong likelihood that the same defense is simply missing on the GraphQL path unless explicitly added inside the resolver code that wasn't fully inspected.

### Recommendation
- Add an explicit role check equivalent to `RequiresEditRole`/`RequiresAdminRole` inside every mutation resolver in `core/web/resolver/mutation.go` that performs a create/update/delete operation (job creation, bridge creation, key management, etc.), using `auth.GetAuthenticatedUser(ctx)` and checking `user.Role`.
- Alternatively/additionally, apply role-based middleware at the GraphQL transport layer (in `NewRouter`/`graphqlHandler`) that inspects the requested mutation name and enforces the same role matrix used in `router.go` for REST routes.
- Audit all GraphQL mutations for parity with their REST-endpoint role requirements, since this analysis found no role-check keywords anywhere in `mutation.go`.

### Proof of Concept
Conceptual PoC (not executed, pending confirmation of resolver internals):
1. Create a user with `UserRoleView`.
2. Attempt `POST /v2/jobs` with a valid job TOML spec and the view-role session cookie/token → expect `401 Unauthorized` due to `RequiresEditRole`.
3. Send the same job-creation payload via `POST /query` with a GraphQL `mutation { createJob(input: {...}) { ... } }` body using the same view-role session.
4. If the job is created successfully (HTTP 200 with job data returned) despite the view role, this confirms the authorization bypass analogous to the `createAgentWithNFT` vs `createAgentWithWhitelistUsers` issue.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
