### Title
Integer underflow in `normalizeHex` causes panic via unprefixed hex `workflowID`/`workflowOwner` in gateway HTTP trigger requests - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The gateway's `workflows.execute` HTTP trigger handler validates `workflowID`/`workflowOwner` length assuming a `"0x"` prefix is present, but does not actually require the prefix. An attacker can submit a hex string of the exact expected total length without the `"0x"` prefix, which passes validation but then underflows a length subtraction in `normalizeHex`, causing `strings.Repeat` to panic on a negative count.

### Finding Description
`validateHexInput` only checks `len(input) > expectedLength` and that `hex.DecodeString` succeeds on the value after stripping an optional `"0x"` prefix; it never enforces that the `"0x"` prefix actually be present: [1](#0-0) 

Later, `normalizeHex` unconditionally assumes 2 characters were consumed by an `"0x"` prefix when computing the amount of zero-padding to add: [2](#0-1) 

If a client submits a `workflowID` consisting of exactly `workflowIDLength` (66) raw hex characters with **no** `"0x"` prefix (e.g., 66 valid hex digits), `validateHexInput` accepts it (`len == 66 <= 66`, and `hex.DecodeString` on the un-prefixed value succeeds since it's valid hex of even length). In `normalizeHex`, `strings.TrimPrefix(input, "0x")` is a no-op (no `"0x"` present), so `hexStr` retains its full 66-character length. `expectedHexLength` is computed as `66-2=64`, and `expectedHexLength-len(hexStr)` becomes `64-66=-2`. `strings.Repeat("0", -2)` panics with `"strings: negative Repeat count"`. The identical logic and reachability applies to `workflowOwner` (`workflowOwnerLength=42`, so a 42-character un-prefixed hex string triggers `40-42=-2`).

Both `resolveWorkflowID` and its call to `normalizeHex` are reached directly from `HandleUserTriggerRequest`, which is the entry point for the unauthenticated `workflows.execute` gateway trigger request path (validated only for length/hex-format, not the `"0x"` prefix), before any node/DON authorization occurs: [3](#0-2) [4](#0-3) 

This is directly analogous to the referenced CVE-2022-21685 class of bug: attacker-controlled length inputs subtracted without a bounds check, producing an integer underflow that crashes the process path handling the request.

### Impact Explanation
A panic raised deep in this call path (not wrapped in a `recover()` — I found no `recover()` calls anywhere under `core/services/gateway/` handler code, aside from unrelated test files) will propagate up through `HandleUserTriggerRequest` → `HandleJSONRPCUserMessage` → `gateway.ProcessRequest`. Whether this crashes only the single request/connection goroutine (if recovered by the underlying HTTP server, e.g., Go's `net/http` per-connection panic recovery) or brings down the whole gateway process depends on framework-level plumbing I could not fully verify from the available files (e.g. `core/services/gateway/network`, HTTP server setup). At minimum, this is a reliable per-request denial-of-service against the gateway's public trigger endpoint; if any code path invokes `ProcessRequest` from a raw goroutine without a top-level recover, it can crash the whole gateway node.

### Likelihood Explanation
High. No authentication or special privileges are required — this is reachable from any unprivileged HTTP client sending a `workflows.execute` message to the gateway's public trigger endpoint with a crafted `workflowID` or `workflowOwner` field, before any auth/authorization checks (`authorizeRequest`) are performed.

### Recommendation
Fix `validateHexInput`/`normalizeHex` to require and validate the `"0x"` prefix explicitly (reject inputs that don't start with `"0x"`), and/or guard `normalizeHex` against negative padding lengths by clamping to zero or returning an error before calling `strings.Repeat`.

### Proof of Concept
Send a `workflows.execute` JSON-RPC request to the gateway's user-facing endpoint with:
```json
{
  "method": "workflows.execute",
  "params": {
    "workflow": { "workflowID": "<66 raw hex chars with no 0x prefix, e.g. 'a'*66>" },
    "input": {}
  }
}
```
This passes `validateWorkflowID`/`validateHexInput` (length 66 ≤ 66, valid hex), then panics in `normalizeHex` via `strings.Repeat("0", -2)` when `resolveWorkflowID` is invoked.

**Uncertainty note:** I could not fully confirm from available files whether `gateway.ProcessRequest` is called within a goroutine lacking panic recovery (which would mean full-process crash) versus being recovered per-request by the underlying HTTP server; I recommend verifying this in `core/services/gateway/network` and the HTTP server bootstrap code to assess the precise blast radius.

func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) {
		return errors.New("must be lowercase")
	}

	if len(input) > expectedLength {
		return fmt.Errorf("hex string too long: expected at most %d characters, got %d", expectedLength, len(input))
	}

	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	if err != nil {
		return errors.New("must be a valid hex string")
	}

	return nil
}

// normalizeHex normalizes a hex string by stripping 0x prefix, padding with leading zeros, and adding 0x prefix back
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	// length-2 because we'll add "0x" prefix
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}

			return "", errors.New("workflow not found")
		}
