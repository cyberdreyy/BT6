Confirmed: `Timestamp` in `webapicap.TriggerRequestPayload` is `int64` (attacker-controlled JSON field), and the staleness check in `handler.go` mixes it with `uint` arithmetic in a subtraction that is vulnerable to integer underflow/wraparound — directly analogous to the CVE-2021-46102 pattern (unchecked attacker-influenced value used in unvalidated arithmetic causing an integer overflow/wraparound that corrupts a security-relevant computation).

### Title
Integer underflow in gateway trigger message staleness check allows negative/attacker-controlled timestamps to bypass freshness validation - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` validates that an incoming `web_api_trigger` message is not stale by computing `uint(time.Now().Unix()) - h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)`. `payload.Timestamp` is an attacker-supplied `int64` field taken directly from the unauthenticated-content JSON payload of the gateway message and cast to `uint` without any bounds/sign validation.

### Finding Description
The handler decodes the trigger payload from client/DON-forwarded content and only checks `payload.Timestamp == 0`, never checking negative or absurdly large values: [1](#0-0) 
The staleness check itself performs unchecked unsigned arithmetic on this attacker-controlled value: [2](#0-1) 
Because `payload.Timestamp` is `int64` and is cast directly to `uint` via `uint(payload.Timestamp)`, a negative timestamp (e.g. `-1`) wraps around to a value near `math.MaxUint64`. Since the check is `now_minus_maxage > uint(payload.Timestamp)`, an attacker who supplies a large negative `Timestamp` produces an enormous unsigned value on the right-hand side, making the comparison always false and defeating the intended "stale message" rejection — the exact same bug class as CVE-2021-46102: an unchecked, attacker-influenced integer value participates in raw arithmetic/casting without range validation, producing a wraparound that undermines a security check (there, memory relocation bounds; here, message freshness/replay-window enforcement).

### Impact Explanation
This staleness/freshness check is the DON node's only defense (besides signature validity) against replay of very old signed trigger messages relayed through the internet-facing Gateway from `web_api_trigger` capability messages. Bypassing it does not itself forge a signature, but it removes the freshness guard entirely for a large class of crafted `Timestamp` values, enabling replay of previously valid signed trigger events far outside the intended 2-minute (`defaultCallbackMaxAgeSec`) freshness window, and allowing attacker-influenced control over how the "stale message" rejection is enforced. The comment "TODO: apply allowlist and rate-limiting here" right below this check indicates the freshness gate is one of the few controls currently present at this stage.

### Likelihood Explanation
The `Timestamp` field is fully attacker-controlled JSON input on a message path (`HandleLegacyUserMessage`) reachable via the gateway from external, unprivileged callers/DON forwarding, requiring no special privilege beyond crafting a JSON-RPC payload with a negative `timestamp` value. No additional preconditions are required beyond message signature validity (which is orthogonal to this check).

### Recommendation
Reject negative `Timestamp` values explicitly before any unsigned conversion, and perform the freshness comparison using signed 64-bit arithmetic (or `time.Unix` comparisons) rather than casting to `uint`:
```go
if payload.Timestamp <= 0 {
    return ... invalid timestamp ...
}
age := time.Now().Unix() - payload.Timestamp
if age < 0 || age > int64(h.config.MaxAllowedMessageAgeSec) {
    return ... stale message ...
}
```

### Proof of Concept
1. Craft a `web_api_trigger` JSON-RPC request whose JSON payload sets `"timestamp": -9999999999` (a large negative `int64`).
2. Sign the message with a valid key as in the existing test helper `triggerRequest`/`gatewayRequest`: [3](#0-2) 
3. Submit through `HandleLegacyUserMessage`. Because `uint(payload.Timestamp)` wraps to a value near `math.MaxUint64`, the comparison `uint(now)-MaxAllowedMessageAgeSec > uint(payload.Timestamp)` evaluates to `false`, so the "stale message" branch at [4](#0-3)  is skipped and the message is forwarded to DON nodes as if fresh.
