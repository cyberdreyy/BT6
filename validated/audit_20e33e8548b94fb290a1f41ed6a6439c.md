### Title
Destination-chain fee parameters in `createDstEscrow` are fully attacker-controlled, allowing protocol/integrator fee avoidance - (File: contracts/BaseEscrowFactory.sol)

### Summary
`BaseEscrowFactory.createDstEscrow` accepts `dstImmutables` entirely from `msg.sender` calldata, including the `parameters` field that encodes `protocolFeeAmount` and `integratorFeeAmount`. Unlike the source-side flow, where these values are computed on-chain by `FeeTaker._getFeeAmounts` inside `_postInteraction` [1](#0-0) , the destination-side deployment never recomputes or validates these amounts against any commitment made on the source chain. Any unprivileged caller can therefore deploy a destination escrow with `protocolFeeAmount = 0` and `integratorFeeAmount = 0`, fully avoiding the fee payments that `EscrowDst._withdraw` would otherwise route to the protocol/integrator fee recipients.

### Finding Description
`createDstEscrow` takes the full `IBaseEscrow.Immutables calldata dstImmutables` struct directly from the caller and only validates the native/token balances and the cancellation-timing relationship to the source chain: [2](#0-1) . It never checks `dstImmutables.parameters` against the `DstImmutablesComplement.parameters` value that was computed and emitted during the source-side `_postInteraction` call [3](#0-2) . That emitted value is documented as purely informational, "Emitted on EscrowSrc deployment to recreate EscrowSrc and EscrowDst immutables off-chain" [4](#0-3)  — there is no on-chain binding.

`EscrowDst._withdraw` blindly trusts whatever `protocolFeeAmount`/`integratorFeeAmount` are encoded in the immutables it receives (which must simply hash-match the escrow's own CREATE2 salt, itself derived from the same attacker-supplied immutables): [5](#0-4) 

Because the salt/address of the destination escrow is deterministically derived from the full `Immutables` (including `parameters`) via `hashMem()`/CREATE2, an attacker simply crafts a `dstImmutables` struct with a legitimate `orderHash`/`hashlock`/`maker`/`token`/`amount` (all publicly visible from the corresponding `SrcEscrowCreated` event) but with `protocolFeeAmount = 0` and `integratorFeeAmount = 0` packed into `parameters`, then calls `createDstEscrow`, funding the escrow with their own tokens/native value as required by the balance checks. This is exactly analogous to the referenced report's root cause: a fee amount that is supposed to be levied on an unprivileged actor's calldata is fully attacker-controllable and defaults/can be forced to zero, with no on-chain enforcement tying it to the correct value.

### Impact Explanation
When the maker later withdraws (or the resolver/public withdrawer triggers `_withdraw`), `integratorFeeAmount` and `protocolFeeAmount` are read straight from the (attacker-supplied) immutables and, being zero, no transfer occurs to `integratorFeeRecipient`/`protocolFeeRecipient`; the maker instead receives the full `immutables.amount` [6](#0-5) . This is a permanent loss of protocol/integrator fee revenue that was expected on every fill — fitting the bounty's High severity: "theft or permanent loss of unclaimed fee-like value."

### Likelihood Explanation
`createDstEscrow` has no access-control restricting callers to a whitelisted/trusted resolver [7](#0-6) ; any address willing to front the destination token amount and safety deposit can call it directly, bypassing the intended off-chain relayer flow that would normally reuse the correct `DstImmutablesComplement.parameters`. No fuzzing/edge amount is required (unlike the original rounding-to-zero bug) — the fee bypass is deterministic and total, making exploitation straightforward for any self-interested actor acting as their own resolver.

### Recommendation
Bind the destination escrow's fee parameters to the source-chain commitment on-chain, e.g., by requiring `createDstEscrow` to receive and verify the `DstImmutablesComplement` (or its hash) against the corresponding `SrcEscrowCreated` event/order commitment, or by having the factory recompute `protocolFeeAmount`/`integratorFeeAmount` itself using the same fee-percentage inputs used on the source side, instead of trusting attacker-supplied `parameters` verbatim.

### Proof of Concept
1. Observe a `SrcEscrowCreated` event containing `orderHash`, `hashlock`, `maker`, destination `token`/`amount`/`safetyDeposit`, and the correct `DstImmutablesComplement.parameters` (with non-zero `protocolFeeAmount`/`integratorFeeAmount`).
2. Craft a new `IBaseEscrow.Immutables` struct reusing the same `orderHash`, `hashlock`, `maker`, `token`, `amount`, `safetyDeposit`, `timelocks`, but replace `parameters` with `abi.encode(0, 0, protocolFeeRecipient, integratorFeeRecipient)`.
3. Call `createDstEscrow(dstImmutables, srcCancellationTimestamp)` funding the required native/token amounts from any unprivileged EOA — call succeeds, since only balance and timing checks are performed [2](#0-1) .
4. After the secret is revealed and `withdraw`/`publicWithdraw` is called, `_withdraw` transfers `0` to both fee recipients and the full `amount` to the maker [6](#0-5) , confirming the protocol/integrator fee was never collected.

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```

```text
    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```
