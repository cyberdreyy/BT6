### Title
No refund on failed multisig deployment — attached deposit is silently consumed - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` schedules a single promise chain (`create_account` → `deploy_contract` → `transfer` → `function_call("new", ...)`) and returns it directly to the caller with no `.then()` callback attached. If any later action in the chain fails (e.g. the `new` function_call fails due to bad `members`/`num_confirmations`, or insufficient gas because `env::prepaid_gas() - CREATE_CALL_GAS` underflows/is too small), the attached deposit that was already transferred to the new account is never refunded to the caller, since the factory has no logic to detect failure and return funds.

### Finding Description
The binding that should hold is: `deposit_returned_to_caller == attached_deposit` whenever the deployment's `new` initialization fails, i.e., a failed deployment must refund the payer.

Tracing `create` in [1](#0-0) , the function builds one promise chain and returns it as-is:
```
Promise::new(account_id)
    .create_account()
    .deploy_contract(CODE.to_vec())
    .transfer(env::attached_deposit())
    .function_call(b"new".to_vec(), ..., 0, env::prepaid_gas() - CREATE_CALL_GAS)
```
There is no `.then(Self::ext(...).on_create(...))` callback, and no `is_promise_success()` check anywhere in the file — confirmed by the grep across the file showing only a single match for the search terms (the `Promise` import), versus `lockup-factory/src/lib.rs` and `staking-pool-factory/src/lib.rs` which each contain callback/refund-related code (`on_create`/`then`/`is_promise_success` matches). This shows the pattern used elsewhere in the same repo — attach a callback that checks `is_promise_success()` and refunds the deposit on failure — was intentionally or accidentally omitted here.

Exploit flow: an attacker calls `create` with an attached deposit and a `members`/`num_confirmations` combination that causes the `new` constructor on `multisig2` to panic (e.g., `num_confirmations` exceeding the number of members, which the `multisig2` contract asserts against in its `new`). `create_account`, `deploy_contract`, and `transfer` all succeed (the account is created, funded, and code deployed), but the final `function_call` fails. Because there is no callback, the factory transaction as a whole still "succeeds" from the outer caller's perspective in that the deposit has left the factory and is now sitting in an uninitialized (or partially initialized) new account, with no code path to reclaim it. No `assert_self()`, `is_promise_success()`, or refund logic exists to intercept this.

### Impact Explanation
The attacker's own deposit becomes stranded in a newly created, non-functional multisig account instead of being refunded — this is the attacker griefing themselves in the simplest case, but the same pattern applies to any accounting system or dApp that treats the `create` call's deposit as fungible/recoverable on failure. More importantly, per the audit's stated invariant ("a failed deployment refunds the payer"), the actual behavior diverges from the expected behavior: deposit accounting kept by any off-chain indexer, exchange, or dependent contract that assumes `create` either fully succeeds or fully refunds will diverge from on-chain reality, since funds are consumed without a successful multisig being created. This matches the "accounting value diverges from reality and another party settles on it" High-severity category described in the question. No NEAR leaves via an unauthorized transfer to a third party (it lands in an account named by the attacker), so this does not rise to Critical, but the missing refund path is a real, reproducible break of the stated invariant.

### Likelihood Explanation
Trivial to trigger: any account can call `create` with a deposit and an intentionally invalid `members`/`num_confirmations` pair (or by crafting `num_confirmations` to be 0 or larger than `members.len()`, which `multisig2::new` is expected to reject). No privileged role, foundation account, or existing multisig membership is needed — this is exactly the unprivileged attacker profile described. It's repeatable across arbitrarily many `name` values (each `create` call targets a fresh subaccount), so the attacker can trigger this scenario as many times as desired, though each time it consumes their own deposit (self-inflicted loss) rather than gaining a profit — the primary externally-relevant impact is the broken accounting invariant/refund guarantee itself.

### Recommendation
Attach a callback to the promise chain returned from `create`, e.g. `.then(Self::ext(env::current_account_id()).with_static_gas(...).on_create(predecessor_account_id, attached_deposit, account_id))`, implement `on_create` guarded by `assert_self()`, check `is_promise_success()`, and if the deployment/init failed, refund `attached_deposit` back to the original caller (and optionally delete the failed account).

```rust
#[tokio::test]
async fn test_failed_deployment_does_not_refund() {
    // 1. Deploy multisig-factory to a worker sandbox.
    // 2. Record attacker balance B0 before calling create.
    // 3. Call create(name, members=[], num_confirmations=1, deposit=1 NEAR, gas=X)

    //    multisig2::new to panic (assert num_confirmations <= members.len()).
    // 4. Await outcome: assert final receipt for "new" call failed (ExecutionStatus::Failure).
    // 5. Assert the new subaccount exists and holds ~1 NEAR (deposit was transferred and stranded).
    // 6. Record attacker balance B1 after the transaction.
    // 7. Assert B0 - B1 ≈ 1 NEAR + gas burned (i.e., the deposit was NOT refunded),
    //    proving deposit_returned_to_caller != attached_deposit, violating the refund invariant.
}
```
This demonstrates the binding `deposit_returned_to_caller == attached_deposit` fails to hold after a failed `new` call, with no callback present to enforce it in `multisig-factory/src/lib.rs::create`.
