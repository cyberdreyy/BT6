### Title
Unprotected, front-runnable initializer on the global `FeeState` singleton lets any user seize `global_fee_admin` control - (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
The Stader `VaultProxy.initialise` bug is a canonical "unprotected initializer" issue: an implementation/singleton account that is supposed to be configured exactly once by the deployer has no access-control gate on who can call its init function, so whoever calls it first takes control of security-critical state used by every downstream user. The equivalent pattern exists in marginfi's `marginfi_group_initialize_fee_state` instruction, which initializes the program-wide `FeeState` PDA and lets the caller supply `admin_key` and `fee_wallet` with no restriction on who the caller is.

### Finding Description
`InitFeeState::initialize_fee_state` writes `admin_key` and `fee_wallet` directly from caller-supplied arguments into the `FeeState` account, and the `Accounts` struct only requires an arbitrary `Signer` as `payer` — there is no check that the caller is the program's upgrade authority, deployer, or any other pre-established authority: [1](#0-0) 

The account struct backing this instruction contains no admin/authority constraint at all — just `payer: Signer` and the PDA to be created: [2](#0-1) 

Because the `fee_state` account is a PDA derived only from the fixed `FEE_STATE_SEED` (i.e., a global singleton, not scoped per-caller), Anchor's `init` constraint guarantees it can be created only once program-wide. Whoever submits this instruction first — legitimate deployer or an attacker racing the deployment transaction — permanently becomes `global_fee_admin` and sets `global_fee_wallet` to an address of their choosing. This mirrors the Stader class of bug: a "run-once" initializer on a shared/implementation-like resource that lacks any authorization check, allowing an unprivileged actor to claim the privileged role before the legitimate owner does.

The `global_fee_admin` role that is captured this way has protocol-wide power, as documented: [3](#0-2) 

Every `MarginfiGroup` created afterward reads and caches the fee wallet/rates from this singleton at group-init time: [4](#0-3) 

The test harness itself acknowledges this is a race — it checks whether the `FeeState` account already exists before deciding whether to submit the init instruction, i.e., relies on nobody else initializing it first: [5](#0-4) 

### Impact Explanation
An attacker who front-runs the legitimate `marginfi_group_initialize_fee_state` call (e.g., during initial mainnet/staging deployment, or on any environment where this PDA has not yet been created) becomes the `global_fee_admin` and sets `global_fee_wallet` to their own address. From that position they can, per the documented admin powers, redirect program fee flows, change fee parameters, and control the pause-delegate admin — a durable, protocol-wide misconfiguration with direct financial effect (value redirection of protocol fees) and indirect effect on every `MarginfiGroup` subsequently initialized, since group init caches fee-state values from this singleton. This is analogous to the Stader finding's severity rationale: an unprivileged actor exploiting a missing access-control gate on a "run-once" initializer to seize control of state relied upon by the whole system, at essentially no cost beyond a small race/transaction fee.

### Likelihood Explanation
Exploitation requires the attacker to be the first to submit this specific instruction against a freshly deployed (or not-yet-initialized) program instance — a narrow window, but a realistic one during deployment, especially given that deployment and initialization are typically separate transactions/observable on-chain (mempool/slot visibility), and the repo's own test utility shows the flow depends on checking whether this account already exists rather than any cryptographic/authority guarantee. Once any legitimate initialization succeeds first, the PDA is permanently occupied and the window closes (Anchor `init` prevents re-initialization). This is lower likelihood than a persistent bug but is a genuine deployment-time authorization gap, not a purely theoretical issue.

### Recommendation
Gate `InitFeeState` behind an authority check tied to the program's actual deployer/upgrade authority (e.g., verify the signer against the `ProgramData` account's `upgrade_authority_address`, as Kamino's `initGlobalConfig`/`initFarmsForReserve` do by requiring the `programData` account), or perform this initialization atomically within the deployment transaction/script so no external actor can race it. At minimum, add an explicit constraint requiring `payer` to match a known, hardcoded deployer pubkey for this one-time setup instruction.

### Proof of Concept
1. Deploy (or upgrade to) a marginfi program instance where the `FeeState` PDA (`seeds = [FEE_STATE_SEED]`) does not yet exist.
2. Before the legitimate deployer submits their `marginfi_group_initialize_fee_state` transaction, an attacker submits their own transaction calling the same instruction with `admin_key = attacker_pubkey` and `fee_wallet = attacker_pubkey`, paying the rent themselves.
3. Because the account is a PDA and `init` only requires the account not already exist, the attacker's transaction succeeds and permanently sets `fee_state.global_fee_admin` and `fee_state.global_fee_wallet` to attacker-controlled keys.
4. All subsequently created `MarginfiGroup`s cache the attacker-controlled fee wallet/rates from this singleton (`marginfi_group/initialize.rs`), and the attacker can use `edit_global_fee`-style instructions to further manipulate program fee parameters and the pause-delegate admin, per the `global_fee_admin` capabilities documented in `PERMISSIONS_AND_ROLES.md`.

// Runs once per program to init the global fee state.
use anchor_lang::prelude::*;
use marginfi_type_crate::{
    constants::FEE_STATE_SEED,
    types::{FeeState, WrappedI80F48},
};

#[allow(unused_variables)]
pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}
