### Title
Zero/unchecked oracle price on rate-limited withdraws lets a fixed-price bank bypass the group outflow rate limiter - (File: programs/marginfi/src/instructions/marginfi_account/withdraw.rs)

### Summary
The Octopus Network report flags a missing check that a price/amount field is not allowed to be zero. The closest reachable analog in marginfi-v2 is the group-rate-limit price-fetch path used by `lending_account_withdraw`, `kamino_withdraw`, `drift_withdraw`, `solend_withdraw`, and `juplend_withdraw`, where the fetched oracle price is validated to be non-zero only for the receivership/order-execution branch, not for the plain group-rate-limiter branch.

### Finding Description
In each withdraw handler the price used to value the outflow for the group rate limiter is fetched like this: [1](#0-0) 

```
let group_rate_limit_enabled = group.rate_limiter.is_enabled();
let price = if in_receivership_or_order_execution || group_rate_limit_enabled {
    let price = fetch_asset_price_for_bank_low_bias(...)?;
    // Validate price is non-zero during liquidation/deleverage to prevent exploits
    if in_receivership_or_order_execution {
        check!(price > I80F48::ZERO, MarginfiError::ZeroAssetPrice);
    }
    price
} else {
    I80F48::ZERO
};
```

Notice the `check!(price > I80F48::ZERO, ...)` only runs when `in_receivership_or_order_execution` is true. When only `group_rate_limit_enabled` is true (the normal, unprivileged withdraw path), a zero price is accepted silently and flows into `record_withdrawal_outflow`, which converts the withdrawn amount into a USD value via `calc_value(amount, price, ...)`. `calc_value` multiplies by `price` and simply returns whatever the product is, including `0` when `price == 0`: [2](#0-1) 

The same unguarded pattern is repeated verbatim in the Kamino, Solend, Drift and JupLend withdraw handlers: [3](#0-2) [4](#0-3) 

A bank can legitimately have a price of exactly `0`: `lending_pool_set_fixed_oracle_price` only rejects negative prices, explicitly permitting `price == 0`: [5](#0-4) 

and `OraclePriceFeedAdapter`'s `OracleSetup::Fixed` branch likewise only checks `price >= I80F48::ZERO`, not `> ZERO`: [6](#0-5) 

Consequently, once any bank in a group is configured with a fixed price of `0` (or, more generally, any oracle wiring that can legitimately/validly resolve to `0` without erroring, e.g. a `FixedKamino`/`FixedDrift` bank whose base fixed price is `0`), a permissionless, unprivileged withdraw against that bank will compute `record_withdrawal_outflow` with `price = 0`, driving the USD-denominated outflow value to `0` regardless of the actual token amount withdrawn. This defeats the entire purpose of the group-level rate limiter (which is designed to cap large-value withdrawals in USD terms), letting a user drain unlimited amounts of that asset through the "rate-limited" path without ever tripping the hourly/daily USD caps, because the accounting layer (`calc_value`/`record_withdrawal_outflow`) never rejects a zero price outside the receivership branch.

### Impact Explanation
The group rate limiter is a protocol-wide financial safety control meant to cap outflow value across all rate-limited withdrawal integrations (native, Kamino, Solend, Drift, JupLend). A missing zero-price guard on this specific path allows an unprivileged user to completely bypass that control for any bank whose price can resolve to zero, silently defeating a documented risk-mitigation mechanism with direct financial exposure (unbounded outflow bypassing the configured USD caps). This is analogous in class (missing zero check on a price feeding financial accounting) to the reported OCT price issue, but here the missing check has a concrete, exploitable effect on an unprivileged financial-safety mechanism, rather than being explicitly accepted as intentional protocol behavior.

### Likelihood Explanation
Requires: (1) group rate limiting enabled, and (2) at least one bank in the group with an oracle configuration that can legitimately return a price of `0` (most directly the `Fixed`/`FixedKamino`/`FixedDrift`/`FixedJuplend` oracle setups, which explicitly allow `price == 0` by design intent, e.g. to represent a "delisted"/zero-value asset). Given the existing test suite exercises `Fixed` price banks extensively and the code allows `price == 0` explicitly, this state is reachable without any special privilege by the withdrawing user — only the bank's oracle configuration (set by an admin, but not necessarily maliciously; it's an accepted valid state) needs to have a zero price at time of withdrawal.

### Recommendation
Apply the same `check!(price > I80F48::ZERO, MarginfiError::ZeroAssetPrice)` guard unconditionally whenever `group_rate_limit_enabled` is true (not only for `in_receivership_or_order_execution`), in all five withdraw handlers (`lending_account_withdraw`, `kamino_withdraw`, `drift_withdraw`, `solend_withdraw`, `juplend_withdraw`), so a zero-valued price cannot be used to value outflow for rate-limiting purposes.

### Proof of Concept
1. Admin configures a bank (e.g., via `lending_pool_set_fixed_oracle_price`) with `price = 0` (allowed, since the check only rejects negative values) — [7](#0-6) .
2. Group admin enables the group-level rate limiter (`GroupRateLimiter`) with a nonzero hourly/daily USD cap.
3. A user deposits tokens into that zero-priced bank and then calls `lending_account_withdraw` (or `kamino_withdraw`/`solend_withdraw`/etc.) for a large amount.
4. Because `in_receivership_or_order_execution` is false, the `check!(price > I80F48::ZERO, ...)` in [8](#0-7)  is skipped; `price = 0` is passed to `record_withdrawal_outflow`.
5. `calc_value(amount, 0, ...)` returns `0`, so the group rate limiter's `try_record_outflow` is called with `rate_limit_amount = 0` in USD terms, consuming none of the configured cap — the withdrawal succeeds and the outflow limiter never engages, regardless of withdrawal size.

```rust
pub fn calc_value(
    amount: I80F48,
    price: I80F48,
    mint_decimals: u8,
    weight: Option<I80F48>,
) -> MarginfiResult<I80F48> {
    if amount == I80F48::ZERO {
        return Ok(I80F48::ZERO);
    }

    let scaling_factor = EXP_10_I80F48[mint_decimals as usize];

    let weighted_asset_amount = if let Some(weight) = weight {
        amount.checked_mul(weight).unwrap()
    } else {
        amount
    };

    #[cfg(target_os = "solana")]
    debug!(
        "weighted_asset_qt: {}, price: {}, expo: {}",
        weighted_asset_amount, price, mint_decimals
    );

    let value = weighted_asset_amount
        .checked_mul(price)
        .ok_or_else(math_error!())?
        .checked_div(scaling_factor)
        .ok_or_else(math_error!())?;

    Ok(value)
}
```
