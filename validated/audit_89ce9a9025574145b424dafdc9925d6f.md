### Title
Permissionless "account pre-funding" griefing blocks legitimate `CreateAccount`/`CreateAccountWithSeed` — ([File: programs/system/src/system_processor.rs])

### Summary
The System Program's `CreateAccount` and `CreateAccountWithSeed` instructions reject account creation if the target address already holds any lamports, allowing any unprivileged user to permanently block a legitimate account creation at a known/derivable address by sending it a trivial amount of lamports first — the same "grief a permissionless, address-keyed creation with a minimal deposit" bug class as the reported RocketJoeFactory issue.

### Finding Description
`create_account()` in `programs/system/src/system_processor.rs` bails with `SystemError::AccountAlreadyInUse` whenever the `to` account already has `lamports > 0`, before any ownership/allocation check is even attempted: [1](#0-0) 

The same "already in use" gate exists for the seed-derived variant, which is resolved via `Address::create()`/`Pubkey::create_with_seed()` — a fully deterministic address that requires no signature from the target address itself, only from the `base` key: [2](#0-1) 

Because `CreateAccountWithSeed` (and PDAs used the same way by on-chain programs) resolve to deterministic addresses, any transaction submitter can precompute the target address off-chain and simply `Transfer` 1 lamport to it before the legitimate creator's `CreateAccount`/`CreateAccountWithSeed` transaction executes. Since `to.get_lamports() > 0` is now true, the legitimate creation permanently fails with `AccountAlreadyInUse` — this is functionally identical to the RocketJoeFactory bug class: a trivial-cost, permissionless action that "claims" an address/key namespace and prevents the rightful party from ever completing its intended one-time creation.

The severity of this exact griefing pattern is corroborated by the fact that Agave itself introduced a dedicated fix — the new `CreateAccountAllowPrefund` instruction (SIMD-0312) — specifically to let programs create an account "without checking for 0 lamports," for cases "where account has already had rent paid in whole or in part before creation": [3](#0-2) [4](#0-3) 

However, `CreateAccountAllowPrefund` is opt-in and feature-gated: [5](#0-4) 

It only protects callers that explicitly switch to the new instruction. The legacy `CreateAccount` / `CreateAccountWithSeed` instructions — still the default path used by essentially all existing on-chain programs, CLI tooling (e.g. nonce/stake/vote account creation), and SDKs — remain fully exposed to this pre-funding griefing vector.

### Impact Explanation
Any ordinary user can send a minimal `Transfer` (as little as 1 lamport) to a deterministically derivable target address before the rightful owner's account-creation transaction lands, permanently denying that party the ability to create the intended account at that address via the legacy instructions. For protocols/programs that rely on a specific derived address (via `create_with_seed`, PDAs materialized as system accounts, etc.) as a unique, one-time-use resource key — analogous to RocketJoeFactory keying `RJLaunchEvent` by `_token` — this enables a low-cost denial-of-service against the legitimate creator, exactly mirroring the reported bug class.

### Likelihood Explanation
High: the attack requires only knowledge of the deterministic target address (computable by anyone off-chain from public `base`/`seed`/`owner` values) and the cost of a single lamport transfer plus a transaction fee, with no special privileges, timing races beyond normal front-running, or validator cooperation required.

### Recommendation
Encourage/require callers (especially those with security-sensitive, address-keyed one-time creation semantics like RJLaunchEvent-style registries) to migrate to `CreateAccountAllowPrefund` once broadly activated, and consider deprecating/hardening the legacy `CreateAccount`/`CreateAccountWithSeed` "already in use" semantics (e.g., only bail on non-zero lamports when the account is also owned by a non-system program or has non-empty data) to remove the incentive/cost asymmetry that lets a 1-lamport donation permanently block legitimate account creation.

### Proof of Concept
1. Attacker computes `derived = Pubkey::create_with_seed(&victim_base, seed, &owner_program)` from public information.
2. Attacker submits `SystemInstruction::Transfer` sending 1 lamport to `derived`.
3. Victim later submits `SystemInstruction::CreateAccountWithSeed` (or `CreateAccount` if `derived` is otherwise predictable/known) targeting `derived`.
4. `create_account()` sees `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse`, as reproduced by the existing test `test_create_already_in_use`: [6](#0-5) 
5. The victim's account can never be created at that address using the legacy instruction path, permanently denying the intended resource.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
