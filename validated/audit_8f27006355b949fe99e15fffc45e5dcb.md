### Title
Owner token rescue can strand funded withdrawal claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.transferToken` lets the owner withdraw any amount of the underlying token without checking the strategy’s outstanding funded withdrawal receipts or `defaultRecoveryReserve`. [1](#0-0)  Consequently, an authorized rescue can leave the contract’s ERC20 balance below its recorded payout obligations, causing later claims to revert rather than paying the receipt holder. [2](#0-1) 

### Finding Description
Withdrawal requests mint strategy-token receipts to users and record their claim basis in `withdrawsRequests`, `instantWithdrawsRequests`, or post-default request storage. [3](#0-2)  The CDO funds ordinary requests through `collectWithdrawFunds`, which transfers underlying to the strategy and clears `pendingWithdraws`, but no aggregate variable tracks the funded amount still owed to receipt holders. [4](#0-3) 

Claims later burn the receipt and call `_transferFundedClaim`; that helper only protects `defaultRecoveryReserve` when it is nonzero and does not otherwise verify that the remaining balance covers all previously funded receipts. [5](#0-4) [2](#0-1)  Likewise, recovery claims decrement `defaultRecoveryReserve` and transfer underlying, but nothing prevents the owner from having removed that backing through `transferToken`. [6](#0-5) 

### Impact Explanation
If the owner withdraws 90 underlying from a vault holding 100 underlying reserved for a 100-underlying receipt, the user’s next claim attempts to transfer 100 from a balance of 10 and reverts. [7](#0-6)  Because claims are paid as their full recorded amount, the deficit can permanently freeze the unclaimed funds unless the owner replenishes the vault. [8](#0-7) 

### Likelihood Explanation
The issue requires the owner to use the documented emergency-rescue path on the accounting-backed underlying token, so it is not directly triggerable by an unprivileged attacker. [1](#0-0)  Nevertheless, the function accepts arbitrary tokens and amounts and has no distinction between recoverable surplus and funds already assigned to users, making an operational rescue sufficient to create the mismatch. [2](#0-1) 

### Recommendation
Disallow `transferToken` for `token`/`underlyingToken`, or add an explicit `fundedClaimsReserve` that is increased when withdrawal funds are collected and decreased when funded claims are paid. [4](#0-3)  If underlying rescues must remain possible, require `underlyingToken.balanceOf(address(this)) - value >= fundedClaimsReserve + defaultRecoveryReserve` before transferring. [9](#0-8)

        IdleCreditVault vault = new IdleCreditVault();
        MockCDO cdo = new MockCDO(asset, vault);

        vault.initialize(
            address(asset),
            address(this),
            address(0xBEEF),
            address(0xB0B),
            "Borrower",
            0

        vault.setWhitelistedCDO(address(cdo));

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }

  /// @notice Transfer default recovery reserve to a user.
  /// @param _user claim receiver
  /// @param _amount amount to transfer
  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
