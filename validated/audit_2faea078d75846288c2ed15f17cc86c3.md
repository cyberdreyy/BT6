## Finding

### Title
Reorg permit exclusion is not scoped to the sanctioned replacement tenure, letting an unrelated tenure bypass the equivocation guard - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The signer's double-sign ("equivocation") guard excludes a conflicting prior signature only when a "reorg permit" for that conflict's tenure still stands. The permit-validity check (`reorg_permit_stands`) verifies only that the *permitting sortition* is still canonical — it never checks that the block currently being evaluated for signing actually belongs to that permitting tenure. Any later proposal from a completely different, unsanctioned tenure that happens to conflict at the same height with the already-superseded tenure's signed block inherits the exclusion for free, letting the signer place a second, conflicting signature at the same height.

### Finding Description
`check_parent_tenure_choice` sanctions a specific reorg: tenure `self` (identified by `self.consensus_hash` / `self.burn_block_hash`) is permitted to replace tenure `tenure`, and this is recorded via `record_superseded_tenure` → `SignerDb::mark_tenure_superseded(tenure.consensus_hash, ..., superseded_by_consensus_hash = self.consensus_hash, superseded_by_burn_block_hash = self.burn_block_hash)`. [1](#0-0) 

Later, when a new block reaches the pre-commit threshold, `handle_block_pre_commit` fetches all signed conflicts at or above its height in ANY tenure via `get_signed_conflicts`, and excludes a conflict from blocking iff `reorg_permit_stands` returns true: [2](#0-1) 

`reorg_permit_stands` only checks whether the permitting sortition (`conflict.superseded_by.burn_block_hash`) is still canonical on the node — it never compares the permitting tenure to the tenure of the block currently being signed: [3](#0-2) 

The DB join that produces `conflict.superseded_by` also only keys on the *conflict's* own consensus hash, not on the new proposal's tenure: [4](#0-3) 

So the permit — granted specifically so that tenure C's replacement of tenure A is not blocked by our earlier signature over A — is consumed by *any* later proposal, from any tenure F, that happens to conflict with A at the same height, as long as C's sortition is still canonical. This is structurally identical to the reported analog: a bypass flag granted for one specific caller/context (vault A / tenure C) is checked with no verification of who is actually invoking it (vault B / tenure F), letting an unintended party exploit the exemption.

### Impact Explanation
This breaks the one-per-height equivocation guard that `get_signed_conflicts` / `reorg_permit_stands` exist to enforce (see the guard's own rationale in `docs/signer-flows.md`, "a signature is a bearer instrument... signing both would be the double-sign this guard exists for"). [5](#0-4) 

Once any tenure has ever been legitimately superseded (a routine, permitted event under the reorg-timing rules), the signer's protection against double-signing at that tenure's block height is silently disabled for *all* future conflicting proposals, not just the one sanctioned replacement. A signer can therefore be induced to sign two mutually conflicting blocks at the same Stacks height in different tenures — the exact "critical" class of bug this codebase is built to prevent (a rejection/veto recounted as a pass, enabling a signature on a non-canonical/conflicting block).

### Likelihood Explanation
Reorg permits are recorded during ordinary, permitted operation (`check_parent_tenure_choice` runs whenever a miner's tenure does not build off the prior sortition and passes the `first_proposal_burn_block_timing` rule) — this is not a rare or adversarial-only path. Once such a permit exists and its sortition remains canonical (the common case), any single miner able to get a conflicting proposal at the superseded tenure's height to reach the pre-commit threshold triggers the bypass; no majority of signers or key compromise is required, only a normally-reachable proposal flow through one miner/gossip.

### Recommendation
`reorg_permit_stands` (and/or the `SignedConflictInfo`/`get_signed_conflicts` query) should additionally verify that the block currently being evaluated for signing (`block_info.block.header.consensus_hash`) equals `conflict.superseded_by.consensus_hash` before excluding the conflict. The permit should only ever exempt the specific tenure it was granted to, matching the doc comment's intent ("our signature must not stand in the way of a replacement we sanctioned" — sanctioned for tenure C, not for an arbitrary tenure F).

### Proof of Concept
1. Tenure A produces and signs block A at Stacks height h (`LocallyAccepted`/`GloballyAccepted`).
2. A miner proposes tenure C, which legitimately satisfies the reorg-timing rule for replacing A (e.g., A produced its only block very close to the burn-block transition). `check_parent_tenure_choice` records `mark_tenure_superseded(A, ..., superseded_by=C)`.
3. Before, or regardless of whether, C ever actually gets a block signed, a miner in an unrelated tenure F proposes a block at the same height h that conflicts with A.
4. When F's proposal crosses the pre-commit threshold, `handle_block_pre_commit`'s conflict lookup finds A as a conflict, calls `reorg_permit_stands`, which returns true solely because C's sortition is still canonical — with no check that F == C.
5. The signer signs F's block, having already signed A's block at height h: two conflicting signatures at the same height are now live, violating the equivocation guard.

    pub fn get_signed_conflicts(
        &self,
        height: u64,
        excluded_signer_signature_hash: &Sha512Trunc256Sum,
    ) -> Result<Vec<SignedConflictInfo>, DBError> {
        let query = "SELECT b.consensus_hash, b.signer_signature_hash, b.stacks_height, b.state,
                MAX(COALESCE(b.signed_self, 0), COALESCE(b.signed_group, 0)) AS last_endorsed,
                st.superseded_by_consensus_hash, st.superseded_by_burn_block_hash
            FROM blocks b
            LEFT JOIN superseded_tenures st ON st.consensus_hash = b.consensus_hash
            WHERE (b.signed_self IS NOT NULL OR b.signed_group IS NOT NULL)
                AND b.stacks_height >= ?1
                AND b.signer_signature_hash != ?2
            ORDER BY b.stacks_height DESC";
        let args = params![
            u64_to_sql(height)?,
            excluded_signer_signature_hash.to_string(),
        ];
        query_rows(&self.db, query, args)
    }
