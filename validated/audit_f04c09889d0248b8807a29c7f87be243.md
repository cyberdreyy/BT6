Confirmed: both `multisig/src/lib.rs` (`DeleteKey`) and `multisig2/src/lib.rs` (`DeleteMember`) exhibit the same pattern — when removing a signer, only requests *created* (`signer_pk`/`member` field) by that signer are purged of confirmations; the `confirmations: LookupMap<RequestId, HashSet<...>>` structure is never scanned to strip out confirmations *cast* by the removed signer on requests created by someone else.

### Title
Stale confirmations from removed multisig members still count toward the execution threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` compares the size of the stored `confirmations` set against `num_confirmations` to decide whether to execute a request [1](#0-0) . When a member is removed via `DeleteMember` (or `DeleteKey` in the legacy `multisig` contract), the cleanup logic only deletes pending requests whose *creator* (`request_with_signer.member` / `signer_pk`) matches the removed member [2](#0-1) ; it never inspects other requests' `confirmations` sets to strip out a confirmation the removed member cast as an *approver* on a request created by someone else. The legacy `multisig` contract has the identical gap in the `DeleteKey` branch [3](#0-2) .

### Finding Description
The intended invariant is: a request executes only once `num_confirmations` **live** members have approved it — i.e. `confirmations counted == confirmations from current members`. In practice, once a member confirms a request they don't create, their public key/account string is inserted permanently into that request's `HashSet<String>` in `confirmations` [4](#0-3) . If that member is later removed from the multisig (e.g., because their key leaked or they're considered malicious/untrusted), `delete_member`/`DeleteKey` removes them from `self.members` and deletes access keys, but leaves their earlier confirmation entry intact on any request they were not the creator of. `confirm()` on that request will still count the stale confirmation when checking `confirmations.len() as u32 + 1 >= self.num_confirmations`, so the request can execute with fewer live-member approvals than the configured threshold actually requires.

### Impact Explanation
This is a Critical-class issue in the terms of the rules: "a multisig request executed below threshold." An adversary who is a member long enough to pre-confirm one or more pending or future-created requests, and is subsequently removed (revoked) by the remaining members, still has an effective, permanent vote baked into any request they touched before removal. Remaining legitimate members believe removing that member fully revokes their influence, but any request confirmed while they were still a member continues to count them, letting attacker-tainted or otherwise unintended transfers/`FunctionCall`s/`AddKey` actions execute with one fewer live confirmation than `num_confirmations` mandates.

### Likelihood Explanation
Likelihood is moderate-to-high in any operational scenario where membership changes over time (rotating signers, revoking a compromised key) while requests are in flight — a normal, expected multisig lifecycle event, not a contrived edge case. No special privilege is needed by the attacker beyond having been a legitimate member at some point and having confirmed at least one request before being removed.

### Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate over all outstanding requests' `confirmations` sets (not just those the removed member created) and remove the departing member's entry from each. If removing a confirmation drops a request below its previous progress, that's fine — the invariant should always be "count of confirmations from currently live members." Alternatively, validate at `confirm`-time (or at execution time) that every entry in `confirmations` still corresponds to a current member of `self.members`, discarding stale ones before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, M]`, `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm` to submit a `Transfer` request `R` (creator = `A`, 1 confirmation).
3. `M` calls `confirm(R)` → 2 confirmations, one short of 3 (`M`'s account string is now permanently in `confirmations[R]`) [4](#0-3) .
4. `A` and `B` submit and confirm a separate `DeleteMember { member: M }` request (requires only the existing 3-of-3, satisfied by `A`, `B`, and possibly a third live member) and it executes, removing `M` from `self.members` and deleting their key [2](#0-1) . Since `M` did not create `R`, `delete_member`'s cleanup loop does not touch `R` or its confirmation set.
5. `B` calls `confirm(R)` → `confirmations.len() + 1 == 3 >= num_confirmations`, so `R` executes — despite only `A` and `B` being current, live members; `M`'s stale confirmation from step 3 supplied the third vote after `M` was already revoked.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
