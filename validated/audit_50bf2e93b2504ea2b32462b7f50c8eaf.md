### Title
Node-side vote tally silently drops a signer's reversal from Accepted to Rejected, letting stale approval weight count toward the 70% signature threshold - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side `StackerDBListener` (the coordinator's message aggregator) tallies each signer's vote by slot id using two separate structures — `responded_signers: HashSet<u32>` and `gathered_signatures: BTreeMap<u32, MessageSignature>` — and gates weight-accounting on different, non-symmetric conditions for the `Accepted` and `Rejected` branches. [1](#0-0)  A signer that legitimately re-evaluates a previously **accepted** block and now sends a **Rejected** message for it (a state transition the signer-side state machine explicitly allows, `LocallyAccepted --> LocallyRejected: re-evaluated`) has its rejection silently discarded by the node's tally, because the `Rejected` branch only counts weight `if block.responded_signers.insert(slot_id)` returns true — and that slot was already inserted when the earlier `Accepted` message was processed.

### Finding Description
In the `Accepted` branch, after verifying the signature, the node adds the signer's weight to `total_weight_approved` when the slot is new to `gathered_signatures`, then unconditionally marks the slot in `responded_signers`: [2](#0-1) 

In the `Rejected` branch, weight is only added to `total_weight_rejected` when `block.responded_signers.insert(slot_id)` is a fresh insertion: [3](#0-2) 

Because `responded_signers` is shared across both message kinds and is only ever added to, never removed from or partitioned per message-type, the two branches are not symmetric:
- Reject-then-Accept: the slot is inserted by the reject path first; when the later accept arrives, the accept path's gate (`gathered_signatures.contains_key`) is independent of `responded_signers`, so the weight is *added again* to `total_weight_approved` on top of the weight already recorded in `total_weight_rejected`.
- Accept-then-Reject (the case that matters for safety): the slot is inserted by the accept path first; when the signer later, after a legitimate re-evaluation, sends a rejection for the very same block, `responded_signers.insert(slot_id)` returns `false` because the slot is already present, so the `if` block guarding `total_weight_rejected += weight` is skipped — the rejection vote is dropped entirely and never counted.

The signer-side flow explicitly allows this "accept, then re-evaluate to reject" transition — it is documented as a valid edge in the local `BlockState` machine (`LocallyAccepted --> LocallyRejected : re-evaluated`), triggered for instance when the block later fails `check_block_against_signer_db_state` (a conflicting/rival block signed at the same height, or a chainstate mismatch discovered on re-proposal). [4](#0-3)  Nothing in `stackerdb_listener.rs` accounts for the possibility that a slot's earlier acceptance is superseded; the coordinator's aggregate state (`total_weight_approved`, `total_weight_rejected`) therefore diverges from the true, most-recent verified vote of each signer — this is exactly the "aggregated-weight vs. verified-accepts" equality break called out as in-scope: the coordinator's threshold check operates on stale weight that no longer reflects what any single signer currently attests to.

### Impact Explanation
This is a Critical-class equality break: the coordinator (`SignerCoordinator::propose_block` / `get_block_status`, `stacks-node/src/nakamoto_node/signer_coordinator.rs:512-545`) decides "block accepted" purely from `block_status.total_weight_approved >= self.weight_threshold`. [5](#0-4)  If a signer flips from Accepted to Rejected after re-evaluating (e.g. discovering the block conflicts with another signed block, or the tenure changed underneath it), the coordinator still counts that signer's stale approval weight toward the 70% threshold and never records their genuine rejection. This lets the miner/coordinator collect and push a block that a supermajority of *currently valid* verdicts would not actually support, i.e. a rejection is effectively never "recounted" and the aggregated-approved weight no longer equals the set of signers who currently endorse the block — a signed/validated mismatch at the safety layer that decides whether a block is pushed to the node.

### Likelihood Explanation
This requires only a single signer (with any nonzero weight) and no majority collusion, and the accept→re-evaluate→reject path is a normal, protocol-sanctioned behavior (documented state transition, triggered by ordinary events like a conflicting signed block appearing or a re-proposal). It can also be triggered without malice: a signer that raced ahead and signed before observing a competing sibling block, then legitimately reversed itself, will have that reversal ignored by the coordinator. The bug is deterministic given the message ordering (accept observed before reject for the same slot/block), so likelihood is high whenever a signer changes its mind after its accept message has already reached the node.

### Recommendation
Track the *current* verdict per slot instead of a monotonic "has responded" set: either (a) key `responded_signers` per message kind (`accepted_signers` / `rejected_signers`) and, on a re-vote, move weight from the old bucket to the new one (decrementing the previous tally and incrementing the new one), or (b) store one `Verdict` enum per slot id, gate weight accounting on state transitions of that enum, and recompute `total_weight_approved`/`total_weight_rejected` as the sum over current-verdict signers instead of ever-accumulated counters. Additionally remove the slot's signature from `gathered_signatures` and decrement `total_weight_approved` when a later `Rejected` supersedes a prior `Accepted` for the same slot, so the invariant `total_weight_approved + total_weight_rejected <= total_weight` (one weight per signer, reflecting only their latest verdict) is always preserved.

### Proof of Concept
1. Signer S (weight W) validates block B, sends `BlockResponse::Accepted` → node processes it: `total_weight_approved += W`, `gathered_signatures[S] = sig`, `responded_signers.insert(S)` (now true/inserted). [2](#0-1) 
2. Before the block reaches 70% approval, a rival block at the same height is signed elsewhere; S re-evaluates B on re-proposal, its chainstate re-check now fails, and S broadcasts `BlockResponse::Rejected` for B via `mark_locally_rejected`/`handle_block_rejection`. [4](#0-3) 
3. The node receives this Rejected message; `block.responded_signers.insert(S)` returns `false` (already present from step 1), so the surrounding `if` body that adds `W` to `total_weight_rejected` never executes — S's rejection is silently dropped. [3](#0-2) 
4. `total_weight_approved` still includes S's original (now-withdrawn) weight; if enough other signers approve, `get_block_status` reports the block as accepted even though S no longer endorses it — the coordinator pushes a block one signer explicitly, and validly, refused. [5](#0-4)
