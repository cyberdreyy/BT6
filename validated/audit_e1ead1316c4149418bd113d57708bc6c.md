### Title
APR0 dust withdraw request permanently vetoes any APR increase and bricks `stopEpoch` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
An unprivileged KYC-passed lender can place a dust-sized `requestWithdraw` while `unscaledApr == 0`. This leaves `apr0TotalPrincipal > 0` in `IdleCreditVault`. If the manager later raises the APR (directly via `setApr`/`setAprsWithBuffer`, or a new fixed APR taking effect), every subsequent `stopEpoch`/`stopEpochWithDuration` reverts inside `prepareStopEpochWithApr0` because it forbids `unscaledApr != 0` while an APR0 principal bucket is open. The epoch can never be stopped while APR is non-zero, freezing all borrower repayments and all pending withdrawal claims. The attacker can re-arm the veto every time APR returns to 0.

### Finding Description
`IdleCDOEpochVariant.requestWithdraw` routes requests to `IdleCreditVault.requestWithdraw`, which diverts them to the APR0 bucket whenever `unscaledApr == 0` and the pool is not closed:

- `contracts/strategies/idle/IdleCreditVault.sol:285-286` — `if (unscaledApr == 0 && !isClosed) { _requestWithdrawApr0(_amount, _user); }`
- `contracts/strategies/idle/IdleCreditVault.sol:567-577` — `_requestWithdrawApr0` increments `apr0TotalPrincipal` by any non-zero `_amount`.

At epoch end, the CDO calls `prepareStopEpochWithApr0`, which hard-reverts when a non-zero APR0 bucket coexists with a non-zero APR:

- `contracts/strategies/idle/IdleCreditVault.sol:499-508` — `uint256 _principal = apr0TotalPrincipal; if (_principal == 0) return ...; if (unscaledApr != 0) { revert NotAllowed(); }`

Because the revert happens inside `_stopEpoch`, the whole `stopEpoch` transaction fails: `epochNumber` is not incremented, `isEpochRunning` stays true, borrower repayment is never collected, and no pending withdraw receipt (`withdrawsRequests`, `instantWithdrawsRequests`) can be claimed since claims are gated on `epochNumber > lastWithdrawRequest[_user]` (`IdleCreditVault.sol:326`).

There is no way for the attacker’s bucket to be cleared without a successful `stopEpoch` (`_settleApr0` only runs inside a claim after `epochNumber` advanced, and `apr0TotalPrincipal` is only reset inside `prepareStopEpochWithApr0` at line 540). The only escape is for the honest manager to set `unscaledApr` back to 0 — i.e., the attacker gains a permanent veto over any APR change, and can re-deposit a dust APR0 request in the next buffer period to repeat the freeze.

### Impact Explanation
- Temporary freezing of all user funds: while APR is non-zero, `stopEpoch` always reverts, so the epoch cannot end, borrower repayments/interest cannot be collected, and every queued withdrawal claim is blocked (claims revert with `NotAllowed` until `epochNumber` advances).
- Effective governance-econ grief: the attacker forces the vault to keep `unscaledApr = 0` forever, denying lenders their negotiated yield; each re-arm costs the attacker only a dust withdraw request (net of management fee).
- Cost: one `requestWithdraw` of minimum size by any whitelisted lender; no privileged role needed. `isWalletAllowed` (Keyring KYC) is the only gate, and a KYC-passed lender is an in-scope attacker.

### Likelihood Explanation
High in any vault whose APR is intended to change from 0 to positive (e.g., a credit line priced dynamically per epoch). The attacker needs only a tranche balance and KYC. There is no existing guard: the revert is intentional (it prevents mixing accounting models), and neither `lastWithdrawRequest` gating, the skim, nor epoch flags prevent a dust request. Note the freeze is *temporary* rather than permanent — an honest manager can recover by setting APR back to 0 and stopping the epoch — but the attacker can repeatedly re-arm it, making sustained APR increases impossible.

### Recommendation
- In `prepareStopEpochWithApr0`, do not revert when `unscaledApr != 0`. Instead settle the APR0 bucket at the APR in effect during its request epoch (store `apr0AprByEpoch` at request time) or simply settle it at zero interest.
- Alternatively, snapshot the APR at request time into `Apr0UserData`/epoch bucket so a later APR change cannot invalidate in-flight requests.
- Enforce a minimum request size (`_amount` above a dust threshold) in `requestWithdraw` to raise the cost of the veto.

### Proof of Concept
```solidity
// Foundry fork PoC (mainnet fork, vault with unscaledApr == 0, epoch running or buffer)
function testApr0DustBlocksStopEpochAfterAprRaise() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);                       // seed pool
    _startEpochAndCheckPrices(0);                    // epoch 0 at apr 0

    // attacker: KYC'd lender deposits dust and requests withdraw during buffer
    address attacker = makeAddr("attacker");
    _depositWithUser(attacker, 1e6);                 // minimal deposit
    uint256 tr = IERC20(AAtranche).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(tr / 2, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // manager raises APR for next epoch (honest action)
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprsWithBuffer(5e18, cdoEpoch.epochDuration(), cdoEpoch.bufferPeriod());

    // attacker dust bucket + non-zero apr -> every stopEpoch reverts
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);                        // epoch bricked, claims frozen
}
```
