### Title
Unchecked length precondition before slicing attacker-supplied L1 deposit calldata - ([File: crates/consensus/protocol/src/info/ecotone_base.rs])

### Summary
`L1BlockInfoEcotone::decode_calldata_body` in [1](#0-0)  indexes into a caller-supplied byte slice (`r[4..8]`, `r[144..164]`, etc.) up to offset 164 with no length check inside the function itself — the safety of every slice operation is documented as an unenforced caller precondition ("Callers must validate the length before calling").

### Finding Description
The function's own doc comment states: "This method assumes the slice is at least 164 bytes long... Callers must validate the length before calling this method," and the body performs eight raw slice-index operations (`r[4..8]`, `r[8..12]`, `r[12..20]`, `r[20..28]`, `r[28..36]`, `r[60..68]`, `r[84..100]`, `r[100..132]`, `r[144..164]`) with no `if r.len() < 164 { return Err(...) }` guard inside the function. This is structurally identical to the NTFS bug class: a parser trusts that a length precondition holds and dereferences/copies from an offset-derived field without re-verifying bounds at the point of use. In the NTFS case it was `next_entry_offset` on EA entries; here it is a hardcoded set of byte offsets on the L1 attributes-deposit-transaction calldata (`setL1BlockValuesEcotone`), which is data written into the chain by an L1 depositor/sequencer and consumed by every L2 node during block derivation and by the fault-proof program during L1 attributes decoding — squarely in the "derivation of attacker-written L1 deposit and system-config data" and "fault-proof program" reachable surfaces named in the rules.

I could not, in the time available, confirm from source whether every call site (`isthmus.rs`, `jovian.rs`, `ecotone.rs`) actually performs the required `r.len() >= 164` (or larger, for isthmus/jovian variants) check *before* invoking `decode_calldata_body`, or whether any call path (e.g., a malformed/short first transaction in a submitted or derived L2 block, or a fault-proof-program replay of a malicious block) could reach this function with a shorter slice. The function's own module-level `SAFETY` comments assert callers already validate it — but I was not able to verify this invariant end-to-end across `isthmus.rs`/`jovian.rs`/`ecotone.rs` before running out of iterations.

### Impact Explanation
If any call site fails to enforce the ≥164-byte length check (e.g., through an upstream refactor, a new caller, or a divergent codepath in the fault-proof program vs. the execution client), this becomes an out-of-bounds slice panic reachable from a single malformed/short first transaction in an L2 block. Given this data feeds L1-attributes/deposit processing that runs identically in the execution client, the derivation pipeline, and the fault-proof program, a panic divergence between implementations (or a straightforward node crash / halt) would be Critical: node halt or a wrong/unprovable output root in the fault-proof program.

### Likelihood Explanation
I was unable to confirm an actual missing check at any live call site in the time available — every RLP/ABI decoder I sampled elsewhere in this codebase (span-batch transactions, EIP-8130, CBOR, DER, deposit RLP) has been hardened with explicit length checks and regression tests for truncated input, which suggests the project has already been through a similar security-hardening pass. It's plausible `isthmus.rs`/`jovian.rs`/`ecotone.rs` already gate calls to `decode_calldata_body` behind a length check I didn't get to inspect. Given I could not verify the call sites, I can't assert this is a live, exploitable Critical/High-severity bug with certainty.

### Recommendation
Move the length assertion (`r.len() >= 164`, matching the largest variant needed by `isthmus`/`jovian` callers) inside `decode_calldata_body` itself (or introduce a checked constructor) rather than relying on caller discipline, and add a truncated-input regression test analogous to the ones already present for `decode_tx_sigs`/`decode_tx_tos`/`read_tx_data` in `crates/consensus/protocol/src/batch/transactions.rs` and `crates/consensus/protocol/src/batch/prefix.rs`.
