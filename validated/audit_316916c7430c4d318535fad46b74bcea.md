Confirmed: `assert_valid_request` only checks that the *current caller* is a live member before confirming [1](#0-0) . It never re-validates that the confirmations already stored in the `HashSet<String>` for a request still belong to current members, and `confirm()` simply compares the size of that stale set against `num_confirmations` [2](#0-1) . `delete_member()` only purges requests *authored* by the removed member (`r.member == member`); it does nothing to the confirmation sets of other requests that the removed member had already confirmed [3](#0-2) . This is the same bug class as the Term Finance report: a validity check ("sum/cardinality of components") diverges from what is actually current/authorized, letting a stale/insufficient input still satisfy the threshold.

### Title
Multisig executes requests counting confirmations from removed members - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` authorizes execution once `confirmations.len() + 1 >= num_confirmations`, but the confirmation set can contain members that have since been removed via `DeleteMember`, since `delete_member` never scrubs stale confirmations from requests it did not author. This lets a request execute with fewer *live* member approvals than `num_confirmations` requires.

### Finding Description
`confirm()` fetches the stored `HashSet<String>` of confirmers for a request and only compares its cardinality to `self.num_confirmations`; it never checks that each entry is still `self.members.contains(...)` [2](#0-1) . `delete_member()` removes outstanding requests *added by* the removed member (`r.member == member`) and clears `num_requests_pk`, but for requests added by *other* members that the removed member had already confirmed, the removed member's confirmation string simply stays in `self.confirmations` forever [3](#0-2) . `assert_valid_request` (invoked by both `confirm` and `delete_request`) only checks that the *caller* is currently a member — it does not re-validate historical confirmations [1](#0-0) .

The binding that should hold is: `live_member_confirmations(request) >= num_confirmations` before execution. Instead the code enforces `stored_confirmations(request).len() >= num_confirmations`, where `stored_confirmations` may include entries for accounts/keys no longer in `self.members`.

### Impact Explanation
This crosses the "confirmations counted versus live members" authorization boundary explicitly called out as in-scope. A multisig configured for, e.g., 3-of-4 can end up executing a `Transfer`, `AddKey`/`FunctionCall`, etc., with only 2 genuinely current members having approved, because a stale confirmation from an ousted member (e.g., someone removed for being compromised or off-boarded) still counts. This is a multisig request executed below the effective live-member threshold — a Critical-class impact per the stated criteria (funds or privileged actions authorized without the required live signer set).

### Likelihood Explanation
No privileged access or redeploy is required beyond normal multisig operation: any member can add a request and get it confirmed by other current members (who are all unprivileged with respect to each other beyond being multisig signers), and membership churn (adding/removing members over time) is a normal, expected lifecycle operation supported by `AddMember`/`DeleteMember`. The stale-confirmation condition is triggered purely by the ordinary sequence "member confirms request → that member is later removed → request is later executed," with no special conditions needed.

### Recommendation
When counting confirmations in `confirm()`, filter `confirmations` to only those entries where `self.members.contains(...)` still holds (or actively prune confirmations for a member in `delete_member()` across *all* requests, not just those they authored, by iterating `self.confirmations` and removing the departing member's key from every confirmation set).

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `B.add_request(request)` — creates request `R` with an empty confirmation set.
3. `A.confirm(R)` — `confirmations[R] = {A}` (1/3).
4. `C.confirm(R)` — `confirmations[R] = {A, C}` (2/3, not yet executed).
5. Multisig executes a governance request `DeleteMember { member: A }` (approved separately by B, C, D). `delete_member` removes `A` from `self.members` and deletes any requests *authored by* `A`, but request `R` (authored by `B`) is untouched, so `confirmations[R]` still contains `A`.
6. `D.confirm(R)` — code computes `confirmations[R].len() + 1 = 3 >= num_confirmations (3)` and executes `R`'s actions, even though only `C` and `D` are current members who approved (`A`'s stale confirmation counted toward the threshold). [2](#0-1) [3](#0-2)

        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",

        // delete outstanding requests by public_key

            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();

            // remove confirmations for this request
            self.confirmations.remove(&request_id);
