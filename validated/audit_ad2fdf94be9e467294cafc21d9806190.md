### Title
Gateway response routed to waiting workflow solely by `MessageId` without validating originating Sender/DON binding - ([File: core/capabilities/webapi/outgoing_connector_handler.go])

### Summary
`OutgoingConnectorHandler.HandleGatewayMessage` dispatches an inbound gateway message to a waiting workflow purely by looking up `c.responses.get(body.MessageId)`, the same class of bug as the LiFi finding where one identifier (`_lifiData.receivingAssetId`) was relied upon for the final action while a different, unchecked identifier (`SwapData.receivingAssetId`) actually determined behavior elsewhere in the flow. Here, the `MessageId` used to route a response back to the calling workflow's `HandleSingleNodeRequest` caller is never bound to (or re-checked against) the `Sender`/DON identity that the request was actually sent to, so any gateway node relaying a message with a matching `MessageId` is accepted as the legitimate response.

### Finding Description
`HandleSingleNodeRequest` allocates a response channel keyed only by `messageID` [1](#0-0) , and that `messageID` is derived deterministically from `req.Metadata.WorkflowExecutionID` and the capability method name, with no per-call randomness or nonce: `messageID := []string{req.Metadata.WorkflowExecutionID, ghcapabilities.MethodWebAPITarget}` [2](#0-1) .

On the inbound side, `HandleGatewayMessage` retrieves the waiting channel using only `body.MessageId` [3](#0-2) , then applies only a per-sender/global rate limit check based on `body.Sender` [4](#0-3) , and finally forwards the message body to the waiting workflow caller without ever confirming that `body.Sender` matches the gateway/node the original request was routed to (`selectedGateway` from `awaitConnection`) [5](#0-4) . Unlike the analogous `handler.go` capabilities handler which does verify `msg.Body.Sender != nodeAddr` before accepting a node response [6](#0-5) , and the `dummyHandler.HandleNodeMessage` which performs the same check [7](#0-6) , `OutgoingConnectorHandler.HandleGatewayMessage` performs no equivalent sender/gateway binding check — it accepts any message whose `MessageId` field matches a pending request, exactly mirroring the LiFi root cause of trusting one identifier field (here, `MessageId`) for the critical routing decision while leaving the complementary identity field (`Sender`/originating gateway) unverified.

### Impact Explanation
If a compromised or misbehaving gateway (or a race/duplicate-delivery condition across multiple gateways the node is connected to) sends a message carrying a `MessageId` that collides with, or is replayed against, another pending request, the `OutgoingConnectorHandler` will deliver that response to the waiting workflow execution as if it were the authentic HTTP-target/compute/workflow-syncer response, since only `MessageId` is checked. Because `MessageId` is deterministically derived from `WorkflowExecutionID` alone (no random request nonce, no re-verified receiver), a response never actually produced by the intended remote endpoint could be accepted, resulting in cross-execution response confusion (a workflow accepting attacker/other-party-controlled data as its own outgoing HTTP call result) and, since target/fetcher outputs feed directly into workflow logic and subsequent on-chain reports, this can degrade to unauthorized data injection into workflow-driven job execution.

### Likelihood Explanation
Reaching this code requires only the standard (unprivileged, from the node's perspective) flow of a workflow using the `web-api-target` capability or `FetcherService`, both of which are triggered by ordinary workflow specs; the gateway is on the trust boundary already but the missing sender check removes a defense-in-depth layer that other, adjacent handlers in the same codebase (`handler.go`, `handler.dummy.go`) already implement, indicating this is an inconsistency/omission bug rather than a fundamental design choice.

### Recommendation
Bind the response channel to the specific gateway/DON the request was sent to (e.g., store `selectedGateway` alongside the channel in `responses.new`), and in `HandleGatewayMessage` verify `gatewayID`/`body.Sender` against that recorded value before dispatching to the channel — mirroring the existing `msg.Body.Sender != nodeAddr` check used in `handler.go` and `handler.dummy.go`.

### Proof of Concept
1. Workflow execution `E` calls the `web-api-target` capability, producing `messageID = "E/webapitarget"` and awaiting a response on the channel registered for that ID [8](#0-7) .
2. `HandleSingleNodeRequest` sends the signed request to `selectedGateway` and blocks on `ch := c.responses.new(messageID)` [9](#0-8) .
3. A gateway (or any component able to submit a message through the connector's read loop, which dispatches purely by JSON-RPC method to registered handlers) sends a `MethodWebAPITarget` message whose body carries `MessageId = "E/webapitarget"` but an arbitrary/forged `Payload` and a `Sender` different from the gateway/endpoint actually targeted.
4. `HandleGatewayMessage` finds the channel via `c.responses.get(body.MessageId)` and forwards the message straight through, with no check that `body.Sender` corresponds to the expected responder [10](#0-9) .
5. `target.Capability.Execute` unmarshals and returns this payload as the legitimate HTTP-target response to the workflow [11](#0-10) .

func (c *OutgoingConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		c.lggr.Errorw("failed to validate request", "err", err, "gatewayID", gatewayID)
		return nil
	}
	body := &msg.Body
	l := logger.With(c.lggr, "gatewayID", gatewayID, "method", body.Method, "messageID", msg.Body.MessageId)

	ch, ok := c.responses.get(body.MessageId)
	if !ok {
		l.Warnw("no response channel found; this may indicate that the node timed out the request")
		return nil
	}

	senderAllow, globalAllow := c.incomingRateLimiter.AllowVerbose(body.Sender)
	errJSON := jsonrpc.WireError{
		Code:    500,
		Message: "",
	}
	if !senderAllow {
		errJSON.Message = errorIncomingRatelimitSender
	}
	if !globalAllow {
		if errJSON.Message == "" {
			errJSON.Message = errorIncomingRatelimitGlobal
		} else {
			errJSON.Message += "\n" + errorIncomingRatelimitGlobal
		}
	}

	if errJSON.Message != "" {
		l.Errorw("request rate-limited")
		errPayload, err := json.Marshal(errJSON)
		if err != nil {
			l.Errorw("failed to marshal err payload", "err", err)
		}
		errMsg := api.Message{
			Body: api.MessageBody{
				MessageId: body.MessageId,
				Method:    api.MethodInternalError,
				Payload:   errPayload,
			},
		}
		ch <- &errMsg
		return nil
	}

	l.Debugw("handling gateway request")
	switch body.Method {
	case capabilities.MethodWebAPITarget, capabilities.MethodComputeAction, capabilities.MethodWorkflowSyncer:
		body := &msg.Body
		var payload capabilities.Response
		err := json.Unmarshal(body.Payload, &payload)
		if err != nil {
			l.Errorw("failed to unmarshal payload", "err", err)
			return nil
		}
		select {
		case ch <- msg:
			return nil
		case <-ctx.Done():
			return nil
		}

func getMessageID(req capabilities.CapabilityRequest) (string, error) {
	if err := validation.ValidateWorkflowOrExecutionID(req.Metadata.WorkflowID); err != nil {
		return "", fmt.Errorf("workflow ID is invalid: %w", err)
	}
	if err := validation.ValidateWorkflowOrExecutionID(req.Metadata.WorkflowExecutionID); err != nil {
		return "", fmt.Errorf("workflow execution ID is invalid: %w", err)
	}
	messageID := []string{
		req.Metadata.WorkflowExecutionID,
		ghcapabilities.MethodWebAPITarget,
	}
	return strings.Join(messageID, "/"), nil
}
