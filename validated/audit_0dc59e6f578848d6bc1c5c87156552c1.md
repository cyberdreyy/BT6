### Title
Unauthenticated `InitializeBuffer` allows front-running of BPF Upgradeable Loader buffer accounts - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The `UpgradeableLoaderInstruction::InitializeBuffer` handler in the BPF Upgradeable Loader sets the `authority_address` of a `Buffer` account without requiring *any* signature check, exactly mirroring the reported flaw where `BeamInitializable.initialize()` is `public` and callable by anyone rather than being restricted to the account's rightful owner.

### Finding Description
`InitializeBuffer` only checks that the target account is currently `UpgradeableLoaderState::Uninitialized`; it then takes whatever pubkey is passed as account index 1 and writes it as the new `authority_address`, with no requirement that this account be a signer or that the caller be privileged in any way: [1](#0-0) 

Compare this with the `Write` handler immediately below it, which *does* verify the authority both matches the stored value and has signed the instruction: [2](#0-1) 

Because `InitializeBuffer` never checks that account 0 (the buffer being initialized) or account 1 (the proposed authority) signed the transaction, any account address that is `Uninitialized` and owned by `bpf_loader_upgradeable` can be "claimed" by whoever submits an `InitializeBuffer` instruction against it first — precisely the same "public, callable-by-anyone, one-shot initialize" defect flagged in the external report for `BeamInitializable.initialize`.

The intended safe usage pattern bundles `CreateAccount` + `InitializeBuffer` into a single atomic transaction, as done by the CLI's `loader_v3_instruction::create_buffer` helper consumed in `do_process_write_buffer`: [3](#0-2) 

This atomic-transaction convention is a client-side choice, not something enforced on-chain by `process_loader_upgradeable_instruction`. Unlike the fix applied to the original Solidity report (`onlyConstruction` modifier checking the `implementation` slot set at construction time, `ForwardTarget.sol`), the BPF loader's `InitializeBuffer` path has no analogous on-chain invariant tying initialization to the account's creation transaction. Any caller who creates a buffer account in isolation (e.g. via `system_instruction::create_account` in a separate transaction, or any tooling/workflow — such as offline/hardware-wallet multisig flows — that does not atomically combine account creation with `InitializeBuffer`) exposes a window in which an attacker can submit `InitializeBuffer` first and set themselves as `authority_address`.

### Impact Explanation
If an attacker wins this race, they become the sole `authority_address` on the victim's rent-funded buffer account. Downstream instructions (`Write`, `SetAuthority`, `Close`, `DeployWithMaxDataLen`/`Upgrade` buffer checks) all trust `authority_address` as the sole gate — e.g. `Write` at lines 177-190 and the buffer-authority check inside `DeployWithMaxDataLen` at lines 414-422. Once the attacker holds the authority, they can call `Close` to redirect the buffer's rent-exempt lamports (paid by the victim) to an account of their choosing, or overwrite the buffer contents before the victim's expected `DeployWithMaxDataLen`, hijacking the deployed program's content — a direct analog of the "hijack the Bootstrap process" impact described in the report (loss of funds and loss of control over the to-be-deployed program).

### Likelihood Explanation
Likelihood is **low-to-moderate** in practice: the standard CLI and most tooling submit `CreateAccount` and `InitializeBuffer` atomically in one transaction, which the Solana execution model guarantees cannot be interleaved with another party's instructions. The exposure only materializes for callers who deviate from this pattern (e.g., custom SDKs, multi-step/offline-signing flows, or pre-funded/pre-created buffer accounts left uninitialized across transactions) — a legitimate but less common usage path. There is no on-chain guarantee preventing this, so the risk is real for any workflow that separates creation from initialization, but it requires a specific (non-default) usage pattern to be reachable, and I could not find in-repo evidence of a first-party, production flow that splits these steps across separate transactions (the CLI always bundles them).

### Recommendation
Add an on-chain invariant to `InitializeBuffer` that ties initialization to account creation, analogous to Eco's fix (`onlyConstruction` gate checked against a value set only at construction time). Concretely: require the buffer account to have been created within the *same* transaction (e.g., verify it was just assigned `bpf_loader_upgradeable` ownership and has zero prior activity), or require the proposed authority (account 1) to be a signer of the `InitializeBuffer` instruction, closing the unauthenticated race window entirely.

### Proof of Concept
1. Victim submits `system_instruction::create_account(payer, buffer_pubkey, rent_exempt_lamports, size, bpf_loader_upgradeable::id())` in Transaction A, intending to send `InitializeBuffer` in a later Transaction B (e.g., due to an offline-signing multisig workflow).
2. Attacker observes `buffer_pubkey` becoming owned by `bpf_loader_upgradeable` and in `Uninitialized` state (public, on-chain).
3. Attacker submits `InitializeBuffer` instruction against `buffer_pubkey`, passing their own key as account index 1 (`authority`), with no signature required for either account: [1](#0-0) 
4. Buffer account's `authority_address` is now the attacker's key; the victim's subsequent `InitializeBuffer` in Transaction B fails with `AccountAlreadyInitialized` (as demonstrated in the existing test `test_bpf_loader_upgradeable_initialize_buffer`): [4](#0-3) 
5. Attacker, now holding `authority_address`, calls `Close` on the buffer to redirect the victim-funded rent-exempt lamports to an account they control.
