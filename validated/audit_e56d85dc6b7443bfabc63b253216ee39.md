### Title
External Initiator credential can invoke arbitrary job IDs via `POST /v2/jobs/:ID/runs` because `PipelineRunsController.Create` cannot distinguish an EI-authenticated context from a real user - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
`auth.RequiresRunRole` does not nil-panic or silently default-allow for EI principals: `AuthenticateExternalInitiator` deliberately injects a synthetic `sessions.User{Role: UserRoleRun}` into the gin context under the same key used for real users, so `GetAuthenticatedUser` succeeds and the role check passes as intended for EI endpoints. However, this same synthetic user is what breaks the downstream authorization logic in `PipelineRunsController.Create`, which relies on `auth.GetAuthenticatedUser` to distinguish "real user" callers (who may run any int-ID job) from EI callers (who should only be able to trigger the specific job/webhook bound to them).

### Finding Description
`AuthenticateExternalInitiator` in [1](#0-0)  sets both `SessionExternalInitiatorKey` and `SessionUserKey` with a synthetic `sessions.User{Role: UserRoleRun}` after successfully validating the EI's access key/secret. Because of this, `auth.RequiresRunRole` in [2](#0-1)  retrieves this synthetic user via `GetAuthenticatedUser`, sees `Role == UserRoleRun` (not `UserRoleView`), and lets the request through to the handler — no panic, no default-allow bug in `RequiresRunRole` itself.

The actual authorization defect is in `PipelineRunsController.Create`: [3](#0-2) . The comment states "only users are allowed to run jobs using int IDs - EIs not allowed," and the code gates this via `_, isUser := auth.GetAuthenticatedUser(c)`. But because `AuthenticateExternalInitiator` sets the exact same `SessionUserKey` that real user auth methods (`AuthenticateByToken`/`AuthenticateBySession`) use, `isUser` evaluates to `true` for EI-authenticated requests as well. The code never calls `auth.GetAuthenticatedExternalInitiator(c)` to check whether the caller is actually an EI, nor does it verify that the presented job ID is the one bound to that specific EI (previously this binding was enforced via webhook UUID job IDs, but that path is now rejected entirely with `job.ErrJobTypeRemoved` at lines 103-107). Consequently, an EI credential — originally scoped to trigger a specific webhook/job — that satisfies the `RequiresRunRole` gate can present *any* integer job ID and have `prc.App.RunJobV2(ctx, jobID, nil)` invoked for that arbitrary job, with no per-EI job binding check.

### Impact Explanation
This is an authorization/scope-bypass bug: an External Initiator credential, meant to be scoped to triggering one job, can be used to trigger any job on the node by numeric ID via `POST /v2/jobs/:ID/runs`, as long as it presents a valid integer ID instead of the legacy webhook UUID. This matches the Chainlink bounty impact class of "unauthorized job run" / authorization bypass using a restricted credential.

### Likelihood Explanation
Preconditions: attacker must hold a valid External Initiator access key/secret pair (a lower-privilege credential intended only to trigger its own bound job/webhook). No admin/operator access is required. The bypass is fully reachable via a normal HTTP request to `POST /v2/jobs/<int_id>/runs` with the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers, provided the route is registered with an EI-capable authentication method group (as implied by the question's `userOrEI` reference). This is deterministic and repeatable given a valid EI credential.

### Recommendation
In `PipelineRunsController.Create`, explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and reject (or separately validate job binding for) any request where an EI is present, instead of relying solely on `GetAuthenticatedUser`/`isUser`, since `AuthenticateExternalInitiator` populates the same `SessionUserKey`. Alternatively, avoid setting `SessionUserKey` for EI-authenticated requests and introduce a distinct context flag/role solely for EI-run-role checks, so downstream handlers can unambiguously differentiate EI vs. real-user sessions.

### Proof of Concept
1. Create two jobs, `jobA` (nominally associated with EI `eiX`) and `jobB` (unrelated job) via admin/edit user.
2. Create an External Initiator `eiX` via `POST /v2/external_initiators`, obtaining `AccessKey`/`Secret`.
3. Send `POST /v2/jobs/<jobB.ID>/runs` (an integer ID for a job NOT bound to `eiX`) with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to `eiX`'s credentials.
4. Assert: current behavior returns `200 OK` and `App.RunJobV2` is invoked for `jobB.ID` (add a mock/spy on `RunJobV2` to confirm invocation with `jobB.ID`).
5. Expected secure behavior: assert `StatusUnauthorized`/`StatusForbidden` and that `RunJobV2` is never invoked for `jobB.ID` when the caller is EI-authenticated and not bound to that job.

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
