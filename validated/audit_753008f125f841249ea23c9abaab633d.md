The claimed ambiguity does not exist in the code. `NakamotoBlockProposal::validate` returns `Result<BlockValidateOk, BlockValidateRejectReason>`, and every resource-cap trip (execution-time, analysis-time, or block-level timeout) explicitly constructs and returns an `Err(BlockValidateRejectReason{...})` — there is no code path where a partial-execution abort falls through to the `Ok` branch.

Specifically:
- The per-tx execution loop checks `Instant::now() >= block_deadline` and returns `Err(BlockValidateRejectReason{ reason_code: ValidateRejectCode::InvalidBlock, failed_txid: None, .. })` for block-level timeouts [1](#0-0) .
- Per-tx execution/analysis-time or memory overruns are surfaced through `TransactionResult::Problematic`, which is mapped to `Err(BlockValidateRejectReason{ reason_code: ValidateRejectCode::ProblematicTransaction, failed_txid: Some(tx.txid()), .. })` [2](#0-1) .
- `spawn_validation_thread` only touches the `Err` arm via `.map_err`; the `Ok(BlockValidateOk)` value, if produced, passes through completely unmodified — there is no code path that converts an `Err` into an `Ok` or vice versa [3](#0-2) .
- `BlockValidateResponse::from` and `signer_signature_hash()` preserve the `Ok`/`Reject` distinction as a tagged Rust enum, and the signer's dispatch (`handle_block_validate_response`) matches exhaustively on this enum with no default/fallback branch that could misclassify a `Reject` as `Ok` [4](#0-3) [5](#0-4) .

This is directly confirmed by existing regression tests that assert the terminal response for both an execution-time trip and an analysis-time trip is always `Err(BlockValidateReject{ reason_code: ProblematicTransaction, failed_txid: Some(...) , ..})`, never `Ok` [6](#0-5) [7](#0-6) , and by an integration-level signer test that resource-cap-triggered analysis timeouts propagate all the way to a `BlockResponse::Rejected` with `RejectReason::ValidationFailed(ValidateRejectCode::ProblematicTransaction)` on the signer's StackerDB channel [8](#0-7) .

Since Rust's type system enforces that `Result<T, E>`'s `Ok`/`Err` discriminant is preserved through `.map_err` (which only transforms the error payload, not the discriminant), and the enum-tagged `BlockValidateResponse` preserves that discriminant through serialization/deserialization, there is no mechanism by which a resource-cap abort (an `Err` value) could be observed by the signer as `BlockValidateResponse::Ok`. The fail-closed equality holds.
