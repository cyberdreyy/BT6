## Analog Found

### Title
Unprotected `InitializeNonceAccount` Allows Front‑Running of Nonce Authority Assignment - (File: `programs/system/src/system_instruction.rs`)

### Summary
The System Program's `InitializeNonceAccount` instruction sets the durable-nonce `authority` field purely from unauthenticated instruction data, with no requirement that the nonce account itself, its creator, or the new authority sign the transaction. This mirrors the reported `L2EthToken.initialize()` bug class: whoever calls the "set owner/authority" function first — not the intended party — wins, because the call is unprotected.

### Finding Description
`initialize_nonce_account` transitions a nonce account from `State::Uninitialized` to `State::Initialized(data)`, embedding the caller-supplied `nonce_authority` pubkey directly into state: [1](#0-0) 

The dispatcher in `system_processor.rs` confirms no signer/authority check is performed for this instruction beyond `check_number_of_instruction_accounts(1)` — it only validates the recent-blockhash sysvar and rent, then calls straight into `initialize_nonce_account`: [2](#0-1) 

Compare this to every other state-mutating instruction in the same file (`allocate`, `assign`, `withdraw_nonce_account`, `advance_nonce_account`), which explicitly check `signers.contains(...)` before mutating state: [3](#0-2) [4](#0-3) 

`InitializeNonceAccount` is the outlier: it neither requires the nonce account to be a signer nor the new `authority` to sign. Once a nonce account exists as system-owned, rent-exempt, and `Uninitialized` — a state reachable via `CreateAccountWithSeed`, whose target account is explicitly **not** required to sign, as demonstrated in the test suite: [5](#0-4) 

— any account can be initialized by any third party who observes it on-chain (the address is deterministically derivable from `base + seed`, per `Address::create`): [6](#0-5) 

The subsequent `withdraw_nonce_account` only checks that a signer matches whatever `authority` value is stored in state — it has no notion of the "intended" owner: [7](#0-6) 

### Impact Explanation
If a nonce account is funded/created in one transaction (e.g., via `CreateAccountWithSeed`, whose target address does not need to sign) and `InitializeNonceAccount` is submitted as a separate, later transaction — a common two-step pattern for wallets and off-chain tooling — an attacker who observes the funded, uninitialized account can race to submit their own `InitializeNonceAccount(attacker_pubkey)` first. Because there is no signature check tying the authority to any legitimate party, the attacker wins outright and permanently becomes the nonce authority (the legitimate initializer's later call fails with `AccountAlreadyInitialized`). The attacker can then call `WithdrawNonceAccount`, signing as the authority they set, and drain the account's lamports. This is a direct unauthorized state mutation leading to fund theft, exactly analogous to seizing the unprotected `l2Bridge` setter in the reported bug.

### Likelihood Explanation
Exploitability depends on client behavior: if `CreateAccount`/`CreateAccountWithSeed` and `InitializeNonceAccount` are always bundled atomically in a single transaction (as done by the reference CLI helper `create_nonce_account`), no window exists. However, nothing in the on-chain program enforces this atomicity, and the core protocol code itself provides no defense — any wallet, exchange integration, or program that funds/creates nonce accounts with seeds ahead of initialization (a legitimate and documented pattern for offline/multi-step signing flows) is exposed to front-running by any network observer, requiring no special privilege beyond normal transaction submission.

### Recommendation
Require `InitializeNonceAccount` to check that either the nonce account itself is a signer, or that the caller intending to set the authority is explicitly authenticated (e.g., require the account creator/base key to co-sign), closing the window between account creation and initialization. At minimum, document and enforce (via a required signer check) that the entity funding the nonce account must also be the one to initialize it.

### Proof of Concept
1. Victim submits `CreateAccountWithSeed(base=victim_base, seed="my-nonce", owner=system_program)` funding a nonce-account-sized PDA-like address, in one transaction, planning to send `InitializeNonceAccount(victim_authority)` in a follow-up transaction.
2. Attacker computes the same deterministic address via `Pubkey::create_with_seed(&victim_base, "my-nonce", &system_program::id())` (public information) and observes the funded, `Uninitialized`, system-owned account on-chain.
3. Attacker submits `InitializeNonceAccount(attacker_pubkey)` referencing that address before the victim's initialize transaction lands — no signature from the account or `attacker_pubkey` is required by `initialize_nonce_account` in `programs/system/src/system_instruction.rs`.
4. Attacker's transaction confirms first; `system_instruction::initialize_nonce_account` sets `State::Initialized(Data { authority: attacker_pubkey, ... })`.
5. Victim's subsequent `InitializeNonceAccount` fails with `InstructionError::AccountAlreadyInitialized`.
6. Attacker calls `WithdrawNonceAccount`, signing as `attacker_pubkey`, which passes the `check_signer(&data.authority)` check in `withdraw_nonce_account`, draining the account's lamports to an address of the attacker's choosing.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}
