### Title
Stale rejection weight is never cleared when a signer flips from Reject to Accept, letting the miner-side `StackerDBListener` double-book a single signer's weight across `total_weight_rejected` and `total_weight_approved` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side `StackerDBListener` tallies `BlockResponse` messages into two independent counters, `total_weight_approved` and `total_weight_rejected`, guarded by two different sets (`gathered_signatures` and `responded_signers`). A signer that first rejects a block and later accepts the same block (a state transition the signer protocol explicitly supports, per `docs/signer-flows.md` §3/§5 "may sign later if the rival dies out" / re-evaluation of a prior reject reason) gets its weight added to `total_weight_rejected` on the reject and then *also* added to `total_weight_approved` on the later accept, with no code path ever subtracting the stale reject weight. This breaks the invariant that a signer's weight should count toward at most one side of the "aggregated-weight vs verified-accepts" tally used by the mining coordinator to decide whether a block is globally accepted or globally rejected.

### Finding Description
In `handle_block_response`-equivalent handling inside `StackerDBListener`'s message loop:

- On `BlockResponse::Accepted`, weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)` [1](#0-0) , and `slot_id` is unconditionally inserted into `responded_signers` [2](#0-1) .
- On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot responds at all) [3](#0-2) .

Because the *Accept* path's dedup check is scoped to `gathered_signatures` (only ever touched by Accept messages) rather than to `responded_signers` (which is touched by both Accept and Reject), the following sequence double-books a single signer's weight:

1. Signer S sends `Rejected` for block B → `responded_signers.insert(S)` succeeds → `total_weight_rejected += weight(S)`.
2. Signer S later re-evaluates and sends `Accepted` for the *same* block B (a supported, non-malicious state transition per the signer's own capitulation/re-evaluation logic, e.g. `should_reevaluate_reject_reason`) → `gathered_signatures.contains_key(S)` is `false` (first Accept from S) → `total_weight_approved += weight(S)` as well.

`total_weight_rejected` is never decremented when S's vote flips, so S's weight is now counted in *both* tallies simultaneously. This violates the assumed invariant `total_weight_approved + total_weight_rejected <= total_weight` that the coordinator relies on when deciding between "block accepted" and "block globally rejected" [4](#0-3) .

### Impact Explanation
The mining coordinator (`SigningCoordinator::watch_for_block_signatures`/wait loop) checks, in order, whether `total_weight_rejected + weight_threshold > total_weight` (blocking minority reached → `Err(SignersRejected)`) and otherwise whether `total_weight_approved >= weight_threshold` (block accepted) [4](#0-3) . Because `total_weight_rejected` can retain stale weight from signers who have since capitulated and accepted, the coordinator can incorrectly conclude that a blocking minority (>30% weight) exists — and abandon/kill a block proposal that in fact has legitimate ≥70% *current* signer support — purely due to accounting staleness, with no need for a majority of malicious signers. This is a liveness wedge on the miner side of the signer/coordinator pipeline: a single signer's ordinary reject→accept transition can cause a canonically valid, sufficiently-signed block to be treated as globally rejected (`NakamotoNodeError::SignersRejected`), stalling block production for that block and forcing miner retries/timeouts. The approve-side counter itself cannot be inflated beyond one weight-count per signer (guarded correctly by `gathered_signatures`), so this analog does not let an invalid/under-signed block get *pushed*, but it does break the accept/reject equality accounting that the coordinator depends on, matching the "aggregated-weight vs verified-accepts" equality class called out in scope.

### Likelihood Explanation
This requires only a single ordinary signer to send a `Rejected` message followed later by an `Accepted` message for the same block hash — a sequence the signer's own state machine explicitly allows for (re-evaluation of rejection reasons, capitulation to a rival block dying out, etc., as documented in `docs/signer-flows.md` sections 3 and 5). No malicious majority, no forged signatures, and no StackerDB-transport tricks are needed — just normal operation timing where a signer's local view changes between the two messages. Because this is a purely local, single-actor sequence (not requiring coordination with other signers), the likelihood of naturally triggering it during ordinary chain forks/tenure changes is non-trivial.

### Recommendation
Track each signer's current vote in a single `HashMap<u32, Vote>` (Accepted/Rejected) instead of separate `gathered_signatures`/`responded_signers` sets, and when a slot's vote changes, subtract the old vote's weight from the corresponding totals before adding the new vote's weight to the new totals. This restores the invariant `total_weight_approved + total_weight_rejected <= total_weight` and prevents stale rejection weight from persisting after a signer has capitulated and accepted the block.

### Proof of Concept
1. Coordinator proposes block B to N signers with total weight W and 70% threshold.
2. Signer S (weight w_S) initially rejects B (e.g., transient chainstate check failure) → `BlockResponse::Rejected` is broadcast and processed by `StackerDBListener`: `total_weight_rejected += w_S`, `responded_signers.insert(S)`.
3. Enough other signers reject as well such that `total_weight_rejected` is just under the blocking threshold (`total_weight - weight_threshold`).
4. S's local chainstate re-check (`check_block_against_signer_db_state`) later passes (the rival conflict staled out, or the reject reason is re-evaluable) and S signs and broadcasts `BlockResponse::Accepted` for the identical `signer_signature_hash`.
5. `StackerDBListener` processes the Accept: `gathered_signatures.contains_key(S)` is false, so `total_weight_approved += w_S` — but `total_weight_rejected` still includes `w_S` from step 2, unchanged.
6. On the next status check, `total_weight_rejected.saturating_add(weight_threshold) > total_weight` can now be true (using the stale rejection weight that double-counts S), causing the coordinator to return `Err(SignersRejected)` for block B, even though the current, up-to-date signer opinions (after S's flip) may in fact represent ≥70% approval weight.
