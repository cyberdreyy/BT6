### Title
Any revert inside the `stopEpoch` funding block is converted into an irreversible borrower default with no retry path — a dust/rounding revert in `collectWithdrawFunds` permanently freezes the pool - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
The external bug class is "a one-way cross-chain call whose failure permanently strands funds because there is no `delegate` to retry and no try/catch handling on the receiver." The same pattern exists in `IdleCDOEpochVariant._stopEpoch`: the entire epoch settlement is wrapped in a single `try this.getFundsFromBorrower(...) { ... } catch { _handleBorrowerDefault(...) }`. The `catch` block cannot distinguish "borrower did not pay" from "a later internal call reverted," and `_handleBorrowerDefault` irreversibly sets `defaulted = true`, pauses the contract, and stops the epoch — with no retry path. A revert in `IdleCreditVault.collectWithdrawFunds` (or any other call inside the try) therefore converts a recoverable failure into a permanent default while the borrower has actually repaid nothing and the funds remain stranded.

### Finding Description
In `_stopEpoch`, the success branch performs several calls *after* the borrower transfer inside the same `try` scope (`contracts/IdleCDOEpochVariant.sol:408-505`):

```solidity
try this.getFundsFromBorrower(_amountToPullFromBorrower + _pendingWithdraws) {
    _strategy.collectWithdrawFunds(_pendingWithdraws);   // can revert NotAllowed
    ...
    IProgrammableBorrower(_borrower()).settleBorrowerInterest(); // external call, can revert
    ...
} catch {
    _handleBorrowerDefault(_amountToPullFromBorrower + _pendingWithdraws);
}
```

`IdleCreditVault.collectWithdrawFunds` reverts `NotAllowed()` when the funded amount is below `pendingWithdraws` and the computed `lossRecoveryPrice` rounds to zero (`contracts/strategies/idle/IdleCreditVault.sol:411-421`):

```solidity
uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
if (lossRecoveryPrice == 0) revert NotAllowed();
```

Because this revert is swallowed by the outer `catch`, `defaulted = true` is set (`IdleCDOEpochVariant.sol:577-599`), `isEpochRunning = false`, deposits/requests are paused, and `onDefault()` is fired on a programmable borrower — even though the borrower-side `transferFrom` was rolled back and the borrower never actually failed to pay. There is no function that unsets `defaulted` or retries the stop; the only way forward is the full default-finalization/recovery flow (`finalizeDefault`, `finalizeDefaultRecovery`), which imposes a recovery haircut on all LPs.

The attacker lever is inflating `pendingBasis`: a KYC'd lender (or tranche holder) calls `requestWithdraw` during the buffer with a very large tranche balance, growing `pendingWithdraws`. When the owner later legitimately calls `stopEpochWithDuration` with a `_lossAmount` that makes `previewLossAdjustedWithdrawFunds` return a small `pendingToFund`, `collectWithdrawFunds` reverts on the zero recovery price — and the catch converts it into a protocol-wide permanent default. Even without deliberate inflation, the same irreversible path triggers on *any* transient failure inside the try (e.g., `settleBorrowerInterest` reverting on a programmable borrower, or an underlying token pause during a fee transfer), which is precisely the "failed call permanently strands funds, no delegate to retry" bug class.

### Impact Explanation
- `defaulted` is irreversible; a correctly-paying borrower is flagged as defaulted and `BorrowerDefault` is emitted.
- All pending withdraw receipts must go through `finalizeDefault`/`finalizeDefaultRecovery` and take a recovery haircut instead of receiving `pendingToFund` at the computed recovery price — LP value loss equal to the difference between actual repayment capacity and the defaulted-epoch recovery price, plus permanent freeze of normal operations until owner finalization.
- Funds that were transferred in the try are rolled back to the borrower, so the vault's accounting claims a default while holding nothing — the exact "msg.value stuck on receiver with no way to access it" outcome mapped to the credit-vault domain (borrowed principal stranded, claimable only through the lossy recovery path).

### Likelihood Explanation
- The `lossRecoveryPrice == 0` revert needs `funded * RECOVERY_FULL < pendingBasis`; with `RECOVERY_FULL` at 18-decimal precision this requires either an astronomically inflated `pendingBasis` or a near-total loss where the funded remainder is dust — the latter occurs naturally in genuine default-adjacent `stopEpochWithDuration` calls.
- More robustly, *any* revert inside the try produces the permanent default, including `settleBorrowerInterest()` on a programmable borrower (an external call to code the vault does not control) and token-level transfer failures to `feeReceiver`. These are transient conditions that would be retryable — but the catch-all removes the retry path entirely.
- No existing guard prevents it: `skipDefaultCheck`, the skim, and `_checkNotAllowed` preconditions run before the try; the catch is unconditional.

### Recommendation
- Narrow the `try` scope to only `getFundsFromBorrower` (and `settleBorrowerInterest` if it is part of borrower funding), moving `collectWithdrawFunds`, accounting, and fee transfers outside the catch, or
- Use catch-reason inspection / an explicit "funding failed" flag so only a genuine borrower shortfall triggers `_handleBorrowerDefault`, while internal accounting reverts propagate and leave the epoch retryable — the equivalent of Connext's recommended "bump/retry the failed xcall via delegate" pattern.
- Alternatively, make `collectWithdrawFunds` handle the zero-recovery-price case by recording an explicit zero-loss epoch (as `IdleCDOEpochQueue` already does with `isEpochWithdrawZero`) instead of reverting.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// Setup: epoch variant + IdleCreditVault, KYC'd lender LP deposits and holds AA tranches.
// 1. Buffer phase: lender requests a large normal withdraw:
vm.prank(lender);
cdoEpoch.requestWithdraw(largeAmount, AATranche); // grows IdleCreditVault.pendingWithdraws

// 2. Epoch ends; borrower has repaid liquidity. Owner applies a loss consuming
//    almost all pending basis so pendingToFund * RECOVERY_FULL / pendingBasis == 0:
vm.prank(owner);
cdoEpoch.stopEpochWithDuration(newApr, 0, newDuration, lossAmount);

// 3. collectWithdrawFunds(pendingToFund) reverts NotAllowed() inside the try;
//    catch executes _handleBorrowerDefault(...):
assertTrue(cdoEpoch.defaulted());          // permanent, no unsetter
assertTrue(cdoEpoch.paused());
assertFalse(cdoEpoch.isEpochRunning());

// 4. Borrower kept the repaid funds (transferFrom rolled back); lender's claim
//    is only available via the defaulted recovery path at a haircut, or frozen
//    until owner finalization:
vm.prank(lender);
vm.expectRevert(); // normal claim path blocked
cdoEpoch.claimWithdrawRequest();
```

Uncertainty: the exact `RECOVERY_FULL` precision constant and the prefunded-variant `_beforeStopEpoch` interactions were not fully verified from the index; the core finding (catch-all converting an internal `NotAllowed` revert into an irreversible `defaulted = true`) is confirmed by `IdleCDOEpochVariant.sol:408-505` and `IdleCreditVault.sol:411-421`.
