### Title
`depositDuringEpoch` credits the full requested amount without measuring the actual received balance, enabling NAV over-crediting or DoS with fee-on-transfer underlyings - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.depositDuringEpoch` pulls `_amount` of `token` from the depositor via `_transferUnderlyingsFrom`, but then mints tranche shares, mints strategy tokens 1:1, and forwards `_amount` to the borrower — all based on the pre-transfer `_amount`, not the post-transfer received balance. The normal `_deposit` path correctly measures `_contractTokenBalance(_token) - _preBal`, but the mid-epoch path does not. With a fee-on-transfer / deflationary underlying, the vault receives less than `_amount` while its accounting is credited for the full `_amount`.

### Finding Description
In `depositDuringEpoch` (contracts/IdleCDOEpochVariant.sol:685-732):

```solidity
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
...
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
_mintShares(_tranche, msg.sender, _minted, _amount);
expectedEpochInterest += interest;
IdleCreditVault(strategy).mintStrategyTokens(_amount);
_transferUnderlyings(_borrower(), _amount);
```

Contrast with `_deposit` in the same hierarchy (contracts/IdleCDOCreditVault.sol:203-206), which explicitly computes the received delta:

```solidity
uint256 _preBal = _contractTokenBalance(_token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
_minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, msg.sender, _tranche);
```

The mid-epoch path has no pre/post balance measurement. If `token` charges a fee on transfer (e.g., a rebasing/deflationary stablecoin used as vault underlying, which is a deployment-time configuration with no guard rejecting such tokens), three things go wrong simultaneously:

1. `_mintShares` increases `lastNAV` of the tranche by the full `_amount` while only `_amount - fee` was received.
2. `IdleCreditVault.mintStrategyTokens(_amount)` mints 1:1 strategy tokens backing NAV that does not exist.
3. `_transferUnderlyings(_borrower(), _amount)` attempts to push the full `_amount` out.

### Impact Explanation
Two failure modes:

- **DoS**: if the vault's idle token balance equals exactly what was just received (typical mid-epoch, since funds are forwarded to the borrower), `_transferUnderlyings(_borrower(), _amount)` reverts on insufficient balance, permanently reverting `depositDuringEpoch` for any deposit — temporarily freezing that funding path.
- **Insolvency / unfair payout**: if the vault holds any residual idle balance ≥ `fee`, the transfer succeeds and the borrower receives `_amount` funded partially by other depositors' assets, while the new lender's tranche NAV and strategy tokens were credited for `_amount`. At `stopEpoch`/claim time, total accounted NAV exceeds actual assets, so the last claimers (`claimWithdrawRequest`, `collectWithdrawFunds`) revert — direct fund loss socialized onto other tranche holders, quantified as `fee` per FoT deposit.

The existing `_skimDonatedAssets` guard does not help (it runs before the transfer), and `_guarded`/`_updateAccounting` operate on `_amount`, not on the received delta.

### Likelihood Explanation
Requires the vault underlying to be a fee-on-transfer token and `isDepositDuringEpochDisabled == false` during a running epoch. The codebase never restricts `token` to non-FoT assets, and Idle vaults have historically used tokens like USDT where fee parameters exist on-chain. Any unprivileged KYC-passed lender can trigger it via a single `depositDuringEpoch` call — no privileged cooperation needed.

### Recommendation
Measure the actually received amount and use it throughout, mirroring `_deposit`:

```solidity
uint256 _preBal = _contractTokenBalance(token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
uint256 _received = _contractTokenBalance(token) - _preBal;
```

Then compute `interest`, `trancheInterest`, `_minted`, `mintStrategyTokens`, and the borrower forwarding using `_received` instead of `_amount`. Alternatively, explicitly document and enforce that FoT underlyings are unsupported (e.g., revert if `received != _amount`).

### Proof of Concept

// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "./IdleCreditVault.t.sol"; // reuse the existing harness

contract FoTToken is ERC20 {
    uint256 public constant FEE_BPS = 100; // 1%
    constructor() ERC20("FoT", "FOT") {}
    function mint(address to, uint256 a) external { _mint(to, a); }
    function _transfer(address f, address t, uint256 a) internal override {
        uint256 fee = a * FEE_BPS / 10_000;
        super._transfer(f, t, a - fee);
        if (fee > 0) super._transfer(f, address(0xdead), fee);
    }
}

contract DepositDuringEpochFoTTest is IdleCreditVaultTest {
    function testDepositDuringEpochFoT() external {
        // deploy vault whose `token` is FoTToken (token is set at init)
        // depositAA / depositBB normally (they measure received delta)
        idleCDO.depositAA(10_000e18);
        idleCDO.depositBB(10_000e18);
        _startEpochAndCheckPrices(0);

        vm.prank(owner);
        cdoEpoch.setIsDepositDuringEpochDisabled(false);

        address user = makeAddr("fot");
        deal(address(token), user, 1_000e18);
        vm.startPrank(user);
        token.approve(address(cdoEpoch), 1_000e18);
        // Case A (vault had no idle balance): reverts on
        // _transferUnderlyings(borrower, _amount) -> depositDuringEpoch bricked
        vm.expectRevert();
        cdoEpoch.depositDuringEpoch(1_000e18, address(AAtranche));
        vm.stopPrank();

        // Case B: pre-fund vault with >= fee dust so transfer succeeds.
        // Then lastNAVAA + strategyToken supply exceed real assets by `fee`,
        // and the last claimWithdrawRequest reverts -> loss socialized.
    }
}
