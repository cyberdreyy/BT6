### Title
Front-Running `LockupFactory::create()` Allows an Employee to Deploy Their Own Lockup With No Vesting Schedule, Bypassing the Foundation's Intended Terms - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create()` derives the address of the to-be-deployed lockup contract deterministically from the `owner_account_id` argument alone, and does not check whether that address is already taken before scheduling the `create_account`/`deploy_contract`/`new` batch. [1](#0-0)  Any account — including the intended beneficiary itself — can call `create()` for a given `owner_account_id` ahead of the NEAR Foundation's official grant transaction, deploying a `LockupContract` at that deterministic address with attacker-chosen (lenient) lockup/vesting parameters, e.g. `vesting_schedule: None`, `lockup_duration: 0`. Because the address is derived solely from `owner_account_id`, the Foundation's subsequent legitimate `create()` call for the same beneficiary fails at the account-creation step, leaving the beneficiary-controlled, vesting-free contract in place at the canonical lockup address. This mirrors the report's "Method 2" pattern: an unprivileged party front-runs a call that is scoped to a target identity, seizing the identity-bound deployment slot and dictating the terms under which that slot is later used.

### Finding Description
`create()` computes the lockup account name as `sha256(owner_account_id)[..20]` concatenated with the factory account, and immediately schedules `create_account().deploy_contract(CODE).transfer(deposit).function_call("new", LockupArgs{...})` for that address: [2](#0-1) 

`LockupArgs.vesting_schedule`, `lockup_duration`, `lockup_timestamp`, and `release_duration` are all supplied by whoever calls `create()`, not by the Foundation exclusively: [3](#0-2)  The `foundation_account_id` field on the created contract is only populated `if vesting_schedule.is_some()`: [4](#0-3)  so a caller who omits `vesting_schedule` produces a fully-unlocked (as of `TRANSFERS_STARTED`), non-vested lockup with no Foundation termination rights, per `LockupContract::new`'s assertion that "Foundation account can't be added without vesting schedule" only enforces the reverse direction, not that vesting must exist. [5](#0-4) 

Since the target address depends only on `owner_account_id` (a value publicly known in advance — e.g., the employee's own account name), the intended beneficiary (or anyone) can call `create(owner_account_id = <beneficiary>, vesting_schedule = None, lockup_duration = 0, ...)` before the Foundation's real grant transaction lands. The Foundation's later `create()` call for the same `owner_account_id` will attempt `create_account()` on an address that already exists; this NEAR runtime action fails, the whole receipt fails, and `on_lockup_create` detects the failure via `is_promise_success()` and simply refunds the attached deposit to the Foundation's predecessor account: [6](#0-5)  The attacker's minimal-deposit, vesting-free contract remains permanently deployed at the canonical lockup address for that `owner_account_id`.

The binding broken is: *the vesting/lockup schedule the Foundation intends to grant for a given `owner_account_id`* vs. *the vesting/lockup schedule that actually ends up deployed at that deterministic address*. An unprivileged party (including the beneficiary) can force these to diverge in their own favor before the Foundation ever acts, with no requirement to compromise Foundation keys, no reliance on a misconfigured deployment, and no assumption of privileged access — only knowledge of the target `owner_account_id` and the ability to submit a transaction first.

### Impact Explanation
This is Critical impact under "locked or unvested tokens released early" / "a wrongly parameterised deployment": once the Foundation (unaware the address is already occupied, or having its own funding transfer sent by plain `Promise`/`near transfer` to what it assumes is a freshly-initialized, correctly-vested contract) funds the account, those NEAR tokens sit behind a contract with no vesting cliff and (`lockup_duration: 0`, default `TransfersInformation::TransfersEnabled` at the fixed `TRANSFERS_STARTED` timestamp) no lockup — the beneficiary can withdraw immediately via the owner methods in `lockup/src/owner.rs`, instead of being subject to the multi-year vesting/lockup schedule the Foundation intended.

### Likelihood Explanation
Likelihood is high for a motivated beneficiary: `owner_account_id` values for planned grants are typically known ahead of time (they are the employee's own chosen NEAR account), the deterministic address is trivially computable off-chain via `sha256`, and the only cost to the attacker is the `MIN_ATTACHED_BALANCE` (3.5 NEAR) required by `create()`, which remains in the attacker/beneficiary's own contract. No special privileges, races against unknown mempool content, or validator collusion are required — the attacker only needs to submit before the Foundation's official grant transaction is included.

### Recommendation
Bind the deployed lockup's parameters to a value the beneficiary cannot unilaterally choose, e.g.:
- Restrict `create()` (or at least the ability to omit `vesting_schedule`/shrink `lockup_duration`) to Foundation-approved callers, consistent with the "Method 1" mitigation of restricting `build`/`create`.
- Before scheduling `create_account`, have the factory check (or have `on_lockup_create` verify post-hoc) that no contract already exists at the derived address, and treat pre-existing accounts at that address as a hard failure rather than silently refunding while leaving the pre-empting deployment intact.
- Consider deriving the deterministic address from a Foundation-issued nonce/grant-id instead of purely from `owner_account_id`, so the address cannot be pre-computed and squatted before the grant is issued.

### Proof of Concept
1. Foundation plans to grant employee `alice.near` a vested lockup and will later call `create(owner_account_id="alice.near", vesting_schedule=Some(...), lockup_duration=..., release_duration=...)` attaching the real grant amount.
2. `alice.near` (or any third party) computes `lockup_account_id = hex(sha256("alice.near")[..20]) + "." + factory_account`.
3. `alice.near` calls `create(owner_account_id="alice.near", lockup_duration=0, lockup_timestamp=None, vesting_schedule=None, release_duration=None, whitelist_account_id=None)` attaching `MIN_ATTACHED_BALANCE`, per [2](#0-1) , creating the contract at `lockup_account_id` with no vesting and zero lockup duration.
4. The Foundation's subsequent `create()` call for the same `owner_account_id` fails at `create_account()` (address already occupied); `on_lockup_create` observes `is_promise_success() == false` and refunds the Foundation's deposit, per [6](#0-5) , leaving `alice.near`'s vesting-free contract as the permanent occupant of the canonical lockup address for `alice.near`.
5. Any NEAR later transferred to that address (believed by operators to be the Foundation-vested lockup) is immediately withdrawable by `alice.near` under `lockup/src/owner.rs`'s owner methods, since `get_locked_amount()` resolves to 0 given the absent vesting schedule and zero lockup duration.

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )
            .then(ext_self::on_lockup_create(
                lockup_account_id,
                env::attached_deposit().into(),
                env::predecessor_account_id(),
                &env::current_account_id(),
                NO_DEPOSIT,
                gas::CALLBACK,
            ))
    }

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
