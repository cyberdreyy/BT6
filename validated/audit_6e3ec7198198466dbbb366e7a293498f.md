### Title
EI-synthetic User bypasses the "EIs not allowed" job-run authorization check in `PipelineRunsController.Create` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`auth.AuthenticateExternalInitiator` injects a synthetic `clsessions.User{Role: UserRoleRun}` (no `ID`/`Email`) into the same `SessionUserKey` used by real session/token authentication. `PipelineRunsController.Create` gates the "run job by integer ID" path on `_, isUser := auth.GetAuthenticatedUser(c)`, which only checks whether *any* `*clsessions.User` object is present in context — it does not verify the request actually came from a real dashboard user (via `AuthenticateBySession`/`AuthenticateByToken`). Because the EI middleware plants an identical `User` object, an external-initiator credential holder satisfies `isUser == true` and can reach `RunJobV2` with an arbitrary numeric job ID, defeating the explicit code comment "EIs not allowed."

### Finding Description
`AuthenticateExternalInitiator` sets: [1](#0-0) 
which stores a synthetic `User{Role: UserRoleRun}` under `SessionUserKey`, indistinguishable in type from a real authenticated user.

`GetAuthenticatedUser` simply type-asserts the object stored at `SessionUserKey`: [2](#0-1) 
It has no way to tell whether the object came from `AuthenticateBySession`/`AuthenticateByToken` (a real user with `ID`/`Email`) or from `AuthenticateExternalInitiator` (a synthetic placeholder).

`PipelineRunsController.Create` relies on this boolean alone to gate the job-run-by-integer-ID branch, with an explicit comment that this path should be user-only: [3](#0-2) 
Since the EI-derived `User` also satisfies `isUser == true`, any external initiator that successfully authenticates (route configured with `AuthenticateExternalInitiator` alongside session/token methods, as evidenced by the very existence of this `isUser` distinction and the removed-webhook-UUID branch immediately above it) can call `prc.App.RunJobV2(ctx, jobID, nil)` for **any** numeric job ID — not just a job bound to that specific external initiator. `RunJobV2` performs no additional check that the caller (EI) is authorized for that particular job.

### Impact Explanation
This is an authorization-bypass / unauthorized-job-run issue: an external-initiator credential (intended only to trigger its own bound webhook job) can be used to trigger an arbitrary job by integer ID on the node, potentially causing unintended on-chain transactions or job side effects for jobs the EI was never provisioned to run. This matches the Chainlink bounty impact class "unauthorized job run or fund movement" via role/authorization bypass.

### Likelihood Explanation
Requires only a valid (but low-privilege) external-initiator access key/secret pair — not an admin, edit, or even a real user account — and knowledge/guessing of a target job's integer ID. No session hijacking or credential theft is needed beyond what an EI is normally issued. The flaw is deterministic and repeatable for any request through the affected route.

### Recommendation
Distinguish real authenticated users from EI-derived synthetic users explicitly, e.g., have `AuthenticateExternalInitiator` set a distinct context key (not reuse `SessionUserKey`), or have `GetAuthenticatedUser` refuse to return `ok=true` for placeholder users lacking `ID`/`Email`. In `PipelineRunsController.Create`, replace the `isUser` boolean check with an explicit check that the caller is NOT an external initiator (`_, isEI := auth.GetAuthenticatedExternalInitiator(c); if isEI { reject }`) rather than relying on presence of any `User` object.

### Proof of Concept
1. Unit test in `core/web/auth/auth_test.go`: call `AuthenticateExternalInitiator` on a `gin.Context` with a valid EI token, then call `AuthenticateBySession`-equivalent in a separate context with a real user; call `GetAuthenticatedUser` on both and assert both return `ok=true`, with the EI case returning a `User{Role: UserRoleRun, ID: "", Email: ""}`.
2. Handler-level test in `core/web/pipeline_runs_controller_test.go`: stand up a test app with an existing job and a registered `ExternalInitiator`. Send `POST /v2/jobs/<int-job-id>/runs` using only `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers (no session/API token). Assert that the response is `200 OK` and a pipeline run resource is returned (expected/current buggy behavior), then assert the fix rejects it with `422`/`401` after the isEI check is added.
