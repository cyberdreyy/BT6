### Title
Builder pending withdrawals can commit more Gwei to the execution layer than the builder's balance can back - ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builder_withdrawals` builds `Withdrawal` objects directly from the raw, unmodified `amount` field of each queued `state.builder_pending_withdrawals` entry, without ever checking it against the builder's actual balance or against amounts already committed to the same builder earlier in the same block. `apply_withdrawals`, in contrast, caps the real balance deduction with `min(withdrawal.amount, builder_balance)`. This decoupling reproduces exactly the bug class from the referenced report: the amount *committed* (to the execution layer, which is required to honor it) diverges from the amount *actually debited* on the consensus-layer side whenever liquidity (here, the builder's balance) is insufficient to cover the full committed amount.

### Finding Description
`get_builder_withdrawals` (specs/gloas/beacon-chain.md): [1](#0-0) 

For every entry in `state.builder_pending_withdrawals` it unconditionally emits a `Withdrawal` with `amount=withdrawal.amount` — the raw requested amount — with no comparison against `builder.balance`, and (unlike the analogous validator path) with no accumulation of amounts already emitted for the same builder within the same batch.

Contrast this with the validator partial-withdrawal path, `get_pending_partial_withdrawals`, which explicitly guards against exactly this double-counting problem by recomputing the balance after all prior withdrawals in the same batch: [2](#0-1) 

No equivalent `get_balance_after_withdrawals`-style guard exists for builders.

`apply_withdrawals`, which performs the actual balance mutation, caps the deduction to what is actually available: [3](#0-2) 

The withdrawal amounts produced by `get_builder_withdrawals`/`get_expected_withdrawals` are committed into `state.payload_expected_withdrawals`, which the spec explicitly states the execution layer must honor for the corresponding block: [4](#0-3) 

If `state.builder_pending_withdrawals` contains two (or more) entries for the same `builder_index` whose requested amounts together exceed `builder.balance` (e.g., two entries each requesting the builder's full balance), `get_builder_withdrawals` will produce two `Withdrawal` objects, each carrying the full requested amount, to be minted by the EL to their respective `fee_recipient` addresses. `apply_withdrawals` will then process them in order: the first debits `min(amount, balance)` (draining the builder to zero), and the second debits `min(amount, 0) = 0`. The consensus-layer state loses only one builder's worth of balance, while the execution layer is committed to paying out up to twice that amount across two recipients — this is a direct Gwei-creation event, breaking the invariant that no Gwei may be created or paid beyond what was actually owned and debited.

This directly parallels the SavingsAccount `withdrawAll`/`switchStrategy` bug class: a partial/limited outcome on the "source of truth" side (capped balance deduction here, capped `unlockTokens` return there) is not propagated back into the "committed" accounting (the uncapped `Withdrawal.amount` sent to the EL here, the full `_amount`/old strategy share removal there), producing a mismatch that either destroys or (in this CL case) creates value relative to what was actually available.

### Impact Explanation
This falls under the Critical category "Gwei created, destroyed or paid to a non-owner." Unlike the validator sweep path — where `amount=balance` is read fresh at the time of computation and is thus self-consistent — the builder pending-withdrawal path commits the execution layer to paying amounts that were never validated against, or reconciled with, the builder's real balance across multiple withdrawal entries processed in the same block. This can inflate total supply and misdirect payments to fee recipients beyond what the builder actually had, entirely through spec-conformant processing (no malicious peer, coalition, or client bug required — only a set of builder pending withdrawal queue entries that a spec-following block producer will faithfully process).

### Likelihood Explanation
The likelihood depends on whether the request-side logic that enqueues entries into `state.builder_pending_withdrawals` prevents the sum of pending amounts for a given builder from exceeding its balance at enqueue time, and whether the builder's balance can be reduced between enqueue and processing (e.g., by additional withdrawal requests being queued in the interim, or other balance-affecting operations). I was not able to fully verify the enqueue-side validation logic for `builder_pending_withdrawals` (the function that pushes `BuilderPendingWithdrawal` entries) within the available search results/iterations, so I cannot confirm with certainty whether upstream checks already prevent the overcommitment scenario described. This is a limitation of my investigation, not a claim that the request path is safe — the processing-side code (`get_builder_withdrawals`) itself contains no such safeguard, which is the root of the issue, and it is inconsistent with the safeguard that exists in the equivalent validator code path.

### Recommendation
Mirror the guard used in `get_pending_partial_withdrawals` for validators: within `get_builder_withdrawals`, track a running total of amounts already queued for withdrawal to each `builder_index` within the same batch (or compute a `get_builder_balance_after_withdrawals`-style helper), and cap each emitted `Withdrawal.amount` to `min(withdrawal.amount, remaining_builder_balance)` at the point the `Withdrawal` object is constructed — not only at balance-application time in `apply_withdrawals`. This ensures the amount committed to the execution layer never exceeds what will actually be debited from the builder.

### Proof of Concept
1. Builder `B` has `balance = X`.
2. Two entries are present in `state.builder_pending_withdrawals` for builder `B`: `{amount: X, fee_recipient: A1}` and `{amount: X, fee_recipient: A2}`.
3. `get_builder_withdrawals` iterates the queue and, for each entry, emits `Withdrawal(amount=X, address=A1)` and `Withdrawal(amount=X, address=A2)` — total committed = `2X` — since it never checks `builder.balance` nor tracks amounts already emitted for `B` in this batch.
4. `apply_withdrawals` runs sequentially: first withdrawal debits `min(X, X) = X` (builder balance → 0); second debits `min(X, 0) = 0`.
5. Net CL-side balance decrease for builder `B`: `X`. Net EL-committed payout across `A1` and `A2`: `2X`. The excess `X` Gwei paid to `A2` is created without any corresponding balance decrease anywhere in the system.

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
