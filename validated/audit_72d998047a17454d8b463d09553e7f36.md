### Title
Unprotected job can force `config.Protected = true` via a crafted cache key suffix, causing volume/cache-dir name collision with legitimate protected-ref caches - ([File: executors/docker/volume.go])

### Summary
`createVolumesManager` sets `config.Protected` to `true` if any cache key in `.gitlab-ci.yml` ends with `-protected` (and not `-non_protected`), regardless of the actual ref protection status. Because the resulting Docker volume name / host cache directory path is derived from `ProjectRealUniqueName()` + `hashPath(destination)` (both ref-independent) plus this same suffix, an attacker on an unprotected branch can make their cache volume name/hostPath collide exactly with the ones used by a legitimately protected-ref build of the same project.

### Finding Description
`createVolumesManager` in `executors/docker/volume.go` computes:
```go
protectedKeyIdx := slices.IndexFunc(e.Build.Cache, func(c spec.Cache) bool {
    return strings.HasSuffix(c.Key, "-protected") && !strings.HasSuffix(c.Key, "-non_protected")
})
config.Protected = e.Build.IsProtected() || protectedKeyIdx >= 0
``` [1](#0-0) 

`c.Key` is the literal `key:` value of a `cache:` entry in the job's `.gitlab-ci.yml`, which is fully attacker-controlled by any pipeline author, including on unprotected branches/MRs. Setting a cache key such as `foo-protected` on an unprotected ref makes `protectedKeyIdx >= 0`, flipping `config.Protected` to `true` even though `e.Build.IsProtected()` is `false`.

`config.Protected` is consumed by `manager.withProtected`, which just appends the literal `-protected` string suffix to a hash-derived name:
```go
func (m *manager) withProtected(s string) string {
    if !m.config.Protected {
        return s
    }
    return s + protectedSuffix
}
``` [2](#0-1) 

This is used both for host-based cache directories and Docker named volumes:
```go
dir := m.withProtected(hashPath(destination))
hostPath := m.parser.Path().Join(m.config.CacheDir, m.config.UniqueName, dir)
``` [3](#0-2) 
```go
volumeName := m.withProtected(fmt.Sprintf("%s-cache-%s", name, hashedDestination))
``` [4](#0-3) 

Crucially, neither `m.config.UniqueName` (`ProjectRealUniqueName()`) nor `hashPath(destination)` depend on the ref or on protection status — they depend only on the project and the cache mount path declared in `.gitlab-ci.yml`. The *only* input that differentiates a "protected" cache path/volume name from a "non-protected" one is this `-protected` string suffix, which is entirely attacker-controlled through the cache key naming heuristic. Consequently, an attacker on an unprotected branch who (a) knows/guesses the cache `destination` path used by protected pipelines of the same project (commonly a fixed, documented path like `node_modules/` or `.cache/`) and (b) adds any cache entry whose key ends in `-protected`, will compute the *exact same* volume name / host cache directory as a genuine protected-ref build of that project.

There is no additional binding of the volume name/hostPath to the actual ref, commit, or a server-verified protection flag — the protection semantics are purely a local, client-computable string transformation. No existing check (image allow-list, overwrite guard, path validation, auth check) inspects or restricts this cache-key-driven protected flag against the real ref protection state.

### Impact Explanation
An attacker who can push to or open an MR against an unprotected branch of a project can read from and write to the same Docker volume / host cache directory that protected-ref builds of that project persist their cache in. This breaks the protected/unprotected cache isolation invariant the code explicitly aims to enforce (per the referenced work item), allowing:
- Exfiltration of cache contents (potentially including build artifacts, dependency caches, or files with sensitive data) written by protected-ref pipelines.
- Poisoning of the protected-ref cache with attacker-controlled files, which get restored into subsequent protected-ref job containers — leading to a persistence/tampering vector across the protection boundary.

### Likelihood Explanation
Feasible for any pipeline author with push/MR access to an unprotected branch (a standard, unprivileged permission level). No admin or leaked-secret involvement is required. The only extra knowledge needed is the cache `destination` path used by the project's `.gitlab-ci.yml`, which is typically visible in the repository's own CI config (not secret). The attack is deterministic and repeatable — the same crafted cache key will always compute the same colliding volume name/hostPath on every run, matching Docker's `-v` volume driver reuse behavior (`Driver: e.Config.Docker.VolumeDriver`).

### Recommendation
Do not derive `config.Protected` (or the resulting volume-name/host-path suffix) from user-controlled cache key content. Either drop this cache-key heuristic entirely and rely solely on the server-verified `e.Build.IsProtected()`, or, if the `-protected` cache-key feature must remain (per work item 494478), validate/authorize it server-side (e.g., require the backend to also confirm ref protection before honoring a `-protected` cache key) rather than trusting a client-supplied string suffix. At minimum, incorporate a value that is not attacker-controlled and reflects real protection state into the hash/volume name so that a spoofed `-protected` suffix cannot alias a genuinely protected ref's cache identity.

### Proof of Concept
Go unit test in `executors/docker/volume_test.go` (or extending `manager_test.go`):
```go
func TestCreateVolumesManager_CacheKeySpoofsProtected(t *testing.T) {
    build := &common.Build{
        JobResponse: common.JobResponse{
            GitInfo: common.GitInfo{Ref: "feature-branch"}, // unprotected
        },
        Cache: []spec.Cache{{Key: "foo-protected"}}, // attacker-controlled key
    }
    // build.IsProtected() == false

    e := &executor{Build: build /* ... */}
    vm, err := createVolumesManager(e)
    require.NoError(t, err)

    // Assert config.Protected ended up true despite IsProtected()==false
    m := vm.(*manager)
    assert.True(t, m.config.Protected)

    // Compute expected colliding name for the same project + same cache destination
    legit := &executor{Build: &common.Build{
        JobResponse: common.JobResponse{GitInfo: common.GitInfo{Ref: "main"}, ProtectedBool: true},
    } /* same UniqueName */}
    legitVM, _ := createVolumesManager(legit)

    // Both managers, given identical destination path, must produce identical
    // withProtected(hashPath(destination)) / volume names -- proving cross-boundary collision.
    assert.Equal(t,
        legitVM.(*manager).withProtected(hashPath("/cache/dest")),
        m.withProtected(hashPath("/cache/dest")),
    )
}
```
Expected assertion: the unprotected-ref manager and the protected-ref manager compute identical volume/hostPath identifiers for the same cache destination, demonstrating that the attacker-controlled `-protected` cache key spoofs the protected volume identity and grants read/write access to the same cache storage.
