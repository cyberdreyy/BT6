### Title
Unvalidated instruction-supplied `decimals` field in SPL-Token "Checked" instruction parsing leads to misreported `tokenAmount` in JSON-RPC parsed transaction output - ([File: transaction-status/src/parse_token.rs])

### Summary
`parse_token` in `transaction-status/src/parse_token.rs` builds the human-readable `tokenAmount` field for `TransferChecked`, `ApproveChecked`, `MintToChecked`, and `BurnChecked` instructions using the `decimals` value taken directly from the instruction's own data, without ever cross-checking it against the actual on-chain mint account's `decimals`. This mirrors the Treasury.sol bug pattern: a decimal/scaling-relevant value supplied by an untrusted party is trusted and used to compute a derived accounting figure without validating it against the authoritative source of truth (the mint account).

### Finding Description
For each "checked" SPL-Token instruction the parser constructs the additional data purely from the caller-controlled instruction bytes: [1](#0-0) 

The same pattern repeats for `ApproveChecked`, `MintToChecked`, and `BurnChecked`: [2](#0-1) [3](#0-2) 

`token_amount_to_ui_amount_v3` then uses this untrusted `decimals` value (with no other source-of-truth check) to compute `ui_amount` / `ui_amount_string`: [4](#0-3) 

This parsed representation is attached to transaction metadata regardless of whether the transaction succeeded, because `parse_ui_transaction_status_meta`/`encode` produce the `JsonParsed` encoding for both successful and failed transactions (the `err`/`status` field is populated independently of whether `meta` is parsed): [5](#0-4) [6](#0-5) 

Note that the SPL Token program itself enforces that the `decimals` field in a "Checked" instruction matches the mint's real decimals *for the instruction to succeed*. However, that enforcement only applies to instructions that actually execute; a transaction can fail (e.g., due to insufficient funds, a preceding instruction failing, or the decimals check itself failing) while still being included on-chain and served by `getTransaction`/`getBlock` with `jsonParsed` encoding. In all such failed-transaction cases the parser still echoes back whatever `decimals` the attacker embedded in the instruction, with no comparison to the true mint decimals fetched from the ledger/bank.

In contrast, the actual pre/post token balance computation used for consensus-affecting accounting (`SvmTokenInfo::unpack_token_account` in `svm/src/transaction_balances.rs`) correctly loads decimals from the real mint account rather than trusting instruction data: [7](#0-6) 

This shows the codebase already recognizes that decimals must come from the authoritative mint account elsewhere, but the human-readable "parsed" instruction display path in `transaction-status/src/parse_token.rs` does not apply the same validation.

### Impact Explanation
An unprivileged user can submit (or have submitted, then queried) a transaction containing a `TransferChecked`/`ApproveChecked`/`MintToChecked`/`BurnChecked` instruction with an arbitrary `decimals` value that does not match the real mint's decimals. When any RPC consumer retrieves that transaction via `getTransaction`, `getBlock`, or similar `jsonParsed`-encoded APIs, the returned `tokenAmount.uiAmount`/`uiAmountString` will misreport the true token quantity by whatever ratio the fabricated decimals implies (e.g., displaying a value 10^9 times too small or too large). This is a decoder misreporting issue in an unprivileged-user-reachable JSON-RPC/transaction-status parsing path, matching the "decoder panic and misreporting" acceptable-impact category. Downstream tooling, block explorers, or accounting systems that rely on this parsed field for a failed (or partially executed prior-to-check) transaction could record or display incorrect token amounts.

### Likelihood Explanation
Likelihood is limited by the fact that for *successful* transactions the SPL Token program enforces decimals correctness, so misreporting is confined to failed transactions (or before the decimals-check instruction executes). Since failed transactions are still recorded on-chain and served through the same `jsonParsed` transaction/instruction parsing code path, any unprivileged user can trivially construct such a transaction, making it easy to trigger though its blast radius is limited to display-layer misreporting rather than consensus-affecting fund loss.

### Recommendation
- Short term: In `parse_token` (`transaction-status/src/parse_token.rs`), do not treat the instruction-embedded `decimals` value as fully authoritative for building `tokenAmount`; either omit `uiAmount`/`uiAmountString` computation when the instruction is part of a failed transaction, or clearly document/flag that these fields reflect the *claimed* decimals rather than a verified value.
- Long term: Where feasible, resolve `decimals` from the actual mint account (as is already done in `account-decoder/src/parse_token.rs`'s `parse_token_v3` and in `svm/src/transaction_balances.rs`) instead of from instruction data for parsed instruction display, to keep the human-readable metadata consistent with the same validated numbers used for real token-balance accounting.

### Proof of Concept
1. Construct a transaction containing a legitimate `TransferChecked` instruction whose `decimals` field is deliberately set to a value different from the real mint's decimals (e.g., mint has 9 decimals, instruction claims `decimals: 0`).
2. Ensure the transaction fails for an unrelated reason before/without the SPL Token program's own decimals-mismatch check causing rejection (or simply rely on the decimals-mismatch itself causing failure) — the transaction is still recorded in the ledger as a failed transaction.
3. Query `getTransaction` (or `getBlock`) with `encoding: "jsonParsed"` for that signature/slot.
4. Observe that the returned `meta.innerInstructions`/`transaction.message.instructions` parsed `transferChecked` entry reports `tokenAmount.decimals` and `tokenAmount.uiAmount` computed straight from the attacker-chosen `decimals`, not the mint's actual decimals, as seen in `transaction-status/src/parse_token.rs:365-373` and `account-decoder/src/parse_token.rs:125-164`.

pub fn token_amount_to_ui_amount_v3(
    amount: u64,
    additional_data: &SplTokenAdditionalDataV2,
) -> UiTokenAmount {
    let decimals = additional_data.decimals;
    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =
        additional_data.interest_bearing_config
    {
        let ui_amount_string =
            interest_bearing_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else if let Some((scaled_ui_amount_config, unix_timestamp)) =
        additional_data.scaled_ui_amount_config
    {
        let ui_amount_string =
            scaled_ui_amount_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else {
        let ui_amount = 10_usize
            .checked_pow(decimals as u32)
            .map(|dividend| amount as f64 / dividend as f64);
        (ui_amount, real_number_string_trimmed(amount, decimals))
    };
    UiTokenAmount {
        ui_amount,
        decimals,
        amount: amount.to_string(),
        ui_amount_string,
    }
}

    fn unpack_token_account<CB: TransactionProcessingCallback>(
        account_loader: &mut AccountLoader<CB>,

            mint,
