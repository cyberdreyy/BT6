### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` only checks the *size* of the `confirmations` set for a request against `num_confirmations`; it never verifies that each account/key that previously confirmed is still a current member. `delete_member` purges only the requests *originated* by the removed member, but does not scrub that member's existing confirmations from other still-pending requests. As a result, a request can execute once `confirmations.len() >= num_confirmations` even though one or more of the counted confirmers have since been removed from `self.members`, so the request is effectively approved by fewer live members than the configured threshold.

### Finding Description
`confirm()` computes the threshold purely from the stored `HashSet<String>` of confirmer identifiers: [1](#0-0) 

There is no re-check that any element of `confirmations` still belongs to `self.members` at confirmation time.

`delete_member` only cleans up requests whose `member` (the *creator*) equals the removed member, and only removes that member's `num_requests_pk` counter — it does not iterate over `self.confirmations` to strip entries created by the removed member on requests they merely *confirmed* but did not create: [2](#0-1) 

So the binding the contract is supposed to maintain — "confirmations counted == confirmations from currently live members" — is broken: a confirmation given while an account was a member persists and counts toward the threshold even after that account is removed via `DeleteMember`.

### Impact Explanation
This allows a `MultiSigRequest` (e.g. a `Transfer` draining the multisig-controlled account, or an `AddKey`/`AddMember` privilege-escalation action) to be executed with fewer *currently trusted* confirmations than `num_confirmations` requires. This directly matches the Critical impact class "a multisig request executed below threshold" defined in scope — funds can move, or membership/keys can change, without the intended K-of-N live approval.

### Likelihood Explanation
It requires normal multisig operation flow (one member creates a request, a second member confirms it, and only later is that second member removed for any reason — compromise, rotation, off-boarding) followed by a third member confirming without being aware the earlier confirmation is stale. Membership churn combined with slow-to-confirm outstanding requests is a realistic operational pattern for a K-of-N scheme, especially since `add_request`/`confirm` are asynchronous and requests can remain pending for the `REQUEST_COOLDOWN` window and beyond.

### Recommendation
In `confirm()`, before comparing `confirmations.len()` to `num_confirmations`, filter `confirmations` to only those entries still present in `self.members` (or recompute the live count). Additionally, in `delete_member`, iterate `self.confirmations` and remove the deleted member's entry from every request's confirmation set, not just requests they authored.

### Proof of Concept
1. Deploy `MultiSigContract` with `members = [A, B, C, D]`, `num_confirmations = 3` via `new()` (`multisig2/src/lib.rs:147-167`).
2. `A` calls `add_request_and_confirm` with a `Transfer` request `R` sending funds to `A`'s own address → `confirmations(R) = {A}`.
3. `B` calls `confirm(R)` → `confirmations(R) = {A, B}` (`len()+1 = 3 >= 3`? No — `len()` is checked *before* insertion: `confirmations.len() as u32 + 1 >= num_confirmations` → `1+1=2 < 3`, so it just inserts, `confirmations(R) = {A, B}`).
4. Separately, `A`, `C`, `D` execute a `DeleteMember{B}` request through the normal 3-confirmation flow, removing `B` from `self.members`. `delete_member` (`multisig2/src/lib.rs:356-379`) deletes any requests `B` *authored*, but `R` was authored by `A`, so `R` and its confirmation set `{A, B}` are untouched.
5. `C` (a live member) calls `confirm(R)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request(R)` runs, transferring funds to `A`.
6. At execution time, the live members are `{A, C, D}`; only `A` and `C` are genuinely current approvers (2 live confirmations), yet the request executed as if 3 members approved, because `B`'s stale confirmation was still counted.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
