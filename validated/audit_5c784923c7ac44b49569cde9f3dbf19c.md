### Title
Rejection bookkeeping keyed by `signer_addr` alone silently drops a signer's rejection record for every block after its first, corrupting per-block rejection tallies - (File: `stacks-signer/src/signerdb.rs`)

### Summary
The `block_rejection_signer_addrs` table is meant to record, per block (`signer_signature_hash`) and per signer (`signer_addr`), that a given signer rejected that block, so per-block rejection weight can be tallied. Its schema declares `PRIMARY KEY (signer_addr)` only — not the compound key `(signer_signature_hash, signer_addr)` that every read/write path assumes. This is the same class of defect as the GoodEntry finding: state that should be scoped per-operation (per-block) is instead left in a single shared slot, so a later, unrelated operation collides with residue left by an earlier one, and ordinary protocol traffic (not an attacker with special privilege) triggers the corruption.

### Finding Description
The table definition: [1](#0-0) 

declares `PRIMARY KEY (signer_addr)`, i.e. globally unique per signer address across the entire database, regardless of which block/tenure/reward cycle the rejection belongs to.

But `add_block_rejection_signer_addr` treats the key as `(signer_signature_hash, signer_addr)` throughout: [2](#0-1) 

- It looks up an existing row filtered by `WHERE signer_signature_hash = ?1 AND signer_addr = ?2`.
- If a row exists for `(hash, addr)` with a different reject code, it does an `UPDATE ... WHERE signer_signature_hash = ?2 AND signer_addr = ?3` (harmless, matches the intended row).
- If no row exists for `(hash, addr)` — which is always true the moment this signer's *first-ever* rejection was for a *different* block hash — it falls into the `None` branch and does a bare `INSERT INTO block_rejection_signer_addrs (signer_signature_hash, signer_addr, reject_code) VALUES (?1, ?2, ?3)`.

Because the table's actual primary key is `signer_addr` alone, and that address already owns a row for the *previous* block's hash, this `INSERT` (not `INSERT OR REPLACE`) violates the primary-key constraint and fails with a SQLite constraint error, which propagates as a `DBError` back to the caller instead of persisting the new block's rejection.

Concretely: once signer address `X` has rejected block `A` (any block, any tenure, any reward cycle — the key has no scoping), every subsequent legitimate rejection by `X` of a *different* block `B` fails to be recorded in `block_rejection_signer_addrs`. This requires no majority, no other signer's key, and no special access — it is simply the normal outcome of the miner proposing more than one block over time and honest signers rejecting more than one of them, which is routine chain-of-tenure operation (e.g. `late_block_proposal.rs`, `proposal_replication_void.rs` tests exercise exactly this "multiple proposals rejected/re-evaluated" pattern) [3](#0-2) .

This mirrors the report's root cause: a value meant to be scoped to one operation (per-block underlying token / per-block rejection record) instead persists in a single shared account slot (`RangeManager` balance / `signer_addr` primary key) and is silently mishandled the next time that slot is touched by a different operation.

### Impact Explanation
`get_block_rejection_signer_addrs` reads back the per-block rejecting-address set: [4](#0-3) 

Any logic that reconstructs a block's rejection tally or the set of signers who rejected a specific block from this table will systematically undercount, because addresses that rejected an *earlier* block can never have their rejection of a *later* block recorded once the PK collision occurs. In a state machine where rejection weight is compared against an acceptance/rejection threshold (the "aggregated-weight vs verified-accepts equality" this scan targets), a silently dropped rejection record means the signer's local bookkeeping of "who rejected this block" is wrong for every block-hash a given address touches after its first rejection is recorded — this can under-report rejection weight for a block that should have accumulated enough weight to be marked `GloballyRejected`, and/or cause spurious `DBError` propagation on the write path (`add_block_rejection_signer_addr` returns `Err`, which upstream code must handle, typically by logging and continuing without having actually recorded the rejection).

I was not able to fully trace, within the remaining tool budget, the exact downstream consumer(s) of `get_block_rejection_signer_addrs` inside `stacks-signer/src/v0/signer.rs` to confirm whether a consensus-critical threshold decision (vs. purely informational/telemetry reporting to the miner) is computed directly from this table's row count. That link should be verified before assigning a final severity; the schema/logic defect itself (compound-key usage against a single-column primary key) is proven directly from the code cited above.

### Likelihood Explanation
High: this requires only ordinary network conditions — a single signer address rejecting more than one distinct block hash over the lifetime of its `signerdb.sqlite` (which is not scoped/reset per reward cycle in the table schema) is a common occurrence for any long-running signer, and is exactly the scenario several existing tests already exercise (rejecting a stale re-proposal, rejecting a competing sibling block, etc.). No majority collusion, private key material, or special timing is needed.

### Recommendation
Fix the table schema to use the compound primary key `(signer_signature_hash, signer_addr)` (matching every query/update/insert already written against it), with an accompanying migration for existing databases, e.g.:
```sql
CREATE TABLE IF NOT EXISTS block_rejection_signer_addrs (
    signer_signature_hash TEXT NOT NULL,
    signer_addr TEXT NOT NULL,
    reject_code INTEGER NOT NULL,
    PRIMARY KEY (signer_signature_hash, signer_addr)
) STRICT;
```
Additionally, change the `INSERT` in the `None` branch of `add_block_rejection_signer_addr` to `INSERT OR REPLACE`/`ON CONFLICT` handling so a constraint violation cannot silently drop a legitimate rejection, and audit every call site of `get_block_rejection_signer_addrs` to confirm whether it feeds a consensus-relevant rejection-weight computation; if so, add a regression test asserting that the same signer address correctly accumulates independent rejection rows for two different block hashes.

### Proof of Concept
1. Signer address `X` receives block proposal `A` (hash `h_A`), rejects it → `add_block_rejection_signer_addr(h_A, X, code1)` inserts row `(h_A, X, code1)` (table's `None` branch, first insert succeeds because the PK slot for `X` is empty).
2. Later, the same signer address `X` receives an unrelated block proposal `B` (hash `h_B`, different tenure/height/reward-cycle) and legitimately rejects it → `add_block_rejection_signer_addr(h_B, X, code2)` runs the lookup `WHERE signer_signature_hash = h_B AND signer_addr = X`, finds nothing (the existing row is keyed to `h_A`), and falls into the `None` branch's plain `INSERT INTO block_rejection_signer_addrs (h_B, X, code2)`.
3. Because `PRIMARY KEY (signer_addr)` already contains a row for `X` (from step 1), this `INSERT` fails with a UNIQUE/PRIMARY KEY constraint violation, returned as `Err(DBError)`.
4. `get_block_rejection_signer_addrs(h_B)` therefore never returns `X` as a rejecting address for block `B`, even though `X` genuinely rejected it — the per-block rejection record for `B` is missing this signer's entry, corrupting any weight computed from this table for block `B`.     /// Record an observed block rejection_signature
    pub fn add_block_rejection_signer_addr(
        &self,
        block_sighash: &Sha512Trunc256Sum,
        addr: &StacksAddress,
        reject_reason: RejectReasonPrefix,
    ) -> Result<bool, DBError> {
        // If this signer/block already has a signature, do not allow a rejection
        let sig_qry = "SELECT EXISTS(SELECT 1 FROM block_signatures WHERE signer_signature_hash = ?1 AND signer_addr = ?2)";
        let sig_args = params![block_sighash, addr.to_string()];
        let exists = self.db.query_row(sig_qry, sig_args, |row| row.get(0))?;
        if exists {
            warn!("Cannot add block rejection because a signature already exists.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %addr,
                "reject_reason" => ?reject_reason
            );
            return Ok(false);
        }

        // Check if a row exists for this sighash/signer combo
        let qry = "SELECT reject_code FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1 AND signer_addr = ?2 LIMIT 1";
        let args = params![block_sighash, addr.to_string()];
        let existing_code: Option<i64> =
            self.db.query_row(qry, args, |row| row.get(0)).optional()?;

        let reject_code = reject_reason as i64;

        match existing_code {
            Some(code) if code == reject_code => {
                // Row exists with same reject_reason, do nothing
                debug!("Duplicate block rejection.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(false)
            }
            Some(_) => {
                // Row exists but with different reject_reason, update it
                let update_qry = "UPDATE block_rejection_signer_addrs SET reject_code = ?1 WHERE signer_signature_hash = ?2 AND signer_addr = ?3";
                let update_args = params![reject_code, block_sighash, addr.to_string()];
                self.db.execute(update_qry, update_args)?;
                debug!("Updated block rejection reason.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(true)
            }
            None => {
                // Row does not exist, insert it
                let insert_qry = "INSERT INTO block_rejection_signer_addrs (signer_signature_hash, signer_addr, reject_code) VALUES (?1, ?2, ?3)";
                let insert_args = params![block_sighash, addr.to_string(), reject_code];
                self.db.execute(insert_qry, insert_args)?;
                debug!("Inserted block rejection.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(true)
            }
        }
    }

    /// Get all signer addresses that rejected the block (and their reject codes)
    pub fn get_block_rejection_signer_addrs(
        &self,
        block_sighash: &Sha512Trunc256Sum,
    ) -> Result<Vec<(StacksAddress, RejectReasonPrefix)>, DBError> {
        let qry =
            "SELECT signer_addr, reject_code FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1";
        let args = params![block_sighash];
        let mut stmt = self.db.prepare(qry)?;

        let rows = stmt.query_map(args, |row| {
            let addr: String = row.get(0)?;
            let addr = StacksAddress::from_string(&addr).ok_or(SqliteError::InvalidColumnType(
                0,
                "signer_addr".into(),
                rusqlite::types::Type::Text,
            ))?;
            let reject_code: i64 = row.get(1)?;

            let reject_code = u8::try_from(reject_code)
                .map_err(|_| {
                    SqliteError::InvalidColumnType(
                        1,
                        "reject_code".into(),
                        rusqlite::types::Type::Integer,
                    )
                })
                .map(RejectReasonPrefix::from)?;

            Ok((addr, reject_code))
        })?;

        rows.collect::<Result<Vec<_>, _>>().map_err(|e| e.into())
    }
