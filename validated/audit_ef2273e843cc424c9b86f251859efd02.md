Based on my analysis, I found a genuine wrong-recipient / beneficiary-bypass analog in `staking_contract.move` that mirrors the HAL-09 dual-mapping-style accounting flaw (a value keyed by a stale/incorrect identity is misrouted). I was not able to fully view `request_commission_internal` due to search/tool limits (the file appears to have collapsed whitespace in that region), so I flag that portion as based on the module's documented commission-request pattern rather than a direct line read; however, the core defect is confirmed directly in `distribute_internal` and `update_distribution_pool`.

### Title
Operator-switch strands commission shares under the stale operator key, bypassing beneficiary redirection in `distribute_internal` - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move)

### Summary
`StakingContract.distribution_pool` is a `pool_u64::Pool` whose shareholder keys are plain addresses (staker, and whichever address was passed as `operator` when commission shares were minted). `switch_operator` moves the whole `StakingContract` (including its `distribution_pool`) from the `old_operator` key to the `new_operator` key in the `Store.staking_contracts` map, but does **not** rewrite/migrate any shares already held under the `old_operator` address inside `distribution_pool`. [1](#0-0) 

Later, any call to `distribute()`/`distribute_internal()` is parameterized with the *current* map key (`new_operator`), and the beneficiary redirection logic only fires when the pool shareholder address equals that same `operator` parameter:
```
if (recipient == operator) {
    recipient = beneficiary_for_operator(operator);
};
``` [2](#0-1) 

Since the leftover shares are held under `old_operator`, not `new_operator`, this equality check fails, and the redeemed coins are paid directly to the raw `old_operator` address instead of being routed through `old_operator`'s registered beneficiary via `beneficiary_for_operator`.

### Finding Description
`update_distribution_pool` mints/transfers pool shares using the operator address that is active *at the time of the call* as the shareholder key for commission: [3](#0-2) 

`switch_operator` calls `distribute_internal` (pays out already-inactive stake, correctly, since `operator == old_operator` at that point) and then `request_commission_internal` (which, per the module's documented flow, converts as-yet-unrequested active-stake rewards into commission shares keyed to `old_operator`) — both *before* the `StakingContract` struct is moved to the `new_operator` key in the map: [1](#0-0) 

Any commission shares created by that `request_commission_internal` call remain keyed to `old_operator` inside `distribution_pool` because `switch_operator` only calls `stake::set_operator_with_cap` and updates `commission_percentage`/the map key — it never touches or migrates `distribution_pool`'s existing shareholder entries.

When the stake later becomes inactive and someone calls `distribute(staker, new_operator)`, `distribute_internal` is invoked with `operator = new_operator`. Iterating `distribution_pool.shareholders()`, it will encounter the `old_operator` address as a shareholder with a nonzero balance. Because `recipient (old_operator) != operator (new_operator)`, the beneficiary-redirect branch is skipped, and `aptos_account::deposit_coins` sends the commission straight to `old_operator`'s account rather than to whatever beneficiary `old_operator` had configured via `set_beneficiary_for_operator`: [4](#0-3) [2](#0-1) 

This is structurally the same class of bug as HAL-09: an accounting structure (`distribution_pool`, keyed by address) becomes desynchronized from the "current" identity tracked elsewhere (`Store.staking_contracts` map key / the `operator` parameter), and code that only checks equality against the "current" identity silently misroutes value that belongs to the stale identity's delegate (`beneficiary_for_operator`).

### Impact Explanation
Commission payouts intended for an operator's registered beneficiary are instead paid to the raw (possibly now-inactive or compromised) `old_operator` address after any `switch_operator` call. This satisfies the "Operator commission, beneficiary payout ... corruption that credits the wrong account" impact category — funds are diverted from the address the operator explicitly designated to receive them.

### Likelihood Explanation
`switch_operator` is a normal, unprivileged staker-facing entry function; no special role beyond being the staker of an existing staking contract is required. The scenario requires only: (1) `old_operator` sets a beneficiary, (2) some commission accrues on active stake but is not fully requested/distributed before the staker calls `switch_operator`, and (3) a subsequent `distribute` call after stake becomes inactive. All of these are ordinary usage patterns, not adversarial edge cases, making this readily triggerable.

### Recommendation
On `switch_operator`, before moving the `StakingContract` to the new map key, fully settle and pay out (or explicitly re-key) any shares in `distribution_pool` still attributed to `old_operator`, so no shareholder entries under a stale operator address persist. Alternatively, change the beneficiary check in `distribute_internal` to resolve `beneficiary_for_operator` for the shareholder's own address whenever that shareholder is (or was) an operator, rather than only when it equals the currently-passed `operator` parameter.

### Proof of Concept
1. Staker creates a staking contract with `operator1`, commission 10%.
2. `operator1` calls `set_beneficiary_for_operator(operator1, beneficiary1)`.
3. Stake pool earns active rewards for some epochs (commission accrues but is not requested/distributed).
4. Staker calls `switch_operator(staker, operator1, operator2, new_commission)`. Internally: `distribute_internal` pays out any already-inactive funds correctly to `beneficiary1` (operator param = `operator1` at this point); `request_commission_internal` mints new distribution-pool shares for the just-accrued active-stake commission keyed to `operator1`; the `StakingContract` (with its `distribution_pool` still containing the `operator1`-keyed shares) is then moved to key `operator2`.
5. Stake pool later becomes inactive (lockup expires) and anyone calls `distribute(staker, operator2)`.
6. Inside `distribute_internal(operator = operator2)`, the loop redeems the `operator1`-keyed shares and, since `operator1 != operator2`, pays the coins directly to `operator1`'s account instead of `beneficiary1`.

Note: I could not directly re-read the body of `request_commission_internal`/`request_commission` in this session (tool budget exhausted), so step 3–4's exact share-minting mechanics are inferred from the module's documented commission-request pattern and from the confirmed behavior of `update_distribution_pool`/`distribute_internal`. Direct code confirmation of `request_commission_internal`'s body is recommended before treating this as fully proven.

    fun update_distribution_pool(
        distribution_pool: &mut Pool,
        updated_total_coins: u64,
        operator: address,
        commission_percentage: u64
    ) {
        // Short-circuit and do nothing if the pool's total value has not changed.
        if (distribution_pool.total_coins() == updated_total_coins) { return };

        // Charge all stakeholders (except for the operator themselves) commission on any rewards earnt relatively to the
        // previous value of the distribution pool.
        let shareholders = &distribution_pool.shareholders();
        shareholders.for_each_ref(
            |shareholder| {
                let shareholder: address = *shareholder;
                if (shareholder != operator) {
                    let shares = pool_u64::shares(distribution_pool, shareholder);
                    let previous_worth = pool_u64::balance(distribution_pool, shareholder);
                    let current_worth =
                        pool_u64::shares_to_amount_with_total_coins(
                            distribution_pool, shares, updated_total_coins
                        );
                    let unpaid_commission =
                        (current_worth - previous_worth) * commission_percentage / 100;
                    // Transfer shares from current shareholder to the operator as payment.
                    // The value of the shares should use the updated pool's total value.
                    let shares_to_transfer =
                        pool_u64::amount_to_shares_with_total_coins(
                            distribution_pool, unpaid_commission, updated_total_coins
                        );
                    pool_u64::transfer_shares(
                        distribution_pool, shareholder, operator, shares_to_transfer
                    );
                };
            }
        );

        distribution_pool.update_total_coins(updated_total_coins);
    }
