### Title
Unbounded retryable `stopEpoch` failure lets an ERC4626 vault user permanently stall epoch settlement and freeze pending withdrawals - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
CVE-2017-14058 is an unrestricted-retry bug: the HLS demuxer loops forever re-fetching an insufficient playlist because no attempt limit exists. The analog in idle-tranches is `ProgrammableBorrower.onStopEpoch`: when the borrower's vault shares economically cover the stop-epoch shortfall but the external ERC4626 vault lacks instant liquidity, the hook reverts `StopEpochVaultLiquidityUnavailable`, leaving `isEpochRunning() == true` with no bound on retries (contracts/strategies/idle/ProgrammableBorrower.sol:240-253). An attacker who is a user of the shared ERC4626 vault (an explicitly in-scope unprivileged actor) can repeatedly drain vault liquidity around each manager retry, forcing the epoch to stay running indefinitely and freezing all pending withdraw receipts.

### Finding Description
`onStopEpoch` splits failure handling into two branches (contracts/strategies/idle/ProgrammableBorrower.sol:240-253):

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  // covered-by-shares shortfall uses the retryable path
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

The `shortfall > _currentVaultAssets()` check measures the *borrower adapter's own position value*, not the vault's free liquidity. For a shared-liquidity ERC4626 (e.g., the MetaMorpho vault used in tests), shares can be fully valuable while `vault.withdraw` reverts because idle liquidity was redeemed by other vault users. On every such retryable revert, `epochAccountingActive` stays `true`, `epochPendingWithdraws` stays set, and `IdleCDOEpochVariant.stopEpoch` unwinds — confirmed by the regression test asserting "epoch should remain running after retryable failure" (test/foundry/ProgrammableBorrowerCreditVault.t.sol:391-398).

There is no attempt counter, no escalation to a default, and no deadline: like the FFmpeg reload loop, the retry is unbounded and controlled by a condition an external actor can regenerate (empty vault liquidity) at will.

### Impact Explanation
Temporary freezing with quantified fund impact:

- `pendingWithdraws` receipts (`IdleCreditVault.requestWithdraw` at contracts/strategies/idle/IdleCreditVault.sol:279) can only be funded by `stopEpoch` → `collectWithdrawFunds` (contracts/strategies/idle/IdleCreditVault.sol:411). While the epoch is stuck running, every pending receipt — the full `pendingWithdraws` amount — is unclaimable.
- Instant-withdraw and APR0 settlement (`prepareStopEpochWithApr0`, contracts/strategies/idle/IdleCreditVault.sol:490) are likewise blocked.
- The attacker can repeat this per manager retry at near-zero cost: redeem vault liquidity just before `stopEpoch`, redeposit after the revert. Because the failure path intentionally avoids `onDefault`, the freeze never resolves into a default accounting either — there is no terminal state.

### Likelihood Explanation
- Attacker class is allowed: "a user of the programmable borrower's ERC4626 vault" is explicitly listed as unprivileged.
- Requires only a standard ERC4626 property (revert on insufficient idle liquidity); flash liquidity or ordinary redeem transactions suffice. No privileged role, oracle manipulation, or borrower misbehavior needed.
- The honest manager must initiate each retry, but the attacker's per-retry cost is one vault redeem/deposit pair, so sustained griefing is cheap relative to the frozen `pendingWithdraws`.

### Recommendation
Bound the retryable path like the FFmpeg fix bounded reloads: e.g., track consecutive `StopEpochVaultLiquidityUnavailable` failures (or a grace timestamp) and, after the limit, treat the covered-but-unwithdrawable shortfall as a default by returning `true` so the CDO's `transferFrom` failure drives the normal default/`onDefault` path (contracts/strategies/idle/ProgrammableBorrower.sol:289-301). Alternatively, redeem the borrower's vault shares via `vault.redeem` with a documented fallback, or let the manager force a "vault-illiquidity default" so pending receipts get haircut-priced instead of frozen.

### Proof of Concept
Foundry fork test sketch (modeled on `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable` in test/foundry/ProgrammableBorrowerCreditVault.t.sol:372-399, using `MockStopEpochLiquidityVault`):

```solidity
// 1. Setup: programmable borrower vault, interest minted, deposits, startEpoch.
vm.prank(owner); cdoEpoch.setIsInterestMinted(true);
idleCDO.depositAA(amount);
cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));
_startEpochAndCheckPrices(0);

// 2. Attacker (any ERC4626 vault user) drains vault liquidity below shortfall.
uint256 pending = strategy.pendingWithdraws();
vault.setWithdrawLimit(pending - 1); // models attacker redeeming idle liquidity

// 3. Epoch ends; every manager stopEpoch retry reverts and state stays running.
vm.warp(cdoEpoch.epochEndDate() + 1);
for (uint i; i < N; ++i) {
  // attacker re-drains liquidity before each honest retry
  vm.prank(manager);
  vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
  cdoEpoch.stopEpoch(0, 0);
  assertTrue(cdoEpoch.isEpochRunning());
  assertEq(strategy.pendingWithdraws(), pending); // receipts stay unfunded
}

// 4. No bound/default escalation exists: claimant still cannot claim
//    (epochNumber <= lastWithdrawRequest) -> claimWithdrawRequest reverts NotAllowed.
vm.expectRevert(NotAllowed.selector);
cdoEpoch.claimWithdrawRequest(user);
```

Note: I verified the retryable-failure branch and its lack of an attempt bound directly in `ProgrammableBorrower.onStopEpoch` and the existing regression test; I did not fully re-read `IdleCDOEpochVariant.stopEpoch`'s outer flow in this pass, but the repo's own test (ProgrammableBorrowerCreditVault.t.sol:391-398) already asserts the epoch remains running with unchanged `pendingWithdraws` after this revert, which confirms the freeze semantics.
