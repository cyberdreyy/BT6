### Title
Stale confirmations from removed multisig members are counted toward the approval threshold, allowing requests to execute below the configured quorum - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges outstanding requests and confirmations for the request that the removed member *itself originated*, but does not scan and strip the removed member's confirmations from *other* outstanding requests that were originated by different members. Because `confirm()` counts entries in the raw `confirmations: HashSet<String>` without verifying every entry is still a current member of `self.members`, a request can execute even though the number of *live* members who actually approved it is below `num_confirmations`.

### Finding Description
The custody/authorization binding a K-of-N multisig is supposed to enforce is:
`confirmations counted in confirm() == confirmations from accounts that are current members`

`confirm()` blindly trusts the size of the stored `HashSet<String>`: [1](#0-0) 

```
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let member = self.current_member().unwrap_or_else(...);
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    ...
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else {
        confirmations.insert(member.to_string());
        ...
    }
}
```
`assert_valid_request` only checks that the *caller confirming right now* is a current member; it never re-validates the membership of accounts whose confirmations were recorded earlier.

`delete_member` only cleans up requests where `r.member == member` (i.e., requests the removed member originated), and leaves the `confirmations` map for every other outstanding request untouched: [2](#0-1) 

```
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    assert(self.members.len() - 1 >= self.num_confirmations as u64, ...);
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self.requests.iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&member.to_string());
    self.members.remove(&member);
    ...
}
```
Only requests *added by* the removed member are pruned; confirmations that removed member gave on requests added by *other* members are never removed from the `confirmations: LookupMap<RequestId, HashSet<String>>` entries for those requests.

Equality broken: `live_signers(request) == confirmations_used_in_threshold_check(request)` no longer holds once a confirming member is removed while their confirmation on someone else's still-open request remains in storage.

### Impact Explanation
This is a Critical-class issue per the accepted impact list ("a multisig request executed below threshold"). A `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc. request can execute with fewer *live* member approvals than `num_confirmations` requires, because a stale confirmation from a departed member is silently counted. This directly undermines the K-of-N custody guarantee the multisig exists to enforce, potentially allowing funds to move, code to be deployed, or keys to be added with less real consensus than configured.

### Likelihood Explanation
This requires no attacker collusion beyond normal contract usage/member churn:
1. Member churn (adding/removing members via `DeleteMember`) is an expected, routine multisig operation supported natively by the contract.
2. Any request left pending (unconfirmed to completion) at the time a confirming member is removed will retain that member's stale confirmation.
3. The remaining members do not need to be aware of this residual confirmation; the contract itself silently counts it, so the shortfall in real consensus is not visible via `get_confirmations` review discipline alone (a reviewer would see the departed member's identifier still listed, but the bug is that the system uses it to reach quorum regardless).

Because member removal, and requests remaining open across a member-list change, are ordinary occurrences (not requiring privileged escalation or unusual conditions), likelihood is realistic in any long-lived multisig deployment.

### Recommendation
In `confirm()`, filter `confirmations` to accounts still present in `self.members` before comparing against `num_confirmations` (i.e., recompute live confirmation count each time, or when calling `delete_member`, additionally scrub the removed member's identifier from every entry in the `confirmations` map, not just requests it originated). Equivalent to using a live/spot value instead of stale cached data, the check should be:
```rust
let live_count = confirmations.iter().filter(|m| self.members.contains(...)).count();
```
or eagerly purge `member.to_string()` from all `confirmations` value sets inside `delete_member`.

### Proof of Concept
Given `num_confirmations = 3`, members `{A, B, C, D}`:

1. `A` calls `add_request` creating request `X` (e.g., a large `Transfer`). `confirmations[X] = {}`.
2. `B` calls `confirm(X)` → `confirmations[X] = {B}` (len 1 < 3, not executed).
3. Separately, and unrelated to `X`, the group executes a `DeleteMember { member: B }` request (approved through normal threshold, e.g., via a different fully-confirmed request `Y`). `delete_member` runs; since `X.member == A != B`, `X` is left untouched, and `confirmations[X]` still equals `{B}` even though `B` is no longer in `self.members`.
4. `C` calls `confirm(X)` → `confirmations.len()+1 = 2 < 3` → inserted, `confirmations[X] = {B, C}`.
5. `D` calls `confirm(X)` → `confirmations.len()+1 = 3 >= 3` → `execute_request(X)` fires.

Result: request `X` executes as "3 confirmations", but only `C` and `D` are current, live multisig members who approved it (B's approval is stale/void). The transfer/action is authorized with fewer live signers than the configured `num_confirmations`, breaking the multisig's core custody guarantee.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
