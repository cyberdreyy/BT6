### Title
Attacker-controlled ERC4626 vault liquidity freezes `stopEpoch` and all LP withdrawals via `StopEpochVaultLiquidityUnavailable` - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStopEpoch` unconditionally reverts when the configured ERC4626 vault cannot honour a liquidity withdrawal, and `IdleCDOEpochVariant._stopEpoch` lets hook reverts bubble up. Any user of the borrower's ERC4626 vault can keep the vault fully drained of liquidity so that every `stopEpoch` call reverts, indefinitely freezing epoch settlement and every LP withdrawal path gated on it — a direct analog of CVE-2020-13977's pattern where a trusted configured endpoint (JSON CGI URL / ERC4626 `vault`) becomes attacker-influenced input that hijacks a privileged flow's success condition.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch` the programmable-borrower hook is invoked and reverts propagate:

- `contracts/IdleCDOEpochVariant.sol:398` — `IProgrammableBorrower(_borrower()).onStopEpoch(...)` return value decides default vs success; a revert aborts the entire stop.

Inside `ProgrammableBorrower.onStopEpoch` (`contracts/strategies/idle/ProgrammableBorrower.sol:231-253`):

```solidity
if (shortfall > _currentVaultAssets()) return true;
try vault.withdraw(shortfall, address(this), address(this)) { ... }
catch { revert StopEpochVaultLiquidityUnavailable(); }
```

`vault` is an immutable ERC4626 set at `initialize` — the trusted external "endpoint", exactly like Nagios' admin-set "URL for JSON CGIs". The contract's stop flow executes whatever the vault's liquidity state dictates:

- If vault shares economically cover the shortfall (`shortfall <= _currentVaultAssets()`), a withdraw revert hits the `catch` and reverts `StopEpochVaultLiquidityUnavailable`. The revert bubbles out of `stopEpoch`, so `isEpochRunning` stays true, `pendingWithdraws` stay unfunded, `epochNumber` never increments, and:
  - `claimWithdrawRequest` reverts (`epochNumber <= lastWithdrawRequest[_user]`, `IdleCreditVault.sol:326`).
  - `claimInstantWithdrawRequest` and `startEpoch` are unreachable.
  - No alternative liquidity path exists; there is no owner bypass — even `emergencyRedeemVault` in `ProgrammableBorrower` (`:360`) hits the same vault liquidity wall.

An attacker who is a normal user of the ERC4626 vault (e.g., a borrower on the underlying Morpho-style market the vault lends into) keeps utilization at ~100% across each `stopEpoch` window. The withdraw revert then permanently blocks settlement for as long as liquidity stays exhausted. The attacker's only cost is ordinary borrow interest on the third-party market; they need no role in idle-tranches.

### Impact Explanation
Temporary freezing of the entire pool NAV: all tranche holders' principal plus accrued interest are locked inside the running epoch with no withdrawal path while the vault lacks liquidity. For a vault holding e.g. $10M of LP deposits, the full $10M is frozen per stalled `stopEpoch` window, including funded `pendingWithdraws` that were supposed to be collected via `collectWithdrawFunds` at `IdleCDOEpochVariant.sol:410`.

### Likelihood Explanation
Requirements are modest: the pool must be in `isProgrammableBorrower` mode (the documented Morpho-vault integration in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`), and the attacker must be able to borrow/redeem the vault's free liquidity — a standard action for any vault user, explicitly one of the in-scope attacker classes. Morpho-style markets routinely hit high utilization; an attacker can also just re-borrow liquidity as it returns, sustaining the freeze across blocks, since `stopEpoch` is retryable but never exempts the vault withdraw.

### Recommendation
Make the liquidity failure non-blocking instead of aborting the whole stop:

- On vault withdraw failure, degrade gracefully: pull whatever is `onHand`, reserve the remaining shortfall, and proceed with accounting; or return `false` into the existing `_handleBorrowerDefault` path rather than reverting, so settlement converges to an explicit default instead of an unbounded freeze.
- Alternatively bound retries: after N failed `stopEpoch` attempts (or a grace deadline), allow manager to force the default path.
- Add a keeper-facing view exposing vault liquidity vs `shortfall` so operators can distinguish "insolvent" from "illiquid" before each call.

### Proof of Concept
Reproducible Foundry fork PoC (scaffolding mirrors `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
function testVaultLiquidityExhaustionFreezesStopEpoch() external {
    uint256 amount = 10_000 * oneScale;
    vm.prank(owner); cdoEpoch.setIsInterestMinted(true);
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);

    // attacker: an ordinary user of the vault's underlying market
    // borrows / redeems all free liquidity in the ERC4626 vault
    address attacker = makeAddr("vaultUser");
    _drainVaultLiquidity(attacker); // e.g. max borrow on Morpho market
    assertEq(IERC20(underlying).balanceOf(vaultAddress), 0);

    // LP requests withdrawal during the epoch -> pendingWithdraws > 0
    uint256 tr = AAtranche.balanceOf(address(this));
    cdoEpoch.requestWithdraw(tr / 2, address(AAtranche));

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // every stopEpoch reverts: shortfall <= share value but vault is illiquid
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // retrying later still reverts while attacker keeps liquidity drained
    vm.warp(block.timestamp + 1 days);
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // all withdrawal paths stay frozen: epoch never rolls
    assertTrue(cdoEpoch.isEpochRunning());
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();
}
```
