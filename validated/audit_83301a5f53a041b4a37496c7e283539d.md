### Title
Stale pre-commit weight from a signer that has since rejected a block still counts toward the 70% signing threshold - (File: `stacks-signer/src/signerdb.rs`, `stacks-signer/src/v0/signer.rs`)

### Summary
The pre-commit weight tally that gates block signing never removes a signer's earlier "I am willing to sign" (pre-commit) record when that same signer later rejects the block. This mirrors the reported bug class: an accounting table (lender shares / here, pre-committer weights) is not corrected when the underlying membership/intent changes, so a stale contribution keeps being counted toward a threshold decision it should no longer support.

### Finding Description
`add_block_pre_commit` unconditionally records a signer's pre-commit with `INSERT OR REPLACE` and has no linkage to that signer's later rejection state: [1](#0-0) 

Contrast this with the acceptance/rejection pair, which *does* maintain mutual exclusivity: adding a signature deletes any existing rejection row for that signer/block, and adding a rejection is refused outright if a signature already exists: [2](#0-1) [3](#0-2) 

No equivalent check exists between `block_pre_commits` and `block_rejection_signer_addrs`. When a signer that previously pre-committed to block B later determines B should be rejected — e.g. via `handle_block_validate_reject` (a fresh validation reject) or via the chainstate re-check inside `handle_block_pre_commit` itself (`check_block_against_signer_db_state` fails, leading to `mark_locally_rejected` + broadcast of `BlockResponse::Rejected`) — the earlier `block_pre_commits` row for that signer/block is never deleted: [4](#0-3) [5](#0-4) 

Meanwhile, every peer signer computes its own pre-commit consensus by summing weights of *all* addresses ever recorded in `get_block_pre_committers`, with no filter for signers who have since rejected: [6](#0-5) 

So a signer's weight, once pre-committed, keeps counting toward the 70% signing threshold on every peer that already recorded it, even after that signer has publicly and locally withdrawn support by rejecting the block. This breaks the equality the protocol is designed to guarantee — "the block is signable only once ≥70% of weight is *currently* willing to sign it" — by letting withdrawn (rejected) weight silently continue to be recounted as pre-commit ("about to accept") weight.

### Impact Explanation
This falls into the "rejection recounted as an accept" impact category. If enough real pre-commit weight plus one stale, since-withdrawn pre-commit pushes `commit_weight` past `min_weight` in `handle_block_pre_commit`, remaining signers proceed past the threshold gate to the chainstate recheck and, if that recheck still passes on their local view, sign the block (`mark_locally_accepted`, broadcast acceptance). This can produce a group signature over a block for which real (weighted) live consensus does not exist, because one signer's weight was double-purposed: it is stale intent from a state that no longer holds, yet it is treated identically to fresh, current willingness to sign.

### Likelihood Explanation
This requires only a single signer to change its mind (pre-commit, then later locally reject the same block due to a subsequently-discovered conflict, reorg, or validation issue) — a routine occurrence under normal asynchronous network conditions, forks, or re-proposals, not an attacker needing a majority of signers or any other signer's key. Both a natural race (validation-then-reorg) and a targeted miner/attacker-crafted proposal that predictably causes exactly one signer to flip after pre-committing (e.g. by controlling timing of a competing tenure-start proposal that only that signer observes as conflicting) can trigger it.

### Recommendation
Enforce mutual exclusivity between `block_pre_commits` and rejection state, symmetric to how signatures and rejections are already kept exclusive: when `mark_locally_rejected` is applied for a block (in `handle_block_validate_reject`, in the pre-commit re-check path, or in `handle_block_validate_ok`'s state-mismatch branch), delete that signer's row from `block_pre_commits`, and have every consumer of `get_block_pre_committers` (i.e. `handle_block_pre_commit`'s weight tally) treat committers who have a recorded rejection for the same block as excluded from the pre-commit weight sum.

### Proof of Concept
1. Miner proposes block B (height h). Signer S (weight w) validates B OK, calls `mark_pre_committed`, and broadcasts a `BlockPreCommit`; every peer signer stores `add_block_pre_commit(B, S)`.
2. Before B reaches the 70% pre-commit threshold anywhere, S's own state changes (e.g. S observes/validates a conflicting tenure-start block at the same height, or a new proposal for B fails `check_block_against_signer_db_state`). S transitions B to `LocallyRejected` via `mark_locally_rejected` and broadcasts `BlockResponse::Rejected(B)` — see `stacks-signer/src/v0/signer.rs:1340-1366` and `1987-2024`.
3. S's earlier pre-commit row for B, already replicated to every peer's `block_pre_commits` table via `add_block_pre_commit`, is never deleted (`stacks-signer/src/signerdb.rs:2441-2456`); nothing in `add_block_rejection_signer_addr` (`1922-1985`) touches that table.
4. Other signers, still receiving/replaying S's stale pre-commit (e.g. via `process_pending_responses_for_block` or a direct prior receipt) plus their own and other genuine pre-commits, compute `commit_weight = compute_signature_signing_weight(get_block_pre_committers(B))` in `handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs:1290-1338`) and find it ≥ `min_weight`, even though S has withdrawn. They proceed to sign B if their local chainstate recheck still passes.
5. Result: B collects and broadcasts a threshold-reaching signature set that included S's already-withdrawn weight as if it were current willingness, i.e. a rejection recounted toward acceptance.

        // Remove any block rejection entry for this signer and block hash

        let del_args = params![block_sighash, signer_addr.to_string()];

        let qry = "INSERT OR IGNORE INTO block_signatures (signer_signature_hash, signer_addr, signature) VALUES (?1, ?2, ?3);";
        let args = params![
            block_sighash,
            signer_addr.to_string(),
            serde_json::to_string(signature).map_err(DBError::SerializationError)?
        ];
        let rows_added = self.db.execute(qry, args)?;

        let is_new_signature = rows_added > 0;
        if is_new_signature {
            debug!("Added block signature.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %signer_addr,
                "signature" => %signature
            );
        } else {
            debug!("Duplicate block signature.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %signer_addr,
                "signature" => %signature
            );
        }
        Ok(is_new_signature)
    }

    fn handle_block_validate_reject(
        &mut self,
        block_validate_reject: &BlockValidateReject,
        sortition_state: &mut Option<SortitionsView>,
    ) {
        crate::monitoring::actions::increment_block_validation_responses(false);
        let signer_signature_hash = &block_validate_reject.signer_signature_hash;
        if self
            .submitted_block_proposal
            .as_ref()
            .map(|(proposal_hash, _)| proposal_hash == signer_signature_hash)
            .unwrap_or(false)
        {
            self.submitted_block_proposal = None;
        }
        let Some(mut block_info) = self.block_lookup_by_reward_cycle(signer_signature_hash) else {
            // We have not seen this block before. Why are we getting a response for it?
            debug!("{self}: Received a block validate response for a block we are not tracking. Ignoring...");
            return;
        };
        if block_info.valid.is_some() {
            // We should only have valid set if we have already processed a validation response for this block OR we locally marked it as rejected.
            // and responded to it. If we received a new proposal for it, we would have reset valid to None.
            warn!(
                "{self}: Already processed a block validate response for block {}. Ignoring validation response.", block_info.block.header.signer_signature_hash(); "valid" => ?block_info.valid,
            );
            return;
        }
        if !block_info.check_static_valid_block() {
            debug!("{self}: Block is syntatically invalid; will not store");
            return;
        }
        if let Err(e) = block_info.mark_locally_rejected() {
            if !block_info.has_reached_consensus() {
                warn!("{self}: Failed to mark block as locally rejected: {e:?}");
