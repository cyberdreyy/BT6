### Title
Claimed instant-withdraw receipts leave dangling per-epoch records that inflate the default-recovery basis and strand recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2023-1393 is a use-after-free: a window object is explicitly destroyed while the parent `CompScreen` keeps a dangling pointer that is later dereferenced. The analog in `IdleCreditVault` is the instant-withdraw receipt ledger: `claimInstantWithdrawRequest` "destroys" a receipt by clearing only the aggregate `instantWithdrawsRequests[_user]`, while the per-epoch pointers `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are never cleared. A later `finalizeDefaultRecovery` dereferences those dangling per-epoch records via `defaultPendingClaimBasis()`, double-counting already-paid receipts in the recovery basis.

### Finding Description
`requestInstantWithdraw` records receipts in three places: the aggregate `instantWithdrawsRequests[_user]`, the per-user per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the global per-epoch `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

The normal claim path clears only the aggregate:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [2](#0-1) 

`instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` remain populated after the receipt is fully paid — the dangling pointers. They are only ever decremented inside `_claimDefaultedInstantWithdrawRequest`, which runs after a default is finalized [3](#0-2) .

At default finalization, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the haircut basis whenever `pendingInstantWithdraws != 0` [4](#0-3) . Requests made in the buffer of epoch N and claimed during epoch N are both recorded under `epochNumber == N`, so a receipt that was already paid at par is still counted in `instantWithdrawClaimsByEpoch[N]` when the borrower defaults at the end of epoch N (e.g. `getInstantWithdrawFunds` fails because a *second* instant request in the same epoch stayed unfunded). `finalizeDefaultRecovery` then computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` with a `totalBasis` inflated by the ghost receipts [5](#0-4) .

Two concrete consequences:

1. **Diluted recovery price / stranded reserve.** Every defaulted-epoch claimant (normal withdrawers, APR0 redeemers, active LPs via `defaultBBNav`) is paid `basis * recoveryPrice`, so the ghost basis transfers value away from real claimants. The share of `defaultRecoveryReserve` attributable to already-claimed receipts is never claimable — `_transferDefaultRecovery` is only reachable through receipt claims — so it is permanently locked in the strategy.
2. **Permanent freeze of a legitimate same-epoch receipt.** A user who claimed instant receipt A in epoch N and still holds unclaimed receipt B from the same epoch triggers `_claimDefaultedInstantWithdrawRequest`, which computes `claimBasis = A + B` from the stale record and then executes `instantWithdrawsRequests[_user] -= claimBasis` where `instantWithdrawsRequests[_user] == B`. The subtraction underflows and the whole `claimInstantWithdrawRequest` reverts forever — receipt B (and the corresponding haircut payout from the reserve) is permanently frozen [6](#0-5) .

### Impact Explanation
Direct, quantifiable loss for unprivileged victims with no privileged attacker: an honest lender who requested and claimed an instant withdrawal in the default epoch is enough to (a) reduce `defaultRecoveryPrice` for every other claimant by `staleBasis / totalBasis`, permanently stranding that fraction of the recovery reserve in the strategy, and (b) permanently freeze any second same-epoch instant receipt they hold. Loss scales with the size of claimed instant receipts relative to total default basis; with one claimed instant receipt equal to the remaining pending basis, roughly half of the reserved recovery for pending claimants is stranded.

### Likelihood Explanation
Requires the confluence of: instant withdrawals enabled and APR dropping (`lastEpochApr > currentApr + instantWithdrawAprDelta`), a user requesting and fully claiming an instant receipt during epoch N, a second instant request in epoch N left partially unfunded so `pendingInstantWithdraws != 0`, and the borrower then defaulting in that same epoch (`getInstantWithdrawFunds` try/catch → `_handleBorrowerDefault`). This is an ordinary operating path — the test suite already exercises funded-then-default instant sequences — and needs no malicious action, only normal user behavior plus a default.

### Recommendation
Keep the per-epoch records consistent with the aggregate. Either track a per-epoch funded cursor and clear `instantWithdrawsRequestsByEpoch[_user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]` when receipts are claimed in `claimInstantWithdrawRequest`, or have `defaultPendingClaimBasis` derive the default-epoch instant basis from still-outstanding receipts (e.g. cap `instantWithdrawClaimsByEpoch[epochNumber]` at the sum of live `instantWithdrawsRequests`) so destroyed receipts can never be dereferenced during finalization.

### Proof of Concept
Foundry fork PoC sketch against `IdleCreditVault.t.sol` harness (standard epoch variant, USDC fork):

```solidity
function testStaleInstantRecordInflatesDefaultBasis() external {
    // 1. Setup: deposits, epoch 0 runs, stopEpoch lowers APR so instant path enabled.
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // 2. User requests instant withdraw (receipt A), recorded under epochNumber == 1.
    uint256 receiptA = cdoEpoch.requestWithdraw(aaAmount / 2, address(AAtranche));
    _startEpochAndCheckPrices(1);           // startEpoch prefunds receiptA fully
    cdoEpoch.claimInstantWithdrawRequest(); // receiptA paid at par
    // DANGLING: instantWithdrawsRequestsByEpoch[user][1] and
    // instantWithdrawClaimsByEpoch[1] still contain receiptA.
    assertEq(
        IdleCreditVault(address(strategy)).instantWithdrawsRequestsByEpoch(address(this), 1),
        receiptA
    );

    // 3. Second instant request (receipt B) in same epoch, left unfunded.
    _stopEpochAndCheckPrices(1, initialProvidedApr / 4, _expectedFundsEndEpoch());
    // ... request again under epochNumber that will equal the default epoch,
    // warp past instantWithdrawDeadline, borrower unfunded:
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();     // -> _handleBorrowerDefault
    // pendingInstantWithdraws != 0 so basis += instantWithdrawClaimsByEpoch[epochNumber]
    // which still includes the already-claimed receiptA.

    // 4. finalizeDefault: recoveryPrice = reserve / (realBasis + receiptA)
    //    => all claimants underpaid; receiptA's share of reserve is stranded.
    // 5. If the same user also holds receipt B in the default epoch,
    //    claimInstantWithdrawRequest() reverts on underflow at
    //    `instantWithdrawsRequests[_user] -= claimBasis`.
}
```

The key assertion is step 2's dangling record: `instantWithdrawsRequestsByEpoch[user][epoch]` remains non-zero after the receipt is claimed, and `defaultPendingClaimBasis()` at `IdleCreditVault.sol:644-649` dereferences it during `finalizeDefaultRecovery`.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
