### Title
Post-default instant withdraw requests bypass the recovery haircut and drain `defaultRecoveryReserve` at par — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The ksmbd bug is a missing lock around a shared list: a lookup (`xa_load`) and a delete (`xa_erase`) race, letting one consumer operate on stale/freed entry state while another mutates it — a classic **read-check-vs-clear desync** on shared accounting. The direct analog in `IdleCreditVault` is `requestInstantWithdraw`: its sibling `requestWithdraw` was patched to detect the post-default state and route new receipts through a haircut-preserving path (`postDefaultRequests`), but `requestInstantWithdraw` still mutates the shared per-epoch receipt lists (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, `pendingInstantWithdraws`) with **no `defaultRecoveryFinalized` branch at all**. After finalization a new instant receipt is written into the *same* epoch bucket (`epochNumber` no longer advances after default) that the default-recovery machinery treats as already-finalized, and it is then paid at par through `_transferFundedClaim` while the reserve that backs defaulted claimants is silently drained — one underlying, two accounting views.

### Finding Description
After `finalizeDefaultRecovery` executes, `defaultRecoveryFinalized = true`, `defaultRecoveryPrice = recoveryPrice < 1e18`, and `defaultRecoveryEpoch = epochNumber`. From that point the epoch counter is frozen (a defaulted pool never calls `stopEpoch`/`deposit`-with-epoch-running again, so `epochNumber` stays equal to `defaultRecoveryEpoch`).

The normal-withdraw path was explicitly hardened for this state — `requestWithdraw` routes post-default requests into `postDefaultRequests` and pays them from the reserve only after the haircut embedded in the lowered `virtualPrice` [1](#0-0) . `requestInstantWithdraw` has no equivalent branch: it burns CDO strategy tokens, mints a receipt to the user, and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `pendingInstantWithdraws` exactly as in the pre-default flow [2](#0-1) .

On claim, `claimInstantWithdrawRequest` only applies the recovery haircut when `defaultInstantWithdrawsFinalized` is set — a flag captured once at finalization from the *then-current* `pendingInstantWithdraws` [3](#0-2) [4](#0-3) . Two desync cases follow:

1. **`defaultInstantWithdrawsFinalized == false`** (all instant claims were funded at finalization, so `pendingInstantWithdraws == 0`): a post-finalization instant request flips `pendingInstantWithdraws` back to non-zero, but the flag is never recomputed. `_claimDefaultedInstantWithdrawRequest` is skipped and the new receipt is paid **at par** via `_transferFundedClaim` [5](#0-4)  — from the same underlying balance that `defaultRecoveryReserve` is supposed to exclusively back. The reserve bookkeeping is not decremented by `_transferFundedClaim`, so each par payout makes `defaultRecoveryReserve` overstate its backing and later defaulted-epoch claimants (normal receipts in `_claimDefaultedWithdrawRequest`, instant receipts in `_claimDefaultedInstantWithdrawRequest`) underpay or revert.

2. **`defaultInstantWithdrawsFinalized == true`**: the new receipt is folded into `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` and `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` — counters the recovery math treated as final. `_claimDefaultedInstantWithdrawRequest` then decrements `instantWithdrawClaimsByEpoch[defaultEpoch]` and `pendingInstantWithdraws` against a basis that was never included in `totalBasis` when `recoveryPrice` was computed [6](#0-5) , corrupting the pro-rata split for every other defaulted claimant.

### Impact Explanation
An unprivileged tranche holder can buy defaulted tranche tokens at their post-default market price (≈ `recoveryPrice` per unit), call `requestInstantWithdraw`, and claim underlying **at par**, extracting `(1 − recoveryPrice) × amount` of value per request directly out of the recovery reserve. This is direct theft from defaulted-epoch receipt holders: the reserve was sized exactly to pay all finalized claims at `defaultRecoveryPrice`, so every par payout leaves an equal shortfall — the last claimants' `_transferDefaultRecovery` calls revert (permanent freezing/theft of their unclaimed recovery). The loss is quantified as the full attacker request size up to the un-claimed reserve balance.

### Likelihood Explanation
Requires the pool to be in `defaulted` + `defaultRecoveryFinalized` state and instant withdrawals to be reachable at the CDO entry point post-default (`requestInstantWithdraw` is `onlyIdleCDO`, so CDO-side gating on `defaulted()`/`isEpochRunning()` determines reachability; the strategy itself performs no such check, unlike `requestWithdraw` which explicitly handles the finalized state — the asymmetry is the bug). No privileged or malicious actor is needed; any tranche-token holder can execute it. If the CDO blocks instant requests after default, the finding reduces to accounting corruption in case 2 whenever the entry point is reachable.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, either revert outright or route the request through a haircut-preserving path (burn/mint at the already-haircut price and record it separately, e.g. a `postDefaultInstantRequests` bucket paid from the reserve), never into `instantWithdrawsRequestsByEpoch[epochNumber]`/`pendingInstantWithdraws`. Additionally, `_transferFundedClaim` should not be able to draw down underlying earmarked by `defaultRecoveryReserve`, or the reserve should be debited for any payout that touches it.

```solidity
// 1. Deposit as attacker, run epoch, borrower defaults (stopEpoch with _expectedFundsEndEpoch == 0)
// 2. owner.finalizeDefault(recoveredAmount, source) -> recoveryPrice = r < 1e18,
//    defaultInstantWithdrawsFinalized = false (pendingInstantWithdraws == 0)
// 3. Attacker acquires tranche tokens cheaply at ~r * par
// 4. cdoEpoch.requestInstantWithdraw(trancheAmount, trancheToken)  // no default guard in strategy
//    -> strategyToken receipt minted 1:1, pendingInstantWithdraws += amount
// 5. cdoEpoch.claimInstantWithdrawRequest()
//    -> defaultInstantWithdrawsFinalized == false, so _claimDefaultedInstantWithdrawRequest skipped
//    -> amount = instantWithdrawsRequests[attacker] paid AT PAR via _transferFundedClaim
// assert: attacker received `amount` underlying for tranche tokens worth ~r*amount
// assert: defaultRecoveryReserve unchanged while strategy balance dropped by `amount`
// 6. Victim's _claimDefaultedWithdrawRequest now underpays/reverts: reserve insolvent by `amount`
```

Note on verification limits: I confirmed the missing `defaultRecoveryFinalized` guard and both desync paths directly in `IdleCreditVault.sol` (lines 356–393, 411–430, 661–710, 842–856). I was not able to fully trace `IdleCDOEpochVariant.requestInstantWithdraw`'s post-default reachability within the investigation budget; if the CDO gates instant requests on `!defaulted()`, the exploitable path narrows to the case-2 accounting corruption, but the missing guard remains a latent defect for any variant (e.g. prefunded) that forwards instant requests after finalization.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
