### Title
External Initiator credentials bypass "EIs not allowed" restriction and can trigger runs on arbitrary jobs via numeric job ID - ([File: core/web/pipeline_runs_controller.go])

### Summary
`auth.AuthenticateExternalInitiator` injects a synthetic `clsessions.User{Role: clsessions.UserRoleRun}` into the gin context for any request successfully authenticated with a valid EI access key/secret pair. `PipelineRunsController.Create` uses `auth.GetAuthenticatedUser(c)` to decide whether the caller is a "user" allowed to run jobs by integer ID, but that check also returns `true` for EI-authenticated requests because they share the same `SessionUserKey`. This defeats the code's own intent ("EIs not allowed") and lets any holder of a single EI's access key/secret trigger `RunJobV2` for any job ID on the node, not just the job the EI is bound to.

### Finding Description
`auth.AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) looks up the EI by access key via `FindExternalInitiator`, verifies the secret with `bridges.AuthenticateExternalInitiator` (which correctly uses `subtle.ConstantTimeCompare`, `core/bridges/external_initiator.go:61-67` — so the timing/replay angle in the question is not exploitable), and then unconditionally sets:
```go
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
```
This fake user object is indistinguishable, from the perspective of `auth.GetAuthenticatedUser`, from a real session/token-authenticated user.

The only `RequiresRunRole` route reachable by EI credentials is `POST /v2/jobs/:ID/runs` (`core/web/router.go:450-456`, `userOrEI` group using `AuthenticateExternalInitiator`); the other `RequiresRunRole` routes (`/replay_from_block/:number`, `/find_lca`, `/lp_skip_to_block`, `/execute_capability`) live in the separate `authv2` group that only accepts `AuthenticateByToken`/`AuthenticateBySession`, so those are NOT reachable by an EI — the "arbitrary v2 routes" framing in the question overstates the blast radius.

However, in `PipelineRunsController.Create` (`core/web/pipeline_runs_controller.go:89-128`):
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
```
`isUser` is `true` for EI-authenticated requests too (since `SessionUserKey` is always set by `AuthenticateExternalInitiator`), so the comment's intended restriction is not enforced. There is no check that the job ID belongs to the specific external initiator that authenticated the request (no lookup against `bridges.ExternalInitiator.Name`/`URL` or any job/EI binding table). As a result, an EI can supply any `int32` job ID and trigger a run for a completely unrelated job.

### Impact Explanation
An attacker holding only one external initiator's access key/secret (a credential intended to authorize runs for a single job/bridge binding) can call `POST /v2/jobs/:ID/runs` with the numeric ID of any job on the node and cause `RunJobV2` to execute it. This is an unauthorized-job-run / broken access control finding: it breaks the "requests are bound to exactly one authorized job/sender" invariant for the one route that is actually reachable by EI credentials. It does not, however, extend to the other `RequiresRunRole` routes (`ReplayFromBlock`, `FindLCA`, `LPSkipToBlock`, `ExecuteCapability`), since those require session/token auth, not EI auth.

### Likelihood Explanation
Requires only a single valid EI access key/secret pair (the minimal precondition stated in the question). No timing attack, secret guessing, or constant-time-compare weakness is needed — the exploit uses the credential exactly as intended for authentication, then leverages the missing job-binding check. Fully reproducible with a simple HTTP call once any EI credential is known/leaked/legitimately issued for one job.

### Recommendation
- Do not set a generic `clsessions.User` with `UserRoleRun` for EI-authenticated requests; instead keep EI identity distinct (e.g., a separate context key/type) so downstream handlers can differentiate EI callers from real users.
- In `PipelineRunsController.Create`, explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and, if present, validate that the target job is the one bound to that specific external initiator (e.g., via the job's webhook/EI association) before calling `RunJobV2`, rather than relying on the overloaded `isUser` boolean.

### Proof of Concept
1. Create two jobs, `job1` (ID 1) and `job2` (ID 2), and one external initiator `EI-A` (intended for `job1`).
2. Authenticate with `EI-A`'s access key/secret via headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` against `POST /v2/jobs/2/runs` (job2, not associated with `EI-A`).
3. Assert the response is `200 OK` with a `pipelineRun` resource for `job2`, and that `App.RunJobV2` was invoked with `jobID=2`.
4. Compare against expected behavior: request should be rejected with `422`/`403` because `EI-A` has no binding to `job2`.
5. Handler-level Go test: construct a `gin.Context` with `auth.AuthenticateExternalInitiator` middleware applied for `EI-A`, call `PipelineRunsController.Create` with `c.Param("ID") = "2"`, and assert `isUser` incorrectly evaluates true and `RunJobV2` is called for an unrelated job ID.
