### Title
View-role authenticated users can read a bridge's plaintext OutgoingToken via unrestricted GET /v2/bridge_types/:BridgeName - ([File: core/web/router.go])

### Summary
The `GET /v2/bridge_types/:BridgeName` route is registered in `v2Routes` as `authv2.GET("/bridge_types/:BridgeName", bt.Show)` with no `auth.RequiresEditRole`/`RequiresAdminRole`/`RequiresRunRole` wrapper, unlike the sibling `Create`, `Update`, and `Destroy` routes on the same resource. Because `auth.Authenticate` only validates that a session/token is valid (not the user's role), any authenticated user — including one with the lowest privilege `UserRoleView` — can call `Show`, which returns the bridge's plaintext `OutgoingToken` via `presenters.NewBridgeResource`.

### Finding Description
In `core/web/router.go` the bridge routes are set up as: [1](#0-0) 
```go
bt := BridgeTypesController{app}
authv2.GET("/bridge_types", paginatedRequest(bt.Index))
authv2.POST("/bridge_types", auth.RequiresEditRole(bt.Create))
authv2.GET("/bridge_types/:BridgeName", bt.Show)
authv2.PATCH("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Update))
authv2.DELETE("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Destroy))
```
`bt.Show` is reachable through `authv2`, which is only wrapped by `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` — this middleware only checks that a valid session/token exists and sets the user in context; it performs no role check [2](#0-1) . The role-gating helpers (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole`) that reject `UserRoleView` are defined but simply not applied to `Show` [3](#0-2) .

`BridgeTypesController.Show` fetches the bridge record and serializes it directly with no field redaction based on role: [4](#0-3) 
```go
func (btc *BridgeTypesController) Show(c *gin.Context) {
	...
	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	...
	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
```
`presenters.NewBridgeResource` copies `b.OutgoingToken` verbatim into the JSON response with no `omitempty`/redaction (unlike `IncomingToken`, which is tagged `omitempty` and only populated on create): [5](#0-4) 

So a `UserRoleView` session, once authenticated, can call `GET /v2/bridge_types/:BridgeName` and receive the real `outgoingToken` field for any bridge — a credential that is meant to authenticate the Chainlink node to an external adapter, and which is otherwise treated as write-role-protected material (its sibling mutating endpoints require edit role).

### Impact Explanation
This is a secret/credential disclosure to a lower-privileged authenticated principal: a view-only user can obtain a bridge's `OutgoingToken`, which the node uses to authenticate to external adapters. With that token an attacker with view-only credentials could impersonate the node to the external adapter or use the token elsewhere, exceeding what a view role is supposed to permit (view role is meant to be read-only/non-sensitive access, but no read endpoint elsewhere in this router redacts a live secret to view-role users the way this one does — comparable secrets like API secrets, external initiator secrets are not exposed post-creation to lower roles).

### Likelihood Explanation
Trivial and fully repeatable: only requires an existing `UserRoleView` session or a restricted API token with view role, then a single unauthenticated-role-gate-free `GET /v2/bridge_types/<name>` call. No race conditions or special timing needed; works for every bridge name known to the attacker (bridge names may also be enumerable via `GET /v2/bridge_types` which is likewise not role-gated) [6](#0-5) .

### Recommendation
Wrap the `Show` route with `auth.RequiresEditRole` (matching `Update`/`Destroy`) in `core/web/router.go`, i.e. `authv2.GET("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Show))`, or redact `OutgoingToken` in `presenters.NewBridgeResource` for non-edit/admin roles (similar to how `IncomingToken` is only ever populated at creation time).

### Proof of Concept
Add a handler-level Go test in `core/web/bridge_types_controller_test.go` alongside the existing `TestBridgeController_Show`:
1. Create an application (`cltest.NewApplication`) and a bridge with a known `OutgoingToken` via `app.BridgeORM().CreateBridgeType`.
2. Create an HTTP client authenticated with a session/user whose `Role` is `sessions.UserRoleView` (use `app.NewHTTPClient` with a view-role user, mirroring how other tests build role-scoped clients, e.g. via `cltest.MustRandomUser` with `Role: sessions.UserRoleView` and a session cookie for that user).
3. Call `client.Get("/v2/bridge_types/" + bt.Name.String())`.
4. Assert `resp.StatusCode == http.StatusOK` (currently succeeds, proving no role gate) and parse the JSON body into `presenters.BridgeResource`, asserting `resource.OutgoingToken == bt.OutgoingToken` (the real secret), demonstrating the view-role user received the plaintext credential — which should instead have been `403 Forbidden` or had the field redacted.

// Authenticate is middleware which authenticates the request by attempting to
// authenticate using all the provided methods.
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
