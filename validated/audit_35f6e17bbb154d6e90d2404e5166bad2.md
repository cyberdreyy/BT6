### Title
Unauthenticated allowlist bypass in `handler.HandleLegacyUserMessage` allows any signer to trigger `web_api_trigger` dispatch to all DON members - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` only validates message structure, signature format, and payload freshness before dispatching `MethodWebAPITrigger` requests to every member of the DON via `don.SendToNode`. The code contains an explicit `// TODO: apply allowlist and rate-limiting here` immediately before the dispatch loop, meaning no check exists to verify the signer is an authorized workflow owner/sender before workflow-triggering requests are broadcast to the entire DON.

### Finding Description
`msg.Validate()` (called by the gateway before invoking the handler, and internally in `common.ValidatedRequestFromMessage`) only checks structural constraints — signature hex length, ID/method/DonId length limits, and recovers the signer address via `ExtractSigner` — it does not check that the recovered signer belongs to any authorized/allowlisted set. [1](#0-0) 

In `HandleLegacyUserMessage`, after payload decoding and a staleness check, the code proceeds directly to forwarding the request to every DON member with no authorization/allowlist check on the sender, exactly where the `TODO` comment sits: [2](#0-1) 

Any party capable of generating an ECDSA keypair and signing a well-formed message (no on-chain registration or prior relationship with the DON required) can produce a validly-signed `web_api_trigger` message that passes `Validate()` and is dispatched to `don.SendToNode` for all `h.donConfig.Members`. This is confirmed by handler tests exercising `HandleLegacyUserMessage` with a signature but no independent authorization step: the "happy case" test signs with an arbitrary key and observes dispatch to all DON members with no allowlist check performed. [3](#0-2) 

### Impact Explanation
This matches the "unauthorized job run" bounty class: an attacker with no prior relationship to a workflow or DON can force the gateway to dispatch trigger events to every node in a DON, potentially causing spurious/unauthorized workflow executions and enabling resource-consumption/DoS against the DON (compounded by the also-missing rate limiting referenced in the same TODO).

I could **not** substantiate the second half of the question — that `handleWebAPITriggerMessage`'s response payload ever contains job-spec or bridge-credential data. The response returned to the caller is constructed from the DON node's own signed reply and encoded via `codec.EncodeLegacyResponse`, which only echoes the trigger-response `Message` (topic/param-style payload), not job specs or bridge credentials; no code path here decodes or forwards job-spec/bridge-credential content into that response. That specific claim is not supported by the code and is excluded from this finding.

### Likelihood Explanation
Fully unauthenticated/unprivileged: attacker only needs a fresh ECDSA keypair (no registration, no allowlisting, no prior relationship to the DON) to sign a structurally valid message. No rate limiting exists to slow repeated abuse. Highly repeatable and trivially scriptable.

### Recommendation
Implement the allowlist check the TODO describes: before forwarding to `don.SendToNode`, verify `msg.Body.Sender` (or the associated workflow owner) against an authorized allowlist (e.g., analogous to `AllowListBasedAuth` used elsewhere in the vault handler) and add per-sender/global rate limiting, rejecting non-allowlisted senders with an authorization error prior to dispatch.

### Proof of Concept
Add a table-driven test to `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `triggerRequest` signed with a freshly generated, never-before-seen private key (not a DON member, not any known/authorized workflow owner).
2. Call `handler.HandleLegacyUserMessage(ctx, msg, cb)`.
3. Assert (expected fix behavior) that `don.SendToNode` is **not** called for any member and that the callback response returns an authorization error (e.g., `api.UnauthorizedError`) — currently this assertion fails because `don.SendToNode` is invoked for every `h.donConfig.Members` regardless of sender identity, demonstrating the gap.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
