### Title
KeyringIdleWhitelist OR-semantics let a stale whitelist "allow" override an external Keyring "deny", so revoked users keep vault access - ([File: contracts/KeyringIdleWhitelist.sol])

### Summary
`KeyringIdleWhitelist.checkCredential` returns `whitelist[entity] || Keyring(keyring).checkCredential(policyId, entity)`. A locally stored "allow" always wins over a deny coming back from the external Keyring credential system, mirroring the OpenEMR `zhAclCheck` bug class where any "allow" grants access regardless of an explicit "deny". [1](#0-0) 

### Finding Description
`IdleCDOEpochVariant.isWalletAllowed` delegates the entire KYC/access decision to `IKeyring(keyring).checkCredential(keyringPolicyId, _user)`. [2](#0-1)  The `keyring` address configured on the CDO is the `KeyringIdleWhitelist` wrapper, not the raw Keyring contract — the factory deploys it and points `cv.keyring()` at it. [3](#0-2)  The wrapper short-circuits on `whitelist[entity]`, so once the whitelist admin has whitelisted an address, any subsequent negative verdict from the upstream Keyring policy (KYC lapse, sanctions hit, credential expiry) is ignored. Every gated entry point in the vault relies on this single check:

- `_deposit` reverts unless `isWalletAllowed(msg.sender)` [4](#0-3) 
- `depositDuringEpoch` reverts unless `isWalletAllowed(msg.sender)` [5](#0-4) 
- `IdleCDOEpochQueue._checkAllowed` gates `requestDeposit` and `requestWithdraw` through the same `isWalletAllowed` call [6](#0-5) 

There is no path where an external "deny" can revoke a whitelisted address: `setWhitelistStatus` is the only removal mechanism and the OR in `checkCredential` means `whitelist[entity] == true` permanently bypasses `Keyring.checkCredential`. The whitelist is a stale-able allow cache with no deny-precedence, exactly the OpenEMR allow-overrides-deny pattern.

### Impact Explanation
A wallet that was whitelisted and later receives a Keyring deny (credential revoked, sanctioned, policy tightened) continues to pass `isWalletAllowed` indefinitely. It can keep depositing into AA/BB tranches, submit withdraw requests through the queue, and — critically — `claimWithdrawRequest` and `claimInstantWithdrawRequest` pay out underlying tokens to `msg.sender` with no additional wallet check, so a denied user can still extract pool funds via `IdleCreditVault.claimWithdrawRequest`. [7](#0-6)  Because tranche tokens are freely transferable, the denied wallet can also acquire tranches on secondary and claim the underlying. Loss is bounded by the denied user's position but constitutes unauthorized withdrawal from a KYC-gated credit pool — a direct violation of the pool's access invariant.

### Likelihood Explanation
Whitelisting exists precisely to bypass Keyring for operational addresses (the factory whitelists the epoch queue itself), so "whitelisted then later denied upstream" is a realistic divergence: the whitelist admin has no on-chain hook forcing it to track upstream revocations, and `checkCredential` gives no precedence to the deny. The attacker is unprivileged (any previously whitelisted EOA) and the honest admin/borrower only need to act in their normal sequence.

### Recommendation
Give denies precedence over the local allow cache. Since upstream Keyring returns a bool (not allow/deny/absent), the cleanest fix is to require both signals when the entity is not operationally exempt, e.g. `return Keyring(keyring).checkCredential(policyId, entity) || whitelist[entity]` is current behavior — instead, either (a) restrict `whitelist` to non-user operational contracts (queue/escrow) enforced at `setWhitelistStatus` time, or (b) add an explicit `denylist` mapping checked first, so revocation is always expressible: `if (denylist[entity]) return false;`. Also consider a re-check of `isWalletAllowed` inside claim paths if claims by revoked users are not intended.

### Proof of Concept
```solidity
// Foundry fork PoC sketch — repo: Noahgrantyt/idle-tranches--018
function testWhitelistedUserBypassesKeyringDeny() external {
  // setup: credit vault deployed via factory with KeyringIdleWhitelist
  KeyringIdleWhitelist kw = KeyringIdleWhitelist(deployment.keyringWhitelist);
  IdleCDOEpochVariant cv = IdleCDOEpochVariant(deployment.cv);
  MockKeyring upstream = MockKeyring(kw.keyring());

  address user = makeAddr("user");

  // honest admin whitelists user (e.g. operational reasons)
  vm.prank(kw.admin());
  kw.setWhitelistStatus(user, true);

  // upstream Keyring now DENIES the user (KYC revoked / sanctioned)
  upstream.setCredential(policyId, user, false);
  assertFalse(upstream.checkCredential(policyId, user), "upstream deny");

  // BUG: stale allow overrides explicit deny
  assertTrue(cv.isWalletAllowed(user), "whitelist allow wins over deny");

  // denied user can still deposit and later claim underlying
  deal(address(underlying), user, 100_000e6);
  vm.startPrank(user);
  underlying.approve(address(cv), 100_000e6);
  cv.depositAA(100_000e6);          // succeeds despite upstream deny
  cv.requestWithdraw(...);          // succeeds
  vm.stopPrank();
  // after epoch processing: cv.claimWithdrawRequest() pays underlying to denied user
}
```

Broken invariant: access — the deny from the authoritative credential source is never honored for whitelisted entities; existing guards (`_checkAllowed`, `_checkNotAllowed`, nonReentrant) do not stop it because they all funnel through the OR-bypassed `checkCredential`.
