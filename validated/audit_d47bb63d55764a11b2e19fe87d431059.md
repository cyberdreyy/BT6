### Title
Closed-pool withdraw requests mint unfunded interest, letting claimants drain other LPs' repaid principal - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analog to the SabreDAV traversal: an alternate input path (backslash as separator) bypasses a check meant for the canonical form. Here, `requestWithdraw` has an alternate accounting path for a closed pool (`epochEndDate == 0`): it skips adding the request to `pendingWithdraws`, but still mints a receipt for `principal + interest - fees`, i.e. the same "interest-bearing" form used for open-pool requests. That interest is never earned or funded — the borrower has already repaid — yet `_claimFundedWithdrawRequest` pays it immediately at par, burning `withdrawsRequests` and transferring real underlying held for remaining LPs.

### Finding Description
In `IdleCreditVault.requestWithdraw` (`contracts/strategies/idle/IdleCreditVault.sol:259-295`), the closed-pool branch is:

- `isClosed = IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0` (line 259)
- `_burn(msg.sender, _principal)` — only principal is burned from the CDO (line 273)
- `_mint(_user, _amount)` — the user receipt includes projected epoch interest, since `IdleCDOEpochVariant.requestWithdraw` passes `_underlyings = principal + interest - totalFees` (`contracts/IdleCDOEpochVariant.sol:773-790`)
- `if (!isClosed) { pendingWithdraws += _amount; }` — the receipt is NOT added to borrower-owed pending withdrawals (lines 277-280)
- The `else` branch still records `withdrawsRequests[_user] += _amount` (lines 287-293)

Claim gating in `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:326-349`) only reverts when `epochEndDate() != 0 && epochNumber <= lastWithdrawRequest[_user]`. In closed mode `epochEndDate() == 0`, so the epoch-wait check is bypassed and the full `withdrawsRequests[_user]` (principal **plus** unfunded interest, net of fees) is paid at par via `_transferFundedClaim` from the strategy's held underlyings — the repaid borrower funds that back other users' receipts and tranche redemptions.

Interest is nonzero because `_calcInterestWithdrawRequest` (`IdleCDOEpochVariant.sol:856-878`) only returns 0 when `epochDuration == 0`; a closed pool retains a nonzero `epochDuration`, so each request mints `amount * apr-scaled interest` out of thin air.

### Impact Explanation
Any KYC-passing tranche holder can repeatedly call `requestWithdraw` after pool close and immediately `claimWithdrawRequest`, receiving `principal + projectedEpochInterest - fees` per request while only `principal` of strategy-token backing was burned and nothing was added to `pendingWithdraws`. The excess is paid from the vault's repaid-liquidity reserve, directly stealing funds owed to other pending claimants / remaining tranche holders. Broken invariant: fair mint/burn and one-receipt-one-payout — interest is minted without any corresponding accrual or borrower funding.

### Likelihood Explanation
Requires only that the pool reaches the closed state (`epochEndDate == 0`, the `_interest == 1` "repay all" path) with `epochDuration != 0` and a nonzero configured APR, and that withdraw-request flags remain enabled — a normal end-of-life state for this product. No privileged misbehavior needed; any tranche holder can do it, and repeat it since each request re-mints interest.

### Recommendation
In closed-pool mode, mint the receipt at principal only: either return `_interest = 0` from `_calcInterestWithdrawRequest` when `epochEndDate == 0`, or pass `principal` (not `principal + interest - fees`) to `IdleCreditVault.requestWithdraw` and skip `interestForOverUnderPerformance`/`pendingWithdrawFees` adjustments that assume a future epoch.
