### Title
Multisig `confirm` executes requests below `num_confirmations` live approvals due to stale confirmations surviving `delete_member` - (File: multisig2/src/lib.rs)

### Summary
`delete_member` only removes outstanding requests whose *creator* field (`MultiSigRequestWithSigner.member`) equals the deleted member, but never scans or purges the deleted member's confirmation string from `self.confirmations` entries on requests created by other members. `confirm` counts raw `HashSet<String>` length against `num_confirmations` without checking membership validity, so a request confirmed by a now-removed member still counts toward quorum, allowing execution (e.g. a `Transfer`) with fewer live confirmations than `num_confirmations`.

### Finding Description
Binding claimed to hold but actually broken: `{distinct current self.members who confirmed R}.len() == self.num_confirmations` at the moment `execute_request` runs inside `confirm`.

Path:
1. Member B creates request R (`add_request_and_confirm`) targeting `receiver_id = attacker_account` with `Transfer{amount}`. `MultiSigRequestWithSigner.member = B` [1](#0-0) .
2. Member A calls `confirm(R)`, which inserts the string `A.to_string()` into `self.confirmations[R]` (a `HashSet<String>`, decoupled from `self.members`) [2](#0-1) . Now `confirmations[R] = {B, A}`, `num_confirmations = 3`.
3. Members B and C confirm and execute a separate request `DeleteMember{member: A}`. `execute_request` calls `delete_member(promise, A)` [3](#0-2) , which only removes requests where `r.member == A` (i.e., requests *created by* A) [4](#0-3) . Since R was created by B, R and its `confirmations[R] = {B, A}` entry are left untouched; only `self.members` and `num_requests_pk[A]` are cleaned [5](#0-4) .
4. Member C calls `confirm(R)`. `assert_valid_request` passes (C is a current member, R exists, confirmations map entry exists) [6](#0-5) . The check `!confirmations.contains(&C.to_string())` passes since C hasn't confirmed. Then `confirmations.len() as u32 + 1 >= self.num_confirmations` evaluates `2 + 1 >= 3` → true, using the stale `A` entry, and `execute_request(R)` runs the `Transfer{amount}` to `attacker_account` [7](#0-6) .

Root cause: confirmations are stored as free-standing account/key strings, never revalidated against `self.members`, and `delete_member`'s cleanup filter keys off request-creator identity (`r.member`) instead of scanning `self.confirmations` values for the removed member's string across all outstanding requests. No existing guard (`assert_valid_request`, `assert_self_request`, `assert_one_action_only`) checks confirmer validity.

### Impact Explanation
NEAR is transferred out of the multisig account to `attacker_account` (or any receiver of the original request) with only 2 live member approvals instead of the required 3, i.e., a multisig request executed below `num_confirmations` live members — matching the Critical impact category. Any member who is later removed after confirming a pending request created by someone else leaves an exploitable stale approval; this is repeatable for every pending, not-yet-quorum request that a to-be-removed member had confirmed.

### Likelihood Explanation
Requires: an existing pending request R with fewer than `num_confirmations` confirmations, one of the confirmers subsequently being removed via a separate, properly-confirmed `DeleteMember` request, and then one more legitimate confirmation to cross the (now effectively lowered) threshold. This does not require the attacker to be a member — the remaining members' ordinary, well-intentioned operational actions (removing a compromised/departing member while other requests are pending) can trigger it, and a receiver_id could be attacker-controlled if the request itself targeted the attacker (e.g., a member's key was compromised and used to create the initial transfer request before being removed). It relies only on normal multisig usage patterns, no privileged bypass, no gas/DoS reasoning.

### Recommendation
When deleting a member, iterate all `self.confirmations` entries (not just requests the member created) and remove the member's string from each `HashSet<String>`; alternatively, in `confirm`, recompute the live confirmation count by intersecting `confirmations` with `self.members.iter().map(|m| m.to_string())` before comparing against `num_confirmations`, rather than trusting stored `HashSet::len()`.

    testing_env!(context_with_key(pk_a(), amount));
    c.confirm(request_id);
    assert_eq!(c.confirmations.get(&request_id).unwrap().len(), 2);

    testing_env!(context_with_key(pk_b(), amount));

    assert_eq!(c.requests.len(), 0);
