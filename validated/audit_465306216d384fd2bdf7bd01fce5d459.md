### Title
Stale `BlockValidateOk` resurrects a `GloballyRejected` block into a pre-commit/signature - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`BlockInfo::mark_pre_committed` (stacks-signer/src/signerdb.rs:272-277) mutates `self.valid = Some(true)` and stamps `approved_time` *before* attempting the state transition via `move_to`, and does not roll back these mutations when `move_to` returns `Err`. `handle_block_validate_ok` (stacks-signer/src/v0/signer.rs:1960-1984) treats a failed `mark_pre_committed` as tolerable whenever `has_reached_consensus()` is true, and unconditionally proceeds to persist the block, broadcast a pre-commit, and invoke `handle_block_pre_commit` for itself — even though the state transition to `PreCommitted` was rejected because the block was already terminally `GloballyRejected`.

### Finding Description
Race sequence:
1. A miner proposes block `B`. Signer `S` cannot yet validate it locally and calls `submit_block_for_validation` (stacks-signer/src/v0/signer.rs:1696), which sets `submitted_block_proposal` and stores `block_info` with `valid = None`.
2. While `S`'s own node is still validating `B` (e.g. because `S`'s node is slower, or the miner deliberately crafts `B` to be slow to validate on some nodes), other signers reject `B` for a legitimate reason and their combined rejection weight exceeds the 30% blocking-minority threshold. `S` receives these rejections via `handle_block_rejection` → `store_and_process_block_rejection` (signer.rs:2268), which calls `block_info.mark_globally_rejected()` (signer.rs:2335, signerdb.rs:304-306). This function **only** calls `move_to(GloballyRejected)`; it never sets `self.valid`. So `block_info.state == GloballyRejected` while `block_info.valid == None` — the terminal-state invariant ("Global states are terminal against each other") is intact, but `valid` remains unset. [1](#0-0) [2](#0-1) 
3. `S`'s node finally answers the earlier submission with `BlockValidateOk`. `handle_block_validate_ok` reloads `block_info` (still `valid = None`, `state = GloballyRejected`), and because `valid.is_some()` is false, the early "already processed" guard at signer.rs:1932-1940 does **not** trigger. [3](#0-2) 
4. `check_block_against_signer_db_state` (signer.rs:1803) only checks tenure/chain-length consistency — it has no knowledge of `GloballyRejected` — and can return `None` (i.e. "still consistent"), so the code takes the `else` branch at signer.rs:1960.
5. `block_info.mark_pre_committed()` sets `valid = Some(true)` and `approved_time`, then calls `move_to(PreCommitted)`, which fails (`check_state` only allows `PreCommitted` from `Unprocessed`, never from `GloballyRejected`) — but the `valid`/`approved_time` mutations already happened and are **not undone**. [4](#0-3) 
6. Because `has_reached_consensus()` is true, the guard at signer.rs:1964-1969 does not `return`; execution falls through to `insert_block` (persisting `valid=Some(true)` with `state=GloballyRejected`), `send_block_pre_commit`, and `handle_block_pre_commit` for the signer's own address. [5](#0-4) 
7. `handle_block_pre_commit` (signer.rs:1250) reloads the (now poisoned) `block_info`, checks only `signed_self.is_some()` (false) and `!valid.unwrap_or(false)` (now `true`, so it does **not** return) — it never checks `state`/`has_reached_consensus()` before proceeding. [6](#0-5)  If the pre-commit weight threshold is already met (or is met by this signer's own contribution plus stragglers who haven't yet processed the rejection), it proceeds through `check_block_against_signer_db_state` again and the conflict checks, and can reach `SIGN: mark_locally_accepted, handle_block_signature, broadcast acceptance` (signer.rs:1345-1366 leads into the sign path documented in docs/signer-flows.md:268).

Net effect: a block this signer's own bookkeeping already recorded as `GloballyRejected` (a terminal state) is broadcast as a pre-commit and can be signed and gossiped as an acceptance — a rejection effectively "recounted" toward acceptance, breaking the terminal/one-way state-machine guarantee documented in `docs/signer-flows.md:130-162` ("Global states are terminal against each other").

### Impact Explanation
This breaks the safety invariant that `GloballyRejected` is terminal and that `valid` is only ever set together with a genuine validation/consistency decision. It lets a stale validation response effectively override a state the signer itself already recorded as terminally rejected, producing a spurious pre-commit broadcast and potentially a real signature contribution toward a block the local signer had already condemned. This matches the "rejection recounted as an acceptance" Critical-impact category: it can let the signer's own weight get added to a block that should be dead, and in aggregate (combined with other stragglers experiencing the same race) risk resurrecting a block the network was converging to reject, or at minimum poison the signer's own audit/consensus bookkeeping (`valid=true` alongside `state=GloballyRejected`) in a way other code paths (e.g. `determine_response`, re-proposal handling) don't anticipate.

### Likelihood Explanation
This requires only a natural asynchronous race: a slow/local validation response arriving after the signer has already tallied ≥30% rejection weight from gossip — no majority of colluding signers or extra privilege is needed. A miner (one slot) can amplify the race window by proposing a transaction set that is fast to reject on some nodes but slow to fully re-validate on others (e.g. exploiting execution/timing variance), increasing the chance that `S`'s own submission answers late. It does not require compromising any signer key, the auth_token, or majority control — only ordinary network/validation timing variance that a miner can nudge.

### Recommendation
- In `BlockInfo::mark_pre_committed` (and other `mark_*` helpers), only mutate `valid`/timestamps after `move_to` succeeds, or roll back the mutation on `Err`.
- In `handle_block_validate_ok`, when `mark_pre_committed` fails because the block `has_reached_consensus()` (i.e., already `GloballyAccepted`/`GloballyRejected`), simply `return` without falling through to `insert_block`/`send_block_pre_commit`/`handle_block_pre_commit` — there is nothing further to do once a block is terminal.
- In `handle_block_pre_commit`, add an explicit `has_reached_consensus()` (or `state`) check before proceeding past the `signed_self`/`valid` checks, so a poisoned `valid=true` on a terminally-rejected block cannot resume the pre-commit → sign pipeline.

### Proof of Concept
1. Signer `S` receives proposal `B`; validation is submitted to node (`submitted_block_proposal` set, `block_info.valid = None`).
2. Inject ≥30%-weight `BlockResponse::Rejected` messages for `B` from other signer slots before `S`'s node responds; `S` calls `store_and_process_block_rejection` → `mark_globally_rejected()`, leaving `state = GloballyRejected`, `valid = None`.
3. Deliver the delayed `BlockValidateResponse::Ok(block_validate_ok)` for `B` to `S` (e.g. via the `TEST_VALIDATE_STALL`/delay fault-injection hooks already present in `stackslib/src/net/api/postblock_proposal.rs`, used similarly in `block_validation_response_timeout`/`signers_wait_for_validation.rs` tests, to hold the node's response until step 2 completes).
4. Observe that `handle_block_validate_ok` does not early-return at the `valid.is_some()` check, `mark_pre_committed` fails but is ignored due to `has_reached_consensus()`, and `S` broadcasts `BlockPreCommit` for `B` and re-enters `handle_block_pre_commit`, which no longer treats `B` as rejected (`valid` is now `Some(true)`) and can proceed toward signing it.
