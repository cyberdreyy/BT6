### Title
Builder withdrawal amount is minted uncapped by the execution layer while the CL-side deduction saturates at the builder's actual balance - Unvalidated withdrawal amount analog to missing min/max sanity check ([File: specs/gloas/beacon-chain.md])

### Summary
The Chainlink report flags a case where a value produced by an untrusted/unbounded source (an oracle price) is consumed without validating it against the real bounds of the underlying asset, letting a stale/incorrect number be treated as truth and used to move funds. The consensus-specs analog is in `apply_withdrawals` (Gloas fork, `specs/gloas/beacon-chain.md`): the beacon state caps the *builder balance deduction* to `min(withdrawal.amount, builder_balance)`, but the `Withdrawal.amount` field that is written into `state.payload_expected_withdrawals` — the value the execution layer is contractually required to honor (mint to the destination address) — is **never capped**. If `withdrawal.amount` (the requested/committed amount) exceeds the builder's actual remaining balance at processing time, the CL only removes what the builder actually has, while the EL still mints the full, uncapped, requested amount. This breaks the “no Gwei created” equality.

### Finding Description
`apply_withdrawals` in `specs/gloas/beacon-chain.md` (lines 1920-1932):
```python
def apply_withdrawals(state: BeaconState, withdrawals: Sequence[Withdrawal]) -> None:
    for withdrawal in withdrawals:
        if is_builder_index(withdrawal.validator_index):
            builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
            builder_balance = state.builders[builder_index].balance
            state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
        else:
            decrease_balance(state, withdrawal.validator_index, withdrawal.amount)
``` [1](#0-0) 

Notice the accounting-side deduction (`state.builders[...].balance`) is safely bounded by `min(...)`, but the `withdrawal.amount` object that is placed unmodified into `state.payload_expected_withdrawals` earlier in `get_builder_withdrawals`/`get_builders_sweep_withdrawals` keeps the full requested value: [2](#0-1) 

This `payload_expected_withdrawals` value is what the execution layer is required to execute — the spec explicitly states withdrawals are "deterministic given the beacon state" and "any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals in the execution layer": [3](#0-2) 

The test suite confirms this asymmetry is real (not a hypothetical): with a builder that only has 1 ETH but a pending withdrawal requesting 5 ETH, the recorded withdrawal in `payload_expected_withdrawals` is the full 5 ETH ("requested amount"), while the CL-side balance is only reduced to 0 (i.e. only 1 ETH was actually deducted): [4](#0-3) [5](#0-4) 

This is the analog to the Chainlink bug: the value used to trigger a real-world payment (`withdrawal.amount`, analogous to an on-chain price feed's raw `latestRoundData()` output) is never clamped against the actual bound (`builder_balance`, analogous to `minAnswer`/`maxAnswer`) before it is committed as the payment truth. The CL clamps its own bookkeeping but forwards the unclamped figure downstream to the EL, which will mint/pay the unclamped amount.

### Impact Explanation
If a `BuilderPendingWithdrawal.amount` (created when a builder bid is accepted) ends up exceeding the builder's real, remaining balance at the time the pending withdrawal is actually processed (e.g., because the balance was reduced by other withdrawals/slashings/fees processed in the interim, or because multiple pending payments were queued against the same balance without reserving it), the fee recipient/execution address receives the full requested amount from the execution layer even though only a fraction (or none) of that value was truly backed by the builder's locked balance. That is a direct Gwei-created-from-nothing event — a Critical-severity equality break per the stated impact categories (“Gwei created, destroyed, or paid to a non-owner”, and “a payload executed or paid that the block did not commit to” in spirit, since what is actually available to back the payment and what is committed for the EL to execute diverge).

### Likelihood Explanation
The exact reachability depends on whether `can_builder_cover_bid` (checked at bid-acceptance time in `process_execution_payload_bid`) properly reserves/accounts for already-queued but not-yet-processed `BuilderPendingWithdrawal`/`BuilderPendingPayment` amounts against the same builder before admitting a new bid. I was not able to fully verify this reservation logic within the available tool budget — the grep for `can_builder_cover_bid` matched many locations in `specs/gloas/beacon-chain.md` but I did not get to inspect its body before running out of iterations. If `can_builder_cover_bid` checks the builder's *current* balance without subtracting sums already pending in `state.builder_pending_payments`/`state.builder_pending_withdrawals`, then a builder (or even an honest builder whose balance changes for unrelated reasons between bid acceptance and processing) can end up in the exact state exercised by `test_builder_withdrawal_insufficient_balance`, and the uncapped `withdrawal.amount` would flow to the EL. This is the key open question that determines whether this is reachable purely through spec-permitted, non-malicious paths, or whether it requires a builder deliberately gaming the check (still an unprivileged actor, since builders are not privileged/trusted entities in this model).

### Recommendation
Cap `withdrawal.amount` itself (not just the CL-side balance decrement) to the builder's actual available balance before it is written into `state.payload_expected_withdrawals`, i.e. compute `amount = min(withdrawal.amount, builder_balance)` once and use that same clamped value both for the `Withdrawal` object placed in the payload and for the balance decrement. Additionally, verify that `can_builder_cover_bid` reserves already-pending committed withdrawal amounts (not just current balance) so that the sum of all outstanding commitments for a builder can never exceed that builder's actual balance.

### Proof of Concept
Using the existing test harness as the concrete demonstration of the divergence (already present in the repo, not hypothetical):
1. Set up a builder with `balance = 1_000_000_000` Gwei (1 ETH).
2. Queue a `BuilderPendingWithdrawal` for that builder with `amount = 5_000_000_000` Gwei (5 ETH) — see `test_builder_withdrawal_insufficient_balance`: [4](#0-3) 
3. Run `process_withdrawals`. The resulting `payload_expected_withdrawals` entry has `amount == 5_000_000_000` (the full requested amount) while `state.builders[0].balance == 0` (only 1 ETH was actually removed from CL accounting).
4. Because the execution layer is contractually bound to execute exactly what is in `payload_expected_withdrawals`, the EL will mint 5 ETH to the fee recipient even though only 1 ETH was ever locked in the builder's CL balance — 4 ETH created from nothing, breaking the total-supply equality.

**Remaining uncertainty:** whether an honest (non-colluding) sequence of spec-compliant bids/payments can actually drive a builder into this insufficient-balance state without a bug/omission in `can_builder_cover_bid`'s reservation of already-pending commitments — this was not confirmed due to running out of investigation iterations, and should be validated against the full body of `can_builder_cover_bid` and `process_builder_pending_payments`/queue-draining logic in `specs/gloas/beacon-chain.md` before treating this as a fully proven, end-to-end unprivileged exploit.

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

##### Modified `process_withdrawals`

*Note*: This is modified to only take the `state` as parameter. Withdrawals are
deterministic given the beacon state, any execution payload that has the
corresponding block as parent beacon block is required to honor these
withdrawals in the execution layer. `process_withdrawals` must be called after
`process_parent_execution_payload` (which updates `state.latest_block_hash`) and
before `process_execution_payload_bid` as the latter function affects validator
balances.

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
