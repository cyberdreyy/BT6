### Title
A dust APR=0 withdraw receipt permanently bricks `stopEpoch` once APR is raised — unprivileged freeze of all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts with `NotAllowed` whenever `unscaledApr != 0` while `apr0TotalPrincipal > 0`. Any KYC-passed lender can create a minimal `requestWithdraw` during an APR=0 epoch, which leaves `apr0TotalPrincipal` and `apr0Users[user].principal` permanently nonzero: the receipt can only be settled inside `_settleApr0`/`_claimFundedWithdrawRequest`, which requires `epochNumber` to increase — and `epochNumber` only increases in `stopEpoch`, the very function that now reverts. Like CVE-2017-7346's unvalidated `levels` data hanging the kernel, no input validation anywhere ensures an outstanding APR0 bucket cannot outlive the APR regime that created it, so a crafted unprivileged request converts the epoch state machine into a deadlocked state.

### Finding Description
In `requestWithdraw`, when `unscaledApr == 0` and the pool is not closed, the request is routed into the APR0 bucket (`IdleCreditVault.sol:285-286`), setting `apr0Users[_user].principal` and increasing `apr0TotalPrincipal` (`IdleCreditVault.sol:567-577`). There is no minimum amount and no guard preventing this state from surviving an APR change.

At the next epoch stop, the CDO calls `prepareStopEpochWithApr0`, which enforces:
```solidity
if (unscaledApr != 0) {
  revert NotAllowed();
}
```
(`IdleCreditVault.sol:506-508`) whenever `apr0TotalPrincipal != 0`.

Clearing paths are all unreachable in this state:
- `_claimFundedWithdrawRequest` → `_settleApr0` returns early while `_reqEpoch >= epochNumber` (`IdleCreditVault.sol:551-555`), and `epochNumber` is only bumped by `stopEpoch` via `deposit` (`IdleCreditVault.sol:607-610`) — which is blocked by the same revert.
- `apr0TotalPrincipal` is only zeroed at the end of `prepareStopEpochWithApr0` (`IdleCreditVault.sol:540`) or decremented in the default-claim path (`IdleCreditVault.sol:822-828`), both unreachable.
- The borrower/manager cannot clear the attacker's per-user `apr0Users` entry; `requestWithdraw` is permissioned only by `_onlyIdleCDO`, so any whitelisted lender via `cdoEpoch.requestWithdraw` can poison the bucket.

### Impact Explanation
Once `unscaledApr` is set nonzero (a normal, honest manager/CDO action via `setAprsWithBuffer`/`setApr`, `IdleCreditVault.sol:217-235`) while a dust APR0 receipt exists, every `stopEpoch` call reverts permanently. The epoch can never end: no `epochNumber` bump, no withdrawal processing, no borrower repayment accounting, and no recovery path short of borrower default. All user deposits, pending withdraw receipts and accrued yield — the full vault TVL — are frozen indefinitely. Cost to the attacker is a single minimal `requestWithdraw` (dust principal plus the management fee on dust).

### Likelihood Explanation
The attacker needs only to be a KYC-passed lender (`isWalletAllowed`/`_checkAllowed`) during a single epoch configured with `unscaledApr == 0` — a supported operating mode exercised by the test suite (`testApr0WithdrawGetsInterestAtStopEpoch`). Triggering the deadlock requires nothing more than sequencing around the honest manager's routine APR update; a manager transitioning the pool from 0% APR to a nonzero APR is an ordinary operational event. The `NotAllowed` revert at `IdleCreditVault.sol:506-508` confirms the code assumes this state is impossible rather than handling it — the same class of missing-validation hang as the CVE.

### Recommendation
Do not revert `stopEpoch` on a nonzero APR with an outstanding APR0 bucket. Either (a) settle the outstanding APR0 principal at a zero rate inside `prepareStopEpochWithApr0` and proceed, (b) allow `requestWithdraw` under `unscaledApr == 0` to be claimable/clearable without an epoch bump, or (c) reject APR increases via `setApr`/`setAprsWithBuffer` while `apr0TotalPrincipal != 0` so the revert happens at the config call, not inside the epoch-finalization path. Enforcing a minimum request size would also raise the attack cost but does not fix the deadlock.

### Proof of Concept
Foundry test (run with `forge test --match-test testApr0DustReceiptBricksStopEpoch` in `test/foundry/IdleCreditVault.t.sol` harness style):

```solidity
function testApr0DustReceiptBricksStopEpoch() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    // pool operates at 0% APR
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    // attacker (whitelisted lender) deposits and queues a dust withdraw request
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 1000 * ONE_SCALE, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // dust APR0 receipt

    // epoch 0 runs and stops at 0 APR; APR0 bucket persists (principal not yet settled)
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, 0, _expectedFundsEndEpoch());

    // honest manager sets a nonzero APR for the next epoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(10e18, 10e18);

    // buffer deposits work, epoch starts...
    _startEpochAndCheckPrices(1);

    // ...but stopEpoch can never succeed again: apr0TotalPrincipal != 0 && unscaledApr != 0
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(10e18, 0);

    // attacker cannot self-clear: claim requires epochNumber > principalEpoch
    vm.prank(attacker);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimWithdrawRequest();
}
```
