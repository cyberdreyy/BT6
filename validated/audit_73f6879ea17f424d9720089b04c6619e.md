### Title
Reorg-timing gate silently permits illegitimate reorgs when the approval timestamp postdates the sortition record - (File: stacks-signer/src/chainstate/mod.rs)

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a signer may sign a block whose miner reorgs away a previously-approved tenure. It only permits the reorg when the reorged tenure's first block was proposed/approved "very close to" the burn-block transition (`first_proposal_burn_block_timing`). The elapsed-time computation uses `saturating_sub`, which silently collapses a negative time delta (approval happening *after* the new sortition was recorded) to `0`. Zero is exactly the value that satisfies "very close to the transition," so instead of failing closed, the check fails open and treats a tenure that was never in a legitimate race as a valid reorg target. This mirrors the reported `ERC20SessionKeyValidator` flaw: one boundary of a two-sided timing condition (an implicit "not-yet-elapsed"/ordering check) is never enforced, letting a state be accepted as valid outside the window it was meant to guard.

### Finding Description
`check_parent_tenure_choice` in [1](#0-0)  computes, for each tenure being reorged that already produced a signed first block, how much time passed between that block's local approval and the receipt of the burn block that started the new (reorging) sortition: [2](#0-1) 

```
let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {
    sortition_state_received_time.saturating_sub(approved_at)
} else { ... 0 };
if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
    // treat as "poorly timed" / raced -> permit reorg, mark tenure superseded
}
```

The intended semantics are: "the tenure's only block was approved so close to the sortition boundary that the miner could not have known about the new sortition — this looks like an honest race, so allow the newer tenure to supersede it." That reasoning is only valid when `approved_at <= sortition_state_received_time`. `saturating_sub` unconditionally clamps negative results to `0`, so if `approved_at` occurs *after* `sortition_state_received_time` (e.g., due to signer processing/validation latency, a slow `check_proposal`/`should_reevaluate_block` path, clock skew between the signer's own event loop, or reordered/delayed local writes), the function reports `proposal_to_sortition == 0`, which is always `< first_proposal_burn_block_timing`. The tenure is then unconditionally classified as "poorly timed" and pushed into `superseded_tenures`, later persisted via `record_superseded_tenure` → `SignerDb::mark_tenure_superseded` at [3](#0-2) .

There is no companion check verifying `approved_at <= sortition_state_received_time` before trusting the subtraction — exactly the missing "other side of the bound" that the external report calls out for `validAfter`.

### Impact Explanation
Once a tenure is (incorrectly) marked superseded, `check_parent_tenure_choice` returns `true` for the reorging sortition, and `SortitionsView::check_proposal` (v1: [4](#0-3) ) accepts the new miner's proposal as building off a "valid" parent tenure instead of rejecting it with `ReorgNotAllowed`. Marking the old tenure as superseded also causes the signer's own already-placed signature over that tenure's block to stop counting as a conflict (per the doc comment on `record_superseded_tenure`), so the signer proceeds to sign the new, non-canonical branch's block even though the reorg does not meet the policy the code is supposed to enforce (globally accepted single-block tenure that was *not* a genuine race). This breaks the "approved-parent vs canonical" equality this module exists to protect and can lead a signer to co-sign a conflicting/non-canonical chain — a Critical-class outcome per the stated impact categories.

### Likelihood Explanation
No majority collusion or key compromise is needed. The trigger is ordinary signer-side timing: any delay between a block's local approval (`approved_time`) and this signer's own recording of the *next* sortition's burn-block receive time (`sortition_state_received_time`) — e.g. because block validation/approval processing is slow, the signer is momentarily busy, or the two events are written by different async paths at slightly different wall-clock moments — can invert the expected ordering. A miner that legitimately wins the next sortition (a normal, single-slot occurrence) and proposes a reorging tenure will have this code path evaluated; if the ordering inversion occurs for even one reorged tenure, the gate fails open. This is plausible under realistic operational jitter and does not require an adversarial majority, satisfying the "one-slot miner (plus gossip)" reachability bar.

### Recommendation
Do not rely on `saturating_sub` to encode a strict ordering assumption. Explicitly check the direction of the timestamps and only take the "well-timed" branch when `approved_at <= sortition_state_received_time`; otherwise treat the tenure as *not* well-timed (fail closed, i.e., reject the reorg) analogous to adding the missing `validAfter`-style bound:

```rust
let proposal_to_sortition = match local_block_info.approved_time {
    Some(approved_at) if approved_at <= sortition_state_received_time => {
        sortition_state_received_time - approved_at
    }
    Some(_) => {
        // approval recorded after the new sortition was seen: this is not a race,
        // do not treat it as well-timed.
        return Ok(false);
    }
    None => 0,
};
```
Additionally log/metric this case distinctly so operators can detect abnormal local clock/processing skew rather than silently permitting a reorg.

### Proof of Concept
Conceptual reproduction (matches the structure of the existing `reorg_timing_testing` unit tests in [5](#0-4) , which already exercise this exact code path with synthetic `proposed_time`/`sortition_time` values):

1. Insert a `BlockInfo` for tenure T with `approved_time = X` (a normal, non-raced approval, e.g. long after T's tenure started) and mark it globally/locally accepted so `get_globally_accepted_block_count_in_tenure(T) <= 1`.
2. Record a burn block for the reorging sortition with `insert_burn_block(..., received_time = Y)` where `Y < X` (simulating the signer recording the new burn block *before* it finished locally approving/committing T's block — reachable via normal async validation latency).
3. Call `SortitionsView::check_proposal` for a block whose sortition's `parent_tenure_id` differs from `prior_sortition`, forcing `check_parent_tenure_choice` to run.
4. Observe `sortition_state_received_time.saturating_sub(approved_at)` evaluates to `0` (since `Y - X` is negative), which is `< first_proposal_burn_block_timing`, so the function returns `Ok(true)` and marks T as superseded — even though `T`'s block was approved well after the "transition," i.e. it was not a race at all. This mirrors `check_proposal_reorg_timing_ok`/`check_proposal_reorg_timing_bad` in the existing test suite, but with the timestamp ordering inverted, which those tests do not cover.

Note: I could not execute this against a live signer/node in this environment; the analysis is based on static review of `stacks-signer/src/chainstate/mod.rs` and the corresponding v1/v2 `check_proposal` call sites and their existing unit tests, which confirm the intended one-directional-only assumption behind this arithmetic.
