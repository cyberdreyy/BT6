### Title
`GlobalStateEvaluator::reached_agreement` uses floor-division instead of the ceiling used by block-signature approval, letting global state "consensus" be reached below the true 70% supermajority - ([File: libsigner/src/v0/signer_state.rs])

### Summary
The external report's bug class is: a numeric adjustment silently loosens a guarantee the protocol is supposed to enforce exactly (the ERC5095 code added slippage the caller never asked for). The reachable analog in this repo is a rounding mismatch between two implementations of the "70% supermajority" rule: block-signature verification rounds the threshold **up** (`ceil`), while the signer's own global-state agreement check rounds it **down** (`floor`). This means the signer's internal notion of "the group agrees" can fire on strictly less real weight than the amount the chain itself requires to approve/sign a block.

### Finding Description
Two independent implementations exist of the "70% of signer weight" supermajority rule, and they are not equivalent:

1. `NakamotoBlockHeader::compute_voting_weight_threshold` (used by `verify_signer_signatures` to validate a block's aggregate signature weight, and by `stacks-signer/src/v0/signer.rs` when deciding whether the pre-commit/signature threshold has been reached) computes the minimum weight with an explicit ceiling: [1](#0-0) 

2. `GlobalStateEvaluator::reached_agreement`, used throughout `stacks-signer` (`determine_global_state`, `determine_global_burn_view`, `determine_latest_supported_signer_protocol_version`, `find_majority_prefix_replay_set`, and `signerdb.rs::get_burn_block_received_time_from_signers`) to decide whether the signer set has reached agreement on the active protocol version, the current miner, the burn view, or the transaction-replay set, computes the same nominal 70% bound with plain integer division (**floor**, no ceiling): [2](#0-1) 

For any `total_weight` where `total_weight * 7` is not a multiple of 10, `compute_voting_weight_threshold` requires one more weight-unit than `reached_agreement` does. E.g. `total_weight = 11`: the chain-level threshold is `ceil(7.7) = 8`, but `reached_agreement` accepts `vote_weight = 7` (`floor(77/10) = 7`), i.e. 63.6% of weight, as "agreement," a full unit of weight short of the actual 70% supermajority the rest of the protocol (and the docs at `docs/signer-flows.md`, which state "at ≥70% weight the signer decides…") assume.

This is exactly the ERC5095 bug class transposed: the code is supposed to enforce *the same* fixed, hard-coded threshold everywhere ("respect the 70% specification exactly"), but one code path silently applies a slightly looser bound than the other, and the discrepancy is deterministic and baked into the arithmetic — not something an operator can tune away.

### Impact Explanation
`determine_global_state()` feeds the signer's `SignerStateMachine` (active protocol version, current miner, burn view, tx replay set), which in turn drives `check_block_against_global_state` / `GlobalStateView::check_proposal` (`stacks-signer/src/chainstate/v2.rs`) — i.e., it is load-bearing for whether a signer treats a proposal as coming from the expected miner/tenure and under the expected replay-set constraints. If the "current miner" or "tx replay set" view can be flipped by a coalition holding only `floor(70%)` instead of the intended `ceil(70%)` of weight, a small additional slice of otherwise-legitimate voters (still well under any conventional "majority" framing, since it is only a fractional weight-unit gap tied to specific `total_weight` values) can cause the group's global state determination to diverge from the threshold the chain itself will require for actual block approval. Downstream, this can make a signer validate/pre-commit/sign a proposal against a "current miner"/replay-set view that was accepted into "agreement" with less real support than the canonical approval threshold, undermining the equality the whole pre-commit/signature protocol is built on ("only sign once ≥70% intends to").

The effect size is small (bounded by at most one weight-unit's worth of the total, e.g. 1 signer's weight out of 30), so it is not a broad universal exploit, but it is a genuine, always-present logic bug reachable without needing a colluding majority — only the specific weight distribution across signers (which is public, since reward-set weights are known in advance) is needed to land in a `total_weight` value where the floor/ceil gap is nonzero.

### Likelihood Explanation
This triggers deterministically whenever `total_weight * 7 % 10 != 0`, which is the common case for most signer-set sizes/weight distributions (it is the exception, not the rule, for `total_weight` to be a multiple of 10 given weights derived from stacked STX proportions). No malicious action, no majority collusion, and no network-timing race is required — only signers whose combined weight equals the floor-rounded (but not ceil-rounded) threshold need to report the same value. This is a systemic rounding defect, present on effectively every reward cycle whose total signer weight isn't a multiple of 10, exactly mirroring the H-1 report's framing that "the slippage amount is hard-coded ... the issue exists for all users every time the protocol is used."

### Recommendation
Make `GlobalStateEvaluator::reached_agreement` (and, for symmetry, `reached_disagreement`) use the same ceiling semantics as `NakamotoBlockHeader::compute_voting_weight_threshold`, e.g. factor out a single shared `compute_voting_weight_threshold`-style helper (already `u64`-widened here) and reuse it in `libsigner/src/v0/signer_state.rs`, so that "70% agreement" means the same integer bound everywhere signer-weight supermajorities are evaluated.

### Proof of Concept
1. Configure a reward cycle where `total_weight = 11` (e.g., 11 signers of weight 1 each, or any set summing to 11).
2. `NakamotoBlockHeader::compute_voting_weight_threshold(11)` returns `8` (`ceil(11*7/10) = ceil(7.7) = 8`) — this is what an actual block signature must reach to be valid on-chain. [1](#0-0) 
3. `GlobalStateEvaluator::reached_agreement(7)` on the same `total_weight = 11` returns `true` (`floor(11*7/10) = 7`, and `7 >= 7`). [3](#0-2) 
4. Thus a set of signers holding weight `7/11 ≈ 63.6%` — one unit short of the real 70% (`8/11 ≈ 72.7%`) supermajority — is enough to make `determine_global_state`/`determine_global_burn_view`/`determine_latest_supported_signer_protocol_version` report "agreement" on a `current_miner`, burn view, protocol version, or `tx_replay_set`, even though that same weight would be insufficient to actually get a block signed/approved by `verify_signer_signatures`.

```rust
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
```

```rust
            >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
```
