### Title
Missing zero-address check on `new_authority` in `transfer_to_new_account`/`transfer_to_new_account_pda` permanently locks the migrated account — ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
The account-authority-initiated migration instructions `transfer_to_new_account` and `transfer_to_new_account_pda` accept an arbitrary `new_authority` account with no validation that it is non-default, and use it directly as the authority of the newly created `MarginfiAccount`, while irreversibly disabling and zeroing the old account.

### Finding Description
Both `TransferToNewAccount` and `TransferToNewAccountPda` account structs mark `new_authority` as an `UncheckedAccount` with the explicit comment "WARN: New authority is completely unchecked": [1](#0-0) [2](#0-1) 

Neither `transfer_to_new_account` nor `transfer_to_new_account_pda` perform a `new_authority != Pubkey::default()` check before calling `initialize_migrated_account`, which sets the new account's `authority` field directly to `ctx.accounts.new_authority.key()`: [3](#0-2) [4](#0-3) 

Immediately after creating the new account, the old account is irreversibly finalized: its `lending_account` is zeroed, it is flagged `ACCOUNT_DISABLED`, and `migrated_to` is set to the new account, with an explicit guard preventing repeat migration (`AccountAlreadyMigrated`) — so this cannot be undone or retried once executed: [5](#0-4) [6](#0-5) 

This is analogous to the reported `setGov()` bug class: an address field that grants exclusive future control (here, the sole `authority` of the migrated `MarginfiAccount` and all its balances) can be set to the zero/default `Pubkey` with no on-chain guard, permanently locking out anyone from controlling the resulting account, since nobody holds the private key for `Pubkey::default()`.

Notably, the accompanying CLI helper `marginfi_account_transfer` in `p0-cli` performs this exact zero-address check client-side (`if new_authority == Pubkey::default() { bail!(...) }`), confirming the team is aware `Pubkey::default()` is an invalid/dangerous value for this field, but this protection only exists off-chain and is trivially bypassable by any direct/CPI caller of the instruction: [7](#0-6) 

### Impact Explanation
If a user (or a buggy/malicious CPI caller invoking `transfer_to_new_account_pda`, which is explicitly designed to be called via CPI per the third-party ID mechanism) supplies `new_authority = Pubkey::default()`, the newly created `MarginfiAccount` inherits the old account's entire `lending_account` (deposits/borrows) but is permanently uncontrollable — the `authority` signer check (`is_signer_authorized`) can never be satisfied since no keypair exists for the default pubkey, and the old account is simultaneously disabled with its balances zeroed out and irreversible `migrated_to` set. This results in a durable freeze of user funds with direct financial effect: the migrated collateral/liabilities become permanently inaccessible to any party.

### Likelihood Explanation
Likelihood is low-to-medium: the on-chain instruction is only reachable by the account's own current `authority` (self-authorized action, not attacker-controlled against a third party), so this is primarily a footgun rather than an attack vector against other users. However, since `transfer_to_new_account_pda` is explicitly designed to be invoked via CPI from third-party programs (using `third_party_id`), an integrating program with a bug (e.g., passing an uninitialized/zeroed pubkey accidentally) could trigger this without any user awareness, and there is no recovery path once triggered.

### Recommendation
Add an explicit on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` that `new_authority.key() != Pubkey::default()` (and ideally that it is not equal to the `System Program` or other known unusable addresses), returning a dedicated error (e.g., `MarginfiError::InvalidAuthority`) before finalizing the migration, mirroring the client-side check already present in `p0-cli`.

### Proof of Concept
1. Caller (holding valid `authority` signature for an existing `MarginfiAccount`) invokes `marginfi_account_transfer_to_new_account` (or the PDA/CPI variant `marginfi_account_transfer_to_new_account_pda`), passing `new_authority = Pubkey::default()` (`11111111111111111111111111111111`) instead of a real wallet.
2. On-chain, `TransferToNewAccount`/`TransferToNewAccountPda` accept this account without any constraint rejecting it, since `new_authority` is an `UncheckedAccount`.
3. `initialize_migrated_account` sets the new `MarginfiAccount.authority = Pubkey::default()`.
4. `finalize_migrated_old_account` disables the old account, zeroes its `lending_account`, and sets `migrated_to` to the new account — this step cannot be reverted (`AccountAlreadyMigrated` guard blocks re-migration).
5. All subsequent user instructions requiring `authority` signature on the new account fail `is_signer_authorized` permanently, since no private key exists for the default pubkey — the migrated collateral/liabilities are permanently frozen.

fn finalize_migrated_old_account(

    new_account_key: Pubkey,
