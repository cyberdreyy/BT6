### Title
`insertValidatedTransaction` RPC accepts arbitrary sender attribution without re-verifying the transaction signature - (File: crates/execution/txpool/src/builder/rpc.rs)

### Summary
The `base_insertValidatedTransaction` RPC method, implemented by `BuilderApiImpl::insert_validated_transaction`, builds a `Recovered` transaction using `Recovered::new_unchecked(consensus_tx, sender)` where `sender` is a caller-supplied field of the request body, not a value cryptographically derived from the transaction's own signature. [1](#0-0) 
The method's own doc comments confirm the design intent — this is meant to be reachable only by "the forwarding mempool node," which is trusted to have already verified the signature — but no caller-authentication or signature-verification logic is present in the handler itself. [2](#0-1) 

### Finding Description
This is structurally analogous to the Rubicon `offer`/`insert` bug: a function whose doc comments state it is "for keepers only" / "trusted from the forwarding mempool node," but which has no code-level access control enforcing that restriction — any caller who can reach the RPC endpoint can invoke it exactly as a trusted party would.

Concretely:
- `insert_validated_transaction` decodes the raw EIP-2718 bytes with `BaseTransactionSigned::decode_2718`, which only checks that the bytes form a structurally valid signed transaction (i.e., that `r`, `s`, `v` are present and RLP/typed-tx encoding is correct) — it does not require that the recovered ECDSA signer equals `tx.sender`. [3](#0-2) 
- The `sender` used for pool bookkeeping (nonce/balance charged to that account, ordering, inclusion) comes directly from the untrusted RPC payload via `Recovered::new_unchecked`, which — per its name — performs no signer/signature cross-check. [4](#0-3) 
- The resulting `BasePooledTransaction` is then fed straight into the pool via `add_external_transaction` (or `add_transaction` for the extension path), the same path used for regular pool admission. [5](#0-4) 
- The RPC method itself carries no authentication, IP allow-listing, or shared-secret check in the handler; it is registered as an ordinary jsonrpsee module (`base_insertValidatedTransaction`) via `BuilderApiExtension`/`add_rpc_module`. [6](#0-5) 

The comment on the trait explicitly documents the trust assumption being violated if this endpoint is exposed without a network-layer guard: "This handler decodes incoming pre-validated transactions and inserts them directly into the pool without re-validating signatures, since the sender addresses are trusted from the forwarding mempool node." [7](#0-6) 

### Impact Explanation
If this endpoint is reachable by an unauthenticated/anonymous RPC client (e.g., misconfiguration, exposure on a public interface, or compromise of a supposedly "trusted" forwarding peer), an attacker can submit a transaction whose claimed `sender` does not match the actual signer of `raw`. Because `Recovered::new_unchecked` bypasses signer/signature cross-validation at this layer, the pool would process the transaction as if it legitimately originated from the victim `sender` address (nonce consumption, ordering by that account's priority, potential inclusion in a built block attributed to that account). This is a direct analog of the Rubicon finding: a function intended only for a privileged, trusted caller lacks the code-level authorization enforcing that restriction, enabling manipulation of pool/orderbook-equivalent state (transaction admission and sender attribution) by an unauthorized party.

### Likelihood Explanation
Likelihood depends entirely on deployment/network topology that is not verifiable from the code: whether the `base_insertValidatedTransaction` module is exposed on a public-facing RPC/WS listener versus restricted to a private network segment only reachable by trusted mempool-forwarding nodes. I could not confirm from the available code whether any additional authentication middleware (mTLS, IP allow-list, shared secret) wraps this specific module in production configuration, nor whether `BaseTransactionValidator::validate_transaction`/pool admission independently re-derives and cross-checks the signer from the raw signature bytes as a second line of defense — I was unable to fully inspect `crates/execution/txpool/src/validator.rs` for this specific check within the available iterations. If such a second signer-check exists downstream, exploitability would be reduced to a benign no-op rejection; if not, and if the endpoint is network-reachable, this is directly exploitable.

### Recommendation
- Verify and document that `base_insertValidatedTransaction` is never exposed on a listener reachable by untrusted callers; enforce this with in-process authentication (mutual TLS, shared secret, or IP allow-list) rather than relying solely on external network configuration.
- Add a defense-in-depth check in `insert_validated_transaction` (or in the pool validator invoked downstream) that recovers the actual signer from the decoded transaction's signature and rejects the request if it does not match the caller-supplied `sender`, removing the implicit trust assumption from the RPC boundary itself.
- Add golden/system tests asserting that a `ValidatedTransaction` with a `sender` that does not match the transaction's actual ECDSA signer is rejected, mirroring the existing decode-error test suite in `crates/execution/txpool/src/builder/rpc.rs`.

### Proof of Concept
Not independently executable from the indexed code alone — a full PoC would require reproducing a running builder node with `BuilderApiExtension` enabled and probing whether `base_insertValidatedTransaction` is reachable without network-layer authentication, then submitting a `ValidatedTransaction { sender: <victim>, raw: <structurally-valid signed tx signed by an unrelated key>, extensions: NoExtensions }` via JSON-RPC and observing whether the pool accepts it under the victim's account, per the code path shown in [8](#0-7) .

    async fn insert_validated_transaction(&self, tx: ValidatedTransaction<E>) -> RpcResult<()> {
        debug!(
            sender = %tx.sender,
            "rpc::insert_validated_transaction"
        );
        let sender = tx.sender;
        let has_extensions = !tx.extensions.is_empty();

        if has_extensions && !self.accept_extensions {
            BuilderApiMetrics::extension_errors().increment(1);
            return Err(ErrorObjectOwned::owned(
                ErrorCode::InvalidParams.code(),
                "transaction extensions are disabled",
                None::<()>,
            ));
        }

        tx.extensions.validate(self.max_extension_items).map_err(|e| {
            BuilderApiMetrics::extension_errors().increment(1);
            ErrorObjectOwned::owned(ErrorCode::InvalidParams.code(), e.to_string(), None::<()>)
        })?;

        // Decode the EIP-2718 transaction bytes
        let consensus_tx =
            BaseTransactionSigned::decode_2718(&mut tx.raw.as_ref()).map_err(|e| {
                BuilderApiMetrics::decode_errors().increment(1);
                ErrorObjectOwned::owned(
                    ErrorCode::InvalidParams.code(),
                    format!("failed to decode transaction: {e}"),
                    None::<()>,
                )
            })?;
        let tx_hash = *consensus_tx.hash();
        let encoded_len = tx.raw.len();

        let recovered = Recovered::new_unchecked(consensus_tx, sender);
        let pool_tx = BasePooledTransaction::new(recovered, encoded_len);

        // Attach any extension data carried on the wire. This is a no-op for
        // `NoExtensions`, the default payload.
        let pool_tx = tx.extensions.apply(pool_tx).map_err(|e| {
            BuilderApiMetrics::extension_errors().increment(1);
            ErrorObjectOwned::owned(ErrorCode::InvalidParams.code(), e.to_string(), None::<()>)
        })?;

        // Extension-bearing transactions remain private so normal P2P gossip
        // cannot propagate the raw transaction without its extension metadata.
        let start = Instant::now();
        let result = if has_extensions {
            self.pool.add_transaction(TransactionOrigin::Private, pool_tx).await
        } else {
            self.pool.add_external_transaction(pool_tx).await
        };
        BuilderApiMetrics::insert_duration().record(start.elapsed().as_secs_f64());

/// Extension that registers the Builder API RPC module (`base_insertValidatedTransaction`).
///
/// Its configuration controls validity metadata acceptance, predicate limits, and shadow-only
/// validity injection. Ordinary validated transactions remain available in all modes.
#[derive(Debug, Default)]
pub struct BuilderApiExtension {
    config: BuilderApiExtensionConfig,
}

impl BaseNodeExtension for BuilderApiExtension {
    fn apply(self: Box<Self>, builder: NodeHooks) -> NodeHooks {
        let config = self.config;
        builder.add_rpc_module(move |ctx: &mut BaseRpcContext<'_>| {
            let api = ShadowValidityBuilderApi::new(ctx.pool().clone(), config);
            ctx.modules.merge_configured(api.into_rpc())?;
            Ok(())
        })
    }
}
