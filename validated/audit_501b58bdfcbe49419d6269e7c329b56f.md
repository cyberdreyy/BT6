### Title
Reorg-permit gate counts only globally-accepted blocks, letting a miner reorg away a tenure the signer already locally endorsed with multiple signatures — ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` in `stacks-signer/src/chainstate/mod.rs` decides whether a new miner is allowed to reorg away a prior tenure. Its own comment says the intent is to "disallow reorg if more than one block has already been **signed**", but the code only counts **globally accepted** blocks via `get_globally_accepted_block_count_in_tenure`, not blocks this signer has locally accepted/signed (`signed_self`/`signed_group`). Everywhere else in this codebase (`get_signed_conflicts`, `get_last_signed_block`, `get_tenure_last_block_info`) "signed" explicitly means "locally OR globally accepted," because a block only reaches the node once the whole signer set has signed it — so a multiply-signed-but-not-yet-globally-accepted tenure is a completely normal, expected state, not an edge case. This one check uses the narrower, wrong predicate. [1](#0-0) 

### Finding Description
`check_parent_tenure_choice` is called from both `SortitionsView::check_proposal` (v1) and `GlobalStateView::check_proposal` (v2) whenever a miner's tenure does not build directly off the prior sortition, i.e. whenever a *reorg* of one or more tenures is being proposed: [2](#0-1) 

For each reorged tenure it is supposed to refuse the reorg outright if the tenure already accumulated more than one signed block — this is the "already-signed" hard gate the comment describes. But the implementation queries only:

```
let globally_accepted_blocks =
    signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)?;
if globally_accepted_blocks > 1 { return Ok(false); }
```

A block only becomes globally accepted once the *entire* signer set's signatures are gathered and handed to (and confirmed by) the node — see `docs/signer-flows.md` section on lifecycle: "Global acceptance is never derived from counting signatures … it is marked … when the node announces the block." [3](#0-2)  Meanwhile a signer's *own* signature (`LocallyAccepted`/`signed_self`) or an observed group threshold (`signed_group`) is placed well before that, at the pre-commit→signature step: [4](#0-3) 

So it is entirely reachable, with no majority collusion and only the normal one-slot-miner + gossip flow, for a tenure to have two or more blocks that are `LocallyAccepted`/`signed_group` (this signer, and/or the group, already signed two heights in that tenure) while `get_globally_accepted_block_count_in_tenure` still returns 0 or 1 — e.g. because the node hasn't yet been handed the aggregated signature set, or a Bitcoin/tenure timing gap delayed the `NewBlock` announcement that flips state to `GloballyAccepted`. `check_parent_tenure_choice`'s "> 1" gate then fails to trip, and execution falls through to the softer, timing-based branch below (`get_first_approved_block_in_tenure` + `first_proposal_burn_block_timing`), which can and will return `true` (reorg allowed) for a tenure that this exact codebase's own invariant ("more than one signed block ⇒ never reorg") says must be refused.

This directly breaks the "approved-parent vs canonical" equality this scan targets: `check_parent_tenure_choice` returning `true` here feeds straight into `check_proposal` accepting the new tenure-change block as valid, `record_superseded_tenure`/`mark_tenure_superseded` marking the abandoned tenure's conflicts as excluded (`reorg_permit_stands`), and the pre-commit conflict guard in `handle_block_pre_commit` (`reorg_permit_stands` check) explicitly *stops treating the old, already twice-signed tenure as a conflict* — see the signing path: [5](#0-4)  The signer then goes on to sign the replacement block over a tenure it had already committed two signatures to, i.e. it signs a block that conflicts with two blocks it previously endorsed — a real equivocation, sanctioned by a check whose own comment says it should have been vetoed.

### Impact Explanation
This is Critical per the scan's rubric: it lets a signer, driven purely by a single miner's proposal sequencing (no majority collusion, no stolen keys), end up signing a block that conflicts with (reorgs away) a tenure it already signed *more than one* block for — the exact case `check_parent_tenure_choice`'s own comment says must never be permitted. It is a genuine "incomplete list of disallowed inputs": the check that is supposed to disallow all "already-signed" tenures instead only disallows the "already globally-accepted" subset, exactly mirroring the Jenkins CVE's pattern of an incomplete blacklist letting disallowed inputs (here, already-multiply-signed tenures) slip through.

### Likelihood Explanation
Reaching the mismatch does not require a majority or adversarial signer collaboration: it only requires that global acceptance (which depends on all signatures being gathered *and* the node processing/announcing the block) lags behind local/group signing, which is a routine timing gap (network latency between StackerDB gossip and the node's `/v3/block_proposal` push, or a tenure-timeout race), not a rare or contrived condition. The rest of the chain (accepting `check_proposal`, `record_superseded_tenure`, `reorg_permit_stands` excluding the conflict, and the pre-commit guard skipping it) is deterministic once the miscount happens.

### Recommendation
Change `check_parent_tenure_choice`'s gate to count blocks that are signed in the sense used consistently elsewhere in this module (`signed_self.is_some() || signed_group.is_some()`, i.e. whatever `get_signed_conflicts`/`get_last_signed_block` treat as "signed"), not merely `GloballyAccepted`. Concretely, replace `get_globally_accepted_block_count_in_tenure` with a query that counts blocks in the tenure with `state IN (LocallyAccepted, GloballyAccepted)` (or `signed_self`/`signed_group` set), matching the invariant stated in the surrounding comment.

### Proof of Concept
1. Signer set signs block B1 in tenure T (reaches pre-commit threshold, everyone calls `mark_locally_accepted`); `signed_self`/`signed_group` are set for B1, but the node has not yet been handed the aggregated signature set (or hasn't processed/announced it), so B1 is not yet `GloballyAccepted`.
2. Before the node catches up, the same or next-turn miner proposes B2, also in tenure T at a higher height, and it too reaches the pre-commit/sign threshold the same way — now tenure T has two signed (but not globally-accepted) blocks.
3. A subsequent miner proposes a tenure-change block whose `prev_tenure_consensus_hash` reorgs *past* T (skips it). `check_parent_tenure_choice` is invoked for T: `get_globally_accepted_block_count_in_tenure(T)` returns 0 (neither B1 nor B2 is globally accepted yet), so the `> 1` gate does not trip.
4. Execution falls into the timing-based branch using `get_first_approved_block_in_tenure`/`first_proposal_burn_block_timing`; depending on timing it can return `true`, permitting the reorg and calling `record_superseded_tenure` for T.
5. The pre-commit guard's `reorg_permit_stands` then excludes B1/B2 as conflicts, and the signer proceeds to sign the new tenure-change block — producing a signature set that conflicts with two blocks it previously signed in T, which the code's own stated invariant ("more than one signed block ⇒ refuse reorg") was meant to prevent.

                );
