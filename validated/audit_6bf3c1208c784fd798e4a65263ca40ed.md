Let me analyze the external bug's root cause and search for a Sui analog. The core issue is: tokens are taken from a user upfront, a swap/order may be **partially filled**, and the unused portion is never returned to the user.

### Title
Bridge Decimal Truncation Permanently Locks User ETH in EVM Vault Without Refund - (`bridge/evm/contracts/SuiBridge.sol`, `bridge/evm/contracts/utils/BridgeUtils.sol`)

---

### Summary

`bridgeERC20` and `bridgeETH` in `SuiBridge.sol` (and `SuiBridgeV2.sol`) transfer the user's full token amount into the vault first, then convert it to Sui-decimal precision via integer division in `BridgeUtils.convertERC20ToSuiDecimal`. The truncated remainder — `amount % factor` — is permanently locked in the vault. No refund path exists. This is the structural analog of M-1: tokens are taken from the user upfront, the downstream operation processes only a portion of them, and the unused portion is never returned.

---

### Finding Description

`BridgeUtils.convertERC20ToSuiDecimal` performs integer division:

```solidity
// bridge/evm/contracts/utils/BridgeUtils.sol L141-142
uint256 factor = 10 ** (erc20Decimal - suiDecimal);
amount = amount / factor;
```

For ETH (18 EVM decimals → 8 Sui decimals), `factor = 10^10`. Any `amount` whose low 10 decimal digits are non-zero loses `amount % 10^10` wei permanently.

The deposit path in `bridgeETH`:

```solidity
// bridge/evm/contracts/SuiBridge.sol L210-221
(bool success,) = payable(address(vault)).call{value: amount}("");   // full amount locked
...
uint64 suiAdjustedAmount = BridgeUtils.convertERC20ToSuiDecimal(
    IERC20Metadata(config.tokenAddressOf(BridgeUtils.ETH)).decimals(),
    config.tokenSuiDecimalOf(BridgeUtils.ETH),
    amount                                                            // truncated here
);
emit TokensDeposited(..., suiAdjustedAmount, ...);                    // only truncated amount recorded
```

The vault receives `amount` wei; the bridge message records only `(amount / 10^10) * 10^10` wei worth of Sui-side tokens. The remainder `amount % 10^10` (up to 9,999,999,999 wei ≈ 10 gwei per transaction) is locked in the vault with no claim mechanism. The same pattern appears in `bridgeERC20` and their V2 counterparts.

The `require(amount > 0, ...)` guard fires **after** the division, so it only ensures the truncated result is non-zero — it does not prevent the remainder from being silently discarded.

---

### Impact Explanation

Every ETH bridge deposit whose `msg.value` is not an exact multiple of `10^10` wei permanently loses up to 9,999,999,999 wei in the EVM vault. The vault has no sweep or refund function accessible to users; only privileged governance can drain it. From the unprivileged-user model, the remainder is an irrecoverable permanent fund lock. Across many deposits the aggregate loss grows unboundedly.

---

### Likelihood Explanation

Any ordinary ETH holder calling `bridgeETH` with a non-round amount (e.g., any amount specified in gwei rather than in units of 10 gwei) triggers the loss. No special access or adversarial setup is required — the loss is automatic and silent on every such deposit.

---

### Recommendation

Before transferring ETH/ERC20 to the vault, compute the truncated amount and either:
1. **Refund the remainder** to `msg.sender` before locking, or
2. **Require the input to be an exact multiple of `factor`** (revert if `amount % factor != 0`).

Example for `bridgeETH`:
```solidity
uint256 factor = 10 ** (erc20Decimal - suiDecimal);
uint256 remainder = amount % factor;
uint256 bridgeable = amount - remainder;
require(bridgeable > 0, "SuiBridge: Amount too small");
// refund remainder
if (remainder > 0) {
    (bool refunded,) = payable(msg.sender).call{value: remainder}("");
    require(refunded, "SuiBridge: Refund failed");
}
// send only bridgeable to vault
(bool success,) = payable(address(vault)).call{value: bridgeable}("");
```

---

### Proof of Concept

1. Alice calls `bridgeETH{value: 1_000_000_000_001}(recipientBytes, destChain)` — 1 ETH + 1 wei.
2. `vault` receives `1_000_000_000_001` wei (full amount).
3. `convertERC20ToSuiDecimal(18, 8, 1_000_000_000_001)`:
   - `factor = 10^10`
   - `amount = 1_000_000_000_001 / 10^10 = 100` (in 8-decimal Sui units = 0.000001 ETH)
   - `1` wei remainder is silently discarded.
4. `TokensDeposited` emits `suiAdjustedAmount = 100`.
5. On Sui, Alice receives tokens worth `100 * 10^10 = 1_000_000_000_000` wei — the 1 wei remainder is permanently locked in the EVM vault.
6. Scaled to `amount = 10 ETH + 9_999_999_999 wei`: Alice loses `9_999_999_999` wei ≈ 10 gwei per call, with no recovery path.

    function convertERC20ToSuiDecimal(uint8 erc20Decimal, uint8 suiDecimal, uint256 amount)
        internal
        pure
        returns (uint64)
    {
        if (erc20Decimal == suiDecimal) {
            // ensure provided amount is greater than 0
            require(amount > 0, "BridgeUtils: Insufficient amount provided");
            // Ensure converted amount fits within uint64
            require(amount <= type(uint64).max, "BridgeUtils: Amount too large for uint64");
            return uint64(amount);
        }

        require(erc20Decimal > suiDecimal, "BridgeUtils: Invalid Sui decimal");

        // Difference in decimal places
        uint256 factor = 10 ** (erc20Decimal - suiDecimal);
        amount = amount / factor;

        // Ensure the converted amount fits within uint64
        require(amount <= type(uint64).max, "BridgeUtils: Amount too large for uint64");

        // Ensure the converted amount is greater than 0
        require(amount > 0, "BridgeUtils: Insufficient amount provided");

        return uint64(amount);
    }
