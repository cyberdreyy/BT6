### Title
Mid-epoch deposits increment `epochNumber`, breaking per-epoch claim uniqueness — premature withdraw claims and orphaned instant receipts - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The external bug is a "unique-per-operation nonce" violation: OpenSSL accepts nonces longer than 12 bytes but silently ignores the extra leading bytes, so an application that expects a different nonce to imply a fresh encryption unknowingly reuses the effective nonce and breaks the uniqueness guarantee. The analog in this codebase is `epochNumber` in `IdleCreditVault`. It is used as the unique identifier binding every withdraw receipt to "its" epoch (`lastWithdrawRequest`, `withdrawsRequestsByEpoch`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, `apr0RateByEpoch`, `lossRecoveryPriceByEpoch`, `defaultRecoveryEpoch`), under the assumption that it changes exactly once per epoch boundary — at `stopEpoch`. In reality `deposit()` increments it on *every* CDO deposit while `isEpochRunning()` is true, so the same logical epoch can span many counter values and distinct logical epochs' keys fragment. Two exploitable consequences follow: the "wait one epoch" gate in `_claimFundedWithdrawRequest` can be bypassed, and instant-withdraw receipts recorded under a pre-bump counter value are excluded from `defaultPendingClaimBasis` / `_claimDefaultedInstantWithdrawRequest`, permanently freezing them while inflating `defaultRecoveryPrice` for everyone else.

### Finding Description
`IdleCreditVault.deposit()` is invoked by `IdleCDOCreditVault._deposit` on every user deposit (`IIdleCDOStrategy(strategy).deposit(_amount)` in `contracts/IdleCDOCreditVault.sol:211`). While an epoch is running, each such call executes `epochNumber += 1` (`contracts/strategies/idle/IdleCreditVault.sol:607-611`). The counter is therefore not unique per epoch — it is per-deposit — yet the entire claim state machine treats it as an epoch-scoped nonce:

- Wait gate: `_claimFundedWithdrawRequest` reverts only while `epochNumber <= lastWithdrawRequest[_user]` (`IdleCreditVault.sol:326-328`). Any deposit by anyone mid-epoch bumps `epochNumber` past the requester's recorded epoch, so a withdraw requested *this same epoch* becomes immediately claimable, before `stopEpoch`/`collectWithdrawFunds` ever funds `pendingWithdraws`. The claim then burns the user's receipt tokens and calls `_transferFundedClaim`, which pays out of strategy-held underlyings — i.e. cash prefunded for instant-withdraw claimants or other funded balances — that was never earmarked for this receipt. This is a direct theft of the instant-withdraw queue's funding (or insolvency if the balance is short, which additionally bricks all subsequent funded claims since the burn already happened atomically in the same path — reverts aside, where balance exists the payout succeeds).
- Default-path orphaning: `defaultPendingClaimBasis()` adds only `instantWithdrawClaimsByEpoch[epochNumber]` (`IdleCreditVault.sol:644-649`), and `finalizeDefaultRecovery` snapshots `defaultRecoveryEpoch = epochNumber` (`:693`). If an instant receipt was recorded at counter value N and a mid-epoch deposit moved the counter to N+1 before default, the receipt's basis is dropped from `totalBasis` — inflating `recoveryPrice` so remaining claimants overdraw the reserve — while `_claimDefaultedInstantWithdrawRequest` looks up `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (`:843-844`), finds 0, and never clears the user's `instantWithdrawsRequests[_user]` / `pendingInstantWithdraws`. The receipt is permanently unclaimable (request can't be re-opened either: `requestWithdraw` reverts on `instantWithdrawsRequests[_user] != 0` post-default at `:249`).
- Loss-adjusted path: `collectWithdrawFunds` stores haircuts under `lossRecoveryPriceByEpoch[epochNumber]` (`:421`) and `requestWithdraw`/`_claimLossAdjustedWithdrawRequest` key lookups via `lastWithdrawRequest[_user]` (`:261-271`, `:790-794`). Because the recorded "epoch" is just whatever the deposit counter happened to be at request time, the guard that forces claiming a loss-adjusted receipt before opening a new one (`:263-271`) compares the request marker to a haircut keyed under the *post-deposit* counter, so a legitimate haircut receipt can be shadowed (never claimed) or a marker mismatch can let a second request proceed against a receipt whose haircut lives under a different key — either way receipts and funding diverge.

None of the existing guards stop this: `_onlyIdleCDO` is satisfied because deposits legitimately come through the CDO; the skim/`_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve`, not the instant-withdraw prefunding; and no check requires `epochNumber` to advance only at `stopEpoch`.

### Impact Explanation
- **Direct theft**: an unprivileged user requests a withdraw, any deposit (by them or anyone) mid-epoch bumps `epochNumber`, and `claimWithdrawRequest` pays out at par immediately from strategy-held underlyings belonging to instant-withdraw claimants, without waiting for borrower funding. Loss = the strategy's funded balance up to the claim amount.
- **Permanent freezing**: instant-withdraw receipt holders whose request epoch predates the last mid-epoch deposit counter can never claim after default finalization; their `instantWithdrawsRequests`/`pendingInstantWithdraws` entries are stuck forever.
- **Insolvency/overpayment**: excluded instant basis inflates `defaultRecoveryPrice`, so remaining claimants can extract more than the recovered amount's fair share, draining the reserve before earlier-in-time claimants.

### Likelihood Explanation
Triggering requires only an ordinary mid-epoch deposit by any KYC'd lender (the CDO calls `strategy.deposit` on every deposit while `isEpochRunning()`), which is routine vault activity, plus a withdraw request in the same epoch. No privileged cooperation is needed; the attacker can be the depositor or simply benefit from any third party's deposit.

### Recommendation
Decouple the receipt-epoch nonce from deposit counting: increment `epochNumber` only inside the `stopEpoch` path (e.g., gate the increment on the actual epoch-transition call rather than `isEpochRunning()` inside `deposit()`), or maintain a separate `depositCounter` for `totEpochDeposits` semantics. Add an invariant test: for any sequence of mid-epoch deposits, `lastWithdrawRequest` epochs must remain claimable only after a real `stopEpoch`, and `instantWithdrawClaimsByEpoch` must remain consistent with `pendingInstantWithdraws` across default finalization.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` setup):

```solidity
// Setup: vault with borrower, epoch started (isEpochRunning == true),
// CDO holds strategy tokens, strategy holds underlying prefunded for instant claims.

// 1. Victim requests instant withdraw during epoch (epochNumber == E).
cdo.requestInstantWithdraw(amountV);          // instantWithdrawsRequestsByEpoch[V][E] = amountV

// 2. Attacker (or any lender) deposits mid-epoch via CDO.
idleToken.approve(address(cdo), amountA);
cdo.depositAA(amountA);                        // -> strategy.deposit -> epochNumber becomes E+1

// 3a. THEFT VARIANT: attacker requested a normal withdraw at epoch E.
//     claimWithdrawRequest no longer reverts because epochNumber (E+1) > lastWithdrawRequest (E);
//     _transferFundedClaim pays from strategy balance never funded for this receipt.
cdo.claimWithdrawRequest(attacker);            // pays funded instant-queue cash to attacker

// 3b. FREEZE VARIANT: borrower defaults; owner calls _handleBorrowerDefault /
//     finalizeDefaultRecovery. defaultRecoveryEpoch == E+1.
//     defaultPendingClaimBasis() omits instantWithdrawClaimsByEpoch[E];
//     victim's claimDefaultedInstantWithdrawRequest reads epoch E+1 -> 0.
//     victim.instantWithdrawsRequests stays >0 forever; cannot request or claim.
assertGt(creditVault.instantWithdrawsRequests(victim), 0);
vm.expectRevert(); // or returns 0 — receipt permanently stranded
cdo.claimInstantWithdrawRequest(victim);
```

Note: I could not fully trace `IdleCDOEpochVariant.stopEpoch`/`_handleBorrowerDefault` call ordering within this pass; the PoC hinges on `deposit()` incrementing `epochNumber` while `isEpochRunning()` (`IdleCreditVault.sol:607-611`), which is directly verified in the source above.
