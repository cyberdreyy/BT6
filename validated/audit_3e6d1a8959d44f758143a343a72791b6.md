### Title
Fee-on-transfer underlying leaves withdrawal receipts underfunded and unclaimable - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`IdleCreditVault.collectWithdrawFunds` clears `pendingWithdraws` using the requested gross amount, but credits the vault with only the net amount actually received from `IdleCDO`. If the configured underlying token charges a transfer fee, funded withdrawal receipts become internally marked as funded while the vault lacks enough underlying to pay them. Later claims can underpay or revert, leaving recipients' funds frozen or lost to the transfer-fee sink.

### Finding Description

`IdleCreditVault` accepts an arbitrary ERC20 underlying at initialization and does not exclude tokens with transfer fees. [1](#0-0) 

When a borrower repayment has been pulled into `IdleCDO`, `collectWithdrawFunds(_amount)` treats `_amount` as fully funded and either clears the entire pending basis or reduces it by `_amount`. [2](#0-1) 

The vault then performs `underlyingToken.safeTransferFrom(idleCDO, address(this), _amount)` without measuring the balance delta. [3](#0-2) 

For a token with a fee `f`, the strategy receives `_amount - f`, while `pendingWithdraws` is reduced by `_amount`. Claims later calculate the nominal receipt amount and attempt to pay it through `_transferFundedClaim`. [4](#0-3) 

The same mismatch exists in `collectInstantWithdrawFunds`: `pendingInstantWithdraws` is reduced by the gross `_amount`, but only the net amount reaches the strategy. [5](#0-4) 

This is especially relevant if a currently feeless supported token introduces a fee later, because already-created pools cannot change their configured underlying.

### Impact Explanation

A funded withdrawal receipt is not actually fully funded.

For example, with pending withdrawals of `P` and a transfer fee `f`:

1. `collectWithdrawFunds(P)` clears or reduces the receipt basis by `P`.
2. The strategy receives only `P - f`.
3. A user claiming `P` triggers a transfer of the nominal claim amount.
4. The claim reverts if the vault's net balance is insufficient, or the recipient receives less than the receipt amount because the outbound transfer also charges a fee.

With multiple receipts, earlier claimants can consume the available balance while the final claimant is permanently underfunded unless additional assets are supplied. The loss is at least the collection transfer fee, plus any outbound transfer fees burned from recipient payouts.

### Likelihood Explanation

The vulnerability requires the credit vault's underlying token to charge a fee on transfer. The code permits arbitrary underlying tokens and contains no fee-on-transfer detection or net-received accounting.

A vault using a token that later enables transfer fees can transition into this state without any privileged misconduct: the honest borrower approves and repays the expected gross amount, the honest manager stops the epoch, and ordinary KYC-passing lenders then claim receipts whose aggregate basis exceeds the strategy's actual balance.

### Recommendation

Account for all inbound underlying transfers by balance delta rather than requested amount.

In `collectWithdrawFunds` and `collectInstantWithdrawFunds`, record the strategy balance before `safeTransferFrom`, then reduce pending accounting only by `balanceAfter - balanceBefore`. If the intended design does not support fee-on-transfer assets, explicitly reject or avoid enabling such tokens at vault initialization.

For full robustness, apply the same net-received accounting to every path that pulls underlying, including `deposit`, borrower repayments, recovery funding, and `depositDuringEpoch`. `depositDuringEpoch` currently pulls `_amount` but mints shares, mints strategy tokens, updates expected interest, and sends `_amount` to the borrower without using the actual received amount. [6](#0-5) 

### Proof of Concept

A reproducible Foundry scenario can use a fork test with an ERC20 whose transfer fee can be enabled after pool funding:

```solidity
function testFeeOnTransferWithdrawReceiptInsolvency() public {
    // 1. Configure FeeToken with fee = 0.
    // 2. Initialize IdleCDOEpochVariant and IdleCreditVault with FeeToken.
    // 3. Alice deposits 10_000 tokens through depositAA.
    // 4. Manager starts the epoch; the borrower receives the deposit.

    uint256 pending = 10_000e18;
    uint256 interest = 100e18;

    // 5. Alice requests a withdrawal for `pending`.
    // 6. Enable a transfer fee, for example 1 token burned per transfer.
    feeToken.setTransferFee(1e18);

    // 7. Borrower honestly approves and repays pending + interest.
    vm.prank(borrower);
    feeToken.approve(address(cdo), pending + interest);
    vm.warp(cdo.epochEndDate() + 1);
    vm.prank(manager);
    cdo.stopEpoch(newApr, 0);

    // 8. IdleCreditVault marked `pending` funded, but received pending - 1e18.
    assertEq(creditVault.pendingWithdraws(), 0);
    assertEq(feeToken.balanceOf(address(creditVault)), pending - 1e18);

    // 9. Alice's funded receipt now cannot be paid in full.
    vm.expectRevert();
    cdo.claimWithdrawRequest();
}
```

The key broken invariant is that zero `pendingWithdraws` no longer means the strategy holds enough underlying to satisfy those receipts.

    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
