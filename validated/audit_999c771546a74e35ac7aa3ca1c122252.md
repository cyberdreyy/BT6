### Title
Stale confirmations from a deleted multisig member remain counted toward the confirmation threshold, allowing a request to execute below the live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` removes a member from `self.members` and deletes any *requests originated by* that member, but it never purges that member's existing *confirmations* recorded on other, still-open requests. Because `confirm()` counts entries in the `confirmations` set (which can contain a member that has since been deleted) against `num_confirmations`, a request can be executed with fewer live, currently-authorized confirmations than the configured threshold `K`.

### Finding Description
`confirm()` decides to execute a request purely by comparing the size of the stored `confirmations: HashSet<Member>` for a `request_id` against `self.num_confirmations`: [1](#0-0) 

`delete_member()` enforces that the *count* of remaining members stays at or above `num_confirmations`, and cleans up requests *created by* the removed member and its `num_requests_pk` entry, but it does not scan the `confirmations` map to strip the removed member's public key/account id from confirmation sets belonging to other pending requests: [2](#0-1) 

Concretely, with `K`-of-`N` set to 3-of-5 (members A, B, C, D, E):
1. Member C creates request `R` (e.g. a `Transfer`). Confirmations = `{}`.
2. Member A confirms `R` → confirmations = `{A}`.
3. Member B confirms `R` → confirmations = `{A, B}` (2 < 3, not yet executed).
4. Members remove A via a separate, properly-confirmed `DeleteMember{A}` request. `self.members` now = `{B, C, D, E}`, still ≥ `num_confirmations` (3), so the removal succeeds. `R`'s confirmation set is untouched and still contains `A`.
5. Member C confirms `R` → confirmations = `{A, B, C}`, size 3 ≥ `num_confirmations` (3) → `execute_request(R)` runs and the transfer is sent.

At execution time, only B and C are actual live members confirming `R`; A's confirmation is stale (A is no longer a member and cannot re-derive that signature/authorization at that point). The binding that should hold is:

`live confirmations on request == confirmations counted toward num_confirmations`

but instead the contract allows:

`confirmations counted (including deleted members) >= num_confirmations` while `live confirmations < num_confirmations`.

This breaks the "confirmations counted versus live members" custody boundary explicitly called out as in-scope, and directly mirrors the external report's bug class: an action (deleting a member) changes the "safety"/validity state of an in-flight request without that request being re-evaluated against the new authorization set, letting execution proceed on a technicality rather than genuine live authorization.

### Impact Explanation
This allows a `MultiSigRequestAction::Transfer`, `AddKey`, `FunctionCall`, `DeployContract`, etc. to be executed with fewer live confirmations than the configured `K` threshold, i.e. "a multisig request executed below threshold" — explicitly listed as a Critical impact. Funds (NEAR) can move, or a full-access/limited key can be added to the account, when the number of *currently valid* confirming members is below the intended security threshold. This is exploitable purely through normal contract calls (`add_request`, `confirm`, `delete_member`) without needing owner/foundation privileges beyond being a legitimate multisig member acting within the normal K-of-N workflow — no redeploy, no victim key theft, no social engineering required.

### Likelihood Explanation
The bug requires: (a) a pending request with partial confirmations, (b) one of the confirming members later being removed via a legitimate `DeleteMember` action, and (c) the removed member's stale confirmation persisting until enough additional confirmations push the count over `num_confirmations`. This is not an exotic sequence — member turnover on a multisig (e.g., an employee leaving, a compromised key rotation) combined with any pending request is a realistic operational occurrence, and nothing in the contract prevents or warns about it. Likelihood is moderate-to-high in any multisig with member churn and concurrently open requests.

### Recommendation
When deleting a member in `delete_member`, iterate `self.confirmations` and remove the deleted member's key/account id from every request's confirmation set (not just delete requests it authored), so stale confirmations can never count toward the threshold. Alternatively, re-validate at `confirm()`/execution time that every account/key in the confirmation set is still a current member before counting it, discarding stale entries and re-checking the size against `num_confirmations`.

### Proof of Concept
Conceptual reproduction using the existing multisig2 unit test harness (`multisig2/src/lib.rs` test module, e.g. following the pattern in `test_multi_3_of_n`):
1. `let mut c = MultiSigContract::new(members_A_B_C_D_E, 3);`
2. As C: `let request_id = c.add_request(transfer_request);`
3. As A: `c.confirm(request_id);` → confirmations `{A}`.
4. As B: `c.confirm(request_id);` → confirmations `{A, B}`.
5. Execute a separate fully-confirmed `DeleteMember{A}` request (3 confirmations from B, C, D) → `c.members` no longer contains A; `c.confirmations.get(&request_id)` still returns `{A, B}` (unchanged).
6. As C: `c.confirm(request_id)` → set becomes `{A, B, C}`, size 3 == `num_confirmations` → `execute_request` fires and the transfer promise is scheduled, even though only B and C are live members who confirmed — one fewer live confirmation than the 3 required. [1](#0-0) [2](#0-1)

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
