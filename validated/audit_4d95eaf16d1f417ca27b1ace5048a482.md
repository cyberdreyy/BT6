### Title
External Initiator authentication does not honor `ExternalInitiatorsEnabled=false`, allowing disabled initiators to keep triggering job runs - (File: `core/web/auth/auth.go`)

### Summary
The `ExternalInitiatorsEnabled` config flag is intended to globally gate the External Initiator (EI) feature, but it is checked only when creating a new EI record, not when authenticating and using an existing one to trigger job runs.

### Finding Description
`ExternalInitiatorsController.Create` enforces the feature flag before allowing a new EI to be registered: [1](#0-0) 

However, the middleware that authenticates and authorizes an EI request, `AuthenticateExternalInitiator`, performs only a credential comparison via `store.FindExternalInitiator` and `bridges.AuthenticateExternalInitiator` — it never re-checks `JobPipeline().ExternalInitiatorsEnabled()`: [2](#0-1) 

This middleware is wired directly into the run-triggering route: [3](#0-2) 

So any EI credential minted while the feature was enabled continues to authenticate successfully and is granted `UserRoleRun`, allowing it to call `POST /v2/jobs/:ID/runs` (via `auth.RequiresRunRole(prc.Create)`), even after an operator disables the feature by setting `ExternalInitiatorsEnabled = false`. Just as the `stETH` report flags a missing `isStopped()` check before allowing a transfer to proceed, Chainlink is missing an equivalent "feature disabled" check before allowing an EI-authenticated request to proceed.

### Impact Explanation
An operator who disables `ExternalInitiatorsEnabled` (e.g., in response to a security incident, believing it revokes all EI access) does not actually revoke the ability of previously-created, unprivileged remote initiators to authenticate and trigger job runs via `/v2/jobs/:ID/runs`. This is a control-bypass: the configuration toggle intended to disable a whole unprivileged-facing attack surface silently fails to do so for already-issued credentials, unless those credentials are also explicitly deleted via `DELETE /v2/external_initiators/:Name`.

### Likelihood Explanation
Any deployment that has ever created an External Initiator and later disables the feature (via config change) remains exposed — no special conditions are required beyond possession of a previously-issued, still-undeleted EI `AccessKey`/`Secret` pair.

### Recommendation
Add a check for `JobPipeline().ExternalInitiatorsEnabled()` inside `AuthenticateExternalInitiator` in `core/web/auth/auth.go`, returning `auth.ErrorAuthFailed` (or a dedicated disabled error) when the feature flag is off, so that disabling the flag immediately revokes all EI-based authentication regardless of previously issued credentials.

### Proof of Concept
1. Enable `JobPipeline.ExternalInitiatorsEnabled = true` and create an External Initiator via `POST /v2/external_initiators`, obtaining `AccessKey`/`Secret`.
2. Set `JobPipeline.ExternalInitiatorsEnabled = false` and restart/reload the node config (no deletion of the EI record).
3. Send `POST /v2/jobs/:ID/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to the previously issued credentials, as in `TestTokenAuthRequired_TokenCredentials` [4](#0-3) .
4. Observe the request succeeds (`200 OK`) and triggers a job run, despite the feature being globally disabled.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
