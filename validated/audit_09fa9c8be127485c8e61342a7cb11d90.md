### Title
Symlinked directory component bypasses chroot validation in tar+zstd `Extract`, allowing writes outside cache/artifact root - (File: commands/helpers/archive/tarzstd/tarzstd_extractor.go)

### Summary
`Extract` validates that a tar entry's destination path is lexically inside `e.dir` using `filepath.Join`/`filepath.Abs` and a `strings.HasPrefix` check, but never resolves the real path of intermediate directory components. If any path component under `e.dir` is a symlink pointing outside the restore root (planted by an earlier extraction into the same, reused build/cache directory), the validated lexical path and the actual filesystem write target diverge, letting `os.Create`/`os.MkdirAll` follow the symlink and write outside the intended root.

### Finding Description
`Extract` computes the destination for each tar entry as: [1](#0-0) 

`path, err = filepath.Abs(filepath.Join(e.dir, hdr.Name))` performs a purely lexical join/clean — it does not touch the filesystem or resolve symlinks. The subsequent `strings.HasPrefix(path, e.dir+separator)` check only guards against `..`-style traversal that is resolvable at the string level; it says nothing about whether any component of `path` is, on disk, actually a symlink pointing elsewhere. Immediately after, `os.MkdirAll(filepath.Dir(path), 0777)` and, for regular files, `os.Create(path)` are real filesystem calls that *do* follow symlinks for every existing intermediate/parent component.

Symlink entries inside a *single* archive are deferred to a second pass (`deferred[path] = hdr`, created only after the whole main loop finishes) at [2](#0-1) , so a symlink and a path using it cannot be ordered within the same archive to defeat validation. However, `e.dir` (the extraction root, e.g. the cache directory or build working directory returned by `os.Getwd()` in `CacheExtractorCommand.Execute`) is **not cleaned before extraction**: [3](#0-2) 

Cache/build directories are intentionally persisted and reused across pipeline runs on the same runner/executor (that is the entire purpose of caching). This means an attacker who controls the contents of one job's cache archive can plant a symlink, e.g. `shared -> /etc` or `shared -> ../../../../etc`, via a normal symlink tar entry. Once that symlink is written to disk by the deferred pass at the end of extraction, it persists in the runner's cache/build directory. In a subsequent job execution (same project/runner, same cache key, or a job that reuses the same working directory), a new cache/artifact archive containing an entry named `shared/evilfile` will:
1. Compute `path = filepath.Join(e.dir, "shared/evilfile")`, which lexically starts with `e.dir` — passes the `HasPrefix` check.
2. Call `os.MkdirAll(filepath.Dir(path), 0777)` — `filepath.Dir(path)` is `e.dir/shared`, which `Stat` resolves through the pre-existing symlink to the real external target; since it already exists as a directory, `MkdirAll` is a no-op.
3. Call `os.Create(path)` — this follows the symlink and creates/truncates `evilfile` inside the real external directory (e.g., `/etc/evilfile`), entirely outside `e.dir`.

The validation at step 1 and the actual write target at step 3 are bound to different real paths, exactly the TOCTOU/symlink-retargeting pattern described in the question.

### Impact Explanation
An unprivileged pipeline author who controls cache or artifact archive content for a job can plant a symlink that later causes files to be written outside the intended cache/build root on the runner host (or inside the executor container's filesystem in unexpected locations), potentially overwriting files reachable through the symlink target. Concretely this is a path-root escape / trusted-file overwrite primitive scoped to the runner's cache/artifact restore tree, consistent with the "path-root escape or trusted-file overwrite" impact category in the question.

### Likelihood Explanation
Exploitability depends on the extraction root (`e.dir`) containing a persisted, attacker-planted symlink from a prior extraction into the same directory — which is a normal, expected condition for cache directories (cache reuse across job runs is the caching feature's purpose), and can also occur for build directories reused without `GIT_STRATEGY=clean`/`fetch`. No admin misconfiguration or privileged access is required; a normal pipeline author supplying a crafted cache/artifact archive across two job runs is sufficient. The attack is deterministic and repeatable once the directory reuse precondition holds.

### Recommendation
Before trusting the lexical prefix check, resolve each destination path's real location relative to `e.dir` (e.g., verify every existing intermediate component via `filepath.EvalSymlinks` on `filepath.Dir(path)`, or use `os.OpenFile`/directory-fd based APis such as `openat2` with `RESOLVE_NO_SYMLINKS`/`O_NOFOLLOW` semantics) and reject extraction if any parent component resolves outside `e.dir`. Additionally, consider refusing to extract into a directory that already contains a symlink at any position that would be traversed, or proactively remove/replace pre-existing symlinks under the restore root before writing regular files/directories.

### Proof of Concept
Go test sketch for `tarzstd` package:
1. Create temp dir `root`.
2. Build and extract archive A containing a symlink entry `link -> /tmp/outside` (a directory outside `root`) using `extractor.Extract`.
3. Build and extract archive B into the same `root` containing a regular file entry `link/pwned.txt` with attacker content.
4. Assert `filepath.Join("/tmp/outside", "pwned.txt")` exists and contains the attacker content, while `Extract` returned no error — demonstrating the write landed outside `root` despite the `HasPrefix` chroot check succeeding.

Expected (buggy) result: no error from `Extract`, and `/tmp/outside/pwned.txt` exists. Expected (fixed) result: `Extract` should either refuse to traverse through the pre-existing symlink or fail extraction rather than silently writing outside `root`.
