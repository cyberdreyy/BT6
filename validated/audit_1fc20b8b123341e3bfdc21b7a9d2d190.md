### Title
No refund path for failed multisig deployment - deposit is silently retained by the factory - ([File: multisig-factory/src/lib.rs])

### Finding Description
The claimed invariant is: `attacker_balance_before - deposit == attacker_balance_after` should hold only when the deployment succeeds; on failure the equality should be `attacker_balance_after == attacker_balance_before` (i.e. the payer is refunded). `MultisigFactory::create` breaks this by never checking the promise result.

`create` builds a single chained `Promise` — `create_account().deploy_contract(CODE.to_vec()).transfer(env::attached_deposit()).function_call("new", ..., 0, ...)` — and returns it directly to the caller without any `.then()` callback: [1](#0-0) 

Because these actions are batched into a single receipt sent to the new `account_id`, if any action fails (e.g. `create_account` fails because the account name is already taken or invalid, or the `new` constructor in `multisig2` panics on bad `members`/`num_confirmations` input), the whole batched receipt fails atomically. NEAR's protocol-level refund mechanism then returns the attached balance not to the original transaction signer (the attacker/user who called `create`), but to the **predecessor of that receipt**, which is the `multisig-factory` contract account itself. Since `MultisigFactory` exposes no other method (no `withdraw`, no owner, no way to reclaim funds), any deposit refunded this way is absorbed into the factory account's balance with no path back to the depositor.

`env::attached_deposit()` is read once and forwarded unconditionally via `.transfer(...)` with no `assert_one_yocto`, no minimum-deposit check, and — critically — no `is_promise_success()` check in a callback to return the deposit if deployment fails. This matches the "path that does not check one" described in the question: the factory neither validates nor guards the deposit at all; it just forwards it into a batch that can fail.

### Impact Explanation
Any account that calls `create` with a deposit and supplies inputs that cause `create_account`, `deploy_contract`, or the `new` call to fail (e.g., reusing a name that's already deployed, or supplying `num_confirmations` that violates `multisig2::new`'s internal assertions) loses their attached NEAR permanently to the factory contract with no mechanism to reclaim it. This is repeatable by any unprivileged user against any deployment attempt, and the factory's on-chain balance accumulates value that does not correspond to any accounted-for liability or ledger entry — a clear divergence between actual held balance and expected/owed balances, matching the "accounting value diverges from reality and another party settles on it" impact category (High).

### Likelihood Explanation
No special privilege is required: any account can call the `#[payable]` `create` method with an attached deposit. Triggering failure is trivial and fully attacker-controlled — attacker chooses `name` (can collide with an existing sub-account to fail `create_account`) or chooses invalid `members`/`num_confirmations` to fail the `new` constructor inside `multisig2`. The attacker's only cost is the deposit itself (which they lose) and gas; the exploit is directly and easily repeatable across many calls/accounts.

### Recommendation
Split deployment into `create_account/deploy_contract/transfer` and a separate `.then()` callback marked `#[private]`/`assert_self()` that checks `is_promise_success()` on the `new` call's result; on failure, `Promise::new(env::predecessor_account_id()).transfer(deposit)` to refund the original caller. Track the deposit amount explicitly (don't just forward `env::attached_deposit()` into an unguarded batch) so the refund path knows the exact amount to return.
