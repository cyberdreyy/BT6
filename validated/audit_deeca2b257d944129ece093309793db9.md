### Title
Stale confirmations from deleted keys let a multisig request execute below the live-key threshold - (File: `multisig/src/lib.rs`)

### Summary
The reported bug class is a custody/authorization binding that is silently broken by an incomplete state update on a privileged action (Stargate's `depositLP` assumed an allowance existed that was never granted). The direct analog in this repository is in `MultiSigContract`: when a key is revoked via `DeleteKey`, the contract only purges *requests authored by* that key, but never purges *confirmations cast by* that key on requests authored by someone else. A revoked key's confirmation therefore keeps counting toward `num_confirmations`, letting a request execute with fewer live, currently-authorized signers than the configured threshold.

### Finding Description
`confirm()` counts confirmations purely from the `HashSet<PublicKey>` stored per request and compares the count to `self.num_confirmations`: [1](#0-0) 

The only cleanup path for a compromised/removed key is the `DeleteKey` request action, which is handled inside `execute_request`: [2](#0-1) 

This code filters `self.requests` for entries whose `signer_pk` (the *original requester*) equals the deleted key, and removes only those requests' confirmations:
```
let request_ids: Vec<u32> = self.requests.iter()
    .filter(|(_k, r)| r.signer_pk == pk)
    .map(|(k, _r)| k)
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```
It never scans other pending requests to strip the deleted key's public key out of their `confirmations` `HashSet`. Consequently, `Confirmations recorded == set of PKs that ever called confirm(), including keys no longer holding an access key on the account`, while `Live members == the set of PKs currently able to sign for the account`. These two are supposed to be equal for the purpose of authorization; `DeleteKey` breaks the equality for confirmations on requests it doesn't own.

### Impact Explanation
This directly matches the Critical impact bucket "a multisig request executed below threshold." A multisig configured for `k`-of-`n` can be tricked into executing a transfer, `AddKey`, `FunctionCall`, etc. with fewer than `k` currently-authorized signatures, because one of the counted confirmations belongs to a key that has already been revoked (e.g., because it was known to be compromised, an employee left, or key rotation occurred). This is exactly the kind of authorization boundary crossing called out in the validation rules ("confirmations counted versus live members").

### Likelihood Explanation
No privileged access beyond normal multisig operation is required beyond what the multisig's own owners already do routinely: (1) some request gets partial confirmations from currently valid keys, (2) one of those confirming keys is later revoked via a `DeleteKey` request (a completely ordinary key-rotation/incident-response action), and (3) the still-pending request later receives one more confirmation from a live key, crossing the threshold with the stale confirmation counted in. No malicious insider, redeploy, or victim key theft is required — this is a straightforward consequence of a normal key-rotation workflow interacting with a pre-existing pending request, so likelihood is high wherever this contract is used with more than a couple of pending requests / occasional key rotation.

### Recommendation
When executing `DeleteKey`, iterate over **all** entries in `self.confirmations` (not just requests originated by the deleted key) and remove the deleted public key from every confirmation set; if this drops a request's count and the request had already reached quorum in a prior epoch that's fine, but going forward it must be re-evaluated with the reduced set. Alternatively, validate at `confirm()`/execution time that every public key in the stored confirmation set still corresponds to a currently valid access key on the account before counting it toward `num_confirmations`.

### Proof of Concept
Multisig deployed with `num_confirmations = 3` and access keys `{A, B, C, D}`.

1. `A` calls `add_request(R)` for a `Transfer` action → `R.signer_pk = A`, confirmations = `{}`.
2. `B` calls `confirm(R)` → confirmations = `{B}` (1/3).
3. `D` calls `confirm(R)` → confirmations = `{B, D}` (2/3, below threshold, not yet executed).
4. Owners detect `D`'s device is compromised and revoke it: a separate request `R2` with `MultiSigRequestAction::DeleteKey{ public_key: D }` is created and confirmed to threshold by `A`, `B`, `C`. `execute_request` runs the `DeleteKey` branch: since `R.signer_pk == A` (not `D`), `R` is not in the filtered `request_ids`, so `R`'s confirmations `{B, D}` are left untouched even though `D`'s key is now deleted from the account.
5. `C` (a live key) calls `confirm(R)` → confirmations = `{B, D, C}`, count = 3 ≥ `num_confirmations` (3) → `execute_request(R)` fires the `Transfer`, even though only `B` and `C` are currently valid signers (2 live confirmations), one short of the intended 3-of-n threshold. [1](#0-0) [2](#0-1)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
