### Title
Loss-adjusted withdraw accounting validates only `lastWithdrawRequest` epoch, letting older-epoch receipts escape the haircut and drain funded underlyings - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` records a single haircut ratio under `lossRecoveryPriceByEpoch[epochNumber]` for the *aggregate* `pendingWithdraws` basis, which can span receipts from multiple epochs (`IdleCreditVault.sol:411-430`). Both the re-request guard in `requestWithdraw` (`IdleCreditVault.sol:261-271`) and the payout path in `_claimLossAdjustedWithdrawRequest` (`IdleCreditVault.sol:789-801`) index the loss record through only one epoch key — `lastWithdrawRequest[_user]` — without validating that this index covers all of the user's receipt epochs. This is the direct analog of "improper validation of array index": an epoch index into `lossRecoveryPriceByEpoch`/`withdrawsRequestsByEpoch` is trusted without checking it bounds the whole claim set, so out-of-index receipts are paid at par and the vault becomes insolvent (DoS for later claimers).

### Finding Description
`requestWithdraw` allows a user to hold unclaimed receipts across multiple epochs — `withdrawsRequestsByEpoch[_user][epoch]` accumulates per epoch (`IdleCreditVault.sol:293`) while `lastWithdrawRequest[_user]` is overwritten each request (`IdleCreditVault.sol:282`). The pre-request haircut guard reads only `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and only blocks when that single epoch holds a receipt. Two index-mismatch cases follow:

1. **Multi-epoch receipts, loss keyed to latest epoch.** User requests in epoch E1, does not claim, epoch rolls, requests again in E2 (`lastWithdrawRequest = E2`). `stopEpochWithDuration(_lossAmount)` funds the aggregate `pendingWithdraws` (E1+E2 basis) at `lossRecoveryPrice`, stored under the current epoch. On `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` clears only the E2 receipt at the haircut and resets `lastWithdrawRequest[_user] = 0` (`IdleCreditVault.sol:832-836`). `_claimFundedWithdrawRequest` then passes the epoch gate (`epochNumber <= 0` is false) and pays the remaining `withdrawsRequests[_user]` — the E1 basis — **at par** through `_transferFundedClaim`, although that basis was only funded at `lossRecoveryPrice`.

2. **Loss keyed to an older epoch.** If the loss price lands on an epoch different from `lastWithdrawRequest` (e.g., the E_old receipt case, or any epoch-number increment ordering where `collectWithdrawFunds` keys a later epoch than the request epoch), the guard at `requestWithdraw` reads `lossRecoveryPriceByEpoch[E_new] == 0`, lets new requests in, and `_claimLossAdjustedWithdrawRequest` finds price 0 → the haircutted receipt is paid at par.

In both cases the invariant "one funded basis ⇒ haircut-proportional payout" is broken: the strategy contract holds only `pendingBasis * lossRecoveryPrice / 1e18`, but pays out more.

### Impact Explanation
The first claimer extracting par value on haircutted basis directly over-draws the strategy's funded balance. Every underpaid haircut dollar is stolen from other pending claimers; when the shortfall materializes, later `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls revert on the underlying transfer — permanent freezing/theft of remaining claims and vault insolvency. Loss equals `(1 - lossRecoveryPrice) × (out-of-index receipt basis)`, bounded by total pending withdrawals.

### Likelihood Explanation
Requires: (a) a `stopEpochWithDuration` with realized loss (manager/borrower-driven, in scope per rules), and (b) a user holding receipts in more than one epoch or a receipt whose epoch differs from the loss key — trivially reachable by requesting a withdraw, skipping the claim (explicitly supported: "Once the epoch is over user can withdraw at any time"), and requesting again. No privileged misbehavior needed; the attacker is an ordinary KYC'd tranche holder sequencing their own requests and claims.

### Recommendation
In `_claimLossAdjustedWithdrawRequest`, iterate/aggregate all receipt epochs with a non-zero `withdrawsRequestsByEpoch`/`apr0Users.principalEpoch` rather than trusting `lastWithdrawRequest` as the sole index, and apply `lossRecoveryPrice` to the aggregate basis. Correspondingly, the `requestWithdraw` guard should reject re-requests while *any* unfunded haircut epoch exists for the user, not only the one at `lastWithdrawRequest`. Alternatively store a per-user bitmask/list of loss epochs instead of a single epoch index.

### Proof of Concept
Foundry fork sketch (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// epoch E1: user requests withdraw of R1 strategy tokens
requestWithdraw(R1);              // withdrawsRequestsByEpoch[user][E1] = R1; lastWithdrawRequest = E1
// user does NOT claim; honest manager stops epoch -> epochNumber = E2
stopEpoch(0);
// epoch E2: user requests R2 (guard passes: lossRecoveryPriceByEpoch[E1] == 0)
requestWithdraw(R2);              // lastWithdrawRequest = E2
// manager stops E2 with loss L: borrower funds pendingWithdraws*(1-haircut)
stopEpochWithDuration(L);         // collectWithdrawFunds stores lossRecoveryPriceByEpoch[E2]; pendingWithdraws = 0
// claim
claimWithdrawRequest(user);
//  -> _claimLossAdjustedWithdrawRequest pays R2 * price (clears epoch E2, lastWithdrawRequest=0)
//  -> _claimFundedWithdrawRequest pays R1 AT PAR via _transferFundedClaim
// invariant broken: paid = R2*price + R1  >  funded = (R1+R2)*price
// second user with equal receipts now finds the strategy underfunded -> claim reverts
```

Caveat: I could not confirm within the available iterations the exact ordering of `epochNumber` increment vs. `collectWithdrawFunds` inside `stopEpochWithDuration` in `IdleCDOEpochVariant.sol`; if the loss key lands on a different epoch than `lastWithdrawRequest`, the same mismatch is even more severe (case 2 — the entire haircutted receipt pays par). The multi-epoch receipt precondition itself is confirmed by the per-epoch accounting and the explicit "claim at any time" comments in `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:320-325`).   function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
