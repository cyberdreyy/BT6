### Title
Rejection weight is never retracted when a signer flips to Accepted, allowing a stale rejection tally to satisfy the "block failed" threshold alongside (or after) a legitimate acceptance threshold - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
This is the closest reachable analog to the `_migrateStake`/`_delegateStake` double-accounting bug: a value that has already been "spent" toward one bucket (a rejection) is never removed from that bucket, and the same signer's weight can later also be added to a different bucket (an acceptance), so the two running totals (`total_weight_approved`, `total_weight_rejected`) are not mutually exclusive per signer, breaking the equality that each signer's weight should count toward at most one live, final decision.

### Finding Description
In the node-side StackerDB listener, block vote tallying is guarded by two different, non-symmetric dedupe keys:

- Accept path only checks `block.gathered_signatures.contains_key(&slot_id)` before adding the signer's weight to `total_weight_approved`: [1](#0-0) 

- Reject path checks and updates a *shared* `block.responded_signers` set before adding weight to `total_weight_rejected`: [2](#0-1) 

Because `responded_signers` is shared but `gathered_signatures` is accept-only, a signer that first sends a Rejected response (added to `total_weight_rejected`, and `responded_signers` now contains its slot) and later sends an Accepted response for the *same* block hash is not blocked by the accept path's gate (`gathered_signatures` is still empty for that slot), so its weight is *also* added to `total_weight_approved`. The prior rejection weight in `total_weight_rejected` is never decremented or invalidated. The stacks-signer's own `CHANGELOG.md` documents that a fix was explicitly made to "not count both a block acceptance and a block rejection for the same signer/block," but that fix lives in the signer-side tallying (`stacks-signer/src/v0/signer.rs` / `signerdb.rs`), not in this node-side miner aggregator, which lacks the equivalent invariant. [3](#0-2) 

The consequence mirrors the reported bug class: a quantity that should be exclusively attributed to one outcome (reject) is retained and then also counted toward the other outcome (accept), so `total_weight_approved + total_weight_rejected` can exceed `self.total_weight`, and the miner's rejection-threshold check [4](#0-3) 
can remain permanently satisfied by stale rejection weight even after the signer set has, in aggregate, actually reached the acceptance threshold, or vice versa depending on message ordering/timing.

### Impact Explanation
This does not let a signer sign an invalid/non-canonical block, nor forge a cross-context signature, nor let a rejection be recounted as an acceptance in the strict sense (it is additive double counting, not a substitution). Its practical effect is a liveness hazard on the miner side: stale, un-retracted rejection weight can keep the coordinator's "signers rejected" branch true (or make it artificially reachable) even though enough signer weight subsequently accepted, causing spurious `NakamotoNodeError::SignersRejected` treatment (txid exclusion, tenure aborts) for a block that in fact reached legitimate consensus, or vice versa muddying the tally used to decide whether to keep waiting. This is a node-local (miner) bookkeeping defect, not a signer-side safety violation of the equivocation guard, and does not by itself allow a non-canonical/invalid block to be signed — the actual gating safety property (`verify_signer_signatures` / `compute_voting_weight_threshold` in `stackslib/src/chainstate/nakamoto/mod.rs`) recomputes weight independently from the header's signature vector and is unaffected. [5](#0-4) 

### Likelihood Explanation
Triggering requires only one signer (or a single Byzantine/faulty signer, or a legitimate signer that revises its vote due to a reconsideration rule) to send a Rejected message followed later by an Accepted message for the same `signer_signature_hash` to the same miner listener — well within a one-slot actor's capability and consistent with documented behavior where "For some rejection reasons, a signer will reconsider a block proposal that it previously rejected" (see CHANGELOG 3.1.0.0.8.0). No majority collusion is needed to create the stale double count; only a majority is needed to actually flip the final outcome, which is a separate concern from the accounting defect itself.

### Recommendation
Make the reject/accept dedupe symmetric: gate both branches with a single per-slot "already responded" set that records the outcome, and if the outcome type changes, subtract the previously counted weight from its bucket before adding it to the new bucket (or refuse to change the tally after a definitive first response), so `total_weight_approved + total_weight_rejected` for a given signer slot never simultaneously reflects a stale, superseded verdict.

### Proof of Concept
1. Miner requests votes on block `B`; listener creates `BlockStatus` for `B` with empty `gathered_signatures`/`responded_signers`.
2. Signer S sends `BlockResponse::Rejected` for `B`: `responded_signers.insert(S.slot)` succeeds, `total_weight_rejected += S.weight`.
3. Signer S (reconsidering, per an allowed reject-reason reconsideration path) later sends `BlockResponse::Accepted` for the same `B`: `gathered_signatures.contains_key(S.slot)` is false (never touched by reject path), so `total_weight_approved += S.weight` is executed and `gathered_signatures`/`responded_signers` are updated.
4. Result: `total_weight_rejected` still includes `S.weight` from step 2, and `total_weight_approved` now also includes `S.weight` from step 3 — the same signer's weight is counted in both running totals, so `total_weight_approved + total_weight_rejected` can exceed `total_weight`, and the coordinator's reject-vs-accept branch decision in `signer_coordinator.rs` (lines 508-545) is fed inconsistent, double-counted data.
