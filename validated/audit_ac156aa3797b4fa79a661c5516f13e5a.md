### Title
Replay guard consumes a request's digest slot before owner-binding validation, allowing an attacker to pre-burn a victim's identical-digest request and cause denial of a legitimate request - ([File: core/capabilities/vault/authorizer.go])

### Summary
`authorizer.AuthorizeRequest` calls `a.replayGuard.CheckAndRecord(authResult.Digest(), ...)` before calling `validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner())`. Because the digest is derived purely from the request's method/params via `req.Digest()` (independent of the authorized owner), an attacker holding their own valid JWT can submit a request whose params (secret ID/owner) belong to a victim, get the digest recorded by the replay guard, fail the subsequent owner-binding check, and thereby cause the victim's later legitimate identical request to be rejected as `ErrRequestAlreadySeen`.

### Finding Description
In `core/capabilities/vault/authorizer.go`, `AuthorizeRequest` performs steps in this order:
1. `authResult, err := a.authorizeRequest(ctx, req)` — either allow-list or JWT-based auth, both of which independently compute `requestDigest, err := req.Digest()` from the request's method+params/ID (see `core/capabilities/vault/jwt_based_auth.go:252` and `core/capabilities/vault/allow_list_based_auth.go:36`), and separately derive `workflowOwner` from the caller's own JWT claims or allowlist entry.
2. `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())` at line 109 — this records the digest in `RequestReplayGuard.seen` and only fails if the digest already exists (`core/capabilities/vault/request_replay_guard.go:35-47`).
3. Only afterward, `validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner())` at line 113 checks that the secret owner fields embedded in `req.Params` (e.g. `CreateSecretsRequest.EncryptedSecrets[i].Id.Owner`) match the caller's authorized owner.

Since the digest is computed from request content that does not include the authenticated owner, an attacker can craft a request whose JSON-RPC method/params exactly mirror a victim's future legitimate request (e.g., same `SecretsCreate`/`SecretsUpdate`/`SecretsDelete` payload naming the victim's owner and secret ID — information the attacker can predict or observe since owners/IDs are not secret), attach their **own valid** authorization (a legitimate JWT for their own org/tenant with `request_digest` claim matching the digest of that crafted payload, or a legitimate allowlist entry for their own address matching that digest), and submit it. Step 2 succeeds and burns the digest slot. Step 3 then fails because the derived owner (attacker) doesn't match the owner embedded in params (victim), so the attacker's request is rejected — but the digest is already permanently recorded until its `expiresAt`. When the victim subsequently submits the actual identical-content request (which computes the same digest), step 2 rejects it with `ErrRequestAlreadySeen` before step 3 (owner validation, which would have legitimately succeeded) is ever reached.

### Impact Explanation
This is a denial-of-service against a specific targeted request: an unprivileged/unauthenticated-relative-to-victim attacker (any holder of a valid JWT for their own org, or any address with an allowlisted-but-mismatched request) can selectively prevent a victim's secret-management operation (`vault.secrets.create/update/delete`) from ever being accepted, by pre-consuming its replay-guard slot with a doomed, owner-mismatched submission. This matches a "denial of legitimate request / unauthorized manipulation of another user's job or secret operation availability" impact class — it does not leak secrets or bypass owner-binding for reads/writes, but it does let an attacker weaponize the authorizer against another user's specific, otherwise-valid request.

### Likelihood Explanation
Exploitability requires: (1) the attacker holds any valid credential accepted by `jwtBasedAuth` or `allowListBasedAuth` (their own JWT or their own allowlisted address) — no privilege beyond a normal external Vault API caller; (2) the attacker can predict or observe the exact method+params of the victim's request (secret owner addresses and secret IDs are not confidential inputs and are often deterministic/known ahead of time, e.g., workflow owner address + fixed secret ID naming conventions); (3) the attacker must be able to obtain a signed authorization (JWT or allowlist entry) whose `request_digest` matches that crafted payload — feasible since digest computation and JWT-minting flow are attacker-controlled for their own identity. The attack is repeatable per targeted request digest and expires only after `authResult.ExpiresAt()`, giving a window during which the victim's genuine request is blocked.

### Recommendation
Reorder the checks in `authorizer.AuthorizeRequest` so that `validateSecretOwnersMatchAuthorized` (owner-binding validation) runs and succeeds **before** `replayGuard.CheckAndRecord` mutates shared state. Only record the digest in the replay guard after all authorization checks (including owner binding) have passed, ensuring a failed/mismatched request never consumes a replay slot that a legitimate request could still need.

### Proof of Concept
Go unit test plan for `core/capabilities/vault/authorizer_test.go`:
1. Construct a fake `Authorizer` (mock allow-list or JWT auth) that returns `AuthResult{workflowOwner: "attacker", digest: "D", expiresAt: future}` for an attacker-supplied request `reqAttacker` whose `Params` contain `EncryptedSecrets[0].Id.Owner = "victim"`.
2. Call `authorizer.AuthorizeRequest(ctx, reqAttacker)` and assert it returns a non-nil owner-mismatch error (from `validateSecretOwnersMatchAuthorized`), confirming the attacker's own request never succeeds.
3. Construct a second request `reqVictim` with identical `Method`/`Params` (so `req.Digest()` computes to the same digest "D"), but backed by a mock auth returning `AuthResult{workflowOwner: "victim", digest: "D", expiresAt: future}` (legitimate victim credentials matching their own owner field).
4. Call `authorizer.AuthorizeRequest(ctx, reqVictim)` and assert the result: **expected (buggy) behavior** — it returns `ErrRequestAlreadySeen` even though the victim's request has correct owner binding and never previously succeeded, proving the pre-burn DoS. After applying the fix (owner-check before replay-record), assert `reqVictim` succeeds and returns a valid `*AuthResult`.
