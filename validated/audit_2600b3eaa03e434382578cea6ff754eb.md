### Title
Unbounded/unfair `savedCallbacks` pruning combined with sender-agnostic MessageId keying enables cross-user callback eviction and response hijack - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`pruneCallbacks` evicts entries from `h.savedCallbacks` purely by global count/age with no per-sender accounting, and `HandleLegacyUserMessage`/`handleWebAPITriggerMessage` key and look up callbacks solely by `msg.Body.MessageId` with no binding to the original sender/receiver. An unprivileged client that floods the gateway with many distinct `MessageId`s can force early eviction of another user's still-pending callback, and because the map is keyed only by `MessageId`, any later message (attacker- or victim-originated) that reuses that exact ID overwrites the map entry, letting the DON's eventual response for the original request be delivered to whoever currently holds that key.

### Finding Description
`HandleLegacyUserMessage` unconditionally stores the caller-supplied `msg.Body.MessageId` in the shared map without checking for a collision or binding it to `msg.Body.Sender`/`Receiver`: [1](#0-0) 

`handleWebAPITriggerMessage`, which processes the DON's response, looks the callback up and deletes it purely by `MessageId`, with no cross-check that the response corresponds to the same sender/context that registered it: [2](#0-1) 

`pruneCallbacks` operates on the entire map globally — it sorts all entries by `createdAt` and deletes the oldest half once `len(h.savedCallbacks) > maxSize`, with no per-sender quota or fairness weighting: [3](#0-2) 

`MessageId` is attacker-controlled input from the JSON-RPC request ID / `msg.Body.MessageId` and is part of the signed payload for the sender's own signature, but nothing prevents a *different* sender from submitting a request carrying the identical `MessageId` string under their own valid signature: [4](#0-3) [5](#0-4) 

Because the map has no sender/receiver isolation, two failure modes exist:
1. **DoS via forced eviction**: an attacker sending > `MaxSavedCallbacks/2` distinct requests in one prune interval can force the age-sorted eviction to remove a victim's legitimately pending, non-expired callback, silently dropping the victim's in-flight response (the callback's `SendResponse` is never invoked, and the caller of `HandleLegacyUserMessage` has already returned before the async DON response arrives).
2. **Response hijack on `MessageId` reuse**: if the attacker knows/reuses the exact evicted `MessageId` (e.g., because it is predictable/observed in a shared workflow context), they can re-register their own callback under that key. When the DON eventually responds with the original `MessageId` (nodes echo back the request ID unmodified), `handleWebAPITriggerMessage` delivers the response to whichever callback currently occupies that map slot — the attacker's, not the victim's.

Note: the second failure mode does not strictly require waiting for `pruneCallbacks` — because `HandleLegacyUserMessage` overwrites `h.savedCallbacks[msg.Body.MessageId]` unconditionally, any sender submitting a colliding `MessageId` before the DON responds can hijack a pending callback slot directly, without needing to trigger eviction first. The eviction path described in the question is one route to the same root cause (lack of sender-scoped isolation in the callback map), but the flood-then-reuse precondition assumes the attacker can guess or already knows the victim's exact `MessageId`, which is not automatically implied by mere flood capability — `MessageId`s are chosen by each requester independently and there is no code path shown here that leaks another user's `MessageId` to an unprivileged party.

### Impact Explanation
Concrete impact is twofold: (a) denial-of-service — a legitimate user's pending web-API-trigger response can be silently dropped because `pruneCallbacks` has no per-sender fairness, and (b) cross-user response confusion — if a `MessageId` is ever known/reused by two different senders, the gateway's sender-agnostic callback map allows the DON's response for one user's request to be delivered to another user's registered callback. This matches Chainlink's "unauthorized action on another user's request/response" bounty class, though severity for (b) is gated by the attacker's ability to learn or predict the victim's exact `MessageId`.

### Likelihood Explanation
Triggering the eviction/DoS half only requires an unprivileged party capable of sending `> MaxSavedCallbacks/2` (default 10,000) legacy user messages within a prune interval (default 30s) — feasible for any client with network access to the gateway and no special role. Achieving the response-hijack half additionally requires the attacker to know or predict the victim's exact `MessageId`, which is not demonstrated as guessable/leaked anywhere in the reviewed code; this significantly limits real-world exploitability of the redirection scenario beyond the DoS component.

### Recommendation
Scope `savedCallbacks` (and `pruneCallbacks` eviction) by sender/receiver in addition to `MessageId`, e.g. key by `(Sender, Receiver, MessageId)` or maintain per-sender submaps/quotas so eviction pressure from one sender cannot displace another sender's pending callbacks. Additionally, reject `HandleLegacyUserMessage` requests whose `MessageId` already exists in `savedCallbacks` (return a conflict error) instead of silently overwriting, and validate in `handleWebAPITriggerMessage` that the response's implied sender/receiver context matches what was recorded at registration time.

### Proof of Concept
1. Construct a `handler` with `HandlerConfig.MaxSavedCallbacks` set small (e.g., 10) and `CallbackMaxAgeSec` large so age-based expiry doesn't interfere.
2. Register a "victim" callback via `HandleLegacyUserMessage` with `MessageId = "victim-id"` and a callback that records if `SendResponse` was invoked.
3. Flood with `N > MaxSavedCallbacks` additional `HandleLegacyUserMessage` calls with distinct `MessageId`s from a different signer, all created after the victim's entry (to be sorted older/together for eviction).
4. Call `h.pruneCallbacks()` directly and assert `victim-id` is no longer present in `h.savedCallbacks` (demonstrating silent eviction/DoS).
5. Re-submit `HandleLegacyUserMessage` with `MessageId = "victim-id"` from the attacker's signer, registering an attacker callback under the same key.
6. Simulate the DON responding with `MessageId = "victim-id"` via `HandleNodeMessage`/`handleWebAPITriggerMessage`, and assert the **attacker's** callback (not the victim's) receives `SendResponse`, confirming cross-user response redirection.

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}

// ValidatedMessageFromReq validated and extracts a legacy Gateway Message
// from params field of JSON-RPC request
func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageId = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}
