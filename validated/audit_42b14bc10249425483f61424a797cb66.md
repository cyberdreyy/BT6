## Title
`join_validator_set_internal` silently converts pending_inactive delegator stake to inactive without any accounting or authorization check, letting an inactive validator's operator move delegators' unlocking stake past its lockup outside the normal `update_stake_pool`/epoch path - ([File: aptos-move/framework/aptos-framework/sources/stake.move])

### Summary
`stake::join_validator_set_internal` was modified (per blame, authored by `actions-user`, not present in the codebase's expected mainline flow) to add a code block that force-merges the entire `pending_inactive` coin balance of the stake pool into `inactive` whenever the operator rejoins the validator set and the pool's `locked_until_secs` has already passed, *before* the normal reward/epoch settlement path (`update_stake_pool`) ever runs on this pool. [1](#0-0) 

### Finding Description
Normally, the transition of `pending_inactive` stake to `inactive` only happens inside `update_stake_pool`, which runs once per epoch for currently-active/pending_inactive validators and simultaneously distributes rewards, updates performance stats, and is the single authoritative place where OLC-consistent accounting occurs for callers like `delegation_pool` and `staking_contract`. `delegation_pool.move`'s own header explicitly states this invariant: *"if detecting that the lockup expired on the stake pool, the delegation pool will isolate its pending_inactive stake (now inactive) and create a new pool_u64... Detecting a lockup expiration on the stake pool resumes to detecting new inactive stake."* [2](#0-1) 

`delegation_pool::synchronize_delegation_pool`/`calculate_stake_pool_drift` detects a "new OLC" strictly by comparing `stake::get_stake`'s `inactive` value against `pool.total_coins_inactive` recorded at the *previous* synchronization: [3](#0-2) 

The newly added code in `join_validator_set_internal` performs exactly the "inactivate pending_inactive" state transition that is supposed to be gated behind `update_stake_pool`/epoch-end, but does it as a side effect of the *operator* calling `join_validator_set` on an inactive pool — a routine, unprivileged (from the staker/delegator's perspective) operation that has nothing to do with settling old unlocking stake. This happens with no interaction with `delegation_pool`'s or `staking_contract`'s own bookkeeping (`total_coins_inactive`, `observed_lockup_cycle`, inactive-shares pools) since those modules only ever call `stake::get_stake` afterward and rely on the OLC-advance detection logic being triggered from within `update_stake_pool`'s normal cadence.

This directly mirrors the Linea "Incorrect Final Block Number" bug class: an accounting-changing state transition is performed outside its normal validated path (there, finalization without checking submitted data boundaries; here, pending_inactive→inactive conversion without going through the synchronized epoch-settlement path that keeps `delegation_pool`/`staking_contract` state consistent), silently causing downstream ledgers to diverge from the real stake-pool state.

### Impact Explanation
Because `join_validator_set_internal` mutates `stake_pool.inactive` and `stake_pool.pending_inactive` directly and is callable by the operator any time the pool is inactive and its lockup has elapsed, an operator can trigger this state change out-of-band relative to when `delegation_pool::synchronize_delegation_pool` (or `staking_contract::distribute_internal`) last recorded `total_coins_inactive`/`observed_lockup_cycle`. Depending on when synchronization is next called relative to this event, this can desynchronize the delegation pool's internal "which OLC does this inactive stake belong to" bookkeeping from the stake pool's real `inactive` balance, corrupting withdrawal-eligibility tracking for delegators who have pending unlock requests (`withdraw_internal` uses `pool.observed_lockup_cycle`/`total_coins_inactive` to decide which shares pool to redeem from and whether "excess" pending_inactive should be preserved). This can strand a delegator's unlock request in the wrong OLC bucket, or allow reactivate/withdraw operations to compute incorrect available amounts, corrupting withdrawal rights for delegator or staker funds not owned by the operator triggering it — a stake-and-lockup accounting corruption that credits/blocks the wrong amount.

### Likelihood Explanation
The path is reachable by any operator who controls a stake pool that has gone inactive (e.g., dropped from the validator set) and whose lockup has since expired — a routine, unprivileged (non-admin) operational sequence (leave/idle then rejoin) rather than a rare or governance-gated scenario. No special permissions beyond being the registered operator of the pool are required, and delegation pools/staking contracts are explicitly built so any account can be an operator of a stake pool holding funds from unrelated stakers/delegators.

### Recommendation
Remove the ad hoc `pending_inactive → inactive` merge from `join_validator_set_internal`, or route it exclusively through the same synchronized path used elsewhere (i.e., trigger `delegation_pool::synchronize_delegation_pool`/`update_stake_pool`-equivalent OLC-advance logic atomically with this settlement, updating `total_coins_inactive` and `observed_lockup_cycle` consistently) so that all downstream consumers of `stake::get_stake` observe a consistent, epoch-boundary-anchored transition rather than one triggered mid-operation by an operator action.

    /// Calculate stake deviations between the delegation and stake pools in order to
    /// capture the rewards earned in the meantime, resulted operator commission and
    /// whether the lockup expired on the stake pool.
    fun calculate_stake_pool_drift(pool: &DelegationPool): (bool, u64, u64, u64, u64) {
        let (active, inactive, pending_active, pending_inactive) = stake::get_stake(get_pool_address(pool));
        assert!(
            inactive >= pool.total_coins_inactive,
            error::invalid_state(ESLASHED_INACTIVE_STAKE_ON_PAST_OLC)
        );
        // determine whether a new lockup cycle has been ended on the stake pool and
        // inactivated SOME `pending_inactive` stake which should stop earning rewards now,
        // thus requiring separation of the `pending_inactive` stake on current observed lockup
        // and the future one on the newly started lockup
        let lockup_cycle_ended = inactive > pool.total_coins_inactive;

        // actual coins on stake pool belonging to the active shares pool
        active += pending_active;
        // actual coins on stake pool belonging to the shares pool hosting `pending_inactive` stake
        // at current observed lockup cycle, either pending: `pending_inactive` or already inactivated:
        if (lockup_cycle_ended) {
            // `inactive` on stake pool = any previous `inactive` stake +
            // any previous `pending_inactive` stake and its rewards (both inactivated)
            pending_inactive = inactive - pool.total_coins_inactive
        };
