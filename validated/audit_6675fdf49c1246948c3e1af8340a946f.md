The premise doesn't identify an exploitable bug. In NEAR's gas-accounting model, action exec fees are fixed per action type and seeded into `ActionResult` **before** the action handler runs — this is documented in `apply_action` (`runtime/runtime/src/lib.rs`), which seeds the result with the action's `exec_fee` prior to dispatching to `action_add_key` [1](#0-0) . This is true for *every* action type (`CreateAccount`, `DeleteKey`, `Stake`, etc.), not something specific to `AddKey`'s existence check. The fee schedule for `AddKey` is a fixed, protocol-defined value chosen to bound the worst-case cost of the operation (including the trie lookup, insert, and storage-usage accounting), not a metered charge tied to the literal bytes touched during that specific call. [2](#0-1) 

The described "gas_burnt difference" between a fresh-key AddKey and an already-existing-key AddKey reflects the intended design: fixed exec fees regardless of whether the action succeeds or fails with `AddKeyAlreadyExists`, since one `get_access_key` trie read (which the failing path already performs) is bounded, single-key work already covered within the fixed fee's provisioned cost — this is a resource-hygiene/fee-calibration observation, not an authorization bypass, fund theft, freezing, double-spend, or consensus-divergence bug. The attacker cannot avoid paying the exec fee — it's deducted the same way whether the key exists or not — nor can they force uncompensated extra work beyond a single bounded trie read that the config already prices in. This does not meet the required "concrete loss or freezing of funds, consensus divergence, or shard/network halt" bar, and per the rules, speculative resource-hygiene claims without a reachable mainnet fund-loss scenario are rejected.
