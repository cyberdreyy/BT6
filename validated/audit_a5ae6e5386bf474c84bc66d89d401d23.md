### Title
External Initiator credentials bypass job/bridge binding and can trigger runs for unrelated jobs via POST /v2/jobs/:ID/runs - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` unconditionally sets `SessionUserKey` to a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` for any valid EI credential pair, without binding that identity to the specific bridge/job the EI is registered for. `PipelineRunsController.Create` attempts to block EI callers from running jobs by int ID via `isUser, ok := auth.GetAuthenticatedUser(c)`, but this check is defeated because the EI middleware populates the exact same `SessionUserKey` used by regular user sessions, making `isUser` true for EI-authenticated requests as well.

### Finding Description
In `core/web/auth/auth.go`, `AuthenticateExternalInitiator` (lines 119-151) validates the `X-Chainlink-EA-AccessKey`/`Secret` headers against a specific `bridges.ExternalInitiator` record, then does: [1](#0-0) 
This sets `SessionUserKey` to a fresh `User{Role: UserRoleRun}` with no reference to which `ExternalInitiator`/bridge authenticated the request — only `SessionExternalInitiatorKey` carries that binding.

Downstream, `PipelineRunsController.Create` (`core/web/pipeline_runs_controller.go`, lines 89-128) contains logic that explicitly intends to reject EI-authenticated requests for `POST /jobs/:ID/runs`: [2](#0-1) 
The comment states "only users are allowed to run jobs using int IDs - EIs not allowed," and the code guards behind `isUser`. However `auth.GetAuthenticatedUser` (auth.go lines 178-187) merely reads `SessionUserKey` and type-asserts to `*clsessions.User` — it cannot distinguish a genuine user session from the synthetic `User{Role: UserRoleRun}` object that `AuthenticateExternalInitiator` injects. Because the EI middleware sets `SessionUserKey` too, `isUser` evaluates to `true` for EI-authenticated calls, defeating the intended "EIs not allowed" restriction. The int32-job-ID branch then calls `prc.App.RunJobV2(ctx, jobID, nil)` for any parseable job ID, with no verification that the job's bridge matches the EI record stored in `SessionExternalInitiatorKey`.

There is no code anywhere in this path that cross-checks `GetAuthenticatedExternalInitiator(c)` against the job specified by `c.Param("ID")`. Consequently, any valid EI credential (registered for bridge A) can trigger a run for a job created under an unrelated bridge B, so long as the job ID is a valid int32 — violating request/job attribution (REQUEST_BINDING).

### Impact Explanation
Impact is limited to unauthorized triggering of job runs across bridge/job boundaries by an external-initiator credential holder — this maps to Chainlink's "unauthorized job run" bounty impact class. It does not grant secret disclosure or fund movement directly, but it lets an EI meant only for bridge A initiate pipeline execution (and any side effects, e.g. on-chain transactions, external API calls) for jobs it has no legitimate relationship to.

### Likelihood Explanation
Exploitation requires only possession of one valid, currently-registered EI `AccessKey`/`Secret` pair (a low-privilege, non-admin credential type) and knowledge/guessability of a target job's integer ID. No operator or admin access is needed. This is fully reproducible via a single authenticated HTTP call and is deterministic — the broken check is unconditional code logic, not a race or timing issue.

### Recommendation
- In `AuthenticateExternalInitiator`, use a distinct context key (e.g. keep only `SessionExternalInitiatorKey`) instead of also writing a synthetic `User{Role: UserRoleRun}` into `SessionUserKey`, or mark the synthetic user object so `GetAuthenticatedUser`/`isUser` checks can distinguish it from a genuine user session.
- In `PipelineRunsController.Create`, explicitly check `auth.GetAuthenticatedExternalInitiator(c)`; if present, reject the request (matching the existing comment's intent) instead of relying on the ambiguous `isUser` flag.
- If EI-triggered runs by job ID are ever intended to be supported, validate that the job's associated bridge matches `ei.Name`/`ei.URL` before calling `RunJobV2`.

### Proof of Concept
Go handler-level integration test plan:
1. Create two bridges/EIs: `eiA` (registered for bridge "bridge-a") and `eiB` (registered for bridge "bridge-b"), each with distinct `AccessKey`/`Secret`.
2. Create `jobA` associated with bridge "bridge-a" and `jobB` associated with bridge "bridge-b"; capture their int32 job IDs.
3. Using `eiA`'s credentials, send `POST /v2/jobs/{jobB.ID}/runs` with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers set to `eiA`.
4. Assert the middleware chain authenticates successfully (`AuthenticateExternalInitiator` succeeds since `eiA` is valid), and observe that `PipelineRunsController.Create` proceeds into the `isUser` branch (assert via mock/spy on `GetAuthenticatedUser` returning `ok=true`).
5. Assert `prc.App.RunJobV2` is invoked with `jobB.ID` and a pipeline run is created and returned with HTTP 200, despite `eiA` never being associated with `jobB`/bridge-b.
6. Compare against expected secure behavior: the request should be rejected with 401/403 because `eiA` is not authorized for `jobB`.
