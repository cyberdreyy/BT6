## Analysis

The claim is valid. `BaseEscrowFactory.createDstEscrow()` takes `dstImmutables` (including `timelocks`) entirely from `msg.sender`-supplied calldata, with only one on-chain sanity check:

```solidity
immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
// Check that the escrow cancellation will start not later than the cancellation time on the source chain.
if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();
``` [1](#0-0) 

Nothing here (or anywhere else in `createDstEscrow`) enforces the relative ordering `DstWithdrawal < DstPublicWithdrawal < DstCancellation`. The caller of `createDstEscrow` (the taker/resolver funding the destination escrow) is free to pick any packed `Timelocks` value as long as the single `DstCancellation` field is `<= srcCancellationTimestamp`.

`EscrowDst.publicWithdraw` gates on:
```solidity
function publicWithdraw(bytes32 secret, Immutables calldata immutables)
    external
    onlyAccessTokenHolder()
    onlyAfter(immutables.timelocks.get(TimelocksLib.Stage.DstPublicWithdrawal))
    onlyBefore(immutables.timelocks.get(TimelocksLib.Stage.DstCancellation))
``` [2](#0-1) 

`onlyAfter`/`onlyBefore` are strict comparisons against `block.timestamp`:
```solidity
modifier onlyAfter(uint256 start) { if (block.timestamp < start) revert InvalidTime(); _; }
modifier onlyBefore(uint256 stop) { if (block.timestamp >= stop) revert InvalidTime(); _; }
``` [3](#0-2) 

If the taker sets `DstPublicWithdrawal >= DstCancellation`, no `block.timestamp` can ever satisfy both conditions, so `publicWithdraw` is permanently unreachable for that escrow — as the question's proof idea correctly predicts. The same lack of ordering validation also lets a malicious taker push `DstWithdrawal >= DstCancellation`, which additionally kills the taker-only private `withdraw()` path (`onlyAfter(DstWithdrawal)`/`onlyBefore(DstCancellation)` at [4](#0-3) ), leaving `cancel()` (which returns the escrowed destination amount to the taker themselves, plus safety deposit) as the only reachable terminal state.

Because the taker is `msg.sender` of `createDstEscrow` — an ordinary, unprivileged call, not an owner/governance/whitelisted action — this satisfies the bounty's "unprivileged actor" requirement. The practical exploit: taker fills the order (or already knows the secret via the normal off-chain reveal), funds `createDstEscrow` with a corrupted timelock encoding that removes the public-withdrawal rescue window (and optionally the private one too), never calls `withdraw`, and after `DstCancellation` calls `cancel()` to reclaim their own deposited destination tokens and safety deposit — while the maker, whose source-side assets were already consumed by the taker's fill, never receives the destination-side funds and has no unprivileged/public path to force delivery. This is a temporary-to-permanent freeze/theft of the maker's expected swap proceeds, matching the bounty's "temporary freezing of funds during the live swap lifecycle" (or worse, theft) impact tier.

### Title
Missing timelock-ordering validation in `createDstEscrow` lets a taker disable the `DstPublicWithdrawal` rescue window - (File: contracts/BaseEscrowFactory.sol)

### Summary
`createDstEscrow` lets the calling taker supply arbitrary `timelocks` for the destination escrow, only constraining the absolute `DstCancellation` timestamp relative to `srcCancellationTimestamp`. No check ensures `DstWithdrawal < DstPublicWithdrawal < DstCancellation`, so a taker can set `DstPublicWithdrawal >= DstCancellation` (and even `DstWithdrawal >= DstCancellation`), collapsing the withdrawal window(s) to empty.

### Finding Description
`BaseEscrowFactory.createDstEscrow` ( [5](#0-4) ) copies `dstImmutables` from calldata, stamps `deployedAt`, and validates only `DstCancellation <= srcCancellationTimestamp`. `EscrowDst.publicWithdraw` and `EscrowDst.withdraw` rely purely on the relative ordering of the `DstWithdrawal`/`DstPublicWithdrawal`/`DstCancellation` stage offsets encoded in the same `Timelocks` word ( [6](#0-5) ). Because these offsets are independently taker-controlled 32-bit fields with no cross-field validation, a taker can construct a `Timelocks` value where `DstPublicWithdrawal >= DstCancellation`, making the `onlyAfter(DstPublicWithdrawal)`/`onlyBefore(DstCancellation)` pair in `publicWithdraw` unsatisfiable for any timestamp, and analogously for the taker-only `withdraw` path if `DstWithdrawal >= DstCancellation` is also chosen.

### Impact Explanation
This removes the public safety-net that lets any access-token holder rescue a maker's destination funds if the taker becomes unresponsive after the secret is known. A taker can guarantee that `cancel()` — which refunds the deposited destination amount and safety deposit back to the taker — is the only reachable terminal state, letting the taker keep both the maker's already-transferred source-chain assets and their own destination deposit. This is a temporary/permanent freezing (and effectively theft) of the maker's expected swap proceeds during the live swap lifecycle.

### Likelihood Explanation
High: the caller of `createDstEscrow` fully controls the `timelocks` field with only one weak, unrelated absolute-value check; no additional privilege, secret knowledge, or trusted role is required to construct this malformed value, only intent.

### Recommendation
In `createDstEscrow`, validate the internal ordering of the destination stages, e.g. require `DstWithdrawal < DstPublicWithdrawal < DstCancellation` (using `TimelocksLib.get` for each stage) before deploying the escrow, in addition to the existing `srcCancellationTimestamp` bound.

### Proof of Concept
1. Taker calls `createDstEscrow` with `dstImmutables.timelocks` encoded so that `Stage.DstPublicWithdrawal offset >= Stage.DstCancellation offset` (both measured from `deployedAt`), while keeping `DstCancellation <= srcCancellationTimestamp` to pass the only existing check.
2. `createDstEscrow` succeeds and deploys the escrow ( [7](#0-6) ).
3. At any `block.timestamp`, calling `publicWithdraw` reverts with `InvalidTime` — either `onlyAfter(DstPublicWithdrawal)` fails (too early) or `onlyBefore(DstCancellation)` fails (too late, since `DstCancellation <= DstPublicWithdrawal`) — proving the window is empty ( [2](#0-1) ).
4. After `DstCancellation`, the taker calls `cancel()` and reclaims the deposited destination amount plus safety deposit, with no unprivileged actor ever able to have forced delivery to the maker ( [8](#0-7) ).

library TimelocksLib {
    enum Stage {
        SrcWithdrawal,
        SrcPublicWithdrawal,
        SrcCancellation,
        SrcPublicCancellation,
        DstWithdrawal,
        DstPublicWithdrawal,
        DstCancellation
    }

    uint256 private constant _DEPLOYED_AT_MASK = 0xffffffff00000000000000000000000000000000000000000000000000000000;
    uint256 private constant _DEPLOYED_AT_OFFSET = 224;

    /**
     * @notice Sets the Escrow deployment timestamp.
     * @param timelocks The timelocks to set the deployment timestamp to.
     * @param value The new Escrow deployment timestamp.
     * @return The timelocks with the deployment timestamp set.
     */
    function setDeployedAt(Timelocks timelocks, uint256 value) internal pure returns (Timelocks) {
        return Timelocks.wrap((Timelocks.unwrap(timelocks) & ~uint256(_DEPLOYED_AT_MASK)) | value << _DEPLOYED_AT_OFFSET);
    }

    /**
     * @notice Returns the start of the rescue period.
     * @param timelocks The timelocks to get the rescue delay from.
     * @return The start of the rescue period.
     */
    function rescueStart(Timelocks timelocks, uint256 rescueDelay) internal pure returns (uint256) {
        unchecked {
            return rescueDelay + (Timelocks.unwrap(timelocks) >> _DEPLOYED_AT_OFFSET);
        }
    }

    /**
     * @notice Returns the timelock value for the given stage.
     * @param timelocks The timelocks to get the value from.
     * @param stage The stage to get the value for.
     * @return The timelock value for the given stage.
     */
    function get(Timelocks timelocks, Stage stage) internal pure returns (uint256) {
        uint256 data = Timelocks.unwrap(timelocks);
        uint256 bitShift = uint256(stage) * 32;
        // The maximum uint32 value will be reached in 2106.
        return (data >> _DEPLOYED_AT_OFFSET) + uint32(data >> bitShift);
    }
