Based on my investigation, I found a plausible analog but could not fully confirm the root-cause chain in `stackslib/src/net/p2p.rs` (the module that polls/consumes the proposal-validation `JoinHandle`) before running out of search budget. ### Title
Unrecovered panic in the detached block-proposal validation thread can permanently wedge `/v3/block_proposal`, starving signers of validation responses - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
`RPCBlockProposalRequestHandler::try_handle_request` spawns a bare, detached OS thread to run `NakamotoBlockProposal::validate(...)` and marks the node as busy (`is_proposal_thread_running`) until that thread's result is consumed. The thread has no panic containment: it is a plain `thread::Builder::spawn`, and the only way its outcome reaches the rest of the node is via `receiver.notify_proposal_result(result)`, called only if `validate()` returns normally.

### Finding Description
`spawn_validation_thread` runs `self.validate(...)` on a bare thread and calls `receiver.notify_proposal_result(result)` only on normal return: [1](#0-0) 

`try_handle_request` refuses new proposals while a prior one is in flight (`network.is_proposal_thread_running()`), and marks the thread as running via `network.set_proposal_thread(thread_info)` once spawned: [2](#0-1) 

`validate()` itself walks attacker/miner-controlled block data — header fields, transactions, and mining/execution via `builder.try_mine_tx_with_len` — all of which are reachable with a single crafted `BlockProposal` from the one miner slot: [3](#0-2) [4](#0-3) 

This is the same bug class as the Kubo advisory: block bytes chosen by a remote party are decoded/processed on a goroutine/thread that is detached from the request and has no panic recovery, so a crafted input's panic kills the worker silently instead of failing just that request. In Kubo, that crashed the whole daemon (Go aborts on an unrecovered goroutine panic). In Rust, a panic in a `thread::spawn`'d thread does *not* by default kill the whole process — it only kills that thread — but the important consequence here is not process death, it's that `receiver.notify_proposal_result` is skipped when `validate()` panics, so whatever housekeeping is supposed to run on completion (via `notify_proposal_result`, or via a later `.join()` on the stored `JoinHandle` in `stackslib/src/net/p2p.rs`) may never fire correctly for the panicking case.

**What I could not fully verify:** the exact code in `stackslib/src/net/p2p.rs` that later polls/joins this `JoinHandle` and clears `is_proposal_thread_running()`/`proposal_thread`. I located the setter (`set_proposal_thread`) and consumer flag (`is_proposal_thread_running`) usages in `p2p.rs` via `grep_search`, but ran out of budget before reading that logic in detail to confirm whether it correctly handles a panicked (`Err`) `JoinHandle::join()` result and resets the flag, or whether it assumes the thread always completes normally (matching `notify_proposal_result`) and thus never resets on panic.

### Impact Explanation
If the `p2p.rs` polling logic does not gracefully handle a panicked join (which is a real possibility, given the codebase's pervasive style of treating any unexpected thread failure as fatal-and-unrecoverable, e.g. mutex-poison `panic!()`/`.expect("FATAL: mutex poisoned")` patterns seen throughout `stacks-node/src/globals.rs` and `stackslib/src/chainstate/stacks/miner.rs`), then a single crafted block proposal from the current miner would leave `is_proposal_thread_running()` permanently `true`. Every subsequent `/v3/block_proposal` submission — from any signer, for any future block — would then receive `TOO_MANY_REQUESTS_STATUS` (429) forever, until the node process is restarted: [5](#0-4) 

On the signer side, `handle_block_proposal` relies on `submit_block_for_validation` to get a verdict; if the node never answers, the signer can never move past "wait for validation" and can never sign any future block through that node: [6](#0-5) 

This would match the in-scope "High" impact category: a signer wedged into never signing valid blocks.

### Likelihood Explanation
Reachable by the single one-slot miner: it only needs to construct one `BlockProposal` (header + transactions) that triggers a panic somewhere inside `validate()`'s static/tx-execution path and gossip it once to the `.miners` StackerDB slot; every signer's configured node would independently spawn the validation thread and hit the same panic. No majority, no other signer's key, and no local/auth-token access is required. However, I was unable to confirm a concrete panicking input inside `validate()`'s call graph (e.g., an unchecked index, arithmetic overflow, or `.unwrap()` in header/consensus-hash/tx-execution code) or confirm that `p2p.rs` fails to reset the busy flag after a panicked join — both of which are necessary to prove this is exploitable rather than already handled defensively.

### Recommendation
- Wrap the body of the `"block-proposal"` thread in `spawn_validation_thread` with `std::panic::catch_unwind`, and always call `receiver.notify_proposal_result(...)` (with a synthetic rejection, e.g. `ValidateRejectCode::ChainstateError`) even when the closure panics.
- In `stackslib/src/net/p2p.rs`, confirm that whatever polls the stored `JoinHandle`/`ProposalThreadInfo` treats a panicked join as a terminal, recoverable event: log it, clear `proposal_thread`, and unblock `is_proposal_thread_running()` so subsequent proposals are not permanently rejected with 429.
- Add a fuzz/property test that feeds structurally-valid-but-semantically-adversarial `NakamotoBlockProposal` values (malformed transactions, edge-case header values) directly into `validate()` to catch any reachable panics before they can be triggered by a single malicious miner in production.

### Proof of Concept
Not able to produce a concrete crafted `BlockProposal` payload that panics inside `validate()`, since I did not locate a specific unguarded `.unwrap()`/indexing bug in the transaction-execution or header-processing path within my available search budget; a background agent with full file access should audit `NakamotoBlockProposal::validate` and its callees (`check_block_has_valid_tenure`, `check_block_has_valid_parent`, `NakamotoChainState::validate_normal_nakamoto_block_burnchain`, `builder.try_mine_tx_with_len`, `builder.mine_nakamoto_block`) for panicking failure modes on attacker-controlled bytes, and separately confirm the `p2p.rs` join/reset behavior described above.
