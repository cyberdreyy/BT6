## Analog Found: Signer vote weight double-counted across accept and reject tallies (stale rejection weight survives a legitimate flip to acceptance)

### Title
Mis-tallied signer weight: a signer's rejection and later acceptance are both counted, inflating `total_weight_rejected`/`total_weight_approved` simultaneously - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The external report's bug class is "the contract computes a corrected/final value (`repayAmountFinal`) but still acts on the original, uncorrected value (`repayAmount`)." The structural analog here is the node-side `StackerDBListener`, which tracks two independent weight tallies for the same block (`total_weight_approved`, `total_weight_rejected`) gated by two different, non-overlapping dedup sets, so a single signer's weight can be counted into both tallies for the same block instead of only reflecting its current vote.

### Finding Description
`BlockStatus` tracks per-block consensus state with two separate guards: [1](#0-0) 

For an acceptance (`BlockResponse::Accepted`), the weight is only added if the signer's slot is not already in `gathered_signatures`: [2](#0-1) 

For a rejection (`BlockResponse::Rejected`), the weight is only added if the slot is not already in the *separate* `responded_signers` set: [3](#0-2) 

These two guards (`gathered_signatures` for approvals, `responded_signers` for rejections) are independent data structures that are never reconciled against each other. Per the signer's own documented state machine, a signer legitimately transitions `LocallyRejected -> LocallyAccepted` on re-evaluation (e.g. `should_reevaluate_reject_reason` allows reconsidering a stale rejection reason), and broadcasts a fresh, validly-signed `BlockAccepted` for the same `signer_signature_hash`: [4](#0-3) [5](#0-4) 

When that happens:
1. The signer's earlier `BlockResponse::Rejected` sets `responded_signers.insert(slot_id)` and adds the signer's weight to `total_weight_rejected`.
2. The signer's later, cryptographically valid `BlockResponse::Accepted` for the *same block* is checked only against `gathered_signatures` (untouched by step 1), so it passes and adds the same signer's weight to `total_weight_approved` as well.

Nothing ever removes or reconciles the stale weight in `total_weight_rejected`. The same signer's weight is now double-counted: once against the block and once for it, for the same `signer_signature_hash`.

### Impact Explanation
`SignerCoordinator::wait_for_signatures` uses these two independently-inflatable tallies to decide the fate of the block: it declares a global rejection when `total_weight_rejected + weight_threshold > total_weight`, and otherwise declares acceptance when `total_weight_approved >= weight_threshold`: [6](#0-5) 

Because a signer's stale rejection weight persists after that same signer later validly accepts, `total_weight_approved + total_weight_rejected` can exceed `total_weight` for the same signer set — the "aggregated weight" no longer reflects the set of currently verified accepts. In the affected direction, phantom leftover rejection weight from signers who have since accepted can push the block over the rejection threshold and cause the miner to declare the block dead (`SignersRejected`) even though a legitimate majority has since accepted it — a liveness fault where a valid, canonical block that should reach 70% consensus is wrongly abandoned due to miscounted, stale votes. This is exactly the class of bug flagged by the rules: mis-tallied recount of a rejection/acceptance breaking the aggregated-weight-vs-verified-accepts equality.

### Likelihood Explanation
This requires no majority collusion, no external key, and no malicious behavior — it is triggered by the signer's own documented, legitimate `LocallyRejected -> LocallyAccepted` re-evaluation path (e.g. a rejection reason such as `RejectedInPriorRound`/transient chainstate mismatch that resolves before the pre-commit/signature threshold is reached), combined with the coordinator's use of disjoint dedup sets. A single signer flipping its vote after an initial rejection — a normal and expected event given retries/timeouts/reproposals in the flow — is sufficient to trigger the double count.

### Recommendation
Use a single per-signer "current vote" record (e.g. keyed by slot_id, storing the latest verdict) rather than two independent dedup sets, and recompute `total_weight_approved`/`total_weight_rejected` from the current set of votes whenever a signer's vote changes, subtracting any previously counted weight from the opposite tally before adding to the new one.

### Proof of Concept
1. Coordinator waits on `wait_for_signatures` for a proposed block with `signer_signature_hash = H`.
2. Signer S (weight `w`) sends `BlockResponse::Rejected` for `H` (e.g., transient chainstate mismatch). `stackerdb_listener.rs` inserts S's slot into `responded_signers` and adds `w` to `total_weight_rejected`.
3. S re-evaluates per `should_reevaluate_reject_reason`/pre-commit re-evaluation and legitimately signs and broadcasts `BlockResponse::Accepted` for the same `H`.
4. Since S's slot is not in `gathered_signatures`, the coordinator adds `w` to `total_weight_approved` as well, without removing `w` from `total_weight_rejected`.
5. `total_weight_rejected` now contains stale weight `w` that no longer reflects S's current vote. If other signers' genuine rejections plus this stale `w` cross `total_weight - weight_threshold`, the coordinator declares the block globally rejected (`SignersRejected`) even though S (and possibly enough other signers) have actually accepted it.
