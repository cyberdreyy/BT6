### Title
Stale confirmations from removed multisig members are still counted toward the approval threshold, allowing request execution below `num_confirmations` live members - (File: multisig2/src/lib.rs)

### Summary
The reported CVE is a use-after-free where a buffer object is dereferenced after having already been freed, because the freeing code path does not invalidate every reference to it. The same "stale reference counted as live" bug class exists in the multisig contracts: when a member is removed via `DeleteMember` (or `DeleteKey` in the legacy `multisig` contract), the contract only cleans up *requests authored by* that member. It never scans `self.confirmations` to strip that member's confirmation entries from *other* still-pending requests they had previously confirmed. Those stale confirmations remain in the `HashSet` and are still counted by `confirm()` toward `num_confirmations`, letting a request execute with fewer distinct, currently-valid members than the configured threshold.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` decides whether to execute a request purely based on the size of the stored confirmations set: [1](#0-0) 

`delete_member()` is the only code path that removes a member and its bookkeeping, but it filters requests strictly by authorship (`r.member == member`), and only clears confirmations for those self-authored requests. It never removes the deleted member's entry from `self.confirmations` for requests authored by *other* members that this member had already confirmed: [2](#0-1) 

Because the deleted member's account/public-key string is never scraped out of other requests' `confirmations` sets, `confirmations.len()` in `confirm()` still includes that now-invalid member. This breaks the binding the multisig is supposed to enforce:

```
num_distinct_current_members_who_confirmed(request) >= num_confirmations
```

which after a member removal can become false while the code still treats it as satisfied, i.e. `confirmations.len() + 1 >= num_confirmations` is true even though one of the counted confirmers is no longer a member.

The identical pattern exists in the legacy key-based contract, where `DeleteKey` filters outstanding requests by `r.signer_pk == pk` (authorship) and likewise never purges the deleted key from confirmation sets of requests authored by other keys: [3](#0-2) [4](#0-3) 

### Impact Explanation
This is a Critical-class finding per the rules: "a multisig request executed below threshold." Once a request executes with fewer live-member confirmations than `num_confirmations`, any action bundled in that request — `Transfer`, `FunctionCall`, `AddKey`/full-access-key grants, `AddMember`, further `DeleteMember` — is authorized outside the K-of-N guarantee the multisig exists to enforce. This can directly move NEAR out of the account, or install a full-access key / add a rogue member controlled by fewer than the required number of legitimate signers, effectively breaking custody of everything the multisig controls.

### Likelihood Explanation
No exotic conditions are required beyond the contract's own documented lifecycle: a request is created and partially confirmed by some members (fewer than threshold), and later, in the normal course of multisig membership rotation, one of those confirming members is removed via `DeleteMember`/`DeleteKey` (e.g., because a signer left, rotated keys, or was compromised — the very scenario multisig membership rotation is designed to handle safely). The stale confirmation silently survives, and the very next `confirm()` call from any remaining valid member can push the count over threshold and trigger execution, even though one fewer live member than configured actually approved it. This requires no privileged bypass or ignored initialization — it is a direct consequence of `delete_member`/`DeleteKey` filtering by request authorship instead of clearing confirmations across all requests.

### Recommendation
When removing a member (`delete_member`) or key (`DeleteKey`), iterate over all entries in `self.confirmations` (not just requests authored by that member) and remove the deleted member's/key's entry from every confirmation set. Alternatively, re-validate at `confirm()` time that every account/key present in a request's confirmations set is still a current member before counting it toward `num_confirmations`, discarding stale entries lazily.

### Proof of Concept
1. Initialize `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A.add_request(X)` creates request `X` (unconfirmed, authored by `A`).
3. `D.confirm(X)` → `confirmations(X) = {D}`.
4. `B.confirm(X)` → `confirmations(X) = {D, B}` (2 of 3, not yet executed).
5. Separately, members legitimately remove `D` from the multisig via a normal `DeleteMember{D}` request that gets 3 valid confirmations from `A, B, C` and executes `delete_member(D)`
   (see [5](#0-4) ). Because request `X` was authored by `A` (not `D`), it is untouched — `confirmations(X)` still contains `"D"`.
6. `D` is now removed from `self.members`; only `A, B, C` remain.
7. `A.confirm(X)` → `confirmations.len() (=2, including stale "D") + 1 = 3 >= num_confirmations (3)` at [6](#0-5) , so `execute_request(X)` runs.
8. Result: request `X` (e.g. a `Transfer`) executes with approvals from only `{D(removed), B, A}` — just 2 currently valid members (`A`, `B`) — despite `num_confirmations = 3`, violating the multisig's K-of-N guarantee.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
