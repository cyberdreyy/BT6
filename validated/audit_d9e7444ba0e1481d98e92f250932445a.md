### Title
Same-origin (credential) policy bypass: non-KYC wallets can withdraw via freely transferable tranche tokens - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The Firefox CVE is a same-origin policy bypass: a security check applied at one entry point is sidestepped through an alternate path to the same resource. The analog in idle-tranches is the Keyring KYC/credential policy. `isWalletAllowed` gates the deposit path, but `IdleCDOTranche` is a plain ERC20 with no transfer hook, and the withdraw/claim path (`requestWithdraw` → `IdleCreditVault.claimWithdrawRequest`) never re-checks the credential of the token holder. Any address — including one that could never pass KYC — can receive tranche tokens and exit into underlying.

### Finding Description
- `IdleCDOEpochVariant.isWalletAllowed` enforces `IKeyring(keyring).checkCredential(...)` and is applied to depositors via `_checkAllowed` in `IdleCDOEpochQueue` (`contracts/IdleCDOEpochQueue.sol:415-421`) and the deposit flow.
- `IdleCDOTranche` (`contracts/IdleCDOTranche.sol:7-41`) is a bare ERC20: `mint`/`burn` are minter-gated, but `transfer`/`transferFrom` have no `_beforeTokenTransfer` hook and no credential check. Tranche tokens are freely transferable to any EOA or contract.
- The exit path does not check the holder's credential: `IdleCDOEpochVariant.claimWithdrawRequest` (`contracts/IdleCDOEpochVariant.sol:967-971`) forwards `msg.sender` directly to `IdleCreditVault.claimWithdrawRequest`, and `IdleCreditVault._claimFundedWithdrawRequest` (`contracts/strategies/idle/IdleCreditVault.sol:319-349`) only verifies the epoch-wait invariant (`epochNumber <= lastWithdrawRequest[_user]`), burns receipts, and pays underlying — no `isWalletAllowed` call anywhere in `IdleCreditVault` (its only origin check is `_onlyIdleCDO` on the caller, which is satisfied by the CDO, not the end user).
- The same holds for `claimInstantWithdrawRequest` (`contracts/IdleCDOEpochVariant.sol:975-979`) and the defaulted/loss-adjusted claim paths (`_claimPostDefaultWithdrawRequest`, `_claimDefaultedWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` at `contracts/strategies/idle/IdleCreditVault.sol:760-801`), which also never consult Keyring.

### Impact Explanation
The credential policy is the pool's origin boundary: only KYC-passing lenders may hold exposure and pull underlying. A sanctioned or non-KYC address can acquire tranche tokens on a secondary transfer (or be gifted them by a KYC'd holder) and call `requestWithdraw`/`claimWithdrawRequest` to redeem underlying at par — obtaining a payout the policy exists to deny. In default/recovery scenarios the same gap lets an unvetted holder claim from `defaultRecoveryReserve`, diluting recovery available to credentialed claimants. This is a broken access invariant: one receipt still pays once, but to a party the protocol explicitly excludes.

### Likelihood Explanation
High feasibility, attacker-unprivileged. Requires only (a) `keyring != address(0)` with a policy that rejects the attacker, and (b) any willing or compromised KYC holder (or a DEX purchase) to route tranche tokens to the attacker. No privileged action needed; the epoch-wait is the only timing constraint and is satisfiable by waiting one epoch like any legitimate request. Caveat: this is a policy/compliance bypass rather than a direct drain of other users' principal — loss materializes as prohibited-party redemption and reserve dilution, not theft of a specific victim's balance.

### Recommendation
Enforce the credential check on the exit side, symmetric to deposits: call `isWalletAllowed(_user)` inside `IdleCreditVault.claimWithdrawRequest`/`claimInstantWithdrawRequest` (or in `IdleCDOEpochVariant.requestWithdraw`/`claimWithdrawRequest`/`claimInstantWithdrawRequest`) so a transferred-in holder cannot redeem, and optionally add a `_beforeTokenTransfer` hook on `IdleCDOTranche` (or a dedicated non-transferable mode) to prevent policy bypass at the token layer.

### Proof of Concept
```solidity
// Foundry fork PoC sketch against an epoch-variant pool with keyring set.
// Setup: pool live, keyringPolicyId set so `attacker` fails checkCredential.
function test_NonKycHolderWithdrawsViaTransferredTranches() external {
    address kycHolder = makeAddr('kycHolder');
    address attacker  = makeAddr('attacker'); // fails IKeyring.checkCredential

    _depositWithUser(kycHolder, 10_000 * ONE_SCALE, true); // KYC'd deposit

    // Policy check applied at deposit; transfers are unrestricted ERC20.
    uint256 trancheBal = IERC20Detailed(address(AAtranche)).balanceOf(kycHolder);
    vm.prank(kycHolder);
    AAtranche.transfer(attacker, trancheBal);

    // Attacker was never KYC'd and could not deposit, but can exit.
    _startEpochAndCheckPrices(0);
    vm.prank(attacker);
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest(); // succeeds despite isWalletAllowed(attacker) == false
    assertEq(underlying.balanceOf(attacker) - balPre, requested);
}
```
Note: I could not fully verify whether `requestWithdraw` itself re-checks `isWalletAllowed` within the iteration limit; if it does, the residual gap still exists at the claim step shown above (`claimWithdrawRequest`/`_claimFundedWithdrawRequest` contain no credential check).
