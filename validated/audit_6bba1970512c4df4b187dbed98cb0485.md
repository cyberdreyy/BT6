### Title
Unbounded per-attempt hang in Azure Key Vault secret resolution outside job timeout enforcement - ([File: helpers/azure_key_vault/service/azure_key_vault.go])

### Summary
`defaultAzureKeyVault.GetSecret` calls `v.client.GetSecret` with `context.Background()`, which has no deadline or cancellation. This call is reached from `Build.resolveSecrets` → `Build.attemptResolveSecrets`, which runs **before** the job-level `context.WithTimeout(ctx, b.GetBuildTimeout())` is even created in `Build.Run`. Combined with the pipeline-author-controlled `SECRETS_RETRIEVAL_ATTEMPTS` variable (clamped to 1-10) and the attacker-influenced `azure_key_vault.server.url` field in the `secrets:` YAML keyword, a job can point the runner at a slow/non-responding endpoint and hang the resolve-secrets stage for a multiple of the attempt count with no upper bound and no way for the runner's own timeout machinery to intervene.

### Finding Description
`Build.Run` executes stages in this order: [1](#0-0) 

1. `b.resolveSecrets(trace)` is invoked at line 1549, **before** `ctx, cancel := context.WithTimeout(ctx, b.GetBuildTimeout())` is created at line 1560. This means the job's configured `CI_JOB_TIMEOUT` / build timeout does not apply to secret resolution at all — there is no context deadline in scope for this stage.

2. `resolveSecrets` calls `attemptResolveSecrets(trace, b.GetSecretsRetrievalAttempts())`: [2](#0-1) 
`retry.New()` defaults to `ctx: context.Background()` unless `.WithContext()` is explicitly called, which `attemptResolveSecrets` never does — so the retry loop itself carries no cancellable context. [3](#0-2) 

3. `SecretsRetrievalAttempts` is a job-influenced setting via the `SECRETS_RETRIEVAL_ATTEMPTS` variable, clamped to the range [1, 10]: [4](#0-3) 
An attacker can therefore force up to 10 retry attempts.

4. Each attempt eventually calls `azureKeyVaultResolver.Resolve()` → `s.GetSecret(name, version)`: [5](#0-4) 
which reaches `defaultAzureKeyVault.GetSecret`: [6](#0-5) 
This uses `context.Background()` for the actual network call to `v.client.GetSecret`, with no per-request timeout of any kind.

5. The `server.URL` used to construct the Azure client (`NewAzureKeyVault`) comes from `spec.AzureKeyVaultServer.URL`, which is part of the `secrets:` block in `.gitlab-ci.yml` (the same mechanism as Vault's `server.url`, confirmed by the `expandVariables` test coverage showing `Server.URL` is a job-payload-carried, pipeline-config-originated field): [7](#0-6)  Note that only `JWT` is expanded via CI variables here — `URL` itself is taken as-is from the secrets configuration, which is populated from the `.gitlab-ci.yml` `secrets:` keyword content, editable by anyone able to modify pipeline configuration (a normal, unprivileged pipeline author with repo push access).

Because there is no timeout anywhere in this chain (no context deadline on `GetSecret`'s HTTP call, no context propagated into the retry runner, and no build-timeout context in scope at the point `resolveSecrets` is called), a slow-responding or connection-holding endpoint at the attacker-supplied URL causes each of up to 10 attempts to block indefinitely. There is no existing check (timeout, deadline, or otherwise) that stops this.

### Impact Explanation
A pipeline author with control over `.gitlab-ci.yml` can set `secrets.<name>.azure_key_vault.server.url` to an endpoint they control and configure `SECRETS_RETRIEVAL_ATTEMPTS` up to 10. If that endpoint accepts the TCP connection but never responds (or responds slowly), the runner's job-execution goroutine for that job is blocked indefinitely per attempt, multiplied by the attempt count — with no bound at all since neither the per-request context nor the retry loop carries any deadline, and critically the job-level build timeout (`b.GetBuildTimeout()`) is not yet active during this stage. On a runner with a limited concurrent job slot count, this ties up a job-execution slot indefinitely, delaying or starving other queued jobs (including jobs from other projects/tenants sharing the runner), which matches the "multi-tenant disruption" impact described in the question.

### Likelihood Explanation
- Preconditions: runner configured to support Azure Key Vault secrets, attacker has permission to edit `.gitlab-ci.yml` / trigger a pipeline with a `secrets:` block (an ordinary developer permission level, not an admin).
- Feasibility: high — the attacker just needs to control an HTTP endpoint that never completes the TLS handshake or holds the connection open without sending a response (a trivial "slowloris"-style listener).
- Repeatability: fully repeatable and can be triggered per-job, at will, by anyone able to push CI config changes.

### Recommendation
- Move `resolveSecrets` to occur after the job-level `context.WithTimeout` is established in `Build.Run`, or introduce a dedicated timeout context for the resolve-secrets stage before calling `attemptResolveSecrets`.
- Pass a `context.Context` with an explicit, bounded timeout (not `context.Background()`) into `defaultAzureKeyVault.GetSecret`'s call to `v.client.GetSecret`, and propagate a cancellable context through `azureKeyVaultResolver.Resolve()` and `AzureKeyVault.GetSecret` interface.
- Ensure `retry.New()` in `attemptResolveSecrets` is created with `.WithContext(ctx)` bound to the job/prepare timeout so retries stop once the job-level deadline is exceeded.

### Proof of Concept
Go unit test using `httptest` to start a TCP listener that accepts connections but never writes a response:
```go
func TestGetSecret_HangsWithoutTimeout(t *testing.T) {
    ln, _ := net.Listen("tcp", "127.0.0.1:0")
    defer ln.Close()
    go func() {
        for {
            conn, err := ln.Accept()
            if err != nil { return }
            _ = conn // never respond, keep connection open
        }
    }()

    server := spec.AzureKeyVaultServer{
        ClientID: "id", TenantID: "tenant", JWT: "jwt",
        URL: "http://" + ln.Addr().String(),
    }
    v, err := service.NewAzureKeyVault(server)
    require.NoError(t, err)

    done := make(chan struct{})
    go func() {
        _, _ = v.GetSecret("name", "version")
        close(done)
    }()

    select {
    case <-done:
        t.Fatal("expected GetSecret to block indefinitely without a context deadline")
    case <-time.After(5 * time.Second):
        // confirms no request-level timeout is enforced
    }
}
```
Expected assertion: the call to `GetSecret` does not return within a bounded window (e.g. 5s), proving no request-level timeout exists distinct from job-level cancellation — and that `attemptResolveSecrets`/`Build.Run`'s ordering means the job-level context isn't even in scope yet to bound it externally.

func (b *Build) resolveSecrets(trace JobTrace) error {
	if b.Secrets == nil {
		return nil
	}

	b.Secrets.ExpandVariables(b.GetAllVariables())

	return b.attemptResolveSecrets(trace, b.GetSecretsRetrievalAttempts())

// wrapSecretResolvingError converts a classified secret-resolution failure
// into a BuildError with a failure reason matching the cause of the failure.
// Historically all secret-resolution failures were reported as
// RunnerSystemFailure (the default for untagged errors), even when the
// failure was caused by the job's configuration — for example a secrets
// provider denying access to the requested path. Resolvers can classify
// their failures with the semantic error types from helpers/secrets:
//
//   - secrets.ResolvingConfigurationError → ConfigurationError
//   - secrets.ResolvingExternalDependencyError → RunnerExternalDependencyFailure
//
// Unclassified failures keep the previous classification and are reported
// as RunnerSystemFailure.
func wrapSecretResolvingError(err error) error {
	var buildErr *BuildError
	if errors.As(err, &buildErr) {
		return err
	}

	var configurationErr *secrets.ResolvingConfigurationError
	if errors.As(err, &configurationErr) {
		return &BuildError{FailureReason: ConfigurationError, Inner: err}
	}

	var externalDependencyErr *secrets.ResolvingExternalDependencyError
	if errors.As(err, &externalDependencyErr) {
		return &BuildError{FailureReason: RunnerExternalDependencyFailure, Inner: err}
	}

	return &BuildError{FailureReason: RunnerSystemFailure, Inner: err}
}

func (b *Build) GetSecretsRetrievalAttempts() int {
	return b.Settings().SecretsRetrievalAttempts
}

func (b *Build) attemptResolveSecrets(trace JobTrace, attempts int) error {
	retryRunner := retry.New().WithMaxTries(attempts)

	if b.IsFeatureFlagOn(featureflags.UseExponentialBackoffStageRetry) {
		backoffConfig := b.getStageRetryBackoffConfig()
		retryRunner = retryRunner.
			WithBackoff(backoffConfig.Min, backoffConfig.Max).
			WithBuildLog(&b.logger)
	}

	return retry.NewNoValue(retryRunner, func() error {
		return b.executeResolveSecretsStage(trace)
	}).Run()
}

func (b *Build) validateAttemptSettings() []error {
	var errs []error

	clamp := func(variable *int, varName string) {
		const minAttempts, maxAttempts = 1, 10
		val := max(minAttempts, min(maxAttempts, *variable))
		if val != *variable {
			*variable = val
			errs = append(errs, fmt.Errorf("%s: number of attempts out of the range [%d, %d], clamping to: %d", varName, minAttempts, maxAttempts, *variable))
		}
	}

	clamp(&b.buildSettings.ExecutorJobSectionAttempts, "EXECUTOR_JOB_SECTION_ATTEMPTS")
	clamp(&b.buildSettings.GetSourcesAttempts, "GET_SOURCES_ATTEMPTS")
	clamp(&b.buildSettings.ArtifactDownloadAttempts, "ARTIFACT_DOWNLOAD_ATTEMPTS")
	clamp(&b.buildSettings.RestoreCacheAttempts, "RESTORE_CACHE_ATTEMPTS")
	clamp(&b.buildSettings.SecretsRetrievalAttempts, "SECRETS_RETRIEVAL_ATTEMPTS")

	return errs
}

func (v *azureKeyVaultResolver) Resolve() (string, error) {
	if !v.IsSupported() {
		return "", secrets.NewResolvingUnsupportedSecretError(resolverName)
	}

	secret := v.secret.AzureKeyVault
	s, err := newVaultService(secret.Server)
	if err != nil {
		return "", err
	}

	name := secret.Name
	version := secret.Version

	data, err := s.GetSecret(name, version)

	if err != nil {
		return "", err
	}

	return fmt.Sprintf("%v", data), nil
}

func (v *defaultAzureKeyVault) GetSecret(name string, version string) (interface{}, error) {
	resp, err := v.client.GetSecret(context.Background(), name, version, nil)
	if err != nil {
		return nil, fmt.Errorf("getting secret failed: %w", err)
	}

	if resp.Value == nil {
		return "", common.ErrSecretNotFound
	}

	return *resp.Value, err
}
