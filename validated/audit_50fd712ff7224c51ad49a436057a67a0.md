### Title
`validate_tenure_change_payload` (v1) misses locally-accepted tenure-start blocks via `get_last_globally_accepted_block`, allowing v1-pinned signers to sign a duplicate tenure-start block - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`GlobalStateView::validate_tenure_change_payload` in v1 uses `signer_db.get_last_globally_accepted_block` to guard against duplicate tenure-start blocks, while the v2 implementation uses `signer_db.get_last_signed_block`, which also matches locally-accepted (signed-but-not-yet-globally-accepted) blocks. This is a real and intentional-looking divergence documented in the codebase itself, and it lets a miner propose a second, competing tenure-start block in a tenure where one block has already been locally accepted by v1-pinned signers, bypassing the `DuplicateBlockFound` guard.

### Finding Description
`SignerDb::get_last_signed_block` (`stacks-signer/src/signerdb.rs:1572-1585`) returns the last block in a tenure whose state is `GloballyAccepted` OR `LocallyAccepted` — i.e., any block that carries this signer's own signature or the observed group's signature. `SignerDb::get_last_globally_accepted_block` only matches `GloballyAccepted` state. In v2's `validate_tenure_change_payload` (`stacks-signer/src/chainstate/v2.rs:344-357`), the duplicate check explicitly calls `get_last_signed_block`, with a comment stating "Only blocks we have signed (locally or globally accepted) count here." In v1's `validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs:505-518`), the equivalent check calls `get_last_globally_accepted_block` instead.

This means: if a first tenure-start block has crossed the 70% local-signature threshold (`mark_locally_accepted`) but the network/node has not yet reported it as globally accepted (no `NewBlock` event processed yet), a v1-pinned signer's `check_proposal` → `validate_tenure_change_payload` will find `None` for `get_last_globally_accepted_block` and skip the `DuplicateBlockFound` rejection, even though a signed sibling block already exists in that same tenure. The unit test `check_tenure_change_rejects_when_locally_accepted_block_exists` (`stacks-signer/src/chainstate/tests/v2.rs:755-850`) explicitly documents this exact scenario and confirms it was a real bug that was fixed for v2 ("Before the fix, this would have incorrectly passed because `get_last_globally_accepted_block` would not find the locally-accepted block") — but the fix was only applied to v2, not v1.

The other guard invoked earlier in `validate_tenure_change_payload`, `check_tenure_change_confirms_parent`, only validates the **parent** tenure's last block, not the current tenure being started — so it does not catch a duplicate tenure-start attempt within the same tenure. This leaves the duplicate check as the sole guard against re-proposing the tenure-start block, and it is exactly this guard that is broken on v1.

### Impact Explanation
This breaks the uniqueness/canonicity guarantee that at most one tenure-start block should be locally accepted per tenure. A v1-pinned signer can be induced to sign a second, competing `BlockFound` tenure-change block for a tenure that already has a locally-accepted sibling, splitting signer weight across two competing tenure-start blocks and enabling the miner to fork the tenure — a Critical chain-safety violation (a signer signing a conflicting/non-canonical block).

### Likelihood Explanation
Preconditions: a mixed-version signer fleet with at least one signer pinned to the v1 chainstate view (e.g. via test/config knobs pinning the protocol version), and a window where a tenure-start block has reached local (not yet global) acceptance. An attacker with a single winning miner slot can, within that window, gossip a second tenure-change `BlockProposal` for the same tenure; any v1-pinned signer that receives it will fail to reject it via `DuplicateBlockFound`. This requires only the standard single-miner-slot-plus-gossip capability and is repeatable each time a v1 signer processes a proposal during the local-acceptance-but-not-yet-global-acceptance window.

### Recommendation
Change v1's `validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs:505-509`) to use `signer_db.get_last_signed_block` instead of `get_last_globally_accepted_block`, matching the v2 semantics, so that both locally- and globally-accepted blocks in the tenure are treated as "already signed" for the duplicate check.

### Proof of Concept
Mirror the existing v2 test `check_tenure_change_rejects_when_locally_accepted_block_exists` (`stacks-signer/src/chainstate/tests/v2.rs:755-850`) but target the v1 `SortitionsView`/`check_proposal` path (as in `chainstate/tests/v1.rs`):
1. Set up a v1 `sortitions_view` and `signer_db` for a current tenure.
2. Insert a `BlockInfo` for a tenure-start block in that tenure and call `mark_locally_accepted(false)` (simulating a signed-but-not-globally-accepted block), then `signer_db.insert_block(&existing_block_info)`.
3. Build a second, competing tenure-change (`TenureChangeCause::BlockFound`) + coinbase block proposal for the same tenure consensus hash.
4. Call `sortitions_view.check_proposal(&stacks_client, &mut signer_db, &block)`.
5. Assert `result` is `Err(RejectReason::DuplicateBlockFound)` — with the current v1 code, this assertion fails because `get_last_globally_accepted_block` returns `None`, and the proposal is wrongly accepted, mirroring exactly the bug the v2 test guards against but here shown to remain present in v1.     /// Return the last signed block in a tenure (identified by its consensus hash).
    /// A block is considered signed if it is locally or globally accepted. Blocks that
    /// have only been pre-committed are excluded, because a pre-commit does not put a
    /// signature over the block and may be safely superseded by a competing proposal.
    ///
    /// This answers "what is the tenure's signed tip?", a different question from
    /// [`SignerDb::has_signed_block_in_tenure`]'s "does a signature bind us to this tenure?",
    /// which is why the predicates deliberately differ on rejected blocks (see there).
    pub fn get_last_signed_block(
        &self,
        tenure: &ConsensusHash,
    ) -> Result<Option<BlockInfo>, DBError> {
        let query = "SELECT block_info FROM blocks WHERE consensus_hash = ?1 AND state IN (?2, ?3) ORDER BY stacks_height DESC LIMIT 1";
        let args = params![
            tenure,
            &BlockState::GloballyAccepted.to_string(),
            &BlockState::LocallyAccepted.to_string(),
        ];
        let result: Option<String> = query_row(&self.db, query, args)?;

        try_deserialize(result)
    }
