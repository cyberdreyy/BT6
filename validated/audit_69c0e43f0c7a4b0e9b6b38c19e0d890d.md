### Title
Unfunded instant-withdraw receipts from prior epochs are excluded from default recovery basis, freezing or underpaying claims - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external report describes a BDV total that is undercounted because the snapshot script uses the wrong boundary: deposits removed between the Enroot-fix block and the Silo-V3 deployment block are wrongly treated as migrated, and yield accrued before the deployment block is never added. The direct analog in idle-tranches is `IdleCreditVault.defaultPendingClaimBasis`, which defines the claim basis for `finalizeDefaultRecovery`. It only adds instant-withdraw claims recorded under the *current* `epochNumber`, so instant receipts requested in an earlier epoch that were never funded are silently dropped from the recovery basis — while their payout path still treats them as fully funded or blocks them behind the reserve guard.

### Finding Description
`defaultPendingClaimBasis()` computes the pending basis for default finalization as `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]`, gated on `pendingInstantWithdraws != 0` [1](#0-0) . Both `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are keyed by the epoch in which `requestInstantWithdraw` was called [2](#0-1) .

An instant request made in epoch N that is not collected via `getInstantWithdrawFunds` before the epoch stops keeps `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch[N]` non-zero into epoch N+1 (startEpoch does not clear them; the CDO only pulls instant funds during a running epoch after `instantWithdrawDeadline`, and a stop/default can occur first). If the borrower defaults in epoch N+1, `finalizeDefaultRecovery` records `defaultRecoveryEpoch = epochNumber` (= N+1) and `defaultRecoveryPrice = reserveAmount / totalBasis` where `totalBasis` excludes the epoch-N instant claims [3](#0-2) . Symmetrically, `_defaultPrefundedInstantReserve` uses `instantWithdrawClaimsByEpoch[epochNumber]` only, so already-collected backing for old instant claims is also omitted from the reserve [4](#0-3) .

After finalization, `claimInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (N+1) via `_claimDefaultedInstantWithdrawRequest`, then attempts to pay the full remaining `instantWithdrawsRequests[user]` at par through `_transferFundedClaim` [5](#0-4) . `_transferFundedClaim` reverts whenever `balance - defaultRecoveryReserve < amount` [6](#0-5) . The same epoch-scoping defect exists in `_claimDefaultedWithdrawRequest`/`_clearWithdrawClaimForEpoch` for normal receipts, but normal pending receipts cannot survive an epoch boundary unfunded (a successful `stopEpoch` funds `pendingWithdraws` via `collectWithdrawFunds`, and a partial funding records `lossRecoveryPriceByEpoch`), whereas instant receipts demonstrably can.

### Impact Explanation
Broken invariant: conservation of the recovery reserve and fair haircut of all defaulted claims. Because old-epoch instant claims are omitted from `totalBasis`, the recovered amount is divided over a smaller basis than the true obligations. Two outcomes:

- If the strategy holds enough non-reserve cash, the old instant claimant is paid 100% while every defaulted-epoch claimant is capped at `defaultRecoveryPrice`, so the instant user escapes the haircut entirely and drains funds ahead of reserve claimants (theft of unclaimed recovery / unfair distribution).
- Otherwise `_transferFundedClaim` reverts on `balance - reserve < amount`, permanently freezing the instant claim and, because claims share the same call path, blocking that user from collecting anything. The excluded basis also means `reserveAmount` was understated at finalization, so even the haircutted claimants are underpaid relative to a correct accounting — mirroring the report's "unmigrated BDV smaller than it should be".

Quantified: every wei of `instantWithdrawClaimsByEpoch[N] - funded portion` for N < defaultRecoveryEpoch is either stolen-at-par or frozen.

### Likelihood Explanation
Requires an unprivileged KYC'd lender to request an instant withdrawal in epoch N that remains unfunded at epoch stop (e.g., `instantWithdrawDeadline` falls after `epochEndDate`, or `getInstantWithdrawFunds` is simply never called), followed by a borrower default in a later epoch. Both are normal operational flows; the instant-withdraw mode exists precisely to leave requests pending. No privileged misbehavior is needed — `finalizeDefault` is an honest owner call. Recovery-price manipulation by the claimant is not required; the loss is structural.

### Recommendation
Aggregate instant claim basis across all epochs with outstanding receipts, not only `epochNumber`. Concretely:

- Track a global `totalInstantClaimBasis` (incremented in `requestInstantWithdraw`, decremented on claim/collection) and use it in `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` instead of `instantWithdrawClaimsByEpoch[epochNumber]`.
- In `_claimDefaultedInstantWithdrawRequest`, clear all per-epoch instant entries for the user (or iterate/stored list of epochs) rather than only `defaultRecoveryEpoch`.
- Alternatively, force settlement or rollover of `pendingInstantWithdraws` in `stopEpoch`/`startEpoch` so no instant receipt can cross an epoch boundary unfunded.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testOldEpochInstantClaimsExcludedFromRecoveryBasis() external {
  // Epoch N: deposit, start epoch, enable instant withdraws
  _depositWithUser(instantUser, amount, true);
  _startEpochAndCheckPrices(0);
  cdoEpoch.setInstantWithdrawParams(delay, minAprDiff, false);

  // instantUser requests instant withdraw mid-epoch-N (APR lowered at stop triggers instant mode),
  // or request instant directly; manager never calls getInstantWithdrawFunds.
  uint256 instantBasis = cdoEpoch.requestWithdraw(0, address(AAtranche)); // instant path
  assertGt(creditVault.pendingInstantWithdraws(), 0);

  // Epoch N stops normally, epoch N+1 starts; instant request still unfunded.
  _stopEpochAndCheckPrices(0, apr, fundsEndEpoch);
  _startEpochAndCheckPrices(1);
  assertEq(creditVault.instantWithdrawClaimsByEpoch(creditVault.epochNumber()), 0); // recorded under N

  // Borrower defaults in epoch N+1; finalize recovery.
  deal(underlying, borrower, 0);
  vm.warp(cdoEpoch.epochEndDate() + 1);
  cdoEpoch.stopEpoch(0, 0); // triggers _handleBorrowerDefault
  deal(underlying, manager, recovered);
  cdoEpoch.finalizeDefault(recovered, manager);

  // BUG 1: instantBasis was NOT included in defaultPendingClaimBasis =>
  //   defaultRecoveryPrice is overstated / reserve underfunded.
  // BUG 2: claimInstantWithdrawRequest either pays instantBasis at par
  //   (draining non-reserve cash while others take haircut) or reverts in
  //   _transferFundedClaim because balance - defaultRecoveryReserve < instantBasis,
  //   permanently freezing the claim.
  vm.prank(instantUser);
  vm.expectRevert(NotAllowed.selector); // or observe par payout vs haircut
  cdoEpoch.claimInstantWithdrawRequest();
}
```

Key assertions: `defaultPendingClaimBasis()` before finalization excludes `instantWithdrawClaimsByEpoch[N]`; after `finalizeDefault`, `claimInstantWithdrawRequest` reverts in `_transferFundedClaim` when reserve > 0, or transfers `instantBasis` unhaircutted when sufficient stray balance exists.

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
