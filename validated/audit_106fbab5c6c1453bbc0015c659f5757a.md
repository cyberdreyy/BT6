### Title
Native-token destination withdrawal permanently reverts if `maker` cannot accept plain ETH transfers, temporarily freezing the taker's locked funds - ([File: contracts/EscrowDst.sol])

### Summary
Like the Hats-token analog (pushing a token to a receiver without verifying it can accept the transfer), `EscrowDst` unconditionally pushes native ETH to the `maker` address recorded in `Immutables` during `withdraw`/`publicWithdraw`, with no fallback or pull-payment path if the recipient cannot receive ETH. Because `_ethTransfer` reverts the whole call on failure, an immutable `maker` address that rejects plain ETH sends (any contract without a compatible `receive`/`fallback`, deliberately or not) makes `withdraw`/`publicWithdraw` permanently unusable for that escrow instance.

### Finding Description
`EscrowDst._withdraw` transfers the swap amount to `immutables.maker.get()` via `_uniTransfer`, which for `token == address(0)` calls `_ethTransfer`: [1](#0-0) 

`_ethTransfer` performs a raw `.call{value: amount}("")` and reverts the entire transaction if the call fails: [2](#0-1) 

The `maker` field is a fixed immutable baked into the deterministic escrow address/salt at deployment and cannot be changed afterward; it is supplied directly by the taker as calldata to `createDstEscrow`, based on the order's `maker`/`receiver`: [3](#0-2) [4](#0-3) 

Both the private `withdraw()` and the unprivileged `publicWithdraw()` paths route through this same `_withdraw` internal function, so any account (including any `accessToken` holder that is unprivileged) that attempts to close out the escrow for the maker will have their transaction revert if `maker` cannot accept ETH: [5](#0-4) 

This is the same root cause as the ERC1155 report: value is pushed to a recipient address without any acceptance check or receiver-callback verification, and the transfer mechanism has no fallback for a non-accepting recipient — it can only fail-closed (revert), unlike the report's real ERC1155 tokens which can at least still be re-transferred, `withdraw`/`publicWithdraw` on this specific escrow become permanently unusable.

### Impact Explanation
Once the destination escrow is funded with native ETH (`token == address(0)`) and the `maker` is a contract that reverts on plain ETH receipt, `withdraw` and `publicWithdraw` will revert for every caller for the lifetime of the escrow. The taker's ETH (swap amount + safety deposit) is thus locked and cannot reach the maker at all; it can only later be recovered by the taker via `cancel()` (after `DstCancellation`) or `rescueFunds()` (after `RESCUE_DELAY`) — both of which return funds to the taker instead of completing the swap. This fits the bounty's High-impact bucket: "temporary freezing of funds during the live swap lifecycle," because the resolver's capital is involuntarily locked for a bounded but arbitrary period, and the swap cannot complete as designed.

### Likelihood Explanation
The trigger requires only that the order's `maker`/`receiver` be a contract without a compatible ETH `receive`/`fallback` function while the destination token is native. This is a plausible scenario for smart-contract-wallet users, and can also be deliberately engineered by a malicious (but unprivileged) maker to grief a resolver who has already deployed and funded the destination escrow, at essentially no cost to the maker's own funds. The maker is a normal, unprivileged order-signing participant reachable through the standard fill/`createDstEscrow` flow, consistent with the required attacker model.

### Recommendation
Do not let a failed native transfer to `maker` block the ability to close out the escrow. Options: (1) use a pull-payment pattern for native-token payouts (credit an internal balance the maker can withdraw later) instead of a push transfer; or (2) on `_ethTransfer` failure to the maker, fall back to forwarding the stuck ETH to a recoverable location (e.g., allow immediate `rescueFunds`-style recovery by the taker) rather than reverting the whole withdrawal, so the safety deposit and any other logic can still proceed and the funds aren't held hostage until the cancellation/rescue timelock elapses.

### Proof of Concept
1. Maker signs an order specifying `order.receiver` (or `order.maker`) as a contract `C` with no `receive()`/`fallback()` (or one that reverts).
2. Resolver fills the order on the source chain, then calls `createDstEscrow` with `dstImmutables.token == address(0)`, sending `msg.value = safetyDeposit + amount` as required by: [6](#0-5) 
3. After `DstWithdrawal` start, resolver (or any accessToken holder via `publicWithdraw`) calls `withdraw(secret, immutables)`.
4. `_withdraw` reaches `_uniTransfer(address(0), C, amount)` → `_ethTransfer(C, amount)` → `C.call{value: amount}("")` fails → `revert NativeTokenSendingFailure()`; the whole transaction reverts.
5. Every subsequent call to `withdraw`/`publicWithdraw` reverts identically for as long as the escrow exists, until the resolver is forced to wait for `DstCancellation` (`cancel()`) or `RESCUE_DELAY` (`rescueFunds()`) to reclaim the locked ETH, confirming temporary freezing of the resolver's funds caused solely by the unprivileged maker's chosen receiver address.

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
