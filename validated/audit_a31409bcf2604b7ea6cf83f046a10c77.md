### Title
Global, client-controlled `requestID` namespace in the HTTP trigger handler lets any authenticated client squat a request ID and DoS a specific workflow execution - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The reported GTE Perps bug is a boundary/slot-squatting DoS: an attacker occupies the first legal tick-aligned price so that all subsequent legitimate maker orders collide with the existing best price and are rejected. The analogous root cause in the Chainlink gateway is a shared, client-controlled key namespace (`requestID`) used to track in-flight HTTP-trigger requests, with no binding to the workflow, owner, or sender that reserved it.

### Finding Description
`httpTriggerHandler` tracks in-flight user requests in a single map keyed only by the plain-string `requestID` supplied by the caller: [1](#0-0) 

The uniqueness check in `setupCallback` operates on this global map with no scoping by workflow ID or workflow owner: [2](#0-1) 

Crucially, this uniqueness check runs only after `authorizeRequest` (JWT verification against the *target* workflow's own key) and `checkRateLimit`, both of which are satisfied by an attacker triggering a workflow they legitimately have credentials for (their own workflow, or any workflow whose JWT they can produce). The `requestID` value itself is entirely attacker-chosen — the only constraints are non-empty and not containing `/`: [3](#0-2) 

The README explicitly documents this design: user request IDs are "Plain string identifiers" with no per-workflow/per-owner namespacing: [4](#0-3) 

Because the `callbacks` map is shared across *all* workflows served by the gateway shard rather than being keyed by `(workflowID, requestID)` or `(owner, requestID)`, any unprivileged-but-authenticated client can pre-emptively insert an entry for a `requestID` value that a victim's integration is expected to use (e.g., a deterministic, sequential, or otherwise predictable ID scheme, which is common in automated integrations). When the victim's real trigger request for their own unrelated workflow arrives with that same `requestID`, `setupCallback` finds the slot already occupied and rejects it with a conflict error instead of ever dispatching it to the DON: [5](#0-4) 

This mirrors the audit finding's pattern precisely: a shared, unpartitioned resource key (tick-aligned price / `requestID`) can be squatted by an unrelated party using a legitimate-looking action of their own, permanently (until cleanup) denying the intended party's future legitimate action on that same key.

### Impact Explanation
An attacker with access to trigger any workflow (including their own) can deny execution of a specific, targeted `workflows.execute` request for an entirely different, unrelated workflow/owner, as long as they can predict or observe the `requestID` the victim's automation will use. This is a denial-of-service against a specific execution attempt of an unprivileged victim's workflow trigger, without needing the victim's credentials, JWT, or workflow ownership.

### Likelihood Explanation
Likelihood depends on the attacker's ability to guess the victim's `requestID` ahead of time. Since `requestID` is fully client-controlled with no server-side randomness requirement, many real integrations use predictable schemes (sequence counters, deterministic hashes of public inputs, fixed constants for idempotent retries), which lowers the bar significantly. The attack requires no special privilege beyond being able to authenticate to trigger some workflow on the same gateway shard.

### Recommendation
Scope the in-flight request tracking key by `(workflowID, requestID)` (or `(workflowOwner, requestID)`) instead of `requestID` alone, so a squatted ID in one workflow's namespace cannot block delivery of a same-named request for a different workflow/owner.

### Proof of Concept
1. Attacker registers/owns Workflow A and obtains a valid JWT for it.
2. Attacker predicts or observes that Victim's Workflow B automation will use `requestID = "42"` for its next trigger.
3. Attacker calls `HandleUserTriggerRequest` targeting Workflow A with `req.ID = "42"`; it passes `authorizeRequest` (valid JWT for A) and `checkRateLimit`, then `setupCallback` inserts `h.callbacks["42"]`.
4. Victim's automation triggers Workflow B with `req.ID = "42"`; `setupCallback` finds `"42"` already present in the shared map and returns `jsonrpc.ErrConflict` ("requestID: 42 has already been used"), as demonstrated by the existing test at [5](#0-4) , denying Victim's legitimate, unrelated execution.

```go
func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}
```

```go
func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
```
