### Title
Order-dependent index matching in `try_receive_completed` can silently drop the wrong transaction while retaining the wrong one - ([File: core/src/banking_stage/transaction_scheduler/scheduler_common.rs])

### Summary
The banking-stage scheduler's completion handler, `SchedulingCommon::try_receive_completed`, reconciles a batch of executed transactions against a `retryable_indexes` list returned by the consume worker. It assumes this list is strictly sorted in ascending index order and walks it in lock-step with the batch via a peekable iterator, matching purely by positional index rather than by transaction/message identity. This is structurally the same bug class as the LayerZeroAdapter report: a positional/index-based reconciliation between "what was executed" and "what should be kept pending," where a broken ordering assumption causes the wrong element to be retried and the correct element to be permanently removed.

### Finding Description
`try_receive_completed` iterates over `ids`/`transactions` by `enumerate()` index and compares against `retryable_indexes.iter().peekable()`, advancing the retry iterator only when `retryable_index.index == index`: [1](#0-0) 

If the current position does not match the next expected retryable index, the transaction at that position is unconditionally dropped from the container via `container.remove_by_id(id)`: [2](#0-1) 

The only protection against a violation of the "must be sorted, must correspond correctly" invariant is a `debug_assert!`, which is compiled out entirely in release/production builds: [3](#0-2) 

This exactly mirrors the reported bug class: the LayerZero code executed message A but popped a different index from `s_pendingMessagesToExecute`, causing the wrong item to be treated as "handled" while the intended item was irrecoverably discarded. Here, if `retryable_indexes` (produced upstream by `retryable_transaction_indexes` in `core/src/banking_stage/consumer.rs`, consumed via `consume_worker.rs`) is ever out of order, contains a duplicate, or is off-by-one relative to the executed batch's `ids`/`transactions` vectors, the same "process the wrong entry, keep/drop the wrong entry" outcome occurs — silently in release builds, since the safety check is a `debug_assert!`.

The test suite explicitly documents that out-of-order retryable indexes are only caught by a panic in debug configuration: [4](#0-3) 

### Impact Explanation
If the ordering invariant is ever violated at runtime (e.g., due to a future change to worker-side index construction, an external/QUIC-message-driven consume path with different indexing semantics such as `consume_worker.rs`'s `external` module which builds responses via `agave_scheduling_utils`/shared-memory regions, or a logic bug introduced during maintenance), a transaction that failed and should be retried would instead be silently dropped from `container` and never resubmitted, while an unrelated (already-successful or differently-failed) transaction would be incorrectly retained/retried. This is a replay-path correctness bug: legitimate user transactions can be permanently lost from the retry queue (never re-attempted, no error surfaced to the user beyond a normal timeout), and/or an already-processed transaction could be needlessly resubmitted. Because the safety net (`debug_assert!`) does not exist in production/release builds used by mainnet validators, such a defect would not halt or warn the validator — it would just quietly drop transactions from the pending buffer, exactly analogous to the "irrecoverable state" impact called out in the report (permanent loss of the intended item from the pending/retry store).

### Likelihood Explanation
Under the current call sites I could confirm (`consume_worker.rs::consume` and `consume_worker.rs::retry`), the `retryable_indexes` vectors are constructed with ascending indices (`0..work.transactions.len()` for full-drain retry, and presumably ascending order from SVM's `retryable_transaction_indexes` output in `consumer.rs`), so the invariant appears to hold for the paths I was able to inspect within tool budget. I was not able to fully verify, within the available iterations, whether the `retryable_transaction_indexes` field returned by `execute_and_commit_transactions_output` in `consumer.rs` (43 references) is guaranteed sorted in every code path (e.g., under partial-batch execution, `all_or_nothing` flags, or the SIMD/external worker path in `consume_worker.rs`'s `external` module which uses shared-memory `WorkerToPackMessage`/`ExecutionResponse` structures with different index-building logic). This uncertainty is the crux of the risk: the reconciliation function has no runtime enforcement of its critical invariant, making it fragile to any future change in the several producers of `retryable_indexes`, similar to how the LayerZero bug was only caught after a fix (PR 9/13) introduced *another* function with a new bug in the same area — i.e., invariant-dependent, unchecked reconciliation logic is inherently high-risk to maintain correctly across code changes.

### Recommendation
Replace the positional/index-matching reconciliation in `try_receive_completed` with identity-based matching (e.g., match on the transaction `id`/signature rather than positional index), or, if index-based matching is retained for performance, upgrade the `debug_assert!` to a `assert!`/hard error (or an explicit `Result` failure path) so that any violation of the sorted-index invariant fails loudly in production rather than silently corrupting the pending-transaction state. Additionally, add invariant checks at each producer of `RetryableIndex` (in `consumer.rs` and `consume_worker.rs::external`) to guarantee sorted, unique indices before they cross the channel boundary, similar to how the report recommended assigning unique identifiers/nonces instead of relying on positional/array semantics.

### Proof of Concept
No working PoC was constructed; within the current codebase state and call sites reviewed (`consume_worker.rs` lines 132-175, `scheduler_common.rs` lines 233-299), the ascending-order invariant appears to be upheld today. The concern is that `try_receive_completed`'s correctness depends entirely on this invariant with no production-time enforcement (`debug_assert!` only), and the report's PoC pattern (a stateful list where indexed "pop"/"consume" logic gets desynchronized from indexed "keep" logic) directly maps onto this code's structure. A concrete PoC would require inducing an out-of-order or mismatched `retryable_indexes` vector from one of the untraced producers (e.g., the `external` SIMD worker path) to demonstrate a live transaction-loss scenario, which was not achievable within the available tool budget.
