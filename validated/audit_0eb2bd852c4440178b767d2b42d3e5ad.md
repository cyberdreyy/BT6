### Title
Lockup contract never re-verifies whitelist status after `select_staking_pool`, letting a de-whitelisted staking pool's self-reported balance inflate the owner's transferable balance - (File: `lockup/src/owner.rs`, `lockup/src/owner_callbacks.rs`, `lockup/src/getters.rs`)

### Summary
`select_staking_pool` checks `is_whitelisted` exactly once, at selection time, via `ext_whitelist::is_whitelisted(...).then(on_whitelist_is_whitelisted)` [1](#0-0) . After that, every staking-pool interaction (`deposit_to_staking_pool`, `deposit_and_stake`, `stake`, `unstake`, `withdraw_from_staking_pool`, `refresh_staking_pool_balance`) is gated only by `assert_owner`, `assert_staking_pool_is_idle`, and `assert_no_termination` — none of them re-checks the whitelist contract [2](#0-1) . If the NEAR Foundation later calls `remove_staking_pool` on the whitelist contract because the pool is misbehaving [3](#0-2) , the lockup contract has no way of knowing and keeps trusting that same pool's self-reported balance.

### Finding Description
The whitelist's entire purpose, per its own README, is to guarantee "the delegated tokens can not be lost or locked" and that the lockup can recover funds from the pool [4](#0-3) . Removal from the whitelist is the Foundation's mechanism "to address mistakes" [5](#0-4) .

However, once `on_whitelist_is_whitelisted` stores `staking_information` [6](#0-5) , the trust binding ("this `staking_pool_account_id` is whitelisted") is never re-validated. `refresh_staking_pool_balance` calls `get_account_total_balance` on the pool and blindly overwrites `staking_information.deposit_amount` with whatever the (possibly now-blacklisted/misbehaving) pool self-reports: [7](#0-6) 

That `deposit_amount` (exposed as `get_known_deposited_balance`) directly feeds `get_owners_balance` and `get_liquid_owners_balance`, which gate the owner's `transfer` calls: [8](#0-7) [9](#0-8) 

This is structurally the same class of bug as the `OPFaultVerifier` issue: a piece of external state (a "game"/"pool") is checked for validity only at selection/proof time, and its later invalidation (blacklisting/de-whitelisting) is never rechecked before the contract keeps relying on data it produces.

### Impact Explanation
If a staking pool is compromised or misbehaves such that it reports an inflated `total_balance` (e.g., a bug or malicious owner-controlled pool contract that was whitelisted, later found bad and removed from the whitelist), the lockup contract will still accept that reported number via `on_get_account_total_balance`, since there is no re-check against `is_whitelisted`. The owner can then call `transfer` using `get_liquid_owners_balance`, which is bounded by `get_owners_balance` (derived from the inflated `known_deposited_balance`) and the actual liquid `env::account_balance()` — meaning the owner could withdraw real NEAR from the lockup account up to the (unreal) reported total, effectively minting a claim on assets the pool doesn't actually hold. This is an accounting value (staking pool balance) diverging from reality, settled upon by another party (the owner withdrawing real NEAR), matching the "High"/"Critical" impact bar (claims exceeding assets actually held).

### Likelihood Explanation
Requires: (1) a staking pool to be legitimately whitelisted and selected by a lockup owner, and (2) that pool later being removed from the whitelist by the Foundation because it misbehaves/misreports balances. This mirrors exactly the scenario the external report highlights (Optimism's Guardian blacklisting a dispute game "only when it resolves incorrectly") — i.e., the trust-revocation event is rare but is precisely the security-critical case the whitelist mechanism exists for, and the lockup contract has zero defense once that revocation happens.

### Recommendation
Re-verify `is_whitelisted(staking_pool_account_id)` against the whitelist contract before accepting balance updates in `on_get_account_total_balance`, and/or before allowing further `deposit_to_staking_pool`/`stake`/`refresh_staking_pool_balance` calls once a pool has been selected. At minimum, expose a path for the owner (or Foundation) to force-unselect/quarantine a staking pool that has since been removed from the whitelist, and refuse to increase `deposit_amount` based on self-reported balances from a de-whitelisted pool.

### Proof of Concept
1. Owner calls `select_staking_pool("pool.factory")`; whitelist confirms it's whitelisted; `staking_information` set with `deposit_amount = 0`. [6](#0-5) 
2. Owner deposits and stakes funds normally via `deposit_and_stake`. [10](#0-9) 
3. NEAR Foundation later calls `remove_staking_pool("pool.factory")` on the whitelist contract after discovering the pool is unsafe. [3](#0-2) 
4. Owner calls `refresh_staking_pool_balance()`; the (now-delisted) pool contract returns an inflated `get_account_total_balance`; the lockup contract accepts it unconditionally, no whitelist re-check performed. [2](#0-1) [7](#0-6) 
5. Owner calls `transfer(amount, receiver_id)`; `get_liquid_owners_balance` now includes the inflated `deposit_amount`, allowing withdrawal of real NEAR from `env::account_balance()` beyond what is actually backed by the staking pool. [11](#0-10) [9](#0-8)

    pub fn on_whitelist_is_whitelisted(
        &mut self,
        #[callback] is_whitelisted: bool,
        staking_pool_account_id: AccountId,
    ) -> bool {
        assert_self();
        assert!(
            is_whitelisted,
            "The given staking pool account ID is not whitelisted"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();
        self.staking_information = Some(StakingInformation {
            staking_pool_account_id,
            status: TransactionStatus::Idle,
            deposit_amount: 0.into(),
        });
        true
    }

    /// Returns the balance of the account owner. It includes vested and extra tokens that
    /// may have been deposited to this account, but excludes locked tokens.
    /// NOTE: Some of this tokens may be deposited to the staking pool.
    /// This method also doesn't account for tokens locked for the contract storage.
    pub fn get_owners_balance(&self) -> WrappedBalance {
        (env::account_balance() + self.get_known_deposited_balance().0)
            .saturating_sub(self.get_locked_amount().0)
            .into()
    }

    /// Returns total balance of the account including tokens deposited to the staking pool.
    pub fn get_balance(&self) -> WrappedBalance {
        (env::account_balance() + self.get_known_deposited_balance().0).into()
    }

    /// Returns the amount of tokens the owner can transfer from the account.
    /// Transfers have to be enabled.
    pub fn get_liquid_owners_balance(&self) -> WrappedBalance {
        std::cmp::min(self.get_owners_balance().0, self.get_account_balance().0).into()
    }
