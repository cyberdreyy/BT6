### Title
Attacker-controlled RTT inflates per-connection QUIC uni-stream credit beyond intended BDP-scaling cap - ([File: streamer/src/nonblocking/swqos.rs])

### Summary
`SwQos::cache_new_connection` reads `connection.rtt()` once at connection setup and feeds it into `compute_max_allowed_uni_streams_with_rtt`, which linearly scales the per-connection uni-stream credit by `rtt_millis / REFERENCE_RTT_MS` (clamped to `MAX_RTT_MS`). Because QUIC RTT is measured from the client's own ACK timing, an unprivileged client can deliberately delay its handshake/initial ACKs to inflate the observed RTT up to `MAX_RTT_MS` (350ms), causing the server to grant up to 7x more concurrent uni-streams than the connection's stake/type would otherwise warrant, then open that many streams and never finish them.

### Finding Description
In `streamer/src/nonblocking/swqos.rs`:
- `cache_new_connection` computes `rtt_millis = connection.rtt().as_millis().min(MAX_RTT_MS as u128) as u32` [1](#0-0) , then calls `compute_max_allowed_uni_streams_with_rtt(rtt_millis, peer_type, total_stake)` and applies the result via `connection.set_max_concurrent_uni_streams(max_uni_streams)` [2](#0-1) .
- `compute_max_allowed_uni_streams_with_rtt` first derives a base stream count from stake (clamped between `QUIC_MIN_STAKED_CONCURRENT_STREAMS` and `QUIC_MAX_STAKED_CONCURRENT_STREAMS = 512`, or `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS = 128` for unstaked peers), and then multiplies that base by `rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS) / REFERENCE_RTT_MS` [3](#0-2) . With `REFERENCE_RTT_MS = 50` and `MAX_RTT_MS = 350` [4](#0-3) , the scaling factor can reach 7x.
- `connection.rtt()` reflects the smoothed RTT as measured by the QUIC transport (quinn), which is derived from the timing of the client's own ACKs. Because the client fully controls when it sends its ACKs, it can hold them back deliberately during the handshake/early connection phase to inflate the perceived RTT toward `MAX_RTT_MS`, then behave normally (or simply never send data) once the stream-count credit has been granted.
- The stream-count credit is computed and applied exactly once, at `cache_new_connection` time (comment: "cache the RTT to avoid grabbing lock for every stream... if it gets stale during connection lifetime it is not the end of the world" in the sibling non-SwQos path at `streamer/src/nonblocking/quic.rs:606-609` confirms the RTT is a one-time snapshot, not re-validated per stream). There is no re-check of RTT plausibility (e.g., against expected geographic/network latency) or of actual application-level responsiveness before granting the multiplier.
- Notably, `QUIC_MAX_STAKED_CONCURRENT_STREAMS` was deliberately lowered from 2048 to 512 specifically "to reduce contention of the limited receive_window among the streams" [5](#0-4) . The RTT-based multiplier can push a staked connection's granted stream count back up to `512 * 7 = 3584` — exceeding even the previously-identified problematic 2048 value — solely based on a self-reported/self-controlled RTT signal, undermining the rationale for the cap reduction.
- The attacker then opens up to the granted number of uni-streams and never sends a FIN, so each stream's receive state and flow-control buffer (bounded by the connection's stream flow-control window / `max_stream_data_bytes` configured for the QUIC endpoint in `streamer/src/nonblocking/quic.rs` and `streamer/src/quic.rs`) remains allocated server-side, consuming per-connection resources disproportionate to what the fair-share stake/type calculation intended.

### Impact Explanation
This is a metering-bypass/DoS finding against the QUIC ingest layer that feeds the TPU/banking stage: an attacker inflates the server-granted concurrent-uni-stream budget via a purely client-observable signal (self-controlled ACK delay) rather than genuine network conditions, then opens that many streams without draining them. This matches the "non-RPC remote resource exhaustion / ingest starvation" bounty category — the attacker occupies a larger share of server-side per-connection stream/flow-control state than the stake-weighted fairness design (`staked_stream_load_ema`/stake-proportional cap) intends, at the expense of other connections sharing the same connection-table/stream budget.

### Likelihood Explanation
The exploit requires only an unprivileged QUIC client capable of connecting to the TPU and controlling its own ACK timing during connection setup — both explicitly allowed unprivileged capabilities. No stake is strictly required (an unstaked connection alone can still amplify from 128 to 896 streams); a staked attacker gets a larger absolute amplification (up to 3584). The mechanism is deterministic and repeatable per new connection, bounded only by `MAX_RTT_MS` and per-peer connection-count limits (`max_connections_per_staked_peer`/`max_connections_per_unstaked_peer`), so the attacker can repeat this across multiple connections/peers for cumulative effect.

### Recommendation
Do not trust a client-observable, one-time RTT sample as an unbounded multiplier on granted stream credit. Options: (1) cross-check RTT plausibility against network-layer/IP-based expectations or require a minimum number of confirmed round trips with consistent variance before trusting the sample; (2) decouple the BDP-scaling multiplier from the hard per-peer-type caps so RTT scaling cannot push a connection above the previously-tuned `QUIC_MAX_STAKED_CONCURRENT_STREAMS`/`QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` ceiling (i.e., cap the final result, not just the base, to the pre-RTT-scaling maximum, or use a smaller scaling ceiling than 7x); (3) periodically re-evaluate `connection.rtt()` during the connection lifetime (not just once at setup) and reduce the stream credit if the smoothed RTT drops sharply after the credit was granted, since a sudden drop from artificially delayed handshake ACKs to a low steady-state RTT is itself a signal of manipulation.

### Proof of Concept
```rust
// streamer/src/nonblocking/swqos.rs (test module)
#[test]
fn test_max_allowed_uni_streams_rtt_amplification() {
    // Baseline: staked peer at reference RTT already at the per-type cap.
    let base = compute_max_allowed_uni_streams_with_rtt(
        REFERENCE_RTT_MS,
        ConnectionPeerType::Staked(1000),
        10_000,
    );
    assert_eq!(base, QUIC_MAX_STAKED_CONCURRENT_STREAMS); // 512

    // Attacker inflates RTT (via deliberate ACK delay) up to MAX_RTT_MS.
    let inflated = compute_max_allowed_uni_streams_with_rtt(
        MAX_RTT_MS,
        ConnectionPeerType::Staked(1000),
        10_000,
    );
    // Amplification exceeds the previously-reduced 2048 cap that
    // QUIC_MAX_STAKED_CONCURRENT_STREAMS was intentionally lowered from.
    assert!(inflated > 2048, "inflated={inflated}");
    assert_eq!(inflated, QUIC_MAX_STAKED_CONCURRENT_STREAMS * (MAX_RTT_MS / REFERENCE_RTT_MS));
}
```

```rust
fn compute_max_allowed_uni_streams_with_rtt(
    rtt_millis: u32,
    peer_type: ConnectionPeerType,
    total_stake: u64,
) -> u32 {
    let streams = match peer_type {
        ConnectionPeerType::Staked(peer_stake) => {
            // No checked math for f64 type. So let's explicitly check for 0 here
            if total_stake == 0 || peer_stake > total_stake {
                warn!(
                    "Invalid stake values: peer_stake: {peer_stake:?}, total_stake: \
                     {total_stake:?}"
                );

                QUIC_MIN_STAKED_CONCURRENT_STREAMS
            } else {
                let delta = (QUIC_TOTAL_STAKED_CONCURRENT_STREAMS
                    - QUIC_MIN_STAKED_CONCURRENT_STREAMS) as f64;

                (((peer_stake as f64 / total_stake as f64) * delta) as u32
                    + QUIC_MIN_STAKED_CONCURRENT_STREAMS)
                    .clamp(
                        QUIC_MIN_STAKED_CONCURRENT_STREAMS,
                        QUIC_MAX_STAKED_CONCURRENT_STREAMS,
                    )
            }
        }
        ConnectionPeerType::Unstaked => QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS,
    };
    // scale amount of streams based on RTT if RTT is larger than REFERENCE_RTT_MS
    // multiply first then divide to avoid rounding errors.
    (streams.saturating_mul(rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS))) / REFERENCE_RTT_MS
}
```
