### Title
Unauthenticated arbitrary storage write via `replace`/`clean` exports - (File: state-manipulation/src/lib.rs)

### Summary
The `replace` and `clean` exported functions in `state-manipulation/src/lib.rs` deserialize attacker-supplied JSON from `input()` and call `storage_write`/`storage_remove` for every key/value pair with **no caller authorization check whatsoever** — no `predecessor_account_id` comparison, no owner assertion, nothing. Once this contract is deployed to an account (per its own README, intended to be layered temporarily over an existing contract to patch broken state), any unprivileged NEAR account can call these exports and rewrite arbitrary storage slots of that account.

### Finding Description
The broken binding: **`predecessor_account_id() == account's_authorised_writer`** is never asserted, yet `storage_write` executes for every entry regardless of caller.

Code path:
- `replace()` at [1](#0-0)  reads `input()`, deserializes `entries: Vec<(&str, &str)>`, base64-decodes each key/value, and calls `storage_write` directly — with no check on who is calling.
- `storage_write` itself is a thin wrapper over the raw `near_sys::storage_write` syscall: [2](#0-1) .
- `clean()` has the identical pattern for `storage_remove`: [3](#0-2) .

Root cause: the contract never calls `near_sys::predecessor_account_id` (or any equivalent) anywhere in the file, so there is no way to restrict who may invoke `replace`/`clean`. In NEAR, a deployed contract's storage belongs to the account it is deployed on, and any account can send a transaction invoking any of its public exported methods; the callee (the account hosting the contract) is the one whose storage is mutated regardless of who the caller is. Since this contract is meant to be deployed onto an account that already hosts a real contract (e.g., a lockup, staking pool, or multisig) in order to patch its state, once deployed it exposes a completely open storage-write/delete primitive to anyone on the network. An attacker can write only part of a multi-key structure (e.g. overwrite `lockup_information`/`vesting_information`'s discriminant fields, staking pool's `total_staked_balance`/`total_stake_shares`, or an FT `total_supply` record) while leaving the rest of the structure untouched, producing an internally inconsistent state that can be leveraged to release locked tokens early, inflate a balance, or otherwise manipulate accounting fields that gate fund movement.

No existing guard (`assert_owner`, `assert_self`, `is_promise_success`, etc.) is present in this file at all — the audit rule's list of mitigating checks is simply absent from this crate.

### Impact Explanation
Whoever controls the funds-bearing account this contract is deployed onto loses exclusive control of that account's storage the moment the contract is live. Any unprivileged caller can:
- Overwrite balance/accounting fields (`total_staked_balance`, `total_stake_shares`, `lockup_information`, `vesting_information`, `ft.total_supply`, etc.) to whatever bytes they choose.
- Repeatedly call `replace`/`clean` at will, across any window in which this contract is deployed, with no cost beyond gas.

This directly matches Critical impact: "direct manipulation of contract state, enabling theft of the account's funds" — NEAR/wNEAR could be released, claimed, or unlocked early by a party never entitled to it, purely by corrupting the state that the real (previously or subsequently redeployed) contract logic trusts.

### Likelihood Explanation
The only precondition is that this `state-manipulation` contract is deployed (by its legitimate operator, per its own documented purpose of "put[ting] key value pairs into storage" to patch an account) onto the target account. Once live, exploitation requires nothing beyond an ordinary NEAR transaction calling `replace` with base64-encoded key/value pairs — no deposit, no special role, no key compromise. This is trivially repeatable by any account, at negligible gas cost, for as long as the contract remains deployed.

### Recommendation
Add an authorization check at the top of both `replace` and `clean` that compares `near_sys::predecessor_account_id` against `near_sys::current_account_id` (i.e., restrict to `Self`) or against an explicit owner key stored in state, aborting via `near_sys::panic` otherwise, before performing any `storage_write`/`storage_remove` calls.

### Proof of Concept
```rust
// cargo test in state-manipulation using near-workspaces
#[tokio::test]
async fn unauthorized_replace_writes_state() -> anyhow::Result<()> {
    let worker = workspaces::sandbox().await?;
    let wasm = tokio::fs::read("res/state_manipulation.wasm").await?;
    let contract = worker.dev_deploy(&wasm).await?; // simulates deploy onto a "victim" account

    // Unrelated attacker account, unrelated to the contract's deployer/owner
    let attacker = worker.dev_create_account().await?;

    let key_b64 = base64::encode(b"total_staked_balance");
    let malicious_value_b64 = base64::encode(b"\xff\xff\xff\xff\xff\xff\xff\xff"); // attacker-chosen bytes

    // Attacker calls `replace` directly — no owner/predecessor check exists
    attacker
        .call(&worker, contract.id(), "replace")
        .args_json(&serde_json::json!({ "entries": [[key_b64, malicious_value_b64]] }))?
        .max_gas()
        .transact()
        .await?;

    let state_items = contract.view_state(&worker, None).await?;
    // Binding broken: state controlled by an account other than the contract's
    // legitimate owner/deployer, proving no authorization is enforced.
    assert_eq!(state_items.get(b"total_staked_balance".as_ref()).unwrap(), &base64::decode(malicious_value_b64)?);
    Ok(())
}
```
This demonstrates that `attacker`, an account with no relationship to the contract's deployer, successfully mutates the account's storage via `replace`, confirming the binding "only an authorised principal can write this account's storage" is broken. [1](#0-0)

#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    #[derive(serde::Deserialize)]
    struct ReplaceInput<'a> {
        #[serde(borrow)]
        entries: Vec<(&'a str, &'a str)>,
    }

    let input = input().unwrap();
    let args: ReplaceInput = serde_json::from_slice(&input).unwrap();
    for (key, value) in args.entries {
        storage_write(
            &base64::decode(key).unwrap(),
            &base64::decode(value).unwrap(),
        );
    }
}
