### Title
Loss haircut from `stopEpochWithDuration` is applied to the whole `pendingWithdraws` but only enforced on the user's last-request epoch — older unclaimed receipts are paid at par, draining the strategy and freezing later claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Analog of CVE-2017-9348 (missing size validation → out-of-bounds read): `IdleCreditVault` validates/reads only the *latest* request epoch (`lastWithdrawRequest[_user]`) when applying a loss-adjusted recovery, ignoring older funded-but-unclaimed receipts that were also covered by the same haircut. The stale slices are then paid at par via `_claimFundedWithdrawRequest`, so total payouts exceed what the borrower funded, leaving later claimants unpayable (insolvency / permanent freezing of unclaimed yield). [1](#0-0) 

### Finding Description
`requestWithdraw` accumulates receipts across epochs: `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `lastWithdrawRequest[_user] = currentEpoch`. A user may hold unclaimed receipts from several epochs simultaneously — `requestWithdraw` only blocks a new request when a *loss-adjusted* receipt is pending; ordinary funded receipts can be stacked. [2](#0-1) 

When `stopEpochWithDuration(_lossAmount)` haircuts the epoch, the strategy funds only `pendingWithdraws * lossRecoveryPrice` and records `lossRecoveryPriceByEpoch[epochNumber]`. `pendingWithdraws` is an aggregate across *all* pending receipts, including requests opened in earlier epochs that were never claimed. However, on claim:

- `_claimLossAdjustedWithdrawRequest` reads only `lastWithdrawRequest[_user]`, looks up `lossRecoveryPriceByEpoch[lossEpoch]`, and calls `_clearWithdrawClaimForEpoch(_user, lossEpoch, false)`, which subtracts only `withdrawsRequestsByEpoch[_user][lossEpoch]` from `withdrawsRequests[_user]`. [3](#0-2) 
- Control then falls into `_claimFundedWithdrawRequest`, which pays the remaining `withdrawsRequests[_user]` (the older-epoch slices) at par. [4](#0-3) 

The "size" that was validated is one epoch's slice, while the aggregate `pendingWithdraws` haircut covered all slices — exactly the overread/past-the-end pattern: accounting beyond the checked boundary is consumed at un-haircut prices.

### Impact Explanation
If a user (or the queue contract) carries receipts from epoch N and N+1, and epoch N+1 ends with `stopEpochWithDuration` loss, the strategy receives `totalPending * price` but pays `epochN_amount * 1.0 + epochN+1_amount * price`. The deficit `epochN_amount * (1 - price)` is drawn from underlying reserved for other claimants/recovery, so the final claimants' `claimWithdrawRequest`/`claimInstantWithdrawRequest` revert on insufficient balance — permanent freezing of unclaimed yield proportional to the older-epoch basis times the haircut. With `price = 0.5e18` and a 100k earlier-epoch receipt, ~50k underlying is misdirected.

### Likelihood Explanation
Requires: (a) a user holding unclaimed withdraw receipts across an epoch boundary — explicitly supported (the code notes a user "will have to wait for another epoch to claim both requests"), and (b) a subsequent `stopEpochWithDuration` loss, which is an ordinary manager/borrower-flow event (partial repayment shortfall), not an attacker-controlled privilege. The attacker is just a tranche holder who requests withdraws at the right times and claims first; loss realization is driven by honest borrower underpayment. Moderate likelihood.

### Recommendation
Apply `lossRecoveryPriceByEpoch` to the user's *entire* outstanding basis at the loss epoch, not just the last-request slice: in `_claimLossAdjustedWithdrawRequest`, compute claim basis over all epochs with pending receipts included in the haircuffed `pendingWithdraws` (e.g., treat `withdrawsRequests[_user]` plus the APR0 bucket as the basis when the loss epoch is current), or record per-epoch loss coverage and block stacking so an unclaimed older receipt cannot escape the haircut. Alternatively, fund the haircut per request-epoch bucket rather than against aggregate `pendingWithdraws`.

### Proof of Concept
Foundry fork sketch (USDC-based vault, standard epoch variant):

```solidity
// 1. Attacker (KYC'd LP) deposits AA, requests withdraw in epoch N (buffer phase).
cdoEpoch.requestWithdraw(amountA, address(AAtranche)); // withdrawsRequestsByEpoch[user][N] += amountA

// 2. Epoch N stops normally (borrower repays in full) -> receipts funded, epochNumber = N+1.
//    Attacker does NOT claim; opens a second request in epoch N+1.
cdoEpoch.requestWithdraw(amountB, address(AAtranche)); // lastWithdrawRequest[user] = N+1

// 3. Epoch N+1: borrower underpays; manager calls stopEpochWithDuration(loss).
//    Strategy receives (amountA + amountB) * lossRecoveryPriceByEpoch[N+1].

// 4. Attacker calls claimWithdrawRequest():
//    - _claimLossAdjustedWithdrawRequest pays amountB * price   (epoch N+1 slice)
//    - _claimFundedWithdrawRequest  pays amountA * 1.0          (epoch N slice, un-haircut)
//    Total paid > total funded by amountA * (1 - price).

// 5. A second user's claimWithdrawRequest() reverts on insufficient underlying balance
//    -> permanent freezing of unclaimed yield.
```

Key assertions: `underlying.balanceOf(strategy)` after step 4 is less than the sum of remaining funded claims; second claimant's call reverts.

Caveat: I was unable to confirm the exact `stopEpochWithDuration` funding path in `IdleCDOEpochVariant.sol` within the iteration budget — specifically whether the haircut is computed against aggregate `pendingWithdraws` or per-epoch. The PoC assumes the aggregate; if funding is per-epoch the severity drops. Verification of `IdleCDOEpochVariant.stopEpochWithDuration`/`_beforeStopEpoch` funding math is required before final severity.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
