### Title
Builder can freely choose `bid.fee_recipient`, letting it misdirect/escape the payment owed to the proposer - (File: `specs/gloas/beacon-chain.md`)

### Summary
The `ExecutionPayloadBid` used in the Gloas proposer-builder separation (PBS) design carries a `fee_recipient` field that is entirely chosen and signed by the builder itself. `process_execution_payload_bid` (the canonical state-transition function) records a `BuilderPendingWithdrawal` using this builder-supplied `fee_recipient` with no check that it matches the proposer's declared preference. The only place such a check exists is a soft, non-enforced gossip-layer `IGNORE` rule, which affects message propagation but not block/state validity. A builder can therefore set `fee_recipient` to its own address (or an accomplice's), diverting the bid payment that is supposed to compensate the block proposer back to itself, exactly as the referenced report's creator diverted royalty revenue away from the rightful seller by manipulating a recipient field the code trusted unconditionally.

### Finding Description
The `ExecutionPayloadBid.fee_recipient` field is set by the builder when constructing and signing the bid, and `process_execution_payload_bid` stores it verbatim into the pending payment/withdrawal without verifying it against the block proposer's authority: [1](#0-0) 

This queued `BuilderPendingWithdrawal.fee_recipient` is later used, unchanged, as the literal destination address of the EL withdrawal that pays out of the builder's own staked balance: [2](#0-1) 

The protocol's intended semantics are that this address should correspond to the proposer's own choice, communicated via the `proposer_preferences` gossip topic: [3](#0-2) 

However, the only place that `bid.fee_recipient == proposer_preferences.fee_recipient` is checked is inside gossip validation, and it is an `IGNORE`, not a `REJECT`: [4](#0-3) 

`IGNORE` only affects whether a node relays/accepts the message over gossip for spam-prevention purposes; it has no bearing on the validity of the bid once it is embedded in a signed beacon block and processed by `process_execution_payload_bid` in `specs/gloas/beacon-chain.md`. That state-transition function performs no equivalent assertion — it never reads `proposer_preferences` at all, and simply trusts `bid.fee_recipient` as supplied by the builder. As a result, a syntactically and cryptographically valid block containing a bid with an attacker-controlled `fee_recipient` is accepted by every spec-following node, and the corresponding withdrawal is paid to that address instead of to the proposer's registered destination.

This is structurally identical to the referenced NFT bug: a party (there, the creator; here, the builder) controls a "recipient" field that the settlement logic (there, `_getCreatorPaymentInfo`; here, `process_execution_payload_bid`/`get_builder_withdrawals`) treats as authoritative without verifying it against the party who is supposed to actually receive the funds (there, the owner/seller; here, the proposer).

### Impact Explanation
This breaks the equality "a builder payment is paid to the entity the block proposer designated to receive it." Concretely, a builder can set `fee_recipient` to its own `execution_address` (or any third party under its control) for every bid it wins, silently converting what is supposed to be compensation paid to the proposer for the right to build the block into money the builder simply routes back to itself out of its own escrowed stake. This matches the report's impact category "a builder payment or withdrawal misdirected" and results in Gwei that is committed and paid out on-chain never actually reaching the intended non-attacker party (the proposer), i.e., Gwei paid to a non-owner/unauthorized recipient.

### Likelihood Explanation
Any active, registered builder can exploit this on every bid it submits — no coalition, no client bug, and no special stake threshold is required beyond already being a payload builder with sufficient balance to cover the bid (`can_builder_cover_bid`). The only mitigation currently in the spec is a non-binding gossip `IGNORE` rule that a builder can trivially avoid by not relying on public gossip propagation (e.g., submitting bids directly to a cooperating or unaware proposer/relay), and which in any case has no effect on the canonical state-transition validity of the resulting block.

### Recommendation
Enforce `bid.fee_recipient == proposer_preferences.fee_recipient` (or an equivalent proposer-authorized destination sourced from state) as part of the canonical state transition in `process_execution_payload_bid`, not merely as a soft gossip-layer `IGNORE` check. If `proposer_preferences` cannot be made part of consensus state, an alternative is to have the proposer commit its desired `fee_recipient` in the block itself and have `process_execution_payload_bid` assert the bid's `fee_recipient` matches that committed value.

### Proof of Concept
1. Builder `B` registers and maintains sufficient balance to win the slot's bid (`can_builder_cover_bid`).
2. Proposer `P` publishes (via gossip or a private relay/direct channel) `SignedProposerPreferences` with `fee_recipient = P_addr`.
3. Builder `B` constructs `ExecutionPayloadBid` with `value = X > 0` and `fee_recipient = B_addr` (its own execution address) instead of `P_addr`.
4. `B` submits this bid directly to the proposer (or via any relay that does not itself enforce the gossip `IGNORE` rule) — bypassing the public gossip network's `IGNORE`, which only affects relaying, not validity.
5. Proposer `P` includes the bid in its `BeaconBlock`; `process_execution_payload_bid` (`specs/gloas/beacon-chain.md` L2124-2141) accepts it and enqueues `BuilderPendingWithdrawal(fee_recipient=B_addr, amount=X, builder_index=B)` with no check against `P_addr`.
6. Once settled and processed by `process_withdrawals`/`get_builder_withdrawals` (`specs/gloas/beacon-chain.md` L1802-1834), `X` Gwei is withdrawn from builder `B`'s own staked balance and paid to `B_addr` — i.e., the builder pays itself back the amount that was supposed to compensate proposer `P`, and the block remains fully valid per spec-following state-transition rules.

```python
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
