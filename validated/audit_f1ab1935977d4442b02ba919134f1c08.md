### Title
One-slot miner can indefinitely suppress its own inactivity timeout via `update_last_activity_time` - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_latest_block_in_tenure` unconditionally bumps a tenure's `last_activity_time` to `get_epoch_time_secs()` whenever *any* rejected or conflicting proposal is seen for that tenure — including proposals the signer is about to reject as too-low or as conflicting with a pre-commit-only block. `SortitionState::is_timed_out` (chainstate/v1.rs) uses that same timestamp as the sole anchor for the `block_proposal_timeout` inactivity check. A single miner (the tenure's own miner, or the leader who won that sortition slot) can therefore keep re-broadcasting cheap, doomed proposals for its own tenure to perpetually reset the clock, preventing signers from ever concluding the miner is inactive and falling back to the prior miner.

### Finding Description
`check_latest_block_in_tenure` is the shared check invoked at proposal-arrival, at validate-ok, and at pre-commit-threshold time (see `docs/signer-flows.md` §7). When a new proposal for a tenure doesn't confirm enough height compared to what the signer already knows (`block.header.chain_length <= info.block.header.chain_length`), the code calls:

```
signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs());
```

guarded only by a loose freshness condition (`signed_time + reorg_attempts_activity_timeout > now`, or "no signed_group time at all"), i.e. essentially any locally-accepted-but-not-yet-globally-accepted state. The same pattern repeats for the pre-commit-only branch just below it. In both cases the *rejected* proposal itself is the trigger for extending activity — this is symmetrical to the reported bug: a variable meant to be pinned to the end of a validity window (`lastRewardTime` should stop at `endTime`; here, `last_activity_time` should stop advancing once a miner is genuinely inactive/misbehaving) is instead advanced every time regardless of whether the underlying condition that justifies "activity" is still true.

`SortitionState::is_timed_out` then computes `elapsed = now - last_activity_time` and only declares the miner timed out if `elapsed > block_proposal_timeout`. Because `last_activity_time` gets reset to "now" on every conflicting/rejected proposal, `elapsed` never grows past the timeout as long as the miner (or anyone relaying block proposals crafted to look like that miner's tenure) keeps sending them at a rate faster than `block_proposal_timeout`.

This breaks the liveness guarantee documented in `docs/signer-flows.md` §8, where `check_miner_inactivity`/`is_timed_out` is supposed to be the backstop that lets the signer set "fall back to prior tenure" (`FALL["fall back to prior tenure: make_miner_state(prior sortition)"]`) when the active miner goes idle or misbehaves.

### Impact Explanation
This is a liveness wedge on the signer state machine: a compromised or malicious single miner that has already won a sortition slot can keep the tenure's inactivity clock perpetually reset by resubmitting low/duplicate/conflicting proposals (which are cheap — they get rejected quickly and cost nothing to the attacker beyond bandwidth), preventing the signer set from ever considering that miner inactive and falling back to the prior miner's tenure. This matches the "High — a signer wedged into never signing valid blocks... or acting on a stale reward set" impact category: signers stay pinned to a stalled/misbehaving miner's tenure instead of recovering, stalling block production for that tenure indefinitely (bounded, in the worst case, by `reorg_attempts_activity_timeout`/`tenure_last_block_proposal_timeout`, but those are per-check gates, not global caps on how many times the reset can happen).

### Likelihood Explanation
Triggering this requires only the one miner who already controls the current sortition slot (no majority of signers, no other signer's key, and no auth token) — well within a single miner's normal capability to submit block proposals and have them relayed to signers, satisfying the "one-slot miner (plus gossip) can trigger" scope rule. The proposals used to trigger the reset are exactly the kind of routine "too-low" or "conflicting-with-pre-commit" proposals that a stalling miner would naturally produce.

### Recommendation
Do not treat every conflicting/rejected proposal as fresh "activity" indefinitely. Bound the effect of `update_last_activity_time`, e.g.:
- Only count a conflicting proposal as activity a bounded number of times per tenure, or
- Require the conflicting/pre-commit block itself to still be within its own freshness window *and* additionally cap the total extension so that `last_activity_time` cannot be pushed forward forever purely by resubmission of already-rejected material,
- Or decouple "did we see a proposal" from "is the miner still trying to make progress" by also considering whether any *new, distinct* validation-worthy proposal has arrived, rather than resetting on every retry of previously-seen-shaped conflicts.

### Proof of Concept
1. Miner M wins the current sortition and starts tenure `T` with a first block `B0`, globally accepted.
2. M (or anyone gossiping in M's tenure) repeatedly submits new block proposals for `T` at height ≤ `B0`'s height (e.g., resubmitting `B0` itself with a fresh timestamp, or minor variants), spaced less than `block_proposal_timeout` apart.
3. Each such proposal reaches `check_latest_block_in_tenure`, fails the height check (`block.header.chain_length <= info.block.header.chain_length`), and because `info.signed_group` is `None` or within `reorg_attempts_activity_timeout`, `update_last_activity_time(tenure_ch, now)` fires (`stacks-signer/src/chainstate/mod.rs:403-417`).
4. On every housekeeping pass, `SortitionState::is_timed_out` (`stacks-signer/src/chainstate/v1.rs:55-94`) computes `elapsed = now - last_activity_time`, which never exceeds `block_proposal_timeout` because step 3 keeps resetting `last_activity_time` to "now".
5. Signers never conclude the miner is inactive and never fall back to the prior tenure (`docs/signer-flows.md` §8, `FALL` branch), stalling recovery even though the miner is not actually producing any valid new blocks.

```rust
    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
```
