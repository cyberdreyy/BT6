### Title
LDAP `CreateSession` fails to reject empty-password ("unauthenticated") binds, allowing authentication bypass for any known email - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`ldapAuthenticator.CreateSession` passes `sr.Password` directly to `conn.Bind(searchBaseDN, sr.Password)` with no check that the password is non-empty. If the configured upstream LDAP server implements the RFC 4513 §5.1.2 "unauthenticated bind" mechanism (returning success for a non-empty DN with an empty password), `conn.Bind` returns `nil`, and the code treats this as a fully authenticated login, minting a valid `ldap_sessions` row for the target user with their real role.

### Finding Description
In `CreateSession` [1](#0-0) , the code builds `searchBaseDN` from the attacker-supplied `sr.Email` and calls `conn.Bind(searchBaseDN, sr.Password)`. There is no validation anywhere in the request path that rejects an empty `sr.Password` before it reaches the bind call:

- The HTTP handler `SessionsController.Create` binds the JSON body directly into `clsessions.SessionRequest` with no non-empty password check [2](#0-1) .
- `SessionRequest` itself has no validation tags or constructor enforcing password length [3](#0-2) .
- `CreateSession` treats `err == nil` from `Bind` as proof of a successful authenticated login and proceeds to call `FindUser` and insert into `ldap_sessions` [4](#0-3) .

Per RFC 4513, a bind request with a non-empty DN and a zero-length password is defined as an "unauthenticated bind," and it is common for LDAP server configurations to allow this to succeed (return `resultCode: success`) unless the server operator has explicitly disabled it (e.g., `disallowBindEmptyPassword=true` for OpenLDAP/AD-derivatives, or an explicit unauthenticated-bind rejection). Because the chainlink code does not itself defend against this well-known LDAP behavior, an attacker who knows only a victim's email (a non-secret, often guessable/enumerable value) and sends an empty password string can potentially get `conn.Bind` to return `nil` on such a server, after which `CreateSession` will look up the victim's real role via `FindUser` and issue a valid session cookie/ID for that victim — a full authentication bypass requiring zero real credentials.

The `TestPassword` function has the identical flaw [5](#0-4) .

### Impact Explanation
If the upstream LDAP server allows unauthenticated/empty-password binds (a common default posture for many LDAP implementations unless proactively hardened), an attacker with zero credentials — only knowledge of a victim's email — can obtain a fully privileged `ldap_sessions` entry impersonating that victim, inheriting their assigned role (up to Admin). This is a node authentication bypass / account takeover, matching the "authentication bypass" bounty impact class.

### Likelihood Explanation
Preconditions: (1) node configured to use `ldapauth` as its authentication provider, (2) the upstream LDAP server has not explicitly disabled unauthenticated/empty-password binds. No credentials, no network position beyond standard API access, and no operator/admin access are required — only a valid victim email address, which is frequently derivable or already known (e.g. via corporate email conventions). This is application-code-driven (missing an explicit empty-password guard before calling `Bind`), not solely a network/host misconfiguration, since applications performing LDAP binds are expected to reject empty passwords defensively regardless of server posture.

### Recommendation
In `CreateSession` (and `TestPassword`), explicitly reject any authentication attempt where `sr.Password` (or `password`) is empty/whitespace-only before calling `conn.Bind`, e.g.:
```go
if strings.TrimSpace(sr.Password) == "" {
    return "", errors.New("unable to log in with LDAP server. Check credentials")
}
```
This ensures the application never relies on the LDAP server's handling of RFC 4513 unauthenticated binds to determine authentication success.

### Proof of Concept
Go unit test plan (using the existing `LDAPConn` mock in `core/sessions/mocks`):
1. Construct `ldapAuthenticator` with a mocked `LDAPClient`/`LDAPConn` where `Bind(dn, "")` returns `nil` (simulating a server that accepts the RFC 4513 unauthenticated bind), and `Search` returns a valid entry for the victim's group membership (as used by `FindUser`).
2. Call `CreateSession(ctx, sessions.SessionRequest{Email: "victim@example.com", Password: ""})`.
3. Assert (currently failing) that `CreateSession` returns an error and does NOT insert a row into `ldap_sessions` / does not return a valid session ID, i.e. `err != nil` and `sessionID == ""`, proving that an explicit empty-password rejection is required before any code fix.
4. After adding the recommended guard, re-run the test and assert `CreateSession` returns an error even when the mocked `Bind` reports success for an empty password.
