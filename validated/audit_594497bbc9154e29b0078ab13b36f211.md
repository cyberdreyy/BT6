### Title
Aggregate instant-withdraw receipt lets unfunded later-epoch requests drain the funded instant-withdraw pool - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a protocol-translation gap: two layers disagree on the framing of a request, letting a second request "smuggle" through under the authority of the first. The analog in `IdleCreditVault` is the mismatch between per-epoch funding accounting (`pendingInstantWithdraws`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`) and aggregate per-user claim accounting (`instantWithdrawsRequests[_user]`). `claimInstantWithdrawRequest` burns and pays the entire user aggregate at par, regardless of which request epochs have actually been funded by `collectInstantWithdrawFunds`, so an unfunded second request can be claimed immediately against funds reserved for other instant withdrawers.

### Finding Description
Instant withdrawals are tracked in two representations:

- Funding side: `collectInstantWithdrawFunds(_amount)` decrements `pendingInstantWithdraws` and pulls underlying from the CDO, epoch by epoch (`IdleCreditVault.sol:398-403`).
- Claim side: `requestInstantWithdraw` accumulates `instantWithdrawsRequests[_user] += _amount` and records the per-epoch split only for default accounting (`IdleCreditVault.sol:356-375`). `claimInstantWithdrawRequest` then does `amount = instantWithdrawsRequests[_user]; _burn(_user, amount); _transferFundedClaim(_user, amount)` with no check that the full aggregate has been funded and no epoch gating like the normal-withdraw path has (`IdleCreditVault.sol:387-392`).

Compare with the normal withdraw flow, which enforces `epochNumber > lastWithdrawRequest[_user]` before paying (`IdleCreditVault.sol:326-328`). The instant path has no equivalent gate: a receipt minted in the current, still-unfunded epoch is fungible with an older funded receipt in the same user's balance.

Attack sequence (unprivileged tranche holder / instant withdrawer):

1. Epoch N: honest users queue instant withdraws; borrower/CDO funds them via `collectInstantWithdrawFunds`, moving underlying into the strategy. `pendingInstantWithdraws` for epoch N goes to 0 but the funded underlying sits in the strategy contract.
2. Attacker (who may also hold an old funded receipt, or none) calls `requestInstantWithdraw` in epoch N+1 through the CDO when `lastEpochApr > currentApr + instantWithdrawAprDelta` triggers the instant path in `IdleCDOEpochVariant` (`IdleCDOEpochVariant.sol:761-768`). Their receipt is recorded in `instantWithdrawsRequests[_user]` and `instantWithdrawClaimsByEpoch[N+1]`, but no funds have been collected for epoch N+1 yet (`pendingInstantWithdraws` increased, underlying not transferred).
3. Attacker immediately calls `claimInstantWithdrawRequest`. The strategy burns the whole `instantWithdrawsRequests[_user]` and `_transferFundedClaim` transfers it. `_transferFundedClaim` only protects `defaultRecoveryReserve` (`IdleCreditVault.sol:899-905`); it does not verify that the claimed amount is backed by collected instant-withdraw funds rather than funds earmarked for other pending instant receipts, buffer deposits awaiting `sendInterestAndDeposits`, or APR0/normal claim funding.

The epoch boundary that is supposed to separate "funded" receipts from "pending" receipts is lost when the per-epoch representation is collapsed into a single per-user aggregate — the same class of bug as an HTTP/2→HTTP/1 translation layer letting one request ride inside another's framing.

### Impact Explanation
Direct theft / insolvency of the instant-withdraw pool: the attacker redeems an unfunded receipt at par, consuming underlying that belongs to earlier instant withdrawers (whose claims then revert on insufficient balance or are permanently underfunded), or consuming deposit liquidity awaiting epoch start. The loss equals the attacker's instant request size, bounded only by tranche value they control and the funded-but-unclaimed instant pool balance, which can be the entire epoch's instant-withdraw queue. The "one receipt one payout" and solvency invariants are broken: one underlying token funds two receipts.

### Likelihood Explanation
Requires only that (a) instant withdrawals are enabled (`_isInstantWithdrawEnabled`, i.e., non-programmable deployment, `disableInstantWithdraw == false`), (b) the APR-drop condition makes `requestInstantWithdraw` reachable — borrower APR movements are normal protocol operation — and (c) funded-but-unclaimed underlying sits in the strategy, which is the steady state between `collectInstantWithdrawFunds` and users' claims. No privileged cooperation is needed; the attacker is an ordinary tranche holder requesting a withdrawal. The only uncertainty is whether the CDO-side `claimInstantWithdrawRequest` wrapper adds epoch gating I could not fully enumerate; the strategy-level function itself contains none, and the normal-withdraw path's explicit epoch gate suggests the instant path's absence is an oversight rather than enforced elsewhere.

### Recommendation
Track and gate instant claims per epoch the same way normal withdrawals are: require `epochNumber > requestEpoch` (or check that the request epoch's slice has been funded, e.g., funded flag/`pendingInstantWithdraws` reconciliation per epoch) before paying `instantWithdrawsRequestsByEpoch[user][epoch]` slices, rather than paying the aggregate `instantWithdrawsRequests[user]` unconditionally. Alternatively, have `_transferFundedClaim` deduct claimed amounts from a funded-instant counter so unfunded receipts cannot spend the collected pool.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";

/// PoC: an unfunded instant-withdraw receipt claims against the funded pool.
contract InstantWithdrawSmugglingPoC is Test {
    IdleCreditVault vault;
    address cdo = address(0xCD0);
    address alice = address(0xA11CE); // honest instant withdrawer, funded
    address bob = address(0xB0B);     // attacker

    function setUp() external {
        // deploy + initialize vault with idleCDO = cdo, underlying = test ERC20
        // 1. Epoch N: alice requestInstantWithdraw(X); cdo collectInstantWithdrawFunds(X)
        //    -> strategy now holds X underlying earmarked for alice's receipt.
    }

    function test_UnfundedInstantClaimDrainsFundedPool() external {
        // 2. Epoch N+1 begins; APR dropped so CDO routes bob's withdraw to requestInstantWithdraw.
        vm.prank(cdo);
        vault.requestInstantWithdraw(100e18, bob); // receipt minted, nothing funded for epoch N+1

        // 3. Bob claims in the SAME epoch. No epoch gate on the instant path.
        uint256 bobBalBefore = underlying.balanceOf(bob);
        vm.prank(cdo);
        vault.claimInstantWithdrawRequest(bob); // _transferFundedClaim sends bob 100e18

        // Bob was paid out of underlying collected for alice's epoch-N receipt.
        assertEq(underlying.balanceOf(bob) - bobBalBefore, 100e18);

        // 4. Alice's funded claim now reverts on insufficient balance (safeTransfer underflow)
        //    or leaves the strategy insolvent w.r.t. her receipt.
        vm.prank(cdo);
        vm.expectRevert();
        vault.claimInstantWithdrawRequest(alice);
    }
}
```

Key lines: `claimInstantWithdrawRequest` pays `instantWithdrawsRequests[_user]` with no epoch/funding check (`contracts/strategies/idle/IdleCreditVault.sol:387-392`), while funding is booked separately via `collectInstantWithdrawFunds`/`pendingInstantWithdraws` (`contracts/strategies/idle/IdleCreditVault.sol:398-403`), and `_transferFundedClaim` guards only `defaultRecoveryReserve`, not the instant pool (`contracts/strategies/idle/IdleCreditVault.sol:899-905`).
