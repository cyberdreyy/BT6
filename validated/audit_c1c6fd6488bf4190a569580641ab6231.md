### Title
Post-default instant-withdraw claims pay unhaircutted non-default-epoch receipts from the recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external bug is a buffer overflow: a write/read that escapes its intended boundary and corrupts adjacent state. The vault analog is `claimInstantWithdrawRequest`, which escapes the default-recovery boundary: after `finalizeDefaultRecovery`, only receipts booked in `defaultRecoveryEpoch` get the `defaultRecoveryPrice` haircut, while any receipt recorded under a different epoch is paid at par from the same contract balance that physically backs `defaultRecoveryReserve`.

### Finding Description
`claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest`, which only clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and pays it at `defaultRecoveryPrice` [1](#0-0) . Execution then falls through and pays the *entire remaining* `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim` [2](#0-1) .

The recovery basis computed at finalization is equally narrow: `defaultPendingClaimBasis` only adds `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch's instant bucket — when `pendingInstantWithdraws != 0` [3](#0-2) . `_defaultPrefundedInstantReserve` likewise reasons only about `instantWithdrawClaimsByEpoch[epochNumber]` [4](#0-3) . Unfunded instant receipts keyed to an earlier epoch are therefore:

- excluded from the haircut basis (never multiplied by `defaultRecoveryPrice`),
- left inside `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws`,
- payable 1:1 through the fallthrough path in `claimInstantWithdrawRequest`.

Because `defaultRecoveryReserve` is only a bookkeeping number — the underlying sits in the strategy contract — `_transferFundedClaim` draws those par payouts from tokens that are supposed to back haircutted default-epoch claims [5](#0-4) . The invariant "one receipt, one recovery-scaled payout" is broken for every instant receipt whose epoch key differs from `defaultRecoveryEpoch`.

### Impact Explanation
An unprivileged lender holding an instant-withdraw receipt from a non-default epoch (created, e.g., when the CDO only partially funded the instant queue before a `startEpoch`) is paid face value instead of `claimBasis * defaultRecoveryPrice / 1e18`. Each such claim directly drains the reserve; once the physical balance is exhausted, `safeTransfer` reverts for legitimate defaulted-epoch claimants — permanent freezing of their recovery proceeds. Quantified loss is up to the full unfunded non-default-epoch instant basis: attacker gains `(1 - defaultRecoveryPrice) * claimBasis` in excess, and late claimants lose their entire haircutted entitlement.

### Likelihood Explanation
Requires: (a) an instant-withdraw request left partially unfunded across an epoch boundary (the `pendingInstantWithdraws` remainder and `_defaultPrefundedInstantReserve` logic exist precisely because partial funding is a supported state), and (b) a subsequent borrower default finalized via `finalizeDefaultRecovery`. Both are reachable by ordinary lenders; the attacker only needs to hold such a receipt and call the CDO's `claimInstantWithdrawRequest` after finalization. Caveat I could not fully verify within this pass: whether `IdleCDOEpochVariant` permits a pending instant request to survive unpaid into a later epoch before default occurs — if the CDO always force-funds or cancels stale instant receipts at `startEpoch`, the cross-epoch remnant may be unreachable and the finding reduces to a latent inconsistency.

### Recommendation
Key instant-receipt clearing by claim, not by a single `defaultRecoveryEpoch`: in `claimInstantWithdrawRequest`, iterate/track per-epoch `instantWithdrawsRequestsByEpoch` (or store a `lastInstantWithdrawRequest` epoch like `lastWithdrawRequest` for normal receipts) so that *every* unfunded receipt outstanding at finalization is paid at `defaultRecoveryPrice`. Correspondingly, `defaultPendingClaimBasis` should aggregate unfunded instant basis across all epochs, not only `epochNumber`. Alternatively, revert post-finalization claims for receipts outside `defaultRecoveryEpoch` until they are explicitly funded.

```text
    _onlyIdleCDO();

    // burn strategy tokens from user
    _burn(_user, amount);

  }
```

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
