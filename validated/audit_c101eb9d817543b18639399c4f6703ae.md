### Title
Instant-withdrawal requests bypass all management and performance fees charged to regular withdrawal requests - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report describes a pool variant (`IndexPool`) that accrues no `barFee` while sibling pools do, letting LPs exit fee-free and starving `barFeeTo`. The analog in idle-tranches is the instant-withdrawal path of `IdleCreditVault`: normal `requestWithdraw` flows pay an upfront management fee (one epoch + remaining buffer) plus a performance fee on projected interest via `IdleCDOEpochVariant._totalWithdrawFees`, and those fees are booked into `pendingWithdrawFees` and settled to `feeReceiver`/`owner` at `stopEpoch`. Instant withdrawals mint a receipt 1:1 with the requested amount and pay it out at par, with no fee deduction anywhere in the path.

### Finding Description
- Regular withdrawals are charged `_totalWithdrawFees(_principal, _interest)`, which combines `_calculateManagementFee(_principal, epochDuration + remaining buffer)` with the performance fee `fee` on net gain (`IdleCDOEpochVariant.sol:888-906`). These fees accumulate in `pendingWithdrawFees` and are transferred to `feeReceiver` and `owner()` at `stopEpoch` via `_transferFeeUnderlyings` (`IdleCDOEpochVariant.sol:416-419, 439-459`).
- APR0 withdraw requests also pay fees: `prepareStopEpochWithApr0` computes `_apr0Fee = _apr0InterestGross * fee / FULL_ALLOC` and adds it to `_adjPendingWithdrawFees` (`IdleCreditVault.sol:521-527`).
- Instant withdrawals pay nothing. `requestInstantWithdraw` burns `_amount` strategy tokens from the CDO and mints the user a receipt of the same `_amount` (`IdleCreditVault.sol:356-375`). `claimInstantWithdrawRequest` transfers the full recorded `instantWithdrawsRequests[_user]` to the user (`IdleCreditVault.sol:380-393`). No call to `_totalWithdrawFees`, no performance-fee split, and no management-fee accrual exists anywhere on this path; `pendingWithdrawFees` is never increased for instant requests.

Because the CDO controls the `_amount` passed to `requestInstantWithdraw`, a complete confirmation requires checking the CDO-side instant-request wrapper (in `IdleCDOEpochVariant`, gated by `instantWithdrawAprDelta`/`instantWithdrawDelay`/`disableInstantWithdraw` in `setInstantWithdrawParams` and `_isInstantWithdrawEnabled`). However, the receipt is minted 1:1 and claimed at par, so any fee would have to be embedded in `_amount`; nothing in the strategy enforces or verifies that, and no fee bookkeeping exists for the instant bucket.

### Impact Explanation
- Direct loss of protocol yield: a KYC-passing lender holding tranche tokens can exit via the instant-withdraw path immediately after `startEpoch` (when `allowInstantWithdraw` is set and surplus underlying remains) and pay zero management fee and zero performance fee, while every lender using `requestWithdraw` is charged both. The uncharged management fee is `principal * managementFee * (epochDuration + buffer) / 31,536,000,000,000`, i.e., roughly `managementFee` percent of principal per epoch — directly diverted from `unclaimedFees`/`feeReceiver`/`owner`.
- Incentive distortion mirrors the original finding: rational LPs prefer instant withdrawals to dodge fees, draining the unlent buffer that exists as "insurance of last resort" and cheap-redeem liquidity for everyone else.
- Caveat on severity: fee-free instant exits may be intentional design (early exit forgoes epoch interest, arguably compensating for skipped fees, and instant mode is disabled for programmable borrowers and the prefunded variant via `_isInstantWithdrawEnabled`). The management fee, however, is charged on principal — not on interest — so forgoing interest does not substitute for it; the management-fee component is unambiguously skipped. If intentional, this is still inconsistent fee treatment worth documenting; if unintentional, it is quantifiable lost fee revenue per instant withdrawal.

### Likelihood Explanation
- Medium. Exploitation requires only a normal whitelisted/KYC'd tranche holder (`isWalletAllowed`), the epoch running with `allowInstantWithdraw == true`, and sufficient unlent underlying to cover `pendingInstantWithdraws`. No privileged role is needed. The window is bounded (instant requests are only serviced at `startEpoch` from available cash), which caps the extractable amount to the unlent buffer per epoch.
- Likelihood is reduced because the owner/manager can disable instant withdrawals (`disableInstantWithdraw`), and the prefunded and programmable-borrower modes permanently disable the path.

### Recommendation
Apply the same fee model to instant withdrawals: when the CDO computes the `_amount` for `requestInstantWithdraw`, deduct `_calculateManagementFee(_principal, _withdrawRequestManagementFeeDuration())` (or the elapsed-period equivalent) and route it into `pendingWithdrawFees`/`unclaimedFees` so it settles to `feeReceiver` and `owner()` at `stopEpoch`, consistent with `_totalWithdrawFees` on normal requests and the APR0 performance-fee split in `prepareStopEpochWithApr0`.

### Proof of Concept
Foundry fork PoC sketch (against `test/foundry/IdleCreditVault.t.sol` harness):
1. Deposit `amount` via `idleCDO.depositAA`, call `_setFeeParams(feeReceiver, feeRate, FULL_ALLOC, mgmtFeeRate)` with nonzero `managementFee`.
2. `startEpoch` with funds left unlent so `allowInstantWithdraw` is enabled.
3. User A calls the CDO instant-withdraw request; User B calls `requestWithdraw` for the same principal.
4. Warp to `epochEndDate`, `stopEpoch`, then have both users claim.
5. Assert: User B's claim was reduced by `_totalWithdrawFees` and `feeReceiver`/`owner` received `pendingWithdrawFees`; User A's claim equals full principal with zero fee deducted and `pendingWithdrawFees` never increased for the instant receipt. The delta `managementFee * principal * duration / FULL_ALLOC / YEAR` is the per-withdrawal leak.
Note: step 3 requires confirming the exact CDO-side instant request entry point and whether it nets fees into `_amount`, which I could not fully verify within the indexed code — if the wrapper already deducts the fee, this finding reduces to a documentation inconsistency.
