### Title
ERC4626 vault fees make `redeemUnderlying` burn too few shares, returning less underlying than requested and breaking tranche withdrawals - (File: contracts/strategies/ERC4626Strategy.sol)

### Summary
`ERC4626Strategy.redeemUnderlying` converts a requested underlying amount into strategy-token shares using `IERC4626(strategyToken).convertToShares(_amount)` (`contracts/strategies/ERC4626Strategy.sol:92-94`). This mirrors the Gnosis auction bug: the contract computes the amount to pull from an external integration without accounting for a fee the external contract may charge on the operation. Any ERC4626-compliant vault that charges a withdrawal/exit fee (common in Morpho-style and fee-taking ERC4626 vaults, and a parameter the vault's admin can enable post-deployment) will deliver less than `_amount` of underlying for those shares. Since `IdleCDO._withdraw`/`IdleCreditVault` redeem flows expect the requested underlying back to pay the redeemer, withdrawals either pay less than owed or revert, freezing user funds.

### Finding Description
In the external report, `GnosisTrade` approved `sellAmount` while `EasyAuction.initiateAuction` pulled `sellAmount * (1 + fee)`, so the call reverted once fees were non-zero. The same mistake exists here in inverse form:

```solidity
function redeemUnderlying(uint256 _amount) external virtual onlyIdleCDO returns (uint256 redeemed) {
    return _redeem(IERC4626(strategyToken).convertToShares(_amount));
}
``` [1](#0-0) 

`convertToShares` prices shares as `assets * totalShares / totalAssets` with no fee term. For a fee-charging vault, the number of shares actually needed to net `_amount` is given by `previewWithdraw(_amount)`, which returns strictly more shares when an exit fee applies. Redeeming only `convertToShares(_amount)` shares makes `redeem` return `_amount` minus the fee. The same class of assumption appears in `deposit`, which pulls `_amount` from the IdleCDO and calls `vault.deposit(_amount)` trusting share-value parity [2](#0-1) , and `price()` uses `convertToAssets` rather than `previewRedeem`, so `getContractValue` overstates NAV when a fee exists [3](#0-2) . The strategy already grants unlimited approval (`_initialize`, L67), so the failure is purely in the share math, not allowance.

### Impact Explanation
When the underlying ERC4626 vault applies a non-zero exit fee:
- `IdleCDO.withdrawAA/withdrawBB` (which invoke `strategy.redeemUnderlying`) either deliver less than the user's owed amount — a solvency/shortfall absorbed silently by the last redeemers — or revert inside `vault.redeem`/`transfer`, permanently freezing withdrawals of the pool's funds held in the vault.
- `price()`/`getContractValue` overstate NAV by up to the fee percentage, so later depositors mint shares at an inflated price, realizing a loss on exit (unfair mint/burn, drained on the remaining holders).
Quantified loss: up to the vault's exit fee times the redeemed amount per withdrawal, plus a withdrawal DoS while funds sit in the fee-charging vault.

### Likelihood Explanation
Conditional, like the original report: currently many ERC4626 vaults charge zero fee, so behavior is correct today. The moment the deployed `strategyToken` vault (or a vault swapped in via a future strategy) enforces a fee, all `redeemUnderlying` calls short or revert. Attacker-side requirements are none — this is an integration/data-validation flaw triggered by an honest user calling `withdrawAA`/`withdrawBB` during any epoch phase.

### Recommendation
- In `redeemUnderlying`, use `previewWithdraw(_amount)` (or `redeem`→measure `balanceOf` delta) instead of `convertToShares`, so the correct number of shares is burned to net `_amount`.
- In `price()`/NAV paths, value the position with `previewRedeem(shares)` rather than `convertToAssets`, so fees are not counted as pool NAV.
- Alternatively, redeem the full share balance and reconcile by `balanceOf` deltas, and document that only fee-free ERC4626 vaults are supported if the fee-aware path is not adopted.

### Proof of Concept
```solidity
// Fork test: deploy a fee-charging ERC4626 (e.g., OpenZeppelin ERC4626Fees with 1% exit fee)
// as strategyToken for ERC4626Strategy via IdleCDO.
uint256 shares = feeVault.convertToShares(amount);   // shares for gross amount
uint256 got = feeVault.redeem(shares, ...);          // returns amount * 99/100
assertLt(got, amount);                                // 1% shortfall per withdrawal
// IdleCDO.withdrawAA then either pays the user 1% less than owed or the
// subsequent safeTransfer of `amount` reverts -> user funds frozen.
```
A Foundry fork PoC requires a live ERC4626 vault with a mutable entry/exit fee (or a mock deployed on fork state) set as `strategyToken`; with fee = 1%, `redeemUnderlying(100e6)` yields ~99e6 underlying while `previewWithdraw` would have required ~1.01% more shares to settle in full.

Uncertain: I could not verify the exact `IdleCDO.sol` lines that consume the `redeemed` return value (whether it tolerates a shortfall or reverts on a strict `transfer(_amount)`), which determines whether the failure mode is silent loss vs. revert — both produce direct fund impact either way.
