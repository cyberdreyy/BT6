### Title
CreateAccount action can permanently pre-empt a NEP-616 deterministic account id, causing silent denial of the rightful deriver's state initialization - (File: `runtime/runtime/src/actions.rs`)

### Summary
`check_account_existence`'s `Action::CreateAccount` branch only rejects account creation when `account_is_implicit` returns true, and `account_is_implicit` (in `core/primitives/src/utils.rs`) only recognizes `AccountType::NearImplicitAccount` and ETH-implicit accounts, not NEP-616 deterministic accounts. An attacker can therefore submit a plain `CreateAccount` action targeting a deterministic-account-shaped `account_id` they don't control the derivation input for, creating an empty account there before the legitimate deriver ever submits `Action::DeterministicStateInit`.

### Finding Description
`check_account_existence` (`runtime/runtime/src/actions.rs:787-818`) handles `Action::CreateAccount` by checking only:
```
if account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts) {
    return Err(ActionErrorKind::OnlyImplicitAccountCreationAllowed { .. }.into());
}
``` [1](#0-0) 

`account_is_implicit` (`core/primitives/src/utils.rs:471-477`) only special-cases `AccountType::NearImplicitAccount` and, when ETH-implicit accounts are enabled, the crate's generic `is_implicit()`: [2](#0-1) 

Separately, this repo implements NEP-616 deterministic accounts via `derive_near_deterministic_account_id` and a dedicated `Action::DeterministicStateInit` action, which is handled by its own branch in `check_account_existence`:
```
Action::DeterministicStateInit(_) => {
    // Existing and non existing is valid for DeterministicStateInit.
    // Does not exist => The account will be created by the action.
    // Does exist => Nothing happens but the receipt is not aborted to
    // allow optional init before other actions.
}
``` [3](#0-2) [4](#0-3) 

Because `CreateAccount` and `DeterministicStateInit` are checked independently, and `DeterministicStateInit` explicitly no-ops (silently) when the target account already exists, an attacker can front-run the legitimate deriver: submit a bare `CreateAccount` action against the deterministic-account-shaped id first (which succeeds as long as `account_is_implicit` returns false for that id and any top-level-name permission checks pass, e.g. the id's length exceeds `min_allowed_top_level_account_length`). Once that empty account exists, the rightful deriver's later `DeterministicStateInit` action targeting the same id becomes a silent no-op per the comment above, permanently denying them the ability to instantiate their intended state at that address.

The root cause is that `account_is_implicit` treats "implicit" narrowly (NEAR-implicit / ETH-implicit only) and does not classify NEP-616 deterministic account ids as implicit, so the `OnlyImplicitAccountCreationAllowed` guard that exists specifically to prevent hijacking of implicit accounts never fires for this account shape.

### Impact Explanation
This falls under "Unauthorized transaction" / permanent griefing of contract execution flows: an unprivileged attacker can permanently deny a legitimate user the ability to instantiate their deterministically-derived contract/account state, since the account will already exist (empty) by the time the rightful `DeterministicStateInit` is submitted, and that action silently no-ops rather than failing or overwriting.

### Likelihood Explanation
The attack requires only a single, permissionless `CreateAccount` transaction with a crafted `receiver_id` matching the deterministic-account id shape and exceeding `min_allowed_top_level_account_length`; no deposit, special permission, or knowledge of the actual `state_init` preimage is needed. This is fully repeatable against any deterministic account id an attacker can predict or observe being referenced (e.g., via a not-yet-submitted `DeterministicStateInit` transaction visible in the mempool), making it low-cost and race-condition-exploitable.

### Recommendation
Extend `account_is_implicit` (or add a dedicated check in `check_account_existence`'s `CreateAccount` branch) to also treat NEP-616 deterministic account ids (`AccountType::NearDeterministicAccount` or equivalent) as implicit/reserved, rejecting plain `CreateAccount` actions against them the same way `OnlyImplicitAccountCreationAllowed` rejects implicit-hex ids. Only `Action::DeterministicStateInit` (with the correct `state_init` producing the matching hash) should be allowed to instantiate such accounts.

### Proof of Concept
Unit test in `runtime/runtime/src/actions.rs` test module:
1. Construct a synthetic `account_id` matching the deterministic-account shape (`"0s"` + 40 lowercase hex, not derived from any real `state_init`).
2. Call `check_account_existence(&Action::CreateAccount(CreateAccountAction {}), &None, &account_id, &config, true)` and assert it returns `Ok(())` (demonstrating the missing guard), contrasted with an equivalent ETH-implicit id (`"0x"` + 40 hex) under the same config returning `Err(ActionErrorKind::OnlyImplicitAccountCreationAllowed { .. })`.
3. Integration/test-loop follow-up: after the `CreateAccount` action executes and the account exists, submit a `DeterministicStateInit` action for the same `account_id` with the real `state_init`, and assert the account's state was never initialized (per the documented no-op-on-exists behavior), confirming permanent denial of the rightful deriver.

/// From `near-account-id` version `1.0.0-alpha.2`, `is_implicit` returns true for ETH-implicit accounts.
/// This function is a wrapper for `is_implicit` method so that we can easily differentiate its behavior
/// based on whether ETH-implicit accounts are enabled.
pub fn account_is_implicit(account_id: &AccountId, eth_implicit_accounts_enabled: bool) -> bool {
    if eth_implicit_accounts_enabled {
        account_id.get_account_type().is_implicit()
    } else {
        account_id.get_account_type() == AccountType::NearImplicitAccount
    }
}

/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
