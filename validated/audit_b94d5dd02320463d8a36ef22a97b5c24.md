### Title
Pre-default-epoch withdraw receipts bypass the recovery haircut and drain the default reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug (crafted input reaches a code path that corrupts memory outside the intended buffer) maps to a claim-routing flaw: a withdraw receipt created in an epoch *earlier* than the defaulted epoch escapes the per-epoch haircut accounting in `_claimDefaultedWithdrawRequest` and is paid at par by `_claimFundedWithdrawRequest`, even though its basis was included in `defaultPendingClaimBasis` and therefore sized into the shared recovery reserve at a haircut.

### Finding Description
`finalizeDefaultRecovery` sizes the recovery reserve using `defaultPendingClaimBasis()`, which is the **aggregate** `pendingWithdraws` plus current-epoch instant claims — it does not distinguish which epoch each receipt belongs to (IdleCreditVault.sol:644-649, 679-688). All pending receipts are therefore priced into one `defaultRecoveryPrice`.

On the claim side, however, the haircut is applied **per epoch**:

- `_claimDefaultedWithdrawRequest` only clears `withdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (lines 772-784 via `_clearWithdrawClaimForEpoch` at 811-837).
- A receipt requested in an earlier epoch `E < defaultRecoveryEpoch` has `withdrawsRequestsByEpoch[_user][E] != 0` but a zero entry at `defaultRecoveryEpoch`, so `claimBasis == 0` and the defaulted path returns nothing.
- `_claimLossAdjustedWithdrawRequest` returns 0 because `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` is 0 for a normally-ended epoch `E`.
- Execution reaches `_claimFundedWithdrawRequest` (lines 319-350). Its only gating is `epochEndDate() != 0 && epochNumber <= lastWithdrawRequest[_user]`. After default, `epochNumber` was already bumped past `E`, so the check passes. It then pays `withdrawsRequests[_user]` **at par** through `_transferFundedClaim`, drawing on the same underlying that backs the haircutted recovery reserve.

Two concrete ways an attacker obtains such a stale-epoch receipt:

1. Request a withdraw during the buffer before the final epoch starts (receipt recorded under `epochNumber = E`), never claim during the healthy epoch `E+1` wait, and let epoch `E+1` end in borrower default. `lastWithdrawRequest[_user] = E < defaultRecoveryEpoch`.
2. Make a second `requestWithdraw` in the same pre-default epoch — allowed — so the aggregate `withdrawsRequests[_user]` mixes epochs; only the `defaultRecoveryEpoch` slice is cleared with a haircut, the rest pays at par.

The broken invariant is one-receipt-one-payout / fair recovery distribution: receipts that were counted in `defaultPendingClaimBasis` (and thus already diluted everyone else's `defaultRecoveryPrice`) are paid 100 cents on the dollar, leaving the reserve underfunded for all other claimants.

### Impact Explanation
Direct theft / insolvency with quantifiable loss. If `pendingWithdraws` contains `X` of pre-default-epoch receipts and `Y` of default-epoch receipts and the recovery price is `p < RECOVERY_FULL`, holders of `X` receive `X` instead of `X * p / RECOVERY_FULL`, extracting `X * (1 - p)` of excess underlying from the reserve. Later claimants (default-epoch receipts and post-default requests paid via `_transferDefaultRecovery`) face an underfunded reserve and receive less than their haircutted entitlement or nothing — a permanent loss of unclaimed recovery funds, not a rounding dust. No privileged misbehavior is required: the attacker is an ordinary KYC'd lender who simply delays claiming (or submits a second request), and the honest manager/owner runs `stopEpoch` and `finalizeDefault` normally.

### Likelihood Explanation
Medium. Requirements: (a) the user requests a withdraw in the buffer of epoch `E` and does not claim during epoch `E+1` (or makes requests in two distinct epochs before default); (b) the borrower defaults at the `stopEpoch` ending `E+1`; (c) recovery is partial (`p < RECOVERY_FULL`), otherwise par payout equals the haircut anyway. Idle lenders who forget to claim, plus intentional positioning before a distressed epoch, both reach the state. Existing guards do not stop it: `requestWithdraw` only blocks a *new* request when `lossRecoveryPriceByEpoch[lastWithdrawRequest] != 0` (a stopEpochWithDuration loss, not a pending default), the post-finalization `revert` on line 249 only fires for requests made *after* finalization, and `_beforeUnpause`/default flags freeze deposits but not `claimWithdrawRequest`.

### Recommendation
In `claimWithdrawRequest`, when `defaultRecoveryFinalized`, do not fall through to `_claimFundedWithdrawRequest` for receipts whose basis was included in `defaultPendingClaimBasis`. Concretely:

- Iterate/clear all non-zero `withdrawsRequestsByEpoch[_user][*]` entries (or track a `firstPendingEpoch`/`claimableBasis` per user) and apply `defaultRecoveryPrice` to the full aggregate basis, not only `defaultRecoveryEpoch`.
- Alternatively, snapshot per-user pending basis at finalization (e.g., `defaultClaimBasis[_user] = withdrawsRequests[_user] + apr0 principal/interest + instant claims`) and pay `basis * defaultRecoveryPrice / RECOVERY_FULL`, clearing every receipt bucket in one shot.
- Subtract every haircutted claim from `pendingWithdraws`/`defaultRecoveryReserve` so the reserve cannot be overdrawn by par-priced claims.

### Proof of Concept
Foundry fork sketch (existing test harness style in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// setup: two KYC'd users A and B deposit AA; epoch runs with fixed APR.
// epoch E buffer (epoch not running):
vm.prank(A); cdoEpoch.requestWithdraw(aTrancheBal, address(AAtranche)); // receipt epoch = E
// manager starts epoch E+1; epochNumber is still E until stopEpoch bumps it
vm.prank(manager); cdoEpoch.startEpoch();
// A could also request again during the next buffer; skip for minimal case
// borrower defaults: repay nothing
deal(underlying, borrower, 0);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager); cdoEpoch.stopEpoch(0, 0); // defaulted == true, epochNumber -> E+1
// B requests withdraw earlier in epoch E+1's buffer BEFORE default -> receipt epoch E+1
// (alternatively B has an instant/normal receipt recorded under epoch E+1)
// manager finalizes with 50% recovery
uint256 recovered = totalBasis / 2;
deal(underlying, manager, recovered);
vm.startPrank(manager);
IERC20(underlying).approve(address(strategy), recovered);
cdoEpoch.finalizeDefault(recovered, manager);
vm.stopPrank();
// A claims: _claimDefaultedWithdrawRequest returns 0 (no entry at epoch E+1),
// _claimFundedWithdrawRequest pays A's full receipt at par from the reserve
uint256 balPre = underlying.balanceOf(A);
vm.prank(A); cdoEpoch.claimWithdrawRequest();
assertEq(underlying.balanceOf(A) - balPre, aReceiptFull); // par, not 50%
// B claims defaulted-epoch receipt at 50%:
vm.prank(B); cdoEpoch.claimWithdrawRequest();
// reserve is now short: remaining claimants (or postDefaultRequests) cannot be paid
```

Caveat: I was unable to read `_transferFundedClaim`/`_transferDefaultRecovery` internals to confirm both draw on the same underlying balance held by the strategy; the finding holds if `_transferFundedClaim` pays from the strategy's general underlying holdings (which include the recovery reserve). If `_transferFundedClaim` enforces a separate "funded" bucket that excludes reserved recovery, severity reduces to a locking/DoS on the residual `pendingWithdraws` accounting instead.

Key code: `claimWithdrawRequest` at IdleCreditVault.sol:301-314, `_claimFundedWithdrawRequest` at 319-350, `_claimDefaultedWithdrawRequest` at 772-784, `defaultPendingClaimBasis` at 644-649, `finalizeDefaultRecovery` at 661-710.
