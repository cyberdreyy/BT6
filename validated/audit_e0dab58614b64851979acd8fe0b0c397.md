### Title
Unauthenticated-role cross-job pipeline run enumeration via GET /v2/pipeline/runs - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Index` calls `prc.App.JobORM().PipelineRuns(ctx, nil, offset, size)` whenever the `ID` route param is absent, returning pipeline runs across every job on the node rather than a caller-owned subset. This code path is reachable at `GET /v2/pipeline/runs`, which is registered with only generic authentication (`auth.Authenticate`) and no per-route role restriction (unlike sibling routes wrapped in `auth.RequiresEditRole`/`auth.RequiresAdminRole`/`auth.RequiresRunRole`), so any authenticated user regardless of role (including the lowest "view" role) can invoke it.

### Finding Description
`PipelineRunsController.Index` branches on `c.Param("ID")`: [1](#0-0) 
When `id == ""`, it passes `nil` as the job ID filter to `JobORM().PipelineRuns`, which returns runs for all jobs, then serializes them via `presenters.NewPipelineRunResources` and returns them in the paginated JSON response.

The route wiring in `router.go` shows two routes mapped to the same `prc.Index` handler: [2](#0-1) 
`/v2/pipeline/runs` has no `:ID` path parameter, so `c.Param("ID")` is always empty on that route — this is exactly the `id == ""` branch that fetches all jobs' runs. Both routes sit inside the `authv2` group, which only requires successful authentication: [3](#0-2) 
Unlike nearly every other mutating/sensitive endpoint in this group (jobs create/update/delete, keys import/export, bridges, transfers, etc.), which are explicitly wrapped with `auth.RequiresEditRole`, `auth.RequiresRunRole`, or `auth.RequiresAdminRole`, the `pipeline/runs` GET routes have no such role wrapper, so a session/token belonging to the lowest privilege level ("view") passes `auth.Authenticate` and reaches `prc.Index` unrestricted.

Pipeline run resources returned by the presenter include task run data (inputs/outputs), which for bridge or HTTP tasks can contain response bodies that may hold sensitive data returned from external adapters. There is no per-job ownership or role-based filtering anywhere in this code path — `JobORM().PipelineRuns` performs a plain SQL query bounded only by `offset`/`size`, not by the requesting user's role or any job ACL (Chainlink v2 job specs have no per-job ownership/ACL model at all; roles are node-wide: admin/edit/run/view).

### Impact Explanation
A user granted only the "view" role (or any authenticated token with any role) can retrieve pipeline run history — including task outputs — for every job on the node, not just jobs they administer. This is a cross-user/cross-tenant information disclosure: it can leak values returned by bridge/HTTP tasks (which may include off-chain API responses configured by another operator on the same node), aggregator internals, and job execution metadata belonging to jobs the caller has no operational relationship to. This matches the bounty impact class of unauthorized access to sensitive information / broken access control (missing authorization on a read endpoint), scoped to node operators running multi-role or multi-tenant instances.

### Likelihood Explanation
Exploitation requires only a valid, low-privileged Chainlink API credential (a "view" role user session or API token) — no admin or edit role is needed. The request is a single unauthenticated-role, fully authenticated `GET /v2/pipeline/runs`. This is trivially repeatable, requires no timing race, and works identically on any node that has more than one job and issues view-only credentials to less-trusted operators/monitoring users.

### Recommendation
Add a role wrapper to the `/v2/pipeline/runs` and `/v2/jobs/:ID/runs` GET routes consistent with the sensitivity of the data (e.g., `auth.RequiresEditRole` or at minimum a dedicated check), and/or change `PipelineRunsController.Index` to reject/scope the `id == ""` case so it cannot return cross-job data to callers without sufficient privilege. If the "all runs" view is intended for admin/edit operators only, restrict the route explicitly rather than relying on generic authentication.

### Proof of Concept
Go handler-level integration test (in `core/web/pipeline_runs_controller_test.go`):
1. Seed two jobs, Job A and Job B, each with at least one completed pipeline run containing distinguishable task output data (e.g., embed a unique bridge response string per job).
2. Create an authenticated test client using a user/token with role `view` (lowest privilege, via the app's test session/auth helpers already used in this test file).
3. Call `GET /v2/pipeline/runs` (no `:ID`) using the view-role client.
4. Assert HTTP 200 (not 403), and that the decoded `PipelineRunResource` list contains run IDs/outputs belonging to both Job A and Job B — i.e., the view-role caller received data from a job it does not administer.
5. Contrast with `GET /v2/jobs/:ID/runs` scoped by Job A's ID to show the per-job endpoint correctly narrows results, proving the `/v2/pipeline/runs` route is the leaking surface.

```go
func (prc *PipelineRunsController) Index(c *gin.Context, size, page, offset int) {
	id := c.Param("ID")

	// Temporary: if no size is passed in, use a large page size. Remove once frontend can handle pagination
	if c.Query("size") == "" {
		size = 1000
	}

	var pipelineRuns []pipeline.Run
	var count int
	var err error

	ctx := c.Request.Context()
	if id == "" {
		pipelineRuns, count, err = prc.App.JobORM().PipelineRuns(ctx, nil, offset, size)
	} else {
		jobSpec := job.Job{}
		err = jobSpec.SetID(c.Param("ID"))
		if err != nil {
			jsonAPIError(c, http.StatusUnprocessableEntity, err)
			return
		}

		pipelineRuns, count, err = prc.App.JobORM().PipelineRuns(ctx, &jobSpec.ID, offset, size)
	}
```
