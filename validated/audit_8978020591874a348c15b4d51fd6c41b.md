### Title
Loss-adjusted withdraw receipts are paid at par after a later request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks a user's request epoch in a single slot, `lastWithdrawRequest[_user]` (line 282). When `stopEpochWithDuration` realizes a loss, the pending receipts of that epoch are funded only at the haircutted `lossRecoveryPriceByEpoch[epoch]`. However, `_claimLossAdjustedWithdrawRequest` (line 789) derives the loss epoch solely from `lastWithdrawRequest[_user]`. If the user submits a second `requestWithdraw` in a subsequent epoch, `lastWithdrawRequest[_user]` is overwritten (line 282), `lossRecoveryPriceByEpoch[newEpoch]` is zero, the loss-adjusted path returns 0 without clearing the old receipt, and `_claimFundedWithdrawRequest` (line 319) then pays the aggregate `withdrawsRequests[_user]` — which still includes the haircutted receipt — at par from funded strategy underlyings.

### Finding Description
Flow:

1. Epoch N (running phase). A tranche holder calls `cdoEpoch.requestWithdraw(amount, tranche)`. `IdleCreditVault.requestWithdraw` burns CDO strategy tokens, mints receipt tokens to the user, increments `pendingWithdraws`, `withdrawsRequests[_user]`, `withdrawsRequestsByEpoch[_user][N]`, and sets `lastWithdrawRequest[_user] = N` (lines 271–294).
2. `stopEpochWithDuration` is called with `_lossAmount > 0`. `previewLossAdjustedWithdrawFunds` haircuts pending receipts, the borrower funds only `pending * price`, and `lossRecoveryPriceByEpoch[N]` is set to the recovery ratio. The user's `withdrawsRequestsByEpoch[_user][N]` and `withdrawsRequests[_user]` are left unchanged — clearing happens lazily in `_clearWithdrawClaimForEpoch`.
3. Epoch N+1 buffer/running: the same user calls `requestWithdraw` again (allowed — comments at lines 323–324 explicitly permit a new request before claiming). Now `lastWithdrawRequest[_user] = N+1`.
4. Epoch N+1 stops normally and funds pending receipts at par.
5. The user calls `cdoEpoch.claimWithdrawRequest()` → `claimWithdrawRequest(_user)`:
   - `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user] = N+1`, `lossRecoveryPriceByEpoch[N+1] == 0`, returns 0 without touching the epoch-N receipt (lines 790–792).
   - `_claimFundedWithdrawRequest` passes the `epochNumber > lastWithdrawRequest` gate and pays `amount = withdrawsRequests[_user]` — the full, un-haircutted basis including the epoch-N receipt — via `_transferFundedClaim` (lines 338–349).

The strategy only received `claimBasis * lossRecoveryPrice` for the epoch-N receipts, but pays `claimBasis` in full. The difference `claimBasis * (1 - lossRecoveryPrice)` is paid out of underlyings that back other users' funded receipts.

### Impact Explanation
Direct insolvency/theft: an attacker holding tranche tokens can deliberately park a receipt through a loss epoch, then re-request in a later epoch to upgrade the haircutted receipt to par. The overpayment `claimBasis * (1 - lossRecoveryPrice)` comes out of the strategy's funded balance, so later legitimate claimants' `claimWithdrawRequest` reverts or is underpaid — one receipt, more than one payout's worth of funding consumed. Quantified loss: proportional to the loss haircut; e.g., a 50% `lossRecoveryPrice` on a 100k receipt steals ~50k of other users' funded claims.

### Likelihood Explanation
Requires only an unprivileged tranche holder and an epoch that ends via `stopEpochWithDuration` with `_lossAmount > 0` (an honest manager action), followed by a normal second request in a later epoch — no privileged role, no timing exoticism. No existing guard stops it: `_checkDefault` does not trigger on loss-adjusted stops, the reserve guard in `_transferFundedClaim` (lines 899–905) only protects `defaultRecoveryReserve` (zero outside defaults), and the funded-claim gate checks `lastWithdrawRequest` which has been overwritten with a settled epoch.

### Recommendation
Do not key the loss-adjusted claim to the mutable `lastWithdrawRequest`. Either iterate the user's receipt epochs and apply `lossRecoveryPriceByEpoch[e]` per epoch inside `_claimFundedWithdrawRequest` before paying the remainder at par, or — simpler — at `requestWithdraw` time, eagerly settle/clear any prior receipt whose epoch has a non-zero `lossRecoveryPriceByEpoch` so `withdrawsRequests[_user]` only ever contains par-eligible basis.

### Proof of Concept
Foundry fork test (sketch, mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testLossReceiptPaidAtParAfterSecondRequest() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);                 // attacker deposits
    _transferBurnedTrancheTokens(address(this), true);

    _startEpochAndCheckPrices(0);              // epoch 0 running
    uint256 principal = cdoEpoch.requestWithdraw(
        IERC20(AAtranche).balanceOf(address(this)) / 2, address(AAtranche));

    // manager stops epoch 0 with a 50% loss -> lossRecoveryPriceByEpoch[0] = 0.5e18
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(30 days, /*loss*/ cdoEpoch.getContractValue() / 2);
    // borrower funds haircutted pendingWithdraws only

    // remaining tranche still deposited; epoch 1 buffer: request again
    _startEpochAndCheckPrices(1);
    cdoEpoch.requestWithdraw(1, address(AAtranche));   // overwrites lastWithdrawRequest to epoch 1

    // epoch 1 ends normally, funded at par
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, /* par funding for pending */);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;

    // BUG: paid includes epoch-0 principal at par instead of 50% haircut
    assertGt(paid, principal / 2, "loss receipt paid at par");
}
```

Expected outcome: the claim succeeds paying the full aggregate `withdrawsRequests` balance; the excess over the haircutted funded amount is taken from underlyings reserved for other claimants, causing subsequent `claimWithdrawRequest` calls to revert on insufficient balance.
