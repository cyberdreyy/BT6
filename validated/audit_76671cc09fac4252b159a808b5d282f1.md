### Title
`getMultipleAccounts`/`getProgramAccounts` abort the entire response when a single matched account's data exceeds the base58 size limit - (File: rpc/src/rpc.rs)

### Summary
The `getMultipleAccounts` and `getProgramAccounts` (non-`jsonParsed`) JSON-RPC handlers encode each requested/matched account individually and propagate any single encoding error with `?`. Since `encode_account` returns a hard `Err` whenever an account's data (or data-slice) exceeds `MAX_BASE58_BYTES` under `Base58`/`Binary` encoding, one oversized account anywhere in a batch causes the whole call to fail with `InvalidRequest`, even though every other pubkey in the batch could have been encoded successfully. This mirrors the reported bug class where a single unavailable/faulty entity in a batch blocks operations on all other, healthy entities in that batch.

### Finding Description
`encode_account` deliberately errors out instead of degrading gracefully when base58/binary encoding cannot represent an account's data: [1](#0-0) 

`get_multiple_accounts` iterates over every requested pubkey and immediately bails out of the whole loop the moment one call to `get_encoded_account` (which calls `encode_account`) errors: [2](#0-1) 

`get_program_accounts` has the same pattern for the non-`jsonParsed`/non-SPL-token-owner path: it maps every matched `(pubkey, account)` pair through `encode_account` and `.collect::<Result<Vec<_>>>()?`, so one oversized account among potentially hundreds of matches aborts the entire scan result: [3](#0-2) 

By contrast, the account-subscription/`encode_ui_account` code path treats the same condition as non-fatal and substitutes an inline error string for just that one account's `data` field, letting the rest of the response succeed: [4](#0-3) [5](#0-4) 

This shows the two nearly-identical encoding paths in the same codebase disagree on error handling: pubsub degrades per-item, while the batched HTTP RPC calls fail the entire batch because of one item — exactly the "one bad/unavailable entity blocks access to all others in the batch" bug class from the external report, just triggered by an oversized account instead of a paused strategy.

### Impact Explanation
Any unprivileged RPC client can make a single, unauthenticated `getMultipleAccounts` call (with `encoding: "base58"` or `"binary"`, which are valid, documented encodings) mixing a small number of normal pubkeys with one pubkey holding more than 128 bytes of data (which is common — most non-trivial program accounts exceed this), and the entire response fails, hiding data for every account in that call including ones that would otherwise have decoded fine. The same applies to `getProgramAccounts`, where the RPC node performs the full (potentially indexed) program-account scan, computes filters, then discards the entire successfully-computed result set because of a single oversized match. This causes legitimate clients to receive spurious `InvalidRequest` errors instead of the correct account data for the well-formed portion of their batch — a wrong/misreported query result caused entirely by a benign, attacker-uncontrolled data property of one unrelated account.

### Likelihood Explanation
Triggering this requires only a single, standard JSON-RPC call from any unprivileged client against a public/API RPC endpoint; no special role or multiple calls are needed. Because base58 has a documented, well known 128-byte ceiling, and callers frequently batch pubkeys of varying account types/sizes, this can be hit accidentally by normal clients (not just adversarially), making it a realistic and reproducible correctness issue.

### Recommendation
In `get_multiple_accounts` and `get_program_accounts`, avoid using `?`/`collect::<Result<Vec<_>>>()` to propagate a single account's encoding error to the whole batch. Instead, mirror the graceful degradation already used by `encode_ui_account`/`encode_bs58` for account subscriptions: substitute an inline error string (or `null`) for the offending account's `data` field and continue encoding the remaining accounts, so one oversized account cannot suppress valid results for the rest of the batch.

### Proof of Concept
1. Create/observe two accounts: `A` (small, e.g. empty data) and `B` (data length > `MAX_BASE58_BYTES` = 128 bytes), as in `test_rpc_get_multiple_accounts` / `test_encode_account_throws_when_data_too_large_to_base58_encode`: [6](#0-5) 
2. Call `getMultipleAccounts` with `[A, B]` and `{"encoding": "base58"}` (or `"binary"`).
3. Observe the RPC call returns an `InvalidRequest` error for the entire call (per `encode_account`'s early return at rpc.rs:2591-2595) instead of returning `A`'s data and an in-band error/placeholder for `B`, even though `A` alone would have succeeded (as shown by the existing base58 test case at rpc.rs:5864-5896 which only passes because none of its accounts exceed the limit).

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}

fn encode_bs58<T: ReadableAccount>(
    account: &T,
    data_slice_config: Option<UiDataSliceConfig>,
) -> String {
    let slice = slice_data(account.data(), data_slice_config);
    if slice.len() <= MAX_BASE58_BYTES {
