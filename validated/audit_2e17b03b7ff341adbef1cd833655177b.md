### Title
Unkeyed callback map allows cross-user response overwrite in `HandleLegacyUserMessage` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores the caller's callback in `h.savedCallbacks` keyed solely by `msg.Body.MessageId`, with no binding to the message sender/requester and no check for an existing entry before overwriting it. A concurrent (or timed) submission using the same `MessageId` from a different caller silently replaces the first caller's stored callback, so the DON's eventual `web_api_trigger` response for that ID is delivered to whichever callback occupies the slot at the time `handleWebAPITriggerMessage` looks it up — not necessarily the original requester's.

Note: the question cites `core/web/api.go`, but no such handler exists there; the actual reachable code implementing this pattern is `handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go`.

### Finding Description
The relevant write path is: [1](#0-0) 

This assigns `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` unconditionally under `h.mu`, with no `if _, exists := ...; exists` guard and no check that the new caller matches the sender that originally reserved that ID.

The read/consume path is: [2](#0-1) 

`handleWebAPITriggerMessage` looks up and deletes by `msg.Body.MessageId` alone and forwards the response to whatever `savedCallback` is present — there is no verification that the response corresponds to the same requester who registered the callback.

The `savedCallback` struct itself carries only an `id` and `createdAt`, with no sender/requester identity field: [3](#0-2) 

So the only thing preventing cross-user delivery is uniqueness of `MessageId` across concurrently in-flight requests for the same DON. Nothing in this file enforces that uniqueness across different senders, nor does it bind the stored callback to `msg.Body.Sender`/caller identity for later verification when the response comes back.

### Impact Explanation
If an attacker can cause (or race into) a `MessageId` collision with a victim's concurrently in-flight legacy web-API-trigger request to the same DON, the attacker's callback overwrites the victim's in `h.savedCallbacks`. When the DON node responds, `handleWebAPITriggerMessage` delivers that response — potentially containing data intended for the victim — to the attacker's callback (cross-user response confusion), and the victim's own request either never resolves or times out. This matches the "cross-user response confusion" impact class called out in the prompt.

### Likelihood Explanation
Exploitability is fully contingent on how `MessageId` is generated/supplied for legacy user messages — this determines whether an unprivileged attacker can actually predict or force a collision with a genuine victim's ID. I was not able to fully trace, within the available tool budget, the exact code path that constructs `msg.Body.MessageId` for inbound legacy HTTP/gateway requests (i.e., whether it is a server-generated random/hash value bound to the sender/signature, or a caller-suppliable field akin to a JSON-RPC `id`). The map/overwrite logic itself (missing existence check, no sender binding) is confirmed and is a structural weakness regardless of ID provenance, but without confirming that `MessageId` is attacker-controllable or crash-guessable across different senders, I cannot confirm this rises to a reproducible, credential-free exploit as strictly required by the rules ("exact file/function support and a reproducible ... PoC").

### Recommendation
- Bind each `savedCallback` to the identity of the request sender (e.g., store and later verify `msg.Body.Sender`/DON member or a per-request nonce/signature reference) rather than trusting `MessageId` alone.
- Reject (rather than silently overwrite) `HandleLegacyUserMessage` calls whose `MessageId` already has an active entry in `h.savedCallbacks`, returning an error to the caller instead of clobbering the existing callback.
- If `MessageId` is derived from caller-supplied input, ensure it is generated/validated server-side (e.g., cryptographically random or a hash including the sender's authenticated identity) so it cannot be reused/guessed across different callers.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
