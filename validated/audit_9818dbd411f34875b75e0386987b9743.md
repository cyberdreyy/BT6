### Title
Cross-user response hijacking via colliding client-controlled `MessageId` in gateway's legacy WebAPI handler - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The Gateway's `capabilities` handler tracks in-flight user requests in a single map keyed only by the client-supplied `MessageId`, with no uniqueness enforcement across concurrent requests from different senders. An unprivileged client can choose an arbitrary `MessageId` (subject only to length/charset checks) and overwrite another user's pending callback entry, causing the DON's eventual response to be delivered to the wrong (attacker-controlled) callback instead of the legitimate requester.

### Finding Description
`HandleLegacyUserMessage` stores the user's callback in a process-wide map keyed solely by `msg.Body.MessageId`: [1](#0-0) 

`MessageId` originates entirely from client input and is only checked for length/suffix constraints, not uniqueness or ownership: [2](#0-1) 

Although the message is signed, the signature only proves who sent it — it does not prevent a different unprivileged sender from independently choosing the same `MessageId` string while a first request is still pending. When the DON's response later arrives, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageId`, with no verification that the responding request matches the original sender/session: [3](#0-2) 

If a second (malicious) client submits a request using the same `MessageId` as a still-pending legitimate request, `h.savedCallbacks[msg.Body.MessageId]` is silently overwritten with the attacker's callback (map write at line 412). The original caller's callback reference is lost, and when the DON node's trigger response comes back for that `MessageId`, it is delivered to the attacker's callback rather than the original user's — analogous to the reported "implicit constraint" (here: implicit assumption of `MessageId` uniqueness/ownership per in-flight request) not being enforced in code, leading to cross-user response confusion instead of relying purely on well-behaved front-ends.

### Impact Explanation
This breaks the request/response isolation the gateway relies on: a legitimate user's trigger response (potentially containing sensitive workflow output) can be redirected to an unrelated, unprivileged attacker who simply races a request with a guessed or observed `MessageId`. The legitimate caller instead receives no response (or a stale/incorrect one), and the callback bookkeeping (`h.mu`/`savedCallbacks`) becomes desynchronized, undermining protocol correctness for the WebAPI trigger path exposed to external clients.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to know or guess a victim's `MessageId` and race a request to the same DON before the legitimate response arrives. `MessageId` values chosen by well-behaved front-ends (e.g., UUIDs) would make guessing hard, but nothing in the code enforces uniqueness/session binding — the code fully relies on client-side convention (comparable to the Ladle relying on front-end recipe conventions rather than in-protocol invariants), so any deviation by a new/careless/malicious integrator directly triggers the bug. In shared/observable contexts (e.g., predictable IDs, or an attacker who can observe the DON's node-to-gateway traffic timing patterns) the race is feasible.

### Recommendation
Enforce uniqueness/ownership of in-flight `MessageId`s explicitly in code rather than relying on client convention:
- Reject new `HandleLegacyUserMessage` calls whose `MessageId` already exists in `savedCallbacks` (return an error instead of silently overwriting).
- Key the callback map by a tuple of `(Sender, MessageId)` or bind the callback to the authenticated sender so a response can only be routed to the callback registered by the same sender.
- Consider generating/validating `MessageId` uniqueness server-side rather than trusting client input entirely.

### Proof of Concept
1. User A sends a `web_api_trigger` request through the gateway with `MessageId = "X"`, which is validated and stored: `h.savedCallbacks["X"] = callbackA` (`handler.go:412`).
2. Before the DON responds, attacker B sends their own signed request also using `MessageId = "X"`. Validation only checks length/format (`message.go:61-66`), not uniqueness, so it succeeds and overwrites the map entry: `h.savedCallbacks["X"] = callbackB`.
3. When the DON node responds for `MessageId = "X"` (e.g., replying to A's original trigger), `handleWebAPITriggerMessage` looks up `h.savedCallbacks["X"]`, now pointing to `callbackB`, and delivers the response to attacker B (`handler.go:150-159`).
4. User A's callback is lost; the legitimate response is exfiltrated to/consumed by an unrelated unprivileged actor.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
