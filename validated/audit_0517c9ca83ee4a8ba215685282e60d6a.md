Based on my investigation, I found a valid analog vulnerability. The external report describes an unbounded, timeout-less network read (`stream.Recv()`) on a gRPC handler that lets a remote client hold a connection open indefinitely, exhausting server resources (file descriptors/goroutines). Searching GitLab Runner's own network-facing servers, I found the runner's gRPC servers (`helpers/runner_wrapper/api/server/server.go`, `steps/localserver/localserver.go`, `commands/steps/steps.go`) are all bound to local Unix domain sockets used for internal process IPC only — not reachable by an external network attacker, so they don't qualify. However, `session/server.go` implements a TCP+TLS `http.Server` that GitLab Runner exposes on the network (`session_server.listen_address` / `advertise_address` in `common/config.go`, wired up in `commands/multi.go`) for interactive web-terminal / port-forwarding sessions, and it never sets any read/write/idle timeouts.

### Title
Session Server DoS via unbounded connection hold (no HTTP timeouts) - (File: session/server.go)

### Summary
GitLab Runner's session server, used to proxy interactive terminal/service sessions to GitLab, listens on a network TCP socket with TLS but constructs its `http.Server` with zero configured timeouts, allowing a remote client to open many connections and hold them open indefinitely (slowloris-style), exhausting listener resources.

### Finding Description
`session.NewServer` creates `httpServer: &http.Server{}` with no `ReadTimeout`, `ReadHeaderTimeout`, `WriteTimeout`, or `IdleTimeout` set [1](#0-0) . It then wraps a plain TCP listener with TLS and hands it to `httpServer.Serve` [2](#0-1) [3](#0-2) . Because no header/read timeout is configured, a client that completes the TLS handshake and then sends data slowly (or not at all) can keep the connection — and the associated goroutine/file descriptor — open indefinitely. This is architecturally the same root cause as the disperser bug: a network-facing handler performs a blocking read (`stream.Recv()` there, HTTP header/body read here) without any deadline derived from the request context, so a malicious peer can pin server resources per connection. Enough concurrent connections can exhaust the process's file-descriptor limit, preventing legitimate session requests (and potentially other runner operations sharing the same process) from being served, mirroring the "hold the default max FD count and prevent responding to new API requests" impact described in the report.

### Impact Explanation
The session server's listen/advertise address is a runner-operator-configured, network-reachable endpoint intended to accept connections initiated by GitLab (for interactive web terminals and service port-forwarding), so it is a legitimate remote entry point, not an admin-opt-in insecure setting. An attacker able to reach this port can open a large number of slow/idle connections to exhaust file descriptors or goroutines in the runner process, causing a persistent denial of service against the session feature (and potentially the whole runner process, since it is a single Go binary).

### Likelihood Explanation
Likelihood is moderate-to-high wherever the session server is enabled and network-reachable: the attack requires no authentication bypass — merely completing (or partially completing) a TCP/TLS connection to the exposed port, which is the intended entry surface for this feature. No privileged access, trusted role, or non-default insecure configuration is required.

### Recommendation
Configure explicit timeouts on the `http.Server` in `session/server.go`, e.g. `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, and `IdleTimeout` (and/or wrap the listener with a connection-level deadline via `netutil.LimitListener` or a custom `net.Conn` deadline wrapper), so that a peer that doesn't complete its request within a bounded time is dropped, consistent with the recommendation in the external report to always bound blocking network reads with a context/deadline.

### Proof of Concept
1. Enable the runner's session server with a publicly reachable `listen_address`.
2. From an attacker-controlled host, open many concurrent TCP connections to the session server's port, complete the TLS handshake, and then send no further data (or send it byte-by-byte with long delays).
3. Because `http.Server{}` has no `ReadHeaderTimeout`/`ReadTimeout`, these connections remain open indefinitely, consuming goroutines and file descriptors until the process hits its FD limit, at which point new legitimate session connections (and potentially other runner network operations) fail. func NewServer(
	config ServerConfig,
	logger *logrus.Entry,
	certGen certificate.Generator,
	sessionFinder sessionFinderFn,
) (*Server, error) {
	if logger == nil {
		logger = logrus.NewEntry(logrus.StandardLogger())
	}

	server := Server{
		config:        config,
		log:           logger,
		sessionFinder: sessionFinder,
		httpServer:    &http.Server{},
	}

	host, err := server.getPublicHost()
	if err != nil {
		return nil, err
	}

	cert, publicKey, err := certGen.Generate(host)
	if err != nil {
		return nil, err
	}

	tlsConfig := tls.Config{
		Certificates: []tls.Certificate{cert},
		MinVersion:   tls.VersionTLS12,
	}

	err = server.setAdvertiseAddress()
	if err != nil {
		return nil, err
	}

	// We separate out the listener creation here so that we can return an error
	// if the provided address is invalid or there is some other listener error.
	listener, err := net.Listen("tcp", server.config.ListenAddress)
	if err != nil {
		return nil, err
	}

	server.tlsListener = tls.NewListener(listener, &tlsConfig)

	server.CertificatePublicKey = publicKey
	server.httpServer.Handler = http.HandlerFunc(server.handleSessionRequest)

	return &server, nil
}
