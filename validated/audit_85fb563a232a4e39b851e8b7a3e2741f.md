### Title
`BlockRejection::hash()` excludes `reason`/`reason_code`/`response_data` from the signed digest, allowing signature-preserving reason forgery - (`libsigner/src/v0/messages.rs`)

### Summary
`BlockRejection::hash()` binds only `signer_signature_hash` and `chain_id` into the structured-data digest that is signed and later re-derived by `verify()`/`recover_public_key()`. Every other field of the message — `reason`, `reason_code`, and the entire `response_data` (including `reject_reason` and `failed_txid`) — is unauthenticated, so any party who observes a genuine signed `BlockRejection` for a given block can splice a different `reason_code`/`response_data` onto the identical `signature` and have it verify successfully as coming from the original signer.

### Finding Description
The equality that must hold is: *the rejection reason a signer's signature authenticates == the rejection reason recipients act on*. This equality is broken because:

```rust
// libsigner/src/v0/messages.rs:1803-1807
pub fn hash(&self) -> Sha256Sum {
    let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
    let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
    structured_data_message_hash(data, domain_tuple)
}
``` [1](#0-0) 

`sign()`, `verify()`, and `recover_public_key()` all call this same `hash()`, so none of them ever look at `reason`, `reason_code`, or `response_data`: [2](#0-1) 

An unprivileged attacker who merely observes gossip/StackerDB traffic can therefore take any genuine `BlockRejection{signer_signature_hash: H, chain_id: C, signature: σ, reason_code: X, response_data: D}` signed by signer S, clone it, and produce `BlockRejection{signer_signature_hash: H, chain_id: C, signature: σ, reason_code: Y, response_data: D'}` for arbitrary `Y`/`D'`. `recover_public_key()`/`verify()` still succeed and recover S's real public key, because the check only re-derives `hash()` from `H` and `C`, both of which are untouched.

This is reachable by two real consumers:
1. `stacks-signer/src/v0/signer.rs::handle_block_rejection` authenticates the signature via `recover_public_key()` and `is_valid_signer()`, then feeds the forgeable `rejection.response_data.reject_reason` into signer-db storage and consensus-weight accounting: [3](#0-2) 
That weight is subsequently used to detect `RejectReasonPrefix::ReorgNotAllowed` and flip `SortitionMinerStatus::InvalidatedBeforeFirstBlock`: [4](#0-3) 
2. `stacks-node/src/nakamoto_node/stackerdb_listener.rs` verifies only the recovered pubkey against the expected signer, then branches directly on the unauthenticated `rejected_data.reason_code` and `rejected_data.response_data.failed_txid` to accumulate per-txid "problematic transaction" weight: [5](#0-4) 

Existing guards (signature verification, `is_valid_signer` address check, chain-id domain separation) all rely on `hash()`, and `hash()` simply never covers the fields that downstream logic branches on. No node validation call, chainstate reorg rule, or signerdb key check compensates for this, since the forgery happens entirely inside the signer/message layer before those checks run.

### Impact Explanation
This breaks a liveness-relevant equality: the recipient's decision (retry-vs-abandon, "mark miner invalid due to reorg", "flag txid as problematic") can be driven by a fabricated `reason_code`/`reject_reason` that rides on a real signer's real signature for a real block hash. Concretely:
- The `ReorgNotAllowed` weight aggregation (`stacks-signer/src/v0/signer.rs:2354-2367`) can be poisoned so that genuine-but-differently-reasoned rejections (e.g. `ConnectivityIssues`, `NoSortitionView`) are relabeled as `ReorgNotAllowed`, accumulating illegitimate weight toward the 30% threshold and marking a miner's sortition `InvalidatedBeforeFirstBlock` — a liveness wedge against a legitimate miner/tenure that neither requires nor implies majority-signer compromise.
- `stackerdb_listener.rs`'s problematic-transaction weight tracking can be fed forged `reason_code`/`failed_txid` pairs, corrupting miner-side transaction exclusion bookkeeping with attributions signers never made.

This matches the "High — signer/miner wedged into liveness failure via forged, signature-riding rejection metadata" category; it is not by itself a chain-safety break (no invalid block gets signed), but it lets an attacker with only one signer/miner slot and gossip access falsify the *cause* attributed to a real signature.

### Likelihood Explanation
- Preconditions: attacker needs to observe at least one genuinely signed `BlockRejection` for the target `signer_signature_hash`/`chain_id` — trivially available since these messages are gossiped/posted to StackerDB and readable by any participant, including unprivileged observers.
- Attacker cost: one signer/miner slot plus the ability to relay a modified message (splice `signature` field verbatim onto a new struct) — no private key, no auth_token, no majority weight required.
- Repeatability: the forged message can be reissued for every genuine rejection the attacker observes, and is reusable across any consumer that trusts `recover_public_key()`/`verify()` as authenticating the whole message rather than just `signer_signature_hash`+`chain_id`.
- Feasibility is high and directly demonstrable with a unit test against `BlockRejection`.

### Recommendation
Include all security-relevant fields (`reason_code`, and ideally the full `response_data`, or at minimum `reject_reason`/`failed_txid`) in the structured-data digest computed by `BlockRejection::hash()`, so that `sign()`/`verify()`/`recover_public_key()` authenticate the complete semantic content of the rejection, not just the block hash and chain id. Bump the structured-data version string used in `make_structured_data_domain` (`"block-rejection", "1.0.0"`) to force a clean cutover and reject old-format-only messages if backward compatibility is a concern.

### Proof of Concept
```rust
// libsigner/src/v0/messages.rs (test module)
#[test]
fn reason_code_is_not_authenticated_by_signature() {
    let sk = StacksPrivateKey::random();
    let pk = StacksPublicKey::from_private(&sk);
    let hash = Sha512Trunc256Sum([0x11; 32]);

    let genuine = BlockRejection::new(
        hash,
        RejectReason::ValidationFailed(ValidateRejectCode::InvalidBlock),
        &sk,
        false,
        0,
        0,
    );
    assert!(genuine.verify(&pk).unwrap());
    assert_eq!(genuine.recover_public_key().unwrap(), pk);

    // Attacker splices the same signature onto a forged reason_code /
    // response_data, without touching signer_signature_hash or chain_id.
    let mut forged = genuine.clone();
    forged.reason = "connectivity issue".to_string();
    forged.reason_code = RejectCode::ConnectivityIssues("forged".to_string());
    forged.response_data = BlockResponseData::new(
        u64::MAX,
        RejectReason::ConnectivityIssues("forged".to_string()),
        u64::MAX,
        None,
    );

    // Equality broken: signature still verifies and recovers the same
    // signer key even though the acted-upon reason_code differs from
    // what the signer actually signed.
    assert!(forged.verify(&pk).unwrap());
    assert_eq!(forged.recover_public_key().unwrap(), pk);
    assert_ne!(forged.reason_code, genuine.reason_code);
}
```
This demonstrates that `.verify()`/`.recover_public_key()` cannot distinguish the genuine reason from the forged one, confirming the vulnerability described.

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
