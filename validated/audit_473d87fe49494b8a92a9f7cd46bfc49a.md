## Title
Permissionless `init_global_fee_state` lets an attacker front-run deployment and become the global fee admin - (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
The instruction that creates the program-wide `FeeState` singleton PDA takes an attacker/caller-supplied `admin_key` argument and writes it directly into `global_fee_admin` with no check that the caller (`payer`) is any privileged or pre-configured deployer key.

### Finding Description
`initialize_fee_state` (wired as `marginfi::init_global_fee_state` in `programs/marginfi/src/lib.rs`) is invoked against `InitFeeState`: [1](#0-0) 

The `payer` account is a bare `Signer` with no ownership/allow-list constraint, and `fee_state` is a PDA derived purely from the constant seed `FEE_STATE_SEED` (no group or authority key mixed in), so it is a single, program-wide account that can only be initialized once via Anchor's `init` constraint: [2](#0-1) 

Inside the handler, `admin_key` — an arbitrary argument fully controlled by whoever calls the instruction — is written straight into `fee_state.global_fee_admin`, along with `fee_wallet` and every fee parameter: [3](#0-2) 

This is the same bug class as the CNote `_setAccountantContract()` finding: a function meant to be called once, immediately after deployment, to set a privileged global role, but with no access-control guard, so whoever gets their transaction landed first (e.g., by monitoring the mempool/network and front-running the legitimate deploy script) becomes the permanent `global_fee_admin` for the entire protocol. Because `fee_state` is a PDA with a fixed seed and Anchor's `init` fails if the account already exists, there is no way to retry or fix this after the fact — the only remedy is a program redeploy with a new program ID (a fresh PDA address).

Once an attacker controls `global_fee_admin`, they gain sole authority to call `edit_global_fee_state`, which is explicitly documented as "(global fee admin only)" and allows changing the fee wallet, all fee parameters, and even reassigning the admin itself: [4](#0-3) 

Every `MarginfiGroup` created afterward caches its fee configuration (including `global_fee_wallet`) from this `FeeState` at group-init time: [5](#0-4) 

so a hijacked `FeeState` directly redirects protocol-wide origination/liquidation/program fees to an attacker-chosen wallet across every group and bank in the deployment.

### Impact Explanation
If an attacker's transaction lands before the legitimate one-time `init_global_fee_state` call, the attacker becomes `global_fee_admin` for the entire protocol permanently (the PDA can't be re-initialized). From there they control `global_fee_wallet` and all program fee rates protocol-wide via `edit_global_fee_state`, redirecting fee revenue and manipulating fee parameters across every marginfi group. As with the original CNote finding, the practical worst case is a costly redeploy under a new program ID, since the PDA cannot be reset.

### Likelihood Explanation
This requires winning a race against the deployer's own initialization transaction (front-running via mempool observation, e.g., on network paths where transactions are publicly visible before confirmation, or simply being faster). It is a one-time, narrow window immediately after program deployment/upgrade, so likelihood is limited to that operational window, matching the Medium-severity judgment applied to the original CNote report.

### Recommendation
Constrain `InitFeeState::payer` to a known, hardcoded upgrade authority or multisig (e.g., require `payer.key() == crate::ID` program upgrade authority, or check against a hardcoded pubkey/allow-list) instead of accepting any signer. Alternatively, remove the caller-supplied `admin_key` argument and always set `global_fee_admin = payer.key()` combined with the authority check, so at minimum the deployer identity is enforced rather than an arbitrary parameter.

### Proof of Concept
1. Program is deployed; the `FeeState` PDA (seeds `[FEE_STATE_SEED]`) does not yet exist.
2. Attacker observes the deployment (e.g., watches for the program's on-chain presence or mempool activity) and submits their own `init_global_fee_state` transaction with `admin_key = attacker_pubkey`, `fee_wallet = attacker_wallet`, before the legitimate operator's transaction lands.
3. Anchor's `init` constraint on `fee_state` succeeds for whichever transaction confirms first; the attacker's call succeeds, setting `fee_state.global_fee_admin = attacker_pubkey`.
4. The legitimate operator's subsequent `init_global_fee_state` call fails (`account already in use`).
5. Attacker now calls `edit_global_fee_state` (guarded only by `global_fee_admin`) to redirect `fee_wallet` and manipulate fee parameters for every group created against this `FeeState`.

pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
