### Title
Vault withdrawal limit reached by other users makes `stopEpoch` revert, temporarily freezing epoch settlement - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary

`ProgrammableBorrower.onStopEpoch` withdraws the liquidity shortfall from the external ERC4626 vault inside a `try/catch` that reverts with `StopEpochVaultLiquidityUnavailable` whenever `vault.withdraw` fails, even though the position economically covers the shortfall. An unprivileged user of that vault can drain its available liquidity (or hit its per-period/per-tx withdrawal limit), which makes `IdleCDOEpochVariant.stopEpoch` revert and prevents epoch settlement for all lenders until liquidity returns.

### Finding Description

In `ProgrammableBorrower.onStopEpoch`, when `IdleCDO` requests `_amountRequired` at epoch stop, the contract checks: [1](#0-0) 

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

The guard at line 245 (`shortfall > _currentVaultAssets()`) only tolerates the case where the vault position cannot economically cover the withdrawal (handled as a default downstream). If the position *does* cover the shortfall but the vault's *available* liquidity or withdrawal cap is exhausted — because other vault users withdrew first — `vault.withdraw` reverts, the catch converts it into `StopEpochVaultLiquidityUnavailable`, and the whole `stopEpoch` call fails.

This mirrors the reported bug class: a withdrawal-limit check triggered by *other users'* withdrawals reverts an unrelated internal flow (epoch settlement / liquidity recall), rather than being scoped to the flow that should actually be limited. The same pattern exists in `_borrow` (line 452), but `borrow` is borrower/executor-only so it is not attacker-reachable; `onStopEpoch` is reachable because the attacker only needs to be an ordinary depositor of the shared ERC4626 vault — an explicitly allowed attacker class.

Sequence (running epoch, programmable mode):

1. Epoch is active; `ProgrammableBorrower` holds most funds as vault shares, `onHand < _amountRequired`.
2. Attacker (a vault user) withdraws/redeems from the vault, leaving `vault.maxWithdraw(address(this)) < shortfall` (liquidity drained or rate-limited).
3. Manager calls `cdoEpoch.stopEpoch(...)` → `onStopEpoch` → `vault.withdraw(shortfall)` reverts → `StopEpochVaultLiquidityUnavailable` propagates → epoch stays running.
4. Repeat at every retry while liquidity is unavailable. The emergency escape `emergencyExitVault` calls `vault.redeem`, which is subject to the same vault-side liquidity constraint, so it does not reliably unblock the flow.

### Impact Explanation

Temporary freezing of all lender funds in the pool: while `stopEpoch` reverts, no withdrawals can be settled, `requestWithdraw` receipts cannot become claimable, and the buffer/start of the next epoch cannot proceed. Funds parked in the vault remain locked to the pool even though the vault position nominally covers them. The freeze lasts until vault liquidity is replenished or the manager can unwind via `emergencyExitVault`/`rescueTokens` — i.e., duration is controlled by third-party vault liquidity the attacker can keep draining with capital proportional to vault TVL, not pool TVL.

### Likelihood Explanation

Low-to-medium. It requires a programmable-borrower deployment whose vault has other withdrawers and temporarily insufficient free liquidity (or a withdrawal cap below `shortfall`). No malicious privileged role is needed — only a normal ERC4626 vault user — and the attack costs only liquidity timing. However, honest manager/owner can eventually unwind the position, making the freeze temporary rather than permanent.

### Recommendation

Do not let a covered-but-unavailable vault withdrawal hard-revert `onStopEpoch`. Options: attempt a `redeem` capped at `vault.maxRedeem(address(this))` / withdraw up to `vault.maxWithdraw(address(this))` instead of reverting, returning a status so `IdleCDO` can treat the residual shortfall through the existing default path; or pre-check `maxWithdraw` and let `stopEpoch` handle a partial pull gracefully. If a full pull is required, document that `stopEpoch` is retryable and add a monitored fallback path that does not depend on `vault.redeem` succeeding for the whole amount in one call.
