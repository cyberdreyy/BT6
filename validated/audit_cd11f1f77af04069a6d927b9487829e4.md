### Title
Unauthenticated/unprivileged cache exhaustion in `RequestCache.NewRequest` causes availability DoS for other gateway users - (File: core/services/gateway/handlers/common/requestcache.go)

### Summary
`requestCache[T].NewRequest` enforces only a single global `maxCacheSize` bound with no per-sender quota, keying entries by `(sender, MessageId)` [1](#0-0) . Any caller able to submit distinct `sender`/`MessageId` pairs (e.g. an attacker generating fresh keypairs and unique message IDs) can fill the cache to `maxCacheSize`, after which legitimate requests from other users fail with `"request cache is full"`.

### Finding Description
`NewRequest` computes `key := globalId{request.Body.Sender, request.Body.MessageId}` and only checks total cache occupancy (`len(c.cache) >= int(c.maxCacheSize)`) before inserting a new entry [1](#0-0) . There is no per-sender counter or quota anywhere in this type.

The reachable path is `capabilities.handler.HandleLegacyUserMessage`, which explicitly documents the gap: `// TODO: apply allowlist and rate-limiting here` immediately before dispatching the message [2](#0-1) . The only checks performed before the request is admitted are payload decoding, timestamp staleness, and method name — none of which limit distinct senders or rate. Message signature validation (`Message.Validate`/`ExtractSigner`) only proves that `Sender` corresponds to whoever signed the message [3](#0-2) ; it does not restrict who may sign, since an attacker can generate unlimited ECDSA keypairs to produce unlimited distinct `Sender` values, and can freely choose distinct `MessageId` values per `Message.Validate` (any non-empty, bounded-length string). Thus an attacker fully controls both fields of the `globalId` key, defeating the "already exists" de-dup check and allowing `maxCacheSize` distinct insertions.

Note: I could not locate the specific call site(s) that construct the `RequestCache` instance backing `HandleLegacyUserMessage`/`NewRequestCache` invocations, nor the configured `maxCacheSize` value, within the indexed contents available to me — this is a limitation of the current search rather than evidence the path doesn't exist, since `requestcache.go` is a generic reusable component and the capabilities handler's `HandleLegacyUserMessage` is a known consumer of the `common` package (`common.ValidatedRequestFromMessage`) [4](#0-3) .

### Impact Explanation
This is a resource-exhaustion/availability issue: once the shared cache reaches `maxCacheSize`, all subsequent legitimate `NewRequest` calls — regardless of sender — fail with `"request cache is full"` [5](#0-4) , denying service to other tenants/users of the gateway. This matches a "Denial of Service" bounty impact class (temporary disruption of gateway request processing for other users), not a fund-loss or key-disclosure issue.

### Likelihood Explanation
Feasibility is high given the explicit TODO acknowledging missing allowlist/rate-limiting in `HandleLegacyUserMessage` [6](#0-5) . An attacker only needs the ability to generate ECDSA keys (free/unlimited) and sign well-formed messages with unique `MessageId`s — no privileged credentials required. The attack is repeatable and cheap, bounded only by `maxCacheSize` and the per-entry `timeout`, meaning the attacker must sustain roughly `maxCacheSize` outstanding (unanswered/never-responded) entries to keep the cache full, refreshing them as they time out.

### Recommendation
Add a per-sender quota/limit inside `requestCache[T]` (e.g., a `map[sender]int` counter checked/incremented alongside the global size check in `NewRequest`), and/or implement the allowlist/rate-limiting noted in the `HandleLegacyUserMessage` TODO before requests reach `NewRequest`.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/common/requestcache_test.go`:
1. Construct `NewRequestCache[T](timeout, maxCacheSize)` with a small `maxCacheSize` (e.g., 5).
2. Loop `maxCacheSize` times, calling `NewRequest` with distinct `Sender` values (e.g. `"attacker0"`..`"attacker4"`) and distinct `MessageId`s, asserting each call returns `nil` error.
3. Call `NewRequest` once more with `Sender: "victim"` and a unique `MessageId`, and assert it returns `error: "request cache is full"`.
4. This demonstrates the cache has no per-sender isolation and a single sender (or Sybil set of senders) can starve out unrelated victims.
