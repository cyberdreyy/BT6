### Title
Unauthorized lamport drain of `Uninitialized` `bpf_loader_upgradeable` accounts via missing signer/authority check in `Close` instruction - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The `UpgradeableLoaderInstruction::Close` handler in the BPF Loader Upgradeable builtin program checks authority/signer requirements for `Buffer` and `ProgramData` states via `common_close_account`, but the `UpgradeableLoaderState::Uninitialized` branch performs **no signer or authority verification at all** before transferring all lamports from the target account to an attacker-specified recipient. This mirrors the "Parity accidentally killed it" bug class: an account sitting in an un-owned/uninitialized intermediate state can be manipulated by an unrelated party because the code assumes "uninitialized" implies "nobody can be harmed," when in fact the account can already hold real, rent-paying lamports.

### Finding Description
In `process_loader_upgradeable_instruction`, the `Close` arm dispatches on the closed account's current state: [1](#0-0) 

For `Buffer` and `ProgramData`, the shared helper `common_close_account` enforces that a valid, signing authority matches the recorded `authority_address`: [2](#0-1) 

But for `UpgradeableLoaderState::Uninitialized`, the code only checks that the account being closed and the recipient are distinct instruction indices (`check_number_of_instruction_accounts(2)`), then unconditionally moves all lamports from the target account to whatever `recipient_account` (instruction account index 1) the attacker supplies — with no `is_instruction_account_signer` check and no ownership/authority binding whatsoever:

```rust
UpgradeableLoaderState::Uninitialized => {
    let mut recipient_account =
        instruction_context.try_borrow_instruction_account(1)?;
    recipient_account.checked_add_lamports(close_account.get_lamports())?;
    close_account.set_lamports(0)?;
    ic_logger_msg!(log_collector, "Closed Uninitialized {}", close_key);
}
```

An `Uninitialized` state is not a placeholder for "no account exists" — it is a concrete, on-chain state that any account owned by `bpf_loader_upgradeable` naturally has immediately after being created via `system_instruction::create_account` (data zero-initialized) and before `InitializeBuffer`/`InitializeUpgradeableLoader` runs, or after a previously-initialized `Buffer`/`ProgramData` account has itself already been closed once (its state is explicitly reset to `Uninitialized` by `common_close_account` at line 1026, while still existing on-chain and being reachable by future writes/lamport top-ups). Because the account's `is_writable` flag in a transaction is controlled purely by the *attacker's* message construction (Solana does not require an account to sign to be marked writable), any user can name a victim's pre-initialization buffer/program-data account as instruction account 0 in their own `Close` transaction and redirect its full lamport balance to themselves, without ever having been granted any authority over it. The unit test at `programs/bpf_loader/src/lib.rs:3811-3830` even demonstrates this path succeeding (`Ok(())`) while an authority account is present in the accounts list but is never actually validated by the code for this branch.

This is directly analogous to the Parity `WalletLibrary` bug: an object left in an un-owned/default state (`Uninitialized`) is treated by privileged operations (fund transfer) as safe to act upon by anyone, because the authorization check that exists for the "initialized" states was omitted for the "uninitialized" one.

### Impact Explanation
Any lamports held in a `bpf_loader_upgradeable`-owned account that is currently `Uninitialized` (a normal, reachable window during buffer creation, or the residual state of any previously closed Buffer/ProgramData account) can be stolen by an arbitrary third party via a single permissionless instruction. This is a concrete unauthorized fund mutation reachable from an ordinary user's transaction against a builtin program.

### Likelihood Explanation
High reachability: `bpf_loader_upgradeable` is a builtin program invoked directly by user transactions; constructing the `Close` instruction with attacker-controlled account metas requires no special privilege, only knowledge of the target account's public key, which is visible on-chain/in the mempool as soon as the funding `create_account` transaction lands.

### Recommendation
Require the same authority/signer proof for closing `Uninitialized` accounts as for `Buffer`/`ProgramData`, or restrict the `Uninitialized` close path to callers who can prove control (e.g., require account 0 itself to be a signer, matching the pattern used when the system program reclaims rent from self-owned accounts) before transferring lamports.

### Proof of Concept
1. Victim: `system_instruction::create_account(payer, buffer_pubkey, rent_exempt_lamports, size_of_buffer(len), &bpf_loader_upgradeable::id())`, signed and submitted, but the follow-up `InitializeBuffer` instruction has not yet landed (e.g., sent in a separate transaction, or delayed/dropped).
2. Attacker observes `buffer_pubkey` on-chain with state `UpgradeableLoaderState::Uninitialized` and non-zero lamports.
3. Attacker submits `UpgradeableLoaderInstruction::Close` with instruction accounts `[buffer_pubkey (writable, non-signer), attacker_pubkey (writable, non-signer)]`.
4. Per `programs/bpf_loader/src/lib.rs:701-709`, the instruction succeeds unconditionally, moving all of `buffer_pubkey`'s lamports to `attacker_pubkey`, matching the test at `programs/bpf_loader/src/lib.rs:3811-3830`.

```rust
fn common_close_account(
    authority_address: &Option<Pubkey>,
    instruction_context: &InstructionContext,
    log_collector: &Option<Rc<RefCell<LogCollector>>>,
) -> Result<(), InstructionError> {
    if authority_address.is_none() {
        ic_logger_msg!(log_collector, "Account is immutable");
        return Err(InstructionError::Immutable);
    }
    if *authority_address != Some(*instruction_context.get_key_of_instruction_account(2)?) {
        ic_logger_msg!(log_collector, "Incorrect authority provided");
        return Err(InstructionError::IncorrectAuthority);
    }
    if !instruction_context.is_instruction_account_signer(2)? {
        ic_logger_msg!(log_collector, "Authority did not sign");
        return Err(InstructionError::MissingRequiredSignature);
    }

    let mut close_account = instruction_context.try_borrow_instruction_account(0)?;
    let mut recipient_account = instruction_context.try_borrow_instruction_account(1)?;

    recipient_account.checked_add_lamports(close_account.get_lamports())?;
    close_account.set_lamports(0)?;
    close_account.set_state(&UpgradeableLoaderState::Uninitialized)?;
    Ok(())
}
```
