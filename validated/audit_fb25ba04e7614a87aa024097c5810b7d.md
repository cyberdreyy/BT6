### Title
Lockup owner can supply an arbitrary `whitelist_account_id` to bypass NEAR Foundation staking-pool vetting - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` lets the caller pass an arbitrary `whitelist_account_id`, which is written into the deployed lockup contract's `staking_pool_whitelist_account_id` field instead of always using the foundation-configured whitelist. This breaks the custody binding the whitelist/lockup system is designed to guarantee: "staking pool contract and account have to be approved by the whitelisting contract to prevent tokens from being lost, locked, or stolen" [1](#0-0) .

### Finding Description
`LockupFactory` is initialized with a foundation-controlled `whitelist_account_id` [2](#0-1) , meant to be the single source of truth for which staking pools are safe to delegate to. However, the payable `create` method accepts an optional `whitelist_account_id: Option<ValidAccountId>` supplied by the unprivileged caller creating the lockup, and only falls back to the factory default if the caller does not provide one: [3](#0-2) 

This caller-supplied value is serialized directly into `LockupArgs.staking_pool_whitelist_account_id` and passed to the newly deployed lockup contract's `new` constructor [4](#0-3) . This is confirmed to be a supported, tested code path: `test_create_lockup_with_custom_whitelist_success` demonstrates a caller successfully creating a lockup with a self-chosen `custom_whitelist_account_id()` [5](#0-4) .

The lockup contract's own guarantee — that the owner can only delegate to staking pools that have been vetted by the NEAR Foundation whitelist — depends entirely on trusting whatever account is recorded in `staking_pool_whitelist_account_id` at init time; the lockup calls `is_whitelisted` on that configured account before allowing staking actions [6](#0-5) . Since the lockup owner (the same unprivileged party calling `create`) can point this field at an account they themselves control, they can deploy a fake "whitelist" contract that always returns `true` for `is_whitelisted`, and thereby delegate locked/unvested tokens to any staking pool of their choosing — including one designed to make funds permanently unrecoverable, defeating the entire point of the whitelist mechanism described in the whitelist README [7](#0-6) .

This is directly analogous to the FeeCollector report's core issue: a mechanism intended to enforce trust in one context (an approved whitelist / a vetted call path) is instead parameterized by attacker-controlled input, breaking the "an account trusted as a whitelist versus the code and arguments that trust was granted for" binding.

### Impact Explanation
This is a Critical-impact issue per the custody binding it breaks: it enables a wrongly whitelisted deployment/binding to be recorded — the lockup is initialized to trust an attacker-controlled whitelist rather than the foundation's whitelist. While the tokens in the lockup belong to the same owner who set the parameter (so this is not directly theft of a third party's funds by an unrelated attacker), it does subvert the documented safety guarantee that "the owner can not lose tokens or block contract operations by using methods under the staking section" [8](#0-7) . If the lockup includes a vesting schedule with a foundation termination clause, an owner routing locked/unvested tokens to a hostile "staking pool" (approved only via their own fake whitelist) can cause them to be irrecoverably lost or locked, undermining the foundation's ability to recover unvested tokens on termination — a frozen/lost-funds outcome for the party (the foundation/beneficiary structure) that relies on the whitelist binding.

### Likelihood Explanation
High likelihood of reachability: the vulnerable parameter is a normal, documented, and tested part of the public `create` API (not a hidden or edge-case flow) — `test_create_lockup_with_custom_whitelist_success` shows it is an intended, exercised code path [5](#0-4) . Any account with the `MIN_ATTACHED_BALANCE` deposit calling `create` can exploit this without any privileged role.

### Recommendation
Remove the ability for the caller to override `staking_pool_whitelist_account_id`; always use the factory's foundation-configured `whitelist_account_id`. If a legitimate use case exists for supporting alternate whitelists, restrict that override to be settable only by the foundation account, not by the lockup owner/creator.

### Proof of Concept
1. Attacker deploys a trivial "whitelist" contract exposing `is_whitelisted` that always returns `true`, and a matching malicious "staking pool" contract that never returns delegated funds.
2. Attacker calls `LockupFactory::create(owner_account_id, lockup_duration, ..., whitelist_account_id: Some(attacker_whitelist))` with the required `MIN_ATTACHED_BALANCE` [9](#0-8) .
3. The deployed lockup contract is initialized with `staking_pool_whitelist_account_id = attacker_whitelist` [10](#0-9) .
4. Owner calls the lockup's staking selection method, which checks `is_whitelisted` against `attacker_whitelist` (always true), and delegates locked/unvested NEAR to the attacker's malicious staking pool, which never returns the funds.

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )

# Whitelist contract for staking pools

The purpose of this contract is to maintain the whitelist of the staking pool contracts account IDs that are approved
by NEAR Foundation.

In order for the lockup contracts to be able delegate to a staking pool, the staking pool should faithfully implement the spec.
The staking pool should guarantee that the delegated tokens can not be lost or locked, such as the lockup contract should be
able to recover delegated tokens back to the lockup from a staking pool. In order to enforce this, only approved (whitelisted)
accounts of staking pool contracts can receive delegated tokens from lockup contracts.

If NEAR Foundation has to approve every single staking pool account it might lead to a bottleneck and centralization
To address this NEAR Foundation can whitelist the account IDs of staking pool factory contracts.

The whitelisted staking pool factory contract will be able to whitelist accounts of staking pool contracts.
A factory contract creates and initializes a staking pool contract in a secure and permissionless way.
This allows anyone on the network to be able to create a staking pool contract for themselves without needing approval from the NEAR
Foundation. This is important to maintain the decentralization of the decision making and network governance.

To be able to address mistakes, NEAR Foundation has the ability to remove staking pools and staking pool factories from the whitelists.
