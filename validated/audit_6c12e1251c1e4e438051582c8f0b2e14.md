### Title
Zip Slip Path Traversal in Legacy Zip Extractor — (File: `helpers/archives/zip_extract.go`)

### Summary
The external report's core defect pattern is: a public/reachable code path performs an unsafe operation with **no bounds/validation on an attacker-influenced value**, enabling silent value/asset extraction. The reachable analog in GitLab Runner is not financial, but structural: the legacy ZIP extraction path used for cache/artifact extraction writes files at **zip-entry-controlled paths with no confinement check against the intended extraction directory**, unlike the sibling `tarzstd` extractor, which explicitly enforces one.

### Finding Description
`archives.ExtractZipArchive` iterates over `zip.Reader.File` entries and calls `extractZipFile`, which in turn calls `os.MkdirAll(filepath.Dir(file.Name), 0o777)` and then `os.OpenFile(file.Name, ...)` / `os.Symlink(...)` **directly using the zip entry's raw `Name` field**, with no `filepath.Join` against a destination root and no rejection of `..` traversal sequences: [1](#0-0) [2](#0-1) 

The wrapping `ziplegacy.extractor` even carries a `dir` field intended to scope extraction, but it is never used or passed to `archives.ExtractZipArchive`: [3](#0-2) 

Compare this to the `tarzstd` extractor, which is the properly-hardened sibling implementation: it resolves each entry against the destination directory and explicitly rejects any path that escapes the chroot: [4](#0-3) 

The `fastzip`-based extractor delegates path safety entirely to the third-party `fastzip` library rather than to in-repo code: [5](#0-4) 

This shows the codebase is clearly aware of the Zip Slip class of bug (it is fixed for tar/zstd) but the legacy zip code path lacks the equivalent guard. Both `commands/helpers/artifacts_downloader.go` and `commands/helpers/cache_extractor.go` call `archive.NewExtractor(format, f, size, wd)` (passing the working directory as the intended confinement root) for artifact and cache extraction: [6](#0-5) [7](#0-6) 

For the `Zip`/legacy-zip format, that `wd` argument is silently discarded by `ziplegacy.extractor.Extract`, so the confinement guarantee the callers assume does not actually exist for this format.

### Impact Explanation
If a malicious or corrupted ZIP archive is ever extracted through this legacy code path — e.g., a cache or artifact archive sourced from a compromised/misconfigured object storage bucket, a MITM'd download, or a cache poisoned by another (less trusted) job/branch sharing the same runner (a scenario GitLab's own docs already warn about for `GIT_STRATEGY: fetch` and shared runners) — entries with `../` sequences in their names can write or overwrite arbitrary files outside the job's working directory on the runner host. This can lead to overwriting other projects' build artifacts/cache, tampering with runner configuration, or planting files elsewhere on the host filesystem the runner process can write to — a persistent, host-level integrity/DoS impact rather than a one-off build failure.

### Likelihood Explanation
Exploitability depends on (a) the legacy zip extractor actually being selected instead of `fastzip` for a given extraction, and (b) an attacker having a path to influence the bytes of a cache/artifact zip that gets extracted (e.g., shared-runner cache poisoning, or a compromised/misconfigured storage backend serving cache/artifact content). I was not able to fully confirm, within the remaining investigation budget, the exact conditions/feature-flag under which `ziplegacy` is chosen over `fastzip` in `commands/helpers/archiver.go` — this is a gap in my verification and should be checked directly in that file before treating this as conclusively exploitable in a default configuration. If `ziplegacy` is only a rarely-used fallback (e.g., only reachable in edge/legacy configurations), likelihood is lower; if it is reachable by default under common conditions, likelihood is higher.

### Recommendation
Add the same path-confinement check used in `tarzstd_extractor.go` to `helpers/archives/zip_extract.go`: resolve each `file.Name` against the intended destination directory with `filepath.Join` + `filepath.Abs`, and reject any entry whose resolved path is not a descendant of that directory (also apply the same check to symlink targets, since `extractZipSymlinkEntry` writes arbitrary link targets without validation). Ensure `ziplegacy.extractor` actually passes and uses its `dir` field.

### Proof of Concept
Conceptual PoC (not executed): a ZIP file containing an entry named `../../../../tmp/evil` (or on Windows, a drive-qualified/absolute path) is passed through `archives.ExtractZipArchive`. Because `extractZipFile` uses `file.Name` verbatim in `os.MkdirAll(filepath.Dir(file.Name), ...)` and `os.OpenFile(file.Name, ...)`, the file is created at the traversed location rather than confined under the job's working directory, whereas the same crafted-traversal entry in a `tarzstd`-format archive would be rejected by the explicit chroot check in `tarzstd_extractor.go:62-64`.

func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}
