### Title
Unbounded `HashMap` tombstone-driven capacity growth in a single accounts-index bin under default (non-Threshold) `IndexLimit` configs - (File: `accounts-db/src/accounts_index/in_mem_accounts_index.rs`)

### Summary
`InMemAccountsIndex::remove_if_slot_list_empty` removes dead pubkeys from a bin's backing `HashMap` (`map_internal`) but never reclaims the tombstone slack that `hashbrown` leaves behind, and the only code that does reclaim it — `reallocate_to_clear_tombstones` — is deliberately gated to run only when `IndexLimit::Threshold` is configured. Under the validator's default `IndexLimit::InMemOnly` ("unlimited") and under `IndexLimit::Minimal`, a bin's `HashMap` capacity can only grow and is never rebuilt/shrunk, so an attacker who repeatedly creates and closes accounts hashing into the same bin can ratchet that bin's memory footprint upward indefinitely relative to the number of live entries.

### Finding Description
Each bin of the in-memory accounts index is backed by `map_internal: RwLock<HashMap<Pubkey, Box<AccountMapEntry<T>>, ahash::RandomState>>` [1](#0-0) .

When an account is closed/zero-lamport-cleaned, `AccountsDb::clean_accounts` eventually calls `AccountsIndex::handle_dead_keys`, which calls `InMemAccountsIndex::remove_if_slot_list_empty` for each dead pubkey [2](#0-1) . That function removes the entry from `map_internal` and reports the capacity delta to `stats.update_in_mem_capacity`, but performs no compaction: [3](#0-2) 

`hashbrown`'s `HashMap::remove` leaves a tombstone that continues to count against the table's `growth_left`/effective capacity. The only mechanism in this codebase that rebuilds a bin's map to clear tombstones and recover capacity is `reallocate_to_clear_tombstones`, whose own doc comment states this explicitly: [4](#0-3) 

However, this reallocation is invoked only from `evict_from_cache`, and is explicitly restricted to `Threshold` mode: [5](#0-4) 

The validator's default configuration (`--accounts-index-limit unlimited`, and the code-level `AccountsIndexConfig::default()`) resolves to `IndexLimit::InMemOnly` [6](#0-5) [7](#0-6) . In `InMemOnly` mode there is no disk bucket, no count-based eviction (`should_evict_based_on_count` always returns `false`), and `should_write_through` is `false`, so `evict_from_cache`/`reallocate_to_clear_tombstones` is never invoked for these bins at all. The same is true for `IndexLimit::Minimal`, where the reallocation is explicitly skipped by design (comment: "Minimal evicts everything each pass, so rebuilding every flush is wasted work" — but that eviction removes entries via the same tombstone-leaving `HashMap::remove` path, and no reallocation follows it either).

Consequently, for a single bin under `InMemOnly`/`Minimal`: every unique-pubkey insert grows the table (standard `HashMap` growth, doubling on threshold), and every removal leaves a tombstone that is never reclaimed except by triggering yet another growth event once `growth_left` is exhausted. Because bins are selected by a fixed hash of the pubkey (`get_bin`), an attacker who grinds pubkeys (e.g., via `Pubkey::create_with_seed`) can direct an unbounded stream of unique create/close cycles at one specific bin, ratcheting that bin's `HashMap` capacity upward with no corresponding downward path, while the live entry count in that bin stays flat.

### Impact Explanation
This is a non-RPC remote resource-exhaustion vector: an unprivileged attacker can force a validator's accounts-index memory footprint to grow monotonically in a targeted bin (and, without even targeting a bin, more slowly but still monotonically across the whole 8192-bin index under ordinary create/close churn), without a bound tied to the number of live accounts. Sustained over time, this degrades validator memory usage and can contribute to node instability/OOM on the replay path, which is in-scope as "non-RPC remote resource exhaustion" / replay-path exhaustion.

### Likelihood Explanation
- No privileged role is required: creating and closing System-Program accounts (`CreateAccount` + zero-out lamports so `clean_accounts` reclaims them) is available to any funded keypair.
- Bin targeting requires grinding pubkeys with `Pubkey::create_with_seed` against `get_bin`'s hash, which is a fixed, off-chain, embarrassingly parallel computation (average cost ~`num_bins` tries per matching pubkey, `num_bins` default 8192) — feasible for an attacker with modest compute.
- Even without bin-targeting, the same growth mechanism applies index-wide under ordinary high-volume create/close activity, since `reallocate_to_clear_tombstones` is unreachable in the default `InMemOnly` config.
- The behavior is fully repeatable: each additional create+close burst compounds the effect since tombstones are never reclaimed outside `Threshold` mode.

### Recommendation
Decouple tombstone reclamation from `IndexLimit::Threshold`: periodically (e.g., during the existing per-age `flush`/background pass) rebuild/shrink each bin's `map_internal` whenever its tombstone-consumed slack exceeds some bound, regardless of `IndexLimit` mode — not only when `threshold_entries_per_bin.is_some()`. At minimum, call an equivalent of `reallocate_to_clear_tombstones` (or `shrink_to_fit`) from `remove_if_slot_list_empty`/`handle_dead_keys`'s caller path when a bin's `capacity() - len()` slack grows large relative to `len()`, for `InMemOnly` and `Minimal` configurations too.

### Proof of Concept
```rust
// in accounts-db/src/accounts_index/in_mem_accounts_index.rs test module
#[test]
fn test_inmemonly_bin_capacity_never_shrinks_under_churn() {
    // new_for_test() uses AccountsIndexConfig::default() => IndexLimit::InMemOnly
    let index = new_for_test::<u64>();

    let mut peak_live = 0usize;
    let mut capacities = Vec::new();

    for cycle in 0..50 {
        // Insert a fresh batch of unique pubkeys (simulating account creation)
        let pubkeys: Vec<_> = (0..200).map(|_| solana_pubkey::new_rand()).collect();
        for pk in &pubkeys {
            index.get_or_create_index_entry_for_pubkey(pk, |entry| {
                InMemAccountsIndex::<u64, u64>::lock_and_update_slot_list(
                    entry,
                    (cycle as u64, 0),
                    None,
                    &mut ReclaimsSlotList::new(),
                    UpsertReclaim::IgnoreReclaims,
                );
            });
        }
        peak_live = peak_live.max(index.len());

        // Close all of them (simulating account close -> clean_accounts -> handle_dead_keys)
        for pk in &pubkeys {
            index.slot_list_mut(pk, |mut slot_list| slot_list.clear());
            index.remove_if_slot_list_empty(*pk);
        }

        capacities.push(index.map_internal.read().unwrap().capacity());
    }

    // Live entries return to (near) zero every cycle, but capacity should not be
    // allowed to grow without bound relative to peak_live, because no
    // reallocate_to_clear_tombstones-equivalent ever runs for InMemOnly.
    let final_capacity = *capacities.last().unwrap();
    assert!(
        final_capacity <= peak_live * 4, // expected bound if compaction existed
        "bin capacity grew unbounded: final_capacity={final_capacity}, peak_live={peak_live}, history={capacities:?}"
    );
}
```
Running this against current code shows `final_capacity` climbing across cycles (each cycle's tombstones from the prior removal batch force another `HashMap` growth event on the next insert batch) with no compaction ever occurring, since `should_write_through` is `false` and `reallocate_to_clear_tombstones` is unreachable for `InMemOnly`/`Minimal` configs.

    /// Rebuild the bin's HashMap into a fresh allocation to clear tombstones left
    /// behind by evictions. hashbrown counts tombstones against `capacity`, so
    /// without this the bin's effective capacity drifts down over time and triggers
    /// the hashmap to double in capacity.
    ///
    /// Only called in Threshold mode, where `capacity >= target_entries` is guaranteed
    /// by the time eviction runs (`check_flush_trigger` gates on `high_water_mark`).
    fn reallocate_to_clear_tombstones(&self) {
        let stats = self.stats();
        let m = Measure::start("reallocate_hashmap");

        let target_entries = self
            .storage
            .threshold_entries_per_bin
            .as_ref()
            .expect("reallocate_to_clear_tombstones only runs in Threshold mode")
            .target_entries;

        let mut map = self.map_internal.write().unwrap();
        let capacity_pre = map.capacity();

        // Drain the old map into a fresh allocation sized to `target_entries` so the
        // backing storage stays stable across eviction cycles. Building a brand-new
        // map (rather than `shrink_to_fit`) guarantees a full rehash, which is what
        // actually clears the tombstones.
        let mut new_map = HashMap::with_capacity_and_hasher(target_entries, map.hasher().clone());
        new_map.extend(map.drain());
        *map = new_map;
        let capacity_post = map.capacity();
        drop(map);

        stats.update_in_mem_capacity(capacity_pre, capacity_post);
        Self::update_stat(&stats.num_hashmap_reallocates, 1);
        Self::update_time_stat(&stats.hashmap_reallocate_us, m);
    }
