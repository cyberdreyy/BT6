### Title
Vote Account Withdraw Authority Can Front-Run Block-Revenue/Inflation Commission Changes via `UpdateCommissionBps` (No Timing Restriction) - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The vote-account commission mechanism introduced by SIMD-0291/SIMD-0249 (`UpdateCommissionBps`) removes the timing restriction that the legacy `UpdateCommission` instruction enforces, allowing the vote account's authorized withdrawer to change the inflation-rewards or block-revenue commission at any slot, with no delay. This is the same bug class as the MIMO `vaultOwner` front-running `setAutomation()` before `rebalance()`: a party who controls a shared, incentive-bearing account can reconfigure the fee/commission parameter immediately around an event that benefits other parties (stakers/delegators or reward callers), capturing more value for themselves at the counterparties' expense.

### Finding Description
The legacy commission-update path enforces a timing rule via `is_commission_update_allowed`, which restricts commission *increases* to the first half of an epoch: [1](#0-0) 

By contrast, the new basis-points commission update path explicitly removes this restriction, per the code comment "No commission update rule, per SIMD-0249 and SIMD-0291": [2](#0-1) 

This instruction only requires the vote account's `authorized_withdrawer` signature — no slot/epoch gate at all — and it applies to both `CommissionKind::InflationRewards` and `CommissionKind::BlockRevenue`: [3](#0-2) 

For the `InflationRewards` kind, the epoch-rewards distribution code does attempt to blunt this by preferring a commission snapshot from one epoch prior when `delay_commission_updates` is active: [4](#0-3) 

However, for the `BlockRevenue` commission kind (SIMD-0123 block-revenue sharing), no equivalent epoch-delay snapshot mechanism was found in the code I could trace: `calculate_block_reward` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:173-232`) reads `pending_delegator_rewards` directly from the current vote state, and fee distribution (`deposit_or_burn_fee` in `runtime/src/bank/fee_distribution.rs:117-180`) deposits 100% of the collected fee to the leader's `block_revenue_collector` without applying any commission split at that point. The actual split between validator and delegators for block revenue appears to happen via a separate `DepositDelegatorRewards` instruction (referenced in `programs/vote/src/vote_processor.rs`), whose exact interaction with `block_revenue_commission_bps` I was unable to fully trace within the available tool budget — this is a gap in my verification.

### Impact Explanation
Because `UpdateCommissionBps` has no timing/epoch restriction (unlike the legacy `UpdateCommission`), a vote account's withdraw authority can, in a single slot or adjacent slots, raise the commission immediately before a reward-relevant event and lower it back afterward, exactly mirroring the MIMO `vaultOwner`/`setAutomation()` pattern. For `InflationRewards`, the `delay_commission_updates` snapshotting reduces (but the analysis could not fully confirm eliminates) this risk. For `BlockRevenue` commission, since no equivalent delay was located, a malicious or opportunistic validator could set `block_revenue_commission_bps` to a high value immediately before depositing/crediting delegator rewards and revert it right after, capturing a larger share of block revenue than delegators were led to expect — an economic value-extraction issue analogous to the referenced finding.

### Likelihood Explanation
Likelihood is moderate: the action requires only the vote account's `authorized_withdrawer` key (not validator-identity/node-level compromise), is a normal permitted instruction, and can be executed once per relevant event without any cooldown, matching the "keeper hides tx / times the update" pattern from the source report. The severity is bounded by the fact this affects only the affected validator's own delegators' commission split, not consensus or funds outside the vote-account/stake ecosystem.

### Recommendation
Confirm whether `BlockRevenue` commission changes are protected by an equivalent epoch-delay/snapshot mechanism as `InflationRewards`; if not, apply the same `delay_commission_updates`-style snapshotting (or a minimum-delay/timelock) to `block_revenue_commission_bps` changes before they affect any pending delegator-reward distribution, consistent with the intent of SIMD-0249.

### Proof of Concept
1. Vote account withdraw authority observes that a `DepositDelegatorRewards` (or equivalent block-revenue distribution) transaction is about to execute for its vote account.
2. It submits `UpdateCommissionBps { commission_bps: <high value>, kind: CommissionKind::BlockRevenue }` — allowed unconditionally per `update_commission_bps` (`programs/vote/src/vote_state/mod.rs:827-859`), with no epoch/slot gating (contrast with `update_commission`'s `is_commission_update_allowed` check at lines 813-815).
3. The distribution transaction executes using the inflated commission, disproportionately crediting the validator instead of delegators.
4. The withdraw authority calls `UpdateCommissionBps` again to restore the original (lower) commission, since there is no cooldown preventing it.

*Note: step 3's exact mechanics for `BlockRevenue` commission application could not be fully confirmed from the code paths reviewed; this should be verified against the `DepositDelegatorRewards` instruction handler before treating this as conclusively exploitable.*

pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
