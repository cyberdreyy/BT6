### Title
Node-side signer weight tally double-counts a signer who switches from Rejected to Accepted, allowing a fully-signed block to be wedged as globally rejected - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The mining node's `StackerDBListener` tracks two independent weight aggregates per block — `total_weight_approved` and `total_weight_rejected` — that are supposed to reflect the *current, mutually-exclusive* verdict of each signer. The de-duplication guards for the two message kinds use two different sets (`gathered_signatures` for acceptances, `responded_signers` for rejections), so a signer who first rejects a block and later legitimately re-evaluates and signs the *same* block (an explicitly supported transition, `LocallyRejected → LocallyAccepted`) has its weight counted in **both** buckets simultaneously. This breaks the invariant `total_weight_approved + total_weight_rejected ≤ total_weight` that `signer_coordinator.rs` relies on to decide between accepting and abandoning a block proposal.

### Finding Description
`handle_signer_message` (the loop body inside `StackerDBListener`'s run loop) processes `BlockResponse::Accepted` and `BlockResponse::Rejected` messages for a given `block_sighash`:

- On `Accepted`, weight is added to `total_weight_approved` only when the slot isn't already in `block.gathered_signatures`: [1](#0-0) 

- On `Rejected`, weight is added to `total_weight_rejected` only when the slot isn't already in `block.responded_signers` (a guard shared with the accept path, since `Accepted` also inserts into `responded_signers`): [2](#0-1) 

The asymmetry: `Accepted` always inserts into `responded_signers` (line 465), so an accept-then-reject sequence is correctly guarded (the later reject is dropped because `responded_signers.insert` returns `false`). But `Accepted`'s own weight-add decision is keyed on `gathered_signatures`, not `responded_signers`. So for the reverse order — reject arrives first (adds weight to `total_weight_rejected`, inserts into `responded_signers`), then the *same* signer later signs the same block sighash (a documented, legal re-evaluation per `BlockInfo::check_state`, `LocallyRejected → LocallyAccepted`) — the accept path only checks `gathered_signatures` (empty), so it adds the signer's weight to `total_weight_approved` too, without ever removing it from `total_weight_rejected`.

The consumer of these aggregates, `signer_coordinator.rs`, uses them as if they were disjoint: [3](#0-2) 

Because a single signer's weight can now be counted in both `total_weight_rejected` and `total_weight_approved` at once, `total_weight_rejected` can be pushed past the blocking-minority threshold (`total_weight - weight_threshold`) purely from *stale* rejections that the signer has since retracted by actually signing. Since the rejection branch is checked first (`if ... total_weight_rejected ... > total_weight { return Err(SignersRejected) }`) the miner can abandon a block and return `NakamotoNodeError::SignersRejected` even though the block has since reached the genuine 70% signature weight required by `NakamotoBlockHeader::verify_signer_signatures`/`compute_voting_weight_threshold`: [4](#0-3) 

This is a break of the "aggregated-weight vs verified-accepts" equality: the coordinator's tally no longer matches the actual, current set of accepting/rejecting signers.

### Impact Explanation
This is a liveness wedge on the miner/coordinator side (in-scope per `signer_set`/`coordinator` node logic): a miner can be forced to prematurely abandon a well-formed, ultimately fully-signed block and give up the tenure slot, even though the real current signer weight satisfies the 70% signing threshold. No signer is tricked into signing anything invalid — the underlying `verify_signer_signatures` check still requires genuine, correctly-ordered signatures — but the coordinator's local bookkeeping of "have we been rejected" is corrupted by stale, superseded rejection votes that double-count a single signer's weight, causing valid block proposals to be wedged/dropped.

### Likelihood Explanation
This requires only a single signer (one already-authorized member of the signer set, not a majority) whose local state legitimately transitions from `LocallyRejected` to `LocallyAccepted` on the same block sighash — a transition explicitly modeled and permitted by the signer's own state machine (e.g., a signed-conflict that later goes stale, or a reject reason that becomes re-evaluable). This can happen during ordinary operation (timing/latency, resolved conflicts) without any signer acting maliciously, though it is also trivially triggerable by one Byzantine-but-authorized signer that intentionally rejects first and then signs.

### Recommendation
Make `total_weight_approved` and `total_weight_rejected` mutually exclusive per signer: use a single per-signer "current verdict" map (or clear the opposite bucket's weight) instead of two independently-guarded sets (`gathered_signatures` vs `responded_signers`). Concretely, when handling `Accepted`, check (and clear) any prior rejection weight/membership for that `slot_id` before adding to `total_weight_approved`, and vice versa for `Rejected`, so the invariant `total_weight_approved + total_weight_rejected ≤ total_weight` always holds.

### Proof of Concept
1. Node proposes block `B` with sighash `H` to the signer set.
2. Signer `S` (weight `w`) locally rejects `B` at time `t0` (e.g., due to a signed conflict at the same height that is still fresh) and broadcasts `BlockResponse::Rejected`. `stackerdb_listener` records `total_weight_rejected += w`, `responded_signers.insert(S)`.
3. The conflict later goes stale (per the documented `conflict_still_blocks`/freshness logic), and `S` re-evaluates the *same* block `B`/`H` and signs it, broadcasting `BlockResponse::Accepted`.
4. `stackerdb_listener`'s accept handler checks only `gathered_signatures.contains_key(S)` (false) and adds `total_weight_approved += w`, leaving `total_weight_rejected` unchanged (still including `w`).
5. If other signers' independent rejections (for unrelated, valid reasons — e.g., competing proposals, timeouts) push `total_weight_rejected` (now inflated by `S`'s stale weight) past `total_weight - weight_threshold`, `signer_coordinator.rs` returns `NakamotoNodeError::SignersRejected` and the miner discards `B`, even though `total_weight_approved` (including `S`) may already or shortly reach the genuine 70% signing threshold.
