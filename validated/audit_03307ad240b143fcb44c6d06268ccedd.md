### Title
Reorg-depth cap in `check_parent_tenure_choice` is a per-call limit, not cumulative — repeated single-block reorgs can unwind arbitrarily deep history - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` is meant to bound how much of the canonical chain a new tenure is allowed to reorg away: it permits reorging a prior tenure only if that tenure has at most one globally-accepted block (or was poorly timed). This mirrors the sNote bug class exactly — a "at most X per action" cap that is evaluated fresh on every single call with no memory of how much has already been unwound via previous, individually-sanctioned reorgs. A sequence of tenures, each individually reorging only "one block's worth" of the immediately preceding tenure, can cumulatively erase far more history than the single-block limit was designed to allow.

### Finding Description
The cap lives here: [1](#0-0) 

For each tenure being reorged, the function only checks that particular tenure's own globally-accepted block count (`globally_accepted_blocks > 1`) via `get_globally_accepted_block_count_in_tenure`. When the check passes, `record_superseded_tenure` is called and the tenure is marked superseded in the signer DB: [2](#0-1) 

This is stateless across sortitions: nothing tracks "how many tenures/blocks have already been sanctioned for removal in this fork's history." Each new tenure's `check_parent_tenure_choice` call only asks the node for the *current* span between `prior_sortition` and the newly-chosen `parent_tenure_id` (`get_tenure_forking_info`), and evaluates the ≤1-block rule tenure-by-tenure within that span. If a chain of single-block tenures is unwound one hop at a time across successive sortitions — each hop individually satisfying "the reorged tenure had ≤1 globally accepted block" — the signer set will sanction each hop in isolation, with no aggregate ceiling on how many blocks have been cumulatively invalidated by the sequence of sanctioned reorgs. This is structurally identical to the sNote bug: a percentage/count cap enforced per-invocation, bypassed by invoking the guarded action repeatedly.

### Impact Explanation
If exploitable, this breaks the equality the signer's reorg-timing rule is supposed to guarantee: "no tenure with more than one confirmed block may be silently orphaned." Instead, an attacker who can repeatedly win the miner slot (or otherwise chain several qualifying single-block tenures) could have signers progressively sanction reorgs that in total discard many blocks' worth of previously globally-accepted history, each individual step looking legitimate to the check. That is a safety violation on par with a signer signing/endorsing a non-canonical replacement chain it was specifically designed to refuse — a signer-set-approved-parent vs. truly-safe-parent equality violation.

### Likelihood Explanation
Likelihood is uncertain and I could not fully confirm it within the available context. Each hop requires the check to run for a *new* sortition/tenure, i.e., a new leader election win. A single winning slot can trigger one instance of `check_parent_tenure_choice`; chaining multiple sanctioned reorgs requires either winning several consecutive elections (bursty luck, not a majority-of-signers or key-compromise requirement, so arguably still in scope per the rules) or an adversarial sequence of one-block tenures set up in advance. I was not able to verify from the available code/tests whether `get_tenure_forking_info` always returns the *entire* span back to a fixed anchor (which would make the check inherently cumulative and safe) or only the span relative to the immediately preceding sortition (which would make it stateless and exploitable step-by-step). This distinction is central to whether the bug is real, and the index does not contain enough of `get_tenure_forking_info`'s node-side implementation to settle it with certainty.

### Recommendation
Track cumulative reorg depth/impact across a chain of sanctioned reorgs (e.g., persist a running count or a "not-to-exceed-N-blocks-since-last-confirmed-checkpoint" boundary in `SignerDb`), rather than re-deriving the single-block limit independently on every `check_parent_tenure_choice` call. Alternatively, confirm and document that `get_tenure_forking_info` always resolves the reorg against a fixed, non-superseded canonical anchor (not merely the previous sortition), which would make the existing per-call check already cumulative and this finding moot.

### Proof of Concept
Not independently reproducible from static review alone; the exploit path depends on the exact semantics of `get_tenure_forking_info`'s return span, which I could not fully verify in the indexed code. A background Devin session with full repository/test access would be needed to trace `get_tenure_forking_info` on the node side and construct a concrete multi-hop sequence of single-block tenures to confirm whether the cumulative bypass is reachable.
