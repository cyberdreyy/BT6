### Title
Mid-epoch withdraw requests are not reserved in `ProgrammableBorrower.epochPendingWithdraws`, letting the borrower draw liquidity owed to new receipts — ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
Analogous to the Zaros bug where the credit-capacity check runs before the withdrawal is accounted, `ProgrammableBorrower.availableToBorrow()` enforces solvency against a **stale snapshot** of pending withdrawals. `epochPendingWithdraws` is set only once in `onStartEpoch()` (`ProgrammableBorrower.sol:205`) and is never increased when users file new withdraw requests during a running epoch, even though `IdleCreditVault.requestWithdraw()` increments the live `pendingWithdraws` liability that `stopEpoch` must pull (`IdleCreditVault.sol:279`). The borrower's `_borrow` solvency check therefore does not account for liquidity reserved to withdrawals created after the check baseline was taken.

### Finding Description
- `onStartEpoch` snapshots `epochPendingWithdraws = _pendingWithdraws` once (`ProgrammableBorrower.sol:201-205`).
- `availableToBorrow()` returns `totalAssets - epochPendingWithdraws` (`ProgrammableBorrower.sol:350-355`), and `_borrow` enforces `assets <= borrowable` (`ProgrammableBorrower.sol:438-445`).
- `IdleCDOEpochVariant.requestWithdraw` can be invoked while an epoch is running — there is no epoch-phase gate, only the `allow*WithdrawRequest` flags and KYC (`IdleCDOEpochVariant.sol:739-791`). Each call routes to `IdleCreditVault.requestWithdraw`, which does `pendingWithdraws += _amount` (`IdleCreditVault.sol:279`) — but no callback updates `ProgrammableBorrower.epochPendingWithdraws`.
- At `stopEpoch`, the CDO pulls `_amountToPullFromBorrower + _pendingWithdraws` via `getFundsFromBorrower` / `onStopEpoch` (`IdleCDOEpochVariant.sol:398-408`). If the honest borrower drew funds that should have been reserved for mid-epoch receipts, `onStopEpoch` returns true only when the vault covers the shortfall; otherwise the `transferFrom` fails and `_handleBorrowerDefault` fires (`IdleCDOEpochVariant.sol:398-402`).

Broken invariant: the reserve-on-draw check does not reflect liabilities created after epoch start — the same "check before, not after, the debt is created" flaw class as the Zaros credit-capacity bug.

### Impact Explanation
A KYC'd tranche holder requests a withdrawal mid-epoch. The honest borrower (or an authorized executor calling `executeBorrow`, which still delivers funds to the borrower) can draw `availableToBorrow()`, which ignores the new receipt. At `stopEpoch` the pull fails by up to the unreserved amount, forcing `_handleBorrowerDefault`: the pool defaults, pending receipts are haircut through `defaultRecoveryPrice`, and active LPs absorb a realized loss via the default waterfall — a direct solvency/loss-socialization failure quantified by the unreserved withdrawal size (up to the full withdrawable tranche value).

### Likelihood Explanation
Requires a programmable-borrower deployment, an active epoch, withdraw requests enabled, and borrower demand — all normal operating conditions. No malicious privileged role is needed; the borrower acts honestly within the stale `borrowable` bound.

### Recommendation
Update `epochPendingWithdraws` on every new withdraw request (e.g., have `IdleCDOEpochVariant.requestWithdraw` push the delta to the borrower, or have `availableToBorrow()` read the live `pendingWithdraws` from `IdleCreditVault` via the CDO), so the borrow cap always reflects post-request liabilities.

### Proof of Concept
Foundry sketch (extend `test/foundry/IdleCreditVault.t.sol` programmable-borrower setup):

```solidity
function testMidEpochWithdrawNotReserved() external {
    // enable programmable borrower mode, deposit, start epoch
    idleCDO.depositAA(100_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0); // onStartEpoch snapshots epochPendingWithdraws = 0

    // attacker (KYC'd holder) requests withdrawal mid-epoch
    cdoEpoch.requestWithdraw(50_000 * ONE_SCALE, address(AAtranche));
    // pendingWithdraws == 50k but epochPendingWithdraws still 0
    assertEq(IdleCreditVault(address(strategy)).pendingWithdraws(), 50_000 * ONE_SCALE);
    assertEq(programmableBorrower.epochPendingWithdraws(), 0);

    // honest borrower draws full "available" amount, ignoring new receipt
    vm.prank(borrower);
    programmableBorrower.borrow(0); // draws ~100k, not capped at 50k

    // stopEpoch pull fails -> forced default
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _checkDefault(); // loss socialized to LPs / haircut on receipts
}
```

Uncertainty: this relies on `requestWithdraw` being callable during a running epoch and on `pendingWithdraws` being included in the stop-epoch pull for programmable deployments; both are indicated by the code and comments shown (`IdleCreditVault.sol:277-280`, `IdleCDOEpochVariant.sol:398-408`), but the absence of an explicit epoch-phase guard on `requestWithdraw` and the exact `_amountToPullFromBorrower` composition were not fully re-verified line-by-line.
