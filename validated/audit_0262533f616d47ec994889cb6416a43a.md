### Title
External initiator credentials satisfy `GetAuthenticatedUser` checks, bypassing "EIs not allowed" restriction on `PipelineRunsController.Create` - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` always calls `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` in addition to `c.Set(SessionExternalInitiatorKey, ei)`, so any handler that merely checks "is a User present" via `auth.GetAuthenticatedUser` cannot distinguish an external initiator from a real user. `PipelineRunsController.Create` explicitly relies on this distinction ("only users are allowed to run jobs using int IDs - EIs not allowed") but only checks `_, isUser := auth.GetAuthenticatedUser(c)`, which is also true for EIs, defeating the intended restriction.

### Finding Description
`AuthenticateExternalInitiator` (core/web/auth/auth.go:119-151) sets both `SessionExternalInitiatorKey` and `SessionUserKey` on every successful EI authentication: [1](#0-0) 

`GetAuthenticatedUser` (core/web/auth/auth.go:178-187) only inspects `SessionUserKey`, with no way to tell whether the underlying identity is a genuine `clsessions.User` row or the synthetic run-role user object created for an EI: [2](#0-1) 

`PipelineRunsController.Create` (core/web/pipeline_runs_controller.go:109-125) uses exactly this ambiguous check to gate access, with a comment stating EIs are intentionally excluded from this int-ID job-run path: [3](#0-2) 

Because `isUser` is true for both real users and EIs, an EI credential holder authenticated via `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers can call `POST /v2/jobs/:ID/runs` with an integer job ID and successfully invoke `prc.App.RunJobV2(ctx, jobID, nil)` for *any* job ID, not just the job(s) the EI is scoped/authorized to trigger via its normal webhook path. This conflates the EI's restricted identity with a full "run" role user for authorization purposes on this endpoint.

### Impact Explanation
This is an authorization-bypass / privilege-escalation issue: an external-initiator credential (intended only to trigger its associated webhook job) can trigger arbitrary jobs by numeric ID through an endpoint whose code comment and design explicitly forbid EI access. This can result in unauthorized job runs (and downstream unauthorized fund movement / off-chain action execution) using credentials that were never granted broad "run any job" authorization — matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Preconditions are minimal: possession of any valid external-initiator access key/secret pair (the lowest-privilege credential type explicitly in scope for this attacker model) is sufficient. No admin/user session or elevated role is required. The request is a straightforward, repeatable `POST /v2/jobs/:ID/runs` call with EI headers and a numeric job ID.

### Recommendation
Do not conflate EI identity with a real `SessionUserKey` user object. Introduce a distinct marker/role (or check `GetAuthenticatedExternalInitiator` first) so that `PipelineRunsController.Create` (and any other handler relying on `GetAuthenticatedUser` to exclude EIs) can reliably differentiate EI-authenticated requests from real user sessions, e.g. by checking `_, isEI := auth.GetAuthenticatedExternalInitiator(c); if isEI { reject }` before/instead of relying solely on `isUser`.

### Proof of Concept
Handler-level integration test plan:
1. Set up a test app with a job created and an external initiator registered with valid access key/secret.
2. Send `POST /v2/jobs/:ID/runs` (where `:ID` is the job's numeric ID) with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to the EI's credentials (no session cookie, no API token).
3. Assert that `AuthenticateExternalInitiator` succeeds and sets `SessionUserKey` (verifiable via `auth.GetAuthenticatedUser(c)` returning `ok=true`).
4. Assert that the response is `200 OK` with a pipeline run resource returned, i.e. `RunJobV2` was invoked for that job — demonstrating the "EIs not allowed" comment is not enforced.
5. Compare against expected behavior: the request should instead return `422 Unprocessable Entity` ("bad job ID") or `401/403`, since EIs should not be able to use this int-ID path.
