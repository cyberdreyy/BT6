### Title
Stale confirmations from removed multisig members are still counted toward the execution threshold, allowing requests to execute below the live `num_confirmations` threshold - (`multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`confirm()` decides whether to execute a pending request purely by comparing the *size* of the stored `confirmations` set to `num_confirmations`. When a member is removed via `DeleteMember`/`DeleteKey`, the cleanup logic only purges requests that member *created*, not the confirmations that member left on *other* pending requests they merely confirmed. Those stale confirmations remain in the `confirmations` set and continue to count toward the threshold, so a request can execute with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` decides execution solely from the confirmation count: [1](#0-0) 

Removal of a member is handled by `delete_member()`, which only cleans up requests where the removed member is the *creator* (`r.member == member`) — confirmations the removed member left on requests created by someone else are never purged: [2](#0-1) 

Because `confirmations` is a bare `HashSet<String>` keyed by member identity string with no reference back to `self.members`, and `confirm()`/`assert_valid_request()` never re-validate that every *existing* entry in the confirmations set still corresponds to a current member (only the *new* confirmer is checked via `current_member()`): [3](#0-2) 

This is the exact analog of the `retryMessage()` bug class: a piece of state (`RETRIABLE` status / here, a recorded confirmation) is captured while a precondition holds (message not banned / here, confirmer is a member), the precondition later changes (address banned / here, member removed), and the code that consumes the stale state (`retryMessage` / here, `confirm`'s threshold check) never rechecks the precondition before acting on it.

The same pattern exists in the older `multisig/src/lib.rs`, where `DeleteKey` only removes requests filtered by `r.signer_pk == pk` (the creator), not confirmer entries on other requests: [4](#0-3) 

### Impact Explanation
This breaks the custody binding "confirmations counted versus live members": the contract can execute an arbitrary `MultiSigRequest` (including `Transfer`, `FunctionCall`, `AddKey`, etc.) using a confirmation count that nominally equals `num_confirmations`, but where one or more of the counted confirmers are no longer members. Effectively, a request that should require `k` live signatures can be pushed through with `k-1` (or fewer) *currently authorized* approvals, i.e., a multisig request executed below the real/live threshold. Per the impact rubric this is Critical: "a multisig request executed below threshold."

### Likelihood Explanation
This does not require any external/unprivileged attacker — it is exploitable purely through the normal state machine already exposed to members: (1) a request accumulates a confirmation from member `M`, (2) `M` is later removed via a `DeleteMember`/`DeleteKey` request (a routine multisig operation, e.g. offboarding a compromised or departing member), (3) the earlier request is later completed by remaining live members. No collusion beyond ordinary multisig operation is required, and the ordering (confirm-then-remove-then-finish) is a natural operational sequence, not a contrived edge case, making this reasonably likely to occur in real deployments that periodically rotate members.

### Recommendation
When counting toward the execution threshold in `confirm()`, filter the stored `confirmations` set to only those entries that are still present in `self.members` (or proactively purge any confirmation entries belonging to a member at the time it is removed in `delete_member`/`DeleteKey` handling, scanning across *all* requests' confirmation sets, not just those the member created). Re-validate live membership of every confirmer, not just the newly confirming one, before comparing against `num_confirmations`.

### Proof of Concept
Given members `{A,B,C,D}` and `num_confirmations = 3`:
1. `A` calls `add_request` to create request `X` (e.g. `Transfer`).
2. `B` calls `confirm(X)` → `confirmations = {B}` (len 1, `1+1=2 < 3`, no execution).
3. `C` calls `confirm(X)` → `confirmations = {B, C}` (len 2, `2+1=3 >= 3`? this check happens before insert, `1+1=2<3` for step, ends up as `{B,C}` len 2).
4. Members `A, C, D` create and confirm a `DeleteMember{member: B}` request (reaching threshold 3) — this executes and removes `B` from `self.members`. Per `delete_member` (`multisig2/src/lib.rs:356-379`), only requests created by `B` are purged; request `X`'s confirmation set `{B, C}` is untouched.
5. `D` calls `confirm(X)`: `confirmations.len() == 2` (`B`,`C`), `2+1 = 3 >= num_confirmations(3)` → `execute_request` fires immediately, even though `B` is no longer a member and only `C` and `D` are live approvers alongside the stale `B` entry — i.e., only 2 of the 3 required *live* member confirmations actually authorized the transfer.     pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
