## No vulnerability found for this question.

### Analysis

The binding to verify is: `staked_amount_from_num_shares_rounded_down(B.stake_shares)` computed after A's dust `unstake` calls must equal (or only legitimately exceed) the value computed at the time B staked.

Tracing `inner_unstake` in `staking-pool/src/internal.rs`, the two rounding operations are asymmetric by design: [1](#0-0) 

`receive_amount` (credited to the caller's `unstaked` balance) is rounded **up**, while `unstake_amount` (subtracted from `total_staked_balance`) is rounded **down**. Since `unstake_amount = floor(S0 * num_shares / T0) <= S0 * num_shares / T0`, algebraically:

`S1 = S0 - unstake_amount >= S0 - S0*num_shares/T0 = P0 * T1`, where `P0 = S0/T0` is the pre-action share price and `T1 = T0 - num_shares`.

This means the post-action price `P1 = S1/T1 >= P0` — the share price can never decrease as a result of an `unstake` call. The same asymmetry exists in `internal_stake` (`charge_amount` rounded down, `stake_amount` added to the total rounded up): [2](#0-1) 

Both rounding pairs are explicitly documented as guaranteeing the share price never decreases ("to guarantee that the account can always unstake at least the same amount as staked" / "to guarantee the 'stake' share price never decreases"). Working a concrete numeric example (`S0=100`, `T0=99`, B holding 98 shares) confirms `staked_amount_from_num_shares_rounded_down(B.stake_shares)` for B goes from 98 to 99 after A's dust `unstake(1)` — it increases, not decreases, because the rounding remainder accrues to the shared pool rather than being extracted by A.

Additionally, A cannot repeatedly call `unstake(1)` without re-staking, since each call consumes A's own `stake_shares` via the check `account.stake_shares >= num_shares` and A only has the shares from their own tiny deposit — there is no mechanism by which A's `unstake` calls draw down B's `stake_shares` or degrade B's price. The `num_shares`/`total_stake_shares` denominator is shared for price computation, but the direction of rounding always biases in favor of remaining shareholders, not against them. [3](#0-2) 

The premise of the question — that A's dust `unstake` calls degrade B's redeemable balance below what B was charged — is contradicted by the algebra and the documented rounding invariant. No solvency violation exists here.

    /// Returns the staked amount rounded down corresponding to the given number of "stake" shares.
    pub(crate) fn staked_amount_from_num_shares_rounded_down(
        &self,
        num_shares: NumStakeShares,
    ) -> Balance {
        assert!(
            self.total_stake_shares > 0,
            "The total number of stake shares can't be 0"
        );
        (U256::from(self.total_staked_balance) * U256::from(num_shares)
            / U256::from(self.total_stake_shares))
        .as_u128()
    }

    /// Returns the staked amount rounded up corresponding to the given number of "stake" shares.
    ///
    /// Rounding up division of `a / b` is done using `(a + b - 1) / b`.
    pub(crate) fn staked_amount_from_num_shares_rounded_up(
        &self,
        num_shares: NumStakeShares,
    ) -> Balance {
        assert!(
            self.total_stake_shares > 0,
            "The total number of stake shares can't be 0"
        );
        ((U256::from(self.total_staked_balance) * U256::from(num_shares)
            + U256::from(self.total_stake_shares - 1))
            / U256::from(self.total_stake_shares))
        .as_u128()
    }
