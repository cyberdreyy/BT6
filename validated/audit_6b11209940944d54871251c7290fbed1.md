### Title
Validator Admission Ticket (VAT) balance eligibility check is a point-in-time snapshot that can be gamed by transient top-up/withdraw ("flash" balance) - (File: `runtime/src/bank.rs`, `vote/src/vote_account.rs`)

### Summary
The VAT mechanism (SIMD-357/SIMD-0357) admits a vote account into a given epoch's active/voting validator set only if, at the moment the epoch-boundary snapshot is taken, its lamport balance is `>= minimum_vote_account_balance` (rent-exempt minimum plus one epoch's VAT burn). Neither `clone_and_filter_for_vat` nor `get_vat_health_for_next_epoch` require that balance to be held for any duration — exactly the "point-in-time" flaw described in the ParaSpace report, where a health/solvency check validated only the instant the transaction executed rather than a sustained state.

### Finding Description
`VoteAccounts::clone_and_filter_for_vat` filters vote accounts for VAT admission purely on the vote account's current lamports at the time it is invoked: [1](#0-0) 
This filtering runs once, synchronously, at the epoch boundary from `update_epoch_stakes`/`get_top_epoch_stakes`, and the resulting filtered set is used both to build the next epoch's stakes and to immediately burn the VAT amount: [2](#0-1) [3](#0-2) 

The equivalent per-validator health check, `Bank::get_vat_health_for_next_epoch`, likewise reads only the vote account's current balance: [4](#0-3) 

Because a vote account is just a normal system-owned account, anyone (including the validator itself) can top it up with an ordinary `SystemInstruction::Transfer` — no vote-program authority is required to *deposit*. The validator that controls the vote account's withdraw authority can later remove those lamports with `VoteInstruction::Withdraw`. Nothing in the VAT logic requires the balance to persist across the epoch boundary beyond the instant the snapshot is taken: a validator can top up just before the snapshot, get admitted for the next epoch, and withdraw immediately after, exactly mirroring the ParaSpace pattern of borrowing funds, satisfying an instantaneous solvency check, then withdrawing them.

### Impact Explanation
VAT is explicitly designed as an economic admission barrier: an epoch's worth of lamports must be "burned" from each admitted vote account (`maybe_burn_vat_from_staked_accounts`), and the comment on that function states it must only run "after the vote accounts have been filtered ... to contain enough balance for admission" — i.e., the whole design assumes the balance check reflects real, sustained economic backing, not a transient balance. A validator can defeat this assumption, gaining admission to the active/voting set for an epoch (and the associated voting rewards and consensus participation, since under Alpenglow this set participates in BLS voting) without maintaining the intended stake commitment. This corrupts the intended stake/economic-backing invariant that the VAT mechanism enforces for consensus and reward accounting, and, because `maybe_burn_vat_from_staked_accounts` relies on the assumption asserted via `.expect()` on a `checked_sub`, any divergence between the balance observed during filtering and the balance available at burn time is an unhandled panic path: [5](#0-4) 

### Likelihood Explanation
Depositing lamports into any vote account is trivial and unprivileged (plain system transfer). Withdrawing requires the vote account's own withdraw authority, so the attacker must be the vote-account owner (or someone colluding with them) — this matches the ParaSpace scenario, where the "attacker" is the account owner gaming their own health check. Timing the top-up before the epoch-boundary snapshot and the withdraw after is straightforward since epoch boundaries and slot timing are publicly known and deterministic.

### Recommendation
Do not rely on an instantaneous balance snapshot for VAT admission. Require the minimum VAT balance to have been continuously held for a minimum window prior to the epoch boundary (e.g., checked across multiple slots or requiring the balance to be locked/committed ahead of time), analogous to the report's recommendation of a time-delay before releasing/validating recovered collateral. At minimum, `maybe_burn_vat_from_staked_accounts` should not `.expect()` on the balance assumption but should re-validate and gracefully exclude accounts whose balance has since dropped below the VAT threshold rather than panicking.

### Proof of Concept
1. Validator `V` controls vote account `VA` with withdraw authority `W`.
2. `VA`'s sustained balance is below `minimum_vote_account_balance_for_vat` (rent-exempt minimum + VAT burn).
3. Shortly before the last slot of the current epoch (when `update_epoch_stakes`/`clone_and_filter_for_vat` runs), `V` submits a `SystemInstruction::Transfer` topping up `VA` to exceed the threshold.
4. At the epoch boundary, `clone_and_filter_for_vat` admits `VA` into the next epoch's VAT-filtered vote-account set, and `maybe_burn_vat_from_staked_accounts` burns one epoch's worth of VAT from `VA`.
5. Immediately after the boundary, `W` submits `VoteInstruction::Withdraw` to withdraw the remaining top-up lamports back out of `VA`, leaving `VA` under-capitalized for the entire epoch it is now admitted for.
6. `V` retains active/voting-set membership (and associated rewards) for the epoch without having sustained the economically-intended balance, defeating the purpose of the VAT admission barrier described in `runtime/src/bank.rs` and `vote/src/vote_account.rs`.

    pub fn get_vat_health_for_next_epoch(
        &self,
        vote_account_pubkey: &Pubkey,
    ) -> std::result::Result<(), VATHealthError> {
        let vote_accounts = self.vote_accounts();

        let Some((_, vote_account)) = vote_accounts.get(vote_account_pubkey) else {
            return Err(VATHealthError::VoteAccountNotFound);
        };

        if vote_account
            .vote_state_view()
            .bls_pubkey_compressed()
            .is_none()
        {
            return Err(VATHealthError::NoBLSPubkey);
        }

        let my_balance = vote_account.lamports();
        let minimum_vote_account_balance_for_vat = self.minimum_vote_account_balance_for_vat();
        if vote_account.lamports() < minimum_vote_account_balance_for_vat {
            return Err(VATHealthError::InsufficientFundsInVoteAccount(
                my_balance,
                minimum_vote_account_balance_for_vat,
            ));
        }

        Ok(())
    }
