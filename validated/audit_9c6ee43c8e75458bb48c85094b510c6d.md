### Title
Missing `return` after failed email-claim extraction lets OIDC login proceed with an unverified/empty email - (File: `core/sessions/oidcauth/oidc.go`)

### Summary
`handleTokenExchange` in the OIDC authentication driver fails to `return` after logging an error when the `email` claim cannot be type-asserted from the verified ID token claims. Execution falls through and creates a persisted, cookie-backed session row keyed on an empty/garbage email value, using a role that was derived independently from a different claim path. This is analogous to the reported class of bug: a failed check whose result is not honored, letting privileged control flow continue as if the check had passed.

### Finding Description
In `handleTokenExchange` [1](#0-0) , the code does:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
```
Unlike every other error branch in this same function (state mismatch, token exchange failure, missing `id_token`, verification failure, claim parsing failure, role-mapping failure all call `return` immediately after writing the HTTP error response), this branch omits `return`. Execution continues to role mapping and to the session-creation `INSERT` [2](#0-1) , then to `ginSession.Set(...)` / `ginSession.Save()` [3](#0-2) , and finally responds `200 OK` with `Success: true` to the client even though the earlier `c.String(http.StatusInternalServerError, ...)` was already written (a double-write to the response, and a functionally successful login flow) [4](#0-3) .

The same pattern (log-then-continue without `return`) also exists for the DB insert error a few lines later [5](#0-4) : if the `INSERT INTO oidc_sessions` fails, the handler still proceeds to set the session cookie to `clSession.ID` and returns success, even though no session row was persisted for that ID.

Root cause: unchecked/ignored failure of a claim assertion (`ok` from `claims["email"].(string)`) does not gate subsequent security-relevant operations (role mapping is independent of `email`, but session creation and audit logging use the empty `email` value), directly mirroring the reported bug class where a failed boolean check is not enforced and downstream logic proceeds as if it succeeded.

### Impact Explanation
If the configured OIDC identity provider ever omits the `email` claim (e.g., IdP scope/config drift, or an IdP that returns email only under a different claim name), a legitimate OIDC login flow will still succeed and create a working, cookie-authenticated session that is persisted in `oidc_sessions` with an empty `user_email` and a role derived from `IDClaimsToUserRole`. This:
- breaks the audit trail (`audit.AuthLoginSuccessNo2FA` is logged with an empty email, and `ClearNonCurrentSessions`/session lookups keyed on email become ambiguous across any accounts sharing the empty value),
- can allow multiple authenticated users lacking the email claim to be recorded/managed as the same identity ("") in the `oidc_sessions` table, a cross-user identity confusion,
- and, in the DB-insert-failure branch, causes the server to hand the client a session cookie referencing a session ID that was never persisted, misleading the client about login state.

This is a real-world reachable path for an unprivileged user completing the standard `/oidc-login` → `/oidc-callback`-style flow; it does not require a compromised node, peer, or operator access — only IdP configuration circumstances outside the node operator's direct control.

### Likelihood Explanation
Likelihood is moderate-to-low in practice because it depends on the IdP configuration failing to return an `email` claim despite the client requesting the `email` scope [6](#0-5) . It is not directly attacker-triggerable by forging the ID token content (the token is signed by the IdP and verified via `oi.provider.Verifier(...).Verify(...)`), but a user of a misconfigured or non-standard IdP can trigger it through ordinary use, and the resulting behavior (silent continuation, double response write, unpersisted session issuance) is a genuine defect regardless of the trigger frequency.

### Recommendation
Add `return` after the `c.String(...)` call in the `!ok` branch for the email claim (mirroring every other error branch in this function), and add `return` after the `c.String(http.StatusInternalServerError, "Error creating session")` call following the failed `INSERT INTO oidc_sessions`. Consider treating a missing/empty `email` claim as a hard authentication failure rather than continuing with an empty string, since `email` is used as the primary session/user identity key throughout the OIDC authenticator (`FindUser`, `ClearNonCurrentSessions`, `AuthorizedUserWithSession`, audit logging).

### Proof of Concept
Not independently exploitable via crafted HTTP input alone (the ID token is IdP-signed and verified before this code path runs), so no standalone PoC request can be constructed. The defect is demonstrated purely by control-flow analysis: any code path where `claims["email"].(string)` type-assertion fails reaches the `!ok` branch, writes an error response, but does not `return`, and the function falls through to create and persist a session and respond `200 OK`: [7](#0-6)
