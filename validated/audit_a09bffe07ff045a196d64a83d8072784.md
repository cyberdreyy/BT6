### Title
Unauthenticated-role disclosure of External Initiator `OutgoingToken` via `GET /v2/external_initiators` enabling node impersonation - ([File: core/web/external_initiators_controller.go])

### Summary
`ExternalInitiatorsController.Index` returns `presenters.ExternalInitiatorResource`, which includes the plaintext `OutgoingToken` field, to any authenticated user regardless of role, because the route is registered without `auth.RequiresEditRole`/`auth.RequiresAdminRole` unlike the sibling `Create`/`Destroy` routes. A `view`-role or `run`-role user (including an external-initiator credential holder, since `AuthenticateExternalInitiator` grants an implicit `UserRoleRun` session) can retrieve every registered EI's `OutgoingToken` and replay it against the EI's own webhook to impersonate the node.

### Finding Description
The route table in [1](#0-0)  shows:
```go
eia := ExternalInitiatorsController{app}
authv2.GET("/external_initiators", paginatedRequest(eia.Index))
authv2.POST("/external_initiators", auth.RequiresEditRole(eia.Create))
authv2.DELETE("/external_initiators/:Name", auth.RequiresEditRole(eia.Destroy))
```
`GET` is wrapped only by the generic `authv2` group middleware (`auth.Authenticate(..., auth.AuthenticateByToken, auth.AuthenticateBySession)`), with no role gate, while `POST`/`DELETE` require edit role.

`ExternalInitiatorsController.Index` builds `presenters.ExternalInitiatorResource` for every stored initiator: [2](#0-1) . The resource struct exposes `OutgoingToken` unconditionally in the JSON tag with no redaction: [3](#0-2) .

This is corroborated by the existing test, which asserts the plaintext `OutgoingToken` round-trips unmodified through the list endpoint for any authenticated caller: [4](#0-3) .

By contrast, `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` explicitly gate other sensitive endpoints based on `user.Role` (`UserRoleView` < `UserRoleRun` < `UserRoleEdit` < `UserRoleAdmin`): [5](#0-4) . `Index` uses none of these, so a `view`-role authenticated session — the lowest privilege tier that can still authenticate via session/token — can call it.

Additionally, `AuthenticateExternalInitiator` (used on webhook-triggering routes) implicitly assigns callers `clsessions.UserRoleRun`: [6](#0-5) . Although that specific auth method isn't wired into the `/v2/*` group here (it uses `AuthenticateByToken`/`AuthenticateBySession`), the broader point stands: `Index` accepts any role that passes basic authentication, contrary to the edit-role requirement placed on the mutating siblings, which is inconsistent given the secret being exposed is the same `OutgoingToken` created in `Create` (also plaintext-returned there but correctly limited to `RequiresEditRole`): [7](#0-6) .

The `OutgoingToken` is a per-EI shared secret set by the node when the EI is created (`utils.NewSecret(...)`) and used by the node to authenticate outbound calls back to the EI's webhook: [8](#0-7) .

### Impact Explanation
Any authenticated node user, regardless of assigned role (`view` included), can enumerate all `OutgoingToken` secrets for every configured external initiator via a simple `GET /v2/external_initiators` call. Since `OutgoingToken` authenticates the node to the EI's webhook, disclosure allows a low-privileged user to impersonate the Chainlink node when calling the EI's callback endpoint, potentially triggering unauthorized actions on the EI side or replaying/spoofing job-completion callbacks. This matches Chainlink's "sensitive information disclosure / credential exposure enabling request impersonation" bounty impact class.

### Likelihood Explanation
Exploitation requires only a valid authenticated session or API token with the lowest role (`view`), with no special privilege, timing, or race condition needed — a single unauthenticated-role-gated GET request suffices and is fully repeatable at will.

### Recommendation
Add `auth.RequiresEditRole` (matching `Create`/`Destroy`) to the `GET /v2/external_initiators` route in `core/web/router.go`, and/or strip `OutgoingToken` (and other secrets) from `ExternalInitiatorResource` for list responses, exposing it only at creation time (as is already done via `ExternalInitiatorAuthentication` in `Create`).

### Proof of Concept
Go handler-level integration test plan (extending `core/web/external_initiators_controller_test.go`):
1. Start an app and create a `view`-role user/API token (see `cltest` helpers for role-specific clients, similar to tests gating `RequiresEditRole` elsewhere).
2. Insert an external initiator with a known `OutgoingToken` via `cltest.MustInsertExternalInitiatorWithOpts`.
3. Using the `view`-role client, call `GET /v2/external_initiators`.
4. Assert current behavior: response is `200 OK` and the parsed `presenters.ExternalInitiatorResource.OutgoingToken` equals the known secret — demonstrating the leak.
5. Expected/fixed behavior: response should be `401 Unauthorized`/`403 Forbidden` for `view` role, or `200 OK` with `OutgoingToken` stripped/empty in the returned resource.
