### Title
External Initiator credentials bypass job-ownership binding and can trigger runs of arbitrary integer-ID jobs via POST /v2/jobs/:ID/runs - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates int-ID job runs on `auth.GetAuthenticatedUser(c)` returning `isUser=true`, intending only session/token "users" to run int-keyed jobs while EIs would be restricted to UUID-keyed webhook jobs. However, `AuthenticateExternalInitiator` also calls `c.Set(SessionUserKey, &clsessions.User{Role: UserRoleRun})`, so `GetAuthenticatedUser` returns `ok=true` for EI-authenticated requests too, defeating the intended restriction.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered with `auth.Authenticate(..., auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` followed by `auth.RequiresRunRole(prc.Create)` [1](#0-0) .

`AuthenticateExternalInitiator` authenticates via EI AccessKey/Secret headers and, regardless of which job/webhook the EI is bound to, unconditionally sets `SessionUserKey` to a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` [2](#0-1) . This satisfies `RequiresRunRole` (role != View) [3](#0-2) .

In `PipelineRunsController.Create`, the comment states "only users are allowed to run jobs using int IDs - EIs not allowed," and the code branches on `_, isUser := auth.GetAuthenticatedUser(c)` [4](#0-3) . But `GetAuthenticatedUser` simply reads whatever was stored under `SessionUserKey` [5](#0-4)  — which is the same synthetic user object set by `AuthenticateExternalInitiator`. There is no code path distinguishing "real user" from "EI acting as a synthetic run-role user," and no check that ties the requested integer job ID to the specific EI's bound webhook/job. As a result, once `idStr` parses as an int32, `prc.App.RunJobV2(ctx, jobID, nil)` is invoked for whatever job ID is supplied in the URL, with no ownership/binding check against the authenticated EI at all.

Only the UUID path is rejected outright (webhook job type removed) [6](#0-5) ; the int-ID path has no equivalent restriction preventing EIs, contradicting the stated intent in the comment.

### Impact Explanation
Any holder of valid EI AccessKey/Secret credentials (a low-privilege, narrowly-scoped credential intended only to trigger its own bound webhook job) can invoke `RunJobV2` for **any** job ID on the node, including OCR, VRF, keeper, or other sensitive jobs unrelated to the EI's registration. This is unauthorized execution of arbitrary jobs/pipelines — a cross-tenant/cross-scope authorization bypass that could trigger fund-moving or state-changing pipeline runs (e.g., ETH transfers via job tasks, on-chain transactions) outside the EI's intended scope.

### Likelihood Explanation
Preconditions are minimal: only a valid EI AccessKey/Secret pair (obtainable by any party the node operator granted EI registration to, which is a low-trust credential by design) and knowledge/guessing of a target job's small integer ID. No admin/user session or API token is needed. The request is a single unauthenticated-relative-to-target-job POST with EI headers; fully repeatable and requires no race conditions or timing.

### Recommendation
In `PipelineRunsController.Create`, do not rely solely on `auth.GetAuthenticatedUser`; explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and reject the request (or verify job binding) when an EI is present, e.g.:
```go
if _, isEI := auth.GetAuthenticatedExternalInitiator(c); isEI {
    jsonAPIError(c, http.StatusUnprocessableEntity, errors.New("external initiators may not run jobs by integer ID"))
    return
}
```
Alternatively, mark the synthetic EI user distinctly (e.g., a dedicated role or flag) instead of reusing `clsessions.User{Role: UserRoleRun}`, so `GetAuthenticatedUser` cannot be used interchangeably as a proxy for "is a real user."

### Proof of Concept
Handler-level integration test plan:
1. Start app, register two jobs (Job A, Job B) with distinct integer IDs via `app.AddJobV2`.
2. Register an External Initiator unrelated to either job (`cltest.MustInsertExternalInitiator` or similar), obtaining its AccessKey/Secret.
3. Build an HTTP client that sets `static.ExternalInitiatorAccessKeyHeader` / `static.ExternalInitiatorSecretHeader` headers (no session cookie, no API token).
4. POST to `/v2/jobs/<JobA.ID>/runs` with EI headers.
5. Assert current (vulnerable) behavior: response is `200 OK` with a `pipelineRun` JSON:API resource for Job A, proving `RunJobV2` executed for a job the EI has no relationship to.
6. Repeat for Job B's ID with the same EI credentials to show it is not scoped to any single job.
7. Expected fixed behavior: both requests should return `422 Unprocessable Entity` (or `401/403`) with an error indicating EIs cannot run jobs by integer ID.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
