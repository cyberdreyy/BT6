### Title
Unfunded instant-withdraw receipts are payable at par and can drain other claimants' funded reserves - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays out the full `instantWithdrawsRequests[_user]` balance without verifying that the request was actually funded by the borrower. `collectInstantWithdrawFunds` tracks only an aggregate unfunded remainder (`pendingInstantWithdraws`), and the strategy's underlying balance is a single commingled pool. Analogous to CVE-2018-8019 accepting a revoked certificate because the responder's invalid response was not properly validated, the vault treats every recorded instant receipt as valid (funded) even when its funding response never arrived, letting an unprivileged user claim underlyings that belong to other claimants.

### Finding Description
- `requestInstantWithdraw` mints a receipt and increments `instantWithdrawsRequests[_user]` and the global `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`). Funding happens later, when the CDO pulls borrower/strategy cash and calls `collectInstantWithdrawFunds`, which decrements the aggregate `pendingInstantWithdraws` and transfers underlying into the strategy (`IdleCreditVault.sol:398-403`).
- `claimInstantWithdrawRequest` burns `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim(_user, amount)` with no check that this user's receipt is within the funded portion (`IdleCreditVault.sol:380-393`). `_transferFundedClaim` only protects `defaultRecoveryReserve`; it does not reserve underlying for other pending receipts (`IdleCreditVault.sol:897-907`).
- There is no per-user or per-epoch funded flag for instant requests: `instantWithdrawClaimsByEpoch`/`instantWithdrawsRequestsByEpoch` are only used for default-recovery accounting, and the non-defaulted claim path pays at par whenever `underlyingToken.balanceOf(address(this))` is sufficient.
- Sequence: user A requests instant withdraw; the CDO collects funds for A (balance now holds A's claim). User B requests instant withdraw in the same or a subsequent epoch window; B's request remains unfunded (`pendingInstantWithdraws > 0`). B calls `claimInstantWithdrawRequest` via the CDO before A does. The strategy transfers `B's` full receipt amount, consuming the underlying reserved for A. A's subsequent claim reverts on insufficient balance — permanent loss for A, direct extraction for B.
- Existing guards do not stop this: `_onlyIdleCDO` only restricts the caller, not funding status; the epoch-wait check in `_claimFundedWithdrawRequest` applies to normal withdraws, not instant ones; the default-recovery paths (`_claimDefaultedInstantWithdrawRequest`) only run after `defaultRecoveryFinalized`.

### Impact Explanation
An unprivileged lender (any EOA holding tranche tokens routed through `IdleCDOEpochVariant.requestInstantWithdraw`/`claimInstantWithdrawRequest`) can steal up to the entire funded instant-withdraw reserve held in the strategy — bounded by the size of their own unfunded receipt, which they control by depositing tranche tokens and requesting an instant withdraw. This is direct theft of other users' funded withdrawals and breaks the "one receipt, one funded payout" invariant.

### Likelihood Explanation
Exploitable whenever the strategy holds funded instant-withdraw underlying while new unfunded instant receipts exist — i.e., any epoch boundary where the borrower's funding covered only part of the instant queue (partial prefunding is explicitly contemplated by `_defaultPrefundedInstantReserve`, `IdleCreditVault.sol:716-723`). The attacker only needs to front-run honest claimants; no privileged role, default, or oracle manipulation is required. Residual uncertainty: if `IdleCDOEpochVariant.claimInstantWithdrawRequest` performs an additional funding check before calling the strategy, the attack is blocked — that call path should be verified during remediation.

### Recommendation
Track funded vs. unfunded instant receipts per user/epoch (e.g., a `fundedInstantWithdraws` watermark analogous to `instantWithdrawClaimsByEpoch`), and in `claimInstantWithdrawRequest` pay only `min(instantWithdrawsRequests[_user], fundedShare)`, reverting or queuing the unfunded remainder. Alternatively, segregate funded underlying per claimant at `collectInstantWithdrawFunds` time so an unfunded receipt can never spend another user's collected funds.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "../../contracts/strategies/idle/IdleCreditVault.sol";
import "../../contracts/IdleCDOEpochVariant.sol";

contract InstantWithdrawUnfundedClaimPoC is Test {
    // Fork a live epoch credit vault deployment where
    // requestInstantWithdraw / collectInstantWithdrawFunds are reachable
    // through IdleCDOEpochVariant.

    function test_unfundedInstantReceiptDrainsFundedReserve() internal {
        IdleCreditVault vault = IdleCreditVault(STRATEGY);
        IdleCDOEpochVariant cdo = IdleCDOEpochVariant(vault.idleCDO());
        IERC20Detailed underlying = vault.underlyingToken();
        address alice = address(0xA11CE);
        address bob = address(0xB0B);

        // 1. Alice deposits into a tranche and requests an instant withdraw of X.
        //    (via cdo.requestInstantWithdraw alice-side tranche position)
        // 2. CDO/borrower funds Alice's request only:
        //    collectInstantWithdrawFunds(X) -> strategy holds X underlying,
        //    pendingInstantWithdraws == 0 at that instant.
        // 3. Bob deposits tranche tokens and calls requestInstantWithdraw(Y).
        //    Borrower does NOT fund Bob: pendingInstantWithdraws == Y,
        //    strategy balance is still only Alice's X.
        // 4. Bob calls cdo.claimInstantWithdrawRequest(...) which reaches
        //    vault.claimInstantWithdrawRequest(bob):
        //    - instantWithdrawsRequests[bob] == Y is burned
        //    - _transferFundedClaim(bob, Y) transfers Y underlying
        //    - there is no check that Y was ever collected
        uint256 bobClaim = vault.instantWithdrawsRequests(bob);
        assertGt(bobClaim, 0);

        uint256 balBefore = underlying.balanceOf(address(vault));
        vm.prank(address(cdo));
        vault.claimInstantWithdrawRequest(bob);

        // Bob received underlying that was collected for Alice's receipt.
        assertEq(underlying.balanceOf(bob), bobClaim);
        assertLt(underlying.balanceOf(address(vault)), balBefore);

        // 5. Alice's legitimate claim now reverts/underflows:
        //    _transferFundedClaim -> safeTransfer fails on insufficient balance.
        vm.prank(address(cdo));
        vm.expectRevert();
        vault.claimInstantWithdrawRequest(alice);
    }
}
```
