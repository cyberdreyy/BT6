### Title
Post-default instant withdraw requests are booked into the defaulted epoch and paid from the recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`requestInstantWithdraw` lacks the `defaultRecoveryFinalized` guard that `requestWithdraw` has. A post-default instant request is recorded under the current `epochNumber`, which still equals `defaultRecoveryEpoch` (no further `stopEpoch` bumps it after default). `claimInstantWithdrawRequest` then treats the new receipt as a defaulted-epoch claim via `_claimDefaultedInstantWithdrawRequest` and pays it out of `defaultRecoveryReserve` — reserve that was sized only for pre-default claims. This is the analog of CVE-2018-10537: a second "chunk" (a new request) is parsed into an already-finalized structure (the defaulted epoch bucket) that was never meant to accept more entries.

### Finding Description
- `requestWithdraw` explicitly branches on `defaultRecoveryFinalized` and routes new requests to `postDefaultRequests`, paid 1:1 and blocked if any old receipt exists. `requestInstantWithdraw` performs no such check; it mints the receipt and increments `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` unconditionally.
- After `finalizeDefaultRecovery`, `epochNumber` is frozen at `defaultRecoveryEpoch`, so the new request lands directly in the defaulted-epoch bucket.
- On `claimInstantWithdrawRequest`, since `defaultInstantWithdrawsFinalized` is true when instant claims were pending, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`, clears it, and calls `_transferDefaultRecovery(user, claimBasis * defaultRecoveryPrice)`, decrementing `defaultRecoveryReserve`.
- The reserve was computed as `reserveAmount` over `totalBasis` at finalization; post-default claims were never part of `totalBasis`, so every such claim is pure reserve dilution. Legitimate defaulted claimants' later `_transferDefaultRecovery` calls underflow/revert once the reserve is drained.

### Impact Explanation
An unprivileged tranche-token holder can, after default finalization, call the CDO's instant-withdraw path and get paid from the recovery reserve, directly reducing the recovery paid to users whose receipts were included in the finalized basis. Once drained or overdrawn (`defaultRecoveryReserve -= _amount` reverts on underflow), remaining legitimate claims are permanently frozen. Even if the CDO passes a haircut amount for the post-default request, the attacker is paid at `defaultRecoveryPrice` from a fixed pool that excluded their claim — every wei they take is stolen pro-rata from real recovery claimants.

### Likelihood Explanation
Requires only: a finalized default with `defaultInstantWithdrawsFinalized == true` (i.e., pending instant withdrawals existed at finalization), a non-empty `defaultRecoveryReserve`, and any tranche holder able to submit an instant withdraw request post-default. All roles needed for setup are honest; the attack is a single user action. No privileged misbehavior needed.

### Recommendation
In `requestInstantWithdraw`, mirror `requestWithdraw`: when `defaultRecoveryFinalized` is set, either revert or route the request into a post-default bucket (e.g., `postDefaultRequests`-style accounting) paid from non-reserve funds, and revert if the user has outstanding receipts. Additionally key defaulted instant claims off `epochNumber < defaultRecoveryEpoch`-style explicit bookkeeping rather than a mutable counter that post-default requests can still write into.

### Proof of Concept
Foundry fork sketch (attacker = ordinary tranche holder; owner/manager/borrower honest):

```solidity
// Setup: deposit into tranches, startEpoch, request instant withdraw for victim,
// borrower defaults -> finalizeDefault / finalizeDefaultRecovery on the vault.
// defaultRecoveryReserve = R, defaultRecoveryPrice = p < 1e18, epochNumber = E = defaultRecoveryEpoch.

// Attack: attacker holds tranche tokens post-default.
vm.prank(attacker);
idleCDO.requestInstantWithdraw(amount); // -> vault.requestInstantWithdraw(amount, attacker)

// vault state now: instantWithdrawsRequestsByEpoch[attacker][E] = amount
//                  instantWithdrawClaimsByEpoch[E] += amount  (post-finalization mutation)
//                  pendingInstantWithdraws += amount

vm.prank(attacker);
idleCDO.claimInstantWithdrawRequest();
// _claimDefaultedInstantWithdrawRequest pays (amount * p) / 1e18 from defaultRecoveryReserve.

// Victim's legitimate defaulted claim now reverts or is underpaid:
vm.prank(victim);
vm.expectRevert(); // defaultRecoveryReserve underflow or empty
idleCDO.claimInstantWithdrawRequest();
```

Invariant broken: "one receipt, one payout" / reserve isolation — the finalized recovery pool pays claims that were never in `totalBasis`, leaving real claimants unpaid.

Caveat: I could not fully trace `IdleCDOEpochVariant.requestInstantWithdraw`/`claimInstantWithdrawRequest` wrappers (grep returned matches but line-level reads were not completed within iteration limits), so whether the CDO applies a haircut on post-default instant requests is unverified. The reserve-dilution and claimant-freeze outcome holds either way; attacker's net profit depends on that haircut.
