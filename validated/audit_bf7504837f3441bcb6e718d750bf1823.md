Found the key vulnerability: `WorkflowMetadataHandler.Authorize()` in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go` verifies a JWT via `utils.VerifyRequestJWT` (`core/utils/jwt.go`) but the JWT digest binds only to the JSON-RPC `Request` (method + params), never to the `workflowID` that is passed in separately. This is directly analogous to the reported bug: a signed message lacks a "domain" binding (there, `chainId`; here, `workflowID`/DON scope), enabling the signature to be replayed in a different context than intended.

### Title
Workflow-scoped JWT authorization does not bind signature to `workflowID`, enabling cross-workflow replay of trigger-execution tokens - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` accepts a `workflowID` argument and a caller-supplied JWT, then verifies the JWT strictly against the JSON-RPC `Request` body via `utils.VerifyRequestJWT` [1](#0-0) . The verification only checks the ECDSA signature over the request digest, JWT `exp`/`iat`/`jti`, and afterwards checks whether the recovered signer address is in the authorized-key set *for the given `workflowID`* [2](#0-1) . Nowhere in `CreateRequestJWT`/`VerifyRequestJWT` is the `workflowID` (or DON id) included as part of the signed digest [3](#0-2) .

### Finding Description
The JWT's cryptographic binding is computed purely from `req.Digest()` (method + params of the JSON-RPC request), as enforced in `VerifyRequestJWT`: [4](#0-3) 

The `workflowID` used to select which "authorized keys" set to check is passed as a separate, unsigned parameter to `Authorize(workflowID, token, req)` [5](#0-4) . If the same signer's ECDSA key is registered as an authorized key for multiple workflows (a supported/expected scenario — a workflow owner may run multiple workflows with the same key), a JWT created and signed for one `workflowID` (with a given request `Method`/`Params`) can be replayed against a *different* `workflowID` as long as: (a) the signer is also an authorized key for that other workflow, and (b) the caller supplies a `req` object whose digest happens to match the original signed digest (trivial, since the attacker controls the `req` passed into `Authorize` at the call site — see `httpTriggerHandler.authorizeRequest`, which passes attacker-controlled `req` alongside an attacker-supplied `workflowID` resolved from the request itself) [6](#0-5) .

This mirrors the Sherlock finding precisely: the missing `chainId` in the opyn EIP-712 signature meant the signature was valid across unintended "domains" (chains); here the missing `workflowID` binding in the JWT digest means a signature/token minted for one workflow-scoped authorization context is valid across unintended "domains" (workflows) that happen to share an authorized signer key.

### Impact Explanation
An unprivileged external caller who can obtain (e.g., intercept, or via a workflow whose trigger endpoint they control) a validly-signed trigger JWT for one workflow can replay that same token to trigger execution of any other workflow that lists the same signer as an authorized key, provided the JSON-RPC `Method`/`Params` are reconstructed to match the original digest. Because the workflow binding is enforced only via a database/map lookup after signature verification and not cryptographically bound into the signed payload, this allows unauthorized triggering of workflow executions outside the workflow the token holder actually possesses authority for — a form of request impersonation / cross-workflow replay, matching the "unauthorized job run" acceptance criterion.

### Likelihood Explanation
Exploitation requires: (1) a workflow owner/operator reusing the same signer key across multiple workflows (a realistic and likely common operational pattern, since keys are tied to a workflow owner's authorized-key set rather than uniquely generated per workflow), and (2) the attacker being able to observe or reconstruct a valid signed JWT+request pair for one workflow and resubmit it against a different `workflowID`. The `jti` replay cache (`jwtReplayCache`) only prevents literal re-use of the *same token+jti value* — it does not prevent replay under a *different* `workflowID` parameter, since `jwtCache.isReplay`/`recordUsage` key off `claims.ID` only, independent of `workflowID` [7](#0-6) .

### Recommendation
Include the `workflowID` (and ideally the DON/environment identifier) as part of the signed digest that `CreateRequestJWT`/`VerifyRequestJWT` compute and validate, analogous to including `chainId` in an EIP-712 domain separator. Concretely, extend `JWTClaims`/the digest input in `core/utils/jwt.go` to bind `workflowID`, and update `WorkflowMetadataHandler.Authorize` to verify that the token's bound `workflowID` claim matches the `workflowID` parameter before consulting the authorized-key map, rather than relying solely on the unsigned `workflowID` argument for scoping.

### Proof of Concept
1. Attacker controls (or colludes with) a signer key `K` that is registered as an authorized key for both `workflowA` and `workflowB` (e.g., a legitimate workflow owner running two workflows with one key).
2. A valid JWT `T` is created and signed by `K` for a JSON-RPC trigger request `{method, params}` intended for `workflowA`, via `CreateRequestJWT`/`SignedString` [8](#0-7) .
3. Attacker submits the same token `T` and same `req` object to the gateway but targeting `workflowB`'s HTTP trigger endpoint (workflowID resolved to `workflowB`).
4. `Authorize(workflowB, T, req)` succeeds because `VerifyRequestJWT` only checks the digest of `req` (identical) and the signer's presence in `workflowB`'s authorized-key set — it never checks that `T` was intended for `workflowA` [9](#0-8) , causing `workflowB` to be executed using a token never intended to authorize it.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
```

// VerifyRequestJWT verifies a signed JWT for a JSON-RPC request
// It recovers and returns the public key used to sign the JWT, checks the issuer, validates the digest,
// and performs all validations done by jwt.ParseWithClaims() including expiration checks.
func VerifyRequestJWT[T any](tokenString string, req jsonrpc.Request[T], opts ...VerifyOption) (*JWTClaims, gethcommon.Address, error) {
	options := &verifyOptions{}
	for _, opt := range opts {
		opt(options)
	}

	maxExpiryDuration := maxJWTExpiryDuration
	if options.maxExpiryDuration != nil {
		maxExpiryDuration = *options.maxExpiryDuration
	}

	issuedAtTolerance := defaultIssuedAtTolerance
	if options.issuedAtTolerance != nil {
		issuedAtTolerance = *options.issuedAtTolerance
	}
	signedString, signature, err := splitToken(tokenString)
	if err != nil {
		return nil, gethcommon.Address{}, err
	}
	decodedSignature, err := base64.RawURLEncoding.DecodeString(signature)
	if err != nil {
		return nil, gethcommon.Address{}, fmt.Errorf("signature segment is not valid base64url: %w", err)
	}
	pubKey, err := GetSignersEthAddress([]byte(signedString), decodedSignature)
	if err != nil {
		return nil, gethcommon.Address{}, err
	}
	verifiedToken, err := jwt.ParseWithClaims(tokenString, &JWTClaims{}, func(token *jwt.Token) (any, error) {
		if token.Method.Alg() != EthereumSigningMethod.Alg() {
			return nil, fmt.Errorf("unsupported JWT 'alg': '%s'. Expected '%s'", token.Method.Alg(), EthereumSigningMethod.Alg())
		}
		if _, ok := token.Method.(*SigningMethodEth); !ok {
			return nil, jwt.ErrSignatureInvalid
		}
		return pubKey, nil
	})
	if err != nil {
		return nil, gethcommon.Address{}, err
	}
	verifiedClaims, ok := verifiedToken.Claims.(*JWTClaims)
	if !ok {
		return nil, gethcommon.Address{}, errors.New("claims payload is not in the expected format")
	}
	if !verifiedToken.Valid {
		return nil, gethcommon.Address{}, errors.New("signature or claims validation failed")
	}
	reqDigest, err := req.Digest()
	if err != nil {
		return nil, gethcommon.Address{}, err
	}
	if verifiedClaims.ID == "" {
		return nil, gethcommon.Address{}, errors.New("JWT ID (jti) is required but missing")
	}
	if verifiedClaims.ExpiresAt == nil {
		return nil, gethcommon.Address{}, errors.New("expiredAt (exp) is required but missing")
	}
	if verifiedClaims.IssuedAt == nil {
		return nil, gethcommon.Address{}, errors.New("issuedAt (iat) is required but missing")
	}
	now := time.Now()
	issuedAt := verifiedClaims.IssuedAt
	if issuedAt.After(now.Add(issuedAtTolerance)) {
		return nil, gethcommon.Address{}, fmt.Errorf("issuedAt (iat) is too far in the future (beyond tolerance of %.0f seconds)", issuedAtTolerance.Seconds())
	}
	duration := verifiedClaims.ExpiresAt.Sub(verifiedClaims.IssuedAt.Time)
	if duration > maxExpiryDuration {
		return nil, gethcommon.Address{}, fmt.Errorf("token lifetime %.0f sec exceeds the maximum allowed %.0f sec. Reduce the gap between 'iat' and 'exp'", duration.Seconds(), maxExpiryDuration.Seconds())
	}
	if verifiedClaims.Digest != "0x"+reqDigest {
		return nil, gethcommon.Address{}, fmt.Errorf("claim digest '%s' does not match calculated request digest '0x%s'", verifiedClaims.Digest, reqDigest)
	}
```

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
