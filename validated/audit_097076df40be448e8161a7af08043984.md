### Title
Cross-job run triggering by unrelated External Initiator credential due to missing initiator-to-job binding check - ([File: core/web/pipeline_runs_controller.go])

### Summary
`RequiresRunRole` (`core/web/auth/auth.go:202-217`) only validates that `user.Role != UserRoleView`, and `AuthenticateExternalInitiator` grants every EI a synthetic `User{Role: UserRoleRun}` session object [1](#0-0) . `PipelineRunsController.Create` then uses `auth.GetAuthenticatedUser(c)` merely to decide the code path, not to verify which job the EI is bound to, so any authenticated EI can trigger a run on any job ID via `POST /v2/jobs/:ID/runs`.

### Finding Description
The route is registered as `authv2.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))` under the `authv2` group. `RequiresRunRole` performs only a role check (`user.Role == clsessions.UserRoleView` → reject, otherwise allow) with no reference to job ownership or initiator binding [2](#0-1) .

Because `AuthenticateExternalInitiator` sets `SessionUserKey` to a pseudo-`User` with `Role: UserRoleRun` in addition to `SessionExternalInitiatorKey` [3](#0-2) , an EI credential passes `RequiresRunRole` identically to a real "run"-role user.

Inside `PipelineRunsController.Create`, the code checks `_, isUser := auth.GetAuthenticatedUser(c)` and, if true, parses the `:ID` path param as an `int32` job ID and calls `prc.App.RunJobV2(ctx, jobID, nil)` directly — with no lookup of `bridges.ExternalInitiator` or any check that the job's webhook spec references that initiator's name [4](#0-3) . The comment "only users are allowed to run jobs using int IDs - EIs not allowed" reflects an intended restriction that is defeated in practice, since `isUser` is `true` for any EI-authenticated request (the EI's session object satisfies `GetAuthenticatedUser`). No code path in `Create`, `RequiresRunRole`, or `RunJobV2` cross-checks the external initiator identity (`ei.Name`) against the target job's webhook spec.

### Impact Explanation
An EI credential scoped to one job (e.g., `foo`) can trigger pipeline runs on any other job accessible by numeric ID, regardless of binding — this is an authorization-exactness / request-binding failure enabling unauthorized job-run triggering (potentially initiating on-chain transactions, VRF fulfillments, or other side effects tied to unrelated jobs), corresponding to Chainlink's "unauthorized job run" bounty impact class.

### Likelihood Explanation
Requires only a single valid EI access key/secret (the minimal "run"-equivalent credential) and knowledge/guessing of a numeric job ID; no additional privilege or binding check exists, making this reliably and repeatably exploitable in the current code path.

### Recommendation
In `PipelineRunsController.Create`, when an External Initiator is authenticated (`auth.GetAuthenticatedExternalInitiator`), verify that the target job's spec (webhook) is actually associated with that initiator's `Name`/ID before invoking `RunJobV2`, and reject with `403` otherwise. Additionally, distinguish real users from EI-derived pseudo-users so the "EIs not allowed to use int IDs" comment's intent is actually enforced (e.g., check `auth.GetAuthenticatedExternalInitiator` presence first).

### Proof of Concept
1. Create job `J1` (webhook type) bound to external initiator `foo`.
2. Create unrelated job `J2` (webhook or any other run-able job type).
3. Create EI `foo` with valid access key/secret.
4. Authenticate as EI `foo` via `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers.
5. `POST /v2/jobs/:J2.ID/runs` using EI `foo`'s credentials.
6. Assert HTTP 200 and that a pipeline run record for `J2` is created — proving EI `foo` triggered a run on a job it has no relation to.
7. Contrast with expected behavior: request should be rejected with 403/422 since `foo` is not bound to `J2`.

```go
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
