### Title
Loss-adjusted withdraw receipts are paid at par once the user makes a later withdraw request — `lastWithdrawRequest` overwrite orphans `lossRecoveryPriceByEpoch` claim — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the Neptune Mutual report where finalization reset a global marker (resolution deadline → 0) and broke later unstakes, `IdleCreditVault._claimLossAdjustedWithdrawRequest` locates a user's loss-adjusted receipt solely through the single global marker `lastWithdrawRequest[_user]`. A new `requestWithdraw` overwrites that marker with the new epoch. Since `lossRecoveryPriceByEpoch[newEpoch]` is 0, the haircutted receipt is never routed through the loss-adjusted path and is instead paid at par by `_claimFundedWithdrawRequest`, which settles the aggregate `withdrawsRequests[_user]` in full.

### Finding Description
When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` stores the haircut in `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws` [1](#0-0) . The user is expected to later claim `claimBasis * lossRecoveryPrice` via `_claimLossAdjustedWithdrawRequest`, which looks up the loss epoch via `lastWithdrawRequest[_user]` [2](#0-1) .

However, `requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` and adds the new principal to the aggregate `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` [3](#0-2) . The old per-epoch entry `withdrawsRequestsByEpoch[user][lossEpoch]` is never removed from the aggregate `withdrawsRequests[user]` — it is only decremented inside `_clearWithdrawClaimForEpoch`, which runs only when the loss path is entered [4](#0-3) .

Sequence (fixed-APR mode, buffer phase after a lossy stop):

1. User requests withdraw in epoch N → receipt minted, `lastWithdrawRequest[user] = N`.
2. `stopEpochWithDuration(apr, interest, dur, loss)` funds `pendingToFund < pendingBasis`; `lossRecoveryPriceByEpoch[N] = p < 1e18` (loss split per `previewLossAdjustedWithdrawFunds` [5](#0-4) ).
3. In the new buffer phase (`allowAAWithdrawRequest` re-enabled), user calls `requestWithdraw` again → `lastWithdrawRequest[user] = N+1`; aggregate grows.
4. After epoch N+1 ends, `claimWithdrawRequest` runs: `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[N+1] == 0` and returns 0 [6](#0-5) ; the gating check `epochNumber <= lastWithdrawRequest` passes, so `_claimFundedWithdrawRequest` pays the full aggregate `withdrawsRequests[user]` — including the haircutted epoch-N basis — at par [7](#0-6) .

### Impact Explanation
The user extracts `claimBasis * (1 - lossRecoveryPrice)` more than funded for epoch N. The strategy only received `pendingToFund` underlying for those receipts; the excess is paid from strategy underlyings backing other claimants' funded receipts or active CDO value. This is direct theft of the realized-loss haircut: the loss that `stopEpochWithDuration` deliberately assigned to pending receipts is transferred back onto remaining LPs/other withdrawers, and if the strategy balance is insufficient the last claimants' `_transferFundedClaim` reverts (permanent freezing of their claims). Loss scales with the haircutted basis × (1 − recovery price); e.g. a 100k receipt at 70% recovery yields a ~30k excess payout.

### Likelihood Explanation
Requires a `stopEpochWithDuration` with `_lossAmount > 0` while pending withdraws exist (manager action, in scope as honest-but-possible sequencing), then the user simply making a second withdraw request in a later epoch — a routine user action with no privileged assumption. Any lender can trigger it; no KYC bypass or privileged role needed.

### Recommendation
Track loss-adjusted claims per request epoch instead of through the single `lastWithdrawRequest` marker — e.g. iterate `lossRecoveryPriceByEpoch` entries for the user or store a per-user loss-epoch mapping — so a later request cannot orphan the haircut. Alternatively, settle all open receipts (or revert) inside `requestWithdraw` when `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0`.

function testLossAdjustedReceiptPaidAtParAfterNewRequest() external {
    // 1. user deposits, epoch 0 runs
    _depositWithUser(user, 100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // 2. buffer: user requests withdraw of all tranches (epoch 1)
    vm.prank(user);
    cdoEpoch.requestWithdraw(AAtranche.balanceOf(user), address(AAtranche));
    uint256 basis = strategy.withdrawsRequests(user);
    assertEq(strategy.lastWithdrawRequest(user), strategy.epochNumber());

    // 3. epoch 1 runs; stopEpochWithDuration realizes a loss so receipts are haircut
    _startEpochAndCheckPrices(1);
    uint256 loss = basis / 4; // 25% loss on pending side
    _fundBorrowerAndStopWithLoss(loss); // borrower approves pendingToFund only
    uint256 price = strategy.lossRecoveryPriceByEpoch(strategy.epochNumber());
    assertLt(price, 1e18);

    // 4. new buffer: user makes a second tiny request -> overwrites lastWithdrawRequest
    _depositWithUser(user, ONE_SCALE, true);
    vm.prank(user);
    cdoEpoch.requestWithdraw(ONE_SCALE, address(AAtranche));

    // 5. after one more epoch, claim pays epoch-1 basis at PAR, not at `price`
    _startEpochAndCheckPrices(2);
    _stopEpochAndCheckPrices(2, initialProvidedApr, _expectedFundsEndEpoch());
    uint256 pre = underlying.balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    // BUG: received basis (par) instead of basis * price / 1e18
    assertGt(underlying.balanceOf(user) - pre, basis * price / 1e18);
}

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }
