### Title
Reject-then-accept flip lets a single signer's weight be counted in both `total_weight_approved` and `total_weight_rejected` — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`BlockStatus` (miner-side tally in `StackerDBListener`) guards duplicate weight accounting on the *rejection* path using the `responded_signers` set, but the *acceptance* path guards duplicate weight accounting using a different, disjoint field (`gathered_signatures`). Because a signer's slot id can be present in `responded_signers` (via a prior rejection) without being present in `gathered_signatures`, a legitimate later `Accepted` message from that same signer is treated as "not yet counted" and adds the signer's weight to `total_weight_approved` a second time, even though that signer's weight already contributed to `total_weight_rejected`. This is the exact analog of the Union Finance bug: one array/counter (`vouchees`/rejections) is bounds/dedup-checked, the symmetric one (`vouchers`/approvals) is not checked against the same guard, letting the same actor's contribution be double-registered across both sides of an invariant that is supposed to partition weight. [1](#0-0) 

### Finding Description
`BlockStatus` tracks, per proposed block: `responded_signers` (a `HashSet<u32>` of slot ids that have answered at all), `gathered_signatures` (a `BTreeMap<u32, MessageSignature>` of slot ids that have signed), `total_weight_approved`, and `total_weight_rejected`. [1](#0-0) 

On the `Accepted` branch, the dedup guard before adding weight is `!block.gathered_signatures.contains_key(&slot_id)`; only after that does the code do `block.gathered_signatures.insert(...)` and `block.responded_signers.insert(slot_id)`: [2](#0-1) 

On the `Rejected` branch, the dedup guard is `block.responded_signers.insert(slot_id)` (true only the first time this slot id is seen at all), and only in that case is `total_weight_rejected` incremented: [3](#0-2) 

The two guards are checked against different collections. If a signer's first message for this block is a `Rejected`, its slot id is inserted into `responded_signers` but *not* into `gathered_signatures`. If that same signer later sends an `Accepted` message for the same block hash (a normal, permitted state-machine transition — the docs and signer code explicitly allow a signer to reconsider and sign after an earlier rejection, e.g. once "the reason I rejected has since gone away"), the `Accepted` branch's check `!block.gathered_signatures.contains_key(&slot_id)` is still true, so `total_weight_approved` is incremented by that signer's weight — while `total_weight_rejected` still retains the weight from the earlier rejection. The signer's weight now counts on *both* sides of the tally simultaneously.

This breaks the invariant the coordinator relies on: that `total_weight_approved` and `total_weight_rejected` are disjoint contributions from distinct signers, bounded by `total_weight`. Both `signer_coordinator.rs::get_block_status` (the miner-side threshold logic) and this listener's own `cvar.notify_all()` triggers depend on that disjointness holding. [4](#0-3) 

### Impact Explanation
This directly parallels the report's impact class "rejection recounted as an accept": a rejection's weight is not excluded from also counting as an acceptance for the same signer. Consequences on the miner/coordinator side:
- `total_weight_approved` can cross `self.weight_threshold` (70%) using less genuinely-distinct approving weight than required, because one signer's weight is double counted (once under rejected, once under approved). This can make the coordinator falsely believe the acceptance threshold was reached (`block.total_weight_approved >= self.weight_threshold` at line 467, and the equivalent check in `signer_coordinator.rs`), triggering an early/incorrect decision to gather and push signatures.
- Symmetrically, since `total_weight_rejected` is unaffected in the other direction (once counted there it stays), a flip from reject→accept does not remove the double-counted weight from the reject side either, so the same event can simultaneously push both `total_weight_approved` toward "accepted" and keep `total_weight_rejected` inflated toward the "blocking minority" (>30%) rejection threshold used in `signer_coordinator.rs` (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`), which aborts the miner's attempt and can wedge legitimate block production (a liveness impact matching the "signer wedged into never signing valid blocks" / node giving up on a proposable block prematurely).

Because the final on-chain acceptance is independently re-verified by `NakamotoBlockHeader::verify_signer_signatures`, which recomputes weight strictly from distinct recovered public keys in the block's `signer_signature` vector, this bug does not by itself let an actually-invalid/under-signed block get accepted on chain — the impact is confined to the miner-local coordinator's tally, causing incorrect premature decisions (false "reached threshold", false "block rejected") rather than a chain-level equivocation. [5](#0-4) 

### Likelihood Explanation
The reject→accept transition for the *same block hash* by the *same signer* is a normal, documented behavior of the v0 signer state machine (a signer may reconsider and sign after a rival dies out or a reject reason clears), so no majority collusion or malicious signer is strictly required to trigger the double count — it can occur under ordinary network conditions whenever a signer's local view changes between its first and second message for a block. A signer wishing to actively grief the tally can trivially reproduce this by broadcasting a `Rejected` then later an `Accepted` message for the same `signer_signature_hash`, without needing another signer's key or a majority.

### Recommendation
Use a single, unified per-signer "already accounted" tracking structure (or check both `responded_signers` presence in the *and* which side previously counted) before incrementing either `total_weight_approved` or `total_weight_rejected`, mirroring what the Union Finance fix does: apply the same bound/dedup check symmetrically to both collections. Concretely, on the `Accepted` path, guard weight-add on `!block.responded_signers.contains(&slot_id)` (matching the `Rejected` path's semantics) instead of `gathered_signatures`, or track a `HashMap<u32, bool /* accepted */>` so a flip clears the previous side's weight before adding to the new side.

### Proof of Concept
1. Coordinator proposes block `B` to signer set with weight_threshold = 70% of total_weight.
2. Signer `S` (slot id `k`, weight `w`) sends `BlockResponse::Rejected` for `B`. In `stackerdb_listener.rs`, `block.responded_signers.insert(k)` returns `true` → `total_weight_rejected += w`.
3. Signer `S` later reconsiders (permitted transition) and sends `BlockResponse::Accepted` for the same `signer_signature_hash`. `block.gathered_signatures.contains_key(&k)` is `false` (never inserted) → `total_weight_approved += w` is applied.
4. Now `total_weight_approved` and `total_weight_rejected` both include `w` from the same signer `S`, i.e., the sum of the two tallies exceeds the sum of distinct signer weights that actually responded, breaking the disjointness invariant the 70%/30% thresholds in `signer_coordinator.rs::get_block_status` rely on. [6](#0-5)
