### Title
Builder payment quorum uses a `total_active_balance` recomputed at epoch-processing time instead of the balance in effect while PTC weight was accumulated - (File: `specs/gloas/beacon-chain.md`)

### Summary
`get_builder_payment_quorum_threshold` recomputes the quorum denominator from the *current* `get_total_active_balance(state)` every time `process_builder_pending_payments` runs, instead of using the active-balance snapshot that existed while the payload-timeliness-committee (PTC) votes that produced `payment.weight` were being accumulated slot-by-slot during the epoch. This mirrors the Maia governance bug: the acceptance threshold for a "proposal" (here, a builder payment) is measured against a total that keeps moving after the votes contributing to it were already cast.

### Finding Description
`payment.weight` for each `BuilderPendingPayment` is built up incrementally, slot by slot, from PTC attestations processed during block processing throughout the epoch (each PTC member's effective balance is added when its vote is counted). At the end of the epoch, `process_builder_pending_payments` decides which payments clear the bar by comparing this pre-accumulated `weight` against a quorum computed fresh at that moment: [1](#0-0) 

```python
def get_builder_payment_quorum_threshold(state: BeaconState) -> Uint64:
    per_slot_balance = get_total_active_balance(state) // Uint64(SLOTS_PER_EPOCH)
    quorum = per_slot_balance * BUILDER_PAYMENT_THRESHOLD_NUMERATOR
    return Uint64(quorum // BUILDER_PAYMENT_THRESHOLD_DENOMINATOR)

`get_total_active_balance` derives from `get_active_validator_indices(state, get_current_epoch(state))` and each validator's `effective_balance`, both of which are mutated during the same epoch-processing pass (registry updates, effective-balance updates, and — per the file's function ordering — pending-deposit processing, which is defined immediately before `process_builder_pending_payments`): [3](#0-2) [4](#0-3) 

Because `total_active_balance` is not fixed at the moment the PTC weight was accumulated (each vote's contribution was recorded against the active-balance distribution *of that slot*), but is instead re-derived from the state as it stands at the end-of-epoch processing step — after that same epoch's deposit/effective-balance/registry mutations have already been applied — the denominator used to gate `builder_pending_withdrawals` can shift up or down relative to what actually backed the votes throughout the epoch. This is the same equality violation as the C4 finding: `threshold = f(current mutable total)` instead of `threshold = f(total at accumulation time)`.

### Impact Explanation
If `total_active_balance` grows between when the PTC votes were cast and when quorum is evaluated (e.g., effective-balance top-ups from pending deposits processed in the same epoch-boundary transition, per the ordering seen at lines 1652–1664), a payment that legitimately garnered ≥2/3 support of the actual voting power present during the epoch can fail to clear the quorum and its withdrawal escapes being queued — a builder payment silently dropped that the vote record shows should have been paid. Conversely, if `total_active_balance` shrinks (exits/slashings finalized in the same pass), a payment with insufficient real-time support could clear an artificially lowered bar and get paid. Both cases fall in the "a builder payment or withdrawal misdirected, doubled, or escaped" High-impact category, since it is a state-transition-level inconsistency reachable by any set of spec-following validators/proposers under normal deposit/exit activity — no coalition or client bug required.

### Likelihood Explanation
This requires no adversarial coalition: any epoch in which deposits, activations, or exits are processed in the same epoch-boundary transition as `process_builder_pending_payments` — which is the ordinary case whenever there is churn — produces a mismatch between the balance basis used during vote accumulation and the balance basis used at quorum-check time. The magnitude of the mismatch scales with the amount of deposit/exit activity in that epoch, so it is more of a "quiet inconsistency" than a large one-off attack, but it is deterministically reachable in normal operation, not merely theoretical.

### Recommendation
Snapshot `total_active_balance` (or the per-slot quorum threshold) at the *start* of the epoch — before any deposit/effective-balance/registry mutation for that epoch is applied — and store it (e.g., in a new state field or computed once and reused) so that `get_builder_payment_quorum_threshold` compares `payment.weight` against the same balance basis that was in effect while the PTC votes contributing to `weight` were being cast, analogous to snapshotting `totalSupply` at proposal-creation time in the referenced report's recommended fix.

### Proof of Concept
1. At the start of epoch `N`, `get_total_active_balance(state) = B0`; PTC votes for `builder_pending_payments[0]` accumulate `weight = W` over the epoch, where `W` represents e.g. 2/3 of `B0`'s per-slot share — enough to clear quorum based on `B0`.
2. During the same epoch-processing pass (per the function ordering in `specs/gloas/beacon-chain.md`, pending-deposit processing runs immediately before `process_builder_pending_payments`), several large deposits are processed, increasing effective balances and therefore `get_total_active_balance(state)` to `B1 > B0`.
3. `process_builder_pending_payments` now calls `get_builder_payment_quorum_threshold(state)` using `B1`, producing a higher quorum than the one `W` was actually measured against throughout the epoch.
4. `payment.weight (W) < quorum(B1)`, so the withdrawal is dropped even though `W` represented sufficient support relative to the balance distribution (`B0`) that existed while votes were being collected — the payment "escapes" without payment, despite having earned the required real-time support.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
