### Title
Vault-user-triggered permanent `stopEpoch` revert via unguarded ERC4626 valuation calls freezes all epoch funds - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStopEpoch` performs uncached, uncaught calls into the configured ERC4626 vault (`_currentVaultAssets()` → `convertToAssets`/`maxWithdraw`-style views) at multiple points in the stop flow, and `totalInterestDueNow` → `_vaultNetInterest` does the same before it. A vault depositor who can push the ERC4626 vault into a state where `convertToAssets` reverts (or `vault.withdraw` permanently fails while shares still "cover" the shortfall on the fallback path) makes `stopEpoch`/`stopEpochWithDuration` revert every time. Because the revert bubbles out of `onStopEpoch` before the `return false` default branch is reachable, IdleCDO can neither stop the epoch nor invoke `_handleBorrowerDefault`, permanently freezing LP principal and pending withdrawal receipts. This is the direct analog of CVE-2018-6540: a crafted external input (malformed zip / manipulated vault state) crashes a read routine (`zzip_disk_findfirst` / `_currentVaultAssets`), producing denial of service with no error-handling path.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch`, the programmable-borrower hook result is the sole gate between normal settlement and default handling: only a `false` return triggers `_handleBorrowerDefault`, while a revert propagates and aborts the whole stop [1](#0-0) .

Inside `ProgrammableBorrower.onStopEpoch`, two valuation reads of the external vault happen **outside** any `try/catch`:
- `shortfall > _currentVaultAssets()` before the withdrawal attempt [2](#0-1) 
- `bufferStartVaultAssets = _currentVaultAssets()` after a successful withdraw [3](#0-2) 

Only `vault.withdraw` is wrapped in `try/catch`, and even that failure is converted into `revert StopEpochVaultLiquidityUnavailable()` which still bubbles to IdleCDO. The same untrusted valuation is consumed earlier through `totalInterestDueNow` → `_vaultNetInterest` → `_currentVaultAssets` [4](#0-3) .

An unprivileged depositor of the configured ERC4626 vault (an in-scope attacker per the rules: "a user of the programmable borrower's ERC4626 vault") can craft vault state — e.g., share/price manipulation or direct asset donation that drives `convertToAssets` into a reverting path (mulDiv overflow on an inflated `totalAssets`, or a vault whose `maxWithdraw`/`withdraw` permanently fails for the borrower's position while `convertToAssets` still reports coverage). Every subsequent `stopEpoch` call reverts at the same point. There is no timeout, no owner fallback that bypasses the hook, and `_beforeUnpause` blocks recovery paths while `isEpochRunning` is true [5](#0-4) .

### Impact Explanation
All tranche-holder principal parked in the programmable borrower (vault shares plus on-hand underlying) and all pending withdrawal receipts in `IdleCreditVault` are permanently frozen: `isEpochRunning` stays true forever, deposits and withdraw requests stay disabled (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` were cleared at `startEpoch`), `_beforeUnpause` reverts on `isEpochRunning`, and `claimWithdrawRequest` can never satisfy the `epochNumber > lastWithdrawRequest` gate because `epochNumber` only increments inside the now-unreachable successful stop. Broken invariant: liveness of the epoch state machine and one-receipt-one-payout. Loss equals the full NAV of the vault sleeve plus the borrower's on-hand balance at stop time (in a live deployment, the entire pool TVL routed through the programmable borrower).

### Likelihood Explanation
Requires a programmable-borrower deployment whose configured ERC4626 vault exposes a revert path reachable by a permissionless depositor (donation-driven `convertToAssets` overflow, or a `withdraw`/`maxWithdraw` mismatch where shares report coverage but redemption permanently fails). This needs no privileged role, no borrower collusion, and only standard ERC4626 interactions by the attacker. The codebase itself acknowledges the hazard — `onDefault` explicitly avoids `convertToAssets` because "the external vault's valuation view is unavailable during stress" [6](#0-5)  — but the same hardening was not applied to the stop-path reads. Medium likelihood conditional on the vault exposing a revertable state; impact is total.

### Recommendation
Wrap every external vault read in `onStopEpoch` (`_currentVaultAssets()` calls and the `vault.withdraw` block) and in the `totalInterestDueNow` consumption path in `try/catch`. On valuation failure, treat it as an unsuccessful stop (return `false` so IdleCDO takes `_handleBorrowerDefault`) rather than bubbling, or add a manager-only escape that stops the epoch using the last snapshot (`epochStartVaultAssets`/`epochWithdrawnFromVault`) without consulting the vault — mirroring the hardening already present in `onDefault`. Optionally bound `convertToAssets` results against recorded shares.

### Proof of Concept
Foundry fork PoC (programmable-borrower deployment, e.g. the MetaMorpho vault used in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
// 1. Pool set up with isProgrammableBorrower = true, isInterestMinted = true.
idleCDO.depositAA(10_000e6);
vm.prank(manager);
cdoEpoch.startEpoch();            // funds parked into external ERC4626 vault

// 2. Attacker = unprivileged vault depositor. Craft vault state so that
//    convertToAssets() reverts for any balance (e.g., donate to push
//    totalAssets * shares over uint256, or drive the vault into a state
//    where its withdraw/valuation path reverts for the borrower's position).
underlying.transfer(address(vault), ATTACKER_DONATION);   // crafted "zip file"
// or: attacker deposit pattern that wedges vault.withdraw while
// convertToAssets still reports coverage.

// 3. Epoch matures. Manager tries to stop — reverts in
//    ProgrammableBorrower.onStopEpoch at the uncaught _currentVaultAssets()
//    read (line ~245), before the `return false` default branch is reachable.
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.expectRevert();                 // bubbles out of onStopEpoch
vm.prank(manager);
cdoEpoch.stopEpoch(0, 0);

// 4. Default path is unreachable too: the revert precedes _handleBorrowerDefault.
assertTrue(cdoEpoch.isEpochRunning());
assertFalse(cdoEpoch.defaulted());

// 5. Recovery blocked: unpause reverts because isEpochRunning is still true
//    (_beforeUnpause). All withdraw receipts and LP principal are frozen.
vm.expectRevert(NotAllowed.selector);
cdoEpoch.unpause();
```

Every retry hits the same revert, matching CVE-2018-6540's profile: one crafted external artifact reliably crashes the read routine with no recovery branch — here the crash permanently locks pool funds instead of merely crashing a parser.

  function totalInterestDueNow() external view returns (uint256) {
    (uint256 vaultInterest, uint256 loss) = _vaultNetInterest();
    uint256 totalGain = vaultInterest + borrowerInterestAccruedNow() + bufferInterest;
    return totalGain > loss ? totalGain - loss : 0;
  }

  /// @notice Compute the net vault delta split into interest and loss (mutually exclusive).
  function _vaultNetInterest() internal view returns (uint256 interest, uint256 loss) {
    if (!epochAccountingActive) return (0, 0);
    uint256 earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault;
    uint256 principalAssets = epochStartVaultAssets + epochDepositedToVault;
    int256 netDelta = bufferedVaultDelta + int256(earnedAssets) - int256(principalAssets);
    if (netDelta > 0) {
      interest = uint256(netDelta);
    } else {
      loss = uint256(-netDelta);
    }
  }
