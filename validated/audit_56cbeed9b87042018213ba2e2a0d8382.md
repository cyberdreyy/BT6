### Title
Attacker-chosen `MessageId` collides with a victim's in-flight callback, enabling gateway response hijack - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`ValidatedMessageFromReq`/`DecodeJSONRequest` copy the JSON-RPC envelope `ID` directly into `m.Body.MessageId` with only length/charset checks, and nothing binds that ID to the caller's identity or enforces uniqueness. `capabilities.handler.HandleLegacyUserMessage` then unconditionally overwrites `h.savedCallbacks[msg.Body.MessageId]` with the new caller's callback, so a second signed request using a known/predictable victim `MessageId` silently replaces the victim's pending callback entry, and the eventual DON response is delivered to the attacker's callback instead of the victim's.

### Finding Description
`ValidatedMessageFromReq` sets `m.Body.MessageId = req.ID` [1](#0-0)  and `Message.Validate()` only checks length/format of `MessageId`, not uniqueness or binding to a specific caller [2](#0-1) . The same pattern exists in the primary legacy-decode path `JsonRPCCodec.DecodeJSONRequest`, which also assigns `msg.Body.MessageId = request.ID` before any handler-level check [3](#0-2) .

The signature verification in `ExtractSigner`/`Sign` does cover `MessageId` as part of the signed payload [4](#0-3) , so an attacker cannot forge a *victim's* signature. However, this does not prevent the attack: the attacker signs their *own* message and simply chooses `req.ID`/`message_id` equal to the victim's known in-flight ID. Since `MessageId` values are entirely user-supplied and there is no cross-request allowlisting of senders on this legacy path (explicitly marked as an unimplemented `TODO: apply allowlist and rate-limiting here`) [5](#0-4) , any unauthenticated caller with a valid keypair can submit such a request.

`HandleLegacyUserMessage` then stores the callback keyed only by `MessageId`, with no existence check before overwriting: [6](#0-5) 

If a victim's request with `MessageId = X` is still pending (its `savedCallbacks[X]` entry not yet consumed), the attacker's request with the same `X` overwrites that map entry with the attacker's own `savedCallback`. When a DON node responds with `MessageId = X` (from either the victim's or attacker's forwarded request, both carrying identical `X`), `handleWebAPITriggerMessage` looks up `savedCallbacks[X]`, finds the current (attacker-owned) entry, deletes it, and delivers the response through it: [7](#0-6) 

The identical pattern exists in `handlers.dummyHandler` [8](#0-7) .

### Impact Explanation
This breaks per-request callback isolation between users of the gateway: an attacker can hijack the response meant for a victim's outstanding `web_api_trigger`/`web_api_target`/`compute_action`/`workflow_syncer` request, receiving whatever payload the DON node returns for that request (potential data/response disclosure), and/or cause the victim's request to never complete (denial of service for that specific in-flight call). This matches the "cross-user response confusion" / request-impersonation impact class.

### Likelihood Explanation
The attacker needs only: (1) the ability to send a signed gateway JSON-RPC request (any keypair works — no allowlist enforced on this path, confirmed by the outstanding TODO in the handler), and (2) knowledge or a correct guess of a victim's pending `MessageId`. `MessageId` is client-chosen and only bounded by length (max 128 bytes) with no entropy or uniqueness requirement, so if a caller uses predictable/sequential/short IDs, collision is trivial; even with less predictable IDs, the race window is the full callback lifetime (`CallbackMaxAgeSec`, default 120s) during which the map entry can be overwritten by anyone who learns the ID (e.g., via logs, timing, or a shared/observable ID scheme).

### Recommendation
- Bind `savedCallbacks` entries to sender identity in addition to `MessageId` (e.g., key by `(sender, MessageId)` or generate/attach a gateway-internal opaque correlation ID rather than trusting caller-supplied `MessageId`).
- In `HandleLegacyUserMessage`, reject (or return an explicit collision error for) requests whose `MessageId` already has a live entry in `savedCallbacks` instead of silently overwriting it.
- Implement the still-outstanding sender allowlist/authorization check noted in the `TODO` before accepting legacy user messages.

### Proof of Concept
Go handler-level integration test (extending `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Sign and submit `victimMsg` (`MessageId = "shared-id"`, signed by `victimKey`) via `handler.HandleLegacyUserMessage`, capture `victimCallback`; assert `handler.savedCallbacks["shared-id"].Callback == victimCallback`.
2. Before the victim's DON response arrives, sign and submit `attackerMsg` (`MessageId = "shared-id"`, signed by an unrelated `attackerKey`) via `handler.HandleLegacyUserMessage`, capture `attackerCallback`.
3. Assert `handler.savedCallbacks["shared-id"].Callback == attackerCallback` (i.e., the victim's entry was overwritten).
4. Simulate a DON node response for `MessageId = "shared-id"` via `handler.HandleNodeMessage`; assert that `attackerCallback.Wait(ctx)` receives the response and `victimCallback.Wait(ctx)` times out/never resolves, proving cross-user response hijack.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

// Message signatures are over the following data:
//  1. MessageId aligned to 128 bytes
//  2. Method aligned to 64 bytes
//  3. DonId aligned to 64 bytes
//  4. Receiver (in hex) aligned to 42 bytes
//  5. Payload (raw bytes before parsing)
func (m *Message) Sign(privateKey *ecdsa.PrivateKey) error {
	if m == nil {
		return errors.New("nil message")
	}
	rawData := GetRawMessageBody(&m.Body)
	signature, err := gw_common.SignData(privateKey, rawData...)
	if err != nil {
		return err
	}
	m.Signature = utils.StringToHex(string(signature))
	m.Body.Sender = strings.ToLower(crypto.PubkeyToAddress(privateKey.PublicKey).Hex())
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
