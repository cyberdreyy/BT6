### Title
Cross-user response confusion via shared `MessageId` key in `dummyHandler.savedCallbacks` - ([File: core/services/gateway/handlers/handler.dummy.go])

### Summary
`dummyHandler.HandleLegacyUserMessage` and `HandleJSONRPCUserMessage` key the shared `d.savedCallbacks` map solely on `msg.Body.MessageId`, a value that is fully attacker-controlled per-request and never scoped to the requesting sender. Any two signed-but-mutually-untrusted senders can pick the same `MessageId`, causing one user's `Callback` to overwrite another's before a response arrives, so `HandleNodeMessage` (which also only keys off `resp.ID`) can deliver one user's response to the other user's `Callback.SendResponse`.

### Finding Description
`ProcessRequest` in `core/services/gateway/gateway.go` accepts any signed message from any client, only validating message structure/signature (`msg.Validate()`) and `len(jsonRequest.ID) <= 200`, with no cross-request uniqueness check on the ID. [1](#0-0)  `MessageId`/`jsonRequest.ID` is attacker-chosen and used verbatim as the map key in `dummyHandler.HandleLegacyUserMessage`:
```go
d.savedCallbacks[msg.Body.MessageId] = &savedCallback{msg.Body.MessageId, callback}
``` [2](#0-1) 

`HandleJSONRPCUserMessage` derives `msg.Body.MessageId` directly from `jsonRequest.ID`, which is also attacker-supplied: [3](#0-2) 

`api.Message.Validate()` only checks length/format of `MessageId`, not global uniqueness or per-sender scoping; the sender identity is only recorded separately as `Body.Sender` and is never combined with `MessageId` to form the map key. [4](#0-3) 

When `HandleNodeMessage` receives a DON response, it looks the callback up purely by `resp.ID` (echoed back as `msg.Body.MessageId`) and resolves whichever `Callback` is currently registered under that key, then deletes the entry:
```go
d.mu.Lock()
savedCb, found := d.savedCallbacks[msg.Body.MessageId]
delete(d.savedCallbacks, msg.Body.MessageId)
d.mu.Unlock()
if found {
    return savedCb.SendResponse(...)
}
``` [5](#0-4) 

The only sender-related check present is `nodeAddr != msg.Body.Sender` at line 95-97, but this validates the *DON node's* identity against the field embedded in its own response — it does not verify that the response corresponds to the original *user's* request or match it to the specific `savedCallback`'s originating sender. [6](#0-5) 

Exploit flow:
1. User A sends a legacy/JSON-RPC request through the gateway HTTP endpoint with `MessageId = X` (attacker-chosen). `ProcessRequest` calls `dummyHandler.HandleLegacyUserMessage`, which stores `savedCallbacks[X] = callback_A` and forwards the request to DON nodes.
2. Before a response arrives, User B (a different signer, unrelated to A) sends a request with the same `MessageId = X`. This overwrites `savedCallbacks[X] = callback_B`.
3. When any DON node responds with `resp.ID = X` (whether it is actually replying to A's forwarded request or B's), `HandleNodeMessage` resolves whatever entry currently sits at `savedCallbacks[X]` and delivers the response to it — cross-wiring A's response to B's `Callback.SendResponse`, or vice versa, and permanently losing the other user's callback (which will hang until gateway-level timeout).

This is reachable by any unauthenticated-but-signed gateway client; the only "credential" needed is a valid ECDSA keypair to sign an arbitrary message, which is available to any external actor.

### Impact Explanation
This is cross-user response confusion / request-response mismatch: an attacker can cause the gateway to deliver another user's job/workflow-related response payload to the attacker's own connection (or vice versa), and can reliably deny service to a victim's request by evicting their callback registration. This matches the "cross-user response confusion" bounty impact class explicitly called out in the audit scope. Because `dummyHandler` is used for the `DummyHandlerType` handler wired via `handler_factory.go`'s `NewHandler` (`case DummyHandlerType: return handlers.NewDummyHandler(...)`), it is real production code path, not test-only, though its usage in deployed configs (`sample_config.toml`) suggests it is intended as a minimal/reference/test handler rather than a primary production handler. [7](#0-6) 

### Likelihood Explanation
Any signed gateway client (no special role or allowlist entry required beyond having a keypair able to produce a valid `Message.Sign`) can trigger this by simply choosing a colliding `MessageId`. The race window is the round-trip time to the DON and back, which is generally on the order of seconds — easily won by an attacker who deliberately sends a second request with the same ID immediately after observing/guessing a victim's ID (IDs are attacker/client chosen and not randomized/enforced-unique by the gateway), or simply by using a fixed constant ID for their own repeated requests, colliding with any other tenant that also uses the DummyHandler with predictable/default IDs.

### Recommendation
Scope `savedCallbacks` keys to `(Body.Sender, MessageId)` instead of `MessageId` alone, so requests from different senders cannot collide, mirroring how `handlers/capabilities/handler.go`'s `HandleLegacyUserMessage` should also be checked for the same key-collision risk. Additionally, reject a `HandleLegacyUserMessage`/`HandleJSONRPCUserMessage` call if an entry for the same key is already pending (rather than silently overwriting), and verify in `HandleNodeMessage` that the resolved `savedCb`'s original sender matches the expected DON member policy for that request.

### Proof of Concept
Go table test in `core/services/gateway/handlers/handler.dummy_test.go`:
1. Construct two `api.Message`s, `msgA` and `msgB`, signed by two different ECDSA keys, both with `Body.MessageId = "X"` and same `DonId`/`Method`.
2. Create two `Callback` instances (e.g., `handlerscommon.NewCallback()`), `cbA` and `cbB`.
3. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)`, then immediately `handler.HandleLegacyUserMessage(ctx, msgB, cbB)` (simulating the race — no response processed in between).
4. Assert `d.savedCallbacks["X"].Callback == cbB` (i.e., `cbA` was silently evicted) via reflection/internal field access or by proceeding to step 5.
5. Simulate a node response for ID `X` — build a `jsonrpc.Response` with `ID:"X"` and `Result` containing a validly signed `api.Message` from a DON member — and call `handler.HandleNodeMessage(ctx, resp, nodeAddr)`.
6. Assert that `cbB.Wait(ctx)` receives the response (unexpectedly, since it was never the request that produced this particular DON response) while `cbA.Wait(ctx)` times out/never resolves, proving that A's original callback was silently dropped/cross-wired.

func (d *dummyHandler) HandleJSONRPCUserMessage(ctx context.Context, jsonRequest jsonrpc.Request[json.RawMessage], callback Callback) error {
	var msg api.Message
	if jsonRequest.Params != nil {
		if err := json.Unmarshal(*jsonRequest.Params, &msg); err != nil {
			return err
		}
	}
	msg.Body.MessageId = jsonRequest.ID
	if msg.Body.Method == "" {
		msg.Body.Method = jsonRequest.Method
	}
	if msg.Body.DonId == "" {
		msg.Body.DonId = d.donConfig.DonId
	}
	return d.HandleLegacyUserMessage(ctx, &msg, callback)

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
