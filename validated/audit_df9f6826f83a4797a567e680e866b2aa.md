### Title
External-initiator credential can trigger arbitrary numeric job runs due to broken user/EI distinction - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` synthesizes a generic `clsessions.User{Role: UserRoleRun}` and stores it under `SessionUserKey` for any valid EI credential, with no job-scoping information attached. `PipelineRunsController.Create` then uses `auth.GetAuthenticatedUser(c)` to decide whether the caller is allowed to trigger numeric job IDs ("EIs not allowed"), but that check is defeated because the EI's synthesized session object satisfies `GetAuthenticatedUser`, letting any EI credential trigger any job by numeric ID.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is mounted under a mixed-auth group that accepts `AuthenticateExternalInitiator`, `AuthenticateByToken`, or `AuthenticateBySession`, then wraps the handler with `auth.RequiresRunRole`: [1](#0-0) 

`AuthenticateExternalInitiator` validates the EI access-key/secret against the `external_initiators` table and, on success, unconditionally sets a synthesized `User` object with `Role: UserRoleRun` into the session context — with no reference to which job the EI is associated with: [2](#0-1) 

`RequiresRunRole` merely checks `user.Role != UserRoleView`, which the synthesized user satisfies, so it passes through: [3](#0-2) 

Inside `PipelineRunsController.Create`, the code explicitly comments that "only users are allowed to run jobs using int IDs - EIs not allowed," and gates that using `isUser, _ := auth.GetAuthenticatedUser(c)`: [4](#0-3) 

`GetAuthenticatedUser` simply reads whatever object is stored under `SessionUserKey`: [5](#0-4) 

Because `AuthenticateExternalInitiator` also populates `SessionUserKey`, `isUser` is `true` for EI-authenticated requests too — the intended distinction between "real user" and "external initiator" is broken. The handler then parses the numeric job ID from the URL and calls `prc.App.RunJobV2(ctx, jobID, nil)` with **no check at all** correlating the authenticated EI record (`bridges.ExternalInitiator`, available via `GetAuthenticatedExternalInitiator`) to the requested job ID. There is no `external_initiator_id`-to-job binding enforced on this numeric-ID code path (that binding only existed historically for the now-removed UUID-based webhook trigger flow, per the comment at lines 103–107 of the same file). As a result, any valid EI credential — regardless of which job it was provisioned for — can trigger a run for **any** numeric job ID in the node.

### Impact Explanation
This is an authorization/request-binding bypass: a narrowly-scoped external-initiator credential (intended to trigger only the specific job it was created for) can be used to trigger runs of arbitrary, unrelated jobs on the node by numeric ID. Depending on job type (e.g., transmission or fund-moving pipelines), this can cause unauthorized job execution, resource exhaustion, or unintended on-chain transactions — matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Exploitation only requires possession of any single valid EI access key/secret pair (a commonly distributed, low-privilege credential) and knowledge/guessing of a target job's small integer ID. No admin/session/API-key access is needed. The flow is fully deterministic and repeatable via a simple HTTP POST.

### Recommendation
Distinguish EI-authenticated sessions from real user sessions instead of relying on `GetAuthenticatedUser` returning any object under `SessionUserKey`. Use `GetAuthenticatedExternalInitiator` explicitly in `PipelineRunsController.Create` to detect EI auth and reject numeric-ID triggering for EI-authenticated requests (matching the code's own comment intent), or reintroduce an explicit EI-to-job binding check before calling `RunJobV2`.

### Proof of Concept
Handler-level integration test:
1. Provision two webhook/pipeline jobs, Job A and Job B, with distinct integer IDs.
2. Create an `ExternalInitiator` (EI) record intended for Job A via `bridges.NewExternalInitiator` / `CreateExternalInitiator`, obtaining `AccessKey`/`Secret`.
3. Send `POST /v2/jobs/<JobB-ID>/runs` with headers `X-Chainlink-EA-AccessKey` and `X-Chainlink-EA-Secret` set to the EI's credentials for Job A.
4. Assert the current (vulnerable) behavior: response is `200/201` and a `pipelineRun` for Job B is created — i.e., `prc.App.RunJobV2` was invoked with Job B's ID despite the credential being scoped to Job A.
5. After the fix, assert the request is rejected (e.g., `422`/`401`) because EI-authenticated requests cannot trigger runs via arbitrary numeric IDs.

func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
