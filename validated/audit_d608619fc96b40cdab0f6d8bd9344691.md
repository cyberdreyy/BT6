### Title
Missing sender-to-DON authorization allows unauthenticated attacker to trigger arbitrary DON's WebAPI capability via forged `DonId` in legacy gateway message - ([File: core/services/gateway/handlers/capabilities/handler.go], related: [File: core/services/gateway/gateway.go], [File: core/services/gateway/api/message.go])

### Summary
`gateway.ProcessRequest` routes legacy messages to a handler purely by `msg.Body.DonId` after calling `msg.Validate()`, but `Validate()`/`ExtractSigner()` only confirm the signature is self-consistent with the attacker-chosen `DonId`/payload — it never checks that the recovered signer is actually a member/owner authorized for that specific DON. The downstream `capabilities.handler.HandleLegacyUserMessage` forwards the trigger request to all members of the targeted DON without any sender allowlist check, a gap explicitly marked by a `TODO` in the code.

### Finding Description
In `core/services/gateway/gateway.go` `ProcessRequest` (lines 250-262), when `msg.Body.DonId != ""` the code treats it as a legacy request: it calls `msg.Validate()` and then looks up the handler purely via `g.handlers[msg.Body.DonId]`. [1](#0-0) 

`Message.Validate()` in `core/services/gateway/api/message.go` verifies structural constraints and calls `ExtractSigner()`, which recovers the signer address from the signature over a payload that *includes* `DonId` as one of the signed fields. [2](#0-1) [3](#0-2) 

Because the attacker controls both the message content (including `DonId`) and the private key used to sign it, they can always produce a message that passes `Validate()` for *any* `DonId` value — the signature only proves "this data was signed by this key," not "this key is authorized for this DON." `Validate()` never cross-checks `signerBytes`/`m.Body.Sender` against DON membership.

The handler that receives the routed legacy message, `capabilities.handler.HandleLegacyUserMessage`, explicitly documents this gap: [4](#0-3) 
The comment `// TODO: apply allowlist and rate-limiting here` at line 384 confirms no sender/DON-membership authorization is performed before the request is forwarded to all DON node members: [5](#0-4) 

The corresponding test suite also flags this as an unresolved gap ("TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated"): [6](#0-5) 

Exploit flow: an attacker holding any ECDSA key (no DON membership) crafts a `Message` with `Body.DonId = "<victim-don>"`, `Body.Method = "web_api_trigger"`, and a payload, signs it with `Sign()`/`SignKS()`, and submits it via the gateway HTTP endpoint reaching `ProcessRequest`. `msg.Validate()` succeeds because the signature matches the attacker-forged body. The gateway resolves `g.handlers["<victim-don>"]` and dispatches to that DON's handler, which forwards the trigger to every member node of the victim DON without verifying the sender belongs to that DON's authorized signer/allowlist set.

### Impact Explanation
This is an authorization-exactness violation: an unauthenticated/unaffiliated key holder can invoke another tenant's/DON's `web_api_trigger` handler and have arbitrary trigger payloads delivered to that DON's node set, causing unauthorized workflow trigger events on infrastructure the attacker has no relationship with. This maps to Chainlink's "unauthorized job run" / authorization-bypass impact class, since a legitimate DON's WebAPI trigger capability processes attacker-supplied, cross-tenant data as if it came from an authorized sender.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only any valid ECDSA private key (self-generated, free) and knowledge/guess of a target `DonId` string (DON IDs are often not secret — they may be visible in job specs, documentation, or service configuration). No DON membership, no admin/operator access, and no special credential is required. The attack is fully repeatable and requires only crafting and POSTing a signed JSON-RPC legacy message.

### Recommendation
`Message.Validate()` (or the caller in `ProcessRequest`/handler dispatch) should verify that the recovered signer (`m.Body.Sender`) is an authorized member/owner for the specific `DonId` being targeted before dispatching to that DON's handler — i.e., implement the allowlist/authorization check referenced by the `TODO` in `capabilities/handler.go` before forwarding to DON nodes, rather than relying solely on signature well-formedness.

### Proof of Concept
1. In `gateway_test.go`, configure two DON handlers (`donA`, `donB`) via `newGatewayWithMockHandler`-style setup, each with distinct member node sets.
2. Generate an attacker key not present in either DON's member list.
3. Construct `api.Message{Body: {MessageId, Method: "web_api_trigger", DonId: "donB", Payload}}`, sign with the attacker key via `msg.Sign(attackerKey)`.
4. Call `msg.Validate()` and assert it returns `nil` (proving signature/DonId-forgery passes validation).
5. Submit the message through `gw.ProcessRequest(ctx, encodedReq, "")` targeting `donB`'s handler.
6. Assert (expected-but-currently-failing) that the handler rejects the request due to sender not being authorized for `donB`; instead observe (current behavior) that `HandleLegacyUserMessage` forwards the request to all of `donB`'s member nodes (`don.SendToNode` invoked for each member) despite the attacker never being associated with `donB`.
