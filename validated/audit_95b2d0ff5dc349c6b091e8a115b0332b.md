### Title
Process-group-based kill in `unixKiller` cannot terminate detached (`setsid`) grandchild processes, allowing them to outlive job cancellation and retain access to the reused per-project build directory - ([File: helpers/process/killer_unix.go])

### Summary
`osKillWait.KillAndWait` in `helpers/process/killer.go` delegates termination to `unixKiller.Terminate`/`ForceKill`, which sends `SIGTERM`/`SIGKILL` to `-pid` (the process group of the direct child) rather than to individual descendant processes. A job script that spawns a grandchild via `setsid` (or otherwise re-parents/detaches into a new session) removes that process from the group, so it never receives the termination signal and survives job cancellation, timeout, or completion, regardless of whether `KillAndWait` returns normally through `waitCh` or via the `&KillProcessError{pid}` fallback.

### Finding Description
`unixKiller.getPID()` returns the negative PID of the direct child (`helpers/process/killer_unix.go:50-52`), and both `Terminate()` and `ForceKill()` call `syscall.Kill(pk.getPID(), …)` against that negative PID [1](#0-0) . This relies on the invariant that the shell/custom-executor's direct child process is the leader of a process group that all its descendants share — documented explicitly in `docs/executors/custom.md`: "Any child process that is spawned by the driver also receives the graceful termination process explained above… This is achieved by having the main process set as a process group which all the child processes belong to."

That invariant is attacker-influenceable: a job's shell script is fully attacker-controlled input, and nothing in `executors/shell/shell.go:Run` or `executors/custom/command/command.go:Run` prevents the script from calling `setsid` (directly, via `nohup`/`disown`, or via a small forked helper) to move a background writer process into a new session/process group. Once detached, that grandchild is outside the group targeted by `syscall.Kill(-pid, …)` and is immune to both the graceful `SIGTERM` and the forceful `SIGKILL` sent by `unixKiller`.

`KillAndWait` (`helpers/process/killer.go:66-92`) only observes success via `waitCh`, which fires when `cmd.Wait()` returns for the *direct* child [2](#0-1) . Two failure modes both leave the detached grandchild alive with continued filesystem access to the job's checkout/cache directory:
1. The direct child dies normally from the signal (waitCh fires, `KillAndWait` returns without error) — the setsid'd grandchild is unaffected and keeps running.
2. The direct child itself is unresponsive/dormant (e.g., blocked in an uninterruptible syscall) so neither timer's `waitCh` fires; `KillAndWait` exhausts `gracefulKillTimeout` and `forceKillTimeout` and returns `&KillProcessError{pid}` (`helpers/process/killer.go:88-90`), whose own error message ("likely process is dormant") acknowledges this scenario as a known, unhandled case.

In either case, none of the runner's existing cleanup logic re-scans for or kills orphaned descendants outside the tracked process group; `KillAndWait` is the only termination mechanism invoked from `executors/shell/shell.go:128-132` and `executors/custom/command/command.go:93-96`.

Separately, the build/workspace directory itself is *not* random or job-unique by design: `Build.ProjectUniqueDir`/`StartBuild` derive `BuildDir` deterministically from the project slug (and optionally `ProjectRunnerID`), so consecutive jobs for the same project on the same runner reuse the same checkout path [3](#0-2) [4](#0-3) . This directory reuse is intentional (to support `GIT_STRATEGY=fetch`/incremental checkouts) and not itself a bug, but it is the precondition that turns "an orphan process keeps running" into "the orphan can poison the next job's workspace."

### Impact Explanation
A malicious job author can leave a background process running after their job is reported as cancelled/finished, with continued read/write access to `CI_PROJECT_DIR`/cache paths. Because the next job for the same project (same `ProjectUniqueDir`) reuses that same directory, the orphan can tamper with checked-out source, injected cache, or artifacts staged for a subsequent job run by a different pipeline/user sharing that runner and project, or exfiltrate data written into that directory by the next job before it's git-cleaned. This is a workspace-isolation violation across job boundaries, scoped specifically to the shell/custom executor's directory-reuse model.

### Likelihood Explanation
Exploitation only requires an attacker capable of authoring a `.gitlab-ci.yml` script (an unprivileged CI job author) targeting a shell or custom executor with default (non-Docker) isolation and reused build directories — a common, supported, and default configuration for shell executors. Using `setsid`/double-fork to detach a background writer is a standard, well-known shell technique requiring no special privileges. The only additional condition needed for the `KillProcessError` code path specifically (as opposed to the normal-return path) is that the direct child also fails to die from the sent signals, which is a secondary aggravating factor rather than a strict precondition for the core issue — the orphaned grandchild escapes cleanup either way.

### Recommendation
Do not rely solely on `kill(-pid, sig)` against the assumed process group. On Linux, use `PR_SET_CHILD_SUBREAPER` or track/enumerate all descendant PIDs (e.g., by walking `/proc/<pid>/task/*/children` or using a dedicated init/reaper wrapper process) and explicitly signal any process still holding open file descriptors or a cwd under the job's `BuildDir`/`CacheDir`, even if it has called `setsid`. At minimum, before starting a new job that reuses an existing project directory, scan for and terminate/refuse-to-start if any process still has that directory open (via `lsof`-equivalent /proc scanning), and log/alert when `KillProcessError` is returned so operators know cleanup could not be guaranteed and can invalidate the reused workspace instead of handing it to the next job.

### Proof of Concept
Extend `helpers/process/killer_unix_integration_test.go` (or add a new integration test) using `helpers/process/testdata/sleep`-style test binary:
1. Build a test binary that, on start, forks a grandchild, calls `setsid()` in the grandchild, and has the grandchild loop writing timestamps into a file inside a shared "checkout" directory; optionally support a `skip-terminate-signals` flag on the parent to simulate a dormant/unresponsive process.
2. Start the command via `Commander`/`osKillWait.KillAndWait` with short `gracefulKillTimeout`/`forceKillTimeout`.
3. Cancel the context / call `KillAndWait`; assert that regardless of whether it returns nil, the wait error, or `&KillProcessError{}`, the grandchild's PID is still alive (`syscall.Kill(pid, 0)` succeeds) and the file in the checkout directory continues to grow after `KillAndWait` returns.
4. Simulate directory reuse: run a second, unrelated job pointing at the same directory and assert the orphaned writer's output/tampering is observable in that second job's workspace.

func (pk *unixKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGTERM)
	if err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}

func (pk *unixKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGKILL)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}
}

func (b *Build) ProjectUniqueDir(sharedDir bool) string {
	dir, err := b.ProjectSlug()
	if err != nil {
		dir = fmt.Sprintf("project-%d", b.JobInfo.ProjectID)
	}

	// for shared dirs path is constructed like this:
	// <some-path>/runner-short-id/concurrent-project-id/group-name/project-name/
	// ex.<some-path>/01234567/0/group/repo/
	if sharedDir {
		dir = path.Join(
			b.Runner.ShortDescription(),
			fmt.Sprintf("%d", b.ProjectRunnerID),
			dir,
		)
	}

	if b.GetGitStrategy() == GitEmpty {
		dir += "-empty"
	}

	return dir
}

func (b *Build) StartBuild(
	rootDir, cacheDir string,
	customBuildDirEnabled, sharedDir, safeDirectoryCheckout bool,
) error {
	if rootDir == "" {
		return &BuildError{Inner: fmt.Errorf("the builds_dir is not configured"), FailureReason: ConfigurationError}
	}

	if cacheDir == "" {
		return &BuildError{Inner: fmt.Errorf("the cache_dir is not configured"), FailureReason: ConfigurationError}
	}

	b.SafeDirectoryCheckout = safeDirectoryCheckout

	// We set RootDir and invalidate variables
	// to be able to use CI_BUILDS_DIR
	b.RootDir = rootDir
	b.CacheDir = path.Join(cacheDir, b.ProjectUniqueDir(false))
	b.RefreshAllVariables()

	var err error
	b.BuildDir, err = b.getCustomBuildDir(b.RootDir, b.Settings().GitClonePath, customBuildDirEnabled, sharedDir)
	if err != nil {
		return err
	}
