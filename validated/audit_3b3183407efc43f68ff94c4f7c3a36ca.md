## Exact Trace of the Bug

**`cyclic_dependencies::verify_module`** (the version used by the new runtime) performs a DFS from a single `target` module and returns a `visited` set. The `visited` set's semantics are: *"all nodes encountered while searching for a path back to `target`."* [1](#0-0) 

Critically, `is_new = visited.insert(cursor.clone())` — a node is skipped on re-encounter. This means `visited` only proves "these nodes cannot reach `target` (Z)." It says **nothing** about whether those nodes form cycles among themselves.

**`verify_package_no_cyclic_relationships`** then removes the entire `visited` set from `to_visit_modules`: [2](#0-1) 

The implicit assumption is: *"if Z has no cycle, then every module reachable from Z is also cycle-free."* This is **false**.

## Concrete Counterexample

Package at address `0xCAFE` with three modules: `alpha`, `beta`, `zeta`

| Module | Immediate deps |
|--------|---------------|
| `zeta` | `alpha` |
| `alpha` | `beta` |
| `beta` | `alpha` ← **cycle** |

`BTreeMap` key order (lexicographic): `alpha < beta < zeta`. `pop_last()` picks `zeta` first.

**Iteration 1 — check `zeta`:**
- `detect_cycles(target=zeta, cursor=alpha, visited={})` → inserts `alpha`, recurses
- `detect_cycles(target=zeta, cursor=beta, visited={alpha})` → inserts `beta`, recurses
- `detect_cycles(target=zeta, cursor=alpha, visited={alpha,beta})` → `is_new = false`, **skips**
- No cycle back to `zeta`. Returns `visited = {alpha, beta}`.
- Both `alpha` and `beta` are removed from `to_visit_modules`.

**Iteration 2:** `to_visit_modules` is empty. Loop exits. `Ok(())` returned.

The `alpha ↔ beta` cycle is **never checked**.

### Title
Incorrect `visited`-set pruning in `verify_package_no_cyclic_relationships` allows publishing a package with intra-package cyclic module dependencies, permanently locking deposited funds — (`external-crates/move/crates/move-vm-runtime/src/validation/verification/linkage.rs`)

### Summary
`verify_package_no_cyclic_relationships` prunes modules from its work-list using the `visited` set returned by `cyclic_dependencies::verify_module`. That set only proves the visited nodes cannot reach the *current* DFS root; it does not prove they are mutually acyclic. A package publisher can craft module names so that the lexicographically greatest module (`zeta`) is checked first, its DFS traverses all other modules (`alpha`, `beta`) into `visited`, and those modules are removed from the work-list before their own mutual cycle is ever checked.

### Finding Description
In `verify_package_no_cyclic_relationships`:

1. `to_visit_modules` is a `BTreeMap<ModuleId, &Module>` over all modules in the package. [4](#0-3) 
2. `pop_last()` always selects the lexicographically greatest `ModuleId`. [5](#0-4) 
3. `cyclic_dependencies::verify_module` returns `visited` = all nodes reachable from the popped module during its DFS. [6](#0-5) 
4. All entries in `visited` are removed from `to_visit_modules`. [7](#0-6) 

The `visited` set's invariant is only "these nodes cannot reach `target`." It carries no guarantee that the visited nodes are mutually acyclic. The pruning is therefore unsound.

A publisher names their modules so that the "umbrella" module sorts last and depends (directly or transitively) on two other modules that form a mutual cycle. The umbrella's DFS visits both cyclic modules, they are pruned, and the cycle is never detected. The package passes `verify_linkage_and_cyclic_checks_for_publication` and is written to chain state.

### Impact Explanation
Once published, every call into the package hits the runtime's topological sort in `translate.rs`, which correctly detects the cycle and aborts with `UNKNOWN_INVARIANT_VIOLATION_ERROR`. [3](#0-2)  No entry point in the package can ever execute. Any assets deposited before the withdrawal path is exercised (staked SUI, bridged tokens, locked coins) are permanently inaccessible — a permanent fund lock meeting the High/Medium bounty threshold.

### Likelihood Explanation
Exploiting this requires only choosing module names: the attacker names the "cover" module so it sorts after the two cyclic modules (e.g., `zeta` > `beta` > `alpha`). No privileged access, no validator cooperation, and no leaked keys are needed. The attacker submits a standard `publish` transaction. Likelihood is high for any attacker who reads this code.

### Recommendation
Remove the `visited`-set pruning optimization entirely and check every module in the package independently:

```rust
while let Some((_, module)) = to_visit_modules.pop_last() {
    cyclic_dependencies::verify_module(&module.value, |original_module_id| {
        // ... same resolver ...
    })?;
    // Do NOT remove visited modules from to_visit_modules
}
```

Alternatively, replace the per-module DFS with a single proper SCC (Tarjan/Kosaraju) pass over the full intra-package module graph.
