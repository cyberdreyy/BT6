### Title
`extractZipSymlinkEntry`/`extractZipFile` lack path-containment checks, allowing zip-slip via cache/artifact extraction - (File: helpers/archives/zip_extract.go)

### Summary
`ExtractZipArchive`/`extractZipFile` write each `zip.File` directly to `file.Name` with no path-containment validation, only a narrow `.git`-specific check (`errorIfGitDirectory`) [1](#0-0) [2](#0-1) . `extractZipSymlinkEntry` reads attacker-controlled symlink target bytes from the archive and calls `os.Symlink(string(data), file.Name)` without validating either the link target or `file.Name` [3](#0-2) . This is the classic "zip-slip" pattern, and it contrasts with the sibling `tarzstd` extractor, which explicitly joins against a chroot directory and rejects any resolved path outside it [4](#0-3) .

### Finding Description
`ExtractZipArchive` iterates `archive.File` and, for each entry, only checks whether the path looks like `.git/...` before calling `extractZipFile(file)` [1](#0-0) . `extractZipFile` dispatches based on file mode to `extractZipDirectoryEntry`, `extractZipSymlinkEntry`, or `extractZipFileEntry`, all of which use `file.Name` verbatim — there is no `filepath.Clean`, no rejection of absolute paths, no rejection of `..` segments, and no containment check against the extraction root (unlike `tarzstd_extractor.go`'s `filepath.Abs`/`HasPrefix` chroot check) [5](#0-4) [4](#0-3) .

`errorIfGitDirectory`/`isPathAGitDirectory` only match paths whose first cleaned path segment equals `.git` [2](#0-1) . It is not a general containment/allow-list filter — a name like `../../secret_file`, `/etc/passwd`, or a dotfile such as `.hidden/../../.ssh/authorized_keys` is never flagged by this check, so the question's premise that a "restore filter" treats hidden/special names specially and might be bypassed doesn't match what's implemented: there simply is no general restore filter to bypass — the containment control is entirely absent for zip extraction.

Concretely, `extractZipSymlinkEntry` will happily create a symlink at any `file.Name` (including a path escaping the working directory via `..` or an absolute path) pointing at any attacker-chosen target string, since it just does `os.Remove(file.Name); os.Symlink(string(data), file.Name)` [6](#0-5) . Combined with `extractZipFile`'s `os.MkdirAll(filepath.Dir(file.Name), 0o777)` for arbitrary parent paths [7](#0-6) , an attacker-produced archive (cache or artifact) can plant a symlink escaping the build directory, and a subsequent entry in the same archive (or a later job stage) that writes through that symlink name would follow it outside the intended cache/artifact root.

This `ExtractZipArchive` path is reachable from cache extraction, e.g. `ziplegacy` extractor calls `archives.ExtractZipArchive(zr)` directly on a zip built from attacker-influenced cache content [8](#0-7) , and from `ExtractZipFile`, used by tests and potentially other legacy extraction call sites [9](#0-8) .

### Impact Explanation
An attacker who can influence archive content consumed via zip extraction (e.g., poisoning a cache archive under their control, or in scenarios where cache keys/artifacts are attacker-influenced) can attempt to write outside the intended extraction root via symlink or path-traversal entry names, potentially overwriting trusted files or exfiltrating data through a planted symlink that a later step writes into (secret exposure or trusted-config overwrite, matching the scoped impact). The severity depends heavily on what directory `ExtractZipArchive`/`ExtractZipFile` is invoked from and whether the process has write access to sensitive paths outside the build/cache directory.

### Likelihood Explanation
Feasibility requires the attacker to control or influence the actual bytes of a zip archive that gets extracted through this exact code path (`ExtractZipArchive`/`extractZipFile`/`extractZipSymlinkEntry`), not just via the primary `fastzip`/modern extractor used for normal job cache/artifact restore — the newer `fastzip` extractor referenced in `commands/helpers/archive/fastzip/zip_fastzip_extractor.go` may have its own (unverified) path handling, so whether this legacy code path is on the default/active job cache-restore path could not be confirmed from the available index. This is a real, exploitable gap in the reviewed function, but I could not verify from the index whether current default job cache/artifact restore flows route through this specific `ExtractZipArchive` implementation versus `fastzip`, which limits certainty about real-world reachability from an unprivileged job today.

### Recommendation
Add path containment validation in `extractZipFile` (and specifically before `extractZipSymlinkEntry`/`extractZipDirectoryEntry`/`extractZipFileEntry` act on `file.Name`): resolve `filepath.Join(extractionRoot, file.Name)`, `filepath.Clean` it, and reject any entry whose resolved path is not a subpath of `extractionRoot`, mirroring the chroot check already used in `tarzstd_extractor.go`. Additionally validate/reject symlink targets that would resolve outside the extraction root.

### Proof of Concept
Go unit test in `helpers/archives/zip_extract_test.go`:
```go
func TestExtractZipFileSymlinkEscape(t *testing.T) {
    testInWorkDir(t, func(t *testing.T, fileName string) {
        f, err := os.Create(fileName)
        require.NoError(t, err)
        archive := zip.NewWriter(f)
        w, err := archive.CreateHeader(&zip.FileHeader{
            Name: "evil_link", // will point outside cwd
        })
        require.NoError(t, err)
        w.(io.Writer)
        hdr := &zip.FileHeader{Name: "evil_link"}
        hdr.SetMode(os.ModeSymlink | 0777)
        w2, _ := archive.CreateHeader(hdr)
        _, _ = w2.Write([]byte("../../outside_target"))
        archive.Close()
        f.Close()

        err = ExtractZipFile(fileName)
        require.NoError(t, err)

        target, err := os.Readlink("evil_link")
        require.NoError(t, err)
        // Assert failure: currently succeeds, target escapes cwd
        assert.NotContains(t, target, "..", "symlink should not be allowed to point outside extraction root")
    })
}
```
Expected result today: the symlink is created pointing to `../../outside_target` with no error, demonstrating the missing containment check.

func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}

func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}

	switch file.Mode() & os.ModeType {
	case os.ModeDir:
		err = extractZipDirectoryEntry(file)

	case os.ModeSymlink:
		err = extractZipSymlinkEntry(file)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningf("File ignored: %q", file.Name)

	default:
		err = extractZipFileEntry(file)
	}
	return
}

func isPathAGitDirectory(path string) bool {
	parts := strings.Split(filepath.Clean(path), string(filepath.Separator))
	if len(parts) > 0 && parts[0] == ".git" {
		return true
	}
	return false
}
