### Title
Stale per-epoch instant-withdraw mappings are never cleared on normal claims, corrupting default recovery accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The `columnar` bug is "a read of data that was never initialized (or is stale) treated as valid input." The credit-vault analog is in `IdleCreditVault.claimInstantWithdrawRequest`: it clears only the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch mappings `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` that were written in `requestInstantWithdraw`. Later, the default-recovery path reads those stale entries as if they were still-live claim basis — inflating `defaultPendingClaimBasis()`, fabricating a "prefunded" reserve in `_defaultPrefundedInstantReserve()`, and producing an underflow revert in `_claimDefaultedInstantWithdrawRequest` for users who already claimed.

### Finding Description
`requestInstantWithdraw` writes three pieces of state [1](#0-0) :

```solidity
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

The funded-claim path clears only one of them [2](#0-1) :

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` remain nonzero forever after the underlying has already been paid out. If the same strategy epoch subsequently defaults and is finalized with `pendingInstantWithdraws != 0` (i.e. some *other* users' instant receipts were unfunded at default), the stale data is consumed by three places:

1. `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]`, which still contains the already-paid claims [3](#0-2) .
2. `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstant` using the inflated `instantBasis`, counting tokens that already left the strategy as still-held reserve [4](#0-3) .
3. `_claimDefaultedInstantWithdrawRequest(_user)` reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` as `claimBasis`, then executes `instantWithdrawsRequests[_user] -= claimBasis` on a zeroed aggregate → underflow revert under Solidity 0.8.10 checked math [5](#0-4) .

### Impact Explanation
Two distinct impacts:

- **Recovery dilution / reserve insolvency.** `finalizeDefaultRecovery` sets `defaultRecoveryPrice = reserveAmount / totalBasis` where both terms are corrupted: `totalBasis` includes already-paid claims, and `reserveAmount` includes a phantom `prefundedReserve` for tokens no longer held [6](#0-5) . If the inflated basis dominates, the recovery price is diluted and every legitimate claimant (pending withdraws, unfunded instant receipts, active LPs) receives less than the real recovered funds warrant; the excess reserve is only partially backed by real tokens, so late claimants can find the reserve drained — a solvency break bounded by the total of stale claimed amounts.
- **Frozen claims.** A user who already claimed their funded instant receipt in the defaulted epoch retains a stale `instantWithdrawsRequestsByEpoch` entry. Their next `claimInstantWithdrawRequest` enters `_claimDefaultedInstantWithdrawRequest`, hits the `instantWithdrawsRequests[_user] -= claimBasis` underflow, and reverts — permanently blocking that user's remaining legitimate claims through this function (e.g. older funded receipts still sitting in the aggregate or post-finalization payouts routed through the same entry point).

### Likelihood Explanation
The attack is triggered by ordinary user behavior, not a privileged call: a lender requests an instant withdrawal, waits out `instantWithdrawDelay`, and claims. That alone leaves the stale entries. The damage materializes only if that epoch then defaults with at least one *unfunded* instant receipt outstanding (`pendingInstantWithdraws != 0`, which sets `defaultInstantWithdrawsFinalized = true` and forces the instant bucket into `defaultPendingClaimBasis` [7](#0-6) [8](#0-7) ). An attacker can actively shape this: deposit, instantly withdraw and claim early in an epoch, while a second sybil instant request stays unclaimed — maximally inflating `instantWithdrawClaimsByEpoch` relative to real backing. No existing guard stops it: the skim/donation isolation in `_transferFundedClaim` only protects the reserve, the `defaultRecoveryFinalized` gate just routes to the corrupted path, and nothing ever clears the per-epoch mappings. The main residual uncertainty is epoch indexing: `epochNumber` is incremented in `deposit()` when `isEpochRunning()` [9](#0-8) , and `defaultRecoveryEpoch` is stamped from `epochNumber` at finalization [10](#0-9) . The PoC must pin down whether the defaulted epoch's key still matches the epoch under which the instant receipts were recorded; if `stopEpoch` increments `epochNumber` before default finalization in a way that desynchronizes the key, the stale entries instead make genuinely pending receipts unreachable (a different but equally serious variant of the same stale-data class).

### Recommendation
Mirror the normal withdraw receipt lifecycle: when a funded instant receipt is claimed (or when `collectInstantWithdrawFunds` finalizes funding for the epoch), decrement `instantWithdrawClaimsByEpoch[currentEpoch]` and delete `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` so per-epoch basis always reflects live claims. Alternatively, track funded-vs-unfunded instant basis per epoch and have `_defaultPrefundedInstantReserve`/`_claimDefaultedInstantWithdrawRequest` only consider receipts that were never paid out.

### Proof of Concept
Foundry fork sketch against `test/foundry/IdleCreditVault.t.sol` harness (mode: instant withdrawals enabled via `setInstantWithdrawParams`, standard epoch variant):

```solidity
// 1. Epoch N running. attacker1 requests instant withdraw (amount A),
//    attacker2 requests instant withdraw (amount B).
// 2. Manager collects instant funds only for A (collectInstantWithdrawFunds(A));
//    B stays pendingInstantWithdraws.
// 3. attacker1 calls cdoEpoch.claimInstantWithdrawRequest() -> paid A.
//    Observe: strategy.instantWithdrawsRequestsByEpoch(attacker1, N) == A   // stale
//             strategy.instantWithdrawClaimsByEpoch(N) == A + B             // stale
// 4. Borrower defaults in epoch N; owner calls cdoEpoch.finalizeDefault(recovered, manager).
//    -> finalizeDefaultRecovery: totalBasis includes A+B (should be B only);
//       prefundedReserve = (A+B) - B = A treated as still-held (it is not).
//    Assert: defaultRecoveryPrice is computed against phantom reserve.
// 5. attacker1 calls claimInstantWithdrawRequest() again (or has any older
//    receipt in the aggregate) -> _claimDefaultedInstantWithdrawRequest reads
//    stale basis A, `instantWithdrawsRequests[attacker1] -= A` underflows -> revert.
// 6. Assert: other claimants' realized payout < basis * trueRecovery, i.e. dilution,
//    and the last reserve claimant cannot be paid in full (insolvency).
```

Step 5's assertion is the minimal, order-independent demonstration: stale per-epoch storage left by a completed claim is later re-read as live debt. Whether the dilution (step 6) also lands depends on `epochNumber`/`defaultRecoveryEpoch` key alignment noted above and should be confirmed when writing the PoC.

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
