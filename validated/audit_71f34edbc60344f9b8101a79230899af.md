This vulnerability is confirmed and reachable through the actual route wiring.

### Title
External-initiator credential holder can trigger integer-ID (non-webhook) job runs via identity confusion in `AuthenticateExternalInitiator` - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
The route `POST /v2/jobs/:ID/runs` is registered with the `userOrEI` middleware chain (`AuthenticateExternalInitiator`, `AuthenticateByToken`, `AuthenticateBySession`) wrapped in `auth.RequiresRunRole`, and its handler `PipelineRunsController.Create` uses `auth.GetAuthenticatedUser` to decide whether to allow running int32 job IDs. Because `AuthenticateExternalInitiator` sets `SessionUserKey` to a synthetic `&clsessions.User{Role: UserRoleRun}`, an EI credential holder passes both `RequiresRunRole` and the `isUser` check in `Create`, allowing it to trigger arbitrary non-webhook jobs by integer ID even though the code comment explicitly states "EIs not allowed."

### Finding Description
The route is defined in [1](#0-0)  as `userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))`, authenticated via `AuthenticateExternalInitiator` first in the chain.

`AuthenticateExternalInitiator` validates the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers against the external initiator record, then stores both the EI object and a synthetic user under the standard user session key: [2](#0-1) 

`RequiresRunRole` only checks `GetAuthenticatedUser` and the role field, so it happily accepts this synthetic `UserRoleRun` user: [3](#0-2) 

Inside `PipelineRunsController.Create`, the code explicitly intends to block EIs from running int-ID (non-webhook) jobs via the comment "only users are allowed to run jobs using int IDs - EIs not allowed", but the check it uses — `auth.GetAuthenticatedUser(c)` — cannot distinguish a real session/token user from the synthetic EI user, since both are stored under the same `SessionUserKey`: [4](#0-3) 

As a result, `isUser` is `true` for an EI-only credential, `strconv.ParseInt` succeeds on any integer job ID, and `prc.App.RunJobV2` is invoked directly — bypassing the intended restriction that EIs may only trigger webhook jobs by UUID.

### Impact Explanation
An attacker who possesses only external-initiator credentials (no user session or API token) can trigger runs of arbitrary non-webhook job types (e.g., OCR, cron, flux monitor, VRF, direct-request jobs) by integer job ID. This is unauthorized triggering of job execution outside the EI's intended scope, matching the bounty class of "unauthorized job run" / authorization bypass via identity confusion across auth methods, since the EI is meant to be restricted to webhook/UUID job runs only.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs valid, low-privilege external-initiator credentials (obtainable by any operator who registers an external initiator, or leaked/compromised EI keys), and knowledge or brute-forcing of a valid integer job ID. No user session, API token, or elevated role is required. The exploit is a single HTTP POST and fully repeatable.

### Recommendation
Distinguish EI-derived pseudo-users from real authenticated users — e.g., store the EI identity under a distinct context key (not reusing `SessionUserKey`), or add an explicit marker/flag (e.g., `IsExternalInitiator bool`) checked in `PipelineRunsController.Create` instead of relying solely on `GetAuthenticatedUser`. Update `Create` to reject the request when the identity originated from `AuthenticateExternalInitiator`, ensuring EIs can only trigger jobs via the webhook/UUID path (which is already otherwise removed/blocked at line 104-107).

### Proof of Concept
Go handler-level test in `core/web/pipeline_runs_controller_test.go` or a new test file:
1. Build a gin `*gin.Context`/router using `auth.Authenticate(store, auth.AuthenticateExternalInitiator)` with a mock `Authenticator` whose `FindExternalInitiator` returns a valid `bridges.ExternalInitiator` matching the test's `X-Chainlink-EA-AccessKey`/`Secret` headers.
2. Send `POST /v2/jobs/123/runs` with those EI headers, no session cookie, no API token.
3. Inside the handler (or via a mock `chainlink.Application` with `RunJobV2` instrumented to record calls), assert:
   - `auth.GetAuthenticatedUser(c)` returns `(user, true)` with `user.Role == clsessions.UserRoleRun`.
   - `prc.App.RunJobV2` is invoked with `jobID == 123`.
   - The HTTP response is `200 OK` with a pipeline run resource, rather than a `422`/`401` rejection.
4. Assert failure of the invariant: expected behavior (EI should be rejected for non-UUID job IDs) does not hold, confirming the bypass.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
