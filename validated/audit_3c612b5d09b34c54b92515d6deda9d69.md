### Title
A single capped ERC4626 withdrawal can indefinitely block `stopEpoch` and freeze pending withdrawals - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower.onStopEpoch` requests the entire liquidity shortfall from the configured ERC4626 vault in one `vault.withdraw(shortfall, ...)` call. If the vault has a per-call or liquidity-based `maxWithdraw` below `shortfall`, the withdrawal reverts even though the borrower’s shares economically cover the obligation. The revert propagates through `IdleCDOEpochVariant._stopEpoch`, preventing epoch settlement and delaying all pending withdrawal claims.

### Finding Description
At epoch stop, `IdleCDOEpochVariant` calculates the full cash amount required for interest plus pending withdrawals and invokes `onStopEpoch` with that aggregate amount. [1](#0-0) 

`ProgrammableBorrower.onStopEpoch` computes only the single shortfall between the required amount and its idle token balance, verifies that the vault position is economically sufficient, and then attempts one withdrawal for the entire shortfall. [2](#0-1) 

There is no loop, chunking, `maxWithdraw` handling, or partial-withdrawal fallback. A standard ERC4626 vault may reject an otherwise solvent withdrawal because `assets > maxWithdraw(owner)`. The catch block converts that failure into `StopEpochVaultLiquidityUnavailable`, which is not caught by `IdleCDOEpochVariant`; therefore the whole stop transaction reverts. [3](#0-2) 

An unprivileged user of the configured ERC4626 vault can create this condition by withdrawing the vault’s immediately available liquidity before the epoch stop. The borrower’s shares can still represent enough total assets for `shortfall <= _currentVaultAssets()` while withdrawable liquidity is temporarily below the shortfall. Because the epoch cannot stop until liquidity is replenished or manually extracted through smaller redemptions, funded withdrawal claims are delayed.

### Impact Explanation
Pending withdraw receipts cannot become claimable because the epoch never advances to a successful stop. In a facility with, for example, `X` underlying assets parked in the ERC4626 vault and `P` pending withdrawals, an attacker can temporarily freeze up to `P` user funds plus required epoch interest whenever available vault liquidity or its per-call withdrawal cap is below the required shortfall.

The impact is temporary freezing rather than permanent loss: owner/manager can potentially recover with smaller `emergencyExitVault(_shares)` calls or wait for liquidity replenishment. The attacker can nevertheless repeat ordinary vault withdrawals to keep settlement unavailable and grief withdrawals for an extended period.

### Likelihood Explanation
This requires a programmable-borrower deployment whose ERC4626 vault has constrained immediately withdrawable liquidity. That is a normal ERC4626 condition and does not require malicious privileged roles or borrower misconduct. Any vault depositor capable of consuming available liquidity can trigger the failed single-call withdrawal around `stopEpoch`.

### Recommendation
Do not assume the ERC4626 vault can satisfy the full shortfall in one call.

- Query `vault.maxWithdraw(address(this))` and withdraw only the currently available amount.
- Loop through capped withdrawals until `shortfall` is covered or the position is exhausted.
- Prefer redeeming by shares when the vault’s asset-side withdrawal limit is restrictive.
- Treat persistent insufficient liquidity separately from a per-call withdrawal failure so an economically covered position can still be settled incrementally.

### Proof of Concept
The existing Foundry harness already models this exact vault behavior with `withdrawLimit` and a `withdraw` revert when `assets > withdrawLimit`. [4](#0-3) 

```solidity
function testStopEpochBlockedByCappedVaultWithdrawal() public {
    uint256 depositAmount = 100_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(depositAmount);
    _startEpochAndCheckPrices(0);

    // Funds are economically present in the vault.
    assertEq(programmableBorrower.vaultSharesBalance(), depositAmount);

    vm.prank(manager);
    cdoEpoch.requestWithdraw(0, address(aaTranche));

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Simulate an unprivileged ERC4626 liquidity consumer reducing the
    // amount available to one withdrawal while the position remains covered.
    MockStopEpochLiquidityVault vault =
        MockStopEpochLiquidityVault(address(programmableBorrower.vault()));
    vault.setWithdrawLimit(1);

    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning());

    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();
}
```

For a mainnet-fork reproduction, configure the programmable borrower with a real liquidity-constrained ERC4626 vault, deposit pool principal, start an epoch, have a third-party vault depositor withdraw available liquidity so `maxWithdraw(programmableBorrower) < requiredShortfall` while `convertToAssets(vaultShares) >= requiredShortfall`, then call `stopEpoch`. The call reverts before `collectWithdrawFunds`, leaving the epoch running and the withdrawal request unclaimable.

contract MockStopEpochLiquidityVault is ERC20 {
  IERC20Detailed public immutable assetToken;
  uint256 public withdrawLimit = type(uint256).max;

  constructor(address _asset) ERC20("Stop Epoch Liquidity Vault", "SELV") {
    assetToken = IERC20Detailed(_asset);
  }

  function asset() external view returns (address) {
    return address(assetToken);
  }

  function convertToAssets(uint256 shares) public view returns (uint256) {
    uint256 supply = totalSupply();
    if (supply == 0) return shares;
    return shares * assetToken.balanceOf(address(this)) / supply;
  }

  function maxWithdraw(address owner) external view returns (uint256) {
    uint256 assets = convertToAssets(balanceOf(owner));
    return assets < withdrawLimit ? assets : withdrawLimit;
  }

  function setWithdrawLimit(uint256 assets) external {
    withdrawLimit = assets;
  }

  function deposit(uint256 assets, address receiver) external returns (uint256 shares) {
    uint256 assetsBefore = assetToken.balanceOf(address(this));
    uint256 supply = totalSupply();
    shares = supply == 0 || assetsBefore == 0 ? assets : assets * supply / assetsBefore;
    assetToken.transferFrom(msg.sender, address(this), assets);
    _mint(receiver, shares);
  }

  function withdraw(uint256 assets, address receiver, address owner) external returns (uint256 shares) {
    require(assets <= withdrawLimit, "insufficient-liquidity");
    shares = _toSharesRoundUp(assets);
    if (msg.sender != owner) _spendAllowance(owner, msg.sender, shares);
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }

  function redeem(uint256 shares, address receiver, address owner) external returns (uint256 assets) {
    assets = convertToAssets(shares);
    require(assets <= withdrawLimit, "insufficient-liquidity");
    if (msg.sender != owner) _spendAllowance(owner, msg.sender, shares);
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }

  function _toSharesRoundUp(uint256 assets) internal view returns (uint256 shares) {
    uint256 supply = totalSupply();
    uint256 managedAssets = assetToken.balanceOf(address(this));
    if (supply == 0 || managedAssets == 0) return assets;
    shares = assets * supply / managedAssets;
    if (shares * managedAssets < assets * supply) shares += 1;
