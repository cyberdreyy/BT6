### Title
`getBlock`/`getConfirmedBlock` RPC fails entirely when a single unrelated transaction in the block cannot be encoded - ([File: transaction-status/src/lib.rs])

### Summary
`ConfirmedBlock::encode_with_options` encodes every transaction in a block via `.collect::<Result<Vec<_>, _>>()?`, which propagates a single per-transaction `EncodeError` (e.g. `EncodeError::UnsupportedTransactionVersion`) as a failure for the *entire block encoding*. The `getBlock` RPC handler (`JsonRpcRequestProcessor::get_block` in `rpc/src/rpc.rs`) then converts that into an RPC error and returns nothing for the whole block, even though only one transaction among potentially hundreds was problematic. This mirrors the CSR `PostTxProcessing` bug class: an isolated, unrelated failure (one bad "item") aborts an otherwise-valid batch operation (the whole block/all other transactions), denying unrelated users their data via a single unprivileged RPC call.

### Finding Description
`ConfirmedBlock::encode_with_options` iterates transactions and uses `?` on `collect::<Result<Vec<_>, _>>()`: [1](#0-0) 

Each transaction's `encode()` call validates its version against `max_supported_transaction_version` and returns `Err(EncodeError::UnsupportedTransactionVersion(version))` when a transaction's version exceeds what the caller requested (or when no `max_supported_transaction_version` is supplied for a non-legacy transaction): [2](#0-1) 

`JsonRpcRequestProcessor::get_block` calls `encode_with_options` on the whole block and maps any error to an RPC error, then returns it for the *entire request*: [3](#0-2) [4](#0-3) 

Because a single unrelated transaction in the block (one that happens to use a newer transaction version than the caller's `max_supported_transaction_version`, or an inner-transaction encode failure) causes `encode_with_options` to return `Err`, the RPC method returns an error for the *whole block*, not just that transaction. All the other, unrelated transactions in the block — which a caller has no way to skip or filter — become unreadable for that request.

### Impact Explanation
An unprivileged caller performing a plain `getBlock` (or `getConfirmedBlock`) query — matching the "transaction-status and instruction parsing" category in scope — can be denied all block data purely because of one transaction's encoding/version property that has nothing to do with the caller's transactions of interest. This is analogous to the CSR finding: a failure isolated to one operation (encoding one transaction / distributing fees for one contract) improperly propagates and blocks/reverts an unrelated batch of operations (all other transactions in the block / the whole user transaction). The effect here is read-only (wrong/missing data returned instead of the correct block), not a crash, but it does produce "wrong-slot/fork/account data returned" in the sense that a legitimate request for existing, valid data returns an error instead of the expected (partial) result, for reasons entirely unrelated to the requester's actual target transaction(s).

### Likelihood Explanation
This is straightforward to trigger for anyone building a full node that has processed versioned (v0/v1) transactions: any caller issuing `getBlock` on a slot containing a mix of transaction versions, without setting `maxSupportedTransactionVersion` high enough (or the default behavior when the client omits it, which yields `None` and thus rejects any non-legacy transaction), will get an all-or-nothing failure for the block. This can happen unintentionally (client using an older RPC client version/default) rather than requiring an adversarial transaction to be crafted, though it can also be intentionally exploited by an unprivileged user to deny block-data retrieval to other callers who share request paths that assume optimistic success (e.g. archiving/indexing services that must fetch full blocks) is limited to that specific request.

### Recommendation
Do not let a single transaction's encode failure abort encoding of the whole block. In `encode_with_options` (and `build_json_accounts`), encode each transaction independently and either: (1) return the transaction with a partial/omitted meta and only the raw transaction (mirroring `TransactionWithStatusMeta::MissingMetadata` behavior already used elsewhere) when its own metadata/encoding fails, or (2) surface which specific transactions failed instead of erroring the whole `Vec`. This follows the general mitigation of "log/skip errors scoped to the failing unit rather than failing the whole batch."

### Proof of Concept
1. Run a validator/RPC node with transaction history enabled.
2. Ensure a slot contains at least one legacy transaction and one v0/v1 versioned transaction (common on mainnet/testnet clusters after version-transaction adoption).
3. Call `getBlock` for that slot without `maxSupportedTransactionVersion` (or with a value lower than the versioned transaction's version):
```
{"jsonrpc":"2.0","id":1,"method":"getBlock","params":[<slot>]}
```
4. Observe the whole request fails via `ConfirmedBlock::encode_with_options`'s `?` on the `collect::<Result<Vec<_>, _>>()` over all transactions, at `transaction-status/src/lib.rs:337-350`, surfaced through `JsonRpcRequestProcessor::get_block` in `rpc/src/rpc.rs:1353-1367`/`1415-1428` — no data is returned for any of the transactions in the block, even the legacy ones that would have encoded successfully on their own.

*Note: Full verification of exact client-facing error text/exact toggling conditions for `max_supported_transaction_version` defaults was not completed within the available search iterations; the control-flow linkage (per-transaction `Result` propagated via `?` through `collect` to a whole-block failure) is confirmed directly from the cited source.*

impl VersionedTransactionWithStatusMeta {
    fn validate_version(
        &self,
        max_supported_transaction_version: Option<u8>,
    ) -> Result<Option<TransactionVersion>, EncodeError> {
        match (
            max_supported_transaction_version,
            self.transaction.version(),
        ) {
            // Set to none because old clients can't handle this field
            (None, TransactionVersion::LEGACY) => Ok(None),
            (None, TransactionVersion::Number(version)) => {
                Err(EncodeError::UnsupportedTransactionVersion(version))
            }
            (Some(_), TransactionVersion::LEGACY) => Ok(Some(TransactionVersion::LEGACY)),
            (Some(max_version), TransactionVersion::Number(version)) => {
                if version <= max_version {
                    Ok(Some(TransactionVersion::Number(version)))
                } else {
                    Err(EncodeError::UnsupportedTransactionVersion(version))
                }
            }
        }
    }

    pub fn encode(
        self,
        encoding: UiTransactionEncoding,
        max_supported_transaction_version: Option<u8>,
        show_rewards: bool,
    ) -> Result<EncodedTransactionWithStatusMeta, EncodeError> {
        let version = self.validate_version(max_supported_transaction_version)?;

        Ok(EncodedTransactionWithStatusMeta {
            transaction: self.transaction.encode_with_meta(encoding, &self.meta),
            meta: Some(match encoding {
                UiTransactionEncoding::JsonParsed => parse_ui_transaction_status_meta(
                    self.meta,
                    self.transaction.message.static_account_keys(),
                    show_rewards,
                ),
                _ => {
                    let mut meta = UiTransactionStatusMeta::from(self.meta);
                    if !show_rewards {
                        meta.rewards = OptionSerializer::None;
                    }
                    meta
                }
            }),
            version,
        })
    }
