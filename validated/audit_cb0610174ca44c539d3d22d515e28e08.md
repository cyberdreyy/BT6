### Title
Kubernetes executor `setupCredentials` reuses stale project-scoped Docker auth secrets across unrelated jobs on Conflict - (File: executors/kubernetes/kubernetes.go)

### Summary
`setupCredentials` derives the Kubernetes `dockercfg` secret name from `s.Build.ProjectUniqueName()`, which is stable across many unrelated jobs (same runner + project + concurrency slot), rather than being unique per job/build. When a create request hits a naming conflict, `requestSecretCreation` silently fetches the pre-existing secret instead of updating it with the current job's auth data, so a stale (and attacker-influenced) `dockercfg` payload from a previous job can be attached as `ImagePullSecrets` to a later, unrelated job's pod.

### Finding Description
`setupCredentials` builds a `dockercfg` secret name with `generateNameForK8sResources(s.Build.ProjectUniqueName())`: [1](#0-0) 

`ProjectUniqueName()` is `runner-<token>-project-<projectID>-concurrent-<ProjectRunnerID>` — a function of the runner, project ID, and concurrency slot only, with no job/build identifier: [2](#0-1) 

This means every job that lands on the same concurrency slot for the same project reuses the exact same secret name, regardless of pipeline, branch, or job author. `requestSecretCreation` handles a name conflict by fetching the existing secret rather than updating it with the current job's freshly computed `dockerCfgContent`: [3](#0-2) 

Cleanup of that secret is conditional: it is only explicitly deleted if it has no `OwnerReferences`; otherwise cleanup relies on Kubernetes garbage-collection cascading from pod deletion, which is asynchronous and can lag or fail: [4](#0-3) 

The docs and troubleshooting guide explicitly acknowledge that secret cleanup can fail or time out (`Error cleaning up secrets`), confirming this is a real, reachable operational condition rather than a purely theoretical one: [5](#0-4) 

Exploit flow: An attacker-controlled job (job A, e.g. an MR pipeline job) supplies `DOCKER_AUTH_CONFIG`/registry credentials (`s.Build.Credentials`), which `setupCredentials` marshals into a `dockercfg` secret named after the project+slot. If job A's cleanup lags (cascade GC delay, transient API error, or a timing race between two jobs scheduled on the same concurrency slot), the secret persists past job A's boundary. Job B — a later, unrelated job (different pipeline/branch/author, potentially higher-trust) — runs `setupCredentials`, computes its own `dockerCfgContent`, attempts to create a secret with the identical name, hits a `Conflict`, and instead of updating the secret with job B's own credentials, `requestSecretCreation` just `Get`s and returns job A's stale secret. That stale secret (attacker-influenced from job A) is then assigned to `s.credentials` and attached to job B's pod as `ImagePullSecrets`, letting job B's pod authenticate against registries using job A's leftover, attacker-controlled auth entries instead of its own.

None of the existing checks (`allowed_images`, RFC1123 name sanitization, owner-reference cleanup) validate that the fetched-on-conflict secret actually corresponds to the current job's intended auth configs; the code assumes any existing secret with that name is equivalent and safe to reuse.

### Impact Explanation
This allows one job's Docker registry auth state to leak into another unrelated job's pod when secret cleanup races or fails, resulting in cross-job credential misuse: a later job may pull images using credentials it never supplied, or fail to use its own intended credentials because they were silently discarded in favor of stale data. Since job authors fully control the `Credentials`/`DOCKER_AUTH_CONFIG` inputs that populate this secret, an attacker with only unprivileged pipeline-authoring rights on a project can plant crafted auth entries that later, unrelated jobs on the same runner/project/concurrency-slot may inherit.

### Likelihood Explanation
Exploitability depends on a timing race: the attacker's job's secret must still exist (via GC lag, cleanup timeout, or transient API failure — all of which are documented, reachable conditions per the troubleshooting docs) when a subsequent job on the same concurrency slot runs `setupCredentials`. This is plausible on busy runners with many concurrent/sequential jobs per project, and is fully repeatable by an attacker who runs jobs back-to-back to increase the race window, but it is not deterministic on every single run.

### Recommendation
Make the credentials secret name unique per job/build (e.g., incorporate `s.Build.ID` similar to `ProjectUniqueShortName`), and/or change `requestSecretCreation`'s conflict handling to `Update` the existing secret with the current job's `dockerCfgContent` instead of blindly `Get`-ing and reusing whatever is already stored.

### Proof of Concept
Go integration test outline in `executors/kubernetes/kubernetes_test.go`:
1. Create executor A with `Build.Credentials` containing registry auth for `http://attacker.example.com` with attacker username/password; call `prepareOverwrites` and `setupCredentials`; capture the created secret name (`generateNameForK8sResources(ProjectUniqueName())`) and confirm the fake client stored the attacker's dockercfg.
2. Do not delete the secret (simulate lagging/failed cleanup by skipping `Cleanup()`).
3. Create executor B with the same `Runner`, same `ProjectID`, and same `ProjectRunnerID` (same `ProjectUniqueName()`), but with different, legitimate `Build.Credentials` for `http://legit-registry.example.com`.
4. Call `prepareOverwrites` and `setupCredentials` on executor B against the same fake clientset (pre-seeded with A's secret) and assert that the fake client's `Create` reactor returns a `Conflict`, triggering the `Get` path.
5. Assert `ex.credentials.Data[api.DockerConfigKey]` on executor B still contains the attacker's `http://attacker.example.com` entry (from job A) and does **not** contain `http://legit-registry.example.com` (job B's own intended credentials) — proving stale, attacker-influenced auth state persisted into the unrelated job B.

func (s *executor) Cleanup() {
	if s.eventsStream != nil {
		s.eventsStream.Stop()
	}

	s.cleanupResources()
	closeKubeClient(s.kubeClient)
	s.AbstractExecutor.Cleanup()
}

// cleanupResources deletes the resources used during the runner job
// Having a pod does not mean that the owner-dependent relationship exists as an error may occur during setting
// We therefore explicitly delete the resources if no ownerReference is found on it
// This does not apply for services as they are created with the owner from the start
// thus deletion of the pod automatically means deletion of the services if any
func (s *executor) cleanupResources() {
	// Here we don't use the build context as its timeout will prevent a successful cleanup of the resources.
	// The solution used here is inspired from the one used for the docker executor.
	// We give a configurable timeout to complete the resources cleanup.
	ctx, cancel := context.WithTimeout(context.Background(), s.Config.Kubernetes.GetCleanupResourcesTimeout())
	defer cancel()

	if s.pod != nil {
		kubeRequest := retry.WithFn(s, func() error {
			// kubeAPI: pods, delete
			return s.kubeClient.CoreV1().
				Pods(s.pod.Namespace).
				Delete(ctx, s.pod.Name, metav1.DeleteOptions{
					GracePeriodSeconds: s.Config.Kubernetes.CleanupGracePeriodSeconds,
					PropagationPolicy:  &PropagationPolicy,
				})
		})

		if err := kubeRequest.Run(); err != nil {
			s.BuildLogger.Errorln(fmt.Sprintf("Error cleaning up pod: %s", err.Error()))
		}
	}

	if s.credentials != nil && len(s.credentials.OwnerReferences) == 0 {
		kubeRequest := retry.WithFn(s, func() error {
			// kubeAPI: secrets, delete
			return s.kubeClient.CoreV1().
				Secrets(s.configurationOverwrites.namespace).
				Delete(ctx, s.credentials.Name, metav1.DeleteOptions{
					GracePeriodSeconds: s.Config.Kubernetes.CleanupGracePeriodSeconds,
				})
		})
		if err := kubeRequest.Run(); err != nil {
			s.BuildLogger.Errorln(fmt.Sprintf("Error cleaning up secrets: %s", err.Error()))
		}
	}

	err := s.teardownBuildNamespace(ctx)
	if err != nil {
		s.BuildLogger.Errorln(fmt.Sprintf("Error tearing down namespace: %s", err.Error()))
	}
}

func (s *executor) setupCredentials(ctx context.Context) error {
	s.BuildLogger.Debugln("Setting up secrets")

	authConfigs, err := auth.Resolver{}.AllConfigs(s.Build.GetDockerAuthConfig(), s.Shell().User, s.Build.Credentials, &s.BuildLogger)
	if err != nil {
		return err
	}

	if len(authConfigs) == 0 {
		return nil
	}

	dockerCfgs := make(map[string]types.AuthConfig)
	for _, config := range authConfigs {
		dockerCfgs[config.AuthConfig.ServerAddress] = config.AuthConfig
	}

	dockerCfgContent, err := json.Marshal(dockerCfgs)
	if err != nil {
		return err
	}

	secret := api.Secret{}
	secret.Name = generateNameForK8sResources(s.Build.ProjectUniqueName())
	secret.Namespace = s.configurationOverwrites.namespace
	secret.Type = api.SecretTypeDockercfg
	secret.Data = map[string][]byte{}
	secret.Data[api.DockerConfigKey] = dockerCfgContent

	s.credentials, err = retry.WithValueFn(s, func() (*api.Secret, error) {
		return s.requestSecretCreation(ctx, &secret, s.configurationOverwrites.namespace)
	}).Run()
	return err
}

func (s *executor) requestSecretCreation(
	ctx context.Context,
	secret *api.Secret,
	namespace string,
) (*api.Secret, error) {
	// kubeAPI: secrets, create
	creds, err := s.kubeClient.CoreV1().
		Secrets(namespace).Create(ctx, secret, metav1.CreateOptions{})
	if isConflict(err) {
		s.BuildLogger.Debugln(
			fmt.Sprintf(
				"Conflict while trying to create the secret  %s ... Retrieving the existing resource",
				secret.Name,
			),
		)

		// kubeAPI: secrets, get
		creds, err = s.kubeClient.CoreV1().
			Secrets(namespace).Get(ctx, secret.Name, metav1.GetOptions{})
	}

	return creds, err
}

// ProjectUniqueName returns a unique name for a runner && project. It uses the runner's short description, thus uses a
// truncated token in it's human readable form.
func (b *Build) ProjectUniqueName() string {
	projectUniqueName := fmt.Sprintf(
		"runner-%s-project-%d-concurrent-%d",
		b.Runner.ShortDescription(),
		b.JobInfo.ProjectID,
		b.ProjectRunnerID,
	)

	return dns.MakeRFC1123Compatible(projectUniqueName)
}
