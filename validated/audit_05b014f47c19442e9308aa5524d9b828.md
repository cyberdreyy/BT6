### Title
Silent Reward Under-Disbursement in `withdraw_rewards` of `StakingPool` — (File: `crates/sui-framework/packages/sui-system/sources/staking_pool.move`)

---

### Summary

The `withdraw_rewards` function in `StakingPool` silently caps the reward payout to whatever is available in `rewards_pool` when the pool's balance is insufficient to cover the staker's entitled amount. The shortfall is permanently lost — no revert, no debt tracking, no event indicating the discrepancy. This is the direct Sui analog of the AFiBase under-disbursement bug.

---

### Finding Description

In `staking_pool.move`, `withdraw_rewards` computes the reward a staker is entitled to based on the pool's exchange rate, then silently truncates it:

```move
// staking_pool.move lines 432–440
let mut reward_withdraw_amount = if (total_sui_withdraw_amount >= principal_withdraw_amount) {
    total_sui_withdraw_amount - principal_withdraw_amount
} else 0;

// This may happen when we are withdrawing everything from the pool and
// the rewards pool balance may be less than reward_withdraw_amount.
// TODO: FIGURE OUT EXACTLY WHY THIS CAN HAPPEN.
reward_withdraw_amount = reward_withdraw_amount.min(pool.rewards_pool.value());
pool.rewards_pool.split(reward_withdraw_amount)
``` [1](#0-0) 

The `TODO` comment is the developers' own acknowledgment that this truncation path is reachable but not understood. When it fires, the staker receives `min(entitled_rewards, pool.rewards_pool.value())` instead of `entitled_rewards`, and the difference is silently discarded.

**Root cause — same as AFiBase**: instead of reverting when funds are insufficient, the code transfers whatever is available and swallows the shortfall.

**When does the shortfall occur?**

The exchange rate recorded at epoch `E` reflects the full `rewards_pool` balance at that moment. Within epoch `E`, each call to `request_withdraw_stake` immediately splits from `rewards_pool` (line 440) while the exchange rate remains fixed at the epoch-start snapshot. If multiple stakers withdraw in the same epoch, later withdrawers compute their entitled reward against the original (full) exchange rate but find a partially-drained `rewards_pool`. The last withdrawer(s) silently receive less than the exchange rate entitles them to. [2](#0-1) 

**Call chain from public entry to the bug:**

`sui_system::request_withdraw_stake` (public entry, line 267) →
`request_withdraw_stake_non_entry` (line 295) →
`sui_system_state_inner::request_withdraw_stake` →
`validator_set::request_withdraw_stake` →
`validator::request_withdraw_stake` →
`staking_pool::request_withdraw_stake` (line 157) →
`staking_pool::withdraw_rewards` (line 424) ← **truncation here** [3](#0-2) [4](#0-3) 

**The emitted event also misreports the reward.** In `validator.move`, `reward_amount` is computed as `withdraw_amount - principal_amount` where `withdraw_amount` is the already-truncated value, so the `UnstakingRequestEvent` reports the reduced reward with no indication of the shortfall: [5](#0-4) 

---

### Impact Explanation

Any ordinary SUI holder who stakes and then calls `request_withdraw_stake` during an epoch in which the `rewards_pool` has been partially drained by earlier withdrawals will permanently lose a portion of their earned staking rewards. The lost amount is not tracked, not refunded at a later epoch, and not surfaced in any event. This constitutes **permanent, unrecoverable fund loss** for stakers — matching the "harmful smart-contract behavior" impact class.

---

### Likelihood Explanation

The condition is reachable by any two stakers withdrawing from the same pool in the same epoch. No special privilege is required. The `TODO` comment confirms the developers have observed this path is reachable. On a live network with many concurrent stakers, this condition can arise organically without any deliberate attack.

---

### Recommendation

Replace the silent `.min()` cap with an explicit invariant check that aborts if the `rewards_pool` cannot satisfy the computed entitlement:

```move
// Instead of silently capping:
// reward_withdraw_amount = reward_withdraw_amount.min(pool.rewards_pool.value());

assert!(
    pool.rewards_pool.value() >= reward_withdraw_amount,
    EInsufficientRewardsPool
);
pool.rewards_pool.split(reward_withdraw_amount)
```

Alternatively, if partial reward delivery is intentional for some edge case, the shortfall must be tracked and paid out at the next epoch boundary, ensuring stakers always receive their full entitled amount.

---

### Proof of Concept

1. At epoch `E` start, `StakingPool` has `rewards_pool = 1000 SUI` and exchange rate `1 pool_token = 2 SUI`.
2. Staker A holds 500 pool tokens (entitled to 1000 SUI: 500 principal + 500 rewards).
3. Staker B holds 500 pool tokens (entitled to 1000 SUI: 500 principal + 500 rewards).
4. Staker A calls `sui_system::request_withdraw_stake` → `withdraw_rewards` computes `reward_withdraw_amount = 500`, splits 500 from `rewards_pool`. Pool now has `rewards_pool = 500 SUI`.
5. Staker B calls `sui_system::request_withdraw_stake` in the **same epoch** → `withdraw_rewards` computes `reward_withdraw_amount = 500` (same exchange rate), but `pool.rewards_pool.value() = 500`. In this case it works. However, if a third staker C also withdraws 500 pool tokens, `withdraw_rewards` computes `reward_withdraw_amount = 500` but `pool.rewards_pool.value() = 0`. The `.min()` clamps to 0. Staker C receives only their 500 SUI principal and **zero rewards**, permanently losing 500 SUI in entitled rewards with no error, no event, and no recourse. [6](#0-5)

public(package) fun request_withdraw_stake(
    pool: &mut StakingPool,
    staked_sui: StakedSui,
    ctx: &TxContext,
): Balance<SUI> {
    // stake is inactive and the pool is not preactive - allow direct withdraw
    // the reason why we exclude preactive pools is to avoid potential underflow
    // on subtraction, and we need to enforce `pending_stake_withdraw` call.
    if (staked_sui.stake_activation_epoch > ctx.epoch() && !pool.is_preactive()) {
        let principal = staked_sui.into_balance();
        pool.pending_stake = pool.pending_stake - principal.value();
        return principal
    };

    let (pool_token_withdraw_amount, mut principal_withdraw) = pool.withdraw_from_principal(
        staked_sui,
    );
    let principal_withdraw_amount = principal_withdraw.value();

    let rewards_withdraw = pool.withdraw_rewards(
        principal_withdraw_amount,
        pool_token_withdraw_amount,
        ctx.epoch(),
    );
    let total_sui_withdraw_amount = principal_withdraw_amount + rewards_withdraw.value();

    pool.pending_total_sui_withdraw = pool.pending_total_sui_withdraw + total_sui_withdraw_amount;
    pool.pending_pool_token_withdraw =
        pool.pending_pool_token_withdraw + pool_token_withdraw_amount;

    // If the pool is inactive or preactive, we immediately process the withdrawal.
    if (pool.is_inactive() || pool.is_preactive()) pool.process_pending_stake_withdraw();

    // TODO: implement withdraw bonding period here.
    principal_withdraw.join(rewards_withdraw);
    principal_withdraw
}
