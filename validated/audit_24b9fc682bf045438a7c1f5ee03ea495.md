### Title
Unbounded recursive RLP decoding of `TrieNode` allows stack-exhaustion DoS of the fault-proof program - ([File: crates/proof/mpt/src/node.rs])

### Summary
`TrieNode::decode` recursively decodes nested MPT nodes with no depth bound, mirroring the QPDF tokenizer bug class in the report (unbounded recursion for nested data structures leading to stack consumption / crash).

### Finding Description
`TrieNode::decode` inspects the RLP header and, for a 2-item list, calls `try_decode_leaf_or_extension_payload`, which — for extension nodes — recursively invokes `Self::decode(buf)` on the child node with no depth counter or limit [1](#0-0) . Branch nodes similarly decode via `Vec::<Self>::decode(buf)`, which decodes each of up to 16 children, each of which can itself be another `Extension`/`Branch`, recursing arbitrarily deep [2](#0-1) . Because a single RLP blob (the preimage supplied through `TrieProvider::trie_node_by_hash`) can encode an arbitrarily long chain of nested `Extension`/`Branch` wrappers, decoding it drives unbounded native-stack recursion, exactly the "recursive tokenizer for arrays/dictionaries...deep data structure" pattern described in ALPINE-CVE-2017-12595 for QPDF's `QPDFObjectHandle::parseInternal`.

`TrieNode` preimages are fetched through the `TrieProvider`/`TrieHinter` interfaces used by the fault-proof program to resolve account/storage trie nodes by hash [3](#0-2) . In the dispute-game/fault-proof context, this preimage data is supplied by an untrusted party (the counter-party in a dispute game, or a malicious preimage-oracle response) and only its keccak hash is verified before/while it is consumed as trie-node bytes — the hash check does not bound the nesting depth of the RLP content, only its byte length matching the hash preimage. A dispute-game participant can therefore craft a preimage blob whose hash matches what's expected but whose RLP payload encodes thousands of nested extension/branch wrappers.

I was not able to fully trace, within the tool-call budget, the exact call site inside the fault-proof program crate that invokes `trie_node_by_hash`/`TrieNode::decode` end-to-end (e.g., whether an explicit depth limit exists further up the stack outside `crates/proof/mpt`), nor did I find any `MAX_DEPTH`/recursion-guard constant anywhere in `crates/proof/mpt/src/*.rs` other than the unrelated CBOR parser's `MAX_CBOR_NESTING_DEPTH` in a different crate (`crates/proof/tee/registrar/src/cbor.rs`), which is not used by the MPT decoder. This should be verified further before treating this as fully confirmed.

### Impact Explanation
If reachable with attacker-controlled bytes in the fault-proof program (running inside a constrained VM/zk environment during dispute resolution), a stack overflow crashes the program before it can produce a valid execution trace/output root. This can halt or corrupt the fault-proof game's evaluation, potentially preventing a correct provable output root from being produced — a "node halt" / "wrong provable output root" class impact for a component explicitly listed in scope ("the fault-proof program and MPT").

### Likelihood Explanation
Likelihood is uncertain without confirming (a) that preimage bytes reaching `TrieNode::decode` are not pre-validated for structural depth elsewhere in the derivation/host pipeline, and (b) that the specific execution environment (native Rust stack size in the fault-proof program's runtime) is small enough to be exhausted by a realistically-sized malicious preimage. Given the uncertainty and that I could not verify the absence of an upstream depth guard, I am not confident this is independently exploitable versus already mitigated by size/gas limits on preimages elsewhere in the stack.

### Recommendation
Add an explicit recursion-depth counter (analogous to `MAX_CBOR_NESTING_DEPTH` in `crates/proof/tee/registrar/src/cbor.rs`) to `TrieNode::decode`/`try_decode_leaf_or_extension_payload`, returning a decode error once a bounded depth (e.g., matching the maximum possible real MPT depth, ~64) is exceeded, rather than relying on the process stack to fail safely.

### Proof of Concept
Not independently constructed/verified — building a concrete failing input requires confirming stack-frame size and the actual harness that feeds `TrieNode::decode`, which was outside the scope of what I could verify via code search alone. Conceptually: RLP-encode `N` nested single-child `Extension` nodes (odd/even nibble prefixes) around a terminal `Leaf`, chosen so `N` is large enough that native recursion in `Self::decode` exhausts the fault-proof program's stack, and supply this blob as the preimage response for the corresponding `trie_node_by_hash` lookup.

    /// Attempts to decode the [`TrieNode`].
    fn decode(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
        // Peek at the header to determine the type of Trie node we're currently decoding.
        let header = Header::decode(&mut (**buf).as_ref())?;

        if header.list {
            // Peek at the RLP stream to determine the number of elements in the list.
            let list_length = rlp_list_element_length(&mut (**buf).as_ref())?;

            match list_length {
                BRANCH_LIST_LENGTH => {
                    let list = Vec::<Self>::decode(buf)?;
                    Ok(Self::Branch { stack: list })
                }
                LEAF_OR_EXTENSION_LIST_LENGTH => {
                    // Advance the buffer to the start of the list payload.
                    buf.advance(header.length());
                    // Decode the leaf or extension node's raw payload.
                    Self::try_decode_leaf_or_extension_payload(buf)
                        .map_err(|_| alloy_rlp::Error::UnexpectedList)
                }
