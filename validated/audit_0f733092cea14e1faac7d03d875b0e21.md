### Title
EI credential holders bypass "EIs not allowed for int IDs" check in `PipelineRunsController.Create` via synthetic run-role user - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` injects a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` into the `SessionUserKey` context value for any request authenticated solely via EI headers. `PipelineRunsController.Create` uses `auth.GetAuthenticatedUser(c)` to decide `isUser`, which returns `true` for this synthetic object, even though the request holds no real user session/token — directly contradicting the code's own comment that "only users are allowed to run jobs using int IDs - EIs not allowed."

### Finding Description
`AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) authenticates a request purely by EI access-key/secret headers (`static.ExternalInitiatorAccessKeyHeader` / `static.ExternalInitiatorSecretHeader`), and on success sets: [1](#0-0) 
This stores a fabricated `clsessions.User` (not a real DB-backed user) under `SessionUserKey`, solely so role-checking middleware (`RequiresRunRole`, etc.) treats EI callers as having "run" privilege.

`PipelineRunsController.Create` then does: [2](#0-1) 
`auth.GetAuthenticatedUser` (`core/web/auth/auth.go:178-187`) simply type-asserts whatever object is stored at `SessionUserKey` — it cannot distinguish a genuine session/token-authenticated user from the synthetic EI stand-in. Since `AuthenticateExternalInitiator` populates the exact same key, `isUser` evaluates to `true` for EI-only-authenticated requests, so the `if isUser` branch executes `prc.App.RunJobV2(ctx, jobID, nil)` for a plain integer job ID — exactly the behavior the inline comment says must be prevented for EIs.

### Impact Explanation
An attacker holding only a valid External Initiator access key/secret (a lower-trust credential intended only to resume webhook-triggered pipeline runs, not to arbitrarily start arbitrary jobs by integer ID) can trigger `RunJobV2` for any job ID reachable via this route. This is an authorization/role-boundary bypass allowing unauthorized job runs, matching the "unauthorized job run" impact class. Depending on the job's tasks, this could cause unwanted external calls, on-chain writes, or resource exhaustion driven by the run pipeline.

### Likelihood Explanation
Preconditions: attacker must possess valid EI access key/secret for the target node (the minimal EI credential explicitly allowed as attacker capability in scope), and the route `/v2/jobs/:ID/runs` must be reachable and configured with `AuthenticateExternalInitiator` in its auth-method chain (consistent with the explicit comment in `auth.go` that EI endpoints assume the run role, implying this route accepts EI auth). Given only credential possession is required and no additional gating exists beyond the flawed `isUser` check, exploitation is straightforward and repeatable for any integer job ID.

### Recommendation
Distinguish real authenticated users from the synthetic EI-injected user before allowing the int-ID run path — e.g., check `auth.GetAuthenticatedExternalInitiator(c)` and reject (or route separately) when an EI is present, or store EI-originated pseudo-users under a different context key so `GetAuthenticatedUser` cannot conflate them with genuine user sessions.

### Proof of Concept
Handler-level integration test in `core/web/pipeline_runs_controller_test.go`:
1. Set up an app with a job having an integer ID.
2. Register/authenticate an External Initiator (via `store.FindExternalInitiator` / EI headers), without any user session or API token.
3. Issue `POST /v2/jobs/:ID/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` (EI headers) only, using the job's integer ID as `:ID`.
4. Assert the response is NOT a created pipeline run (expect rejection, e.g. `422 bad job ID` or similar), and assert `prc.App.RunJobV2` was never invoked.
5. Currently, the test would show a `200`/created pipeline run response, proving the bypass, since `isUser` is `true` for the EI-only request.
