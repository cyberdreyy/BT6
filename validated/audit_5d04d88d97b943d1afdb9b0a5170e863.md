### Title
CPU cost amplification via unbounded zstd compression of attacker-sized on-chain account data on `getAccountInfo(encoding=base64+zstd)` - ([File: account-decoder/src/lib.rs])

### Summary
`encode_ui_account`'s `Base64Zstd` branch calls `zstd::stream::write::Encoder::write_all`/`finish()` directly on the full (or sliced) account data with no size check, unlike the `Base58`/`Binary` paths which are gated by `MAX_BASE58_BYTES`. An attacker who writes a maximal-size, highly-incompressible-time or simply large on-chain account and then issues a single `getAccountInfo` call with `base64+zstd` encoding forces the RPC node to zstd-compress data whose size is entirely attacker-chosen (up to the runtime's max account data length), with no explicit RPC-side size limit gating that compression step.

### Finding Description
`encode_ui_account` in [1](#0-0)  handles `UiAccountEncoding::Base64Zstd` by constructing a zstd `Encoder` and calling `write_all` on `slice_data(account.data(), data_slice_config)` followed by `finish()`, with no length check performed before compressing. This contrasts directly with `encode_bs58` at [2](#0-1)  and the explicit `MAX_BASE58_BYTES` guard applied only to `Binary`/`Base58` encodings in `encode_account` at [3](#0-2) ; no equivalent guard exists for `Base64Zstd`.

The call path from the JSON-RPC entrypoint is: `getAccountInfo` → `JsonRpcRequestProcessor::get_account_info` → `get_encoded_account` → `encode_account` → `encode_ui_account` (Base64Zstd branch), as seen in [4](#0-3) . At no point along this path is there a check that gates the size of the data passed into the zstd encoder — the only size gate in `encode_account` is scoped to `Binary`/`Base58`.

An attacker can use `SystemProgram::CreateAccount`/`Allocate` to grow an owned account up to the maximum permitted account data length (a value defined in the runtime — I was unable to locate its concrete numeric definition in the indexed files, e.g. `programs/system/src/system_processor.rs` and `program-runtime/src/serialization.rs` reference `MAX_PERMITTED_DATA_LENGTH` but the exact constant value was not resolved from the available index). Regardless of the exact cap value, the compression cost scales with attacker-controlled account size, and a single `getAccountInfo(encoding=base64+zstd)` call forces the RPC thread to perform that full compression synchronously (within `spawn_blocking`, per [5](#0-4) ), consuming one blocking-pool thread for the full compression duration.

### Impact Explanation
This is a CPU-cost-amplification / resource-consumption issue on the account-read path: a single unprivileged client request (one `getAccountInfo` call with `base64+zstd` encoding) can force the validator's RPC service to spend CPU time proportional to attacker-chosen on-chain data size, with no size-based rejection analogous to the `MAX_BASE58_BYTES` check. This matches the "unbounded cost for a single low-rate call" category permitted by the rules. The impact is scoped to the RPC-serving thread pool (a `spawn_blocking` task) rather than the consensus/banking path, so it does not affect consensus state, but repeated single such calls (still within the one-call-per-half-slot-time budget) could tie up blocking-thread-pool capacity used to serve other RPC reads.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controllable: fund and grow a normal, unprivileged account to the maximum permitted size via standard `SystemProgram::CreateAccount`/`Allocate` instructions, then issue a single `getAccountInfo` call with `UiAccountEncoding::Base64Zstd`. No special privileges, leader/validator control, or multiple concurrent calls are required — this fits squarely within the single-call, single-client threat model. The main uncertainty is the magnitude of real-world impact, since zstd compression throughput is generally high (hundreds of MB/s) even for large or adversarial inputs, so the amplification factor per single call may be modest unless combined with other data-size or client-repeated-request behavior; without confirming the exact `MAX_PERMITTED_DATA_LENGTH` constant and doing a benchmark, the severity in absolute wall-clock terms is not fully substantiated in this environment.

### Recommendation
Add an explicit size gate for the `Base64Zstd` encoding path in `encode_account`/`encode_ui_account`, similar to the existing `MAX_BASE58_BYTES` check for `Binary`/`Base58`, e.g., reject or fall back to plain `Base64` (without compression) when `slice_data(...).len()` exceeds a defined maximum before invoking the zstd encoder, so that server-side CPU cost of compression is bounded independent of attacker-authored account size.

### Proof of Concept
```rust
// account-decoder/src/lib.rs (add to existing #[cfg(test)] mod test)
#[test]
fn test_base64_zstd_cost_scales_unbounded_with_account_size() {
    use std::time::Instant;

    // Simulate a maximal-size, attacker-controlled account (e.g., 10 MiB of zeros
    // or a size representative of MAX_PERMITTED_DATA_LENGTH).
    let large_data = vec![0u8; 10 * 1024 * 1024];
    let account = AccountSharedData::from(Account {
        data: large_data,
        ..Account::default()
    });

    let start = Instant::now();
    let encoded_account = encode_ui_account(
        &Pubkey::default(),
        &account,
        UiAccountEncoding::Base64Zstd,
        None,
        None,
    );
    let elapsed = start.elapsed();

    // No size gate exists today: this call always proceeds to compress the full
    // account regardless of size. A fix should assert that requests above some
    // MAX_ZSTD_INPUT_BYTES either fail fast (Err) or fall back to Base64 without
    // ever invoking the zstd encoder, keeping `elapsed` bounded independent of
    // the caller-chosen account size.
    assert_matches!(
        encoded_account.data,
        UiAccountData::Binary(_, UiAccountEncoding::Base64Zstd)
    );
    println!("compress 10MiB took: {:?}", elapsed);
    // Expected after fix: either an early rejection (no compression attempted)
    // or a documented, enforced upper bound on compression input size.
}
```
Run this benchmark across increasing account sizes up to the maximum permitted account data length and confirm that, absent a fix, compression time grows linearly with attacker-controlled size and no size check short-circuits it before the `zstd::stream::write::Encoder` call in [1](#0-0) .

```rust
fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
```
