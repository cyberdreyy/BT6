### Title
API tokens remain valid after password reset, enabling persistent access via stale credentials - (File: core/sessions/localauth/orm.go)

### Summary
The local-auth `SetPassword` implementation only updates `hashed_password` and never rotates or clears the user's `token_salt`, `token_key`, or `token_hashed_secret` columns. Because token-based authentication (`AuthenticateByToken`) validates requests purely against these token fields, a previously issued API token continues to authenticate successfully even after the account password has been changed via `UpdatePassword`/`UpdateUserPassword`.

### Finding Description
`orm.SetPassword` at [1](#0-0)  only executes `UPDATE users SET hashed_password = $1, updated_at = now() WHERE email = $2`, leaving `token_salt`/`token_key`/`token_hashed_secret` untouched. The REST password-change flow, `UserController.UpdatePassword` → `updateUserPassword`, at [2](#0-1)  only calls `ClearNonCurrentSessions` (which purges cookie-based sessions) and `SetPassword`; it never calls `DeleteAuthToken` or `SetAuthToken`. The GraphQL equivalent `UpdateUserPassword` resolver at [3](#0-2)  follows the identical pattern.

Meanwhile, `AuthenticateByToken` at [4](#0-3)  authenticates purely by looking up the user via `FindUserByAPIToken(ctx, token.AccessKey)` (`core/sessions/localauth/orm.go:49-53`) and comparing `token.Secret` against `TokenHashedSecret` using `AuthenticateUserByToken` (`core/sessions/session.go:66-74`) — this path has zero dependency on `hashed_password`. Since `SetPassword` never invalidates the token fields, a token issued via `CreateAndSetAuthToken`/`SetAuthToken` before the password reset continues to authenticate every subsequent API request after the reset, bypassing the intent of credential rotation.

### Impact Explanation
This is a persistent-credential/authentication-bypass issue: rotating a user's password (whether done by the user themselves after suspecting compromise, or by an admin responding to an incident) fails to revoke a previously leaked or attacker-held API token. This maps to Chainlink's "authentication bypass" / "unauthorized persistent access" bounty impact class — an attacker who obtained a victim's API token (e.g., via a prior leak) retains full API access matching the victim's role indefinitely, regardless of subsequent password resets, undermining the security assumption that password rotation revokes account access.

### Likelihood Explanation
Preconditions are minimal and realistic: the attacker only needs to have previously obtained a valid API token for the target account (e.g., from a leaked config file, log, or compromised CI secret) — a scenario this project's own bounty program treats as a credible threat model given `X-API-KEY`/`X-API-SECRET` are commonly stored in `apicredentials` files and shell/CI environments. No admin, host, or DB access is needed by the attacker; only the already-issued token. The behavior is fully deterministic and repeatable via `UpdatePassword`/`UpdateUserPassword` followed by any authenticated GET/POST using the old token.

### Recommendation
Have `SetPassword` (or the callers in `UserController.UpdatePassword` / `Resolver.UpdateUserPassword`) also call `DeleteAuthToken` (or re-issue via `SetAuthToken`) to invalidate any existing API token whenever a password is changed, mirroring the existing `ClearNonCurrentSessions` call that already purges session cookies on password change.

### Proof of Concept
Go integration test plan (mirrors `core/internal/features/features_test.go:TestIntegration_AuthToken` and `core/web/user_controller_test.go:TestUserController_UpdatePassword`):
1. Start app, create user, issue API token via `orm.SetAuthToken`/`CreateAndSetAuthToken`.
2. Assert an authenticated GET to a protected route (e.g. `/v2/bridge_types/`) using `X-API-KEY`/`X-API-SECRET` headers succeeds (200).
3. Call `PATCH /v2/user/password` (or GraphQL `updateUserPassword`) as the same user with a valid old→new password change; assert success (200).
4. Replay the exact same original `X-API-KEY`/`X-API-SECRET` headers against the protected route.
5. Expected (secure) behavior: 401 Unauthorized. Actual (vulnerable) behavior: 200 OK, proving the token survives password rotation.
6. Add assertion that after fix, `dbUser.TokenKey`/`TokenHashedSecret` are empty or rotated post-`UpdatePassword`, matching the pattern already used in `TestOrm_GenerateAuthToken` (`core/sessions/localauth/orm_test.go:321-351`) for `DeleteAuthToken`.

func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}
