### Title
Deposit attached to `DeterministicStateInitAction` is silently lost (no refund, no credit) when `use_global_contract` fails on the receiver shard - ([File: runtime/runtime/src/deterministic_account_id.rs])

### Summary
When a smart contract calls `promise_batch_action_state_init_by_account_id` (or the code-hash variant) with a nonzero `amount`, the deposit is deducted from the sender's in-flight balance immediately at schedule time via `deduct_balance` in `promise_batch_action_state_init_impl`. If the referenced `GlobalContractIdentifier` cannot be resolved when the resulting `DeterministicStateInitAction` executes on the receiver shard, `action_deterministic_state_init` returns early without crediting the deposit to the receiver account and without generating any refund receipt, permanently destroying the deducted balance.

### Finding Description
At schedule time, `promise_batch_action_state_init_impl` unconditionally deducts the deposit from the sender's balance and appends the action to the receipt: [1](#0-0) 

On the receiver shard, `action_deterministic_state_init` handles the `uninit -> active` transition by calling `deploy_deterministic_account`, which in turn calls `use_global_contract`: [2](#0-1) [3](#0-2) 

`use_global_contract` sets `result.result = Err(ActionErrorKind::GlobalContractDoesNotExist { .. })` and returns `Ok(())` when the identifier (code hash or account id) does not resolve to a deployed global contract: [4](#0-3) 

Back in `action_deterministic_state_init`, the check `if result.result.is_err() { return Ok(()); }` fires immediately after `deploy_deterministic_account` returns, before the deposit-refund logic (`check_storage_stake` / `deposit_refund` / push of a `Receipt::new_balance_refund`) is ever reached: [5](#0-4) 

Note that `action.deposit` is never added to `account.amount()` unconditionally — it is only credited inside the `check_storage_stake` match arms (either fully refunded when storage is not needed, or partially consumed via `safe_add_balance` when storage staking requires it, with a refund receipt for the remainder). Because the `use_global_contract` failure path exits before this match block is ever reached, the deposit is neither credited to the new account nor refunded to `receipt.balance_refund_receiver()`. The amount that was deducted from the sender at `deduct_balance` time simply vanishes from total supply.

An attacker (unprivileged, ordinary account) can trigger this deterministically and without any special access:
1. Deploy their own wasm contract.
2. Call a method that invokes `promise_batch_action_state_init_by_account_id` with a `GlobalContractIdentifier::AccountId` (or hash) that has never deployed a global contract, and a nonzero `amount`.
3. The outgoing receipt deducts `amount` from the sender's balance at schedule time.
4. On the receiver shard, `use_global_contract` fails (`GlobalContractDoesNotExist`), and `action_deterministic_state_init` returns before any refund logic runs.
5. No refund receipt is created, and `action.deposit` is never added to any account balance — the funds are unrecoverably lost.

No existing signature/nonce/gas/storage-staking check prevents this: gas accounting and the storage-staking check govern only successfully-resolved global contracts; the `GlobalContractDoesNotExist` branch is a distinct pre-storage-staking failure path that the refund logic never covers.

### Impact Explanation
This is a permanent loss of user funds (token burn), violating value conservation. The deposit debited from the sender's account disappears from total supply — it is not credited to the receiver, not refunded to the sender, and not burnt as a fee (no `tokens_burnt` accounting for it either). This matches the "Stealing or loss of funds" bounty category.

### Likelihood Explanation
Trivial precondition and cost: the attacker only needs a funded account and a trivial wasm contract that calls `promise_batch_action_state_init_by_account_id`/`promise_batch_action_state_init` with an unresolved `GlobalContractIdentifier` and any nonzero deposit. This requires no special account, no validator/node privilege, and is fully repeatable at will — attacker (or anyone, even accidentally, e.g. due to a typo in a global contract account id or a stale/removed global contract) can trigger loss of an arbitrary amount of funds with each such call.

### Recommendation
In `action_deterministic_state_init` (`runtime/runtime/src/deterministic_account_id.rs`), when `deploy_deterministic_account` sets `result.result` to an error (e.g., `GlobalContractDoesNotExist`), push a `Receipt::new_balance_refund(receipt.balance_refund_receiver(), action.deposit)` for the full `action.deposit` before returning, mirroring the refund behavior already present in the `check_storage_stake` success/partial-use paths.

### Proof of Concept
Add a test-loop integration test in `test-loop-tests/src/tests/deterministic_account_id.rs`:
1. Construct a `DeterministicAccountStateInit::V1` referencing a `GlobalContractIdentifier::AccountId` (or `CodeHash`) that is never deployed.
2. Derive the deterministic account id and submit a `DeterministicStateInitAction` (directly, or via a contract calling `promise_batch_action_state_init_by_account_id`) with `deposit > 0` from a funded signer account.
3. Run the transaction/receipt to completion.
4. Assert:
   - The execution outcome for the `DeterministicStateInitAction` fails with `ActionErrorKind::GlobalContractDoesNotExist`.
   - No account balance (sender, receiver, or any intermediate account) ends up holding the deposited amount.
   - **Currently missing/expected to fail**: assert that a `Receipt::new_balance_refund` for the full `deposit` is emitted to `receipt.balance_refund_receiver()` — this assertion will fail on the current code, confirming the fund-loss bug, and should pass once the fix pushes the refund receipt.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
