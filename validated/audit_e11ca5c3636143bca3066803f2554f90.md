### Title
Unbounded per-call cost in `getProgramAccounts` (jsonParsed) over a secondary-indexed program allows N×parse_config decode/re-serialize work with no request-size cap - ([File: rpc/src/rpc.rs])

### Summary
`JsonRpcRequestProcessor::get_program_accounts` in `rpc/src/rpc.rs` fetches all indexed accounts for `solana_config_interface::id()` via `get_filtered_indexed_accounts`/`index_scan_accounts` and then, for `jsonParsed` encoding, calls `encode_account` → `parse_account_data_v3` → `parse_config` once per returned account with no limit on the number of accounts or aggregate bytes processed in a single call. An attacker who pre-writes N maximal-size Config/ValidatorInfo accounts can force one low-rate RPC call to parse and re-serialize O(N × MAX_VALIDATOR_INFO) bytes.

### Finding Description
The RPC handler path is:
- `rpc_accounts_scan::AccountsScan::get_program_accounts` (`rpc/src/rpc.rs:3422-3446`) validates the pubkey/filters and calls `meta.get_program_accounts(...)`.
- `JsonRpcRequestProcessor::get_program_accounts` (`rpc/src/rpc.rs:603-671`) resolves accounts through `get_filtered_program_accounts` (`rpc/src/rpc.rs:2254-2308`), which for an indexed program id (`self.config.account_indexes.contains(&AccountIndex::ProgramId)`) calls `get_filtered_indexed_accounts`. This ultimately reaches `AccountsDb::index_scan_accounts` (`accounts-db/src/accounts_db.rs:3358-3421`), which iterates `self.accounts_index.get_index_key_pubkeys(&index_key)` and loads every matching account with `do_load`, with no count or byte-size cap on the returned set ( [1](#0-0) ).
- Back in `get_program_accounts` (`rpc/src/rpc.rs:652-666`), for non-SPL-token programs each `(pubkey, account)` is passed to `encode_account(&account, &pubkey, encoding, data_slice_config)` for every returned account, with `encoding == UiAccountEncoding::JsonParsed` triggering `parse_account_data_v3` → `parse_config(data, pubkey)` (`account-decoder/src/parse_account_data.rs:143`, `account-decoder/src/parse_config.rs:13-29`) per account ( [2](#0-1) ).
- `parse_config` deserializes `ConfigKeys`, extracts `config_data` via `get_config_data`, and does a further `serde_json::from_str` deserialize/re-serialize of the validator-info JSON blob for every matching account ( [3](#0-2) ).

Each such Config account can independently be written by any unprivileged account up to `MAX_VALIDATOR_INFO = 576` bytes of config data ( [4](#0-3) ). There is no limit anywhere in `get_program_accounts`, `get_filtered_program_accounts`, `get_filtered_indexed_accounts`, or `index_scan_accounts` on the number of accounts returned per call or on the aggregate bytes decoded/parsed/re-serialized. The comment at `rpc/src/rpc.rs:2284` ("this path does not need to provide a mb limit because we only want to support secondary indexes") confirms the indexed path intentionally has no size limit, relying instead on operator-side indexing being deliberately scoped — but that scoping only bounds *which keys* are indexed, not the *volume* of matching data behind one indexed key.

### Impact Explanation
This matches the "unbounded cost for a single low-rate call" category in scope. A single `getProgramAccounts(solana_config_interface::id(), {"encoding":"jsonParsed"})` call causes the validator's RPC-serving thread to perform O(N) bincode deserializations, `get_config_data` slicing, and `serde_json` deserialize+serialize round-trips proportional to the total pre-seeded data (up to `N × 576` bytes plus `ConfigKeys` overhead), all within one request whose cost is bounded only by how much data the attacker previously wrote on-chain rather than by any explicit per-request CPU/memory/response-size cap. This directly matches the invariant under test: "cost of one request bounded by explicit limits, not by aggregate on-chain data reachable via one indexed call."

### Likelihood Explanation
Preconditions are fully attacker-reachable and match the in-scope rules: (1) attacker writes N maximal Config accounts independently, no privilege required (standard `solana_config_interface` config-account creation costs only rent/lamports); (2) operator has enabled `--account-index program-id` (explicitly called out as in-scope in the question since it is index-backed); (3) attacker issues a single `getProgramAccounts` call with `jsonParsed` encoding, at or below the allowed rate of one call per `CLUSTER_SLOT_TIME_TARGET / 2`. This is fully repeatable and scales linearly with attacker-controlled N.

### Recommendation
Add an explicit cap in `get_filtered_indexed_accounts`/`index_scan_accounts` (or in `JsonRpcRequestProcessor::get_program_accounts`) on the number of accounts and/or total bytes processed per `getProgramAccounts` call when using a secondary index, returning an RPC error (e.g., similar to `RpcCustomError::ScanError`) once a fixed account-count or aggregate-byte budget is exceeded, independent of how much matching data exists on-chain.

### Proof of Concept
Integration test plan (in `rpc/src/rpc.rs` test module, extending `test_rpc_get_program_accounts`):
1. Start `RpcHandler` with `account_indexes` configured to include `AccountIndex::ProgramId` for `solana_config_interface::id()` (mirrors `test_get_filtered_indexed_accounts` setup pattern in `runtime/src/bank/tests.rs:3504-3529`).
2. Pre-seed N (e.g., 5,000) Config accounts owned by `solana_config_interface::id()`, each containing `ConfigKeys{keys: [(validator_info::id(), false), (some_pubkey, true)]}` followed by a `config_data` string near `MAX_VALIDATOR_INFO` (576 bytes) JSON payload, via `bank.store_account`.
3. Issue a single `getProgramAccounts` JSON-RPC request with `{"encoding": "jsonParsed"}` against `solana_config_interface::id()`.
4. Measure wall-clock time and peak allocation for step 3 as N grows (e.g., N = 100, 1000, 5000), asserting cost grows linearly with N×576 bytes with no request-level cap enforced, i.e., no error is returned and latency exceeds a fixed baseline multiple (e.g., 10×) of the single-account baseline once N is large — demonstrating the missing explicit per-request budget described in the invariant.

pub fn parse_config(data: &[u8], _pubkey: &Pubkey) -> Result<ConfigAccountType, ParseAccountError> {
    let parsed_account = deserialize::<ConfigKeys>(data).ok().and_then(|key_list| {
        if !key_list.keys.is_empty() && key_list.keys[0].0 == validator_info::id() {
            parse_config_data::<String>(data, key_list.keys).and_then(|validator_info| {
                Some(ConfigAccountType::ValidatorInfo(UiConfig {
                    keys: validator_info.keys,
                    config_data: serde_json::from_str(&validator_info.config_data).ok()?,
                }))
            })
        } else {
            None
        }
    });
    parsed_account.ok_or(ParseAccountError::AccountNotParsable(
        ParsableAccount::Config,
    ))
}
