### Title
Anyone can grief a victim's sync `redeem`/`withdraw` by repeatedly triggering `deposit`/`mint` on their behalf, perpetually extending `userUnitsRefundableUntil` - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.deposit()` and `mint()` allow **any caller** to specify an arbitrary `receiver` address and, on every successful sync deposit, unconditionally set `userUnitsRefundableUntil[receiver] = block.timestamp + depositRefundTimeout` [1](#0-0) . `redeem()` and `withdraw()` both gate on `userUnitsRefundableUntil[msg.sender] < block.timestamp` [2](#0-1) [3](#0-2) . This is the same "attacker keeps refreshing a per-user cooldown window to block the victim's own withdrawal path" root cause described in the GMX/PirexGmx report, applied to Aera's `depositRefundTimeout` lock instead of GMX's `cooldownDuration`.

### Finding Description
`deposit(token, tokensIn, minUnitsOut, receiver)` and `mint(token, unitsOut, maxTokensIn, receiver)` only validate that `receiver` is a well-formed address via `_requireValidReceiver` [4](#0-3) [5](#0-4) ; neither function checks `depositReceiverApprovals[receiver][msg.sender]`, which is only ever *set* by `setDepositReceiverApproval` [6](#0-5)  but is never read/enforced inside `deposit`/`mint`. As a result, any ordinary user can call `deposit()`/`mint()` with `receiver = victim` and a minimal `tokensIn` (just enough that `_tokensToUnitsFloorIfActive` rounds to ≥1 unit, satisfying `minUnitsOut`), which calls `_syncDeposit(token, tokenAmount, unitAmount, receiver)`. This function unconditionally overwrites `userUnitsRefundableUntil[receiver]` to `block.timestamp + depositRefundTimeout` [7](#0-6) .

`redeem()` and `withdraw()` — the synchronous exit paths — require `userUnitsRefundableUntil[msg.sender] < block.timestamp` before proceeding [8](#0-7) [9](#0-8) . An attacker who repeatedly (every `depositRefundTimeout` seconds, bounded by `MAX_DEPOSIT_REFUND_TIMEOUT` [10](#0-9) ) deposits a trivial amount on behalf of the victim keeps refreshing this lock, permanently blocking the victim's `redeem`/`withdraw` calls exactly as GMX's `cooldownDuration` blocked PirexGmx's `_removeLiquidity` — the victim never consented to or benefits from these deposits, and the lock timestamp is keyed solely off `receiver`, not off any spender-approval or benefit check.

### Impact Explanation
The victim is denied use of the synchronous `redeem`/`withdraw` exit functions for as long as the attacker keeps re-triggering deposits in their name, at a cost proportional only to gas plus a negligible token amount (rounding-safe minimum). This is a temporary freezing of a user's ability to exit via the sync path, matching Immunefi's Medium "temporary freezing of funds" category — analogous to the cited GMX/PirexGmx cooldown-griefing report. Note: the async `requestRedeem`/`solveRequestsDirect`/`solveRequestsVault` paths do not check `userUnitsRefundableUntil`, so full permanent freezing of principal is not achieved, but the sync redemption/withdrawal function is reliably and continuously blocked.

### Likelihood Explanation
High feasibility: no privileged role is required, `deposit`/`mint` are public functions callable by any address for any `receiver`, and the attack only costs gas plus a minimal token amount per refresh cycle. The only prerequisite is that `depositRefundTimeout` is nonzero (which is the intended operating configuration, since it exists to allow refunds).

### Recommendation
Enforce `depositReceiverApprovals[receiver][msg.sender]` (or `msg.sender == receiver`) inside `deposit()` and `mint()` before allowing a caller to deposit on behalf of another address, so a victim's `userUnitsRefundableUntil` can only be extended by deposits they authorized. Additionally, consider decoupling the refund-timeout lock from `redeem`/`withdraw` eligibility so a benign refundable-deposit window cannot be weaponized against unrelated exit calls.

### Proof of Concept
Local Foundry fork steps:
1. Deploy `ProvisionerV2` with `depositRefundTimeout = T` (e.g. 15 minutes) and a token with sync deposits enabled.
2. Victim deposits normally via `deposit()` as their own receiver, then attempts `redeem()` — succeeds once `T` has elapsed.
3. Attacker (separate address, no approval from victim) calls `deposit(token, minimalTokensIn, 1, victim)` every `T` seconds in a loop.
4. Assert `provisioner.areUserUnitsLocked(victim) == true` continuously.
5. Assert victim's call to `redeem()`/`withdraw()` reverts with `Aera__UnitsLocked()` for as long as the attacker keeps refreshing, while the attacker's cost per cycle is only gas + negligible token amount.

    function deposit(IERC20 token, uint256 tokensIn, uint256 minUnitsOut, address receiver)
        external
        nonReentrant
        anyoneButVault
        solvingNotPaused(token)
        returns (uint256 unitsOut)
    {
        // Requirements: receiver is valid
        _requireValidReceiver(receiver);

        // Requirements: token amount and min units out are positive
        _validateNonZeroAmounts(minUnitsOut, tokensIn);

        // Requirements: sync deposits are enabled
        TokenDetailsV2 storage tokenDetails = _requireSyncDepositsEnabled(token);

        // Interactions: convert token amount to units out

        // Requirements: units out meets min units out

        // Effects + interactions: sync deposit
        _syncDeposit(token, tokensIn, unitsOut, receiver);

        // Interactions: push funds to yield source if configured (swallows failures)

    }

    function _syncDeposit(IERC20 token, uint256 tokenAmount, uint256 unitAmount, address receiver) internal {
        uint256 refundableUntil = block.timestamp + depositRefundTimeout;
        bytes32 depositHash = _getDepositHash(msg.sender, receiver, token, tokenAmount, unitAmount, refundableUntil);

        // Requirements: deposit hash is not set
        require(!syncDepositHashes[depositHash], Aera__HashCollision());
        // Effects: set hash as used
        syncDepositHashes[depositHash] = true;

        // Effects: set receiver's refundable until timestamp
        userUnitsRefundableUntil[receiver] = refundableUntil;

        // Interactions: enter vault
        IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).enter(msg.sender, token, tokenAmount, unitAmount, receiver);

        // Log deposit event
        emit Deposited(msg.sender, receiver, token, tokenAmount, unitAmount, depositHash);
    }
