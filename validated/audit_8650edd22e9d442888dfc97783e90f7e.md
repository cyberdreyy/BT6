### Title
Default recovery payout can be permanently burned by claiming to `address(0)` - ([File: contracts/DefaultDistributor.sol](contracts/DefaultDistributor.sol))

### Summary
`DefaultDistributor.claim` lets a tranche-token holder specify an arbitrary payout recipient, but it does not reject `address(0)` before transferring the holder’s recovery payout. For underlying tokens that allow transfers to the zero address, the tranche tokens are permanently escrowed and the recovery payout is burned. [1](#0-0) 

### Finding Description
After a default, `DefaultDistributor` is intended to exchange each claimant’s full tranche balance for a pro-rata amount of `token`. The function first transfers all of `msg.sender`’s tranche tokens into the distributor and then sends `trancheBal * rate / ONE_TRANCHE` underlying tokens to the user-supplied `_to`. [2](#0-1) 

There is no `_to != address(0)` validation. Other production code explicitly treats a zero withdrawal recipient as invalid, demonstrating that this invariant is recognized elsewhere. [3](#0-2) 

The claim is active once the honest owner calls `setIsActive(true)`, which freezes the payout rate from the distributor’s token balance and current tranche supply. [4](#0-3) 

### Impact Explanation
A lender calling `claim(address(0))` irrevocably surrenders its entire tranche balance but receives no usable recovery funds when the configured underlying token accepts a zero-address transfer. The tranche tokens remain held by the distributor while the underlying payout becomes inaccessible at `address(0)`, permanently destroying the claimant’s recovery value. [5](#0-4) 

The loss equals the claimant’s full claim entitlement, `balanceOf(msg.sender) * rate / 1e18`. Because the function always uses the caller’s entire tranche balance, a zero recipient forfeits the caller’s complete post-default claim rather than a user-selected partial amount. [5](#0-4) 

### Likelihood Explanation
Exploitation does not require any privileged role, borrower cooperation, epoch manipulation, or third-party action. After claims are activated, any tranche holder that supplies `address(0)`—directly or through an integration that leaves the recipient unset—executes the loss in one transaction. [1](#0-0) 

The issue is token-dependent: it materializes when the configured recovery token permits transfers to the zero address. The distributor is implemented against generic `IERC20`, so it does not restrict deployment to tokens that reject such transfers. [6](#0-5) 

### Recommendation
Reject the zero recipient before any token movements:

```solidity
// contracts/DefaultDistributor.sol
function claim(address _to) external {
    require(_to != address(0), 'TO_0');
    require(isActive, '!ACTIVE');
    IERC20 tranche = IERC20(trancheToken);
    uint256 trancheBal = tranche.balanceOf(msg.sender);
    tranche.safeTransferFrom(msg.sender, address(this), trancheBal);
    IERC20(token).safeTransfer(_to, trancheBal * rate / ONE_TRANCHE);
}
```

The check must occur before `safeTransferFrom` so the entire transaction reverts atomically and cannot strand or burn the claimant’s tranche claim. [1](#0-0) 

### Proof of Concept
The following Foundry test uses an ERC20 that permits zero-address transfers to demonstrate the accounting and payout failure:

```solidity
// test/foundry/DefaultDistributorZeroRecipient.t.sol
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "../../contracts/DefaultDistributor.sol";
import "../../contracts/IdleCDOTranche.sol";

contract ZeroTransferToken is ERC20 {
    constructor() ERC20("ZeroTransferToken", "ZTT") {}

    function mint(address to, uint256 amount) external {
        _mint(to, amount);
    }

    function _beforeTokenTransfer(
        address,
        address,
        uint256
    ) internal pure override {
        // Intentionally allow transfers to address(0), as some ERC20s do.
    }
}

contract DefaultDistributorZeroRecipientTest is Test {
    ZeroTransferToken internal underlying;
    IdleCDOTranche internal tranche;
    DefaultDistributor internal distributor;

    address internal user = address(0xA11CE);

    function setUp() public {
        underlying = new ZeroTransferToken();
        tranche = new IdleCDOTranche("Tranche", "TR");
        distributor = new DefaultDistributor(
            address(underlying),
            address(tranche),
            address(this)
        );

        tranche.mint(user, 100e18);
        underlying.mint(address(distributor), 200e18);
        distributor.setIsActive(true);

        vm.prank(user);
        tranche.approve(address(distributor), type(uint256).max);
    }

    function testClaimToZeroBurnsRecoveryPayout() public {
        uint256 expectedPayout = 100e18 * distributor.rate() / 1e18;

        vm.prank(user);
        distributor.claim(address(0));

        assertEq(tranche.balanceOf(user), 0);
        assertEq(tranche.balanceOf(address(distributor)), 100e18);
        assertEq(underlying.balanceOf(address(0)), expectedPayout);
        assertEq(underlying.balanceOf(user), 0);
    }
}
```

The test passes when the token accepts the zero-address transfer: the user’s full tranche balance is escrowed, while the corresponding recovery payout is sent to `address(0)` and becomes inaccessible. [1](#0-0)
