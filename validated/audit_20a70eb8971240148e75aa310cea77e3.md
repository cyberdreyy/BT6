### Title
Stale unresolved `savedCallback` entries after partial `SendToNode` failures enable cross-request response hijacking via `MessageId` collision - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` registers `h.savedCallbacks[msg.Body.MessageId]` before attempting to relay the request to all DON members, but on partial or total `SendToNode` failure it only returns a joined error without deleting the entry it just created. Because the map is keyed solely by the client-supplied `MessageId` with no sender binding, this stale/orphaned entry can later be overwritten by any subsequent request (from the same or a colliding `MessageId`), and the eventual (possibly delayed) node response for the original request will be delivered to whichever callback currently occupies that map slot.

### Finding Description
In `HandleLegacyUserMessage`, the callback is saved unconditionally before nodes are contacted: [1](#0-0) 

If `don.SendToNode` fails for some or all `donConfig.Members`, the function returns `errors.Join(err, ...)` without removing `h.savedCallbacks[msg.Body.MessageId]`. In `gateway.ProcessRequest`, a non-nil error from `HandleLegacyUserMessage` causes the gateway to immediately return an error response to the original caller without ever calling `callback.Wait`: [2](#0-1) 

The map entry therefore remains alive, unresolved, until `pruneCallbacks()` removes it after `CallbackMaxAgeSec` (default 120s): [3](#0-2) 

Meanwhile, `handleWebAPITriggerMessage`, invoked from `HandleNodeMessage` on any subsequent node response, resolves purely by `MessageId` with no sender/session binding: [4](#0-3) 

Because `MessageId` is fully attacker-controlled (part of the signed `api.Message.Body`, only checked for length/format in `Message.Validate`) and the map key has no per-sender namespace, any new `HandleLegacyUserMessage` call using the same `MessageId` as an existing, not-yet-pruned entry will silently overwrite it. If the original send was reported as failed but a node actually still processed and later responded (e.g., a transient error rather than true delivery failure), that late response will be routed to whichever callback currently sits in the map — potentially a different (attacker-controlled) request.

### Impact Explanation
This is a cross-request/cross-user response confusion primitive: a legitimate response intended for request A's caller can be delivered instead to request B's caller if B reused A's `MessageId` while A's entry was still stranded in the map due to the missing cleanup on partial-failure paths. The Chainlink bounty impact class most closely matched is "attacker-controlled data returned to another user" / cross-user response confusion, though the practical severity is capped by the fact that exploitation additionally requires either colliding with a legitimate victim's `MessageId` (which depends on how unpredictable client-chosen IDs are) or racing one's own stale entry — the latter has no cross-user value.

### Likelihood Explanation
- Precondition: attacker only needs the ability to sign and submit `api.Message` requests to the gateway HTTP endpoint — no privileged role required.
- Triggering the stale-entry condition requires that `don.SendToNode` return an error for at least one member while the underlying delivery may still eventually succeed (partial/soft failures), which is plausible under network flakiness but not attacker-controlled directly.
- Full cross-user exploitation additionally requires guessing/colliding with another party's in-flight `MessageId`, which is not demonstrated to be feasible against random/UUID-style identifiers; self-directed reuse (attacker overwriting their own stale entry) is trivially reproducible but has no cross-privilege impact.
- Overall, the missing cleanup is confirmed and reproducible as a code-level defect, but reliable weaponization against a specific victim depends on `MessageId` predictability, which is not established in this codebase region.

### Recommendation
On any `SendToNode` failure path in `HandleLegacyUserMessage` (partial or total), delete the just-created `h.savedCallbacks[msg.Body.MessageId]` entry (or only insert it after all sends succeed, or track per-member send status and only leave the callback registered if delivery is confirmed to at least one node). Additionally, consider binding the callback map key to `(sender, MessageId)` instead of `MessageId` alone to eliminate any possibility of cross-sender collision regardless of cleanup timing.

### Proof of Concept
1. In `handler_test.go`, build on the existing `TestHandlerReceiveHTTPMessageFromClient`-style setup with a DON mock (`don.SendToNode`) configured to return an error for every member address.
2. Call `handler.HandleLegacyUserMessage(ctx, msg, cb)` with a message whose `Body.MessageId = "dup-id"`; assert the returned error is non-nil (joined from all members).
3. Lock `handler.mu` and assert `handler.savedCallbacks["dup-id"]` still exists (demonstrating the cleanup bug), contrasting with the existing test `"savedCallbacks stored only when message is valid"` which only covers pre-send validation failures, not post-send partial failures.
4. Reconfigure the DON mock to succeed, and call `handler.HandleLegacyUserMessage` again with a second message reusing `Body.MessageId = "dup-id"` and a second callback `cb2`.
5. Call `handler.HandleNodeMessage` with a node response addressed to `MessageId = "dup-id"` and assert the response is delivered to `cb2` (via `cb2.Wait`) and not to the original `cb`, confirming the overwrite/hijack path.

```go
func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}
```
