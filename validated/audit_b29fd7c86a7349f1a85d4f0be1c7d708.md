### Title
Loss-adjusted withdraw receipts keyed to the wrong epoch let users claim unfunded receipts at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` stores the haircut ratio under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` is already incremented inside `deposit()` during the same `stopEpoch` borrower repayment (line 607-610). User receipts were recorded under the *previous* epoch via `lastWithdrawRequest[_user]` / `withdrawsRequestsByEpoch[_user][currentEpoch]`. The recovery price is therefore written under an epoch key that no receipt maps to — the "lock" is applied to the bridge's new position, not to the node holding the receipts.

### Finding Description
Analogous to `pci_bus_lock()` locking every child bus but not the bridge itself, the loss-adjustment bookkeeping protects the aggregate (`pendingWithdraws = 0`, funds pulled) but the per-epoch key used to gate later requests/claims never matches:

1. During `stopEpoch`, the CDO pulls borrower repayment via `deposit()`, which bumps `epochNumber` from N to N+1 while `isEpochRunning()` is still true (lines 607-610).
2. `collectWithdrawFunds(_amount)` with `_amount < pendingWithdraws` then writes `lossRecoveryPriceByEpoch[N+1]` (line 421) — one epoch ahead of the receipts, which live under epoch N.
3. Consequences:
   - `requestWithdraw`'s re-request guard (lines 261-271) reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` = `lossRecoveryPriceByEpoch[N]` = 0, so a user with a haircutted epoch-N receipt can open a fresh request without claiming the loss-adjusted one first.
   - `_claimLossAdjustedWithdrawRequest` (lines 789-801) also reads the stale epoch key, returns 0, and the claim falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` **at par** — even though only the haircutted amount was funded.

### Impact Explanation
Broken invariant: loss socialization / one receipt one payout. Every holder of an epoch-N receipt can claim 100% from a pool that only received `pendingToFund < pendingBasis`. Early claimants drain the funded underlyings at par; later claimants' claims revert or pay nothing. This is direct theft of other users' withdrawal proceeds, quantified as `pendingBasis - amountCollected` for that epoch.

### Likelihood Explanation
Requires a `stopEpochWithDuration(_lossAmount > 0)` partial-funding event with `pendingWithdraws != 0` — an honest-manager path, reachable whenever the borrower repays less than owed. No malicious privileged role needed; any tranche-token holder with a pending request in that epoch benefits by claiming first.

### Recommendation
Store the loss price under the epoch that owns the receipts: capture `epochNumber - 1` (or pass the request epoch explicitly) in `collectWithdrawFunds`, or increment `epochNumber` only after `collectWithdrawFunds` completes. Add a test asserting `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0` after a loss-funded stop.

### Proof of Concept
```
// Foundry fork sketch
// 1. Epoch N running: user requests withdraw of 100e6 -> lastWithdrawRequest[user]=N,
//    withdrawsRequestsByEpoch[user][N]=100e6, pendingWithdraws=100e6
// 2. Manager calls stopEpochWithDuration(loss): borrower repays, strategy.deposit()
//    bumps epochNumber to N+1; collectWithdrawFunds(60e6) writes
//    lossRecoveryPriceByEpoch[N+1]=0.6e18, pendingWithdraws=0
// 3. user calls claimWithdrawRequest:
//    _claimLossAdjustedWithdrawRequest reads epoch N -> price 0 -> returns 0
//    _claimFundedWithdrawRequest pays 100e6 (only 60e6 was funded)
// 4. Second receipt holder's identical claim reverts on insufficient balance
// Assert: vm.expectRevert / balance drift showing first claimant took > funded share
```

Caveat: this finding depends on `collectWithdrawFunds` being invoked after the `deposit()` call that increments `epochNumber` within the same `stopEpoch` transaction; the exact call ordering in `IdleCDOEpochVariant.stopEpoch` could not be fully verified within the available tool iterations. If `collectWithdrawFunds` runs before the epoch bump, the key matches and the issue does not trigger.
