### Title
External Initiator credential grants unrestricted "run" role, allowing any job (not just its bound job) to be triggered via `/v2/jobs/:ID/runs` - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` unconditionally sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` for any valid external-initiator (EI) credential, with no binding to the specific job/bridge the EI was created for. Because `PipelineRunsController.Create` treats the presence of `SessionUserKey` as proof of "user" authentication (its comment claims "EIs not allowed"), this synthetic user object lets any EI credential trigger a run for an arbitrary job ID via `POST /v2/jobs/:ID/runs`.

### Finding Description
The route `userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))` accepts `AuthenticateExternalInitiator`, `AuthenticateByToken`, or `AuthenticateBySession` [1](#0-0) . `AuthenticateExternalInitiator` only verifies the EI access-key/secret pair against the stored `ExternalInitiator` record via `bridges.AuthenticateExternalInitiator` — it never checks which job(s)/bridge the EI is entitled to run [2](#0-1) . On success it sets `SessionUserKey` to a bare `&clsessions.User{Role: clsessions.UserRoleRun}`, satisfying `RequiresRunRole` for any handler [3](#0-2) [4](#0-3) .

In `PipelineRunsController.Create`, the code explicitly intends to prevent EI-authenticated callers from running jobs by integer ID ("only users are allowed to run jobs using int IDs - EIs not allowed"), gating that path on `_, isUser := auth.GetAuthenticatedUser(c)` [5](#0-4) . However, `GetAuthenticatedUser` simply reads `SessionUserKey` from the gin context [6](#0-5) , and since `AuthenticateExternalInitiator` also populates `SessionUserKey`, `isUser` evaluates to `true` for EI-authenticated requests as well — defeating the intended EI exclusion. The `ExternalInitiator` model itself carries no job/bridge scoping field (`ID`, `Name`, `URL`, credential fields only) [7](#0-6) , so there is no per-initiator authorization check performed anywhere in this path. As a result, any holder of a valid EI access-key/secret pair (issued for one specific bridge/job) can invoke `RunJobV2` for any job by numeric ID system-wide.

### Impact Explanation
This is an authorization-exactness violation: a credential scoped to trigger a single external initiator's job can be used to trigger runs of arbitrary jobs on the node, corresponding to Chainlink's "unauthorized job run" bounty impact class. An attacker with a low-privilege EI credential (e.g., issued to a benign external service) can cause arbitrary job executions, potentially including jobs with side effects such as on-chain transactions, unrelated to the credential's intended purpose.

### Likelihood Explanation
Preconditions are minimal: possession of any single valid EI access-key/secret pair (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers), which is a normal precondition explicitly permitted by the threat model (external-initiator credential holder). No admin/operator access is required, and the exploit is deterministic and repeatable — the attacker only needs to know or guess a target job's integer ID and issue `POST /v2/jobs/<ID>/runs`.

### Recommendation
Bind `ExternalInitiator` authentication to the specific job(s)/webhook specs it is associated with (the existing `webhook_specs_external_initiators` join table appears intended for this purpose) and enforce that binding in `PipelineRunsController.Create` before invoking `RunJobV2`. Additionally, fix `isUser` detection so that EI-authenticated sessions are distinguishable from real user sessions — e.g., check `GetAuthenticatedExternalInitiator` first and reject/scope such requests instead of relying solely on the presence of the synthetic `SessionUserKey`.

### Proof of Concept
1. Create two jobs, `JobA` (bound to `ExternalInitiator EI1` via webhook spec) and `JobB` (unrelated, owned by a different bridge/EI or a user-only job).
2. Provision `EI1` credentials (access key/secret) via `POST /v2/external_initiators`.
3. Send `POST /v2/jobs/<JobB numeric ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to `EI1`'s credentials.
4. Assert (currently failing): the response should be `401/403` since `EI1` has no relation to `JobB`, but observe the handler proceeds to `isUser == true` (because `SessionUserKey` was set by `AuthenticateExternalInitiator`), reaches `RunJobV2(ctx, JobB.ID, nil)`, and returns `200` with a created pipeline run for `JobB`.
5. A Go handler-level test can be added in `core/web/pipeline_runs_controller_test.go`, using `auth.AuthenticateExternalInitiator` as the auth method and asserting `httpResp.StatusCode == http.StatusOK` and that a `pipeline.Run` for the unrelated job ID was created — demonstrating the unauthorized cross-job run.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
