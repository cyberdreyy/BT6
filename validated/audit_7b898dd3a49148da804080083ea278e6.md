### Title
Withdrawal-epoch pointer escape: a second `requestWithdraw` moves `lastWithdrawRequest` past a loss-adjusted epoch, letting the defaulted/haircut receipt be re-claimed at par through the funded path - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report is a directory traversal: user-controlled path resolution escapes the intended directory root to reach files outside it. The credit-vault analog is epoch-scoped claim resolution: `IdleCreditVault.claimWithdrawRequest` resolves which payout "directory" a receipt belongs to via the single pointer `lastWithdrawRequest[_user]`. A lender with a loss-adjusted (haircutted) receipt from `stopEpochWithDuration` can traverse out of that epoch's recovery bucket by filing a new `requestWithdraw`, which rewrites the pointer to a fresh epoch where `lossRecoveryPriceByEpoch` is zero. The loss-adjusted path is skipped and the aggregate `withdrawsRequests[_user]` — still containing the old epoch's full basis — is paid at par through `_claimFundedWithdrawRequest`, even though only the haircut amount was ever funded.

### Finding Description
- `requestWithdraw` (via `IdleCDOEpochVariant.requestWithdraw` → `IdleCreditVault.requestWithdraw`) mints the user a receipt and stores `lastWithdrawRequest[_user] = currentEpoch`, accumulating into both `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]`. [1](#0-0) 
- When an epoch ends with a loss, `lossRecoveryPriceByEpoch[lossEpoch]` is set and the borrower only funds `pendingBasis - pendingLoss`; the code comments confirm "pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount." [2](#0-1) 
- `_claimLossAdjustedWithdrawRequest` derives the loss epoch solely from `lastWithdrawRequest[_user]`. [3](#0-2) 
- The funded path pays the **aggregate** `withdrawsRequests[_user]` at par; the per-epoch loss-adjusted clearing in `_clearWithdrawClaimForEpoch` only subtracts `withdrawsRequestsByEpoch[_user][_claimEpoch]` when the *loss* path runs — the funded path never re-checks per-epoch haircuts. [4](#0-3) 
- The only gate is `epochNumber <= lastWithdrawRequest[_user]` reverting while `epochEndDate() != 0`. Once the attacker files a second request in epoch N+1 and one more epoch ends, `epochNumber > lastWithdrawRequest` passes.

Attack sequence (running mode, epoch N ends with `stopEpochWithDuration(_lossAmount)`):
1. Attacker (KYC'd tranche holder) calls `requestWithdraw` during epoch N's buffer → receipt basis B, `lastWithdrawRequest = N`.
2. Manager stops epoch N with a loss; only B·(1−haircut) is funded; `lossRecoveryPriceByEpoch[N]` set.
3. Attacker calls `requestWithdraw` again for a small additional amount in epoch N+1 → `lastWithdrawRequest = N+1`, aggregate `withdrawsRequests` now B + ε.
4. After epoch N+2 ends, `claimWithdrawRequest`: `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[N+1] == 0` and returns 0; `_claimFundedWithdrawRequest` pays B + ε **at par**.
5. The unfunded haircut portion `B·haircut` is paid out of vault liquidity belonging to other claimants/active LPs.

### Impact Explanation
The broken invariant is loss socialization / one-receipt-one-payout: a haircutted receipt is converted into a par claim, directly stealing the crystallized loss amount from the shared funded pool. Quantified loss ≈ `receiptBasis · lossRatio` per attacking receipt; multiple receipts compound it. This is theft from other funded claimants and active tranche holders, i.e., direct fund loss, not a temporary freeze. The `_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve` and does not apply here since no borrower default occurred. [5](#0-4) 

### Likelihood Explanation
Requires only an unprivileged KYC-passing lender, a `stopEpochWithDuration` loss epoch (an expected code path, not a default), and honest manager sequencing. The attacker spends gas and keeps a small residual position; no privileged action needed. Main uncertainty: if `requestWithdraw` were blocked while any prior receipt is unclaimed, or if `stopEpochWithDuration` also netted the old basis out of `withdrawsRequests`, the exploit collapses — neither guard is visible in the reviewed code (`_clearWithdrawClaimForEpoch` clears per-epoch state only when the loss path itself executes).

### Recommendation
Resolve claims by iterating all epochs with entries in `withdrawsRequestsByEpoch[_user]` rather than keying loss lookup off `lastWithdrawRequest`; or check `lossRecoveryPriceByEpoch` for **every** epoch contributing to the aggregate claim, not just the latest request epoch. Alternatively, refuse a new `requestWithdraw` while `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` is unclaimed.

```solidity
function testTraverseLossEpochToParClaim() external {
    uint256 amt = 100_000 * ONE_SCALE;
    idleCDO.depositAA(amt);                       // attacker is a normal KYC'd lender

    // epoch 0 runs, then a lossy stopEpochWithDuration is simulated per existing helpers
    _startEpochAndCheckPrices(0);
    uint256 receipt = cdoEpoch.requestWithdraw(trancheBal, address(AAtranche)); // basis B
    _startEpochAndCheckPrices(1);
    // manager stops epoch 1 with _lossAmount covering e.g. 30% of pendingWithdraws
    _stopEpochWithLoss(1, lossAmount);            // funds only B * 0.7; lossRecoveryPriceByEpoch[1] = 0.7e18

    // attacker files a tiny second request in epoch 2 buffer → lastWithdrawRequest = 2
    cdoEpoch.requestWithdraw(1, address(AAtranche));
    _startEpochAndCheckPrices(2);
    _stopEpochAndCheckPrices(2, apr, expected);   // epochNumber advances past lastWithdrawRequest

    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();              // pays B at par via _claimFundedWithdrawRequest
    assertGt(underlying.balanceOf(address(this)) - balPre,
             receipt * 70 / 100, "haircut bypassed: claimed above funded amount");
}
```

```text
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
