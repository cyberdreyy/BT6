### Title
`pending_delegator_rewards` accumulator on `VoteStateV4` is never decremented after distribution, allowing repeated/duplicate stake reward payouts each epoch - (File: `programs/vote/src/vote_state/mod.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
SIMD-0123 introduces `pending_delegator_rewards`, a lamport pool held in a vote account and shared pro-rata among all stake accounts delegated to that vote account, computed once per epoch as `pending_delegator_rewards * stake / total_active_stake` in `calculate_block_reward`. This is structurally the same "accumulator / per-share reward pool" pattern as `GiantMevAndFeesPool`'s `accumulatedETHPerLPShare`. In the original finding, the bug arose because the accumulator was never correctly reduced to reflect what had already been paid out, letting a claimant walk away with previously-accumulated funds they never contributed to. The agave analog shows the same accounting gap: the only mutator of `pending_delegator_rewards` found in the codebase is `add_pending_delegator_rewards` (checked add) in `programs/vote/src/vote_state/handler.rs:196-209`, invoked from `deposit_delegator_rewards` in `programs/vote/src/vote_state/mod.rs:936-988`. No corresponding decrement/subtract call was found anywhere in the reward-distribution path (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs`, `calculation.rs`) despite `pending_delegator_rewards` being read and paid out epoch after epoch via `calculate_block_reward` at `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:173-232`.

### Finding Description
`calculate_block_reward` reads the full, undiminished `pending_delegator_rewards` value from the vote account on every epoch boundary and pays each stake delegation its proportional share: [1](#0-0) 

The `block_reward` computed there is folded into `PartitionedStakeReward` and then minted into each stake account's lamport balance during distribution (`stake_reward_lamports_minted`), and separately tracked for capitalization changes via `block_reward_lamports_distributed`/`block_reward_lamports_burned` in `distribute_epoch_rewards_in_partition`: [2](#0-1) 

The vote-account field `pending_delegator_rewards` is only ever incremented, via `add_pending_delegator_rewards`: [3](#0-2) 

called from `deposit_delegator_rewards`, which purposefully documents that the field must be updated "last" after the CPI transfer: [4](#0-3) 

Searching the entire reward-calculation and distribution code paths (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs`, `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`, `programs/vote/src/vote_state/mod.rs`, `programs/vote/src/vote_state/handler.rs`) turned up no subtraction of `pending_delegator_rewards` (no `checked_sub`, no `set_pending_delegator_rewards` with a decreased value, no "delegator_reward" decrement call). The only place the value decreases at all is when the withdraw path checks it as a reserved minimum before allowing a withdrawal, which does not zero it out either: [5](#0-4) 

This mirrors the `GiantMevAndFeesPool` root cause exactly: an accumulator (`accumulatedETHPerLPShare` / here `pending_delegator_rewards`) is used to compute payouts on every distribution cycle, but the mechanism to mark already-distributed amounts as "spent" from that accumulator (the `claimed` bookkeeping in the C4 report) appears to be absent for the vote-program delegator reward pool. If the accumulator is genuinely never decremented, every subsequent epoch's `calculate_block_reward` call recomputes and re-mints the *entire* `pending_delegator_rewards` balance to all currently-active delegators again, not just the incremental amount deposited since the last distribution.

### Impact Explanation
If confirmed, this results in unauthorized lamport minting: each epoch, stake delegators receive newly-minted lamports (via `stake_reward_lamports_minted`/capitalization increase in `distribute_epoch_rewards_in_partition`) equal to their share of the *entire historical* `pending_delegator_rewards` pool rather than just the unclaimed delta, since the pool total never shrinks. This inflates total supply/capitalization indefinitely from a single validator-side deposit, a direct analog to "any user being first to claim gets all previously generated rewards," except here the effect compounds every epoch rather than only on first claim. This is a concrete unauthorized fund creation / consensus-relevant state mutation impacting bank capitalization and stake balances.

### Likelihood Explanation
The `DepositDelegatorRewards`/block-revenue-sharing feature (SIMD-0123) requires several feature flags (`commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing`) to be active, gating this to networks where that feature set is enabled. Given the feature is present in code with unit tests already exercising `calculate_block_reward` and `deposit_delegator_rewards`, likelihood is tied to feature activation status; once active, the trigger condition (multiple epochs elapsing with any nonzero `pending_delegator_rewards`) is the normal, expected operating mode, not an edge case—so likelihood of triggering is high once the feature is live, assuming the missing decrement is real and not implemented elsewhere outside indexed files.

### Recommendation
Verify whether `pending_delegator_rewards` is decremented anywhere outside the files reviewed (index coverage limitations may have excluded some code, e.g., a possible SVM- or bank-level updater not resolved in this search). If it is not decremented, `calculate_block_reward` and the distribution path must be reworked so that the vote account's `pending_delegator_rewards` is reduced by exactly the total amount minted to stake accounts as block reward in that epoch's distribution (analogous to fixing the `accumulatedETHPerLPShare`/`claimed` interaction in the original report), preventing the same funds from being redistributed on subsequent epochs.

### Proof of Concept
Not independently executable from static review; the control-flow evidence is:
1. `deposit_delegator_rewards` increases `pending_delegator_rewards` by `deposit` lamports [6](#0-5) .
2. Every epoch, `calculate_block_reward` computes and pays out a share of the *full* `pending_delegator_rewards` to every delegator with active stake [7](#0-6) .
3. No call site decrements `pending_delegator_rewards` after this payout is minted into stake accounts in `distribute_epoch_rewards_in_partition`/`store_stake_accounts_in_partition` [8](#0-7) .

Because tool access ended before a full repo-wide trace of every possible mutator of `VoteStateV4.pending_delegator_rewards` could be completed (index size limits may exclude some files), this should be verified with a live Devin session that can grep the complete, uncompressed source tree and, ideally, run/extend the existing `test_calculate_block_reward_specific` and `test_deposit_delegator_rewards` tests across two simulated epochs to confirm whether the pool balance decreases after distribution.

        self.capitalization
            .fetch_sub(block_reward_lamports_burned, Relaxed);

        self.update_epoch_rewards_sysvar(
            stake_reward_lamports_minted + stake_reward_lamports_burned,
            block_reward_lamports_distributed + block_reward_lamports_burned,
        );

        // update reward history for this partitioned distribution
        self.update_reward_history_in_partition(&updated_stake_rewards);

        let metrics = RewardsStoreMetrics {
            pre_capitalization,
            post_capitalization: self.capitalization(),
            total_stake_accounts_count: partition_rewards.all_stake_rewards.num_rewards(),
            total_num_partitions: partition_rewards.partition_indices.len(),
            partition_index,
            store_stake_accounts_us,
            store_stake_accounts_count: updated_stake_rewards.len(),
            distributed_rewards: stake_reward_lamports_minted,
            burned_rewards: stake_reward_lamports_burned,

    fn store_stake_accounts_in_partition(
        &self,
        partition_rewards: &StartBlockHeightAndPartitionedRewards,
        partition_index: u64,
    ) -> DistributionResults {
        let feature_snapshot = self.feature_set.snapshot();
        // Name intentionally doesn't match -- "adjust delegations for rent" is
        // part of relaxing post-exec min balance checks.
        let adjust_delegations_for_rent = feature_snapshot.relax_post_exec_min_balance_check;
        let use_fixed_point_stake_math = feature_snapshot.upgrade_bpf_stake_program_to_v5_1;

        let mut stake_reward_lamports_minted = 0;
        let mut stake_reward_lamports_burned = 0;
        let mut block_reward_lamports_distributed = 0;
        let mut block_reward_lamports_burned = 0;
        let indices = partition_rewards
            .partition_indices
            .get(partition_index as usize)
            .unwrap_or_else(|| {
                panic!(
                    "partition index out of bound: {partition_index} >= {}",
                    partition_rewards.partition_indices.len()
                )
            });
        let mut updated_stake_rewards = Vec::with_capacity(indices.len());
        let stakes_cache = self.stakes_cache.stakes();
        let stakes_cache_accounts = stakes_cache.stake_delegations();
        let stake_history = stakes_cache.history();
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        let rent = &self.rent_collector.rent;
        for index in indices {
            let partitioned_stake_reward = partition_rewards
                .all_stake_rewards
                .get(*index)
                .unwrap_or_else(|| {
                    panic!(
                        "partition reward out of bound: {index} >= {}",
                        partition_rewards.all_stake_rewards.total_len()
                    )
                })
                .as_ref()
                .unwrap_or_else(|| {
                    panic!("partition reward {index} is empty");
                });
            let stake_pubkey = partitioned_stake_reward.stake_pubkey;
            let stake_reward_amount = partitioned_stake_reward.inflation.stake_reward;
            let block_reward_amount = partitioned_stake_reward.block_reward;

            match Self::build_updated_stake_reward(
                self.epoch,
                stake_history,
                new_warmup_cooldown_rate_epoch,
                stakes_cache_accounts,
                partitioned_stake_reward,
                rent,
                adjust_delegations_for_rent,
                use_fixed_point_stake_math,
            ) {
                Ok(stake_reward) => {
                    stake_reward_lamports_minted += stake_reward_amount;
                    block_reward_lamports_distributed += block_reward_amount;
                    updated_stake_rewards.push(stake_reward);
                }
                Err(err) => {
                    error!(
                        "bank::distribution::store_stake_accounts_in_partition() failed for \
                         {stake_pubkey}, {stake_reward_amount} lamports burned: {err:?}"
                    );
                    stake_reward_lamports_burned += stake_reward_amount;
                    block_reward_lamports_burned += block_reward_amount;
                }
            }
        }
        drop(stakes_cache);
        self.store_accounts(
            (self.slot(), &updated_stake_rewards[..]),
            // Reuse the rewards calculation thread pool to parallelize
            // loading the previous versions of the stake accounts.
            Some(crate::bank::rewards_calculation_thread_pool()),
        );
        DistributionResults {
            stake_reward_lamports_minted,
            stake_reward_lamports_burned,
            block_reward_lamports_distributed,
            block_reward_lamports_burned,
            updated_stake_rewards,
        }
    }

    pub(crate) fn add_pending_delegator_rewards(
        &mut self,
        amount: u64,
    ) -> Result<(), InstructionError> {
        match &mut self.target_state {
            TargetVoteState::V4(v4) => {
                v4.pending_delegator_rewards = v4
                    .pending_delegator_rewards
                    .checked_add(amount)
                    .ok_or(InstructionError::ArithmeticOverflow)?;
                Ok(())
            }
        }
    }

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
