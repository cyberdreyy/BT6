### Title
Zip extraction lacks path-traversal sanitization, allowing `processZipTimestampField`'s `os.Chtimes` to touch paths outside the extraction root - (File: `helpers/archives/zip_extra.go`)

### Summary
The legacy zip extraction path (`archives.ExtractZipArchive` → `extractZipFile*` → `processZipExtra` → `processZipTimestampField`) never validates or sanitizes `zip.FileHeader.Name` against the extraction root before performing filesystem operations. A crafted zip cache/artifact with `Name` containing `../` sequences and a `ZipTimestampField` extra field causes `os.Chtimes(file.Name, ...)` in `processZipTimestampField` to operate on an attacker-chosen path.

### Finding Description
`helpers/archives/zip_extract.go`'s `ExtractZipArchive` iterates `archive.File` and calls `extractZipFile(file)` (which does `os.MkdirAll(filepath.Dir(file.Name), ...)` and then `os.OpenFile`/`os.Symlink`/`os.Mkdir` directly on `file.Name`) followed by `processZipExtra(&file.FileHeader)` [1](#0-0) . The only sanity check performed anywhere in this path is `errorIfGitDirectory`, which merely rejects paths whose first cleaned component is `.git`; it does not reject `..` traversal or absolute paths [2](#0-1) . `processZipExtra` then dispatches `ZipTimestampFieldType` extra fields straight to `processZipTimestampField(data, file)`, which calls `os.Chtimes(file.Name, acTime, modTime)` using the same unsanitized `file.Name` [3](#0-2) .

The extraction destination directory (`dir`/`wd`) is passed into `ziplegacy.NewExtractor` but is never joined with `file.Name` or used to chdir/confine extraction — `Extract()` just calls `archives.ExtractZipArchive(zr)` with no root confinement [4](#0-3) . The caller, `CacheExtractorCommand.Execute` in `commands/helpers/cache_extractor.go`, resolves `wd = os.Getwd()` and passes it to `archive.NewExtractor(format, f, size, wd)`, relying entirely on the extractor implementation to confine writes to `wd` [5](#0-4) ; for the zip format routed to the legacy extractor, no such confinement exists.

Since `extractZipFileEntry`/`extractZipDirectoryEntry`/`extractZipSymlinkEntry` already perform raw filesystem writes on the unsanitized `file.Name` before `processZipExtra` runs, `os.Chtimes` in `processZipTimestampField` is simply the last operation in a chain that already lacks path-root validation — it does not introduce a *new* class of write capability, but it does add an additional, distinct attacker-controlled `os.Chtimes` primitive on arbitrary filesystem paths (metadata modification) reachable via the same missing check.

### Impact Explanation
An attacker who can poison a cache or (legacy-format) artifact archive consumed by a later job/stage in the same pipeline can cause the runner process to modify file timestamps (`os.Chtimes`) on paths outside the intended extraction root, anywhere the runner process has write permission on the host/container filesystem. Combined with the pre-existing unsanitized `os.OpenFile`/`os.Mkdir`/`os.Symlink` calls in `extractZipFile`, the practical impact extends beyond timestamps to arbitrary file/symlink creation outside the job root — this is a real path-traversal (Zip Slip) vulnerability in the legacy zip extractor, not merely a Chtimes-only issue.

### Likelihood Explanation
Preconditions match the threat model: a normal, unprivileged pipeline author can control the contents of a cache key/artifact that a later job in the same pipeline consumes, and can construct a zip whose `FileHeader.Name` contains `../` sequences and a `ZipTimestampField` extra field (0x5455) using standard `archive/zip` APIs — no special privilege is required. The bug is reachable via `cache-extractor` (`commands/helpers/cache_extractor.go`) whenever the legacy zip format/extractor is selected for extraction, making it a realistic, repeatable exploit path.

### Recommendation
In `helpers/archives/zip_extract.go` (and `zip_extra.go`), validate/canonicalize `file.Name` against the extraction root before any filesystem operation: reject entries where `filepath.Clean(file.Name)` is absolute or escapes the root (e.g., using `filepath.Rel(root, filepath.Join(root, file.Name))` and checking for a leading `..`), and pass/store the extraction root through `ziplegacy.extractor` so every `os.Mkdir`, `os.OpenFile`, `os.Symlink`, `lchmod`, and `os.Chtimes` call operates on a path joined with and confined to that root, matching the confinement guarantees implied by `archive.NewArchiver`'s doc comment ("archiver will ensure that files to be archived are children of the directory provided") [6](#0-5) .

### Proof of Concept
Go unit test in `helpers/archives/zip_extract_test.go`:
1. Build an in-memory `zip.Writer`, create a `zip.FileHeader` with `Name = "../outside/evil.txt"` and craft `Extra` bytes encoding a `ZipExtraField{Type: ZipTimestampFieldType, Size: ...}` followed by a `ZipTimestampField{Flags: 1, ModTime: <epoch>}`.
2. `chdir` into a temp "extraction root" directory, then call `archives.ExtractZipArchive` on the resulting `*zip.Reader`.
3. Assert that `../outside/evil.txt` (relative to the extraction root's parent) was created/modified and that `os.Stat` on that path reflects the attacker-supplied `modTime` — i.e., `os.Chtimes` executed outside the intended root — proving the missing path-root check; then assert the fix rejects/sandboxes such entries (extraction returns an error or the file is written only inside the root).

func processZipTimestampField(data []byte, file *zip.FileHeader) error {
	if !file.Mode().IsDir() && !file.Mode().IsRegular() {
		return nil
	}

	var tsField ZipTimestampField
	err := binary.Read(bytes.NewReader(data), binary.LittleEndian, &tsField)
	if err != nil {
		return err
	}

	if (tsField.Flags & 1) == 1 {
		modTime := time.Unix(int64(tsField.ModTime), 0)
		acTime := time.Now()
		return os.Chtimes(file.Name, acTime, modTime)
	}

	return nil
}
