### Title
PipelineRunsController.Create's `isUser` check is satisfied by EI-authenticated requests, allowing any External Initiator credential to trigger an arbitrary job run via int ID without external_initiator_webhook_specs binding validation - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` intends to restrict int-ID job runs to authenticated users ("EIs not allowed" per the code comment), but `auth.AuthenticateExternalInitiator` populates the same `SessionUserKey` context value with a synthetic `User{Role: UserRoleRun}` for any successfully authenticated External Initiator. Because `GetAuthenticatedUser` simply checks for the presence of that key, `isUser` evaluates to `true` for EI callers, letting them reach `prc.App.RunJobV2(ctx, jobID, nil)` for any job ID with no check that the calling EI is bound to that job's `external_initiator_webhook_specs`.

### Finding Description
In `core/web/pipeline_runs_controller.go`, `Create` does: [1](#0-0) 

`isUser` is derived from `auth.GetAuthenticatedUser(c)`: [2](#0-1) 

However, `AuthenticateExternalInitiator` — the middleware that authenticates EI credentials — explicitly also sets the `SessionUserKey` to a fabricated `User` object with `Role: UserRoleRun`, purely so EI-authenticated requests can pass role-based `RequiresRunRole` checks elsewhere: [3](#0-2) 

Because `GetAuthenticatedUser` only checks for existence of the `SessionUserKey`/type-assert success (not whether the underlying credential was actually a session/token user vs. a synthetic EI stand-in), `isUser` is `true` for both real users and EI callers. The comment "only users are allowed to run jobs using int IDs - EIs not allowed" is therefore not enforced by this check — any EI that authenticates successfully falls into the `isUser` branch and can call `RunJobV2` with an arbitrary int job ID, with zero lookup of `auth.GetAuthenticatedExternalInitiator(c)` or any join against `external_initiator_webhook_specs` to confirm that EI is actually bound to the target job.

### Impact Explanation
This allows an attacker holding valid credentials for **any one** External Initiator on the node to trigger runs of **any** job on the node (not just the job(s) that EI is configured for), bypassing the job-to-initiator binding that `external_initiator_webhook_specs` is meant to enforce. This is an authorization-bypass leading to unauthorized job execution, which can cause fund movement (e.g., triggering an OCR/direct-request job that writes on-chain) or unauthorized consumption/side effects tied to another job's pipeline — matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Preconditions: attacker needs only a single valid External Initiator credential pair (access key + secret) for the node — no admin/session/user credential is required, and no relationship between that EI and the target job is needed. The exploit is a single unauthenticated-role HTTP POST with valid EI headers set instead of session/API-key headers, using an integer job ID of an unrelated job. This is trivially repeatable and requires no timing or race conditions.

### Recommendation
In `PipelineRunsController.Create`, do not rely solely on `auth.GetAuthenticatedUser` to gate the "isUser" branch. Instead, explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and reject (or route to a distinct, binding-validated path) whenever an EI object is present in context. If EI-triggered runs by int ID must be supported, look up `external_initiator_webhook_specs` for the target job and confirm it references the authenticated EI's ID before calling `RunJobV2`. Alternatively, mark the synthetic EI user object distinctly (e.g., a separate context key or explicit `IsEI` flag) so `isUser` genuinely means "session/token user" and not "any caller with `UserRoleRun`."

### Proof of Concept
1. Create a job (any type, e.g., webhook or non-webhook) with no `external_initiator_webhook_specs` rows.
2. Create a separate, unrelated External Initiator record with valid access key/secret via `bridges.ExternalInitiator`.
3. Send `POST /v2/jobs/:ID/runs` with `:ID` set to the int ID of the job from step 1, using headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` (per `static.ExternalInitiatorAccessKeyHeader/SecretHeader`) for the EI from step 2 (no session cookie, no user API key).
4. Assert the middleware chain authenticates successfully via `AuthenticateExternalInitiator`, that `auth.GetAuthenticatedUser` returns `Role: UserRoleRun`, and that `Create` proceeds into the `isUser` branch, calling `RunJobV2` and returning HTTP 200 with a pipeline run resource — despite there being zero `external_initiator_webhook_specs` rows binding this EI to job ID from step 1.
5. Expected (secure) behavior: request should be rejected with 401/403 for lacking a valid job-initiator binding; current behavior: request succeeds and triggers the run.

func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
