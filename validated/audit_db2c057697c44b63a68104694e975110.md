### Title
Unfunded instant-withdraw receipts are paid at par from other users' funded claims - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` burns the caller's entire `instantWithdrawsRequests` receipt balance and pays it out at par via `_transferFundedClaim`, with no check that the underlying for that receipt was actually collected through `collectInstantWithdrawFunds`. This is the same bug class as CVE-2024-35839: a receipt is enqueued against a funding context (`pendingInstantWithdraws` / per-epoch claim buckets), but the claim path dereferences the aggregate `instantWithdrawsRequests[_user]` as if the backing object still exists, instead of resolving and validating the funded portion (the "ifindex + lookup" fix in the kernel). `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are recorded per epoch but are only consulted in the *defaulted* path (`_claimDefaultedInstantWithdrawRequest`); the normal path ignores them entirely.

### Finding Description
- `requestInstantWithdraw` burns CDO strategy tokens, mints a 1:1 receipt, and adds the amount to `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`, and `pendingInstantWithdraws` (IdleCreditVault.sol:356-375).
- Funding arrives later, only when the manager calls `getInstantWithdrawFunds`, which invokes `collectInstantWithdrawFunds(_amount)` to decrement `pendingInstantWithdraws` and pull underlying from the CDO (IdleCreditVault.sol:398-403).
- `claimInstantWithdrawRequest` then does `amount = instantWithdrawsRequests[_user]; _burn(_user, amount); _transferFundedClaim(_user, amount)` (IdleCreditVault.sol:380-393). There is no epoch gate, no check that `pendingInstantWithdraws` no longer covers this receipt, and no per-epoch funded/unfunded split — unlike the normal path, which enforces `epochNumber > lastWithdrawRequest[_user]` (IdleCreditVault.sol:326).
- On the CDO side, `IdleCDOEpochVariant.claimInstantWithdrawRequest` gates only on the `allowInstantWithdraw` flag (IdleCDOEpochVariant.sol:975-979), which is a feature toggle, not a funding-state check.

So a receipt created seconds ago — whose underlying the borrower has not yet returned — is treated identically to a fully funded receipt.

### Impact Explanation
An unprivileged, KYC-passing tranche holder can:
1. During a running epoch with instant withdraws enabled, call `requestInstantWithdraw` (or `requestWithdraw` routed to the instant bucket) for their full tranche balance.
2. Immediately call `claimInstantWithdrawRequest` before `getInstantWithdrawFunds` collects anything.
3. The vault pays the full receipt at par from whatever underlying the strategy currently holds — which includes matured normal-withdraw funding collected via `collectWithdrawFunds`, already-collected instant funds of other users, and `defaultRecoveryReserve`. The attacker burns a receipt whose backing (`pendingInstantWithdraws`) still sits with the borrower and walks away with assets earmarked for honest claimants.

Broken invariant: "one receipt, one funded payout." `pendingInstantWithdraws` remains elevated while its backing was already paid out, so the last honest claimants' transfers revert — direct theft plus insolvency of the instant-withdraw queue, quantified as `min(attackerReceipt, strategyUnderlyingBalance)`.

### Likelihood Explanation
Requires `allowInstantWithdraw == true` and the strategy holding underlying at claim time — a routine state whenever funded withdrawals or reserves sit in the vault. The attacker is an ordinary allowed lender; no privileged call needed, only ordering their claim inside the `instantWithdrawDelay` window before collection. The missing funded-vs-unfunded check is evident by comparison with the normal and defaulted paths, which do enforce it.

### Recommendation
Track funded instant claims separately (e.g., per-epoch `instantWithdrawClaimsByEpoch` cleared down as `collectInstantWithdrawFunds` arrives, or a `fundedInstantWithdraws` counter), and in `claimInstantWithdrawRequest` pay only the funded portion — mirroring the kernel fix: resolve the backing (`dev_get_by_index_rcu` analogue) and drop/claim zero when it doesn't exist, rather than trusting the stored receipt pointer.

### Proof of Concept
```solidity
// Foundry fork PoC sketch against IdleCreditVault.t.sol harness
// 1. Owner/manager enable instant withdraws: setInstantWithdrawParams(delay, minAprDiff, true)
// 2. Honest users' matured withdraw funding sits in the strategy (prior collectWithdrawFunds),
//    so underlying.balanceOf(strategy) > 0 while an epoch runs.
// 3. Attacker (KYC-allowed AA holder) calls cdoEpoch.requestWithdraw(attackerTranches, AAtranche)
//    -> routed to instant bucket; pendingInstantWithdraws += attackerAmount.
// 4. In the SAME epoch, before manager calls getInstantWithdrawFunds, attacker calls
//    cdoEpoch.claimInstantWithdrawRequest().
// 5. Vault burns the receipt and transfers attackerAmount underlying at par from the
//    strategy balance that belongs to other claimants.
// Assert: attacker underlying balance increased by attackerAmount while
//         pendingInstantWithdraws still equals attackerAmount (double-counted liability).
```

Uncertainty note: I could not fully trace `getInstantWithdrawFunds` / `_transferFundedClaim` internals and whether some outer guard re-checks `pendingInstantWithdraws` at CDO level; the visible code shows none. If the strategy reliably holds zero underlying during running epochs, impact degrades to a revert (no loss), but any funded-claim or reserve balance in the vault is exposed.   function requestInstantWithdraw(uint256 _amount, address _user) external {
```text
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```
