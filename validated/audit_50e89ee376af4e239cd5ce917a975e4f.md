### Title
`getMultipleAccounts` aborts the entire batch and discards all valid account data when a single account fails Base58 encoding - ([File: rpc/src/rpc.rs])

### Summary
The `getMultipleAccounts` JSON-RPC handler iterates over the requested pubkeys and calls `encode_account` for each one in a loop using `?` to propagate errors. If Base58/Binary encoding is requested and even one account's data exceeds `MAX_BASE58_BYTES`, `encode_account` returns an `Err`, which aborts the entire request via early return — discarding the successfully encoded results for every other (valid) pubkey in the same batch, instead of only failing/nulling that one entry.

### Finding Description
`JsonRpcRequestProcessor::get_multiple_accounts` loops through all requested `pubkeys`, and for each one calls `get_encoded_account`, which calls `encode_account`, propagating any error with `?`: [1](#0-0) 

`encode_account` returns `Err(...)` (an `InvalidRequest` JSON-RPC error) whenever the account's data (after slicing) exceeds `MAX_BASE58_BYTES` (128 bytes) for `Binary`/`Base58` encodings: [2](#0-1) 

This is confirmed by the existing unit test `test_encode_account_throws_when_data_too_large_to_base58_encode`, which shows `encode_account` panics/errors (rather than emitting an in-band error string like `encode_bs58` does for the account-decoder's `Base58`/`Base64` paths) when data is oversized: [3](#0-2) 

Because the `for pubkey in pubkeys { ... }` loop in `get_multiple_accounts` uses `?` on each iteration's result, one bad pubkey in a batch (Base58/Binary encoding + data > 128 bytes) causes the whole `Result<RpcResponse<Vec<Option<UiAccount>>>>` to become `Err`, discarding data already computed for every other pubkey in the request. This mirrors the C4 finding: a per-item precondition failure ("not past `nextFundingTime`" / "encodable in Base58") inside a loop reverts/returns an error for the *entire batch* instead of skipping just that item and returning results for the rest.

Note: by default `get_multiple_accounts` uses `UiAccountEncoding::Base64` (line 577), so a caller must explicitly request `binary` or `base58` encoding to trigger this; it is fully within the unprivileged caller's control via `RpcAccountInfoConfig.encoding`.

### Impact Explanation
An unprivileged RPC client issuing `getMultipleAccounts` with `encoding: "base58"` (or the default/legacy `binary`) and a list of pubkeys where any single account holds more than 128 bytes of data will get the *entire batch* rejected with an `InvalidRequest` error, even though the other accounts in the list are perfectly valid and encodable. This degrades availability/correctness of a public RPC method for legitimate multi-account queries (a common pattern for dApps batching lookups), and is inconsistent with the account-decoder's own `encode_bs58` helper, which handles oversized data gracefully by returning an in-band `"error: data too large for bs58 encoding"` string per-account rather than aborting the whole call. This does not cause a validator crash, deadlock, or consensus-state mutation, and the client can trivially work around it by using `base64` encoding.

### Likelihood Explanation
Any RPC client can trigger this deterministically and with no special access, by knowing (or blindly enumerating) that at least one of the requested pubkeys holds >128 bytes of data while requesting base58/binary encoding — this is not a rare or adversarial edge case, since many common program accounts exceed 128 bytes.

### Recommendation
In `get_multiple_accounts` (`rpc/src/rpc.rs`), do not propagate an `encode_account` error for a single pubkey as a hard failure for the whole batch. Instead, either: (1) validate the encoding/size precondition up front and reject the whole request only if *all* encodings would be invalid, or (2) change per-account encoding failures to produce an in-band error indicator for just that entry (similar to `encode_bs58`'s `"error: data too large for bs58 encoding"` string), so the remaining valid accounts in the batch are still returned to the caller.

### Proof of Concept
1. Store two accounts on-chain: account A with ≤128 bytes of data, account B with >128 bytes of data.
2. Call `getMultipleAccounts` with `[A, B]` and `{"encoding": "base58"}` (or `"binary"`).
3. Observe: the RPC returns a JSON-RPC error (`InvalidRequest`, "Encoded binary (base 58) data should be less than 128 bytes...") for the *entire* request, and account A's valid, encodable data is never returned to the client, even though it was already computed inside the loop before B was processed. This is directly demonstrated by the loop/early-return structure in [1](#0-0)  combined with the error path in [4](#0-3) .

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
