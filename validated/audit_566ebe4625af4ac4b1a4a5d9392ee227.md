### Title
Global unbounded `savedCallbacks` map allows single attacker to exhaust callback quota and evict/starve legitimate users - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` inserts every accepted legacy trigger request into a single shared `h.savedCallbacks` map keyed only by `MessageId`, bounded by a global `defaultMaxSavedCallbacks` (20000) with no per-sender accounting. [1](#0-0) . Because eviction in `pruneCallbacks` is purely age/creation-time based and applies to the whole map regardless of sender, a single attacker able to generate enough valid signed messages with unique `MessageId`s can fill or dominate the map and cause legitimate concurrent users' callbacks to be evicted before their DON responses arrive, or exhaust capacity before the periodic prune runs.

### Finding Description
`HandleLegacyUserMessage` validates payload shape, timestamp staleness, and method, then transforms the message via `common.ValidatedRequestFromMessage` (which the code comment explicitly notes still needs "allowlist and rate-limiting" — see the `TODO` at line 384: `// TODO: apply allowlist and rate-limiting here`) [2](#0-1) . After validation, it unconditionally stores the callback in the shared map:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
``` [1](#0-0) 

There is no per-sender key, counter, or limit anywhere in this insertion path — only a single global `sync.Mutex`-protected map and a global `MaxSavedCallbacks` config value (default `defaultMaxSavedCallbacks = 20000`) enforced solely inside the periodic `pruneCallbacks` job [3](#0-2) [4](#0-3) .

`pruneCallbacks` runs only every `CallbackPruneIntervalSec` (default 30s), first removing expired-by-age entries, then — if still above `maxSize` — sorting **all** remaining entries by `createdAt` and deleting the oldest half, irrespective of who owns them [5](#0-4) . Between prune cycles, the map can grow past `defaultMaxSavedCallbacks` entirely from a single sender's messages (the comment even says "could briefly exceed under heavy load" [6](#0-5) ). Since insertion has no per-sender ceiling, an attacker who can produce a large volume of individually-valid, uniquely-keyed legacy trigger messages (each merely needing to pass payload decoding, non-zero/non-stale timestamp, and `common.ValidatedRequestFromMessage`'s signature check — which only proves the message was self-signed by *some* ECDSA key, not that the sender is allow-listed) can:
1. Flood the map with entries whose `createdAt` is recent, so they will not be pruned as "expired" and will instead occupy capacity/eviction priority ahead of older legitimate entries when the age-based eviction sorts by `createdAt`.
2. Cause a victim's freshly-submitted, concurrently-processed callback to be evicted during the same prune cycle purely because attacker entries are more numerous, or cause memory/goroutine growth that degrades service for all users sharing the DON's handler instance.

Nothing in this file enforces isolation per sender/DON; the whole quota is a single global resource shared by every legacy user of the DON's `WebAPIHandler`.

### Impact Explanation
This maps to a Denial-of-Service / quota-bypass impact: one unprivileged sender can consume the entire shared `savedCallbacks` capacity of a DON's capabilities handler, causing other legitimate senders' pending web-API trigger requests to have their callback dropped/evicted (their eventual node response in `handleWebAPITriggerMessage` will find `found == false` and be silently discarded [7](#0-6) , so the legitimate caller never receives a response). This is a cross-user availability impact against a shared gateway resource, not privilege escalation, and it also explicitly matches the code's own acknowledged gap: `// TODO: apply allowlist and rate-limiting here`.

### Likelihood Explanation
The attacker only needs the ability to sign JSON-RPC legacy messages with any ECDSA key (self-signed, no allow-list membership is required to reach the `savedCallbacks` insertion — allow-list checks are noted as not-yet-applied at this stage) and to generate unique `MessageId`s and pass the shallow validation (`Timestamp != 0`, not stale, method == `MethodWebAPITrigger`). This is inexpensive and fully repeatable by an unauthenticated/unprivileged sender of gateway messages, requiring only sustained request volume, no special role or credentials beyond producing valid signatures.

### Recommendation
Enforce quotas and eviction per sender (e.g., keyed by `msg.Body.Sender` or public key) rather than a single global map/limit — track and cap outstanding callback counts per sender, reject/rate-limit new inserts once a sender's own quota is exhausted, and only evict entries belonging to the offending sender(s) rather than globally by age across all senders. Additionally, implement the still-outstanding `TODO: apply allowlist and rate-limiting here` at line 384 before the message is accepted into `savedCallbacks`.

### Proof of Concept
Go handler-level integration test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with `MaxSavedCallbacks` set to a small test value (e.g., 100) for speed.
2. Simulate `defaultMaxSavedCallbacks` (or the small test cap) legitimate-looking but attacker-generated `HandleLegacyUserMessage` calls, each self-signed with a distinct throwaway ECDSA key and unique `MessageId`, all with `Sender = attackerAddr`.
3. Concurrently submit one victim `HandleLegacyUserMessage` call with `Sender = victimAddr` and a distinct `MessageId`.
4. Trigger `pruneCallbacks()` (or wait for the prune ticker) and then simulate the DON node responding to the victim's `MessageId` via `handleWebAPITriggerMessage`.
5. Assert that the victim's callback either was evicted (test fails to find `savedCb` / `SendResponse` never called) or that the handler enforces a per-sender quota preventing the attacker from occupying more than a fair share of the map — demonstrating the current code allows the attacker's flood to starve/evict the victim's entry solely because there is no per-sender isolation.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response

	}
	return nil
}

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}
```
