## Title
Reentrant Merkle-validation overwrite lets a malicious order maker desynchronize the escrow hashlock from the validated partial-fill index - (File: `contracts/BaseEscrowFactory.sol`, `contracts/MerkleStorageInvalidator.sol`)

### Summary
`BaseEscrowFactory._postInteraction` mirrors the reported root cause: it records validation state (`lastValidated[key]`) via `MerkleStorageInvalidator.takerInteraction` in an earlier phase of the fill, then later *reads that same storage slot* to decide the hashlock and to validate the partial-fill index — but between the write and the read it makes an unguarded external call to an attacker-suppliable "custom postInteraction" contract. That external call can re-enter the Limit Order Protocol to trigger another partial fill of the same order, overwriting `lastValidated[key]` before the outer call consumes it, exactly like the HSG report's pattern of a transient "expected state" being clobbered by a nested call before the post-check reads it.

### Finding Description
In `_postInteraction` [1](#0-0) , the sequence is:
1. An arbitrary attacker-suppliable target from `tail` is invoked via `IPostInteraction(...).postInteraction(...)` [2](#0-1) .
2. Only afterward does the code read `lastValidated[key]` and validate the partial-fill index against it: [3](#0-2) .

`lastValidated[key]` is written earlier in the same top-level fill by `MerkleStorageInvalidator.takerInteraction`, keyed only by `keccak256(orderHash, rootShortened)` [4](#0-3)  — it carries no binding to a specific fill's `makingAmount`/`remainingMakingAmount`. Because `allowMultipleFills` orders can legitimately be filled repeatedly, a maker can embed a malicious "custom postInteraction" contract (the `tail` target) in the extension. When invoked mid-fill (step 1 above, before the outer fill's own validation read), that contract re-enters the Limit Order Protocol to trigger another partial fill of the *same order* with a taker-supplied `(idx, secretHash, proof)` of the attacker's choosing. This nested fill runs `takerInteraction` again and overwrites `lastValidated[key]` with a different `(index, leaf)` pair before the *outer* fill resumes and reads it at line 118-119.

The outer fill then computes `hashlock = validated.leaf` from the *nested* call's leaf — not the leaf that was actually validated for the outer fill's own index — while `_isValidPartialFill` is checked using the outer fill's own `makingAmount`/`remainingMakingAmount` [5](#0-4) . Since the attacker fully controls the nested call's `idx`, they can choose it to satisfy `_isValidPartialFill`'s arithmetic check for the outer fill while supplying a mismatched `leaf`/secret hash, desynchronizing the escrow's `hashlock` from the secret that legitimately corresponds to the outer fill's position in the Merkle tree.

### Impact Explanation
The escrow deployed by the outer `_postInteraction` call is funded with the maker's real tokens/safety deposit but bound to a hashlock the resolver did not intend/expect for that fill index. Because the hashlock no longer matches the secret the resolver is expecting to receive for their tranche, the resolver cannot withdraw with the correct secret at the correct time, and the funds become stuck until the cancellation timelock — matching "temporary freezing of funds during the live swap lifecycle." Depending on which secret the attacker controls, it can also enable them to redeem the escrow prematurely with a secret unrelated to their actual fill share, i.e., direct manipulation of fund flow.

### Likelihood Explanation
This requires the order maker to craft a malicious extension using the optional "custom postInteraction" hook (`tail`) and for the order to use `allowMultipleFills`, both of which are attacker-reachable, unprivileged actions (maker is not privileged in this protocol) and do not depend on any external/imported-contract bug — the reentrancy path is entirely inside this repo's own `_postInteraction`/`MerkleStorageInvalidator` state machine. The main uncertainty is whether the Limit Order Protocol itself blocks nested fills of the same order within one transaction; if it does not (which is plausible since multi-fill orders are explicitly designed to be filled multiple times), the attack is directly reachable.

### Recommendation
Do not rely on a global, fill-agnostic `lastValidated` mapping read after an external call. Either:
- Capture the validated `(index, leaf)` locally immediately in the same call that performs the write (avoid re-reading storage after any external call), or
- Bind the `lastValidated` entry to the specific fill (e.g., include `makingAmount`/`remainingMakingAmount` in the key or pass the validated data directly through calldata instead of via storage), or
- Move the custom `IPostInteraction` external call to *after* the hashlock/immutables are finalized and the escrow is deployed, eliminating the reentrancy window between the storage write and its consumption.

### Proof of Concept
1. Maker creates a Merkle-multi-fill order with `allowMultipleFills` set, and sets a malicious contract `M` as the "custom postInteraction" target in the extension's `tail`.
2. A taker fills part of the order; LOP calls `takerInteraction` (validates proof #1, writes `lastValidated[key] = (idx1+1, leaf1)`), transfers assets, then calls `_postInteraction`.
3. Inside `_postInteraction`, before `lastValidated[key]` is read, the call to `M.postInteraction(...)` executes [2](#0-1) . `M` re-enters the Limit Order Protocol to perform a second partial fill of the same order with attacker-chosen `(idx2, leaf2, proof2)`, running `takerInteraction` again and overwriting `lastValidated[key] = (idx2+1, leaf2)` [6](#0-5) , then that nested fill completes its own `_postInteraction`/escrow deployment.
4. Control returns to the outer `_postInteraction`, which reads the now-overwritten `lastValidated[key]` = `(idx2+1, leaf2)` and uses `leaf2` as the outer escrow's `hashlock`, while `_isValidPartialFill` is checked against the outer fill's own `makingAmount`/`remainingMakingAmount` but `idx2` [7](#0-6) . If `idx2` is chosen to satisfy the arithmetic check, the outer escrow is deployed with a hashlock (`leaf2`) unrelated to the outer fill's real Merkle position. [1](#0-0) [8](#0-7)

    function _isValidPartialFill(
        uint256 makingAmount,
        uint256 remainingMakingAmount,
        uint256 orderMakingAmount,
        uint256 partsAmount,
        uint256 validatedIndex
    ) internal pure returns (bool) {
        uint256 calculatedIndex = (orderMakingAmount - remainingMakingAmount + makingAmount - 1) * partsAmount / orderMakingAmount;

        if (remainingMakingAmount == makingAmount) {
            // If the order is filled to completion, a secret with index i + 1 must be used
            // where i is the index of the secret for the last part.
            return (calculatedIndex + 2 == validatedIndex);
        } else if (orderMakingAmount != remainingMakingAmount) {
            // Calculate the previous fill index only if this is not the first fill.
            uint256 prevCalculatedIndex = (orderMakingAmount - remainingMakingAmount - 1) * partsAmount / orderMakingAmount;
            if (calculatedIndex == prevCalculatedIndex) return false;
        }

        return calculatedIndex + 1 == validatedIndex;
    }
