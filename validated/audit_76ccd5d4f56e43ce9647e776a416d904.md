Confirmed: the GraphQL mutation `Resolver.UpdateUserPassword` never calls `utils.VerifyPasswordComplexity`, while the equivalent REST endpoint `UserController.UpdatePassword` does. This is a direct analog of the reported bug class — a validation check applied at one entry point (constructor/creation, or in this case the REST setter) is missing from another setter path (the GraphQL mutation) that changes the same underlying security-relevant field.

### Title
Password complexity validation is bypassed in the GraphQL `updateUserPassword` mutation - (File: core/web/resolver/mutation.go)

### Summary
The REST API endpoint for changing a user's password (`UserController.UpdatePassword`) enforces `utils.VerifyPasswordComplexity` before persisting a new password, but the GraphQL mutation resolver `Resolver.UpdateUserPassword` calls `AuthenticationProvider().SetPassword` directly without ever validating the new password against the same complexity rules.

### Finding Description
`core/web/user_controller.go` requires that any new password pass `utils.VerifyPasswordComplexity(request.NewPassword, user.Email)` before calling `updateUserPassword`/`SetPassword`: [1](#0-0) 

The `SetPassword` implementations themselves (local, LDAP, OIDC ORMs) perform no complexity validation — they simply hash and store whatever string is given: [2](#0-1) 

The GraphQL resolver `Resolver.UpdateUserPassword`, which is the alternate entry point for the exact same "change my password" operation, checks only that the old password matches, then calls `SetPassword` directly — it never calls `utils.VerifyPasswordComplexity`: [3](#0-2) 

This mirrors the reported bug class precisely: a security invariant (minimum password complexity, analogous to `votingPeriod`/`votingQuorum` being required to be non-zero at construction) is enforced on one code path that creates/sets the value (`ValidateAndHashPassword`/`NewUser` and the REST `UpdatePassword` setter) but is missing on another reachable setter path (`UpdateUserPassword` GraphQL mutation) that mutates the same field.

Password complexity is otherwise enforced centrally via `utils.VerifyPasswordComplexity`, requiring at least `MinRequiredLen` (16) characters and no leading/trailing whitespace: [4](#0-3) 
And this is the function used both at user-creation time and in the REST password-update path — but omitted from the GraphQL path.

### Impact Explanation
Any authenticated user who knows their current password can set their new password to an arbitrarily short/weak value (e.g., a single character) via the GraphQL API, bypassing the intended organization-wide password complexity policy. This weakens brute-force/credential-stuffing resistance for that admin/API account, undermining the operator security invariant that all Chainlink node API users must have passwords meeting the documented complexity requirements. Because the node API password gates access to job management, key management, and other sensitive node operations, a weakened password materially increases the risk of account compromise.

### Likelihood Explanation
High. This requires no special privilege beyond an already-authenticated session (which is the same precondition needed for the correctly-validated REST endpoint) and no unusual state; it is a straightforward mutation invocable by any logged-in operator UI user via the GraphQL endpoint. There is no additional check anywhere in the call chain (`Resolver.UpdateUserPassword` → `AuthenticationProvider().SetPassword`) that would prevent it.

### Recommendation
Add the same `utils.VerifyPasswordComplexity(args.Input.NewPassword, dbUser.Email)` check (returning a mutation-level validation error, consistent with the `NewUpdatePasswordPayload` error pattern already used for the old-password mismatch case) inside `Resolver.UpdateUserPassword` before calling `SetPassword`, so both code paths that can change a password enforce identical validation. Alternatively, centralize the complexity check inside `AuthenticationProvider.SetPassword` (or `ValidateAndHashPassword`) itself so it cannot be bypassed by any future caller.

### Proof of Concept
1. Log in via the Operator UI / GraphQL endpoint as any existing node API user, obtaining a valid session cookie.
2. Send the following GraphQL mutation with the correct current password and an arbitrarily weak new password (e.g., `"a"`):
```graphql
mutation {
  updateUserPassword(input: { oldPassword: "<currentPassword>", newPassword: "a" }) {
    ... on UpdatePasswordSuccess {
      user { email }
    }
    ... on InputErrors {
      errors { path message code }
    }
  }
}
```
3. Observe that the mutation succeeds and `SetPassword` is called with `newPassword = "a"`, whereas submitting the same weak password via `PATCH /v2/user/password` (REST) is rejected with `HTTP 422` and the message `"password is less than 16 characters long"` as shown in the existing REST test suite: [5](#0-4)

func VerifyPasswordComplexity(password string, disallowedStrings ...string) (merr error) {
	errMsg := ErrMsgHeader
	var stringErrs []string

	if LeadingWhitespace.MatchString(password) || TrailingWhitespace.MatchString(password) {
		stringErrs = append(stringErrs, ErrWhitespace.Error())
	}

	if len(password) < MinRequiredLen {
		stringErrs = append(stringErrs, fmt.Sprintf("password is less than %d characters long", MinRequiredLen))
	}

	for _, s := range disallowedStrings {
		if strings.Contains(strings.ToLower(password), strings.ToLower(s)) {
			stringErrs = append(stringErrs, fmt.Sprintf("password may not contain: %q", s))
		}
	}

	if len(stringErrs) > 0 {
		for _, stringErr := range stringErrs {
			errMsg = fmt.Sprintf("%s	%s\n", errMsg, stringErr)
		}
		merr = errors.New(errMsg)
	}

	return
}
