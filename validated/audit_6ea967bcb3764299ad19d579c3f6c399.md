### Title
Authentication error paths leak raw internal error strings to unauthenticated callers - ([File: core/web/auth/helpers.go])

### Summary
`jsonAPIError` serializes any non-`*models.JSONAPIErrors` error directly via `err.Error()` into the JSON response body. In `AuthenticateBySession`, `AuthenticateByToken`, and `AuthenticateExternalInitiator` (`core/web/auth/auth.go`), several error branches return the raw underlying error (e.g., from `AuthorizedUserWithSession`, `FindUserByAPIToken`, `clsessions.AuthenticateUserByToken`, or the `errors.Wrap(err, "finding external initiator")` path) instead of the generic `auth.ErrorAuthFailed`, and this raw error is surfaced to an unauthenticated caller through the `Authenticate` middleware's call to `jsonAPIError(c, http.StatusUnauthorized, err)`.

### Finding Description
The `Authenticate` middleware at `core/web/auth/auth.go:157-175` iterates over auth methods and, if the final error is not `auth.ErrorAuthFailed`, passes it straight to `jsonAPIError`:
```go
if err != nil {
    c.Abort()
    jsonAPIError(c, http.StatusUnauthorized, err)
    return
}
```
`jsonAPIError` (`core/web/auth/helpers.go:15-23`) only special-cases errors of type `*models.JSONAPIErrors`; anything else falls through to `models.NewJSONAPIErrorsWith(err.Error())`, which puts the raw `Error()` string of the underlying error directly into the response JSON.

Looking at the callers:
- `AuthenticateBySession` (`auth.go:55-71`) returns any error from `authr.AuthorizedUserWithSession(ctx, sessionID)` unmodified — there is no filtering to `auth.ErrorAuthFailed` for non-"not found" failures (e.g., a database connectivity error, unexpected DB error, or any other internal error type raised by the auth provider implementation would flow straight through).
- `AuthenticateByToken` (`auth.go:78-112`) filters `sql.ErrNoRows` / `clsessions.ErrUserSessionExpired` from `FindUserByAPIToken` to `auth.ErrorAuthFailed`, but any *other* error type from that call, or any error from `clsessions.AuthenticateUserByToken`, is returned raw (`auth.go:98`, `auth.go:103`).
- `AuthenticateExternalInitiator` (`auth.go:119-151`) explicitly wraps unexpected `FindExternalInitiator` errors with `errors.Wrap(err, "finding external initiator")` (`auth.go:132`), which is not `auth.ErrorAuthFailed`, so it also reaches `jsonAPIError` and exposes the wrapped underlying error text (potentially raw DB driver error strings) to the caller.

This gives an unauthenticated attacker a path to trigger backend error conditions (e.g., malformed request causing driver-level errors, or any implementation-specific `AuthenticationProvider`/`Authenticator` error) and read back the internal error text in the HTTP response, rather than a generic "Unauthorized" message.

I was not able to fully verify, within the available tool budget, the exact set of error types each concrete `Authenticator`/`AuthenticationProvider` implementation (`localauth`, `ldapauth`, `oidcauth`) can realistically produce for `AuthorizedUserWithSession` / `FindUserByAPIToken`, so I cannot confirm with certainty that any of these paths can be forced by an unauthenticated caller to yield a *sensitive* (as opposed to generic driver/timeout) error string, or that these errors would contain data such as email existence signals or secrets.

### Impact Explanation
If reachable, this is an information-disclosure issue: internal error text (potentially including database driver messages, connection details, or implementation internals) would be returned to an unauthenticated client, aiding fingerprinting/enumeration attacks and violating the general principle that internal error state should never leave a response boundary. This does not by itself grant authentication bypass, key/secret disclosure, or privilege escalation — the impact is confined to error-message content, not a functional bypass of any auth check.

### Likelihood Explanation
Any unauthenticated caller can send a session or `X-API-KEY`/`X-API-SECRET` request; no special preconditions are required. However, triggering an error path that returns something more than `auth.ErrorAuthFailed` requires the backing `Authenticator` implementation to actually return a non-`sql.ErrNoRows`/non-`ErrUserSessionExpired` error under attacker-controlled conditions (e.g., malformed input causing a driver-level failure) — this depends on implementation details of `localauth`/`ldapauth`/`oidcauth` that were not fully verified. Absent confirmation of a concrete trigger producing a sensitive string (vs. a generic, non-sensitive Go error like context deadline exceeded), this remains a lower-confidence, defense-in-depth-style finding rather than a demonstrated concrete leak of secrets/PII.

### Recommendation
In `AuthenticateBySession`, `AuthenticateByToken`, and `AuthenticateExternalInitiator`, normalize all non-nil errors returned to the `Authenticate` middleware to `auth.ErrorAuthFailed` (or a similarly generic sentinel) for any case that isn't already a deliberate expected error, and log the original error server-side instead of forwarding it to `jsonAPIError`. Alternatively, harden `jsonAPIError` itself to never emit `err.Error()` for errors originating from the `Authenticate` middleware, always substituting a fixed message like `"Unauthorized"`.

### Proof of Concept
Go unit test plan (in `core/web/auth/auth_test.go` or a new `helpers_test.go`):
1. Construct a mock `Authenticator` whose `AuthorizedUserWithSession` returns a distinctive internal error, e.g. `errors.New("pq: connection to server at \"10.0.0.5\" failed")`.
2. Call `AuthenticateBySession` (or invoke the `Authenticate(store, AuthenticateBySession)` gin handler with a fake session cookie) and capture the `httptest.ResponseRecorder` body.
3. Assert the JSON body's error `detail` field does **not** contain the substring `"10.0.0.5"` or `"pq:"` — expected (buggy) behavior today is that it *does* contain it, since `jsonAPIError` calls `models.NewJSONAPIErrorsWith(err.Error())` unfiltered.
4. Repeat for `AuthenticateByToken` with `FindUserByAPIToken` returning a non-`sql.ErrNoRows` error, and for `AuthenticateExternalInitiator` with `FindExternalInitiator` returning a wrapped internal error, asserting the response body only ever contains the literal string `"Unauthorized"`/`"not a valid session"` and never the underlying error text.
