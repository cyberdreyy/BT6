### Title
`resolver.Resolve()` uses `context.Background()` instead of the job's cancellable context, letting a cancelled job's GCP STS/SecretManager calls run to completion - ([File: helpers/secrets/resolvers/gcp_secret_manager/resolver.go])

### Summary
The `gcp_secret_manager` resolver's `Resolve()` method calls `v.client.GetSecret(context.Background(), ...)`, ignoring any per-job cancellation context. Because the `SecretResolver.Resolve()` interface itself is defined as `Resolve() (string, error)` with no `context.Context` parameter, there is no mechanism by which a cancelled job can interrupt an in-flight STS token exchange or Secret Manager access call.

### Finding Description
The call chain is: `Build.resolveSecrets` → `Build.attemptResolveSecrets` → `Build.executeResolveSecretsStage` (`common/build.go`) → `defaultSecretsResolver.Resolve`/`handleSecret` (`common/secrets.go`) → `gcp_secret_manager.resolver.Resolve()` (`helpers/secrets/resolvers/gcp_secret_manager/resolver.go:40-46`) → `service.Client.GetSecret(context.Background(), secret)` (`helpers/gcp_secret_manager/service/gcp_secret_manager.go:38-60`), which sequentially calls `getToken` (STS token exchange) and `accessSecret` (Secret Manager access). [1](#0-0) [2](#0-1) 

The `SecretResolver` interface (`common/secrets.go:28-32`) declares `Resolve() (string, error)` with no context argument, so even if `Build.executeResolveSecretsStage` (`common/build.go:1757-1786`) has access to job-scoped state, there's no plumbing to pass a cancellable context down into any resolver, and `gcp_secret_manager`'s resolver hardcodes `context.Background()` rather than deriving one from anything build-scoped. [3](#0-2) [4](#0-3) 

This means: an attacker (pipeline author) can configure a `secrets: gcp_secret_manager` block referencing a workload identity federation / STS setup they control (or one that is slow/unresponsive), causing `getToken`/`accessSecret` HTTP calls to hang. If the job is then cancelled (e.g. via `gitlab-ci` cancel button or trace abort), the `Build`'s own cancellation signaling (via `trace.SetCancelFunc`/`SetAbortFunc`, `common/build.go:1681-1684`) has no way to reach the blocked `context.Background()`-scoped network call, because it isn't tied to any cancellable context at all. The retry loop (`attemptResolveSecrets`, `common/build.go:1742-1755`) will also keep re-invoking `executeResolveSecretsStage` synchronously, further compounding any concurrency-slot/goroutine accumulation on repeated attempts.

### Impact Explanation
If the STS/SecretManager network calls hang (due to attacker-controlled or slow/unreachable STS/audience endpoints), cancelling the job at the GitLab UI/API level does not free the underlying goroutine or its network connection performing `getToken`/`accessSecret`, since neither is bound to a cancellable context. The stage's synchronous execution (blocking inside `section.Execute`) means the runner-side goroutine handling that job also cannot return promptly, potentially holding a job/concurrency slot longer than intended and delaying other projects' jobs from being picked up on that runner. The blast radius is scoped to the runner instance's overall concurrency budget, not project isolation or secret leakage.

### Likelihood Explanation
This requires only an unprivileged pipeline author capable of defining a `secrets: gcp_secret_manager` stanza that is configured to point to a slow-responding or hung STS/audience/service target (e.g., a project-controlled workload identity federation provider that is deliberately non-responsive, or exploiting normal network latency/outage conditions). No special runner privilege is needed beyond having the GCP secret manager resolver enabled, which is an intended runner feature. The bug is fully reachable through standard `.gitlab-ci.yml` configuration and does not require any secondary compromise.

### Recommendation
Thread a job-scoped, cancellable `context.Context` through the entire secrets-resolution call path: change `SecretResolver.Resolve()` (and `SecretsResolver.Resolve`, `defaultSecretsResolver.handleSecret`) to accept a `context.Context`, have `Build.executeResolveSecretsStage`/`resolveSecrets` pass the build's cancellation context, and update `gcp_secret_manager.resolver.Resolve()` (and other resolvers using `context.Background()`) to use that context instead so `GetSecret`, `getToken`, and `accessSecret` calls are aborted promptly on job cancellation. Additionally, apply a bounded per-call timeout as defense in depth for STS/SecretManager calls.

### Proof of Concept
Go unit/integration test plan:
1. In `helpers/gcp_secret_manager/service`, construct a `Client` with a mock `getTokenFunc` that blocks on a channel until explicitly released (mirroring the existing table-driven tests in `gcp_secret_manager_test.go`).
2. Call `client.GetSecret(ctx, secret)` with a `ctx` derived from `context.WithCancel`, then cancel `ctx` while `getToken` is blocked.
3. Assert that because the resolver layer (`resolver.Resolve()`) actually invokes `GetSecret(context.Background(), ...)` rather than the cancellable `ctx`, the underlying goroutine/mock call is unaffected by cancellation — i.e., add an instrumentation counter/goroutine-leak detector (e.g. `goleak`) around a call to `resolver.Resolve()` wrapped in a cancellable context that gets cancelled mid-call, and assert the blocked goroutine is still running after cancellation returns control to the caller.
4. At the `Build` level, simulate `Build.executeResolveSecretsStage` being cancelled via the job's trace abort, and assert that a concurrently-queued second `Build.Run` for a different project is delayed until the first `GetSecret` call's blocking channel is released, demonstrating concurrency-slot starvation across "tenants".

func (c Client) GetSecret(ctx context.Context, secret *spec.GCPSecretManagerSecret) (string, error) {
	tokenResponse, err := c.getToken(ctx, secret)
	if err != nil {
		return "", fmt.Errorf("failed to exchange sts token: %w", err)
	}

	tokenSource := toTokenSource(tokenResponse)

	accessSecretVersionResponse, err := c.accessSecret(ctx, secret, tokenSource)

	if err != nil {
		return "", fmt.Errorf("failed to get secret: %w", err)
	}

	if accessSecretVersionResponse.Payload == nil {
		return "", common.ErrSecretNotFound
	}

	if !validChecksum(accessSecretVersionResponse.Payload) {
		return "", fmt.Errorf("data corruption detected")
	}

	return string(accessSecretVersionResponse.Payload.Data), nil
}

func (b *Build) executeResolveSecretsStage(trace JobTrace) error {
	b.OnBuildStageStartFn.Call(BuildStageResolveSecrets)
	defer b.OnBuildStageEndFn.Call(BuildStageResolveSecrets)

	section := helpers.BuildSection{
		Name:        string(BuildStageResolveSecrets),
		SkipMetrics: !b.Job.Features.TraceSections,
		Run: func() error {
			logger := b.getNewLogger(trace, b.Log(), false)
			defer logger.Close()

			resolver, err := b.secretsResolver(&logger, GetSecretResolverRegistry(), b.IsFeatureFlagOn)
			if err != nil {
				return fmt.Errorf("creating secrets resolver: %w", err)
			}

			variables, err := resolver.Resolve(b.Secrets)
			if err != nil {
				return fmt.Errorf("resolving secrets: %w", err)
			}

			b.secretsVariables = variables
			b.RefreshAllVariables()

			return nil
		},
	}

	return section.Execute(&b.logger)
}
