### Title
Unexpected stop-epoch yield can be harvested through just-in-time `depositDuringEpoch` deposits - (File: `contracts/IdleCDOEpochVariant.sol`)

### Summary
`depositDuringEpoch` prices new tranche shares using only the stored `expectedEpochInterest`, while `stopEpoch` can subsequently distribute a larger caller-supplied interest amount. An allowed depositor can therefore enter immediately before epoch end, obtain a dominant share of the tranche, and capture most of an unexpected positive interest override despite contributing almost none of the capital that generated it. [1](#0-0) [2](#0-1) 

### Finding Description
`depositDuringEpoch` is permitted while an epoch is running when the owner-enabled flag is cleared, AYS is disabled, the tranche already has supply, and the caller passes wallet validation. [3](#0-2) 

The function updates accounting and then calculates the expected final tranche NAV from the pre-deposit NAV plus the tranche's share of `expectedEpochInterest`. [4](#0-3)  It mints shares according to `(amount + prorated trancheInterest) * trancheSupply / expectedFinal`, so the mint price does not account for any interest above `expectedEpochInterest` that will later be supplied to `stopEpoch`. [5](#0-4) 

A valid attack sequence is:

1. A victim deposits into AA during the buffer phase, and an honest manager starts a fixed-APR epoch.
2. Immediately before `epochEndDate`, an attacker calls `depositDuringEpoch` with a much larger AA deposit. At that point `remaining` is nearly zero, so the attacker's own projected interest is nearly zero, but the attacker receives a dominant fraction of AA supply. [6](#0-5) 
3. After `epochEndDate`, the manager calls `stopEpoch(0, realizedInterest)` where `realizedInterest > expectedEpochInterest`. The override is allowed when `_newApr == 0` and covers pending withdrawal fees. [7](#0-6) 
4. `stopEpoch` pulls the actual interest and calls `_updateAccounting`, crystallizing the entire excess over expected interest as tranche gain. [8](#0-7) 
5. Because the attacker acquired most AA shares at a price that ignored this excess, the attacker receives most of the upside. After the epoch is stopped and withdrawal requests are re-enabled, the attacker can create a withdrawal receipt at the inflated tranche price and later claim it. [9](#0-8) [10](#0-9) 

The donation skim does not mitigate this because the attacker enters through a legitimate deposit rather than a raw token transfer. [11](#0-10)  The minted strategy-token backing also does not prevent the dilution because `mintStrategyTokens` adds principal backing while leaving the later excess interest to be shared by all outstanding tranche tokens. [12](#0-11) [13](#0-12) 

### Impact Explanation
This is direct theft of vault yield from incumbent tranche holders.

For example, assume:

- Existing AA principal: `1_000` underlying.
- Fixed expected epoch interest: `100` underlying.
- Attacker deposits `10_000` underlying one second before epoch end.
- No fees and no buffer.
- Honest borrower repayment/manager override realizes `200` underlying instead of `100`.

Ignoring the attacker's negligible one-second interest, the attacker receives approximately `10_000 * 1_000 / 1_100 = 9_090.909` AA-equivalent shares. After `stopEpoch`, total AA NAV is approximately `11_200`, while total supply is `10_090.909`, producing a price of approximately `1.1099`.

- Attacker redeems approximately `10_099`, gaining about `99` underlying from a deposit held for one second of the epoch.
- Without the JIT deposit, the incumbent would receive approximately `1_200`.
- With the JIT deposit, the incumbent receives approximately `1_110`, losing about `90` underlying of realized yield.

The loss scales approximately with the attacker's post-deposit share of the tranche and with the excess of realized stop interest over `expectedEpochInterest`.

### Likelihood Explanation
Likelihood is configuration-dependent but viable in supported deployments.

The attack requires:

- `isDepositDuringEpochDisabled == false`;
- `isAYSActive == false`;
- a non-programmable borrower;
- an existing tranche supply;
- a KYC-passing attacker when Keyring is configured; and
- an honest stop call or repayment flow that produces interest above `expectedEpochInterest`.

All of these states are explicitly supported by the deposit gate. [3](#0-2)  Positive stop-interest overrides are also an existing accounting path rather than an exceptional privileged abuse: any `_interest > 1` is accepted when `_newApr == 0` and it covers pending withdrawal fees. [2](#0-1) 

An attacker does not need to control the manager or borrower. They only need to observe that a larger-than-expected repayment or interest override will be used, then submit `depositDuringEpoch` before the epoch end. The deposit remains locked until normal withdrawal processing, but that does not prevent the immediate share-price dilution.

### Recommendation
Prevent mid-epoch deposits from being priced against incomplete epoch yield. At minimum, enforce a cutoff such that `depositDuringEpoch` cannot be called during a configurable period before `epochEndDate`.

A stronger design is to defer share issuance until after realized stop interest is known, or to calculate the mint price using a bound on the maximum realizable epoch gain rather than only `expectedEpochInterest`. Simply skimming raw underlying donations is insufficient because this attack uses the intended deposit path and supplies real principal.

### Proof of Concept
The following Foundry test can be added to `test/foundry/IdleCreditVault.t.sol`, using the existing test helpers and deployment:

```solidity
function testDepositDuringEpochJITHarvestsUnexpectedStopInterest() external {
    uint256 initialDeposit = 1_000 * ONE_SCALE;
    uint256 attackDeposit = 10_000 * ONE_SCALE;
    uint256 realizedInterest = 200 * ONE_SCALE;

    // Remove fee effects so the yield-dilution accounting is exact.
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0);

    // 10% APR for one year, no buffer.
    vm.startPrank(manager);
    cdoEpoch.setEpochParams(365 days, 0);
    IdleCreditVault(address(strategy)).setAprs(10e18, 10e18);
    vm.stopPrank();

    // Incumbent AA liquidity.
    uint256 victimShares = idleCDO.depositAA(initialDeposit);

    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);

    _startEpochAndCheckPrices(0);
    assertEq(cdoEpoch.expectedEpochInterest(), 100 * ONE_SCALE);

    // Enable the supported mid-epoch deposit path.
    vm.prank(owner);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);

    address attacker = makeAddr("jit-depositor");
    deal(defaultUnderlying, attacker, attackDeposit);

    // Enter one second before the epoch ends. The depositor's own
    // prorated interest is negligible, but minting uses expectedEpochInterest.
    vm.warp(cdoEpoch.epochEndDate() - 1);
    vm.startPrank(attacker);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), attackDeposit);
    uint256 attackerShares = cdoEpoch.depositDuringEpoch(attackDeposit, address(AAtranche));
    vm.stopPrank();

    // Honest manager settles an unexpectedly large realized interest payment.
    // `_newApr == 0` makes the `realizedInterest > expectedEpochInterest`
    // override path valid.
    deal(defaultUnderlying, borrower, realizedInterest);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, realizedInterest);

    uint256 price = cdoEpoch.virtualPrice(address(AAtranche));
    uint256 attackerValue = attackerShares * price / ONE_TRANCHE_TOKEN;
    uint256 victimValue = victimShares * price / ONE_TRANCHE_TOKEN;

    // Without the JIT deposit the victim's claim is approximately
    // 1_000 principal + 200 realized yield = 1_200.
    assertLt(victimValue, 1_200 * ONE_SCALE);

    // The dominant JIT depositor captures most of the unexpected 100
    // underlying of excess yield despite entering at epoch end.
    assertGt(attackerValue, attackDeposit + 90 * ONE_SCALE);
}
```
