Based on my investigation, the strongest analog is the `SystemInstruction::InitializeNonceAccount` handler, which initializes a nonce account without requiring any signature from the nonce account itself.

### Title
Unsigned Front-Runnable Nonce Account Initialization Allows Authority Hijack and Fund Theft - ([File: programs/system/src/system_processor.rs])

### Summary
`SystemInstruction::InitializeNonceAccount` is processed without checking that the target nonce account (or any related party) signed the instruction. Only prior existence of the account (created via a separate `CreateAccount` instruction) and its `Uninitialized` state are checked. If a legitimate user submits `CreateAccount` for a nonce account in one transaction and a subsequent `InitializeNonceAccount` in a later, separate transaction (rather than atomically bundling both in one transaction, as the SDK/CLI helpers do), a third party can observe the pending state and front-run the second transaction with their own `InitializeNonceAccount` instruction naming themselves as the nonce authority.

### Finding Description
`initialize_nonce_account` only verifies that the account is writable, in the `Uninitialized` state, and rent-exempt; it does not check any signer at all: [1](#0-0) 

The `system_processor.rs` dispatcher for `InitializeNonceAccount` likewise only borrows the account and checks the sysvars — it never calls `instruction_context.is_instruction_account_signer` on the nonce account or the authority: [2](#0-1) 

This contrasts with the vote program's `InitializeAccount`, which explicitly requires the `node_pubkey` to be a signer via `verify_authorized_signer`, closing this exact race for vote accounts: [3](#0-2) 

Because `InitializeNonceAccount` has no such signer requirement, any account that has been created (funded, allocated, and assigned to the system program) but is still `Uninitialized` is "up for grabs" by whoever's `InitializeNonceAccount` transaction lands first — this is the direct Solana analog of the GSP `init()` front-running bug: an unprivileged party can steal the initialization step and set themselves as the account's controlling authority.

### Impact Explanation
If the attacker's `InitializeNonceAccount` instruction lands before the legitimate owner's, the attacker becomes the nonce account's authority (`nonce::state::Data.authority`) while the account already holds the lamports transferred during `CreateAccount`. The attacker, as authority, can subsequently issue `WithdrawNonceAccount` to drain the account's lamports to themselves, resulting in concrete unsigned fund theft from the original creator/funder. This requires the ecosystem/dApp code to split account creation and initialization into two separate transactions instead of bundling them atomically (as the CLI/SDK helpers such as `create_nonce_account` do by default), which limits — but does not eliminate — real-world exposure.

### Likelihood Explanation
Likelihood is low-to-medium: the exploit requires (1) an entity to create a nonce account and delay sending the paired `InitializeNonceAccount` in a separate transaction, and (2) an attacker to observe this in the mempool/gossip and race a transaction ahead of it. Because all standard Agave SDK/CLI construction helpers bundle `CreateAccount` + `InitializeNonceAccount` atomically in one transaction/message (see `cli/src/nonce.rs`, `system_instruction::create_nonce_account`), this is generally not hit by default usage; it would primarily affect custom off-path integrations or multi-step onboarding flows.

### Recommendation
Require a signer check in `initialize_nonce_account` / the `InitializeNonceAccount` processor arm — e.g., require the nonce account itself (or a designated creator) to be a signer on the `Initialize` instruction, mirroring the vote program's `verify_authorized_signer` pattern, or document/enforce (at the SDK level) that `CreateAccount` and `InitializeNonceAccount` must always be atomically combined in a single transaction.

### Proof of Concept
1. Victim submits Tx1: `system_instruction::create_account(payer, nonce_pubkey, lamports, NonceState::size(), &system_program::id())`, signed by `payer` and `nonce_keypair` — creating an uninitialized, rent-exempt nonce account owned by the system program.
2. Victim intends to submit Tx2: `system_instruction::initialize_nonce_account(&nonce_pubkey, &victim_authority)` afterward.
3. Attacker observes Tx1 land (or observes it pending) and submits Tx3: `system_instruction::initialize_nonce_account(&nonce_pubkey, &attacker_pubkey)` before Tx2 is confirmed. Since `initialize_nonce_account` ( [4](#0-3) ) and the processor dispatch ( [2](#0-1) ) never verify a signer for the nonce account, Tx3 succeeds and sets `attacker_pubkey` as the nonce authority.
4. Victim's Tx2 now fails with `InstructionError::InvalidAccountData` because the account is already `Initialized` (as demonstrated by `initialize_inx_initialized_account_fail`, [5](#0-4) ).
5. Attacker, now the authority, submits `system_instruction::withdraw_nonce_account` to drain the account's lamports (funded by the victim in Tx1) to an attacker-controlled address.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}

/// Initialize the vote_state for a vote account
/// Assumes that the account is being init as part of a account creation or balance transfer and
/// that the transaction must be signed by the staker's keys
pub fn initialize_account<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    vote_init: &VoteInit,
    signers: &HashSet<Pubkey, S>,
    clock: &Clock,
) -> Result<(), InstructionError> {
    VoteStateHandler::check_vote_account_length(vote_account, target_version)?;
    let versioned = vote_account.get_state::<VoteStateVersions>()?;

    if !versioned.is_uninitialized() {
        return Err(InstructionError::AccountAlreadyInitialized);
    }

    // node must agree to accept this vote account
    verify_authorized_signer(&vote_init.node_pubkey, signers)?;

    VoteStateHandler::init_vote_account_state(vote_account, vote_init, clock, target_version)
}
