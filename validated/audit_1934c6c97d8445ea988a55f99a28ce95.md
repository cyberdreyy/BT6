### Title
`bitcoin_block_arrival` can permanently wedge a signer's local state machine into `Uninitialized`/no-valid-miner after any transient error, causing it to reject all future valid proposals - (File: `stacks-signer/src/v0/signer_state.rs`)

### Summary
`LocalStateMachine::bitcoin_block_arrival` follows the same "irreversible sanity-gate" pattern as the reported Seaport bug: it optimistically destroys the prior good state up front (`std::mem::replace(self, Self::Uninitialized)`) and only restores a valid state at the very end of the function if every intervening fallible step succeeds. Any `?`-propagated error on the way (client/DB errors, tenure-validity checks, `get_current_and_last_sortition`, `make_miner_state`, etc.) causes the function to return early while `self` is still `Self::Uninitialized`, permanently discarding the previously good `tx_replay_set` and parent-tenure/miner view. The code even documents the fragility: "we do this at the end so that the transform isn't fallible... we should come up with a better scheme here."

### Finding Description
`bitcoin_block_arrival` starts with: [1](#0-0) 
which replaces `self` with `Self::Uninitialized` before doing any of the actual work, keeping `prior_state_machine` only as a local variable. It restores `self` to a proper `Initialized` state only at the very end: [2](#0-1) 
with the accompanying comment acknowledging the risk of this scheme.

Between those two points there are multiple fallible operations that `return Err(...)` (via `?` or explicit `return`) without first restoring `self`:
- The replay-state inference check: if `tx_replay_scope` is unexpectedly `None` while `tx_replay_set` is non-empty, the function returns `Err(SignerChainstateError::LocalStateMachineNotReady)` with `self` left as `Uninitialized`: [3](#0-2) 
- `handle_possible_bitcoin_fork(...)?` can propagate an error.
- `client.get_current_and_last_sortition()?`, `cur_sortition.is_tenure_valid(...)?`, `last_sortition.try_into()?`, and `Self::make_miner_state(...)?` can all propagate errors: [4](#0-3) 

Once any of these paths is taken, `self` is stuck as `LocalStateMachine::Uninitialized`. On the *next* call, `bitcoin_block_arrival`'s match arm for `Uninitialized` does not restore the previously known miner/tenure/replay state — it falls back to a bare placeholder with `MinerState::NoValidMiner` and an empty replay set: [5](#0-4) [6](#0-5) 

This is consequential because the block-proposal check path (`GlobalStateView::check_proposal` for v2, and the analogous v1 path) treats anything other than `MinerState::ActiveMiner` as an automatic, hard rejection: [7](#0-6) 

So a signer whose local state machine transiently errors out of `bitcoin_block_arrival` loses its `ActiveMiner`/replay-set context, and even though subsequent calls don't error out forever (they can re-derive `ActiveMiner` from a fresh sortition query), any prior in-progress `tx_replay_set`/`tx_replay_scope` state is silently wiped without going through the designed fail-safe (`handle_possible_replay_failsafe`), and the signer will reject every proposal it receives until a subsequent `bitcoin_block_arrival` call happens to complete cleanly and reconstruct a valid `ActiveMiner`. If the triggering condition recurs on every attempt (e.g., a lingering DB/client error, or a burn view for which `get_current_and_last_sortition`/`is_tenure_valid` keeps failing), the signer is wedged indefinitely into `NoValidMiner`/`Uninitialized`, unable to sign any valid block — a liveness break analogous to the permanently-bricked contract in the report, caused by an early, unconditional "reset to invalid" that has no guaranteed rollback path.

### Impact Explanation
This matches the "High" impact bucket: a signer can be wedged into never signing valid blocks (liveness), and it also risks losing its tx-replay equivocation-guard state (`tx_replay_set`/`tx_replay_scope`) outside of the intended fail-safe reset path (`handle_possible_replay_failsafe`), which is explicitly designed to be the only sanctioned way to clear replay state. An uncontrolled reset via this error path could interact badly with the replay-protection invariant the signer relies on across forks/tenure-extends.

### Likelihood Explanation
The precondition is any transient failure during `bitcoin_block_arrival` after the state has been provisionally wiped — a client/RPC hiccup, a DB error, or (most interestingly) the internal `ReplayState::infer_state` returning `None` because `tx_replay_scope` is unset while `tx_replay_set` is non-empty, a state combination that can legitimately arise from bitcoin-fork handling. Because this function runs on every burn-block arrival event for every signer, and its early-teardown/late-restore pattern is unconditional, the window for hitting this is not rare; it does not require a signer majority, another signer's key, or node access — only a burn-block event that triggers one of the internal error branches while processing miner-state/replay-state derivation. The report itself notes: "we should come up with a better scheme here," which is the codebase authors' own acknowledgment that this pattern is fragile.

### Recommendation
Refactor `bitcoin_block_arrival` so that `self` is only ever set to `Uninitialized` if the function is guaranteed to complete, or so that all early-return error paths explicitly restore `self` to `LocalStateMachine::Initialized(prior_state_machine)` (or an appropriate `Pending` variant) before returning `Err`, mirroring what is already done correctly for the `node_behind_expected || node_on_equal_fork` branch. Alternatively, compute the new state into a local variable throughout and only assign to `self` once, at the single success exit point, never destructively mutating `self` before success is known.

### Proof of Concept
Conceptual PoC (unit-test style), consistent with existing tests in `stacks-signer/src/tests/signer_state.rs`:
1. Initialize a `LocalStateMachine::Initialized(SignerStateMachine)` with a non-empty `tx_replay_set` but drive `tx_replay_scope` to `None` (achievable via the existing bitcoin-fork/replay-scope handling paths exercised in `check_capitulate_viewpoint_time_guards`/replay tests).
2. Call `bitcoin_block_arrival` with an `expected_burn_block` such that `node_behind_expected`/`node_on_equal_fork` is false but `ReplayState::infer_state(&tx_replay_set, tx_replay_scope)` returns `None` (lines 630-638).
3. Observe the function returns `Err(SignerChainstateError::LocalStateMachineNotReady)` and `self` is now `LocalStateMachine::Uninitialized`, discarding the previously known `ActiveMiner`/replay state.
4. Call `bitcoin_block_arrival` (or `check_miner_inactivity`/`handle_pending_update`) again and observe `self` is rebuilt from `Self::place_holder(...)` (a `MinerState::NoValidMiner`, empty replay set) rather than the pre-error state, and that `GlobalStateView::check_proposal`/`SortitionsView::check_proposal` now reject any valid block proposal with `RejectReason::InvalidMiner` until a subsequent clean run happens to re-derive an `ActiveMiner`.

Note: I was not able to fully trace every internal call (`is_tenure_valid`, `get_current_and_last_sortition`, `make_miner_state`) down to a fully attacker-forced deterministic trigger within the remaining tool budget; the `ReplayState::infer_state` branch is the most directly-inspectable, reliably-reachable trigger. A background Devin session with full repo access could confirm the exact external conditions (e.g., specific bitcoin-fork sequences or malformed tenure-change proposals) that most reliably force one of these `?`-propagated errors in production.
