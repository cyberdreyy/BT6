### Title
Unchecked subtraction in `getSupply` RPC handler using time-inconsistent `capitalization`/`non_circulating_supply` reads can misreport (or underflow) circulating supply - (File: `rpc/src/rpc.rs`)

### Summary
The `get_supply` RPC handler computes `total_supply` and `non_circulating_supply.lamports` from the same `Arc<Bank>` at two different points in time separated by an account-index scan, then performs a plain, unchecked `u64` subtraction to derive `circulating`. This mirrors the OZ ERC1155Supply class of bug: a derived/aggregate value (`totalSupply` in the original report, `capitalization` here) is read either before or after — but not atomically with — the data used to compute a dependent quantity, so the two values can be mutually inconsistent when the underlying state is still changing during the query.

### Finding Description
`get_supply` first performs a full accounts-scan for non-circulating stake accounts, then reads `bank.capitalization()` afterwards: [1](#0-0) 

```rust
async fn get_supply(...) -> ... {
    let bank = self.bank(config.commitment);
    let non_circulating_supply =
        self.calculate_non_circulating_supply(&bank).await...?;
    let total_supply = bank.capitalization();
    ...
    RpcSupply {
        total: total_supply,
        circulating: total_supply - non_circulating_supply.lamports,
        non_circulating: non_circulating_supply.lamports,
        ...
    }
}
```

When `config.commitment` selects an unrooted/"processed" bank (the still-being-built working bank), that `Arc<Bank>` is not frozen: `capitalization` is a live `AtomicU64` that is concurrently mutated (via `fetch_add`/`fetch_sub` in `store_account_and_update_capitalization`, reward distribution, VAT burns, etc.) while transactions continue to land during the scan window: [2](#0-1) 

The non-circulating scan (`calculate_non_circulating_supply` → `get_filtered_indexed_accounts`/`get_program_accounts`) walks the stake-program accounts and sums balances as observed while the scan runs, which is not guaranteed to correspond to the exact same instant as the later `bank.capitalization()` read: [3](#0-2) 

Because `total_supply - non_circulating_supply.lamports` uses raw subtraction (no `checked_sub`/`saturating_sub`), any mismatch where the non-circulating sum exceeds the (differently-timed) capitalization value will either wrap to a huge bogus `u64` (release builds, the default arithmetic overflow behavior) or panic on overflow (debug builds). This is the same root-cause pattern as the reported bug: relying on an aggregate/derived total that isn't synchronized with the underlying account mutations used to compute a subtraction/derived quantity.

Notably, the codebase's own `/v0/circulating-supply` REST handler already guards against exactly this by using `saturating_sub`, confirming the maintainers are aware such a mismatch is possible: [4](#0-3) 

but the JSON-RPC `getSupply` path at `rpc/src/rpc.rs:1148` was not given the same protection.

### Impact Explanation
This is reachable by any unprivileged client calling the public `getSupply` JSON-RPC method with `commitment: "processed"` (or default) against a busy validator. The result is either a grossly incorrect `circulating` supply value returned to callers (wrong-data-returned) or — depending on the build's arithmetic-overflow configuration — a panic in the RPC-serving thread. No consensus state is affected, and no special access is required, matching the "wrong-slot/fork/account data returned" / decoder-misreporting class permitted by the validation rules.

### Likelihood Explanation
Requires no attacker privilege — a single `getSupply` call while the target bank is actively processing transactions (i.e., at "processed" commitment) is enough to expose the race window between the scan and the capitalization read. The window widens on validators with more stake accounts (longer scan time), making the race easier to hit on mainnet-scale validators, though the practical frequency of `non_circulating_supply.lamports` exceeding `total_supply` depends on concurrent capitalization-changing events (rewards distribution, incinerator burns, VAT burns) landing mid-scan.

### Recommendation
Use `total_supply.saturating_sub(non_circulating_supply.lamports)` (matching the existing `/v0/circulating-supply` REST handler) instead of raw subtraction, and consider reading `total_supply` before starting the scan (or otherwise ensuring both values are derived from the same consistent point in time) so `circulating` is never computed from mismatched snapshots.

### Proof of Concept
1. Run a validator handling steady transaction throughput.
2. Repeatedly issue `{"jsonrpc":"2.0","id":1,"method":"getSupply","params":[{"commitment":"processed"}]}` while a reward-distribution or incinerator-burn event is in flight on the working bank.
3. Because `calculate_non_circulating_supply` (a multi-account scan) completes before `bank.capitalization()` is sampled, the two values can reflect different points in time; instrument or artificially delay the scan (e.g., large stake-account set) to reliably produce `non_circulating_supply.lamports > total_supply`, and observe the unchecked subtraction at `rpc/src/rpc.rs:1148` wrap to a near-`u64::MAX` `circulating` value (release build) or panic the RPC service thread (debug/overflow-checked build).

pub fn calculate_non_circulating_supply(bank: &Bank) -> ScanResult<NonCirculatingSupply> {
    debug!("Updating Bank supply, epoch: {}", bank.epoch());
    let mut non_circulating_accounts_set: HashSet<Pubkey> = HashSet::new();

    for key in non_circulating_accounts() {
        non_circulating_accounts_set.insert(key);
    }
    let withdraw_authority_list = withdraw_authority();

    let clock = bank.clock();
    let stake_accounts = if bank
        .rc
        .accounts
        .accounts_db
        .account_indexes
        .contains(&AccountIndex::ProgramId)
    {
        bank.get_filtered_indexed_accounts(
            &IndexKey::ProgramId(stake::program::id()),
            // The program-id account index checks for Account owner on inclusion. However, due to
            // the current AccountsDb implementation, an account may remain in storage as a
            // zero-lamport Account::Default() after being wiped and reinitialized in later
            // updates. We include the redundant filter here to avoid returning these accounts.
            |account| account.owner() == &stake::program::id(),
            None,
        )?
    } else {
        bank.get_program_accounts(&stake::program::id())?
    };

    for (pubkey, account) in stake_accounts.iter() {
        let stake_account = account
            .deserialize_data::<StakeStateV2>()
            .unwrap_or_default();
        match stake_account {
            StakeStateV2::Initialized(meta)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            StakeStateV2::Stake(meta, _stake, _stake_flags)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            _ => {}
        }
    }

    let lamports = non_circulating_accounts_set
        .iter()
        .map(|pubkey| bank.get_balance(pubkey))
        .sum();

    Ok(NonCirculatingSupply {
        lamports,
        accounts: non_circulating_accounts_set.into_iter().collect(),
    })
}

async fn calculate_circulating_supply_async(bank: &Arc<Bank>) -> Result<u64, SupplyCalcError> {
    let total_supply = bank.capitalization();
    let bank = Arc::clone(bank);
    let non_circulating_supply =
        tokio::task::spawn_blocking(move || calculate_non_circulating_supply(&bank))
            .await
            .expect("Failed to spawn blocking task")
            .map_err(|e| SupplyCalcError::Scan(e.to_string()))?;

    Ok(total_supply.saturating_sub(non_circulating_supply.lamports))
}
