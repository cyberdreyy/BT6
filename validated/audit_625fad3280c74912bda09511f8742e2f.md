### Title
Unbounded per-request `do_load` calls in secondary-index scans due to `None`-by-default byte limit - ([File: accounts-db/src/accounts_db.rs])

### Summary
`AccountsDb::index_scan_accounts` iterates every pubkey returned by `AccountsIndex::get_index_key_pubkeys` and calls `self.do_load` for each one, checking `config.is_aborted()` only between iterations. The abort condition is driven by `Accounts::accumulate_and_check_scan_result_size`, which is a no-op unless `byte_limit_for_scan` (i.e. `JsonRpcConfig::scan_results_limit_bytes`) is `Some`. Since this option defaults to `None` and has no CLI `default_value`, an attacker who creates N SPL token accounts under a single owner can make one `getTokenAccountsByOwner` call trigger N `do_load` calls and proportional memory allocation with no cap.

### Finding Description
The RPC handler `JsonRpcRequestProcessor::get_filtered_spl_token_accounts_by_owner` (rpc/src/rpc.rs:2311-2357) calls `get_filtered_indexed_accounts`, which reads `self.config.scan_results_limit_bytes` and forwards it as `byte_limit_for_scans` to `bank.get_filtered_indexed_accounts` [1](#0-0) . That flows into `Accounts::load_by_index_key_with_filter`, which passes `byte_limit_for_scan` into a closure that calls `accumulate_and_check_scan_result_size` and aborts the `ScanConfig` only once the accumulated size *exceeds* the limit [2](#0-1) . That check is a no-op when `byte_limit_for_scan` is `None`: [3](#0-2) 

The actual scan loop in `AccountsDb::index_scan_accounts` iterates `self.accounts_index.get_index_key_pubkeys(&index_key)` — which returns the raw, attacker-sized list of pubkeys under the owner's secondary index — and calls `self.do_load` for every pubkey before the per-account callback (and thus the byte-limit check) ever runs, breaking only on `config.is_aborted()` on the *next* loop iteration: [4](#0-3) 

`JsonRpcConfig::scan_results_limit_bytes` defaults to `Option::default()` (`None`): [5](#0-4) 

and the corresponding CLI flag `--accounts-index-scan-results-limit-mb` has no `default_value`, so it stays unset unless an operator explicitly configures it: [6](#0-5) 

With `SplTokenOwner` indexing enabled (a supported, documented account-index feature) and no explicit `--accounts-index-scan-results-limit-mb`, an attacker who creates N token accounts under one owner causes a single `getTokenAccountsByOwner` call to perform N `do_load` calls (each of which, on disk-backed configurations, resolves through `BucketMap::read_value`), with memory for N `AccountSharedData` results collected via `collector: Vec<KeyedAccountSharedData>` [7](#0-6) . The cost is proportional to attacker-authored on-chain data rather than bounded by any explicit per-request limit.

### Impact Explanation
A single, low-rate `getTokenAccountsByOwner` call for an owner with N attacker-created token accounts drives O(N) `do_load`/`BucketMap::read_value` calls and O(N) memory allocation on the API node servicing the request, with no default cap. This matches the "RPC/validator single-request unbounded resource consumption" bounty category: attacker-controlled on-chain data size, not an explicit request parameter, determines the cost of one JSON-RPC call.

### Likelihood Explanation
Preconditions: the validator must have `AccountIndex::SplTokenOwner` enabled (an operator-selectable but supported and documented feature, explicitly listed as in-scope by the question), and must not have set `--accounts-index-scan-results-limit-mb` (the default state, since the flag has no default value). Given those preconditions — which do not require any special privilege from the attacker, only normal token-account creation transactions and one RPC call — the exploit is fully reproducible and repeatable at will.

### Recommendation
Give `scan_results_limit_bytes` a sane non-`None` default (or enforce a hard maximum count/byte limit independent of operator configuration) so that `index_scan_accounts`'s per-pubkey `do_load` loop is always bounded, regardless of whether `--accounts-index-scan-results-limit-mb` is set. Additionally, consider checking the abort condition/size accumulation before or during iteration over `get_index_key_pubkeys` rather than only relying on filters applied after `do_load` completes each iteration.

### Proof of Concept
Integration test in `accounts-db/src/accounts.rs` (or `runtime/src/bank/tests.rs`, following the pattern of `test_get_filtered_indexed_accounts_limit_exceeded`):
```rust
#[test]
fn test_index_scan_by_owner_unbounded_without_limit() {
    // Enable SplTokenOwner secondary index, matching AccountIndex::SplTokenOwner
    let account_indexes = spl_token_owner_index_enabled();
    let accounts = AccountsDb { account_indexes, ..AccountsDb::new_for_tests_with_config(...) };

    let owner = Pubkey::new_unique();
    const N: usize = 200_000; // attacker-controlled, unbounded in principle
    for _ in 0..N {
        // store a valid SPL token account with `owner` at the SPL_TOKEN_ACCOUNT_OWNER_OFFSET
        accounts.store_for_tests((slot, &[(&Pubkey::new_unique(), &make_token_account(owner))]));
    }
    accounts.add_root_and_flush_write_cache(slot);

    // Simulate the RPC default: byte_limit_for_scan = None (scan_results_limit_bytes unset)
    let result = accounts.load_by_index_key_with_filter(
        &Ancestors::default(),
        0,
        &IndexKey::SplTokenOwner(owner),
        |_| true,
        None, // default JsonRpcConfig::scan_results_limit_bytes
    ).unwrap();

    // FINDING: no cap enforced; do_load was called N times and N results collected,
    // with cost fully proportional to attacker-authored account count.
    assert_eq!(result.len(), N); // demonstrates missing bound
}
```
Expected result under current code: the call succeeds and returns all N accounts (no abort, no cap), demonstrating that a single request's cost scales unboundedly with attacker-controlled on-chain state whenever `scan_results_limit_bytes` is left at its default `None`.
