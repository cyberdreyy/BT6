### Title
Unbounded per-request cost in `getTokenAccountsByMint`/`getProgramAccounts` (SplTokenMint index) due to unpaginated, uncapped `index_scan_accounts` loop - ([File: accounts-db/src/accounts_db.rs])

### Summary
`AccountsDb::index_scan_accounts` iterates every pubkey returned by `get_index_key_pubkeys` and calls `do_load` on each one sequentially, with no per-request count cap and no default byte limit. An attacker who creates N spl-token accounts for a single mint (a normal, permissionless on-chain action) can make a single `getTokenAccountsByMint` RPC call force the validator to perform O(N) sequential account loads, so the CPU/wall-clock cost of that one call scales linearly with N.

### Finding Description
`getTokenAccountsByMint` (served through `get_token_accounts_by_owner`'s sibling path `get_filtered_spl_token_accounts_by_mint`) routes into `JsonRpcRequestProcessor::get_filtered_indexed_accounts` [1](#0-0) , which calls `Bank::get_filtered_indexed_accounts` → `Accounts::load_by_index_key_with_filter` [2](#0-1)  → `AccountsDb::index_scan_accounts`.

In `index_scan_accounts`, once the secondary index is used, the code does:
```
for pubkey in self.accounts_index.get_index_key_pubkeys(&index_key) {
    if config.is_aborted() { break; }
    if let Some((account, slot)) = self.do_load(...) { scan_func(...) }
}
``` [3](#0-2) 

`get_index_key_pubkeys` simply returns the full `Vec<Pubkey>` of every pubkey ever inserted for that mint into `spl_token_mint_index` [4](#0-3) . Each pubkey in that list is then loaded individually with a full `do_load` disk/cache lookup — this cost is O(N) in the number of token accounts under the mint, executed synchronously inside the single RPC request's blocking task.

The only mitigation is `accumulate_and_check_scan_result_size`, which aborts the scan once accumulated *result* bytes exceed `scan_results_limit_bytes` [5](#0-4) . This limit is controlled by the `--accounts-index-scan-results-limit-mb` CLI flag, which is **not set by default** — `scan_results_limit_bytes` defaults to `None` [6](#0-5)  and there is no `default_value` configured for the corresponding clap arg [7](#0-6) . When `byte_limit_for_scan` is `None`, `accumulate_and_check_scan_result_size` always returns `false` [8](#0-7) , so the scan never aborts by default — the entire `get_index_key_pubkeys` list is walked and `do_load`-ed regardless of size or count.

Other guards (`max_multiple_accounts`, `max_request_body_size`) apply to different endpoints (`getMultipleAccounts`, request body size) and do not bound this scan. There is no pagination or per-request count cap on `getTokenAccountsByMint`.

### Impact Explanation
A single unprivileged RPC call can force the node to perform an amount of work (sequential `do_load` calls) proportional to the number of token accounts ever created for an attacker-chosen mint — a count fully controlled by the attacker via ordinary, permissionless account-creation transactions. Because this executes inside a `spawn_blocking` task using the RPC blocking-thread pool, a sufficiently large N (achievable with a modest amount of prior on-chain activity, e.g. tens or hundreds of thousands of associated token accounts) causes substantial CPU/latency cost for a single low-rate RPC call, consistent with the "unbounded cost for a single low-rate call" impact category.

### Likelihood Explanation
Feasible and repeatable: creating spl-token accounts for a given mint is a normal, permissionless on-chain operation requiring no elevated privilege, and it does not need to be done by the attacker issuing the RPC call in the same session (they can be created ahead of time or by any number of prior legitimate users). Only a single `getTokenAccountsByMint` call (one request, well within the one-call-per-`CLUSTER_SLOT_TIME_TARGET/2` budget) is needed to trigger the O(N) scan. This requires the RPC node to have the `SplTokenMint` secondary index enabled — which is exactly the configuration needed to serve `getTokenAccountsByMint` at all — and to not have manually configured `--accounts-index-scan-results-limit-mb` (which is unset by default).

### Recommendation
Enforce a default, non-optional upper bound on the number of pubkeys iterated per `index_scan_accounts` call (independent of the optional byte-size limit), e.g., cap `get_index_key_pubkeys(...).len()` and return `ScanError::Aborted`/a dedicated RPC error before invoking `do_load` when the count exceeds a hard-coded or configurable maximum, and/or require a mandatory default value for `scan_results_limit_bytes` so unbounded scans cannot occur unless explicitly opted into by the operator.

### Proof of Concept
Integration test plan in `accounts-db/src/accounts_db/tests/impl.rs` style:
1. Configure `AccountsDb` with `AccountIndex::SplTokenMint` enabled via `spl_token_mint_index_enabled()` and `scan_results_limit_bytes = None` (default).
2. Create a single mint pubkey `mint_key`; store N (e.g. 50, 5_000, 50_000) synthetic spl-token accounts, each with distinct pubkeys but the same `mint_key` embedded at the correct offset (as in `test_flush_purged_zero_lamport_account_purges_secondary_index`, `accounts-db/src/accounts_db/tests/impl.rs:3500-3555`), and root/flush them.
3. Measure wall-clock time of `accounts.index_scan_accounts(&Ancestors::default(), bank_id, IndexKey::SplTokenMint(mint_key), |_| {}, &ScanConfig::default())` for increasing N.
4. Assert that measured time (or an instrumented `do_load` call counter) scales linearly with N and that no early abort occurs, confirming there is no per-request cap when `scan_results_limit_bytes` is `None`.
5. Optionally, extend to an RPC-level test invoking `JsonRpcRequestProcessor::get_filtered_indexed_accounts`/`get_token_accounts_by_owner` equivalent for mint filtering and assert response latency for N=50 vs N=50,000 differs by a factor consistent with linear scaling.

            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
