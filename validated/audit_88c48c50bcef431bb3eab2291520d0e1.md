**Analysis:**

The premise conflates two unrelated mechanisms: (1) Move's resource-level state mutation model for `stake::withdraw_with_cap`, and (2) the Rust-level `VMChangeSet`/`ChangeSet` squashing logic in `aptos-move/aptos-vm-types/src/change_set.rs`.

`stake::withdraw_with_cap` operates on a single `StakePool` resource read via `borrow_global_mut<StakePool>(pool_address)` [1](#0-0) . Every withdrawal caps the amount by the *current* in-memory `inactive` coin value at the time of execution: `withdraw_amount = min(withdraw_amount, coin::value(&stake_pool.inactive))` [2](#0-1) , then extracts exactly that amount from the resource in the same transaction [3](#0-2) . The resulting write op for the `StakePool` resource in the transaction's write set is a full, materialized overwrite of the resource — not a delta — so a subsequent transaction that reads the resource sees the fully-updated `inactive` balance, not a stale snapshot.

The `squash_additional_change_set`/`squash_additional_resource_writes` logic in `change_set.rs` [4](#0-3)  exists to combine writes produced by *multiple Move sessions within the same transaction* (e.g., prologue/execution/epilogue, or genesis module publishing as shown in `vm-genesis/src/lib.rs`) [5](#0-4) . It is not a mechanism that merges writes from two separate, sequential `withdraw` transactions, and it does not reintroduce a "stale StakePool snapshot" across transaction boundaries. Each transaction reads global storage as of its own execution point (with the block executor's validation ensuring correctness under speculative/parallel execution), so two sequential `withdraw_with_cap` calls will always operate on the correctly updated `inactive` balance — the second call's cap is bounded by whatever `inactive` remains after the first call's write is committed.

The formal spec for `withdraw` also encodes this cap explicitly, confirming the intended (and enforced) invariant that withdrawal is bounded by the actual `inactive`/`pending_inactive` balance at call time [6](#0-5) .

No unprivileged input to `withdraw_with_cap` can cause double-counting of inactive stake across two calls in the same epoch — the accounting is self-consistent because each call re-derives its cap from the post-previous-call resource state, and there is no cross-transaction "stale snapshot merge" pathway in the described files.

    public fun withdraw_with_cap(
        owner_cap: &OwnerCapability, withdraw_amount: u64
    ): Coin<AptosCoin> acquires StakePool, ValidatorSet {
        assert_reconfig_not_in_progress();
        let pool_address = owner_cap.pool_address;
        assert_stake_pool_exists(pool_address);
        let stake_pool = borrow_global_mut<StakePool>(pool_address);
        // There's an edge case where a validator unlocks their stake and leaves the validator set before
        // the stake is fully unlocked (the current lockup cycle has not expired yet).
        // This can leave their stake stuck in pending_inactive even after the current lockup cycle expires.
        if (get_validator_state(pool_address) == VALIDATOR_STATUS_INACTIVE
            && timestamp::now_seconds() >= stake_pool.locked_until_secs) {
            let pending_inactive_stake =
                coin::extract_all(&mut stake_pool.pending_inactive);
            coin::merge(&mut stake_pool.inactive, pending_inactive_stake);
        };

        // Cap withdraw amount by total inactive coins.
        withdraw_amount = min(withdraw_amount, coin::value(&stake_pool.inactive));
        if (withdraw_amount == 0) return coin::zero<AptosCoin>();

        event::emit(WithdrawStake { pool_address, amount_withdrawn: withdraw_amount });

        coin::extract(&mut stake_pool.inactive, withdraw_amount)
    }
