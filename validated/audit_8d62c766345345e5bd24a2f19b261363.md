### Title
Unbounded overwrite of `savedCallbacks` keyed by client-controlled `MessageId` in legacy gateway trigger handler enables cross-user response hijacking - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The gateway's legacy webhook/trigger handler stores a pending user callback in a shared map keyed solely by the client-supplied JSON-RPC request `ID` (propagated as `MessageId`), with no check for an existing in-flight entry before overwriting it. An unprivileged HTTP client to the gateway can supply a `MessageId` that collides with another concurrent request, hijacking the ability to receive that other request's asynchronous node response, or vice versa — corrupting response delivery. This mirrors the external report's root cause: an attacker-influenced identifier is trusted to gate state that is later relied upon to route/credit a result, without an atomicity/uniqueness check comparable to what re-entrancy guards or "no re-entrant overwrite" protections would provide.

### Finding Description
When the gateway receives a legacy-style JSON-RPC request, it builds an internal `api.Message` and sets `m.Body.MessageId = req.ID` directly from the caller-supplied JSON-RPC `id` field: [1](#0-0) 

This message is then dispatched to the DON handler's `HandleLegacyUserMessage`, which stores the caller's response `Callback` in a shared `savedCallbacks` map keyed by this attacker-controlled `MessageId`, with **no check for whether an entry already exists** at that key: [2](#0-1) 

Later, when a node responds for that method/`MessageId`, the handler looks up and deletes whatever callback currently occupies that key and delivers the response to it — with no verification that the responding session matches the callback owner: [3](#0-2) 

The only bound enforced upstream is a length cap (200 chars) on the request ID, not uniqueness: [4](#0-3) 

This is a structural contrast with the newer v2 HTTP trigger path, which explicitly guards against this exact class of bug by checking for an existing/in-flight `requestID` and rejecting the request with `jsonrpc.ErrConflict` before registering a callback: [5](#0-4) 

Without this same check in the legacy handler, two concurrent (or maliciously timed) requests using the same `MessageId`/request ID cause the second write to `savedCallbacks` to silently clobber the first. Whichever caller's callback is present in the map when the node responds receives the (possibly unrelated) response — analogous to the reported bug's core weakness where trusting attacker-influenced state (there, an untrusted swap estimate; here, an untrusted response-routing key) without exclusivity/ordering guarantees leads to funds/response misattribution.

### Impact Explanation
An unprivileged external caller of the gateway's legacy `/v2/...` (or equivalent JSON-RPC) endpoint can pick an arbitrary or predictable `MessageId`/request ID. By racing or reusing an ID, one user's HTTP request can capture (or be overwritten by) another concurrent user's pending trigger callback slot, causing:
- Cross-user response confusion: a workflow trigger's real response can be delivered to the wrong caller.
- Denial of service for the original caller, whose callback slot is silently evicted and who then times out.

This falls squarely within the accepted "cross-user response confusion" impact category for the internet-facing gateway component.

### Likelihood Explanation
Exploitation requires only sending two concurrent unauthenticated/unprivileged JSON-RPC requests with a colliding `id` value to the gateway's legacy endpoint before the first request's node response arrives — no special privileges, node compromise, or contract-level access is needed, only network access to the gateway HTTP endpoint and knowledge (or guessing) of an in-flight request ID. The absence of any uniqueness check (contrasted with the fix already present in the v2 path) makes this straightforward to trigger.

### Recommendation
Add the same in-flight uniqueness/rejection check to `HandleLegacyUserMessage` that already exists in `httpTriggerHandler.setupCallback`: before storing into `savedCallbacks`, check `if _, found := h.savedCallbacks[msg.Body.MessageId]; found` and reject the new request (e.g., with a conflict error) instead of overwriting. Consider deriving `MessageId` uniqueness scoping per-sender/session rather than relying purely on a global, client-supplied string, and add tests mirroring `TestHttpTriggerHandler_HandleUserTriggerRequest`'s "duplicate request ID" case for the legacy handler.

### Proof of Concept
1. Attacker sends legacy JSON-RPC request `A` to the gateway with `id = "X"`, targeting a workflow trigger; the gateway stores `savedCallbacks["X"] = callbackA` per [2](#0-1) .
2. Before nodes respond to request `A`, a victim (or the same attacker in a second session) sends request `B` also with `id = "X"` (same DON), which overwrites `savedCallbacks["X"] = callbackB` with no error, per the same code path (no `found` check exists, unlike [5](#0-4) ).
3. When a node responds with `MessageId = "X"`, `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackB`, deletes the entry, and sends the response intended for request `A`'s trigger to `callbackB` — see [3](#0-2) .
4. The attacker (owner of request `B`) receives a response destined for a different request/session, while the legitimate caller of request `A` never receives their response (times out).

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
