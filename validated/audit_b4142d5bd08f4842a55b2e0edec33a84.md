## Analysis

The Isomorph bug is a stale-authorization / trust-binding break: an entity's historical grant of custody (the depositor recorded as `relatedDepositor`) is not re-validated at the point where trust is consumed (`burn`/`withdraw`), letting an unentitled party redeem value that was staked by someone else.

The closest reachable analog in this repository is in the `multisig2` contract: confirmations recorded against a `RequestId` are never revalidated against the *current* set of live members. `delete_member` only purges requests that a removed member *originated*, not confirmations that member cast on other members' pending requests, and `confirm` counts confirmations purely by set size without checking that each confirming identity is still in `self.members`. ### Title
Multisig request can execute with confirmations from removed members (stale confirmation vs. live-member binding broken) - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` treats the size of the stored `confirmations: HashSet<String>` for a request as equivalent to "number of currently authorized members who approved," but `delete_member` never removes a departing member's confirmation entries from requests they did not themselves create. This breaks the equality `confirmations_counted == live_authorized_confirmers`, allowing a request to reach `num_confirmations` and execute using one or more confirmations cast by an account that is no longer a member at execution time.

### Finding Description
`confirm` increments/consults `self.confirmations.get(&request_id)` and executes once `confirmations.len() + 1 >= self.num_confirmations`, with no re-check that every account/key in that set is still present in `self.members`: [2](#0-1) 

`assert_valid_request`, called before both `confirm` and `delete_request`, only checks that the *caller* is currently a member and that the request/confirmation map entries exist — it does not scrub or revalidate previously recorded confirmations: [3](#0-2) 

`delete_member` is the only place member removal is handled, and it deliberately filters and deletes only the requests *originated* by the removed member (`r.member == member`); it removes that member's `num_requests_pk` bookkeeping, but does not touch `self.confirmations` entries the member added to *other* members' pending requests: [1](#0-0) 

Concretely: with `num_confirmations = 3` and 5 members, suppose member `X` confirms `RequestA` (created by another member) — 1/3. Separately, the members legitimately execute a `DeleteMember { member: X }` request (e.g. because `X`'s key was compromised or `X` left). `RequestA`'s confirmation set still contains `X`'s serialized identity because `delete_member` never scans/prunes `self.confirmations` for requests not authored by `X`. Two more currently-live members then confirm `RequestA`, and `confirm` computes `confirmations.len() + 1 = 3 >= num_confirmations`, executing the request — even though only 2 *live* members ever approved it after `X`'s removal.

This is the direct on-chain analog of the reported bug class: a custody/authorization record (`relatedDepositor` in the external report, `confirmations` set here) is trusted at time of use without re-validating it against the current state of the entity it was supposed to be scoped to (the depositor that actually minted it / the member who is actually still authorized).

### Impact Explanation
This matches the Critical impact category explicitly listed in scope: "a multisig request executed below threshold." A `Transfer`, `FunctionCall`, `AddKey`/full-access-key grant, or `DeployContract` action can be pushed through with fewer currently-authorized approvals than `num_confirmations` mandates, letting funds move or control of the account (via `AddKey` with a full access key) be granted without the required live quorum.

### Likelihood Explanation
The precondition (a member removed while they have outstanding confirmations on other pending requests) is a normal, expected operational event — not an edge case requiring a compromised deployment or foundation privilege. Any coalition of the remaining members (or an attacker who compromises/collaborates with one already-confirmed but soon-to-be-removed member) can exploit this by simply timing a `DeleteMember` request relative to outstanding confirmations, since the removal of a member is a routine multisig action already supported by the contract and does not itself require special access beyond normal quorum.

### Recommendation
When executing `DeleteMember`, iterate all `self.requests` entries and remove the deleted member's entry from every stored `confirmations` `HashSet`, not just requests it originated. Alternatively, when tallying confirmations in `confirm`, filter the stored confirmation set to intersect with `self.members` before comparing against `num_confirmations`, so stale confirmations from removed members can never count toward the live quorum.

### Proof of Concept
1. Deploy `multisig2` with 5 members `[A,B,C,D,E]`, `num_confirmations = 3`.
2. `B` calls `add_request` creating `RequestA` (e.g. `Transfer` to an attacker-controlled account).
3. `E` calls `confirm(RequestA)` → confirmations = `{E}` (1/3).
4. Separately, members legitimately execute `DeleteMember { member: E }` (via its own properly-confirmed multisig request), removing `E` from `self.members`. `RequestA`'s confirmation set still contains `E` because `delete_member` (multisig2/src/lib.rs:355-379) only clears requests where `r.member == E`, and `RequestA` was authored by `B`, not `E`.
5. `C` and `D` (both still live members) call `confirm(RequestA)`, bringing `confirmations.len() = 3 >= num_confirmations(3)`.
6. `RequestA` executes via `execute_request`, transferring funds — even though only `C` and `D` (2 live members) actually approved it after `E`'s removal, one confirmation short of `num_confirmations` among currently-authorized signers.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
