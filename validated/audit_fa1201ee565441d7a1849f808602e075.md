### Title
`SnapshotHashes::sanitize` does not enforce `MAX_INCREMENTAL_SNAPSHOT_HASHES`, allowing unbounded `incremental` vector through the gossip decode harness - ([File: gossip/src/crds_data.rs])

### Summary
`SnapshotHashes::sanitize` in `gossip/src/crds_data.rs` only validates slot ordering and bounds (`MAX_SLOT`) and wallclock, but never checks the length of the `incremental: Vec<(Slot, Hash)>` field against `MAX_INCREMENTAL_SNAPSHOT_HASHES`, a limit that is documented and enforced only in the sender-side packet-splitting logic in `gossip/src/cluster_info.rs`. A single crafted `CrdsValue::SnapshotHashes` with far more than 25 incremental entries can pass `sanitize()` and be decoded via the `sol_compat_gossip_decode_v1` harness in `gossip/src/harness.rs`.

### Finding Description
The `SnapshotHashes` struct is defined at [1](#0-0)  with an unbounded `incremental: Vec<(Slot, Hash)>` field. Its `Sanitize` implementation at [2](#0-1)  checks `wallclock`, `full.0 < MAX_SLOT`, and per-incremental-entry slot ordering/bounds, but performs no length check on `self.incremental`. `CrdsData::sanitize` simply delegates to `val.sanitize()` for the `SnapshotHashes` variant with no additional bound [3](#0-2) . The `MAX_INCREMENTAL_SNAPSHOT_HASHES` constant exists only in `gossip/src/cluster_info.rs`, referenced in the outbound packet-splitting path (i.e., logic that limits how many incremental hashes the local node *sends*), not in the deserialization/sanitize path that governs what is *accepted*. The `sol_compat_gossip_decode_v1` harness in `gossip/src/harness.rs` calls `gossip_decode_to_effects` directly on attacker-supplied bytes, which internally deserializes the `Protocol` and calls `sanitize()` on `CrdsValue`s before converting them into effects — since `sanitize()` never bounds `incremental.len()`, an attacker-controlled buffer with an oversized `incremental` vector will pass sanitization.

### Impact Explanation
This allows a single crafted message to carry an `incremental` vector far larger than the documented/expected cap of 25 entries (only bounded by the wire format's own length-prefix and overall `PACKET_DATA_SIZE`/buffer size), causing over-allocation and unbounded iteration in any code (such as `convert_crds_data`) that maps over `incremental` without re-checking the cap. This is a decoder-invariant violation and a potential unbounded-cost/panic issue in the conformance decode path rather than a full remote-crash primitive in the live cluster network path, since gossip's real network path is bounded by `PACKET_DATA_SIZE` (1232 bytes), which would limit the practical number of `(Slot, Hash)` tuples (40 bytes each) to roughly 25-30 regardless. The primary exploitable surface here is the harness/decoder itself, where input is not constrained to `PACKET_DATA_SIZE`.

### Likelihood Explanation
Feasible and repeatable: a single crafted binary blob fed once into `sol_compat_gossip_decode_v1` (or any equivalent deserialize+sanitize call path) is sufficient — no cluster interaction, staking, or repeated calls are required. The lack of a length check is a straightforward code-level gap, not a timing- or state-dependent condition.

### Recommendation
Add an explicit length check in `SnapshotHashes::sanitize` (e.g., `if self.incremental.len() > MAX_INCREMENTAL_SNAPSHOT_HASHES { return Err(SanitizeError::ValueOutOfBounds); }`), mirroring the sender-side cap in `cluster_info.rs`, so the invariant is enforced uniformly on both the write and read paths.

fn test_snapshot_hashes_incremental_cap_enforced() {

    let keypair = Keypair::new();
    let full = (1u64, Hash::new_unique());
    let incremental: Vec<(u64, Hash)> = (0..100)

        full,

        wallclock: timestamp(),

    let value = CrdsValue::new(CrdsData::SnapshotHashes(snapshot_hashes), &keypair);

    // Expect sanitize() to reject values exceeding MAX_INCREMENTAL_SNAPSHOT_HASHES (25).
    assert_eq!(value.sanitize(), Err(SanitizeError::ValueOutOfBounds));
}

impl Sanitize for SnapshotHashes {
    fn sanitize(&self) -> Result<(), SanitizeError> {
        sanitize_wallclock(self.wallclock)?;
        if self.full.0 >= MAX_SLOT {
            return Err(SanitizeError::ValueOutOfBounds);
        }
        for (slot, _) in &self.incremental {
            if *slot >= MAX_SLOT {
                return Err(SanitizeError::ValueOutOfBounds);
            }
            if self.full.0 >= *slot {
                return Err(SanitizeError::InvalidValue);
            }
        }
        self.from.sanitize()
    }
}
