The chainlink analog is a genuine excessive-privilege issue in the `AuthenticateExternalInitiator` middleware, which grants a broad `Run` role to any successfully-authenticated External Initiator rather than scoping its privileges to job-run-triggering only.

### Title
External Initiator authentication grants a full `Run` role rather than a scoped webhook-trigger permission - (File: core/web/auth/auth.go)

### Summary
An `ExternalInitiator` is an unprivileged, remote actor whose only intended capability is to trigger a specific webhook job run via `POST /v2/jobs/:ID/runs`. However, `AuthenticateExternalInitiator` authenticates the initiator and then assigns it the generic `sessions.UserRoleRun` on the gin context, the same role used for any human "Run"-level API user. Because RBAC checks elsewhere in the router only check for the coarse `Run` role (via `auth.RequiresRunRole`) rather than checking "is this specifically an External Initiator, restricted to job-run creation," the initiator inherits every other capability granted to the `Run` role across the API, not just the ability to post a run to its own job.

### Finding Description
`AuthenticateExternalInitiator` verifies the access-key/secret pair against the `external_initiators` table and, on success, sets the authenticated principal for the request: [1](#0-0) 

This is functionally identical in structure to the `MANAGER` over-privilege bug class in the report: a narrowly-scoped credential (external initiator, meant only to "swap"/"trigger" a specific action) is mapped to a broad role (`Run`) that unlocks unrelated capabilities across the system, instead of being confined to the single intended operation (create webhook job run).

The `Run` role is checked generically via `auth.RequiresRunRole`, which only inspects `user.Role`, with no distinction between a real "Run" human/API-token user and an ephemeral External Initiator principal: [2](#0-1) 

Per the project's own RBAC route table, more than a `Run`-role check is used to gate routes; several mutating endpoints are explicitly enabled for the `Run` role (`editMinimalAllowed: true`), for example: [3](#0-2) 

Any of these `editMinimalAllowed=true` routes registered with `auth.RequiresRunRole` in `core/web/router.go` would therefore also be reachable by an External Initiator's access-key/secret pair, even though External Initiators are documented to exist only to "initiate runs remotely": [4](#0-3) 

### Impact Explanation
If the intent of the External Initiator credential is strictly to POST job runs for a specific webhook job (as the comment in `auth.go` states — "External initiator endpoints ... inherently assume the role of 'run' (required to trigger job runs)"), then any endpoint gated only by `RequiresRunRole` but not intended for initiators (e.g. `POST /v2/replay_from_block/:evmChainID`) becomes reachable using leaked or compromised initiator credentials, which are lower-trust, externally-distributed secrets used specifically for automation/webhook triggers. This expands the blast radius of a compromised or malicious external-initiator secret beyond "trigger a specific job" to "perform any Run-role-permitted mutating action on the node," which can affect chain replay/reprocessing behavior.

### Likelihood Explanation
Exploitation requires possession of a valid External Initiator `AccessKey`/`Secret` pair, which is a lower-privilege, admin-issued credential intended to be distributed to third parties/automation systems by design — this is exactly the kind of "restricted, less-trusted actor" scenario the original report addresses. Because External Initiator credentials are meant to be handed to external, semi-trusted systems, the likelihood of credential exposure/compromise is materially higher than for a full admin session.

### Recommendation
Do not conflate the External Initiator authentication path with the generic `UserRoleRun`. Introduce a distinct, explicitly scoped role/permission for External Initiators, and enforce that only the intended `POST /v2/jobs/:ID/runs` endpoint accepts it. All other `Run`-gated mutating routes should require an actual authenticated `Run`/`Edit`/`Admin` user, not the synthetic user created in `AuthenticateExternalInitiator`.

### Proof of Concept
Not independently verified end-to-end due to remaining uncertainty over the exact route registration lines for `POST /v2/replay_from_block/:evmChainID` in `core/web/router.go` (I was unable to fetch that specific registration line before running out of tool calls, so I cannot confirm with 100% certainty which auth middleware chain wires this route). Conceptually: an attacker holding a compromised External Initiator `AccessKey`/`Secret` sends `POST /v2/replay_from_block/:evmChainID` with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers set to the initiator's credentials; if that route is registered behind `auth.RequiresRunRole` (as the RBAC test table implies for `editMinimalAllowed: true` routes), the request succeeds despite the caller only being an External Initiator, not a genuine `Run`-role user. func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
