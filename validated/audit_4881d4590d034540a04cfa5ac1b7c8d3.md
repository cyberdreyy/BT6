### Title
Stale rejection weight is never cleared when a signer flips its vote to Accepted, letting stale aggregated-reject-weight kill an otherwise-approvable block (analog of "no equality enforced between recorded state and actual current vote") - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The mining-node's `StackerDBListener` tallies `total_weight_approved` and `total_weight_rejected` for a proposed block by inspecting two different guard sets depending on the message type: the accept path gates on `block.gathered_signatures.contains_key(&slot_id)`, while the reject path gates on `block.responded_signers.insert(slot_id)`. Because these two guards are not the same set, a signer that first rejects and later legitimately flips to accept the same block gets its weight added to `total_weight_approved` *without* the earlier contribution to `total_weight_rejected` ever being removed. The aggregated reject weight can therefore remain stale/inflated relative to the signer's actual current vote.

### Finding Description
In `handle_block_response`-equivalent logic in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`:

- Accept path (`SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))`):
```rust
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
``` [1](#0-0) 

- Reject path (`SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))`):
```rust
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
``` [2](#0-1) 

Sequence that breaks the equality "current recorded weight reflects the signer's current vote":
1. Signer S rejects block B first: `responded_signers.insert(slot_id)` returns `true` (first time), so `total_weight_rejected += S.weight`. `S` is now in `responded_signers` but **not** in `gathered_signatures`.
2. The signer-side state machine legitimately allows a rejected block to later be re-evaluated and locally accepted (`LocallyRejected --> LocallyAccepted : re-evaluated`, driven by `should_reevaluate_reject_reason` / `should_reevaluate_block` in `stacks-signer/src/v0/signer.rs`), and S broadcasts a fresh `BlockResponse::Accepted` for the same `signer_signature_hash`.
3. On the coordinator side, the accept-path guard checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` (S never signed before), so `total_weight_approved += S.weight` is applied.
4. Nothing in the accept path decrements `total_weight_rejected` or removes S's prior contribution there.

Result: `total_weight_approved` and `total_weight_rejected` both simultaneously contain S's weight, i.e. the aggregated reject tally no longer equals the set of signers whose *current* vote is "reject." The reverse direction (accept-then-reject) is correctly guarded, because the reject path's `responded_signers.insert` returns `false` once S is already present — but the accept path was never made symmetric with this guard.

This is directly analogous to the TurboRouter class of bug: an implicit invariant ("a response updates one, and only the correct, aggregate; the other must be consistent") is assumed by the reject-side code but never actually enforced end-to-end on the accept side, because a different, non-equivalent guard (`gathered_signatures` vs `responded_signers`) is used.

### Impact Explanation
The consumer of these tallies, `stacks-node/src/nakamoto_node/signer_coordinator.rs`, evaluates the reject weight *before* the approve weight:
```rust
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ...
    return Err(NakamotoNodeError::SignersRejected { ... });
} else if block_status.total_weight_approved >= self.weight_threshold {
``` [3](#0-2) 

Because `total_weight_rejected` can retain stale weight from signers who have already flipped to Accepted, the node can compute that the blocking-minority threshold (>30% weight) has been reached from stale data and abort the proposal (`SignersRejected`) even though those same signers currently support the block and the honest approving weight may in fact be sufficient. This is a liveness wedge: a block that the signer set would ultimately approve can be prematurely killed by the miner due to an aggregate-weight bookkeeping bug, not because a real supermajority rejected it. It requires only a single signer (plus normal gossip of its own two responses) to trigger — no majority collusion, no other signer's key, and no auth/local access is needed — matching the required threat model.

### Likelihood Explanation
The precondition — a signer initially rejecting a block and later re-evaluating to accept it — is an explicitly supported, documented path in the signer state machine (`LocallyRejected --> LocallyAccepted : re-evaluated`, via `should_reevaluate_reject_reason`/`should_reevaluate_block` in `stacks-signer/src/v0/signer.rs`), not an edge case requiring malicious behavior. It can occur naturally, e.g. when a transient rejection (e.g., due to `RejectedInPriorRound`/stale chain-state checks) becomes stale and the signer re-validates and accepts on a later pass. Any legitimately operating signer that flips its vote in this direction will trigger the stale-weight bug on the coordinator, making this readily reachable in normal operation, especially under contention/forks where re-evaluation is common.

### Recommendation
Use a single, unambiguous per-signer "current vote" record (a `HashMap<slot_id, Vote>` rather than two separate marker sets) so that when a signer's vote changes from Rejected to Accepted (or vice versa), the previous contribution is subtracted from the old aggregate before the new contribution is added to the new aggregate. Concretely, in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, before adding to `total_weight_approved`, check whether `slot_id` is present in a rejection-weight map and, if so, subtract that signer's weight from `total_weight_rejected` (and vice versa on the reject path), instead of gating the two aggregates on two different, non-equivalent sets (`gathered_signatures` vs `responded_signers`).

### Proof of Concept
1. Miner proposes block B; `StackerDBListener` tracks `BlockStatus` for B with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer S (weight w) sends `BlockResponse::Rejected` for B. Coordinator code path: `responded_signers.insert(slot_id)` → `true` → `total_weight_rejected += w`. [2](#0-1) 
3. S's local state (per docs `LocallyRejected --> LocallyAccepted : re-evaluated`) re-evaluates B and moves to `LocallyAccepted`, and S broadcasts `BlockResponse::Accepted` for the same `signer_signature_hash`.
4. Coordinator processes the Accepted message: `gathered_signatures.contains_key(&slot_id)` is `false` (never signed before) → `total_weight_approved += w`. [1](#0-0) 
5. Now `total_weight_rejected` still includes `w` from step 2 and `total_weight_approved` also includes `w` from step 4 — S's weight is double-booked across both aggregates, and `total_weight_rejected` no longer equals the sum of weights of signers whose *current* vote is reject.
6. If enough such flips accumulate stale reject weight past `self.total_weight - self.weight_threshold`, `signer_coordinator.rs`'s check at lines 509–520 fires `SignersRejected` and the miner abandons block B even though the actual current signer votes may support it.
