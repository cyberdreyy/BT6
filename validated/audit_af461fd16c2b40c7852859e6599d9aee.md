## Vulnerability Analog Found

### Title
Stale confirmations from removed multisig members still count toward the K-of-N threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges the requests that the removed member itself created; it never scans `confirmations` for entries the removed member may have added to *other* members' pending requests. Because `confirm()` simply compares the size of the `confirmations` `HashSet<String>` against `num_confirmations`, a stale confirmation from a member who has since been removed still counts toward the threshold, letting a request execute without the required number of *currently live* signers approving it.

### Finding Description
`confirm()` tallies approvals purely by set cardinality of `self.confirmations.get(&request_id)`: [1](#0-0) 

`delete_member()` is supposed to clean up multisig state when a member is removed, but it filters requests by `r.member == member` — i.e. only requests *authored* by the removed member — and only clears confirmations tied to those requests: [2](#0-1) 

`confirmations` is a separate `LookupMap<RequestId, HashSet<String>>` keyed by `member.to_string()`, independent from who created the request: [3](#0-2) 

Consequently, if member `A` confirms a request originally created by member `B` (not `A`), and `A` is later removed via `DeleteMember`, that confirmation entry survives in `confirmations` for `B`'s request (since the filter only matches `r.member == A`, not `B`'s request). The equality that should hold — *confirmations counted == approvals from currently live members* — is broken: the set can contain a signature from an account/key that is no longer in `self.members`.

### Impact Explanation
This directly undermines the K-of-N custody guarantee that the multisig contract exists to provide. A request (e.g. a `Transfer` of the contract's NEAR balance, an `AddKey`/`AddMember` granting new access, or a `DeployContract` upgrade) can reach `num_confirmations` and execute even though one of the counted approvals came from a member who was removed — possibly *because* they were compromised or malicious. This is a Critical-impact class: NEAR could be moved, or a malicious key/member added, "below threshold" of live signers, i.e. a multisig request executed below the effective threshold of currently trusted signers.

### Likelihood Explanation
No privileged foundation action or redeploy is needed beyond ordinary multisig operation: any legitimate governance flow of adding a request, having a subset of members confirm it, and later removing one of those confirming members (a normal security response to key rotation/compromise) leaves the stale confirmation in place. The bug is triggered by routine `DeleteMember` usage, not an edge case requiring social engineering.

### Recommendation
When removing a member in `delete_member`, iterate `self.confirmations` for *all* pending `request_ids` (not just requests the member authored) and strip the removed member's entry from each `HashSet`. Alternatively, revalidate at `confirm()`/execution time that every entry in `confirmations` still corresponds to a member currently present in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C]` and `num_confirmations = 2`.
2. `B` calls `add_request` creating a `Transfer` request `R` to an attacker-controlled account (`add_request` at [4](#0-3)  records `member: B`).
3. `A` calls `confirm(R)` — since `2 < num_confirmations(2)`? adjust: with 1 confirmation and threshold 2, it just records `A`'s confirmation via `confirmations.insert(member.to_string())` ( [5](#0-4) ).
4. Members detect `A`'s key is compromised and submit/execute a `DeleteMember { member: A }` request. `delete_member` runs, but since `R.member == B` (not `A`), `R`'s confirmations (including `A`'s stale entry) are **not** cleared ( [6](#0-5) ).
5. `B` (or the attacker who compromised `B`) calls `confirm(R)`. `confirmations.len()` is still 1 (from `A`) plus `B`'s new confirmation reaches 2, meeting `num_confirmations`, and the transfer executes — despite only `B`, a single *current* member, actually approving it live, with the second "vote" coming from a member already revoked.

        let confirmations = HashSet::new();
        self.confirmations

        self.request_nonce += 1;
        self.request_nonce - 1
    }

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
