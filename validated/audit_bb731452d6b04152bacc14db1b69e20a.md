### Title
Tenure-duplicate guard (`DuplicateBlockFound`) is proposal-only and re-derived by height, not by tenure, letting a signer sign a second tenure-start block for a tenure it already signed — ([File: stacks-signer/src/chainstate/v1.rs], [File: stacks-signer/src/chainstate/v2.rs], [File: stacks-signer/src/signerdb.rs])

### Summary
The Apollo advisory's root cause is that an access-control equality (fields reached via `@requires`/`@fromContext` must carry the same guard as the fields they depend on) was enforced only at one code path (explicit query) and silently skipped on another (transitive fetch). The stacks-signer chainstate code has a structurally identical pattern: `validate_tenure_change_payload`'s `DuplicateBlockFound` check — the guard that stops a signer from signing two different tenure-start blocks for the same tenure — is executed only in `check_proposal` (the "explicit" proposal-arrival path) and is documented as never re-run at validate-ok or at pre-commit-threshold signing time. Those later paths instead rely on a *different*, height-keyed predicate (`get_signed_conflicts`) as a "backstop," but that backstop is not equivalent to the original tenure-based equality it is supposed to stand in for.

### Finding Description
`validate_tenure_change_payload` in both `stacks-signer/src/chainstate/v1.rs` [1](#0-0)  and `stacks-signer/src/chainstate/v2.rs` [2](#0-1)  rejects a tenure-change block proposal with `RejectReason::DuplicateBlockFound` if the signer has already signed a block in that tenure. This is the "guard field" — analogous to the access-control directive that must be enforced.

This guard runs only inside `check_proposal`, i.e. only when a block is first proposed (docs confirm: "the `DuplicateBlockFound` check... lives in `check_proposal` and runs only at proposal arrival, never again") [3](#0-2) . It is not re-invoked in `check_block_against_signer_db_state`, which is the function actually re-run at validate-ok time and again right before a signature is cast at the pre-commit threshold [4](#0-3) , [5](#0-4) .

The only thing standing between a stale `DuplicateBlockFound` decision at proposal time and an actual double-signed tenure at pre-commit/signing time is the *height-based* `get_signed_conflicts` query, called from `handle_block_pre_commit` [6](#0-5) , [7](#0-6) . This query is not a tenure-membership check — it looks only for any other block *at or above the same Stacks chain height*. A tenure-change (tenure-start) block for tenure X can be proposed and reach a *different* chain height than a previously-signed non-tenure-change block already signed within tenure X (heights only strictly increase within a tenure, and a tenure-start proposal's height is fixed by its own chain length, not necessarily colliding with the already-signed block's height in the way `get_signed_conflicts`'s `>= height` filter guarantees a match). The engineering notes in the codebase itself acknowledge this reliance and flag it explicitly rather than proving it airtight ("a block that crosses the pre-commit threshold long after it was proposed relies on section 5's own-tenure conflict guard to cover the same ground") [8](#0-7) .

Additionally, the v1 and v2 implementations of this "duplicate" guard are inconsistent in which state they check: v1 uses `get_last_globally_accepted_block` (misses a block this signer has only *locally* accepted/signed) [9](#0-8) , while v2 uses `get_last_signed_block` (locally or globally accepted) [10](#0-9) . Under v1, if the signer has locally (but not yet globally) accepted a block in tenure X, a second, competing tenure-start block for the same tenure X will *pass* `validate_tenure_change_payload`'s duplicate check at proposal time — the exact same asymmetry-between-checkpoints pattern as the Apollo bug (guard present at the "canonical" checkpoint, silently absent when data is reached a different way).

### Impact Explanation
If this proposal-time-only, height-keyed backstop can be bypassed (e.g., a re-proposed/competing tenure-start block for a tenure the signer already signed, at a height that does not trip `get_signed_conflicts`'s `stacks_height >= ?1` filter, or via the v1 globally-vs-locally-accepted asymmetry), a single miner (one slot) crafting a re-proposal could get the signer to sign two conflicting tenure-start blocks for the same tenure — i.e., a signer signing a conflicting/non-canonical block, which is explicitly called out as a Critical-class outcome in the rules (rejection/acceptance equality break / conflicting-block signature).

### Likelihood Explanation
This requires no majority collusion, no other signer's key, and no auth_token — only a miner crafting a second tenure-change proposal for a tenure already signed, at a specific point in the pre-commit lifecycle (after proposal-time rejection window, before the pre-commit-threshold recheck would otherwise catch it via height). The docs' own admission that the duplicate check "never runs again" and that the height-based conflict guard is relied on to "cover the same ground" indicates the developers were aware this substitution is not proven equivalent — this raises plausibility but I could not fully trace all height-arithmetic edge cases (e.g., whether a tenure-start block's `chain_length` is guaranteed to be `>=` a previously-signed same-tenure block's height in every code path) to conclusively prove a concrete height value where the substitution fails, given the available context.

### Recommendation
Re-run (or make equivalent to) the tenure-scoped `DuplicateBlockFound`/`has_signed_block_in_tenure` check at every point where a signature could be produced (validate-ok recheck and pre-commit-threshold recheck in `check_block_against_signer_db_state`), rather than relying solely on a height-keyed cross-tenure query as a substitute. Unify the v1/v2 predicate to use the same signed-block definition (`get_last_signed_block`, i.e., locally-or-globally accepted) consistently, so the guard cannot be bypassed by differing acceptance state across versions.

### Proof of Concept
Not fully constructible from the indexed context alone: reproducing this requires stepping through the exact height values a tenure-start proposal takes versus the already-signed block's height in a running signer/network harness (e.g., `stacks-signer/src/tests` or a Nakamoto integration test) to demonstrate `get_signed_conflicts` failing to return a match while `validate_tenure_change_payload`'s tenure-scoped check is skipped on the second pass. A background Devin session with repo access and test execution would be needed to build and run such a harness to confirm exploitability.

        if let Some(tenure_change) = proposed_block.get_tenure_change_tx_payload() {

    pub fn get_signed_conflicts(
        &self,
        height: u64,
        excluded_signer_signature_hash: &Sha512Trunc256Sum,
    ) -> Result<Vec<SignedConflictInfo>, DBError> {
        let query = "SELECT b.consensus_hash, b.signer_signature_hash, b.stacks_height, b.state,
                MAX(COALESCE(b.signed_self, 0), COALESCE(b.signed_group, 0)) AS last_endorsed,
                st.superseded_by_consensus_hash, st.superseded_by_burn_block_hash
            FROM blocks b
            LEFT JOIN superseded_tenures st ON st.consensus_hash = b.consensus_hash
            WHERE (b.signed_self IS NOT NULL OR b.signed_group IS NOT NULL)
                AND b.stacks_height >= ?1
                AND b.signer_signature_hash != ?2
            ORDER BY b.stacks_height DESC";
        let args = params![
            u64_to_sql(height)?,
            excluded_signer_signature_hash.to_string(),
        ];
        query_rows(&self.db, query, args)
    }
