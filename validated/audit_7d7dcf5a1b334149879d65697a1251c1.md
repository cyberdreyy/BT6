### Title
`setEpochParams` changes `epochDuration`/`bufferPeriod` without rescaling the stored strategy APR or repricing in-flight interest commitments, letting a mid-epoch depositor over-mint tranche shares - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
Analogous to `setReservedUntilTokenId` updating the reserve boundary without recomputing founder allocations, `IdleCDOEpochVariant.setEpochParams` mutates `epochDuration`/`bufferPeriod` without recomputing the scaled APR already stored in `IdleCreditVault` (`lastApr`) and without repricing interest derived from the old duration. All downstream pricing — `_calcInterest`, `_calcInterestWithdrawRequest`, and the discounted mint in `depositDuringEpoch` — combines the stale scaled `lastApr` with the new duration/buffer, producing a mispriced exchange rate that an unprivileged KYC-passed lender can capture.

### Finding Description
`setEpochParams` is callable by owner or manager whenever the epoch is not running and the pool is not closed/defaulted [1](#0-0) . The scaled APR lives in the strategy and is only written by `_setScaledApr`, which is invoked at init and inside `stopEpoch`/`stopEpochWithDuration` [2](#0-1) . The code itself acknowledges the hazard: "bufferPeriod should not be changed once set otherwise interest calculations will be wrong" [3](#0-2) .

After a legitimate `setEpochParams` call, `_calcInterest` prices interest with `epochDuration` (new) times the strategy `lastApr` (scaled for the old duration/buffer) [4](#0-3) . In `depositDuringEpoch`, the prorated interest credited to the depositor is computed as `_calcInterest(_amount) * (remaining + buffer) / (epochDuration + buffer)` with the new buffer/duration but the stale APR, and this inflated `trancheInterest` directly increases the minted share count via `(amount + trancheInterest) * _trancheTotSupply / expectedFinal` [5](#0-4) . The borrower, however, only owes interest accrued at the stale scaled rate, so the over-minted shares are paid by diluting existing tranche NAV — the same "earmarked entitlement re-priced under a new boundary" shape as the Nouns founder-token theft.

### Impact Explanation
An attacker mints more tranche shares than their principal-plus-fair-interest entitlement; the excess is drawn from the NAV of honest AA/BB holders when the epoch settles, a direct theft of yield/NAV proportional to the APR-vs-duration mismatch. In the opposite direction (or for withdrawers), `_calcInterestWithdrawRequest` scales `totInterest` by `_duration / (_duration + _buffer)` under the new parameters while receipts remain fixed, so honest withdrawers' promised interest is under-funded relative to what the strategy accrues — permanent loss of expected payout, matching the report's "founder loses vesting tokens" impact [6](#0-5) .

### Likelihood Explanation
Requires `isDepositDuringEpochDisabled == false` (a supported non-default mode, guarded at [7](#0-6) ), a KYC-passed wallet, and an honest owner/manager calling `setEpochParams` between epochs — a routine governance action. No existing guard prevents it: `setEpochParams` only checks `defaulted || isEpochRunning || duration==0`, `_skimDonatedAssets` is irrelevant, and there is no recompute of `lastApr` or pending interest counters. The attacker only sequences a `depositDuringEpoch` (or `requestWithdraw`) around the setter call.

### Recommendation
Either forbid changing `epochDuration`/`bufferPeriod` while `expectedEpochInterest`, `pendingWithdrawFees`, or `interestForOverUnderPerformance` are non-zero, or inside `setEpochParams` immediately call `_setScaledApr(unscaledApr)` so `IdleCreditVault.lastApr` is rescaled under the new duration+buffer before any user-facing pricing function can run; additionally document/enforce the "do not change bufferPeriod" invariant as a revert rather than a comment.

### Proof of Concept
Foundry fork sketch:

```solidity
// Mode: fixed-APR, depositDuringEpoch enabled, epoch NOT running (buffer phase)
// 1. Owner/manager: cdo.setEpochParams(30 days, 60 days); // bufferPeriod 5d -> 60d
//    strategy.lastApr remains scaled as unscaled * 35/30
// 2. Epoch starts (owner): cdo.startEpoch();
//    expectedEpochInterest = _calcInterest(NAV) uses stale lastApr
// 3. Attacker (KYC'd): cdo.depositDuringEpoch(A, AATranche);
//    interest = _calcInterest(A) * (remaining + 60d) / (30d + 60d)  // new buffer
//    minted   = (A + trancheInterest) * supply / expectedFinal      // over-minted
// 4. Borrower repays only old-scaled-apr interest at stopEpoch;
//    attacker redeems/claims more underlying than fair share.
// assertGt(attackerUnderlyingOut, attackerPrincipal + fairInterest);
```

Key assertions: `strategy.lastApr` unchanged after `setEpochParams`; `tranche.balanceOf(attacker)` exceeds the mint amount that the same deposit would receive pre-change; post-`stopEpoch` NAV shows the excess drawn from other LPs.

  function setEpochParams(uint256 _epochDuration, uint256 _bufferPeriod) public {
    _checkOnlyOwnerOrManager();
    // cannot set epoch params if epoch is running
    // cannot set epochDuration to 0 as it's reserved for closing the pool
    // and cannot set epochDuration if previously was set to 0 as borrower repaid all funds
    _checkNotAllowed(defaulted || isEpochRunning || _epochDuration == 0 || epochDuration == 0);
    epochDuration = _epochDuration;
    bufferPeriod = _bufferPeriod;
  }

      );
    }
    // interest this deposit will earn for the tranche over the remaining time (net of fees)
    uint256 trancheInterest = _calcTrancheInterestShare(
      _netGainAfterFees(interest, _calculateManagementFee(_amount, remaining)),
      _tranche
    );
    // pre-deposit expected final NAV for existing holders.
    // This won't ever be zero as we checked _trancheTotSupply and we seed initial NAV at tranche creation
    uint256 expectedFinal = _lastSavedNAV(_tranche) + trancheExpected;
