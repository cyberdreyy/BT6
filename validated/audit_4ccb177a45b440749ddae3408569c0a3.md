Confirmed - both `multisig/src/lib.rs` and `multisig2/src/lib.rs` have the same structural gap: the confirmation-cleanup logic on member/key removal only purges requests that the removed key/member itself *authored*, never requests it merely *confirmed*. This is directly analogous to the ERC-6492 `ownerIndex` bug's core weakness — stale identity-bound approvals surviving a membership change and still counting toward an authorization threshold.

### Title
Stale confirmations from removed multisig members/keys still count toward execution threshold - (File: multisig2/src/lib.rs, multisig/src/lib.rs)

### Summary
In both `multisig/src/lib.rs` and `multisig2/src/lib.rs`, when a signer (key or member) is removed via `DeleteKey`/`DeleteMember`, the contract only deletes the *requests that the removed signer created*, not the *confirmations that signer previously cast on other, still-pending requests*. Because `confirm()` never re-validates that entries in the stored confirmation set still belong to current, live members, a pending request can reach the `num_confirmations` threshold using confirmations from members who have since been removed from the multisig.

### Finding Description
`MultiSigContract::confirm` in `multisig2/src/lib.rs` executes a request once the confirmation count crosses the threshold, purely by counting entries already stored in `self.confirmations`: [1](#0-0) 

That count is never checked against current membership; it simply trusts whatever public keys/account ids were recorded historically. The only cleanup of stale confirmations happens in `delete_member`, and it is scoped to requests where `r.member == member` (i.e. requests *authored* by the removed member), not requests they merely confirmed: [2](#0-1) 

The exact same gap exists in the legacy `multisig/src/lib.rs` contract's `DeleteKey` handling, which filters only on `r.signer_pk == pk` (the request author), leaving confirmations by that key on other requests untouched: [3](#0-2) [4](#0-3) 

The custody binding that should hold is: `count(confirmations from currently live members on request R) >= num_confirmations` before `R` executes. What is actually enforced is: `count(confirmations ever recorded on R, including from members removed afterward) >= num_confirmations`. This mirrors the ERC-6492 report's root cause — an identity-bound authorization artifact (`ownerIndex` there, a member's confirmation entry here) that is not re-validated against the live/current authorization state at the moment it is relied upon.

### Impact Explanation
This breaks the K-of-N authorization threshold that the multisig's entire security model depends on. Concretely:
1. Members A, B, C, D exist with `num_confirmations = 3`.
2. Member D adds a request `R` (e.g. `Transfer` of funds, or `AddKey`/`AddMember` granting an attacker access) and confirms it. B also confirms it. Confirmations = {D, B} (2 of 3 needed).
3. Before the third confirmation is cast, the group legitimately removes B (e.g. because B's key is believed compromised, or as routine membership rotation) via a `DeleteMember{member: B}` request. `delete_member` only purges requests *authored* by B — `R` is authored by D, so `R`'s confirmation set `{D, B}` is untouched even though B is no longer a member.
4. `R` still shows 2 confirmations. Any single remaining live member (e.g. C) can now call `confirm(R)`, pushing the count to 3, meeting the threshold and executing `R` — even though B is no longer part of the multisig and never re-confirmed after its removal.

The request executed here can be a `Transfer` moving all contract funds, or an `AddKey`/`AddMember` action that installs a new controlling key/member — i.e. funds can move, or control of the account can be seized, with fewer *live, current* approvals than the multisig's own `num_confirmations` guarantee promises. This is a Critical-class break of the multisig's authorization binding: a request executed below the intended live-member threshold.

### Likelihood Explanation
No special privilege beyond ordinary multisig membership is needed to trigger the unsafe path — any member can create/confirm a request and any member removal (a routine, legitimate multisig operation) leaves stale confirmations in place on any other still-pending request. The precondition is simply "a member is removed while they have an outstanding confirmation on some other pending request," which is a normal, expected occurrence in long-lived multisig operation (key rotation, offboarding, compromise response), not an exotic setup.

### Recommendation
When removing a member/key (`delete_member` in `multisig2/src/lib.rs`, the `DeleteKey` action in `multisig/src/lib.rs`), also strip that member's/key's entry from the confirmation sets of *all* pending requests, not just requests they authored — e.g. iterate `self.confirmations` and remove the departing identity's entry from every `HashSet`, decrementing effective progress accordingly. Alternatively, re-validate in `confirm()` that every entry in the stored confirmation set still corresponds to a current member before counting it toward the threshold.

### Proof of Concept
Given `multisig2/src/lib.rs`'s `MultiSigContract::new(members: [A,B,C,D], num_confirmations: 3)`:
1. As `D`: `add_request_and_confirm(Transfer{...})` → confirmations `{D}`.
2. As `B`: `confirm(request_id)` → confirmations `{D,B}` (2/3).
3. Group runs and executes a separate `DeleteMember{member:B}` request (3 legitimate confirmations from A, C, D) — see `delete_member` at [2](#0-1)  which only clears requests where `r.member == B`, leaving the `Transfer` request's `{D,B}` confirmation set intact.
4. As `C` (now one of only 3 live members A, C, D): `confirm(request_id)` → `confirmations.len() + 1 == 3 >= num_confirmations`, per [5](#0-4) , so the `Transfer` executes — funds move having received only 2 confirmations (`D`, `C`) from currently-live members, one confirmation short of the "live member" threshold, with `B`'s stale, post-removal confirmation making up the difference.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
