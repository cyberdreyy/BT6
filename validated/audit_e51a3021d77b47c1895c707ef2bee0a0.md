### Title
Sensitive URL parameter masking bypass for the longest token key ("x-amz-security-token") when a chunk boundary falls exactly after the key, before "=" - ([File: common/buildlogger/internal/urlsanitizer/urlsanitizer.go])

### Summary
`URLSanitizer.Write` accumulates a candidate parameter key in `s.match`, byte-by-byte, until it finds `=`, `?`, or `&`. The guard `if len(s.match) == cap(s.match) { s.match = s.match[:0] }` at line 82 unconditionally discards the accumulated match at the start of processing, without checking whether the next byte is the `=` that would complete a valid token key. Because `cap(s.match)` is sized to exactly fit the longest known key (`x-amz-security-token`, 21 chars + 1 delimiter = 22), a `Write()` call boundary that lands exactly after the 21st character of that specific key — with `=` as the very first byte of the next `Write()` call — causes the fully-assembled, valid match to be wiped out right before it would be recognized, so the token and its value are emitted unmasked.

### Finding Description
`New()` sizes the match buffer to `len(longestToken)+1` [1](#0-0) . The longest entry in `tokenParamKeys` is `x-amz-security-token` (21 characters), giving `cap(s.match) == 22` [2](#0-1) .

While no `=`/`?`/`&` is found in the current chunk, bytes are appended to `s.match` one at a time and the function returns when the chunk is exhausted, preserving `s.match` in the struct across `Write()` calls [3](#0-2) . If a chunk boundary happens to fall right after the last character of `?x-amz-security-token` (making `len(s.match) == 22 == cap`), the *next* `Write()` call re-enters the loop and immediately hits:
```go
if len(s.match) == cap(s.match) {
    s.match = s.match[:0]
}
``` [4](#0-3) 
This reset happens unconditionally, before the code ever looks at the new chunk's first byte (which is `=`). The match is wiped, `s.masking` is never set, and the fast path then scans for the next `?`/`&` only [5](#0-4) , so `=` and everything following it (the credential value) is written straight through unmasked until the next delimiter or end of input.

Note this defect is specific to `x-amz-security-token`: it is the only key whose `delimiter+key` length equals `cap(s.match)` exactly (22). Shorter keys (e.g. `x-amz-credential`, 17 chars, `1+17=18`) reach their terminating `=` well before `len(s.match)` can reach 22, so they are not affected by this particular boundary condition.

The write chain that feeds `urlsanitizer.Write` is `tokensanitizer -> urlsanitizer -> masker -> internal.NewSync`, driven directly by executor/job output [6](#0-5) . Chunk boundaries into this pipeline are determined by underlying pipe/stream reads from the job's shell process, which a job author can influence (e.g., by controlling how/when a URL string is printed, using partial writes, `printf`, redirection buffering, or timing of output), making the exact split point attacker-influenceable.

### Impact Explanation
An AWS presigned URL security token (`x-amz-security-token`) embedded in job output (e.g., printed by a script) can be leaked verbatim into the job trace/log if a job author (or output timing) causes the `Write()` chunk boundary to land immediately after the key name and before the `=`. This is a leak of sensitive pre-signed URL credentials to anyone who can view the job trace/log, matching the scoped impact.

### Likelihood Explanation
The precondition is narrow: it requires the specific longest key `x-amz-security-token`, and a chunk split occurring at one specific byte offset (immediately after the 21st character of the key, with `=` starting the next chunk). Although this exact split is not something a job author can directly force via CI YAML (chunk boundaries are governed by pipe read sizes in the executor/shell layer, not directly by job script content), a job author who controls what is echoed and its exact byte layout, combined with small/slow writes (e.g. via `printf` byte-by-byte, `dd`, or crafted binary output) or via naturally occurring buffering boundaries, can increase the likelihood of triggering this exact split, especially since output splitting can be forced by writing exactly aligned strings. It is deterministically reproducible in a unit test by feeding the writer in two chunks split at the correct offset.

### Recommendation
Do not reset `s.match` purely based on reaching `cap`; only reset when it's confirmed that no valid key can still complete (i.e., after actually checking for `=`/`?`/`&` in the newly available bytes and failing to find a match, or when a definitively invalid character is encountered). Alternatively, check for `=` as the very first byte of a new `Write()` call before applying the cap-based reset, or increase buffer accounting so the reset only fires once it's certain the accumulated bytes cannot form any valid `tokenParamKeys` entry followed by `=`.

### Proof of Concept
Add a test case to `urlsanitizer_test.go` splitting exactly after the key and before `=`:
```go
{
    input:    "boundary at cap: http://example.com/?x-amz-security-token|=deadbeef",
    expected: "boundary at cap: http://example.com/?x-amz-security-token=[MASKED]",
},
```
Using the existing test harness (which splits `tc.input` on `|` into separate `Write()` calls), run the test and assert that `deadbeef` never appears unmasked in `buf.String()`. This test is expected to fail against the current implementation because the reset at line 82 discards the fully-accumulated `?x-amz-security-token` match right before the `=` byte, producing `"...?x-amz-security-token=deadbeef"` unmasked instead of `"...?x-amz-security-token=[MASKED]"`.

func New(w io.WriteCloser) *URLSanitizer {
	var max int
	for token := range tokenParamKeys {
		if len(token) > max {
			max = len(token) + 1
		}
	}

	return &URLSanitizer{w: w, match: make([]byte, 0, max)}
}
