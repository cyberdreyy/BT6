### Title
Duplicate builder-balance commitment in `get_expected_withdrawals` mints Gwei the builder never staked - (File: `specs/gloas/beacon-chain.md`)

### Summary
`get_builder_withdrawals` and `get_builders_sweep_withdrawals` are both pure, non-mutating helpers called back-to-back inside `get_expected_withdrawals`. Each of them reads `state.builders[builder_index].balance` independently and neither subtracts the amount the other has already queued for the same builder in the *same* withdrawals batch. If a builder simultaneously (a) has an entry in `state.builder_pending_withdrawals` and (b) is sweep-eligible (`builder.withdrawable_epoch <= current_epoch and builder.balance > 0`), the beacon block ends up committing **two** withdrawals for that builder whose amounts both derive from the *same, undiminished* `builder.balance`, so the sum committed to the execution layer exceeds the builder's actual staked balance.

### Finding Description
`get_builder_withdrawals` iterates `state.builder_pending_withdrawals` and emits a `Withdrawal` for each entry using the entry's stored `.amount`, uncapped by the builder's current balance: [1](#0-0) 

`get_builders_sweep_withdrawals`, called immediately afterward in `get_expected_withdrawals` with no intervening state mutation, independently emits a full-balance sweep withdrawal for any builder whose `withdrawable_epoch <= epoch and balance > 0`, using `builder.balance` — the very same pre-mutation balance already referenced above: [2](#0-1) 

Both calls happen inside one pure computation: [3](#0-2) 

Only later, when `apply_withdrawals` actually mutates state, is a `min(withdrawal.amount, builder_balance)` cap applied — sequentially, entry by entry: [4](#0-3) 

This means the **committed** `payload_expected_withdrawals` list (which the execution layer is contractually bound to honor in full, minting ETH to each listed address for the listed amount) can legitimately request `pending_amount + balance` for one builder even though the builder only ever had `balance` Gwei. The CL-side capping in `apply_withdrawals` only protects `state.builders[...].balance` from going negative; it does nothing to reduce what was already promised to the EL in the block.

A builder can reach the (pending-withdrawal, sweep-eligible) state simultaneously because `builder_pending_withdrawals` entries are appended later, out of the builder's control, by `settle_builder_payment` (deferred payment settlement, up to 2 epochs after a bid) or directly on eviction: [5](#0-4) [6](#0-5) 

while exit (which sets `withdrawable_epoch`, making the builder sweep-eligible) only checks that pending balance is zero **at the moment the exit request is processed**: [7](#0-6) 

Because bid payments for slots the builder already won can settle in a later epoch (via `settle_builder_payment`, driven by `process_parent_execution_payload`), a `builder_pending_withdrawals` entry can be created for a builder *after* it has already exited and become sweep-eligible, landing both a pending withdrawal and a sweep withdrawal for the same builder into the same `process_withdrawals` call.

### Impact Explanation
This breaks the Gwei-conservation invariant explicitly called out elsewhere in the same file (the note on `process_withdrawals` acknowledges that any scenario where "the execution layer mints the full committed amount" while the CL deducts less "creates a net supply inflation"). Here the inflation is not merely a documented, mitigated edge case (that note only covers validator withdrawal-vs-consolidation timing) — it is an unaddressed double count between two independent builder-withdrawal generators in `get_expected_withdrawals`. The result is Gwei minted on the execution layer with no corresponding stake ever having existed to back it, credited to the builder's own `fee_recipient`/`execution_address`. This matches the Critical impact category: "Gwei created ... paid to a non-owner" (here, paid beyond what the builder ever staked).

### Likelihood Explanation
This requires no adversarial coalition or client bug — only the builder timing its exit request so that a bid payment it already won settles after (or in the same block as) its sweep becomes eligible. Both events are entirely reachable through the normal builder deposit/bid/exit lifecycle already codified in the spec, so any active builder can trigger it deliberately.

### Recommendation
When computing `get_builders_sweep_withdrawals` (and `get_builder_withdrawals`), account for amounts already queued for the same builder earlier in the same batch (analogous to how `get_balance_after_withdrawals` is used for validator sweep/partial withdrawals in Electra), e.g. compute the sweep amount as `builder.balance - sum(amount for w in prior_withdrawals if w.validator_index == converted_index)` instead of the raw `builder.balance`.

### Proof of Concept
1. Builder `B` has `balance = 40 ETH`, `execution_address = A_sweep`.
2. `B` submits a winning bid for slot `N` worth `10 ETH`, payment deferred via `builder_pending_payments`.
3. `B` submits (and it processes) a `BuilderExitRequest` before the bid settles, while `get_pending_balance_to_withdraw_for_builder(B) == 0` at that moment — exit succeeds, `withdrawable_epoch = current_epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY`.
4. Two epochs later, `settle_builder_payment` for slot `N`'s payment fires (via `process_parent_execution_payload`), appending `BuilderPendingWithdrawal(fee_recipient=A_fee, amount=10 ETH, builder_index=B)` to `state.builder_pending_withdrawals`. At the same slot, `B.withdrawable_epoch <= current_epoch` and `B.balance == 40 ETH > 0`, so `B` is also sweep-eligible.
5. In the next `process_withdrawals` call: `get_builder_withdrawals` emits `Withdrawal(address=A_fee, amount=10 ETH)`; `get_builders_sweep_withdrawals` emits `Withdrawal(address=A_sweep, amount=40 ETH)` (both read the same pre-mutation `balance=40 ETH`).
6. Committed `payload_expected_withdrawals` totals `50 ETH` for a builder that only ever staked `40 ETH`. The execution layer mints `50 ETH` to `A_fee`/`A_sweep`; `apply_withdrawals` on the CL only ever had `40 ETH` to deduct (ending at `0`, correctly, via the `min()` cap) — the extra `10 ETH` is minted on L1 with no CL-side stake ever backing it.

def get_builders_sweep_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    epoch = get_current_epoch(state)
    builders_limit = min(len(state.builders), MAX_BUILDERS_PER_WITHDRAWALS_SWEEP)
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    builder_index = state.next_withdrawal_builder_index
    for _ in range(builders_limit):
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder = state.builders[builder_index]
        if builder.withdrawable_epoch <= epoch and builder.balance > 0:
            withdrawals.append(
                Withdrawal(
                    index=withdrawal_index,
                    validator_index=convert_builder_index_to_validator_index(builder_index),
                    address=builder.execution_address,
                    amount=builder.balance,
                )
            )
            withdrawal_index += 1

        builder_index = (builder_index + 1) % len(state.builders)
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

def process_builder_exit_request(state: BeaconState, request: BuilderExitRequest) -> None:
    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        return

    builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
    builder = state.builders[builder_index]

    if not is_active_builder(state, builder_index):
        return
    if builder.execution_address != request.source_address:
        return
    if get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0:
        return

    initiate_builder_exit(state, builder_index)
