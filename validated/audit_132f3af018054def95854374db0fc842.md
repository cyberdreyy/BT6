### Title
Missing job/project binding in `EnvironmentKey` allows cross-job hijack of suspended environments - (File: common/build.go, common/environment_key.go, executors/internal/autoscaler/executor.go)

### Summary
`EnvironmentKey` is composed only of `RunnerID`, `SystemID`, and executor-supplied `Fields` [1](#0-0) ; `RunnerID`/`SystemID` are constant for every job the runner ever processes, so they provide zero job-level isolation. The resume path (`prepareResume`/`validateEnvKey`) only re-checks that the key's `RunnerID`/`SystemID` match the current runner config, never that the resuming job/project actually owns the suspended state, and the full key (including opaque resource identifiers such as container IDs / PVC names) is logged to the job trace at Info level, making it obtainable by any user who can read that job's log.

### Finding Description
`Build.suspendEnvironment` builds the key purely from runner identity plus executor-returned `Fields` and never incorporates `JobInfo.ProjectID`, job ID, or any per-job secret/nonce: [2](#0-1) 

The key is then logged in full to the build's own trace: `b.logger.Infoln("Job environment suspended:", s)` [3](#0-2) , and set on the trace via `trace.SetEnvironmentKey(envKey)` [4](#0-3) , as confirmed by `TestRun_ShouldSuspend_SetsEnvironmentKeyOnTrace` which shows the raw key (`"7/sys-1/namespace=gitlab-runner&pvc=gl-runner-env-abc123"`) being written out [5](#0-4) . Job logs are readable by anyone with pipeline/job read access (including anonymous users on public projects), so the key is not a Runner-side secret — it is Runner-side *public data*.

On resume, `EnvironmentKey()` simply returns `b.Job.SuspendOptions.EnvironmentKey` as-is when the feature flag is on [6](#0-5) , and the autoscaler executor's `Prepare` unconditionally takes the resume branch whenever this string is non-empty: `envKey := options.Build.EnvironmentKey(); if envKey != "" { return e.prepareResume(...) }` [7](#0-6) . `prepareResume` validates the key only against `options.Config.ID` and `options.Config.GetSystemID()` — i.e., "is this the same runner instance" — via `validateEnvKey(envKey, options.Config.ID, options.Config.GetSystemID())` [8](#0-7) , then calls `scaler.Resume(ctx, acqKey)` and `e.Resume(ctx, executorFields)` to reattach to the suspended instance/workspace [9](#0-8) . Nowhere in this path is `JobInfo.ProjectID`, job ID, or any authorization token compared between the suspending job and the resuming job. The docker executor's `resumeDependencies` exhibits the same pattern, parsing container/service IDs straight out of `SuspendOptions.EnvironmentKey` [10](#0-9) .

Because `RunnerID`/`SystemID` are identical for every job dispatched to that runner (shared/group runners serve many projects), and the only "job-specific" component (`Fields`) is public information visible in that job's own log, any subsequent job scheduled on the same runner that can set `SuspendOptions.EnvironmentKey` (directly, per the audit's stated precondition, or indirectly by replaying a previously logged key) can trigger `prepareResume`/`resumeDependencies` and reattach to a *different* job's suspended executor state/workspace. The `executeStage`'s "resuming suspended environment" skip logic for `BuildStageGetSources` then trusts that this resumed executor already has the correct sources/workspace in place and skips re-fetching, compounding the confusion by running subsequent stages against another job's checked-out workspace.

### Impact Explanation
A job belonging to one project can cause the runner to resume and operate on the suspended executor state (container, volumes, PVC, or cloud instance) that belongs to a different job/project sharing the same runner, and then skip `GetSources` under the assumption that the environment is legitimately its own. This breaks the "no job may access another project's workload" invariant and can lead to workspace/data cross-contamination, execution of one project's scripts inside a container/volume provisioned for another project, and potential leakage of files, cache, or credentials left in that suspended environment.

### Likelihood Explanation
Requires: (1) `SuspendableEnvironments` feature flag enabled, (2) a runner shared across multiple jobs/projects, and (3) the attacker being able to set/replay a `SuspendOptions.EnvironmentKey` value obtained from another job's log output (which the code itself prints at Info level) or, per the stated audit precondition, directly control this field. Given that Runner performs no ownership check beyond runner identity, and the key value is deliberately logged in cleartext, the only real barrier is whichever GitLab backend policy decides which job's payload receives which key — a check that lives outside this repository and that Runner does not itself verify or rely on as a second line of defense.

### Recommendation
Bind `EnvironmentKey` cryptographically to the job/project that created it (e.g., HMAC the key with a runner-held secret over `RunnerID`, `SystemID`, `JobInfo.ProjectID`, and job ID, or require a matching job token) so that `validateEnvKey`/`prepareResume`/`resumeDependencies` can reject keys not issued for the current job's project. Additionally, avoid logging the raw `Fields` portion of the key to the user-visible job trace, or redact/mask it, since it currently discloses the exact resume capability.

### Proof of Concept
Go test outline (extending `setupResumeTest` in `executors/internal/autoscaler/executor_test.go`):
1. Suspend "job A" (ProjectID=1) via `suspendEnvironment`, capture the resulting `EnvironmentKey` string exactly as it would appear in job A's trace output.
2. Construct "job B" with a different `JobInfo.ProjectID` (e.g., 2) but the same `Runner.ID`/`SystemID`, and set `build.Job.SuspendOptions.EnvironmentKey` to the string captured from job A.
3. Call `executor.Prepare` for job B and assert `prepareResume`/`resumeDependencies` succeeds and reattaches `acqRef.acq`/`buildContainer` to the same underlying resource that belongs to job A, with no error and no check comparing `JobInfo.ProjectID` between the two builds — proving cross-project reuse is accepted by Runner's own logic.

// EnvironmentKey identifies a suspended environment. The runner produces it
// when suspending a job and parses it when a follow-up job resumes. The
// runner-id and system-id route the resume back to the same runner instance
// that issued the suspension; the fields carry executor-specific state.
//
// Format: <runner-id>/<url-encoded-system-id>/<url-encoded-fields>
type EnvironmentKey struct {
	RunnerID int64
	SystemID string
	Fields   url.Values
}

func (k EnvironmentKey) String() string {
	return fmt.Sprintf("%d/%s/%s", k.RunnerID, url.PathEscape(k.SystemID), k.Fields.Encode())
}
```

func (b *Build) suspendEnvironment(ctx context.Context, executor Executor) (string, error) {
	se, ok := executor.(SuspendableExecutor)
	if !ok {
		b.logger.Warningln("Job environment suspension not supported by executor")
		return "", errors.New("executor does not support suspend/resume")
	}
	fields, err := se.Suspend(ctx)
	if err != nil {
		b.logger.Warningln("Job environment suspension failed:", err.Error())
		return "", fmt.Errorf("suspending environment: %w", err)
	}
	envKey := EnvironmentKey{
		RunnerID: b.Runner.ID,
		SystemID: b.Runner.GetSystemID(),
		Fields:   fields,
	}
	s := envKey.String()
	b.logger.Infoln("Job environment suspended:", s)
	return s, nil
}
```
