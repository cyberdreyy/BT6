### Title
Minted-interest `stopEpoch` double-counts `pendingWithdrawFees` into `unclaimedFees`, minting excess AA fee shares that dilute tranche NAV - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external NTE-1 pattern (one fee bucket incremented from two different denominations and paid out as a single asset) has a direct analog in `IdleCDOEpochVariant._stopEpoch` when `isInterestMinted` is true. `pendingWithdrawFees` is both included in the minted `_grossInterest` that inflates NAV before `_updateAccounting` (so it is hit by the `(nav - lastNAV) * fee` performance-fee accrual) and then added a second time in full via `unclaimedFees += _pendingWithdrawFees`. The result is that fee receivers are minted AA tranche shares worth `pendingWithdrawFees * (1 + fee/FULL_ALLOC)` while tranche holders absorb the extra reduction — a misattributed-fee/dilution bug, not a donation or oracle issue.

### Finding Description
- At `requestWithdraw`, `totalFees` (upfront management fee + net performance fee) is subtracted from the user receipt and added to `pendingWithdrawFees` (`IdleCDOEpochVariant.sol:774-778`). The receipt principal leaves live NAV via `_withdrawOps(_amount, principal)`.
- At `startEpoch`, `expectedEpochInterest = pendingWithdrawFees + adjustedActiveInterest` (`IdleCDOEpochVariant.sol:262`), so `_grossInterest` in `_stopEpoch` already contains `pendingWithdrawFees`.
- In the minted path (`_mintInterest`), the code mints strategy tokens for the full `_grossInterest` — including `pendingWithdrawFees` — and then adds `unclaimedFees += _pendingWithdrawFees` *before* `_updateAccounting` (`IdleCDOEpochVariant.sol:428-433`).
- `_updateAccounting` then computes `gain = nav - lastNAV` over a NAV that includes the minted `pendingWithdrawFees`, and accrues `unclaimedFees += gain * fee / FULL_ALLOC` (`IdleCDOCreditVault.sol:230-232`). The tranche gain split in `_virtualPriceAux` is net of total `unclaimedFees`, so `pendingWithdrawFees` is charged to tranche holders twice: once in full (the explicit add) and once at `fee%` inside the performance-fee accrual.
- The whole `unclaimedFees` balance is then converted into AA shares for `feeReceiver` and `owner()` via `_mintSharesAtCurrPrice` (`IdleCDOEpochVariant.sol:439-447`), and `unclaimedFees` is zeroed at line 459.

Compare the non-minted path: `_pendingWithdrawFees` is transferred to `feeReceiver` *before* `_updateAccounting` and `_availableForFees` is capped at `_grossInterest - _pendingWithdrawFees` (`IdleCDOEpochVariant.sol:418-456`), so the fee portion is excluded from the gain base exactly once. The minted path reintroduces it.

### Impact Explanation
Every epoch that settles in minted-interest mode with pending withdraw requests mints `pendingWithdrawFees * fee / FULL_ALLOC` excess AA tranche tokens to `feeReceiver`/`owner()`. These shares are backed by NAV belonging to AA and BB tranche holders, so tranche prices are diluted and the last redeemers/claimants can be left undercollateralized — the same "backing drained by misattributed fees" outcome as NTE-1. With `fee = 10%` (10000) and, e.g., 100e6 of `pendingWithdrawFees` accrued from large withdraw requests, ~10e6 of unbacked AA shares are minted per such epoch.

### Likelihood Explanation
Requires only minted-interest mode (mandatory for programmable-borrower deployments per `_checkProgrammableBorrowerMode`, `IdleCDOEpochVariant.sol:105-107`) plus ordinary `requestWithdraw` calls — an unprivileged KYC-passed lender creates `pendingWithdrawFees`, and honest manager `stopEpoch` calls crystallize the over-mint. No privileged misbehavior, oracle, or default is needed. The skim guard does not apply (no raw underlying donation is involved) and there is no cap analogous to `_availableForFees` on the minted branch.

### Recommendation
Mirror the non-minted path: exclude `pendingWithdrawFees` from the gain base before the performance-fee accrual — e.g. mint strategy tokens only for `_grossInterest - _pendingWithdrawFees` (or add `pendingWithdrawFees` to `unclaimedFees` *after* `_updateAccounting`/`_virtualPriceAux` has computed the gain, ensuring it is not double-charged), so `pendingWithdrawFees` reaches fee receivers exactly once.

// Foundry fork PoC (setup mirrors test/foundry/IdleCreditVault.t.sol::testStopEpochMintInterestMintsStrategyTokensAndFees)
function testPendingWithdrawFeesDoubleCountedInMintedMode() external {
    uint256 amount = 10_000 * ONE_SCALE;
    _setFeeParams(TL_MULTISIG, 10_000, FULL_ALLOC, cdoEpoch.managementFee()); // 10% perf fee
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // epoch 0 runs and stops normally to set lastEpochApr
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // user requests withdraw -> pendingWithdrawFees > 0
    cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 2, address(AAtranche));
    uint256 pendingFees = cdoEpoch.pendingWithdrawFees();
    assertGt(pendingFees, 0);

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // minted mode: expected path

    uint256 grossInterest = /* expectedEpochInterest at stop */ ;
    uint256 perfFeeOnGross = grossInterest * cdoEpoch.fee() / FULL_ALLOC;

    // Correct fee mint = pendingFees + (grossInterest - pendingFees) * fee%
    // Actual mint    = pendingFees +  grossInterest              * fee%
    uint256 excessShares = pendingFees * cdoEpoch.fee() / FULL_ALLOC; // in underlying terms
    uint256 feeBacked = IERC20(AAtranche).balanceOf(TL_MULTISIG) + IERC20(AAtranche).balanceOf(owner)
        * cdoEpoch.tranchePrice(address(AAtranche)) / ONE_TRANCHE_TOKEN;

    assertGt(feeBacked, pendingFees + (grossInterest - pendingFees) * cdoEpoch.fee() / FULL_ALLOC,
        'pendingWithdrawFees double counted: excess AA fee shares minted');
}
