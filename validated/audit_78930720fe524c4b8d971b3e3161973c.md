### Title
Gateway legacy DON-ID routing forwards attacker-signed messages to any configured DON without verifying signer is an authorized subscriber of that DON - ([File: core/services/gateway/gateway.go])

### Summary
`gateway.ProcessRequest` selects the target handler purely from the attacker-supplied `msg.Body.DonId` field and only requires that `msg.Validate()` succeed, which merely checks structural constraints and ECDSA-recovers a signer address into `msg.Body.Sender` — it never checks that the recovered signer belongs to the targeted DON. The downstream `HandleLegacyUserMessage` in the capabilities handler explicitly defers allowlist enforcement (`// TODO: apply allowlist and rate-limiting here`) and unconditionally fans the message out to every member of that DON.

### Finding Description
In `gateway.ProcessRequest`, for any request whose decoded `msg.Body.DonId` is non-empty, the code takes the legacy path: [1](#0-0) 
It calls `msg.Validate()` and then indexes `g.handlers[handlerKey]` using `handlerKey = msg.Body.DonId` directly, with no cross-check against the recovered signer.

`Message.Validate()` performs only structural checks (lengths, null-byte suffixes) and recovers the signer via `ExtractSigner`, storing it in `m.Body.Sender` — it never validates that this signer is a member/subscriber of `m.Body.DonId`: [2](#0-1) 

The selected handler is then invoked directly: [3](#0-2) 

In the capabilities handler's `HandleLegacyUserMessage` (a common legacy handler implementation used for web API triggers), the code explicitly marks the allowlist check as unimplemented and proceeds to forward the message, signed by any key, to every configured DON member: [4](#0-3) 

Because `g.handlers` is keyed by DON ID and any caller can set `Body.DonId` to any configured value, an attacker who knows a target DON ID (often derivable from job specs, node configuration, or previous requests) can sign a structurally valid message with an unrelated key and have it routed to, and executed against, that DON's handler and node set — with no verification that the signer is a subscriber authorized for that DON.

### Impact Explanation
This allows an unauthenticated/unprivileged actor holding any ECDSA key to submit workflow-trigger (or other legacy-method) requests that are forwarded to a victim DON's nodes, consuming that DON's trigger/callback capacity, exhausting `savedCallbacks`, or invoking trigger workflows the attacker is not authorized to invoke — a request-impersonation / authorization-bypass class issue matching "unauthorized job run" bounty impact, scoped to whatever authorization the specific handler was supposed to enforce (allowlist is explicitly TODO in the capabilities handler).

### Likelihood Explanation
Preconditions are minimal: an unauthenticated HTTP client, any valid ECDSA key pair, and knowledge of a configured `DonId` string (which is frequently public/discoverable via job configs or prior legitimate traffic). The attack requires only signing a well-formed message and POSTing it — fully repeatable and scriptable, no special privileges needed.

### Recommendation
Enforce DON/subscriber authorization at (or before) the routing step in `gateway.ProcessRequest`: after `msg.Validate()` recovers `msg.Body.Sender`, check that the sender is present in the target DON's configured allowlist/member set (or an explicit user-subscriber list) before invoking `HandleLegacyUserMessage`/`HandleJSONRPCUserMessage`. At minimum, implement the allowlist check flagged by the `// TODO: apply allowlist and rate-limiting here` comment in `core/services/gateway/handlers/capabilities/handler.go` before fanning the message out to DON members.

### Proof of Concept
1. In `gateway_test.go`, using `newGatewayWithMockHandler` (or a real `capabilities` handler wired with a `donConfig` containing an allowlist for DON `victimDON`), construct a signed legacy message with `Body.DonId = "victimDON"` but signed by a key not present in `victimDON`'s member/allowlist config.
2. Call `gw.ProcessRequest(ctx, req, "")`.
3. Assert that `HandleLegacyUserMessage` (mock or real handler's `don.SendToNode`) is invoked despite the signer not belonging to `victimDON`'s configured members/allowlist — i.e., no error such as "unauthorized sender" or "signer not a DON subscriber" is ever returned, and the handler mock records the call as if it came from a legitimate subscriber.
4. Compare against expected behavior: the call should be rejected with an authorization error before `HandleLegacyUserMessage` executes.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
