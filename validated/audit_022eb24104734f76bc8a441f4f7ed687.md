### Title
Potential validation against a non-canonical sortition fork via unchecked `burn_view_consensus_hash` in `TenureChange::Extend` proposals - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
In `NakamotoBlockProposal::validate`, the `sort_tip` used to build the `SortitionHandleConn` for tenure validation is derived from `burn_view_consensus_hash` via `SortitionDB::get_block_snapshot_consensus`, with no visible check in this function that `sort_tip` is the sortdb's current canonical tip. [1](#0-0)  If a stale/non-canonical but still-indexed consensus hash is accepted here, `check_block_has_valid_tenure` would validate tenure ancestry against that non-canonical fork's own history rather than rejecting it outright.

### Finding Description
The claimed equality is: the sortition tip used to validate a block proposal's tenure (`sort_tip`) must equal the sortdb's canonical Bitcoin-fork tip, not merely any snapshot indexed under a queried consensus hash.

The traced path in `validate()`:
1. `burn_view_consensus_hash` is computed by `NakamotoChainState::get_block_burn_view(sortdb, &self.block, &parent_stacks_header)` — for a `TenureChange` with cause `Extend`, this is documented as being "whatever is indicated in the TenureChange" [2](#0-1) .
2. `sort_tip` is resolved via `SortitionDB::get_block_snapshot_consensus(sortdb.conn(), &burn_view_consensus_hash)`, which looks up a snapshot purely by consensus hash, with rejection only if no snapshot exists at all (`NoSuchTenure`) [3](#0-2) .
3. `db_handle`/`burn_dbconn` are built as `sortdb.index_handle(&sort_tip.sortition_id)` — a handle scoped to the ancestry of `sort_tip`, not necessarily the canonical chain tip [4](#0-3) .
4. `check_block_has_valid_tenure` then only checks `db_handle.has_consensus_hash(tenure_id)`, i.e., whether the block's declared tenure consensus hash is an ancestor within `sort_tip`'s own lineage — this is self-consistent within a fork but does not itself assert `sort_tip` is canonical [5](#0-4) .

If a non-canonical burn-view consensus hash (from an orphaned Bitcoin fork branch that the sortdb has not pruned) is still queryable via `get_block_snapshot_consensus`, and the attacker crafts a `TenureChange::Extend` block whose own `consensus_hash` is an ancestor within that same non-canonical branch, the described self-consistency check would pass without any explicit comparison to the sortdb's actual canonical tip.

### Impact Explanation
If confirmed, this would fall under Critical: a signer validating and signing a block whose tenure derivation is rooted in a non-canonical Bitcoin fork, which is a canonicity violation of chain safety. This is a `Critical` category "signer signing an invalid, non-canonical block."

### Likelihood Explanation
This requires: (a) the victim's sortdb still has the non-canonical fork's snapshots indexed (not pruned), which depends on internal sortdb reorg/pruning behavior I could not fully verify; (b) the attacker can craft a valid `TenureChange::Extend` transaction and win a block-commit slot referencing that stale consensus hash; (c) `get_block_burn_view` does not itself perform a canonicity check before returning the consensus hash (unverified — I could not read this function's body). Given these open dependencies, I cannot state with confidence whether this is exploitable in practice or whether canonicity is enforced by `get_block_burn_view`, `has_consensus_hash`, or sortdb pruning logic that I did not have the opportunity to inspect.

### Recommendation
Regardless of the exact preconditions, defense-in-depth suggests explicitly asserting `sort_tip.sortition_id` equals (or is an ancestor of) `sortdb.get_canonical_burn_chain_tip()`'s sortition_id immediately after resolving `sort_tip` in `validate()`, rejecting with `NonCanonicalTenure`/`NoSuchTenure` otherwise, rather than relying solely on `has_consensus_hash`'s ancestor check scoped to a caller-supplied consensus hash.

### Proof of Concept
I could not construct a verified reproducible Rust test because I was unable to confirm within available tool calls (a) whether `get_block_burn_view` performs upstream canonicity validation of the Extend tenure's declared consensus hash, and (b) whether the sortdb retains queryable snapshots for orphaned/non-canonical forks long enough for `get_block_snapshot_consensus` to return them. A conclusive test would need to: seed a `SortitionDB` with two competing burnchain forks, orphan one via a longer competing fork, confirm the orphaned fork's consensus hash is still resolvable via `SortitionDB::get_block_snapshot_consensus`, then submit a `NakamotoBlockProposal` with a `TenureChange::Extend` referencing that orphaned consensus hash and assert whether `NakamotoBlockProposal::validate` rejects with `NonCanonicalTenure`/`NoSuchTenure` or proceeds to full validation.
