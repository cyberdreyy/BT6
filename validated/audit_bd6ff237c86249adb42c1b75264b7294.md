### Title
Distinguishable authorization error messages in `WorkflowMetadataHandler.Authorize` leak workflow-ID existence and per-workflow signer-authorization status to unauthenticated callers - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`Authorize` returns four semantically distinct, human-readable errors (JWT invalid, replay, workflow-ID-not-found, signer-not-authorized), and the gateway trigger-handling code forwards the raw `err.Error()` text back to the calling client verbatim. This lets any unauthenticated party who can submit a self-signed, syntactically-valid JWT distinguish between a non-existent workflow ID and an existing workflow ID for which their own key is simply not on the authorized-signer list.

### Finding Description
`WorkflowMetadataHandler.Authorize` performs checks in this order: JWT verification, replay check, workflow-ID existence check, signer-authorization check [1](#0-0) . The workflow-ID-not-found branch returns `fmt.Errorf("workflow ID %s not found", workflowID)` and the signer-not-authorized branch returns `fmt.Errorf("signer '%s' is not authorized for workflow '%s'...", ...)` [2](#0-1) .

The caller of `Authorize`, `httpTriggerHandler.authorizeRequest`, does not sanitize or genericize this error — it concatenates the raw error text into the JSON-RPC error response sent to the external requester: `h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)` [3](#0-2) . Since an attacker can trivially generate a self-signed JWT with an arbitrary key for `utils.VerifyRequestJWT` to accept (verification only checks the signature is self-consistent and the digest matches the request, not that the signer is registered), the attacker fully controls two dimensions: the `workflowID` guessed and the signer key used. By toggling `workflowID` while holding the signer fixed, they can distinguish:
- "workflow ID ... not found" → workflowID does not exist in `authorizedKeys`
- "signer '...' is not authorized for workflow '...'" → workflowID exists but this signer is not in its authorized set

This confirms workflow-ID existence and, combined with repeated queries using different candidate signer addresses, whether a given address belongs to the authorized-signer set for a known workflow ID.

### Impact Explanation
This is an information-disclosure/enumeration issue, not key or private-material disclosure — no private keys are exposed, and `Authorize` never returns the authorized-key set itself, only a yes/no signal per guessed address. The practical impact is: (1) confirmation of which workflow IDs are live/registered on the gateway, and (2) confirmation of whether a specific EOA address is a registered signer for that workflow. This maps to a low-severity "information disclosure enabling enumeration" class rather than authentication bypass or fund movement, since it does not grant the attacker execution rights, does not bypass the authorization check itself (an unauthorized signer is still correctly rejected), and does not achieve the "secrets never leave" violation the question frames (no secret key material leaves the node).

### Likelihood Explanation
Preconditions are minimal: an attacker with no privileges can self-sign JWTs (own key) and hit the workflow trigger endpoint repeatedly, exactly as described. However, feasibility of exploiting this for *enumeration* is bounded by workflow-ID space: workflow IDs are derived hashes and validated to be `workflowIDLength` characters [4](#0-3) , so blind brute-forcing valid IDs is impractical; the oracle is only useful to confirm/deny IDs an attacker already suspects (e.g., obtained from elsewhere), and to test candidate signer addresses one at a time against a known ID.

### Recommendation
Return a single generic error (e.g., "authorization failed") from `authorizeRequest`/`handleUserError` to external callers for all `Authorize` failure branches, while retaining the detailed, distinguishable errors only in server-side logs (as is already done via `h.lggr.Errorw`/`Warnw`). This removes the external oracle without affecting operator debuggability.

### Proof of Concept
Add a table-driven test in `workflow_metadata_handler_test.go` (or an integration test on `httpTriggerHandler.HandleUserTriggerRequest`) that:
1. Registers one workflow ID with one authorized signer.
2. Sends request A with a self-signed JWT for a random non-existent workflow ID and captures the JSON-RPC error message returned via the `callback`.
3. Sends request B with a self-signed JWT (different, unauthorized key) for the existing workflow ID and captures the JSON-RPC error message.
4. Assert that today the two messages differ (`"not found"` vs `"is not authorized for workflow"`), demonstrating the oracle exists at `http_trigger_handler.go:365`.
5. After applying the fix, assert both paths return an identical generic error string/code.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
