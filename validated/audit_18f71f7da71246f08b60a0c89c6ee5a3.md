### Title
Stale confirmations from removed signers are not purged, allowing a request to execute below the live-member threshold - (File: `multisig/src/lib.rs`)

### Summary
The `MultiSigContract::confirm` function counts confirmations against `self.num_confirmations` purely from the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map [1](#0-0) . When a signer key is removed via the `DeleteKey` action, the contract only purges requests that the removed key itself *authored*, never the confirmations that the removed key contributed to *other, still‑pending* requests [2](#0-1) . Those stale confirmations remain counted toward the threshold, so a request can later be executed with fewer live (currently‑authorized) signers than `num_confirmations` actually requires.

### Finding Description
`execute_request`'s `DeleteKey` branch removes the deleted key's own authored requests and its `num_requests_pk` entry, then deletes the access key from the account: [2](#0-1) 
It never scans the `confirmations` map to strip the removed public key from confirmation sets of requests that key had merely *confirmed* (but did not author). `confirm` itself has no notion of "is this pk still a valid signer" — it only checks set membership and size: [1](#0-0) 

Binding broken: `confirmations_counted(request) == live_members_who_confirmed(request)`. After a `DeleteKey`, the left side can exceed the right side because a dead key's confirmation is still present in the set, so `confirmations.len() + 1 >= num_confirmations` can become true while the number of *currently authorized* confirming keys is one less than `num_confirmations`.

### Impact Explanation
This falls under the Critical impact category "a multisig request executed below threshold." A request (e.g., a `Transfer` of NEAR funds, or an `AddKey`/`DeployContract`) can be finalized and executed with effectively fewer live signer approvals than the configured `num_confirmations`, undermining the custody guarantee that `K` currently-valid keys must approve any action.

### Likelihood Explanation
This requires no privileged/foundation action and no compromise of a live key — it only requires the ordinary sequence of: a pending request accumulating a partial confirmation, followed by an unrelated, legitimate `DeleteKey` request removing that confirming signer (for the normal reason of key rotation/offboarding), followed by continued confirmations on the still-pending request by other legitimate signers. This is a natural operational sequence (key rotation while a request is outstanding) rather than a contrived attack path, since nothing in `add_request`/`confirm`/`delete_request` invalidates or re-validates outstanding confirmations against the current signer set.

### Recommendation
On `DeleteKey` (and equivalently `DeleteMember` in `multisig2`), iterate all pending requests' `confirmations` sets and remove the deleted public key/member from every set, not only from the requests it authored. Alternatively, validate at `confirm`/execution time that all keys/members present in a request's confirmation set are still current members before counting them toward the threshold.

### Proof of Concept
1. Initialize multisig with `num_confirmations = 3` and keys A, B, C, D, E.
2. Key A calls `add_request` to create request R (e.g., `Transfer`), then `confirm` (1 confirmation: A).
3. Key B calls `confirm(R)` (2 confirmations: A, B) — R is still pending, one short of threshold.
4. Separately, keys A, C, D submit and confirm a `DeleteKey { public_key: B }` request, which executes and removes B's access key. The `DeleteKey` branch in `execute_request` only removes requests where `signer_pk == B` (B did not author R, so R is untouched) — B's stale confirmation stays in `confirmations[R]`.
5. Key C now calls `confirm(R)`. `confirmations.len()` is 2 (A, B) `+ 1 = 3 >= num_confirmations`, so R executes — even though B is no longer a valid signer and only A and C are currently live confirmers, i.e., only 2 live confirmations authorized a 3-of-N action. [3](#0-2)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
