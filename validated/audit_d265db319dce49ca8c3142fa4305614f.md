### Title
Unvalidated symlink target in zip extraction allows planting a symlink pointing outside the job workspace - (File: helpers/archives/zip_extract.go)

### Summary
`extractZipSymlinkEntry` reads the raw file content of a `zip.File` entry with `os.ModeSymlink` mode and passes it directly to `os.Symlink(string(data), file.Name)` with no validation that the target is relative and confined to the extraction root. Because zip/artifact/cache contents are attacker-controlled (a pipeline author can craft the archive that another job later extracts, e.g. via shared cache keys or artifact dependencies), this lets an attacker plant a dangling symlink whose target is an absolute path or contains `../` segments.

### Finding Description
The exploitable path is: `ExtractZipFile`/`ExtractZipArchive` (`helpers/archives/zip_extract.go:85-120`) iterates `archive.File` entries and calls `extractZipFile` (`:61-83`), which dispatches `os.ModeSymlink` entries to `extractZipSymlinkEntry` (`:22-39`): [1](#0-0) 

The function reads the entry's content (`data`) — which in a zip symlink entry is conventionally the literal symlink target string — and calls `os.Symlink(string(data), file.Name)` with zero validation of `data`. No check enforces that the target:
- is a relative path, or
- resolves to a location inside the extraction root.

The only pre-extraction checks present in `ExtractZipArchive` are `errorIfGitDirectory` (warns about `.git` paths) and a `pathErrorTracker` that simply suppresses repeated log warnings — neither validates symlink *targets*, only entry *names*, and even the name checks don't reject absolute/traversal targets embedded in symlink content. There is also no confinement (chroot/chdir/path-prefix check) applied to the resolved symlink target anywhere in this file. `os.Symlink` itself performs no target validation — it will happily create a symlink to `/etc/passwd` or `../../other-job-workspace/secrets.env`.

This matches the classic "zip-slip via symlink" pattern: the entry itself is created inside the job/cache extraction directory (its *name*, `file.Name`, is used as the link path), but the link's *target* can point anywhere on the filesystem the runner process has permission to reach. The symlink creation alone does not read/write foreign data, but it silently succeeds and persists a dangling link inside the job's directory tree.

### Impact Explanation
If a subsequent step in the same job (a build script, or an artifact-collection step that writes to a filename that turns out to be this symlink) writes through the planted symlink, the write is redirected outside the job workspace to wherever the attacker specified — e.g. clobbering another job's workspace file, or writing to a path reachable on a shared host runner. Read-side impact is more limited: extraction itself does not read through the symlink, so information disclosure requires a later read operation (e.g., the victim's build script `cat`-ing a file at the same relative name) that happens to dereference the attacker-controlled symlink. The concrete, reachable impact is limited to whatever the victim job's own subsequent build/artifact steps do with a file at that path — the extraction step by itself only plants the dangling symlink, it does not by itself cause a write.

### Likelihood Explanation
This requires the attacker to control the contents of a cache or artifact archive that a victim job later extracts (e.g., via a shared cache key across branches/MRs, or an artifact dependency in the same project). This is a normal, GitLab-permitted primitive for pipeline authors (job artifacts/cache are attacker-writable within their own job) and is not an admin-only precondition. However, actual host-file compromise depends on the victim job's own subsequent behavior (whether it writes to the same relative path the symlink occupies), so the "write" half of the impact is conditional rather than automatic on extraction alone.

### Recommendation
In `extractZipSymlinkEntry`, validate the symlink target before calling `os.Symlink`:
- Reject absolute targets (`filepath.IsAbs(string(data))`).
- Resolve `filepath.Join(filepath.Dir(file.Name), string(data))`, clean it, and reject targets that escape the intended extraction root (i.e., the cleaned path must not start with `..` after making it relative to the root, mirroring protections used elsewhere against zip-slip on entry names).
- Apply the same containment check consistently to both the entry name (`file.Name`) and the symlink target, and add this to the extractor's `pathErrorTracker`-based rejection flow so violations are treated as (at minimum) warnings/errors rather than silently succeeding.

### Proof of Concept
```go
func TestExtractZipSymlinkEscapesRoot(t *testing.T) {
    testInWorkDir(t, func(t *testing.T, fileName string) {
        f, err := os.Create(fileName)
        require.NoError(t, err)
        archive := zip.NewWriter(f)

        // Create a symlink entry whose "content" (target) is an absolute path
        hdr := &zip.FileHeader{Name: "evil_link"}
        hdr.SetMode(os.ModeSymlink | 0o777)
        w, err := archive.CreateHeader(hdr)
        require.NoError(t, err)
        _, err = w.Write([]byte("/tmp/outside-target"))
        require.NoError(t, err)
        require.NoError(t, archive.Close())
        f.Close()

        err = ExtractZipFile(fileName)
        require.NoError(t, err) // extraction currently succeeds without validation

        target, err := os.Readlink("evil_link")
        require.NoError(t, err)
        // Expected (after fix): extraction should reject or rewrite so target stays within root
        assert.False(t, filepath.IsAbs(target), "symlink target escaped extraction root: %s", target)
    })
}
```
Expected current (vulnerable) behavior: the test creates `evil_link -> /tmp/outside-target` with no error, demonstrating the missing validation. After the fix, extraction should either fail or normalize/reject the out-of-root target.

```go
func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}
```
