Hardcoded EIP-8130 canonical authenticator addresses cause permanent authentication failure and fund lock if the deployed authenticator contracts are ever redeployed - (File: crates/common/consensus/src/transaction/eip8130/addresses.rs)

### Summary
Base's native EIP-8130 (account-abstraction) execution path enshrines the canonical `P256`, `WebAuthn`, and `Delegate` authenticator contracts by hardcoding their deterministic CREATE2 addresses in `Eip8130Contracts`. Every sender/payer authentication and account-configuration authorization in block execution and mempool admission compares the transaction's declared `authenticator` address against these hardcoded constants. This is structurally the same class of bug as the reported Stargate issue: an external/derived contract address is pinned in code, and if that pinned value ever diverges from the actual on-chain contract (e.g. a bytecode/redeploy change), the enshrined dispatch treats every authentication for the new contract as non-canonical and reverts, even though account holders assigned that authenticator as their real signer.

### Finding Description
`Eip8130Contracts` pins the canonical authenticator addresses (`P256_AUTHENTICATOR`, `WEBAUTHN_AUTHENTICATOR`, `DELEGATE_AUTHENTICATOR`) and their CREATE2 `(salt, init_code_hash)` triples as compile-time constants: [1](#0-0) [2](#0-1) 

The module's own doc comment states the invariant this depends on: "any change to the contract bytecode changes its address... On each redeploy, re-pin the address, its `*_SALT`, and its `*_INIT_CODE_HASH` together". This is precisely the "router redeployment" failure mode from the external report, generalized to authenticator contracts.

`AuthenticatorDispatch::authenticate` — the enshrined, stateless dispatch used during block execution and validation — routes strictly by matching the caller-declared authenticator address against these hardcoded constants, rejecting everything else with `AuthError::NotCanonical`: [3](#0-2) 

`ActorAuthorizer::authenticate`/`resolve_bound` similarly binds a stored `actor_config.authenticator` against this fixed constant and reverts with `AuthorizeError::AuthenticatorMismatch` on any mismatch: [4](#0-3) [5](#0-4) 

Both the txpool admission path and the full block-execution path (`Eip8130Executor::authorize_and_apply`) run this same authorization pipeline, so any transaction whose account is configured to use an authenticator contract that no longer matches the hardcoded address is rejected identically at mempool and inclusion time: [6](#0-5) [7](#0-6) 

The failure scenario mirrors the Stargate report exactly: EIP-8130 accounts are configured (via `actor_config`, an on-chain, user-controlled storage binding) to trust a specific authenticator contract address. If that authenticator contract is ever redeployed at a different address (upgrade, migration, bug fix, or a change to its init code that the node's pinned constant is not updated to match), the enshrined dispatch treats every attempted authentication through the new/updated contract as `NotCanonical`/`AuthenticatorMismatch` and reverts the transaction. Unlike a simple failed transaction, however, an account whose only bound non-k1 authenticator is the stale one becomes **permanently unable to authenticate any sender or payer action** — it cannot move funds, revoke the stale binding, or reconfigure itself, because reconfiguration (`ConfigChange`) itself requires successful authentication through the same broken pipeline.

### Impact Explanation
This differs from the original Stargate report's transient "stuck tokens in a bridge contract" scenario in one important way: the Base analog can produce a **permanent** loss-of-access condition rather than a one-time stuck-funds event. Any EIP-8130 account whose registered actor authenticator address goes stale (due to the pinned `Eip8130Contracts` constant falling out of sync with an actual redeployed/upgraded authenticator, or a client-side pinning error at network upgrade time) permanently loses the ability to authorize transactions through that actor — including account-configuration changes needed to add a new authenticator — resulting in funds and control being irrecoverably locked in the account. Because this is enforced identically in both the enforcement/consensus path (block execution) and the pool admission path, there is no fallback: even a "self-heal" transaction cannot get past validation. This satisfies the Medium/High funds-freezing bar (permanent freezing of funds for the affected account(s)).

### Likelihood Explanation
Likelihood is low but non-zero, matching the qualitative language of the original report ("difficult to estimate ... but a risk remains"). The addresses are derived deterministically via CREATE2 from mined vanity salts and pinned init-code hashes, and the repository includes a drift test (`addresses_match_create2_derivation`) asserting internal self-consistency of `(address, salt, init_code_hash)` — but that test only proves internal consistency of the constants, not that the constants still match whatever is actually deployed on-chain. Any of: (a) an authenticator contract bytecode fix/upgrade that is deployed under a new address, (b) an operational mistake pinning the wrong constant during a network upgrade, or (c) a future protocol change to one of the authenticator contracts, would silently desynchronize the enshrined path from the deployed contract address that user accounts are configured to trust.

### Recommendation
- Add a fallback verification path that does not use hard-pinned addresses as the sole source of authenticator legitimacy — e.g., verify by comparing the resolved authenticator's on-chain codehash (or a codehash allowlist, similar to the `erc1167_proxy_code_hash` recognition already used for `CANONICAL_HIGH_RATE_PAYER_ACCOUNT`) instead of (or in addition to) exact address equality, so a redeployed-but-parity contract at a new address does not immediately lock out every account bound to it.
- Provide an explicit, permissionless (or minimally-permissioned) migration/rebinding path for `actor_config` entries that lets an account holder move off a deprecated authenticator address using an authentication method that does not itself depend on the potentially-stale binding (e.g., the account's own k1 self, if still live and unrevoked).
- Treat any change to `Eip8130Contracts` canonical addresses as a hard-fork-gated protocol upgrade with an explicit compatibility/migration window, and monitor the deployed authenticator contracts' actual bytecode/address on-chain as part of release validation, analogous to the report's recommendation to monitor Stargate's router address for changes.

### Proof of Concept
1. An EIP-8130 account `A` registers an actor bound to `Eip8130Contracts::WEBAUTHN_AUTHENTICATOR` via `actor_config[actorId][A] = pack(WEBAUTHN_AUTHENTICATOR, scope, expiry)` (a normal, permissionless on-chain configuration transaction).
2. The `WebAuthnAuthenticator` contract is later redeployed (e.g., as part of a bugfix), yielding a new address `WEBAUTHN_AUTHENTICATOR_V2`, but the network's `Eip8130Contracts::WEBAUTHN_AUTHENTICATOR` constant is not (or cannot yet be) updated in lockstep across all node software — or the account owner is told to re-point to the new address before the node's enshrined dispatch table is upgraded.
3. Any subsequent transaction signed via the new authenticator hits `AuthenticatorDispatch::authenticate`, which does not match `WEBAUTHN_AUTHENTICATOR_V2` against any of the three hardcoded canonical addresses ( [8](#0-7) ) and returns `AuthError::NotCanonical`, propagating to `AuthorizeError` and rejecting the transaction both in the pool (`validator.rs`) and at block execution (`eip8130.rs::authorize_and_apply`).
4. Because `actor_config[actorId][A]` still stores the stale `WEBAUTHN_AUTHENTICATOR` (old) address, and the account's `resolve_bound` check requires `config.authenticator == authenticator` exactly, any attempt to reconfigure via the new authenticator also fails ( [9](#0-8) ), leaving the account permanently unable to authorize sender or payer actions if the WebAuthn actor was its only means of authentication (e.g., default EOA already revoked/disabled).

    pub fn authenticate(
        hash: B256,
        authenticator: Address,
        data: &[u8],
    ) -> Result<DispatchOutcome, AuthError> {
        // `address(0)` is the empty / "no actor configured" sentinel and is never
        // a valid authenticator selector; it falls through to `NotCanonical`.
        //
        // secp256k1 is the protocol-reserved native k1 sentinel (`address(1)`);
        // there is no deployed secp256k1 authenticator contract.
        if authenticator == Eip8130Constants::K1_AUTHENTICATOR {
            return Ok(DispatchOutcome::Authenticated { actor_id: Self::ecrecover(hash, data)? });
        }
        if authenticator == Eip8130Contracts::P256_AUTHENTICATOR {
            return Ok(DispatchOutcome::Authenticated { actor_id: Self::p256(hash, data)? });
        }
        if authenticator == Eip8130Contracts::WEBAUTHN_AUTHENTICATOR {
            return Ok(DispatchOutcome::Authenticated { actor_id: Self::webauthn(hash, data)? });
        }
        if authenticator == Eip8130Contracts::DELEGATE_AUTHENTICATOR {
            return Self::delegate(data);
        }
        Err(AuthError::NotCanonical(authenticator))
    }

    fn resolve_bound(
        storage: &AccountConfigurationStorage<'_>,
        account: Address,
        actor_id: B256,
        authenticator: Address,
        now: u64,
    ) -> Result<ResolvedActor, AuthorizeError> {
        if actor_id.is_zero() {
            return Err(AuthorizeError::AuthenticationFailed);
        }
        let config = storage.actor_config_slot(account, actor_id)?;
        if config.authenticator != authenticator {
            return Err(AuthorizeError::AuthenticatorMismatch { actor_id, authenticator });
        }
        // 0 = no expiry; otherwise valid while now <= expiry.
        if config.expiry != 0 && now > config.expiry {
            return Err(AuthorizeError::ActorExpired { actor_id, expiry: config.expiry });
        }
        // `_resolvePolicyTarget`: address(0) when ungated, else the policy manager
        // (never the signed commitment). Resolved from the `config` already in
        // hand so an ungated actor costs no extra read and a gated one reads only
        // the manager slot (no `actor_config` re-read). OPERATOR overrides POLICY.
        let policy_target = if Eip8130Constants::sender_is_policy_gated(config.scope) {
            storage.get_policy_manager(account, actor_id)?
        } else {
            Address::ZERO
        };
        Ok(ResolvedActor { actor_id, scope: config.scope, policy_target, expiry: config.expiry })
    }
