### Title
Missing `return` after failed email-claim extraction lets OIDC token-exchange still complete and issue an authenticated session — ([File: core/sessions/oidcauth/oidc.go])

### Summary
`handleTokenExchange` in `core/sessions/oidcauth/oidc.go` writes an error response when the `email` claim cannot be extracted from the ID token, but does not `return` afterward, so execution falls through to the success path that creates a DB session record and issues an authenticated session cookie to the caller — mirroring the reported bug class where a failure condition is detected but the code continues on to mark the outcome as successful because a `return` was omitted.

### Finding Description
In `handleTokenExchange`, when the type assertion on the email claim fails, the handler logs the error and writes an error body, but has no `return`: [1](#0-0) 

Execution then continues into the "success" logic exactly as in the fully-valid case: it calls `IDClaimsToUserRole` (line 234), creates a new session (`clsessions.NewSession()`), inserts a row into `oidc_sessions` with the (empty-string) `user_email` (lines 249-260), sets the session cookie key (`ginSession.Set(webauth.SessionIDKey, clSession.ID)`), saves the session, and finally emits `ExchangeTokenResponse{Success: true}`: [2](#0-1) 

This is structurally identical to the Babylon root cause: a validation/failure branch that should abort request handling instead falls through into code that finalizes/persists an "authorized" outcome (there, marking a message refundable via `IndexRefundableMsg`; here, persisting a session row and setting the authenticated session cookie via `ginSession.Save()`), solely because the necessary `return` statement is missing.

### Impact Explanation
An OIDC-authenticated flow that should be rejected when the identity provider's ID token does not carry a usable `email` claim instead completes: the server creates and persists a session (`oidc_sessions` row with an empty `user_email`), sets the session cookie in the gin context, and returns `Success: true` to the client — despite the code path deciding, moments earlier, that the exchange should fail. This results in a client being granted an authenticated session (with a role derived from `IDClaimsToUserRole`) through a code path the developers clearly intended to short-circuit, and pollutes the `oidc_sessions` table with a row keyed by an empty email, which can be reused/looked up in `FindUser`/`AuthorizedUserWithSession` in ways not intended by the original claim-validation logic.

### Likelihood Explanation
This is reachable by any user going through the standard OIDC sign-in/callback flow (`handleSignIn` → `handleTokenExchange`) whenever the identity provider's ID token omits the `email` claim (e.g., IdP configured without email scope, or an IdP account lacking email) — no privileged access or special network position is required, only a normal OIDC login attempt with a token lacking the expected claim.

### Recommendation
Add a `return` immediately after handling the missing/invalid `email` claim (mirroring the pattern already used for every other error branch in this function), so the request is aborted instead of falling through to session creation and the success response:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```

### Proof of Concept
1. Configure the node with OIDC auth where the identity provider's token response does not include an `email` claim (or use a test IdP mock that omits it).
2. Initiate `/oidc/signin`, complete the provider's auth flow, and let it call back to `/oidc/callback`, which invokes `handleTokenExchange`.
3. Observe that despite `claims["email"].(string)` failing (`ok == false`) and an error string being written, the handler proceeds to insert into `oidc_sessions`, sets `SessionIDKey` on the gin session, calls `ginSession.Save()`, and returns `ExchangeTokenResponse{Success: true}` — confirming the session is issued despite the earlier failure, matching the missing-`return` finding pattern.
