### Title
Activation Registry `setAdmin` Uses Unprotected Single-Step Transfer, Allowing Admin to Permanently Brick Feature-Activation Governance - (File: `crates/common/precompiles/src/activation/storage.rs`)

### Summary
`ActivationRegistryStorage::set_admin` rotates the activation-registry admin in a single, irreversible step and only rejects the zero address. Unlike the sibling `PolicyRegistry` precompile, which protects admin rotation with a stage/finalize two-step handshake, the activation registry has no such safeguard, so a single mistaken `setAdmin` transaction can permanently strand admin control of B-20/PolicyRegistry feature activation — mirroring the original report's "admin sets a bad address and breaks the protocol" bug class.

### Finding Description
`set_admin` writes the caller-supplied `new_admin` directly to storage after only checking it is non-zero: [1](#0-0) 

The only current admin can call this (`require_admin_caller`), and afterward only the newly stored address can authorize any further admin action: [2](#0-1) 

There is no timelock, no pending/staged admin, and no validation that `new_admin` is an address capable of originating transactions (e.g. it could accidentally be set to a predeploy such as `WETH9` at `0x4200000000000000000000000000000000000006`, another precompile, or any address whose key is unknown/unrecoverable). Once that happens, `require_admin_caller` will never match `msg.sender` again for any real transaction sender, because the stored admin can never be a valid `tx.origin`/EOA signer.

Contrast this with `PolicyRegistry`'s admin rotation, which explicitly stages the new admin and only finalizes once the new admin itself submits a confirming transaction — this two-step design is exactly the kind of mitigation the original report recommended ("change it through governance" / gated transfer) and it is already implemented elsewhere in this codebase: [3](#0-2) 

The activation registry gates activation/deactivation of every native B-20 feature (`PolicyRegistry`, `B20Stablecoin`, `B20Asset`) through this same admin: [4](#0-3) [5](#0-4) 

so losing control of the admin address permanently removes the only path to activate or deactivate those features going forward.

### Impact Explanation
If the configured/rotated activation admin address is set to an address that can never originate a signed transaction (a predeploy, a precompile, a burn/typo address, or simply a key that was never generated/lost), then:
- No account can ever again call `activate`/`deactivate`/`setAdmin` on the activation registry (`require_admin_caller` will never succeed).
- Any feature not yet activated (e.g. `B20Asset`, `B20Stablecoin`, `PolicyRegistry`) becomes permanently un-activatable, and any active feature can never be turned off in an emergency (e.g., to respond to a bug in the B-20 token logic).
This is a permanent freezing of a core governance/administration capability of the chain's native token system, reachable by a single mis-issued admin transaction, matching Medium severity per the report's own classification.

### Likelihood Explanation
The admin only needs to make one mistake in a single `setAdmin` transaction (typo, wrong environment/config value, accidental use of a well-known predeploy address like WETH9) since there is no simulation-friendly two-step confirmation and no revert path once the value is anything non-zero. Given that other precompiles in the same codebase (`PolicyRegistry`) already recognized this class of risk and implemented a staged transfer, its absence here indicates a real gap rather than an intentional design choice.

### Recommendation
Adopt the same stage/finalize (or timelocked) admin-transfer pattern already used by `PolicyRegistryStorage` (`stageUpdateAdmin` / `finalizeUpdateAdmin`) for `ActivationRegistryStorage::set_admin`, requiring the new admin to confirm the rotation from its own address before it takes effect. At minimum, add a confirmation step or an admin-renunciation/recovery path so that a single erroneous transaction cannot permanently freeze feature-activation governance.

### Proof of Concept
1. Deploy/enable Beryl with a state-backed activation admin `A`.
2. `A` calls `IActivationRegistry.setAdmin(newAdmin = WETH9_PREDEPLOY_ADDRESS)` — this succeeds because `set_admin` only checks `new_admin.is_zero()`: [6](#0-5) 
3. From this point on, `require_admin_caller` compares `msg.sender` to the stored admin (`WETH9_PREDEPLOY_ADDRESS`), which no signer can ever match: [7](#0-6) 
4. All subsequent `activate`, `deactivate`, and `setAdmin` calls revert with `Unauthorized` forever, permanently freezing B-20/PolicyRegistry feature governance.

    /// Sets the activation registry admin address.
    pub fn set_admin(
        &mut self,
        new_admin: Address,
        admin_config: ActivationAdminConfig,
    ) -> Result<()> {
        if self.storage.is_static() {
            return Err(BasePrecompileError::revert(IActivationRegistry::StaticCallNotAllowed {}));
        }
        if !admin_config.state_enabled {
            return Err(BasePrecompileError::revert(
                IActivationRegistry::AdminStorageNotEnabled {},
            ));
        }
        if new_admin.is_zero() {
            return Err(BasePrecompileError::revert(IActivationRegistry::ZeroAdminAddress {}));
        }

        let caller = self.require_admin_caller(admin_config)?;

        self.__initialize()?;
        self.admin.write(new_admin)?;
        self.emit_event(IActivationRegistry::AdminChanged {
            previousAdmin: caller,
            newAdmin: new_admin,
            caller,
        })?;

        Ok(())
    }

    /// Reverts unless the current caller is the effective activation admin.
    pub fn require_admin_caller(&self, admin_config: ActivationAdminConfig) -> Result<Address> {
        let caller = self.storage.caller();
        let admin = self.authorized_admin(admin_config)?;
        if caller != admin {
            return Err(BasePrecompileError::revert(IActivationRegistry::Unauthorized { caller }));
        }
        Ok(caller)
    }
}
