### Title
Stale per-epoch instant-withdraw basis is never released on claim, inflating default recovery basis and permanently locking recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The CVE pattern is retained partial state that is never released, letting unauthenticated clients exhaust a shared resource pool. The closest analog in `IdleCreditVault` is instant-withdraw accounting: `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are written on every request but are only cleared inside the post-default claim path — never on a normal successful claim. The retained "ghost" basis is later consumed by `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` during `finalizeDefaultRecovery`, inflating `totalBasis`, diluting `defaultRecoveryPrice`, and leaving a residual `defaultRecoveryReserve` that no function can ever distribute.

### Finding Description

`requestInstantWithdraw` accrues per-epoch state: `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`, and `pendingInstantWithdraws` [1](#0-0) .

When funds are collected, `collectInstantWithdrawFunds` decrements only `pendingInstantWithdraws` [2](#0-1) . A normal claim via `claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` and burns the receipt — the per-epoch entries are retained [3](#0-2) . Those entries are only decremented inside `_claimDefaultedInstantWithdrawRequest`, which is unreachable until after a default [4](#0-3) .

On default finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, regardless of how much of that epoch basis was already paid out at par [5](#0-4) . Worse, `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as *strategy-held* backing reserved for those claims, crediting the reserve for underlying that was already transferred to claimants [6](#0-5) . Both terms are folded into `reserveAmount`/`totalBasis` in `finalizeDefaultRecovery` [7](#0-6) .

### Impact Explanation

Two compounding effects:

1. **Dilution**: `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` divides an unchanged (or smaller real) reserve by a basis inflated with ghost claims, so every honest pending receipt holder and active LP (via `activeFinalNAV`) receives less than entitled.
2. **Permanent freezing**: `defaultRecoveryReserve` only ever decreases through `_transferDefaultRecovery` claims. Because the inflated basis produces sub-unity prices, the portion of the reserve "attributed" to already-claimed receipts is never drawn by anyone and is locked in the strategy forever. `_defaultPrefundedInstantReserve` additionally mints phantom reserve accounting for funds that left the contract, further distorting the split.

An attacker maximizes the locked/diluted amount by making a large instant request, getting it funded at epoch start, claiming at par, and leaving the stale epoch basis in place when default finalization runs in the same epoch. The frozen amount scales with the attacker's claimed basis — bounded only by their capital, not by fees or gas.

### Likelihood Explanation

Requirements: instant withdrawals enabled (`setInstantWithdrawParams`), an epoch in which some instant claims are funded/claimed while `pendingInstantWithdraws` remains non-zero (a second, unfunded instant requester suffices), and default finalization occurring before `epochNumber` bumps. Defaults are triggered around honest owner/manager/borrower calls (`stopEpoch` default path, `finalizeDefault`), which the attacker sequences around rather than controls. The stale-state write itself costs the attacker only a normal deposit/instant-withdraw cycle. The narrower the epoch boundary, the lower the likelihood, but the accounting defect is unconditional — no guard ever reconciles `instantWithdrawClaimsByEpoch` against claimed amounts.

### Recommendation

- In `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (or track the request epoch per user) and `instantWithdrawClaimsByEpoch[currentEpoch]` by the claimed amount, mirroring the cleanup in `_claimDefaultedInstantWithdrawRequest`.
- Alternatively, derive the "already-funded" instant basis in `_defaultPrefundedInstantReserve` and `defaultPendingClaimBasis` from actual remaining receipt balances rather than cumulative per-epoch request sums, so paid-out claims cannot re-enter recovery accounting.
- Add an invariant test: after any successful instant claim, `instantWithdrawClaimsByEpoch[epoch]` must equal the sum of outstanding unclaimed instant receipts for that epoch.

### Proof of Concept

Foundry fork PoC sketch against `IdleCreditVault` + `IdleCDOEpochVariant` with instant withdrawals enabled:

```solidity
// Setup: pool running, instant withdraws enabled via
// cdoEpoch.setInstantWithdrawParams(delay, minAprDelta, true)

// Epoch N:
// 1. attacker deposits 1_000_000e6 USDC worth of AA tranches, victim deposits same.
// 2. attacker requests instant withdraw of full balance; victim requests 1e6 instant
//    withdraw slightly later so it stays unfunded.
// 3. manager triggers instant funding: collectInstantWithdrawFunds pays attacker basis;
//    pendingInstantWithdraws == 1e6 (victim remainder).
// 4. attacker calls claimInstantWithdrawRequest -> paid at par.
//    BUG: instantWithdrawsRequestsByEpoch[attacker][N] and
//         instantWithdrawClaimsByEpoch[N] still include attacker's 1_000_000e6.

assertEq(strategy.instantWithdrawsRequests(attacker), 0);
assertGt(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), 0); // stale

// 5. borrower default in same epoch (stopEpoch default path), then:
//    manager calls finalizeDefault(recovered, source) -> finalizeDefaultRecovery.
//    defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[N]
//    which still counts the attacker's already-paid 1_000_000e6, and
//    _defaultPrefundedInstantReserve() adds (instantBasis - pendingInstant)
//    as phantom strategy-held backing.

uint256 basis = strategy.defaultPendingClaimBasis();
assertGt(basis, realOutstandingClaims); // inflated by ghost basis

// 6. Post-finalization: victim and LPs claim at a diluted defaultRecoveryPrice;
//    after all legit claims, strategy.defaultRecoveryReserve() > 0 with no
//    remaining claimant -> permanently locked reserve.
```

Uncertainty note: I could not fully trace `IdleCDOEpochVariant`'s `claimInstantWithdrawRequest` call path and the exact conditions under which `pendingInstantWithdraws` remains nonzero while same-epoch claims execute. If the CDO always fully funds or fully zeroes the instant bucket before any claim, the inflation window narrows to that specific sequence; the stale-state defect itself is confirmed in the code.

    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
