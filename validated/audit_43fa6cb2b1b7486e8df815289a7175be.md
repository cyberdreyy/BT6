### Title
Unbounded per-caller DON fan-out amplification via `HandleJSONRPCUserMessage` / `fanOutToNodes` lacking per-owner/per-caller quota - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`(*handler).HandleJSONRPCUserMessage` only validates that `req.ID` is non-empty, ≤200 chars, and not already active before calling `fanOutToNodes`, which sends the request to every DON member node. The only throttles present (`globalNodeRateLimiter` and `perNodeRateLimiters`) are applied exclusively in `HandleNodeMessage` on the *inbound node response* path, not on the *inbound user request* path, so any unauthenticated/unprivileged caller can generate unlimited distinct `req.ID`s and force unbounded fan-out sends to all DON nodes.

### Finding Description
`HandleJSONRPCUserMessage` (`core/services/gateway/handlers/confidentialrelay/handler.go:349-366`) performs only: empty-ID check, 200-char length check, and a duplicate-ID rejection via `newActiveRequest` (`handler.go:368-383`). It then unconditionally calls `fanOutToNodes` (`handler.go:618-652`), which spawns a goroutine per DON member and calls `h.don.SendToNode` for each one. There is no check of caller identity, subscription, workflow owner, or API credential anywhere in this path, and no rate limiter is consulted before the fan-out occurs.

The two rate limiters that exist on the `handler` struct — `globalNodeRateLimiter` and `perNodeRateLimiters` (`handler.go:183-184`) — are only read inside `HandleNodeMessage` (`handler.go:391-406`), which governs responses coming *from* DON nodes back to the gateway, not requests coming *from* users into the gateway. This is confirmed by grepping the confidentialrelay package: there is no `userRateLimiter`/`perSender` construct in this file, unlike the sibling `capabilities/v2/http_handler.go` and `http_trigger_handler.go`, which explicitly build a `userRateLimiter` keyed by workflow owner and call `checkRateLimit`/`AllowErr` before dispatching to nodes (`http_trigger_handler.go:371-396`).

The only upstream gate in `gateway.go`'s `ProcessRequest` (`gateway.go:218-292`) is the same 200-character ID length check and JSON-RPC decoding/method routing — no caller-scoped quota is applied before `HandleJSONRPCUserMessage` is invoked. Each unique `req.ID` submitted by any caller therefore becomes an independent `activeRequest` (`handler.go:368-383`) that triggers a full-DON fan-out with no cap tied to caller identity, subscription, or workflow owner.

### Impact Explanation
An unprivileged caller (any client able to reach the confidential-relay gateway method, e.g. `MethodSecretsGet`/`MethodCapabilityExec`) can submit an arbitrary volume of requests with distinct IDs, each forcing `NodeSendTimeoutSec`-bounded sends to every member of the DON. This consumes shared, finite DON node execution/send capacity (websocket send slots, node processing bandwidth) that is paid for and relied upon by other subscribers/tenants of the same DON, degrading or denying service to legitimate users — a resource-exhaustion / quota-bypass impact matching Chainlink's "Denial of Service" / unauthorized resource consumption bounty class. This is a service-availability finding rather than fund loss, key disclosure, or cross-user data exposure.

### Likelihood Explanation
Feasibility is high: no credential beyond ordinary node-API/gateway access is required, distinct `req.ID` generation is trivial (e.g., UUIDs), and the only server-side gate (200-char length, non-empty, and no duplicate ID) is easily satisfied at scale. Repeatability is limited only by the caller's own request throughput and the `activeRequests` cleanup cadence (`defaultCleanUpPeriod` = 1s, `requestTimeout` default 30s), meaning many concurrent in-flight fan-outs can be sustained continuously.

### Recommendation
Add a per-caller/per-owner rate limiter analogous to the `userRateLimiter` pattern used in `capabilities/v2/http_trigger_handler.go` (keyed by an authenticated caller/workflow-owner identity extracted from `req.Auth` or equivalent), and invoke it in `HandleJSONRPCUserMessage` before calling `fanOutToNodes`, returning a rate-limit error (mirroring `checkRateLimit`) rather than proceeding to fan out.

### Proof of Concept
Go handler-level integration test plan for `core/services/gateway/handlers/confidentialrelay/handler_test.go`:
1. Construct a `handler` via `NewHandler` with a small `donConfig.Members` list and a mocked `gwhandlers.DON` (`handlermocks.NewDON`) expecting `SendToNode` to be called for every node on every distinct request.
2. Loop N (e.g., 1000) times, each iteration constructing a `jsonrpc.Request[json.RawMessage]` with a unique `req.ID` (≤200 chars) from the same simulated caller (no distinguishing owner/auth field is even required), and call `handler.HandleJSONRPCUserMessage(ctx, req, callback)`.
3. Assert: (a) all N calls succeed without error, (b) `mockDon.SendToNode` is invoked N × len(Members) times, (c) no per-caller/per-owner limiter field exists on `handler` and no rejection occurs regardless of volume — confirming there is no cap on a single caller's aggregate fan-out consumption, unlike `globalNodeRateLimiter`/`perNodeRateLimiters` which only gate the `HandleNodeMessage` response path.
