### Title
Unbounded `getProgramAccounts`/`getTokenAccountsByOwner` full-database scan without secondary index enables RPC node DoS - (File: rpc/src/rpc.rs)

### Summary
When a validator's JSON-RPC node does not have secondary account indexes enabled (the default), `getProgramAccounts` and the related `getTokenAccountsByOwner`/`getTokenAccountsByDelegate` calls fall back to a full, unbounded iteration over every account in accounts-db, filtering by owner in-memory with no size/time cap. An attacker can create a very large number of accounts owned by an arbitrary program (including their own on-chain program) and then repeatedly issue `getProgramAccounts` calls, forcing the node to perform expensive full-table scans, degrading or DoS'ing the RPC service — the same bug class as the Canto coinswap report ("iterate through all X in a loop without limit, high resource consumption causes failure").

### Finding Description
`get_filtered_program_accounts` in `rpc/src/rpc.rs` branches on whether the `ProgramId` secondary index is configured: [1](#0-0) 

When the index is enabled, results are bounded by `scan_results_limit_bytes` and an abortable `ScanConfig`, as shown in `get_filtered_indexed_accounts`: [2](#0-1) [3](#0-2) 

But when the index is **not** enabled (the default configuration, unless `--account-index program-id` is explicitly set), the code takes the `else` branch, whose comment explicitly notes "this path does not need to provide a mb limit because we only want to support secondary indexes": [4](#0-3) 

This calls `Bank::get_filtered_program_accounts`, which delegates to `Accounts::load_by_program_with_filter`, which performs `accounts_db.scan_accounts` over **every account in the accounts index** with `ScanConfig::default()` — no byte limit, no abort mechanism: [5](#0-4) [6](#0-5) [7](#0-6) 

This is directly analogous to the Canto `k.bk.GetAllBalances` bug: an unbounded loop over a data structure whose size is influenced by an ordinary, unprivileged actor (anyone can permissionlessly create arbitrarily many accounts owned by any program, e.g. by deploying/using a program that creates many zero-cost or low-cost accounts, or by using a widely-used program such as the SPL Token program). The RPC node has no cap on how many accounts it will visit or how much memory/CPU it will spend before returning (or failing).

### Impact Explanation
Each `getProgramAccounts` call without the secondary index configured walks the entire in-memory accounts index (potentially hundreds of millions of entries on a mainnet-scale validator), allocating a `Vec<KeyedAccountSharedData>` for matches and cloning account data for every match. An attacker can:
1. Cheaply inflate the number of accounts owned by a widely-queried program (or an attacker-deployed program) to bloat the scan cost.
2. Issue concurrent `getProgramAccounts`/`getTokenAccountsByOwner` requests to force repeated full scans, consuming CPU and memory on the RPC node's blocking thread pool (`rpc_blocking_threads`), degrading service for legitimate clients or exhausting node resources (RPC crash/unresponsiveness).

This impacts the RPC-serving node's availability. It does not affect consensus or on-chain fund safety, since RPC serving is a non-consensus subsystem, but it matches the "RPC crash / ingest starvation" impact category explicitly permitted by the scan rules.

### Likelihood Explanation
Likelihood is constrained by two mitigating factors that reduce this from a clear-cut Medium/High finding:
- This is a long-documented, intentional design tradeoff in Solana/Agave: the code comment itself acknowledges the missing limit ("we only want to support secondary indexes"), and operators are expected to either enable `--account-index program-id/spl-token-owner/spl-token-mint` (which activates the bounded path via `scan_results_limit_bytes`, configurable with `--accounts-index-scan-results-limit-mb`) or disable/restrict `getProgramAccounts` on public-facing RPC endpoints.
- I could not confirm within the available index whether `getProgramAccounts` is gated behind `--full-rpc-api` (a common operator practice), which would reduce exposure on public RPC nodes; this is a known limitation of the codebase index and could not be verified with the tools available in this session.

Because this is an already-acknowledged operational tradeoff rather than a newly introduced logic bug, and default/major RPC providers commonly deploy secondary indexes or disable full RPC API for public endpoints, real-world likelihood is lower than the original Canto finding (which affected core module functionality with no operator mitigation available).

### Recommendation
- Enforce a default `scan_results_limit_bytes`/scan abort mechanism even on the non-indexed `get_filtered_program_accounts` path in `rpc/src/rpc.rs`, rather than only on the indexed path, so an operator without secondary indexes still has bounded worst-case scan cost.
- Consider adding a hard cap on the number of accounts inspected per scan (not just accumulated result size) to bound CPU time regardless of match rate.
- Document/require `--account-index` for `getProgramAccounts`-heavy deployments, and consider disabling the unindexed `getProgramAccounts`/`getTokenAccountsByOwner` fallback by default for nodes serving public traffic.

### Proof of Concept
1. Run an Agave validator/RPC node without `--account-index` flags (default configuration).
2. From an ordinary unprivileged account, deploy or use an existing program and create a very large number of accounts owned by that `program_id` (e.g., hundreds of thousands of small accounts, which is inexpensive since account creation only requires rent-exempt lamports, not privileged access).
3. Issue repeated `getProgramAccounts` JSON-RPC calls for that `program_id` against the target node — traced through:
   `rpc/src/rpc.rs::get_filtered_program_accounts` (else branch, lines 2283-2301) → `runtime/src/bank.rs::get_filtered_program_accounts` (lines 5121-5132) → `accounts-db/src/accounts.rs::load_by_program_with_filter` (lines 338-358) → `accounts-db/src/accounts_index.rs::scan_accounts` (lines 345-374).
4. Observe that each call performs a full unbounded scan with no configurable byte/time limit, consuming a blocking-thread-pool worker and CPU/memory proportional to total account count; repeating the call concurrently exhausts the RPC node's blocking thread pool and degrades service for other clients.

    pub async fn get_filtered_indexed_accounts(
        &self,
        bank: &Arc<Bank>,
        index_key: &IndexKey,
        program_id: &Pubkey,
        filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let bank = Arc::clone(bank);
        let index_key = index_key.to_owned();
        let program_id = program_id.to_owned();
        let byte_limit_for_scans = self.config.scan_results_limit_bytes;
        let mut accounts = self
            .runtime
            .spawn_blocking(move || {
                bank.get_filtered_indexed_accounts(
                    &index_key,
                    |account| {
                        // The program-id account index checks for Account owner on inclusion.
                        // However, due to the current AccountsDb implementation, an account may
                        // remain in storage as a zero-lamport AccountSharedData::Default() after
                        // being wiped and reinitialized in later updates. We include the redundant
                        // filters here to avoid returning these accounts.
                        account.owner().eq(&program_id)
                            && filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                    },
                    byte_limit_for_scans,
                )
            })
            .await
            .expect("Failed to spawn blocking task")?;
        if sort_results {
            // Avoid copying pubkeys (using Ord::cmp(a, b) silences clippy::unnecessary_sort_by).
            accounts.sort_unstable_by(|(addr_a, _), (addr_b, _)| Ord::cmp(addr_a, addr_b));
        }
        Ok(accounts)
    }

        &self,

        bank_id: BankId,
        index_key: &IndexKey,
        filter: F,
        byte_limit_for_scan: Option<usize>,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let sum = AtomicUsize::default();
        let config = ScanConfig::default().recreate_with_abort();
        let mut collector = Vec::new();
        let result = self
            .accounts_db
            .index_scan_accounts(
                ancestors,
                bank_id,
                *index_key,
                |some_account_tuple| {
                    Self::load_while_filtering(&mut collector, some_account_tuple, |account| {
                        let use_account = filter(account);
                        if use_account
                            && Self::accumulate_and_check_scan_result_size(
                                &sum,
                                account,
                                &byte_limit_for_scan,
                            )
                        {
                            // total size of results exceeds size limit, so abort scan
                            config.abort();
                        }
                        use_account
                    });
                },
                &config,
            )
            .map(|_| collector);
        Self::maybe_abort_scan(result, &config)
    }

    /// call func with every pubkey and index visible from a given set of ancestors
    pub(crate) fn scan_accounts<F>(
        &self,
        ancestors: &Ancestors,
        max_root: Slot,
        mut func: F,
        config: &ScanConfig,
    ) where
        F: FnMut(&Pubkey, (&T, Slot)),
    {
        for pubkeys in self.iter() {
            for pubkey in pubkeys {
                self.get_and_then(&pubkey, |entry| {
                    if let Some(list) = entry {
                        let list_r = &list.slot_list_read_lock();
                        if let Some(index) =
                            self.latest_slot(Some(ancestors), list_r, Some(max_root))
                        {
                            func(&pubkey, (&list_r[index].1, list_r[index].0));
                        }
                    }
                    let add_to_in_mem_cache = false;
                    (add_to_in_mem_cache, ())
                });
                if config.is_aborted() {
                    return;
                }
            }
        }
    }
