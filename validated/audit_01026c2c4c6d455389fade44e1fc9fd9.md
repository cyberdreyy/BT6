### Title
Instant-withdraw receipts keyed to a prior epoch are unclaimable after `finalizeDefaultRecovery`, and their already-funded underlyings are absorbed into the recovery reserve - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.requestInstantWithdraw` stores each user's receipt under `instantWithdrawsRequestsByEpoch[_user][epochNumber]` using the **epoch number at request time** (`contracts/strategies/idle/IdleCreditVault.sol:367-372`). `epochNumber` is later incremented inside `deposit()` whenever a stopEpoch repayment lands while the epoch is running (`IdleCreditVault.sol:607-611`). However, both the recovery-basis computation `defaultPendingClaimBasis()` (`IdleCreditVault.sol:644-649`) and the defaulted-claim path `_claimDefaultedInstantWithdrawRequest()` (`IdleCreditVault.sol:842-856`) look up instant claims **only under the finalization-time `epochNumber`/`defaultRecoveryEpoch`**. This is the same bug class as the external report: a stored per-epoch pointer goes stale when a shared counter (`epochNumber`, analogous to the locker address) advances, and the consumer keeps reading only the newest key. Any instant receipt created in epoch N whose `pendingInstantWithdraws` bucket is still non-zero when epoch N+1 defaults is silently dropped from the recovery basis: its already-collected underlying is folded into `defaultRecoveryReserve` for other claimants, and the holder's own claim reverts permanently.

### Finding Description
1. During epoch N an unprivileged lender calls `IdleCDOEpochVariant.requestWithdraw` with the instant flag, which calls `requestInstantWithdraw(_amount, _user)`. This mints a strategy-token receipt and records `instantWithdrawsRequestsByEpoch[_user][N] += _amount`, `instantWithdrawClaimsByEpoch[N] += _amount`, and `pendingInstantWithdraws += _amount` (`IdleCreditVault.sol:356-375`).
2. Epoch N stops without the CDO fully collecting the instant queue (`collectInstantWithdrawFunds` may pull less than `pendingInstantWithdraws`, `IdleCreditVault.sol:398-403`), so the claim remains partially pending. The repayment `deposit()` during `stopEpoch` bumps `epochNumber` to N+1 while `instantWithdrawClaimsByEpoch` still holds the debt under key N.
3. Epoch N+1 runs and the borrower defaults. `finalizeDefaultRecovery` computes `pendingBasis = defaultPendingClaimBasis()` = `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` — now `epochNumber == N+1`, so the user's epoch-N instant claim contributes **zero basis** (`IdleCreditVault.sol:644-649`). `_defaultPrefundedInstantReserve()` likewise uses `instantWithdrawClaimsByEpoch[epochNumber]`, so the portion of the user's claim that was already funded into the strategy is not attributed to them and is merged into `reserveAmount` (`IdleCreditVault.sol:716-723`). The final `defaultRecoveryReserve` is priced only over active LPs and other-epoch claims (`IdleCreditVault.sol:679-692`), and `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` is set true (`IdleCreditVault.sol:696`).
4. The user calls `claimInstantWithdrawRequest`. Because `defaultInstantWithdrawsFinalized` is true, `_claimDefaultedInstantWithdrawRequest` runs and reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — i.e., key N+1 — finds 0, and returns (`IdleCreditVault.sol:842-846`). Execution falls through to `instantWithdrawsRequests[_user]` (still the full amount), burns the receipt, and calls `_transferFundedClaim`, which enforces `balance - defaultRecoveryReserve >= amount` (`IdleCreditVault.sol:899-906`). The strategy's balance now equals the reserve, so the call reverts `NotAllowed()` **every time**.

The receipt's funded underlyings are permanently trapped in `defaultRecoveryReserve` and are paid out to *other* claimants via `_transferDefaultRecovery`, while the receipt holder can never clear their claim — direct theft of their funded instant withdrawal plus permanent freezing of the remainder.

### Impact Explanation
Any lender whose instant-withdraw request was only partially collected in the epoch it was created, and whose next epoch defaults, loses their entire funded claim. The loss equals `instantWithdrawsRequestsByEpoch[_user][N]` × `defaultRecoveryPrice / RECOVERY_FULL` for the unfunded share and the full funded share that was absorbed into the reserve — up to 100% of the request when recovery funds fully exist but are inaccessible. It also slightly dilutes/`reverts` accounting for other claimants only in their favor, so the harm is concentrated on the unprivileged instant requester. No privileged actor misbehaves: default, finalization, and epoch transitions are all honest manager/borrower calls.

### Likelihood Explanation
Requires: (a) an instant withdraw request in epoch N that remains pending into epoch N+1 (the code comments at `IdleCreditVault.sol:637-640` explicitly acknowledge partial instant funding at `startEpoch` is a real state), and (b) a borrower default in epoch N+1 finalized via `finalizeDefault`. Borrower defaults are the designed-for risk event of the vault, and instant withdrawals with partial coverage are a supported mode (`setInstantWithdrawParams`). Not gated by KYC beyond normal deposits; exploitable by any tranche holder. Likelihood is moderate — it needs a specific-but-ordinary epoch sequence, not attacker manipulation.

### Recommendation
- In `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, aggregate `instantWithdrawClaimsByEpoch` over *all* epochs with non-zero entries (or track a global `instantWithdrawClaimsTotal` mirroring `pendingInstantWithdraws`), instead of only `instantWithdrawClaimsByEpoch[epochNumber]`.
- In `_claimDefaultedInstantWithdrawRequest`, iterate/aggregate over every epoch bucket the user holds (or maintain a per-user list of receipt epochs, the same fix pattern already applied to `withdrawsRequestsByEpoch` vs `lastWithdrawRequest`), rather than only `defaultRecoveryEpoch`.
- As in the external report's recommendation: never let a newer state key overwrite or shadow older claimable balances; keep historical epoch buckets claimable while `instantWithdrawsRequestsByEpoch[_user][e] != 0`.

### Proof of Concept
Foundry fork PoC (scaffold against `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testInstantReceiptFromPriorEpochIsUnclaimableAfterDefault() external {
    // enable instant withdrawals with small liquidity so the queue is only partially covered
    uint256 delay = cdoEpoch.instantWithdrawDelay();
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(delay, 1000, false); // ~10% instant liquidity

    address user = makeAddr('instant-user');
    uint256 amount = 100_000 * ONE_SCALE;
    _depositWithUser(user, amount, true);              // deposit during buffer, epoch N
    _startEpochAndCheckPrices(0);

    // epoch N: user requests an instant withdraw larger than instant liquidity
    vm.prank(user);
    cdoEpoch.requestInstantWithdraw(amount / 2, address(AAtranche));
    // strategy bookkeeping: receipt keyed under epoch N
    assertGt(strategy.instantWithdrawsRequestsByEpoch(user, strategy.epochNumber()), 0);
    assertGt(strategy.pendingInstantWithdraws(), 0);    // not fully funded

    // stop epoch N: borrower repays principal+interest; deposit() bumps epochNumber to N+1
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);
    assertEq(strategy.epochNumber(), /*N+1*/ strategy.instantWithdrawsRequestsByEpoch(user, /*N*/) != 0 ? strategy.epochNumber() : 0);

    // epoch N+1: new deposits, epoch runs, borrower defaults
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(1);
    deal(defaultUnderlying, borrower, 0, true);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);
    assertTrue(cdoEpoch.defaulted());

    // manager finalizes recovery; user's epoch-N instant basis is silently excluded
    uint256 recovered = strategy.balanceOf(address(cdoEpoch)) / 2;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // user's claim reverts forever: defaulted lookup uses defaultRecoveryEpoch == N+1 (== 0 for them),
    // then _transferFundedClaim reverts because balance == defaultRecoveryReserve
    vm.prank(user);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimInstantWithdrawRequest();
    // and their previously collected underlyings remain locked inside defaultRecoveryReserve,
    // later consumed by other claimants via _transferDefaultRecovery.
}
```

Note: exact helper names/amounts follow the existing `test/foundry/IdleCreditVault.t.sol` harness (`_depositWithUser`, `_startEpochAndCheckPrices`, `_expectedFundsEndEpoch`, `finalizeDefault`); the key assertions are that `instantWithdrawsRequestsByEpoch[user][N]` stays non-zero while `defaultRecoveryEpoch == N+1`, and that `claimInstantWithdrawRequest` permanently reverts via the `_transferFundedClaim` reserve guard.

*Uncertainty: I could not read `IdleCDOEpochVariant.sol`'s instant-collection path (`getInstantWithdrawFunds`/`collectInstantWithdrawFunds` call sites) before the iteration limit, so the precise trigger for `pendingInstantWithdraws` surviving an epoch boundary (partial collection at `startEpoch` vs `stopEpoch`) is inferred from `IdleCreditVault.sol:637-640` comments, which document exactly that partial-funding state. If the CDO in fact always fully settles `pendingInstantWithdraws` before `epochNumber` can advance, the finding reduces to the narrower case where collection is partial — which the code explicitly allows.*
