### Title
Redeem requests routed through `solveRequestsVault` send tokens directly to an attacker-chosen `receiver` without fallback, letting a blacklisted/reverting receiver permanently DoS that user's redeem and grief the whole solve batch - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.requestRedeem` lets any user pick an arbitrary `receiver` for the redeemed tokens, and `_solveRedeemVaultAutoPrice` / `_solveRedeemVaultFixedPrice` (invoked from `solveRequestsVault`) pay that receiver via a bare `token.safeTransfer(request.receiver, ...)` with no fallback. This is the exact analog of the reported issue: a USDC/USDT-blacklisted (or reverting) recipient makes the transfer revert, which reverts the entire `solveRequestsVault` batch and blocks the user's own units from ever being redeemed through that path.

### Finding Description
`requestRedeem` (v3/src/core/ProvisionerV2.sol:812-857) escrows the caller's vault units and stores a hash keyed on an arbitrary `receiver` chosen by the requester, with no check that `receiver` can actually accept the payout token. [1](#0-0) 

When an authorized solver services this request via `solveRequestsVault` → `_solveRequestsVault` → `_solveRedeemVaultAutoPrice`/`_solveRedeemVaultFixedPrice`, the vault is exited and the underlying token is sent straight to `request.receiver` with a plain `safeTransfer`, no try/fallback: [2](#0-1) [3](#0-2) 

This is inconsistent with every other payout path in the same file, which explicitly guards against a reverting/blacklisted receiver by falling back to the original requester: [4](#0-3) 

Because `_solveRequestsVault` processes an entire array of requests in a single loop and only reverts explicitly on the pre-solve submit, an unguarded `safeTransfer` failure for one poisoned request bubbles up and reverts the whole call: [5](#0-4) 

### Impact Explanation
If `request.receiver` is or becomes blacklisted by a centralized stablecoin (USDC/USDT) - which the requester fully controls at request-creation time - every solver attempt to include that request in `solveRequestsVault` reverts. The requester's own escrowed vault units become permanently unredeemable via the vault-solved path (the same broken invariant as the original report: "the borrower/user cannot complete the exit because the payout transfer to a blacklisted address reverts"). Additionally, because many requests are batched in one `solveRequestsVault` call, a single poisoned request can revert the payouts for every other honest user bundled in that same transaction until the solver identifies and excludes it, causing a temporary freeze of other users' funds/yield — a live Immunefi Medium-severity impact (temporary freezing of user funds).

### Likelihood Explanation
Fully triggerable by an ordinary user: call `requestRedeem` with `receiver` set to an address they know is or will be blacklisted (or a contract designed to revert on receipt), no privileged role required. The griefing effect on batched requests only additionally requires the normal, non-malicious operation of an authorized solver batching multiple pending requests together, which is the intended/expected usage pattern.

### Recommendation
Route the token payout in `_solveRedeemVaultAutoPrice` and `_solveRedeemVaultFixedPrice` through the same `_transferWithFallback` (or an equivalent try/catch with fallback to `request.user`) used elsewhere in `ProvisionerV2.sol`, so a reverting/blacklisted `receiver` cannot block the user's own redeem completion nor other bundled solves.

### Proof of Concept
1. Deploy `ProvisionerV2` + `MultiDepositorVault` with a mock ERC20 token that implements a `blacklist(address)` function causing `transfer`/`transferFrom` to revert for blacklisted addresses (mimicking USDC).
2. User A calls `requestRedeem(token, unitsIn, minTokensOut, tip, deadline, maxPriceAge, isFixedPrice=true, receiver=addrX)` where `addrX` is an address User A controls.
3. Before the deadline, blacklist `addrX` on the mock token.
4. Solver calls `solveRequestsVault(token, [requestA, requestB, ...])` bundling User A's request with User B's legitimate redeem request.
5. Assert the whole transaction reverts (`token.safeTransfer` to blacklisted `addrX` reverts), so User B's otherwise-valid redeem is also blocked.
6. Assert that even in a batch containing only User A's request, every subsequent call to `solveRequestsVault` for that request reverts, leaving User A's escrowed units permanently stuck (unless/until the deadline passes and self-cancel `_transferWithFallback` handles it, which only works if `receiver != requester`).

    function _solveRequestsVault(IERC20 token, RequestV2[] calldata requests) internal {
        // Requirements: vault is not paused in the priceAndFeeCalculator
        require(!PRICE_FEE_CALCULATOR.isVaultPaused(MULTI_DEPOSITOR_VAULT), Aera__PriceAndFeeCalculatorVaultPaused());

        // Interactions: get price age
        uint256 priceAge = block.timestamp - PRICE_FEE_CALCULATOR.getVaultPriceTimestamp(MULTI_DEPOSITOR_VAULT);

        uint256 solverTip;
        RequestV2 calldata request;

        uint256 length = requests.length;
        TokenDetailsV2 memory tokenDetails = tokensDetails[token];
        bool depositsExist;
        for (uint256 i = 0; i < length; i++) {
            request = requests[i];
            if (_isRequestTypeDeposit(request.requestType)) {
                // Requirements: async deposit is enabled
                if (!tokenDetails.asyncDepositEnabled) {
                    // Log async deposit disabled event
                    emit AsyncDepositDisabled(i);
                    continue;
                }

                if (!depositsExist) {
                    depositsExist = true;
                    token.forceApprove(MULTI_DEPOSITOR_VAULT, type(uint256).max);
                }

                if (_isRequestTypeAutoPrice(request.requestType)) {
                    // Requirements + Effects + Interactions: solve auto price deposit
                    solverTip += _solveDepositVaultAutoPrice(
                        token, tokenDetails.asyncDepositMultiplier, request, priceAge, i
                    );
                } else {
                    // Requirements + Effects + Interactions: solve fixed price deposit
                    solverTip += _solveDepositVaultFixedPrice(
                        token, tokenDetails.asyncDepositMultiplier, request, priceAge, i
                    );
                }
            } else {
                // Requirements: async redeem is enabled
                if (!tokenDetails.asyncRedeemEnabled) {
                    // Log async redeem disabled event
                    emit AsyncRedeemDisabled(i);
                    continue;
                }

                if (_isRequestTypeAutoPrice(request.requestType)) {
                    // Requirements + Effects + Interactions: solve auto price redeem
                    solverTip += _solveRedeemVaultAutoPrice(
                        token, tokenDetails.asyncRedeemMultiplier, request, priceAge, i
                    );
                } else {
                    // Requirements + Effects + Interactions: solve fixed price redeem
                    solverTip += _solveRedeemVaultFixedPrice(
                        token, tokenDetails.asyncRedeemMultiplier, request, priceAge, i
                    );
                }
            }
        }

    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
    }
