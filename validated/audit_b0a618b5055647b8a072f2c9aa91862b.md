### Title
Attacker can block `stopEpoch` indefinitely by exhausting the external ERC4626 vault's underlying liquidity, freezing all LP funds - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The external-report bug class is "reliance on a vulnerable third-party dependency." The credit-vault analog is `ProgrammableBorrower`'s hard dependency on the live liquidity of its configured ERC4626 vault (`vault`), which it does not control. `onStopEpoch` decides whether the vault can cover the recall using the valuation view `convertToAssets` (`_currentVaultAssets`), but then executes a real `vault.withdraw`. For vaults like MetaMorpho/ERC4626 lenders, `convertToAssets` counts assets allocated to underlying markets, while `withdraw` reverts when those markets have no free liquidity. Any unprivileged actor who can borrow from those underlying markets can make every `stopEpoch` revert with `StopEpochVaultLiquidityUnavailable`, freezing the pool. Even the privileged escape hatch `emergencyExitVault` calls `vault.redeem`, which fails for the same reason, so LP funds are stuck for as long as the attacker keeps the markets drained.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch`, the programmable-borrower path calls `IProgrammableBorrower(_borrower()).onStopEpoch(...)` and relies on hook reverts bubbling up ("Hook reverts bubble so transient ERC4626 liquidity failures can be retried") [1](#0-0) .

Inside `ProgrammableBorrower.onStopEpoch`, coverage is checked with the share valuation (`shortfall > _currentVaultAssets()`), but settlement is a real `vault.withdraw(shortfall, ...)` wrapped in `try/catch` that reverts `StopEpochVaultLiquidityUnavailable` [2](#0-1) . `_currentVaultAssets` is `vault.convertToAssets(shares)` [3](#0-2) .

For MetaMorpho-style vaults (the fork tests use `STEAKHOUSE_USDC`), `convertToAssets` values the position across allocated markets, but `withdraw`/`redeem` only succeeds up to currently idle liquidity in those markets. An attacker can borrow available liquidity from the underlying Morpho markets (or deposit/withdraw in a way that leaves the withdrawal path illiquid), so `convertToAssets` still reports full coverage while `withdraw` reverts. Because the revert propagates out of `onStopEpoch`, `_stopEpoch` aborts entirely — `isEpochRunning` stays true, no default is triggered (the `try this.getFundsFromBorrower` catch is never reached since the failure happens earlier), and the epoch cannot be stopped [1](#0-0) .

The emergency unwind does not help: `emergencyExitVault` calls `vault.redeem`, which requires the same underlying liquidity [4](#0-3) . `rescueTokens` on vault shares only moves shares off the contract, which would strand the position rather than free it. Since `setVault` requires `vault.balanceOf(address(this)) == 0`, the manager cannot swap the integration either [5](#0-4) .

### Impact Explanation
All LP funds parked through the programmable borrower are frozen for the duration of the liquidity squeeze: no `stopEpoch`, no interest settlement, and pending withdraw requests cannot be funded. Withdrawal requestors and tranche holders cannot exit because the epoch state machine never advances. This is temporary freezing of user funds with real fund impact, sustained at the attacker's cost of borrow interest on the underlying markets — for a large pool, keeping a MetaMorpho vault illiquid is cheap relative to the frozen TVL. The same condition also blocks borrower repayments being re-deployed and pool closure (`_interest == 1` path also calls `onStopEpoch`).

### Likelihood Explanation
Attacker requirements are minimal: any EOA able to interact with the underlying lending markets (e.g., a Morpho borrower posting collateral). No privileged role is needed, no timing around honest-role calls beyond acting before epoch end. MetaMorpho vaults routinely experience high-utilization periods even without an attacker, so the trigger can also occur organically; an attacker can manufacture it deterministically at epoch end and unwind after the griefing window. The revert-bubbles design intentionally makes this retryable, so the vulnerability is the absence of any fallback path (partial withdraw, redeem of only-liquid portion, or forced default after repeated failures).

### Recommendation
- In `onStopEpoch`, attempt `vault.withdraw` for the maximum withdrawable amount (`vault.maxWithdraw(address(this))`) instead of the full `shortfall`, and only revert when truly nothing can be freed; alternatively return a status that lets IdleCDO count a verified shortfall as a default instead of reverting.
- Add a bounded retry/grace mechanism: after N failed stops or a timeout past `epochEndDate`, allow the manager to route the shortfall through `_handleBorrowerDefault` or a degraded stop so the epoch state machine cannot be wedged forever.
- Make `emergencyExitVault` use `vault.maxRedeem`/`maxWithdraw` and exit the liquid portion rather than reverting on the full amount.
- Treat `convertToAssets` as an upper bound only; use `maxWithdraw` for coverage checks since it accounts for live market liquidity.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "./ProgrammableBorrowerCreditVault.t.sol"; // existing fork harness (STEAKHOUSE_USDC, Morpho markets)

contract StopEpochLiquidityGriefPoC is ProgrammableBorrowerCreditVaultTest {
    function testAttackerFreezesStopEpochByDrainingVaultLiquidity() external {
        uint256 amount = 10_000 * oneScale;

        vm.prank(owner);
        cdoEpoch.setIsInterestMinted(true);
        idleCDO.depositAA(amount);
        _startEpochAndCheckPrices(0);

        // --- Attacker step: any EOA drains free liquidity from the Morpho markets
        // backing STEAKHOUSE_USDC (e.g., via Morpho borrow with posted collateral),
        // leaving the vault's markets at ~100% utilization.
        _drainMorphoLiquidity(); // helper: whitelisted markets' borrow() until idle liquidity ~ 0

        // Vault still *values* the position fully: coverage check passes.
        uint256 owed = strategy.pendingWithdraws(); // amountRequired leg
        assertGt(programmableBorrower.totalUnderlying(), 0);

        vm.warp(cdoEpoch.epochEndDate() + 1);

        // --- stopEpoch reverts: convertToAssets covers the shortfall, withdraw() reverts,
        // catch -> StopEpochVaultLiquidityUnavailable bubbles out of onStopEpoch.
        vm.prank(manager);
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        cdoEpoch.stopEpoch(0, 0);

        // Epoch is still running; nothing can progress.
        assertTrue(cdoEpoch.isEpochRunning());
        assertFalse(cdoEpoch.defaulted());

        // --- Privileged escape also fails: redeem needs the same market liquidity.
        vm.expectRevert(); // vault.redeem reverts on illiquid markets
        programmableBorrower.emergencyExitVault(0);

        // --- setVault fallback is gated on a zero share balance -> cannot migrate.
        vm.expectRevert(NotAllowed.selector);
        programmableBorrower.setVault(ANOTHER_USDC_VAULT);

        // Funds remain frozen until the attacker (or market) restores liquidity.
    }
}
```

The PoC runs on the existing mainnet-fork harness in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`, which already deploys `ProgrammableBorrower` against the live `STEAKHOUSE_USDC` MetaMorpho vault; `_drainMorphoLiquidity` only needs to borrow out the idle assets of the vault's listed markets, which any unprivileged Morpho user can do.

    _checkOnlyOwnerOrManager();
    if (_shares == 0) {
      _shares = vault.balanceOf(address(this));
    }
