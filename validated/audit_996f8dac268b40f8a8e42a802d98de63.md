### Title
No allowlist/subscriber authorization check in `HandleLegacyUserMessage` — any address with a valid ECDSA signature is forwarded to all DON nodes - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`(h *handler).HandleLegacyUserMessage` validates message structure, payload freshness, and method name, but performs no check that `msg.Body.Sender` (the ECDSA-recovered signer) belongs to an allowlisted/subscribed user for the DON, as explicitly flagged by the `// TODO: apply allowlist and rate-limiting here` comment. Any party who can generate an ECDSA keypair and sign a well-formed `web_api_trigger` message can have it forwarded to every DON member via `don.SendToNode`.

### Finding Description
`msg.Body.Sender` is populated purely from cryptographic signature recovery in `Message.Validate()` → `ExtractSigner()` [1](#0-0) , which only proves that *some* private key produced the signature — it carries no notion of identity being a registered/subscribed user of the DON. `HandleLegacyUserMessage` then checks: payload decoding, `Timestamp != 0`, staleness window, and `Method == MethodWebAPITrigger` [2](#0-1) . Immediately after these checks, at the exact point marked `// TODO: apply allowlist and rate-limiting here`, the code proceeds straight to converting the message to a JSON-RPC request and looping over `h.donConfig.Members`, calling `don.SendToNode` for every member with no sender-authorization gate [3](#0-2) . There is no lookup of `msg.Body.Sender` against any subscriber/allowlist data structure (e.g., no `h.donConfig` field or map queried by sender address) anywhere in this function or its call path.

### Impact Explanation
This matches Chainlink's "allowlist/quota bypass" and "unauthorized job run" bounty impact class: any unprivileged party capable of generating an ECDSA keypair (trivial, no credentials needed) can have arbitrary trigger messages relayed to and processed by every node in the DON, consuming node compute/HTTP-egress resources (via the corresponding outgoing HTTP request flow in `handleWebAPIOutgoingMessage`) and bypassing whatever per-user quota/allowlist model the product intends to enforce at this layer.

### Likelihood Explanation
Trivial and fully repeatable: no operator, admin, or node compromise is required — an attacker only needs to generate a standard secp256k1 keypair, construct a `Message` with a valid `web_api_trigger` payload and non-stale timestamp, sign it per `GetRawMessageBody`, and submit it through the gateway's user-facing entry point that ultimately calls `HandleLegacyUserMessage`. The code path is unconditionally reached for any structurally valid, freshly-signed message, and the missing gate is explicitly acknowledged by the TODO comment in the source itself.

### Recommendation
Before forwarding to `don.SendToNode`, look up `msg.Body.Sender` against a DON-configured allowlist/subscriber list (e.g., derived from `h.donConfig` or an external subscription registry) and reject unauthorized senders with `api.UnauthorizedError` (or similar), and apply per-sender rate-limiting analogous to `h.nodeRateLimiter` but keyed on `msg.Body.Sender`.

### Proof of Concept
Go unit test plan for `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` via `NewHandler` with a `donConfig` containing several `Members` and a mock `handlers.DON` (e.g., using the existing mocks package) that records calls to `SendToNode`.
2. Generate a fresh, random ECDSA keypair using `crypto.GenerateKey()` (go-ethereum) — not derived from any configured/allowlisted DON key or existing subscriber.
3. Build a `webapicap.TriggerRequestPayload` with `Timestamp = uint32(time.Now().Unix())` and marshal it into `msg.Body.Payload`; set `Method = MethodWebAPITrigger`, a valid `MessageId`, and `DonId` matching `donConfig.DonId`.
4. Call `msg.Sign(randomPrivateKey)` to populate `Signature` and `Body.Sender` with the random signer's address.
5. Call `h.HandleLegacyUserMessage(ctx, msg, mockCallback)`.
6. Assert: (a) no error/unauthorized response is returned via `callback.SendResponse` with an authorization-related error code, and (b) the mock DON's `SendToNode` was invoked once per member in `donConfig.Members`, proving the message was forwarded to the entire DON despite the sender never having been allowlisted or subscribed anywhere in the test setup.
