### Title
ProgrammableBorrower deposits LP funds into the ERC4626 vault with no minimum-shares (slippage) check, allowing a share-price manipulation/donation attack — (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower._depositToVault()` calls `vault.deposit(_assetAmount, address(this))` and never validates the number of shares returned. This is the credit-vault analog of "hardcoded slippage = 0": just as a swap with `amountOutMinimum: 0` accepts any output, the vault deposit accepts any share amount. Any unprivileged user of the vault (a permitted attacker class — "a user of the programmable borrower's ERC4626 vault") can inflate the vault's assets-per-share (direct underlying donation / inflation-style share manipulation, or sandwiching the deposit via MEV) so the deposit mints far fewer shares than the deposited assets are worth. The loss is then realized inside the epoch accounting as a vault loss and socialized to tranche holders BB-first.

### Finding Description
In `contracts/strategies/idle/ProgrammableBorrower.sol`:

```solidity
function _depositToVault(uint256 _assetAmount, uint256 _principalAssets) internal {
    if (_assetAmount == 0) return;
    uint256 shares = vault.deposit(_assetAmount, address(this)); // L380: no minShares check
    ...
}
```

`_depositToVault` is invoked from two externally reachable paths:

1. `onStartEpoch(uint256)` (L216) — callable only by the CDO, but triggered inside `IdleCDOEpochVariant.startEpoch`, which is a public/keeper transaction. An attacker can front-run it: donate underlying directly to the ERC4626 vault to push `pricePerShare` up, so `vault.deposit` mints shares worth less than `_assetAmount`.
2. `_repay(uint256)` (L499) — parks repaid funds back into the vault while an epoch is active; same sandwich exposure around the honest borrower's repay transaction.

Crucially, `onStartEpoch` snapshots `epochStartVaultAssets` from the **pre-deposit** asset value (L214–L219):

```solidity
uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets;
_depositToVault(underlyingToken.balanceOf(address(this)), 0);
epochStartVaultAssets = startAssets;
```

So the shares lost to the manipulation are immediately registered as a vault loss: `_vaultNetInterest()` (L337–L347) compares `_currentVaultAssets() + epochWithdrawnFromVault` against `epochStartVaultAssets + epochDepositedToVault`, and the shortfall becomes `loss`. That loss flows into `totalInterestDueNow()` and at `stopEpoch` reduces realized interest / crystallizes a NAV loss, which `IdleCDOCreditVault._updateAccounting`/`IdleCDOEpochVariant` applies BB-first to tranche holders. The attacker, holding pre-existing vault shares, redeems them at the inflated price and captures most of the difference.

No existing guard prevents this: there is no `minSharesOut` parameter anywhere in `deposit`/`repay`/`onStartEpoch`, and `vault.deposit`/`vault.redeem`/`vault.withdraw` return values are only used for events/accounting, never validated against a floor. `onStopEpoch`'s `vault.withdraw(shortfall,...)` is an exact-assets call so it is not affected; only the deposit side is.

### Impact Explanation
Direct theft of LP funds. In the worst case for a vault without virtual-share (decimals-offset) protection, a donation attack costs the attacker roughly the donated amount but they recover it plus a fraction of the victim deposit as a shareholder; the victim deposit can lose up to ~50% of its value in the classic first-deposit/donation construction, and proportionally less when the attacker must hold a larger existing share position. The quantified loss equals `depositedAssets - sharesReceived * postDepositPricePerShare`, borne by AA/BB tranche holders as a vault loss (BB absorbs first). This is "direct theft / insolvency" under the acceptance criteria, not a depeg or oracle issue — the vault price is manipulated by an on-chain transaction the attacker controls.

### Likelihood Explanation
Low-to-medium. Exploitation requires: (a) the configured ERC4626 vault to lack effective share-inflation protection (e.g., no virtual shares/offset — MetaMorpho-style vaults mitigate classic inflation, but the owner can `setVault` to any ERC4626, and sandwich/PVG manipulation does not require first-depositor); (b) the attacker to hold or mint vault shares and front-run `startEpoch` or a borrower `repay` — feasible via public mempool/MEV since `startEpoch` is a keeper transaction whose timing (epochEndDate/buffer expiry) is predictable. Privileged roles remain honest; the attacker is purely an external vault user.

### Recommendation
Add a slippage floor to vault deposits, mirroring the `amountOutMinimum` fix: e.g., compute `expectedShares = vault.convertToShares(_assetAmount)` (or accept a `minShares` parameter through `onStartEpoch`/`repay`) and `require(shares >= minExpected * (1 - maxSlippage))`. Equivalently, validate `vault.convertToAssets(shares) >= _assetAmount * (FULL_ALLOC - tolerance) / FULL_ALLOC` after the deposit and revert otherwise. Optionally preview with `previewDeposit` and bound the deviation.

### Proof of Concept
Reproducible on a Foundry fork using the harness in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`. Use a vault without inflation protection (the file's `MockStopEpochLiquidityVault` at L24–L60 models exactly this: `shares = assets * supply / assetsBefore` with no offset).

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;

// Setup identical to _setUpProgrammableBorrowerCreditVault but with
// MockStopEpochLiquidityVault as the ERC4626 vault.

function testDepositToVaultShareInflation() external {
    uint256 lpDeposit = 100_000 * oneScale;

    // LP deposits into AA tranche (funds sit on ProgrammableBorrower during buffer)
    idleCDO.depositAA(lpDeposit);

    // Attacker seeds the vault and becomes a shareholder
    deal(USDC, attacker, 1_000_000 * oneScale);
    vm.startPrank(attacker);
    underlying.approve(address(vault), type(uint256).max);
    vault.deposit(1e6, attacker); // mint initial shares
    // Inflate pricePerShare via direct donation (unprotected ERC4626)
    underlying.transfer(address(vault), donation); // e.g. 100k USDC
    vm.stopPrank();

    uint256 sharesBefore = vault.balanceOf(address(programmableBorrower));
    uint256 expectedShares = vault.convertToShares(lpDeposit); // pre-inflation value

    // Honest manager starts the epoch -> _depositToVault(lpDeposit) with no min check
    _startEpochAndCheckPrices(0);

    uint256 sharesAfter = vault.balanceOf(address(programmableBorrower));
    uint256 mintedShares = sharesAfter - sharesBefore;

    // mintedShares << expectedShares: deposit accepted arbitrary share output
    assertLt(mintedShares, expectedShares / 2);

    // Attacker redeems at inflated price and profits
    vm.prank(attacker);
    vault.redeem(vault.balanceOf(attacker), attacker, attacker);
    assertGt(underlying.balanceOf(attacker), 1_000_000 * oneScale + donation * 9 / 10);

    // Loss is socialized to LPs: vaultNetInterest reports it, stopEpoch crystallizes it
    (, uint256 vaultLoss) = ... // _vaultNetInterest via totalInterestDueNow
    assertGt(vaultLoss, 0); // reduces realized interest -> BB-first NAV loss
}
```

Key assertion: `vault.deposit` at `ProgrammableBorrower.sol:380` returns `shares` that is never checked against any minimum, so the minted share count is arbitrarily low after the attacker's donation, and the resulting deficit is recorded as a vault loss borne by tranche holders.
