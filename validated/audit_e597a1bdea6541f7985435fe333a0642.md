### Title
Multisig confirmations from removed members still count toward execution threshold, allowing requests to execute below the live member quorum - (File: `multisig2/src/lib.rs`)

### Summary
`confirm()` tallies confirmations recorded in the `confirmations: LookupMap<RequestId, HashSet<String>>` set against `num_confirmations` [1](#0-0) . When a member is removed via `delete_member`, the code only purges pending requests that were *originally submitted* by that member, and does not remove that member's stale confirmations recorded on requests submitted by *other* members [2](#0-1) . This breaks the intended binding: `confirmations counted == confirmations from currently live members`.

### Finding Description
`delete_member` filters `self.requests` by `r.member == member` (the account that originally added the request) and removes only those requests, then removes the member from `self.members` and (if key-based) revokes the access key [3](#0-2) . It does not scan `self.confirmations` for entries containing the removed member's identity string on requests added by *other* members.

Consequently, if member `M` confirms a pending request `R` (added by member `A`, not `M`), and `M` is later removed from the multisig via a separate `DeleteMember` request, `R`'s `confirmations` set still contains `M`'s string identity. When live members subsequently call `confirm(R)`, the check `confirmations.len() as u32 + 1 >= self.num_confirmations` at [4](#0-3)  counts `M`'s stale confirmation toward the threshold, even though `M` is no longer a member and could not confirm again. This lets a request execute (e.g., a `Transfer` action moving NEAR out of the contract, per `execute_request` at [5](#0-4) ) with fewer *live* confirmations than `num_confirmations` requires — the equality `confirmations counted == live member confirmations` is violated.

This is the "confirmations counted versus live members" custody-binding class explicitly called out as in-scope, and it is structurally analogous to the external report's bug class: a redemption/threshold check validated against stale recorded state rather than the actual current entitlement (current membership), letting an unprivileged party (any remaining member coordinating with the fact that a removed member's old confirmation still counts) obtain execution of a request that should require more live confirmations.

### Impact Explanation
This is Critical impact per the rules: "a multisig request executed below threshold." A `Transfer` action can move NEAR held by the multisig account to any receiver with fewer genuinely live confirming members than `num_confirmations` mandates, effectively lowering the security threshold of the multisig without any member's key compromise — only requires that a member confirmed before being removed, and the request survives to be executed later with the stale confirmation retained.

### Likelihood Explanation
Requires no privileged actor beyond members who are already entitled to call `confirm`/`add_request`/`DeleteMember` (standard multisig operation flow: membership rotation is expected and routine). No attacker needs to be the foundation, an owner, or exploit a redeploy — this occurs through the normal lifecycle of adding a request, confirming it partially, then rotating out a confirming member before the request reaches quorum, and continuing to confirm it afterward. The order-of-operations (confirm-then-remove, versus remove-then-confirm) is plausible in normal multisig usage (e.g. member offboarding while requests are in flight).

### Recommendation
When removing a member in `delete_member`, iterate over all pending requests' `confirmations` sets and strip the departing member's identity string from any set that contains it (not just requests where `r.member == member`). Alternatively, validate at `confirm()` time that every entry in the stored `confirmations` set still belongs to a current member of `self.members`, recomputing the effective count of live confirmations before comparing against `num_confirmations`.

### Proof of Concept
Conceptual sequence (not runnable without a full test harness, but demonstrates the state-machine flaw in `multisig2/src/lib.rs`):
1. Deploy `MultiSigContract::new(members = [A, B, M], num_confirmations = 3)`.
2. `A` calls `add_request(Transfer{amount})` → `request_id`.
3. `M` calls `confirm(request_id)` → `confirmations = {M}` (1/3), request not yet executed (see the `confirm` logic at [6](#0-5) ).
4. Members execute a separate, already-confirmed `DeleteMember{member: M}` request → `delete_member` removes `M` from `self.members` and only purges requests where `r.member == M` (i.e., requests submitted by `M`); the pending transfer request submitted by `A` is untouched, and its `confirmations` set still contains `M` [2](#0-1) .
5. `B` calls `confirm(request_id)` → `confirmations.len() (1, stale M) + 1 (B) = 2`, still below 3, so it adds `B` → `confirmations = {M, B}` (2 counted, but only 1 live member, `B`, has actually confirmed).
6. Any remaining live member (e.g., `A`, who originally submitted, using `add_request_and_confirm` style or a fresh confirm call) calls `confirm(request_id)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request` fires the `Transfer`, even though only 2 live members (`B` and the confirmer) ever genuinely confirmed against a nominal 3-of-3 policy — `M`'s stale confirmation was silently counted.

This is a structural code-path issue verifiable directly from `delete_member`'s scope-limited request cleanup at [7](#0-6)  combined with `confirm`'s unconditional trust in the stored `confirmations` set size at [8](#0-7) ; I did not have access to a live test runner to execute this sequence end-to-end, so this should be validated with an integration test before remediation.

    fn execute_request(&mut self, request: MultiSigRequest) -> PromiseOrValue<bool> {
        let mut promise = Promise::new(request.receiver_id.clone());
        let receiver_id = request.receiver_id.clone();
        let num_actions = request.actions.len();
        for action in request.actions {
            promise = match action {
                MultiSigRequestAction::Transfer { amount } => promise.transfer(amount.into()),
                MultiSigRequestAction::CreateAccount => promise.create_account(),
                MultiSigRequestAction::DeployContract { code } => {
                    promise.deploy_contract(code.into())
                }
                MultiSigRequestAction::AddMember { member } => {
                    self.assert_self_request(receiver_id.clone());
                    self.add_member(promise, member)
                }
                MultiSigRequestAction::DeleteMember { member } => {
                    self.assert_self_request(receiver_id.clone());
                    self.delete_member(promise, member)
                }
                MultiSigRequestAction::AddKey {
                    public_key,
                    permission,
                } => {
                    self.assert_self_request(receiver_id.clone());
                    if let Some(permission) = permission {
                        promise.add_access_key(
                            public_key.into(),
                            permission
                                .allowance
                                .map(|x| x.into())
                                .unwrap_or(DEFAULT_ALLOWANCE),
                            permission.receiver_id,
                            permission.method_names.join(","),
                        )
                    } else {
                        // wallet UI should warn user if receiver_id == env::current_account_id(), adding FAK will render multisig useless
                        promise.add_full_access_key(public_key.into())
                    }
                }
                MultiSigRequestAction::FunctionCall {
                    method_name,
                    args,
                    deposit,
                    gas,
                } => promise.function_call(
                    method_name,
                    args.into(),
                    deposit.into(),
                    Gas::from(gas.0),
                ),
                // the following methods must be a single action
                MultiSigRequestAction::SetNumConfirmations { num_confirmations } => {
                    self.assert_one_action_only(receiver_id, num_actions);
                    self.num_confirmations = num_confirmations;
                    return PromiseOrValue::Value(true);
                }
                MultiSigRequestAction::SetActiveRequestsLimit {
                    active_requests_limit,
                } => {
                    self.assert_one_action_only(receiver_id, num_actions);
                    self.active_requests_limit = active_requests_limit;
                    return PromiseOrValue::Value(true);
                }
            };
        }
        promise.into()

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
