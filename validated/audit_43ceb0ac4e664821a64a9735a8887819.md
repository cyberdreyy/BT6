### Title
Builder withdrawal payload commits the uncapped requested amount while `apply_withdrawals` only debits the capped available balance, creating unbacked Gwei paid to `fee_recipient` — (`specs/gloas/beacon-chain.md`)

### Summary
`get_builder_withdrawals` builds `Withdrawal` records for `state.builder_pending_withdrawals` using the raw *requested* `amount` field, with no check against the builder's current `balance`. That uncapped amount is what gets committed into `state.payload_expected_withdrawals`, which the execution layer is contractually bound to pay in full. However, `apply_withdrawals` only debits the builder's CL-side `balance` by `min(withdrawal.amount, builder_balance)`. This is the same class of bug as the reported `KangarooVault.removeCollateral` finding: a storage/bookkeeping decrement (`builder.balance -= min(...)`) is decoupled from the actual value that is promised/paid out (the full committed `withdrawal.amount` in the payload), breaking the equality between what is subtracted from CL accounting and what is actually transferred by the EL.

### Finding Description
`get_builder_withdrawals` copies the pending withdrawal's requested amount verbatim into the outgoing `Withdrawal`: [1](#0-0) 

This list becomes `state.payload_expected_withdrawals`, and the execution layer is required to honor these withdrawals exactly as committed (per the spec note on `process_withdrawals`): [2](#0-1) 

But the CL-side balance debit in `apply_withdrawals` is capped to the builder's *current* available balance, using `min()`: [3](#0-2) 

The requested `amount` on a `BuilderPendingWithdrawal` is never validated against `builder.balance` at either enqueue time or at withdrawal-construction time inside `get_builder_withdrawals`. If a builder's balance is insufficient to cover the requested amount — either because it was already insufficient when queued, or because it was depleted by an earlier withdrawal processed within the same call to `apply_withdrawals` (multiple pending withdrawals for the same builder, as shown by `test_duplicate_builder_index_in_pending_withdrawals`) — the `Withdrawal.amount` committed to the execution layer remains the full, uncapped requested amount, while the CL balance decrease is silently capped at zero. The gap between "amount promised to `fee_recipient` on the EL" and "amount actually deducted from the builder's staked balance on the CL" is Gwei that is created without any corresponding CL-side backing, and paid to an address (`fee_recipient`) that has no entitlement to more than the builder's real balance.

This exactly mirrors the reported Solidity bug: `removeCollateral` decremented `positionData.totalCollateral` (bookkeeping) but the actual value movement (the amount ultimately released via `Exchange`/`ShortCollateral`) was governed by a different, decoupled number, causing a permanent mismatch between the ledger and reality.

### Impact Explanation
This breaks the Critical-severity equality "Gwei created ... or paid to a non-owner": the execution layer pays out `withdrawal.amount` (uncapped) to `fee_recipient`, while the consensus layer only ever removes `min(withdrawal.amount, builder_balance)` from the builder's tracked stake. The difference is ETH that leaves the system's committed accounting without ever having been backed by a real balance reduction — an inflationary payment funded by nothing, delivered to a party (`fee_recipient`) that is not entitled to it. This is analogous to the High/Critical-severity loss described in the source report, where the mismatch caused collateral (value) to be lost/misappropriated relative to bookkeeping.

### Likelihood Explanation
This is directly reachable through spec-defined mechanics, not a client bug or malicious-peer scenario: the spec itself permits multiple `BuilderPendingWithdrawal` entries for the same builder (see `test_duplicate_builder_index_in_pending_withdrawals`), and neither the enqueue path nor `get_builder_withdrawals` validates that the cumulative requested amount is bounded by the builder's balance before committing the withdrawal amount to the payload. Any proposer/validator honestly following the spec would produce this exact payload and CL state transition, so all honest nodes agree on the (flawed) result — this is a spec-level, not implementation-level, discrepancy.

### Recommendation
`get_builder_withdrawals` should cap `withdrawal.amount` to the running/available builder balance at construction time (mirroring the `min(amount, builder_balance)` cap already applied in `apply_withdrawals`), tracking balance consumption across multiple pending withdrawals for the same builder within a single call, so that the amount committed to `state.payload_expected_withdrawals` (and thus paid by the execution layer) can never exceed what `apply_withdrawals` actually debits from the builder's CL balance.

### Proof of Concept
1. Register a builder with `balance = 1 ETH`.
2. Append a `BuilderPendingWithdrawal` for that builder with `amount = 5 ETH`, `fee_recipient = X` (as in `test_builder_withdrawal_insufficient_balance`).
3. Call `process_withdrawals(state)`.
4. `get_builder_withdrawals` places `Withdrawal(amount=5 ETH, address=X)` into `state.payload_expected_withdrawals` — the execution layer must pay X 5 ETH.
5. `apply_withdrawals` executes `state.builders[0].balance -= min(5 ETH, 1 ETH)`, leaving `balance = 0`.
6. Net effect: the execution layer pays out 5 ETH to `X`, but only 1 ETH of builder stake was ever debited on the consensus layer — 4 ETH of value is created and paid to `X` with no corresponding CL-side backing. [4](#0-3)

*Note*: This is modified to only take the `state` as parameter. Withdrawals are
deterministic given the beacon state, any execution payload that has the
corresponding block as parent beacon block is required to honor these
withdrawals in the execution layer. `process_withdrawals` must be called after
`process_parent_execution_payload` (which updates `state.latest_block_hash`) and
before `process_execution_payload_bid` as the latter function affects validator
balances.

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
