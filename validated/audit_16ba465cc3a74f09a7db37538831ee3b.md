### Title
Front-runnable, unauthenticated `init_global_fee_state` allows an attacker to seize the protocol's `global_fee_admin` role and fee wallet - (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
The `init_global_fee_state` instruction (`InitFeeState` account context) initializes the program-wide `FeeState` singleton PDA and lets the caller supply arbitrary `admin_key` and `fee_wallet` values with no authorization check on who may call it. Because the PDA address is fully deterministic (seeded only by `FEE_STATE_SEED`) and the instruction can only ever succeed once (Anchor `init` constraint), any unprivileged party who submits this instruction before the legitimate deployer does becomes the permanent `global_fee_admin` and routes all protocol fee flows to a wallet of their choosing — the same "predictable address + no-owner-restricted init" bug class described in the external report for `setVibeFees`/`MintSaleBase`.

### Finding Description
`init_global_fee_state` is documented as "(Runs once per program)": [1](#0-0) 

Its handler and account context place no restriction on the caller — `payer` is merely `Signer<'info>`, and the `admin_key`/`fee_wallet` values are taken verbatim from instruction arguments and written directly into the new `FeeState` account: [2](#0-1) 

The `fee_state` account is a PDA derived only from the constant seed `FEE_STATE_SEED`:
```
seeds = [FEE_STATE_SEED.as_bytes()], bump, payer = payer, space = 8 + FeeState::LEN
``` [3](#0-2) 

This is exactly the pattern flagged in the report: the target account's address is fully predictable ahead of time (a PDA with fixed seeds, analogous to the deterministic clone address in `MintSaleBase`), and the privileged "owner" field is set by whoever calls the init function first, without any check that the caller is the legitimate deployer or has any other on-chain authority. `MarginfiGroupInitialize` (the per-group init) at least binds the group admin to the transaction's own signer/payer for that specific group, but `InitFeeState` sets a *global*, protocol-wide admin with no scoping at all.

Once set, `global_fee_admin` cannot be reset by anyone else — subsequent calls to `edit_global_fee_state` require the caller to already be `global_fee_admin`, and `init_global_fee_state` cannot run twice since the PDA already exists: [4](#0-3) 

The `global_fee_admin` role controls protocol-wide fee economics: [5](#0-4) 

### Impact Explanation
Whoever wins the race to call `init_global_fee_state` first permanently becomes `global_fee_admin` for the whole program deployment and sets the `global_fee_wallet` that receives program fees from every group. This is a durable, protocol-wide authorization bypass: the attacker can subsequently call `edit_global_fee_state` to redirect all protocol fee revenue to an address they control, change `program_fee_fixed`/`program_fee_rate`, and set/clear the `pause_delegate_admin`, all without ever needing a privileged key. This is a direct value-redirection and unauthorized privileged-state-capture impact, matching the "Unrestricted access to `setVibeFees`" bug class (front-runnable ownership/fee-parameter seizure on a not-yet-configured singleton).

### Likelihood Explanation
Exploitation requires only that the instruction is publicly observable prior to confirmation (mempool/pre-confirmation monitoring) and that the attacker submits a transaction calling `init_global_fee_state` with attacker-controlled `admin_key`/`fee_wallet` before the legitimate deployer's transaction lands — the exact scenario described in the report, and realistic on Solana any time this instruction is (re-)invoked: initial mainnet bring-up, any future program redeployment/migration to a new program ID, or any environment (devnet/staging) where the `FeeState` PDA has not yet been created. No privileged key, governance access, or economic prerequisite is needed by the attacker; the only barrier is a race to land first, which is a standard, well-understood on-chain front-running capability.

### Recommendation
Restrict `init_global_fee_state` (and `init_global_fee_state_v2`) so that only a hardcoded/known upgrade authority (e.g. the program's upgrade authority or a fixed governance pubkey compiled into the program) can execute it — mirroring the report's fix of checking `msg.sender == owner()` when no higher-level authority (a "master contract" analog) exists yet. Concretely, add an explicit constraint in `InitFeeState` verifying `payer.key()` (or a separate required signer) equals a compile-time-known deployer/governance pubkey, rather than trusting the first caller's supplied `admin_key` unconditionally.

### Proof of Concept
1. Attacker monitors the network for a not-yet-confirmed `init_global_fee_state` transaction (or simply submits speculatively on a freshly deployed/redeployed `marginfi` program before the operator does, since the `FeeState` PDA is deterministically derivable from `FEE_STATE_SEED` and the program ID).
2. Attacker submits their own transaction invoking:
```
init_global_fee_state(
  admin = attacker_pubkey,
  fee_wallet = attacker_wallet,
  ...
)
```
targeting the same deterministic `fee_state` PDA, with higher priority fee / earlier landing than the legitimate transaction.
3. Anchor's `init` constraint succeeds for whichever transaction lands first; the `FeeState` account is created with `global_fee_admin = attacker_pubkey` and `global_fee_wallet = attacker_wallet` as shown in `initialize_fee_state`: [6](#0-5) 
4. The legitimate deployer's subsequent `init_global_fee_state` call fails (`account already in use`), permanently leaving the attacker as `global_fee_admin`.
5. Attacker calls `edit_global_fee_state` (gated only on `global_fee_admin`, which they now hold) to redirect `fee_wallet` and adjust fee parameters for the entire protocol.

// Runs once per program to init the global fee state.
use anchor_lang::prelude::*;
use marginfi_type_crate::{
    constants::FEE_STATE_SEED,
    types::{FeeState, WrappedI80F48},
};

#[allow(unused_variables)]
pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}

#[derive(Accounts)]
pub struct InitFeeState<'info> {
    /// Pays the init fee
    #[account(mut)]
    pub payer: Signer<'info>,

    #[account(
        init,
        seeds = [
            FEE_STATE_SEED.as_bytes()
        ],
        bump,
        payer = payer,
        space = 8 + FeeState::LEN,
    )]
    pub fee_state: AccountLoader<'info, FeeState>,

    pub system_program: Program<'info, System>,
}
