### Title
Post-default instant withdraw requests bypass the default haircut and are paid at par from the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a race where a filter-sync subtask keeps updating a VSI's filter list after the VSI has been released, because nothing marks the resource as "releasing". The analog in `IdleCreditVault` is the instant-withdraw receipt path: after `defaultRecoveryFinalized` is set (the vault's analogue of "VSI released"), `requestInstantWithdraw` still mints new receipts into `instantWithdrawsRequests`/`pendingInstantWithdraws`, and `claimInstantWithdrawRequest` pays those receipts at par via `_transferFundedClaim` once the defaulted-epoch receipts are cleared. New receipts created *after* the default resource was torn down are indistinguishable from pre-default funded receipts, so they are paid at full value out of the same vault balance that backs haircutted default claims.

### Finding Description
- `requestWithdraw` (line 243-295) is default-aware: once `defaultRecoveryFinalized` it reverts if the user has any pending request, and routes new requests to `postDefaultRequests`, which are claimed through `_claimPostDefaultWithdrawRequest` against correctly priced/haircut accounting.
- `requestInstantWithdraw` (line 356-375) has **no** `defaultRecoveryFinalized` branch and no check against `postDefaultRequests`, `withdrawsRequests`, or defaulted-epoch receipts. It burns CDO strategy tokens, mints a receipt to the user, and increases `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` unconditionally.
- `claimInstantWithdrawRequest` (line 380-393) clears defaulted-epoch instant receipts via `_claimDefaultedInstantWithdrawRequest` only when `defaultInstantWithdrawsFinalized` is set, then unconditionally pays `instantWithdrawsRequests[_user]` in full through `_transferFundedClaim` (burning the receipt 1:1). There is no epoch-wait check (instant withdrawals are claimable immediately by design) and no haircut applied to receipts created after finalization.
- Result: a receipt that was never part of the defaulted-epoch basis, never included in `pendingInstantWithdraws` at default time, and never funded by the borrower's `collectInstantWithdrawFunds` pull, is paid at par from the vault's underlying balance — the same balance that constitutes the recovery reserve backing all other users' haircutted default claims (`_claimDefaultedWithdrawRequest`, `postDefaultRequests`, `DefaultDistributor`).

### Impact Explanation
Direct theft of default-recovery funds. After a borrower default is finalized and `finalizeDefaultRecovery` funds the vault reserve at a haircut price, an attacker holding tranche tokens (or acquiring them cheaply post-default, since defaulted tranches trade below par) calls `requestInstantWithdraw`, then `claimInstantWithdrawRequest` in the same transaction/epoch, and receives underlying at par (1 strategy token : 1 underlying claim basis) instead of the `defaultPendingClaimBasis`-derived haircut every other claimant receives. Each atomic pair of calls converts sub-par tranche tokens into par-valued underlying, draining the reserve that honest users' defaulted and post-default claims rely on. Loss is quantified as `(1 - recoveryPrice) * amount` stolen per receipt, bounded only by the reserve balance and the attacker's tranche holdings; it is repeatable until the reserve is depleted, breaking the "one receipt, one haircut payout" invariant and socializing the theft onto all remaining claimants (insolvency of the recovery reserve).

### Likelihood Explanation
- Preconditions: a default has occurred and recovery has been finalized (`defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`). The instant-withdraw path in the vault itself has no epoch-running or non-default gate — the only gating is `_onlyIdleCDO`, so exploitability depends on the CDO variant's `requestInstantWithdraw` entry point remaining callable post-default (it is designed to be callable during the running/buffer phases and is not gated on `defaultRecoveryFinalized` in the vault; I could not fully verify the CDO-side `allowInstantWithdraw`/`defaulted` gating in `IdleCDOEpochVariant.sol` within the search budget — this is the one uncertain link).
- Attacker cost: only tranche tokens, which are haircut-priced after default, making the par payout a direct arbitrage.
- No privileged role is needed; attacker is an ordinary tranche-token holder.
- Existing guards do not stop it: `_ensureDefaultRecoveryInitialized` is a no-op once initialized, the `postDefaultRequests`/`_hasWithdrawRequest` checks in `requestWithdraw` are absent from `requestInstantWithdraw`, and the claim path treats all `instantWithdrawsRequests` as funded once defaulted-epoch receipts are cleared.

### Recommendation
Mirror the `requestWithdraw` post-default gating in `requestInstantWithdraw`: when `defaultRecoveryFinalized` is true, either revert outright, or route the request into `postDefaultRequests`/a separately-funded bucket that can only be paid from newly collected funds — never from the existing recovery reserve. At minimum, in `claimInstantWithdrawRequest`, separate pre-default funded instant receipts (tracked per-epoch via `instantWithdrawsRequestsByEpoch`) from post-default receipts and apply `defaultPendingClaimBasis`/recovery-price haircut to the latter, or revert claims for receipts recorded in epochs after the default epoch.

```solidity
// test/foundry/IdleCreditVaultInstantDefault.t.sol
function testPostDefaultInstantWithdrawPaysParFromReserve() external {
    // 1. Normal deposit, run epoch, force borrower default.
    uint256 amount = 10000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);
    // borrower repays less than owed -> default
    _stopEpochAndCheckPrices(0, initialApr, /*shortfall*/ 1000);
    // finalize default + fund recovery at haircut price
    // ... call finalizeDefault / finalizeDefaultRecovery as in existing default tests ...

    IdleCreditVault vault = IdleCreditVault(address(strategy));
    assertTrue(vault.defaultRecoveryFinalized());

    // 2. Attacker (tranche holder) requests instant withdraw AFTER default.
    uint256 attackerTranches = IERC20(AAtranche).balanceOf(address(this));
    cdoEpoch.requestInstantWithdraw(attackerTranches, address(AAtranche));

    // 3. Claim immediately - paid at par from recovery reserve.
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;

    // 4. paid == par amount while defaulted claims only get haircut * basis.
    //    assertEq(paid, attackerTranches * ONE_SCALE / ...) shows no haircut applied.
}
```

The expected failure mode: `paid` equals the full receipt amount rather than `amount * recoveryPrice / RECOVERY_FULL`, and subsequent honest `claimWithdrawRequest`/`DefaultDistributor.claim` calls revert or underpay due to reserve depletion.
