### Title
Withdraw-request fees are paid in full while the underlying receipt claims are haircut by a stop-epoch loss - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
When a loss is realized at epoch stop via `stopEpochWithDuration(_lossAmount)`, pending withdrawal receipts are haircut pro rata through `previewLossAdjustedWithdrawFunds` / `collectWithdrawFunds` (stored as `lossRecoveryPriceByEpoch`), and the remaining active loss is applied BB-first to LP tranches. In cash mode (`isInterestMinted == false`), however, the upfront management/performance fees that were charged on those same receipts (`pendingWithdrawFees`) are transferred to `feeReceiver`/`owner` in full, before and independently of the loss. The same asymmetry exists for accrued `unclaimedFees`, which are settled from epoch interest before the loss burn. Governance therefore retains fees on principal/interest that was destroyed, mirroring the Kyber finding where rTokens minted to the fee recipient were never burned when attacker shares were burned.

### Finding Description
In `IdleCDOEpochVariant.stopEpochWithDuration`-family logic (`contracts/IdleCDOEpochVariant.sol:391-459`):

1. `IdleCreditVault.previewLossAdjustedWithdrawFunds(_lossAmount)` splits the loss between pending receipts (`pendingLoss`) and active LPs (`activeLoss`) — `contracts/strategies/idle/IdleCreditVault.sol:440-460`.
2. `collectWithdrawFunds(_pendingWithdraws)` funds only `pendingBasis - pendingLoss` and stores `lossRecoveryPriceByEpoch[epochNumber] < RECOVERY_FULL`, so receipt holders later claim a haircut amount — `contracts/strategies/idle/IdleCreditVault.sol:411-430`.
3. Immediately after, `_transferFeeUnderlyings(_pendingWithdrawFees)` pays the entire accrued withdraw fees to `feeReceiver`/`owner` with no haircut — `contracts/IdleCDOEpochVariant.sol:419`. `_totalWithdrawFees` (`contracts/IdleCDOEpochVariant.sol:900-906`) charged these fees upfront at `requestWithdraw` time on principal plus projected interest that is now partially lost.
4. `unclaimedFees` (performance fee on gross gain plus accrued management fee) is then paid up to `_grossInterest - _pendingWithdrawFees` — `contracts/IdleCDOEpochVariant.sol:451-456` — also before `_strategy.burnStrategyTokens(_lossAmount)` and `_forceUpdateAccounting()` realize the loss at lines 496-500.

The codebase itself acknowledges the correct treatment in minted mode: `_lossActiveBasis` explicitly states "Minted fee shares remain backed by CDO-held strategy tokens and therefore join the active-side loss" (`contracts/strategies/idle/IdleCreditVault.sol:462-473`). Minted fee shares are exposed to the post-mint `_forceUpdateAccounting` loss. Cash-mode fees face no such exposure: they are already in `feeReceiver`'s wallet before the loss is crystallized.

Concrete trace (cash mode, running epoch → stop):
- Lender deposits AA/BB, calls `requestWithdraw`; `_totalWithdrawFees` deducts mgmt+perf fee F into `pendingWithdrawFees`; receipt claim C is recorded in `pendingWithdraws`.
- Borrower repays short / manager calls `stopEpochWithDuration(_lossAmount)` reflecting a real loss L on the epoch portfolio.
- `previewLossAdjustedWithdrawFunds` assigns `pendingLoss = L * C / (activeBasis + C)`; receipt holders' recovery price is `< 1`.
- `collectWithdrawFunds` pulls only `C - pendingLoss`; `_transferFeeUnderlyings(F)` still sends F in full; `burnStrategyTokens(activeLoss)` + `_forceUpdateAccounting` push the rest of L onto BB then AA holders.
- Result: governance collects fees computed on pre-loss claim amounts, while every corresponding user claim is haircut — an effective fee rate above the configured `fee`/`managementFee` on net-of-loss gains.

### Impact Explanation
Direct over-payment of fees extracted from the epoch's funded cash: the portion of `pendingWithdrawFees` (and `unclaimedFees` attributable to destroyed NAV) that corresponds to lost claim value is paid out of the same pool that backs receipt holders and active LPs, so remaining LPs and receipt holders absorb more than their waterfall share of the loss. Quantified over-payment ≈ `pendingWithdrawFees * (1 - lossRecoveryPrice)` per loss epoch, plus the fee-on-gross vs fee-on-net delta in `unclaimedFees`. The loss magnitude is bounded by the fee rates and the haircut, so this is a medium-severity fairness/insolvency-adjacent leak rather than full theft, matching the medium severity of the source report.

### Likelihood Explanation
Requires a loss epoch (`stopEpochWithDuration` with `_lossAmount > 0` or a borrower shortfall settled through the loss path) while `pendingWithdraws` or accrued `unclaimedFees` are nonzero and `isInterestMinted == false`. These conditions coincide exactly in stressed epochs where borrowers repay partially via the write-off/loss settlement flow — precisely when the over-collection is most damaging. No privileged misbehavior is needed: the privileged actors follow the honest flow; the defect is purely in fee ordering and lack of haircut.

### Recommendation
Apply the same haircut to fee payouts as to the claims they were charged on:
- Scale `_pendingWithdrawFees` by `lossRecoveryPrice` (i.e., `pendingToFund * RECOVERY_FULL / pendingBasis`) before `_transferFeeUnderlyings`, or route them through the vault so they are haircut alongside `pendingWithdraws`.
- Compute the cash-mode fee cap in `stopEpochWithDuration` on net-of-loss gain (`_grossInterest - activeLoss`) rather than gross interest, and run `burnStrategyTokens(_lossAmount)` + accounting before finalizing `unclaimedFees` payouts, so fees are never paid on value that no longer exists.

### Proof of Concept
```solidity
// Foundry fork test sketch (cash mode, isInterestMinted == false)
// Setup: AA + BB deposits, nonzero managementFee and fee, epoch started.

// 1. User requests withdraw; upfront fee charged.
uint256 trancheAmt = AAtranche.balanceOf(user);
cdoEpoch.requestWithdraw(trancheAmt, address(AAtranche));
uint256 feesCharged = cdoEpoch.pendingWithdrawFees();      // F > 0
uint256 claimBasis  = vault.pendingWithdraws();            // C

// 2. Epoch ends; borrower/manager settle with a real loss L.
uint256 loss = (cdoEpoch.getContractValue() + claimBasis) / 4; // 25% portfolio loss
deal(underlying, borrower, owedMinusLoss);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(newApr, newDuration, loss);

// 3. Receipt holders are haircut.
uint256 price = vault.lossRecoveryPriceByEpoch(vault.epochNumber());
assertLt(price, vault.RECOVERY_FULL());

// 4. feeReceiver was paid the FULL fee F, not F * price.
assertEq(underlying.balanceOf(feeReceiver) - balPre, feesCharged);
// Expected-fair value: feesCharged * price / RECOVERY_FULL
// Overpayment = feesCharged * (RECOVERY_FULL - price) / RECOVERY_FULL
// borne by active LPs via burnStrategyTokens(activeLoss).
```

Key check: `collectWithdrawFunds` haircuts `pendingBasis` but `pendingWithdrawFees` is transferred unconditionally at `IdleCDOEpochVariant.sol:419` and reset to 0 at line 476 — there is no code path that reduces the fee when the receipt is haircut.
