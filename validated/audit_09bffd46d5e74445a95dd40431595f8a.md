### Title
Cross-epoch instant-withdraw receipts escape default haircut and drain the recovery reserve — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The kernel bug's essence is a shared registry entry reclaimed/mutated for one entity while another entity still relies on it: concurrent `idr_remove()` let multiple memcgs share one ID, so cleaning up one wiped shared state used by the rest. `IdleCreditVault` has the same shape: instant-withdraw receipts are tracked both per-epoch (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`) and in global aggregates (`instantWithdrawsRequests`, `pendingInstantWithdraws`), but default finalization only accounts for receipts tagged with the *current* `epochNumber`. An unfunded instant receipt created in an earlier epoch shares the aggregate `pendingInstantWithdraws` bucket but not the current-epoch claim basis. After `finalizeDefaultRecovery`, that stale receipt is still paid out 1:1 through `_transferFundedClaim`, spending underlying that belongs to default-recovery claimants.

### Finding Description
- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, `instantWithdrawsRequests[user]` and `pendingInstantWithdraws`. If the borrower cannot fully fund instant withdrawals at `stopEpoch`, the unfunded remainder persists in `pendingInstantWithdraws` and `instantWithdrawsRequests` into the next epoch, while the per-epoch ledger entries keep the *old* epoch key. [1](#0-0) 
- On default, `defaultPendingClaimBasis()` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the **default-epoch** instant claims — to the haircut basis. Receipts keyed to older epochs are omitted from `totalBasis`, so no recovery is reserved for them. [2](#0-1) 
- `_defaultPrefundedInstantReserve()` compares the *global* `pendingInstantWithdraws` against the *current-epoch* `instantWithdrawClaimsByEpoch[epochNumber]`; a stale receipt inflates `pendingInstant`, shrinking the prefunded reserve that would otherwise be credited to the recovery pool. [3](#0-2) 
- At claim time, `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[user][defaultEpoch]`; a stale-epoch receipt survives untouched. Execution then falls through to `amount = instantWithdrawsRequests[_user]`, which burns the whole aggregate — including the unfunded stale receipt — and pays it at par via `_transferFundedClaim`. [4](#0-3) 
- `_transferFundedClaim` only checks `balance - reserve >= amount`; because the stale receipt's basis was never added to `defaultRecoveryReserve` requirements in the same proportion as it inflates `pendingInstant`, the payout consumes the recovery reserve earmarked for defaulted-epoch claimants and post-default receipts. [5](#0-4) 

Broken invariant: one receipt one haircut. Two receipts sharing the `pendingInstantWithdraws` aggregate are treated as one identity at funding time but as different identities at finalization time — the same "aliased ID" failure as CVE-2024-43892.

### Impact Explanation
The holder of a stale, never-funded instant receipt withdraws it at par after default finalization while defaulted-epoch claimants only receive `defaultRecoveryPrice < 1`. The payout comes out of `defaultRecoveryReserve`-backed balance, directly reducing what every other recovery claimant can withdraw — direct theft of user funds, quantified as `staleReceipt × (1 − defaultRecoveryPrice)` stolen plus up to `staleReceipt` of reserve drained. If the reserve is exhausted first, later legitimate recovery claims revert, permanently freezing their remaining recovery.

### Likelihood Explanation
Requires (a) an instant-withdraw request that the borrower leaves partially or wholly unfunded across a `stopEpoch` boundary — exactly the scenario the code comments acknowledge (`pendingInstantWithdraws` is the "still-unfunded remainder"), and (b) a subsequent borrower default with `pendingInstantWithdraws != 0` so `defaultInstantWithdrawsFinalized` is set. The attacker only needs to be a normal KYC'd lender who made an instant-withdraw request in the right epoch; sequencing depends on honest-manager epoch calls and a default, both within the expected operating envelope. No privileged misbehavior needed.

### Recommendation
Make instant-receipt accounting fully epoch-aware at finalization: include **all** outstanding instant claim basis (every epoch with `instantWithdrawClaimsByEpoch > 0`, not only `epochNumber`) in `defaultPendingClaimBasis()`, and in `claimInstantWithdrawRequest` iterate/clear each epoch entry applying `defaultRecoveryPrice` to any unfunded portion, paying at par only the portion that was actually collected via `collectInstantWithdrawFunds` before default. Alternatively, track a per-receipt funded vs unfunded split so stale receipts cannot share the global `pendingInstantWithdraws` identity.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
