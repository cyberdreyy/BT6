### Title
Post-default instant-withdraw receipts collide with defaulted-epoch receipts on the same epoch key, causing recovery-reserve theft and haircut payout on fully funded claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the gRPC-Web codec failing to distinguish request states, `IdleCreditVault` fails to distinguish *defaulted-epoch* instant-withdraw receipts from *post-default* instant-withdraw receipts. Both are keyed under `instantWithdrawsRequestsByEpoch[user][epochNumber]`, and `epochNumber` does not advance when `finalizeDefaultRecovery` runs. A post-default instant request therefore lands in the same bucket `_claimDefaultedInstantWithdrawRequest` uses, is paid at `defaultRecoveryPrice` instead of par, and is paid out of `defaultRecoveryReserve`, stealing from genuine default claimants.

### Finding Description
`requestInstantWithdraw` has no post-default branch (unlike `requestWithdraw`, which routes to `postDefaultRequests`):

`contracts/strategies/idle/IdleCreditVault.sol:356-375` — after `defaultRecoveryFinalized`, it still burns the CDO's tokens, mints a 1:1 receipt, and writes `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]`. `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` (line 693) but does not bump `epochNumber`, so a request made after finalization but before the next `stopEpoch` is recorded under the *defaulted epoch key*.

On claim, `claimInstantWithdrawRequest` runs `_claimDefaultedInstantWithdrawRequest` whenever `defaultInstantWithdrawsFinalized` is true (lines 382-385). That function reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (line 844) and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` via `_transferDefaultRecovery` (line 855), which decrements `defaultRecoveryReserve` (line 915).

Broken invariant: one receipt one payout / recovery-reserve isolation. A post-default instant receipt is funded at par via `collectInstantWithdrawFunds` (line 398), yet it is settled at the haircut price from the reserve earmarked for default claimants.

### Impact Explanation
Two simultaneous impacts for an unprivileged lender requesting an instant withdraw after default finalization while `epochNumber == defaultRecoveryEpoch`:
- The attacker/lender is paid `recoveryPrice` of a par-funded request — the funded remainder is stranded in the strategy.
- `defaultRecoveryReserve` is debited for that payout, so legitimate defaulted-epoch claimants receive less (or nothing once the reserve is exhausted) — direct theft of reserved funds.

`instantWithdrawClaimsByEpoch[defaultEpoch]` is also decremented by an amount that was never part of the finalized claim basis, corrupting the epoch accounting that `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` rely on.

### Likelihood Explanation
Requires: borrower default (honest sequence), `pendingInstantWithdraws != 0` at finalization so `defaultInstantWithdrawsFinalized` is set (partially unfunded instant queue — a normal occurrence), recovery price < 1, and a KYC'd lender calling `requestInstantWithdraw` before the next `stopEpoch`. All attacker actions are unprivileged; the honest manager/borrower calls are only sequenced around.

### Recommendation
Mirror the `postDefaultRequests` segregation used by `requestWithdraw`: in `requestInstantWithdraw`, when `defaultRecoveryFinalized` is true, either reject while `instantWithdrawsRequests[_user]` mixes with the defaulted epoch, or record post-default instant requests in a separate ledger (e.g. `postDefaultInstantRequests`) claimed at par from collected funds — never keyed under `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and never routed through `_transferDefaultRecovery`.

### Proof of Concept
Foundry fork PoC sketch (mirroring `testPostDefaultWithdrawRequiresClaimingOpenPriorReceipt` in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testPostDefaultInstantWithdrawCollidesWithDefaultEpoch() external {
    address user = makeAddr('instant-user');
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 recoveryRatio = 7e17;

    _depositWithUser(user, amount, true);

    // epoch 0 runs; borrower defaults at stopEpoch with an unfunded instant queue
    _startEpochAndCheckPrices(0);
    // create a partially-funded instant queue so pendingInstantWithdraws != 0
    vm.prank(user);
    cdoEpoch.requestInstantWithdraw(IERC20(AAtranche).balanceOf(user) / 4, address(AAtranche));
    uint256 activeBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    uint256 recovered = activeBasis * recoveryRatio / ONE_TRANCHE;
    _stopEpochAndCheckPrices(0, initialProvidedApr, 0);
    _checkDefault();

    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();
    assertTrue(creditVault.defaultInstantWithdrawsFinalized());

    // epochNumber is still the default epoch; user requests a new instant withdraw
    vm.prank(user);
    cdoEpoch.requestInstantWithdraw(IERC20(AAtranche).balanceOf(user), address(AAtranche));
    // CDO funds it at par via getInstantWithdrawFunds -> collectInstantWithdrawFunds

    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimInstantWithdrawRequest();
    // The par-funded post-default request is paid at recoveryRatio from defaultRecoveryReserve
    // assert payout < par and reserve debited by the haircutted amount
}
```

Uncertainty note: I did not fully verify that `IdleCDOEpochVariant.requestInstantWithdraw`/`getInstantWithdrawFunds` permits the call while `defaulted()` — if the CDO blocks post-default instant requests entirely, the collision window closes, but the missing segregation in `requestInstantWithdraw` remains the latent defect (any path that restores operations, e.g. `restoreOperations`, before `epochNumber` advances re-opens it).
