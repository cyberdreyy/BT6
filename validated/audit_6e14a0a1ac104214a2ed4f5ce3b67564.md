## Analysis

The reported bug class — a Merkle leaf/root hash intentionally truncated to a subset of the full digest, opening a brute-force/collision path against something that is supposed to give unique, unforgeable identity to an on-chain asset — has a direct analog in Base's B-20 token factory precompile.

### Title
Truncated 72-bit hash tail in B-20 token address derivation enables brute-forceable address squatting - (File: `crates/common/precompiles/src/b20_factory/variant.rs`)

### Summary
`B20Variant::compute_address_from_hash` derives every B-20 token's on-chain address by taking only the **low-order 9 bytes (72 bits)** of `keccak256(creator, salt)` and appending them to a fixed, publicly known 11-byte variant prefix, instead of using the full 160-bit/256-bit hash output that normal `CREATE`/`CREATE2` address derivation relies on for collision resistance.

### Finding Description
`compute_address_from_hash` copies only `hash[..9]` into the deployed address's tail: [1](#0-0) 

This is invoked from the precompile's create path, `FactoryV1::create_b20`, which computes the deterministic `token_address` from this 72-bit tail and only guards against redeployment by checking whether an account already has code at that address: [2](#0-1) 

Both `createB20` and the public `getB20Address` view function are reachable by any unprivileged caller (the "B20 token creator" actor explicitly in scope), since `(caller, salt)` fully determines the address and `salt` is a fully attacker-chosen `bytes32`: [3](#0-2) [4](#0-3) 

Because only 72 bits of hash output determine token address uniqueness within a variant (versus the 160-bit address space normal Ethereum contract creation relies on), the security margin against address collision is reduced by roughly 88 bits. An attacker can grind `salt` values off-chain (a pure hash computation, no chain interaction required) to find a `(creator, salt)` pair whose `keccak256` tail collides with the tail of a specific target token address that a victim intends to create (e.g. a well-known or predictable `getB20Address` prediction that an integrator has already begun trusting, pre-funding, or whitelisting before `createB20` is actually submitted).

### Impact Explanation
If an attacker grinds a colliding `(creator, salt)` and calls `createB20` first, `already_deployed` in `create_b20` will see code already present at the intended victim address, causing the legitimate creator's later `createB20` to permanently revert with `TokenAlreadyExists`: [5](#0-4) 

This is a permanent denial-of-service against the intended token's deployment at its documented deterministic address. Worse, if any user or integrator pre-funds, approves, or hardcodes the address returned by `getB20Address` before the legitimate `createB20` transaction lands (a normal integration pattern, since the whole point of `getB20Address` is to let callers act on the future address ahead of time), those funds/approvals are directed at an attacker-controlled malicious B-20 contract instead of the legitimate token — resulting in theft or permanent freezing of funds. The precompile's `isB20` check only validates the structural address prefix, not that a specific expected party deployed it, so downstream consumers cannot distinguish the attacker's squatted contract from the legitimate one by address form alone: [6](#0-5) 

### Likelihood Explanation
Reaching this path requires only a normal, unprivileged `createB20`/`getB20Address` call — no special role or privilege is needed. The attack cost is bounded by the 72-bit tail search space (a birthday-style grind between attacker-controlled candidates costs roughly `2^36` hash evaluations, well within reach of commodity hardware/GPU farms; targeting one specific known future address costs up to `2^72`, still dramatically weaker than the `2^160` collision resistance normally expected of contract addresses). Any protocol or workflow that predicts a B-20 address via `getB20Address` before the token exists — a pattern the codebase itself uses in load-test tooling — is exposed to this front-running/squatting window.

### Recommendation
Use the full 20-byte `keccak256(creator, salt)` output (or otherwise preserve full 160-bit collision resistance) for the address tail rather than truncating to 9 bytes, or otherwise ensure the variant-prefix bits do not reduce the effective security margin of address uniqueness below what integrators assume for deterministic contract addresses.

### Proof of Concept
1. Attacker observes (or predicts) a victim's intended `getB20Address(variant, victim, salt_v)` — either from a public documented salt convention or from a pending mempool transaction.
2. Attacker enumerates candidate `salt_a` values, computing `keccak256(attacker, salt_a)` off-chain, until `hash[..9]` matches the low 9 bytes of `keccak256(victim, salt_v)`, i.e., `compute_address_from_hash` yields the identical `token_address`.
3. Attacker submits `createB20(variant, salt_a, maliciousParams, maliciousInitCalls)` first, deploying their contract at the shared address (`crates/common/precompiles/src/b20_factory/logic/v1.rs` lines 201-214).
4. Victim's subsequent `createB20(variant, salt_v, ...)` reverts with `TokenAlreadyExists` (permanent DoS), and any party that trusted the pre-computed `getB20Address` result now interacts with the attacker's contract instead.

    /// Computes the deterministic token address from a pre-computed `keccak256(creator, salt)` hash.
    ///
    /// Use when the hash is already available (e.g. after charging keccak gas via `ctx.metered_keccak256`)
    /// to avoid re-encoding and re-hashing.
    pub fn compute_address_from_hash(self, hash: B256) -> (Address, [u8; 9]) {
        let mut tail = [0u8; 9];
        tail.copy_from_slice(&hash[..9]);

        let mut addr_bytes = [0u8; 20];
        addr_bytes[..11].copy_from_slice(&self.address_prefix());
        addr_bytes[11..].copy_from_slice(&tail);

        (Address::from(addr_bytes), tail)
    }
