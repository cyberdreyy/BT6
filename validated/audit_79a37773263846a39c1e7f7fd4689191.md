### Title
External Initiator credential holders can bypass the "EIs not allowed" restriction and trigger arbitrary jobs by integer ID via `POST /v2/jobs/:ID/runs` - ([File: core/web/router.go])

### Summary
The `userOrEI` route group in `v2Routes` allows an External Initiator (EI) credential to authenticate to `POST /v2/jobs/:ID/runs`, which is handled by `PipelineRunsController.Create`. That handler contains an explicit comment stating "only users are allowed to run jobs using int IDs - EIs not allowed", but the guard it uses (`auth.GetAuthenticatedUser`) always returns `ok=true` for EI-authenticated requests too, because `AuthenticateExternalInitiator` injects a synthetic `clsessions.User{Role: UserRoleRun}` into the same context key used for real users. As a result, any holder of EI credentials can trigger arbitrary jobs by numeric ID, which the code intends to forbid.

### Finding Description
The route is registered as: [1](#0-0) 

`auth.AuthenticateExternalInitiator` authenticates the caller solely via the `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers, and — critically — sets the same `SessionUserKey` context value that real user auth methods use, with a synthetic role: [2](#0-1) 

`RequiresRunRole` only checks `user.Role != UserRoleView`, so this synthetic "run" role passes: [3](#0-2) 

Inside `PipelineRunsController.Create`, the code attempts to specifically block EIs from running jobs via integer job IDs (this is a legacy path; UUID-based webhook job triggering was already removed), using: [4](#0-3) 

`auth.GetAuthenticatedUser(c)` simply checks presence of `SessionUserKey` in the gin context: [5](#0-4) 

Because `AuthenticateExternalInitiator` sets `SessionUserKey` too, `isUser` is always `true` for an EI-authenticated request, defeating the intended restriction. The EI branch of `Create` is therefore unreachable dead logic — an EI credential holder is treated identically to a full "run"-role user and can call `prc.App.RunJobV2(ctx, jobID, nil)` for any job ID on the node, not limited to jobs tied to that specific external initiator.

### Impact Explanation
An attacker holding only an External Initiator credential (a narrowly-scoped, lower-trust credential intended for triggering specific webhook-integrated jobs) gains the ability to trigger execution of **any** job on the node by guessing/enumerating small integer job IDs. This is an authorization/role-boundary bypass leading to unauthorized job execution, which can cause unintended on-chain transactions, fund movement (e.g., ETH transfer jobs), or unwanted pipeline side effects — matching the "unauthorized job run or fund movement" impact class called out in the audit scope.

### Likelihood Explanation
Exploitation requires only a valid EI access key/secret pair (issued for some legitimate, narrow purpose via `ExternalInitiatorsController`) — no admin/session/full-API-token credential is needed. Job IDs are small sequential integers, making enumeration trivial. The flaw is deterministic and repeatable on any node with at least one registered external initiator.

### Recommendation
Distinguish EI-authenticated context from real user context — e.g., check `auth.GetAuthenticatedExternalInitiator(c)` (or a dedicated flag) instead of relying on the shared `SessionUserKey` presence to determine `isUser` in `PipelineRunsController.Create`. Alternatively, do not set `SessionUserKey` for EI callers, and instead have `RequiresRunRole` accept either a real user or an EI via distinct context keys, without conflating identity types.

### Proof of Concept
Handler-level integration test plan (Go, using `httptest` + gin, mirroring existing tests in `core/web/pipeline_runs_controller_test.go`):
1. Set up an app with a registered `ExternalInitiator` and a job with a known integer ID (`jobID`).
2. Build a request `POST /v2/jobs/<jobID>/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to the EI's valid credentials, and no session cookie / API token headers.
3. Send the request through the router built by `NewRouter`.
4. Assert: current (vulnerable) behavior returns `200 OK` with a `pipelineRun` resource (i.e., `prc.App.RunJobV2` was invoked) — demonstrating the "EIs not allowed" comment is not enforced.
5. Expected (fixed) behavior: response should be `422 Unprocessable Entity` with "bad job ID" (or equivalent explicit EI-rejection) once `isUser` correctly excludes EI-authenticated contexts.

// GetAuthenticatedUser extracts the authentication user from the context.
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
