### Title
Unchecked `BlockInfo` state-transition result lets a signer broadcast a signature/assembled block for a proposal it has already globally rejected - (File: stacks-signer/src/signerdb.rs, stacks-signer/src/v0/signer.rs)

### Summary
`BlockInfo::mark_locally_accepted` mutates side-effect fields (`valid`, `approved_time`, `signed_self`, or `signed_group`) unconditionally, *before* attempting the guarded state transition via `move_to`. Its `Result` is therefore not a reliable success/failure indicator of "did we actually accept this block," yet both call sites in `stacks-signer/src/v0/signer.rs` treat a returned `Err` as informational only (logged, sometimes not even that) and unconditionally continue to persist the block and broadcast a signature/assembled block — exactly the ERC20 `transfer()`-return-value pattern: a fallible operation's failure is silently absorbed and the code proceeds as if it succeeded.

### Finding Description
`BlockInfo::mark_locally_accepted` (signerdb.rs): [1](#0-0) 
```rust

    } else {
        self.valid = Some(true);

        self.signed_self.get_or_insert(get_epoch_time_secs());
```

`self.signed_self` / `self.signed_group` are set **before** `move_to` runs its `check_state` guard. `move_to` can legitimately fail here only when the block has already reached `GloballyRejected` or `GloballyAccepted` [2](#0-1) . If the block is `GloballyRejected`, the transition is correctly refused, but the "we signed" bookkeeping field is already set regardless.

Both call sites treat this `Err` as non-fatal and continue the accept/broadcast path unconditionally:

`broadcast_signed_block` unconditionally assembles the aggregated multi-signer signature and calls `handle_post_block` → `stacks_client.post_block(block)`, pushing the block to the node [5](#0-4) , [6](#0-5) .

Root cause of reachability: `store_and_process_block_rejection` can move a `BlockInfo` straight to `GloballyRejected` via `mark_globally_rejected()` without ever setting `valid = false` (that only happens via `mark_locally_rejected`, which this path does not call) [7](#0-6) . So a block can be `GloballyRejected` while `block_info.valid == Some(true)` and `signed_self == None`. `handle_block_pre_commit`'s early gates only check `signed_self.is_some()` and `!valid.unwrap_or(false)` [8](#0-7) ; neither excludes a `GloballyRejected` block whose `valid` was never flipped. A late-arriving/replayed `BlockPreCommit` (queued via `add_pending_block_pre_commit_response` and replayed by `process_pending_responses_for_block`, or simply a slow gossip message) that crosses the 70% pre-commit-weight threshold after the same block already crossed the 30% rejection threshold on this signer will run through `check_block_against_signer_db_state` and the conflict checks and land in the `SIGN` branch, invoking the buggy `mark_locally_accepted`.

### Impact Explanation
This breaks the "rejection vs. acceptance" equality that the whole two-phase-commit protocol is built to guarantee: once a signer's own DB records `GloballyRejected` for a block, that signer must never subsequently produce a valid signature for it. Here, the signer both (a) writes an inconsistent `BlockInfo` to its own DB (`state = GloballyRejected` but `signed_self`/`signed_group` set as if signed) and (b) actually emits and broadcasts a cryptographically valid `BlockAccepted` signature (single-signer path) or pushes a fully assembled multi-signature block to the node (group-threshold path) for a block it has already treated as invalid/rejected. This is a signer signing/helping finalize a conflicting/already-rejected block — the report's Critical-impact category ("a signer signing an invalid, non-canonical, or conflicting block" / "a rejection recounted as an acceptance").

### Likelihood Explanation
No majority compromise is required. It only needs ordinary gossip-timing skew between `BlockPreCommit` and `BlockResponse::Rejected` messages for the same block on a single honest signer: a block near the 30/70 split boundary, where pre-commits from a slower peer set arrive (or are replayed from the pending-response queue) after this signer has already reached the 30% rejection threshold. This is a naturally occurring race in an asynchronous gossip network and does not require an attacker to control the signer's key, StackerDB auth, or a majority of the signer set — matching the report's "one-slot miner (plus gossip)" trigger class.

### Recommendation
Make `mark_locally_accepted`/`mark_locally_rejected`/`mark_pre_committed`/`mark_globally_accepted`/`mark_globally_rejected` atomic with respect to their `Result`: only mutate `valid`/`approved_time`/`signed_self`/`signed_group` if `move_to` succeeds (i.e., call `move_to` first and early-return on `Err` before touching any other field). Additionally, in both call sites in `stacks-signer/src/v0/signer.rs`, treat `Err` from `mark_locally_accepted` as fatal to the accept/broadcast path — return immediately instead of continuing to `insert_block`, `handle_block_signature`, `send_block_response`, or `broadcast_signed_block`. Also close the underlying gap by having `store_and_process_block_rejection` call `mark_locally_rejected()` (setting `valid = false`) before `mark_globally_rejected()`, so `handle_block_pre_commit`'s existing `!valid.unwrap_or(false)` gate correctly vetoes late pre-commits for globally-rejected blocks.

### Proof of Concept
1. Signer S receives `BlockProposal` for block B, validates it OK, and reaches `PreCommitted` (`valid = Some(true)`), broadcasting its own pre-commit; assume S's pre-commit weight is currently below 70%.
2. Due to network conditions, other signers' `BlockResponse::Rejected` messages for B (from a >30%-weight blocking minority) arrive at S first. Each call to `store_and_process_block_rejection` records the rejection and, once weight crosses `total_weight - min_weight`, calls `block_info.mark_globally_rejected()` directly (without `mark_locally_rejected`), moving B's `BlockState` to `GloballyRejected` while leaving `valid = Some(true)` and `signed_self = None`.
3. A previously delayed `BlockPreCommit` from another signer (or a replay via `process_pending_responses_for_block`) now arrives and pushes the tallied pre-commit weight for B over the 70% threshold. `handle_block_pre_commit` passes its `signed_self.is_some()` and `!valid.unwrap_or(false)` gates (both false), passes `check_block_against_signer_db_state` and the conflict checks, and reaches the `SIGN` branch.
4. `block_info.mark_locally_accepted(false)` sets `valid = Some(true)`, `approved_time`, and `signed_self = Some(now)` before calling `move_to(LocallyAccepted)`, which fails because the prior state is `GloballyRejected`. The `Err` is swallowed (`has_reached_consensus()` is true, so not even logged).
5. Execution continues unconditionally: `insert_block` persists the inconsistent `BlockInfo` (`state = GloballyRejected`, `signed_self = Some(now)`), then `create_block_acceptance` + `handle_block_signature` + `send_block_response` produce and broadcast a valid `BlockAccepted` signature for a block S's own DB already marked `GloballyRejected`.

**Uncertainty/Unverified:** Confirming this exact interleaving occurs in a live network (rather than only being reachable in principle from the code paths shown) would require running the signer test harness (e.g., a variant of `stacks-node/src/tests/signer/v0/mod.rs` scenarios) with injected message delays; that dynamic verification was not performed here, only static code-path analysis.
