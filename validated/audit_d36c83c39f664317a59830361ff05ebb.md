## Title
Builder payments are settled unconditionally on quorum-eligible slots, bypassing the PTC weight/quorum requirement - (File: `specs/gloas/beacon-chain.md`)

## Summary
The analog to the fee-on-transfer bug ("the amount actually settled differs from the amount the contract/spec believes it committed to, because the settlement path skips the check that was supposed to gate it") shows up in Gloas's (ePBS) builder-payment settlement logic. `settle_builder_payment`, called unconditionally from `apply_parent_execution_payload` for any parent slot in the current or previous epoch, releases the full pending builder payment with **no quorum/weight check**, while the parallel epoch-processing path `process_builder_pending_payments` is explicitly gated on `payment.weight >= quorum`. Because `apply_parent_execution_payload` runs on every child block (i.e., as soon as a child confirms the parent payload as FULL) and always precedes the epoch-boundary quorum check for that slot, the quorum gate is effectively dead code for the common case, and a builder gets paid even when the payload-timeliness committee (PTC) never reached quorum on the payload's availability.

## Finding Description
Two independent, inconsistent state mutators exist for turning a `BuilderPendingPayment` into an actual `BuilderPendingWithdrawal`:

1. `settle_builder_payment` (called from `apply_parent_execution_payload` on every block, keyed off `parent_epoch == current/previous epoch`) unconditionally appends the withdrawal if `payment.withdrawal.amount > 0`, with no reference to `payment.weight`: [1](#0-0) 

2. `process_builder_pending_payments`, run once per epoch, is the function that is documented/designed to gate the payment on PTC attestation weight reaching quorum: [2](#0-1) 

`apply_parent_execution_payload` is invoked from `process_parent_execution_payload` for every incoming block (processing the *previous* block's parent payload), and it calls `settle_builder_payment(state, payment_index)` whenever `parent_epoch` equals the current or previous epoch: [3](#0-2) 

Since a child block is normally built on top of its parent in the very next slot, `apply_parent_execution_payload` runs — and settles the payment via `settle_builder_payment` — before `process_builder_pending_payments` has a chance to evaluate `payment.weight` against the quorum for that slot (that epoch-boundary function only fires days/epochs later and, by then, `settle_builder_payment` has already emptied the payment slot: `state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()`). The weight accumulated via PTC attestations in `process_attestation` (`payment.weight` incremented there) is therefore never consulted for the normal, common-case block flow.

This mirrors the fee-on-transfer bug pattern: the protocol *believes* it committed to a value gated on an external confirmation signal (attester/PTC weight, i.e. the "actual transferred amount"), but the code path that actually moves the funds (`settle_builder_payment`) ignores that signal and always uses the raw recorded amount (`bid.value`), exactly as `DInterest.deposit` used the raw `depositAmount` parameter instead of the confirmed transferred amount.

## Impact Explanation
This breaks the equality "a builder payment is only paid when the payload-timeliness committee attests quorum weight confirming the payload was actually delivered/available" vs. "the builder is paid regardless." A builder can receive the full bid payment even if the PTC never reached quorum on the corresponding payload — i.e., a payment is applied that block validity (per spec design intent) did not actually commit to via quorum confirmation. This is a payment-integrity issue (Impact bucket: "a builder payment or withdrawal misdirected, doubled or escaped" / "a payload executed or paid that the block did not commit to").

## Likelihood Explanation
This triggers on the ordinary, majority-case chain flow (every full parent block followed by a child in the same or next epoch) — not merely for an adversarial minority. However, I was not able to fully confirm within the available context whether `settle_builder_payment`'s unconditional payout is the intended design (i.e., whether quorum is meant only to apply to the "evicted"/never-attested case, such as when a slot is skipped) rather than a bug. The test `test_builder_payment_after_missed_epochs` (`tests/.../sanity/test_blocks.py`) explicitly documents that the quorum check is bypassed for missed-epoch payments too ("The fix creates the withdrawal directly from the bid in this case"), suggesting this unconditional-settlement behavior is a known, deliberate design choice for the "normal" settlement path, with quorum only mattering when the payment is *not* settled promptly (e.g., across long gaps). Given this, I cannot assert with confidence that this is an unintended vulnerability rather than documented intended behavior — this significantly reduces confidence in labeling it a vulnerability rather than a design quirk that the spec text alone (without accompanying design rationale) leaves ambiguous.

## Recommendation
Clarify (or, if unintended, fix) whether `settle_builder_payment` should also check `payment.weight >= get_builder_payment_quorum_threshold(state)` before appending the withdrawal, consistent with `process_builder_pending_payments`. If quorum is only meant to gate the epoch-level "catch-all" path and immediate settlement via the child block is intentionally unconditional (e.g., because block inclusion itself is the confirmation signal), this should be explicitly documented in the spec text near `settle_builder_payment` to avoid the appearance of an inconsistency between the two payment-release paths.

## Proof of Concept
Given the ambiguity described above, I cannot construct a concrete state-transition PoC proving unauthorized fund loss with full confidence — the "PoC" would just be the standard block-production flow (bid → parent FULL → child block calls `apply_parent_execution_payload` → `settle_builder_payment` fires unconditionally), which the existing test suite (`tests/core/pyspec/eth_consensus_specs/test/gloas/sanity/test_blocks.py::test_builder_payment_after_missed_epochs`) already exercises and asserts as expected behavior, not as a fix for a discovered flaw. Because of this, I present this as a candidate analog for further review rather than a definitively validated bug.

def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
