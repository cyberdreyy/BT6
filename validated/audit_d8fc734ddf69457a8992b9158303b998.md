### Title
Unvalidated symlink target (`hdr.Linkname`) in tar+zstd cache/artifact extraction allows creation of out-of-chroot symlinks - ([File: commands/helpers/archive/tarzstd/tarzstd_extractor.go])

### Summary
`(*extractor).Extract` validates that the *location* of an extracted entry (`path`, derived from `hdr.Name`) stays inside `e.dir`, but never validates the *target* of a symlink entry (`hdr.Linkname`) before calling `os.Symlink(hdr.Linkname, path)`. A job that controls the contents of a cache or artifact archive (e.g. via `cache: paths`) can embed a symlink entry whose `Linkname` is an absolute path such as `/etc/passwd` or another project's workspace path, and the extractor will happily create that symlink inside the job's own chroot.

`hdr.Linkname` comes directly from the tar stream, which is fully attacker-controlled content of a cache/artifact archive (e.g. produced by a malicious `cache: paths` entry in `.gitlab-ci.yml`, or a crafted binary blob committed as a "cache" from a previous job run). Since `os.Symlink` does not resolve or validate the link target, any string (absolute path, `../../` sequences, path to a sibling job's workspace like `/builds/project-2/.git/config`) is accepted, and a dangling/out-of-chroot symlink is created inside the job's own directory tree.

The path corresponding to `path.Symlink`'s destination (the second argument) is never passed through the `strings.HasPrefix(path, e.dir+...)` check that guards entry placement — that check only applies to where the tar entry is written, not what a symlink entry points to.

### Impact Explanation
Once such a symlink exists inside the job workspace, any subsequent step in the same job (a build script, another cache/artifact restore that writes through the symlinked path, or a later stage that resolves relative paths through it) that reads or writes through that path will transparently follow the symlink outside the intended chroot. This provides a primitive for unauthorized file read/write outside the job root — e.g., overwriting or reading files elsewhere on the host filesystem that the job process has permissions for, or targeting predictable paths belonging to other jobs/projects on a shared shell/host executor. This matches the scoped impact: "unauthorized file access outside job root via a dangling symlink later followed by build steps."

### Likelihood Explanation
This is straightforward and repeatable for any unprivileged pipeline author: they only need to get a symlink with an absolute/traversal `Linkname` into a cache or artifact archive that will later be extracted by `cache-extractor`/`artifacts-extractor` using this tarzstd path (e.g., by running `ln -s /etc/passwd foo` inside `cache: paths`, so it gets archived, then triggering extraction on the same or a later job run). No special privileges beyond normal job execution are required, and the attack is fully deterministic — it does not depend on race conditions or admin misconfiguration.

### Recommendation
Validate `hdr.Linkname` before calling `os.Symlink`: for absolute-looking or path-escaping link targets, either reject the entry, or resolve `filepath.Join(filepath.Dir(path), hdr.Linkname)` and apply the same `e.dir` prefix containment check used for `path`. This mirrors how zip-slip fixes are applied to symlink targets, not just symlink locations, and should be applied consistently to any other extractors (e.g. `helpers/archives/zip_extract.go`'s `extractZipSymlinkEntry`) that create symlinks from untrusted archive content.

### Proof of Concept
Go unit test sketch:
```go
func TestExtract_RejectsSymlinkEscapingChroot(t *testing.T) {
    dir := t.TempDir()
    var buf bytes.Buffer
    zw, _ := zstd.NewWriter(&buf)
    tw := tar.NewWriter(zw)
    hdr := &tar.Header{
        Name:     "evil-link",
        Linkname: "/etc/passwd", // or "../../outside"
        Typeflag: tar.TypeSymlink,
        Mode:     int64(os.ModeSymlink | 0777),
    }
    tw.WriteHeader(hdr)
    tw.Close()
    zw.Close()

    r := bytes.NewReader(buf.Bytes())
    ext, _ := NewExtractor(r, int64(r.Len()), dir)
    err := ext.Extract(context.Background())

    // Expect an error, or that the created symlink target is verified
    // to remain within dir.
    linkPath := filepath.Join(dir, "evil-link")
    target, _ := os.Readlink(linkPath)
    resolved, _ := filepath.Abs(filepath.Join(filepath.Dir(linkPath), target))
    assert.True(t, strings.HasPrefix(resolved, dir+string(filepath.Separator)),
        "symlink target escaped chroot: %s -> %s", linkPath, target)
}
```
Expected current behavior (bug present): `Extract` succeeds and `evil-link` resolves to `/etc/passwd`, failing the assertion. After the fix, `Extract` should either reject the entry or the symlink target must stay within `dir`.
