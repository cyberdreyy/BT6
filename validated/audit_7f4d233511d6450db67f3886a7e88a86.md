## Title
Permissionless `InitializeNonceAccount` allows frontrunning of nonce-account authority when account creation and initialization are separate transactions - (File: `programs/system/src/system_instruction.rs`)

### Summary
The `InitializeNonceAccount` system instruction sets the nonce account's authority to whatever `Pubkey` is supplied in the instruction data, with no check that the caller is the account's creator, fee payer, or otherwise privileged with respect to that account. If a wallet, dApp, or CLI flow creates a nonce account with `SystemInstruction::CreateAccount` (or `Allocate`+`Assign`) in one transaction and defers the `InitializeNonceAccount` call to a later, separate transaction, an attacker who observes the pending/confirmed creation can frontrun and submit `InitializeNonceAccount` first, setting themselves as the `authority`. This is the exact "two-step deploy/initialize" pattern described in the external report.

### Finding Description
`initialize_nonce_account` only validates that the account is writable and currently `State::Uninitialized`; it does not verify any relationship between the transaction signer and the target account address, nor does it require the account's creator to sign: [1](#0-0) 

The dispatcher in `system_processor.rs` likewise performs no additional authorization for this instruction beyond the recent-blockhashes and rent sysvar checks: [2](#0-1) 

Because a system-owned, uninitialized account can be created by anyone (any account address is a valid `CreateAccount`/`Allocate` target, and once created it is simply "owned by the System Program, empty data, `State::Uninitialized`"), there is no cryptographic or protocol-level binding between "who paid to create this account" and "who is allowed to call `InitializeNonceAccount` on it." Whoever's `InitializeNonceAccount` transaction lands first wins and becomes the durable-nonce `authority`.

Compare this to the correct atomic pattern used by the CLI helper, which bundles `CreateAccount`/`CreateAccountWithSeed` and `InitializeNonceAccount` into a single `Message`/transaction so they cannot be split by a frontrunner: [3](#0-2) 

Once an attacker wins the race and becomes `authority`, they fully control the nonce account: they can advance the nonce (`AdvanceNonceAccount`, which only checks `signers.contains(&data.authority)`): [4](#0-3) 

and — critically — they can withdraw all lamports at any time by signing as `authority` via `WithdrawNonceAccount`, which only requires the recorded authority's signature, not the original creator's: [5](#0-4) 

### Impact Explanation
This is a concrete, unsigned fund-theft vector reachable by a single unprivileged attacker transaction: any lamports subsequently deposited into (or already rent-funded in) the hijacked nonce account can be withdrawn entirely by the attacker via `WithdrawNonceAccount`, since they alone hold the authority key. Any application, wallet, or durable-nonce-based transaction flow that relies on the victim's ability to control the nonce account (e.g., for offline/durable transaction signing) is broken and could result in stuck or maliciously-substituted transactions, since the attacker-controlled authority decides when/whether the nonce advances.

### Likelihood Explanation
Medium — exploitation requires the attacker to frontrun a specific `InitializeNonceAccount` transaction that is broadcast separately from account creation. This depends on client/wallet implementations that split account creation and nonce initialization into two transactions (which the built-in CLI helper avoids by bundling them atomically), so the vulnerability is only reachable when such a non-atomic deployment pattern is used by an external client, not by the CLI path shown above.

### Recommendation
Since `InitializeNonceAccount` cannot verify "who created the account" (Solana accounts carry no creator provenance), any client or SDK helper that creates a nonce account must always submit `CreateAccount`/`CreateAccountWithSeed` and `InitializeNonceAccount` atomically within the same transaction, exactly as `solana_system_interface::instruction::create_nonce_account[_with_seed]` already does. Documentation/guidance should explicitly warn integrators never to split nonce-account creation and initialization across transactions, and any tooling that currently does so (or generically composes system-program deployment flows) should be audited and fixed to always bundle the two instructions.

### Proof of Concept
1. Attacker monitors the mempool/RPC for a `SystemInstruction::CreateAccount` transaction targeting address `N`, owned by `system_program`, intended to become a nonce account.
2. Once `N` is confirmed as an uninitialized system-owned account, attacker submits `SystemInstruction::InitializeNonceAccount(attacker_pubkey)` targeting `N` before the victim's own `InitializeNonceAccount(victim_pubkey)` lands (per `programs/system/src/system_instruction.rs:163-211`, no signer/creator check exists).
3. The victim's later `InitializeNonceAccount` call fails with `InstructionError::InvalidAccountData` (state already `Initialized`), while attacker's account now has `authority = attacker_pubkey`.
4. If the victim (unaware of the failed initialize, or via a UI that doesn't surface it) deposits lamports into `N`, attacker calls `WithdrawNonceAccount` signed by `attacker_pubkey` (`programs/system/src/system_instruction.rs:80-161`) to drain the account.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}
