### Title
Builder withdrawal payloads commit uncapped amounts while CL only debits `min(amount, balance)`, minting unbacked Gwei to the fee recipient - (File: specs/gloas/beacon-chain.md)

### Summary
In the Gloas fork, `get_builder_withdrawals` builds `Withdrawal` entries for `state.builder_pending_withdrawals` using the raw, requested `withdrawal.amount` with no cap against the builder's current balance. That uncapped amount is what gets committed into `state.payload_expected_withdrawals` and is what the execution layer will unconditionally mint to `withdrawal.address`. Meanwhile `apply_withdrawals` only deducts `min(withdrawal.amount, builder_balance)` from `state.builders[builder_index].balance` on the consensus side. When a builder's balance is less than the sum of amounts recorded in its pending withdrawals, the execution layer credits more Gwei than is ever removed from the builder's CL-tracked balance — this is the exact analog of the PrizeVault bug, where the amount computed/committed for a withdrawal diverges from the amount actually deducted from the underlying store.

### Finding Description
`get_builder_withdrawals` [1](#0-0)  appends a `Withdrawal` with `amount=withdrawal.amount` directly from `state.builder_pending_withdrawals`, without ever comparing it to `state.builders[builder_index].balance`. This withdrawal is placed into `state.payload_expected_withdrawals` via `update_payload_expected_withdrawals`, which is the binding commitment that the execution layer is required to honor (per the note on `process_withdrawals`: "any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals in the execution layer") [2](#0-1) .

The consensus-layer side effect is applied separately by `apply_withdrawals`:
```python
if is_builder_index(withdrawal.validator_index):
    builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
    builder_balance = state.builders[builder_index].balance
    state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
``` [3](#0-2) 

Here the deduction is explicitly capped ("saturated") at the builder's current balance, but the **committed withdrawal amount that the EL will pay out is not capped**. These two numbers — the amount promised to the EL vs. the amount actually removed from `state.builders[*].balance` — are supposed to be equal (this is the equality the PrizeVault bug also breaks: "assets redeemed from the yield vault" vs "assets transferred to the receiver"). Here they can diverge whenever `withdrawal.amount > builder_balance`.

The spec's own test suite demonstrates and asserts this exact divergence as expected behavior:
- `test_builder_withdrawal_insufficient_balance`: builder has 1 ETH balance, pending withdrawal requests 5 ETH; the resulting `payload_expected_withdrawals` entry has `amount = 5 ETH` (the full requested amount), while `builders[0].balance` becomes `0` (only 1 ETH actually deducted) [4](#0-3) .
- `test_builder_withdrawal_insufficient_balance_realistic_bounds` confirms the same pattern with more realistic values: `withdrawal.amount` in the committed payload equals the requested amount, while the builder's balance deduction is capped to what was actually available [5](#0-4) .

The input-space documentation for `process_withdrawals` itself records this as the intended semantics ("Builder pending: `actual_amount = min(requested_amount, builder.balance)`... withdrawal amount field is the requested amount") [6](#0-5) , but the field committed to `state.payload_expected_withdrawals` — the thing that actually determines what the EL mints — is the uncapped `requested_amount`, not the `actual_amount`.

A builder's balance can legitimately fall below the sum of its queued `builder_pending_withdrawals` entries because those entries are created from committed bid values at settlement time (`settle_builder_payment` appends `payment.withdrawal`, whose `amount` was fixed when the bid was accepted) [7](#0-6) , while the builder's balance can independently be consumed by other slots/payments in between settlement and the withdrawal sweep being processed. Any accumulation of pending withdrawal obligations exceeding the current balance — even completely non-adversarial insolvency — triggers this mismatch.

### Impact Explanation
This is a **Critical** impact: Gwei is created and paid to a party (the `fee_recipient` named in the pending withdrawal) that never had a corresponding balance decrease on the consensus layer. Every honest, spec-following execution-layer client will mint the full `withdrawal.amount` because that is what the beacon block/payload commits to; the consensus layer's own bookkeeping shows a smaller (saturated) deduction. This breaks the fundamental Gwei-conservation invariant between the CL and EL — new, unbacked ETH enters circulation at the fee recipient's address.

### Likelihood Explanation
Likelihood is high in any state where a builder's obligations (queued `builder_pending_withdrawals`) exceed its current `balance` — this can occur through ordinary operation (multiple payments settled in sequence exceeding the deposit) and does not require any malicious peer, coalition, or client bug; the divergence is baked into the reference spec logic itself and is exercised/asserted by the existing unit tests, confirming it is reachable via normal state transitions.

### Recommendation
Cap the amount placed into the committed `Withdrawal` (in `get_builder_withdrawals`, and correspondingly in `get_builders_sweep_withdrawals`/`apply_withdrawals`) to the builder's actual available balance at commitment time, mirroring what `get_pending_partial_withdrawals` already does for validators (compute `balance_after_withdrawals` and clamp the withdrawal amount to it *before* it is added to `withdrawals` and thus before it is committed to the payload). Concretely, `get_builder_withdrawals` should track a running "available builder balance" across `prior_withdrawals` (analogous to `get_balance_after_withdrawals`) and set `amount=min(withdrawal.amount, running_balance)` when constructing each `Withdrawal`, so that the amount promised to the EL always equals the amount that will be deducted from `state.builders[*].balance`.

### Proof of Concept
Using the existing spec test harness (`prepare_process_withdrawals` / `run_gloas_withdrawals_processing` / `assert_process_withdrawals`), the already-present test `test_builder_withdrawal_insufficient_balance` demonstrates the bug directly [4](#0-3) :

1. Set `state.builders[0].balance = 1 ETH`.
2. Queue `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, amount=5 ETH, fee_recipient=X)]`.
3. Run `spec.process_withdrawals(state)`.
4. Observe: `state.payload_expected_withdrawals[0].amount == 5 ETH` (this is what the EL will credit to `X`), while `state.builders[0].balance == 0` (only 1 ETH was ever debited on the CL).
5. Net effect: 4 ETH worth of Gwei is minted at `X` on the execution layer with no corresponding consensus-layer balance decrease anywhere in the system — a direct violation of Gwei conservation.

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
