### Title
Global unstaked-aware `overall_connection_rate_limiter` allows distributed unstaked flood to starve legitimate staked TPU connections - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`run_server` gates every incoming QUIC connection attempt on a single, stake-agnostic global `TokenBucket` (`overall_connection_rate_limiter`) before any per-peer or stake information is available. An attacker distributing connection attempts across many source IPs, each individually under the per-IP `ConnectionRateLimiter` threshold, can keep this shared bucket permanently drained, causing `incoming.ignore()` to be invoked for all new connections — staked or not — cluster-wide.

### Finding Description
In `run_server`, before any handshake completes and before stake can be determined, every `Incoming` connection is checked against a single process-wide bucket: [1](#0-0) [2](#0-1) 

This check runs strictly before the per-IP `rate_limiter.is_allowed()` check and long before `get_connection_stake` can identify a peer's stake weight (stake is only knowable via `get_remote_pubkey(connection)` after the TLS handshake completes, as seen in `get_connection_stake`): [3](#0-2) 

The bucket refills at `TOTAL_CONNECTIONS_PER_SECOND = 2500.0` with `MAX_CONNECTION_BURST = 1000` capacity, both fixed constants independent of any config: [4](#0-3) 

Meanwhile the per-IP limiter (`ConnectionRateLimiter`) only restricts each individual source IP to `max_connections_per_ipaddr_per_min` (default 8/min, i.e. roughly 0.13/sec sustained, times 10 burst per the comment in `run_server`): [5](#0-4) [6](#0-5) 

Because the per-IP limiter operates independently per key, an attacker controlling ~hundreds to low-thousands of distinct source IPs (each staying just under its individual per-IP allowance) can aggregate a sustained rate above 2500 connections/sec plus the 1000 burst, keeping `overall_connection_rate_limiter.current_tokens()` at 0 continuously. Since the check order is global-bucket-first, per-IP-second, and no stake information exists at this stage, legitimate staked validators' connection attempts are shed identically to attacker traffic via `incoming.ignore()`, which as the code comment states is deliberate ("shed fast... before a peer has asserted control over their ip address"). This design choice explicitly avoids doing anything stake-aware pre-handshake to prevent IP-spoofing attacks, but as a side effect provides no protection once an attacker legitimately owns many real IPs (e.g., a botnet), which does not require IP spoofing at all.

### Impact Explanation
This is a non-RPC remote resource exhaustion / ingest liveness DoS: cluster-wide denial of new TPU QUIC connections, including from staked validators, under default configuration values (`TOTAL_CONNECTIONS_PER_SECOND`, `MAX_CONNECTION_BURST`, `DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE` are all defaults not requiring any special validator configuration). This matches the "non-RPC remote resource exhaustion" bounty category. Note the impact is limited to *new* connection establishment; existing already-established QUIC connections between staked peers are unaffected by this ignore path, since `incoming.ignore()` only applies to the initial `Incoming` accept queue, not established `Connection`s.

### Likelihood Explanation
The attacker only needs unprivileged network access from many source IPs (a botnet, cloud IP pool, or similar) — no stake, no keys, no privileged access. Sustaining ~2500 handshake-initiation packets/sec split across enough distinct IPs to stay under each IP's individual token-bucket allowance is well within the capability of a modest botnet (this is a volumetric SYN/Initial-packet-style flood, cheaper than completing full handshakes, since `current_tokens() == 0` is checked pre-accept). The attack is fully repeatable and does not require IP spoofing (the code's own rationale for not being "smarter" earlier only applies to spoofing-based attacks, not to an attacker that owns real IPs).

### Recommendation
Consider stake-independent but load-aware mitigations that don't require pre-handshake identity, such as: increasing `MAX_CONNECTION_BURST`/`TOTAL_CONNECTIONS_PER_SECOND` to scale with cluster/validator hardware limits and separately reserving a fraction of the global budget/queue depth for anti-amplification-safe address-validated retries; or moving to QUIC's built-in Retry/address-validation token mechanism to cheaply distinguish return-path-controlling clients before consuming the scarce global token budget, so that a widely-distributed flood must at minimum complete a round trip per source IP, raising attacker cost proportionally to the number of distinct IPs needed to reach the aggregate threshold.

```rust
// streamer/src/nonblocking/quic.rs (integration-style test, conceptual)
// Spawn a quic server via setup_quic_server with default QuicStreamerConfig.
// From N > MAX_CONNECTION_BURST (1000) distinct source IPs (e.g. using SO_REUSEADDR/
// virtual interfaces or a multi-homed test harness), each issuing connection attempts
// at a rate below max_connections_per_ipaddr_per_min, but aggregating > 2500/sec + 1000 burst.
//
// Expected: stats.connection_rate_limited_across_all increases continuously while the
// flood is sustained, and a subsequent legitimate high-stake client's connection attempt
// (from an unused IP) is also ignored (never reaches setup_connection / register_connection),
// i.e. it will time out at the client's QUIC handshake stage because incoming.ignore()
// was called at the server before accept().
```
Because reproducing thousands of distinct source IPs in a unit test environment is impractical, the exact aggregate threshold behavior is best validated via a scaled-down variant: temporarily reduce `TOTAL_CONNECTIONS_PER_SECOND`/`MAX_CONNECTION_BURST` in a test build and drive the flood from a smaller number of local addresses (e.g. loopback aliases `127.0.0.2`..`127.0.0.50`) to confirm `stats.connection_rate_limited_across_all` climbs and a subsequent "legitimate" connection from an unused IP is also rejected via the same `overall_connection_rate_limiter.current_tokens() == 0` branch at [7](#0-6) .
