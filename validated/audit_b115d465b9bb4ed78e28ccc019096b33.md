### Title
Empty-members multisig with `num_confirmations = 0` permanently freezes attached deposit - (`multisig-factory/src/lib.rs::create`, `multisig2/src/lib.rs::new`)

### Summary
`MultisigFactory::create` forwards attacker-chosen `members` and `num_confirmations` unchecked to the deployed `multisig2` contract's `new`. `new` only asserts `members.len() >= num_confirmations`, which is trivially satisfied by `members = []`, `num_confirmations = 0`. Any attacker can deploy such a multisig, attach the minimum deposit, and the resulting account can never process any request because `current_member()` always returns `None` for an empty member set.

### Finding Description
The invariant under test is: `deployed multisig members.len() >= num_confirmations` AND `members.len() >= 1` (a live signer must exist). The `new` constructor only checks the first part: `assert(members.len() >= num_confirmations as usize, ...)` [3](#0-2) . With `members = []` and `num_confirmations = 0`, `0 >= 0` holds, so initialization succeeds and no member is ever added via `add_member` (the loop over an empty `members` vec does nothing) [5](#0-4) .

The factory itself performs zero validation on `members` or `num_confirmations` before creating the account, depositing funds, and calling `new` [4](#0-3) .

Every state-mutating entrypoint (`add_request`, `confirm`, `delete_request`) requires `current_member()` to return `Some`, which is only true if the caller (predecessor account or signer's access key) is present in `self.members` [6](#0-5) [2](#0-1) . Since `members` is empty, `self.members.contains(&member)` is always false, so `current_member()` always returns `None`, and every call panics with "Caller ... is not a member of this multisig" or "Must be validated above". There is no other path (no owner override, no admin recovery) to add a member or otherwise touch the account's balance, since `AddMember`/`SetNumConfirmations` actions can only be reached through `execute_request`, which can only be reached through a successfully confirmed request, which requires a member to exist in the first place.

### Impact Explanation
Any NEAR attached during `create` (the attacker's own minimum deposit, matching the target account's minimum balance requirement) becomes permanently locked in the newly created `<name>.<factory>` account: no account (not even the attacker who created it) can ever satisfy `current_member()`, so no `Transfer`, `AddMember`, or `SetNumConfirmations` request can ever be added or confirmed. This is a **Critical - funds permanently frozen** condition per the stated impact taxonomy, though notably the attacker only freezes their own deposit (no third-party funds are at risk) since nobody else would be tricked into sending funds to a multisig they didn't set up themselves. The severity classification concerns the multisig's degenerate-state invariant break itself: "a deployed multisig always has at least num_confirmations members" is violated, and any funds later sent to this address (e.g., by a mistaken depositor, or the attacker demonstrating the freeze) are unrecoverable.

### Likelihood Explanation
Trivial and fully repeatable: any unprivileged account can call `create` with `members: []`, `num_confirmations: 0`, and the minimum required attached deposit (enough to cover account creation/storage). No special permissions, keys, or preconditions are needed, and the exploit can be repeated across arbitrarily many `name` values.

### Recommendation
In `multisig2::new`, require `members.len() >= 1` (or `members.len() >= max(num_confirmations, 1)`), rejecting `num_confirmations == 0` outright and ensuring at least one live member always exists after initialization. Additionally, the factory (`multisig-factory/src/lib.rs::create`) should perform matching validation before scheduling the `create_account`/`deploy_contract`/`transfer` promise, to fail fast and avoid wasting the attacker's/any depositor's funds on an unrecoverable account.
