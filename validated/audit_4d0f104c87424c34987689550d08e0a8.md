### Title
Removed multisig member's stale confirmation still counts toward execution threshold, allowing requests to execute below the live-member quorum - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm()` counts approvals purely by the size of the `confirmations: HashSet<String>` stored per request, without re-validating at execution time that every entry still corresponds to a current member of `self.members`. `delete_member()` only purges pending *requests originally submitted by* the removed member; it does not purge that member's *confirmations* recorded on requests submitted by other members. This lets a request execute a `Transfer` (or other privileged action) with fewer live-member approvals than `num_confirmations` is supposed to guarantee.

### Finding Description
`confirm()` reaches execution when `confirmations.len() as u32 + 1 >= self.num_confirmations`: [1](#0-0) 

`delete_member()` cleans up outstanding requests filtered by `r.member == member` (the request's *original submitter*) and removes the `num_requests_pk` entry for that member, but never scans `self.confirmations` to strip that member's public key/account-id string out of confirmation sets belonging to requests submitted by *other* members: [2](#0-1) 

Sequence:
1. Multisig has 4 members (`K = 3`).
2. Member `A` submits a legitimate-looking `Transfer` request `X` (`add_request`, 0 confirmations recorded).
3. Member `D` (later found compromised or removed for unrelated reasons) confirms `X` while still a member → `confirmations = {D}`.
4. Member `B` confirms `X` → `confirmations = {D, B}` (2 of 3, not yet executable).
5. Members legitimately submit and pass a separate `DeleteMember { member: D }` request to remove `D` (e.g., because `D`'s key was compromised). `delete_member()` runs; because request `X` was *submitted by* `A`, not `D`, it is left untouched — `D`'s stale confirmation on `X` remains in `self.confirmations`.
6. `D` is now no longer in `self.members` and `current_member()` would reject any *new* action from `D`. However, the already-stored entry for `D` is never invalidated.
7. Member `C` confirms `X` → `confirmations.len() + 1 == 3 >= num_confirmations (3)` → `execute_request` runs and the transfer is sent.

The transfer executed with confirmations from `{D, B, C}`, but `D` was not a member at the time of execution. Effectively only 2 *live* members (`B`, `C`) approved the request, even though the contract's guarantee is that `num_confirmations` distinct **current** members must approve before funds move. The binding `confirmations counted == live-member approvals` is broken: `confirmations.len() == num_confirmations` no longer implies `num_confirmations` current members approved.

The v1 `multisig/src/lib.rs` contract has the analogous structure (`confirmations` set of `Base58PublicKey`, `remove_request` used from `delete_key`/`confirm`, filtered similarly by submitter), so the same class of gap is expected there as well, though full confirmation of its `delete_key` cleanup logic was not completed within the available search budget.

### Impact Explanation
This is a Critical-severity binding violation matching "a multisig request executed below threshold": a privileged operation (fund transfer, key addition, contract upgrade, etc.) can be executed with fewer genuinely live-member confirmations than the configured `num_confirmations`, because a removed member's historical approval is silently retained and counted. In the worst case, if the removed member colludes with an attacker or the removal itself is what an attacker orchestrates (e.g. socially engineering removal of an honest signer whose earlier confirmation on a still-pending malicious request is left in place), fewer surviving honest signers than `K` can push an approved-looking request through.

### Likelihood Explanation
This does not require any protocol violation, malicious infrastructure, or code deployment outside what's already in scope — it arises purely from the intended, documented multisig workflow (submit → confirm → confirm → remove a member → confirm) using only the contract's public methods `add_request`, `confirm`, and `execute_request` (via `DeleteMember`). Any multisig where membership changes over time (a normal, expected lifecycle event) while requests are pending is exposed. The scenario requires a request to still be pending when a confirming member is removed, which is a very plausible operational sequence (e.g., emergency member removal for a suspected key compromise while other requests are mid-flight).

### Recommendation
When a member is deleted, `delete_member()` must also strip that member's identity string from every entry in `self.confirmations` for all *remaining* requests (not just requests it originally submitted), or `confirm()`/`execute_request()` must re-validate, at execution time, that every account/key present in the stored `confirmations` set is still contained in `self.members` before counting it toward the threshold.

### Proof of Concept
Using the existing test harness in `multisig2/src/lib.rs`:
1. Initialize `MultiSigContract::new(members(), 3)` with 4 members `A, B, C, D`.
2. As `A`, call `add_request` for a `Transfer` to `bob()` (no auto-confirm).
3. As `D`, call `confirm(request_id)` → confirmations = 1.
4. As `B`, call `confirm(request_id)` → confirmations = 2.
5. As `A`+2 members, submit and confirm a `DeleteMember{ member: D }` request (self-request, executes immediately once it reaches 3 confirmations, e.g. via `add_request_and_confirm` chained by 3 members) — `D` is removed from `self.members`; `self.confirmations` for the original `Transfer` request is untouched because `delete_member` only filters `self.requests` by submitter `== D`, and `A` (not `D`) submitted it.
6. As `C` (still a member), call `confirm(request_id)` → `confirmations.len() + 1 == 3 >= num_confirmations` → `execute_request` fires and the `Transfer` promise is scheduled, despite `D` no longer being a member. Inspecting `c.get_confirmations(request_id)` before step 6 would still show `D`'s identity present, confirming the stale approval was counted. [2](#0-1) [1](#0-0)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
