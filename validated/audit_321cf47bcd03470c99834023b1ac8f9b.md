### Title
Fee-payment bypass via `value_len`/register-content mismatch in BLS12-381 multiexp host functions - (File: runtime/near-vm-runner/src/logic/bls12381.rs)

### Summary
The `bls12381_impl!` macro computes the per-element gas charge (`elements_count = value_len / ITEM_SIZE`) strictly from the caller-supplied `value_len` argument, but the actual bytes processed by `$g_multiexp` are taken from `data = get_memory_or_register!(self, value_ptr, value_len)`, which is not guaranteed to have length equal to `value_len` when the register-read path is used. Since `g1_multiexp`/`g2_multiexp` iterate over the fetched `data` with `data.chunks_exact(ITEM_SIZE)` (bls12381.rs:176), any element present in `data` beyond what `value_len` accounted for is executed (one `blst_p1_mult`/`blst_p2_mult` scalar multiplication each) without being charged the `bls12381_g1_multiexp_element`/`bls12381_g2_multiexp_element` fee.

### Finding Description
In the shared macro: [1](#0-0) 

`elements_count` and the associated `pay_per($bls12381_element, elements_count)` charge are derived solely from the untrusted `value_len` parameter, before the actual input buffer is materialized. The buffer used for computation, `data`, is fetched afterward via `get_memory_or_register!(self, value_ptr, value_len)` and handed to the element-processing routine: [2](#0-1) 

`$g_multiexp` processes every full `ITEM_SIZE` (`96+32=128` for G1, `192+32=224` for G2) chunk contained in `data` via `data.chunks_exact(ITEM_SIZE)`, performing one `blst_p_mult` (scalar multiplication) per chunk — this is the actual metered unit of work — regardless of how many chunks were paid for based on `value_len`.

The vulnerability hinges on the size relationship between `value_len` (used only for the gas charge) and the true length of the bytes returned by `get_memory_or_register!`. When `value_ptr` selects the register-read code path, the number of bytes actually returned is governed by the contents previously stored in that register (e.g., via a prior `write_register`/host call), not by the numeric value of `value_len`. An attacker-controlled contract can:
1. Populate a register with `k * 128` bytes of valid, in-group `(G1 point || scalar)` items (via ordinary wasm host calls it fully controls, no privileged access required).
2. Invoke `bls12381_g1_multiexp(value_len, value_ptr = <sentinel selecting the register-read path>, register_id)` with `value_len` chosen so that `value_len / 128 < k` (e.g. `value_len = k*128 - 1`), while the register actually resolved by the call still yields the full `k*128`-byte buffer.
3. `pay_per` charges only `elements_count = value_len/128 = k-1` scalar multiplications, but `g_multiexp`'s `chunks_exact(128)` loop executes all `k` `blst_p_mult` operations because it operates on `data.len()`, not on the value that was billed.

This breaks the metering-totality invariant that every `blst_p_mult`/`blst_p2_mult` must be pre-paid via `bls12381_g1_multiexp_element`/`bls12381_g2_multiexp_element`.

### Impact Explanation
This is a fee/gas-metering bypass: real CPU work (BLS12-381 scalar multiplications, which are computationally expensive relative to their advertised cost) is performed for free or under-priced. Repeated across many receipts within a single gas-limited chunk, this lets an attacker force chunk producers to perform substantially more computation than the gas paid for, which is a resource/DoS-adjacent metering-bypass finding (not a direct fund-theft or state-root divergence issue by itself), matching the "fee payment bypass" bounty category tied to metering totality.

### Likelihood Explanation
The attacker needs only an ordinary deployed wasm contract capable of (a) writing arbitrary byte content into a register through standard host calls and (b) calling `bls12381_g1_multiexp`/`bls12381_g2_multiexp` with crafted `value_len`/`value_ptr` arguments — both fully available to any unprivileged account with a deployed contract. No validator, network, or privileged access is required, and the exploit is trivially repeatable across many transactions/receipts.

### Recommendation
Compute `elements_count` (and the associated gas charge) from the length of the resolved `data` buffer (`data.len() / ITEM_SIZE`) after `get_memory_or_register!` resolves the actual bytes, rather than from the caller-supplied `value_len` before resolution — mirroring the pattern already used in `$p_decompress` (`let elements_count = data.len() / ITEM_SIZE;`, bls12381.rs:205), or explicitly assert `data.len() == value_len` and reject the call otherwise before charging/using `value_len`.

### Proof of Concept
Unit-test plan (in `runtime/near-vm-runner/src/logic/tests/bls12381.rs` or a dedicated gas-accounting test):
1. Build a valid multiexp input buffer of `k = 1000` `(96-byte G1 point || 32-byte scalar)` items (`128000` bytes total), each point in-group.
2. Write this buffer into a register via the VM logic test harness's register-write path.
3. Call `bls12381_g1_multiexp(value_len = 127999, value_ptr = <sentinel for register read>, register_id = <output>)` on that logic instance.
4. Assert the call succeeds (`Ok(0)`, i.e. a valid result is produced, proving all 1000 elements were actually processed).
5. Read `ext_costs_counter[ExtCosts::Bls12381G1MultiexpElement]` from the gas counter/profile and assert it equals `999` (`value_len/128`) while the correct/expected charge should have been `1000` (`data.len()/128`), demonstrating one full unpaid `blst_p1_mult`.
