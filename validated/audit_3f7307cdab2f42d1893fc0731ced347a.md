### Title
Stale rejection weight is never retracted when a signer switches its vote to accept, letting the miner's coordinator wrongly kill a block that has legitimate quorum support - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tallies signer support for a proposed block using two independently-maintained counters, `total_weight_approved` and `total_weight_rejected`, gated by two different dedup sets (`gathered_signatures` for accepts, `responded_signers` for rejects). A signer is explicitly permitted by the v0 signer protocol to change its vote from `Rejected` to `Accepted` for the same block (`should_reevaluate_reject_reason`), but when that happens the listener adds the signer's weight to `total_weight_approved` without ever subtracting it from `total_weight_rejected`. The stale rejection weight persists, exactly like the `GovLocks` bug where `deposits[user]` kept accruing/depleting independently of the actual, transferable `govLocks` balance and drifted out of sync with ground truth.

### Finding Description
`BlockStatus` in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` holds: [1](#0-0) 

On `BlockResponse::Accepted`, weight is added to `total_weight_approved` only if the signer's slot isn't already present in `gathered_signatures`: [2](#0-1) 

On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` only if the signer's slot isn't already present in `responded_signers`: [3](#0-2) 

These are two separate "ground truths" for the same underlying fact (this signer's current vote), just like `deposits[msg.sender]` and the `govLocks` balance were two separate ground truths for the same fact (how many `LOCKS` this address is entitled to withdraw). Crucially, the accept path checks `gathered_signatures` (not `responded_signers`), so a signer that previously rejected and is now accepting is *not* blocked from incrementing `total_weight_approved` — but nothing decrements `total_weight_rejected` for that signer. The signer.rs logic confirms vote-switching from reject to accept is a legitimate, expected path for several reject reasons (`UnknownParent`, `NotFoundError`, `NoSortitionView`, `ConnectivityIssues`, `TestingDirective`, `InvalidTenureExtend`, `ConsensusHashMismatch`, `NoSignerConsensus`, `NotRejected`, `Unknown`): [4](#0-3) 

and `should_reevaluate_block` explicitly re-sends a fresh response (which can be `Accepted`) for a block previously answered: [5](#0-4) 

The miner's `SignerCoordinator::wait_for_signer_blocks` then evaluates the reject condition *before* the accept condition using these drifted tallies: [6](#0-5) 

Because `total_weight_rejected` keeps the stale weight of a signer that has since switched to `Accepted`, `total_weight_rejected + weight_threshold > total_weight` can become true (and be evaluated first) even though the same signer's current, live vote is now counted toward `total_weight_approved`. The miner concludes `SignersRejected` and drops/excludes the block's transactions, even in a scenario where the true, current set of signer votes has enough weight to approve the block.

### Impact Explanation
This is a liveness wedge affecting a single mining round: a block that currently has legitimate ≥70% approving weight (counting each signer's live, current vote once) can be miner-side killed as globally rejected because of a phantom, never-retracted rejection weight left over from a signer's earlier, since-superseded vote. This matches the "signer wedged" / "acting on a stale...tally" class in the rules — the equality broken is "aggregated weight tally vs. the set of currently verified accepts," directly analogous to `deposits` mapping vs. `govLocks` balance drifting apart because the tracked quantity can change (a vote can flip) without the tracked ledger being updated to match.

### Likelihood Explanation
No majority collusion or malicious key is required. This is triggered by ordinary operational conditions already exercised in-repo (e.g. `ConnectivityIssues`, `UnknownParent` while the node hasn't yet processed the block's parent, or a `NoSortitionView`/`NoSignerConsensus` timing gap) — conditions explicitly enumerated as "re-evaluable" reject reasons in `should_reevaluate_reject_reason`. A single miner delaying/reproposing a block (a normal, unprivileged, one-slot-miner action already covered by `check_pending_block_validations`/reproposal flows) is enough to produce a reject-then-accept sequence from any signer, at which point the coordinator-side drift occurs unconditionally.

### Recommendation
Do not maintain `total_weight_approved` and `total_weight_rejected` as two independently-incrementing accumulators. Track a single per-signer "current vote" (analogous to relying only on the `govLocks` balance instead of a separate `deposits` ledger), and derive `total_weight_approved`/`total_weight_rejected` by summing weights of signers currently in the accept set and reject set respectively, removing a signer's slot from the opposing set when its vote flips (i.e., when accepting, remove the slot from `responded_signers`'/rejection accounting exactly as `add_block_signature` does for `block_rejection_signer_addrs` in the signer-side `signerdb.rs`, which does clean up the opposite table). Concretely, in `stackerdb_listener.rs`, when handling `BlockResponse::Accepted`, if the slot was previously counted in `total_weight_rejected`, subtract the signer's weight from `total_weight_rejected` before adding it to `total_weight_approved` (and vice versa, for symmetry, though the reject-path already guards via `responded_signers`).

### Proof of Concept
1. Miner proposes block `B`. Signer `S` (weight `w`) currently cannot find `B`'s parent block yet and returns `BlockResponse::Rejected` with `RejectReason::ValidationFailed(UnknownParent)`. `StackerDBListener` records this: `responded_signers.insert(S)`; `total_weight_rejected += w`.
2. Shortly after, `S`'s node catches up; the miner re-proposes/re-broadcasts `B` (a normal reproposal path). `should_reevaluate_reject_reason` returns `true` for `UnknownParent`, so `S` re-evaluates and this time sends `BlockResponse::Accepted` with its signature.
3. In `StackerDBListener`, the accept handler checks only `gathered_signatures.contains_key(&slot_id)` (false, since `S` never signed before), so it adds `w` to `total_weight_approved`. `total_weight_rejected` is left untouched at its stale value containing `w`.
4. Now `total_weight_approved + total_weight_rejected > total_weight` by `w`. If enough other signers' weight is already present in `total_weight_rejected` from earlier legitimate transient rejections (each similarly stale), `total_weight_rejected.saturating_add(weight_threshold) > total_weight` can become true in `SignerCoordinator::wait_for_signer_blocks`, which is checked *before* the approval branch, causing the miner to return `SignersRejected` and drop the block/txids even though the live signer votes (correctly summed once each) would have reached the 70% approval threshold.

/// Determine if a block should be re-evaluated based on its rejection reason˝
fn should_reevaluate_reject_reason(block_info: &BlockInfo) -> bool {
    if let Some(reject_reason) = &block_info.reject_reason {
        match reject_reason {
            RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
            | RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
            | RejectReason::NoSortitionView
            | RejectReason::ConnectivityIssues(_)
            | RejectReason::TestingDirective
            | RejectReason::InvalidTenureExtend
            | RejectReason::ConsensusHashMismatch { .. }
            | RejectReason::NoSignerConsensus
            | RejectReason::NotRejected
            | RejectReason::Unknown(_) => true,
            RejectReason::ValidationFailed(_)
            | RejectReason::RejectedInPriorRound
            | RejectReason::SortitionViewMismatch
            | RejectReason::ReorgNotAllowed
            | RejectReason::InvalidBitvec
            | RejectReason::PubkeyHashMismatch
            | RejectReason::InvalidMiner
            | RejectReason::NotLatestSortitionWinner
            | RejectReason::InvalidParentBlock
            | RejectReason::DuplicateBlockFound
            | RejectReason::IrrecoverablePubkeyHash
            | RejectReason::ProblematicTransactions
            | RejectReason::ProposalTooOld => {
                // No need to re-validate these types of rejections.
                false
            }
        }
    } else {
        false
