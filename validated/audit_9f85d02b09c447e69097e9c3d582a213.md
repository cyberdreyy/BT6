## Title
Stale confirmations combined with a lowered `num_confirmations` threshold let a request execute with fewer real approvals than the threshold ever required at any single point in time - ([File: multisig2/src/lib.rs])

### Summary
Both multisig contracts (`multisig/src/lib.rs` and `multisig2/src/lib.rs`) check the required approval count for *any* pending request against the **current, mutable** `num_confirmations` field rather than the threshold that was in effect when the confirmations were collected. Because `SetNumConfirmations` can lower this value while other requests are still pending with partial confirmations, a request that never actually gathered the number of approvals its threshold demanded at any single instant can still be pushed through by one incidental extra `confirm()` call after the threshold drops.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` decides whether to execute a request purely by comparing the live count of stored confirmations to `self.num_confirmations` at the time of the call: [1](#0-0) 

`self.num_confirmations` is a single mutable field that can be changed at any time via the `SetNumConfirmations` action, which itself only needs to reach the *current* threshold to execute: [2](#0-1) 

Confirmations recorded on a request are never re-validated or invalidated when `num_confirmations` changes; they are simply stored in a `HashSet` per `request_id` and persist until the request executes or is deleted: [3](#0-2) 

The invariant the contract is supposed to enforce is:
`confirmations_collected_for_R >= num_confirmations_at_the_time_those_confirmations_were_meant_to_authorize_R`

What the code actually enforces is:
`confirmations_collected_for_R (accumulated under a possibly higher, now-stale threshold) >= num_confirmations_current (possibly lowered later)`

Concretely: with threshold K=3, a request `R` (e.g. a `Transfer`) can sit with 2 confirmations indefinitely (2 < 3, never executes). If the threshold is later lowered to 2 — through an entirely separate, unrelated `SetNumConfirmations` request that legitimately collects 3 confirmations from members with no knowledge of `R` — `R`'s already-stored 2 confirmations now satisfy the *new* threshold. `R` does not auto-execute, but the very next `confirm()` call on `R` by any member (who may believe, based on the original threshold of 3, that their approval is only "one of three needed," and is unaware the effective bar had already been met by 2 confirmations gathered under a different regime) triggers `execute_request`, moving funds or taking privileged actions without the number of approvals that were ever concurrently valid for a K=3 policy. The same construction and the same unguarded field exist in the older `multisig/src/lib.rs`: [4](#0-3) [5](#0-4) 

This is the same bug class as the external report: a time/threshold-dependent value (`lockWindow` there, `num_confirmations` here) is mutated live, and code paths that read it assume consistency across two different reads (`internalLatestData` calls in Oval, "confirmations vs. threshold" here), creating a window where stale state (an old cached price / stale pending confirmations) is combined with a new parameter to produce an outcome — sudden price change / request execution — that was never valid under any single consistent state.

### Impact Explanation
If `num_confirmations` is ever reduced while any request has partial confirmations recorded under the higher, prior threshold, that request can later execute having collected strictly fewer real approvals than the threshold enforced at any instant in the request's lifetime. Since `MultiSigRequestAction::Transfer` and `FunctionCall` actions can move NEAR out of the multisig account or drive arbitrary contract calls, this breaks the fundamental K-of-N custody guarantee of the multisig: "a multisig request executed below threshold," which the rules explicitly list as a Critical impact. Money can leave the account, or privileged actions (adding/removing keys, deploying new contract code) can be taken, with an authorization level below what the multisig's policy was ever meant to allow concurrently.

### Likelihood Explanation
This requires: (1) a pending request with partial confirmations under a higher threshold, (2) a subsequent, independent lowering of `num_confirmations` (a normal, foreseeable multisig lifecycle event — e.g., removing a departing member's key and correspondingly reducing the threshold), and (3) one more ordinary `confirm()` call on the stale request by any member who is not necessarily colluding, simply unaware the effective bar has silently dropped. None of these steps require the foundation, a contract owner, a victim's private key, or a malicious validator — only routine multisig operation combined with request ordering that any member (or a member who is partially compromised/malicious and deliberately times their confirmations) can arrange. Because `add_request`/`confirm` impose no linkage between a request's required threshold and the threshold active when it was created, exploitation depends only on transaction ordering across two independently-valid multisig requests, which is realistic in active production multisigs that periodically re-tune `num_confirmations`.

### Recommendation
Snapshot the required threshold at request-creation time (store `required_confirmations` inside `MultiSigRequestWithSigner`) and check confirmations against that snapshot instead of the live `self.num_confirmations`. Alternatively, when `SetNumConfirmations` is executed, iterate all outstanding requests and either (a) re-validate/reject any that would now be under-confirmed relative to their original creation-time threshold, or (b) require pending requests to be re-confirmed from scratch under the new threshold before they can execute.

### Proof of Concept
1. Deploy `multisig2` with 5 members and `num_confirmations = 3`.
2. Attacker who controls (via key compromise, insider access, or partial collusion) 2 of the 5 member keys, `M1` and `M2`, calls `add_request` with a `Transfer` action draining funds to an attacker-controlled account → `request_id = R`.
3. `M1` calls `confirm(R)` → 1 confirmation stored; `2.len()+1=1 < 3`, no execution — see check at [6](#0-5) 
4. `M2` calls `confirm(R)` → 2 confirmations stored; `2+1=3` would trigger, but here `confirmations.len()==1` before this call so `1+1=2 < 3`; request remains pending with 2 confirmations.
5. Independently, legitimate members later submit and confirm (with 3 legitimate confirmations, e.g. `M3, M4, M5`) a `SetNumConfirmations{num_confirmations: 2}` request for an unrelated, legitimate reason (e.g. removing a departed member). This executes and sets `self.num_confirmations = 2`.
6. Any member (e.g. `M3`, who never looked at `R`, or who confirms `R` believing under the old policy an additional confirmation beyond 2 was still required) calls `confirm(R)`. Now `confirmations.len()==2`, so `2+1=3 >= self.num_confirmations (2)` → `execute_request(R)` fires, transferring the funds, even though at no point did 3 members concurrently agree to authorize `R` under the K=3 policy that was in force when `R` was created and confirmed by `M1`/`M2`.

Note: this walkthrough is based on static analysis of `multisig2/src/lib.rs` and `multisig/src/lib.rs`; there is no executable test harness available in this session to run the exact sequence, so the exploit path is derived directly from the code logic cited above rather than confirmed via a live transaction trace.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
