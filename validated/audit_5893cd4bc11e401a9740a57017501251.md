### Title
Missing minimum-shares (slippage) check on ERC4626 deposits lets a vault share-price manipulator steal pool principal - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` parks undrawn credit-facility funds in an external ERC4626 `vault`. Every deposit path goes through `_depositToVault`, which calls `vault.deposit(_assetAmount, address(this))` and accepts whatever amount of shares comes back, with no `minSharesOut`/slippage bound. An unprivileged attacker who is a user of the ERC4626 vault (or a direct token sender) can inflate the vault's share price (first-deposit + donation / sandwich) right before `onStartEpoch` or `_repay` deposits pool funds, so the borrower mints ~0 shares while the vault keeps the underlying. The attacker then redeems its own shares and extracts the deposited assets. The shortfall is recorded as `vaultLoss` via `_vaultNetInterest`/`totalInterestDueNow`, so the loss is socialized onto tranche LPs at the next `stopEpoch` (or becomes a borrower default), exactly matching the "positive/zero-but-lower-than-expected swap output" bug class.

### Finding Description
In `ProgrammableBorrower.sol`:

```solidity
function _depositToVault(uint256 _assetAmount, uint256 _principalAssets) internal {
  if (_assetAmount == 0) return;
  uint256 shares = vault.deposit(_assetAmount, address(this));  // no minShares check
  if (epochAccountingActive && _principalAssets != 0) {
    epochDepositedToVault += _principalAssets;
  }
  emit DepositedIntoVault(_assetAmount, shares);
}
```

Called from:
- `onStartEpoch` (`_depositToVault(underlyingToken.balanceOf(address(this)), 0)`) — parks the entire idle facility balance at epoch start, a predictable, manager-triggered event that can be sandwiched.
- `_repay` (`_depositToVault(totalRepaidAssets, ...)`) — re-deposits borrower repayments while an epoch is active, also sandwichable.

Neither call validates `shares` against the deposited assets (e.g., via `previewDeposit` ± tolerance). The accounting treats the *assets sent* as principal baseline:

- `onStartEpoch` snapshots `startAssets = balanceOf + _currentVaultAssets()` **before** depositing and sets `epochStartVaultAssets = startAssets`, so the just-deposited amount is part of the principal baseline.
- `_vaultNetInterest` computes `netDelta = bufferedVaultDelta + (currentVaultAssets + epochWithdrawnFromVault) - (epochStartVaultAssets + epochDepositedToVault)`. If the deposit minted ~0 shares, `_currentVaultAssets()` is near zero while `epochStartVaultAssets` includes the full deposit → `loss ≈ deposit size`.
- `totalInterestDueNow` returns `totalGain - loss`, so the stolen amount reduces the interest `IdleCDOEpochVariant` reads at `stopEpoch`, directly lowering tranche NAV/AA-BB waterfall value. If the vault can't cover the pull, `onStopEpoch` shortfall handling routes to `_handleBorrowerDefault`, again socializing the loss to LPs through the default waterfall (`defaultPendingClaimBasis`, `postDefaultRequests`).

Existing guards do not stop it: there is no skim/donation isolation for vault deposits, no `minShares` parameter, no revert on `shares == 0`, and the `shortfall > _currentVaultAssets()` check in `onStopEpoch` only decides whether to revert vs. let the transfer fail — it does not recover funds.

### Impact Explanation
Direct theft of pool principal: the attacker extracts (approximately) the full deposited amount from the vault by redeeming their own shares after the borrower mints ~0 shares. The pool records it as vault loss, so tranche holders (BB first, then AA) absorb it via reduced `totalInterestDueNow` or the default waterfall — solvency and loss-waterfall invariants broken. Loss is bounded by the facility's idle balance, which is typically the bulk of pool TVL for a programmable borrower.

### Likelihood Explanation
Requires a permissionless ERC4626 vault whose share price can be inflated (donation or low-liquidity first-deposit state) and the ability to sequence a vault deposit/donation before `startEpoch`/`repay` — both callable by honest roles at predictable times, and `repay`/`borrow` flows are attacker-observable in the mempool. Medium likelihood: depends on vault liquidity/share state, but `onStartEpoch` deposits the entire idle balance in one shot, so a single successful sandwich is catastrophic.

### Recommendation
Add a slippage bound to `_depositToVault`, e.g.:

```solidity
uint256 expectedShares = vault.previewDeposit(_assetAmount);
uint256 shares = vault.deposit(_assetAmount, address(this));
if (shares < expectedShares * (BPS - maxSlippageBps) / BPS) revert SlippageExceeded();
```

and/or compute a `minShares` from a sanity price (e.g., `convertToShares(_assetAmount)` with tolerance). Alternatively use `vault.mint(expectedShares, ...)` so the share count is fixed and excess asset cost reverts. Apply the same bound in `onStartEpoch` and `_repay` deposit paths; consider also bounding `vault.redeem`/`withdraw` in `onStopEpoch`/`_borrow`/`emergencyExitVault` with a max-shares-burned check.

### Proof of Concept
Foundry fork-style PoC against a mock/vulnerable ERC4626 (e.g., a fresh OpenZeppelin `ERC4626` with no virtual shares defense):

```solidity
// setup: pool deployed with ProgrammableBorrower pb, honest deposits, buffer phase.
// attacker is a normal vault user.
// 1. Attacker seeds vault: vault.deposit(1, attacker) -> 1 share
// 2. Attacker inflates price: underlying.transfer(vault, donation) with donation >> pb idle balance
//    -> share price now ~donation per share.
// 3. Manager calls cdoEpoch.startEpoch(...) -> sendFundsToBorrower -> pb.onStartEpoch(...)
//    -> _depositToVault(idleBalance): mints idleBalance * 1 / donation ~ 0 shares
// 4. Attacker calls vault.redeem(1, attacker, attacker) -> receives ~donation + idleBalance
//    attacker profit ~= idleBalance
// 5. Warp to epoch end, manager calls stopEpoch -> totalInterestDueNow reduced by ~idleBalance
//    (or pool defaults); assert tranche NAV / claimable funds decreased by stolen amount.
```

Assert `pb.vaultSharesBalance() == 0` after `startEpoch` while `epochStartVaultAssets` includes the deposit, then show `vaultLoss() ≈ idleBalance` and attacker balance delta ≈ `idleBalance`.
