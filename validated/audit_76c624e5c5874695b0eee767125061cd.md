## Title
`apply_withdrawals` in Gloas can commit a builder withdrawal `amount` to the execution layer that exceeds the actual decrease applied to the builder's CL balance, minting Gwei that was never destroyed - (File: `specs/gloas/beacon-chain.md`)

### Summary
In the Gloas fork, builder payments are queued as `BuilderPendingWithdrawal` entries and later turned into `Withdrawal` objects with the full, uncapped requested `amount`. When those withdrawals are applied to consensus state, the builder's on-chain balance is only decreased by `min(withdrawal.amount, builder_balance)`, but the `Withdrawal.amount` that is committed to `state.payload_expected_withdrawals` — which the execution layer is required to honor by minting ETH to the recipient — is never adjusted to match the actual (possibly smaller) balance decrease.

### Finding Description
`get_builder_withdrawals` builds each `Withdrawal` directly from the pending withdrawal's requested `amount`, with no clamping to the builder's current balance: [1](#0-0) 

That withdrawal list becomes `state.payload_expected_withdrawals`, which the spec explicitly states the execution layer "is required to honor": [2](#0-1) 

However, when the withdrawal is actually applied to consensus state, the builder's balance deduction is capped to whatever balance is currently available: [3](#0-2) 

Contrast this with the analogous validator-sweep case, where `decrease_balance` also saturates at zero, but the spec's own commentary acknowledges this creates a "net supply inflation" risk and treats it as a known, examined trade-off for validators: [4](#0-3) 

For builders, though, there is no equivalent narrowing of `withdrawal.amount` before it is written into `payload_expected_withdrawals`. The committed `Withdrawal.amount` (what the EL mints to `fee_recipient`) and the actual consensus-side balance decrease (`min(amount, builder_balance)`) can diverge whenever the builder's balance is smaller than the amount it agreed to pay. The test suite explicitly documents and asserts this divergent behavior as intended: [5](#0-4) 

Builder payment amounts originate from the builder's own bid value at `apply_parent_execution_payload`/`settle_builder_payment` time: [6](#0-5) [7](#0-6) 

Because settlement of a builder payment can be delayed by up to roughly an epoch (via `builder_pending_payments`/`process_builder_pending_payments`), and because builders can also submit multiple bids/payments against the same balance across slots, it is possible for a builder's `Builder.balance` to have fallen below a previously-committed payment amount by the time that payment is finally converted into a `Withdrawal` and applied. In that scenario, `apply_withdrawals` only burns `builder_balance` (less than `amount`) from `state.builders[...].balance`, yet `payload_expected_withdrawals` — the value the execution layer commits to minting to `fee_recipient` — still records the full, uncapped `amount`.

### Impact Explanation
This breaks the Gwei conservation equality: the execution layer mints `withdrawal.amount` Gwei-equivalent ETH to the recipient address, while the consensus layer only destroys `min(amount, builder_balance)` from the builder's balance. The difference is Gwei created out of nothing and paid to whichever address the builder designated as `fee_recipient` (a non-owner in the sense that it did not correspond to burned stake). Per the report's own equality-break criteria ("a Gwei created, destroyed or paid to a non-owner"), this is a Critical-class issue if reachable, since it is a supply-inflating discrepancy between CL commitment and CL-side balance accounting, executed unilaterally by the builder's own payment/bid behavior — no other party's cooperation or malicious client is required.

### Likelihood Explanation
Reachability depends on whether a builder can legitimately end up with `Builder.balance < amount` for a payment it already committed to when a bid was accepted. The spec does not appear to enforce, at withdrawal-application time, that pending builder payments are always backed by sufficient current balance (a builder can have concurrently accruing payments/exits and multiple settlements racing against the same balance across epochs). Confirming the precise sequence that produces this state (e.g., interaction between `process_builder_pending_payments`, multiple pending payments, and builder exit/full-sweep withdrawals) requires deeper tracing of `Builder.balance` mutation sites, which is present but was not exhaustively enumerated here.

### Recommendation
In `apply_withdrawals` (or earlier, in `get_builder_withdrawals`/`settle_builder_payment`), clamp the `Withdrawal.amount` that is written into `payload_expected_withdrawals` to `min(requested_amount, builder_balance)` at the time the withdrawal is finalized, so the amount the execution layer is instructed to mint always matches the amount actually deducted from `state.builders[...].balance`.

### Proof of Concept
1. A builder accrues two pending payments (or a pending payment plus another balance-reducing event) such that, by the epoch/slot the first payment settles into `builder_pending_withdrawals`, `Builder.balance` is smaller than the settled `amount` (see `settle_builder_payment`, `specs/gloas/beacon-chain.md:1518-1527`).
2. `get_builder_withdrawals` emits a `Withdrawal` with the full, unclamped `amount` from the pending withdrawal entry (`specs/gloas/beacon-chain.md:1802-1834`), which is placed into `state.payload_expected_withdrawals`.
3. `apply_withdrawals` decreases `state.builders[builder_index].balance` by only `min(withdrawal.amount, builder_balance)` (`specs/gloas/beacon-chain.md:1923-1931`), i.e., strictly less than `withdrawal.amount`.
4. The execution layer, honoring `payload_expected_withdrawals`, mints the full `withdrawal.amount` to `fee_recipient`, while the consensus layer only destroyed the smaller, capped amount from the builder's balance — net Gwei created without a matching burn, exactly mirroring `test_builder_withdrawal_insufficient_balance` (`tests/core/pyspec/eth_consensus_specs/test/gloas/block_processing/test_process_withdrawals.py:114-156`), which explicitly asserts `withdrawal.amount == 5 ETH` (requested) while `builders[0].balance` is only reduced from 1 ETH to 0.

##### New `get_builder_withdrawals`

```python
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

**File:** specs/gloas/beacon-chain.md (L1977-1990)
```markdown
*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
