### Title
Cross-job run-role escalation via unrestricted "run" role assignment in AuthenticateExternalInitiator - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` unconditionally sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` for any valid EI credential, without binding that role to the EI's own bridge/job. Because `RequiresRunRole`/`GetAuthenticatedUser` only checks `user.Role`, and `PipelineRunsController.Create` treats the presence of *any* `SessionUserKey` object (including this synthetic EI user) as `isUser == true`, a valid credential for external initiator A can be used to trigger a run for an arbitrary integer job ID belonging to an unrelated job/bridge B.

### Finding Description
`AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) validates the EI's access key/secret against `store.FindExternalInitiator` and `bridges.AuthenticateExternalInitiator`, then stores both the `ExternalInitiator` object (`SessionExternalInitiatorKey`) and a brand-new, unscoped `User{Role: UserRoleRun}` object (`SessionUserKey`) in the gin context: [1](#0-0) 

This session-user object carries no reference back to the specific `ExternalInitiator` (`ei`) that was authenticated — it is a generic run-role user usable by any downstream handler that calls `GetAuthenticatedUser`.

The route `POST /v2/jobs/:ID/runs` is registered under the `userOrEI` group, which accepts `AuthenticateExternalInitiator`, `AuthenticateByToken`, or `AuthenticateBySession`, and is wrapped only with `auth.RequiresRunRole`: [2](#0-1) 

`RequiresRunRole` only checks `user.Role != UserRoleView`, it does not distinguish a real logged-in run-role user from the synthetic EI-derived user, and does not look at `SessionExternalInitiatorKey` at all: [3](#0-2) 

`PipelineRunsController.Create` then reads `isUser, _ := auth.GetAuthenticatedUser(c)` intending, per its own comment, to prevent EI credentials from running jobs by numeric job ID ("only users are allowed to run jobs using int IDs - EIs not allowed"): [4](#0-3) 

However, because `AuthenticateExternalInitiator` also populates `SessionUserKey`, `GetAuthenticatedUser` returns `ok == true` for EI-authenticated requests just as it would for a real user — the code has no way to tell the two apart at this point. `GetAuthenticatedExternalInitiator` (which *would* reveal that the caller is actually an EI, and for which bridge) is never consulted in this handler: [5](#0-4) 

As a result, an EI credential bound to bridge/job A satisfies `isUser`, passes `RequiresRunRole`, and can supply any int32 job ID in the URL to trigger `prc.App.RunJobV2(ctx, jobID, nil)` for job B, which has no relation to EI A's bridge. There is no ownership/ACL check tying the EI identity to the target job anywhere in this call path.

### Impact Explanation
This is an authorization/role-scoping bypass: unauthorized triggering of pipeline runs on jobs the caller's credential was never authorized for. This matches the "unauthorized job run" impact class — a holder of a narrow, single-bridge EI credential can force execution of arbitrary jobs (any job addressable by int32 ID), potentially causing unwanted on-chain transactions, unintended contract writes, oracle responses, or resource exhaustion/DoS via unbounded run triggering, all attributable to a credential that was supposed to be scoped to one job/bridge only.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only a single valid EI access key/secret pair (issued for any one bridge/job), which is the credential class explicitly assumed compromised in the prompt. The exploit requires a single HTTP `POST /v2/jobs/<targetIntID>/runs` request carrying `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers — no additional privilege, session, or admin action is needed, and it is fully repeatable for any target job whose numeric ID is known or guessable.

### Recommendation
Do not silently promote EI authentication to a generic run-role `User`. Either:
1. In `AuthenticateExternalInitiator`, avoid setting `SessionUserKey` to an unscoped user; instead have `RequiresRunRole`-protected job-run handlers explicitly check `GetAuthenticatedExternalInitiator` and verify the target job's bridge/webhook spec matches the authenticated EI's name/ID before proceeding, or
2. In `PipelineRunsController.Create`, replace the `isUser` check with an explicit check that rejects EI-originated sessions (`GetAuthenticatedExternalInitiator` present) for the int32-job-ID path, and require an ownership check binding the EI to job B whenever an EI is allowed to trigger a run at all.

### Proof of Concept
Go handler-level integration test (to be added near `core/web/pipeline_runs_controller_test.go`):
1. Create two jobs, Job A (bound to `ExternalInitiator` "EI-A") and Job B (unrelated job, could be OCR or any int32-addressable job type, owned by a different bridge/consumer).
2. Insert `ExternalInitiator` "EI-A" with its own `AccessKey`/`Secret` via `FindExternalInitiator`/`bridges.AuthenticateExternalInitiator` fixtures (see `cltest` helpers for EI creation).
3. Send `POST /v2/jobs/<JobB.ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to EI-A's credentials.
4. Assert: response is **not** `401 Unauthorized`/`403 Forbidden`, and instead a pipeline run resource for Job B is returned (`200 OK` with `presenters.PipelineRunResource`), demonstrating that credentials scoped to EI-A were able to trigger Job B.
5. Contrast with expected/fixed behavior: the handler should return `422`/`403` because EI-A is not associated with Job B.

```go
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
