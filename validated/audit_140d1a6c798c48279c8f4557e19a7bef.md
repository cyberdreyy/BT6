# Vulnerability Analysis

### Title
Stale `lastWithdrawRequest` lets an old pending receipt escape a `stopEpochWithDuration` loss haircut and claim at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` applies a stop-epoch loss to the **entire** `pendingWithdraws` bucket — which aggregates receipts from multiple request epochs — but records the haircut under a single key, `lossRecoveryPriceByEpoch[epochNumber]`, i.e. the *current* epoch only. `_claimLossAdjustedWithdrawRequest` later looks up the haircut exclusively through `lastWithdrawRequest[_user]`, which stores only the user's *most recent* request epoch. A user whose receipt was requested in an earlier epoch (and who never re-requested) has `lastWithdrawRequest` pointing to an epoch with no stored price, so the loss-adjusted claim path returns 0 and `_claimFundedWithdrawRequest` pays the full un-haircut `withdrawsRequests[_user]` at par. This is the same bug class as the DittoETH report: bad debt is applied to a position (`pendingWithdraws` bucket) without updating the per-position freshness marker (`lastWithdrawRequest`), so the recorded state no longer reflects the applied loss.

### Finding Description
In `IdleCreditVault`:

- `requestWithdraw` sets `lastWithdrawRequest[_user] = currentEpoch` and adds to `withdrawsRequestsByEpoch[_user][currentEpoch]` and the aggregate `pendingWithdraws` (lines 277-294). A user may hold a receipt from an older epoch and simply never request again, keeping `lastWithdrawRequest` at the old epoch.
- On `stopEpochWithDuration` with `_lossAmount`, `previewLossAdjustedWithdrawFunds` splits the loss pro rata between **all** pending receipts and active LPs — including receipts from prior epochs still inside `pendingWithdraws` (lines 440-460). `collectWithdrawFunds` then stores a single `lossRecoveryPriceByEpoch[epochNumber]` (current epoch) and zeroes `pendingWithdraws` (lines 411-421).
- `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest(_user)`, which reads `lossEpoch = lastWithdrawRequest[_user]` (line 790). For the stale-epoch user, `lossRecoveryPriceByEpoch[lossEpoch] == 0`, so it returns 0 without clearing the receipt. Execution falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` in full (lines 319-349) — the epoch gate passes because `epochNumber` was incremented during `deposit()` inside the same `stopEpoch` flow (lines 607-611), so `epochNumber > lastWithdrawRequest[_user]`.
- The guard in `requestWithdraw` (lines 263-271) only prevents *opening a new request* while holding a loss-adjusted receipt at `lastWithdrawRequest`; it does nothing for a receipt that was haircut under a *different* epoch key than the one stored.

Broken invariant: one receipt, one (haircut-adjusted) payout. The strategy funded only `pendingBasis - pendingLoss`, but the stale-epoch receipt withdraws its full basis, draining underlying that backs the `lossRecoveryPriceByEpoch` claims of all other pending receipts of that epoch.

### Impact Explanation
Direct theft of unclaimed yield/withdrawal funds by an unprivileged tranche holder. The attacker withdraws `(1 - lossRecoveryPrice/1e18) * claimBasis` more than entitled; the shortfall is borne by other pending receipt holders whose loss-adjusted claims can no longer be fully paid (insolvency of the funded claim reserve). Loss magnitude scales with the attacker's old-epoch pending basis and the realized loss fraction.

### Likelihood Explanation
Requires: (a) the user holds a withdraw receipt from an epoch earlier than the epoch in which the loss is realized — achievable by requesting in epoch N and waiting; receipts survive across epochs since claiming is permissionless-any-time, and (b) the honest manager calls `stopEpochWithDuration` with a nonzero `_lossAmount`, a normal protocol flow for realized losses. No privileged action by the attacker is needed; attacker is a regular KYC'd lender/tranche holder. Note: the attacker's own receipt also escapes the haircut, so the attack is self-executing on the next `claimWithdrawRequest`.

### Recommendation
In `collectWithdrawFunds`, when `pendingBasis > _amount`, store the loss price for every epoch that contributed to `pendingWithdraws`, or key receipts' haircut lookup by claim epoch rather than `lastWithdrawRequest`. Minimal fix: in `_claimLossAdjustedWithdrawRequest`/`_claimFundedWithdrawRequest`, iterate the user's per-epoch receipts (`withdrawsRequestsByEpoch`) and apply `lossRecoveryPriceByEpoch[e]` for each epoch `e` individually instead of only `lastWithdrawRequest[_user]`; alternatively block `collectWithdrawFunds` haircuts while `pendingWithdraws` contains receipts whose request epoch differs from `epochNumber`, or require claim/clear of prior-epoch receipts at request time (extend the existing guard to check all epochs, not only `lastWithdrawRequest`).

### Proof of Concept
```solidity
// test/foundry/IdleCreditVault.t.sol style, fork/mainnet-config harness
function test_StaleEpochReceiptEscapesLossHaircut() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // Attacker and victim deposit; epoch N starts
    idleCDO.depositAA(amount);                 // attacker
    _depositWithUser(VICTIM, amount);          // victim AA
    _startEpochAndCheckPrices(0);

    // Attacker requests withdraw in epoch N
    vm.prank(ATTACKER);
    cdoEpoch.requestWithdraw(attackerTrancheBal, address(AAtranche));
    // Victim requests in epoch N as well (same pending bucket)
    vm.prank(VICTIM);
    cdoEpoch.requestWithdraw(victimTrancheBal, address(AAtranche));

    // Epoch N ends normally (no loss): borrower repays fully
    _stopCurrentEpochWithApr(initialProvidedApr);   // epochNumber -> N+1
    // Both receipts are claimable at par now, but attacker does NOT claim
    // and does NOT open a new request: lastWithdrawRequest[ATTACKER] stays N.

    // Victim also leaves receipt pending (still in pendingWithdraws).

    // Epoch N+1 runs; at stop the manager realizes a loss.
    vm.prank(manager);
    cdoEpoch.startEpoch();
    vm.warp(cdoEpoch.epochEndDate() + 1);

    uint256 pendingBasis = strategy.pendingWithdraws(); // includes BOTH old receipts
    (uint256 pendingToFund, uint256 activeLoss) =
        strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    // fund borrower with reduced amount, then stop with loss
    deal(defaultUnderlying, borrower, fundsNeeded);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(apr, 0, duration, lossAmount);
    // lossRecoveryPriceByEpoch[N+1] = price < 1e18; pendingWithdraws = 0
    // epochNumber incremented to N+2 inside deposit()

    // Attacker claims: _claimLossAdjustedWithdrawRequest checks
    // lossRecoveryPriceByEpoch[lastWithdrawRequest=N] == 0 -> skips,
    // _claimFundedWithdrawRequest pays full withdrawsRequests[ATTACKER] at par.
    uint256 balPre = underlying.balanceOf(ATTACKER);
    vm.prank(ATTACKER);
    cdoEpoch.claimWithdrawRequest(); // wraps strategy.claimWithdrawRequest
    uint256 stolen = underlying.balanceOf(ATTACKER) - balPre;

    // Attacker got full basis despite the haircut applied to the bucket.
    assertGt(stolen, attackerBasis * strategy.lossRecoveryPriceByEpoch(N+1) / 1e18);

    // Victim's loss-adjusted claim is now underfunded: strategy is short
    // (attacker's excess == victim's haircut), i.e. insolvency of the funded reserve.
}
```
