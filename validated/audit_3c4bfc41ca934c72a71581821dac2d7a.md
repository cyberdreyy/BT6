### Title
Double-free analog: stale per-epoch withdraw basis pays at par after a loss-adjusted epoch — users can claim the un-haircutted amount twice - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2017-9078 is a double free in cleanup of TCP listeners: two cleanup paths release the same resource. The credit-vault analog is the dual cleanup of a user's withdraw receipt: `_claimLossAdjustedWithdrawRequest` only clears the receipt whose epoch equals `lastWithdrawRequest[_user]`, while `_claimFundedWithdrawRequest` pays the aggregate `withdrawsRequests[_user]` at par. A user who holds a loss-adjusted receipt from an earlier epoch can stack a second withdraw request on top, moving `lastWithdrawRequest` to the later epoch; the stale haircutted basis is then claimed in full through the funded path — the same underlying claim is effectively released twice (once haircutted, once at par).

### Finding Description
`requestWithdraw` records both a per-user aggregate and a per-epoch basis:

- `withdrawsRequests[_user] += _amount`
- `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`
- `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) 

When a `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` is called with `pendingToFund < pendingBasis`; it sets `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and zeroes only the **global** `pendingWithdraws`. The per-user `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch` entries keep their full, un-haircutted basis. [2](#0-1) 

On claim, `claimWithdrawRequest` runs two paths:

1. `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` and only pays `lossRecoveryPriceByEpoch[lossEpoch]` — i.e., it can only ever haircut the **most recent** request epoch. If `lastWithdrawRequest` points at a later epoch that has no loss price, it returns 0 and clears nothing. [3](#0-2) 

2. `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — which still includes the earlier loss-epoch basis — **at par**, burning the receipt tokens and transferring via `_transferFundedClaim`. [4](#0-3) 

So the cleanup is epoch-scoped for the loss path but aggregate-scoped for the funded path — structurally the same "one resource, two inconsistent frees" as the Dropbear listener bug. The attacker only needs a second `requestWithdraw` in a later epoch to shift `lastWithdrawRequest` past the loss epoch.

### Impact Explanation
Direct theft / insolvency. The strategy only holds `lossRecoveryPrice` fraction of the loss-epoch receipts (funded via `collectWithdrawFunds`), yet the attacker withdraws the full pre-loss basis. The excess `(1 - lossRecoveryPrice) * basisN` is paid from underlying belonging to other funded claimants and LPs, breaking solvency and the loss-waterfall invariant that `stopEpochWithDuration` is supposed to enforce on pending receipts. For a 50% loss epoch, a user with a 100k receipt steals 50k of other users' funded claims, plus can repeat across users.

### Likelihood Explanation
Requires only unprivileged actions sequenced around honest privileged calls:

1. Epoch N buffer: attacker calls `cdo.requestWithdraw` (queue or direct) — `lastWithdrawRequest = N`, `withdrawsRequests += X`.
2. Manager calls `stopEpochWithDuration(apr, 0, duration, lossAmount)`; borrower funds `pendingToFund < X_total`. `lossRecoveryPriceByEpoch[N+1']` is set (epoch numbering per `deposit()` bump inside stopEpoch); global `pendingWithdraws = 0`.
3. Attacker does **not** claim. In the next buffer they call `requestWithdraw` again with a dust amount `ε`. Now `lastWithdrawRequest = N+1`, `withdrawsRequests = X + ε`.
4. Epoch N+1 stops normally. `epochNumber > lastWithdrawRequest` passes the gate at line 326.
5. Attacker calls `claimWithdrawRequest`: loss path sees `lossRecoveryPriceByEpoch[N+1] == 0` → skips; funded path pays `X + ε` at par.

Existing guards do not stop it: the `epochNumber <= lastWithdrawRequest` check passes, `_clearWithdrawClaimForEpoch` is only invoked for the latest epoch, and nothing zeroes stale `withdrawsRequestsByEpoch` entries of earlier loss epochs when a new request is made.

### Recommendation
When a new `requestWithdraw` is recorded while the user still has uncleared basis in an epoch with a non-zero `lossRecoveryPriceByEpoch`, either (a) force-settle the loss-adjusted portion first (migrate it to a haircutted claim basis, not the par aggregate), or (b) iterate all epochs with `lossRecoveryPriceByEpoch != 0` in `withdrawsRequestsByEpoch` during the funded claim, not just `lastWithdrawRequest`. A minimal fix is to track `withdrawsRequests[_user]` net of loss-adjusted basis (i.e., reduce it by the haircut at `collectWithdrawFunds` time proportionally, or exclude epochs with a loss price from the funded aggregate and always pay them through the recovery-price path).

### Proof of Concept
Foundry fork test (sketch, modeled on `test/foundry/IdleCDOEpochQueue.t.sol` flows):

```solidity
// 1. Attacker deposits and requests withdraw of X tranches (buffer of epoch N)
uint256 tr = _depositWithUser(attacker, 100_000e6);
_requestWithdrawWithUser(attacker, tr);

// 2. Epoch ends with loss; borrower funds only pendingToFund < pendingBasis
vm.warp(cdoEpoch.epochEndDate() + 1);
uint256 pendingBasis = strategy.pendingWithdraws();
uint256 activeBasis  = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
uint256 totalBasis   = activeBasis + pendingBasis;
uint256 lossAmount   = totalBasis / 2;                       // ~50% loss
(uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
deal(address(underlying), strategy.borrower(), repay, true);
vm.prank(strategy.borrower()); underlying.approve(address(cdoEpoch), repay);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), lossAmount);
// lossRecoveryPriceByEpoch[lossEpoch] ~= 0.5e27; pendingWithdraws == 0
// BUT strategy.withdrawsRequests(attacker) still == full basis X

// 3. Next buffer: attacker makes a dust request to move lastWithdrawRequest
_requestWithdrawWithUser(attacker, 1); // minimal tranche amount
vm.prank(manager); cdoEpoch.startEpoch();
_stopCurrentEpochWithApr(10e18);       // honest stop, full funding of epsilon

// 4. Claim: funded path pays X (unhaircutted) + epsilon at par
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker); // via cdo.claimWithdrawRequest path
cdoEpoch.claimWithdrawRequest(...);    // whichever CDO entrypoint
uint256 got = underlying.balanceOf(attacker) - balPre;
// assert got > funded basis: strategy only received ~X/2 for epoch-N receipt
assertGt(got, fundedForEpochN, "attacker drained unhaircutted basis");
```

The final assertion shows the strategy paid out roughly `X * (1 - lossRecoveryPrice)/RECOVERY_FULL` more than was funded for that receipt — value taken from other claimants' reserve.

```text
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
