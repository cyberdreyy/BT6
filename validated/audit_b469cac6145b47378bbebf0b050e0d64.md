### Title
Stale rejection weight is never reclaimed when a signer re-evaluates a block from `Rejected` to `Accepted`, allowing an inconsistent-guard tally to wedge block signing - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener`'s per-block vote tally (`BlockStatus`) uses two different "already counted?" guards for the two response kinds: the `Accepted` path gates on `block.gathered_signatures.contains_key(&slot_id)`, while the `Rejected` path gates on `block.responded_signers.insert(slot_id)`. Because `responded_signers` is a single set shared by both paths but the two paths query different data structures to decide whether a given signer's vote has already been tallied, a signer's weight can be added into `total_weight_rejected` and later *also* added into `total_weight_approved` for the very same block, without the earlier rejection ever being reversed. This mirrors the gitoxide flaw: two guards that are supposed to answer "is this the authoritative source/state for this identity" instead inspect two different, decoupled pieces of state.

### Finding Description
`BlockStatus` tracks per-block voting weight for the miner-side coordinator: [1](#0-0) 

For `BlockResponse::Accepted`, the "have we already counted this slot" check is against `gathered_signatures` (a map only ever populated by the Accept branch): [2](#0-1) 

For `BlockResponse::Rejected`, the "have we already counted this slot" check is against the shared `responded_signers` set: [3](#0-2) 

Walking the state: if signer `S` (slot `k`) sends `Rejected` first, `responded_signers.insert(k)` succeeds, `total_weight_rejected` gets `S`'s weight, and `gathered_signatures` is untouched (rejection path never writes to it). If `S` later sends `Accepted` for the *same block* — which is a normal, sanctioned transition in the signer's own state machine (`LocallyRejected -> LocallyAccepted: re-evaluated`, per `BlockInfo::check_state`) — the Accept-path guard `!gathered_signatures.contains_key(&k)` is still `true` (nothing has ever written to `gathered_signatures` for `k`), so `total_weight_approved` is incremented for `S` as well. `total_weight_rejected`, however, is **never decremented** anywhere in this file: there is no code path that removes a slot from the rejected tally when that signer's later message supersedes the rejection. The two guards are answering different questions ("does this slot exist in the Accept-only map" vs. "does this slot exist in the shared responded set") instead of the same one ("what is this signer's current, authoritative vote"), exactly analogous to the gitoxide bug where the existence check inspected a different section than the one that actually supplied the value used downstream.

This is reachable by a single one-slot signer's legitimate re-evaluation (no majority, no other signer's key, no StackerDB-transport trick needed) and is entirely inside the node-side coordinator code explicitly listed as in-scope (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`, feeding `signer_coordinator.rs`'s `get_block_status`).

### Impact Explanation
`SignCoordinator::get_block_status` (in `signer_coordinator.rs`) uses the running `total_weight_rejected` to decide when a "blocking minority" (>30% by weight) has forever doomed a proposal: [4](#0-3) 

Because `total_weight_rejected` accumulates and is never reclaimed even after the rejecting signer changes their mind and accepts, a set of signers that individually and validly re-evaluate from reject→accept can leave the aggregate rejected-weight figure permanently inflated. If enough such stale rejections accumulate to cross the 30% blocking-minority threshold — even though the *current* state of every signer is "accept" — the coordinator will erroneously conclude the block is dead (`NakamotoNodeError::SignersRejected`) and abandon a proposal that, under the true current vote state, should have reached the 70% approval threshold. This is a liveness break: the miner can be wedged away from a block that a supermajority of signers actually currently support, matching the in-scope "liveness wedge" / "aggregated-weight vs verified-accepts equality" criteria (High impact class: a signer set being unable to move forward on a validly-approved block due to stale accounting).

### Likelihood Explanation
No majority collusion, no other signer's key, and no transport/StackerDB manipulation is required — only the documented, sanctioned local re-evaluation transition `LocallyRejected -> LocallyAccepted`, which the codebase's own flow docs describe as valid (`BlockInfo::check_state`, "re-evaluated" transitions), combined with normal network conditions where a proposal's chainstate acceptability legitimately flips for some signers (e.g., after a reorg permit is granted, timing-based re-checks, or first-seen invalid transaction status changing). Any single signer taking this path exercises the asymmetric guard.

### Recommendation
Use one consistent, authoritative "has this signer already been tallied, and in which direction" state per slot (e.g., store the last counted vote kind per `slot_id` and, on a vote-kind change, subtract the previous weight from the old bucket before adding it to the new one), rather than gating `Accepted` on `gathered_signatures` and `Rejected` on `responded_signers`. Both response kinds must consult the same per-slot bookkeeping so that flipping a vote correctly moves weight between `total_weight_approved` and `total_weight_rejected` instead of only ever adding.

### Proof of Concept
1. Coordinator submits proposal for block `B` to signer `S` (weight `w_S`), among others.
2. `S` sends `BlockResponse::Rejected` for `B`: `responded_signers.insert(slot_S)` succeeds → `total_weight_rejected += w_S` (per [3](#0-2) ).
3. `S`'s own state machine later legitimately re-evaluates `B` from `LocallyRejected` to `LocallyAccepted` (sanctioned transition) and broadcasts `BlockResponse::Accepted` for the same `signer_signature_hash`.
4. The coordinator's Accept handler checks `!block.gathered_signatures.contains_key(&slot_S)`, which is still `true` (never written by the Reject branch) → `total_weight_approved += w_S` (per [2](#0-1) ).
5. `total_weight_rejected` still includes `w_S`; nothing in this file ever subtracts it.
6. If other signers' weight (whether currently rejecting or via the same stale mechanism) pushes `total_weight_rejected.saturating_add(weight_threshold) > total_weight` in `signer_coordinator.rs`, the coordinator errors with `SignersRejected` and abandons the block, even though `S` (and potentially others in the same situation) currently accept it — demonstrating the aggregated-rejected-weight vs. current-verified-accepts inequality this bug produces.
