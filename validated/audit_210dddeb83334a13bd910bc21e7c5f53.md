### Title
Cross-user response hijacking via `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.handleWebAPITriggerMessage` looks up and delivers a pending user callback keyed solely by `msg.Body.MessageId`, with no binding to the original requester's identity. Because `MessageId` is client-supplied (taken directly from the JSON-RPC request `ID`) and `HandleLegacyUserMessage` silently overwrites any existing `savedCallbacks` entry with the same ID, a second requester who picks a colliding `MessageId` for an in-flight request can hijack the callback slot and receive the response intended for the original requester.

### Finding Description
`HandleLegacyUserMessage` stores the pending callback with no uniqueness/ownership check: [1](#0-0) 
The key, `msg.Body.MessageId`, originates from the JSON-RPC request `ID` supplied by the caller of the gateway's public HTTP endpoint: [2](#0-1) [3](#0-2) 
`msg.Validate()` (invoked in `gateway.ProcessRequest` and inside `HandleLegacyUserMessage`) only checks length/format and signature validity of the message; it never checks that the `MessageId` is globally unique across pending requests from other users: [4](#0-3) 

When a node later posts a matching trigger message, `handleWebAPITriggerMessage` pops whatever callback is currently registered under that `MessageId` and delivers the payload to it, without verifying that the callback belongs to the sender that originated the underlying trigger subscription: [5](#0-4) 

Exploit flow:
1. Victim sends a legitimate legacy request (`web_api_trigger`) with JSON-RPC ID `X`; `savedCallbacks["X"]` is registered pointing to victim's callback.
2. Before a node responds (within the `CallbackMaxAgeSec` window, default 120s), attacker sends their own legacy request choosing the same JSON-RPC ID `X` (nothing prevents an attacker from choosing an ID that they guess/predict a concurrent victim is using, or simply racing many IDs).
3. `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with the attacker's callback — victim's original callback reference is now orphaned.
4. When a DON node responds to the trigger with `MessageId == "X"` (which was meant to serve the victim's subscription), `handleWebAPITriggerMessage` pops the current entry (now the attacker's) and calls `savedCb.SendResponse(...)`, delivering the trigger payload to the attacker instead of the victim.
5. The victim's request silently times out (denial of the victim's expected response) while the attacker receives data not scoped to their own request.

No sender/owner check anywhere between registration (`HandleLegacyUserMessage`) and delivery (`handleWebAPITriggerMessage`) prevents this; the map is keyed purely by attacker-influenceable `MessageId`.

### Impact Explanation
This is a cross-user response confusion vulnerability: an unprivileged, external user of the gateway's public request endpoint can cause data meant for another user's outstanding `web_api_trigger` request to be delivered to themselves, and can simultaneously deny the victim their response. Depending on the payload content of the trigger response (which can include external API/off-chain data configured by the victim's workflow), this constitutes unauthorized disclosure of another user's request result and a targeted denial-of-service against the victim's request — matching the "cross-user response confusion" / unauthorized access to another user's request outcome bounty impact class.

### Likelihood Explanation
The only precondition is the ability to submit two overlapping legacy gateway requests with colliding `MessageId` (JSON-RPC `ID`) values, something any unauthenticated/unprivileged caller of the gateway's public HTTP endpoint can do since `MessageId` is fully attacker-chosen and validated only for length/format, not uniqueness. No node compromise, signature forgery, or elevated privileges are required — an attacker just needs to race a request with the same ID as a victim's in-flight request within the callback TTL window (up to 120s by default), which is feasible especially if IDs are predictable (sequential counters, workflow execution IDs, timestamps) or if the attacker can simply flood many guessed IDs.

### Recommendation
Bind each `savedCallbacks` entry to a unique, non-attacker-controlled key (e.g., a gateway-generated UUID combined with `MessageId`, or `(sender, MessageId)` composite key derived from the verified `msg.Body.Sender`), and reject/queue-separate registration when a `MessageId` collision with a still-pending, different-sender request is detected instead of silently overwriting. On delivery in `handleWebAPITriggerMessage`, verify that the responding trigger message's associated identity (workflow/execution scope) matches the identity that registered the callback before calling `SendResponse`.

### Proof of Concept
Add a test in `handler_test.go`:
1. Call `handler.HandleLegacyUserMessage` with callback `cbA` and a message whose `Body.MessageId = "collide-1"` (signed by nodeA/userA context), simulating victim's pending request.
2. Before resolving it, call `handler.HandleLegacyUserMessage` again with callback `cbB` and a distinct message that nonetheless also carries `Body.MessageId = "collide-1"`, simulating the attacker's overlapping request.
3. Assert `h.savedCallbacks["collide-1"]` now equals the `savedCallback` wrapping `cbB` (proving the overwrite/collision).
4. Trigger `handler.HandleNodeMessage`/`handleWebAPITriggerMessage` with a node response carrying `MessageId = "collide-1"`, and assert that `cbB.Wait()` receives the response (attacker) while `cbA.Wait()` times out — demonstrating the victim (`cbA`) never receives their own response and the attacker (`cbB`) receives it instead, violating the required requester-callback isolation invariant.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
