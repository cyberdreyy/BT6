### Title
Missing role check on `GET /v2/external_initiators` lets view-role users enumerate all EI AccessKeys/OutgoingTokens - ([File: core/web/router.go])

### Summary
The `Index` handler for `/v2/external_initiators` is registered with only `paginatedRequest`, unlike `Create`/`Destroy` which require `auth.RequiresEditRole`, so any authenticated user regardless of role (including `view`) can list every external initiator's `AccessKey` and `OutgoingToken`. The plaintext `Secret`, however, is never persisted and is not part of the `Index` response, so the specific claim of "Secret disclosure" via this endpoint does not hold.

### Finding Description
`v2Routes` wires the endpoints as: [1](#0-0) 
`eia.Index` is reachable by any user who passes `auth.Authenticate` (session or API token), with no `RequiresEditRole`/`RequiresRunRole` gate, whereas `Create`/`Destroy` explicitly require edit role.

`Index` builds its response using `presenters.NewExternalInitiatorResource`: [2](#0-1) 

The presenter used for listing only serializes `Name`, `URL`, `AccessKey`, `OutgoingToken`, `CreatedAt`, `UpdatedAt`: [3](#0-2) 

The plaintext `Secret` field only exists transiently at creation time (`auth.Token.Secret`), is never stored (only `HashedSecret`+`Salt` are persisted), and is only ever returned once via `ExternalInitiatorAuthentication` on `Create`: [4](#0-3) [5](#0-4) 
`bridges.ExternalInitiator` (the DB model) does not carry a plaintext `Secret` field at all, so `Index` structurally cannot leak it. This is confirmed by the existing integration test which asserts only `AccessKey`/`OutgoingToken`/`Name`/`URL` are returned by `Index`: [6](#0-5) 

Role check logic confirms `view`-role users pass `auth.Authenticate` but are only blocked by `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` wrappers, which `Index` lacks: [7](#0-6) 

### Impact Explanation
A `view`-role authenticated user can call `GET /v2/external_initiators` and obtain the `AccessKey` and `OutgoingToken` of every configured external initiator across the node, information that `Create`/`Destroy` intentionally restrict to `edit`-role+ users. `AccessKey` alone is insufficient to authenticate as the external initiator (authentication requires the corresponding `Secret`, matched via `bridges.AuthenticateExternalInitiator`'s hashed comparison) [8](#0-7) , so this does not directly enable impersonation of the EI toward the node. `OutgoingToken`, however, is a credential the node itself sends outward, and its exposure to a lower-privileged user is still an authorization-boundary violation (least-privilege / role-exactness issue) even though it does not meet the bounty-level bar of secret/credential disclosure that grants node compromise, since the corresponding `Secret` needed for authentication bypass is never returned by this endpoint.

### Likelihood Explanation
Trivial and fully repeatable: any authenticated `view`-role session or API token can call the endpoint with no additional preconditions, since the route lacks a role wrapper.

### Recommendation
Wrap `Index` with `auth.RequiresEditRole` (or at minimum `RequiresRunRole`) to match `Create`/`Destroy`, e.g. `authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))`.

### Proof of Concept
Go handler-level integration test (extending `core/web/external_initiators_controller_test.go`):
1. Start app, insert an external initiator via `cltest.MustInsertExternalInitiatorWithOpts`.
2. Create an HTTP client authenticated as a `view`-role user (`app.NewHTTPClient(&cltest.User{Role: sessions.UserRoleView})` or equivalent helper).
3. `GET /v2/external_initiators` and assert current behavior returns `http.StatusOK` with `AccessKey`/`OutgoingToken` populated (demonstrating the authorization gap), while also asserting the response never contains a `secret`/`incomingSecret` field (confirming no Secret leak).
4. After applying the fix, assert the same request returns `http.StatusUnauthorized`/`http.StatusForbidden` for the view-role client, matching `Create`/`Destroy` behavior.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

func AuthenticateExternalInitiator(eia *auth.Token, ea *ExternalInitiator) (bool, error) {
	hashedSecret, err := auth.HashedSecret(eia, ea.Salt)
	if err != nil {

	}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
