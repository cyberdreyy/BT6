Based on my investigation, I found a concrete analog: the CRE gateway HTTP response cache is keyed by a hash that intentionally excludes `WorkflowID`, similarly to how the SecondSwap `stepsClaimed` value was carried over from the "first" context (first vesting sold) and blindly applied to a different context (a new buyer) because the state wasn't scoped to the correct per-entity granularity.

### Title
Gateway HTTP action response cache is scoped only by workflow owner, not by workflow ID, allowing cached responses to be shared across a workflow owner's distinct workflows - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
### Finding Description
The gateway's HTTP capability response cache stores outbound HTTP action responses keyed by `req.Hash()`, which the implementation and its own test suite confirm is computed from method, URL, headers, body and `WorkflowOwner` — explicitly excluding `WorkflowID`: [1](#0-0) [2](#0-1) 

This directly contradicts the documented design intent in the handler's own README, which states the cache key is "generated from workflow ID and request hash" and that entries are "scoped by workflow ID to prevent cross-workflow data leakage": [3](#0-2) 

This is structurally the same root-cause pattern as the referenced SecondSwap bug: a piece of shared state (`stepsClaimed` in SecondSwap; a cached HTTP response here) is meant to be scoped per fine-grained entity (per-listing in SecondSwap; per-workflow here), but is instead only scoped to a coarser identity (the vesting-manager's single slot in SecondSwap; the workflow *owner* here), so state computed/cached in the context of one workflow is silently reused by a different workflow that happens to issue a request with the same method/URL/headers/body under the same owner. The cache lookup path (`makeOutgoingRequest` → `responseCache.Fetch`/`Set`) never differentiates by `WorkflowID`: [4](#0-3) 

### Impact Explanation
If two different workflows belonging to the same owner (which is a realistic, unprivileged scenario — an owner can deploy multiple workflows, and CRE documentation for other flows treats per-workflow isolation as a security boundary, e.g. `SecretsFor`/`refreshSecrets` keying by `workflowID`) issue HTTP action requests with identical method/URL/headers/body but different intended semantics or timing expectations, one workflow's cached (possibly stale, or intended-for-a-different-purpose) response will silently be returned to the other workflow instead of a fresh fetch. Combined with `CacheSettings.Store`/`MaxAgeMs` being attacker/workflow-controlled parameters in the `OutboundHTTPRequest` payload, a workflow author could deliberately warm the cache with a favorable/stale response and have it served to another of their own workflows expecting a fresh external state check, undermining any workflow logic that relies on request freshness (e.g., price feeds, nonce/state checks used as an oracle input) at the point where two workflows share the same owner. This is a cross-workflow "response confusion" class issue analogous to the vesting mix-up: correctness/state is silently shared instead of properly isolated.

### Likelihood Explanation
Likelihood is limited by the fact that the cache is at least scoped to `WorkflowOwner` (confirmed by test), so no cross-*owner* leakage occurs. The vulnerability class only manifests within a single owner's set of workflows that (a) issue byte-identical requests and (b) enable `CacheSettings.Store`/read `MaxAgeMs`. It requires no special privilege beyond deploying/operating a workflow (an unprivileged, ordinary CRE workflow author), and is easily reachable via the documented `HTTP Action` capability flow.

### Recommendation
Include `WorkflowID` in the cache-key hash computation (or otherwise make caching strictly per-workflow, per the documented design), matching the stated "Workflow Isolation" guarantee, so responses fetched/stored for one workflow cannot be transparently served to a different workflow even when owned by the same address. Add a regression test analogous to the existing `TestRequestHash` "different workflowID results in same Hash" case but asserting the opposite (different hash), and update/align the README description of the caching key with the corrected implementation.

### Proof of Concept
Not independently reproducible from static analysis alone since it depends on runtime interaction with actual external endpoints; however, the existing unit test in the repository already demonstrates the root cause deterministically: [2](#0-1) 
This test asserts (as intended current behavior) that `req1.Hash() == req2.Hash()` even when `WorkflowID` differs, which is the exact condition that permits Workflow B to receive Workflow A's cached response via `responseCache.Fetch` in `makeOutgoingRequest`: [5](#0-4) 

**Note on scope/uncertainty:** I could not locate the actual `gateway.OutboundHTTPRequest.Hash()` implementation itself (it lives in the `chainlink-common` dependency, not indexed in this repo), so the exact field list is inferred from the code comment and the test file's confirmed behavior rather than direct inspection of the hash function body. If you need the precise byte-level hash construction, a Devin session with full filesystem/dependency access would be needed to pull in `chainlink-common/pkg/types/gateway`.

func (h *gatewayHandler) makeOutgoingRequest(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
