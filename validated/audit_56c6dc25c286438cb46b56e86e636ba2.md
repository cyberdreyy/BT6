### Title
`check_block_builds_on_highest_block_in_tenure` compares only block **height**, not block **identity**, allowing a proposal to be approved with a superseded sibling as parent - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
`NakamotoBlockProposal::check_block_has_valid_parent` delegates to `check_block_builds_on_highest_block_in_tenure`, which decides whether `self.block.header.parent_block_id` is acceptable by comparing `parent_header.anchored_header.height()` to `highest_header.anchored_header.height()` — it never compares the actual block identifiers. When two competing blocks exist at the same height in the same tenure (a same-height fork/tie), this height-only comparison can return `Ok(())` even though the referenced parent is not the block that `find_highest_known_block_header_in_tenure` would itself pick as canonical.

### Finding Description
`validate()` calls `Self::check_block_has_valid_parent(chainstate, sortdb, &self.block)` exactly once, using the miner-supplied `self.block.header.parent_block_id` [1](#0-0) .

For non-tenure-start blocks, that call reaches `check_block_builds_on_highest_block_in_tenure`, which fetches the "highest known" header for the tenure via `NakamotoChainState::find_highest_known_block_header_in_tenure` and the caller-supplied `parent_header` via `get_block_header(parent_block_id)`, then does:
```
if parent_header.anchored_header.height() != highest_header.anchored_header.height() { reject }
``` [2](#0-1) 

This is a **height** equality check, not an **identity** (block-id) equality check. `find_highest_known_block_header_in_tenure` itself explicitly documents that ties can exist and that different nodes/candidates can differ for the same tenure:
```
/// Get the highest blocks in a given tenure ... at each burn view
///  active in that tenure. If there are ties at a given burn view, they will both be returned
``` [3](#0-2) 
and picks the first candidate whose burn view is on the canonical sortition fork, in an order that does not disambiguate genuine height ties:
```
fn get_highest_canonical_block_header_from_candidates(...) {
    for candidate in candidates.into_iter() {
        let candidate_ch = candidate.burn_view.as_ref().unwrap_or(&candidate.consensus_hash);
        let in_canonical_fork = canonical_sortition_handle.processed_block(candidate_ch)?;
        if in_canonical_fork { return Ok(Some(candidate)); }
    }
    Ok(None)
}
``` [4](#0-3) 

So the equality the check should establish — "the claimed parent IS the block that this node considers the current highest/canonical block of the tenure" — is weakened to "the claimed parent has the same height as *some* block this node considers highest." If two sibling blocks B1 (the block that subsequently becomes canonical) and B2 (a superseded/orphaned sibling) exist at the same height in the same tenure, a proposal whose `parent_block_id == B2` passes this check as long as `B2.height == B1.height`, regardless of which of B1/B2 is actually the current tip returned by `find_highest_known_block_header_in_tenure`. The rest of `validate()` (burn-view lookup, burn amount checks, timestamp/height-contiguity checks) all key off `parent_stacks_header` derived from the attacker-chosen `parent_block_id`, so none of those downstream checks catch that B2 is not the real tip [5](#0-4) .

### Impact Explanation
This breaks the CANONICITY property the comment at the call site promises: "Verify that this block's parent is the highest such block we can build off of" [1](#0-0) . If a signer's node returns `BlockValidateOk` for a block built on a superseded sibling, and the signer signs based on that `Ok`, its signature endorses a block that forks off the non-canonical parent. If enough signer weight is fooled the same way (each independently validating via their own node under the same race), a fork could be finalized — a Critical chain-safety violation (signature valid across a canonicity boundary).

### Likelihood Explanation
The precondition is a genuine height tie for the "highest known block in tenure" — i.e., two Nakamoto blocks at the same height within one tenure both known to the validating node (one becomes canonical, one is superseded). This requires a timing race (two blocks accepted/known in quick succession) rather than any signer-key or node-operator privilege; an attacker only needs their own miner slot to produce a forking block and gossip a proposal referencing the losing sibling immediately after the winning sibling becomes canonical. Whether a node's chainstate DB in practice retains a superseded sibling header long enough for this race to be exploitable is a node-side storage/consensus-acceptance question that could not be fully confirmed in this review (out of scope to verify further per the audit rules, since that mechanic is node-side consensus acceptance) — this is the residual uncertainty in this finding.

### Recommendation
In `check_block_builds_on_highest_block_in_tenure`, replace the height comparison with a strict identity comparison, e.g. compare `parent_header.index_block_hash()` (or `StacksBlockId::new(...)`/`block_id()`) against `highest_header.index_block_hash()`, rejecting the proposal unless the claimed parent is *exactly* the block returned by `find_highest_known_block_header_in_tenure`, not merely one at the same height.

    /// Get the first canonical block header in a vector of height-ordered candidates
    fn get_highest_canonical_block_header_from_candidates(
        sort_db: &SortitionDB,
        candidates: Vec<StacksHeaderInfo>,
    ) -> Result<Option<StacksHeaderInfo>, ChainstateError> {
        let canonical_sortition_handle = sort_db.index_handle_at_tip();
        for candidate in candidates.into_iter() {
            // if burn_view is None, then this is an epoch 2.x header, and since epoch 2.x tenure's correspond
            // to a single stacks block, we can use the miner's tenure sortition as a proxy for canonicity.
            let candidate_ch = candidate
                .burn_view
                .as_ref()
                .unwrap_or(&candidate.consensus_hash);
            let in_canonical_fork = canonical_sortition_handle.processed_block(candidate_ch)?;
            if in_canonical_fork {
                return Ok(Some(candidate));
            }
        }

        // did not find any blocks in candidates
        Ok(None)
    }
