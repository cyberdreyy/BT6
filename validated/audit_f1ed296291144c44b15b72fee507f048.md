### Title
Debug/pprof routes wired without role check inside `authv2` group allow low-privilege 'view' user to dump memory, goroutines, and command-line arguments - ([File: core/web/router.go])

### Summary
The `metricRoutes` function, which registers `net/http/pprof` handlers (`/v2/debug/pprof/cmdline`, `/heap`, `/goroutine`, `/profile`, `/trace`, `/allocs`, `/block`, `/mutex`, `/threadcreate`), is mounted directly inside the `authv2` router group in `v2Routes` [1](#0-0) . Unlike every other sensitive endpoint in that group (keys export/import/delete, user management, transfers), the pprof routes are registered with no `auth.RequiresAdminRole` / `auth.RequiresEditRole` / `auth.RequiresRunRole` wrapper, meaning any user who merely satisfies the group-level `auth.Authenticate(... AuthenticateByToken, AuthenticateBySession)` middleware can reach them [2](#0-1) [3](#0-2) .

### Finding Description
`v2Routes` builds `authv2` as a group requiring only session/token authentication, not a specific role: [4](#0-3) 

All other capability-sensitive routes registered on `authv2` are explicitly wrapped with a role check, e.g. `auth.RequiresAdminRole(ekc.Export)`, `auth.RequiresEditRole(...)`, `auth.RequiresRunRole(...)` [5](#0-4) [6](#0-5) . However, the call to `metricRoutes(authv2)` at line 446 registers the pprof endpoints with no such wrapper: [3](#0-2) [1](#0-0) 

Since `authv2` itself carries no role restriction (only `auth.Authenticate` for identity, not role), any authenticated session — including one belonging to a user with only the 'view' role — passes the group middleware and reaches `pprof.Cmdline`, `pprof.Handler("heap")`, `pprof.Handler("goroutine")`, etc. `pprof.Cmdline` returns the process's `os.Args`, which for chainlink nodes can include command-line flags/paths; `heap`/`goroutine`/`profile` dumps can leak in-memory secrets (e.g., decrypted key material, config values, session tokens) held in the Go heap or stack traces during processing.

Note: this specific finding concerns `metricRoutes` reachable via `/v2/...` (the `authv2` group), not `AuthenticateGQL`/`/query` directly — `AuthenticateGQL` itself only attaches a `GQLSession` to context and defers all authorization to individual GraphQL resolvers [7](#0-6) ; there is no evidence in the codebase that pprof/debug/metrics handlers are wired into the GraphQL resolver tree or reachable via `POST /query`. The debug-route exposure that exists is on the REST `/v2` group, reachable with only a valid authenticated session regardless of role, not specifically tied to the GraphQL `AuthenticateGQL` path described in the question.

### Impact Explanation
An authenticated user with only 'view' role could pull `/v2/debug/pprof/heap`, `/v2/debug/pprof/goroutine?debug=2`, or `/v2/debug/pprof/cmdline` to inspect the node's memory and stack traces, potentially exposing sensitive in-memory data (decrypted keys, secrets, tokens) and process startup arguments. This matches a credential/key-disclosure impact class, though the actual presence of secrets in heap/goroutine dumps depends on runtime state at request time and is not guaranteed — the routes are reachable regardless.

### Likelihood Explanation
Precondition is any valid authenticated session or API token (lowest privilege, 'view' role, obtainable via normal login) — no admin/edit/run role needed since no role wrapper is applied. This is straightforward and repeatable: a standard HTTP GET to a known, documented pprof path with valid session cookie/token succeeds.

### Recommendation
Wrap `metricRoutes(authv2)` (and the `/debug/pprof/...` route group) with `auth.RequiresAdminRole(...)` consistent with other sensitive diagnostic/key operations in the same file, so only admin-role sessions can access `net/http/pprof` endpoints.

### Proof of Concept
Go handler-level integration test plan (in `core/web` test package, following patterns in `core/web/router_test.go` or similar):
1. Bootstrap the app/router via `NewRouter` with a mocked `AuthenticationProvider`.
2. Create two sessions: one with role `view`, one anonymous (no cookie).
3. For each of `/v2/debug/pprof/cmdline`, `/v2/debug/pprof/heap`, `/v2/debug/pprof/goroutine`:
   - Send authenticated GET request with the 'view' role session cookie/token.
   - Assert response status is `200` (currently) — expected fix: `403 Forbidden` after adding `RequiresAdminRole`.
   - Send unauthenticated GET request (no session) — assert `401 Unauthorized` (should already fail via `auth.Authenticate`).
4. Confirm admin-role session still returns `200` after the fix, verifying no regression for legitimate admin diagnostics use.

// AuthenticateGQL middleware checks the session cookie for a user and sets it
// on the request context if it exists. It is the responsibility of each resolver
// to validate whether it requires an authenticated user.
//
// We currently only support GQL authentication by session cookie.
func AuthenticateGQL(authenticator Authenticator, lggr logger.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		ctx := c.Request.Context()
		session := sessions.Default(c)
		sessionID, ok := session.Get(SessionIDKey).(string)
		if !ok {
			return
		}

		user, err := authenticator.AuthorizedUserWithSession(ctx, sessionID)
		if err != nil {
			if errors.Is(err, clsessions.ErrUserSessionExpired) {
				lggr.Warnw("Failed to authenticate session", "err", err)
			} else {
				lggr.Errorw("Failed call to AuthorizedUserWithSession, unable to get user", "err", err)
			}
			return
		}

		ctx = WithGQLAuthenticatedSession(c.Request.Context(), user, sessionID)

		c.Request = c.Request.WithContext(ctx)
	}
}
