### Title
Prefunded epoch-queue operations are unreachable for orchestrator-managed vaults, permanently freezing queued deposits and blocking `stopEpoch` - ([File: contracts/IdleCreditVaultManagerOrchestrator.sol](contracts/IdleCreditVaultManagerOrchestrator.sol), [File: contracts/IdleCDOEpochQueue.sol](contracts/IdleCDOEpochQueue.sol))

### Summary
The bug-class analog: the M-4 report describes functions that are access-gated to a caller path (`Governor::execute` populating `_governanceCall`) that satellite chains never exercise, so the guarded functions are permanently uncallable. In idle-tranches, `IdleCDOEpochQueue` gates its privileged operations behind `_checkOnlyOwnerOrManager()`, and `IdleCreditVaultManagerOrchestrator` is the designated "manager" surface that forwards queue operations for clustered credit vaults. However, the orchestrator only exposes `processDeposits`, `processWithdrawRequests` and `processWithdrawalClaims` — it has **no** forwarders for `processDepositsToBorrower()` or `setPrefundedDepositWindow()`. When a prefunded-mode vault's queue has its owner/manager set to the orchestrator, these prefunded functions can never be called, deposits stuck in `epochPendingDeposits` make `prefundedDepositsToProcess()` revert, and `stopEpochWithDuration` can never succeed.

### Finding Description
In `IdleCDOEpochQueue.sol`, the two functions that drive the prefunded deposit flow are restricted:

- `setPrefundedDepositWindow` calls `_checkOnlyOwnerOrManager()` (`IdleCDOEpochQueue.sol:97`)
- `processDepositsToBorrower` calls `_checkOnlyOwnerOrManager()` (`IdleCDOEpochQueue.sol:153`) and is the *only* path that moves `epochPendingDeposits[nextEpoch]` → `epochPrefundedDeposits[nextEpoch]` and sends the underlyings to the borrower (`IdleCDOEpochQueue.sol:166-179`).

The orchestrator is the contract intended to act as manager/operator for a cluster of vaults. Its queue forwarders are `processDeposits`, `processWithdrawRequests`, and `processWithdrawalClaims` (`IdleCreditVaultManagerOrchestrator.sol:136-154`) — validated through `_creditVaultQueue`, which accepts any queue whose `idleCDOEpoch()` is a registered vault (`IdleCreditVaultManagerOrchestrator.sol:166-170`). There is deliberately no forwarder for `processDepositsToBorrower` or `setPrefundedDepositWindow` (confirmed by the test `testPrefundedQueueForwardersAreNotExposed`, which asserts raw calls to those selectors on the orchestrator fail).

This mirrors M-4 exactly: a guarded function exists, a legitimate privileged executor exists, but the executor's only reachable call surface never routes to the guarded function — so it is dead code for orchestrator-managed queues.

The freeze is hard, not soft:

- `requestDeposit` for an AA prefunded queue succeeds and funds sit as `epochPendingDeposits[nextEpoch]` (`IdleCDOEpochQueue.sol:103-127`).
- At epoch end, `IdleCDOEpochVariantPrefunded._afterStopEpochWithDuration` calls `prefundedDepositsToProcess()` (`IdleCDOEpochVariantPrefunded.sol:77`), which reverts via `_checkNotAllowed(epochPendingDeposits[_epoch] != 0)` whenever raw queue-held deposits remain (`IdleCDOEpochQueue.sol:280-281`).
- `stopEpochWithDuration` therefore always reverts; the epoch can never stop, borrower principal/interest can never be recalled, and queued user deposits are frozen. `deleteRequest` does not rescue users once `epochPrefundedDeposits[_requestEpoch] != 0` or `epochPrice` is set, and even beforehand each user must individually withdraw — but with the window set impossible via the orchestrator path, deposits can keep accumulating against an epoch that can never settle.

### Impact Explanation
All underlyings queued in a prefunded AA queue managed through the orchestrator are frozen: neither the operator nor any forwarder can invoke `processDepositsToBorrower`, so `epochPendingDeposits` never clears, `stopEpochWithDuration` always reverts inside `prefundedDepositsToProcess`, and the vault is bricked in the "running" epoch phase. Loss equals the full queued deposit balance plus inability to settle the epoch (borrower funds remain outstanding, interest cannot be accrued/distributed). This is permanent freezing with direct fund impact, satisfying the acceptance criteria.

### Likelihood Explanation
Requires a deployment where the queue's owner and/or the strategy manager is the orchestrator — the natural configuration for a "cluster" vault operated through `IdleCreditVaultManagerOrchestrator`, since all other queue lifecycle functions are only callable through it. If the queue owner is instead an EOA/multisig, that owner can call `processDepositsToBorrower` directly and the issue degrades to an operational inconvenience; the vulnerability exists specifically when the orchestrator is the sole privileged executor, which is the design intent of the orchestrator pattern. No attacker action is needed — this is a protocol liveness flaw (consistent with the threat model, which is about broken invariants rather than attacker-initiated theft for this bug class).

Caveat: I could not verify the actual deployed owner/manager wiring from the repo (deployment scripts may hold this); if deployments always keep a separate EOA owner on the queue, likelihood is low but the code path remains a latent trap.

### Recommendation
Add orchestrator forwarders for the prefunded queue surface, e.g. `processDepositsToBorrower(address _cdo, address _epochQueue)` and `setQueuePrefundedDepositWindow(address _cdo, address _epochQueue, uint256 _window)`, both gated by `_checkOnlyOperator()` and routed through `_creditVaultQueue` — the same pattern used by `processDeposits`. Alternatively, relax `_checkOnlyOwnerOrManager` gating or document/enforce that prefunded queues must never have the orchestrator as sole owner/manager.

### Proof of Concept
```solidity
// Foundry fork test — assumes queue.owner() (and strategy manager) == orchestrator,
// the configuration the orchestrator is designed for.

function testPrefundedQueueBrickedUnderOrchestrator() external {
    // 1. Register CDO with orchestrator, start an epoch, enable prefunded queue
    vm.startPrank(orchestratorOwner);
    orchestrator.setCreditVaultAllowed(address(cdoEpoch), true);
    // queue ownership/manager routed to orchestrator (managed cluster)
    vm.stopPrank();

    vm.prank(operator);
    orchestrator.startEpoch(_cdos(address(cdoEpoch)));

    // 2. KYC'd user deposits into AA prefunded queue
    deal(address(underlying), user1, 1e6);
    vm.startPrank(user1);
    underlying.approve(address(queue), 1e6);
    queue.requestDeposit(1e6); // succeeds; epochPendingDeposits[nextEpoch] = 1e6
    vm.stopPrank();

    // 3. Operator tries to forward deposits to borrower via orchestrator — no such selector
    vm.prank(operator);
    (bool ok,) = address(orchestrator).call(
        abi.encodeWithSignature("processDepositsToBorrower(address,address)",
        address(cdoEpoch), address(queue)));
    assertFalse(ok); // forwarder does not exist

    // 4. Direct call impossible: orchestrator is the owner/manager; any EOA call reverts
    vm.prank(operator);
    vm.expectRevert(NotAllowed.selector);
    queue.processDepositsToBorrower();

    // 5. Warp past epoch end; stopEpochWithDuration reverts inside
    //    prefundedDepositsToProcess() because epochPendingDeposits != 0
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(operator);
    vm.expectRevert(NotAllowed.selector);
    orchestrator.stopEpochWithDuration(actions);

    // 6. Funds frozen: queued deposit unreachable, epoch can never stop
    assertEq(queue.epochPendingDeposits(nextEpoch), 1e6);
}
```
