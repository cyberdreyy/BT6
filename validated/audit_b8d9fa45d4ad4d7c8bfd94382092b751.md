### Title
Stale epoch duration lets withdrawers lock obsolete APR terms - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`setEpochParams()` can change `epochDuration` while the pool is between epochs and withdrawal requests are still allowed. A withdrawal request made immediately before the update permanently records projected interest calculated with the old duration, while the next epoch runs with the new duration and APR. A KYC-approved lender can front-run a duration reduction to obtain borrower-funded interest for the old, longer epoch.

### Finding Description
`requestWithdraw()` converts tranche tokens to principal and adds projected next-epoch interest through `_calcInterestWithdrawRequest()`. The resulting `_underlyings` amount is fixed when `IdleCreditVault.requestWithdraw()` records it in `pendingWithdraws`. [1](#0-0) [2](#0-1) 

The projected interest is based on the current `epochDuration`, `bufferPeriod`, and scaled strategy APR. [3](#0-2)  However, `setEpochParams()` permits the owner or manager to replace those epoch parameters whenever `isEpochRunning` is false; it does not check pending withdrawal receipts or require that the next epoch use the same terms that were quoted to requesters. [4](#0-3) 

For example, with a 10% APR, a 30-day epoch, and a 5-day buffer:

1. A lender requests withdrawal during the buffer period.
2. The receipt includes projected interest for 30 days.
3. The manager shortens the next epoch to 10 days and resets the same nominal APR.
4. The lender's receipt remains payable at the 30-day interest amount.
5. The next `stopEpoch` must fund that inflated `pendingWithdraws` receipt even though the current epoch schedule is 10 days.

The excess is approximately:

```text
principal * apr * (oldDuration - newDuration) / 365 days
```

For 10,000,000 underlying units at 10% APR, reducing the epoch from 30 days to 10 days creates an excess claim of approximately `54,794.52` underlying units.

### Impact Explanation
The borrower must fund a withdrawal receipt calculated under obsolete epoch terms. The excess is paid from borrower-supplied funds at epoch stop rather than from actual yield for the new epoch, causing direct loss equal to the stale-duration interest delta.

### Likelihood Explanation
The attack requires a pending owner or manager epoch-duration change and a user able to submit `requestWithdraw()` before it. Public mempool transactions or observable operations make this sequence available to any KYC-passing tranche holder. No malicious privileged role is required.

### Recommendation
Prevent `setEpochParams()` from changing `epochDuration` or `bufferPeriod` while `pendingWithdraws`, APR0 principal, or pending instant withdrawals exist. Alternatively, make epoch parameters immutable, or update epoch parameters and APR atomically before opening the withdrawal-request window so every receipt for the same next epoch uses identical terms.

### Proof of Concept
The following test can be added to `test/foundry/IdleCreditVault.t.sol` and uses the existing fixture:

```solidity
function testWithdrawRequestUsesStaleEpochDuration() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0);

    uint256 principal = 10_000_000 * ONE_SCALE;
    uint256 oldDuration = cdoEpoch.epochDuration();
    uint256 newDuration = oldDuration / 3;
    uint256 buffer = cdoEpoch.bufferPeriod();

    idleCDO.depositAA(principal);

    // Attacker front-runs the epoch-duration update and fixes a receipt
    // containing interest for the old duration.
    uint256 receipt = cdoEpoch.requestWithdraw(0, idleCDO.AATranche());
    uint256 staleInterest = receipt - principal;

    // Honest manager configures the next shorter epoch and restores the
    // intended nominal APR under the new duration.
    vm.startPrank(manager);
    cdoEpoch.setEpochParams(newDuration, buffer);
    IdleCreditVault(address(strategy)).setAprsWithBuffer(
        initialProvidedApr,
        newDuration,
        buffer
    );
    vm.stopPrank();

    uint256 intendedInterest = principal *
        (initialProvidedApr / 100) *
        newDuration /
        (365 days * ONE_TRANCHE_TOKEN);

    assertEq(staleInterest, principal * (initialProvidedApr / 100) * oldDuration / (365 days * ONE_TRANCHE_TOKEN));
    assertGt(staleInterest, intendedInterest);

    uint256 owedToReceipt = receipt;
    assertEq(IdleCreditVault(address(strategy)).pendingWithdraws(), owedToReceipt);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, owedToReceipt);

    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    cdoEpoch.claimWithdrawRequest();

    // The claim is paid even though its interest was priced using oldDuration.
    assertGe(
        IERC20Detailed(defaultUnderlying).balanceOf(address(this)),
        staleInterest - intendedInterest
    );
}
```

  /// @notice update epoch duration
  /// @dev IMPORTANT: bufferPeriod should not be changed once set otherwise interest calculations will be wrong
  /// @param _epochDuration duration in seconds
  /// @param _bufferPeriod time between 2 epochs
  function setEpochParams(uint256 _epochDuration, uint256 _bufferPeriod) public {
    _checkOnlyOwnerOrManager();
    // cannot set epoch params if epoch is running
    // cannot set epochDuration to 0 as it's reserved for closing the pool
    // and cannot set epochDuration if previously was set to 0 as borrower repaid all funds
    _checkNotAllowed(defaulted || isEpochRunning || _epochDuration == 0 || epochDuration == 0);
    epochDuration = _epochDuration;
    bufferPeriod = _bufferPeriod;
  }

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
