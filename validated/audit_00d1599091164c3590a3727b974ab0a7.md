### Title
`depositDuringEpoch` mints tranche shares and strategy tokens on the nominal `_amount` instead of the actually received balance — fee-on-transfer/deflationary underlyings inflate NAV and drain the buffer - (File: `contracts/IdleCDOEpochVariant.sol`)

### Summary
The SafeDollar hack class is "reward/pool accounting trusts the requested amount rather than the received balance of a fee-on-transfer token." The same mismatch exists in `IdleCDOEpochVariant.depositDuringEpoch`: the ordinary deposit path deliberately measures the real balance delta, but the mid-epoch deposit path prices shares, mints strategy tokens, and forwards funds to the borrower using the nominal `_amount`. With an underlying that takes a transfer fee (or any token whose `transferFrom` delivers less than requested), the vault mints fully-backed claims while receiving less, and pushes the shortfall onto other depositors.

### Finding Description
In `IdleCDO._deposit` / `IdleCDOCreditVault._deposit`, shares are minted on the measured delta:
```solidity
uint256 _preBal = _contractTokenBalance(_token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
_minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, ...);
```
This shows the codebase intends deposits to account for what actually arrives.

`depositDuringEpoch` does not do this. It skims donations, then:
```solidity
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
...
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
_mintShares(_tranche, msg.sender, _minted, _amount);
expectedEpochInterest += interest;
IdleCreditVault(strategy).mintStrategyTokens(_amount);
_transferUnderlyings(_borrower(), _amount);
```
Every accounting leg uses the requested `_amount`:

1. `_mintShares` credits `lastNAVAA`/`lastNAVBB` with `_amount` even though only `_amount - fee` arrived.
2. `mintStrategyTokens(_amount)` mints strategy tokens 1:1 with the nominal amount, so `getContractValue()` (strategyToken balance + raw balance − fees) is inflated by the fee amount.
3. `_transferUnderlyings(_borrower(), _amount)` sends the full nominal amount to the borrower. Since the contract only received `_amount - fee`, this transfer is funded by underlying still sitting in the CDO from other users' buffer deposits or pending operations — i.e., other depositors' principal is forwarded to the borrower to cover the fee shortfall.

The attacker, as a KYC-passed lender (`isWalletAllowed`), calls `depositDuringEpoch` mid-epoch (in fixed-APR, non-AYS, non-programmable mode where the function is enabled), receives tranche shares priced on the full amount plus prorated interest, and later redeems/requests withdrawal at par. The fee component is socialized onto all other tranche holders whose NAV now backs more tranche supply than real assets.

### Impact Explanation
Direct theft via NAV dilution. Each `depositDuringEpoch` call lets the attacker mint shares worth `_amount` while only contributing `_amount - fee`, and simultaneously pushes `_amount` of other users' underlying to the borrower (borrower is honest and will repay nominal principal + interest, but the extra `fee` forwarded is drawn from the vault's buffer balance, i.e., other LPs). The invariant broken is fair mint/burn: shares and strategy tokens are issued against money that never arrived. Loss per call equals the token's transfer fee on `_amount`; repeatable up to the deposit `limit`, and at scale it makes the vault insolvent for later withdrawers (last claimers' `requestWithdraw`/`claimWithdrawRequest` underpay or revert).

### Likelihood Explanation
Requires the deployed underlying to be a fee-on-transfer or deflationary token. Vault underlyings are stablecoins; this is exploitable for any deployment where the token charges transfer fees (e.g., USDT with fees enabled, or a token that later enables fees). The guard set (`_skimDonatedAssets`, `_guarded`, epoch gating, KYC) does not stop it — skim only removes pre-existing raw balances and the delta is never measured. Likelihood is deployment-dependent but the fix cost is trivial and the base contract already demonstrates the correct pattern, so this is a real inconsistency rather than a design assumption.

### Recommendation
Measure the received amount in `depositDuringEpoch` the same way `_deposit` does:
```solidity
uint256 _preBal = _contractTokenBalance(token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
uint256 _received = _contractTokenBalance(token) - _preBal;
```
then compute `trancheInterest`, `minted`, `expectedEpochInterest`, `mintStrategyTokens`, and the borrower transfer on `_received` (or revert if `_received != _amount` if fee-on-transfer tokens are explicitly unsupported). Apply the same received-vs-requested check to any other path that transfers underlying and mints claims on a nominal amount.

### Proof of Concept
Foundry fork/mock PoC outline:
1. Deploy `IdleCDOEpochVariant` + `IdleCreditVault` with a mock ERC20 underlying that burns 1% on `transfer`/`transferFrom`.
2. `depositAA` normally for seed liquidity; owner starts an epoch (`startEpoch`) in fixed-APR mode with `isDepositDuringEpochDisabled = false`, AYS off, non-programmable.
3. Warp to mid-epoch; attacker (KYC-allowed) calls `depositDuringEpoch(10000e6, AA)`.
4. Assert: contract received `9900e6`, but `mintStrategyTokens` minted `10000e6`, `lastNAVAA` increased by `10000e6`, and `10000e6` was forwarded to the borrower — i.e., 100e6 of pre-existing vault balance subsidized the transfer.
5. After `stopEpoch` with honest borrower repayment, attacker claims principal + interest at par; remaining LP's `virtualPrice`/`maxWithdrawable` shows a shortfall equal to the cumulative fee — vault is insolvent for the full minted amount.

Uncertainty: I did not fully enumerate every other nominal-amount transfer site (e.g., `WriteOffEscrow`, prefunded variant paths) for the same pattern, but `depositDuringEpoch` is sufficient as the concrete analog.
