### Title
Account authority transfer does not reset `emissions_destination_account`, allowing prior authority to divert future emissions after account sale/migration - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
`transfer_to_new_account` and `transfer_to_new_account_pda` migrate a `MarginfiAccount` to a new account/authority but copy the `emissions_destination_account` field verbatim from the old account instead of resetting it to the new authority or the zero-default. This is the same root cause as Sherlock H-12 in Astaria's `LienToken`: a "payee"-style redirect field survives an ownership-transfer/buyout operation, so the previous owner keeps receiving value streams (there, loan repayments; here, off-chain emissions/incentive airdrops) intended for the new owner.

### Finding Description
`initialize_migrated_account` explicitly propagates the stale field: [1](#0-0) 

This function is called by both `transfer_to_new_account` and `transfer_to_new_account_pda`, the two permissionless-by-the-current-authority instructions that move a `MarginfiAccount`'s balances and control to a new authority: [2](#0-1) [3](#0-2) 

`emissions_destination_account` is a user-controlled redirect target set via `marginfi_account_update_emissions_destination_account`, and per the docs it determines where off-chain incentive airdrops are sent instead of the account's `authority`: [4](#0-3) [5](#0-4) 

Because the migration flow copies this field rather than clearing it or setting it to the `new_authority`, a party who sets `emissions_destination_account` to their own wallet and then transfers/migrates the account to a new authority (analogous to "selling" the account and its positions, since balances move over) leaves the new authority's future emissions still routed to the old owner's chosen address. The new authority must proactively notice this and call `marginfi_account_update_emissions_destination_account` themselves to redirect emissions to themselves — otherwise they silently lose future incentive payouts, mirroring exactly the LienToken `buyoutLien()`/`payee` bug.

Notably, the project's own test suite flags this exact gap as unresolved: [6](#0-5) 

The developer docs only acknowledge a *transient* one-week carryover ("emissions will still airdrop to the old account for that week"), not a permanent silent redirect: [7](#0-6) 
But the code provides no automatic reset after that transitional period — the field remains whatever the old authority set indefinitely until the new authority manually updates it.

### Impact Explanation
Emissions/incentive campaigns distribute real-value tokens pro-rata based on account balances (which are migrated intact to the new account): [8](#0-7) 
If the previous authority set `emissions_destination_account` to their own address before transferring the account (e.g. selling the account/its lending position off-chain, or simply migrating for legitimate reasons like moving to a PDA), all future emissions earned by the new account's balances continue to be paid to the old authority's chosen destination until the new authority notices and resets it. This is a direct, durable financial redirection of value away from the rightful current owner of the position — the same impact class as H-12.

### Likelihood Explanation
Both migration instructions are reachable by any account authority holder without any privileged role, guardian, or admin gating beyond ownership of the source account (only frozen/flashloan/receivership/order-execution/already-migrated states block it): [9](#0-8) 
Since `new_authority` is explicitly documented as "completely unchecked", any current authority can pick an arbitrary new authority to migrate to (e.g., as part of an account sale), while retaining the emissions redirect they previously configured. The project's own TODO comment in the test suite confirms this scenario is neither tested nor handled by the current implementation, making it a realistic, low-effort oversight rather than a purely theoretical one.

### Recommendation
In `initialize_migrated_account`, either reset `new_account.emissions_destination_account` to `Pubkey::default()` (falling back to the new authority per normal emissions logic) or explicitly set it to `new_authority`, instead of copying the old account's value. Optionally, also clear/reset `old_account.emissions_destination_account` in `finalize_migrated_old_account` since the old account is disabled and has no future balances to earn emissions on.

### Proof of Concept
1. Authority A creates a `MarginfiAccount`, deposits/borrows to earn emissions eligibility.
2. A calls `marginfi_account_update_emissions_destination_account` setting `destination_account = A`'s own separate wallet (already the default behavior, but here A does this deliberately to keep control).
3. A calls `transfer_to_new_account`/`transfer_to_new_account_pda`, setting `new_authority = B` (e.g., as part of selling the account/position to B off-chain). Balances (`lending_account`) move to the new account fully intact per `initialize_migrated_account`.
4. Per `initialize_migrated_account` line 32, `new_account.emissions_destination_account` is set equal to A's previously-configured destination, not to B.
5. Going forward, B owns and operates the account (deposits/borrows/repays under the new account), earning emissions pro-rata on B's activity, but the off-chain emissions system pays out to A's `destination_account`, not to B — until B independently discovers this and calls `marginfi_account_update_emissions_destination_account` to fix it.

```rust
pub fn transfer_to_new_account_pda(
    ctx: Context<TransferToNewAccountPda>,
    account_index: u16,
    third_party_id: Option<u16>,
) -> MarginfiResult {
    // Validate the global fee wallet and claim a nominal fee
    let group = ctx.accounts.group.load()?;
    check_eq!(
        ctx.accounts.global_fee_wallet.key(),
        group.fee_state_cache.global_fee_wallet,
        MarginfiError::InvalidFeeAta
    );
    anchor_lang::system_program::transfer(ctx.accounts.transfer_fee(), ACCOUNT_TRANSFER_FEE)?;

    let mut old_account = ctx.accounts.old_marginfi_account.load_mut()?;

    check!(
        !old_account.get_flag(ACCOUNT_IN_FLASHLOAN),
        MarginfiError::AccountInFlashloan
    );

    check!(
        !old_account.get_flag(ACCOUNT_IN_RECEIVERSHIP),
        MarginfiError::ForbiddenIx
    );

    check!(
        !old_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION),
        MarginfiError::ForbiddenIx
    );

    check!(
        old_account.active_orders == 0,
        MarginfiError::IllegalAction,
        "Close all active orders before transfer"
    );

    // Prevent multiple migrations from the same account
    check_eq!(
        old_account.migrated_to,
        Pubkey::default(),
        MarginfiError::AccountAlreadyMigrated
    );

    // Validate third-party id restriction if provided
    if let Some(id) = third_party_id {
        if !is_allowed_cpi_for_third_party_id(&ctx.accounts.instructions_sysvar, id)? {
            return err!(MarginfiError::Unauthorized);
        }
    }

    let mut new_account = ctx.accounts.new_marginfi_account.load_init()?;
    let current_timestamp = Clock::get()?.unix_timestamp as u64;
    initialize_migrated_account(
        &mut new_account,
        &old_account,
        ctx.accounts.new_authority.key(),
        current_timestamp,
        ctx.accounts.old_marginfi_account.key(),
    );
```

```markdown
## Summary

Some banks, including banks from other venues, might offer a token incentive to depositors, or even
to borrowers. We call a set of incentives over time a "Campaign".

For example, a Campaign might distribute 7 tokens of A to lenders per week (one per day). Each
lender's share is determined on a pro-rata basis in real time. If there are two lenders, each
depositing the same amount, then each will be 3.5 tokens per week.

Now let's say there are two users, the first one has \$1 in deposits. User 2 deposits \$1 on
Thursday, and \$5 more on Saturday. This means User 1 and 2 both get 0.5 tokens/day on Thursday and
Friday. On Saturday and beyond, User 1 gets $1/(1+6)= 0.143$ tokens, and User 2 gets $6/(1+6)=0.857$
tokens/day.

Emissions/incentives are delivered by airdrop to the Account's authority, typically on Wednesday, in
no particular order. In the above example, User 1 would get $0.5 + 0.5 * 0.143 * 5 = 1.715$ tokens
and User 2 would get $0.5 + 0.5 + 0.857 * 5 = 5.285$ tokens
```
