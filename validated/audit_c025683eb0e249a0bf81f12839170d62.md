### Title
Service `alias` values are attached to Docker network endpoints before Runner's alias-collision check can veto them, allowing alias hijack of `build`/other services - ([File: executors/docker/services.go])

### Summary
`createFromServiceDefinition` computes the full `serviceMeta.Aliases` list and passes it unconditionally into `e.createService(...)` (and from there into the container's Docker network `EndpointsConfig`/`networkConfig(linkNames)`) the first time a non-colliding alias is seen, *before* the per-alias collision check in the surrounding loop has evaluated every alias in that same list. The collision check (`linksMap[linkName] != nil`) also never covers the reserved `build` hostname, since that name is never inserted into `linksMap`. As a result an unprivileged job can declare a service with `alias: build` (or with an alias equal to another, later-processed alias in its own list) and have Docker actually register that network alias on its container, even though Runner's own bookkeeping "skips" it and only logs a warning.

### Finding Description
In `executors/docker/services.go`: [1](#0-0) 

The loop iterates `serviceMeta.Aliases` and only vetoes an alias if it's already present in `linksMap`. But the container (and its full alias set) is created once, on the *first* alias in the list, via: [2](#0-1) 

`serviceMeta.Aliases` — the complete list, including aliases that later iterations of the same loop would flag as colliding — is handed to `createService`, which builds the container's network config (`networkConfig(linkNames)`) from that same full list. The `continue` on a later colliding alias only prevents `linksMap`/`e.links` (used for legacy `--link` wiring) from pointing at it; it does **not** retroactively strip that alias from the network endpoint that was already configured when the container was created. Consequently, Docker-level network alias registration is not actually gated by Runner's dedup logic.

Separately, `linksMap` never contains the string `build` (that alias belongs to the build container and is wired up independently of this map), so nothing in this collision check stops a job from setting a service's `alias:` to `build`. Docker's embedded DNS resolves duplicate aliases on the same network by returning all matching container IPs (order/priority is not guaranteed to favor the "real" one), so any process resolving `build` on the per-build network could be routed to the attacker-controlled service container instead of the actual build container.

### Impact Explanation
Under `FF_NETWORK_PER_BUILD` (all job containers/services share one bridge network), a job author who fully controls the `services:` block in `.gitlab-ci.yml` can set `alias: build` on one of their own services, or set two aliases within one service definition where the second collides with an already-claimed name. Either path results in Docker registering the attacker's container under a name a script or another service is expected to resolve (`build` or a peer service's alias), enabling DNS-level redirection/MITM of intra-job traffic without any privileged Runner configuration.

### Likelihood Explanation
This requires only standard job-author capabilities (defining `services:` with custom `alias:` in CI config) plus the widely-used `FF_NETWORK_PER_BUILD` feature flag, no admin cooperation. The `alias: build` case needs no guessing of container IDs and is deterministically reachable every time a job is run with services and this flag; it is fully reproducible.

### Recommendation
- Reject or ignore reserved alias values (`build`, and the format used for the 12-character container-ID hostname) at alias-validation time, before container creation.
- Move the alias-collision check so that the full alias set for a service is validated against `linksMap` (including the reserved `build` name) before `createService`/`networkConfig` is invoked, and strip/reject any alias that fails validation from the list passed into the network config, rather than only skipping the `linksMap` bookkeeping entry after container creation.

### Proof of Concept
Integration test in `executors/docker/services_test.go` style:
1. Enable `FF_NETWORK_PER_BUILD`.
2. Configure a job with two services: `service-a` (default alias) and `service-b` with `alias: build` (and, in a second sub-test, `service-c` with two aliases `["shared", "shared2"]` where `shared` is already claimed by `service-a`).
3. After `createServices()` runs, inspect the created containers' `NetworkSettings.Networks[<network>].Aliases` via the Docker API/mock client.
4. Assert that no service container ever receives the alias `build`, and that a colliding alias is never present in more than one container's `EndpointsConfig.Aliases`.
5. Expected failure today: `service-b`'s container is created with network alias `build` attached (or the colliding alias from `service-c` appears on two containers), demonstrating that Runner's warning/skip logic does not prevent the actual Docker-level alias registration.
