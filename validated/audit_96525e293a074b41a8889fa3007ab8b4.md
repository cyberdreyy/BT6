### Title
Signer signature does not commit to `problematic_txs` for pre-Epoch-4.0 header versions, allowing a signed block to be mutated after signing without invalidating the signature - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
The external report's bug class is: a validation/sanitization step operates on data, but a later transformation (unicode NFKC normalization) is not covered by that validation, so content that was checked can be turned into something dangerous without re-validation. The structural analog here is a cryptographic commitment (the signer signature hash) that conditionally excludes a security-relevant field (`problematic_txs`) depending on the block header `version`, so a block can be mutated after a signer approves/signs it without changing the hash the signature covers.

### Finding Description
`NakamotoBlockHeader::signer_signature_hash_inner` (and `miner_signature_hash_inner`) only include the `problematic_txs` field in the hash preimage when `version_includes_problematic_txs(self.version)` is true, i.e. when `(version & 0x7f) >= NAKAMOTO_BLOCK_VERSION_EPOCH_4`: [1](#0-0) 

For any header whose version is below `NAKAMOTO_BLOCK_VERSION_EPOCH_4`, `problematic_txs` is entirely excluded from both the miner's and the signers' signature preimages: [2](#0-1) 

Meanwhile, the signer explicitly treats a non-empty `problematic_txs` list as a hard rejection reason before it will ever sign a block: [3](#0-2) 

Because `problematic_txs` is not part of the hash for a pre-Epoch-4.0-version header, a miner can:
1. Propose a "clean" block (`problematic_txs = []`) at a version below `NAKAMOTO_BLOCK_VERSION_EPOCH_4`.
2. Get it validated by the node and signed by signers (`sign_miner`/signer signatures over `signer_signature_hash()`), following the normal pre-commit → sign flow (`handle_block_proposal` → `check_block_against_state` → `submit_block_for_validation` → `handle_block_validate_ok` → pre-commit → `handle_block_pre_commit` → SIGN path): [4](#0-3) 
3. After collecting the threshold of signatures, mutate the header's `problematic_txs` field to a non-empty list (the field the signer explicitly forbade) and re-broadcast/finalize this modified block. Because `version_includes_problematic_txs` returns `false` for this version, `signer_signature_hash()` is byte-for-byte identical before and after the mutation, so the existing signer signatures still verify successfully against the mutated header in `verify_signer_signatures`: [5](#0-4) 

This breaks the intended equality "what the signers validated and signed" == "what is accepted as validly signed," the same class of defect as the html-sanitizer bug: a post-check transformation (unicode normalization there; a mutable, hash-excluded field here) invalidates a security property (safe HTML / "no problematic transactions") that the validator believed it had enforced.

### Impact Explanation
This is a "rejection recounted as an accept" / signature-malleability class issue: signers unanimously refuse to sign any block containing problematic transaction markers, specifically because "the criteria for what may legitimately appear in `problematic_txs` has not been decided yet" — yet a single miner can silently attach such markers to an already-signed block without invalidating any signer's signature, for any header using a pre-Epoch-4.0 version. Depending on how the node/consensus layer treats `problematic_txs` at execution time (outside the signer's purview), this could let a miner get signer approval for a block, then present a variant of that same, validly-signed block carrying transaction-safety markers that were never actually approved by the signer set. This falls under the "cross-context-valid signature" category: a signature bound to hash H is valid for two different block contents.

### Likelihood Explanation
Requires only a single (potentially malicious) miner — no majority of signers, no other party's key, and no privileged access. It is fully reachable through the normal proposal/sign flow: any block whose header version is below `NAKAMOTO_BLOCK_VERSION_EPOCH_4` (which is legitimate prior to the Epoch 4.0 boundary and possibly still constructible after, depending on whether the node enforces `expected_version_for_epoch` strictly at every validation step) is affected. I was not able to fully confirm from the available index whether `postblock_proposal.rs`'s `validate()` (or an earlier check) rejects a header whose `version` does not match `NakamotoBlockHeader::expected_version_for_epoch(epoch_id)` prior to computing/accepting signatures — the search only surfaced the `version_includes_problematic_txs` mask logic and not an explicit version-vs-epoch enforcement call inside the postblock_proposal validation path. If such enforcement exists and is applied unconditionally at both proposal-validation and block-storage time, the practical window may be limited to the pre-Epoch-4.0 period; if it is not enforced there, the issue is exploitable at any time a miner can produce an old-version header.

### Recommendation
Include `problematic_txs` unconditionally in the signature preimages (or otherwise enforce that any header version accepted post-migration must match `expected_version_for_epoch`, checked in both the node's `postblock_proposal::validate` path and in `verify_signer_signatures`/block storage, not just at construction time), so a miner cannot choose an older header version specifically to detach a field from the signature commitment.

### Proof of Concept
1. Build a `NakamotoBlockHeader` with `version < NAKAMOTO_BLOCK_VERSION_EPOCH_4` and `problematic_txs = vec![]`.
2. Sign as miner (`sign_miner`) and have the signer set produce enough `signer_signature` entries via the normal proposal/pre-commit/sign flow (per `stacks-signer/src/v0/signer.rs`), since `check_block_against_state` passes when `problematic_txs.is_empty()`.
3. After collecting signatures, set `header.problematic_txs = vec![ProblematicTxMarker { tx_index: 0, category: 0 }]` without re-signing anything.
4. Call `header.signer_signature_hash()` before and after step 3 — the digests are identical because `version_includes_problematic_txs(version)` is `false`, per [6](#0-5) .
5. Call `verify_signer_signatures` on the mutated header — it succeeds, using the same signatures the signers produced over the "clean" block, even though the block now carries the exact field the signers were designed to reject.

impl NakamotoBlockHeader {
    /// Whether a header at the given `version` includes the `problematic_txs`
    /// field in its serialization and signature/block-hash preimages.
    ///
    /// This is the single source of truth shared by `consensus_serialize`,
    /// `consensus_deserialize`, and both signature-hash calculations, so the
    /// field's presence can never diverge between them. The field was added in
    /// Epoch 4.0; version-0 headers omit it entirely.
    pub fn version_includes_problematic_txs(version: u8) -> bool {
        // The high bit (0x80) of `version` is the shadow-block flag; the header
        // version number is the low 7 bits. Mask it off before comparing so a
        // pre-4.0 shadow block (version 0x80) isn't mistaken for a v1 header.
        (version & 0x7f) >= NAKAMOTO_BLOCK_VERSION_EPOCH_4
    }

    /// Inner calculation of the message digest for stackers to sign.
    /// This includes all fields _except_ the stacker signature.
    fn signer_signature_hash_inner(&self) -> Result<Sha512Trunc256Sum, CodecError> {
        let mut hasher = Sha512_256::new();
        let fd = &mut hasher;
        write_next(fd, &self.version)?;
        write_next(fd, &self.chain_length)?;
        write_next(fd, &self.burn_spent)?;
        write_next(fd, &self.consensus_hash)?;
        write_next(fd, &self.parent_block_id)?;
        write_next(fd, &self.tx_merkle_root)?;
        write_next(fd, &self.state_index_root)?;
        write_next(fd, &self.timestamp)?;
        write_next(fd, &self.miner_signature)?;
        write_next(fd, &self.pox_treatment)?;
        if Self::version_includes_problematic_txs(self.version) {
            write_next(fd, &self.problematic_txs)?;
        }
        Ok(Sha512Trunc256Sum::from_hasher(hasher))
    }
