### Title
Job scripts that call `setsid`/double-fork escape process-group kill and survive job cancellation - ([File: helpers/process/job_unix.go])

### Summary
`setProcessGroup` in `helpers/process/job_unix.go` only sets `Setpgid: true` on the immediate shell/custom-command process, and `killer_unix.go` terminates jobs by signaling the negative PID (the process group) of that single process. A job script that spawns a grandchild via `setsid`, `nohup`, or a double-fork places that grandchild in a *new* session/process group, which is outside the pgid targeted by `Terminate`/`ForceKill`, so the grandchild is never signaled and can outlive job cancellation.

### Finding Description
`setProcessGroup` (`helpers/process/job_unix.go:36-40`) sets `Setpgid: true` on the `exec.Cmd` for the top-level shell process only: [1](#0-0) 

`unixKiller.getPID` (`helpers/process/killer_unix.go:46-52`) computes `-Pid` of that same top-level process and `Terminate`/`ForceKill` call `syscall.Kill(-Pid, SIGTERM/SIGKILL)`: [2](#0-1) 

This signals every process that is still a member of the pgid created by `Setpgid`. However, `setsid(2)` (invoked from within the job script, e.g. `setsid sleep 3600 &`) or a double-fork detaches the child into a brand-new session and process group. That new pgid is never known to or tracked by the Runner — there is no recursive descendant enumeration, cgroup-based containment, or session tracking anywhere in `killer.go`/`killer_unix.go`. Consequently `KillAndWait` (`helpers/process/killer.go:66-92`), invoked from `executors/shell/shell.go:128-131` and `executors/custom/command/command.go:93-96` on job cancellation, will terminate the shell/top-level command but leave the detached descendant running.

This is reachable purely from job script content (attacker-controlled job/pipeline definition), requires no special executor privileges beyond the shell/custom executor already trusting the job script to run local commands — which is the documented trust model for shell executors. The relevant gap is specifically the *cancellation cleanup guarantee*, not arbitrary code execution (which shell executors already grant to the job by design).

### Impact Explanation
For shell/custom executors configured with `SharedBuildsDir`/build-dir reuse across jobs (the shell executor here sets `SharedBuildsDir: true` at `executors/shell/shell.go:167`), an orphaned attacker process can persist after the job is cancelled and continue running in the shared workspace, potentially reading/writing cache or artifacts of a subsequent job that reuses the same build directory, or generally causing persistent resource consumption/DoS on the runner host beyond the job's lifetime. This matches the scoped impact: cross-job takeover / persistent multi-tenant disruption in shared-build-dir shell/custom-executor deployments.

### Likelihood Explanation
This is trivially reproducible by any pipeline author who can supply a `.gitlab-ci.yml` script — no elevated runner privileges are needed, only that the runner uses a shell or custom executor with a shared/reused build directory (a common, documented configuration for shell executors, distinct from the excluded "shell executor trust on a shared host" category since the issue here is specifically the cancellation/kill guarantee, not general host access). The only precondition is that the job be cancelled/timed out while the detached process is alive, which an attacker fully controls by sleeping long enough.

### Recommendation
Track and terminate all descendants of the job's process tree at cancellation time rather than relying solely on the single process group created by `Setpgid`. Options:
- Recursively enumerate `/proc/<pid>/task/*/children` (or use `pgrep -P`) at kill time and signal/kill each descendant PID individually, not just the top-level pgid.
- Alternatively (stronger isolation), constrain job processes with a Linux cgroup (freezer/kill) created per job so that killing the cgroup terminates all processes regardless of `setsid`/double-fork, independent of pgid membership.
- If cgroups are unavailable, at minimum call `Setsid` or record the pgid before spawning and after the job also sweep for stray processes owning the job's build-dir path or environment marker (e.g. `CI_JOB_ID`) as a defense-in-depth cleanup step.

### Proof of Concept
Go/shell integration test outline (extends `helpers/process/killer_unix_integration_test.go` style):
1. Use the shell executor with `SharedBuildsDir` and a job script:
   ```sh
   setsid sh -c 'sleep 300' < /dev/null &> /tmp/orphan.log &
   echo $! > /tmp/orphan.pid
   ```
2. Cancel the job's context shortly after start (simulate via `cmd.Context` cancellation as done in `shell.go:128`).
3. Wait `GracefulKillTimeout + ForceKillTimeout`.
4. Assert: `kill -0 $(cat /tmp/orphan.pid)` still succeeds (process alive) — proving the process group kill in `killer_unix.go` did not reach the detached descendant.
5. Contrast with a non-`setsid` background job (`sleep 300 &`), where the same test shows the descendant *is* killed, confirming the pgid-based kill only works absent `setsid`/session detachment.

```go
func (pk *unixKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGTERM)
	if err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}

func (pk *unixKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGKILL)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}
}
```
