### Title
Stale per-epoch instant-withdraw receipts are never cleared, enabling double-counted default claims and permanent freezing of instant claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` releases funds and zeroes `instantWithdrawsRequests[_user]`, but never deletes the per-epoch bookkeeping (`instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`). This is a use-after-free style flaw: state belonging to an already-paid ("freed") receipt is later re-read by the default-recovery path as if it were a live claim. If the same epoch ends in default, `defaultPendingClaimBasis()` double-counts the stale basis, `finalizeDefaultRecovery` computes a diluted `defaultRecoveryPrice`, and `_claimDefaultedInstantWithdrawRequest` subtracts the stale amount from `instantWithdrawsRequests[_user]`, reverting on underflow and permanently freezing the user's remaining claim.

### Finding Description
The instant-withdraw lifecycle has asymmetric clearing:

1. `requestInstantWithdraw` (lines 356–375) increments three trackers: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`, plus `pendingInstantWithdraws`.
2. `collectInstantWithdrawFunds` (lines 398–403) decrements only `pendingInstantWithdraws` when the CDO funds the receipts.
3. `claimInstantWithdrawRequest` (lines 380–393) burns the receipt tokens and zeroes `instantWithdrawsRequests[_user]` — but leaves `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` untouched.

The stale entries become live again at default:

- `defaultPendingClaimBasis` (lines 644–649): `if (pendingInstantWithdraws != 0) basis += instantWithdrawClaimsByEpoch[epochNumber]` — the already-claimed amount `X` is included as defaulted claim basis, inflating `totalBasis` in `finalizeDefaultRecovery` (lines 679–688) and lowering `defaultRecoveryPrice` for every claimant.
- `_claimDefaultedInstantWithdrawRequest` (lines 842–856): `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` returns stale `X` (or `X + Y` if the user re-requested `Y` in the same epoch), then `instantWithdrawsRequests[_user] -= claimBasis` underflows against the user's real `Y`, reverting every call — permanent freeze.

Attack sequence (unprivileged lender, fixed-APR mode, running epoch):
1. During epoch N, attacker calls `requestInstantWithdraw(X)`; CDO collects funds (`pendingInstantWithdraws` → 0 contribution) and attacker calls `claimInstantWithdrawRequest` → receives X underlying. Stale `instantWithdrawsRequestsByEpoch[attacker][N] = X`, `instantWithdrawClaimsByEpoch[N] = X` remain.
2. Attacker requests `requestInstantWithdraw(Y)` in the same epoch N; `pendingInstantWithdraws = Y`, claimsByEpoch[N] = X+Y. Another user also has an unfunded instant request keeping `pendingInstantWithdraws != 0`.
3. Epoch N ends in default (`stopEpoch` with insufficient repayment → `defaulted()`), owner calls `finalizeDefault`.
4. `defaultPendingClaimBasis` returns `pendingWithdraws + (X+Y)` — `X` is phantom basis. `defaultRecoveryPrice` is diluted: every defaulted receipt (normal pending withdraws, other instant receipts, active tranche NAV) is underpaid proportionally, while excess reserve sits stranded forever.
5. Attacker (or any user with a stale entry in the default epoch) calls `claimInstantWithdrawRequest` → `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = X+Y` but `instantWithdrawsRequests[user] = Y` → underflow revert → their real claim `Y` is permanently frozen.

### Impact Explanation
Two distinct impacts:
- **Recovery dilution / misallocation**: `defaultRecoveryPrice` divides a fixed reserve by an inflated `totalBasis`. All defaulted-epoch claimants (pending withdraw requesters, unfunded instant requesters, active AA/BB holders via `activeFinalNAV`) receive less than entitled, and the un-claimable surplus is locked in the strategy as permanent recovery dust.
- **Permanent freezing**: any user holding a stale `instantWithdrawsRequestsByEpoch` entry matching `defaultRecoveryEpoch` can never execute `claimInstantWithdrawRequest` — it always underflows — freezing their legitimately unfunded claims.

### Likelihood Explanation
Requires a same-epoch sequence: instant request → funded → claimed → (optional re-request) → epoch default. Instant withdraws and borrower default within the same epoch is plausible in stressed conditions, which is exactly when defaults occur. The missing cleanup is unconditional — every successful instant claim leaves the stale entry — so any default coinciding with an epoch where an instant claim was paid triggers the dilution; only the freeze additionally requires the claimant to hold residual unfunded basis. Note: I was unable to fully verify the CDO-side gating (`IdleCDOEpochVariant.getInstantWithdrawFunds`/`collectInstantWithdrawFunds` call ordering) in this iteration, but nothing in the strategy prevents the sequence above.

### Recommendation
Clear the per-epoch instant bookkeeping atomically when the receipt is paid. In `claimInstantWithdrawRequest`, after burning, delete `instantWithdrawsRequestsByEpoch[_user][reqEpoch]` (tracking the epoch per user, e.g., a `lastInstantWithdrawRequest` marker) and decrement `instantWithdrawClaimsByEpoch[reqEpoch]` by the claimed amount. Alternatively, record per-epoch claims only as the unfunded remainder (delta vs. `pendingInstantWithdraws`) at finalization time. Add a regression test: funded-then-claimed instant receipt in epoch N followed by epoch-N default must not inflate `defaultPendingClaimBasis` nor block later claims.

### Proof of Concept
```solidity
// Foundry fork test against an existing IdleCreditVault deployment
function testStaleInstantReceiptCorruptsDefaultRecovery() public {
    // --- epoch N running ---
    uint256 X = 1_000e6;
    uint256 Y = 500e6;

    // Attacker deposits and requests an instant withdraw in epoch N
    vm.prank(attacker);
    cdo.requestInstantWithdraw(X, address(AAtranche));

    // CDO funds the instant request; attacker claims at par
    // (collectInstantWithdrawFunds only reduces pendingInstantWithdraws)
    vm.prank(attacker);
    cdo.claimInstantWithdrawRequest(); // receives X; stale per-epoch data remains

    // Attacker re-requests in the SAME epoch; another user's request stays unfunded
    vm.prank(attacker);
    cdo.requestInstantWithdraw(Y, address(AAtranche));

    // --- epoch N ends in default ---
    vm.warp(cdo.epochEndDate() + 1);
    vm.prank(owner);
    cdo.stopEpoch(0, lossAmount);          // defaulted() == true
    vm.prank(owner);
    cdo.finalizeDefault(recovered, manager);

    // BUG 1: recovery basis included the already-paid X
    assertGt(
        vault.instantWithdrawClaimsByEpoch(vault.epochNumber()),
        vault.pendingInstantWithdraws(),
        "stale instant claims inflated default basis"
    );

    // BUG 2: attacker's claim reverts forever on underflow
    vm.prank(attacker);
    vm.expectRevert();                     // instantWithdrawsRequests[user] -= claimBasis underflows
    cdo.claimInstantWithdrawRequest();
}
```
