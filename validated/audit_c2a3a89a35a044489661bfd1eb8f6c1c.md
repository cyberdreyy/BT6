Based on my investigation, I found that the guard against user-controlled `-protected` suffix is only enforced for `CACHE_FALLBACK_KEY` (a runtime variable), via `blockProtectedFallback` in `shells/abstract.go` and the equivalent check in `functions/concrete/builder/builder.go`, but **no such guard exists for the primary `cache: key:` field itself** as consumed by `createVolumesManager` in `executors/docker/volume.go`. ### Title
Pipeline-author-controlled cache key `-protected` suffix forces protected Docker volume namespace collision - (File: executors/docker/volume.go)

### Summary
`createVolumesManager` computes the `Protected` flag for the Docker volume manager as `e.Build.IsProtected() || protectedKeyIdx >= 0`, where `protectedKeyIdx` is derived directly from the raw, user-supplied `spec.Cache.Key` value ending in `-protected`. This lets an unprivileged pipeline author (e.g., contributor pushing to an unprotected branch/MR) force their own job's cache/workspace volume into the exact same protected-namespace name that a genuinely protected job on the same project would use for the same cache destination, since the volume name is `UniqueName-cache-hash(destination)[-protected]` and `UniqueName` is project-scoped, not ref-scoped.

### Finding Description
`createVolumesManager` in `executors/docker/volume.go` sets `Protected` based on either `e.Build.IsProtected()` (true ref protection) **or** the presence of any `spec.Cache.Key` ending in `-protected` (excluding `-non_protected`) — this second condition comes straight from job config (`.gitlab-ci.yml` `cache: key:`), which an unprivileged pipeline author fully controls on their own (unprotected) branch/MR. [2](#0-1) 

This `Protected` flag feeds `manager.withProtected`, which appends the `-protected` suffix to the Docker volume name used both for cache volumes (`createCacheVolume`) and for the build/workspace volume created by `createBuildVolume` (which calls `Create`/`CreateTemporary` on the same `jobsDir` path, going through `addCacheVolume`→`createCacheVolume` when no host `CacheDir` is configured). [3](#0-2) [4](#0-3) [5](#0-4) 

Since the resulting Docker volume name is `UniqueName-cache-hash(destination)[-protected]`, and `UniqueName = e.Build.ProjectRealUniqueName()` is scoped to the *project* (not the specific ref or protection state), any job whose config yields the same `(UniqueName, destination, Protected)` tuple will resolve to the identical Docker volume object. An unprivileged contributor can set `cache: key: something-protected` (or, for the reusable/persistent workspace volume path, simply rely on their unprotected MR pipeline reusing the same project's default cache/build destination) to deliberately collide with the volume namespace that legitimate protected-ref jobs use for the same cache/workspace destination path — mounting, reading, and writing into that volume from an unprotected/attacker-controlled job.

The only existing mitigation for this exact class of attack — blocking a `-protected` suffix — is applied solely to `CACHE_FALLBACK_KEY` (a distinct, secondary mechanism) in `functions/concrete/builder/builder.go` and `shells/abstract.go`, not to the primary `cache.key` field that actually drives `createVolumesManager`'s `Protected` computation. [6](#0-5) [7](#0-6) 

There is a dedicated integration test, `Test_CacheVolumeProtected`, that documents and asserts exactly this behavior: an unprotected ref with a cache key ending in `-protected` yields a volume with the `-protected` suffix, identical in naming pattern to what a truly protected ref would produce. [8](#0-7) 

Whether this constitutes a genuine boundary break depends on whether GitLab's backend (Rails) is the only entity that ever sets a `-protected`-suffixed `cache.key`, or whether an ordinary user's literal `.gitlab-ci.yml` `cache: key:` value is passed through to Runner unmodified/unfiltered. Based on the Runner-side code alone, there is no sanitization or origin-check that distinguishes a backend-injected suffix from a user-authored one for the primary cache key — only `CACHE_FALLBACK_KEY` is filtered. This asymmetry (filtered fallback key vs. unfiltered primary key) is itself the concrete Runner-level control gap for this specific path, even though full confirmation would require checking GitLab Rails-side validation of `cache.key`, which is outside this repository's index.

### Impact Explanation
If reachable end-to-end (i.e., if GitLab Rails does not itself filter/reject `-protected`-suffixed cache keys before sending the job to Runner), an unprivileged pipeline author could poison a Docker volume that a later protected-ref job mounts for its cache or workspace, injecting malicious build artifacts, source files, or dependency payloads that execute or get trusted within a protected job's context — protected-job escalation through mounted-state reuse, matching the scoped impact.

### Likelihood Explanation
Preconditions: the attacker needs push access to any unprotected branch/MR of the target project (a standard, low-privilege capability), needs the project to configure Docker executor with cache/build volumes (default, common), and needs a matching cache destination path with a genuinely protected job (plausible for shared `.gitlab-ci.yml` cache paths like `node_modules`, `.cache`, etc.). The attack is reproducible and requires no timing races — it is fully deterministic based on volume naming. However, exploitability is gated entirely on whether the backend/API validates or strips `-protected` suffixes from user-supplied `cache.key` before Runner ever sees it; this cannot be confirmed from the Runner repository alone.

### Recommendation
In `executors/docker/volume.go`, do not derive `Protected` from a raw, unauthenticated `spec.Cache.Key` string comparison alone. Either: (1) have GitLab Rails/backend communicate protection intent via a dedicated, backend-signed field (not a user-editable string suffix), or (2) if the `-protected`/`-non_protected` suffix mechanism must remain string-based, apply the same sanitization/rejection used for `CACHE_FALLBACK_KEY` (see `functions/concrete/builder/builder.go:321-333` and `shells/abstract.go:319-329`) to the primary `cache.key` field as well, so a user cannot self-assign the `-protected` namespace for an actually-unprotected ref.

### Proof of Concept
Extend `Test_CacheVolumeProtected` (already in `executors/docker/docker_command_integration_test.go:3378`) with a two-phase scenario:
1. Run job A with `GitInfo.Protected = true` (simulating a real protected pipeline), cache key `"blammo"`, and cache path `"cached/*"`; write a marker file into the cache path and let cache-archive/volume creation persist it.
2. Run job B with `GitInfo.Protected = false` (unprotected/MR-simulated) but cache key `"blammo-protected"` and the same cache path, targeting the same `ProjectRealUniqueName()`.
3. Assert that job B's created/mounted Docker volume name equals job A's volume name (both end in `-protected` with identical `UniqueName-cache-hash(destination)` prefix), and that job B can read/overwrite the marker file left by job A — proving cross-boundary mounted-state reuse from an unprotected job into the protected-job's volume namespace.

var createVolumesManager = func(e *executor) (volumes.Manager, error) {
	// Note if any of the cache keys includes the `-protected` suffix (but not the `-non_protected` suffix).
	// See https://gitlab.com/gitlab-org/gitlab/-/work_items/494478.
	protectedKeyIdx := slices.IndexFunc(e.Build.Cache, func(c spec.Cache) bool {
		return strings.HasSuffix(c.Key, "-protected") && !strings.HasSuffix(c.Key, "-non_protected")
	})

	config := volumes.ManagerConfig{
		CacheDir:      e.Config.Docker.CacheDir,
		BasePath:      e.Build.FullProjectDir(),
		UniqueName:    e.Build.ProjectRealUniqueName(),
		TemporaryName: e.getProjectUniqRandomizedName(),
		DisableCache:  e.Config.Docker.DisableCache,
		Driver:        e.Config.Docker.VolumeDriver,
		DriverOpts:    e.Config.Docker.VolumeDriverOps,
		// the volume should be protected if the ref is protected OR if any of the cache volumes have the protected
		// suffix. See https://gitlab.com/gitlab-org/gitlab/-/work_items/494478.
		Protected: e.Build.IsProtected() || protectedKeyIdx >= 0,
	}

func (m *manager) createCacheVolume(
	ctx context.Context,
	destination string,
	reusable bool,
) (string, error) {
	destination, err := m.absolutePath(destination)
	if err != nil {
		return "", fmt.Errorf("defining absolute path: %w", err)
	}

	err = m.managedVolumes.Add(destination)
	if err != nil {
		return "", fmt.Errorf("updating managed volumes list: %w", err)
	}

	hashedDestination := hashPath(destination)
	name := m.config.TemporaryName
	if reusable {
		name = m.config.UniqueName
	}

	// volumeName might get quite long. Docker is however happy to create volumes with long names. There is the "myth"
	// that volume names are treated like DNS labels, and thus only allow a length of 63 chars, however that does not hold
	// true. In fact, we already create way longer names, and would catch those issues in various integration tests.
	volumeName := m.withProtected(fmt.Sprintf("%s-cache-%s", name, hashedDestination))

	vBody := client.VolumeCreateOptions{
		Name:       volumeName,
		Driver:     m.config.Driver,
		DriverOpts: m.config.DriverOpts,
		Labels: m.labeler.Labels(map[string]string{
			"destination": destination,
			"protected":   strconv.FormatBool(m.config.Protected),
			"reusable":    strconv.FormatBool(reusable),
			"type":        "cache",
		}),
	}

	v, err := m.client.VolumeCreate(ctx, vBody)
	if err != nil {
		return "", fmt.Errorf("creating docker volume: %w", err)
	}

	if m.permissionSetter != nil {
		err = m.permissionSetter.Set(ctx, v.Name, m.labeler.Labels(map[string]string{"type": "cache-init"}))
		if err != nil {
			return "", fmt.Errorf("set volume permissions: %w", err)
		}
	}

	m.appendVolumeBind(&parser.Volume{
		Source:      v.Name,
		Destination: destination,
	})
	m.logger.Debugln(fmt.Sprintf("Using volume %q as cache %q...", v.Name, destination))

	return volumeName, nil
}

func (e *executor) createBuildVolume() error {
	e.SetCurrentStage(ExecutorStageCreatingBuildVolumes)
	e.BuildLogger.Debugln("Creating build volume...")

	if e.volumesManager == nil {
		return errVolumesManagerUndefined
	}

	jobsDir := e.Build.RootDir

	var err error

	if e.Build.GetGitStrategy() == common.GitFetch {
		err = e.volumesManager.Create(e.Context, jobsDir)
		if err == nil {
			return nil
		}
	} else {
		err = e.volumesManager.CreateTemporary(e.Context, jobsDir)
	}

	if err != nil {
		var volDefinedErr *volumes.ErrVolumeAlreadyDefined
		if !errors.As(err, &volDefinedErr) {
			return err
		}
	}

	return nil
}

func Test_CacheVolumeProtected(t *testing.T) {
	test.SkipIfGitLabCIOn(t, test.OSWindows)
	helpers.SkipIntegrationTests(t, "docker", "info")

	tests := map[string]struct {
		protectedRef          bool
		cacheKey              string
		expectProtectedVolume bool
	}{
		"not protected ref, not protected cache key": {false, "blammo", false},
		"not protected ref, non_protected cache key": {false, "blammo-non_protected", false},
		"protected ref, not protected cache key":     {true, "blammo", true},
		"not protected ref, protected cache key":     {false, "blammo-protected", true},
		"protected ref, protected cache key":         {true, "blammo-protected", true},
	}

	for name, tt := range tests {
		t.Run(name, func(t *testing.T) {
			successfulBuild, err := common.GetRemoteSuccessfulBuild()
			assert.NoError(t, err)

			successfulBuild.GitInfo.Protected = &tt.protectedRef

			successfulBuild.JobInfo.ProjectID = time.Now().Unix()
			successfulBuild.Cache = spec.Caches{
				spec.Cache{
					Key:   tt.cacheKey,
					Paths: spec.ArtifactPaths{"cached/*"},
				},
			}

			build := &common.Build{
				Job: successfulBuild,
				Runner: &common.RunnerConfig{
					RunnerSettings: common.RunnerSettings{
						Executor: "docker",
						Docker: &common.DockerConfig{
							Image:      common.TestAlpineImage,
							PullPolicy: common.StringOrArray{common.PullPolicyIfNotPresent},
							Volumes:    []string{"/cache"},
						},
						Cache: &cacheconfig.Config{},
					},
				},
				ExecutorProvider: docker_executor.NewProvider(),
			}

			// Run a job. We only care that the cache volume is created.
			_, err = buildtest.RunBuildReturningOutput(t, build)
			require.NoError(t, err)

			require.NoError(t, err, "creating docker client")
			defer client.Close()

			// Inspect the created cache volume
			vols, err := client.VolumeList(context.Background(), mobyclient.VolumeListOptions{
				Filters: mobyclient.Filters{}.Add("name", build.ProjectRealUniqueName()),

			require.NoError(t, err)
			assert.Len(t, vols.Items, 1)

				assert.Equal(t, vol.Labels["com.gitlab.gitlab-runner.protected"], "false", "volume label 'com.gitlab.gitlab-runner.protected' should be 'false'")
			}
		})
	}
