### Title
Unfunded instant-withdraw receipts from earlier epochs are dropped from default recovery basis, inflating `defaultRecoveryPrice` and permanently freezing late claimants' recovery - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` look up `instantWithdrawClaimsByEpoch[epochNumber]`, i.e. only the *current* epoch index. Instant-withdraw receipts recorded against an older epoch (`instantWithdrawsRequestsByEpoch[user][oldEpoch]` / `instantWithdrawClaimsByEpoch[oldEpoch]`) can remain unfunded (`pendingInstantWithdraws > 0`) across an epoch boundary. When `finalizeDefaultRecovery` runs in a later epoch, the epoch-keyed lookup "misses" — the same bug class as CVE-2021-33449's `mjs_bcode_part_get_by_offset()` returning a NULL/stale entry for a valid offset — and those claims are silently excluded from `totalBasis`.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestInstantWithdraw` keys receipt basis by the epoch at request time: `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (line 372) and increments `pendingInstantWithdraws` (line 374).
- `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` (line 401) but never touches `instantWithdrawClaimsByEpoch`, so a partially funded instant bucket keeps its claim basis under the *request* epoch forever.
- `defaultPendingClaimBasis` (lines 644-649) computes `basis = pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` — only the current epoch. Old-epoch instant claims contribute `pendingInstantWithdraws`-triggered inclusion logic but zero basis.
- `_defaultPrefundedInstantReserve` (lines 716-720) has the identical defect: `instantBasis = instantWithdrawClaimsByEpoch[epochNumber]` is 0 for old-epoch claims, so already-collected underlying backing them is also not counted as reserve.
- `finalizeDefaultRecovery` (lines 679-692) then computes `recoveryPrice = reserveAmount / totalBasis` on a shrunken `totalBasis`, producing an inflated price, and sets `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` (line 696).

Broken invariant: one receipt one payout / solvency of the recovery reserve. The reserve is sized for a basis that omits valid claims.

### Impact Explanation
Two loss paths:

1. `recoveryPrice` is inflated by the missing basis. Every `_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` and `_claimPostDefaultWithdrawRequest` pays `claimBasis * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve` (lines 782-783, 855, 912-916). Earlier claimants are overpaid relative to the correct pro-rata share; once the reserve is exhausted, `defaultRecoveryReserve -= _amount` underflows and reverts, so the last claimants' recovery is permanently frozen.
2. Old-epoch instant receipts survive `_claimDefaultedInstantWithdrawRequest` because it only clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (line 844). Their remainder falls through to `instantWithdrawsRequests[_user]` → `_transferFundedClaim`, which reverts when `balance - reserve < amount` (lines 899-905) because the strategy holds no funded balance for them. These receipts are permanently unclaimable while any reserve exists — and if the reserve later drains, they still have no funding source.

Quantified loss: if `X` underlying of old-epoch instant claims are excluded, honest claimants lose up to `X` worth of recovery (overpayment to others plus frozen tail claims), and the old-epoch instant claimants lose their entire unfunded receipt.

### Likelihood Explanation
Requires: (a) instant withdrawals enabled, (b) an instant request in epoch N left partially unfunded (borrower funding shortfall at `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` without triggering default), (c) the pool rolls into epoch N+1 so `epochNumber` advances past the request epoch, and (d) a later borrower default finalized via `finalizeDefaultRecovery`. Each step is reachable by unprivileged users (any tranche holder can request instant withdraw; default is a borrower/liquidity event, not attacker-controlled privilege). The attacker in the losing position is simply a claimant whose receipt lands in the wrong epoch bucket — no privileged collusion needed. Medium likelihood: it needs the specific sequence of cross-epoch unfunded instant claims plus default.

### Recommendation
Track instant-claim basis across all epochs, not just the current one: e.g., keep a global `instantWithdrawClaimsTotal` counter alongside `instantWithdrawClaimsByEpoch`, or iterate/accumulate the claim basis and prefunded portion so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` include every outstanding receipt. Alternatively, clear `instantWithdrawClaimsByEpoch[oldEpoch]` entries when claims are funded, and gate `startEpoch` on `pendingInstantWithdraws == 0` so instant receipts cannot outlive their request epoch unfunded.

### Proof of Concept
Foundry fork PoC sketch (against `IdleCDOEpochVariant` + `IdleCreditVault`):

```solidity
function testOldEpochInstantClaimsDroppedFromRecovery() external {
    // 1. Deposit AA/BB, start epoch 0, enable instant withdraws.
    idleCDO.depositAA(100_000e6);
    vm.prank(manager); cdoEpoch.startEpoch();
    cdoEpoch.setInstantWithdrawParams(delay, minAprDelta, true);

    // 2. Stop epoch 0 with low APR so epoch 1 offers instant withdraws.
    _stopEpoch(aprLow);

    // 3. User requests instant withdraw in epoch 1.
    uint256 req = cdoEpoch.requestInstantWithdraw(shares, AAtranche);
    // instantWithdrawClaimsByEpoch[1] == req; pendingInstantWithdraws == req

    // 4. Borrower partially funds: collectInstantWithdrawFunds(req / 2)
    //    -> pendingInstantWithdraws == req/2, claims basis still keyed at epoch 1.

    // 5. Manager starts epoch 2 then epoch 3 (epochNumber advances to 3).
    //    Old instant receipt remains unfunded in instantWithdrawClaimsByEpoch[1].

    // 6. Borrower defaults; owner/manager finalize with _recoveredAmount = R.
    cdoEpoch.finalizeDefault();
    strategy.finalizeDefaultRecovery(R, recoverySource);

    // ASSERT BUG:
    // defaultPendingClaimBasis() == pendingWithdraws + instantWithdrawClaimsByEpoch[3] (== 0)
    // => req is missing from totalBasis => defaultRecoveryPrice inflated.
    // Users claiming first receive claimBasis * inflatedPrice; reserve underflows for the
    // last claimant -> their _transferDefaultRecovery reverts (permanent freeze).
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest(); // last claimant
    // Old instant receipt: _claimDefaultedInstantWithdrawRequest clears only epoch==3,
    // remainder hits _transferFundedClaim guard -> reverts while reserve > 0.
}
```

The exact revert depends on claim ordering, but the deterministic assertion is `defaultPendingClaimBasis()` returning a value that excludes the still-outstanding `instantWithdrawClaimsByEpoch[oldEpoch]` amount while `pendingInstantWithdraws > 0`.

Note: I could not fully verify within this pass whether `startEpoch`/`getInstantWithdrawFunds` unconditionally blocks progression while `pendingInstantWithdraws > 0` without defaulting; if the CDO hard-blocks new epochs on any unfunded instant remainder, the cross-epoch precondition may be unreachable and this finding would downgrade. That check would need to be confirmed in `IdleCDOEpochVariant.startEpoch`/`_beforeStopEpoch` before finalizing severity.
