### Title
`fastzip` extractor bypasses `.git`-path protections applied by the legacy zip extractor - ([File: commands/helpers/archive/fastzip/zip_fastzip_extractor.go])

### Summary
`extractor.Extract` in `zip_fastzip_extractor.go` delegates entirely to the external `github.com/saracen/fastzip` library's `Extract` method without any repo-control-path check, whereas the legacy extractor path (`helpers/archives/zip_extract.go`) at least calls `errorIfGitDirectory` on every archive entry before extraction. Because `FF_USE_FASTZIP` routes both artifact and cache restores through this code, jobs configured with the fastzip extractor lose even the warning-level `.git` detection that exists elsewhere in the codebase.

### Finding Description
`Extract` in `commands/helpers/archive/fastzip/zip_fastzip_extractor.go:33-46` builds a `fastzip.Extractor` from the untrusted archive reader and directly calls `extractor.Extract(ctx)`, with no inspection of entry names, and no `.git`-path detection comparable to `errorIfGitDirectory`/`printGitArchiveWarning` used in `helpers/archives/zip_extract.go:12,89` (`ExtractZipArchive`). Path traversal / `zip-slip` handling is delegated entirely to the third-party `saracen/fastzip` library, which is outside this repo's control and not audited as part of this codebase.

An unprivileged pipeline author fully controls the contents of a job's own cache and artifact archives (via `cache:paths`/`artifacts:paths`, or by uploading a crafted artifact/cache blob from an earlier stage). If cache/artifact restore for a later job in the same working directory writes into `.git/hooks/*`, `.git/config`, or `core.hooksPath`-referenced files, and the job's `GIT_STRATEGY` is `fetch` (the default, which reuses the existing checkout instead of a clean clone), those files persist in the build directory across job invocations on the same runner. Even noting that `errorIfGitDirectory` in the legacy path is only a *warning* (it does not actually block extraction — `tracker.actionable` just triggers a log message, and `extractZipFile` still runs immediately after), the fastzip path doesn't even emit that warning, giving operators/監視 no signal that `.git` content is being overwritten via archive restore.

### Impact Explanation
If a later git operation (`git fetch`, `git checkout`, or any git subcommand) executes in the same directory after a poisoned `.git/hooks/*` or `.git/config` (e.g., `core.hooksPath`, `core.fsmonitor`, `.git/hooks/post-checkout`) is restored, arbitrary commands can run in the context of the job's git helper invocation the next time the workspace is reused — e.g. on a subsequent pipeline run on the same runner with `GIT_STRATEGY=fetch`. This is scoped to a single project/runner's reused workspace (not a cross-tenant sandbox escape), but it does allow a low-privilege contributor whose job runs on a shared/reused runner workspace to plant execution that fires on a later, possibly protected-branch, job sharing that same checkout directory.

### Likelihood Explanation
Requires: (1) `FF_USE_FASTZIP` enabled (fastzip is the intended eventual default extractor), (2) the job's cache or artifacts include `.git/...` paths (fully attacker-controlled, since cache/artifact content is produced by the attacker's own job scripts), and (3) `GIT_STRATEGY=fetch` (default) so the checkout directory and its `.git` are reused rather than being freshly cloned. All three preconditions are common in real CI configurations (shared runners with persistent build dirs, default git strategy). It's a repeatable, self-contained PoC: no external services or admin compromise needed.

### Recommendation
Add the same `.git`-path detection used in `helpers/archives/zip_extract.go` (or, better, an actual rejection rather than a warning) to the fastzip extraction path — either by wrapping/filtering entries before calling `fastzip.Extractor.Extract`, or by post-processing the extracted file list and refusing/removing any path whose first component is `.git`. This should reject rather than merely warn, since a warning provides no security benefit once files have already been written to disk.

### Proof of Concept
Go integration test outline:
1. Build a zip archive containing an entry named `.git/hooks/post-checkout` with executable content (e.g., a shell script that touches a marker file).
2. Extract it via `fastzip.NewExtractor(...).Extract(ctx)` into a temp dir that already has a `.git` directory (simulating a reused build workspace).
3. Assert the file `.git/hooks/post-checkout` exists and is executable (proving no protection), unlike the desired end-state where extraction into `.git/*` should be rejected.
4. As a comparison, run `helpers/archives.ExtractZipArchive` on the same archive and observe that although `printGitArchiveWarning` fires, the file is still written — demonstrating the legacy path's check is warning-only and the fastzip path lacks even that. [1](#0-0) [2](#0-1) [3](#0-2)

func isPathAGitDirectory(path string) bool {
	parts := strings.Split(filepath.Clean(path), string(filepath.Separator))
	if len(parts) > 0 && parts[0] == ".git" {
		return true
	}
	return false
}

func errorIfGitDirectory(path string) *os.PathError {
	if !isPathAGitDirectory(path) {
		return nil
	}

	return &os.PathError{
		Op:   ".git inside of archive",
		Path: path,
		Err:  errors.New("trying to archive or extract .git path"),
	}
}

func printGitArchiveWarning(operation string) {
	logrus.Warn(fmt.Sprintf("Part of .git directory is on the list of files to %s", operation))
	logrus.Warn("This may introduce unexpected problems")
