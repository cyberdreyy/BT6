### Title
Stale confirmations from removed multisig members allow request execution below the live confirmation threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
When a multisig key/member is removed via `DeleteKey` (`multisig`) or `DeleteMember` (`multisig2`), the contract only purges *requests originally submitted by* that key/member. It never scans the `confirmations` map to strip that key/member's prior approvals from *other, still-pending* requests. Because `confirm()` only ever compares the raw size of the stored confirmation set to `num_confirmations`, a confirmation recorded by a member who is no longer part of the multisig continues to count toward the K-of-N threshold, letting a request execute with fewer *live* approvals than required.

### Finding Description
The invariant the multisig is supposed to enforce is: `confirmations.len() == number of currently-valid members who approved` must reach `num_confirmations` before a request executes. In practice the code only enforces `confirmations.len() >= num_confirmations`, treating the stored `HashSet` as ground truth even after membership changes.

In `multisig/src/lib.rs`, `DeleteKey` handling only removes requests whose *signer* matches the deleted key and clears `num_requests_pk`, but does not touch `confirmations` entries for other requests: [1](#0-0) 

The threshold check in `confirm()` blindly trusts the stored confirmation set size: [2](#0-1) 

The same pattern exists in `multisig2/src/lib.rs`: `delete_member()` removes requests submitted by the departing member and the member from the `members` set, but leaves that member's `String` entries inside `confirmations` for any other pending requests untouched: [3](#0-2) 

And `confirm()` again only checks `confirmations.len()` against `num_confirmations` without re-validating that every recorded confirmer is still in `self.members`: [4](#0-3) 

This mirrors the reported bug class: a recorded value (`utilizeIndex`/interest, here "confirmations counted") is not correctly reconciled when the underlying entity it depends on changes state (repay/utilize, here "member removed"), so a stale record keeps being trusted as if it still reflected reality.

### Impact Explanation
This breaks the core custody/authorization binding of the multisig: `confirmations counted == live members who approved`. A request (e.g., `Transfer`, `AddKey`/`AddMember`, `DeployContract`, `FunctionCall`) can be executed with strictly fewer live, currently-authorized approvals than `num_confirmations` requires, because a stale confirmation from a removed member is still counted. This is a Critical impact per the rules: "a multisig request executed below threshold," and can directly result in unauthorized transfer of NEAR held by the multisig account, or unauthorized key/contract changes.

### Likelihood Explanation
This requires only ordinary, in-scope multisig operations — not any foundation/owner/admin privilege outside the contract's own design: (1) a member submits and gets partial confirmations on a pending request, (2) that member is later removed via a normal `DeleteKey`/`DeleteMember` request (e.g., routine key rotation or removing a suspected-compromised member), and (3) the remaining/malicious members confirm just enough additional times to reach the raw `num_confirmations` count. No `assert_valid_request`/`confirm` check re-validates the currently stored confirmers against `self.members` (`multisig2`) or currently-valid keys (`multisig`), so nothing prevents this. This is a realistic operational sequence for any long-lived multisig that periodically rotates members.

### Recommendation
In `delete_member` (`multisig2`) / `DeleteKey` handling (`multisig`), iterate over all pending requests' `confirmations` sets (not just requests submitted by the removed member) and remove any confirmation entry matching the removed member/key. Additionally, in `confirm()`, before comparing against `num_confirmations`, filter the stored confirmation set to only members currently present in `self.members` (or currently valid keys), so removed members can never contribute toward the threshold, even transiently.

### Proof of Concept
1. Deploy `multisig2` with 4 members (`A`, `B`, `C`, `D`) and `num_confirmations = 3`.
2. `A` calls `add_request` for a `Transfer` of the pool's NEAR balance to an attacker-controlled account; `A` auto-confirms (`add_request_and_confirm`), so confirmations = `{A}` (count 1).
3. `B` calls `confirm(request_id)` → confirmations = `{A, B}` (count 2), still below threshold (3).
4. Separately, the multisig legitimately removes `B` (e.g., `B`'s device is lost) via a `DeleteMember { member: B }` request confirmed by `A`, `C`, `D`. `delete_member()` removes `B` from `self.members` and deletes requests *submitted by* `B`, but the pending transfer request from step 2 was submitted by `A`, so it is untouched — its confirmations set still contains `B`.
5. `C` (now the second still-live confirmer) calls `confirm(request_id)`. `confirmations.len() + 1 == 3 >= num_confirmations`, so the transfer executes — even though only `A` and `C` are actually live, authorized members who approved (2 live approvals against a 3-of-4 policy), with `B`'s stale confirmation illegitimately making up the difference.     pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
