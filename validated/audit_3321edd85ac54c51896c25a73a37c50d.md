### Title
Forged exit-status JSON markers in job stdout can desynchronize `remoteProcessTerminated`/`remoteStageStatus`, hanging the kubernetes log-processor goroutine and misattributing stage exit codes - ([File: executors/kubernetes/kubernetes.go])

### Summary
The kubernetes executor determines stage completion and exit status entirely from JSON markers (`{"command_exit_code":N,"script":"..."}`) that are read back from the build container's own stdout/log file, which is fully attacker-controlled content since it is literally the job script's own output. Because `forwardLogLine` unconditionally forwards every such marker to a single-slot handoff (`s.remoteProcessTerminated`) and only one receive happens per stage in `runInContainer`, a script that emits more than one exit-status marker (or an out-of-order one) can leave a stale send pending that gets consumed by a *later* stage's receive, or block the log-processing goroutine's send if nobody is listening.

### Finding Description
`StageCommandStatus.BuildStage()` derives the "current stage" purely from the `script` field of a JSON blob parsed out of the job's own stdout [1](#0-0) . This JSON is expected to be printed once by a shell trap (`bashJSONTerminationScript`) on script exit [2](#0-1) , but nothing prevents the job's own script from printing additional, forged lines matching the same shape to stdout, since it's the same stream that is `tee`'d into the log file the log-processor reads from [3](#0-2) .

`processLogs` runs a single-threaded loop that calls `forwardLogLine` synchronously for every line read from the log stream [4](#0-3) . `forwardLogLine` unconditionally sends any exited status onto `s.remoteProcessTerminated` [5](#0-4) . On the consumer side, `runInContainer` performs exactly one blocking receive from `s.remoteProcessTerminated` per stage invocation [6](#0-5) , and `checkScriptExecution` uses `s.remoteStageStatus.BuildStage()` compared against the stage being retried to decide whether an attach failure should be retried or treated as already-completed [7](#0-6) .

If the attacker's script (in the same job) prints two or more exit-status markers during a single stage's execution (trivial: `echo '{"command_exit_code": 0, "script": "<any-stage-name>"}'` in the job's `.gitlab-ci.yml` script), the extra marker's send on `remoteProcessTerminated` has no consumer at that point in time (the one receive for the current stage has already happened or hasn't happened yet), so:
- The send blocks inside `forwardLogLine`, which blocks the single `processLogs` goroutine's `select` loop entirely — no further log lines are forwarded to the trace and no further exit-status markers (including legitimate ones from subsequent stages) can be processed, because the same goroutine must return to the `select` before it can read anything else.
- Alternatively, if the extra send does eventually get matched by the *next* stage's single receive in `runInContainer`, that next stage will use a stale/forged exit code and forged `script` field, since `runInContainer` blindly trusts whatever comes off the channel as *the current stage's* result [8](#0-7) .

There is no sequencing check, sequence number, nonce, or correlation ID tying a given marker to the specific attach/exec invocation that's expected to produce it. `checkScriptExecution`'s `BuildStage()` comparison is the *only* correctness mechanism, and it is driven entirely by attacker-suppliable content, not by a real termination signal from the Kubernetes API (e.g., container exit status) or a unique per-invocation token.

### Impact Explanation
Within the attacker's own job, forged/duplicated markers can (a) hang the `processLogs` goroutine indefinitely by leaving an unconsumed blocking send on `remoteProcessTerminated`, and (b) cause a subsequent stage's `runInContainer` call to consume a stale/forged exit status intended for a different stage, corrupting exit-code reporting and retry decisions. A hung `processLogs` goroutine started via `go s.processLogs(ctx)` [9](#0-8)  is tied to the job's own context; it is cancelled when the build context is cancelled, and `Cleanup`/`cleanupResources` deletes the pod on a separate background context with its own timeout regardless of `processLogs` state [10](#0-9) , so pod teardown itself is not blocked by this goroutine. The concrete, verifiable impact is therefore scoped to the attacker's own job: incorrect/missed exit-code reporting, and a leaked/blocked goroutine for the duration of that job (bounded by job/context cancellation) rather than a cross-tenant resource-exhaustion vector, since the pod delete path (`cleanupResources`) does not wait on `processLogs`.

### Likelihood Explanation
Trivially reproducible by any unprivileged pipeline author: they fully control the script executed in the build container and can simply `echo` a matching JSON line as part of their own `.gitlab-ci.yml` script. No special privileges, cluster access, or timing tricks beyond controlling job script content are required. It only affects the attacker's own job's log-processing/state-tracking correctness, not other tenants' pods or namespaces, and does not bypass the pod cleanup path.

### Recommendation
- Add a correlation mechanism (e.g. a per-attach nonce/sequence embedded in the marker and validated on receipt) so a marker is only accepted by the specific `runInContainer` invocation that generated the script producing it.
- Change `runInContainer`'s receive from a single blind read to a loop that discards/logs unexpected or duplicate markers not matching the expected stage/sequence, rather than trusting the first thing off the channel.
- Make `forwardLogLine`'s send onto `remoteProcessTerminated` non-blocking (e.g. `select` with a default/drop-and-log branch) so a malformed or duplicated marker cannot stall the entire log-processing goroutine.
- Do not rely solely on the `script` field's basename match in `checkScriptExecution`; combine with an invocation-scoped token.

### Proof of Concept
Go unit test extending `TestProcessLogs`-style setup in `kubernetes_test.go`:
1. Feed the mock log processor's `lineCh` two exit-status marker lines for the *same* stage in quick succession (e.g. `{"command_exit_code":0,"script":"prepare_script"}` twice) before any consumer has issued its second receive.
2. Assert that `processLogs`'s goroutine still services the `select` loop afterward (e.g. push a plain log line and confirm it is written to `mockTrace.Write` within a bounded timeout) — a failure to do so within the timeout demonstrates the blocking-send hang.
3. Separately, in a `runInContainer`-level test, arrange for two markers to be emitted during stage A's run, then start stage B's `runInContainer` and assert that stage B does not receive stage A's stale marker (i.e., `checkScriptExecution`/`BuildStage()` correctly rejects the mismatched marker rather than silently accepting it as stage B's result).

func (c StageCommandStatus) BuildStage() common.BuildStage {
	if c.Script == nil {
		return ""
	}

	// When using `powershell/pwsh`, script contains only the script name without its extension being executed.
	// When using `bash` shell, script contains the script absolute path. We therefore need to extract the script name.
	split := strings.Split(*c.Script, "/")
	stage := split[len(split)-1]

	return common.BuildStage(stage)
}

func (s *executor) forwardLogLine(w io.Writer, line string) {
	var status shells.StageCommandStatus
	if !status.TryUnmarshal(line) {
		if _, err := w.Write([]byte(line)); err != nil {
			s.BuildLogger.Warningln(fmt.Sprintf("Error writing log line to trace: %v", err))
		}

		return
	}

	s.BuildLogger.Debugln(fmt.Sprintf("Setting remote stage status: %s", status))
	s.remoteStageStatusMutex.Lock()
	s.remoteStageStatus = status
	s.remoteStageStatusMutex.Unlock()

	if status.IsExited() {
		s.remoteProcessTerminated <- status
	}
}

func (s *executor) cleanupResources() {
	// Here we don't use the build context as its timeout will prevent a successful cleanup of the resources.
	// The solution used here is inspired from the one used for the docker executor.
	// We give a configurable timeout to complete the resources cleanup.
	ctx, cancel := context.WithTimeout(context.Background(), s.Config.Kubernetes.GetCleanupResourcesTimeout())
	defer cancel()

	if s.pod != nil {
		kubeRequest := retry.WithFn(s, func() error {
			// kubeAPI: pods, delete
			return s.kubeClient.CoreV1().
				Pods(s.pod.Namespace).
				Delete(ctx, s.pod.Name, metav1.DeleteOptions{
					GracePeriodSeconds: s.Config.Kubernetes.CleanupGracePeriodSeconds,
					PropagationPolicy:  &PropagationPolicy,
				})
		})

		if err := kubeRequest.Run(); err != nil {
			s.BuildLogger.Errorln(fmt.Sprintf("Error cleaning up pod: %s", err.Error()))
		}
	}

	if s.credentials != nil && len(s.credentials.OwnerReferences) == 0 {
		kubeRequest := retry.WithFn(s, func() error {
			// kubeAPI: secrets, delete
			return s.kubeClient.CoreV1().
				Secrets(s.configurationOverwrites.namespace).
				Delete(ctx, s.credentials.Name, metav1.DeleteOptions{
					GracePeriodSeconds: s.Config.Kubernetes.CleanupGracePeriodSeconds,
				})
		})
		if err := kubeRequest.Run(); err != nil {
			s.BuildLogger.Errorln(fmt.Sprintf("Error cleaning up secrets: %s", err.Error()))
		}
	}

	err := s.teardownBuildNamespace(ctx)
	if err != nil {
		s.BuildLogger.Errorln(fmt.Sprintf("Error tearing down namespace: %s", err.Error()))

func (s *executor) checkScriptExecution(stage common.BuildStage, err error) error {
	// Retrying attach command is a bit different from regular Kubernetes requests.
	// Since the attach commands are executed by openning an HTTP stream to the Kubernetes server
	// and piping the command into that stream and then expecting a response there's no good place to check
	// whether the whole command execution was successful.
	// If we check whether the Stdin stream was read - the connection might have broken up after during transit of that
	// meaning that the command was never executed.
	// It could have also been broken during the reading of the response stream - meaning that it was executed, but we can't know that.
	// The only solution is to check for certain whether the process is already running.
	// For attach that is easy since the process is completely running in the background, and we receive the status of it through
	// the log file and the log processor moves things forward.

	// Non-network errors don't concern this function
	if slices.ContainsFunc(retryNetworkErrorsGroup, func(v string) bool {
		return err != nil && strings.Contains(err.Error(), v)
	}) {
		return err
	}

	s.remoteStageStatusMutex.Lock()
	defer s.remoteStageStatusMutex.Unlock()
	s.BuildLogger.Debugln(fmt.Sprintf("Checking remote stage status after trying attach with err %v. Remote stage status: %v", err, s.remoteStageStatus))

	// If the remote stage is the one we are trying to retry it means that it was already executed.
	s.BuildLogger.Debugln(fmt.Sprintf("Remote stage: %v, trying to execute stage %v", s.remoteStageStatus.BuildStage(), stage))
	if s.remoteStageStatus.BuildStage() == stage {
		return nil
	}

	// If the remote stage is not the same, then we can retry
	return err
}
