### Title
Missing `env::state_exists()` guard in `LockupContract::new` allows unprivileged re-initialization of a live lockup account, releasing locked/unvested funds to an attacker - (File: `lockup/src/lib.rs`)

### Summary
`LockupContract::new` (lines 181-243) is a public `#[init]` method with no check that state does not already exist, unlike every other privileged/init method in this repo (`staking-pool::new`, `lockup-factory::new`, `staking-pool-factory::new`, `multisig::new`, `voting::new`, `whitelist::new`, all of which call `assert!(!env::state_exists(), ...)`). Since `new` carries no owner/predecessor check either, any unprivileged account can send a `FunctionCall` to an already-deployed lockup account invoking `new` again with attacker-chosen parameters, completely overwriting `owner_account_id`, `lockup_information`, and `vesting_information` in place, while `lockup_amount` is recomputed from `env::account_balance()` — the full current balance of the victim's lockup, including all previously locked/unvested tokens.

### Finding Description
The invariant broken: `state_exists(lockup_account) == true` should imply `new` can never execute successfully again ("initialisation happens exactly once per account"). In this codebase that binding is enforced everywhere except here:

- `staking-pool/src/lib.rs:179`: `assert!(!env::state_exists(), "Already initialized");`
- `lockup-factory/src/lib.rs:80`: `assert!(!env::state_exists(), "The contract is already initialized");`
- `whitelist`, `voting`, `multisig`, `staking-pool-factory` all contain the equivalent guard (per repo grep, each has exactly one `state_exists`/`ignore_state` match).
- `lockup/src/lib.rs` `LockupContract::new` (lines 181-243) has **no such assertion**, and no `assert_owner`/`assert_self`/`assert_called_by_foundation` check either — it only validates the account IDs supplied as arguments. [1](#0-0) 

Because `new` is a normal public contract method (the `#[init]` attribute in the near-sdk version used here is only a documentation/tooling hint and does not itself insert a `state_exists` check — evidenced by every other contract having to add the check manually), any account can submit a transaction whose receiver is the victim lockup account and whose function call is `new`, without holding any key on that account. On success:

- `lockup_information.lockup_amount = env::account_balance()` is recomputed as the current balance of the victim lockup account (i.e., the previously locked/unvested funds sitting there). [2](#0-1) 
- `owner_account_id` is overwritten with an attacker-chosen account.
- `transfers_information` can be set to `TransfersEnabled { transfers_timestamp: <a past timestamp> }`, immediately satisfying `assert_transfers_enabled`.
- `vesting_schedule` can be omitted (`VestingInformation::None`), removing any vesting/termination restriction, and `release_duration` can be omitted or set arbitrarily, removing any linear-release restriction.

Once state is overwritten, every owner-only method (`select_staking_pool`, unstake/withdraw flows, and ultimately transfer methods) checks only `assert_owner`, i.e. `predecessor_account_id == self.owner_account_id`: [3](#0-2) 
Since the attacker just set `owner_account_id` to their own account, they now pass `assert_owner` and can withdraw the full liquid balance (`get_liquid_owners_balance`, bounded only by `MIN_BALANCE_FOR_STORAGE`) that was previously locked/unvested and belonged to the legitimate owner.

None of the existing guards catch this: `assert_owner`/`assert_called_by_foundation`/`assert_self()` are irrelevant because `new` itself checks none of them; `assert_no_termination`/`assert_transfers_enabled` operate on the state the attacker just wrote, not the prior state; there is no `is_promise_success()` or one-yocto guard involved since this is a direct call, not a callback.

### Impact Explanation
This allows NEAR that was locked or unvested in a legitimate employee/investor lockup to be moved out of the contract to a party (the attacker) never entitled to it — a direct match for the Critical impact category "locked or unvested tokens released early" / "funds moved out of a lockup by a party not entitled to it." The attack is repeatable against any deployed lockup account (every lockup created via `lockup-factory` is a fresh target), and the attacker's cost is a single low-gas transaction with no deposit requirement (the only assertions in `new` are format checks on account IDs). This is total loss of custody of the target lockup's balance, not merely griefing.

### Likelihood Explanation
Preconditions: the target must be an existing, already-initialized lockup contract with a nonzero balance (locked/unvested funds) — this is the normal state of any active lockup. No special balances, no foundation/owner privilege, and no whitelist status are required from the attacker; they only need the target's account ID, which is public (all lockup accounts are deterministically named `sha256(owner)[..20].<factory>` and enumerable/knowable). The exploit costs a single `FunctionCall` transaction to `new` with attacker-controlled arguments — no attached deposit is required since `new` doesn't check balance beyond what's already on the account. This is straightforward and repeatable across every lockup account in the ecosystem.

### Recommendation
Add `assert!(!env::state_exists(), "The contract is already initialized");` as the first statement in `LockupContract::new` in `lockup/src/lib.rs`, mirroring the guard present in `staking-pool::new`, `lockup-factory::new`, and the other contracts in this repository.

### Proof of Concept
```rust
// lockup/src/lib.rs tests module (near-sdk testing_env! unit test)
#[test]
#[should_panic(expected = "already initialized")]
fn test_reinit_blocked_after_fix_or_demonstrates_bug() {
    let mut context = basic_context(); // sets account balance to LOCKUP_NEAR, predecessor = system_account()
    testing_env!(context.clone());

    // Legitimate initialisation by rightful owner via factory-style call.
    let _contract = LockupContract::new(
        account_owner(),
        to_nanos(YEAR).into(),
        None,
        TransfersInformation::TransfersDisabled {
            transfer_poll_account_id: AccountId::from("transfers"),
        },
        None,
        None,
        AccountId::from("whitelist"),
        None,
    );
    // Binding under test: owner_account_id == account_owner()
    // assert_eq!(_contract.owner_account_id, account_owner());

    // Attacker (arbitrary predecessor, no key on the lockup account) calls `new` again.
    context.predecessor_account_id = "attacker".to_string();
    testing_env!(context.clone());

    let attacker_contract = LockupContract::new(
        AccountId::from("attacker"),           // owner_account_id overwritten
        0.into(),                              // lockup_duration = 0
        None,
        TransfersInformation::TransfersEnabled {
            transfers_timestamp: to_ts(0).into(), // already-past timestamp: transfers immediately enabled
        },
        None,                                  // no vesting schedule
        None,                                  // no release_duration lock
        AccountId::from("whitelist"),
        None,
    );

    // Binding violated: owner_account_id now equals the attacker, not account_owner().
    assert_eq!(attacker_contract.owner_account_id, AccountId::from("attacker"));
    // On unpatched code this assertion passes (no panic), proving state was overwritten.
    // With the recommended fix (`assert!(!env::state_exists(), ...)` added), this second
    // `LockupContract::new` call panics with "already initialized" instead, matching the
    // #[should_panic] expectation.
}
```
