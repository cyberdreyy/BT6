### Title
Post-default instant withdraw requests are smuggled into the already-finalized default epoch's claim bucket and drain the fixed `defaultRecoveryReserve` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestInstantWithdraw` has no `defaultRecoveryFinalized` handling at all, unlike `requestWithdraw`, which explicitly routes post-default requests to `postDefaultRequests` and rejects users with open receipts (`IdleCreditVault.sol:243-258` vs `356-375`). Because the strategy `epochNumber` is intentionally not bumped when the borrower defaults (see `IdleCDOEpochQueue._prefundedEpochToProcess`, `IdleCDOEpochQueue.sol:288-291`), a receipt created after `finalizeDefaultRecovery` is written into `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — the same slot used by pre-default defaulted-epoch receipts — and is then paid out by `_claimDefaultedInstantWithdrawRequest` from the fixed `defaultRecoveryReserve` (`IdleCreditVault.sol:842-856`). This mirrors the llhttp bug class: a new request is smuggled across a boundary (the terminated default epoch) that the accounting already considers closed, because the epoch "record" was never terminated.

### Finding Description
When the borrower defaults and the manager calls `finalizeDefault`, `finalizeDefaultRecovery` computes `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` where `totalBasis` is fixed over the claims that existed at finalization (`IdleCreditVault.sol:679-693`). The resulting `defaultRecoveryReserve` exactly covers `sum(claimBasis_i * recoveryPrice)` for those claims.

After finalization:

1. A tranche holder calls `IdleCDOEpochVariant.requestWithdraw`. If instant mode is enabled and `lastEpochApr > unscaledApr + instantWithdrawAprDelta`, the CDO calls `creditVault.requestInstantWithdraw(_underlyings, msg.sender)` (`IdleCDOEpochVariant.sol:761-768`). Neither the CDO path nor `requestInstantWithdraw` checks `defaultRecoveryFinalized`.
2. `requestInstantWithdraw` mints the user a 1:1 strategy-token receipt and increments `instantWithdrawsRequestsByEpoch[user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws` (`IdleCreditVault.sol:360-374`). Since `epochNumber == defaultRecoveryEpoch` (no bump on default), the new receipt is indistinguishable from a defaulted-epoch receipt.
3. The user calls `claimInstantWithdrawRequest` (via the CDO). Because `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` is true (the latter requires `pendingInstantWithdraws != 0` at finalization, i.e. at least one unfunded pre-default instant receipt existed), `_claimDefaultedInstantWithdrawRequest` clears `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — now including the post-default receipt — and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` (`IdleCreditVault.sol:380-393`, `842-856`, `912-917`).

The reserve was sized only for basis that existed at finalization. Every post-default claim paid at `defaultRecoveryPrice` consumes reserve belonging to legitimate defaulted-epoch claimants, so later claimants' `safeTransfer` reverts once the reserve (and balance) is exhausted — their unclaimed recovery is permanently frozen/stolen.

### Impact Explanation
`defaultRecoveryReserve` solvency is broken: `reserve < sum over remaining claimants of claimBasis * defaultRecoveryPrice` after the attack. Early post-default claimants extract recovery funds; pre-default claimants (tranche holders and queue users with funded instant receipts) who claim later receive less than their entitlement or nothing, since `_transferDefaultRecovery` does `defaultRecoveryReserve -= _amount` and reverts on underflow. Loss is bounded by the reserve itself but directly steals unclaimed recovery — quantified as `postDefaultReceipt * defaultRecoveryPrice / RECOVERY_FULL` per smuggled receipt, repeatable until the reserve is drained.

### Likelihood Explanation
Requires: (a) instant withdraw mode enabled (`setInstantWithdrawParams`), (b) an unfunded instant receipt at finalization so `defaultInstantWithdrawsFinalized` is set, and (c) post-default, the APR-drop trigger `lastEpochApr > unscaledApr + instantWithdrawAprDelta` firing on an attacker `requestWithdraw` — achievable if the honest manager lowers APR post-default, or if `lastEpochApr` still exceeds a near-zero APR after default. Any KYC-passed tranche holder can perform it. The attacker is paid below their contributed value (double haircut), so the exploit is griefing-flavored theft-by-exhaustion rather than self-enrichment; it still causes permanent freezing of other users' unclaimed recovery, which meets the impact bar, but the attacker's own economic incentive is weak, lowering practical likelihood.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: either revert when `defaultRecoveryFinalized` is set, or route the receipt into a distinct post-default bucket that is paid only at par from newly-funded underlyings (never from `defaultRecoveryReserve`). Additionally, guard `_claimDefaultedInstantWithdrawRequest` to clear only receipts recorded at or before `defaultRecoveryEpoch` (e.g. snapshot `instantWithdrawClaimsByEpoch[defaultEpoch]` at finalization and cap per-user claimBasis at the value recorded then).

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// setup: instant withdraw enabled, user1 deposits, epoch runs, apr drops -> instant request
_setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
cdoEpoch.setInstantWithdrawParams(instantDelay, aprDelta, false);
idleCDO.depositAA(amount1); // user1
cdoEpoch.requestInstantWithdraw(user1TrancheBal, address(AAtranche)); // pendingInstantWithdraws > 0

// borrower defaults; manager finalizes with partial recovery
_checkDefault();
uint256 basis = creditVault.defaultPendingClaimBasis();
uint256 recovered = basis * 6e17 / 1e18;
deal(defaultUnderlying, manager, recovered);
vm.prank(manager);
cdoEpoch.finalizeDefault(recovered, manager);
assertTrue(creditVault.defaultRecoveryFinalized());
assertTrue(creditVault.defaultInstantWithdrawsFinalized()); // pendingInstantWithdraws != 0

// attacker: deposit tranches post-default at haircut price, trigger instant request
// (apr drop condition still met: lastEpochApr > unscaledApr + delta)
uint256 attackerReceipt = cdoEpoch.requestInstantWithdraw(attackerTrancheBal, address(AAtranche));
// BUG: no revert; receipt lands in instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch]
assertEq(
  creditVault.instantWithdrawsRequestsByEpoch(attacker, creditVault.defaultRecoveryEpoch()),
  attackerReceipt
);

// attacker claims immediately, paid from defaultRecoveryReserve
uint256 reservePre = creditVault.defaultRecoveryReserve();
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
uint256 paid = attackerReceipt * creditVault.defaultRecoveryPrice() / creditVault.RECOVERY_FULL();
assertEq(creditVault.defaultRecoveryReserve(), reservePre - paid); // reserve drained

// victim user1's legitimate defaulted-epoch claim now underpays/reverts
vm.prank(user1);
cdoEpoch.claimInstantWithdrawRequest(); // insufficient reserve -> revert / partial payout
```

The invariant violation: `defaultRecoveryReserve` is consumed by claims whose basis was never part of `totalBasis` at finalization, because `requestInstantWithdraw` fails to terminate the default-epoch boundary the way `requestWithdraw` does via `postDefaultRequests`.
