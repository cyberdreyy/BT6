### Title
Removing a multisig member does not purge their stale confirmations from other pending requests, allowing a request to execute below the effective live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` only deletes *requests created by* the removed member; it does not scan and strip that member's *confirmations on other members' pending requests*. Because `confirm()` counts `confirmations.len()` regardless of whether the signers are still current members, a stale confirmation from a member who has since been removed keeps counting toward `num_confirmations`, allowing a request to execute with fewer truly-authorized live confirmations than the configured threshold.

### Finding Description
`confirm()` accepts a confirmation from any `current_member()` and inserts `member.to_string()` into the `confirmations: LookupMap<RequestId, HashSet<String>>` set for that request, then executes once `confirmations.len() as u32 + 1 >= self.num_confirmations`: [1](#0-0) 

When a `DeleteMember` action executes, `delete_member` removes the member from `self.members` and cleans up only the requests that the removed member *originated* (`r.member == member`); it does not touch `confirmations` entries recorded by that member against requests created by *other* members: [2](#0-1) 

`assert_valid_request` (called from `confirm`) only checks that the request and its confirmation set still exist — it never revalidates that every account/key already present in `confirmations` is still a current member: [3](#0-2) 

This is the same accounting-drift pattern as the referenced GTL bug: a piece of local bookkeeping (`_subaccounts` in GTL / `confirmations` here) is populated by one code path (order fill / `confirm`) and is expected to reflect a live, authoritative set (GTL's collateralized subaccounts / the multisig's current membership), but a *different* state-changing path (post-only order placement / `delete_member`) fails to keep that bookkeeping consistent with the authoritative state. The mismatch is later read by a downstream accounting function (`totalAssets` / the `>= num_confirmations` check) that produces an inflated/incorrect result — inflated shares in GTL, an under-threshold execution here.

Concretely, with members `{A, B, C}` and `num_confirmations = 2`:
- `B` creates request `R` via `add_request` (no confirmation yet). Confirmations for `R` = `{}`. [4](#0-3) 
- `A` calls `confirm(R)`. Confirmations for `R` = `{A}` (1 < 2, not executed).
- Members legitimately vote to remove `A` (e.g. `A` resigns/is offboarded) via a `DeleteMember` request that is confirmed and executed by the remaining members. `self.members` no longer contains `A`, but `R`'s confirmations set still contains the string for `A` because `delete_member` never inspects `R` (it was created by `B`, not by `A`).
- `C`, a single remaining live member, now calls `confirm(R)`. `confirmations.len() (1) + 1 >= 2` → `R` executes, even though only one currently-authorized member (`C`) actually approved it in the post-removal state; the second "confirmation" comes from a member who is no longer part of the multisig.

### Impact Explanation
This breaks the multisig's core custody/authorization binding: `live confirmations from current members >= num_confirmations` before executing an action on the controlled account (transfers, `AddKey`, `DeployContract`, `FunctionCall`, etc.). A request (e.g. a `Transfer` of NEAR/wNEAR held by the multisig account) can be pushed through by fewer currently-authorized members than the configured K-of-N threshold, because a stale confirmation from a removed member is still counted. This matches the Critical impact category "a multisig request executed below threshold," and can directly result in unauthorized movement of funds held by the multisig account.

### Likelihood Explanation
The trigger sequence relies only on standard, documented contract flows (a member confirming a request, and a subsequent, unrelated `DeleteMember` request executing) — no owner/foundation privilege beyond normal multisig membership is required, and no redeploy or external actor is needed. Any multisig that ever removes a member who had previously confirmed a still-pending, not-yet-executed request is exposed; membership churn (onboarding/offboarding signers) is an expected, routine operation for these contracts, making the precondition realistic rather than contrived.

### Recommendation
When executing `DeleteMember`, iterate over all requests in `self.requests` and, for each request's `confirmations` set, remove the entry corresponding to the deleted member's `to_string()` representation (not just requests the removed member created). Additionally, `confirm()`/`assert_valid_request()` should re-validate that every account/key already stored in a request's `confirmations` set is still a current member before counting it toward `num_confirmations`, so that removed members can never contribute a phantom confirmation.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2` (`MultiSigContract::new`) [5](#0-4) .
2. `B` calls `add_request(R)` where `R` is e.g. a `Transfer` action [4](#0-3) .
3. `A` calls `confirm(R)`; `confirmations[R] = {A}` [1](#0-0) .
4. Remaining members execute a `DeleteMember{A}` request (via its own separate confirm flow reaching threshold with e.g. `B` and `C`); `A` is removed from `self.members`, but `delete_member` does not touch `confirmations[R]` [2](#0-1) .
5. `C` calls `confirm(R)`. `confirmations[R].len() (1) + 1 >= num_confirmations (2)` is true, so `R` executes and its funds/action are dispatched, even though only `C` is a genuinely current, live approver in addition to the stale `A` entry.

    /// Add request for multisig.
    pub fn add_request(&mut self, request: MultiSigRequest) -> RequestId {
        let current_member = self.current_member().unwrap_or_else(|| {
            env::panic_str(
                "Predecessor must be a member or transaction signed with key of given account",
            )
        });
        // track how many requests this key has made
        let num_requests = self
            .num_requests_pk
            .get(&current_member.to_string())
            .unwrap_or(0)
            + 1;
        assert(
            num_requests <= self.active_requests_limit,
            "Account has too many active requests. Confirm or delete some.",
        );
        self.num_requests_pk
            .insert(&current_member.to_string(), &num_requests);
        // add the request
        let request_added = MultiSigRequestWithSigner {
            member: current_member,
            added_timestamp: env::block_timestamp(),
            request,
        };
        self.requests.insert(&self.request_nonce, &request_added);
        let confirmations = HashSet::new();
        self.confirmations
            .insert(&self.request_nonce, &confirmations);
        self.request_nonce += 1;
        self.request_nonce - 1
    }

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
