### Title
EI-authenticated callers pass the `isUser` check via a synthetic User context set by `AuthenticateExternalInitiator`, letting external initiators run arbitrary jobs by integer ID - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates the int32-ID run path with `_, isUser := auth.GetAuthenticatedUser(c)`, intending "only users are allowed to run jobs using int IDs - EIs not allowed". However, `auth.AuthenticateExternalInitiator` explicitly injects a synthetic `*clsessions.User{Role: UserRoleRun}` into the same context key that `GetAuthenticatedUser` reads, so `isUser` evaluates `true` for EI-authenticated requests as well. The uuid.Parse short-circuit is irrelevant to this bypass since it only blocks UUID-format IDs (the removed webhook job type identifier) for both users and EIs equally — the real gap is downstream in the `isUser` branch.

### Finding Description
In `core/web/pipeline_runs_controller.go` `Create`:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
``` [1](#0-0) 

`auth.GetAuthenticatedUser` simply reads the `SessionUserKey` value from the gin context: [2](#0-1) 

But `AuthenticateExternalInitiator`, the middleware used to authenticate external-initiator credentials, sets that exact same key to a fabricated `User` object so downstream `RequiresRunRole`/`RequiresEditRole` wrappers work uniformly for EIs:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [3](#0-2) 

Because of this, `GetAuthenticatedUser(c)` returns `ok=true` for an EI-authenticated request exactly the same as for a real logged-in/token user — the code has no way to distinguish "real user" from "EI masquerading as a run-role user" at this call site. The comment's stated intent ("EIs not allowed") is not actually enforced: any EI credential holder whose route is wired through `auth.Authenticate(..., auth.AuthenticateExternalInitiator)` can supply any integer job ID and reach `prc.App.RunJobV2(ctx, jobID, nil)`, then receive the full `pipeline.Run` resource back via `respondWithPipelineRun`/`presenters.NewPipelineRunResource`, which can include task output/results.

This is broader than the question's specific "legacy webhook UUID" framing: it's not limited to jobs that used to be webhook-typed — because `RunJobV2` performs no check that ties the caller's EI identity to the target job, an EI can trigger **any** job by sequential/guessable int32 ID, not just ones it is authorized for.

The `uuid.Parse(idStr)` short-circuit does correctly reject the *UUID-format* legacy identifier for everyone (users and EIs alike) with `job.ErrJobTypeRemoved`, so that specific vector is closed. The actual exploitable gap is the `isUser` check being trivially satisfiable by EI credentials due to the shared session key.

### Impact Explanation
Unauthorized job run: an external-initiator credential — intended only to be scoped to triggering the specific webhook/job it's bound to — can instead run **any** job in the node by supplying its integer database ID, and read back that job's latest run data/results via the response. This is an authorization-bypass / unauthorized-action-on-another-user's-job class impact matching Chainlink's bounty categories for "unauthorized job run" and potential secret/result disclosure.

### Likelihood Explanation
Requires only a valid (even narrowly-scoped) external-initiator access key/secret pair — no admin/user credentials needed. Job IDs are small sequential integers in the DB, easily enumerable/guessable. The bypass is deterministic and repeatable (not a race or timing issue) — every request from a valid EI credential with an integer `:ID` param takes this same code path.

### Recommendation
Distinguish EI-originated sessions from genuine user sessions at the `isUser` check, e.g. by checking `auth.GetAuthenticatedExternalInitiator(c)` first and rejecting if present, rather than relying solely on `GetAuthenticatedUser`, since `AuthenticateExternalInitiator` populates the same `SessionUserKey`. Example: reject if `_, isEI := auth.GetAuthenticatedExternalInitiator(c); isEI` before allowing the int32-ID `RunJobV2` path.

### Proof of Concept
1. Create any job (e.g., a cron or direct-request job) via the admin API; note its integer `ID`.
2. Register/authenticate an External Initiator (obtain its access key/secret via `bridges.ExternalInitiator` creation flow).
3. Send `POST /v2/jobs/:ID/runs` with `:ID` set to the job's integer DB id, using headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` (EI auth headers) instead of user session/API token.
4. Assert (current buggy behavior): response is `200`/`201` with a `pipelineRun` JSON body (i.e., `RunJobV2` executed) — this should be `422`/`401` instead.
5. Handler-level Go test: build a gin test context with `auth.AuthenticateExternalInitiator` invoked (or manually `c.Set(auth.SessionExternalInitiatorKey, ei)` + `c.Set(auth.SessionUserKey, &clsessions.User{Role: UserRoleRun})` as that middleware does), set `c.Params` `ID` to a numeric job ID, call `PipelineRunsController.Create`, and assert `mockRunJobV2` was **not** invoked and the response status is `422 Unprocessable Entity` / `401 Unauthorized`. Currently `RunJobV2` mock will be invoked, proving the bypass.
