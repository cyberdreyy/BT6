Confirmed: `common_close_account` requires the buffer's `authority_address` to sign and be present, then drains all lamports from the buffer account to any recipient account the closer names.### Title
Front-runnable `InitializeBuffer` lets an attacker seize authority over a victim's just-created buffer account and drain its rent-exempt lamports - (File: programs/bpf_loader/src/lib.rs)

### Summary
The `bpf_loader_upgradeable` `InitializeBuffer` instruction assigns the `authority_address` of a `Buffer` account from an arbitrary instruction-supplied account, with no signature requirement tying that account to the creator of the buffer. If the `CreateAccount` (which allocates and funds the buffer, owned by `bpf_loader_upgradeable`, in `Uninitialized` state) and the subsequent `InitializeBuffer` call are not submitted as a single atomic transaction, any unprivileged transaction sender who observes the pending/landed `CreateAccount` can race to submit their own `InitializeBuffer` instruction naming themselves as authority before the legitimate creator's instruction lands. This is structurally identical to the reported `EarnStrategyRegistry` bug: a "first owner"/authority is derived from arbitrary caller-supplied instruction data during a public, unauthenticated initialization step on an account that already exists, enabling front-running takeover.

### Finding Description
`InitializeBuffer` only checks that the target account's state is `Uninitialized`; it does not require any signer for either the buffer account or the authority account: [1](#0-0) 

Because this check requires no signature and no cryptographic link between "whoever created the account" and "whoever calls InitializeBuffer," an attacker who can see that a buffer account exists on-chain in the `Uninitialized` state (visible as soon as the victim's `CreateAccount` transaction lands, or is observed in-flight) can submit a competing `InitializeBuffer` transaction naming themselves as `authority_address`, provided theirs lands first.

Once the attacker controls `authority_address`, they can subsequently call `Close` on the buffer, which requires only that the recorded authority sign, and pays out all lamports held by the buffer (funded by the victim as rent-exemption) to an arbitrary recipient of the attacker's choosing: [2](#0-1) 

This mirrors the reported class exactly: an unauthenticated "first owner" assignment on a permissionless, always-public initialization entrypoint, exploitable by racing (front-running) the legitimate initializer's transaction, followed by using the seized authority to move out funds.

The standard SDK helper `create_buffer` avoids this by bundling `CreateAccount` and `InitializeBuffer` into one atomic transaction signed by both the payer and the buffer keypair: [3](#0-2) [4](#0-3) 

This atomic bundling is a convention, not an enforced protocol invariant — nothing in `process_loader_upgradeable_instruction` prevents `CreateAccount` and `InitializeBuffer` from being submitted as two separate transactions, which reopens the front-run window.

### Impact Explanation
If a victim (or any tooling/wallet/program) ever submits account creation and `InitializeBuffer` as separate transactions (e.g., due to transaction size limits when combined with other setup instructions, custom deployment tooling, or a delay between the two steps), an unprivileged attacker can:
1. Detect the victim's rent-exempt, `Uninitialized`, loader-owned buffer account.
2. Submit their own `InitializeBuffer` naming themselves as authority, racing ahead of the victim's own call.
3. Call `Close` (or `SetAuthority` + later drain via program upgrade abuse) to redirect the buffer's rent-exempt lamports to themselves, and/or block the victim from ever deploying their intended program through that buffer.

This is a concrete unsigned/unauthorized fund movement (lamports paid by the victim to fund the buffer are stolen by the attacker) achievable with a single attacker-submitted transaction, requiring no leader privilege, no network-layer manipulation, and no special access — only observation of a public on-chain account state and correct transaction timing.

### Likelihood Explanation
Likelihood is moderate-to-low in practice because the canonical SDK path (`create_buffer`) already avoids the race by bundling both instructions atomically in one transaction. The vulnerability is only reachable when a caller (custom tooling, a program invoking `InitializeBuffer` via CPI in a separate instruction/transaction, or any deployment flow that splits `CreateAccount` and `InitializeBuffer`) deviates from that atomic pattern. However, since nothing in the instruction handler enforces atomicity or ties the authority to the account creator, any workflow (present or future) that does this split is silently exploitable, and the impact (direct lamport theft, denial of legitimate program deployment) is severe when it occurs.

### Recommendation
Apply the same remediation strategy adopted for the reported bug: remove the ability for an arbitrary caller-supplied account to become the authority of an account it did not create. Options:
- Require the account being initialized (or its creator) to co-sign `InitializeBuffer`, tying authority assignment to a verifiable relationship instead of unauthenticated instruction data.
- Enforce, at the instruction-processing level, that `InitializeBuffer` can only be effectively invoked as part of the same transaction/CPI chain as the `CreateAccount` for that buffer (e.g., by checking `is_instruction_account_signer` for the authority or requiring a signer on the buffer account itself equal to the account's own key derived deterministically, rather than accepting any pubkey unconditionally).
- Update documentation and audits of any code paths that call `InitializeBuffer` outside of the atomic `create_buffer` helper to flag this front-running window explicitly.

### Proof of Concept
1. Victim (Alice) submits transaction T1: `system_instruction::create_account` allocating and funding `buffer_pubkey` (rent-exempt lamports), owned by `bpf_loader_upgradeable`, in a transaction that does NOT also include `InitializeBuffer` (e.g., split due to transaction size or custom tooling).
2. T1 lands; `buffer_pubkey` account is now `Uninitialized`, owned by `bpf_loader_upgradeable`, funded with rent-exempt lamports, and its address is now public.
3. Attacker (Bob) observes the account and submits transaction T2 before Alice's intended `InitializeBuffer` transaction: `UpgradeableLoaderInstruction::InitializeBuffer` with account 0 = `buffer_pubkey`, account 1 = `bob_pubkey` (no signature required on either), per [1](#0-0) .
4. T2 lands first; `buffer_pubkey`'s state becomes `Buffer { authority_address: Some(bob_pubkey) }`.
5. Alice's originally-intended `InitializeBuffer` transaction now fails with `AccountAlreadyInitialized` (per the check at line 162-165).
6. Bob submits `UpgradeableLoaderInstruction::Close` signing as `bob_pubkey` (the recorded authority), directing the recipient to his own wallet, per [5](#0-4) , draining all of Alice's rent-exempt lamports from `buffer_pubkey` to himself.
