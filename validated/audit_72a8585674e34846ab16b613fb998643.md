### Title
APR0 withdraw requests permanently poison `stopEpoch` if the APR is later set non-zero, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` classifies a withdraw request at request time based on the *current* value of `unscaledApr`: when `unscaledApr == 0` the principal is recorded in the `apr0Users`/`apr0TotalPrincipal` bucket instead of `withdrawsRequestsByEpoch`. However, `prepareStopEpochWithApr0` re-validates that same *type* at `stopEpoch` time and reverts `NotAllowed` whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0`. The request's accounting type was fixed at request time, but the settle path re-reads a mutable global to decide whether that type is still legal — the same "type changed between read and free" shape as CVE-2017-17670. An unprivileged tranche holder can create an `apr0TotalPrincipal > 0` state that cannot be cancelled, so the next honest APR change makes every subsequent `stopEpoch` revert.

### Finding Description
In `requestWithdraw`, when `unscaledApr == 0` the request is routed to `_requestWithdrawApr0`, which increments the global `apr0TotalPrincipal` and stores per-user `Apr0UserData` [1](#0-0) . There is no way for the user to remove this principal.

At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which reverts if the APR0 bucket is non-empty while `unscaledApr` has since become non-zero:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
``` [2](#0-1) 

`setApr`/`setAprsWithBuffer` are routine manager/CDO operations that legitimately change `unscaledApr` between epochs [3](#0-2) . Once `apr0TotalPrincipal != 0` and `unscaledApr != 0`, `prepareStopEpochWithApr0` reverts unconditionally: the epoch can never be stopped, `epochNumber` never advances, `collectWithdrawFunds` is never called, and all pending withdraws (and all tranche redemptions routed through epoch mechanics) are frozen. The only escape is the manager restoring `unscaledApr` to 0, at which point the APR0 bucket accrues interest at a rate the manager never intended, or settles with zero interest.

There is no alternative clearing path: `_clearWithdrawClaimForEpoch` only runs during default/loss claims, and `apr0TotalPrincipal` is otherwise only reset inside the reverting function itself [4](#0-3) .

### Impact Explanation
Any KYC-passing lender or tranche-token holder can permanently wedge the epoch state machine at the cost of a single `requestWithdraw` while `unscaledApr == 0`. The moment the honest manager (or the CDO via `setAprsWithBuffer` during `startEpoch`) sets a non-zero APR — a routine, honest action — every `stopEpoch` reverts. All user funds are frozen: pending withdraw receipts cannot be claimed (`epochNumber` never passes `lastWithdrawRequest`), active depositors cannot exit, and borrower repayments cannot be booked. The freeze persists until the manager deliberately returns `unscaledApr` to 0, forcing either an unintended APR0 interest distribution or a zero-interest settlement, and the attacker can re-arm the griefing in every future APR0 window. This is temporary freezing of all vault funds caused entirely by unprivileged attacker sequencing.

### Likelihood Explanation
- Attacker requirements: none beyond holding tranche tokens and calling `requestWithdraw` during an APR0 epoch — explicitly an in-scope unprivileged actor.
- Trigger: any honest APR change while an APR0 receipt is open. APRs are reconfigured per epoch via `setAprsWithBuffer`, and AYS mode actively manages `trancheAPRSplitRatio`/APR, so a 0 → non-zero transition is a normal operational event.
- No guard prevents it: the `unscaledApr == 0` check at request time is read-time classification; nothing blocks the subsequent type mismatch at settle time, and `maxApr`/`NotAllowed` checks in `setApr` do not consider `apr0TotalPrincipal`.

### Recommendation
Do not re-validate the request-time type at settle time. Options:
1. Settle the open APR0 bucket at the last recorded APR0 terms before allowing `setApr`/`setAprsWithBuffer` to move `unscaledApr` off 0 (i.e., snapshot `apr0RateByEpoch` and clear `apr0TotalPrincipal` inside `setApr`).
2. Or, in `prepareStopEpochWithApr0`, treat a non-zero `unscaledApr` with pending `apr0TotalPrincipal` as "settle APR0 principal with zero rate" and close the bucket instead of reverting, so `stopEpoch` remains live.

Either way, `stopEpoch` must never revert due to a mismatch between a mutable global APR and an immutable, already-recorded request type.

### Proof of Concept
```solidity
// Fork test against the epoch-variant CDO + IdleCreditVault strategy.
function testApr0RequestPoissonsStopEpoch() external {
    // 1. Manager sets APR = 0 (legit APR0 epoch).
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    // 2. Attacker (normal AA holder) deposits and requests a withdraw.
    //    This routes through _requestWithdrawApr0, setting apr0TotalPrincipal > 0.
    idleCDO.depositAA(10_000 * ONE_SCALE);
    cdoEpoch.requestWithdraw(attackerTrancheBal / 2, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // 3. Honest manager later restores a normal APR for the next epoch.
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(10e18, 0); // unscaledApr != 0

    // 4. Epoch end: every stopEpoch now reverts inside prepareStopEpochWithApr0.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, type(uint256).max);
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // 5. Funds are frozen: epochNumber never advances, no claim can pass the
    //    `epochNumber <= lastWithdrawRequest` gate, and there is no user-level
    //    way to clear apr0TotalPrincipal.
}
```

Caveat: I was unable to read `IdleCDOEpochVariant.stopEpoch` to confirm the exact ordering of the `prepareStopEpochWithApr0` call and the `epochNumber` increment (index excerpt limits), but `prepareStopEpochWithApr0` is `_onlyIdleCDO` and is only invoked from the epoch-stop path, so the revert propagates to `stopEpoch` regardless of ordering.
