### Title
`depositDuringEpoch` mints shares and forwards the full nominal `_amount` to the borrower without measuring the actual tokens received — fee-on-transfer underlyings let a depositor extract value from existing lenders ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
The external report describes accounting on the nominal transfer amount instead of `balanceAfter - balanceBefore` when a fee-on-transfer token is used. The credit-vault analog is `IdleCDOEpochVariant.depositDuringEpoch`: it pulls `_amount` from the depositor, mints tranche shares priced on `_amount`, books `expectedEpochInterest` on `_amount`, mints strategy tokens for `_amount`, and then pushes the full `_amount` to the borrower — all without ever checking how much the vault actually received. With a fee-on-transfer underlying, the vault receives `_amount - fee` but pays out `_amount`, so the fee is silently covered by other depositors' idle liquidity and the attacker is minted shares for tokens they never delivered.

### Finding Description
In `contracts/IdleCDOEpochVariant.sol`, `depositDuringEpoch` performs the following after the allowance/epoch gating:

1. `_transferUnderlyingsFrom(msg.sender, address(this), _amount)` — pulls tokens, but no `balanceBefore`/`balanceAfter` delta is taken (line 685).
2. Shares are minted on the nominal amount: `_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal` (line 724), and `_mintShares(_tranche, msg.sender, _minted, _amount)` (line 725).
3. `expectedEpochInterest += interest` where `interest = _calcInterest(_amount) * ...` is computed on the nominal amount (lines 693, 728).
4. `IdleCreditVault(strategy).mintStrategyTokens(_amount)` and `_transferUnderlyings(_borrower(), _amount)` — the full nominal amount is sent to the borrower (lines 730–732).

Contrast with the guarded path: `IdleCDOCreditVault._deposit` correctly measures the received amount via `_contractTokenBalance(_token) - _preBal` before minting (`contracts/IdleCDOCreditVault.sol:203-206`). The mid-epoch path reimplements the transfer/mint logic and drops that protection.

Broken invariants: fair mint (shares minted for un-delivered tokens) and solvency (the vault forwards `_amount` to the borrower while only holding `_amount - fee` of the new deposit; the difference is taken from the idle balance backing existing tranche holders' NAV).

### Impact Explanation
A KYC-passed lender calls `depositDuringEpoch` with a fee-on-transfer underlying while an epoch is running. For a 1% fee and a 10,000-token deposit, the vault receives 9,900 but (a) mints the attacker shares for 10,000 plus prorated interest, (b) inflates `expectedEpochInterest` based on 10,000, and (c) sends 10,000 to the borrower. The 100-token shortfall is paid out of the vault's existing idle liquidity, i.e. other AA/BB depositors' principal. The attacker can later withdraw or claim against shares worth the full nominal amount plus interest, realizing a direct gain equal to the transfer fee on every deposit, repeatable each deposit. If the vault's idle balance is insufficient to cover `_amount`, the transaction reverts — but whenever it succeeds, existing depositors absorb the loss. Higher token transfer fees scale the theft linearly.

### Likelihood Explanation
Likelihood is conditional: it requires the vault's `token` to be a fee-on-transfer (or rebasing-down-on-transfer) asset. Deployment configuration picks the underlying; nothing in `depositDuringEpoch` or the KYC/epoch gates prevents such a token, and the attacker needs only `isWalletAllowed` plus an active epoch with `isDepositDuringEpochDisabled == false`, `isAYSActive == false`, non-programmable borrower, and nonzero tranche supply — all normal operating conditions. No privileged role is involved; the borrower/manager calls are honest and sequenced around the attacker's deposit.

### Recommendation
Measure the received amount and use it consistently:

```solidity
uint256 preBal = _contractTokenBalance(token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
uint256 received = _contractTokenBalance(token) - preBal;
```

Then compute `interest`, `trancheInterest`, `_minted`, `expectedEpochInterest`, `mintStrategyTokens`, and the borrower transfer on `received` instead of `_amount`. The same fix should be applied anywhere else the nominal amount is assumed after a `transferFrom` (e.g., `IIdleCDOStrategy(strategy).deposit(_amount)` in `_deposit`, which pulls the nominal amount rather than the measured delta).

### Proof of Concept
Foundry fork PoC sketch (reproducible against a running epoch):

```solidity
// MockFeeToken: burns 1% on every transfer/transferFrom
function testFeeOnTransferDepositDuringEpoch() external {
    // setup: vault deployed with MockFeeToken as `token`, AA tranche seeded
    deal(feeToken, alice, 10_000e18); // alice: KYC-passed lender
    // owner/manager: normal epoch start (honest)
    vm.prank(manager); cdoEpoch.startEpoch();
    vm.warp(cdoEpoch.epochEndDate() - cdoEpoch.epochDuration() / 2);
    vm.prank(owner); cdoEpoch.setIsDepositDuringEpochDisabled(false);

    uint256 vaultBalBefore = feeToken.balanceOf(address(cdoEpoch));
    uint256 sharesBefore = AAtranche.totalSupply();

    vm.startPrank(alice);
    feeToken.approve(address(cdoEpoch), 10_000e18);
    uint256 minted = cdoEpoch.depositDuringEpoch(10_000e18, address(AAtranche));
    vm.stopPrank();

    // vault gained only 9,900 but shares were minted on 10,000 (+ interest)
    assertEq(feeToken.balanceOf(address(cdoEpoch)) - vaultBalBefore, 9_900e18);
    // borrower received the full 10,000 - funded from prior depositors' liquidity
    // alice's tranche tokens redeem for >= 10,000 nominal -> profit = fee amount
}
```

Note on scope/uncertainty: the standard `_deposit` path already defends itself via the balance-delta mint (though it then calls `strategy.deposit(_amount)` with the nominal amount, which at minimum breaks fee-on-transfer deposits and, where the CDO holds other users' idle balance, misroutes the fee). The concrete exploitable path is `depositDuringEpoch` as detailed above.
