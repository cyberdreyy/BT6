### Title
Stale instant-withdraw receipt data corrupts default-recovery basis and reserve in `finalizeDefaultRecovery` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays out a funded instant-withdraw receipt but never clears the per-epoch accounting entries `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. If a borrower default is later finalized in the same epoch, `finalizeDefaultRecovery` reads that stale basis twice: once to inflate the claim denominator (`defaultPendingClaimBasis`) and once to fabricate "prefunded" reserve (`_defaultPrefundedInstantReserve`). This is the credit-vault analog of a buffer overflow: state written past its logical bounds corrupts adjacent accounting, producing a reserve that is larger than the underlying actually held. Recovery is overpaid to early claimants and later claimants' transfers revert — permanent freezing of the tail of the recovery reserve.

### Finding Description
The instant-withdraw receipt lifecycle:

1. `requestInstantWithdraw` mints receipt tokens and increments `instantWithdrawsRequests[user]`, `instantWithdrawsRequestsByEpoch[user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, `pendingInstantWithdraws` (lines 356-375).
2. `collectInstantWithdrawFunds` decreases `pendingInstantWithdraws` when the CDO funds the queue (lines 398-403).
3. `claimInstantWithdrawRequest` burns the receipt, zeroes `instantWithdrawsRequests[user]`, and pays out — but leaves `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` untouched (lines 380-393).

On default finalization:

- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (lines 644-649) — including basis whose receipt was already claimed and paid.
- `_defaultPrefundedInstantReserve` returns `instantBasis - pendingInstant` (lines 716-723) — counting the already-paid claim as underlying held by the strategy.
- `finalizeDefaultRecovery` adds that phantom amount into `reserveAmount` and computes `recoveryPrice = reserveAmount * 1e18 / totalBasis` (lines 685-692).

The strategy never received underlying for the stale basis: the paid claim already left via `_transferFundedClaim`. So `defaultRecoveryReserve` is credited with funds that do not exist.

Attack sequence (running epoch, fixed-APR mode with instant withdrawals enabled):
1. APR drops > `instantWithdrawAprDelta`. Attacker (KYC'd lender) calls `IdleCDOEpochVariant.requestWithdraw`, triggering `requestInstantWithdraw`.
2. Epoch is stopped; borrower funds instant withdrawals via `collectInstantWithdrawFunds`.
3. Attacker calls `claimInstantWithdrawRequest` and is paid in full. Stale `instantWithdrawClaimsByEpoch[N]` still includes attacker's amount.
4. New borrower/epoch N continues; another user (or attacker) opens a new instant request so `pendingInstantWithdraws > 0`; borrower defaults; manager finalizes recovery.
5. `finalizeDefaultRecovery` counts attacker's already-paid amount in both `totalBasis` and `prefundedReserve`, over-stating `defaultRecoveryReserve` by exactly the claimed amount.

### Impact Explanation
`defaultRecoveryReserve` exceeds actual underlying by the stale claim amount. `_transferDefaultRecovery` decrements the inflated reserve while transferring real tokens; early claimants (including the attacker, who can hold genuine defaulted receipts too) are paid at an inflated `recoveryPrice`, and the reserve hits the real balance early. The last claimants' `safeTransfer` calls revert — permanent freezing of the residual recovery funds, quantified by the stale claimed amount. One paid receipt is counted twice, violating "one receipt one payout" and solvency of the recovery reserve.

### Likelihood Explanation
Requires a borrower default in the same `epochNumber` in which an instant receipt was funded and claimed, plus `pendingInstantWithdraws != 0` at finalization. Instant withdrawals trigger only when APR drops materially between epochs, and defaults are rare events; however the sequence needs only honest manager/borrower actions around it, and the attacker merely uses the normal claim path. Any KYC'd lender qualifies. Guards do not help: `_ensureDefaultRecoveryInitialized` refuses to clear pending instant withdrawals (line 926), `_transferFundedClaim` cannot detect the inflation because at claim time `defaultRecoveryReserve == 0`, and nothing ever decrements `instantWithdrawClaimsByEpoch` on a funded claim.

### Recommendation
In `claimInstantWithdrawRequest` (and symmetrically in `_claimDefaultedInstantWithdrawRequest`), clear the per-epoch bookkeeping when a receipt is consumed: subtract the claimed amount from `instantWithdrawsRequestsByEpoch[user][epochNumber]`/`instantWithdrawClaimsByEpoch[epochNumber]` for the epoch in which the request was recorded (store the request epoch, e.g. `lastInstantWithdrawRequest[user]`, analogous to `lastWithdrawRequest`). Alternatively, make `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` derive instant basis from still-outstanding receipts rather than the lifetime epoch aggregate.

### Proof of Concept
Foundry fork sketch against `IdleCreditVault` + `IdleCDOEpochVariant` (fixed-APR, instant-withdraw enabled):

```solidity
// Epoch N running; APR dropped so instant withdraw path is active.
cdo.requestWithdraw(amount, aaTranche);          // -> requestInstantWithdraw, receipt minted
// manager stops epoch; borrower funds instant queue
// CDO calls collectInstantWithdrawFunds(amount)
creditVault.claimInstantWithdrawRequest(user);   // user paid; instantWithdrawClaimsByEpoch[N] stale

// same epoch N: another request keeps pendingInstantWithdraws > 0
cdo.requestWithdraw(amount2, bbTranche);
// borrower defaults; owner/manager finalizes
cdo.finalizeDefault(recovered, recoverySource);

// Assert corruption:
assertEq(creditVault.defaultRecoveryReserve(),
         underlying.balanceOf(address(creditVault)) + /*phantom*/ amount);
// last claimant's claimWithdrawRequest/claimInstantWithdrawRequest reverts
// on safeTransfer for the tail amount == attacker's stale claim.
```

The assertion `defaultRecoveryReserve > actualBalance - fundedClaims` demonstrates the phantom reserve; a second claimant's claim reverting demonstrates the permanent freeze.
