## Analysis

The CVE describes an unbounded-recursion stack overflow in a PDF parser's `XRef::fetch` function. The closest reachable analog in this codebase is the recursive RLP decoding of `TrieNode` in the fault-proof/MPT crate, which decodes attacker-influenced preimage bytes supplied during dispute-game execution.

### Title
Unbounded recursive `TrieNode::decode` on Extension nodes causes stack-overflow DoS in the fault-proof program - (File: `crates/proof/mpt/src/node.rs`)

### Summary
`TrieNode::decode` recursively calls itself when decoding an `Extension` node's inlined (non-blinded) child pointer, with no depth limit. `Extension` nodes are only blinded (hashed and looked up separately) when their encoded length is ≥ 32 bytes; smaller children are inlined directly into the same buffer and decoded via a direct recursive call.

### Finding Description
In the `Decodable` implementation for `TrieNode`, when a two-element list is decoded as a leaf/extension node, `try_decode_leaf_or_extension_payload` handles the `Extension` case by invoking `Self::decode(buf)` on the remaining buffer to decode the child pointer inline: [1](#0-0) 

Whether a child is inlined or blinded is controlled entirely by the encoded length of the child (`< 32 bytes` stays inline), which is decided by the node's producer, not enforced during decode: [2](#0-1) 

Because inline extension children only need to be a few bytes each (short RLP header + 1-byte-or-less path + pointer), an attacker can construct a single blob containing dozens/hundreds of nested `Extension` nodes, each pointing directly (not via hash) to the next, causing `TrieNode::decode` to recurse once per nesting level with no depth check anywhere in the call chain.

This decode routine is invoked directly on preimages fetched from the untrusted preimage oracle in both the L1 and L2 oracle-backed providers used by the fault-proof client program: [3](#0-2) [4](#0-3) 

The oracle only validates that the returned bytes' keccak256 hash matches the requested key — it performs no structural/depth validation before handing the bytes to `TrieNode::decode`: [5](#0-4) 

The `readme` for the crate itself documents this is "a recursive, in-memory implementation" of the MPT, and the walking of blinded nodes (`unblind`, `open`, `insert`, `delete`) is all similarly unbounded recursion on attacker-influenceable inputs, but the tightest analog to the CVE's *single-call, single-blob* stack overflow is the inline-Extension decode path, since it requires no additional oracle round-trips — one malicious preimage blob is sufficient. [6](#0-5) 

### Impact Explanation
During dispute-game resolution, a dispute-game participant (challenger or defender) who can produce a preimage whose keccak256 hash matches a hash referenced somewhere in the trie being traversed by the fault-proof program can trigger unbounded recursive decoding, exhausting the call stack and crashing the fault-proof program with a stack overflow. This is a Denial-of-Service against the program that computes the provable output root during dispute resolution — if the program cannot run to completion, the correct output root cannot be computed/verified, which can stall or corrupt dispute resolution (a node-halt / wrong-provable-output-root class impact per the validation criteria).

### Likelihood Explanation
Reaching this code path requires the attacker to have (or find) a value whose keccak256 preimage they control and that is treated as an "opened" trie-node commitment somewhere along a path the fault-proof program traverses (e.g., a node value stored under a hash they control, such as a value in a receipts/withdrawals/transactions MPT that is derivable from attacker-influenced L1 data). Because RLP allows near-minimal inline extension encodings, achieving deep recursion (hundreds of frames) requires only a small number of extra bytes per level, making a stack-exhausting payload compact and cheap to construct once a controllable hash is found.

### Recommendation
Add an explicit recursion/depth counter (or convert `TrieNode::decode`, `unblind`/`open`/`insert`/`delete`/`fetch_leaves` to iterative implementations with an explicit stack) and reject inputs whose nesting exceeds a sane bound (e.g., the maximum possible MPT depth for a 32-byte/64-nibble key, plus a small margin). This bound should be enforced both in the `Decodable` implementation for `TrieNode` and in `OrderedListWalker::fetch_leaves`.

### Proof of Concept
Construct a preimage blob consisting of N nested RLP-encoded `Extension` node payloads, each using a 1-nibble prefix and inlining (not hashing) its child, e.g. recursively:
```
node_0 = leaf(prefix, value)                     // small leaf, terminal
node_i = rlp([ encode_path_leaf(single_nibble, false), node_{i-1} ])   // inline extension, list len 2
```
Ensure each `node_i` remains below 32 bytes in encoded length so `encode`/`decode` keep it inline rather than blinding it. Feed the resulting `node_N` bytes (whose keccak256 the attacker must get referenced as a commitment the fault-proof program will open) to `TrieNode::decode`; with N in the low hundreds this exhausts the stack in `crates/proof/mpt/src/node.rs`'s `decode`/`try_decode_leaf_or_extension_payload` recursive pair.

    /// Get the data corresponding to the currently set key from the host. Return the data in a new
    /// heap allocated `Vec<u8>`
    async fn get(&self, key: PreimageKey) -> PreimageOracleResult<Vec<u8>> {
        trace!(target: "oracle_client", key = %key, "Requesting data from preimage oracle");

        let length = self.write_key(key).await?;

        if length == 0 {
            return Ok(Default::default());
        }

        let mut data_buffer = alloc::vec![0; length];

        trace!(target: "oracle_client", key = %key, "Reading data from preimage oracle");

        // Grab a read lock on the preimage channel to read the data.
        self.channel.read_exact(&mut data_buffer).await?;

        trace!(target: "oracle_client", key = %key, "Successfully read data from preimage oracle");

        Ok(data_buffer)
    }

# `base-proof-mpt`

A recursive, in-memory implementation of Ethereum's hexary Merkle Patricia Trie (MPT).

## Overview

Implements Ethereum's Merkle Patricia Trie with support for retrieval, insertion, deletion, and
root computation via RLP-encoded trie node encoding. Starting from a trie root hash, `TrieNode`
lazily fetches and caches node preimages via `TrieProvider`, enabling stateless block execution
without storing the full state. Designed as the trie backend for [`base-proof-executor`](../executor).
