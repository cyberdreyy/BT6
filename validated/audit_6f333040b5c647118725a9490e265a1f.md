### Title
Unbounded `activeRequests` map growth in Gateway Vault/ConfidentialRelay handlers enables memory/CPU exhaustion DoS - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
The Gateway's Vault handler (and the structurally identical ConfidentialRelay handler) tracks every in-flight user request in an in-memory map `activeRequests map[string]*activeRequest` that is only pruned by a periodic timer-based sweep, with no cap on the number of concurrent entries. This mirrors the Spartan `arrayPools`/`curatedPoolCount()` pattern: an actor who can cheaply and repeatedly trigger the "add" operation (here, submitting requests) can grow an unbounded collection that a fixed-interval background routine must fully scan, degrading service for everyone.

### Finding Description
`handler.activeRequests` is a plain Go map with no `maxCacheSize`-style limit [1](#0-0) , unlike the generic `RequestCache` used elsewhere in the gateway, which explicitly enforces `maxCacheSize` and rejects new requests once full [2](#0-1) .

Every JSON-RPC user request that reaches `HandleJSONRPCUserMessage` (other than the cached `MethodPublicKeyGet` fast path) creates a new `activeRequest` entry via `h.newActiveRequest(req, callback)` before dispatching to DON members [3](#0-2) . Entries are only removed by the periodic `removeExpiredRequests` sweep, which runs once every `defaultCleanUpPeriod` (5 seconds) and does a full linear scan of the map [4](#0-3) [5](#0-4) .

The identical pattern exists in `confidentialrelay/handler.go`: `activeRequests` has no size bound in its struct [6](#0-5) , and cleanup is likewise a periodic full-map scan every second [7](#0-6) [8](#0-7) .

Because request timeout (default 30s) is much longer than the cleanup interval (5s or 1s), any client able to submit distinct-ID requests faster than they expire and are swept can keep growing the map, exactly analogous to how the Spartan `arrayPools` array could be inflated faster than it was ever shrunk, eventually making the shared `curatedPoolCount()`/`addCuratedPool()` operation revert or become prohibitively expensive for everyone.

### Impact Explanation
Unbounded growth of `activeRequests` increases gateway node memory usage and the per-tick cost of the mandatory cleanup scan (`removeExpiredRequests`), which holds `h.mu.RLock()`/`RUnlock()` over the whole map [9](#0-8) . Sustained request flooding can degrade or stall processing of legitimate Vault/ConfidentialRelay requests from all users of that gateway node/DON, which is a shared-resource, unprivileged-actor availability issue — consistent with the "Block usage" class in the source report (a cheap, repeatable action inflating an unbounded structure that a critical shared routine must iterate).

### Likelihood Explanation
Likelihood depends on whether request creation is gated by strict per-identity rate limits proportional to concurrent in-flight requests. The code shows feature/method gates (`writeMethodsEnabled`, `signedResponseRequestIDEnabled`) and generic node/global rate limiters, but no cap tied to the size of `activeRequests` itself, and no evidence of a hard maximum on concurrently pending requests per sender was found in the reviewed code. I could not fully inspect `newActiveRequest`'s implementation body to confirm whether it performs any additional request-count check beyond ID length/emptiness validation, so this should be verified against the full function before treating this as fully confirmed.

### Recommendation
Add an explicit upper bound on `activeRequests` (mirroring `RequestCache.maxCacheSize` in `core/services/gateway/handlers/common/requestcache.go`), reject new requests once the bound is reached, and/or rate-limit new-request creation per sender/workflow-owner independently of the existing feature gates, in both `core/services/gateway/handlers/vault/handler.go` and `core/services/gateway/handlers/confidentialrelay/handler.go`.

### Proof of Concept
1. An authenticated (but otherwise unprivileged) client repeatedly sends distinct-ID Vault or ConfidentialRelay JSON-RPC requests (each triggers `newActiveRequest`) at a rate exceeding what `removeExpiredRequests` can prune within `requestTimeout`.
2. `activeRequests` grows without bound since no size cap exists in either handler.
3. Each cleanup tick's linear scan over `activeRequests` (`h.mu.RLock()` loop) grows correspondingly more expensive, and gateway memory usage rises, degrading responsiveness for all other users of that DON/gateway node.

// removeExpiredRequests removes expired requests from the pending requests map
func (h *handler) removeExpiredRequests(ctx context.Context) {
	h.mu.RLock()
	var expiredRequests []*activeRequest
	now := h.clock.Now()
	for _, userRequest := range h.activeRequests {
		if now.Sub(userRequest.createdAt) > h.requestTimeout {
			expiredRequests = append(expiredRequests, userRequest)
		}
	}
	h.mu.RUnlock()

	for _, er := range expiredRequests {
		responses := er.copiedResponses()
		var nodeResponses strings.Builder
		for nodeKey, nodeResponse := range responses {
			_, _ = fmt.Fprintf(&nodeResponses, "%s ---::: %v               ", nodeKey, nodeResponse)
		}
		nodeResponsesStr := nodeResponses.String()
		err := h.sendResponse(ctx, er, h.errorResponse(er.req, api.RequestTimeoutError, errors.New("request expired without getting quorum of responses from nodes. Available responses: "+nodeResponsesStr), []byte(nodeResponsesStr)))
		if err != nil {
			h.lggr.Errorw("error sending response to user", "requestID", er.req.ID, "error", err)
		}
	}
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
	if len(c.cache) >= int(c.maxCacheSize) {
		return errors.New("request cache is full")
	}

func (h *handler) removeExpiredRequests(ctx context.Context) {
	h.mu.RLock()
	var expiredRequests []*activeRequest
	now := h.clock.Now()
	for _, userRequest := range h.activeRequests {
		if now.Sub(userRequest.createdAt) > h.requestTimeout {
			expiredRequests = append(expiredRequests, userRequest)
		}
	}
	h.mu.RUnlock()

	for _, er := range expiredRequests {
		responses := er.copiedResponses()
		l := logger.With(h.lggr, "method", er.req.Method, "requestID", er.req.ID)
		l.Debugw("request expired, evaluating collected relay responses",
			"collected", len(responses),
			"nodes", len(h.donConfig.Members),
			"unanswered", len(h.donConfig.Members)-len(responses),
		)
		summary, err := h.bundler.Bundle(er.req, responses, l)
		if err != nil {
			l.Errorw("failed to build relay response bundle", "error", err)
			if sendErr := h.sendResponseAndClearRequest(ctx, er, h.constructErrorResponse(er.req, api.FatalError, err)); sendErr != nil {
				l.Errorw("error returning bundle failure on expiry", "error", sendErr)
			}
			continue
		}
		// Expiry makes further responses unavailable to this request. The common
		// readiness path forwards a viable partial bundle or returns a timeout.
		if err := h.forwardBundleOrTerminateIfReady(ctx, l, er, summary, 0, true); err != nil {
			l.Errorw("error forwarding bundle on expiry", "error", err)
		}
	}
}
