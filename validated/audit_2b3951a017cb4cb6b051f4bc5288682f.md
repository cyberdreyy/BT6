### Title
Allowlist authentication bypass in JWT-only Vault deployments due to hardcoded fallback on `req.Auth == ""` - ([File: core/capabilities/vault/authorizer.go])

### Summary
`authorizer.authorizeRequest` unconditionally routes any request with an empty `req.Auth` to `allowListBasedAuth`, with no configuration flag to disable this fallback. Because `NewGatewayHandler` always wires up `allowListBasedAuth` (`NewAllowListBasedAuth`) regardless of whether `auth0`/JWT is configured, an attacker holding only a stale/legacy allowlist grant can force allowlist-based authorization in an environment the operator intended to be JWT-only, simply by omitting `req.Auth`.

### Finding Description
`authorizeRequest` selects the auth mechanism purely based on whether `req.Auth` is empty: [1](#0-0) 
There is no accompanying mode/config check (e.g., "JWT-only enabled") that disables the allowlist branch — the comment even documents this as an intentional "backwards compatibility" fallback, but nothing prevents a client from perpetually choosing that fallback by never populating `Auth`.

Critically, `NewGatewayHandler` constructs `allowListBasedAuth` unconditionally whenever no explicit `authorizer` override is passed, independent of whether `auth0` (JWT) config is present: [2](#0-1) 
So even in a deployment where the operator supplies `auth0` config intending JWT-only auth, `allowListBasedAuth` is still built from `workflowRegistrySyncer` and wired into `authorizer`, remaining fully reachable via the `req.Auth == ""` branch. Any gateway message reaching `HandleGatewayMessage` → `requestProcessor.ProcessRequest` → `authorizer.AuthorizeRequest` → `authorizeRequest` will honor an attacker-supplied empty `Auth` field and fall through to the allowlist check, which only validates workflow-registry-syncer state (e.g., stale on-chain registrations) rather than JWT identity.

There is no operator-facing toggle to actually disable the allowlist authorizer path itself — the only "disabling" mechanism is not configuring `auth0`, but that has no effect on the allowlist branch, which is always active as long as `allowListBasedAuth` is non-nil (which it always is by default).

### Impact Explanation
This is a full authentication-method bypass for the Vault gateway handler: in an environment intended to be JWT-only, an attacker who only controls a legacy/stale allowlist grant (e.g., an old on-chain workflow registration not yet rotated out) can still authenticate and perform Vault operations (`secrets.create`, `secrets.update`, `secrets.delete`, `secrets.list`) as that allowlisted workflow owner by simply omitting `req.Auth`, entirely bypassing the JWT requirement the operator believes is enforced. This matches Chainlink's authentication-bypass impact class.

### Likelihood Explanation
Exploitation requires no special privilege beyond possessing (or forging, if the allowlist source itself is stale/misconfigured) a valid allowlist entry recognized by `AllowListBasedAuth`/`workflowRegistrySyncer` — no JWT token, no admin/host access. The trigger is trivial: send a gateway JSON-RPC request with `Auth` unset/empty. It's fully deterministic and repeatable for any Vault method routed through `authorizer.authorizeRequest`.

### Recommendation
Introduce an explicit "auth mode" configuration (e.g., `AllowListEnabled`/`JWTOnly` flag) surfaced from `NewGatewayHandler`/`NewAuthorizer`, and have `authorizeRequest` reject requests with empty `req.Auth` outright (rather than falling back to `allowListBasedAuth`) whenever JWT-only mode is configured. Only wire up `allowListBasedAuth` in `NewGatewayHandler` when allowlist mode is explicitly enabled by the operator.

### Proof of Concept
Go handler-level integration test in `core/capabilities/vault`:
1. Construct `authorizer` (or `GatewayHandler`) with `auth0` config set (JWT enabled) and a real `allowListBasedAuth` backed by a `workflowRegistrySyncer` containing a stale/legacy allowlisted workflow owner, simulating a "JWT-only intended" deployment.
2. Send a `jsonrpc.Request[json.RawMessage]` with `Auth: ""` and a method like `vaulttypes.MethodSecretsList` for the stale allowlisted owner.
3. Assert current behavior: `authorizer.AuthorizeRequest` succeeds via `allowListBasedAuth`, returning a valid `AuthResult` for that owner — proving JWT is bypassed.
4. Expected/fixed behavior: with a JWT-only mode flag set, the same request should be rejected with an authentication error instead of falling through to `authorizeAllowListBasedAuth`.

```go
func (a *authorizer) authorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	// Requests without req.Auth continue using the allowlist-based path for backwards compatibility.
	// Existing clients do not populate the auth field yet, so treating an empty value as JWT would break them.
	if req.Auth == "" {
		return a.authorizeAllowListBasedAuth(ctx, req)
	}
	return a.authorizeJWTBasedAuth(ctx, req)
}
```
