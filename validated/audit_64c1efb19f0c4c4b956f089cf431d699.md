### Title
Loss-adjusted withdraw receipts bypass their haircut because `lossRecoveryPriceByEpoch` is keyed by the strategy `epochNumber` at collection time while user claims look it up by `lastWithdrawRequest` request-epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The upstream bug is a NULL-pointer dereference: code dereferences a state object that was never populated. The closest analog in `IdleCreditVault` is a **missing/mis-keyed state dereference**: a partial-loss stop records the recovery price under `lossRecoveryPriceByEpoch[epochNumber]` (the epoch counter value *at collection time*), but `_claimLossAdjustedWithdrawRequest` and the `requestWithdraw` guard both dereference `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the epoch in which the user *requested*. When these two keys diverge, the loss record is effectively a NULL entry for that user: the haircut is silently skipped and the receipt is paid at par through `_claimFundedWithdrawRequest`.

### Finding Description
In `collectWithdrawFunds` (`contracts/strategies/idle/IdleCreditVault.sol:411-430`), when the borrower funds less than `pendingWithdraws`, the shortfall is socialized by writing:

```solidity
uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
if (lossRecoveryPrice == 0) revert NotAllowed();
pendingWithdraws = 0;
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
```

`epochNumber` is incremented inside `deposit()` (lines 607-610) when `isEpochRunning()` is still true — i.e. during the same `stopEpoch`/`stopEpochWithDuration` sequence in which `collectWithdrawFunds` runs. Foundry tests confirm the counter is already at `requestEpoch + 1` once the stop completes (`test/foundry/IdleCDOEpochQueue.t.sol:862-867`).

However, a user who requested during the buffer has `lastWithdrawRequest[_user] = N` and `withdrawsRequestsByEpoch[_user][N]` set at request time (lines 282-293). If the loss price is stored under `N+1`:

1. `_claimLossAdjustedWithdrawRequest` (lines 789-801) reads `lossRecoveryPriceByEpoch[N]`, gets `0` (the "NULL" entry) and returns without burning or paying anything.
2. `_claimFundedWithdrawRequest` (lines 319-350) then pays `withdrawsRequests[_user]` **at par**, burning the full receipt, even though the aggregate pending bucket was only funded at `lossRecoveryPrice`.
3. Symmetrically, the guard in `requestWithdraw` (lines 261-271) dereferences `lossRecoveryPriceByEpoch[lastWithdrawRequest]` — also `0` — so the user can even open *new* requests while their haircut receipt still sits unclaimed, which the code explicitly says must be impossible ("A loss-adjusted receipt must be claimed before opening a later request").

The same class of mis-keyed lookup affects the APR0 path: `apr0Users[_user].principalEpoch == _claimEpoch` comparisons in `_clearWithdrawClaimForEpoch` (lines 822-831) will never match the loss epoch for these users, so their APR0 principal is neither haircutted under the loss price nor blocked from re-requesting.

### Impact Explanation
Broken invariant: **loss waterfall / fair burn**. Pending receipts are meant to share a realized `stopEpochWithDuration` loss pro rata via `lossRecoveryPriceByEpoch`. Affected receipt holders instead redeem 1:1 from the funded pool. Because the strategy only holds `_amount < pendingBasis` underlying for that bucket, every par-paid wei is taken from other pending receipt holders' recovery share — the last claimers find the reserve depleted and receive nothing (or the claim underflows/reverts, freezing their payout). Loss is quantified as `claimBasis * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL` per escaping receipt — i.e. up to the entire shortfall if `lossRecoveryPrice` is small. An unprivileged lender triggers this with a single ordinary `requestWithdraw` during the buffer; no privileged cooperation is needed — only an epoch that ends with `collectWithdrawFunds(_amount < pendingBasis)`, which the honest borrower/manager path produces whenever a loss is realized.

### Likelihood Explanation
Medium-high *if* the keying diverges. The precondition — a user requesting in the buffer epoch preceding a lossy stop — is the normal usage pattern (the queue contract itself batches requests this way). The one caveat I could not fully verify within the search index: the exact ordering inside `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` between the `strategy.deposit()` call that bumps `epochNumber` and the `collectWithdrawFunds` call that stores the price. If `collectWithdrawFunds` executes *before* the incrementing deposit, keys align and the mechanism works as intended (several Foundry tests around loss-adjusted claims suggest at least some paths do align). If it executes after — consistent with `claimEpoch = epochNumber() + 1` in `IdleCDOEpochQueue.t.sol:862` — every buffer-epoch receipt escapes its haircut. This should be confirmed by tracing `stopEpoch` in `contracts/IdleCDOEpochVariant.sol`.

### Recommendation
Key the loss record by the same identifier used at request time. Either:
- Store the recovery price under the epoch the pending receipts belong to (e.g. pass the request epoch from the CDO, or record `epochNumber` before the increment), or
- Record a per-user/per-epoch loss pointer: when storing `lossRecoveryPriceByEpoch`, also track which request epochs are covered, and have `_claimLossAdjustedWithdrawRequest`/`requestWithdraw` consult a `receiptEpoch → lossEpoch` mapping instead of assuming `lastWithdrawRequest == lossEpoch`.

Add a regression test: buffer-epoch `requestWithdraw` → `stopEpochWithDuration` partial loss → `claimWithdrawRequest` must pay `amount * lossRecoveryPrice / RECOVERY_FULL`, and a second `requestWithdraw` before claiming must revert.

### Proof of Concept
```solidity
// Foundry fork PoC (contracts/strategies/idle/IdleCreditVault.sol)
// Setup: deposits, APR > 0, manager runs a normal epoch.

// 1. Buffer epoch N: attacker requests a normal withdraw.
uint256 reqEpoch = strategy.epochNumber();          // = N
cdoEpoch.requestWithdraw(attackerShares, AAtranche);
assertEq(strategy.lastWithdrawRequest(attacker), reqEpoch);
assertGt(strategy.withdrawsRequestsByEpoch(attacker, reqEpoch), 0);

// 2. Honest manager stops the epoch with a realized loss:
//    borrower funds only part of pendingWithdraws.
uint256 pending = strategy.pendingWithdraws();
uint256 funded  = pending / 2;                       // 50% recovery
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(lossAmount, funded);  // internally:
                                                     //   deposit() -> epochNumber = N+1
                                                     //   collectWithdrawFunds(funded)
uint256 lossEpoch = strategy.epochNumber();          // = N+1
assertGt(strategy.lossRecoveryPriceByEpoch(lossEpoch), 0);
// NULL-deref analog: the user's lookup key has NO record.
assertEq(strategy.lossRecoveryPriceByEpoch(reqEpoch), 0);

// 3. Attacker claims — the haircut branch sees price 0 and returns;
//    _claimFundedWithdrawRequest pays the FULL basis at par.
uint256 balPre = underlying.balanceOf(attacker);
cdoEpoch.claimWithdrawRequest();                     // via CDO -> claimWithdrawRequest(attacker)
uint256 paid = underlying.balanceOf(attacker) - balPre;
assertEq(paid, attackerRequestBasis);                // par payout, NOT basis * 50%

// 4. Invariant broken: remaining receipt holders of the same loss epoch
//    are under-collateralized by (basis - funded)/2 == the escaped haircut.
//    The last claimer reverts on underflow / receives dust.

// 5. Bonus: guard bypass — a new requestWithdraw no longer reverts even
//    though the loss receipt was never haircutted.
cdoEpoch.requestWithdraw(moreShares, AAtranche);     // succeeds, should revert
```
