### Title
Miner can indefinitely reset the inactivity clock with a rejected reorg-attempt proposal, wedging the never-timeout/fallback logic - (File: `stacks-signer/src/chainstate/mod.rs`, `stacks-signer/src/chainstate/v1.rs`)

### Summary
`SortitionState::is_timed_out` decides whether the current miner has gone inactive long enough that the signer set should give up on it and fall back to the prior tenure's miner. The clock it measures against, `last_activity_time`, is meant to reflect genuine miner progress. But `check_latest_block_in_tenure` explicitly bumps `last_activity_time` even when the proposal it just examined is *rejected* (it does not confirm enough blocks, or conflicts with a locally-accepted/pre-committed block). This lets the current, one-slot miner keep resetting its own inactivity timer by repeatedly submitting doomed reorg-attempt proposals, exactly as `Borrower.liquidate` in the Aloe report let a self-liquidation with an oversized "strain" value clear the `warn` timestamp without meaningfully changing the account.

### Finding Description
`is_timed_out` treats "no signature yet, and no activity for `block_proposal_timeout`" as the trigger to invalidate the current miner (`SortitionMinerStatus::InvalidatedBeforeFirstBlock`), which is the precondition for the signer's miner-view state machine to fall back to the prior tenure: [1](#0-0) 

`last_activity_time` for a tenure is not only updated by legitimate progress; it is also updated by `check_latest_block_in_tenure` whenever a proposal fails to confirm as many blocks as expected against a locally-accepted block, or conflicts with a fresh pre-commit — i.e., on a *rejected* proposal: [2](#0-1) [3](#0-2) 

This function is invoked from the tenure-change payload validation path (`validate_tenure_change_payload` → `check_tenure_change_confirms_parent` → `check_latest_block_in_tenure`), which runs on every incoming block proposal for a tenure-change block, before the "has this miner ever signed a block" gate is even considered: [4](#0-3) 

Because the update happens unconditionally on the *attempt* rather than being gated on the proposal actually advancing anything, a miner who has never produced a valid, signable block can keep the tenure alive indefinitely: submit a tenure-change (or ordinary) proposal that is guaranteed to fail the "confirms latest block" check, get rejected, but still refresh `last_activity_time`. Repeating this faster than `block_proposal_timeout` means `elapsed > block_proposal_timeout` in `is_timed_out` never becomes true, so `check_miner_inactivity`/`is_timed_out` never fires and the miner-view state machine never falls back (`FALL` branch in `docs/signer-flows.md` section 8) to the prior sortition: [5](#0-4) 

This is the direct analog of H-1: the "warning timer" (here, the inactivity clock that gates fallback to a healthier miner) is supposed to be cleared/reset only by genuine progress (a signed block, or here — the intended interpretation — real chain advancement), but is instead reset by a cheap, self-triggered, guaranteed-to-fail action that leaves the underlying bad state (a miner who has produced nothing signable) completely unchanged.

### Impact Explanation
This is a liveness wedge on the signer state machine's remedial fallback mechanism: a stalling or malicious current-slot miner can prevent the signer set from ever recognizing it as inactive and switching its miner view back to the prior (working) tenure, by repeatedly sending free, rejected reorg-attempt proposals. Per the stated impact taxonomy, this is High: "a signer wedged into never signing valid blocks... " — here, wedged into never falling back away from an unproductive miner, stalling chain progress for as long as the miner keeps sending sub-timeout-interval junk proposals. Unlike a majority-signer requirement, this needs only the single sortition-winning miner (plus normal proposal gossip already in scope).

### Likelihood Explanation
The mechanism requires no cooperation from other signers or the node beyond normal proposal processing, and no elevated privilege — only being the current tenure's sortition winner (a role attacker-controlled miners already occupy in the threat model). The attacker only needs to resend a proposal (which is cheap, no signature needed to submit, no gas-equivalent cost) more frequently than `block_proposal_timeout`, mirroring the "once every 2 minutes" cadence judged sufficient for High severity in the H-1 precedent. The code comments in `check_latest_block_in_tenure` show this behavior is deliberate ("the miner may just be slow, so count this invalid block proposal towards valid miner activity"), which means it is a real, reachable code path rather than a hypothetical edge case, though it was evidently accepted as an intentional trade-off by the implementers to tolerate slow-but-honest miners — the risk is that this same tolerance is fully exploitable by a miner acting in bad faith with no cost.

### Recommendation
Do not credit `last_activity_time` for proposals that fail validation/rejection checks (i.e., for the branches in `check_latest_block_in_tenure` that return `Ok(false)` because the proposal does not confirm enough blocks or conflicts with an already-accepted/pre-committed block). If "miner may be slow" tolerance is still desired, bound the number of consecutive rejected-proposal activity credits per tenure, or require some independent evidence of real progress (e.g., a rising burn-chain view or an actually-valid, pre-committable proposal) before refreshing the clock that gates the never-times-out/fallback decision.

### Proof of Concept
Conceptual PoC (network/tool access is unavailable to construct a live end-to-end run in this session, so this is a logical trace through the cited code):
1. Miner M wins the current sortition but never manages to build a block that will pass `confirms_latest_block_in_same_tenure`/`check_tenure_change_confirms_parent` (e.g., it is stuck on a stale or wrong parent view).
2. M sends a tenure-change block proposal for its own tenure. The signer runs `validate_tenure_change_payload` → `check_tenure_change_confirms_parent` → `check_latest_block_in_tenure`.
3. `check_latest_block_in_tenure` finds the proposal's `chain_length` does not exceed the already locally-accepted/pre-committed block in this tenure, so it returns `Ok(false)` (rejects the proposal) — but first calls `signer_db.update_last_activity_time(...)` because the last signed/pre-committed time is still within `reorg_attempts_activity_timeout`.
4. The signer sends a rejection for the proposal, but `last_activity_time` for M's tenure has been refreshed to "now".
5. M repeats step 2–4 at an interval shorter than `block_proposal_timeout`.
6. `SortitionState::is_timed_out` always computes `elapsed <= block_proposal_timeout` since `last_activity_time` keeps being bumped, so `check_miner_inactivity` never invalidates M, and the "fall back to prior tenure" path in the miner-view state machine (`docs/signer-flows.md` section 8, `FALL` branch) is never taken, even though M never produces a single block the signer set will actually sign.

    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
