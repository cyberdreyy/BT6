### Title
Front-runnable multisig account creation allows name squatting with attacker-chosen members - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` lets any unprivileged caller pick an arbitrary `name` and deploy a multisig at `<name>.<factory>` with a `members` list and `num_confirmations` fully controlled by the caller, with no check that the caller is entitled to that name. Because NEAR sub-account creation is first-come-first-served, an attacker can pre-register the name an intended, more-privileged party (e.g. `treasury.multisig-factory.near`, or a name that a DAO/exchange plans to use) before that party calls `create`, permanently squatting the address with attacker-controlled signers.

### Finding Description
The binding the system is supposed to guarantee is:
`members_deployed_at(<name>.<factory>) == members_intended_by_the_rightful_owner_of(<name>)`

`create` builds the account id purely from caller-supplied `name` and the factory's own account id, then unconditionally issues `create_account()` + `deploy_contract()` + `function_call("new", {members, num_confirmations})` using the caller-supplied `members`/`num_confirmations`: [1](#0-0) 

There is no `assert_owner`, no allow-list, no reservation mechanism, and no check that `predecessor_account_id` has any relationship to `name`. On NEAR, `Promise::new(account_id).create_account()` succeeds for any not-yet-existing sub-account and simply fails (with the whole promise batch failing) if the account already exists — so the deployment race is a pure "whoever calls first wins" situation with no additional privilege required by the attacker.

Exploit flow:
1. Attacker observes (e.g., via off-chain coordination, a UI, or expected naming convention) that party `V` intends to later call `create("treasury", V_members, V_confirmations)`.
2. Attacker deploys their own transfer/poll contract at some account they control.
3. Attacker calls `create("treasury", attacker_members, attacker_num_confirmations)` first, creating `treasury.multisig-factory.near` with signers and threshold entirely chosen by the attacker.
4. `V`'s later `create("treasury", ...)` call fails because the sub-account already exists.
5. Third parties who trust `treasury.multisig-factory.near` by name (depositing funds, granting roles, whitelisting it, or naming it as a transfer/poll target) are actually interacting with a multisig whose members and confirmation threshold were chosen entirely by the attacker, allowing the attacker to authorize withdrawal/transfer of any funds routed to that address.

None of the existing guards apply here: there is no `assert_owner`/`assert_called_by_foundation` equivalent in this factory, no `assert_self()` callback validates who created the account, and there is no uniqueness/reservation check prior to `create_account()`. The only "protection" is NEAR's account-creation race itself, which favors whoever transacts first — i.e., the attacker, not the intended owner.

### Impact Explanation
Funds or trust routed to `<name>.<factory>` under the assumption that its owner controls its members are instead controlled by the attacker's chosen signer set and confirmation threshold. Any multisig request against that account can be executed with the attacker's own confirmations, so any NEAR/wNEAR/asset later deposited into or authorized to move through that address can be drained by the attacker — this is NEAR leaving (or being authorizable to leave) an account by a party never entitled to it, and an account deployed with parameters its rightful creator never chose, matching the Critical impact category ("an account whitelisted or a lockup deployed with parameters its rightful creator never chose" / "a multisig request executed below `num_confirmations` live members" analog, here below the *intended* member set entirely). The attack is repeatable for every name any party might plan to use.

### Likelihood Explanation
The attack requires no special privilege: it is a normal `create` call, funded by whatever deposit/gas is required to deploy the multisig2 contract, well within reach of any account holder. The only requirement is that the attacker calls before the legitimate party for a given `name` — a pure race that is easy to win if the attacker monitors for or anticipates the target name (e.g., known/expected treasury or protocol account names), and costless to attempt for many candidate names in parallel.

### Recommendation
Require the caller to prove entitlement to `name` before allowing `create` to succeed, e.g., restrict `create` to be callable only by an account matching `name` itself (`predecessor_account_id() == name`), or require a reservation/allow-list step controlled by a trusted authority (mirroring the pattern used for `foundation_account_id`-gated whitelisting in the lockup/staking-pool factories) so that sub-account creation cannot be front-run by an unrelated party.

### Proof of Concept
```rust
// multisig-factory/tests/spec.rs (near-sdk-sim or near-workspaces)
#[test]
fn test_name_squat_multisig() {
    // setup factory, two signer accounts: attacker, victim
    // 1. attacker calls create("treasury", attacker_members, 1) and it succeeds,
    //    deploying treasury.<factory> with members == attacker_members
    let attacker_members = vec![MultisigMember::Account { account_id: "attacker".to_string() }];
    call_create(&factory, &attacker, "treasury", attacker_members.clone(), 1);

    // 2. victim later calls create("treasury", victim_members, N) - the account already
    //    exists, so create_account fails and the promise batch fails
    let victim_members = vec![MultisigMember::Account { account_id: "victim".to_string() }];
    let outcome = call_create(&factory, &victim, "treasury", victim_members.clone(), 2);
    assert!(!outcome.is_ok());

    // 3. Assert the equality is broken: deployed members == attacker_members, not victim_members
    let deployed_members: Vec<MultisigMember> = view(&"treasury.factory".to_string(), "get_members", "{}");
    assert_eq!(deployed_members, attacker_members);
    assert_ne!(deployed_members, victim_members);
}
```
This demonstrates the deployed multisig's member set diverges from what the intended owner (`victim`) chose, confirming the front-running/name-squatting vulnerability at `multisig-factory/src/lib.rs::create`.

    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }
