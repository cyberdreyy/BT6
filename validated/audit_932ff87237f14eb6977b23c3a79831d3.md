### Title
Unauthenticated write to global `pendingUnderlyings` with unbounded `underlyingsRequested` in `createWriteOffRequest` — (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
The GLPI Fields bug class is a missing access-control check on a write path: an authenticated-but-unauthorized user can write data into a container they have no rights to. The closest analog in this repo is `IdleCreditVaultWriteOffEscrow.createWriteOffRequest`, which lets **any** wallet write an arbitrary `underlyingsRequested` into the escrow's global `pendingUnderlyings` accumulator, gated only by depositing a nonzero amount of tranche tokens — with no KYC/whitelist check (unlike vault deposit paths) and no bound tying the requested underlyings to the tranche tokens escrowed.

### Finding Description
`createWriteOffRequest` (contracts/IdleCreditVaultWriteOffEscrow.sol:86-102) does only two checks: epoch running and `amount != 0`. It then takes `amount` tranche tokens and executes:

```solidity
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
pendingUnderlyings += underlyingsRequested;
``` [1](#0-0) 

The unprivileged attacker can call this repeatedly. `underlyingsRequested` is a free parameter with no upper bound and no relation to the value of escrowed tranche tokens, so `pendingUnderlyings` — a shared global used to size borrower write-off settlement (`fullfillWriteOffRequest` decrements it at lines 133-134, and `writeOffDeposit` in `IdleCDOEpochVariant` consumes the same accounting) — can be inflated to `type(uint256)`-scale values for the cost of dust tranche tokens, which are fully recoverable via `deleteWriteOffRequest` (lines 105-116, which also floors `pendingUnderlyings` at 0 rather than reverting). No `isWalletAllowed`/Keyring check restricts who may write to the escrow, in contrast to the guarded deposit surfaces of the credit vault.

### Impact Explanation
`pendingUnderlyings` is a global solvency/accounting invariant for the write-off path: the borrower (or any fulfiller) is expected to cover the aggregate requested underlyings, and per-request fulfillment subtracts `currentRequest.underlyings` from the same counter. An attacker who inflates it (a) makes honest `fullfillWriteOffRequest` calls on their own entries effectively unfulfillable at the stated price, and (b) pollutes the aggregate the borrower must satisfy when writing off escrowed tranches, skewing the write-off economics and the escrow's reserve expectations. Because requests can be stacked across many fresh EOAs (no KYC), the write is Sybil-scalable and costs only gas plus recoverable dust.

### Likelihood Explanation
Likelihood is moderate-to-high on preconditions (only requires an epoch in `isEpochRunning()` state and a nonzero tranche-token balance, obtainable on secondary markets without KYC since the escrow never checks `isWalletAllowed`). Direct profit is limited — the attacker's tranche tokens are escrowed — so the primary impact is integrity corruption of `pendingUnderlyings` and griefing of the write-off market rather than direct theft. Severity is tempered because the attacker can unwind via `deleteWriteOffRequest` and the decrement at line 134 floors at zero.

### Recommendation
- Apply the same wallet-allowance check used by the vault entry points (e.g., `isWalletAllowed` via `KeyringIdleWhitelist`) in `createWriteOffRequest`.
- Bound `underlyingsRequested` to a sane function of the escrowed tranche amount (e.g., cap at the current virtual-price value of `amount` tranche tokens) so `pendingUnderlyings` cannot diverge arbitrarily from escrowed collateral.
- Consider restricting `fullfillWriteOffRequest` bookkeeping so a fulfilled request can never reduce `pendingUnderlyings` below what that request contributed.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVaultWriteOffEscrow} from
    "../contracts/IdleCreditVaultWriteOffEscrow.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract WriteOffEscrowUnauthorizedWriteTest is Test {
    IdleCreditVaultWriteOffEscrow escrow;
    IdleCDOEpochVariant cdo;
    IERC20Detailed tranche;
    address attacker = address(0xBEEF); // non-KYC EOA

    function testInflatePendingUnderlyings() public {
        // Setup: fork mainnet, epoch is running, escrow initialized for AA tranche.
        vm.startPrank(attacker);
        uint256 dust = 1; // 1 wei of tranche tokens
        tranche.approve(address(escrow), type(uint256).max);

        uint256 before = escrow.pendingUnderlyings();
        // Each call writes an arbitrary huge underlyingsRequested for dust cost
        escrow.createWriteOffRequest(dust, 1_000_000_000e6); // 1e9 USDC claim
        escrow.createWriteOffRequest(dust, 1_000_000_000e6);
        vm.stopPrank();

        uint256 after_ = escrow.pendingUnderlyings();
        // Global accumulator inflated by 2e9 underlyings for 2 wei of tranche tokens
        assertEq(after_ - before, 2_000_000_000e6);
        // Attacker's tranche tokens fully recoverable -> grief is free
        vm.prank(attacker);
        escrow.deleteWriteOffRequest();
    }
}
```

Caveat: I was able to verify the unauthenticated, unbounded write in `createWriteOffRequest` and the decrement/floor logic in `fullfillWriteOffRequest`/`deleteWriteOffRequest`, but could not fully trace every consumer of `pendingUnderlyings` in `IdleCDOEpochVariant.writeOffDeposit` within the available context; the concrete downstream impact (freeze vs. accounting skew) depends on how strictly the borrower's `writeOffDeposit` path validates against `pendingUnderlyings`.

```text
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
  }
```
