### Title
Stale per-epoch instant-withdraw receipts are never released after claim, enabling double payout at default finalization - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestInstantWithdraw` records each receipt twice: once in the aggregate `instantWithdrawsRequests[_user]` and once per epoch in `instantWithdrawsRequestsByEpoch[_user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]` (`IdleCreditVault.sol:366-374`). The per-epoch entries exist so that `finalizeDefault`/`_claimDefaultedInstantWithdrawRequest` can distinguish "receipts pending in the defaulted epoch" from "old receipts already funded before default". However, `claimInstantWithdrawRequest` only zeroes the aggregate `instantWithdrawsRequests[_user]` (`IdleCreditVault.sol:391`) — the per-epoch bookkeeping is never deleted when a funded receipt is claimed. Like the kernel bug where a `debugfs_lookup()` result is never `dput()` back, a recorded reference to an already-paid receipt is leaked and remains visible to the default-recovery path.

### Finding Description
In the buffer phase of a running epoch a KYC-passing tranche holder calls `requestWithdraw(amount, tranche)` on the CDO with an instant amount, which calls `requestInstantWithdraw`. Once `getInstantWithdrawFunds` has collected the underlying and the delay has passed, the holder calls `claimInstantWithdrawRequest`, which burns their strategy-token receipt and pays out, but leaves `instantWithdrawsRequestsByEpoch[user][epoch]` non-zero. If a later epoch ends with a shortfall and the manager calls `finalizeDefault`, the finalization path reads the stale per-epoch entry and treats the already-paid receipt as still pending in the defaulted epoch. The user is then entitled to recovery proceeds on a receipt that was already honored at par, double-claiming underlying from the vault reserve / `DefaultDistributor`. Because every other honest user's recovery share is computed against the same inflated default-epoch pending basis, the leaked entry dilutes real claimants proportionally to the stale amount.

### Impact Explanation
Direct theft / dilution of the default-recovery pool: the attacker withdraws their funds once at par via `claimInstantWithdrawRequest` and a second time via the default-recovery claim keyed to the unreleased `instantWithdrawsRequestsByEpoch` entry. Loss is bounded by the attacker's receipt size but repeatable across epochs and accounts, and it directly reduces `recoveryRatio` payouts to all other defaulted-epoch receipt holders.

### Likelihood Explanation
Requires only an unprivileged KYC-passing lender. The sequence — request instant withdraw, wait for funding, claim, then have a later epoch default — is an ordinary usage pattern, not an edge case: the comment at `IdleCreditVault.sol:368-370` shows per-epoch data exists precisely to be consulted at finalization, and no code path between claim and finalize clears it. The same unreleased-state pattern affects `withdrawsRequestsByEpoch` in `requestWithdraw`/`_claimFundedWithdrawRequest` (only `withdrawsRequests[_user]` and `lastWithdrawRequest[_user]` are cleared at lines 344-345), though the guard at lines 263-271 partially mitigates the normal-flow variant by reverting when a stale loss-epoch is detected.

### Recommendation
In `claimInstantWithdrawRequest` (and symmetrically in `_claimFundedWithdrawRequest`/`_claimLossAdjustedWithdrawRequest`), delete `instantWithdrawsRequestsByEpoch[_user][lastWithdrawRequest-style epoch key]` and decrement `instantWithdrawClaimsByEpoch[epoch]` whenever the corresponding funded amount is claimed — i.e., release the per-epoch "dentry" when the receipt is released — or track a funded-vs-pending flag per epoch so finalization can ignore already-paid receipts.

### Proof of Concept
Foundry fork PoC outline: (1) lender deposits AA, epoch starts, lender calls `requestWithdraw` with instant amount in epoch N; (2) warp past `instantWithdrawDelay`, `getInstantWithdrawFunds`, lender `claimInstantWithdrawRequest` → paid at par; assert `instantWithdrawsRequestsByEpoch[lender][N] != 0` while `instantWithdrawsRequests[lender] == 0`; (3) epoch N+1 stops with a loss triggering `_handleBorrowerDefault`; manager calls `finalizeDefault`; (4) lender calls `claimInstantWithdrawRequest`/`DefaultDistributor.claim` again and receives recovery pro-rata on the stale entry — assert second payout > 0 despite receipt already burned. Note: this analysis is based on the indexed code available; the body of `_claimDefaultedInstantWithdrawRequest` could not be read directly, so the exact payout path through it should be confirmed in a live session, but the unreleased per-epoch state is verifiable at lines 366-392.
