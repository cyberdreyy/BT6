### Title
Job object explicitly permits `CREATE_BREAKAWAY_FROM_JOB`, allowing a CI job script to spawn processes that survive job cancellation/kill - ([File: helpers/process/job_windows.go])

### Summary
`CreateJobObject` in `helpers/process/job_windows.go` sets `windows.JOB_OBJECT_LIMIT_BREAKAWAY_OK` on every job object used to sandbox a build process, with a comment explicitly acknowledging this "allow[s] subprocesses to explicitly avoid termination using `CREATE_BREAKAWAY_FROM_JOB`". Because Windows job objects only terminate member processes when the handle is closed (`KILL_ON_JOB_CLOSE`), any process created by the job's process tree with `CREATE_BREAKAWAY_FROM_JOB` is removed from job membership and is not affected by `closeJobObject`/`ForceKill`.

### Finding Description
`CreateJobObject` (`helpers/process/job_windows.go:86-108`) builds a `JOBOBJECT_EXTENDED_LIMIT_INFORMATION` with: [1](#0-0) 

`JOB_OBJECT_LIMIT_BREAKAWAY_OK` is a well-documented Windows flag that permits any process inside the job to call `CreateProcess` with the `CREATE_BREAKAWAY_FROM_JOB` creation flag; the resulting child process is not added to the job at all. Runner cancellation/timeout relies on `windowsKiller.ForceKill` calling `taskkill /F /T /PID <pid>` and then `cmd.closeJobObject()`, which closes the job handle to trigger `KILL_ON_JOB_CLOSE`: [2](#0-1) [3](#0-2) 

Because a breakaway process is no longer a job member, `KILL_ON_JOB_CLOSE` does not terminate it. `taskkill /T` walks the live parent-child PID tree at the moment it's invoked; a script can reduce or eliminate the chance of being caught by this fallback (e.g., detaching, or having its immediate parent exit before the tree-kill scan, or being spawned via a wrapper that itself exits quickly). A pipeline author fully controls the job script executed by the shell executor inside this job object, and Windows does not require any special privilege to call `CreateProcess` with `CREATE_BREAKAWAY_FROM_JOB` — only that the job object's limit flags permit it, which Runner unconditionally does here for every job.

There is no other Runner-side control (allow-list, privilege drop, or job-object restriction) that prevents a job script from invoking a small helper (via PowerShell `Add-Type`/P-Invoke, a compiled helper binary checked into the repo, or `cmd.exe` with a native launcher) that calls `CreateProcessW` directly with `CREATE_BREAKAWAY_FROM_JOB`.

### Impact Explanation
A malicious/compromised CI job on a Windows shell/shell-executor runner can spawn a process that escapes the job object used to bound the build. When the job is cancelled, times out, or otherwise force-killed via `windowsKiller.ForceKill`/`closeJobObject`, that escaped process is not terminated and keeps running on the runner host after the job's nominal lifetime ends — a persistence primitive scoped to the runner host, violating the invariant that job cancellation must terminate the full process tree.

### Likelihood Explanation
Feasible and fully attacker-controlled: no elevated privileges or GitLab-admin actions are required, only the ability to run job scripts (any pipeline author on a shell-executor Windows runner). The technique (`CREATE_BREAKAWAY_FROM_JOB` with `JOB_OBJECT_LIMIT_BREAKAWAY_OK` present) is standard, well-documented Windows API usage, reproducible on any Windows Runner host that uses `UseWindowsJobObject`.

### Recommendation
Do not set `JOB_OBJECT_LIMIT_BREAKAWAY_OK` (nor `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`) on the per-job job object created in `CreateJobObject`; omit the flag entirely so job membership cannot be voluntarily escaped, and rely solely on `KILL_ON_JOB_CLOSE` plus nested-job support (already gated by `EnsureSubprocessTerminationOnExit`'s Windows-8+ check) to guarantee full process-tree termination.

### Proof of Concept
Go integration test outline for `helpers/process`:
1. Start an `osCmd` with `UseWindowsJobObject: true` running a wrapper script.
2. Wrapper script uses PowerShell `Add-Type` to P/Invoke `CreateProcessW` with `CREATE_BREAKAWAY_FROM_JOB` to spawn a long-lived grandchild (e.g., `powershell -Command "Start-Sleep -Seconds 600"`), writing the grandchild PID to a file.
3. Call `windowsKiller.ForceKill()` on the parent command.
4. Assert: `taskkill`/`closeJobObject` succeeded on the parent, but `windows.OpenProcess` on the recorded grandchild PID still succeeds (process alive) after `ForceKill` returns — proving job-based and taskkill-based termination did not reach the breakaway process.
