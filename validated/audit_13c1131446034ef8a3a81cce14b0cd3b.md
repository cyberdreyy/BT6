### Title
Signer can equivocate by signing two conflicting blocks in the same tenure when the node's tenure-tip lookup errors - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`handle_block_pre_commit` guards against signing a block that conflicts with one this signer already signed, but for *stale* same-tenure conflicts, that guard is delegated entirely to a live RPC call (`get_tenure_tip`) to the signer's own node. When that call errors, the code treats the tenure as "unconfirmed" and falls through to sign anyway, allowing the signer to produce a second, conflicting signature for the same tenure — an equivocation that a single miner plus normal gossip/timing can trigger, without needing a majority of signers.

### Finding Description
`docs/signer-flows.md` explicitly documents that the proposal-time `DuplicateBlockFound` check (`validate_tenure_change_payload`) is **not** re-run at validate-ok time or at signing time, and that "a block that crosses the pre-commit threshold long after it was proposed relies on section 5's own-tenure conflict guard to cover the same ground" [1](#0-0) .

That "own-tenure conflict guard" lives in `handle_block_pre_commit`. It first re-checks freshness of any previously signed conflicting block; only *fresh* conflicts are vetoed by `conflict_still_blocks`/`reorg_permit_stands` [2](#0-1) . For a **stale** same-tenure conflict (older than `tenure_last_block_proposal_timeout`), the code instead asks the node directly for the tenure's tip:

```rust
if conflicts.iter().any(|conflict| {
    conflict.consensus_hash == block_info.block.header.consensus_hash
        && !self.reorg_permit_stands(stacks_client, conflict)
}) {
    match stacks_client.get_tenure_tip(&block_info.block.header.consensus_hash) {
        Ok(tip) => { /* only refuse if tip_height >= proposed height */ }
        Err(e) => {
            warn!(
                "{self}: Failed to fetch the canonical tip of the proposed block's tenure: {e:?}. Treating the tenure as unconfirmed.";
                ...
            );
        }
    }
}
``` [3](#0-2) 

If the RPC call errors (node hasn't processed any block for that tenure yet, a transient connectivity issue, or the tenure genuinely has no chain tip visible to this specific signer's node), the code does **not** refuse to sign; it logs a warning and falls straight through to the signing path, which explicitly announces it is "Signing the replacement" [4](#0-3)  and then calls `mark_locally_accepted`/`handle_block_signature` to produce and broadcast the signature [5](#0-4) .

The comment directly above this block acknowledges the gap is intentional design, not accidental: "The chainstate checks don't cover this for tenure-change blocks: those check the parent tenure instead of their own" [6](#0-5)  — i.e., this `get_tenure_tip` call is the *only* remaining backstop against signing a duplicate tenure-start block once the conflict has gone stale, and it degrades to "allow" on any error.

This mirrors the reported bug class: a decision boundary ("we have already committed a signature for this tenure/height") that should be immutable once crossed is instead re-evaluated against a mutable, externally-supplied input (the node's momentary view of its own tenure tip), and an error/absence of that input is treated as permission to proceed rather than as a reason to refuse.

### Impact Explanation
This allows a single signer instance to sign two different blocks for the same tenure at the same or overlapping height (an equivocation) once the first signature has gone stale (`tenure_last_block_proposal_timeout` elapsed) and the node's tenure-tip RPC does not confirm the first block (e.g., because the first block never reached global acceptance, or the node is momentarily unreachable/lagging). This is a "signer signing a conflicting block," which falls into the Critical impact bucket defined by the rules (a signer signing an invalid, non-canonical, or conflicting block).

### Likelihood Explanation
No majority of signers, no additional signer's key, and no privileged access is required. A single miner can drive this by proposing two different blocks that both claim to start the same tenure, spaced further apart than `tenure_last_block_proposal_timeout` (a value under the miner/network's control to exploit via timing), relying on ordinary gossip propagation. The trigger condition (the local node's `get_tenure_tip` call erroring or not yet reflecting the first block) is a routine occurrence (node lag, transient RPC failure, or the first block simply not reaching the node because it never achieved global signature threshold), making this plausible without any signer collusion.

### Recommendation
Do not let an RPC failure/absence from `get_tenure_tip` be treated as "unconfirmed ⇒ safe to sign." Instead, treat a query error for a same-tenure stale conflict the same as the "still blocks" outcome (fail closed), or independently consult the signer's own local record of `signed_self` blocks for that tenure (the same source `get_signed_conflicts` already reads) as an authoritative veto that does not depend on live node availability.

### Proof of Concept
1. Miner proposes tenure-change block `A` for tenure `T` at height `h`; signer `S` validates, pre-commits, and — after threshold — signs `A` via `handle_block_pre_commit` (`mark_locally_accepted`) [5](#0-4) . Suppose `A` does not reach global acceptance (e.g., other signers reject or split), so `S`'s own node never processes/adopts a block for tenure `T`.
2. Wait longer than `tenure_last_block_proposal_timeout` so `A`'s conflict record becomes stale (`last_endorsed <= freshness_cutoff`) [7](#0-6) .
3. Miner (or gossip of an equivalent competing proposal) proposes a different block `A'` also claiming to start tenure `T` at height `h`. `S` validates and pre-commits to `A'`.
4. On reaching threshold for `A'`, `handle_block_pre_commit` finds the stale conflict against `A` (same `consensus_hash`), calls `stacks_client.get_tenure_tip(consensus_hash)`, which errors because the node has no chain data for tenure `T` [8](#0-7) .
5. The error path only logs a warning; execution falls through to "Signing the replacement" and `S` signs `A'` [9](#0-8) .
6. `S` has now produced valid signatures over two conflicting blocks (`A` and `A'`) for the same tenure/height — an equivocation achievable by one miner plus normal gossip and node-lag conditions, no signer majority required.
