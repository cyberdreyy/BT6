### Title
EI-authenticated identity can trigger a run on any arbitrary job ID via POST /v2/jobs/:ID/runs, bypassing initiator-to-job binding - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` sets `SessionUserKey` to a synthetic `User{Role: UserRoleRun}` for any valid EI credential, which is indistinguishable from a real user session as far as `auth.GetAuthenticatedUser` is concerned. `PipelineRunsController.Create` only checks that *some* authenticated-user-like object exists (`isUser`) and never validates the EI identity (`SessionExternalInitiatorKey`) against the target job's configured initiator before calling `RunJobV2`.

### Finding Description
The route is registered as: [1](#0-0) 

`userOrEI` accepts `AuthenticateExternalInitiator`, `AuthenticateByToken`, or `AuthenticateBySession`. When an EI credential is used, `AuthenticateExternalInitiator` sets both the EI object and a synthetic run-role user in the same session map: [2](#0-1) 

`RequiresRunRole` then only inspects `SessionUserKey`, which is now populated (as `UserRoleRun`), so it passes the request through with no distinction from a genuine session/token user: [3](#0-2) 

Inside `PipelineRunsController.Create`, the code comment states "only users are allowed to run jobs using int IDs - EIs not allowed," but the actual gate is `_, isUser := auth.GetAuthenticatedUser(c)`, which returns `true` for the EI-synthesized user object exactly as it would for a real user: [4](#0-3) 

Once `isUser` is true, the handler parses the numeric job ID from the URL and calls `prc.App.RunJobV2(ctx, jobID, nil)` directly — there is no lookup of `c.Get(SessionExternalInitiatorKey)` (the actual EI identity) and no check that this EI is the one associated with `jobID`'s configured `ExternalInitiatorWebhookSpec`/initiator binding. Any valid EI credential, regardless of which job(s) it was provisioned for, can therefore trigger `RunJobV2` on any numeric job ID that exists on the node.

### Impact Explanation
This is an authorization-bypass allowing an unprivileged EI credential holder (one bound to Job A) to force execution of pipeline runs on Job B, C, etc. — any job on the node — via `RunJobV2`. Since pipeline runs can include tasks performing on-chain writes, external HTTP calls, bridge calls, and other side effects, this constitutes "unauthorized job run" as defined in scope: an attacker with a single, low-privilege EI credential can drive execution of jobs they were never granted access to, potentially causing unwanted on-chain transactions, resource exhaustion, exfiltration via bridge/HTTP tasks configured in other users' jobs, or unexpected fund movement if the target job includes a transmission task.

### Likelihood Explanation
Precondition is minimal: possession of any single valid External Initiator access key/secret pair (which is explicitly a low-trust, run-only credential intended for a specific job/webhook, not for arbitrary job execution). No knowledge of the specific job's own EI binding is required — merely the numeric job ID (`/v2/jobs`, `/v2/jobs/:ID` responses, or predictable sequential IDs, may reveal these). The exploit is a single unauthenticated-to-node-context HTTP POST and is fully repeatable.

### Recommendation
In `PipelineRunsController.Create`, distinguish EI-based pseudo-users from real users by checking `auth.GetAuthenticatedExternalInitiator(c)` explicitly (not relying on `GetAuthenticatedUser`), and if an EI is present, verify that the target job's ID/spec is actually associated with that EI (e.g., via the job's `ExternalInitiatorWebhookSpec.ExternalInitiatorID` or equivalent binding) before calling `RunJobV2`. Reject with `403 Forbidden` if the EI does not own the job. Also update/remove the misleading comment and add a unit test asserting EIs can only trigger runs for jobs they are bound to.

### Proof of Concept
1. Seed two jobs, Job A (webhook-type, bound to `ExternalInitiator` "EI-A") and Job B (any type, unrelated to EI-A).
2. Create EI-A credentials via `POST /v2/external_initiators` (as an edit-role user).
3. As EI-A, send `POST /v2/jobs/<Job B numeric ID>/runs` with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers matching EI-A.
4. Assert:
   - Handler chain reaches `PipelineRunsController.Create` (mock `App.RunJobV2` and assert it is called with Job B's ID).
   - Response is `200`/run resource returned instead of expected `403 Forbidden`.
5. Compare against expected behavior: request should be rejected with `403` because EI-A has no association with Job B.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
