## Analysis

I confirmed the mismatch in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`: the `Accepted` branch only guards double-counting on `block.gathered_signatures.contains_key(&slot_id)`, and the `Rejected` branch only guards on `block.responded_signers.insert(slot_id)`. Neither branch checks the other side's set, so a single signer who first rejects a block and later accepts it (or vice versa) gets counted in *both* `total_weight_rejected` and `total_weight_approved` simultaneously, since `responded_signers` is a single shared set inserted into by both branches and nothing ever removes a slot's weight from the tally it was first recorded in. ### Title
Signer flip-flop (reject-then-accept or accept-then-reject) double-counts weight in the node's block-signing coordinator - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The node-side `StackerDBListener` tallies `total_weight_approved` and `total_weight_rejected` per block from signed `BlockResponse` messages gossiped over StackerDB. The guard that prevents double-counting a single signer's weight is scoped independently per verdict (`gathered_signatures` for Accepted, `responded_signers` for Rejected), rather than being a single mutually-exclusive "has this signer already voted" check across both verdicts. A signer that sends first a `Rejected` and later an `Accepted` for the same `signer_signature_hash` (or the reverse) has its weight added to both `total_weight_rejected` and `total_weight_approved`.

### Finding Description
`handle_signer_message`'s `Accepted` arm checks only `!block.gathered_signatures.contains_key(&slot_id)` before adding weight to `total_weight_approved`, then unconditionally inserts into both `gathered_signatures` and `responded_signers`. [1](#0-0) 

The `Rejected` arm checks only `block.responded_signers.insert(slot_id)` (true the first time the slot appears in `responded_signers`) before adding weight to `total_weight_rejected`. [3](#0-2) 

Consider slot `S` that first sends `Rejected`: `responded_signers.insert(S)` succeeds, `total_weight_rejected += w`. `S` later sends `Accepted` for the same block hash: `gathered_signatures.contains_key(S)` is false (never touched by the reject path), so the accept path adds `total_weight_approved += w` as well, and only then inserts `S` into `gathered_signatures`/`responded_signers` (already present, no-op). The result: `total_weight_approved + total_weight_rejected` now double-counts `w`, and `S`'s weight is simultaneously present in both aggregates. The reverse order (Accepted then Rejected) does not double count because the `Rejected` guard (`responded_signers.insert`) is already `true`→`false` after the accept path inserted `S` into `responded_signers` — but this asymmetry itself shows the two tallies are not maintained as complementary partitions of one "signer's final vote," they are independently-gated running totals that can drift out of sync with the actual, distinct set of signers who accepted vs. rejected.

This breaks the invariant the wiki's flow doc states should be maintained ("70% signed" vs. "over 30% rejected — 70% is now impossible" are meant to be mutually exclusive, weight-partitioned outcomes) [4](#0-3) . The coordinator's threshold checks — `total_weight_approved >= self.weight_threshold` to notify acceptance, and `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` to notify rejection — read `block.total_weight_rejected`/`total_weight_approved` as if they were a clean partition of `total_weight`, i.e. "aggregated weight vs. verified accepts/rejects." A single signer flip-flopping breaks that equality.

### Impact Explanation
Because a signer's earlier reject weight is never retracted when it later accepts, `total_weight_rejected` can remain inflated even though the true set of currently-rejecting signers no longer supports 30%+ weight. This can cause the node's coordinator to spuriously conclude that "70% is now impossible" (triggering the rejection-side `cvar.notify_all()` at line 573) and abandon waiting on a block that in fact has (or could still reach) the acceptance threshold — a liveness wedge on that specific block/tenure-attempt, forcing the miner to re-propose. It does not directly cause an invalid or non-canonical block to be signed (the underlying `BlockResponse` messages are still individually signature-checked at lines 411-426 and 501-513), so it is a coordinator-side accounting/liveness defect rather than a "sign an invalid block" defect.

### Likelihood Explanation
Triggering this requires only one signer (which could be the single signer collocated with a byzantine/buggy miner setup, or any single misbehaving/flaky signer client) to emit two `BlockResponse` messages with opposite verdicts for the same block hash — something the protocol does not forbid at the wire level, and which can occur naturally from a signer's local state machine changing its mind (the `stacks-signer` code explicitly supports re-evaluating and flipping a decision, e.g. `LocallyRejected --> LocallyAccepted : re-evaluated` in the signer's own state machine) [5](#0-4) . Since `signer.rs`'s own state machine allows exactly this transition, and the node coordinator has no defense against a slot re-appearing under the opposite verdict, the precondition is plausibly hit even without malice — a legitimate signer that rejects, then later re-evaluates and accepts (or the reverse) after a timeout/re-proposal, is enough.

### Recommendation
Track each signer's final verdict as a single overwritable per-slot state (e.g. one `HashMap<slot_id, Verdict>` instead of independent `gathered_signatures`/`responded_signers` sets), recomputing `total_weight_approved`/`total_weight_rejected` from that map, so a slot flipping its vote moves its weight from one tally to the other atomically rather than being double-counted.

### Proof of Concept
1. Node's `StackerDBListener` tracks a block `B` awaiting signatures with `weight_threshold` set for 70%.
2. Signer slot `S` (weight `w`) sends `BlockResponse::Rejected` for `B` → `responded_signers = {S}`, `total_weight_rejected = w`.
3. Signer slot `S` later (e.g. after re-evaluating per its own `LocallyRejected --> LocallyAccepted` transition) sends `BlockResponse::Accepted` for the same `signer_signature_hash` → since `gathered_signatures` does not yet contain `S`, `total_weight_approved = w` is added as well.
4. Now `total_weight_approved + total_weight_rejected > total_weight` is possible for this block, and `S`'s weight is counted on both sides — an accounting break in the aggregated-weight vs. distinct-signer-verdict equality that the 70%/30% thresholds rely on.

Note: I was unable to fully trace whether `signer_coordinator.rs` (which also references these same weight fields per the grep results) applies any additional reconciliation/clamping on top of `StackerDBListener`'s tallies before acting on the threshold signals; that file's exact logic could not be inspected in this pass and would be worth reviewing to confirm whether this drift is consumed unguarded downstream.
