### Title
Stale confirmations from removed members count toward `num_confirmations` threshold in `confirm` - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` compares `confirmations.len() as u32 + 1 >= self.num_confirmations`, where `confirmations` is a `HashSet<String>` of member identifiers recorded on past `confirm()` calls. When a member is removed via `DeleteMember`, `delete_member` only purges requests **originated** by that member (`r.member == member`), never scrubbing that member's entries from the `confirmations` set of requests they had merely confirmed but did not create. A pending request can therefore reach the required confirmation count using fewer live members than `num_confirmations`, and be executed.

### Finding Description
The invariant the code is supposed to maintain is:
`confirmations_count_used_in_threshold_check == count_of_confirmations_from_current_members`

The actual code path in [1](#0-0)  only checks that the *calling* member is currently valid (via `assert_valid_request` → `current_member()`), and that the caller has not confirmed already — it never re-validates the members already present in the stored `confirmations` `HashSet<String>` against the live `self.members` set.

`delete_member`, invoked only through the self-referential `DeleteMember` action, purges outstanding requests only when the removed member is the **request originator**: [2](#0-1) 
It filters `self.requests` for `r.member == member` (the signer who called `add_request`), and removes those requests/confirmations entirely. It does **not** scan every request's `confirmations` `HashSet` to strip out entries belonging to the member being deleted when that member was merely a *confirmer* (not the originator) of some other still-pending request.

Exploit flow (4 members A, B, C, D; `num_confirmations = 3`):
1. Member A calls `add_request` to create a `Transfer` request `R` (no `assert_self_request` needed for `Transfer`).
2. A calls `confirm(R)` → `confirmations = {A}` (1 < 3, stored not executed).
3. B calls `confirm(R)` → `confirmations = {A, B}` (2 < 3, stored not executed).
4. Separately, a fully-confirmed (3-of-4, legitimate) `DeleteMember{member: B}` request executes, removing B from `self.members`. Because B did not originate `R`, the `delete_member` cleanup loop at [3](#0-2)  never touches `R`'s confirmations; `R.confirmations` still contains `B`.
5. Now only A, C, D are live members. C calls `confirm(R)`. `current_member()` succeeds for C (a live member) via [4](#0-3) , and `confirmations.len() as u32 + 1 = 2 + 1 = 3 >= num_confirmations (3)` at [5](#0-4) , so `execute_request` runs and the `Transfer` executes.

Only **two** live members (A and C) actually authorized the still-pending state of request `R` at execution time (B's stale confirmation, from a since-removed member, is counted). The threshold of 3 live confirmations required by the multisig configuration was never actually reached, yet funds move.

`assert_self_request` is irrelevant to this specific `Transfer` path (it only gates `AddMember`/`DeleteMember`/`AddKey`/`SetNumConfirmations`), so the "receiver_id = self" framing in the question does not materially change this particular exploit for fund-moving `Transfer` actions — the vulnerability is the stale-confirmation accounting itself, independent of `receiver_id`.

### Impact Explanation
This directly matches the Critical category: "a multisig request executed below `num_confirmations` live members." NEAR held by the multisig account can be transferred out via `MultiSigRequestAction::Transfer` (or other actions such as `AddKey`/`FunctionCall`) with fewer genuinely-live confirmations than the configured threshold, effectively bypassing the multisig's security guarantee. This is repeatable any time membership changes occur while requests are pending with partial confirmations from members who are later removed as non-originators.

### Likelihood Explanation
No privileged access is required beyond being (or having been) a legitimate multisig member acting normally — no special attacker capability beyond ordinary member/request lifecycle timing is needed. The only precondition is: a request accumulates confirmations from members who are later removed (a routine occurrence in any multisig doing membership rotation), and any subsequent live confirmation completes the threshold using the stale entries. This is entirely feasible in normal contract operation and costs the attacker (or colluding members) nothing extra.

### Recommendation
When counting confirmations in `confirm`, filter `confirmations` against the live `self.members` set (e.g., `confirmations.iter().filter(|m| self.members.contains(...)).count()`), or alternatively have `delete_member` scan **all** requests' confirmation sets (not just those originated by the removed member) and strip the removed member's entry from each, deleting confirmations regardless of origination.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
