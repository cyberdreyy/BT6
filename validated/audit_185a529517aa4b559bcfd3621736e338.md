### Title
Loss-adjusted withdraw receipts claimable at par due to epoch-key mismatch in `collectWithdrawFunds` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug (CVE-2025-48188) is a heap-based over-read caused by passing mismatched buffer parameters to a decrypt routine — i.e., data is read under the wrong boundary/key. The analog in `IdleCreditVault` is that `collectWithdrawFunds` records the loss haircut under `epochNumber` at collection time (line 421), while both the pre-request guard and `_claimLossAdjustedWithdrawRequest` look the haircut up under `lastWithdrawRequest[_user]`, i.e. the epoch in which the receipt was created (lines 261–262, 790–791). Since `deposit()` increments `epochNumber` during `stopEpoch` while `isEpochRunning()` is still true (lines 607–610), if `collectWithdrawFunds` is invoked by the CDO after the strategy-token deposit inside the same `stopEpoch`, the haircut is stored under `requestEpoch + 1` and is never read under `requestEpoch`.

### Finding Description
- `requestWithdraw` records receipts under `withdrawsRequestsByEpoch[user][epochNumber]` and sets `lastWithdrawRequest[user] = epochNumber` at request time (lines 282–293).
- On a `stopEpochWithDuration(_lossAmount)` partial funding, `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (line 421).
- The claim path reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` (lines 790–791); the re-request guard reads the same key (lines 261–266).
- `deposit()` bumps `epochNumber` when called while the epoch is still flagged running (lines 607–610). If the CDO's `stopEpoch` collects withdraw funds after that bump, the write key diverges from every read key by one epoch.

Caveat: I could not confirm the exact ordering between `deposit`/`mintStrategyTokens` and `collectWithdrawFunds` inside `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` within the available tool budget. The vulnerability exists iff `collectWithdrawFunds` executes after the epoch-incrementing `deposit` call. If the CDO collects funds before the deposit that bumps `epochNumber`, the keys align and this finding does not hold.

### Impact Explanation
If the key mismatch occurs, `_claimLossAdjustedWithdrawRequest` returns 0 because `lossRecoveryPriceByEpoch[requestEpoch] == 0`, so control falls to `_claimFundedWithdrawRequest`. There, `epochNumber (requestEpoch+1) > lastWithdrawRequest (requestEpoch)` passes the gating check, and the user is paid `withdrawsRequests[user]` at par via `_transferFundedClaim` — even though only `pendingToFund < pendingBasis` was collected. Early claimers drain the strategy at unhaircutted prices; later claimers' transfers revert for insufficient balance. Result: direct insolvency/permanent freezing of the unpaid remainder, quantified as the haircut portion `pendingLoss = _lossAmount * pendingBasis / totalBasis` from `previewLossAdjustedWithdrawFunds` (lines 457–458). Additionally, the re-request guard (lines 263–271) never fires for these users, so they can stack further requests on top of unclaimed loss receipts, worsening the shortfall. The broken invariant is the loss waterfall: pending receipts escape their assigned loss share.

### Likelihood Explanation
The trigger is a single honest-sequence `stopEpochWithDuration` with `_lossAmount > 0` while pending withdraws exist — no privileged misbehavior required. Any tranche holder with a pending receipt then claims at par. Exploitability depends entirely on intra-`stopEpoch` call ordering, which could not be fully verified; if `collectWithdrawFunds` runs after the funding deposit, the bug triggers deterministically on every loss-adjusted stop with pending receipts.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the request epoch of the receipts being funded rather than the mutable `epochNumber` at collect time — e.g., store the haircut under a dedicated `lastPendingWithdrawEpoch` captured when `pendingWithdraws` was last increased, or record `pendingWithdrawsEpoch` alongside the aggregate and write `lossRecoveryPriceByEpoch[pendingWithdrawsEpoch]`. Alternatively, make `collectWithdrawFunds` revert unless every entry contributing to `pendingWithdraws` shares one request epoch, or snapshot `epochNumber` into a local variable before any `deposit` call can increment it. Add a Foundry test asserting that after `stopEpochWithDuration(loss>0)` with pending receipts, `claimWithdrawRequest` pays `basis * lossRecoveryPrice` and the last claim does not revert.

### Proof of Concept
Sketch (Foundry fork, requires confirmed ordering):

```solidity
// Setup: standard epoch variant, deposit AA+BB, requestWithdraw during buffer/epoch N
uint256 req = cdoEpoch.requestWithdraw(mintedAA, address(AAtranche)); // lastWithdrawRequest = N

// Honest manager: borrower repays less than owed -> stopEpochWithDuration(_lossAmount)
// Inside stopEpoch: strategy.deposit() bumps epochNumber to N+1, then
// strategy.collectWithdrawFunds(pendingToFund) stores price under N+1.
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(initialApr, lossAmount);

IdleCreditVault v = IdleCreditVault(address(strategy));
// Key mismatch: haircut stored under N+1
assertEq(v.lossRecoveryPriceByEpoch(N), 0);
assertGt(v.lossRecoveryPriceByEpoch(N + 1), 0);

// Attacker (ordinary receipt holder) claims at par instead of haircutted amount
uint256 balPre = underlying.balanceOf(user1);
vm.prank(user1);
cdoEpoch.claimWithdrawRequest();
// Received full `req` rather than req * lossRecoveryPrice / 1e18
assertEq(underlying.balanceOf(user1) - balPre, req);

// Victim claimer reverts: strategy balance insufficient for remaining basis
vm.expectRevert();
vm.prank(user2);
cdoEpoch.claimWithdrawRequest();
```

If, upon inspection, `IdleCDOEpochVariant.stopEpoch` calls `collectWithdrawFunds` strictly before the epoch-incrementing `deposit`, this PoC fails and the finding should be rejected — in that case no stronger analog to the over-read bug class was identified in the epoch/withdraw accounting surface within the search budget.
