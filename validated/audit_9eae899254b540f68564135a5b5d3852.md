### Title
SSH executor `Cleanup()` never terminates detached/background remote processes, allowing job-created listeners to persist on shared host - (File: executors/ssh/ssh.go)

### Summary
`executor.Cleanup()` delegates entirely to `ssh.Client.Cleanup()`, which only closes the top-level SSH connection object and issues no remote command to kill leftover process groups. `ssh.Client.Run()` only sends `SIGKILL` to the session's own channel when the build `context` is cancelled; it never targets descendant/detached processes, so a job script that backgrounds a process (e.g. `nohup ... &`, `setsid ...`, `disown`) survives both normal completion and cancellation, remaining bound to a port on the shared host.

### Finding Description
`executor.Cleanup()` in `executors/ssh/ssh.go:75-78` calls `s.sshCommand.Cleanup()` then `s.AbstractExecutor.Cleanup()`. `ssh.Client.Cleanup()` in `helpers/ssh/ssh_command.go:180-184` does nothing but `s.client.Close()` - closing the underlying `*ssh.Client` TCP connection. It sends no remote `kill`, `pkill -P`, or process-group teardown command.

Separately, `ssh.Client.Run()` (`helpers/ssh/ssh_command.go:141-178`) only reacts to context cancellation, and even then only signals the specific SSH *session* (`session.Signal(ssh.SIGKILL)`) tied to the invoking shell, not a process group. Standard SSH server semantics deliver signals to the foreground process associated with the session's PTY/channel; a process explicitly detached by the job script (`&` combined with `disown`, `setsid`, or `nohup`) is reparented away from that session and is not part of the signalled process tree, so it is unaffected by both the `SIGKILL` on cancellation and by closing the connection on normal Cleanup.

Because the SSH executor is explicitly a shared-host executor (`SharedBuildsDir: true`, `features.Shared = true` in `NewProvider()`), multiple jobs from different projects run sequentially or concurrently against the same target host/user. A job's build script is fully attacker-controlled CI YAML (`script:` steps), so an attacker-controlled job can trivially background a listener that the SSH executor never reclaims, regardless of whether the job succeeds, fails, or is cancelled.

Existing checks that might stop this (allowed images, path validation, auth checks) are inapplicable here since this executor has no sandboxing by design; the only relevant control point is `Cleanup()`, and it lacks a remote-side cleanup command to reclaim job-created OS resources such as bound sockets, which is a real gap relative to the invariant that executor `Cleanup()` must fully reclaim job-created resources.

### Impact Explanation
A subsequent job from a different project running on the same shared SSH host can fail its setup/build steps if it tries to bind the same fixed port (e.g., a test server, service healthcheck, or local proxy on a well-known port). This is a cross-project denial-of-service on a shared resource (network port) caused directly by an executor's incomplete cleanup, not by any documented/expected admin trust boundary being crossed (the flaw is that `Cleanup()` doesn't do what its name and contract imply, not that shared-host execution itself is inherently insecure administrative policy).

### Likelihood Explanation
Highly feasible and fully attacker-controlled: any pipeline author whose jobs run against a shared SSH executor host can include a `script:` step like `nohup nc -l -p 8080 & disown` (or any long-running background daemon) with no special privileges required. It requires only normal CI job authoring rights and a runner configured with the `ssh` executor pointing at a reused host (a common configuration, since the SSH executor is designed for persistent/shared hosts). It is deterministically repeatable across job runs since `Cleanup()` never changes behavior based on what the job did.

### Recommendation
Have `ssh.Client.Cleanup()` (and/or `executor.Cleanup()`) actively reclaim remote resources before/while closing the connection, e.g.:
- Track the PID of the shell process launched by `Run()` and, in `Cleanup()`, execute a best-effort remote command such as `pkill -KILL -P <pid>` or `kill -KILL -- -<pgid>` (killing the whole process group, not just the immediate session) prior to closing the connection.
- Alternatively, launch job scripts in a dedicated process group/session (e.g., via `setsid`) whose PGID is recorded, then send the kill signal to `-PGID` so detached/background children are included.
- Document and warn operators that the SSH executor provides no isolation between jobs' OS-level resources (ports, files, processes) if this cannot be fully closed, so operators can avoid relying on it for untrusted/multi-tenant use unless combined with external supervision (e.g., cgroup/process-group enforcement, ephemeral hosts).

### Proof of Concept
Go integration test outline (in `helpers/ssh` or `executors/ssh` test package):
```go
func TestSSHClient_Cleanup_DoesNotKillBackgroundedProcess(t *testing.T) {
    client := &ssh.Client{SshConfig: testSSHConfig(t)} // points to a test SSH server
    require.NoError(t, client.Connect())

    var stdout, stderr bytes.Buffer
    err := client.Run(context.Background(), ssh.Command{
        Command: "bash",
        Stdin:   "nohup sh -c 'exec nc -l -p 18080' >/dev/null 2>&1 & disown; sleep 1",
        Stdout:  &stdout,
        Stderr:  &stderr,
    })
    require.NoError(t, err)

    client.Cleanup() // simulates executor.Cleanup()

    // Assert the port is still bound on the remote host after Cleanup,
    // e.g. by attempting a second SSH connection/exec and checking
    // `nc -z localhost 18080` succeeds (listener still alive),
    // or by attempting a fresh "different project" job's setup step
    // that itself tries to bind 18080 and observing bind failure ("address already in use").
    verifyClient := &ssh.Client{SshConfig: testSSHConfig(t)}
    require.NoError(t, verifyClient.Connect())
    defer verifyClient.Cleanup()

    var checkOut bytes.Buffer
    err = verifyClient.Run(context.Background(), ssh.Command{
        Command: "bash",
        Stdin:   "nc -z localhost 18080 && echo STILL_LISTENING",
        Stdout:  &checkOut,
    })
    require.NoError(t, err)
    require.Contains(t, checkOut.String(), "STILL_LISTENING",
        "Cleanup() should have terminated job-spawned background processes/listeners but did not")
}
```
Expected result confirming the bug: `STILL_LISTENING` is printed, proving the port remains bound after `Cleanup()`, which would cause any following job (from any project) attempting to bind port `18080` to fail with `bind: address already in use`.
