### Title
Withdraw confidential-transfer instruction parser mislabels a context-state account as `owner` and silently drops a required proof-context field when `account_indexes` is undersized relative to the proof-offset combination - ([File: transaction-status/src/parse_token/extension/confidential_transfer.rs])

### Summary
`parse_confidential_transfer_instruction`'s `Withdraw` branch only enforces a minimum of 4 accounts via `check_num_token_accounts(account_indexes, 4)`, but the real spl-token-2022 program needs 5 accounts when both the equality and range proofs are context-account based (`equality_proof_instruction_offset == 0 && range_proof_instruction_offset == 0`). Because each optional field insertion is gated by `offset < account_indexes.len().saturating_sub(1)`, when `account_indexes.len() == 4` only the equality context account is inserted and the loop stops one iteration early, so the range-proof context account is silently omitted from the parsed JSON, and the account actually meant to be the range-proof context is instead relabeled as `owner` by the trailing `parse_signers` call.

### Finding Description
In `transaction-status/src/parse_token/extension/confidential_transfer.rs`, the `Withdraw` arm: [1](#0-0) 

only checks `check_num_token_accounts(account_indexes, 4)` up front, which enforces `account_indexes.len() >= 4`. It then walks through up to three optional slots (`instructionsSysvar`, `equalityProofContextStateAccount`, `rangeProofContextStateAccount`), each gated by `offset < account_indexes.len().saturating_sub(1)`. This bound is designed to always leave the last index reserved for `parse_signers`'s owner/multisig account: [2](#0-1) 

The bound assumes at most one optional account is needed beyond `source`/`mint` before the owner slot. That assumption is false whenever `equality_proof_instruction_offset == 0` **and** `range_proof_instruction_offset == 0` simultaneously - in that case the real spl-token-2022 processor consumes two context-state accounts (equality, then range) before the owner account, i.e. it needs 5 accounts total (source, mint, eqCtx, rangeCtx, owner), not 4.

An attacker (unprivileged, single client, one `getTransaction` call) can craft a transaction whose `Withdraw` instruction carries `account_indexes.len() == 4` with both proof offsets set to `0`:
- `offset` starts at `2`.
- `has_sysvar` is `false` (since both offsets are `0`), so the sysvar branch is skipped.
- Equality check: `offset(2) < len-1(3)` → true → `equalityProofContextStateAccount = accounts[2]`, `offset` becomes `3`.
- Range check: `offset(3) < len-1(3)` → false → **`rangeProofContextStateAccount` is never added**, even though the encoded proof offsets say it should be present.
- `parse_signers(map, 3, ...)`: since `accounts.len()(4) > 3+1(4)` is false, it labels `accounts[3]` as `"owner"`.

On the real spl-token-2022 program's actual account-consumption convention, with only 4 accounts supplied and both proofs context-based, the program would consume `accounts[2]` as the equality context account and attempt to consume `accounts[3]` as the range context account, then fail with a missing-account error when trying to fetch the owner account (index 4, which doesn't exist). The transaction fails on-chain but is still recorded in the blockstore and retrievable via `getTransaction` with `jsonParsed` encoding, because instruction parsing is independent of execution success. The parser therefore reports `accounts[3]` with the role `"owner"` and omits `rangeProofContextStateAccount` entirely - a mismatch with what the actual program's account-consumption convention dictates for that instruction, and a silently dropped field, which is exactly the "misreported/omitted authority or context account" scoped impact.

The existing test suite (`test_withdraw`) does not catch this because it always builds instructions via the SPL `inner_withdraw` helper, which always supplies the correct number of accounts for the given `ProofLocation` combination; it never exercises an undersized/malformed `account_indexes` list.

### Impact Explanation
This is a decoder/JSON-RPC misreporting bug in `getTransaction`'s `jsonParsed` encoding path: a single crafted, low-cost, unprivileged transaction (which need not even succeed on-chain) causes the parsed instruction JSON to (a) drop a required `rangeProofContextStateAccount` field entirely, and (b) mislabel a proof-context account as the `owner`/authority field. Any downstream tooling (block explorers, indexers, compliance tooling) that trusts `getTransaction` jsonParsed output to enumerate required accounts/authorities for a confidential-transfer withdrawal would under-report or misattribute account roles. This matches the "wrong/misreported data returned" and "decoder misreporting" categories in scope.

### Likelihood Explanation
Fully attacker-controlled and trivially reproducible: the attacker only needs to submit one transaction with a `TokenInstruction::ConfidentialTransferExtension` / `Withdraw` sub-instruction carrying exactly 4 accounts and both `equality_proof_instruction_offset == 0` and `range_proof_instruction_offset == 0`, then query it once via `getTransaction` with `jsonParsed` encoding. No special privileges, timing, or repeated calls are required, and the transaction can fail on-chain (it will still be recorded and parsed). This is deterministic and 100% repeatable.

### Recommendation
For `Withdraw` (and structurally identical `Transfer`/`TransferWithFee`/`confidential_mint_burn` arms using the same pattern), compute the exact number of optional accounts required from the proof-offset booleans up front (e.g., `required_extra = has_sysvar as usize + (eq_offset==0) as usize + (rng_offset==0) as usize`) and call `check_num_token_accounts(account_indexes, 2 + required_extra + 1)` (the `+1` for the mandatory owner slot) before attempting any insertion, returning `ParseInstructionError::InstructionNotParsable` if the account list is too short instead of silently truncating the optional-field insertion loop.

```rust
// transaction-status/src/parse_token/extension/confidential_transfer.rs (test module)
#[test]
fn test_withdraw_undersized_accounts_misreports_range_context() {
    use solana_instruction::{AccountMeta, Instruction};
    use solana_message::Message;
    use spl_token_2022_interface::extension::confidential_transfer::instruction::WithdrawInstructionData;

    // Manually construct a Withdraw instruction with only 4 accounts
    // (source, mint, equalityCtx-that-should-be-shared, "owner"-slot-that-is-really-rangeCtx),
    // and both proof offsets == 0 (both context-account based, needs 5 accounts really).
    let source = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let eq_ctx = Pubkey::new_unique();
    let range_ctx_masquerading_as_owner = Pubkey::new_unique();

    let mut data = vec![/* ConfidentialTransferExtension tag */ 27, /* Withdraw tag */ 6];
    // encode WithdrawInstructionData with amount, decimals, new_decryptable_balance,
    // equality_proof_instruction_offset = 0, range_proof_instruction_offset = 0
    // (bytes elided - use bytemuck::bytes_of on a zeroed WithdrawInstructionData with offsets set to 0)
    data.extend_from_slice(/* ... encoded bytes ... */ &[]);

    let instruction = Instruction {
        program_id: spl_token_2022_interface::id(),
        accounts: vec![
            AccountMeta::new(source, false),
            AccountMeta::new_readonly(mint, false),
            AccountMeta::new_readonly(eq_ctx, false),
            AccountMeta::new_readonly(range_ctx_masquerading_as_owner, false),
        ],
        data,
    };

    let message = Message::new(&[instruction], None);
    let parsed = parse_token(
        &message.instructions[0],
        &AccountKeys::new(&message.account_keys, None),
    )
    .unwrap();

    // Bug: rangeProofContextStateAccount is silently dropped.
    assert!(
        parsed.info.get("rangeProofContextStateAccount").is_none(),
        "expected field to be missing due to boundary bug"
    );
    // Bug: the account that should represent rangeProofContextStateAccount
    // is instead mislabeled as "owner".
    assert_eq!(
        parsed.info["owner"],
        serde_json::json!(range_ctx_masquerading_as_owner.to_string())
    );
}
```
Expected outcome demonstrating the bug: the assertions pass on current code (confirming the field is dropped and the role is mislabeled), whereas a correct implementation should either reject the instruction as unparsable (insufficient accounts for the declared proof-offset combination) or correctly report `rangeProofContextStateAccount` and leave `owner` absent/at the correct index.

```rust
fn parse_signers(
    map: &mut Map<String, Value>,
    last_nonsigner_index: usize,
    account_keys: &AccountKeys,
    accounts: &[u8],
    owner_field_name: &str,
    multisig_field_name: &str,
) {
    if accounts.len() > last_nonsigner_index + 1 {
        let mut signers: Vec<String> = vec![];
        for i in accounts[last_nonsigner_index + 1..].iter() {
            signers.push(account_keys[*i as usize].to_string());
        }
        map.insert(
            multisig_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
        map.insert("signers".to_string(), json!(signers));
    } else {
        map.insert(
            owner_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
    }
}
```
