### Title
External Initiator authentication grants a global "run" role without binding the authenticated EI identity to the specific webhook job's registered initiator, allowing any EI to trigger any EI-gated job run - ([File: core/web/auth/auth.go])

### Summary
The reported bug class is a missing verification between two related values (`tokenAmount` vs `bridgeAmount`) that allows an attacker to trigger an unintended, unauthorized action (fund movement) using credentials/inputs that don't actually correspond to what is being acted upon. The closest unprivileged-actor analog in this repo is in the node's External Initiator (EI) authentication path: `AuthenticateExternalInitiator` authenticates the *caller* (any registered EI, via its own AccessKey/Secret), but grants a blanket `UserRoleRun` session without verifying that the authenticated EI is the specific initiator bound to the target webhook job.

### Finding Description
`AuthenticateExternalInitiator` in `core/web/auth/auth.go` looks up an `ExternalInitiator` by the caller-supplied `AccessKey`/`Secret` headers, verifies the HMAC-style secret match via `bridges.AuthenticateExternalInitiator`, and then unconditionally elevates the request to `UserRoleRun`: [1](#0-0) 

This authenticates *that a valid EI exists*, but the resulting session role (`UserRoleRun`) is generic - it is not scoped to the specific EI that was authenticated, nor is the `SessionExternalInitiatorKey` value subsequently consulted anywhere else in the codebase to confirm that the job/run being created is actually linked to that EI. A `grep` across the repository shows `SessionExternalInitiatorKey` is only referenced inside `core/web/auth/auth.go` itself - it is never read by the job-run creation handlers (e.g. `core/web/pipeline_runs_controller.go`) to cross-check against the webhook job's registered `external_initiator_webhook_specs` binding (`external_initiator_id` ⇄ `webhook_spec_id`), which is how EI-to-job ownership is modeled in the schema: [2](#0-1) 

This mirrors the external report's root cause: the system authenticates one value (the caller's identity/`tokenAmount`) but never verifies it against the specific resource being acted upon (the job's bound EI/`bridgeAmount`), relying only on a coarse role check (`UserRoleRun`) rather than an exact identity match, analogous to the missing `tokenAmount == bridgeAmount` check in `BridgingUtils::executeBridging`.

### Impact Explanation
If job-run creation for webhook/EI-gated jobs only checks `clsessions.UserRoleRun` (set identically for every authenticated EI) rather than validating that the specific authenticated `ExternalInitiator` matches the job's configured `externalInitiators` binding, any registered EI (an unprivileged, external actor who only possesses their own EI credentials) could trigger runs on webhook jobs belonging to a *different* EI. This is an unauthorized job-run / cross-user confusion issue: it lets one external caller invoke pipeline runs that should be restricted to another initiator's credentials, potentially triggering unintended fund-moving or state-changing job pipelines.

### Likelihood Explanation
Medium - it requires an attacker to have registered at least one legitimate EI (a low bar given the External Initiators feature is meant to be self-service/config-gated via `ExternalInitiatorsEnabled`), and requires that the target node runs multiple webhook jobs registered to different EIs. Given `AuthenticateExternalInitiator` never re-derives or checks EI-to-job binding at the point of consuming `SessionExternalInitiatorKey`, exploitation, if the run-creation code path indeed does not filter by EI identity, would not require any additional secret compromise beyond the attacker's own valid EI credentials.

### Recommendation
1. In the job-run creation path (wherever `SessionExternalInitiatorKey` should matter, e.g. `core/web/pipeline_runs_controller.go`), explicitly verify that the `ExternalInitiator` retrieved from the session context matches the `external_initiator_webhook_specs` entry bound to the target job, rejecting runs where the authenticated EI does not equal the job's registered initiator.
2. Avoid using a single, undifferentiated `UserRoleRun` for all authenticated EIs; instead carry the specific EI identity through to authorization checks so the "role vs. identity" data are cross-verified exactly as the external report recommends (verify the two related values, don't just check that "some" identity/amount is present).

### Proof of Concept
Not independently confirmed with a runtime PoC because the run-creation handler's authorization logic (`core/web/pipeline_runs_controller.go`) could not be retrieved to confirm whether it performs this cross-check. Conceptually:
1. Register two External Initiators, EI-A and EI-B, via `POST /v2/external_initiators` (handled by `ExternalInitiatorsController.Create`) [3](#0-2) .
2. Create a webhook job whose `externalInitiators` list references only EI-B.
3. Using EI-A's `AccessKey`/`Secret` headers, call the job's run-creation endpoint. `AuthenticateExternalInitiator` succeeds (EI-A is a valid, authenticated EI) and sets `UserRoleRun` [4](#0-3) .
4. If the downstream handler only checks `UserRoleRun` and not identity equality with the job's bound EI, the run for EI-B's job is created using EI-A's credentials.

Given the inability to inspect `core/web/pipeline_runs_controller.go`'s exact authorization logic within the current search results, this finding should be verified against that file's implementation before treating it as conclusively exploitable - a Devin session with full repository access could confirm whether such a cross-check exists.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

func (eic *ExternalInitiatorsController) Create(c *gin.Context) {
	ctx := c.Request.Context()
	eir := &bridges.ExternalInitiatorRequest{}
	if !eic.App.GetConfig().JobPipeline().ExternalInitiatorsEnabled() {
		err := errors.New("The External Initiator feature is disabled by configuration")
		jsonAPIError(c, http.StatusMethodNotAllowed, err)
		return
	}

	eia := auth.NewToken()
	if err := c.ShouldBindJSON(eir); err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	ei, err := bridges.NewExternalInitiator(eia, eir)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	if err := ValidateExternalInitiator(ctx, eir, eic.App.BridgeORM()); err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}
	if err := eic.App.BridgeORM().CreateExternalInitiator(ctx, ei); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	eic.App.GetAuditLogger().Audit(audit.ExternalInitiatorCreated, map[string]any{
		"externalInitiatorID":   ei.ID,
		"externalInitiatorName": ei.Name,
		"externalInitiatorURL":  ei.URL,
	})

	resp := presenters.NewExternalInitiatorAuthentication(*ei, *eia)
	jsonAPIResponseWithStatus(c, resp, "external initiator authentication", http.StatusCreated)
}
