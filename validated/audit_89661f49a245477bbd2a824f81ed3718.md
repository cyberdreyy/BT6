### Title
Operator/beneficiary can permanently freeze a staker's unlocked stake by refusing direct coin transfers - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`staking_contract::distribute_internal` pays out every entry in the `distribution_pool` — including the staker's unlocked/withdrawn stake and the operator's commission — in a single atomic loop, using `aptos_account::deposit_coins` for each recipient. Neither `distribute()` nor `switch_operator()` (which both call `distribute_internal` unconditionally before doing anything else) verifies that all recipients, in particular the operator's beneficiary, can actually accept the funds. If the operator (or its beneficiary) opts out of direct coin transfers via `aptos_account::set_allow_direct_coin_transfers(false)`, any subsequent call to `distribute()` or `switch_operator()` aborts on `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`, reverting the whole transaction and permanently blocking the staker's own unlocked-stake withdrawal that is bundled in the same pool.

### Finding Description
`distribute_internal` iterates over all shareholders of `distribution_pool` in one atomic loop and routes the operator's commission to its beneficiary via `beneficiary_for_operator`: [1](#0-0) 

The commission recipient can be redirected to any address via `set_beneficiary_for_operator`, an action fully controlled by the operator, independent of the pool it applies to: [2](#0-1) 

`aptos_account::deposit_coins` will abort if the destination account exists but has explicitly opted out of receiving un-registered/direct coin transfers: [3](#0-2) [4](#0-3) 

Both of the entry points that are supposed to let the staker recover value from a staking contract call `distribute_internal` first and unconditionally:
- `distribute(staker, operator)` calls `distribute_internal` directly.
- `switch_operator(...)` also calls `distribute_internal` before doing anything else, specifically so it can "force distribution of any already inactive stake" prior to detaching from the old operator: [5](#0-4) 

Because both recovery paths route through the same atomic `distribute_internal` call, if the operator's beneficiary refuses direct transfers, both `distribute()` and `switch_operator()` abort every time they are invoked while any unpaid commission share exists for that operator. The staker has no mechanism to remove the operator's own beneficiary setting or to bypass this validation — `set_beneficiary_for_operator` can only be invoked by the operator itself. Unlike `vesting::set_beneficiary`, which explicitly requires `assert_account_is_registered_for_apt(new_beneficiary)` before installing a beneficiary: [6](#0-5) 

`staking_contract::set_beneficiary_for_operator` performs no such registration/acceptance check on `new_beneficiary`: [7](#0-6) 

This is the direct Aptos-native analog of the reported bug: just as `_xcall()` never validates that a `delegate` exists/is workable before it becomes load-bearing for recovering stuck funds, `set_beneficiary_for_operator` never validates that the configured beneficiary can actually receive funds before it becomes load-bearing for every future `distribute`/`switch_operator` call that touches that operator's staking contract.

### Impact Explanation
An operator (who holds a legitimate but limited role, and does not own the staker's principal) can unilaterally and permanently deny the staker access to already-unlocked/withdrawn stake and prevent the staker from ever switching away to a different operator, simply by pointing its beneficiary at an account that has disabled direct coin transfers. Since `distribute_internal` is atomic and aborts the whole transaction on the first failed deposit, this blocks payouts to *all* parties sharing the `distribution_pool` (the staker's own principal/rewards withdrawal included), not just the operator's own commission. This is a "permanent lock or non-recoverable loss of claim rights" for the staker's stake, caused entirely by the operator role without the operator ever gaining custody of the staker's funds — exactly the kind of impact called out as in-scope (owner/operator boundary violation, non-recoverable loss of withdrawal rights).

### Likelihood Explanation
Both actions required are trivial, permissionless, and cheap: (1) the operator calls `set_beneficiary_for_operator` to point at an address it controls, and (2) that address calls `aptos_account::set_allow_direct_coin_transfers(false)`. No governance, no privileged access, and no cooperation from the staker is needed. Any staking-contract operator can do this at will, at any time an unpaid commission distribution exists (which is a very common state since rewards/commissions accrue every epoch).

### Recommendation
- Have `set_beneficiary_for_operator` require the same registration check used in `vesting::set_beneficiary` (`assert_account_is_registered_for_apt`), and/or re-validate at distribution time that the resolved beneficiary can accept funds before crediting it.
- Decouple the staker's own distribution share from the operator/beneficiary's share so that a failure to pay one party cannot revert payouts to unrelated shareholders — e.g., process each shareholder's payout in its own sub-transaction/try-catch equivalent, or fall back to depositing into a claimable/escrow balance instead of aborting the whole loop when a `deposit_coins` call fails for one recipient.
- In particular, make `switch_operator` resilient to a stuck/malicious operator beneficiary (e.g., allow switching operators even if the old operator's commission distribution cannot complete, deferring that specific payout instead of blocking the whole staker migration).

### Proof of Concept
1. Staker creates a staking contract with `operator` via `create_staking_contract`, and the pool accrues rewards/commission over epochs.
2. `operator` calls `staking_contract::set_beneficiary_for_operator(operator, malicious_beneficiary)` (requires `operator_beneficiary_change_enabled` feature, already assumed live) — see [2](#0-1) .
3. `malicious_beneficiary` (any account the operator controls) calls `aptos_account::set_allow_direct_coin_transfers(malicious_beneficiary, false)` — see [4](#0-3) .
4. Staker calls `unlock_stake`/lets the lockup expire so their principal becomes withdrawable, and calls `staking_contract::distribute(staker, operator)`. Once the operator has any pending commission recorded in `distribution_pool`, the internal loop reaches the operator's entry, resolves `beneficiary_for_operator(operator) == malicious_beneficiary`, and `aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` — see [1](#0-0)  and [3](#0-2) . The whole `distribute` transaction reverts, and the staker receives nothing.
5. Staker tries `staking_contract::switch_operator(staker, operator, new_operator, ...)` to escape — this also calls `distribute_internal` first ( [5](#0-4) ) and aborts for the same reason, so the staker cannot leave the operator either.
6. As long as the operator keeps `malicious_beneficiary` opted out of direct transfers, the staker's already-unlocked stake and rewards are permanently unreachable through any framework-provided entry function.

*(Note: I was unable to fully trace `request_commission`/`request_commission_internal` in the final iteration due to a failed grep on function signatures, so it's not confirmed whether that specific entry point offers an alternate, unaffected recovery path; if it exists and bypasses `distribute_internal`'s full-loop payout, the severity assessment above may need revision. This should be verified before remediation.)*

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
