### Title
Windows job-object breakaway (`JOB_OBJECT_LIMIT_BREAKAWAY_OK`) combined with single-shot `taskkill` allows a CI job to spawn a self-respawning detached process that survives cancellation - (`File: helpers/process/job_windows.go`, `helpers/process/killer_windows.go`)

### Summary
GitLab Runner's Windows job object is explicitly configured with `JOB_OBJECT_LIMIT_BREAKAWAY_OK`, which permits any child process spawned by the CI job to detach itself from the job object (via `CREATE_BREAKAWAY_FROM_JOB`). Combined with the fact that `KillAndWait`/`ForceKill` only take a single, snapshot-based `taskkill /F /T` pass and rely on the original tracked process handle exiting to declare success, an attacker-controlled job script can spawn a watchdog process on receipt of `CTRL_BREAK_EVENT` that escapes both the process tree seen by `taskkill` and the job object's `KILL_ON_JOB_CLOSE` safety net, and respawn indefinitely.

### Finding Description
On the non-legacy path (`UseWindowsLegacyProcessStrategy=false`, the default), `taskTerminate` sends `CTRL_BREAK_EVENT` to the process group rather than forcibly killing it: [1](#0-0) . A job process is free to ignore/catch this signal (e.g. via a console control handler) and, before exiting, spawn a new process using `CREATE_BREAKAWAY_FROM_JOB`.

This is possible because the job object created for the job explicitly sets `JOB_OBJECT_LIMIT_BREAKAWAY_OK`: [2](#0-1) . That flag is a deliberate opt-in that allows a child process to escape job-object membership entirely, meaning it will not be terminated when the job handle is closed (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` only affects processes still associated with the job): [3](#0-2) .

If graceful termination doesn't complete in time, `ForceKill` performs exactly one `taskkill /F /T /PID <pid>` call (a point-in-time enumeration of the process tree) and then closes the job object handle: [4](#0-3) , [5](#0-4) . There is no repeated/looped verification that all descendants (especially breakaway ones) are actually gone.

`KillAndWait` orchestrates exactly one `Terminate()` and, if the graceful timeout elapses, exactly one `ForceKill()`, and considers the job "done" as soon as `waitCh` fires (i.e., as soon as the originally tracked `os.Process` handle exits): [6](#0-5) . Since the malicious watchdog is a detached, breakaway descendant, its lifecycle is decoupled from the tracked process's `Wait()` — the tracked process can exit normally (satisfying `waitCh`) while its detached respawn-child (and all its future generations, which are spawned after the single `taskkill` snapshot) continue running unmonitored and unkilled.

None of the existing mechanisms address this: the job object's kill-on-close is bypassed by design via `BREAKAWAY_OK`, and `taskkill /T` only reflects the process tree at one instant, so any process forked after that instant (i.e., each generation of the respawn loop) is never targeted.

### Impact Explanation
On a shared Windows runner (e.g. shell executor, a common Windows configuration since Docker isolation isn't available), an attacker-controlled job can leave behind an indefinitely respawning, detached process tree that continues consuming CPU/memory/handles on the host long after the job is cancelled or completes. This degrades capacity for other tenants' jobs scheduled on the same host and requires manual host intervention (e.g. reboot) to clear, since GitLab Runner never re-checks for or attempts to kill descendants outside the job object/tracked PID after the single `ForceKill` pass.

### Likelihood Explanation
Preconditions match GitLab Runner's default Windows configuration: `UseWindowsLegacyProcessStrategy=false` and `UseWindowsJobObject=true`. Exploitation requires only the ability to run a CI job with a script (any executor that runs arbitrary commands on the Windows host, e.g. shell executor) that: (1) installs a console control handler to detect `CTRL_BREAK_EVENT`, and (2) spawns a child with `CREATE_BREAKAWAY_FROM_JOB` and `CREATE_NEW_PROCESS_GROUP`, which is standard, unprivileged Win32 API usage available to any process. This is fully reproducible and repeatable — no race condition finesse is even required, since `BREAKAWAY_OK` guarantees the child is never part of the job regardless of timing.

### Recommendation
- Remove or restrict `JOB_OBJECT_LIMIT_BREAKAWAY_OK` from the job object created in `CreateJobObject` (`helpers/process/job_windows.go`) unless there's a specific documented need for it; without it, `CREATE_BREAKAWAY_FROM_JOB` requests fail and all descendants remain tied to the job's kill-on-close guarantee.
- If breakaway must remain supported for legitimate use cases, add a verification loop after `ForceKill`/`closeJobObject` that enumerates and force-kills any remaining processes rooted at the original PID (repeatedly, until none remain or a hard timeout is hit), rather than relying on a single `taskkill /T` snapshot and the tracked process's `Wait()` signal.
- Track job completion based on confirmed absence of the full descendant tree (via job object accounting APIs like `QueryInformationJobObject`/`JOBOBJECT_BASIC_PROCESS_ID_LIST`), not solely on the original process handle exiting.

### Proof of Concept
Go integration test outline (Windows only):
1. Build a small test helper binary `respawn_watchdog.exe` that:
   - Installs a `SetConsoleCtrlHandler` callback.
   - On receiving `CTRL_BREAK_EVENT`, spawns a copy of itself with `CREATE_BREAKAWAY_FROM_JOB | CREATE_NEW_PROCESS_GROUP` and then exits immediately (parent doesn't wait).
   - The new instance repeats the same behavior on receiving `CTRL_BREAK_EVENT`, or simply loops indefinitely and re-arms itself.
2. Start the helper via `process.NewOSCmd` with `UseWindowsJobObject: true`, `UseWindowsLegacyProcessStrategy: false`.
3. Call `KillWaiter.KillAndWait` with a short `gracefulKillTimeout`/`forceKillTimeout`.
4. After `KillAndWait` returns, wait a few seconds and enumerate running processes (e.g. via `tasklist` or `CreateToolhelp32Snapshot`) filtering for the watchdog binary name.
5. Assertion: no process matching the watchdog binary should remain. Expected (failing) result under the current code: at least one descendant process is still alive/respawning, proving the invariant "cancellation must be terminal" is violated.

func (kw *osKillWait) KillAndWait(command Commander, waitCh chan error) error {
	process := command.Process()
	if process == nil {
		return ErrProcessNotStarted
	}

	log := kw.logger.WithFields(logrus.Fields{
		"PID": process.Pid,
	})

	processKiller := newProcessKiller(log, command)
	processKiller.Terminate()

	select {
	case err := <-waitCh:
		return err
	case <-time.After(kw.gracefulKillTimeout):
		processKiller.ForceKill()

		select {
		case err := <-waitCh:
			return err
		case <-time.After(kw.forceKillTimeout):
			return &KillProcessError{pid: process.Pid}
		}
	}
}
