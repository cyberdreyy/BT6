### Title
APR0 withdraw bucket permanently deadlocks `stopEpoch` if the manager ever raises the APR while an APR=0 receipt is open - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`, but `apr0TotalPrincipal` is only cleared inside that same function, after the revert check. An unprivileged lender who opens a withdraw request while the epoch APR is 0 creates an accounting bucket that makes every subsequent `stopEpoch`/`stopEpochWithDuration` call revert as soon as the honest manager or CDO sets a non-zero APR. This mirrors the kernel bug class: a deferred execution path (the APR0 bucket settlement) can never run once a precondition flips, so the critical section (`stopEpoch`) deadlocks forever.

### Finding Description
- `requestWithdraw` routes a request into the APR0 bucket when `unscaledApr == 0`: `_requestWithdrawApr0` sets `apr0Users[_user].principal` and increments `apr0TotalPrincipal` (IdleCreditVault.sol:285-286, 567-577).
- At epoch end, `_stopEpoch` in `IdleCDOEpochVariant` calls `_strategy.prepareStopEpochWithApr0(_interest)` (IdleCDOEpochVariant.sol:362).
- Inside `prepareStopEpochWithApr0`, if `apr0TotalPrincipal != 0` and `unscaledApr != 0`, it reverts `NotAllowed()` (IdleCreditVault.sol:506-508). The only line that resets `apr0TotalPrincipal` is `apr0TotalPrincipal = 0` at line 540, unreachable once the revert triggers.
- `unscaledApr` is set by `setAprs`/`setAprsWithBuffer`/`setApr`, callable by the manager or the CDO (`_setScaledApr` during `stopEpochWithDuration`) (IdleCreditVault.sol:206-235, 225). Setting APR to a non-zero value is a legitimate, expected honest action.
- Because the revert happens inside the CDO's `_stopEpoch` transaction, the whole stop reverts atomically: `epochNumber` never increments, pending withdraws are never funded, and `_settleApr0` can never run (`_reqEpoch >= epochNumber` blocks settlement, IdleCreditVault.sol:553). There is no other code path that decrements `apr0TotalPrincipal` for an open bucket; `requestWithdraw` for a loss-adjusted receipt path doesn't apply, and `_claimDefaultedWithdrawRequest` only helps after a default finalization, which itself requires a `stopEpoch` failure path that is also gated.

The only escape is for the manager to set `unscaledApr` back to 0, run one full epoch cycle so `stopEpoch` can clear the bucket, and only then raise the APR. Meanwhile the attacker can keep the bucket open with new APR0 requests each epoch (as long as APR stays 0), or — critically — the moment the manager sets APR > 0, an attacker cannot close their own bucket either: `claimWithdrawRequest` reverts because `epochNumber <= lastWithdrawRequest[_user]` (IdleCreditVault.sol:326-328) since `epochNumber` cannot advance.

Broken invariant: epoch liveness / one-receipt-one-payout. The state machine enters a configuration (open APR0 bucket ∧ `unscaledApr > 0`) that no transaction can exit except an exact APR rollback by the manager.

### Impact Explanation
All funds in the credit vault are frozen: no user can claim withdraw requests (epoch number never advances), no new epoch can start, and active tranche holders cannot exit because their own `requestWithdraw` receipts would also be unclaimable. In the interim, deposits continue to be accepted during buffer periods with no path to yield or redemption. Quantified loss: temporary freezing of 100% of vault TVL for the duration of the deadlock, plus permanent freezing in any deployment where the manager cannot or does not restore `unscaledApr = 0` (e.g., an honest operator unaware of the interaction, or governance/timelock delay on APR changes).

### Likelihood Explanation
Triggering requires only: (1) a KYC-passing lender (in-scope attacker) calls `requestWithdraw` while the pool runs at `unscaledApr == 0` — a normal, low-cost action with a dust-size request sufficing; (2) the manager or CDO later sets any non-zero APR, an entirely honest and routine operation. No privileged misbehavior, oracle manipulation, or exotic token behavior is required. The deadlock persists until the manager deliberately rolls APR back to zero, which is a non-obvious remediation.

### Recommendation
Do not revert in `prepareStopEpochWithApr0` when `unscaledApr != 0`. Instead, settle the open APR0 bucket at the stored `apr0RateByEpoch`/0 rate for the new epoch (e.g., move `apr0TotalPrincipal` into each user's `settledPrincipal` at claim time, or treat the bucket as zero-interest and clear it), and/or allow `stopEpoch` to proceed while flagging APR0 receipts as settling with no new interest. Alternatively, block APR increases at the `setApr` layer while `apr0TotalPrincipal != 0` (turning the deadlock into an explicit, recoverable guard) and let pending APR0 receipts settle at the closing epoch regardless of the APR used for the next epoch.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
// assumes deployment harness from test/foundry/* providing:
//   cdoEpoch (IdleCDOEpochVariant), strategy (IdleCreditVault), idleCDO, manager

contract Apr0StopEpochDeadlockTest is Test {
    function testApr0BucketDeadlocksStopEpochAfterAprRaise() external {
        // --- Phase: running epoch with unscaledApr == 0 ---
        // attacker is a KYC-passed lender with a funded AA position
        vm.prank(attacker);
        idleCDO.depositAA(100e18);

        // manager starts epoch (honest); epoch runs with APR = 0
        // attacker requests a withdraw during the buffer/epoch while unscaledApr == 0
        vm.prank(attacker);
        cdoEpoch.requestWithdraw(50e18);        // -> strategy._requestWithdrawApr0
        assertGt(strategy.apr0TotalPrincipal(), 0);

        // --- Honest manager raises APR for the next epoch ---
        vm.prank(manager);
        strategy.setAprs(5e18, 5e18);           // unscaledApr != 0 now

        // --- Epoch end passes; every stopEpoch attempt reverts forever ---
        vm.warp(cdoEpoch.epochEndDate() + 1);
        vm.prank(manager);
        vm.expectRevert(NotAllowed.selector);   // prepareStopEpochWithApr0 reverts
        cdoEpoch.stopEpoch(0, 0);

        // attacker cannot self-clear the bucket: epochNumber never advances
        vm.prank(attacker);
        vm.expectRevert(NotAllowed.selector);   // epochNumber <= lastWithdrawRequest
        cdoEpoch.claimWithdrawRequest();

        // repeat: still deadlocked; only escape is manager restoring unscaledApr = 0
        vm.warp(block.timestamp + 365 days);
        vm.prank(manager);
        vm.expectRevert(NotAllowed.selector);
        cdoEpoch.stopEpoch(0, 0);
    }
}
```

Reproduce on a mainnet/state fork by deploying the standard `IdleCDOEpochVariant` + `IdleCreditVault` harness (as in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`), funding an attacker AA position, running one epoch at `unscaledApr == 0`, and following the transaction sequence above; every `stopEpoch` reverts at `IdleCreditVault.sol:506-508` once APR is raised.
