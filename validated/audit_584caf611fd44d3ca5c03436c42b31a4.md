### Title
Pending withdrawal receipts are haircut pro rata by `stopEpochWithDuration` losses even when the loss is fully absorbable by junior (BB) tranche TVL — protected "winner" claims are denied their full payout - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug class — "winner judgment based on a wrong comparison" — maps to how `IdleCreditVault.previewLossAdjustedWithdrawFunds` decides who bears a realized epoch loss. When the manager stops an epoch with a loss, the loss is split **pro rata** between pending withdrawal receipts and active LPs (`pendingLoss = _lossAmount * pendingBasis / totalBasis`). But pending receipts that originated from AA (senior) tranche holders would have been fully protected by the BB-first loss waterfall had they stayed active. The vault effectively judges every pending receipt a "loser" pro rata, even receipts that are "winners" under the tranche waterfall, and haircuts them via `lossRecoveryPriceByEpoch`.

### Finding Description
During the buffer period a user calls `requestWithdraw` on `IdleCDOEpochVariant`, which calls `IdleCreditVault.requestWithdraw`, burns `_principal` strategy tokens, mints a `_amount` receipt (principal + accrued interest) and adds it to `pendingWithdraws` (`contracts/strategies/idle/IdleCreditVault.sol:272-294`). If the epoch ends with a realized loss, `IdleCDOEpochVariant._stopEpoch` calls `previewLossAdjustedWithdrawFunds(_lossAmount)`, which splits the loss pro rata between `pendingBasis` and `activeBasis`, then `collectWithdrawFunds(pendingToFund)` stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` (`contracts/strategies/idle/IdleCreditVault.sol:411-460`). The user later claims `claimBasis * lossRecoveryPrice / 1e18` in `_claimLossAdjustedWithdrawRequest` (`contracts/strategies/idle/IdleCreditVault.sol:789-800`).

The invariant break: the normal waterfall (`_virtualPriceAux`/`_updateAccounting`) applies losses BB-first — seniors take zero loss until junior TVL is exhausted (`contracts/IdleCDOUsualVariant.sol:152-168`). A user who requested withdrawal of an AA position and is no longer in active NAV loses tranche identity, so a loss fully covered by BB capital still haircuts the pending AA receipt. The comment at `contracts/IdleCDOEpochVariant.sol:391-392` acknowledges pro-rata loss *across receipts*, but the pending-vs-active split itself bypasses the junior-first waterfall, so senior pending withdrawers fund losses that belong to active BB holders — the same "wrong winner judgment" class as `entitledShares > assets` in Carousel.

### Impact Explanation
Direct loss of user funds: an AA holder who queued a withdrawal before a losing epoch permanently loses `lossAmount * pendingBasis / totalBasis` (their share), even when `lossAmount < BB NAV` and active AA holders lose nothing. The shortfall accrues to active LPs (BB holders dodge part of the loss they should fully absorb), i.e. a value transfer between user classes, quantified by `pendingLoss` in `previewLossAdjustedWithdrawFunds`.

### Likelihood Explanation
Requires a `stopEpochWithDuration` call with `_lossAmount > 0` while pending withdrawals exist — i.e. a partial borrower shortfall (not full default, which uses the separate `finalizeDefaultRecovery` path) while withdrawal receipts are queued. The privileged caller (owner/manager) is honest per the threat model, so this triggers whenever a real mid-size loss occurs with a non-empty withdrawal queue — plausible in normal operation of a credit vault with junior capital smaller than total basis.

### Recommendation
Compute the pending-receipt haircut through the tranche waterfall rather than pro rata over total basis: first apply `_lossAmount` to active BB NAV (`_lossActiveBasis` split by `lastNAVAA/lastNAVBB`), and only assign a haircut to pending receipts for the residual loss exceeding junior coverage (or track per-tranche pending basis so pending AA receipts are only haircut after BB is exhausted). Alternatively, record each receipt's tranche class at `requestWithdraw` time and apply BB-first ordering inside `collectWithdrawFunds`.

### Proof of Concept
Foundry fork test sketch against the credit-vault fixtures in `test/foundry/IdleCreditVault.t.sol`:

```solidity
// Setup: deposit AA and BB so that BB NAV > future loss.
uint256 amountAA = 100_000 * ONE_SCALE;
uint256 amountBB = 50_000 * ONE_SCALE;
_depositWithUser(activeBB, amountBB, false);
_depositWithUser(pendingAAUser, amountAA, true);

// pendingAAUser queues a full withdrawal during the buffer period.
vm.prank(pendingAAUser);
uint256 pendingBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

// Run the epoch, then stop it with a loss strictly smaller than BB NAV.
_startEpochAndCheckPrices(0);
uint256 lossAmount = cdoEpoch.lastNAVBB() / 2; // loss < junior TVL
uint256 pendingToFund = strategy.previewLossAdjustedWithdrawFunds(lossAmount).pendingToFund;
// ... fund borrower, approve, then:
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(0, 0, duration, lossAmount);

// Active AA is untouched by the BB-first waterfall:
assertEq(cdoEpoch.virtualPrice(address(AAtranche)), ONE_TRANCHE, "active AA must not take loss");

// But the pending AA receipt is haircut pro rata:
uint256 price = strategy.lossRecoveryPriceByEpoch(strategy.epochNumber());
assertLt(price, 1e18, "pending AA receipt wrongly haircut");

uint256 balPre = underlying.balanceOf(pendingAAUser);
vm.prank(pendingAAUser);
cdoEpoch.claimWithdrawRequest();
uint256 payout = underlying.balanceOf(pendingAAUser) - balPre;
assertLt(payout, pendingBasis, "winner claim paid less than basis");
assertApproxEqAbs(payout, pendingBasis * price / 1e18, 1);
```

Note: I could not fully verify whether `stopEpochWithDuration` is reachable in every deployed configuration (it exists on `IdleCDOEpochVariant`), and the pro-rata pending/active split is partially documented in code comments — a sponsor may argue it is an accepted approximation, which is the main risk to this finding's validity.
