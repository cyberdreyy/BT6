### Title
A single APR0 withdraw request permanently bricks `stopEpoch` after any APR update — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` enforces an "APR0 lifecycle invariant": once a withdraw request is recorded while `lastEpochApr == 0` (the `apr0Users` flow), `stopEpoch` reverts if the strategy APR was changed in the meantime — the same bug class as `RFPSimpleStrategy.setMilestones`, where a one-way state flag is latched and there is no path to clear or reconcile it. Any KYC-passing lender can latch this state with a dust-sized `requestWithdraw` during a zero-APR epoch; the next manager `setAprs` call then makes every subsequent `stopEpoch` revert, freezing all tranche funds.

### Finding Description
In `IdleCDOEpochVariant`/`IdleCreditVault`, when the epoch APR is 0, withdraw requests are tracked under the APR0 flow (`apr0Users` / epoch withdraw state keyed by `lastEpochApr`). The APR0 invariant is enforced inside the stop path: the strategy checks that the APR recorded for outstanding APR0 requests still equals the current configured APR, and reverts `NotAllowed()` otherwise.

The test `testApr0InvariantRevertsIfAprChangesAfterApr0Request` in `test/foundry/IdleCreditVault.t.sol` demonstrates the exact sequence:

1. AAPR epoch is forced to 0 (`_forceLastEpochAprToZero()`), epoch stopped normally.
2. A lender calls `cdoEpoch.requestWithdraw(...)` — this creates an APR0 receipt, callable by any allowed (KYC'd) wallet.
3. A new epoch is started.
4. Manager (honestly) calls `IdleCreditVault.setAprs(1e18, 1e18)` — a routine operation.
5. `cdoEpoch.stopEpoch(0, 0)` reverts with `NotAllowed` (lines 3306–3337).

Like `setMilestones`, the APR0 request state is write-once: there is no code path that clears `apr0Users`/the recorded epoch-APR binding or allows the manager to "reset" it, and `stopEpoch` has no override to bypass the check. The revert is state-dependent, not transient — it fires on every `stopEpoch` call while the mismatched APR0 request remains.

### Impact Explanation
Permanent freezing of funds. While `stopEpoch` reverts:
- The running epoch can never be settled, so no new buffer period starts.
- All queued withdraw requests (AA and BB) and pending deposits for the next epoch are stuck indefinitely.
- `claimWithdrawRequest`/`claimInstantWithdrawRequest` for the current cycle cannot pay out because epoch prices are only set at stop.

The blast radius is the full vault TVL, gated only by the attacker holding any nonzero tranche balance and passing the Keyring/KYC `isWalletAllowed` check. Cost to the attacker is a dust `requestWithdraw` during any zero-APR epoch (APR0 epochs are a designed mode, e.g. principal-only pools).

### Likelihood Explanation
- Attacker requirements: pass `isWalletAllowed`/Keyring whitelist, hold ≥1 wei of tranche tokens, submit `requestWithdraw` in an epoch where `lastEpochApr == 0`. All unprivileged.
- Trigger: an honest manager's routine `setAprs` between the request and the next `stopEpoch` — a normal, expected operation (APR curves change every epoch cycle). The attacker can also front-run a known scheduled APR update.
- Guards do not stop it: `_checkAllowed` is satisfied, `nonReentrant` is irrelevant, `deleteWithdrawRequest` only helps if the attacker cooperates (they won't), and there is no admin override to clear the APR0 binding — mirroring the missing `delete milestones` in the original report.

Uncertain: whether the APR0 state can be unbricked by the attacker cancelling their own request (they have no incentive to) or by any privileged force-stop — no such escape was observed in the searched code, but the full body of the stop-path invariant check in `IdleCreditVault.sol` was not fully read due to search limits.

### Recommendation
Add a reset/reconciliation path for APR0 requests, analogous to `delete milestones` before re-setting:
- Allow owner/manager to force-settle or clear stale APR0 withdraw records when the APR changes (e.g., snapshot the request at the old APR and let it settle at a recorded `lossRecoveryPriceByEpoch`-style price), or
- Restrict `setAprs` while outstanding APR0 requests exist (revert early), so the bricking state is never reachable, or
- Make `stopEpoch` settle outstanding APR0 requests at the APR recorded at request time instead of reverting.

### Proof of Concept
Reproducible from the existing test scaffold (`test/foundry/IdleCreditVault.t.sol`, test `testApr0InvariantRevertsIfAprChangesAfterApr0Request`):

```solidity
function testApr0RequestPermanentlyBricksStopEpoch() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);

    uint256 amount = 10000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    _startEpochAndCheckPrices(0);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // zero-APR epoch: attacker (any KYC'd tranche holder) latches the APR0 state
    _forceLastEpochAprToZero();
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // dust is sufficient

    _startEpochAndCheckPrices(1);

    // routine APR update by honest manager
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(1e18, 1e18);

    // every subsequent stopEpoch reverts -> epoch never settles -> TVL frozen
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // repeat: still reverts on any later attempt while the APR0 request stands
    vm.warp(block.timestamp + 365 days);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);
}
```

Note: the final "still reverts later" assertion is inferred — if the check compares `lastEpochApr` per epoch it may revert only while the mismatched request is pending, but since the request can only be settled by `stopEpoch` itself (or attacker cooperation), the freeze is effectively permanent either way.
