### Title
Stale confirmations from removed multisig members are not purged and can count toward the confirmation threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` removes a departing member from `self.members` and deletes only the *requests that member itself created*, but it never scans `self.confirmations` to strip that member's prior confirmations from requests created by *other* members. Because `confirm()` (per the documented state machine) executes a request once the size of its confirmation set reaches `num_confirmations`, a confirmation recorded by a member who has since been removed remains counted, letting a request execute with fewer than `num_confirmations` currently-live members approving it. This mirrors the GitLab report's core failure mode: a principal that is no longer a recognized member of the group (multisig) still retains effective access/influence (a counted confirmation) without being visible or valid anymore.

### Finding Description
- `add_request` creates an empty `HashSet` in `self.confirmations` keyed by `request_id` [1](#0-0) .
- Per the documented state machine, `confirm` adds the caller to that `HashSet`, and once its size reaches `num_confirmations` the request is executed [2](#0-1) .
- `delete_member` only removes requests where `r.member == member` (i.e., requests *created* by the removed member) and clears `num_requests_pk`/`members` entries for that member, but does not iterate `self.confirmations` to remove the departing member's entries from confirmation sets of requests created by other members [3](#0-2) .
- `remove_request`/`delete_request` similarly only clean up confirmations tied to the request being deleted, not confirmations tied to a specific member across all requests [4](#0-3) .

As a result, the equality that should hold — *confirmations counted == confirmations from currently live members* — is broken: a member removed via `DeleteMember` still has a "ghost" confirmation baked into any pending request they confirmed before removal, exactly as GitLab's transferred-subgroup members retained invisible access without being current members.

### Impact Explanation
If a request is pending (not yet at threshold) and a confirming member is subsequently removed (e.g., because their key/account was compromised, or as part of routine key rotation), their stale confirmation still counts. This can let the remaining, fewer-than-`num_confirmations` live members push the request over the confirmation threshold and execute it — including sensitive actions such as `Transfer`, `FunctionCall`, `DeployContract`, or `AddKey`. This is a "multisig request executed below threshold" scenario, which the rules classify as Critical impact.

### Likelihood Explanation
This requires no attacker to be an owner or the multisig itself — any legitimate multisig operator who removes a member for standard security hygiene (e.g., an employee offboarding, suspected key compromise) is exposed, since existing pending requests silently retain that removed member's confirmation. No malicious redeploy, foundation action, or victim key is required; it is a natural sequence: confirm → remove member → confirm again to reach threshold with fewer live approvers.

### Recommendation
When removing a member in `delete_member`, iterate all entries in `self.confirmations` and strip the departing `MultisigMember` from every confirmation set (not just requests they authored), or alternatively delete/invalidate all pending requests whose confirmation set includes the removed member, forcing re-confirmation from currently valid members.

### Proof of Concept
1. Initialize a 2-of-3 multisig with members A, B, C.
2. A calls `add_request_and_confirm` for a sensitive `Transfer` request → confirmations = {A}.
3. Multisig executes `DeleteMember` to remove A (e.g., via a separate B+C-approved request), leaving members {B, C} with `num_confirmations = 2`.
4. B calls `confirm` on the original transfer request. Confirmation set becomes {A, B} (A never removed from that specific set) → size reaches 2 → request executes with only one currently-live member (B) actually approving it, bypassing the 2-of-2 (post-removal) intended threshold.

```rust
    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
```

```rust
    /// Removes request, removes confirmations and reduces num_requests_pk - used in delete, delete_key, and confirm
    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .unwrap_or_else(|| env::panic_str("Failed to remove existing element"));
        // decrement num_requests for original request signer
        let original_member = request_with_signer.member;
        let mut num_requests = self
            .num_requests_pk
            .get(&original_member.to_string())
            .unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_member.to_string(), &num_requests);
        // return request
        request_with_signer.request
    }
```

```markdown
### State machine

Per each request, multisig maintains next state machine:
 - `add_request` adds new request with empty list of confirmations.
 - `add_request_and_confirm` adds new request with 1 confirmation from the adding key.
 - `delete_request` deletes request and ends state machine.
 - `confirm` either adds new confirmation to list of confirmations or if there is more than `num_confirmations` confirmations with given call - switches to execution of request. `confirm` fails if request is already has been confirmed and already is executing which is determined if `confirmations` contain given `request_id`.
 - each step of execution, schedules a promise of given set of actions on `receiver_id` and puts a callback.
 - when callback executes, it checks if promise executed successfully: if no - stops executing the request and return failure. If yes - execute next transaction in the request if present.
```
