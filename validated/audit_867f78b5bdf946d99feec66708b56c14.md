### Title
Stale `IdleCreditVaultWriteOffEscrow` requests can be force-filled after tranche price appreciation, stealing lender upside - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
The clickjacking bug class — a victim's standing permission being abused by an attacker to perform an action that benefits the attacker at the victim's expense — maps onto `IdleCreditVaultWriteOffEscrow`. A lender creates a `createWriteOffRequest` that locks tranche tokens plus a fixed `underlyingsRequested` ask. That ask never expires and is not re-priced. If the tranche appreciates (interest accrual raises `virtualPrice`/`_tranchePrice`), any unprivileged fulfiller can call `fullfillWriteOffRequest` and buy the escrowed tranche tokens at the old, now-underpriced ask. The lender's only defense is `deleteWriteOffRequest`, which the fulfiller can front-run in the same block, giving the lender no safe exit once the request exists.

### Finding Description
`createWriteOffRequest` escrows the lender's tranche tokens and stores a static `underlyings` ask per user [1](#0-0) . `fullfillWriteOffRequest` is permissionless (`@dev this function can be called by any wallet`) and only requires `currentRequest.tranches == _tranches` and `_underlyings >= currentRequest.underlyings` [2](#0-1) . There is no expiry, no min-price oracle check against the current tranche price, and no epoch-scoped validity — the request stays fillable across epochs as long as it isn't deleted, since only `createWriteOffRequest` is gated on `isEpochRunning` while `fullfillWriteOffRequest` and `deleteWriteOffRequest` are not. When the tranche's underlying value exceeds the recorded ask, the fulfiller pockets the difference: they receive `currentRequest.tranches` worth more than the `_underlyings` paid. An attacker who observes a `deleteWriteOffRequest` transaction can front-run it with a fulfill, so the escrowed request functions as a free perpetual option on tranche appreciation.

### Impact Explanation
Direct theft of tranche price appreciation from lenders. For a request of `T` tranche tokens at ask `U`, once the tranche price rises so `T * price / 1e18 > U`, the attacker captures `T * price - U - exitFee` by fulfilling. Lenders who set an ask near par to negotiate a borrower write-off lose the spread whenever NAV grows faster than their ask — a quantified loss equal to the appreciation, bounded only by the request size.

### Likelihood Explanation
Medium. Requires a stale request plus tranche appreciation; both are routine over multi-epoch lifetimes since requests persist indefinitely. Attacker is any EOA (no KYC needed to fulfill — confirmed by the repo's own tests allowing non-Keyring fulfillers), and the capital cost is just the ask amount, repaid immediately in tranche tokens of higher value.

### Recommendation
Add a validity constraint to `fullfillWriteOffRequest`: either an expiry epoch, a check that `_underlyings` is within a band of the current `cdoEpoch` tranche price (`_trancheToUnderlyings(_tranches)`), or restrict fulfillment to the recorded borrower so third-party sniping of stale asks isn't possible. Alternatively require requests to be re-confirmed each epoch.

```solidity
// test/foundry/WriteOffEscrowStaleFill.t.sol
function testStaleRequestFilledAfterAppreciation() external {
    // 1. LP creates request: 10_000 tranches for 10_000 USDC while epoch runs
    vm.prank(LP);
    escrow.createWriteOffRequest(10_000e18, 10_000e6);

    // 2. Epoch ends, interest accrues; tranche price rises so the same
    //    tranches are now worth e.g. 10_500 USDC (simulate via stopEpoch/startEpoch
    //    with borrower repayment including interest, or warp + mock virtualPrice).
    _stopAndRestartEpochWithInterest(); // helper: repay principal+APR

    uint256 trancheValueNow = cdoEpoch.contractValue(); // price * tranches > 10_000e6
    // tranche value now exceeds the stale ask
    assertGt(_trancheToUnderlyings(10_000e18), 10_000e6);

    // 3. Attacker (any EOA, no KYC) front-runs LP's deleteWriteOffRequest
    address attacker = makeAddr("attacker");
    deal(address(underlying), attacker, 10_000e6);
    vm.startPrank(attacker);
    underlying.approve(address(escrow), 10_000e6);
    escrow.fullfillWriteOffRequest(LP, 10_000e18, 10_000e6);
    vm.stopPrank();

    // 4. Attacker holds tranche tokens redeemable for ~10_500 USDC;
    //    paid only 10_000e6 -> ~500 USDC stolen appreciation (minus 0.1% fee).
    assertEq(tranche.balanceOf(attacker), 10_000e18);
}
```

```text
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
  }
```

```text
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }
```
