Confirmed root cause found — this is a genuine analog of the "excess ETH not refunded" bug class, but inverted into a **supply-inflation / mispayment bug**: the withdrawal amount that the execution layer is instructed to pay is not clamped to the payer's actual balance, while the corresponding on-chain balance deduction *is* clamped.

### Title
Builder pending withdrawal pays out uncapped requested amount while builder balance is only decreased by the capped amount, minting Gwei not backed by the builder's balance - (`specs/gloas/beacon-chain.md`)

### Summary
`get_builder_withdrawals` builds a `Withdrawal` entry using the *requested* `withdrawal.amount` from `state.builder_pending_withdrawals`, without capping it to the builder's current balance. That same uncapped `Withdrawal.amount` becomes part of `state.payload_expected_withdrawals`, which the execution layer is required to honor by crediting `fee_recipient` with exactly that amount. Meanwhile `apply_withdrawals` deducts only `min(withdrawal.amount, builder_balance)` from `state.builders[builder_index].balance`. When the requested amount exceeds the builder's balance, the fee recipient is paid the full requested amount on the EL side, but the builder's balance is only reduced by its (smaller) actual balance — the difference is Gwei created out of thin air, paid to the (non-owner) fee recipient.

### Finding Description [1](#0-0) 
`get_builder_withdrawals` appends a `Withdrawal(..., amount=withdrawal.amount)` directly from the pending withdrawal's requested amount — no `min()` with `state.builders[builder_index].balance` is applied here. [2](#0-1) 
`apply_withdrawals`, however, deducts `state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)` — i.e., the CL-side balance decrease is saturated/capped at the builder's actual balance.

The `Withdrawal` list (`state.payload_expected_withdrawals`) generated by `get_expected_withdrawals` is the authoritative list the execution layer must apply verbatim (mint/credit the stated `amount` to `address`) — this is explicitly how Capella/Gloas withdrawals work (the EL "mints the full committed amount regardless" per the spec's own note about saturation risk): [3](#0-2) 

So for a builder with insufficient balance, the recorded `Withdrawal.amount` (paid on EL) and the CL-side balance deduction diverge. This is corroborated by the repo's own test, which documents this exact behavior as "expected": [4](#0-3) 
Here `withdrawal_amount = 5 ETH`, `available_balance = 1 ETH`; the test explicitly asserts `withdrawal_amounts_builders={builder_index: withdrawal_amount}` (i.e., the payload commits to paying 5 ETH) while `builder_balances={builder_index: 0}` (only 1 ETH was actually debited).

The helper test-assertion code even documents the invariant as "by design": [5](#0-4) 
`expected_deduction = min(total_amount, pre_balance)` while the `Withdrawal.amount` used for the EL commitment remains the uncapped `total_amount`.

### Impact Explanation
This breaks the fundamental equality that a withdrawal payment on the execution layer must be exactly backed by an equal decrease of the corresponding balance on the consensus layer. Any beacon-chain-triggered withdrawal is supposed to be a 1:1 transfer of custody from CL balance to an EL account — not a mint. Here, the EL is committed (via `execution_payload_bid`/envelope machinery that must match `payload_expected_withdrawals`) to credit `fee_recipient` the full requested `amount`, while the builder's own balance is only reduced by what it actually had. The difference is Gwei created from nothing and paid to a `fee_recipient` (a non-owner, arbitrary address controlled by whoever submitted the withdrawal request), inflating total ETH supply. This matches the "Gwei created ... paid to a non-owner" Critical-impact class in the rules.

### Likelihood Explanation
This is reachable by any builder (or protocol path) that creates a `BuilderPendingWithdrawal` (e.g., via `process_builder_exit_request` or normal builder withdrawal flows) whose requested `amount` exceeds the builder's `balance` at the time of processing — a builder can trivially engineer this (e.g., spend down balance via other means, or simply request withdrawal of more than they hold, since nothing at withdrawal-request time enforces `amount <= balance`, only `apply_withdrawals` clamps the *balance* side). It requires no coalition, no client bug, no malicious peer — it is fully within the spec's own state-transition logic and reachable by a single unprivileged builder acting alone (or even honestly, if balance changes between the request and processing, e.g. due to slashing/other withdrawals draining the balance first, since `builder_pending_withdrawals` amounts are fixed at request time).

### Recommendation
Cap the `Withdrawal.amount` emitted by `get_builder_withdrawals` (and any other builder-balance-based withdrawal amount) to `min(withdrawal.amount, state.builders[builder_index].balance)` at the point the `Withdrawal` object is constructed, so the amount committed to the execution layer for minting exactly matches the amount actually deducted from the builder's balance:

### Proof of Concept
1. A builder's `state.builder_pending_withdrawals` queue contains an entry with `builder_index = B`, `amount = 5_000_000_000` (5 ETH), `fee_recipient = F`.
2. Prior to this withdrawal being processed, `state.builders[B].balance` drops to `1_000_000_000` (1 ETH) — e.g., through prior withdrawals processed earlier in the same sweep, or because nothing prevents the requested amount at enqueue-time from exceeding the balance at processing time.
3. `process_withdrawals(state)` → `get_expected_withdrawals(state)` → `get_builder_withdrawals` emits `Withdrawal(validator_index=convert(B), address=F, amount=5_000_000_000)` (uncapped).
4. `apply_withdrawals` executes `state.builders[B].balance -= min(5_000_000_000, 1_000_000_000)` → new balance `0`.
5. `state.payload_expected_withdrawals` now commits the execution layer to crediting `F` with `5_000_000_000` Gwei, while only `1_000_000_000` Gwei was actually removed from the builder's on-chain balance — `4_000_000_000` Gwei (4 ETH) has been created and paid to `F` with no corresponding debit anywhere in the system, confirmed directly by the repository's own test `test_builder_withdrawal_insufficient_balance` [6](#0-5) , which asserts exactly this mismatched outcome (`withdrawal_amounts_builders={builder_index: withdrawal_amount}` i.e. 5 ETH paid, vs. `builder_balances={builder_index: 0}` i.e. only 1 ETH deducted).

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
