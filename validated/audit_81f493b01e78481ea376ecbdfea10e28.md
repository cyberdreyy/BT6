### Title
Stale confirmations from deleted multisig members are counted toward the confirmation threshold, allowing requests to execute below the required live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` in the generalized-member multisig only purges confirmations for requests that the deleted member *created* (`r.member == member`), not confirmations that member cast on *other* pending requests. `confirm()` counts `HashSet<String>` entries against `num_confirmations` without checking that each entry still belongs to a current member, so a removed member's stale confirmation continues to count toward execution.

### Finding Description
`confirm()` compares the size of the request's `confirmations` set (plus the new confirmer) directly against `self.num_confirmations` and, once satisfied, calls `execute_request`: [1](#0-0) 

Membership removal is handled by `delete_member`, which only cleans up requests that the removed member originally *submitted* (matched via `r.member == member`, i.e. the request signer field), and only clears `num_requests_pk` for that member: [2](#0-1) 

It never scans `self.confirmations` (the per-request `HashSet<String>` of confirmer identities) to strip entries belonging to the member being removed on requests *created by other members*. Since `confirmations` is a raw `HashSet<String>` keyed on `member.to_string()` with no cross-reference back to `self.members`, once a member is deleted, any confirmation they previously cast on a still-open request (created by someone else) remains in that set forever, and is never revalidated against current membership at `confirm()` time: [3](#0-2) 

This breaks the intended equality: `confirmations counted == confirmations from currently-live members`. After removal, `confirmations counted > confirmations from currently-live members`, so a request can reach `num_confirmations` and execute (e.g. `Transfer`, `AddKey`, `FunctionCall`) using fewer live confirmers than the threshold mandates.

This is the direct analog of the reported bug class: `TokensController.checkApproval` trusted a stale/misattributed approval state (NFT `getApproved`) without verifying the actual current authorized party (the true owner), letting an unauthorized listing be created. Here, the multisig trusts a stale confirmation entry without verifying the actual current authorized party (a live member), letting an under-threshold execution occur.

### Impact Explanation
This maps to the Critical impact category explicitly listed in scope: "a multisig request executed below threshold." Confirmations are the sole security binding enforcing the K-of-N custody scheme over the multisig account's NEAR balance and keys; if that binding can be violated, funds can be transferred, keys added, or contracts deployed by fewer independent parties than configured, undermining the entire threshold guarantee.

### Likelihood Explanation
Requires no privileged capability beyond being (at some point) a legitimate multisig member — i.e., a normal, in-scope member workflow: (1) member B confirms a pending request created by member A but the request stays open (not yet at threshold), (2) the multisig later executes a `DeleteMember` request removing B (e.g., through normal key rotation), (3) the original request A created is still open with B's stale confirmation counted, (4) fewer than `num_confirmations` live members are needed to push the request over threshold because B's ghost confirmation is already banked. This is a realistic operational sequence (member rotation while requests are outstanding) rather than a contrived edge case, making likelihood moderate-to-high for any organization that rotates multisig membership without manually clearing/re-confirming all outstanding requests.

### Recommendation
When deleting a member in `delete_member`, iterate over all entries in `self.confirmations` (not just requests created by the removed member) and remove the removed member's identity string from every confirmation set, or alternatively make `confirm()` filter/re-validate the counted confirmations against `self.members` before comparing to `num_confirmations`. The safer fix is to recompute the "live" confirmation count at threshold-check time by intersecting the stored confirmer set with current `self.members`, ensuring removed members can never contribute to reaching the threshold.

### Proof of Concept
1. Deploy `MultiSigContract::new` with members `{A, B, C}` and `num_confirmations = 2`.
2. A calls `add_request(...)` creating request `R` (e.g., `Transfer` to an attacker-controlled account) — `R.member = A`, `confirmations[R] = {}`.
3. B calls `confirm(R)` → `confirmations[R] = {B}` (1 < 2, not yet executed), per `confirm()` logic: [4](#0-3) 
4. The group later executes a separate, properly-confirmed `DeleteMember { member: B }` request. `delete_member` only purges requests where `r.member == B` (i.e., requests B created); `R` was created by A, so its `confirmations[R] = {B}` entry is untouched: [5](#0-4) 
5. B's access key/account is now removed from `self.members`, so B is no longer a live, authorized confirmer of anything.
6. A (or anyone able to call `confirm`) calls `confirm(R)` again as a genuinely live member (e.g., A itself, if `assert_valid_request` only requires the caller be a current member and does not require a *different* confirmer): `confirmations.len() (1, from stale B) + 1 (new live confirmer) = 2 >= num_confirmations (2)` → `execute_request(R)` fires the `Transfer`.
7. The transfer executes having only ever received one genuinely live confirmation (A's) in addition to a ghost confirmation from a removed member B — i.e., the request executed below the real live-member threshold of 2, moving NEAR out of the account without the required number of currently authorized approvers.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
