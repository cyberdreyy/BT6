### Title
Unauthenticated `reason_code`/`response_data` in `BlockRejection` lets any signer forge another signer's rejection reason - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection::hash()` — the payload that `BlockRejection.signature` is computed over — covers only `signer_signature_hash` and `chain_id`. It does **not** cover `reason`, `reason_code`, or `response_data` (which includes `reject_reason`, `failed_txid`, and the tenure-extend timestamps). Any signer who observes a peer's genuine, validly-signed `BlockRejection` for a given block (via public StackerDB gossip) can re-publish a new `BlockRejection` message — under their own slot, using their own StackerDB transport key — that reuses the peer's untouched signature but swaps in an attacker-chosen `reason_code`/`response_data`. `stacks-signer/src/v0/signer.rs::handle_block_rejection` authenticates the message purely by recovering the public key from this signature (`rejection.recover_public_key()`), and never cross-checks that recovered identity against the StackerDB slot owner that actually posted the chunk. This lets the attacker attribute an arbitrary rejection reason to the victim signer's weight.

### Finding Description
`BlockRejection::hash()`: [1](#0-0) 

only signs `self.signer_signature_hash` (plus a fixed domain separator and `chain_id`). The struct itself carries much more state that is *not* included in that hash: [2](#0-1) 

`verify()`/`recover_public_key()` only check the signature against this narrow `hash()`: [3](#0-2) 

On the signer side, incoming `SignerMessage`s are first gated by the StackerDB slot owner's identity (`signer_public_key` from the chunk), then dispatched by message type: [4](#0-3) 

But `handle_block_rejection` throws away that slot-derived identity and re-derives an entirely separate `signer_address` from the embedded, narrowly-scoped signature, with no check that it matches the slot owner: [5](#0-4) 

That `signer_address` (attributed to whoever's signature is embedded, not to whoever posted the chunk) is what gets persisted and weighted: [6](#0-5) [7](#0-6) 

The recorded `reject_reason` (taken straight from the attacker-controlled, unsigned `response_data`) is later used to compute the `ReorgNotAllowed` blocking-minority weight that flips miner status: [8](#0-7) [9](#0-8) 

By contrast, the node-side listener (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`) *does* cross-check the recovered pubkey against the StackerDB slot's known signer entry before trusting a rejection: [10](#0-9) 

That mitigating check is present on the node side but is missing from the signer-to-signer path in `stacks-signer/src/v0/signer.rs::handle_block_rejection`. This is the analog to the reported bug class: an attacker-controllable field (`manager` in the report; `reason_code`/`response_data` here) is trusted in place of the properly authenticated identity/data (`msg.sender` in the report; the full signed payload here), producing a mismatch between what a peer actually attested to and what gets counted against them.

### Impact Explanation
This breaks the equality between "what a signer actually rejected/attested to" and "what is recorded and weighted as that signer's rejection." Concretely:
- An attacker who holds any single valid signer slot can, upon seeing signer B reject a proposed block for any reason (e.g. a transient `ConnectivityIssues` rejection), immediately rebroadcast a `BlockRejection` for the same `signer_signature_hash` with B's stolen (still-valid) signature but `reason_code = RejectReasonPrefix::ReorgNotAllowed` (or a `ProblematicTransaction` flag on an arbitrary `failed_txid`).
- This is stored under B's identity via `add_block_rejection_signer_addr`/`store_and_process_block_rejection`, and its weight is added into `total_reorg_reject_weight` used to decide `SortitionMinerStatus::InvalidatedBeforeFirstBlock`.
- Combining a handful of forged reason attributions with genuinely rejecting signers can push the "> 30% weight `ReorgNotAllowed`" threshold and cause the miner to be wrongly invalidated — a liveness/safety-relevant consequence achievable without compromising any signer's private key and without a majority of signers, only a single attacker-controlled slot plus normal gossip visibility of a peer's rejection.

### Likelihood Explanation
High feasibility: the attacker needs no majority and no other signer's key — only (a) their own signer key to post to StackerDB, and (b) visibility of a peer's already-published `BlockRejection` for the same block, which is inherently public via StackerDB gossip. Since `BlockRejection.reason_code`/`response_data` are plain, unsigned struct fields, forging a new message with the desired values plus the copied signature/`signer_signature_hash` requires no cryptography beyond re-serializing the message and signing the StackerDB chunk transport layer with the attacker's own key.

### Recommendation
Include `reason_code` and all of `response_data` (or at minimum the fields consumed for consensus decisions, `reject_reason`/`failed_txid`) in the `BlockRejection::hash()` payload that is actually signed, so the signature authenticates the full rejection content, not just `signer_signature_hash`. Additionally, in `stacks-signer/src/v0/signer.rs::handle_block_response`/`handle_block_rejection` (and the analogous accepted-signature path), cross-check that the address recovered from the embedded message signature matches the StackerDB slot owner's identity that was already validated in the outer message loop, mirroring the check already present in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`.

### Proof of Concept
1. Signer A (attacker) is a legitimate, single-slot member of the current signer set.
2. Signer B genuinely rejects a proposed block for reason `RejectReason::ConnectivityIssues(...)` and publishes a signed `BlockRejection { signer_signature_hash: H, reason_code: ConnectivityIssues, signature: S, response_data: {...}, ... }` to its own StackerDB slot. `S` is valid because `BlockRejection::hash()` only commits to `H` and `chain_id`.
3. Signer A observes this message via StackerDB gossip (all messages are public reads).
4. Signer A constructs a new `BlockRejection` reusing `signer_signature_hash: H` and `signature: S` (unchanged, still a valid signature over `hash()`), but sets `reason_code = RejectCode::ValidationFailed(ValidateRejectCode::???)` mapped to `RejectReasonPrefix::ReorgNotAllowed` and arbitrary `response_data`.
5. Signer A signs the StackerDB chunk with its own key and writes this crafted message to its own slot.
6. Any signer processing the event runs `handle_block_response` → `handle_block_rejection`, which calls `rejection.recover_public_key()` on `S`, recovering **B's** public key (since the signed payload — just `H`+chain id — is unchanged), and stores/weights this forged `ReorgNotAllowed` rejection under B's `signer_address`, even though B never rejected for that reason.
7. Repeating this for enough already-rejecting peers can push the recorded `ReorgNotAllowed` weight over the 30% blocking-minority threshold, triggering `sortition_state.cur_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock` on a fabricated basis.

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }

    /// Compute the rejection weight for the given reject code, given a list of signatures
    fn compute_reject_code_signing_weight<'a>(
        &self,
        addrs: impl Iterator<Item = &'a (StacksAddress, RejectReasonPrefix)>,
        reject_code: RejectReasonPrefix,
    ) -> u32 {
        addrs.filter(|(_, code)| *code == reject_code).fold(
            0u32,
            |signing_weight, (stacker_address, _)| {
                let stacker_weight = self.signer_weights.get(stacker_address).unwrap_or(&0);
                signing_weight.saturating_add(*stacker_weight)
            },
        )
    }

    fn handle_block_rejection(
        &mut self,
        rejection: &BlockRejection,

    ) {
        debug!("{self}: Received a block-reject signature: {rejection:?}");

        let block_hash = &rejection.signer_signature_hash;
        let signature = &rejection.signature;

        // recover public key
        let Ok(public_key) = rejection.recover_public_key() else {

            return;
