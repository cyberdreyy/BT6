### Title
Stale per-epoch instant-withdraw records enable double payout and inflated recovery reserve after default - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug class is an accounting invariant updated in every flow except one: `release()` restored `selfStakes`/`communityStakes` amounts without restoring `userTotalStaked`, causing underflow and permanent loss. The analog in `IdleCreditVault` is `claimInstantWithdrawRequest()`: it clears the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch records `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`, and never decrements them on claim. If the borrower defaults in the same epoch while another instant request remains unfunded, the stale records are counted again in `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, and the already-paid user can claim a second time through `_claimDefaultedInstantWithdrawRequest()`.

### Finding Description
`requestInstantWithdraw()` records three pieces of state for the same receipt: the aggregate `instantWithdrawsRequests[_user]`, the per-user-per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the epoch aggregate `instantWithdrawClaimsByEpoch[currentEpoch]` (lines 366-372). `collectInstantWithdrawFunds()` only decrements `pendingInstantWithdraws` (line 401); it does not touch the per-epoch maps. `claimInstantWithdrawRequest()` pays the user, burns the receipt tokens, and zeroes only the aggregate `instantWithdrawsRequests[_user]` (lines 387-392). The per-epoch records are left permanently nonzero.

Those stale records are read again by the default-recovery flow:

- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the haircut basis whenever `pendingInstantWithdraws != 0` (lines 644-649). It therefore includes instant receipts that were already fully funded *and already claimed*.
- `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstant` as "already-held" reserve (lines 716-723). Already-claimed amounts inflate `instantBasis`, so underlying that left the strategy is counted as reserve backing, pushing `defaultRecoveryPrice` above what real funds support.
- `_claimDefaultedInstantWithdrawRequest()` reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` and pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` from `defaultRecoveryReserve` (lines 842-856). Because the per-epoch entry was never cleared, a user who already claimed at par is paid a second time.

This is exactly the `release()` pattern: one path mutates the detailed record while the sibling total (`instantWithdrawsRequests`, and implicitly the funded/unfunded split) is updated without keeping the per-epoch mirrors in sync, breaking the invariant `instantWithdrawClaimsByEpoch[e] == sum of unclaimed epoch-e instant receipts`.

### Impact Explanation
Direct theft from the default recovery reserve. After finalization, the attacker calls `claimWithdrawRequest`/`claimInstantWithdrawRequest` and `_claimDefaultedInstantWithdrawRequest` pays `claimedAmount * defaultRecoveryPrice` a second time for funds already withdrawn at par. Additionally, the phantom prefunded reserve inflates `defaultRecoveryPrice`, so every defaulted receipt (normal pending withdraws and unfunded instant receipts) is overpaid relative to real backing; since the reserve is fixed, later claimants (honest users) absorb the shortfall — the last claimants' transfers underflow/revert or pay nothing, mirroring the original finding's lost-funds outcome. Magnitude: up to the full value of same-epoch instant receipts that were claimed before default.

### Likelihood Explanation
Requires a specific but legitimate sequence inside one epoch in instant mode:

1. Epoch running, instant withdrawals enabled (`setInstantWithdrawParams`).
2. Attacker (KYC-passed lender) requests an instant withdraw; CDO collects funds via `collectInstantWithdrawFunds` and the attacker claims at par — per-epoch records remain stale.
3. Another user's instant request remains unfunded, keeping `pendingInstantWithdraws != 0` (partial collection is explicitly supported: `collectInstantWithdrawFunds` takes a partial `_amount`, and `defaultPendingClaimBasis`'s comment describes partially covered instant queues).
4. Borrower defaults within the same epoch; `finalizeDefaultRecovery` runs while `epochNumber` is unchanged. `defaultInstantWithdrawsFinalized = true`, so the attacker's stale per-epoch receipt is claimable again.

No privileged actor misbehaves; the attacker only sequences ordinary user calls around the honest default flow. The only mitigating factor is that the unfunded remainder must coexist in the same epoch, which is precisely the scenario the accounting was built for.

### Recommendation
Clear the per-epoch mirrors when an instant receipt is claimed. In `claimInstantWithdrawRequest()`, record the request epoch at claim time (or iterate) and zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, keeping them consistent with `instantWithdrawsRequests[_user]` — the same fix pattern as updating `userTotalStaked` inside `release()`. Alternatively, derive `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` from currently-unclaimed balances rather than cumulative epoch records.

### Proof of Concept
Foundry fork test in `test/foundry/IdleCreditVault.t.sol` style:

```solidity
function testInstantClaimStaleEpochRecordDoublePays() external {
    // Epoch running with instant withdraws enabled
    _stopCurrentEpochWithApr(10e18);
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    address attacker = makeAddr('attacker');
    address victim = makeAddr('victim');
    uint256 tranchesA = _depositWithUser(attacker, 50e6);
    uint256 tranchesV = _depositWithUser(victim, 50e6);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // Both request instant withdraws
    _requestInstantWithdrawWithUser(attacker, tranchesA);
    _requestInstantWithdrawWithUser(victim, tranchesV);

    // CDO collects only attacker's share; victim stays unfunded
    // => pendingInstantWithdraws == victimAmount != 0
    // attacker claims at par: instantWithdrawsRequests[attacker] = 0,
    // but instantWithdrawsRequestsByEpoch[attacker][epoch] and
    // instantWithdrawClaimsByEpoch[epoch] are NOT cleared
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();

    // Borrower defaults in the same epoch; finalizeDefaultRecovery runs
    _defaultAndFinalize(); // sets defaultInstantWithdrawsFinalized = true

    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    // Attacker paid a second time: claimBasis = stale instantWithdrawsRequestsByEpoch
    assertGt(underlying.balanceOf(attacker) - balPre, 0, 'double payout');

    // Recovery reserve is now short by the double-paid amount; victim's
    // defaulted claim reverts or pays less than claimBasis * defaultRecoveryPrice
}
```

Key assertions: after the legitimate claim, `strategy.instantWithdrawsRequestsByEpoch(attacker, epoch) != 0` and `instantWithdrawClaimsByEpoch(epoch)` still includes the paid amount, proving `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` double-count it.
