### Title
Denial of Service in Escrow Withdrawal/Cancellation for Zero-Transfer Reverting Tokens - ([File: contracts/EscrowDst.sol, contracts/EscrowSrc.sol, contracts/BaseEscrow.sol])

### Summary
The protocol's escrow contracts use `SafeERC20.safeTransfer` (via `_uniTransfer`) to distribute tokens during withdrawal, cancellation, and fund rescue. Several tokens (e.g., LEND, ZRX) revert on zero-value transfers. If any of these operations result in a zero-amount transfer, the entire transaction will revert. This can lead to a Denial of Service (DoS) where users are unable to complete swaps, reclaim safety deposits, or rescue stuck funds. [1](#0-0) 

### Finding Description
In `EscrowDst.sol`, the `_withdraw` function calculates the remaining amount for the maker after deducting integrator and protocol fees. If the fees equal the total amount, the `amount` variable becomes zero. The contract then calls `_uniTransfer` with this zero amount. [2](#0-1) 

Similarly, in `EscrowSrc.sol`, `_withdrawTo` and `_cancel` transfer the `immutables.amount` without checking if it is zero. [3](#0-2) [4](#0-3) 

The `BaseEscrow.rescueFunds` function also lacks a zero-check, allowing a caller to trigger a revert by passing `amount = 0` for a zero-transfer-reverting token. [5](#0-4) 

If the token used in the swap is one that reverts on zero transfers, these functions will become unusable whenever the transfer amount is zero, even if the primary purpose of the call (e.g., releasing a safety deposit or marking a swap as complete) is valid.

### Impact Explanation
This is a **High** impact vulnerability. For tokens that revert on zero transfers:
1.  **Temporary Freezing of Funds**: A Resolver's safety deposit (native ETH) could be locked in the escrow if the `withdraw` or `cancel` call reverts due to a zero-token transfer. The Resolver would be unable to reclaim their deposit even after fulfilling their obligations or during the cancellation phase.
2.  **Protocol Malfunction**: Swaps where the taker amount is fully consumed by fees will fail to settle on the destination chain, breaking the atomic swap invariant.

### Likelihood Explanation
The likelihood is **Medium**. While many modern tokens handle zero transfers, several well-known tokens still revert. The scenario where fees equal the total amount is possible, especially in partial fills or small-value swaps where fixed fees might dominate.

### Recommendation
Add a non-zero check before calling `safeTransfer` or `_uniTransfer` for ERC20 tokens.

```solidity
// Example for EscrowDst.sol
uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
if (amount > 0) {
    _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
}
```

### Proof of Concept
1.  Deploy a swap using a token that reverts on zero transfers (e.g., a mock token that reverts if `amount == 0`).
2.  Set `immutables.amount` to a value (e.g., 100) and set fees such that `integratorFeeAmount + protocolFeeAmount = 100`.
3.  Attempt to call `EscrowDst.withdraw`.
4.  The call to `_uniTransfer(token, maker, 0)` will trigger `safeTransfer(maker, 0)`, which reverts.
5.  The Resolver is unable to complete the withdrawal and cannot receive the `safetyDeposit` reward, despite the swap logic being otherwise correct.
