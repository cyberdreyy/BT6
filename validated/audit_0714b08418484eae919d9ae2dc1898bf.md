### Title
Permanent freeze of epoch settlement and LP withdrawals via unprivileged ERC4626 liquidity exhaustion on the programmable-borrower stop hook - (contracts/strategies/idle/ProgrammableBorrower.sol:246-252)

### Summary
The external report's bug class is "a restricted dispatcher validates the operation name but executes unvalidated inputs in a privileged scope." The analog in this codebase is the stop-epoch path in `IdleCDOEpochVariant._stopEpoch`, which unconditionally delegates liquidity provisioning to `IProgrammableBorrower.onStopEpoch`. That hook performs a raw `vault.withdraw(shortfall, …)` against an external ERC4626 vault whose liquidity state is controlled by unprivileged third parties (any borrower/depositor of that vault). When the withdrawal reverts, `StopEpochVaultLiquidityUnavailable` is thrown and the revert bubbles through `stopEpoch`, meaning the epoch can never be stopped and no default is ever declared. The code intentionally bubbles this revert so "transient" failures can be retried (line 397 comment in `IdleCDOEpochVariant.sol`), but a sustained liquidity drain turns the retry path into a permanent freeze of all pool funds.

### Finding Description
In `ProgrammableBorrower.onStopEpoch` (ProgrammableBorrower.sol:231-253), when the required cash exceeds the on-hand balance, the contract calls `vault.withdraw(shortfall, address(this), address(this))` inside a try/catch that reverts `StopEpochVaultLiquidityUnavailable` on any failure:

```solidity
try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) { … }
catch { revert StopEpochVaultLiquidityUnavailable(); }
```

`IdleCDOEpochVariant._stopEpoch` (IdleCDOEpochVariant.sol:395-404) lets that revert propagate — the borrower default handler is only reached if `onStopEpoch` returns `false` (only for the close-pool ledger check at line 235) or if the subsequent `getFundsFromBorrower` transfer fails. There is no path that treats a *reverting* vault withdrawal as a default:

```solidity
if (!IProgrammableBorrower(_borrower()).onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)) {
    _handleBorrowerDefault(_amountToPullFromBorrower + _pendingWithdraws);
    return;
}
```

For an ERC4626 lending-style vault (e.g., a Morpho vault as wired in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`), `withdraw` reverts whenever vault liquidity is fully utilized. An unprivileged attacker who is a borrower of that external vault can draw (or keep drawn) all available liquidity before the honest manager calls `stopEpoch`. Every subsequent `stopEpoch` reverts, `epochNumber` never advances (`IdleCreditVault._claimFundedWithdrawRequest` reverts via `epochNumber <= lastWithdrawRequest`), `claimInstantWithdrawRequest` stays disabled, and `emergencyExitVault` also reverts for the same reason. The attacker only needs to keep utilization high — borrowing against their own collateral — and the pool's entire NAV (LP principal plus accrued interest) is frozen inside vault shares.

Guards do not help: `shortfall > _currentVaultAssets()` only returns early when the shares are economically insufficient (genuine default), not when they are solvent-but-illiquid; `_skimDonatedAssets`, KYC checks, and epoch gating are all upstream of the hook call and irrelevant; the default path is unreachable because the revert happens before `getFundsFromBorrower` is ever attempted.

### Impact Explanation
Permanent freezing of funds: all tranche-holder capital parked in the external ERC4626 vault (potentially ~100% of pool NAV) becomes unrecoverable for as long as the attacker sustains full vault utilization, which they can do indefinitely by keeping a borrow position open. Withdraw requests already in flight cannot be claimed, new epochs cannot start, and the graceful `defaulted` recovery machinery (`finalizeDefault`, recovery pricing) can never be engaged because the revert bypasses `_handleBorrowerDefault`.

### Likelihood Explanation
Requires a programmable-borrower deployment whose ERC4626 vault is a shared lending market where liquidity can be exhausted by external borrowers — exactly the deployment shape exercised by `ProgrammableBorrowerCreditVault.t.sol` against a Morpho vault. The attacker needs no protocol privilege: only the ability to borrow from the external vault, which is unprivileged by design. The cost is the interest on the external borrow, not any loss of principal.

### Recommendation
Do not let vault liquidity failures bubble as raw reverts. Options: (a) treat a covered-but-failed `vault.withdraw` as a borrower default (`return false` → `_handleBorrowerDefault`), since reserve-style recovery is strictly better than an unbounded freeze; or (b) allow `onStopEpoch` to withdraw `vault.maxWithdraw(address(this))` and let the subsequent `transferFrom` shortfall drive the existing default accounting. If a retryable path is desired, bound it (e.g., owner-only `forceDefault` after N failed stops).

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/ProgrammableBorrowerCreditVault.t.sol` setup with a real Morpho vault):

```solidity
function testVaultLiquidityDrainFreezesStopEpoch() external {
    uint256 amount = 10_000 * oneScale;
    vm.prank(owner); cdoEpoch.setIsInterestMinted(true);
    idleCDO.depositAA(amount);
    vm.prank(manager); cdoEpoch.startEpoch();          // funds parked into Morpho vault via onStartEpoch

    // Attacker: unprivileged borrower of the external ERC4626 vault.
    // Supplies collateral to the vault's market and borrows all available liquidity
    // so vault.maxWithdraw(programmableBorrower) < shortfall => withdraw() reverts.
    _attackerBorrowAllVaultLiquidity(morphoVault);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Repeat arbitrarily: epoch never stops, default never set,
    // claimWithdrawRequest / emergencyExitVault remain bricked while
    // attacker keeps utilization at 100%.
}
```

Note: the "covered" check at ProgrammableBorrower.sol:245 confirms the shares are solvent, so the revert is purely a liquidity condition the attacker controls. I could not verify within the available iterations whether the specific deployed vaults for this pool admit full liquidity drains; the finding depends on the vault being a shared-liquidity ERC4626 rather than an isolated one.
