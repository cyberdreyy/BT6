### Title
ziplegacy extractor lacks path-containment enforcement present in tarzstd extractor, permitting zip-slip path traversal - ([File: helpers/archives/zip_extract.go])

### Summary
`extractZipFile` (helpers/archives/zip_extract.go:61-83) writes cache/artifact entries using `file.Name` verbatim with no `filepath.Abs` + prefix check, unlike `tarzstd_extractor.go`'s `Extract` which explicitly rejects any entry that resolves outside `e.dir` [1](#0-0) . Since `archive.NewExtractor` (commands/helpers/archive/archive.go:102-109) dispatches purely on the detected `Format` string and the `ziplegacy` path (`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go:26-32`) forwards directly into `archives.ExtractZipArchive` → `extractZipFile` with no directory-containment check of its own, any cache/artifact archive processed via the legacy zip format can place files anywhere the process has write permission, including outside the intended extraction directory.

### Finding Description
`CacheExtractorCommand.Execute` opens the cache file, detects its format, and calls `archive.NewExtractor(format, f, size, wd)` then `extractor.Extract(ctx)` [2](#0-1) . The three registered formats dispatch to different backends: `fastzip` (backed by the `saracen/fastzip` library, which internally validates and cleans zip entry paths), `tarzstd` (which explicitly enforces `strings.HasPrefix(path, e.dir+separator)` before any write) [3](#0-2) , and `ziplegacy`, whose `Extract` simply calls `zip.NewReader` then `archives.ExtractZipArchive(zr)` [4](#0-3) .

`ExtractZipArchive` iterates `archive.File` and calls `extractZipFile(file)` for each entry, using `file.Name` directly for `os.MkdirAll(filepath.Dir(file.Name), ...)`, `os.Mkdir`, `os.Remove`/`os.Symlink`, and `os.OpenFile` [5](#0-4) . There is no `filepath.Abs` resolution against a root directory and no rejection of entries containing `..` segments or absolute paths — the only validation present is `errorIfGitDirectory`, which is unrelated to path containment [6](#0-5) . This is a classic zip-slip: an entry named e.g. `../../../../home/other-project/authorized_keys` or an absolute path will be written exactly there, relative to the process's current working directory, when the `ziplegacy` format is used.

Because `NewExtractor` is chosen purely by `Format` (detected from the archive content/magic bytes at `openArchive`, not hardcoded), and the invariant "all extractor backends must enforce identical path-containment guarantees regardless of format selection" clearly does not hold, this is a real backend-inconsistency bug: the same malicious entry that is blocked by `tarzstd` extraction is not blocked by `ziplegacy` extraction.

### Impact Explanation
On a shell executor or any executor where multiple jobs/projects share a filesystem, or even within a single job's container, an attacker-controlled cache/artifact archive processed through the legacy zip path can overwrite arbitrary files reachable by the extracting process's permissions — outside the intended cache/build root. This directly violates the stated invariant that "file operations must stay within intended build/cache/artifact roots" and can lead to cross-project file tampering (shell executor) or unexpected file overwrite within the container in other executor types.

### Likelihood Explanation
The attacker only needs to supply a cache archive whose bytes are detected by GitLab Runner as legacy zip format and whose file entries contain `../` sequences or absolute paths — fully within reach of a normal pipeline author who controls the cache contents/upload for their own job. No admin privileges or GitLab-side compromise are required; the bug is deterministic and repeatable given the archive's file list, matching the problem statement's "attacker controls cache archive bytes/format detection" precondition.

### Recommendation
Add the same containment check used in `tarzstd_extractor.go` to `extractZipFile`/`ExtractZipArchive` in `helpers/archives/zip_extract.go`: resolve each `file.Name` with `filepath.Abs(filepath.Join(dir, file.Name))` against the extraction root and reject (or skip with a warning) any entry whose resolved path does not have the root directory as a prefix, before any `os.MkdirAll`/`os.OpenFile`/`os.Symlink` call. This requires threading the extraction root (`e.dir`) into `ExtractZipArchive`/`extractZipFile`, since currently those functions have no notion of a root directory at all.

### Proof of Concept
Go unit test in `helpers/archives`:
1. Build an in-memory `zip.Writer` containing one entry named `../evil.txt` (or `/tmp/evil.txt`).
2. Call `ExtractZipArchive` (or `ExtractZipFile`) with a target directory `dir` and assert the file was NOT created outside `dir` — currently this assertion fails because the file is written outside `dir`.
3. Differential test: run the identical malicious entry through `tarzstd` extractor's `Extract` and assert it returns the `"cannot be extracted outside of chroot"` error [7](#0-6) , while `ziplegacy`'s `Extract` returns no error and writes the file outside root — demonstrating the inconsistency.

func ExtractZipArchive(archive *zip.Reader) error {
	tracker := newPathErrorTracker()

	for _, file := range archive.File {
		if err := errorIfGitDirectory(file.Name); tracker.actionable(err) {
			printGitArchiveWarning("extract")
		}

		if err := extractZipFile(file); tracker.actionable(err) {
			logrus.Warningf("%s: %s (suppressing repeats)", file.Name, err)
		}
	}
