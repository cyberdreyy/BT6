### Title
Aggregated instant-withdraw ledger lets a user claim unfunded current-epoch receipts using the vault's shared underlying balance - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays out the *entire* aggregate `instantWithdrawsRequests[_user]` balance — spanning all epochs — while funding for instant requests is tracked separately and lazily via `pendingInstantWithdraws`, which is only decremented by `collectInstantWithdrawFunds`. A user who stacks a second, still-unfunded instant request on top of a funded one can have the CDO claim burn and pay the full aggregate, spending shared vault underlyings that are owed to other users' pending receipts. This mirrors the reported bug class: a shared resource (the vault's pooled underlying balance) is consumed by one user without per-request funding isolation.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol:356-375`, `requestInstantWithdraw` mints a receipt, adds `_amount` to `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `pendingInstantWithdraws`. Funds for those requests only arrive later when the CDO calls `collectInstantWithdrawFunds(_amount)` (line 398-403), which decreases `pendingInstantWithdraws` by the collected amount.

`claimInstantWithdrawRequest` (lines 380-393) then does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

There is no check that the whole `instantWithdrawsRequests[_user]` aggregate has actually been funded. `_transferFundedClaim` (lines 897-907) only guards `defaultRecoveryReserve` — it does not compare the transfer against `pendingInstantWithdraws` or the unfunded remainder. So if a user holds a funded instant receipt from epoch N and then opens a new instant request in epoch N+1 (which bumps `pendingInstantWithdraws` but has no underlying backing yet, since the borrower hasn't repaid and `collectInstantWithdrawFunds` has not run for it), a single claim pays out both requests. The unfunded portion is drawn from whatever underlying the vault happens to hold — funds earmarked for other users' funded instant claims or recovery reserves above the guarded floor.

The per-epoch bookkeeping (`instantWithdrawsRequestsByEpoch`) is only consulted on the default-finalization path (`_claimDefaultedInstantWithdrawRequest`); the normal funded-claim path deliberately aggregates across epochs, so the shared-pool isolation failure is in the happy path, not an edge case.

### Impact Explanation
Direct theft of vault underlyings. The attacker withdraws underlying equal to their unfunded second request without ever having that request backed by a borrower repayment. The vault's underlying balance is drained below the sum of outstanding funded claims, leaving the last claimants (or the default-recovery claimants if the deficit is large enough) unable to withdraw — insolvency shifted onto honest users. Loss is bounded by the attacker's own tranche value but is essentially free leverage: they convert an unfunded IOU into immediate cash.

### Likelihood Explanation
Requires: instant withdrawals enabled on the CDO variant, the attacker being a KYC'd tranche holder able to make two instant requests across the request window, and the CDO's claim path being reachable while part of the user's aggregate is unfunded. The vault-level code unconditionally pays the full aggregate, so exploitability reduces to whether `IdleCDOEpochVariant` gates `claimInstantWithdrawRequest` on full funding of `pendingInstantWithdraws` — a check that is aggregate (not per-user) in `collectInstantWithdrawFunds`, so collecting "the matured portion" still leaves the second request unfunded inside the same user's balance. No privileged misbehavior, oracle input, or timing edge beyond normal epoch sequencing is needed.

### Recommendation
In `claimInstantWithdrawRequest`, cap the payout to the funded portion of the user's aggregate: track a per-user funded counter (or compare against `instantWithdrawClaimsByEpoch` and the amount already collected via `collectInstantWithdrawFunds`), and only burn/pay receipts whose backing has actually been transferred to the vault. Alternatively, require `pendingInstantWithdraws == 0` or subtract the user's unfunded request-epoch basis before paying, so an unfunded receipt can never consume the shared pool. Add a Foundry test where user A has a funded epoch-N instant receipt plus an unfunded epoch-N+1 instant receipt and assert the claim reverts or pays only the funded part.
