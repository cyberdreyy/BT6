### Title
Post-default withdraw requests pay at par from the recovery reserve, draining funds owed to defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` mints post-default withdraw receipts that are paid **1:1** out of `defaultRecoveryReserve` via `_claimPostDefaultWithdrawRequest` → `_transferDefaultRecovery`, even though `finalizeDefaultRecovery` sized that reserve only to cover *pre-default* claims at `defaultRecoveryPrice`. The reserve receives no new backing when a post-default request is created, so each post-default claim dilutes/insolvents the reserve and later defaulted claimants are left permanently unable to claim.

### Finding Description
When the CDO finalizes a borrower default (`IdleCDOEpochVariant.finalizeDefault` → `IdleCreditVault.finalizeDefaultRecovery`), the strategy computes `totalBasis = activeBasis + pendingBasis`, sets `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + oldReserve` and `defaultRecoveryPrice = reserve * 1e18 / totalBasis` [1](#0-0) . The reserve is therefore exactly sufficient to pay every defaulted receipt at `recoveryPrice`, and nothing more.

After finalization, `requestWithdraw` takes the `defaultRecoveryFinalized` branch: it burns `_amount` strategy tokens from the CDO, mints the same `_amount` to the user, and stores `postDefaultRequests[_user] = _amount` — crucially, it does **not** add anything to `defaultRecoveryReserve` [2](#0-1) . The comment claims the amount is "already priced after the haircut because finalization lowered virtualPrice", but lowering the CDO's `virtualPrice` only changes how many *underlying* the tranche tokens convert to — it does not create any underlying backing in the strategy. The burned strategy tokens correspond to active CDO NAV, which after a hard default is unbacked; the only real cash in the contract is `defaultRecoveryReserve`.

The claim path then pays the full `_amount` from that reserve: `_claimPostDefaultWithdrawRequest` calls `_transferDefaultRecovery`, which does `defaultRecoveryReserve -= _amount` and transfers `_amount` 1:1 [3](#0-2) . Since the reserve was sized only for `totalBasis * recoveryPrice`, every post-default claim is pure reserve drain. Once post-default claims exceed any rounding slack, `defaultRecoveryReserve` underflows (Solidity 0.8 checked arithmetic) or pays out funds earmarked for other claimants — the last defaulted-epoch claimants' `_claimDefaultedWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest` calls permanently revert, freezing their recovery.

The bug class maps to the CVE's "attacker-controlled request crashes/strands the application" pattern translated to the credit-vault surface: a minimal attacker transaction (a post-default `requestWithdraw` + `claimWithdrawRequest`) deterministically drains or freezes other users' claims.

### Impact Explanation
Direct theft and permanent freezing of unclaimed default recovery. An unprivileged KYC-passing lender holding tranche tokens can, immediately after `finalizeDefault`, request a withdraw (priced at the haircut virtualPrice, so it costs them little) and claim the receipt at par, extracting up to 1/p times more underlying than a defaulted-epoch claimant per unit of basis. If enough post-default requests are made, `defaultRecoveryReserve` is exhausted and every remaining defaulted/instant claim reverts permanently — including honest lenders' pending withdraw receipts from the defaulted epoch. Loss magnitude: up to the entire `defaultRecoveryReserve` (all recovered borrower funds), bounded only by the attacker's post-default tranche holdings, which can be arbitrarily large since post-default deposits are unrestricted.

### Likelihood Explanation
Requires a borrower default and `finalizeDefault` — rare but explicitly supported, and the post-default request/claim path exists precisely so users can exit afterward. The attacker needs only tranche tokens (acquirable before or after default at the now-haircut price) and two calls; no privileged role is involved — only the owner/manager's honest `finalizeDefault` call to set up the state. No guard prevents it: `requestWithdraw` only checks that the user has no outstanding receipts, `claimWithdrawRequest` routes post-default claims straight to the reserve, and `_transferFundedClaim`'s reserve guard does not apply to `_transferDefaultRecovery`.

### Recommendation
Pay post-default requests from a separate bucket, not from `defaultRecoveryReserve`. Either:
- fund post-default receipts only from new underlying actually returned by the borrower post-finalization (track a `postDefaultReserve` incremented on such repayments), or
- apply `defaultRecoveryPrice` to post-default claims as well (`_transferDefaultRecovery(_user, amount * defaultRecoveryPrice / RECOVERY_FULL)`) so they are paid at the same rate as the basis they convert, and proportionally increment `defaultRecoveryReserve`/total basis at request time.

### Proof of Concept
Foundry fork test (modeled on `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testPostDefaultRequestDrainsRecoveryReserve() external {
  uint256 amount = 10000 * ONE_SCALE;
  // victim (user1) and attacker both deposit AA
  idleCDO.depositAA(amount);                 // attacker (this contract)
  _depositWithUser(user1, amount, true);     // victim

  _startEpochAndCheckPrices(0);
  // borrower repays nothing -> default
  vm.warp(cdoEpoch.epochEndDate() + 1);
  deal(defaultUnderlying, borrower, 0);
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);                  // getFundsFromBorrower fails -> _handleBorrowerDefault

  // victim requests withdraw in the defaulted epoch (receipt enters default basis)
  vm.prank(user1);
  cdoEpoch.requestWithdraw(0, address(AAtranche));

  // owner finalizes with partial recovery (e.g. 50%)
  uint256 recovered = IdleCreditVault(address(strategy)).defaultPendingClaimBasis() / 2;
  deal(defaultUnderlying, recoverySource, recovered);
  vm.prank(recoverySource);
  underlying.approve(address(strategy), recovered);
  vm.prank(manager);
  cdoEpoch.finalizeDefault(recovered, recoverySource);

  // attacker makes a post-default withdraw request (haircut price, pays at par)
  uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche));
  uint256 balPre = underlying.balanceOf(address(this));
  cdoEpoch.claimWithdrawRequest();
  // attacker receives full `receipt` 1:1 from the recovery reserve
  assertEq(underlying.balanceOf(address(this)) - balPre, receipt);

  // reserve is now under-funded: victim's defaulted-epoch claim reverts
  vm.prank(user1);
  vm.expectRevert();  // defaultRecoveryReserve underflow / NotAllowed
  cdoEpoch.claimWithdrawRequest();
}
```

The invariant violated is "one receipt, one payout at the finalized recovery price": `defaultRecoveryReserve` is sized for `totalBasis * defaultRecoveryPrice`, but post-default requests add claims paid at `RECOVERY_FULL` with zero added backing, so aggregate claims exceed the reserve.
