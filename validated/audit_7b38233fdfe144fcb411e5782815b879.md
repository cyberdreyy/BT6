### Title
Nil pointer dereference panic in `validChecksum` on malformed GCP Secret Manager response - (File: helpers/gcp_secret_manager/service/gcp_secret_manager.go)

### Summary
`validChecksum` unconditionally dereferences `payload.DataCrc32C` without a nil check, and `GetSecret` calls it right after only checking `Payload == nil` (not `Payload.DataCrc32C == nil`). A response with a non-nil `Payload` but nil `DataCrc32C` causes a nil pointer dereference panic in the goroutine resolving the secret.

### Finding Description
`GetSecret` fetches `accessSecretVersionResponse` from the backend, checks only `accessSecretVersionResponse.Payload == nil`, then calls `validChecksum(accessSecretVersionResponse.Payload)`: [1](#0-0) 

`validChecksum` dereferences `*payload.DataCrc32C` without checking it for nil: [2](#0-1) 

If the backend (or a MITM'd/redirected endpoint) returns `Payload: &smpb.SecretPayload{Data: [...], DataCrc32C: nil}`, `Payload != nil` so the existing guard passes, but `DataCrc32C` is nil, so `*payload.DataCrc32C` panics with a nil pointer dereference. `AccessSecretVersionResponse.Payload.DataCrc32C` is a protobuf optional field (`*int64`) that legitimately can be nil (e.g., older API behavior, partial/incomplete responses, or a spoofed/malformed response if an attacker can influence the endpoint reached by `access()`), and nothing in this code path enforces that it be populated before use.

### Impact Explanation
A panic here occurs inside the goroutine resolving the job's secret. Whether this only fails the individual job or crashes the whole runner process depends on whether the panic is recovered somewhere up the call stack (e.g., in the job-processing goroutine wrapper) or propagates unrecovered to the process's top level. The finding as scoped assumes an unrecovered panic causing full runner-process crash, which is a process-wide, multi-tenant availability issue affecting concurrently running jobs of other tenants. If the runner recovers panics per-job (common pattern in job execution frameworks), the actual impact would be a single job resolving failure rather than process-wide crash — this repo view does not show the panic-recovery wrapper around secret resolution, so the exact blast radius (single job vs. whole process) could not be fully confirmed from the available code.

### Likelihood Explanation
Regardless of blast radius, the root-cause bug is real and concretely reachable: `validChecksum` is called on every successful `GetSecret` with no defensive nil check on `DataCrc32C`, and the existing test suite in `gcp_secret_manager_test.go` only exercises the "correct checksum" and "incorrect checksum" cases — never `DataCrc32C == nil` — confirming this branch is untested and unguarded: [3](#0-2) 
Triggering it requires the `access()` call (via the Secret Manager client, using attacker-influenced `secret.Server` / STS-issued token) to return such a payload, which requires control over the backend response — i.e., MITM or a redirected/self-hosted endpoint, as stated in the question's precondition. This is a plausible defensive-coding gap even absent a confirmed MITM vector, since the client should never trust that an optional protobuf field is populated.

### Recommendation
Add an explicit nil check for `payload.DataCrc32C` in `validChecksum` (or in `GetSecret` before calling it) and return a graceful error (e.g., "data corruption detected" or a new "missing checksum" error) instead of dereferencing a possibly-nil pointer:
```go
func validChecksum(payload *smpb.SecretPayload) bool {
    if payload.DataCrc32C == nil {
        return false
    }
    return *calculateCrc32C(payload.Data) == *payload.DataCrc32C
}
```
