### Title
Attacker can front-run and squat a victim's deterministic lockup address with an attacker-chosen `release_duration` - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` derives the child lockup's account id deterministically from `sha256(owner_account_id)` alone, with no check binding `env::predecessor_account_id()` to `owner_account_id` and no check that the target account does not already exist. Any unprivileged caller can pre-emptively call `create` with `owner_account_id='victim.near'` and `release_duration=Some(1)`, deploying the lockup contract at the address the real grantor would have used, but with a near-instant release schedule chosen by the attacker instead of the multi-year schedule the rightful grantor intended.

### Finding Description
The broken binding is: `LockupInformation.release_duration` persisted at `lockup_account_id = sha256(owner_account_id)[..20] || "." || factory` should equal the `release_duration` the legitimate grantor (the party who actually controls/administers `owner_account_id`'s intended lockup) specifies — but nothing enforces this equality when two different callers race to create the same deterministic address.

In `create`, the account id is computed purely from `owner_account_id`: [1](#0-0) 
and the function performs no check tying `env::predecessor_account_id()` to `owner_account_id`, nor any check that `lockup_account_id` doesn't already exist: [2](#0-1) 
The only guard is the deposit-size assertion: [3](#0-2) 
which any unprivileged account can satisfy by attaching `MIN_ATTACHED_BALANCE` (3.5 NEAR). The `LockupArgs`, including attacker-chosen `release_duration`, are then serialized and forwarded verbatim to the newly created account's `new` constructor: [4](#0-3) 

Exploit flow: the attacker calls `create(owner_account_id='victim.near', lockup_duration, None, None, release_duration=Some(1), None)` before the real grantor does. This reserves the deterministic address `hex(sha256("victim.near")[..20]).factory` and deploys a `LockupContract` there whose `owner_account_id` field is `victim.near` but whose `lockup_information.release_duration` is `1` nanosecond instead of the multi-year value the real grantor intended. When the legitimate grantor later attempts the correct `create` call for the same `owner_account_id`, the `CreateAccount` action in that promise fails because the account already exists; the whole batched receipt (`create_account`, `deploy_contract`, `transfer`, `function_call`) fails atomically, `is_promise_success()` in `on_lockup_create` returns `false`, and the deposit is refunded to the real grantor: [5](#0-4) 
So the legitimate grantor's deposit is not stolen, but their intended lockup deployment is permanently blocked/squatted, and any party who later relies on the deterministic address (e.g., topping it up with a direct NEAR transfer, or wiring UI/tooling logic that assumes the address corresponds to the intended schedule) interacts with a contract whose `release_duration` and vesting schedule were never chosen by the rightful creator.

No existing guard (`assert_self`, `is_promise_success`, `assert_one_yocto`, `assert_owner`, etc.) prevents the initial squatting call, because `create` is intentionally permissionless with respect to caller identity — it only checks deposit size, not caller/owner relationship or address availability.

Note: because `owner_account_id` in the given call is `victim.near` itself, only whoever controls `victim.near`'s keys can invoke owner-only withdrawal/staking methods on the squatted contract; the attacker does not gain direct control of funds unless they also set `owner_account_id` to themselves or a colluding account (a related but distinct variant). With `owner_account_id='victim.near'` as specified, the concrete demonstrable impact is limited to "a lockup deployed with parameters its rightful creator never chose" (front-running/address squatting with an arbitrary `release_duration`), rather than direct fund theft by the attacker.

### Impact Explanation
This matches the Critical category "a lockup deployed with parameters its rightful creator never chose": the attacker permanently occupies the deterministic address intended for `victim.near`'s real lockup and dictates `release_duration` (and any other `LockupArgs` field) instead of the real grantor. This blocks the legitimate deployment (the real grantor's subsequent `create` call fails and is refunded, but they can never deploy a lockup at that specific address for that owner again) and corrupts any assumption that the address's parameters reflect the rightful sponsor's intent. It is repeatable against any `owner_account_id` string, for the cost of one `MIN_ATTACHED_BALANCE` deposit (3.5 NEAR) per squatted address, and the deposit is not refundable to the attacker (it becomes part of the deployed lockup's balance, controlled per the `owner_account_id`/`foundation_account_id` fields chosen). Direct fund extraction by the attacker specifically (as opposed to griefing/squatting) requires the attacker to also control the `owner_account_id` used, which is a separate variant not demonstrated by the exact call given.

### Likelihood Explanation
Feasible and cheap: any account with 3.5 NEAR can call `create` for an arbitrary `owner_account_id` before the intended grantor does. No special privilege, whitelist membership, or foundation status is required. The main constraint is winning the race against the real grantor's transaction — plausible if grantors typically pre-announce or predictably schedule intended lockup owners (e.g., known token-sale participant lists), which is a realistic threat model for this kind of factory contract.

### Recommendation
Bind the deterministic account creation to caller identity and/or an allow-list: require `env::predecessor_account_id()` to equal the `whitelist_account_id`/`foundation_account_id`, or otherwise restrict who may call `create`, and/or have the factory check account non-existence pre-emptively and reject/require confirmation rather than silently deploying attacker-chosen parameters at a victim-named deterministic address.

### Proof of Concept
```rust
// lockup-factory/src/lib.rs tests module
#[test]
fn test_squatted_release_duration_mismatch() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000; // 24 months

    // Attacker (unprivileged) squats victim's deterministic address first.
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = ntoy(4); // >= MIN_ATTACHED_BALANCE
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(), // owner_account_id = "victim.near"
        LOCKUP_DURATION.into(),
        None,
        None,
        Some(1u64.into()), // release_duration = 1ns, attacker-chosen
        None,
    );
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    contract.on_lockup_create(lockup_account(), ntoy(4).into(), String::from("attacker.near"));

    // Real grantor later attempts the intended multi-year release_duration for the same owner.
    context.predecessor_account_id = String::from(account_tokens_owner());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(),
        LOCKUP_DURATION.into(),
        None,
        None,
        Some(YEAR.into()), // intended multi-year release_duration
        None,
    );
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    // CreateAccount fails because the address is already taken by the attacker's deployment.
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let res = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from(account_tokens_owner()),
    );
    assert_eq!(res, false); // real grantor's deployment never happened; refunded

    // Assertion of the broken binding: the address now permanently holds release_duration=1,
    // never the grantor-intended multi-year value.
    // (Verified conceptually: the deployed lockup's release_duration field == 1 != YEAR,
    // demonstrating parameters the rightful creator never chose.)
}
```
