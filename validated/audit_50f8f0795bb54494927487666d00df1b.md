## Finding: Single griefing shareholder can permanently block APT distribution to all other shareholders in `aptos_framework::vesting`

### Title
Unprivileged shareholder can DoS `distribute()`/`vest()`/`terminate_vesting_contract()` for an entire vesting pool by opting out of direct coin transfers - (File: `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary
`vesting::distribute` iterates over **every** shareholder of a vesting contract in a single loop and calls `aptos_account::deposit_coins` for each one [1](#0-0) . If any single recipient's deposit aborts, the entire loop — and thus the entire transaction — reverts, exactly like the `ZappingProxy` bug where one failed leg (the ETH refund) reverts an otherwise-successful batch operation. Any shareholder can unilaterally make their own deposit revert by calling the permissionless `aptos_account::set_allow_direct_coin_transfers(account, false)` if they have not yet registered a `CoinStore`/primary store for `AptosCoin`.

### Finding Description
`aptos_account::deposit_coins` (referenced from `vesting.move`) auto-registers the recipient for the coin only if the recipient has opted in to direct transfers; otherwise it aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`. The opt-out check comes from `can_receive_direct_coin_transfers`, gated by the `DirectTransferConfig` resource that any account can create/flip via the permissionless entry function `set_allow_direct_coin_transfers` [2](#0-1) , and the registration gate itself [3](#0-2) .

`vesting::create_vesting_schedule` adds arbitrary shareholder addresses to `grant_pool` without ever validating that they are registered for `AptosCoin` (only `set_beneficiary` enforces `assert_account_is_registered_for_apt` for a *beneficiary*, not for the base shareholder) [4](#0-3) .

`distribute()` then does a single un-guarded loop over all shareholders:
```
shareholders.for_each_ref(|shareholder| {
    ...
    aptos_account::deposit_coins(recipient_address, share_of_coins);
});
``` [1](#0-0) 

If any one shareholder (or their designated beneficiary, before being registered) has previously called `set_allow_direct_coin_transfers(false)` and is not yet registered for `AptosCoin`, every future `deposit_coins` call to that address aborts, which propagates up and aborts the whole `distribute()` transaction — not just that one shareholder's payout. Because `distribute()` is also invoked internally by `vest()`, `terminate_vesting_contract()`, and `admin_withdraw()`'s sibling flow, this single griefing shareholder can block reward/vested-stake distribution to **every other shareholder** in the same vesting contract, and block contract termination cleanup as well [5](#0-4) [6](#0-5) .

This mirrors the `ZappingProxy` root cause precisely: a batched/forwarding operation has no isolation for a single failing leg, so one uncooperative/misconfigured party can revert value transfers intended for unrelated parties.

### Impact Explanation
This breaks the stake/vesting invariant that distribution and withdrawal rights of unrelated shareholders must be preserved independently of another shareholder's account configuration. A single unprivileged shareholder in a multi-shareholder vesting pool can strand vested APT and staking rewards for all co-shareholders indefinitely, until the admin notices and calls `set_beneficiary` to redirect the griefing shareholder's payout to a registered address (an admin-only, not delegator-controlled, mitigation). If the admin is unresponsive, malicious, or has already relinquished control (vesting contracts are commonly created for third parties without an active admin), the block is effectively permanent, matching "permanent lock/non-recoverable loss of claim rights" for the impacted shareholders' vesting and reward balances.

### Likelihood Explanation
High likelihood: any account can call the permissionless `set_allow_direct_coin_transfers(false)` function on itself before ever being registered for `AptosCoin`, and vesting contract shareholder addresses are added without any registration check. No special privileges, timing, or coordination with the admin/operator are required.

### Recommendation
Do not let one recipient's failed deposit abort the whole distribution loop in `vesting::distribute` (and analogous logic in `staking_contract::distribute_internal`, which has the same unguarded-loop pattern [7](#0-6) ). Options: use a non-aborting deposit path that falls back to an escrow/claimable balance when the direct deposit would fail, or defer/skip that shareholder's payout (e.g., accumulate it in a per-shareholder claimable resource) instead of failing the entire batch.

### Proof of Concept
1. Account `B` (a would-be vesting shareholder) calls `aptos_account::set_allow_direct_coin_transfers(B, false)` before ever holding/registering `AptosCoin`.
2. Admin creates a vesting contract via `vesting::create_vesting_schedule` with shareholders `[A, B]` (no registration check is performed on `B`).
3. Vesting starts, `vest()`/`unlock_rewards()` unlock funds; when `distribute(contract_address)` is called, the loop reaches `B`, calls `aptos_account::deposit_coins(B, ...)`, which aborts because `B` is not registered and has opted out.
4. The entire `distribute()` transaction reverts — `A` receives nothing, and this repeats on every subsequent call to `distribute`, `vest`, or `terminate_vesting_contract` for this contract until the admin intervenes with `set_beneficiary(admin, contract_address, B, some_registered_addr)`.

Note: I could not view the exact body of `aptos_account::deposit_coins` in the index (the code around lines 90–120 in `aptos_account.move` was truncated in the available index), so its exact abort condition is inferred from the visible `transfer_coins` logic and `can_receive_direct_coin_transfers` gate, which are consistent with the well-known Aptos framework implementation. If you need to confirm the exact `deposit_coins` body, a full-repo Devin session would be able to read the untruncated file.

    public entry fun terminate_vesting_contract(admin: &signer, contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        // Distribute all withdrawable coins, which should have been from previous rewards withdrawal or vest.
        distribute(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        verify_admin(admin, vesting_contract);
        let (active_stake, _, pending_active_stake, _) = stake::get_stake(vesting_contract.staking.pool_address);
        assert!(pending_active_stake == 0, error::invalid_state(EPENDING_STAKE_FOUND));

        // Unlock all remaining active stake.
        vesting_contract.state = VESTING_POOL_TERMINATED;
        vesting_contract.remaining_grant = 0;
        unlock_stake(vesting_contract, active_stake);

        emit(
            Terminate {
                admin: vesting_contract.admin,
                vesting_contract_address: contract_address,
            },
        );
    }

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
