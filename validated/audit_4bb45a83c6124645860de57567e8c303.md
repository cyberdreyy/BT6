### Title
Signer drops stale-but-still-canonical signed conflicts without re-verifying against the node, allowing a second signature on a conflicting block - (File: `stacks-signer/src/v0/signer.rs`, `stacks-signer/src/signerdb.rs`)

### Summary
In the pre-commit → signature flow, before signing a block that has crossed the ≥70% pre-commit weight threshold, the signer looks up every other **signed** block at or above the same Stacks height, in any tenure (`get_signed_conflicts`), and only re-verifies against the node's live chain state (`get_sortition_by_burn_hash` / `get_tenure_tip`) if that conflict is judged "fresh" (`last_endorsed > cutoff`). If a conflict is judged "stale," it is *skipped entirely* rather than re-checked against the node's authoritative (live) chain state — the flow instead falls through to a check of only its *own* tenure's conflicts. This mirrors the `Asset.lotPrice()` bug class: rather than re-querying the most up-to-date source of truth (the node/"oracle") when locally cached state (a prior endorsement) has aged past a timeout, the code trusts the decayed/absent local view and proceeds, potentially missing a genuinely still-canonical, globally accepted conflicting block signed in another tenure.

### Finding Description
`stacks-signer/src/signerdb.rs::get_signed_conflicts` returns every signed block (locally or globally accepted; pre-commits excluded) at or above a given height, across *all* tenures, each annotated with `last_endorsed` (the later of `signed_self`/`signed_group`) [1](#0-0) . This is consumed at the pre-commit-threshold-crossing step of `handle_block_pre_commit`, documented as:

> `FRESH -- yes` → re-derive whether the conflict still blocks by asking the node whether its tenure's sortition is canonical (`get_sortition_by_burn_hash`) and whether the node's chain still reaches the block (`get_tenure_tip`).
> `FRESH -- "no — all stale"` → jump straight to `OWN` (does a conflict exist in the block's *own* tenure), skipping the node round-trip for the other-tenure conflict entirely. [2](#0-1) 

The `HOLD1`/`HOLD2` branches (refuse to sign) are reachable **only** through the fresh-conflict path (`SORT`/`LIVE`) or the own-tenure `TIP` check; a stale other-tenure conflict is never re-verified against the node and therefore can never veto the new signature [2](#0-1) . Because the last confirmed data used to decide "does this conflict still block?" is the signer's own possibly-outdated local timestamp, this is structurally identical to `Asset.lotPrice()`'s fallback: instead of re-querying the freshest available truth (the node, analogous to the oracle) once the cached value (the endorsement) times out, the code accepts the decayed/absent value as if the underlying fact (the conflicting block's canonical status) had also decayed — which it has not, since chain canonicity does not expire with a wall-clock timer.

`get_last_signed_block` for the *other* tenure's conflict is what a globally accepted, still-canonical block would have set via `mark_globally_accepted`/`mark_locally_accepted` [3](#0-2) [4](#0-3) , so the "conflict" being dropped as stale can be a fully canonical, globally accepted sibling block.

### Impact Explanation
If a miner (a single one-slot miner, aided only by ordinary gossip of pre-commits/signatures) produces two conflicting blocks at the same height in different tenures far enough apart in time that the first conflict's endorsement ages past the freshness cutoff, a signer can be induced to place a second signature over the later, conflicting block — even though the earlier one remains the canonical, globally accepted block on-chain. This breaks the "one canonical block per height, no conflicting signature" equality that `get_signed_conflicts`/`conflict_still_blocks` exists to protect, matching the Critical impact category: a signer signing a conflicting block.

### Likelihood Explanation
This requires only: (1) a miner producing two same-height blocks in different tenures (ordinary equivocation/reorg-attempt behavior a single miner can perform), and (2) enough elapsed time between the two proposals for the earlier endorsement to cross the "stale" cutoff used by the `FRESH` check. No majority of signers, no other signer's key, and no node compromise is required — only the natural passage of time between two proposals from the same miner and gossip of pre-commits/signatures that any signer already processes. The exact cutoff/timeout constant backing the `FRESH` decision could not be pinned to a specific line in this pass (the codebase's size limits meant I could not retrieve the precise function body implementing the `FRESH` cutoff comparison in `stacks-signer/src/v0/signer.rs`), so the precise timing window needed to trigger this is not fully confirmed from the index; a Devin session with full repo access would be needed to confirm the exact constant and function (likely `conflict_still_blocks`/`reorg_permit_stands` in `stacks-signer/src/v0/signer.rs`).

### Recommendation
When a signed conflict in another tenure is judged "stale" by the local endorsement-time cutoff, do not skip node re-verification outright — still perform the `SORT`/`LIVE` node round-trip (or a cheaper canonical-tip check) before falling through to the own-tenure-only check, so that a genuinely still-canonical conflicting block is never allowed to be silently dropped merely because its local endorsement timestamp aged out.

### Proof of Concept
Conceptual reproduction (exact code path could not be fully re-verified due to index limits):
1. Miner produces block A in tenure T1 at height H; enough signers pre-commit/sign so A becomes globally accepted (`mark_globally_accepted`).
2. Time passes beyond the local "freshness" cutoff used in the `FRESH` branch of the pre-commit-threshold flow.
3. The same or a colluding one-slot miner in a later tenure T2 proposes a conflicting block B also at height H.
4. When B crosses the ≥70% pre-commit weight threshold, `get_signed_conflicts` finds A as a conflict, but because A's `last_endorsed` is now older than the cutoff, the flow treats it as stale and skips the node-verification (`SORT`/`LIVE`) that would otherwise detect A is still canonical, falling through to the `OWN`-tenure-only check, which finds no conflict in B's own tenure and signs B [2](#0-1) .
