### Title
External-initiator credential holder can trigger `RunJobV2` for an arbitrary job because `Create` treats EI-authenticated pseudo-users as real users - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` attempts to block external-initiator (EI) credentials from running jobs by integer job ID via `isUser := auth.GetAuthenticatedUser(c)`, with the comment "only users are allowed to run jobs using int IDs - EIs not allowed." However, `AuthenticateExternalInitiator` middleware injects a synthetic `*sessions.User{Role: UserRoleRun}` into the same context key (`SessionUserKey`) that `GetAuthenticatedUser` reads, so the check cannot actually distinguish a real logged-in user from an EI credential holder. This lets any EI credential holder call `RunJobV2` for any int32 job ID on the node, with no check that the job was ever registered to that EI.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered in `core/web/router.go` under `authv2`, protected by `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` [1](#0-0) . Critically, `AuthenticateByToken`/`AuthenticateBySession` are not the only path into this handler — the EI-only routes elsewhere use `auth.AuthenticateExternalInitiator`. But regardless of route wiring, the vulnerability is in how `Create` distinguishes user- vs EI-originated requests:

In `AuthenticateExternalInitiator`, after validating the EI's access key/secret, the middleware sets: [2](#0-1) 
This stores a fabricated `*clsessions.User{Role: clsessions.UserRoleRun}` under the same `SessionUserKey` used for genuine logged-in users, purely so role-gated handlers (`RequiresRunRole`, etc.) work uniformly for EIs.

In `Create`: [3](#0-2) 
The code calls `auth.GetAuthenticatedUser(c)`, which simply checks for presence of `SessionUserKey`: [4](#0-3) 
Since `AuthenticateExternalInitiator` also populates `SessionUserKey`, `isUser` evaluates to `true` for an EI-authenticated request exactly the same as for a genuine user session/token. The comment's intended restriction ("EIs not allowed") is therefore not enforced — the code has no way, using `GetAuthenticatedUser`, to tell an EI-impersonated pseudo-user apart from a real user. The correct check would need to use `auth.GetAuthenticatedExternalInitiator(c)` to detect and reject EI credentials, which `Create` never calls.

Additionally, there is no lookup of `ExternalInitiatorWebhookSpec` (or any binding record) in `Create` to verify the target job ID was ever the one this EI account was configured against — even if such a binding were checked, this code path (int32-ID branch) bypasses it entirely because it goes straight to `prc.App.RunJobV2(ctx, jobID, nil)`.

### Impact Explanation
An external-initiator credential (a low-privilege, non-admin credential type intended to trigger only its own bound webhook job) can invoke `RunJobV2` for any job ID on the node — including OCR, VRF, Cron, or other job types unrelated to the EI's registration. This matches the "unauthorized job run" bounty impact class: an attacker holding only EI credentials can force execution of arbitrary jobs, potentially causing unwanted on-chain transactions, resource exhaustion, or leaking pipeline outputs for jobs they should have no access to (via the returned `PipelineRunResource`).

### Likelihood Explanation
Exploitation only requires possessing any valid external-initiator access key/secret pair (a credential class explicitly designed to be handed to lower-trust remote systems) and the target job's integer ID (job IDs are sequential/enumerable and often visible in job specs, error logs, or UI links). No additional privilege or race condition is needed; the request is a single unauthenticated-relative-to-target-job HTTP POST, fully repeatable.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests authenticated as an external initiator before allowing the int32-ID branch, e.g.:
```go
if _, isEI := auth.GetAuthenticatedExternalInitiator(c); isEI {
    jsonAPIError(c, http.StatusUnauthorized, errors.New("external initiators may not run jobs by integer ID"))
    return
}
```
Do not rely solely on `GetAuthenticatedUser`, since `AuthenticateExternalInitiator` populates the same session key. If EI-triggered runs need to be supported at all, additionally validate that the requesting EI is bound to the specific target job (e.g., via a job/EI binding record) before calling `RunJobV2`.

### Proof of Concept
Handler-level integration test plan (Go, in `core/web/pipeline_runs_controller_test.go` style):
1. Start an `cltest.NewApplicationEVMDisabled(t)` and create two jobs, Job-A and Job-B (e.g., two Cron or OCR jobs) via `app.AddJobV2`.
2. Create an external initiator "EI-A" via `app.BridgeORM().CreateExternalInitiator` using `bridges.NewExternalInitiator`, conceptually intended/registered only in relation to Job-A (there is no actual binding table left to register against, which itself underscores the missing authorization).
3. Build an HTTP client that authenticates using EI-A's access key/secret headers (`X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret`) instead of a session/token.
4. Send `POST /v2/jobs/<Job-B-ID>/runs` with the EI-A headers.
5. Assert the current (vulnerable) behavior returns `200 OK` with a `PipelineRunResource` for Job-B (i.e., `RunJobV2` was actually invoked) — demonstrating the flaw.
6. After applying the fix, assert the same request returns `401 Unauthorized` (or `403`), and that `RunJobV2` was never invoked (e.g., via a mock `chainlink.Application` asserting `AssertNotCalled(t, "RunJobV2", ...)`, using `core/internal/mocks/application.go`).
