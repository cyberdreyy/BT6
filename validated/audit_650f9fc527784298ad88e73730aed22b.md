### Title
Loss-adjusted withdrawal receipts can be paid at par and drain newer deposits - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`collectWithdrawFunds` records a partial-loss recovery price under the strategy epoch that is current when the epoch stops, while `requestWithdraw` stores the request under the epoch that was current during the preceding buffer period. Because `startEpoch` increments `epochNumber`, these indices differ by one. `_claimLossAdjustedWithdrawRequest` then looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]`, misses the recorded haircut, and falls through to `_claimFundedWithdrawRequest`, which pays the full original receipt if enough underlying is available.

### Finding Description
A user calls `requestWithdraw` during the buffer while `epochNumber == N`; `lastWithdrawRequest[user]` and `withdrawsRequestsByEpoch[user][N]` are set to the full receipt amount. After the next epoch starts, `epochNumber` is `N + 1`. If the manager calls `stopEpochWithDuration` with a nonzero loss, `previewLossAdjustedWithdrawFunds` reduces the amount collected for pending receipts, but `collectWithdrawFunds` stores the resulting recovery price at `lossRecoveryPriceByEpoch[N + 1]`.

When the user later calls `claimWithdrawRequest`, the loss-adjusted path checks `lossRecoveryPriceByEpoch[N]`, sees zero, and returns without clearing the haircutted receipt. The funded path then considers the request mature because `epochNumber > lastWithdrawRequest[user]`, clears `withdrawsRequests[user]`, burns the full strategy-token receipt, and attempts to transfer the full pre-loss amount.

During the post-stop buffer, new deposits place underlying in `IdleCreditVault` before the next `startEpoch`. That liquidity can fund the stale full receipt. The attacker therefore receives the unhaircutted amount even though only the reduced amount was collected for that receipt, consuming assets backing newer depositors or other pending claims.

### Impact Explanation
This breaks the loss-waterfall and one-receipt-one-payout invariants. A pending withdrawer escapes the pro-rata loss assigned by `stopEpochWithDuration` and can claim up to the full original receipt amount. The direct loss equals the withheld `pendingLoss` portion, capped by available strategy liquidity and the claimant's receipt. If insufficient liquidity exists, the claim reverts instead of paying the intended reduced amount, permanently freezing the affected receipt until enough unrelated funds accumulate.

### Likelihood Explanation
The path requires a normal user withdrawal request and a successful `stopEpochWithDuration` partial loss. The attacker does not need a privileged role or to cause the loss; they only need to hold the affected withdrawal receipt and claim after the stop. The epoch-index mismatch is deterministic whenever the strategy epoch is incremented between request and loss-adjusted collection.

### Recommendation
Store the loss recovery price under the request epoch represented by `lastWithdrawRequest`, or maintain an explicit `pendingWithdrawEpoch`/mapping of all pending receipt epochs that `collectWithdrawFunds` updates. The epoch used in `requestWithdraw`, `collectWithdrawFunds`, and `_claimLossAdjustedWithdrawRequest` must be identical. Add a regression test that requests a withdrawal in epoch `N`, starts epoch `N + 1`, applies a nonzero loss, verifies the recovery price is found by the claimant, and confirms the claim pays only `claimBasis * lossRecoveryPrice / RECOVERY_FULL`.

### Proof of Concept
A Foundry test should follow this sequence:

```solidity
// Existing fixture setup omitted.
// 1. Alice deposits during buffer epoch N.
idleCDO.depositAA(10_000e6);

// 2. Alice requests a full withdrawal while strategy.epochNumber() == N.
uint256 requestEpoch = strategy.epochNumber();
cdoEpoch.requestWithdraw(0, address(AAtranche));
uint256 receipt = strategy.withdrawsRequests(alice);
assertEq(strategy.lastWithdrawRequest(alice), requestEpoch);

// 3. Manager starts the next epoch; strategy.epochNumber() becomes N + 1.
cdoEpoch.startEpoch();
assertEq(strategy.epochNumber(), requestEpoch + 1);

// 4. Manager stops with a nonzero loss and funds only pendingToFund.
(uint256 pendingToFund, uint256 activeLoss) =
    strategy.previewLossAdjustedWithdrawFunds(lossAmount);
// borrower approves/transfers pendingToFund + required interest
cdoEpoch.stopEpochWithDuration(nextApr, interest, duration, lossAmount);

// Vulnerable state:
assertEq(strategy.lossRecoveryPriceByEpoch(requestEpoch), 0);
assertGt(strategy.lossRecoveryPriceByEpoch(requestEpoch + 1), 0);

// 5. Bob deposits during the following buffer, leaving underlying in the strategy.
idleCDO.depositAA(receipt);

// 6. Alice claims the stale receipt.
uint256 before = underlying.balanceOf(alice);
cdoEpoch.claimWithdrawRequest();
assertEq(underlying.balanceOf(alice) - before, receipt);
assertLt(receipt, pendingToFund); // Expected for fixed accounting; currently inverted.
```

The decisive assertion is that `claimWithdrawRequest` pays `receipt`, rather than `receipt * lossRecoveryPriceByEpoch[requestEpoch + 1] / 1e18`.
