### Title
Cancelled/expired deposit and redeem requests refund assets to `request.receiver` instead of the requesting user, causing fund loss when receiver differs from requester - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.cancelRequest` and `ProvisionerV2.refundRequest` (and the internal `_solveRequestDirect`/`_solveDepositVaultFixedPrice`/`_solveRedeemVaultAutoPrice`/`_solveRedeemVaultFixedPrice` refund branches) route the returned escrowed asset to `request.receiver` via `_transferWithFallback`, only falling back to the requesting user (`request.user`) if `receiver == requester` or the transfer to `receiver` reverts. Since `requestDeposit`/`requestRedeem` allow the requester to set an arbitrary `receiver` different from `msg.sender` (no `_requireValidReceiver`-style check exists for the async path), a user who deposits/redeems for another account and later cancels or lets the request expire has their own escrowed tokens sent to that third-party receiver instead of back to themselves. This is the same root-cause/impact pattern as the Dinari "Cancelled order should not send tokens to recipient" finding: cancellation is supposed to be a self-recovery action for the requester, but it discharges to the designated recipient regardless.

### Finding Description
In `v3/src/core/ProvisionerV2.sol`:

- `requestDeposit(...)`/`requestRedeem(...)` (public overloads, lines ~763-840) let `msg.sender` supply any `receiver` address for the request; only `_validateRequest` is called, which merely checks `receiver != address(0)` [1](#0-0) . There is no restriction requiring `receiver == msg.sender` or receiver approval for async requests (unlike sync `deposit`/`mint`, which enforce `_requireValidReceiver`) [2](#0-1) .
- `cancelRequest` requires `msg.sender == request.user` to authorize self-cancellation [3](#0-2) , but the actual refund destination is computed by `_clearHashAndTransferRefund(token, request, msg.sender, refundAmount, token)`, which calls `_transferWithFallback(transferToken, requester, request.receiver, amount)` [4](#0-3) [5](#0-4) .
- `_transferWithFallback` explicitly prioritizes `receiver` over `requester`: `if (receiver == requester || !token.trySafeTransfer(receiver, amount)) { token.safeTransfer(requester, amount); }` [6](#0-5) . When `receiver != requester` and the receiver can accept the token, the escrowed asset (payment token for a deposit request, or vault units for a redeem request) is sent to `receiver`, not to the user who paid for and initiated the cancellation.
- The same routing exists in `refundRequest` (for expired requests) at line 314/317 [7](#0-6) , and in the solver-refund branches of `_solveDepositVaultFixedPrice`, `_solveRedeemVaultAutoPrice`, `_solveRedeemVaultFixedPrice`, and `_solveRequestDirect` [8](#0-7) [9](#0-8) .

No guard anywhere checks that the refund on cancellation/expiration goes back to `request.user` (the party who transferred the escrowed tokens into the Provisioner in `requestDeposit`/`requestRedeem`, lines 784/832 [10](#0-9) [11](#0-10) ). This mirrors exactly the Dinari root cause: the requester ("sponsor" confirmed "an account may place an order for another account") self-cancels expecting to recover their own escrowed funds, but the code sends the refund to the (potentially third-party) `receiver` instead.

### Impact Explanation
The user who deposited tokens (or units, for a redeem) loses their escrowed principal to the designated `receiver` upon cancellation or expiration, rather than recovering it. This is a direct, unauthorized loss of the requester's funds to a third party whenever `receiver != request.user` — e.g., a user requesting a deposit/redeem on behalf of another account, or a user who mis-specifies `receiver` (typo/phishing UI), then attempts to cancel to recover their own assets. Because this affects the requester's own principal that was already pulled into escrow, it constitutes real fund loss, not merely misdirected proceeds of a successful trade.

### Likelihood Explanation
Feasible with only ordinary-user actions and no privileged role: any account can call `requestDeposit`/`requestRedeem` with an arbitrary `receiver`, then call `cancelRequest` (if `_depositCancellationsEnabled`/`_redeemCancellationsEnabled` is on) or wait for `deadline` to pass and call `refundRequest` (permissionless post-deadline). The only preconditions are that async deposits/redeems are enabled for the token and (for `cancelRequest`) that self-cancellation is enabled — both are normal operating configurations, not privileged bypasses.

### Recommendation
On cancellation and expiration/refund paths (`cancelRequest`, `refundRequest`, and the expired branches inside `_solveDepositVaultFixedPrice`/`_solveRedeemVaultAutoPrice`/`_solveRedeemVaultFixedPrice`/`_solveRequestDirect`), return the escrowed asset to `request.user` (the party who funded escrow) rather than `request.receiver`, or require `request.receiver == request.user` for requests that are eligible for self-cancellation/refund. Preserve `receiver`-directed routing only for the successful "solved" branches where the request outcome (units/tokens for a completed trade) is intentionally directed to a beneficiary.

### Proof of Concept
1. On a local fork, use an authorized account to enable async deposits for a token and enable `_depositCancellationsEnabled` (via `requiresAuth` setter) in `ProvisionerV2`.
2. Alice (ordinary user) approves the deposit token and calls `requestDeposit(token, tokensIn, minUnitsOut, solverTip, deadline, maxPriceAge, isFixedPrice, receiver = Bob)` — a legitimate "deposit on behalf of another account" flow; `tokensIn` is pulled from Alice into `ProvisionerV2` escrow.
3. Before the request is solved, Alice calls `cancelRequest(token, request)` from her own address (satisfies `msg.sender == request.user`).
4. Assert: Bob's token balance increases by `refundAmount` and Alice's balance is unchanged (net of the deposited amount) — i.e., Alice's own escrowed tokens were sent to Bob, not refunded to Alice, despite Alice being the one who cancelled to recover her funds.
5. Repeat with `refundRequest` after `deadline` passes without solving, observing the same misdirected refund to `receiver`.

    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
    }
