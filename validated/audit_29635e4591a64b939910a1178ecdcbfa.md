### Title
Stale per-epoch instant-withdraw ledger entries are never cleared on claim, permanently freezing defaulted-epoch recovery claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to CVE-2023-42794 (a resource is opened but never cleaned up, and the stale record poisons later processing), `claimInstantWithdrawRequest` clears the aggregate `instantWithdrawsRequests[_user]` but never deletes the per-epoch records `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. When a later default finalizes on that same epoch, `_claimDefaultedInstantWithdrawRequest` reads the stale, inflated per-epoch basis and subtracts it from the now-smaller aggregate, reverting on underflow. The affected user's recovery claim is permanently bricked — the equivalent of a temp file that was never deleted now blocking the cleanup path.

### Finding Description
In `requestInstantWithdraw` the vault records three ledgers: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` (`IdleCreditVault.sol:366-374`).

The normal claim path only clears the aggregate: [1](#0-0) 

`instantWithdrawsRequests[_user]` is zeroed, but `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are left untouched — the "file is never deleted".

On default, `_claimDefaultedInstantWithdrawRequest` re-derives the claim from the per-epoch mapping: [2](#0-1) 

Because `claimBasis` includes the already-claimed amount while `instantWithdrawsRequests[_user]` does not, `instantWithdrawsRequests[_user] -= claimBasis` underflows and reverts. There is no other path that clears the stale per-epoch entry, so the revert is permanent. The same stale `instantWithdrawClaimsByEpoch[defaultEpoch]` total also corrupts the aggregate accounting (`instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` over-decrements), which can prematurely zero `pendingInstantWithdraws` via the `claimBasis >= pending ? 0 : pending - claimBasis` clamp, distorting the unfunded-remainder tracking used during recovery distribution.

### Impact Explanation
Any user who (a) successfully claimed an instant withdrawal during an epoch and (b) has any further instant-withdraw receipt outstanding in that same epoch when the borrower defaults loses their entire defaulted-epoch recovery claim: every call to `claimInstantWithdrawRequest` reverts forever. The loss equals their post-haircut recovery amount (`claimBasis * defaultRecoveryPrice / RECOVERY_FULL`). This is permanent freezing/theft of unclaimed recovery funds, not a pure gas DoS. Additionally the corrupted `instantWithdrawClaimsByEpoch`/`pendingInstantWithdraws` bookkeeping can misattribute reserve funding across claimants.

### Likelihood Explanation
Requires only an unprivileged tranche holder performing two ordinary actions (request instant withdraw, claim, request again) during one epoch, followed by a borrower default — an event the protocol explicitly supports via `finalizeDefaultRecovery`/`defaultRecoveryEpoch`. No privileged misbehavior is needed; the attacker is just a normal lender whose own honest activity poisons their claim. Instant-withdraw mode is a supported epoch configuration (`setInstantWithdrawParams`).

### Recommendation
In `claimInstantWithdrawRequest`, also clear the per-epoch records for each epoch contributing to the claimed amount (or track the current open epoch and zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` correspondingly). Alternatively, have `_claimDefaultedInstantWithdrawRequest` reconcile `claimBasis` against `instantWithdrawsRequests[_user]` and clamp/skip stale basis rather than underflowing, and add a regression test covering claim-then-default in the same epoch.

### Proof of Concept
Foundry fork PoC outline (standard epoch variant, instant withdrawals enabled via `cdoEpoch.setInstantWithdrawParams(delay, minAprDiff, false)`):

```solidity
// 1. Epoch N running. KYC'd lender alice deposits and holds tranche tokens.
uint256 tranches = _depositWithUser(alice, 100e6);

// 2. Alice requests an instant withdraw of X, waits instantDelay, and claims.
vm.prank(alice); cdoEpoch.requestInstantWithdraw(X, address(tranche));
skip(instantDelay + 1);
vm.prank(alice); cdoEpoch.claimInstantWithdrawRequest();
// Alice is paid, but instantWithdrawsRequestsByEpoch[alice][N] == X remains
// and instantWithdrawClaimsByEpoch[N] still counts X.

// 3. Alice requests a second instant withdraw of Y in the same epoch N.
vm.prank(alice); cdoEpoch.requestInstantWithdraw(Y, address(tranche));
// instantWithdrawsRequests[alice] == Y
// instantWithdrawsRequestsByEpoch[alice][N] == X + Y  (stale X included)

// 4. stopEpoch: borrower repays nothing -> default path.
//    finalizeDefault / finalizeDefaultRecovery set defaultRecoveryEpoch = N.

// 5. Alice tries to claim her recovery on the defaulted receipt Y.
vm.prank(alice);
vm.expectRevert(); // underflow: instantWithdrawsRequests[alice](Y) -= claimBasis(X+Y)
cdoEpoch.claimInstantWithdrawRequest();
// Permanently bricked: every subsequent call reverts identically,
// and there is no admin or user path to delete the stale per-epoch entry.
```

Verified from code: the per-epoch mappings are written at request time (`IdleCreditVault.sol:371-372`), never cleared on the normal claim path (`IdleCreditVault.sol:387-392`), and consumed raw at default claim time (`IdleCreditVault.sol:844-848`). The one aspect not fully verified within available context is exactly how `finalizeDefaultRecovery` sizes the reserve from `instantWithdrawClaimsByEpoch`, so the secondary accounting-corruption impact should be confirmed against that function, but the per-user permanent claim freeze follows directly from the cited lines.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
