### Title
Missing allowlist/authorization check in legacy Web API trigger gateway handler allows unauthenticated broadcast to all DON nodes - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The `HandleLegacyUserMessage()` function in the `capabilities` gateway handler processes incoming legacy user requests (routed via `gateway.ProcessRequest` for any request that carries a `DonId`) and, aside from basic payload/timestamp checks, forwards the request to every node in the DON without any allowlist or caller-authorization check. This mirrors the OmniPortal `_xcall()` bug class in the external report: a public-facing entrypoint accepts and propagates an unvalidated/unauthorized request to downstream infrastructure because a required gating check was never implemented, only left as a TODO.

### Finding Description
`gateway.ProcessRequest()` routes any incoming JSON-RPC request that includes `Body.DonId` as a "legacy request" straight to `handler.HandleLegacyUserMessage()` after only signature-format validation (`msg.Validate()`), not caller authorization: [1](#0-0) 

Inside `HandleLegacyUserMessage()`, the code decodes the payload, checks the payload is non-empty and not stale, and then reaches an explicit `// TODO: apply allowlist and rate-limiting here` comment before validating the method name and broadcasting the request to every DON member: [2](#0-1) 

No allowlist, workflow-owner check, or sender authorization equivalent to the vault handler's `AllowListBasedAuth`/`Authorizer` pipeline (see `core/capabilities/vault/allow_list_based_auth.go` and `gateway_vault_request_processor.go`) is applied here. Any caller who can reach the gateway's HTTP endpoint and craft a validly-signed `api.Message` with `Method: web_api_trigger` can have it fanned out to all nodes of the target DON — this is exactly analogous to the `_xcall()` bug where the destination-validity check (`isSupportedChain`) was omitted and only later "moved"/added, while the request was still allowed to propagate downstream (increment `outXStreamOffset`) before the check existed. [3](#0-2) 

By contrast, other gateway-facing paths (vault gateway handler, v2 HTTP trigger handler) do implement authorization before forwarding to nodes — e.g., `GatewayHandler.HandleGatewayMessage` calls `requestProcessor.ProcessRequest` (which runs `AuthorizeRequest`) before dispatching: [4](#0-3) 
and the v2 HTTP trigger handler documents an explicit "Authentication: Verifies JWT token ... Rate Limiting" step before node distribution, per its own design doc. The legacy capabilities handler lacks this parity.

### Impact Explanation
Because the request is broadcast to every member of the DON via `don.SendToNode` with no allowlist/authorization gate, an unprivileged/unauthenticated caller (any client able to reach the gateway's public HTTP endpoint) can cause the DON to process arbitrary `web_api_trigger` requests. This can be used to:
- Trigger workflow execution paths on all DON nodes without being an authorized workflow owner, i.e., unauthorized job/trigger invocation (paralleling "unauthorized job run" in the analog scope).
- Flood/spam all nodes of a DON with attacker-controlled trigger payloads, since rate limiting is likewise not applied at this stage (also called out in the same TODO), which is a denial-of-service vector analogous to the XStream DoS in the source report.

### Likelihood Explanation
High likelihood of reachability: `gateway.ProcessRequest()` is the direct entrypoint invoked by the gateway's public HTTP server for any external caller, and any message containing `Body.DonId` is routed as a "legacy request" straight into this code path with only structural/signature validation, not authorization. The missing check is explicitly flagged in-code with a `TODO`, confirming it was never implemented rather than intentionally omitted for a benign reason.

### Recommendation
Implement the allowlist/authorization check called out by the TODO in `HandleLegacyUserMessage` before dispatching to DON members — analogous to the `allowListBasedAuth`/`Authorizer` pattern already used by the vault gateway handler (`core/capabilities/vault/gw_handler.go`, `allow_list_based_auth.go`). At minimum:
1. Verify the sender/signer of the incoming legacy message against a registered/allowlisted sender set (e.g., workflow-registry-backed allowlist) before processing `MethodWebAPITrigger`.
2. Apply per-sender/per-DON rate limiting prior to fan-out to `don.SendToNode`.
3. Remove/resolve the `// TODO: apply allowlist and rate-limiting here` comment once the check is enforced, and add regression tests asserting that unauthorized/non-allowlisted senders are rejected before any node dispatch occurs.

### Proof of Concept
Not independently exploitable in a live environment from this static analysis, but the code path is fully traceable:
1. Attacker sends a validly-formed & signed legacy JSON-RPC request (any keypair can sign; `msg.Validate()` only checks structural signature validity, not that the signer is authorized) with `Body.DonId` set to a target DON and `Body.Method = "web_api_trigger"` to the gateway's public HTTP endpoint.
2. `gateway.ProcessRequest` classifies it as a legacy request, resolves the handler by `DonId`, and calls `h.HandleLegacyUserMessage(ctx, msg, callback)`. [5](#0-4) 
3. `HandleLegacyUserMessage` passes the payload-shape/staleness checks, skips the (unimplemented) allowlist/rate-limit check, and forwards the request to every node in `h.donConfig.Members` via `don.SendToNode`. [6](#0-5) 

I was not able to confirm from the index alone whether an outer layer (e.g., TLS client-cert allowlisting at the gateway's HTTP transport, if configured) restricts callers before reaching `ProcessRequest`; if such network-layer gating exists in a specific deployment, it would need to be checked against the "unprivileged client request" threat model to fully assess exploitability. Based purely on the application-layer code visible here, no caller-authorization check exists between HTTP ingress and DON-wide message broadcast for legacy `web_api_trigger` requests.

	body := msg.Body
	var payload webapicap.TriggerRequestPayload
	codec := api.JsonRPCCodec{}
	err := json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw(ErrDecodingPayload, "err", err)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload+" "+err.Error(),
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}
