### Title
Instant-withdraw path in `requestWithdraw` skips the `interestForOverUnderPerformance`/`pendingWithdrawFees` bookkeeping, inflating `expectedEpochInterest` after a BB exit - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
In `IdleCDOEpochVariant.requestWithdraw`, when instant withdraw is enabled and the APR dropped (`lastEpochApr > currentApr + instantWithdrawAprDelta`), the function burns the user's tranches via `creditVault.requestInstantWithdraw` + `_withdrawOps` and returns early. This early return skips the accounting updates performed on the normal path: `pendingWithdrawFees += totalFees`, and critically `interestForOverUnderPerformance += diff`, which is later folded into `expectedEpochInterest` at `startEpoch` to correct what the borrower owes after a tranche exit.

### Finding Description
Analogous to the referenced bug — where `dyad.burn` changes the debt but `updateXP` is only executed under a collateral condition (`address(vault) == KEROSENE_VAULT` and `depositAmount != 0`), leaving `balanceOfNote` stale — here `_withdrawOps` burns tranche tokens and reduces NAV (the "debt change"), but the compensating interest bookkeeping is only executed on the non-instant branch.

On the normal path (lines 772-790), `_calcInterestWithdrawRequest` returns `_diff` — the difference between the TVL-proportional interest and the tranche-split interest of the withdrawn amount — and `interestForOverUnderPerformance += diff` adjusts the next epoch's `expectedEpochInterest`:

- For a **BB** withdraw, `diff` is negative: the withdrawn junior principal would have earned an outsized interest share, so `expectedEpochInterest` must be *reduced*.
- For an **AA** withdraw, `diff` is positive: the senior's overperformance that would have flowed to BB is preserved.

On the instant-withdraw branch (lines 761-769) neither adjustment happens, nor is the upfront management fee (`_totalWithdrawFees`) charged:

```solidity
if (_isInstantWithdrawEnabled()) {
  uint256 currentApr = creditVault.unscaledApr();
  if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
    creditVault.requestInstantWithdraw(_underlyings, msg.sender);
    _withdrawOps(_amount, _underlyings, _tranche);
    return _underlyings;   // pendingWithdrawFees and interestForOverUnderPerformance never updated
  }
}
```

A BB instant-withdraw therefore leaves `expectedEpochInterest` overstated: the borrower is still charged epoch interest as if the exited junior principal (with its high junior share) were still deployed. That excess interest is paid by the borrower at `stopEpoch` and distributed through `_updateAccounting`/`trancheAPRSplitRatio` predominantly to remaining AA holders.

### Impact Explanation
An unprivileged KYC'd lender holding both a BB and an AA position can, when the manager lowers the APR (a normal operational event that enables the instant path), instantly withdraw the BB position without the corresponding `diff` correction, while keeping the AA position. The overstated `expectedEpochInterest` is funded by the honest borrower at `stopEpoch` and flows disproportionately to the attacker's residual AA holdings — a direct transfer of value (theft of yield / interest the pool was not owed), quantified by `-diff ≈ withdrawnBB × apr × (1 - splitRatio) × epochDuration/365d`. Equivalently, the skipped upfront management fee (`_totalWithdrawFees` over `epochDuration + remaining buffer`) is revenue permanently lost to `feeReceiver`/owner.

### Likelihood Explanation
- Trigger condition is only that `lastEpochApr` exceeds `unscaledApr + instantWithdrawAprDelta` — set entirely by honest manager APR updates, which occur routinely at `stopEpoch`.
- Requires no privileged action, no default, no timing race beyond one epoch boundary; works in fixed-APR, non-programmable deployments where instant withdrawals are enabled (`_isInstantWithdrawEnabled()` true by default).
- Every BB instant withdraw deterministically misstates `expectedEpochInterest` in the attackers-favor direction when paired with a retained AA position.

### Recommendation
Apply the same withdrawal bookkeeping on the instant branch: compute `(interest, diff) = _calcInterestWithdrawRequest(_underlyings, _tranche)` before `_withdrawOps`, do `interestForOverUnderPerformance += diff`, and charge the management/performance fees (`_totalWithdrawFees`) against the instant-withdrawn amount (or document why instant withdrawers are exempt and instead decrement `expectedEpochInterest` by the withdrawn principal's full share `interestWithoutSplitRatio` so the borrower is not overcharged).

### Proof of Concept
Foundry fork PoC sketch (modeled on `test/foundry/IdleCreditVault.t.sol` helpers `_startEpochAndCheckPrices`/`_stopEpochAndCheckPrices`):

```solidity
// 1. Attacker deposits into BOTH AA and BB (KYC'd wallet).
idleCDO.depositAA(amountAA); idleCDO.depositBB(amountBB);

// 2. Epoch 0 runs at high APR; manager then lowers APR at stopEpoch
//    so that lastEpochApr > unscaledApr + instantWithdrawAprDelta.
_stopEpochWithNewApr(lowApr);   // honest manager action

// 3. Epoch 1 starts. Attacker instantly withdraws the full BB position.
//    Early return skips interestForOverUnderPerformance += diff (diff < 0).
uint256 expectedBefore = cdoEpoch.expectedEpochInterest();
cdoEpoch.requestWithdraw(bbBal, BBTranche);   // takes instant branch
uint256 expectedAfter = cdoEpoch.expectedEpochInterest();
assertEq(expectedAfter, expectedBefore);      // BUG: should have decreased by -diff

// 4. Manager stops epoch 1; borrower (honest) repays the overstated
//    expectedEpochInterest. Excess accrues mostly to AA via trancheAPRSplitRatio.
//    Attacker claims inflated AA yield > pro-rata entitlement.
```

Broken invariant: fair interest accounting — `expectedEpochInterest` must reflect the actually-deployed principal after any exit; the instant branch leaves it stale exactly as `balanceOfNote` is left stale when `updateXP` is skipped.
