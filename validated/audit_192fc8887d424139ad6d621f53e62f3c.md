### Title
Attacker-controlled `MessageId` collision lets an unprivileged sender overwrite another user's pending `savedCallbacks` entry, causing cross-user response hijacking - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each pending request under `h.savedCallbacks[msg.Body.MessageId]` without checking whether that key is already occupied by an in-flight request from a different sender. Because `MessageId` is fully attacker-chosen (it is only length/format validated in `Message.Validate()` and signed only by the sender's own key, never bound to a global uniqueness constraint), an unprivileged attacker can submit a `web_api_trigger` request with the same `MessageId` as a legitimate victim's outstanding request, silently overwriting the victim's callback and hijacking the victim's DON response.

### Finding Description
- In `core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage` unconditionally writes: `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` [1](#0-0)  with no check for an existing entry under the same key.
- `MessageId` originates entirely from client input. For legacy JSON-RPC requests it is copied straight from the request `ID` field: `m.Body.MessageId = req.ID` [2](#0-1) , and `Message.Validate()` only enforces length/format constraints on `MessageId`, not uniqueness or binding to sender identity [3](#0-2) .
- Any client can freely choose an arbitrary `MessageId` string and sign it with their own key via `msg.Sign(key)` — the signature only proves who sent that particular message, it does not prevent another sender from reusing the same `MessageId` value.
- When a DON node later responds, `handleWebAPITriggerMessage` looks up and deletes `h.savedCallbacks[msg.Body.MessageId]` and forwards the response to whatever callback is currently stored there: [4](#0-3) .
- Exploit flow: victim A sends a `web_api_trigger` request with `MessageId = "X"`, and `HandleLegacyUserMessage` stores `savedCallbacks["X"] = callbackA`. Before the DON responds, attacker B sends their own signed `web_api_trigger` request also using `MessageId = "X"`, which overwrites `savedCallbacks["X"] = callbackB`. When the DON node responds to A's original request (with the same `MessageId` "X"), `handleWebAPITriggerMessage` delivers the response to `callbackB`, so the attacker receives A's response, and A's callback is silently dropped (never notified, or times out).
- The v2 handler (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`) has this exact class of check and explicitly rejects duplicate/in-flight request IDs with a `jsonrpc.ErrConflict`/"in-flight request" error (confirmed by `TestHttpTriggerHandler_HandleUserTriggerRequest`'s "duplicate request ID" subtest) [5](#0-4) , but the legacy v1 handler analyzed here has no equivalent protection.

### Impact Explanation
This allows an unauthenticated/unprivileged attacker to hijack another user's pending gateway response (cross-user response confusion), matching the "unauthorized action on/exposure of another user's request/response data" bounty impact class. Depending on payload contents returned by the DON/HTTP capability, this could expose data intended only for the victim, and additionally causes denial-of-service for the victim's specific request (silently dropped, no response delivered).

### Likelihood Explanation
Exploitability requires no privilege beyond normal unauthenticated access to submit signed `web_api_trigger` gateway messages (the attacker just needs any valid key to sign their own message body — the signature does not need to match the victim). The main practical constraint is that the attacker must guess/know the victim's chosen `MessageId` and race the overwrite before the DON responds; if IDs are predictable, sequential, or reused/echoed by client tooling (e.g., request tracing conventions), this is straightforward and repeatable.

### Recommendation
In `HandleLegacyUserMessage`, before inserting into `savedCallbacks`, check whether an entry already exists for `msg.Body.MessageId` and reject the new request with a conflict/duplicate error (mirroring the v2 `http_trigger_handler`'s in-flight-request check) instead of silently overwriting it. Consider additionally namespacing `savedCallbacks` keys by sender address plus `MessageId` to prevent any possibility of cross-sender collision.

### Proof of Concept
Go handler-level test plan (extending `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Build handler via `setupHandler(t)`.
2. Craft victim message `msgA` via `triggerRequest` with a fixed `MessageId` (e.g., "shared-id") signed by `nodes[0].PrivateKey` (victim key), call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)`.
3. Craft attacker message `msgB` with the **same** `MessageId` "shared-id" but signed with a different attacker private key, call `handler.HandleLegacyUserMessage(ctx, msgB, cbB)`.
4. Assert: without the fix, the second call succeeds and overwrites the map entry (no error returned, `cbA` is now orphaned).
5. Simulate DON response for the victim's original request (`resp` built from `msgA`), call `handler.HandleNodeMessage(ctx, resp, nodes[0].Address)`.
6. Assert (bug reproduction): `cbB.Wait(ctx)` receives the victim's response payload (cross-user leak), while `cbA.Wait(ctx)` times out/never resolves.
7. After applying the fix, assert the second `HandleLegacyUserMessage` call for `msgB` returns a conflict/duplicate error and `cbA` still correctly receives the DON response for `msgA`.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
