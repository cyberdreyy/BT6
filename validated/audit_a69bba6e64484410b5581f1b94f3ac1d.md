### Title
Multisig request executes below `num_confirmations` live members due to stale confirmations surviving `DeleteMember` - (File: `multisig2/src/lib.rs`)

### Summary
`confirm()` compares `confirmations.len() as u32 + 1` against `self.num_confirmations`, where `confirmations` is a `HashSet<String>` of member identities that previously confirmed a request. `delete_member()` only purges confirmations for requests that were *added by* the removed member; it never scans other pending requests to strip that member's own confirmation entries from their `HashSet<String>`. A member's stale confirmation therefore keeps counting toward the threshold forever, even after that member is removed (and regardless of whether they are later re-added), letting a request execute with fewer *live* confirming members than `num_confirmations`.

### Finding Description
The invariant the code is supposed to maintain is:
`confirmations.len() (as counted in confirm()) == |{ live members who confirmed request_id }|`

In `confirm()`:
```rust
let mut confirmations = self.confirmations.get(&request_id).unwrap();
...
if confirmations.len() as u32 + 1 >= self.num_confirmations {
```
`confirmations` is a raw `HashSet<String>` of `MultisigMember::to_string()` values recorded at confirmation time — it is never re-validated against the current `self.members` set. [1](#0-0) 

`delete_member()` is the only code path that ever mutates `confirmations` in response to membership changes, and it only touches confirmation sets belonging to requests the removed member itself *added* (`r.member == member`), not sets where the removed member is merely a *confirmer*:
```rust
let request_ids: Vec<u32> = self.requests.iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
self.num_requests_pk.remove(&member.to_string());
self.members.remove(&member);
``` [2](#0-1) 

`assert_valid_request()` only checks that the *caller* is currently a member and that the request/confirmation entries exist — it never re-checks that entries already stored inside a request's `confirmations` set still belong to current members: [3](#0-2) 

Exploit flow (all state transitions performed via the contract's own public API):
1. Multisig has members `{A,B,C,D}`, `num_confirmations = 3`.
2. `A` calls `add_request` to create request `R` (e.g. `Transfer` of contract funds).
3. `B` calls `confirm(R)` → `confirmations(R) = {B}`.
4. `C` calls `confirm(R)` → `confirmations(R) = {B,C}` (len 2, threshold not yet met since `2+1<3`... actually `2>=3` false, still pending).
5. The group later executes a *separate*, independently-confirmed `DeleteMember{C}` request (a normal member-rotation action, e.g. because `C`'s key is suspected compromised). `delete_member` removes `C` from `self.members`, but since `C` did not *add* `R`, `confirmations(R)` is left untouched: `{B,C}`.
6. `D` (a live member) later calls `confirm(R)`. The check computes `confirmations.len() (=2) + 1 = 3 >= num_confirmations (3)` → **true**, and `R` executes immediately via `self.execute_request(request)`.

Only `B` and `D` are live members who actually confirmed `R` at execution time — two live confirmations — yet the contract enforced and believed three. `C`'s stale, pre-removal confirmation counted as if it were a current, valid member's approval. Re-adding `C` afterward changes nothing (it does not clear or re-validate the stale entry; it only resets `num_requests_pk`), so the same phantom confirmation persists across removal *and* re-addition indefinitely until the specific request is finally deleted or executed.

No existing guard (`assert_valid_request`, `current_member`, `assert_self_request`) inspects historical entries inside a request's `confirmations` set against the live `self.members` set, so nothing prevents this divergence.

### Impact Explanation
This breaks the core multisig safety guarantee — a request (e.g. a `Transfer` moving NEAR out of the multisig account) can be executed with fewer live-member confirmations than the configured `num_confirmations`. This directly matches the enumerated Critical impact "a multisig request executed below `num_confirmations` live members." The effect is repeatable for any pending request that a subsequently-removed member had confirmed, and the blast radius covers any multisig account using this contract that ever rotates membership while requests are outstanding.

### Likelihood Explanation
The bug requires no attacker to bypass any authorization check by force — it is triggered purely by the normal, expected sequence of multisig operations (create request, confirm, remove a member, confirm again), all performed through the contract's public, documented interface. No special privileges beyond ordinary multisig usage are needed to trigger it, and member rotation (removing a suspect or departing member) is a routine, expected operation for any multisig, making the precondition realistic and low-cost to hit accidentally or deliberately by a member who confirms a self-serving transfer shortly before being rotated out.

### Recommendation
In `delete_member`, iterate over all pending requests' confirmation sets (not just requests authored by the removed member) and strip the removed member's identity string from each `confirmations` entry. Alternatively, change `confirm()` to recompute the live-confirmation count by intersecting the stored `confirmations` set with `self.members` (filtering out entries whose corresponding `MultisigMember` no longer exists) before comparing against `num_confirmations`.

fn test_stale_confirmation_survives_member_removal() {

    // 6. assert_eq!(c.get_confirmations(R).len(), 2); // BUG: still contains C's stale entry

```
The key assertions: after step 6, `c.get_confirmations(request_id)` still contains the string for the removed member `C`; after step 7, `confirm()` executes the request even though only two currently-live members (`B`, `D`) ever confirmed it, proving `confirmations.len() + 1 >= num_confirmations` was satisfied using a stale, non-live entry.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
