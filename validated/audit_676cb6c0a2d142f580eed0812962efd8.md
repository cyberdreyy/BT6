### Title
Run-role user can globally reset a chain's LogPoller checkpoint via POST /v2/lp_skip_to_block, affecting all jobs on that chain - ([File: core/web/router.go], [File: core/web/lp_skip_controller.go])

### Summary
The route `POST /v2/lp_skip_to_block` is registered with only `auth.RequiresRunRole`, the lowest authenticated privilege tier, and its handler `LPSkipController.LPSkipToBlock` repositions the shared, chain-wide `LogPoller` checkpoint identified only by `chain-id`, with no job ID or ownership parameter anywhere in the request or handler logic.

### Finding Description
The route is wired as: [1](#0-0) 

`LPSkipToBlock` validates only `blockNumber`, `family`, and `chain-id`, then calls `c.App.LPSkipToBlock(ctx, request.Family, request.ChainID, request.BlockNumber)`: [2](#0-1) 

There is no job identifier in the request struct or the validated fields, and no check that the calling user owns or administers any specific job on that chain: [3](#0-2) 

The `LogPoller` for a given `chain-id` is a single shared component consumed by every job/contract listener on that chain (this is standard chainlink architecture — one `LogPoller` instance per EVM chain, shared by all log-based jobs such as OCR2, VRF, Automation, etc.). Repositioning its checkpoint to an attacker-chosen block affects log replay/pruning state for every job on that chain, not just a job the caller administers. Since the route only requires `RequiresRunRole` (satisfied by any API token/session with the lowest "run" permission, which per the design is meant to allow only triggering job runs, e.g. `POST /v2/jobs/:ID/runs`), a low-privilege run-role credential holder can invoke this chain-wide administrative action.

### Impact Explanation
A run-role user (not an admin/edit-role user) can force the shared `LogPoller` for a chain to reprocess or skip blocks. This can cause: (a) unfinalized logs being dropped, causing another job's on-chain event triggers to be silently missed; or (b) forcing re-emission of already-processed logs, causing duplicate pipeline runs for jobs the caller does not own. This is a cross-job/cross-tenant availability and data-integrity impact reachable with a minimally privileged credential, matching "unauthorized action affecting another user's job" impact class.

### Likelihood Explanation
Any credential with `run` role (the least privileged authenticated role, intended only to trigger job runs via `/v2/jobs/:ID/runs`) can call this endpoint directly with just `family` and `chain-id`, both trivially discoverable/guessable (e.g., `"evm"`, `"1"`). No job ID, no ownership proof, and no per-job scoping is required, making this trivially reproducible and repeatable by any run-role holder in a multi-tenant/multi-job node.

### Recommendation
Require `auth.RequiresAdminRole` (matching other chain-wide operational endpoints like `/log`, `/keys/*` deletion, `/transfers`) for `/v2/lp_skip_to_block`, since it is a chain-level operational/debug action, not a per-job run action appropriate for the `run` role. Alternatively, scope the action to specific jobs/contracts and verify the caller owns/administers those jobs before allowing checkpoint manipulation.

### Proof of Concept
Go handler-level integration test plan:
1. Set up two independent jobs (Job A, Job B) both consuming logs via the same EVM chain's `LogPoller` (e.g., two OCR2/log-triggered job specs on chain-id `1`).
2. Create a user/API token with only the `run` role (not `admin`/`edit`).
3. As the run-role user, call `POST /v2/lp_skip_to_block` with `{"family":"evm","chain-id":"1","blockNumber":<N>}` where `<N>` is chosen to skip over blocks containing logs relevant to Job B (owned/administered by a different user/team).
4. Assert the handler returns 200 (`LPSkipToBlockResponse`), confirming `App.LPSkipToBlock` was invoked without any per-job authorization check — verify via `lp_skip_controller_test.go` patterns that no job ownership parameter is validated in `LPSkipToBlockRequest`.
5. Assert that the `LogPoller` for chain `1` (shared instance) reports the new checkpoint, and that Job B's log-consumption state (next block to process) is altered by an action taken by a user with no relationship to Job B, demonstrating cross-job isolation is not enforced.

```go
func (c *LPSkipController) LPSkipToBlock(gctx *gin.Context) {
	var request LPSkipToBlockRequest
	if err := gctx.ShouldBindJSON(&request); err != nil {
		jsonAPIError(gctx, http.StatusUnprocessableEntity, err)
		return
	}
	if request.BlockNumber < 2 {
		jsonAPIError(gctx, http.StatusUnprocessableEntity, errors.Errorf("block number must be >= 2: %v", request.BlockNumber))
		return
	}

	if request.Family == "" {
		jsonAPIError(gctx, http.StatusUnprocessableEntity, errors.New("chain family was not provided"))
		return
	}
	if request.Family != relay.NetworkEVM {
		jsonAPIError(gctx, http.StatusUnprocessableEntity, errors.Errorf("unsupported chain family %q, only %s is supported", request.Family, relay.NetworkEVM))
		return
	}

	if strings.TrimSpace(request.ChainID) == "" {
		jsonAPIError(gctx, http.StatusUnprocessableEntity, errors.New("chain-id was not provided"))
		return
	}

	ctx := gctx.Request.Context()
	if err := c.App.LPSkipToBlock(ctx, request.Family, request.ChainID, request.BlockNumber); err != nil {
		if errors.Is(err, chainlink.ErrNoSuchRelayer) {
			jsonAPIError(gctx, http.StatusBadRequest, err)
			return
		}
		jsonAPIError(gctx, http.StatusInternalServerError, err)
		return
	}
```
