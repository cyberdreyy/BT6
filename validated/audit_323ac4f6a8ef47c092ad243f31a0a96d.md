## Title
Cross-Workflow HTTP Response Cache Poisoning via `WorkflowID`-Insensitive Cache Key - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
The gateway's outbound-HTTP response cache keys entries only by `req.Hash()` — computed from method, URL, headers, body, and `WorkflowOwner` — while explicitly excluding `WorkflowID`. This mirrors the ThorChain root cause: a value used to authorize/scope a later action (there, an allowance amount; here, a cache entry) is decoupled from the actual identity/state it should track, so a later, unrelated request can consume state that was established by a different, earlier context.

### Finding Description
`responseCache.Fetch`/`Set` key the cache exclusively by `gateway.OutboundHTTPRequest.Hash()`. The test suite documents the exact hashing semantics: identical `WorkflowOwner` produces identical hashes regardless of `WorkflowID`, and `WorkflowID` is explicitly excluded from the hash [1](#0-0) , while requests with different `WorkflowOwner` do produce different hashes [2](#0-1) . The cache struct comment itself states the key is "a hash of the request (method, URL, headers, body, workflowOwner)" [3](#0-2) .

The `Fetch` path returns any prior cached response for a matching key without any further per-workflow authorization check: it looks up by `cacheKey := req.Hash()`, and on a hit returns the stored response directly to the caller [4](#0-3) . This is invoked from `makeOutgoingRequest`, which dispatches the (possibly stale, possibly cross-workflow) cached response straight back to whatever node/workflow made the current request [5](#0-4) .

The project's own README documents the intended security invariant that this code violates: "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [6](#0-5) . In reality, isolation is scoped only to `WorkflowOwner`, not `WorkflowID` — so any two workflows belonging to the same owner (a routine, unprivileged multi-workflow scenario) share cache entries for requests with identical method/URL/headers/body.

This is directly analogous to the ThorChain finding's root cause: an accounting/authorization value (there, `_vaultAllowance`, computed from a stale balance snapshot; here, a cached HTTP response, keyed on an incomplete identity tuple) is reused across a boundary (there, across users; here, across workflows) that the system nominally intends to keep separate, because the tracked/keyed value doesn't actually reflect the full scope it's meant to represent.

### Impact Explanation
An unprivileged workflow author who controls two (or more) workflows under the same `WorkflowOwner` — or any case where `WorkflowOwner` collides/is reused across logically distinct workflows — can have one workflow's cached HTTP response (potentially containing sensitive external-API data returned for that specific workflow's context) served to a different workflow that issues a request with the same method/URL/headers/body. This is a concrete cross-user/cross-workflow response confusion: data that should be isolated per workflow leaks across workflow boundaries within the same owner scope, and a workflow can also poison/short-circuit another workflow's outbound requests (e.g., causing it to receive a previously cached, possibly stale or attacker-influenced, 2xx/4xx response instead of hitting the live external endpoint).

### Likelihood Explanation
Any external-facing workflow owner can trigger this by simply running two workflows under the same owner that issue outbound HTTP action requests to the same URL with the same method/headers/body and enabling `CacheSettings.Store`/`MaxAgeMs`. No special privilege beyond normal workflow-authoring capability is required; the confusion is deterministic given the documented hash semantics, not a rare race condition.

### Recommendation
Include `WorkflowID` (and any other identity fields needed for correct isolation, e.g., workflow execution scoping if required by design) in the cache key computed by `Hash()`, or otherwise scope the `responseCache` map by workflow ID in addition to the request hash, so that cache entries are only ever returned to the workflow that created them, matching the isolation guarantee already claimed in the component's documentation.

### Proof of Concept
1. Workflow A (owner `0xabc`, `WorkflowID = "wf-A"`) issues an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", CacheSettings: {Store: true, MaxAgeMs: 600000}}`. The gateway fetches live data and, per `Set`/`Fetch`, stores it keyed by `req.Hash()` [7](#0-6) .
2. Workflow B (same owner `0xabc`, `WorkflowID = "wf-B"`) — a logically separate workflow — issues an identical `OutboundHTTPRequest` (same method/URL/headers/body) with `CacheSettings.MaxAgeMs > 0`.
3. Because `Hash()` ignores `WorkflowID` and only incorporates `WorkflowOwner` [1](#0-0) , Workflow B's `Fetch` call computes the same `cacheKey` as Workflow A's and receives Workflow A's cached response without ever calling the live HTTP endpoint [4](#0-3) .
4. This is directly demonstrated by the existing test `TestRequestHash`/`"having different workflowID results in same Hash"`, which asserts this exact behavior as current (intended, per the test) functionality [1](#0-0) , contradicting the workflow-isolation guarantee stated in the module's README.

```go
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}
```
