### Title
Stale per-epoch instant-withdraw residue permanently bricks a user's default-recovery claim - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a failure to wipe sensitive material when a buffer is freed: `kfree()` leaves derived keys behind in the slab. The direct analog in `IdleCreditVault` is a failure to wipe per-epoch receipt material when an instant-withdraw claim is paid: `claimInstantWithdrawRequest` zeroes only the aggregate `instantWithdrawsRequests[_user]` and leaves `instantWithdrawsRequestsByEpoch[_user][epoch]` populated. If the same epoch later ends in a borrower default, that leftover residue is re-added into the user's default claim basis, forcing an underflow revert that permanently blocks the user's legitimate recovery payout.

### Finding Description
`claimInstantWithdrawRequest` pays a funded instant receipt by burning the aggregate balance and clearing only `instantWithdrawsRequests[_user]`: [1](#0-0) 

The per-epoch mapping entry written in `requestInstantWithdraw` is never cleared on the funded path: [2](#0-1) 

Later, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — where `defaultEpoch = defaultRecoveryEpoch = epochNumber` at finalization (`finalizeDefaultRecovery`, line 693) — and subtracts that basis from the aggregate: [3](#0-2) 

If a user claimed a funded instant receipt in epoch N (residue `R` left at `instantWithdrawsRequestsByEpoch[user][N]`) and then opened a new instant receipt `s` in the same epoch N which is still unfunded when the borrower defaults, then at claim time:

- `claimBasis = instantWithdrawsRequestsByEpoch[user][N] = R + s`
- `instantWithdrawsRequests[user] = s`
- `instantWithdrawsRequests[user] -= claimBasis` computes `s - (R + s)` → arithmetic underflow → revert.

Because `claimInstantWithdrawRequest` is the only entry point and the revert happens before the funded-claim payout at line 387-392, the user's valid new receipt `s` can never be claimed. The same stale-residue pattern also exists for normal withdraws (`_claimFundedWithdrawRequest` clears `withdrawsRequests[_user]` and `lastWithdrawRequest` but leaves `withdrawsRequestsByEpoch` populated at line 338-348); there the epoch-advance gate prevents `defaultRecoveryEpoch` from colliding with a residue epoch, so it is a latent inconsistency rather than an exploitable path. The instant path has no epoch-advance requirement, which is what makes it reachable.

### Impact Explanation
Permanent freezing of unclaimed recovery funds. The victim's post-default instant receipt of `s` underlying can never be paid out: every `claimInstantWithdrawRequest` call reverts on the underflow in `_claimDefaultedInstantWithdrawRequest`. The corresponding `defaultRecoveryReserve` portion is stranded in the strategy (no non-owner sweep exists for reserve accounting; `transferToken` would also desync `defaultRecoveryReserve`). Quantified loss: `s * defaultRecoveryPrice / RECOVERY_FULL` per affected user — up to the full recovery value of the receipt.

### Likelihood Explanation
Requires a specific but plausible sequence, all with unprivileged/honest actors:

1. An epoch is running and the pool is in instant-withdraw mode with available liquidity.
2. User requests an instant withdrawal, the CDO pulls funds via `collectInstantWithdrawFunds`, and the user claims — leaving residue at the current epoch key.
3. The same user requests a second instant withdrawal in the same epoch (no epoch rollover needed since instant claims are not epoch-gated).
4. The borrower defaults and `finalizeDefaultRecovery` runs while `pendingInstantWithdraws != 0`, setting `defaultInstantWithdrawsFinalized = true` and `defaultRecoveryEpoch = epochNumber` — the same epoch key holding the residue.

No privileged misbehavior is needed; the manager/queue/CDO act honestly. The only timing requirement is two instant requests plus a default inside one epoch.

### Recommendation
Mirror the normal-withdraw cleanup in `_clearWithdrawClaimForEpoch` on the funded instant path: in `claimInstantWithdrawRequest`, before zeroing the aggregate, iterate/clear `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (and keep `instantWithdrawClaimsByEpoch` consistent if it is meant to track only unclaimed basis). Alternatively, subtract the claimed amount from the per-epoch entry instead of leaving it, so a later default finalization in the same epoch only sees genuinely unclaimed basis.

### Proof of Concept
Foundry fork PoC sketch (to be placed under `test/foundry/`):

```solidity
// Assume instant-withdraw mode pool, KYC'd `user`, honest borrower/manager.
_idleCDO.depositAA via user; epoch running (epochNumber == N).

// 1) First instant request, funded and claimed -> residue left
vm.prank(user);
cdoEpoch.requestInstantWithdraw(amount1);          // instantWithdrawsRequestsByEpoch[user][N] = a1
// CDO collects instant funds (getInstantWithdrawFunds / collectInstantWithdrawFunds path)
vm.prank(user);
cdoEpoch.claimInstantWithdrawRequest();            // aggregate = 0, byEpoch[N] still = a1  (BUG)

// 2) Second instant request in the SAME epoch, left partially/fully unfunded
vm.prank(user);
cdoEpoch.requestInstantWithdraw(amount2);          // byEpoch[N] = a1 + a2, aggregate = a2

// 3) Borrower defaults; stop epoch with default and finalize recovery
//    pendingInstantWithdraws != 0  ->  defaultInstantWithdrawsFinalized = true
//    defaultRecoveryEpoch = N
_stopEpochWithDefault();
finalizeDefault(recoveredAmount, manager);

// 4) User tries to claim legitimate recovery -> permanent revert
vm.prank(user);
vm.expectRevert();                                 // panic: arithmetic underflow at
                                                   // instantWithdrawsRequests[user] -= a1 + a2
cdoEpoch.claimInstantWithdrawRequest();
```

Assertions to add: `underlying.balanceOf(user)` never increases by `a2 * defaultRecoveryPrice / RECOVERY_FULL`, and `defaultRecoveryReserve` remains elevated by the stranded amount, proving permanent freeze rather than a transient DoS.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
