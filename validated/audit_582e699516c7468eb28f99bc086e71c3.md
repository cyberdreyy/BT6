### Title
Stop-epoch loss haircut skips stale receipts from earlier epochs, letting them claim at par and drain the funded pool - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` records a loss recovery price only under `lossRecoveryPriceByEpoch[epochNumber]` (the epoch that was open when `stopEpochWithDuration` ran), but `pendingWithdraws` — the basis used to compute `pendingToFund` — is a global aggregate that also contains receipts requested in earlier epochs that were never claimed. When a user holds pending receipts spanning two epochs and the later epoch is haircut, `_claimLossAdjustedWithdrawRequest` clears only the `lastWithdrawRequest` epoch's portion; the older portion survives in `withdrawsRequests` and is paid 1:1 by `_claimFundedWithdrawRequest`, even though the borrower underfunded the pool by a loss computed on the aggregate. The result is that early claimants with stale multi-epoch receipts siphon funds that were haircut-priced for later claimants.

### Finding Description
In `requestWithdraw`, the per-epoch receipt is recorded via `withdrawsRequestsByEpoch[_user][currentEpoch]`, while the liability is aggregated into `pendingWithdraws` (lines 279–293). A user may request in epoch N, let the epoch roll to N+1 without claiming, then request again — the guard at lines 263–271 only blocks re-requesting if `lossRecoveryPriceByEpoch[lastWithdrawRequest]` is set, which it isn't before the loss happens. `lastWithdrawRequest` is then overwritten to N+1.

When the manager stops epoch N+1 with a loss, `previewLossAdjustedWithdrawFunds` computes `pendingLoss` pro rata over the *entire* `pendingBasis` — including the attacker's epoch-N receipts (lines 440–459) — and `collectWithdrawFunds` stores the haircut solely under `lossRecoveryPriceByEpoch[epochNumber]` i.e. epoch N+1 (line 421).

On `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` (N+1), clears only `withdrawsRequestsByEpoch[_user][N+1]` at the haircut price, and `_clearWithdrawClaimForEpoch` subtracts only that epoch's amount from the aggregate (lines 789–836). Control then falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` — now containing only the stale epoch-N amount — at par, burning 1:1 (lines 319–349). The epoch-N share of the loss was priced into the funding but is never applied to the payout, so the strategy's funded underlying is overdrawn: later claimants (including other users' haircut receipts) are left short.

### Impact Explanation
Direct theft / insolvency: an attacker who stacks a pending receipt across two epochs recovers the pre-loss value on the stale portion while the funding math assumed it was haircut. The overpaid amount is taken from underlyings collected to back haircutted receipts, permanently impairing remaining claimants' payouts (they revert on `_transferFundedClaim` or receive dust). The extraction scales with the size of the stale receipt the attacker can park, bounded only by their deposit size.

### Likelihood Explanation
Requires no privileged action: deposit during buffer, request withdraw, wait one epoch, request again, then wait for any `stopEpochWithDuration` that realizes a partial loss (a manager-declared loss event on the honest path). The KYC-gated but otherwise unprivileged lender role suffices, and no guard in `requestWithdraw`, `collectWithdrawFunds`, or the claim chain prevents the stale-epoch slip-through.

### Recommendation
Apply `lossRecoveryPriceByEpoch` to the user's full pending basis when a loss-adjusted epoch exists — e.g. in `_claimLossAdjustedWithdrawRequest`, compute `claimBasis` over `withdrawsRequests[_user]` plus outstanding APR0 amounts rather than only `withdrawsRequestsByEpoch[_user][lossEpoch]`, or record the haircut under every epoch contributing to `pendingBasis` at stop time. Alternatively, force settlement of all prior pending receipts before accepting a new `requestWithdraw` when `withdrawsRequests[_user] != 0`, so `pendingWithdraws` can never span multiple request epochs per user.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
// 1. Setup: standard epoch variant, attacker (KYC'd) deposits X via _depositWithUser.
// 2. Epoch N (running): attacker calls cdoEpoch.requestWithdraw(x1, AAtranche)
//    -> withdrawsRequestsByEpoch[attacker][N] = x1; pendingWithdraws += x1; lastWithdrawRequest = N.
// 3. vm.prank(manager) cdoEpoch.stopEpoch(apr, 0) -> epochNumber = N+1, receipt funded fully.
//    Attacker does NOT claim.
// 4. Epoch N+1 buffer: attacker calls cdoEpoch.requestWithdraw(x2, AAtranche) again.
//    Guard passes: lossRecoveryPriceByEpoch[N] == 0. lastWithdrawRequest = N+1.
//    pendingWithdraws now = x1 + x2.
// 5. Epoch N+1 running: borrower repays only part; manager calls
//    cdoEpoch.stopEpochWithDuration(apr, loss) -> collectWithdrawFunds(pendingToFund)
//    where pendingToFund = (x1+x2) - pendingLoss. lossRecoveryPriceByEpoch[N+1] = p < 1e18.
// 6. Attacker calls cdoEpoch.claimWithdrawRequest():
//    - _claimLossAdjustedWithdrawRequest pays x2 * p (haircut on epoch N+1 only)
//    - _claimFundedWithdrawRequest then pays x1 at PAR
//    Total received = x1 + x2*p  >  (x1+x2)*p  expected for the funded amount.
// 7. A second user with a pure epoch-(N+1) receipt of size ~= pendingLoss share now
//    finds strategy underfunded: claim reverts / pays less than basis*p.
// Assert: underlying.balanceOf(attacker) delta == x1 + x2*p, while
// strategy funding only ever received (x1+x2) - pendingLoss.
```

The invariant broken is the loss-waterfall: every unit of `pendingBasis` contributing to `pendingLoss` must be haircut, but stale epoch-N basis escapes at par.
