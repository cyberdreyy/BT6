### Title
Multisig `DeleteKey` Fails To Purge Stale Confirmations, Letting Requests Execute Below The Confirmation Threshold - (`multisig/src/lib.rs`)

### Summary
The `MultiSigContract` in `multisig/src/lib.rs` allows a request to be executed once `confirmations.len() + 1 >= num_confirmations`. When a signer key is removed via `MultiSigRequestAction::DeleteKey`, the contract only purges requests that were *created* by the removed key — it never scans other requests' `confirmations` sets to strip the revoked key's stale confirmation. A confirmation recorded by a key that is later deleted therefore continues to count toward the k-of-n threshold forever, letting a request execute with fewer genuinely live/authorized confirmations than `num_confirmations` requires.

### Finding Description
`confirm()` checks the confirmation count against `num_confirmations` and executes the request once the threshold is reached: [1](#0-0) 

`execute_request`'s `DeleteKey` branch only removes requests whose *original signer* (`r.signer_pk`) matches the deleted key; it does not touch the `confirmations` sets of other, unrelated requests that the deleted key had already confirmed: [2](#0-1) 

`assert_valid_request` (called from `confirm`) only checks that the request and its confirmation set exist — it never re-validates that previously recorded confirming public keys are still valid/live access keys on the account: [3](#0-2) 

**Binding broken:** the contract's core invariant is `live confirmations counted == num_confirmations required` before a request executes. Once a confirming key is revoked, its stored confirmation becomes stale (no longer backed by a live, authorized signer), yet it is still counted:

`confirmations_recorded (including revoked keys) == confirmations_required` ✗ should be `confirmations_from_live_keys == confirmations_required`.

**Concrete attack/failure path:**
1. `num_confirmations = 3`, signer keys `A, B, C, D` exist.
2. `A` creates request `R` (e.g. a `Transfer`). `B` confirms `R` → `confirmations = {B}` (1/3).
3. `C` confirms `R` → `confirmations = {B, C}` (2/3, not yet executed).
4. The group later revokes `B` (e.g. `B` is deemed compromised) via a separate, properly-confirmed `DeleteKey{public_key: B}` request. `execute_request`'s `DeleteKey` branch removes only requests *created by* `B`; `R` was created by `A`, so `R`'s confirmations `{B, C}` are left untouched, and `B`'s access key is deleted from the account.
5. `D` (a live key) confirms `R`: `confirmations.len() + 1 = 2 + 1 = 3 >= num_confirmations(3)` → `R` executes.
6. `R` executed with confirmations from `{B, C, D}`, but `B`'s key was already revoked at the time of execution — only 2 live, currently-authorized signers (`C`, `D`) actually backed the execution, one short of the intended 3-of-4 threshold.

Because NEAR's runtime only prevents a *revoked* key from signing *new* transactions, it does nothing to invalidate confirmations that key already deposited into contract storage before revocation — so this is fully exploitable through normal contract calls, no protocol bypass needed.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." Any request (including `Transfer`, `AddKey`, `FunctionCall`, etc.) that has partial confirmations from a key that is subsequently removed can later execute with the deleted key's stale confirmation silently making up the deficit, letting a lower number of live/current signers push through requests (including fund transfers) that were never legitimately authorized to the full threshold. If the multisig is a treasury or DAO controller, this can result in unauthorized fund movement or configuration changes.

### Likelihood Explanation
This requires no privileged access beyond normal multisig usage: any legitimate confirmer's confirmation becomes a permanent "banked" vote even after that key is later removed for any reason (rotation, compromise, offboarding). Multisig deployments regularly rotate/replace keys, and outstanding unconfirmed requests routinely persist across such rotations (the contract explicitly supports many concurrent pending requests via `active_requests_limit`), so the precondition (a pending request with a partial confirmation from a key that is later deleted) is a normal, foreseeable operational sequence rather than an exotic edge case.

### Recommendation
When executing `DeleteKey`, iterate over *all* requests' `confirmations` sets (not just requests created by the deleted key) and remove the deleted public key from each. Alternatively, when counting confirmations in `confirm()`/before executing a request, filter the stored confirmation set down to keys that are still valid access keys on the account before comparing against `num_confirmations`.

### Proof of Concept
```rust
// num_confirmations = 3, keys A, B, C, D added to the account
let mut c = MultiSigContract::new(3);

// A creates request R
testing_env!(context_with_key(A, amount));
let request_id = c.add_request(MultiSigRequest { receiver_id: bob(), actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }] });

// B confirms R (1/3)
testing_env!(context_with_key(B, amount));
c.confirm(request_id);

// C confirms R (2/3, not executed)
testing_env!(context_with_key(C, amount));
c.confirm(request_id);

// Separately, group revokes B via a fully-confirmed DeleteKey request
// (omitted: creating + confirming a DeleteKey{public_key: B} request to threshold with A, C, D)
// -> B's access key removed from account, but R's confirmations {B, C} untouched

// D confirms R: count becomes {B, C} + D = 3 >= num_confirmations(3) -> executes
testing_env!(context_with_key(D, amount));
c.confirm(request_id); // executes with only 2 live signers (C, D) actually backing it
```

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
