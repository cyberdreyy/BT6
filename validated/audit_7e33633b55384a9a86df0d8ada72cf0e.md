### Title
Stale in-memory allowlist entries remain authorizable after on-chain revocation until natural expiry - ([File: core/services/workflows/syncer/v2/workflow_registry.go])

### Summary
`workflowRegistry.syncAllowlistedRequests` maintains `w.allowListedRequests` as a monotonically-growing, additive cache: on each tick it prunes entries **only** by `ExpiryTimestamp` and appends newly fetched entries, then advances `w.lastSeenAllowlistedRequestsCount`. There is no logic anywhere in this loop that removes a cached `WorkflowRegistryOwnerAllowlistedRequest` because it was revoked on-chain before its expiry. `AuthorizeRequest` in `allow_list_based_auth.go` simply matches `RequestDigest` against this in-memory slice, so a revoked-but-not-yet-expired digest continues to authorize requests.

### Finding Description [1](#0-0) 
shows the sync logic: `activeAllowlistedRequests` is built by (1) keeping every previously-cached entry whose `ExpiryTimestamp` has not passed, and (2) appending `newAllowListedRequests` fetched since `lastSeenAllowlistedRequestsCount`. `w.lastSeenAllowlistedRequestsCount` is then overwritten with the latest `totalAllowlistedRequestsResult`. There is no code path that removes/invalidates a cached entry because the on-chain allowlist entry for that `(Owner, RequestDigest)` was explicitly revoked — the only removal path is time-based expiry.

`AuthorizeRequest` (`core/capabilities/vault/allow_list_based_auth.go`) calls `GetAllowlistedRequests` and does a linear scan via `fetchAllowlistedItem`, matching purely on `RequestDigest` equality: [2](#0-1) 
It does not re-verify current on-chain allowlist membership; it trusts whatever is currently sitting in the node's in-memory cache, bounded only by `ExpiryTimestamp` freshness (line 64 check), not by actual current revocation state.

Because the incremental fetch (`getActiveAllowlistedRequestsReverse`/`totalAllowlistedRequests`) appears to be an append-only, monotonically increasing counter-driven mechanism (based on the field name and comments), an on-chain revoke operation that does not increase `totalAllowlistedRequests` produces no signal to the syncer to drop the corresponding cached entry. The node therefore continues to authorize a digest/owner pair for the full remainder of its original `ExpiryTimestamp`, regardless of the revocation.

### Impact Explanation
An owner/request whose vault access has been revoked on-chain (e.g., due to compromise, policy violation, or quota exhaustion) can continue to have previously-signed/allowlisted requests authorized by any node that had already cached the entry, for up to the full remaining `ExpiryTimestamp` window — not bounded by the 5s poll interval (`defaultTickIntervalForAllowlistedRequests`). This is a stale-allowlist-based unauthorized execution: a party whose privilege was revoked can still get vault/gateway requests authorized as if still allowlisted, which maps to Chainlink's "allowlist/quota bypass" / authorization-bypass impact class.

### Likelihood Explanation
Requires only that the attacker (a previously-legitimately-allowlisted workflow owner or request holder) already possesses a valid signed request/digest and that the node has cached the entry prior to revocation — no special node/DON/admin access is needed by the attacker. The window of exploitability is bounded by the entry's `ExpiryTimestamp`, which is contract-configurable and can be arbitrarily long, making this readily and repeatably exploitable within that window. The severity is data/contract dependent: if `ExpiryTimestamp` windows are always short and revocation always coincides with imminent expiry, impact is minor; if long-lived allowlist entries can be revoked mid-lifetime, this is a real gap.

### Recommendation
Treat the on-chain allowlist as authoritative rather than additive: on each poll, replace (not just append/prune-by-expiry) the cached set with the currently active on-chain allowlist, or explicitly diff and drop entries that no longer appear in the current on-chain active set (in addition to expiry-based pruning). If the contract cannot cheaply return a full current-state snapshot, expose/consume an explicit revocation event or "still active" check as part of `AuthorizeRequest`'s hot path (or a bounded-freshness re-check) so revocation takes effect within a fixed, short SLA regardless of `ExpiryTimestamp`.

		}
