### Title
Signer's stale rejection weight is never retracted when the same signer later accepts, letting one signer's weight simultaneously satisfy the accept tally and the reject/blocking-minority tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` aggregates `BlockResponse::Accepted` and `BlockResponse::Rejected` messages from signers into two independent weight totals, `total_weight_approved` and `total_weight_rejected`, that the mining coordinator treats as mutually exclusive partitions of the signer set's weight. The guard that prevents double-counting on the accept path (`gathered_signatures.contains_key(&slot_id)`) and the guard on the reject path (`responded_signers.insert(slot_id)`) are two separate, unsynchronized structures. A signer who first rejects and later reconsiders and accepts the same block gets counted in `total_weight_rejected` *and* `total_weight_approved` at the same time, because nothing clears their earlier reject contribution when the later accept is recorded.

### Finding Description
In the `BlockResponse::Accepted` handling branch: [1](#0-0) 

weight is only added to `total_weight_approved` when `!block.gathered_signatures.contains_key(&slot_id)`, and `responded_signers.insert(slot_id)` is called unconditionally afterward.

In the `BlockResponse::Rejected` handling branch: [2](#0-1) 

weight is added to `total_weight_rejected` only when `block.responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot_id is seen in `responded_signers`).

Because these two "already counted" checks live on different collections (`gathered_signatures` for accept-dedup vs. `responded_signers` for reject-dedup), the ordering of messages determines whether double counting occurs:

- **Reject, then Accept:** Reject is processed first → `responded_signers.insert(slot_id)` returns `true` → `total_weight_rejected` gains this signer's weight. Later, the same signer's Accepted message arrives → `gathered_signatures.contains_key(&slot_id)` is `false` (this signer never accepted before) → `total_weight_approved` also gains this signer's weight. The signer's weight is now present in *both* totals; the earlier reject is never retracted from `total_weight_rejected`.
- **Accept, then Reject:** Accept is processed first → `responded_signers.insert(slot_id)` already returns `true` from the accept path, so a later Reject from the same signer silently does not add to `total_weight_rejected` (a related but distinct anomaly — a legitimate later rejection is dropped).

The mining coordinator (`SignerCoordinator::get_block_status`) then makes its accept/reject decision purely from these two totals: [3](#0-2) 

Since `total_weight_rejected` and `total_weight_approved` are supposed to represent disjoint, mutually-exclusive weight pools that never sum to more than `self.total_weight`, a single signer contributing to both pools breaks that invariant: `total_weight_rejected` can remain permanently inflated by a vote the signer has already reversed, which feeds into the `blocking_minority`/`SignersRejected` logic (including the per-txid `permanently_excluded_txids`/`temporarily_excluded_txids` accounting) using stale, already-superseded rejection weight.

### Impact Explanation
This is the direct analog of the reported bug class: two conceptually distinct vote types (accept vs. reject) that must be mutually exclusive per signer are commingled because the "already counted" bookkeeping for each type lives in a separate, unsynchronized structure. The practical effect matches the "rejection recounted as acceptance" family of impacts called out for this analysis: a signer's superseded rejection persists and continues to be tallied toward the blocking-minority/`SignersRejected` threshold even after that signer has legitimately switched to accepting the block, and — in the reverse ordering — a legitimate later rejection is silently discarded. This can cause the miner to spuriously reject/txid-exclude on stale weight, or to treat a signer's later rejection as a no-op, both of which distort the aggregated-weight-vs-verified-accepts equality the coordinator relies on to decide whether a block is safe to broadcast/retry.

### Likelihood Explanation
This requires only a single signer sending two conflicting `BlockResponse` messages (Reject then Accept, or vice versa) for the same block hash over StackerDB — well within the reach of one signer's own key/messages and ordinary gossip relay, with no majority collusion, no other signer's key, and no node-side auth token needed.

### Recommendation
Track accept/reject state per signer slot in a single unified structure (e.g., a `HashMap<u32, BlockResponseKind>`), so that recording a new vote from a signer retracts/replaces their previous contribution from whichever pool it was in before adding it to the new one. Both `total_weight_approved` and `total_weight_rejected` should be recomputed (or adjusted) atomically whenever a signer's vote changes, guaranteeing `total_weight_approved + total_weight_rejected <= self.total_weight` at all times.

### Proof of Concept
1. Miner proposes a block; `StackerDBListener` creates a `BlockStatus` entry with empty `gathered_signatures`/`responded_signers` and zero weight totals (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:70-82`).
2. Signer S (weight `w`) sends `BlockResponse::Rejected` for the block → `responded_signers.insert(S)` returns `true` → `total_weight_rejected += w` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:515-518`).
3. Signer S reconsiders and sends `BlockResponse::Accepted` for the same block → `gathered_signatures.contains_key(S)` is `false` → `total_weight_approved += w`, and `gathered_signatures`/`responded_signers` are updated (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:443-465`).
4. Now `block.total_weight_rejected` still includes `w` from step 2 even though S has moved to acceptance in step 3; both totals simultaneously reflect S's weight, violating the intended disjointness the coordinator's threshold checks (`stacks-node/src/nakamoto_node/signer_coordinator.rs:509-545`) assume.
