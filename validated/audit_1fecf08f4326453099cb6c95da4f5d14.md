Confirmed: `rescueFunds` is restricted to `onlyCaller(immutables.taker.get())` only, so the maker cannot self-rescue even after the rescue delay elapses.### Title
Permanent freezing of maker's `EscrowSrc` funds when maker's own address becomes token-blacklisted before cancellation — ([File: contracts/EscrowSrc.sol])

### Summary
`EscrowSrc.cancel()`/`publicCancel()` unconditionally refunds the escrowed principal to the hardcoded `immutables.maker` address, with no ability to redirect the transfer to an alternate recipient. If the maker's address is added to a token's blacklist (e.g., a Circle-style USDC blacklist) while the swap is in-flight, the refund path permanently reverts, and the maker has no self-service way to recover the funds, mirroring the CCTP `mintRecipient`-blacklist DoS described in the external report.

### Finding Description
`EscrowSrc._cancel` sends the locked ERC20 principal directly to `immutables.maker.get()` via `safeTransfer`, with no parameterized target: [1](#0-0) 

This is asymmetric with the withdrawal path, where the taker can freely redirect funds via `withdrawTo(secret, target, immutables)`: [2](#0-1) 

but `cancel()`/`publicCancel()` have no equivalent `cancelTo` — the destination is baked into the validated `immutables` hash and can never be changed: [3](#0-2) 

An unprivileged attacker can dust the maker's own address with tainted funds (stolen exploit proceeds, or an OFAC-sanctioned token) at any point while the `EscrowSrc` clone holds the maker's principal — i.e., during the entire window between order fill and the maker's own cancellation eligibility — forcing the token issuer to blacklist the maker's address on that chain. Once this happens, both `cancel()` (private) and `publicCancel()` (public) will always revert inside `_cancel`, because `safeTransfer` to a blacklisted address fails on tokens like USDC.

The only remaining exit is `rescueFunds`, but it is gated to `onlyCaller(immutables.taker.get())` — the maker cannot call it themselves — and it sends the swept funds to `msg.sender` (the taker), not to any maker-controlled address: [4](#0-3) 

So even after `RESCUE_DELAY` elapses, the maker's principal can only be recovered by the taker sweeping it to themselves, not by the maker. This exactly parallels the CCTP report's root cause: a fixed, unchangeable recipient address whose blacklisting by the token issuer permanently blocks the only intended fund-release path, with no in-protocol mechanism to redirect the transfer to a non-blacklisted address.

### Impact Explanation
This fits the "Medium: smart contract unable to operate because required token/native balances can be broken by an unprivileged actor" bounty class, and arguably rises to "High: temporary/permanent freezing of funds during the live swap lifecycle." An unprivileged third party (not owner/governance/resolver) can, purely by sending dust to the maker's public address, break the invariant that `cancel()` always returns principal to its rightful owner. Once broken, the maker's tokens are stuck in the `EscrowSrc` clone: `withdraw`/`publicWithdraw` become unavailable after the cancellation timelock starts (`onlyBefore(SrcCancellation)`), and `cancel`/`publicCancel` are permanently blocked by the blacklist, leaving `rescueFunds` (taker-only, funds routed to taker) as the sole recovery path — meaning the maker only recovers funds at the taker's discretion/goodwill, not by protocol design.

### Likelihood Explanation
Moderate. The attacker only needs to know the maker's address (public in the order/immutables) and send it dust from a source that is itself blacklisted/sanctioned or laundered from a known exploit — no permissions, timing precision, or protocol interaction are required, matching the "unprivileged user" attacker model. It requires the target token to implement issuer-side blacklisting (e.g., USDC/EURC-style tokens), which is a realistic subset of tokens used in cross-chain swaps.

### Recommendation
Add a `cancelTo`/parameterized-target variant analogous to `withdrawTo`, allowing the maker (or a maker-designated caller) to specify an alternate recipient for the cancellation refund, and/or allow the maker to call `rescueFunds` for their own principal after the rescue delay so that a blacklisted maker address does not permanently strand the funds.

### Proof of Concept
1. Maker signs an order; Resolver fills it, deploying `EscrowSrc` and locking maker's USDC-like token as principal.
2. Attacker (unprivileged) sends a small amount of stolen/sanctioned USDC-like tokens to the maker's address on the source chain.
3. The issuer blacklists the maker's address.
4. Resolver never reveals the secret (or fails to), so the `SrcWithdrawal`/`SrcPublicWithdrawal` windows pass unused; `SrcCancellation` window opens.
5. Anyone calls `cancel()`/`publicCancel()`; `_cancel` reverts every time because `safeTransfer(immutables.maker.get(), ...)` reverts on the blacklisted maker.
6. Maker cannot call `rescueFunds` (restricted to `immutables.taker`); funds remain stuck in `EscrowSrc`, recoverable only by the taker sweeping them to themselves after `RESCUE_DELAY`.
