The codebase does correctly separate the fixed-size baseline from variable contract-linkage overhead, contradicting the premise of the audit question:

- `Account::new` routes `AccountContract::None` and `AccountContract::Local(_)` into the `AccountV1` representation, which has a fixed borsh-serialized size (two `Balance`, one `CryptoHash`, one `StorageUsage`) — it only becomes `AccountV2` when the contract is `Global`/`GlobalByAccount`. [1](#0-0) 

- The variable-size portion of `AccountContract` (specifically `GlobalByAccount(AccountId)`) is explicitly isolated via `identifier_storage_usage()`, which returns `0` for `None`/`Local`, a fixed `32` for `Global`, and the id length for `GlobalByAccount`. [2](#0-1) 

- Every account-creation call site that starts an account away from the `None` baseline explicitly adds its own delta on top of `num_bytes_account` rather than relying on the constant to cover it: implicit near-account creation adds public-key/access-key bytes, ETH-implicit creation adds the global-contract-hash identifier length, and deterministic-account creation starts at the `None` baseline then routes contract installation through `use_global_contract`, which performs its own storage accounting. [3](#0-2) [4](#0-3) 

- This design is also validated by an existing test that cross-checks the borsh sizes of the constituent records (access keys, public keys) against `storage_num_bytes_account`/`num_extra_bytes_record` from the `RuntimeConfigStore`, confirming the constant is treated as a fixed baseline and reconciled with actual serialized sizes rather than assumed. [5](#0-4) 

Since `num_bytes_account` is never applied to a variable-size `AccountContract` variant without an accompanying explicit delta, and every transition away from `None` (deploy_contract, use_global_contract, deterministic state-init) adds its own accounting, there is no under-charging of storage staking here, and no reachable attacker path that lets an unprivileged account holder under-pay for storage.

pub(crate) fn create_deterministic_account(
    initial_balance: Balance,
    storage_usage_config: &StorageUsageConfig,
) -> Account {
    // Unlike `CreateAccount`, this account creation does not change
    // actor_id. This is important to prevent hijacking the account.
    // Actor id remains the predecessor, so any actions following will
    // be checked against that for actor permissions, preventing
    // `AddKey`, `DeployContract`, or any other actions that only the
    // account owner is permitted to do.
    Account::new(
        initial_balance,
        Balance::ZERO,
        AccountContract::None,
        storage_usage_config.num_bytes_account,
    )
}

#[test]
fn test_storage_usage_components() {
    // confirm these numbers don't change, as the zero balance limit is derived from them
    const PUBLIC_KEY_STORAGE_USAGE: usize = 33;
    const FULL_ACCESS_PERMISSION_STORAGE_USAGE: usize = 9;
    const FUNCTION_ACCESS_PERMISSION_STORAGE_USAGE: usize = 98;

    let edwards_public_key = PublicKey::from_seed(KeyType::ED25519, "seed");
    assert_eq!(PUBLIC_KEY_STORAGE_USAGE, borsh::object_length(&edwards_public_key).unwrap());

    let full_access_key = AccessKey::full_access();
    assert_eq!(
        FULL_ACCESS_PERMISSION_STORAGE_USAGE,
        borsh::object_length(&full_access_key).unwrap()
    );

    let fn_access_key = AccessKey {
        nonce: u64::MAX,
        permission: AccessKeyPermission::FunctionCall(FunctionCallPermission {
            allowance: Some(Balance::MAX),
            receiver_id: "a".repeat(64),
            method_names: vec![],
        }),
    };
    assert_eq!(
        FUNCTION_ACCESS_PERMISSION_STORAGE_USAGE,
        borsh::object_length(&fn_access_key).unwrap()
    );

    let config_store = RuntimeConfigStore::new(None);
    let config = config_store.get_config(PROTOCOL_VERSION);
    let account_overhead = config.fees.storage_usage_config.num_bytes_account as usize;
    let record_overhead = config.fees.storage_usage_config.num_extra_bytes_record as usize;
    // The NEP proposes to fit 4 full access keys + 2 fn access keys in a zero balance account
    let full_access =
        PUBLIC_KEY_STORAGE_USAGE + FULL_ACCESS_PERMISSION_STORAGE_USAGE + record_overhead;
    let fn_access =
        PUBLIC_KEY_STORAGE_USAGE + FUNCTION_ACCESS_PERMISSION_STORAGE_USAGE + record_overhead;
    let total = account_overhead + 4 * full_access + 2 * fn_access;
    assert_eq!(total as u64, ZERO_BALANCE_ACCOUNT_STORAGE_LIMIT);
