### Title
Cross-workflow `requestID` collision in the gateway's HTTP trigger handler lets any authorized workflow caller grief another user's trigger request - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The `httpTriggerHandler` used by the gateway's internet-facing HTTP trigger endpoint tracks in-flight `workflows.execute` requests in a single map keyed only by the caller-supplied `requestID` string, with no scoping to workflow ID or workflow owner. Any unprivileged caller who is authorized for *any* workflow on the DON can pre-claim an arbitrary `requestID` before a victim submits their own request with that same ID for a *different, unrelated* workflow, causing the victim's legitimate request to be rejected with a conflict error. This is the same "front-run a shared identifier to deny a legitimate user's action" bug class as the referenced `multiClaim()` griefing report, translated to the gateway's request-tracking cache.

### Finding Description
`httpTriggerHandler.callbacks` is declared as a single, handler-wide map: [1](#0-0) 

`setupCallback` inserts into this map using only the raw `requestID` supplied by the caller, and rejects the request outright if that key is already present, with no notion of which workflow or owner registered it: [2](#0-1) 

The only validation applied to `requestID` before it reaches this map is that it must be non-empty and must not contain `/`; there is no per-workflow or per-owner namespacing, and no binding to the authorized key/owner returned by `authorizeRequest`: [3](#0-2) 

Critically, `authorizeRequest` (and the auth check inside `HandleUserTriggerRequest`) validates that the caller is authorized for *the workflow specified in their own request* — not for the `requestID` value itself: [4](#0-3) [5](#0-4) 

Because the `callbacks` map has global scope across all workflows served by this gateway handler, an attacker who is authorized for their own (unrelated) workflow can supply the exact same `requestID` string that a victim is about to use for a completely different workflow. The attacker's request succeeds through `validatedTriggerRequest` → `resolveWorkflowID` → `authorizeRequest` (all validated against the attacker's own workflow) and reaches `setupCallback`, claiming the shared `requestID` key first. When the victim's genuine request for their own workflow arrives with that same `requestID`, `setupCallback` finds the key already present and rejects it via `jsonrpc.ErrConflict`, sending back "requestID: ... has already been used" and never dispatching the trigger to the DON.

### Impact Explanation
This allows a low-privilege, authenticated caller (authorized only for their own workflow) to deny service to another user's `workflows.execute` HTTP trigger call by winning a race on a caller-chosen, globally shared identifier. This is a concrete unauthorized-request/DoS primitive on the internet-facing gateway: a legitimate workflow trigger that should have executed is silently blocked, and the victim must retry with a new `requestID`, mirroring the "griefing gas/attempts and forcing repeated retries" impact described in the source report. Because the map has no cross-user scoping, this is not limited to griefing a single victim's own re-tries — it can be repeated against any predictable or observed `requestID` used by any workflow on the shared DON.

### Likelihood Explanation
Exploitability depends on the attacker being able to predict or learn the victim's chosen `requestID` before the victim's request lands (e.g., sequential/predictable IDs, IDs echoed in prior client-visible traffic, or a race where the attacker observes/anticipates client retry behavior). This requires timing and knowledge of the ID scheme, so it is not trivially exploitable against fully random, unobservable IDs, but it is a genuine, currently-unmitigated race in a state cache reachable directly from unprivileged internet-facing gateway traffic, with no code path that scopes or salts the shared key by workflow/owner to prevent it.

### Recommendation
Scope the `callbacks` map key (and the conflict check in `setupCallback`) by workflow ID (or the authorized owner) in addition to the caller-supplied `requestID`, e.g. key on `workflowID + "/" + requestID` (note `/` is already reserved from user-supplied IDs) or a composite struct key. This prevents callers authorized for one workflow from colliding with, and blocking, in-flight requests belonging to a different workflow.

### Proof of Concept
1. Attacker is a normal, authorized caller for their own workflow `W_attacker` (no privilege on the victim's workflow `W_victim` is required).
2. Attacker predicts/observes that the victim's client will next submit a `workflows.execute` request with `id = "R123"` for `W_victim` (e.g., due to a predictable ID scheme or observed retry behavior).
3. Attacker sends their own valid `workflows.execute` request for `W_attacker` with `id = "R123"`. It passes `validatedTriggerRequest`, `resolveWorkflowID`, and `authorizeRequest` (all validated against `W_attacker`), then `setupCallback` inserts `callbacks["R123"]`.
4. Victim submits their `workflows.execute` request for `W_victim` with `id = "R123"`. `setupCallback` finds `"R123"` already present in the shared map and returns `jsonrpc.ErrConflict`, so the victim's trigger is never dispatched to the DON — despite the victim being fully authorized for their own workflow.

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
