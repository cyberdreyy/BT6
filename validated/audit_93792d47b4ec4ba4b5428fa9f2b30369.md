### Title
Epoch counter incremented by mid-epoch `deposit()` lets withdraw requesters skip the one-epoch wait and claim unfunded receipts — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.epochNumber` is used as the epoch identity that both timestamps withdraw requests (`lastWithdrawRequest`, `withdrawsRequestsByEpoch`, `apr0Users.principalEpoch`) and gates claims (`epochNumber <= lastWithdrawRequest` reverts). But `epochNumber` is incremented inside `deposit()` whenever `isEpochRunning()` is true — i.e., by *any* strategy-token deposit executed while an epoch is running, not only once per `stopEpoch`. A third-party depositor (or the attacker themselves through the CDO's mid-epoch/instant deposit path) can therefore bump `epochNumber` mid-epoch, "freeing" the request-epoch marker prematurely — the analog of CVE-2021-33033's refcount mishandling leaving a stale/reused identifier. The requester then calls `claimWithdrawRequest` in the same epoch and is paid from strategy-held underlyings before `stopEpoch` has sourced `pendingWithdraws` from the borrower.

### Finding Description
- `requestWithdraw` stores `lastWithdrawRequest[_user] = epochNumber` and records `withdrawsRequestsByEpoch[_user][epochNumber] += _amount` (IdleCreditVault.sol:282,293).
- `_claimFundedWithdrawRequest` only enforces `epochNumber <= lastWithdrawRequest[_user]` → revert (line 326). The comment states the intent: claim allowed only after the next `stopEpoch` funds the receipts.
- However `deposit()` increments `epochNumber` whenever `IIdleCDOEpochVariant(idleCDO).isEpochRunning()` is true (lines 607–611). The comment explicitly distinguishes "deposit done on stopEpoch (before setting the var to false)" — but the condition is `isEpochRunning()`, which is also true throughout the running epoch, so any deposit routed through `deposit()` mid-epoch (instant/prefunded deposit flows in epoch variants) increments the counter.
- After one such deposit, `epochNumber > lastWithdrawRequest[_user]`, the gate passes, `_settleApr0` is skipped correctly, and `_burn(_user, ...)` + `_transferFundedClaim` pays out `withdrawsRequests[_user]` from the strategy's underlying balance — funds that are reserved for instant-withdraw claimants, the `defaultRecoveryReserve` guard, or simply not yet collected from the borrower.
- The same premature `epochNumber` bump corrupts `apr0Users.principalEpoch` accounting: `_settleApr0` settles only when `_reqEpoch < epochNumber` (line 553), so APR0 principal can settle a full epoch early and accrue/claim against the wrong `apr0RateByEpoch`.

### Impact Explanation
Direct theft / insolvency: a withdraw requester claims underlyings that were never funded by the borrower at `stopEpoch`, draining underlyings reserved for other claimants (instant-withdraw receipts, funded older receipts, default recovery reserve protected only by the `balance < reserve` check in `_transferFundedClaim`, line 904). Loss is bounded by the attacker's withdraw request size but directly removes funds owed to other users, and can leave `pendingWithdraws` permanently underfunded at the next `stopEpoch` (paid twice from the same basis).

### Likelihood Explanation
Requires only that the deployed epoch variant routes any user-facing deposit through `strategy.deposit()` while `isEpochRunning()` is true (prefunded/instant deposit variants do this; standard variants route queued deposits at `startEpoch`/buffer where `isEpochRunning()` is false, in which case `epochNumber` only bumps once per stop and the bug does not fire). The attacker needs only a KYC'd wallet to request a withdraw and an accomplice/self deposit to bump the counter. Caveat I could not fully verify within available context: whether `IdleCDOEpochVariant`'s mid-epoch deposit path calls `deposit()` or `mintStrategyTokens()` — the finding holds only for the former.

### Recommendation
Increment `epochNumber` only on the `stopEpoch` transition, not inside `deposit()`. E.g., gate the increment on a dedicated `stopEpoch`/epoch-rollover callback from the CDO, or compare against a stored epoch identifier supplied by the CDO rather than a locally bumped counter. Alternatively, have `deposit()` detect "first deposit after stop" via an explicit flag set by `stopEpoch` instead of `isEpochRunning()`.

### Proof of Concept
Foundry fork sketch (prefunded epoch variant, where mid-epoch deposits reach `strategy.deposit`):

```solidity
// Running epoch N: attacker (KYC'd) requests withdraw of tranche tokens
cdoEpoch.requestWithdraw(amount, address(AAtranche));
// epochNumber == N, lastWithdrawRequest[attacker] == N, pendingWithdraws += amount

// Mid-epoch: attacker (or any depositor) triggers an instant deposit that
// calls strategy.deposit() while isEpochRunning() == true
idleCDO.depositAA(dust); // -> strategy.deposit -> epochNumber becomes N+1

// Gate epochNumber <= lastWithdrawRequest no longer holds; claim succeeds
// BEFORE stopEpoch funds pendingWithdraws from the borrower
cdoEpoch.claimWithdrawRequest(); // _transferFundedClaim pays from strategy balance

// At next stopEpoch the same pendingWithdraws basis is funded again,
// while strategy underlyings were already drained -> other claimants' reserve shortfall.
```
