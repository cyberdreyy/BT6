### Title
Global, client-controlled `req.ID` in `ConfidentialRelayHandler` lets any unprivileged caller pre-empt/block another user's request - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
The gateway's confidential-relay JSON-RPC entrypoint tracks in-flight requests in a single map keyed only by the client-supplied `req.ID`, with no per-caller or per-session isolation. Any unauthenticated/unprivileged HTTP caller can submit a request with the same `ID` as a legitimate user's about-to-be-sent request and cause the legitimate request to be rejected outright, exactly mirroring the "nonce front-running" bug class from the report (a party with access to the same shared identifier space races the victim to claim an identifier first and knocks out the victim's request).

### Finding Description
`gateway.ProcessRequest` accepts an arbitrary caller-chosen `jsonRequest.ID` from any HTTP request hitting the gateway's public user port and forwards it unchanged to the handler: [1](#0-0) [2](#0-1) 

For the confidential relay service, `HandleJSONRPCUserMessage` only validates that `req.ID` is non-empty and ≤200 chars, then calls `newActiveRequest`, which fails hard if that exact ID string is already present in the shared `activeRequests` map: [3](#0-2) [4](#0-3) 

`activeRequests` is a single `map[string]*activeRequest` shared across *all* callers of the DON/service, with no per-user/per-owner namespace — the key is only the raw `req.ID`: [5](#0-4) 

This is structurally identical to the reported `NonceMap` flaw: an identifier meant to correlate/de-duplicate a specific caller's request is drawn from a single shared namespace that any other unprivileged party (anyone who can reach the gateway HTTP endpoint) can also write to. A malicious client that predicts or observes (e.g., replays or guesses) another user's about-to-be-used request ID can submit it first and cause `newActiveRequest` to return `"request ID already exists: <id>"`, permanently blocking the legitimate caller's ability to have that specific request processed until it naturally expires from the map (`removeExpiredRequests`, bounded by `requestTimeout`).

Existing tests confirm this collision behavior is by design for duplicate submissions from the *same* caller, but nothing in the code distinguishes "same caller retries" from "different, malicious caller races the ID": [6](#0-5) 

By contrast, the Vault handler's equivalent duplicate-ID path is protected by cryptographic replay-guard logic and owner-prefixed IDs tied to an authorized allowlist digest (`requestDigest` bound to a specific workflow owner via `AllowListBasedAuth`/`RequestReplayGuard`), so a request ID collision there can only occur if the *same* authorized owner's digest is reused: [7](#0-6) [8](#0-7) 

The confidential relay handler has no equivalent authorization/ownership binding on `req.ID` — it is a bare user-supplied string with no cryptographic tie to a specific caller.

### Impact Explanation
Impact is a targeted denial-of-service against a specific, unprivileged caller's request: an attacker who can reach the gateway's public endpoint (no special permission required — this path serves the internet-facing gateway to unprivileged clients) can prevent a chosen request ID from being processed, effectively cancelling/blocking a legitimate user's confidential-relay capability invocation. This does not by itself allow reading another user's data or forging responses, but it directly maps to the "unauthorized... blocking legitimate order/request" impact class called out in the report (Impact: High in the original, but here bounded to availability/blocking of a single request rather than fund loss).

### Likelihood Explanation
Likelihood depends on the attacker's ability to predict or observe a victim's request ID before it reaches the gateway (e.g., IDs generated with low entropy, sequential counters, or observed via client-side/network exposure) and on winning a timing race against the legitimate submission. Where request IDs are unpredictable (e.g., random UUIDs generated per-request, as seen in vault system tests), likelihood is low; where callers use predictable/sequential IDs, likelihood rises substantially. This is analogous to the report's "Likelihood: Low" rating for the nonce race.

### Recommendation
Scope `activeRequests` (and any duplicate-ID rejection) per authenticated caller/session rather than as a single global namespace, or require that `req.ID` be namespaced/prefixed server-side with a value derived from an authenticated identity (similar to the Vault handler's owner-prefixed request ID pattern), so that one caller cannot collide with or pre-empt another caller's request ID.

### Proof of Concept
1. Victim client prepares to POST a JSON-RPC request to the gateway's confidential-relay endpoint with `id = "req-victim-1"`.
2. Attacker, with no special privileges, sends a POST to the same public gateway endpoint using `id = "req-victim-1"` first (as shown feasible by the duplicate-ID test path): [9](#0-8) 
3. When the victim's request with the same ID arrives, `newActiveRequest` rejects it with `"request ID already exists: req-victim-1"` [10](#0-9) , and `gateway.ProcessRequest` returns this as a `HandlerError` response to the victim [11](#0-10) , blocking the victim's capability invocation for that request ID until it later expires.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
