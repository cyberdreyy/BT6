### Title
Stale per-epoch instant-withdraw receipt is never cleared on claim, inflating default recovery basis and reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` zeroes the aggregate `instantWithdrawsRequests[_user]` but never deletes `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrements `instantWithdrawClaimsByEpoch[epoch]`. This is the analog of CVE-2024-32624's incomplete "setnull" routine: a receipt pointer is cleared on one path but left dangling in the per-epoch mapping, and the default-recovery code later dereferences the stale entry as if the claim were still pending.

### Finding Description
In `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393) the funded path only does:

```
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

The per-epoch bookkeeping written in `requestInstantWithdraw` (`instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]`, lines 371-372) is left untouched. Those same per-epoch values are later consumed by the default-recovery machinery:

- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0` (lines 644-649).
- `_defaultPrefundedInstantReserve()` treats `instantBasis - pendingInstant` as underlying already held by the strategy (lines 716-722), but the stale portion's underlying was already paid out at claim time.
- `_claimDefaultedInstantWithdrawRequest` pays out `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` from the reserve (lines 842-856).

So if a user claims an instant withdrawal in epoch N, and the borrower defaults and `finalizeDefaultRecovery` runs while `epochNumber` is still N (default finalization happens within the same epoch for unfunded instant requests), the already-paid amount X is counted twice: once in `totalBasis` via `defaultPendingClaimBasis`, and once as phantom `prefundedReserve`/`defaultRecoveryReserve` even though the underlying left the strategy.

Because the phantom X appears in both numerator and denominator of `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (line 688), it pushes the recovery price toward par while the actual token balance of the strategy is smaller than `defaultRecoveryReserve` accounts for. Claims processed first succeed at the inflated price and drain the real balance; the last defaulted claimants' `safeTransfer`s revert because the reserve is insolvent.

Additionally, for the user whose claim was already paid, `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = X > 0` and executes `instantWithdrawsRequests[_user] -= claimBasis` on a zeroed aggregate. Unless that user opened a new post-default request, this underflow-reverts, permanently blocking their subsequent legitimate claim path within the same epoch.

### Impact Explanation
- Broken invariant: donation-isolation / solvency of the default recovery reserve. `defaultRecoveryReserve` is set to a value exceeding the strategy's actual underlying balance by exactly the stale claimed amount.
- Direct impact: defaulted-epoch claimants are paid at an inflated `defaultRecoveryPrice`; the trailing claimants' transfers revert, permanently freezing their share of the reserve. Magnitude equals the stale `instantWithdrawClaimsByEpoch` surplus — bounded by the instant-withdraw queue, which can be a large fraction of TVL when instant withdrawals are enabled.

### Likelihood Explanation
Requirements: instant withdrawals enabled (`setInstantWithdrawParams`), an attacker (any KYC'd tranche holder) requests and claims an instant withdrawal in epoch N, some other instant requests remain unfunded (`pendingInstantWithdraws > 0`), and the borrower defaults with `finalizeDefaultRecovery` called while `epochNumber == N`. All attacker actions are unprivileged; the default and finalization are honest actor calls the attacker's stale state exploits. The stale write exists unconditionally on every funded instant claim, so likelihood is determined only by the default timing, not by attacker contrivance.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch receipt when paying a funded claim:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
uint256 reqEpoch = lastInstantWithdrawEpoch[_user]; // or track via mapping
instantWithdrawsRequestsByEpoch[_user][reqEpoch] = 0;
instantWithdrawClaimsByEpoch[reqEpoch] -= amount;
_transferFundedClaim(_user, amount);
```

Equivalently, store the request epoch per user (mirroring `lastWithdrawRequest`) so the funded-claim path can zero the per-epoch entries. Also consider making `_claimDefaultedInstantWithdrawRequest` cap `claimBasis` at `instantWithdrawsRequests[_user]` rather than trusting the per-epoch mapping alone.

### Proof of Concept
Foundry fork PoC sketch (existing harness `test/foundry/IdleCreditVault.t.sol` provides helpers `_depositWithUser`, `_requestInstantWithdrawWithUser`, `_stopCurrentEpochWithApr`):

```solidity
function testStaleInstantReceiptInflatesRecovery() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);           // epoch #1
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false); // enable instant withdraws

    address alice = makeAddr('alice'); // attacker
    address bob = makeAddr('bob');
    uint256 tranchesA = _depositWithUser(alice, 50e6);
    uint256 tranchesB = _depositWithUser(bob, 50e6);

    vm.prank(manager); cdoEpoch.startEpoch();
    skip(101);

    // Alice requests and claims an instant withdraw while it is funded
    _requestInstantWithdrawWithUser(alice, tranchesA);
    vm.prank(alice); cdoEpoch.claimInstantWithdrawRequest();

    // stale entries remain
    assertGt(strategy.instantWithdrawsRequestsByEpoch(alice, strategy.epochNumber()), 0);

    // Bob's instant request stays pending/unfunded
    _requestInstantWithdrawWithUser(bob, tranchesB);
    // borrower defaults within the same epoch; honest actors finalize
    _handleBorrowerDefault();              // CDO marks defaulted
    cdoEpoch.finalizeDefaultRecovery(recovered, recoverySource);

    // Recovery price and reserve are inflated by Alice's already-paid claim
    // -> subsequent defaulted claims overpay until balance is exhausted;
    // last claimant's safeTransfer reverts (insolvency), and Alice's own
    // defaulted-claim path underflows on instantWithdrawsRequests -= basis.
}
```

Note: I could not fully verify within this session whether `requestInstantWithdraw` remains callable post-default at the `IdleCDOEpochVariant` level, which determines whether the attacker can additionally re-inflate `instantWithdrawsRequests` to bypass the underflow and drain the reserve directly rather than only freezing the tail claimants. The insolvency/frozen-funds impact stands regardless, since the stale `instantWithdrawClaimsByEpoch` entry is written unconditionally on every funded claim.
