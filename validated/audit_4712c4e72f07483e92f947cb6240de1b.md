### Title
Unbounded Recursive Descent in `TrieNode::decode` Enables Stack-Overflow DoS of the Fault-Proof Program via Crafted Preimages - (File: crates/proof/mpt/src/node.rs)

### Summary
`TrieNode::decode`, the RLP decoder used throughout Base's fault-proof program (op-program-equivalent) to parse Merkle-Patricia-Trie node preimages fetched from the L1/L2 preimage oracles, recurses into itself for `Extension` and `Branch` children with no depth limit and no size constraint forcing "large" children to be blinded (hashed) before being embedded. An attacker who can supply an arbitrary byte blob as a preimage (which, in the OP-Stack preimage-oracle / large-preimage-proposal flow, is validated only by checking that `keccak256(bytes) == requested_key` — i.e. the content is entirely attacker-chosen as long as they use its own hash as the key) can construct a single preimage containing thousands of nested, non-blinded `Extension`/`Branch` encodings. When the fault-proof program later decodes this preimage, `TrieNode::decode` will recurse thousands of levels deep on the native call stack, causing a stack overflow and crashing the proof-execution process. This is the same bug class as CVE-2024-8176 (libexpat): recursive structure parsing with no depth cap on untrusted input leading to stack exhaustion.

### Finding Description
`TrieNode::decode` peeks the RLP header and, for 2-element lists, calls `try_decode_leaf_or_extension_payload`, which for an `Extension` node calls `Self::decode(buf)` again on the child payload: [1](#0-0) 

For `Branch` nodes (17-element lists), it decodes a `Vec<Self>`, which itself invokes `Self::decode` for every one of the (up to 17) children, each of which may again be a `Branch` or `Extension`: [2](#0-1) 

Nowhere in this decode path is there a maximum-depth counter or a limit that an embedded (non-`Blinded`) child must be ≤32 bytes, unlike the canonical Ethereum trie invariant that only nodes ≤32 bytes may be embedded inline and larger ones must be represented as a `Blinded` 32-byte hash reference. Contrast this with the CBOR parser elsewhere in the same repository, which explicitly enforces `MAX_CBOR_NESTING_DEPTH` for exactly this reason: [3](#0-2) 

`TrieNode::decode` is invoked directly on preimage bytes fetched from the trusted-but-attacker-suppliable preimage oracle in both the L1 and L2 chain providers used by the fault-proof program: [4](#0-3) [5](#0-4) 

The only check performed before decoding is that the retrieved bytes hash to the requested `PreimageKey` (a `Keccak256` type), which is a self-consistency check, not a validity check of the trie-node structure. Any party participating in a dispute game (or feeding data through the preimage oracle's large-preimage-proposal mechanism) fully controls the byte content as long as they compute and use its own hash as the lookup key, so they can freely embed thousands of nested `Extension`/`Branch` structures inside one accepted preimage.

### Impact Explanation
When the fault-proof program (used to compute/verify the L2 output root during a dispute) opens such a maliciously crafted trie node while walking account/storage state, `TrieNode::decode`'s unbounded recursion will overflow the native stack and crash the process. This directly halts fault-proof execution, preventing correct resolution of a dispute game — either denying the honest party the ability to produce/verify the correct output root (enabling an attacker to win the dispute with an incorrect claim) or halting the proof program outright (a node/process halt in the fault-proof/verification path). Both are explicitly in-scope high-impact outcomes (wrong provable output root / node halt).

### Likelihood Explanation
Reachability is straightforward for anyone able to participate in the dispute-game/preimage-oracle flow: constructing a deeply nested chain of minimal RLP `Extension` nodes (each just a few bytes) is trivial, and no authentication beyond "hash of the bytes equals the claimed key" is required to get such a blob accepted as a valid preimage. No special privilege beyond being a dispute-game participant/preimage submitter is needed, and the vulnerable decode path (`TrieNode::decode`) is on the core state-resolution path exercised by every fault-proof run.

### Recommendation
Add an explicit recursion/nesting depth limit to `TrieNode::decode` (and its recursive helper `try_decode_leaf_or_extension_payload`), mirroring the `MAX_CBOR_NESTING_DEPTH` pattern already used in `crates/proof/tee/registrar/src/cbor.rs`. Additionally, enforce the canonical MPT invariant that only nodes with an RLP-encoded length ≤32 bytes may be embedded inline; any larger child must be rejected unless represented as `TrieNode::Blinded`. Converting the decoder to an iterative/worklist algorithm instead of native recursion would also eliminate the stack-overflow risk entirely.

### Proof of Concept
1. Construct nested RLP `Extension` nodes bottom-up, e.g. starting from `TrieNode::Empty`/a short `Leaf`, and repeatedly wrap: `ext_i = rlp([single_nibble_path, ext_(i-1)])`, keeping each `ext_i` embedded (not blinded) regardless of size (the encoder/decoder does not enforce the 32-byte embedding rule on decode).
2. Repeat wrapping ~50,000+ times to produce one large byte blob `P`.
3. Compute `key = keccak256(P)` and submit `P` as the preimage for `key` via the standard preimage-oracle path used by the dispute game (large preimage proposal), or via any mock/test `TrieProvider` in the codebase for local reproduction, e.g.:
```rust
let mut buf = P.as_slice();
let _ = TrieNode::decode(&mut buf); // recurses ~50,000 times -> stack overflow
```
4. Observe process crash (SIGSEGV/stack overflow) instead of a decode error, demonstrating the missing depth bound described above.
