### Title
Reward-partition count cap allows single-block/getBlock reward payload size to scale unboundedly with attacker-created stake account count - ([File: runtime/src/bank/partitioned_epoch_rewards/mod.rs])

### Finding Description
`Bank::get_reward_distribution_num_blocks` computes the number of partitions (blocks) used to distribute epoch rewards as `total_stake_accounts.div_ceil(stake_account_stores_per_block)`, but then clamps this value to a hard ceiling of `slots_per_epoch / 10` [1](#0-0) . This clamp is only a lower/upper bound on the *number of blocks*, not on the *number of rewards per block*. When an attacker creates and delegates from a very large number (N) of stake accounts, `total_stake_accounts` grows unboundedly while `num_chunks` is capped at `slots_per_epoch / 10` (e.g. 43,200 on mainnet-like schedules). Once `total_stake_accounts / stake_account_stores_per_block` exceeds this cap, the number of partitions stops growing and the average number of rewards placed in each partition becomes `N / (slots_per_epoch / 10)`, growing linearly with attacker-controlled N instead of being bounded by `MAX_PARTITIONED_REWARDS_PER_BLOCK = 4096` [2](#0-1) .

`hash_rewards_into_partitions` then places each stake reward into a partition bucket using `EpochRewardsHasher::hash_address_to_partition`, an address-hash-based assignment with no size cap per bucket [3](#0-2) . `Bank::store_stake_accounts_in_partition` then processes the entire `indices` slice for one partition/one block unconditionally, `Vec::with_capacity(indices.len())`-allocating and pushing every one into `updated_stake_rewards` with no truncation [4](#0-3) . `distribute_epoch_rewards_in_partition` then calls `update_reward_history_in_partition`, appending all non-zero rewards from that partition directly into `self.rewards`, the per-block reward history [5](#0-4) [6](#0-5) .

`Bank::get_rewards_and_num_partitions` exposes `self.rewards` unfiltered/untruncated as the reward set for the block, which is what a single `getBlock` (or `getInflationReward`, which itself issues one `getBlock` per partition slot as seen in `RpcHandler::get_inflation_reward`) RPC call serializes and returns to the client [7](#0-6) [8](#0-7) . There is no RPC-side limit on the size of the `rewards` array returned for a block — its size is purely a function of how many stake-account rewards landed in that partition, which an attacker fully controls by creating enough stake accounts.

### Impact Explanation
A single low-rate `getBlock` (or `getInflationReward`) RPC call against the block containing an inflated partition must construct and serialize a rewards vector whose length scales linearly with N attacker-created stake accounts, well beyond the intended `MAX_PARTITIONED_REWARDS_PER_BLOCK` (4096) design target. This is an unbounded single-request CPU/memory/serialization cost driven entirely by attacker-authored on-chain data (stake accounts), matching the "unbounded cost for a single low-rate call" bounty category.

### Likelihood Explanation
The attacker only needs funds (to pay rent for many stake accounts) and to delegate them before an epoch boundary — no special privileges, keys, or validator control are required. The vulnerable code path (`get_reward_distribution_num_blocks`'s clamp to `slots_per_epoch/10`) is unconditionally reachable any time reward distribution partitioning is computed at every epoch boundary, so this is entirely repeatable across epochs, limited only by how many stake accounts and how much rent-exempt SOL the attacker is willing to spend.

### Recommendation
Remove or redesign the `slots_per_epoch / 10` upper clamp on `num_chunks` in `get_reward_distribution_num_blocks`, or add an independent per-partition size cap (e.g., enforce `MAX_PARTITIONED_REWARDS_PER_BLOCK` strictly by increasing partition count beyond the 10%-of-epoch cap, or splitting oversized partitions across additional blocks/pages) so the number of rewards stored and returned per block/partition remains bounded regardless of total stake-account count. Additionally, consider adding an RPC-side pagination or truncation limit on the `rewards` field returned by `getBlock`/`getInflationReward` independent of on-chain content size.

        }

    stake_rewards: &PartitionedStakeRewards,
    parent_blockhash: &Hash,
    num_partitions: usize,
) -> Vec<Vec<usize>> {
    let hasher = EpochRewardsHasher::new(num_partitions, parent_blockhash);
    let mut indices = vec![vec![]; num_partitions];

    for (i, reward) in stake_rewards.enumerated_rewards_iter() {
        // clone here so the hasher's state is reused on each call to `hash_address_to_partition`.

        let partition_index = hasher
            .clone()
            .hash_address_to_partition(&reward.stake_pubkey);
        indices[partition_index].push(i);
    }
    indices
}
