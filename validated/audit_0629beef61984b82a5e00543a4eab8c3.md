### Title
Unbounded recursive `TrieNode::decode` allows stack-exhaustion crash of the fault-proof program on a hash-verified-but-attacker-shaped MPT preimage - (File: crates/proof/mpt/src/node.rs)

### Summary
`TrieNode::decode` recursively parses embedded (non-blinded, <32-byte) trie children with no depth limit, mirroring the CVE-2019-9903 bug class where `Dict::find()`/`PDFDoc::markObject` recursed without bound on attacker-crafted nested structures, exhausting the stack.

### Finding Description
`TrieNode::decode` in `crates/proof/mpt/src/node.rs` (lines 567-605) recurses into itself for `Extension` nodes via `Self::try_decode_leaf_or_extension_payload` → `Self::decode(buf)` at [1](#0-0)  and for `Branch` nodes via `Vec::<Self>::decode(buf)`, which itself calls `TrieNode::decode` for each of the up to 17 children, at [2](#0-1) . Per the MPT spec, a child node whose RLP encoding is under 32 bytes is embedded inline rather than "blinded" behind a keccak hash, so an attacker can nest short extension/branch nodes directly inside a single preimage buffer without ever needing a second `TrieProvider::trie_node_by_hash` round trip. Nowhere in this module (nor anywhere in `crates/proof/mpt`) is a `MAX_DEPTH`/recursion-depth guard defined — unlike the CBOR parser in `crates/proof/tee/registrar/src/cbor.rs`, which explicitly caps nesting at `MAX_CBOR_NESTING_DEPTH = 64` (see [3](#0-2) ), or the EIP-8130 delegate-authenticator path, which enforces a depth-1 guard.

This decode path is reached from attacker-influenced input in the fault-proof program: `OracleL1ChainProvider::trie_node_by_hash` decodes oracle-served preimage bytes directly with `TrieNode::decode` after only a hash-equality check against the requested key, not a structural/size check, at [4](#0-3) . The same untrusted-content, hash-verified-only pattern applies to the L2 chain provider (`crates/proof/proof/src/l2/chain_provider.rs`), which also imports and uses `TrieNode`/`TrieProvider` for L2 trie/account/history data. The preimage oracle protocol (used during a fault dispute game) only requires that submitted bytes hash to the requested key — it does not validate that the decoded RLP structure is a well-formed, depth-bounded MPT node. A dispute-game participant (defined in-scope as a reachable actor) can therefore submit a crafted preimage that hashes correctly but decodes into thousands of nested inline `Extension`/`Branch` levels, each recursive call frame consuming stack space with no bound, until the process stack is exhausted.

### Impact Explanation
A stack-overflow SIGSEGV in the fault-proof program (used by the dispute-game verifier/challenger to compute the correct output root) crashes that process. The codebase does install a SIGSEGV handler (`crates/utilities/cli/src/sigsegv.rs`) that prints diagnostics on overflow, but it terminates the process regardless — it does not recover execution. During dispute resolution, causing the honest challenger's proof-execution to crash on a malicious/crafted preimage can prevent computation of the correct output root, i.e. it can produce a wrong provable output root or halt fault-proof verification for that game, which are both explicitly in-scope high-impact outcomes (wrong provable output root / node halt).

### Likelihood Explanation
Reachability requires a dispute-game participant (or preimage-serving actor) to supply a preimage during proof execution whose bytes hash correctly to a value the fault-proof program looks up, but whose RLP content is a deeply nested chain of small embedded `Extension`/`Branch` nodes rather than a well-formed single-level node. Building such a preimage is a mechanical RLP-construction exercise (no cryptographic break required), and the depth achievable in a modestly sized buffer (a few KB) can be very large given how little each recursive frame needs to consume. The main open question — not verifiable from indexed contents alone — is the exact default thread stack size configured for the fault-proof program's execution thread and the per-frame cost of `TrieNode::decode`, which determine how large a preimage is required to trigger the crash in practice.

### Recommendation
Add an explicit recursion/nesting-depth counter to `TrieNode::decode` (mirroring the `MAX_CBOR_NESTING_DEPTH` pattern already used in `crates/proof/tee/registrar/src/cbor.rs`), rejecting RLP payloads whose embedded-node depth exceeds a small bound consistent with realistic mainnet MPT structure (state tries rarely embed more than a couple of levels of sub-32-byte nodes). Alternatively/additionally, convert the decode to an iterative, explicit-stack algorithm so recursion depth is decoupled from call-stack depth.

### Proof of Concept
Conceptually: construct RLP bytes for a `TrieNode::Extension` whose child is itself an `Extension` (both paths encoded with a single nibble so each level's RLP payload stays under 32 bytes and is therefore embedded rather than blinded), and repeat this nesting N times (e.g., tens of thousands) within one buffer. Feed this buffer as the "preimage" for a requested hash `H = keccak256(bytes)` through the oracle path exercised by `OracleL1ChainProvider::trie_node_by_hash` ( [4](#0-3) ), which calls `TrieNode::decode(&mut preimage.as_ref())`. Because each level's hash check only verifies the requested top-level key, not every embedded child, the attacker only needs the outer node's encoding to hash to `H`; the recursive `Self::decode` calls in `try_decode_leaf_or_extension_payload` ( [5](#0-4) ) will then walk the entire nested structure with no depth cap, exhausting the stack before returning.
