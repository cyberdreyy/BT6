### Title
Stale write-off requests can be fulfilled at outdated prices, extracting lender upside after tranche value changes - (File: `contracts/IdleCreditVaultWriteOffEscrow.sol`)

### Summary
`IdleCreditVaultWriteOffEscrow` lets a lender lock tranche tokens into a standing sell request at a fixed `underlyingsRequested` amount agreed off-chain with a buyer/borrower. The request has **no expiry, no epoch-binding, and no price re-check**. `fullfillWriteOffRequest` can be called by *any* wallet at *any* later time, paying only the stale `underlyings` amount to seize the escrowed tranche tokens — even when the on-chain tranche price has materially diverged from the price at request creation. This is the direct analog of the reported bug class (off-chain agreed data executed against a changed on-chain state).

### Finding Description
- `createWriteOffRequest` (lines 86–102) escrows `amount` tranche tokens and records a fixed `underlyingsRequested`. It only requires `isEpochRunning()` at creation. There is no deadline field, no nonce, no epoch identifier, and no price sanity check against the live tranche price (`IdleCDOEpochVariant._tranchePrice`).
- `fullfillWriteOffRequest` (lines 123–155) is callable by anyone. The only validation is `currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings` — i.e., the fulfiller merely has to pay at least the stale agreed amount. It transfers `_underlyings - fee` to the lender and the full tranche balance to `msg.sender`.
- Tranche NAV is not static during a running epoch: `writeOffDeposit` (IdleCDOEpochVariant.sol:936–963) burns tranches and changes supply/NAV, `depositDuringEpoch` (lines 656–733) mints at discounted prices and adds `expectedEpochInterest`, and a forced loss via `stopEpochWithDuration(_lossAmount)` re-prices tranches BB-first. Any of these moves `_trancheToUnderlyings` away from the value implied at request creation.
- Broken invariant: fair exchange at execution time. The escrow guarantees the lender's ask price but not the trade's fairness — a request priced when `tranchePrice` implied a haircut becomes a standing below-market option on the tranche tokens once NAV appreciates (e.g., after interest accrual or recovery), and conversely the lender's tranches sit frozen in escrow if NAV falls, since no rational fulfiller pays the stale (now above-market) ask.
- Existing guards do not stop it: `nonReentrant` only blocks reentrancy, `WrongRequest` only enforces the stale minimum, and `deleteWriteOffRequest` requires the lender to actively monitor and win the race — there is no liveness guarantee for the victim.

### Impact Explanation
- **Theft of lender upside**: if tranche value rises above `underlyingsRequested`, any attacker (fulfiller) calls `fullfillWriteOffRequest`, pays the stale amount, and receives tranches redeemable for more than paid. Loss to the lender ≈ `tranches * currentTranchePrice / 1e18 - underlyingsRequested` (net of ≤1% exit fee).
- **Value-locked requests**: if tranche value falls below the ask (loss event), the lender's tranches are stranded in escrow until manually deleted — temporary freezing of funds attributable to the missing expiry.

### Likelihood Explanation
Requires a lender to leave a request open while tranche value moves — realistic across epoch boundaries, interest accrual, `writeOffDeposit` executions, and loss events, precisely the "market condition changes between agreement and execution" scenario in the external report. The attacker needs only capital equal to the stale ask; fulfillment is permissionless. Likelihood is bounded by the lender's ability to front-run `deleteWriteOffRequest`, but there is no on-chain protection when they fail to.

### Recommendation
- Add an `expiry`/`deadline` (and optionally an `epochId`/epoch-number binding) to `WriteOffRequest`, set by the lender at creation; revert fulfillment after expiry.
- Alternatively, bind fulfillment to a fresh on-chain price check (e.g., require `underlyings >= tranches * _tranchePrice / 1e18 * (1 - maxDiscount)` or re-verify `isEpochRunning()` and same-epoch creation).
- Emit the epoch/price context in events so off-chain counterparties can detect stale requests.

### Proof of Concept
Foundry fork PoC (conceptual trace against the deployed CDO/escrow):

```solidity
// test/WriteOffStaleRequest.t.sol
function test_staleWriteOffRequestFulfillment() public {
    // setup: epoch running, lender holds AA tranches
    uint256 trancheAmt = 1000e18;
    // off-chain agreed price: 0.95 underlying per tranche
    uint256 agreed = 950e18;

    vm.prank(lender);
    escrow.createWriteOffRequest(trancheAmt, agreed);   // request created, no expiry

    // time passes / NAV changes: e.g. interest accrual pushes tranchePrice to 1.10
    vm.warp(block.timestamp + 20 days); // epoch still running
    // (or: borrower executes writeOffDeposit altering NAV upward)

    // attacker fulfills the stale request
    uint256 before = tranche.balanceOf(attacker);
    vm.prank(attacker);
    deal(underlying, attacker, agreed);
    vm.startPrank(attacker);
    IERC20(underlying).approve(address(escrow), agreed);
    escrow.fullfillWriteOffRequest(lender, trancheAmt, agreed);
    vm.stopPrank();

    // attacker received 1000 tranches worth ~1100 underlying for 950
    assertEq(tranche.balanceOf(attacker) - before, trancheAmt);
    uint256 profit = trancheAmt * cdo.tranchePrice(AATranche) / 1e18 - agreed;
    assertGt(profit, 0);
}
```

The gap is unverified on a live fork (no execution environment here), but the missing expiry and the permissionless stale-price fulfillment are directly evident at `IdleCreditVaultWriteOffEscrow.sol:86-102` and `123-155`.
