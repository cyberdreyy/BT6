### Title
Withdraw confidential-transfer instruction parser mislabels a proof-context account as the token `owner` when `account_indexes` is at the minimum length boundary - (File: `transaction-status/src/parse_token/extension/confidential_transfer.rs`)

### Summary
`parse_confidential_transfer_instruction`'s `Withdraw` arm sequentially advances an `offset` cursor to label `instructionsSysvar`, `equalityProofContextStateAccount`, and `rangeProofContextStateAccount`, but each label assignment is individually bounds-checked against `account_indexes.len().saturating_sub(1)` instead of validating that enough accounts exist for the actual number of context accounts implied by the attacker-controlled proof offsets. With the minimum accepted account count (`check_num_token_accounts(account_indexes, 4)`) and both `equality_proof_instruction_offset == 0` and `range_proof_instruction_offset == 0` (both proofs supplied as context-state accounts, not via sysvar), the loop assigns `equalityProofContextStateAccount` to `account_indexes[2]` but skips `rangeProofContextStateAccount` because `offset(3) < len-1(3)` is false, then calls `parse_signers(map, 3, ...)`, which mislabels `account_indexes[3]` (the true range-proof context account) as `owner`.

### Finding Description
The relevant code: [1](#0-0) 

- `check_num_token_accounts(account_indexes, 4)` at line 178 only enforces a *minimum* of 4 accounts; it does not enforce that the exact number of accounts matches the combination of proof-location choices encoded in `withdrawal_data.equality_proof_instruction_offset` / `range_proof_instruction_offset`, both attacker-controlled `i8` fields decoded directly from `instruction_data` via `decode_instruction_data`.
- Each conditional block (`instructionsSysvar`, `equalityProofContextStateAccount`, `rangeProofContextStateAccount`) independently checks `offset < account_indexes.len().saturating_sub(1)` before consuming an index and incrementing `offset`. When `account_indexes.len() == 4` (the allowed minimum) and both offsets are `0` (both proofs are context-state accounts, so `has_sysvar == false`), the sequence is:
  - `offset = 2`: sysvar skipped (`has_sysvar` false).
  - `offset = 2 < 3`: `equalityProofContextStateAccount = account_indexes[2]`, `offset = 3`.
  - `offset = 3 < 3` → **false**: `rangeProofContextStateAccount` assignment is skipped even though `range_proof_instruction_offset == 0` says it should exist.
  - `parse_signers(map, offset=3, ...)` then labels `account_indexes[3]` as `"owner"`.
- This differs from what the spl-token-2022 reference (`inner_withdraw`) actually lays accounts out as when both proofs are context-state accounts: `[account, mint, equalityProofContextState, rangeProofContextState, authority, ...]` (5+ accounts). The parser here, with an attacker-crafted 4-account instruction, mislabels the 4th account (which should be `rangeProofContextStateAccount`) as the token `owner`, and silently drops `rangeProofContextStateAccount` from the JSON output.
- The attacker fully controls `instruction_data` (the two `i8` offsets) and `account_indexes`/`accounts` list length of a `CompiledInstruction` addressed to the SPL Token-2022 program ID; this instruction data is not validated by this parser against the true spl-token-2022 program semantics, only decoded byte-for-byte via `decode_instruction_data`.
- This parser is reached from `parse_token` [2](#0-1)  which is called unconditionally from `parse_instruction::parse` for `ParsableProgram::SplToken` when a client requests `encoding=jsonParsed` on a transaction [3](#0-2) , and this happens regardless of whether the instruction actually executed successfully on-chain (parsing operates purely on the raw compiled instruction/account keys recorded in the block).

### Impact Explanation
This is a decoder/parser misreporting bug: `getTransaction`/`getConfirmedTransaction` (and any RPC/websocket path using `UiTransactionEncoding::JsonParsed`) will return a JSON-parsed instruction where the `owner` field actually points to what is really the on-chain `rangeProofContextStateAccount` pubkey, and the `rangeProofContextStateAccount` field is missing entirely. Any client, block explorer, or downstream indexer consuming the parsed output would attribute account/authority semantics to the wrong pubkey — this matches the "wrong ... account data returned" / "decoder ... misreporting" category called out in the Validate section. It does not cause a crash, panic, or consensus impact; the scope is limited to the correctness of the human-readable/jsonParsed transaction-history representation.

### Likelihood Explanation
Fully attacker-controlled and trivially reproducible: the attacker only needs to construct and submit a single transaction containing a compiled instruction addressed to the SPL Token-2022 program ID with `ConfidentialTransferInstruction::Withdraw` discriminator, `equality_proof_instruction_offset = 0`, `range_proof_instruction_offset = 0`, and an `accounts` list of exactly 4 entries. The transaction can even fail on-chain execution (e.g. real SPL Token-2022 validation rejecting the malformed layout) and still be recorded in a block; the parser applies regardless of execution success. A single subsequent `getTransaction` call with `encoding: "jsonParsed"` (one client, one call) triggers the misreporting. No validator/leader/staked control or elevated privileges are required.

### Recommendation
In the `Withdraw` (and analogously `Transfer`/`TransferWithFee`) arms, compute the exact number of trailing accounts required from the combination of `has_sysvar` plus the number of `== 0` proof offsets, and validate `account_indexes.len()` against that exact count (or at least `expected_offset_count + 1` for the signer) before assigning any labels, returning `ParseInstructionError::InstructionNotParsable` if the account list is too short — rather than silently skipping a context-account assignment because of a loose `len() - 1` boundary check that conflates "not enough room for a context account" with "not enough room for a context account AND signer both".

### Proof of Concept
Rust unit test (in `transaction-status/src/parse_token/extension/confidential_transfer.rs` test module) demonstrating the mislabeling:

```rust
#[test]
fn test_withdraw_min_len_both_context_mislabels_owner() {
    let token_account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let range_ctx = Pubkey::new_unique(); // should be labeled rangeProofContextStateAccount
    let equality_ctx = Pubkey::new_unique();

    // Craft raw WithdrawInstructionData with both offsets == 0 (context-account mode)
    // and exactly 4 account indexes: [account, mint, equality_ctx, range_ctx]
    let instruction_data = build_withdraw_instruction_data(
        /* amount */ 42, /* decimals */ 9,
        /* new_decryptable_available_balance */ Default::default(),
        /* equality_proof_instruction_offset */ 0i8,
        /* range_proof_instruction_offset */ 0i8,
    );

    let account_keys_vec = vec![token_account, mint, equality_ctx, range_ctx];
    let compiled_instruction = CompiledInstruction {
        program_id_index: 4, // separate program id entry appended
        accounts: vec![0, 1, 2, 3],
        data: instruction_data,
    };
    let mut all_keys = account_keys_vec.clone();
    all_keys.push(spl_token_2022_interface::id());
    let account_keys = AccountKeys::new(&all_keys, None);

    let parsed = parse_token(&compiled_instruction, &account_keys).unwrap();

    // BUG: rangeProofContextStateAccount is missing from output
    assert!(parsed.info.get("rangeProofContextStateAccount").is_none());
    // BUG: "owner" is actually the range-proof context account, not a real owner
    assert_eq!(parsed.info["owner"], json!(range_ctx.to_string()));
}
```

Expected (correct) behavior per spl-token-2022 semantics: `rangeProofContextStateAccount` should equal `range_ctx`, and no `owner`/`multisigOwner` field should be populated from an account slot that doesn't actually exist (a 5th account for the true owner is absent). The test as written demonstrates the current mislabeling defect.
