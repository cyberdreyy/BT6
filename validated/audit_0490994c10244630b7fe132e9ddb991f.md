### Title
Docker executor's `resumeDependencies()` skips the RunnerID/SystemID ownership check that the autoscaler executor enforces on the same `EnvironmentKey` - ([File: executors/docker/docker.go])

### Summary
`executors/docker/docker.go`'s `resumeDependencies()` parses `common.ParseEnvironmentKey()` and immediately calls `ContainerInspect`/`ContainerAttach`/`ContainerStart` on the `build-container-id`/`helper-id`/`service-ids` it contains, without ever checking that `envKey.RunnerID`/`envKey.SystemID` match the runner instance processing the job. The analogous autoscaler code path (`executors/internal/autoscaler/executor.go`'s `validateEnvKey`) explicitly performs this check ("environment key was not issued by this runner"/"...this machine") before trusting the key's fields, showing the codebase's own security model expects this validation, but it is missing in the Docker executor.

### Finding Description
`common.ParseEnvironmentKey` (`common/environment_key.go:26-58`) only validates syntactic well-formedness of the `<runner-id>/<system-id>/<fields>` string; it does not, and cannot, know which runner is calling it. The caller is responsible for verifying `RunnerID`/`SystemID` ownership. `executors/internal/autoscaler/executor.go`'s `validateEnvKey` (lines 190-209) does exactly that: [1](#0-0) 

By contrast, `executors/docker/docker.go`'s `resumeDependencies()` never performs this check: [2](#0-1) 

It goes straight from `common.ParseEnvironmentKey`/`parseEnvKeyFields` to `e.dockerConn.ContainerInspect(...)` using attacker/backend-controlled container ID strings, then later `Prepare()` -> `Run()` reaches `startAndWatchContainer` -> `exec.NewDocker(...).Exec` -> `defaultDocker.Exec` which does `ContainerAttach`/`ContainerStart` on that same container ID: [3](#0-2) 

The `EnvironmentKey` itself is generated by the runner during `suspendEnvironment` (embedding `RunnerID`/`SystemID`) and reported to the GitLab backend via `trace.SetEnvironmentKey`/`UpdateJob`, and is later fed back to the runner as `spec.Job.SuspendOptions.EnvironmentKey` on the resuming job: [4](#0-3) [5](#0-4) 

Correct routing of that key back to the same runner/environment is a responsibility split between GitLab backend (project/environment scoping) and the runner (RunnerID/SystemID check as defense-in-depth). The autoscaler executor implements the runner-side check; the Docker executor does not. Existing tests (`executors/docker/docker_test.go` `TestResumeDependencies*`) only cover "container not found" failure paths, never an RunnerID/SystemID-mismatch rejection, confirming no such guard exists for Docker.

### Impact Explanation
If a `SuspendOptions.EnvironmentKey` referencing container IDs owned by a different runner/project ever reaches a Docker executor instance (e.g., misrouting, multi-runner-per-host misconfiguration, or a backend logic flaw feeding back a stale/foreign key), the Docker executor will blindly `ContainerInspect`/`ContainerAttach`/`ContainerStart` that container and inject the job's script into it via `defaultDocker.Exec`, exfiltrating whatever secrets/tokens are present in that container's environment or filesystem, and potentially disrupting/taking over the other job's execution. The Docker executor provides no local ownership check to stop this, unlike the autoscaler executor.

### Likelihood Explanation
Exploitability depends entirely on whether GitLab backend can be made to deliver a foreign `EnvironmentKey` to a runner/job it wasn't issued for. Given the rules of this audit (GitLab-backend compromise or external-service compromise alone is out of scope, and the feature is gated behind `featureflags.SuspendableEnvironments`), a purely runner-side unprivileged attacker cannot, by themselves, forge or redirect an `EnvironmentKey` across projects without such backend-level routing/authorization also failing. The finding is therefore about an absent *defense-in-depth* check on the runner side rather than a directly, independently exploitable primitive.

### Recommendation
Add a `RunnerID`/`SystemID` ownership check to `executors/docker/docker.go`'s `resumeDependencies()`, mirroring `validateEnvKey` in `executors/internal/autoscaler/executor.go`: reject the environment key with an explicit error if `envKey.RunnerID != e.Config.ID` or `envKey.SystemID != e.Config.GetSystemID()` before calling `ContainerInspect`/`ContainerAttach`.

### Proof of Concept
Add a test alongside `TestResumeDependencies` in `executors/docker/docker_test.go`:
```go
func TestResumeDependencies_RejectsForeignRunnerEnvKey(t *testing.T) {
    c := docker.NewMockClient(t)
    e := executorWithMockClient(c)
    require.NoError(t, e.dockerConnector.Connect(t.Context(), common.ExecutorPrepareOptions{}, e))
    e.Config = common.RunnerConfig{RunnerCredentials: common.RunnerCredentials{ID: 7}, SystemID: "sys-1"}
    e.Build = &common.Build{Runner: &common.RunnerConfig{RunnerCredentials: common.RunnerCredentials{ID: 7}}}
    e.Build.Variables = append(e.Build.Variables, spec.Variable{Key: featureflags.SuspendableEnvironments, Value: "true"})
    // Env key issued for a *different* runner/system:
    e.Build.Job.SuspendOptions.EnvironmentKey =
        "99/other-sys/build-container-id=victim-build&helper-id=victim-helper"

    err := e.resumeDependencies()
    require.Error(t, err) // currently fails: ContainerInspect is called with no rejection
    assert.Contains(t, err.Error(), "not issued by this runner")
}
```
Currently this test would fail because `resumeDependencies()` proceeds straight to `c.On("ContainerInspect", ...)` without any RunnerID/SystemID assertion, demonstrating the missing check.

```go
func validateEnvKey(envKey string, runnerID int64, systemID string) (string, url.Values, error) {
	key, err := common.ParseEnvironmentKey(envKey)
	if err != nil {
		return "", nil, err
	}

	if key.RunnerID != runnerID {
		return "", nil, errors.New("environment key was not issued by this runner")
	}
	if key.SystemID != systemID {
		return "", nil, errors.New("environment key was not issued by this machine")
	}
```

```go
func (e *executor) resumeDependencies() error {
	envKey, err := common.ParseEnvironmentKey(e.Build.EnvironmentKey())
	if err != nil {
		return err
	}
	fields, err := parseEnvKeyFields(envKey.Fields)
	if err != nil {
		return err
	}

	buildInspect, err := e.dockerConn.ContainerInspect(e.Context, fields.buildContainerID)
	if err != nil {
		return fmt.Errorf("build container %s not found: %w", fields.buildContainerID, err)
	}
	e.buildContainerID = buildInspect.ID
	e.buildContainer = &buildInspect

	helperInspect, err := e.dockerConn.ContainerInspect(e.Context, fields.helperContainerID)
	if err != nil {
		return fmt.Errorf("helper container %s not found: %w", fields.helperContainerID, err)
	}
	e.helperContainer = &helperInspect
```

```go
func (b *Build) suspendEnvironment(ctx context.Context, executor Executor) (string, error) {
	se, ok := executor.(SuspendableExecutor)
	if !ok {
		b.logger.Warningln("Job environment suspension not supported by executor")
		return "", errors.New("executor does not support suspend/resume")
	}
	fields, err := se.Suspend(ctx)
	if err != nil {
		b.logger.Warningln("Job environment suspension failed:", err.Error())
		return "", fmt.Errorf("suspending environment: %w", err)
	}
	envKey := EnvironmentKey{
		RunnerID: b.Runner.ID,
		SystemID: b.Runner.GetSystemID(),
		Fields:   fields,
	}
	s := envKey.String()
	b.logger.Infoln("Job environment suspended:", s)
	return s, nil
}
```
