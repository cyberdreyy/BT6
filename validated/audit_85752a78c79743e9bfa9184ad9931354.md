### Title
Attacker-controlled JSON-RPC request ID collision can grief/DoS legitimate Vault gateway requests - (File: core/services/gateway/handlers/vault/handler.go)

### Summary
The Gateway's Vault handler (`core/services/gateway/handlers/vault/handler.go`) tracks all in-flight requests in a single global map `h.activeRequests`, keyed only by the client-supplied JSON-RPC `req.ID` [1](#0-0) . `HandleJSONRPCUserMessage` accepts any non-empty ID up to 200 characters from an unauthenticated caller before authorization is fully applied for some methods, and inserts it via `newActiveRequest`, which fails if the ID already exists: [2](#0-1) .

### Finding Description
`newActiveRequest` performs a simple existence check and rejects the request with `"request ID already exists"` if any other in-flight request (from any sender/workflow) currently holds that same ID: [1](#0-0) 

The confidential relay handler shares the identical pattern: [3](#0-2) 

The `activeRequests` map is global to the handler instance and is not partitioned by sender, workflow owner, or authorization key — unlike `common/requestcache.go`'s `RequestCache`, which explicitly scopes pending entries by `globalId{sender, id}` to prevent exactly this collision: [4](#0-3) 

Because the Vault/relay handlers lack this per-sender scoping, an attacker who can reach the gateway's JSON-RPC user-message endpoint can:
1. Observe or guess a victim's `req.ID` (e.g., IDs may be predictable, sequential, or leaked in logs/telemetry), or race to submit a request with the same ID as a soon-to-be-sent legitimate request.
2. Send a request with that same ID first. If it lands in `activeRequests` before the victim's genuine request, the victim's call to `newActiveRequest` fails and their request is dropped with a "request ID already exists" error — exactly analogous to the LP-token griefing in `exitTempusAMM`, where an attacker pollutes shared state keyed by an identifier the victim also relies on, causing the victim's legitimate call to revert/fail.

This is reachable without any privilege beyond being able to submit a message through the gateway's JSON-RPC ingress (`HandleJSONRPCUserMessage`), since request-ID validation happens before/independent of authorization outcome for the ID uniqueness check itself (the uniqueness check occurs regardless of whether the attacker's own request is ultimately authorized).

### Impact Explanation
An attacker can selectively deny service to a specific victim's Vault secrets operation (create/update/delete/list) or confidential-relay capability call by colliding on the `req.ID`, without needing to be an authorized party for that workflow. This is a targeted griefing/DoS vector against normal node clients rather than a global DoS, similar in class/severity to the original Medium-severity finding: it makes the operation "unusable" for the intended requester while requiring only that an unprivileged party can reach the gateway ingress and predict or race the `req.ID`.

### Likelihood Explanation
Likelihood depends on how `req.ID`s are generated by legitimate callers (e.g., UUIDs are hard to guess, reducing likelihood to a pure race-condition/timing attack) and how easily the gateway ingress can be reached by non-DON-authorized senders. If IDs are sufficiently random (per `fetchVaultPublicKey`'s use of `uuid.New().String()` [5](#0-4) ), pure guessing is impractical, but the vulnerability is still present as a race-window griefing bug for any two concurrent submissions sharing an ID (whether from misconfiguration, retries, or malicious duplication), and the lack of sender-scoping is a structural weakness compared to the safer pattern already used in `common/requestcache.go`.

### Recommendation
Scope `activeRequests` (and the analogous map in `confidentialrelay/handler.go`) by both the authenticated sender/workflow identity and `req.ID`, following the `globalId{sender, id}` pattern already implemented in `core/services/gateway/handlers/common/requestcache.go`, rather than by `req.ID` alone. Perform this uniqueness check only after authorization succeeds, so an unauthenticated/unauthorized attacker cannot occupy an ID slot at all.

### Proof of Concept
Not independently executable from static analysis alone; the collision would require: (1) attacker submits `jsonrpc.Request{ID: "X", ...}` to `HandleJSONRPCUserMessage`, (2) victim's legitimate client submits a request with the same `ID: "X"` before the attacker's entry is cleaned up (via response or `removeExpiredRequests` timeout), (3) `newActiveRequest` for the victim returns `"request ID already exists: X"` [6](#0-5) , causing `HandleJSONRPCUserMessage` to return that error instead of processing the victim's request. This matches the test scaffold pattern already present for duplicate IDs: [7](#0-6) 

**Uncertainty**: I could not fully verify from the index (1) exactly how/where `req.ID` is generated by legitimate node-side clients calling into this gateway ingress (whether always cryptographically random, thus limiting practical guessability), and (2) whether an additional network/authentication layer in front of the gateway (e.g., mTLS allowlist for DON members) restricts who can invoke `HandleJSONRPCUserMessage` in production deployments, which would reduce this from an "any unprivileged internet client" issue to a "any authenticated DON member" issue. A Devin session with full repo/build access would be needed to trace the gateway's connection-layer authentication to confirm the exact unprivileged-reachability boundary.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		// Arbitrary limit to prevent abuse
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)
	if req.Method == vaulttypes.MethodPublicKeyGet {
		// Public key requests don't require authorization,
		// Let's process this request right away.
		// Note we cache this value quite aggressively so don't need to worry about DoS.
		publicKeyResponseBytes, cachedPublicKey := h.getCachedPublicKey()
		if cachedPublicKey == nil {
			// Not found in cache. Fetch from nodes.
			ar, err := h.newActiveRequest(req, callback)
			if err != nil {
				h.lggr.Errorw("failed to create new activeRequest", "error", err)
				return err
			}
			return h.handlePublicKeyGet(ctx, ar)
		}
		h.lggr.Debugw("returning cached public key response")
		return h.handlePublicKeyGetSynchronously(ctx, req, publicKeyResponseBytes, callback)
	}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

	sender string
	id     string

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
