### Title
Loss haircut applied to aggregate `pendingWithdraws` only hits current-epoch receipts — stale-epoch receipt holders claim at par and drain the funded pot - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` computes the loss haircut on the *aggregate* `pendingWithdraws` bucket and stores the recovery price under the *current* `epochNumber`. But claims only apply the haircut to receipts whose request epoch equals `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]`. Receipts from earlier epochs still sit in `withdrawsRequests` and are paid at par via `_claimFundedWithdrawRequest`, even though the borrower only funded the haircutted total. First-come claimants drain the underfunded pot; later claimants' funded withdrawals revert.

### Finding Description
The analog of CVE-2018-11624 (stale state used after being logically released/repurposed) is the per-epoch receipt accounting:

1. `requestWithdraw` records `withdrawsRequestsByEpoch[user][epochNumber]` and adds `_amount` to the global `pendingWithdraws` (lines 279-293). A user who does not claim keeps their basis in `pendingWithdraws` indefinitely across epochs.
2. On a `stopEpochWithDuration` loss, `collectWithdrawFunds(_amount)` compares `_amount` to `pendingWithdraws` — the whole aggregate including old-epoch receipts — and stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis`, then zeroes `pendingWithdraws` (lines 411-421). The funded `_amount` is the haircut value of *all* pending receipts.
3. `_claimLossAdjustedWithdrawRequest` only looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` (lines 789-800). A user whose `lastWithdrawRequest` is an older epoch sees `lossRecoveryPriceByEpoch[oldEpoch] == 0` and falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[user]` at par (lines 319-349).

The haircut math assumed *every* pending receipt bears the loss, but only receipts created in the loss epoch actually do. Old-epoch receipts are "freed" from the pending basis at `collectWithdrawFunds` yet remain claimable at par — the same underlying is effectively owed twice.

### Impact Explanation
Broken invariant: loss waterfall / one receipt one payout. Concretely: user A requests 100 in epoch N and never claims; user B requests 100 in epoch N+1; `pendingWithdraws = 200`. A 50% loss leads `collectWithdrawFunds(100)` — a recovery price of 0.5e18 stored under epoch N+1, and 100 underlying pulled in. User A calls `claimWithdrawRequest` first and receives the full 100 at par (old epoch, no haircut). User B's legitimate haircutted claim of 50 now reverts on `underlyingToken.safeTransfer` because the pot is empty. User A permanently escapes a 50 loss that was priced into B's receipts; user B suffers a total loss of their funded 50 instead of the intended 50% haircut.

### Likelihood Explanation
Requires an epoch ending with `stopEpochWithDuration`/`collectWithdrawFunds` partial funding (a real borrower shortfall/loss event — an expected code path, not an edge case) plus at least one stale unclaimed receipt from a prior epoch. Both are unprivileged-lender-reachable states: any KYC'd lender can `requestWithdraw` and simply not claim. No privileged attacker is needed — the honest manager triggers the loss epoch and the attacker just claims first. Race ordering is cheap since claims are first-come-first-served on an underfunded pot.

### Recommendation
Track the pending basis per epoch (e.g., `pendingWithdrawsByEpoch[epoch]`) and apply `lossRecoveryPriceByEpoch` to *all* outstanding receipt epochs, not only `lastWithdrawRequest`; alternatively settle/roll stale receipts into the loss epoch's haircut at `collectWithdrawFunds` time. At minimum, compute the recovery price only over receipts that will actually be haircut, or carry an explicit funded-par bucket for older receipts.

//   claimBasis=100e6 * 0.5e18 / 1e18 = 50e6; safeTransfer reverts (insufficient balance).
