### Title
Signer vote-flip (Reject → Accept) double-counts weight across `total_weight_approved` and `total_weight_rejected` in the node's `StackerDBListener` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run` (in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`) tallies each signer's weight into either `total_weight_approved` or `total_weight_rejected` as `BlockResponse` messages arrive for a proposed block, guarding against double-counting with two *different* "already seen" sets: `gathered_signatures` for acceptances and `responded_signers` for rejections. Because a signer that first rejects and then later accepts the same block (a normal, single-signer state transition explicitly supported by the signer's own state machine, `LocallyRejected --> LocallyAccepted`) is gated by `responded_signers` on the reject path but by `gathered_signatures` on the accept path, its weight gets added to `total_weight_rejected` on the first message and *again* added to `total_weight_approved` on the second message, with nothing ever removed from the rejected tally.

### Finding Description
The rejection-handling branch gates weight addition solely on `responded_signers`: [1](#0-0) 

while the acceptance-handling branch gates weight addition solely on `gathered_signatures`, and unconditionally inserts into `responded_signers` afterward: [2](#0-1) 

These are two independent sets tracking two independent conditions:
- Accept-then-Reject is safe: accepting inserts the slot into `responded_signers`, so a later reject's `responded_signers.insert(slot_id)` returns `false` and is skipped.
- Reject-then-Accept is *not* safe: rejecting only touches `responded_signers`, never `gathered_signatures`. When the same signer later sends an acceptance for the same block/sighash, `!block.gathered_signatures.contains_key(&slot_id)` is still `true`, so `total_weight_approved` is incremented — while the earlier contribution to `total_weight_rejected` is never removed.

The signer-side state machine explicitly allows this reject→accept sequence for the exact same block hash during ordinary re-evaluation (see `docs/signer-flows.md` lifecycle: `LocallyRejected --> LocallyAccepted : re-evaluated`), so this is reachable by any single ordinary signer under normal operation — no majority, no other signer's key, and no auth bypass is required. It can also be triggered adversarially by a single signer replaying a stale/duplicate rejection followed by a legitimate late acceptance, or vice versa across message reordering on the gossip layer.

The consequence is that `total_weight_approved + total_weight_rejected` can exceed the signer set's `total_weight`, i.e. the same signer's weight is simultaneously "spent" on both sides of the tally. This breaks the intended invariant that a signer's weight counts toward exactly one side of the acceptance/rejection accounting used by the block-signing coordinator.

### Impact Explanation
This is used directly by `SignCoordinator::get_block_status` in `stacks-node/src/nakamoto_node/signer_coordinator.rs`, which checks:
- `total_weight_rejected.saturating_add(weight_threshold) > total_weight` → treat block as globally rejected (`SignersRejected`)
- `total_weight_approved >= weight_threshold` → treat block as accepted [3](#0-2) 

Because a signer's stale rejection weight is never cleared after that signer flips to acceptance, `total_weight_rejected` can remain permanently inflated with weight from signers who no longer object, while `total_weight_approved` also independently accumulates their later acceptance weight. In an adversarial or even just poorly-timed honest scenario (message reordering/re-evaluation), this can push `total_weight_rejected` over the blocking-minority threshold for a block that, based on current signer intent, actually has enough real approval — causing the miner to spuriously abandon a legitimate block (`NakamotoNodeError::SignersRejected`) and stall/retry the tenure. This is a liveness degradation of the block-production pipeline driven by a single signer's ordinary vote-flip, not requiring a majority or any privileged access.

### Likelihood Explanation
The reject→accept sequence for the same block sighash is a normal, documented transition in the signer's own state machine (re-evaluation of a previously-rejected block), so it can occur without any adversarial behavior — merely from the signer changing its view (e.g., after `should_reevaluate_reject_reason` allows re-evaluation) after the node already recorded the earlier rejection. Because the two acceptance/rejection paths in `stackerdb_listener.rs` use disjoint dedup sets, this is deterministically triggered any time that ordering occurs, without requiring cooperation from other signers.

### Recommendation
Use a single per-block "already tallied" map keyed by `slot_id` that records which side (approved/rejected) a signer's weight was counted toward, and when a signer's vote is observed to flip, atomically move the weight from one bucket to the other (or subtract it) instead of relying on two independently-checked sets (`gathered_signatures` and `responded_signers`). Concretely, before adding to `total_weight_approved`, check whether the signer's slot is already recorded as rejected and, if so, subtract its weight from `total_weight_rejected` (and vice versa for the reject path).

### Proof of Concept
1. Node proposes block `B` to a signer set with signer `S` holding weight `w`.
2. `S` sends `BlockResponse::Rejected` for `B`. In `stackerdb_listener.rs`, `responded_signers.insert(slot_id)` succeeds, so `total_weight_rejected += w` (lines 515-519).
3. `S`'s local signer state machine later re-evaluates `B` (e.g., `should_reevaluate_reject_reason` permits it) and moves from `LocallyRejected` to `LocallyAccepted`, broadcasting `BlockResponse::Accepted` for the same `signer_signature_hash`.
4. The node's listener processes this: `gathered_signatures.contains_key(&slot_id)` is `false` (it was never touched by the reject path), so `total_weight_approved += w` (lines 443-465), while `total_weight_rejected` still retains the earlier `w` from step 2 — never decremented.
5. `total_weight_approved + total_weight_rejected` now exceeds `total_weight` by `w`; `S`'s weight has been counted on both sides simultaneously, corrupting the threshold computation used by `SignCoordinator::get_block_status`.
