### Title
Instant-withdraw receipts from non-default epochs escape the recovery haircut and are permanently unclaimable or overpaid — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Analogous to the UPX crash where a crafted file drives `invert_pt_dynamic()` to index an invalid/missing `PT_DYNAMIC` entry, an unprivileged lender can craft a receipt set whose "index" (per-epoch instant-withdraw bookkeeping) points at a bucket the default-finalization math never looks at. `defaultPendingClaimBasis()` only adds `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch — while `pendingInstantWithdraws` is a global aggregate that can carry unfunded instant receipts from an earlier epoch. After `finalizeDefaultRecovery`, those stale-epoch receipts are neither haircut through `_claimDefaultedInstantWithdrawRequest` (which only clears `defaultRecoveryEpoch`) nor covered by the computed reserve, breaking the "one receipt, one haircut payout" invariant.

### Finding Description
`requestInstantWithdraw` records claims per epoch (`instantWithdrawsRequestsByEpoch[user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`) but aggregates liability globally in `pendingInstantWithdraws` [1](#0-0) . Nothing forces the honest manager to call `getInstantWithdrawFunds()` in a given epoch, and nothing clears `pendingInstantWithdraws` at epoch boundaries, so instant receipts can remain unfunded across an epoch transition.

At default finalization, `defaultPendingClaimBasis()` returns `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` — it uses only the current epoch's claim map even though `pendingInstantWithdraws != 0` may include prior-epoch claims [2](#0-1) . Consequently `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is computed on a basis that omits the stale-epoch instant claims [3](#0-2) . Afterwards, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest`, which clears only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`, then pays the *entire remaining* `instantWithdrawsRequests[user]` at par through `_transferFundedClaim` [4](#0-3) [5](#0-4) .

Attack sequence (fixed-APR, instant-withdraw mode):
1. Epoch E1 buffer: attacker deposits AA and requests an instant withdraw for amount X → `instantWithdrawClaimsByEpoch[E1] += X`, `pendingInstantWithdraws += X`. Manager never calls `getInstantWithdrawFunds` (honest, but optional).
2. Epoch E1 stops, E2 runs and stops; borrower shortfall at `stopEpoch` triggers `_handleBorrowerDefault`.
3. Owner/manager calls `finalizeDefault(recovered, src)`. `defaultRecoveryEpoch = E2`; total basis excludes X.
4. Attacker calls `claimInstantWithdrawRequest`: defaulted-E2 clearing returns 0, then `amount = instantWithdrawsRequests[user] = X` is burned and paid at par via `_transferFundedClaim`.

### Impact Explanation
Two outcomes, both with fund impact:
- If the strategy holds any non-reserve underlying ≥ X, the attacker is paid 100% while every other claimant (active LPs, defaulted receipts) absorbs a recovery price computed on a diluted basis — direct theft of the haircut X·(1 − recoveryPrice) and reserve dilution for honest users.
- If no non-reserve balance exists, the `_transferFundedClaim` reserve guard (`balance - reserve < _amount → revert NotAllowed`) permanently freezes the stale-epoch receipt [6](#0-5) , i.e., permanent freezing of a legitimate claim.

Either way, `recoveryPrice` is inflated relative to true outstanding claims, so the reserve is insolvent against all claims by exactly the omitted stale-epoch instant basis.

### Likelihood Explanation
Requires only: instant withdrawals enabled, an attacker making an instant request in an epoch where the (honest) manager happens not to call `getInstantWithdrawFunds`, and a later borrower default in a subsequent epoch. All attacker steps are unprivileged (`depositAA`, `requestWithdraw`, `claimInstantWithdrawRequest`). The missing aggregation in `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` is deterministic once the state exists.

Uncertainty: the claim requires that an epoch can end with `pendingInstantWithdraws > 0` without the pool defaulting — i.e., that the manager's funding call is genuinely optional within the epoch lifecycle. If off-chain operations always fund instantly, the window narrows. I could not fully verify whether `_stopEpoch` or `startEpoch` reverts on nonzero `pendingInstantWithdraws`; the view snippets suggest they do not gate on it, but this should be confirmed in the PoC.

### Recommendation
In `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, aggregate instant claim basis across all epochs with outstanding receipts (e.g., track a global `totalInstantClaimBasis` instead of relying solely on `instantWithdrawClaimsByEpoch[epochNumber]`), or iterate/sum stale-epoch buckets. Additionally, in `claimInstantWithdrawRequest`, route *all* unfunded instant receipts (any epoch) through `_claimDefaultedInstantWithdrawRequest` semantics when `defaultInstantWithdrawsFinalized`, rather than paying non-default-epoch claims at par.

```solidity
// Foundry fork-style PoC (contracts under test in test/foundry/IdleCreditVault.t.sol harness)
function testStaleEpochInstantClaimEscapesRecovery() external {
    uint256 instantDelay = cdoEpoch.instantWithdrawDelay();
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(instantDelay, 1000, false);

    address attacker = makeAddr('attacker');
    uint256 amount = 10_000 * ONE_SCALE;
    _depositWithUser(attacker, amount, true);

    // Epoch E0 -> stop with lower apr so instant withdraws are available
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // Epoch E1 buffer: attacker requests instant withdraw; manager NEVER funds it
    vm.prank(attacker);
    uint256 instantClaim = cdoEpoch.requestWithdraw(0, address(AAtranche));

    IdleCreditVault creditVault = IdleCreditVault(address(strategy));

    // Epoch E1 runs (no getInstantWithdrawFunds call), then stops into E2 buffer
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // Epoch E2 runs; borrower defaults at stopEpoch (no funds dealt)
    deal(defaultUnderlying, borrower, 0);
    _startEpochAndCheckPrices(2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _checkDefault();

    // Finalize: basis omits instantWithdrawClaimsByEpoch[1] (stale epoch)
    uint256 recoveryRatio = 7e17;
    uint256 recovered = (cdoEpoch.getContractValue()
        + cdoEpoch.expectedEpochInterest()
        - cdoEpoch.pendingWithdrawFees()
        + creditVault.defaultPendingClaimBasis()) * recoveryRatio / ONE_TRANCHE;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // Attacker claims stale-epoch instant receipt at PAR via _transferFundedClaim,
    // instead of instantClaim * recoveryPrice via the recovery reserve.
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    // BUG: payout == instantClaim (par) rather than haircut — or the call reverts
    // via the reserve guard, permanently freezing the claim.
}
```

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
