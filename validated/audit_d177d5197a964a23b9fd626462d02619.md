### Title
Unprotected-branch job can force `-protected` cache-volume reuse via cache-key naming, crossing protected/unprotected cache isolation - ([File: executors/docker/volume.go], [File: executors/docker/internal/volumes/manager.go])

### Summary
`createVolumesManager` in `executors/docker/volume.go` computes `ManagerConfig.Protected` as `e.Build.IsProtected() || protectedKeyIdx >= 0`, where `protectedKeyIdx` is found by scanning job-supplied cache keys for a `-protected` suffix. This means an unprivileged pipeline author, purely by naming a cache key ending in `-protected` in `.gitlab-ci.yml`, can force the entire build's cache-volume manager into "protected" mode even when `GitInfo.Protected` is false, causing the runner to compute and reuse the exact same volume name/label that a legitimate protected-ref pipeline would use for the same cache destination.

### Finding Description
`createVolumesManager` (`executors/docker/volume.go:11-42`) sets:
```go
protectedKeyIdx := slices.IndexFunc(e.Build.Cache, func(c spec.Cache) bool {
    return strings.HasSuffix(c.Key, "-protected") && !strings.HasSuffix(c.Key, "-non_protected")
})
...
Protected: e.Build.IsProtected() || protectedKeyIdx >= 0,
``` [1](#0-0) 

`Cache.Key` is a job-config field the pipeline author fully controls (no server-side validation tying it to actual branch protection). `IsProtected()` is derived only from GitLab-verified `GitInfo.Protected`/`CI_COMMIT_REF_PROTECTED` [2](#0-1) , but the OR with `protectedKeyIdx >= 0` lets an attacker on an unprotected ref flip the manager's `Protected` boolean to `true` regardless of the true git-protection status.

This single boolean is then applied uniformly to *all* cache volumes in the build via `manager.withProtected`:
```go
func (m *manager) withProtected(s string) string {
    if !m.config.Protected {
        return s
    }
    return s + protectedSuffix
}
``` [3](#0-2) 

and used to build the volume name and label in `createCacheVolume`:
```go
volumeName := m.withProtected(fmt.Sprintf("%s-cache-%s", name, hashedDestination))
...
"protected": strconv.FormatBool(m.config.Protected),
``` [4](#0-3) 

Crucially, the volume name is derived from `name` (`ProjectRealUniqueName()` for reusable volumes) and `hashedDestination` (hash of the mount destination path, e.g. `/cache`) — **not** from the cache key text itself. Since `ProjectRealUniqueName()` is project-scoped and stable across branches, and mount destinations declared in `.gitlab-ci.yml`/runner config are typically identical across branches of the same project, an unprotected-branch job that names any one cache key with a `-protected` suffix will compute the identical `-protected`-suffixed volume name that a legitimate protected-branch pipeline uses for the same destination — causing Docker to attach to (reuse) that same volume rather than creating an isolated one.

The existing "protection" (the `-non_protected` suffix exclusion) only prevents a false match against unrelated key names; it does not prevent the forward attack of an unprotected job opting itself *into* the protected volume namespace. There is no check that ties `Protected=true` usage back to a server-verified protected ref before reusing/creating the volume.

### Impact Explanation
Within the same project, an unprivileged contributor who can edit `.gitlab-ci.yml` on a feature/MR branch (unprotected ref) can name a cache key `foo-protected` to make their job's cache volume manager operate in protected mode. If the cache destination matches what protected-ref pipelines use, the attacker's job reuses the same persistent Docker volume that protected pipelines write to/read from — enabling reading (exfiltration) of protected-branch cache contents and writing (cache poisoning) that will be picked up by subsequent legitimate protected-branch runs. This directly violates the intended segregation invariant that protected-tier cache storage must be governed only by GitLab-verified branch protection.

### Likelihood Explanation
Preconditions are low-bar and fully attacker-controlled: any pipeline author with push access to an unprotected branch (including many external MR contributors depending on project settings) can set `cache.key` in `.gitlab-ci.yml`, and cache destinations are commonly fixed/shared paths (e.g. `/cache`, `node_modules`) across branches for cache-hit purposes, making a destination collision with the protected pipeline's cache highly likely in typical project configurations. This is trivially repeatable — the effect is deterministic based on the naming convention.

### Recommendation
Do not let job-supplied cache-key text elevate the volume manager's `Protected` state used for volume *naming/reuse* and cross-namespace access; if the cache-key-based opt-in is intended, use it only additively (e.g., a distinct destination/key salt) rather than mapping it onto the exact same volume name that a true protected-ref build computes. Alternatively, always incorporate the GitLab-verified `GitInfo.Protected` value directly into the resulting volume name (not the merged/OR'd boolean) so that a `-protected`-suffixed cache key can request the protected label but cannot cause name collision with a volume actually created under a verified-protected ref.

### Proof of Concept
Extend `Test_CacheVolumeProtected` in `executors/docker/docker_command_integration_test.go` to run two builds for the *same* `ProjectID`/`UniqueName` and same cache destination (`/cache`):
1. Build A: `GitInfo.Protected = true`, cache key `"real"` → creates volume `V`.
2. Build B: `GitInfo.Protected = false`, cache key `"attacker-protected"`, same destination.

Assert that Build B's computed volume name equals `V` (i.e., `client.VolumeList` returns exactly one volume shared by both builds), and that content written by Build A (via `cached/*`) is visible to Build B, proving cross-branch protected-cache access from an unprotected-ref job.

var createVolumesManager = func(e *executor) (volumes.Manager, error) {
	// Note if any of the cache keys includes the `-protected` suffix (but not the `-non_protected` suffix).
	// See https://gitlab.com/gitlab-org/gitlab/-/work_items/494478.
	protectedKeyIdx := slices.IndexFunc(e.Build.Cache, func(c spec.Cache) bool {
		return strings.HasSuffix(c.Key, "-protected") && !strings.HasSuffix(c.Key, "-non_protected")
	})

	config := volumes.ManagerConfig{
		CacheDir:      e.Config.Docker.CacheDir,
		BasePath:      e.Build.FullProjectDir(),
		UniqueName:    e.Build.ProjectRealUniqueName(),
		TemporaryName: e.getProjectUniqRandomizedName(),
		DisableCache:  e.Config.Docker.DisableCache,
		Driver:        e.Config.Docker.VolumeDriver,
		DriverOpts:    e.Config.Docker.VolumeDriverOps,
		// the volume should be protected if the ref is protected OR if any of the cache volumes have the protected
		// suffix. See https://gitlab.com/gitlab-org/gitlab/-/work_items/494478.
		Protected: e.Build.IsProtected() || protectedKeyIdx >= 0,
	}

```go
// IsProtected states if the git ref this build is for is protected.
// GitLab 18.3+ provides the `protected` property in GitInfo to check if a branch is protected.
// For older GitLab versions, we fall back to the CI_COMMIT_REF_PROTECTED predefined variable.
func (b *Build) IsProtected() bool {
	if p := b.GitInfo.Protected; p != nil {
		return *p
	}

	// we dedup the vars here, keeping the original, so that we don't consider an override by the user.
	return b.GetAllVariables().Dedup(true).Bool("CI_COMMIT_REF_PROTECTED")
}
```
