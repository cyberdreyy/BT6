### Title
Miner-controlled `last_activity` refresh via non-progressing competing proposals suppresses `SortitionState::is_timed_out`, wedging fallback to prior miner - (File: stacks-signer/src/chainstate/v1.rs, stacks-signer/src/chainstate/mod.rs)

### Summary
`SortitionState::is_timed_out` (v1.rs) only declares a tenure inactive if `elapsed` since `last_activity` (or burn-block receipt) exceeds `block_proposal_timeout`, and `last_activity` is refreshed by `update_last_activity_time` inside `check_latest_block_in_tenure` (chainstate/mod.rs) whenever a *fresh pre-committed* block in the tenure is contested by another proposal at the same or lower height. A winning miner who never lets any proposal reach the 70% pre-commit/signature threshold can keep manufacturing new, distinct, "conflicting" but individually valid proposals inside the `tenure_last_block_proposal_timeout` window, which resets `last_activity` at every honest signer independently and indefinitely defeats `elapsed > block_proposal_timeout`.

### Finding Description
`is_timed_out` (stacks-signer/src/chainstate/v1.rs:55-94) computes:
```
let last_activity = db.get_last_activity_time(sortition)?.unwrap_or(received_time);
elapsed = now - last_activity
timed_out = elapsed > block_proposal_timeout
``` [1](#0-0) 

`get_last_activity_time` is only ever refreshed by `update_last_activity_time`, and the sole caller of that write is `check_latest_block_in_tenure` (stacks-signer/src/chainstate/mod.rs), specifically the branch that treats a proposal conflicting with a still-fresh `PreCommitted` block (`approved_time + tenure_last_block_proposal_timeout > now`) as "miner activity" even though it is never rejected or accepted definitively: [2](#0-1) 

Critically, `PreCommitted` state (set via `mark_pre_committed`) carries **no signature** — it is a purely local, single-signer verdict produced as soon as that signer's own node-validation of a block succeeds (see `handle_block_validate_ok` in signer.rs, which calls `mark_pre_committed` on `Ok` validation and independently on every signer node): [3](#0-2) 

This means a single miner, holding only their own winning slot, can:
1. Propose block `B1` for `cur_sortition`. Each honest signer independently validates it and marks it locally `PreCommitted` (no cooperation from any other signer required, no threshold reached).
2. Before `B1`'s pre-commit goes stale (within `tenure_last_block_proposal_timeout`), broadcast a distinct competing proposal `B1'` at the same/lower `chain_length` (e.g., only the timestamp differs, so `signer_signature_hash` differs and it is treated as a *new* proposal rather than a resend of `B1`).
3. Each signer's fresh evaluation of `B1'` hits the "fresh pre-commit conflict" branch in `check_latest_block_in_tenure`, which calls `signer_db.update_last_activity_time(consensus_hash, now)` — regardless of whether `B1'` is ultimately accepted by the node-tip check.
4. Repeat indefinitely with a new distinct competing proposal at least once per `tenure_last_block_proposal_timeout`, at negligible cost (crafting valid-but-non-progressing Nakamoto blocks is free for the tenure's legitimate miner).

Because `has_signed_block_in_tenure` is false throughout (no proposal ever reaches the pre-commit/signature threshold — the attacker only needs *their own* local pre-commit records to look fresh, not group consensus), and `last_activity` is continuously refreshed at every signer, `elapsed > block_proposal_timeout` never evaluates true. `SortitionMinerStatus` never becomes `InvalidatedBeforeFirstBlock`, so `check_miner_inactivity` (v0/signer_state.rs) never triggers fallback to `last_sortition`: [4](#0-3) 

Existing guards do not close this: the pre-commit-conflict branch is explicitly documented and coded to treat any contested-but-fresh pre-commit as valid activity ("this should still count as activity for the miner" / "Treat any attempt to reorg a locally accepted block as valid miner activity"), and this is validated by the repo's own test `pre_committed_block_does_not_veto_replacement`, which asserts `get_last_activity_time` becomes `Some` purely from a same-height competing proposal against a fresh pre-commit, with no signatures or thresholds involved: [5](#0-4) 

### Impact Explanation
This breaks the bounded-liveness guarantee that a signer will eventually fall back to the prior miner if the current miner goes silent/misbehaves without producing a signed block. A malicious winning miner can indefinitely prevent `is_timed_out` from firing across the entire signer set (each signer independently refreshes its own `last_activity` from the same broadcast proposals), which stalls tenure progression forever: no valid block from the current miner is ever produced (attacker's goal), and no fallback to the prior miner's tenure is possible either, since `miner_status` never flips to `InvalidatedBeforeFirstBlock`. This matches the "signer wedged into never signing valid blocks (liveness)" High-severity category. It requires only the attacker's own miner slot plus normal proposal gossip — no other signer's cooperation, key, or the auth token — and is repeatable for as long as the attacker keeps sending proposals.

### Likelihood Explanation
Preconditions: attacker must win a sortition slot (single BTC-funded commit) and be able to broadcast distinct, individually-valid (node-validation-passing) `BlockProposal`s at will — both are within the described unprivileged attacker's normal capability. No majority-signer collusion, no local host access, and no auth token are needed since `PreCommitted` marking and `last_activity` refresh are single-signer-local decisions triggered purely by the content of gossiped proposals. The attack is mechanically simple (vary timestamp/nonce fields to produce a new `signer_signature_hash` at the same/lower chain length, repeat before `tenure_last_block_proposal_timeout` expires) and fully repeatable for the whole tenure. The main uncertainty is whether `check_latest_block_in_tenure` (and thus this refresh) is invoked strictly during `SortitionsView::check_proposal`'s first-pass evaluation or only later at `handle_block_validate_ok`/pre-commit re-check time (`check_block_against_signer_db_state` in signer.rs) — I could not fully confirm the exact call site inside `check_proposal` itself in v1.rs, but the refresh is reachable during ordinary per-proposal processing regardless of which specific function boundary triggers it, so the underlying liveness gap stands.

### Recommendation
Do not treat a contested-but-unsigned pre-commit conflict as unconditional "miner activity" for timeout purposes. Options: (a) cap the number of times a single tenure's `last_activity` can be refreshed by pre-commit-conflict events without any block reaching the pre-commit/signature threshold, (b) require that a refresh only count if it originates from a genuinely new proposal that also makes verifiable progress (e.g., a higher-or-equal weight of *distinct signers'* pre-commits than the previous round, not just node-validation success), or (c) bound `is_timed_out` by both "time since last activity" AND "time since the tenure's *first* proposal was seen," so a miner cannot extend the window indefinitely purely by resubmitting variants.

### Proof of Concept
```rust
// stacks-signer/src/chainstate/tests/v1.rs (new test)
#[test]
fn miner_can_suppress_timeout_via_repeated_precommit_conflicts() {
    // setup: signer_db, cur_sortition consensus_hash CH, block_proposal_timeout = 5s,
    // tenure_last_block_proposal_timeout = 3s (as in existing setup_test_environment helpers)

    // 1. Insert burn block for CH (start the timeout clock).
    signer_db.insert_burn_block(&burn_hash, &CH, height, &SystemTime::now(), &parent_hash).unwrap();

    // 2. Propose B1, mark PreCommitted (simulating handle_block_validate_ok's mark_pre_committed).
    let mut b1_info = BlockInfo::from(make_proposal(&CH, chain_length = 10, nonce = 0));
    b1_info.mark_pre_committed().unwrap();
    signer_db.insert_block(&b1_info).unwrap();

    // 3. Loop: every < tenure_last_block_proposal_timeout, submit a distinct competing
    //    proposal at the same chain_length and assert is_timed_out stays false even
    //    as real time passes well beyond block_proposal_timeout.
    for i in 1..10 {
        std::thread::sleep(Duration::from_secs(2)); // < tenure_last_block_proposal_timeout, cumulative > block_proposal_timeout
        let competing = make_proposal(&CH, chain_length = 10, nonce = i);
        SortitionData::check_latest_block_in_tenure(
            &CH, &competing, &mut signer_db, &stacks_client,
            Duration::from_secs(30), // tenure_last_block_proposal_timeout
            Duration::from_secs(3),  // reorg_attempts_activity_timeout
        ).unwrap();

        assert!(!SortitionState::is_timed_out(&CH, &signer_db, Duration::from_secs(5)).unwrap(),
            "iteration {i}: signer must NOT be timed out despite {} elapsed seconds since burn block",
            2 * i);
    }
    // Assert: after > block_proposal_timeout elapsed wall-clock time with zero signed
    // blocks in the tenure, is_timed_out is still false -> fallback to last_sortition
    // never triggers, contradicting the intended liveness bound.
}
