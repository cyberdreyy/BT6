### Title
Post-default instant withdraw requests bypass recovery accounting and can drain funded claim reserves - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.requestInstantWithdraw` has no `defaultRecoveryFinalized` branch, unlike `requestWithdraw` which routes post-default requests into the reserve-backed `postDefaultRequests` flow. Once default recovery is finalized, any subsequent instant-withdraw receipt is minted, recorded only in the generic `instantWithdrawsRequests`/`pendingInstantWithdraws` buckets, and `claimInstantWithdrawRequest` pays it **at par** through `_transferFundedClaim`, which only protects `defaultRecoveryReserve`. Funds sitting in the strategy that were collected for other funded/loss-adjusted claimants are not isolated, so a post-default instant receipt can spend them.

### Finding Description
In `requestWithdraw`, once `defaultRecoveryFinalized` is true the strategy burns the CDO's tokens, mints the receipt to the user, and records it in `postDefaultRequests[_user]` so it can only be paid 1:1 out of `defaultRecoveryReserve` via `_transferDefaultRecovery` [1](#0-0) . `requestInstantWithdraw` performs no equivalent check — it unconditionally burns/mints and increments `instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch` and `pendingInstantWithdraws` [2](#0-1) .

On the claim side, `claimInstantWithdrawRequest` clears only the **default-epoch** receipt (`_claimDefaultedInstantWithdrawRequest`) and then pays the entire remaining `instantWithdrawsRequests[_user]` at par with `_transferFundedClaim` [3](#0-2) . `_transferFundedClaim` guarantees only that `balance - defaultRecoveryReserve >= amount`; any other underlying held by the strategy — e.g., funds collected via `collectWithdrawFunds`/`collectInstantWithdrawFunds` for loss-adjusted (`lossRecoveryPriceByEpoch`) or still-pending funded receipts — is fair game [4](#0-3) .

Analog mapping: the CVE is an unspecified request-handling flaw in a protocol state machine (HTTP/2 experimental feature). The analog is an unhandled protocol-state transition — an instant-withdraw request created in the "finalized default" state is processed by the pre-default code path, escaping the haircut/reserve accounting that governs every other post-default receipt.

Broken invariant: loss socialization / donation isolation — post-default claims must be paid exclusively from `defaultRecoveryReserve`.

### Impact Explanation
After `finalizeDefault`/`finalizeDefaultRecovery`, the strategy may still hold underlying collected for funded or loss-adjusted receipts (those tracked by `lossRecoveryPriceByEpoch` are paid via `_transferFundedClaim`, not the reserve). An attacker who can place an instant-withdraw request post-default receives minted receipt tokens and immediately claims the full amount at par, spending underlying earmarked for those claimants. Loss is bounded by the strategy's non-reserve underlying balance and is a direct theft from other users' pending claims; victims' receipts become unbacked (permanent freezing of their payouts).

### Likelihood Explanation
Requirements: the pool must be in the finalized-default state (`defaultRecoveryFinalized`, `defaultInstantWithdrawsFinalized`), the strategy must hold non-reserve underlying (normal whenever loss-adjusted or funded claims are still unclaimed), and the CDO path that calls `requestInstantWithdraw` must be reachable post-default — the CDO's instant-withdraw feature flags/epoch gating may restrict this, which is the main uncertainty (the corresponding `IdleCDOEpochVariant` gating was not fully verified). If reachable, no privileged role is needed: any tranche holder triggers it via `IdleCDOEpochVariant.requestWithdraw` in instant mode, and `requestInstantWithdraw` itself performs no state check. Notably, `requestInstantWithdraw` also lacks the `NotAllowed` guard that `requestWithdraw` applies when a user already holds unclaimed receipts post-default.

### Recommendation
Mirror the `requestWithdraw` post-default logic in `requestInstantWithdraw`: when `defaultRecoveryFinalized` is set, either revert or route the request into a reserve-backed bucket (e.g., extend `postDefaultRequests` semantics to instant receipts) so it can only be paid from `defaultRecoveryReserve`. Additionally, in `claimInstantWithdrawRequest`, exclude post-default instant receipts from the at-par `_transferFundedClaim` payment, and decrement `pendingInstantWithdraws` consistently so unfunded post-default receipts are never treated as funded.

### Proof of Concept
Conceptual Foundry fork sequence (reproducibility requires the CDO's instant-withdraw path to be callable post-default):

```solidity
// Setup: standard epoch variant, lender U deposits AA, epoch running.
// 1. Borrower defaults: manager calls stopEpochWithDuration / default flow,
//    then finalizeDefaultRecovery -> defaultRecoveryFinalized = true,
//    defaultRecoveryReserve is funded; loss-adjusted receipts exist for user V
//    (lossRecoveryPriceByEpoch[e] != 0, funded underlying sits in the vault).
// 2. Attacker A (KYC'd holder) requests an instant withdraw via the CDO:
vm.prank(A);
cdoEpoch.requestInstantWithdraw(amount); // routes to strategy.requestInstantWithdraw
// -> no defaultRecoveryFinalized check: receipt minted, pendingInstantWithdraws += amount
// 3. Attacker claims immediately:
vm.prank(A);
cdoEpoch.claimInstantWithdrawRequest(); // strategy.claimInstantWithdrawRequest(A)
// _claimDefaultedInstantWithdrawRequest clears only defaultEpoch basis (A has none),
// then _transferFundedClaim pays `amount` at par since balance - reserve >= amount.
// 4. Victim V later calls claimWithdrawRequest -> _claimLossAdjustedWithdrawRequest
// -> _transferFundedClaim reverts NotAllowed (balance - reserve < amount):
// V's funded loss-adjusted payout is permanently unbacked.
```

Key assertions: `strategy.balanceOf(A)` receipt minted post-default; `underlying.balanceOf(A)` increases by the full request amount; victim's claim reverts. If step 2 reverts inside `IdleCDOEpochVariant` due to epoch/default gating, the same gap remains latent for any future path (queue or CDO variant) that can invoke `requestInstantWithdraw` post-finalization.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
