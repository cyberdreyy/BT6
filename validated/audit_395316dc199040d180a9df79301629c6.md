### Title
v1 chainstate's `validate_tenure_change_payload` uses `get_last_globally_accepted_block` instead of `get_last_signed_block`, allowing a same-tenure duplicate tenure-start proposal to bypass the proposal-time `DuplicateBlockFound` guard - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
`stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` checks for an already-signed sibling tenure-start block in the *same* tenure by calling `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` [1](#0-0) , which only matches blocks in `GloballyAccepted` state. The v2 equivalent was patched to call `get_last_signed_block`, which also matches `LocallyAccepted` blocks [2](#0-1) . This exact class of bug is documented as fixed for v2 with an explicit regression test and CHANGELOG entry ("When checking tenure change blocks, ensure there are no locally accepted blocks in the tenure, not just globally accepted blocks") [3](#0-2) [4](#0-3) , but v1 still contains the unfixed pattern.

### Finding Description
This is the same bug class as the Froxlor advisory: a security-relevant check (equivalence/ownership validation there; here, the "have I already signed a sibling in this tenure" duplicate check) was fixed on one code path but an equivalent path was missed, silently reintroducing the same equality-bypass.

Concretely: a signer that has *locally* signed tenure-start block A (i.e. `signed_self` is set via `mark_locally_accepted`, but the block has not yet reached the group threshold to become `GloballyAccepted`) is asked by the miner to evaluate a second, conflicting tenure-start block B in the same tenure. `check_proposal` (v1) routes tenure-change blocks into `validate_tenure_change_payload`, whose only same-tenure duplicate guard queries `get_last_globally_accepted_block` [5](#0-4) . Because A is only `LocallyAccepted`, this query returns `None`, so `check_proposal` for B does **not** reject with `DuplicateBlockFound`, and B is forwarded to the stacks-node for validation.

The documentation for the shared re-check machinery explicitly states that the `DuplicateBlockFound` check "lives in `check_proposal` and runs only at proposal arrival, never again," and that the *only* remaining backstop against this exact miss is the pre-commit-time "own-tenure conflict guard" in `handle_block_pre_commit` (section 5 of `docs/signer-flows.md`), which is fed by `get_signed_conflicts`, which itself considers `signed_self`/`signed_group` (i.e. it *does* count locally-accepted blocks) [6](#0-5) . So in the common (online, connected) case, the later `handle_block_pre_commit` re-check should still catch the conflict for a *fresh* signature on A and refuse to sign B. But this depends entirely on that later re-check firing correctly and being reachable — it is a documented "blind spot [that] make[s] the guard necessary" rather than the primary defense, and it was only added to patch a similar historical gap (v1.rs was never updated for the same fix that widened v2's check). The v1 proposal-time defense-in-depth layer that the v2 codebase explicitly fixed is silently absent in v1, meaning v1-configured signers rely solely on the later stage to prevent equivocation on a duplicate/sibling tenure-start block, and any additional gap in that later stage (e.g., timing/staleness, the freshness window in `handle_block_pre_commit`, or an unreachable node during the `conflict_still_blocks` questions) removes that last line of defense entirely for v1.

### Impact Explanation
If the pre-commit-stage backstop does not intervene (e.g., signature A becomes stale per `tenure_last_block_proposal_timeout`, or the "own tenure confirmed at ≥ height" node check returns false/unreachable, both explicitly listed as paths that let the signer sign a replacement, per `docs/signer-flows.md` section 5), a v1 signer could produce a *second* signature over a conflicting sibling tenure-start block B while a signature already exists over A in the very same tenure. This is a direct equivocation: the signer signs two conflicting/non-canonical blocks at the same height in the same tenure, which is exactly the "signer signing an invalid/non-canonical/conflicting block" class called out as Critical impact.

### Likelihood Explanation
Reaching this state requires only a one-slot miner (or gossip of the required message) proposing a conflicting sibling tenure-start block after the first one was locally (but not yet globally) accepted — no majority of signers or any other signer's key is needed to *create the scenario*; the safety of the outcome then depends on the freshness/backstop logic in `handle_block_pre_commit`, which is time- and node-connectivity-dependent. Because v2 was already patched for the identical root cause (and has a regression test proving the pre-patch behavior was exploitable), the persistence of the same pattern in v1 is a credible, concrete regression for any deployment still running the v1 chainstate path.

### Recommendation
Update `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` to call `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, mirroring the v2 fix, so that a locally-accepted (signed but not yet globally accepted) block in the same tenure is also detected and rejected with `DuplicateBlockFound` at proposal time, rather than relying solely on the later pre-commit-time backstop.

### Proof of Concept
1. Signer running v1 chainstate signs tenure-start block A for tenure T via `mark_locally_accepted` (state = `LocallyAccepted`, `signed_self` set), but A never reaches the group signature threshold (`signed_group` stays `None`).
2. Miner proposes a second, conflicting tenure-start block B for the same tenure T.
3. `SortitionsView::check_proposal` → `validate_tenure_change_payload` calls `get_last_globally_accepted_block(&T)`, which returns `None` because A is only `LocallyAccepted` [1](#0-0) ; no `DuplicateBlockFound` rejection is issued.
4. B is submitted to the stacks-node for validation and, if the node has no conflicting record either, returns Ok.
5. B now depends solely on `handle_block_pre_commit`'s conflict guard (`get_signed_conflicts` + freshness + `conflict_still_blocks`) to be refused; if A's signature has gone stale (per `tenure_last_block_proposal_timeout`) or the node cannot confirm the tenure's tip at the time of the check, the signer signs B, producing two signed, conflicting blocks in the same tenure — a direct equivocation. (The v2 regression test `check_tenure_change_rejects_when_locally_accepted_block_exists` demonstrates the exact pre-fix behavior that is analogous to what v1 still exhibits.) [7](#0-6)
