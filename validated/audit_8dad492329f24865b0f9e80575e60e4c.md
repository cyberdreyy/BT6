### Title
External Initiator can bypass "EIs not allowed" check and trigger arbitrary numeric job runs - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` intends to block External Initiators (EIs) from running jobs by numeric ID via `_, isUser := auth.GetAuthenticatedUser(c)`, but `AuthenticateExternalInitiator` also populates the same context key with a synthetic `run`-role `User`, so `GetAuthenticatedUser` returns `ok=true` for EI-authenticated requests as well. This lets any valid EI credential holder call `RunJobV2` on an arbitrary numeric job ID unrelated to its bound webhook job.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is authenticated via the chain `auth.Authenticate(..., AuthenticateBySession, AuthenticateByToken, AuthenticateExternalInitiator)`, since EIs are expected to trigger UUID-based webhook job runs on this same endpoint. When authentication succeeds via `AuthenticateExternalInitiator` in `core/web/auth/auth.go`: [1](#0-0) 

it sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` — the exact same context key (`SessionUserKey`) that real session/token authentication uses to store the actual authenticated `User`.

`GetAuthenticatedUser` has no way to distinguish a real user session from this synthetic EI-injected user; it simply performs a type assertion on the stored value: [2](#0-1) 

In `PipelineRunsController.Create`, the code explicitly relies on this to gate the numeric-jobID path, per its own comment "only users are allowed to run jobs using int IDs - EIs not allowed": [3](#0-2) 

Because `isUser` will be `true` for an EI-authenticated request, an EI can supply any numeric job ID in the URL path and the handler calls `prc.App.RunJobV2(ctx, jobID, nil)` with no check that the job ID corresponds to a job the EI is bound to. The intended restriction (EIs can only trigger their own bound webhook job by UUID) is bypassed entirely for numeric IDs.

### Impact Explanation
An EI credential — a relatively low-privilege, narrowly-scoped credential meant to trigger exactly one bound webhook job — can be used to trigger arbitrary jobs on the node by numeric ID, including jobs unrelated to the EI and potentially higher-impact jobs (e.g., jobs that move funds, write on-chain transactions, or trigger flux monitor/OCR-adjacent pipelines). This is an authorization bypass / unauthorized job run, matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Exploitation requires only valid EI credentials (`X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers per `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`), which is the lowest-privilege external-initiator credential class explicitly in scope as an "unprivileged" attacker per the audit rules. No session or user API token is needed. The request is a single `POST /v2/jobs/<numericJobID>/runs` with EI headers; it is fully repeatable against any numeric job ID present on the node.

### Recommendation
Do not overload `SessionUserKey` for EI authentication. Instead:
- Use `auth.GetAuthenticatedExternalInitiator(c)` in `Create` to explicitly detect EI-authenticated requests and reject the numeric-ID path if an EI is present, e.g. check `if _, isEI := auth.GetAuthenticatedExternalInitiator(c); isEI { reject }` before/independently of the `isUser` check.
- Alternatively, store EI-derived pseudo-users under a distinct context key (not `SessionUserKey`) so `GetAuthenticatedUser` never returns `ok=true` for EI requests, restoring the intended semantic distinction between "authenticated user" and "authenticated external initiator."

### Proof of Concept
Go handler-level test plan (extending `core/web/pipeline_runs_controller_test.go`):
1. Set up an app with two jobs: JobA bound to EI "ei1" (webhook, existing legit UUID trigger) and JobB (unrelated numeric job, e.g. owned by another user/spec).
2. Create/register an external initiator "ei1" and obtain its `AccessKey`/`Secret`.
3. Send `POST /v2/jobs/<JobB.ID>/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to ei1's credentials (no session cookie, no `X-API-KEY`).
4. Assert current (vulnerable) behavior: response is `200`/`201` and `RunJobV2` was invoked for `JobB.ID`, proving `isUser` was `true` for an EI-only request.
5. Assert expected (fixed) behavior after remediation: response is `422`/`401` with an authorization error, and `RunJobV2` is never called for `JobB.ID` when only EI credentials are present.
6. Unit-test `auth.GetAuthenticatedUser` and `auth.GetAuthenticatedExternalInitiator` together after calling `AuthenticateExternalInitiator` on a fake `gin.Context`, asserting that a fixed implementation causes `GetAuthenticatedUser` to return `ok=false` (or a dedicated EI-detection helper returns `true`) for EI-only authenticated contexts.
