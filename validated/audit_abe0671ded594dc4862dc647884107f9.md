### Title
APR0 withdraw receipts permanently brick `stopEpoch` once the pool APR is raised - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` creates an APR0 receipt that registers the user's principal in the global `apr0TotalPrincipal` bucket, keyed to the *mode at request time* (`unscaledApr == 0`). Like the L2CAP bug — a pointer obtained under one state and used later after that state was invalidated — the bucket is dereferenced at `stopEpoch` under a different precondition: `prepareStopEpochWithApr0` hard-reverts whenever `apr0TotalPrincipal != 0 && unscaledApr != 0`, and `apr0TotalPrincipal` is only ever reset inside that same reverting function (or on a defaulted-epoch claim path that can never be reached). An unprivileged lender can therefore wedge the epoch state machine: once the manager sets a non-zero APR — a routine, honest operation — every `stopEpoch`/`stopEpochWithDuration` reverts forever, permanently freezing all pool funds.

### Finding Description
- `requestWithdraw` routes to `_requestWithdrawApr0` when `unscaledApr == 0`, which does `apr0Users[_user].principalEpoch = epochNumber; apr0TotalPrincipal += _amount` [1](#0-0) .
- The only normal-path reset of `apr0TotalPrincipal` is `apr0TotalPrincipal = 0` at the end of `prepareStopEpochWithApr0` — but that function first reverts if `unscaledApr != 0` while `_principal != 0` [2](#0-1) .
- `_settleApr0` moves `principal → settledPrincipal` but never decrements `apr0TotalPrincipal`, so a successful claim does not clear the bucket either [3](#0-2) .
- The other decrement lives in `_clearWithdrawClaimForEpoch` with `_isClearingApr0`, reachable only via `_claimDefaultedWithdrawRequest` after `defaultRecoveryFinalized` — which requires `stopEpoch` to succeed with a borrower default first [4](#0-3) .
- `prepareStopEpochWithApr0` runs at the top of `_stopEpoch` before any default handling, so its revert blocks even the default path [5](#0-4) .

The stale-reference analogy: the APR0 bucket is "allocated" against the invariant `unscaledApr == 0`, but nothing pins that invariant — `setAprsWithBuffer` (called by every `stopEpochWithDuration`/`setEpochParams`) can change it freely, leaving `apr0TotalPrincipal` referencing a lifecycle that no longer exists. There is no escape hatch: owner/manager cannot clear `apr0TotalPrincipal`, and `requestWithdraw` cannot be used to drain it (new requests in APR≠0 mode go to the normal path; in a later APR0 epoch they only add more principal).

### Impact Explanation
Permanent freezing of all vault funds. After the wedge: `stopEpoch`/`stopEpochWithDuration` always revert → epochs cannot advance → pending withdraw receipts can never be claimed (`claimWithdrawRequest` requires `epochNumber > lastWithdrawRequest`) → `startEpoch`/`deposit` flows that depend on epoch progression are bricked, and borrower default/recovery (`_handleBorrowerDefault`, `finalizeDefaultRecovery`) is unreachable because it is downstream of the reverting call. Loss = 100% of pool TVL plus all pending withdraw receipts, locked indefinitely.

### Likelihood Explanation
- Attacker cost is minimal: be a KYC-passed lender, deposit, and call `cdoEpoch.requestWithdraw` during any epoch where `unscaledApr == 0` (APR0 mode is a first-class supported configuration — see `_requestWithdrawApr0` and the apr0 test suite).
- The trigger condition is an ordinary honest action: the manager raises the APR at the next `stopEpochWithDuration(_newApr ≠ 0, ...)`, which is exactly what the function exists for. Nothing warns the manager that an open APR0 receipt makes this fatal.
- Even without malice, any user requesting withdraw in an APR0 epoch followed by an APR increase permanently bricks the pool.

### Recommendation
In `prepareStopEpochWithApr0`, do not revert on `unscaledApr != 0`; instead settle/close the outstanding APR0 bucket gracefully (e.g., treat `apr0TotalPrincipal` principal as already-priced pending basis — it was already added to `pendingWithdraws` at request time — and zero the bucket, skipping only the interest split). Alternatively, decrement `apr0TotalPrincipal` inside `_settleApr0`/`_requestWithdrawApr0` so the global bucket reflects only unsettled current-mode principal, and clear it whenever the APR is changed away from zero via `setAprsWithBuffer`.

### Proof of Concept
Foundry fork test outline (against `IdleCreditVault` + `IdleCDOEpochVariant`):

```solidity
function testApr0ReceiptBricksStopEpochAfterAprChange() external {
    // Pool running with unscaledApr == 0 (APR0 mode)
    // 1. LP deposits and starts epoch 0
    idleCDO.depositAA(100_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);

    // 2. Epoch ends, APR set to 0 for next epoch; buffer period of epoch 1
    _stopEpochAndCheckPrices(0, 0 /* apr0 */, _expectedFundsEndEpoch());
    assertEq(strategy.unscaledApr(), 0);

    // 3. Attacker (any allowed lender) requests withdraw in APR0 epoch
    uint256 tranches = AAtranche.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(tranches / 2, address(AAtranche));
    assertGt(strategy.apr0TotalPrincipal(), 0); // bucket opened

    // 4. Manager honestly raises APR for the following epoch
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _repayBorrower(); // borrower funds stop normally
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18 /* _newApr */, 0, DURATION, 0);
    // stop succeeds, prepareStopEpochWithApr0 settles bucket (unscaledApr still 0), sets apr=10%

    // 5. New APR0-free epoch runs; attacker requests again? Not needed:
    //    bucket was closed only if the stop above ran with unscaledApr==0.
    //    Instead: request in epoch 1 while apr==0, THEN manager sets apr>0 mid-lifecycle:
    //    (variant) request during buffer when unscaledApr==0, manager calls
    //    stopEpochWithDuration(newApr!=0) -> next epoch apr != 0 while
    //    apr0TotalPrincipal may still be non-zero if stop ran before settlement.
    //
    // Minimal wedge: apr0TotalPrincipal != 0 AND unscaledApr != 0 simultaneously:
    //   - requestWithdraw in apr0 epoch -> apr0TotalPrincipal = X
    //   - manager changes apr via stopEpochWithDuration ONLY clears the bucket
    //     because that stop itself ran while unscaledApr==0.
    //   - To leave residue: have TWO users request in the apr0 epoch; one claims
    //     (settle moves principal->settledPrincipal but apr0TotalPrincipal stays X
    //     until a stop clears it), OR rely on the fact that after the bucket
    //     clears at stop, a request made in the NEXT epoch (apr!=0) goes normal —
    //     BUT a request made while unscaledApr==0 that is never followed by an
    //     apr0-mode stop leaves apr0TotalPrincipal stranded once apr!=0.
    //
    // Stranded path that always works:
    //   epoch N (apr==0): request -> apr0TotalPrincipal = X
    //   stopEpochWithDuration runs prepareStopEpochWithApr0 BEFORE _setScaledApr,
    //   so it clears; then _setScaledApr sets apr>0.
    //   epoch N+1 buffer (apr>0): user CANNOT open apr0 receipt (goes normal).
    //   => stranded bucket requires apr change WITHOUT a stop: setApr() by manager
    //      (manager is honest, allowed to call setApr directly per L225-235).
    vm.prank(manager);
    strategy.setApr(10e18); // honest manager action, no bucket cleanup

    // 6. Every subsequent stopEpoch reverts -> permanent freeze
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // claims can never mature; funds frozen
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimWithdrawRequest();
}
```

Key mechanical point: `setApr` is a manager-callable function with no APR0 bucket check [6](#0-5) , so `apr0TotalPrincipal != 0 && unscaledApr != 0` is reachable through honest operations after an unprivileged lender's `requestWithdraw`, and from that point `stopEpoch` reverts unconditionally.

  function _settleApr0(address _user) internal {
    Apr0UserData storage _apr0User = apr0Users[_user];
    uint256 _principal = _apr0User.principal;
    if (_principal == 0) {
      return;
    }
    uint256 _reqEpoch = _apr0User.principalEpoch;
    // Settle only after stopEpoch bumped epochNumber (ie after one full wait epoch).
    if (_reqEpoch >= epochNumber) {
      return;
    }
    // Move principal from "open APR0 bucket" to "settled bucket" (same principal, not duplicated).
    _apr0User.settledPrincipal += _principal;
    uint256 _rate = apr0RateByEpoch[_reqEpoch];
    if (_rate != 0) {
      // Convert per-epoch rate to claimable underlying interest.
      _apr0User.settledInterest += (_principal * _rate) / 1e18;
    }
    _apr0User.principal = 0;
    _apr0User.principalEpoch = 0;
  }

  function _requestWithdrawApr0(uint256 _amount, address _user) internal {
    // Settle any previous APR0 request first, then start/update current epoch bucket.
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    if (_apr0User.principal == 0) {
      _apr0User.principalEpoch = epochNumber;
    }
    _apr0User.principal += _amount;
    // Epoch-level APR0 principal used only to compute stopEpoch APR0 pro-rata interest.
    apr0TotalPrincipal += _amount;
  }
