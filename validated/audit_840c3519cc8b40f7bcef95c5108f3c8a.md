### Title
Fee-on-transfer underlying causes over-minted tranche shares and underfunded borrower debt in mid-epoch deposits - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`depositDuringEpoch` pulls `_amount` of underlying via `_transferUnderlyingsFrom` but then computes minted tranche shares, prorated interest, and borrower-side strategy tokens entirely from the *nominal* `_amount`, not the balance actually received. With a fee-on-transfer underlying (e.g., USDT with a nonzero `basisPointsRate`, which is a realistic credit-vault asset), the vault credits `_amount` while receiving `_amount - fee`. Unlike `IdleCDO._deposit`/`IdleCDOCreditVault._deposit`, which mint shares using the measured balance delta (`_contractTokenBalance(_token) - _preBal`), the mid-epoch path never measures the received amount. The depositor is over-minted shares and the borrower is debited principal it never received, breaking solvency.

### Finding Description
In `IdleCDOEpochVariant.depositDuringEpoch`:

```solidity
// contracts/IdleCDOEpochVariant.sol:685
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
...
uint256 interest = _calcInterest(_amount) * (remaining + buffer) / (epochDuration + buffer);
...
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
_mintShares(_tranche, msg.sender, _minted, _amount);
expectedEpochInterest += interest;
IdleCreditVault(strategy).mintStrategyTokens(_amount); // line 730
```

Every downstream value — `_minted`, `interest`/`expectedEpochInterest`, and `mintStrategyTokens(_amount)` — uses nominal `_amount`. With a 1% transfer fee, a deposit of 100_000 delivers only 99_000 to the vault, yet the borrower debt grows by 100_000 and the depositor receives shares priced for 100_000 + prorated interest. Note `mintStrategyTokens` is bookkeeping (minted interest mode), so unlike the buffer-phase path where `IIdleCDOStrategy(strategy).deposit(_amount)` would pull the nominal amount and simply revert on insufficient balance, this call succeeds and silently records the shortfall.

At `stopEpoch`/`stopEpochWithDuration`, the vault expects `expectedEpochInterest` plus principal from the borrower, but 1% of every mid-epoch deposit was never transferred. When the borrower repays the recorded debt, the vault is short by the cumulative fees; the shortfall is socialized to the last withdrawers via `claimWithdrawRequest`/`collectWithdrawFunds`, or a borrower that repays only actual funds received causes an unwarranted default-state NAV shortfall hitting BB first.

### Impact Explanation
Two distinct harms, both reachable by an unprivileged KYC-passed lender on any vault deployed over a fee-on-transfer underlying with `isDepositDuringEpochDisabled == false`:

1. Over-minting: the attacker mints shares worth `_amount + trancheInterest` while contributing only `_amount - fee`, directly diluting existing AA/BB holders' NAV (theft of ~fee% per mid-epoch deposit, repeatable).
2. Insolvency: `mintStrategyTokens(_amount)` records borrower principal never received; repayment accounting (`totalInterestDueNow`/expected NAV) exceeds real balance, so final withdrawers are permanently underpaid by the cumulative fee amount — a quantified NAV shortfall rather than a mere revert.

### Likelihood Explanation
Medium. Requires (a) a vault whose underlying charges a transfer fee — USDT supports exactly this via `setParams` on mainnet and is a standard credit-vault asset — and (b) `depositDuringEpoch` enabled (guarded by `isDepositDuringEpochDisabled`, `isAYSActive`, `isProgrammableBorrower`, epoch running, and `isWalletAllowed`). All are honest-owner configurations consistent with the protocol supporting arbitrary ERC20 underlyings. No privileged misbehavior is needed; the attacker is a normal allowed depositor.

### Recommendation
Measure the received amount and use it everywhere:

```solidity
uint256 _preBal = _contractTokenBalance(token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
uint256 _received = _contractTokenBalance(token) - _preBal;
```

Then compute `interest`, `trancheInterest`, `_minted`, and `mintStrategyTokens` from `_received`. Alternatively, document that fee-on-transfer underlyings are unsupported and enforce it at factory/deployment time.

### Proof of Concept
Foundry fork sketch (mainnet, USDT as underlying):

```solidity
function testFotMidEpochDepositOvermint() public {
  // vault deployed with USDT underlying; AA deposit in buffer; epoch started
  vm.prank(owner); cdoEpoch.setIsDepositDuringEpochDisabled(false);
  // enable USDT fee: prank Tether owner, setParams(100, 100) => 1% fee
  vm.prank(TETHER_OWNER);
  TetherToken(USDT).setParams(100, 100);

  vm.warp(cdoEpoch.epochEndDate() - cdoEpoch.epochDuration() / 2);

  address lender = makeAddr("kycLender");
  _allowWallet(lender);
  deal(USDT, lender, 100_000e6);
  vm.startPrank(lender);
  IERC20(USDT).approve(address(cdoEpoch), 100_000e6);
  uint256 minted = cdoEpoch.depositDuringEpoch(100_000e6, address(AAtranche));
  vm.stopPrank();

  // vault received only 99_000e6 but minted shares & borrower debt assume 100_000e6
  assertEq(IERC20(USDT).balanceOf(address(cdoEpoch)), preVaultBal + 99_000e6);
  assertGt(minted * cdoEpoch.virtualPrice(address(AAtranche)) / 1e18, 99_000e6);
  // expectedEpochInterest & strategy debt inflated by interest on never-received 1_000e6
}
```

Confidence caveat: I verified `_deposit` (buffer path) uses balance deltas and `depositDuringEpoch` does not; I did not fully trace `mintStrategyTokens` internals or borrower repayment crediting in `IdleCreditVault`/`ProgrammableBorrower`, so the exact loss distribution at repayment should be confirmed against those functions.
