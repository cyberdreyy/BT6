## Analog Found: Divergent duplicate-tenure-start checks between chainstate v1 and v2 (`validate_tenure_change_payload`)

### Title
Duplicated "already-signed-in-tenure" logic diverges between v1 and v2, weakening the proposal-time duplicate-block gate for v1 signers - (File: `stacks-signer/src/chainstate/v1.rs`, `stacks-signer/src/chainstate/v2.rs`)

### Summary
The Trail of Bits report's bug class is code duplication that drifted apart, silently dropping a security-relevant check (the Rekey check) from one of two copies of the same logic. The stacks-signer codebase has the same structural pattern: the "does this tenure-start proposal duplicate a block we've already signed in this tenure" check is implemented twice, once for protocol v1 and once for v2, and the two copies use different criteria for what counts as "already signed."

### Finding Description
`SortitionsView::validate_tenure_change_payload` (v1) and `GlobalStateView::validate_tenure_change_payload` (v2) both exist to reject a second tenure-start block for a tenure that has already produced a signed block, before the signer spends a node validation or a pre-commit on it. v1 checks `get_last_globally_accepted_block`, while v2 checks `get_last_signed_block` (locally *or* globally accepted): [1](#0-0) [2](#0-1) 

The v2 implementation carries an explicit comment justifying its (deliberately) broader definition: "Only blocks we have signed (locally or globally accepted) count here." v1 has no such comment and simply omits the locally-accepted case, exactly as `vault.teal.tmpl` silently omitted the Rekey check present in `vault.js`'s `vaultTEAL` string. The project's own developer documentation independently flags this exact spot as a place where two copies of chain-state logic must be kept semantically aligned by hand, and where a later, harder-to-audit check ends up "covering the same ground" if the earlier one is weaker or skipped: [3](#0-2) 

Because a v1 signer's proposal-time gate does not consult `get_last_signed_block`, a v1 signer that has already locally accepted (signed) a tenure-start block B1 in tenure T, but has not yet observed B1 reach global acceptance, will *not* reject a second tenure-start proposal B2 in the same tenure T at the `validate_tenure_change_payload` stage. The rejection responsibility silently shifts entirely onto the later, timing-sensitive pre-commit-stage conflict guard (`get_signed_conflicts` / `conflict_still_blocks`, section 5 of the signer flow), which is written for the general cross-tenure conflict case (freshness cutoffs, reorg-permit exclusions, sortition-canonicity lookups) rather than as a deterministic "we already signed in this exact tenure" veto: [4](#0-3) 

### Impact Explanation
This matches the report's bug class precisely: a single logical rule ("do not reconsider a tenure that already has our signature") is copied into two independently maintained implementations, and one copy is missing a case the other has. The consequence for the v1 code path is that the early, cheap, deterministic reject is skipped for a block that should have been rejected outright, and the signer instead relies solely on the later, more complex pre-commit-time re-check to prevent placing a second signature on a conflicting tenure-start block. If that later guard's freshness/timeout/canonicity conditions ever diverge from what the early v1 check assumed (which is the whole point of maintaining two hand-synchronized copies of similar logic), the result is the equivocation-guard class of impact this task scopes as High: a signer could end up validating and pre-committing to a second, conflicting tenure-start block that a stricter (v2-equivalent) proposal-time check would have discarded immediately.

### Likelihood Explanation
Likelihood is moderate and conditional rather than a slam-dunk exploit: a single miner (plus normal gossip) can trigger the scenario simply by re-proposing a competing tenure-start block for the same tenure after the first has been locally, but not yet globally, accepted by v1 signers — this is a normal occurrence during signature-timeout re-proposals described elsewhere in the docs. The full compromise depends on the pre-commit-stage guard's freshness window and cannot be proven to fail with certainty from static reading alone; this is a code-duplication weakness (present check vs. missing check) rather than a demonstrated complete signature bypass in this pass.

### Recommendation
Consistent with the original report's recommendation to "maintain one version...and parse it" rather than hand-copy, unify `validate_tenure_change_payload` for v1 and v2 into a single shared implementation of "does this tenure already have a signed block" (using `get_last_signed_block` semantics for both), or explicitly document and test why v1's narrower `get_last_globally_accepted_block` check is safe given the fallback to the pre-commit-time conflict guard. At minimum, add regression tests exercising: v1 signer signs B1 (locally accepted only) → miner re-proposes tenure-start B2 in the same tenure → assert the signer's decision matches the v2 signer's decision under the same conditions.

### Proof of Concept
Not applicable in the strict sense used for the other analog categories (no forged message/signature is required); the "proof of concept" is the direct code diff between the two files cited above (`get_last_globally_accepted_block` in v1.rs vs `get_last_signed_block` in v2.rs) for the same purpose, which is confirmed by reading the source. A dynamic PoC would require exercising `SignerTest` harness with a mixed v1/v2 reward-cycle-boundary scenario (as done in existing tests like `injected_signatures_are_ignored_across_boundaries`) to force a locally-accepted-but-not-globally-accepted tenure-start block and then re-propose a conflicting one — this was not runnable in this analysis.
