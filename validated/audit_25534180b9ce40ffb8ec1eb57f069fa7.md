## Analysis

The relevant control is in `stacks-signer/src/v0/signer.rs`, function `handle_block_pre_commit`, specifically the "own-tenure" conflict guard that runs once the pre-commit threshold is reached and the chainstate re-check (`check_block_against_signer_db_state`) has already passed: [1](#0-0) 

This guard exists precisely because the chainstate check does **not** cover same-tenure duplication for tenure-change blocks — it only checks the *parent* tenure (`check_tenure_change_confirms_parent`), and the one-time `DuplicateBlockFound` check that would catch a second tenure-start block in the same tenure only runs at proposal arrival, never again: [2](#0-1) [3](#0-2) [4](#0-3) 

So the *only* remaining backstop against signing two sibling tenure-start blocks in the same tenure is the own-tenure branch shown above and documented in the flow doc: [5](#0-4) [6](#0-5) 

That branch only vetoes signing when `get_tenure_tip` for the block's own consensus_hash returns a tip **at or above** the proposed height — i.e. when the node has already confirmed a block in that tenure. If the tenure has never been confirmed on the node (`Err` from `get_tenure_tip`, or a tenure the node has simply never seen a block for), the code logs a warning and **falls through without returning**, allowing the pre-commit path to proceed straight to `mark_locally_accepted` and sign: [7](#0-6) [8](#0-7) 

This is the exact analog of the Harden-Runner bug class: a policy ("don't sign a second, conflicting block for a tenure you've already signed a block in") is enforced through one channel (`check_block_against_signer_db_state` for the *parent* tenure, and `DuplicateBlockFound` at proposal time) but the equivalent alternate path — a *stale* same-tenure conflict where the node has not yet confirmed any block in that tenure — is left unguarded, exactly like DNS-over-TCP bypassing an egress block that only filtered one query path.

### Why this is reachable by one miner + gossip
The freshness window is bounded by `tenure_last_block_proposal_timeout` (a config duration, commonly tens of seconds): [9](#0-8) 

A single block-producing miner fully controls the timing of a tenure: it can propose block `A` (tenure-start for tenure `T`), let it be signed locally by a subset of signers (enough to make `A`'s signature "stale" once `tenure_last_block_proposal_timeout` elapses) while deliberately withholding/delaying propagation of the aggregated signature so the node in this signer's view never actually processes any block in tenure `T` — nothing here requires colluding with a majority of signers or possessing any signer's key. It then proposes sibling `B` in the same tenure `T`. Once `B` clears pre-commit threshold at this signer, the own-tenure guard's `get_tenure_tip(T)` call returns "never confirmed" (or errors, e.g., transient RPC issue), the `if tip_height >= ...` branch is skipped, and the fall-through lets this signer place a second signature over `B` — a direct conflict with the earlier signature over `A` in the very same tenure.

### Title
Stale-and-Unconfirmed Same-Tenure Conflict Bypasses the Pre-Commit Double-Sign Guard — ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_pre_commit`'s own-tenure conflict guard is the sole remaining backstop against signing two sibling tenure-start blocks within the same tenure (the chainstate re-check only verifies the *parent* tenure for tenure-change blocks, and the proposal-time `DuplicateBlockFound` check never re-runs). That guard only refuses to sign when the node's canonical view of the block's own tenure is already at or above the proposed height; when the tenure has not yet been confirmed on the node (or the RPC call errors), the code falls through and signs anyway, even though this signer already has a signature outstanding on a conflicting sibling in that same tenure.

### Finding Description
`check_block_against_signer_db_state` for a tenure-change block verifies only the *parent* tenure via `check_tenure_change_confirms_parent` [10](#0-9) , never the block's own tenure. The one check that does look at the block's own tenure for duplication, `validate_tenure_change_payload`'s `DuplicateBlockFound`, executes only once, at proposal arrival [2](#0-1) , and is never re-evaluated at pre-commit time. The intended replacement guard, in `handle_block_pre_commit`, only blocks signing when `get_tenure_tip` proves the node's chain already reached at least the proposed height in that tenure; any other outcome ("never confirmed" or RPC failure) is treated as non-blocking and signing proceeds [7](#0-6) . Consequently a stale, same-tenure conflict that the node has simply never confirmed provides no protection at all, letting this signer place a signature on two mutually exclusive tenure-start blocks for the same tenure.

### Impact Explanation
This breaks the "one signature per tenure/height" safety invariant that the whole pre-commit conflict machinery exists to enforce — a signer ends up signing a conflicting (non-canonical, sibling) block for a tenure it has already signed. If enough other signers hit the same fall-through independently (each only needs its own node to lack confirmation of the tenure, not majority collusion), both siblings can accumulate 70% weight from different, possibly overlapping, sets of signers, producing two validly-signed conflicting blocks at the same height/tenure — a critical safety break per the stated impact classes.

### Likelihood Explanation
Requires only a single malicious/faulty miner controlling block-proposal timing within its own tenure (to make the first signature stale and to keep the node from confirming any block in that tenure before proposing the sibling) plus normal gossip of pre-commits; no signer key, no majority of signers, and no StackerDB/transport exploit is needed. The window is bounded by `tenure_last_block_proposal_timeout`, a config value the miner does not control but can simply wait past.

### Recommendation
Extend the own-tenure guard so that an `Err`/"never confirmed" result from `get_tenure_tip` is treated the same as "tip at or above proposed height" (i.e., still blocking) whenever a same-tenure conflict exists and the conflicting block was locally or globally accepted, rather than defaulting to permit signing. Alternatively, re-run the `DuplicateBlockFound`-style own-tenure check at pre-commit time instead of relying solely on a node-tip lookup that can be legitimately unanswerable.

### Proof of Concept
1. Miner proposes tenure-start block `A` for tenure `T`. A minority-plus of signers locally accept and sign `A`, but the miner withholds/delays relaying the aggregate signature so the target signer's connected node never processes any block in `T`.
2. After `tenure_last_block_proposal_timeout` elapses, the target signer's earlier signature over `A` is now "stale" per `freshness_cutoff` [9](#0-8) .
3. Miner proposes sibling tenure-start block `B` for the same tenure `T`. `check_block_against_signer_db_state` on `B` only checks `B`'s parent tenure, passing.
4. `B` reaches the 70% pre-commit threshold at the target signer. The own-tenure guard queries `get_tenure_tip(T)`; because the node has never confirmed any block in `T`, the call returns an error or "no tip", so the `tip_height >= proposed height` check never triggers [7](#0-6) .
5. The signer falls through to `mark_locally_accepted`/`handle_block_signature`, producing a second signature over `B`, conflicting with its earlier signature over `A` in the same tenure.
