### Title
Unfunded instant-withdraw receipts from pre-default epochs are excluded from the recovery basis and become permanently unclaimable - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`defaultPendingClaimBasis()` only adds `instantWithdrawClaimsByEpoch[epochNumber]` (the *current*, defaulted epoch) to the recovery basis, even though `pendingInstantWithdraws` aggregates unfunded instant receipts across *all* epochs. After `finalizeDefaultRecovery`, a user whose instant receipt was requested in an earlier epoch and never funded gets zero recovery allocation; their claim then falls through to `_transferFundedClaim`, which is guarded to never spend the default recovery reserve and reverts when the strategy's non-reserve balance is insufficient. The receipt is effectively frozen forever, while the reserve is drained by default-epoch claimants.

### Finding Description
The analog of the libyang bug — dereferencing a copied pointer to an *unresolved* object — maps here to claiming an instant receipt that references an epoch whose claim basis was never resolved into recovery accounting.

- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and bumps the global `pendingInstantWithdraws` (lines 366–374). There is no per-epoch funding tracking: `collectInstantWithdrawFunds` just decrements the aggregate `pendingInstantWithdraws` (line 401).
- On default, `defaultPendingClaimBasis()` returns `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` only when `pendingInstantWithdraws != 0` (lines 644–649). Unfunded instant receipts from earlier epochs are excluded from `totalBasis`, so `defaultRecoveryReserve`/`defaultRecoveryPrice` are computed without them.
- After finalization, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest`, which clears **only** `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (line 844). The user's older unfunded receipt remains in `instantWithdrawsRequests[_user]`, is burned at line 389, and is paid via `_transferFundedClaim`, which reverts if `balance - defaultRecoveryReserve < amount` (line 904) — and the strategy holds no non-reserve funding for that receipt because the borrower never repaid it.

### Impact Explanation
Permanent freezing of user funds. An unprivileged lender with an unfunded instant receipt from epoch N loses any recovery allocation when epoch N+1 defaults and is finalized; their `claimWithdrawRequest`/`claimInstantWithdrawRequest` path reverts indefinitely (or, if dust non-reserve balance exists, they withdraw at par and steal reserve-isolated funds accounting-wise — either way the solvency/fair-recovery invariant breaks). Loss = full unfunded receipt amount.

### Likelihood Explanation
Requires a low-liquidity epoch where an instant request stays in `pendingInstantWithdraws` through a `stopEpoch` (borrower doesn't fund it), followed by a later-epoch borrower default and `finalizeDefault`. All privileged actors (borrower, owner, manager) behave honestly — partial funding and default are normal protocol states, not malicious configuration.

### Recommendation
Track instant claims per epoch like normal receipts and include *all* unfunded instant receipt epochs in `defaultPendingClaimBasis` (e.g., keep an `instantWithdrawsRequestsByEpoch`-backed aggregate of unfunded claims), or roll pre-default-epoch unfunded instant receipts into the default recovery basis so every outstanding receipt either joins recovery at the haircut or is provably already funded.
