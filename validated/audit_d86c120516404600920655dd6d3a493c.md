### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing requests to execute below the required K-of-N quorum - (File: multisig2/src/lib.rs)

### Summary
In `multisig2/src/lib.rs`, `confirm()` checks a request's confirmation `HashSet<String>` against `self.num_confirmations` without ever revalidating that each entry in that set still corresponds to a *current* member of `self.members`. When a member is removed via `DeleteMember`, `delete_member()` only purges requests that the removed member *originated* (`r.member == member`), not requests the removed member had merely *confirmed*. Any pending request the removed member had already confirmed keeps that confirmation in its `confirmations` set forever, and it still counts toward reaching `num_confirmations`, even though the confirming party is no longer an authorized signer.

### Finding Description
The binding that should hold is: `confirmations.len() at execution == number of confirmations from accounts/keys currently in self.members`. The code breaks this equality.

- `confirm()` only prevents the *same predecessor* from confirming twice and only checks that the *caller* is a current member via `current_member()`/`assert_valid_request()`: [1](#0-0) 
It never re-derives the confirmation count from members that are still live; it simply reads whatever strings are stored in `self.confirmations.get(&request_id)`.

- `delete_member()` only cleans up requests *created by* the removed member, leaving confirmations placed by that member on other, still-pending requests untouched: [2](#0-1) 

- The only guard on removal is that the remaining member count stays `>= num_confirmations`: [3](#0-2) 
This guarantees there are *enough members* to eventually reach the quorum, but it does nothing to invalidate a stale confirmation already recorded by the removed member.

This is the same bug class as the reported lottery issue: a credit ("has confirmed"/"has lost a round") is recorded against a participant and is never revoked or re-checked when that participant's eligibility changes (leaves the lottery / is removed from the multisig), so the stale credit keeps counting toward a later threshold decision made by an unrelated party.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." A transfer, `AddKey` (full access key), or `DeployContract` request can be executed having received confirmations from fewer *currently authorized* members than `num_confirmations` requires, because a stale confirmation from a removed member is silently counted. This undermines the entire K-of-N custody guarantee of the multisig account and can lead to unauthorized movement of funds or unauthorized code/key changes on the multisig account.

### Likelihood Explanation
Exploitation requires: (1) a pending request that a soon-to-be-removed member confirmed but did not create, (2) that member later being removed via a separate `DeleteMember` execution, and (3) the original request remaining unconfirmed/unexecuted at removal time. This is a plausible operational sequence for any multisig that rotates membership while it has other in-flight requests (a common maintenance activity), so it does not require attacker-controlled privileged actions beyond normal multisig usage by any subset of members reaching quorum to remove another member — no foundation/owner/redeploy assumption is needed, only ordinary member turnover.

### Recommendation
When a member is removed, iterate over *all* pending requests' confirmation sets (not just requests the member created) and strip the removed member's entry from each. Alternatively, at `confirm()` time (and especially right before the `>= num_confirmations` check that triggers execution), filter the stored confirmations against `self.members` and only count confirmations from currently-live members.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. `A` calls `add_request(Transfer{...})` → `request_id = R`.
3. `B` calls `confirm(R)` → `confirmations(R) = {B}` (1 of 3, not yet executed): [4](#0-3) 
4. Separately, members `A`, `C`, `D` create and confirm a `DeleteMember{member: B}` request (a self-request reaching the 3-confirmation quorum) which removes `B` from `self.members` and deletes its access key. Because `delete_member()` only removes requests *authored* by `B`, request `R` (authored by `A`) and its confirmation set `{B}` are left intact: [5](#0-4) 
5. Now only `A`, `C`, `D` remain as members. `A` calls `confirm(R)` → `confirmations(R) = {A, B}` (len 2). `C` calls `confirm(R)` → `confirmations(R) = {A, B, C}` (len 3 ≥ `num_confirmations = 3`) → `execute_request` runs and the transfer is sent: [6](#0-5) 

The transfer executes with only two currently-authorized confirmations (`A`, `C`) instead of the required three, because the stale confirmation from the removed member `B` was still counted — a K-of-N quorum bypass.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
