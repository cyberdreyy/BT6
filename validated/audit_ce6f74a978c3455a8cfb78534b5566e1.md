### Title
TOCTOU race in `ValidateEthBalanceForTransfer` allows concurrent `/v2/transfers` requests to bypass the per-request balance cap - ([File: core/web/evm_transfer_controller.go])

### Summary
`EVMTransfersController.CreateEVMLegacy` validates the sender's balance via `ValidateEthBalanceForTransfer` and then calls `chain.TxManager().SendNativeToken` to queue the transfer, but the balance check and the transaction submission are not performed atomically or against any shared "in-flight amount" tracker. An edit-role user issuing N concurrent transfer requests for the same `fromAddress` can have all N requests pass the balance check independently against the same (stale) balance snapshot, since none of the concurrent validations account for other transfers in flight.

### Finding Description
In `core/web/evm_transfer_controller.go`, `CreateEVMLegacy` performs:
1. `ValidateEthBalanceForTransfer(c, chain, tr.FromAddress, tr.Amount, tr.DestinationAddress)` — reads current balance either from `chain.BalanceMonitor().GetEthBalance(fromAddr)` (a cached/polled value) or `chain.Client().BalanceAt` (an eth_getBalance snapshot), then compares it to `amount + gas fees`.
2. If valid, `chain.TxManager().SendNativeToken(...)` is called to enqueue the transaction for broadcast. [1](#0-0) 

There is no locking, no per-account "reserved/pending balance" accounting, and no serialization between the balance check and the enqueue-for-send step within this handler or in `ValidateEthBalanceForTransfer` itself: [2](#0-1) 

Because on-chain balance only decreases once a transaction is mined (not merely queued/broadcast), and `BalanceMonitor`/`BalanceAt` reflect on-chain state, N concurrent requests for the same `fromAddress`, each individually within the balance limit, will all read the same pre-transfer balance and all pass validation, even though their combined amount can exceed the actual balance. All N will then be handed to `TxManager().SendNativeToken`, which allocates sequential nonces and queues them for broadcast regardless of aggregate spend. The result is that transactions beyond what the balance can actually cover are attempted, either failing at execution (wasting nonces/gas estimation cycles, consuming node resources) or, depending on gas dynamics, executing until real balance is exhausted mid-sequence — an outcome the per-request-only validation was explicitly meant to prevent.

### Impact Explanation
This breaks the intended "each individually-authorized transfer must be independently bounded to actual balance" invariant. Concrete impact: an edit-role user can force the node to attempt sending more value than the account actually holds, causing failed/partially-failed transactions, nonce churn, and unnecessary gas-estimation/RPC load — a resource-exhaustion and fund-management integrity issue rather than a direct authentication/authorization bypass. This aligns with the "unauthorized/uncontrolled fund movement" bounty class, though impact is bounded by the fact the attacker must already hold edit privileges on the node's transfer endpoint.

### Likelihood Explanation
Requires only an edit-role session (already a documented precondition) and the ability to fire concurrent HTTP requests to `POST /v2/transfers` — no special network position or additional exploit primitive needed, making it straightforward and repeatable for any user who already has edit access to this endpoint.

### Recommendation
Serialize balance validation and transfer submission per `fromAddress` (e.g., a per-key mutex or DB-level advisory lock held across the check-then-submit sequence), or maintain a per-key "reserved pending amount" that is incremented atomically before validation and decremented on failure/confirmation, so concurrent requests are validated against `balance - alreadyReservedPending` rather than the raw on-chain/cached balance.

### Proof of Concept
Go handler-level integration test plan:
1. Set up a test `legacyevm.Chain` with a mock `BalanceMonitor` returning a fixed balance `B` (e.g., 1 ETH) and a mock `TxManager` whose `SendNativeToken` records the amounts it is called with instead of hitting a real chain.
2. Issue `N` (e.g., 5) concurrent `EVMTransfersController.Create` calls, each requesting `0.3 ETH` (individually valid since `0.3 < B`, but `N * 0.3 > B`).
3. Assert that after all requests complete, the sum of amounts passed to `SendNativeToken` does not exceed `B` minus fees.
4. Expected current (failing) behavior: `SendNativeToken` is called with all 5 requests (aggregate `1.5 ETH > 1 ETH` balance), demonstrating the TOCTOU gap; after the fix, only requests that fit within the remaining reserved balance should be allowed through, with the rest failing validation with `422 Unprocessable Entity`.

func ValidateEthBalanceForTransfer(c *gin.Context, chain legacyevm.Chain, fromAddr common.Address, amount assets.Eth, toAddr common.Address) error {
	var err error
	var balance *big.Int

	balanceMonitor := chain.BalanceMonitor()

	if balanceMonitor != nil {
		balance = balanceMonitor.GetEthBalance(fromAddr).ToInt()
	} else {
		balance, err = chain.Client().BalanceAt(c, fromAddr, nil)
		if err != nil {
			return err
		}
	}

	zero := big.NewInt(0)

	if balance == nil || balance.Cmp(zero) == 0 {
		return fmt.Errorf("balance is too low for this transaction to be executed: %v", balance)
	}

	gasLimit := chain.Config().EVM().GasEstimator().LimitTransfer()
	estimator := chain.GasEstimator()

	amountWithFees, err := estimator.GetMaxCost(c, amount, nil, gasLimit, chain.Config().EVM().GasEstimator().PriceMaxKey(fromAddr), &fromAddr, &toAddr)
	if err != nil {
		return err
	}
	if balance.Cmp(amountWithFees) < 0 {
		// ETH balance is less than the sent amount + fees
		return fmt.Errorf("balance is too low for this transaction to be executed: %v", balance)
	}

	return nil
