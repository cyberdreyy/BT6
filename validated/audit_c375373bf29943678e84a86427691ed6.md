### Title
Stale pre-default instant-withdraw receipts bypass the default-recovery haircut and pay at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Yaws traversal bug class — a specially-shaped input slipping past a protection check — maps here to instant-withdraw receipts from an epoch *older* than `defaultRecoveryEpoch` slipping past the haircut path. `IdleCreditVault` finalizes default recovery using only the *current* epoch's instant-claim basis, then `claimInstantWithdrawRequest` pays every receipt still in `instantWithdrawsRequests` at 1:1 through the funded-claim path. A user holding an unfunded instant receipt from an earlier epoch is never haircutted, never added to `defaultPendingClaimBasis`, and is paid at par out of funded underlyings that belong to loss-adjusted or other claimants.

### Finding Description
In `IdleCreditVault.finalizeDefaultRecovery`, the defaulted instant-claim basis is `defaultPendingClaimBasis()`, which adds `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch only (IdleCreditVault.sol:644-649). On claim, `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (lines 842-856); any remainder in `instantWithdrawsRequests[_user]` then flows to `_burn` + `_transferFundedClaim` at par (lines 387-392).

`pendingInstantWithdraws` is decremented by `collectInstantWithdrawFunds` (line 401), so a partially funded instant queue can leave an unfunded remainder attributed to older epochs. Those stale receipts:

- are excluded from `totalBasis` at finalization (so the recovery price does not account for them),
- are excluded from `defaultRecoveryReserve` coverage,
- still sit inside `instantWithdrawsRequests[_user]`, and
- are burned and paid 1:1 by `claimInstantWithdrawRequest` once `defaultRecoveryFinalized` is true.

`_transferFundedClaim` only blocks spending `defaultRecoveryReserve` (lines 899-905). Any non-reserve underlying balance — loss-adjusted `collectWithdrawFunds` proceeds awaiting `_claimLossAdjustedWithdrawRequest`, or prefunded amounts — is fair game for a stale receipt that economically belongs to the defaulted basis and should be haircutted (or revert), not paid at par.

### Impact Explanation
An attacker holding an unfunded instant receipt of `X` from epoch N-1 can, after `finalizeDefaultRecovery` (which only haircutted epoch-N claims), call `claimWithdrawRequest`/`claimInstantWithdrawRequest` via the CDO and receive `X` at par, directly stealing `X` underlying that is owed to loss-adjusted withdraw claimants (`lossRecoveryPriceByEpoch` receipts) or other funded claimants. This breaks the "one receipt one payout" and loss-socialization invariants: the attacker's claim evaded the haircut entirely while honest claimants bear the crystallized loss.

### Likelihood Explanation
Requires: (a) an instant-withdraw remainder that was never funded by the CDO across an epoch boundary (`pendingInstantWithdraws != 0` spanning epochs is possible because the CDO collects only what it sends via `collectInstantWithdrawFunds`), (b) a borrower default finalized via `finalizeDefaultRecovery`, and (c) non-reserve underlyings present in the strategy. The attacker is an ordinary tranche-token holder/requester; all privileged roles (manager, borrower, owner) act honestly — the exploit is pure sequencing around their calls. Funded loss-adjusted balances sitting in the strategy between `collectWithdrawFunds` and user claims provide the stealable balance, so this is realistic rather than theoretical.

### Recommendation
In `_claimDefaultedInstantWithdrawRequest` / `claimInstantWithdrawRequest`, after `defaultRecoveryFinalized` every receipt still in `instantWithdrawsRequests` must either be paid at `defaultRecoveryPrice` from `defaultRecoveryReserve` or revert — never via `_transferFundedClaim`. Concretely: include all epochs' unfunded instant basis in `defaultPendingClaimBasis` (track a global `instantClaimsBasis` rather than only `instantWithdrawClaimsByEpoch[epochNumber]`), and in `claimInstantWithdrawRequest` haircut `amount` by `defaultRecoveryPrice` when `defaultRecoveryFinalized` is set.

### Proof of Concept
Foundry fork PoC sketch (using the repo's `test/foundry/IdleCreditVault.t.sol` harness style):

```solidity
function test_StaleInstantReceiptStealsAtPar() public {
    // epoch N-1: attacker requests instant withdraw; CDO collects only part,
    // leaving pendingInstantWithdraws > 0 attributed to epoch N-1.
    // (attacker receipt: instantWithdrawsRequests[attacker] = X,
    //  instantWithdrawsRequestsByEpoch[attacker][N-1] = X)

    // victim requests normal withdraw in epoch N; borrower funds only partially
    // -> collectWithdrawFunds stores lossRecoveryPriceByEpoch[N] < 1e18
    // and strategy now holds funded victim underlyings.

    // borrower defaults; owner calls _handleBorrowerDefault then
    // finalizeDefault / finalizeDefaultRecovery with some _recoveredAmount.
    // defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[N]
    // -> attacker's epoch N-1 instant basis is NOT included.

    // attacker calls CDO.claimInstantWithdrawRequest(attacker):
    //   _claimDefaultedInstantWithdrawRequest clears only epoch N (==0 for attacker)
    //   amount = instantWithdrawsRequests[attacker] = X  (paid at PAR)
    //   _transferFundedClaim sees balance > defaultRecoveryReserve -> succeeds
    assertEq(underlying.balanceOf(attacker), X); // stolen at par, no haircut
    // victim's loss-adjusted claim now underflows/reverts or is short X.
}
```

Uncertainty note: I could not fully trace `IdleCDOEpochVariant.collectInstantWithdrawFunds` sequencing (whether partial instant funding across epochs is reachable) before the iteration limit; the finding assumes an unfunded remainder can survive an epoch boundary, which the `pendingInstantWithdraws` accounting permits on its face. If the CDO always fully funds `pendingInstantWithdraws` before `epochNumber` increments, this reduces to a permanent-freeze/griefing edge case rather than theft.
