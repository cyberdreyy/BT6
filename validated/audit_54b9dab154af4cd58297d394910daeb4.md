### Title
Unprivileged queued deposit permanently bricks `stopEpochWithDuration` on the prefunded variant - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
Analog of CVE-2026-6470 (missing authorization lets an unprivileged user create a dependency that DoSes a privileged DDL operation): any KYC-passing wallet can permissionlessly create `epochPendingDeposits` via `requestDeposit`, and `prefundedDepositsToProcess()` reverts while that entry is non-zero, which makes `IdleCDOEpochVariantPrefunded.stopEpochWithDuration` always revert. Only the depositor can remove the dependency (`deleteRequest`), so an attacker-controlled dust deposit can block the privileged epoch-stop path.

### Finding Description
In the prefunded flow, the privileged stop path settles queue state through `_afterStopEpochWithDuration`, which calls `prefundedDepositsToProcess()` on the queue. That view reverts if raw pending deposits still exist for the epoch being settled: `_checkNotAllowed(epochPendingDeposits[_epoch] != 0)` [1](#0-0) . The only managers' path to move those deposits is `processDepositsToBorrower`, which is gated to the prefunding window: `_checkNotAllowed(_prefundedWindow == 0 || block.timestamp + _prefundedWindow < _cdo.epochEndDate())` [2](#0-1) . Two consequences:

1. When `prefundedDepositWindow == 0` (the default; `setPrefundedDepositWindow` is a separate manager call [3](#0-2) ), `processDepositsToBorrower` reverts unconditionally, while `requestDeposit`'s cutoff check `(_prefundedWindow != 0 && ...)` is bypassed, so deposits are accepted indefinitely. Any 1-wei `requestDeposit` creates `epochPendingDeposits` that no privileged actor can clear, permanently reverting `stopEpochWithDuration`/`_afterStopEpochWithDuration` [4](#0-3) .
2. Even with a window set, a deposit that is not prefunded before `epochEndDate` (missed window) can never be forwarded, because `processDepositsToBorrower` reverts once outside the window, leaving `stopEpochWithDuration` permanently reverting until each depositor voluntarily calls `deleteRequest` [5](#0-4) .

The direct `stopEpoch` selector is also blocked once a queue is configured (`_checkNotAllowed(msg.sig == this.stopEpoch.selector)`), so there is no privileged fallback [6](#0-5) .

### Impact Explanation
Temporary freezing of all pool funds: the epoch cannot be stopped, borrower repayment cannot be pulled, withdraw receipts cannot be funded, and `startEpoch` for the next epoch is unreachable. The only unwind is the attacker deleting their own request, or the owner calling `setEpochQueue(address(0))`, which abandons the queue and forces every queued depositor to individually `deleteRequest` to recover funds. Loss magnitude equals the full TVL's time value for the duration of the freeze; the attack cost is a dust deposit plus gas.

### Likelihood Explanation
Requires a prefunded-queue deployment where the AA queue is enabled (`epochQueue` set) — confirmed reachable in the test harness [7](#0-6) . Attacker needs only `isWalletAllowed` (Keyring credential), no privileged role [8](#0-7) . The zero-window variant triggers whenever the manager enables the queue before setting `prefundedDepositWindow`; the missed-window variant requires no misconfiguration at all — one late or dust deposit that survives the window suffices, and there is no forced-cleanup path for leftover `epochPendingDeposits`.

### Recommendation
Give privileged actors a way to clear stray pending deposits at stop time, or make settlement tolerant of leftovers:
- In `prefundedDepositsToProcess`/`processPrefundedDeposits`, treat a non-zero `epochPendingDeposits` for the settled epoch by refunding queued users (`safeTransfer` back or marking the epoch claimable at a fixed price) instead of reverting.
- Alternatively, allow `processDepositsToBorrower` (or a new `sweepPendingDeposits`) to run up to `epochEndDate` regardless of `prefundedDepositWindow`, and revert `requestDeposit` when `prefundedDepositWindow == 0` on a prefunded-enabled AA queue.

// test/foundry/PrefundedQueueDoS.t.sol — fork setup as in IdleCDOEpochQueue.t.sol
function testDustDepositBlocksStopEpochWithDuration() external {
    // manager enables prefunded queue but window is still default (0)
    vm.prank(manager);
    IdleCDOEpochVariantPrefunded(address(cdoEpoch)).setEpochQueue(address(queue));

    // unprivileged (KYC'd) attacker deposits 1 wei of underlying
    address attacker = makeAddr('attacker');
    deal(address(underlying), attacker, 1);
    vm.startPrank(attacker);
    underlying.approve(address(queue), 1);
    queue.requestDeposit(1);                       // epochPendingDeposits[nextEpoch] = 1
    vm.stopPrank();

    // privileged sweep path is unusable with window == 0
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    queue.processDepositsToBorrower();

    // borrower ready to repay
    uint256 interest = 1000 * 1e6;
    address borrower = strategy.borrower();
    deal(address(underlying), borrower, interest + strategy.pendingWithdraws());
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), type(uint256).max);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpochWithDuration(0, interest, cdoEpoch.epochDuration(), 0); // reverts in prefundedDepositsToProcess

    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, interest); // also blocked by _beforeStopEpoch
}

  function deleteRequest(uint256 _requestEpoch) external {
    // if the epoch price is already set, deposits were already processed so
    // the deposit request can't be deleted.
    _checkNotAllowed(epochPrice[_requestEpoch] != 0 || epochPrefundedDeposits[_requestEpoch] != 0);

    uint256 amount = userDepositsEpochs[msg.sender][_requestEpoch];
    if (amount == 0) {
      return;
    }
    // reset user deposit for the epoch
    userDepositsEpochs[msg.sender][_requestEpoch] = 0;
    // update pending deposits
    epochPendingDeposits[_requestEpoch] -= amount;
    // transfer underlyings back to the user
    IERC20Detailed(underlying).safeTransfer(msg.sender, amount);
  }
