### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing request execution below the live-member quorum - (File: `multisig2/src/lib.rs`)

### Summary
`multisig2`'s `delete_member()` only purges *requests originally authored by* the removed member; it never scans `self.confirmations` to strip that member's confirmation entries from requests authored by *other* members. Because `confirm()` counts every entry in the `confirmations` set with no check that the signer is still a current member, a confirmation cast by an account that is later removed from the multisig continues to count toward `num_confirmations`, letting a request execute with fewer genuinely live confirmations than the configured threshold.

### Finding Description
`confirm()` increments/executes purely off the size of the stored confirmation set: [1](#0-0) 

`delete_member()` is the only cleanup path invoked when a member is removed (via `DeleteMember` executed through `execute_request`). It removes requests filtered by `r.member == member` (i.e., only requests the removed member *authored*) and drops their `num_requests_pk` entry, but it never iterates `self.confirmations` to remove the departing member's confirmation from requests authored by someone else: [2](#0-1) 

This mirrors the Union Protocol bug class: a value that should be invalidated/refreshed whenever the underlying state it depends on changes (`vouch.lastUpdated` vs. `lockedCoinAge`; here, a member's confirmation vs. current membership) is instead left stale, and a downstream accumulator (`lockedCoinAge` vs. `confirmations.len()`) keeps counting the stale contribution as if it were still valid, breaking an equality that should hold:

`confirmations_counted == confirmations_from_current_members`

### Impact Explanation
Because `execute_request()` can dispatch `Transfer`, `FunctionCall`, `AddKey`/`AddMember` (full-access key grants), or `DeployContract` actions once the (partially stale) threshold is reached, an attacker (or a remaining conspiring member) can get a request executed — e.g. transferring NEAR out, granting a full access key, or upgrading the contract — with fewer real, currently-authorized signers than `num_confirmations` requires. This directly matches the Critical impact category "a multisig request executed below threshold," and can result in NEAR being moved by parties not entitled to it under the configured K-of-N policy.

### Likelihood Explanation
This requires only ordinary multisig operation, no privileged bypass:
1. Any member confirms a pending request without being its author.
2. That member is later removed via a normal `DeleteMember` request (a routine operation, e.g. key rotation or removing a compromised/departing signer) — no attacker privilege is needed beyond being a normal actor in the intended workflow.
3. A remaining member confirms the still-pending request, and the stale confirmation is silently counted.

Since key rotation/removal of multisig members is an expected, common operation, and nothing in `confirm()` or `delete_member()` prevents this sequence, the bug is straightforward to trigger unintentionally, and trivially exploitable by a member who wants to "bank" a confirmation that outlives their own removal.

### Recommendation
When a member is removed in `delete_member()`, iterate over `self.confirmations` for **all** pending requests (not just those authored by the removed member) and remove the departing member's entry from each confirmation set. Alternatively/additionally, `confirm()` should validate that every address in a stored confirmation set still belongs to `self.members` before counting it toward `num_confirmations`, discarding stale entries at read time.

### Proof of Concept
1. Initialize `multisig2` with members `{M1, M2, M3, M4}` and `num_confirmations = 3`. [3](#0-2) 
2. `M1` calls `add_request_and_confirm(Transfer{amount})` → confirmations = `{M1}`. [4](#0-3) 
3. `M2` calls `confirm(request_id)` → confirmations = `{M1, M2}` (2 < 3, not yet executed). [1](#0-0) 
4. Separately, members pass a `DeleteMember{member: M2}` request (3 confirmations from `M1, M3, M4`) to legitimately remove `M2` (e.g. key rotation). `delete_member()` only cleans requests authored by `M2`; the Transfer request from step 2 (authored by `M1`) keeps `M2`'s stale confirmation. [2](#0-1) 
5. `M3` (a live member) now calls `confirm(request_id)` on the original Transfer request: `confirmations.len() (2, including stale M2) + 1 = 3 >= num_confirmations(3)` → `execute_request()` fires the `Transfer`, even though only `M1` and `M3` are current members who actually approved it — one fewer live approval than the configured 3-of-N policy requires. [5](#0-4)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
