### Title
Cross-user response hijack via unauthenticated, attacker-chosen `MessageId` in gateway WebAPI handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The gateway's legacy WebAPI handler stores each in-flight user callback keyed only by the client-supplied `MessageId`, with no uniqueness check and no binding of the callback to the requester's identity. Any unprivileged client (any external HTTP caller hitting the gateway) can choose an arbitrary `MessageId`, including one matching another in-flight legitimate request, and silently overwrite the stored callback, redirecting that response to itself.

### Finding Description
`HandleLegacyUserMessage` accepts a `MessageId` fully controlled by the calling client (`msg.Body.MessageId`, sourced from `jsonRequest.ID`/message body) and stores the caller's callback in a shared, process-wide map keyed solely by that ID, with no check for an existing in-flight entry: [1](#0-0) 

Compare this to the sibling v2 HTTP trigger handler and the confidential-relay/vault handlers, which explicitly reject a request whose ID collides with one already in flight: [2](#0-1) [3](#0-2) 

The legacy `capabilities` handler has no equivalent guard — `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` unconditionally overwrites any prior entry. When the node's response for the original (victim) request eventually arrives, it is routed purely by `MessageId`: [4](#0-3) 

Node-to-gateway routing only validates that the responding node address matches `msg.Body.Sender` (i.e., that the DON node is legitimate); it does not verify that the message id belongs to the same user/session that originally submitted it: [5](#0-4) 

Because `MessageId` values are supplied entirely by unauthenticated/unprivileged callers of the gateway's public HTTP endpoint (`ProcessRequest`), an attacker only needs to guess or observe another user's `MessageId` (or race to submit first) to have their own callback registered under that ID: [6](#0-5) 

### Impact Explanation
If an attacker submits a `web_api_trigger`/`web_api_target` request with the same `MessageId` as a victim's in-flight legitimate request (whether by guessing a low-entropy/predictable ID, observing it via logs/telemetry, or racing), the attacker's callback silently replaces the victim's in the `savedCallbacks` map. The next DON node response tagged with that `MessageId` is delivered to the attacker instead of the victim — a cross-user response confusion that can leak the victim's workflow/job result data to an unauthorized party, while the legitimate caller either hangs until timeout or never receives their result. This is a request/response integrity break reachable purely from an unprivileged HTTP client of the gateway, matching the "single weak link breaks the system" class described in the source report (no owner/authorization layer validates ID ownership before overwrite).

### Likelihood Explanation
Exploitability depends on the attacker being able to predict or observe a victim's `MessageId` and race their own request in before the victim's response returns (this is a legacy code path guarded functionally by the fact that IDs are meant to be unique per caller, but nothing enforces that). Given the same-class handlers elsewhere in the codebase (v2 HTTP trigger handler, confidential relay handler, vault handler) explicitly added a duplicate-ID rejection as a hardening measure, the absence of this check in the legacy `capabilities` handler indicates a known gap in this specific code path rather than a defense already covered elsewhere.

### Recommendation
In `HandleLegacyUserMessage`, before storing a new `savedCallback`, check whether `h.savedCallbacks[msg.Body.MessageId]` already exists and reject the request (mirroring the `setupCallback` duplicate-ID guard in `http_trigger_handler.go` and `newActiveRequest` in the confidential relay / vault handlers) instead of silently overwriting it. Consider additionally binding the callback entry to the request's authenticated sender/session where available, so that even non-colliding but spoofed IDs cannot cause cross-user delivery.

### Proof of Concept
1. Victim submits a legacy gateway request (`web_api_trigger`) with `MessageId = "X"` via `ProcessRequest`; the handler stores `savedCallbacks["X"] = victimCallback` and forwards to DON nodes.
2. Before the DON responds, attacker submits their own legacy request with the same `MessageId = "X"`. `HandleLegacyUserMessage` unconditionally overwrites: `savedCallbacks["X"] = attackerCallback` (no existence check, see cited lines 411-414).
3. When a DON node later responds with `MessageId = "X"` (destined for the victim's original request), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds the attacker's callback, deletes the entry, and sends the response to the attacker (lines 148-162) — the victim never receives their result, and the attacker receives data intended for the victim.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
