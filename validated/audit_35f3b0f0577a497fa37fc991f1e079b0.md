### Title
Post-default withdraw receipts drain the fixed `defaultRecoveryReserve`, stealing finalized recovery funds from defaulted-epoch claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Analogous to CVE-2015-8721 (decompression writes past a fixed-size buffer), `requestWithdraw`'s post-default path mints new claim receipts that pay out 1:1 from `defaultRecoveryReserve` — a buffer sized at `finalizeDefaultRecovery` exactly for the already-existing defaulted claim basis. New claims inflate total obligations beyond the fixed reserve, so late claimants find the buffer exhausted.

### Finding Description
`finalizeDefaultRecovery` computes `reserveAmount` and `recoveryPrice` against `totalBasis` (active + pending receipts) and stores them in `defaultRecoveryReserve` / `defaultRecoveryPrice` (`IdleCreditVault.sol:686-692`). The sum of all entitled defaulted claims equals the reserve; the reserve is fully earmarked.

After finalization, `requestWithdraw` takes the `defaultRecoveryFinalized` branch (`IdleCreditVault.sol:247-258`): it burns the CDO's strategy tokens and mints `_amount` receipt tokens to the user, recording `postDefaultRequests[_user] = _amount`. Crucially it does **not** increase `pendingWithdraws`, does not pull any underlying, and no function can add to `defaultRecoveryReserve` after finalization (`reserveDefaultRecovery` reverts once `defaultRecoveryFinalized` is set, `IdleCreditVault.sol:631`).

`claimWithdrawRequest` then routes to `_claimPostDefaultWithdrawRequest` (`IdleCreditVault.sol:760-767`), which pays `amount` 1:1 via `_transferDefaultRecovery`, decrementing `defaultRecoveryReserve` (`IdleCreditVault.sol:912-917`). The comment "post-default withdraw requests that are already backed by default recovery reserve" (`:104`) is incorrect: the reserve was sized only for pre-finalization claims. Every post-default payout is a direct withdrawal of funds earmarked for defaulted-epoch receipt holders and for the active-side recovery.

The only gate is that the requester must have no outstanding requests (`:249`), trivially satisfied with a fresh tranche-token-holding address. Claims are first-come-first-served, so an attacker can claim before honest defaulted-epoch claimants.

### Impact Explanation
Direct theft / permanent freezing of recovery funds. Any unprivileged tranche holder who still has an active position after default finalization can request a post-default withdraw and immediately claim underlying 1:1 from `defaultRecoveryReserve`. Once the reserve is drained below the sum of remaining entitled claims, honest defaulted-epoch claimants' `claimWithdrawRequest` / `claimInstantWithdrawRequest` calls revert on the `defaultRecoveryReserve -= _amount` underflow — their recovery is permanently frozen/stolen. Loss is bounded only by the reserve size and the attacker's post-default position; in a vault where most users haven't yet claimed, nearly the entire recovery can be captured by early post-default claimers.

### Likelihood Explanation
Requires the vault to be defaulted and finalized — an ordinary, supported state with dedicated handling throughout this contract. The attacker needs only a tranche position (or can acquire tranche tokens post-default) and a clean receipt state; no privileged role, no timing precision, no economic risk. The CDO calls `requestWithdraw`/`claimWithdrawRequest` on the user's behalf in the normal flow, so the sequence is two ordinary user-initiated transactions.

### Recommendation
Fund post-default receipts from a source other than the finalized recovery reserve:
- Track a separate `postDefaultReserve` credited by borrower repayments collected post-finalization, or
- Apply `defaultRecoveryPrice` to post-default claims and expand the reserve/basis accounting so total obligations stay solvent, or
- Disallow `requestWithdraw` entirely once `defaultRecoveryFinalized` is set, since no new funding can arrive.

### Proof of Concept
Foundry fork PoC sketch (against `test/foundry/IdleCreditVault.t.sol` harness style):

```solidity
// Setup: vault running epoch E with user H holding a pending withdraw
// request (receipt basis B_H) and attacker A holding active tranche tokens.
// 1. Epoch stops, borrower defaults; manager triggers default flow.
// 2. CDO calls finalizeDefaultRecovery(recovered, source):
//    reserve = recovered + prefunded + defaultRecoveryReserve
//    price   = reserve * 1e18 / totalBasis   (< 1e18)
// 3. Attacker, fresh state (no requests), calls into CDO which invokes:
//       strategy.requestWithdraw(amountA, A, principalA)  // post-default branch
//       strategy.claimWithdrawRequest(A)                  // _claimPostDefaultWithdrawRequest
//    -> A receives amountA underlying 1:1; defaultRecoveryReserve -= amountA
// 4. Honest user H calls claimWithdrawRequest(H):
//    -> _claimDefaultedWithdrawRequest computes
//       amount = B_H * price / 1e18
//    -> _transferDefaultRecovery: defaultRecoveryReserve -= amount
//       underflows/reverts once cumulative claims exceed reserve.
// assert: A profited; H's claim reverts (permanent freeze of recovery).
```

The key assertion is that post-finalization `postDefaultRequests` payouts reduce a reserve whose sizing math (`reserveAmount * RECOVERY_FULL / totalBasis`) never accounted for them, i.e., cumulative claims exceed cumulative reserve — the vault-side equivalent of writing past the decompression buffer.
