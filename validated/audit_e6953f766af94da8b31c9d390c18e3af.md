### Title
Unbounded, capacity-less `bundle_cache` in `IngressService::send_raw_transaction` enables memory-exhaustion DoS via attacker-controlled transaction hashes - (File: crates/infra/ingress-rpc/src/service.rs)

### Summary
`IngressService`, the handler behind the public, unauthenticated `eth_sendRawTransaction` JSON-RPC method exposed by `ingress-rpc`, deduplicates submissions using a `moka::future::Cache<B256, ()>` keyed by the bundle hash derived from each submitted transaction. Unlike every other cache in this codebase, this cache is constructed with only a `time_to_live` and **no `max_capacity`**, so its size is bounded solely by wall-clock TTL, not by entry count. This is the same bug class as CVE-2026-85584: state keyed by attacker-controlled, effectively unique values, with no capacity limit or eviction policy, exploitable by an unauthenticated remote client sending many unique requests.

### Finding Description

with `bundle_cache_ttl` defaulting to 20 seconds: [2](#0-1) 

Every call to `send_raw_transaction` decodes the raw transaction into a bundle, computes `bundle_hash` from the transaction bytes (a value fully controlled by the caller, since any syntactically valid signed transaction produces a distinct hash), and unconditionally inserts it into `bundle_cache` before simulation results are evaluated: [3](#0-2) 

Every other cache in this same codebase explicitly sets a `max_capacity` alongside `time_to_live` to bound memory (`crates/execution/payload/src/rejection_cache.rs`, `crates/builder/metering/src/store.rs`, `crates/infra/audit/src/rpc.rs`'s `dedup_cache`, `bin/audit-archiver/src/main.rs`), confirming this is the established, intended pattern that `bundle_cache` deviates from: [4](#0-3) [5](#0-4) 

`crates/infra/ingress-rpc` implements no per-IP or global request rate limiting, connection limiting, or request-size throttling anywhere in the crate (verified by search — no matches for rate-limiting constructs), unlike `crates/infra/telemetry` (`IpRateLimiter`) and `crates/infra/websocket-proxy` (`InMemoryRateLimit`). The `eth_sendRawTransaction` endpoint is explicitly described as receiving submissions "from external clients": [6](#0-5) 

### Impact Explanation
An unauthenticated remote client can locally sign an unlimited number of syntactically valid transactions (no on-chain balance, nonce validity, or gas sufficiency is required to pass decoding/signature recovery) and flood `eth_sendRawTransaction` with them. Each unique transaction produces a distinct `bundle_hash` that is inserted into `bundle_cache` regardless of whether metering/simulation ultimately accepts or rejects it. Because the cache has no `max_capacity`, its entry count is unbounded within the (configurable, default 20s) TTL window; sustained submission at high rate grows the cache without limit for the process's lifetime of sustained traffic, degrading the `ingress-rpc` service and, in the worst case, causing it to be OOM-killed, denying `eth_sendRawTransaction` service to legitimate senders — matching the CVE's outcome of "exhaust memory... degrading service availability" and the required impact category of "an RPC the node can no longer serve."

### Likelihood Explanation
High: the endpoint requires no authentication, no API key, and no CAPTCHA; there is no rate limiter or connection limiter anywhere in the `ingress-rpc` crate to throttle the attacker; and generating large volumes of distinct, decodable, signature-valid transactions is computationally cheap for an attacker (no on-chain state is checked before the hash is cached).

### Recommendation
Add a `max_capacity` (and ideally an LRU/TinyLFU eviction policy, matching the pattern used elsewhere in the codebase such as `rejection_cache.rs` and `MeteringStore`) to the `bundle_cache` builder in `IngressService::new` (`crates/infra/ingress-rpc/src/service.rs`), and/or add per-client-IP rate limiting to the ingress-rpc server analogous to `IpRateLimiter` in `crates/infra/telemetry/src/rate_limit.rs`.

### Proof of Concept
1. Generate N (e.g., 10,000,000) distinct locally-signed Ethereum transactions from N different ephemeral private keys (no funding required), each with a random nonce/value so each produces a unique `bundle_hash`.
2. Submit each via `eth_sendRawTransaction` to the public `ingress-rpc` endpoint in a tight loop/parallel client, sustaining submissions faster than the `bundle_cache_ttl` (default 20s) expiry.
3. Observe `bundle_cache` entry count (exposed indirectly via cache-hit/miss metrics or process RSS) grow unbounded with sustained request rate, with no capacity ceiling, until the ingress-rpc process is memory-constrained or OOM-killed, denying `eth_sendRawTransaction` to legitimate users.

Note: I could not verify whether an external load balancer, API gateway, or Kubernetes-level rate limit is deployed in front of `ingress-rpc` in production (that infrastructure is outside this repository's indexed code), so likelihood should be reassessed against actual deployment topology.
