## Summary

The external report's bug class is: *"a single failed/rejected token transfer inside a value-distribution routine causes the entire operation to revert, trapping funds that legitimately belong to other parties."* Searching Aptos-native lockup/stake code for the same class of bug (one recipient's inability to receive funds poisoning a shared distribution loop) leads to `aptos_framework::staking_contract::distribute_internal`.

## Finding Description

`distribute_internal` in [1](#0-0)  withdraws all inactive/pending_inactive stake from the underlying stake pool in one shot, buys everyone (staker, operator(s), and any prior operators still owed unpaid commission from `switch_operator`) into a single `distribution_pool`, and then pays every shareholder out in a `while` loop: [2](#0-1) 

Each payout uses `aptos_account::deposit_coins<AptosCoin>`, which **aborts** if the recipient has explicitly disabled unsolicited coin transfers and is not yet registered for `AptosCoin`: [3](#0-2) 

`can_receive_direct_coin_transfers` returns `false` only if the target account has previously called `set_allow_direct_coin_transfers(false)` — a setting fully controlled by that account itself: [4](#0-3) 

Critically, an **operator** (a role with no privilege over the staker's principal) can unilaterally choose the recipient of their own commission via `set_beneficiary_for_operator`, which accepts an arbitrary address: [5](#0-4) 

If the operator sets a beneficiary address (or uses their own address) that has `allow_arbitrary_coin_transfers = false` and is not registered for `AptosCoin`, then every future call to `distribute()`/`distribute_internal()` for that staker/operator pair will hit the abort inside the `while` loop when it tries to pay that specific shareholder — and because Move transactions are atomic, the **entire** distribution reverts, not just that one payout.

Since `distribute_internal` is also invoked internally from `unlock_stake`, `switch_operator`, `update_commision`, and `set_beneficiary_for_operator` itself (to force-flush pending distributions before mutating state), this one poisoned shareholder entry permanently blocks:
- the staker's own principal/reward withdrawal,
- any other operator's already-earned but undistributed commission (left in the pool from a prior `switch_operator`),
- the ability to ever change beneficiary/operator cleanly (those functions also call `distribute_internal` first).

There is no code path that removes a shareholder from `distribution_pool` other than being successfully paid, so once poisoned, the pool can never be flushed again — a **permanent lock** of stake/commission funds belonging to parties other than the attacker.

## Impact Explanation

This matches the "Permanent lock or non-recoverable loss of claim rights in stake, delegation, commission, beneficiary, or vesting flows" impact category. An operator with zero special privilege over the staker's funds can grief and permanently freeze the staker's entire unlocked/inactive stake balance and any co-existing operator commissions, by simply disabling direct transfers on the address they nominate as their beneficiary before rewards accrue. Vesting contracts are also affected since `vesting::distribute` and `vesting::unlock_rewards` ultimately call into `staking_contract::distribute_internal` [6](#0-5) , so a malicious/compromised operator on a vesting-backed staking contract can strand vested funds owed to shareholders.

## Likelihood Explanation

Likelihood is high in terms of trigger simplicity (any operator can call `set_allow_direct_coin_transfers(false)` on an account they control and then set it as their beneficiary via `staking_contract::set_beneficiary_for_operator`), but this is self-inflicted by the operator and requires them to want to grief rather than collect commission, which is a plausible malicious-but-unprivileged action rather than an accidental one. **I was not able to fully verify one detail before running out of investigation budget**: whether `coin::is_account_registered<AptosCoin>` behaves identically to a generic `CoinType` given Aptos's ongoing migration of `AptosCoin` to the Fungible Asset framework (some FA-migrated flows auto-create a primary store and could make this check trivially always pass, which would neutralize the bug for `AptosCoin` specifically). I could not locate and read `coin::is_account_registered`'s current implementation in the time available, so this should be independently confirmed before treating the finding as conclusively exploitable on `AptosCoin`.

## Recommendation

- In `distribute_internal`, do not let a single recipient's failed deposit abort the whole loop. Catch the failure (or pre-check `coin::is_account_registered` / `can_receive_direct_coin_transfers`) and, if the recipient cannot accept the funds, credit them to a separately claimable/escrow slot instead of aborting, similar in spirit to the external report's suggested "route unpaid funds back rather than reverting the whole transfer."
- Alternatively, disallow operators from designating a beneficiary that has direct transfers disabled and is unregistered, or force-register the recipient for `AptosCoin` up front at `set_beneficiary_for_operator` time rather than at distribution time.

## Proof of Concept

1. Staker creates a staking contract with `operator` and non-zero commission via `staking_contract::create_staking_contract`.
2. `operator` calls `aptos_account::set_allow_direct_coin_transfers(false)` on a fresh address `B` that is never registered for `AptosCoin`.
3. `operator` calls `staking_contract::set_beneficiary_for_operator(operator, B)`.
4. Time passes, stake pool earns rewards, lockup ends (rewards become inactive/withdrawable).
5. Anyone calls `staking_contract::distribute(staker, operator)` (or the staker calls `unlock_stake`, which triggers `distribute_internal` first). The `while` loop reaches shareholder `B`'s share, calls `aptos_account::deposit_coins<AptosCoin>(B, ...)`, which asserts `can_receive_direct_coin_transfers(B)` and aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
6. The entire transaction reverts. The staker's principal/rewards and any other pending operator commissions in the same `distribution_pool` remain permanently stuck, since there is no alternate code path to remove `B` from the pool or to force-flush other shareholders independently.

        account: address
    ): bool acquires DirectTransferConfig {
        !exists<DirectTransferConfig>(account)
