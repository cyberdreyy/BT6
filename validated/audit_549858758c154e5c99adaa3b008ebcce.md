Based on my investigation, the Size protocol issue is about hardcoded decimal/pair assumptions breaking math when the borrow/collateral roles are reversed. The closest concrete analog in marginfi-v2 is not a "reverse market" issue per se (marginfi is decimals-agnostic by design, using dynamic `EXP_10_I80F48` lookups keyed by `mint_decimals`), but a genuine **unchecked decimals bound** that can cause the same class of failure: unvalidated escalation input causing reverts/panics in the exact same functions family (`calc_value`/`calc_amount`, the marginfi analogs of `debtTokenAmountToCollateralTokenAmount`).

### Title
Unvalidated `mint_decimals >= 24` on bank creation causes out-of-bounds panic in value/amount conversion, permanently DoS'ing accounts - ([File: programs/marginfi/src/state/marginfi_account.rs])

### Summary
`calc_value` and `calc_amount` — the core functions that convert token amounts to USD value and back (marginfi's analog of Size's `debtTokenAmountToCollateralTokenAmount`) — index directly into the fixed-size `EXP_10_I80F48` lookup table using `bank.mint_decimals` as an index, with no bounds check. The `Bank` struct's own documentation states `mint_decimals` "Must be < 24," but this constraint does not appear to be enforced by `BankConfigImpl::validate()` (no `mint_decimals` references were found in `bank_config.rs`) or by the standard/permissionless bank-creation instructions. Only the Drift integration path explicitly checks `mint.decimals <= DRIFT_PRECISION_EXP (19)`.

### Finding Description
`calc_value` and `calc_amount` perform: [1](#0-0) [2](#0-1) 

`EXP_10_I80F48` is a fixed 24-element array (`MAX_EXP_10_I80F48 = 24`, valid indices 0–23): [3](#0-2) 

The `Bank` struct documents the constraint but it is a comment, not an enforced invariant: [4](#0-3) 

Bank-creation paths (`lending_pool_add_bank`, `lending_pool_add_bank_permissionless`, `lending_pool_add_bank_kamino`) copy `bank_mint.decimals` straight into the bank with no range check: [5](#0-4) [6](#0-5) 

Only the Drift-specific path enforces a decimals ceiling, and even that ceiling (19) is below the array bound (23) for an unrelated protocol-specific reason: [7](#0-6) 

Token-2022 mints support admin-configurable decimals up to `u8::MAX` (255) via the mint extension. Since `mint_decimals` is stored as `u8` with no explicit `< 24` check on the standard or permissionless bank-add paths, a bank can be created (including via the **permissionless** `lending_pool_add_bank_permissionless` instruction, which is reachable by any unprivileged user for staked-collateral pools) backed by a Token-2022 mint with `decimals >= 24`.

### Impact Explanation
Once such a bank is registered, any call to `calc_value`/`calc_amount` — invoked during deposits, borrows, withdraws, repays, health-pulse, and liquidation checks — performs `EXP_10_I80F48[mint_decimals as usize]` with `mint_decimals >= 24`, which is an out-of-bounds array index. In Rust this panics, aborting the transaction. Because health checks iterate over *all* balances on a `MarginfiAccount`, any user who holds even a dust position in the malformed bank would have every subsequent instruction requiring a health check (deposit, borrow, withdraw, repay, liquidation) permanently revert — a durable freeze of that account's funds with no legitimate recovery path (matching the "durable freeze/inconsistency with financial effect" criterion). This mirrors the Size finding's root cause: an un-escalated/un-validated decimals assumption baked into the value-conversion function silently breaking once real-world inputs deviate from the assumed range.

### Likelihood Explanation
Likelihood is moderate: exploiting this requires either (a) an admin mistakenly configuring a bank with a high-decimal Token-2022 mint (no protection currently prevents this), or (b) for setups exposing permissionless bank creation (e.g., staked-collateral onramp), an attacker creating a Token-2022 mint with `decimals >= 24` and registering it as a bank, then getting a victim (or themselves, to grief shared pools/liquidators) to hold a balance in it. I was not able to fully confirm the contents of `BankConfigImpl::validate()` in `programs/marginfi/src/state/bank_config.rs` (only inferred its likely absence of a decimals check from the fact that this file did not appear among files referencing `mint_decimals`), so there is residual uncertainty about whether some other validation path blocks this before genesis.

### Recommendation
Add an explicit runtime check (e.g., in `BankConfigImpl::validate()` or in `Bank::new`) that rejects `mint_decimals >= MAX_EXP_10_I80F48` (24) for every bank-creation/clone path, not just Drift. Additionally, harden `calc_value`/`calc_amount`/`convert_decimals` to use `.get(...)` with an explicit `MarginfiError` instead of direct indexing, so an out-of-range decimals value degrades gracefully (instruction error) rather than panicking.

### Proof of Concept
1. Create a Token-2022 mint with the mint-close-authority/metadata extensions and set `decimals = 24` (or higher) — permitted by the SPL Token-2022 program.
2. Call `lending_pool_add_bank` (or `lending_pool_add_bank_permissionless` for the staked-collateral flow) with this mint as `bank_mint`. No check rejects `decimals >= 24`.
3. Deposit any nonzero amount into the resulting bank.
4. Trigger a health check (e.g., attempt any borrow/withdraw, or call `lending_account_pulse_health`) on the account holding this balance.
5. `calc_weighted_asset_value_standalone`/`calc_weighted_liab_value_cached_standalone` call `calc_value(..., bank.get_balance_decimals(), ...)`, which indexes `EXP_10_I80F48[24]` (or higher) on a 24-element array — an out-of-bounds panic, aborting the transaction and freezing all account operations requiring a health check.
