This confirms the mechanics. Redeploying under `AccountId` mode overwrites the same `TrieKey::GlobalContractCode { identifier: AccountId(...) }` in-place, and `precompile_contract_with_warming` re-warms the cache for the *new* code immediately during distribution processing (`runtime/runtime/src/global_contracts.rs:211-222`). Resolution for referencing accounts is always done live via `GlobalContractAccessExt::hash()` (`runtime/runtime/src/contract_code.rs:92-106`), which performs a fresh trie lookup on every call rather than storing a cached/stale hash on the account. For `CodeHash` mode, the identifier is `hash(&contract_code)` — a pure content hash (`runtime/runtime/src/global_contracts.rs:150-153`) — so the attacker cannot "redeploy different code under the same identifier" at all; different code necessarily produces a different identifier/trie key.

### No vulnerability found for this question.

**Reasoning:**

1. **CodeHash mode**: `GlobalContractIdentifier::CodeHash` is derived as `hash(&contract_code)` at deploy time [1](#0-0) . It is content-addressed — the attacker cannot deploy *different* bytecode under the *same* `CodeHash` identifier; doing so would produce a different hash and thus a different trie key entirely. The premised attack ("redeploys DIFFERENT code under the same GlobalContractIdentifier" for a hash-mode identifier) is cryptographically impossible.

2. **AccountId mode**: Redeploying is the explicitly documented, intended behavior — "This allows the owner to update the contract for all its users" [2](#0-1) . A third party referencing via `AccountContract::GlobalByAccount(account_id)` never stores a fixed/stale code hash on their own account; resolution is performed fresh on every access through `GlobalContractAccessExt::hash()`, which does a live trie lookup (`store.get_ref(&key, ...)`) rather than caching a stale value [3](#0-2) . `RuntimeContractIdentifier::resolve` performs this same live resolution at contract-call time [4](#0-3) .

3. **Bytecode availability**: When the owner redeploys new code under `AccountId` mode, `apply_distribution_current_shard` overwrites the *same* `TrieKey::GlobalContractCode` entry in place and immediately calls `precompile_contract_with_warming` to populate the `ContractRuntimeCache` for the new code [5](#0-4) . There is no scenario where a referencing account is left pointing at a hash whose bytecode has vanished — the referencing account's identifier (`AccountId`) always resolves to whatever code is *currently* stored for that account, and that code is always present in the trie (it's the authoritative source; `ContractRuntimeCache` is merely a compiled-artifact cache with its own re-compile-on-miss fallback described in `contract-vm.md` §3 and §7 — a cache miss triggers `Contract::get_code` + `compile_and_cache`, not a permanent failure).

4. Since a third party can only reference a global contract via `UseGlobalContract`, and that reference always resolves live to the identifier's *current* code, there is no reachable path where the referencing account's `AccountContract` field ends up pointing to a hash/identifier whose bytecode is permanently unretrievable due to cache eviction. The premise conflates the compiled-artifact `ContractRuntimeCache` (which has re-compile-on-miss recovery) with the actual contract-code storage in the trie (which is never deleted for a live identifier that's still referenced), and additionally misdescribes `CodeHash` mode as mutable when it is by construction content-addressed and immutable.

impl GlobalContractAccessExt for GlobalContractIdentifier {
    fn hash(self, store: &TrieUpdate, access: AccessOptions) -> Result<CryptoHash, StorageError> {
        if let GlobalContractIdentifier::CodeHash(hash) = self {
            return Ok(hash);
        }
        let key = TrieKey::GlobalContractCode { identifier: self.into() };
        let value_ref =
            store.get_ref(&key, KeyLookupMode::MemOrFlatOrTrie, access)?.ok_or_else(|| {
                let TrieKey::GlobalContractCode { identifier } = key else { unreachable!() };
                StorageError::StorageInconsistentState(format!(
                    "Global contract identifier not found {:?}",
                    identifier
                ))
            })?;
        Ok(value_ref.value_hash())
    }
