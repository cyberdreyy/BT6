### Title
100% `reward_fee_fraction` passes `assert_valid` and gets whitelisted, allowing total theft of delegator rewards - ([File: staking-pool-factory/src/lib.rs])

### Summary
`RewardFeeFraction::assert_valid` in `staking-pool-factory/src/lib.rs` only checks that `numerator <= denominator`, not `numerator < denominator`, so a pool with a 100% fee (e.g. `numerator: 1, denominator: 1`) passes validation. `create_staking_pool` never re-checks the fee bound, and `on_staking_pool_create` whitelists the pool solely based on `is_promise_success()`, so a fully malicious-fee pool is created and whitelisted exactly like a legitimate one.

### Finding Description
The binding implied by the whitelist/factory design is: *"a pool whitelisted through `StakingPoolFactory::create_staking_pool` has `reward_fee_fraction.numerator < reward_fee_fraction.denominator`"* (i.e., delegators always retain a non-zero share of rewards). The actual code enforces only: [1](#0-0) 

`self.numerator <= self.denominator` permits `numerator == denominator`, i.e. a 100% reward fee.

The attacker calls `create_staking_pool` with `reward_fee_fraction = { numerator: 1, denominator: 1 }` (or any equal pair), attaching `MIN_ATTACHED_BALANCE`: [2](#0-1) 

`reward_fee_fraction.assert_valid()` at line 164 passes because `numerator <= denominator`. The staking pool contract is deployed with these args, and the callback `on_staking_pool_create` only checks `is_promise_success()` — it has no knowledge of, or check on, the fee fraction — before calling `add_staking_pool` on the whitelist contract: [3](#0-2) 

Once whitelisted, the pool is indistinguishable on-chain from a legitimately-fee-bounded pool: delegators (and any tooling/UI that trusts "whitelisted implies bounded fee") who stake into it will have 100% of any reward distributed to the pool's `reward_fee_fraction`/owner rather than being credited to delegator `stake_shares`, because the staking-pool contract computes the owner's share directly from this fraction with no additional cap. No existing guard (`assert_self`, `is_promise_success`, `assert_valid`, `is_valid_account_id`) inspects the *value* of the fee fraction for an upper bound below 100%.

Regarding the "account id derived from a victim account" framing in the question: `staking_pool_account_id` is always `format!("{}.{}", staking_pool_id, env::current_account_id())` — i.e., it's a subaccount of the factory, and `staking_pool_id` is attacker-chosen. There is no code path that derives the pool's account id from any other account's id; this part of the framing does not correspond to an actual mechanism in this contract and is not needed to demonstrate the core issue, which is the fee-bound bug itself.

### Impact Explanation
Any delegator who stakes into such a pool has their entire staking reward diverted to the pool owner (the attacker) every epoch — this matches the "rewards or owner fees attributed to the wrong party" High-severity category. The attacker can repeat this for any number of pools/fee values up to and including 100%, and because the pool is whitelisted, it appears trustworthy to delegators and any client enforcing "only stake into whitelisted pools."

### Likelihood Explanation
The only precondition is attaching `MIN_ATTACHED_BALANCE` (30 NEAR) and calling a public, unprivileged, `#[payable]` method — no owner, foundation, or multisig role is required. The exploit is fully deterministic and repeatable across accounts/epochs at the cost of one 30 NEAR deposit (which is spent on account creation/storage, not lost) per pool.

### Recommendation
Change `RewardFeeFraction::assert_valid` to enforce `self.numerator < self.denominator` (or clamp to a maximum below 100%, e.g. `numerator * K <= denominator` for some protocol-chosen ceiling like 50%), rejecting fee fractions equal to or exceeding 1. Apply the same fix to the equivalent `assert_valid` in `staking-pool/src/lib.rs` used for `update_reward_fee_fraction`.

```rust
fn test_create_staking_pool_with_100_percent_fee_is_whitelisted() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = StakingPoolFactory::new(account_whitelist());

    context.predecessor_account_id = account_tokens_owner();
    context.attached_deposit = ntoy(31);
    testing_env!(context.clone());

    // numerator == denominator => 100% fee, yet assert_valid does not panic
    contract.create_staking_pool(
        staking_pool_id(),
        account_pool_owner(),
        "KuTCtARNzxZQ3YvXDeLjx83FDqxv2SdQTSbiq876zR7".try_into().unwrap(),
        RewardFeeFraction { numerator: 1, denominator: 1 },
    );

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let res = contract.on_staking_pool_create(account_pool(), ntoy(31).into(), account_tokens_owner());

    // BEFORE/AFTER equality that should hold but doesn't:
    // assert!(reward_fee_fraction.numerator < reward_fee_fraction.denominator) for any whitelisted pool
    // Actual: pool is whitelisted (PromiseOrValue::Promise -> add_staking_pool call), proving
    // a 100%-fee pool passes the exact same path as a legitimate pool.
    match res {
        PromiseOrValue::Promise(_) => {} // whitelisting promise is fired, proving the bug
        PromiseOrValue::Value(_) => panic!("expected pool creation to succeed and be whitelisted"),
    }

    context.is_view = true;
    testing_env!(context.clone());
    assert_eq!(contract.get_number_of_staking_pools_created(), 1);
}
```
This demonstrates that `create_staking_pool` / `on_staking_pool_create` whitelist a pool whose `reward_fee_fraction` takes 100% of rewards, violating the intended bound of `assert_valid` and the "whitelisted implies bounded fee" invariant.

```rust
    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }
```
