### Title
`setEpochParams` changes `epochDuration`/`bufferPeriod` without rescaling the stored APR, inflating withdraw-request receipts - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
The scaled APR stored in `IdleCreditVault` is computed once via `setAprsWithBuffer(_newApr, epochDuration, bufferPeriod)` inside `_setScaledApr` (called at `stopEpoch` / `stopEpochWithDuration`). `setEpochParams` can later change `epochDuration` and `bufferPeriod` while the epoch is not running, but it never recomputes the scaled APR. All subsequent interest math in `_calcInterestWithApr`, `_calcInterestWithdrawRequest`, and `startEpoch` then combines a stale scaled APR (baked with the old duration/buffer ratio) with the new `epochDuration`, so withdraw-request receipts and `expectedEpochInterest` are mispriced. An unprivileged KYC'd lender can sandwich the honest `setEpochParams` call with `requestWithdraw` during the buffer to mint an inflated receipt that is later funded from the borrower/strategy. ### Finding Description
The intended accounting is:

- Manager sets APR at `stopEpoch`/`stopEpochWithDuration` via `_setScaledApr(_newApr)` → `IdleCreditVault.setAprsWithBuffer(_newApr, epochDuration, bufferPeriod)`, storing `scaledApr = _newApr * (epochDuration + bufferPeriod) / epochDuration`.
- `_calcInterestWithApr` then multiplies this `scaledApr` by the *current* `epochDuration`, yielding interest for `epochDuration + bufferPeriod`.
- `requestWithdraw` removes the buffer share again via `_calcInterestWithdrawRequest` (`* _duration / (_duration + _buffer)`).

`stopEpochWithDuration` keeps this consistent because it calls `setEpochParams` and *then* re-calls `_setScaledApr`. But the standalone `setEpochParams` (callable by owner/manager whenever `!isEpochRunning && !defaulted`) changes `epochDuration`/`bufferPeriod` with no APR rescale:

```solidity
// contracts/IdleCDOEpochVariant.sol
function setEpochParams(uint256 _epochDuration, uint256 _bufferPeriod) public {
    _checkOnlyOwnerOrManager();
    _checkNotAllowed(defaulted || isEpochRunning || _epochDuration == 0 || epochDuration == 0);
    epochDuration = _epochDuration;
    bufferPeriod = _bufferPeriod;
}
```

After this call, `_calcInterest(_amount)` computes `amount * [apr * (d_old + b_old)/d_old] * d_new / 365d` instead of the correct `amount * apr * (d_new + b_new) / 365d`. The on-code comment acknowledges only the `bufferPeriod` hazard ("should not be changed once set"), leaving the `epochDuration` path unguarded and functionally broken whenever `b != 0` or `d` changes.

Exact analog to the external report: a bound (`epochDuration`/`bufferPeriod` ↔ Truflation's `maxAllocation`) is mutated by a privileged setter while a dependent schedule (`scaledApr` ↔ `emissions[]`) validated against the old bound is left stale, so the invariant `scaledApr == apr * (epochDuration + bufferPeriod) / epochDuration` silently becomes false.

### Impact Explanation
A lender's `requestWithdraw` receipt is fixed at request time (`_underlyings = principal + interest - totalFees`, `creditVault.requestWithdraw`) and is funded at par from the borrower at the next `stopEpoch` via `pendingWithdraws`/`collectWithdrawFunds`. If `epochDuration` is increased (e.g. 30d→90d with 5d buffer), the stale scaled APR makes `totInterest` ≈ 10.5% larger than intended (`apr*35/30*90` vs correct `apr*95`), so the attacker's receipt — and every other LP's `expectedEpochInterest` accrual — is inflated at the honest borrower's expense; the borrower must repay interest it never agreed to, or the epoch stop under-collateralizes remaining LPs if the borrower funds only the correct amount. If duration is decreased, receipts are understated and the difference is permanently locked as `pendingWithdraws` shortfall → frozen/underpaid user claims. Either direction breaks fair mint/burn and solvency with a quantifiable loss proportional to `|d_new*(d_old+b_old) − d_old*(d_new+b_new)| / (d_old*(d_new+b_new))`. [3](#0-2) [4](#0-3) 

### Likelihood Explanation
`setEpochParams` is a normal public owner/manager operation usable between epochs (the honest actor may reasonably retune duration for the next loan term without going through `stopEpochWithDuration`, which bundles a stop). No guard forces an APR rescale afterwards; `setAprs` on the strategy *could* fix it manually but nothing requires or validates it. The attacker needs only a KYC-passing wallet, a tranche balance, and to call `requestWithdraw` in the buffer window — all unprivileged actions explicitly allowed while `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are true. Existing guards (`_skimDonatedAssets`, epoch gating, default checks) do not cover this inconsistency.

### Recommendation
Inside `setEpochParams`, after updating `epochDuration`/`bufferPeriod`, re-derive the scaled APR from the stored unscaled APR (`IdleCreditVault(strategy).setAprsWithBuffer(unscaledApr, _epochDuration, _bufferPeriod)`), mirroring the fix applied in `stopEpochWithDuration`. Alternatively, restrict `setEpochParams` to only be callable via `stopEpochWithDuration` where the rescale already happens, or revert if `requestWithdraw`-relevant state exists when parameters change.

### Proof of Concept
Foundry fork test (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testSetEpochParamsLeavesStaleScaledApr() external {
    uint256 amount = 10_000 * ONE_SCALE;
    // buffer=5d, epoch=30d, apr=initialProvidedApr (already configured in setUp)
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // epoch 0 runs and stops; scaledApr now encodes apr*(30+5)/30
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // honest manager retunes duration during buffer: 30d -> 90d, buffer unchanged
    vm.prank(manager);
    cdoEpoch.setEpochParams(90 days, 5 days);   // no APR rescale happens

    // attacker (this contract, KYC'd lender) requests full withdraw in the buffer
    uint256 trancheBal = IERC20(AAtranche).balanceOf(address(this));
    uint256 requested = cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));

    // correct interest should be principal * apr * 90/365
    // stale math gives principal * apr * (35/30) * 90/365 * (90/95)... i.e. ~10.5% excess
    uint256 principal = trancheBal * cdoEpoch.tranchePrice(address(AAtranche)) / ONE_TRANCHE_TOKEN;
    uint256 fairInterest = principal * (initialProvidedApr / 100) * 90 days / (365 days * ONE_TRANCHE_TOKEN);
    assertGt(requested, principal + fairInterest, "receipt inflated by stale scaledApr");

    // next start/stopEpoch funds the inflated receipt via pendingWithdraws,
    // overcharging the borrower / under-collateralizing remaining LPs
}
```

Uncertainty note: exact percentage depends on deployed `bufferPeriod`; the PoC demonstrates directionality. With `bufferPeriod == 0` the stale-APR effect on `epochDuration` changes vanishes, so the finding requires `bufferPeriod > 0` (the default init is 5 days).

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
  }
