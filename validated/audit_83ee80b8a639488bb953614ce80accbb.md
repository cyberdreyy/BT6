The `delete_member` function at line 356-379 only removes confirmations for requests that were originally *created* (added) by the departing member (filtered via `r.member == member`, i.e., the request submitter). It never scans `confirmations` sets of *other* pending requests to strip out the departing member's signature. ### Title
Multisig executes requests below live-member confirmation threshold due to stale confirmations from removed members - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` at [1](#0-0)  counts confirmations toward `num_confirmations` purely from the `confirmations` `HashSet<String>` recorded per request, without re-validating that each confirming identity is still present in `self.members`. `delete_member`, at [2](#0-1) , only purges confirmations for requests that the removed member itself originated (`r.member == member`); it never removes the departing member's entry from the confirmation sets of other pending requests they had confirmed.

### Finding Description
The intended custody/authorization binding is: `confirmations counted == confirmations from current live members`. This binding is broken as follows:

1. Member `A` calls `add_request` creating request `R` (e.g., a `Transfer` or `AddKey` action) — `self.confirmations.insert(&request_id, &HashSet::new())` at [3](#0-2) .
2. Member `B` calls `confirm(R)`; since threshold isn't yet reached, `B`'s identity is inserted into `confirmations[R]` at [4](#0-3) .
3. Separately, the multisig members execute a `DeleteMember { member: B }` request through `execute_request` → `delete_member`. This routine only removes requests where `r.member == member` (requests *created* by `B`), and only strips confirmations tied to those specific requests, at [5](#0-4) . Request `R` (created by `A`, merely confirmed by `B`) is untouched — `B`'s stale confirmation remains inside `confirmations[R]`.
4. `B` is now removed from `self.members` (and their access key deleted), no longer a "live" member with a valid custody claim.
5. Later, member `C` calls `confirm(R)`. The check `confirmations.len() as u32 + 1 >= self.num_confirmations` at [6](#0-5)  counts `B`'s stale confirmation plus `C`'s new one, reaching `num_confirmations` and executing `R` — even though only `C` (and possibly `A`, if `A` confirmed too) are still live members.

Equality before attacker action: `confirmations counted in confirmations[R] == confirmations from members ⊆ self.members`.
Equality after `DeleteMember{B}` executes: `confirmations counted in confirmations[R] ⊇ {B} ∪ (confirmations from current self.members)`, i.e., the count is inflated by removed members whose authorization should no longer be valid.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." A request (fund transfer, `AddKey`/`AddMember`/`DeleteMember`, `FunctionCall`, etc.) can execute with fewer *currently authorized* confirmations than `num_confirmations` truly requires, because stale confirmations from members who have since been removed still count toward the threshold. This can be leveraged to move funds or change multisig membership/keys with insufficient live-member consensus — an authorization boundary violation on custody of the multisig's NEAR balance and control.

### Likelihood Explanation
This requires no attacker-privileged access beyond being (at some point) a legitimate confirming member before removal — a realistic operational scenario for any K-of-N multisig that rotates membership (e.g., replacing a compromised/departing signer), which the contract's own `DeleteMember` action is explicitly designed to support. Any request left pending (not yet reaching threshold) at the time a confirming member is removed is vulnerable; no special timing race or malicious deployment is needed, only routine member-list evolution combined with normal request pendency.

### Recommendation
When executing `DeleteMember`, iterate over all pending requests' `confirmations` sets (not only ones the removed member authored) and strip the removed member's identity from every set; alternatively, re-validate at `confirm()` time (and at threshold-check time) that every entry in `confirmations[request_id]` still belongs to `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new([A, B, C, D], 3)`.
2. `A` calls `add_request(R)` (e.g. `Transfer` to attacker-controlled receiver).
3. `B` calls `confirm(R)` → `confirmations[R] = {B}`.
4. Members reach 3-of-4 threshold on a separate `DeleteMember{member: B}` request and execute it — `B` is removed from `self.members`, but `confirmations[R]` (belonging to `R`, authored by `A`, not `B`) is left untouched per [5](#0-4) .
5. `C` calls `confirm(R)` → `confirmations[R].len() + 1 == 2 + 1 == 3 >= num_confirmations(3)` → `R` executes via `execute_request`, transferring funds, despite only `A` (creator, uncounted in `confirmations`) and `C` being live confirmers — effectively 2 live-member approvals executing a 3-of-4 policy request.

        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
