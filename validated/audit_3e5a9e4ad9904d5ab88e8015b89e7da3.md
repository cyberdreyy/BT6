### Title
`get_builder_withdrawals` commits an uncapped withdrawal amount while `apply_withdrawals` caps the balance deduction, minting Gwei paid to a fee recipient beyond the builder's actual stake — ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builder_withdrawals` copies `withdrawal.amount` from `state.builder_pending_withdrawals` verbatim into the committed `Withdrawal` object, without ever checking it against the builder's actual balance or tracking a running balance across multiple pending withdrawals for the same builder. `apply_withdrawals`, however, caps the *balance deduction* with `min(withdrawal.amount, builder_balance)`. Because the execution layer must pay out exactly what the block committed to (the uncapped `Withdrawal.amount`), while the beacon state only deducts the capped amount, ETH can be paid to a `fee_recipient` in excess of what was ever deducted from the builder's stake — a net Gwei-creation bug, structurally identical to the `StargateStrategy._withdraw` flaw where the code assumed a requested amount and an actually-available amount were equal.

### Finding Description
Compare the validator-withdrawal path with the builder-pending-withdrawal path in `specs/gloas/beacon-chain.md`:

Validator sweep and partial withdrawals (inherited from Capella/Electra) always compute the *current* balance net of all prior withdrawals already queued in the same block, and cap the amount before creating the `Withdrawal`: [1](#0-0) [2](#0-1) 

This guarantees `Withdrawal.amount <= balance_after_prior_withdrawals`, so what the execution layer is told to pay always equals what the beacon state actually deducts.

`get_builder_withdrawals`, however, does none of this. It appends the raw pending-withdrawal amount with no capping and no running-balance tracking across multiple entries for the same builder: [3](#0-2) 

The only capping in the entire path happens later, inside `apply_withdrawals`, and it only affects `state.builders[builder_index].balance` — it does not (and cannot, since `payload_expected_withdrawals`/the execution payload has already been fixed by `get_expected_withdrawals`) reduce the amount that the execution layer will actually pay to `fee_recipient`: [4](#0-3) 

`process_withdrawals` binds the committed withdrawal list to the payload before applying it, and the execution layer is required to honor exactly that list: [5](#0-4) 

### Impact Explanation
Consider a builder with `balance = 10 ETH` and two entries in `state.builder_pending_withdrawals` for the same `builder_index`, each requesting `8 ETH` (e.g. from two separate payments owed to the same builder that were queued in the same slot, capped individually at `MAX_WITHDRAWALS_PER_PAYLOAD - 1` in `get_builder_withdrawals`):

- `get_builder_withdrawals` emits two `Withdrawal` objects, `amount=8 ETH` each, total `16 ETH` committed to the execution payload for `fee_recipient`.
- `apply_withdrawals` runs sequentially:
  - First withdrawal: `builder_balance = 10`, deducts `min(8, 10) = 8` → balance becomes `2`.
  - Second withdrawal: `builder_balance = 2`, deducts `min(8, 2) = 2` → balance becomes `0`.
- Total Gwei deducted from the builder in `state.builders[*].balance` = `10`.
- Total Gwei that the execution layer is committed to pay to `fee_recipient` (per the `Withdrawal` list the block must honor) = `16`.

This is a `6 ETH` (`6,000,000,000` Gwei) discrepancy: ETH paid out to a non-owner (`fee_recipient`) that was never backed by any validator/builder balance — a direct Gwei-creation bug, breaking the beacon chain / execution layer total-supply equality. This satisfies the "Critical: Gwei created ... paid to a non-owner" impact class.

### Likelihood Explanation
This requires only that `state.builder_pending_withdrawals` contain more than one entry for the same `builder_index` whose amounts sum to more than the builder's current balance, within the same slot's processing window (bounded by `MAX_WITHDRAWALS_PER_PAYLOAD - 1`). Nothing in `settle_builder_payment` / `process_parent_execution_payload` (the code appending to `builder_pending_withdrawals`) appears to enforce that the sum of all pending entries for one builder can never exceed that builder's balance at enqueue time — each entry is appended independently based on `parent_bid.value`, a value fixed at bid time, not validated against the builder's balance at withdrawal-processing time. This is a spec-level (not implementation-detail) omission reachable purely through normal, honest state transitions (no malicious peer, coalition, or client bug required) — an honestly-processing consensus client following the spec text verbatim would produce this outcome.

### Recommendation
`get_builder_withdrawals` should track a running balance per builder (analogous to `get_balance_after_withdrawals` for validators) and cap each emitted `Withdrawal.amount` at `min(pending.amount, remaining_builder_balance)` at the time the `Withdrawal` object is constructed — not merely at `apply_withdrawals` time. This ensures the amount the execution layer is committed to pay always equals the amount actually deducted from the builder's stake.

### Proof of Concept
Given (informal, using spec pseudocode/state):
```
state.builders[B].balance = 10_000_000_000            # 10 ETH
state.builder_pending_withdrawals = [
    BuilderPendingWithdrawal(builder_index=B, fee_recipient=F, amount=8_000_000_000),
    BuilderPendingWithdrawal(builder_index=B, fee_recipient=F, amount=8_000_000_000),
]
```
Call `get_builder_withdrawals(state, idx, [])`:
- Iteration 1: appends `Withdrawal(validator_index=conv(B), address=F, amount=8_000_000_000)`
- Iteration 2: appends `Withdrawal(validator_index=conv(B), address=F, amount=8_000_000_000)`
- No check against `state.builders[B].balance` is ever performed in this function. [6](#0-5) 

These two `Withdrawal` objects (total `16 ETH`) become part of `expected.withdrawals`, and `process_withdrawals` sets `state.payload_expected_withdrawals` to exactly this list — which the execution layer is bound to pay in full to `F`: [7](#0-6) 

Then `apply_withdrawals` only deducts `10 ETH` total from `state.builders[B].balance` (saturating), per: [8](#0-7) 

Net result: `16 ETH` paid to `F` on the execution layer, but only `10 ETH` ever deducted from any account in the beacon state — `6 ETH` created out of nothing.

def get_balance_after_withdrawals(
    state: BeaconState,
    validator_index: ValidatorIndex,
    withdrawals: Sequence[Withdrawal],
) -> Gwei:
    withdrawn = sum(
        withdrawal.amount
        for withdrawal in withdrawals
        if withdrawal.validator_index == validator_index
    )
    return state.balances[validator_index] - withdrawn

```python
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
```
