### Title
Instant-withdraw receipts keyed to a pre-default epoch skip the recovery haircut and are paid at par - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` indexes instant-withdraw receipts per epoch (`instantWithdrawsRequestsByEpoch`), but the default-recovery path only ever looks at `instantWithdrawClaimsByEpoch[epochNumber]` — the single current/default epoch. An attacker who times `requestInstantWithdraw` so that its receipt is recorded in an epoch boundary slot *before* the defaulted epoch gets that unfunded receipt paid 1:1 after `finalizeDefaultRecovery`, while same-epoch claimants take a `defaultRecoveryPrice` haircut. This is the credit-vault analog of CVE-2017-9469's off-by-one read (terminating quote searched one byte before the buffer): the recovery basis reads only the current epoch bucket and misses obligations sitting one epoch slot earlier.

### Finding Description
`requestInstantWithdraw` records the receipt under `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and increments the aggregate `instantWithdrawClaimsByEpoch[epochNumber]` plus global `pendingInstantWithdraws` (IdleCreditVault.sol:367-374). If the CDO cannot fund the instant request before the epoch rolls over (instant delay not elapsed, or insufficient prefunded liquidity), `pendingInstantWithdraws` stays non-zero while `epochNumber` is bumped by `deposit()` during `stopEpoch` (line 610). The receipt is now keyed to a stale epoch `N`, while the contract is in epoch `N+1`.

When the borrower then defaults and `finalizeDefault` → `finalizeDefaultRecovery` runs in epoch `N+1`:

- `defaultPendingClaimBasis()` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — i.e., epoch `N+1` claims — to the haircut basis (line 647). The epoch-`N` receipt that is still part of `pendingInstantWithdraws` is excluded from `totalBasis`, so `defaultRecoveryPrice` is computed without it.
- `_defaultPrefundedInstantReserve()` computes the already-funded reserve as `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` (lines 719-721). Because the epoch-`N` claim inflates `pendingInstantWithdraws` but not `instantWithdrawClaimsByEpoch[N+1]`, the prefunded reserve is *understated* (or driven to zero), pushing what should be reserved cash out of the recovery bucket.
- On `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (line 844). The attacker's epoch-`N` receipt survives in `instantWithdrawsRequests[_user]` and is then burned and paid **at par** via `_transferFundedClaim` (lines 387-392), against the contract's non-reserve underlying balance.

The per-epoch "one slot early" indexing means the obligation was never haircut in the basis yet is still paid in full, spending underlying that belongs to funded normal withdraw claimants or recovery dust.

### Impact Explanation
Direct theft with quantified magnitude: the attacker receives `instantAmount` at par instead of `instantAmount * defaultRecoveryPrice / RECOVERY_FULL`. With e.g. a 50% recovery price, a 100k-underlying instant request yields a 100k payout instead of 50k — the excess 50k comes out of the funded-claim cash (`balance - defaultRecoveryReserve`), i.e., other users' already-funded withdraw receipts, or leaves the contract insolvent for them (permanent freezing of their claims). The attacker is an ordinary KYC-passed lender; no privileged role is needed. All existing guards pass: `_transferFundedClaim`'s reserve check only protects `defaultRecoveryReserve`, not the funded bucket; `_ensureDefaultRecoveryInitialized` only requires `pendingInstantWithdraws == 0` at init time, not at default time.

### Likelihood Explanation
Requires `pendingInstantWithdraws` to remain non-zero across an epoch boundary, which occurs whenever `instantWithdrawDelay` exceeds the remaining epoch time or the CDO lacks cash at `stopEpoch` — a normal operating condition configured by `setInstantWithdrawParams`. It then needs a borrower default in a later epoch, which is precisely the scenario the recovery machinery exists for. The attacker's only action is timing a public `requestInstantWithdraw` call; they can even sandwich it so part of their receipt lands in each epoch.

### Recommendation
Make the default-claim basis epoch-agnostic for instant receipts: include the entire unfunded `pendingInstantWithdraws` (or track all unfunded per-epoch buckets, not only `epochNumber`) in `defaultPendingClaimBasis`, and iterate/clear every non-zero `instantWithdrawsRequestsByEpoch` entry in `_claimDefaultedInstantWithdrawRequest` rather than only `defaultEpoch`. Alternatively, key instant receipts to a single pending bucket instead of a per-epoch map so the boundary slot cannot escape the haircut.

### Proof of Concept
Foundry fork PoC sketch (against `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testInstantReceiptPrevEpochSkipsHaircut() external {
    // 1. Configure instant delay longer than remaining epoch time.
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(epochDuration + 1, type(uint256).max, false);

    // 2. Attacker deposits AA, then requests instant withdraw late in epoch N
    //    so the receipt is keyed to epoch N but never funded.
    _depositWithUser(attacker, 100_000 * ONE_SCALE, true);
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(IERC20(AAtranche).balanceOf(attacker), address(AAtranche));
    // pendingInstantWithdraws > 0, instantWithdrawClaimsByEpoch[N] > 0

    // 3. Epoch rolls over without funding the instant request -> epoch N+1.
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, apr, /* insufficient instant liquidity */);

    // 4. Borrower defaults in epoch N+1; manager finalizes with 50% recovery.
    _checkDefault();
    uint256 recovered = /* 50% of totalDefaultBasis */;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // 5. Attacker claims: epoch-N receipt bypasses defaultRecoveryEpoch haircut
    //    and is paid at par from the funded-claim balance.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(underlying.balanceOf(attacker) - balPre,
        100_000 * ONE_SCALE * creditVault.defaultRecoveryPrice() / 1e18,
        "epoch-N instant receipt overpaid at par");
}
```

Note: I could not fully trace `IdleCDOEpochVariant.stopEpoch`/`finalizeDefault` call ordering within the tool budget, so the exact PoC wiring (steps 3-4) should be validated against those functions, but the contract-side accounting gap — basis restricted to `instantWithdrawClaimsByEpoch[epochNumber]` while `pendingInstantWithdraws` and the payable remainder span older epochs — is directly visible in `IdleCreditVault.sol:644-649, 842-856, 387-392`.
