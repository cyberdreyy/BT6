### Title
Unfunded pending instant-withdraw receipts can be claimed immediately, draining funded withdraw reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays out the entire `instantWithdrawsRequests[_user]` aggregate through `_transferFundedClaim` without verifying that the receipt's epoch was actually funded by the borrower. Unlike the normal claim path, which gates on `epochNumber <= lastWithdrawRequest[_user]` (`IdleCreditVault.sol:326`), the instant claim path has no epoch/funding check at all — it only avoids spending `defaultRecoveryReserve`. This mirrors CVE-2026-60023: a "pending" item is retrievable through the single-item read/claim path because the visibility check lives on the parent aggregate, not on the item's own state.

### Finding Description
- `requestInstantWithdraw` mints a receipt and increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`). Funding only arrives when the CDO calls `collectInstantWithdrawFunds`, which pulls underlying from the CDO and decrements `pendingInstantWithdraws` (`IdleCreditVault.sol:398-403`).
- `claimInstantWithdrawRequest` then pays `instantWithdrawsRequests[_user]` in full via `_transferFundedClaim` (`IdleCreditVault.sol:380-393`), which reverts only if the payment would dip into `defaultRecoveryReserve` (`IdleCreditVault.sol:897-907`).
- Therefore a receipt created *after* the epoch's instant-withdraw funding was collected is still "pending" (its `pendingInstantWithdraws` contribution is unfunded), yet the claim path will pay it out of any non-reserve balance sitting in the vault. That balance is funded normal-withdraw claim money (`collectWithdrawFunds`, `IdleCreditVault.sol:411-430`) held for users who requested in prior epochs and haven't claimed yet.
- The CDO-side guard only checks `allowInstantWithdraw` (`IdleCDOEpochVariant.sol:975-979`), and `msg.sender` is passed through, so the receipt owner triggers this freely.

Attack sequence (instant-withdraw enabled, epoch running):
1. Victim requested a normal withdraw in epoch N; borrower funds it at `stopEpoch` → underlying sits in the vault as funded-but-unclaimed balance.
2. Attacker calls `requestInstantWithdraw` mid-epoch N+1. No funding is pulled for this receipt until the next epoch transition.
3. Attacker immediately calls `IdleCDOEpochVariant.claimInstantWithdrawRequest()`. The vault burns the receipt and transfers the full amount from the funded reserve via `_transferFundedClaim`.
4. When the victim later claims their funded withdraw, the vault is short → the victim's claim reverts (insolvency) or is paid by the next epoch's funding, i.e., direct theft of unclaimed funded proceeds.

### Impact Explanation
Direct theft / insolvency: the attacker extracts underlying equal to their unfunded instant receipt, backed by funded normal-withdraw claims belonging to other users. Loss is bounded by the funded-but-unclaimed balance in the vault, which can be the entire pending funded withdraw bucket.

### Likelihood Explanation
Requires `allowInstantWithdraw` enabled and an attacker able to call `requestInstantWithdraw` (KYC'd tranche holder) while funded claims sit idle — a common state between `stopEpoch` funding and user claims. No privileged action needed; sequencing is entirely around honest manager/borrower epoch calls.

### Recommendation
Gate `claimInstantWithdrawRequest` on funded status the same way `claimWithdrawRequest` gates on `epochNumber`: record the request epoch (already tracked in `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`) and only pay receipts whose epoch's `pendingInstantWithdraws` share was collected via `collectInstantWithdrawFunds`; revert or defer claims for the still-pending epoch.

### Proof of Concept
Foundry fork/unit PoC sketch:
```solidity
// setup: AA tranche, allowInstantWithdraw = true, epoch N stopped with
// victim's normal withdraw funded via collectWithdrawFunds -> vault holds underlying
// 1. startEpoch N+1 (borrower funds nothing extra for instant)
// 2. attacker: cdoEpoch.requestInstantWithdraw(attackerTranches, AATranche)
//    -> requestInstantWithdraw mints receipt, pendingInstantWithdraws += amount
// 3. attacker: cdoEpoch.claimInstantWithdrawRequest()
//    -> IdleCreditVault pays attacker from victim's funded balance
assertEq(underlying.balanceOf(attacker), attackerAmount);
// 4. victim: cdoEpoch.claimWithdrawRequest() -> reverts NotAllowed/insufficient balance
vm.expectRevert();
cdoEpoch.claimWithdrawRequest();
```

Uncertainty note: I could not fully verify in this iteration whether `IdleCDOEpochVariant.requestInstantWithdraw` restricts requests to the buffer period only; if instant requests are exclusively buffer-phase and always funded at the subsequent `startEpoch`, this analog weakens. If claims are nevertheless permitted while `pendingInstantWithdraws` contributions remain unfunded (e.g., partial borrower funding shortfall), the same broken invariant applies.
