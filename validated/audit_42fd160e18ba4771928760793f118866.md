### Title
Zip extraction (`extractZipSymlinkEntry`/`extractZipFileEntry`) lacks path-traversal/absolute-path validation, allowing writes outside the build/cache root - (File: helpers/archives/zip_extract.go)

### Summary
`extractZipSymlinkEntry` and `extractZipFileEntry` use the raw `zip.File.Name` from an attacker-supplied archive as the filesystem destination path with no normalization or containment check, unlike the sibling tar/zstd extractor which enforces a chroot-style prefix check. A job that controls cache/artifact zip content (e.g. via `cache: paths` restore or artifact download for a pipeline the attacker authors) can craft entries with `../` segments or platform path separators to write regular files or symlinks outside the intended extraction directory.

### Finding Description
`extractZipFile` (helpers/archives/zip_extract.go:61-83) dispatches on `file.Mode()&os.ModeType` and calls `extractZipSymlinkEntry`/`extractZipFileEntry` directly with `file.Name`, after only calling `os.MkdirAll(filepath.Dir(file.Name), 0o777)` [1](#0-0) . Inside `extractZipSymlinkEntry`, the destination is `os.Remove(file.Name)` followed by `os.Symlink(string(data), file.Name)` — both `file.Name` (the link path) and the symlink target content `data` (read straight from the archive entry bytes) are attacker-controlled with zero validation [2](#0-1) . `extractZipFileEntry` similarly opens `file.Name` for writing with no checks [3](#0-2) .

The only pre-extraction validation applied by `ExtractZipArchive` is `errorIfGitDirectory`, which only flags paths beginning with `.git` — this is a warning suppression mechanism for `.git` directories, not a path-traversal or absolute-path guard [4](#0-3) . There is no `filepath.Clean` + prefix check against the extraction root, no rejection of absolute paths, and no rejection of `..` segments in `helpers/archives/zip_extract.go` or `path_check_helper.go`.

This is called from `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go` (`extractor.Extract` → `archives.ExtractZipArchive`), which is reachable from the cache-extractor and artifact-extractor commands. `CacheExtractorCommand.Execute` resolves `wd` via `os.Getwd()` and passes it to `archive.NewExtractor(format, f, size, wd)` [5](#0-4) , but the legacy zip extractor ignores the `dir` argument entirely for path confinement — it never joins/validates against `e.dir`, unlike the tar/zstd extractor which explicitly does `path, err = filepath.Abs(filepath.Join(e.dir, hdr.Name))` and rejects escapes with a `HasPrefix` check [6](#0-5) . `ziplegacy`'s `Extract` simply calls `zip.NewReader` then `archives.ExtractZipArchive(zr)`, dropping `e.dir` on the floor [7](#0-6) .

Practically, extraction runs with the process cwd set to the job's build directory (`wd`), so a crafted zip entry named e.g. `../../../../tmp/some-helper-consumed-file` or an absolute path (`os.Symlink`/`os.OpenFile` accept absolute paths verbatim) can write or symlink outside the build directory to wherever the runner process has filesystem permissions — including paths later read by helper binaries, `.env` files, or temp scripts (e.g. a cache-extractor env file, custom_executor driver scripts, or any file consumed later in the job's lifecycle).

### Impact Explanation
On shell/custom/docker executors where the runner helper process has write access outside the strict build root (which is the normal case for shell executors and many custom executor configurations), an attacker who controls cache or artifact zip content can plant files/symlinks at fixed, predictable paths that later stages (helper scripts, env files consumed by subsequent commands, or other jobs sharing the same host/user) will read as trusted input. This can lead to secret exposure (e.g. overwriting/symlinking a path that is later read into job logs or variables) or execution in a stronger context if a later stage `source`s or executes a file at an attacker-controlled path. Impact severity is bounded by the runner process's own file permissions but the missing containment check is a clear, concrete regression relative to the tar/zstd extractor's explicit chroot enforcement.

### Likelihood Explanation
Any unprivileged pipeline author can supply a cache/artifact zip with crafted entry names — no special GitLab or admin privilege is required, only the ability to define `cache:`/`artifacts:` paths and control job output that becomes archived content (or, more directly, uploading a pre-built malicious cache archive is restored by a later job in the same project). The bug is 100% reproducible: any zip containing an entry name with `../` traversal or an absolute path will be extracted at that literal path with no rejection.

### Recommendation
In `helpers/archives/zip_extract.go`, before dispatching in `extractZipFile`, resolve the destination against the extraction root (mirroring `tarzstd_extractor.go`'s pattern: `filepath.Abs(filepath.Join(root, file.Name))` and reject if it doesn't stay within the root with `strings.HasPrefix`/`filepath.Rel` check), reject absolute paths in `file.Name`, and additionally validate the symlink target (`data` in `extractZipSymlinkEntry`) doesn't point outside the root or to a sensitive absolute path. Ensure `ziplegacy.extractor.Extract` actually threads `e.dir` through to `ExtractZipArchive`/`extractZipFile` so the root-confinement check has a concrete boundary to validate against, consistent with the tar/zstd extractor.

### Proof of Concept
Go unit test in `helpers/archives/zip_extract_test.go`:
1. Build an in-memory zip with an entry named `../outside/evil.txt` (regular file) and another entry that is a symlink named `linkname` whose target/content is `/etc/passwd` or a path outside a temp extraction dir.
2. Extract into a `t.TempDir()` subdirectory `root` using `ExtractZipArchive`.
3. Assert: `os.Stat(filepath.Join(filepath.Dir(root), "outside/evil.txt"))` exists outside `root` (traversal succeeded) — this should fail the test/invariant, i.e. `assert.NoError` currently succeeds when it should be rejected.
4. Assert: `os.Lstat(filepath.Join(root, "linkname"))` shows a symlink whose target lies outside `root` (containment invariant violated).
Expected fixed behavior: `ExtractZipArchive`/`extractZipFile` should return an error (or skip with a warning, similar to `.git` handling) for any entry whose resolved absolute path escapes the extraction root, and the PoC assertions above should then fail to find files outside `root`.

func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}

func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}

func isPathAGitDirectory(path string) bool {
	parts := strings.Split(filepath.Clean(path), string(filepath.Separator))
	if len(parts) > 0 && parts[0] == ".git" {
		return true
	}
	return false
}

func errorIfGitDirectory(path string) *os.PathError {
	if !isPathAGitDirectory(path) {
		return nil
	}

	return &os.PathError{
		Op:   ".git inside of archive",
		Path: path,
		Err:  errors.New("trying to archive or extract .git path"),
	}
}
