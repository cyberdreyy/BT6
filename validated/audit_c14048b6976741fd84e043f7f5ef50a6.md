### Title
External Initiator credentials can trigger job runs for any job by integer ID with no binding check to the job's configured external initiator - ([File: core/web/pipeline_runs_controller.go])

### Summary
The `POST /v2/jobs/:ID/runs` route is reachable by any of `AuthenticateExternalInitiator`, `AuthenticateByToken`, or `AuthenticateBySession`, and `PipelineRunsController.Create` only checks whether *some* authenticated user object is present (`auth.GetAuthenticatedUser`) before calling `prc.App.RunJobV2(ctx, jobID, nil)`. Because `auth.AuthenticateExternalInitiator` also populates `SessionUserKey` with a synthetic `UserRoleRun` user, an External Initiator credential is indistinguishable from a real user at this check, and `RunJobV2` is called with no reference to which External Initiator authenticated the request or to the job's webhook/EI spec.

### Finding Description
The router wires the trigger endpoint as: [1](#0-0) 

`AuthenticateExternalInitiator` sets both `SessionExternalInitiatorKey` and, critically, `SessionUserKey` to a synthetic run-role user: [2](#0-1) 

In `PipelineRunsController.Create`, the comment claims "only users are allowed to run jobs using int IDs - EIs not allowed", but the actual check `_, isUser := auth.GetAuthenticatedUser(c)` only tests for the presence of `SessionUserKey`, which is always set for EI-authenticated requests too (per the code above). The handler then calls `prc.App.RunJobV2(ctx, jobID, nil)` using only the `:ID` path parameter, with no reference to `SessionExternalInitiatorKey` or the job's declared External Initiator webhook spec: [3](#0-2) 

Because the intended EI-vs-job binding check (`c.MustGet(SessionExternalInitiatorKey)` cross-checked against the job's `ExternalInitiatorWebhookSpec`) is never performed, any valid EI credential (or any run-role/token/session-authenticated caller reachable at this route) can trigger a run for an arbitrary job ID, including jobs bound to a different External Initiator, simply by supplying that job's integer ID.

### Impact Explanation
An attacker holding valid credentials for External Initiator A can invoke `POST /v2/jobs/<job-of-EI-B>/runs` and successfully trigger a pipeline run for a job that is supposed to only be reachable by External Initiator B's webhook callback. This is an authorization bypass allowing unauthorized job-run triggering, matching the "unauthorized job run" bounty impact class. Depending on the job's task graph (e.g., on-chain writes, VRF, external adapter calls), this could cause unintended on-chain transactions or resource exhaustion.

### Likelihood Explanation
Requires only a valid External Initiator credential pair (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers) for any registered EI plus knowledge of the target job's integer ID (job IDs are often small sequential integers, and the job UUID/EI binding is not required for this endpoint). No admin/edit/session role is needed — the run-role synthetic user created for EI auth is sufficient to pass `auth.RequiresRunRole`. The path is directly reachable and repeatable with no rate/one-time constraints beyond the API rate limiter.

### Recommendation
In `PipelineRunsController.Create`, explicitly distinguish EI-authenticated requests from real user sessions/tokens (e.g., check `auth.GetAuthenticatedExternalInitiator(c)` separately from `auth.GetAuthenticatedUser`), and when the caller is an External Initiator, load the target job's `ExternalInitiatorWebhookSpec` and verify it references the exact `ExternalInitiator` set in `SessionExternalInitiatorKey` before calling `RunJobV2`. Reject with 403/404 on mismatch.

### Proof of Concept
1. Create two Webhook jobs, Job B bound to External Initiator EI-B and Job A bound to EI-A, via `POST /v2/jobs`.
2. Authenticate as EI-A using its `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers.
3. `POST /v2/jobs/<JobB.ID (int)>/runs` using EI-A's headers.
4. Assert current (vulnerable) behavior: HTTP 200 with a created pipeline run for Job B.
5. Assert expected (fixed) behavior: HTTP 403/404, and no pipeline run row is created for Job B under EI-A's request.
