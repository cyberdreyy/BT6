### Title
Debited `unstaked` balance survives a failing self-transfer with no restoration - (`staking-pool/src/internal.rs`)

### Summary
`internal_withdraw` decrements `account.unstaked` and `last_total_balance` and then issues a bare, fire-and-forget `Promise::new(account_id).transfer(amount)` with no `.then()` callback. [1](#0-0)  If that transfer receipt fails (which happens when the destination account no longer exists at execution time), the ledger reduction is never reverted, breaking the invariant that "NEAR leaving the pool for an account equals the `unstaked` the account was debited."

### Finding Description
The invariant to test is: `Δ(actual NEAR received by account_id) == Δ(account.unstaked debited) == Δ(last_total_balance)`.

`internal_withdraw` reads `account.unstaked`, asserts sufficiency and the unstaking-delay epoch, then unconditionally does:
```
account.unstaked -= amount;
self.internal_save_account(&account_id, &account);
...
Promise::new(account_id).transfer(amount);
self.last_total_balance -= amount;
``` [2](#0-1) 

`account_id` here is always `env::predecessor_account_id()` — the caller itself, not an attacker-chosen third party — so this is invoked identically from `withdraw(amount)` and `withdraw_all()` on the public entrypoints. [3](#0-2) [4](#0-3) 

Unlike the lockup contract's equivalent flow — which schedules the withdrawal transfer with an explicit `.then(ext_self_owner::on_staking_pool_withdraw(...))` callback that calls `is_promise_success()` before mutating any deposit accounting [5](#0-4)  — the staking pool's `internal_withdraw` has no such callback anywhere in the crate; the state mutation (`account.unstaked -=`, `last_total_balance -=`) happens synchronously and unconditionally regardless of whether the scheduled transfer receipt later succeeds or fails.

For the bare `Promise::new(account_id).transfer(amount)` to fail, `account_id` (the caller) must not exist by the time the transfer receipt is processed. Since `account_id` is always the transaction signer, this requires the attacker to delete their own account (a `DeleteAccount` action, which any unprivileged holder of a full-access key on their own account can send) timed so it lands before the pending transfer receipt executes. In that scenario the transfer fails, its deposit is refunded back to the staking-pool contract's own account balance (not credited to any tracked `unstaked` field), while `account.unstaked` and `last_total_balance` were already permanently decremented. The staking pool's actual on-chain balance therefore exceeds `last_total_balance`; the discrepancy is picked up as a "reward" by `internal_ping`'s reward-distribution logic on the next epoch transition, and gets redistributed to whichever accounts hold `stake_shares` at that time — not necessarily returned to the account it was debited from. Since the attacker created the pool "moments earlier" via the public `create_staking_pool` factory, they can arrange to be the sole or dominant `stake_shares` holder, letting them recapture the diverted amount (or as owner, some/all of it via the reward-fee-and-restake path) while the original debited `unstaked` entry is gone.

No guard in this path — `internal_ping`'s balance assert, `assert_self()`, `is_promise_success()` — is used to gate or reverse this, because no callback exists at all for `internal_withdraw`'s transfer.

### Impact Explanation
This produces an accounting divergence where `last_total_balance` (and the debited account's claim) is reduced but the actual NEAR is retained by the contract and later redistributed via reward accounting to current stakeholders rather than being lost outright. Depending on who ends up holding the redistributed shares, this can be leveraged by the attacker (as the pool's owner/staker) to recapture value that should be attributed to the deleted account's now-void `unstaked` claim — an accounting value diverging from reality that other parties (future delegators, the owner's reward fee) settle on, and money movement not authorized by the entitled party. This most closely matches the High-severity category ("an accounting value diverging from reality where another party settles on it") rather than a clean, repeatable Critical direct theft, because the funds are not straightforwardly extracted to an attacker-chosen third party in one atomic step — they re-enter the pool's reward pipeline first, and the eventual beneficiary distribution depends on pool state (shares) at the next `ping`.

### Likelihood Explanation
The precondition (racing a self-`DeleteAccount` transaction against the pool's own pending transfer receipt) is technically nontrivial to land deterministically cross-shard/cross-block, and the requirement that `account_id` in the failing transfer is always the caller's own account (not an arbitrary attacker-chosen target) limits the directness of the exploit compared to the framing in the question. It requires deploying/owning a fresh pool, staking, unstaking, waiting the 4-epoch delay, then timing a self-deletion — feasible for a patient, unprivileged attacker, but with real timing uncertainty and dependent on subsequent pool activity (a `ping`) to realize any benefit.

### Recommendation
Attach a `.then()` callback to the withdrawal transfer (mirroring the lockup contract's `on_staking_pool_withdraw` pattern) that checks `is_promise_success()` and restores `account.unstaked` and `last_total_balance` if the transfer failed, instead of mutating state unconditionally before the promise result is known.

### Proof of Concept
Using `near-sdk-sim` / `RuntimeStandalone`:
1. Deploy `staking-pool` fresh via `create_staking_pool`, deposit and stake NEAR from account `A`, `unstake`, advance 4 epochs.
2. Call `withdraw_all()` from `A`, then in the same/next block submit a `DeleteAccount` action for `A` before the scheduled transfer receipt executes.
3. Assert: (a) the transfer receipt fails (`A` no longer exists), (b) `last_total_balance` and the stored `account.unstaked` for `A` were nonetheless already decremented by `amount`, and (c) no compensating state restoration occurred — i.e. `last_total_balance` != actual queryable contract balance minus other accounts' claims, confirming NEAR left the recorded ledger without a matching delivery or restoration, per `staking-pool/src/internal.rs:42-68`.

    pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        assert!(
            account.unstaked >= amount,
            "Not enough unstaked balance to withdraw"
        );
        assert!(
            account.unstaked_available_epoch_height <= env::epoch_height(),
            "The unstaked balance is not yet available due to unstaking delay"
        );
        account.unstaked -= amount;
        self.internal_save_account(&account_id, &account);

        env::log(
            format!(
                "@{} withdrawing {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );

        Promise::new(account_id).transfer(amount);
        self.last_total_balance -= amount;
    }
```

    /// Withdraws the entire unstaked balance from the predecessor account.
    /// It's only allowed if the `unstake` action was not performed in the four most recent epochs.
    pub fn withdraw_all(&mut self) {
        let need_to_restake = self.internal_ping();

        let account_id = env::predecessor_account_id();
        let account = self.internal_get_account(&account_id);
        self.internal_withdraw(account.unstaked);

        if need_to_restake {
            self.internal_restake();
        }
    }

    /// Withdraws the non staked balance for given account.
    /// It's only allowed if the `unstake` action was not performed in the four most recent epochs.
    pub fn withdraw(&mut self, amount: U128) {
        let need_to_restake = self.internal_ping();

        let amount: Balance = amount.into();
        self.internal_withdraw(amount);

        if need_to_restake {
            self.internal_restake();
        }
    }
