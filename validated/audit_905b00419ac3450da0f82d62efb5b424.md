### Title
Untrusted ERC4626 share-price feeds epoch accounting: vault inflation attack fabricates vault loss and freezes/wipes tranche NAV - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The Ostium exploit was not a signature forgery — it was a *trusted price input* accepted without any sanity check, used directly to settle payouts. The closest analog in idle-tranches is `ProgrammableBorrower`, which prices the entire epoch off a single unprivileged-influenceable value: `vault.convertToAssets(shares)` inside `_currentVaultAssets()` [1](#0-0) . That value drives `_vaultNetInterest()` / `totalInterestDueNow()` [2](#0-1) , which `IdleCDOEpochVariant` reads to settle the epoch and mint interest. An attacker who is merely "a user of the programmable borrower's ERC4626 vault" can execute the classic share-price inflation (donation/first-depositor) attack so that the facility's deposit mints a near-zero share count, fabricating a vault "loss" equal to essentially the whole facility deposit — exactly the Ostium shape: the system trusts an authorized-looking number and settles real accounting against a fabricated value.

### Finding Description
`onStartEpoch` snapshots `epochStartVaultAssets` as the *asset amount* before depositing idle cash, then deposits via `vault.deposit` with **no minimum-shares / slippage bound** [3](#0-2) [4](#0-3) . All subsequent PnL is measured as `convertToAssets(shares) + epochWithdrawnFromVault - (epochStartVaultAssets + epochDepositedToVault)` [5](#0-4) .

Attack sequence (epoch in **buffer** phase, programmable mode, interest-minted):

1. Attacker, as an ordinary ERC4626 vault user, inflates the vault's share price (first-depositor/wei-share + direct asset donation to the vault, the standard ERC4626 inflation attack).
2. Honest owner calls `startEpoch` → `onStartEpoch` records `epochStartVaultAssets` in *asset* terms, then `_depositToVault` mints ProgrammableBorrower ≈0 shares for the whole pool balance.
3. `_currentVaultAssets()` now returns ≈0 while `epochStartVaultAssets` holds the full deposit → `vaultLoss()`/`totalInterestDueNow()` report a fabricated loss ≈ entire facility TVL.
4. At `stopEpoch` / `_updateAccounting`, that fabricated loss is treated as real: it exceeds `lossToleranceBps`, exhausts `lastNAVBB`, and hits the `nav == 0`/BB-exhausted branch → `revert Default()` or `_emergencyShutdown(true)` [6](#0-5) . All lender withdrawals freeze, and if `skipDefaultCheck` is set, the BB tranche is crystallized to `priceBB = 0` — a permanent, real loss booked against junior holders on a price that was never real (BTC at $5,000 → $60,000 analog).

No existing guard stops it: `_skimDonatedAssets` only protects the CDO's own `token` balance, not the external vault's share price; the `Default` revert is precisely the *harm mechanism*, not a mitigation; there is no bound on `convertToAssets` output relative to `epochStartVaultAssets`, just as Ostium had no bound on the reported BTC price.

### Impact Explanation
Direct, quantified impact: for a facility holding `T` underlying, the fabricated `vaultLoss ≈ T` (donation cost to attacker is small — typically ~1 share's worth of donation amplification, not `T`). Result is either (a) permanent freezing of the full pool via `Default`/emergency shutdown pending governance intervention, or (b) actual loss socialization that zeroes `lastNAVBB` and `priceBB`, permanently destroying junior tranche holders' claims [7](#0-6) . Mirrors Ostium's $23.75M payout on a fabricated price: here the vault's entire NAV is settled against a fabricated price.

### Likelihood Explanation
Requires only that the chosen ERC4626 vault is susceptible to share-price inflation (common for low-liquidity or newly deployed vaults lacking virtual shares/dead-share protection) and that the attacker can transact as an ordinary vault depositor — explicitly an allowed unprivileged role. No privileged role is involved; `startEpoch`/`stopEpoch` callers remain honest and merely sequence around the manipulated input. Likelihood is moderate: it depends on vault choice (`setVault` is owner/manager gated), but the code performs zero validation of the external price at either deposit or accounting time — the same "assumed trusted" posture Ostium documented for its keepers.

### Recommendation
Bound the trusted input, in both directions:
- In `_depositToVault`, require a minimum share output: `require(shares >= vault.convertToShares(_assetAmount) * maxSlippageBps / BPS)` or compare post-deposit `convertToAssets(shares)` against `_assetAmount` and revert on a deviation beyond a tolerance.
- In `_vaultNetInterest`, sanity-check `loss` against a configured `maxVaultLossBps` of `principalAssets`; values beyond it should route to a pauseable review path rather than directly into tranche loss accounting.
- Prefer vaults with dead-share/virtual-share inflation protection, and document that the vault's `convertToAssets` is a security-critical oracle input — the same lesson Ostium's Immunefi scope failed to apply.
