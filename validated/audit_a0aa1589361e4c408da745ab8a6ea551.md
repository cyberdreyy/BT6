### Title
Confidential Transfer `Withdraw` parser mislabels a proof context account as `owner`/omits it when the supplied account list is shorter than the proof offsets imply - ([File: transaction-status/src/parse_token/extension/confidential_transfer.rs])

### Summary
The `ConfidentialTransferInstruction::Withdraw` branch derives which `account_indexes` slot maps to `instructionsSysvar`, `equalityProofContextStateAccount`, `rangeProofContextStateAccount`, and finally `owner` purely from a running `offset` counter and generic length guards (`offset < account_indexes.len().saturating_sub(1)`), rather than validating that the account list actually contains a slot for every context account implied by `equality_proof_instruction_offset == 0` / `range_proof_instruction_offset == 0`. An attacker who crafts the instruction's account list to be exactly the `check_num_token_accounts` minimum (4 accounts) while setting both offsets to `0` (declaring two `ContextStateAccount`s) causes the parser to silently drop the `rangeProofContextStateAccount` field and instead label that same account slot as `owner`.

### Finding Description
In `parse_confidential_transfer_instruction`, the `Withdraw` arm at [1](#0-0)  walks `offset` starting at 2 and conditionally consumes one account per branch (`instructionsSysvar`, then `equalityProofContextStateAccount` if `equality_proof_instruction_offset == 0`, then `rangeProofContextStateAccount` if `range_proof_instruction_offset == 0`), gated only by `offset < account_indexes.len().saturating_sub(1)`. Afterwards, `parse_signers(map, offset, ...)` labels `account_indexes[offset]` as `owner` [2](#0-1) .

`check_num_token_accounts(account_indexes, 4)` only guarantees 4 accounts minimum [3](#0-2) , but a correct 4-account layout only matches the "no sysvar, no context accounts" case. If both `equality_proof_instruction_offset` and `range_proof_instruction_offset` are set to `0` (declaring two `ContextStateAccount`s, which semantically requires 5 accounts: `account, mint, eqCtx, rangeCtx, owner`) but the attacker supplies only 4 accounts, the bound check `offset < len - 1` (with `len == 4`) stops after consuming just one context slot (`equalityProofContextStateAccount = account_indexes[2]`), because at that point `offset == 3` and `3 < 3` is false. The loop never inserts `rangeProofContextStateAccount`, and the last account slot `account_indexes[3]` — which the attacker fully controls and can point at any pubkey, including one that has nothing to do with the authority/owner — is instead labeled `owner` by `parse_signers`.

This is a decoder misreporting bug: the JSON-parsed instruction reports a pubkey as `owner` when, per the encoded proof-offset semantics, that slot was declared to be (or is ambiguous with) a proof context account. The existing `test_withdraw` table only exercises account lists built by the real `inner_withdraw` helper, which always emits the semantically-correct number of accounts, so it never surfaces this attacker-controlled short-list case.

Because `transaction-status` parsing operates on transaction data already committed to a block (successful or not — this instruction need not execute successfully on-chain to be included and later fetched), a single unprivileged actor can submit one transaction containing this crafted instruction and then retrieve it via `getTransaction`/`getConfirmedTransaction` with `jsonParsed` encoding to trigger the misreporting.

### Impact Explanation
A single RPC client can cause `getTransaction`/`getConfirmedTransaction` (jsonParsed encoding) to return incorrect field-to-account mapping: an account is reported under the `owner` key when it was actually intended as `rangeProofContextStateAccount` (or, in the symmetric case, `equalityProofContextStateAccount`), while the true semantic content of that field is silently dropped from the output. This falls into the accepted "decoder ... misreporting" / "wrong ... account data returned" bounty category since downstream consumers (explorers, wallets, indexers) trust the JSON-parsed `owner` field for confidential-transfer withdrawals.

### Likelihood Explanation
Fully attacker-controlled and requires no special privileges: only a self-submitted transaction with a crafted `Withdraw` instruction (arbitrary account list length and arbitrary `equality_proof_instruction_offset`/`range_proof_instruction_offset` values in the instruction data) and a single subsequent `getTransaction` RPC call. The instruction does not need to execute successfully on-chain for the transaction (and thus the instruction bytes/account list) to be recorded and later parsed. This is deterministic and 100% repeatable.

### Recommendation
Instead of relying solely on the generic `offset < account_indexes.len().saturating_sub(1)` bound, compute the exact expected account count from the combination of `has_sysvar`, `equality_proof_instruction_offset == 0`, and `range_proof_instruction_offset == 0`, and validate `account_indexes.len()` against that exact expected count before emitting any field. If the account list is too short for the declared offsets, return `ParseInstructionError::InstructionNotParsable` rather than silently omitting the field and mislabeling the trailing slot as `owner`.

### Proof of Concept
```rust
// transaction-status/src/parse_token/extension/confidential_transfer.rs (test mod)
#[test]
fn test_withdraw_short_account_list_mislabels_owner() {
    use spl_token_2022_interface::extension::confidential_transfer::instruction::WithdrawInstructionData;

    // Build a Withdraw instruction whose data declares BOTH proofs as
    // ContextStateAccount (offset == 0), but only supply the minimum 4 accounts
    // (account, mint, eqCtx-slot-that-becomes-mislabeled-owner's-neighbor, victim_account).
    let account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let eq_ctx = Pubkey::new_unique();
    let victim = Pubkey::new_unique(); // attacker-controlled slot, NOT the real owner

    let data = WithdrawInstructionData {
        equality_proof_instruction_offset: 0,
        range_proof_instruction_offset: 0,
        ..Default::default() // amount/decimals/etc irrelevant for parsing
    };

    let instruction = Instruction::new_with_bytes(
        spl_token_2022_interface::id(),
        &encode_instruction(&data, ConfidentialTransferInstruction::Withdraw), // pseudo-helper
        vec![
            AccountMeta::new(account, false),
            AccountMeta::new_readonly(mint, false),
            AccountMeta::new_readonly(eq_ctx, false),
            AccountMeta::new_readonly(victim, false), // should be rangeProofContextStateAccount
        ],
    );

    let message = Message::new(&[instruction], None);
    let parsed = parse_token(
        &message.instructions[0],
        &AccountKeys::new(&message.account_keys, None),
    )
    .unwrap();

    // Bug: rangeProofContextStateAccount is silently missing ...
    assert!(parsed.info.get("rangeProofContextStateAccount").is_none());
    // ... and `victim` (meant to be the range proof context account) is
    // mislabeled as `owner`.
    assert_eq!(parsed.info["owner"], json!(victim.to_string()));
}
```
Expected (buggy) result: `rangeProofContextStateAccount` is absent and `owner == victim`, even though `victim` was never intended to be an authority/owner account — demonstrating the field-to-index mapping violation described in the invariant.
