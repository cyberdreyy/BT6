### Title
Cross-user response hijack via attacker-chosen `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each pending user callback in `h.savedCallbacks` keyed solely by `msg.Body.MessageId`, a value fully chosen by the requesting client and not scoped by sender/signer. An attacker who submits a request with the same `MessageId` as another in-flight user request overwrites that user's callback entry, causing the victim's response to be delivered to the attacker (or lost) instead.

### Finding Description
`MessageId` originates from `jsonRequest.ID`/`req.ID`, which is attacker-controlled JSON-RPC request ID data set by `ValidatedMessageFromReq` (`m.Body.MessageId = req.ID`) [1](#0-0)  and, for the legacy path, directly copied from the client-supplied message body in `gateway.ProcessRequest`/`Message.Validate` [2](#0-1) . `Message.Validate()` only checks length/format of `MessageId`, and computes `Sender` from the signature, but never ties `MessageId` uniqueness to `Sender` [3](#0-2) .

In `HandleLegacyUserMessage`, the pending callback is unconditionally stored keyed only by `msg.Body.MessageId`: [4](#0-3) 
There is no check for an existing entry before the assignment — a second request with the same `MessageId` silently overwrites the first user's `savedCallback` (which holds a reference to the first user's `handlers.Callback`, i.e., their HTTP response channel). When the DON later responds, `handleWebAPITriggerMessage` looks up and deletes the map entry by `MessageId` and invokes whichever callback is currently stored: [5](#0-4) 

Exploit flow: Attacker A sends request R1 with `MessageId=X`; before nodes respond, Attacker/legit user B sends R2 also with `MessageId=X` (same or different sender address — nothing scopes the key by sender). B's entry overwrites A's in `savedCallbacks[X]`. When node responses for `X` arrive (whichever request they correspond to, since both were forwarded to the DON with `MessageId=X`), only the fields in the map (B's callback) fire, so A's HTTP client hangs until callback timeout/expiry (`h.pruneCallbacks`) while B is able to receive a response for a request they may not have legitimately triggered (or intercept/consume A's response if the DON responds to A's request body but keyed by the shared MessageId). The DON is trusted, but the vulnerability lies entirely in gateway-side multiplexing of untrusted, attacker-chosen `MessageId` without per-sender scoping — no signature or auth check anywhere prevents two different senders (or the same sender) from choosing an identical `MessageId`.

### Impact Explanation
This is a cross-user response confusion / hijack: one user's pending webAPI trigger response can be silently redirected to another user (or dropped, causing denial of response for the victim). This matches the "cross-user response confusion" bounty impact class explicitly listed as in-scope — no funds are moved and no keys are disclosed, but request/response isolation between unprivileged users is broken, and a victim's response can be captured by an attacker.

### Likelihood Explanation
- Precondition: attacker is any unprivileged client allowed to hit the gateway's `web_api_trigger` legacy endpoint — no special role, credential, or elevated permission is required.
- The attacker only needs to guess or predict another in-flight `MessageId` (e.g., low-entropy IDs like the sample script's default `"12345"`, or via observation/enumeration if the ecosystem uses predictable/sequential IDs) and fire a colliding request while the victim's request is still pending (default callback window is `defaultCallbackMaxAgeSec = 120` seconds) [6](#0-5) .
- Fully reproducible with a simple two-call unit test against `HandleLegacyUserMessage` with the same `MessageId` and different `Callback` instances — no timing race with real network components required since the map write is synchronous and unconditional.

### Recommendation
Scope the `savedCallbacks` key by both `MessageId` and the verified `Sender` address (e.g., `fmt.Sprintf("%s:%s", msg.Body.Sender, msg.Body.MessageId)`), and apply the same composite key when correlating DON responses back (the node response method/`Receiver` field would need to carry the sender too, or the DON dispatch loop needs to preserve association). Alternatively, reject the request outright with a distinct error if a non-expired entry for the same key already exists (`if _, exists := h.savedCallbacks[key]; exists { return error }`), and/or generate the storage key server-side.

### Proof of Concept
Go test plan (handler-level, no plan section requested but conceptually):
1. Construct handler via `NewHandler` with a fake `handlers.DON` recording `SendToNode` calls.
2. Build two valid signed `api.Message` legacy trigger requests, `msgA` and `msgB`, from two different private keys (different `Sender`s) but with identical `Body.MessageId = "X"`.
3. Call `handler.HandleLegacyUserMessage(ctx, msgA, callbackA)` then `handler.HandleLegacyUserMessage(ctx, msgB, callbackB)`.
4. Assert `len(h.savedCallbacks) == 1` and `h.savedCallbacks["X"].Callback == callbackB` (proving `callbackA` was overwritten/lost).
5. Simulate a node response by calling `handler.HandleNodeMessage` (or directly `handleWebAPITriggerMessage`) with `MessageId="X"`; assert `callbackB.SendResponse` was invoked (received the DON reply) while `callbackA.Wait` times out/never resolves — demonstrating cross-user response hijack.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
