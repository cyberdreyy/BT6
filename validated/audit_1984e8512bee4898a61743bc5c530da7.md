## Finding

An unprivileged operator can permanently freeze a staker's ability to withdraw stake from `staking_contract.move` by pointing their own commission `beneficiary_for_operator` at an address that is engineered to make `aptos_account::deposit_coins` abort forever. Since `distribute_internal`'s payout loop is all-or-nothing and is invoked as a mandatory prerequisite of `unlock_stake` and `switch_operator`, one poisoned recipient in the shared distribution queue blocks every other recipient (including the staker) from ever being paid or from ever leaving the poisoned staking contract.

### Title
Operator can permanently lock a staker's stake by poisoning the shared distribution queue with an unpayable beneficiary - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move)

### Summary
`staking_contract::distribute_internal` pays out every pending recipient in a `StakingContract`'s `distribution_pool` in a single atomic `while` loop using `aptos_account::deposit_coins`, exactly the push-based, all-or-nothing settlement pattern that the external `BoxExchange._payment()` report warns about. [1](#0-0) 

`aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient is not yet registered for the coin and has opted out of direct transfers via `set_allow_direct_coin_transfers(false)`: [2](#0-1) 

`set_allow_direct_coin_transfers` is a fully unprivileged, self-service entry function: [3](#0-2) 

### Finding Description
An operator controls their own commission destination via `set_beneficiary_for_operator`, independent of the staker's consent: [4](#0-3) 

Attack setup:
1. Operator creates/controls a fresh address `B` that has never registered a `CoinStore<AptosCoin>` and calls `set_allow_direct_coin_transfers(false)` from `B` (or simply never opts in — but by default `can_receive_direct_coin_transfers` returns true unless explicitly disabled, so the operator must actively disable it once from `B`).
2. Operator calls `staking_contract::set_beneficiary_for_operator(operator, B)`, redirecting all future commission distributions to `B`.
3. Operator earns any commission (e.g., via `request_commission` or automatically via `unlock_stake`/`add_stake` accounting), which enqueues a distribution entry for `B` in the shared `distribution_pool` of that `StakingContract`.
4. Any subsequent call that must clear the queue — `distribute`, or the mandatory pre-step inside `unlock_stake` and `switch_operator` — reaches `B` in the `while` loop and calls `aptos_account::deposit_coins(B, ...)`, which aborts because `B` is unregistered and has opted out of direct transfers.

`unlock_stake` and `switch_operator` unconditionally force a full distribution before doing anything else: [5](#0-4) [6](#0-5) 

Because the whole call is one Move transaction, the abort rolls back everything — the withdrawn coins are not lost per-transaction, but the queue entry for `B` can never be cleared (it is always `recipients[0]` again on retry, since nothing is ever committed). As a result:
- `distribute` can never succeed for anyone in that pool (staker's own pending stake distributions included).
- `unlock_stake` can never succeed, so the staker can never unlock/withdraw further stake from this contract.
- `switch_operator` can never succeed either, so the staker cannot even escape the malicious operator by switching operators.

This is a durable denial of the staker's withdrawal and operator-switch rights, caused entirely by an operator action the staker never approved, matching "Permanent lock or non-recoverable loss of claim rights in stake ... beneficiary ... flows" and "Wrong-role control over ... beneficiary state."

The same root cause (`aptos_account::deposit_coins` aborting inside an unskippable settlement loop) also affects `vesting::distribute`, whose shareholder loop uses the identical push pattern and can be poisoned via `set_beneficiary`/`vesting::update_operator`/beneficiary paths that route into `staking_contract`'s queue: [7](#0-6) 

### Impact Explanation
This is a high-impact, unprivileged, non-recoverable denial of stake withdrawal and operator-switch rights. A staker who never expected the operator's own beneficiary choice to matter to them can have their unlocked/inactive stake permanently stuck, with no code path in `staking_contract.move` to skip, requeue, or force-clear a poisoned distribution entry (no pull pattern, no per-recipient try/catch, no admin override). The staker's only avenue would be an off-chain governance/framework upgrade, not anything reachable from their own account.

### Likelihood Explanation
High likelihood: every action needed (`set_allow_direct_coin_transfers(false)`, `set_beneficiary_for_operator`, earning any commission) is a normal, permissionless entry function already exposed to operators, requiring no special privileges, races, or governance access — only an operator willing (or careless enough) to set an unregistered/opted-out address as their beneficiary.

### Recommendation
Adopt the pull-over-push pattern recommended in the external report for `staking_contract::distribute_internal` (and by extension `vesting::distribute`): instead of pushing coins to each recipient inline inside the settlement loop, credit an internal per-recipient claimable balance and let each recipient withdraw independently via a separate `withdraw`-style entry function. Alternatively, catch/ignore a failing `deposit_coins` for an individual recipient (skip and requeue) so that one broken recipient cannot block the entire pool's redemption loop, and ensure `unlock_stake`/`switch_operator` do not hard-depend on successfully clearing every unrelated recipient in the same pool.

### Proof of Concept
1. Staker calls `staking_contract::create_staking_contract(staker, operator, voter, amount, commission_percentage, seed)`.
2. From account `B` (fresh, never registered for `AptosCoin`), call `aptos_account::set_allow_direct_coin_transfers(B_signer, false)`.
3. Operator calls `staking_contract::set_beneficiary_for_operator(operator_signer, B)`.
4. Let validator earn rewards (`stake::end_epoch()` in test / normal epoch progression on chain) so the operator accrues commission; call `staking_contract::request_commission(operator_signer, staker, operator)` to enqueue the operator's commission distribution to `B` in `staking_contract.move`'s `distribution_pool`.
5. Fast-forward past lockup so the commission becomes withdrawable.
6. Staker calls `staking_contract::unlock_stake(staker_signer, operator, amount)` (or anyone calls `staking_contract::distribute(staker, operator)`).
7. Observe the transaction aborts inside `distribute_internal`'s `while` loop at `aptos_account::deposit_coins(B, ...)` with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`, and that every subsequent retry of `unlock_stake`, `distribute`, or `switch_operator` for this `(staker, operator)` pair fails identically, permanently.

    public entry fun set_beneficiary_for_operator(

        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.

                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );

    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
