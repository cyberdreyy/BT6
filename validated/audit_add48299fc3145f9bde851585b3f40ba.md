### Title
`grant_role_unchecked` accepts the zero address as a role member, silently bypassing the "last admin" safety check - ([File: crates/common/precompiles/src/b20_asset/logic/v1.rs])

### Summary
The reported bug class ("`transferOwnership` fails silently when passed the zero address, instead of reverting") reappears in the B20 asset/stablecoin precompile logic's role-management functions. `grant_role`/`grant_role_unchecked` never validate that `account != Address::ZERO`, unlike sibling functions (`approve`, `mint`, `transfer_inner`, `transfer_from`) in the very same files, which explicitly revert with `InvalidReceiver`/`InvalidSender`/`InvalidApprover` on `Address::ZERO`.

### Finding Description
`grant_role_unchecked` unconditionally sets the role bit and, for `DefaultAdmin`, increments `role_member_count`, with no check that `account` is non-zero: [1](#0-0) 

This is invoked by the externally reachable `grant_role` for any role (including `DefaultAdmin`), gated only by role-admin authorization, not by the identity of the target account: [2](#0-1) 

The "last admin cannot renounce" safety net relies purely on `role_member_count(role) == U256::ONE`: [3](#0-2) [4](#0-3) 

Because `Address::ZERO` can be granted the `DefaultAdmin` role, `role_member_count` can be silently inflated to include an address that can never be `msg.sender` of any externally-originated transaction. The remaining real admin can then revoke/renounce their own role — the count check (`== U256::ONE`) no longer matches "1 real admin", it now reads "2 members (1 real + 1 zero)", so the guard is bypassed and the last *usable* admin can remove themselves, leaving `DefaultAdmin` permanently held only by the unreachable zero address.

By contrast, transfer/mint/approve in the exact same file already treat zero-address inputs as invalid and revert, showing the codebase's established convention that this class of function must reject `Address::ZERO`: [5](#0-4) [6](#0-5) 

The same missing check exists identically in the B20 stablecoin logic (`v1`/`v2`) and the asset logic `v2`: [7](#0-6) [8](#0-7) [9](#0-8) 

### Impact Explanation
Once `DefaultAdmin` (or any role gating `pause`/`unpause`, `update_policy`, `set_role_admin`, `grant_role`/`revoke_role`) ends up held solely by `Address::ZERO`, every function requiring that role becomes permanently unreachable, because no signed transaction can ever originate from the zero address. This can permanently freeze a token's administrative controls — for example, an already-paused B20 token (via `PausableFeature::TRANSFER`) could never be unpaused again, and transfer/mint policies could never be updated, permanently locking user funds held in or governed by that token. This satisfies the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Triggering this requires only a legitimate role-admin (e.g., a `DefaultAdmin` holder) to call the externally exposed `grantRole` precompile entry point with `account = address(0)`, then revoke/renounce their own role — both are ordinary, unprivileged-at-the-protocol-level transactions signed by an EOA that merely happens to hold that token's admin role. This is the direct behavioral analog of the ICO report: a caller-supplied address parameter that should be rejected as zero is accepted and processed silently, and here it corrupts a security invariant (`role_member_count`) rather than merely losing ownership.

### Recommendation
Add a zero-address guard to `grant_role`/`grant_role_unchecked` (and equivalently for `set_role`/`set_role_admin` account parameters) across `b20_asset/logic/v1.rs`, `v2.rs` and `b20_stablecoin/logic/v1.rs`, `v2.rs`, reverting with an existing or new typed error (e.g., `InvalidReceiver`/`InvalidAccount`) when `account == Address::ZERO`, mirroring the pattern already used in `approve`, `mint`, and `transfer_inner` in the same files.

### Proof of Concept
1. Deploy a B20 asset/stablecoin token; `ADMIN` holds `DefaultAdmin` role, `role_member_count(DefaultAdmin) == 1`.
2. `ADMIN` calls `grantRole(DefaultAdmin_ID, address(0))`. `grant_role_unchecked` sets `has_role(DefaultAdmin, 0x0) = true` and bumps `role_member_count` to `2`, per [10](#0-9) .
3. `ADMIN` calls `renounceRole`/`renounceLastAdmin` (or is `revoke_role`'d): the guard `role_member_count(role)? == U256::ONE` in [11](#0-10)  now evaluates `2 == 1 → false`, so the revoke succeeds instead of reverting with `LastAdminCannotRenounce`.
4. `DefaultAdmin` is now held exclusively by `Address::ZERO`. No future transaction can satisfy `B20Guards::ensure_role`/`ensure_token_role` for that role, permanently disabling `update_policy`, `set_role_admin`, `grant_role`, `revoke_role`, and any pause/unpause path gated by `DefaultAdmin`.

```rust
    fn grant_role_unchecked(
        &self,
        token: &mut B20AssetToken<S, A>,
        role: B256,
        account: Address,
        sender: Address,
    ) -> Result<()> {
        if token.accounting().has_role(role, account)? {
            return Ok(());
        }
        token.accounting_mut().set_role(role, account, true)?;
        if role == B20TokenRole::DefaultAdmin.id() {
            let current = token.accounting().role_member_count(role)?;
            let next =
                current.checked_add(U256::ONE).ok_or_else(BasePrecompileError::under_overflow)?;
            token.accounting_mut().set_role_member_count(role, next)?;
        }
        token
            .accounting_mut()
            .emit_event(IB20::RoleGranted { role, account, sender }.encode_log_data())
    }
```

    fn renounce_last_admin(&self, token: &mut B20AssetToken<S, A>, caller: Address) -> Result<()> {
        let admin_role = B20TokenRole::DefaultAdmin.id();
        B20Guards::ensure_role(token, caller, admin_role)?;
        if token.accounting().role_member_count(admin_role)? != U256::ONE {
            return Err(BasePrecompileError::revert(IB20::NotSoleAdmin {}));
        }
        self.revoke_role_unchecked(token, admin_role, caller, caller)?;
        token
            .accounting_mut()
            .emit_event(IB20::LastAdminRenounced { previousAdmin: caller }.encode_log_data())
    }
