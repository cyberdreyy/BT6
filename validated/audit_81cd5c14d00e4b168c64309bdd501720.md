### Title
Non-deterministic / weight-driven regression of `parent_tenure_last_block` in `capitulate_miner_view` allows adoption of a stale, lower canonical tip - ([File: stacks-signer/src/v0/signer_state.rs])

### Summary
`LocalStateMachine::capitulate_miner_view` selects a new miner viewpoint from aggregated `StateMachineUpdate` messages using a height guard that only checks the signer's own recomputed height is **not less than** the candidate's claimed `parent_tenure_last_block_height`, and then final tie-breaking among qualifying candidates is done solely by the *tenure's burn-block height*, never by the candidate's `parent_tenure_last_block_height` itself. This lets a candidate that reports a regressed (lower) `parent_tenure_last_block`/height for the *same* tenure be adopted instead of the signer's own already-confirmed canonical value, if that stale candidate accumulates enough minority+attacker weight to cross the disagreement/agreement threshold.

### Finding Description
In `capitulate_miner_view` (`stacks-signer/src/v0/signer_state.rs`, lines 984-1115), for every `(address, update)` in `eval.address_updates` matching the global burn view, the code buckets `ActiveMiner` states by their **entire** `StateMachineUpdateMinerState` value (including `parent_tenure_last_block` and `parent_tenure_last_block_height`) into `miners: HashMap<_, weight>` [1](#0-0) . Once a bucket's weight reaches the disagreement threshold, the code recomputes the signer's own authoritative height via `get_parent_tenure_last_block` (which is `max(node tip, signerdb)` per its doc comment) [2](#0-1)  and only guards with:

```rust
if local_parent_tenure_last_block_height < *parent_tenure_last_block_height {
    // We haven't processed this stacks block yet.
    continue;
}
``` [3](#0-2) 

This guard only rejects candidates claiming a height the signer hasn't caught up to; it does **not** reject (and does not correct) a candidate whose claimed height is *lower* than the signer's own canonical view. Such a candidate is inserted into `potential_matches` keyed by `(tenure_burn_block_height, miner_state)` [4](#0-3) , and the final selection is:

```rust
potential_matches.sort_by_key(|(block_height, _)| *block_height);
let new_miner = potential_matches.last().map(|(_, miner)| (*miner).clone());
``` [5](#0-4) 

The sort key is only the tenure's burn-block height — never the candidate's `parent_tenure_last_block_height`. When two distinct `miner_state` values exist for the *same* tenure (one correct/higher, one stale/regressed, both surviving the guard above because the signer's local height is `>=` both), both entries share the same `block_height` sort key. Tie-break behavior then depends on the unspecified iteration order of the `HashSet<(u64, &StateMachineUpdateMinerState)>` that is collected into a `Vec` before sorting — Rust's `sort_by_key` is stable but the *input* order from a `HashSet` is not guaranteed, so the "last" (i.e., selected) entry among ties is not guaranteed to be the one with the higher `parent_tenure_last_block_height`.

The adopted `new_miner` (whichever is picked) is then installed verbatim — including its `parent_tenure_last_block`/height fields exactly as reported by the remote peers, not recomputed to the signer's local canonical max — into the signer's `current_miner` state in `capitulate_viewpoint` [6](#0-5) . This value subsequently gates block-proposal acceptance for that tenure's parent-tenure continuity checks.

An attacker who wins a single miner slot (or simply gossips a crafted `StateMachineUpdate` as a signer of their own weight) can craft an update reporting an artificially low `parent_tenure_last_block_height` for the *same* tenure_id that a threshold of honest-but-stale signers are also reporting (a natural byproduct of network propagation delay in a near-50/50 split). Adding the attacker's weight tips that minority bucket over `eval.reached_disagreement`/`reached_agreement`, causing it to enter `potential_matches` alongside the correct/higher bucket for the same tenure and burn height, at which point the tie-break is not height-aware.

### Impact Explanation
If the regressed candidate is selected, the signer's `current_miner.parent_tenure_last_block`/height is set below the signer's own already-confirmed canonical tip. Any subsequent `BlockProposal` for that tenure is checked against this regressed parent-tenure state, which can let the signer approve a block that does not build on/confirm the actually-canonical parent tip — a non-canonical continuation / silent reorg of already-signed blocks. This falls under the Critical category: a signer signing an invalid/non-canonical block, breaking canonicity/chain safety.

### Likelihood Explanation
Requires a split-view scenario where the same-tenure candidates are close to the disagreement/agreement threshold weight (near 50/50), a single attacker signer-weight contribution to tip the balance, and non-deterministic `HashSet`-derived tie ordering to favor the stale entry. This is plausible but probabilistic/non-deterministic rather than deterministically forced by the attacker — the attacker cannot guarantee which of the tied entries is picked, only increase the odds that the stale one crosses threshold and is available for selection. It is repeatable across capitulation checks (bounded by `capitulate_miner_view_timeout`) and costs only one miner/signer slot plus gossip, matching the attacker model.

### Recommendation
When building `potential_matches`, break ties by `parent_tenure_last_block_height` (or `parent_tenure_last_block`) as a secondary/primary sort key so the highest confirmed value always wins deterministically, and additionally clamp/reject any candidate whose `parent_tenure_last_block_height` is strictly less than the signer's own already-recorded canonical maximum (`max(node tip, signerdb)`) rather than only rejecting candidates the signer hasn't caught up to.

### Proof of Concept
Extend `check_capitulate_split_view_node_at_higher_height` in `stacks-signer/src/tests/signer_state.rs`:
1. Set up the node/signerdb tip strictly higher (canonical) `parent_tenure_last_block_height = H`.
2. Construct `eval.address_updates` with honest signers split so one bucket (weight just under threshold) reports the correct `ActiveMiner` state with height `H`, and inject one additional attacker-controlled update reporting the *same tenure_id* but a lower height `H' < H`, whose weight is enough to also cross `reached_disagreement`/`reached_agreement` for the `H'` bucket.
3. Call `capitulate_miner_view` repeatedly (or with a fixed/controlled `HashSet` ordering) and assert that the returned `new_miner`'s `parent_tenure_last_block_height` is never `< H`, i.e., always equals the local canonical max — the test should fail against current code by observing selection of `H'` in at least one ordering/run, demonstrating the guard does not enforce `adopted_height == max(node tip, signerdb)`.
