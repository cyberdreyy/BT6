### Title
Unprivileged ERC4626 vault user can permanently brick `stopEpoch` by making `vault.withdraw` revert, freezing all lender funds - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStopEpoch` calls `vault.withdraw(shortfall, ...)` whenever `shortfall <= _currentVaultAssets()`, and converts any revert into `StopEpochVaultLiquidityUnavailable`. The check uses `convertToAssets` (share valuation), not actual withdrawable liquidity (`maxWithdraw` / market liquidity). Any unprivileged user of the external ERC4626 vault can make `withdraw` revert while `convertToAssets` still prices the shares high — e.g. by borrowing out all liquidity in the underlying Morpho market(s) of a Gauntlet/MetaMorpho vault, or via a market with bad debt where liquidity never returns. Because the hook reverts before `IdleCDOEpochVariant.stopEpoch` reaches its `try this.getFundsFromBorrower(...)` block, the default path (`_handleBorrowerDefault`) is never reached, the epoch stays `isEpochRunning`, and every retry of `stopEpoch` reverts identically.

### Finding Description
Analog to CVE-2019-20812 (a failure-case path that spins/locks instead of completing): here the *failure branch* of the external liquidity recall is a hard revert that makes the only epoch-finalization entry point unusable.

In `IdleCDOEpochVariant.stopEpoch` (`contracts/IdleCDOEpochVariant.sol:395-404`), the hook is called *outside* the `try/catch`:

```solidity
if (!IProgrammableBorrower(_borrower()).onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)) {
  _handleBorrowerDefault(...);
  return;
}
```

In `ProgrammableBorrower.onStopEpoch` (`contracts/strategies/idle/ProgrammableBorrower.sol:239-253`):

```solidity
uint256 shortfall = _amountRequired - onHand;
if (shortfall > _currentVaultAssets()) return true;      // insolvency -> default path later
try vault.withdraw(shortfall, ...) { ... }
catch { revert StopEpochVaultLiquidityUnavailable(); }   // illiquidity -> revert, no default
```

The guard at line 245 compares the shortfall against `convertToAssets`, which counts *lent-out* assets. A Morpho-market borrower (unprivileged EOA, allowed attacker class: "a user of the programmable borrower's ERC4626 vault") can borrow all available liquidity in the vault's underlying markets, or the market can simply carry bad debt. `withdraw` then reverts on insufficient liquidity while `convertToAssets` still reports full value → `shortfall <= _currentVaultAssets()` → revert path.

Result: `stopEpoch` reverts forever. The escape hatches are all gated off the same stuck state:
- `setVault` reverts because `epochAccountingActive` is never cleared (it is only cleared at the end of the successful hook, `ProgrammableBorrower.sol:165`).
- `setBorrower` reverts for the same reason (line 181).
- `_handleBorrowerDefault` is unreachable — it requires either `onStopEpoch` returning `false` or a failure inside the `try this.getFundsFromBorrower` block, neither of which happens when the hook reverts.
- `pendingWithdraws` are only funded inside the successful `stopEpoch` via `collectWithdrawFunds`, so `claimWithdrawRequest` users can never be paid.
- Even `_isRequestingAllFunds` (pool closure) hits the same revert, so the honest manager cannot force a default/close.

### Impact Explanation
All TVL in the facility is frozen: pending withdraw receipts remain unfunded, new epochs cannot start, instant-withdraw funding (`getInstantWithdrawFunds` → `stopEpoch` flow) is blocked, and the default/recovery machinery (`finalizeDefault`, `defaultRecoveryReserve`) can never engage. If the underlying market illiquidity is permanent (bad debt), the freeze is permanent and the loss equals the full NAV still parked in the vault; if liquidity is restored later, it is still an attacker-controlled temporary freeze of user funds.

### Likelihood Explanation
Requires only an unprivileged EOA interacting with the external vault's underlying liquidity markets (borrowing remaining liquidity with collateral, or waiting for organic full utilization / bad debt). No privileged role needed. The cost to sustain the freeze is the borrow interest on the drained amount — small relative to freezing the entire credit facility.

### Recommendation
In `ProgrammableBorrower.onStopEpoch`, check *withdrawable liquidity* instead of (or in addition to) share valuation — e.g. `vault.maxWithdraw(address(this))` — and return `false` (letting IdleCDO run `_handleBorrowerDefault`) when the vault cannot actually pay, rather than reverting. Alternatively, let the `catch` return `false` so a persistent illiquidity degrades into a default + recovery haircut instead of an unrecoverable revert, and/or give the manager a way to force-default when the hook is stuck.

### Proof of Concept
A Foundry PoC follows the existing test `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable` (`test/foundry/ProgrammableBorrowerCreditVault.t.sol:372-399`) but makes the illiquidity persistent and demonstrates there is no escape:

```solidity
function testStopEpochPermanentlyBrickedByVaultIlliquidity() external {
    MockStopEpochLiquidityVault limitedVault = new MockStopEpochLiquidityVault(USDC);
    uint256 amount = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    vm.prank(manager);
    programmableBorrower.setVault(address(limitedVault));

    idleCDO.depositAA(amount);
    cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));
    _startEpochAndCheckPrices(0);

    uint256 pending = strategy.pendingWithdraws();
    // Attacker (unprivileged vault user / underlying-market borrower) drains liquidity:
    // convertToAssets still prices shares fully, but withdraw always reverts.
    limitedVault.setWithdrawLimit(0); // persistent: e.g. Morpho market fully borrowed / bad debt

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // stopEpoch can never succeed and can never fall through to _handleBorrowerDefault
    for (uint256 i; i < 3; i++) {
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        vm.prank(manager);
        cdoEpoch.stopEpoch(0, 0);
    }
    // even close-pool (request all funds) hits the same revert
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 1);

    assertFalse(cdoEpoch.defaulted());
    assertTrue(cdoEpoch.isEpochRunning());
    assertEq(strategy.pendingWithdraws(), pending); // receipts never funded

    // manager cannot migrate the vault: epochAccountingActive stuck true
    vm.expectRevert(NotAllowed.selector);
    vm.prank(manager);
    programmableBorrower.setVault(address(new MockStopEpochLiquidityVault(USDC)));

    // withdraw claimants are frozen
    vm.expectRevert(); // no funded pendingWithdraws
    cdoEpoch.claimWithdrawRequest();
}
```

Key asymmetry demonstrated: `convertToAssets` (used in the guard at `ProgrammableBorrower.sol:245`) overestimates true liquidity, so `withdraw` reverts, the default path at `IdleCDOEpochVariant.sol:398-404` is skipped because the revert precedes the `try`, and `setVault`/`setBorrower` are blocked by the permanently stuck `epochAccountingActive` flag.
