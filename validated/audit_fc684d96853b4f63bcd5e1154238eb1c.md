### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing request execution below the live member quorum - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` counts entries in the per-request `confirmations: LookupMap<RequestId, HashSet<String>>` set toward `num_confirmations` without verifying that every recorded confirmer is still a current member of `self.members`. `delete_member` only purges pending *requests created by* the removed member; it does not scan other pending requests' confirmation sets and strip the departing member's entry. As a result, a request can execute with fewer live, currently-authorized members approving it than the configured `num_confirmations` threshold — breaking the binding `confirmations actually held by live members == num_confirmations required`.

### Finding Description
`confirm()` at [1](#0-0)  only checks that the caller is *currently* a member (`assert_valid_request` → `current_member()`), and that the caller hasn't already confirmed; it then compares `confirmations.len() + 1 >= self.num_confirmations` to decide whether to execute. It never re-validates that the *other* entries already present in the `confirmations` set still correspond to current members.

`delete_member()` at [2](#0-1)  removes the member from `self.members` and cleans up only:
- pending requests where `r.member == member` (i.e. requests that member *created*), and
- that member's `num_requests_pk` entry.

It does not iterate `self.confirmations` to remove the departing member's confirmation string from *other* pending requests (created by someone else) that the member had previously confirmed via `confirm()` at [3](#0-2) .

Sequence that breaks the binding:
1. Multisig has members `{A,B,C,D}`, `num_confirmations = 3`.
2. `A` creates request `R` (a `Transfer`) via `add_request`.
3. `B` confirms `R` → `confirmations(R) = {B}` (1 < 3).
4. `C` confirms `R` → `confirmations(R) = {B, C}` (2 < 3, not executed).
5. Through the normal multisig governance flow, members vote to remove `C` (`DeleteMember{C}`), which succeeds because `members.len() - 1 (=3) >= num_confirmations (3)` per the check at [4](#0-3) . `C` is now removed from `self.members` and loses its access key, but `confirmations(R)` still contains `"C"` because `R` was created by `A`, not `C`, so it was never touched.
6. `D` confirms `R` → `confirmations(R).len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request(R)` runs, transferring funds.

At execution time, only `B` and `D` are actual live, current members who approved; `C`'s stale confirmation — from a member who has since been expelled — is what pushed the count over the threshold. The contract believed it had 3-of-N live approvals when it only had 2.

### Impact Explanation
This is a Critical-tier issue per the rubric: "a multisig request executed below threshold." The custody binding that the multisig is supposed to enforce — a `Transfer`, `FunctionCall`, `AddKey`, or `DeployContract` action requires `K` *currently authorized* members to approve — is violated. Funds (NEAR) held by the multisig account can be moved, or the account's key/code can be altered, with effectively fewer than `K` live approvals, undermining the entire security guarantee of the K-of-N scheme (`multisig/README.md` explicitly states "Any of the access keys or set of specified accounts can confirm, **until the required number of confirmation achieved**" — implying live confirmations, not stale ones).

### Likelihood Explanation
This does not require any external "unprivileged attacker" — it arises from the contract's own state-management bug during normal, expected multisig operations (member rotation while requests are in flight), which is a routine occurrence for any long-lived multisig (e.g. rotating a compromised or departing signer's key). No malicious member collusion beyond what the K-of-N scheme already assumes is required; the flaw is purely in the bookkeeping between `confirmations` and `members`, which is exactly the "confirmations counted versus live members" custody binding called out in scope. The scenario is easily reproducible deterministically given only routine sequencing of legitimate calls (`add_request`, `confirm`, `DeleteMember` request, `confirm` again).

### Recommendation
In `confirm()`, before comparing to `num_confirmations`, filter/recompute the confirmation count using only entries in `confirmations` that are still present in `self.members` (or lazily prune stale entries whenever confirmations are read/counted). Alternatively, in `delete_member()`, iterate all entries of `self.confirmations` (not just requests created by the removed member) and remove the departing member's string from every confirmation set, so a member who leaves cannot retroactively contribute to any pending request's quorum.

### Proof of Concept
```
// members = {A, B, C, D}, num_confirmations = 3
A: add_request(Transfer{receiver_id: attacker_controlled, amount})   // request_id = R
B: confirm(R)                                        // confirmations(R) = {B}      (1 < 3)
C: confirm(R)                                        // confirmations(R) = {B, C}   (2 < 3)

// Separate governance action: remove C from the multisig (executed with 3 live confirmations)
A: add_request_and_confirm(DeleteMember{member: C})  // request_id = R2
B: confirm(R2)
D: confirm(R2)                                       // executes delete_member(C):
                                                      //   - only purges requests where r.member == C (none, since R was created by A)
                                                      //   - confirmations(R) is untouched, still contains "C"
                                                      //   - members = {A, B, D}

// C is now removed, but its stale confirmation on R remains counted
D: confirm(R)                                        // confirmations(R).len() (2) + 1 = 3 >= num_confirmations (3)
                                                      // execute_request(R) runs the Transfer
                                                      // Only B and D are live approvers — 2 of 3, not 3 of 3
```
This demonstrates a `Transfer` (or any other `MultiSigRequestAction`, including `AddKey`/`DeployContract`) executing with a confirmation count that includes a member who was removed from the live member set before the quorum was reached, i.e. execution below the intended live-member threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
