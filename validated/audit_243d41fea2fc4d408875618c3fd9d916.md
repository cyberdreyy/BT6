### Title
Last-moment stake before `ping()` captures already-accrued validator reward pro-rata across shares - ([File: staking-pool/src/internal.rs])

### Summary
`internal_ping` credits `total_reward` (the delta in `account_locked_balance() + account_balance()` since the last ping) to every current `stake_shares` holder in proportion to shares held at the single ping snapshot, with no accounting for how long those shares were actually staked. An attacker who calls `deposit()` then `stake()` inside the same epoch as the last `ping()` (i.e. before the epoch height changes) buys shares at the pre-reward price; when the epoch turns over and someone next calls a pool method, the reward that was earned entirely by the pre-existing staked balance is distributed across the now-enlarged `total_stake_shares` set, giving the attacker a slice of a reward their capital never participated in earning, at the expense of the pre-existing delegators.

### Finding Description
The claimed binding — `account_reward = stake_shares(account)/total_stake_shares * total_reward` should be proportional to the NEAR-epochs the account's capital was actually staked, not merely the shares held at the single ping snapshot — is violated by design of `internal_ping`: [1](#0-0) 

`internal_ping` only measures the delta between `self.last_total_balance` and the current `account_locked_balance()+account_balance()`, and applies `remaining_reward` to `self.total_staked_balance` and distributes it implicitly across whatever `total_stake_shares` exist *at the moment ping runs* — not the shares that existed when the underlying reward was earned.

Path: attacker calls `deposit()`; inside `deposit()`, `internal_ping()` is invoked first (line `let need_to_restake = self.internal_ping();` in `staking-pool/src/lib.rs`), which is a no-op if `env::epoch_height()` still equals `self.last_epoch_height` (no reward realized yet this epoch): [2](#0-1) 

Then `stake()` is called, which mints `num_shares` at the current (pre-reward) price via `num_shares_from_staked_amount_rounded_down`: [3](#0-2) 

On real NEAR, a stake-amount change submitted via `internal_restake()`'s `Promise::new(...).stake(...)` does not retroactively affect the validator seat/reward computation for the epoch that already elapsed — that reward was fixed based on the stake amount effective before the attacker joined. Yet once the epoch height changes and any account calls a pool method, `internal_ping` distributes that already-baked-in `total_reward` across `total_stake_shares`, which now includes the attacker's freshly-minted, not-yet-reward-earning shares. Using S = pre-existing staked balance, T = pre-existing shares, `amount` = attacker's stake, R = the reward attributable entirely to S: after the attacker joins at unchanged price S/T and the reward posts, the new price becomes `(S/T) * (1 + R/(S+amount))`, so the attacker's position grows from `amount` to `amount + amount*R/(S+amount)` — a reward captured despite contributing zero epochs of actual validation — while the original holders receive only `S*R/(S+amount)` instead of the full `R` they earned.

No existing guard prevents this: `internal_ping`'s only assertion is that the new `total_balance` is not less than the old one (line 208-211), which is unrelated; there is no per-account time-weighting, no deposit lockup, and no fee/vesting check applicable to `deposit()`/`stake()`. The share-price-never-decreases invariant (verified in the emulator's `verify_stake_price_increase_guarantee`) is preserved throughout this flow, so it does not catch the misattribution.

### Impact Explanation
Value (in the form of future-withdrawable NEAR once unstaked and released after the `NUM_EPOCHS_TO_UNLOCK` delay) is shifted from long-term delegators to a last-moment staker purely through internal share accounting — no code invariant is technically broken (share price still only increases), but the reward is mis-credited to a party whose capital did not earn it. This matches the "rewards ... attributed to the wrong party" High-severity category: it is an accounting value (each account's `stake_shares`-derived balance) diverging from the economic reality of who actually contributed staking time, and other delegators settle on this incorrect value when they later withdraw. The attack is repeatable every epoch boundary against any pool with nonzero pending reward, and scales with the attacker's capital relative to pool size.

### Likelihood Explanation
This requires only: an unprivileged account with liquid NEAR, knowledge of the pool's epoch/reward timing (publicly observable on-chain), and two ordinary calls (`deposit()`, `stake()`) timed to land in the epoch immediately before a reward-bearing `ping()`. No special privilege, no owner action, and no cooperation from the pool owner is needed beyond the pool having a nonzero pending reward at epoch turnover, which is a routine, externally observable condition for any actively-validating pool. This is inherent to the pool's point-in-time, share-based accounting design (shared by essentially all non-time-weighted liquid-staking pools) rather than a coding defect, but it is concretely demonstrable and repeatable.

### Recommendation
Introduce a minimum holding/cool-down period before newly staked shares participate in reward distribution (e.g., only shares held since before `last_epoch_height` are eligible for `remaining_reward` in a given `ping`), or require deposits/stakes to also pass through an epoch boundary before being reward-eligible, mirroring the existing unstake delay (`NUM_EPOCHS_TO_UNLOCK`) but for the stake side.

### Proof of Concept
Using the existing `Emulator` test harness in `staking-pool/src/lib.rs` (`tests` module):
1. `Emulator::new` with `zero_fee()` (or nonzero fee, per the question's precondition), deposit and `stake()` a large amount as `alice()` at epoch 0 — establishes `S`, `T`.
2. `skip_epochs(k)` to simulate elapsed validation epochs and increase `emulator.locked_amount` to represent an accrued but not-yet-`ping()`-realized reward `R`, WITHOUT calling `ping()` yet (i.e., stay in the same `epoch_height` the contract last saw).
3. As `bob()` (attacker), call `deposit()` then `stake(amount)` while `epoch_height` still equals `contract.last_epoch_height` (so `internal_ping` is a no-op and bob's shares are minted at the pre-reward price).
4. Advance `epoch_height` by 1 and call `ping()`.
5. Assert: `bob`'s `get_account_staked_balance` increased by `amount*R/(S+amount)` (nonzero reward despite zero epochs staked), and `alice`'s staked balance increased by only `S*R/(S+amount)` instead of the full `R` she alone earned — i.e., compare `alice`'s realized reward share against `R * S/(S+amount)` versus the naive expectation of receiving the full `R`, demonstrating the misattributed slice captured by `bob`.

    pub(crate) fn internal_stake(&mut self, amount: Balance) {
        assert!(amount > 0, "Staking amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);

        // Calculate the number of "stake" shares that the account will receive for staking the
        // given amount.
        let num_shares = self.num_shares_from_staked_amount_rounded_down(amount);
        assert!(
            num_shares > 0,
            "The calculated number of \"stake\" shares received for staking should be positive"
        );
        // The amount of tokens the account will be charged from the unstaked balance.
        // Rounded down to avoid overcharging the account to guarantee that the account can always
        // unstake at least the same amount as staked.
        let charge_amount = self.staked_amount_from_num_shares_rounded_down(num_shares);
        assert!(
            charge_amount > 0,
            "Invariant violation. Calculated staked amount must be positive, because \"stake\" share price should be at least 1"
        );

        assert!(
            account.unstaked >= charge_amount,
            "Not enough unstaked balance to stake"
        );
        account.unstaked -= charge_amount;
        account.stake_shares += num_shares;
        self.internal_save_account(&account_id, &account);

        // The staked amount that will be added to the total to guarantee the "stake" share price
        // never decreases. The difference between `stake_amount` and `charge_amount` is paid
        // from the allocated STAKE_SHARE_PRICE_GUARANTEE_FUND.
        let stake_amount = self.staked_amount_from_num_shares_rounded_up(num_shares);

        self.total_staked_balance += stake_amount;
        self.total_stake_shares += num_shares;

    pub(crate) fn internal_ping(&mut self) -> bool {
        let epoch_height = env::epoch_height();
        if self.last_epoch_height == epoch_height {
            return false;
        }
        self.last_epoch_height = epoch_height;

        // New total amount (both locked and unlocked balances).
        // NOTE: We need to subtract `attached_deposit` in case `ping` called from `deposit` call
        // since the attached deposit gets included in the `account_balance`, and we have not
        // accounted it yet.
        let total_balance =
            env::account_locked_balance() + env::account_balance() - env::attached_deposit();

        assert!(
            total_balance >= self.last_total_balance,
            "The new total balance should not be less than the old total balance"
        );
        let total_reward = total_balance - self.last_total_balance;
        if total_reward > 0 {
            // The validation fee that the contract owner takes.
            let owners_fee = self.reward_fee_fraction.multiply(total_reward);

            // Distributing the remaining reward to the delegators first.
            let remaining_reward = total_reward - owners_fee;
            self.total_staked_balance += remaining_reward;

            // Now buying "stake" shares for the contract owner at the new share price.
            let num_shares = self.num_shares_from_staked_amount_rounded_down(owners_fee);
