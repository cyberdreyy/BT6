### Title
Stale rejection weight not retracted when a signer switches its vote from Reject to Accept on the same block — inflated/conflicting weight tallies in the miner's `StackerDBListener` — (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The lock_api CVE (GHSA-ppj3-7jw3-8vc4) is a class of bug where two logically-linked views of the same guarded state can be updated independently and fall out of sync, breaking an invariant the caller relies on. The closest reachable analog in this repo is in the miner-side StackerDB message tally: `total_weight_approved` and `total_weight_rejected` are two independently-maintained counters keyed off *different* de-duplication sets (`gathered_signatures` vs `responded_signers`), so a single signer's vote-switch updates one counter without retracting the other, breaking the "aggregated-weight vs verified-accepts" equality the coordinator relies on.

### Finding Description
In `stackerdb_listener.rs`, `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` is gated for double-counting via `gathered_signatures.contains_key(&slot_id)`, while `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` is gated via `responded_signers.insert(slot_id)`: [1](#0-0) 

These are two separate sets that are never reconciled with each other. If a signer legitimately rejects a block first (adding weight to `total_weight_rejected` and marking its slot in `responded_signers`), and later legitimately reconsiders the *same* block hash and accepts it — a flow explicitly supported by the signer's own logic ("repeat my earlier answer, unless the reason I rejected has since gone away", per the documented decision flow) — the Accept branch only checks `gathered_signatures`, which does not yet contain this slot, so it adds the signer's weight to `total_weight_approved` as well: [2](#0-1) 

The earlier contribution to `total_weight_rejected` is never removed. The two tallies drift out of the equality the caller (`SignCoordinator`) depends on — that `total_weight_rejected` and `total_weight_approved` are mutually-exclusive partitions of `total_weight` — because the same signer's weight now appears (or effectively double-counts) across both buckets.

The consumer of this state is `signer_coordinator.rs`, which checks the two counters independently to decide between three outcomes: reject the proposal (`SignersRejected`), accept it (return gathered signatures), or keep waiting: [3](#0-2) 

Because `total_weight_rejected` retains stale weight from a signer who has since switched to Accept, the sum `total_weight_rejected + total_weight_approved` can legitimately exceed `total_weight`, and the miner can reach the `>30% rejected` branch (line 509-513) even after enough weight has switched to approve, or vice versa depending on message arrival order and which check the loop executes first.

### Impact Explanation
This is a liveness wedge, not a signature-forgery bug: the actual `gathered_signatures` map still only contains real, cryptographically-verified signatures from signers who currently accept, so the miner cannot be tricked into broadcasting a block with fewer than threshold *real* signatures. The concrete damage is that stale rejection weight from a signer who has since reconsidered can cause the coordinator to prematurely declare `NakamotoNodeError::SignersRejected` for a block that would otherwise reach the acceptance threshold, or distort the adaptive rejection-timeout stepping in the same loop: [4](#0-3) 
This matches the "High" impact bucket: it can wedge a valid block proposal into a rejected/retry loop rather than letting it be signed, degrading miner liveness. It does not, on the evidence gathered, break block-signing safety (no invalid/conflicting signature is fabricated).

### Likelihood Explanation
Requires only one signer that legitimately changes its vote on the exact same `signer_signature_hash` from Reject to Accept — a scenario the signer's own state machine explicitly supports when "the reason I rejected has since gone away." No majority collusion, no other signer's key, and no StackerDB-sync exploitation is needed; it is triggered by ordinary single-signer reconsideration plus the miner observing both messages, well within the one-slot/gossip threat model. I could not fully verify from the index which specific reject reasons are eligible for this in-place reconsideration (`should_reevaluate_reject_reason` body was not retrieved), so the exact frequency in practice is uncertain, though the flow is corroborated by the documented "repeat my earlier answer unless the reason has gone away" behavior.

### Recommendation
When recording an Accept for a slot that is already present in `responded_signers` with a prior Reject (or vice-versa), retract the stale contribution from the opposite counter before adding to the new one, so `total_weight_approved` and `total_weight_rejected` remain a true partition of `total_weight` per signer slot at all times.

### Proof of Concept
1. Miner proposes block B; signer S (weight w) rejects B for a transient reason (e.g., `ConnectivityIssues`), incrementing `total_weight_rejected` by `w` and inserting S's slot into `responded_signers`.
2. Miner re-broadcasts/re-proposes the same block (or time passes) and S's local state machine determines the rejection reason has gone away, so S now signs and broadcasts `BlockResponse::Accepted` for the same `signer_signature_hash`.
3. `stackerdb_listener.rs` receives the Accepted message; because `gathered_signatures` does not yet contain S's slot, it adds `w` to `total_weight_approved` without removing `w` from `total_weight_rejected`.
4. Depending on iteration order, `signer_coordinator.rs`'s loop can observe `total_weight_rejected.saturating_add(weight_threshold) > total_weight` (using the stale rejected weight) and return `Err(NakamotoNodeError::SignersRejected)` even though enough weight has, in reality, moved to Accept — stalling the tenure unnecessarily.
