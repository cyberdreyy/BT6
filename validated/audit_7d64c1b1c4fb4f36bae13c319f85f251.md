### Title
Job objects created with `JOB_OBJECT_LIMIT_BREAKAWAY_OK` allow CI job subprocesses to escape termination on cancellation - ([File: helpers/process/job_windows.go])

### Summary
`CreateJobObject` in `helpers/process/job_windows.go` explicitly sets `JOB_OBJECT_LIMIT_BREAKAWAY_OK` alongside `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, which permits any process the job script launches to opt out of the job object via `CREATE_BREAKAWAY_FROM_JOB`. If a job script (or a tool/binary it invokes) starts a child process with that creation flag, the child is never assigned to the job object, so `closeJobObject()` closing the handle on `Wait()`/cancellation does not terminate it.

### Finding Description
`CreateJobObject()` builds a `JOBOBJECT_EXTENDED_LIMIT_INFORMATION` with: [1](#0-0) 
The comment on line 95 itself documents that this flag is intended to "allow subprocesses to explicitly avoid termination using `CREATE_BREAKAWAY_FROM_JOB`" — i.e., it is a deliberate, code-confirmed design choice, not merely a theoretical possibility.

The runner's cancellation/kill-on-close guarantee relies entirely on the Windows job-object "kill on job close" semantics: [2](#0-1) 
`Start()` creates the job object and assigns the top-level job process's PID to it via `AssignPidToJobObject`/`AssignProcessToJobObject`: [3](#0-2) 
Because `BREAKAWAY_OK` is set on the job, any descendant process created by the job's script with `CreateProcess(..., CREATE_BREAKAWAY_FROM_JOB, ...)` is deliberately *not* placed in the job hierarchy, and thus is unaffected by `windows.CloseHandle(c.jobObject)` in `closeJobObject()`.

An unprivileged pipeline author fully controls the job script executed under `UseWindowsJobObject` (shell/custom executors, per `executors/shell/shell.go` and `executors/custom/custom.go` referencing `UseWindowsJobObject`). A job script that runs a small compiled binary (or uses OS-level tooling capable of calling `CreateProcess` with `CREATE_BREAKAWAY_FROM_JOB`, e.g. via `Add-Type`/P/Invoke in PowerShell) can spawn a long-lived subprocess that will survive job cancellation/termination via `ForceKill`/`Terminate`, since those rely on the same job-object-close mechanism.

No other check in the reviewed path (kill/terminate logic in `helpers/process`, `AssignPidToJobObject`, `closeJobObject`) enumerates or otherwise force-terminates descendant PIDs independent of the job object; the sole termination mechanism for `UseWindowsJobObject` mode is the job-object kill-on-close, which `BREAKAWAY_OK` explicitly circumvents for opted-out children.

### Impact Explanation
On a shared, autoscaled Windows host (e.g., windows shell executor with autoscaling), a malicious/unprivileged pipeline author can leave a subprocess running indefinitely after their job is cancelled or the pipeline is torn down. This is a resource-persistence / cleanup-bypass issue: the escaped process continues consuming CPU/memory/network/disk on the shared runner host and persists into subsequent jobs' execution window on the same machine, since the invariant "closing/cancelling a job must terminate all its descendant processes" is violated for any process explicitly requesting breakaway.

### Likelihood Explanation
Preconditions are fully attacker-controlled and easily met: `UseWindowsJobObject` feature flag enabled (this is the only mode where job objects are used at all — the flag is intentionally an opt-in mitigation), and the job script must be able to execute an unprivileged process with `CREATE_BREAKAWAY_FROM_JOB`. Any Windows shell/custom executor job that can run arbitrary commands (the normal case for CI jobs) can compile/run a small helper (Go, C#, PowerShell P/Invoke) to do this — no elevated privileges are required, since `JOB_OBJECT_LIMIT_BREAKAWAY_OK` is what grants unprivileged callers the right to breakaway (normally `CREATE_BREAKAWAY_FROM_JOB` requires the job to have this limit set, which the runner itself sets). This makes the bug fully repeatable by any pipeline author on a Windows runner with the feature flag on.

### Recommendation
Do not set `JOB_OBJECT_LIMIT_BREAKAWAY_OK` on the job object created for CI job processes in `CreateJobObject()` (`helpers/process/job_windows.go` lines 92-97). Removing that limit flag prevents child processes from breaking away from the job at all, restoring the kill-on-close guarantee for all descendants. If breakaway is required for some specific internal use case, it should be scoped to that specific process/job object rather than applied to every job-controlled job object, and the general CI job object should keep only `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`.

### Proof of Concept
Go integration test (Windows-only), modeled on the existing `killer_integration_test.go` pattern:

```go
// helpers/process/breakaway_windows_integration_test.go
//go:build integration && windows

func TestJobObjectBreakawayEscapesTermination(t *testing.T) {
    // 1. Build a small "breakaway.exe" test binary whose main() calls
    //    windows.CreateProcess with CreationFlags = windows.CREATE_BREAKAWAY_FROM_JOB
    //    to launch a long-sleeping child (e.g. "sleep 60"), then exits itself.
    breakawayBinary := prepareBreakawayTestBinary(t)

    command := process.NewOSCmd(breakawayBinary, nil, process.CommandOptions{
        UseWindowsJobObject: true,
        Logger:              &dumbTestLogger{},
    })
    require.NoError(t, command.Start())

    // capture the breakaway child's PID (e.g. written to a temp file by the helper binary)
    childPID := waitForChildPIDFile(t)

    // Cancel/terminate the parent job as the runner would on job cancellation.
    k := process.NewKillerForTest(loggerMock, command)
    k.ForceKill()
    _ = command.Wait() // this calls closeJobObject()

    // Assert: child process launched with CREATE_BREAKAWAY_FROM_JOB is still alive
    // after the job object handle is closed -- proving escape from termination.
    assert.True(t, isProcessAlive(childPID),
        "breakaway child survived job-object closure; expected it to be terminated")
}
```

Expected result with current code: the assertion passes (child alive), demonstrating the escape — which is the safety violation. After applying the recommended fix (removing `JOB_OBJECT_LIMIT_BREAKAWAY_OK`), the same `CreateProcess` call with `CREATE_BREAKAWAY_FROM_JOB` would fail (`ERROR_ACCESS_DENIED`) or the child would remain in the job and be killed, so the test should be updated to assert the child process is *not* alive (`isProcessAlive(childPID) == false`).

func (c *osCmd) Start() error {
	setProcessGroup(c.internal, c.options.UseWindowsLegacyProcessStrategy)

	if c.options.UseWindowsJobObject {
		jobObj, err := CreateJobObject()
		if err != nil {
			return fmt.Errorf("starting OS command: %w", err)
		}
		c.jobObject = jobObj
	}

	err := c.internal.Start()
	if err != nil {
		return fmt.Errorf("starting OS command: %w", err)
	}

	if c.options.UseWindowsJobObject {
		// Any failures here are ignored, since we've already started the process running.
		if err := AssignPidToJobObject(c.internal.Process.Pid, c.jobObject); err != nil {
			c.options.Logger.Warn("assigning process to job object:", err)
		}
	}
	return nil
}

func (c *osCmd) closeJobObject() {
	if !c.options.UseWindowsJobObject {
		return
	}
	c.once.Do(func() {
		windows.CloseHandle(c.jobObject)
	})
}
