### Title
`isTransferProcessed` Keyed Only by Nonce, Not by `(chainID, nonce)` — Permanent Fund Lock Across Multi-Source-Chain Bridge - (File: `bridge/evm/contracts/SuiBridge.sol`)

---

### Summary

`SuiBridge.sol` and `SuiBridgeV2.sol` track processed token-transfer messages in a mapping keyed solely by `message.nonce` (`uint64`). Because the bridge accepts transfers from **multiple supported source chains** (each with its own independent nonce counter starting at 0), two distinct legitimate transfers from two different source chains that happen to share the same nonce value will collide in this mapping. The first transfer to be processed permanently marks that nonce as consumed, causing every subsequent transfer from any other source chain with the same nonce to revert with `"SuiBridge: Message already processed"` — permanently locking the deposited funds.

---

### Finding Description

`SuiBridge.sol` declares the replay-prevention mapping as:

```solidity
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;
``` [1](#0-0) 

Both `transferBridgedTokensWithSignatures` (v1) and `transferBridgedTokensWithSignaturesV2` (v2) check and set this mapping using only `message.nonce`:

```solidity
require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");
// ...
isTransferProcessed[message.nonce] = true;
``` [2](#0-1) [3](#0-2) 

The `message.chainID` field carries the **source chain identifier**. The `onlySupportedChain(message.chainID)` modifier confirms the bridge is explicitly designed to accept transfers from multiple supported source chains:

```solidity
modifier onlySupportedChain(uint8 targetChainID) {
    require(
        committee.config().isChainSupported(targetChainID),
        "SuiBridge: Target chain not supported"
    );
    _;
}
``` [4](#0-3) 

Each source chain maintains its own independent nonce counter starting at 0. Nonces are **not globally unique across chains** — they are only unique within a single source chain. The `isTransferProcessed` mapping therefore conflates nonces from different source chains, treating `(chainA, nonce=5)` and `(chainB, nonce=5)` as the same key.

Contrast this with the non-TOKEN_TRANSFER path in `MessageVerifier.sol`, which **does** enforce `message.chainID == committee.config().chainID()` before checking the nonce — but this guard is explicitly skipped for `TOKEN_TRANSFER` messages:

```solidity
if (messageType != BridgeUtils.TOKEN_TRANSFER) {
    require(
        message.chainID == committee.config().chainID(), "MessageVerifier: Invalid chain ID"
    );
    require(message.nonce == nonces[message.messageType], "MessageVerifier: Invalid nonce");
    nonces[message.messageType]++;
}
``` [5](#0-4) 

The token-transfer path therefore has no chain-scoped nonce uniqueness guarantee, exactly mirroring the external report's root cause: an identifier assumed to be globally unique is only locally unique per source context.

---

### Impact Explanation

When source chain A's transfer with `nonce=N` is processed first, `isTransferProcessed[N]` is set to `true`. Any subsequent call to claim a transfer from source chain B that also carries `nonce=N` will revert unconditionally. The tokens locked or burned on chain B cannot be recovered — they are permanently inaccessible. This constitutes **permanent fund lock**, matching the High/Medium impact tier in the allowed impact gate.

---

### Likelihood Explanation

Nonces on each source chain start at 0 and increment monotonically. As soon as any two supported source chains have both processed at least one transfer, their nonce spaces overlap completely (both have nonce=0, nonce=1, …). The collision is not a rare edge case — it is structurally guaranteed for any deployment where more than one source chain is active. Any ordinary user depositing tokens on a source chain whose nonce has already been consumed by another source chain triggers the lock with no special privilege required.

---

### Recommendation

Key the processed-transfer mapping by the composite `(chainID, nonce)` pair rather than nonce alone:

```solidity
// Replace:
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;

// With:
mapping(uint8 chainID => mapping(uint64 nonce => bool isProcessed)) public isTransferProcessed;
```

Update all reads and writes accordingly:

```solidity
require(!isTransferProcessed[message.chainID][message.nonce], "SuiBridge: Message already processed");
// ...
isTransferProcessed[message.chainID][message.nonce] = true;
```

Apply the same fix to `SuiBridgeV2.sol`, which inherits and reuses the same `isTransferProcessed` storage slot.

---

### Proof of Concept

1. The EVM bridge is configured to support two source chains: Sui mainnet (`chainID=0x01`) and a second supported Sui chain (`chainID=0x02`).
2. A user on chain `0x01` deposits tokens; the bridge emits `TokensDeposited` with `nonce=0`. Validators sign and submit `transferBridgedTokensWithSignatures` with `message.chainID=0x01, message.nonce=0`. The call succeeds; `isTransferProcessed[0] = true`.
3. A different user on chain `0x02` also deposits tokens; the bridge emits `TokensDeposited` with `nonce=0` (independent counter). Validators sign and submit `transferBridgedTokensWithSignatures` with `message.chainID=0x02, message.nonce=0`.
4. The call hits `require(!isTransferProcessed[0])` → reverts with `"SuiBridge: Message already processed"`.
5. The user's tokens on chain `0x02` are permanently locked; no recovery path exists. [6](#0-5) [7](#0-6)

    function transferBridgedTokensWithSignatures(
        bytes[] memory signatures,
        BridgeUtils.Message memory message
    )
        external
        nonReentrant
        verifyMessageAndSignatures(message, signatures, BridgeUtils.TOKEN_TRANSFER)
        onlySupportedChain(message.chainID)
    {
        // verify that message has not been processed
        require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");

        IBridgeConfig config = committee.config();

        BridgeUtils.TokenTransferPayload memory tokenTransferPayload =
            BridgeUtils.decodeTokenTransferPayload(message.payload);

        // verify target chain ID is this chain ID
        require(
            tokenTransferPayload.targetChain == config.chainID(), "SuiBridge: Invalid target chain"
        );

        // convert amount to ERC20 token decimals
        uint256 erc20AdjustedAmount = BridgeUtils.convertSuiToERC20Decimal(
            IERC20Metadata(config.tokenAddressOf(tokenTransferPayload.tokenID)).decimals(),
            config.tokenSuiDecimalOf(tokenTransferPayload.tokenID),
            tokenTransferPayload.amount
        );

        _transferTokensFromVault(
            message.chainID,
            tokenTransferPayload.tokenID,
            tokenTransferPayload.recipientAddress,
            erc20AdjustedAmount
        );

        // mark message as processed
        isTransferProcessed[message.nonce] = true;

        emit TokensClaimed(
            message.chainID,
            message.nonce,
            config.chainID(),
            tokenTransferPayload.tokenID,
            erc20AdjustedAmount,
            tokenTransferPayload.senderAddress,
            tokenTransferPayload.recipientAddress
        );
    }
