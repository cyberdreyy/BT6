Confirmed: `_validateImmutables` (implemented via `Escrow`/`Create2` address recomputation, using `immutables.hash()` from `ImmutablesLib`) forces the withdraw-time caller to submit the *exact same* `parameters` bytes used at `createDstEscrow` — the CREATE2 salt is `hashMem()`, which hashes the full immutables including `parameters`. So an attacker cannot "fix up" a short `parameters` blob at withdraw time; whatever length was chosen at creation is permanently fixed for that clone's whole lifecycle.

### Title
Undersized `parameters` blob in `createDstEscrow` permanently breaks `EscrowDst.withdraw`/`publicWithdraw` (temporary freeze) - (File: `contracts/EscrowDst.sol`, `contracts/libraries/ImmutablesLib.sol`)

### Summary
`EscrowDst._withdraw` unconditionally calls `immutables.integratorFeeAmountCd()` and `immutables.protocolFeeAmountCd()` before ever checking whether fees are non-zero. Both revert with `IndexOutOfRange()` if `immutables.parameters.length < 0x40` (64 bytes). Since `createDstEscrow` performs no validation on `dstImmutables.parameters` and the CREATE2 salt/`onlyValidImmutables` check locks the escrow to the exact `parameters` bytes supplied at creation, any destination escrow created with a `parameters` blob shorter than 64 bytes (e.g., 32 bytes) can never be withdrawn — neither via `withdraw` nor `publicWithdraw` — for its entire lifetime. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`createDstEscrow` is a public, unprivileged entrypoint that accepts `dstImmutables` verbatim from the caller and deploys a deterministic clone funded with the caller's tokens/native value, with zero validation of the `parameters` field's length or contents. [3](#0-2) 

`ImmutablesLib.integratorFeeAmountCd`/`protocolFeeAmountCd` each require `parameters.length` to be at least `0x40`/`0x20` respectively and revert `IndexOutOfRange()` otherwise. [4](#0-3) 

`EscrowDst._withdraw` reads both `integratorFeeAmountCd()` and `protocolFeeAmountCd()` unconditionally at the top of the function, regardless of whether any fee is actually owed: [5](#0-4) 

Because the escrow's deployment salt is `immutables.hashMem()` (which hashes the `parameters` bytes as part of the immutables struct) and `withdraw`/`publicWithdraw`/`cancel`/`rescueFunds` all gate on `onlyValidImmutables(immutables.hash())` (Create2-address re-derivation), the caller of `withdraw` cannot supply a longer/corrected `parameters` blob than the one used at creation — doing so changes the hash and fails validation. [6](#0-5) [7](#0-6) 

Consequently, once a destination escrow is created with `parameters.length < 0x40`, both `withdraw` (taker-only) and `publicWithdraw` (access-token-holder fallback) permanently revert with `IndexOutOfRange()` for that clone. The only remaining path is `cancel()` after the `DstCancellation` timelock, which returns `immutables.amount` to `taker` (not to `maker`) and the safety deposit to the caller. [8](#0-7) 

Note the premise in the question ("protocol fee alone is near the full amount") is not actually required — the revert is triggered purely by insufficient `parameters` length (any length under 64 bytes), independent of the fee value encoded.

### Impact Explanation
This breaks the stated invariant that "every funded destination escrow should remain withdrawable with the exact parameters used to create it." The maker cannot receive the destination payout through `withdraw` or the `publicWithdraw` failsafe at all; the swap is forced into cancellation, where funds return to the taker rather than completing the swap for the maker. This is a temporary freeze of the intended destination-side payout (the maker does not receive the tokens within the swap's designed windows and must wait for cancellation), consistent with the "temporary freezing of funds during the live swap lifecycle" bounty category. It does not cause permanent loss or theft, since `cancel()` still returns the deposited destination funds to their depositor (the taker) and the safety deposit is refunded to the caller — the outcome is functionally equivalent to a taker who simply refuses to ever call `withdraw`, except that the `publicWithdraw` failsafe (meant to force settlement even against an uncooperative taker) is also disabled by this bug.

### Likelihood Explanation
`createDstEscrow` is fully permissionless and takes attacker-controlled `parameters` bytes without any length/shape validation; triggering the revert requires nothing more than encoding a `parameters` field under 64 bytes when creating the destination clone (with correct native/token funding). This is trivially reproducible.

### Recommendation
In `EscrowDst._withdraw`, avoid unconditionally decoding fee fields — check `parameters.length` up front (or make `ImmutablesLib` fee getters tolerant of missing fields, e.g., default to zero rather than reverting when the corresponding slot is absent), and/or have `BaseEscrowFactory.createDstEscrow` validate that `dstImmutables.parameters.length` meets the minimum size (`0x40` at least, `0x80` if any fee recipient is needed) before deploying the clone, so malformed escrows can never be created in the first place.

### Proof of Concept
1. Attacker (as taker) calls `createDstEscrow` with `dstImmutables.parameters = abi.encode(protocolFeeAmount)` (32 bytes only), funding the escrow with the correct `amount + safetyDeposit`. [3](#0-2) 
2. After `DstWithdrawal` stage begins, taker or a public-withdraw caller calls `withdraw`/`publicWithdraw` with the identical `immutables` (required to pass `onlyValidImmutables`). [9](#0-8) 
3. `_withdraw` calls `immutables.integratorFeeAmountCd()`, which reverts `IndexOutOfRange()` because `parameters.length (0x20) < 0x40`. [10](#0-9) [11](#0-10) 
4. Every subsequent call to `withdraw`/`publicWithdraw` with the same (only valid) immutables reverts identically; the escrow can only reach `cancel()` after `DstCancellation`, returning funds to `taker`, not completing the swap for `maker`.

```text
    function hashMem(IBaseEscrow.Immutables memory immutables) internal pure returns(bytes32 ret) {
        // Compute the EIP-712 hash for the immutables struct
        // Patch the last word (bytes parameters) in the struct with the hash of it
        bytes memory parameters = immutables.parameters;
        assembly ("memory-safe") {
            let parametersHash := keccak256(add(parameters, 0x20), mload(parameters))
            let patchLocation := sub(add(immutables, IMMUTABLES_SIZE), 0x20)
            let backup := mload(patchLocation)

            // Patch the last word with the hash of parameters to compute the EIP-712 hash
            mstore(patchLocation, parametersHash)
            ret := keccak256(immutables, IMMUTABLES_SIZE)

            mstore(patchLocation, backup) // Restore the original value
        }
    }
```

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```
