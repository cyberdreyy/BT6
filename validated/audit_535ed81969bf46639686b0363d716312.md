### Title
Cross-user response hijacking via `MessageId` collision in `h.savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores each pending user callback in `h.savedCallbacks` keyed solely by the attacker-controlled `msg.Body.MessageId`, with no `sender` component and no existence check before overwrite. An unauthenticated client can submit a signed message reusing a legitimate user's `MessageId` while their request is still pending, silently replacing the legitimate user's callback so that the eventual node response for that `MessageId` is delivered to the attacker instead.

### Finding Description
`HandleLegacyUserMessage` unconditionally overwrites the map entry: [1](#0-0) 

There is no duplicate-key check here, unlike the sibling primitive `common.RequestCache`, whose `NewRequest` explicitly keys by `globalId{sender, id}` and rejects collisions: [2](#0-1) 

When the node's response arrives, `HandleNodeMessage` → `handleWebAPITriggerMessage` looks up and deletes the entry purely by `msg.Body.MessageId`, with no sender/receiver binding back to the original requester: [3](#0-2) [4](#0-3) 

`msg.Body.MessageId` is fully attacker-controlled — it comes from the client-supplied, self-signed `api.Message.Body.MessageId` field, validated only for length/format, not uniqueness or ownership: [5](#0-4) 

`gateway.ProcessRequest` routes any correctly-signed legacy message straight to `h.HandleLegacyUserMessage` regardless of who signed it — there is no authentication of "who owns this MessageId", only per-message signature validation for sender attribution: [6](#0-5) 

Exploit flow: (1) legitimate user submits `MethodWebAPITrigger` with `MessageId=X`, `h.savedCallbacks[X]` set to the legitimate callback; (2) before the node's response returns, attacker submits their own validly-signed message reusing `MessageId=X`, overwriting `h.savedCallbacks[X]` with the attacker's callback; (3) when the DON node's response for `X` arrives, `handleWebAPITriggerMessage` delivers it to whichever callback currently occupies `h.savedCallbacks[X]` — the attacker's, per last-writer-wins map semantics — and the legitimate user's own HTTP call then times out or never resolves correctly.

### Impact Explanation
This is a cross-user response confusion / hijacked callback delivery bug: an attacker can consume the response destined for another user's request and simultaneously deny that response to the legitimate user (denial/griefing of their gateway request). While the payload delivered for `MethodWebAPITrigger` is generally an accept/error acknowledgement rather than a workflow secret, the underlying primitive — delivering another party's async response to an attacker-chosen recipient by keying solely on a client-supplied ID — is a broken isolation guarantee that the same package (`common.RequestCache`) explicitly enforces elsewhere via `sender`-scoped keys, confirming this is a real, deliberate isolation gap rather than intended behavior.

### Likelihood Explanation
No special privilege is needed: any client able to reach the gateway's HTTP endpoint and sign a `Message` with a throwaway ECDSA key can trigger this. The only requirement is winning a small timing race (submitting the colliding `MessageId` before the DON node's response returns) and knowing/guessing the victim's `MessageId`, which is entirely attacker/application chosen and not scoped to session or sender, making collisions plausible in deployments with predictable or client-reused ID schemes.

### Recommendation
Key `h.savedCallbacks` by `(sender, MessageId)` (mirroring `common.RequestCache`'s `globalId`), and/or reject `HandleLegacyUserMessage` calls that would silently overwrite an existing unexpired entry for the same `MessageId`, instead returning an explicit "duplicate message ID" error to the second caller.

### Proof of Concept
Add a table test in `handler_test.go`:
1. Call `setupHandler(t)`; construct `msgA` signed by `nodes[0].PrivateKey`-style throwaway key "legit key" with `MessageId="dup-id"`, and `msgB` signed by a different throwaway "attacker key" also with `MessageId="dup-id"`.
2. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbLegit)` then `handler.HandleLegacyUserMessage(ctx, msgB, cbAttacker)` (simulating the attacker's request arriving second, before any node response).
3. Construct a node response for `MessageId="dup-id"` via `hc.ValidatedResponseFromMessage`, and call `handler.HandleNodeMessage(ctx, resp, nodes[0].Address)`.
4. Assert `cbAttacker.Wait(ctx)` returns the response payload (proving hijack) while `cbLegit.Wait(ctx)` times out/never resolves — demonstrating last-writer-wins overwrite and cross-user delivery, in contrast to `common.RequestCache.NewRequest`, which would return `"request already exists"` for the same scenario keyed by `(sender, id)`.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {

type globalId struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
