### Title
Permissionless APR override before `idleCDO` is wired — the auth check in `setApr` is skipped when `idleCDO == address(0)` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2020-25284 is an incomplete-permission-check bug: the kernel's rbd driver mapped/unmapped block devices without verifying the caller's full capability set, so an unauthorized local actor could perform a privileged action. The analog in this codebase is `IdleCreditVault.setApr` / `setAprs` / `setAprsWithBuffer`: the caller check `if (_cdo != address(0)) { if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed(); }` means that while `idleCDO` is still unset (the interval between `initialize` and `setWhitelistedCDO`, or after an implementation upgrade before rewiring), *any* EOA can write `lastApr` and `unscaledApr`. `lastApr` is the exact value returned by `getApr()` and consumed by `IdleCDOEpochVariant` to compute `expectedEpochInterest`, so an attacker can distort the epoch accounting basis used by `prepareStopEpochWithApr0`, `previewLossAdjustedWithdrawFunds`, and the stop-epoch funding waterfall.

### Finding Description
`setApr` gates on `msg.sender == idleCDO || msg.sender == manager` only conditionally:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:225-235
function setApr(uint256 _apr) public {
  address _cdo = idleCDO;
  // if cdo is not yet set we skip the check (this can happen only during the setup)
  if (_cdo != address(0)) {
    if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
  }
  uint256 _maxApr = maxApr;
  if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
  lastApr = _apr;
}
```

`setAprs` and `setAprsWithBuffer` inherit the gap and additionally let the caller write `unscaledApr` with no bound at all (`unscaledApr` is only ever compared to `0`, so the attacker can pick 0 or any value). The `maxApr` cap (default `20e18`) bounds `lastApr` but not `unscaledApr`.

The "setup" escape hatch was intended for the honest deployer, but nothing restricts it to the deployer: the check is entirely absent, not merely relaxed to owner/manager. The attacker needs no tokens, no KYC, and no role — only an EOA calling a public function in the window before `setWhitelistedCDO` runs (or on any upgraded proxy whose `idleCDO` storage slot is cleared).

### Impact Explanation
Two concrete harm paths, both in the "in-scope" attacker model:

1. **Inflated interest basis → forced loss/default.** Attacker sets `lastApr = maxApr` (20e18) via `setApr(20e18)`. When the honest manager later runs `startEpoch`/`stopEpoch`, `expectedEpochInterest` is computed from this inflated APR. If the honest borrower funds only the negotiated amount, `collectWithdrawFunds(_amount)` receives `_amount < pendingWithdraws`, writes a `lossRecoveryPriceByEpoch[epochNumber] < 1e18` haircut, and all pending receipts are haircut — a permanent loss borne by withdraw requesters; for active LPs the shortfall flows through `previewLossAdjustedWithdrawFunds`/`_updateAccounting` BB-first. Quantified loss is up to the delta between the inflated expected interest and the actually-funded amount, capped at `pendingWithdraws + activeBasis`.
2. **`unscaledApr = 0` → APR0 accounting hijack.** Attacker calls `setAprs(0, 0)`. Every `requestWithdraw` while the pool is not closed is then routed into `_requestWithdrawApr0`, and `prepareStopEpochWithApr0` diverts a pro-rata share of realized epoch interest (`_apr0NetInterest`) to the APR0 bucket and inflates `pendingWithdraws` by that amount. An attacker holding a pending receipt extracts interest that belongs to active LPs; if the borrower funds only the contractual amount the mismatch again crystallizes as a loss haircut.

Both break the fair-mint/fair-interest invariant: epoch interest distribution is determined by attacker-written state rather than by the CDO/manager.

### Likelihood Explanation
The exploit window is real but conditional: it requires the gap between `initialize` (which does not set `idleCDO` — only `setWhitelistedCDO` does, a separate owner call) and the CDO wiring to be non-atomic, or an upgraded proxy where `idleCDO` is cleared. Upgradeable deployments commonly split these calls across transactions, and `initialize` explicitly tolerates `idleCDO == 0` "during the setup". The CDO does call `setAprs*` on epoch transitions, so persistence of the malicious value depends on whether the honest manager's next `setAprs` call overwrites both fields before `startEpoch` consumes `lastApr`/`unscaledApr` — if the manager only calls `setApr` (not `setAprs`), the attacker's `unscaledApr` persists indefinitely. Attacker cost is one public call; no privileged role is needed.

### Recommendation
Replace the conditional check with an unconditional authorization:

```solidity
function setApr(uint256 _apr) public {
  if (msg.sender != idleCDO && msg.sender != manager && msg.sender != owner()) revert NotAllowed();
  ...
}
```

or restrict the setup path to `onlyOwner` (e.g., a separate `initializeApr` callable only before `idleCDO` is set), so the "cdo not yet set" escape hatch can never be exercised by an arbitrary EOA. Apply the same fix to `setAprs`/`setAprsWithBuffer` and bound `unscaledApr`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {MockERC20} from "../contracts/mocks/MockERC20.sol";

contract SetAprAuthGapTest is Test {
  IdleCreditVault vault;
  MockERC20 underlying;
  address attacker = address(0xbeef);
  address owner = address(0x1);
  address manager = address(0x2);
  address borrower = address(0x3);

  function setUp() public {
    underlying = new MockERC20("USDC", "USDC", 6);
    vault = new IdleCreditVault(); // via proxy in production
    vm.prank(owner);
    vault.initialize(address(underlying), owner, manager, borrower, "B", 5e18);
    // NOTE: owner has not yet called setWhitelistedCDO; idleCDO == address(0)
  }

  function test_AttackerSetsAprBeforeCdoWired() public {
    assertEq(vault.idleCDO(), address(0));
    vm.startPrank(attacker);
    // completely bypasses the cdo/manager check
    vault.setAprs(0, 0);          // forces APR0 accounting path
    vault.setApr(20e18);          // max APR, no revert
    vm.stopPrank();
    assertEq(vault.getApr(), 20e18);
    assertEq(vault.unscaledApr(), 0);
    // After setWhitelistedCDO + startEpoch, expectedEpochInterest is priced off
    // the attacker-written lastApr; a borrower funding the negotiated amount
    // leaves collectWithdrawFunds with _amount < pendingWithdraws, storing a
    // lossRecoveryPriceByEpoch haircut on all pending receipts.
  }
}
```

Caveat on full-fork quantification: whether the corrupted `lastApr`/`unscaledApr` survives until consumed depends on the deployment/upgrade wiring order (`IdleCreditVaultFactory` / CDO `startEpoch` sequence), which determines if the honest `setAprs` overwrite happens first. The access-control gap itself is unconditional and reproducible as shown.
