### Title
Unauthenticated `/v2/resume/:runID` endpoint allows anyone who obtains a pending run's UUID to inject arbitrary task-run results and hijack the eventual on-chain execution outcome - (File: core/web/pipeline_runs_controller.go)

### Summary
The zkSync report describes a two-phase commit/execute pattern (`proposeDiamondCut` → `executeDiamondCut`) where the payload (`_calldata`) is not locked at commit time, letting an attacker supply malicious data at execution and front-run the legitimate actor. Chainlink's pipeline runner has a structurally identical two-phase pattern: an async task (e.g. a `bridge` task) is committed to the DB as `pending`/`suspended` [2](#0-1) , and the second phase — supplying the actual result data and resuming execution — happens later via `PATCH /v2/resume/:runID`, which is **not gated by any authentication middleware**.

### Finding Description
`v2Routes` registers the resume route on the raw, unauthenticated group before any `auth.Authenticate` wrapper is applied: [1](#0-0) 

`PipelineRunsController.Resume` takes the `runID` path parameter (a task UUID) and an attacker-controlled JSON body, decodes it into a `pipeline.ResumeRequest`, and feeds it directly into `ResumeJobV2` without checking who is calling it: [3](#0-2) 

This flows into `runner.ResumeRun`, which updates the task-run result and restarts pipeline execution with whatever `value`/`err` was supplied in the request: [4](#0-3) 

The only "secret" gating this endpoint is the task-run UUID itself — a value returned to the external adapter as `ResponseURL` when the job is created (e.g. `http://.../v2/resume/<uuid>`), as demonstrated in tests: [5](#0-4) . The audit-log call name itself, `audit.UnauthedRunResumed`, confirms this is a deliberately unauthenticated endpoint: [6](#0-5) .

This mirrors the zkSync bug class exactly: the "commit" (creating the pending run/task with an ID) does not lock in the eventual payload; the "execute" step (resume) accepts arbitrary caller-supplied data as long as the caller knows/guesses the run ID, allowing a party other than the intended external adapter to front-run the legitimate callback with malicious data (e.g. spoofed price data, forcing a fatal error, or overwriting output before the real adapter responds).

### Impact Explanation
Because the endpoint accepts and trusts caller-supplied `value`/`error` for any pending task run identified only by a UUID, an attacker who obtains or guesses a run's UUID (e.g. via response URL leakage, log exposure, or a race where they observe the pending run before the legitimate external adapter responds) can:
- Inject falsified data into an in-flight pipeline run (e.g. price feed value feeding an `ethtx` submission task), potentially causing incorrect on-chain transactions.
- Prematurely resume/complete a run with attacker data, racing/front-running the legitimate external adapter's callback — directly analogous to the zkSync front-running of the malicious `_calldata`.
- Force error states or repeatedly resume the same run, causing denial of service or resource exhaustion on the node.

### Likelihood Explanation
Exploitation requires knowledge of a specific pending run's UUID, which is a v4 UUID (128 bits) and not brute-forceable directly. However, this UUID is transmitted in plaintext as part of the `ResponseURL` sent to the (possibly compromised, network-adjacent, or logging-instrumented) external adapter, and is also visible in the node's own request logs and audit trail, meaning any party that can observe that traffic (rather than obtaining the governor/admin key as in the zkSync case) can hit the endpoint before the legitimate response arrives. This is a realistic "unprivileged actor with partial information disclosure" scenario rather than pure brute force.

### Recommendation
- Require some form of proof-of-possession or shared-secret validation for `/v2/resume/:runID` (e.g. HMAC-signed callback token tied to the specific task run, verified server-side) rather than relying solely on UUID secrecy.
- Bind the resume payload to the specific external adapter/bridge that was originally invoked (mirroring the zkSync fix suggestion of binding the executed payload to what was committed at proposal time), rather than accepting arbitrary result data from any caller.
- Rate-limit and audit repeated resume attempts against the same `runID` to detect front-running/race attempts.

### Proof of Concept
1. Create a job with an async `bridge` task; the node returns `ResponseURL: http://<node>/v2/resume/<taskUUID>` to the configured external adapter as shown in `TestBridgeTask_AsyncJobPendingState` [5](#0-4) .
2. An attacker who learns `<taskUUID>` (via network observation, log access, or a compromised/malicious intermediary on the adapter's network path) sends `PATCH /v2/resume/<taskUUID>` with a forged JSON body before the legitimate adapter responds.
3. Since the route has no authentication middleware [1](#0-0) , the request is accepted, and `ResumeJobV2`/`ResumeRun` commits the attacker's value/error and resumes the pipeline [4](#0-3) , producing a poisoned run outcome before or instead of the genuine adapter response.

// StoreRun will persist a partially executed run before suspending, or finish a run.
// If `restart` is true, then new task run data is available and the run should be resumed immediately.
func (o *orm) StoreRun(ctx context.Context, run *Run) (restart bool, err error) {
	err = o.transact(ctx, func(tx *orm) error {
		finished := run.FinishedAt.Valid
		if !finished {
			// Lock the current run. This prevents races with /v2/resume
			sql := `SELECT id FROM pipeline_runs WHERE id = $1 FOR UPDATE;`
			if _, err = tx.ds.ExecContext(ctx, sql, run.ID); err != nil {
				return fmt.Errorf("failed to select pipeline run %d: %w", run.ID, err)
			}

			taskRuns := []TaskRun{}
			// Reload task runs, we want to check for any changes while the run was ongoing
			if err = tx.ds.SelectContext(ctx, &taskRuns, `SELECT * FROM pipeline_task_runs WHERE pipeline_run_id = $1`, run.ID); err != nil {
				return fmt.Errorf("failed to select piepline task run %d: %w", run.ID, err)
			}

			// Construct a temporary run so we can use r.ByDotID
			tempRun := Run{PipelineTaskRuns: taskRuns}

			// Diff with current state, if updated, swap run.PipelineTaskRuns and early return with restart = true
			for i, tr := range run.PipelineTaskRuns {
				if !tr.IsPending() {
					continue
				}

				// Look for new data
				if taskRun := tempRun.ByDotID(tr.DotID); taskRun != nil && !taskRun.IsPending() {
					// Swap in the latest state
					run.PipelineTaskRuns[i] = *taskRun
					restart = true
				}
			}

			if restart {
				return nil
			}

			// Suspend the run
			run.State = RunStatusSuspended
			if _, err = tx.ds.NamedExecContext(ctx, `UPDATE pipeline_runs SET state = :state WHERE id = :id`, run); err != nil {
				return fmt.Errorf("failed to update pipeline run %d to %s: %w", run.ID, run.State, err)

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)

		Value: value,
		Error: err,
	})
	if err != nil {
		return fmt.Errorf("failed to update task run result: %w", err)
	}

	// TODO: Should probably replace this with a listener to update events
	// which allows to pass in a transactionalised database to this function
	if start {
		// start the runner again
		go func() {
			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}
