### Title
Stale confirmations from removed multisig members/keys still count toward execution threshold - (File: multisig2/src/lib.rs, multisig/src/lib.rs)

### Summary
When a multisig member (or access key, in the legacy `multisig` contract) is removed via `DeleteMember`/`DeleteKey`, the contract only deletes pending requests that member *created*. It never scrubs that member's confirmations from other pending requests that member had already confirmed but did not create. Because `confirm()` simply counts entries in the stored `confirmations` `HashSet` against `num_confirmations` [1](#0-0) , a "confirmation" from a member who is no longer part of the live member set is still counted as valid, letting a request execute with fewer genuinely-live approvals than `K`.

### Finding Description
`delete_member` removes the member from `self.members` and deletes only requests where `r.member == member` (i.e. requests *authored* by the removed member); confirmations that member cast on requests authored by *other* members are left untouched in the `self.confirmations` map: [2](#0-1) 

The same pattern exists in the legacy `multisig` contract's `DeleteKey` action, which purges only requests keyed by `r.signer_pk == pk`, not confirmations by that key on other requests: [3](#0-2) 

`confirm()` then executes the request purely by counting existing entries in the confirmations set plus the new confirmer, without re-validating that every entry still corresponds to a live member: [4](#0-3) 

This breaks the intended custody binding of the multisig: `live confirming members == K`. In reality, a stale confirmation from a member removed *after* confirming, but *before* the request reaches quorum, still counts, so the equality becomes `(K-1) live members + 1 removed member == K`, i.e. fewer genuinely authorized parties than the configured threshold can trigger execution of an arbitrary request (e.g. `Transfer`, `FunctionCall`, `AddKey`/`AddMember` to attacker-controlled accounts).

### Impact Explanation
This is Critical: it allows a multisig-controlled account to execute a `Transfer` or other privileged action (adding an attacker's key, deploying a malicious contract) with fewer live confirmations than the configured `num_confirmations` threshold, i.e., funds move by parties not entitled to move them under the multisig's own security model. It directly parallels the IronBank analog class of "claims recorded (confirmations counted) diverging from reality (live members)".

### Likelihood Explanation
Requires no attacker keys beyond normal multisig membership churn: any time a legitimate member's key is compromised or an untrusted member is voted out via a `DeleteMember`/`DeleteKey` request while other pending requests exist that the departing member had already confirmed, those stale confirmations remain armed. A malicious or compromised member who anticipates their own removal can pre-confirm a malicious request beforehand so their vote persists after removal, or an operator relying on membership rotation for security may unknowingly leave dangling votes active.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over all pending requests' confirmation sets (not just requests authored by the removed member) and remove any confirmation entry belonging to the removed member/key. Alternatively, validate at `confirm()`/execution time that every entry in the confirmations set still corresponds to a current member of `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Multisig initialized with members `A, B, C, D` and `num_confirmations = 3`.
2. `D` (compromised or malicious) creates and confirms a malicious `Transfer` request `X` to an attacker account (1 confirmation: `D`).
3. `A` also confirms `X` (2 confirmations: `D`, `A`) — still below threshold of 3.
4. Members `A, B, C` legitimately raise and confirm a `DeleteMember { member: D }` request to remove `D` for unrelated reasons; this executes via `execute_request` → `delete_member`, which only purges requests where `r.member == D` — `X` was authored by `D`... 

   To avoid the request being cleaned up (since `X` was authored by `D`), consider instead: `D` confirms (but does not author) a request `X` authored by `A`. `A` confirms `X` too (2 of 3: `A`, `D`). `D` is later removed via `DeleteMember`; `delete_member` filters only requests where `r.member == D` (i.e., authored by `D`), so `X` (authored by `A`) is untouched, and `D`'s confirmation remains in `X`'s confirmation set.
5. `B` (still a live member, 3rd distinct live member) confirms `X`. `confirm()` counts `{A, D, B}` = 3 >= `num_confirmations` (3), and executes the `Transfer`, even though `D` is no longer a member — only 2 live members (`A`, `B`) plus 1 stale, removed member (`D`) authorized the transfer.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
