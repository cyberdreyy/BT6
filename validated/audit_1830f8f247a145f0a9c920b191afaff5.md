### Title
`PipelineRunsController.Create` binds job runs to any run-role credential without validating the External Initiator's job association - (File: `core/web/pipeline_runs_controller.go`)

### Summary
`prc.Create` is reachable via `POST /v2/jobs/:ID/runs`, gated only by `auth.RequiresRunRole`, which merely checks the generic role level and never verifies that the calling identity (EI or user) is the one authorized for the specific job `:ID`. The handler's own "EIs not allowed" comment is defeated because `AuthenticateExternalInitiator` also populates `SessionUserKey`, making `auth.GetAuthenticatedUser` return `isUser == true` for EI-authenticated requests too, so any valid EI credential can trigger `RunJobV2` for an arbitrary job ID with no cross-check against that job's `ExternalInitiatorWebhookSpec`.

### Finding Description
The route is registered at: [1](#0-0) 

as accessible to any of `AuthenticateExternalInitiator`, `AuthenticateByToken`, or `AuthenticateBySession`, gated only by `auth.RequiresRunRole`, which just checks `user.Role != UserRoleView`: [2](#0-1) 

Critically, `AuthenticateExternalInitiator` sets **both** `SessionExternalInitiatorKey` and `SessionUserKey` (with a synthetic `UserRoleRun` user) on success: [3](#0-2) 

Inside `prc.Create`, the code comment states "only users are allowed to run jobs using int IDs - EIs not allowed," and gates on `isUser` from `auth.GetAuthenticatedUser(c)`: [4](#0-3) 

Because `AuthenticateExternalInitiator` also sets `SessionUserKey`, `isUser` is `true` for EI-authenticated calls too, so the intended EI exclusion is ineffective. The handler then parses the path `:ID` as an integer job ID and calls `prc.App.RunJobV2(ctx, jobID, nil)` directly — there is no lookup of the job's `ExternalInitiatorWebhookSpec` to compare against `c.Get(SessionExternalInitiatorKey)`, and no use of `auth.GetAuthenticatedExternalInitiator` at all in this function. Any credential satisfying `RequiresRunRole` — a legitimate EI registered for an unrelated webhook job, or a minimal-privilege run-role user/API token — can therefore trigger a run for any job ID on the node, not just the job(s) associated with that EI.

### Impact Explanation
This allows an attacker holding any valid run-role credential (including an External Initiator credential provisioned for a completely unrelated job) to trigger pipeline execution for arbitrary jobs on the node, including jobs that perform fund-related actions (e.g., ETH transfer tasks, VRF fulfillment, other webhook-triggered pipelines). This is unauthorized job-run triggering / authorization bypass, matching Chainlink's "unauthorized job run or fund movement" bounty impact class.

### Likelihood Explanation
Exploitation only requires possession of any valid run-role-granting credential — the lowest privilege tier explicitly supported by this endpoint (EI credential, run-role user session, or run-role API token). No admin/edit privileges, no knowledge of the target job's EI association, and no additional bypass are needed; a simple `POST /v2/jobs/:ID/runs` with a differing job ID than the one the EI/credential was intended for succeeds because the code performs no per-job binding check. This is trivially repeatable.

### Recommendation
In `prc.Create`, when the authenticated principal is an External Initiator (`auth.GetAuthenticatedExternalInitiator`), look up the job's `ExternalInitiatorWebhookSpec` and confirm `ExternalInitiatorID` matches the authenticated EI's ID before calling `RunJobV2`; return 403/404 otherwise. Additionally, fix the `isUser` detection so that EI-only sessions (which currently also populate `SessionUserKey`) are not treated as ordinary users — e.g., check `auth.GetAuthenticatedExternalInitiator` first and branch explicitly, rather than relying solely on `SessionUserKey` presence.

### Proof of Concept
Handler-level Go test plan for `core/web/pipeline_runs_controller_test.go`:
1. Create two jobs, JobA with a webhook spec bound to `ExternalInitiator-A`, and JobB with a webhook spec bound to `ExternalInitiator-B` (or no EI association at all).
2. Authenticate as `ExternalInitiator-B` (via `AuthenticateExternalInitiator` headers) and send `POST /v2/jobs/{JobA.ID}/runs`.
3. Assert the current (vulnerable) behavior: the request succeeds (HTTP 200 with a `pipelineRun` resource) and `RunJobV2` was invoked for JobA despite `ExternalInitiator-B` having no association with it.
4. After the fix, assert the same request returns 403/404 and `RunJobV2` is never called, while a request from `ExternalInitiator-A` for `JobA.ID` still succeeds.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
