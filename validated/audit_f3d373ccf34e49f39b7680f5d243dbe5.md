### Title
Silent fallback to root bank on cache-miss allows wrong-slot/fork data to be returned for confirmed/finalized RPC queries - (File: `rpc/src/rpc.rs`)

### Summary
`JsonRpcRequestProcessor::bank()` resolves the `Bank` to use for confirmed/finalized RPC queries by looking up a slot in `BlockCommitmentCache` and then fetching that slot from `BankForks`. When that specific slot is missing from `BankForks` (a documented, acknowledged race), the code silently substitutes `root_bank()` instead of returning an error, causing wrong-slot/fork data to be returned to the RPC caller.

### Finding Description
`fn bank()` computes `slot` from `block_commitment_cache.slot_with_commitment(commitment.commitment)` and then does: [1](#0-0) 

```rust
let r_bank_forks = self.bank_forks.read().unwrap();
r_bank_forks.get(slot).unwrap_or_else(|| {
    // We log a warning instead of returning an error, because all known error cases
    // are due to known bugs that should be fixed instead.
    //
    // The slot may not be found as a result of a known bug in snapshot creation, where
    // the bank at the given slot was not included in the snapshot.
    // Also, it may occur after an old bank has been purged from BankForks and a new
    // BlockCommitmentCache has not yet arrived. To make this case impossible,
    // BlockCommitmentCache should hold an `Arc<Bank>` everywhere it currently holds
    // a slot.
    //
    // For more information, see https://github.com/solana-labs/solana/issues/11078
    warn!(
        "Bank with {:?} not found at slot: {:?}",
        commitment.commitment, slot
    );
    r_bank_forks.root_bank()
})
```

This is directly analogous to the reported bug class: a function returns a "best effort" value instead of validating/erroring on the expected result, and callers unconditionally accept whatever is returned. Here, instead of surfacing an error when the requested-commitment slot cannot be resolved (analogous to disabled slippage control accepting any `netTokenOut`), the code silently substitutes `root_bank()` — which can be a completely different, older slot/fork than what the caller's `commitment` (`processed`/`finalized`) requested.

`fn bank()` is the underlying primitive for `get_bank_with_config()` [2](#0-1)  and is reachable, unauthenticated, from many public JSON-RPC handlers including `getAccountInfo`, `getMultipleAccounts`, `getProgramAccounts`, `getBalance`, `getSlot`, `getBlockHeight`, `getTokenAccountBalance`, `getTokenSupply`, etc. [3](#0-2) [4](#0-3) . Since `min_context_slot` is checked only against `bank.slot()` *after* this substitution occurs (`get_bank_with_config`), a client requesting `min_context_slot` protection could still be silently served data from the root bank if the fallback triggers, and the check would pass or fail based on the substituted bank's slot rather than the truly intended commitment slot.

### Impact Explanation
This causes queries (`getAccountInfo`, `getBalance`, `getProgramAccounts`, `getTokenAccountBalance`, etc.) to silently return account/balance data from the wrong slot/fork (the root bank) rather than the slot corresponding to the client-requested commitment level, with no error returned to the caller. This falls squarely into the accepted "wrong-slot/fork/account data returned" impact category — the caller has no way to detect that the response context does not correspond to the commitment level they requested, other than noticing an unexpected `context.slot`.

### Likelihood Explanation
The condition is triggered purely by node/internal state (a race between `BlockCommitmentCache` update and `BankForks` bank purge, or a snapshot-creation gap), and is reachable via a single normal RPC call from an unprivileged client (no special commitment/messages needed beyond calling `getAccountInfo`/`getBalance`/etc. with `commitment: "confirmed"` or `"finalized"`). The code comment itself acknowledges this is a "known bug" scenario that recurs, referencing the historical issue https://github.com/solana-labs/solana/issues/11078, indicating the race is realistically triggerable in production under normal validator/bank-forks churn rather than purely theoretical.

### Recommendation
Do not silently substitute `root_bank()` when the desired commitment slot cannot be found in `BankForks`. Instead, return an explicit RPC error (e.g. reuse `RpcCustomError::MinContextSlotNotReached`-style handling or a dedicated error) so callers can retry rather than silently receiving stale/wrong-fork data. Alternatively, as suggested in the existing code comment, have `BlockCommitmentCache` hold an `Arc<Bank>` directly instead of a bare `Slot`, eliminating the possibility of the referenced bank being purged from `BankForks` before it is used.

### Proof of Concept
1. Observe the race window described in the code comment: `BlockCommitmentCache` is updated to point at slot `N`, but before RPC processes a request, `N` gets purged from `BankForks` (old bank pruning) while a fresh commitment-cache update for a newer slot hasn't landed yet — or a snapshot-creation gap causes bank `N` to be absent from `BankForks` entirely.
2. Issue an unprivileged RPC call, e.g. `getAccountInfo`/`getBalance` with `{"commitment": "confirmed"}` (or `"finalized"`), during this window.
3. `fn bank()` computes `slot = N` from the commitment cache, `r_bank_forks.get(N)` returns `None`, and the function falls back to `r_bank_forks.root_bank()` — a different (potentially much older) bank/slot/fork than the one the requested commitment level was supposed to guarantee.
4. The RPC response is returned successfully (no error) with `context.slot` and account data corresponding to the substituted root bank instead of the caller's requested commitment slot, with only a `warn!` log on the validator side and nothing surfaced to the client.

    fn get_bank_with_config(&self, config: RpcContextConfig) -> Result<Arc<Bank>> {
        let RpcContextConfig {
            commitment,
            min_context_slot,
        } = config;
        let bank = self.bank(commitment);
        if let Some(min_context_slot) = min_context_slot
            && bank.slot() < min_context_slot
        {
            return Err(RpcCustomError::MinContextSlotNotReached {
                context_slot: bank.slot(),
            }
            .into());
        }
        Ok(bank)
    }

            min_context_slot,

        let bank = self.get_bank_with_config(RpcContextConfig {
            commitment,
            min_context_slot,
        })?;
        let encoding = encoding.unwrap_or(UiAccountEncoding::Base64);

        let mut accounts = Vec::with_capacity(pubkeys.len());
        for pubkey in pubkeys {
            let bank = Arc::clone(&bank);
            accounts.push(
                self.runtime
                    .spawn_blocking(move || {
                        get_encoded_account(&bank, &pubkey, encoding, data_slice, None)
                    })
                    .await
                    .expect("rpc: get_encoded_account panicked")?,
            );
        }
        Ok(new_response(&bank, accounts))
    }

    pub fn confirm_transaction(
        &self,
        signature: &Signature,
        commitment: Option<CommitmentConfig>,
    ) -> Result<RpcResponse<bool>> {
        let bank = self.bank(commitment);
        let status = bank.get_signature_status(signature);
        match status {
            Some(status) => Ok(new_response(&bank, status.is_ok())),
            None => Ok(new_response(&bank, false)),
        }
    }

    fn get_block_commitment(&self, block: Slot) -> RpcBlockCommitment<BlockCommitmentArray> {
