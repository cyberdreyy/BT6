### Title
Cross-Module Display Hijack via Package-Level Publisher Check in `new_with_publisher` — (`crates/sui-framework/packages/sui-framework/sources/registries/display_registry.move`)

### Summary

`new_with_publisher<T>` and `claim_with_publisher<T>` use `publisher.from_package<T>()` to authorize display creation, which only verifies the **package address** matches. A `Publisher` obtained from any module's OTW in a multi-module package passes this check for **all types in the package**, including types defined in sibling modules. The invariant that only the publisher of the specific module defining `T` may create the canonical `Display<T>` is violated.

### Finding Description

`Publisher` records both a `package` address and a `module_name`. The `from_package<T>` check only compares the package address of `T` against `self.package`, ignoring `module_name`. In a package with modules `A` and `B`, the `Publisher` obtained from module A's OTW has `module_name = "a"` but `package = <shared_package_address>`. Calling `new_with_publisher<TypeFromModuleB>(registry, publisher_a, ctx)` passes the `from_package<TypeFromModuleB>()` check because both types share the same package address. The function then calls `new_display<TypeFromModuleB>`, which creates and registers the canonical derived-object `Display<TypeFromModuleB>` in the `DisplayRegistry` under `DisplayKey<TypeFromModuleB>`, with the `DisplayCap<TypeFromModuleB>` owned by the attacker.

### Impact Explanation

Once the attacker creates `Display<TypeFromModuleB>`, the `DisplayRegistry` derived-object slot for `DisplayKey<TypeFromModuleB>` is permanently occupied. Any subsequent call by the legitimate module B publisher to `new_with_publisher<TypeFromModuleB>` or `new<TypeFromModuleB>` will abort with `EDisplayAlreadyExists`. The attacker permanently controls the canonical display metadata for `TypeFromModuleB` — they can set arbitrary `name`, `image_url`, `description`, etc. fields via `set`/`unset`/`clear` using their `DisplayCap<TypeFromModuleB>`. This is unauthorized object creation causing permanent state corruption of the system-level `DisplayRegistry` and permanent lock-out of the legitimate type owner from the canonical display slot.

### Likelihood Explanation

Any publisher of a multi-module package can exploit this at publish time or any time after, against any sibling module's types, as long as no `Display<T>` has been created yet for the target type. No special privileges beyond being a co-publisher in the same package are required.

### Recommendation

Replace `from_package<T>()` with `from_module<T>()` in both `new_with_publisher` and `claim_with_publisher`:

```move
// display_registry.move line 69
assert!(publisher.from_module<T>(), ENotValidPublisher);

// display_registry.move line 118
assert!(publisher.from_module<T>(), ENotValidPublisher);
```

This ensures only the publisher of the exact module that defines `T` can create or claim the canonical display for `T`.
