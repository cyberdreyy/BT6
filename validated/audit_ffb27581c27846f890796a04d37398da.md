Confirmed: `programs/marginfi/src/instructions/solend/withdraw.rs` implements the "receivership/order-execution" gating logic inconsistently with the other three integration withdraw handlers (`kamino/withdraw.rs`, `drift/withdraw.rs`, `juplend/withdraw.rs`). This is the same bug class described in the external report — a check/fix that exists in several sibling implementations was not carried over to one structurally identical sibling.

### Title
Solend withdraw ignores `ACCOUNT_IN_ORDER_EXECUTION`, skipping oracle price validation that Kamino/Drift/Juplend enforce - (File: `programs/marginfi/src/instructions/solend/withdraw.rs`)

### Summary
`solend_withdraw` derives its price-fetch/zero-price gating solely from `ACCOUNT_IN_RECEIVERSHIP`, while `kamino_withdraw`, `drift_withdraw`, and `juplend_withdraw` all gate the same logic on `ACCOUNT_IN_RECEIVERSHIP | ACCOUNT_IN_ORDER_EXECUTION`. This is the same "fix applied to sibling implementations but missed in one" defect pattern as the ConvexSpell/CurveSpell report.

### Finding Description
In `kamino_withdraw`, `drift_withdraw`, and `juplend_withdraw`, the price used for rate-limiting/deleverage tracking is computed like this: [1](#0-0) [2](#0-1) [3](#0-2) 

All three treat `in_receivership_or_order_execution = get_flag(ACCOUNT_IN_RECEIVERSHIP | ACCOUNT_IN_ORDER_EXECUTION)` as the trigger for (a) fetching a live oracle price and (b) requiring `check!(price > I80F48::ZERO, MarginfiError::ZeroAssetPrice)`.

`solend_withdraw` instead only checks `ACCOUNT_IN_RECEIVERSHIP`: [4](#0-3) 

The same divergence repeats at the end of the instruction, where the other three integrations skip the final `check_account_init_health` call using `ACCOUNT_IN_RECEIVERSHIP | ACCOUNT_IN_ORDER_EXECUTION` (see e.g. `drift/withdraw.rs:273-275`, `juplend/withdraw.rs:282-287`, `kamino/withdraw.rs:241-246`), while `solend_withdraw` only skips it for `in_receivership` (`solend/withdraw.rs:241,245`).

The `ACCOUNT_IN_ORDER_EXECUTION` flag and its withdraw/repay flow (`StartExecuteOrder`/`EndExecuteOrder`) are documented as applying broadly across integrations: the withdraw handlers explicitly comment "during liquidation/deleverage or order execution, we skip health checks until the end of the transaction," confirming this is a deliberate, cross-integration invariant that the Solend path violates.

### Impact Explanation
When a Keeper executes a conditional order (`StartExecuteOrder` → withdraw/repay → `EndExecuteOrder`) involving a Solend-backed bank and the group rate limiter is disabled:
- The `price` used for the deleverage-withdraw-limit accounting (`calc_value`/`check_deleverage_withdraw_limit`, only reached if `ACCOUNT_IN_DELEVERAGE` is also set) is silently `I80F48::ZERO` instead of a live oracle price, because the fetch is gated only on `in_receivership`, which is false during order execution.
- Unlike the sibling integrations, there is no `check!(price > I80F48::ZERO, ...)` guard for order execution, so a zero/never-fetched price is not rejected — the safety net that exists everywhere else for exactly this state is absent for Solend.
- The health check at the end of `solend_withdraw` is not skipped during order execution, unlike Kamino/Drift/Juplend, breaking the intended "defer all risk checks to `EndExecuteOrder`" invariant for Solend-only orders. This inconsistency can either cause spurious mid-flow failures of otherwise valid order executions (denial of service for legitimate Solend positions) or, more importantly, undermines whichever accounting relies on `in_receivership_or_order_execution` semantics being uniformly applied across integrations for withdrawal-limit enforcement.

The overall effect mirrors the sherlock report's class: a security control (zero/stale-price rejection during a privileged, time-boxed withdrawal window) that was fixed/added consistently for three integrations is missing for a fourth structurally identical one.

### Likelihood Explanation
This requires a marginfi group to actually have a Solend-integrated bank configured as part of an executable order (asset or liability leg), and for the group's rate limiter to be disabled (a legitimate, supported configuration, since the check is `if in_receivership_or_order_execution || group_rate_limit_enabled`). Order execution is a permissionless-keeper-driven flow reachable by any keeper, so no privileged access is required to trigger the code path; the missing branch is purely a logic/consistency gap, not a theoretical one, since the exact same flag combination is exercised and tested for Kamino/Drift/Juplend withdraws in this repo's test suite (e.g., `tests/specs/limits/m03_liquidationLimits.spec.ts` exercises Kamino/Drift/Juplend withdraws in liquidation limit paths, and `tests/specs/basic/16_orders.spec.ts` exercises order-execution withdraws), but no equivalent Solend + order-execution price/health-skip test exists.

### Recommendation
Update `programs/marginfi/src/instructions/solend/withdraw.rs::solend_withdraw` to match the pattern used in `kamino_withdraw`/`drift_withdraw`/`juplend_withdraw`:
1. Compute `in_receivership_or_order_execution = marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP | ACCOUNT_IN_ORDER_EXECUTION)` and use it (instead of the bare `in_receivership`) to decide whether to fetch a live oracle price and to enforce `check!(price > I80F48::ZERO, MarginfiError::ZeroAssetPrice)`.
2. Use the same combined flag to decide whether to skip the final `check_account_init_health` call, mirroring `drift/withdraw.rs:273-275` and `juplend/withdraw.rs:282-287`.

### Proof of Concept
Not independently reproduced in this analysis (no sandbox/test execution available); the divergence is demonstrated purely by side-by-side code comparison:
- Kamino/Drift/Juplend: `in_receivership_or_order_execution = get_flag(ACCOUNT_IN_RECEIVERSHIP | ACCOUNT_IN_ORDER_EXECUTION)` gates both the price fetch/zero-check and the end-of-instruction health-check skip.
- Solend (`solend/withdraw.rs:92,241,245`): only `get_flag(ACCOUNT_IN_RECEIVERSHIP)` is used in both places, omitting `ACCOUNT_IN_ORDER_EXECUTION`.

To confirm the exploitable impact, a Devin agent with test-execution access should: (1) set up a marginfi group with a Solend bank and rate limiter disabled, (2) place and trigger a Stop-Loss/Take-Profit order using the Solend bank as the withdrawn leg, (3) assert whether `check_account_init_health` incorrectly fires mid-flow (breaking legitimate order executions) and/or whether `price` is silently zero for any downstream accounting reached via `ACCOUNT_IN_DELEVERAGE`-gated code during order execution.

                check!(price > I80F48::ZERO, MarginfiError::ZeroAssetPrice);
            }

            price
        } else {
            I80F48::ZERO
        };
