### Title
Stale per-epoch instant-withdraw ledger after funded claim inflates default-epoch claim basis and permanently freezes recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` but never cleans up the per-epoch entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` that were written in `requestInstantWithdraw`. If the borrower defaults in that same epoch while other instant receipts remain unfunded, `defaultPendingClaimBasis` counts the already-claimed (already-paid) receipts again, the finalized recovery price is diluted, and the portion of `defaultRecoveryReserve` attributed to the phantom claims can never be paid out — `_claimDefaultedInstantWithdrawRequest` reverts on underflow for the already-paid user — so recovered underlying is permanently locked in the strategy.

### Finding Description
On request, the vault records both a global per-epoch total and a per-user per-epoch receipt:

- `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount`
- `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (IdleCreditVault.sol, `requestInstantWithdraw`, ~L367-374)

On a normal (funded) claim the cleanup is incomplete — only the aggregate is zeroed:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

(`claimInstantWithdrawRequest`, ~L387-392). Neither `instantWithdrawsRequestsByEpoch[_user][epoch]` nor `instantWithdrawClaimsByEpoch[epoch]` is decremented. The only place those per-epoch ledgers are cleared is `_claimDefaultedInstantWithdrawRequest`, which is reachable only after default finalization.

Later, if the borrower defaults and `finalizeDefaultRecovery` runs while `epochNumber` still equals that epoch (the strategy epoch number is not bumped on default — see `_prefundedEpochToProcess` comment in `IdleCDOEpochQueue.sol` L285-290), then:

1. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` — this value still includes the already-claimed receipts (L644-649).
2. `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is therefore understated, and `defaultInstantWithdrawsFinalized` is set true (L688-696).
3. When the already-paid user (or anyone) triggers `claimInstantWithdrawRequest` → `_claimDefaultedInstantWithdrawRequest`, `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` returns the stale amount, but `instantWithdrawsRequests[_user] -= claimBasis` underflows (user aggregate is 0), reverting (L844-848). The share of `defaultRecoveryReserve` earmarked for that phantom claim can never be distributed.

This is the direct analog of CVE-2020-24489's "incomplete cleanup": stale per-epoch receipt state survives its lifecycle and poisons a later security-critical accounting path.

### Impact Explanation
Two compounding harms, both with quantified fund impact:

- **Recovery dilution / theft from honest claimants**: `defaultRecoveryPrice` is computed against an inflated `totalBasis` (default-epoch instant basis includes funds already paid out 1:1). Every legitimate defaulted-epoch receipt holder and every active tranche holder (whose NAV is minted/burned to `activeBasis * recoveryPrice`) recovers strictly less than they should.
- **Permanent freezing of recovered funds**: the reserve fraction allocated to phantom receipts (`staleAmount * recoveryPrice`) is undistributable — the stale user's claim path reverts, and no other function drains `defaultRecoveryReserve`. Those recovered underlyings are locked in `IdleCreditVault` forever.

Example: epoch E, attacker requests instant withdraw of 100, victim requests 50. Borrower/CDO funds 100 via `collectInstantWithdrawFunds` (pendingInstantWithdraws: 150 → 50). Attacker claims 100 at par. Borrower defaults at stop of epoch E. `defaultPendingClaimBasis` reports 150 instead of 50, so a real recovery of e.g. 50 produces price 1/3 instead of 1. The ~33.3 underlying attributed to the attacker's phantom receipt is permanently frozen, and all other claimants' recovery is scaled down by the same factor.

### Likelihood Explanation
Requires instant withdrawals enabled (`allowInstantWithdraw`), a borrower default in the same epoch where some instant receipts were funded-and-claimed while others remain pending, and default finalization. Defaults are an anticipated, in-scope flow (`_handleBorrowerDefault`, `finalizeDefaultRecovery`, `DefaultDistributor`). The attacker is an ordinary KYC-passed lender performing only allowed calls (`requestInstantWithdraw` → `claimInstantWithdrawRequest`); no privileged or malicious role is needed, and no existing guard (skim, default reverts, epoch gating) clears the stale per-epoch entries.

### Recommendation
In `claimInstantWithdrawRequest`, clean up the per-epoch ledgers alongside the aggregate: decrement `instantWithdrawClaimsByEpoch[requestEpoch]` and delete `instantWithdrawsRequestsByEpoch[_user][requestEpoch]` for the epoch(s) being claimed (tracking the request epoch analogously to `lastWithdrawRequest`). Alternatively, make `defaultPendingClaimBasis`/`_claimDefaultedInstantWithdrawRequest` compute basis from `instantWithdrawsRequests`-consistent state rather than the unstale-checked per-epoch mappings.

### Proof of Concept
Foundry fork PoC outline (mirroring `test/foundry/IdleCDOEpochQueue.t.sol` instant-withdraw setup):

```solidity
// Setup: standard IdleCDOEpochVariant + IdleCreditVault, instant withdraws enabled.
cdoEpoch.setInstantWithdrawParams(instantDelay, minAprDiff, false); // manager

// Epoch E running. Attacker A and victim B both request instant withdraws.
cdoEpoch.requestInstantWithdraw(100e6, AATranche); // as A, burns tranches, mints receipts
cdoEpoch.requestInstantWithdraw(50e6,  AATranche); // as B

// CDO funds only 100e6 of instant claims from borrower/cash.
// (via getInstantWithdrawFunds/collectInstantWithdrawFunds path)
// pendingInstantWithdraws == 50e6; instantWithdrawClaimsByEpoch[E] == 150e6

// A claims at par — funded claim path.
cdoEpoch.claimInstantWithdrawRequest(); // as A: receives 100e6
// BUG: instantWithdrawsRequestsByEpoch[A][E] still == 100e6,
//      instantWithdrawClaimsByEpoch[E]   still == 150e6

// Borrower defaults at stop of epoch E; manager/owner finalizes recovery.
cdoEpoch.stopEpochWithDuration(...);    // triggers _handleBorrowerDefault
cdoEpoch.finalizeDefaultRecovery(recovered, source); // epochNumber still E

// Assertions:
// 1. defaultPendingClaimBasis() counted 150e6 instant basis, not 50e6.
// 2. defaultRecoveryPrice is diluted by factor 1/3 vs correct.
// 3. A's claim path reverts on instantWithdrawsRequests[A] underflow:
vm.expectRevert(); cdoEpoch.claimInstantWithdrawRequest(); // as A
// 4. strategy retains ~100e6 * recoveryPrice of defaultRecoveryReserve
//    that no account can ever claim — permanently frozen.
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
