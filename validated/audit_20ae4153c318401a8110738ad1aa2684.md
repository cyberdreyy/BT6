### Title
Stale write-off requests remain fulfillable after `stopEpoch`, letting any fulfiller buy tranches at pre-interest pricing - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` requires the epoch to be running when a lender escrows tranche tokens and quotes an underlyings amount, but `fullfillWriteOffRequest` performs no freshness or epoch-state validation. Once `stopEpoch` credits accrued interest and raises the tranche virtual price, the escrowed request still pays out at the stale quote. Any unprivileged fulfiller can buy the lender's tranches below their post-stop value and capture the accrued epoch yield.

### Finding Description
The escrow models a two-sided order: the lender deposits `tranche` tokens and fixes `underlyings` in `createWriteOffRequest` (IdleCreditVaultWriteOffEscrow.sol:86-102), which is gated by `isEpochRunning()`. The counterpart, `fullfillWriteOffRequest` (IdleCreditVaultWriteOffEscrow.sol:123-155), only checks:

```solidity
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
  revert WrongRequest();
}
```

There is no check that the epoch is still running, no expiry, and no re-pricing against `IdleCDOEpochVariant.virtualPrice(tranche)`. Requests therefore survive across `stopEpoch`, where `_updateAccounting`/`_mintSharesAtCurrPrice`-equivalent NAV updates bake realized borrower interest into the tranche price. A quote that was fair at request time becomes underpriced the moment the epoch is stopped with positive interest, and the fulfiller receives the now-more-valuable tranche tokens for the stale underlyings amount.

### Impact Explanation
Direct theft of accrued yield from a write-off-requesting lender. The lender asked for `U` underlyings when the tranche price was `P0`; after `stopEpoch` the same tranches are worth `U' = T * P1 > U`. The fulfiller pays only `U` (minus the ≤1% exit fee borne by the lender) and immediately owns tranches redeemable for `U'`, extracting `U' - U` ≈ the tranche's share of one epoch's interest on the escrowed amount. The theft is bounded by one epoch of tranche yield per request (e.g., ~`apr * epochDuration` on the escrowed NAV), scales linearly with request size, and can be repeated across every open request and both tranches. The lender's only defense, `deleteWriteOffRequest`, races with fulfillment; the fulfiller can execute atomically in the same block as `stopEpoch` (or via private mempool ordering) before the lender can cancel.

### Likelihood Explanation
High whenever write-off requests exist across an epoch boundary: it requires only that a lender created a request during a running epoch and did not cancel before `stopEpoch`. The attacker is any unprivileged EOA (a "write-off fulfiller" is an explicitly allowed role); no privileged action is needed beyond the honest manager/borrower `stopEpoch` flow, which the attacker simply sequences around. The analogous bug class from CVE-2021-21163 — insufficient validation letting stale/cross-context data be consumed as if current — is present verbatim: a price quote valid only in the running-epoch context is honored in the post-stop context.

### Recommendation
Gate `fullfillWriteOffRequest` on `IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()` (matching `createWriteOffRequest`), or record the epoch number / NAV snapshot at request creation and re-price or invalidate the request once `epochNumber` advances. Alternatively, cap fulfillment validity with an explicit lender-chosen expiry timestamp.

### Proof of Concept
Foundry fork/unit PoC sketch (patterned on `test/foundry/IdleCreditVault.t.sol` helpers `_startEpochAndCheckPrices`, `_depositWithUser`):

```solidity
function testStaleWriteOffFulfilledAfterStopEpoch() external {
  // 1. Epoch running: lender deposits in AA and escrows tranches
  uint256 amount = 10_000 * ONE_SCALE;
  idleCDO.depositAA(amount);                       // lender is KYC'd
  uint256 tranches = IERC20(AAtranche).balanceOf(address(this));
  uint256 price0 = cdoEpoch.virtualPrice(AAtranche);
  uint256 ask = tranches * price0 / ONE_TRANCHE;   // fair quote at P0
  IERC20(AAtranche).approve(address(escrow), tranches);
  escrow.createWriteOffRequest(tranches, ask);

  // 2. Honest flow: epoch ends, borrower repays principal + interest
  vm.warp(cdoEpoch.epochEndDate() + 1);
  uint256 interest = cdoEpoch.expectedEpochInterest();
  deal(underlying, borrower, pending + interest);
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, interest);                 // virtualPrice now P1 > P0

  // 3. Attacker (any fulfiller) buys at stale quote in same block
  address fulfiller = makeAddr("fulfiller");
  deal(underlying, fulfiller, ask);
  vm.startPrank(fulfiller);
  IERC20(underlying).approve(address(escrow), ask);
  escrow.fullfillWriteOffRequest(address(this), tranches, ask);
  vm.stopPrank();

  // 4. Stolen value = accrued epoch yield on escrowed tranches
  uint256 worth = tranches * cdoEpoch.virtualPrice(AAtranche) / ONE_TRANCHE;
  assertGt(worth, ask);                            // fulfiller profit = worth - ask
}
```

No existing guard blocks step 3: `fullfillWriteOffRequest` checks neither `isEpochRunning` nor request age, and the skim/epoch gating in `IdleCDOEpochVariant` does not cover the escrow.
