### Title
Dust withdrawal request permanently reverts `processWithdrawRequests`, freezing all queued withdrawals for the epoch - ([File: contracts/IdleCDOEpochQueue.sol](contracts/IdleCDOEpochQueue.sol))

### Summary
The external finding's bug class — a single poisoned element that makes an aggregate processing function revert, blocking downstream fund releases — maps directly onto `IdleCDOEpochQueue.processWithdrawRequests`. A withdrawal epoch is processed as one aggregate call: all tranche tokens queued in `epochPendingWithdrawals[_epoch]` are passed to `IdleCDOEpochVariant.requestWithdraw(_pending, tranche)` and the implied price `_underlyingsRequested * ONE_TRANCHE / _pending` is stored. The function hard-reverts with `Is0()` when that price rounds to 0. Any unprivileged, KYC-passed tranche holder can queue a dust-sized `requestWithdraw` whose converted underlying amount is so small that the aggregate epoch price computes to 0, bricking processing for every user who queued a withdrawal in the same epoch.

### Finding Description
In `requestWithdraw` (queue), an attacker deposits tranche tokens and registers a withdrawal for `nextEpoch` at `userWithdrawalsEpochs[msg.sender][nextEpoch]` / `epochPendingWithdrawals[nextEpoch]` (contracts/IdleCDOEpochQueue.sol:131-143). There is no minimum amount.

During the buffer period the owner/manager calls `processWithdrawRequests` (contracts/IdleCDOEpochQueue.sol:298-329):

```solidity
uint256 _underlyingsRequested = _cdo.requestWithdraw(_pending, tranche);
uint256 _epochPrice = _underlyingsRequested * ONE_TRANCHE / _pending;
if (_epochPrice == 0) {
  revert Is0();
}
```

`_underlyingsRequested` is produced inside `IdleCDOEpochVariant.requestWithdraw` via `_trancheToUnderlyings(_amount, _tranche)` = `_amount * _tranchePrice(_tranche) / ONE_TRANCHE_TOKEN`, then adjusted by `_calcInterestWithdrawRequest` minus `_totalWithdrawFees` (contracts/IdleCDOEpochVariant.sol:739-791, 815-817, 856-906). Management fees are charged upfront for a full epoch plus remaining buffer (`_withdrawRequestManagementFeeDuration`), so for a dust tranche amount `principal + interest - totalFees` can be a tiny positive number or, at a tranche price below 1e18, `principal` itself rounds below `_pending`, making `_epochPrice == 0`. The in-repo test `testProcessWithdrawRequestsWith0Price` demonstrates exactly this path: a `requestWithdraw` of 100 wei tranche tokens makes `processWithdrawRequests` revert with `Is0` (test/foundry/IdleCDOEpochQueue.t.sol:1431-1456).

Because the whole call reverts, `epochPendingWithdrawals[_epoch]` is never reset, `epochWithdrawPrice[_epoch]` stays 0, `pendingClaims` is unaffected but the epoch can never be processed — every revert leaves the poisoned dust request in place. The only unstick paths are (a) the attacker calls `deleteWithdrawRequest` (which is only blocked *after* a price is set, contracts/IdleCDOEpochQueue.sol:203-218) or (b) the honest owner/manager cannot remove individual requests at all — there is no admin function to drop a single user's request. The attacker can re-create the dust request every epoch at near-zero cost (only tranche token transfer, tokens are even refundable via `deleteWithdrawRequest` before processing), so for the cost of one transaction per epoch they keep the queue's withdrawal pipeline permanently DoSed while honest users' tranche tokens sit locked in the queue contract.

This is the same structural flaw as the PoH finding: there, `processVouches` reverted on a single vouch whose `requestCount` was 0, blocking `executeRequest` for everyone; here, `processWithdrawRequests` reverts on a single dust request whose implied price is 0, blocking claims for every user in that epoch.

### Impact Explanation
All tranche tokens queued in `epochPendingWithdrawals` for the targeted epoch are frozen: users cannot get underlyings (processing never completes, so `epochWithdrawPrice` stays 0 and `claimWithdrawRequest` reverts via the `_withdrawPrice == 0 && !isEpochWithdrawZero` check at contracts/IdleCDOEpochQueue.sol:396-399), and they cannot get their tranche tokens back because `deleteWithdrawRequest` returns tokens only to the requester — each honest user can delete their own request, but the aggregate still contains the attacker's dust and keeps reverting, so the epoch can never settle. Net effect: temporary but indefinitely renewable freezing of all queued withdrawals in the queue contract, at negligible cost to the attacker (the dust request can be recycled each epoch). On a queue holding meaningful queued TVL this is a full withdrawal DoS.

### Likelihood Explanation
Requires only a KYC-passing wallet holding a dust amount of tranche tokens and one `requestWithdraw` call per epoch while the epoch is running — permissionless under the stated threat model. No privileged action, oracle manipulation, or borrower cooperation needed. The revert path is already exercised by the repository's own test (`testProcessWithdrawRequestsWith0Price`), confirming the 0-price condition is reachable with a 100-wei request at ordinary prices.

### Recommendation
Handle dust/zero-value requests gracefully instead of reverting the whole batch, e.g.:
- enforce a minimum `requestWithdraw` amount in the queue (in underlying terms at current `virtualPrice`), or
- in `processWithdrawRequests`, treat a 0-implied-price epoch like the existing zero-payout path: set `isEpochWithdrawZero[_epoch] = true`, reset `epochPendingWithdrawals[_epoch]`, and burn/escrow the tranche tokens rather than reverting, or
- return the raw tranche tokens pro-rata to requesters when `_epochPrice == 0` instead of reverting.

The zero-payout machinery added in `processWithdrawalClaims` (`isEpochWithdrawZero`) is the established pattern for a claim that legitimately settles to 0; the same treatment should apply at request-processing time.

### Proof of Concept
Foundry fork-style PoC, derived directly from `testProcessWithdrawRequestsWith0Price` in `test/foundry/IdleCDOEpochQueue.t.sol`:

```solidity
function testDustWithdrawRequestDoS() external {
    // buffer period, epoch #1 setup
    _stopCurrentEpoch();

    // honest user queues a large withdraw
    address honest = makeAddr('honest');
    uint256 tranches = _depositWithUser(honest, 100e6);
    vm.prank(manager);
    cdoEpoch.startEpoch();
    _requestWithdrawWithUser(honest, tranches);

    // attacker queues a dust withdraw in the same epoch
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 1e6);
    _requestWithdrawWithUser(attacker, 100); // 100 wei tranche tokens

    // end epoch -> buffer
    _stopCurrentEpoch();

    // aggregate processing reverts on the dust request -> whole epoch bricked
    vm.expectRevert(abi.encodeWithSelector(Is0.selector));
    vm.prank(manager);
    queue.processWithdrawRequests();

    // epochWithdrawPrice stays 0 -> honest user cannot claim and cannot be
    // unblocked by owner/manager; only the attacker can delete its request
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    vm.prank(honest);
    queue.claimWithdrawRequest(strategy.epochNumber());
}
```

The attacker repeats the dust `requestWithdraw` each subsequent epoch to keep the DoS alive indefinitely.
