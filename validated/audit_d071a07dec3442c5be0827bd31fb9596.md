### Title
Removing a multisig member/key does not purge their existing confirmations on other pending requests, allowing a request to execute below the live-member confirmation threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
When a multisig member (or access key) is removed via `DeleteKey`/`DeleteMember`, the contract only deletes requests that member *created*, and clears `num_requests_pk` for them. It never scans the `confirmations` map to strip that member's votes from *other* pending requests they had already confirmed but did not create. Those stale confirmations remain counted toward `num_confirmations` on future `confirm()` calls, so a request can be executed using a confirmation from an account/key that is no longer an authorized multisig member — breaking the binding "confirmations counted == confirmations from live members."

### Finding Description
`confirm()` in both `multisig/src/lib.rs` and `multisig2/src/lib.rs` decides whether to execute a request purely by comparing the size of the stored `confirmations` `HashSet` against `self.num_confirmations`: [1](#0-0) 

Membership is only checked for the *current* caller via `current_member()`/`assert_valid_request`, not for the confirmers already recorded in the set: [2](#0-1) 

When a member is removed, `delete_member` (multisig2) / the `DeleteKey` action (multisig) only clean up requests that were *created* by the removed member — it filters `self.requests` by `r.member == member` (or `r.signer_pk == pk`) and clears confirmations only for those requests. It does not iterate `self.confirmations` values to remove the departing member's vote from requests created by someone else: [3](#0-2) [4](#0-3) 

As a result, a confirmation cast by a member who is later removed remains permanently embedded in the `confirmations` set of any request they did not create, and is still counted by `confirm()`'s `len() + 1 >= num_confirmations` check.

This is the same bug class as the reported MysteryBox issue: an internal bookkeeping structure (owner/holder mapping in the ERC1155 case, confirmer set here) is never synchronized when the underlying authorization/ownership changes (token transfer there, member removal here), so a stale entry lets an operation succeed that should be blocked under the current, correct state.

### Impact Explanation
This crosses the "confirmations counted versus live members" custody boundary explicitly called out as in-scope: a `MultiSigRequestAction::Transfer` (or `AddKey`/`FunctionCall`/`DeployContract`) request can be executed with fewer live-member approvals than `num_confirmations` requires, because one of the "confirmations" belongs to an account that is no longer a member. This is a multisig request executed below threshold, which is explicitly listed as a Critical impact: it enables NEAR to be transferred, keys added, or code deployed on the multisig account with less real authorization than the configured K-of-N policy demands.

### Likelihood Explanation
This requires only ordinary, unprivileged multisig operation flow: a member confirms a pending request (their normal duty), and is later removed from the multisig for any routine reason (rotation, offboarding, compromise). No malicious action from the removed member is required — the remaining members trigger the bug purely by continuing to confirm the still-pending, older request. Because member turnover is an expected operational event for any long-lived multisig, this is a realistic and repeatable scenario, not a purely theoretical one.

### Recommendation
When removing a member/key (`DeleteMember` in `multisig2/src/lib.rs`, `DeleteKey` in `multisig/src/lib.rs`), iterate over all entries in `self.confirmations` (not just requests created by that member) and remove the departing member's/key's vote from every confirmation set. Alternatively, validate at `confirm()`-execution time that every account/key present in the stored `confirmations` set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request(request)` (e.g., `Transfer` to some receiver) → `request_id = 1`, confirmations = `{}`.
3. `B` calls `confirm(1)` → confirmations = `{B}`.
4. `C` calls `confirm(1)` → confirmations = `{B, C}` (2 < 3, so it just stores confirmations, per [5](#0-4) ).
5. Separately, the multisig (via its own normal 3-of-4 process) executes a `DeleteMember { member: C }` request, removing `C` from `self.members`. Per [6](#0-5) , this only removes requests created by `C`; request `1` (created by `A`) is untouched, and its confirmations set still contains `C`.
6. `D` calls `confirm(1)`. `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → the request executes per [7](#0-6) , even though only `B` and `D` are currently live members who confirmed; `C`'s vote is stale/unauthorized. The `Transfer` (or other) action executes with only 2 live-member confirmations against a nominal 3-of-4 policy.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
