### Title
Cross-epoch instant-withdraw over-read in `defaultPendingClaimBasis` undercounts the default recovery basis, inflating `defaultRecoveryPrice` and causing insolvency at the tail of defaulted claims — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.defaultPendingClaimBasis()` reads only `instantWithdrawClaimsByEpoch[epochNumber]` — the instant receipts recorded in the *current* epoch — while `pendingInstantWithdraws` is a global aggregate that survives across epochs. An attacker (any lender/tranche holder who requested an instant withdrawal in a prior epoch that was only partially funded) carries an unfunded instant receipt from epoch N into epoch N+k. When the borrower defaults and the CDO calls `finalizeDefaultRecovery`, the current-epoch-only read both undercounts `totalBasis` (inflating `defaultRecoveryPrice` so the reserve becomes insolvent before all claims pay) and miscomputes the prefunded reserve, leaving the attacker's receipt unclaimable while other claimants over-draw the recovery reserve.

### Finding Description
- `pendingInstantWithdraws` is only decremented by `collectInstantWithdrawFunds` (the funded amount) and is never epoch-scoped (contracts/strategies/idle/IdleCreditVault.sol:398-403).
- `instantWithdrawsRequestsByEpoch[user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` are written only for the epoch in which the request was made (lines 367-372).
- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` — only the current epoch's claims — whenever `pendingInstantWithdraws != 0` (lines 644-649). Prior-epoch unfunded receipts are the reason `pendingInstantWithdraws` is non-zero in the first place, yet they never enter `basis`.
- `_defaultPrefundedInstantReserve` uses the same current-epoch key: if the old-epoch remainder makes `pendingInstantWithdraws > instantWithdrawClaimsByEpoch[epochNumber]`, the already-collected underlying backing old receipts is *not* counted as reserve (lines 716-723), so `finalizeDefaultRecovery` stores a `defaultRecoveryReserve` that excludes funds actually sitting in the contract, and computes `recoveryPrice = reserveAmount * 1e18 / totalBasis` on an undercounted denominator (lines 685-699).
- At claim time, `_claimDefaultedInstantWithdrawRequest` only clears receipts keyed by `defaultRecoveryEpoch` (lines 842-856). A prior-epoch instant receipt falls through to the funded path in `claimInstantWithdrawRequest`, which burns the full `instantWithdrawsRequests[user]` and calls `_transferFundedClaim`; once the reserve covers the contract balance, that call reverts (`balance - reserve < amount`, lines 899-905), permanently freezing the attacker's-victim receipt — and symmetrically, any excess balance above the reserve is paid to prior-epoch claimants at par before the correctly-haircut default-epoch claimants are served.

### Impact Explanation
Broken invariant: loss waterfall / one-receipt-one-payout. `defaultRecoveryPrice` is overstated because `totalBasis` omits legacy-epoch instant receipts, so `defaultRecoveryReserve` is drained pro-rata too quickly and the last defaulted claimants' `_transferDefaultRecovery` reverts (insolvency). Conversely, prior-epoch instant receipts that escape the haircut can be paid at par from non-reserve balance, stealing recovery value from default-epoch claimants. Loss equals the inflated-price overpayment multiplied across claims, i.e. `reserve * (1 - trueBasis/recordedBasis)` worth of misallocation plus permanent freezing of the omitted receipts.

### Likelihood Explanation
Reachable by an unprivileged lender: (1) request instant withdraw in epoch N via `requestInstantWithdraw`; (2) the honest CDO collects less than pending at the next epoch transition (partial borrower liquidity — `collectInstantWithdrawFunds(_amount)` with `_amount < pending`), leaving `pendingInstantWithdraws > 0` into epoch N+k; (3) borrower defaults; owner calls default handling and `finalizeDefaultRecovery`. No privileged misbehavior required; the stale cross-epoch counter is created by ordinary sequenced calls.

### Recommendation
Make the instant-claim basis epoch-aware in `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`: track a global `instantWithdrawClaimsTotal` (sum over all epochs) and use it instead of `instantWithdrawClaimsByEpoch[epochNumber]`, or add a mapping flag `instantEpochPending[epoch]`/iteration over outstanding epochs. Also make `_claimDefaultedInstantWithdrawRequest` clear *all* epochs' instant receipts for the user (or store a per-user list of request epochs), and include prior-epoch receipts in the default claim basis so the haircut and reserve are consistent.

### Proof of Concept
Foundry fork scenario (sketch — to be executed against the deployed vault/IdleCDOEpochVariant pair):

```solidity
// Epoch N: attacker and victim both requestInstantWithdraw(100)
// Honest borrower funds only partially: CDO calls
//   collectInstantWithdrawFunds(100)  -> pendingInstantWithdraws = 100 remains
// Epoch N+1: borrower defaults; CDO triggers finalizeDefaultRecovery(recovered, src)
//   instantWithdrawClaimsByEpoch[N+1] = 0  (requests were made in epoch N)
//   but pendingInstantWithdraws = 100 != 0
//   -> defaultPendingClaimBasis adds 0 instant basis
//   -> recoveryPrice overstated; reserve excludes already-collected 100
// Attacker calls claimInstantWithdrawRequest via CDO:
//   _claimDefaultedInstantWithdrawRequest reads epoch[N+1] key -> 0
//   funded path burns 100 receipt, _transferFundedClaim pays at par (or reverts
//   once reserve == balance), stealing/ freezing value owed to default-epoch claims.
assertEq(strategy.pendingInstantWithdraws(), 100);
assertEq(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), 0); // over-read: wrong epoch key
vm.prank(cdo); strategy.finalizeDefaultRecovery(recovered, recoverySource);
// recoveryPrice > true price; tail claims revert on _transferDefaultRecovery
```

Note: confirmation requires the CDO-side call sequence (`IdleCDOEpochVariant.stopEpoch`/`_handleBorrowerDefault` → `collectInstantWithdrawFunds`/`finalizeDefaultRecovery`); this analysis is source-level — a fork test against the deployed pair is needed to confirm whether `pendingInstantWithdraws` can realistically remain non-zero across an epoch boundary under honest borrower funding behavior.
