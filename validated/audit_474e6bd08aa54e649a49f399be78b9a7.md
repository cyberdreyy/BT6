### Title
APR0 withdraw receipt permanently bricks `stopEpoch` once APR is set non-zero — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. An unprivileged lender can open an APR0 withdraw receipt while `unscaledApr == 0`. Because `apr0TotalPrincipal` is only cleared inside `prepareStopEpochWithApr0` itself (or through a default-finalization claim path), a later honest manager/CDO APR update to a non-zero value makes every subsequent `prepareStopEpochWithApr0` call revert, permanently freezing the epoch state machine and all funds.

### Finding Description
When `unscaledApr == 0`, `requestWithdraw` routes to `_requestWithdrawApr0`, which sets `apr0Users[_user].principal`/`principalEpoch` and increments the global `apr0TotalPrincipal` (`IdleCreditVault.sol:285-294, 567-577`).

At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`. After the fast path, it enforces:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) return ...;
if (unscaledApr != 0) {
  revert NotAllowed();
}
```
(`IdleCreditVault.sol:499-508`)

`apr0TotalPrincipal` is reset to 0 only at the end of this same function (`:540`), or decremented in `_clearWithdrawClaimForEpoch` during default-recovery claims (`:827`). A user cannot clear it early: `_settleApr0` refuses while `principalEpoch >= epochNumber` (`:551-554`), and `epochNumber` only advances via a successful `stopEpoch`/`deposit` during stop. So once a non-zero APR is set while an open APR0 receipt exists, there is no recovery path — the check reverts forever.

Triggering the inconsistent state requires only sequencing around honest privileged calls, which is allowed:

1. Epoch N runs with `unscaledApr == 0` (APR0 pool mode).
2. Attacker (KYC'd tranche holder) calls `requestWithdraw` → `apr0TotalPrincipal > 0`, `principalEpoch = N`.
3. Before `stopEpoch`, the honest manager updates pricing via `setAprs`/`setAprsWithBuffer` (permitted — `setApr` allows `msg.sender == manager`, `:206-235`), or the CDO applies a new non-zero APR for the next epoch ahead of the `prepareStopEpochWithApr0` call. I could not fully verify the ordering inside `IdleCDOEpochVariant.stopEpoch` in the available iterations; the manager-initiated `setAprs` path is sufficient on its own.
4. Every `stopEpoch`/`stopEpochWithDuration` call now reverts at `prepareStopEpochWithApr0`.

This mirrors the source bug class: two orderings of "the same" operation (APR update vs. APR0 receipt settlement) leave the shared accounting (`apr0TotalPrincipal` vs. `unscaledApr`) in an inconsistent state that crashes the epoch loop — analog of the concurrent RPZ modification leading to crash/DoS.

### Impact Explanation
Permanent freezing of all vault funds. While `stopEpoch` reverts, borrower funds cannot be recalled, no `epochNumber` increment occurs, pending withdraw receipts (normal and APR0) can never be claimed (`epochNumber <= lastWithdrawRequest` gate at `:326`), and active tranche holders cannot exit. This is a permanent freeze/insolvency-equivalent for everyone in the pool, caused by one unprivileged `requestWithdraw` plus a routine APR change.

### Likelihood Explanation
Requires the confluence of (a) an APR0-configured epoch and (b) a subsequent APR change to non-zero while an APR0 receipt is still open. APR0 is a supported, first-class mode of this vault (dedicated `apr0Users`/`apr0RateByEpoch` accounting), and manager-initiated repricing via `setAprs` is an explicitly allowed operation. The attacker's only action is a normal `requestWithdraw` — no privileged role, no oracle manipulation, no malformed input. The freezing is not guarded against anywhere: there is no function to force-settle or clear `apr0TotalPrincipal` once `unscaledApr != 0`.

### Recommendation
In `prepareStopEpochWithApr0`, do not revert on `unscaledApr != 0` when `apr0TotalPrincipal != 0`. Instead, settle/close the open APR0 bucket gracefully — e.g., treat the open APR0 principal as a normal pending withdraw for that epoch (already tracked in `pendingWithdraws`), zero out `apr0TotalPrincipal`, and optionally store `apr0RateByEpoch[epochNumber] = 0`. Alternatively, block APR transitions to non-zero at the manager/CDO entry points (`setAprs`, `setAprsWithBuffer`) while `apr0TotalPrincipal != 0`, so the inconsistent state can never be entered.

### Proof of Concept
Foundry fork PoC sketch against `IdleCreditVault` + `IdleCDOEpochVariant` (mirror `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testApr0ReceiptBricksStopEpoch() external {
    // Configure APR0 mode: unscaledApr = 0
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    // Attacker deposits AA and requests withdraw during the APR0 epoch
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 tr = _depositWithUser(attacker, amount, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(tr, address(AAtranche));
    assertGt(strategy.apr0TotalPrincipal(), 0);

    _startEpochAndCheckPrices(0);

    // Honest manager repricing to a non-zero APR mid-epoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(5e18, 5e18);

    // Every subsequent stopEpoch reverts -> permanent freeze
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Repeat to show it is permanent, not transient
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Attacker cannot self-clear: claim reverts because epoch never advanced
    vm.prank(attacker);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();
}
```

Caveat: if `IdleCDOEpochVariant.stopEpoch` internally resets `unscaledApr` to the new epoch's APR *after* calling `prepareStopEpochWithApr0` and no other path ever leaves `unscaledApr != 0` while an APR0 receipt is open, the freeze would depend solely on the manager calling `setAprs`/`setAprsWithBuffer` — which the contract explicitly permits — so the finding stands on that path regardless.
