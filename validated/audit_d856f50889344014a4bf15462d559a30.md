Let me check a few remaining details: how `createWriteOffRequest` computes `underlyingsRequested`, where `pendingUnderlyings` is consumed, and whether prefunded instant receipts can be stranded.### Title
Repeated post-default withdraw requests overwrite `postDefaultRequests`, permanently freezing receipt funds in the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug (CVE-2022-31627) is a mismatched free: memory allocated by one path is released through the wrong function, corrupting the heap. The analog in `IdleCreditVault` is a mismatched "alloc/free" of recovery claims: each post-default `requestWithdraw` allocates a fresh claim against `defaultRecoveryReserve` and mints receipt tokens, but the payout ledger `postDefaultRequests[_user]` is *overwritten* (not accumulated) on every request. The second allocation frees the record of the first while its backing stays locked in the reserve — a one-receipt-one-payout violation that permanently freezes part of the isolated recovery fund and leaves the user holding unspendable receipt tokens.

### Finding Description
In `requestWithdraw`, after `defaultRecoveryFinalized`, the strategy takes the post-default branch: it burns the CDO's strategy tokens, mints a `_amount` receipt to the user, and records the claim: [1](#0-0) 

```solidity
_burn(msg.sender, _amount);
_mint(_user, _amount);
postDefaultRequests[_user] = _amount;   // overwrite, not +=
return;
```

The pre-default branch correctly accumulates (`withdrawsRequests[_user] += _amount`, `instantWithdrawsRequests[_user] += _amount`), but the post-default bucket is a plain assignment. Nothing in the post-default path rejects a second request: the only early-exit guard in `requestWithdraw` is the loss-adjusted-receipt check (`lossRecoveryPriceByEpoch[lastWithdrawRequest]` plus `withdrawsRequestsByEpoch`/APR0-per-epoch checks), which does not inspect `postDefaultRequests`, and `_hasWithdrawRequest` likewise ignores it.

On the claim side, `_claimPostDefaultWithdrawRequest` clears the slot and pays only the recorded amount via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve`: [2](#0-1) 

```solidity
amount = postDefaultRequests[_user];
postDefaultRequests[_user] = 0;
_burn(_user, amount);
_transferDefaultRecovery(_user, amount);
```

So after `req1 = X` and `req2 = Y`, the user holds `X + Y` strategy-token receipts but can only ever claim `Y`. The first `X` of underlying stays inside `defaultRecoveryReserve` with no claimant — it was allocated to the user at request time but the ledger that would free it was overwritten. Because `recoveryPrice` was fixed at `finalizeDefaultRecovery`, this stranded reserve is not redistributed; it is locked forever (there is no reserve sweep, and `emergencyWithdraw` does not exist on this strategy).

### Impact Explanation
Permanent freezing of funds, with a quantified loss equal to the earlier overwritten request amount `X`:

- The victim (any defaulted-epoch lender who requests twice) permanently loses `X` of underlying that was already sourced to back their claim; they hold `X` dead receipt tokens.
- `defaultRecoveryReserve` is inflated by `X` forever, so the reserve no longer matches outstanding claims — an accounting-invariant break identical in spirit to freeing a heap chunk with the wrong allocator while a stale pointer still references it.
- The stranded funds can never be recovered by anyone (no sweep path), so it is a permanent loss, not a delay.

Note the attacker model fits: the "attacker" can even be the victim's own counterparty — e.g., an EOA griefing is not needed; a user induced (or front-run/sandwiched via the CDO's public `requestWithdraw(_user)` wrapper, if the CDO exposes a user-parameterized entry point as `_user` suggests) into a second small request loses the bulk of their recovery. Even uninduced, any lender who requests, then tops up post-default, triggers it themselves.

### Likelihood Explanation
- Preconditions: vault in `defaulted` + `defaultRecoveryFinalized` state (a supported, heavily-tested mode in this codebase — `finalizeDefaultRecovery`, `postDefaultRequests`, `_claimPostDefaultWithdrawRequest` are all live code paths, not dead code).
- Trigger: two `requestWithdraw` calls post-finalization. There is no `postDefaultRequests[_user] != 0 → revert` guard and no "request already exists" check on this branch, unlike the loss-adjusted branch which explicitly forbids a second request before claiming.
- Severity is bounded by the size of the first overwritten request, which can be the user's entire defaulted position.

Uncertainty I could not fully resolve in this pass: whether the IdleCDO-side entry point prevents a second post-default `requestWithdraw` for the same user before reaching the strategy (the strategy receives `_user` from `msg.sender == idleCDO`, so the CDO's own request bookkeeping could add a guard). If the CDO does not block it, the bug stands exactly as described.

### Recommendation
Make the post-default bucket consistent with every other receipt bucket:

```solidity
postDefaultRequests[_user] += _amount;
```

or, if a single post-default request is intended, revert when `postDefaultRequests[_user] != 0`. If the overwrite semantics are deliberate (latest price wins), the previously minted `postDefaultRequests[_user]` receipt tokens must be burned and its reserve share released before recording the new request, so that minted receipts and reserve accounting stay 1:1.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";

// Setup: fork mainnet, deploy/attach to an IdleCreditVault whose CDO has been
// defaulted and finalizeDefaultRecovery called with recoveryPrice < RECOVERY_FULL.
// user = lender holding CDO strategy-token backed position post-default.

function testPostDefaultRequestOverwriteFreezesReserve() {
    // --- state: defaultRecoveryFinalized == true, defaultRecoveryPrice = p ---
    uint256 balUser;   // user's post-haircut claimable backing, e.g. 1000e6
    uint256 reserve0 = vault.defaultRecoveryReserve();

    // Request 1: post-default branch burns CDO tokens, mints receipt, sets slot = X
    vm.prank(cdo);
    vault.requestWithdraw(X, user);          // postDefaultRequests[user] = X
    assertEq(vault.balanceOf(user), X);

    // Request 2: same branch, slot overwritten with Y < X
    vm.prank(cdo);
    vault.requestWithdraw(Y, user);          // postDefaultRequests[user] = Y (X lost)
    assertEq(vault.balanceOf(user), X + Y);  // user holds X+Y receipts

    // Claim pays only Y; X receipt tokens unspendable, X underlying stranded
    vm.prank(cdo);
    vault.claimWithdrawRequest(user);
    assertEq(underlying.balanceOf(user), Y);
    assertEq(vault.balanceOf(user), X);                      // dead receipts
    assertEq(vault.defaultRecoveryReserve(), reserve0 - Y);  // X locked forever

    // No path frees the stranded X: further claim returns 0 / reverts.
    vm.prank(cdo);
    vault.claimWithdrawRequest(user);
    assertEq(underlying.balanceOf(user), Y); // unchanged -> permanent freeze
}
```
