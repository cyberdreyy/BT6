### Title
EI-to-job binding is not validated on job-run trigger, but exploitation is gated by `build.IsProd()` - ([File: core/web/pipeline_runs_controller.go])

### Finding Description
`AuthenticateExternalInitiator` in `core/web/auth/auth.go` sets a **synthetic user** in the gin context for any successfully-authenticated External Initiator: `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` [1](#0-0) . Because of this, `PipelineRunsController.Create`'s check `_, isUser := auth.GetAuthenticatedUser(c)` returns `true` for EI-authenticated requests too, even though the code comment states "only users are allowed to run jobs using int IDs - EIs not allowed" [2](#0-1) . This means an EI credential holder can reach the `prc.App.RunJobV2(ctx, jobID, nil)` branch with an arbitrary integer job ID, and `RunJobV2` performs no EI-to-job association check at all — it simply does `app.jobORM.FindJob(ctx, jobID)` and executes the pipeline [3](#0-2) . `auth.RequiresRunRole` (used in the router at `userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))`) only checks `user.Role`, not job/EI binding [4](#0-3) [5](#0-4) .

However, `RunJobV2` is explicitly hard-gated: `if build.IsProd() { return 0, errors.New("manual job runs not supported on secure builds") }`, and the function is documented as "Only used for local testing, not supported by the UI" [6](#0-5) . This means that in production/secure builds of the Chainlink node — the builds actually distributed and run by node operators — this entire code path is unreachable and always errors out regardless of authentication method or role. I was unable to locate the definition of `build.IsProd`/`build.IsDev` in this index to confirm exactly which build tags trigger it, so I cannot fully verify whether any real-world deployment configuration leaves this open; this is a limitation of the available index.

### Impact Explanation
In a genuinely "secure"/production build, there is no exploitable impact: `RunJobV2` unconditionally returns an error before touching the job/pipeline. In non-production (dev/test) builds, the missing EI-to-job binding check would allow an EI credential holder for job A to trigger runs on unrelated job B (cross-job run triggering / unauthorized pipeline execution), but this class of build is not what bounty programs typically target since it's explicitly documented as a local-testing-only feature, not the deployed node runtime.

### Likelihood Explanation
Low/unclear. Exploitation depends entirely on the node being deployed with a non-"secure" build (`build.IsProd() == false`), which is a build-configuration dependency outside the standard deployed node runtime, rather than something an unprivileged remote attacker can control or that represents the standard node operation. Given the explicit "not supported by the UI"/"testing only" gating, this does not represent a reproducible vulnerability against the intended production Chainlink node binary.

### Recommendation
N/A for production builds given the existing `build.IsProd()` gate. If dev/test builds are considered in-scope, tighten `PipelineRunsController.Create`'s `isUser` check to explicitly reject external-initiator-authenticated sessions (e.g., check `auth.GetAuthenticatedExternalInitiator(c)` and reject, or use a distinct context key/role instead of overloading `SessionUserKey` with a synthetic user for EIs), and additionally validate that the requested job's `ExternalInitiatorWebhookSpecs` includes the authenticated EI before invoking `RunJobV2`.

### Proof of Concept
Not applicable as a production-impacting PoC: any handler-level integration test hitting `POST /v2/jobs/:ID/runs` with EI credentials against a binary built without disabling `build.IsProd()` will receive `500` with "manual job runs not supported on secure builds" regardless of job ID, since `RunJobV2` short-circuits before any job/pipeline logic executes.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
