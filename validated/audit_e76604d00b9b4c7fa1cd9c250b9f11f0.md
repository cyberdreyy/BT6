## Title
Stale confirmations from removed multisig keys/members still count toward quorum, allowing requests to execute below the live-key threshold - (File: `multisig/src/lib.rs`, also present in `multisig2/src/lib.rs`)

### Summary
The GMX bug is a class of "stale record not reconciled with current state" — a decrease order keeps existing in the order store after the position it corresponds to no longer exists, and the stale record is later used to extract value that was never re-validated against present reality. The `multisig` (v1) and `multisig2` contracts in this repo have a structurally identical flaw: when an access key (v1) or member (v2) is removed via `DeleteKey`/`DeleteMember`, the contract only purges **requests that key/member originally created**, but it never purges that key/member's **confirmations recorded on requests created by someone else**. Those stale confirmations remain in the `confirmations` set and continue to count toward `num_confirmations`, letting a request execute even though one of its "confirmers" is no longer a live key/member.

### Finding Description
`DeleteKey` (v1) only cleans up requests where the removed key is the *signer* of the request, not requests it merely *confirmed*: [1](#0-0) 

The same limited cleanup exists in v2's `delete_member`, which also filters only by `r.member == member` (i.e., the request creator), leaving confirmations by that member on other members' requests untouched: [2](#0-1) 

`confirm()` only checks that `confirmations.len() + 1 >= num_confirmations`; it never re-validates that every public key/member already present in the `confirmations` set is still a current, live key/member of the multisig: [3](#0-2) [4](#0-3) 

This breaks the intended custody binding: **confirmations counted == live members currently entitled to authorize a request**. A key that has been removed (e.g., rotated out, or a compromised key revoked) can still have its earlier confirmation silently "vote" for an unrelated request forever, because nothing walks all `confirmations` entries and strips revoked keys/members.

### Impact Explanation
This falls under the Critical impact category "a multisig request executed below threshold." A pending request that already has confirmations from a key that is later removed can be pushed to execution with fewer *currently valid* signers than `num_confirmations` mandates — e.g., a 3-of-4 multisig can execute a transfer with only 2 live confirmations plus one confirmation from a key that no longer exists on the account. This can move NEAR (or trigger `AddKey`/`FunctionCall` actions) without the governance quorum the multisig was configured to require.

### Likelihood Explanation
This requires normal multisig operation: a request is proposed and partially confirmed, and — independently — one of the confirming keys/members is later removed for routine key-rotation reasons (common practice) without the removal transaction being aware of, or bothering to scan, all outstanding requests' confirmation sets. Since `delete_request`/`DeleteKey`/`DeleteMember` never scans confirmations of requests it didn't create, this is essentially guaranteed to occur any time key rotation happens while requests are mid-flight. No malicious redeploy, foundation action, or victim key theft is required — only ordinary multisig lifecycle events (a member proposing, confirming, and later legitimately rotating another member's key).

### Recommendation
When a key/member is deleted, iterate over **all** `requests`/`confirmations` entries and remove the deleted key/member from every confirmation set (not just requests it authored), re-checking whether any request that now has a diminished distinct-live-confirmer count should be un-armed. Alternatively, validate at `confirm()`/execution time that every entry in a request's `confirmations` set corresponds to a currently valid key/member before counting it toward `num_confirmations`.

### Proof of Concept
Using the v1 contract with `num_confirmations = 3`, members `{A, B, C, D}` (four keys added to the account):
1. `A` calls `add_request_and_confirm(R)` for a malicious `Transfer` — `confirmations(R) = {A}`.
2. `B` calls `confirm(R)` — `confirmations(R) = {A, B}` (2/3, not yet executed).
3. Independently, `A`, `C`, `D` confirm a separate legitimate `DeleteKey { public_key: B }` request to rotate out `B`'s key (3/3, executes). Per `multisig/src/lib.rs:198-216`, this only removes requests where `r.signer_pk == B`; `R` was created by `A`, so `R` and its confirmations (`{A, B}`) are left untouched, and `B`'s access key is now deleted from the account.
4. `C` now calls `confirm(R)` — `confirmations(R) = {A, B, C}`, length 3 `>= num_confirmations` (3), so `execute_request` fires per `multisig/src/lib.rs:246-266`, even though `B` is no longer a valid key on the account. The transfer executes with only 2 truly live confirmers (`A`, `C`) instead of the required 3.

        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/

        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);

        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })

            self.requests.remove(&request_id);

        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
