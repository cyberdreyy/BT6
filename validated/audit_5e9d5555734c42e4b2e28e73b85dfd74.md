### Title
Last-second mid-epoch deposit receives full realized APR0 epoch yield - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary

`depositDuringEpoch` correctly prorates the **expected** interest for a mid-epoch depositor, but only using the configured strategy APR. When the epoch is configured at APR 0, a depositor who enters immediately before `epochEndDate` is credited with zero expected interest and minted shares at the pre-interest NAV price. If the manager then stops the epoch with a positive realized interest override, that interest is distributed pro rata over ending tranche balances rather than time-weighted balances.

This matches the reported bug class: a user can appear immediately before an epoch boundary and receive nearly the same yield as a user who supplied liquidity for the entire epoch.

### Finding Description

`depositDuringEpoch` permits deposits while the epoch is running and does not impose a late-deposit cutoff or reject APR0 epochs. It checks only tranche/flag state, programmable-borrower mode, AYS mode, epoch status, `epochEndDate`, and KYC status. [1](#0-0) 

The mint calculation prorates `_calcInterest(_amount)` by the deposit's remaining participation time. [2](#0-1) 

However, `_calcInterest` is based on the configured strategy APR, not realized epoch yield. [3](#0-2) 

During an APR0 epoch, `interest == 0`, so the attacker receives shares according to `(amount + 0) * trancheSupply / expectedFinal`. [4](#0-3) 

At `stopEpoch`, the realized interest override is accounted into tranche NAV for all ending holders. The accounting has no record of when the attacker deposited and therefore cannot distinguish one second of participation from a full epoch. [5](#0-4) 

The dedicated APR0 withdrawal accounting confirms that realized interest can be distributed even when the configured unscaled APR is zero: `prepareStopEpochWithApr0` takes a positive realized `_expInterest`, allocates part of it to pending APR0 principal, and subtracts that amount from the active-pool interest. [6](#0-5) 

### Impact Explanation

An unprivileged KYC-passed user can steal unclaimed epoch yield from existing depositors.

For example, with zero fees, an active AA NAV of `1000 ether`, and a realized epoch gain of `10 ether`, an attacker depositing `1000 ether` one second before the epoch ends receives approximately one-half of the gain. A time-weighted result would assign the attacker only approximately `10 ether / 2,592,000` for one second of a 30-day epoch, before pool-share calculations.

The loss is bounded by the realized epoch interest but can approach the attacker's proportional share of ending NAV. Repeating the behavior across epochs allows the attacker to capture yield without exposing capital to the epoch's duration or loss window.

### Likelihood Explanation

The attack requires:

- fixed-APR mode, not programmable-borrower mode;
- `depositDuringEpoch` enabled;
- AYS disabled;
- an existing tranche supply;
- configured epoch APR of 0;
- a positive realized interest amount at `stopEpoch`.

These conditions are plausible because APR0 withdrawal accounting explicitly supports positive realized interest during an APR0 epoch. The attacker only needs an allowed wallet and does not need cooperation from the owner, manager, borrower, or another privileged role.

### Recommendation

Track time-weighted principal for mid-epoch deposits or use a two-component accounting model that separates principal from accrued/realized yield.

At minimum, `depositDuringEpoch` should mint shares using a price that preserves unexpected realized yield for pre-existing holders. A stronger fix is an index such as `rewardPerShare` or `interestPerShare`, updated on each accounting transition and applied according to the depositor's share balance and entry timestamp.

An explicit late-deposit cutoff would reduce the impact but would not fully fix time-weighting for deposits made shortly before the cutoff.

### Proof of Concept

The following Foundry fork-style PoC demonstrates the accounting flaw. Deployment-specific initialization should reuse the repository's existing `IdleCreditVault.t.sol` fixture, with fees set to zero, programmable borrower disabled, AYS disabled, and `depositDuringEpoch` enabled.

```solidity
function test_APR0_LastSecondDeposit_DilutesRealizedYield() public {
    uint256 amount = 1_000 ether;
    uint256 realizedInterest = 10 ether;

    // Honest LP is present for the whole epoch.
    _depositWithAllowedUser(honestLp, amount);

    // Configure/start an epoch with unscaled APR = 0.
    _startEpochWithUnscaledApr(0);

    uint256 supplyBefore = IERC20(AAtranche).totalSupply();
    uint256 navBefore = cdoEpoch.getContractValue();

    // Attacker deposits one second before epoch end.
    vm.warp(cdoEpoch.epochEndDate() - 1);

    uint256 attackerShares = cdoEpoch.depositDuringEpoch(
        amount,
        address(AAtranche)
    );

    // At APR0, no expected interest is charged in the mint calculation.
    assertApproxEqRel(
        attackerShares,
        amount * supplyBefore / navBefore,
        1e12
    );

    // Honest manager stops the epoch with realized borrower yield.
    uint256 borrowerBalance = underlying.balanceOf(borrower);
    deal(
        address(underlying),
        borrower,
        borrowerBalance + realizedInterest + pendingWithdraws()
    );

    vm.prank(manager);
    cdoEpoch.stopEpoch(0, realizedInterest);

    uint256 priceAfter = cdoEpoch.virtualPrice(address(AAtranche));
    uint256 attackerValue = attackerShares * priceAfter / 1e18;

    // The attacker receives a material share of the epoch's realized gain after
    // only one second of participation.
    assertGt(attackerValue - amount, realizedInterest * 40 / 100);
}
```

A two-account variant makes the broken invariant explicit:

```solidity
uint256 honestShares = IERC20(AAtranche).balanceOf(honestLp);
uint256 attackerShares = IERC20(AAtranche).balanceOf(attacker);

uint256 price = cdoEpoch.virtualPrice(address(AAtranche));

uint256 honestYield = honestShares * price / 1e18 - amount;
uint256 attackerYield = attackerShares * price / 1e18 - amount;

// With equal principal, the attacker earns approximately the same per-share
// yield despite participating for one second rather than the full epoch.
assertApproxEqRel(attackerYield, honestYield, 5e15);
```

The expected fixed behavior is that `attackerYield` is approximately `honestYield / epochDuration` for a one-second deposit, not approximately equal to the full-epoch depositor's per-share yield.

  function prepareStopEpochWithApr0(uint256 _interest) external returns (uint256 _expInterest, uint256 _adjPendingWithdrawFees) {
    _onlyIdleCDO();
    IIdleCDOEpochVariant _cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 _pendingFees = _cdo.pendingWithdrawFees();
    uint256 _tvl = _cdo.getContractValue();
    _expInterest = _interest > 1 ? _interest : _cdo.expectedEpochInterest();
    _adjPendingWithdrawFees = _pendingFees;
    // Principal currently waiting for withdraw that was requested while APR was 0,
    // net of the upfront management fee charged at request time.
    uint256 _principal = apr0TotalPrincipal;

    // Fast path: no APR0 accounting needed.
    if (_principal == 0) {
      return (_expInterest, _adjPendingWithdrawFees);
    }
    // APR0 principal is only valid while APR is 0 for that request lifecycle.
    if (unscaledApr != 0) {
      revert NotAllowed();
    }

    uint256 _apr0NetInterest;
    // APR0 allocation is computed only when stopEpoch receives a real override interest.
    // _expectedInterest == 1 is the "request all funds back" sentinel and is handled in IdleCDO.
    if (_expInterest > 1 && _expInterest > _pendingFees) {
      // Remove already booked withdraw fees from the interest base before splitting.
      uint256 _interestNetOfFees = _expInterest - _pendingFees;
      // Total principal used for the pro-rata split:
      // IdleCDO TVL (which excludes APR0 requested principal) + APR0 principal bucket.
      uint256 _totalPrincipalForSplit = _tvl + _principal;
      if (_totalPrincipalForSplit != 0) {
        // APR0 users get a pro-rata share of realized interest.
        uint256 _apr0InterestGross = _interestNetOfFees * _principal / _totalPrincipalForSplit;
        if (_apr0InterestGross != 0) {
          // Same fee model as normal withdraw interest.
          uint256 _apr0Fee = _apr0InterestGross * _cdo.fee() / FULL_ALLOC;
          _apr0NetInterest = _apr0InterestGross - _apr0Fee;
          _adjPendingWithdrawFees += _apr0Fee;
          _expInterest -= _apr0NetInterest;
        }
      }
    }

    // Finalize one-epoch APR0 interest for current epoch only.
    if (_apr0NetInterest != 0) {
      // Funds owed to withdraw requesters increase by APR0 net interest.
      pendingWithdraws += _apr0NetInterest;
      // Save per-epoch net rate; each APR0 request accrues exactly once on its request epoch.
      apr0RateByEpoch[epochNumber] = (_apr0NetInterest * 1e18) / _principal;
    }
    // Close current APR0 bucket so it cannot accrue again on later stopEpoch calls.
    apr0TotalPrincipal = 0;
