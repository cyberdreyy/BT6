### Title
Per-account write-cost limit lets an attacker cheaply grief a victim's account out of block inclusion, mirroring the ParaSpace balance-limit lockout - (File: `cost-model/src/cost_tracker.rs`)

### Summary
The ParaSpace finding shows a class of bug where a hard per-entity cap, checked against a shared/writable resource, can be filled by an unauthorized third party for the price of a cheap transaction, permanently (until the window resets) locking a victim out of a time-critical operation on that same resource. Agave's cost-model contains a structurally identical cap: `MAX_WRITABLE_ACCOUNT_UNITS` in `cost-model/src/block_cost_limits.rs`, enforced per writable account per block by `CostTracker::would_fit` / `try_add` in `cost-model/src/cost_tracker.rs`.

### Finding Description
`CostTracker` tracks compute-unit cost per writable account for the currently-building block in `cost_by_writable_accounts` [1](#0-0) . Every transaction that writes to an account is checked with `would_fit`, which rejects the transaction with `CostTrackerError::WouldExceedAccountMaxLimit` (mapped to `TransactionError::WouldExceedMaxAccountCostLimit`) once the cumulative cost charged against that account for the block reaches `limits.account_cost` (`MAX_WRITABLE_ACCOUNT_UNITS = 24_000_000` CU by default) [2](#0-1) [3](#0-2) .

This mirrors the ParaSpace bug exactly: a hard cap tied to a resource (the writable account, analogous to the victim's NFT balance) is filled by cheap, unauthorized transactions from an attacker (who need not own or be authorized on the account at all — any signer can write-lock any account they include as writable in an instruction that references it, e.g. any account passed to a program as a writable account, or trivially the attacker's own accounts if the victim's critical transaction must write to a shared/contended account such as an AMM pool, oracle, or global config account). Once the per-account cost ceiling is hit, `try_add` fails for every subsequent transaction touching that account for the remainder of the current leader's cost-tracker window (reset only across leader/bank boundaries), exactly as the NToken balance check failed for Bob once his balance hit the limit.

### Impact Explanation
An attacker who identifies that a victim needs to submit a time-critical transaction touching a specific hot account (e.g., a lending-protocol vault/pool account the victim must write to add collateral or repay before a liquidation threshold is crossed) can flood that account with minimal-cost writable transactions to saturate `MAX_WRITABLE_ACCOUNT_UNITS` for the block(s) the victim's transaction would land in. The victim's legitimate transaction is then rejected at cost-tracker admission (in banking stage `consumer.rs`/scheduler and again at bank commit) with `WouldExceedMaxAccountCostLimit`, effectively preventing timely inclusion. This is the same "griefing lockout via a filled shared cap" primitive as the ParaSpace M-10 finding, just relocated from a per-user NFT-balance counter to a per-account CU-cost counter enforced by the SVM cost metering path.

### Likelihood Explanation
The cost is low — the attacker only pays the compute-unit cost of self-authored transactions that write-lock the target account; no special privilege on the victim's account is required, only that the attacker's transaction also declares the same account as writable. The attack window per leader slot is short (limits reset with each new cost tracker/bank), so sustaining the lockout across the multiple slots needed for a liquidation-style race requires repeated spam across successive leaders, which raises the cost/complexity somewhat but does not require any special access.

### Recommendation
Consider giving fee-priority or reserved capacity to the actual owner/authority of a contended account, or make the per-account cost limit dynamic/fee-weighted so an attacker cannot cheaply monopolize a shared account's write-cost budget purely with low-fee transactions, similar to the ParaSpace mitigation of disallowing "worthless" collateral spam.

### Proof of Concept
Not independently reproduced in this analysis; the mechanism is derived directly from reading `would_fit`/`try_add` in `cost-model/src/cost_tracker.rs` and the constant `MAX_WRITABLE_ACCOUNT_UNITS` in `cost-model/src/block_cost_limits.rs`.     fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }
