### Title
Unauthorized override of the staking-pool whitelist trust anchor in `LockupFactory::create` allows a wrongly parameterised lockup deployment - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` lets any unprivileged caller supply an arbitrary `whitelist_account_id` argument that is baked into the deployed lockup contract as `staking_pool_whitelist_account_id`, overriding the factory's own audited default. This mirrors the `setWorkerPublicKey()` root cause: an entity that later gets implicitly *trusted* as an authority (here, the contract that gates which staking pools may receive delegated custody of locked NEAR) is set by an unauthenticated caller rather than being pinned to a value the beneficiary/owner can rely on.

### Finding Description
`LockupFactory::create` accepts an optional `whitelist_account_id: Option<ValidAccountId>` from the caller (the funder), which — if present — is used verbatim as the `staking_pool_whitelist_account_id` passed into the newly deployed lockup contract's `new()`, instead of always using the factory's own configured `self.whitelist_account_id`: [1](#0-0) 

Specifically: [2](#0-1) 

The lockup contract stores this value unconditionally at init: [3](#0-2) 

Later, when the lockup contract's owner tries to delegate to a staking pool, the contract trusts whatever whitelist contract was recorded at creation time to vouch for the staking pool's legitimacy, without any way for the owner to know or verify that this whitelist is the NEAR-Foundation-approved one: [4](#0-3) 

The binding that should hold is:
`staking_pool_whitelist_account_id used for is_whitelisted checks == the NEAR-Foundation-maintained whitelist contract`

but the factory allows an unprivileged funder (who is not the lockup owner and not the Foundation) to substitute any account ID for this trust anchor at deployment time, breaking that equality. A funder deploying a lockup contract on behalf of an owner (a very common real-world flow — e.g., an employer funding an employee's lockup) can point `staking_pool_whitelist_account_id` at their own contract that always returns `true` from `is_whitelisted`. When the owner later calls `select_staking_pool` believing pool legitimacy is verified against the Foundation's list, the check is instead satisfied by the attacker-controlled whitelist, letting the owner unknowingly delegate to a malicious staking pool that never returns the staked/locked NEAR.

### Impact Explanation
This falls under the Critical impact category "a wrongly whitelisted or wrongly parameterised deployment": the lockup contract is deployed with a maliciously parameterised trust anchor (`staking_pool_whitelist_account_id`) chosen by an unprivileged third party rather than the intended authority. Funds later delegated by the (unwitting) lockup owner to a staking pool "approved" only by this rogue whitelist can be permanently lost/frozen, since the whitelist guarantee that "delegated tokens can not be lost or locked" (as documented in `whitelist/README.md`) is exactly the protection subverted here.

### Likelihood Explanation
Likelihood is realistic in the funder-funds-owner pattern that the factory itself documents ("Lockups can be funded from any account", "No need to have access to the foundation keys to create lockup" — `lockup-factory/README.md`). Any account funding a lockup for someone else can silently substitute a malicious whitelist with no signal to the owner that the whitelist differs from the Foundation's, and no on-chain assertion restricts `whitelist_account_id` to a small trusted set.

### Recommendation
Restrict `create()` to always use the factory's configured `self.whitelist_account_id` unless the caller is the Foundation account (or another vetted authority), or require that any custom `whitelist_account_id` be itself validated against a Foundation-controlled meta-whitelist before being accepted as a deployment parameter.

### Proof of Concept
1. Attacker calls `lockup-factory.create(owner_account_id=victim, ..., whitelist_account_id=Some(attacker_whitelist))`, attaching the minimum deposit, where `attacker_whitelist` is a contract the attacker controls whose `is_whitelisted` always returns `true`.
2. The lockup contract is deployed for `victim` with `staking_pool_whitelist_account_id = attacker_whitelist` [5](#0-4) .
3. Later, `victim` (the owner) calls `select_staking_pool(malicious_pool)`, which queries `attacker_whitelist.is_whitelisted(malicious_pool)` and receives `true` [4](#0-3) .
4. `victim` delegates locked NEAR to `malicious_pool`, which never returns the funds — resulting in the owner's locked/vested tokens being frozen or lost.

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )
            .then(ext_self::on_lockup_create(
                lockup_account_id,
                env::attached_deposit().into(),
                env::predecessor_account_id(),
                &env::current_account_id(),
                NO_DEPOSIT,
                gas::CALLBACK,
            ))
    }
