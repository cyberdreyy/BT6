### Title
Multisig confirmations from a deleted key are never purged, allowing a request to execute below the live-key threshold - (File: `multisig/src/lib.rs`, also `multisig2/src/lib.rs`)

### Summary
The multisig contract's `confirm()` tallies confirmations by counting entries in a stored `HashSet<PublicKey>` per request, but when an access key is removed via the `DeleteKey` action, the contract only purges *requests originally created (signed)* by that key — it never scrubs that key's public key out of the `confirmations` set of *other* pending requests it had previously confirmed. This is the same bug class as the referenced Golom finding: a trust/eligibility parameter is revoked (here, a key's membership), but data recorded while that trust existed (a confirmation) keeps counting toward a later threshold check as if the party were still trusted.

### Finding Description
`confirm()` only checks the *count* of stored public keys against `num_confirmations`, not whether those keys are still valid multisig members at confirmation time: [1](#0-0) 

When `DeleteKey` executes, it removes outstanding *requests whose creator* (`signer_pk`) equals the deleted key, and clears `num_requests_pk` for that key — but it does not iterate over `self.confirmations` to strip the deleted key's public key from confirmation sets of *other* requests it had confirmed: [2](#0-1) 

Confirmations are stored purely as a `HashSet<PublicKey>` per request with no secondary index of "which requests has key X confirmed", so there is no mechanism to retroactively invalidate a stale confirmation once the confirming key is removed: [3](#0-2) 

The equality this breaks is: `count(confirmations recorded on request R)` should equal `count(live, currently-authorized members who confirmed request R)`. Once a confirming key is deleted, the left side stays the same while the right side should decrease by one — but the contract never re-checks this invariant, so `confirmations.len() + 1 >= num_confirmations` in `confirm()` can be satisfied by combining a stale, revoked confirmation with confirmations from fewer than `num_confirmations` currently-live keys.

The identical structural flaw exists in `multisig2`: `delete_member` only removes requests where `r.member == member` (i.e. requests the removed member *created*), not confirmations that member had cast on other pending requests: [4](#0-3) 

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." A pending, sensitive request (e.g., `Transfer`, `AddKey`, `FunctionCall`) can end up executed using fewer live confirmations than `num_confirmations` requires, because a stale confirmation from a since-removed key is silently counted. This weakens the K-of-N security guarantee the contract is built around and can allow funds/actions to be authorized without the intended number of currently-trusted signers agreeing.

### Likelihood Explanation
The trigger sequence uses only actions the multisig already exposes to its members (`add_request`, `confirm`, `DeleteKey`) and requires no protocol bug beyond the contract's own bookkeeping. Any multisig instance where key rotation/removal happens while other requests are pending — a routine operational pattern — is susceptible. No special privilege beyond being one of the existing signers is needed to observe/exploit the stale-confirmation state; the flaw is in the contract's accounting, not in any single actor's authorized capability.

### Recommendation
When executing `DeleteKey` (or `DeleteMember` in multisig2), iterate over all pending requests' confirmation sets and remove the deleted key/member's public key from each, not just from requests the deleted key itself created. Alternatively, when tallying confirmations in `confirm()`/`execute_request()`, filter the confirmation set to only currently valid keys/members before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy multisig with 3 keys `A, B, C` and `num_confirmations = 2`.
2. Key `C` creates Request `X` (e.g. `Transfer` of funds) via `add_request`. Key `A` calls `confirm(X)` → `confirmations[X] = {A}` (1/2).
3. Separately, keys `B` and `C` create+confirm a `DeleteKey{public_key: A}` request (2/2 confirmations from live keys), which executes and removes `A` as an access key on the account: `multisig/src/lib.rs` lines 198-216. This only removes requests where `signer_pk == A` (none, since `A` didn't create any request) — `confirmations[X]` is untouched and still contains `A`.
4. Key `B` calls `confirm(X)`. In `confirm()`, `confirmations.len() (1, containing stale key A) + 1 (B) = 2 >= num_confirmations (2)` → Request `X` executes.
5. Result: Request `X` (the `Transfer`) executed with only one currently-live key (`B`) actually approving it at execution time, even though the contract is supposed to require 2 live signers — the second "confirmation" came from a key that was already revoked before the tally was made.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
