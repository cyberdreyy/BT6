I traced this through the code and found a genuine gap between `staking_contract::switch_operator` and the `BeneficiaryForOperator` redirect logic in `distribute_internal`. I have enough evidence to write it up.

### Title
Stale commission distribution shares bypass the departing operator's registered beneficiary after `switch_operator` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::switch_operator` requests any outstanding commission for the old operator and stores it as a pending share in the `StakingContract`'s `distribution_pool` keyed by the **old operator's address**, then re-parents the whole `StakingContract` struct under the **new operator's key** in `Store.staking_contracts`. When that pending share is later paid out via `distribute_internal`, the code only redirects a payout to `beneficiary_for_operator(operator)` when `recipient == operator` — but by then `operator` is the *new* operator address, while `recipient` is still the *old* operator's address. The comparison never matches, so the payment goes straight to the old operator's own account instead of the beneficiary the old operator had configured via `set_beneficiary_for_operator`.

### Finding Description
In `switch_operator` [1](#0-0) , the sequence is:
1. `distribute_internal(staker_address, old_operator, &mut staking_contract)` — pays out any already-inactive funds, correctly redirecting `recipient == old_operator` to `beneficiary_for_operator(old_operator)`.
2. `request_commission_internal(old_operator, &mut staking_contract)` — computes the *new* unpaid commission and calls `add_distribution(operator, staking_contract, operator, commission_amount)` with `operator = old_operator`, storing a pending share keyed by `old_operator`'s literal address [2](#0-1) . This amount is only `unlock_with_cap`'d (pending_inactive), not yet distributed.
3. `stake::set_operator_with_cap(&staking_contract.owner_cap, new_operator)` and `staking_contracts.add(new_operator, staking_contract)` — the same struct, including the still-pending `old_operator` share, is now stored under the `new_operator` key.

Once the lockup expires and the pool is eventually distributed (via `distribute`, `unlock_stake`, `update_commision`, or `request_commission` called against `staker`/`new_operator`), `distribute_internal` is invoked with `operator = new_operator` [3](#0-2) . Inside the payout loop:
```
if (recipient == operator) {
    recipient = beneficiary_for_operator(operator);
};
``` [4](#0-3) 
Here `recipient == old_operator` and `operator == new_operator`, so the redirect condition is false. The funds are paid directly to `old_operator`'s address, silently bypassing whatever beneficiary `old_operator` had registered via `set_beneficiary_for_operator` [5](#0-4)  before the switch.

The existing regression test `test_staker_can_switch_operator` demonstrates exactly this payout path (commission accrued by `operator_1` before the switch is later paid to `operator_1_address` directly) [6](#0-5) , but no test in the suite combines `switch_operator` with a previously-configured `BeneficiaryForOperator`, so this beneficiary-bypass path is untested and unhandled.

### Impact Explanation
An operator who has configured a beneficiary (e.g., a custody/cold wallet, or a compliance-mandated payout account, as documented for `set_beneficiary_for_operator`: "Any existing unpaid commission rewards will be paid to the new beneficiary") expects **all** unpaid commission — including commission requested at the moment they stop operating a pool — to be routed to that beneficiary. Because of this ordering bug, commission requested during `switch_operator` is instead credited to the operator's own account, corrupting the beneficiary payout accounting that the protocol explicitly documents as an invariant. This falls under "Operator commission, beneficiary payout ... corruption that credits the wrong account."

### Likelihood Explanation
This triggers automatically, with no attacker-controlled malicious input, any time a staker calls `switch_operator`/`switch_operator_with_same_commission` on an operator that has previously called `set_beneficiary_for_operator`. Both are ordinary, permissionless entry functions available to any staker/operator pair, so the sequence is easy to hit in normal usage (operator rotation is a supported, expected workflow) rather than requiring privileged access.

### Recommendation
When re-parenting a `StakingContract` to a new operator in `switch_operator`, either (a) fully flush/settle all pending distribution shares tied to `old_operator` (call an additional `distribute_internal` after `request_commission_internal`, before re-keying under `new_operator`), or (b) have `distribute_internal` redirect any recipient that equals a *former* operator by checking `beneficiary_for_operator(recipient)` unconditionally for any recipient that isn't a plain staker, rather than comparing against the currently active `operator` parameter.

### Proof of Concept
1. Staker creates a staking contract with `operator_1`, commission 10%.
2. `operator_1` calls `set_beneficiary_for_operator(operator_1, beneficiary)`.
3. Pool accrues rewards over an epoch.
4. Staker calls `switch_operator(staker, operator_1, operator_2, new_commission)`. This internally calls `request_commission_internal(operator_1, ...)`, creating a pending distribution share keyed to `operator_1`, then re-keys the `StakingContract` under `operator_2`.
5. Lockup expires; anyone calls `distribute(staker_address, operator_2)` (or any function invoking `distribute_internal` with `operator = operator_2`).
6. Observe: the commission amount computed in step 4 is paid to `operator_1`'s own address, not to `beneficiary` — despite `operator_1` having registered `beneficiary` to receive exactly this kind of payout.

    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;

            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
