### Title
Masker fails to detect phrase re-occurrences that require multi-character overlap ("border") after an almost-complete match diverges, leaking masked/protected values into the job trace - (File: common/buildlogger/internal/masker/masker.go)

### Summary
The per-phrase masking state machine in `masker.Write` tracks an in-progress match only as an integer count (`m.matching`) and, on a failed continuation, only checks whether the *single* current byte equals `phrase[0]` before giving up and flushing the tracked prefix as plain, unmasked text. This is not a correct KMP-style failure-function fallback, so phrases with an internal self-overlap ("border") of length ≥2 can appear in the combined output stream (across a `Trace.Write()` boundary) without being detected, and the previously tracked bytes get flushed verbatim before the algorithm re-scans.

### Finding Description
`Build.getNewLogger`/`buildlogger.New(log, entry, opts)` builds the mask-writer chain via `wrap()`, which calls `masker.New(w, l.maskPhrases)` [1](#0-0) , with `l.maskPhrases` populated from `Options.MaskPhrases` (masked/protected CI/CD variables, `CI_JOB_TOKEN`, resolved secrets, registry/cache credentials) [2](#0-1) .

Each phrase gets its own `masker` writer, stacked so state persists across separate `Write()` calls to allow phrase to be caught even when split by the executor/trace pipeline [3](#0-2) . Internally `m.matching` counts how many phrase bytes have matched so far, but it does not retain the actual matched bytes, and crucially the fallback logic on a failed extension is:

```go
if m.matching > 0 {
    _, err = m.next.Write(m.phrase[:m.matching])   // flush entire tracked prefix, unmasked
    ...
    if m.phrase[0] == p[n] {
        m.matching = 1
        ...
    }
}
m.matching = 0
``` [4](#0-3) 

This only restarts a partial match of length 1 (when the very next byte equals `phrase[0]`) or discards the match completely; it never considers a proper KMP border of length ≥2 in the discarded prefix. Since the discarded prefix is written directly to `m.next` before the loop resumes scanning, any occurrence of the phrase that legitimately begins inside that already-flushed border is never re-examined and is therefore never masked.

Concrete trace (verified by manual simulation of the exact code path):
- phrase = `"abcabd"` (has a length-2 border: prefix `"ab"` == suffix of `"abcab"`).
- `Write("abcab")` → `m.matching` becomes `5` (whole chunk buffered internally, nothing flushed yet).
- `Write("cabd")` → the next expected byte is `'d'` but the actual byte is `'c'`, so the mismatch branch fires: it flushes `"abcab"` unmasked, and since `phrase[0]=='a' != 'c'`, `m.matching` resets to `0` entirely (losing the valid `"ab"` border). The loop then rescans the remainder of `"cabd"` for `phrase[0]`, but the border bytes already flushed are gone.
- Combined logical stream = `"abcabcabd"`, which **does contain** the full phrase `"abcabd"` at offset 3, but the masker outputs `"abcabcabd"` entirely unmasked instead of masking it.

### Impact Explanation
Any masked/protected value (project/group masked variable, `CI_JOB_TOKEN`, resolved secret, registry or cache credential passed through `Options.MaskPhrases`) that happens to contain an internal self-overlapping ("periodic") byte pattern can be printed to the job log unmasked if its bytes are split across `Trace.Write()` calls at the specific offset that triggers this failure-function bug. This directly violates the invariant that masked/protected values must never appear in traces, and results in the secret being exposed in plaintext in the job log, which is readable by the job's own token/user and potentially other privileged viewers.

### Likelihood Explanation
Triggering the bug requires: (1) a masked phrase with an exploitable internal border of length ≥2, and (2) the job's stdout output being split into separate `Trace.Write()` calls exactly at the vulnerable offset. A pipeline author fully controls job script output (buffering, chunked writes, explicit flush timing via multiple `echo`/`printf` calls or file-descriptor writes) and can therefore deliberately choose both the phrase content (for their own masked CI/CD variables they define) and the split point, making exploitation of *self-chosen* masked variables straightforward and reliable. For runner/GitLab-generated secrets such as `CI_JOB_TOKEN` (high-entropy, unlikely to contain such a border by chance), reliable exploitation is far less likely but not provably impossible, and the underlying logic defect is real and reachable regardless.

### Recommendation
Replace the ad-hoc single-byte overlap check with a correct partial-match fallback (e.g., a proper KMP failure/border table computed once per phrase at `masker` construction time). On a failed extension, instead of discarding the tracked prefix outright or checking only `phrase[0] == p[n]`, fall back to the largest proper border of the already-matched prefix and re-attempt matching from there before flushing any bytes as literal/unmasked output, iterating until a valid restart point or zero is found (standard KMP mismatch handling).

func TestMasking_BorderOverlapAcrossWriteBoundary(t *testing.T) {
    buf := new(bytes.Buffer)
    m := New(internal.NewNopCloser(buf), internal.Unique([]string{"abcabd"}))

    _, err := m.Write([]byte("abcab"))
    require.NoError(t, err)
    _, err = m.Write([]byte("cabd"))
    require.NoError(t, err)
    require.NoError(t, m.Close())

    // "abcabcabd" contains "abcabd" at offset 3 and must be masked.
    assert.NotContains(t, buf.String(), "abcabd", "secret phrase leaked unmasked across Write() boundary")

func (l *Logger) wrap(w io.WriteCloser, streamID int, streamType StreamType) io.WriteCloser {
	if l.timestamping {

// Package masker implements a masking Writer, where specified phrases are
// replaced with the word "[MASKED]".
//
// To achieve masking over Write() boundaries, each phrase has its own writer.
// These writers are stacked, with each one calling the next, in length order,
