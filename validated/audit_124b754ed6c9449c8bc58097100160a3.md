### Title
Over-claim of loss-adjusted withdraw receipts at par after re-requesting in a later epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` selects the epoch to haircut solely via `lastWithdrawRequest[_user]`. If a user whose epoch-N receipt was haircutted by `stopEpochWithDuration`/`collectWithdrawFunds` makes a new `requestWithdraw` in a later epoch M before claiming, the epoch-N receipt is never cleared through the loss-adjusted path. It remains in `withdrawsRequests[_user]` and is later paid **at par** by `_claimFundedWithdrawRequest`, even though the borrower only funded the haircut amount. This is the credit-vault analog of the Synapse path-traversal bug class: a stale, attacker-influenced "path" (the request epoch stored in `lastWithdrawRequest`) lets a claim escape its intended loss-adjusted scope and reach fully-funded reserves.

### Finding Description
Flow:

1. In buffer of epoch N, user calls `IdleCDOEpochVariant.requestWithdraw`, which calls `IdleCreditVault.requestWithdraw`. This sets `withdrawsRequests[user] += amt`, `withdrawsRequestsByEpoch[user][N] += amt`, and `lastWithdrawRequest[user] = N` [1](#0-0) .
2. `stopEpoch` runs and the borrower under-funds: `collectWithdrawFunds(_amount < pendingBasis)` stores `lossRecoveryPriceByEpoch[N] = _amount * 1e18 / pendingBasis` and zeroes `pendingWithdraws` [2](#0-1) . Only the haircut amount of underlying was transferred to the strategy.
3. Instead of claiming, the user calls `requestWithdraw` again in a subsequent buffer (epoch M). `requestWithdraw` blindly overwrites `lastWithdrawRequest[user] = M` [3](#0-2) . The epoch-N entry in `withdrawsRequestsByEpoch` and `withdrawsRequests` is untouched.
4. After epoch M ends (funded normally at par by the borrower), the user calls `claimWithdrawRequest`. `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` = `lossRecoveryPriceByEpoch[M]` = 0 and returns 0 — the epoch-N loss receipt is skipped entirely [4](#0-3) .
5. `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — which still includes the epoch-N `normalAmount` — **at full value** via `_transferFundedClaim` [5](#0-4) .

The vault only holds `(claimBasis_N * lossRecoveryPrice) / 1e18` for the epoch-N piece; the excess `claimBasis_N * (1 - lossRecoveryPrice)/1e18` is paid out of underlyings belonging to active LPs or other claimants.

### Impact Explanation
Direct theft / insolvency. The attacker receives `claimBasis_N * (RECOVERY_FULL - lossRecoveryPriceByEpoch[N]) / RECOVERY_FULL` more than they are owed, paid from the strategy's underlying balance (i.e., other users' deposits and funded claims). Example: 100k USDC receipt haircut to 60%, then re-requested and claimed at par → ~40k USDC stolen. The `_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve`, not regular LP funds [6](#0-5) .

### Likelihood Explanation
Requires a `stopEpochWithDuration` loss event (honest manager call, realistic after borrower partial repayment) plus an unprivileged user holding a pending receipt who simply requests another withdraw before claiming — a normal action the code explicitly permits ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait another epoch", line 323). Any KYC-passed lender can execute it; no privileged cooperation is needed beyond the loss event occurring.

### Recommendation
Do not let the loss-adjusted lookup depend on the mutable `lastWithdrawRequest`. Either iterate/record the user's loss-adjusted epochs explicitly (e.g., a per-user list or checking `withdrawsRequestsByEpoch` against all epochs with nonzero `lossRecoveryPriceByEpoch`), or subtract the haircut in `collectWithdrawFunds`/`_clearWithdrawClaimForEpoch` at the time the loss is applied so the aggregate `withdrawsRequests` only ever contains fully-funded basis. At minimum, in `requestWithdraw`, force-settle any existing loss-adjusted receipt for the user's previous epoch before overwriting `lastWithdrawRequest`.

### Proof of Concept
Foundry fork PoC sketch (against the existing `IdleCreditVault.t.sol` harness):

```solidity
function testLossReceiptClaimedAtParAfterReRequest() external {
    address user = makeAddr('loss-user');
    _depositWithUser(user, 100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // buffer: request withdraw for all tranches in epoch 1
    vm.prank(user);
    uint256 basis1 = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // epoch 1 ends with a loss: borrower funds only 60% of pendingWithdraws
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    uint256 funded = pending * 6 / 10;
    _stopEpochWithLoss(funded); // stopEpochWithDuration -> collectWithdrawFunds(funded)
    assertGt(IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(1), 0);

    // user does NOT claim; instead re-requests in the next buffer (epoch 2)
    _depositWithUser(user, 10_000 * ONE_SCALE, true);
    vm.prank(user);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // overwrites lastWithdrawRequest

    // epoch 2 ends fully funded
    _startEpochAndCheckPrices(2);
    _stopEpochAndCheckPrices(2, initialProvidedApr, _expectedFundsEndEpoch());

    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();

    uint256 expected = basis1 * 6 / 10; // loss-adjusted share for epoch-1 receipt
    uint256 got = IERC20Detailed(defaultUnderlying).balanceOf(user) - balPre;
    // BUG: epoch-1 receipt paid at par; got >> expected + epoch-2 receipt
    assertGt(got, expected, 'loss receipt escaped haircut');
}
```

Key assertion: `lossRecoveryPriceByEpoch[1]` remains nonzero and `withdrawsRequestsByEpoch[user][1]` remains set after the claim, proving the epoch-1 receipt was paid via `_transferFundedClaim` at par rather than through the loss-adjusted path.

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
```
