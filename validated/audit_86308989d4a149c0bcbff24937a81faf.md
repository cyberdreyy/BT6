### Title
v1 tenure-change duplicate-block check uses `get_last_globally_accepted_block` instead of `get_last_signed_block`, letting a signer sign a conflicting tenure-start block - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
The Maia report describes two related validation paths that are supposed to enforce the same invariant, but one path is stale and does not account for a state dimension the other tracks, so the stale path lets through what the authoritative one would block. The exact same class of divergence exists in `stacks-signer`'s tenure-change duplicate-block guard: the v1 chainstate path checks only `get_last_globally_accepted_block`, while the v2 path (fixed specifically because of this gap) checks `get_last_signed_block`, which additionally covers locally-accepted (signed but not yet globally-accepted) blocks.

### Finding Description
`validate_tenure_change_payload` exists in both `stacks-signer/src/chainstate/v1.rs` and `stacks-signer/src/chainstate/v2.rs`, and both are meant to reject a tenure-change proposal with `RejectReason::DuplicateBlockFound` when the signer has already accepted a block in the same (new) tenure.

- v1 implementation queries `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` [1](#0-0) .
- v2 implementation instead queries `signer_db.get_last_signed_block(&block.header.consensus_hash)`, explicitly because "Only blocks we have signed (locally or globally accepted) count here" [2](#0-1) .

`get_last_signed_block` is documented as covering both `LocallyAccepted` and `GloballyAccepted` states, while `get_last_accepted_block`/`get_last_globally_accepted_block` differ specifically on whether pre-commit-only or locally-accepted-only blocks are counted [3](#0-2) .

The project's own regression test proves this is a real, previously-exploited gap: `check_tenure_change_rejects_when_locally_accepted_block_exists` explicitly documents "previously, the check used `get_last_globally_accepted_block`, which would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change" [4](#0-3) . The `CHANGELOG.md` confirms the fix was made ("When checking tenure change blocks, ensure there are no locally accepted blocks in the tenure, not just globally accepted blocks") [5](#0-4) , and `docs/signer-flows.md` explicitly documents that v1 and v2 diverge on this exact point today: "v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1 counts only globally accepted ones (`get_last_globally_accepted_block`)" [6](#0-5) .

This mirrors the Maia bug class precisely: two code paths meant to enforce one invariant (duplicate-block/one-per-tenure) diverge because one path (`v1`, analogous to `vMaia`'s own modifiers) was never updated to track a state transition (`LocallyAccepted`, analogous to the conversion-rate increase) that the other, corrected path (`v2`, analogous to `ERC4626PartnerManager`'s modifiers) already accounts for.

### Impact Explanation
`validate_tenure_change_payload` is checked only once, at proposal time, and is documented as never re-run at validate-ok or at signing time ("Two things belong to the proposal path only and are not re-run at validate-ok or at signing") [7](#0-6) . If a v1-protocol signer has already locally accepted (i.e., signed, via crossing the 70% signature threshold marked with `mark_locally_accepted`) a first tenure-start block for a tenure, but that block has not yet been globally accepted by the node, `get_last_globally_accepted_block` returns `None`, so v1's duplicate check passes a second, competing tenure-start block for the very same tenure. The signer then proceeds to sign that second block as well, since the duplicate guard never fires again downstream. This produces two signed, conflicting tenure-start blocks for the same tenure from the same signer — a direct equivocation/conflicting-block signature, which is the highest-severity outcome defined by the rules ("a signer signing an invalid, non-canonical, or conflicting block").

### Likelihood Explanation
This requires only a single miner (one-slot) proposing a first tenure-start block, waiting for it to reach the local-acceptance threshold via normal signer gossip (no majority of signers colluding, no key compromise), and then proposing a second competing tenure-start block for the same tenure before the first is globally accepted by the node. This is entirely within the "one-slot miner (plus gossip)" trigger class permitted by the rules, and does not require a majority of signers to misbehave — only the miner needs to race the global-acceptance window. It is gated on the affected signer(s) still running the v1 protocol path (mixed-version fleets are explicitly a supported/expected scenario per `docs/signer-flows.md` section 6's discussion of "mixed-version fleets").

### Recommendation
Update `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, matching the v2 implementation, so that locally-accepted (signed) blocks are also treated as blocking a duplicate tenure-start proposal.

### Proof of Concept
1. Signer is running the v1 chainstate path (v1 protocol version active in the reward cycle).
2. Miner proposes tenure-start block A for tenure `T`. Enough signers (including the victim signer) sign it, crossing the 70% threshold, so the victim signer calls `mark_locally_accepted` on block A, but the stacks-node has not yet processed/globally-accepted A.
3. Miner proposes a second, competing tenure-start block B for the same tenure `T` (e.g., with different transactions).
4. `validate_tenure_change_payload` (v1.rs) calls `signer_db.get_last_globally_accepted_block(consensus_hash)` [8](#0-7)  — this returns `None` because A is only locally accepted, not globally accepted, so the `DuplicateBlockFound` rejection at lines 510-518 is skipped.
5. Block B passes the proposal-time duplicate check and is never re-checked at validate-ok or signing time per the documented flow [9](#0-8) ; the victim signer proceeds to sign B.
6. The signer has now signed two conflicting tenure-start blocks (A and B) for the same tenure `T` — the exact scenario the v2 regression test `check_tenure_change_rejects_when_locally_accepted_block_exists` was written to prevent [4](#0-3) , demonstrating that v1's un-patched equivalent remains vulnerable.

/// Test that a tenure change proposal is rejected when a locally-accepted
/// (but not globally-accepted) block already exists in the same tenure.
///
/// This is a regression test: previously, the check used
/// `get_last_globally_accepted_block`, which would miss blocks in
/// `LocallyAccepted` or `PreCommitted` state and incorrectly allow
/// a duplicate tenure change.
#[test]
fn check_tenure_change_rejects_when_locally_accepted_block_exists() {
    let MockServerClient {
        server,
        client: stacks_client,
        config: _,
    } = MockServerClient::new();
    let rand_int = server.local_addr().unwrap().port();

    let (_stacks_client, mut signer_db, block_sk, mut block, cur_sortition, _, sortitions_view) =
        setup_test_environment(&format!("{}_{rand_int}", function_name!()));

    // Set up the block in the current tenure
    block.header.consensus_hash = cur_sortition.data.consensus_hash.clone();
    let parent_block_header = make_parent_header_meta(&block_sk, &mut block);
    let response = crate::client::tests::build_get_tenure_tip_response(&parent_block_header);

    // Insert a locally-accepted block in the same tenure (same consensus_hash).
    // This simulates a miner's first tenure-start block that the signer has
    // locally accepted but that hasn't yet gathered enough signatures to be
    // globally accepted. In practice this block would contain a tenure-change
    // and coinbase tx, but we omit them here because `get_last_accepted_block`
    // only queries by consensus_hash and block state — the block's transactions
    // are irrelevant to the duplicate check.
    let existing_block_proposal = BlockProposal {
        block: NakamotoBlock::new(
            NakamotoBlockHeader {
                version: 1,
                chain_length: 10,
                burn_spent: 10,
                consensus_hash: cur_sortition.data.consensus_hash.clone(),
                parent_block_id: StacksBlockId([0; 32]),
                tx_merkle_root: Sha512Trunc256Sum([0; 32]),
                state_index_root: TrieHash([0; 32]),
                timestamp: 11,
                miner_signature: MessageSignature::empty(),
                signer_signature: vec![],
                pox_treatment: BitVec::ones(1).unwrap(),
                problematic_txs: vec![],
            },
            vec![],
        ),
        burn_height: 2,
        reward_cycle: 1,
        block_proposal_data: BlockProposalData::empty(),
    };
    let mut existing_block_info = BlockInfo::from(existing_block_proposal);
    existing_block_info.mark_locally_accepted(false).unwrap();
    signer_db.insert_block(&existing_block_info).unwrap();

    // Now build a *second* tenure-start block proposal for the same tenure.
    // This simulates the miner attempting to replace their first block (e.g.,
    // with different transactions). The tenure change tx must have
    // cause=BlockFound with a coinbase to be recognized as a tenure-start block.
    let tenure_change_payload = TenureChangePayload {
        tenure_consensus_hash: cur_sortition.data.consensus_hash.clone(),
        prev_tenure_consensus_hash: cur_sortition.data.parent_tenure_id.clone(),
        burn_view_consensus_hash: cur_sortition.data.consensus_hash.clone(),
        previous_tenure_end: block.header.parent_block_id.clone(),
        previous_tenure_blocks: 1,
        cause: TenureChangeCause::BlockFound,
        pubkey_hash: Hash160::from_node_public_key(&StacksPublicKey::from_private(&block_sk)),
    };
    let tenure_change_tx = make_tenure_change_tx(tenure_change_payload);
    let coinbase_tx = StacksTransaction::new(
        TransactionVersion::Testnet,
        TransactionAuth::Standard(TransactionSpendingCondition::new_initial_sighash()),
        TransactionPayload::Coinbase(CoinbasePayload([0; 32]), None, Some(VRFProof::empty())),
    );
    *block.executed_and_skipped_txs_mut() = vec![tenure_change_tx, coinbase_tx];
    block.header.sign_miner(&block_sk).unwrap();

    let exit_flag = Arc::new(AtomicBool::new(false));
    let moved_exit_flag = exit_flag.clone();

    let serve = std::thread::spawn(move || {
        crate::client::tests::write_response_nonblockinig(
            &server,
            response.as_bytes(),
            moved_exit_flag,
        );
    });

    let result = sortitions_view.check_proposal(&stacks_client, &mut signer_db, &block);

    exit_flag.store(true, Ordering::SeqCst);
    serve.join().unwrap();

    // The proposal should be rejected because there's already a locally-accepted
    // block in this tenure. Before the fix, this would have incorrectly passed
    // because get_last_globally_accepted_block would not find the locally-accepted block.
    assert!(
        matches!(result, Err(RejectReason::DuplicateBlockFound)),
        "Expected DuplicateBlockFound rejection when a locally-accepted block exists in the tenure, got: {result:?}"
    );
}
