### Title
`parse_bpf_upgradeable_loader` uses a conditional (variable) metadata offset while the runtime always writes a fixed-size metadata header, causing JSON-RPC `jsonParsed` decoding to return the wrong program/buffer bytes for accounts with no authority - (File: `account-decoder/src/parse_bpf_loader.rs`)

### Summary
The externally reported bug is a classic proxy "storage layout" mismatch: the writer of storage (the logic/implementation contract) and the reader (the proxy) disagree about where a fixed-size header ends and variable data begins, so if the assumptions diverge, data gets misread. The Solana analog is `account-decoder`'s parsing of `bpf_loader_upgradeable` (`UpgradeableLoaderState::Buffer`/`ProgramData`) accounts, where the on-chain writer (`programs/bpf_loader/src/lib.rs`) always uses a **fixed** metadata size for the header, but the RPC-facing decoder (`account-decoder/src/parse_bpf_loader.rs`) computes a **variable** offset depending on whether the authority `Option<Pubkey>` is `Some` or `None`.

### Finding Description
In `account-decoder/src/parse_bpf_loader.rs`, `parse_bpf_upgradeable_loader` computes the start of the embedded program/ELF bytes as: [1](#0-0) 
and similarly for `ProgramData`: [2](#0-1) 

Both branches subtract `serialized_size(&Pubkey::default())` from the metadata size whenever `authority_address`/`upgrade_authority_address` is `None`, on the assumption that bincode encodes a smaller `Option::None` than `Option::Some(Pubkey)` and that the account's stored bytes shrink accordingly.

However, every write path in the loader program itself treats the metadata region as a **fixed-size header regardless of Option state**. For example, `deploy_program`/`Upgrade`/`extend_program` all use the constant `UpgradeableLoaderState::size_of_programdata_metadata()` unconditionally to locate where ELF bytes begin, with no adjustment for `None` vs `Some`: [3](#0-2) [4](#0-3) [5](#0-4) 

The same fixed-offset assumption is used by other trusted account readers such as `svm/src/program_loader.rs`: [6](#0-5) 
and by `cli/src/program.rs`'s dump/list logic, which slices at the constant `size_of_programdata_metadata()`/`size_of_buffer_metadata()` with no Option-based adjustment: [7](#0-6) 

Because the account's allocated size and the actual byte layout written on-chain never shrink when the authority becomes `None` (the account was created at a fixed `size_of_programdata(max_data_len)`/`size_of_buffer(len)` and `set_state` just overwrites the leading metadata bytes in place, leaving the ELF payload where it always was), `parse_bpf_upgradeable_loader`'s smaller offset when `authority_address.is_none()` reads starting **earlier** than the true payload boundary. This causes the JSON-parsed `data` field returned by `jsonParsed`-encoded `getAccountInfo`/`getProgramAccounts` to include trailing metadata bytes as if they were program bytes, i.e., wrong/misaligned account data returned from an unprivileged RPC query.

### Impact Explanation
This is reachable by any unprivileged client requesting `encoding: jsonParsed` on a `bpf_loader_upgradeable`-owned Buffer or ProgramData account whose authority has been renounced (`SetAuthority`/`SetAuthorityChecked` with `new_authority = None`, a common "finalize"/immutable pattern). The RPC response for such accounts will misreport program data content (data corruption/misreporting at the RPC layer), which falls under the "wrong-slot/fork/account data returned" and "decoder... misreporting" impact categories called out in scope.

### Likelihood Explanation
Renounced-authority (immutable) programs/buffers are common in production (e.g., finalized on-chain programs), and `jsonParsed` is a standard, frequently used encoding for `getAccountInfo`/`getProgramAccounts`. No special permissions or multiple calls are required — a single unprivileged RPC request against an existing immutable program account triggers the mis-offset.

### Recommendation
Make `parse_bpf_upgradeable_loader`'s offset calculation match the loader's actual on-chain write behavior: always use the fixed `UpgradeableLoaderState::size_of_buffer_metadata()` / `size_of_programdata_metadata()` regardless of whether the authority is `Some` or `None`, removing the conditional subtraction of `serialized_size(&Pubkey::default())`. This aligns the decoder with the fixed-size header contract enforced by `programs/bpf_loader/src/lib.rs` and `svm/src/program_loader.rs`.

### Proof of Concept
1. Deploy an upgradeable program via `bpf_loader_upgradeable` (creates Program + ProgramData accounts, ProgramData allocated at `size_of_programdata(max_data_len)` with a fixed header of `size_of_programdata_metadata()` bytes).
2. Call `SetAuthority`/`SetAuthorityChecked` on the ProgramData account with `new_authority = None` to make it immutable — the account keeps its original size; only the leading metadata bytes are rewritten in place (`upgrade_authority_address: None`) as shown in `programs/bpf_loader/src/lib.rs` (`SetAuthority` handling around lines 577-609).
3. Query the account via RPC with `getAccountInfo(programdata_address, {"encoding": "jsonParsed"})`.
4. `parse_bpf_upgradeable_loader` computes `offset = size_of_programdata_metadata() - serialized_size(&Pubkey::default())`, which is smaller than the actual fixed header size the runtime used to write the account, so `data[offset..]` includes leftover header bytes (the discriminant/slot/option-tag bytes) prepended to what should be pure ELF bytes — the returned `data.rawProgram`/binary content is misaligned relative to the real program bytes at `size_of_programdata_metadata()..`.
