This confirms the asymmetry. `SignerDb::add_block_signature` at `stacks-signer/src/signerdb.rs:1876-1880` explicitly `DELETE`s any prior rejection row for that signer/block before recording the new signature, keeping the signer-side rejection/acceptance tallies mutually exclusive (`get_block_rejection_signer_addrs` returns empty after a flip, as shown in the `reject_then_accept` test at `stacks-signer/src/signerdb.rs:3234-3263`).

The node-side coordinator does not have this safeguard.

### Title
Node coordinator never retracts stale rejection weight when a signer flips to acceptance, letting phantom rejected weight force a spurious `SignersRejected` on a validly-signed block - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener`'s `BlockStatus` accumulates `total_weight_approved` and `total_weight_rejected` as two independent monotonic counters keyed on `responded_signers`/`gathered_signatures`, but only prevents double-counting *within* each direction — it never subtracts a signer's weight from `total_weight_rejected` when that same signer later sends an `Accepted` response for the same block. This is the direct analog of the Yieldoor bug: the "accept" tally is computed without netting out weight that the reject tally has already booked, so idle/duplicated weight lingers and corrupts a threshold decision downstream.

### Finding Description
In the `Rejected` branch, weight is added once per signer via `block.responded_signers.insert(slot_id)` [1](#0-0) . In the `Accepted` branch, the only dedup guard is `!block.gathered_signatures.contains_key(&slot_id)` [2](#0-1) ; it never checks or clears `responded_signers`/`total_weight_rejected` for a signer transitioning from reject to accept. Contrast this with the signer-side `SignerDb::add_block_signature`, which explicitly deletes the signer's prior rejection row before recording the new signature [3](#0-2) , and whose accept/reject tallies are proven mutually exclusive by the `reject_then_accept`/`accept_then_reject` tests [4](#0-3) . A rejection is documented in this codebase as a "revocable opinion" that a signer can retract by later signing the same proposal (e.g. after a reproposal that resolves the original rejection reason) [5](#0-4) , and `handle_block_pre_commit`'s comments confirm signers can reconsider a previously-rejected block when a new proposal for the same hash arrives [6](#0-5) . So this reject→accept transition for the same `signer_signature_hash` is a normal, legitimate protocol path reachable by a single signer (no majority needed), not a contrived edge case.

The coordinator's decision loop checks the rejection condition before the acceptance condition: `if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight { ... return Err(SignersRejected) } else if block_status.total_weight_approved >= self.weight_threshold { return Ok(...) }` [7](#0-6) . Because a signer's weight can be simultaneously present in both `total_weight_rejected` (stale, never retracted) and `total_weight_approved` (freshly added on the flip), and rejection is checked first, a block that has genuinely reached the ≥70% acceptance threshold among currently-standing votes can instead be discarded as `SignersRejected` purely because of leftover phantom rejection weight from a signer who has since legitimately switched to Accept.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality explicitly called out in scope: the coordinator's `total_weight_rejected` no longer reflects the set of signers who currently hold a rejecting position, yet it is used, un-corrected, to make a binding decision. The consequence is that the coordinator can wrongly treat a validly, sufficiently signed block as globally rejected (`NakamotoNodeError::SignersRejected`), which:
- wedges block production for the miner (liveness impact — the miner discards a block the signer set actually approved and must reattempt tenure/mining), and
- creates a split view between the signer set (which locally/eventually treats the block as accepted per `store_and_process_block_signature`) and the coordinator (which treats it as rejected), i.e. a signed-vs-validated state divergence.

This requires only a single signer's own natural reject→accept transition (triggered by rejection-then-reproposal, a normal protocol event), not a majority or another signer's key, matching the "one-slot miner (plus gossip)"-triggerable bar from scope.

### Likelihood Explanation
The reject→accept transition for the same block hash is an explicitly supported and tested code path on the signer side (comments and tests confirm rejections are revocable and reconsideration on reproposal is intended behavior), so the preconditions are not exotic — any single flaky/slow-to-validate signer that initially rejects (e.g. on a transient validation issue) and later accepts once conditions clear will trigger the discrepancy on the coordinator side. The bug is a straightforward missing-decrement, present unconditionally in the `Accepted` handler.

### Recommendation
In the `Accepted` handling branch of `stackerdb_listener.rs`, before adding the signer's weight to `total_weight_approved`, check whether `responded_signers` already contains this slot due to a prior rejection and, if so, retract the corresponding weight from `total_weight_rejected` (mirroring `SignerDb::add_block_signature`'s deletion of the stale rejection row on the signer side), so the two tallies remain mutually exclusive and reflect only each signer's current position.

### Proof of Concept
1. Miner proposes block `B` (hash `H`) to the signer set.
2. Signer `S` (weight `w`) sends `BlockResponse::Rejected` for `H` due to a transient/local issue. Coordinator: `total_weight_rejected += w`, `responded_signers ∪= {S}` [1](#0-0) .
3. Other signers accumulate enough weight that `total_weight_approved` is just under threshold; the reject condition is not yet triggered because `w` alone is below the blocking minority.
4. The condition causing `S`'s rejection is resolved (e.g. reproposal with the same header/hash), and `S` legitimately reconsiders and sends `BlockResponse::Accepted` for the same `H`.
5. Coordinator's `Accepted` handler only checks `gathered_signatures`, not `responded_signers`; it adds `w` to `total_weight_approved` without removing it from `total_weight_rejected` [8](#0-7) .
6. If, meanwhile, other signers' rejections (unrelated to `S`) plus the stale `w` push `total_weight_rejected` over the blocking-minority threshold at the moment the coordinator polls, `wait_for_block_acceptance`'s rejection check fires first and returns `SignersRejected` [7](#0-6) , even though the true current accepting weight (including `S`'s corrected vote) already reached ≥70%.
