### Title
Unbounded zstd compression cost in `encode_ui_account` for `base64Zstd`-encoded `getAccountInfo` on attacker-grown accounts - ([File: account-decoder/src/lib.rs])

### Summary
`encode_ui_account` compresses the *entire* (post-slice) account data with `zstd::stream::write::Encoder` whenever a client requests `UiAccountEncoding::Base64Zstd`, with no cap on the input size or on CPU/memory spent compressing it. Since an attacker fully controls the size of data stored in an account they own (up to `MAX_ACCOUNT_DATA_LEN`, ~10 MiB), a single `getAccountInfo` call against such a large account forces the validator to zstd-compress up to the max account size in one synchronous RPC call.

### Finding Description
`encode_ui_account` in `account-decoder/src/lib.rs` handles `UiAccountEncoding::Base64Zstd` by calling `zstd::stream::write::Encoder::new(Vec::new(), 0)` and then `write_all(slice_data(account.data(), data_slice_config))` followed by `finish()`: [1](#0-0) 

This is reached from the RPC handler via `encode_account`, which only imposes a size limit for `Binary`/`Base58` encodings (`MAX_BASE58_BYTES`), not for `Base64Zstd`: [2](#0-1) 

`slice_data` only truncates the buffer if the client supplies an explicit `dataSlice` offset/length; by default (no `dataSlice`), the full account data (`account.data()`) is passed straight through: [3](#0-2) 

An unprivileged attacker who owns a program account can grow that account's data up to `MAX_ACCOUNT_DATA_LEN` via `TransactionAccounts::set_data_length`/CPI realloc within normal transaction execution rules (no special privilege required beyond controlling their own program/account). Once such a max-size account exists on-chain, a single `getAccountInfo` RPC call with `encoding: "base64+zstd"` and no `dataSlice` forces the validator's JSON-RPC thread to run zstd compression over the full ~10 MiB buffer synchronously within that one request's processing, with no explicit CPU-time or memory budget check gating this work relative to request cost.

### Impact Explanation
This falls under the RPC single-request unbounded-cost category: one low-rate `getAccountInfo` call can force disproportionate CPU (compression work scales with input size, and zstd compression is far more CPU-intensive than the plain-Base64 path) and heap allocation (multiple buffers: original account data buffer, `Vec::new()` growing to hold compressed output, base64-encoded output, and the final JSON-serialized response) for a single request. This is a legitimate, in-scope cost-asymmetry issue: cost of one request is not bounded independent of attacker-controlled account size, matching the "unbounded cost for a single low-rate call" acceptance criterion.

### Likelihood Explanation
Highly feasible and fully repeatable: the attacker only needs (1) a program they control that can grow one of its owned accounts to `MAX_ACCOUNT_DATA_LEN` (a standard, permitted on-chain operation, not requiring elevated privilege), and (2) to issue a single `getAccountInfo` JSON-RPC call with `encoding=base64+zstd` against that account, staying within the one-call-per-`CLUSTER_SLOT_TIME_TARGET/2` constraint. No mocked paths, no direct store mutation, and no multi-client amplification are required — this is a straightforward, deterministic single-request cost spike that can be repeated periodically at the allowed low rate.

### Recommendation
Bound the cost of `Base64Zstd` encoding relative to the size of the data being compressed, analogous to the existing `MAX_BASE58_BYTES` check for `Binary`/`Base58`:
- Add an explicit maximum data-size threshold for `Base64Zstd` encoding in `encode_account` (rpc/src/rpc.rs) similar to the `MAX_BASE58_BYTES` check, rejecting or falling back to plain `Base64` (uncompressed) when the sliced data exceeds the threshold.
- Alternatively/additionally, use a bounded/streaming compression level and cap CPU/memory via a preallocated bounded buffer, and measure/limit actual compression wall-time per request in the RPC layer.
- Ensure the same guard applies uniformly regardless of `dataSlice`, since by default no slice is applied and the full account can reach `MAX_ACCOUNT_DATA_LEN`.

### Proof of Concept
```rust
// account-decoder/src/lib.rs (add near existing tests)
#[test]
fn test_base64_zstd_cost_scales_with_account_size() {
    use std::time::Instant;

    // Simulate an attacker-grown account near MAX_ACCOUNT_DATA_LEN.
    const MAX_ACCOUNT_DATA_LEN: usize = 10 * 1024 * 1024; // matches transaction-context constant
    let large_data = vec![0xABu8; MAX_ACCOUNT_DATA_LEN];
    let account = AccountSharedData::from(Account {
        data: large_data,
        ..Account::default()
    });

    let start = Instant::now();
    let encoded = encode_ui_account(
        &Pubkey::default(),
        &account,
        UiAccountEncoding::Base64Zstd,
        None,
        None, // no dataSlice: full account data is compressed
    );
    let elapsed = start.elapsed();

    // Expected (failing) assertion: a single getAccountInfo request's
    // encoding cost should be bounded by an explicit limit independent
    // of attacker-controlled account size, e.g. under a fixed budget
    // (e.g. a few milliseconds) regardless of input size.
    assert!(
        elapsed.as_millis() < 5,
        "encode_ui_account took {:?} for {}-byte account; cost is unbounded relative to a single request budget",
        elapsed,
        MAX_ACCOUNT_DATA_LEN
    );
    assert_matches::assert_matches!(
        encoded.data,
        UiAccountData::Binary(_, UiAccountEncoding::Base64Zstd)
    );
}
```
Run with `cargo test -p solana-account-decoder test_base64_zstd_cost_scales_with_account_size --release -- --nocapture` and observe compression time/memory growing with account size, with no enforced upper bound in `encode_ui_account`/`encode_account`, confirming the missing cost guard.

```rust
fn slice_data(data: &[u8], data_slice_config: Option<UiDataSliceConfig>) -> &[u8] {
    if let Some(UiDataSliceConfig { offset, length }) = data_slice_config {
        if offset >= data.len() {
            &[]
        } else if length > data.len() - offset {
            &data[offset..]
        } else {
            &data[offset..offset + length]
        }
    } else {
        data
    }
}
```

```rust
fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
```
