### Title
`claimInstantWithdrawRequest` pays the full instant receipt without validating it was actually funded, letting an unprivileged claim drain underlyings earmarked for other (funded) withdraw claimants - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The reported CVE is a missing-input-validation flaw (CWE-20) that lets a caller trigger unauthorized access to data/funds it was not entitled to. The analog in idle-tranches is `IdleCreditVault.claimInstantWithdrawRequest`: it burns the caller's instant-withdraw receipt and transfers the entire recorded amount out of the strategy's underlying balance without verifying that this specific request was actually funded, and without touching the `pendingInstantWithdraws` accounting that tracks the unfunded remainder.

### Finding Description
Instant withdrawals work in two steps:

- `requestInstantWithdraw` burns CDO strategy tokens, mints a receipt to the user, and increases `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]` and the global `pendingInstantWithdraws` (IdleCreditVault.sol:356-375).
- `collectInstantWithdrawFunds` is the only funding step: it decreases `pendingInstantWithdraws` and pulls underlying from the CDO into the strategy (IdleCreditVault.sol:398-403). Notably, it does **not** mark which user requests are funded — funding is purely aggregate.

The claim path performs no corresponding check:

```solidity
function claimInstantWithdrawRequest(address _user) external {
  _onlyIdleCDO();
  if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
    _claimDefaultedInstantWithdrawRequest(_user);
  }
  uint256 amount = instantWithdrawsRequests[_user];
  _burn(_user, amount);
  instantWithdrawsRequests[_user] = 0;
  _transferFundedClaim(_user, amount);
}
```

(IdleCreditVault.sol:380-393)

And on the CDO side the only gate is `allowInstantWithdraw` (IdleCDOEpochVariant.sol:975-979) — there is no epoch delay, no `instantWithdrawDelay` enforcement, and no check that `pendingInstantWithdraws` (the still-unfunded remainder) has reached zero or that the caller's share was funded.

`_transferFundedClaim` only protects `defaultRecoveryReserve`; it happily spends any other underlying sitting in the strategy (IdleCreditVault.sol:897-907). That balance includes:

- underlyings collected via `collectWithdrawFunds` to back *normal* (queued) withdraw receipts that honest users claim through `_claimFundedWithdrawRequest`, and
- prefunded instant-withdraw cash moved to the strategy at `startEpoch` (referenced by `_defaultPrefundedInstantReserve`, IdleCreditVault.sol:712-723).

So a caller whose instant request is *unfunded* (or only partially prefunded) can still burn their receipt and pull the full amount from funds reserved for other claimants.

### Impact Explanation
Broken invariant: "one receipt, one payout — a receipt may only spend its own funded backing."

Attack sequence (running epoch, instant withdrawals enabled):

1. Epoch starts; the CDO moves only partial prefunded cash to the strategy, or a prior `stopEpoch` collected normal-withdraw funds into the strategy via `collectWithdrawFunds`.
2. Attacker calls `requestWithdraw`/instant request, minting a receipt and increasing `pendingInstantWithdraws`.
3. Before `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` funds the request (i.e., while `pendingInstantWithdraws > 0`), attacker calls `claimInstantWithdrawRequest` on the CDO, which invokes `IdleCreditVault.claimInstantWithdrawRequest(attacker)`.
4. The strategy pays the attacker's full `instantWithdrawsRequests` amount out of the shared underlying balance — consuming funds earmarked for honest funded normal-withdraw claimants or other instant claimants.
5. Honest claimants' later `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls revert on insufficient balance (permanent freezing of their funded claims), and the attacker exits with underlying they were never entitled to. Loss is bounded by the strategy's non-reserve underlying balance.

### Likelihood Explanation
Requires an instant-withdraw-enabled vault and a window where a request exists but is not (fully) funded — which is the *normal* state between request and `collectInstantWithdrawFunds`. The attacker only needs to be a KYC-passing lender able to request an instant withdrawal; no privileged role is needed. The missing funding check is unconditional.

### Recommendation
Track funded vs. unfunded instant requests explicitly (e.g., decrease `pendingInstantWithdraws` and a per-user/aggregate funded counter inside `claimInstantWithdrawRequest`, or only allow claiming an amount proportional to collected funds), and make `claimInstantWithdrawRequest` revert while the caller's claim exceeds the funded portion. Alternatively, hold funded instant cash in a segregated bucket that `_transferFundedClaim` cannot spend for unrelated claims.

### Proof of Concept
Foundry fork (mainnet, mirroring `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol` setup at block 23032567 with the etched `IdleCDOEpochVariant`/`IdleCreditVault`):

```solidity
// setup: enable instant withdraws, deposit AA for attacker and victim,
// get victim a *funded* normal withdraw receipt via a prior stopEpoch + collectWithdrawFunds
// so the strategy holds victimBacking underlying.
//
// epoch starts; instant queue is only partially prefunded
vm.prank(attacker);
uint256 req = cdoEpoch.requestInstantWithdraw(attackerAmount, address(AAtranche));

// attacker request is still unfunded:
assertGt(IdleCreditVault(strategy).pendingInstantWithdraws(), 0);

// no delay/funding check on the claim path
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();

// attacker received full req paid out of the shared strategy balance,
// which included victim's funded backing
uint256 stolen = underlying.balanceOf(attacker) - balPre;
assertGt(stolen, fundedShareOfAttacker);

// victim's funded claim now reverts on insufficient strategy balance
vm.prank(victim);
vm.expectRevert(); // ERC20 transfer exceeds balance
cdoEpoch.claimWithdrawRequest();
```

Caveat: I was unable to fully trace `getInstantWithdrawFunds`/`requestInstantWithdraw` gating on the CDO side in this session; if the CDO blocks `claimInstantWithdrawRequest` until `pendingInstantWithdraws == 0` somewhere outside the lines reviewed, the exploit window shrinks accordingly. The strategy-level function itself (`IdleCreditVault.claimInstantWithdrawRequest`) performs no funding validation and relies entirely on the CDO — the same improper-validation pattern as the referenced advisory.
