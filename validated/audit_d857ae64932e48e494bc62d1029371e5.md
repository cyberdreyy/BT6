### Title
Unprivileged rate-limit bypass via flashloan-flag wrapping of an ordinary withdrawal - (File: `programs/marginfi/src/utils/general.rs::record_withdrawal_outflow`, `programs/marginfi/src/state/rate_limiter.rs::should_skip_rate_limit`)

### Summary
`record_withdrawal_outflow` skips both the bank-level and group-level rate limiters whenever `should_skip_rate_limit(marginfi_account.account_flags)` is true, and that function simply checks the `ACCOUNT_IN_FLASHLOAN`, `ACCOUNT_IN_RECEIVERSHIP`, and `ACCOUNT_IN_DELEVERAGE` bits with no further validation that a real flashloan repayment or liquidation actually occurred. Because `ACCOUNT_IN_FLASHLOAN` is set/unset by the fully permissionless `lending_account_start_flashloan` / `lending_account_end_flashloan` instruction pair (any account owner may call these on their own account), a normal user can wrap an ordinary `lending_account_withdraw` (or the kamino/juplend/drift/solend withdraw variants) that exceeds the configured hourly/daily bank or group cap inside a flashloan and have the withdrawal outflow accounting entirely skipped.

### Finding Description
`should_skip_rate_limit` is defined as: [1](#0-0) 

and is consumed unconditionally inside `record_withdrawal_outflow`: [2](#0-1) 

`ACCOUNT_IN_FLASHLOAN` is set by `lending_account_start_flashloan`, whose account constraints only require `has_one = authority` (i.e. the caller's own signature) — no admin/oracle/integration-operator gate: [3](#0-2) 

It is cleared by `lending_account_end_flashloan`, which only re-checks account health via `check_account_init_health` — it does not verify that any borrowed liquidity was returned or that withdrawn collateral was redeposited, and it does not re-run rate-limit accounting for withdrawals made while the flag was set: [4](#0-3) 

Every withdraw path (`lending_account_withdraw`, and the kamino/juplend/drift/solend withdraw instructions) calls `record_withdrawal_outflow` with the account's live `account_flags`, e.g.: [5](#0-4) 

Since a user's own withdrawal of their own healthy collateral does not require restoring it before `end_flashloan`'s health check (that check only enforces the account remains solvent, not that any specific outflow was reversed), the attacker can:
1. Call `lending_account_start_flashloan` on their own account (permissionless, self-authorized) — sets `ACCOUNT_IN_FLASHLOAN`.
2. Call `lending_account_withdraw` for an amount exceeding the configured bank/group hourly or daily rate-limit cap. `record_withdrawal_outflow` sees `ACCOUNT_IN_FLASHLOAN` set and skips both the bank `try_record_outflow` call and the group-level capacity check/`RateLimitFlowEvent` emission entirely.
3. Call `lending_account_end_flashloan`, which only requires the account to remain healthy (e.g., attacker has sufficient remaining/other collateral) and clears the flag.

The withdrawal permanently leaves the protocol's liquidity vault, with no rate-limit accounting ever recorded — the admin-configured hourly/daily outflow caps designed to throttle large withdrawals are fully bypassed by an ordinary, permissionless user action.

### Impact Explanation
This bypasses the admin-configured bank and group rate limiters described in `guides/ADMIN/RATE_LIMITS_AND_DELEVERAGE_WITHDRAW_LIMITS.md`, whose stated purpose is to cap large native/USD outflows within hourly/daily windows. An unprivileged user can drain up to the full amount of their own withdrawable position in a single flashloan-wrapped transaction regardless of the configured cap, and the omission is silent — no `RateLimitFlowEvent` is emitted for the off-chain aggregator, so the outflow is invisible to monitoring built on top of that event stream. This directly matches the scoped impact: "unauthorized bypass of admin-configured outflow protections, unsafe settlement of large flows outside the rate window."

### Likelihood Explanation
Fully feasible and repeatable by any user with a funded, healthy `MarginfiAccount`: no admin/oracle/integration-operator privileges, no leaked keys, no race conditions — just two permissionless instructions (`lending_account_start_flashloan`, `lending_account_end_flashloan`) sandwiching the normal `lending_account_withdraw` call, all within a single transaction, exactly the reachable call sequence described in the question.

### Recommendation
`record_withdrawal_outflow` (and the parallel `record_deposit_inflow`) should not unconditionally trust `ACCOUNT_IN_FLASHLOAN`/`ACCOUNT_IN_RECEIVERSHIP`/`ACCOUNT_IN_DELEVERAGE` to skip accounting for withdrawals that are not actually reversed. Options: (a) always record outflow into the bank/group rate limiter regardless of these flags, and instead net out inflows recorded before `end_flashloan` against the same-transaction outflow so only genuinely temporary flows are exempted; or (b) track flashloan-specific cumulative outflow and enforce/settle it against the rate limiter at `lending_account_end_flashloan` before clearing `ACCOUNT_IN_FLASHLOAN`, so a flashloan cannot be used purely as a rate-limit bypass wrapper for a net permanent withdrawal.

### Proof of Concept
Rust integration test plan (using existing `test-utils` harness):
1. Set up a group/bank and call `configure_bank_rate_limits` (or `configure_group_rate_limits`) with a small hourly max outflow (e.g. 100 tokens).
2. Fund a user account with collateral well above the cap (e.g. 10,000 tokens) so post-withdrawal health remains positive.
3. Build a single transaction: `lending_account_start_flashloan(end_index=2)` → `lending_account_withdraw(amount=1000)` (exceeds the 100-token cap) → `lending_account_end_flashloan`.
4. Assert the transaction succeeds (no `BankHourlyRateLimitExceeded`/`GroupHourlyRateLimitExceeded` error) and that the bank's `rate_limiter.hourly.cur_window_outflow` remains unchanged (0), while the user's token balance increased by 1000 and no `RateLimitFlowEvent` was emitted.
5. Contrast with a control test: same withdraw called directly outside a flashloan (`lending_account_withdraw` without `ACCOUNT_IN_FLASHLOAN` set) for the same amount, asserting it correctly fails with the rate-limit error — demonstrating that wrapping in a flashloan is what causes the bypass.

/// Checks if rate limiting should be skipped based on account flags.
/// Returns true for flashloan, liquidation, and deleverage operations.
pub fn should_skip_rate_limit(account_flags: u64) -> bool {
    (account_flags & ACCOUNT_IN_FLASHLOAN) != 0
        || (account_flags & ACCOUNT_IN_RECEIVERSHIP) != 0
        || (account_flags & ACCOUNT_IN_DELEVERAGE) != 0
}
