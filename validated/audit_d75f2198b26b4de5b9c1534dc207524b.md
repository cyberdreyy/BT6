## Analysis

I found a concrete, verifiable analog. The bug class from the Jenkins CSRF report — *an endpoint accepts an unvalidated identifier and lets it silently clobber/misattribute stored state* — maps to a schema defect in `stacks-signer/src/signerdb.rs`: the `block_rejection_signer_addrs` table is keyed **only** by `signer_addr`, not by `(signer_signature_hash, signer_addr)`, even though every read/write in `add_block_rejection_signer_addr` treats it as if it were scoped per-block. [1](#0-0) 

`add_block_rejection_signer_addr` first checks for an existing row filtered by *both* `signer_signature_hash` and `signer_addr`; if none is found it falls to a plain `INSERT` (not `INSERT OR REPLACE`): [2](#0-1) 

Since the real primary key is `signer_addr` alone, the very first time a given signer address's rejection is recorded for *any* block, that row permanently occupies the only slot that address can ever have in the table. Any later rejection by that same address for a *different* block hash fails the "existing row" lookup (which is scoped by hash+addr and finds nothing), falls into the `None` branch, and issues a plain `INSERT` that violates the `PRIMARY KEY(signer_addr)` uniqueness constraint — returning an `Err`, which `store_and_process_block_rejection` merely logs as a warning and returns from, discarding the vote: [3](#0-2) 

### Title
Rejection weight is silently and permanently lost after a signer's first rejection due to a missing composite primary key - (File: `stacks-signer/src/signerdb.rs`)

### Summary
`block_rejection_signer_addrs` is created with `PRIMARY KEY (signer_addr)` instead of `PRIMARY KEY (signer_signature_hash, signer_addr)`. This silently breaks per-signer, per-block rejection bookkeeping: once a signer address has ever rejected one block, its next rejection of any *different* block fails to persist, and its weight is never counted toward that new block's rejection tally.

### Finding Description
`add_block_rejection_signer_addr(block_sighash, addr, reject_reason)` is the only write path into `block_rejection_signer_addrs`, called from `store_and_process_block_rejection` for both the signer's own rejections and observed rejections gossiped by peers [4](#0-3) . Its logic assumes the table is uniquely keyed by `(signer_signature_hash, signer_addr)` — it looks up an existing row scoped by both columns to decide between "duplicate / same reason" (no-op), "different reason for the same block" (`UPDATE`), or "new row" (`INSERT`) [2](#0-1) .

But the table's actual schema declares `PRIMARY KEY (signer_addr)` only [1](#0-0) . Consequently:
1. Signer address `X` rejects block `A` → the two-column lookup finds nothing → plain `INSERT` succeeds, occupying the only row `X` can ever have.
2. Signer address `X` later rejects a different block `B` → the two-column lookup (scoped to `B`) again finds nothing, since the existing row belongs to `A` → the code again takes the "insert new row" branch → the `INSERT` collides with the `PRIMARY KEY(signer_addr)` constraint on the pre-existing row for `A` and errors out.
3. `add_block_rejection_signer_addr` returns `Err`; `store_and_process_block_rejection` only logs a warning and returns, discarding `X`'s vote for `B` entirely — no retry, no fallback path.

From that point forward, `X`'s rejection weight can never again be counted by `get_block_rejection_signer_addrs`/`compute_signature_signing_weight`, for any subsequent distinct block, for the lifetime of that signer's database (the table is never purged in the shown code).

### Impact Explanation
This corrupts the equality the rejection-weight aggregation is supposed to preserve: "the DB-tallied reject weight equals the verified set of rejecting signers for this block." Because rejections are naturally triggered by ordinary miner behavior — stale/duplicate re-proposals (`ProposalTooOld`, `DuplicateBlockFound`), invalid parent/tenure proposals, or reorg attempts (`ReorgNotAllowed`) — a single miner can, with no collusion and no signer key, deliberately or incidentally cause every signer in the set to reject two or more *distinct* blocks over the life of a reward cycle. After each signer's first rejection, the rejection-weight table becomes permanently unable to accumulate weight against later distinct blocks that legitimately deserve rejection.

This directly undermines the reject-threshold consensus computed in `store_and_process_block_rejection` (`total_reject_weight.saturating_add(min_weight) > total_weight`) [5](#0-4) , meaning the network-wide rejection weight can never accumulate correctly even when a genuine 30%+ blocking minority is rejecting a bad or reorg-violating block. It also prevents the follow-on invalidation of a miner attempting an unauthorized reorg (pre-global-state versions), since that check is derived from the same corrupted `rejection_addrs` set [6](#0-5) . This is a liveness/safety-adjacent wedge in the rejection consensus mechanism, triggerable purely by miner-driven traffic, matching the "aggregated-weight vs verified-accepts equality" break called out in the rules.

### Likelihood Explanation
High. No majority of signers, no signer private key, and no auth token are needed. A single one-slot miner simply needs to cause any signer to reject two different blocks over time — an ordinary occurrence given `block_proposal_max_age_secs` rejections, duplicate-block rejections on re-proposal, and reorg-not-allowed rejections that are all part of normal tenure churn.

### Recommendation
Change `CREATE_BLOCK_REJECTION_SIGNER_ADDRS_TABLE` to declare `PRIMARY KEY (signer_signature_hash, signer_addr)` (with a migration to correct any already-deployed single-column-key databases), so each signer's rejection is properly scoped per block, matching the intent of the query/update logic in `add_block_rejection_signer_addr`.

### Proof of Concept
1. Fresh `SignerDb`; signer address `X` weight `w`.
2. Miner sends an old/duplicate block proposal `A`; the local signer rejects it: `add_block_rejection_signer_addr(hash_A, X, reason1)` → succeeds, row `(hash_A, X, reason1)` persisted.
3. Miner sends a different, distinct block `B` later in the same reward cycle that also merits rejection (e.g. `ReorgNotAllowed`, `DuplicateBlockFound`): `add_block_rejection_signer_addr(hash_B, X, reason2)` is invoked.
   - Lookup `WHERE signer_signature_hash = hash_B AND signer_addr = X` → no rows found.
   - Falls to `INSERT INTO block_rejection_signer_addrs (...) VALUES (hash_B, X, reason2)` → fails with a `PRIMARY KEY` uniqueness violation on `signer_addr = X` (row for `hash_A` still exists).
   - `store_and_process_block_rejection` logs `"Failed to save block rejection signature"` and returns; `X`'s rejection of `B` is dropped and permanently unrecoverable — this reproduces with the existing unit-test helpers `add_block_rejection_signer_addr`/`get_block_rejection_signer_addrs` in `stacks-signer/src/signerdb.rs` simply by using two different `block_sighash` values for the same address instead of the same one used in the existing tests (`add_and_get_block_rejections`, `duplicate_block_rejections`) [7](#0-6) .

CREATE TABLE IF NOT EXISTS block_rejection_signer_addrs (
    -- The block sighash commits to all of the stacks and burnchain state as of its parent,

    -- the sighash is sufficient to uniquely identify the block across all burnchain, PoX,
    -- and stacks forks.
    signer_signature_hash TEXT NOT NULL,
    -- the signer address that rejected the block
    signer_addr TEXT NOT NULL,
