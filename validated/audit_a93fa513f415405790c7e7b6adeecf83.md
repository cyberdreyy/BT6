## Analog Found

The reported pattern — a broken/reverting external hook gating the burn path with no emergency bypass — has a direct analog in the Aera v3 `MultiDepositorVault`/`ProvisionerV2` unit-burn flow.

### Title
Broken `beforeTransferHook` permanently blocks all unit burns/redemptions with no emergency exit - (File: `v3/src/core/MultiDepositorVault.sol`)

### Summary
`MultiDepositorVault._update` unconditionally calls the external `beforeTransferHook.beforeTransfer(from, to, provisioner)` on every mint/burn/transfer whenever a hook is set, including inside `exit()`'s `_burn()` call used by every user-facing redemption path in `ProvisionerV2`. There is no try/catch, timeout, or user-triggered bypass — if the hook contract reverts (due to a bug, or any faulty logic that always returns false/reverts), `_burn` reverts, and every synchronous and asynchronous redeem/withdraw path in `ProvisionerV2` becomes permanently unusable, freezing all depositor funds in the vault.

### Finding Description
`MultiDepositorVault._update` is inherited from OZ `ERC20._update` and is invoked internally by `_mint`/`_burn`/`transfer`: [1](#0-0) 

`exit()`, called by `onlyProvisioner`, burns the caller's units before releasing tokens: [2](#0-1) 

Every ordinary-user exit path in `ProvisionerV2` funnels through this `exit()`/`_burn` call, including the synchronous `redeem`/`withdraw` functions: [3](#0-2) [4](#0-3) 

as well as async solve/cancel paths (`_solveRedeemVaultAutoPrice`, `_solveRedeemVaultFixedPrice`, `solveRequestsDirect`, `cancelRequest`'s fee burn) that all call `IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).exit(...)`.

The hook interface is declared `view`, so it cannot maliciously drain funds itself, but a broken hook implementation (bug causing an unconditional revert for some or all `(from, to)` pairs) still causes every downstream `_burn` to revert. There is no fallback: `setBeforeTransferHook` can only be changed by a `requiresAuth`-gated call, and no user-callable emergency-exit function exists that skips the hook check.

### Impact Explanation
If the deployed `beforeTransferHook` implementation has a defect that causes it to revert (e.g., an edge case in `isVaultUnitsTransferable`/allow-list logic), then `_burn` reverts for all users, and:
- `ProvisionerV2.redeem` / `withdraw` (sync exits) revert.
- All async redeem solving (`solveRequestsVault`, `solveRequestsDirect`) for redeem-type requests revert.
- `cancelRequest`'s redeem-cancellation-fee burn reverts, blocking self-cancellation of redeem requests too.

This freezes all depositor principal and unclaimed yield in the vault with no user-triggerable recovery path, matching a live "temporary/permanent freezing of user funds" impact.

### Likelihood Explanation
Requires only that a vault deployment configures a non-zero `beforeTransferHook` (an expected, supported configuration per `MultiDepositorVaultFactory`/`IBeforeTransferHook`) and that the hook contract contains a bug causing it to revert for legitimate `(from, to)` pairs. No malicious actor, privileged role, or oracle/token fault is required — it's a pure code-defect-in-dependency scenario, exactly mirroring the reported pattern (broken hook blocking `burn`).

### Recommendation
Add a user-triggerable emergency exit path in `MultiDepositorVault`/`ProvisionerV2` that allows burning units and releasing owed tokens even if `beforeTransferHook.beforeTransfer` reverts — e.g., wrap the hook call in `try/catch` and allow burns (`to == address(0)`) to proceed regardless of hook outcome, or provide an authorized "hook bypass" flag that any user can invoke after a fixed grace period if the hook has reverted repeatedly.

### Proof of Concept
1. Deploy `MultiDepositorVault` via `MultiDepositorVaultFactory` with a mock `IBeforeTransferHook` whose `beforeTransfer` always reverts.
2. As a user, call `ProvisionerV2.enter`-equivalent deposit path successfully (hook still allows mint since it's the same call — or set hook to only revert on burn/`to==address(0)` conditions to isolate exit-blocking).
3. Call `ProvisionerV2.redeem(token, unitsIn, minTokensOut, receiver)`.
4. Assert the call reverts due to the hook's `beforeTransfer` revert propagating from `MultiDepositorVault._update` → `_burn` → `exit`.
5. Confirm no alternative public function exists to retrieve the underlying tokens without going through `exit`/`_burn`. [5](#0-4)

        IBeforeTransferHook hook = beforeTransferHook;
        if (address(hook) != address(0)) {
            // Requirements: perform before transfer checks
            hook.beforeTransfer(from, to, provisioner);
        }

        // Requirements: check that the from address does not have its units locked

            Aera__UnitsLocked()
        );

        // Effects: transfer the tokens
