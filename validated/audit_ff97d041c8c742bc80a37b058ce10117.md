### Title
`delete_member` fails to purge stale confirmations left by the removed member on requests they did not originate, allowing execution below `num_confirmations` live members - (`multisig2/src/lib.rs`)

### Summary
`delete_member` only deletes requests whose `MultiSigRequestWithSigner.member` equals the removed member (i.e., requests that member *originated*), but never scans `self.confirmations: LookupMap<RequestId, HashSet<String>>` to strip that member's `to_string()` entry from *other* surviving requests they merely confirmed. `confirm()` later counts these stale entries toward `num_confirmations`, so a request can execute with fewer distinct **current** members confirming than `num_confirmations` requires.

### Finding Description
The binding that must hold is: `distinct_current_members_who_confirmed(request_id) == confirmations.get(request_id).len()` at the moment `confirm()` decides `confirmations.len() + 1 >= num_confirmations` and calls `execute_request`. This binding is broken because membership is not re-validated against stored confirmation strings.

Code path:
1. Member `A` calls `add_request` for a `Transfer`, creating `requests[rid]` with `member == A` and `confirmations[rid] = {}` [1](#0-0) .
2. Member `B` (not the originator) calls `confirm(rid)`. Since `confirmations.len()+1 (=1) < num_confirmations`, `B.to_string()` is inserted into the set instead of executing [2](#0-1) .
3. Remaining members submit and approve a `DeleteMember { member: B }` request. `delete_member` filters `self.requests` by `r.member == member` — i.e., only requests **originated** by `B` — and removes those plus their confirmations; it never inspects other requests' `confirmations` sets for `B.to_string()` entries [3](#0-2) . The Transfer request from step 1 is untouched, and `confirmations[rid]` still contains `B`'s string even though `B` is removed from `self.members`.
4. Two more current members (e.g., `C`, then `D`) call `confirm(rid)`. The check `confirmations.len() as u32 + 1 >= self.num_confirmations` counts `B`'s stale entry, so with `num_confirmations = 3` the set reaches size 3 (`{B, C}` plus `D`'s implicit +1) and `execute_request` fires the `Transfer` [4](#0-3) .

At execution time, only `A` (originator, uncounted separately but not a confirmer) is irrelevant; the actual confirming set is `{B, C, D}` where `B` is no longer in `self.members`. Distinct **current** confirming members = `{C, D}` = 2, which is below `num_confirmations = 3`, yet the NEAR transfer executes.

None of the existing guards prevent this: `assert_valid_request` only checks the *calling* member is currently valid, not the members whose confirmations are already stored [5](#0-4) ; `confirm`'s duplicate check only prevents the same member confirming twice, it does not revalidate existing entries [6](#0-5) .

### Impact Explanation
NEAR is transferred out of the multisig contract account with fewer live/current confirming members than `num_confirmations` mandates — this directly matches the Critical category "a multisig request executed below `num_confirmations` live members." The blast radius covers any `multisig2` deployment where a member is removed after having confirmed (but not originated) a still-pending request; it is repeatable for every pending request the removed member had confirmed, and across any subsequent member removal event.

### Likelihood Explanation
The precondition is realistic and requires no special privilege beyond the normal member-removal governance flow already supported by the contract: a member confirms a request they didn't create, then gets removed via a standard `DeleteMember` approval (which happens for many legitimate reasons — key rotation, off-boarding, compromise response). No attacker-controlled deposit or extra cost is needed beyond normal multisig operation; it can happen even without malicious intent, purely from omitted cleanup logic, making it highly likely to occur in practice on any active multisig with turnover in membership and outstanding requests.

### Recommendation
In `delete_member`, iterate all entries in `self.confirmations` (not just requests originated by the member) and remove the member's `to_string()` entry from each `HashSet`; alternatively, have `confirm()`/`execute_request` recompute the confirmation count by filtering the stored set against `self.members.contains(...)` at execution time before comparing against `num_confirmations`.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
