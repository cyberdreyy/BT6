### Title
APR0 withdraw requests permanently DoS `stopEpoch` once the manager raises APR mid-epoch - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.prepareStopEpochWithApr0()` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. `apr0TotalPrincipal` is only incremented when a user calls `requestWithdraw` while `unscaledApr == 0`, and it is only ever cleared inside that same function — a function that now unconditionally reverts. An unprivileged lender can therefore poison the stop-epoch path, and once the (honest) manager/CDO later sets a non-zero APR — a routine, legitimate action — every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts, freezing the vault.

### Finding Description
In `requestWithdraw`, when `unscaledApr == 0` and the pool is not closed, `_requestWithdrawApr0(_amount, _user)` runs, incrementing the global bucket `apr0TotalPrincipal` (`contracts/strategies/idle/IdleCreditVault.sol:567-577`).

At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which contains:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```
(`contracts/strategies/idle/IdleCreditVault.sol:499-508`)

The only place `apr0TotalPrincipal` is decremented outside this function is `apr0TotalPrincipal = 0` at line 540 — unreachable once the revert condition holds — plus the default-claim path in `_clearWithdrawClaimForEpoch` (lines 822-828) which only runs after a default finalization, i.e. after funds are already lost. `_settleApr0` (lines 545-565) clears per-user `principal` but never reduces `apr0TotalPrincipal`, so user claims cannot heal the global bucket either.

Concretely:

1. Vault is configured with `unscaledApr == 0` (APR0 mode, a supported configuration — `_requestWithdrawApr0` exists specifically for it). An epoch is running.
2. Attacker (any KYC'd lender / tranche holder) calls `requestWithdraw` via `IdleCDOEpochVariant` for even a dust amount. `apr0TotalPrincipal` becomes non-zero and `lastWithdrawRequest[attacker]` is set. The attacker pays only the management fee on a tiny principal.
3. The honest manager (or the CDO at `startEpoch` via `setAprsWithBuffer`) sets a non-zero `unscaledApr`/`lastApr` — a normal operational action.
4. Borrower repays; manager calls `stopEpoch`. `prepareStopEpochWithApr0` reverts `NotAllowed` at line 508 — and reverts on every retry, because nothing in the non-defaulted path can zero `apr0TotalPrincipal` while `unscaledApr != 0`.
5. The only recovery is for the manager to set `unscaledApr` back to 0 via `setAprs`/`setApr`, which also resets the epoch's interest accounting — meaning the freeze is only resolvable by abandoning the intended APR for that epoch.

### Impact Explanation
All underlying held by the CDO and owed by the borrower is frozen at `stopEpoch`: pending withdraw receipts cannot be funded (`collectWithdrawFunds` is only invoked from `stopEpoch`), instant-withdraw funding halts, and active tranche holders cannot enter the withdrawal flow for the stopped epoch. The freeze persists until the manager reverts `unscaledApr` to 0 — i.e. the protocol must sacrifice the epoch's entire interest accrual to unstick the vault, a quantified loss equal to `expectedEpochInterest` for the epoch, on top of the temporary freeze of full TVL.

### Likelihood Explanation
- Attacker cost is minimal: a single dust `requestWithdraw` during an APR0 epoch. The attacker does not even need to keep the position — `apr0TotalPrincipal` is never decremented by settlement or claims in the non-default path.
- Triggering condition (manager raising `unscaledApr` mid-lifecycle or at the next `startEpoch`) is ordinary privileged behavior, not a malicious or negligent act.
- No existing guard helps: the `NotAllowed` check is the bug itself; KYC/`isWalletAllowed` does not prevent a legitimate lender from holding a small position; `epochEndDate == 0` closed-pool handling only skips the APR0 branch on new requests, it does not clear `apr0TotalPrincipal`.

### Recommendation
Instead of reverting, treat a non-zero `unscaledApr` as "APR0 epoch ended": settle `apr0TotalPrincipal` pro-rata or return it to the normal `pendingWithdraws` basis and zero the bucket before continuing. Alternatively, decrement `apr0TotalPrincipal` in `_settleApr0`/per-user settlement and add a privileged recovery function that can close a stale APR0 bucket. At minimum, guard `requestWithdraw`'s APR0 branch against requests that outlive the APR0 configuration rather than bricking `stopEpoch`.

### Proof of Concept
Foundry fork PoC (schematic, against the deployed vault/strategy):

```solidity
// Setup: credit vault in APR0 mode (unscaledApr == 0), epoch running,
// attacker holds AA tranche tokens and passes KYC.
uint256 dust = 1e6; // 1 USDC
cdo.requestWithdraw(dust, attacker); // -> strategy.requestWithdraw -> _requestWithdrawApr0
assertGt(strategy.apr0TotalPrincipal(), 0);

// Honest operations: manager sets a non-zero APR (or next startEpoch scales it).
vm.prank(manager);
strategy.setAprs(10e18, 10e18); // unscaledApr = 10e18

// Borrower repays interest+principal to the CDO.
repayToCDO();

// Every stop attempt now reverts permanently.
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdo.stopEpoch();

vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdo.stopEpochWithDuration(30 days, interestOverride);

// Funds remain frozen until manager reverts unscaledApr to 0,
// forfeiting the epoch's interest.
```
