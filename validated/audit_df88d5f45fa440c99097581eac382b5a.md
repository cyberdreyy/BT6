## Analog Found: Stale Confirmations From Removed Multisig Members Count Toward Quorum

### Title
Multisig executes requests below the confirmation threshold because stale confirmations from removed members are never purged - (File: `multisig2/src/lib.rs`, also present in `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` treats "number of entries in the `confirmations` set" as equivalent to "number of *current* members who approved the request." `delete_member` only purges outstanding requests that were *created* by the removed member; it never scrubs that member's confirmation entries from requests created by other members. A confirmation cast by a member while they were still a member remains valid and counted even after that member is deleted from `self.members`, letting a request execute with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
The intended binding is: `confirmations.len() >= num_confirmations` ⇒ "at least `num_confirmations` distinct **current** members approved this request." The code breaks that equality.

`confirm` only checks that the request/confirmation records exist and that the *caller* is currently a member; it never re-validates the *existing* confirmers still are members: [1](#0-0) 

`delete_member` removes a departing member from `self.members`, deletes their access key, and cleans up only the requests **they created** (`r.member == member`). Confirmations they placed on requests created by *other* members are left untouched in the `confirmations` `LookupMap`: [2](#0-1) 

`assert_valid_request`, called from both `confirm` and `delete_request`, likewise only asserts the *caller* is a current member, not that stored confirmations belong to current members: [3](#0-2) 

The same pattern exists in the original `multisig` contract: `DeleteKey` purges only requests whose `signer_pk` (creator) matches the deleted key, not confirmations that key contributed to requests created by others: [4](#0-3) 

### Impact Explanation
This crosses the exact "confirmations counted versus live members" custody binding: the multisig's security model is "N confirmations from N current trusted members are required before any `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc. executes." Once a member is removed (e.g., because their key/account was compromised or they were offboarded), any confirmation they previously placed on a still-pending request continues to count. A request can therefore reach `num_confirmations` and execute (including NEAR transfers, arbitrary `FunctionCall`s, or contract redeployment) with strictly fewer *currently trusted* confirmations than the threshold mandates — i.e., "a multisig request executed below threshold," moving NEAR to a party not entitled to it under the multisig's stated authorization rule.

### Likelihood Explanation
This requires no attacker privilege beyond having been a legitimate member at some point (e.g., a compromised member key, or a member later deemed untrustworthy and removed). Any pending request that a since-removed member confirmed before removal remains exploitable by simply gathering the remaining confirmations from current members — no code path re-validates confirmer membership at confirm-time or at delete-time. Given that member rotation/removal for compromised keys is the exact scenario the multisig is meant to defend against, this is a realistic and directly reachable state.

### Recommendation
When counting confirmations toward `num_confirmations` (in `confirm`), filter/recompute the confirmation count against `self.members` (or reject/renormalize stale confirmations) rather than trusting the raw stored set size. Additionally, `delete_member`/`DeleteKey` should scrub the departing member's confirmation entries from **all** pending requests, not only requests they created.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. Member `B` calls `add_request` to create request `X` (e.g., `Transfer` of contract funds to an attacker-controlled account) — `X.member = B`, `confirmations[X] = {}`.
3. Member `A` (whose key is about to be flagged as compromised) calls `confirm(X)` — `confirmations[X] = {A}` (count = 1, below threshold).
4. The remaining members detect the compromise and pass a separate request `DeleteMember{A}` with 3 confirmations from `B, C, D`. `delete_member` executes: `self.members = {B, C, D}`; it scans `self.requests` for `r.member == A` (none, since `A` didn't create any request) and does **not** touch `confirmations[X]`, which still contains `"A"`.
5. `C` calls `confirm(X)` → `confirmations[X] = {A, C}` (count = 2).
6. `D` calls `confirm(X)` → `confirmations[X] = {A, C, D}` (count = 3 ≥ `num_confirmations`), triggering `execute_request(X)` — the `Transfer` fires.
7. Only `C` and `D` are current live members who actually approved; `A`'s stale confirmation supplied the third vote after being removed. The transfer executed with 2-of-3 *live* approvals against a nominal 3-of-N policy — a below-threshold, unauthorized fund movement. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
