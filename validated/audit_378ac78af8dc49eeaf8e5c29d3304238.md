### Title
Unauthenticated APR manipulation while `idleCDO` is unset lets any caller inflate lender interest and drain vault value - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`IdleCreditVault.setApr` (and its wrappers `setAprs`/`setAprsWithBuffer`) skip the caller check entirely when `idleCDO == address(0)`. Any EOA that calls it during the window between `initialize()` and `setWhitelistedCDO()` — or on any vault deployed but not yet paired with a CDO — can set `lastApr`/`unscaledApr` to any value up to `maxApr` (default `DEFAULT_MAX_APR = 20e18`, i.e. a ~2000% scaled annual rate). This is the on-chain analog of the ChurchCRM unsanitized-`EN_tyid` bug: an input parameter reaches a security-critical operation without proper authorization/validation.

### Finding Description

In `contracts/strategies/idle/IdleCreditVault.sol:225-235`:

```solidity
function setApr(uint256 _apr) public {
    address _cdo = idleCDO;
    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
        if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
}
```

`setAprs` (`:206-210`) and `setAprsWithBuffer` (`:217-220`) write `unscaledApr` unconditionally and then funnel into `setApr`, so they inherit the same bypass. `unscaledApr` itself is never bounded — only the scaled `lastApr` is capped by `maxApr`, and `maxApr` can even be `0` (cap disabled) if the owner configured it that way.

Once `idleCDO` is set and epochs run, `IdleCDOEpochVariant` reads this APR via `getApr()`/`_getStrategyApr()` to compute `expectedEpochInterest`. The attacker needs only to be a KYC-passing lender (an allowed unprivileged role) holding tranche tokens to profit.

### Impact Explanation

- **Minted-interest mode** (`isInterestMinted == true`): at `stopEpoch`, `expectedEpochInterest` derived from the attacker-set `lastApr` is minted as strategy tokens to the CDO, inflating tranche `virtualPrice` far beyond real backing. The attacker-lender's tranche tokens become redeemable/claimable against the inflated NAV, draining real underlying held by the vault (including `defaultRecoveryReserve`-adjacent funded balances and instant-withdraw liquidity) — direct theft of other lenders' funds.
- **Cash mode**: the inflated `expectedEpochInterest` is demanded from the honest borrower at `stopEpoch`. If the borrower cannot repay, the loss machinery (`previewLossAdjustedWithdrawFunds`, `collectWithdrawFunds`, `lossRecoveryPriceByEpoch`) crystallizes a fake insolvency; if they partially repay, the attacker's tranches absorb recovery value priced on the fake interest basis — insolvency/theft of unclaimed yield either way.

Broken invariant: fair mint/burn — interest accounting is priced from a parameter an unprivileged user controlled. The only guard (`maxApr`) is owner-configured and settable to 0, and the authorization check is explicitly skipped.

### Likelihood Explanation

Requires `idleCDO == address(0)` at call time, which the code comments say happens "only during the setup". Exploitability therefore hinges on deployment ordering: if `initialize()` and `setWhitelistedCDO()` are not executed atomically in one transaction by the factory/deployer, there is a mempool-visible window in which any EOA can front-run `setWhitelistedCDO` with a `setApr` call. Even if the standard factory is atomic, any vault left unpaired (paused rollout, failed follow-up tx, manual deployment) is permanently exposed until paired — the bypass has no expiry. Uncertainty: I could not fully verify `IdleCreditVaultFactory`'s deployment atomicity within the indexed context; if pairing is guaranteed atomic, likelihood drops but the defect remains a latent uninitialized-state exposure.

### Recommendation

- Remove the `idleCDO == address(0)` skip and instead gate `setApr` behind `msg.sender == manager || msg.sender == owner() || msg.sender == idleCDO`, or add an `aprInitialized` flag that only the owner/manager can satisfy once.
- Bound `unscaledApr` in `setAprs`/`setAprsWithBuffer` the same way `lastApr` is bounded by `maxApr`.
- Ensure `initialize` → `setWhitelistedCDO` is atomic (factory-enforced) and add an assertion that `lastApr` is within expected bounds when the CDO is paired.
