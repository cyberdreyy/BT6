### Title
Instant-withdraw path in `requestWithdraw` skips management and performance fees entirely - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external report describes a fee being computed but never applied. The direct analog exists in `IdleCDOEpochVariant.requestWithdraw`: the normal withdrawal path computes and deducts `totalFees` (upfront management fee plus net performance fee) via `_totalWithdrawFees`, but the instant-withdraw branch pays out the raw tranche value with no fee deduction at all. The code comment itself states the rationale for the upfront fee — receipts "leave live NAV at request time" and "can be claimed only after" settlement — which applies identically to instant receipts, yet no fee is charged on that path.

### Finding Description
In `requestWithdraw` at `contracts/IdleCDOEpochVariant.sol:761-769`, when `_isInstantWithdrawEnabled()` and `lastEpochApr > currentApr + instantWithdrawAprDelta`, the function calls `creditVault.requestInstantWithdraw(_underlyings, msg.sender)` using `_underlyings = _trancheToUnderlyings(_amount, _tranche)` — the full tranche value — and returns immediately. The fee-bearing code at lines 772-778 is never reached:

```solidity
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;
pendingWithdrawFees += totalFees;
```

`_totalWithdrawFees` (`IdleCDOEpochVariant.sol:900-906`) computes `_calculateManagementFee(_principal, _withdrawRequestManagementFeeDuration())` plus the performance fee on projected interest. The duration helper (`IdleCDOEpochVariant.sol:925-931`) exists precisely because withdraw receipts sit outside live NAV while waiting to be funded — instant receipts are in exactly the same situation (they wait until `startEpoch` funding plus `instantWithdrawDelay`), yet they bypass the charge entirely. `pendingWithdrawFees` is also not incremented, so the fee revenue never reaches `feeReceiver`/`owner` at `stopEpoch` (`IdleCDOEpochVariant.sol:419`, `442-457`).

### Impact Explanation
Any KYC-passed tranche holder can exit at full tranche value, avoiding the upfront management fee charged on `_withdrawRequestManagementFeeDuration()` (epoch duration plus remaining buffer) and any performance fee on projected interest. With `managementFee = 1%` annualized, a holder of 100,000 underlying requesting an instant withdraw keeps the entire ~1,000+ underlying fee that an identical normal requester would pay. Because `pendingWithdrawFees` is not credited, these fees are permanently lost to the protocol rather than merely deferred — direct loss of protocol revenue, quantifiable per request.

### Likelihood Explanation
The path requires `allowInstantWithdraw`-enabled configuration (`disableInstantWithdraw == false`) and an APR decrease exceeding `instantWithdrawAprDelta` set by the honest manager at `stopEpoch`. Whenever these conditions hold, every rational withdrawer chooses the instant path to evade fees; no privileged action is needed by the attacker. Note the default deployment sets `disableInstantWithdraw = true` (`IdleCDOEpochVariant.sol:83`), so the bug only manifests on deployments that enable instant withdrawals.

### Recommendation
Apply `_totalWithdrawFees(principal, interest)` (or at minimum the upfront management-fee component, since instant receipts earn no projected interest) to the instant-withdraw path before calling `creditVault.requestInstantWithdraw`, and increment `pendingWithdrawFees` accordingly, mirroring the normal path. If the intended policy is fee-free instant exits, update `maxWithdrawable` and documentation to reflect that instant withdrawals bypass fees, and assess the resulting incentive asymmetry.

### Proof of Concept
Foundry fork sketch against `test/foundry/IdleCreditVault.t.sol` harness:

```solidity
// 1. Configure fees and enable instant withdrawals
_setFeeParams(TL_MULTISIG, perfFeeBps, FULL_ALLOC, cdoEpoch.managementFee());
_setManagementFee(1_000); // 1% annualized
vm.prank(manager);
cdoEpoch.setInstantWithdrawParams(3 days, 0, false); // enable instant withdraws

// 2. Deposit AA and run one epoch
uint256 amount = 100_000 * ONE_SCALE;
uint256 trancheAmount = idleCDO.depositAA(amount);
_startEpochAndCheckPrices(0);

// 3. Stop epoch with a lower APR so instant withdrawals trigger
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpoch(initialProvidedApr / 2, 0); // lastEpochApr > newApr + delta

// 4. Request withdraw: takes the instant branch, no fees deducted
uint256 tranchePrice = cdoEpoch.tranchePrice(address(AAtranche));
uint256 expectedFull = trancheAmount * tranchePrice / ONE_TRANCHE_TOKEN;
uint256 requested = cdoEpoch.requestWithdraw(trancheAmount, address(AAtranche));

// 5. Assert the discrepancy vs the fee-bearing path
uint256 expectedMgmtFee = _calcManagementFee(
    expectedFull, 1_000, cdoEpoch.epochDuration());
assertEq(requested, expectedFull);                    // full value paid out
assertEq(cdoEpoch.pendingWithdrawFees(), 0);          // no fee booked
assertLt(expectedFull - requested + expectedMgmtFee, expectedMgmtFee);
```

On a normal (non-instant) request, `requested` would be `principal + interest - totalFees` and `pendingWithdrawFees == expectedMgmtFee + perfFee`; the instant path returns the raw amount and books zero fees.
