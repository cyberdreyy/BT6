## Title
EIP-8130 local sequence counter overflow check operates on the wrong integer width, allowing silent truncation on pack (mirrors bnxt_en's un-masked `bd_cnt` wraparound) - (File: `crates/execution/eip8130/src/apply.rs`)

### Summary
The bnxt_en bug masked a hardware bit-field (`bd_cnt`, 5 bits, max value 32) incorrectly, so the value `32` silently wrapped to `0` in the field instead of being rejected, corrupting the descriptor. Base's EIP-8130 `AccountConfiguration` local-sequence advance has the same defect: the "saturation" check that is supposed to prevent the sequence from exceeding its `uint32` storage width is performed on a value that has already been narrowed to `u32` and then widened back to `u64`, so it can never fail. When the field's true value reaches `2^32`, packing it back into the 32-bit storage slot in `AccountState::to_word` silently truncates it to `0`, exactly like `bd_cnt` truncating `32` to `0`.

### Finding Description
`advance_channel_sequence` computes the new local sequence like this: [1](#0-0) 

```rust
let seq = sequence as u32;
if seq != Eip8130Constants::UNSEQUENCED {
    state.local_sequence =
        u64::from(seq).checked_add(1).ok_or(ApplyError::SequenceSaturated)?;
} else if !state.is_initialized() {
    state.local_sequence = 1;
}
```

`seq` is first truncated to `u32`, then widened back to `u64` before `checked_add(1)` is evaluated. Since `seq` can never exceed `u32::MAX`, `u64::from(seq) + 1` can never overflow a `u64`, so `checked_add` can never return `None` and `ApplyError::SequenceSaturated` is dead code — the intended saturation guard never fires.

`state.local_sequence` is declared and stored as `u64` in memory but its *storage* representation is a `uint32` field packed into the account's single storage word: [2](#0-1) 

The pack function explicitly documents that "`local_sequence`/`local_epoch` must fit in `uint32` ... higher bytes are dropped" and only guards this with a `debug_assert!`, which is compiled out in release builds:

```rust
debug_assert!(
    self.local_sequence >> 32 == 0,
    "local_sequence exceeds uint32 storage width"
);
...
b[20..24].copy_from_slice(&self.local_sequence.to_be_bytes()[4..]); // uint32: low 4 bytes
```

Because the saturation check in `advance_channel_sequence` never fires, an account whose Local channel sequence is advanced enough times to reach exactly `2^32` will have `state.local_sequence == 4294967296`. When this value is packed via `to_word()`, the low-4-byte slice silently drops the high bit, producing a stored `local_sequence` of `0` — identical in effect to `bd_cnt`'s masking bug, where the boundary value (`32` for a 5-bit field, `2^32` for this 32-bit field) wraps to `0` instead of being rejected.

### Impact Explanation
`local_sequence` is EIP-8130's replay-protection counter for the account's `Local` authorization channel — it gates every `AuthorizeActor`/`RevokeActor`/config-change batch signed against that channel. If the counter silently wraps to `0`, a previously valid signature authored against `local_sequence == 0` (which was only valid once, at account initialization) becomes accepted again by the nonce-sequence check, because the on-chain state now reads `0` again without the `local_epoch` having been bumped (the only sanctioned mechanism for resetting `local_sequence`, via `IncrementLocalEpoch`, deliberately advances the epoch half of the word to invalidate old signatures — this silent wrap does not). This reintroduces stale authorization material, allowing replay of an old signed account-configuration change (e.g., re-authorizing a previously revoked actor), i.e., an unauthorized operation on the account's authorization state.

### Likelihood Explanation
Reaching the wrap requires driving a single account's Local-channel sequence through `2^32` (~4.29 billion) sequenced applied batches, which is impractical to reach purely through transaction volume under current gas economics. However, the root cause — the saturation guard being checked against the wrong integer width so it can never trigger — is a genuine, deterministic logic defect independent of practicality of reaching the boundary; the safety net that was supposed to convert this from "silent corruption" into an explicit, safely-rejected error (`SequenceSaturated`) is unreachable code today.

### Recommendation
Perform the overflow check against the actual storage width (`u32`) before widening, e.g.:
```rust
let next = seq.checked_add(1).ok_or(ApplyError::SequenceSaturated)?;
state.local_sequence = u64::from(next);
```
so that a sequence at `u32::MAX` returns `ApplyError::SequenceSaturated` instead of allowing `state.local_sequence` to exceed the field's packed width. Additionally, replace the `debug_assert!`s in `AccountState::to_word` with a real, always-enforced check (returning an error) so a value that doesn't fit in its declared storage width can never be silently truncated in a release build, matching the fix pattern used for `bd_cnt` (explicit masking/validation rather than relying on debug-only assertions).

### Proof of Concept
1. Drive a single EIP-8130 account's `Local` channel sequence, via repeated valid sequenced `applySignedAccountChanges`-equivalent batches, from `0` up to `u32::MAX` (`4294967295`).
2. Submit one more valid sequenced batch with `nonce_sequence == u32::MAX`. `advance_channel_sequence` computes `seq = u32::MAX`, then `u64::from(seq).checked_add(1)` succeeds (`= 4294967296`) instead of erroring, setting `state.local_sequence = 4294967296`.
3. Persist the account state: `AccountState::to_word` copies only the low 4 bytes of `local_sequence` into the storage word, storing `0` in place of `4294967296` (the `debug_assert!` guarding this does not run in a release build).
4. A signature originally created for `local_sequence == 0` (e.g., the account's very first authorization batch) is now valid again against the live on-chain state, since the stored counter reads `0`. [3](#0-2) [4](#0-3)
