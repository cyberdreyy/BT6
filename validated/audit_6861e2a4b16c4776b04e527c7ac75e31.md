### Title
DefaultDistributor redemption rate trusts the unverified contract balance, so a dust donation before activation inflates `rate` and lets early claimers steal late claimers' recovery - (File: contracts/DefaultDistributor.sol)

### Summary
`DefaultDistributor.setIsActive(true)` computes the post-default redemption rate as `balanceOf(this) * ONE_TRANCHE / trancheToken.totalSupply()` with no validation that the balance equals the amount the vault actually recovered. `claim(_to)` then pays `trancheBal * rate / ONE_TRANCHE` to any holder. An unprivileged attacker can donate underlying to the distributor and front-run the owner's `setIsActive(true)` call, inflating `rate` so that early claimers (including the attacker) are paid more than their fair share, leaving the contract insolvent for all later claimers.

### Finding Description
After a borrower default, the owner deploys/funds a `DefaultDistributor` per tranche class and calls `setIsActive(true)` to open claims. The rate is derived from the raw token balance at that instant:

```solidity
// contracts/DefaultDistributor.sol
rate = IERC20(token).balanceOf(address(this)) * ONE_TRANCHE / IERC20(trancheToken).totalSupply();
```

`claim` pays out at that rate to `msg.sender` (any tranche holder):

```solidity
tranche.safeTransferFrom(msg.sender, address(this), trancheBal);
IERC20(token).safeTransfer(_to, trancheBal * rate / ONE_TRANCHE);
```

Unlike the main vault (`IdleCDOEpochVariant._skimDonatedAssets` / `_updateAccounting`), which explicitly isolates raw donations before every accounting step, `DefaultDistributor` has no donation defense at all. It performs no validation that `balanceOf(this)` matches an expected funded amount — the direct analog of skipping host-key validation: the "peer" (the funding source) is implicitly trusted, and unauthenticated tokens injected by a third party are indistinguishable from the legitimate recovery funding.

Attack sequence (phase: `defaulted`, post-`finalizeDefault`/`_transferFundedClaim` funding):

1. Owner funds the distributor with `R` underlyings for a tranche supply `S` (fair rate `R/S`).
2. Attacker (any tranche holder or EOA) transfers `D` dust underlying directly to the distributor and front-runs `setIsActive(true)`.
3. `rate = (R + D)/S` is locked in.
4. Attacker calls `claim(attacker)` first: receives `bal * (R+D)/S > bal * R/S`, overpaid by `D * bal/S` per token — paid out of other holders' recovery.
5. With large `D` relative to `R` (e.g. `D = R`), the first ~half of claimants drain the contract; every subsequent `claim` reverts on `safeTransfer` underflow — permanent freezing of the remaining claimants' recovery funds.

The invariant broken is fair redemption: `sum(claims) <= funded amount` is never enforced. No guard stops this — `claim` only checks `isActive`, and `setIsActive` has no `expectedAmount`/funding-hash check. The attacker needs only to be a tranche-token holder (explicitly in scope) and to sequence around an honest owner call (allowed).

### Impact Explanation
Direct theft of default-recovery funds and permanent freezing of unclaimed recovery. With `D >= R`, roughly half the tranche supply can never claim; the attacker and early claimers extract up to `D` more than their entitlement. Because the distributor is a fixed-pool contract, the shortfall is unrecoverable — late claimants' claims revert forever (the contract holds less than `rate * remaining supply`).

### Likelihood Explanation
Activation requires an honest owner transaction (`setIsActive(true)`), which is public in the mempool; front-running it with a donation is trivial. The attacker can combine the donation and their own `claim` in the same bundle (`transfer` → `claim`), guaranteeing first claim. The only mitigations are operational (owner funding and activating atomically, or funding via the same tx), which the code does not enforce — the constructor takes a token address and the contract explicitly expects funds to arrive "before the first claim" but never validates that they are the only funds present.

### Recommendation
- Pass the expected funded amount to `setIsActive` (or to the constructor) and `require` exact equality: `rate = expectedAmount * ONE_TRANCHE / totalSupply; require(balanceOf(this) == expectedAmount)`.
- Alternatively, fund the distributor and activate it atomically in the same transaction, and add a `sweep`/skim step that removes any tokens beyond the recorded principal before computing `rate`.

### Proof of Concept
```solidity
// Foundry test; distributor funded for defaulted AA tranche
function testDefaultDistributorDonationInflatesRate() public {
    uint256 supply = AAtranche.totalSupply();          // e.g. 10_000e18
    uint256 recovery = 5_000 * ONE_SCALE;              // fair rate = 0.5

    // owner funds distributor
    deal(underlying, address(distributor), recovery);

    // attacker (tranche holder) donates D = recovery and front-runs activation
    deal(underlying, attacker, recovery);
    vm.prank(attacker);
    IERC20(underlying).transfer(address(distributor), recovery);

    vm.prank(owner);
    distributor.setIsActive(true);                     // rate = (R+D)/S = 1.0 instead of 0.5

    // attacker holds 20% of supply -> receives 2x fair share
    uint256 attackerTranche = supply / 5;
    uint256 balBefore = IERC20(underlying).balanceOf(attacker);
    vm.prank(attacker);
    distributor.claim(attacker);
    uint256 got = IERC20(underlying).balanceOf(attacker) - balBefore;
    assertEq(got, attackerTranche * 2 * recovery / supply); // 2000 vs fair 1000

    // once half the supply has claimed, the pool is empty:
    // remaining claimants' safeTransfer reverts -> permanent freeze of their recovery
}
```

Expected outcome: `rate` is doubled by the donation, the attacker is overpaid, and the distributor goes insolvent before all holders claim — reproducible on a mainnet fork with any ERC-20 underlying.
