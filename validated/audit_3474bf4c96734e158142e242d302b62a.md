### Title
Local state machine capitulating to `NoValidMiner` does not update the parallel `SortitionsView`'s miner-validity gate, allowing the signer to keep treating a demoted miner as valid - (File: `stacks-signer/src/v0/signer_state.rs`)

### Summary
`LocalStateMachine::capitulate_viewpoint` mirrors the `BlastOnboardingBoot.setStaking` bug: it switches the signer's authoritative "current miner" pointer without propagating the same change to the other structure (`SortitionsView.cur_sortition.miner_status`) that gates actual block-signature approval, leaving the two views of "is this miner still valid" out of sync.

### Finding Description
`capitulate_viewpoint` computes a new miner viewpoint (`new_miner`) from the aggregated peer state and, when it differs from the current one, replaces `self` (the broadcast `SignerStateMachine`) with the new viewpoint: [1](#0-0) 

Note the `match new_miner` block at the end: when the new viewpoint is `ActiveMiner`, the code reconciles the independent `sortition_state: &mut Option<SortitionsView>` by demoting `sortition_state.cur_sortition.miner_status` if the pubkeys mismatch. But when the new viewpoint is `NoValidMiner`, the arm is a no-op:
```
StateMachineUpdateMinerState::NoValidMiner => (),
``` [2](#0-1) 

`sortition_state.cur_sortition.miner_status` is the actual gate consulted when a block proposal is validated. `SortitionsView::check_proposal` treats `miner_status == Valid` as the default assumption and only demotes it locally based on its own re-derived timeout check; a signature-gating check later hard-rejects proposals when `miner_status != Valid`: [3](#0-2) [4](#0-3) 

`docs/signer-flows.md` explicitly documents that the broadcast miner state (which `capitulate_viewpoint` mutates) is "the equality key for global agreement" that the rest of the signer network relies on: [5](#0-4) 

Elsewhere in the codebase, the same `sortition_state.cur_sortition.miner_status = InvalidatedBeforeFirstBlock` demotion is performed explicitly on the `ReorgNotAllowed` rejection-threshold path in `v0/signer.rs`, but that code path is only used for `active_signer_protocol_version < Global state activation` (i.e., it is explicitly skipped for signer protocol versions that use the global state machine): [6](#0-5) 

This means for global-state protocol versions, `capitulate_viewpoint`'s `NoValidMiner` arm is one of the few places that is supposed to propagate a miner demotion into `SortitionsView`, and it silently fails to do so — analogous to `setStaking` never re-`approve()`-ing the new pool: the "pointer" (current miner viewpoint) is switched, but the dependent gating state is not updated to match.

### Impact Explanation
This breaks the intended equality between "what the signer broadcasts as its agreed state" (current miner = `NoValidMiner`) and "what the signer's own validation logic will actually accept" (`SortitionsView.cur_sortition.miner_status` still `Valid`). If the network capitulates to `NoValidMiner` for reasons the local `is_timed_out`/reorg-timing re-derivation in `check_proposal` cannot independently reconstruct, the signer's block-proposal gate keeps treating the demoted miner as `Valid` and can validate/sign a proposal from a miner the signer's own broadcast state has already declared invalid — a signer signing off on a state its own consensus-visible viewpoint contradicts. Per the stated impact categories, this falls under "a signer acting on a stale reward set/threshold" / effectively a stale-validity-state class issue (High), with the caveat below about certainty.

### Likelihood Explanation
Triggering `capitulate_viewpoint`'s `NoValidMiner` arm only requires normal gossip of `StateMachineUpdate` messages from other signers indicating no valid miner (e.g., after a miner inactivity timeout is observed network-wide) — it does not require compromising a majority of signers or their keys; it is a codepath exercised as part of the routine capitulation/housekeeping flow described in `docs/signer-flows.md`.

### Recommendation
In the `NoValidMiner` arm of `capitulate_viewpoint`'s `match new_miner` block, mirror the `ActiveMiner` arm's behavior: unconditionally demote `sortition_state.cur_sortition.miner_status` (and, if applicable, `last_sortition.miner_status`) to `InvalidatedBeforeFirstBlock`/`InvalidatedAfterFirstBlock` whenever the local state machine capitulates away from an active miner to `NoValidMiner`, so the gating structure used by `check_proposal` never diverges from the state the signer has already broadcast to the network.

### Proof of Concept
Not independently reproduced with a live scenario in this pass — the finding is derived by static tracing of `capitulate_viewpoint` (`stacks-signer/src/v0/signer_state.rs:956-977`) against the `check_proposal` gating logic (`stacks-signer/src/chainstate/v1.rs:144-163, 276-300`) and the protocol-version gating comment in `stacks-signer/src/v0/signer.rs:2342-2368`. I was not able to inspect the v2/global-state chainstate `check_proposal` equivalent or `SortitionsView` construction/refresh timing in this pass (ran out of tool iterations), so it is **uncertain** whether v2's proposal-check path independently re-derives `miner_status` from scratch on every call (which would make the stale flag transient/benign) or persists it across calls the way v1 does. This should be verified against `stacks-signer/src/chainstate/v2.rs` and the exact call sites that construct/reuse `sortition_state` around `capitulate_viewpoint` before treating this as conclusively exploitable.
