### Title
Decimal Truncation in `bridgeETH`/`bridgeERC20` Permanently Locks User Dust in Vault Without Refund — (`bridge/evm/contracts/SuiBridge.sol`, `bridge/evm/contracts/SuiBridgeV2.sol`)

---

### Summary

`bridgeETH`, `bridgeETHV2`, `bridgeERC20`, and `bridgeERC20V2` transfer the user's full token/ETH amount into the vault, then compute the Sui-side credit via integer division in `convertERC20ToSuiDecimal`. The truncated remainder (`amount % factor`) is permanently locked in the vault with no refund path to the caller — the direct Sui-bridge analog of the RubiconRouter M-04 excess-value-not-returned class.

---

### Finding Description

`BridgeUtils.convertERC20ToSuiDecimal` converts an ERC-20 amount to Sui decimals by integer division:

```solidity
// bridge/evm/contracts/utils/BridgeUtils.sol  lines 141-142
uint256 factor = 10 ** (erc20Decimal - suiDecimal);
amount = amount / factor;
```

For ETH (18 EVM decimals → 8 Sui decimals), `factor = 10^10`. Any ETH amount whose last 10 decimal digits are non-zero produces a truncated `suiAdjustedAmount`; the remainder (`amount % 10^10`, up to ~10 Gwei) is silently discarded.

In `bridgeETH` (and `bridgeETHV2`), the **full** `msg.value` is forwarded to the vault **before** the conversion:

```solidity
// bridge/evm/contracts/SuiBridge.sol  lines 207-221
uint256 amount = msg.value;
(bool success,) = payable(address(vault)).call{value: amount}("");   // full amount locked
...
uint64 suiAdjustedAmount = BridgeUtils.convertERC20ToSuiDecimal(     // truncated
    IERC20Metadata(config.tokenAddressOf(BridgeUtils.ETH)).decimals(),
    config.tokenSuiDecimalOf(BridgeUtils.ETH),
    amount
);
emit TokensDeposited(..., suiAdjustedAmount, ...);                   // only truncated amount credited
```

The same pattern appears in `bridgeERC20` / `bridgeERC20V2`:

```solidity
// bridge/evm/contracts/SuiBridge.sol  lines 162-175
SafeERC20.safeTransferFrom(IERC20(tokenAddress), msg.sender, address(vault), amount); // full amount
...
uint64 suiAdjustedAmount = BridgeUtils.convertERC20ToSuiDecimal(..., amountTransfered); // truncated
emit TokensDeposited(..., suiAdjustedAmount, ...);
```

The `TokensDeposited` event drives the Sui-side mint. Only `suiAdjustedAmount` is ever credited on Sui; the truncated dust (`amount % factor`) stays in the vault forever with no user-facing recovery mechanism.

The existing test suite explicitly acknowledges this truncation:

```solidity
// bridge/evm/test/SuiBridgeTest.t.sol  lines 439-458
// Now test rounding. For ETH, the last 10 digits are rounded
// 2_000_000_011_000_000_888 is rounded to 2.00000001 eth
bridge.bridgeERC20(BridgeUtils.ETH, 2_000_000_011_000_000_888, ...);
assertEq(IERC20(wETH).balanceOf(address(vault)), 3_000_000_011_000_000_888);
```

The vault receives `2_000_000_011_000_000_888` wei but only `2_000_000_010_000_000_000` wei worth is credited on Sui; `1_000_000_888` wei is permanently locked.

---

### Impact Explanation

Every call to `bridgeETH`/`bridgeERC20` with a non-round amount permanently locks up to `factor − 1` wei (≈ 9.99 Gwei for ETH) in the vault per transaction. There is no on-chain mechanism for the user to recover the truncated dust. The vault accumulates this excess silently across all bridge deposits. This constitutes a **permanent fund lock** for the depositing user — matching the "High or Medium: permanent fund lock" impact class in the allowed gate.

---

### Likelihood Explanation

Any ordinary bridge user who calls `bridgeETH` or `bridgeERC20` with an amount that is not an exact multiple of `10^(erc20Decimal − suiDecimal)` triggers the loss. For ETH (factor = 10^10), virtually any real-world ETH amount expressed in wei will have non-zero low-order digits. The trigger is public, requires no privilege, and is exercised on every non-round deposit.

---

### Recommendation

Before transferring funds to the vault, compute the aligned amount and refund the remainder to `msg.sender`:

```solidity
// bridgeETH example
uint256 factor = 10 ** (erc20Decimal - suiDecimal);
uint256 aligned = (msg.value / factor) * factor;
uint256 dust    = msg.value - aligned;

(bool success,) = payable(address(vault)).call{value: aligned}("");
require(success, "SuiBridge: Failed to transfer ETH to vault");

if (dust > 0) {
    (bool refunded,) = payable(msg.sender).call{value: dust}("");
    require(refunded, "SuiBridge: Failed to refund dust");
}
```

Alternatively, `require(msg.value % factor == 0, "SuiBridge: Amount not aligned to Sui decimals")` to reject non-aligned deposits outright.

---

### Proof of Concept

1. ETH has 18 EVM decimals; Sui represents ETH with 8 decimals → `factor = 10^10`.
2. User calls `bridgeETH{value: 1_000_000_001_000_000_000}(recipient, destChain)` (1.000000001 ETH).
3. Line 210 of `SuiBridge.sol`: vault receives `1_000_000_001_000_000_000` wei in full.
4. `convertERC20ToSuiDecimal(18, 8, 1_000_000_001_000_000_000)` → `1_000_000_001_000_000_000 / 10^10 = 100_000_000` (truncated).
5. `TokensDeposited` emits `suiAdjustedAmount = 100_000_000` → Sui credits exactly 1 ETH.
6. The `1_000_000_000` wei remainder (1 Gwei) is permanently locked in the vault; the user has no way to recover it. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
