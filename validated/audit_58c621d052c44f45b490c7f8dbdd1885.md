### Title
Attached NEAR permanently lost when `MultisigFactory::create` account creation fails - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` takes a user's attached deposit and batches `create_account` + `deploy_contract` + `transfer` + `function_call("new", ...)` into a single `Promise`, then returns that promise directly to the runtime with no `.then()` callback. If the batched receipt fails (e.g., the target account `{name}.{factory}` already exists, `name` contains invalid characters, or the `new` initializer panics because `members`/`num_confirmations` are invalid), the entire receipt — including the `transfer(env::attached_deposit())` action — is rolled back. On NEAR, when a receipt fails, any unused/refunded balance is returned to the **predecessor of that receipt**, which is the factory contract itself (`env::current_account_id()`), not the original caller who attached the deposit. Unlike `lockup-factory` and `staking-pool-factory`, which both implement an `on_*_create` callback that checks `is_promise_success()` and explicitly `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` on failure, `multisig-factory` has no such callback at all.

### Finding Description
Compare the three sibling factories that all follow "attach deposit → create sub-account → deploy code → init":

- `lockup-factory/src/lib.rs` `create()` chains `.then(ext_self::on_lockup_create(..., env::attached_deposit().into(), env::predecessor_account_id(), ...))`, and `on_lockup_create` refunds the caller on failure: [1](#0-0) , [2](#0-1) 
- `staking-pool-factory/src/lib.rs` `create_staking_pool()` does the same, refunding via `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` in `on_staking_pool_create` when `is_promise_success()` is false: [3](#0-2) 
- `multisig-factory/src/lib.rs` `create()` has **no callback**, so no refund logic exists whatsoever: [4](#0-3) 

The binding this breaks: `attached_deposit charged to caller == NEAR ultimately controlled by the caller (either in the new multisig or refunded)`. When creation fails, the left side stays charged but the right side is zero for the caller — the funds land back with the factory contract account instead, effectively frozen/lost from the user's perspective (the factory has no `withdraw` method to recover or redistribute them).

### Impact Explanation
This matches the "funds frozen for at least one epoch" / "an accounting value diverging from reality" High-severity class: the user's attached NEAR is debited but never delivered to them nor to the intended multisig, and the factory contract has no mechanism to return or otherwise account for it. This is a direct analog of the ether-fi `createBid` finding, where a user's ether is not returned when the bid-creation flow fails.

### Likelihood Explanation
Any unprivileged user calling `create` can trigger this by supplying a `name` that collides with an existing account, or a `members`/`num_confirmations` combination that causes `multisig2::new` to panic (e.g. `num_confirmations` greater than `members.len()`, if such validation exists in `multisig2::new`). No special privileges are required — this is reachable by any caller of the public `create` function.

### Recommendation
Add a callback analogous to `on_lockup_create` / `on_staking_pool_create`: split `create` into the account-creation promise chained with `.then(ext_self::on_multisig_create(env::attached_deposit().into(), env::predecessor_account_id(), ...))`, and in that callback check `is_promise_success()`, refunding `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` on failure.

### Proof of Concept
1. Attacker (or any user) calls `create` with `name` set to an account ID that already exists as a sub-account of the factory (or with a `num_confirmations` value the `multisig2::new` initializer will reject), attaching `X` NEAR.
2. The batched promise's `function_call("new", ...)` (or `create_account`) fails, causing the whole receipt to fail.
3. The `transfer(X)` action inside the same failed receipt is rolled back and the balance is returned to the receipt's predecessor — the `multisig-factory` contract account — not to the calling user.
4. `multisig-factory` has no method to return this balance to the original caller; the user's `X` NEAR is now stuck in the factory contract's balance indefinitely.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }

    /// Callback after a staking pool was created.
    /// Returns the promise to whitelist the staking pool contract if the pool creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }
