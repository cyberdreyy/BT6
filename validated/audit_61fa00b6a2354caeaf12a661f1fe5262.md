### Title
Stale `apr0TotalPrincipal` permanently DoSes `stopEpoch` once APR is raised — a dust APR0 withdraw request freezes the whole vault epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0 && unscaledApr != 0`. An unprivileged lender can plant `apr0TotalPrincipal > 0` with a dust `requestWithdraw` while `unscaledApr == 0`. There is no user-level path to decrement `apr0TotalPrincipal` (it is only cleared inside `prepareStopEpochWithApr0` itself, at line 540 — after the revert at line 506), and per-user settlement (`_settleApr0`) only clears `apr0Users[user].principal`, never the global bucket. Once the manager sets a non-zero APR (a normal epoch operation via `setAprs`/`setAprsWithBuffer`), every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts inside the same transaction before `apr0TotalPrincipal` is zeroed — mirroring CVE-2016-4964, where a state variable (`s->state`) traps execution in a path that can never complete. ### Finding Description
The flow:

1. Vault is configured with `unscaledApr == 0` (a supported mode; see `testApr0Withdraw*` tests).
2. Attacker deposits dust via `depositAA`, then calls `requestWithdraw` during the buffer epoch. `requestWithdraw` hits `_requestWithdrawApr0` because `unscaledApr == 0 && !isClosed`, so `apr0TotalPrincipal += _amount` and `apr0Users[attacker].principal = _amount` (IdleCreditVault.sol:285-286, 567-577). The attacker can even withdraw-and-redeposit to keep the bucket alive; a never-claimed `apr0Users` entry keeps `principal` non-zero indefinitely.
3. Epoch runs and ends. Manager (honest) reconfigures APR to non-zero for the next epoch (`setAprs(apr, scaled)` — a routine operation).
4. Manager calls `stopEpoch(0, interest)`. `IdleCDOEpochVariant.stopEpochWithDuration` calls `_strategy.prepareStopEpochWithApr0(_interest)` at IdleCDOEpochVariant.sol:362. Inside, `_principal = apr0TotalPrincipal > 0` passes the fast-path check, then `unscaledApr != 0` triggers `revert NotAllowed()` at line 506 — *before* `apr0TotalPrincipal = 0` at line 540 can execute.
5. Because the revert is inside the CDO's `stopEpoch` call, the whole transaction reverts. `isEpochRunning` stays true, deposits remain paused (`_pause()` at startEpoch), `allowAAWithdrawRequest`/`allowBBWithdrawRequest` remain false, and `epochNumber` never increments. No user can claim (`_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest`), and the attacker cannot clear the bucket either — `apr0TotalPrincipal` has no other decrementation path.

The only recovery is the manager manually restoring `unscaledApr` to 0 so one stopEpoch can clear the bucket. Until recognized, the epoch is frozen with all LP funds locked; if the APR policy legitimately requires a non-zero rate, the vault is permanently wedged in a running epoch with paused deposits and disabled claims. The existing test at `IdleCreditVault.t.sol:3331-3338` demonstrates the revert but treats it as a one-off; it does not cover that the bucket is unreachable/clearable only by reverting APR — i.e., the freeze persists across every retry. ### Impact Explanation
Temporary-to-permanent freezing of all vault funds. With `isEpochRunning` stuck true: deposits are paused, new withdraw requests are disabled, and all outstanding receipts (normal, APR0, instant) cannot be claimed because claims require `epochNumber` to advance past the request epoch. The attacker's cost is a dust deposit plus one withdraw request; the frozen amount is the entire vault TVL plus borrower-due interest. Recovery requires a privileged `setAprs(0, 0)` rollback that may not be operationally possible, and nothing in the code alerts operators that a stale dust bucket is the cause.

### Likelihood Explanation
High in any APR0-configured vault: the trigger is a single unprivileged `requestWithdraw` of arbitrary size, and the activating event (manager setting a non-zero APR) is a routine, honest configuration change — the rules permit sequencing around honest privileged calls. No economic prerequisite, oracle dependence, or privileged collusion is needed. The main mitigation is that recovery is possible if the manager can set APR back to 0, which downgrades permanent loss to a freeze — still in scope per the acceptance criteria.

### Recommendation
- Do not revert on `unscaledApr != 0` in `prepareStopEpochWithApr0`; instead settle the outstanding APR0 bucket at a zero (or stored per-epoch) rate and clear `apr0TotalPrincipal` unconditionally — the bucket already encodes that it accrued under APR0, so forfeiting or honoring its `apr0RateByEpoch` share is deterministic without blocking stopEpoch.
- Alternatively, let `_settleApr0` decrement `apr0TotalPrincipal` so user claims drain the bucket, and provide a manager escape that migrates a stale bucket.
- Add a check at APR-change time (`setApr`/`setAprs`) rejecting a non-zero APR while `apr0TotalPrincipal != 0`, converting the hidden freeze into an explicit guard.

### Proof of Concept
Foundry (fork/local) sketch, matching existing harness helpers in `test/foundry/IdleCreditVault.t.sol`:

```solidity
function testApr0DustBlocksStopEpochAfterAprRaise() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // APR0 mode

    // attacker: dust deposit + withdraw request
    address attacker = makeAddr("attacker");
    deal(defaultUnderlying, attacker, 10);
    vm.startPrank(attacker);
    underlying.approve(address(idleCDO), 10);
    idleCDO.depositAA(10);
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // apr0TotalPrincipal > 0

    // honest manager raises APR for next epoch
    _startEpochAndCheckPrices(1);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(1e18, 1e18);

    // every stopEpoch reverts; epoch is frozen
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, type(uint128).max);
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), type(uint256).max);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning()); // frozen: no claims, no deposits
}
```

The revert comes from `prepareStopEpochWithApr0` line 506 because `apr0TotalPrincipal` is non-zero while `unscaledApr` is now non-zero, and the clearing assignment at line 540 is unreachable.

  function _requestWithdrawApr0(uint256 _amount, address _user) internal {
    // Settle any previous APR0 request first, then start/update current epoch bucket.
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    if (_apr0User.principal == 0) {
      _apr0User.principalEpoch = epochNumber;
    }
    _apr0User.principal += _amount;
    // Epoch-level APR0 principal used only to compute stopEpoch APR0 pro-rata interest.
    apr0TotalPrincipal += _amount;
  }
