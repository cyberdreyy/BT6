### Title
Stale per-epoch instant-withdraw keys are never deleted on claim, inflating `instantWithdrawClaimsByEpoch` and corrupting default recovery accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` deletes the user's aggregate receipt (`instantWithdrawsRequests[_user] = 0`) but never removes the per-epoch keys `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. This is the same bug class as the OBI advisory: a removal path that clears the main map but leaves the key in the tracking structure. The stale epoch key is later re-read by `_defaultPrefundedInstantReserve()` during borrower-default finalization, which treats already-paid instant claims as strategy-held reserve, overstating prefunded recovery backing and leaving the default recovery pot underfunded.

### Finding Description
In `requestInstantWithdraw`, three ledgers are incremented together:

```solidity
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
``` [1](#0-0) 

But `claimInstantWithdrawRequest` only clears the aggregate entry:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [2](#0-1) 

`instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` retain the claimed amount forever. The only path that clears those keys is `_claimDefaultedInstantWithdrawRequest`, which runs only after default finalization — too late, because the stale value is already consumed by finalization itself:

```solidity
uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
if (instantBasis > pendingInstant) {
  prefundedReserve = instantBasis - pendingInstant;
}
``` [3](#0-2) 

`pendingInstantWithdraws` is correctly decremented by `collectInstantWithdrawFunds` (line 401), but `instantWithdrawClaimsByEpoch` is not. After a funded claim inside epoch E, `instantWithdrawClaimsByEpoch[E]` still counts the paid-out amount while `pendingInstantWithdraws` no longer does, so `_defaultPrefundedInstantReserve()` reports a phantom reserve of already-distributed underlyings. This inflated `instantBasis` is also the claim denominator used by `_claimDefaultedInstantWithdrawRequest` (line 844), so the epoch's instant-claim basis is permanently overstated by every claim settled mid-epoch.

### Impact Explanation
When the borrower defaults in an epoch where any instant withdrawal was already funded and claimed, default finalization computes `prefundedReserve` from a basis that includes ghosts — underlyings that were transferred to users and no longer exist in the strategy. The recovery accounting therefore assumes more instant-claim backing than the strategy holds, and `instantWithdrawClaimsByEpoch[defaultEpoch]` remains inflated, so the recovery pot is split across claims that exceed the real liability. Concretely this produces either (a) default-recovery transfers that revert for lack of underlying (`_transferDefaultRecovery` / `_burn` underflow), permanently freezing or truncating legitimate defaulted-epoch claims, or (b) dilution of the recovery price for all default-epoch claimants. The loss equals the sum of all instant withdrawals claimed mid-epoch before the default — directly quantifiable and unbounded by any cap.

### Likelihood Explanation
The trigger requires only normal user behavior: request an instant withdraw during a running epoch, let the honest CDO/manager call `collectInstantWithdrawFunds`, then `claimInstantWithdrawRequest` — all standard, mid-epoch operations per the queue's documented instant-withdraw flow. If the borrower subsequently defaults within the same epoch (`_handleBorrowerDefault` → finalization runs with `defaultRecoveryEpoch == epochNumber`), the stale key is consumed automatically. No malicious privileged role is needed; any instant-withdrawing user creates the stale key, and an honest-manager-driven default activates it. No existing guard (`_onlyIdleCDO`, `defaultRecoveryFinalized` checks, the `pendingInstantWithdraws` floor at line 852) prevents it, because the inconsistency is between the per-epoch ledger and the aggregate, not a permissions violation.

### Recommendation
Mirror the fix applied upstream to `CappedConcurrentHashMap.remove()`: clear the per-epoch tracking keys on the claim path. In `claimInstantWithdrawRequest`, after burning, delete `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount. Note this requires instant receipts to record their request epoch (analogous to `lastWithdrawRequest` for normal requests), since claims may occur in a later epoch than the request; alternatively store the request epoch alongside `instantWithdrawsRequests` and use it to locate the stale key.

### Proof of Concept
Foundry fork sketch (run against a live-fork vault deployment per `test/foundry/IdleCreditVault.t.sol` conventions):

```solidity
function testStaleInstantEpochKeyInflatesDefaultReserve() public {
  // Epoch E running (fixed-APR mode, instant withdrawals enabled)
  address user = makeAddr("user");
  uint256 amount = 100e6;

  // 1. user deposits via CDO, then requests instant withdraw in epoch E
  _depositWithUser(user, amount);
  vm.prank(manager); cdoEpoch.startEpoch();          // epoch E running
  _requestInstantWithdraw(user, amount);             // burns CDO tokens, mints receipt
  // instantWithdrawsRequestsByEpoch[user][E] == amount
  // instantWithdrawClaimsByEpoch[E]     == amount

  // 2. honest CDO collects instant funds; user claims mid-epoch
  vm.warp(block.timestamp + instantDelay + 1);
  vm.prank(address(cdoEpoch));
  // collectInstantWithdrawFunds(amount) pulled underlying into strategy
  strategy.claimInstantWithdrawRequest(user);        // via cdo.claimInstantWithdrawRequest()
  // BUG: instantWithdrawsRequests[user] == 0
  //      but instantWithdrawsRequestsByEpoch[user][E] == amount   (stale key)
  //      and instantWithdrawClaimsByEpoch[E]     == amount        (stale aggregate)
  assertEq(strategy.instantWithdrawsRequestsByEpoch(user, E), amount); // leftover

  // 3. Borrower defaults within the same epoch E (honest borrower/manager flow)
  _defaultBorrower();                                 // defaultRecoveryEpoch = E

  // 4. _defaultPrefundedInstantReserve sees instantBasis=amount, pendingInstant=0
  //    => prefundedReserve = amount of PHANTOM underlying already paid to user
  //    => recovery reserve / instant claim basis overstated by `amount`

  // 5. Second user's defaulted instant claim (or AA/BB recovery) is underfunded:
  //    _transferDefaultRecovery reverts or pays less than defaultRecoveryPrice implies
  address user2 = makeAddr("user2");
  // user2 had a genuine pending instant receipt in epoch E
  vm.expectRevert(); // underflow / insufficient underlying in recovery reserve
  strategy.claimInstantWithdrawRequest(user2);
}
```

Key assertions: `instantWithdrawClaimsByEpoch[E]` remains `amount` after the claim (line 372 never reversed), and `instantBasis - pendingInstant` in `_defaultPrefundedInstantReserve` counts already-paid funds as reserve. The invariant broken is conservation of the recovery pool: `Σ claims ≤ funded reserve` fails by the total of mid-epoch instant claims.
