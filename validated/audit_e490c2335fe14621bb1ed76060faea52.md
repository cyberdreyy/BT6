### Title
`AnchorUpdater` permanently stalls after a `DisputeGameFactory.setImplementation` that changes the proposal-interval pair - (File: `crates/proof/challenge/src/anchor.rs`)

### Summary
This mirrors the reported bug class: a downstream component derives a game/interval lookup from a value that a factory can change out from under it (`DisputeGameFactory.gameImpls`), permanently desynchronizing the component's expectation from the state that was actually committed on-chain when the relevant object was created — exactly like `Quest`'s stale, immutable `RabbitHoleReceipt` reference after `QuestFactory.setRabbitHoleReceiptContract`.

### Finding Description
`AnchorUpdater::next_game` resolves the `(block_interval, intermediate_block_interval)` pair used to compute the deterministic lookup key for the successor dispute game by calling `resolve_intervals`, which reads the **factory's current** `gameImpls(game_type)` implementation address and asks that implementation for its interval pair: [1](#0-0) 

The comment directly above the call in `AnchorUpdater::next_game` documents the exact failure mode: the successor game may already exist, created against an *older* implementation/interval pair, while the factory's `gameImpls` entry has since been swapped by a governance `setImplementation` call. Because the pair changes, `game_lookup_key`/`game_lookup_blocks` compute a different UUID than the one the existing game was actually created with, so the factory lookup never matches: [2](#0-1) 

The `IntervalResolver` used on the proposer side documents the same read-per-call design rationale (to avoid caching a stale pair at startup), but the underlying race between "factory's current implementation" and "the implementation the existing game was actually created against" is inherent to reading `gameImpls` fresh each time rather than deriving the pair from the game that already exists: [3](#0-2) 

Once the lookup misses, `next_game` returns `None`, `poll` simply returns without setting `cached_next_game`, and the miss is retried every poll — but always against the same mismatched key, since nothing rescans the factory from the anchor index or falls back to enumerating actual games: [4](#0-3) 

The code explicitly states this state "which a restart no longer clears" — i.e., it is not a transient condition, it is a durable stall.

### Impact Explanation
`AnchorUpdater` is responsible for advancing the `AnchorStateRegistry`'s anchor root, which gates which dispute games are considered "respected"/finalized for downstream proof and withdrawal logic. If the anchor permanently stalls because it can no longer locate the successor game after a `setImplementation` interval-pair change, the anchor state stops advancing indefinitely. This is a node/process-level halt of an on-chain-consequential control loop (not a peer/network DoS or purely cosmetic bug) — comparable in impact class to the report's "rewards permanently unclaimable without expensive manual admin intervention": here, anchor progression (and everything downstream that depends on it advancing) is permanently stuck without a code fix, and a restart does not clear it since the mismatch is deterministic given on-chain state.

### Likelihood Explanation
This requires a governance action (`DisputeGameFactory.setImplementation` for the tracked `game_type`) that changes the `BLOCK_INTERVAL`/`INTERMEDIATE_BLOCK_INTERVAL` pair, occurring after a successor game has already been created under the old implementation but before the anchor has advanced past it. This is a realistic and foreseeable admin/upgrade operation (the codebase already anticipates and names this exact race in its own comments), rather than a purely theoretical or attacker-controlled path — the "Known limitation" comment indicates the maintainers are aware it is reachable but have not implemented the described fallback.

### Recommendation
Implement the fallback the code comment itself proposes: when the keyed lookup misses, scan the factory forward from the anchor's index (via `gameAtIndex`/`gameCount`) to find the next game of the tracked `game_type` instead of relying solely on a deterministically-keyed lookup built from the factory's *current* implementation. Alternatively, derive the interval pair from the actual on-chain game once it is known to exist (mirroring `read_intervals_for_starting_block` called against a game's own proxy, as already done in `basectl`'s `game_details`) rather than only from `factory_client.game_impls`.

### Proof of Concept
1. `DisputeGameFactory` has `game_impls(game_type) = ImplA`, with `ImplA.intervalsForStartingBlock` yielding `(B1, I1)`.
2. A dispute game `G` is created at anchor block `X`, computing its UUID/lookup key using `(B1, I1)`.
3. Governance calls `setImplementation(game_type, ImplB)`, where `ImplB.intervalsForStartingBlock(X)` yields a different pair `(B2, I2)`.
4. `AnchorUpdater::next_game` calls `resolve_intervals`, which now reads `ImplB` via the factory's current `gameImpls`, producing `(B2, I2)`.
5. `game_lookup_key`/`game_lookup_blocks` built from `(B2, I2)` produce a different `extra_data`/UUID than the one `G` was actually created with, so `self.factory_client.games(...)` (inside the lookup path) never returns `G`.
6. `next_game` returns `None` every poll cycle indefinitely, and per the code's own comment, a process restart does not clear the condition, since `resolve_intervals` deterministically re-derives the same mismatched `(B2, I2)` pair. [5](#0-4)

pub async fn resolve_intervals(
    factory_client: &dyn DisputeGameFactoryClient,
    verifier_client: &dyn AggregateVerifierClient,
    game_type: u32,
    starting_block: u64,
) -> Result<(u64, u64), ContractError> {
    let impl_address = factory_client.game_impls(game_type).await?;
    if impl_address.is_zero() {
        return Err(ContractError::validation(format!(
            "no AggregateVerifier implementation registered for game type {game_type}"
        )));
    }

    verifier_client.read_intervals_for_starting_block(impl_address, starting_block).await
}

    async fn next_game(
        &self,
        verifier_client: &dyn AggregateVerifierClient,
        anchor_root: AnchorRoot,
        anchor_game: Address,
    ) -> Option<Address> {
        // Resolved from the anchor block, which is where the next game's range starts:
        // the verifier switches to a shorter cadence at the Denim activation block, so a
        // pair cached at startup silently stops matching any game past the boundary.
        //
        // Known limitation: this reads the factory's *current* implementation, but the
        // successor game may already exist and have been created with an older pair. Across a
        // `setImplementation` that changes the pair the keyed lookup never matches and the
        // anchor stalls at "next anchor game not found", which a restart no longer clears.
        // Denim itself does not trigger it (the pair is a function of the starting block,
        // not of which implementation is current). Fix by scanning the factory from the
        // anchor index when the keyed lookup misses, if it ever bites.
        let (block_interval, intermediate_block_interval) = match resolve_intervals(
            self.factory_client.as_ref(),
            verifier_client,
            self.game_type,
            anchor_root.l2_block_number,
        )
        .await
        {
            Ok(intervals) => intervals,
            Err(e) => {
                warn!(error = %e, "failed to resolve anchor update intervals");
                return None;
            }
        };

        let blocks = match game_lookup_blocks(
            anchor_root.l2_block_number,
            block_interval,
            intermediate_block_interval,
        ) {
            Ok(blocks) => blocks,
            Err(e) => {
                warn!(error = %e, "invalid anchor update lookup blocks");
                return None;
            }
        };

/// Resolves [`Intervals`] from the onchain `AggregateVerifier`.
///
/// Both the implementation address and the interval pair are read per lookup:
/// the factory's `gameImpls` entry can be swapped by an upgrade, and the pair
/// changes at the Denim activation block. Caching either one at startup makes
/// the proposer stop finding — and stop creating — games on the far side of a
/// boundary it never observes.
pub struct IntervalResolver {
    verifier_client: Arc<dyn AggregateVerifierClient>,
    factory_client: Arc<dyn DisputeGameFactoryClient>,
    game_type: u32,
}
