### Title
Multisig confirmations from removed members remain counted toward execution threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`confirm()` executes a pending request once `confirmations.len() + 1 >= num_confirmations`, but `delete_member` / `DeleteKey` only purges requests *created* by the removed member — it never scrubs that member's confirmation entries from other members' pending requests. A confirmation cast by a member who is later removed remains valid and counted forever, letting a request execute with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
The threshold check in `confirm()` only compares the size of the stored `HashSet<String>` of confirmations against `num_confirmations`: [1](#0-0) 

Membership removal is handled by `delete_member`, which removes the member from the `members` set and deletes only the *requests this member created*; it does not touch the `confirmations` map for requests created by other members that this member may have already confirmed: [2](#0-1) 

Because `confirm()` never re-validates that each entry in the stored confirmation set still corresponds to a current member of `self.members`, a stale confirmation string (e.g. `member.to_string()` for an account/key that has since been deleted) keeps counting toward the K-of-N threshold. The custody binding that should hold — *confirmations counted == confirmations from currently-live members* — is broken: `confirmations.len()` can include confirmations from accounts/keys no longer in `self.members`.

The same pattern exists in the v1 contract, where `DeleteKey` purges only requests signed by that key, not confirmations recorded by that key on other pending requests: [3](#0-2) [4](#0-3) 

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." If any pending request retains confirmations from members who are later removed (e.g., in normal member-rotation/offboarding flows, or as a deliberate attack sequence), that request can later be pushed to execution by fewer live, currently-authorized members than `num_confirmations` mandates — including transfers, `AddKey`/`AddMember`, `DeleteMember`, or arbitrary `FunctionCall` actions on the multisig account. This breaks the fundamental K-of-N security guarantee the contract is designed to enforce.

### Likelihood Explanation
No special privilege beyond being (at some point) a legitimate multisig member is required, and no unusual conditions are needed beyond the ordinary lifecycle event of member rotation/removal, which is an expected and routine multisig operation. Any pending, not-yet-fully-confirmed request that received a confirmation from a member prior to that member's removal is silently left with a "phantom" confirmation that inflates the effective approval count.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over all `confirmations` entries (not just requests created by that member) and remove the departing member's/key's confirmation string from every stored `HashSet`. Alternatively, at the moment of counting, filter `confirmations` to only members present in `self.members` before comparing against `num_confirmations` in `confirm()`.

### Proof of Concept
1. Multisig initialized with members `{A, B, C, D, E}`, `num_confirmations = 3`.
2. `A.add_request_and_confirm(R)` — creates request `R` (e.g. `Transfer` to attacker) with 1 confirmation (`A`).
3. `B.confirm(R)` — `R` now has 2 confirmations (`A`, `B`), still short of 3, so it stays pending.
4. Members `A`, `C`, `D` confirm a separate `DeleteMember { member: B }` request (through its own K-of-3 flow) and it executes: `B` is removed from `self.members`, per `delete_member` at [2](#0-1) . Note this cleanup only removes requests where `r.member == B` (i.e., requests *authored* by `B`); it does not touch `confirmations.get(&R)`, which still contains `B`'s confirmation string.
5. `C.confirm(R)` — `confirmations.len()` for `R` is still 2 (`A`, `B`) prior to this call, so `2 + 1 >= 3` is satisfied and `R` executes, per the check at [5](#0-4) .
6. Result: `R` executes with confirmations from only `A` and `C` as currently-live members plus a stale, no-longer-valid confirmation from removed member `B` — i.e., the request executed with 2-of-5 live approvals despite `num_confirmations = 3`.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
