### Title
Withdraw-request fees are still charged after the pool is closed, permanently penalizing exiting LPs - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
The external report describes an early-exit penalty that keeps being applied during a protective timelock window whose entire purpose is to let users exit unharmed. The direct analog in idle-tranches is `requestWithdraw`: it unconditionally deducts a full-epoch-plus-buffer upfront management fee via `_totalWithdrawFees`/`_withdrawRequestManagementFeeDuration`, even after the pool has been closed (`epochEndDate == 0`, i.e. `stopEpoch` called with `_interest == 1` which recalls all principal from the borrower). In closed mode there is no next epoch, no further `stopEpoch` to pay `pendingWithdrawFees`, and no live-NAV period that could justify the fee — yet the user's receipt is still haircut by it.

### Finding Description
`requestWithdraw` computes the user's entitlement and always subtracts `totalFees` before registering the receipt:

```solidity
// contracts/IdleCDOEpochVariant.sol:772-778
uint256 principal = _underlyings;
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;
pendingWithdrawFees += totalFees;
```

The fee duration is a full `epochDuration` plus any remaining buffer:

```solidity
// contracts/IdleCDOEpochVariant.sol:925-930
uint256 bufferEnd = epochEndDate + bufferPeriod;
_duration = epochDuration;
if (block.timestamp < bufferEnd) {
  _duration += bufferEnd - block.timestamp;
}
```

The stated justification is that "receipts leave live NAV at request time but can be claimed only after the next epoch settles" (line 921-923). That rationale ceases to exist once the pool is closed: the strategy explicitly supports requests in this state (`isClosed` check at `contracts/strategies/idle/IdleCreditVault.sol:259`, and `pendingWithdraws` is not incremented because "a successfully closed pool already recalled all funds and has no later stopEpoch", lines 276-280). Since no future `stopEpoch` runs, `pendingWithdrawFees` is never paid to `feeReceiver` (`_transferFeeUnderlyings` is only called inside `_stopEpoch`, line 419). The haircut amount is simply retained in CDO NAV, redistributing the exiting user's principal to remaining holders — identical in structure to the reported bug where the scaling fee punishes participants during a window that exists to protect them.

### Impact Explanation
A KYC'd LP requesting withdrawal after `stopEpoch(0, 1)` (close-pool mode) loses `principal * managementFee * epochDuration / (365 days * FULL_ALLOC)` with no corresponding service rendered and no fee receiver ever paid. The loss is permanent and quantified per request.

### Likelihood Explanation
Requires a close-pool configuration (`epochEndDate == 0`) and a non-zero `managementFee`; both are honest manager/owner configurations, and any tranche holder can then be penalized. The window is indefinite after closure.

### Recommendation
Skip `_totalWithdrawFees` (or at least the management-fee component) in `requestWithdraw` when `epochEndDate == 0` / `!isEpochRunning` and no further epoch will settle, mirroring the report's recommendation to not apply the scaling fee after the protective period has started.

### Proof of Concept
A Foundry test would: deposit via `depositAA`, run one epoch, call `stopEpoch(0, 1)` to close the pool, then call `requestWithdraw` and assert `requested == principal` (no `epochDuration` management fee deducted), where the test at `test/foundry/IdleCreditVault.t.sol:1255` (`testRequestWithdrawChargesManagementFeeUpfront`) shows the fee is currently deducted.

Caveat: I could not fully confirm whether `requestWithdraw` is additionally gated (e.g. `allowAAWithdrawRequest` cleared or `_updateAccounting` reverting) after pool close or post-default; if a guard already blocks post-close requests, the same defect applies to requests made in the buffer after the final `stopEpoch` where the fee duration includes `bufferEnd - block.timestamp` for a period in which funds are already recalled.
