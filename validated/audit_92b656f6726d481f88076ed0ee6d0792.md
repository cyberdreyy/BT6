### Title
Dust/large instant-withdraw request blocks all instant claims and stopEpoch until borrower funding - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Analogous to the linx-server `uploadPostHandler` DoS (a single crafted request degrades service for everyone), an unprivileged tranche holder can submit an `instant` withdraw request that leaves `pendingInstantWithdraws > 0`. While any instant receipt is unfunded, `stopEpoch` reverts and every user's `claimInstantWithdrawRequest` reverts, freezing all pending instant withdrawals until the manager pulls funds from the borrower after `instantWithdrawDeadline`.

### Finding Description
`IdleCreditVault.requestInstantWithdraw` (`contracts/strategies/idle/IdleCreditVault.sol:356-375`) accepts any `_amount`, burns the CDO's strategy tokens, mints the user a 1:1 receipt, and increments `pendingInstantWithdraws` — with no minimum amount and no per-epoch gating.

Two downstream effects create the DoS:

1. `IdleCDOEpochVariant._stopEpoch` reverts whenever `_pendingInstant() != 0` (`contracts/IdleCDOEpochVariant.sol:343-345`). The epoch cannot be stopped until the manager calls `getInstantWithdrawFunds`, which itself is only callable once `block.timestamp >= instantWithdrawDeadline` and only while the epoch is running (`contracts/IdleCDOEpochVariant.sol:558-574`).
2. While a pending instant request is unfunded, `claimInstantWithdrawRequest` reverts `NotAllowed` for *all* users, not just the requester. This is confirmed by `testClaimInstantWithdrawRequestAfterAnEpochWithInstantWithdraw` (`test/foundry/IdleCreditVault.t.sol:4881-4884`): a second unfunded instant request makes the first (funded) claim revert.

Sequence: after a `stopEpoch` where `lastEpochApr > unscaledApr + instantWithdrawAprDelta` (instant-withdraw window opens whenever the manager lowers APR), the attacker — any KYC'd tranche holder — calls `cdoEpoch.requestWithdraw(amount, tranche)`, which routes into `requestInstantWithdraw` (`contracts/IdleCDOEpochVariant.sol:761-768`). If the requested amount exceeds the idle buffer cash, `startEpoch`'s prefunding path (`contracts/IdleCDOEpochVariant.sol:279-292`) cannot cover it, so `pendingInstantWithdraws` stays nonzero. From then until `instantWithdrawDeadline` plus a manager `getInstantWithdrawFunds` call: every instant claim reverts and `stopEpoch` reverts. The attacker can repeat this each epoch the APR drops, at the cost of temporarily locking (not losing) their own funds, since a 1:1 strategy-token receipt is minted back to them.

Broken invariant: one request's funding state is global — a single unfunded receipt freezes all instant claims and the epoch state machine.

### Impact Explanation
Temporary freezing of funds: all instant-withdraw claimants are blocked, and epoch finalization (`stopEpoch`) is blocked, until the manager funds the requests after the delay. Repeated each low-APR epoch, this approaches a persistent freeze of instant withdrawals and forced extension of running epochs, delaying all normal withdraw settlement that depends on `stopEpoch`. The attacker's cost is only opportunity cost of locked (receipt-backed) capital.

### Likelihood Explanation
Requires (a) instant withdrawals enabled (`instantWithdrawAprDelta` configured) and (b) an epoch where the manager lowers APR enough to trigger the instant path — a routine operational action. The attacker must post an amount larger than idle buffer liquidity so prefunding at `startEpoch` doesn't clear it; there is no lower bound on the request, so even modest unfunded amounts suffice when buffer cash is thin. Manager intervention is required to resolve it each time, so the freeze duration is bounded by `instantWithdrawDelay` plus operational response, but it is repeatable.

### Recommendation
- Enforce a minimum `requestInstantWithdraw` amount and/or cap pending instant requests relative to available buffer liquidity.
- Scope the claim freeze per-epoch/user: allow `claimInstantWithdrawRequest` to pay receipts that were already funded (`instantWithdrawsRequestsByEpoch` + funded markers) instead of reverting globally on any `pendingInstantWithdraws > 0`.
- Let `stopEpoch` proceed while instant requests are pending by auto-invoking the funding pull or treating unfunded instant receipts like normal pending withdraws.

### Proof of Concept
Foundry fork PoC sketch (modeled on `testClaimInstantWithdrawRequestAfterAnEpochWithInstantWithdraw`, `test/foundry/IdleCreditVault.t.sol:4854-4893`):

```solidity
function testInstantWithdrawGriefingDos() external {
    uint256 amountWei = 10000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amountWei);

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch()); // APR drops -> instant window open

    // victim requests instant withdraw
    address victim = makeAddr('victim');
    _depositWithUser(victim, amountWei, true);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(1);
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    _getInstantFunds(); // victim's request now funded

    // attacker requests instant withdraw larger than idle buffer cash
    address attacker = makeAddr('attacker');
    uint256 attackerMint = _depositWithUser(attacker, amountWei, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(attackerMint, address(AAtranche));

    _startEpochAndCheckPrices(2);
    assertGt(IdleCreditVault(address(strategy)).pendingInstantWithdraws(), 0);

    // victim's funded claim now reverts
    vm.prank(victim);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimInstantWithdrawRequest();

    // stopEpoch is also blocked until deadline + manager funding call
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);
}
```

Uncertainty note: the exact revert path for claims depends on the CDO-side `claimInstantWithdrawRequest` gating (the test at `IdleCreditVault.t.sol:4883` confirms the `NotAllowed` revert while pending instant requests are unfunded); the `stopEpoch` revert is directly at `IdleCDOEpochVariant.sol:345`.
