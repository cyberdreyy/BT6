### Title
Post-default instant withdraw receipts are misclassified as defaulted-epoch receipts and paid the recovery haircut from the shared reserve — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestInstantWithdraw` never checks `defaultRecoveryFinalized`, unlike `requestWithdraw` which has a dedicated post-default path (`postDefaultRequests`). Because `epochNumber` is not bumped after a default, a new instant withdraw request made after `finalizeDefaultRecovery` is recorded into `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — the same bucket used for defaulted-epoch receipts. `claimInstantWithdrawRequest` then routes it through `_claimDefaultedInstantWithdrawRequest`, paying `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` out of `defaultRecoveryReserve`.

### Finding Description
The bug class of the external report — an object interpreted under the wrong type/state — maps directly onto receipt classification in the vault:

- `requestInstantWithdraw` (IdleCreditVault.sol:356-375) burns strategy tokens and records the receipt under `epochNumber`. After `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` (line 693) and no further `stopEpoch`/`deposit` bumps `epochNumber`, any new instant request lands in the defaulted epoch bucket.
- `claimInstantWithdrawRequest` (lines 380-393) unconditionally calls `_claimDefaultedInstantWithdrawRequest` whenever `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`.
- `_claimDefaultedInstantWithdrawRequest` (lines 842-856) reads `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — which now includes post-default requests — and pays them at `defaultRecoveryPrice` via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` (line 915).

`defaultRecoveryReserve` was sized at finalization to cover only the claims outstanding at that time (`reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve`, line 686). Post-default instant receipts were never part of that basis, yet they consume the same reserve. Two failure modes:

1. `defaultRecoveryPrice > RECOVERY_FULL` (explicitly allowed: "Recovery can be above par", line 687): an attacker holding strategy tokens requests a large instant withdraw post-default and is paid `amount * price > amount` directly from the reserve — unbounded theft proportional to their request size.
2. `defaultRecoveryPrice < RECOVERY_FULL`: the attacker still drains reserve while receiving less than their burn — but combined with `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` decrements it desynchronizes the reserve ledger, and any other user's post-default instant request is permanently haircutted (theft/freezing of their funds) since no par path exists for them. Unlike `requestWithdraw`, which burns/mints into `postDefaultRequests` and pays 1:1 (lines 247-257, 760-767), instant requests have no post-default branch at all.

### Impact Explanation
Theft of the isolated default recovery reserve: post-default instant claims spend `defaultRecoveryReserve` that is earmarked for genuine defaulted-epoch claimants. At above-par recovery this is direct profit; at sub-par recovery it still removes reserve earmarked for honest claimants, causing underpayment/insolvency for them. Additionally, honest users making post-default instant requests receive only `amount * defaultRecoveryPrice`, an unearned haircut — a direct loss of funds with no borrower loss to justify it.

### Likelihood Explanation
Preconditions: pool defaulted and `finalizeDefaultRecovery` executed; `pendingInstantWithdraws != 0` at finalization so `defaultInstantWithdrawsFinalized` is true (i.e., there was at least one unfunded instant receipt — common when the borrower returns nothing). The attacker only needs strategy tokens, obtainable by any KYC-passing lender via a normal deposit (strategy tokens are minted to the CDO; the CDO calls `requestInstantWithdraw` on behalf of the user — the strategy-side entrypoint itself has no post-default gate). One uncertainty I could not fully verify within the search budget: whether `IdleCDOEpochVariant.requestInstantWithdraw` itself reverts when `defaulted()` is true or the pool is closed (`epochEndDate == 0`). The strategy code's asymmetry — a dedicated post-default path for normal requests but none for instant requests — strongly suggests post-default requests were intended to be supported, but if the CDO blocks instant requests post-default the attack is unreachable and only the mis-haircut of legitimate claims remains (a freeze rather than theft). This should be confirmed with the CDO-side call path before relying on the theft scenario.

### Recommendation
- In `requestInstantWithdraw`, add an explicit post-default branch mirroring `requestWithdraw`: revert if any prior open receipt exists, and route the amount to a par-paid path (e.g., reuse `postDefaultRequests` or a dedicated instant post-default mapping keyed by a fresh epoch marker) instead of `instantWithdrawsRequestsByEpoch[epochNumber]`/`instantWithdrawClaimsByEpoch`.
- Alternatively, record post-default instant receipts under a sentinel epoch (e.g., `epochNumber + 1` or a dedicated `postDefaultInstantRequests` mapping) and pay them via `_transferFundedClaim`, not `_transferDefaultRecovery`.

### Proof of Concept
Foundry fork PoC outline (mainnet fork, real pool config):

```solidity
// 1. Deposit as user A (KYC'd), request instant withdraw; borrower returns nothing.
cdoEpoch.requestInstantWithdraw(amountA, tranche);
// 2. Warp past epochEndDate; manager stops epoch with loss -> defaulted.
vm.warp(cdoEpoch.epochEndDate() + 1);
cdoEpoch.stopEpoch(0, 0);               // defaulted == true, pendingInstantWithdraws != 0
// 3. Manager finalizes recovery with partial (or above-par) recovered amount.
cdoEpoch.finalizeDefault(recovered, manager); // sets defaultRecoveryFinalized, price, epoch
// 4. Attacker B (holds strategy tokens via deposit) requests instant withdraw NOW.
cdoEpoch.requestInstantWithdraw(amountB, tranche); // lands in instantWithdrawsRequestsByEpoch[B][defaultRecoveryEpoch]
// 5. Attacker claims: paid amountB * defaultRecoveryPrice / 1e18 from defaultRecoveryReserve.
cdoEpoch.claimInstantWithdrawRequest();
// Assert: defaultRecoveryReserve decreased by attacker payout; attacker profit if price > 1e18;
// honest defaulted-epoch instant claimant A is left undercollateralized.
```

Key assertions: `strategy.instantWithdrawsRequestsByEpoch(B, strategy.defaultRecoveryEpoch()) == amountB` after step 4 proves the misclassification; `underlying.balanceOf(B) > amountB` (above-par case) or `defaultRecoveryReserve` depleted below the sum owed to pre-default claimants (sub-par case) proves the invariant break.
