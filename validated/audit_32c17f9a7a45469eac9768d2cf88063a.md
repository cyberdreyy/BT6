### Title
Commission-percentage cutover in `delegation_pool.move` is gated on wall-clock time, not on actual lockup-cycle rollover, letting anyone trigger premature commission-rate application - (File: `aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

### Summary
`is_next_commission_percentage_effective` only compares `timestamp::now_seconds()` to the stored `effective_after_secs`, with no dependency on whether the delegation pool's observed lockup cycle (OLC) has actually advanced on-chain. `synchronize_delegation_pool` — a public, unauthenticated entry function that is also invoked implicitly by every delegator action (`add_stake`, `unlock`, `reactivate_stake`, `withdraw`, `set_beneficiary_for_operator`, etc.) — uses this same timestamp check, independently of the `lockup_cycle_ended` flag, to switch `pool.operator_commission_percentage` to the new rate. This allows the new commission rate to be applied to reward drift that was accrued while the pool's lockup cycle had not yet actually rolled over on the underlying stake pool.

### Finding Description
`is_next_commission_percentage_effective` is defined purely in terms of wall-clock time: [1](#0-0) 

`synchronize_delegation_pool` first computes the reward drift and commission owed using `pool.operator_commission_percentage` (the *old* percentage, since it hasn't been overwritten yet): [2](#0-1) 

It then distributes that commission to the operator's beneficiary based on the old rate: [3](#0-2) 

Separately — and NOT nested inside the `lockup_cycle_ended` branch that actually advances the delegation pool's observed lockup cycle — the function unconditionally checks the wall-clock condition and swaps in the new commission percentage for all future accounting: [4](#0-3) 

Because `lockup_cycle_ended` (line 1977) and the commission-percentage swap (line 1988) are two independent `if` statements rather than a single coupled transition, `pool.operator_commission_percentage` can be updated to the new value on a sync call where `lockup_cycle_ended` is `false` — i.e., where the delegation pool's own OLC bookkeeping has not advanced. Any reward drift observed on a *subsequent* sync call (before the real lockup eventually rolls over and `lockup_cycle_ended` becomes true) will then be split using the new commission percentage, even though those rewards accrued during what is still the same lockup cycle that the operator's new rate was only supposed to apply to "next."

The `update_commission_percentage` function's own comment acknowledges the intended sequencing ("the operator is paid its uncommitted commission rewards with the old commission percentage, and any pending commission percentage change is applied before the new commission percentage is set"), but the code enforces this ordering only for the single sync call that performs the update — it does not gate the percentage swap on the lockup cycle actually having ended: [5](#0-4) 

Since `synchronize_delegation_pool` is a `public entry fun` callable directly by anyone, and is also triggered implicitly by ordinary delegator actions, an unprivileged party can control *when* this state transition first fires, independent of the underlying stake pool's actual lockup renewal.

**Caveat / unverified area:** I was unable to fully trace `stake.move`'s epoch/lockup-renewal path (`on_new_epoch` / lockup renewal logic that determines when `lockup_cycle_ended` actually becomes observable) before exhausting my tool budget, so I cannot precisely quantify how large the exploitable window is (i.e., how much reward drift can realistically accumulate between "wall clock crosses `effective_after_secs`" and "the stake pool's lockup actually renews"). This would need confirmation via a unit/integration test as the proof idea suggests.

### Impact Explanation
This does not let an attacker steal principal or redirect commission to an arbitrary address — `beneficiary_for_operator` routing itself is correct. The impact is a value-accounting error: reward drift that should be split at the *old* commission percentage for the remainder of the current lockup cycle can instead be split at the *new* percentage, shifting value between the operator's beneficiary and the pool's delegators. Depending on whether the new rate is higher or lower than the old, this either over- or under-pays commission relative to the lockup cycle that should be in effect, which falls within the "Accounting … must preserve value" pivot in scope.

### Likelihood Explanation
Triggering the premature transition requires no special privileges — any account can call `synchronize_delegation_pool(pool_address)` directly, or simply be a delegator performing a normal `add_stake`/`unlock`/`reactivate_stake` action, at the moment wall-clock time crosses `effective_after_secs` but before the pool's actual lockup rollover is observed on-chain. This is a narrow timing window whose exact size depends on stake/epoch mechanics I could not fully verify in this session.

### Recommendation
Couple the commission-percentage cutover to the same condition that gates `lockup_cycle_ended` (i.e., only update `pool.operator_commission_percentage` when the OLC has actually advanced), or otherwise ensure `is_next_commission_percentage_effective` cannot return `true` before the real lockup cycle it refers to has ended on the underlying stake pool.

### Proof of Concept
