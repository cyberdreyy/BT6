### Title
Jovian operator fee formula omits division by `OPERATOR_FEE_SCALAR_DECIMAL`, inflating charged fees by up to 10,000x - (File: `crates/common/l1-fees/src/params.rs`)

### Summary
`L1FeeParams::operator_fee_charge_inner` computes the operator fee differently depending on whether the Jovian upgrade is active. In every other branch of this fee-math module, a raw scalar product is normalized by dividing by a fixed decimal factor before being applied (e.g. `data_gas`/1e6, `calculate_tx_l1_cost_bedrock`/1e6, `calculate_tx_l1_cost_ecotone`/16e6, `calculate_tx_l1_cost_fjord`/1e12). The Jovian branch of the operator fee, however, multiplies `gas * operator_fee_scalar * OPERATOR_FEE_JOVIAN_MULTIPLIER` without ever dividing by `OPERATOR_FEE_SCALAR_DECIMAL` (1,000,000), while the pre-Jovian (Isthmus) branch correctly divides by that same decimal factor.

### Finding Description [1](#0-0) 

```rust
pub fn operator_fee_charge_inner(&self, gas: U256, upgrade: BaseUpgrade) -> U256 {
    let operator_fee_scalar = self.operator_fee_scalar.unwrap_or_default();
    let operator_fee_constant = self.operator_fee_constant.unwrap_or_default();

    let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
        gas.saturating_mul(operator_fee_scalar)
            .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
    } else {
        gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
    };
    product.saturating_add(operator_fee_constant)
}
```

Compare this to the sibling constant comment describing the scalar's fixed-point meaning: [2](#0-1) 

`OPERATOR_FEE_SCALAR_DECIMAL` (1e6) is documented as the fixed-point scale of `operator_fee_scalar`, and it is applied consistently on the pre-Jovian path — `gas * scalar / 1e6`. On the Jovian path this division is dropped, and only the `OPERATOR_FEE_JOVIAN_MULTIPLIER` (100) is applied on top of the raw product. Since 1,000,000 / 100 = 10,000, the effective operator fee charged under Jovian is roughly 10,000× larger than the value the same scalar would have produced pre-Jovian, i.e. exactly the class of error described in the external report: a scaling/percentage normalization step is applied in one branch but incorrectly omitted (or malformed) in the parallel branch of the same computation.

This computed value directly feeds the on-chain fee actually deducted from the transaction sender and credited to `Predeploys::OPERATOR_FEE_VAULT`: [3](#0-2) [4](#0-3) 

The upfront balance-sufficiency check (`ensure_can_pay_fees`) and the actual charge use the same `operator_fee_charge` output, so an inflated fee is both charged from the sender and credited to the vault: [5](#0-4) 

### Impact Explanation
Every non-deposit, non-empty transaction processed after the Jovian upgrade activates would be charged an operator fee roughly `OPERATOR_FEE_SCALAR_DECIMAL / OPERATOR_FEE_JOVIAN_MULTIPLIER` (10,000×) larger than intended relative to the configured `operator_fee_scalar`. This is a direct, protocol-wide overcharge of every L2 transaction sender's funds (deducted from the sender's balance and credited to `OPERATOR_FEE_VAULT`), and can also cause otherwise well-funded senders to be rejected by `ensure_can_pay_fees`/`InsufficientFunds`, effectively halting normal transaction processing network-wide once Jovian is active with a nonzero `operator_fee_scalar`. This matches the "wrong provable output"/"unauthorized fund movement" class of impact required — value is siphoned from every sender's balance in excess of the intended fee schedule.

### Likelihood Explanation
Any signed, non-deposit transaction reaching this code path after the Jovian upgrade activates and the operator fee scalar is set triggers the bug — no special privileges are required by the transaction sender, and the bug fires unconditionally for that fork/config combination. The severity would be config-dependent (magnitude scales with `operator_fee_scalar`), but the code path itself is unconditionally reachable by any RPC-submitted transaction once Jovian is live.

### Recommendation
Apply the same `/ OPERATOR_FEE_SCALAR_DECIMAL` normalization in the Jovian branch as in the pre-Jovian branch, consistent with how the multiplier is meant to scale the existing fee (i.e. `gas * operator_fee_scalar * OPERATOR_FEE_JOVIAN_MULTIPLIER / OPERATOR_FEE_SCALAR_DECIMAL`), and add a differential test asserting the Jovian fee equals the Isthmus fee multiplied by exactly `OPERATOR_FEE_JOVIAN_MULTIPLIER` (not `OPERATOR_FEE_SCALAR_DECIMAL`-times larger) for identical scalars/gas.

### Proof of Concept
Using the existing unit test fixture in the repo itself: [6](#0-5) 
with `operator_fee_scalar = 1000`, `operator_fee_constant = 10`, `gas = 1000`:
- Isthmus (correct, divides by 1e6): `1000*1000/1_000_000 + 10 = 11`.
- Jovian (buggy, no division): `1000*1000*100 + 10 = 100_000_010`.

Expected (if normalized consistently, applying the 100x multiplier on top of the Isthmus-normalized value): `11 * 100 = 1100`, not `100_000_010`. The current Jovian output is ~90,909× larger than the value that would result from correctly reapplying the `OPERATOR_FEE_SCALAR_DECIMAL` normalization, confirming the missing division.

    /// Returns the Isthmus operator fee for `envelope` over `gas`. Zero for deposits and before
    /// Isthmus.
    ///
    /// The operator fee is an Isthmus feature; `L1FeeParams::operator_fee_charge` computes it
    /// unconditionally, so the Isthmus gate is applied here (matching the reference, which gates
    /// in its `reward_beneficiary`). The Base upgrade ladder is discriminant-ordered.
    fn operator_fee(host: &mut Evm<'_, BaseEvmTypes>, envelope: &BaseTxEnvelope, gas: u64) -> U256 {
        let Some(enveloped) = envelope.enveloped() else {
            return U256::ZERO;
        };
        let upgrade = host.config_spec_id().upgrade();
        if (upgrade as u8) < (BaseUpgrade::Isthmus as u8) {
            return U256::ZERO;
        }
        host.block_env().ext.operator_fee_charge(enveloped, U256::from(gas), upgrade)
    }

    /// Rejects the transaction when `caller` cannot cover the full upfront charge — the maximum
    /// gas cost, the transferred value, and the OP-stack L1 data and operator fees.
    ///
    /// The framework's `validate_sender` already rejects a caller that cannot cover the gas cost
    /// and value, but it is unaware of the L1 and operator fees charged here, and
    /// [`charge_upfront`] deducts with wrapping arithmetic. Without this guard an underfunded
    /// caller would silently wrap to a spurious balance instead of the transaction failing; this
    /// mirrors the revm reference, which rejects such a caller with `LackOfFundForMaxFee`.
    ///
    /// A no-op for deposits (funded on L1 and exempt) and when fee charging or balance checks are
    /// disabled (e.g. `eth_call` simulation), matching the conditions under which `validate_sender`
    /// and `charge_upfront` themselves enforce balances.
    fn ensure_can_pay_fees(
        host: &mut Evm<'_, BaseEvmTypes>,
        envelope: &BaseTxEnvelope,
        caller: Address,
        l1_fee: U256,
        operator_fee: U256,
    ) -> HandlerResult<()> {
        let Some(tx) = envelope.as_standard() else {
            return Ok(());
        };
        if !host.feature(EvmFeatures::FEE_CHARGE) || !host.feature(EvmFeatures::BALANCE_CHECK) {
            return Ok(());
        }
        let required = U256::from(tx.gas_limit())
            .saturating_mul(U256::from(tx.max_fee_per_gas()))
            .saturating_add(tx.value())
            .saturating_add(l1_fee)
            .saturating_add(operator_fee);
        let balance =
            host.state_mut().account(&caller, false).map_err(HandlerError::Fatal)?.balance();
        if balance < required {
            return Err(HandlerError::InsufficientFunds);
        }
        Ok(())
    }
