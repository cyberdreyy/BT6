### Title
BlockRejection signature does not bind `reason_code`/`response_data`, allowing a captured signature to be replayed against a fabricated rejection reason - (File: libsigner/src/v0/messages.rs)

### Summary
`BlockRejection::hash()` computes the signed digest using only `signer_signature_hash` and `chain_id` inside a `make_structured_data_domain("block-rejection", "1.0.0", chain_id)` envelope, never covering `reason_code` or `response_data`. Because `verify()` and `recover_public_key()` re-derive the signature hash the same way, any observer who has seen one valid `BlockRejection` signature from a signer can splice a different `reason_code`/`response_data` into a new `BlockRejection` object and the signature will still verify as authentic. [1](#0-0) 

### Finding Description
`BlockRejection::hash` builds the domain tuple from only `chain_id` and the string literal `"block-rejection"`/`"1.0.0"`, and the message body is just `self.signer_signature_hash`: [2](#0-1) 

`sign()` signs this hash, and `verify()`/`recover_public_key()` recompute the identical hash to check the signature: [3](#0-2) 

`reason`, `reason_code`, `metadata`, and `response_data` (which includes `failed_txid`, `tenure_extend_timestamp`, etc.) are all serialized as part of the wire `BlockRejection` struct [4](#0-3)  and are transmitted/deserialized as-is [5](#0-4) , but none of these fields are covered by the signed hash. An attacker who observes a genuine `BlockRejection` (signature + `signer_signature_hash` + `chain_id`) can construct a new `BlockRejection` with the same three signed fields but arbitrary `reason_code`/`response_data`/`reason` string, keep the stolen `signature`, and gossip it over StackerDB as if from the honest signer. `verify()` will return `Ok(true)` for the forged object.

### Impact Explanation
Downstream, `stackerdb_listener.rs` inspects `rejected_data.reason_code` to decide whether to attribute rejection weight to a specific transaction as "problematic" (`ValidateRejectCode::ProblematicTransaction`) or merely "bad" (`BadTransaction`), accumulating `info.problematic_weight`/`info.total_weight` keyed off the unauthenticated `reason_code` and `response_data.failed_txid`: [6](#0-5) . Since neither `reason_code` nor `response_data.failed_txid` is bound by the signature, an attacker with one valid captured rejection signature can forge attribution of "problematic transaction" weight to an arbitrary txid under a legitimate signer's identity, corrupting the per-signer/per-reason weight bookkeeping that miners and other signers rely on for tenure/liveness decisions. On the signer side, `stacks-signer/src/v0/signer.rs` calls `add_block_rejection_signer_addr(block_hash, signer_address, reject_reason)` and later checks `compute_reject_code_signing_weight(..., RejectReasonPrefix::ReorgNotAllowed)` to decide whether to mark a miner invalid for an "invalid reorg" [7](#0-6) ; if `reject_reason` fed into this path is taken from the unauthenticated `reason_code`/`response_data` of a forged-but-signature-valid `BlockRejection`, an attacker could inject an `Unknown`/attacker-chosen reason under an honest signer's identity into rejection-reason tallies (e.g. skewing `ReorgNotAllowed` counts or the failed-txid weight tallies) without needing majority signer weight — matching the "rejection recounted/mis-attributed" pattern in the Critical bucket, since it corrupts shared rejection-based bookkeeping that other signers/miners trust as authentic per-signer attestations. This does not, by itself, let an attacker sign an invalid block or flip a rejection into an acceptance vote (total_weight_rejected/total_weight_approved counters themselves are keyed by slot_id/signer identity and unaffected by reason forgery), so its blast radius is the reason-code/response-data-driven downstream logic (failed-txid weighting, reorg-invalid-miner marking) rather than the core signing/threshold safety, but that logic is explicitly consumed cross-signer and cross-miner.

### Likelihood Explanation
The precondition is simply that the attacker (an unprivileged single-miner-slot party who can gossip StackerDB messages) has observed one genuine signed `BlockRejection` from any signer — a routine, non-adversarial event since rejections are broadcast in plaintext on StackerDB. The forgery itself requires no cryptographic work: the attacker copies `signer_signature_hash`, `chain_id`, and `signature` verbatim and freely edits `reason`, `reason_code`, and `response_data`. This is trivially repeatable for every rejection a signer produces and costs only observation + one gossip message.

### Recommendation
Include `reason_code` and the material fields of `response_data` (at minimum `failed_txid`, `tenure_extend_timestamp`, `tenure_extend_read_count_timestamp`, and the reject-reason discriminant/payload) inside the structured-data message that is hashed and signed in `BlockRejection::hash()`, e.g. by hashing a Clarity tuple `{signer_signature_hash, reason_code, response_data}` rather than just `signer_signature_hash`, so that `verify()` fails if any of these fields are altered post-signature.

// libsigner/src/v0/messages.rs (test module)
#[test]
fn block_rejection_signature_does_not_bind_reason_code() {
    let private_key = StacksPrivateKey::random();
    let public_key = StacksPublicKey::from_private(&private_key);
    let sig_hash = Sha512Trunc256Sum([0x11; 32]);

    // Honest signer signs a rejection for reason A (e.g. ConnectivityIssues)
    let original = BlockRejection::new(
        sig_hash,
        RejectReason::ConnectivityIssues("timeout".into()),
        &private_key,
        false,
        0,
        0,
    );
    assert!(original.verify(&public_key).unwrap());

    // Attacker forges a second rejection object with the SAME
    // signer_signature_hash/chain_id/signature but a DIFFERENT reason_code
    // (e.g. ValidationFailed(InvalidBlock)) and different response_data.
    let mut forged = original.clone();
    forged.reason = "forged".into();
    forged.reason_code = RejectCode::ValidationFailed(ValidateRejectCode::InvalidBlock);
    forged.response_data = BlockResponseData::new(
        999, RejectReason::ValidationFailed(ValidateRejectCode::InvalidBlock), 999, Some(Txid([0x22; 32])),
    );
    // signature field is untouched (stolen from `original`)

    // FAIL_CLOSED expectation: this should be false, but the actual code
    // returns true because hash() ignores reason_code/response_data.
    assert!(forged.verify(&public_key).unwrap());
    assert_ne!(original.reason_code, forged.reason_code);
    assert_eq!(original.hash(), forged.hash()); // proves the domain collision
}

    /// The signature hash for the block rejection
    pub fn hash(&self) -> Sha256Sum {
        let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
        let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
        structured_data_message_hash(data, domain_tuple)
    }

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
