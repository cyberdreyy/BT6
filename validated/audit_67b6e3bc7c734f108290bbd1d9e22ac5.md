### Title
Confirmations from removed multisig members remain valid and count toward the execution threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` decides whether to execute a request purely by comparing the size of the `confirmations` set to `num_confirmations`. When a member is removed via `DeleteMember`/`DeleteKey`, the contract only purges requests and confirmations that member *authored*; it never scrubs confirmations that member previously *cast* on other members' pending requests. Those stale confirmations keep counting toward the K-of-N threshold, letting a request execute with approvals from fewer currently-live members than `num_confirmations` requires.

### Finding Description
`delete_member` (multisig2) / the `DeleteKey` action (multisig) removes a member and cleans up only requests whose `MultiSigRequestWithSigner.member` (or `signer_pk`) equals the removed member: [1](#0-0) 

It does **not** scan `self.confirmations` for entries where the removed member appears as a *confirmer* of someone else's request. Meanwhile `confirm` only checks the raw cardinality of the confirmations set: [2](#0-1) 

The binding that should hold is:
```
confirmations.len() == number of *currently live* members who approved the request
```
but after a member removal it becomes:
```
confirmations.len() > number of currently live members who approved
```
because the removed member's stale confirmation is never deleted from `confirmations` for requests it didn't author. The identical construction exists in the older `multisig` contract's `confirm`/`DeleteKey` path: [3](#0-2)  and [4](#0-3) .

### Impact Explanation
This crosses the explicitly listed Critical impact "a multisig request executed below threshold": a request can be executed (e.g. a `Transfer`, `AddKey`/`AddMember`, or `FunctionCall`) with fewer live, currently-authorized members having actually approved it than `num_confirmations` mandates. This directly undermines the K-of-N security guarantee the contract exists to provide, and can be leveraged to move funds or add keys with insufficient live authorization.

### Likelihood Explanation
Only unprivileged actions available to any existing member are needed: (1) a member confirms a pending request created by someone else, (2) that member is later removed via the normal `DeleteMember`/`DeleteKey` governance flow (a routine operation, e.g. key rotation or offboarding), and (3) the remaining members finish confirming the still-pending request. No foundation, redeploy, or malicious validator involvement is required — this is a straightforward operational sequence likely to occur during normal multisig membership changes.

### Recommendation
When removing a member, iterate over **all** requests' confirmation sets (not just requests authored by that member) and remove the departing member's entry from each. Alternatively, validate at `confirm`/execution time that every entry in `confirmations` still corresponds to a current member of `self.members`, discarding stale ones before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with 4 members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request` for a `Transfer` request `X` (or any sensitive action) to attacker-controlled `receiver_id`.
3. `D` calls `confirm(X)` → `confirmations(X) = {D}` (len 1, < 3, stored).
4. `A` calls `confirm(X)` → `confirmations(X) = {D, A}` (len 2, < 3, stored) — this matches [5](#0-4) .
5. Separately, members execute a `DeleteMember{ member: D }` request (reaching 3-of-4 confirmations among live members, a normal action). `delete_member` runs: since request `X` was authored by `A`, not `D`, its confirmations are untouched — see [1](#0-0) . `D` is removed from `self.members`, and `num_confirmations` remains 3 (asserted only against `self.members.len() - 1 >= num_confirmations` at line 358).
6. `B` (a live member) calls `confirm(X)` → `confirmations(X).len() + 1 == 3 >= num_confirmations (3)`, so `execute_request` runs and the transfer to the receiver executes.
7. Result: request `X` executed with confirmations counted from `{D, A, B}` = 3, satisfying the threshold, even though `D` was removed before step 6 and only `A` and `B` are live members who actually approved at execution time — the request executed with only 2 live-member approvals against an intended 3-of-N (now effectively 3-of-3 remaining) threshold.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
