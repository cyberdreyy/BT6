### Title
`accountSubscribe` (and `programSubscribe`) silently ignore `min_context_slot`, unlike equivalent HTTP RPC methods - (File: rpc/src/rpc_pubsub.rs)

### Summary
The Vader finding describes a case where a protection (IL protection) is only enforced on one entry point (`Router.removeLiquidity()`) but silently bypassed when the underlying function (`Pools.removeLiquidity()`) is invoked through an alternate path, with no explicit rejection or warning. The analogous pattern exists in agave's JSON-RPC surface: the `min_context_slot` staleness guard is enforced for HTTP methods such as `getAccountInfo`/`getProgramAccounts` via `JsonRpcRequestProcessor::get_bank_with_config`, but the equivalent pubsub subscription methods `accountSubscribe` and `programSubscribe` explicitly destructure and discard the field instead of validating it.

### Finding Description
For synchronous/HTTP RPC calls, `min_context_slot` is a documented client-supplied guarantee meant to ensure the node being queried has observed at least the given slot before returning a response. This is enforced centrally in `get_bank_with_config`: [1](#0-0) 

Callers such as `get_account_info`, `get_multiple_accounts`, and `get_program_accounts` all route through this check: [2](#0-1) [3](#0-2) 

However, the pubsub equivalents in `RpcSolPubSubImpl` take the same `RpcAccountInfoConfig` (which includes `min_context_slot`), but `account_subscribe` explicitly discards the field with `min_context_slot: _, // ignored` and never validates it against the current bank/root slot before establishing the subscription: [4](#0-3) 

`program_subscribe` goes further and doesn't even destructure `min_context_slot` from the account config at all, it is dropped implicitly when constructing `ProgramSubscriptionParams`: [5](#0-4) 

This mirrors the reported bug class exactly: a protection (freshness/consistency guarantee) is enforced through one interface (`getAccountInfo`/`getProgramAccounts` HTTP RPC) but silently bypassed when the "equivalent" interface (`accountSubscribe`/`programSubscribe` pubsub) is used, with no error surfaced to the caller and no documentation distinguishing the behavior at the call site.

### Impact Explanation
A client that relies on `min_context_slot` to avoid reading state from a node that hasn't caught up to a known slot (e.g., after submitting and confirming a transaction on another node, then subscribing for follow-up state changes) will silently get subscribed and receive account/program notifications computed against whatever bank the node currently has — potentially stale by an arbitrary number of slots — without any `MinContextSlotNotReached` error. This falls into the "wrong-slot/fork/account data returned" impact category: an unprivileged client makes a normal `accountSubscribe`/`programSubscribe` call and receives account data that does not honor its supplied staleness bound, which can lead the client to act on outdated on-chain state while wrongly believing the guarantee held.

### Likelihood Explanation
High. Any unprivileged JSON-RPC pubsub client can trigger this by simply passing `min_context_slot` in the config of `accountSubscribe` or `programSubscribe` — no special privileges, timing races, or multiple calls are required. It is a single, straightforward call with a field that is silently ignored, exactly the "no-privilege, single request" bar required by the validation rules.

### Recommendation
Enforce `min_context_slot` in the pubsub subscription handlers analogous to `get_bank_with_config`: on `account_subscribe`/`program_subscribe` (and any other subscription config carrying `min_context_slot`), check the current bank/root slot against the requested `min_context_slot` and return `RpcCustomError::MinContextSlotNotReached` if not yet reached, instead of silently dropping the field. At minimum, if intentional, this divergence must be clearly documented in the RPC/pubsub API docs so clients do not assume parity with the HTTP methods.

### Proof of Concept
1. Start a validator/RPC node that is behind (e.g., artificially delay bank_forks root advancement or connect right at startup before it has processed slot `N`).
2. Call the pubsub method:
```
{"jsonrpc":"2.0","id":1,"method":"accountSubscribe","params":["<pubkey>", {"commitment":"processed","minContextSlot": N}]}
```
where `N` is far ahead of the node's actual current slot.
3. Observe the code path in `RpcSolPubSubImpl::account_subscribe`: `min_context_slot` is destructured into `_` and dropped, and `self.subscribe(...)` succeeds immediately, in contrast to `JsonRpcRequestProcessor::get_bank_with_config` used by `getAccountInfo`, which would return a `MinContextSlotNotReached` error for the same slot bound. The subscription is established and later notifications reflect whatever bank slot the node processes, without ever validating against `N`.

impl JsonRpcRequestProcessor {
    fn get_bank_with_config(&self, config: RpcContextConfig) -> Result<Arc<Bank>> {
        let RpcContextConfig {
            commitment,
            min_context_slot,
        } = config;
        let bank = self.bank(commitment);
        if let Some(min_context_slot) = min_context_slot
            && bank.slot() < min_context_slot
        {
            return Err(RpcCustomError::MinContextSlotNotReached {
                context_slot: bank.slot(),
            }
            .into());
        }
        Ok(bank)
    }
