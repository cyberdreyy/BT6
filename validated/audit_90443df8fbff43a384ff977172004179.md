### Title
Older loss-haircutted withdraw receipts are paid at par after a newer epoch's loss claim, draining the funded reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault` applies a single `lossRecoveryPriceByEpoch` haircut to the *aggregate* `pendingWithdraws` basis in `collectWithdrawFunds`, but `_claimLossAdjustedWithdrawRequest` only clears the receipt slice recorded under `lastWithdrawRequest[_user]` (the latest request epoch). Any older per-epoch receipt the same user holds falls through to `_claimFundedWithdrawRequest`, which pays it 1:1 even though the strategy was only funded `amount * lossRecoveryPrice / 1e18` for it. The bug class is stale/uninitialized-state read (CVE-2021-21218 analog): the claim path reads the receipt under a stale epoch key and prices it with the wrong (full) recovery rate instead of the haircutted rate it was actually funded at.

### Finding Description
In `requestWithdraw`, a user who already has an unclaimed request may open another one in a later epoch as long as no loss price exists yet for their `lastWithdrawRequest` epoch (`contracts/strategies/idle/IdleCreditVault.sol:259-294`). `lastWithdrawRequest[_user]` is then overwritten to the new epoch (`:282`).

At `stopEpoch` with a loss, `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * 1e18 / pendingBasis` over the *whole* `pendingWithdraws` — which includes both the user's old and new receipts — and stores it under `lossRecoveryPriceByEpoch[epochNumber]` (`:411-421`).

On claim (`claimWithdrawRequest`, `:301-314`):
1. `_claimLossAdjustedWithdrawRequest` uses `lossEpoch = lastWithdrawRequest[_user]` (the *newest* epoch) and clears only `withdrawsRequestsByEpoch[_user][lossEpoch]` via `_clearWithdrawClaimForEpoch` (`:789-837`). The older receipt stays in `withdrawsRequests[_user]`.
2. `_claimFundedWithdrawRequest` then pays the remaining `withdrawsRequests[_user]` at par through `_transferFundedClaim` (`:319-349`), gated only by `epochNumber > lastWithdrawRequest` (now reset to 0).

The older receipt was haircut in the funding math but is redeemed at 100%. The strategy's funded balance only covers `pendingBasis * lossRecoveryPrice / 1e18`, so the excess paid to the attacker is taken from funds reserved for other claimants.

### Impact Explanation
Direct theft / insolvency. The attacker extracts `(1 - lossRecoveryPrice) * oldReceiptAmount` more underlying than was funded. Because the reserve is fixed, other users' loss-adjusted or funded claims are left undercollateralized and will revert on transfer — permanent loss for honest LPs quantified by the attacker's overpayment. With a 50% loss price, a user holding an old receipt of size X steals ~X/2.

### Likelihood Explanation
Requires only unprivileged actions by a KYC'd lender: request a withdraw in epoch N, do not claim after it is funded, request again in epoch N+1, then claim once an honest `stopEpochWithDuration(_lossAmount)` produces a `lossRecoveryPriceByEpoch`. The loss event itself is a normal, honest borrower/manager sequence (e.g., partial borrower shortfall), not attacker-controlled privilege. No existing guard stops it: the `requestWithdraw` re-request check only inspects the *latest* epoch's price (`:263-271`), and nothing ties older receipts to the epoch loss price.

### Recommendation
Track per-epoch funding price for every pending receipt, not just the latest. Either:
- refuse new `requestWithdraw`s while *any* unclaimed receipt exists once a loss epoch has been recorded globally (not only for `lastWithdrawRequest`), or
- record the cumulative haircut per pending receipt (e.g., store a `fundedPrice` alongside `withdrawsRequestsByEpoch`) and have `_claimFundedWithdrawRequest` pay `amount * fundedPrice / 1e18` for receipts that were inside the haircutted `pendingBasis`.

Simplest fix consistent with existing structure: in `requestWithdraw`, revert if `withdrawsRequests[_user] != 0 || apr0Users[_user].principal != 0` whenever *any* `lossRecoveryPriceByEpoch` was set after the user's oldest open receipt epoch — i.e., keep per-user oldest-request epoch and compare against the loss epoch.

### Proof of Concept
Foundry fork PoC sketch (mainnet fork, real IdleCDOEpochVariant + IdleCreditVault):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";

contract StaleEpochLossClaimPoC is Test {
    // vm.createSelectFork(<mainnet rpc>);
    // idleCDOEpoch = deployed IdleCDOEpochVariant, strategy = IdleCreditVault
    // attacker = KYC-passing AA holder

    function test_overclaim() public {
        // Epoch N (running->buffer): attacker requests withdraw of X
        vm.prank(attacker);
        cdoEpoch.requestWithdraw(X, address(aaTranche));   // lastWithdrawRequest = N

        // stopEpoch N fully funds, startEpoch N+1
        vm.prank(manager); cdoEpoch.stopEpoch(interestN);
        vm.warp(epochEnd + buffer);
        vm.prank(manager); cdoEpoch.startEpoch();          // epochNumber -> N+1

        // attacker does NOT claim; opens second receipt of Y in epoch N+1
        vm.prank(attacker);
        cdoEpoch.requestWithdraw(Y, address(aaTranche));   // lastWithdrawRequest = N+1

        // borrower shortfall: manager stops with loss; collectWithdrawFunds
        // stores lossRecoveryPriceByEpoch[N+1] < 1e18 over pendingBasis = X + Y
        vm.prank(manager); cdoEpoch.stopEpochWithDuration(loss, duration);

        // claim: epoch N+1 receipt paid at haircut (correct),
        // epoch N receipt then paid AT PAR by _claimFundedWithdrawRequest
        uint256 balBefore = underlying.balanceOf(attacker);
        vm.prank(attacker);
        cdoEpoch.claimWithdrawRequest();
        uint256 got = underlying.balanceOf(attacker) - balBefore;

        // funded amount was (X+Y)*price/1e18; attacker receives Y*price/1e18 + X
        assertGt(got, (X + Y) * price / 1e18);             // overpayment = X*(1-price)
        // subsequent honest claimer reverts / is underpaid -> insolvency
    }
}
```

The assertion that `got` exceeds the haircutted funded total demonstrates the broken "one receipt, one (funded) payout" invariant and the reserve drain.
