### Title
Unpaid distribution can be permanently DoS'd by one recipient opting out of direct coin transfers, freezing rewards/commission for all other shareholders/stakers - (File: `aptos-move/framework/aptos-framework/sources/vesting.move`, also `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`vesting::distribute()` and `staking_contract::distribute_internal()` pay out withdrawable coins to *all* shareholders/recipients in a single transaction by looping over them and calling `aptos_account::deposit_coins`. If any single recipient in that loop has called `aptos_account::set_allow_direct_coin_transfers(false)` on their own account and has not yet registered a `CoinStore<AptosCoin>`, `deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`. Because Move has no partial-loop rollback, this aborts the entire `distribute` transaction, permanently blocking payout to every other shareholder/staker/operator in that pool — the same failure mode as the reported "blacklisted pfBidder" bug where one bad actor bricks settlement for everyone.

### Finding Description
`vesting::distribute` iterates the vesting contract's shareholders and sends each their share via `aptos_account::deposit_coins`: [1](#0-0) 

`staking_contract::distribute_internal` does the analogous thing for the staker/operator (and beneficiary) via the same `aptos_account::deposit_coins` call inside a `while` loop over `distribution_pool.shareholders()`: [2](#0-1) 

`aptos_account::deposit_coins` will only auto-register a `CoinStore<CoinType>` for the recipient if `can_receive_direct_coin_transfers` returns true; otherwise it aborts: [3](#0-2) 

`can_receive_direct_coin_transfers` is controlled entirely by the recipient account itself via `set_allow_direct_coin_transfers`, which any account holder can call at will and toggle back and forth: [4](#0-3) 

Because Move transactions abort atomically, an abort thrown while processing any single shareholder in the middle of the `for_each_ref`/`while` loop reverts the *entire* `distribute`/`distribute_internal` call — no other shareholder, staker, or operator gets paid, and the withdrawn coins that were already pulled out of the stake pool (`withdraw_stake`/`stake::withdraw_with_cap`) are stuck in the temporary `Coin<AptosCoin>` object for that failed transaction (i.e., the whole operation fails, so nothing is lost from storage, but it can never succeed while the hostile account keeps `allow_arbitrary_coin_transfers = false` and refuses to register a `CoinStore<AptosCoin>`).

This is functionally identical to the reported bug class: one address (which does not need any special role — just being listed as a shareholder/delegator in the pool) can indefinitely block a shared, unprivileged distribution function that every other beneficiary depends on to claim funds.

Caveat / uncertainty: I could not fully confirm from index search whether all realistic vesting/staking-contract shareholder addresses are guaranteed to have `CoinStore<AptosCoin>` pre-registered (e.g., via `aptos_account::create_account`) at the moment they are added as a shareholder — if the framework always force-registers APT for every address before it can be named a shareholder, this specific trigger path would not be reachable. I was not able to verify this pre-registration invariant for shareholder addition on `vesting::create_vesting_contract` / `staking_contract::create_staking_contract` within the available context, so this should be validated against the actual account-creation code paths before treating this as fully proven.

### Impact Explanation
If proven reachable, this is a **permanent lock of stake rewards/commission and vesting distributions** for all shareholders and the operator of a pool — not just the hostile actor. Per the task's Required Impacts, this matches "Permanent lock or non-recoverable loss of claim rights in stake, delegation, commission, beneficiary, or vesting flows," since:
- No alternate code path exists to skip a single bad recipient and pay the rest.
- The malicious shareholder has full incentive to keep `allow_arbitrary_coin_transfers = false` forever (griefing), since it costs them nothing and can be triggered by a single-signer transaction.
- Both `vesting::distribute` (used by `terminate_vesting_contract` too, since `terminate_vesting_contract` calls `distribute` before terminating) and `staking_contract::distribute_internal` (used by `unlock_stake`, `switch_operator`, `request_commission`, `update_commission_percentage`, and plain `distribute`) are affected, so this can also block operator switches and commission updates for the whole pool, not just fund withdrawal.

### Likelihood Explanation
Likelihood depends on the unresolved caveat above. If a shareholder/staker/operator can reach the distribution loop while lacking `CoinStore<AptosCoin>` and having set `allow_arbitrary_coin_transfers = false`, the attack requires only two ordinary, unprivileged, cheap transactions from the attacker's own account (`set_allow_direct_coin_transfers(false)` at any time before the pool tries to pay them) — no elevated privileges, race conditions, or special preconditions on the victim pool are required. This would make it a trivial, cheap, fully local griefing vector.

### Recommendation
- Wrap the per-recipient payout in `vesting::distribute` and `staking_contract::distribute_internal` so that a failure for one recipient does not abort the whole loop — e.g., check `aptos_account::can_receive_direct_coin_transfers` (and `coin::is_account_registered`) before attempting deposit, and if the recipient cannot accept a direct deposit, route their share to a separate claimable/escrow balance instead of calling `deposit_coins` inline.
- Alternatively, expose a `claim`-style pull function per shareholder (analogous to separating pfBidder payout from settlement in the referenced fix) so that one recipient's incompatibility with direct transfer cannot block payouts to all others.

### Proof of Concept
Not independently executable from the indexed code alone because I could not confirm whether shareholder addresses added to a vesting contract or staking_contract are always pre-registered for `CoinStore<AptosCoin>`. Conceptual PoC, contingent on that being false for at least one legitimate shareholder-onboarding path:
1. Attacker address `A` is added as a shareholder to a vesting contract (or as staker/operator/beneficiary in a `staking_contract`), without ever registering `CoinStore<AptosCoin>`.
2. `A` calls `aptos_account::set_allow_direct_coin_transfers(A_signer, false)`. [5](#0-4) 
3. Rewards accrue and become withdrawable (lockup expires); anyone calls `vesting::distribute(contract_address)` or `staking_contract::distribute(staker, operator)`.
4. Inside the loop, when `A`'s payout share is reached, `aptos_account::deposit_coins` hits `coin::is_account_registered<AptosCoin>(A) == false` and `can_receive_direct_coin_transfers(A) == false`, aborting with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`. [3](#0-2) 
5. The abort unwinds the entire `distribute`/`distribute_internal` transaction; all other shareholders/operator/staker receive nothing, and no future call to `distribute` can succeed while `A` keeps this configuration, since `A` remains in `shareholders()`/`distribution_pool` indefinitely.

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }

    #[view]
    /// Return true if `account` can receive direct transfers of coins that they have not explicitly registered to
    /// receive.
    ///
    /// By default, this returns true if an account has not explicitly set whether the can receive direct transfers.
    public fun can_receive_direct_coin_transfers(
        account: address
    ): bool acquires DirectTransferConfig {
        !exists<DirectTransferConfig>(account)
            || borrow_global<DirectTransferConfig>(account).allow_arbitrary_coin_transfers
