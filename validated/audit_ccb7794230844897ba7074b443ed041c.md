Confirmed: `EpochCreditsItem` (`vote/src/vote_state_view/field_frames.rs:257-262,289-302`) is decoded as a raw `#[repr(C)]` byte view with no validation that `credits >= prev_credits` or that entries are monotonically increasing across the list — any `u64` value in `[epoch, credits, prev_credits]` bytes is accepted as long as the list length fits the frame. This is passed unchanged into `DelegatedVoteState::from(&VoteStateView)` (`runtime/src/inflation_rewards/points.rs:94-101`), which forwards `(epoch, final_epoch_credits, initial_epoch_credits)` tuples straight from raw bytes.

### Title
Non-monotonic/crafted `epoch_credits` in an attacker-controlled vote account causes integer-subtraction overflow (panic in debug, wraparound in release) in `calc_earned_credits` - (File: `runtime/src/inflation_rewards/points.rs`)

### Summary
`calc_earned_credits` performs plain (non-saturating) `u64` subtractions `final_epoch_credits - initial_epoch_credits` and `final_epoch_credits - *new_credits_observed` on values taken directly from an unvalidated `VoteStateView` byte layout. An attacker who owns a vote account can write raw bytes such that `credits < prev_credits` for an epoch-credits entry (or that violate the invariant `final >= new_credits_observed`), causing this subtraction to underflow.

### Finding Description
The call chain is: `calculate_reward_points_partitioned`/`redeem_delegation_rewards` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:992-998`, `:726-743`) → `vote_account.vote_state_view()` → `DelegatedVoteState::from(vote_state)` (`runtime/src/inflation_rewards/points.rs:94-101`, which maps `vote_state.epoch_credits_iter()` directly into `(Epoch, u64, u64)` tuples via `EpochCreditsItem`'s raw accessors, `vote/src/vote_state_view/field_frames.rs:289-308`) → `calculate_points_for_tower`/`redeem_rewards` → `calculate_stake_points_and_credits` → `tower_epoch_credits_iter` (`runtime/src/inflation_rewards/points.rs:187-234`) → `calc_earned_credits` (`runtime/src/inflation_rewards/points.rs:158-181`).

`EpochCreditsItem` is parsed as a `#[repr(C)]` struct straight from raw account bytes with `read_item` (`field_frames.rs:23-26`), performing no sanity check that `credits() >= prev_credits()` for any entry, nor that entries across the list are non-decreasing in credits. `VoteStateFrame::try_new` (`vote_state_view.rs:270-284`) only validates version tag and list-length bounds (`u8::try_from(len)`), never the semantic content of each `EpochCreditsItem`.

In `calc_earned_credits`, when `credits_in_stake < initial_epoch_credits`, the code computes `final_epoch_credits - initial_epoch_credits` (line 170) with plain `-`. If the attacker crafts `initial_epoch_credits > final_epoch_credits` (e.g., entry `(epoch=5, credits=0, prev_credits=u64::MAX)`), this subtraction underflows: it panics in debug builds and wraps to a near-`u64::MAX` value in release builds. That value is converted `u128::from(earned_credits)` and multiplied by `stake_amount` (`points.rs:212-222`), producing an enormous, garbage `points` value that flows into `PointValue.points`, which is the shared denominator for **all** validators' reward distribution that epoch (`calculate_reward_points_partitioned`, `calculation.rs:1005-1008`).

This is reachable purely by writing on-chain vote-account data the attacker controls (their own vote account, submitted via ordinary vote/withdraw instructions or any instruction path that lets them set arbitrary `epoch_credits` bytes within `VoteStateVersions` bounds), then having stake delegated to it — no privileged access is required to trigger decoding of this data during normal epoch-reward computation, which happens automatically at epoch boundaries.

### Impact Explanation
- In debug/test builds, this is an unconditional validator panic within the reward-calculation path, matching "decoder panic" impact.
- In release builds (wrapping arithmetic), it produces a bogus, attacker-inflated `earned_credits` value that corrupts `PointValue.points` for the whole epoch, misreporting inflation-reward distribution across all stake accounts delegated to any vote account for that epoch — a "misreported amount" impact as scoped in the question.

### Likelihood Explanation
Feasibility depends entirely on whether the normal vote-program instruction path (`increment_credits`/vote processing in `programs/vote/src/vote_state/handler.rs`) can ever produce `credits < prev_credits` for a stored entry, since the attacker cannot arbitrarily overwrite raw account bytes outside of instructions validated by the vote program (this is not "direct store mutation," which is out of scope). The reachable `VoteStateView` decoder blindly trusts on-chain bytes it is given, but the *production* of those bytes goes through the vote program's own state-transition logic, which is expected to only ever append/increase credits monotonically. Whether an attacker can exploit a bug elsewhere in the vote program (out of the scope of this specific question, which is about the reward-math decoder robustness only) to actually get such bytes on-chain is unverified from what I could inspect — the decoder itself has no defense-in-depth validation, but exploitability requires either (a) a separate vote-program bug that lets an authorized voter write a non-monotonic `epoch_credits` entry, or (b) confirmation that no such bug exists, in which case this is purely a missing-defense-in-depth issue rather than an exploitable one within the current preconditions (attacker fully controls only the vote account it owns, subject to vote-program instruction validation).

### Recommendation
Use `saturating_sub` for both subtractions in `calc_earned_credits` (`runtime/src/inflation_rewards/points.rs:170,173`), and add a decoder-level or reward-math-level assertion/guard that rejects or clamps `epoch_credits` entries where `credits() < prev_credits()`, independent of whether the vote program can currently produce such data, as defense-in-depth against any current or future vote-program bug or version-mismatch replay that could write such bytes.
