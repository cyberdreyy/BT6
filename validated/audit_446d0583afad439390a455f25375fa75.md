### Title
Unscoped regex validation in `evaluateMapOverwrite` allows attacker-controlled keys (e.g. `runner.gitlab.com/*` pod labels or arbitrary `node_selector` keys) - (File: `executors/kubernetes/overwrites.go`)

### Summary
`evaluateMapOverwrite` validates the operator-configured `*OverwriteAllowed` regex against the raw `KEY=VALUE` job-variable string, then blindly splits and inserts whatever key the attacker supplies into the pod's labels/annotations/node selector map, with no restriction on the key itself. If an operator sets a permissive value-oriented regex (e.g. `.+` or a value-format pattern), a job can set `KUBERNETES_POD_LABELS_X=runner.gitlab.com/some-label=value` or `KUBERNETES_NODE_SELECTOR_X=node-pool=restricted` and have that literal key injected into the pod spec.

### Finding Description
In `evaluateMapOverwrite` (executors/kubernetes/overwrites.go:659-696), for each job variable whose key has the `KUBERNETES_POD_LABELS_`/`KUBERNETES_NODE_SELECTOR_`/`KUBERNETES_POD_ANNOTATIONS_` prefix, the code does: [1](#0-0) 
1. Check `overwriteRegexCheck(regex, variable.Value)` — the regex is matched against the **entire** `variable.Value` (i.e., the whole `key=value` payload for pod-labels/annotations/node-selector, since `splitMapOverwrite` hasn't run yet).
2. Call `split(variable.Value)` (`splitMapOverwrite`) to break it into `key, value` on the first `=`.
3. Insert `finalValues[key] = value` unconditionally.

There is no separate validation, allow-list, or reserved-prefix check applied to `key` after the split. The regex configured by the operator (`PodLabelsOverwriteAllowed`, `NodeSelectorOverwriteAllowed`, etc.) is intended by operators to validate acceptable *label/annotation values*, but because it is applied to the raw pre-split string, an operator who (reasonably, per GitLab docs) writes a regex intended to constrain the value portion (e.g. `^[\w-]+$` matched loosely, or `.+`) does not — and structurally cannot cleanly — separately constrain the key. Nothing in this code path prevents the key from being `runner.gitlab.com/managed-by`, `kubernetes.io/hostname`-style reserved keys, or any node-selector key that happens to match labels used by administrator-restricted node pools (e.g. `node-pool=restricted-admin`), as long as the whole `key=value` string satisfies the configured regex.

### Impact Explanation
Whether this is exploitable depends entirely on the operator's configured regex — this is squarely a "permissive admin regex" scenario, which the question itself frames as a precondition. Given that precondition:
- Pod labels: an attacker could set a label like `runner.gitlab.com/<reserved-key>=<value>` if that whole string matches the regex, potentially spoofing labels that downstream tooling (RBAC selectors, network policies, ownership/ownership-based garbage collection, custom admission controllers) uses to make trust decisions about "runner-managed" pods.
- Node selector: an attacker could set `node-pool=gpu-privileged` or any label expected on tainted/admin-restricted nodes, steering scheduling onto nodes the operator intended to reserve, *if* those nodes are reachable via label-based node selectors and the cluster doesn't also enforce taints (node selectors alone do not bypass taints/tolerations, which are separately gated by `NodeTolerationsOverwriteAllowed`).

This is a real gap in defense-in-depth (missing reserved-key denylist/allow-list on the map key), but the actual exploitability is conditional on operator misconfiguration of the regex to be permissive over key=value pairs, and for node-selector to be a *practical* privilege escalation it also requires that scheduling onto the target node isn't blocked by a taint (since Kubernetes still requires toleration for tainted nodes) or other cluster-level admission control (e.g. Pod Security Admission, OPA/Gatekeeper) — none of which are Runner-enforced.

### Likelihood Explanation
- Precondition: operator has set `PodLabelsOverwriteAllowed`/`NodeSelectorOverwriteAllowed` to a permissive regex (documented as an operator responsibility — GitLab's own docs warn these regexes should be written carefully). This is explicitly given as a precondition in the question.
- Given that precondition, the exploit is trivially reachable by any pipeline author able to set CI/CD job variables, with no special privilege required.
- Repeatable: deterministic, no race conditions involved.

### Recommendation
Split the `key=value` pair before regex validation and validate the value only, then additionally enforce a Runner-owned denylist (not overridable by operator config) on keys, e.g. reject keys with the `runner.gitlab.com/` (or whatever internal domain Runner uses for its own management labels) prefix, and reserved Kubernetes label prefixes (`kubernetes.io/`, `k8s.io/`) for pod labels/annotations at minimum. For `node_selector`, consider documenting/enforcing that operators intending to gate scheduling should rely on taints/tolerations (already separately gated) rather than solely on node-selector regexes, since label-based node selection has no built-in reserved-key protection in Kubernetes itself.

### Proof of Concept
```go
func TestEvaluateMapOverwrite_RejectsReservedRunnerLabelKey(t *testing.T) {
    o := &overwrites{}
    vars := spec.Variables{
        {Key: "KUBERNETES_POD_LABELS_1", Value: "runner.gitlab.com/managed-by=attacker"},
    }
    logger := buildlogger.New(...) // test logger

    result, err := o.evaluateMapOverwrite(
        "PodLabels",
        map[string]string{},
        ".+", // permissive operator regex, matches value-format checks only
        vars,
        PodLabelsOverwriteVariablePrefix,
        logger,
        splitMapOverwrite,
    )

    require.NoError(t, err)
    // Expected (currently failing) assertion: reserved key must never be injectable
    _, exists := result["runner.gitlab.com/managed-by"]
    assert.False(t, exists, "attacker-controlled key in reserved runner.gitlab.com/ namespace was accepted")
}

func TestEvaluateMapOverwrite_NodeSelectorArbitraryKey(t *testing.T) {
    o := &overwrites{}
    vars := spec.Variables{
        {Key: "KUBERNETES_NODE_SELECTOR_1", Value: "node-pool=restricted-admin"},
    }
    result, err := o.evaluateMapOverwrite(
        "NodeSelector", map[string]string{}, ".+", vars,
        NodeSelectorOverwriteVariablePrefix, logger, splitMapOverwrite,
    )
    require.NoError(t, err)
    assert.Equal(t, "restricted-admin", result["node-pool"]) // demonstrates unrestricted key injection
}
```
These tests demonstrate that, under a permissive (but plausible/documented-as-operator-controlled) regex, `evaluateMapOverwrite` places attacker-chosen keys — including ones in a reserved-looking `runner.gitlab.com/` namespace or targeting node-pool selection — directly into the resulting map with no key-level guardrail.
