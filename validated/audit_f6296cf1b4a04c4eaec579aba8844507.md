### Title
Stale `instantWithdrawsRequestsByEpoch` entries cause instant-withdraw claims in the defaulted epoch to be double-counted, permanently freezing funded receipts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` balance; it never clears the per-epoch ledger `instantWithdrawsRequestsByEpoch[_user][epoch]`. When a user requests an instant withdrawal, claims it, and then requests another instant withdrawal **in the same epoch** that subsequently ends in a borrower default, `_claimDefaultedInstantWithdrawRequest` reads the full stale per-epoch amount (already-claimed + unclaimed) and subtracts it from the smaller aggregate balance, reverting via arithmetic underflow. The user's legitimately funded post-claim instant receipt becomes permanently unclaimable — a replay/double-counting analog of the referenced "same proposal executed twice" multisig bug, where the lack of a cleaned/unique per-request marker lets already-settled votes leak into a new tally.

### Finding Description
In `requestInstantWithdraw`, each request adds to both the aggregate and per-epoch ledgers:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:366-374
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

But `claimInstantWithdrawRequest` zeroes only the aggregate:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:387-392
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` are left populated — the same "vote count" that was already consumed. Later, if that same epoch is finalized as a default, `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest`, which uses `defaultRecoveryEpoch` as the lookup key:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:844-855
claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
instantWithdrawsRequests[_user] -= claimBasis;   // <-- underflows
pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
_burn(_user, claimBasis);
_transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```

Because instant requests and claims both occur *within* a running epoch (after `instantWithdrawDelay`), the sequence is realistic:

1. Epoch N running, instant withdrawals enabled. Attacker requests 100 via `requestInstantWithdraw` → `byEpoch[N] = 100`, `aggregate = 100`, receipt minted.
2. Attacker claims → `aggregate = 0`, but `byEpoch[N]` stays 100.
3. Attacker requests another 50 in epoch N → `byEpoch[N] = 150`, `aggregate = 50`.
4. Epoch N ends; borrower defaults; `finalizeDefault` sets `defaultRecoveryEpoch = N` and `defaultInstantWithdrawsFinalized = true`.
5. Attacker (or anyone via the CDO) calls `claimInstantWithdrawRequest` → `claimBasis = 150`, `instantWithdrawsRequests[_user] (50) -= 150` → arithmetic underflow → revert.

Every subsequent claim attempt reverts identically. The 50-underlying receipt — which was funded into the default recovery reserve — is permanently locked in the vault, and `_burn` is never reached, so the receipt tokens are stuck too. The same stale-ledger pattern exists for normal withdraws (`withdrawsRequestsByEpoch` is not cleared by `_claimFundedWithdrawRequest` at lines 338-345), though the instant path is the cleanest trigger because request and claim share the same epoch as the default.

### Impact Explanation
Permanent freezing of user funds: any funded or recovery-reserved instant-withdraw entitlement accumulated after a same-epoch claim becomes unclaimable forever. The funds remain in the strategy/reserve indefinitely; the user's receipt tokens cannot be burned and the accounting entries (`pendingInstantWithdraws`, `instantWithdrawClaimsByEpoch`) are left inconsistent. The loss equals the sum of all instant withdrawals requested after the user's first claim within the defaulted epoch.

### Likelihood Explanation
Medium-low. Requires: instant withdrawals enabled (`setInstantWithdrawParams`), the same user requesting again after claiming inside one epoch, and that epoch ending in a borrower default with `defaultInstantWithdrawsFinalized`. Defaults are rare but explicitly supported flows (`finalizeDefault`, `defaultRecoveryEpoch`), and the re-request-after-claim pattern needs no attacker privilege — any KYC-passing lender can hit it accidentally.

### Recommendation
In `claimInstantWithdrawRequest`, also clear the per-epoch entries for the epochs being paid out (e.g., delete `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` accordingly), or track a per-epoch "claimed" watermark so already-paid receipts cannot be re-aggregated into the defaulted-epoch basis. Apply the same cleanup to `withdrawsRequestsByEpoch` in `_claimFundedWithdrawRequest`.

### Proof of Concept
Foundry fork-style test (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testInstantClaimDoubleCountFreeze() external {
    _stopCurrentEpoch();                        // buffer
    _depositWithUser(address(this), 10000 * ONE_SCALE, false);
    // enable instant withdrawals
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);
    _startEpochAndCheckPrices(0);               // epoch running
    skip(101);

    // 1) request + claim instant withdraw in same epoch
    cdoEpoch.requestInstantWithdraw(100 * ONE_SCALE, address(AAtranche));
    cdoEpoch.claimInstantWithdrawRequest();

    // 2) request again in the same epoch
    cdoEpoch.requestInstantWithdraw(50 * ONE_SCALE, address(AAtranche));

    // 3) epoch ends in borrower default
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);                   // defaulted
    // finalizeDefault + finalize instant recovery (harness helpers)

    // 4) claim always reverts: 50 - 150 underflows
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest();
    // user's funded 50 underlyings are permanently frozen in the vault
}
```
