### Title
`check_block_has_valid_tenure` validates tenure canonicity against a sortition handle rooted at the proposal's own self-declared burn view instead of the node's true canonical Bitcoin tip - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
`NakamotoBlockProposal::check_block_has_valid_tenure` calls `db_handle.has_consensus_hash(tenure_id)` on a `SortitionHandleConn` whose `chain_tip` is derived from `NakamotoChainState::get_block_burn_view`, which for a tenure-start block returns the block's own `tenure_change.burn_view_consensus_hash` [1](#0-0) . Because the handle is rooted at exactly the tenure being checked, canonicity is only ever evaluated relative to that self-supplied tip, not the node's actual heaviest Bitcoin fork.

### Finding Description
The equality the code needs is: *"the sortition tip used to test canonicity of `tenure_id` == the node's real, currently-heaviest Bitcoin fork tip."* Instead, `check_block_has_valid_tenure` receives a `db_handle` built via:

```
get_block_burn_view(sortdb, self.block, parent_header) -> burn_view_consensus_hash
SortitionDB::get_block_snapshot_consensus(burn_view_consensus_hash) -> sort_tip snapshot
sortdb.index_handle(sort_tip.sortition_id) -> db_handle
check_block_has_valid_tenure(db_handle, tenure_id) -> db_handle.has_consensus_hash(tenure_id)
``` [2](#0-1) 

`get_block_burn_view` returns `tenure_change.burn_view_consensus_hash` straight from the proposed block when it carries a tenure-change payload, i.e. it is attacker-supplied for a tenure-start proposal [3](#0-2) . `SortitionDB::get_block_snapshot_consensus` returns whatever snapshot matches that consensus hash without any canonicity filter ("the snapshot may not be valid") [4](#0-3) . `index_handle` then builds a `SortitionHandleConn` whose `context.chain_tip` is fixed to that (possibly orphaned) sortition [5](#0-4) . All ancestry/ "canonical" checks on such a handle (`has_consensus_hash`, `get_ancestor_sort_id`) walk the MARF fork rooted at that fixed tip only — they never compare against the DB's actual heaviest fork.

This is structurally different from the real block-acceptance canonicity check used in consensus code, `validate_nakamoto_tenure_snapshot`, which explicitly re-derives the tip from `SortitionDB::get_canonical_burn_chain_tip(db_handle)` — the node's true canonical tip — before checking ancestry of the tenure snapshot [6](#0-5) . `postblock_proposal.rs`'s `check_block_has_valid_tenure` has no equivalent step; it substitutes the block's self-declared burn view for the canonical tip.

For a tenure-start proposal, `tenure_id` passed into `check_block_has_valid_tenure` is the block's own tenure consensus hash, which for a fresh tenure-change is the same sortition as `burn_view_consensus_hash`. Consequently `db_handle` is rooted at exactly the sortition being validated, making `has_consensus_hash(tenure_id)` trivially true regardless of whether that sortition has since been orphaned by a heavier, already-known competing Bitcoin fork sitting in the same `sortdb`. The check never asks "is this sortition still the node's canonical tip," only "is it an ancestor of itself."

### Impact Explanation
This breaks the canonicity/fail-closed guarantee that `postblock_proposal`'s `Ok(BlockValidateOk)` is supposed to certify: that the tenure is on the node's actual canonical Bitcoin fork. A signer treats this response as ground truth in `check_block_against_signer_db_state` and will sign a block for a tenure that the node's own sortdb already knows (via other, already-processed sortitions) is not the heaviest/canonical fork. This is a Critical chain-safety violation — a signer signing a non-canonical/orphaned-tenure block — matching the "signer signing an invalid, non-canonical block" impact category.

### Likelihood Explanation
Preconditions required: the attacker must win one sortition (achievable with their own BTC, no majority-signer or privileged role needed) and race a Bitcoin burn-fork so their own sortition is being/has-been orphaned by a heavier, already-broadcast competing fork that the node has already recorded in its `snapshots` table. The attacker then crafts and gossips a `BlockProposal` for their own (soon-to-be-orphaned) tenure. This requires precise timing around a natural Bitcoin fork/reorg window and only one signer slot plus normal gossip — no access to other signers' keys, the auth token, or local host access. It is repeatable whenever a burn fork/reorg window coincides with an attacker-won sortition.

### Recommendation
In `check_block_has_valid_tenure` (or its caller in `validate`), root the `SortitionHandleConn` at the sortdb's actual canonical burn chain tip (`SortitionDB::get_canonical_burn_chain_tip`), not at a tip derived from the proposal's own `burn_view_consensus_hash`, mirroring the approach used in `NakamotoChainState::validate_nakamoto_tenure_snapshot`. Additionally verify that the block's declared `burn_view_consensus_hash`/tenure sortition itself is an ancestor of that true canonical tip before trusting any ancestry checks performed within a handle rooted at it.

### Proof of Concept
Rust test plan (in `postblock_proposal` test module):
1. Build a `SortitionDB` test harness with two competing burn forks: fork A (attacker's winning sortition, tenure_id `CH_A`) and fork B (heavier, already fully processed/canonical in the sortdb, extending past A's parent).
2. Construct a `NakamotoBlock` whose `TenureChange.burn_view_consensus_hash == CH_A` and `header.consensus_hash == CH_A` (tenure-start block on the losing fork).
3. Call `NakamotoChainState::get_block_burn_view(&sortdb, &block, &parent_header)` — assert it returns `CH_A`.
4. Compute `sort_tip = SortitionDB::get_block_snapshot_consensus(sortdb.conn(), &CH_A)` and `db_handle = sortdb.index_handle(&sort_tip.sortition_id)`.
5. Assert `NakamotoBlockProposal::check_block_has_valid_tenure(&db_handle, &CH_A)` returns `Ok(())`.
6. Separately assert that `SortitionDB::get_canonical_burn_chain_tip(sortdb.conn())` is on fork B and that `CH_A` is NOT an ancestor of that true tip (e.g., via `get_ancestor_sort_id`), proving the "canonical" result in step 5 is against a non-canonical tenure — demonstrating the equality break.

    pub(crate) fn check_block_has_valid_tenure(
        db_handle: &SortitionHandleConn,
        tenure_id: &ConsensusHash,
    ) -> Result<(), BlockValidateRejectReason> {
        // Verify that the block's tenure is on the canonical sortition history
        if !db_handle.has_consensus_hash(tenure_id)? {
            warn!(
                "Rejected block proposal";
                "reason" => "Block's tenure consensus hash is not on the canonical Bitcoin fork",
                "consensus_hash" => %tenure_id,
            );
            return Err(BlockValidateRejectReason {
                reason_code: ValidateRejectCode::NonCanonicalTenure,
                reason: "Tenure consensus hash is not on the canonical Bitcoin fork".into(),
                failed_txid: None,
            });
        }
        Ok(())
    }
