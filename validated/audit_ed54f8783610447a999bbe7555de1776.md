### Title
Stale-rejection weight double-counted against fresh acceptance weight allows a signer's vote-switch to inflate/miscount aggregated block-response tallies - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener`'s `BlockStatus` tracks `total_weight_approved` and `total_weight_rejected` as two independently-guarded running sums. The `Accepted` branch guards its increment with `!block.gathered_signatures.contains_key(&slot_id)`, while the `Rejected` branch guards its increment with `block.responded_signers.insert(slot_id)`. Because `responded_signers` is shared and updated by *both* branches, a signer who rejects first is protected from being double counted on a later reject, but nothing ever removes that signer's weight from `total_weight_rejected` when they later legitimately accept (sign) the same block. The two accumulators are not mutually exclusive over time, so a single signer that changes its vote from Reject → Accept has its weight counted in *both* totals simultaneously, even though the project's own design says "a rejection is a revocable opinion" that should not persist once superseded by a signature.

### Finding Description
In `stackerdb_listener.rs`, the `Accepted` case does: [1](#0-0) 
- guarded by `!block.gathered_signatures.contains_key(&slot_id)`, and unconditionally also inserts into `responded_signers` afterward.

The `Rejected` case does: [2](#0-1) 
- guarded by `block.responded_signers.insert(slot_id)` returning `true` (i.e., first time this slot has responded at all).

The asymmetry: if signer `S` first rejects, `responded_signers` gains `S`'s slot and `total_weight_rejected += weight(S)`. If `S` later sends a valid `Accepted` (e.g., after reconsidering, or after a re-proposal that flips their decision per `should_reevaluate_reject_reason`/pre-commit re-evaluation in `stacks-signer/src/v0/signer.rs`), the `Accepted` branch's guard only checks `gathered_signatures` (not yet containing `S`), so `total_weight_approved += weight(S)` executes — but nothing ever decrements `total_weight_rejected`. `S`'s weight is now present in both cumulative totals at once.

This is structurally identical to the reported analog: `refresh_target_allocations` capped a *new* increment against `token_allocation_cap` without accounting for the *already-accumulated* `token_target_allocation`, allowing the sum to exceed the cap. Here, the "cap" is the total registered signer weight `self.total_weight`; the two running sums `total_weight_approved` and `total_weight_rejected` are supposed to be mutually exclusive per-signer contributions bounded by `total_weight`, but the accept-path increment is applied without checking (or clearing) the signer's prior contribution already counted in the reject-path sum. `total_weight_approved + total_weight_rejected` can therefore legitimately exceed `total_weight`, breaking the equality/bound the miner's coordinator logic in `signer_coordinator.rs` relies on when comparing these sums against `self.total_weight` and `self.weight_threshold`: [3](#0-2) 

### Impact Explanation
Because a signer's stale rejection weight is never retracted, `total_weight_rejected` can remain artificially inflated by weight belonging to a signer who has since produced a valid, verified signature (`Accepted`) for the very same block. Since the miner's rejection check (`block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight`) can be satisfied purely from this stale/double-counted weight, the coordinator can conclude the block has been rejected by a "blocking minority" (`SignersRejected`) even though the real, current set of distinct signer decisions no longer supports rejection — the miner is wedged away from following through on a block that a live majority (by current votes) actually wants to accept. Conversely, because there is no cross-check preventing counted weight from appearing in both buckets, the aggregated-weight accounting itself is not an accurate reflection of "verified distinct signer accepts/rejects", violating the aggregated-weight vs. verified-accepts equality this consensus mechanism depends on. This falls under the "High" impact bucket: a signer/coordinator path can be wedged based on stale, double-counted vote weight rather than the current, verified state of signer opinions.

### Likelihood Explanation
This requires only a single signer (one slot in a normal reward-cycle signer set) to send a `Rejected` message for a block and later a valid `Accepted` message (signature) for the same block-sighash — both are legitimate, individually-signed StackerDB messages a signer can produce naturally as part of the documented "reconsideration" flow (`should_reevaluate_reject_reason`, pre-commit re-evaluation after re-proposal) or simply via gossip replay of stale/late messages. No majority, no other signer's key, and no additional privilege is required — exactly matching the class of "one slot miner (plus gossip)" triggerable bugs in scope.

### Recommendation
Make the two weight accumulators mutually exclusive per signer slot. Track, per slot, which bucket (approved/rejected) last counted that signer's weight, and when a signer's vote changes, subtract their weight from the previous bucket before adding it to the new one — mirroring the fix pattern in the report: check the *existing* accumulated contribution for that signer before applying the new increment, rather than checking only a single unconditional map for the new response type. Concretely, when processing `Accepted`, if the slot is present in `responded_signers` but not yet in `gathered_signatures` (i.e., it previously only rejected), first `saturating_sub` its weight from `total_weight_rejected` before adding it to `total_weight_approved` (and analogously guard against re-processing a signer who already accepted, then later rejects, if that transition is intended to be permitted).

### Proof of Concept
1. Reward cycle with signers `S1..Sn`; miner proposes block `B` with sighash `H`.
2. `S1` (weight `w1`) sends `BlockResponse::Rejected` for `H`. `stackerdb_listener.rs` inserts `S1`'s slot into `responded_signers` and sets `total_weight_rejected = w1`.
3. `S1` later re-evaluates (e.g., due to a re-proposal or a chainstate-check flip covered by `should_reevaluate_reject_reason`/pre-commit path in `stacks-signer/src/v0/signer.rs`) and sends a valid `BlockResponse::Accepted` with signature for the same `H`.
4. In the `Accepted` handler, `block.gathered_signatures.contains_key(&slot_id)` is `false` (this is `S1`'s first accept), so `total_weight_approved` is incremented by `w1`. `total_weight_rejected` still equals `w1` from step 2 — it is never decremented.
5. Now `total_weight_approved + total_weight_rejected = 2*w1 + (other signers' weights)`, exceeding `self.total_weight`. Depending on the exact weight distribution, the miner's coordinator can observe `total_weight_rejected.saturating_add(weight_threshold) > total_weight` (spurious rejection) triggered purely by `S1`'s stale, already-superseded rejection weight, wedging the miner into treating the block as rejected by a blocking minority that no longer exists in the signers' current votes.
