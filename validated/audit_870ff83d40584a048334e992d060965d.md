### Title
`harvest()` reward swaps can be sandwiched by passing `_minAmount = 0` — no enforced slippage control on Uniswap reward sales - ([File: contracts/IdleCDO.sol])

### Summary
`harvest()` is a permissionless `nonReentrant` entry point whose caller supplies the `_minAmount` array used as `amountOutMinimum` when selling reward tokens on Uniswap V3. Any unprivileged user can call `harvest()` with `_minAmount[i] = 0`, giving the swap zero slippage protection, then sandwich the `exactInput` call to extract nearly the entire reward-sale value, permanently reducing gains distributed to AA/BB tranche holders via `_updateAccounting`.

### Finding Description
In `contracts/IdleCDO.sol`, `_sellReward` performs a Uniswap V3 `exactInput` swap where the only slippage bound is the caller-provided `_minAmount`, passed straight into `amountOutMinimum` [1](#0-0) . The multi-reward driver `_sellAllRewards` consumes attacker-controlled `_sellAmounts`, `_minAmount`, `_skipReward` and `_extraData` (the latter containing the swap path bytes) [2](#0-1) . If `_amount == 0` is passed for a reward, the contract sells its entire reward-token balance [3](#0-2) , and `_minAmount` is injected verbatim as `amountOutMinimum` [4](#0-3) .

This mirrors the DODO `externalSwap()` bug exactly: the external router call's protection depends entirely on user-supplied calldata, and the contract performs no sanity check (no oracle-based minimum, no `require(_minAmount[i] > 0)`, no post-swap balance check). Any accrued reward tokens in the IdleCDO contract (strategy reward tokens pushed to the CDO or claimable via `redeemRewards`) can be sold at a manipulated price. The swapped proceeds flow back to `address(this)` (`recipient: address(this)`), so the loss is socialized into `getContractValue`/`_virtualBalance` and hits tranche holders rather than the caller.

The swapped value feeds the NAV used by `_updateAccounting`/`_virtualPriceAux` to split interest between AA and BB [5](#0-4) , so slippage loss is a real, quantifiable reduction of distributable yield — theft of unclaimed yield by an unprivileged attacker.

### Impact Explanation
An attacker (any EOA; no role needed since `harvest` is externally callable) can extract nearly 100% of the value of pending reward-token sales in a single harvest: set `_minAmount` to 0, sandwich the `exactInput` swap across the reward→underlying pool, and the CDO receives far less underlying than fair value. The loss is borne by tranche holders through a reduced contract NAV, cutting accrued yield for AA/BB per the split ratio. This is direct theft of yield that would otherwise be distributed, satisfying the "theft of unclaimed yield" acceptance criterion.

### Likelihood Explanation
High whenever a CDO accumulates sellable rewards: the function is permissionless, the `_skipReward` flags let the attacker isolate the swap, `_sellAmounts = 0` sells the full balance, and `_extraData` lets them pick an illiquid multi-hop path through a pool they control or can cheaply manipulate, guaranteeing near-total extraction. No existing guard stops this: `nonReentrant` doesn't prevent same-tx sequencing, there is no KYC/`onlyOwner`/`onlyIdleCDO` gate on `harvest`, `_checkDefault` only detects strategy-price drops (not a bad reward swap unless it exceeds `maxDecreaseDefault`), and `liquidationTolerance`/`AmountTooLow` apply only to `_liquidate`, not `_sellReward` [6](#0-5) . The same flaw exists in all chain variants overriding `_sellReward` (`IdleCDOAvax`, `IdleCDOBase`, `IdleCDOArbitrum`, `IdleCDOOptimism`, `IdleCDOOPolygon`, `IdleCDOPolygonZK`), which copy the identical pattern [7](#0-6) . Caveat: I was unable to view the `harvest` function body itself within the iteration budget to confirm it has no caller whitelist; if `harvest` is gated to a trusted keeper, the severity drops to a documentation/robustness issue.

### Recommendation
Do not trust caller-supplied `_minAmount` in `_sellAllRewards`/`_sellReward`. Options:
- Enforce a sanity bound, e.g. `require(_minAmount[i] > 0)` plus a lower bound derived from an on-chain TWAP/oracle quote of the reward→underlying rate with a configured `maxSlippageBps`.
- Alternatively restrict `harvest` to the owner/keeper and treat `harvest` parameters as trusted input (defense in depth still recommends a floor check, as in the DODO recommendation `require(minReturnAmount > 0)`).
- Optionally verify `underlyingToken.balanceOf(address(this))` delta post-swap against an oracle-priced minimum.

### Proof of Concept
Foundry fork PoC (mainnet) sketch:

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";
import "../contracts/IdleCDO.sol";

contract HarvestSandwichTest is Test {
    IdleCDO cdo;            // forked live CDO with accrued reward tokens
    IERC20Detailed reward;  // e.g. reward token held by CDO
    IERC20Detailed underl;  // CDO underlying
    address attacker = address(0xBEEF);

    function test_sandwichHarvest() public {
        vm.createSelectFork(vm.envString("ETH_RPC_URL"));

        // 1. Attacker pushes down reward->underlying pool price (swap reward for underl, or
        //    manipulate the chosen pool in _extraData path).

        // 2. Attacker calls harvest with zero slippage protection:
        uint256[] memory sellAmounts = new uint256[](N); // 0 -> sell whole balance
        uint256[] memory minAmounts  = new uint256[](N); // all zero
        bool[]    memory skipRewards = new bool[](N);    // false for target reward
        bytes memory extraData = abi.encode(paths);      // attacker-chosen path

        vm.prank(attacker);
        cdo.harvest(false, false, true, sellAmounts, minAmounts, skipRewards, extraData);

        // 3. Back-run: restore pool price / capture the discounted reward tokens.
        // Assert: CDO received far less underlying than fair market value of the rewards sold;
        // getContractValue / virtualPrice(AA) decreased vs a harvest executed with a sane
        // amountOutMinimum, quantifying attacker profit as ~ value of rewards minus dust.
    }
}
```

On a mainnet fork of any live IdleCDO (or IdleCDOAvax/IdleCDOBase variants) holding reward-token balances, the attacker-held manipulated path plus `_minAmount = 0` deterministically yields the discounted swap; the delta between the oracle-fair value and the actual `exactInput` output is the stolen amount.
