### Title
`SortitionsView::reset_view` discards a locally-invalidated miner's status, letting a signer re-validate and sign for a miner it had already rejected - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::check_proposal` marks a sortition's `miner_status` as `InvalidatedBeforeFirstBlock`/`InvalidatedAfterFirstBlock` in memory when it detects misbehavior (tenure timeout, invalid parent-tenure choice, disallowed reorg, bad bitvec, etc.). This mirrors the reported pattern: a boolean/flag is cleared ("this miner may no longer be signed for") without cleaning up the fact that led to it. When the same code path later calls `self.reset_view(client)` (triggered whenever a proposal's consensus hash matches neither the tracked current nor last sortition), the entire `SortitionsView` is rebuilt from `client.get_current_and_last_sortition()` via `SortitionState::try_from`, which unconditionally sets `miner_status: SortitionMinerStatus::Valid`. If the "current"/"last" sortition pair returned by the node is unchanged (no new sortition has occurred), this silently restores the previously-invalidated miner back to `Valid`, even though the underlying misbehavior/timeout that caused the invalidation has not been re-checked or resolved.

### Finding Description
`SortitionMinerStatus` is the signer's local "policy" over a given sortition/miner: once set to `InvalidatedBeforeFirstBlock` or `InvalidatedAfterFirstBlock`, `check_proposal` is supposed to reject any further proposal from that miner via `RejectReason::InvalidMiner` / `RejectReason::ReorgNotAllowed`. [1](#0-0) [2](#0-1) 

This flag is set in several places inside `check_proposal` in response to a misbehavior condition (timeout, invalid parent tenure choice, etc.): [3](#0-2) 

However, whenever a proposal's consensus hash matches neither the tracked `cur_sortition` nor `last_sortition`, and `reset_view_if_wrong_consensus_hash` is true, the code discards the whole view and rebuilds it, then recurses into `check_proposal` again: [4](#0-3) 

`reset_view` re-fetches `current_sortition`/`last_sortition` from the node and wraps each with `SortitionState::try_from`, which always initializes `miner_status` as `Valid` — it does not look at, or preserve, any prior invalidation for that same sortition: [5](#0-4) [6](#0-5) 

Because `get_current_and_last_sortition` can return the *same* current/last sortition pair (no new sortition has necessarily happened between the invalidation and the reset — the reset is keyed only on "this proposal's consensus hash matches neither tracked sortition," which can legitimately occur for other reasons, e.g. a stale/duplicate proposal, a race with a fresh burn-block event, or a crafted proposal carrying an unrelated consensus hash to force the reset branch), the freshly rebuilt view re-marks the very same miner/sortition the signer had just invalidated as `Valid` again — with no re-verification of the timeout/reorg condition that caused the invalidation. This is the direct analog of the `removeContract` bug: the "disallow" flag is cleared, but the state that justified disallowing it (and that should gate whether it can become "allowed" again) is never re-derived; it is simply reset to the permissive default. This test explicitly documents that `check_proposal` behaves differently once `miner_status` is (or is not) `InvalidatedBeforeFirstBlock`/`InvalidatedAfterFirstBlock`, underscoring how load-bearing this field is for the accept/reject decision: [7](#0-6) 
There is also a dedicated regression test, `check_proposal_refresh`, that exercises exactly the `reset_view_if_wrong_consensus_hash` path — but it only asserts that the refreshed view *validates a legitimate proposal*; it does not exercise the case where the pre-reset view had already invalidated the current/last sortition's miner, so the loss of the invalidation is not covered: [8](#0-7) 

### Impact Explanation
This breaks the "verified-invalid vs. re-validated" equality that the signer's whole reorg-abuse and inactivity-timeout defenses rely on. A signer that correctly decided a miner was invalid (e.g. after `block_proposal_timeout` elapsed, or after detecting an unauthorized reorg attempt) can have that decision silently undone by an unrelated proposal that merely forces a `reset_view`, without the timeout/misbehavior condition being resolved. The signer can then sign a proposal from a miner it had already, correctly, decided to reject — a signer signing a block it should not have signed. Depending on the protocol-version path in use (this is the pre-global-state v1 chainstate path; global-state versions route this decision differently through `signer_state.rs`), this can contribute to a rejected/blocked tenure being resumed inappropriately, or to inconsistent local views across the signer set feeding into acceptance/rejection tallies.

### Likelihood Explanation
Reachable by a single miner (or by ordinary network conditions) without needing a majority of signers or any privileged access: any proposal whose consensus hash doesn't match the tracked current/last sortition drives the reset branch, and the node's `get_current_and_last_sortition` response can legitimately still be the same pair the signer just invalidated (e.g. no new sortition has occurred yet). No signer collusion, node compromise, or auth token is required — only a proposal or timing sequence that trips `reset_view_if_wrong_consensus_hash` while the previously-tracked sortition is still current/last.

### Recommendation
`SortitionState::try_from`/`SortitionsView::reset_view` should not unconditionally reinitialize `miner_status` to `Valid`. When rebuilding the view, the signer should re-derive `miner_status` for a sortition it already holds a record for (e.g., re-run the same timeout/parent-tenure/reorg checks that produced the original invalidation, or persist and carry over the invalidation from the prior view/signerdb) instead of defaulting to `Valid` purely because a fresh `SortitionInfo` was fetched from the node.

### Proof of Concept
1. A signer detects the current sortition's miner has exceeded `block_proposal_timeout` (or attempted a disallowed reorg) and sets `cur_sortition.miner_status = InvalidatedBeforeFirstBlock` inside `check_proposal` (`stacks-signer/src/chainstate/v1.rs:144-203`).
2. Before any new sortition occurs, the same miner (or a race condition) sends a block proposal whose `consensus_hash` matches neither the tracked `cur_sortition` nor `last_sortition` (e.g., a stale/duplicate proposal for a different, unrelated tenure id it also controls, or a delayed proposal race with a burn-block event).
3. `check_proposal` enters the `reset_view_if_wrong_consensus_hash` branch and calls `self.reset_view(client)` (`v1.rs:254-265`), which re-fetches `get_current_and_last_sortition()` — returning the *same* current/last sortition pair as before — and wraps each freshly as `SortitionMinerStatus::Valid` (`v1.rs:97-106`, `546-563`), erasing the earlier invalidation.
4. `check_proposal` recurses with the rebuilt view; the previously invalid miner's original (still-current) proposal is now re-evaluated with `miner_status == Valid` and can pass the check at `v1.rs:288-300`, so the signer signs a block from a miner it had already, correctly, invalidated.

    /// Reset the view to the current sortition and last sortition
    pub fn reset_view(&mut self, client: &StacksClient) -> Result<(), ClientError> {
        let CurrentAndLastSortition {
            current_sortition,
            last_sortition,
        } = client.get_current_and_last_sortition()?;

        let cur_sortition = SortitionState::try_from(current_sortition)?;
        let last_sortition = last_sortition
            .map(SortitionState::try_from)
            .transpose()
            .ok()
            .flatten();

        self.cur_sortition = cur_sortition;
        self.last_sortition = last_sortition;
        Ok(())
    }
