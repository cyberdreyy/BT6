### Title
Divide-Before-Multiply Precision Loss in `L1FeeParams::jovian_da_footprint` Understates Jovian DA-Footprint Gas - (File: `crates/common/l1-fees/src/params.rs`)

### Summary
`L1FeeParams::jovian_da_footprint` computes the Jovian DA-footprint gas by dividing the FastLZ-estimated compressed size by `1e6` *before* multiplying by `da_footprint_gas_scalar`, instead of multiplying first and dividing last. This is the same order-of-operations defect described in the external report (`bucket = timeElapsed / bucketSize; priceChange = bucket * slope`): truncating in the division step before the scaling multiplication understates the result relative to the mathematically precise `size * scalar / 1e6`.

### Finding Description
`tx_estimated_size_fjord` returns the estimated compressed transaction size pre-scaled by `1e6` (fixed-point). To convert this back to a real gas-relevant footprint, the code should multiply by the scalar first and divide by `1e6` last to preserve maximal precision, mirroring how `data_gas`, `calculate_tx_l1_cost_bedrock`, `calculate_tx_l1_cost_ecotone`, and `calculate_tx_l1_cost_fjord` all correctly do "multiply-then-divide" in this exact same file.

Instead, `jovian_da_footprint` divides by `1e6` first and multiplies by `scalar` second: [1](#0-0) 

Compare to the correctly-ordered sibling functions in the same file, e.g.: [2](#0-1) [3](#0-2) 

Any remainder of `tx_estimated_size_fjord(input) mod 1_000_000` is discarded by the early division and can never be recovered by the subsequent multiplication by `scalar`, whereas multiply-first would only discard the (much smaller, scalar-independent) remainder of `(size * scalar) mod 1_000_000`. Because `scalar` values are non-trivial (e.g., the protocol default is `400`, per `DaFootprintGasScalarUpdate::DEFAULT_DA_FOOTPRINT_GAS_SCALAR`), the truncation loss is effectively amplified by up to `scalar - 1` gas units per transaction compared to the correct calculation. [4](#0-3) 

This function is directly reachable by any unprivileged transaction sender: it is invoked during per-transaction resource metering in the block executor to enforce the Jovian DA-footprint budget against the block gas limit. [5](#0-4) 

### Impact Explanation
Because `jovian_da_footprint` systematically understates each transaction's true DA-footprint gas cost (by up to `scalar-1` units per tx due to early truncation), the aggregate `da_footprint_used`/`blob_gas_used` accounting across a block will be lower than the value that would result from the mathematically correct multiply-then-divide formula. This allows more transactions (or larger DA payloads) to be packed into a block than the Jovian DA-footprint resource-metering budget intends, directly undermining the block-building resource-metering safety mechanism that the Jovian upgrade introduces to bound L1 data-availability exposure per block. [6](#0-5) 

This is a systemic under-metering of a protocol-enforced resource limit (DA footprint vs. block gas limit) rather than a one-off rounding error, since it affects every transaction that goes through the Jovian DA-footprint check.

### Likelihood Explanation
The bug triggers on every Jovian-era transaction that is not fee-exempt (not empty, not a deposit) and whose FastLZ-estimated size (scaled by `1e6`) is not an exact multiple of `1e6` — which will be the case for essentially all real-world transaction sizes given `tx_estimated_size_fjord`'s intercept/coefficient formula. It requires no special crafting, malicious input, or elevated privilege; any regular signed transaction reaching the sequencer's block builder or node's block executor will exercise this path post-Jovian activation.

### Recommendation
Reorder the arithmetic in `jovian_da_footprint` to multiply by the scalar before dividing by `1_000_000`, consistent with the pattern already used elsewhere in the same file (`data_gas`, `calculate_tx_l1_cost_fjord`, etc.):
```rust
pub fn jovian_da_footprint(&self, input: &[u8]) -> u64 {
    let Some(scalar) = self.da_footprint_gas_scalar else {
        return 0;
    };
    U256::from(tx_estimated_size_fjord(input))
        .saturating_mul(scalar)
        .wrapping_div(U256::from(1_000_000u64))
        .saturating_to::<u64>()
}
```

### Proof of Concept
Given `tx_estimated_size_fjord(input) = 1_599_999` (i.e., 1.599999 compressed bytes scaled by `1e6`) and `da_footprint_gas_scalar = 400`:
- Current (buggy) order: `1_599_999 / 1_000_000 = 1` → `1 * 400 = 400`.
- Correct order: `1_599_999 * 400 = 639_999_600_000` → `/ 1_000_000 = 639_999`.

The buggy path reports a DA-footprint gas cost of `400` instead of the mathematically correct `639_999`, an understatement of over 1000x for this input, directly reducible via `L1FeeParams::jovian_da_footprint` (`crates/common/l1-fees/src/params.rs:90-98`) as consumed by the Jovian per-tx DA-footprint check in `crates/common/evm2/src/executor.rs:281-296`.
