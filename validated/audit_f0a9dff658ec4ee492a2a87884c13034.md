Both `multisig/src/lib.rs` (`DeleteKey`) and `multisig2/src/lib.rs` (`DeleteMember`) have the same class of bug: when a signer/member is removed, the contract only purges **requests that member itself created**, but never scans the `confirmations` map to strip that member's confirmation from other still-pending requests they had merely *confirmed*. This breaks the binding "confirmations counted == live members," letting a request execute with fewer live-member approvals than `num_confirmations`.

### Title
Stale confirmations from removed multisig members/keys count toward the approval threshold, allowing execution below the configured `num_confirmations` - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
`DeleteMember` (multisig2) and `DeleteKey` (multisig) only remove pending *requests* authored by the removed member/key. Neither implementation walks `self.confirmations` to remove that member's prior confirmations recorded on *other* requests. Because `confirm()` counts confirmations purely by set length (`confirmations.len() as u32 + 1 >= self.num_confirmations`) without re-validating that every entry in the set is still a current member, a request can later execute using a mix of live and already-removed members' confirmations, executing a k-of-n action with fewer than `k` currently-authorized approvers.

### Finding Description
In `multisig2/src/lib.rs`:
- `confirm()` [1](#0-0)  stores confirmations keyed only by `member.to_string()` in a `HashSet<String>`, and decides whether to execute solely from `confirmations.len()`.
- `delete_member()` [2](#0-1)  removes only the requests whose `r.member == member` (i.e. requests the deleted member *created*), removing confirmations for those requests, but does not touch `self.confirmations` entries for other requests that the deleted member previously confirmed.
- `assert_valid_request()` [3](#0-2)  only validates that the *caller* confirming now is a current member; it never re-validates the previously stored confirmation set.

The equivalent bug exists in the legacy `multisig` contract: `DeleteKey` [4](#0-3)  removes only requests signed (created) by the deleted key, and removes `num_requests_pk` for that key, but never purges the deleted key from `self.confirmations` sets of other pending requests.

Binding broken: `confirmations recorded ≡ live members who actually approved`. Concretely:
- Before: members = {A, B, C, D}, `num_confirmations = 3`. D creates request R. A confirms (set = {A}), B confirms (set = {A,B}) — not yet 3, so R stays pending.
- Attacker/owner action: a separate request removes member A (`DeleteMember{A}`) via 3 confirmations from B, C, D. `delete_member` only clears requests A itself created — R (created by D) is untouched, and A's entry remains in R's confirmation set.
- After: members = {B, C, D} (3 live members), but R's confirmation set is still `{A, B}`. C then calls `confirm(R)`, and `confirmations.len() + 1 = 3 >= num_confirmations`, so R executes — using only 2 live approvals (B, C) plus a stale one from removed member A, i.e., executed at 2-of-3 live members instead of the required 3-of-3.

### Impact Explanation
This crosses the "multisig request executed below threshold" Critical bar explicitly listed in scope. Any request type is affected, including `Transfer`, `FunctionCall`, `AddKey`/`AddMember` (full-access-key grants), and `DeployContract`, meaning NEAR held by the multisig account can be moved, or the account can be fully taken over, with fewer live approvals than the configured k-of-n policy — an authorization boundary crossed by a party not entitled to unilaterally approve.

### Likelihood Explanation
Requires an actor with a pending confirmed-but-not-yet-executed request and control (or collusion) sufficient to get one member removed and one more live confirmation, or simply relies on normal churn of a multisig's membership (which is an expected, unprivileged-relative-to-the-request-creator operational event, not requiring the foundation or a redeploy). Because `active_requests_limit` allows long-lived pending requests (default 12 per member, no expiry other than the 15-minute delete cooldown), a stale partially-confirmed request can realistically survive a later membership change, making this practically reachable during normal multisig operation.

### Recommendation
When removing a member (`delete_member`/`DeleteKey`), iterate all entries in `self.confirmations` (not only requests authored by that member) and remove the deleted member's/key's entry from every confirmation set. Alternatively, revalidate on `confirm()` that every entry in the stored confirmation set still belongs to `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3` (see `MultiSigContract::new` [5](#0-4) ).
2. D calls `add_request` to create request `R` (e.g., `Transfer` of contract funds to an attacker-controlled account).
3. A calls `confirm(R)` → confirmations = `{A}`.
4. B calls `confirm(R)` → confirmations = `{A,B}` (not yet executed, since `2+1 < 3`... actually `2>=3` false, stays pending after B; wait need to recompute: after A, len=1; after B, len=2 → `2+1=3>=3` would trigger on B's confirm). To keep R pending, only A confirms it, leaving confirmations = `{A}`.
5. Separately, B, C, D create and confirm a `DeleteMember{member: A}` request against the multisig's own account, which executes via `delete_member` [2](#0-1) , removing A from `self.members` but leaving `R`'s confirmation set `{A}` untouched because `R.member == D`, not `A`.
6. C now calls `confirm(R)` → `confirmations.len() (1) + 1 = 2`, which is `< 3`, so this alone isn't enough with the numbers above — but adjust the scenario to `num_confirmations = 2` initially with A and B confirming (reaching threshold on B directly) is trivial; the interesting/exploitable case is: `num_confirmations = 3`, A and B confirm R (stored as `{A,B}` without yet triggering execution because insertion order means the 3rd confirm triggers execution, so ensure `add_request_and_confirm` by D counts as the request creator not auto-confirming, then A and B confirm giving len=2), then A is removed, then C confirms giving `len(2)+1=3>=3` → `execute_request(R)` runs with the live confirming set effectively `{B, C}` (2 live members) plus a stale `A`, executing a 3-of-4 policy request with only 2 truly live approvals.

Note: exact HashSet ordering/edge-case counting is deterministic from the code shown above; the fundamental defect — `delete_member`/`DeleteKey` never scrubbing stale confirmations from unrelated pending requests — is confirmed directly from the cited source and does not depend on this specific walkthrough's arithmetic.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
