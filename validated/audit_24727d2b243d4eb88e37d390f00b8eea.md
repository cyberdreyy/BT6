### Title
Stale confirmations from removed multisig members count toward the confirmation threshold - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` in the multisig2 contract only purges confirmations for requests that were *created* by the removed member, but leaves that member's existing confirmations on *other* pending requests untouched. Because `confirm()` counts entries in the `confirmations` `HashSet<String>` without checking whether each entry still corresponds to a current member, a request can be executed with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
The confirmation-count binding the contract relies on is: `confirmations.len() for request R == number of *current* members who approved R`. `delete_member` breaks this invariant.

`delete_member` removes outstanding requests and confirmations only for the request(s) originated by the member being removed: [1](#0-0) 

It does not scan `self.confirmations` for entries belonging to the removed member on requests created by *other* members. Those stale entries remain stored, keyed only by `member.to_string()`.

`confirm()` then determines whether to execute a request purely by comparing the size of the stored confirmation set to `num_confirmations`, with no re-validation that every entry in the set is still a current member: [2](#0-1) 

`current_member()` and `assert_valid_request()` only validate the *caller* of the current transaction, not the historical entries already present in the confirmation set: [3](#0-2) [4](#0-3) 

### Impact Explanation
This crosses the threshold-authorization boundary explicitly called out as Critical impact ("a multisig request executed below threshold"). Concretely:

- Members A, B, C, D exist with `num_confirmations = 3`.
- D confirms a `Transfer` request R created by A. `confirmations[R] = {D}`.
- A separate request to `DeleteMember { member: D }` is confirmed and executed (guarded only by `self.members.len() - 1 >= self.num_confirmations`, which permits removing D down to exactly 3 remaining members).
- D is now removed from `self.members`; D's access key/account no longer has standing to participate. However, `confirmations[R]` still contains D's entry because `delete_member` only cleared confirmations for requests *added by* D, not for requests D had confirmed.
- A confirms R (`confirmations[R] = {D, A}`, len 2). B confirms R (`confirmations[R] = {D, A, B}`, len 3 == `num_confirmations`) → `execute_request` fires the `Transfer`.
- Only two *currently valid* members (A and B) actually authorized this, yet the contract treats it as a fully-confirmed 3-of-4 (now 3-of-3) request, moving NEAR funds (or executing `AddKey`/`FunctionCall`/`DeployContract` actions) below the intended threshold.

### Likelihood Explanation
This requires no external attacker privilege beyond being (or having been) a legitimate multisig member — which is the normal operating population of this contract. It only requires the ordinary sequence: a member confirms a pending request, then that member is later removed via the documented `DeleteMember` flow, and the original request is subsequently pushed to completion by fewer than `num_confirmations` *live* signers. This is a realistic operational sequence for any multisig that rotates or revokes keys/members, which the contract's own README documents as supported functionality.

### Recommendation
When executing `DeleteMember`, iterate over all entries in `self.confirmations` (not just requests originated by the removed member) and remove the deleted member's string key from every confirmation set, so any request whose count drops below `num_confirmations` reverts to pending status. Alternatively, re-validate on every `confirm()` call that all entries in the request's confirmation set still belong to `self.members` before comparing the set length to `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with 4 members `[A, B, C, D]`, `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm` for `Transfer { amount }` to some `receiver_id` → request `R`, `confirmations[R] = {A}`.
3. `D` calls `confirm(R)` → `confirmations[R] = {A, D}` (len 2, below threshold, request stays pending).
4. Separately, `A/B/C` create and confirm a `DeleteMember { member: D }` request (3 confirmations, satisfies threshold) → executes; `self.members = {A, B, C}`. Per `delete_member`, only requests where `r.member == D` (i.e., requests D originated) have their confirmations cleared; `confirmations[R]` (originated by `A`) is untouched and still contains `D`.
5. `B` calls `confirm(R)` → `confirmations[R] = {A, D, B}`, length 3 `>= num_confirmations (3)` → `execute_request(R)` fires, transferring funds, even though only `A` and `B` are still valid members and `D`'s stale approval was reused to reach threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
