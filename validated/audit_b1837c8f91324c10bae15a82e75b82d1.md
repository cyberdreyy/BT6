### Title
Missing RunnerID/SystemID (and job/project) authorization check in Docker executor's `resumeDependencies` allows cross-job container hijack via crafted `EnvironmentKey` - (File: executors/docker/docker.go)

### Summary
`common.EnvironmentKey` is documented as routing a resume "back to the same runner instance that issued the suspension" via `RunnerID`/`SystemID`, but that binding is enforced only inside the autoscaler wrapper (`validateEnvKey` in `executors/internal/autoscaler/executor.go`), not in the Docker executor itself. `executors/docker/docker.go`'s `resumeDependencies` parses the raw `EnvironmentKey` and immediately trusts `buildContainerID`/`helperContainerID` from it, without ever checking `key.RunnerID`/`key.SystemID` against the current runner, and without any job/project scoping at all.

### Finding Description
`Build.EnvironmentKey()` returns `b.Job.SuspendOptions.EnvironmentKey` verbatim when the `SuspendableEnvironments` feature flag is on [1](#0-0) . The Docker executor's own `Prepare()` reads this value directly and, if non-empty, calls `resumeDependencies()` instead of creating fresh containers [2](#0-1) .

`resumeDependencies()` only calls `common.ParseEnvironmentKey`, which validates *format* (numeric positive runner id, non-empty system id, parseable query string) but performs no comparison to the current runner/machine identity, then directly uses `fields.buildContainerID`/`fields.helperContainerID` to `ContainerInspect` and adopt containers, networks, and volumes: [3](#0-2) 

Compare this to the autoscaler package's `validateEnvKey`, which explicitly checks `key.RunnerID != runnerID` and `key.SystemID != systemID` before proceeding [4](#0-3) . That check exists **only** in the autoscaler wrapper; it is not part of `common.ParseEnvironmentKey` nor of the Docker executor's own logic. When the Docker executor runs standalone (the ordinary `docker` executor type, not `docker-autoscaler`/`instance`), which is the common configuration for shared runners, nothing enforces that the `EnvironmentKey`'s `RunnerID`/`SystemID` fields match the runner processing the job at all - any syntactically valid value is accepted.

Even when the autoscaler wrapper is present, its `validateEnvKey` only binds the key to the runner/machine (`RunnerID`+`SystemID`) and to an autoscaler-internal `acquisition-key`; it never scopes the embedded `build-container-id`/`helper-id`/`service-ids` fields to the specific job or project that owns those containers [5](#0-4) . Those raw Docker container IDs are read straight from attacker-controlled `Fields` and handed to `ContainerInspect`, `networksManager.Adopt`, and `volumesManager.Adopt` with no ownership/ACL check [6](#0-5) .

The result: whichever layer is in play, the only thing standing between "resume my own suspended job" and "attach to another job's containers on the same Docker host" is the unguessability of the raw 64-hex container ID (and, for the autoscaler path, the runner/system ID, which is explicitly documented and displayed as non-secret). There is no per-job or per-project token embedded in `EnvironmentKey` that `resumeDependencies` or `validateEnvKey` checks.

### Impact Explanation
If an attacker (a normal CI job author) can influence or supply the `EnvironmentKey`/`resume_from` string that the runner is given for their job, and knows (or leaks) the `build-container-id`/`helper-id`/`service-ids` of a *different* job's suspended containers on the same shared Docker-executor host, the runner will `ContainerInspect`, adopt the network mode, adopt the volumes, and restart/attach to those containers as if they belonged to the attacker's own job - i.e., cross-project/cross-job workload takeover, breaking the "job/session/trace/backend auth state must not let one job impersonate another" invariant. For the non-autoscaler `docker` executor case, this requires no correct `RunnerID`/`SystemID` at all, only knowledge of the container IDs.

### Likelihood Explanation
- The `SuspendableEnvironments` feature and `resume_from`/`SuspendOptions.EnvironmentKey` mechanism must be enabled (feature-flag gated), and this question's threat model already assumes the field is attacker-influenced job input.
- `RunnerID` and `SystemID` are explicitly documented as non-secret and shown in job logs / the runner admin page, so they present no real barrier for shared runners.
- The remaining barrier is knowledge of the target job's 64-hex Docker container ID (or its 12-char short-ID, which Docker's inspect API also accepts), which is not trivial to obtain remotely but can leak via container hostname defaults, `/proc`/`docker ps`-adjacent side channels on a shared host, or verbose logs - none of which the runner code defends against once the ID is known.
- The check that exists (`validateEnvKey`) is architecturally inconsistent: present in `executors/internal/autoscaler` but absent from `executors/docker`, so the same feature has two different trust postures depending on executor wiring - a real logic/consistency bug, not a theoretical one.

### Recommendation
- Move `RunnerID`/`SystemID` validation into `common.ParseEnvironmentKey` or a shared helper called unconditionally by every executor `Resume`/`resumeDependencies` path (not just the autoscaler wrapper), so the Docker executor cannot resume using a key issued for a different runner/machine.
- Bind `EnvironmentKey` (or its Docker-specific fields) to the issuing job/project (e.g., an HMAC over job ID/project ID with a runner-held secret, verified before trusting `build-container-id`/`helper-id`/`service-ids`), so knowledge of a raw container ID alone is insufficient to resume/adopt it.
- Add ownership/label verification in `resumeDependencies` (e.g., check a runner-set label on the container matching the requesting job/project) before `ContainerInspect`-driven adoption.

func TestResumeDependencies_DoesNotValidateRunnerOrSystemID(t *testing.T) {
    c := docker.NewMockClient(t)
    e := executorWithMockClient(c)
    require.NoError(t, e.dockerConnector.Connect(t.Context(), common.ExecutorPrepareOptions{}, e))
    e.Config = common.RunnerConfig{} // this runner's real RunnerID/SystemID
    e.Config.Docker = &common.DockerConfig{}
    e.Build = &common.Build{Runner: &common.RunnerConfig{RunnerCredentials: common.RunnerCredentials{ID: 1}, SystemID: "s_thisrunner"}}
    e.Build.Variables = append(e.Build.Variables,
        spec.Variable{Key: featureflags.SuspendableEnvironments, Value: "true"})
    // Attacker-crafted key: wrong RunnerID/SystemID, but valid container IDs
    // belonging to another job's suspended containers on the same host.
    e.Build.Job.SuspendOptions.EnvironmentKey =
        "999999/not-my-system-id/build-container-id=victim-build-cid&helper-id=victim-helper-cid"

    buildInspect := container.InspectResponse{ID: "victim-build-cid", HostConfig: &container.HostConfig{}}
    c.On("ContainerInspect", mock.Anything, "victim-build-cid").Return(buildInspect, nil).Once()
    c.On("ContainerInspect", mock.Anything, "victim-helper-cid").Return(container.InspectResponse{ID: "victim-helper-cid"}, nil).Once()

    // Expect success even though RunnerID/SystemID don't match this runner at all -
    // demonstrating the missing authorization check.
    err := e.resumeDependencies()
    require.NoError(t, err)
    assert.Equal(t, "victim-build-cid", e.buildContainerID)
}

func validateEnvKey(envKey string, runnerID int64, systemID string) (string, url.Values, error) {
	key, err := common.ParseEnvironmentKey(envKey)
	if err != nil {
		return "", nil, err
	}

	if key.RunnerID != runnerID {
		return "", nil, errors.New("environment key was not issued by this runner")
	}
	if key.SystemID != systemID {
		return "", nil, errors.New("environment key was not issued by this machine")
	}

	data, executorFields, err := parseEnvKeyFields(key.Fields)
	if err != nil {
		return "", nil, fmt.Errorf("environment key fields: %w", err)
	}

	return data.acqKey, executorFields, nil
}

// EnvironmentKey identifies a suspended environment. The runner produces it
// when suspending a job and parses it when a follow-up job resumes. The
// runner-id and system-id route the resume back to the same runner instance
// that issued the suspension; the fields carry executor-specific state.
//
// Format: <runner-id>/<url-encoded-system-id>/<url-encoded-fields>
type EnvironmentKey struct {
	RunnerID int64
	SystemID string
	Fields   url.Values
}

func (k EnvironmentKey) String() string {
	return fmt.Sprintf("%d/%s/%s", k.RunnerID, url.PathEscape(k.SystemID), k.Fields.Encode())
}
