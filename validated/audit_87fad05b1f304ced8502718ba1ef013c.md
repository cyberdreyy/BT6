### Title
Donation-inflated `getContractValue()` trips the guarded TVL `limit` and blocks all deposits — (File: contracts/IdleCDOCreditVault.sol)

### Summary
`GuardedLaunchUpgradable._guarded` enforces a global deposit cap (`limit`) using `getContractValue()`. In `IdleCDOCreditVault` (and its `IdleCDOEpochVariant`/`IdleCDOEpochVariantPrefunded` subclasses), `getContractValue()` adds the raw underlying token balance of the CDO contract — including unsolicited donations — to the strategy-token NAV. An unprivileged attacker can permanently push measured TVL above `limit` with a plain `token.transfer(cdo, dust)`, causing every subsequent `depositAA`/`depositBB` (and queue `requestDeposit` prefunding path) to revert with `ContractLimitReached` until the owner raises `limit` or an epoch start skims the donation. This is the direct analog of the reported "global limit manipulation" bug: a shared, globally accumulated statistic is polluted by an unprivileged transfer.

### Finding Description
`getContractValue()` counts raw underlying held by the contract: [1](#0-0) 

The deposit guard consumes this value directly: [2](#0-1) 

and every user deposit routes through `_guarded`: [3](#0-2) 

The donation-isolation defense is asymmetric: `_managedContractValue()` (used for `virtualPrice`/NAV) deliberately excludes raw token balance, so share pricing is safe, but `getContractValue()` — the value the TVL limit checks — still includes it. The only mitigation, `_skimDonatedAssets()`, runs solely inside `startEpoch`: [4](#0-3) 

During the buffer period (deposits open, `isEpochRunning == false`, epoch stopped/closed, or while the manager delays `startEpoch`), an attacker sends `limit - getContractValue() + 1` (or more) underlying directly to the CDO. The donation is never counted in NAV (no share-price theft), but it is counted for the guard, so all deposits revert. The prefunded queue path reverts identically (`testPrefundedRequestRespectsContractLimit` confirms `requestDeposit` applies the same `_guarded` check). The state persists until either the owner calls `_setLimit`/`setLimit` higher, or `startEpoch` is invoked — both privileged actions, exactly the "system remains in an undesired state until the smart contract owner intervenes" pattern in the report. The attacker permanently loses the donated tokens (they are skimmed to `feeReceiver` on the next `startEpoch`), so the griefing has a real cost, but for a vault with a meaningful cap the donation needed can be small relative to blocked deposit volume, and repeat attacks are possible after every skim if `limit` is tight.

### Impact Explanation
Temporary freezing of the deposit surface for all legitimate users, proportional to however long the owner/manager takes to intervene (raise `limit` or run `startEpoch`). New lenders cannot enter, prefunded queue deposits revert, and the borrower receives no new funding during the freeze. The attacker sacrifices only the donated amount; if `limit` is close to current TVL the cost is negligible.

### Likelihood Explanation
Requires only an unprivileged direct `token.transfer` to the CDO address (a "direct token sender" is explicitly in-scope). No privileged call, no KYC, no epoch precondition beyond the buffer period. Feasible whenever `limit > 0` and `limit - getContractValue()` is within the attacker's budget — the same "fill the shared quota" mechanic as the external report.

### Recommendation
Make the deposit limit consistent with NAV accounting: change `_guarded`'s basis to `_managedContractValue()` (which excludes raw token balance), or skim donated underlyings at the top of `_deposit`/`requestDeposit` before the `_guarded` check, so unsolicited transfers can never count toward the cap.

### Proof of Concept
Foundry fork PoC (requires `limit > 0`, buffer period):

```solidity
function testDonationTripsDepositLimit() external {
  uint256 limit_ = cdoEpoch.limit();
  require(limit_ > 0, "needs configured cap");

  // Attacker: top up measured TVL to/over the cap with a raw transfer
  uint256 headroom = limit_ - cdoEpoch.getContractValue();
  deal(address(underlying), attacker, headroom + 1);
  vm.prank(attacker);
  underlying.transfer(address(cdoEpoch), headroom + 1); // no skim during buffer

  // Victim deposit reverts
  deal(address(underlying), victim, 1e6);
  vm.startPrank(victim);
  underlying.approve(address(cdoEpoch), 1e6);
  vm.expectRevert(ContractLimitReached.selector);
  cdoEpoch.depositAA(1e6);
  vm.stopPrank();

  // Frozen until owner raises the limit or manager calls startEpoch (skim -> feeReceiver)
}
```
