## Finding: Confirmed, but the misrouting direction is reversed from what was hypothesized

Tracing `distribute_internal` and `switch_operator` in `staking_contract.move` shows the beneficiary-redirect check does break across an operator switch — but not in the direction the question describes.

### Why the literal hypothesis doesn't hold
`switch_operator` removes the `StakingContract` from the `Store.staking_contracts` map under the `old_operator` key and re-inserts the *same* struct (including its `distribution_pool`) under the `new_operator` key [1](#0-0) . After this, `assert_staking_contract_exists(staker, old_operator)` fails, so `distribute(staker, old_operator)` can no longer be called at all [2](#0-1) . The only reachable permissionless call is `distribute(staker, new_operator)`, which passes `operator = new_operator` into `distribute_internal` [3](#0-2) . Since the `recipient == operator` check inside `distribute_internal` compares the stored share recipient against this current key, it can never spuriously equal `new_operator` for shares that were bought in under `old_operator`.

### The actual bug: old_operator's pending commission bypasses old_operator's own beneficiary
During `switch_operator`, `request_commission_internal(old_operator, &mut staking_contract)` is invoked *before* the operator is swapped, so it records a distribution-pool share under `recipient = old_operator` and unlocks that commission via `stake::unlock_with_cap` [4](#0-3) [5](#0-4) . This amount is only `pending_inactive` at that point — it does not become withdrawable until the stake pool's lockup expires, so it survives the switch as an outstanding share in the pool.

Once the lockup expires, any unprivileged caller can invoke `distribute(staker, new_operator)`. Inside `distribute_internal`, the redeemed share's `recipient` is `old_operator`, but the function's `operator` parameter is now `new_operator` [6](#0-5) :

```move
if (recipient == operator) {
    recipient = beneficiary_for_operator(operator);
};
aptos_account::deposit_coins(recipient, coin::extract(&mut coins, amount_to_distribute));
```

Because `old_operator != new_operator`, this condition is false, so `beneficiary_for_operator(old_operator)` is **never consulted**. The commission that accrued during `old_operator`'s tenure is deposited straight to the raw `old_operator` account, silently bypassing any beneficiary `old_operator` had configured via `set_beneficiary_for_operator` [7](#0-6) .

### Impact
This does not let a bystander steal funds or redirect them to an unrelated third party — the coins still land in `old_operator`'s own account, which `old_operator` controls. However, it is a real, unprivileged-triggerable "beneficiary payout corruption that credits the wrong account" per the review's required-impact list: any operator who uses a beneficiary address for custodial/compliance separation (e.g., a staking-as-a-service provider routing commission into a separate treasury key) will have in-flight commission from before a `switch_operator` land in the operator's hot/validator key instead of the intended beneficiary, once any third party calls the permissionless `distribute()`.

### Recommendation
`distribute_internal` should resolve the beneficiary redirect based on whether `recipient` itself has a `BeneficiaryForOperator` mapping (i.e. check `exists<BeneficiaryForOperator>(recipient)` and redirect to `beneficiary_for_operator(recipient)`), rather than comparing `recipient == operator`, so that a stale operator identity captured in the distribution pool at switch time still resolves through its own beneficiary mapping.

### Note
The originally submitted hypothesis (funds from `old_operator`'s tenure being redirected to `new_operator`'s beneficiary) is not supported by the code — the `SimpleMap` key swap in `switch_operator` prevents that specific direction of misrouting. The verified bug is the inverse: the beneficiary redirect for `old_operator`'s pending commission is dropped entirely after a switch.

        operator: address,
