This is a strong analog to the Fenwick-tree griefing bug: a bounded, per-key (`signer_addr`) auto-evicting structure that is keyed by an attacker-controlled index (`signer_signature_hash`), so a small number of malicious/unsolicited block hashes can evict a legitimate entry recorded for that same signer under a *different* hash.

### Title
Pending-block-response eviction is keyed by `signer_signature_hash`, letting a malicious peer evict a legitimate signer's early vote before it is replayed - ([File: stacks-signer/src/signerdb.rs])

### Summary
`add_pending_block_pre_commit_response`, `add_pending_block_signature_response`, and `add_pending_block_rejection_response` store "early votes" (accept/reject/pre-commit) that arrive before the corresponding `BlockProposal` is known locally, keyed by `(signer_signature_hash, signer_addr)` [1](#0-0) . Each table carries an eviction trigger that, per `signer_addr`, keeps only the 3 most-recently-received rows and deletes the rest [2](#0-1) . These entries are only drained/replayed when the matching `BlockProposal` finally arrives, via `drain_pending_block_responses` inside `handle_block_proposal` [3](#0-2) .

### Finding Description
The eviction cap of 3 is applied per `(signer_addr)` globally across *all* block hashes, not per legitimate proposal context. Since `signer_signature_hash` is fully attacker-influenced (any gossiped `BlockResponse`/`BlockPreCommit` referencing an as-yet-unknown hash triggers `add_pending_block_*_response` for the sender's own signature, but any node observing and relaying such votes writes entries keyed by whatever hash is in the message), a party that can get 3+ distinct "untracked" responses inserted for a given `signer_addr` before the real proposal for the legitimate pending hash arrives causes the trigger to delete the oldest rows — which may be the legitimate signer's genuine early vote for a real, still-in-flight proposal. This mirrors the reported Fenwick pattern: a bounded per-key structure, filled by an outside actor operating on someone else's slot, causing legitimate data to be silently dropped rather than an explicit rejection.

Concretely: signer S sends an early `Accepted`/`Rejected`/`BlockPreCommit` for hash H1 (a proposal not yet locally known) before the miner's `BlockProposal` for H1 arrives. This gets stored via `add_pending_block_*_response(H1, S, ...)`. If, before the proposal for H1 shows up, three *other* distinct hashes are relayed with responses attributed to S (H2, H3, H4 — which can be replayed/gossiped stale messages, or a miner cycling through several rapid re-proposals each producing a fresh hash), the eviction trigger removes H1's row for S once a 4th insert for S occurs [4](#0-3) . When the real proposal for H1 finally arrives, `drain_pending_block_responses(H1)` returns nothing for S, so S's early vote is silently lost rather than replayed [5](#0-4) , [6](#0-5) .

The unit tests explicitly demonstrate this cross-hash eviction behavior (`test_signer_pre_commit_responses_eviction`, `test_signer_signature_responses_eviction`, `test_signer_rejection_responses_eviction`), confirming that inserting responses under 4 different block hashes for the *same* signer address evicts the oldest hash's entry regardless of whether that hash's real proposal has arrived yet [7](#0-6) .

### Impact Explanation
This is a liveness degradation rather than a signature-safety break: the dropped entry is only an "early vote" cache used to short-circuit re-evaluation when a proposal is later seen; losing it does not cause a signer to sign an invalid/non-canonical block, nor does it recount a rejection as an acceptance (each `insert_block`/`process_pending_responses_for_block` path still independently re-checks state). Its worst effect is that a legitimate early pre-commit/signature/rejection observation is dropped and must be naturally resent by the originating signer's own retry/gossip once the proposal is finally routed to it directly, or the signer simply re-evaluates on the next `BlockResponse`/`BlockPreCommit` broadcast it directly observes rather than through this pending cache. Given the strict rules for this repo (impact must be a concrete safety break or a genuine wedge into never signing valid blocks), this finding does not clearly rise to "signer wedged into never signing valid blocks" — normal gossip and periodic re-broadcast (pre-commit resend on `should_reevaluate_block`, or direct receipt of `BlockResponse`/`BlockPreCommit`) recovers the lost vote through other code paths, so there's no permanent wedge, only a transient delay in tallying weight for one specific block/signer pair.

### Likelihood Explanation
Triggering the eviction requires only gossip-reachable, correctly-signed-or-not-even-checked messages referencing fabricated/rapidly-changing block hashes attributed to a target signer's address in the "untracked" pending tables — no majority or privileged access is required, matching the one-slot/gossip constraint. However, because the drained cache is only an optimization (the signer re-derives its own opinion once it actually receives the real `BlockProposal`, and other signers' direct broadcasts are handled through `handle_block_response`/`handle_block_pre_commit`, not solely through this pending-cache replay), the practical likelihood of this causing an observable consensus/liveness delay of any significance is low to medium.

### Recommendation
Scope the per-`signer_addr` eviction quota independently per reward cycle or, better, avoid a global 3-entry cap across arbitrary hashes; instead bound the *table size* and evict by insertion time only among entries that are provably for a proposal the signer set actually knows about (or extend the retention window past the plausible max time between an early vote and proposal arrival). Alternatively, key the quota to be per-`(signer_addr, tenure/consensus_hash)` rather than a flat global 3, so that spoofed hashes unrelated to any real, currently in-flight tenure cannot evict pending entries tied to a live proposal.

### Proof of Concept
1. Signer S is expected to receive `BlockProposal` for hash H1, but the proposal is delayed (network jitter/reorg).
2. Attacker relays 3 additional `BlockResponse`/`BlockPreCommit` messages (any distinct fabricated hashes H2, H3, H4) that are attributed to S's address (values a receiving node's gossip layer stores via `add_pending_block_*_response`).
3. Per the eviction trigger, S's earliest entry (for H1) is deleted once the 4th distinct-hash entry for S is inserted, exactly as shown by `test_signer_pre_commit_responses_eviction` with blocks 0-4 [8](#0-7) .
4. When the real `BlockProposal` for H1 finally arrives and `drain_pending_block_responses(H1)` is called, S's early vote for H1 is gone, so it is not replayed into the fresh `BlockInfo` [3](#0-2) .

static CREATE_PENDING_PRE_COMMIT_RESPONSES_EVICTION_TRIGGER: &str = r#"
CREATE TRIGGER IF NOT EXISTS evict_old_pending_pre_commit_responses
AFTER INSERT ON signer_pending_pre_commit_responses
FOR EACH ROW
BEGIN
    DELETE FROM signer_pending_pre_commit_responses
    WHERE signer_addr = NEW.signer_addr
    AND (signer_signature_hash, received_time) IN (
        SELECT signer_signature_hash, received_time
        FROM signer_pending_pre_commit_responses
        WHERE signer_addr = NEW.signer_addr
        ORDER BY received_time DESC
        LIMIT -1 OFFSET 3
    );
END;

    /// Retrieve and clear all pending block response entries matching the given block signer_signature_hash
    /// Returns PendingBlockResponses containing all matching pre-commits, approval signatures, and rejections
    pub fn drain_pending_block_responses(
        &self,
        block_sighash: &Sha512Trunc256Sum,
    ) -> Result<PendingBlockResponses, DBError> {
        let hash_str = block_sighash.to_string();

        // Delete and return pre-commits in one operation
        let pre_commits_qry = "DELETE FROM signer_pending_pre_commit_responses WHERE signer_signature_hash = ?1 RETURNING signer_addr";
        let mut stmt = self.db.prepare(pre_commits_qry)?;
        let pre_commits_rows = stmt.query_map(params![&hash_str], |row| {
            let addr_str: String = row.get(0)?;
            let addr = StacksAddress::from_string(&addr_str).ok_or(
                SqliteError::InvalidColumnType(0, addr_str.clone(), rusqlite::types::Type::Text),
            )?;
            Ok(addr)
        })?;
        let pre_commits: Vec<_> = pre_commits_rows.collect::<Result<Vec<_>, _>>()?;

        // Delete and return signatures in one operation
        let signatures_qry = "DELETE FROM signer_pending_signature_responses WHERE signer_signature_hash = ?1 RETURNING signer_addr, signature";
        let mut stmt = self.db.prepare(signatures_qry)?;
        let signatures_rows = stmt.query_map(params![&hash_str], |row| {
            let addr_str: String = row.get(0)?;
            let sig_str: String = row.get(1)?;
            let addr = StacksAddress::from_string(&addr_str).ok_or(
                SqliteError::InvalidColumnType(0, addr_str.clone(), rusqlite::types::Type::Text),
            )?;
            let signature: MessageSignature = serde_json::from_str(&sig_str).map_err(|_| {
                SqliteError::InvalidColumnType(1, sig_str.clone(), rusqlite::types::Type::Text)
            })?;
            Ok((addr, signature))
        })?;
        let signatures: Vec<_> = signatures_rows.collect::<Result<Vec<_>, _>>()?;

        // Delete and return rejections in one operation
        let rejections_qry = "DELETE FROM signer_pending_rejection_responses WHERE signer_signature_hash = ?1 RETURNING signer_addr, reject_code";
        let mut stmt = self.db.prepare(rejections_qry)?;
        let rejections_rows = stmt.query_map(params![&hash_str], |row| {
            let addr_str: String = row.get(0)?;
            let reject_code: u8 = row.get(1)?;
            let addr = StacksAddress::from_string(&addr_str).ok_or(
                SqliteError::InvalidColumnType(0, addr_str.clone(), rusqlite::types::Type::Text),
            )?;
            let reject_reason = RejectReasonPrefix::from(reject_code);
            Ok((addr, reject_reason))
        })?;
        let rejections: Vec<_> = rejections_rows.collect::<Result<Vec<_>, _>>()?;

        let pending_block_responses = PendingBlockResponses {
            pre_commits,
            signatures,
            rejections,
        };
        if !pending_block_responses.is_empty() {
            debug!("Drained pending block responses for block {block_sighash}";
                "pre_commits_count" => pending_block_responses.pre_commits.len(),
                "signatures_count" => pending_block_responses.signatures.len(),
                "rejections_count" => pending_block_responses.rejections.len());
        }
        Ok(pending_block_responses)
    }

    #[test]
    fn test_signer_pre_commit_responses_eviction() {
        let db_path = tmp_db_path();
        let db = SignerDb::new(db_path).expect("Failed to create signer db");

        let signer = StacksAddress::p2pkh(
            false,
            &StacksPublicKey::from_private(&StacksPrivateKey::random()),
        );

        // Create 5 different block hashes
        let blocks: Vec<Sha512Trunc256Sum> =
            (0..5).map(|i| Sha512Trunc256Sum([i as u8; 32])).collect();

        // Add first 3 pre-commits from same signer for different blocks
        for block in blocks.iter().take(3) {
            db.add_pending_block_pre_commit_response(block, &signer)
                .unwrap();
            std::thread::sleep(std::time::Duration::from_secs(1));
        }

        // Check block 0 has the signer
        let responses = get_pending_pre_commit_responses(&db, &blocks[0]).unwrap();
        assert_eq!(responses.len(), 1, "Should have 1 signer for block 0");
        assert!(responses.contains(&signer));

        // Add 4th pre-commit from same signer to a different block - should evict oldest
        db.add_pending_block_pre_commit_response(&blocks[3], &signer)
            .unwrap();
        std::thread::sleep(std::time::Duration::from_secs(1));

        // Block 0 should now be evicted (oldest per signer)
        let responses = get_pending_pre_commit_responses(&db, &blocks[0]).unwrap();
        assert_eq!(
            responses.len(),
            0,
            "Block 0 should be evicted (oldest per signer)"
        );

        // Blocks 1, 2, 3 should still have the signer
        let responses = get_pending_pre_commit_responses(&db, &blocks[1]).unwrap();
        assert_eq!(responses.len(), 1, "Block 1 should have the signer");
        assert!(responses.contains(&signer));

        let responses = get_pending_pre_commit_responses(&db, &blocks[2]).unwrap();
        assert_eq!(responses.len(), 1, "Block 2 should have the signer");

        let responses = get_pending_pre_commit_responses(&db, &blocks[3]).unwrap();
        assert_eq!(responses.len(), 1, "Block 3 should have the signer");

        // Add 5th pre-commit - should evict block 1 now
        db.add_pending_block_pre_commit_response(&blocks[4], &signer)
            .unwrap();
        std::thread::sleep(std::time::Duration::from_secs(1));

        // Block 1 should now be evicted
        let responses = get_pending_pre_commit_responses(&db, &blocks[1]).unwrap();
        assert_eq!(responses.len(), 0, "Block 1 should be evicted");

        // Blocks 2, 3, 4 should still have the signer
        let responses = get_pending_pre_commit_responses(&db, &blocks[2]).unwrap();
        assert_eq!(responses.len(), 1, "Block 2 should have the signer");

        let responses = get_pending_pre_commit_responses(&db, &blocks[3]).unwrap();
        assert_eq!(responses.len(), 1, "Block 3 should have the signer");

        let responses = get_pending_pre_commit_responses(&db, &blocks[4]).unwrap();
        assert_eq!(responses.len(), 1, "Block 4 should have the signer");
    }
