### Title
Multisig executes requests with stale confirmations from removed members - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` only purges *outstanding requests created by* the removed member, but never purges *confirmations that member had already cast on other, still-pending requests*. Because `confirm()` counts entries in the `confirmations` set purely by size (`confirmations.len() as u32 + 1 >= self.num_confirmations`), a confirmation from an account that has since been removed from the multisig still counts toward the K-of-N threshold, allowing a request (including a fund `Transfer`) to execute with fewer live, currently-authorized members than `num_confirmations` requires.

### Finding Description
The intended invariant of the K-of-N multisig is: *a request executes only once K **currently valid** members have confirmed it* — i.e. `confirmations (live members) == num_confirmations`.

`confirm()` in `multisig2/src/lib.rs` never re-validates that previously recorded confirmers are still members before counting them: [1](#0-0) 

`delete_member` scrubs only the requests *authored* by the removed member (`r.member == member`), leaving intact any `confirmations` set entries that the removed member added to requests authored by someone else: [2](#0-1) 

So the sequence:
1. Multisig with members `{A,B,C,D}`, `num_confirmations = 3`.
2. Someone (any member) calls `add_request` for a `Transfer` (request `R`), and member `A` calls `confirm(R)` → `confirmations = {A}`.
3. Members execute a separate, legitimate `DeleteMember { member: A }` request (3-of-4) to remove `A` from the multisig (e.g. key rotation/offboarding). `delete_member` only deletes requests where `A` was the *author*; it does **not** touch `R`'s confirmation set because `R` wasn't authored by `A`.
4. `confirmations` for `R` still contains stale entry `A`, even though `A` is no longer in `self.members`.
5. Now only `B` and `C` (2 live members, not 3) call `confirm(R)`. `confirmations.len() + 1 >= 3` is satisfied by the stale `A` entry plus `B` and `C`, so `execute_request` fires the `Transfer`.

The `Transfer` (or any other action, e.g. adding a full-access key) is thus executed with only 2 genuinely authorized signers instead of the required 3 — a multisig request executed below the real threshold of live members. The identical structural bug class exists in the older `multisig/src/lib.rs` (keyed by `signer_account_pk` instead of `MultisigMember`), where `delete_key`/`remove_request`-style cleanup similarly only targets requests created by the deleted key, not confirmations the key placed elsewhere.

### Impact Explanation
This breaks the custody/authorization binding "confirmations counted == confirmations from live members," which is explicitly called out as in-scope. A `Transfer` request (or `AddKey`/`AddMember` compromising the whole account) can be pushed through with fewer live signers than the configured threshold, i.e. "a multisig request executed below threshold" — a Critical-severity impact per the given rubric, since it can move NEAR out of the account or hand out access with insufficient authorization.

### Likelihood Explanation
The vulnerable pattern requires: (a) a member confirms a request, (b) that member is subsequently removed via a normal `DeleteMember` governance action (a routine event — e.g. offboarding a departing member, rotating a compromised key), and (c) the pending request is later completed by the remaining members without anyone deleting/expiring it first. None of this requires any privileged role beyond normal multisig operation, and no code path currently prevents or even warns about it — `delete_member`'s comment only claims to clean up "outstanding requests by public_key," not confirmations given on foreign requests. Any member set change alongside outstanding requests is enough to trigger the flaw, making it a realistic operational hazard, not merely theoretical.

### Recommendation
When executing `delete_member` (and the analogous `delete_key` path in `multisig/src/lib.rs`), also purge the removed member's entries from `confirmations` sets on *all* pending requests, not just the ones it authored; alternatively, filter `confirmations` against `self.members` at the top of `confirm()`/`execute_request` before comparing against `num_confirmations`, so only confirmations from currently valid members are counted toward the threshold.

### Proof of Concept
```rust
// members = {A, B, C, D}, num_confirmations = 3
let request_id = <as B> c.add_request(transfer_request); // authored by B
<as A> c.confirm(request_id); // confirmations = {A}

// Separate legitimate governance action removes A (3-of-4 confirm)
<as B,C,D> execute DeleteMember{ member: A };
// delete_member only clears requests authored by A; `request_id` (authored by B) untouched,
// confirmations still = {A} even though A is no longer in self.members

<as B> c.confirm(request_id); // confirmations = {A, B}
<as C> c.confirm(request_id); // confirmations.len()+1 == 3 >= num_confirmations -> execute_request fires
// Transfer executes with only 2 live members (B, C) actually approving, not the required 3.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
