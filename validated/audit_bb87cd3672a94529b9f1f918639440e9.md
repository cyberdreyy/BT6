## Finding

### Title
Missing validation that `protocolFeeAmount + integratorFeeAmount < amount` in `createDstEscrow` causes a permanent arithmetic-underflow DoS in `EscrowDst._withdraw`, letting a malicious taker steal the maker's source funds while never delivering destination funds - (File: `contracts/BaseEscrowFactory.sol`, `contracts/EscrowDst.sol`)

### Summary
`BaseEscrowFactory.createDstEscrow()` accepts an arbitrary `IBaseEscrow.Immutables` struct — including its `parameters` field encoding `protocolFeeAmount`, `integratorFeeAmount`, and their recipients — directly from the calling taker, with no check that the fee amounts are bounded by `immutables.amount`. This is the direct analog of the reported `setRoyaltyInfo()` bug: an unbounded fee value is accepted without an upper-bound check against the base amount it is deducted from.

### Finding Description
On the source-chain path, `BaseEscrowFactory._postInteraction` explicitly guards against fee amounts exceeding the taking amount: [1](#0-0) 

However, `parameters` embedded in the *destination*-chain `Immutables` (`protocolFeeAmount`, `integratorFeeAmount`, recipients) are only assembled off-chain and passed by the caller of `createDstEscrow` — there is no equivalent check performed on-chain for the destination escrow: [2](#0-1) 

`createDstEscrow` has no access-control modifier, so any unprivileged address can call it and supply any `dstImmutables`, including a `parameters` blob where `protocolFeeAmount + integratorFeeAmount >= amount`.

These unvalidated values are later consumed in `EscrowDst._withdraw`, which unconditionally subtracts both fees from `immutables.amount`: [3](#0-2) 

Because the contract is compiled with Solidity 0.8's checked arithmetic, if `integratorFeeAmount + protocolFeeAmount > immutables.amount`, the subtraction at `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` underflows and reverts — for every future call to `withdraw` or `publicWithdraw` with the correct secret, since `immutables` (and hence the fee fields) are immutable per-escrow (bound into the CREATE2 salt via `ImmutablesLib.hash`). There is no mechanism to fix or bypass these values afterward.

Meanwhile, `EscrowDst.cancel` refunds the *full* `immutables.amount` back to the taker, uninfluenced by the broken fee fields: [4](#0-3) 

### Impact Explanation
A malicious taker can:
1. Fill the maker's order on the source chain normally (funding `EscrowSrc` as usual).
2. Call `createDstEscrow` themselves, supplying `dstImmutables.parameters` with `protocolFeeAmount + integratorFeeAmount >= amount`, funding the destination escrow with their own tokens/native currency (satisfying `msg.value`/`safeTransferFrom` checks, which do not reference the fee fields at all).
3. Once the maker (or any relayer) is convinced the destination escrow appears correctly funded and calls/attempts `withdraw`/`publicWithdraw` with the secret, the transaction reverts every time (arithmetic underflow) — yet the secret is exposed on-chain (in the reverted transaction calldata / mempool).
4. The attacker immediately uses the now-exposed secret to call `EscrowSrc.withdraw`/`withdrawTo`, draining the maker's source-chain tokens.
5. The destination escrow can never pay out to the maker (every withdraw call permanently underflows), and after the cancellation timelock the attacker calls `EscrowDst.cancel`, reclaiming their own deposited destination funds in full.

Net effect: the maker's source-chain funds are stolen and the maker never receives the corresponding destination-chain funds — this is direct theft of user funds in motion during the live swap lifecycle (Critical impact per bounty scope), and it is triggered purely by an unprivileged actor through the normal `createDstEscrow` entry point without any owner/governance/privileged-resolver assumption (since `createDstEscrow` has no access control).

### Likelihood Explanation
Likelihood is high: `createDstEscrow` is a permissionless, publicly documented entry point in the intended taker flow, and nothing in the contract validates that the caller-supplied `parameters` bytes correspond to sane fee values relative to `amount`. An attacker fully controls the `Immutables.parameters` blob for their own destination escrow deployment and needs no privileged role, front-running capability, or race condition — only ordinary participation as taker in a swap.

### Recommendation
In `createDstEscrow`, decode `protocolFeeAmount` and `integratorFeeAmount` from `dstImmutables.parameters` and revert (mirroring the existing `InvalidFeeAmounts` check in `_postInteraction`) if `integratorFeeAmount + protocolFeeAmount >= dstImmutables.amount`. Alternatively/additionally, add a defensive bound check inside `EscrowDst._withdraw` before performing the subtraction, and use `unchecked`-free but explicitly guarded arithmetic that reverts with a clear error rather than a bare underflow, ensuring the failure is caught at escrow-creation time rather than surfacing (and exposing the secret) only when withdrawal is attempted.

### Proof of Concept
1. Maker signs and taker fills a cross-chain order; `EscrowSrc` is deployed and funded normally via `_postInteraction`.
2. Taker (attacker) calls `createDstEscrow` with `dstImmutables.amount = X` and `dstImmutables.parameters = abi.encode(protocolFeeAmount = X, integratorFeeAmount = X, protocolFeeRecipient, integratorFeeRecipient)` (i.e., `protocolFeeAmount + integratorFeeAmount == 2X > X`), funding the escrow with `X` tokens/native currency as required by the `msg.value`/`safeTransferFrom` checks in `contracts/BaseEscrowFactory.sol` lines 165-185.
3. Maker/relayer later calls `EscrowDst.withdraw(secret, immutables)`: execution reaches `contracts/EscrowDst.sol` line 92 `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;`, which underflows and reverts on every call, forever, for that escrow (the secret becomes visible in the failed transaction regardless).
4. Attacker uses the leaked secret to call `EscrowSrc.withdraw`/`withdrawTo`, draining the maker's source funds.
5. After the destination cancellation timelock, attacker calls `EscrowDst.cancel`, per `contracts/EscrowDst.sol` lines 64-73, and recovers their own `X` tokens in full — the maker receives nothing on the destination chain.

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```

```text
    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```
