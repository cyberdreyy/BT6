### Title
External Initiator credential grants unrestricted job-run triggering for any job ID due to authenticated-user conflation - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` stores a synthetic `*clsessions.User{Role: UserRoleRun}` under `SessionUserKey` in addition to the actual `ExternalInitiator` under `SessionExternalInitiatorKey`. `PipelineRunsController.Create` gates its numeric-ID job-run trigger path solely on `auth.GetAuthenticatedUser(c)` returning `ok == true` ("isUser"), a check that is indistinguishable between a real user session/token and an EI session, and never reads or validates the authenticated `ExternalInitiator` (`GetAuthenticatedExternalInitiator`) against the job being triggered.

### Finding Description
In `core/web/auth/auth.go`, `AuthenticateExternalInitiator` (lines 119-151) sets both context keys: [1](#0-0) 
This makes `GetAuthenticatedUser(c)` (lines 178-187) succeed for EI-authenticated requests exactly as it would for a genuine session/token user.

In `core/web/pipeline_runs_controller.go`, `Create` (the `POST /v2/jobs/:ID/runs` handler) relies on that ambiguous check to decide whether to allow triggering a job by its numeric `ID`: [2](#0-1) 
The inline comment states "only users are allowed to run jobs using int IDs - EIs not allowed," but this is false in practice: because `AuthenticateExternalInitiator` also populates `SessionUserKey`, `isUser` is `true` for an EI-authenticated request too. The handler then calls `prc.App.RunJobV2(ctx, jobID, nil)` using only the job ID taken verbatim from the URL parameter (`c.Param("ID")`) — it never calls `auth.GetAuthenticatedExternalInitiator(c)` to confirm the authenticated EI is actually authorized for that specific job/initiator ID. Previously, webhook-run triggering by UUID enforced an EI-to-job binding, but that path was removed (`job.ErrJobTypeRemoved`), leaving the numeric-ID path as the only remaining trigger mechanism — and it has no EI-ownership check at all.

As a result, holding valid AccessKey/Secret credentials for External Initiator A is sufficient to trigger job runs for *any* job ID on the node, including jobs that belong to (or are meant to be restricted to) a different initiator B, or jobs with no EI association whatsoever.

### Impact Explanation
This is an authorization/role-bypass allowing unauthorized job-run triggering: a credential holder for one external initiator can trigger job runs owned by unrelated initiators/jobs, and can read back that run's result via `respondWithPipelineRun`. This matches the Chainlink bounty "unauthorized job run" impact class and violates the REQUEST_BINDING invariant (a request must be attributable to exactly one authorized initiator/job).

### Likelihood Explanation
Requires only a valid EI AccessKey/Secret pair (a low-trust, easily provisioned credential type) and knowledge/guessing of a target job's integer ID (job IDs are small sequential integers, easily enumerable). No admin or user-session access is needed. The exploit is a single authenticated HTTP POST, fully repeatable.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests authenticated via `AuthenticateExternalInitiator` for the numeric-ID trigger path (check `auth.GetAuthenticatedExternalInitiator(c)` presence and reject if set, rather than relying on `GetAuthenticatedUser`), or, if EI-triggered runs by ID are intended to be supported, validate that the resolved job's associated `external_initiator_id`/webhook spec matches `ei.ID` before calling `RunJobV2`. More broadly, stop overloading `SessionUserKey` for EI sessions so that `GetAuthenticatedUser` cannot be mistaken for real-user authentication in authorization checks.

### Proof of Concept
Handler-level integration test in `core/web/pipeline_runs_controller_test.go` style:
1. Create two External Initiators, A and B, each with valid AccessKey/Secret, and create Job J owned/associated with B (or simply any job J unrelated to A).
2. Send `POST /v2/jobs/{J.ID}/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to A's credentials (per `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`).
3. Assert current (vulnerable) behavior: HTTP 200 with a `pipelineRun` resource returned, proving A triggered job J despite no relation to A.
4. Expected/fixed behavior: HTTP 403/404, asserting the server rejects the cross-initiator run trigger.
