### Title
`depositDuringEpoch` mints tranche shares and forwards the full `_amount` to the borrower without measuring the actually received underlying — fee-on-transfer / non-standard ERC20 underlyings dilute tranche holders and insolvent the vault - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
In `IdleCDOEpochVariant.depositDuringEpoch`, the vault pulls underlyings via `_transferUnderlyingsFrom` but then computes prorated interest, mints shares, mints strategy tokens, and forwards `_amount` to the borrower — all using the nominal `_amount`, not the actual received balance delta. The base `_deposit` path correctly measures `balanceAfter - balanceBefore`; the mid-epoch path does not, so an underlying that takes a transfer fee (or returns less than requested) produces minted shares and a borrower payout backed by less collateral than accounted.

### Finding Description
The normal deposit flow defends against this bug class explicitly:

```solidity
// contracts/IdleCDOCreditVault.sol:203-206
uint256 _preBal = _contractTokenBalance(_token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
_minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, msg.sender, _tranche);
```

`depositDuringEpoch` (which is enabled only while `isEpochRunning` and in fixed-APR, non-programmable, non-AYS mode) drops that defense:

```solidity
// contracts/IdleCDOEpochVariant.sol:684-732
_transferUnderlyingsFrom(msg.sender, address(this), _amount);   // no pre/post balance check
uint256 interest = _calcInterest(_amount) * (remaining + buffer) / (epochDuration + buffer);
...
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
_mintShares(_tranche, msg.sender, _minted, _amount);
expectedEpochInterest += interest;
IdleCreditVault(strategy).mintStrategyTokens(_amount);          // mints strategy receipt tokens on phantom principal
_transferUnderlyings(_borrower(), _amount);                     // forwards the FULL nominal _amount to borrower
```

Three concrete discrepancies when `token` charges a fee (or short-pays) on transfer:

1. **Insolvent forwarding**: the vault received `_amount - fee` but calls `_transferUnderlyings(_borrower(), _amount)`, paying out `fee` more than it took in. The excess is drained from other depositors' idle underlyings sitting in the vault (buffer-period liquidity, pending-withdrawal funds, or instant-withdraw reserve).
2. **Share inflation**: `_minted` is computed on `_amount` plus interest on `_amount`, so the attacker receives tranche shares priced on principal never delivered.
3. **Strategy/accounting skew**: `mintStrategyTokens(_amount)` and `expectedEpochInterest += interest` record principal and yield that were never funded, corrupting `expectedEpochInterest`, the discounted end-price logic, and the fee split at `stopEpoch`.

Note `SafeERC20.safeTransferFrom` already reverts on a `false` return, so the first half of the USSD report is covered; the balance-difference half is not.

### Impact Explanation
During a running epoch, an unprivileged KYC'd lender (`isWalletAllowed` is the only gate) deposits `_amount` of a fee-on-transfer underlying. The vault immediately pays the borrower more than it received and mints the attacker shares for phantom principal plus phantom interest. The shortfall is socialized across all other tranche holders and any pending withdrawal liquidity: at epoch end the vault owes `expectedEpochInterest` and tranche redemptions that exceed collected assets — direct theft of up to the transfer-fee portion times deposited size, repeatable until vault liquidity is drained.

### Likelihood Explanation
Requires (a) an epoch-variant vault whose `token` is a fee-on-transfer / short-pay ERC20 (USDT's fee mode is the canonical example; vaults are deployed per-pool with arbitrary underlyings), and (b) `isDepositDuringEpochDisabled == false`, `isAYSActive == false`, `isProgrammableBorrower == false`, and a running epoch with existing tranche supply. Conditional but fully attacker-initiable once configured.

### Recommendation
Mirror the `_deposit` pattern: record `_preBal = _contractTokenBalance(token)` before `_transferUnderlyingsFrom`, compute `received = balance - _preBal`, and use `received` (not `_amount`) for `_calcInterest`, the `_minted` formula, `_mintShares`, `mintStrategyTokens`, and the borrower transfer. The same delta check should be applied to `IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest` (contracts/IdleCreditVaultWriteOffEscrow.sol:139-149), which likewise assumes full receipt of `_underlyings` before paying out `_underlyings - _totFee`.

```solidity
//    - vault receives 990_000e6 (1% fee)
//    - vault sends borrower 1_000_000e6  -> -10_000e6 vs other depositors

// 4. Repeat N times; then at stopEpoch / claimWithdrawRequest:
//    - attacker redeems shares at the full accounted price,

assertLt(vault.getContractValue(), vault.expectedEpochInterest() + lastNAV);
```

Every claim traces to `contracts/IdleCDOEpochVariant.sol:685-732` — the absence of the balance-delta check present in the sibling deposit paths (`contracts/IdleCDOCreditVault.sol:203-206`, `contracts/IdleCDO.sol:250-253`).
