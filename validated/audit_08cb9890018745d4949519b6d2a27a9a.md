### Title
Per-sender rate limiter can be bypassed via un-normalized `body.Sender` string casing - ([File: core/capabilities/webapi/trigger/trigger.go])

### Summary
The `allowedSenders` allowlist check in `processTrigger` normalizes the sender by parsing it into an `ethCommon.Address` and comparing its canonical `.String()` form, but the rate limiter check on the very next line uses the raw, un-normalized `body.Sender` string as the map key. An attacker with a single valid signing key can vary the hex-string casing/formatting of their own address across requests to generate distinct rate-limiter keys for what is cryptographically the same sender, defeating per-sender throttling.

### Finding Description
In `HandleGatewayMessage`, the sender address is parsed once via `ethCommon.HexToAddress(body.Sender)` [1](#0-0)  and passed into `processTrigger` as a strongly-typed `ethCommon.Address`.

Inside `processTrigger`, the allowlist check correctly uses the canonicalized address: [2](#0-1) 

However, immediately after, the rate limiter is keyed by the *raw, attacker-supplied* `body.Sender` string, not the normalized `sender.String()`: [3](#0-2) 

`ethCommon.HexToAddress` and `Address` equality (used implicitly for the allowlist match, since `sender.String()` always emits EIP-55 checksummed form) are agnostic to the input casing, `0x` prefix presence, or leading-zero padding of the hex string. This means many distinct raw strings (e.g. `0xabc...`, `0xABC...`, mixed-case variants) all decode to the identical `ethCommon.Address` and therefore pass signature verification and the `allowedSenders` check identically. But because the rate limiter's `Allow(body.Sender)` call uses the raw string as its bucket key, each casing variant is treated as a distinct sender for quota purposes, giving the attacker effectively unlimited independent rate-limit buckets for the same underlying identity — as long as the signature over the message body (which is verified against the recovered address, not a literal string match) remains valid for whatever casing is chosen. Signature validation (`msg.Validate()` in `core/services/gateway/api/message.go`) is not defeated by casing changes because Ethereum address recovery/verification is inherently case-insensitive at the byte level.

### Impact Explanation
This breaks the "quota/allowlist enforcement consistency" invariant: a single credentialed attacker (any holder of a valid signing key permitted to call the trigger, i.e., unprivileged relative to node/operator access) can flood a workflow trigger far beyond its configured `PerSenderRPS`/`PerSenderBurst` limits by simply rotating the casing/padding of their own address string across requests. This maps to a Denial-of-Service / rate-limit (quota) bypass impact class — enabling trigger flooding of a workflow's `web-api-trigger` channel and increased attack surface for probing workflow topics, resource exhaustion of the gateway/node trigger processing pipeline, and undermining a documented security control.

### Likelihood Explanation
Highly feasible and fully repeatable: the attacker needs only a single valid signing key already authorized in `allowedSenders` for the target workflow (a precondition explicitly allowed by the audit scope — "attacker holds any valid signing key"). No race conditions, timing, or infrastructure access are required; the attacker just needs to vary the string representation of their own address per request while producing a valid signature for each corresponding `body.Sender` value.

### Recommendation
Normalize the sender identity used as the rate-limiter key to match the allowlist check — use `sender.String()` (the canonical `ethCommon.Address` string) instead of the raw `body.Sender` when calling `trigger.rateLimiter.Allow(...)`:
```go
if !trigger.rateLimiter.Allow(sender.String()) {
```
Additionally, consider normalizing (or rejecting non-canonical) `body.Sender` earlier in `HandleGatewayMessage`/`ValidatedMessageFromReq` so all downstream consumers (rate limiter, `TriggerEventID` construction, logging) consistently use one canonical representation.

### Proof of Concept
Go unit test plan for `core/capabilities/webapi/trigger/trigger_test.go`:
1. Register a workflow trigger via `RegisterTrigger` with `AllowedSenders` containing a single checksummed address `0xAbC...` and a `RateLimiter` config with a small `PerSenderRPS`/`PerSenderBurst` (e.g., burst=1).
2. Construct N > burst signed `api.Message` requests, each with a valid signature for the same underlying private key, but with `body.Sender` set to distinct casing/hex-padding variants of the same address (e.g., lowercase, uppercase, EIP-55 checksummed).
3. Call `HandleGatewayMessage` for each message and capture responses via the gateway connector mock's `SendToGateway`.
4. Assert (failing on current code, passing after fix): after the fix, once the per-sender burst is exhausted, subsequent requests — regardless of `body.Sender` casing — receive `Status: "ERROR"` with a rate-limited error message; on current code, all casing variants return `Status: "ACCEPTED"` because each casing hits a fresh rate-limiter bucket.
