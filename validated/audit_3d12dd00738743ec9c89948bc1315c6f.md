## Title
Stale confirmations from removed multisig members are never purged, allowing requests to execute below the live-member confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member()` in `multisig2/src/lib.rs` only purges pending *requests that the removed member created*, but never purges *confirmations the removed member cast on other members' requests*. Since `confirm()` counts confirmation-set size against `num_confirmations` without re-validating that every entry in the set is still a current member, a request can be executed using a mix of live confirmations plus one or more "phantom" confirmations from accounts that have since been removed from the multisig. This lets a request (including a `Transfer`) execute with fewer *live* member approvals than `num_confirmations` requires.

### Finding Description
The equality that must hold for the K-of-N guarantee to be sound is:
`number of confirmations counted in confirm()` == `number of currently-live members who explicitly approved this specific request`.

`delete_member` breaks this invariant: [1](#0-0) 

It filters `self.requests` for requests whose `member` field (the *creator*) equals the member being deleted, and clears confirmations only for those requests:
```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```
This does not scan `self.confirmations` for entries where the removed member is a *confirmer* (but not the creator) of some other pending request. Those stale confirmations remain in the `HashSet<String>` stored per request.

`confirm()` never re-validates the members already present in the confirmation set — it only checks the current caller and the set's size: [2](#0-1) 

```rust

    ...
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    ...
```
`assert_valid_request()` also only checks that the *current caller* is a member, not that every confirmer already recorded in the set still is: [3](#0-2) 

As a result, a member who confirmed a request while still part of the multisig continues to count toward the threshold even after being removed via a separate, unrelated `DeleteMember` action.

### Impact Explanation
This maps to Critical impact: "a multisig request executed below threshold." An attacker (or colluding minority of members) can get a request — including a `Transfer` of NEAR funds owned by the multisig account — executed with fewer live, currently-authorized members having actually approved it than `num_confirmations` mandates. The custody binding the multisig is supposed to enforce (funds move only with K live members' consent) is broken because a removed member's stale approval is silently retained and counted.

### Likelihood Explanation
This requires only benign, expected multisig operations that already exist in the contract's API: adding a request, confirming it partially, and then executing an unrelated (properly-quorate) `DeleteMember` request for one of the partial confirmers before the first request reaches quorum. No privileged access beyond normal member actions and no owner/foundation cooperation beyond the multisig's own documented flows is needed; it is entirely reachable by members who are otherwise entitled to call `add_request`, `confirm`, and to participate in a `DeleteMember` request. Any multisig that rotates members over time (a normal operational pattern) is exposed whenever a member leaves while they have outstanding partial confirmations on other pending requests.

### Recommendation
When a member is deleted, iterate `self.confirmations` (not just `self.requests` filtered by creator) and remove the deleted member's entry from every confirmation set, or re-validate at `confirm()`-time that every account/key already in the confirmation set is still present in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
Setup: multisig with `num_confirmations = 3` and members `M1..M5`.
1. `M1` calls `add_request(R)` where `R` is `Transfer { amount }` to some receiver. `R.member = M1`, `confirmations[R] = {}`.
2. `M2` calls `confirm(R)` → `confirmations[R] = {M2}` (size 1, below threshold, not executed).
3. Separately, `M1`, `M3`, `M4` create and confirm a `DeleteMember { member: M2 }` request; it reaches 3 confirmations and executes `delete_member(M2)`:
   - `self.requests` is scanned for requests created by `M2` — `R` was created by `M1`, so it is untouched.
   - `M2` is removed from `self.members` and their access key (if key-based) is revoked.
   - `confirmations[R]` still equals `{M2}`.
4. `M3` calls `confirm(R)` → `confirmations[R] = {M2, M3}`, size 2, `2 + 1 >= 3` → **not yet**, wait for one more (still below threshold by count logic: `confirmations.len() as u32 + 1 >= num_confirmations` → `2+1=3>=3`, so this step alone already satisfies the check and `execute_request(R)` fires).

So in fact only `M1` (creator) and `M3` (confirmer) plus the stale `M2` are involved — the `Transfer` request executes with only 2 live members (`M1`, `M3`) having ever explicitly approved it post-removal, while `num_confirmations` is still configured as 3 and `M2` is no longer a valid member of the multisig at execution time.

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
