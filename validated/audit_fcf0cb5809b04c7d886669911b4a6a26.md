## Title
Missing `elasticity == 0` validation in fault-proof executor's Holocene/Jovian extra-data decoding causes division-by-zero panic — (File: `crates/proof/executor/src/util.rs`)

### Summary
The stateless L2 executor used by Base's fault-proof program decodes EIP-1559 base-fee parameters (`elasticity`, `denominator`) from a parent block header's `extra_data` field and validates only that the `denominator` is non-zero before constructing a `BaseFeeParams` struct that is later used as a divisor in base-fee computation. Unlike the equivalent logic in `crates/execution/chainspec/src/basefee.rs`, the executor's checks omit the symmetric `elasticity == 0` guard, allowing a crafted header to reach the base-fee arithmetic with a zero `elasticity_multiplier`, causing an integer division-by-zero panic — the same bug class as CVE-2026-7007 (checking one divisor field from untrusted on-disk/on-chain data but not the other).

### Finding Description
`decode_holocene_eip_1559_params_block_header` and `decode_jovian_eip_1559_params_block_header` in `crates/proof/executor/src/util.rs` decode `(elasticity, denominator[, min_base_fee])` from `header.extra_data()` and only reject `denominator == 0`: [1](#0-0) 

The resulting `BaseFeeParams { elasticity_multiplier: elasticity.into(), max_change_denominator: denominator.into() }` is returned unchecked for `elasticity == 0` and consumed by `active_base_fee_params` in `crates/proof/executor/src/builder/env.rs`, which feeds it into `calc_next_block_base_fee`/`next_block_base_fee` to compute the block's base fee: [2](#0-1) [3](#0-2) 

EIP-1559 next-base-fee computation divides the gas limit/gas used by `elasticity_multiplier` to derive the gas target; a zero `elasticity_multiplier` triggers an integer division-by-zero panic in Rust (a hard process abort), analogous to the trapped divide-by-zero fault in the Zephyr CVE.

By contrast, the sibling implementation used by the live execution-layer chain spec correctly validates **both** fields symmetrically: [4](#0-3) 

and the Engine API attribute validator (`ensure_well_formed_attributes`) also explicitly checks both directions: [5](#0-4) 

This shows the codebase's own design intent is that `elasticity == 0` combined with a nonzero `denominator` is an invalid, rejectable combination — but the fault-proof executor's `util.rs` copy of this logic (and its Jovian analogue) omits that half of the check.

### Impact Explanation
The `crates/proof/executor` crate is the stateless L2 block execution engine backing Base's fault-proof program (`base-proof-executor`), which is executed by dispute-game participants (challengers/proposers) when resolving output-root disputes. If a parent header's `extra_data` reaching this code path can encode `elasticity == 0` with `denominator != 0` (i.e., before/outside the engine-level `ensure_well_formed_attributes` guard that normally prevents this combination from being embedded into legitimately-produced headers), the executor panics during base-fee computation instead of returning a controlled error. This crashes the fault-proof program process, denying availability of proof execution/dispute resolution for that pipeline component — a Medium-severity DoS matching the CVE's impact profile (availability only, panic reachable purely through a malformed divisor field).

### Likelihood Explanation
The likelihood hinges on whether the fault-proof program processes header/extra_data content that has not already passed through the Engine API's `ensure_well_formed_attributes` double-sided zero check. Within the normal engine/attributes-validation flow (`crates/consensus/engine/src/attributes.rs`, `crates/execution/node/src/engine.rs`), this exact `elasticity == 0` case is defended against, which limits the practical reachability of this specific gap to the fault-proof/derivation-only code paths that reconstruct headers independently (e.g., `crates/proof/host/src/handler.rs::payload_attributes_from_l2_block`, which also decodes `extra_data` without any zero-elasticity guard). This is a structural inconsistency in the codebase (an incomplete safety check that exists correctly elsewhere) rather than a directly demonstrated end-to-end exploit chain from an unprivileged actor.

### Recommendation
Mirror the symmetric check already present in `crates/execution/chainspec/src/basefee.rs::base_fee_params_from_extra_data` inside `crates/proof/executor/src/util.rs`'s `decode_holocene_eip_1559_params_block_header` and `decode_jovian_eip_1559_params_block_header` (and in `crates/proof/host/src/handler.rs::payload_attributes_from_l2_block`): reject the decoded parameters whenever exactly one of `elasticity`/`denominator` is zero, returning a proper `ExecutorError`/`HostError` instead of allowing a zero `elasticity_multiplier` to flow into base-fee arithmetic.

### Proof of Concept
1. Construct a Holocene/Jovian `extra_data` byte sequence with `elasticity = 0` and `denominator != 0` (valid per `HoloceneExtraData`/`JovianExtraData` wire format — 9 or 18 bytes, version byte `0`/`1`).
2. Supply this as the `extra_data` of a header fed into `decode_holocene_eip_1559_params_block_header` / `decode_jovian_eip_1559_params_block_header` (e.g., via `crates/proof/host/src/handler.rs::payload_attributes_from_l2_block` fetching a crafted block from an RPC source, or via the stateless executor's `active_base_fee_params` on a reconstructed parent header).
3. Observe that the `denominator == 0` check passes (since denominator is nonzero) and a `BaseFeeParams` with `elasticity_multiplier == 0` is returned.
4. When `calc_next_block_base_fee`/`next_block_base_fee` in `crates/proof/executor/src/builder/env.rs` subsequently computes the gas target using this `elasticity_multiplier`, the division by zero panics the executor process.

pub(crate) fn decode_holocene_eip_1559_params_block_header(
    header: &Header,
) -> ExecutorResult<BaseFeeParams> {
    let (elasticity, denominator) = HoloceneExtraData::decode(header.extra_data())?;

    // Check for potential division by zero.
    // In the block header, the denominator is always non-zero.
    // <https://github.com/ethereum-optimism/specs/blob/main/specs/protocol/holocene/exec-engine.md#eip-1559-parameters-in-block-header>
    if denominator == 0 {
        return Err(ExecutorError::InvalidExtraData(Eip1559ValidationError::ZeroDenominator));
    }

    Ok(BaseFeeParams {
        elasticity_multiplier: elasticity.into(),
        max_change_denominator: denominator.into(),
    })
}

    fn next_block_base_fee(
        &self,
        params: BaseFeeParams,
        parent: &Header,
        min_base_fee: u64,
    ) -> Option<u64> {
        if !self.config.is_jovian_active(parent.timestamp()) {
            return parent.next_block_base_fee(params);
        }

        // Starting from Jovian, we use the maximum of the gas used and the blob gas used to
        // calculate the next base fee.
        let gas_used = if parent.blob_gas_used().unwrap_or_default() > parent.gas_used() {
            parent.blob_gas_used().unwrap_or_default()
        } else {
            parent.gas_used()
        };

        let mut next_block_base_fee = calc_next_block_base_fee(
            gas_used,
            parent.gas_limit(),
            parent.base_fee_per_gas().unwrap_or_default(),
            params,
        );

        // If the next block base fee is less than the min base fee, set it to the min base fee.
        // # Note
        // Before Jovian activation, the min-base-fee is 0 so this is a no-op.
        if next_block_base_fee < min_base_fee {
            next_block_base_fee = min_base_fee;
        }

        Some(next_block_base_fee)
    }

    /// Returns the active base fee parameters for the parent header.
    /// Returns the min-base-fee as the second element of the tuple.
    ///
    /// ## Note
    /// Before Jovian activation, the min-base-fee is 0.
    pub(crate) fn active_base_fee_params(
        config: &RollupConfig,
        parent_header: &Header,
        payload_timestamp: u64,
    ) -> ExecutorResult<(BaseFeeParams, u64)> {
        match config {
            // After Holocene activation, the base fee parameters are stored in the
            // `extraData` field of the parent header. If Holocene wasn't active in the
            // parent block, the default base fee parameters are used.
            _ if config.is_jovian_active(parent_header.timestamp) => {
                decode_jovian_eip_1559_params_block_header(parent_header)
            }
            _ if config.is_holocene_active(parent_header.timestamp) => {
                decode_holocene_eip_1559_params_block_header(parent_header)
                    .map(|base_fee_params| (base_fee_params, 0))
            }
            // If the next payload attribute timestamp is past canyon activation,
            // use the canyon base fee params from the rollup config.
            _ if config.is_canyon_active(payload_timestamp) => {
                // If the payload attribute timestamp is past canyon activation,
                // use the canyon base fee params from the rollup config.
                Ok((config.chain_op_config.post_canyon_params(), 0))
            }
            _ => {
                // If the next payload attribute timestamp is prior to canyon activation,
                // use the default base fee params from the rollup config.
                Ok((config.chain_op_config.pre_canyon_params(), 0))
            }
        }
    }
}

fn base_fee_params_from_extra_data(
    chain_spec: impl EthChainSpec,
    timestamp: u64,
    elasticity: u32,
    denominator: u32,
) -> Result<BaseFeeParams, EIP1559ParamError> {
    if elasticity == 0 && denominator == 0 {
        Ok(chain_spec.base_fee_params_at_timestamp(timestamp))
    } else if elasticity == 0 || denominator == 0 {
        Err(EIP1559ParamError::InvalidParams)
    } else {
        Ok(BaseFeeParams::new(denominator as u128, elasticity as u128))
    }
}
