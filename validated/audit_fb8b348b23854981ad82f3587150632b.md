### Title
Unchecked single-step `AuthorizeNonceAccount` instruction permanently locks nonce accounts and their lamports if set to an unreachable authority - (File: `programs/system/src/system_instruction.rs`)

### Summary
The System Program's `AuthorizeNonceAccount` instruction changes a durable nonce account's `authority` field in a single, unchecked step. Unlike the BPF Loader Upgradeable's `SetAuthorityChecked` instruction and the Stake Program's `authorize_checked` instruction — both of which require the *new* authority to co-sign the transaction as an explicit confirmation — `AuthorizeNonceAccount` only requires the *current* authority's signature. If the current authority supplies an incorrect or unreachable pubkey as the new authority (a typo, wrong keypair, or address for which no private key exists), the nonce account becomes permanently unusable: no further `AdvanceNonceAccount`, `WithdrawNonceAccount`, or re-`AuthorizeNonceAccount` instruction can ever succeed, and any lamports held in the account are locked forever. This directly mirrors the reported `uberOwner`/single-step-ownership-change bug class, which recommends a two-step "propose/claim" pattern to prevent lock-out from fat-fingered addresses.

### Finding Description
`authorize_nonce_account` in `programs/system/src/system_instruction.rs` only validates that the *current* authority (or the account itself pre-initialization) is present in `signers`; it never checks that the *new* authority pubkey is a valid, reachable key or requires it to sign: [1](#0-0) 

The instruction is dispatched unconditionally from `system_processor.rs`, with only the standard 1-account-count check — no additional confirmation step or "checked" variant exists for this instruction: [2](#0-1) 

This directly gates the account's future usability, since `WithdrawNonceAccount` and `AdvanceNonceAccount` (and any further `AuthorizeNonceAccount`) all check the signature of `data.authority`, which is the same field set by the vulnerable, unchecked instruction: [3](#0-2) 

By contrast, Agave's own BPF Loader Upgradeable program provides exactly the two-step mitigation recommended for this bug class: `SetAuthority` (single-step, unchecked) alongside `SetAuthorityChecked`, which requires the new authority to co-sign the same transaction, so a wrong/unreachable address transaction simply fails to be constructed/signed instead of silently bricking the account: [4](#0-3) 

The Stake Program similarly offers `authorize_checked`, which the CLI defaults to whenever a keypair (rather than a bare pubkey) is supplied for the new authority: [5](#0-4) 

The System Program has no equivalent `AuthorizeNonceAccountChecked` instruction — a grep for such a variant returns no results, confirming there is no built-in guardrail for this specific authority-transfer path.

### Impact Explanation
Durable nonce accounts are ordinary, unprivileged accounts created and controlled by any user (frequently used by exchanges, market makers, and off-chain signing services to hold pre-signed durable-nonce transactions and often funded with non-trivial lamport balances for rent-exemption and fee payment). A single incorrect `AuthorizeNonceAccount` transaction — reachable by any ordinary user through the standard CLI (`solana authorize-nonce-account`) or a hand-crafted transaction — irreversibly and permanently locks:
- All lamports held in the nonce account (no `WithdrawNonceAccount` path remains, since it also checks `data.authority`).
- The nonce account's usability as a durable-nonce mechanism (no `AdvanceNonceAccount` or further `AuthorizeNonceAccount` is possible).

This is a concrete, irreversible state/fund lock reachable from an ordinary transaction, matching the "concrete unauthorized fund or state mutation" impact bar, and is directly analogous to the reported `uberOwner` two-step-authority-change bug class.

### Likelihood Explanation
Low probability (requires user error: typo, wrong keypair, or copy-paste mistake when authorizing a nonce account) but the impact is total and irreversible for the affected account, exactly matching the original report's "low probability, high impact" characterization that the judge rated as Medium risk. The absence of any "checked" variant for this specific instruction (while the sibling Stake and BPF Loader Upgradeable programs both offer one) also reflects an inconsistency in the codebase's own established mitigation pattern.

### Recommendation
Add a `AuthorizeNonceAccountChecked` variant to `SystemInstruction`/`system_processor.rs`, following the same pattern already used by `UpgradeableLoaderInstruction::SetAuthorityChecked` and the Stake Program's `authorize_checked`: require the new authority account to be present in the instruction and to sign the transaction, so that a nonce account can never be authorized to a key whose private key is not held by the submitter. Update `solana-cli`'s `authorize-nonce-account` subcommand to default to the checked instruction (mirroring `stake-authorize-checked`) while still permitting the unchecked instruction for programmatic pubkey-only transfers via an explicit opt-out flag.

### Proof of Concept
1. Create and initialize a durable nonce account `N` with authority `A` (owned/controlled by the user), funding it with lamports.
2. As authority `A`, submit `system_instruction::authorize_nonce_account(&N, &A, &B)` where `B` is a pubkey the user does not control the private key for (e.g., a mistyped address or `Pubkey::new_unique()`), signed only by `A`. This succeeds because `authorize_nonce_account` only checks that `A` (the *current* authority) signed: [6](#0-5) 
3. Attempt `WithdrawNonceAccount` or `AdvanceNonceAccount` or another `AuthorizeNonceAccount` on `N` — all fail permanently with `MissingRequiredSignature` because the required signer is now `B`, an unreachable key, matching the check in `withdraw_nonce_account`: [7](#0-6) 
4. The lamports in `N` and the account's nonce functionality are now permanently inaccessible.
