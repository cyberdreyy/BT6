### Title
v1 `validate_tenure_change_payload` only checks `get_last_globally_accepted_block`, letting a signer double-sign two competing tenure-start blocks in the same tenure - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
In the v1 (`SortitionsView`) chainstate path, the duplicate-tenure-start guard in `validate_tenure_change_payload` only checks whether a block in the current tenure has been marked **globally** accepted before rejecting a second, competing tenure-change block for the same tenure. The v2 (`GlobalStateView`) equivalent checks the broader `get_last_signed_block` (locally OR globally accepted). This asymmetry means a v1 signer that has already locally accepted/signed one tenure-start block for a tenure, but has not yet observed it reach the global 70% threshold, has no proposal-time guard against signing a second, conflicting tenure-start block for the same tenure.

### Finding Description
`SortitionsView::validate_tenure_change_payload` (v1) ends with: [1](#0-0) 
which calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` and only raises `RejectReason::DuplicateBlockFound` if a block in the same tenure was already **globally** accepted.

By contrast, `GlobalStateView::validate_tenure_change_payload` (v2) does: [2](#0-1) 
using `get_last_signed_block`, which the surrounding comment explicitly states counts blocks that are "locally or globally accepted" — i.e., any block this signer has already signed, not just ones that reached global consensus.

The project's own architecture documentation confirms this is a real, acknowledged difference between the two code paths and calls out that the duplicate check is proposal-time-only and not re-run later: [3](#0-2) 

Because v1 gates on *global* acceptance, a v1 signer who has already produced its own signature over a tenure-start block B1 for tenure T (i.e., `mark_locally_accepted` fired, `signed_self` is set — see `handle_block_pre_commit` flow) but has not yet seen the network cross the 70% signature threshold for B1, will not reject a second tenure-change block B2 for the same tenure T at proposal time, because `get_last_globally_accepted_block` returns `None` until B1 is globally accepted. The signer can then proceed to also sign B2.

The doc's own section 5 walkthrough describes a backstop "own-tenure conflict guard" (`get_signed_conflicts` at pre-commit time) meant to catch exactly this gap, but it is explicitly scoped as covering "a conflict in this block's OWN tenure" as a silent, non-sticky check that can let a signature through once a conflict goes "stale," and it runs at the pre-commit-threshold step, not at proposal rejection. The v1-specific weakening of the primary `DuplicateBlockFound` check at the earlier, sticky rejection point removes one of the two independent layers of protection against equivocation for exactly the scenario (self-signed-but-not-yet-globally-accepted first block in a tenure) that the check exists to prevent.

### Impact Explanation
This falls under the "signer signing a conflicting block" Critical impact category: a single v1 signer can end up producing signatures over two different, competing tenure-start blocks (B1 and B2) for the same tenure, when the correct behavior is to sign at most one. If enough signers hit the same timing window (each has locally signed B1 but not yet observed the global 70% for B1) and then also sign B2, this can help either fork accumulate signatures, which weakens the equivocation guarantee that "at most one block per tenure/height gets a valid quorum signature," a core signer safety invariant described throughout the state-machine documentation (`docs/signer-flows.md` sections 3, 5, and 7).

### Likelihood Explanation
This requires only a single miner (or malicious actor gossiping a competing tenure-start block via StackerDB) proposing two tenure-start blocks for the same tenure in short succession — no majority of signers or another signer's key is needed. The trigger window is the gap between a signer locally accepting/signing its first block in a tenure and that block being observed as globally accepted, which routinely exists in normal operation (it's the time needed to collect and observe 70% of pre-commits/signatures across the network). This is a per-signer, always-reachable race rather than a rare edge case, though it depends on which chainstate version (v1 vs v2) the signer network has migrated to; v1 is the legacy/pre-nakamoto-refactor path and may still be in active use depending on deployment.

### Recommendation
Change `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` (as v2 does) instead of `get_last_globally_accepted_block`, so that a signer refuses to consider a second tenure-start block for a tenure it has already locally signed a block in, closing the gap between the sticky proposal-time rejection and the weaker global-only check.

### Proof of Concept
1. Signer (v1, `SortitionsView`) receives tenure-start block B1 for tenure T; it passes `check_proposal`, is submitted for node validation, and the signer proceeds through the pre-commit flow to `mark_locally_accepted` / signs B1 (`signed_self` set), broadcasting its signature. `get_last_globally_accepted_block(T)` is still `None` because global 70% has not yet been observed by this signer.
2. Before this signer observes B1 crossing the global signature threshold, the miner (or an equivocating actor) broadcasts a second tenure-change block B2, also citing tenure T's parent, satisfying `check_tenure_change_confirms_parent` and `check_parent_tenure_choice`.
3. `validate_tenure_change_payload` calls `get_last_globally_accepted_block(T)`, gets `None`, and does **not** return `RejectReason::DuplicateBlockFound`, so B2 passes `check_proposal`.
4. The signer submits B2 for validation and, absent the pre-commit-time own-tenure conflict guard catching it (which is documented as a "silent backstop," not guaranteed to trigger for every timing), can end up signing B2 as well, producing two valid signer signatures for competing blocks in tenure T.

*Note: I was unable to fully trace the exact conditions under which the pre-commit-stage backstop (`get_signed_conflicts`, `conflict_still_blocks`, `reorg_permit_stands` mentioned in `docs/signer-flows.md`) would or would not catch this specific v1 scenario, since `grep_search` for those identifiers in `stacks-signer/src/v0/signer.rs` and `stacks-signer/src/signerdb.rs` did not return the implementation before the tool budget was exhausted. This limits full end-to-end confirmation that the outcome reaches an actual double-signature rather than being caught by the backstop; the root-cause asymmetry between v1's and v2's `validate_tenure_change_payload` is confirmed directly from the source, and the documentation explicitly frames this as an intentional gap covered only by a separate, weaker mechanism.*
