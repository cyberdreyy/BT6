### Title
Address squatting via deterministic `sha256(owner_account_id)[..20]` derivation in `create()` lets an attacker permanently occupy a victim's lockup address with attacker-chosen minimal-deposit terms - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the lockup account id solely from `owner_account_id` via `sha256(owner_account_id)[..20].<factory>` and only validates `env::attached_deposit() >= MIN_ATTACHED_BALANCE`, with no check that the caller is entitled to create for that owner and no dependency of the address on deposit size, vesting schedule, or whitelist. Any unprivileged party can call `create(owner_account_id=victim, ...)` with the flat minimum deposit (3,500 NEAR) before the legitimate funder does, permanently claiming the victim's canonical NAME-derived account with attacker-chosen `lockup_duration`, `vesting_schedule`, and `staking_pool_whitelist_account_id`. Any subsequent legitimate `create()` call for the same `owner_account_id` fails at the `create_account()` action (account already exists) and is refunded, but the intended, larger grant can never be deployed at that address.

### Finding Description
The binding claimed broken: `LockupArgs` readable at `sha256(owner_account_id)[..20].<factory>` should equal the args of the grant the rightful funder authorized for `owner_account_id`; instead it can permanently equal the cheapest attacker-supplied args.

There is no check that `env::predecessor_account_id()` corresponds to `owner_account_id`, the foundation, or any other authorized party, and the derived `lockup_account_id` depends **only** on `owner_account_id` — not on deposit amount, vesting schedule, or caller. An unprivileged attacker can therefore call `create(owner_account_id=victim, lockup_duration=0, vesting_schedule=None, whitelist_account_id=attacker_controlled_or_default)` attaching exactly `MIN_ATTACHED_BALANCE` [2](#0-1) . This creates the account at `victim`'s deterministic address with the attacker's minimal args before the intended, larger grant creation.

When the legitimate funder later calls `create(owner_account_id=victim, ...)` with the real vesting schedule and a much larger deposit, the underlying NEAR `create_account()` action fails because the account already exists. The receipt fails as a whole (the batched `create_account/deploy_contract/transfer/function_call` are one action list), so `is_promise_success()` in `on_lockup_create` returns `false` [3](#0-2) , and the deposit is refunded to `predecessor_account_id`. The legitimate funder does not lose funds, but the victim's canonical lockup address is now permanently occupied by the attacker-chosen `LockupArgs` (owner still equals the victim, but duration/vesting/whitelist parameters were never chosen by the rightful creator), and there is no mechanism in this factory to retry at a different address for the same `owner_account_id`.

None of the existing guards prevent this: `assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, ...)` only bounds the minimum, not who may call or what parameters are attached; there is no `assert_owner`, `assert_called_by_foundation`, or any check that `predecessor_account_id == owner_account_id`.

### Impact Explanation
No NEAR is stolen from the legitimate funder (it is refunded), but a lockup contract is deployed at the victim's expected address with parameters (`lockup_duration`, `vesting_schedule`, `staking_pool_whitelist_account_id`, deposit size) that the rightful creator never chose — this matches the Critical category "a lockup deployed with parameters its rightful creator never chose." The victim's real grant can never be created at the deterministic address the factory always derives for their account id, since NEAR does not allow re-creating an existing account; the vulnerability is repeatable against any named victim account for a flat, fixed cost (`MIN_ATTACHED_BALANCE`) regardless of how large the intended grant is.

### Likelihood Explanation
The attack requires only: knowledge of the victim's `owner_account_id` (public, generally known ahead of a scheduled grant), 3,500 NEAR (`MIN_ATTACHED_BALANCE`) which is returned to the attacker as the balance of their own now-controlled-name lockup (not lost, just relocated to an account nominally owned by the victim but under attacker-chosen terms), and a single `create()` call. No special privileges, keys, or foundation access are needed, matching the "unprivileged attacker" threat model, and the attack is fully repeatable across any number of victims.

### Recommendation
Bind the derived `lockup_account_id` to more than just `owner_account_id`, and/or require that only the `foundation_account_id` (or the `owner_account_id` itself) can call `create` for a given `owner_account_id`, and/or check via `Promise::create_account` pre-flight (e.g. via a stored registry mapping `owner_account_id -> created`) before allowing arbitrary unprivileged callers to occupy an owner's canonical address.

### Proof of Concept
```rust
#[test]
fn test_squat_blocks_legitimate_grant() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker squats victim's address with minimum deposit and attacker-chosen args.
    context.predecessor_account_id = String::from("attacker.testnet");
    context.attached_deposit = MIN_ATTACHED_BALANCE; // exactly the minimum
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), 0u64.into(), None, None, None, None);

    context.predecessor_account_id = account_factory();
    context.attached_deposit = 0;
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    assert!(contract.on_lockup_create(
        lockup_account(),
        MIN_ATTACHED_BALANCE.into(),
        String::from("attacker.testnet"),
    ));

    // Legitimate funder later attempts the real, much larger grant for the same victim.
    context.predecessor_account_id = String::from("legit_funder.testnet");
    context.attached_deposit = ntoy(1_000_000); // orders of magnitude larger grant
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), YEAR.into(), None, None, None, None);

    // create_account fails because lockup_account() already exists -> callback sees failure.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = 0;
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let ok = contract.on_lockup_create(
        lockup_account(),
        ntoy(1_000_000).into(),
        String::from("legit_funder.testnet"),
    );
    assert_eq!(ok, false); // legitimate grant can never be created at victim's address
}
```
This demonstrates the attacker's fixed, minimal-cost call permanently occupies `sha256(victim)[..20].<factory>` with attacker-chosen `LockupArgs`, and the legitimate, larger grant is unconditionally blocked at that address regardless of its deposit size.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
