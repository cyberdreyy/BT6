## Title
Sensitive tokens preceded by an empty query parameter (`?=` or `&=`) bypass masking entirely - [File: common/buildlogger/internal/urlsanitizer/urlsanitizer.go]

## Summary
`URLSanitizer.Write` desynchronizes its parser state when a bare `=` immediately follows a `?`/`&` separator (i.e. an empty parameter name). This causes the leading separator that should mark the start of the *next* sensitive token to be consumed as part of the empty-key parse, so the real `tokenParamKeys` key that follows (e.g. `x-amz-credential`, `private_token`) is never recognized and its value is written to the log/trace completely unmasked.

## Finding Description
In `Write` [1](#0-0) , the fast path only looks for a leading `?`/`&` when `len(s.match) == 0`, and consumes exactly one such byte into `s.match` as the marker for "start of a candidate key". It then scans forward to the next `=`, `?`, or `&` to delimit the key name.

When the input contains `?=` or `&=` (an empty parameter name), the sequence is:
1. Fast path finds `?`/`&`, sets `s.match = ['?']` (or `['&']`), advances `n` past it.
2. Key-scan immediately hits the following `=` at offset 0, so `key := append(s.match, p[n:n+0]...)` yields just the separator byte with an empty name.
3. `tokenParamKeys[""]` is not found, so masking is not triggered, `s.match` is reset, and `n` is advanced **past the `=`** — landing directly at the start of the real key text (e.g. `x-amz-credential`) with **no leading `?`/`&` byte remaining in front of it** in the unprocessed buffer.
4. On the next loop iteration, the fast path's `bytes.IndexAny(p[n:], "?&")` scans for a *new* separator and finds none before the real key (since the one that would have marked it was already consumed in step 1-3). The real `key=value` is therefore skipped over as ordinary text via the `off == -1` early-exit at line 90-92, and ultimately flushed unmasked by the trailing `s.w.Write(p[last:n])` at line 147-149.

This is a genuine parsing/state-desync bug, not a documented limitation — `isParamEnd` (line 168-175) never fires because masking mode was never entered for the real token; the bug is upstream of it, in how the key-matching state machine treats a zero-length key.

Concretely, for input `?x-amz-credential=SECRET1&=x-amz-credential=SECRET2`, tracing the algorithm shows the output becomes:
`?x-amz-credential=[MASKED]&=x-amz-credential=SECRET2`
i.e. the first token is masked, but the interleaving `&=` desyncs the parser and the second, distinct sensitive token (`SECRET2`) is written verbatim. This matches the "interweaved tokens" pattern referenced by the existing test at [2](#0-1) , but that test does not cover the `&=`/`?=` empty-key-adjacent-to-real-key case, so this particular desync path is untested and unguarded.

`URLSanitizer` is wired into every job's build log stream via `Logger.wrap` [3](#0-2) , covering both the job's own stdout/stderr and Runner-emitted messages (e.g. cache/artifact download messages containing presigned S3 URLs with `x-amz-credential`/`x-amz-signature`/`x-amz-security-token`) written to the same executor-level stream.

## Impact Explanation
A pipeline author fully controls job script stdout (an attacker-controlled input to the trace stream). By echoing a string containing `&=` or `?=` immediately before or interleaved with a genuinely sensitive URL (own or reflected from a Runner/API message sharing the same stream, e.g. an S3 presigned cache/artifact URL), they can suppress masking for that following credential and leak `x-amz-credential`/`x-amz-signature`/`x-amz-security-token`/`private_token`/`authenticity_token` values in job logs — a concrete violation of the "secrets must not leak in logs/traces" invariant.

## Likelihood Explanation
Fully deterministic and reachable with a single crafted string; no timing/race is required to demonstrate the bug in isolation (it reproduces with one `Write` call). Feasibility of leaking a *specific* Runner-held credential depends on the attacker being able to place the `&=`/`?=` marker immediately adjacent to that credential's occurrence in the same trace stream, which is plausible since job stdout and Runner-generated cache/artifact messages share the same `wrap`-ed writer chain.

## Recommendation
Fix the key-matching state machine so that an empty key name (offset `0` between the separator and the next `=`/`?`/`&`) does not consume the separator byte. Specifically, when `len(key[1:]) == 0`, `s.match` should be reset without advancing past the discovered `=`/`?`/`&` in a way that drops the separator — instead, re-scan from the position of that character so it can still serve as the marker for the next candidate key (similar to how the existing double-`&`/double-`?` bail-early paths at line 114-119 correctly preserve the separator for re-scanning).

## Proof of Concept
Add to `urlsanitizer_test.go`'s `TestMasking` table:
```go
{
    input:    "empty key before real key: http://example.com/?x-amz-credential=SECRET1&=x-amz-credential=SECRET2",
    expected: "empty key before real key: http://example.com/?x-amz-credential=[MASKED]&=x-amz-credential=[MASKED]",
},
{
    input:    "empty key at start: http://example.com/?=x-amz-credential=SECRET2",
    expected: "empty key at start: http://example.com/?=x-amz-credential=[MASKED]",
},
```
Running `go test ./common/buildlogger/internal/urlsanitizer/...` against the current implementation is expected to FAIL: the actual output for both cases will contain the literal `SECRET2` unmasked instead of `[MASKED]`, confirming the desync bug. A fuzz test (`FuzzMasking`, extending the existing fuzz harness in `build_logger_fuzz.go`) can additionally assert that for any two distinct `tokenParamKeys` joined with `0/1/2` separators including an `=` immediately after `?`/`&`, both secret values are absent from the sanitized output.
