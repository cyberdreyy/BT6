### Title
Builder Pending Withdrawal Pays Full Requested Amount to the Execution Layer While Beacon State Only Debits the Capped Balance — Gwei Created From Nothing (`specs/gloas/beacon-chain.md`, builder withdrawal processing in `process_withdrawals`)

### Summary
In Gloas, when a `BuilderPendingWithdrawal` requests more Gwei than the builder's current `balance`, the beacon state correctly caps the *debit* to `min(amount, balance)`, but the `Withdrawal` object appended to `state.payload_expected_withdrawals` — which is what the execution layer actually credits to the recipient's address — carries the full, uncapped requested `amount`. This breaks the equality "Gwei paid out on the EL == Gwei removed from the payer on the CL," effectively minting ETH out of thin air for the `fee_recipient`.

### Finding Description
`BuilderPendingWithdrawal.amount` represents a *requested* payout amount, and `builder.balance` is decremented by `min(amount, balance)` so the builder's on-chain balance can never go negative: [1](#0-0) [2](#0-1) 

However, the resulting `Withdrawal` object placed into `state.payload_expected_withdrawals` (the list committed to the execution payload and paid out by the EL) uses the *requested* amount, not the capped amount actually removed from the builder. This is explicitly demonstrated by the spec's own test suite: [3](#0-2) 

The test sets `builders[0].balance = 1 ETH` and a pending withdrawal requesting `5 ETH`, then asserts the *output* withdrawal carries `amount = 5 ETH` (the requested amount) while `builders[0].balance` is reduced only to `0` (a debit of `1 ETH`, capped by `min()`): [4](#0-3) 

The same pattern repeats with realistic (non-round) bounds, confirming it is systematic rather than a rounding artifact: [5](#0-4) 

The independent test-helper invariant used to check balance deltas confirms the CL-side debit is capped via `min()`, separately from whatever amount is written into the emitted `Withdrawal`: [6](#0-5) 

This is the direct analog of the reported bug class: just as `_processTokenTransfers()` in the external report clamps one side of a payment (`pulseFee = amount`) without reconciling the other side (`solverAmount`), here the CL clamps the *debit* side (`builder.balance -= min(amount, balance)`) without clamping the *credit* side (`Withdrawal.amount`) that the execution layer will actually pay out. The two sides of the same transfer disagree, and the disagreement favors creating unbacked Gwei rather than merely shorting a recipient.

### Impact Explanation
This falls under the Critical impact category "Gwei created, destroyed, or paid to a non-owner." If a builder's registered balance drops below the sum of its queued pending withdrawal requests (e.g., due to prior slashing, prior withdrawals, or simply an over-large withdrawal request being queued), the execution layer will credit the withdrawal's `fee_recipient` with the full requested amount even though the beacon state only actually removed the smaller, capped amount from the builder. The result is ETH created and paid out that is not backed by any corresponding balance decrease anywhere in the system, i.e., a genuine Gwei-conservation violation, not merely an underpayment to the "worker" as in the original report.

### Likelihood Explanation
No malicious peer, coalition, or client bug is required — a builder simply needs its `balance` to be less than the total pending `BuilderPendingWithdrawal.amount` values queued against it (achievable through normal protocol flows such as prior full/partial withdrawals or slashings reducing `balance` while withdrawal requests remain queued). Because `process_withdrawals` is a mandatory, deterministic part of every honest block's state transition, any spec-following node that reaches this state will reproduce the over-payment identically, making this reachable through ordinary protocol operation rather than a contrived edge case.

### Recommendation
Ensure the amount written into the `Withdrawal` object appended to `state.payload_expected_withdrawals` for builder pending withdrawals is the same capped value used to debit `builder.balance`, i.e. `withdrawal.amount = min(pending_withdrawal.amount, builder.balance)` consistently on both the CL debit and EL credit sides, so that the sum of Gwei credited by withdrawals in a payload can never exceed the sum of Gwei actually removed from beacon-state balances.

### Proof of Concept
1. Register a builder with `balance = 1 ETH` (`spec.Gwei(1_000_000_000)`).
2. Queue a `BuilderPendingWithdrawal` for that builder requesting `amount = 5 ETH`.
3. Run `process_withdrawals(state)` for a slot where the parent block is full.
4. Observe (as the spec's own test asserts): `state.builders[0].balance == 0` (only `1 ETH` debited) while the resulting `Withdrawal` object in `state.payload_expected_withdrawals` has `amount == 5 ETH`. [7](#0-6) 
5. When the execution layer applies this withdrawal, it credits the `fee_recipient` address with `5 ETH`, `4 ETH` more than was actually removed from any account in the consensus state — an unbacked Gwei credit.

def test_builder_withdrawal_insufficient_balance(spec, state):
    """
    Test builder withdrawal with insufficient balance.

    Input State Configured:
        - state.builders[0]: Builder exists with only 1 ETH balance
        - builder_pending_withdrawals: Contains 1 entry requesting 5 ETH
        - builders[0].balance: 1 ETH (insufficient for requested 5 ETH)

    Output State Verified:
        - payload_expected_withdrawals: Contains 1 withdrawal
        - withdrawal.amount: 5 ETH (requested amount)
        - builders[0].balance: 0 (deduction capped to available balance)
        - builder_pending_withdrawals: Reduced by 1 (processed even if capped)
        - next_withdrawal_index: Incremented by 1
    """
    builder_index = 0
    withdrawal_amount = spec.Gwei(5_000_000_000)
    available_balance = spec.Gwei(1_000_000_000)

    prepare_process_withdrawals(
        spec,
        state,
        builder_indices=[builder_index],
        builder_withdrawal_amounts={builder_index: withdrawal_amount},
        builder_balances={builder_index: available_balance},
    )

    pre_state = state.copy()
    yield from run_gloas_withdrawals_processing(spec, state)

    assert_process_withdrawals(
        spec,
        state,
        pre_state,
        withdrawal_count=1,
        builder_balances={builder_index: 0},
        builder_pending_delta=-1,
        withdrawal_index_delta=1,
        withdrawal_amounts_builders={builder_index: withdrawal_amount},
    )
