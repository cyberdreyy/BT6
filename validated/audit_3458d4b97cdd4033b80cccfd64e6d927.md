### Title
Fee-on-transfer underlyings inflate strategy-token supply and NAV in `IdleCreditVault.deposit` / `IdleCDOCreditVault._deposit` - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCDOCreditVault._deposit` correctly mints tranche shares using a balance-delta measurement, but then forwards the **gross** `_amount` to `IIdleCDOStrategy(strategy).deposit(_amount)`. `IdleCreditVault.deposit` in turn pulls `_amount` via `safeTransferFrom` and mints `_amount` strategy tokens without measuring what it actually received. With an ERC20 that charges a fee on transfer, each deposit mints more strategy tokens than the underlying received, inflating `getContractValue()`/`_managedContractValue()` and breaking the 1:1 backing of strategy tokens — an unbacked-NAV/insolvency bug analogous to the UXD fee-on-transfer report.

### Finding Description
Deposit flow:

1. `IdleCDOCreditVault._deposit` measures the actual received amount and mints tranche shares for `_contractTokenBalance(_token) - _preBal` — this part is fee-safe.
2. It then calls `IIdleCDOStrategy(strategy).deposit(_amount)` with the **gross** amount.
3. `IdleCreditVault.deposit` does `underlyingToken.safeTransferFrom(msg.sender, address(this), _amount); _mint(msg.sender, _amount);` — it mints strategy tokens for the full `_amount` even though it only received `_amount - fee` (a second fee is charged on this hop, on top of the one charged on the user→CDO transfer).

Net effect per deposit of `A` with per-hop fee `f` (approx.):

- Real assets increase: `A - f_user→CDO - f_CDO→strategy` across CDO+strategy balances.
- Booked NAV increase (`getContractValue` = CDO strategyToken balance + CDO token balance − unclaimedFees): `A - f_user→CDO` because strategy tokens minted = `A`.
- Phantom NAV per deposit ≈ `f_CDO→strategy`.

Additionally, the CDO pays the strategy `_amount` (gross) although it only received `A - f`; the missing `f` is taken from any pre-existing CDO underlying balance — funds earmarked for funded withdraw receipts (`collectWithdrawFunds` pulls CDO cash to the strategy) or `unclaimedFees`, degrading claim backing.

The same assumption exists in `finalizeDefaultRecovery`, which does `safeTransferFrom(_recoverySource, address(this), _recoveredAmount)` and credits `defaultRecoveryReserve = _recoveredAmount + ...` at the gross amount — with a fee token the reserve is overstated by the fee, so the last recovery claimants' `_transferDefaultRecovery` transfers underflow and revert (permanent freeze of tail claims).

### Impact Explanation
- **Unbacked share inflation / solvency:** strategy tokens are minted 1:1 with gross `_amount` while the vault holds less. `getContractValue()`/`virtualPrice()` overstate TVL by the fee on every deposit and on every `totEpochDeposits`/`sendInterestAndDeposits` cycle. Tranche prices are set from this inflated NAV, so later withdrawers (including pending withdraw/instant-withdraw receipts funded via `collectWithdrawFunds`) cannot be paid in full — the deficit is socialized to the last claimants (BB-first, then AA).
- **Reserve overstatement:** `defaultRecoveryReserve`/`defaultRecoveryPrice` are computed on the gross `_recoveredAmount`, so finalized recovery claims exceed the real reserve and revert for the last claimants.
- Any KYC-passing lender can trigger the inflation simply by depositing during the buffer phase or via `depositDuringEpoch`; no privileged role needed. Repeated deposits compound the phantom NAV linearly.

### Likelihood Explanation
Medium: the bug requires the vault's `token` to be a fee-on-transfer ERC20 (or a token that can enable fees later, e.g. USDT/USDC-style upgradeable tokens). Credit vaults accept a configurable `_underlyingToken` at `initialize`; nothing restricts it to fee-less tokens. Attacker is any whitelisted lender — an unprivileged, in-scope actor.

### Recommendation
- In `IdleCreditVault.deposit` (and every place that pulls underlying: `collectWithdrawFunds`, `collectInstantWithdrawFunds`, `finalizeDefaultRecovery`), measure `balanceOf` before/after the `safeTransferFrom` and mint/credit only the received amount.
- In `IdleCDOCreditVault._deposit`, pass the measured received amount (`_contractTokenBalance(_token) - _preBal`) — not the gross `_amount` — to `strategy.deposit`, and skip the strategy call entirely when the measured delta is zero.
- Alternatively, enforce a whitelist of known fee-less underlying tokens at initialization.

### Proof of Concept
Foundry fork test sketch (mock fee-on-transfer ERC20 charging 1% on both `transfer` and `transferFrom`):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOCreditVault} from "../contracts/IdleCDOCreditVault.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";

contract FeeOnTransferPoC is Test {
    function testFeeTokenInflatesStrategyTokens() public {
        // deploy FeeToken (1% fee on transfer/transferFrom)
        // deploy + initialize IdleCreditVault strategy + IdleCDOCreditVault
        // lender = KYC-passed address; give it 1000e6 feeTokens
        //
        // uint256 before = strategy.balanceOf(address(cdo));
        // vm.startPrank(lender);
        // feeToken.approve(address(cdo), 1000e6);
        // uint256 minted = cdo.depositAA(1000e6);
        // vm.stopPrank();
        //
        // CDO received 990, minted ~990 tranche shares -> OK
        // BUT strategy pulled 1000 and minted 1000 strategyTokens
        // while receiving only 990.
        //
        // assertEq(strategy.balanceOf(address(cdo)) - before, 1000e6);   // minted
        // assertEq(feeToken.balanceOf(address(strategy)), 990e6);        // backing
        // => 10e6 phantom NAV; getContractValue() overstates TVL
        // => after epoch claim/stopEpoch, pending receipts + active LPs
        //    exceed real assets: last claimant's safeTransfer reverts
    }
}
```

Key assertions:
- `strategy.balanceOf(cdo)` increases by `_amount` while `underlyingToken.balanceOf(strategy)` increases by `_amount - fee` — unbacked strategy tokens.
- `cdo.getContractValue()` after the deposit exceeds total real underlying held by CDO + strategy by the second-hop fee.
- On `stopEpoch`/`claimWithdrawRequest`, the sum of funded claims + active LP value exceeds `underlyingToken.balanceOf(strategy) + balanceOf(cdo)`, so the last claimant's `safeTransfer` reverts or is short-paid — quantified loss ≈ `fee` per deposit (per recovery pull for `finalizeDefaultRecovery`).

Note: I verified the deposit path and `IdleCreditVault` accounting directly; I did not fully trace `IdleCDOEpochVariant.depositDuringEpoch`/borrower funding paths line-by-line, but they route through the same `deposit`/`mintStrategyTokens` surface and inherit the same gross-amount assumption.
