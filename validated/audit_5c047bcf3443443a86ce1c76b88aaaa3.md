### Title
Default recovery basis undercounts instant-withdraw receipts from earlier epochs, inflating the recovery price - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`defaultPendingClaimBasis` computes the pending-claim denominator used to derive `defaultRecoveryPrice`, but adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the claims recorded under the *current* epoch key — whenever `pendingInstantWithdraws != 0`. Instant receipts requested in earlier epochs that were never fully funded remain stored under their original epoch key and in `instantWithdrawsRequests[_user]`, yet they are excluded from the recovery basis. This is the same bug class as using `baseSupplyIndex` instead of `baseBorrowIndex`: the balance/basis is computed from the wrong index.

### Finding Description
In `IdleCreditVault.requestInstantWithdraw` each receipt is recorded per epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount`, where `currentEpoch` is `epochNumber` at request time (lines 367–372). Funding arrives via `collectInstantWithdrawFunds`, which only decrements `pendingInstantWithdraws` — it never clears or re-keys the per-epoch records. When funding covers only part of the queue (an explicitly supported case: "that cash covered only part of the instant queue"), unfunded receipts persist under their old epoch keys across subsequent epochs.

At default finalization, `finalizeDefaultRecovery` computes:

- `pendingBasis = defaultPendingClaimBasis()`, which adds only `instantWithdrawClaimsByEpoch[epochNumber]` — i.e., claims keyed to the *current* epoch (lines 644–649).
- `prefundedReserve = _defaultPrefundedInstantReserve()`, computed as `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` (lines 716–723) — again keyed to the current epoch only.
- `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (line 688).

Any still-unfunded instant receipt from an earlier epoch is missing from `instantWithdrawClaimsByEpoch[epochNumber]`, so `totalBasis` is too small and `recoveryPrice` is inflated. After finalization, `claimInstantWithdrawRequest` pays `instantWithdrawsRequests[_user]` in full (aggregate across epochs, burned 1:1) without any haircut for old-epoch receipts (lines 387–392), while `_claimDefaultedInstantWithdrawRequest` only haircuts receipts under `defaultRecoveryEpoch` (line 844). Old-epoch instant claims therefore (a) escape the default haircut, and (b) are paid out of a reserve that was never sized for them.

### Impact Explanation
Broken invariant: one receipt, one payout at the finalized recovery ratio. Concretely:

1. A lender requests an instant withdraw in epoch N; the CDO only partially collects funds, so the receipt remains in `pendingInstantWithdraws` under epoch key N.
2. Epoch N+1 runs; other users also request instant withdraws (recorded under key N+1).
3. Borrower defaults; `finalizeDefaultRecovery` counts only epoch-N+1 instant claims as pending basis.
4. The epoch-N holder claims via `claimInstantWithdrawRequest` and is paid 100% from `defaultRecoveryReserve`, even though every other creditor takes `recoveryPrice < RECOVERY_FULL`.
5. The inflated `recoveryPrice` plus unhaircutted old-epoch claims overdraws the reserve: later defaulted-epoch claimants (both normal receipts via `_claimDefaultedWithdrawRequest` and instant receipts via `_claimDefaultedInstantWithdrawRequest`) find `defaultRecoveryReserve` depleted and are permanently underpaid. The excess paid to early/old-epoch claimants equals `claimBasis * (RECOVERY_FULL − fairPrice) / RECOVERY_FULL` plus the entirely unhaircutted old-epoch claims — a direct transfer of recovery funds away from other creditors.

### Likelihood Explanation
Requires a partial funding of the instant queue followed by at least one epoch boundary and then a borrower default. Partial instant funding is an anticipated state per the code comments, and borrower default is a first-class protocol path (`_handleBorrowerDefault` → `finalizeDefaultRecovery`). The attacker needs no privilege: any KYC-passed lender can request an instant withdraw during an epoch where the CDO lacks liquidity, wait through an epoch rollover, and claim at par after finalization while other creditors are haircut. No existing guard stops it: `requestWithdraw`'s `lossRecoveryPriceByEpoch` check (lines 261–271) applies to normal requests, and nothing forces old-epoch instant receipts to be claimed or re-keyed before finalization.

Uncertainty: I could not fully trace every path by which `collectInstantWithdrawFunds` is invoked in `stopEpoch`/`startEpoch` to confirm old-epoch partial funding persists rather than being swept; if the CDO always funds the full `pendingInstantWithdraws` before an epoch increments, the stale-key state cannot arise and the issue reduces to unreachable code.

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, aggregate all outstanding instant receipts rather than indexing only `instantWithdrawClaimsByEpoch[epochNumber]` — e.g., maintain a running `totalInstantClaims` counter incremented in `requestInstantWithdraw` and decremented on each claim, and use it as the instant basis. Alternatively, when an epoch rolls over with unfunded instant receipts, fold `instantWithdrawClaimsByEpoch[oldEpoch]` into the new epoch key. Add a test with a partially funded instant request, an epoch rollover, then `finalizeDefaultRecovery`, asserting old-epoch receipts receive `recoveryPrice`-haircutted payouts.
