### Title
Missing role check on pprof debug routes exposes heap/goroutine dumps to any authenticated view/run-role user - (File: core/web/router.go)

### Summary
`metricRoutes` mounts the full `net/http/pprof` handler set (`heap`, `profile`, `goroutine`, `trace`, `cmdline`, etc.) under `/v2/debug/pprof/*` inside the `authv2` group, but is invoked without any `auth.RequiresEditRole`/`auth.RequiresAdminRole`/`auth.RequiresRunRole` wrapper. Every other sensitive endpoint in that same group is explicitly wrapped with a role-check function, but `metricRoutes(authv2)` is called bare at line 446, so any user who can pass `AuthenticateByToken`/`AuthenticateBySession` — including the lowest-privileged `UserRoleView` — can reach the pprof endpoints.

### Finding Description
The `authv2` group is created with `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` [1](#0-0) , which only verifies that the request has a valid session or API token — it performs no role check by itself. Role enforcement is done per-route via `auth.RequiresRunRole`, `auth.RequiresEditRole`, and `auth.RequiresAdminRole`, as seen throughout `v2Routes` (e.g. lines 251-254, 265-266, 298-302, 311-320). Those wrappers explicitly reject `UserRoleView` (and `UserRoleRun` for edit-level routes) with `401`/`403` [2](#0-1) [3](#0-2) .

However, `metricRoutes(authv2)` is called directly with no such wrapper: `authv2.GET("/debug/pprof/heap", ...)` etc. are registered unwrapped [4](#0-3)  and invoked at [5](#0-4) . Since `authv2` only requires successful authentication (any role), a `UserRoleView` or `UserRoleRun` user's valid session/API token is sufficient to hit `GET /v2/debug/pprof/heap`, `/v2/debug/pprof/profile`, `/v2/debug/pprof/goroutine`, `/v2/debug/pprof/trace`, etc. These pprof handlers return raw process memory/goroutine/CPU-profile dumps, which can contain in-memory secrets (private keys, API tokens, DB credentials) depending on what is resident in the process heap/stack at capture time.

This breaks the codebase's own exact-role-authorization pattern: comparable-sensitivity endpoints (key export, key import, admin user management) are all wrapped with `RequiresAdminRole`/`RequiresEditRole`, but the pprof debug surface — arguably more sensitive since it can leak raw memory — has no such gate.

### Impact Explanation
A low-privileged, view-only (read-only) authenticated user or run-role external-initiator-equivalent user can obtain heap dumps and goroutine stacks of the running Chainlink node process. This is an information-disclosure / authorization-bypass vulnerability: it can expose key material, secrets, or other sensitive in-memory state to a user who should only have read access to job/run data, breaking the intended role separation (view < run < edit < admin). This maps to Chainlink's "unauthorized information disclosure" / "authorization bypass" bounty impact class rather than direct fund loss, but the compromised memory/secret disclosure can be a stepping stone to full key compromise.

### Likelihood Explanation
Minimal precondition: only a valid `UserRoleView` (the lowest role) session cookie or API token is required — no special network position, no admin credentials, no misconfiguration. The route is always mounted (not gated by `build.IsDev()` or any feature flag), so it is reachable on any production node with the standard node API exposed. This is trivially and repeatably exploitable via a single authenticated `GET` request.

### Recommendation
Wrap `metricRoutes(authv2)` (and each pprof sub-route) with an explicit role check, e.g. `auth.RequiresAdminRole`, consistent with other sensitive/debug endpoints (`/log` PATCH requires admin, key export/import require admin). Concretely, change each route registration inside `metricRoutes` to `pprofGroup.GET("/heap", auth.RequiresAdminRole(ginHandlerFromHTTP(pprof.Handler("heap").ServeHTTP)))` (and similarly for the other pprof endpoints), or wrap the whole `pprofGroup` with a `RequiresAdminRole`-based group-level middleware.

### Proof of Concept
Go handler-level integration test (pattern following existing tests in `core/web/*_test.go` that use `cltest.NewTestClient`/`cltest.CreateSessionAndUser`/`sessions.UserRoleView`):

1. Set up a test app/router via `setupJobsControllerTests`-style helper (or equivalent used in `router_test.go`).
2. Create a user with `clsessions.UserRoleView`, log in to obtain a session cookie (or issue an API token) for that user.
3. Issue `client.Get("/v2/debug/pprof/heap")` and `client.Get("/v2/debug/pprof/profile?seconds=1")` using that view-role session.
4. Assert current (vulnerable) behavior: response status is `200 OK` with pprof binary/profile content-type, proving the dump is returned instead of `401`/`403`.
5. After applying the recommended fix (wrapping with `auth.RequiresAdminRole`), re-run the same test and assert `http.StatusForbidden` (403) is returned for the view-role and run-role users, and only an admin-role session receives `200`.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
