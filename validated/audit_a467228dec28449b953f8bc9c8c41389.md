### Title
Stale confirmations from removed multisig members still count toward the execution threshold, allowing a request to execute below the live-member quorum - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` decides whether to execute a request purely by counting the size of the `confirmations` `HashSet<String>` stored for that `request_id`, without re-validating that every entry in that set still corresponds to a current member. `delete_member` only purges requests *proposed by* the removed member; it never scrubs that member's *confirmations* left on requests proposed by others. This lets a request be executed with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
`confirm()` reads the stored `HashSet<String>` of confirmers and executes once `confirmations.len() + 1 >= self.num_confirmations`: [1](#0-0) 

The identity string inserted into that set is simply `member.to_string()` computed at the time of the `confirm()` call, with no link back to whether that member remains valid at execution time: [2](#0-1) 

`delete_member` only removes/cleans requests where `r.member == member` (i.e., requests *proposed* by the removed member) and clears `num_requests_pk` for that member. It does **not** scan other requests' `confirmations` sets to strip out entries belonging to the removed member: [3](#0-2) 

`assert_valid_request`, called from both `confirm` and `delete_request`, only checks that the *caller* is a current member and that the request/confirmations map entries exist — it never re-validates the *existing* confirmers against the current `members` set: [4](#0-3) 

The intended custody binding for a k-of-n multisig is: *confirmations counted toward execution == confirmations from currently-authorized (live) members*. Because stale confirmations from since-removed members persist in storage and are never invalidated, this equality is broken: a request can accumulate a confirmation from member B, B can later be removed via a `DeleteMember` request, and B's earlier confirmation still counts when a remaining member subsequently confirms the same request — even though only one truly live member actually approved it at the moment of execution.

### Impact Explanation
This is a Critical-impact bug per the custody binding categories: **a multisig request executed below threshold**. If `num_confirmations = 2` and members are `{A, B, C}`:
1. B confirms request `R` (proposed by A), a transfer of funds out of the multisig account. `confirmations = {B}`, `1 < 2`, not yet executed.
2. Separately, `B` is removed from the multisig via a `DeleteMember` request (e.g., because their key was compromised or they left the organization). `delete_member(B)` does not touch `R`'s confirmation set, so `{B}` remains stored against `R`.
3. `A` (or `C`) now calls `confirm(R)`. `current_member()` succeeds for `A`/`C` since they are still live members. `confirmations.len() (1) + 1 = 2 >= num_confirmations (2)` → `R` executes.

The transfer (or `AddKey`, `DeployContract`, etc.) executes having received only one genuinely live confirmation (A or C), plus one stale confirmation from a member who was intentionally revoked — precisely the scenario the k-of-n threshold is meant to prevent. This can move NEAR out of the multisig account, add unauthorized access keys, or deploy new contract code, all with fewer authorizing live signers than configured.

### Likelihood Explanation
This does not require any privileged actor, malicious node, or redeploy — only two ordinary multisig-governance actions available to any current member: proposing/confirming a normal request, and later proposing/confirming a `DeleteMember` action (a routine key-rotation/offboarding operation any k-of-n multisig will perform over its lifetime). The vulnerable window is naturally created any time a member is removed after having confirmed but not yet triggered execution of some other pending request — a realistic and likely operational sequence, not a contrived edge case.

### Recommendation
When a member is removed in `delete_member`, iterate all `confirmations` entries system-wide (or maintain a reverse index of member → confirmed request IDs) and remove the departing member's entry from every request's confirmation set, not just requests they proposed. Alternatively, when counting confirmations in `confirm()`, filter the stored set to only those entries still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
Conceptual sequence (no code changes needed to trigger, only the exposed public API):
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. `A.add_request(R)` — a `Transfer` action draining the account, proposer = A.
3. `B.confirm(R)` → `confirmations[R] = {B}`, `1 < 2`, request stays open.
4. Members execute a separate request `DeleteMember { member: B }` (2-of-3 confirm, e.g. A and C confirm it) → `delete_member(B)` runs: removes B from `members`, deletes B's access key, cleans up requests proposed by B, but leaves `confirmations[R] = {B}` untouched.
5. `A.confirm(R)` (or `C.confirm(R)`): `current_member()` returns `A`, `assert_valid_request` passes (A is live, R exists). `confirmations[R].len() (1) + 1 = 2 >= num_confirmations (2)` → `execute_request(R)` runs, draining funds, despite only one currently-trusted member (A) actually approving at execution time.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
