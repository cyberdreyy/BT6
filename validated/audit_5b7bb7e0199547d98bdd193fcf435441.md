Based on my investigation, the closest structural analog to the OpenQ bug is in the Gateway's legacy WebAPI trigger handler, where a client-controlled `MessageId` is used as a map key without any uniqueness/ownership validation, allowing a callback belonging to one caller to be silently overwritten and responses routed to the wrong caller — the same "generic accept path breaks a later specific-path assumption" root cause as the OpenQ finding (funding function accepts arbitrary token types, but the payout path assumes a specific type).

### Title
Unvalidated, client-controlled MessageId allows cross-user response hijacking in Gateway WebAPI trigger handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` stores each pending user callback in `h.savedCallbacks` keyed by the caller-supplied `msg.Body.MessageId`, with no check for whether that ID is already in use [1](#0-0) . The `MessageId` originates from the client's JSON-RPC request ID, which is attacker-controlled and only validated for length/format (max 200 chars, no null-byte suffix), never for uniqueness or ownership [2](#0-1) [3](#0-2) . Later, when a DON node responds, `handleWebAPITriggerMessage` looks up and deletes the entry by that same `MessageId` and routes the response to whichever `Callback` currently occupies the map slot [4](#0-3) .

### Finding Description
The vulnerability class mirrors the OpenQ bug: a generic "accept anything that satisfies a minimal shape" entry point (`_receiveERC20` accepting ERC721 tokens; here, `HandleLegacyUserMessage` accepting any string as `MessageId`) is paired with a downstream consumer (`handleWebAPITriggerMessage`) that implicitly assumes the accepted value uniquely and correctly identifies the intended recipient/owner. Because there is no check-then-set validation (`_, exists := h.savedCallbacks[id]`) before the assignment at [1](#0-0) , an unprivileged HTTP client hitting the gateway's user-facing endpoint can:

1. Predict or brute-force an in-flight `MessageId` (client-chosen JSON-RPC `ID`, echoed straight through `ProcessRequest` -> `msg.Body.MessageId` -> `HandleLegacyUserMessage`) belonging to a legitimate, still-pending request from another caller.
2. Submit a second request reusing that same ID before the legitimate request's callback is fulfilled or pruned.
3. Overwrite the map entry so that the attacker's `Callback` object now occupies the slot for that `MessageId`.
4. When the DON node eventually responds for the original request, `handleWebAPITriggerMessage` deletes the (now-attacker-owned) entry and calls `savedCb.SendResponse(...)`, delivering the legitimate user's response payload to the attacker instead [5](#0-4) .
5. Simultaneously, the original caller's HTTP request hangs until `callback.Wait(ctx)` times out (`RequestTimeoutError`), since its callback slot was replaced [6](#0-5) .

This is the same structural flaw as the report: the acceptance function (`HandleLegacyUserMessage`/map assignment) is more permissive than the consuming function (`handleWebAPITriggerMessage`) expects, and there is no whitelist/ownership separation to prevent identity confusion.

### Impact Explanation
An unprivileged client can hijack another user's response, potentially leaking response payloads (which can carry sensitive workflow/trigger data returned by DON nodes) to an attacker-controlled HTTP callback, and cause denial-of-service (timeout) for the legitimate caller's request. This matches the "cross-user response confusion" and unauthorized disclosure categories called out as in-scope.

### Likelihood Explanation
Requires the attacker to know or guess another in-flight request's `MessageId` and race the response window (bounded by `CallbackMaxAgeSec`, default 120s) [7](#0-6) . If IDs are predictable (sequential, timestamp-based, or reused by a client SDK), likelihood is high; if IDs are high-entropy random values chosen by well-behaved clients, likelihood is low. I could not verify from the indexed code how the reference gateway client (if any) generates `MessageId`/JSON-RPC `ID` values, so the practical exploitability depends on external client behavior not fully covered by the index.

### Recommendation
In `HandleLegacyUserMessage`, check for an existing entry for `msg.Body.MessageId` before inserting, and reject (or generate a gateway-side unique ID instead of trusting the client-supplied one) rather than silently overwriting:
```go
h.mu.Lock()
if _, exists := h.savedCallbacks[msg.Body.MessageId]; exists {
    h.mu.Unlock()
    return callback.SendResponse(... "duplicate message ID" ...)
}
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}
h.mu.Unlock()
```
Additionally, consider deriving the internal callback key from a gateway-generated nonce plus the caller's identity/session rather than the raw client-supplied ID, so that no external input alone can determine which callback slot is targeted.

### Proof of Concept
Not independently executable from the index (no test harness proving predictable MessageId sourcing was found), but the code path is directly traceable:
1. `gateway.ProcessRequest` takes `jsonRequest.ID` from the raw client request and sets it on `msg.Body.MessageId` without uniqueness checks [8](#0-7) .
2. `HandleLegacyUserMessage` unconditionally overwrites `h.savedCallbacks[msg.Body.MessageId]` [1](#0-0) .
3. `handleWebAPITriggerMessage` delivers the node's response to whatever `Callback` is currently stored under that ID [4](#0-3) .

I was unable to confirm within the indexed code exactly how downstream node/DON identifies which trigger request a response corresponds to beyond `MessageId` matching, so full end-to-end confirmation of exploitability would require reviewing the client-side ID-generation logic and the full node-side WebAPI trigger response flow, which may not be fully covered in the index. If this matters for verification, a full Devin session with repository access could trace client ID generation and add a reproducing integration test.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

	if err != nil {
		return newError(jsonRequest.ID, api.UserMessageParseError, err.Error())
	}
	if len(jsonRequest.ID) > 200 {
		// Arbitrary limit to prevent abuse
		return newError(jsonRequest.ID, api.UserMessageParseError, "request ID is too long: "+strconv.Itoa(len(jsonRequest.ID))+". max is 200 characters")
	}
	var isLegacyRequest = false
	var h handlers.Handler
	var handlerKey string
	if msg == nil || msg.Body.DonId == "" {
		serviceName := jsonRequest.ServiceName()
		if handler, ok := g.serviceToMultiHandler[serviceName]; ok {
			h = handler
			handlerKey = serviceName
		} else if donID, ok := g.serviceNameToDonID[serviceName]; ok {
			// Fallback to legacy service name -> DON ID mapping
			if handler, ok := g.handlers[donID]; ok {
				h = handler
				handlerKey = donID
			}
		}
		if h == nil {
			return newError(jsonRequest.ID, api.HandlerError, "Service name not found: "+serviceName)
		}
	} else {
		// Legacy request with DON ID - validate and fetch handler
		isLegacyRequest = true
		if err = msg.Validate(); err != nil {
			return newError(jsonRequest.ID, api.UserMessageParseError, err.Error())
		}
		handlerKey = msg.Body.DonId
		var ok bool
		h, ok = g.handlers[handlerKey]
		if !ok {
			return newError(jsonRequest.ID, api.UnsupportedDONIdError, "Unsupported DON ID: "+handlerKey)
		}
	}

	startTime := time.Now()
