### Title
`getSlotLeaders` RPC cost scales with `start_slot` position in epoch rather than `limit` due to `LeaderSchedule::get_slot_leaders` flat_map-before-skip pattern - ([File: leader-schedule/src/vote_keyed.rs])

### Summary
`LeaderSchedule::get_slot_leaders` builds a lazily-flat-mapped iterator over every entry in `slot_leaders` (expanded by `repeat`) before any `skip`/`take` is applied by the caller in `rpc/src/rpc.rs`. Because `Iterator::skip` is implemented by repeatedly calling `.next()` and discarding results, the number of iterator steps actually executed for a `getSlotLeaders(start_slot, limit)` request is proportional to `slot_index = start_slot - epoch_start_slot`, not to the requested `limit`.

### Finding Description
`get_slot_leaders` is defined as: [1](#0-0) 

This returns `self.slot_leaders.iter().flat_map(|leader| iter::repeat_n(leader, self.repeat()))`, i.e., a lazy iterator whose total length is `num_slots() == slot_leaders.len() * repeat()` — effectively the full epoch's slot count. The RPC handler in `rpc/src/rpc.rs` (matches for `skip(`, `take(`, `MAX_GET_SLOT_LEADERS`) consumes this iterator with `.skip(slot_index as usize).take(limit)` to select the requested window. Because `skip` on a lazily-composed `flat_map` iterator must advance through each discarded element via `.next()`, a request with `start_slot` positioned near the end of a large epoch forces the iterator machinery to step through nearly the full `slot_index` count before yielding any of the `limit` results.

By contrast, `LeaderSchedule` already exposes an O(1) random-access primitive, `get_slot_leader_at_index`, which computes the leader directly via `index % num_slots() / repeat()`: [2](#0-1) 
The RPC path does not use this O(1) accessor for windowed reads; instead it pays for `slot_index` iterator advances per call, which is disproportionate to the `limit`-bounded work the API contract implies.

An attacker who knows `epoch_schedule.slots_per_epoch` can request `start_slot` near `last_slot_of_epoch - 1` with `limit = MAX_GET_SLOT_LEADERS`, forcing the handler to internally advance through close to `slots_per_epoch` iterator steps (each step involving a `flat_map`/`repeat_n` state transition) regardless of the small `limit` actually requested.

### Impact Explanation
This violates the intended invariant that a single `getSlotLeaders` call's cost should scale with the client-supplied `limit`, not with the position of `start_slot` inside the epoch. The scoped impact is CPU cost of a single RPC call scaling with epoch size (bounded by `slots_per_epoch`, a fixed cluster constant such as 432,000) instead of with `limit`. This falls under "unbounded cost for a single low-rate call" in spirit, though the worst case is bounded by the fixed `slots_per_epoch` constant rather than truly unbounded — this caps the practical severity, since the attacker cannot exceed `slots_per_epoch` iterator steps no matter how they choose `start_slot`.

### Likelihood Explanation
Fully attacker-controlled with no privileged access: the attacker only needs to know the public `epoch_schedule` (obtainable via `getEpochSchedule`) and issue one `getSlotLeaders` call per allowed interval with `start_slot` chosen near the end of a large epoch and `limit = MAX_GET_SLOT_LEADERS`. This is repeatable once per `CLUSTER_SLOT_TIME_TARGET / 2`, so a sustained low-rate stream of maximal-skip requests is possible, but each individual request's overhead is capped by the fixed `slots_per_epoch` constant.

### Recommendation
Replace the `get_slot_leaders().skip(slot_index).take(limit)` pattern in the RPC handler with direct index-based access using `get_slot_leader_at_index` (or an equivalent O(1)/O(limit) windowed accessor) so that the work performed is proportional to `limit` rather than `slot_index`.

### Proof of Concept
Rust benchmark/integration test plan:
```rust
#[bench]
fn bench_get_slot_leaders_skip_cost(b: &mut Bencher) {
    let epoch_len = 432_000usize; // slots_per_epoch
    let schedule = build_large_leader_schedule(epoch_len); // helper constructing LeaderSchedule
    let limit = 5000; // MAX_GET_SLOT_LEADERS

    // Case A: start_slot near beginning of epoch
    b.iter(|| {
        schedule.get_slot_leaders().skip(0).take(limit).count()
    });
}

#[bench]
fn bench_get_slot_leaders_skip_cost_end(b: &mut Bencher) {
    let epoch_len = 432_000usize;
    let schedule = build_large_leader_schedule(epoch_len);
    let limit = 5000;

    // Case B: start_slot near end of epoch (slot_index ~ epoch_len - limit - 1)
    b.iter(|| {
        schedule.get_slot_leaders().skip(epoch_len - limit - 1).take(limit).count()
    });
}
```
Expected assertion: elapsed time for Case B should be near-constant relative to Case A if cost is bounded by `limit`; observed behavior is that Case B takes measurably longer, scaling with `slot_index`, confirming the cost is driven by `skip` distance rather than `limit`.
