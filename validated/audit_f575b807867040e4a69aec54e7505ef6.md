### Title
Closed-pool `requestWithdraw` mints instantly-claimable receipts that drain underlying reserved for other users' funded withdraw claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` has a dedicated branch for a closed pool (`epochEndDate() == 0`): it mints a receipt to the user but deliberately skips `pendingWithdraws += _amount`, because "a successfully closed pool already recalled all funds and has no later stopEpoch." However, `_claimFundedWithdrawRequest` also skips the one-epoch waiting check when `epochEndDate() == 0`. The combination lets any tranche holder burn tranche tokens, receive a withdraw receipt, and claim it in the same transaction — paid out of underlying still held by the vault that was collected via `collectWithdrawFunds` to back *other* users' already-funded, not-yet-claimed withdraw receipts. This is a use-after-free analog of CVE-2024-6989: the closed-pool epoch guard is "freed" (skipped) while the receipt is still alive and spendable, so the same underlying backing is used twice.

### Finding Description
In `requestWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:259-294):

- `isClosed = IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0` is computed.
- The user's receipt is minted (`_mint(_user, _amount)`) and `withdrawsRequests[_user] += _amount` is recorded.
- Because `isClosed` is true, `pendingWithdraws += _amount` is skipped (line 277-280). No borrower funding will ever arrive for this receipt — there is no future `stopEpoch`/`collectWithdrawFunds` in a closed pool.

In `_claimFundedWithdrawRequest` (lines 319-349):

```solidity
if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
  revert NotAllowed();
}
```

When `epochEndDate() == 0` the entire waiting-epoch check is bypassed, so the freshly created request is immediately claimable.

The claim pays via `_transferFundedClaim` (lines 897-907), which only protects `defaultRecoveryReserve` — there is no guard that the vault's underlying balance actually covers the new receipt plus all pre-existing funded receipts. Since no `collectWithdrawFunds` ever ran for the attacker's receipt, the payout comes from the residual vault balance that was collected to satisfy earlier, legitimate pending withdraw claims.

### Impact Explanation
Direct theft / insolvency. Any tranche-token holder in a closed pool can atomically `requestWithdraw` + `claimWithdrawRequest` and pull underlying equal to their tranche value at the 1:1 receipt rate, consuming funds that belong to users with funded-but-unclaimed withdraw receipts (or APR0 settled claims). Those users' subsequent claims revert on insufficient balance — a "one receipt one payout" invariant violation where the last claimant is left unpaid. Loss is bounded by the vault's residual underlying balance earmarked for funded claims, which can be the full unclaimed amount.

### Likelihood Explanation
Requires a closed pool (`epochEndDate() == 0`, reached via the `_interest == 1` repay-all stopEpoch path — an honest manager/borrower action, not attacker-controlled) plus unclaimed funded withdraw receipts in the vault, which is common since claims are permissionless and lazy. The attacker only needs to hold tranche tokens (any KYC-passing lender). No privileged action, oracle manipulation, or timing race is needed — the drain is atomic in one transaction.

### Recommendation
In a closed pool, either (a) revert in `requestWithdraw` and route redemptions through a dedicated par-redemption path backed by verifiably idle CDO funds, or (b) only allow the immediate claim if the underlying backing the burned strategy tokens is transferred to the vault atomically as part of the request (i.e., make the closed-pool receipt self-funded). At minimum, `_transferFundedClaim` should also reserve the aggregate outstanding funded claims (`withdrawsRequests` + settled APR0 + instant receipts) so a new receipt can never spend backing earmarked for earlier claims.

### Proof of Concept
Foundry fork PoC (solidity pseudocode, using the repo's existing harness style in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// test/foundry/ClosedPoolClaimDrain.t.sol
function testClosedPoolRequestDrainsFundedClaims() external {
    // Setup: deposit with victim (AA) and attacker (AA)
    uint256 victimAA = idleCDO.depositAA(100_000 * ONE_SCALE);
    uint256 attackerAA = idleCDO.depositAA(50_000 * ONE_SCALE);

    // Epoch 0 runs; victim requests withdraw during buffer of epoch 1
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
    cdoEpoch.requestWithdraw(victimAA / 2, address(AAtranche)); // from victim CDO-side
    _startEpochAndCheckPrices(1);
    // stopEpoch collects victim's funded claim into the vault
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // Victim does NOT claim yet -> vault holds underlying earmarked for victim.

    // Manager/borrower close the pool: repay-all sentinel (_interest == 1)
    // -> cdoEpoch.epochEndDate() == 0
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(1, 0); // or equivalent close-pool path

    // ATTACK: atomic request + claim in closed pool
    uint256 vaultBalPre = underlying.balanceOf(address(strategy));
    uint256 attackerBalPre = underlying.balanceOf(attacker);

    vm.startPrank(attacker);
    cdoEpoch.requestWithdraw(attackerAA, address(AAtranche)); // isClosed: no pendingWithdraws++
    cdoEpoch.claimWithdrawRequest();                          // epoch-wait check skipped
    vm.stopPrank();

    // Attacker was paid at par from the vault even though no stopEpoch
    // ever collected funds for the attacker's receipt.
    assertGt(underlying.balanceOf(attacker) - attackerBalPre, 0);
    assertLt(underlying.balanceOf(address(strategy)), vaultBalPre);

    // Victim's previously funded claim now reverts / is underpaid (insolvency).
    vm.expectRevert();
    victim.claimWithdrawRequestViaCDO(); // safeTransfer fails on drained balance
}
```

Key assertions: (1) `requestWithdraw` succeeds while `epochEndDate() == 0` and `pendingWithdraws` is unchanged; (2) `claimWithdrawRequest` succeeds in the same epoch; (3) vault underlying decreases by the attacker's payout while the victim's funded claim basis is unchanged — the same backing was spent twice.
