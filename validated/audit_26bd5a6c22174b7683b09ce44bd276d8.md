### Title
Removing a Multisig Member Does Not Invalidate Their Prior Confirmations, Allowing Requests to Execute Below the Live-Member Threshold - (File: `multisig2/src/lib.rs`, also present in `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm()` counts confirmations purely by the size of the `confirmations` set stored for a request, without checking whether each confirming key/account is still a current member. `delete_member()` (and the analogous `DeleteKey` action in `multisig/src/lib.rs`) only purges requests and `num_requests_pk` entries *originated by* the removed member; it does not scrub that member's confirmation from other, still-pending requests they had previously confirmed. This lets a request execute once `confirmations.len() + 1 >= num_confirmations` even though one or more of the counted confirmations belong to a member who has since been removed, so the request runs with fewer *live* confirmations than the configured threshold.

### Finding Description
The invariant the contract is supposed to enforce is:

```
number of confirmations from currently-valid members >= num_confirmations
```

`confirm()` instead checks:

```
confirmations.len() (a snapshot set that can contain stale entries) + 1 >= num_confirmations
``` [1](#0-0) 

When a member is removed via `MultiSigRequestAction::DeleteMember`, `delete_member()` only cleans up:
- requests where `r.member == member` (i.e. requests *created* by that member), and
- the `num_requests_pk` counter for that member.

It never inspects or updates the `confirmations` map for *other* pending requests that this member had already confirmed: [2](#0-1) 

`assert_valid_request()`, called at the top of both `confirm()` and `delete_request()`, only validates that the *caller* is currently a member and that the request/confirmations entries exist — it does not revalidate the *existing* confirmers in the stored set: [3](#0-2) 

The same pattern exists in the original `multisig` contract: `DeleteKey` removes requests keyed by `signer_pk == pk` and the `num_requests_pk` entry, but does not scrub `pk`'s confirmations from other pending requests' `confirmations` sets: [4](#0-3) [5](#0-4) 

This mirrors the report's bug class: a status/membership check ("is this signer still valid?") that is enforced only at the time an action is originated (add/confirm), never re-validated at the point where the threshold decision actually authorizes fund movement or privileged execution (`confirm`'s branch to `execute_request`). The binding broken is:

`confirmations counted (stale, includes removed members) == confirmations required (num_confirmations)`

should instead be:

`confirmations from members ∈ current members set == confirmations required (num_confirmations)`

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." A request (e.g. a `Transfer`, `FunctionCall`, or `AddKey`) can execute with fewer confirmations from currently-authorized members than `num_confirmations` requires, because a stale confirmation from a removed member still counts toward the threshold. This can move NEAR out of the multisig account, add unauthorized keys, or perform other privileged self-actions with an effectively lower approval threshold than configured, undermining the entire security model of the multisig.

### Likelihood Explanation
This requires no attacker with special privileges beyond being a normal outgoing/incoming member scenario that multisig owners naturally exercise (member rotation/offboarding). Any organization using `multisig2` (or `multisig`) that rotates members — a routine operational event, e.g. removing a departing employee or a compromised key — while a request is mid-confirmation, will hit this: the departing member's earlier confirmation remains valid indefinitely on any request they touched before removal. No malicious action is even required; it can happen from ordinary sequencing of legitimate multisig operations (confirm request A partially, then execute a DeleteMember request B, then finish confirming A).

### Recommendation
When executing `DeleteMember` (or `DeleteKey`), iterate over all pending requests' `confirmations` sets and remove any entry belonging to the removed member/key, not only requests they originated. Alternatively, when counting confirmations in `confirm()`, filter `confirmations` to only those entries still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
Using `multisig2` with `num_confirmations = 3` and `members = {A, B, C, D}`:

1. `B` calls `add_request(R1)` (e.g. a `Transfer` of funds out of the multisig account).
2. `A` calls `confirm(R1)` → `confirmations(R1) = {A}` (len 1 < 3, not yet executed).
3. `C` calls `confirm(R1)` → `confirmations(R1) = {A, C}` (len 2 < 3, not yet executed) — see `confirm()` logic at [1](#0-0) .
4. Members submit and fully confirm a separate self-request `R2 = DeleteMember { member: C }` (e.g. because `C` is departing or their key was compromised). `R2` executes: `C` is removed from `self.members`, and `delete_member()` only removes requests *originated by* `C` and `num_requests_pk[C]` — it does not touch `confirmations(R1)`, which still contains `C`. See [2](#0-1) .
5. Now `self.members = {A, B, D}`, but `confirmations(R1)` is still `{A, C}`.
6. `D` calls `confirm(R1)`. `confirmations.len() as u32 + 1 = 2 + 1 = 3 >= num_confirmations (3)` → the request executes via `execute_request(R1)`, moving funds out of the account, even though only `A` and `D` are actually current, live members who approved it — one fewer live confirmation than the configured threshold of 3.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
