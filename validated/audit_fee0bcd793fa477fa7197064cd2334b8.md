### Title
Front-runnable `LockupFactory::create` allows squatting a victim's deterministic lockup address with attacker-chosen `release_duration` - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the lockup account id deterministically from `sha256(owner_account_id)` and lets **any** caller who attaches `MIN_ATTACHED_BALANCE` deploy a lockup for **any** `owner_account_id`, with any `release_duration`, `lockup_duration`, `lockup_timestamp` and `vesting_schedule` of their choosing. There is no check that the caller is the intended issuer (e.g. the foundation) or that the target address has been reserved for a specific grant, so an unprivileged attacker can front-run the legitimate issuer's transaction and permanently occupy `owner_account_id`'s lockup address with parameters the real issuer never authorized.

### Finding Description
The broken binding: `deployed_lockup(owner_account_id).release_duration == real_issuer_intended_release_duration`.

Code path:
- `lockup_account_id` is computed purely from the caller-supplied `owner_account_id`: [1](#0-0) .
- `create` has no access control beyond an attached-deposit minimum check, so any account can call it with any `owner_account_id` and any `release_duration`: [2](#0-1) .
- The caller-supplied `release_duration` (and other args) are forwarded verbatim into `LockupArgs` and serialized into the `new` call on the newly created account: [3](#0-2) .
- If the underlying `create_account()` fails (because the address is already taken), `on_lockup_create` simply refunds the attached deposit to whichever predecessor sent that particular transaction, and returns `false` - it performs no comparison against any previously "intended" parameters, since the factory has no notion of intended parameters at all: [4](#0-3) .

Exploit flow: attacker observes (or predicts) that a grant is about to be created for `owner_account_id`, computes the same deterministic address, and races a `create(owner_account_id, lockup_duration, None, None, Some(1), None)` call with `MIN_ATTACHED_BALANCE` attached, ahead of the real issuer's transaction. If the attacker's transaction lands first, the address is permanently claimed with `release_duration = 1`. The real issuer's subsequent `create()` call fails at `create_account()` (name already taken) and is refunded to its own predecessor via `on_lockup_create` - it is not merged into or applied to the already-deployed contract. No `assert_owner`, `assert_called_by_foundation`, or reservation mechanism exists in this contract to prevent this race, since `create` is fully permissionless by design.

### Impact Explanation
This matches the rubric's Critical category "a lockup deployed with parameters its rightful creator never chose": the address permanently associated with `owner_account_id` ends up governed by a `release_duration` (and any other lockup terms) chosen solely by the attacker, not the real issuer. Once deployed, this cannot be corrected without a full lockup redeploy, which is out of scope for factory-only actors. The attack is repeatable against any not-yet-created `owner_account_id`; each attempt costs the attacker `MIN_ATTACHED_BALANCE` (3.5 NEAR) and produces one squatted contract per targeted account.

Note: because the legitimate issuer's larger deposit is refunded (not locked) when `create_account()` fails, the funds that actually end up locked under the squatted `release_duration` are only the attacker's own `MIN_ATTACHED_BALANCE` deposit, not the "full grant" as literally claimed in the question. The genuine critical impact is that the deployed lockup contract's terms diverge from the issuer's intent for that account id, blocking the real grant from ever being placed there under the intended terms (the legitimate call is not retried automatically, and any manual retry will hit the same already-taken address).

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's capability: knowledge of (or ability to guess) the target `owner_account_id`, and `MIN_ATTACHED_BALANCE` (3.5 NEAR) attached to a `create` call sent before the real issuer's transaction is included. Since `owner_account_id` values for planned grants are often predictable/public (e.g., known employee or investor account names), and NEAR transaction ordering can be raced via gas-price/priority or mempool visibility, this is practically exploitable without requiring foundation privileges, multisig membership, or key compromise.

### Recommendation
Add a reservation/whitelist step controlled by `foundation_account_id` (or another trusted party) so that `create` can only be called for a given `owner_account_id` by an authorized issuer, or require a pre-committed hash of the intended `LockupArgs` (analogous to the `VestingScheduleOrHash` pattern already used for vesting schedules) that must match what is ultimately deployed.

```rust
// cargo test in lockup-factory/src/lib.rs (tests module)
#[test]
fn test_frontrun_squats_release_duration() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker front-runs with release_duration = 1 for the victim's owner_account_id
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = MIN_ATTACHED_BALANCE;
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(), // victim owner_account_id
        lockup_duration,
        None,
        None,
        Some(1u64.into()), // malicious near-instant release_duration
        None,
    );

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    assert!(contract.on_lockup_create(
        lockup_account(),
        MIN_ATTACHED_BALANCE.into(),
        String::from("attacker.near"),
    )); // squatted lockup deployed with release_duration = 1

    // Real issuer's legitimate create() for the same owner_account_id now fails at create_account()
    context.predecessor_account_id = String::from(account_tokens_owner_issuer());
    context.attached_deposit = ntoy(1_000_000); // intended real grant
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(),
        lockup_duration,
        None,
        None,
        Some((YEAR * 4).into()), // intended long release_duration, never applied
        None,
    );

    context.predecessor_account_id = account_factory();
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let res = contract.on_lockup_create(
        lockup_account(),
        ntoy(1_000_000).into(),
        String::from(account_tokens_owner_issuer()),
    );
    assert_eq!(res, false); // refunded, real release_duration never deployed
    // Assert divergence: deployed release_duration (1) != intended release_duration (YEAR*4)
}
```

```rust
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
```
