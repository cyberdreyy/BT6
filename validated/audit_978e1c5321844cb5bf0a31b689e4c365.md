### Title
Re-proposal of an already group-accepted block wipes local consensus bookkeeping, defeating the conflict guard - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_proposal` decides whether to re-evaluate a previously-seen block via `should_reevaluate_block`. For a block that reached `BlockState::LocallyAccepted` purely because *other* signers' broadcast signatures pushed the aggregate weight over threshold (`mark_locally_accepted(true)` in `store_and_process_block_signature`, which — unlike the `group_signed=false` path — never sets `valid`), a second copy of the *same* proposal (same `signer_signature_hash`) causes the signer to fall through every "don't touch it" branch in `should_reevaluate_block` and reconstruct the tracked `BlockInfo` from scratch via `BlockInfo::from(block_proposal.clone())`. That constructor unconditionally resets `state` to `Unprocessed` and clears `valid`, `signed_self`, `signed_group`, and `approved_time`, erasing the local record that this block already reached group consensus. This is the same bug class as CVE-2022-46167: a locally-mutable piece of bookkeeping that is the *sole* enforcement mechanism (there, the Kubernetes `OwnerReference`; here, `BlockInfo.state`/`signed_group`) can be wiped by an actor who is allowed to touch the object, silently disabling the guard it backs — in this case, the same-height conflict guard described in `docs/signer-flows.md` section 5 (`get_signed_conflicts`), which exists specifically to stop the signer from endorsing two blocks at the same height.

### Finding Description
- `BlockInfo::from<BlockProposal>` unconditionally zeroes out `state`, `valid`, `signed_self`, `signed_group`, and `approved_time`: [1](#0-0) 

- `mark_locally_accepted(true)` (the "group signed" path, invoked when the pre-commit/signature threshold is reached from *other* signers' signatures) transitions `state` to `LocallyAccepted` and sets `signed_group`, but does **not** set `valid`: [2](#0-1) 

- `store_and_process_block_signature` performs exactly this transition purely from accumulated `block_signatures` weight, independent of whether the local signer itself ever validated the block (`block_info.valid`): [3](#0-2) 

- `should_reevaluate_block` is the sole guard against reprocessing a block we've already decided on. It bails out early only for `globally_approved_and_responded()` blocks or blocks in `PreCommitted` state or blocks for which `determine_response` (which requires `valid` to be `Some`) can answer immediately: [4](#0-3) 
`determine_response` explicitly early-returns `None` when `valid` is `None`: [5](#0-4) 

- Because the `mark_locally_accepted(true)` path never sets `valid`, a block that is `LocallyAccepted`/`signed_group`-set through group consensus alone has `valid == None`. Since its `state` is `LocallyAccepted` (not `PreCommitted`) and it's not "globally approved" (that state is reserved for `GloballyAccepted`/`GloballyRejected`, judging by the function name and the fact the `PreCommitted` branch is checked separately), it falls through every early-return in `should_reevaluate_block` and reaches the final `true`.

- Back in `handle_block_proposal`, `should_reevaluate_block == true` leads straight into overwriting the tracked record: [6](#0-5) 
The comment on line 1653 even documents that this is a deliberate overwrite ("will overwrite any prior proposal info on the block if it exists, e.g. validity, signed_timestamps, etc.") but does not account for the case where the wiped state was backing the equivocation guard.

- The equality/guard this breaks is the one documented in `docs/signer-flows.md` section 5: `get_signed_conflicts`/`handle_block_pre_commit` treat "any block that was ever signed (`signed_self` or `signed_group`), regardless of current state" as a hard block against signing a sibling at the same height: [7](#0-6) [8](#0-7) 
Once `BlockInfo::from` resets `state` to `Unprocessed` and clears `signed_group`, that block's row no longer appears as a signed conflict when a sibling at the same height is later evaluated — even though the underlying signatures are still sitting in the independent `block_signatures` table and could still complete the block on-chain.

### Impact Explanation
This breaks the "no signature on two conflicting blocks at the same height" equality that the whole pre-commit/conflict-check design in section 5 of `docs/signer-flows.md` exists to enforce. If the signer subsequently signs a conflicting sibling at the same height because the conflict guard no longer sees the wiped record, the signer commits an equivocation: two candidate blocks at the same height that could both be finalized, which is a Critical-class outcome per the stated impact tiers ("a signer signing an invalid, non-canonical, or conflicting block"). This requires only one miner (or any StackerDB writer able to re-post the identical block proposal) and normal gossip of peer signatures — no majority of signers, no other signer's key, and no auth token.

### Likelihood Explanation
The precondition — a block reaching `LocallyAccepted`/`signed_group` state purely from peer signatures while the local signer's own `valid` is still `None` — is a routine timing scenario: it happens whenever a signer's own validation round-trip (or record of it) lags behind the group's, which is common under any network jitter, and does not require adversarial control of other signers. The trigger — a repeated `BlockProposal` message with the same content — is trivially reproducible by the miner (whose proposal loop already re-sends proposals, as noted in the surrounding code comments about `ProposalTooOld`) or by any StackerDB participant able to write to the miner's proposal slot.

### Recommendation
`should_reevaluate_block` should treat any `BlockInfo` with `signed_group.is_some()` or `signed_self.is_some()` (i.e., any block ever endorsed by this signer or the group) the same way it treats `globally_approved_and_responded()` — refuse to re-evaluate/overwrite it — regardless of whether `valid` happens to be `None`. Alternatively, `BlockInfo::from` should never be used to overwrite an existing DB row; instead, `handle_block_proposal` should merge only the fields that legitimately need refreshing (e.g., `block_proposal_data`) while preserving `state`, `signed_self`, and `signed_group` verbatim when they are already set.

### Proof of Concept
1. Miner proposes block `B` at height `h`.
2. Signer S validates `B`... but before S's own validation response arrives (or after S has decided but the in-memory/DB record is not yet marked with `valid=Some(true)`), enough *other* signers broadcast `BlockAccepted` signatures over `B` on StackerDB to cross the weight threshold.
3. `store_and_process_block_signature` on S calls `block_info.mark_locally_accepted(true)`, setting `state=LocallyAccepted`, `signed_group=Some(t)`, `valid` still `None`.
4. The miner (or any party able to write to the proposal slot) re-broadcasts the identical `BlockProposal` for `B`.
5. On S, `handle_block_proposal` → `should_reevaluate_block` returns `true` (all early-return branches miss this specific `valid=None && state=LocallyAccepted` combination) → `BlockInfo::from(block_proposal.clone())` overwrites S's record for `B`, resetting `state` to `Unprocessed` and clearing `signed_group`.
6. A conflicting sibling block `C` at height `h` is now proposed. `get_signed_conflicts`/the pre-commit conflict check on S no longer finds `B` as a signed conflict (its `state` is `Unprocessed`), so S proceeds to sign `C` — producing signatures over two conflicting blocks at the same height.

Note: I was not able to view the bodies of `globally_approved_and_responded()` and `should_reevaluate_reject_reason()`, nor the exact SQL predicate used by `get_signed_conflicts`, before the tool budget ran out; the conclusion that the `LocallyAccepted`/`valid=None`/`signed_group=Some` combination is not excluded by these functions is inferred from their names, from the branch structure of `should_reevaluate_block`, and from the documented semantics in `docs/signer-flows.md`, not from direct inspection of their implementations. This should be verified directly against those three function bodies before treating the PoC as fully confirmed.

    /// Determine if an already tracked block should be re-evaluated based on a new block proposal for it.
    /// Returns true if the block should be re-evaluated, false if it should be ignored.
    fn should_reevaluate_block(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &BlockInfo,
        block_proposal: &BlockProposal,
    ) -> bool {
        let signer_signature_hash = block_info.block.header.signer_signature_hash();
        if block_info.globally_approved_and_responded() {
            info!("{self}: received a block proposal for a globally accepted block to which we have already responded. Ignoring.";
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_info.block.block_id(),
                "block_height" => block_info.block.header.chain_length,
                "burn_height" => block_proposal.burn_height,
                "consensus_hash" => %block_info.block.header.consensus_hash,
                "timestamp" => block_info.block.header.timestamp,
                "signed_group" => block_info.signed_group,
                "signed_self" => block_info.signed_self,
                "valid" => ?block_info.valid
            );
            return false;
        }
        if !should_reevaluate_reject_reason(block_info) {
            if block_info.state == BlockState::PreCommitted {
                // We validated this block but haven't signed it. Signing requires the
                // pre-commit threshold and the conflict checks in `handle_block_pre_commit`.
                // Re-broadcast our pre-commit and re-run that evaluation instead of
                // responding with a signature directly, so a re-proposed block can't
                // bypass those checks.
                info!(
                    "{self}: received a block proposal for a block we have pre-committed to but not signed. Re-evaluating the pre-commit.";
                    "signer_signature_hash" => %signer_signature_hash,
                    "block_id" => %block_info.block.block_id(),
                    "block_height" => block_info.block.header.chain_length,
                    "burn_height" => block_proposal.burn_height,
                    "consensus_hash" => %block_info.block.header.consensus_hash
                );
                self.send_block_pre_commit(signer_signature_hash.clone());
                let address = self.stacks_address.clone();
                self.handle_block_pre_commit(
                    stacks_client,
                    sortition_state,
                    &address,
                    &signer_signature_hash,
                );
                return false;
            }
            if let Some(block_response) = self.determine_response(block_info) {
                self.send_block_response(&block_info.block, block_response);
                return false;
            } else {
                let is_pending = self
                    .signer_db
                    .has_pending_block_validation(&signer_signature_hash)
                    .unwrap_or_else(|e| {
                        warn!("{self}: Failed to load pending block validations: {e:?}");
                        false
                    });
                if is_pending {
                    debug!(
                        "{self}: received a block proposal for a block for which we is already pending validation. Do nothing.";
                        "signer_signature_hash" => %block_info.block.header.signer_signature_hash(),
                        "block_id" => %block_info.block.block_id()
                    );
                    return false;
                } else {
                    info!(
                        "{self}: received a block proposal for this block before, but we do not have a pending validation for it.";
                        "reject_reason" => ?block_info.reject_reason,
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %block_info.block.block_id(),
                        "block_height" => block_info.block.header.chain_length,
                        "burn_height" => block_proposal.burn_height,
                        "consensus_hash" => %block_info.block.header.consensus_hash
                    );
                }
            }
        } else {
            info!(
                "{self}: received a block proposal for this block before, but our rejection reason allows us to reconsider";
                "reject_reason" => ?block_info.reject_reason,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_proposal.block.block_id(),
                "block_height" => block_proposal.block.header.chain_length,
                "burn_height" => block_proposal.burn_height,
                "consensus_hash" => %block_proposal.block.header.consensus_hash
            );
        }
        true
    }
