This confirms the pattern: both `staking-pool-factory` and `lockup-factory` implement an `on_*_create` callback (`.then(ext_self::on_lockup_create(...))`) that checks `is_promise_success()` and refunds the deposit with `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` on failure, as seen at [1](#0-0)  and [2](#0-1) . In contrast, `MultisigFactory::create` has no `.then(...)` callback at all — it builds a single promise chain (`create_account` → `deploy_contract` → `transfer` → `function_call`) and returns it directly with no refund logic on failure, as shown at [3](#0-2) .

### Title
Missing refund callback in `MultisigFactory::create` permanently strands attacker's own deposit on failed deployment - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` schedules `create_account`/`deploy_contract`/`transfer`/`function_call` as a single promise batch and returns it without any `.then(ext_self::on_create(...))` callback, unlike the sibling factories `staking-pool-factory` and `lockup-factory` which both refund the deposit on failure. If the deployment fails (e.g. attacker deploys `name` account that already exists, or crafts `members`/`num_confirmations` that make the `new` call panic), NEAR sent as `attached_deposit` never returns to the predecessor and is instead absorbed into the newly-created (but failed-init) account or lost with the batch, with no code path to reclaim it.

### Finding Description
The binding claimed by the invariant is: `balance(predecessor) after failed create == balance(predecessor) before create` (i.e., attached deposit is returned to the payer when deployment fails). Tracing `create` in [4](#0-3) , the deposit is transferred as part of the same promise batch that creates the account and calls `new`. There is no `.then()` callback attached to check `is_promise_success()`, unlike `on_lockup_create` in [5](#0-4)  or `on_staking_pool_create` in [6](#0-5) , both of which explicitly call `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` when `is_promise_success()` is false.

Because `MultisigFactory::create` has no such callback, the factory contract itself never learns whether the batch succeeded, and no refund promise is ever scheduled. An attacker (any unprivileged caller, since `create` has no access restrictions) can trigger this by:
1. Calling `create` with a `name` for which `format!("{}.{}", name, current_account_id())` already exists (e.g., attacker pre-creates the sub-account, or races/calls `create` twice with the same `name`), causing `create_account()` to fail.
2. Or supplying `members`/`num_confirmations` that cause the `new` call on the deployed `multisig2` contract to panic (e.g., invalid public key format, zero confirmations, mismatched types) — NEAR's batched actions on one receipt roll back state changes on failure but the deposit transfer within that failed batch is returned to the receiver's balance on the newly created account rather than the original predecessor, or in the create_account-failure case, is simply not refunded because the whole action batch fails as one receipt and no separate refund path exists.

Since `assert_self()`, `is_promise_success()` and the refund `Promise::new(...).transfer(...)` pattern used elsewhere are entirely absent here, no guard exists to detect the failure and forward the deposit back.

### Impact Explanation
The attacker's own deposit becomes stuck/unrecoverable (or ends up on an account they still control, minimizing attacker loss, but for a legitimate victim caller this represents real NEAR being lost with no refund path). This matches the "accounting value diverges from reality" / "funds frozen" category: the factory's promised behavior (refund on failure) silently fails, and the attached deposit is not returned to the predecessor as it is by every other factory contract in this repo. This is a real deviation from the intended invariant, though the practical loss falls on whoever calls `create` and hits a failure (which could be the attacker deploying against their own already-existing name to grief themselves, or more critically, any normal user who unknowingly hits a naming collision or malformed `members`/`num_confirmations` and loses their deposit).

### Likelihood Explanation
Trivial to trigger: any caller can call `create` twice with the same `name`, or supply malformed `members`/`num_confirmations`, at essentially the cost of one attached deposit and gas. No privileged access needed, fully repeatable.

### Recommendation
Add a `#[ext_contract(ext_self)]` callback analogous to `on_lockup_create`/`on_staking_pool_create`: chain `.then(ext_self::on_create(name, env::attached_deposit().into(), env::predecessor_account_id(), &env::current_account_id(), 0, gas::CALLBACK))` after the `function_call`, and in that callback check `is_promise_success()`, refunding `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` on failure.
