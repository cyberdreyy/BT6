### Title
Legacy WebAPI Trigger Gateway Handler Skips Allowlist/Rate-Limit Enforcement, Allowing Any Unprivileged Client to Broadcast Attacker-Controlled Trigger Payloads to All DON Nodes - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The reported issue describes a smart contract that lacks a proper access-restriction/upgradeability mechanism, effectively hard-coding one caller path with no way to add the intended authorization/relayer logic later. The equivalent bug class in this repo appears in the internet-facing Gateway's legacy WebAPI trigger handler: `HandleLegacyUserMessage` forwards every syntactically-valid message to all DON nodes, but the allowlist/rate-limit check that is supposed to gate this is literally left as a `TODO` and never implemented, unlike the sibling node-message path which does enforce a rate limiter.

### Finding Description
The gateway's public entry point `gateway.ProcessRequest` decodes an incoming HTTP request and, for "legacy" requests (those with a non-empty `DonId`), calls `msg.Validate()` and then dispatches to the resolved handler's `HandleLegacyUserMessage`: [1](#0-0) 

`Message.Validate()` only checks structural/format constraints (ID/method/DonId lengths, null-byte suffixes, signature length) and extracts a `Sender` address from the ECDSA signature — it does not check that the sender is an authorized/allowlisted identity. Any client can generate a fresh keypair, sign an arbitrary message, and pass `Validate()`: [2](#0-1) 

`HandleLegacyUserMessage` in the capabilities WebAPI handler then processes this message. It checks payload decodability, a non-zero timestamp, and message staleness — but the authorization/allowlist step is explicitly marked as unimplemented with a `TODO` comment, and is skipped entirely before the request is fanned out to every member of the DON: [3](#0-2) 

By contrast, the sibling path that handles *node-to-gateway* traffic (`handleWebAPIOutgoingMessage`) does enforce a `nodeRateLimiter.Allow(nodeAddr)` check before proceeding: [4](#0-3) 

This asymmetry shows the intended design includes a client-side allowlist/rate-limit gate for `HandleLegacyUserMessage` (as the comment states), but it was never implemented — directly analogous to the smart-contract report's core issue: a security mechanism (relayer/caller restriction) that the team intended to exist but is architecturally missing, leaving the entry point open to any caller who can reach it.

### Impact Explanation
Because no allowlist or per-sender rate limiting is enforced in `HandleLegacyUserMessage`, any unprivileged actor who can reach the Gateway's public HTTP endpoint and craft a well-formed, self-signed legacy message can:
- Trigger `MethodWebAPITrigger` payloads that get broadcast via `don.SendToNode` to every member of the target DON, impersonating a "trigger" event to all nodes.
- Exhaust DON node resources or the `savedCallbacks` map (bounded only by time/size pruning) with attacker-controlled traffic, since there's no admission control tied to identity.
- Because the DON-side allowlist that the code comment in `handleWebAPIOutgoingMessage` references ("the connection between the Gateway and DON Node is already authorized via a DON-side and Gateway-side allowlist") is assumed to exist but the corresponding Gateway-side check for this specific path is a stub, the assumed defense-in-depth is not actually present here.

This maps to the "allowlist bypass" / "unauthorized job run" category called out as acceptable analog impact.

### Likelihood Explanation
High for reachability: this is the primary, documented public entry point of the internet-facing Gateway (`gateway.ProcessRequest` → legacy dispatch), requiring no credentials beyond generating an ECDSA keypair to produce a valid signature that passes `Validate()`. No session, API key, or membership check gates this specific code path.

### Recommendation
Implement the allowlist/authorization and rate-limiting check called out by the `TODO` in `HandleLegacyUserMessage` before dispatching to `don.SendToNode`, consistent with the check already performed in `handleWebAPIOutgoingMessage`. The allowlist should validate `msg.Body.Sender` (extracted during `Validate()`) against a configured/queried set of permitted workflow owners or clients for the target `DonId`, and apply per-sender/global rate limiting symmetric to the node-message path.

### Proof of Concept
1. Generate an arbitrary ECDSA keypair (no registration required).
2. Construct a `MessageBody{ MessageId, Method: "web_api_trigger", DonId: <target>, Payload: <TriggerRequestPayload with Timestamp=now> }`, sign it with the new key via `Message.Sign`, satisfying `Validate()`.
3. POST the encoded request to the Gateway's public HTTP endpoint that reaches `gateway.ProcessRequest`.
4. Observe that `HandleLegacyUserMessage` runs the format/timestamp checks only, skips the (unimplemented) allowlist check noted in the `TODO`, and forwards the request via `don.SendToNode` to every member in `h.donConfig.Members` — despite the sender never having been authorized.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
