### Title
Path traversal via unsanitized `AlternateKey` under `FF_HASH_CACHE_KEYS=on` escapes `CacheDir` - ([File: functions/concrete/builder/builder.go])

### Summary
The literal claim that the primary `resolvedKey` returned by `builder.cacheKey` can escape `CacheDir` is false: when `FF_HASH_CACHE_KEYS` is on, `resolvedKey` is always a SHA-256 hex digest of `humanKey`, and when the flag is off, `humanKey` is sanitized by `cachekey.Sanitize`, which resolves `..`/`\`/percent-encoding against a virtual root before it is ever used as a path component. However, the same unsanitized `humanKey` is reused as the **alternate** cache key (`AlternateKey`) when `FF_HASH_CACHE_KEYS` is on, and that value flows unchecked into a real filesystem path via `filepath.Join`, producing a genuine path traversal outside `CacheDir`.

### Finding Description
`builder.cacheKey` (functions/concrete/builder/builder.go:570-603) sets `humanKey = rawKey` unsanitized when `FF_HASH_CACHE_KEYS` is on, and derives `resolvedKey = sha256(humanKey)` in that case [1](#0-0) . Because `resolvedKey` is a fixed-format hex digest whenever the flag is on, and a sanitized value otherwise, `resolvedKey`/`Key` itself can never contain `../`, `\`, or traversal sequences — the question's precise claim about `resolvedKey` escaping is disproven.

The real problem is in `buildCacheArchive` (functions/concrete/builder/builder.go:339-398). It computes:
```
alternateResolved := humanKey
if !b.isFeatureFlagOn(featureflags.HashCacheKeys) {
    alternateResolved = fmt.Sprintf("%x", sha256.Sum256([]byte(humanKey)))
}
``` [2](#0-1) 
When `FF_HASH_CACHE_KEYS` is **on**, the guard `!b.isFeatureFlagOn(...)` is false, so `alternateResolved` keeps the raw, unsanitized `humanKey` (i.e., attacker-controlled `cache:key` / `CACHE_FALLBACK_KEY` value, expanded but never sanitized) and is assigned to `archive.AlternateKey`.

That `AlternateKey` is passed through `stages.CacheArchive.AlternateKey` to `alternateArchivePath`, which calls `cacheArchivePath(e, key)`:
```go
func cacheArchivePath(e *env.Env, key string) string {
    absPath := filepath.Join(e.CacheDir, key, "cache.zip")
    ...
}
``` [3](#0-2) 
`filepath.Join` cleans the path, so a key like `../../other-project/secret` resolves the result outside `e.CacheDir`. This alternate path is then passed as `--alternate-file` to the `cache-archiver` helper command [4](#0-3) , meaning the helper process is instructed to write/rename an archive at an attacker-chosen filesystem path relative to `CacheDir`.

The guard `if alternateResolved == resolvedKey { alternateResolved = "" }` only prevents the traversal-path from being used when it happens to coincidentally equal the (hashed) primary key — it provides no sanitation. No other check validates `AlternateKey` against `CacheDir` boundaries before it is joined into a path.

### Impact Explanation
An attacker-controlled `cache:key` (or `CACHE_FALLBACK_KEY`) value containing `../` segments, when combined with `FF_HASH_CACHE_KEYS=on`, causes the runner to compute an "alternate" cache archive file path that escapes the per-project `CacheDir`. This is passed to the `cache-archiver` helper as `--alternate-file`, potentially causing a cache archive write/rename outside the intended cache root — matching the scoped impact of cross-project/out-of-root cache file access, though via the `AlternateKey`/`--alternate-file` mechanism rather than the primary `resolvedKey` named in the question.

### Likelihood Explanation
Feasible for any pipeline author who can set `cache:key` (or `CACHE_FALLBACK_KEY`) and toggle `FF_HASH_CACHE_KEYS=on` as a job variable — both are ordinary `.gitlab-ci.yml`/CI-variable controlled inputs, no special privileges required. It reproduces deterministically on every job run using such a configuration.

### Recommendation
Do not use the raw/unsanitized `humanKey` for the `AlternateKey` path component under `FF_HASH_CACHE_KEYS=on`. Either always sanitize (or hash) the value used to construct `AlternateKey` regardless of feature-flag state, or validate/clean the resulting path in `cacheArchivePath`/`cacheArchivePath`-equivalent in `functions/concrete/run/stages/cache_extract.go` to ensure it stays within `e.CacheDir` before passing it to the helper command.

### Proof of Concept
Go unit test in `functions/concrete/builder/builder_test.go`:
```go
func TestBuildCacheArchive_AlternateKeyEscapesCacheDir(t *testing.T) {
    job := baseJob()
    job.Cache = []spec.Cache{
        {Key: "../../other-project/secret", Paths: []string{"build/"}, Policy: spec.CachePolicyPush},
    }
    vars := newTestVars(t, nil, expandValues(map[string]string{"../../other-project/secret": "../../other-project/secret"}))
    ff := func(f string) bool { return f == featureflags.HashCacheKeys }

    config := buildConfig(t, job, vars, WithFeatureFlagProvider(ff))
    require.Len(t, config.CacheArchive, 1)
    archive := config.CacheArchive[0]

    // resolvedKey (Key) is safe: sha256 hex, 64 chars.
    assert.Len(t, archive.Key, 64)
    // AlternateKey is NOT sanitized and contains traversal.
    assert.Contains(t, archive.AlternateKey, "../")
}
```
Combined with an integration-level assertion in `functions/concrete/run/stages/cache_archive_test.go` that `cacheArchivePath(env, archive.AlternateKey)` (or the resulting `--alternate-file` argument) resolves to a path outside `env.CacheDir`, e.g. via `filepath.Rel`/`strings.HasPrefix` check failing to stay under `CacheDir`.

// archivePath mirrors CacheExtract.archivePath — see that doc comment.
func (s CacheArchive) archivePath(e *env.Env) string {
	return cacheArchivePath(e, s.Key)
}

func (s CacheArchive) alternateArchivePath(e *env.Env) string {
	return cacheArchivePath(e, s.AlternateKey)
}

func cacheArchivePath(e *env.Env, key string) string {
	absPath := filepath.Join(e.CacheDir, key, "cache.zip")
	rel, err := filepath.Rel(e.WorkingDir, absPath)
	if err != nil {
		return absPath
	}
	return rel
}
