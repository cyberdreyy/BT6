### Title
Unauthenticated pipeline-run `Resume` endpoint allows arbitrary task-result injection - (File: core/web/pipeline_runs_controller.go)

### Summary
`PipelineRunsController#Resume` is wired into the router as a completely unauthenticated route, `unauthedv2.PATCH("/resume/:runID", prc.Resume)` [1](#0-0) , mirroring the `VestingWallet#release()` pattern: the state-changing action (finishing a suspended pipeline task and resuming the run) has no access control at all, and the code relies solely on the caller knowing an unguessable value (the task's UUID) rather than any authentication.

### Finding Description
The route is registered with no `auth.Authenticate` middleware, unlike every other `/v2/*` endpoint which requires session/token/external-initiator auth [2](#0-1) . The handler itself performs no ownership or credential check — it only parses the `runID` path param as a UUID and directly calls `App.ResumeJobV2` with attacker-supplied JSON body content: [3](#0-2) 

This design intentionally mirrors the external-adapter async callback flow: when a `BridgeTask` runs asynchronously, it embeds a `responseURL` of the form `.../v2/resume/<taskUUID>` in the outgoing request to the bridge adapter [4](#0-3) , and the adapter is expected to `PATCH` back to that URL with the real result once ready. The node deliberately does not require credentials on this endpoint because the external adapter has none — access control is delegated entirely to the secrecy of the UUID, and the audit event is literally named `UnauthedRunResumed` [5](#0-4) , showing the team already knows this endpoint is deliberately open, exactly as the Salty team argued `VestingWallet#release()` intentionally has no access control by design.

The parallel to the external report's root cause is that the *integration* around the unauthenticated primitive is what matters, not the primitive itself. In Salty, `Upkeep` failed to account for `release()` being callable by anyone. Here, the risk hinges on whether the "secret" UUID is actually kept secret throughout the system. The `Show`/`Index` endpoints on the same controller return full pipeline run/task details, including task UUIDs, for any authenticated session [6](#0-5)  — I could not confirm from the indexed code whether these read endpoints are gated behind `RequiresEditRole`/`RequiresRunRole` or are reachable by the lowest ("view") role, since the relevant `jobsRoute`/`pipelineRunsRoutes` wiring in `router.go` was not fully visible in the indexed context.

### Impact Explanation
If the task UUID is ever observable by a lower-privileged or unauthenticated party (e.g., leaked via logs, via a "view"-role API response, via a misconfigured reverse proxy that logs URLs, or via network capture of the plaintext callback to the external adapter), any actor can `PATCH /v2/resume/:runID` with fabricated `pipeline.ResumeRequest` data to force-complete a suspended pipeline task with attacker-chosen values. Because pipeline runs back price feeds, VRF fulfillment, and other jobs whose outputs can trigger on-chain transactions, this is a potential vector for injecting falsified data into a job run — directly analogous to the "fund/reward misdirection" impact class the Salty report addressed, but with confidentiality-of-a-token substituting for pure absence of access control.

### Likelihood Explanation
Likelihood is bounded by how well the UUID token is protected as a secret across the whole system (transport, logs, and any authenticated-but-lower-privileged read APIs that might expose it). I was not able to confirm from available index content whether the `Show`/`Index` read routes for pipeline runs enforce the same role restriction as the guessing-resistance requires; this needs verification against the live router configuration and role-check middleware in a full checkout, which the index does not fully expose.

### Recommendation
- Treat the task UUID as a true bearer secret: ensure it is never returned in any authenticated response accessible to non-admin/non-edit roles, is not logged in plaintext, and is transmitted only over TLS to the external adapter.
- Consider binding the resume callback to additional adapter-known secrets (e.g., the bridge's per-bridge shared token) in addition to the task UUID, rather than relying on UUID unguessability alone.
- Add rate limiting / anomaly detection on `/v2/resume/:runID` to reduce brute-force feasibility.

### Proof of Concept
Not independently reproducible from the indexed code alone — full confirmation requires validating (in a live checkout) whether pipeline run/task UUIDs are exposed through any lower-privileged or unauthenticated API response, which would let an external actor learn a `runID` and then call:
```
PATCH /v2/resume/<taskUUID>
{"error":null,"value":"<attacker-controlled result>"}
```
which per `PipelineRunsController#Resume` [3](#0-2)  requires no authentication headers whatsoever.

```go
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
```
