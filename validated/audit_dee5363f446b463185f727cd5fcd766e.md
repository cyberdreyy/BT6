### Title
Stale withdraw reserve in `ProgrammableBorrower` lets the borrower drain funds owed to epoch-end withdraw requests, forcing a spurious default - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
`ProgrammableBorrower.availableToBorrow()` reserves liquidity for epoch-end withdrawals using `epochPendingWithdraws`, a value snapshotted once inside `onStartEpoch()`. `IdleCDOEpochVariant._stopEpoch()` later pulls the *fresh* `IdleCreditVault.pendingWithdraws()`, which is explicitly re-read after `prepareStopEpochWithApr0()` because APR0 settlement can increase it. This is the same bug class as the nano-node report: the borrow-cap check (`availableToBorrow`) is evaluated against a reservation captured before the obligation actually grows, i.e. the "votes" are checked against a stale copy taken before the state the check is supposed to guard against.

### Finding Description
- At `onStartEpoch(uint256 _pendingWithdraws)` the CDO passes the pending-withdraw total known at that instant and it is stored in `epochPendingWithdraws` (`ProgrammableBorrower.sol` ~line 205).
- For the whole epoch, `_borrow()` caps draws via `availableToBorrow()`, which only subtracts that snapshot: `reserved = epochPendingWithdraws` (`~line 353`).
- At `_stopEpoch`, the CDO calls `_strategy.prepareStopEpochWithApr0(_interest)` and *then* reads `uint256 _pendingWithdraws = _strategy.pendingWithdraws()`, with the comment "Pending withdraws may be increased during APR0 settlement" (`IdleCDOEpochVariant.sol` lines 362-364).
- The CDO then demands `_amountToPullFromBorrower + _pendingWithdraws` from the borrower (`onStopEpoch`, line 398; `getFundsFromBorrower` transferFrom, line 408).
- If the borrower legitimately drew everything allowed by the stale reserve, `onHand + vault < amountRequired`. `onStopEpoch` returns `true` when `shortfall > _currentVaultAssets()` (line 245, deliberately deferring to the transferFrom failure), the pull reverts, the catch executes `_handleBorrowerDefault(_amountToPullFromBorrower + _pendingWithdraws)` (line 504) and the facility enters the defaulted/recovery state.
- `epochPendingWithdraws` is only cleared at the end of `onStopEpoch` (line 264); nothing re-synchronizes it with the strategy's growing `pendingWithdraws` between `startEpoch` and `stopEpoch`.

So the "lock is released" between snapshotting the withdrawal obligation (`onStartEpoch`) and enforcing it against borrower draws (`availableToBorrow`), exactly like the vote cache reading an election after the `active_elections` mutex is dropped.

### Impact Explanation
A solvent, honest borrower is reported as defaulted because liquidity that should have been reserved for APR0-generated withdraw requests was allowed to leave the contract. `_handleBorrowerDefault` flips the vault into the default flow: normal withdrawals are blocked, LPs are pushed into `postDefaultRequests`/`_claimDefaulted*` recovery claims, and tranche prices take the recovery haircut until `finalizeDefault`/`finalizeDefaultRecovery` completes — i.e. insolvency state plus temporary freezing of all LP funds, proportional to the delta between real `pendingWithdraws` and the stale `epochPendingWithdraws` reserve.

### Likelihood Explanation
Requires the programmable-borrower variant in APR0/minted mode where `prepareStopEpochWithApr0` grows `pendingWithdraws`, and the borrower/executor drawing close to `availableToBorrow()`. Both are normal, expected flows — APR0 users' settlement naturally creates withdraw obligations at stop time, and executors are explicitly meant to draw the maximum available. The unprivileged trigger is simply holding tranche/APR0 positions whose settlement inflates `pendingWithdraws`; the borrow itself is performed by honest keeper sequencing, which the threat model permits. One caveat I could not fully verify within scope: whether mid-epoch `requestWithdraw` is enabled (the `allowAAWithdrawRequest`/`allowBBWithdrawRequest` flags appear set only around `stopEpoch`); the finding stands on the documented APR0-settlement growth alone even if mid-epoch requests are disabled.

### Recommendation
Keep the borrow reservation synchronized with the live obligation: either expose `IdleCreditVault.pendingWithdraws()` to `ProgrammableBorrower` and compute `reserved` from the fresh value in `availableToBorrow()`, or add an `_onlyIdleCDO` sync function the CDO calls whenever `pendingWithdraws` changes (including a pre-settlement sync inside `onStopEpoch` before clearing `epochPendingWithdraws`). At minimum, in `_stopEpoch` compare the post-settlement `_pendingWithdraws` with the borrower-side reserve and treat the deficit as expected pull, not as borrower default.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/ProgrammableBorrowerCreditVault.t.sol` setup):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "./ProgrammableBorrowerCreditVault.t.sol";

contract StaleReserveDefaultTest is ProgrammableBorrowerCreditVaultTest {
    function testStaleReserveForcesDefault() external {
        // epoch running, APR0 users hold positions; pendingWithdraws = P0 at startEpoch
        uint256 borrowed0 = pb.availableToBorrow();
        // honest keeper draws the full "available" amount; stale reserve excludes
        // the pendingWithdraws that APR0 settlement will add at stopEpoch
        vm.prank(executor);
        pb.executeBorrow(borrowed0);

        // warp past epoch end
        vm.warp(cdo.epochEndDate() + 1);

        // APR0 settlement inside _stopEpoch grows pendingWithdraws to P1 > P0;
        // onStopEpoch returns true (shortfall > vault assets), transferFrom of
        // amountToPull + P1 reverts -> _handleBorrowerDefault
        vm.prank(manager);
        cdo.stopEpoch(0, 0);

        assertTrue(cdo.defaulted(), "solvent borrower forced into default by stale reserve");
    }
}
```
