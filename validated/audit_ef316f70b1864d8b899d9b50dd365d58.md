### Title
Unvalidated fee amounts in `createDstEscrow` allow underflow-bricking of `EscrowDst.withdraw`/`publicWithdraw` - (File: `contracts/BaseEscrowFactory.sol`, `contracts/EscrowDst.sol`)

### Summary
`createDstEscrow` accepts caller-supplied `Immutables.parameters` (encoding `protocolFeeAmount` and `integratorFeeAmount`) with no validation that their sum does not exceed `immutables.amount`. `EscrowDst._withdraw` later computes `immutables.amount - integratorFeeAmount - protocolFeeAmount` using Solidity 0.8 checked arithmetic. If the fee sum exceeds `amount`, every call to `withdraw`/`publicWithdraw` reverts, permanently bricking the fund-release path of that escrow — the same unchecked-subtraction root cause as the referenced `LPDA.getPrice()` underflow.

### Finding Description
On the source-chain path, `BaseEscrowFactory._postInteraction` explicitly guards against this exact condition: [1](#0-0) 
computing `integratorFeeAmount`/`protocolFeeAmount` on-chain via `FeeTaker._getFeeAmounts` and reverting with `InvalidFeeAmounts` if `integratorFeeAmount + protocolFeeAmount >= takingAmount`.

However, `createDstEscrow` does not derive fee amounts on-chain at all — it simply takes the caller-supplied `dstImmutables` (whose `parameters` field carries `protocolFeeAmount`/`integratorFeeAmount`) verbatim and deploys the clone, funding it from `msg.sender`: [2](#0-1) 
There is no check equivalent to the `InvalidFeeAmounts` guard on this path — nothing enforces `protocolFeeAmount + integratorFeeAmount < immutables.amount`.

`EscrowDst._withdraw` then reads these fee values straight from calldata and performs an unchecked-order subtraction: [3](#0-2) 
Specifically line 92: `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;`. If `integratorFeeAmount + protocolFeeAmount > immutables.amount`, Solidity 0.8's default checked math causes this subtraction to revert, exactly mirroring the LPDA `startPrice - dropPerSecond*timeElapsed` underflow pattern: an unvalidated arithmetic input from an untrusted configuration path reaches a subtraction that can go negative in `uint256`.

Because both `withdraw` (`onlyCaller(taker)`) and `publicWithdraw` (`onlyAccessTokenHolder`) route through the same `_withdraw` internal function, both entry points revert identically once the fee parameters are misconfigured — there is no way to release the escrowed destination funds to the maker.

### Impact Explanation
Once `_withdraw` is bricked, the only remaining exit is `cancel()`, which does not use the fee parameters and sends the full `immutables.amount` back to `taker`: [4](#0-3) 
This is gated by the `DstCancellation` timelock. Consequently:
- The intended fund transfer to the maker (the purpose of the destination escrow in the swap lifecycle) can never complete — this is a temporary freeze of the destination-chain funds for the entire withdrawal window, and the swap itself fails even though a valid secret exists.
- Funds are only recoverable via `cancel()` after the cancellation delay, and even then only by the `taker`, not the intended recipient (`maker`).
- This matches the Medium/High bounty criteria: "smart contract unable to operate because required token/native balances can be broken by an unprivileged actor" and "temporary freezing of funds during the live swap lifecycle," since `createDstEscrow` has no access control and any caller (an unprivileged actor supplying the `Immutables`, typically the taker/resolver itself, but the function itself imposes no privilege check) can set the fee fields that trigger this underflow.

### Likelihood Explanation
`createDstEscrow` is a normal, unprivileged, publicly reachable entry point in the live swap flow — it is the exact "destination path" described in the audit pivots (`createDstEscrow` -> timelock binding -> native/ERC20 funding -> destination withdraw/cancel flow). Unlike the source-side `_postInteraction`, which derives and bounds-checks fees on-chain, the destination-side flow blindly trusts caller-provided fee amounts embedded in `parameters`. Any misconfiguration (accidental or deliberate) of a resolver's off-chain fee-encoding logic, or a resolver script bug, directly triggers the underflow with no on-chain safeguard — making this readily reachable without any privileged role.

### Recommendation
Add an explicit validation in `createDstEscrow` (or in `EscrowDst._withdraw`) enforcing `integratorFeeAmount + protocolFeeAmount < immutables.amount`, mirroring the existing `InvalidFeeAmounts` check used in `_postInteraction`:
```solidity
uint256 integratorFeeAmount = immutables.integratorFeeAmount();
uint256 protocolFeeAmount = immutables.protocolFeeAmount();
if (integratorFeeAmount + protocolFeeAmount >= immutables.amount) revert InvalidFeeAmounts();
```
placed inside `createDstEscrow` before deployment, so malformed fee configurations are rejected at creation time rather than bricking the withdrawal path after funds are already locked.

### Proof of Concept
1. A taker calls `createDstEscrow` with `dstImmutables.amount = 100` (destination token amount) and `parameters` encoding `protocolFeeAmount = 60`, `integratorFeeAmount = 60` (sum = 120 > 100). No revert occurs since no validation exists: [2](#0-1) 
2. After the withdrawal timelock opens, the taker (or an access-token holder) calls `withdraw(secret, immutables)` / `publicWithdraw(secret, immutables)`.
3. Execution reaches `_withdraw`, which computes `immutables.amount - integratorFeeAmount - protocolFeeAmount` = `100 - 60 - 60`, which underflows and reverts under Solidity 0.8 checked arithmetic: [5](#0-4) 
4. Every subsequent call to `withdraw`/`publicWithdraw` reverts identically; the maker never receives the destination tokens, and the only recovery path is `cancel()` (funds returned to `taker`, not `maker`) after the cancellation timelock elapses.

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```

```text
    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```
