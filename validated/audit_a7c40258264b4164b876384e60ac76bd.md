### Title
JWT replay-cache TOCTOU race between `isReplay` and `recordUsage` allows duplicate authorized DON execution - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks `jwtReplayCache.isReplay(claims.ID)` under an `RLock`, performs authorized-key lookup without holding any lock, and only records usage via `recordUsage` (a separate `Lock`) after that lookup succeeds. Two concurrent `HandleUserTriggerRequest` calls carrying the identical signed JWT (`jti`) can both pass `isReplay` before either calls `recordUsage`, producing two successful authorizations and two DON executions for a single signed request.

### Finding Description
The attacker-reachable path is: HTTP/gateway request → `httpTriggerHandler.HandleUserTriggerRequest` → `h.authorizeRequest` → `WorkflowMetadataHandler.Authorize` [1](#0-0) , which calls:

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	...
	if h.jwtCache.isReplay(claims.ID) {
		...
		return nil, errors.New(...)
	}
	...
	h.jwtCache.recordUsage(claims.ID)
	return &key, nil
}
``` [2](#0-1) 

`isReplay` and `recordUsage` are independent lock acquisitions on `jwtReplayCache.mu` (an `RWMutex`):
```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()
	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	cache.cache[jti] = time.Now()
}
``` [3](#0-2) 

Because there is no single atomic "check-and-set" operation, if the same signed JWT is submitted twice in parallel, both goroutines can execute `isReplay` (returning `false`) before either reaches `recordUsage`. Both requests then pass the authorized-key lookup (`keys[key]` check, which is a stateless read of the authorized signer map and not itself a replay guard) and both return successfully from `Authorize`, allowing the caller (`HandleUserTriggerRequest`) to proceed to `sendWithRetries`, dispatching the workflow execution to the DON twice for what should be a single-use signed authorization. Nothing else in the request path (rate limiting via `checkRateLimit`, `setupCallback`'s per-`requestID` uniqueness check) prevents this, since those checks key on `requestID`, not the JWT `jti`, and the attacker can supply two different request IDs while reusing the same signed JWT, provided the underlying JWT `authorization_details`/digest binding (if any) does not tie the JWT to a single request ID. Even where digest-binding exists, the race is inherent to the two-step lock pattern, not prevented by it.

By contrast, the sibling `vault` package addresses exactly this class of race with an atomic `RequestReplayGuard.CheckAndRecord`, which does the existence-check and insertion under a single `Mutex.Lock` acquisition:
```go
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()
	g.clearExpiredLocked()
	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}
	g.seen[digest] = expiresAtUnix
	return nil
}
``` [4](#0-3)  This confirms the codebase is aware of and normally guards against this exact TOCTOU pattern elsewhere, but `jwtReplayCache` in the HTTP trigger gateway path was not implemented atomically.

### Impact Explanation
An unprivileged JWT holder authorized to trigger a specific workflow can cause a single signed `workflows.execute` request to be dispatched to the DON more than once by racing two concurrent submissions before the replay cache records the `jti`. This is an authorization/request-binding bypass ("one signature = one authorized action" invariant violated), resulting in duplicate DON executions charged to/attributed to the workflow at the requester's or workflow owner's expense — mapping to the "unauthorized job run" / replay-bypass impact class.

### Likelihood Explanation
Exploitability requires only: (1) possession of one valid signed JWT authorized for a workflow (a normal low-privileged capability of any legitimate workflow-execute caller — no operator/admin access needed), and (2) the ability to send two requests concurrently, which is trivial over HTTP/gateway. The race window is small (time between `isReplay` and `recordUsage`, including the authorized-key map lookup in between) but is a classic, reliably-triggerable Go TOCTOU race, especially under load or with slight artificial delay/synchronization by the attacker (e.g., firing both requests in the same instant from parallel goroutines/connections). This is repeatable and does not depend on any misconfiguration.

### Recommendation
Replace the separate `isReplay`/`recordUsage` calls with a single atomic check-and-set method (mirroring `vault.RequestReplayGuard.CheckAndRecord`), performed under one `Lock()` acquisition in `jwtReplayCache`, e.g. add a `CheckAndRecord(jti string) error` method that checks existence and inserts atomically, and call it in `Authorize` immediately after the JWT is verified (before or in place of the separate authorized-key check ordering, ensuring the whole check-and-insert is one critical section).

### Proof of Concept
Go test in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler_test.go`:
1. Set up a `WorkflowMetadataHandler` with a registered workflow ID and an authorized signer key (as done in existing `TestWorkflowMetadataHandler_Authorize` "JWT replay protection" subtest).
2. Create one signed JWT (`tokenString`) with a fixed `jti`, request ID, and workflow ID.
3. Launch two goroutines, each calling `handler.Authorize(workflowID, tokenString, req)` concurrently (using a `sync.WaitGroup` and a shared start barrier, e.g. both waiting on a channel closed simultaneously to maximize race probability), collecting `(key, err)` results in a channel.
4. Optionally run with `go test -race -count=100` to increase reproducibility of the race window.
5. Assert: exactly one of the two calls returns `err == nil` and a non-nil key; the other returns the "JWT token has already been used" error. Under the current implementation, running many iterations under `-race` (or inserting a `time.Sleep`/hook between `isReplay` and `recordUsage` for determinism) should show both calls occasionally returning `err == nil`, demonstrating the double-authorization bug.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
```
