### Title
Confirmations from removed multisig members remain valid and count toward `num_confirmations`, allowing a request to execute below the live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
The `MultiSigContract::confirm()` function counts the size of a request's confirmation set against `num_confirmations` without verifying that every account/key already recorded in that set is still a current multisig member. `delete_member()` (and the analogous `DeleteKey` handling in the legacy `multisig` contract) only purges pending requests that were *submitted* by the removed member, but never scrubs that member's confirmation entries from other, still-open requests they had merely *confirmed*. A stale confirmation from a removed member therefore keeps counting toward the K-of-N threshold, letting a request execute with fewer than `num_confirmations` live confirmers.

### Finding Description
`confirm()` finalizes and executes a request purely based on the size of the stored `confirmations` set: [1](#0-0) 

`delete_member()` removes a departing member from `self.members` and cleans up only the requests that member itself submitted (`r.member == member`); it does not iterate `self.confirmations` to strip that member's entry from requests submitted by *other* members that this member had already confirmed: [2](#0-1) 

`assert_valid_request()` (called from `confirm`) only checks that the *caller* is currently a member and that the request/confirmation records exist — it never re-validates the members already present in the stored confirmation `HashSet`: [3](#0-2) 

As a result, once a member who previously confirmed request `R` (but did not submit it) is removed via `DeleteMember`, `R`'s confirmation set still contains that now-invalid member's identity. Any subsequent live member confirming `R` can push `confirmations.len()+1 >= num_confirmations` to true and trigger `execute_request`, even though the number of currently-live confirmers is one less than `num_confirmations`. The same structural flaw exists in the legacy `multisig` contract, where `DeleteKey` also filters cleanup by `r.signer_pk == pk` (the submitter key only): [4](#0-3) 

This breaks the core custody/authorization guarantee of the contract: `confirmations counted == live members who approved`. Instead, `confirmations counted > live members who approved`, meaning a `Transfer`, `FunctionCall`, `AddKey`, or any other `MultiSigRequestAction` can be executed with fewer than the configured K live approvals.

### Impact Explanation
This is Critical: it allows a multisig request (e.g., `Transfer`, `AddKey`, `FunctionCall`) to execute below the threshold of confirmations from members who are actually authorized at execution time, directly matching "a multisig request executed below threshold." Funds or permissions controlled by the multisig account can move or change with less real consensus than the K-of-N scheme is supposed to require.

### Likelihood Explanation
Likelihood is high in any multisig that experiences normal membership churn (a common, expected operational event — e.g., removing a departing employee's key/account). No malicious action is required from the removed member after their removal; any subset of the remaining live members simply needs to add enough confirmations to reach the stale total, which is a routine multisig operation, not an attack requiring special access beyond normal member confirm/delete_member calls.

### Recommendation
When removing a member (`delete_member`/`DeleteKey`), scan all pending requests' confirmation sets (not just the requests the removed member submitted) and remove that member's/key's entry from every set. Alternatively, at `confirm()` time, re-validate that every entry currently stored in `confirmations` for the request still corresponds to a live member before counting it toward `num_confirmations`, discarding stale entries.

### Proof of Concept
Using `multisig2/src/lib.rs` with members `{A, B, C, D}` and `num_confirmations = 3`:
1. `B` calls `add_request_and_confirm(R)` where `R = Transfer{...}` — `confirmations(R) = {B}`.
2. `A` calls `confirm(R)` — `confirmations(R) = {B, A}` (size 2, `<3`, not yet executed).
3. Members `B`, `C`, `D` create and confirm a separate `DeleteMember{A}` request (3 confirmations, satisfying `self.members.len() - 1 >= self.num_confirmations` in `delete_member`, line 358). This executes, removing `A` from `self.members`.
   - Because `R`'s submitter (`r.member`) is `B`, not `A`, the cleanup loop in `delete_member` (lines 362-371) does not touch `R`; `confirmations(R)` still contains `A`.
4. `C` (a live member) calls `confirm(R)`. `assert_valid_request` passes because `C` is a live member. `confirmations.len() (2) + 1 >= num_confirmations (3)` is true, so `execute_request` runs and the `Transfer` is executed.
5. Result: only `B` and `C` are actually-live members who approved `R` (2 live approvals), yet the request executed as if 3 confirmations from current members were obtained — the stored, now-invalid confirmation from removed member `A` was silently counted.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
