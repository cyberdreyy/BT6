## Title
`reached_agreement`/`reached_disagreement` use floor-division while the on-chain block threshold uses ceiling-division — a signer can act on a global state view backed by less than the real 70% majority — ([File: libsigner/src/v0/signer_state.rs])

### Summary
`GlobalStateEvaluator::reached_agreement` and `reached_disagreement` in `libsigner/src/v0/signer_state.rs` compute the 70%/30% weight thresholds with plain integer division (floor), while the canonical, consensus-critical threshold used for actual block-signature verification, `NakamotoBlockHeader::compute_voting_weight_threshold` in `stackslib/src/chainstate/nakamoto/mod.rs`, rounds the same 70% *up* (ceiling). For `total_weight` values where `total_weight * 7` is not a multiple of 10, the two computations diverge by exactly 1 unit of weight — the same class of "wrong scaling/rounding constant produces a materially different percentage" bug as the reported `routeFeeRate` off-by-10x issue, just manifesting as an off-by-one rather than off-by-10x.

### Finding Description
`compute_voting_weight_threshold` (the value actually enforced when verifying block signatures on-chain and re-derived by the v0 signer at `stacks-signer/src/v0/signer.rs:1298` and `:2498` before it will put a signature over a block or broadcast a group-signed block) explicitly rounds up: [1](#0-0) 

By contrast, `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` — which decide the signer's *global state machine* view (protocol version, burn view, current miner, tx-replay set) — use a plain floor division of the same `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` constant: [2](#0-1) 

For any `total_weight` where `total_weight * 7 % 10 != 0`, `compute_voting_weight_threshold` requires 1 more unit of weight than `reached_agreement`'s floor computation. E.g. for `total_weight = 11`: `compute_voting_weight_threshold` returns `8` (ceil(7.7)), while `reached_agreement(7)` already returns `true` (`7 >= floor(77/10)=7`). The test suite even documents and locks in this floor behavior as intended for the global-state evaluator: [3](#0-2) 

`reached_agreement` gates `determine_global_state`, `determine_latest_supported_signer_protocol_version`, `determine_global_burn_view`, and the tx-replay-set majority/prefix logic: [4](#0-3) 

Because the global state machine (current miner, burn view, protocol version, tx-replay set) is what governs whether a signer treats a given miner/tenure as legitimate and what replay-transaction set it will accept in a proposal, a discrepancy between "what weight the signer considers sufficient to declare global agreement" and "what weight is actually required to produce a chain-valid block signature" breaks the equality between the signer's internally-assumed threshold and the verified/canonical threshold. In small or oddly-weighted signer sets, this off-by-one gap means a set of colluding/coordinated non-majority signers (weight strictly between the floor and the ceiling thresholds) could be recognized by `determine_global_state` as constituting "global agreement" on a burn view, current-miner choice, or replay set, when in fact the real (ceiling) 70% supermajority required by `verify_signer_signatures`/`compute_voting_weight_threshold` has not been met.

### Impact Explanation
This falls under the "acting on a stale reward set/threshold" impact class: a signer's global-state agreement (which decides which miner is treated as canonical and which tx-replay set to enforce) can be triggered by strictly less than the real 70% consensus threshold that gates actual block signing. In the worst case this could let the signer's local state machine settle on a "current miner"/burn view/replay set that a full ceiling-majority has not actually endorsed, causing it to diverge from signers correctly using the ceiling threshold — a liveness/consistency wedge across the signer set, or a replay-set decision the true majority did not agree to. The magnitude is small (1 unit of weight, only in specific `total_weight` residues), which keeps this at High rather than Critical, and it does not by itself forge a block signature.

### Likelihood Explanation
This is deterministic and requires no majority collusion beyond weight arithmetic falling on the specific residue where `total_weight * 7 mod 10 != 0` — a very common case (any `total_weight` not a multiple of 10 already produces the discrepancy, e.g. `total_weight=11,13,17,...`). No cryptographic breaks, no external actor collusion beyond normal, honestly-signed `StateMachineUpdate` gossip from existing signers at the boundary weight is needed; the two functions are simply inconsistent constants/rounding for the same conceptual 70% threshold.

### Recommendation
Make `reached_agreement`/`reached_disagreement` use the same ceiling-based rounding as `NakamotoBlockHeader::compute_voting_weight_threshold` (or better, have both call the single canonical function) so that "global agreement" as used by the signer's state machine can never be declared with less weight than what `verify_signer_signatures` will actually require on-chain.

### Proof of Concept
Given `total_weight = 11` and `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD = 7`:
- `NakamotoBlockHeader::compute_voting_weight_threshold(11)` → `ceil(11*7/10) = ceil(7.7) = 8` (this is what `verify_signer_signatures` and the v0 signer's own pre-commit/signature-threshold checks require, see `stacks-signer/src/v0/signer.rs:1298`, `:2498`).
- `GlobalStateEvaluator::reached_agreement(7)` on the same `total_weight=11` → `7 >= (11*7)/10 = 7` → `true`.

So a coalition with combined weight `7` out of `11` (63.6%, below the required 70% ceiling of `8`) is treated by `determine_global_state`/`determine_latest_supported_signer_protocol_version`/`determine_global_burn_view` as having reached global agreement, while the exact same weight would be rejected as insufficient by the block-signature threshold check used elsewhere in the same signer (`stacks-signer/src/v0/signer.rs:1333`, `:2503`). This constant/rounding mismatch is directly analogous to the reported `routeFeeRate` bug: a value meant to represent "70%" is computed two different ways in two places that must agree, and the discrepancy silently changes the effective threshold that participants sign off on.     /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }

    /// Check if the supplied vote weight crosses the global agreement threshold.
    /// Returns true if it has, false otherwise.
    pub fn reached_agreement(&self, vote_weight: u32) -> bool {
        u64::from(vote_weight)
            >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
                / 10
    }

    /// Check if the supplied vote weight crosses the blocking minority threshold.
    /// Returns true if it has, false otherwise.
    pub fn reached_disagreement(&self, vote_weight: u32) -> bool {
        u64::from(vote_weight)
            > u64::from(self.total_weight).strict_mul(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
                / 10
    }

#[test]
/// Locks the joint behavior of `reached_agreement` and `reached_disagreement`
/// at a single `total_weight`:
///   - agreement: `>=` 70% (inclusive)
///   - disagreement: `>` 30% (strict)
///   - three regions: [0, 30%] neither, (30%, 70%) disagreement only,
///     [70%, total] both
///
/// Walking 0, 30%, 30%+1, 70%-1, 70% catches a flipped inequality on either
/// side and any drift between the two threshold constants. Also pins the
/// "agreement implies disagreement" relation, which holds as long as the
/// agreement threshold sits above the disagreement one.
fn thresholds_partition_weight_space() {
    let evaluator = evaluator_with_total_weight(1_000_000_000);

    // 0%: neither.
    assert!(!evaluator.reached_agreement(0));
    assert!(!evaluator.reached_disagreement(0));

    // Exactly 30%: strict `>`, so not yet disagreement.
    assert!(!evaluator.reached_agreement(300_000_000));
    assert!(!evaluator.reached_disagreement(300_000_000));

    // One unit past 30%: gap region, disagreement only.
    assert!(!evaluator.reached_agreement(300_000_001));
    assert!(evaluator.reached_disagreement(300_000_001));

    // One unit below 70%: still in the gap.
    assert!(!evaluator.reached_agreement(699_999_999));
    assert!(evaluator.reached_disagreement(699_999_999));

    // Exactly 70%: agreement (`>=`), and disagreement still holds since 70% > 30%.
    assert!(evaluator.reached_agreement(700_000_000));
    assert!(evaluator.reached_disagreement(700_000_000));
}
