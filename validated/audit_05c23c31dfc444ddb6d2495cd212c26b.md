### Title
Inconsistent duplicate-tenure-change guard: v1 chainstate uses "globally accepted" instead of "signed" check, weakening the equivocation guard - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
The Sherlock report's root cause is a scope mismatch: a function was called with a narrower operation mode (`EXACT_BPT_IN_FOR_ONE_TOKEN_OUT` / single-sided) where the broader, correct mode (`EXACT_BPT_IN_FOR_TOKENS_OUT` / proportional) was required, silently weakening a safety guarantee. The same class of bug exists in this repo between the v1 and v2 chainstate implementations of the tenure-change duplicate-block guard: `SortitionsView::validate_tenure_change_payload` (v1) checks a narrower predicate (`get_last_globally_accepted_block`) where `GlobalStateView::validate_tenure_change_payload` (v2) explicitly documents and uses the broader, correct predicate (`get_last_signed_block`).

### Finding Description
Both v1 and v2 `check_proposal` paths must reject a tenure-change block proposal that conflicts with a tenure-change block this signer has already signed for the same tenure (`RejectReason::DuplicateBlockFound`). This is the *only* duplicate-tenure-change check performed inside `check_proposal`, since for tenure-change blocks the generic `confirms_latest_block_in_same_tenure` check is skipped in favor of `validate_tenure_change_payload`.

In v2: [1](#0-0) 
the code explicitly documents the intended semantics: "Only blocks we have signed (locally or globally accepted) count here… a block we have merely pre-committed to carries no signature from us, so it is safe to accept a competing tenure-start block in its place." It implements this via `signer_db.get_last_signed_block(...)`, which the docs confirm covers both `LocallyAccepted` and `GloballyAccepted` states.

In v1, the equivalent check uses a strictly narrower predicate: [2](#0-1) 
`signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` — this only returns a block once the node has independently confirmed it on-chain (`GloballyAccepted`), not merely once this signer has already produced a valid signature that counted toward the 70% threshold (`LocallyAccepted`, set in `store_and_process_block_signature` via `block_info.mark_locally_accepted(true)`): [3](#0-2) 

There is a real window between `mark_locally_accepted` (this signer has already signed block A for tenure T) and `mark_globally_accepted` (the node has observed A on-chain via `NewBlock`/push), as the docs make explicit: "reaching 70% signatures still only marks the block _locally_ accepted with the group timestamp; global acceptance waits for the node to adopt it." [4](#0-3) 

During that window, if a conflicting tenure-change block B for the same tenure T is proposed (e.g., a miner races two competing tenure-start blocks, or replays/re-proposes an alternate tenure-change block before A is confirmed on-chain), the v1 path's `get_last_globally_accepted_block` returns `None` for tenure T, so the `DuplicateBlockFound` guard inside `validate_tenure_change_payload` does not fire, and `check_proposal` treats B as passing this check — even though this exact signer already signed a conflicting block A for the same tenure moments earlier. This is functionally identical to the report's bug class: using the wrong (narrower) mode/predicate for an operation that must use the broader one to preserve correctness, silently degrading a safety check into a no-op in the relevant race window.

### Impact Explanation
This directly targets the "conflicting block" safety property: a signer must never sign two different tenure-change blocks for the same tenure. The v1 `check_proposal` early-rejection gate for this specific case is weaker than the intended (v2-documented) semantics, so a proposal that should be rejected outright at arrival can instead proceed to node validation and the normal signing pipeline, relying solely on the later, more complex and time/freshness-sensitive pre-commit conflict logic (`get_signed_conflicts` / `conflict_still_blocks`) as the only remaining backstop. Because that backstop is height-scoped, freshness-gated, and has documented "blind spots" (e.g., it only looks at one tenure per check, and staleness cutoffs can let a signature through once a conflict is judged stale), removing the tenure-scoped early rejection in v1 increases the chance that a signer ends up signing two conflicting tenure-change blocks for the same tenure — an equivocation.

### Likelihood Explanation
Reachable by a single miner (plus normal gossip) without needing collusion among a majority of signers: the miner only needs to broadcast two different tenure-change proposals for the same tenure, timed so the second arrives in the local-accept-but-not-yet-globally-accepted window of the first. Likelihood is tempered by (a) needing a v1 (pre-global-state-activation) signer, (b) the timing window being narrow (roughly the time it takes the node to observe the newly signed block), and (c) the existence of the later pre-commit-level conflict guard which may catch some, but not documented to catch all, cases (its own doc notes explicit blind spots). I was not able to fully trace `get_signed_conflicts`/`conflict_still_blocks` internals in this session to determine whether it always closes this specific gap, so residual likelihood is uncertain but plausible.

### Recommendation
Change `SortitionsView::validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` (matching v2's semantics and comment) instead of `get_last_globally_accepted_block`, so the duplicate-tenure-change check fires as soon as this signer has locally signed any block in the tenure, not only once the node has confirmed global acceptance.

### Proof of Concept
1. Signer S runs the v1 (pre-global-state) protocol.
2. Miner proposes tenure-change block A for tenure T. S and enough peers sign it; S's own contribution crosses the 70% threshold, so S calls `mark_locally_accepted(true)` (`stacks-signer/src/v0/signer.rs:2528`) — A is now `LocallyAccepted` but not yet `GloballyAccepted` (node hasn't processed/pushed it yet).
3. Before the node confirms A, the miner (or a relayed duplicate) proposes a different tenure-change block B for the same tenure T (different transaction set/timestamp).
4. S's `check_proposal` → `validate_tenure_change_payload` calls `signer_db.get_last_globally_accepted_block(&T)` (`stacks-signer/src/chainstate/v1.rs:505-509`), which returns `None` since A is only locally accepted — the `DuplicateBlockFound` rejection is skipped.
5. B passes `check_proposal` and proceeds into the normal validation/signing pipeline, relying entirely on the separate pre-commit-time conflict check to prevent S from also signing B — a check with documented blind spots and staleness-based exceptions, rather than the deterministic tenure-scoped rejection that v2's implementation provides.
