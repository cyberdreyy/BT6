Unlike `staking-pool-factory` and `lockup-factory`, which both use `.then(ext_self::on_..._create(...))` callbacks with `assert_self()` and `is_promise_success()` to detect failed deployment and refund the deposit to `predecessor_account_id`, `multisig-factory/src/lib.rs::create` builds a `Promise` chain (`create_account().deploy_contract().transfer().function_call()`) with no `.then()` callback at all.

### Title
No refund path on failed multisig deployment - deposit silently retained - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` schedules `create_account`/`deploy_contract`/`transfer`/`function_call` as a single promise batch but never attaches a `.then()` callback to check the result, unlike its siblings `staking-pool-factory` and `lockup-factory`, which both use `on_staking_pool_create`/`on_lockup_create` to detect failure via `is_promise_success()` and refund `attached_deposit` to `predecessor_account_id`. Because the attacker chooses `name`, an account-ID collision (or any other deployment-time failure) causes the created-account promise batch to fail while the attached NEAR deposit — already transferred within the same batch to the target account before failure occurs at any later action, or simply lost since no compensating transfer is scheduled back to the caller — is never returned to the caller.

### Finding Description
The broken binding: `predecessor_balance_after_failed_create == predecessor_balance_before_attached_deposit` should hold whenever the multisig `name` account fails to be created (e.g., because it already exists, or the `new` call panics due to attacker-supplied `members`/`num_confirmations`). Tracing `multisig-factory/src/lib.rs::create` (lines 29-49): the function attaches the deposit inline in the same promise batch as `create_account`, `deploy_contract`, and `function_call(new, ...)`, with no `.then(ext_self::...)` callback to inspect the outcome. Compare with `staking-pool-factory/src/lib.rs::create_staking_pool` (lines 172-195) and `lockup-factory/src/lib.rs::create` (lines 136-166), both of which append `.then(ext_self::on_..._create(...))`, and whose callbacks (`on_staking_pool_create` lines 200-239, `on_lockup_create` lines 171-198) call `assert_self()` and `is_promise_success()` to detect failure and issue `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` to refund the caller. `MultisigFactory::create` has no such callback, so if the batch fails (e.g., account name collision, out-of-gas in the deployed contract's `new`, or the attacker deploying a name that later conflicts), the attached deposit is not refunded to the predecessor. No `assert_self()`, `is_promise_success()`, or refund logic exists anywhere in `multisig-factory/src/lib.rs` to prevent this.

### Impact Explanation
If deployment of the attacker's own `name` fails after the deposit has already left the caller's account context (attached to the promise batch), the deposit is not returned; it either remains with the factory account or is lost depending on how the runtime settles a failed batch, but critically no logic exists to return it to the caller as the sibling factories do. This matches the "accounting value diverging from reality" pattern: the caller's NEAR balance is debited but no corresponding multisig contract/functionality is delivered and no refund occurs. This is repeatable by any unprivileged account for each `create` call using a colliding or otherwise-guaranteed-to-fail `name`/config.

### Likelihood Explanation
Any unprivileged account can call `create` with attached deposit and a `name` engineered to collide with an existing sub-account, or with `members`/`num_confirmations` that cause the deployed contract's `new` to panic. This requires no special privileges — just a standard NEAR transaction with a deposit, matching the attacker profile in scope. It is directly reproducible with a `near-sdk-sim`/`near-workspaces` test that forces the created-account promise to fail and observes that the caller's balance is not restored.

### Recommendation
Add a callback analogous to `on_staking_pool_create`/`on_lockup_create`: chain `.then(ext_self::on_multisig_create(name, env::attached_deposit().into(), env::predecessor_account_id(), ...))` after the `function_call`, and in that callback call `assert_self()`, check `is_promise_success()`, and if the deployment failed, `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` to refund the caller.
