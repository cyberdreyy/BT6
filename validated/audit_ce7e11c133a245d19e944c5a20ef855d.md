### Title
Service containers in Concrete/steps mode share build-role volume mounts (scripts, repo, cache) with the build container - blurs build/service trust boundary - (File: executors/kubernetes/steps_pod.go)

### Summary
`setupStepsPod`'s Concrete-mode pod assembly gives user-declared **service** containers the exact same volume mounts as the **build** container, via the shared `stepsVolumeMounts()` helper with no service/build differentiation. This includes the `scripts` emptyDir (which holds the writable `gitlab-runner-helper` binary later exec'd inside the build container) and, when required, the build workspace (`repo`) and `cache` emptyDirs — resources the legacy non-Concrete path intentionally withholds from services.

### Finding Description
`stepsBuildContainer` and `stepsServiceContainer` both call the identical `s.stepsVolumeMounts()` with no `isServiceContainer` distinction: [1](#0-0) [2](#0-1) 

`stepsVolumeMounts` unconditionally mounts `scripts`, any user-configured config volumes, `repo` (build workspace) when a default builds-dir is required, and `cache` when a default cache dir is required — for every container, build or service: [3](#0-2) 

Comments in the file acknowledge that Concrete mode deliberately diverges from the legacy `buildContainer`/`getVolumeMounts(isServiceContainer bool)` path specifically to avoid handing services the logs volume, showing that role-aware volume scoping is a recognized requirement elsewhere in the codebase, but the same scoping was not carried over for the `repo`/`cache`/`scripts` volumes in the steps path: [4](#0-3) [5](#0-4) 

Consequences:
- A service image (attacker-controlled via the `services:` keyword, which is frequently a third-party/public image the pipeline author does not fully control, e.g. a mutable tag) gets read/write access to the build workspace (`repo`) that legacy behavior keeps isolated. Any secrets or credential material that lands on disk during checkout/build (e.g. `.git-credentials`, `.netrc`, downloaded artifacts, dependency manager auth files) becomes readable by that service container.
- The `scripts` emptyDir is writable by the service container and also holds the `gitlab-runner-helper` binary at `stepsRunnerBinaryPath()`, the exact path later invoked via `kubectl exec` inside the build container for `steps proxy`/`steps serve`: [6](#0-5) 
Because the mount is not `ReadOnly`, a compromised or malicious service container can overwrite this binary before the build container's subsequent `pods/exec` invocation of `<path> steps proxy`, causing the build container (a higher-trust role, running the job author's own image and driving job execution/secret injection) to execute service-controlled code. That is a service→build privilege/role escalation, not merely information disclosure.

None of the existing checks stop this: `verifyAllowedImages` only validates image name/pull policy allow-listing, not filesystem isolation; there is no `ReadOnly` flag differentiation, no per-role volume mount function for services, and no test asserting that service containers are denied `repo`/`cache`/writable-`scripts` access. The one existing steps-pod test only checks container identity/ordering, not mount scoping: [7](#0-6) 

### Impact Explanation
A malicious or compromised service image (image name attacker/job-author controlled) gains: (1) read access to build-workspace files that may contain checkout credentials, cache contents, or artifacts with secrets, and (2) write access to the shared `scripts` emptyDir containing the helper binary that is later exec'd by the higher-trust build role, enabling code substitution that executes in the build container's security context. This matches the "secret exposure or stronger-context execution" impact class.

### Likelihood Explanation
Precondition is just an ordinary pipeline definition using Concrete/steps mode with at least one `services:` entry and a default builds-dir/cache-dir volume (the common case when no custom volumes are configured). No cluster-admin or GitLab-admin compromise is required — only normal `.gitlab-ci.yml` authoring capability, which matches the "unprivileged pipeline author" threat model. It is deterministically reproducible for any job matching these conditions.

### Recommendation
Introduce a role-aware volume-mount function (mirroring the legacy `isServiceContainer` pattern) so that:
- Service containers never receive the `repo` (build workspace) or `cache` emptyDir mounts unless explicitly requested via user-configured volumes.
- The `scripts` volume mount is `ReadOnly: true` for service containers (and ideally for the build container after bootstrap completes), so only the init container can write the helper binary.
- Add a unit test asserting `stepsServiceContainer`'s `VolumeMounts` excludes `repo`/`cache` and marks `scripts` read-only, complementing the existing `TestStepsPreparePodConfig_HasBuildAndServicesButNoHelper` test.

### Proof of Concept
Go unit test in `executors/kubernetes/steps_pod_test.go`:
```go
func TestStepsServiceContainer_DoesNotShareBuildWorkspaceOrWritableScripts(t *testing.T) {
    ex := newStepsTestExecutor(t)
    // configure so isDefaultBuildsDirVolumeRequired() and isDefaultCacheDirVolumeRequired() are true
    svc := spec.Image{Name: "attacker/malicious-service:latest"}
    c, err := ex.stepsServiceContainer("svc", svc, nil)
    require.NoError(t, err)

    for _, m := range c.VolumeMounts {
        assert.NotEqual(t, "repo", m.Name, "service container must not mount the build workspace")
        assert.NotEqual(t, "cache", m.Name, "service container must not mount the cache dir")
        if m.Name == "scripts" {
            assert.True(t, m.ReadOnly, "service container's scripts mount must be read-only")
        }
    }
}
```
Expected current result: test fails, showing `repo`/`cache` mounted and `scripts` mounted read-write on the service container, confirming the role-confusion vulnerability.

```go
// stepsVolumeMounts returns the volume mounts shared by the bootstrap
// init container and the build container in Concrete mode.
func (s *executor) stepsVolumeMounts() []api.VolumeMount {
	mounts := []api.VolumeMount{
		{
			Name:      "scripts",
			MountPath: s.scriptsDir(),
		},
	}

	mounts = append(mounts, s.getVolumeMountsForConfig()...)

	if s.isDefaultBuildsDirVolumeRequired() {
		mounts = append(mounts, api.VolumeMount{
			Name:      "repo",
			MountPath: s.AbstractExecutor.RootDir(),
		})
	}

	if s.isDefaultCacheDirVolumeRequired() {
		mounts = append(mounts, api.VolumeMount{
			Name:      "cache",
			MountPath: s.AbstractExecutor.CacheDir(),
		})
	}

	return mounts
}
```
