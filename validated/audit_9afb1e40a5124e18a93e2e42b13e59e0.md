### Title
Concurrent `taskTerminate` calls race on shared per-process console state, causing cross-job termination signal misdelivery - ([File: helpers/process/killer_windows.go])

### Summary
`taskTerminate` in `helpers/process/killer_windows.go` mutates process-wide (not per-job) Windows console state via `FreeConsole`/`AttachConsole`/`SetConsoleCtrlHandler` without any mutex or serialization. Two jobs cancelled concurrently on the same Windows runner process (with `UseWindowsLegacyProcessStrategy` enabled) can interleave these calls, causing job A's `CTRL_C_EVENT` to be delivered to job B's attached console (or vice versa), or the Ctrl-C handler disable/restore to apply to the wrong window.

### Finding Description
`taskTerminate(pid, UseWindowsLegacyProcessStrategy)` at [1](#0-0)  performs, when the legacy strategy is enabled: `FreeConsole()` (detach runner process from its current console), `AttachConsole(pid)` (attach to the target job's console), then `SetConsoleCtrlHandler(nil, TRUE)` (disable the runner's own Ctrl-C handler) — all of which are per-process, global kernel32 state, not per-goroutine or per-job. It then generates `CTRL_C_EVENT` and restores state via `FreeConsole`/`AttachConsole(ATTACH_PARENT_PROCESS)`/`SetConsoleCtrlHandler(nil, FALSE)` at [2](#0-1) .

`windowsKiller.Terminate()` at [3](#0-2)  is invoked from `osKillWait.KillAndWait` at [4](#0-3) , which runs per-build in its own goroutine as part of build cancellation/timeout handling. There is no mutex guarding `taskTerminate`, no serialization in `newKiller`, `killer.go`, `commander.go`, or `job_windows.go` — confirmed by inspection of all these files. If GoRoutine1 calls `taskTerminate(pidA, true)` and GoRoutine2 calls `taskTerminate(pidB, true)` concurrently, the sequence of syscalls (`FreeConsole`→`AttachConsole`→`SetConsoleCtrlHandler`→`GenerateConsoleCtrlEvent`→restore) for the two calls can interleave arbitrarily since they operate on the same process-global console attachment state. For example: GoRoutine1 calls `FreeConsole()` then `AttachConsole(pidA)`; before GoRoutine1 calls `GenerateConsoleCtrlEvent`, GoRoutine2 calls `FreeConsole()` (detaching from pidA's console) then `AttachConsole(pidB)`. GoRoutine1 then calls `GenerateConsoleCtrlEvent(CTRL_C_EVENT, pidA)` while attached to pidB's console — delivering the signal to job B's console group instead of, or in addition to, job A's, or failing to reach A at all. `SetConsoleCtrlHandler` state can similarly be restored/disabled out of order, leaving the runner's own Ctrl-C handling in an inconsistent state or applying to the wrong job's cancellation attempt.

This is only reachable when `UseWindowsLegacyProcessStrategy` is true (an opt-in Windows shell executor setting), and requires two builds' cancel/timeout paths to race on the same runner process — feasible any time a runner is configured to run multiple concurrent jobs (`concurrent` setting > 1) on Windows with the legacy strategy.

### Impact Explanation
A job cancellation/timeout for job A can silently fail to stop job A's process (no CTRL_C delivered, falling through to `ForceKill`/`taskkill` eventually — which mitigates but does not close the race window during which the wrong console received the signal), while job B — an unrelated job/pipeline potentially belonging to a different project — unexpectedly receives a `CTRL_C_EVENT`/Ctrl-C interrupt it did not request, terminating or corrupting job B's build unexpectedly. This is a concrete cross-job disruption: one tenant's job cancellation action can disrupt another tenant's unrelated running job on a shared multi-job Windows runner.

### Likelihood Explanation
Requires: (1) a Windows runner configured with `concurrent > 1` running the shell/legacy process executor, (2) `UseWindowsLegacyProcessStrategy` enabled, and (3) two jobs terminating (via timeout, cancellation, or deployment shutdown) within the same narrow multi-syscall window. This is a plausible real-world scenario on any shared Windows runner host running multiple concurrent jobs, and doesn't require attacker privilege beyond normal job cancellation (which any project member with cancel permission, or a job hitting its own timeout, can trigger) — it's a timing race dependent on scheduler behavior rather than an artificial or purely theoretical scenario.

### Recommendation
Serialize all invocations of `taskTerminate` with a process-wide mutex so that the console attach/detach/handler-toggle/signal/restore sequence for one PID completes atomically before another can begin. Alternatively, avoid mutating global console state altogether by using per-job job objects/process groups combined with `GenerateConsoleCtrlEvent` targeting the correct process group ID directly (which is already the approach used in the non-legacy path via `CREATE_NEW_PROCESS_GROUP`), and deprecate/guard the legacy strategy more strongly against concurrent invocation.

```go
// helpers/process/killer_windows_race_test.go
func TestTaskTerminate_ConcurrentRace(t *testing.T) {
    cmdA := startSleepProcess(t, "10")
    cmdB := startSleepProcess(t, "10")
    defer cmdA.Process.Kill()
    defer cmdB.Process.Kill()

    var wg sync.WaitGroup
    wg.Add(2)
    go func() {
        defer wg.Done()
        _ = taskTerminate(cmdA.Process.Pid, true)
    }()
    go func() {
        defer wg.Done()
        _ = taskTerminate(cmdB.Process.Pid, true)
    }()
    wg.Wait()

    // Assert: process A terminated in response to its own signal, not B's,
    // and vice versa. Run many iterations (e.g. 1000x) under `go test -race`
    // and with artificial delays injected between syscalls to widen the
    // race window; assert exactly one of {A exited via CTRL_C, B exited via CTRL_C}
    // per invocation, correlated to the correct PID.
    aExited := waitForExit(cmdA, 2*time.Second)
    bExited := waitForExit(cmdB, 2*time.Second)
    assert.True(t, aExited, "process A should have received its own termination signal")
    assert.True(t, bExited, "process B should have received its own termination signal")
}
```
Run with `-race` and repeated iterations/injected delays between the `AttachConsole`/`GenerateConsoleCtrlEvent` calls to reliably reproduce cross-signal delivery.

```go
func taskTerminate(pid int, UseWindowsLegacyProcessStrategy bool) error {
	kernel32 := windows.NewLazySystemDLL("kernel32.dll")
	if err := kernel32.Load(); err != nil {
		return fmt.Errorf("failed to load kernel32: %w", err)
	}

	kernel32Function := func(methodName string) func(string, ...uintptr) error {
		return func(description string, args ...uintptr) error {
			if res1, _, callErr := kernel32.NewProc(methodName).Call(args...); res1 == 0 {
				return fmt.Errorf("failed to %s: %w", description, callErr)
			}
			return nil
		}
	}

	freeConsole := kernel32Function("FreeConsole")
	attachConsole := kernel32Function("AttachConsole")
	setConsoleCtrlHandler := kernel32Function("SetConsoleCtrlHandler")
	generateConsoleCtrlEvent := kernel32Function("GenerateConsoleCtrlEvent")

	if UseWindowsLegacyProcessStrategy {
		if err := freeConsole("detach the runner process from its console"); err != nil {
			return err
		}
		if err := attachConsole("attach to the console of the process being terminated", uintptr(pid)); err != nil {
			return err
		}
		if err := setConsoleCtrlHandler("disable Ctrl-C event handler for runner process", uintptr(unsafe.Pointer(nil)), uintptr(1)); err != nil {
			return err
		}
	}
```
