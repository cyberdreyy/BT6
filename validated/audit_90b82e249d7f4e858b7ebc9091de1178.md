## Analog Found

### Title
Missing reentrancy protection around external CPI/token-transfer callbacks in Kamino/Drift/JupLend integration deposit flows allows Token-2022 transfer-hook reentrancy - (File: `programs/marginfi/src/instructions/kamino/deposit.rs`, `programs/marginfi/src/instructions/drift/deposit.rs`, `programs/marginfi/src/instructions/juplend/deposit.rs`)

### Summary
The Code4rena finding flags `CollateralizedDebt.sol::mint()` for invoking `_safeMint()`, which hands control to an attacker-influenced `to` address callback before/without a reentrancy guard. The closest reachable analog in marginfi-v2 is the Kamino/Drift/JupLend "wrapped-integration" deposit instructions, which release their `AccountLoader` borrows on `bank` and `marginfi_account` *before* performing token transfers and third-party CPIs, and only re-acquire them afterward to record the accounting update. Because Token-2022 mints with an active `transfer_hook` extension execute attacker-registered program code during `transfer_checked`, and this check is enforced in only one narrow instruction (`lending_pool_emissions_deposit`), the integration deposit paths are exposed to hook-driven reentrancy while the relevant accounts are unlocked.

### Finding Description
In `kamino_deposit` (and structurally identically in `drift_deposit` / `juplend_deposit`), the flow is:

1. `bank`/`marginfi_account` are loaded (immutably) inside a short-lived block and the borrow (`Ref`) is dropped at the end of that block: [1](#0-0) 
2. Pre-CPI snapshots are taken (`initial_obligation_deposited_amount`, `expected_collateral_amount`): [2](#0-1) 
3. With `bank`/`marginfi_account` **unborrowed**, the underlying-asset token transfer (`transfer_checked`) and the Kamino CPI are executed: [3](#0-2) [4](#0-3) 
4. Only afterward are `bank.load_mut()`/`marginfi_account.load_mut()` reacquired to credit shares based on the pre-CPI snapshot delta: [5](#0-4) 

`transfer_checked` on a Token-2022 mint automatically performs a CPI into the mint's registered `transfer_hook` program when the `TransferHook` extension is active — this is enforced by SPL Token-2022 itself, not opted out of by marginfi. marginfi's codebase confirms first-class support for such hooked mints (dedicated `test_transfer_hook` program, `SupportedExtension::TransferHook`, and helper code that assembles the hook's `extra_account_metas` for deposit/liquidation flows): [6](#0-5) [7](#0-6) 

Crucially, the *only* place in the codebase that explicitly rejects mints with an active transfer hook is `lending_pool_emissions_deposit`: [8](#0-7) 

No equivalent `has_transfer_hook` check exists in `kamino_deposit`, `drift_deposit`, `juplend_deposit`, `solend` flows, or the standard `lending_account_deposit`. In the standard `lending_account_deposit`, the risk is mitigated because `bank_loader.load_mut()` and `marginfi_account_loader.load_mut()` are held continuously across the transfer CPI (Anchor's underlying `RefCell`/account-data-borrow check would reject any reentrant CPI attempting to touch the same `bank`/`marginfi_account`): [9](#0-8) 

The Kamino/Drift/JupLend integration deposits do **not** preserve that invariant — the borrows are dropped precisely during the window where the hook-triggering transfer and third-party CPI occur, mirroring the `_safeMint()` callback pattern from the referenced report: state-changing external control-flow with no guard, sandwiched between a "before" read and an "after" reconciliation.

### Impact Explanation
If a bank is (or can be) configured with a Token-2022 underlying mint carrying an active transfer hook, any depositor into that bank triggers execution of the hook program during `cpi_transfer_user_to_obligation_owner`/`cpi_transfer_user_to_liquidity_vault`, at a point where `bank` and `marginfi_account` for that deposit are not held under Anchor's account-data borrow lock. A hook program could reenter marginfi (e.g., call `lending_account_withdraw`, `lending_account_close_balance`, or another integration instruction) against the *same* bank/account to mutate `total_asset_shares`/`asset_share_value` or the position's balance before the outer `kamino_deposit`/`drift_deposit`/`juplend_deposit` call finishes crediting shares from its stale pre-CPI snapshot (`initial_obligation_deposited_amount`, `pre_f_token_balance`, `initial_scaled_balance`). This can lead to double-credited/duplicated shares, share-value manipulation, or accounting divergence between the bank's internal ledger and the actual underlying/Kamino-obligation balances — a durable, financially impactful state inconsistency.

### Likelihood Explanation
Exploitation requires a bank whose underlying mint is Token-2022 with an attacker-controlled/attacker-updatable `transfer_hook`. Whether such a mint can be paired with a Kamino/Drift/JupLend-tagged bank is gated by the (privileged) `lending_pool_add_bank_*` admin action, and confirming that this specific bank-creation path unconditionally accepts arbitrary T22 mints (vs. restricting to a hardcoded/verified pool mint) could not be fully verified within the available tool budget — `add_pool.rs`/`init_position.rs` account constraints were located but not read in full to confirm the mint-type check. Given that the codebase treats T22 transfer-hook mints as a first-class supported feature elsewhere (and only special-cases the emissions path), and that a mint's transfer-hook program can be changed by the mint authority independent of bank governance, the likelihood is non-trivial but conditioned on this unresolved bank-creation constraint.

### Recommendation
- Hold `bank.load_mut()` and `marginfi_account.load_mut()` for the duration of `kamino_deposit`/`kamino_withdraw`/`drift_deposit`/`juplend_deposit` (and their withdraw counterparts), matching the pattern already used in `lending_account_deposit`, so Anchor's account-data borrow check blocks reentrant CPIs on the same accounts during the transfer/CPI window.
- Alternatively/additionally, apply the same `has_transfer_hook`/`nonzero_fee` rejection used in `lending_pool_emissions_deposit` to all integration deposit/withdraw paths, or reject transfer-hook mints entirely for Kamino/Drift/Solend/JupLend-tagged banks at `lending_pool_add_bank_*` time.
- Add an explicit reentrancy guard (e.g., a transient "busy" flag on the bank/account, or Anchor account-borrow retention) for any instruction that performs a token transfer capable of routing to attacker-influenced code before finalizing internal share accounting.

### Proof of Concept
1. Admin adds a Kamino-wrapped bank whose underlying `mint` is Token-2022 with a `TransferHook` extension pointing at an attacker-controlled hook program (or the mint authority later swaps in a malicious hook post bank-creation).
2. User calls `kamino_deposit`. Execution reaches `ctx.accounts.cpi_transfer_user_to_obligation_owner(amount)` at `programs/marginfi/src/instructions/kamino/deposit.rs:76`, which performs `transfer_checked` on the T22 mint, invoking the hook program.
3. At this point `bank` and `marginfi_account` are unborrowed (their `Ref`s from lines 55-56 were already dropped at line 61). The hook program CPI's back into marginfi, e.g., calling `lending_account_close_balance` or another deposit/withdraw on the same `bank`/`marginfi_account`, mutating `total_asset_shares`/the position balance.
4. Control returns to `kamino_deposit`, which proceeds to `cpi_kamino_deposit`, then reloads `bank`/`marginfi_account` at line 92 and credits `share_amount` based on the pre-reentrancy snapshot `initial_obligation_deposited_amount` captured at line 65 — now inconsistent with the mutated state, producing an accounting error (e.g., extra/duplicated shares or a mismatched liquidity-vault-to-shares ratio).

```rust
/// Returns `true` if the given mint has an active transfer hook program.
/// If the hook is present but no program is active it would return false.
pub fn has_transfer_hook(mint_ai: AccountInfo) -> MarginfiResult<bool> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(false);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    if let Ok(hook) = mint.get_extension::<TransferHook>() {
        let program_id: Option<Pubkey> = Option::from(hook.program_id);
        return Ok(program_id.is_some());
    }

    Ok(false)
}
```
