## Analysis Result

The go-ipfs CVE-2020-26283 bug class (untrusted data containing raw control/ANSI escape characters written unescaped to console output, allowing spoofing/hiding of terminal content) has a valid analog in the agave codebase's handling of on-chain program log messages that are ultimately displayed by the CLI.

### Title
Untrusted program log messages are written unescaped to console output, enabling terminal control-character/ANSI injection - (File: `cli-output/src/display.rs`)

### Summary
A malicious or compromised on-chain program can emit arbitrary bytes (any valid UTF-8, including ANSI escape sequences and other control characters) via the `sol_log` syscall. These bytes are stored verbatim in the transaction's log messages and later printed unescaped to a user's terminal by the Agave CLI when displaying transaction results (e.g. `solana confirm`, `solana transaction-history`, simulate output). This mirrors the go-ipfs advisory's root cause: failure to escape/neutralize control characters before writing untrusted content to console output.

### Finding Description
The `SyscallLog` builtin syscall handler reads a user/program-supplied byte buffer from VM memory and forwards it to `stable_log::program_log` after only validating that the bytes are valid UTF-8: [1](#0-0)  The only sanitization performed anywhere on this path is a UTF-8 validity check (`SyscallError::InvalidString(Utf8Error, Vec<u8>)`), not a check for printable/control characters: [2](#0-1) 

`stable_log::program_log` stores the raw message string with only a `"Program log: "` prefix and forwards it into the `LogCollector`: [3](#0-2)  `LogCollector::log` stores the message as-is (subject only to a byte-length truncation limit), with no character filtering: [4](#0-3) 

These log messages ultimately become the transaction's `log_messages` field, and are printed to the user's terminal without any escaping by the Agave CLI's transaction display logic: [5](#0-4)  which is invoked from `println_transaction`, writing the composed string directly to stdout bytes: [6](#0-5)  A similar unescaped path exists in the `ledger-tool program run` debugging output, which formats collected log content directly with `writeln!`: [7](#0-6) 

Because valid UTF-8 permits arbitrary C0 control characters (e.g. `\x1b` ESC, used to start ANSI escape sequences, or `\r`, `\x07` BEL, etc.), a program author fully controls what gets written to a victim's terminal when they inspect a transaction with the CLI.

### Impact Explanation
An attacker-deployed program can craft `Program log:` messages containing ANSI escape sequences to:
- Overwrite, clear, or visually spoof previously displayed lines (e.g., hide a "Instruction Error" or fee/warning line, or fake a "Success" message) when a user runs `solana confirm <signature>`, inspects transaction history, or simulates a transaction via the CLI.
- Manipulate terminal title, cursor position, or use OSC sequences supported by some terminal emulators, which in the worst case (depending on terminal emulator support) could trick a user's terminal or clipboard, increasing the risk of social-engineering-driven fund loss (e.g., convincing a user a malicious transaction is benign).

This is a genuine, unprivileged, ordinary-user-reachable console spoofing issue — any user who runs a transaction against a malicious program and later displays it via CLI tooling is affected. It does not by itself cause fund loss or consensus divergence but does enable output spoofing that could facilitate further attacks (aligned with the "Medium" severity of the original advisory).

### Likelihood Explanation
Likelihood is high for exposure but limited in severity: any transaction invoking a program that calls `sol_log`/`msg!` with attacker-chosen bytes will have its logs surfaced through RPC `log_messages` and rendered unescaped by any client (including the reference CLI) that prints them directly, as agave's own CLI does. No special privileges, malicious snapshots, or node-level access are required — only a deployed program and a user who views the transaction output.

### Recommendation
Escape or filter non-printable/control characters (excluding `\n`/normal whitespace where intended) from program log messages before they are written to any terminal/console sink, e.g. in `write_log_messages`/`println_transaction`/`writeln_transaction` in `cli-output/src/display.rs`, and in the `ledger-tool` `program run` `Output::fmt` implementation. This should mirror the go-ipfs fix by escaping control characters (e.g., rendering them as `\xNN` or stripping ESC-initiated sequences) at the point untrusted log content is rendered to a human-facing console, rather than relying on UTF-8 validity as the only filter.

### Proof of Concept
1. Deploy a program that calls `sol_log_(msg, len)` with `msg` containing bytes such as `\x1b[2K\x1b[1G` (clear line / move cursor) followed by a fabricated status string, e.g. spoofing "Transaction succeeded" text over the real error output.
2. Submit a transaction invoking this program.
3. Run `solana confirm <signature>` or any CLI path that calls `println_transaction`/`write_log_messages` — the escape sequences execute in the user's terminal, altering the perceived output [8](#0-7) .

**Uncertainty**: I could not fully trace every downstream RPC/consumer path (e.g. `solana-explorer`-style tooling, other third-party clients) that renders `log_messages`, only the in-repo CLI display code and `ledger-tool` debug output, which are the concrete in-scope sinks confirmed here.

    pub fn log(&mut self, message: &str) {

            self.messages.push(message.to_string());
            return;
        };

        let bytes_written = self.bytes_written.saturating_add(message.len());

fn write_log_messages<W: io::Write>(
    w: &mut W,
    log_messages: Option<&Vec<String>>,
    prefix: &str,
) -> io::Result<()> {
    if let Some(log_messages) = log_messages
        && !log_messages.is_empty()
    {
        writeln!(w, "{prefix}Log Messages:",)?;
        for log_message in log_messages {
            writeln!(w, "{prefix}  {log_message}")?;
        }
    }
    Ok(())
}

pub fn println_transaction(
    transaction: &VersionedTransaction,
    transaction_status: Option<&UiTransactionStatusMeta>,
    prefix: &str,
    sigverify_status: Option<&[CliSignatureVerificationStatus]>,
    block_time: Option<UnixTimestamp>,
) -> io::Result<()> {
    let mut w = Vec::new();
    if write_transaction(
        &mut w,
        transaction,
        transaction_status,
        prefix,
        sigverify_status,
        block_time,
        CliTimezone::Local,
    )
    .is_ok()
        && let Ok(s) = String::from_utf8(w)
    {
        write_stdout_str(&s)?;
    }
    Ok(())
}
