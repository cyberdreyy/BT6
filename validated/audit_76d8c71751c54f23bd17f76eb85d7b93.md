### Title
`getLargestAccounts` cache key omits commitment level, returning stale/wrong-commitment data to unprivileged RPC callers - ([File: rpc/src/rpc_cache.rs])

### Summary
The external report's bug class is: a time-based "cooldown"/cache mechanism causes a mandatory state-refresh step to be skipped, so a caller ends up being served stale accounting state instead of the correct up-to-date state. The `LargestAccountsCache` used by the `getLargestAccounts` JSON-RPC handler exhibits the analogous defect: it caches results only by `RpcLargestAccountsFilter` for a fixed TTL window, but never accounts for the `commitment` level the caller requested, so a cache entry populated under one commitment (e.g. `processed`/`confirmed`) is blindly served back to a subsequent call requesting a different commitment (e.g. `finalized`) within the TTL window.

### Finding Description
`get_largest_accounts` in [1](#0-0)  first resolves a `bank` for the caller-specified `commitment` via `self.bank(config.commitment)`, but then checks the cache using only `config.filter` as the key:

```rust
if let Some((slot, accounts)) = self.get_cached_largest_accounts(&config.filter) {
    Ok(RpcResponse { context: RpcResponseContext::new(slot), value: accounts })
}
```

`get_cached_largest_accounts`/`set_cached_largest_accounts` [2](#0-1)  and the underlying `LargestAccountsCache` [3](#0-2)  key the cache map purely by `Option<RpcLargestAccountsFilter>`:

```rust
pub struct LargestAccountsCache {
    duration: u64,
    cache: HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>,
}
```

`get_largest_accounts` in `rpc_cache.rs` only checks that the cache entry's age is under the configured `duration` (a TTL/"cooldown" window), with no comparison of the commitment level used to populate the entry [4](#0-3) . Because the commitment level is never part of the equality key or the freshness check, any RPC caller with a different `commitment` but the same `filter` will, within the TTL window, receive the slot and account-balance data computed for the *previous caller's* commitment level instead of data consistent with their own requested bank.

This mirrors the root cause of the Sherlock report: a "must always be checked against the exact requested state" invariant (there, claiming rewards up to the exact withdrawal moment; here, computing largest-accounts data against the exact requested commitment/bank) is bypassed by a blanket time-based cache/cooldown check that ignores the differing input state.

### Impact Explanation
An unprivileged RPC client requesting `getLargestAccounts` with `commitment: finalized` can be served a `slot`/account-balance snapshot that was actually computed for an earlier `processed` or `confirmed` bank (or vice versa), within the `LARGEST_ACCOUNTS_CACHE_DURATION` window. This is a wrong-slot/wrong-commitment data return to a query, matching the "wrong-slot/fork/account data returned" acceptance criterion: the response's `context.slot` and balances do not correspond to the bank state the caller actually asked to observe, and callers relying on `finalized` commitment for correctness guarantees can be misled into believing not-yet-finalized data is finalized.

### Likelihood Explanation
This requires no special privileges — a single unprivileged JSON-RPC caller (or interleaved calls from different callers hitting the same public RPC node) making back-to-back `getLargestAccounts` requests with different `commitment` values but the same `filter` within the cache TTL window will trigger it deterministically. No malicious input crafting, multiple clients, or elevated rate is required beyond two ordinary RPC calls.

### Recommendation
Include the resolved bank's commitment (or the `commitment` field of `RpcLargestAccountsConfig`) as part of the `LargestAccountsCache` key, e.g. `HashMap<(Option<RpcLargestAccountsFilter>, CommitmentConfig), LargestAccountsCacheValue>`, so cached results are only reused for requests targeting the same commitment level and bank lineage.

### Proof of Concept
1. Call `getLargestAccounts` with `commitment: "processed"` (or omit commitment, defaulting to `finalized`, then use `"confirmed"`/`"processed"` for the second call) — this populates the cache under `filter = None` with the processed bank's slot/accounts.
2. Immediately (within `LARGEST_ACCOUNTS_CACHE_DURATION`, see `rpc_service.rs`) call `getLargestAccounts` with `commitment: "finalized"` and the same `filter`.
3. Observe that the second response's `context.slot` and account balances match step 1's processed/confirmed bank rather than being recomputed against the finalized bank — i.e., data inconsistent with the requested commitment is returned, confirmed by tracing `get_largest_accounts` ( [1](#0-0) ) never re-deriving from `bank` when a same-filter cache hit exists regardless of commitment.

    pub(crate) fn get_largest_accounts(
        &self,
        filter: &Option<RpcLargestAccountsFilter>,
    ) -> Option<(u64, Vec<RpcAccountBalance>)> {
        self.cache.get(filter).and_then(|value| {
            if let Ok(elapsed) = value.cached_time.elapsed()
                && elapsed < Duration::from_secs(self.duration)
            {
                return Some((value.slot, value.accounts.clone()));
            }
            None
        })
    }
