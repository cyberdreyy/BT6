### Title
Precompile signature verification consumes zero compute units and is priced by a fixed per-signature cost estimate that is decoupled from the actual (unbounded) verification work performed - ([File: precompiles/src/secp256k1.rs])

### Summary
This is a valid analog of the compute/fee metering-bypass bug class described in the report. In the ERC20 report, the fee is calculated from gas consumed *before* the payment-transfer stage, while the payment-transfer stage itself performs unmetered, attacker-controlled work (arbitrary contract execution) that is never accounted for in the fee. In Agave, `secp256k1`, `ed25519`, and `secp256r1` precompile instructions perform real CPU-expensive cryptographic verification work (`libsecp256k1::recover`, `ed25519_dalek::verify_strict`, OpenSSL ECDSA verification) entirely *outside* the SBPF interpreter and its `compute_meter`. This work is instead billed using a fixed, count-based cost estimate (`SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, `SECP256R1_VERIFY_COST`) that is used only for cost-tracker/QoS accounting, not for CPU-time-proportional charging or hard compute-budget enforcement.

### Finding Description
The precompile verify functions run the real cryptographic verification logic directly, without any interaction with the metered `InvokeContext::compute_meter`: [1](#0-0) [2](#0-1) 

This is confirmed directly by the test suite, which explicitly documents that VM execution of a precompiled instruction "consume[s] 0 from CU-meter": [3](#0-2) 

Instead of metering actual work, the cost model assigns a *fixed per-signature* cost purely from the attacker-controlled `num_signatures`/`count` byte embedded in the precompile instruction data: [4](#0-3) [5](#0-4) 

The signature count used for this pricing is read straight from `instruction.data.first()` (an attacker-supplied byte), independent of the actual per-signature message size that will be hashed/verified: [6](#0-5) 

Crucially, the *actual* CPU cost of verification scales with the `message_data_size` (a `u16`, up to 65535 bytes) referenced by each signature offset entry, and with the declared signature `count` (up to 255 for secp256k1/ed25519, 8 for secp256r1). Each signature entry performs a full hash (keccak256 for secp256k1) plus an EC-point recovery/verification over the referenced message bytes: [7](#0-6) [8](#0-7) 

Because the fixed per-signature cost constant is a flat "average" estimate (`SECP256K1_VERIFY_COST = 223 * 30` CU) and does not scale with the size of the message actually hashed/verified, an attacker can construct signature offsets that reuse or overlap the same (or maximal-size) message-bytes across many declared signature entries, forcing repeated expensive elliptic-curve recovery/verification operations for a cost that is billed identically regardless of the actual bytes processed. Because none of this work touches `compute_meter.consume_checked`, the SBPF per-instruction hard compute-unit cap (`ComputationalBudgetExceeded`) never triggers to bound it — the only limiting factor is the (loosely related) cost-model estimate used for block/account cost-tracker bookkeeping and scheduling, not a real-time metering of the work being performed.

### Impact Explanation
This decoupling between "actual expensive verification work" and "billed compute units" mirrors the reported bug's exploit primitive: the party charging for resource consumption (banking stage / cost tracker / block producers) uses a coarse, pre-computed price signal instead of metering the actual unbounded work performed during the "settlement" phase. A validator processing a block full of maximum-signature-count precompile instructions can be forced to perform disproportionately large amounts of real cryptographic CPU work (elliptic-curve point recovery/verification, hashing) relative to the compute units/fees actually reserved and billed for the transaction, since this work happens outside the enforced compute-unit ceiling. This is a compute-metering bypass that can be used for validator-side CPU exhaustion/ingest-starvation at comparatively low cost to the attacker, analogous to draining a resource pool (the Gelato deposit in the original report) by exploiting a mismatch between "measured cost" and "actual unmetered cost."

### Likelihood Explanation
Likelihood is moderate-to-high for a determined attacker: constructing precompile instructions with maximum signature counts and maximal `message_data_size` offsets requires no special privileges — any user can submit ordinary transactions containing `secp256k1_program`/`ed25519_program`/`secp256r1_program` instructions with attacker-chosen offset tables. The only natural bound is the overall transaction/packet size limit, but offsets can reference the same bytes multiple times across many signature entries, amplifying actual CPU work without a corresponding increase in the billed, count-based cost estimate.

### Recommendation
Meter precompile verification cost proportionally to the actual work performed (e.g., charge based on `message_data_size` and cryptographic operation count actually executed, not just a flat cost times a self-reported "count" byte), and/or route precompile verification through the `InvokeContext`/`compute_meter` so a hard compute-unit ceiling actually bounds this work in real time, consistent with how SIMD-0159 already intends to "move precompile verification into SVM."

### Proof of Concept
1. Construct a `secp256k1_program` instruction with `count = 255` (max `u8`) signature offset entries.
2. For each entry, set `message_data_offset`/`message_data_size` to reference a large (near-64KB) byte range within another instruction's data in the same transaction (reused/overlapping across entries is permitted; `get_data_slice` only checks bounds, not uniqueness).
3. Submit the transaction. `precompiles/src/secp256k1.rs::verify` will perform up to 255 full keccak-256 hashes plus 255 `libsecp256k1::recover` operations over large message slices, consuming zero units from `compute_meter` (confirmed by `test_builtin_ix_precompiled`), while the cost model bills a flat `count * SECP256K1_VERIFY_COST` regardless of the message sizes actually processed.

pub fn verify(
    data: &[u8],
    instruction_datas: &[&[u8]],
    _feature_set: &FeatureSet,
) -> Result<(), PrecompileError> {
    if data.is_empty() {
        return Err(PrecompileError::InvalidInstructionDataSize);
    }
    let count = data[0] as usize;
    if count == 0 && data.len() > 1 {
        // count is zero but the instruction data indicates that is probably not
        // correct, fail the instruction to catch probable invalid secp256k1
        // instruction construction.
        return Err(PrecompileError::InvalidInstructionDataSize);
    }
    let expected_data_size = count
        .saturating_mul(SIGNATURE_OFFSETS_SERIALIZED_SIZE)
        .saturating_add(1);
    if data.len() < expected_data_size {
        return Err(PrecompileError::InvalidInstructionDataSize);
    }

pub fn get_precompile_signature_details<'a>(
    instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
) -> PrecompileSignatureDetails {
    let mut builder = PrecompileSignatureDetailsBuilder::default();
    for (program_id, instruction) in instructions {
        builder.process_instruction(program_id, &instruction);
    }
    builder.build()
}

#[inline]
