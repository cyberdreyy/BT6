### Title
Vault-position rewards accrued by `ProgrammableBorrower` are unclaimable through any pool-facing interface - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
This is the direct analog of the external report: an intermediary contract that stakes user funds into an external reward-bearing system but exposes no interface to claim the extra rewards that staking earns. `ProgrammableBorrower` parks all idle credit-facility capital into an ERC4626 `vault` via `_depositToVault` (`ProgrammableBorrower.sol:378-385`). Its accounting (`_currentVaultAssets`, `_vaultNetInterest`, `totalInterestDueNow` at lines 330-347, 545-549) only ever measures `convertToAssets(shares)`, i.e. price-accreted yield. ERC4626 vaults in this ecosystem routinely distribute *additional* incentives that do not accrete to share price — e.g. MetaMorpho vaults distribute rewards through a `UniversalRewardsDistributor` merkle-claim (this codebase itself implements that claim in `MetaMorphoStrategy._claimReward`, `contracts/strategies/morpho/MetaMorphoStrategy.sol:161-171`). `ProgrammableBorrower` has no `claim`, `redeemRewards`, `getRewardTokens` or equivalent hook, so any such side rewards attributable to its share balance are never collected for the pool.

### Finding Description
1. `IdleCDOEpochVariant` calls `ProgrammableBorrower.onStartEpoch`, which deposits the pool's idle underlying into `vault` (`ProgrammableBorrower.sol:216`).
2. While shares are held, the vault's distributor emits off-price rewards (e.g. URD/Merkl claims) allocatable to `ProgrammableBorrower`'s share balance.
3. When claimed (by anyone, via `distributor.claim(address(this), …)` on the URD pattern the repo already uses), reward tokens land on `ProgrammableBorrower` — but no function routes them into `totalInterestDueNow`, `bufferedVaultDelta` or the IdleCDO, and `_currentVaultAssets()` ignores any token that isn't vault-share-denominated.
4. The only escape hatch is `rescueTokens` (`ProgrammableBorrower.sol:602-605`), an `onlyOwner` trusted emergency function — exactly mirroring the external finding's "missing claim interface" defect: reward recovery depends entirely on manual privileged intervention rather than a designed interface, and unclaimed yield never reaches AA/BB tranche holders at `stopEpoch`.

### Impact Explanation
Unclaimed yield attributable to the pool's vault sleeve is permanently excluded from epoch accounting. On every `stopEpoch`, `totalInterestDueNow()` under-reports pool profit by the full value of these side rewards, so tranche prices and withdraw-request payouts are systematically lower than they should be. If the vault shares are later migrated via `setVault` or the position fully redeemed, rewards still sit stranded on the contract.

### Likelihood Explanation
High whenever the configured ERC4626 vault offers any off-price incentive program — the repo's own `MetaMorphoStrategy` exists precisely because MetaMorpho vaults have such distributions, and `setVault` (`ProgrammableBorrower.sol:158-170`) imposes no restriction beyond matching `asset()`, so pointing the facility at a reward-emitting vault is a normal configuration. No attacker action is needed; the loss accrues passively each epoch rewards go unclaimed.

### Recommendation
Add a reward-claim interface to `ProgrammableBorrower` (e.g. a `claimVaultRewards(bytes data)` callable by owner/manager that claims via the vault's distributor and either deposits proceeds as principal-baseline-exempt profit via `_depositToVault(amount, 0)` or forwards them to `idleCDO`), and/or extend `totalInterestDueNow` to include harvested reward value. Optionally restrict `setVault` to vaults with a documented reward-claim path.
