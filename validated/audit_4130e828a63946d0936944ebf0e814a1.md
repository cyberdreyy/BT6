### Title
Stale per-epoch instant-withdraw ledger is re-read by default recovery after the receipt was already claimed — double payout and inflated recovery basis - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The kernel bug is a "two locks protecting the same list" race: `icc_set_bw` iterates `req_list` under `icc_bw_lock` while `icc_put`/`of_icc_get` mutate it under `icc_lock`. The vault analog is a two-ledger invariant: `claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` while the per-epoch ledgers `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` (the "other lock's list") are left stale. The default-recovery path then iterates those stale ledgers, paying the already-claimed receipt a second time and inflating both the claim basis and the prefunded reserve.

### Finding Description
`requestInstantWithdraw` maintains two copies of the same receipt: the aggregate `instantWithdrawsRequests[_user]` / `pendingInstantWithdraws`, and the per-epoch `instantWithdrawsRequestsByEpoch[_user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]` [1](#0-0) . The normal claim path updates only the first copy: it burns and zeroes `instantWithdrawsRequests[_user]` but never touches the per-epoch entries [2](#0-1) . The only function that clears them is `_claimDefaultedInstantWithdrawRequest` [3](#0-2) .

Two distinct corruptions follow when the borrower defaults in the same epoch while `pendingInstantWithdraws != 0`:

1. **Double payout.** After finalization, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest`, which reads the still-nonzero `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` for a user who already claimed at par, and transfers `claimBasis * defaultRecoveryPrice` again [4](#0-3) .

2. **Inflated recovery basis and phantom reserve.** `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]`, which still includes the already-claimed amount [5](#0-4) . `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant`, counting the already-paid-out underlying as "already-held" reserve, so `recoveryPrice` is set against tokens that no longer exist in the contract [6](#0-5) . Early claimants are then paid at an inflated price until `defaultRecoveryReserve`/balance is exhausted, and later claimants (normal withdraw receipts, the other tranche) are left unpayable [7](#0-6) .

### Impact Explanation
Direct theft and insolvency of the default-recovery reserve. A user whose instant receipt was already funded and claimed in the defaulted epoch is paid a second time at `defaultRecoveryPrice`. Independently, the inflated `totalBasis` + phantom `prefundedReserve` mean the sum of all recovery payouts exceeds actual held underlying, so the last claimants' recovery is permanently frozen (transfers revert / reserve underflows). Loss is quantified as `claimedInstantBasis * defaultRecoveryPrice` plus the dilution spread across all remaining recovery claimants.

### Likelihood Explanation
Requires a specific but reachable sequence by an unprivileged user (a tranche holder requesting instant withdraw): request instant withdraw in epoch N → CDO partially funds the instant bucket at `startEpoch` so `pendingInstantWithdraws` stays nonzero while some underlying sits in the strategy → attacker claims their funded receipt → borrower defaults in epoch N → `finalizeDefaultRecovery` runs. Every step is a normal protocol operation; the attacker only chooses claim timing. No privileged misbehavior needed (borrower default is a protocol event, not attacker-controlled, but the corrupted accounting exists regardless of who defaults).

### Recommendation
Keep the two ledgers consistent on every mutation, mirroring the kernel fix (always hold `icc_bw_lock` before touching `req_list`). In `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` for each outstanding epoch entry (or store a per-user "claimed" flag so `_claimDefaultedInstantWithdrawRequest` skips already-claimed receipts). Alternatively, have `_claimDefaultedInstantWithdrawRequest` compute its basis as `min(perEpochBasis, instantWithdrawsRequests[_user])` so an already-zeroed aggregate cannot resurrect an epoch claim. Add a regression test: partially funded instant bucket → user claims → default same epoch → assert the user cannot claim again and `defaultPendingClaimBasis` excludes the claimed amount.

### Proof of Concept
Foundry fork test sketch (fork mainnet, deploy `IdleCreditVault` + `IdleCDOEpochVariant`, honest owner/manager/borrower):

```solidity
function test_InstantReceiptDoubleClaimOnDefault() public {
    // epoch N running; attacker A and victim B both request instant withdraw
    vm.prank(cdo); vault.requestInstantWithdraw(10e18,  A);   // pendingInstant=10
    vm.prank(cdo); vault.requestInstantWithdraw(190e18, B);   // pendingInstant=200
    // instantWithdrawClaimsByEpoch[N] == 200

    // startEpoch: CDO partially funds instant bucket (100 of 200)
    vm.prank(cdo); vault.collectInstantWithdrawFunds(100e18); // pendingInstant=100, vault holds 100

    // A claims funded receipt at par BEFORE default
    vm.prank(cdo); vault.claimInstantWithdrawRequest(A);
    // instantWithdrawsRequests[A]==0 BUT instantWithdrawsRequestsByEpoch[A][N]==10 (stale)
    // instantWithdrawClaimsByEpoch[N] still == 200

    // borrower defaults in epoch N; recovery of 150 supplied externally
    vm.prank(cdo); vault.finalizeDefaultRecovery(150e18, recoverySource);
    // BUG 1: defaultPendingClaimBasis() counted 200 instant basis incl. A's paid 10
    // BUG 2: _defaultPrefundedInstantReserve() = 200-100 = 100 phantom "held" tokens
    //        (vault actually holds 90 after A's claim) -> recoveryPrice inflated

    // BUG 3: A claims the same receipt a second time through the default path
    uint256 balBefore = underlying.balanceOf(A);
    vm.prank(cdo); vault.claimInstantWithdrawRequest(A);
    assertGt(underlying.balanceOf(A), balBefore); // double payout at defaultRecoveryPrice

    // last defaulted-epoch claimant now reverts: reserve drained by phantom basis
    vm.expectRevert();
    vm.prank(cdo); vault.claimInstantWithdrawRequest(B);
}
```

Key invariants to assert: after `claimInstantWithdrawRequest(A)`, `instantWithdrawsRequestsByEpoch[A][N]` should be 0 (currently stays 10), and `defaultPendingClaimBasis()` should not exceed unfunded instant claims.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
