Based on my investigation, I found a genuine analog in `multisig2/src/lib.rs`. `confirm()` checks membership *at the time of confirming* via `current_member()` [1](#0-0) , but confirmations already recorded in the `confirmations: LookupMap<RequestId, HashSet<String>>` are never invalidated when a member is later removed via `DeleteMember` [2](#0-1) . `confirm()` only counts `confirmations.len()` against `num_confirmations` without re-validating that each previously stored confirming identity is still a current member [3](#0-2) .

### Title
Stale confirmations from removed multisig members still count toward execution threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` accumulates confirmations keyed by member identity string in `self.confirmations`, and executes a request once `confirmations.len() + 1 >= self.num_confirmations`. There is no re-validation that stored confirmations belong to accounts/keys that are still active members at execution time. This mirrors the `GroupingModule.addIp` bug class: a state (confirmation / license attachment) is validated at the moment it is created but never re-checked for continued validity (membership / expiration) at the moment it is relied upon to authorize a privileged action.

### Finding Description
`add_request` and `confirm` insert the confirming identity's string representation into a `HashSet<String>` stored in `self.confirmations` [4](#0-3) . `current_member()` is only used to validate the identity of the *caller performing the current `confirm` call*, checking `self.members.contains(&member)` [1](#0-0) . It never re-validates the members whose confirmations are *already stored* in the set. When `DeleteMember` executes via `execute_request`, it removes the member from `self.members`/access keys [2](#0-1)  but does not purge or invalidate that member's existing confirmations on other still-pending requests. Thus a request confirmed in part by a member who is later removed can still reach the `num_confirmations` threshold and execute, counting a "confirmation" from an identity no longer authorized — the equality that should hold (`confirmations counted == confirmations by live members`) is broken.

### Impact Explanation
This falls under the Critical category ("a multisig request executed below threshold"): effectively, a stale confirmation from a since-removed member is functionally equivalent to executing with fewer than `num_confirmations` *currently authorized* signers, since a party no longer entitled to approve transactions is still contributing to the approval count that authorizes fund transfers, key additions, or contract deployment via `execute_request` (`Transfer`, `AddKey`, `DeployContract`, etc.) [5](#0-4) .

### Likelihood Explanation
This requires a plausible sequence that can occur in normal contract lifecycle: (1) a member confirms a pending request, (2) before the request reaches threshold, the members later vote to remove that member (e.g., due to key compromise, employee departure), and (3) the remaining members confirm the request to reach threshold, silently counting the removed member's earlier confirmation as still valid. No attacker-privileged role beyond normal multisig member operation is required, and this is a realistic sequencing rather than a purely theoretical one.

### Recommendation
When a `DeleteMember` (or key rotation) action executes, iterate pending requests and strip confirmations belonging to the removed member, or re-validate at `confirm()` time that every identity in the stored confirmation set is still `self.members.contains(...)` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with 3 members `A`, `B`, `C` and `num_confirmations = 2`.
2. `A` calls `add_request_and_confirm` for a `Transfer` request → `confirmations = {A}`.
3. Members submit and confirm a `DeleteMember { member: A }` request (via its own required threshold) and it executes, removing `A` from `self.members`.
4. `B` calls `confirm` on the original transfer request. `confirmations.len() (1) + 1 >= 2` → request executes, even though only `B` is a currently valid member confirming; `A`'s stale confirmation was counted toward the threshold.

**Note on verification limits:** I confirmed the relevant code paths (`confirm`, `execute_request`, `DeleteMember`, `current_member`) directly in `multisig2/src/lib.rs`, but I did not locate or inspect a `delete_member` helper's full body or any cross-request cleanup logic beyond what's shown (it may exist elsewhere in the file outside the ranges I read); if such cleanup exists, it would need to be confirmed against all pending requests to fully rule out this finding.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Returns current member: either predecessor as account or if it's the same as current account - signer.
    fn current_member(&self) -> Option<MultisigMember> {
        let member = if env::current_account_id() == env::predecessor_account_id() {
            MultisigMember::AccessKey {
                public_key: env::signer_account_pk()
                    .try_into()
                    .unwrap_or_else(|_| env::panic_str("Failed to deserialize public key")),
            }
        } else {
            MultisigMember::Account {
                account_id: env::predecessor_account_id(),
            }
        };
        if self.members.contains(&member) {
            Some(member)
        } else {
            None
        }
    }
