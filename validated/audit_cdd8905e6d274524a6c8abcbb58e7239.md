### Title
Post-default withdraw requests drain the isolated default recovery reserve, freezing or stealing funds owed to defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` mints an unlimited number of post-default withdraw receipts paid 1:1 out of `defaultRecoveryReserve`, but that reserve was sized at finalization only to cover `activeBasis + pendingBasis` claims at `defaultRecoveryPrice`. Each new post-default claim consumes the same reserve without adding any backing, so the "free" of recovery funds is not bound to any accounting entry — the analog of CVE-2017-11109's invalid free: a release operation applied to memory (reserve) the allocator never accounted for.

### Finding Description
`finalizeDefaultRecovery` computes `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, where `totalBasis = activeBasis + pendingBasis` (defaulted-epoch receipts only). Post-default receipts do not exist yet and are not part of `totalBasis`, so the reserve covers them only if the recovery price is below 1.

After finalization, `requestWithdraw` enters the `defaultRecoveryFinalized` branch: it burns `_amount` strategy tokens from the CDO, mints `_amount` receipt tokens to the user, and sets `postDefaultRequests[_user] = _amount` — no underlying moves into the strategy and `defaultRecoveryReserve` is not increased for these claims (`IdleCreditVault.sol:247-257`). Later, `_claimPostDefaultWithdrawRequest` calls `_transferDefaultRecovery`, which executes `defaultRecoveryReserve -= _amount` and transfers underlying (`IdleCreditVault.sol:760-767`, `912-917`).

The burn side does destroy CDO-held strategy tokens (which represent defaulted active NAV), but no new underlying is pulled for the payout; the tokens burned were worth `defaultRecoveryPrice` per unit, yet the claim pays 1:1. When the recovery price is below `RECOVERY_FULL`, paying post-default receipts at par consumes more reserve per unit of burned basis than those tokens were provisioned for, so either:
- the reserve is drained early and later `_transferDefaultRecovery` calls underflow (`reserve -= _amount` reverts on Solidity ≥0.8), permanently freezing defaulted-epoch and other claimants' recovery, or
- earlier post-default claimants are paid out of recovery earmarked for defaulted claimants — direct theft of unclaimed recovery.

### Impact Explanation
An unprivileged tranche-token holder (KYC-passed lender) who keeps tokens after default finalization can call `requestWithdraw` and then `claimWithdrawRequest` repeatedly, drawing the shared `defaultRecoveryReserve` at par rather than at `defaultRecoveryPrice`. Quantified: with `recoveryPrice = p < RECOVERY_FULL`, each post-default claim of `x` burns basis provisioned for `x·p` but withdraws `x`, over-consuming `x·(1−p)` of reserve. Once cumulative over-consumption exhausts the reserve, all remaining `_claimDefaultedWithdrawRequest` / `_claimDefaultedInstantWithdrawRequest` payouts revert on underflow — permanent freezing of the unclaimed recovery, or direct misappropriation by first movers.

### Likelihood Explanation
Requires a defaulted vault with `recoveryPrice < 1` (the common case for a real default) and any unprivileged holder retaining tranche tokens post-default — both routine conditions. The only guard is `defaultRecoveryReserve -= _amount` reverting on underflow, which converts the theft into a freeze for later claimants rather than preventing the bug. No epoch gating, KYC re-check beyond normal flow, or cap ties post-default claims to unallocated reserve.

### Recommendation
Track a distinct accounting bucket for post-default requests, or fund them separately: when `requestWithdraw` mints a post-default receipt, either pull the corresponding underlying from the CDO into `defaultRecoveryReserve` (or a new `postDefaultReserve`), or pay post-default claims only up to `reserve - reserveEarmarkedForDefaultedBasis`. Alternatively, apply `defaultRecoveryPrice` to post-default claims so consumption matches the provisioned basis.

```solidity
// Fork test: default the vault, finalize recovery at price < 1,
// then a post-default requester drains the shared reserve.
function testPostDefaultDrainsRecovery() external {
    // setup: deposit, run epoch, borrower defaults
    // manager calls _handleBorrowerDefault / finalizeDefaultRecovery
    //   -> defaultRecoveryReserve = R, defaultRecoveryPrice = p < RECOVERY_FULL

    // attacker (KYC'd tranche holder) still holds tranche tokens
    uint256 amt = attackerTrancheBalance * loweredVirtualPrice / ONE_TRANCHE;
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(attackerTrancheBalance, address(tranche)); // mints postDefault receipt, no funding

    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest(); // pays `amt` 1:1 out of defaultRecoveryReserve

    // defaulted-epoch claimant now reverts on underflow or receives less than
    // claimBasis * defaultRecoveryPrice / RECOVERY_FULL
    vm.expectRevert();
    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest();
}
```

The invariant violated is "one receipt, one provisioned payout": `defaultRecoveryReserve` is a fixed pool sized for defaulted-epoch basis only, yet post-default receipts claim from it at par with no corresponding provisioning — the Solidity analog of freeing memory outside the allocator's bookkeeping, yielding theft or permanent freezing of unclaimed recovery.
