### Title
Webhook-job UUID rejection check in `PipelineRunsController.Create` is bypassed when the same job is reachable by its int32 database ID - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` only blocks webhook-triggered runs when the `:ID` path parameter parses as a UUID; if the same job is requested by its integer primary key, the code explicitly comments "process it regardless of type" and forwards straight to `RunJobV2`, which contains no job-type restriction. `RunJobV2` only depends on `jb.Type.RequiresPipelineSpec()`/bootstrap checks, not on whether the type is an allowed run type, so a Webhook-typed job row (if one exists, e.g. from before the type was removed, or inserted via the ORM-level `MustInsertWebhookSpec` path used in tests) can be run via its int32 ID.

### Finding Description
In `core/web/pipeline_runs_controller.go`, `Create` first checks: [1](#0-0) 
This only rejects UUID-shaped IDs with `job.ErrJobTypeRemoved`. It then falls through to the int32 branch: [2](#0-1) 
The comment "Is it an int32? Then process it regardless of type" confirms there is no type gate on this path — any authenticated user (`isUser`) can call `RunJobV2` for any job ID, including one whose `Type == job.Webhook`.

`RunJobV2` itself performs no job-type allowlist check either: [3](#0-2) 
It only special-cases bootstrap OCR jobs and VRF; for any other type — including Webhook, since `Webhook.RequiresPipelineSpec()` returns `true` — it will execute the job's `PipelineSpec` via `ExecuteAndInsertFinishedRun`.

Job creation of `Type: Webhook` is blocked at `job.orm.CreateJob` and at the REST/GraphQL job-creation validators (`ErrJobTypeRemoved`), so new webhook jobs cannot normally be created through the API: [4](#0-3) 
However, this only prevents *new* insertion through the ORM/API layer. It does not retroactively delete or invalidate any webhook job rows that existed in the database prior to the removal (schema migrations only add a code-level check; there is no evidence in the reviewed code that historical webhook rows are purged). The test helper `cltest.MustInsertWebhookSpec` (used in `runner_integration_test.go` and `pipeline_runs_controller_test.go`) demonstrates that a Webhook job record can exist in the `jobs` table independent of the `CreateJob` guard, confirming the DB schema still supports such rows.

Existing regression tests only validate the UUID path is blocked: [5](#0-4) 
This test posts to `/v2/jobs/<uuid>/runs` and confirms rejection, but there is no equivalent test that posts to `/v2/jobs/<int32-id-of-webhook-job>/runs`, meaning the int32 path for a legacy webhook job is unverified and, per the code read, unguarded.

Note: `RunJobV2` has a `build.IsProd()` guard with the comment "Only used for local testing, not supported by the UI" that returns an error on secure/production builds: [6](#0-5) 
I was unable to fully resolve the `build` package's `IsProd()` implementation within the indexed context (no `package build` file was found by search), so I cannot confirm under what exact build/runtime conditions this guard is active vs. bypassed. This uncertainty affects whether the finding is exploitable in all deployments or only in specific (e.g., non-"prod-labeled") builds.

### Impact Explanation
If a Webhook-typed job row persists in the database (e.g., a legacy job created before the type was removed, or one inserted through a non-REST path), a low-privileged authenticated user with only run/edit role can trigger execution of that job's pipeline by requesting its integer job ID instead of its UUID, circumventing the explicit "job type webhook has been removed" restriction that the UUID-based check was designed to enforce. This corresponds to an "unauthorized job run" impact — reintroducing a run path (external-initiator-style) that was intentionally removed from the product, which could execute bridge/HTTP tasks against internal/external resources without the intended access controls that historically gated webhook runs (external initiator access key/secret).

### Likelihood Explanation
Exploitability is conditional and not fully confirmed:
- Requires a Webhook-typed job to already exist in the DB with a known int32 ID — the API-level `CreateJob`/`ValidateSpec` paths reject new webhook job creation, so this depends on the presence of a legacy/pre-existing row, which is an operational/data precondition outside the attacker's control (not a general misconfiguration but a residual-data condition).
- Requires only a run-role or edit-role authenticated user (`isUser` true) — no admin/EI credential needed, matching the stated precondition.
- Additionally gated by the unresolved `build.IsProd()` check in `RunJobV2`; if this check is active in production, the endpoint returns a hard error ("manual job runs not supported on secure builds") regardless of job type, which would eliminate the vulnerability in production deployments. This is a material open question I could not resolve from the available index.

### Recommendation
Move the job-type rejection check in `PipelineRunsController.Create` to occur after resolving the job record (not just based on ID string format), so it applies uniformly regardless of whether the job is referenced by UUID or int32 ID — e.g., look up the job's `Type` before invoking `RunJobV2` and reject `job.Webhook`/other removed types with `ErrJobTypeRemoved` for both ID formats. Alternatively, add the same type-based rejection inside `RunJobV2` itself so all callers (REST, GraphQL `RunJob`) are protected consistently.

### Proof of Concept
1. In `core/web/pipeline_runs_controller_test.go`, add a test that:
   - Starts an app (`cltest.NewApplicationEVMDisabled` or similar) with a run/edit-role authenticated HTTP client.
   - Directly inserts a job via `cltest.MustInsertWebhookSpec(t, app.GetDB(), uuid.New())` (bypassing `CreateJob`'s `ErrJobTypeRemoved` guard) to obtain a job with `Type: job.Webhook` and a known int32 `job.ID`.
   - Sends `POST /v2/jobs/<job.ID>/runs` (using the integer ID, not the UUID) with an authenticated user client.
   - Asserts on the response: if the response is `200`/success and a pipeline run row is created (`pipeline_runs` count increases), the bypass is confirmed; if the response is `422 Unprocessable Entity` referencing `ErrJobTypeRemoved`, or if `RunJobV2` errors due to `build.IsProd()`, the endpoint is safe under those build conditions.
2. Compare against the existing `TestPipelineRunsController_RunExistingWebhookJobRejected` test (`core/web/pipeline_runs_controller_test.go:51-72`), which only exercises the UUID path, to demonstrate the coverage gap for the int32 path.

func (app *ChainlinkApplication) RunJobV2(
	ctx context.Context,
	jobID int32,
	meta map[string]any,
) (int64, error) {
	if build.IsProd() {
		return 0, errors.New("manual job runs not supported on secure builds")
	}
	jb, err := app.jobORM.FindJob(ctx, jobID)
	if err != nil {
		return 0, errors.Wrapf(err, "job ID %v", jobID)
	}
	var runID int64

	// Some jobs are special in that they do not have a task graph.
	isBootstrap := jb.Type == job.OffchainReporting && jb.OCROracleSpec != nil && jb.OCROracleSpec.IsBootstrapPeer
	if jb.Type.RequiresPipelineSpec() || !isBootstrap {
		var vars map[string]any
		var saveTasks bool
		if jb.Type == job.VRF {
			saveTasks = true
			// Create a dummy log to trigger a run
			testLog := types.Log{
				Data: bytes.Join([][]byte{
					jb.VRFSpec.PublicKey.MustHash().Bytes(),  // key hash
					common.BigToHash(big.NewInt(42)).Bytes(), // seed
					evmutils.NewHash().Bytes(),               // sender
					evmutils.NewHash().Bytes(),               // fee
					evmutils.NewHash().Bytes(),
				}, // requestID
					[]byte{}),
				Topics:      []common.Hash{{}, jb.ExternalIDEncodeBytesToTopic()}, // jobID BYTES
				TxHash:      evmutils.NewHash(),
				BlockNumber: 10,
				BlockHash:   evmutils.NewHash(),
			}
			vars = map[string]any{
				"jobSpec": map[string]any{
					"databaseID":    jb.ID,
					"externalJobID": jb.ExternalJobID,
					"name":          jb.Name.ValueOrZero(),
					"publicKey":     jb.VRFSpec.PublicKey[:],
					"evmChainID":    jb.VRFSpec.EVMChainID.String(),
				},
				"jobRun": map[string]any{
					"meta":           meta,
					"logBlockHash":   testLog.BlockHash[:],
					"logBlockNumber": testLog.BlockNumber,
					"logTxHash":      testLog.TxHash,
					"logTopics":      testLog.Topics,
					"logData":        testLog.Data,
				},
			}
		} else {
			vars = map[string]any{
				"jobRun": map[string]any{
					"meta": meta,
				},
			}
		}
		runID, _, err = app.pipelineRunner.ExecuteAndInsertFinishedRun(ctx, *jb.PipelineSpec, pipeline.NewVarsFrom(vars), saveTasks)
	}
	return runID, err
}

func TestPipelineRunsController_RunExistingWebhookJobRejected(t *testing.T) {
	t.Parallel()

	ethClient := cltest.NewEthMocksWithStartupAssertions(t)
	ethClient.On("BalanceAt", mock.Anything, mock.Anything, mock.Anything).Maybe().Return(big.NewInt(0), nil)
	cfg := configtest.NewGeneralConfig(t, func(c *chainlink.Config, s *chainlink.Secrets) {
		c.JobPipeline.HTTPRequest.DefaultTimeout = commonconfig.MustNewDuration(2 * time.Second)
	})

	app := cltest.NewApplicationWithConfig(t, cfg, ethClient)
	require.NoError(t, app.Start(t.Context()))

	jobUUID := uuid.New()
	cltest.MustInsertWebhookSpec(t, app.GetDB(), jobUUID)

	client := app.NewHTTPClient(nil)
	body := strings.NewReader(`{"data":{"result":"123.45"}}`)
	response, cleanup := client.Post("/v2/jobs/"+jobUUID.String()+"/runs", body)
	defer cleanup()
	cltest.AssertServerResponse(t, response, http.StatusUnprocessableEntity)
	require.Contains(t, string(cltest.ParseResponseBody(t, response)), "webhook")
}
