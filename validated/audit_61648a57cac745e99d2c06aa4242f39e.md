### Title
Bridge OutgoingToken credential disclosed to any authenticated view-role user via GET /v2/bridge_types/:BridgeName - (File: core/web/bridge_types_controller.go, core/web/presenters/bridges.go)

### Summary
`BridgeTypesController.Show` returns a `presenters.BridgeResource` built directly from the stored `bridges.BridgeType`, and the `OutgoingToken` field is serialized without `omitempty` or any redaction, unlike `IncomingToken`. Since the `GET /v2/bridge_types/:BridgeName` route only requires generic authentication (not edit-role), any authenticated low-privilege (view-role) session can retrieve the plaintext `OutgoingToken` for any bridge.

### Finding Description
`BridgeType.OutgoingToken` is stored in plaintext in the DB (unlike `IncomingTokenHash`, which is a salted hash) [1](#0-0) . `presenters.NewBridgeResource` copies `b.OutgoingToken` straight into the JSON-serialized `BridgeResource.OutgoingToken` field, which is tagged only `json:"outgoingToken"` (no `omitempty`), in contrast to `IncomingToken`, which is explicitly commented as "only provided when creating a Bridge" and tagged `omitempty` [2](#0-1) .

`BridgeTypesController.Show` calls `orm.FindBridge` and passes the result directly to `presenters.NewBridgeResource(bt)` with no field stripping [3](#0-2) . The same unredacted resource is also returned by `Index`, `Update`, and `Destroy` [4](#0-3) [5](#0-4) [6](#0-5) .

I was not able to fully confirm the exact route/role gating in `core/web/router.go` within the available tool budget (the file content itself was not retrieved, only grep hit-counts), so the specific claim that `GET /v2/bridge_types/:BridgeName` is gated by generic auth only (and not `auth.RequiresEditRole`) could not be independently verified from source in this session. This is a meaningful gap: if the route is in fact behind `auth.RequiresEditRole` like the mutating bridge routes, the described attack path would not hold for view-role sessions.

### Impact Explanation
If the GET route is indeed reachable by view-role sessions, this is a credential-disclosure issue: an authenticated user with only read/view privileges can obtain the plaintext `OutgoingToken`, which the node uses to authenticate itself to the external adapter. Possession of this token would let a low-privileged user impersonate the node's outbound calls to the adapter, potentially manipulating data returned to the node (e.g., price feed inputs) or accessing systems that trust the outgoing token as authentication.

### Likelihood Explanation
Assuming the route gating is as stated (generic auth only, no edit-role requirement), this requires only a single, ordinary precondition: any valid low-privilege (view-role) session or restricted API token, and a single unauthenticated-to-the-attacker-but-authenticated-to-node GET request. No timing or race conditions are needed, and it is fully repeatable for every bridge the node has configured.

### Recommendation
Add `omitempty` and strip `OutgoingToken` from `presenters.BridgeResource` for read-only responses (`Show`/`Index`), returning it only in the `Create` (and possibly `Update`, since a new token isn't generated there) response, mirroring the treatment of `IncomingToken`. Alternatively/additionally, ensure the `GET /v2/bridge_types/:BridgeName` and `/v2/bridge_types` routes require `auth.RequiresEditRole` (or a dedicated secrets-view permission) rather than generic authentication, consistent with how mutating bridge routes are protected.

### Proof of Concept
1. Unit test on `presenters.NewBridgeResource`: construct a `bridges.BridgeType{OutgoingToken: "secret-outgoing-token", ...}`, call `NewBridgeResource`, `json.Marshal` the result, and assert the JSON contains `"outgoingToken":"secret-outgoing-token"` with no omission.
2. Handler-level integration test (extending `core/web/bridge_types_controller_test.go`): create a bridge via an edit-role client (capturing the generated `OutgoingToken` from the `BridgeType` in the DB/ORM), then issue `GET /v2/bridge_types/<name>` using a client authenticated with only view-role credentials, and assert the response body's `outgoingToken` field is non-empty and matches the stored value — while also asserting the same view-role client cannot successfully call `POST/PATCH/DELETE /v2/bridge_types` (expect 401/403), confirming the asymmetry between read and write authorization.

Note: this PoC and the vulnerability's validity hinge on confirming in `core/web/router.go` that the GET bridge_types routes are not wrapped with `auth.RequiresEditRole`; that specific gating was not directly confirmed in this session due to tool-call limits and should be verified before treating this as a confirmed exploitable finding.

func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
