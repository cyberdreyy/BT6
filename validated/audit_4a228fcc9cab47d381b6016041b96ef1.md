### Title
Miner's `StackerDBListener` never reverses stale rejection weight when a signer later flips to acceptance, permanently inflating `total_weight_rejected` for that block — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The miner-side `StackerDBListener` tallies `total_weight_approved` and `total_weight_rejected` per block from signer `BlockResponse` messages using two independent, never-reconciled counters. A signer's weight is added to `total_weight_rejected` the first time it rejects (gated only by `block.responded_signers.insert(slot_id)`), and separately added to `total_weight_approved` the first time it accepts (gated only by `!block.gathered_signatures.contains_key(&slot_id)`). Because `responded_signers` is a single shared set used to gate *both* paths, a signer that rejects first and later accepts the same block gets counted in both totals — its rejection weight is never subtracted when it flips to acceptance.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`:

- On `BlockResponse::Accepted`, weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`: [1](#0-0) 

- On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot is seen in `responded_signers`): [2](#0-1) 

- The rejection-threshold check that wakes the miner's waiting thread is purely additive and never decremented: [3](#0-2) 

The signer side legitimately re-evaluates and flips a prior rejection to an acceptance for the same block when the reject reason is deemed re-evaluable (`should_reevaluate_reject_reason`), or when a pre-commit is re-sent — this is documented, intended behavior of the state machine (`LocallyRejected --> LocallyAccepted : re-evaluated`): [4](#0-3) [5](#0-4) 

When such a signer's flipped `Accepted` message reaches the miner:
1. Its earlier `Rejected` message already set `responded_signers.insert(slot_id) == true` and added `signer_entry.weight` to `total_weight_rejected`.
2. The later `Accepted` message checks `!block.gathered_signatures.contains_key(&slot_id)`, which is still `true` (this map is untouched by the reject path), so the same `signer_entry.weight` is *also* added to `total_weight_approved`.

`total_weight_rejected` is never decremented on this transition, so the same signer's weight now counts toward both the rejection tally and the acceptance tally simultaneously. This breaks the invariant that `total_weight_approved` and `total_weight_rejected` are drawn from disjoint sets of signer weight (i.e., "aggregated weight vs. verified per-signer decision" no longer match).

### Impact Explanation
This is a liveness wedge on the miner's block-response coordinator, not merely a bookkeeping inconsistency: the stale, never-cleared rejection weight can push `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` to trip even though, at the time evaluated, that signer no longer opposes the block (it accepted). This can cause the miner to prematurely conclude a valid, consensus-reachable block was rejected and abandon/re-mine it, even when the real, current tally of signer decisions would have crossed the acceptance threshold instead. Because the two counters are permanently desynchronized once a flip occurs (no code path ever decrements `total_weight_rejected` for a slot that later accepts, nor vice versa for a slot that had accepted and later rejects, since `gathered_signatures` is likewise never cleared), the corruption persists for the lifetime of that block's tracked `BlockInfo` in the miner process. This matches the rule's named liveness impact of miscounted/aggregated-weight vs. verified-accept divergence.

### Likelihood Explanation
This requires only a single ordinary signer (no majority, no other signer's key) to send a `Rejected` message followed later by an `Accepted` message for the same `signer_signature_hash` — a normal occurrence the signer state machine explicitly supports via reject-reason re-evaluation and pre-commit re-proposal flows. No malicious signature forgery or protocol violation is needed; only ordinary message ordering/timing (reject then accept) that the documented state machine permits.

### Recommendation
Make `total_weight_approved` and `total_weight_rejected` mutually exclusive per slot: when processing an `Accepted` message, if `slot_id` is present in `responded_signers` due to a prior rejection (and not yet counted as accepted), subtract the signer's weight from `total_weight_rejected` before adding it to `total_weight_approved` (and symmetrically for the reverse transition). Alternatively, track each slot's current classification (accepted/rejected) explicitly and recompute both totals from that per-slot state rather than using independent monotonic add-only counters gated by different keys (`gathered_signatures` vs `responded_signers`).

### Proof of Concept
1. Miner proposes block `B` (hash `H`) and starts tracking it in `self.blocks`.
2. Signer `S` (weight `w`) validates `B`, finds a transient issue, and sends `BlockResponse::Rejected` for `H`. Miner's listener: `responded_signers.insert(slot_S) == true` → `total_weight_rejected += w`.
3. `S`'s local reject reason is one that `should_reevaluate_reject_reason` allows to be reconsidered (e.g., due to a later proposal/pre-commit re-evaluation), and `S` subsequently sends `BlockResponse::Accepted` for the same `H`.
4. Miner's listener: `gathered_signatures.contains_key(slot_S) == false` (untouched by the reject path) → `total_weight_approved += w`.
5. Now `total_weight_rejected` still includes `w` from step 2, and `total_weight_approved` also includes `w` from step 4 — the same signer's weight is double-counted across the two disjoint tallies, and `total_weight_rejected` never gets corrected, so `block.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` can be true even though `S` currently supports the block.
