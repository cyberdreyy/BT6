This confirms the core mechanism: chunk validators call `apply_new_chunk` with `StorageDataSource::Recorded` and replay the *entire* deterministic `apply()` function, processing **all** receipts in the exact same order as the producer — including R1, whether it fails or not. Both producer and validator run the identical `apply_action_receipt` logic on R1 (same reads, same failure, same `TrieUpdate::rollback()` of only prospective writes), then process R2 identically. The recorder's `upper_bound_size` is monotonically accumulated from `self.trie.recorder`, which lives at the `Trie`/apply-call level, not scoped per-receipt, and is never reset between receipts on either side.

### Title
No vulnerability found — premise of consensus divergence is false - ([File: runtime/runtime/src/lib.rs])

### Summary
The question's premise — that a chunk validator would replay "only the successful receipts" from a witness while the producer's baseline includes bytes from a failed, rolled-back receipt R1 — does not match how stateless validation works. Validators re-execute the *entire* deterministic `apply()` over *all* receipts (successful and failed) using the recorded partial storage, so both sides observe identical `recorded_storage_size_upper_bound()` growth from R1 before computing R2's delta.

### Finding Description
`TrieUpdate::rollback` at [1](#0-0)  only clears `self.prospective` (pending key/value writes) and rolls back contract deploys; it does not and should not touch `self.trie.recorder`, because the recorder in `TrieRecorder` (`core/store/src/trie/trie_recording.rs`) tracks the storage *proof* — the trie nodes that were genuinely read from the underlying trie during execution, which must be included in the witness regardless of whether the receipt that triggered the read ultimately succeeded or failed. Both producer and validator need this proof because the validator has to be able to reproduce the same intermediate reads (including reads that occurred before a failure was detected) to verify the failure was legitimate and that state changes were correctly rolled back.

Crucially, the `storage_proof_size_before_receipt` snapshot at [2](#0-1)  is taken inside `apply_action_receipt`, which is called once per receipt, in order, for every receipt in the chunk — by both the chunk producer (`apply_new_chunk` against `StorageDataSource::DbTrieOnly`/`Recorded`) and the chunk validator (`apply_new_chunk` against `StorageDataSource::Recorded`, per `validate_chunk_state_witness_impl` at [3](#0-2) ). The validator does not selectively skip failed receipts — `validate_source_receipt_proofs` determines *which receipts to apply* (based on the merkle-proven outgoing-receipt set), not whether a receipt "succeeded"; success/failure is an outcome of re-executing the same deterministic logic, not a filter applied beforehand.

Since `apply()` is fully deterministic given the same trie/partial-storage and receipt list, R1's execution (including its trie reads, its failure, and its rollback) happens identically on both producer and validator, so `recorded_storage_size_upper_bound()` is identical on both sides at the point R2's snapshot is taken. There is no divergence.

### Impact Explanation
None. No state-root divergence, no consensus split, and no bypassable per-receipt storage-proof limit — the check is deterministic and applied identically on both replicas.

### Likelihood Explanation
Not applicable; the described precondition (validator sees a different set of receipts than the producer, omitting failed ones) does not occur in this codebase's stateless-validation design.

### Recommendation
No fix needed. If auditing this area further, the actually interesting properties to test are (a) that `apply()` truly is bit-for-bit deterministic across producer and validator paths for chunks containing failing receipts, and (b) that recorder state is never reset mid-apply-call in a way that could desync the two paths — but nothing found here does that.

### Proof of Concept
Not applicable — no exploit exists. A useful *regression* test (not a security PoC) would be: in `runtime/runtime/src/tests/apply.rs`, construct a chunk with R1 (a receipt that triggers several trie reads then fails, e.g., a `FunctionCall` action that reads storage and then panics) followed by R2 (a receipt near `per_receipt_storage_proof_size_limit`), run `apply()` twice — once via the normal `DbTrieOnly` path and once by capturing the resulting `PartialStorage` and re-running via `StorageDataSource::Recorded` (mirroring `validate_chunk_state_witness_impl`) — and assert both runs produce the identical `ExecutionOutcome`/error for R2 (i.e., the per-receipt limit decision matches), confirming determinism rather than exposing a flaw.
