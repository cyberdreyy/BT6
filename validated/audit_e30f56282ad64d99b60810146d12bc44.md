### Title
Unfunded instant-withdraw receipts can drain unrelated underlying held by the strategy because `claimInstantWithdrawRequest` never checks that funds were actually collected — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` burns the user's full `instantWithdrawsRequests` receipt balance and pays it out via `_transferFundedClaim`, which only excludes `defaultRecoveryReserve`. There is no check that the corresponding `pendingInstantWithdraws` amount was ever collected from the CDO/borrower through `collectInstantWithdrawFunds`. Because `deposit()` parks new buffer-period deposits as raw underlying in the strategy, an unprivileged receipt holder can spend other depositors' funds (or any underlying held by the strategy) with an unfunded or partially funded instant receipt.

### Finding Description
The instant-withdraw flow is two-phase:

1. `requestInstantWithdraw` mints the user a 1:1 strategy-token receipt and increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (IdleCreditVault.sol:356-375).
2. Later, `getInstantWithdrawFunds` on the CDO pulls borrower funds, calling `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and pulls underlying into the strategy (IdleCreditVault.sol:398-403).

The claim path (`claimInstantWithdrawRequest`, IdleCreditVault.sol:380-393, invoked by `IdleCDOEpochVariant.claimInstantWithdrawRequest` gated only by the `allowInstantWithdraw` flag, IdleCDOEpochVariant.sol:975-979) transfers `instantWithdrawsRequests[_user]` out of the strategy with no accounting of how much was actually funded:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);   // only guards defaultRecoveryReserve
```

Meanwhile, ordinary deposits made between epochs route underlying into the strategy itself — `deposit()` executes `underlyingToken.safeTransferFrom(msg.sender, address(this), _amount)` (IdleCreditVault.sol:596-605). `sendInterestAndDeposits` only sweeps these funds back to the CDO at the next `startEpoch`. During the buffer window, therefore, the strategy's underlying balance equals buffered deposits plus whatever (if anything) was collected for instant receipts.

The receipt was funded only if the borrower returned enough at `startEpoch`/`getInstantWithdrawFunds`; `collectInstantWithdrawFunds` merely tracks `pendingInstantWithdraws -= _amount` — a counter that `claimInstantWithdrawRequest` never consults. An attacker holding an instant receipt can claim while the strategy balance is inflated by other users' buffered deposits, and receive underlying far beyond what was funded for their receipt.

### Impact Explanation
Direct theft: any unprivileged user (a KYC-passed lender or tranche holder who made an instant-withdraw request when the APR dropped) can convert an unfunded receipt into real underlying drawn from other depositors' buffered deposits or any residual strategy balance. This breaks the "one receipt one funded payout" invariant and makes the vault insolvent for the depositors whose funds are taken — their strategy tokens remain minted but the underlying backing is gone, crystallizing a loss equal to the overclaimed amount.

### Likelihood Explanation
- Requires only that the attacker request an instant withdrawal in a buffer window where the APR dropped (a normal, expected condition), and that at claim time the strategy holds underlying belonging to someone else — precisely what `deposit()` creates for every buffer-period deposit.
- No privileged cooperation is needed; the attacker simply calls `cdoEpoch.claimInstantWithdrawRequest()` earlier than honest claimants, or before/partially-without `getInstantWithdrawFunds` collecting the full pending amount.
- The only gates are `allowInstantWithdraw` (enabled for claims after epochs stop) and the balance check in `_transferFundedClaim`, which deliberately excludes only `defaultRecoveryReserve` — not unfunded instant basis.
- Caveat: exploitability depends on the ordering of `allowInstantWithdraw` being set versus when buffered deposits land in the strategy; this window exists whenever claims are enabled while `deposit()`-held underlying is present in the strategy. I could not fully enumerate every site that toggles `allowInstantWithdraw` within my search budget, so this timing assumption should be verified in a PoC.

### Recommendation
Track funded vs. unfunded instant receipts separately. For example, keep `pendingInstantWithdraws` as the *claimable* funded pool and add a check in `claimInstantWithdrawRequest` that the claim does not exceed the funded portion (e.g., `amount <= fundedInstant` or decrementing a `claimableInstantWithdraws` counter that `collectInstantWithdrawFunds` increments). Alternatively, extend `_transferFundedClaim`-style isolation so that instant claims can only spend underlying explicitly reserved for them, never the `deposit()` buffer balance.

### Proof of Concept
Foundry fork PoC (against the epoch CDO deployment, mirroring `test/foundry/IdleCreditVault.t.sol` helpers `_startEpochAndCheckPrices`/`_toggleEpoch`/`_getInstantFunds`):

```solidity
function testUnfundedInstantReceiptDrainsDeposits() external {
    uint256 amountWei = 10_000 * ONE_SCALE;

    // Setup: attacker and victim both deposit, epoch 0 runs and stops with lower APR
    // so instant withdraws become available.
    idleCDO.depositAA(amountWei);                       // attacker-owned (this contract)
    _depositWithUser(victim, amountWei, true);          // honest depositor
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // Attacker requests an instant withdraw; strategy mints them a receipt and
    // pendingInstantWithdraws increases. No underlying has been collected yet.
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // New epoch starts; borrower is honest but slow — getInstantWithdrawFunds has
    // NOT been called (or only partially funded). Strategy underlying balance is 0
    // for instant receipts at this point.
    _startEpochAndCheckPrices(1);
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    // epoch stops; buffer period opens, allowInstantWithdraw claims enabled
    _stopEpochAndCheckPrices(1, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // During the buffer, a fresh depositor's underlying is transferred into the
    // strategy via deposit() and sits there until the next startEpoch sweep.
    _depositWithUser(freshVictim, requested, true);
    assertGe(underlying.balanceOf(address(strategy)), requested);

    // Attacker claims the full receipt even though pendingInstantWithdraws was
    // never collected. _transferFundedClaim only excludes defaultRecoveryReserve.
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(address(this)) - balPre, requested,
        'unfunded instant receipt paid from buffered deposits');

    // freshVictim's deposit backing is gone: strategy holds ~0 underlying while
    // freshVictim's strategy tokens remain minted => insolvency of `requested`.
}
```

Key assertions: `pendingInstantWithdraws` is unchanged by the claim (theft bypasses the funding counter entirely), and the stolen amount equals the attacker's receipt even though zero underlying was collected for it.
