## Title
Activation-registry precompile permanently strands ETH sent pre-Cobalt (Beryl) — ([File: crates/common/precompiles/src/activation/dispatch.rs])

### Summary
The `IActivationRegistry` precompile's `dispatch_with_observer` only rejects calls carrying `msg.value` starting at the `Cobalt` hardfork. On `Beryl` (and any earlier upgrade at which the precompile could be reached), any call — including the completely unauthenticated, read-only `isActivated`/`checkActivated` selectors — that attaches ETH is accepted and executed successfully, transferring the ETH to the precompile's address. This precompile has no accounting for received value and no withdrawal function, so the ETH becomes permanently unrecoverable, mirroring the reported `EsEMBR.sol` class of bug: a contract that can receive ETH with no state to track or retrieve it.

### Finding Description
`ActivationRegistryStorage::dispatch_with_observer` gates the `NonPayable` revert behind `upgrade >= BaseUpgrade::Cobalt`: [1](#0-0) 

Before `Cobalt` (i.e., at `Beryl`, the activation registry's genesis fork per `provider.rs`), the guard is skipped entirely and calldata gas deduction plus `self.inner(...)` execute normally with any attached value, meaning the ETH transfer that accompanies the CALL succeeds and the precompile logic runs to completion. The comment and accompanying test confirm this is deliberate "accept-and-strand" behavior preserved only for byte-identical historical replay: [2](#0-1) 

The test explicitly documents the exploitation path: an unauthenticated, read-only selector (`isActivated`) is "the exact path an attacker uses to strand ETH": [3](#0-2) 

Because the activation registry is a virtual precompile (not deployed bytecode with a `receive`/withdraw path), any ETH value that lands at its address via a successful CALL has no code path to move it back out — it is permanently locked at that address, just as `EsEMBR.sol`'s `receive()` accepted ETH into `totalEthPerEsembr` accounting that could never be triggered to release it when `totalSupply == 0`.

### Impact Explanation
Any unprivileged, unauthenticated transaction sender who submits a CALL to the activation-registry precompile address with nonzero `value` while `Beryl` is the active upgrade permanently loses that ETH — it is not credited to any account, tracked in any recoverable state, or refundable. This is a concrete permanent freezing/loss of user funds, matching the report's "medium" bug class (ETH becomes stuck with no accounting or retrieval mechanism).

### Likelihood Explanation
The path requires no special privilege: it is reachable by any signed transaction from any EOA that targets the precompile address with a small amount of ETH attached to any calldata (even the unauthenticated `isActivated` read). The behavior is deterministic and 100% reproducible for the duration that `Beryl` remains the active upgrade for the chain (or during replay of historical Beryl-era blocks). The code and tests explicitly acknowledge this is intentional legacy behavior rather than an oversight, which lowers its novelty but does not change the fact that funds sent this way are unrecoverable.

### Recommendation
Since replay parity requires that pre-Cobalt block execution remain byte-identical, this behavior cannot be retroactively "fixed" for already-processed blocks. Going forward, ensure the `NonPayable` guard remains in place from `Cobalt` onward (as it is today) and audit whether any currently-live chain configuration can still have `Beryl` (pre-`Cobalt`) active for new blocks; if so, expedite the `Cobalt` upgrade activation or add an explicit warning/documentation for integrators so that no wallets or contracts ever attach value to activation-registry calls while `Beryl` semantics are live.

### Proof of Concept
The existing unit test demonstrates the exact mechanics: [2](#0-1) 
Submitting a transaction with `to = <activation registry precompile address>`, `value > 0`, and calldata `IActivationRegistry::isActivatedCall{...}` while the chain's active upgrade resolves to `Beryl` causes the call to succeed (`output.is_success()`), transferring `value` to the precompile address with no way to retrieve it afterward.
