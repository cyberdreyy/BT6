### Title
Loss-adjusted withdraw receipts are paid at par because `lossRecoveryPriceByEpoch` is keyed by the post-increment `epochNumber` while user receipts stay keyed by their request epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

Analog to CVE-2020-16159 (out-of-bounds read in `GPMF_ScaledData()` on attacker-influenced indexing): `IdleCreditVault` looks up a receipt's recovery price through an epoch index that can point at the wrong slot. `requestWithdraw` records `withdrawsRequestsByEpoch[user][epochNumber]` and `lastWithdrawRequest[user] = epochNumber` at request time (lines 282, 293). `collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]` using the value of `epochNumber` at collection time (line 421). `deposit()` increments `epochNumber` when called while the epoch is still running, i.e. inside `stopEpoch` (lines 607-610). If `collectWithdrawFunds` runs after that increment during a lossy `stopEpochWithDuration`, the haircut is stored under `N+1` while every pending receipt is still keyed to `N`. `_claimLossAdjustedWithdrawRequest` then reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` = `lossRecoveryPriceByEpoch[N]` = 0 (lines 790-792), returns 0, and the claim falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[user]` at par (lines 338-349) even though the strategy only collected the loss-reduced amount.

### Finding Description

The receipts and the haircut are indexed by two different epoch values:

- Write side of the index (request): `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `lastWithdrawRequest[_user] = currentEpoch` where `currentEpoch = epochNumber` read before the epoch ends (lines 260-293).
- Write side of the price: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` inside `collectWithdrawFunds` (line 421).
- Read side: `uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (line 791).

`epochNumber` is only bumped inside `deposit()` when `IIdleCDOEpochVariant(idleCDO).isEpochRunning()` is still true (lines 607-610). So whether the haircut lands on the same key the claim path later reads depends entirely on intra-`stopEpoch` call ordering, not on the epoch the receipts were created in — exactly like an OOB read: the lookup slot is derived from a counter that moved between write and read.

When the mismatch occurs, `_claimLossAdjustedWithdrawRequest` silently returns 0 instead of reverting, and `_claimFundedWithdrawRequest` succeeds because `epochNumber (N+1) > lastWithdrawRequest (N)` (line 326). The user is paid the full `withdrawsRequests` basis from a strategy balance that only received `pendingBasis - pendingLoss`.

### Impact Explanation

Broken invariant: loss socialization / one receipt one payout. The realized `stopEpochWithDuration` loss that `previewLossAdjustedWithdrawFunds` assigned to pending receipts is never applied: every receipt in the affected epoch redeems at par. Since only `_amount < pendingBasis` was transferred in, either:

- early claimants drain the strategy and later claimants' `safeTransfer` reverts (permanent freezing of remaining receipts, or spillover into `defaultRecoveryReserve` isolation), or
- the shortfall is paid out of funds belonging to other receipts, creating direct insolvency equal to `pendingLoss = _lossAmount * pendingBasis / totalBasis`.

Quantified loss: up to the full pending-receipt share of the realized loss, `pendingLoss`, stolen by first claimants / frozen for later ones.

### Likelihood Explanation

Requires a lossy `stopEpochWithDuration` (borrower underpays, an honest-manager event in scope) combined with `collectWithdrawFunds` being invoked after the strategy-token `deposit()` that bumps `epochNumber`. Both are ordinary protocol calls; the user-side precondition is simply having an unclaimed `requestWithdraw` receipt in that epoch, which any KYC-passing lender creates. The guard at lines 263-271 only prevents *new* requests while a loss receipt is pending; it does not fix the index skew itself.

### Recommendation

Key the loss price by the epoch that the receipts were recorded under, not the live counter at collection time. Either snapshot `epochNumber` before the increment inside `stopEpoch` and pass it to `collectWithdrawFunds`, or store `lossRecoveryPriceByEpoch[epochNumber - 1]` when the collection happens after the bump. Additionally, make `_claimLossAdjustedWithdrawRequest`/`_claimFundedWithdrawRequest` revert when `withdrawsRequestsByEpoch[user][lastWithdrawRequest]` is non-zero but no recovery price exists for that epoch and funding was partial, instead of silently falling through to a par payout.

### Proof of Concept

Foundry fork sketch (mainnet fork, epoch variant CDO + `IdleCreditVault`):

```solidity
function testLossReceiptIndexSkew() public {
    // Epoch N running, APR > 0. KYC'd lender deposits into AA and requests withdraw.
    vm.startPrank(lender);
    cdo.requestWithdraw(0, AA);              // records receipt under epochNumber = N
    vm.stopPrank();

    // Manager stops epoch with a loss: borrower repays deposits + interest - loss.
    // Inside stopEpoch: strategy.deposit(...) bumps epochNumber to N+1,
    // then cdo calls collectWithdrawFunds(funded < pendingBasis)
    // -> lossRecoveryPriceByEpoch[N+1] = price  (line 421)
    vm.prank(manager);
    cdo.stopEpochWithDuration(lossAmount, duration);

    // Attacker/user claims: reads lossRecoveryPriceByEpoch[N] == 0,
    // falls through to _claimFundedWithdrawRequest and receives FULL basis.
    uint256 balBefore = underlying.balanceOf(lender);
    vm.prank(lender);
    cdo.claimWithdrawRequest();
    uint256 claimed = underlying.balanceOf(lender) - balBefore;

    assertEq(claimed, fullReceiptBasis);          // paid at par
    assertLt(strategyUnderlyingBal, remainingReceiptBasis); // insolvency for later claimants
}
```

Uncertainty note: I could not fully confirm the intra-`stopEpoch` ordering in `IdleCDOEpochVariant.sol` (whether `collectWithdrawFunds` executes after the `deposit()` that increments `epochNumber`) within the available search iterations. If collection happens strictly before the increment, this specific skew does not trigger; in that case the closest residual analog — the same stale-index read pattern via `lastWithdrawRequest` being reset to 0 in `_clearWithdrawClaimForEpoch` (line 835) while receipts from other epochs remain — should be audited but I cannot confirm a fund-impact path for it.
