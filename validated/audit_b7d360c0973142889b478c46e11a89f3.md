### Title
Loss-adjusted withdraw receipts are keyed to the wrong epoch, so the haircut is never applied and claimants over-draw funded proceeds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` stores the stop-epoch loss haircut under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` has already been incremented earlier in the same `stopEpoch` flow by `deposit()` (which bumps `epochNumber` when `isEpochRunning()` is still true). Users' receipts were recorded against `lastWithdrawRequest = oldEpoch`, so `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[oldEpoch] == 0` — an effectively uninitialized slot — treats the receipt as fully funded, and `_claimFundedWithdrawRequest` pays it out at par. The first claimants drain more than the haircut-funded amount; later claimants' transfers revert.

### Finding Description
- `deposit()` increments `epochNumber` when called while the epoch is still running, i.e. during `stopEpoch`'s borrower-repay deposit: `totEpochDeposits = 0; epochNumber += 1;` [1](#0-0) 
- `collectWithdrawFunds` then persists the loss price under the already-bumped counter: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;` [2](#0-1) 
- Receipts are keyed by `lastWithdrawRequest[_user] = currentEpoch` captured at `requestWithdraw` time (the pre-stop epoch) [3](#0-2) 
- At claim time the lookup uses that stale epoch: `uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch]; if (lossRecoveryPrice == 0) return amount;` [4](#0-3) 
- The same wrong-key read exists in the `requestWithdraw` guard (`lossRecoveryPriceByEpoch[lossEpoch]`), so users are also free to stack new requests while their haircut receipt is invisible. [5](#0-4) 
- Because the haircut path returns 0, `_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]` in full via `_transferFundedClaim` [6](#0-5) , while only `_amount < pendingBasis` was ever transferred in. `pendingWithdraws` was already zeroed, so there is no solvency check left.

### Impact Explanation
Any unprivileged withdrawer who claimed early after a `stopEpochWithDuration`-style partial funding receives their unhaircutted amount, stealing the loss share that should have been socialized; once the funded balance is exhausted, remaining claimants' `safeTransfer` reverts — permanent loss for late claimants / direct theft for early ones. Loss magnitude equals `pendingBasis - _amount` (the haircut) plus freezing of the residual unpaid receipts.

### Likelihood Explanation
Requires only the ordinary loss-adjusted funding path (borrower repays less than `pendingWithdraws`) with honest manager/borrower sequencing; every claim thereafter misreads the uninitialized epoch slot. Caveat: if `collectWithdrawFunds` is invoked before the epoch-number-bumping deposit in the same `stopEpoch`, the key would match and this collapses — the PoC must confirm the call order in `IdleCDOEpochVariant.stopEpoch`.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the epoch in which the receipts were requested (the pre-increment epoch) rather than the live `epochNumber` — e.g., capture `epochNumber` into a `pendingEpoch` at `requestWithdraw`/`startEpoch` time, or pass the request epoch from the CDO. Alternatively, persist per-epoch pending basis (`pendingWithdrawsByEpoch`) so the claim path cannot fall through to par payout when the haircut entry is absent.
