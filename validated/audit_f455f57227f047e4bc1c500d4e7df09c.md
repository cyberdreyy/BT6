### Title
Multi-epoch withdraw receipts escape `stopEpochWithDuration` haircut — stale `lastWithdrawRequest` pays pre-loss receipts at par - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The vault tracks a user's pending withdraw receipt ownership with a single slot, `lastWithdrawRequest[user]` — the epoch of the *latest* request. When `collectWithdrawFunds` applies a stop-epoch loss, `lossRecoveryPriceByEpoch[epochNumber]` haircuts the entire aggregate `pendingWithdraws`, which includes older, still-unclaimed receipts from earlier epochs. On claim, only the latest-epoch receipt is paid at the haircut via `_claimLossAdjustedWithdrawRequest`; older receipts fall through to `_claimFundedWithdrawRequest` and are paid **at par**, even though their share of funding was haircut. This drains the funded pool and leaves later claimants unpayable.

### Finding Description
The kernel bug is state saved at the wrong point and restored without ownership tracking: a single saved pointer (`ctx->stable_pstate`) is restored on exit, trampling a newer override. The analog here is `lastWithdrawRequest[_user]`, which records only one epoch and drives which receipts get the loss haircut:

- `requestWithdraw` records basis per epoch (`withdrawsRequestsByEpoch[user][epoch]`) but overwrites `lastWithdrawRequest[user] = currentEpoch` (IdleCreditVault.sol:282). Multiple unclaimed receipts across epochs are explicitly supported ("if a user does not claim... he will have to wait for another epoch to claim both requests", line 323).
- `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * 1e18 / pendingBasis` where `pendingBasis` is the *aggregate* across all epochs (line 417), and stores it under `lossRecoveryPriceByEpoch[epochNumber]` (line 421). Every pending receipt — including earlier-epoch ones — has its funding reduced by this ratio.
- `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` only looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` (lines 790-794), i.e. only the newest epoch's basis is haircut. `_clearWithdrawClaimForEpoch` then resets `lastWithdrawRequest` to 0 (line 835), and `_claimFundedWithdrawRequest` pays the remaining aggregate `withdrawsRequests[user]` at par (lines 338-349).
- The guard at lines 263-271 only blocks a *new* request when the *last* request epoch itself has a nonzero `lossRecoveryPriceByEpoch` — it does not prevent the configuration below, where the loss lands on a later epoch than the older receipt.

### Impact Explanation
Broken invariant: fair loss socialization / solvency of the funded-claims pool. An attacker overpays themselves by `oldBasis * (1 - lossRecoveryPrice)`, paid from underlying that accounting assumes is haircut. Since `collectWithdrawFunds` only pulled `pendingBasis - pendingLoss`, the pool is short by exactly that amount; honest users' `_transferFundedClaim` calls then revert on insufficient balance (or the guard at line 904) — permanent freezing of unclaimed funded yield for the last claimants, and direct theft for the attacker. Loss magnitude: up to `totalPreLossBasis * (1 - price)`; with a 50% haircut epoch the attacker captures half of their stale basis, stolen from other receipt holders.

### Likelihood Explanation
Requirements: (1) attacker is a KYC'd lender who requests withdraw in epoch N, lets it fund, and requests again in epoch N+M without claiming (explicitly supported UX); (2) epoch N+M ends via `stopEpochWithDuration` with `_lossAmount > 0` — an honest-manager action triggered by a real borrower shortfall, which is a normal operating mode for a credit vault. No privileged misbehavior needed. The attacker can also simply be one of many ordinary users; whoever holds the oldest unclaimed basis claims first and exits at par.

### Recommendation
Track haircut ownership per receipt, not per user: when `collectWithdrawFunds` records a loss price for an epoch, mark *every* still-pending epoch's receipts as loss-adjusted, or store per-(user, epoch) recovery prices and iterate all of the user's non-zero `withdrawsRequestsByEpoch`/`apr0Users` entries at claim time. Alternatively, revert in `requestWithdraw` whenever the user has *any* unclaimed receipt (not only when the last request epoch has a loss price), forcing claim-then-rerequest so no receipt spans a haircut boundary unaccounted.

### Proof of Concept
Foundry fork PoC (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleEpochReceiptEscapesLossHaircut() external {
    address attacker = makeAddr('attacker');
    address victim   = makeAddr('victim');
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
    _depositWithUser(victim,   10_000 * ONE_SCALE, true);

    // Epoch 1: both request withdraw; epoch ends fully funded, neither claims.
    cdoEpoch.requestWithdraw(0, address(AAtranche));           // test contract = victim path not needed
    vm.prank(attacker); /* via CDO */ ... // requestWithdraw for attacker & victim
    _startEpochAndCheckPrices(0);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);                 // funds pendingWithdraws at par

    // Epoch 2: attacker (and victim) request again WITHOUT claiming epoch-1 receipts.
    _startEpochAndCheckPrices(0);
    // attacker/victim call requestWithdraw again -> lastWithdrawRequest = epoch2
    // borrower funds only partially: loss on the aggregate pendingBasis
    deal(defaultUnderlying, borrower, fundedWithLoss);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, newDuration, lossAmount);
    // -> collectWithdrawFunds(amount < pendingBasis), lossRecoveryPriceByEpoch[epoch2] = p < 1e18

    // Attacker claims: epoch-2 basis paid at p, epoch-1 basis paid at PAR.
    vm.prank(attacker);
    uint256 got = cdoEpoch.claimWithdrawRequest();
    uint256 expected = e1Basis + e2Basis * p / 1e18;
    uint256 fairShare = (e1Basis + e2Basis) * p / 1e18; // what accounting funded
    assertGt(got, fairShare);                            // attacker steals e1Basis*(1-p)

    // Victim's claim (or last claimant) now reverts / underpays: pool is insolvent
    // by exactly the attacker's excess.
}
```

Key assertion: `underlyingToken.balanceOf(strategy)` after funding equals `pendingBasis - pendingLoss`, while the sum of all claimants' entitlements under the current logic is `sum(oldBasis) + sum(newBasis)*p/1e18 > funded`. The delta is stolen/locked value.
