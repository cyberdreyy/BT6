### Title
Delegator rewards are silently and permanently lost when a validator's vote account temporarily falls out of the VAT-filtered `RewardEpochDelegatedStakes` snapshot for an epoch it actually voted in - (File: runtime/src/inflation_rewards/points.rs)

### Summary
`calculate_alpenglow_points()` computes a stake's earned credits for the alpenglow reward epoch, but if the voter's total delegated stake cannot be found in the `RewardEpochDelegatedStakes` denominator map, it returns zero reward points while still force-advancing `credits_observed` past the earned credits. This is the same root-cause pattern as the Fei Flywheel "reactivated gauges" bug: a mismatch between the stored/snapshot state (`RewardEpochDelegatedStakes.delegated_stakes`, analogous to `gaugeCycle`) and the per-stake tracked state (`credits_observed`, analogous to `storedCycle`) causes rewards that were actually earned in a given period to be computed and then discarded instead of preserved for a later, correct payout.

### Finding Description
Alpenglow reward accounting works per-epoch: for `rewarded_epoch = E`, `AlpenglowEpochType::Alpenglow{ reward_epoch_delegated_stakes, .. }` carries a `delegated_stakes: HashMap<Pubkey, u64>` that gives, for each *vote account eligible for distribution*, the total effective stake used as the reward-sharing denominator.

Crucially, this map is **not** built from all vote accounts with delegated stake — it is built only from vote accounts that survive SIMD-0357 VAT filtering (`clone_and_filter_for_vat`, capped at `MAX_ALPENGLOW_VOTE_ACCOUNTS` and requiring a minimum lamport balance): [1](#0-0) [2](#0-1) 

`RewardEpochDelegatedStakes::set()` only copies over stakes for pubkeys present in `distribution_vote_accounts` (the filtered set), so a vote account that is momentarily filtered out for epoch `E` (e.g., its balance temporarily dips below `minimum_vote_account_balance_for_vat()`, or it ranks below the `MAX_ALPENGLOW_VOTE_ACCOUNTS` stake cutoff for exactly that epoch) will simply be absent from the `delegated_stakes` map for epoch `E`, **even if the vote account actually voted and accumulated credits in epoch `E`**.

When a delegator's stake is later processed for reward epoch `E`, `calculate_alpenglow_points()` first checks that the vote account's latest `epoch_credits` entry matches `reward_epoch_delegated_stakes.epoch` (i.e., the vote account did vote in the target epoch), computes the credits earned for that epoch, and only *then* looks up the stake-denominator: [3](#0-2) 

If the vote pubkey is missing from `reward_epoch_delegated_stakes.delegated_stakes` (the filtered-out case above), the function returns `Err` with `ag_points: 0` but `new_credits_observed` already advanced to `final_epoch_credits`, and sets `force_credits_update_with_skipped_reward: true`.

That error/flag is unwrapped in the caller and propagated up: [4](#0-3) 

In `calculate_stake_rewards()`, `force_credits_update_with_skipped_reward` short-circuits to `skipped_reward()`, i.e. **zero** `staker_rewards`/`voter_rewards` but the already-advanced `new_credits_observed`: [5](#0-4) 

Finally, `redeem_stake_rewards()` unconditionally commits this `new_credits_observed` into the stake account: [6](#0-5) 

Because `credits_observed` is monotonically advanced to cover epoch `E`'s credits, and `calc_earned_credits()` only ever looks at credits between `credits_observed` and the latest vote-account epoch-credits entry, epoch `E`'s earned credits can never be recovered in any subsequent epoch — they are permanently discarded, while the vote account's own commission/other-mechanism accounting is unaffected. This mirrors the reported FlywheelV2 issue exactly: state used to determine "did this period's rewards get counted" (`RewardEpochDelegatedStakes`/VAT filtering) can be transiently out of sync with the per-account tracking state (`credits_observed`), and the code path chosen on mismatch (`force_credits_update_with_skipped_reward = true`) advances the tracked state without paying the reward, rather than deferring/retrying.

### Impact Explanation
This causes a real loss of stake-inflation rewards for legitimate delegators/stakers, with no way to recover the lost value in later epochs (since `credits_observed` has already moved past the affected epoch). The trigger condition (a vote account dropping out of the VAT top-N or below the minimum balance for exactly one epoch, e.g., due to normal balance fluctuation from VAT burn, commission timing, or stake ranking near the cutoff) is a state transition an ordinary validator operator can hit without malicious intent, and affects all of that validator's delegators simultaneously for that epoch. This is a concrete, unauthorized loss of protocol-computed rewards (state mutation reducing entitled lamports) stemming from the reward-calculation path exercised on every epoch boundary for all banks.

### Likelihood Explanation
Likelihood is moderate: it requires a vote account to be present and voting during epoch `E` (so its `epoch_credits` last entry equals `E`) but excluded from the VAT-filtered snapshot that specific epoch (falling marginally below `minimum_vote_account_balance_for_vat()` or the stake-rank cutoff of `MAX_ALPENGLOW_VOTE_ACCOUNTS`). Given `minimum_vote_account_balance_for_vat()` incorporates per-epoch VAT burn and validators near the tail of the top-N set can shuffle in/out due to ordinary stake movement, this is plausible in production without any attacker action, and will recur every time such a borderline validator re-enters the set after being filtered.

### Recommendation
When a stake's vote account voted in the reward epoch but is not found in `RewardEpochDelegatedStakes.delegated_stakes` (filtered out of VAT distribution for that epoch only), do not force-advance `credits_observed` past that epoch's earned credits. Instead, either (a) leave `credits_observed` unchanged so the credits remain claimable once the vote account reappears in a future epoch's `delegated_stakes` snapshot (mirroring the Flywheel fix's "always include" approach), or (b) explicitly document/enforce that being VAT-filtered means being permanently excluded from historical credit accrual and reconcile this with the `<=`-style recommendation from the original report so that a subsequently-available `RewardEpochDelegatedStakes` entry for a prior epoch can still be used to compute the owed reward rather than silently zeroing it.

### Proof of Concept
The existing unit test already demonstrates the zeroing/mismatch behavior for the epoch-mismatch case (denominator epoch doesn't match credits epoch), confirming the code path and its `points=0` result while returning a `new_credits` value tied to the mismatch: [7](#0-6) 

To reproduce the VAT-filter variant end-to-end: construct `MAX_ALPENGLOW_VOTE_ACCOUNTS + 1` validators as in `test_alpenglow_reward_epoch_delegated_stakes_account_is_bounded()` [8](#0-7) , arrange for the lowest-staked validator to vote normally during epoch `E` (so its `epoch_credits` last entry is `E`) while its balance/stake keeps it just below the VAT cutoff for that specific epoch's `RewardEpochDelegatedStakes` snapshot, then advance the epoch and inspect the affected delegator's stake account: `credits_observed` will have advanced through epoch `E`'s credits while `inflation.stake_reward` for that epoch is `0`, and no later epoch recomputation restores the lost reward.

fn calculate_alpenglow_points(
    stake: &Stake,
    reward_epoch_credits: Option<(Epoch, u64, u64)>,
    stake_history: &StakeHistory,
    inflation_point_calc_tracer: Option<impl Fn(&InflationPointCalculationEvent)>,
    new_rate_activation_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
    reward_epoch_delegated_stakes: &RewardEpochDelegatedStakes,
) -> Result<(u128, u64), CalculatedStakePoints> {
    let Some((epoch, final_epoch_credits, initial_epoch_credits)) = reward_epoch_credits else {
        return Ok((0, stake.credits_observed));
    };
    if epoch != reward_epoch_delegated_stakes.epoch {
        // In this case, the vote account did not record any credits in this epoch
        // The latest entry is from a prior epoch - thus the delegation gets 0 rewards
        return Ok((0, stake.credits_observed));
    }

    let (earned_credits, new_credits_observed) = {
        let mut new_credits_observed = stake.credits_observed;
        let earned_credits = calc_earned_credits(
            stake,
            final_epoch_credits,
            initial_epoch_credits,
            &mut new_credits_observed,
        );
        (earned_credits, new_credits_observed)
    };

    let stake_amount = u128::from(delegation_effective_stake(
        &stake.delegation,
        epoch,
        stake_history,
        new_rate_activation_epoch,
        use_fixed_point_stake_math,
    ));

    let earned_points = if earned_credits == 0 || stake_amount == 0 {
        0
    } else {
        let Some(total_stake) = reward_epoch_delegated_stakes
            .delegated_stakes
            .get(&stake.delegation.voter_pubkey)
            .copied()
            .filter(|stake| *stake != 0)
        else {
            record_error(format!(
                "AG delegated stake denominator for vote_pubkey={} in epoch={} failed",
                stake.delegation.voter_pubkey, reward_epoch_delegated_stakes.epoch
            ));
            return Err(CalculatedStakePoints {
                tower_points: 0,
                ag_points: 0,
                new_credits_observed,
                force_credits_update_with_skipped_reward: true,
            });
        };
        earned_credits * stake_amount / total_stake as u128
    };

    fn test_alpenglow_reward_epoch_delegated_stakes_account_is_bounded() {
        let num_validators = crate::bank::MAX_ALPENGLOW_VOTE_ACCOUNTS + 1;
        let validator_keypairs = (0..num_validators)

            .last()

            .vote_keypair

            mut genesis_config, ..

        genesis_config.epoch_schedule = EpochSchedule::new(SLOTS_PER_EPOCH);
        let features_to_deactivate = crate::slot_params::slot_time_feature_ids().to_vec();
