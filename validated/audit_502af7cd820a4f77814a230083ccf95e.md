### Title
Unsanitized `AlternateKey` bypasses path sanitization when `FF_HASH_CACHE_KEYS` is enabled, enabling `path.Join` traversal in alternate cache URL construction - (File: `shells/abstract.go`)

### Summary
When `FF_HASH_CACHE_KEYS` is enabled, `newCacheConfig` disables the `cachekey.Sanitize` sanitizer entirely and computes `AlternateKey` as the raw, unsanitized, attacker-expanded `humanKey` rather than the sanitized/hashed value. This unsanitized key is passed directly into `getAlternateCacheDownloadURL`, which forwards it to `cache.GetAdapter` to build an object path, allowing path-traversal segments in a job-supplied `cache:key`/fallback key to escape the runner's `project/<id>/` object prefix.

### Finding Description
In `newCacheConfig` (`shells/abstract.go:133-208`), when `build.IsFeatureFlagOn(featureflags.HashCacheKeys)` is true: [1](#0-0) 
the `sanitizer` is replaced with an identity function (`return s, nil`), so `humanKey` becomes the raw, unsanitized `rawKey` — which is derived directly from `build.GetAllVariables().ExpandValue(userKey)`, i.e., the job's `cache:key`/`cache:key:prefix`/fallback keys, fully attacker-controlled via CI variables. [2](#0-1) 

`AlternateKey` is then computed via `cacheAlternateKey(humanKey, true)`, which for the FF-ON case returns `humanKey` itself — the unsanitized value: [3](#0-2) [4](#0-3) 

This `AlternateKey` flows into `addExtractCacheCommand`, which calls `getAlternateCacheDownloadURL(ctx, info.Build, cacheConfig.AlternateKey)`: [5](#0-4) 

`getAlternateCacheDownloadURL` passes this raw key straight into `cache.GetAdapter`, along with the trusted `build.JobInfo.ProjectID`, to build the object path/URL: [6](#0-5) 

The project ID segment (`project/<id>/`) itself is server-controlled and cannot be forged, but the *key* segment joined onto it is not sanitized in this code path when `FF_HASH_CACHE_KEYS` is on. If the underlying adapter constructs the object path with `path.Join("project/<id>", key)` (as referenced by the `alternateURLValid`/`HasPrefix` checks exercised in `shells/abstract_test.go`), `path.Clean` semantics of `path.Join` will collapse `../` segments in the key, allowing a crafted key such as `../<other-project-id>/<known-cache-key>` to resolve to an object path outside the caller's own project prefix — e.g., `project/<other-id>/<known-cache-key>` — while `HasPrefix(objectPath, "project/<own-id>/")` would then fail to hold (or would need to be explicitly checked and reject the request, which is not evidently done for the alternate-key path since the sanitizer step is skipped entirely for this branch).

In contrast, when `FF_HASH_CACHE_KEYS` is off, the primary/alternate keys go through `cachekey.Sanitize`, which is presumably designed to strip such traversal-enabling characters — this is the normal protection the audit references. The gap is specifically the `FF_HASH_CACHE_KEYS`-enabled branch, where sanitization is bypassed for the human-readable key that becomes `AlternateKey`.

### Impact Explanation
If exploitable end-to-end (i.e., if the cache adapter's object-path builder does not independently re-validate/clean the joined path against the project prefix), an attacker who can set `cache:key`, `cache:key:prefix`, or fallback cache keys in `.gitlab-ci.yml`/CI variables could cause the runner to construct an `--alternate-url`/`--alternate-gocloud-url` pointing at another project's cache object path. The job's own `cache-extractor` would then download and extract that blob into the attacker's job workspace — a cross-tenant cache-data exfiltration/read primitive, matching the scoped impact.

### Likelihood Explanation
Preconditions are low-privilege and fully attacker-reachable: any pipeline author can set `cache:key`/`cache:key:prefix` and multiple `fallback_keys`/`CACHE_FALLBACK_KEY` values via CI configuration, and `FF_HASH_CACHE_KEYS` must be enabled on the runner (a runner-level feature flag, not attacker-controlled, which somewhat limits exposure but does not require any admin/privileged action from the attacker themselves). Given the flag is enabled, the exploit path requires only crafting a key value that resolves outside the project prefix after `path.Join` cleaning, and guessing or knowing another project's numeric ID and an existing cache key/blob name there.

### Recommendation
Apply the same sanitization (or an equivalent path-traversal-safe validation) to `AlternateKey` regardless of `FF_HASH_CACHE_KEYS` state, since it is used as a raw path component for the alternate cache lookup even when the primary key is hashed. Additionally, the cache adapter's object-path construction should independently enforce that the final joined object path has the expected `project/<id>/` prefix (matching the `HasPrefix` invariant already tested in `shells/abstract_test.go`) and reject/skip generating the alternate URL if it does not, rather than relying solely on upstream sanitization.

### Proof of Concept
Go unit test in `shells/abstract_test.go` style:
```go
func TestGetAlternateCacheDownloadURL_RejectsTraversal(t *testing.T) {
    build := &common.Build{ /* enable FF_HASH_CACHE_KEYS, set JobInfo.ProjectID = 123 */ }
    build.Variables = common.JobVariables{
        {Key: "FF_HASH_CACHE_KEYS", Value: "true"},
    }
    build.JobInfo.ProjectID = 123

    cfg, _, err := newCacheConfig(build, "../456/known-cache-key")
    require.NoError(t, err)

    // AlternateKey should not contain raw traversal segments once fixed
    assert.NotContains(t, cfg.AlternateKey, "..")

    args, err := getAlternateCacheDownloadURL(context.Background(), build, cfg.AlternateKey)
    require.NoError(t, err)
    for _, a := range args {
        if strings.HasPrefix(a, "http") {
            u, _ := url.Parse(a)
            assert.True(t, strings.Contains(u.Path, "project/123/"),
                "alternate URL escaped own project prefix: %s", a)
            assert.False(t, strings.Contains(u.Path, "project/456/"),
                "alternate URL leaked into another project's namespace")
        }
    }
}
```
Expected (current/vulnerable) behavior: `cfg.AlternateKey` equals the raw `"../456/known-cache-key"` and the generated alternate URL's object path resolves under `project/456/...`, failing the prefix assertion — confirming the bug. Expected (fixed) behavior: sanitization removes/rejects the traversal segment or the adapter enforces the `project/123/` prefix, causing the assertions to pass.

func getAlternateCacheDownloadURL(ctx context.Context, build *common.Build, cacheKey string) ([]string, error) {
	// The alternate key was uploaded under the opposite FF setting, so its object path uses the opposite sharding scheme.
	alternateSharded := !build.IsFeatureFlagOn(featureflags.HashCacheKeys)
	adapter := cache.GetAdapter(build.Runner.Cache, build.GetBuildTimeout(), build.Runner.ShortDescription(), fmt.Sprintf("%d", build.JobInfo.ProjectID), cacheKey, alternateSharded)

	goCloudURL, err := adapter.GetGoCloudURL(ctx, false)
	if err != nil {
		return nil, err
	}
	if goCloudURL.URL != nil {
		return []string{"--alternate-gocloud-url", goCloudURL.URL.String()}, nil
	}

	if url := adapter.GetDownloadURL(ctx); url.URL != nil {
		args := []string{"--alternate-url", url.URL.String()}
		if headURL := adapter.GetHeadURL(ctx); headURL.URL != nil {
			args = append(args, "--alternate-head-url", headURL.URL.String())
		}
		return args, nil
	}

	return nil, nil
}
