### Title
Stale confirmations from removed multisig members are still counted toward the execution threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` purges only the requests that were *created* by the removed member, but never scrubs that member's `confirm()` votes from the `confirmations` sets of *other* still-pending requests. `confirm()` later counts `confirmations.len()` against `num_confirmations` with no re-validation that every entry in the set still corresponds to a live member. This breaks the binding: `confirmations counted == live members who confirmed`.

### Finding Description
`delete_member` only cleans up requests whose signer (`r.member`) equals the member being removed [1](#0-0) . It does not iterate `self.confirmations` to strip the deleted member's entry from confirmation sets of requests created by *other* members.

`confirm()` treats `self.confirmations.get(&request_id)` as the authoritative vote count and executes the request once `confirmations.len() as u32 + 1 >= self.num_confirmations`, without checking that each stored voter (`member.to_string()`) is still present in `self.members` [2](#0-1) .

Consequence: if member X confirms request R (created by member A) while still a member, and later X is removed from the multisig via a separate `DeleteMember` request, R's confirmation set still contains X's vote. A subsequent confirmation from any remaining member can push the count to `num_confirmations` and trigger `execute_request`, even though only `num_confirmations - 1` *currently valid* members actually approved it. This is the same class of defect flagged in the external report: state trusted for authorization (the confirmation) is not re-validated against who is currently entitled to grant it (the live member set) at the point of use.

### Impact Explanation
This crosses an authorization/threshold boundary explicitly called out as in-scope: "a multisig request executed below threshold" is listed as a Critical impact. A `Transfer`, `AddKey`/`AddMember` (privilege escalation), or `DeployContract` action can be executed with fewer live, currently-authorized confirmations than `num_confirmations` requires, because a removed member's stale vote is still counted.

### Likelihood Explanation
Likelihood is Medium: it requires a normal operational sequence (member removal happening while another request from a different signer is still pending with a confirmation from the member being removed) — no privileged/attacker-only precondition beyond the ordinary lifecycle of the multisig (members are added/removed periodically, e.g. offboarding). No malicious insider action is strictly required to reach the vulnerable state; it can occur purely from routine key rotation while unrelated requests are outstanding.

### Recommendation
When executing `DeleteMember`, iterate all pending requests' confirmation sets and remove the deleted member's entry (mirroring the existing removal of requests where `r.member == member`), and/or re-validate at `confirm()` time that every confirming member in `self.confirmations.get(&request_id)` still exists in `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, X}` and `num_confirmations = 3`.
2. Member A calls `add_request` for `Transfer{amount}` to `receiver_id` → request `R` (0 confirmations, A is implicit creator).
3. Member X calls `confirm(R)` → confirmations = `{X}` (1/3).
4. Separately, a `DeleteMember{member: X}` request is created and reaches 3/4 confirmations from A, B, C and executes, removing X from `self.members` — per `delete_member`, only requests where `r.member == X` are purged; `R` (created by A) is untouched, so its confirmations set still contains `X`.
5. Member B calls `confirm(R)` → confirmations = `{X, B}` (2/3, per stale count).
6. Member C calls `confirm(R)` → `confirmations.len() + 1 = 3 >= num_confirmations` → `execute_request` fires and the transfer executes, even though only B and C (2 of the 3 *current* members A, B, C) plus one stale vote from removed member X approved it — effectively executed below the true live-member threshold.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
