### Title
Stale Rejection Weight Never Reconciled When a Signer Flips to Acceptance — Corrupts Node-Side Vote Tally (`StackerDBListener`) - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
### Finding Description
The node-side `StackerDBListener` maintains a `BlockStatus` struct per proposed block with two independently-accumulated weight counters, `total_weight_approved` and `total_weight_rejected`, plus a shared `responded_signers: HashSet<u32>` used to prevent double-counting a signer's weight *within* one response type. [1](#0-0) 

For `BlockResponse::Accepted`, the gate that decides whether to add `signer_entry.weight` to `total_weight_approved` is `!block.gathered_signatures.contains_key(&slot_id)` — it checks only whether *this signer already signed*, never whether the same signer already contributed weight to `total_weight_rejected` via `responded_signers`.

For `BlockResponse::Rejected`, by contrast, the gate is `block.responded_signers.insert(slot_id)` (only tallies if the signer hasn't responded before at all): [2](#0-1) 

This is asymmetric: if a signer *rejects first* (adding weight to `total_weight_rejected` and inserting itself into `responded_signers`) and then legitimately *re-evaluates and accepts* the same block — a transition the signer protocol explicitly allows (`LocallyRejected --> LocallyAccepted : re-evaluated`, `should_reevaluate_reject_reason`) — the Accepted-branch check only inspects `gathered_signatures`, which does not yet contain this signer, so the weight is added to `total_weight_approved` as well. The stale weight in `total_weight_rejected` is never removed, unlike the signer's own local bookkeeping in `signerdb.rs::add_block_signature`, which explicitly deletes any prior rejection row for that signer before inserting a new signature: [3](#0-2) 

The result is that `total_weight_approved + total_weight_rejected` can exceed the true `total_weight`, breaking the disjoint-partition invariant that the coordinator's threshold math implicitly assumes.

### Impact Explanation
`SignerCoordinator::get_block_status` (used by the mining/coordinator loop) treats `total_weight_rejected` as authoritative when deciding to abandon a block proposal: [4](#0-3) 

Because a single signer's rejection weight can persist in `total_weight_rejected` after that same signer has switched to accepting the block (an event that requires no majority, no other signer's key, and no elevated access — only ordinary re-evaluation timing by one signer), the coordinator can compute `total_weight_rejected + weight_threshold > total_weight` and conclude the blocking minority (>30%) has been reached, causing it to return `NakamotoNodeError::SignersRejected` and abandon a block that in reality retains sufficient approving weight. This is a liveness wedge on the block-production/coordination path: valid, later-approved blocks can be discarded due to stale accounting that the codebase's own signer-local logic (in `signerdb.rs`) is careful to avoid, but the node-side coordinator tally is not.

### Likelihood Explanation
This only requires ordinary operation of a single non-Byzantine signer: reject a proposal (e.g., pending validation, timing checks) and subsequently re-evaluate and sign it once the concerning condition clears, which is an explicitly supported and even expected state transition (`LocallyRejected --> LocallyAccepted`). No majority collusion, no key compromise, and no auth-token access is needed, so the likelihood of triggering the stale-count condition during normal signer flip-flopping (e.g., around pre-commit/threshold races or reorg-permit timing) is non-trivial.

### Recommendation
In the `BlockResponse::Accepted` handling, before crediting `total_weight_approved`, check whether the signer had previously registered a rejection (e.g., track per-signer response type, or subtract the signer's weight from `total_weight_rejected` if it was previously counted there) so that a signer's weight is only ever attributed to one side of the vote at any time, mirroring the reconciliation `signerdb.rs::add_block_signature` already performs for the signer's own local database.

### Proof of Concept
1. Signer S (weight w) sends `BlockResponse::Rejected` for block B. `StackerDBListener` records: `responded_signers += {S}`, `total_weight_rejected += w` (stacks-node/src/nakamoto_node/stackerdb_listener.rs:515-519).
2. The condition that caused rejection clears (e.g., a competing conflict goes stale, `reorg_permit_stands`, etc.), and per the documented re-evaluation flow S transitions `LocallyRejected --> LocallyAccepted` and broadcasts `BlockResponse::Accepted` for the same B.
3. `StackerDBListener` processes the Accepted message: `gathered_signatures` does not yet contain S's slot, so `total_weight_approved += w` is applied (stacks-node/src/nakamoto_node/stackerdb_listener.rs:443-465). `total_weight_rejected` is never decremented.
4. Now `total_weight_approved + total_weight_rejected > total_weight` for this block, and the stale `total_weight_rejected` value can independently push `SignerCoordinator::get_block_status`'s rejection-threshold check (signer_coordinator.rs:509-519) over the blocking-minority line, causing the coordinator to abandon a block that a re-tally of live signer intent would show has enough real approving weight.
