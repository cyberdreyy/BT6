### Title
Builder pending withdrawals can commit an execution-payload amount larger than the debited builder balance, minting unbacked Gwei - ([File: specs/gloas/beacon-chain.md])

### Summary
In the Gloas fork, `get_builder_withdrawals` copies the stored `BuilderPendingWithdrawal.amount` verbatim into the `Withdrawal` object that becomes part of `state.payload_expected_withdrawals` (binding on the execution layer), while `apply_withdrawals` only debits the builder's on-chain balance by `min(withdrawal.amount, builder_balance)`. If a builder's committed pending-withdrawal total exceeds its current balance at settlement time, the execution layer will credit the `fee_recipient` the full, uncapped amount while the consensus layer only removes the smaller, capped amount from the builder's balance — creating Gwei that is not backed by any debited balance.

### Finding Description
`get_builder_withdrawals` builds the `Withdrawal` entries directly from the stored request amount without capping it to the builder's current balance: [1](#0-0) 

This is inconsistent with the sibling function for validator partial withdrawals, `get_pending_partial_withdrawals`, which caps the amount to the available balance *before* constructing the `Withdrawal` object: [2](#0-1) 

Later, `apply_withdrawals` performs the actual balance deduction for builders, but it silently caps the deduction to whatever balance remains: [3](#0-2) 

The amount that ends up in `state.payload_expected_withdrawals` (and therefore in the execution payload that the block commits to) is the **uncapped** `withdrawal.amount`, confirmed explicitly by the repository's own test: [4](#0-3) 

The queue-population path, `process_builder_pending_payments`, enqueues `payment.withdrawal` (a fixed amount recorded at bid time) into `builder_pending_withdrawals` for every slot whose weight reaches quorum, without re-checking the builder's *current* balance against the *cumulative* amount already queued for that builder: [5](#0-4) 

Because up to `SLOTS_PER_EPOCH` payments can be queued for the same builder (one bid per slot, each individually validated by `can_builder_cover_bid` against the balance *at bid time*, not against the sum of all payments still pending), the sum of `builder_pending_withdrawals` amounts for one builder can exceed the builder's actual balance by the time the withdrawals sweep processes them (further payments can also decrease the effective available balance in the interim). At settlement, `get_builder_withdrawals` still emits the full requested amount into the committed withdrawal, while `apply_withdrawals` only debits the actually-available (smaller) amount. The execution layer must honor the amount specified in the committed `Withdrawal` (that is what "the block committed to" means for withdrawals), so it will credit `fee_recipient` the full amount, exceeding what was actually removed from the builder's balance — Gwei paid to a recipient with no corresponding debit, breaking the Gwei conservation invariant that `apply_withdrawals`'s own comment on Capella/Gloas withdrawal semantics is trying to preserve.

### Impact Explanation
This breaks the equality "a Gwei created must correspond to a Gwei destroyed/debited somewhere in state." A builder (or any actor who can drive multiple same-slot bids for one builder across an epoch, each individually within `can_builder_cover_bid`'s check) can cause the protocol to commit, via the execution payload, to pay a `fee_recipient` more Gwei than is deducted from consensus-layer accounting. Per the scoring rubric, this is Critical: "Gwei created, destroyed or paid to a non-owner" / "a payload executed or paid that the block did not commit to" (here inverted: the block *does* commit to it, but the debit side of the ledger doesn't match), since it inflates supply without a corresponding backing balance.

### Likelihood Explanation
Likelihood is Low/Medium: it requires a builder to have multiple pending payments queued that in aggregate exceed its balance by the time the sweep settles them (e.g., several honest same-slot bids accepted across an epoch, each passing `can_builder_cover_bid` individually against a shrinking or stale balance view, or a builder exit/other balance-reducing event occurring between bid acceptance and settlement). This does not require a malicious peer/client bug — only ordinary protocol-permitted sequences of bids and settlement timing, which the repository's own edge-case tests (`test_builder_withdrawal_insufficient_balance`) demonstrate is a reachable and expected state.

### Recommendation
Cap the amount written into the `Withdrawal` object in `get_builder_withdrawals` to `min(withdrawal.amount, state.builders[builder_index].balance)` at construction time (mirroring `get_pending_partial_withdrawals`'s pattern), so the value committed into `payload_expected_withdrawals` can never exceed what `apply_withdrawals` will actually debit. Alternatively, validate cumulative outstanding `builder_pending_withdrawals` amounts against the builder's balance whenever `process_builder_pending_payments` enqueues a new withdrawal, rejecting/truncating queued amounts that would exceed the builder's current balance.

### Proof of Concept
1. Builder `B` submits payloads across multiple slots within the same epoch, each with a bid value that individually satisfies `can_builder_cover_bid` against `B`'s balance at that time.
2. `process_builder_pending_payments` queues each corresponding `BuilderPendingWithdrawal` (full requested amount) into `state.builder_pending_withdrawals` once quorum weight is reached for each slot — see [5](#0-4) . The sum of queued amounts for `B` now exceeds `B`'s actual balance.
3. During `process_withdrawals`, `get_builder_withdrawals` emits `Withdrawal(amount=withdrawal.amount)` for each queued entry unmodified — see [6](#0-5) . These withdrawals are committed into `state.payload_expected_withdrawals`, which the execution layer must honor by crediting `fee_recipient` those exact amounts.
4. `apply_withdrawals` deducts only `min(withdrawal.amount, builder_balance)` from `B`'s balance — see [7](#0-6) , capping the debit at zero once `B`'s balance is exhausted, while later queued withdrawals for `B` still list their full uncapped amount in the payload commitment.
5. The repository's own test `test_builder_withdrawal_insufficient_balance` ( [4](#0-3) ) confirms this exact mismatch for a single withdrawal: `withdrawal.amount` = 5 ETH (committed to the EL) vs. `builders[0].balance` deduction capped at 1 ETH — 4 ETH is credited to `fee_recipient` with no matching debit anywhere in state.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
