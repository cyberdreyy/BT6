### Title
`calculate_rewards` and exchange-rate preview overestimate actual SUI delivered by `request_withdraw_stake` due to intra-epoch `rewards_pool` depletion — (`crates/sui-framework/packages/sui-system/sources/staking_pool.move`)

---

### Summary

The Sui staking pool exposes `calculate_rewards` and the public `pool_token_exchange_rate_at_epoch` + `get_sui_amount` pair as the canonical way to preview how much SUI a `StakedSui` holder will receive on withdrawal. However, the actual withdrawal path (`request_withdraw_stake` → `withdraw_rewards`) silently caps the reward payout at the live `pool.rewards_pool.value()`, which can be materially lower than the preview value because earlier withdrawals in the same epoch drain the pool. The preview therefore overestimates the actual payout — the exact invariant violation described in M-6 for ERC-4626.

---

### Finding Description

**Preview path** — `calculate_rewards` (public(package), also reachable off-chain via the public exchange-rate getters):

```move
// staking_pool.move lines 680-702
public(package) fun calculate_rewards(pool: &StakingPool, staked_sui: &StakedSui, current_epoch: u64): u64 {
    let staked_amount = staked_sui.amount();
    let pool_token_withdraw_amount = {
        let exchange_rate_at_staking_epoch =
            pool.pool_token_exchange_rate_at_epoch(staked_sui.stake_activation_epoch);
        exchange_rate_at_staking_epoch.get_token_amount(staked_amount)
    };
    let new_epoch_exchange_rate = pool.pool_token_exchange_rate_at_epoch(current_epoch);
    let total_sui_withdraw_amount =
        new_epoch_exchange_rate.get_sui_amount(pool_token_withdraw_amount);
    let mut reward_withdraw_amount = if (total_sui_withdraw_amount >= staked_amount) {
        total_sui_withdraw_amount - staked_amount
    } else 0;
    reward_withdraw_amount = reward_withdraw_amount.min(pool.rewards_pool.value()); // ← snapshot at T1
    reward_withdraw_amount
}

**The broken invariant:**

Both paths apply `.min(pool.rewards_pool.value())`, but they read that value at different points in time:

| Step | Actor | Effect on `rewards_pool` |
|------|-------|--------------------------|
| T0 | Epoch boundary | `deposit_rewards` fills pool; exchange rate snapshot recorded |
| T1 | Staker A | Calls `calculate_rewards` → preview = **R** (capped at `rewards_pool` = P) |
| T2 | Staker B | Calls `request_withdraw_stake` → drains `rewards_pool` by D |
| T3 | Staker A | Calls `request_withdraw_stake` → actual payout = **min(R, P−D) < R** |

The exchange rate stored in `exchange_rates[epoch]` is set once at the epoch boundary by `process_pending_stakes_and_withdraws` and never updated intra-epoch:

```move
// staking_pool.move lines 355-370
public(package) fun process_pending_stakes_and_withdraws(pool: &mut StakingPool, ctx: &TxContext) {
    let new_epoch = ctx.epoch() + 1;
    pool.process_pending_stake_withdraw();
    pool.process_pending_stake();
    pool.exchange_rates.add(new_epoch, PoolTokenExchangeRate {
        sui_amount: pool.sui_balance,
        pool_token_amount: pool.pool_token_balance,
    });
    ...
}
``` [3](#0-2) 

Every call to `pool_token_exchange_rate_at_epoch(current_epoch)` during the epoch therefore returns the epoch-start snapshot, which reflects the full `rewards_pool` balance before any intra-epoch withdrawals. The `rewards_pool` itself is drained by each `withdraw_rewards` call, but the exchange rate never reflects that drain. The developers themselves flag this with the `TODO: FIGURE OUT EXACTLY WHY THIS CAN HAPPEN` comment, confirming the discrepancy is real and unresolved. [4](#0-3) 

The public getter `pool_token_exchange_rate_at_epoch` is part of the published API and is used by external integrators (liquid staking protocols, DeFi collateral vaults, the Rosetta adapter) to quote expected SUI output: [5](#0-4) 

The Rosetta adapter explicitly mirrors the on-chain exchange-rate walk to compute expected SUI amounts for FSS redemptions, and its own comment warns that a stale rate read can "silently violat[e] AtMost caps": [6](#0-5) 

---

### Impact Explanation

Any staker or external protocol that reads `pool_token_exchange_rate_at_epoch` + `get_sui_amount` (or calls `calculate_rewards`) to decide whether to withdraw, how much collateral to post, or whether a minimum-output guard is satisfied, will receive an optimistic figure. The actual `request_withdraw_stake` call in a later transaction silently delivers fewer rewards because `rewards_pool` has been partially drained by concurrent withdrawals in the same epoch. The shortfall is permanent for that epoch — the staker cannot recover the missing rewards after the epoch closes. This constitutes harmful smart-contract behavior with a direct, quantifiable SUI loss for the affected staker.

---

### Likelihood Explanation

The condition is triggered whenever two or more stakers withdraw in the same epoch from the same pool — an ordinary, high-frequency event on mainnet. No special privilege is required; any ordinary SUI holder with a `StakedSui` object can call `request_withdraw_stake` via the public entry point `sui_system::request_withdraw_stake`. The larger the pool and the more active the epoch, the larger the shortfall for later withdrawers.

---

### Recommendation

1. **Accounting fix**: Track `pending_rewards_withdrawn` intra-epoch alongside `pending_total_sui_withdraw`. Subtract it from the exchange-rate-derived reward estimate in `calculate_rewards` so the preview is always ≤ the actual payout.
2. **Alternatively**: Document explicitly that `calculate_rewards` and the exchange-rate getters return an upper bound that may not be fully realised within the same epoch, and that callers must re-read `rewards_pool.value()` at withdrawal time to get a tight bound.
3. **Resolve the TODO**: The `// TODO: FIGURE OUT EXACTLY WHY THIS CAN HAPPEN` comment in `withdraw_rewards` should be replaced with a precise invariant statement and a test that exercises the depletion scenario.

### Proof of Concept

```
Epoch E boundary:
  rewards_pool = 1_000 SUI
  exchange_rates[E] = { sui_balance: 10_000, pool_token_balance: 8_000 }

Staker A holds pool tokens worth 600 SUI total; principal = 500 SUI.
  calculate_rewards(A, epoch=E) →
      total_sui = get_sui_amount(pool_tokens_A) = 600
      reward = 600 - 500 = 100 SUI
      min(100, 1_000) = 100 SUI   ← preview

Staker B (large holder) calls request_withdraw_stake in the same epoch:
  withdraw_rewards drains rewards_pool by 950 SUI
  rewards_pool is now 50 SUI

Staker A calls request_withdraw_stake:
  withdraw_rewards:
      total_sui = 600, principal = 500, computed reward = 100
      min(100, 50) = 50 SUI   ← actual payout

Staker A receives 50 SUI in rewards instead of the previewed 100 SUI.
The 50 SUI shortfall is silently lost to Staker A for this epoch.
```
