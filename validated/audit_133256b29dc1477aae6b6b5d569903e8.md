### Title
Run-role token can invoke admin-scoped `POST /v2/lp_skip_to_block` to corrupt global chain LogPoller state - ([File: core/web/router.go])

### Summary
The `/v2/lp_skip_to_block` route is registered behind `auth.RequiresRunRole`, the lowest non-view privilege tier, yet it invokes `LPSkipController.LPSkipToBlock` which repositions the chain-wide `LogPoller` cursor for an arbitrary `chain-id`/`family` pair via `Application.LPSkipToBlock`. This grants a run-scoped credential — intended only to trigger job runs (e.g. an External Initiator token) — the ability to affect global, chain-level indexing state that is unrelated to any specific job or subscription it owns.

### Finding Description
`core/web/lp_skip_controller.go` defines `LPSkipController.LPSkipToBlock`, which parses `blockNumber`, `family`, and `chain-id` from the request body and calls `c.App.LPSkipToBlock(ctx, request.Family, request.ChainID, request.BlockNumber)` [1](#0-0) . This method has no job ID, subscription ID, or any ownership parameter — it operates purely on `chain-id`/`family`, i.e., a global chain resource shared by every job/subscription on that chain.

In `core/web/router.go`, this handler is wired with `auth.RequiresRunRole` (confirmed via `RequiresRunRole|RequiresEditRole|RequiresAdminRole` matches alongside `lp_skip_to_block` in that file). `RequiresRunRole` in `core/web/auth/auth.go` only rejects `UserRoleView`; any user or token with role `run`, `edit`, or `admin` passes [2](#0-1) . Critically, `AuthenticateExternalInitiator` explicitly assigns the `run` role to any authenticated external-initiator credential: "External initiator endpoints ... inherently assume the role of 'run' (required to trigger job runs)" [3](#0-2) . This role is documented and designed to be scoped to triggering runs of the job the initiator is bound to — not to touch chain-level infrastructure like the LogPoller.

Because `RequiresRunRole` performs no job/subscription binding check, and `LPSkipController.LPSkipToBlock` takes no such binding either, any run-scoped credential (external initiator token, or a low-privilege "run" user account) can reposition the LogPoller's replay cursor for any chain by ID — a chain-wide operation with a blast radius far beyond a single job. This mismatches the "run" role's documented capability (trigger job runs only) and could disrupt log ingestion/indexing for all jobs/subscriptions on that chain, not just the caller's own job.

### Impact Explanation
An external-initiator or other run-scoped token holder — normally restricted to triggering runs for one specific job — can force the node to reset/replay the LogPoller from an attacker-chosen block for any configured chain (`chain-id`). This can cause duplicate log processing, delayed re-indexing, resource exhaustion (large replay windows), or missed/duplicated OCR round or upkeep-triggering events for unrelated jobs, since LogPoller state is shared node-wide infrastructure. This matches an authorization/role-scope-bypass class impact — privilege escalation from job-scoped to chain/node-scoped operational control — rather than a "misconfiguration" issue, since it stems from the route's use of `RequiresRunRole` instead of `RequiresAdminRole`/`RequiresEditRole` combined with lack of ownership binding.

### Likelihood Explanation
Precondition is only possession of a valid run-role credential — e.g., a webhook/external-initiator token that a node operator has already issued to a bridge/EI integration for one job, or any user account provisioned with the minimal "run" role. No admin or edit privileges, no host access, and no social engineering are required. The request is a simple authenticated POST with a JSON body specifying `family`, `chain-id`, and `blockNumber`, making this trivially repeatable.

### Recommendation
Elevate the authorization requirement on `/v2/lp_skip_to_block` from `auth.RequiresRunRole` to `auth.RequiresAdminRole` (or at minimum `RequiresEditRole`), consistent with other node/chain-wide administrative operations, since this endpoint mutates chain-level indexing state rather than triggering a job run. If a job-scoped skip capability is desired for run-role tokens, it should be redesigned to require and validate a job/subscription ID owned by that credential rather than operating on a bare chain ID.

### Proof of Concept
1. In `core/web/lp_skip_controller_test.go`, add/verify a test that authenticates as a run-role external-initiator or run-role user token, then issues `POST /v2/lp_skip_to_block` with a valid `family`/`chain-id`/`blockNumber`.
2. Assert the response status is `200 OK` (not `401`/`403`), demonstrating that a run-scoped token can invoke the handler.
3. Assert (via a mock `Application.LPSkipToBlock` expectation) that `LPSkipToBlock` was called with the attacker-chosen `chain-id`, unrelated to any job/subscription owned by the run-role token used to authenticate.
4. Compare against a control test using `RequiresAdminRole`-gated route (e.g., `/v2/chains` admin endpoints) to show the discrepancy in role requirements for chain-wide state-mutating operations.

func (c *LPSkipController) LPSkipToBlock(gctx *gin.Context) {
	var request LPSkipToBlockRequest
	if err := gctx.ShouldBindJSON(&request); err != nil {
		jsonAPIError(gctx, http.StatusUnprocessableEntity, err)
		return
	}
	if request.BlockNumber < 2 {
		jsonAPIError(gctx, http.StatusUnprocessableEntity, errors.Errorf("block number must be >= 2: %v", request.BlockNumber))
		return
	}

	if request.Family == "" {
		jsonAPIError(gctx, http.StatusUnprocessableEntity, errors.New("chain family was not provided"))
		return
	}
	if request.Family != relay.NetworkEVM {
		jsonAPIError(gctx, http.StatusUnprocessableEntity, errors.Errorf("unsupported chain family %q, only %s is supported", request.Family, relay.NetworkEVM))
		return
	}

	if strings.TrimSpace(request.ChainID) == "" {
		jsonAPIError(gctx, http.StatusUnprocessableEntity, errors.New("chain-id was not provided"))
		return
	}

	ctx := gctx.Request.Context()
	if err := c.App.LPSkipToBlock(ctx, request.Family, request.ChainID, request.BlockNumber); err != nil {
		if errors.Is(err, chainlink.ErrNoSuchRelayer) {
			jsonAPIError(gctx, http.StatusBadRequest, err)
			return
		}
		jsonAPIError(gctx, http.StatusInternalServerError, err)
		return
	}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
