### Title
Builder payment can be misdirected: `process_execution_payload_bid` never verifies `bid.fee_recipient` matches the proposer's committed preference - ([File: specs/gloas/beacon-chain.md])

### Summary
The Gloas fork's builder-payment flow settles a builder's promised payment (`bid.value`) to whatever `ExecutionAddress` the *builder* wrote into `bid.fee_recipient`. The only place that checks this address against the proposer's own preference is a **gossip-layer, `IGNORE`-severity** rule, which is not part of state-transition validity and can be bypassed. The consensus state machine (`process_execution_payload_bid`, and the later settlement path through `apply_parent_execution_payload` / `process_builder_pending_payments` / `apply_withdrawals`) accepts and pays out any `fee_recipient` the builder signs into the bid, with no binding to the proposer's actual designated address.

### Finding Description
When a builder constructs a bid, the spec instructs it to set `bid.fee_recipient` to the proposer's preferred address, obtained from a `SignedProposerPreferences` message: [1](#0-0) 

However, this is a *builder-side convention*, not a cryptographically or consensus-enforced constraint. The actual state transition, `process_execution_payload_bid`, records the pending payment using `bid.fee_recipient` verbatim and never cross-checks it against any proposer-committed value: [2](#0-1) 

The only validation of `bid.fee_recipient` against the proposer's preference lives in the gossip validator, and it is explicitly an `IGNORE` (spam-control) condition rather than a `REJECT` (consensus-safety) condition: [3](#0-2) 

Because this check is only a network-propagation heuristic, it does not gate what a proposer may actually put into `block.body.signed_execution_payload_bid`, nor does it gate what `process_execution_payload_bid` will accept and settle. A proposer/relay pipeline that sources bids out-of-band (e.g., via a builder API/relay rather than strict gossip validation) or a client that doesn't faithfully enforce the `IGNORE` heuristic will happily include a bid whose `fee_recipient` differs from the proposer's real address. The state transition function has no equivalent check, so such a block is fully valid.

Once included, the mismatched `fee_recipient` propagates unchanged through the whole settlement pipeline: it is recorded in `BuilderPendingPayment.withdrawal.fee_recipient`, later moved into `state.builder_pending_withdrawals` once quorum weight is reached, and finally paid out via `apply_withdrawals` to that address - with `Gwei` value taken from the builder's balance: [4](#0-3) [5](#0-4) 

This is the same bug class as the referenced `LiquidityProviders.setLiquidityPool` report: a destination address for a committed payment can be set to a value that diverges from the actual entitled recipient, and the protocol faithfully executes the payment to the wrong address, with no on-chain enforcement tying the payment destination to the true owner of the funds.

### Impact Explanation
The equality broken is "a builder payment... paid to a non-owner": the `Gwei` amount `bid.value`, which the spec states "the builder will pay the proposer if the bid is accepted", ends up paid to an address of the builder's (or a colluding party's) choosing instead of the proposer's committed `fee_recipient`. This matches the explicitly listed High-impact category: "a builder payment or withdrawal misdirected, doubled or escaped." The proposer who accepted the bid (believing they'd receive `bid.value`) receives nothing, while the builder effectively pays itself (or an accomplice) instead of the block proposer it owed the funds to.

### Likelihood Explanation
Likelihood depends on whether validator/proposer software independently re-verifies `bid.fee_recipient == self_address` before including a bid in its own block, since the spec provides no consensus-level enforcement of this - only a best-effort gossip `IGNORE`. Any pipeline that accepts bids through a channel other than the exact gossip validator described (e.g., builder-relay integrations, local mempools, or a client that treats the check as advisory) is exposed. Because the check is explicitly non-`REJECT`, it is not treated as a safety-critical rule by the spec's own model, making this a documented gap rather than a deeply hidden edge case.

### Recommendation
Add a consensus-level (`REJECT`-equivalent) check in `process_execution_payload_bid` (or in block validity rules) that binds `bid.fee_recipient` to a value the proposer has actually committed to for that slot - e.g., by requiring the proposer to sign/commit their `fee_recipient` inside the block itself (similar to how other bid fields like `parent_block_root`/`prev_randao` are already bound to state), rather than relying solely on an off-chain, `IGNORE`-severity gossip heuristic that has no bearing on state-transition validity.

### Proof of Concept
1. Proposer `P` for slot `S` broadcasts `SignedProposerPreferences(fee_recipient=A, ...)`.
2. Builder `B` crafts `SignedExecutionPayloadBid` with `bid.value = V`, `bid.builder_index = B`, and `bid.fee_recipient = B_addr` (an address `B` controls), instead of `A`. All other bid fields (parent hash, slot, randao, signature, etc.) are valid per `process_execution_payload_bid`'s checks: [6](#0-5) .
3. This bid reaches `P` outside strict gossip validation (e.g., via a relay/builder API), or `P`'s client does not itself re-check `fee_recipient` before including the bid in its own block (nothing in `process_execution_payload_bid` requires it to).
4. `P` includes `signed_bid` in `block.body.signed_execution_payload_bid`; the block passes all state-transition checks in `process_execution_payload_bid`, recording `BuilderPendingPayment(withdrawal=BuilderPendingWithdrawal(fee_recipient=B_addr, amount=V, builder_index=B), proposer_index=P)`.
5. Once attesters reach quorum weight for this payment slot, `process_builder_pending_payments` moves the withdrawal into `state.builder_pending_withdrawals` unchanged (`fee_recipient=B_addr`) - as confirmed by the existing test showing the withdrawal's `fee_recipient` is taken directly from the payment record: [7](#0-6) .
6. `apply_withdrawals` eventually decreases `builder[B].balance` by `V` and credits `V` Gwei to `B_addr` - not to `A`, the proposer's actual designated address.

Result: `V` Gwei that the builder owed to proposer `P` is instead paid to an address `B` controls, with the beacon state faithfully executing this misdirected payment because no consensus rule ever compared `bid.fee_recipient` to the proposer's real preference.

**Note on confidence**: I could not find, within the indexed portion of `specs/gloas/validator.md` (block-production duties), an explicit `MUST` instruction requiring the proposer's own software to re-validate `bid.fee_recipient` before inclusion, beyond the informal gossip convention. It's possible reference client implementations perform this check as a local safety measure even though the spec doesn't mandate it at the state-transition level; if so, the practical exploitability depends on implementation choices outside the spec text, which is consistent with this being a spec-level gap rather than a fully self-contained on-chain exploit.

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

@with_gloas_and_later
@spec_state_test
def test_process_builder_pending_payments_equal_quorum(spec, state):
    """Test payment equal to quorum threshold - should be processed."""
    # Advance past genesis epochs
    next_epoch(spec, state)
    next_epoch(spec, state)

    builder_index = 0
    amount = spec.MIN_ACTIVATION_BALANCE
    quorum = spec.get_builder_payment_quorum_threshold(state)
    weight = quorum  # Equal to threshold
    fee_recipient = b"\x41" * 20

    # Add pending payment with weight equal to quorum
    payment = create_builder_pending_payment(spec, builder_index, amount, weight, fee_recipient)
    state.builder_pending_payments[0] = payment

    pre_builder_pending_withdrawals = len(state.builder_pending_withdrawals)

    yield from run_epoch_processing_with(spec, state, "process_builder_pending_payments")

    # Withdrawal should be added since weight must be >= quorum
    assert len(state.builder_pending_withdrawals) == pre_builder_pending_withdrawals + 1

    # Check the withdrawal details
    withdrawal = state.builder_pending_withdrawals[len(state.builder_pending_withdrawals) - 1]
    assert withdrawal.fee_recipient == fee_recipient
    assert withdrawal.amount == amount
    assert withdrawal.builder_index == builder_index
    # Payment should be rotated out
    assert state.builder_pending_payments[0].weight == 0
