### Title
Unprivileged lender can force an extra APR=0 epoch, blocking `stopEpoch` at any positive APR and stripping a full epoch of yield from all LPs - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` routes any withdraw made while `unscaledApr == 0` into the APR0 bucket (`apr0TotalPrincipal`) [1](#0-0) . `prepareStopEpochWithApr0`, called by the CDO inside `stopEpoch`, unconditionally reverts `NotAllowed` whenever `apr0TotalPrincipal != 0 && unscaledApr != 0` [2](#0-1) , and the bucket is only closed (set to 0) inside that same function [3](#0-2) . There is no user-facing cancel and no privileged escape: the only way to make `stopEpoch` succeed is to keep `unscaledApr` at 0 for one more epoch so the bucket finalizes.

### Finding Description
The MySQL CVE is a privileged-triggered crash/DoS plus unauthorized state modification; the credit-vault analog is a transaction-level revert (DoS) on the epoch state machine plus forced modification of the pool's APR.

Attack sequence:
1. Pool is running an epoch with `unscaledApr == 0` (e.g., borrower renegotiating, or right after `setAprs(0,0)`).
2. Attacker (any KYC-passing lender holding tranche tokens) calls `IdleCDOEpochVariant.requestWithdraw` for even a dust-sized amount. `IdleCreditVault.requestWithdraw` mints the receipt and calls `_requestWithdrawApr0`, which sets `apr0Users[user].principalEpoch = epochNumber` and adds the amount to `apr0TotalPrincipal` [4](#0-3) .
3. The honest manager later wants the next epoch to run at a positive APR and calls `setAprs`/`setAprsWithBuffer` with a nonzero rate, then `stopEpoch`.
4. `stopEpoch` → `prepareStopEpochWithApr0` hits `if (unscaledApr != 0) revert NotAllowed()` and reverts. Every subsequent `stopEpoch` at any positive APR reverts identically, because `apr0TotalPrincipal` can only be zeroed inside the reverting function itself [5](#0-4) .
5. The only recovery path is `setAprs(0, 0)` and one full additional epoch at 0% APR so the bucket clears — exactly what the attacker wanted.

The attacker can repeat this every time the pool is at APR=0, and can re-arm it at negligible cost (dust deposits + withdraw requests).

### Impact Explanation
- **Forced zero-interest epoch (integrity + availability analog of the CVE):** all honest LPs lose a full epoch of interest on the entire TVL. For a pool of size `T` and intended APR `a`, the quantified loss is `T * a * epochDuration / 365 days`, minus whatever override interest the manager optionally passes to `stopEpoch`. The attacker's cost is one dust withdraw request.
- **Temporary freezing of the epoch state machine:** `stopEpoch` cannot be executed at the intended APR; epoch rollover, withdraw-claim funding (`collectWithdrawFunds`), and deposit claims are all delayed until the manager yields to APR=0.
- Existing guards do not stop it: the revert is itself the (intended) guard for APR0-accounting consistency, but it creates a griefing lever because any single lender can keep `apr0TotalPrincipal` nonzero. The attacker needs no privileged role — only `isWalletAllowed`, the same KYC every lender passes.

### Likelihood Explanation
Low-to-medium effort for the attacker; requires the pool to be in an APR=0 configuration, which is a supported, documented mode (the whole `apr0Users`/`apr0RateByEpoch` machinery exists for it) [6](#0-5) . Once APR=0 occurs naturally (e.g., borrower paused borrowing), any withdraw requester — even a well-meaning one — arms the trap, and the manager cannot raise APR afterward. The bug triggers deterministically on the next `stopEpoch`.

### Recommendation
Do not revert in `prepareStopEpochWithApr0` when `unscaledApr != 0`. Instead, close the APR0 bucket gracefully: settle the open principal at `apr0RateByEpoch[epochNumber] = 0` (or at a rate computed from the override interest) and set `apr0TotalPrincipal = 0`, mirroring the `_apr0NetInterest == 0` path. Alternatively, allow `requestWithdraw` to be routed to the normal (`withdrawsRequests`) path — or let users cancel APR0 requests — so a nonzero `apr0TotalPrincipal` can never hold `stopEpoch` hostage.

### Proof of Concept
Foundry fork-style PoC (adapted to the existing test harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

// Assumes the standard fixtures in test/foundry/IdleCreditVault.t.sol:
// idleCDO/cdoEpoch, IdleCreditVault strategy, borrower, manager, owner, AAtranche.

function testApr0RequesterBlocksAprRaise() external {
    // honest LP deposits and attacker deposits dust
    uint256 victimAmount = 1_000_000 * ONE_SCALE;
    idleCDO.depositAA(victimAmount);
    _transferBurnedTrancheTokens(address(this), true);
    address attacker = makeAddr("attacker");
    _depositWithUser(attacker, 1e6, true); // 1 USDC dust

    // epoch 0 runs at APR 0
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _forceLastEpochAprToZero();

    // epoch 1 still APR 0: attacker requests a dust withdraw -> APR0 bucket
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // dust tranche amount
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // manager now wants next epoch at positive APR
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(5e18, 5e18);

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, type(uint120).max);

    // every stopEpoch at positive APR reverts -> forced extra APR0 epoch
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // only recovery: manager must run ANOTHER full epoch at APR = 0
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // succeeds, closes bucket
    assertEq(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);
    // Loss: victimAmount * intendedApr * epochDuration / 365 days of foregone yield.
}
```

Caveat: I was unable to re-read the exact `stopEpoch`/`startEpoch` bodies in `IdleCDOEpochVariant.sol` before this iteration ended, so the PoC assumes `stopEpoch` calls `prepareStopEpochWithApr0` unconditionally (consistent with the `_onlyIdleCDO` + unconditional `apr0TotalPrincipal` check in the vault). If the CDO skips the call unless `apr0TotalPrincipal != 0`, the finding is unchanged — the revert still fires whenever the attacker armed the bucket — but the PoC call site should be verified against `contracts/IdleCDOEpochVariant.sol` `stopEpoch`.

  function _requestWithdrawApr0(uint256 _amount, address _user) internal {
    // Settle any previous APR0 request first, then start/update current epoch bucket.
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    if (_apr0User.principal == 0) {
      _apr0User.principalEpoch = epochNumber;
    }
    _apr0User.principal += _amount;
    // Epoch-level APR0 principal used only to compute stopEpoch APR0 pro-rata interest.
    apr0TotalPrincipal += _amount;
  }
