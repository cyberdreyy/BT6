### Title
Stale confirmation from a deleted multisig member still counts toward execution threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` in multisig2/src/lib.rs:356-379 removes a member from `self.members` and purges only the requests that member originally *created* (`r.member == member`), but does not remove that member's `confirm()` votes recorded in the `confirmations` `LookupMap` for requests created by *other* members. Because `confirm()` (multisig2/src/lib.rs:294-315) counts confirmations purely by set length against `self.num_confirmations` without re-validating that every recorded confirmer is still `self.members.contains(...)`, a removed member's stale confirmation continues to count toward the K-of-N threshold.

### Finding Description
The invariant the contract is supposed to enforce is: `execute_request` fires only when the number of *live* member confirmations ≥ `num_confirmations`. Instead the code enforces: `confirmations.len() ≥ num_confirmations`, where `confirmations` is a `HashSet<String>` populated by `member.to_string()` at the time of `confirm()`.

`delete_member`:
```

    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
``` [1](#0-0) 
only matches on the *requester* field `r.member`, not on entries inside the `confirmations` sets of unrelated requests. So if member `B` confirms a request `X` created by member `A`, and is later removed via `DeleteMember`, `X`'s confirmation set still contains `B`'s serialized identity and it still counts in:
```

``` [2](#0-1) 
letting the request execute with fewer than `num_confirmations` *currently authorized* members.

### Impact Explanation
This crosses the threshold/authorization boundary explicitly called out as in-scope: "confirmations counted versus live members." A request that legitimately requires K live signers can be executed with K-1 live signers plus one stale confirmation from a removed member, i.e. `MultiSigRequest` (including `Transfer`, `AddKey`, `FunctionCall`, `AddMember`, further `DeleteMember`, etc.) is authorized below the configured threshold. This can lead to unauthorized movement of NEAR held by the multisig account, or unauthorized modification of the member/threshold set itself, which maps to the "Critical - a multisig request executed below threshold" impact category.

### Likelihood Explanation
No privileged actor, redeploy, or off-chain assumption is required beyond the normal multisig workflow: (1) member A creates request X, (2) member B (about to be removed) confirms X, (3) members vote to delete member B via a separate `DeleteMember` request that executes, (4) any other single live member confirms X, crossing the threshold with B's now-stale vote still counted. This is a straightforward sequencing available to any legitimate member acting alone in step 4, without needing collusion beyond normal multisig operation, so likelihood is not negligible.

### Recommendation
When removing a member in `delete_member`, iterate over all `confirmations` entries (not just requests originated by that member) and strip the removed member's serialized identity from every confirmation set, or alternatively re-validate at `confirm()`/execution time that all recorded confirmers in a request's confirmation set are still present in `self.members` before comparing the count against `self.num_confirmations`.

### Proof of Concept
1. Initialize multisig with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A.add_request_and_confirm(request_X)` → confirmations = `{A}`.
3. `B.confirm(request_X)` → confirmations = `{A, B}` (2/3, not yet executed).
4. Members submit and confirm a separate `DeleteMember { member: B }` request (requires 3/3 from `{A, C, D}` or any live trio not including B) → `delete_member` executes, removing B from `self.members`, but `request_X`'s confirmation set `{A, B}` is untouched since `r.member` for `request_X` is `A`, not `B`.
5. `C.confirm(request_X)` → `confirmations.len() as u32 + 1 == 3 >= num_confirmations (3)` → `execute_request` runs `request_X`, even though only `A` and `C` are currently live members who approved it (2 live confirmations, not 3). [3](#0-2) [4](#0-3)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));

        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );

            let request = self.remove_request(request_id);
