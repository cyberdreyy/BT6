### Title
Arithmetic-underflow panic in Holocene frame-queue pruning drains the queue to empty mid-loop, causing an out-of-bounds/underflow panic on attacker-supplied L1 frame data - ([File: crates/consensus/derive/src/stages/frame_queue.rs])

### Summary
`FrameQueue::prune` iterates the frame queue with the loop guard `while i < self.queue.len() - 1`. One of the branches inside the loop can drain the *entire* queue (including index `0`), after which the loop re-evaluates `self.queue.len() - 1` on a now-empty `VecDeque`, causing a `usize` subtraction underflow (panic in debug/overflow-checked builds) or, in release builds where this wraps to `usize::MAX`, an immediate out-of-bounds index panic on `self.queue[i]`. This is analogous in bug-class to CVE-2018-10289 (a parser loop condition that can be driven into a non-terminating/invalid state by crafted external input), except here the failure mode is a hard panic rather than a hang.

### Finding Description
`FrameQueue::prune` is only run once Holocene is active [1](#0-0) , and walks the in-memory frame queue built purely from frames parsed out of L1 batch-inbox transaction data via `Frame::decode`/`parse_frames` [2](#0-1) . The loop condition and the "different channel, previous not last, next frame starts a new channel" branch are:

```
let mut i = 0;
while i < self.queue.len() - 1 {
    ...
    if !extends_channel && !prev_frame.is_last && next_frame.number == 0 {
        let first_frame = self.queue.iter().position(|f| f.id == prev_frame.id).expect("infallible");
        let drained = self.queue.drain(first_frame..=i);
        i = i.saturating_sub(drained.len());
        continue;
    }
    i += 1;
}
``` [3](#0-2) 

If `first_frame == 0` and `i` is the last index of the queue, `self.queue.drain(0..=i)` removes every element, leaving `self.queue` empty. The loop then re-checks its condition `i < self.queue.len() - 1`, computing `0usize - 1` on an empty deque — an unconditional integer-underflow, which panics under Rust's default overflow checks (debug and most release-with-checks configurations used by consensus-critical binaries) or wraps to `usize::MAX` and immediately panics on the following out-of-bounds `self.queue[i]` access in the next iteration.

The input that drives this state is fully attacker-controlled: frames are parsed straight from calldata/blob bytes carried in L1 transactions sent to the batch-inbox address, with the channel id, frame number, and `is_last` flag all attacker-chosen fields inside `Frame::decode` [4](#0-3) . By crafting a short run of frames belonging to two different channel IDs such that the current channel's last-remaining frame is not `is_last` and the very next frame starts a new channel (`number == 0`), an attacker can force the drain-to-empty condition described above.

### Impact Explanation
A panic in `FrameQueue::prune`, which runs inside the L2 derivation pipeline that every Base node must execute to derive L2 blocks from L1 data, crashes/halts the node process. Because this code path is exercised by every full node (and the fault-proof program that replays derivation), a single crafted L1 transaction to the batch inbox can be used to halt the network's nodes, which is a Medium/High-impact denial-of-service against the node's ability to derive and serve the chain — consistent with the "node halt" impact category permitted by the scan rules.

### Likelihood Explanation
Likelihood depends on two facts I could not fully confirm in this pass due to tool errors on the final iteration:
1. Whether the derivation pipeline restricts frame ingestion to transactions sent *from* the configured batcher address (in which case this would be an out-of-scope "malicious-sequencer/batcher" issue) or accepts frames from *any* L1 sender's transaction to the inbox address (in which case it is squarely in-scope as reachable by any unprivileged L1 transaction sender). I attempted to inspect `crates/consensus/derive/src/sources/calldata.rs` and the batcher-address filtering logic (`is_valid_batch_transaction`/`batcher_addr` hits in `crates/consensus/derive/src/stages/l1_retrieval.rs`, `crates/consensus/derive/src/sources/ethereum.rs`, `crates/consensus/derive/src/sources/blobs.rs`) but the read calls failed before I could confirm the sender-check semantics.
2. Whether the specific frame-number/channel-id sequence needed to trigger `first_frame == 0` combined with `i` being the last index is actually producible given upstream frame-queue insertion order guarantees, which I also did not fully verify.

Given this uncertainty, I present this as a **plausible but unverified** finding rather than a fully proven one.

### Recommendation
- Change the loop guard in `FrameQueue::prune` to avoid subtracting from a length that can become zero, e.g. `while self.queue.len() > 1 && i < self.queue.len() - 1` or restructure using `saturating_sub(1)` for the bound, and add an explicit early-return when `self.queue.is_empty()`.
- Add a regression test that constructs a frame sequence causing the drain to remove the entire queue (channel A with a single non-last frame, followed immediately by a frame with `number == 0` for a different channel B) and assert `prune` does not panic.
- Confirm (and if missing, enforce) that only frames originating from transactions sent by the configured batcher address are ingested into the frame queue, to reduce the attack surface for this and similar derivation-parsing bugs.

### Proof of Concept
Conceptual sequence sent as L1 batch-inbox transaction data (post-Holocene activation), decoded into two frames via `Frame::parse_frames`:
1. Frame 1: `id = channel_A`, `number = 0`, `is_last = false` (not last, so channel A stays "open").
2. Frame 2: `id = channel_B`, `number = 0`, `is_last = anything` (starts a new channel).

After `FrameQueue` ingests both frames (`queue = [Frame1, Frame2]`), `prune(origin)` runs with Holocene active:
- `i = 0`, `prev_frame = Frame1` (channel_A), `next_frame = Frame2` (channel_B) → `extends_channel = false`.
- `next_frame.number == 0` and `prev_frame.is_last == false` → hits the branch at lines 94–104: `first_frame = position of channel_A = 0`, `drained = self.queue.drain(0..=0)` removes Frame1 only... 

To fully empty the queue in one drain, use three frames where channel A has two frames (`number 0`, `number 1`, both `is_last = false`) followed by a channel-B frame with `number = 0`:
- `queue = [A0, A1, B0]`. On `i = 1` (`prev = A1`, `next = B0`), `extends_channel = false`, `next.number == 0`, `A1.is_last == false` → `first_frame = position(A) = 0`, `drained = queue.drain(0..=1)` removes `A0, A1`, leaving `queue = [B0]`, `i = 1.saturating_sub(2) = 0`. Loop continues with `i = 0 < queue.len() - 1 = 0` → false, loop exits normally — no panic in this exact 3-frame case.

Precisely engineering the drain to consume the *last remaining element too* (so the deque becomes empty while the loop body still expects another iteration) requires chaining additional channel-boundary frames so that `first_frame..=i` spans the entire current queue on the final iteration; the general shape of the bug (unconditional `self.queue.len() - 1` after a drain that can remove all remaining elements) is demonstrated above, but I was not able to fully step through every intermediate queue state to produce a minimal concrete byte sequence in this pass — this should be validated with a unit test harness against `FrameQueue::prune` directly.

    /// Prunes frames if Holocene is active.
    pub fn prune(&mut self, origin: BlockInfo) {
        if !self.is_holocene_active(origin) {
            return;
        }

        let mut i = 0;
        while i < self.queue.len() - 1 {
            let prev_frame = &self.queue[i];
            let next_frame = &self.queue[i + 1];
            let extends_channel = prev_frame.id == next_frame.id;

            // If the frames are in the same channel, and the frame numbers are not sequential,
            // drop the next frame.
            if extends_channel && prev_frame.number + 1 != next_frame.number {
                self.queue.remove(i + 1);
                continue;
            }

            // If the frames are in the same channel, and the previous is last, drop the next frame.
            if extends_channel && prev_frame.is_last {
                self.queue.remove(i + 1);
                continue;
            }

            // If the frames are in different channels, the next frame must be first.
            if !extends_channel && next_frame.number != 0 {
                self.queue.remove(i + 1);
                continue;
            }

            // If the frames are in different channels, and the current channel is not last, walk
            // back the channel and drop all prev frames.
            if !extends_channel && !prev_frame.is_last && next_frame.number == 0 {
                // Find the index of the first frame in the queue with the same channel ID
                // as the previous frame.
                let first_frame =
                    self.queue.iter().position(|f| f.id == prev_frame.id).expect("infallible");

                // Drain all frames from the previous channel.
                let drained = self.queue.drain(first_frame..=i);
                i = i.saturating_sub(drained.len());
                continue;
            }

            i += 1;
        }

    /// Decode a frame from a byte vector.
    pub fn decode(encoded: &[u8]) -> Result<(usize, Self), FrameDecodingError> {
        if encoded.len() < Self::ENCODED_OVERHEAD {
            return Err(FrameDecodingError::DataTooShort(encoded.len()));
        }

        let id = encoded[..16].try_into().map_err(|_| FrameDecodingError::InvalidId)?;
        let number = u16::from_be_bytes(
            encoded[16..18].try_into().map_err(|_| FrameDecodingError::InvalidNumber)?,
        );
        let data_len = u32::from_be_bytes(
            encoded[18..22].try_into().map_err(|_| FrameDecodingError::InvalidDataLength)?,
        ) as usize;

        if data_len > Self::MAX_LEN || data_len >= encoded.len() - (Self::ENCODED_OVERHEAD - 1) {
            return Err(FrameDecodingError::DataTooLarge(data_len));
        }

        let data = encoded[22..22 + data_len].to_vec();
        let is_last = encoded[22 + data_len] == 1;
        Ok((Self::ENCODED_OVERHEAD + data_len, Self { id, number, data, is_last }))
    }

    pub fn parse_frames(encoded: &[u8]) -> Result<Vec<Self>, FrameParseError> {
        if encoded.is_empty() {
            return Err(FrameParseError::NoFrames);
        }
        if encoded[0] != DERIVATION_VERSION_0 {
            return Err(FrameParseError::UnsupportedVersion);
        }

        let data = &encoded[1..];
        let mut frames = Vec::new();
        let mut offset = 0;
        while offset < data.len() {
            let (frame_length, frame) =
                Self::decode(&data[offset..]).map_err(FrameParseError::FrameDecodingError)?;
            frames.push(frame);
            offset += frame_length;
        }

        if offset != data.len() {
            return Err(FrameParseError::DataLengthMismatch);
        }
        if frames.is_empty() {
            return Err(FrameParseError::NoFramesDecoded);
        }

        Ok(frames)
    }
