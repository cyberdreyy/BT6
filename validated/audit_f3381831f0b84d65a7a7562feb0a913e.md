### Title
DeterministicStateInit lacks the single-action gate that protects Transfer/CreateAccount, allowing an attacker to piggy-back `AddKey` (or `DeployContract`) in the same receipt that creates a not-yet-existing deterministic account - (File: `runtime/runtime/src/actions.rs`)

### Summary
`check_account_existence` explicitly exempts `Action::DeterministicStateInit` from the single-action / `implicit_account_creation_eligible` restriction that is enforced for `Action::Transfer` and `Action::CreateAccount`, and the surrounding comment states this is intentional "to allow optional init before other actions." This means a receipt of `[DeterministicStateInit{state_init}, AddKey{attacker_pubkey, full_access}]` targeting a fresh derived account id is not rejected the way the semantically analogous `[Transfer, AddKey]` batch is (proven blocked by `test_transfer_and_add_key_to_deterministic_account`), letting whoever submits the first receipt for a given `(code, data)` pair install an attacker-controlled full-access key atomically with account creation.

### Finding Description
`validate_deterministic_state_init` (`runtime/runtime/src/action_validation.rs:435-449`) only checks that `derive_near_deterministic_account_id(&action.state_init) == *receiver_id`; `validate_actions_with_mode` (`runtime/runtime/src/action_validation.rs:97-113`) only special-cases `DeleteAccount` (must be final) and `Delegate` (must be unique) — there is no rule limiting `DeterministicStateInitAction` to be the sole action in a receipt.

At execution time, `check_account_existence` (`runtime/runtime/src/actions.rs:787-855`) treats `Action::DeterministicStateInit` specially:
```
Action::DeterministicStateInit(_) => {
    // Existing and non existing is valid for DeterministicStateInit.
    // Does not exist => The account will be created by the action.
    // Does exist => Nothing happens but the receipt is not aborted to
    // allow optional init before other actions.
}
``` [1](#0-0) 
This is unconditional — unlike `Action::Transfer`, which routes to `check_transfer_to_nonexisting_account` and is gated by `implicit_account_creation_eligible = is_the_only_action && !is_refund` (`runtime/runtime/src/lib.rs:548-550`). That gate exists precisely to stop an attacker from combining account creation with `AddKey`/`DeployContract` in the same receipt (documented for `CreateAccount` at `runtime/runtime/src/actions.rs:802-816`: "you should not be able to add another access key to the account in the same transaction... Otherwise you can hijack an account").

The test suite explicitly proves this protection exists for the `Transfer` path (`test_transfer_and_add_key_to_deterministic_account`, `test-loop-tests/src/tests/deterministic_account_id.rs:511-545`) and even for `Transfer`+`DeterministicStateInit` combos (`test_transfer_and_state_init_to_deterministic_account`, lines 591-624) and `Transfer`+`DeployContract` (lines 553-585) — all fail with `AccountDoesNotExist` because `Transfer` (the account-creating action in those receipts) is not the sole action. However, there is no equivalent test where `DeterministicStateInit` is the *first, account-creating* action followed by `AddKey` or `DeployContract` in the same receipt. Given the explicit "allow optional init before other actions" comment and the absence of any single-action gate for `DeterministicStateInit`, the second action (`AddKey`) would see `account.is_some()` (created by the first action in the same `apply_actions` loop) and pass `check_account_existence` unconditionally, regardless of receipt action count.

Because `derive_near_deterministic_account_id` is a pure function of `(code, data)`, any party who can predict/observe the intended `(code, data)` pair for a not-yet-created deterministic account (e.g., a sharded-contract instance keyed by a target user's account id, as used in `sharded_contract_data(user_to_onboard)` in the same test file) can race to submit `[DeterministicStateInit{same code/data}, AddKey{attacker_key, full_access}]` first, deploying the exact intended code but simultaneously installing an attacker-owned full-access key on the account before the legitimate flow (which may rely on the "code-only, no owner key" security model of NEP-616 sharded contracts) ever runs.

### Impact Explanation
This is an authorization-escalation bug: it lets an unprivileged attacker obtain a full-access key on a deterministic account whose entire security model (per NEP-616) is supposed to be "identity/ownership determined solely by code+data, no access key." A full-access key lets the attacker bypass all contract-level ownership checks and directly issue `Transfer` (drain funds sent to the account), `DeployContract` (replace the code), or `DeleteAccount` (steal balance to a beneficiary) — i.e., theft of any funds subsequently sent to that deterministic account. This falls under "authorization escalation across accounts" / "unauthorized transaction" per the bounty scope.

### Likelihood Explanation
Preconditions: attacker must know/guess the `(code, data)` pair the legitimate party intends to use (often predictable/public, e.g. based on a target account id as in `sharded_contract_data`), and must be first to submit a receipt for that not-yet-existing derived id. Cost is a normal transaction fee; no special privileges are needed — any funded account can sign and submit `[DeterministicStateInit, AddKey]`. This is fully repeatable for any deterministic account whose `(code, data)` becomes known before initialization. Note: I was not able to trace `check_actor_permissions` or the `DeterministicStateInit` action handler implementation directly (index limits truncated some files), so the exact permission-model chain that lets the second action act on behalf of the newly-created account is inferred from the analogous `CreateAccount` pattern and the explicit "allow optional init before other actions" comment rather than fully verified line-by-line.

### Recommendation
Apply the same single-action restriction used for `Transfer`/`CreateAccount` when `DeterministicStateInit` is the action that actually creates the account (i.e., when `account.is_none()` prior to the action): require `implicit_account_creation_eligible` (or an equivalent "is the only action, or all remaining actions are also `DeterministicStateInit`/idempotent" rule) before allowing subsequent state-mutating actions (`AddKey`, `DeployContract`, `Stake`, etc.) in the same receipt as the creating `DeterministicStateInit`. Only allow additional actions in the same receipt if the account already existed prior to the receipt (the "lazy re-init" case), not on first creation.

### Proof of Concept
Add a test parallel to `test_transfer_and_add_key_to_deterministic_account` in `test-loop-tests/src/tests/deterministic_account_id.rs`:
1. Derive a fresh deterministic account id from `(global_contract_code, data)` that has never been created.
2. Build `SignedTransaction::from_actions` with `receiver = det_account` and actions `[Action::DeterministicStateInit(state_init), Action::AddKey(attacker_pubkey, AccessKey::full_access())]`, signed by an unrelated attacker account.
3. Execute via `env.try_execute_tx(tx)` and assert on the outcome:
   - Expected (if vulnerable): `FinalExecutionStatus::SuccessValue`, and a subsequent query shows `det_account` now has `attacker_pubkey` as a full-access key.
   - Expected (if fixed): failure analogous to the `Transfer`+`AddKey` case, e.g. `ActionErrorKind::AccountDoesNotExist` or a new dedicated error at index 1, blocking the `AddKey` from ever executing atomically with creation. [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

pub(crate) fn check_account_existence(
    action: &Action,
    account: &Option<Account>,
    account_id: &AccountId,
    config: &RuntimeConfig,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    match action {
        Action::CreateAccount(_) => {
            if account.is_some() {
                return Err(ActionErrorKind::AccountAlreadyExists {
                    account_id: account_id.clone(),
                }
                .into());
            } else {
                if account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts) {
                    // If the account doesn't exist and it's implicit, then you
                    // should only be able to create it using single transfer action.
                    // Because you should not be able to add another access key to the account in
                    // the same transaction.
                    // Otherwise you can hijack an account without having the private key for the
                    // public key. We've decided to make it an invalid transaction to have any other
                    // actions on the implicit hex accounts.
                    // The easiest way is to reject the `CreateAccount` action.
                    // See https://github.com/nearprotocol/NEPs/pull/71
                    return Err(ActionErrorKind::OnlyImplicitAccountCreationAllowed {
                        account_id: account_id.clone(),
                    }
                    .into());
                }
            }
        }
        Action::Transfer(_) => {
            if account.is_none() {
                return check_transfer_to_nonexisting_account(
                    config,
                    account_id,
                    implicit_account_creation_eligible,
                );
            }
        }
        Action::DeterministicStateInit(_) => {
            // Existing and non existing is valid for DeterministicStateInit.
            // Does not exist => The account will be created by the action.
            // Does exist => Nothing happens but the receipt is not aborted to
            // allow optional init before other actions.
        }
        Action::DeployContract(_)
        | Action::FunctionCall(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeleteAccount(_)
        | Action::Delegate(_)
        | Action::DelegateV2(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::TransferToGasKey(_)
        | Action::WithdrawFromGasKey(_) => {
            if account.is_none() {
                return Err(ActionErrorKind::AccountDoesNotExist {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
    };
    Ok(())
}

/// Try to do Transfer and AddKey in a single transaction targeting a
/// deterministic account. A single Transfer can create a deterministic
/// account, but multiple actions are disallowed.
/// It should not be possible to add an access key to a deterministic account this way, as it would
/// give the creator control over the account before StateInit.
#[test]
fn test_transfer_and_add_key_to_deterministic_account() {
    let mut env = TestEnv::setup(Balance::from_near(100));
    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    let data = empty();
    let (_state_init, det_account) = env.new_deterministic_account_with_data(data);

    let user_signer = create_user_test_signer(&env.user_account());
    let public_key = PublicKey::from_seed(KeyType::ED25519, "test");

    let tx = SignedTransaction::from_actions(
        env.next_nonce(),
        env.user_account(),
        det_account,
        &user_signer,
        vec![
            Action::Transfer(TransferAction { deposit: Balance::from_near(1) }),
            Action::AddKey(Box::new(AddKeyAction {
                public_key,
                access_key: AccessKey::full_access(),
            })),
        ],
        env.get_tx_block_hash(),
    );

    let outcome = env.try_execute_tx(tx).expect("should be able to send transaction");
    assert_matches!(
        outcome.status,
        FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
            kind: ActionErrorKind::AccountDoesNotExist { .. },
            index: Some(0)
        }))
    );
}
