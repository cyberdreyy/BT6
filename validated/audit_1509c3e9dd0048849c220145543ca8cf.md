### Title
Cross-user response hijacking via unchecked MessageId collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Finding Description
`HandleLegacyUserMessage` unconditionally stores the caller's callback into a shared map keyed only by `msg.Body.MessageId`, with no check for an existing in-flight entry: [1](#0-0) 

`msg.Body.MessageId` is fully attacker/user-controlled — `Message.Validate()` only enforces length and null-terminator constraints, never uniqueness or unpredictability: [2](#0-1) 

The MessageId is not derived from any secret; it is simply supplied by the client and bound into the signature over that client's own message. Nothing prevents two different signed requests (from the victim and from an unrelated attacker) from using the identical `MessageId` string. If an attacker submits a `web_api_trigger` request with the same `MessageId` as an in-flight victim request (racing before the DON responds), the second `HandleLegacyUserMessage` call at line 412 blindly overwrites `h.savedCallbacks[msg.Body.MessageId]`, replacing the victim's stored `Callback` with the attacker's.

When the DON later responds, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageId` and delivers the DON's response to whichever `Callback` is currently stored: [3](#0-2) 

Because the lookup/delete is keyed solely on `MessageId` with no binding to the original sender/session, the DON's response intended for the victim is delivered to the attacker's HTTP connection instead — the victim's original callback object is discarded and never invoked (it will simply be silently dropped/never called, appearing to the victim as a hung/no-response request), while the attacker receives the victim's capability output.

### Impact Explanation
This is a cross-user response confusion / theft of another subscriber's capability output. An attacker who wins the race receives another user's `web_api_trigger` response payload — which may contain secret-derived or user-specific external API output not intended for them — while the legitimate requester's connection never gets a response. This matches the "cross-user data exposure / broken isolation between tenants" bounty impact class.

### Likelihood Explanation
Exploitability depends entirely on the attacker's ability to predict or guess the victim's `MessageId` and win a race before the DON responds. If client-generated MessageIds are low-entropy, sequential, timestamp-based, or otherwise guessable (nothing in the code enforces high entropy), this is trivially exploitable by any unauthenticated/self-signed gateway client with no special privilege — they simply need to send their own signed message with a chosen `MessageId` and race the timing window between message submission and DON response, which can span the full node round-trip. The root cause (no uniqueness check on insert) is deterministic and always present; only the practicality of the race and MessageId prediction gates real-world likelihood.

### Recommendation
In `HandleLegacyUserMessage`, before inserting into `savedCallbacks`, check whether an entry already exists for that `MessageId` and reject the request (return an error response, e.g. `DuplicateMessageId`) instead of silently overwriting:
```go
h.mu.Lock()
if _, exists := h.savedCallbacks[msg.Body.MessageId]; exists {
    h.mu.Unlock()
    return callback.SendResponse(...duplicate MessageId error...)
}
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}
h.mu.Unlock()
```
Additionally, consider deriving the map key from a combination that includes the sender's authenticated address (`msg.Body.Sender`) plus `MessageId`, so collisions across different senders can never occur even if `MessageId` values coincide.

### Proof of Concept
Go handler-level test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler with a fake `DON` that just records `SendToNode` calls (does not respond immediately).
2. Create two mock `handlers.Callback` implementations, `victimCallback` and `attackerCallback`, each recording the `UserCallbackPayload` they receive via `SendResponse`.
3. Craft `victimMsg` with `Body.MessageId = "X"`, signed by victim's key, method `web_api_trigger`.
4. Craft `attackerMsg` with the same `Body.MessageId = "X"`, signed by attacker's key.
5. Call `h.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)`, then immediately `h.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)`.
6. Assert `h.savedCallbacks["X"]` now points to `attackerCallback`'s `Callback` (demonstrating overwrite) — or, after the fix, assert the second call returns a duplicate-MessageId error and `victimCallback` remains stored.
7. Simulate a DON node response via `h.HandleNodeMessage` with `MessageId = "X"`; assert (pre-fix) that `attackerCallback.SendResponse` is invoked with the response payload and `victimCallback.SendResponse` is never called — proving cross-user response hijack. Post-fix, assert the second request is rejected and `victimCallback` correctly receives the DON response.
