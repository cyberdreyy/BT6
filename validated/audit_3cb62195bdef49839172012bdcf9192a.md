## Analysis

The relevant analog is in `specs/gloas/beacon-chain.md`, in the builder-withdrawal path introduced for EIP-7732. It reproduces the exact bug class from the `Vault.addValue()` report: a value that is *committed for external payment* is taken from a source (`withdrawal.amount`, the requested amount) that is not reconciled with the actual internal balance available, while the internal ledger deduction is capped separately.

### Title
Builder withdrawal amount committed to the execution layer is not capped to the builder's actual balance — ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builder_withdrawals` writes the full **requested** `BuilderPendingWithdrawal.amount` into the `Withdrawal` object that becomes `state.payload_expected_withdrawals` (the amount the execution layer is bound to credit to `fee_recipient`), while `apply_withdrawals` only deducts `min(withdrawal.amount, builder_balance)` from `state.builders[builder_index].balance`. If a builder's CL-tracked balance is ever lower than the queued withdrawal amount when the withdrawal is finally processed, the two operations diverge: the EL pays the full amount, but the CL only removes the capped (smaller) amount.

### Finding Description
`get_builder_withdrawals` (specs/gloas/beacon-chain.md) builds the `Withdrawal` entirely from the queued `BuilderPendingWithdrawal`, with no balance check: [1](#0-0) 

That output feeds `get_expected_withdrawals` → `state.payload_expected_withdrawals`, which the execution layer is contractually required to honor for the corresponding slot: [2](#0-1) 

Meanwhile, `apply_withdrawals` deducts only up to the builder's *current* balance, silently saturating instead of asserting or reconciling with the amount already promised to the EL: [3](#0-2) 

This is structurally identical to `Vault.addValue()`: the code that determines "what to credit externally" (`withdrawal.amount`) and the code that determines "what was actually available/removed internally" (`min(withdrawal.amount, builder_balance)`) are not the same value, and nothing enforces that they must be equal.

The spec's own regression tests confirm this divergence is a real, reachable state rather than a theoretical impossibility: [4](#0-3) 

and the auto-generated I/O report for the function documents it as expected behavior: "`actual_amount = min(requested_amount, builder.balance)` (builder balance can go to zero)." [5](#0-4) 

A concrete path by which a builder's balance can legitimately fall below a previously-queued commitment is the "missed epoch" eviction/re-append path in `apply_parent_execution_payload`: when a pending payment's slot ages out of `builder_pending_payments` before its host block is confirmed, its withdrawal is appended directly to `builder_pending_withdrawals` using the stale `parent_bid.value`: [6](#0-5) 

Between the original bid's `can_builder_cover_bid` check (which validates against the balance and pending obligations known *at bid time*) and the eventual processing of this re-appended withdrawal (potentially several epochs later, after other bids/withdrawals for the same builder have been processed), the builder's balance can have moved independently of this specific obligation, since the obligation is off-ledger during the eviction gap (not present in `builder_pending_payments` nor yet in `builder_pending_withdrawals`) and thus not counted by subsequent `can_builder_cover_bid` checks for new bids. This lets a builder queue more total commitments than its balance can back by the time all of them are settled.

### Impact Explanation
When `state.builders[builder_index].balance` is less than the committed `BuilderPendingWithdrawal.amount` at settlement time:
- `payload_expected_withdrawals` commits the EL to credit `fee_recipient` with the full requested amount (Gwei paid out).
- `apply_withdrawals` only removes `min(amount, balance)` from the CL-tracked builder balance — the shortfall is never subtracted from anywhere.

This creates Gwei out of thin air on the EL side that has no corresponding CL-side backing — a direct violation of the "Gwei created ... or paid to a non-owner" invariant, matching the Critical/High impact bar (payment applied beyond what the block/state can actually back, net protocol-level ETH supply inflation, as the spec's own commentary on saturation elsewhere in this file acknowledges is a real risk: "any CL-side saturation creates a net supply inflation"). [7](#0-6) 

### Likelihood Explanation
The core mismatch (`get_builder_withdrawals` amount vs. `apply_withdrawals` capped deduction) is unconditional and always present in the code — no attacker action is required to introduce the discrepancy logic itself. What is uncertain (and I was unable to fully verify within the available tool budget) is whether `can_builder_cover_bid`'s accounting across all in-flight `builder_pending_payments`/`builder_pending_withdrawals` entries fully closes every timing window (in particular the payment-eviction/re-append race described above) such that a builder can never legitimately reach a state where committed pending-withdrawal amounts exceed its live balance. This should be verified by reviewing `can_builder_cover_bid` and the full epoch-boundary eviction logic for `builder_pending_payments` in `process_builder_pending_payments` before treating this as fully exploitable in isolation from that check.

### Recommendation
Either (a) cap `withdrawal.amount` to `min(withdrawal.amount, state.builders[builder_index].balance)` at the point `get_builder_withdrawals` constructs the `Withdrawal` object (so the EL-committed amount and the CL deduction are always identical, as is already done for validator partial withdrawals via `min(balance - MIN_ACTIVATION_BALANCE, withdrawal.amount)`), or (b) strengthen `can_builder_cover_bid`/the pending-payment eviction path so that the sum of all outstanding builder obligations (`builder_pending_payments` + `builder_pending_withdrawals`, including those mid-eviction) can never exceed `builder.balance` at any point, eliminating the possibility of the saturation branch in `apply_withdrawals` ever firing for a nonzero shortfall.

### Proof of Concept
The existing spec test already demonstrates the state-level mismatch directly: [8](#0-7) 
With `builder.balance = 1 ETH` and a queued `BuilderPendingWithdrawal.amount = 5 ETH`, after `process_withdrawals`: `payload_expected_withdrawals` contains a `Withdrawal` with `amount = 5 ETH` (paid to `fee_recipient` by the EL) while `builders[0].balance` only decreases to `0` (a 1 ETH deduction) — a 4 ETH shortfall that the EL will mint/pay without any corresponding CL-side backing.

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
