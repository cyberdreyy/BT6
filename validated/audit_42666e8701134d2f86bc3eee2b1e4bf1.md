### Title
Staking pool account-ID front-running lets an attacker seize a whitelisted pool with attacker-chosen parameters - ([File: staking-pool-factory/src/lib.rs], [File: whitelist/src/lib.rs])

### Summary
`whitelist::add_staking_pool` only verifies that the caller is a whitelisted factory; it never verifies who requested the specific `staking_pool_id` be created or with what parameters. Because `staking-pool-factory::create_staking_pool` derives the pool's account ID purely from a caller-supplied string (`format!("{}.{}", staking_pool_id, factory)`) with no binding to the predecessor account, an unprivileged attacker can front-run a victim's `create_staking_pool` transaction for the same `staking_pool_id`, claim that account name with attacker-chosen `owner_id`/`stake_public_key`/`reward_fee_fraction`, and have it automatically whitelisted — while the victim's own transaction simply fails and is refunded.

### Finding Description
The claimed binding is:
`is_whitelisted(pool_id) == true` ⟺ `pool_id was deployed with the parameters chosen by the party who originally requested that pool_id`.

What the code actually guarantees is only:
`is_whitelisted(pool_id) == true` ⟺ `pool_id has the factory's suffix AND whichever create_staking_pool(pool_id, …) call executed first for that id succeeded`.

Trace:
- `StakingPoolFactory::create_staking_pool` builds `staking_pool_account_id = format!("{}.{}", staking_pool_id, env::current_account_id())` from a free-form `staking_pool_id` string with no tie to `env::predecessor_account_id()`. [1](#0-0) 
- Uniqueness is enforced only via `self.staking_pool_account_ids.insert(&staking_pool_account_id)`, a first-come-first-served check with no ownership binding. [2](#0-1) 
- On success, the factory calls `ext_whitelist::add_staking_pool(staking_pool_account_id, …)` from its own callback `on_staking_pool_create`, with `owner_id`/`stake_public_key`/`reward_fee_fraction` being whatever the winning caller supplied. [3](#0-2) 
- `WhitelistContract::add_staking_pool` accepts any `staking_pool_account_id` string from a whitelisted factory predecessor — it has no knowledge of, and does not check, which end user originated the underlying `create_staking_pool` call. [4](#0-3) 

Exploit flow: attacker observes (or predicts) a pending `create_staking_pool("myorg", ownerA, keyA, feeA)` transaction from the intended owner A, and submits `create_staking_pool("myorg", attacker, keyAttacker, RewardFeeFraction{100,100})` one block earlier. Because insertion is first-come-first-served and unrelated to predecessor identity, the attacker's account `myorg.factory` is created, deployed with the legitimate `staking_pool.wasm`, and whitelisted — indistinguishable from a "real" pool to any consumer that only checks `is_whitelisted`. A's later identical call panics on `"The staking pool account ID already exists"`, and A's deposit is refunded, but A never gets to create `myorg.factory` at all. Any lockup owner or delegator who was told (or assumes) that `myorg.factory` belongs to organization A and calls `select_staking_pool("myorg.factory")` — which only checks `ext_whitelist::is_whitelisted` before trusting the pool — will delegate stake to the attacker-owned pool. [5](#0-4) [6](#0-5) 

None of the existing guards stop this: `assert_called_by_foundation` is irrelevant (the factory path is used), `is_valid_account_id` only validates syntax, and `is_promise_success`/`assert_self` in the callbacks only check that account creation succeeded, not who requested the name.

### Impact Explanation
Once whitelisted with attacker parameters, the pool is a spec-compliant `staking_pool` contract, so delegator principal remains individually withdrawable (unstake+withdraw). However, `reward_fee_fraction` (settable up to 100%) is attacker-controlled, and `internal_ping` routes that fraction of every epoch's rewards to the attacker as `owner_id` permanently. [7](#0-6)  This matches the Critical category "an account whitelisted ... with parameters its rightful creator never chose," since the whitelisted pool at the expected account ID is entirely attacker-parameterized, and any staking rewards accrued by mistaken delegators are permanently redirected to the attacker. This is repeatable against every future `create_staking_pool` call whose `staking_pool_id` an attacker can predict or observe in the mempool.

### Likelihood Explanation
The attacker needs only: (1) NEAR to cover `MIN_ATTACHED_BALANCE` (30 NEAR) for `create_staking_pool`, and (2) visibility of a pending `create_staking_pool` transaction (or a predictable/well-known `staking_pool_id`, e.g. an organization's own name) to front-run by one block. No privileged role, key compromise, or foundation cooperation is required — fully within the unprivileged attacker's stated capabilities (creating a staking pool via the public factory with chosen arguments).

### Recommendation
Bind the staking pool account ID (or at minimum the right to claim a given `staking_pool_id`) to the predecessor account, e.g. require `staking_pool_id` derivation or reservation to include/verify `env::predecessor_account_id()`, or require `owner_id == env::predecessor_account_id()` unless explicitly authorized, so a third party cannot squat a name with attacker-chosen owner/parameters. Alternatively, have `add_staking_pool`/consumers of `is_whitelisted` also verify `get_owner_id()` matches an expected identity before trusting a pool, rather than treating whitelisting alone as sufficient proof.

### Proof of Concept
Using `staking-pool-factory/tests/spec.rs` harness (`near-runtime-standalone`):
1. Setup factory + whitelist as in `setup_factory()`.
2. Attacker calls `create_staking_pool("myorg", attacker_id, attacker_key, {100,100})` with `MIN_ATTACHED_BALANCE`.
3. Assert `is_whitelisted("myorg.factory") == true` (whitelist side of the binding holds).
4. Assert `get_owner_id()` on `myorg.factory` returns `attacker_id`, not the intended owner (binding: "parameters its rightful creator never chose" — violated).
5. Victim then calls `create_staking_pool("myorg", victim_id, victim_key, {10,100})` with sufficient deposit; assert the call panics with `"The staking pool account ID already exists"` and victim's balance is refunded (no pool created for victim at that id).
6. Optionally simulate a delegator staking into `myorg.factory`, advance an epoch, call `ping`, and assert the reward share credited to `attacker_id`'s account grows per `internal_ping`'s owner-fee logic, demonstrating reward siphoning.
