### Title
Goroutine leak in custom executor `command.KillAndWait` path due to unbuffered `waitCh` when target process becomes unkillable (SIGSTOP/D-state) - ([File: executors/custom/command/command.go])

### Summary
`executors/custom/command/command.go` creates an **unbuffered** `chan error` (`waitCh`) and hands it to `process.NewOSKillWait().KillAndWait` (`helpers/process/killer.go`). If the target process cannot be reaped within `gracefulKillTimeout + forceKillTimeout` (e.g. it self-delivers `SIGSTOP` right before `ForceKill`'s `SIGKILL`, or is stuck in kernel D-state), `KillAndWait` returns a `KillProcessError` and `Run()` returns, but the `waitForCommand` goroutine is still blocked inside `cmd.Wait()`. If/when the OS process eventually actually exits (stop lifted, I/O completes), that goroutine tries `c.waitCh <- err` on the now-unread, unbuffered channel and blocks forever — a genuine, permanent goroutine leak.

### Finding Description
- `command.New` allocates `waitCh: make(chan error)` (unbuffered): [1](#0-0) 
- `Run()` starts `waitForCommand` in a goroutine and races it against `ctx.Done()`, delegating to `KillAndWait(c.cmd, c.waitCh)` on cancellation: [2](#0-1) 
- `waitForCommand` blocks on `c.cmd.Wait()` and then unconditionally does `c.waitCh <- err`: [3](#0-2) 
- `KillAndWait` performs at most two bounded waits (`gracefulKillTimeout`, then `forceKillTimeout`) on the same `waitCh` and, on double timeout, returns `&KillProcessError{...}` without ever consuming `waitCh` again: [4](#0-3) 
- `Terminate`/`ForceKill` just issue `SIGTERM`/`SIGKILL` via `syscall.Kill` to the process group; there is no verification the signal was actually delivered/acted upon: [5](#0-4) 

A job-controlled process (job script) can trivially make itself briefly unkillable: self-`SIGSTOP` right before/while being terminated. A stopped process does not process `SIGTERM` or `SIGKILL` until continued (`SIGCONT`) — `SIGKILL` normally kills even stopped processes, but the point in the exploit description is about a race window, and D-state (blocked in uninterruptible I/O, e.g. heavy NFS/disk I/O) is a legitimate way to delay signal delivery arbitrarily. In both cases `KillAndWait` can time out twice and return `KillProcessError` while the process/goroutine is still alive underneath.

Once `Run()` returns due to `KillProcessError`, nothing in `command.go` ever reads `c.waitCh` again. When the underlying process eventually does exit (D-state clears, or the process is later reaped/continued), `waitForCommand`'s blocking send `c.waitCh <- err` on the unbuffered channel has no receiver and blocks forever — the goroutine (and its stack, and the `os.Process`/`exec.Cmd` structures it references) is leaked permanently, not until the runner process exits.

Note: `executors/shell/shell.go` uses the same `KillAndWait` API but with a **buffered** `waitCh := make(chan error, 1)`, so the equivalent send in its wait-goroutine never blocks and the goroutine always terminates cleanly: [6](#0-5) . This is the correct pattern; the custom executor's `command.go` diverges from it.

### Impact Explanation
Each job that triggers this condition in the **custom executor** leaves one goroutine permanently blocked (until process manager restart), pinning the memory for that goroutine's stack and the referenced `exec.Cmd`/`os.Process`. Repeated across many jobs/pipelines this is a slow, unbounded memory/goroutine leak on the runner host, degrading it over time. However, contrary to the broader claim in the question, `Run()` itself returns as soon as `KillAndWait` returns (whether success or `KillProcessError`), so the executor's concurrency slot for that job **is** released promptly — this is a goroutine/memory leak, not a stuck concurrency-slot/capacity exhaustion issue. The scoped "blocked executor slots" impact is not substantiated by the code; only the goroutine-leak portion is.

### Likelihood Explanation
Requires the custom executor (custom driver script under attacker/job control that spawns children) and the ability to put a monitored process into D-state or self-SIGSTOP — both are things a normal, unprivileged job author can trigger from within their own job (heavy disk/NFS I/O, or a script that sends itself `SIGSTOP`). It is fully repeatable per job/pipeline, so an attacker (or accidental script) can accumulate leaked goroutines over many CI runs.

### Recommendation
Make `command.go`'s `waitCh` buffered (size 1), matching `shell.go`, so `waitForCommand`'s terminal send can never block regardless of whether `KillAndWait` already gave up:
```go
waitCh: make(chan error, 1),
```
This is a one-line, low-risk fix that eliminates the leak without changing `KillAndWait`'s external contract.

### Proof of Concept
Go unit test in `executors/custom/command` (or a small standalone repro):
1. Build a `Commander`/`exec.Cmd` wrapping a helper binary that, on receiving `SIGTERM`, ignores it, and on receiving `SIGKILL`, is guaranteed by test scaffolding to remain running long enough (simulate via a mock `Commander.Wait()` that blocks past both timeouts before returning).
2. Call `command.New(...).Run()` with a context that is canceled immediately, and tiny `gracefulKillTimeout`/`forceKillTimeout` (e.g. 10ms each) so `KillAndWait` returns `KillProcessError` quickly while the mock `Wait()` is still blocked.
3. Assert `Run()` returns `*process.KillProcessError`.
4. Record `runtime.NumGoroutine()` before step 2, then let the mock `Wait()` finally return (simulating the process exiting later) and re-check `runtime.NumGoroutine()`.
5. Expected (bug present): goroutine count does not return to baseline — the `waitForCommand` goroutine remains blocked on `c.waitCh <- err` forever.
6. Expected (after fix, buffered channel): goroutine count returns to baseline once the mock `Wait()` returns, proving the leak is closed.

func (c *command) waitForCommand() {
	err := c.cmd.Wait()

	eerr, ok := err.(*exec.ExitError)
	if ok {
		exitCode := getExitCode(eerr)
		switch {
		case exitCode == BuildFailureExitCode:
			err = c.parseBuildFailure(eerr)
		case exitCode != SystemFailureExitCode:
			err = &ErrUnknownFailure{Inner: eerr, ExitCode: exitCode}
		}
	}

	c.waitCh <- err
}

func (pk *unixKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGTERM)
	if err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}

func (pk *unixKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGKILL)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}
}
