### Title
Preregistration binding expiry reopens the exact deposit-hijack window it was designed to close, permanently misdirecting a validator's withdrawal credentials — ([File: specs/_features/eip8205/beacon-chain.md])

### Summary
EIP-8205's preregistration mechanism binds a `pubkey` to `withdrawal_credentials` before a validator's first deposit, specifically to stop a party who holds a validator's signing key (e.g. a delegated/liquid-staking node operator) from front-running the rightful depositor's deposit and stealing control of the withdrawal address. The binding, however, is enforced only while `state.slot < preregistration.expiry_slot` (`PREREGISTRATION_EXPIRY_SLOTS`, ≈262,144 slots). Once it silently expires, any holder of the private key for that `pubkey` can re-register a new, attacker-controlled binding for the *same* `pubkey`, permanently steer the eventual validator's withdrawal credentials to themselves, and cause the legitimate depositor's later, correctly-signed deposit to be silently discarded.

### Finding Description
`process_preregistration_request` only refuses to register/replace a binding when an **active** one already exists: [1](#0-0) 

Activity is purely a slot comparison with no renewal or grace mechanism: [2](#0-1) 

If the record is expired, `get_stored_preregistration_index` still finds it by `pubkey` alone, and the request handler **replaces it in place** with a brand-new binding: [3](#0-2) 

Because `is_valid_preregistration_signature` only proves possession of the `pubkey`'s private key (not "true ownership" in the delegated-staking threat model the EIP itself describes — an untrusted operator holding the key is exactly the attacker class this feature targets), the same key holder that the mechanism is meant to defend against can simply wait for the ~36-day window to lapse and re-bind the pubkey to withdrawal credentials of their choosing.

Once the attacker's binding is active, `process_deposit_request` enforces it against the *legitimate* depositor's later deposit: [4](#0-3) 

- If the rightful depositor's deposit carries the original (correct) `withdrawal_credentials`, it now mismatches the attacker's replacement binding, so the request returns early at line 440 and is **never appended to `pending_deposits`** — the already-locked EL-side ETH is destroyed (never credited to any validator, never refunded).
- If instead the attacker submits their own deposit request matching their own malicious binding, it passes the credential and signature checks, the stored preregistration is removed, and a new validator is created with `add_validator_to_registry` (via `apply_pending_deposit`) using the attacker's withdrawal credentials — permanently redirecting all future rewards and exit balance for that validator to the attacker.

The attacker's active malicious binding also blocks the true owner from correcting the situation: any preregistration attempt by the legitimate party is a no-op while the attacker's binding is active (line 391-392), so the true owner cannot re-claim the pubkey until the attacker's own binding expires — and the attacker can simply repeat the replacement forever.

### Impact Explanation
This breaks the equality the EIP itself claims to guarantee: "a preregistration binds a validator pubkey to withdrawal credentials … protecting delegated staking deployments against deposit front-running." Concretely:
- Gwei is destroyed: a correctly signed, legitimate deposit is discarded once the binding it should have matched has been silently swapped out.
- Gwei is paid to a non-owner: the validator that is ultimately created is permanently keyed to attacker-chosen withdrawal credentials, diverting all future withdrawals/rewards.
- A validator's identity/withdrawal path is mutated without the true depositor's authority, purely because of an unmonitored, unrenewable timeout — exactly the "Client ID"-style identity-hijack pattern in the source advisory, where an unauthenticated re-claim of a stale identifier lets a party seize a binding that should belong to someone else.

### Likelihood Explanation
The threat model the EIP text explicitly names (a delegated staking operator holding the signing key) already possesses everything needed to exploit this: knowledge of the pubkey, the private key to sign both preregistration and deposit messages, and the ability to observe `expiry_slot` (public state) and time a replacement transaction the moment the window lapses. No coalition, partition, or client bug is required — only patience for a fixed, on-chain-readable timeout and use of key material the operator is already assumed to hold. Long delegated-staking key-handoff or operational timelines (well beyond ~36 days) make the exploit window realistically reachable.

### Recommendation
Either make `PREREGISTRATION_EXPIRY_SLOTS` effectively permanent/renewable only by consuming (removing) the binding upon a matching deposit — never allowing a same-`pubkey` replacement once *any* binding (active or expired) has ever existed for that pubkey unless the replacement is signed in a way that also authenticates control transfer — or require that expired-but-previously-registered pubkeys can only be re-bound by a withdrawal_credentials value cryptographically tied to the original registrant (e.g., disallow silent replacement entirely once a validator's intended credentials have been announced, and instead fail closed rather than fail open on expiry).

### Proof of Concept
1. At slot `S`, the legitimate depositor's key custodian (or an operator with delegated custody) submits `PreregistrationRequest(pubkey=P, withdrawal_credentials=A, signature=sig_A)`. It is stored as `StoredPreregistration(P, A, expiry_slot=S+PREREGISTRATION_EXPIRY_SLOTS)` (`process_preregistration_request`, lines 416-427).
2. The actual deposit transaction for `P` is delayed past `expiry_slot` (e.g. legal/operational delay in a delegated-staking setup, or the operator simply withholds submission).
3. At slot `S' >= expiry_slot`, `is_active_preregistration` returns `False` (line 254), so `get_active_preregistration(state, P)` returns `None` (lines 281-291).
4. The operator (who has always held the private key for `P`) submits `PreregistrationRequest(pubkey=P, withdrawal_credentials=B, signature=sig_B)` where `B` is the operator's own address. The check at line 391-396 passes (no active binding, no validator, no pending deposit for `P`), the signature check at line 413 passes since the operator holds the key, and the stored record for `P` is replaced in place with `(P, B, expiry_slot=S'+PREREGISTRATION_EXPIRY_SLOTS)` (lines 421-424).
5. The legitimate depositor's deposit request `(pubkey=P, withdrawal_credentials=A, signature=sig_A, amount=X)` finally arrives. In `process_deposit_request`, `get_active_preregistration` now returns the attacker's binding `(P, B, ...)`; since `A != B`, the request returns at line 440 without ever appending to `state.pending_deposits` — the deposited `X` Gwei is never credited to any validator.
6. The operator submits their own deposit request `(pubkey=P, withdrawal_credentials=B, signature=sig_B)`, which matches the active binding, passes `is_valid_deposit_signature`, removes the stored preregistration, and is queued/applied via `apply_pending_deposit` → `add_validator_to_registry`, creating validator `P` with withdrawal credentials `B`. All future rewards and the eventual exit balance for `P` are now paid to the operator, not the original depositor.

def process_preregistration_request(state: BeaconState, request: PreregistrationRequest) -> None:
    pubkey = request.pubkey

    # An active binding for this pubkey makes the new request a no-op,
    # whether the duplicate is exact or conflicting
    if get_active_preregistration(state, pubkey) is not None:
        return

    # A pubkey with an existing validator cannot be preregistered
    if pubkey in [validator.pubkey for validator in state.validators]:
        return

def process_deposit_request(state: BeaconState, deposit_request: DepositRequest) -> None:
    # [New in EIP8205]
    preregistration = get_active_preregistration(state, deposit_request.pubkey)
    if preregistration is not None:
        if deposit_request.withdrawal_credentials != preregistration.withdrawal_credentials:
            return

        if not is_valid_deposit_signature(
            deposit_request.pubkey,
            deposit_request.withdrawal_credentials,
            deposit_request.amount,
            deposit_request.signature,
        ):
            return

        remove_stored_preregistration(state, deposit_request.pubkey)

    state.pending_deposits.append(
        PendingDeposit(
            pubkey=deposit_request.pubkey,
            withdrawal_credentials=deposit_request.withdrawal_credentials,
            amount=deposit_request.amount,
            signature=deposit_request.signature,
            slot=state.slot,
        )
    )
