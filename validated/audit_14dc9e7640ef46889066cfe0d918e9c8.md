This confirms the design: `refund_to` is set by the **creator of the promise/receipt itself** (via `promise_set_refund_to`), and can only be applied to a receipt the caller is currently constructing (`ctx.ext.set_refund_to(receipt_idx, ...)` at [1](#0-0)  and the host function itself at [2](#0-1) ). The deposit funding that receipt's actions is deducted from the *predecessor's own balance* (`ctx.result_state.deduct_balance(amount)` in [3](#0-2) ), i.e., the same account that is setting `refund_to`. There is no mechanism by which an unprivileged attacker can inject or override a `refund_to`/`balance_refund_receiver` on a receipt whose deposit was funded by a *different, unrelated* account (e.g., a victim's transaction or a relayed meta-transaction signer) — the predecessor of the receipt is fixed by `Receipt::from_tx` (bound to `tx_signer_id`, no `refund_to`, so `balance_refund_receiver()` falls back to `predecessor_id()`, per [4](#0-3)  and [5](#0-4) ), and for contract-generated receipts, `refund_to` can only be set on receipts the calling contract itself constructs and funds via its own balance.
