## Title
Rejoining validator set force-inactivates `pending_inactive` stake, corrupting `delegation_pool`'s observed-lockup-cycle accounting and stranding/misrouting delegator withdrawals - (File: `aptos-move/framework/aptos-framework/sources/stake.move`)

### Summary
`join_validator_set_internal` in `stake.move` contains logic that, when an operator rejoins the validator set for a pool whose lockup has already expired while `INACTIVE`, unconditionally merges the pool's entire `pending_inactive` balance into `inactive`: [1](#0-0) 
This directly contradicts an invariant that `delegation_pool.move` depends on and explicitly documents/tests: pending_inactive stake belonging to a validator that went inactive before its lockup expired must **not** be inactivated outside of the delegator's own withdrawal/synchronization flow, so that the observed lockup cycle (OLC) does not spuriously advance. [2](#0-1) [3](#0-2) 

### Finding Description
`delegation_pool.move` relies on `calculate_stake_pool_drift`/`synchronize_delegation_pool` to detect a "real" lockup expiration strictly by observing `inactive > pool.total_coins_inactive` on the underlying `StakePool`: [4](#0-3) 
The module's own test explicitly documents and asserts that when a validator goes `INACTIVE` before lockup expiry, and the lockup later expires while still inactive, the `pending_inactive` bucket on the `StakePool` stays untouched (`stake::assert_stake_pool(pool_address, ..., 0, 10200999997)` after expiry) and the delegation pool's OLC does **not** advance: [5](#0-4) 

However, `join_validator_set_internal` — callable by the operator via `join_validator_set` whenever the pool is `VALIDATOR_STATUS_INACTIVE` — silently forces this exact merge before that invariant can be preserved: [6](#0-5) 
Because `join_validator_set` requires only that the caller be `stake_pool.operator_address` (not the staker/owner, and independent of delegation-pool synchronization), the operator can trigger this state mutation on the raw `StakePool` resource used underneath a `delegation_pool` at any time after lockup expiry while inactive — a path that is not gated behind `synchronize_delegation_pool`.

Once this merge executes, the next `synchronize_delegation_pool` call will observe `inactive > pool.total_coins_inactive` and interpret it as a genuine lockup-cycle-ended event, advancing the OLC and closing out the current `pending_inactive` shares pool: [7](#0-6) 
This is the same code path shown in the "should not advance" test, but is now forced to run — mixing pending_inactive stake originating from what should still be the same OLC into an inactive-shares pool for a "new" OLC boundary. This breaks two documented invariants at once:
- "no delegator can have unlocking and/or unlocked stake ... in different OLCs" (line 43-45 of module doc), and
- "withdrawing pending_inactive stake ... does not inactivate any stake additional to the requested one to ensure OLC would not advance indefinitely" (line 47-48).

The forced OLC advance can happen for delegators who never triggered any of their own actions, at a time chosen by the operator (any time after lockup expiry while inactive, simply by calling `join_validator_set`), decoupled from the delegator's own accounting expectations built around `can_withdraw_pending_inactive`: [8](#0-7) 

### Impact Explanation
This corrupts share/OLC accounting in `delegation_pool`, a core mainnet-relevant delegation flow. Concretely:
- A delegator who queried `can_withdraw_pending_inactive` (expecting direct/simple withdrawal without an OLC transition) can have the pool's internal bookkeeping mutated underneath them by the operator's `join_validator_set` call, forcing an OLC advance they did not initiate and did not expect.
- The pending-withdrawal state semantics (`get_pending_withdrawal`, `pending_withdrawals` map keyed by OLC) can become inconsistent with the actual stake-pool state, since a `pending_inactive` bucket that should remain within the current OLC is retroactively treated as belonging to an ended lockup.
- This is a share-accounting corruption in a `pending_inactive`/lockup flow, fitting the required-impact class "Accounting across active, pending_active, pending_inactive, inactive, rewards, and commission state must preserve value and withdrawal rights," triggered by an operator (a role that must not be able to unilaterally corrupt delegator claim rights).

### Likelihood Explanation
The trigger requires only that: (1) a validator using a `delegation_pool`-owned `StakePool` leaves the validator set (a normal validator operation), (2) its lockup subsequently expires while inactive (a normal timing occurrence), and (3) the operator calls `join_validator_set` again (an entirely ordinary, expected operator action to resume validating). No privileged owner/governance access is needed beyond the operator role that is already assigned to run the pool's stake — the same role the gate says "must hold without assuming the attacker already has any of those roles" in terms of *delegator* claim rights. This makes the sequence very likely to occur incidentally (an operator simply restarting validation after downtime), not only via malicious intent.

### Recommendation
Do not perform the `pending_inactive → inactive` settlement inside `join_validator_set_internal`. Either:
1. Remove this merge entirely and rely on the standard invariant (already used by `delegation_pool` and reflected in `can_withdraw_pending_inactive`) that an inactive validator's `pending_inactive` stays untouched until either a genuine `end_epoch`/`update_stake_pool` cycle on an *active* validator, or the delegator withdraws through the "already-inactive-because-validator-is-inactive-and-lockup-expired" direct path; or
2. If settlement is required for correctness of voting-power computation at rejoin time, confirm `get_voting_power` does not need `pending_inactive` merged (it should already exclude `pending_inactive`) and instead simply skip the merge, relying on `locked_until_secs`/`increase_lockup` to naturally reset the lockup window without mutating `pending_inactive`/`inactive` balances.

### Proof of Concept
Not independently executable in this environment (no build/test harness access), but the trace is directly supported by existing code:
1. Operator runs a validator backing a `delegation_pool`; delegator unlocks stake, moving it to `pending_inactive`. [9](#0-8) 
2. Validator leaves the set (`leave_validator_set`) before lockup expiry; delegation_pool's test confirms `pending_inactive` remains un-inactivated once lockup subsequently expires while `INACTIVE`, and OLC does not advance: [10](#0-9) 
3. Operator calls `join_validator_set` (as they normally would to resume duties). Since `locked_until_secs > 0` and `now >= locked_until_secs`, the new merge branch executes and moves the entire `pending_inactive` coin balance into `inactive` on the underlying `StakePool`: [11](#0-10) 
4. Any subsequent `synchronize_delegation_pool` call now observes `inactive > pool.total_coins_inactive`, forcing `lockup_cycle_ended = true` and advancing the OLC: [12](#0-11) [7](#0-6) 

**Uncertainty**: I could not confirm the exact contents of `get_voting_power` (the grep for its definition timed out/returned no match within the remaining budget) to verify whether the intent behind this merge was to fix a genuine voting-power miscount, nor could I diff this function against the unmodified upstream aptos-core `stake.move` to confirm this block is a deliberate deviation versus pre-existing code. A Devin session with full repository/build access should verify (a) `get_voting_power`'s definition, (b) whether this merge block exists in upstream aptos-core, and (c) run `delegation_pool.move`'s existing test `test_operator_can_join_validator_set_after_lockup_expired` and the "no excess pending_inactive is inactivated" test after simulating a `join_validator_set` call in between, to confirm the OLC-advance regression empirically.

    fun calculate_stake_pool_drift(pool: &DelegationPool): (bool, u64, u64, u64, u64) {
        let (active, inactive, pending_active, pending_inactive) = stake::get_stake(get_pool_address(pool));
        assert!(
            inactive >= pool.total_coins_inactive,
            error::invalid_state(ESLASHED_INACTIVE_STAKE_ON_PAST_OLC)
        );
        // determine whether a new lockup cycle has been ended on the stake pool and
        // inactivated SOME `pending_inactive` stake which should stop earning rewards now,
        // thus requiring separation of the `pending_inactive` stake on current observed lockup
        // and the future one on the newly started lockup
        let lockup_cycle_ended = inactive > pool.total_coins_inactive;

        // actual coins on stake pool belonging to the active shares pool
        active += pending_active;
        // actual coins on stake pool belonging to the shares pool hosting `pending_inactive` stake
        // at current observed lockup cycle, either pending: `pending_inactive` or already inactivated:
        if (lockup_cycle_ended) {
            // `inactive` on stake pool = any previous `inactive` stake +
            // any previous `pending_inactive` stake and its rewards (both inactivated)
            pending_inactive = inactive - pool.total_coins_inactive
        };

        // on stake-management operations, total coins on the internal shares pools and individual
        // stakes on the stake pool are updated simultaneously, thus the only stakes becoming
        // unsynced are rewards and slashes routed exclusively to/out the stake pool

        // operator `active` rewards not persisted yet to the active shares pool
        let pool_active = pool.active_shares.total_coins();
        let commission_active = if (active > pool_active) {
            math64::mul_div(active - pool_active, pool.operator_commission_percentage, MAX_FEE)
        } else {
            // handle any slashing applied to `active` stake
            0
        };
        // operator `pending_inactive` rewards not persisted yet to the pending_inactive shares pool
        let pool_pending_inactive = pending_inactive_shares_pool(pool).total_coins();
        let commission_pending_inactive = if (pending_inactive > pool_pending_inactive) {
            math64::mul_div(
                pending_inactive - pool_pending_inactive,
                pool.operator_commission_percentage,
                MAX_FEE
            )
        } else {
            // handle any slashing applied to `pending_inactive` stake
            0
        };

        (lockup_cycle_ended, active, pending_inactive, commission_active, commission_pending_inactive)
    }
