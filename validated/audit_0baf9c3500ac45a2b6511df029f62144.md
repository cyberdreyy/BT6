### Title
Epoch-keyed recovery/rate lookups are miskeyed by the in-stopEpoch `epochNumber` increment, so loss-adjusted and APR0 receipts settle under the wrong epoch - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The external bug is an index mismatch: Nouns Builder schedules a founder's token under `baseTokenId = 100` but `_isForFounder` looks up `_tokenId % 100 = 0`, so the scheduled allocation is never matched and the founder is underpaid. The exact same "store under key K+1, read under key K" pattern exists in `IdleCreditVault`: `epochNumber` is incremented inside `deposit()` during `stopEpoch`, while receipts were keyed to the *pre-increment* epoch at request time. `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber]` and `prepareStopEpochWithApr0` writes `apr0RateByEpoch[epochNumber]`; claims later read both mappings through the request-time epoch stored in `lastWithdrawRequest`/`Apr0UserData.principalEpoch`. If the CDO's stopEpoch sequence calls the epoch-incrementing `deposit` before `collectWithdrawFunds`/`prepareStopEpochWithApr0` — which the code comment suggests ("deposit done on stopEpoch ... so we reset the counter") — the haircut price and APR0 rate are permanently stored under an epoch key no claim path will ever read.

### Finding Description
- `requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch]`, and `_requestWithdrawApr0` records `apr0User.principalEpoch = epochNumber` — all at request-time epoch N (`IdleCreditVault.sol:282,293,572`).
- `deposit()` increments `epochNumber` whenever `isEpochRunning()` is true, i.e. inside `stopEpoch` (`IdleCreditVault.sol:607-610`).
- `collectWithdrawFunds` then writes `lossRecoveryPriceByEpoch[epochNumber]` (`IdleCreditVault.sol:421`) — under N+1 if the deposit ran first — while `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. key N (`IdleCreditVault.sol:790-791`). The stored price is unreachable; the loss-adjusted claim returns 0 and the receipt falls through to `_claimFundedWithdrawRequest`, which pays the full un-haircutted `withdrawsRequests[_user]` while the strategy only received the haircutted amount — early claimants are overpaid and later claimants' funds are permanently frozen.
- The same miskey hits `prepareStopEpochWithApr0`: `apr0RateByEpoch[epochNumber]` (`IdleCreditVault.sol:537`) versus `_settleApr0` reading `apr0RateByEpoch[_reqEpoch]` (`IdleCreditVault.sol:558`), where `_reqEpoch` is the request-time epoch. APR0 withdrawers settle with `rate == 0` and receive zero of the interest that `stopEpoch` allocated to them and added to `pendingWithdraws`.
- The mirror guard in `requestWithdraw` (`IdleCreditVault.sol:262-271`) also reads `lossRecoveryPriceByEpoch[lastWithdrawRequest]`, so it likewise never sees the miskeyed price — the state is permanently inconsistent, not just skipped once.
- Caveat: validity hinges on CDO call ordering inside `IdleCDOEpochVariant.stopEpoch` / `stopEpochWithDuration` (epoch-incrementing `strategy.deposit` before `collectWithdrawFunds`/`prepareStopEpochWithApr0`). The `deposit()` comment states the increment happens "on stopEpoch (before setting the var to false)", consistent with that ordering, but I could not fully trace the CDO-side sequence within the available iterations.

### Impact Explanation
Direct theft/permanent freezing of unclaimed yield and principal: a stopEpoch that realizes a loss (or allocates APR0 interest) writes the recovery price/rate under an epoch key no user maps to. Loss-adjusted receipts are then paid at par on a first-come-first-served basis until the strategy's haircutted balance is exhausted, after which remaining claimants' requests revert on insufficient funds — identical impact class to the source report ("founders get fewer tokens than expected"), i.e., users receive less than their entitled amount or nothing.

### Likelihood Explanation
Triggers on any loss-realizing `stopEpochWithDuration`/`collectWithdrawFunds` shortfall or any APR0 epoch with positive net interest — both are normal protocol paths requiring no attacker action beyond holding a pending withdraw request. The only precondition is the CDO ordering described above, which is the natural sequence (repay/deposit, then collect) implied by the code comments.

### Recommendation
Key the per-epoch write with the same epoch the receipts were recorded under. Either (a) capture `uint256 reqEpoch = epochNumber - 1` (or the pre-increment value passed in from the CDO) when writing `lossRecoveryPriceByEpoch` and `apr0RateByEpoch`, or (b) move the `epochNumber += 1` increment out of `deposit()` to the end of `stopEpoch` after `collectWithdrawFunds`/`prepareStopEpochWithApr0` run. Alternatively, make claims resolve "latest non-zero price epoch" rather than assuming `lastWithdrawRequest` equals the storage key.

### Proof of Concept
```solidity
// Foundry fork PoC (sketch): APR0/loss-adjusted receipt underpaid
// 1. LP deposits via cdoEpoch.depositAA, startEpoch begins epoch N.
// 2. LP calls cdoEpoch.requestWithdraw -> strategy.requestWithdraw records
//    lastWithdrawRequest[user] = N, withdrawsRequestsByEpoch[user][N] = amt.
// 3. Borrower repays with a shortfall; manager calls
//    cdoEpoch.stopEpochWithDuration(_lossAmount):
//      - strategy.deposit() executes first -> epochNumber becomes N+1
//      - collectWithdrawFunds(pendingToFund) stores
//        lossRecoveryPriceByEpoch[N+1] = price  (receipts live under N)
// 4. User calls cdoEpoch.claimWithdrawRequest:
//      _claimLossAdjustedWithdrawRequest reads lossRecoveryPriceByEpoch[N] == 0 -> skips
//      _claimFundedWithdrawRequest pays full withdrawsRequests[user]
// 5. A second user with a pending receipt in epoch N claims next:
//      strategy holds only the haircutted amount -> transfer reverts /
//      second user receives less than their pro-rata funded share.
// Asserts:
//   assertEq(vault.lossRecoveryPriceByEpoch(N), 0);
//   assertGt(vault.lossRecoveryPriceByEpoch(N + 1), 0);
//   first claim paid at par; second claim reverts on insufficient balance.
```
Analogous APR0 variant: request with `unscaledApr == 0`, then `stopEpoch` with positive interest — `apr0RateByEpoch[N+1]` is set while `_settleApr0` reads `apr0RateByEpoch[N] == 0`, so `settledInterest` stays 0 and the allocated APR0 interest in `pendingWithdraws` is never claimable.
