### Title
External Initiator credentials bypass job binding and can trigger arbitrary job runs via POST /v2/jobs/:ID/runs - ([File: core/web/pipeline_runs_controller.go])

### Finding Description
`PipelineRunsController.Create` determines whether a request is allowed to run a job by an integer ID solely via `_, isUser := auth.GetAuthenticatedUser(c)` [1](#0-0) . The comment states "only users are allowed to run jobs using int IDs - EIs not allowed," but this check does not actually distinguish real dashboard/API users from External Initiators.

`AuthenticateExternalInitiator` in `core/web/auth/auth.go` forcibly injects a synthetic user object into the same session key that real users use: `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` [2](#0-1) . Since `GetAuthenticatedUser` simply reads `SessionUserKey` and returns `ok=true` whenever that key is set [3](#0-2) , an EI-authenticated request will also satisfy `isUser == true` in `Create`.

Once `isUser` is true, the handler parses the `:ID` path parameter as an int32 job ID and unconditionally calls `prc.App.RunJobV2(ctx, jobID, nil)` [4](#0-3) . There is no lookup or comparison against the External Initiator's own bound/registered job — the function has no reference to `GetAuthenticatedExternalInitiator` or any job-ownership check at all. Any job ID that parses as an int32 is dispatched to `RunJobV2`, regardless of which job the EI credential was created for.

### Impact Explanation
An EI credential holder — a low-privilege, narrowly-scoped API credential intended only to trigger its own bound webhook job — can trigger pipeline runs for **any** job on the node by ID, matching the bounty impact class of "unauthorized job run" / authorization bypass across job boundaries. This can cause execution of arbitrary jobs (including jobs that move funds, submit on-chain transactions, or perform privileged pipeline tasks) that the EI was never authorized to invoke.

### Likelihood Explanation
Exploitation only requires a valid EI access key/secret pair (the minimal EI credential), which is the lowest privilege class explicitly targeted by the audit question. No admin, session, or higher-role credential is needed. The request is a single unauthenticated-relative-to-target-job POST to `/v2/jobs/:ID/runs` with an arbitrary integer job ID, fully repeatable and requiring no race condition or timing dependency.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests authenticated as an External Initiator before treating the request as a user-triggered run — e.g., check `auth.GetAuthenticatedExternalInitiator(c)` and return `403`/`422` if present, rather than relying on the coincidentally-shared `SessionUserKey`. More robustly, stop overloading `SessionUserKey` for EI sessions in `AuthenticateExternalInitiator`; use a distinct marker so that `GetAuthenticatedUser` cannot be satisfied by EI credentials, and re-introduce explicit job-to-EI binding validation if EI-triggered runs are still supported.

### Proof of Concept
1. Create two jobs, Job A and Job B, via the jobs API/ORM.
2. Create an External Initiator record with access key/secret (independent of Job A/B, since no EI-to-job binding is enforced by `Create`).
3. Send `POST /v2/jobs/<JobB.ID>/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to the EI's credentials.
4. Assert: `AuthenticateExternalInitiator` succeeds and sets `SessionUserKey` to `{Role: UserRoleRun}` [5](#0-4) .
5. Assert: `PipelineRunsController.Create` treats `isUser` as `true` [1](#0-0)  and calls `RunJobV2` for Job B, returning `200 OK` with a `pipelineRun` resource rather than a `401/403` rejection — demonstrating the EI credential can trigger an unrelated job.
