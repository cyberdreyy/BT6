### Title
Stale confirmations from removed multisig members remain counted toward the confirmation threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
When a multisig member (or access key) is removed via `DeleteMember`/`DeleteKey`, the contract only purges *requests that member created*, not *confirmations that member cast on other members' still-pending requests*. Those stale confirmations remain in the `confirmations` set and continue to count toward `num_confirmations` in `confirm()`, even though the signer is no longer a member. This breaks the binding "confirmations counted == live members who approved," allowing a request to execute while fewer *currently authorized* members actually approved it than the configured threshold requires.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` executes a request purely based on the size of the stored `confirmations: HashSet<String>` for that request: [1](#0-0) 

`delete_member()` only removes requests whose *creator* (`r.member`) matches the member being deleted; it does not scan `self.confirmations` to strip that member's vote from other pending requests they had merely confirmed: [2](#0-1) 

Concretely:
1. Member `M1` creates request `R` (a `Transfer`, `AddKey`, etc.).
2. Member `M2` confirms `R` (`confirmations[R] = {M2}`), one short of `num_confirmations`.
3. A separate governance request removes `M2` from the multisig (e.g., `M2`'s key was compromised or their term ended) via `DeleteMember`. `delete_member` only removes requests *created* by `M2`; `R` was created by `M1`, so it is untouched, and `M2`'s entry in `confirmations[R]` survives.
4. `M2` is no longer in `self.members`, so `current_member()` would reject any *new* action by `M2`, but the ghost confirmation they already cast remains valid data in `confirmations[R]`.
5. Any subsequent member confirms `R`. `confirm()` checks `confirmations.len() as u32 + 1 >= self.num_confirmations`, counting `M2`'s stale vote as if `M2` were still a trusted member. The request executes with one fewer *live* member's approval than the threshold requires.

The same defect exists in the legacy `multisig/src/lib.rs` contract: `DeleteKey` in `execute_request` purges only requests signed (created) by the deleted `public_key`, not confirmations that key gave on other pending requests: [3](#0-2) [4](#0-3) 

This is a direct analog to the reported class: an "unencrypted"/unverified fallback path (here, unaudited stale state) silently weakens a security guarantee (the confirmation threshold) that the system is supposed to always enforce — the recorded "claims" (confirmations set size) diverge from the ground truth (currently authorized, live members).

### Impact Explanation
This is Critical: a `MultiSigRequestAction::Transfer`, `AddKey`, `FunctionCall`, or any other privileged action can be executed with effectively fewer live-member confirmations than `num_confirmations` mandates, because a removed member's earlier vote is silently retained and counted. This is precisely the "multisig request executed below threshold" impact category — funds can be moved, keys added, or contracts upgraded by a coalition of members that is smaller than the configured security threshold, undermining the entire multisig trust model.

### Likelihood Explanation
The trigger requires no privileged access beyond being a former legitimate member (or someone whose confirmation was cast before being removed) plus normal member activity that already occurs in practice — i.e., committee membership changes over time while requests are outstanding. Any multisig deployment that rotates members while requests are pending (a routine, expected operational scenario, not a contrived edge case) is exposed. No malicious deployment, redeploy, or victim key theft is needed — the flaw is in the standard `delete_member`/`DeleteKey` code path shipped in this repository.

### Recommendation
- Short term: When removing a member/key, iterate `self.requests`/`self.confirmations` and strip the removed member's identifier from every pending request's confirmation set (not just requests they created), re-checking whether the removal drops any request below quorum.
- Long term: Instead of storing raw confirmation counts, validate at `confirm()`/execution time that every entry in the confirmation set still corresponds to a current member of `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
```rust
// multisig2 scenario, num_confirmations = 3, members = {M1, M2, M3, M4}
let mut c = MultiSigContract::new(members(), 3);

// 1. M1 creates a Transfer request R
let r_id = c.add_request(transfer_request); // as M1

// 2. M2 confirms R (1/3)
c.confirm(r_id); // as M2  -> confirmations[r_id] = {M2}

// 3. Members vote to remove M2 (e.g. suspected compromise) via a separate,
//    fully-confirmed DeleteMember request.
c.add_request_and_confirm(delete_m2_request); // reaches 3/3, executes delete_member(M2)
// delete_member only removes requests CREATED by M2; R (created by M1) is untouched.
// confirmations[r_id] still contains M2's stale entry.

// 4. M3 confirms R -> confirmations.len() == 2, but code computes 2 + 1 >= 3 -> executes!
c.confirm(r_id); // as M3
// Transfer executes with only {M2 (removed), M3} = effectively 1 live-member approval
// plus a ghost vote from a non-member, despite num_confirmations == 3.
```

        self.assert_valid_request(request_id);

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
