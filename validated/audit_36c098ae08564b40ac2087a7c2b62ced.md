### Title
Missing new-authority validation in `bpf_loader_upgradeable`'s unchecked `SetAuthority` allows permanently bricking a program's or buffer's authority - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The `UpgradeableLoaderInstruction::SetAuthority` handler in the BPF Upgradeable Loader accepts an arbitrary `new_authority` pubkey from the instruction accounts and writes it into the `Buffer`/`ProgramData` account state without requiring that pubkey to sign the transaction or validating that it is a controllable address. This mirrors the `setGov()` bug class: the entity holding an admin-like capability (the upgrade/buffer authority) can set the successor authority to an unusable address (e.g. the system program ID, `Pubkey::default()`), permanently losing the ability to upgrade or reassign the program - with no recovery path, since nobody controls the private key for that pubkey.

### Finding Description
In `process_instruction` for `UpgradeableLoaderInstruction::SetAuthority`, the new authority is taken directly from account index 2 with no signature requirement and no restriction on which key it can be: [1](#0-0) 

For the `Buffer` case, the code only checks that a `new_authority` was supplied and that the *current* authority signed — it never validates the new authority itself: [2](#0-1) 

Similarly, for the `ProgramData` (program upgrade authority) case, only the current authority's signature is checked before writing whatever `new_authority` was passed in the instruction: [3](#0-2) 

By contrast, the safer `SetAuthorityChecked` variant explicitly requires the *new* authority account to also sign the instruction, which prevents accidentally naming an address nobody controls: [4](#0-3) [5](#0-4) [6](#0-5) 

This asymmetry is the exact root cause described in the external report: the "unchecked" administrative setter (`SetAuthority`) is missing a sanity check that its "checked" sibling (`SetAuthorityChecked`) enforces. Because `SetAuthority` doesn't require the new authority to sign, a current authority (or a confused-deputy CPI caller acting on the authority's behalf) can pass `Pubkey::default()` (the System Program address, `11111111111111111111111111111111111111111`, for which no private key exists) as `new_authority`, and the instruction succeeds, writing `Some(Pubkey::default())` into `upgrade_authority_address` or `authority_address`.

### Impact Explanation
Once the authority is set to an uncontrollable pubkey like `Pubkey::default()`:
- The `ProgramData` account's `upgrade_authority_address` is `Some(Pubkey::default())`, so the "Program not upgradeable" `Immutable` check never triggers, yet no future `SetAuthority`/`Upgrade`/`Close` call can ever succeed because the required signer (`Pubkey::default()`) can never sign a transaction.
- This permanently locks the program in whatever state it was last deployed, with no way to upgrade, transfer, or close it — an unrecoverable state mutation analogous to the loss of `gov` access described in the report, and equally applicable to `Buffer` accounts (funds in the buffer account also become unrecoverable since `Close` requires signature by the current authority).

### Likelihood Explanation
This is reachable by any ordinary transaction that already holds the current authority's signature — no special privilege beyond that already required for legitimate authority transfer is needed. It requires either a user/authority mistake (directly analogous to the original `setGov()` scenario) or a malicious/buggy program that constructs the `SetAuthority` instruction with an incorrect `new_authority` account (e.g., via CPI where the authority blindly forwards a pubkey to this instruction). Since `SetAuthority` (unlike `SetAuthorityChecked`) does not require the new-authority account to sign, there is no safety net to catch this mistake at the protocol layer, matching the "Acknowledged" medium-severity classification of the analog.

### Recommendation
Add a Sanity/zero-address style check in the `SetAuthority` branch to reject setting the new authority to a known "black-hole" pubkey (e.g., `Pubkey::default()`, i.e., the System Program ID), or more robustly, encourage/require use of `SetAuthorityChecked` (which already requires the new authority to sign) for all cases, deprecating the unchecked path, since the checked variant already resolves this exact bug class.

### Proof of Concept
1. Deploy an upgradeable program; its `ProgramData` account has `upgrade_authority_address = Some(authority)`.
2. The current `authority` signs and submits a `SetAuthority` instruction (see accounts layout in `programs/bpf_loader/src/lib.rs:549-553`) where instruction account index 2 (`new_authority`) is set to `Pubkey::default()` — this account does not need to be a signer.
3. The instruction succeeds, and `programdata.set_state(...)` writes `upgrade_authority_address: Some(Pubkey::default())` (`programs/bpf_loader/src/lib.rs:605-608`).
4. Any subsequent `Upgrade`, `SetAuthority`, `SetAuthorityChecked`, or `Close` instruction targeting this `ProgramData`/`Program` fails permanently with `MissingRequiredSignature`, because no keypair exists for `Pubkey::default()` — the program is now unmodifiable and any lamports in a similarly-bricked `Buffer` account are permanently unrecoverable.
