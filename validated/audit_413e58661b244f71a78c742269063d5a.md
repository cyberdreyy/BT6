### Title
`instantWithdrawClaimsByEpoch` is never decremented on paid instant claims, so `finalizeDefaultRecovery` counts already-paid receipts as both claim basis and "prefunded" reserve, inflating the recovery price with phantom funds — (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`claimInstantWithdrawRequest` pays out an instant receipt and clears `instantWithdrawsRequests[_user]`, but it never reduces `instantWithdrawClaimsByEpoch[epoch]` — the epoch-level aggregate that mirrors the airoha "completion" counter. Later, `defaultPendingClaimBasis()` adds that stale aggregate to the default claim basis whenever `pendingInstantWithdraws != 0`, and `_defaultPrefundedInstantReserve()` treats `instantBasis - pendingInstantWithdraws` as underlying still held by the strategy — even though those funds were already transferred to claimers. The result is a double-sided phantom entry: phantom basis plus phantom reserve, which pushes `recoveryPrice` toward 1 while `defaultRecoveryReserve` records tokens the contract does not hold.

### Finding Description
Enqueue/dequeue asymmetry, mirroring the BQL imbalance (account on one counter set, complete against a different one):

- Enqueue (request): `requestInstantWithdraw` increments `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch[currentEpoch]`, and `pendingInstantWithdraws` [1](#0-0) 
- Funding: `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` by the collected amount only [2](#0-1) 
- Dequeue (claim): `claimInstantWithdrawRequest` burns `instantWithdrawsRequests[_user]` and transfers underlying out, but leaves `instantWithdrawClaimsByEpoch` untouched [3](#0-2) 
- Recovery accounting then reads the stale aggregate as if it were still live basis: `basis += instantWithdrawClaimsByEpoch[epochNumber]` [4](#0-3) 
- And `_defaultPrefundedInstantReserve` credits `instantBasis - pendingInstant` as "already-held" strategy funds that may in fact have been fully paid out [5](#0-4) 

In `finalizeDefaultRecovery`, `reserveAmount` includes this phantom prefunded reserve and `totalBasis` includes the already-claimed receipts [6](#0-5) . Since `(a + x)/(b + x) > a/b` when `a < b`, adding the same phantom `x` to numerator and denominator inflates `recoveryPrice` above the true recovery ratio, while `defaultRecoveryReserve` is set to a value exceeding the real balance. Early post-finalization claimants are paid at the inflated price from real funds; the reserve is exhausted early and later claimants' transfers fail — their receipts are permanently unclaimable.

### Impact Explanation
Direct theft plus permanent freezing of unclaimed yield. An attacker holding a defaulted-epoch pending receipt (instant or normal) is paid at an inflated `recoveryPrice`, drawing more than their pro-rata share of the real recovered funds. The deficit is socialized onto later claimants whose claims revert on insufficient balance — their recovery is permanently frozen in accounting. The magnitude scales with the amount of instant claims already paid out in the default epoch: with `x` phantom units and true recovery ratio `r`, claimants are collectively overpromised `x * (1 - r)` that does not exist.

### Likelihood Explanation
Requires an epoch where instant withdrawals were partially funded and at least partially claimed before a borrower default — a normal operating state, not an edge case: `collectInstantWithdrawFunds` funds the instant queue in arbitrary `_amount` increments and `pendingInstantWithdraws != 0` is exactly the trigger condition [2](#0-1) . No privileged misbehavior is needed; the attacker is an ordinary receipt holder sequencing a claim before default finalization. Existing guards do not stop it: `defaultPendingClaimBasis` has no check that the epoch aggregate still corresponds to outstanding receipts, and `_defaultPrefundedInstantReserve` assumes, without checking the token balance, that the funded-but-not-collected delta is still held [7](#0-6) .

### Recommendation
Decrement `instantWithdrawClaimsByEpoch[epochNumber]` in `claimInstantWithdrawRequest` (and in any instant-claim path) by the claimed amount, so the epoch aggregate reflects only outstanding receipts. Alternatively, compute `_defaultPrefundedInstantReserve` from the actual underlying balance / unclaimed receipts (`instantWithdrawsRequests` outstanding sum) rather than the cumulative epoch counter, and exclude already-claimed amounts from `defaultPendingClaimBasis`.

### Proof of Concept
Foundry fork sketch (standard epoch variant with instant withdrawals enabled):

```solidity
// Epoch N running; instant withdraws enabled via setInstantWithdrawParams.
// 1. Attacker and victim each requestInstantWithdraw: 60 and 40 units.
cdoEpoch.requestWithdraw(attackerAmt, AA); // routed to instant ledger
cdoEpoch.requestWithdraw(victimAmt, AA);
// strategy: instantWithdrawClaimsByEpoch[N] = 100, pendingInstantWithdraws = 100

// 2. stopEpoch funds only 60 of the instant queue.
cdoEpoch.stopEpoch(apr, 0);
// collectInstantWithdrawFunds(60) -> pendingInstantWithdraws = 40

// 3. Attacker claims their funded 60.
cdoEpoch.claimInstantWithdrawRequest(); // attacker paid; instantWithdrawClaimsByEpoch[N] still 100

// 4. Borrower defaults (honest borrower; partial default is a normal event).
// 5. finalizeDefaultRecovery:
//    pendingInstantWithdraws = 40 != 0  -> basis += 100 (includes attacker's paid 60)
//    _defaultPrefundedInstantReserve = 100 - 40 = 60 counted as "held" — phantom
//    reserveAmount = realRecovered + 60 phantom; totalBasis += 100
//    recoveryPrice inflated; defaultRecoveryReserve overstated by 60

// 6. Attacker (also holding a defaulted-epoch normal receipt) claims first at
//    inflated price -> drains real reserve.
// 7. Victim's claimWithdrawRequest / instant claim reverts on insufficient
//    underlying -> permanently unclaimable receipt.
```

Caveat: the exact payout math in `_claimDefaultedInstantWithdrawRequest` / `_claimDefaultedWithdrawRequest` was not fully inspected in this pass, but both consume `defaultRecoveryPrice` against `defaultRecoveryReserve`, so the inflated-price-then-insolvency sequence holds regardless of per-claim rounding.
