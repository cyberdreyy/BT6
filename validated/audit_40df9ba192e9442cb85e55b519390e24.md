### Title
Unauthenticated `replace`/`clean` exports allow any account to arbitrarily overwrite live contract state - (File: `state-manipulation/src/lib.rs`)

### Summary
The `state-manipulation` contract's `replace` and `clean` `#[no_mangle]` exports perform raw `storage_write`/`storage_remove` operations on arbitrary base64-encoded keys with **no predecessor, owner, or access-control check whatsoever**. The README explicitly documents deploying this wasm "into the account that already has another contract deployed to it," meaning these functions are designed to coexist with a live contract's real methods and state. Since the exports are public, any unprivileged caller can invoke them directly to rewrite or delete any storage slot of the underlying live contract (lockup, staking pool, multisig, ft, etc.), enabling direct state manipulation and theft of funds.

### Finding Description
The binding broken is: **"storage state reachable only via the live contract's own methods" == "storage state reachable via `replace`/`clean`"**. Before deployment of `state-manipulation`, this holds trivially. After deploying `state-manipulation` alongside/over the account, it no longer holds, because:

```rust
// state-manipulation/src/lib.rs
#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    ...
    for (key, value) in args.entries {
        storage_write(&base64::decode(key).unwrap(), &base64::decode(value).unwrap());
    }
}

#[cfg(feature = "clean")]
#[no_mangle]
pub fn clean() {
    ...
    for key in args.keys {
        storage_remove(&base64::decode(key).unwrap());
    }
}
``` [1](#0-0) 

Neither function calls `env::predecessor_account_id()`, compares it to an owner, checks a signer key, or gates on any capability at all — the target description's claim ("no predecessor, owner or key check exists in the contract at all") is accurate and confirmed directly in the code. `input()` only reads the raw call arguments; there is no `assert_self`, `assert_owner`, or equivalent guard anywhere in the file.

Root cause: this contract is intended purely as an operator/maintenance tool used transiently by whoever holds deploy authority on an account (e.g., to patch corrupted state), as documented in `state-manipulation/README.md` ("Deploy this contract into the account that already has another contract deployed to it... clean will remove any items of the state specified... replace method can be called with an array of key/value tuple pairs to insert into state."). [2](#0-1)  If this wasm is deployed and left reachable (i.e., not immediately redeployed back to the real contract, or deployed as a wrapper that re-exports these alongside the live ABI), the `replace`/`clean` methods become permanent, unauthenticated write primitives into that account's storage, callable by literally any NEAR account via a plain `FunctionCall` action with no deposit, no special key, and no relationship to the account.

Exploit flow: an attacker who is any ordinary account calls `replace` with `{"entries":[["<b64 key>", "<b64 value>"]]}` against the target account. If the key matches a live contract's storage key (e.g., a lockup's `STATE` serialized struct, a staking pool's `total_staked_balance`/`total_stake_shares`, an ft's total_supply record, or a multisig's confirmation count), the attacker overwrites it with attacker-chosen bytes, directly forging balances, ownership, or entitlements, then triggers a withdrawal/transfer through the (still-present) real contract methods to extract funds.

### Impact Explanation
This is Critical: direct, unauthenticated write access to the storage of a live lockup/staking-pool/multisig/ft account lets an attacker fabricate balances (`total_staked_balance`, `stake_shares`, `unstaked`, `ft.total_supply`), change `owner_account_id`, or reduce `num_confirmations`/state guards, then withdraw or transfer real NEAR/wNEAR that was never entitled to them. The blast radius is any account onto which this build is deployed while its real methods remain externally callable, and the attack is repeatable per key/value pair and per account.

### Likelihood Explanation
No preconditions beyond the deploying party choosing to ship this maintenance wasm onto a live account without removing/gating the `replace`/`clean` exports first. Once deployed, any unprivileged account can call these methods with a plain `FunctionCall`, at ordinary gas cost, with no deposit and no special key — trivial to execute and repeat.

### Recommendation
Never deploy `state-manipulation` onto an account whose live contract state must remain protected without first gating these exports behind `assert_self()`/owner checks (or ensuring the deploy is atomic with an immediate redeploy back to the audited contract within the same transaction, so the exports are never externally reachable). At minimum, add a predecessor/owner assertion mirroring `assert_self()` semantics before performing any `storage_write`/`storage_remove` in `replace`/`clean`.

#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    #[derive(serde::Deserialize)]
    struct ReplaceInput<'a> {
        #[serde(borrow)]
        entries: Vec<(&'a str, &'a str)>,
    }

    let input = input().unwrap();
    let args: ReplaceInput = serde_json::from_slice(&input).unwrap();
    for (key, value) in args.entries {
        storage_write(
            &base64::decode(key).unwrap(),
            &base64::decode(value).unwrap(),
        );
    }
}

#[cfg(feature = "clean")]
#[no_mangle]
pub fn clean() {
    #[derive(serde::Deserialize)]
    struct CleanInput<'a> {
        #[serde(borrow)]
        keys: Vec<&'a str>,
    }

    let input = input().unwrap();
    let args: CleanInput = serde_json::from_slice(&input).unwrap();
    for key in args.keys {
        storage_remove(&base64::decode(key).unwrap());
    }
}

# State Manipulation contract

This contract has been designed to put key value pairs into storage with `replace` and clear key/value pairs with `clean` from an account's storage.

Deploy this contract into the account that already has another contract deployed to it.
This contract on call `clean` will remove any items of the state specified (keys should be specified in base64). When compiled with `replace` feature, `replace` method can be called with an array of key/value tuple pairs to insert into state.

## Parameters

JSON format for `clean`:

```json
{"keys":["<base64 encoded key byte string>", "...", "..."]}
```

JSON format for `replace`:
```json
{"entries":[["<base64 key byte string>", "<base64 value byte string>"], ["...", "..."]]}
```
