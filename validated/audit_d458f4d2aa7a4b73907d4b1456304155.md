### Title
Loss-adjusted withdraw receipt escapes its haircut when a newer `requestWithdraw` overwrites `lastWithdrawRequest`, paying the pre-loss basis at par — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a recursive reclaim path that silently skips the writeback it was supposed to perform (`nfs_release_folio` skipping `nfs_wb_folio`), leaving the resource permanently blocked. The credit-vault analog is in `IdleCreditVault`: the loss-adjusted claim path is keyed off a single mutable epoch marker `lastWithdrawRequest[_user]`. When a new `requestWithdraw` overwrites that marker before the user claims, the haircutted epoch's claim is silently skipped and the receipt's full pre-loss basis is later paid at par through the funded-claim path — a stale-epoch escape of the loss waterfall.

### Finding Description
At `stopEpochWithDuration`-style stops with a loss, `collectWithdrawFunds` records a per-epoch haircut in `lossRecoveryPriceByEpoch[epochNumber]` and transfers only the funded (haircutted) `_amount` into the strategy [1](#0-0) . The corresponding user payout is meant to go through `_claimLossAdjustedWithdrawRequest`, which reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` [2](#0-1) .

However `requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` while leaving the old epoch's `withdrawsRequestsByEpoch[_user][E]` and the aggregate `withdrawsRequests[_user]` intact [3](#0-2) . On the next `claimWithdrawRequest`:

1. `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[E+1]` — it is `0`, so it returns 0 and never clears the epoch-E receipt [4](#0-3) .
2. Once `epochNumber > E+1`, `_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]`, which still contains the **full, un-haircutted** epoch-E basis, via `_transferFundedClaim` [5](#0-4) .

The epoch-E receipt was only funded with `claimBasis * lossRecoveryPrice / RECOVERY_FULL`, yet it is redeemed for `claimBasis`. The difference `(claimBasis * (RECOVERY_FULL - price) / RECOVERY_FULL)` is paid out of strategy underlyings that back other users' funded receipts and active tranche value.

### Impact Explanation
An unprivileged KYC-passing lender can escape a realized loss that was explicitly socialized onto pending receipts, receiving more underlyings than were funded for their receipt. This breaks the loss-waterfall and one-receipt-one-payout invariants and directly insolvents the strategy's funded-claim reserve: later claimants (including honest users' funded receipts paid via `_transferFundedClaim` / `_claimDefaultedWithdrawRequest`'s par path) are left undercollateralized. Quantified loss equals `Σ claimBasis_E × (1 − lossRecoveryPrice)`, up to the full pending-receipt basis of the loss epoch.

### Likelihood Explanation
The trigger requires only that a loss epoch occurs (`collectWithdrawFunds` with `_amount < pendingBasis`, i.e. borrower underfunds at stop) and that the attacker holds a pending receipt in that epoch, then calls `requestWithdraw` again — all normal user actions in the buffer phase. No privileged or external dependency is needed; the guard `_checkNotAllowed` in `requestWithdraw` does not check `lossRecoveryPriceByEpoch` or pending haircutted receipts. The prerequisite is a lossy epoch, which is an intended (if infrequent) operating mode, making this conditional rather than speculative.

### Recommendation
In `requestWithdraw` (and `requestInstantWithdraw` if an equivalent marker exists), either revert when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` for an uncleared prior epoch, or eagerly settle the loss-adjusted claim inside `requestWithdraw` before overwriting `lastWithdrawRequest[_user]`. Alternatively, iterate `withdrawsRequestsByEpoch` for all epochs with a nonzero `lossRecoveryPriceByEpoch` instead of keying the loss-adjusted claim off the single latest marker.

### Proof of Concept
Foundry fork PoC outline (modeled on `test/foundry/IdleCreditVault.t.sol`):

```solidity
// setup: deposit AA, start epoch 0, user requests withdraw -> receipt in epoch 0
uint256 receipt = cdoEpoch.requestWithdraw(userTrancheBal, address(AAtranche));
_startEpoch();                       // epoch 0 runs
// manager stops epoch with a loss so collectWithdrawFunds records
// lossRecoveryPriceByEpoch[epochNumber] = price < RECOVERY_FULL
cdoEpoch.stopEpochWithDuration(0, 0, lossAmount); // or stopEpoch path that underfunds
uint256 price = strategy.lossRecoveryPriceByEpoch(lossEpoch);
assertLt(price, RECOVERY_FULL);

// attacker: instead of claiming the haircutted receipt, request a new withdraw
// in the buffer of epoch 1 -> lastWithdrawRequest[user] overwritten to epoch 1
cdoEpoch.requestWithdraw(smallAmount, address(AAtranche));

_startEpoch();                       // epoch 1 runs
_stopEpoch();                        // epoch 1 ends, epochNumber increments

// claimWithdrawRequest: loss-adjusted lookup for epoch 1 returns 0,
// funded path pays withdrawsRequests[user] which still includes FULL epoch-0 basis
uint256 balPre = underlying.balanceOf(user);
cdoEpoch.claimWithdrawRequest();
uint256 paid = underlying.balanceOf(user) - balPre;

// expected at par:
assertEq(paid, receipt + smallAmountClaim);
// but strategy was only funded receipt*price/RECOVERY_FULL + smallAmountClaim for it
// -> attacker received receipt*(RECOVERY_FULL - price)/RECOVERY_FULL more than funded,
//    draining reserve backing other claimants.
```

The assertion gap `paid - (receipt * price / RECOVERY_FULL + epoch1Claim) > 0` demonstrates the haircut escape and reserve insolvency.

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
