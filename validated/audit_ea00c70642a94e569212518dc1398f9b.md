### Title
Validator panic via `getTransaction` RPC due to unchecked empty-`signatures` indexing in `find_transaction_in_slot` - (File: `ledger/src/blockstore.rs`)

### Summary
`Blockstore::find_transaction_in_slot` deserializes raw entries for a slot and, without filtering out transactions that fail sanitization, unconditionally indexes `transaction.signatures[0]` while searching for the requested signature. Because malformed/unsanitized transaction data (e.g. an empty `signatures` vector) is only logged and not discarded, a transaction with zero signatures reaching this code path causes an index-out-of-bounds panic, crashing the validator's RPC-serving process from a single unprivileged `getTransaction` call.

### Finding Description
`find_transaction_in_slot` retrieves all entries for a slot and flattens their transactions, calling `sanitize()` purely for logging purposes — the result is discarded and processing continues regardless of failure: [1](#0-0) 

```rust
fn find_transaction_in_slot(
    &self,
    slot: Slot,
    signature: Signature,
) -> Result<Option<(VersionedTransaction, u32)>> {
    let slot_entries = self.get_slot_entries(slot, 0)?;
    Ok(slot_entries
        .into_iter()
        .flat_map(|entry| entry.transactions)
        .enumerate()
        .map(|(index, transaction)| {
            if let Err(err) = transaction.sanitize() {
                warn!(
                    "Blockstore::find_transaction_in_slot sanitize failed: {err:?}, slot: \
                     {slot:?}, {transaction:?}",
                );
            }
            (index, transaction)
        })
        .find(|(_, transaction)| transaction.signatures[0] == signature)
        .map(|(index, transaction)| (transaction, index as u32)))
}
```

The `.find(|(_, transaction)| transaction.signatures[0] == signature)` call directly indexes into the `signatures` vector without checking its length. `VersionedTransaction::signatures` is a plain `Vec<Signature>` deserialized from raw shred/entry bytes stored in the blockstore, and the explicit `warn!` on `sanitize()` failure (rather than skipping/filtering the malformed transaction) demonstrates the authors anticipated malformed transactions reaching this point — yet the code still proceeds to index `signatures[0]` unconditionally. If any transaction stored for that slot has zero signatures (a state that `sanitize()` is specifically designed to reject), this indexing operation panics with an out-of-bounds access.

This function is reachable from `get_transaction_with_status`, which backs the public `get_rooted_transaction` / `get_complete_transaction` APIs used to implement the `getTransaction` JSON-RPC method: [2](#0-1) 

### Impact Explanation
This falls under the accepted "decoder panic and misreporting" / "concrete validator-process crash ... from one request" categories. Any client able to issue a single unprivileged `getTransaction` RPC request targeting a slot containing a signature-less transaction can crash the RPC-serving validator thread/process, an availability impact with no privileged access required.

### Likelihood Explanation
Likelihood depends on whether a transaction with an empty `signatures` vector can actually be persisted into blockstore entries for a slot (e.g., via shreds received before/without full transaction verification during turbine propagation or catch-up replay). The presence of the `sanitize()` call with only a warning (not a filter/skip) strongly suggests the authors were aware such malformed transactions can occur in stored entries, which is the primary evidence for this being a real, reachable condition rather than purely theoretical. I could not fully trace the exact shred-ingestion path that would allow a signature-less transaction to be committed into blockstore entries; this would need additional verification (e.g., via a Devin session with the ability to run reproduction tests) to confirm exploitability in an end-to-end scenario.

### Recommendation
Change the `.find(...)` predicate to safely handle transactions with no signatures, e.g. use `transaction.signatures.first() == Some(&signature)` instead of `transaction.signatures[0] == signature`, and/or filter out transactions that fail `sanitize()` before searching, rather than merely logging the failure and continuing to process the transaction as if valid.

### Proof of Concept
Not independently reproducible with the available read-only tooling. Conceptually: get a slot's blockstore entries to contain a `VersionedTransaction` with an empty `signatures` field (bypassing `sanitize()`, which only produces a warning here rather than filtering), then issue `getTransaction` (or any path invoking `get_rooted_transaction`/`get_complete_transaction`) for any signature; the lookup in `find_transaction_in_slot` will panic on `transaction.signatures[0]` when it reaches the malformed transaction.
