### Title
Unprivileged Vault client can wipe all other users' pending secret requests via pending-queue stall threshold crossing - (File: `core/services/ocr2/plugins/vault/plugin.go`)

### Summary
The `StRSR.sol` bug class in the external report describes a threshold-crossing mechanism that wipes an entire pool of legitimately-held value when the pool's rate crosses a boundary, even though the crossing itself can be caused by a comparatively small, final event. The Chainlink Vault OCR plugin's pending-queue stall-purge mechanism exhibits the same structural flaw: reaching a stall-signal threshold causes the plugin to unconditionally delete the **entire shared pending queue** — including all other unprivileged users' in-flight `CreateSecrets`/`UpdateSecrets`/`DeleteSecrets`/`GetSecrets` requests — rather than only the offending request.

### Finding Description
The `ReportingPlugin.Observation` method walks the on-chain (KV-store-backed) pending queue and must produce a store-backed `Observation` for every item when `VaultOptimizationsEnabled` is disabled [1](#0-0) . If a single unprivileged client submits a request whose ciphertext passes ingress-time size checks (`VaultCiphertextSizeLimit`) but whose resulting store-backed `Observation` exceeds `VaultMaxObservationSizeLimit`, that item can never be validly observed by a node without violating either the wire cap or the "must observe all items" invariant, causing the node to be permanently unable to make progress on that request in every round.

Each round, `Observation()` checks `shouldPurgePendingQueue`, which increments a per-round `pendingQueueStallTracker` and compares it against `VaultPendingQueueStallThreshold` (clamped to be at least `2f+1`) [2](#0-1) . Once enough nodes emit `PENDING_QUEUE_STALL_SIGNAL_STALLED` observations (≥ `f+1` in `StateTransition`), the plugin calls `purgeStalledPendingQueue`, which does an unconditional `store.WritePendingQueue(ctx, nil)` — erasing the *entire* pending queue in one shot [3](#0-2) [4](#0-3) .

This is structurally identical to the StRSR bug: a threshold (`stallThreshold` / rate cap) that, once crossed, discards the entirety of shared state rather than just the portion responsible for the imbalance. Here the "value" wiped is every other user's queued Vault request (secret creation/update/deletion/read requests), and the trigger can be a single unprivileged client's carefully-sized ciphertext, analogous to the "small seizure" that tips an already-strained rate over the edge.

The project's own test/smoke-test infrastructure explicitly documents and reproduces this exact scenario ("Vault pending-queue stall purge smoke coverage... a valid-at-ingress ciphertext can produce an oversized store-backed observation") [5](#0-4) , and unit tests confirm the queue purge behavior wipes all store-backed pending items, only preserving node-local (not-yet-broadcast) requests for normal TTL eviction [6](#0-5) .

### Impact Explanation
Any unprivileged Vault client (workflow owner submitting requests through the gateway) can craft a request whose plaintext/ciphertext passes ingress validation but produces an oversized store-backed `Observation`. Once accepted into the shared on-chain pending queue, it stalls OCR consensus for that item indefinitely. If this persists past the configured stall threshold, the entire pending queue — potentially containing many other legitimate users' secret create/update/delete requests — is deleted. This is a shared-state DoS/loss-of-request vulnerability: unrelated, valid, in-flight requests from other unprivileged users are silently dropped and must be resubmitted, with no compensating "migration" of in-flight work, matching the impact profile of the referenced bug (irrecoverable loss of legitimately-held state due to one party's action tipping a shared threshold).

### Likelihood Explanation
The scenario is reachable purely by an unprivileged, non-malicious-node actor: a normal Vault API client submitting a request through the gateway. The chainlink repo's own smoke/regression test suite (`workflow-gateway-capabilities-don-vault-stall-purge.toml`, `pending_queue_stall_purge_test.go`) exists specifically to reproduce and validate this exact "oversized store-backed observation → stall → purge" flow, indicating it is a known, exercised code path rather than a theoretical corner case [7](#0-6) . The likelihood is higher when `VaultOptimizationsEnabled=false` (a supported, tested configuration) since that path enforces "must observe all items," making a single oversized item enough to stall the whole queue.

### Recommendation
Rather than purging the entire pending queue on stall, isolate and remove/skip only the specific request(s) that cannot be validly observed (e.g., those exceeding `VaultMaxObservationSizeLimit`), and preserve all other queued requests for normal processing. If a full-queue purge is retained as a fallback safety valve, add a governance/manual-recovery path (mirroring the Reserve Protocol's mitigation of a manually-triggered `beginEra()`), or emit compensating events so affected clients can resubmit without silent, ambiguous data loss. Additionally, tighten ingress-time validation so a ciphertext that will exceed `VaultMaxObservationSizeLimit` once wrapped into a store-backed `Observation` is rejected at admission time rather than being allowed into the shared pending queue at all.

### Proof of Concept
1. Deploy with `VaultOptimizationsEnabled=false`, a small `VaultPendingQueueStallThreshold` (e.g., `3`), a tight `VaultMaxObservationSizeLimit` (e.g., `4kb`), and a larger `VaultCiphertextSizeLimit` (e.g., `8kb`) — exactly the configuration shipped in `workflow-gateway-capabilities-don-vault-stall-purge.toml` [8](#0-7) .
2. As an unprivileged Vault client, submit a `CreateSecrets`/similar request whose ciphertext is under 8kb (passes gateway ingress) but whose resulting store-backed `Observation` exceeds 4kb.
3. Have another unprivileged client submit a normal, valid secret request that enters the same shared pending queue.
4. Over consecutive rounds, the oversized item can never be legally observed under the "must observe all items" rule; `pendingQueueStallTracker` increments each round via `Observation()` [9](#0-8) .
5. Once `f+1` nodes signal stall, `StateTransition` calls `purgeStalledPendingQueue`, wiping the entire pending queue including the second client's legitimate, unrelated request [3](#0-2) .
6. The second client's request is lost and must be resubmitted, despite having done nothing wrong — demonstrating the same "small trigger crosses a threshold, wiping out a large pool of legitimately held state" pattern as the original StRSR finding.

func (r *ReportingPlugin) purgeStalledPendingQueue(
	ctx context.Context,
	l logger.Logger,
	store pendingQueueStore,
	stallSignalCount int,
) (ocr3_1types.ReportsPlusPrecursor, error) {
	if err := store.WritePendingQueue(ctx, nil); err != nil {
		return ocr3_1types.ReportsPlusPrecursor{}, fmt.Errorf("could not purge stalled pending queue: %w", err)
	}
	r.metrics.trackPendingQueueWrittenSize(ctx, 0)
	r.metrics.trackPendingQueuePurge(ctx)
	l.Warnw("purged stalled pending queue after f+1 stall signals",
		"stallSignalCount", stallSignalCount,
		"threshold", r.onchainCfg.F+1,
	)
	ospb, err := proto.MarshalOptions{Deterministic: true}.Marshal(&vaultcommon.Outcomes{})
	if err != nil {
		return ocr3_1types.ReportsPlusPrecursor{}, fmt.Errorf("could not marshal empty outcomes after pending queue purge: %w", err)
	}
	return ocr3_1types.ReportsPlusPrecursor(ospb), nil
}

func (r *ReportingPlugin) shouldPurgePendingQueue(ctx context.Context) bool {
	if gateAllows(ctx, r.lggr, r.cfg.VaultForceEmptyOCRRounds, "VaultForceEmptyOCRRounds") {
		return true
	}
	stallThreshold, err := r.cfg.VaultPendingQueueStallThreshold.Limit(ctx)
	if err != nil {
		r.lggr.Errorw("could not fetch pending queue stall threshold", "error", err)
		return false
	}
	if stallThreshold == 0 {
		return false
	}
	// The pending queue must never be purged with fewer than 2f+1 stall
	// signals, regardless of the configured stall threshold.
	if stallThreshold < 2*r.onchainCfg.F+1 {
		stallThreshold = 2*r.onchainCfg.F + 1
	}

	stalledObservationCount := r.pendingQueueStallTracker.getCount()
	return stalledObservationCount >= stallThreshold
}
