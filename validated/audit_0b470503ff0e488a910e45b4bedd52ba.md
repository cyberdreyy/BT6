### Title
Loss-adjusted withdraw receipt is repaid at par when a newer request moves `lastWithdrawRequest` past the haircut epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` locates a user's loss-adjusted receipt exclusively through `lastWithdrawRequest[_user]`. When a borrower underpays pending receipts via `collectWithdrawFunds`, the haircut is stored in `lossRecoveryPriceByEpoch[epochNumber]` and `pendingWithdraws` is zeroed, but each user's full claim basis remains in `withdrawsRequests[_user]`. If the user files any subsequent withdraw request, `lastWithdrawRequest` moves to the newer epoch, the loss-adjusted path silently returns 0, and `_claimFundedWithdrawRequest` then pays the entire aggregate — including the haircut receipt — at par from strategy reserves, even though the borrower only funded the reduced amount.

### Finding Description
In `collectWithdrawFunds`, when `_amount < pendingWithdraws`, the strategy stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and sets `pendingWithdraws = 0`, while pulling only `_amount` underlying (IdleCreditVault.sol:411-430). Each user's unpaid remainder survives inside `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][epoch]`.

On claim, `claimWithdrawRequest` (IdleCreditVault.sol:301-314) runs `_claimLossAdjustedWithdrawRequest`, which reads `lossEpoch = lastWithdrawRequest[_user]` and returns 0 if `lossRecoveryPriceByEpoch[lossEpoch] == 0` (lines 789-795). `_clearWithdrawClaimForEpoch` only clears the single keyed epoch (lines 811-837). A user who had a receipt haircut in epoch N can then call `requestWithdraw` in epoch N+1 (explicitly allowed per the NOTE at lines 323-324), which sets `lastWithdrawRequest[_user] = N+1`. Since `lossRecoveryPriceByEpoch[N+1] == 0`, the loss path is skipped entirely, and `_claimFundedWithdrawRequest` (lines 319-350) pays `withdrawsRequests[_user]` — which still contains the epoch-N basis at par — via `_transferFundedClaim` once `epochNumber > N+1`.

This is the use-after-free analog: the "freed" epoch-N haircut record becomes unreachable once `lastWithdrawRequest` is overwritten, but its underlying claim data is still consumed by the generic funded-claim path.

### Impact Explanation
The user receives `claimBasis_N + claimBasis_{N+1}` at par, while the strategy only received `_amount < pendingBasis` for epoch N and the epoch N+1 funding. The excess `(claimBasis_N - claimBasis_N * lossRecoveryPrice / RECOVERY_FULL)` is paid out of strategy-held underlying belonging to other funded claimants / recovery reserve / CDO-held liquidity, causing direct theft or insolvency proportional to the haircut applied. No privileged action is required: the attacker only needs a tranche position and one extra `requestWithdraw`.

### Likelihood Explanation
Requires a realized `stopEpochWithDuration`-style loss (honest manager call, allowed by scope) while the attacker has a pending receipt, plus a second `requestWithdraw` by the attacker — both ordinary unprivileged flows. The overwritten-pointer gap is deterministic; there is no guard keying `lossRecoveryPriceByEpoch` against anything other than `lastWithdrawRequest`, and no per-epoch iteration that would catch stale haircut epochs.

### Recommendation
Track loss-adjusted epochs per user (e.g., a `lossEpochs[_user]` set or a dedicated `lastLossEpoch[_user]` marker set in `collectWithdrawFunds`/`requestWithdraw`) and iterate/clear every epoch with a nonzero `lossRecoveryPriceByEpoch` before falling through to `_claimFundedWithdrawRequest`. Alternatively, subtract each user's unfunded remainder out of `withdrawsRequests[_user]` at loss-crystallization time so the funded aggregate can never contain a haircutted basis.

### Proof of Concept
Reproducible Foundry flow on `test/foundry/IdleCreditVault.t.sol` harness:

```solidity
function testLossAdjustedReceiptPaidAtParAfterNewRequest() external {
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // Epoch N: attacker requests withdraw of 10k.
    vm.prank(attacker);
    uint256 basis = cdoEpoch.requestWithdraw(0, address(AAtranche)); // 10_000e6 basis

    // Manager stops epoch with a realized loss; borrower funds only 60%
    // through stopEpochWithDuration -> collectWithdrawFunds(0.6 * pendingBasis).
    uint256 funded = basis * 60 / 100;
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0); // loss path -> lossRecoveryPriceByEpoch[N]=0.6
    // (use stopEpochWithDuration variant as in existing loss tests so
    //  collectWithdrawFunds is invoked with _amount < pendingBasis)

    // Epoch N+1: attacker files a second (small) request, moving
    // lastWithdrawRequest[attacker] = N+1, hiding the epoch-N haircut.
    _startEpochAndCheckPrices(0);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Let epoch N+1 end normally and be funded.
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // Claim: loss path sees lossRecoveryPriceByEpoch[N+1] == 0 and skips;
    // funded path pays withdrawsRequests[attacker] at PAR, including the
    // 40% haircut from epoch N that was never funded.
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - pre;

    // Attacker should have received 0.6*basis_N + basis_{N+1},
    // but receives basis_N + basis_{N+1}.
    assertEq(paid, basis /* + epoch N+1 basis */, 'haircut receipt repaid at par');
}
```

Expected result: `paid` exceeds the funded amount by the epoch-N haircut (40% of the epoch-N basis), drawn from strategy reserves owned by other claimants.
