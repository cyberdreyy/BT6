### Title
Stale confirmations from deleted multisig members allow requests to execute below the configured `num_confirmations` threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges the confirmation records for requests that were *originally added* by the member being removed. It never scans the `confirmations` map to strip out votes that the removed member cast on requests added by *other* members. Those stale votes remain counted toward `num_confirmations` in `confirm`, so a request can later be executed with fewer genuine, currently-authorized approvals than the threshold requires.

### Finding Description
The contract stores, per request, a `HashSet<String>` of member identifiers that have confirmed it: [1](#0-0) 

When a request is confirmed, the contract simply checks the *size* of that set against `num_confirmations`, without re-validating that every entry in the set still corresponds to a current member: [2](#0-1) 

Member removal (`DeleteMember`) is handled by `delete_member`, which only cleans up confirmations for requests that were *added* by the removed member — it does not touch confirmations that member left on *other* still-pending requests: [3](#0-2) 

So the binding that should hold — `confirmations.len() == number of currently-authorized live members who approved this request` — is broken. After a member is removed, `confirmations.len()` can still include that now-unauthorized identity, i.e. `live_authorized_votes < confirmations.len()`.

### Impact Explanation
This lets a `MultiSigRequest` (e.g. a `Transfer`, `AddKey`, `FunctionCall`, or even a further `DeleteMember`/`AddMember`) reach the execution threshold with fewer live, currently-trusted approvals than `num_confirmations` mandates. This directly matches the Critical criterion "a multisig request executed below threshold" — funds can be transferred, keys added, or governance actions executed with an effectively reduced quorum, undermining the entire security assumption of the multisig (k-of-n authorization).

### Likelihood Explanation
This does not require any privileged or malicious action beyond normal, expected multisig lifecycle operations:
1. A pending request is created and confirmed by one or more members (normal usage — pending requests routinely sit for the `REQUEST_COOLDOWN` window before they can even be deleted).
2. Membership rotation (removing a departing or compromised member) is a standard, expected multisig operation, not an edge case — precisely the situation `DeleteMember` is designed for.
3. Any time these two ordinary operations interleave (a member confirms a request, then is later removed while that same request is still pending), the stale vote silently persists.

Because this only requires ordinary contract usage (no attacker privilege escalation, no owner override, no malicious validator), the likelihood is high in any long-lived multisig that rotates members.

### Recommendation
When removing a member in `delete_member`, iterate over all entries in `self.confirmations` (not just requests added by that member) and remove the departing member's identifier from every confirmation set. Alternatively, validate at `confirm`-time (and before executing) that every identifier in the confirmation set still belongs to `self.members`, discarding/ignoring stale entries when computing the effective confirmation count.

### Proof of Concept
1. Deploy `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. Member `A` calls `add_request` with a malicious `Transfer`/`FunctionCall` action (request added, not yet confirmed — `confirmations = {}`).
3. Member `B` calls `confirm(request_id)` → `confirmations = {B}` (size 1, below threshold, so it's just stored).
4. Through the normal multisig process, the group later approves a `DeleteMember { member: B }` request to rotate `B` out. `delete_member` runs: since the pending `Transfer` request above was added by `A` (not `B`), `r.member == member` is false for it, so its confirmations set is left untouched — `B`'s stale vote remains inside `confirmations[request_id] = {B}` even though `B` is no longer in `self.members`.
5. Now only two more live members, `C` and `D`, need to call `confirm(request_id)`. After both: `confirmations.len() == 3` (`{B, C, D}`) which is `>= num_confirmations (3)`, so `execute_request` fires the `Transfer`.
6. The request executed with confirmations from only 2 genuinely live/authorized members (`C`, `D`) plus one stale vote from removed member `B` — one short of the intended 3-of-4 live-member threshold. [2](#0-1) [3](#0-2)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
