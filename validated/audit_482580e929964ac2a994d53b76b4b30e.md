### Title
Missing allowlist/rate-limit enforcement lets any unauthenticated gateway user fan out messages to the full DON - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The Flatmoney bug allowed a keeper to bypass a mandatory validation step (Pyth price update) by passing an empty array, letting them selectively skip an enforcement gate depending on what favored them. The Chainlink analog is in the gateway's `WebAPIHandler.HandleLegacyUserMessage`, which is documented to require allowlist and rate-limiting before forwarding user-submitted messages to DON nodes, but the enforcement itself is literally absent (`// TODO: apply allowlist and rate-limiting here`). This is an unprivileged-actor path: the gateway is internet-facing and `HandleLegacyUserMessage` is invoked for every external "legacy" user message per the `Handler` interface contract [1](#0-0) .

### Finding Description
`HandleLegacyUserMessage` decodes the untrusted `api.Message` payload, checks payload decoding, checks for a non-zero timestamp, and checks message staleness against `MaxAllowedMessageAgeSec` — but right after those checks, instead of enforcing an allowlist/subscription and rate limit on the sender, the code has an explicit `TODO` and proceeds straight to validating the method name and forwarding the request to every member of the DON: [2](#0-1) 

Unlike the node-to-gateway path (`HandleNodeMessage`/rate limiter in `nodeRateLimiter`, seen in the handler's other message flows) and the `Vault` capability's `GatewayHandler`, which wires an explicit `Authorizer`/allowlist chain before processing requests (`NewAllowListBasedAuth`, `NewAuthorizer`) [3](#0-2) , the legacy web-API user message path has no equivalent authorization/allowlist/quota gate. Any caller reaching the gateway's user-message ingress can submit a `MethodWebAPITrigger` message with an arbitrary `Sender`/payload, and it will be dispatched to `don.SendToNode` for all DON members with no allowlist, subscription, or per-sender/global rate-limit check applied at this call site.

### Impact Explanation
This mirrors the Flatmoney root cause in spirit: an explicitly-required protective check (there, mandatory price update; here, mandatory allowlist/rate-limit) is not actually enforced, leaving the door open for any unprivileged party to abuse the bypassed path. Concretely, this allows:
- Unauthorized triggering of DON-wide message fan-out (`SendToNode` to every `donConfig.Members`) by non-allowlisted senders, i.e., an allowlist/quota bypass on the internet-facing gateway.
- Resource-exhaustion / spam potential against the entire DON node set since no per-sender/global throttling is applied before dispatch, unlike the node-message and Vault paths that do have such checks.

This satisfies the "concrete allowlist or quota bypass" acceptance criterion for the internet-facing gateway.

### Likelihood Explanation
High likelihood: the missing check is unconditional (not behind a flag) and sits directly in the mainline `HandleLegacyUserMessage` flow that is reachable by any external client hitting the gateway's legacy user-message endpoint; no privileged role or node identity is required to exercise it. The `TODO` comment itself documents that this is a known gap rather than a hypothetical one.

### Recommendation
Apply the allowlist/subscription check and per-sender/global rate limiting to `msg.Body.Sender` (and DON/workflow selector, as applicable) before decoding/dispatching the request in `HandleLegacyUserMessage`, mirroring the pattern already used for `Vault`'s `Authorizer`/allowlist chain and the existing `nodeRateLimiter` used elsewhere in this handler. Reject (via `callback.SendResponse` with an appropriate error code) any message from a sender that is not allowlisted or that exceeds rate limits, prior to invoking `don.SendToNode`.

### Proof of Concept
Not applicable in ask-only mode (no code execution available). Conceptually: send a well-formed `api.Message` (valid signature per `Message.Validate()`, non-zero `Timestamp`, method `web_api_trigger`) from any address to the gateway's legacy HTTP/JSON-RPC ingress that is not present in any DON allowlist; observe that `HandleLegacyUserMessage` still forwards the request to every node in `donConfig.Members` [4](#0-3)  because no allowlist or rate-limit rejection path exists between the staleness check and dispatch.

	job.ServiceCtx

	// Each user request is processed by a separate goroutine, which:
	//   1. calls HandleUserMessage
	//   2. waits on callbackCh with a timeout
	HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback Callback) error

	// Each user request is processed by a separate goroutine, which:
	//   1. calls HandleUserMessage
	//   2. waits on callbackCh with a timeout
	HandleJSONRPCUserMessage(ctx context.Context, jsonRequest jsonrpc.Request[json.RawMessage], callback Callback) error

	// Handlers should not make any assumptions about goroutines calling HandleNodeMessage.
	// should be non-blocking
	// should validate the message inside the response
	HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error

	// The methods support by this Handler.
	// Should be globally unique across all handlers.
	Methods() []string
}
