### Title
Claimed instant-withdraw receipts remain in `instantWithdrawClaimsByEpoch`/`instantWithdrawsRequestsByEpoch`, inflating the default-recovery basis and reserve so recovery payouts exceed actual funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The kernel bug is a type-confusion: an object allocated as the smaller `plock_op` is later cast to the larger `plock_xop` because no flag distinguishes the two. The analog in `IdleCreditVault` is a ledger-confusion: an instant-withdraw receipt that has already been fully claimed and burned via `claimInstantWithdrawRequest` is still recorded in the per-epoch ledgers `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch`. At default finalization those ledgers are treated as "still-pending receipts" and folded into both `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, so the recovery price is computed over claims that were already paid at par. The reserve is nominal, not real — the last defaulted claimants' transfers revert or are underpaid.

### Finding Description
When a user claims an instant withdrawal, `claimInstantWithdrawRequest` burns `instantWithdrawsRequests[_user]`, zeroes the aggregate ledger, and pays the user via `_transferFundedClaim` — but it never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [1](#0-0) 

Those per-epoch entries are only cleared inside `_claimDefaultedInstantWithdrawRequest`, i.e. only for receipts still pending at finalization [2](#0-1) .

At default, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` — i.e. whenever the instant queue was only partially funded [3](#0-2) . Symmetrically, `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` and treats that difference as underlying already held by the strategy, adding it to `reserveAmount` in `finalizeDefaultRecovery` [4](#0-3) [5](#0-4) .

An attacker's already-claimed amount `X` is counted in `instantBasis` even though the `X` underlyings left the strategy. Both `totalBasis` and `reserveAmount` are inflated by `X`, so `recoveryPrice` is near-correct but the contract only holds `reserveAmount - X`. `claimInstantWithdrawRequest` has no epoch gating — it pays out of the strategy's underlying balance whenever funds are available — so a user can legitimately claim early while the rest of the epoch's instant queue remains unfunded (`pendingInstantWithdraws > 0`).

### Impact Explanation
After `finalizeDefaultRecovery`, total entitled payouts equal `recoveryPrice * basis ≈ reserveAmount`, but real holdings are `reserveAmount - X`. Every defaulted instant claimant's `_claimDefaultedInstantWithdrawRequest` does `_burn` then `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` and transfers real tokens [6](#0-5) . Once the phantom `X` of reserve is reached, subsequent claims revert on the ERC20 transfer — permanent freezing of up to `X` of recovery funds belonging to honest defaulted users, or equivalently an `X` insolvency in the recovery reserve. `X` is bounded by the epoch's instant-withdraw volume, which can be the full instant queue.

### Likelihood Explanation
Requirements: (1) instant withdrawals enabled (normal `IdleCDOEpochVariant` with `allowInstantWithdraw`); (2) the CDO partially funds instant requests via `collectInstantWithdrawFunds` (leaving `pendingInstantWithdraws > 0`) while some users claim from already-collected funds — the claim path has no gating on funding completeness; (3) the borrower defaults in the same epoch, triggering `finalizeDefaultRecovery` while `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` [7](#0-6) . All attacker steps (request instant withdraw, claim early) are unprivileged user actions; the honest manager/borrower steps are ordinary epoch operations. No existing guard removes claimed receipts from the per-epoch ledgers, and `_transferFundedClaim`'s reserve guard does not apply pre-finalization.

### Recommendation
Decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` inside `claimInstantWithdrawRequest` when the claimed amount is paid (tracking the request epoch, e.g. via a per-user last-instant-request marker or by clearing per-epoch entries on claim), so only genuinely pending receipts enter `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`. Alternatively, snapshot the prefunded reserve from actual underlying balance rather than `instantBasis - pendingInstant`.

### Proof of Concept
Foundry fork/harness sketch (mirroring `test/foundry/IdleCreditVault.t.sol` setup):

```solidity
function testClaimedInstantReceiptInflatesDefaultBasis() external {
    // AA deposits, epoch 0 stops, epoch 1 starts; apr drops so instant withdraws enabled
    uint256 req = cdoEpoch.requestInstantWithdraw(amount, user1); // user1
    cdoEpoch.requestInstantWithdraw(amount, user2);

    // CDO partially funds instant queue: collectInstantWithdrawFunds(amount) for user1 only
    // (pendingInstantWithdraws stays == amount for user2)
    vm.prank(user1);
    cdoEpoch.claimInstantWithdrawRequest(); // user1 paid at par

    // assert: instantWithdrawsRequestsByEpoch[user1][epoch] still == amount
    // assert: instantWithdrawClaimsByEpoch[epoch] still == 2*amount

    // borrower defaults within epoch -> finalizeDefaultRecovery(...)
    // basis = pendingWithdraws + 2*amount  (should be amount)
    // prefundedReserve = 2*amount - pendingInstant  (double counts user1's paid funds)
    // user2's _claimDefaultedInstantWithdrawRequest / later claimants revert
    // on safeTransfer: reserve was spent on phantom basis
}
```

Uncertainty: the exact CDO-side sequencing for partial instant funding (`getInstantWithdrawFunds`/`_getInstantFunds` helpers) and whether a default can be triggered mid-epoch after instant requests were filed in the same epoch needs confirmation against `IdleCDOEpochVariant.stopEpochWithDuration`/`_handleBorrowerDefault`, which I did not fully trace; if defaults only finalize after `pendingInstantWithdraws` is zeroed, the inflated-basis path would not be reachable and this reduces to a no-finding.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
