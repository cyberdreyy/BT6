### Title
Claimed instant-withdraw receipts remain counted in `instantWithdrawClaimsByEpoch`, inflating the default-recovery basis and draining the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays out a funded instant-withdraw receipt but never clears `instantWithdrawsRequestsByEpoch[user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. If the borrower defaults in the same epoch after some instant receipts were already funded and claimed, `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` still count those already-paid amounts as pending claim basis and as "prefunded reserve". The finalized `defaultRecoveryPrice` is therefore computed on phantom basis/backing, diluting every real recovery claimant and potentially exhausting `defaultRecoveryReserve` before all claims are paid.

### Finding Description
Instant withdraw receipts are tracked per epoch in `instantWithdrawClaimsByEpoch` (incremented at `requestInstantWithdraw`, line 371-372). The funded claim path only zeroes `instantWithdrawsRequests[_user]` and burns the receipt; the per-epoch aggregates are left stale (lines 387-392). Only the *defaulted* claim path decrements `instantWithdrawClaimsByEpoch` (line 853).

At default finalization:

- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` — including receipts already claimed — to the basis (lines 644-649).
- `_defaultPrefundedInstantReserve` counts `instantBasis - pendingInstant` as underlying already held for those claims (lines 716-723). Claimed receipts were already paid out, so this "prefunded" amount no longer exists in the contract but is still added into `reserveAmount` (line 686).
- `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (line 688) is then priced against a denominator and numerator that both include the phantom claimed amount — but only the numerator error is partially self-canceling; the claimed user's basis is still counted in `totalBasis` while their underlying is gone, so the real recovery per unit of legitimate basis is lower than intended, and the mint/burn applied to the CDO's active balance (lines 699-705) crystallizes a wrong haircut.

Sequence (running epoch, instant mode):

1. Attacker (any KYC'd lender/tranche holder) calls `requestInstantWithdraw` via the CDO; `instantWithdrawClaimsByEpoch[N] += amount`.
2. Honest `stopEpoch`/`collectInstantWithdrawFunds` funds the request; `pendingInstantWithdraws` decreases but `instantWithdrawClaimsByEpoch[N]` does not.
3. Attacker calls `claimInstantWithdrawRequest` and receives underlying at par. `instantWithdrawClaimsByEpoch[N]` still holds the claimed amount.
4. Later in the same epoch (instant receipts can persist across the epoch if partially funded, or a subsequent `stopEpochWithDuration`/default path leaves epoch number unchanged until bump), the borrower defaults; manager/owner call `_handleBorrowerDefault`/`finalizeDefaultRecovery`.
5. `finalizeDefaultRecovery` computes basis and reserve including the already-claimed amount → overstated `prefundedReserve` and `totalBasis`, understated effective payout per real claim.
6. When other claimants call `claimWithdrawRequest`/`claimInstantWithdrawRequest`, `_transferDefaultRecovery` decrements `defaultRecoveryReserve` (line 915) that was never fully backed → last claimants revert or are underpaid; the attacker already extracted full value.

### Impact Explanation
Direct mispricing of the default recovery waterfall: legitimate pending receipt holders and active LPs (whose NAV is crystallized via `_burn`/`_mint` at line 701-705) absorb a diluted recovery ratio, while early claimants received par. Quantified loss ≈ `claimedInstantBasis` worth of phantom backing spread over `totalBasis`; recovery claimants lose `claimedInstantBasis * recoveryPrice / totalBasis` each pro-rata, and the tail claimant can face a reserve shortfall causing permanent revert (permanent freezing of unclaimed recovery).

### Likelihood Explanation
Requires: instant withdrawals enabled (`setInstantWithdrawParams`), at least one funded-and-claimed instant receipt, unfunded instant or pending basis remaining in the same epoch, and a borrower default before the epoch number moves. Borrower default is honest-role behavior explicitly in scope, and instant-withdraw flows are a supported vault mode. No privileged malicious action needed.

### Recommendation
In the funded claim path of `claimInstantWithdrawRequest`, clear the per-epoch entries: set `instantWithdrawsRequestsByEpoch[_user][<epoch>]` to 0 and decrement `instantWithdrawClaimsByEpoch[<epoch>]` by the claimed amount. Because the aggregate `instantWithdrawsRequests[_user]` loses epoch attribution, track the request epoch (e.g., `lastInstantWithdrawRequest[_user]` or reuse the per-epoch mapping) symmetric to `lastWithdrawRequest`, mirroring the cleanup already done for defaulted claims at line 847-853.

```solidity
// test/foundry/IdleCreditVault.t.sol style fork test

//    -> instantWithdrawClaimsByEpoch[N] == amount
// 3. Honest stopEpoch funds instant bucket:
//    deal(underlying, borrower, needed); vm.warp(epochEnd+1);
//    cdoEpoch.stopEpoch(apr, interest) -> collectInstantWithdrawFunds
// 4. Attacker: cdoEpoch.claimInstantWithdrawRequest()
//    assertEq(strategy.instantWithdrawClaimsByEpoch(N), amount); // STALE - bug
//    assertEq(strategy.instantWithdrawsRequests(attacker), 0);
// 5. Other user opens instant/withdraw request in epoch N (still unfunded)
// 6. Borrower defaults: underfund borrower, stopEpoch -> defaulted()
//    owner -> finalizeDefaultRecovery(recovered, source)
// 7. Observed: defaultRecoveryPrice computed with claimed amount still in
//    basis and counted as prefundedReserve; sum of all legitimate claims >
//    defaultRecoveryReserve -> last _transferDefaultRecovery reverts or
//    recovery price is depressed by claimedAmount / totalBasis.
```

Note: step 5-6 requires verifying that the vault's epoch numbering keeps the claimed receipt's epoch equal to `epochNumber` at finalization (i.e., the default occurs in the same epoch as the claim, or `instantWithdrawClaimsByEpoch` entries persist until a default in their request epoch). This epoch-timing condition is the part I could not fully verify against `IdleCDOEpochVariant`'s `epochNumber` bump semantics within the available budget; the missing decrement itself is unambiguous.
