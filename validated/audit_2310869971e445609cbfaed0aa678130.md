### Title
Stale confirmations from a deleted multisig key still count toward `num_confirmations`, allowing execution below current live-member threshold - ([File: multisig/src/lib.rs])

### Summary
`MultiSigContract::confirm` decides whether a request is ready to execute purely by counting the size of the `confirmations: HashSet<PublicKey>` bag stored for that `request_id`, without checking whether each public key in that bag is still a valid access key on the account. When a member's key is removed via a `DeleteKey` request, the code only purges *requests that key had authored* — it never scans other pending requests' `confirmations` sets to strip that key out. A stale confirmation left behind by a since-removed key can therefore still be counted toward the threshold of a later-completed request, letting it execute with fewer truly-live confirmers than `num_confirmations`.

### Finding Description
The broken binding: for an executed request, `confirmations_recorded_for(request_id) == num_confirmations` should imply `num_confirmations` **currently valid** keys approved it. The code only guarantees the count, not the validity of each entry at execution time.

- `confirm()` bumps the bag and checks `confirmations.len() as u32 + 1 >= self.num_confirmations` before calling `execute_request` [1](#0-0) . There is no re-check that every `PublicKey` already stored in `confirmations` is still an access key on the account.
- `MultiSigRequestAction::DeleteKey` handling, when a `DeleteKey` request executes, removes only the *outstanding requests authored by* the deleted key (`r.signer_pk == pk`) and the `num_requests_pk` counter — it never walks other requests' `confirmations` sets to drop the deleted key from them [2](#0-1) .
- Consequently, if key `B` already confirmed pending request `R` (added by `A`) before `B` is removed via a separate, fully-confirmed `DeleteKey{public_key: B}` request, `R`'s `confirmations` set still contains `B`'s (now-defunct) entry. When a still-valid key `C` later confirms `R`, the count `len()+1 >= num_confirmations` can be satisfied using `A`, stale-`B`, and `C` — i.e., only 2 genuinely live keys — and `execute_request` fires, e.g. releasing a `Transfer` amount out of the multisig account.
- No guard in the contract (`assert_valid_request`, `assert_self_request`, `assert_one_action_only`) revalidates confirmer identities against current access keys; membership in this design is implicit in "holds an access key on the account," and the contract has no mechanism to prune stale confirmer entries from unrelated pending requests when a key is deleted.

Note: the exploit does not require the removed key to call `confirm()` again after removal (that call would fail at the NEAR protocol level once the access key is deleted). The vulnerability instead is that the removed key's *earlier, legitimately recorded* confirmation persists and is later combined with confirmations from currently-valid members to cross the threshold.

### Impact Explanation
A pending `Transfer` (or any other) request can execute moving NEAR out of the multisig account while carrying fewer live approvals than `num_confirmations` mandates, i.e. exactly the Critical category "a multisig request executed below `num_confirmations` live members." This is repeatable for any pending request that has partial confirmations at the time a confirmer's key is removed, and for any multisig deployed from this contract's factory.

### Likelihood Explanation
Preconditions: a multisig with `num_confirmations >= 3` (or any threshold > 2 so a gap exists between partial and full confirmation), a pending request partially confirmed by a key that is subsequently removed via a separate `DeleteKey` request, and a later confirm by a still-valid key. All actions are ordinary multisig operations (`add_request`, `confirm`, `DeleteKey`) — no special privilege beyond being a current key holder at the time actions are taken, and no cost beyond gas. This is a design/bookkeeping gap rather than a rare edge case, and is deterministically reproducible.

### Recommendation
When executing a `DeleteKey` action, iterate over all entries in `self.confirmations` (not just requests authored by the deleted key) and remove the deleted public key from every confirmation set; alternatively, revalidate at execution time (inside `confirm`, before calling `execute_request`) that every public key present in the request's `confirmations` set still corresponds to an existing access key / has not been removed, discounting stale entries from the threshold count.

### Proof of Concept
```rust
#[test]
fn test_stale_confirmation_survives_key_deletion() {
    let amount = 1_000;
    let pk_a = vec![1u8; 33];
    let pk_b = vec![2u8; 33];
    let pk_c = vec![3u8; 33];
    let pk_d = vec![4u8; 33];

    testing_env!(context_with_key(pk_a.clone(), amount));
    let mut c = MultiSigContract::new(3);

    // R: transfer request authored & confirmed by A -> confirmations = {A}
    let r_id = c.add_request_and_confirm(MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    });

    // B confirms R -> confirmations = {A, B}, 2 < 3, not executed
    testing_env!(context_with_key(pk_b.clone(), amount));
    c.confirm(r_id);
    assert_eq!(c.confirmations.get(&r_id).unwrap().len(), 2);

    // D adds + A, C confirm a DeleteKey(B) request, which executes and deletes B's key
    testing_env!(context_with_key(pk_d.clone(), amount));
    let del_id = c.add_request_and_confirm(MultiSigRequest {
        receiver_id: alice(),
        actions: vec![MultiSigRequestAction::DeleteKey {
            public_key: Base58PublicKey::try_from(pk_b.clone()).unwrap(),
        }],
    });
    testing_env!(context_with_key(pk_a.clone(), amount));
    c.confirm(del_id);
    testing_env!(context_with_key(pk_c.clone(), amount));
    c.confirm(del_id); // 3rd confirmation -> DeleteKey executes, B's key gone

    // Assert R's confirmations still contain the stale B entry (DeleteKey only purged
    // requests authored by B, not confirmations B left on other requests)
    assert_eq!(c.confirmations.get(&r_id).unwrap().len(), 2);

    // C confirms R -> len(2)+1 = 3 >= num_confirmations(3) -> executes with only
    // 2 truly live approvers (A, C); B's stale confirmation counted toward the threshold
    testing_env!(context_with_key(pk_c.clone(), amount));
    c.confirm(r_id);
    assert!(c.requests.get(&r_id).is_none()); // R executed / transfer promise scheduled
}
```
This demonstrates `R` executing (Transfer promise scheduled) with only `A` and `C` as live confirmers while `num_confirmations == 3`, violating the intended `confirmations == num_confirmations` live-member binding.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
