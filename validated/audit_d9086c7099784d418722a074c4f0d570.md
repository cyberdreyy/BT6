### Title
v1 `validate_tenure_change_payload` uses global-only duplicate check, allowing a signer to sign two conflicting tenure-start blocks - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
`SortitionsView::validate_tenure_change_payload` in the v1 chainstate module checks for a prior signed block in the current tenure via `signer_db.get_last_globally_accepted_block(...)`, whereas the v2 implementation deliberately checks `signer_db.get_last_signed_block(...)` (which also covers locally-accepted-but-not-yet-globally-accepted blocks). Because a locally accepted block carries this signer's own signature, v1's weaker check lets the same signer sign a second, conflicting tenure-start block for the same tenure whenever the first one never reached global (threshold) acceptance.

### Finding Description
The equality that must hold is: for a given tenure T, the number of distinct `signer_signature_hash` values this signer signs for T's first (tenure-start) block must be ≤ 1.

In `stacks-signer/src/chainstate/v1.rs`, `validate_tenure_change_payload` performs the duplicate-tenure-start check with: [1](#0-0) 
This only returns `Some(...)` (and thus `Err(RejectReason::DuplicateBlockFound)`) when a block in this tenure has reached *global* acceptance. If the signer merely locally accepted (signed) block A for tenure T but the signature threshold was never reached, `get_last_globally_accepted_block` returns `None`, and the function proceeds to `Ok(())`, permitting the signer to sign a second tenure-start block B for the same tenure.

By contrast, v2's equivalent code explicitly documents and fixes this gap: [2](#0-1) 
The v2 comment states plainly that "Only blocks we have signed (locally or globally accepted) count here: a block we have merely pre-committed to carries no signature from us, so it is safe to accept a competing tenure-start block in its place" — implying blocks that *are* signed (even locally) must block a competing tenure-start proposal. v1 lacks this correction.

Attack flow: an attacker who can win a miner slot (one BTC-based slot) or otherwise get a `BlockProposal` gossiped to a v1 signer can:
1. Propose tenure-start block A for tenure T; the victim signer locally accepts/signs A (but the network never reaches the global signature threshold for A, e.g., because other signers are split, slow, or the attacker only needs this one signer's contribution as part of a wider equivocation scenario).
2. Propose a second, distinct tenure-start block B for the same tenure T (same `consensus_hash`, different `signer_signature_hash`), also satisfying `check_tenure_change_confirms_parent` and `check_parent_tenure_choice`.
3. Because `get_last_globally_accepted_block` returns `None` (A was never globally accepted), the `DuplicateBlockFound` guard is bypassed, and the v1 signer signs B as well.

This breaks the per-signer, per-tenure uniqueness guarantee (no two different signature hashes signed by the same signer for the same tenure-start slot), which is exactly the guard v2 restored.

### Impact Explanation
This breaks the uniqueness/equivocation-guard safety property for tenure-start blocks under the v1 code path: chain safety can be violated because a single signer can contribute valid signatures to two mutually conflicting tenure-start blocks (A and B) for the same tenure. If this pattern is repeated across enough v1 signers (each of whom locally-but-not-globally accepted a first block), it becomes possible for two different sets of signers to independently cross their respective global thresholds for A and B, finalizing two competing chains for the same tenure — a critical chain-safety/equivocation failure. This matches the "Critical" category: a signer signing a conflicting block.

### Likelihood Explanation
Preconditions: the targeted signer must be running the v1 chainstate path, must have locally accepted (signed) a tenure-start block A without ever seeing it reach global acceptance, and a second conflicting tenure-start block B for the same tenure must satisfy the other checks (`check_tenure_change_confirms_parent`, `check_parent_tenure_choice`). Local-only (not globally) acceptance is a normal, frequent occurrence in practice — it happens whenever the network doesn't reach consensus quickly on the first proposal (network partition, competing miners, slow votes, etc.), so no privileged access is needed beyond an attacker's own miner slot and normal StackerDB/gossip message crafting, consistent with the unprivileged threat model. Because this only requires one signer's weight and standard message crafting, it is realistically triggerable and repeatable across tenures.

### Recommendation
In `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload`, replace the `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` call with `signer_db.get_last_signed_block(&block.header.consensus_hash)` (as done in v2), so that a block this signer has already locally accepted/signed in the tenure also blocks a competing tenure-start proposal from being signed.

### Proof of Concept
Rust signer test plan (in `stacks-signer/src/chainstate/tests/`, mirroring existing v1/v2 test harnesses):
1. Build a `SignerDb` and a v1 `SortitionsView` fixture with a sortition for tenure T.
2. Construct tenure-start block A for consensus hash T; call `signer_db.mark_block_signed_locally` / the local-acceptance path (the local-accept write, not the global-accept write) so `get_last_globally_accepted_block(T)` returns `None` while `get_last_signed_block(T)` returns `Some(A)`.
3. Construct a second, distinct tenure-start block B for the same consensus hash T (different `signer_signature_hash`), with a valid `TenureChangePayload` satisfying `check_tenure_change_confirms_parent` and `check_parent_tenure_choice`.
4. Call v1's `validate_tenure_change_payload(...)` for B against the signer_db state above and assert it returns `Ok(())` — demonstrating the gap.
5. Call v2's `validate_tenure_change_payload(...)` for the same fixture/state and assert it returns `Err(RejectReason::DuplicateBlockFound)` — demonstrating the v1/v2 inconsistency and confirming v2's guard is correct while v1's is not.
