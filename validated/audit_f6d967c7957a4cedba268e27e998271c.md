### Title
Stale in-memory `BlockInfo` snapshot clobbers a concurrently-promoted DB record in `process_pending_responses_for_block` - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`process_pending_responses_for_block` replays early-arriving pre-commits, rejections, and signatures for a freshly-proposed block using a *single* in-memory `block_info` value that is captured once, before the loop starts. Pending pre-commits are replayed through `handle_block_pre_commit`, which independently re-reads the row from `signer_db`, can promote it all the way to `LocallyAccepted` (self-signed) and persists that promotion — but it never updates the caller's `block_info` variable. The very next iteration of the same loop then hands that stale, un-promoted `block_info` to `store_and_process_block_rejection`/`store_and_process_block_signature`, which mutate and persist it, silently overwriting the just-established signed state. This is the direct analog of the Oj bug: a routine holds a "pointer" (`block_info`) into what it believes is the current state while a nested call reallocates/mutates the real backing store, and the routine goes on to use (and here, write back) the now-stale copy.

### Finding Description
`handle_block_proposal` builds a fresh `BlockInfo` for a newly-seen proposal, persists it, then calls: [1](#0-0) 

into `process_pending_responses_for_block`, which iterates the pending-response buckets collected by `drain_pending_block_responses` in this order — pre-commits, then rejections, then signatures — all against the *same* `&mut block_info` captured before the loop began: [2](#0-1) 

For each pending pre-commit, `handle_block_pre_commit` is invoked. Crucially, that function does **not** take `block_info` from the caller — it performs its own independent read of the row (`block_lookup_by_reward_cycle`), and if the pre-commit weight threshold is already satisfied by the replayed votes it can drive the block straight to `SIGN: mark_locally_accepted, handle_block_signature, broadcast acceptance`, persisting that state itself: [3](#0-2) [4](#0-3) 

That promotion (and the `signed_self` timestamp/signature it stamps) never flows back into the `block_info` variable still held by `process_pending_responses_for_block`. The loop's next bucket — pending rejections — is then processed against that same stale copy: [5](#0-4) 

Because the in-memory `block_info.state` still reads `Unprocessed`/`PreCommitted` (its value from before the pre-commit replay ran), the state-machine guard described in the docs — "local state is reachable from anything not yet global" — permits the transition to `LocallyRejected` on this stale copy. Persisting it (as every other handler in this file does, e.g. the identical `insert_block(&block_info)` pattern in `handle_block_validate_ok`) overwrites the DB row that `handle_block_pre_commit` had *just* set to `LocallyAccepted` with a real self-signature: [6](#0-5) [7](#0-6) 

The net effect: the signer has already broadcast a `BlockAccepted` (its own signature) via `handle_block_pre_commit`'s SIGN path, but the local `signerdb` record for that `signer_signature_hash` is stomped back to `LocallyRejected`/`Unprocessed` by the very next loop iteration. This is the equality the task is scoped to protect — "signed vs. validated" and the equivocation guard on the same `signer_signature_hash` — and it is broken purely by input (attacker-controlled ordering/timing of pre-commit vs. rejection/signature gossip that lands in the pending tables before the proposal itself arrives) plus the miner re-sending the same proposal, both of which a lone miner + gossip peer can trigger without needing a majority of signers.

### Impact Explanation
Once the on-disk record no longer reflects that this signer already signed the block, later logic that consults `signer_db` state (e.g. `should_reevaluate_block`, `determine_response`, `check_static_valid_block`/`valid.is_some()` early-outs in `handle_block_validate_ok`/`handle_block_validate_reject`) sees a block that looks "not yet decided," or explicitly rejected, when a real signature for it is already on the wire. On a later re-proposal or a conflicting sibling at the same height, the signer can re-evaluate and sign the conflicting block, having lost its own record that it already committed to the first one — this is the "losing the equivocation guard" outcome the rules call out as High impact, and depending on which state is clobbered can also manifest as a rejection silently discarding a valid acceptance record that other logic depends on for conflict detection (`get_signed_conflicts`), undermining the reorg-permit / conflict-still-blocks logic in `handle_block_pre_commit`'s later section.

### Likelihood Explanation
This requires only: (1) a miner re-proposing the same block after some signers already pre-committed/voted (an ordinary, already-anticipated path — `should_reevaluate_block`/re-proposal handling exists specifically for this), and (2) at least one pre-commit vote for the block arriving and being queued in the pending tables *before* the proposal itself is seen by this signer, so that `drain_pending_block_responses` returns a non-empty `pre_commits` bucket alongside rejections/signatures. Both conditions are ordinary gossip-timing occurrences reachable by a single miner (re-broadcasting) plus normal signer-to-signer StackerDB traffic — no majority or privileged key is needed.

### Recommendation
`process_pending_responses_for_block` must not carry a single stale `block_info` value across heterogeneous pending-response processing. After each call that can mutate the persisted row for the same `signer_signature_hash` (in particular after each `handle_block_pre_commit` call in the pre-commit loop), re-read the row from `signer_db` before proceeding to the rejection/signature buckets, or restructure `store_and_process_block_rejection`/`store_and_process_block_signature` to always fetch-then-mutate-then-persist against the current DB row rather than an externally-supplied `&mut BlockInfo` that may already be stale.

### Proof of Concept
1. Miner proposes block `B` to signer set; before signer `S` observes the proposal itself, two other signers' `BlockPreCommit(B)` messages plus one signer's stale `BlockResponse::Rejected(B)` (queued from a prior, now-irrelevant round) arrive and land in `S`'s pending tables via `add_pending_block_pre_commit_response` / rejection pending storage.
2. `S`'s weight for those pre-commits alone already meets `compute_voting_weight_threshold` (e.g., small signer set).
3. `S` finally receives the `BlockProposal` for `B`; `handle_block_proposal` builds a fresh `BlockInfo`, persists it, and calls `process_pending_responses_for_block`.
4. In that call, the pre-commit bucket is replayed first: `handle_block_pre_commit` re-reads the fresh row, finds the threshold met, and drives it to `mark_locally_accepted` + broadcasts `S`'s own `BlockAccepted` — persisted to `signer_db`.
5. The loop then processes the pending rejection bucket against the *original* stale `block_info` (still showing pre-promotion state), calling `store_and_process_block_rejection`, which marks it `LocallyRejected` and persists — overwriting the just-recorded `LocallyAccepted`/`signed_self` state.
6. Result: `S` has broadcast an acceptance signature for `B` that its own `signerdb` no longer records, breaking the local signed/validated equality and the equivocation guard for any subsequent conflicting proposal at the same height.

    fn process_pending_responses_for_block(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &mut BlockInfo,
        pending_responses: PendingBlockResponses,
    ) {
        let signer_signature_hash = block_info.block.header.signer_signature_hash();
        for stacker_address in pending_responses.pre_commits {
            debug!("{self}: Processing pending pre-commit.";
                "stacker_address" => %stacker_address,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_info.block.block_id(),
            );
            self.handle_block_pre_commit(
                stacks_client,
                sortition_state,
                &stacker_address,
                &signer_signature_hash,
            );
        }
        for (stacker_address, reject_reason) in pending_responses.rejections {
            debug!("{self}: Processing pending rejection.";
                "stacker_address" => %stacker_address,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_info.block.block_id(),
                "reject_reason" => ?reject_reason,
            );
            self.store_and_process_block_rejection(
                sortition_state,
                block_info,
                &stacker_address,
                reject_reason,
            );
        }
        let block_id = block_info.block.block_id();
        for (stackers_address, signature) in pending_responses.signatures {
            debug!("{self}: Processing pending signature.";
                "stacker_address" => %stackers_address,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_id,
            );
            self.store_and_process_block_signature(
                stacks_client,
                sortition_state,
                block_info,
                &stackers_address,
                &signature,
            );
        }
    }
