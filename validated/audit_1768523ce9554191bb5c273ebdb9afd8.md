### Title
Stale confirmations from removed multisig members are still counted toward quorum, allowing a request to execute below the required threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` counts entries in the `confirmations` `HashSet` for a request without ever re-validating that every confirming identity is still a current member. `delete_member` only purges confirmations for requests that the removed member itself *originated* (`r.member == member`), never confirmations that member cast on other members' requests. A confirmation cast by a member who is later removed therefore remains permanently counted toward `num_confirmations`, letting a request execute with fewer live, currently-authorized confirmers than the configured threshold.

### Finding Description
In `confirm`, the quorum check is purely a length comparison against the stored `confirmations` set: [1](#0-0) 

Membership removal is handled in `delete_member`, which walks `self.requests` and clears confirmations only for requests whose `MultiSigRequestWithSigner.member` equals the member being deleted (i.e. requests that member created), then removes the member from `self.members`: [2](#0-1) 

It never scans the `confirmations` map for *other* requests where the removed member had already cast a `confirm`. Those `HashSet<String>` entries (serialized `MultisigMember` strings) are left untouched, so they continue to count toward `confirmations.len() as u32 + 1 >= self.num_confirmations` in `confirm` even though that member is no longer in `self.members`.

This breaks the intended equality that the protocol relies on: `confirmations.len() == number of live members who approved this specific request`. After a member is deleted, the true count of *live* approvers for a still-pending request can be strictly less than `confirmations.len()`, yet the contract treats them as equal.

### Impact Explanation
This is a K-of-N authorization boundary. Multisig accounts commonly hold NEAR funds, and requests include `Transfer`, `AddKey`/`AddFullAccessKey`, `DeployContract`, `AddMember`, and `DeleteMember` actions, all executed once `confirm` deems quorum reached. If a stale confirmation from a departed member is counted, a request (e.g., a `Transfer` of the account's balance, or granting a full-access key) can be executed with fewer live, currently-authorized confirmations than `num_confirmations` mandates — i.e., "a multisig request executed below threshold." This directly enables unauthorized movement of NEAR held by the account or unauthorized privilege escalation (adding a full access key/new member) by a coalition smaller than the configured quorum.

### Likelihood Explanation
Exploitation only requires: (1) a member confirms a pending request they created or was created by someone else, (2) that confirming member is later removed via a legitimate `DeleteMember` request (a routine multisig maintenance action, e.g. rotating an old key), and (3) the original request is still pending and gets executed later with the remaining live members. No malicious deployment or foundation privilege is required — any normal churn in multisig membership while requests are outstanding can trigger this, and a colluding/soon-to-be-removed member could deliberately pre-confirm malicious requests before requesting their own removal.

### Recommendation
When a member is deleted in `delete_member`, iterate over all pending requests' `confirmations` sets (not just requests originated by that member) and remove the deleted member's serialized identity from each. Alternatively, when checking quorum in `confirm`, filter `confirmations` to only those entries still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new([A, B, C, D], 3)` (quorum = 3 of 4).
2. `C` calls `add_request` creating request `R` (e.g., `Transfer` of the account balance).
3. `A` calls `confirm(R)` → `confirmations[R] = {A}` (len 1, `1+1 < 3`, not executed).
4. `B` calls `confirm(R)` → `confirmations[R] = {A, B}` (len 2, `2+1 < 3`, not executed).
5. Separately, an already-approved `DeleteMember{member: B}` request executes (a normal maintenance action unrelated to `R`), removing `B` from `self.members`; `delete_member` only clears confirmations for requests where `r.member == B` (requests B created) — `R` was created by `C`, so `confirmations[R]` still contains `B`, per [3](#0-2) .
6. `D` (the only remaining live confirmer needed) calls `confirm(R)` → `confirmations[R].len() (2) + 1 >= 3` → quorum satisfied and `R` (the `Transfer`) executes, even though only `A` and `D` are live members who actually approved it (2 live approvals versus the required 3).

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
