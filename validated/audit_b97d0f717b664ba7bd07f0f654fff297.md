### Title
External initiators can trigger jobs by numeric job ID despite comment "EIs not allowed" - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates numeric (int32) job-ID execution behind `isUser` from `auth.GetAuthenticatedUser(c)`, intending to block external initiators from running jobs by int ID and require them to use UUID-based webhook triggers. However, `auth.AuthenticateExternalInitiator` injects a synthetic `User{Role: UserRoleRun}` into the same session key used by `GetAuthenticatedUser`, so `isUser` evaluates true for EI-authenticated requests too, defeating the intended restriction.

### Finding Description
In `Create`, the code first rejects UUID-formatted `idStr` (webhook job type removed) [4](#0-3) , then checks `isUser` before allowing `strconv.ParseInt`-based numeric job execution, with the comment "only users are allowed to run jobs using int IDs - EIs not allowed" [5](#0-4) . The route `POST /v2/jobs/:ID/runs` is mounted with `auth.Authenticate(..., auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` and `auth.RequiresRunRole` [1](#0-0) . `AuthenticateExternalInitiator`, upon validating the EI's access-key/secret headers, sets both `SessionExternalInitiatorKey` and `SessionUserKey` (the latter to a fabricated `User{Role: UserRoleRun}`) [2](#0-1) . Because `GetAuthenticatedUser` only checks for the presence of `SessionUserKey` [3](#0-2) , an EI-authenticated request satisfies `isUser == true` in `Create`, so the numeric-ID branch executes for EIs exactly as it would for a real user — the comment's intended restriction is not enforced by code. This is not actually about UUID-prefix collision or ordering of the `uuid.Parse` check (a plain numeric string like `"123"` never parses as a UUID, so that check is a non-issue); the real gap is that the `isUser` variable is not EI-aware.

### Impact Explanation
An external initiator credential holder (not an admin/edit-role user) can trigger arbitrary job runs on any job by numeric ID via `POST /v2/jobs/:ID/runs`, bypassing the intended restriction that only user sessions/API tokens may run jobs by int ID. This matches "unauthorized job run" — a job may perform on-chain actions (transactions, VRF fulfillment, OCR reporting triggers, etc.) depending on job type, so an EI could force execution of jobs it was never scoped to trigger, potentially causing unwanted fund movement or resource exhaustion via repeated job runs.

### Likelihood Explanation
Requires only a valid External Initiator access key/secret (the minimal EI credential), which is explicitly designed to be a low-privilege, narrowly-scoped credential distinct from full user sessions. Given that credential, the exploit is a single unauthenticated-role HTTP POST to `/v2/jobs/:ID/runs` with a numeric job ID and no dependency on database/host access — trivially repeatable.

### Recommendation
Make the numeric-ID gating explicitly reject External-Initiator-authenticated requests, e.g. check `auth.GetAuthenticatedExternalInitiator(c)` and reject if present, or have `AuthenticateExternalInitiator` set a distinguishable marker (not overload `SessionUserKey` with a role that satisfies `isUser` checks elsewhere) so `PipelineRunsController.Create` can differentiate real users from EIs.

### Proof of Concept
1. Handler-level integration test: register the same route group as production (`auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, `auth.AuthenticateBySession` then `auth.RequiresRunRole(prc.Create)`), create a valid `ExternalInitiator` record with known access key/secret in the test ORM.
2. Send `POST /v2/jobs/123/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to the EI's credentials and no session cookie / API token.
3. Assert the request reaches `prc.App.RunJobV2(ctx, int32(123), nil)` and returns `200`/pipeline-run resource instead of `422 "bad job ID"`.
4. Compare against a control test using a genuine "view"/"run" role user session to confirm identical code path is taken, proving `isUser` cannot distinguish the two, contrary to the code comment's intent.
