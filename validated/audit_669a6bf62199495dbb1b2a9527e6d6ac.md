### Title
Durable nonce authority changes do not invalidate pre-signed nonce transactions bound to the old authority, enabling delayed replay after an authority round-trip - (File: `programs/system/src/system_instruction.rs`)

### Summary
The system program's `authorize_nonce_account` instruction changes a durable nonce account's `authority` field without advancing the `durable_nonce` (stored blockhash) value [1](#0-0) . Nonce transaction validity in `validate_transaction_nonce` (SVM) and `check_nonce_transaction_validity` (bank) is determined dynamically against the *current* stored authority and durable-nonce value at inclusion time, not against a value bound at signing time [2](#0-1) [3](#0-2) . Because the durable-nonce hash is unaffected by authority rotation, a nonce transaction signed under authority `A` that fails validation (and is silently dropped, uncharged, non-consumed) while the authority is temporarily `B` can become valid and executable again if the authority is later reverted back to `A`, exactly mirroring the "key reuse" replay pattern described in the external report.

### Finding Description
A durable nonce account stores `(authority, durable_nonce, lamports_per_signature)`. Only `advance_nonce_account` and `withdraw_nonce_account` (on full withdrawal) change `durable_nonce`; `authorize_nonce_account` only swaps the `authority` field, confirmed by the unit test showing `final_nonce_data` retains the pre-authorization `initial_durable` value after `authorize_nonce_account` executes [4](#0-3) .

Nonce transaction admissibility is re-derived at each attempt from the account's *current* on-chain state: `validate_transaction_nonce` requires the stored `durable_nonce` to equal the message's `recent_blockhash`, and requires the current stored `authority` to be among the instruction's signers [2](#0-1) . There is no mechanism binding a durable-nonce transaction's validity to a specific authority "generation" — the check is purely: "does the on-chain authority right now match one of the tx's signers, and does the stored blockhash match." When a transaction fails this authority check it is simply dropped as `BlockhashNotFound`/`Discarded` — the fee is not charged and, critically, the `durable_nonce` value is **not consumed or advanced**, as shown by the `test_receive_and_buffer_nonce_dedup_validation_failure` "bad authority" case [5](#0-4)  and the batch-10 integration test where an old-authority nonce tx is `Discarded` after an authority change while the nonce hash is left untouched [4](#0-3) .

This is precisely the pattern flagged in the external report: a mutable "key" (here, the nonce `authority`) can be changed and later reverted while a separate piece of validity state (the durable-nonce hash) is left untouched, so a transaction that failed under an intermediate key state can become valid again once the key is rolled back — without any new user action or new signature.

### Impact Explanation
If a nonce authority is controlled by a service acting on a user's behalf (a common durable-nonce use case for session/hot-wallet keys, exchanges, or custodial signing infrastructure — analogous to Dharma's account-recovery-manager pattern), a user's pre-signed nonce transaction that "fails" and is presumed void when the authority is rotated away can silently become valid and broadcastable again if the authority is ever rotated back to the original key (intentionally, during key-rotation/incident-response, or maliciously by an attacker who gained authority-change rights). Because ordinary nonce accounts, `authorize_nonce_account`, and `advance_nonce_account` are all reachable via ordinary user transactions with no special validator privilege, an attacker who has recorded/observed a stale, previously-rejected signed nonce transaction can resubmit it for unauthorized execution (e.g., an unintended fund transfer) once the authority reverts, resulting in unauthorized state mutation.

### Likelihood Explanation
Exploitation requires: (1) a durable nonce account whose authority is changed away and later changed back to the same value without an intervening `advance_nonce_account`, and (2) an attacker who has retained a previously-signed, previously-invalid nonce transaction targeting that account. Authority round-trips are plausible in key-rotation, backup/restore, or multi-signer workflows for custodial/session-key setups, but require the operator to reuse a prior authority key rather than always rotating to a fresh one — a realistic but not universal operational pattern. This differs from typical single-use durable-nonce replay protection (which correctly prevents reuse once a nonce is *consumed* by a successful `advance_nonce_account`), so it requires specific authority-management practices to trigger.

### Recommendation
Bind nonce transaction acceptance to more than just the current `authority` value and stored blockhash: consider incorporating an authority-generation counter (incremented on every `authorize_nonce_account` call) into the value compared for advanceability, or require `authorize_nonce_account` to also advance `durable_nonce` (consuming any outstanding pre-signed transactions) whenever the authority changes, similar to how `withdraw_nonce_account` deinitializes state on full withdrawal [6](#0-5) . At minimum, document clearly for wallet/custodial integrators that authority rotation does not invalidate outstanding pre-signed nonce transactions and that authority values must never be reused.

### Proof of Concept
1. Create nonce account `N` with `authority = A`, `durable_nonce = H0` via `initialize_nonce_account`.
2. Sign (offline) transaction `T`: `[advance_nonce_account(N, A), transfer(...)]`, `recent_blockhash = H0`, signed by `A` and the fee payer.
3. Submit `authorize_nonce_account(N, A -> B)`; this executes successfully and leaves `durable_nonce = H0` unchanged, per `programs/system/src/system_instruction.rs:213-249` and the batch-10 test at `svm/tests/integration_test.rs:1941-1979`.
4. Submit `T`. It fails `validate_transaction_nonce`/`check_nonce_transaction_validity` because current `authority = B` is not among `T`'s signers; the tx is dropped as `BlockhashNotFound`, uncharged, and `durable_nonce` remains `H0`, matching the "bad authority" behavior in `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs:1605-1627`.
5. Later, submit `authorize_nonce_account(N, B -> A)`, reverting the authority; `durable_nonce` still remains `H0`.
6. Resubmit the previously-rejected `T`. It now again satisfies both checks (`durable_nonce == H0 == recent_blockhash`, current `authority == A ∈ signers`) and executes successfully, replaying a transaction the user/observer believed was permanently invalid.

pub(crate) fn authorize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Authorize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }
    match account
        .get_state::<Versions>()?
        .authorize(signers, *nonce_authority)
    {
        Ok(versions) => account.set_state(&versions),
        Err(AuthorizeNonceError::Uninitialized) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
        Err(AuthorizeNonceError::MissingRequiredSignature(account_authority)) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} must sign",
                account_authority
            );
            Err(InstructionError::MissingRequiredSignature)
        }
    }
}
