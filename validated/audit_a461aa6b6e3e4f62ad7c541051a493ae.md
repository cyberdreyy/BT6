### Title
Missing sender-to-DON membership check allows cross-DON routing of legacy gateway requests via attacker-controlled `body.don_id` - ([File: core/services/gateway/gateway.go])

### Summary
`gateway.ProcessRequest` routes legacy requests purely on the attacker-supplied `msg.Body.DonId` field, looking up `g.handlers[handlerKey]` and forwarding the request to that DON's handler/nodes without verifying that the message signer is a member of, or otherwise authorized for, that DON. The downstream `HandleLegacyUserMessage` implementation in the capabilities handler explicitly has no allowlist/sender check, so any holder of a valid keypair can direct a legacy request at any configured DON ID and have it forwarded to that DON's node set.

### Finding Description
In `ProcessRequest` (core/services/gateway/gateway.go:250-262), when `msg.Body.DonId != ""` the code treats the request as legacy, calls `msg.Validate()`, and then sets `handlerKey = msg.Body.DonId`, looking the handler up in `g.handlers[handlerKey]` with no further checks: [1](#0-0) 

`msg.Validate()` (core/services/gateway/api/message.go:54-88) only verifies the signature is well-formed and recovers the signer address from the signature over the message body — critically, `DonId` is part of the signed payload (`GetRawMessageBody` includes `alignedDonId`), so an attacker can freely choose *any* `DonId` value, sign the whole message (including that `DonId`) with their own private key, and produce a fully valid signature/message: [2](#0-1) [3](#0-2) 

Nothing in `Validate()` checks whether the recovered `Sender` is actually a member of, or otherwise entitled to reach, the DON named in `Body.DonId` — it only confirms the signature is internally consistent with the message contents the attacker chose.

Downstream, `handler.HandleLegacyUserMessage` (core/services/gateway/handlers/capabilities/handler.go:341-421) processes the message and forwards it to every member of the resolved DON (`h.donConfig.Members`) without any sender-authorization check. This is explicitly marked as a known gap in the code: [4](#0-3) 

and confirmed by an accompanying test-file TODO stating this validation is not yet implemented: [5](#0-4) 

Exploit flow: an attacker generates their own ECDSA keypair (no DON membership needed), builds an `api.Message` with `Body.DonId` set to a victim DON's ID and `Body.Method` set to `MethodWebAPITrigger`, calls `msg.Sign(attackerKey)` to produce a self-consistent valid signature, and submits it via `ProcessRequest`. `Validate()` passes because the signature matches the message the attacker crafted; `handlerKey` resolves to the victim DON's handler; the request is forwarded to that DON's nodes as a legitimate-looking trigger, with `Sender` recorded as the attacker's own address (not a spoofed identity, but an unauthorized cross-DON message).

### Impact Explanation
This allows an unprivileged actor holding only their own keypair to route/consume gateway capability requests (e.g., WebAPI triggers) against a DON they have no legitimate relationship with, consuming that DON's node resources, shared rate limits/quotas, and callback slots (`savedCallbacks`), and potentially triggering workflow executions on a foreign DON's nodes. This matches "unauthorized job run"/"allowlist bypass" impact classes — cross-tenant resource consumption and unauthorized capability invocation across DON boundaries.

### Likelihood Explanation
Fully feasible with zero privileges beyond generating a keypair and knowing a target DON ID (DON IDs/names are typically discoverable via configuration or public capability registry data). No membership, allowlist entry, or prior interaction with the victim DON is required. The path is deterministic and repeatable — every legacy request follows this exact same routing logic.

### Recommendation
Add sender-authorization/allowlist enforcement at the point `DonId` is used to select a handler: verify that the recovered `Sender` address is a registered/allowlisted member for the target DON (or is otherwise authorized to invoke that DON's capability) before forwarding, both in `gateway.ProcessRequest`/`msg.Validate()` and in `handler.HandleLegacyUserMessage`, resolving the outstanding `TODO: apply allowlist and rate-limiting here`.

### Proof of Concept
1. In a handler-level integration test (extending `handler_test.go`), configure two DONs/handlers: `victimDON` (with a configured allowlist/member set) and construct a message with `Body.DonId = "victimDON"` signed by a key that is **not** part of `victimDON`'s configuration.
2. Call `gateway.ProcessRequest` (or `handler.HandleLegacyUserMessage` directly) with this message.
3. Current behavior (bug): `msg.Validate()` succeeds, `handlerKey` resolves to `victimDON`'s handler, and `don.SendToNode` is invoked for each of `victimDON`'s members (assert via mock `don.On("SendToNode", ...)` invocation count > 0).
4. Expected/fixed behavior: the handler or gateway should reject the request with an authorization error (e.g., `api.UnauthorizedSenderError` or similar) and `don.SendToNode` should never be called.

// Message signatures are over the following data:
//  1. MessageId aligned to 128 bytes
//  2. Method aligned to 64 bytes
//  3. DonId aligned to 64 bytes
//  4. Receiver (in hex) aligned to 42 bytes
//  5. Payload (raw bytes before parsing)
func (m *Message) Sign(privateKey *ecdsa.PrivateKey) error {
	if m == nil {
		return errors.New("nil message")
	}
	rawData := GetRawMessageBody(&m.Body)
	signature, err := gw_common.SignData(privateKey, rawData...)
	if err != nil {
		return err
	}
	m.Signature = utils.StringToHex(string(signature))
	m.Body.Sender = strings.ToLower(crypto.PubkeyToAddress(privateKey.PublicKey).Hex())
	return nil
}

func GetRawMessageBody(msgBody *MessageBody) [][]byte {
	alignedMessageId := make([]byte, MessageIdMaxLen)
	copy(alignedMessageId, msgBody.MessageId)
	alignedMethod := make([]byte, MessageMethodMaxLen)
	copy(alignedMethod, msgBody.Method)
	alignedDonId := make([]byte, MessageDonIdMaxLen)
	copy(alignedDonId, msgBody.DonId)
	alignedReceiver := make([]byte, MessageReceiverLen)
	copy(alignedReceiver, msgBody.Receiver)
	return [][]byte{alignedMessageId, alignedMethod, alignedDonId, alignedReceiver, msgBody.Payload}
}
