### Title
Job script stdout can forge the JSON exit-status marker, causing stage-completion spoofing and trace log suppression - (File: shells/trap_command_exit_status.go)

### Summary
`StageCommandStatus.TryUnmarshal` accepts any line from the container/job stdout stream that happens to parse as `{"command_exit_code": N, "script": "..."}`, with no distinguishing marker, source separation, or authentication tying it to the actual `runner_script_trap` invocation. Because the Kubernetes executor's log pipeline (`forwardLogLine` / `entrypointLogForwarder.writeLine`) feeds raw job/container stdout through this same function, a job script that can `echo`/`printf` arbitrary text into its own stdout stream can fabricate this marker and manipulate Runner's internal stage-tracking state.

### Finding Description
`bashJSONTerminationScript` (and the pwsh equivalent) writes a JSON line like `{"command_exit_code": $exit_code, "script": "$0"}` to stdout via a `trap ... EXIT` [1](#0-0) . This same stdout stream (redirected with `tee`/`Out-File`, see `buildRedirectionCmd`) is read line-by-line and passed to `StageCommandStatus.TryUnmarshal`, both in the Kubernetes executor's polling log processor (`forwardLogLine`) and in the container-attach log forwarder (`entrypointLogForwarder.writeLine`) [2](#0-1) [3](#0-2) .

`TryUnmarshal` performs a plain `json.Unmarshal` of the raw line with no nonce, signature, prefix delimiter, or provenance check beyond "does it parse and is at least one of the two optional fields non-nil" [4](#0-3) . Any job stdout line matching that shape is indistinguishable from the genuine trap output.

Since job scripts (before_script, script, after_script) fully control what is written to their own stdout (`echo`, `printf`, heredocs, etc.), an attacker-authored pipeline can emit, e.g.:
```
echo '{"command_exit_code": 0, "script": "/builds/project/.gitlab-runner-stageA"}'
```
This line will:
1. Be parsed successfully by `TryUnmarshal`, so it is **not** written to the visible job trace at all (`forwardLogLine` returns early without calling `w.Write`), silently swallowing that line and the caller assumes a stage transition [5](#0-4) .
2. Update `s.remoteStageStatus` and, because `CommandExitCode` is non-nil, push a fabricated `StageCommandStatus` onto `s.remoteProcessTerminated` — this is the exact channel the executor's wait logic uses to decide a stage script has exited and with what exit code [6](#0-5) .
3. In `entrypointLogForwarder`, an injected marker with only `script` set (no exit code) sets `paused = true`, which stops forwarding any further stdout to the trace sink until a later marker with an exit code appears (`IsExited()`), i.e. the attacker's script can hide its own subsequent output from the job trace/log entirely [7](#0-6) .

No existing check filters or escapes job-produced stdout before it is fed to the JSON-marker parser; the parser trusts any line shaped like the marker regardless of whether it came from the trap or from `echo` in user code.

### Impact Explanation
The attacker can only forge state for **their own job's** stage-tracking channel — this does not cross job/project isolation boundaries by itself, since the log stream being manipulated already belongs to the job runner is executing on the attacker's behalf. The concrete impact is confined to:
- **Trace/log integrity loss**: the attacker can suppress arbitrary subsequent output from appearing in the job trace, which matters when the trace is reviewed by others (maintainers approving MR pipelines, security audits of protected-branch runs) — commands executed after the forged marker can run silently, undetected in the log even though they still execute in the sandbox.
- **Stage-completion desync**: `s.remoteProcessTerminated` receiving a forged exit status can cause the executor to believe the current stage's script has exited (with an attacker-chosen exit code) while the actual container process keeps running, decoupling the reported outcome from the real script execution for that stage.

This does not grant sandbox escape, cross-job/cross-project access, secret leakage, or auth bypass — it is a self-scoped log/observability integrity issue rather than an isolation breach, and forging one's own job's reported exit code is not materially different from what a job author can already do with `exit 0`. The novel part is the ability to **hide** subsequent output from the trace, which is a real but narrow observability-defeat impact.

### Likelihood Explanation
Trivially reproducible by any pipeline author with no special privileges: a single `echo` in `before_script`/`script` targeting the Kubernetes executor (any executor using this trap/marker convention and this shared log-line parser) is sufficient. It requires the attacker to know/guess the exact JSON schema (documented in the shell package/comments and easily inferred from public Runner source), which is trivial.

### Recommendation
Make the exit-status marker unforgeable by ordinary job stdout: prefix it with a per-job random, non-guessable token (e.g., generated per build and never exposed to the script) that is checked in `TryUnmarshal`/`tryUnmarshal` before treating a line as a control marker, or emit the marker on a distinct, out-of-band channel (e.g., a separate file descriptor/stream not intermixed with the job's stdout) instead of multiplexing it into the same `tee`'d stdout that user scripts write to.

### Proof of Concept
Go unit test extension for `shells/trap_command_exit_status_test.go`:
```go
func TestTryUnmarshal_AcceptsArbitraryUserEcho(t *testing.T) {
    // Simulates a job script doing:
    //   echo '{"command_exit_code": 0, "script": "/builds/project/.gitlab-runner-stageA"}'
    forged := `{"command_exit_code": 0, "script": "/builds/project/.gitlab-runner-stageA"}`

    var c StageCommandStatus
    decoded := c.TryUnmarshal(forged)

    assert.True(t, decoded, "attacker-controlled stdout line was accepted as a genuine control marker")
    assert.True(t, c.IsExited())
    assert.Equal(t, common.BuildStage("stageA"), c.BuildStage())
}
```
Assertion: `decoded == true` for a line that never originated from `runner_script_trap`, proving the parser cannot distinguish forged job output from the genuine trap marker. A fuller integration PoC would run a Kubernetes-executor job whose `script` is `echo '{"script":"/x"}'; echo SECRET_COMMAND_OUTPUT; echo '{"command_exit_code":0,"script":"/x"}'` and assert that `SECRET_COMMAND_OUTPUT` never appears in the resulting job trace, confirming the log-suppression exploit.

```go
func (s *executor) forwardLogLine(w io.Writer, line string) {
	var status shells.StageCommandStatus
	if !status.TryUnmarshal(line) {
		if _, err := w.Write([]byte(line)); err != nil {
			s.BuildLogger.Warningln(fmt.Sprintf("Error writing log line to trace: %v", err))
		}

		return
	}

	s.BuildLogger.Debugln(fmt.Sprintf("Setting remote stage status: %s", status))
	s.remoteStageStatusMutex.Lock()
	s.remoteStageStatus = status
	s.remoteStageStatusMutex.Unlock()

	if status.IsExited() {
		s.remoteProcessTerminated <- status
	}
}
```

```go
func (lf *entrypointLogForwarder) writeLine(p []byte) error {
	cmdStatus, ok := lf.commandStatus(p)
	if ok {
		if cmdStatus.IsExited() {
			lf.paused = false
		} else if cmdStatus.BuildStage() != "" {
			lf.paused = true
		}
	}

	if lf.paused || ok {
		return nil
	}

	_, err := lf.Sink.Write(p)
	return err
}
```

```go
func (c *StageCommandStatus) TryUnmarshal(line string) bool {
	var status stageCommandExitStatusImpl
	err := status.tryUnmarshal(line)
	if err != nil {
		return false
	}

	if status.isEmpty() {
		return false
	}

	status.applyTo(c)

	return true
}
```
