### Title
EI-authenticated requests bypass the "users only" restriction on `PipelineRunsController.Create` and can run ANY job by integer ID - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` attempts to restrict integer-ID job runs to session/token-authenticated users only, explicitly excluding external initiators (EIs), via `_, isUser := auth.GetAuthenticatedUser(c)`. However, `auth.AuthenticateExternalInitiator` sets the exact same `SessionUserKey` context value (a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}`) that `GetAuthenticatedUser` checks for, so the check always passes for EI-authenticated requests too, defeating the intended restriction and its accompanying comment.

### Finding Description
The route `/v2/jobs/:ID/runs` is registered under a group that authenticates via `AuthenticateExternalInitiator`, `AuthenticateByToken`, or `AuthenticateBySession` (in that order), wrapped only by `auth.RequiresRunRole` [1](#0-0) .

In `AuthenticateExternalInitiator`, once EI credentials are validated, the code sets both `SessionExternalInitiatorKey` and, critically, `SessionUserKey` to a synthetic run-role user object: [2](#0-1) 

`RequiresRunRole` only checks that `GetAuthenticatedUser` returns a user with role >= run, which the synthetic EI user satisfies [3](#0-2) .

Inside `PipelineRunsController.Create`, the code comment states "only users are allowed to run jobs using int IDs - EIs not allowed," and gates on `isUser` from `GetAuthenticatedUser(c)`: [4](#0-3) 

Because `GetAuthenticatedUser` merely checks presence/type of the `SessionUserKey` context value — not whether the request was actually authenticated via `AuthenticateBySession`/`AuthenticateByToken` versus `AuthenticateExternalInitiator` — an EI-authenticated request also produces `isUser == true`. The correct discriminator would have been checking `GetAuthenticatedExternalInitiator(c)` to explicitly reject EI-authenticated calls, but no such check exists.

Once past this gate, `prc.App.RunJobV2(ctx, jobID, nil)` is called directly with the parsed `jobID` from the URL param, with no check that the authenticated EI (or its associated `WebhookSpec`/`DirectRequestSpec`) has any relation to the target job ID. `RunJobV2`/`JobORM` perform no initiator-to-job binding check in this path (only the input `jobID` is used).

### Impact Explanation
Any credential holder for a single external initiator can trigger pipeline runs of arbitrary jobs by integer ID belonging to other job specs/owners, not just the EI's bound job. This is an authorization bypass allowing unauthorized triggering of job execution ("unauthorized job run") across job boundaries — potentially causing unwanted on-chain transactions, spurious task executions consuming node resources/funds (e.g., gas for ETH-transaction tasks), unintended external HTTP calls with the caller-controlled `meta`, or interference with unrelated jobs' pipeline run history/metrics. This matches the "unauthorized job run" impact class in the bounty program.

### Likelihood Explanation
The only precondition is possession of valid EI credentials for any single external initiator registered on the node (a low-privilege credential explicitly intended to be scoped to running its own bound job(s)). The attack requires a single crafted HTTP POST with correct EI headers and an arbitrary numeric job ID; it is fully reproducible and repeatable, with no timing or race conditions involved.

### Recommendation
In `PipelineRunsController.Create`, do not rely solely on `auth.GetAuthenticatedUser`; explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and reject (403) when present, restoring the intended "EIs not allowed for int ID runs" behavior. Alternatively, avoid overloading `SessionUserKey` in `AuthenticateExternalInitiator` with a synthetic user object; instead, propagate EI identity through a distinct mechanism so role-based helpers do not conflate EI and human/API-token sessions. If EIs must run jobs, additionally validate that the requested job ID belongs to a spec bound to the authenticated EI (its `WebhookSpec`/`DirectRequestSpec`) before invoking `RunJobV2`.

### Proof of Concept
1. Handler-level integration test in `core/web/pipeline_runs_controller_test.go`:
   - Create Job A (e.g., OCR or any non-webhook job type usable with int ID) owned/unrelated to any EI.
   - Register an External Initiator `EI1` (via `ExternalInitiatorsController` or DB helper `cltest.MustInsertExternalInitiator`), unrelated to Job A.
   - Build an HTTP client that sends `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers matching `EI1`'s credentials (per `static.ExternalInitiatorAccessKeyHeader`/`ExternalInitiatorSecretHeader`).
   - `POST /v2/jobs/{JobA.ID}/runs` with these EI headers.
   - Expected (secure) behavior: `403 Forbidden` or `404 Not Found`.
   - Actual (vulnerable) behavior: `200 OK` with a `pipelineRun` JSON:API resource in the response body, proving `RunJobV2` executed for a job unrelated to the EI.
2. Unit test on `auth.GetAuthenticatedUser` after calling `AuthenticateExternalInitiator` in a fake `gin.Context`, asserting it returns `ok=true`, demonstrating the root cause independent of the full HTTP stack.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
