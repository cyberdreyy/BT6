This is a confirmed vulnerability class, exactly analogous to the reported issue: the protocol's `is_protocol_paused()` check relies entirely on a per-group cached copy (`panic_state_cache`) of the canonical `FeeState.panic_state`, and that cache is only updated when someone permissionlessly calls `propagate_fee_state`. Just like `syncAllContracts` in the Graph Protocol report, if this sync isn't called immediately after an admin invokes `panic_pause`, every group that hasn't had its cache refreshed continues to operate as if unpaused.

### Title
Emergency pause is not enforced group-wide until `propagate_fee_state` is permissionlessly called, allowing continued fund movement in unsynced groups - ([File: programs/marginfi/src/state/marginfi_group.rs])

### Summary
The global `global_fee_admin`/`pause_delegate_admin` triggers an emergency-wide pause by setting `PanicState` on the singleton `FeeState` account via `panic_pause`. However, every `MarginfiGroup` account enforces the pause using its own locally-cached `panic_state_cache`, not the canonical `FeeState`. This cache is only refreshed when a `permissionless propagate_fee_state` instruction is executed against that specific group.

### Finding Description
`is_protocol_paused()` reads only the group's local cache: [1](#0-0) 

That cache is a copy, refreshed only by the explicit permissionless action `propagate_fee`: [2](#0-1) 

All pause-gated instructions (deposit/borrow/withdraw/repay, `LendingAccountBorrow`, `LendingPoolAccrueBankInterest`, `LendingPoolCollectBankFees`, etc.) check `!group.load()?.is_protocol_paused()`: [3](#0-2) [4](#0-3) 

The tests explicitly confirm this two-step dependency — pausing alone is not enough; propagation is required for the pause to be enforced against a given group: [5](#0-4) 

The protocol documentation itself confirms this is meant to be a group-wide freeze the moment the admin calls `panic_pause`: [6](#0-5) 

There is no automatic/atomic mechanism ensuring `propagate_fee_state` runs for every group in the same transaction as `panic_pause`, nor is there any documented SLA, alert system, or timestamp comparison exposed to users to know whether a given group's pause state is stale (mirroring exactly the missing "last sync timestamp" gap called out in the referenced Graph Protocol report). If a group's cache is not refreshed (e.g., admin forgets, propagation transaction fails/is delayed, or there are many groups and the crank hasn't reached this one yet), users interacting with that specific group are not blocked despite an active protocol-wide emergency pause.

### Impact Explanation
During an emergency pause — invoked specifically to stop an active exploit, oracle manipulation, or other incident — any group whose `panic_state_cache` has not yet been refreshed remains fully operational. Users (including a malicious actor who is the reason for the pause) can continue to deposit, borrow, withdraw, repay, and even trigger permissionless liquidation/interest accrual/fee collection against that group's banks, fully bypassing the intended circuit breaker. This is a direct, exploitable authorization-bypass with financial impact: it defeats the sole emergency stop mechanism of the protocol for any group not yet synced, during exactly the window when it's needed most.

### Likelihood Explanation
Likelihood is more than theoretical: `propagate_fee_state` is permissionless and per-group, so pausing requires N follow-up transactions for N groups. In an actual incident (network congestion, RPC issues, or simply operational delay while an admin/keeper iterates over groups), the delta between `panic_pause` execution and full propagation across all live groups is realistic and could be extended by an attacker (e.g., front-running propagation transactions or targeting a group known to be synced last).

### Recommendation
Either (a) make the pause check consult the canonical `FeeState.panic_state` directly (via CPI/account read) instead of the per-group cache, removing propagation as a prerequisite for enforcement, or (b) require `propagate_fee_state`-style validation as part of every pause-gated instruction (e.g., pass `FeeState` into every gated instruction and compare timestamps/`last_cache_update` recency against the current pause, erroring if stale beyond a safe threshold). At minimum, expose the cache's `last_update`/`last_cache_update` timestamp prominently and document/automate that `panic_pause` must be immediately followed by mass propagation across all groups, ideally batched into the same or an atomically-enforced follow-up transaction.

### Proof of Concept
1. Global admin detects an active exploit affecting Group B and calls `panic_pause` (updates `FeeState.panic_state.pause_flags = FLAG_PAUSED`).
2. Before (or instead of) calling `propagate_fee_state` against Group B, an attacker (or any user) submits `lending_account_borrow`/`withdraw` against a bank in Group B.
3. Group B's `MarginfiGroup.panic_state_cache.is_paused_flag()` is still `false` (never refreshed), so `is_protocol_paused()` returns `false` and the constraint `!group.load()?.is_protocol_paused()` passes.
4. The instruction executes successfully, exactly as shown by the passing "happy path" cases in [7](#0-6)  contrasted with the paused case in the same file, where the *only* difference enabling the block is the additional `try_propagate_fee_state()` call — proving the pause has zero effect on a group until that permissionless sync runs.

## Protocol Panic-Pause

When the `global_fee_admin` or `pause_delegate_admin` invokes `panic_pause`, the protocol enters a
group-wide paused state. The pause auto-expires (see `PanicState::PAUSE_DURATION_SECONDS`) and is
rate-limited (max consecutive pauses per window, max per day) so it cannot be held indefinitely.

### Blocked while paused

All normal user flows are disabled:

- Deposit, Borrow, Withdraw, Repay (both native banks and integration banks — Kamino, Drift,
  Juplend, Solend)
- Order placement / order flows
- Account transfer
- Classic liquidation (`LendingAccountLiquidate`)
- Permissionless bank-fee collection
- Permissionless bad-debt settlement (`HandleBankruptcy` when called by a non-admin, even on banks
  with the `PERMISSIONLESS_BAD_DEBT_SETTLEMENT` flag)
- Admin bank configuration changes that route through `LendingPoolConfigureBank`
