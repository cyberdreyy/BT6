## Analysis

The code at `core/web/auth/auth.go` lines 145-148 explicitly sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` after successful EI authentication — using the exact same context key (`SessionUserKey`) that `AuthenticateBySession`/`AuthenticateByToken` use for real users.### Title
EI credentials can impersonate a user to trigger int-ID job runs via shared `SessionUserKey` context value - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` using the same context key that user-authenticating methods (`AuthenticateBySession`, `AuthenticateByToken`) use for the *actual authenticated user object*. `PipelineRunsController.Create` gates the "int-ID job run" path solely on `_, isUser := auth.GetAuthenticatedUser(c)`, which returns `true` for any successfully-authenticated EI request, defeating the code's own comment "only users are allowed to run jobs using int IDs - EIs not allowed".

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered with `auth.Authenticate(..., auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` wrapped by `auth.RequiresRunRole(prc.Create)` [1](#0-0) . Because `Authenticate` tries methods in order and stops on the first non-`ErrorAuthFailed` result [2](#0-1) , a request presenting only valid EI headers (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret`) succeeds via `AuthenticateExternalInitiator` alone.

Inside `AuthenticateExternalInitiator`, after validating the EI's HMAC-style secret via `bridges.AuthenticateExternalInitiator` [3](#0-2) , the code sets both the EI key and, deliberately, a synthetic `User{Role: UserRoleRun}` under `SessionUserKey`: [4](#0-3) 

`RequiresRunRole` only checks `user.Role != UserRoleView` [5](#0-4) , which the synthetic `UserRoleRun` satisfies, so the request reaches `PipelineRunsController.Create`.

In `Create`, the code comment explicitly states int-ID runs are for users only, but the check is `_, isUser := auth.GetAuthenticatedUser(c)` — merely testing presence of a `*clsessions.User` object at `SessionUserKey`, not whether the request was actually authenticated as a real logged-in user: [6](#0-5) 

Since `GetAuthenticatedUser` just reads and type-asserts whatever is stored at `SessionUserKey` [7](#0-6) , and the EI auth path stores a `*clsessions.User`, `isUser` evaluates to `true` for EI-authenticated requests too. This lets an EI credential holder invoke `prc.App.RunJobV2(ctx, jobID, nil)` for arbitrary integer job IDs — a code path explicitly intended to be blocked for EIs by both the code comment and design intent (EIs are meant to use UUID-based webhook triggering, not direct int-ID job execution).

### Impact Explanation
An attacker holding only an external-initiator's access key/secret (a lower-trust credential class, often distributed to third-party bridge/EA operators) can trigger job runs for any job by integer ID, bypassing the intended EI/user access-method separation. This matches the "unauthorized job run" bounty impact class — an attacker can cause execution of pipeline jobs (potentially including fund-moving OCR/VRF/EVM transaction jobs) that were not meant to be externally triggerable via EI credentials, and can consume compute resources or trigger unintended on-chain transactions.

### Likelihood Explanation
Requires possession of valid external-initiator credentials, which are a standard, lower-privilege credential type used by external bridge integrations — not admin/host access. Given valid EI credentials (attacker scope allows "external-initiator credential holder"), the exploit is straightforward and fully reproducible: send `POST /v2/jobs/<intJobID>/runs` with EI headers only. No race conditions or timing dependencies are involved, and it is repeatable per job.

### Recommendation
In `PipelineRunsController.Create`, distinguish real users from EI-impersonated context by also checking `_, isEI := auth.GetAuthenticatedExternalInitiator(c)` and rejecting the int-ID path when an EI is present, or by not overloading `SessionUserKey` for EI requests at all (use a distinct sentinel/role, or avoid storing a `*clsessions.User` for EIs). Preferably, refactor `AuthenticateExternalInitiator` to not set `SessionUserKey`, and instead have `RequiresRunRole` accept either a real user or an EI via `GetAuthenticatedExternalInitiator`, so identity types are never conflated under one key.

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
