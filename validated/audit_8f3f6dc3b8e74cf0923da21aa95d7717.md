### Title
Unfunded instant withdrawals can drain already-funded claim reserves - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.requestInstantWithdraw` immediately mints a one-to-one receipt and records it as pending, but `claimInstantWithdrawRequest` pays that receipt without checking that the instant withdrawal was actually funded. The payout helper also does not exclude `pendingInstantWithdraws`, so a tranche holder can claim immediately and consume strategy-held underlying reserved for older funded withdrawal receipts.

### Finding Description
`requestInstantWithdraw` burns the CDO’s strategy tokens, mints the same amount to the user, and increments both user/global pending instant-request accounting. No cash is collected or earmarked at that point. [1](#0-0) 

`claimInstantWithdrawRequest` then reads the full `instantWithdrawsRequests[_user]`, burns the receipt, clears the request, and transfers the full amount. It never requires `pendingInstantWithdraws` to have been reduced by `collectInstantWithdrawFunds`, nor does it compare the payout against an already-funded instant bucket. [2](#0-1) 

Funding is only tracked later through `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws`; claims do not inspect this counter. [3](#0-2)  The transfer helper only protects `defaultRecoveryReserve`; it does not protect underlying earmarked for ordinary funded receipts or the unfunded instant bucket. [4](#0-3) 

The CDO entry point directly forwards `claimInstantWithdrawRequest` and has no epoch/funding check beyond `allowInstantWithdraw`. [5](#0-4) 

### Impact Explanation
An unprivileged KYC-passed tranche holder can convert an unfunded instant-withdraw receipt into underlying held by the strategy. If the strategy balance contains borrower-funded amounts intended for older normal withdrawal receipts, instant receipts, or other pending settlement cash, the attacker can withdraw those assets before the entitled users claim.

The broken invariant is one receipt, one funded payout. The attacker receives cash whose backing was created for another liability, leaving later legitimate claims insolvent. The extractable amount is bounded by `min(instantReceiptAmount, strategyUnderlyingBalance - defaultRecoveryReserve)`, which can equal the entire non-default-funded reserve held by `IdleCreditVault`.

### Likelihood Explanation
The issue requires instant withdrawals to be enabled and the APR-decrease trigger in `IdleCDOEpochVariant.requestWithdraw` to be active, namely `lastEpochApr > unscaledApr + instantWithdrawAprDelta`. [6](#0-5)  The attacker only needs to already hold tranche tokens and sequence the request after an honest APR update, then call `claimInstantWithdrawRequest` before the borrower/strategy funding step occurs.

The reserve guard does not stop this because `defaultRecoveryReserve` is normally zero outside finalized default recovery, so `_transferFundedClaim` performs no effective liability reservation. [4](#0-3) 

### Recommendation
Track funded and unfunded instant withdrawals separately. `collectInstantWithdrawFunds` should increase a `fundedInstantWithdraws` counter, while `claimInstantWithdrawRequest` should cap the claim to the user’s funded allocation or require `pendingInstantWithdraws == 0`. Alternatively, make `_transferFundedClaim` revert whenever transferring `_amount` would leave less than the currently unfunded `pendingInstantWithdraws` plus other reserved liabilities.

### Proof of Concept
A Foundry PoC should fork the production deployment and reproduce the unfunded claim with real roles:

```solidity
// test/foundry/InstantWithdrawFunding.t.sol
function testUnfundedInstantWithdrawDrainsFundedReceipt() public {
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    // Arrange:
    // 1. victim has an already borrower-funded withdraw receipt whose
    //    underlying now sits in IdleCreditVault.
    // 2. attacker holds KYC-approved tranche tokens.
    // 3. instant withdrawals are enabled and APR was decreased by the
    //    honest manager enough to satisfy:
    //    lastEpochApr > unscaledApr + instantWithdrawAprDelta.

    uint256 attackerTranches = 1_000e18;
    uint256 strategyCash = underlying.balanceOf(address(creditVault));
    assertGt(strategyCash, 0);

    uint256 victimClaim = creditVault.withdrawsRequests(victim);
    uint256 attackerBefore = underlying.balanceOf(attacker);

    // APR drop path creates an instant receipt without collecting cash.
    vm.prank(attacker);
    cdo.requestWithdraw(attackerTranches, address(aaTranche));

    uint256 pending = creditVault.pendingInstantWithdraws();
    assertGt(pending, 0);

    // No collectInstantWithdrawFunds call occurs. The receipt is unfunded,
    // yet the claim immediately transfers strategy-held underlying.
    vm.prank(attacker);
    cdo.claimInstantWithdrawRequest();

    uint256 stolen = underlying.balanceOf(attacker) - attackerBefore;
    assertGt(stolen, 0);

    // Later victim claim is underfunded/reverts because the attacker consumed
    // cash that was collected for older funded liabilities.
    vm.prank(victim);
    vm.expectRevert();
    cdo.claimWithdrawRequest();
}
```

The critical assertion is that `pendingInstantWithdraws > 0` immediately before the successful instant claim. That demonstrates that the payout was not funded through `collectInstantWithdrawFunds` and therefore consumed unrelated strategy cash.

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
```
