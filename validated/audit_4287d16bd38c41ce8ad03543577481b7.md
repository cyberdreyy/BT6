### Title
Unauthenticated `MethodPublicKeyGet` requests bypass owner-prefixing and can collide with a victim's authorized-and-prefixed `activeRequest` ID, causing denial of service against the victim's request - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
`handler.HandleJSONRPCUserMessage` handles `vaulttypes.MethodPublicKeyGet` on a special unauthenticated path that never calls `h.requestProcessor.ProcessRequest`, so the attacker-supplied `req.ID` is registered in `h.activeRequests` verbatim, without the `owner+RequestIDSeparator+id` prefixing applied to every other (authorized) method. Because `newActiveRequest` keys the single shared `h.activeRequests` map on this raw string, an attacker who knows or predicts a victim's `authorizedOwner` and `requestId` can pre-register an entry under the exact string the victim's request will be prefixed to (`"victimOwner" + RequestIDSeparator + "1"`), causing the victim's legitimately authorized request to be rejected as a duplicate.

### Finding Description
`HandleJSONRPCUserMessage` special-cases `vaulttypes.MethodPublicKeyGet` before authorization: [1](#0-0) . In that branch, `req.ID` (fully attacker-controlled, only bounded to ≤200 chars, see the initial validation) is passed unchanged to `h.newActiveRequest(req, callback)` [2](#0-1) .

For every other (authenticated) method, `req.ID` is only registered into `activeRequests` **after** `h.requestProcessor.ProcessRequest` runs, which rewrites `req.ID` to `authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID` inside `authorizeAndStamp`: [3](#0-2) . That prefixed ID is what `newActiveRequest` uses as the map key: [4](#0-3) .

Both code paths write into the *same* `h.activeRequests map[string]*activeRequest` [5](#0-4) , and `newActiveRequest` performs no namespace segregation by method or owner - it only checks for an existing key. Consequently, an unauthenticated attacker can submit `MethodPublicKeyGet` with `req.ID` literally equal to `"victimOwner" + vaulttypes.RequestIDSeparator + "1"`. If this attacker request registers first, then when the victim (an authorized owner named `"victimOwner"`) submits e.g. `MethodSecretsCreate` with client-chosen ID `"1"`, `authorizeAndStamp` computes the identical prefixed ID `"victimOwner:1"`, and `newActiveRequest` returns `errors.New("request ID already exists: " + req.ID)` [6](#0-5) , which propagates back up through `HandleJSONRPCUserMessage` as a hard error, so the victim's authorized secrets request is never forwarded to Vault nodes at all [7](#0-6) .

Note: this does **not** achieve cross-owner response/result leakage. Because `newActiveRequest` rejects the second registration outright rather than overwriting the first entry, whichever request registers second is entirely blocked before being dispatched to nodes - there is no window where both requests share one `activeRequest` object and a node response could be routed to the wrong callback. The exploitable outcome is limited to **denial of a specific victim request** (or, symmetrically, an attacker's own `MethodPublicKeyGet` fetch being blocked by a victim's authorized request), not disclosure of secrets or impersonation of the victim's identity.

### Impact Explanation
This is a targeted request-collision / griefing vector: an unauthenticated caller can block a specific authorized user's single vault secrets request (create/update/delete/list) by winning a race to pre-register the same post-prefix ID via the unauthenticated `MethodPublicKeyGet` path. It requires the attacker to know or guess both the victim's `authorizedOwner` string and the exact client-chosen `requestId`, and to win a timing race before the victim's request arrives (the collision self-clears after `defaultCleanUpPeriod`/`requestTimeout`, and the attacker's own registered `activeRequest` also gets cleaned up or resolves via `handlePublicKeyGet`). This falls under a "unauthorized action affecting a legitimate job/request" / limited availability-impact class rather than fund movement, key disclosure, or auth bypass — it is a denial-of-service against a single request, not systemic compromise. It does not achieve the cross-owner response confusion (leaking one owner's Vault operation result to another owner) that the question hypothesizes, because `newActiveRequest`'s exclusivity check prevents map-entry overwrite.

### Likelihood Explanation
Exploitability requires: (1) no privileges - the `MethodPublicKeyGet` path is intentionally unauthenticated [8](#0-7) ; (2) knowledge of the victim's `authorizedOwner` value (workflow owner address / allow-listed owner identifier, which may be discoverable from on-chain workflow registry data) and the victim's client-generated `requestId`; and (3) winning a race to register the ID before the victim's real request lands. Given that request IDs are often small/sequential/predictable client-side values (e.g., "1", "2", ...) and owner identifiers can be public (workflow owner addresses), this is plausible but requires precise timing and target knowledge, making it a low-to-moderate likelihood griefing vector rather than a trivially repeatable attack.

### Recommendation
Segregate the `activeRequests` namespace so unauthenticated `MethodPublicKeyGet` requests can never collide with owner-prefixed request IDs — e.g., always prefix `MethodPublicKeyGet` request IDs with a reserved, non-owner-derivable sentinel (such as a fixed `"__pubkey__"` + separator) before calling `newActiveRequest`, or maintain two separate maps (one for unauthenticated public-key requests, one for authorized/prefixed requests) so the two ID spaces cannot overlap regardless of attacker-chosen literal values.

### Proof of Concept
Go unit test plan for `core/services/gateway/handlers/vault/handler_test.go`:
1. Construct a `handler` with a stub authorizer that authorizes owner `"victimOwner"` for a `MethodSecretsCreate`/`MethodSecretsList` request with `req.ID = "1"`.
2. Call `h.HandleJSONRPCUserMessage` with `req.Method = vaulttypes.MethodPublicKeyGet` and `req.ID = "victimOwner" + vaulttypes.RequestIDSeparator + "1"` from an unauthenticated caller (no `req.Auth`), and a stub/no-op callback; ensure `h.getCachedPublicKey()` returns `nil` so it goes through `h.newActiveRequest`.
3. Assert this call succeeds and `h.activeRequests["victimOwner:1"]` is populated with the attacker's `MethodPublicKeyGet` request.
4. Then call `h.HandleJSONRPCUserMessage` with the victim's `MethodSecretsCreate` request (`req.ID = "1"`, valid auth resolving to owner `"victimOwner"`).
5. Assert this second call returns an error containing `"request ID already exists: victimOwner:1"` and that `h.don.SendToNode` (mock DON) was never invoked for the victim's request — proving the victim's legitimate, authorized request was silently blocked by the unauthenticated attacker request, while confirming no cross-response resolution occurs (the victim callback is never invoked with the attacker's or any node's response).

```go
func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
```
