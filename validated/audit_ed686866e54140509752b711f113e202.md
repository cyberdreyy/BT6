### Title
Mid-epoch deposits credit the depositor with the nominal amount instead of the received amount, letting fee-on-transfer shortfalls be socialized onto the pool - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The Cooler bug class (accounting credited for nominal `amount` while the ERC20 `transferFrom` delivers `amount - fee`) does not exist in the ordinary deposit path — `IdleCDO._deposit` and `IdleCDOCreditVault._deposit` both mint shares on the actual balance delta (`_contractTokenBalance(_token) - _preBal`) [1](#0-0) [2](#0-1) . However, the mid-epoch deposit path `depositDuringEpoch` reintroduces the exact same class: it pulls tokens via `_transferUnderlyingsFrom` but then does all accounting — share minting, NAV increase, expected interest, strategy token minting, and the onward transfer to the borrower — using the nominal `_amount` rather than the received amount [3](#0-2) .

### Finding Description
In `IdleCDOEpochVariant.depositDuringEpoch`:

```solidity
// Get underlyings from user
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
...
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
_mintShares(_tranche, msg.sender, _minted, _amount);
expectedEpochInterest += interest;
IdleCreditVault(strategy).mintStrategyTokens(_amount);
_transferUnderlyings(_borrower(), _amount);
```

For a fee-on-transfer underlying (e.g. USDT with fee enabled, or any rebasing/FoT ERC20 the factory is pointed at), the vault receives only `_amount - fee` yet:

- `lastNAV*` is increased by the full `_amount` via `_mintShares`, so NAV > actual assets.
- `_minted` shares are priced off nominal `_amount`, over-minting tranche tokens relative to value contributed.
- `mintStrategyTokens(_amount)` mints full strategy tokens, and `_transferUnderlyings(_borrower(), _amount)` pushes out the full nominal `_amount`.

The vault therefore sends out `fee` more underlying than it received. That difference is paid out of residual vault balance (buffer liquidity, reserved instant-withdraw funds, other depositors' unlent funds); if the balance is insufficient the call reverts. The `expectedEpochInterest`/`trancheInterest` math also inflates since `interest` is computed on the un-received nominal `_amount`. At epoch end the depositor's tranche tokens claim `_amount + interest` of value while only `_amount - fee` ever entered the system — the shortfall is socialized across all other tranche holders, identically to the Cooler finding where collateral was credited at nominal while less was received.

### Impact Explanation
Direct theft / insolvency: each mid-epoch deposit of nominal `_amount` extracts `fee` underlying from the pool (or dilutes tranche value by `fee + fee-derived interest`). An unprivileged KYC-passed lender repeating `depositDuringEpoch` drains vault liquidity proportional to the token's transfer fee, and the inflated `lastNAV`/`minted` shares make honest withdrawers absorb the loss at claim time via `claimWithdrawRequest`/`_claimDefaulted*` payouts. No guard catches it: `_skimDonatedAssets` only removes excess over accounted value, `_updateAccounting` runs *before* the transfer, and no post-transfer balance check exists in this path (unlike `_deposit`).

### Likelihood Explanation
Conditional on the vault's `token` being a fee-on-transfer ERC20. Credit vault deployments target stablecoins, but the code enforces nothing about token behavior, and USDT (a plausible credit-vault underlying) has a fee switch. Additionally `depositDuringEpoch` must be enabled (`isDepositDuringEpochDisabled == false`), epoch must be running with `block.timestamp < epochEndDate`, AYS/programmable-borrower mode off, and the caller must pass `isWalletAllowed` — all attacker-satisfiable conditions [4](#0-3) .

### Recommendation
Mirror the fix already used in `_deposit`: snapshot `_contractTokenBalance(token)` before `_transferUnderlyingsFrom` and use `received = balanceAfter - balanceBefore` for `interest`, `_minted`, `_mintShares`, `mintStrategyTokens`, and the borrower transfer. Alternatively, document and enforce that only non-fee-on-transfer tokens are supported.

### Proof of Concept
Foundry fork-style PoC sketch (mock an FoT token or use a USDT-like token with fee on):

```solidity
// token: ERC20 that burns 1% on transferFrom
// Setup: AA + BB deposits, startEpoch(), warp to mid-epoch,
// setIsDepositDuringEpochDisabled(false)
uint256 amount = 10_000e6; // 100e6 fee
uint256 vaultBalPre = token.balanceOf(address(cdoEpoch));
uint256 navPre = cdoEpoch.lastNAVAA();

token.approve(address(cdoEpoch), amount);
uint256 minted = cdoEpoch.depositDuringEpoch(amount, AAtranche);

// received only amount - fee, but:
assertEq(cdoEpoch.lastNAVAA() - navPre, amount);        // NAV up by nominal
assertEq(token.balanceOf(borrower) - borrowerPre, amount); // full amount sent out
assertEq(token.balanceOf(address(cdoEpoch)) - vaultBalPre, -int256(fee)); // vault down by fee
// minted claims amount + prorated interest -> other holders absorb fee + its interest
```

  function depositDuringEpoch(uint256 _amount, address _tranche) external virtual returns (uint256 _minted) {
    _checkTranche(_tranche);
    _checkNotAllowed(
      (_tranche == BBTranche && !isBBDepositEnabled) ||
      isDepositDuringEpochDisabled ||
      skipDefaultCheck ||
      // programmable borrowers use APR=0 so mid-epoch deposits would dilute existing depositors
      isProgrammableBorrower ||
      // check if AYS is active as we don't support deposits during epoch in that case
      isAYSActive ||
      // check if epoch is still running even if not manually stopped yet
      !isEpochRunning || block.timestamp >= epochEndDate ||
      !isWalletAllowed(msg.sender)
    );

    if (_amount == 0) {
      return _minted;
    }

    uint256 _trancheTotSupply = _trancheSupply(_tranche);
    // Avoid pricing discontinuities for the first mid-epoch deposit in a tranche
    _checkNotAllowed(_trancheTotSupply == 0);

    _transferUnderlyingsFrom(msg.sender, address(this), _amount);

    // interest for the remaining epoch plus the full buffer period
    // NOTE: _calcInterest already gives full‑epoch + full‑buffer interest for the whole epoch
    //   So when a user joins mid‑epoch, we take the fraction of that full‑period interest 
    //   that matches the time they actually remain plus the entire buffer
    uint256 buffer = bufferPeriod;
    uint256 remaining = epochEndDate - block.timestamp;
    uint256 interest = _calcInterest(_amount) *
      // the time the depositor actually participates (remaining epoch + full buffer)
      (remaining + buffer) /
      // the total time baked into the scaled APR (epoch + buffer).
      (epochDuration + buffer);

    uint256 expectedInt = expectedEpochInterest;
    uint256 pendingFees = pendingWithdrawFees;
    uint256 trancheExpected;
    // existing holders' share of net expected interest for the epoch (pre-deposit)
    // (exclude pendingWithdrawFees since they go to fee receivers, not tranche holders)
    if (expectedInt > pendingFees) {
      trancheExpected = _calcTrancheInterestShare(
        _netGainAfterFees(expectedInt - pendingFees, _calculateManagementFee(lastNAVAA + lastNAVBB, remaining)),
        _tranche
      );
    }
    // interest this deposit will earn for the tranche over the remaining time (net of fees)
    uint256 trancheInterest = _calcTrancheInterestShare(
      _netGainAfterFees(interest, _calculateManagementFee(_amount, remaining)),
      _tranche
    );
    // pre-deposit expected final NAV for existing holders.
    // This won't ever be zero as we checked _trancheTotSupply and we seed initial NAV at tranche creation
    uint256 expectedFinal = _lastSavedNAV(_tranche) + trancheExpected;

    // mint at a discounted price so depositor gets principal + its prorated interest at epoch end
    // A mid‑epoch depositor should get _amount + trancheInterest at epoch end.
    // So they need minted = (amount + trancheInterest) / priceEnd.
    // priceEnd = expectedFinal / _trancheTotSupply
    // so minted = (amount + trancheInterest) * _trancheTotSupply / expectedFinal
    _minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
    _mintShares(_tranche, msg.sender, _minted, _amount);

    // update expected epoch interest
    expectedEpochInterest += interest;
    // mint strategy tokens to this contract
    IdleCreditVault(strategy).mintStrategyTokens(_amount);
    // transfer underlyings to the borrower
    _transferUnderlyings(_borrower(), _amount);
