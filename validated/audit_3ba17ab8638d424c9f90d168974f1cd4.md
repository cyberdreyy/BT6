## Analysis

The JWT signature scheme used to authorize HTTP-triggered workflow executions in the gateway binds the signed digest only to the JSON-RPC request's `method`+`id`+`params` (via `req.Digest()`), but the `workflowID` used for authorization is resolved and passed **separately**, outside of what is covered by the signature. This is structurally the same root cause described in the report: a signature scheme that omits the "instance" identifier (there, the contract address/chainID; here, the `workflowID`) from the signed payload, enabling reuse of a valid signature across different scopes that share the same signer. [1](#0-0) [2](#0-1) [3](#0-2) 

`Authorize` takes `workflowID` as an out-of-band parameter and only checks that the *recovered signer* is present in that workflow's authorized-keys set; the digest check in `VerifyRequestJWT` never incorporates `workflowID`: [4](#0-3) 

Because `resolveWorkflowID` can match a request either by explicit `workflowID` or by `(workflowOwner, workflowName, workflowTag)`, and the signed digest is computed purely from the request body: [5](#0-4) 

replay is only prevented (a) within a single workflow by the `jti` replay cache, and (b) across workflows only incidentally if the signer of a captured request is not also an authorized key for another workflow. If a workflow owner reuses the same signer/authorized key across multiple workflows/tags (a legitimate, supported configuration — `authorizedKeys` is keyed per `workflowID`, and the same key can appear in multiple sets via `syncMetadata`), a JWT+request pair captured for workflow A can be replayed unmodified against workflow B by simply presenting a different `workflowID`/`workflowOwner+Name+Tag` combination in the outer envelope, since none of that routing information is part of the signed digest.

This matches the report's exploit pattern precisely: the report's contract signatures omit the contract address (its "instance"), letting Eve reuse Alice/Bob's signature on a second deployment; here the JWT digest omits the workflow instance identifier, letting a captured signature be replayed against a different workflow instance that shares the same authorized signer.

I was not able to fully verify, within the given exploration budget, whether `req.Digest()` in the `jsonrpc.Request` type (from `chainlink-common`) incorporates any additional context (e.g., a DON or gateway domain separator) that might mitigate this — that type lives outside this repo's index and its `Digest()` implementation was not retrievable. This uncertainty affects whether the digest is *purely* method/id/params or includes some other binding; based on all reachable evidence in this repo, workflowID/owner/name/tag are never part of what's hashed or checked.

### Title
JWT signature for HTTP-triggered workflow execution omits workflow-instance binding, enabling cross-workflow replay - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The gateway's `WorkflowMetadataHandler.Authorize` verifies an ECDSA-signed JWT (`utils.VerifyRequestJWT`) whose digest covers only the JSON-RPC request `method`/`id`/`params`, not the `workflowID` being authorized against. `workflowID` is resolved independently in `httpTriggerHandler.resolveWorkflowID` and passed as a bare string to `Authorize`. Any signer authorized on more than one workflow (a supported, common configuration) can have a validly-signed request for workflow A replayed to trigger workflow B, because the signature never bound the specific workflow instance.

### Finding Description
`CreateRequestJWT`/`VerifyRequestJWT` compute the JWT's `digest` claim solely from `req.Digest()` — derived from the JSON-RPC request body — and check `jti` uniqueness for replay protection, but never mix in the `workflowID`, `workflowOwner`, `workflowName`, or `workflowTag` that the caller separately supplies to route/authorize the request: [6](#0-5) [3](#0-2) 

`Authorize(workflowID, token, req)` only checks that the signer recovered from the JWT is present in `authorizedKeys[workflowID]`: [4](#0-3) 

The caller resolves `workflowID` from user-supplied routing fields (`workflowID` or `workflowOwner`+`workflowName`+`workflowTag`) that are part of the *unsigned* envelope, before calling `Authorize`: [1](#0-0) [7](#0-6) 

This is the direct analog of the external report's root cause: the signature scheme fails to bind the "contract instance" (here, workflow instance) into the signed data, so a signature valid for one instance can be replayed against another sharing the same authorized signer.

### Impact Explanation
An unprivileged party who observes (or is the intended recipient of) a valid signed HTTP-trigger request for one workflow can replay the same JWT+params against any other workflow for which the same signer/authorized key is also registered, causing unauthorized execution of a different workflow (potentially with different logic, funds, or side effects) using the observer's captured, otherwise-legitimate authorization. This is an authentication/authorization-scope-bypass issue (cross-instance replay), not merely a duplicate-run issue, since the `jti` cache only prevents replay against the *same* JWT ID — it does not stop presenting the same token against a different `workflowID`.

### Likelihood Explanation
Exploitability depends on a signer being authorized across multiple workflows and on an attacker being able to observe a valid signed request (e.g., via network exposure, logs, or being a legitimate but lower-privilege caller for workflow A). This is a realistic operational pattern for organizations that reuse the same signing key across several workflows they own. The bug is reachable directly from the internet-facing HTTP trigger gateway endpoint without any privileged access.

### Recommendation
Include the resolved `workflowID` (and ideally `workflowOwner`, `workflowName`, `workflowTag`, and DON/gateway identifier) as part of the data covered by the JWT digest, and verify that the claims match the specific workflow instance being authorized in `Authorize`, similar to how EIP-712 domain separation binds a contract address and chain ID into the signed hash. Reject any JWT whose signed digest does not incorporate the exact target workflow instance.

### Proof of Concept
1. Workflow owner registers the same authorized ECDSA key for two workflows, W1 and W2 (supported since `authorizedKeys` is a per-workflow-ID map populated independently via metadata sync).
2. A legitimate caller sends a signed HTTP trigger request `{method, id, params}` for W1, producing a JWT whose digest is `Digest(method, id, params)` and is verified/authorized in `Authorize(W1, token, req)`.
3. An observer captures this `(token, req)` pair.
4. The observer re-submits the identical `token` and `req`, but changes only the outer routing (e.g., `workflowOwner`/`workflowName`/`workflowTag` or `workflowID` field inside `params.Workflow`, which is not part of the signed digest binding check) to resolve to W2 instead of W1.
5. Because `VerifyRequestJWT` recomputes `req.Digest()` from the same `method`/`id`/`params` and it matches, and the signer is also authorized for W2, `Authorize(W2, token, req)` succeeds, causing W2 to execute using a signature never intended for it.

func (h *httpTriggerHandler) resolveWorkflowID(ctx context.Context, triggerReq *jsonrpc.Request[gateway_common.HTTPTriggerRequest], requestID string, callback handlers.Callback) (string, error) {
	h.lggr.Debugw("resolving workflow ID", "workflowID", triggerReq.Params.Workflow.WorkflowID, "workflowOwner", triggerReq.Params.Workflow.WorkflowOwner, "workflowName", triggerReq.Params.Workflow.WorkflowName, "workflowTag", triggerReq.Params.Workflow.WorkflowTag, "requestID", requestID)
	workflowID := triggerReq.Params.Workflow.WorkflowID
	if workflowID != "" {
		workflowID = normalizeHex(workflowID, workflowIDLength)
		_, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
		if !found {
			h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, fmt.Sprintf("Workflow not found. 'workflowID' %s is not a valid workflow ID", workflowID), callback)
			return "", errors.New("workflow not found")
		}
		return workflowID, nil
	}
	workflowOwner := normalizeHex(triggerReq.Params.Workflow.WorkflowOwner, workflowOwnerLength)
	workflowName := "0x" + hex.EncodeToString([]byte(workflows.HashTruncateName(triggerReq.Params.Workflow.WorkflowName)))
	workflowID, found := h.workflowMetadataHandler.GetWorkflowID(
		workflowOwner,
		workflowName,
		triggerReq.Params.Workflow.WorkflowTag,
	)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "Workflow not found. Provide either a valid 'workflowID' or a valid combination of 'workflowOwner', 'workflowName', and 'workflowTag'", callback)
		return "", errors.New("workflow not found")
	}
	return workflowID, nil
}

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func CreateRequestJWT[T any](req jsonrpc.Request[T], opts ...Option) (*jwt.Token, error) {
	// Apply options
	options := &jwtOptions{}
	for _, opt := range opts {
		opt(options)
	}

	expiryDuration := maxJWTExpiryDuration
	if options.expiryDuration != nil {
		expiryDuration = *options.expiryDuration
	}

	digest, err := req.Digest()
	if err != nil {
		return nil, err
	}

	var issuer string
	if options.issuer != nil {
		issuer = *options.issuer
	}

	var subject string
	if options.subject != nil {
		subject = *options.subject
	}

	var audience []string
	if options.audience != nil {
		audience = options.audience
	}

	now := time.Now()
	jti := uuid.New().String()

	claims := JWTClaims{
		Digest: "0x" + digest,
		RegisteredClaims: jwt.RegisteredClaims{
			ID:        jti,
			Issuer:    issuer,
			Subject:   subject,
			Audience:  jwt.ClaimStrings(audience),
			ExpiresAt: jwt.NewNumericDate(now.Add(expiryDuration)),
			IssuedAt:  jwt.NewNumericDate(now),
		},
	}

	return jwt.NewWithClaims(&SigningMethodEth{}, claims), nil
}
