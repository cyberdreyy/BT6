### Title
Quadratic-time transaction-replay-set reconciliation lets a single malicious signer stall every other signer's state machine — `find_majority_prefix_replay_set` in `libsigner/src/v0/signer_state.rs`

### Summary
`GlobalStateEvaluator::determine_global_state()` calls `find_majority_prefix_replay_set()` whenever signers disagree on the exact `tx_replay_set` (the set of transactions to replay after a Bitcoin fork). This helper truncates the candidate replay-set prefix one transaction at a time and, on every truncation, re-scans **all** gossiped replay sets and re-runs `Vec::starts_with` against the (still long) candidate prefix — an O(L²·N) computation where L is the length of the longest gossiped replay set and N is the number of distinct replay sets seen. This is structurally the same flaw as the CommonMark advisory: a shared reconciliation routine that restarts an expensive linear scan on every step instead of caching/pruning progress, so an attacker who controls the size of the input (here, `tx_replay_set`) can drive the cost up quadratically.

### Finding Description
`GlobalStateEvaluator::determine_global_state` (`libsigner/src/v0/signer_state.rs:102-158`) builds a `tx_replay_sets: HashMap<ReplayTransactionSet, u32>` from every signer's most recent `StateMachineUpdate` and, if no single replay set reaches the 70% agreement threshold, falls back to:

```
libsigner/src/v0/signer_state.rs:192-276
fn find_majority_prefix_replay_set(&self, tx_replay_sets: &HashMap<ReplayTransactionSet, u32>) -> Option<ReplayTransactionSet> {
    ...
    let mut candidate_prefix = initial_set.0.clone();
    ...
    while !candidate_prefix.is_empty() {
        candidate_prefix.pop();
        total_supporting_weight = 0u32;
        for (replay_set, weight) in tx_replay_sets {
            if replay_set.0.starts_with(&candidate_prefix) {   // O(len(candidate_prefix))
                total_supporting_weight = total_supporting_weight.saturating_add(*weight);
            }
        }
        if self.reached_agreement(total_supporting_weight) { return Some(...); }
    }
    None
}
```

Each iteration of the `while` loop removes exactly one element from `candidate_prefix` and then rescans **every** entry of `tx_replay_sets`, calling `starts_with` (itself O(len(candidate_prefix))) on each. In the worst case (no signer agrees, forcing the loop to run down to an empty prefix), this is `Σ_{k=1}^{L} N·k = O(L²·N)`.

`tx_replay_set` is a field of the gossiped `StateMachineUpdate`/`StateMachineUpdateContent` message (`libsigner/src/v0/messages.rs`), capped only by the generic message-size limit `STATE_MACHINE_UPDATE_MAX_SIZE = 2 * 1024 * 1024` (2 MB) (`libsigner/src/v0/messages.rs:66`). Since each `Txid` is 32 bytes, a single signer can pack tens of thousands of transaction IDs into one `tx_replay_set` and broadcast it over StackerDB — well within the size limit and requiring no special privilege beyond being a registered signer (the "one-slot miner (plus gossip)" class: any signer, however small its weight, can post this message). `insert_update` (`libsigner/src/v0/signer_state.rs:161-167`) accepts an update from any address already known to `address_weights`, i.e. any current signer regardless of weight.

`determine_global_state` (and therefore `find_majority_prefix_replay_set`) is invoked from the hot path every time a signer's local state machine tries to compute the global view — `capitulate_viewpoint`/`capitulate_miner_view` and `get_global_tx_replay_set`, called on every event-loop tick's housekeeping pass (`docs/signer-flows.md` section 8, `stacks-signer/src/v0/signer_state.rs:888-979`, `984-1000+`). This means every signer in the network re-runs the quadratic reconciliation on essentially every tick/gossip update as long as the crafted `tx_replay_set` remains un-reconciled.

### Impact Explanation
A single low-weight signer can broadcast one 2 MB `StateMachineUpdate` with a maximal-length, no-common-prefix `tx_replay_set`. Every other signer that ingests this update into its `GlobalStateEvaluator` (which happens automatically via StackerDB sync of `StateMachineUpdate` messages, in scope per the rules) will, on each capitulation/housekeeping pass, pay O(L²) cost trying to reconcile the replay sets — with L in the tens of thousands, this is billions of comparisons per call, repeated on every tick. This directly matches the "High" impact category: **a signer wedged into never signing valid blocks** — while the event loop or state-machine update is stuck computing `find_majority_prefix_replay_set`, the signer cannot process new block proposals, cannot update its parent-tenure/miner view, and cannot advance its local state machine, producing a liveness wedge across the honest signer set for the duration the crafted update remains active in `address_updates`.

### Likelihood Explanation
Likelihood is high: constructing the crafted `tx_replay_set` requires no special access — only that of a normal registered signer able to write to its own `StateMachineUpdate` StackerDB slot (in-scope gossip). The payload is well within the existing `STATE_MACHINE_UPDATE_MAX_SIZE` limit, so no additional bypass of size checks is needed. The condition that triggers the fallback path (`found_replay_set.is_none()`) is easy to reach: the attacker just needs their replay set to disagree with everyone else's (trivial, since it's their own message) and for no one else's replay set to independently cross the 70% agreement threshold on its own (already the common case whenever a live transaction-replay is genuinely in progress and signers haven't yet converged).

### Recommendation
Replace the "truncate-by-one and rescan-everything" loop with a linear algorithm, e.g.:
- Precompute, for the maximum-weight candidate, cumulative "still-supports-this-length" bitmasks in a single O(N·L) pass (walking all sets simultaneously instead of restarting per truncation), or
- Use a trie/radix structure over the replay sets so that the longest majority-supported prefix can be found in O(N·L) total instead of O(N·L²).
- Additionally, bound `ReplayTransactionSet` length independently of the generic 2 MB message cap (e.g., cap the number of txids to a small constant tied to realistic replay scenarios), so that even a linear-time fix cannot be pushed into pathological territory by a single gossiping signer.

### Proof of Concept
1. Attacker controls one registered signer address (any weight) and constructs a `StateMachineUpdate`/`StateMachineUpdateContent` whose `tx_replay_set` contains ~60,000 distinct, adversarially-ordered `Txid`s (fits under the 2 MB `STATE_MACHINE_UPDATE_MAX_SIZE` cap).
2. Attacker publishes this update to their `StateMachineUpdate` StackerDB slot (`MessageSlotID::StateMachineUpdate`), which is normal gossip traffic every signer subscribes to.
3. Every honest signer's `GlobalStateEvaluator::insert_update` accepts it (`libsigner/src/v0/signer_state.rs:161-167`, no validation of `tx_replay_set` size/content beyond the raw message-size cap).
4. On the next `capitulate_viewpoint` / `get_global_tx_replay_set` call — which happens routinely during event-loop housekeeping (`docs/signer-flows.md` §8) — `determine_global_state` finds no exact-agreement replay set (guaranteed, since the attacker's set is unique) and falls into `find_majority_prefix_replay_set`, which iterates ~60,000 times, each iteration rescanning all `tx_replay_sets` entries and performing an O(L) `starts_with` — producing on the order of 10⁹+ operations per call, repeated on essentially every subsequent tick until the attacker's update is superseded or cleared, wedging each honest signer's state-machine progression during that time.
