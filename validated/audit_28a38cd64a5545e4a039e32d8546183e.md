### Title
Unguarded `initializeConfig` Allows Any Caller to Permanently Inject a Malicious Config into `BridgeCommittee` — (`File: bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig` is an `external` function with no access-control modifier and no zero-address check on its `_config` parameter. The deployment sequence requires a separate transaction between `initialize()` and `initializeConfig()`. Any ordinary caller can front-run that window and permanently bind the committee to an attacker-controlled `IBridgeConfig` implementation, breaking every downstream bridge operation that depends on `committee.config()`.

---

### Finding Description

`BridgeCommittee.initializeConfig` is declared as:

```solidity
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
``` [1](#0-0) 

There is no `onlyOwner`, `onlyDeployer`, or any other access-control guard. The only protection is the one-time check `address(config) == address(0)`, which is satisfied by any caller before the legitimate deployer acts.

The deployment script shows the two-transaction window explicitly:

```
1. BridgeCommittee.initialize(...)   ← config is still address(0) here
2. BridgeConfig.initialize(...)
3. BridgeCommittee.initializeConfig(address(bridgeConfig))  ← race target
``` [2](#0-1) 

Between steps 1 and 3, any EOA can call `initializeConfig(malicious_address)` and win the race. Once set, the slot is permanently locked (`config != address(0)` forever).

`committee.config()` is consumed in three critical paths:

1. **`MessageVerifier.verifyMessageAndSignatures`** — chain-ID domain separation for every non-TOKEN_TRANSFER message (EMERGENCY_OP, UPGRADE, BLOCKLIST, UPDATE_BRIDGE_LIMIT, UPDATE_TOKEN_PRICE):
   ```solidity
   require(message.chainID == committee.config().chainID(), "MessageVerifier: Invalid chain ID");
   ``` [3](#0-2) 

2. **`SuiBridge._transferTokensFromVault`** — token address resolution and limit enforcement:
   ```solidity
   address tokenAddress = committee.config().tokenAddressOf(tokenID);
   ``` [4](#0-3) 

3. **`SuiBridge.onlySupportedChain` modifier** — chain support gate on every deposit/withdrawal:
   ```solidity
   require(committee.config().isChainSupported(targetChainID), ...);
   ``` [5](#0-4) 

---

### Impact Explanation

A malicious `IBridgeConfig` that returns:
- `chainID()` → any value ≠ the real chain ID: all UPGRADE, EMERGENCY_OP, and governance messages fail the chain-ID check in `MessageVerifier`, **blocking the committee's own upgrade path** and preventing recovery.
- `isChainSupported()` → `false` for all chains: every `bridgeERC20` / `bridgeETH` deposit and every `transferBridgedTokensWithSignatures` withdrawal reverts, **permanently locking all funds in the vault**.
- `tokenAddressOf()` → `address(0)`: `_transferTokensFromVault` hits `require(tokenAddress != address(0), "SuiBridge: Unsupported token")` and reverts on every withdrawal.

Because the UPGRADE message itself is gated behind the same `committee.config().chainID()` check, the committee cannot self-rescue via `upgradeWithSignatures` unless they can sign a message whose `chainID` matches whatever the malicious contract returns — which is attacker-controlled and can be made to change or revert.

This satisfies the **permanent fund lock** impact class (High/Medium).

---

### Likelihood Explanation

- The function is callable by any EOA with no preconditions beyond `config == address(0)`.
- The deployment script performs `initialize` and `initializeConfig` in separate transactions, creating a publicly observable mempool window.
- Front-running is a standard, well-understood attack on Ethereum mainnet (where the Sui bridge is deployed).
- No special knowledge or capital is required; gas cost is a single `SSTORE`.

---

### Recommendation

Add both an access-control guard and a zero-address check:

```solidity
function initializeConfig(address _config) external onlyOwner {
    require(_config != address(0), "BridgeCommittee: config cannot be zero address");
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

Alternatively, pass `_config` directly into `initialize()` and set it atomically in the same initializer call, eliminating the two-transaction window entirely.

### Proof of Concept

```solidity
// Attacker contract
contract MaliciousConfig is IBridgeConfig {
    function chainID() external pure override returns (uint8) { return 255; }
    function isChainSupported(uint8) external pure override returns (bool) { return false; }
    function tokenAddressOf(uint8) external pure override returns (address) { return address(0); }
    // ... other IBridgeConfig stubs returning zero/false
}

// Attack sequence (front-run step 3 of deploy_bridge.s.sol)
MaliciousConfig mal = new MaliciousConfig();
// Attacker observes BridgeCommittee.initialize() in mempool, submits with higher gas:
BridgeCommittee(committeeProxy).initializeConfig(address(mal));
// config is now permanently set to mal; deployer's subsequent call reverts:
// "BridgeCommittee: Config already initialized"
// All bridge operations now revert; UPGRADE path is also blocked.
