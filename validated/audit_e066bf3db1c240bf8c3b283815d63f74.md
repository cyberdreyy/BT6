## #Title
Front-runnable `AllowlistRequest` digest claiming enables griefing/DoS of Vault secrets requests via owner-mismatch rejection - (File: `core/capabilities/vault/allow_list_based_auth.go`)

### Summary
The Vault capability's `AllowListBasedAuth` flow mirrors the reported "front-runnable external call" bug class from the ZeroLend `Pool.supplyWithPermit()`/`repayWithPermit()` report. In both cases, a security-critical action is split into two steps: (1) a public, unauthenticated on-chain call whose parameters are fully visible before confirmation, and (2) a follow-up privileged operation that trusts whatever state that first call produced — without cryptographically binding the two steps to the same actor. An unprivileged attacker who observes the first call's calldata can race a duplicate call ahead of the legitimate user, corrupting the trust state consumed in step 2 and causing the legitimate user's real request to be denied (griefing, no attacker profit).

### Finding Description
Vault workflow-owner authorization for gateway-routed JSON-RPC secrets requests (`vault.secrets.create/update/delete/list`) works as follows:

1. A workflow owner computes a `requestDigest = req.Digest()` (hash of method + id + params only — it does **not** include any signature or caller identity binding) and submits it on-chain via `WorkflowRegistry.AllowlistRequest(bytes32 requestDigest, uint32 expiryTimestamp)`. The recorded `Owner` for that digest is simply `msg.sender` of this call [1](#0-0) .
2. Later, the actual JSON-RPC request (with the exact method/id/params that hash to that digest) is sent to the public Vault gateway. Node-side `allowListBasedAuth.AuthorizeRequest` recomputes the digest and looks it up among all on-chain allowlisted entries via `fetchAllowlistedItem`, which returns the **first array entry whose `RequestDigest` matches** — with no check that it is the "right" or only entry for that digest [2](#0-1) .
3. The returned entry's `Owner` field is trusted as the authorized workflow owner for the request [3](#0-2) .
4. `authorizer.authorizeRequest` then enforces that the params' declared secret owner matches this authorized owner via `validateSecretOwnersMatchAuthorized`, rejecting the request outright on mismatch [4](#0-3) [5](#0-4) .

Because `AllowlistRequest(digest, expiry)` is a plain, unauthenticated on-chain call whose calldata (the digest and expiry) is fully visible in the mempool before confirmation, and because the digest itself carries no binding to the true requester's identity or signature, an attacker can:
- Observe a pending `AllowlistRequest` transaction (or otherwise learn the digest of an upcoming legitimate request),
- Front-run it with their own `AllowlistRequest(sameDigest, anyExpiry)` call from an attacker-controlled address,
- Get their entry recorded first (or simply co-exist) in the on-chain allowlisted-requests array with `Owner = attacker`.

When the real owner's JSON-RPC request later reaches the gateway, `fetchAllowlistedItem` may return the attacker's entry (first match by digest, order-dependent, no dedup/priority logic), causing `AuthResult.workflowOwner` to be the attacker's address instead of the real owner. `validateSecretOwnersMatchAuthorized` then rejects the legitimate request because the params' declared owner (the real user) does not match the authorized owner (the attacker) — exactly the same griefing-by-corrupted-external-call-state pattern as the reported `permit()` front-running issue, just with an on-chain allowlist call replacing the ERC-2612 `permit()` call.

### Impact Explanation
This is a griefing/DoS impact with no direct attacker profit, matching the report's classified impact category: a legitimate workflow owner's secrets create/update/delete/list request is denied because the authorization owner resolved from the allowlist no longer matches them, requiring the user to detect the failure and resubmit (and remains vulnerable to repeat griefing as long as digests are predictable/observable pre-confirmation). It does not directly leak secrets since `validateSecretOwnersMatchAuthorized` still blocks cross-owner access, but it denies service to the real user.

### Likelihood Explanation
Exploitability requires the attacker to observe a pending, unconfirmed `AllowlistRequest(digest, expiry)` transaction (e.g., via mempool monitoring on the underlying chain) and race it with their own transaction — a well-established front-running technique. No privileged keys, node access, or protocol-owner permissions are needed; only mempool visibility and a small amount of gas, making it reachable purely from an unprivileged external actor.

### Recommendation
Bind the on-chain digest allowlisting to the intended requester before it becomes actionable, e.g.: require the `AllowlistRequest` call (or the digest itself) to include a signature over `(requestDigest, expiry, workflowOwner)` verified against an already-linked owner (similar to the existing `LinkOwner` ownership-proof flow), and have `fetchAllowlistedItem`/`AuthorizeRequest` reject ambiguous digests that resolve to more than one distinct `Owner`, rather than silently picking the first match.

### Proof of Concept
1. Legitimate owner `U` prepares a `vault.secrets.create` request body producing `digest D`.
2. `U` submits `AllowlistRequest(D, expiryU)` to the chain; the tx sits in the mempool with `D` visible in calldata.
3. Attacker `A` observes `D` in the mempool and submits `AllowlistRequest(D, expiryA)` from their own address with higher gas, getting mined first.
4. `U`'s tx also gets mined (if the contract permits multiple entries for the same digest) or reverts (if it does not) — either way `U`'s intended authorization state is now polluted.
5. `U` sends the actual JSON-RPC request (matching digest `D`) to the Vault gateway. `allowListBasedAuth.fetchAllowlistedItem` returns `A`'s entry first (see loop in `core/capabilities/vault/allow_list_based_auth.go` lines 113-120), so `AuthResult.workflowOwner = A`.
6. `authorizer.authorizeRequest` calls `validateSecretOwnersMatchAuthorized(req, A)`; since the params declare owner `U`, the check fails and the legitimate request is rejected — griefing `U` without any gain to `A`.
