### Title
Signer treats a failed "is this the latest tenure block?" liveness check as a pass at the final pre-commit signing gate, letting it sign a stale/conflicting block - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_latest_block_in_tenure` is the one function that answers "does this proposal still confirm the tenure's actual latest block?" It is re-run immediately before a signer converts a pre-commit into an irreversible signature. When the RPC call it uses to ask the node for ground truth (`client.get_tenure_tip`) fails or times out, the function does not abstain — it returns `Ok(true)`, i.e. "the proposal is fine, sign it." A transient RPC hiccup on the signer's own node at exactly the wrong moment therefore removes the very check that exists to catch a signer whose local DB is behind the network.

### Finding Description
`check_latest_block_in_tenure` first tries to veto a proposal using purely local knowledge (`get_tenure_last_block_info`/`get_last_accepted_block`). Only when the local signer DB has no relevant record does it fall back to asking the node directly: [1](#0-0) 

The comment above the function explicitly frames the `Ok(true)` fallback as "safe" because the proposal will ultimately be checked by the node's `/v3/block_proposal` endpoint: [2](#0-1) 

That reasoning only holds at proposal-arrival time. But `check_latest_block_in_tenure` (via `check_block_against_signer_db_state`) is also the "one last look" gate run right before a signer turns a pre-commit into a signature, once the 70% pre-commit weight threshold has been reached: [3](#0-2) [4](#0-3) 

At this point the block is *not* resubmitted to the node's full `/v3/block_proposal` validation — the node's earlier "OK" plus this local re-check is the only thing standing between "pre-committed" and "SIGN, an irreversible act" (see `docs/signer-flows.md` sections 4–5, and section 7's own diagram labeling the "node unreachable" branch as passing): [5](#0-4) [6](#0-5) 

So the "backstop" the code comment relies on (the node's proposal-validation endpoint) is not actually consulted again at the moment this fallback fires. The fallback is exercised precisely in the case this check exists to cover: the signer's local DB has no fresh record of the tenure's real latest block (e.g., after a restart, a missed StackerDB message, or simply because another signer's node saw a later block first) and the signer must ask its own node for the truth. If that single RPC call errors or times out — which needs no signer collusion, no majority, and no malicious miner behavior, just ordinary node load/latency/restart at the wrong instant — the check silently converts an "I don't actually know" state into "confirmed fresh, sign."

This is directly analogous to the reported class of bug: consulting a liveness-sensitive oracle/check and, on failure to get a live answer, defaulting to "assume everything is fine" instead of refusing to act. Here the "oracle" is the signer's own node RPC, and the irreversible action gated on it is a **block signature**, not a swap.

### Impact Explanation
This can produce a signer signature over a block that is stale or conflicts with the tenure's actual latest block — an equivocation-guard failure precisely in the one place (`check_block_against_signer_db_state` right before `mark_locally_accepted`) designed to prevent it. A signer whose local view of a tenure is behind (through no fault of its own) can be pushed into signing a conflicting/non-canonical block purely because a single RPC call to its own node failed at the pre-commit threshold moment. This falls under the Critical bucket: a signer signing an invalid/non-canonical/conflicting block.

### Likelihood Explanation
No majority of signers, no other signer's key, and no auth-token/local access is required — only: (a) the local signer DB lacking a fresh record for the tenure (routine after restart or a missed message, and explicitly anticipated by the surrounding code/comments), and (b) a single failed/timed-out RPC call to the signer's own node at the pre-commit-threshold instant, which is a normal operational occurrence (node restart, GC pause, load spike, connection reset). A one-slot miner or ordinary network gossip is sufficient to get a proposal to 70% pre-commit weight and trigger this exact recheck window; the RPC failure itself is a liveness condition, not an adversarial input, which is precisely the class of bug the reported Arbitrum-sequencer issue highlights (missing safety net when a liveness dependency is unavailable at a critical decision point).

### Recommendation
Do not treat an unanswerable `get_tenure_tip` lookup as "pass" when it is invoked from the pre-commit/signing recheck path (`check_block_against_signer_db_state`). At minimum, differentiate the proposal-arrival call site (where the node's own `/v3/block_proposal` validation is still forthcoming and can serve as the real backstop) from the pre-commit/signing call site (where no further node validation will occur before the signature is produced). At the signing gate, a connectivity failure should result in `RejectReason::ConnectivityIssues`/abstention (as already done elsewhere in this function via `SignerChainstateError`/`ClientError`), not `Ok(true)`.

### Proof of Concept
1. Signer `S` restarts (or otherwise has no local `BlockInfo` for tenure `T`, e.g., `get_tenure_last_block_info`/`get_last_accepted_block` both return `None` — a routine, non-adversarial state).
2. A block `B` is proposed for tenure `T`; `S` validates it via its node's `/v3/block_proposal`, which returns OK because *the node itself* also has stale/partial knowledge of `T`'s progress at that moment (e.g., it hasn't yet processed a `NewBlock` event for a fresher sibling `B'` that other signers have already signed).
3. `S` pre-commits to `B`. Enough other signers' pre-commits arrive to cross the 70% threshold.
4. `handle_block_pre_commit` re-runs `check_block_against_signer_db_state(stacks_client, &B)` → `SortitionData::check_latest_block_in_tenure(T, B, ...)`.
5. Local lookups still find nothing (still no local record of `B'`), so the function calls `client.get_tenure_tip(T)`. Simulate/observe a transient RPC failure (node briefly unreachable/timeout) at this exact call — reproducible in the existing signer test harness by pausing/stalling the node's RPC endpoint the way `signers_wait_for_validation.rs`'s `pause_commits_miner_2`/stall helpers already do for adjacent races.
6. Per lines 450–461 of `stacks-signer/src/chainstate/mod.rs`, the function returns `Ok(true)` on this error instead of propagating a rejection.
7. `check_block_against_signer_db_state` returns `None` (no rejection), so `handle_block_pre_commit` proceeds to `mark_locally_accepted` and broadcasts `S`'s signature over `B` — even though `B` does not confirm `T`'s actual latest block `B'`, which `S`'s own node would have reported had the RPC call succeeded.
