## Analysis

The root cause from the external report — a `.call{value: ...}("")` whose return data is decoded into memory even when unused, allowing a malicious recipient to return an oversized blob and force an out-of-gas revert — has a direct analog in this repository's `BaseEscrow._ethTransfer`.

### Title
Unbounded return-data copy in `_ethTransfer` enables return-bomb DoS that freezes destination escrow funds - (File: contracts/BaseEscrow.sol)

### Summary
`BaseEscrow._ethTransfer` performs a native-token transfer using the high-level `.call{value: amount}("")` syntax and destructures only the boolean success flag: `(bool success,) = to.call{ value: amount }("");`. Even though the `bytes` return value is discarded, Solidity's high-level `.call()` semantics still ABI-decode/copy the callee's full `returndata` into memory before the tuple is destructured. A malicious recipient can therefore return an arbitrarily large blob from its `receive`/`fallback` function, forcing the caller (the escrow) to pay for expanding memory to copy that blob, which can exhaust the transaction's gas and revert — a classic "return bomb" DoS, exactly matching the bug class described in the external report. [1](#0-0) 

### Finding Description
`_ethTransfer` is used throughout `EscrowSrc` and `EscrowDst` (via `_uniTransfer`) to pay out native-token amounts to addresses that originate from unprivileged, attacker-controlled `Immutables.parameters` data — specifically `integratorFeeRecipient` and `protocolFeeRecipient`, which are extracted from the `parameters` bytes blob with no address validation: [2](#0-1) 

In `EscrowDst._withdraw`, when the destination token is native (`address(0)`), the escrow performs, in sequence, an integrator-fee native transfer, a protocol-fee native transfer, a maker native transfer, and finally a safety-deposit native transfer to the caller — all via `_ethTransfer`/`_uniTransfer`: [3](#0-2) 

Because the maker (order creator) supplies the `parameters` bytes (and thus the `integratorFeeRecipient`/`protocolFeeRecipient` addresses) when the order/extension is built off-chain, an unprivileged maker can set `integratorFeeRecipient` to a contract whose fallback returns a huge blob of data. Once `integratorFeeAmount > 0` and the destination token is native, every call to `withdraw`/`publicWithdraw` on `EscrowDst` will attempt `_ethTransfer` to that malicious recipient, triggering the return-bomb and reverting the entire withdrawal transaction due to out-of-gas memory expansion — regardless of which legitimate taker or access-token holder calls it.

### Impact Explanation
This blocks the entire destination-side withdraw path (`withdraw`, `publicWithdraw`) for the life of the swap, since the malicious recipient address is baked into the immutable hash checked by `onlyValidImmutables`. Funds locked in the destination escrow (taker's deposited tokens, safety deposit, and any legitimate fee amounts) become stuck until the `DstCancellation` timelock elapses and `cancel()` (which pays the taker directly, not through the poisoned recipient) can be called. This matches the bounty's High-severity category: "temporary freezing of funds during the live swap lifecycle."

### Likelihood Explanation
Any unprivileged user acting as the maker can construct such an order/extension without needing any privileged role, malicious relayer, or bridge assumption — it only requires setting `integratorFeeRecipient` to a contract they control with `integratorFeeAmount > 0` and destination token `address(0)`, then having the swap proceed normally through `createDstEscrow`. No existing guard validates or bounds the recipient's return data size, and `_ethTransfer` forwards all available gas with no gas cap.

### Recommendation
Replace the high-level `.call()` in `_ethTransfer` with a raw assembly call that ignores return data entirely (e.g., using `call(...)` opcode directly without capturing `returndatacopy`), or cap the gas forwarded and explicitly discard return data via `assembly`, mirroring the recommendation in the external report.

### Proof of Concept
1. Deploy a malicious contract `Bomb` whose `receive()`/`fallback()` executes `assembly { return(0, 1000000) }` to return ~1MB of zeroed data.
2. As the maker, craft a limit order/extension whose `parameters` set `integratorFeeAmount > 0` and `integratorFeeRecipient = address(Bomb)`, with the destination token set to `address(0)` (native).
3. Complete the swap flow: source fill creates the src escrow, and the taker calls `createDstEscrow` funding the dst escrow with native tokens.
4. When the taker (or any access-token holder) calls `EscrowDst.withdraw`/`publicWithdraw` with the valid secret, `_withdraw` reaches `_uniTransfer(token=0, integratorFeeRecipient=Bomb, integratorFeeAmount)` → `_ethTransfer` → `Bomb.call{value:...}("")` returns the large blob → the transaction runs out of gas copying return data into memory and reverts.
5. Every subsequent withdrawal attempt reverts identically until `DstCancellation` timelock passes, at which point only `cancel()` (refund to taker) succeeds — demonstrating the funds were frozen for the intended withdraw window. [4](#0-3) [5](#0-4)

        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
