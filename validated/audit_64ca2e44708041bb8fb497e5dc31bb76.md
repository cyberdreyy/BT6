### Title
Loss-adjusted withdrawal haircut written under the post-stop epoch index lets requesters claim full un-funded receipts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`sctp_auth_ep_add_chunkid` validated capacity against the wrong constant, letting the source list grow past the copy destination. The analog here is an epoch-index mismatch: `collectWithdrawFunds` stores a stop-epoch loss under the *current* `epochNumber`, but `epochNumber` is bumped inside `deposit()` during stopEpoch settlement, so the haircut lands under epoch N+1 while every pending receipt is keyed to request epoch N. Lookups via `lastWithdrawRequest` then miss the stored price, and receipts bypass the haircut entirely.

### Finding Description
In `collectWithdrawFunds`, when the borrower funds less than `pendingWithdraws`, the strategy zeroes the pending basis and stores a recovery price:

```solidity
// IdleCreditVault.sol
pendingWithdraws = 0;
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
```

But `epochNumber` is incremented in `deposit()` (line ~610: `epochNumber += 1;`) when the CDO pushes borrower repayment during stopEpoch while `isEpochRunning()` is still true. Withdraw requests made during epoch N are recorded as `lastWithdrawRequest[user] = N` and `withdrawsRequestsByEpoch[user][N]`.

Claim resolution reads the price under the *request* epoch, not the storage epoch:

```solidity
// _claimLossAdjustedWithdrawRequest
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```

With the price stored under N+1, `lossRecoveryPriceByEpoch[N] == 0`, so `_claimLossAdjustedWithdrawRequest` returns 0 and execution falls through to `_claimFundedWithdrawRequest`. The epoch-wait guard `epochNumber <= lastWithdrawRequest[_user]` is satisfied (N+1 > N), so the user is paid the full un-haircut `withdrawsRequests[_user]` at par.

### Impact Explanation
Insolvency / theft of funded reserves. Every receipt in a loss-epoch claims the full basis even though the borrower only funded `lossRecoveryPrice * basis`. If the vault holds the reduced funded amount, the last claimants are frozen out (DoS via underflowed balance) or earlier claimants overdraw what should be haircut funds, breaking the "one receipt, haircut-adjusted payout" invariant. When `defaultRecoveryReserve != 0`, `_transferFundedClaim`'s reserve guard partially isolates default recovery funds, but all non-reserved funded balances — including amounts collected for other epochs and instant-withdraw funding — are drainable at par. In `isInterestMinted`/prefunded modes the CDO may still hold strategy tokens whose backing was already written down, amplifying the shortfall borne by honest LPs.

### Likelihood Explanation
Requires: (1) stopEpoch ordering where `deposit()` (the epoch bump) executes before `collectWithdrawFunds` — this is the natural flow since the deposit is what funds the collections, and the code comment "deposit done on stopEpoch (before setting the var to false) so we reset the counter" confirms the bump happens mid-stopEpoch; (2) a partial funding (`stopEpochWithDuration(_lossAmount)` with `0 < loss < pendingBasis`), reachable whenever the borrower repays short during a stopped epoch with queued withdrawals — no privileged misbehavior needed beyond an honest shortfall. A single unprivileged requester in the request epoch triggers it. Note: if a deployment calls `collectWithdrawFunds` before the repayment deposit, the haircut lands on the correct epoch and this does not trigger; the PoC must pin down the actual call order in `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration`.

### Recommendation
Store the haircut under the request epoch it applies to rather than the live counter. Options: pass the loss epoch explicitly from the CDO (the epoch being settled), or snapshot `epochNumber` before the deposit bump, e.g. use `lossRecoveryPriceByEpoch[epochNumber - 1]` semantics derived from the pending requests' epoch, or record a `pendingWithdrawsEpoch` whenever `pendingWithdraws` first becomes nonzero and key `lossRecoveryPriceByEpoch` to it. Additionally, in `_claimFundedWithdrawRequest`, assert the claimed epoch has no stored loss price under *any* adjacent index, or have claims iterate the receipt's own `withdrawsRequestsByEpoch` keys instead of trusting `lastWithdrawRequest`.

### Proof of Concept
Conceptual Foundry fork test (Assumes `IdleCDOEpochVariant.stopEpochWithDuration` calls `strategy.deposit()` before `collectWithdrawFunds()`):

```solidity
// Epoch N running; lender deposited via CDO
vm.startPrank(cdo);
vault.requestWithdraw(amount, user, principal); // lastWithdrawRequest[user] = N
vm.stopPrank();

// Borrower repays short: stopEpochWithDuration(loss)
// internally: strategy.deposit(repaid) -> epochNumber becomes N+1
//           strategy.collectWithdrawFunds(funded) -> funded < pendingBasis
//           -> lossRecoveryPriceByEpoch[N+1] = price (WRONG EPOCH)
cdo.stopEpochWithDuration(lossAmount);

// Attacker claim: lossRecoveryPriceByEpoch[N] == 0 -> falls to funded path
// epochNumber (N+1) > lastWithdrawRequest (N) -> guard passes
cdo.claimWithdrawRequest(user);

// Expected: user received `amount` (par) instead of `amount * price / 1e18`.
// Vault balance now < sum of remaining receipt claims -> insolvency.
assertGt(underlying.balanceOf(user), amount * price / 1e18);
```

Caveat: I could not fully read `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` within the available iterations to confirm the deposit-before-collect ordering. If collections precede the epoch bump, the mismatch instead manifests as haircuts being keyed to the correct epoch — in which case this specific path is safe and no valid analog exists. The PoC assertion directly discriminates between the two orderings.
