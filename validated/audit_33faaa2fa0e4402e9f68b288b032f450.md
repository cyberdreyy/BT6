### Title
Stale-epoch instant-withdraw receipts are excluded from the default-claim basis and become unpayable or drain the recovery reserve — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to CVE-2019-11596 — where `process_lru_command` dereferenced a NULL pointer because a required argument was missing — `defaultPendingClaimBasis()` and `_claimDefaultedInstantWithdrawRequest()` look up instant-withdraw receipts through a single pointer, `instantWithdrawClaimsByEpoch[epochNumber]`. Any unfunded instant receipt recorded in an *earlier* epoch resolves to an empty (NULL-equivalent) bucket at the default epoch. It is silently dropped from `totalBasis`, inflating `defaultRecoveryPrice` for everyone else, and the affected holder's claim can never be paid.

### Finding Description
`requestInstantWithdraw` records receipts per-epoch (`instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`) and tracks only the *unfunded remainder* in `pendingInstantWithdraws` (IdleCreditVault.sol:356-375). The code comments themselves acknowledge that a partially prefunded instant queue can persist across `startEpoch`, so `pendingInstantWithdraws` can legitimately contain receipts whose per-epoch entries live under an older epoch key.

At default finalization:

- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` — **only the current epoch's** instant claims — whenever `pendingInstantWithdraws != 0` (lines 644-649). Older-epoch unfunded instant receipts contribute to `pendingInstantWithdraws` (which flips `defaultInstantWithdrawsFinalized = true`, line 696) but are absent from `totalBasis`.
- `_defaultPrefundedInstantReserve()` has the same single-epoch pointer: `instantBasis = instantWithdrawClaimsByEpoch[epochNumber]` (lines 716-723), so prefunded cash backing old receipts is misclassified.
- On claim, `_claimDefaultedInstantWithdrawRequest()` reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — again only the default epoch — returns 0 for the stale receipt, and control falls to `claimInstantWithdrawRequest`'s par-value path (lines 387-392), which calls `_transferFundedClaim`. That guard (`balance - reserve < _amount`, line 904) reverts because the stale receipt's underlying was never collected and the reserve belongs to haircutted claimants — so the claim reverts forever.

The recovery price `reserveAmount * RECOVERY_FULL / totalBasis` (line 688) is computed with too small a denominator, overpaying current-epoch and normal claimants and leaving the reserve short for the stale-receipt holder.

### Impact Explanation
Broken invariant: one receipt one payout / solvency of the recovery reserve. Quantified loss: a holder of an unfunded instant receipt of size X created before the default epoch is permanently frozen out of X underlying; additionally, recoveryPrice is inflated by roughly `reserveAmount * X / (totalBasis + X)` basis points, so other defaulted claimants are overpaid and the last claimants' transfers revert once the reserve is exhausted. Attacker role is any ordinary tranche/instant-withdraw requester; no privileged collusion is needed — the bug is triggered by sequencing a partially funded instant queue across an epoch boundary before a borrower default (borrower default is an honest event, not attacker action).

### Likelihood Explanation
Requires: (1) an instant-withdraw request that is only partially funded at an epoch boundary (explicitly supported — the CDO moves only available cash), (2) the borrower defaulting in a later epoch before the remainder is funded. Both are normal operating states for a credit vault during borrower stress, which is precisely when defaults occur.

### Recommendation
Aggregate unfunded instant claims across all open epochs when computing the basis — e.g., track a global `pendingInstantClaimsBasis` incremented at request time and decremented on claim/collect — instead of keying `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` to `instantWithdrawClaimsByEpoch[epochNumber]`. Similarly, `_claimDefaultedInstantWithdrawRequest` should clear *all* unfunded instant receipts of the user (not only `defaultRecoveryEpoch`), or maintain per-user claimable-unfunded accounting.

### Proof of Concept
Foundry fork sketch (cannot be executed here; line references from `contracts/strategies/idle/IdleCreditVault.sol`):

```solidity
// Setup: credit vault epoch running, CDO holds strategy tokens, instant withdrawals enabled.
// Epoch N:
cdoEpoch.requestInstantWithdraw(X, tranche);      // user U
// Fund only part of the instant queue at stopEpoch so that
// pendingInstantWithdraws == X_unfunded > 0 and
// instantWithdrawClaimsByEpoch[N] == X.
// Epoch N+1 starts; epochNumber is now N+1.
// Borrower defaults (honest event): cdoEpoch._handleBorrowerDefault -> defaulted.
// Owner calls finalizeDefault / finalizeDefaultRecovery( R, source ).
//   - totalBasis = activeBasis + pendingWithdraws + instantWithdrawClaimsByEpoch[N+1]
//     (== Y only; X_unfunded excluded)
//   - defaultInstantWithdrawsFinalized = true because pendingInstantWithdraws != 0
// U calls cdoEpoch.claimInstantWithdrawRequest():
//   _claimDefaultedInstantWithdrawRequest -> instantWithdrawsRequestsByEpoch[U][N+1] == 0
//   amount = instantWithdrawsRequests[U] == X
//   _transferFundedClaim: balance - defaultRecoveryReserve < X  => revert NotAllowed
// Assert: vm.expectRevert(NotAllowed.selector) — U's claim is permanently frozen.
// Assert: reserve exhausted early for subsequent claimants => their claims revert too.
```

Uncertainty I could not fully resolve without additional reads: the exact IdleCDOEpochVariant flow for `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` (whether an unfunded instant remainder can always persist across `startEpoch`, which the in-code comments on `_defaultPrefundedInstantReserve` strongly imply). If the instant queue is guaranteed to be fully funded every epoch, the stale-epoch state is unreachable and this reduces to a non-issue.
