### Title
Deleting a multisig member does not purge that member's existing confirmations on other members' pending requests, allowing a request to execute below the effective live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` counts confirmations by comparing the size of the `confirmations` set for a request to `self.num_confirmations`. When a member is removed via `DeleteMember`, `delete_member` only purges confirmations for **requests originally created by that member** — it does not scan and remove that member's confirmation entries from other pending requests that member had confirmed. As a result, a confirmation cast by an account that has since been deleted as a member can still count toward the K-of-N threshold on a different, still-pending request.

### Finding Description
`confirm()` computes the threshold check purely from the stored confirmation set size: [1](#0-0) 
It never re-validates that every account/key in `confirmations` is still a current member — it just checks `confirmations.len() as u32 + 1 >= self.num_confirmations` and, once satisfied, calls `remove_request` and `execute_request`.

`delete_member` (invoked via the `DeleteMember` request action inside `execute_request`) only removes confirmations for requests that were *created* by the deleted member: [2](#0-1) 
```
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```
This filters strictly on `r.member == member`, i.e. the request's *creator*. It does not iterate over `self.confirmations` to strip the deleted member's entry from requests created by *other* members that this member had merely confirmed. Those stale confirmations remain stored and are still counted by `confirm()`.

The binding this breaks is: **confirmations counted toward `num_confirmations` should equal confirmations cast by currently-live members**. After a `DeleteMember` action executes, the invariant `count(confirmations for request R) == count(live members who confirmed R)` no longer holds for any request R that the deleted member had confirmed but did not create.

### Impact Explanation
This falls under "Critical — a multisig request executed below threshold": an attacker (or a group of accomplices) can arrange for a pending request to receive a confirmation from a member who is later removed, and then close the threshold gap with fewer live members than `num_confirmations` actually requires. For example, with `num_confirmations = 2`: member A confirms request R (1/2). Member A is then removed via a separate `DeleteMember` request executed by other members. Member B — the only remaining live member relevant to R — confirms R, and the stale count from A (still present in `confirmations`) pushes the total to 2, executing R (e.g., a `Transfer`) with only one currently-live confirming member instead of the required two. This moves NEAR (or executes arbitrary `FunctionCall`/`AddKey`/`Transfer` actions) authorized below the configured threshold, i.e., an unauthorized move of funds/control.

### Likelihood Explanation
Reaching this requires only ordinary multisig operations already exposed to members: `add_request`/`confirm` and `DeleteMember`, no owner/foundation privilege beyond being one of the K members (which the threat model explicitly allows as "unprivileged" relative to the full committee). No redeploy, no malicious validator, no RPC interception is needed — it is a pure sequencing issue reachable by any subset of members colluding or by natural churn (e.g., offboarding a departing member while requests are in flight). This makes it a realistic, not merely theoretical, ordering bug.

### Recommendation
When executing `DeleteMember`, iterate over all entries in `self.confirmations` (not just requests created by the removed member) and remove the member's identity from each confirmation set, re-persisting the updated set. Alternatively, when counting confirmations in `confirm()`, filter out confirmations whose signer is no longer in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `num_confirmations = 2` and members `{A, B, C}`.
2. A creates and confirms request `R` (a `Transfer`) via `add_request_and_confirm` — `confirmations[R] = {A}`.
3. C creates and confirms (or A+B collude to create/confirm) a separate request `R2` containing `DeleteMember { member: A }`, reaching threshold with B and C, executing `R2` — A is removed from `self.members`, but `delete_member` only scans requests where `r.member == A` (i.e., requests A created), leaving `confirmations[R] = {A}` untouched because `R` was created by A itself in this scenario — but more generally, if R had been created by B instead, `delete_member(A)` would not touch `confirmations[R] = {A}` at all, since `r.member == A` is false for that request.
4. B confirms `R`: `confirmations[R].len() + 1 = 2 >= num_confirmations`, so `R` executes — even though A is no longer a member, so only one currently-live member (B) actually authorized it besides the stale A entry.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
