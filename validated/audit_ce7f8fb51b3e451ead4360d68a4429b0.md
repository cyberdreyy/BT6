### Title
Rejection weight tally silently corrupted by an under-scoped `PRIMARY KEY` on `block_rejection_signer_addrs` — ([File: stacks-signer/src/signerdb.rs])

### Summary
`SignerDb`'s `block_rejection_signer_addrs` table is declared with `PRIMARY KEY (signer_addr)` — keyed on the signer address alone, not on `(signer_signature_hash, signer_addr)`. All of the code that reads/writes this table (`add_block_rejection_signer_addr`, `store_and_process_block_rejection`) assumes the key is the pair `(block_sighash, signer_addr)`. The mismatch is the same bug *class* as the SmallVec report: a container is provisioned with an under-sized capacity/uniqueness domain relative to what the caller believes it holds, so writes beyond the assumed capacity silently fail/corrupt state instead of raising a hard, immediately visible error.

### Finding Description
The schema is defined as:
```rust
static CREATE_BLOCK_REJECTION_SIGNER_ADDRS_TABLE: &str = r#"
CREATE TABLE IF NOT EXISTS block_rejection_signer_addrs (
    signer_signature_hash TEXT NOT NULL,
    signer_addr TEXT NOT NULL,
    PRIMARY KEY (signer_addr)
) STRICT;"#;
``` [1](#0-0) 

but `add_block_rejection_signer_addr` looks up and writes rows as if the table were keyed on `(signer_signature_hash, signer_addr)`:
```rust
let qry = "SELECT reject_code FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1 AND signer_addr = ?2 LIMIT 1";
...
None => {
    let insert_qry = "INSERT INTO block_rejection_signer_addrs (signer_signature_hash, signer_addr, reject_code) VALUES (?1, ?2, ?3)";
    ...
}
``` [2](#0-1) 

Because the physical `PRIMARY KEY` is only `signer_addr`, once any signer address has one row in this table (from rejecting some block `A`), a later rejection of a *different* block `B` by the same address:
1. Fails the existence lookup (`WHERE signer_signature_hash=B AND signer_addr=X` → no match, since the stored row's hash is `A`), so the code falls into the `None` branch.
2. Attempts a bare `INSERT`, which violates the `PRIMARY KEY(signer_addr)` uniqueness constraint (the address already owns a row for hash `A`) and returns a SQLite constraint error.

That error propagates as `Err(DBError)` into `store_and_process_block_rejection`:
```rust
match self.signer_db.add_block_rejection_signer_addr(block_hash, signer_address, reject_reason) {
    Err(e) => { warn!("{self}: Failed to save block rejection signature: {e:?}",); }
    Ok(false) => return,
    Ok(true) => (),
}
``` [3](#0-2) 

Note the `Err(e)` arm only logs a warning and does **not** return — execution falls through into the weight-tally computation using `get_block_rejection_signer_addrs`, which will *not* contain the just-failed insert. The practical effect: after a given remote signer address is first observed rejecting any block, every subsequent rejection from that same address for any different block is silently dropped from persistence, and `compute_signature_signing_weight`/`compute_reject_code_signing_weight` (used to decide whether 30%+ weight has rejected a block, i.e. whether it should be `mark_globally_rejected`) under-counts that signer's weight forever after. [4](#0-3) 

This is exactly the analog of CVE-2021-25900's bug class: a storage structure is allocated/keyed with a capacity/uniqueness domain smaller than the logical domain the algorithm assumes (per-item vs. per-container), so once the assumed bound is exceeded, writes corrupt/drop state rather than growing correctly — here manifesting as silent, permanent data loss in the rejection tally rather than a heap overflow.

### Impact Explanation
This breaks the aggregated-weight-vs-verified-rejections equality that gates `mark_globally_rejected` in `store_and_process_block_rejection`. In a live network, distinct block proposals (different tenures/heights, or rival forks at the same height) constantly produce distinct `signer_signature_hash` values, so this bug degrades almost immediately after startup: each signer's local view of "how much weight has rejected block X" becomes an undercount for any signer address that has previously rejected a different block. This can indefinitely delay (wedge) a legitimate signer's ability to locally recognize that ≥30% weight has rejected an invalid/non-canonical block, stalling detection of bad proposals and blocking forward liveness of the local state machine — a High-severity liveness wedge per the stated impact criteria ("a signer wedged … acting on a stale … threshold").

### Likelihood Explanation
This requires only normal signer-set gossip activity (one-slot miner producing sequential/competing proposals plus StackerDB rejection gossip) — no majority collusion, no other signer's key, and no auth-token/local access is needed. It is triggered purely by the natural sequence of legitimate rejection messages a signer relays and stores in its own `SignerDb`. Existing unit tests (`duplicate_block_rejections`, `add_and_get_block_rejections`) only exercise the *same* block hash across writes and never exercise two *different* block hashes for the same signer address, so this path appears untested. I could not find or rule out a later ALTER/migration that widens the primary key within the time available; the finding rests entirely on the schema and function bodies cited above.

### Recommendation
Change the primary key of `block_rejection_signer_addrs` to the composite `(signer_signature_hash, signer_addr)` (matching the query/insert logic already used in `add_block_rejection_signer_addr`), add a migration to correct any deployed databases, and change the `Err(e)` arm in `store_and_process_block_rejection` to `return` (as the `Ok(false)` arm does) so a persistence failure cannot silently continue into the weight tally.

### Proof of Concept
1. Signer X rejects block A (any legitimate `RejectReasonPrefix`), which succeeds and inserts row `(A, X, code)` into `block_rejection_signer_addrs`. [5](#0-4) 
2. Later, the same node observes signer X reject a different block B (e.g. a rival fork block at the same height, or the next tenure's block). `add_block_rejection_signer_addr(B, X, ...)` runs the existence check keyed on `(B, X)`, finds nothing, and issues a bare `INSERT`, which violates `PRIMARY KEY(signer_addr)` since `X` already owns a row for `A`. [6](#0-5) 
3. The resulting `Err(DBError)` is only logged in `store_and_process_block_rejection`, execution continues, and `get_block_rejection_signer_addrs(B)` never returns X's weight for block B. [7](#0-6) 
4. Repeat for every subsequent block: X's rejection weight is permanently excluded from every future rejection tally computed by this node, understating `total_reject_weight` and delaying/preventing `mark_globally_rejected`.

    /// Record an observed block rejection_signature
    pub fn add_block_rejection_signer_addr(
        &self,
        block_sighash: &Sha512Trunc256Sum,
        addr: &StacksAddress,
        reject_reason: RejectReasonPrefix,
    ) -> Result<bool, DBError> {
        // If this signer/block already has a signature, do not allow a rejection
        let sig_qry = "SELECT EXISTS(SELECT 1 FROM block_signatures WHERE signer_signature_hash = ?1 AND signer_addr = ?2)";
        let sig_args = params![block_sighash, addr.to_string()];
        let exists = self.db.query_row(sig_qry, sig_args, |row| row.get(0))?;
        if exists {
            warn!("Cannot add block rejection because a signature already exists.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %addr,
                "reject_reason" => ?reject_reason
            );
            return Ok(false);
        }

        // Check if a row exists for this sighash/signer combo
        let qry = "SELECT reject_code FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1 AND signer_addr = ?2 LIMIT 1";
        let args = params![block_sighash, addr.to_string()];
        let existing_code: Option<i64> =
            self.db.query_row(qry, args, |row| row.get(0)).optional()?;

        let reject_code = reject_reason as i64;

        match existing_code {
            Some(code) if code == reject_code => {
                // Row exists with same reject_reason, do nothing
                debug!("Duplicate block rejection.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(false)
            }
            Some(_) => {
                // Row exists but with different reject_reason, update it
                let update_qry = "UPDATE block_rejection_signer_addrs SET reject_code = ?1 WHERE signer_signature_hash = ?2 AND signer_addr = ?3";
                let update_args = params![reject_code, block_sighash, addr.to_string()];
                self.db.execute(update_qry, update_args)?;
                debug!("Updated block rejection reason.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(true)
            }
            None => {
                // Row does not exist, insert it
                let insert_qry = "INSERT INTO block_rejection_signer_addrs (signer_signature_hash, signer_addr, reject_code) VALUES (?1, ?2, ?3)";
                let insert_args = params![block_sighash, addr.to_string(), reject_code];
                self.db.execute(insert_qry, insert_args)?;
                debug!("Inserted block rejection.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(true)
            }
        }
