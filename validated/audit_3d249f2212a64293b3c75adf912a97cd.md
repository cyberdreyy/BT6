### Title
Uncontrolled resource consumption in `NakamotoBlockProposal::validate_replay` via unbounded, unbudgeted transaction re-execution triggered by a crafted miner block - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
The v3 block-proposal validation path enforces a per-tx execution/analysis time budget and an overall `block_deadline` only in the *main* transaction-mining loop of `NakamotoBlockProposal::validate` [1](#0-0) . The separate `validate_replay` routine, which runs *before* that deadline is even created, re-executes candidate transactions with `TransactionResourceBudgets::unlimited()` and no per-iteration deadline check at all [2](#0-1) . A miner can craft a block whose transactions are deliberately out of step with the node's/signers' agreed replay set so that this inner loop repeatedly pops and fully executes replay-set transactions with no timeout, and the trailing "unmineable" scan does the same over the *entire remaining replay queue* [3](#0-2) .

### Finding Description
`validate()` builds a `block_deadline` and a `resource_budgets` object (with `max_duration` caps for both analysis and execution) specifically to bound the cost of validating an arbitrary, miner-supplied block [4](#0-3) . That protection is applied only inside the `for (i, tx) in self.block.txs.iter()` loop that mines transactions into the real candidate block [5](#0-4) .

`validate_replay`, called earlier in `validate()` to check the block against a transaction-replay set, does not receive or honor this deadline. Its inner "skip mismatched replay tx" loop calls `try_mine_tx_with_len` with `TransactionResourceBudgets::unlimited()` for every replay-set transaction it must pop and discard before finding (or failing to find) a match for the current block tx [6](#0-5) . After the per-block-tx loop, it additionally re-executes *every remaining* replay transaction, again unlimited, to classify them as "mineable"/"unmineable" [7](#0-6) .

`self.block.txs` is fully attacker-controlled: it is the content proposed by the current tenure's miner and forwarded, unmodified except for the trusted `replay_txs` field the signer supplies, to the node's `/v3/block_proposal` handler, which spawns a dedicated OS thread to run `validate()` [8](#0-7) . Nothing outside `validate()` enforces a wall-clock kill on that thread — `timeout_secs` is only used to compute the internal `block_deadline`, which `validate_replay` never checks. A one-slot miner can therefore submit a block whose transactions are chosen to never match the head of the replay queue (or to intentionally desync from it), forcing the validating node to spend unbounded wall-clock time inside `validate_replay` executing replay-set transactions with no per-tx timeout, no per-tx memory cap, and no overall deadline — exactly the "uncontrolled resource consumption from crafted input" pattern in the reference CVE (a decoder that lacks bounds/limits on attacker-supplied data).

### Impact Explanation
This maps to the "signer wedged into never signing valid blocks" High-impact category. Each signer only tracks a single in-flight `submitted_block_proposal` at a time [9](#0-8) ; while its node's validation thread is stuck inside the unbudgeted `validate_replay` loop, that signer cannot obtain a validation verdict for the current proposal in any bounded time, and the signer-side timeout only frees the signer's own tracking slot — it does not stop the runaway thread or its consumption of the node's chainstate/Clarity execution resources. A single crafted proposal is sufficient (no majority, no other signer's key, no `auth_token` needed by the attacker) to consume disproportionate node CPU relative to the legitimate per-tx budgets the code otherwise enforces, degrading or stalling that signer's ability to validate and sign subsequent legitimate blocks in the tenure — a liveness effect on the affected signer(s), not merely generic network flooding, since it is triggered by the content of a single proposal rather than request volume.

### Likelihood Explanation
Likelihood is bound to the tx-replay feature being active (a non-empty transaction replay set, e.g., during a signer-driven mempool replay/rollback event) and requires only the standard capability already granted to any block-proposing miner: crafting the transaction ordering/content of a proposed block. No majority of signers, no other signer's key, and no privileged access are required beyond the miner's ordinary one-slot proposal rights. This is somewhat conditional (replay sets are not always populated), which moderates otherwise-high likelihood, but the code path is exercised on every proposal validation and requires no unusual timing races.

### Recommendation
Thread the same `block_deadline` and bounded `resource_budgets` (or an appropriately scoped variant) into `validate_replay`, and check the deadline before each iteration of both the per-tx "skip mismatched replay tx" loop and the trailing "unmineable" scan, exactly as the main mining loop already does. Replace `TransactionResourceBudgets::unlimited()` in `validate_replay` with a bounded budget so that no single transaction execution triggered during replay validation can run unbounded wall-clock time, and cap the total number of replay-set transactions considered per validation call.

### Proof of Concept
1. Arrange for the signer set to have an active, non-trivial `tx_replay_set` (transaction replay in progress), so the node's `/v3/block_proposal` requests include a non-empty `replay_txs`.
2. As the current tenure's miner, propose a `NakamotoBlock` whose `txs` are ordered/crafted so that, for each block tx, many entries at the front of the replay queue must be popped and executed (via `try_mine_tx_with_len` with `TransactionResourceBudgets::unlimited()`) before a match is found or the queue is exhausted [6](#0-5) ; alternatively, include transactions that never satisfy the replay set, driving the block toward the "unmineable" full-queue rescan at lines 1056–1080.
3. Observe that the validation thread spawned by `spawn_validation_thread` runs `validate()` and spends unbounded time inside `validate_replay` before `block_deadline`/`resource_budgets` are ever consulted, since those are constructed only later in `validate()` at lines 731–753 and used only in the loop at lines 755–825.
4. Confirm the signer's own submission times out per its configured `tenure_last_block_proposal_timeout`/validation-submission timeout while the node-side thread continues consuming CPU, delaying processing of subsequent proposals routed through the same node.

*Note: I was unable to fully verify from the indexed code snippets whether any additional external watchdog (outside `postblock_proposal.rs`) kills long-running validation threads at the RPC/connection layer; if such a mechanism exists elsewhere in the node's HTTP/RPC framework, it would bound but not eliminate this issue, since Clarity execution inside a spawned OS thread generally cannot be interrupted mid-instruction by an external timeout.*
