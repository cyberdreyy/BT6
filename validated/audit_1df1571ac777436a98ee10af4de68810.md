### Title
Loss-adjusted withdraw haircut is bypassed by re-requesting in a later epoch — `lastWithdrawRequest` only tracks the newest epoch, letting defaulted/loss-adjusted receipts claim at par - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The parse-server bug is a *sanitization bypass via fallback*: when the guarded access-controlled path denied the read, the endpoint fell back to the raw record, exposing fields that policy (CLP/`protectedFields`) was supposed to strip. The credit-vault analog is the same shape: when a stop-epoch loss is applied, `IdleCreditVault` stores a haircut in `lossRecoveryPriceByEpoch[epoch]` and routes claims through the "sanitized" path `_claimLossAdjustedWithdrawRequest`. But that path is keyed on `lastWithdrawRequest[_user]` — a single-slot marker holding only the user's *latest* request epoch. By making a new withdraw request in a later epoch, the attacker overwrites the marker, the haircutted lookup returns `lossRecoveryPrice == 0`, and the claim falls through to `_claimFundedWithdrawRequest`, which pays the *aggregate* `withdrawsRequests[_user]` (including the loss-epoch basis) at par. The loss haircut — the vault's equivalent of a protected-field policy — is silently bypassed, and the strategy pays out underlyings the borrower never funded.

### Finding Description
`requestWithdraw` records receipts per epoch (`withdrawsRequestsByEpoch[_user][currentEpoch]`) and also into the aggregate `withdrawsRequests[_user]`, and unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) . The code comments explicitly acknowledge stacking requests without claiming is allowed ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch") [2](#0-1) .

When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` collects only `pendingBasis - loss` from the borrower, zeroes `pendingWithdraws`, and stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice < RECOVERY_FULL` [3](#0-2) . Holders of that epoch's receipts are meant to claim only `claimBasis * lossRecoveryPrice / RECOVERY_FULL` via `_claimLossAdjustedWithdrawRequest` — but that function derives the epoch to check from `lastWithdrawRequest[_user]` alone [4](#0-3) .

Attack trace (running → stopped-with-loss → running again):
1. Epoch N (running): attacker calls `requestWithdraw` for a large amount. `withdrawsRequests[atk] = B`, `withdrawsRequestsByEpoch[atk][N] = B`, `lastWithdrawRequest[atk] = N`.
2. Manager stops epoch N with a realized loss: `collectWithdrawFunds(lossAdjustedAmount)` sets `lossRecoveryPriceByEpoch[N] = p < 1` and `pendingWithdraws = 0`. The strategy now holds only `B * p` for that receipt bucket.
3. Epoch N+1 (running): attacker calls `requestWithdraw` for a dust amount `d`. Now `lastWithdrawRequest[atk] = N+1`, `withdrawsRequests[atk] = B + d`, `withdrawsRequestsByEpoch[atk][N+1] = d`.
4. Epoch N+1 stops normally (`epochNumber` becomes N+2). Attacker calls `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest`: `lossEpoch = lastWithdrawRequest[atk] = N+1`, `lossRecoveryPriceByEpoch[N+1] == 0` → returns 0 without clearing anything [5](#0-4) .
   - `_claimFundedWithdrawRequest`: gate `epochNumber (N+2) <= lastWithdrawRequest (N+1)` is false → proceeds; `amount = withdrawsRequests[atk] = B + d` is paid at par through `_transferFundedClaim` [6](#0-5) .

The attacker receives `B + d` instead of `B * p + d`. The `B * (1 - p)` difference was never collected from the borrower — `collectWithdrawFunds` only pulled `B * p` — so the excess is drained from underlying held for other claimants (funded receipts of other users, default recovery reserve is guarded but ordinary funded-claim liquidity is not).

Existing guards do not stop this: `_transferFundedClaim` only protects `defaultRecoveryReserve` [7](#0-6) , and the epoch-wait check in `_claimFundedWithdrawRequest` is satisfied because the attacker legitimately waited past epoch N+1.

### Impact Explanation
Direct theft / insolvency: an unprivileged tranche holder whose withdraw receipt was crystallized at a loss price `p` can recover it at par, stealing `claimBasis * (1 - p)` of underlyings that belong to other funded claimants. With a deep haircut (e.g., borrower repays 10% of pending receipts), the theft approaches the full claim basis. The invariant broken is "one receipt one haircut-adjusted payout" — the per-epoch loss price is enforced only when the loss epoch happens to be the user's *latest* request epoch.

### Likelihood Explanation
Requires a `stopEpochWithDuration` loss (partial borrower underfunding) — a normal, non-privileged-attack protocol event — and the attacker merely needs an unclaimed receipt in the loss epoch plus a second dust request in any later epoch. No privileged cooperation, no timing race; the second request is an ordinary user action. Any user with a loss-epoch receipt can do this, and the first to do so extracts the unfunded difference at the expense of everyone else.

### Recommendation
Resolve loss-adjusted claims by scanning/iterating the user's request epochs (or persisting a per-user loss-epoch marker that isn't overwritten by new requests) rather than keying solely on `lastWithdrawRequest`. Concretely: in `_claimFundedWithdrawRequest`, check `lossRecoveryPriceByEpoch` for *every* outstanding epoch in `withdrawsRequestsByEpoch[_user]` (or maintain a per-user `oldestUnsettledEpoch`), and revert or route through the haircut path if any outstanding receipt epoch has a non-zero `lossRecoveryPriceByEpoch`. Alternatively, in `requestWithdraw`, revert if the user's existing `lastWithdrawRequest` epoch has a stored `lossRecoveryPrice` that has not yet been claimed, forcing the haircutted claim first.

### Proof of Concept
Foundry fork-style PoC (against the repo's own harness conventions):

```solidity
// Assume: AA tranche deposit by attacker, epoch running, APR normal.
// 1) Attacker deposits and requests withdraw in epoch N.
uint256 basis = 100_000e6;
deal(underlying, attacker, basis);
vm.startPrank(attacker);
IERC20Detailed(underlying).approve(address(cdoEpoch), type(uint256).max);
cdoEpoch.depositAA(basis);
uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche)); // == claim basis B
vm.stopPrank();

// 2) Manager stops epoch N with a realized loss: borrower funds only p = 50%.
//    (stopEpochWithDuration -> collectWithdrawFunds(B/2) -> lossRecoveryPriceByEpoch[N] = 0.5e18)
uint256 lossAmount = requested / 2;
_stopEpochWithLoss(0, lossAmount); // helper: borrower partially repays pendingWithdraws
assertEq(strategy.lossRecoveryPriceByEpoch(0), RECOVERY_FULL / 2);

// 3) Epoch N+1 running: attacker re-requests a dust amount to overwrite lastWithdrawRequest.
vm.startPrank(attacker);
cdoEpoch.requestWithdraw(1, address(AAtranche)); // dust
vm.stopPrank();

// 4) Epoch N+1 ends normally; borrower fully repays the dust request.
_startEpochAndCheckPrices(1);
_stopEpochAndCheckPrices(1, apr, dustInterest);

// 5) Attacker claims: loss path looks up epoch N+1 (price 0), falls through
//    to the funded path which pays the aggregate (B + dust) AT PAR.
uint256 balPre = IERC20Detailed(underlying).balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();
uint256 paid = IERC20Detailed(underlying).balanceOf(attacker) - balPre;

// Expected honest payout: B * 0.5 + dust. Actual: B + dust.
assertGt(paid, requested / 2 + 1, "haircut bypassed: claimed loss-epoch basis at par");
```

The assertion shows the attacker recovered the full loss-epoch basis `B` plus dust, while the strategy only received `B/2` from the borrower for that receipt — the difference is extracted from underlying reserved for other claimants.

      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
