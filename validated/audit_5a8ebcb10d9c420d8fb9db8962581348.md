### Title
Allowed-image allowlist bypass via variable expansion occurring after `VerifyAllowedImage` validation - ([File: executors/instance/instance.go], [File: executors/internal/autoscaler/acquisition.go])

### Summary
`executor.Prepare` validates the **raw, unexpanded** `options.Build.Image.Name` against `AllowedImages` via `common.VerifyAllowedImage`, but the nested VM is later created in `acquisitionRef.createVMTunnel` using the **same field re-expanded with job variables** (`options.Build.GetAllVariables().ExpandValue(image)`). Because the value that is checked and the value that is executed are different strings, a pipeline author can smuggle a variable reference into `image:` that passes the allowlist glob match in its literal, unexpanded form, then have it expand into a different, effectively arbitrary image string when the nesting VM is actually created.

### Finding Description
In `executors/instance/instance.go`, `Prepare` performs the allowlist check directly on the job-supplied field: [1](#0-0) 

`options.Build.Image.Name` here has not been run through variable expansion.

In `executors/internal/autoscaler/acquisition.go`, `createVMTunnel` computes the image to actually hand to the nesting daemon from the *same* raw field, then expands it: [2](#0-1) 

The expanded value is what is passed to `nc.Create(ctx, image, &slot)` to actually build the nested VM: [3](#0-2) 

`VerifyAllowedImage` itself does a plain `doublestar.Match(allowedImage, options.Image)` glob comparison with no notion of variable expansion: [4](#0-3) 

Exploit flow:
1. Preconditions: instance executor, `VMIsolation.Enabled = true`, and `allowed_images` configured (e.g. `["registry.example.com/allowed-*"]`).
2. Attacker (pipeline author, fully in-scope as unprivileged) defines a job-level CI/CD variable and image such as:
   ```
   variables:
     PAYLOAD: "evil"
   image: "registry.example.com/allowed-$PAYLOAD"
   ```
3. `Prepare` validates the literal string `"registry.example.com/allowed-$PAYLOAD"` against the glob `registry.example.com/allowed-*` — this matches, because `doublestar.Match` treats `$PAYLOAD` as ordinary text, not a variable, and `*` matches any trailing text including `$PAYLOAD`. Validation passes.
4. `createVMTunnel` re-derives `image` from `options.Build.Image.Name` and expands it with `ExpandValue`, turning it into `"registry.example.com/allowed-evil"` (or any string the attacker's variable value produces, since `PAYLOAD` is fully attacker-controlled, including additional path segments, different tags, or in principle a value crafted to break out of the intended, narrower image scope the admin wrote the glob for).
5. The nested VM is created from the **expanded, admin-unintended** string, while the compliance/audit trail (the allowlist check) only ever validated the pre-expansion literal.

This is a genuine TOCTOU / validate-then-use mismatch: the string checked by the security control (`VerifyAllowedImage`) is not the string that determines the actual privileged action (`nc.Create`). Existing controls (the allowlist itself) do not stop this because the check operates on the wrong (pre-expansion) representation of the value.

Regarding the masking half of the question: GitLab Runner's job-log masking is implemented generically at the trace/writer layer, replacing all registered masked-variable substrings in any text written to the log, not specific to particular `Println`/`Warningln` call sites. I was not able to fully re-verify the masking implementation in this session (index/tool-call limits), so I cannot conclusively confirm or rule out a masking gap for `logger.Println("Creating nesting VM", image)` at acquisition.go:213. If masking is applied trace-wide as expected, an attacker-embedded masked variable value would still be redacted in the log even though it was used unmasked for VM creation; the log-echo portion of the hypothesis is therefore unconfirmed and likely not an additional independent bug, but this specific line should be reviewed to confirm secret values reaching it are covered by the masking variable registry before job start.

### Impact Explanation
This defeats the purpose of the `allowed_images` restriction for the `instance` executor with VM isolation — a runner-enforced control intended to constrain which images/VM images a job can request. A pipeline author with no more privilege than "define CI/CD variables and `image:` in `.gitlab-ci.yml`" can cause the runner to build a nested VM/image outside the intended allowlist, because the check is performed on a different string representation than the one used to act.

### Likelihood Explanation
Feasible and repeatable by any user who can edit `.gitlab-ci.yml` for a project running on a fleet with `allowed_images` + VM isolation configured — no elevated GitLab or runner-admin privileges required. The only requirement is an `allowed_images` glob broad enough to match a raw string containing `$VAR` syntax (e.g., any prefix/suffix `*` pattern, which is the common idiom for allowlists), which is a very common configuration pattern.

### Recommendation
Perform the allowlist check on the fully-expanded image string (the same value that will actually be used to create/select the VM), not on the raw field. Concretely, expand `options.Build.Image.Name` with `options.Build.GetAllVariables().ExpandValue(...)` in `executors/instance/instance.go` `Prepare` before calling `common.VerifyAllowedImage`, mirroring the exact resolution logic used later in `createVMTunnel` (including the `mapJobImageToVMImage` precedence rule), so the validated value and the executed value are guaranteed identical.

### Proof of Concept
Go differential test (conceptual, to be added near `executors/internal/autoscaler/acquisition_test.go` and `common/allowed_images_test.go`):
```go
func TestImageAllowlistBypassViaVariableExpansion(t *testing.T) {
    allowed := []string{"registry.example.com/allowed-*"}
    rawImage := "registry.example.com/allowed-$PAYLOAD"

    // 1. Simulate Prepare's validation call
    err := common.VerifyAllowedImage(common.VerifyAllowedImageOptions{
        Image:         rawImage,
        AllowedImages: allowed,
    }, testLogger)
    require.NoError(t, err) // validation passes on the raw literal

    // 2. Simulate createVMTunnel's resolution of the actually-used image
    vars := spec.Variables{{Key: "PAYLOAD", Value: "totally-different-namespace/evil:latest"}}
    actualImage := vars.ExpandValue(rawImage)

    // 3. Assert the differential: validated string != executed string,
    // and the executed string may not itself satisfy the allowlist intent.
    assert.NotEqual(t, rawImage, actualImage)
    ok, _ := doublestar.Match(allowed[0], actualImage)
    assert.False(t, ok, "expanded image no longer matches the allowlist pattern that was validated")
}
```
Expected result: the test demonstrates that `VerifyAllowedImage` approves `rawImage`, while the actually-created VM image (`actualImage`) is a different string that would fail the same allowlist check if validated directly — proving the validate/execute mismatch.
