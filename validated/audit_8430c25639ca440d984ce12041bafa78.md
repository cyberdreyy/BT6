### Title
Loss-adjusted withdraw receipts are keyed under the wrong epoch, so `stopEpochWithDuration` haircuts are never applied and underfunded receipts pay out in full - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report describes a "wrong registration key" bug class: data registered under one name is later looked up under another, silently breaking routing. The exact analog exists in `IdleCreditVault`: haircut recovery prices are stored under the post-increment `epochNumber`, while the receipts they should discount are stored under the pre-increment `lastWithdrawRequest` epoch. The lookup in `_claimLossAdjustedWithdrawRequest` therefore always misses, and loss-adjusted receipts are paid at par through the funded-claim path.

### Finding Description
In `requestWithdraw`, the user's receipt epoch is snapshotted before the next `stopEpoch` runs:

- `lastWithdrawRequest[_user] = currentEpoch` where `currentEpoch = epochNumber`, and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (IdleCreditVault.sol:259-294). Per the contract's own comment, "Epoch number is increased at stopEpoch" (IdleCreditVault.sol:322).

At epoch end, `_stopEpoch` in `IdleCDOEpochVariant` first calls `_strategy.prepareStopEpochWithApr0(_interest)` (IdleCDOEpochVariant.sol:362) — which increments `epochNumber` — and only later calls `_strategy.collectWithdrawFunds(_pendingWithdraws)` (IdleCDOEpochVariant.sol:410). When the borrower under-funds (`_amount < pendingBasis`), the recovery price is stored at the already-incremented epoch:

```solidity
// IdleCreditVault.sol:417-421
uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
if (lossRecoveryPrice == 0) revert NotAllowed();
pendingWithdraws = 0;
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice; // epoch N+1
```

But all pending receipts were recorded at epoch `N` (`lastWithdrawRequest == N`, `withdrawsRequestsByEpoch[user][N] != 0`). The claim path then reads the price under the wrong key:

```solidity
// IdleCreditVault.sol:789-800
uint256 lossEpoch = lastWithdrawRequest[_user];          // == N
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch]; // reads [N], stored at [N+1]
if (lossRecoveryPrice == 0) return amount;               // always 0 -> skips haircut
```

Execution falls through to `_claimFundedWithdrawRequest`, whose epoch gate `epochNumber <= lastWithdrawRequest[_user]` (IdleCreditVault.sol:326) evaluates to `N+1 <= N` → false → passes, and pays `withdrawsRequests[_user]` at full par (IdleCreditVault.sol:338-349).

The same stale-key miss also defeats the protective guard in `requestWithdraw` (IdleCreditVault.sol:261-270): `lossRecoveryPriceByEpoch[lossEpoch]` reads `[N]` which is 0, so a user holding a haircut receipt can stack a new request on top of it — the exact state the comment says must be prevented.

### Impact Explanation
`stopEpochWithDuration(_lossAmount)` is designed to socialize the pending share of the loss across pending receipts via `lossRecoveryPriceByEpoch`. Because the price is stored under `epochNumber` after `prepareStopEpochWithApr0` incremented it, while receipts live under `lastWithdrawRequest` epoch `N`, every pending receipt in a lossy stop is paid its full pre-loss basis. The vault only received `pendingToFund < pendingBasis` from the borrower, so paying receipts at par drains underlyings funded for other purposes (reserves, other epochs' claims), producing direct insolvency for later claimants and breaking the "loss waterfall" invariant. This is not a guardian/owner-error-only path: the price write and the claim are both deterministic given any `_lossAmount > 0`, so an unprivileged user simply calling `claimWithdrawRequest()` after a partial-loss `stopEpochWithDuration` receives more than intended — theft of the difference `claimBasis * (1 - lossRecoveryPrice)` from the shared pool.

### Likelihood Explanation
The trigger requires only that owner/manager calls `stopEpochWithDuration` with `_lossAmount > 0` and `_interest != 1` (an accepted flow: `previewLossAdjustedWithdrawFunds` exists precisely to support it) while `pendingWithdraws > 0`. Any user with a pending receipt then auto-exploits it by claiming normally — no adversarial sequencing beyond requesting a withdraw in the buffer, which is the standard path. Existing guards don't stop it: the `lossRecoveryPrice == 0` early-returns treat the miss as "no loss epoch," and the funded-claim epoch gate is satisfied because `epochNumber` was incremented.

Uncertain element I could not fully verify within budget: the exact line where `epochNumber` is incremented (inside `prepareStopEpochWithApr0` or elsewhere in the strategy's stop flow). If the increment happened strictly after `collectWithdrawFunds`, the keys would match and this bug collapses — but the comment "Epoch number is increased at stopEpoch" combined with `prepareStopEpochWithApr0` running before `collectWithdrawFunds` in `_stopEpoch`, and the guard comment stating the receipt epoch must be "preserved," strongly indicate the off-by-one ordering described above.

### Recommendation
Use a consistent epoch key. Either:
- store the haircut under the epoch in which the receipts were created, e.g. `lossRecoveryPriceByEpoch[epochNumber - 1]` or the epoch tracked for the pending batch, or
- record a dedicated `pendingReceiptsEpoch` when `pendingWithdraws` was accumulated and key `lossRecoveryPriceByEpoch` under it.

Additionally, harden `_claimLossAdjustedWithdrawRequest`/`_claimFundedWithdrawRequest` so a funded-but-haircutted epoch cannot be paid at par (e.g. revert in the funded path if `pendingBasis` was loss-adjusted for the user's receipt epoch), and add a Foundry test asserting `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0` after a partial-loss stop.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
// Fork test against IdleCDOEpochVariant + IdleCreditVault (see test/foundry/IdleCreditVault.t.sol harness)

function testLossHaircutBypassedByEpochKeyMismatch() external {
    // Setup: user deposits 10_000 underlying into AA, epoch 1 starts and runs.
    _depositWithUser(user, 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // Epoch 1 ends; stopEpoch increments strategy.epochNumber to 1.
    deal(underlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(newApr, 0);

    // Buffer period: user requests a normal withdraw. Stored under epochNumber == 1.
    vm.prank(user);
    uint256 basis = cdoEpoch.requestWithdraw(0, AAtranche);
    assertEq(strategy.lastWithdrawRequest(user), strategy.epochNumber());
    assertEq(strategy.withdrawsRequestsByEpoch(user, 1), basis);

    // Epoch 2 starts and runs to its end.
    _startEpochAndCheckPrices(0);
    uint256 lossAmount = basis / 4; // 25% pro-rata loss on pending receipts
    uint256 pendingToFund = basis - (lossAmount * basis / (activeBasis + basis));

    // Borrower only funds pendingToFund. stopEpochWithDuration(loss) succeeds.
    deal(underlying, borrower, neededFunds);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(newApr, 0, 30 days, lossAmount);

    // BUG: price stored at epochNumber == 2, receipt recorded at epoch 1.
    assertGt(strategy.lossRecoveryPriceByEpoch(2), 0);
    assertEq(strategy.lossRecoveryPriceByEpoch(strategy.lastWithdrawRequest(user)), 0); // == [1] == 0

    // User claims: _claimLossAdjustedWithdrawRequest returns 0, funded path pays full `basis`.
    uint256 balBefore = underlying.balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(user) - balBefore, basis); // should be basis * price / 1e18 < basis
}
```

Expected: the user receives `basis` at par instead of `basis * lossRecoveryPrice / 1e18`, while the strategy only collected `pendingToFund < basis`, leaving the vault short and later claimants unfunded.
