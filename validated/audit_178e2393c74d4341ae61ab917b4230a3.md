### Title
Authenticate middleware leaks raw internal/DB error messages via jsonAPIError instead of generic ErrorAuthFailed - ([File: core/web/auth/auth.go])

### Summary
`Authenticate` iterates auth methods and only continues the loop while an authMethod returns `auth.ErrorAuthFailed`; any other non-nil error breaks the loop immediately and is passed unmodified to `jsonAPIError`, which serializes `err.Error()` directly into the JSON 401 response body. Because `AuthenticateByToken` and `AuthenticateExternalInitiator` propagate raw/wrapped internal errors (e.g. non-`sql.ErrNoRows` DB lookup failures) rather than mapping them to `auth.ErrorAuthFailed`, an unauthenticated attacker who triggers such an internal error path can receive internal error text in the HTTP response instead of a generic auth failure message.

### Finding Description
In `Authenticate` [1](#0-0) , the loop logic is:
```go
for _, method := range methods {
    err = method(c, store)
    if !errors.Is(err, auth.ErrorAuthFailed) {
        break
    }
}
if err != nil {
    jsonAPIError(c, http.StatusUnauthorized, err)
    return
}
```
This only "continues trying the next authMethod" when the current err is exactly `auth.ErrorAuthFailed`. Any other error — including a raw internal/DB error — causes an immediate `break`, and that raw error is handed to `jsonAPIError`.

`jsonAPIError` [2](#0-1)  only redacts errors that are of type `*models.JSONAPIErrors`; any other error type (including plain DB errors) is serialized verbatim via `err.Error()` into the response JSON.

Two authMethods can surface such raw errors to an unauthenticated caller:
- `AuthenticateByToken` only maps `sql.ErrNoRows` / `clsessions.ErrUserSessionExpired` to `ErrorAuthFailed`; any other error from `FindUserByAPIToken` is returned as-is (`return err`) [3](#0-2) .
- `AuthenticateExternalInitiator` maps only `sql.ErrNoRows` to `ErrorAuthFailed`; any other error is wrapped with `errors.Wrap(err, "finding external initiator")` and returned, still not `ErrorAuthFailed` [4](#0-3) .

The underlying DB calls (`FindUserByAPIToken`, `FindExternalInitiator`) execute parameterized SQL queries and return raw `sqlx`/driver errors unmodified [5](#0-4) [6](#0-5) . Any error other than "no rows" (e.g., a transient DB error, connection issue, or driver-level fault) will therefore be forwarded, unsanitized, to the unauthenticated caller in the JSON 401 body.

Note that because the query parameters are bound (`$1`), a simple attacker-supplied string value alone does not obviously trigger a non-`ErrNoRows` SQL error via SQL syntax; reliable triggering of this specific error class (vs. transient DB failures) could not be confirmed from the code alone. The core defect — that the middleware's error-handling path does not sanitize non-`ErrorAuthFailed` errors before returning them to an unauthenticated client — is present regardless of the exact triggering condition.

### Impact Explanation
This is an information-disclosure issue (CWE-209): unauthenticated or minimally-privileged callers could receive internal error text (potentially including SQL driver error strings, DB error codes, or other backend implementation details) in a 401 response body. It does not itself provide authentication bypass, privilege escalation, or fund movement, but it discloses internal state that could assist further attacks (e.g., fingerprinting the schema/driver, or via the wrapped `"finding external initiator"` string, exposing lookup context). This maps to a low-severity information-leakage bounty class, not a critical auth-bypass class.

### Likelihood Explanation
Exploitability depends on reliably forcing `FindUserByAPIToken`/`FindExternalInitiator` to return an error other than `sql.ErrNoRows` while remaining reachable by an unauthenticated attacker (e.g., transient DB connectivity issues, driver-level scan errors, or malformed data in the row causing a struct-scan failure). Because the SQL query is parameterized, straightforward attacker-supplied strings are unlikely to deterministically produce such non-`ErrNoRows` errors, making exploitation environment-dependent and not trivially repeatable on a healthy DB. The code-level flaw (unsanitized error propagation) is deterministic and always present whenever such an error does occur.

### Recommendation
In `Authenticate`, treat any non-nil error from an authMethod that is not itself a well-defined "public" auth failure as an internal error: log it server-side and return a generic `auth.ErrorAuthFailed`-equivalent message to the client rather than `err.Error()`. Concretely:
- In `AuthenticateByToken` and `AuthenticateExternalInitiator`, wrap/replace non-`ErrNoRows` DB errors with a sentinel internal error, and have `Authenticate` map any such sentinel (or any error that isn't `auth.ErrorAuthFailed`) to a generic "Unauthorized" JSON body while logging the real error via `c.Error(err)` for operators only.
- Harden `jsonAPIError` to never emit raw `err.Error()` for errors originating from `core/web/auth` unless they've been explicitly classified as safe/public.

### Proof of Concept
Go unit test plan (`core/web/auth/auth_test.go`):
1. Construct a mock `Authenticator` whose `FindUserByAPIToken` returns a distinctive internal error, e.g. `errors.New("pq: connection reset by peer")` (not `sql.ErrNoRows`).
2. Build a `gin.Engine` with `Authenticate(mockStore, AuthenticateBySession, AuthenticateByToken)`, where `AuthenticateBySession` is configured to fail with `auth.ErrorAuthFailed` (no session cookie).
3. Send a request with `X-API-KEY`/`X-API-SECRET` headers set so `AuthenticateByToken` reaches the `FindUserByAPIToken` call.
4. Assert response status is 401 and assert the JSON body does **not** contain the substring `"pq: connection reset by peer"` or any DB-specific text — only assert it contains a generic message equivalent to `auth.ErrorAuthFailed.Error()`.
5. Repeat for `AuthenticateExternalInitiator` with `FindExternalInitiator` returning a non-`ErrNoRows` error and assert the wrapped `"finding external initiator: ..."` text is not present in the response body.

Expected (current, vulnerable) result: the test fails because the raw/wrapped internal error string is present in the JSON response. After the fix, the test should pass with only the generic auth-failure message returned.

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
```

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```
