### Title
Unbounded per-slot notification cost for a single `programSubscribe` scales with attacker-controlled account count under one program - ([File: rpc/src/rpc_subscriptions.rs])

### Summary
A single `programSubscribe` subscription's per-slot notification cost is driven by `bank.get_program_accounts_modified_since_parent(&params.pubkey)` followed by `filter_program_results`, both invoked from `notify_watchers` in `rpc/src/rpc_subscriptions.rs`. The number of accounts processed and encoded in this step is bounded only by how many accounts under the target program were touched in that slot, which an attacker fully controls by creating many accounts under a program they own and writing to all of them in one transaction/slot.

### Finding Description
`RpcSubscriptions::notify_watchers` iterates all program watchers in parallel and for each `SubscriptionParams::Program(params)` calls `check_commitment_and_notify` with the account-fetch closure `|bank, params| bank.get_program_accounts_modified_since_parent(&params.pubkey)` and the filter/encode function `filter_program_results` [1](#0-0) . `get_program_accounts_modified_since_parent` returns every account under the given program pubkey that was modified relative to the parent bank for that slot, with no cap on the number of returned accounts [2](#0-1) . `filter_program_results` then applies the subscription's filters and encodes matching accounts; this work scales linearly with however many modified accounts are returned, i.e., with N, the number of accounts the attacker rewrote under their own program in that slot.

The `Measure` instrumentation wraps the entire `notify_watchers` call (`total_time = Measure::start("notify_watchers")`) purely for metrics/logging purposes [3](#0-2) [4](#0-3) ; it does not cap or throttle the loop, it only records duration/counts after the fact via `datapoint_info!`.

Subscription-count limits (`SubscriberCountGuard`/`max_active_subscriptions`) cap how many *subscriptions* a client can hold, not the cost of processing a single subscription per notified slot [5](#0-4) . There is no limit tying the number of program accounts scanned/filtered/encoded per slot to a fixed bound; it is entirely a function of on-chain state under the targeted program, which the attacker (as the program's account creator) fully controls.

### Impact Explanation
This matches the Agave bounty category of "unbounded cost for a single low-rate call": a single `programSubscribe` subscription, kept open at a rate well under `CLUSTER_SLOT_TIME_TARGET / 2`, forces the pubsub notification thread to process (filter + encode) all N modified accounts under the attacker's program every time any of them changes in a slot. Because `notify_watchers` runs on a shared notification-processing path (`process_notifications`) common to all subscribers, a large-N program subscription degrades notification latency/throughput for all other subscribers on the node, not just the attacker's own connection.

### Likelihood Explanation
Feasible and repeatable with only unprivileged, permissionless actions: create a program-owned set of N accounts (e.g., via a token-like program or attacker's own on-chain program), open one `programSubscribe` for that program id, then submit one transaction per slot that touches all N accounts. No special validator/peer/gossip access or protocol violation is needed; account creation and a single subscription are both attacker-available operations, and the per-slot notification is bank-driven (any slot committing changes to the tracked accounts triggers it), not gated by additional rate limits beyond normal transaction/slot cadence.

### Recommendation
Cap the number of accounts processed per `Program` subscription per notification cycle (e.g., truncate `get_program_accounts_modified_since_parent` results to a fixed maximum, or apply a per-subscription/per-notification work budget), and/or move expensive filter+encode work for large result sets off the shared notification thread pool or apply back-pressure/coalescing so one large program subscription cannot dominate the batch alongside other subscribers's notifications.

### Proof of Concept
Integration test plan (in `rpc/src/rpc_subscriptions.rs` test module or a new integration test):
1. Set up `Bank`/`BankForks` and `RpcSubscriptions` similar to existing tests using `RpcSubscriptions::default_with_bank_forks`.
2. Create N accounts owned by a single attacker-chosen program pubkey (vary N = 10 and N = 100000), writing them all in the bank in one slot.
3. Subscribe once via `SubscriptionParams::Program` for that program id.
4. Trigger `notify_subscribers`/`notify_watchers` for the slot and measure wall-clock time (or use `Measure` directly) for the call to complete for both N values.
5. Assert that runtime grows roughly linearly with N (e.g., ratio of durations for N=100000 vs N=10 is on the order of 10,000x, not capped/sub-linear), demonstrating the cost of one subscription is unbounded by any explicit limit and instead scales with attacker-controlled on-chain account count.

struct SubscriberCountGuard(Arc<SubscriptionControlInner>);

impl SubscriberCountGuard {
    fn try_reserve(control: &Arc<SubscriptionControlInner>) -> Option<Self> {
        let max = control.max_active_subscriptions;
        control
            .subscriber_count
            .fetch_update(Ordering::Relaxed, Ordering::Relaxed, |current| {
                (current < max).then_some(current + 1)
            })
            .ok()?;
        Some(Self(Arc::clone(control)))
    }
}

impl Drop for SubscriberCountGuard {
    fn drop(&mut self) {
        self.0.subscriber_count.fetch_sub(1, Ordering::Relaxed);
    }
}
