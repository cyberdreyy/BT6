### Title
`seizeWithMemo` can be front-run by the target account, letting a seizable balance escape before enforcement completes - ([File: crates/common/precompiles/src/b20_asset/logic/v2.rs])

### Summary
`seizeWithMemo` (B20 asset/stablecoin V2 precompile logic) is a privileged compliance operation that transfers a fixed `amount` from a "seizable" account to a destination, gated only by role and policy checks, then applies the debit via `move_balance`, which reverts if the `from` balance is less than `amount` at execution time. [1](#0-0) [2](#0-1) 

### Finding Description
`seizeWithMemo` gates the `from` account only on the `SeizeExempt` policy scope, and gates `to` only on `SeizeReceiver`; it does not consult `TransferSender`/`TransferReceiver` at all, and explicitly bypasses those transfer policies by design (`seize_ignores_receiver_policy_on_to` test documents this). [3](#0-2) 
`SeizeExempt` and `TransferSender` are independent, separately-configured policy slots (distinct `B256` ids), so an account being "seizable" (not exempt from seizure) carries no guarantee that it is simultaneously blocked from initiating ordinary `transfer`/`transferFrom` calls. [4](#0-3) 
Because `seizeWithMemo`'s debit is a plain balance check performed at execution time (`from_balance < amount` -> `InsufficientBalance` revert) rather than a balance that is locked/reserved when the compliance action is initiated, the seizable account can observe the pending `seizeWithMemo` transaction in the mempool and front-run it with an ordinary `transfer` moving its funds to an unblocked address it controls before the seize lands. This mirrors the `SecondSwap_StepVesting.transferVesting` bug class: a privileged, amount-based operation on another party's balance that is invalidated by that same party racing an ordinary balance-mutating call first. [5](#0-4) 

### Impact Explanation
Where the original report's impact was "temporary DoS of a vesting transfer," here the practical impact is worse: `seizeWithMemo` exists specifically to let a token issuer freeze/reassign funds from an account judged non-exempt (e.g., for compliance/regulatory/blocklist reasons). If the flagged account can react to the pending seize by transferring its balance to a fresh, non-seizable address before the seize executes, the enforcement action either reverts (DoS on that seize call) or, more importantly, the malicious/flagged funds simply escape seizure by moving to an address not yet flagged as seizable — undermining the entire purpose of the seize capability rather than just griefing a single vesting transfer.

### Likelihood Explanation
Requires only an unprivileged account with a pending `seizeWithMemo` visible against it in the mempool and any unblocked destination address it controls under a token where the issuer has not independently mirrored `SeizeExempt` status into `TransferSender`/`TransferReceiver` policy. This is analogous to (and arguably higher-likelihood than) the original C4 finding, since it requires no cooperation from anyone but the flagged account itself, and issuers are not required by the code to keep the two policy scopes in sync.

### Recommendation
Do not rely on a live, execution-time balance check for `seizeWithMemo`'s core debit. Either (a) require/derive that an account failing `SeizeExempt` is automatically also blocked under `TransferSender` (single source of truth for "frozen" state) so it cannot move funds once flagged, or (b) snapshot/lock the target balance atomically with the seize decision (e.g., pause transfers for the account for the duration of the seize, or seize the entire current balance rather than a stale pre-computed amount) so a front-run transfer cannot invalidate or evade the enforcement action.

### Proof of Concept
1. Token issuer flags Alice as seizable by setting `SEIZE_EXEMPT_POLICY` to always-block for her (`make_seizable`), but does not (and is not required to) touch `TRANSFER_SENDER_POLICY`/`TRANSFER_RECEIVER_POLICY` for her.
2. Issuer submits `seizeWithMemo(from=Alice, to=Treasury, amount=100)`. [6](#0-5) 
3. Alice, seeing this transaction pending, submits an ordinary `transfer(to=AliceAlt, amount=100)` with higher priority/gas so it lands first; this call is unaffected by `SeizeExempt` because `transfer` only checks `TransferSender`/`TransferReceiver`. [7](#0-6) 
4. When `seizeWithMemo` executes, `move_balance` reads Alice's now-zero balance and reverts with `InsufficientBalance`, and the funds are already at `AliceAlt`, an address not (yet) marked seizable. [8](#0-7)

    ///
    /// `from` / `to` are [`NonZeroAddress`]: callers validate zero addresses (and choose the
    /// typed revert) before any policy SLOAD. `policies` carries the sender/receiver ids
    /// pre-read from their shared slot by the caller; `Some` enforces both (unprivileged
    /// path), `None` skips them (factory-privileged path).
    fn transfer_inner<S: AssetAccounting, A: PolicyAccounting>(
        &self,
        token: &mut B20AssetToken<S, A>,
        from: NonZeroAddress,
        to: NonZeroAddress,
        amount: U256,
        policies: Option<&TransferPolicyIds>,
    ) -> Result<()> {
        let from = from.get();
        let to = to.get();
        if let Some(policies) = policies {
            B20Guards::ensure_authorized_by_id(
                token,
                B20PolicyType::TransferSender.id(),
                policies.sender,
                from,
            )?;
            B20Guards::ensure_authorized_by_id(
                token,
                B20PolicyType::TransferReceiver.id(),
                policies.receiver,
                to,
            )?;
        }
        self.move_balance(token, from, to, amount)
    }

    fn seize_with_memo(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        from: Address,
        to: Address,
        amount: U256,
        memo: B256,
    ) -> Result<()> {
        B20Guards::ensure_not_paused(token, IB20::PausableFeature::SEIZE)?;
        B20Guards::ensure_token_role(token, caller, B20TokenRole::Seize)?;
        // `to != 0` guards against a disguised burn; `from != 0` guards against a disguised mint
        // (`Transfer(0x0, to, ...)`), matching `transfer_inner`.
        if to == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidReceiver { receiver: to }));
        }
        if from == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidSender { sender: from }));
        }
        if from == to {
            return Err(BasePrecompileError::revert(IB20::InvalidReceiver { receiver: to }));
        }
        B20Guards::ensure_seizable(token, from)?;
        // Gate the destination like `mint` gates `MintReceiver`: an unset scope is always-allow, so a
        // treasury need not be allowlisted by default.
        B20Guards::ensure_policy_type(token, B20PolicyType::SeizeReceiver, to)?;
        self.move_balance(token, from, to, amount)?;
