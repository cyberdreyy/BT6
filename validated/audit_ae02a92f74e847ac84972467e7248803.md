### Title
Cross-Workflow Response Injection via Request-ID Reuse in `HandleNodeTriggerResponse` - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`h.callbacks` is a single flat, user-controlled `requestID -> savedCallback` map with no binding to workflow identity beyond the string key itself. Once a request's callback is removed by `cleanupCallback` (quorum reached, `HandleNodeTriggerResponse` line 491) or by `reapExpiredCallbacks`, the same `requestID` string can be immediately reused for an unrelated workflow via `HandleUserTriggerRequest` → `setupCallback` (line 402 only checks "in-flight", not history). A late/retried node response still tagged with the old `resp.ID` can then be captured by the new `savedCallback` and injected into an unrelated workflow's `IdenticalNodeResponseAggregator`.

### Finding Description
`setupCallback` (`http_trigger_handler.go:398-435`) keys callbacks purely by the caller-supplied JSON-RPC `req.ID`, which is validated only for non-emptiness and absence of `/` in `validateRequestID` (`http_trigger_handler.go:183-195`) — there is no per-workflow or per-owner namespacing, and no server-side uniqueness/randomness is enforced (the only protection is rejecting an ID that is *currently* in-flight, line 402-405).

When request A (`requestID='X'`, workflowA) reaches quorum, `HandleNodeTriggerResponse` sends the response and then calls `h.cleanupCallback(resp.ID)` (line 491), which deletes `h.callbacks['X']` (lines 439-446). This happens strictly after `SendResponse` succeeds but independent of whether other, slower nodes for that request are still transmitting responses back to the gateway — those in-flight node responses are not cancelled or invalidated; they are echoed with the same `resp.ID='X'`.

An attacker who controls a second workflow (workflowB, assigned to a shard whose `donID` overlaps with a node from workflowA's shard) can issue `HandleUserTriggerRequest` with `req.ID='X'` immediately after A's cleanup. Since the map no longer contains `'X'`, `setupCallback` succeeds and installs a brand-new `savedCallback` for workflowB, with `responseAggregators` keyed by `donID` (lines 415-424).

If a stale/late node response for the original request A subsequently arrives with `resp.ID='X'` from a node belonging to a `donID` that workflowB is also assigned to, `HandleNodeTriggerResponse` (lines 448-467) finds `saved = h.callbacks['X']` (now workflowB's callback), resolves `shard := h.nodeAddrToShard[nodeAddr]`, and looks up `agg, ok := saved.responseAggregators[shard.donID]`. This lookup succeeds purely because the `donID` string matches — there is no check that the aggregator belongs to the same workflow/request that originally produced the node's response. `CollectAndAggregate` (`response_aggregator.go:38-75`) has no knowledge of workflow identity either; it aggregates purely on response digest, so workflowA's stale response is merged into what is now workflowB's aggregator and, if it reaches threshold, is delivered via `saved.SendResponse(...)` to the attacker's callback for workflowB — cross-workflow response injection/confusion.

None of the existing checks stop this: the "in-flight" duplicate check in `setupCallback` only blocks reuse while the old ID is still active, not after cleanup; the "not assigned to workflow" check in `HandleNodeTriggerResponse` (line 466) only validates that the *donID* is registered for whichever workflow currently owns `resp.ID`, not that the *specific in-flight request* the node is responding to is the same one.

### Impact Explanation
This constitutes cross-user/cross-workflow response confusion (explicitly named in-scope in the audit rules): a workflow owner can receive execution output that was generated for a different, unrelated workflow/request, and vice versa — an unrelated user's data (from workflowA) can be delivered into an attacker-controlled workflowB's execution result. Depending on data sensitivity in the HTTP trigger flow, this can leak the content of another party's workflow response, or corrupt/spoof the result an attacker-controlled workflow acts on (e.g., feeding forged/foreign data into downstream workflow logic).

### Likelihood Explanation
Preconditions: (1) attacker must operate at least one registered workflow (authorized key/JWT for that workflow — a normal, unprivileged capability of any gateway user), (2) attacker must know or guess the exact `requestID` string used by a different, unrelated in-flight/just-completed request, and (3) the attacker's workflow must be assigned to a shard/donID overlapping with a node still transmitting a stale response for the guessed ID. Because `requestID` is entirely free-form user input with no server-enforced randomness, and single-shard DON deployments make condition (3) trivially true (all workflows on that DON share the one donID), the main obstacle is timing/guessing the victim's ID, which is feasible if IDs are predictable/sequential or if the attacker races their own prior request against another tenant sharing infrastructure. This is a race condition, not deterministic, but repeatable with retries.

### Recommendation
Bind callbacks to the originating request more strongly than the raw string `requestID`:
- Namespace the `callbacks` map key by `(workflowID, requestID)` or embed a server-generated, non-reusable execution nonce (as already done internally via `legacyExecutionID`/`executionIDWithTriggerIndex`) rather than relying solely on the attacker-supplied `req.ID`.
- In `HandleNodeTriggerResponse`, verify that the response actually corresponds to the workflow/execution the aggregator was built for (e.g., include workflowID or the executionID in the node's echoed response and validate it matches `saved`'s expected workflow before aggregating).
- Consider retaining a short tombstone (recently-used ID) after `cleanupCallback` to reject stale node responses for already-completed requests, rather than silently allowing the ID to be adopted immediately.

### Proof of Concept
Go integration test plan (extending existing tests in `http_trigger_handler_test.go`, style of `TestHttpTriggerHandler_MultiShardQuorumRace`):
1. Build a multi-shard handler (`createMultiShardTriggerHandler`) with shard0 (`n1,n2,n3`) and shard1 (`n4,n5,n6`), both under the same `donID`s reused for two workflows.
2. Register `workflowA` assigned to shard0+shard1 and trigger `HandleUserTriggerRequest` with `req.ID = "X"`, capture `callbackA`.
3. Drive shard0 nodes (`n1,n2,n3`) to quorum with a normal response so `HandleNodeTriggerResponse` sends `callbackA`'s response and calls `cleanupCallback("X")`, removing `h.callbacks["X"]`.
4. Immediately register `workflowB` (assigned to shard1 only, sharing `donID` "don_1" with shard1 above) and call `HandleUserTriggerRequest` with the same `req.ID = "X"`, capture `callbackB`. Assert `setupCallback` succeeds (no conflict error) and `h.callbacks["X"]` now belongs to workflowB.
5. Simulate the stale/late shard1 responses for the *original* workflowA request still arriving: call `handler.HandleNodeTriggerResponse(ctx, nodeRespWithID_X_fromWorkflowA, "n4")`, `"n5"`, `"n6"`.
6. Assert (showing the bug) that `callbackB.Wait(ctx)` receives workflowA's stale response content instead of an error — i.e., `HandleNodeTriggerResponse` does NOT reject the late response as belonging to a different workflow, and `err == nil` with `aggResp` delivered to `callbackB`.
7. A fixed implementation should instead cause step 6 to error out (e.g., "response request/workflow mismatch") or the stale response should be rejected because the request context no longer matches.
