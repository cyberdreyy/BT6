### Title
Missing fee-sum validation in `createDstEscrow` allows fee amounts to exceed escrow amount, permanently bricking destination withdrawal - (File: `contracts/BaseEscrowFactory.sol`)

### Summary
`BaseEscrowFactory.createDstEscrow` deploys a destination escrow using caller-supplied `dstImmutables`, whose `parameters` field encodes `protocolFeeAmount` and `integratorFeeAmount`. Unlike the source-chain path (`_postInteraction`), which explicitly checks `integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts()` [1](#0-0) , `createDstEscrow` performs no equivalent validation of the fee amounts against `dstImmutables.amount` before deploying the clone [2](#0-1) .

### Finding Description
`EscrowDst._withdraw` computes the maker's payout as:
```
uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
``` [3](#0-2) 

Because Solidity 0.8 reverts on underflow, if `integratorFeeAmount + protocolFeeAmount > immutables.amount`, every call to `withdraw`/`publicWithdraw` on that destination escrow reverts unconditionally. `Immutables.parameters` (containing these two fee values) is supplied directly by whoever calls `createDstEscrow` — this function has no access-control restricting it to a "trusted" taker and performs no check that the encoded fee amounts are individually or jointly bounded by `dstImmutables.amount` [2](#0-1) . Contrast this with the src-side `_postInteraction` flow, which computes fee amounts from a trusted `FeeTaker._getFeeAmounts` call and then explicitly enforces the sum invariant before proceeding [1](#0-0) . This is precisely the analog of the referenced bug class: individual/no checks on fee components instead of a validated aggregate bound.

Once such a dst escrow is deployed with over-sized fees, the maker can never receive the destination funds via `withdraw`/`publicWithdraw` (both routes hit the same underflow revert in `_withdraw`) [4](#0-3) . The only remaining path is `cancel`, callable only by the `taker` after the cancellation timelock, which returns the full `amount` (and safety deposit) back to the taker, not the maker [5](#0-4) . Meanwhile, the corresponding source-chain escrow was already funded by the maker and can be withdrawn by the taker once the secret is known/shared (the standard Fusion+ resolver flow), independent of whether the destination leg ever completes successfully.

### Impact Explanation
This falls in the "destination path" pivot explicitly called out (`createDstEscrow` -> native/ERC20 funding -> destination withdraw/cancel flow) and matches an "unprivileged user" entry point since `createDstEscrow` has no privileged-caller restriction. The break of the invariant (fee sum bounded by amount) causes the destination escrow to become permanently unable to pay the maker while the taker can still reclaim (via `cancel`) or exploit the source-side secret reveal — this maps to "temporary/permanent freezing of funds during the live swap lifecycle," and in the worst case (taker already possesses/reveals the secret to redeem the source escrow while the maker's destination proceeds are permanently stuck) constitutes theft/permanent loss of the maker's expected swap proceeds.

### Likelihood Explanation
Likelihood is straightforward to trigger: any caller of `createDstEscrow` fully controls `dstImmutables.parameters` (including the two fee fields), and there is no on-chain validation tying them to `dstImmutables.amount`. No signature or Merkle relationship binds the dst-side fee fields to a maker-approved value — only off-chain trust/coordination between the maker and resolver is assumed to keep these consistent, but nothing on-chain enforces it in `createDstEscrow`.

### Recommendation
Add the same aggregate-fee check used in `_postInteraction` to `createDstEscrow`:
```solidity
uint256 integratorFeeAmount = immutables.integratorFeeAmount();
uint256 protocolFeeAmount = immutables.protocolFeeAmount();
if (integratorFeeAmount + protocolFeeAmount >= immutables.amount) revert InvalidFeeAmounts();
```
placed before the escrow is deployed and funded in `createDstEscrow` [2](#0-1) .

### Proof of Concept
1. Attacker (any unprivileged caller, acting as `taker`) calls `createDstEscrow` with `dstImmutables.amount = 100`, and `parameters` encoding `protocolFeeAmount = 60`, `integratorFeeAmount = 60` (sum = 120 > 100), matching the ABI layout consumed by `ImmutablesLib.integratorFeeAmountCd`/`protocolFeeAmountCd` [6](#0-5) .
2. `createDstEscrow` accepts this without any fee-sum check and deploys+funds the clone [2](#0-1) .
3. Once the maker's secret becomes available and `withdraw` is attempted, `_withdraw` computes `immutables.amount - integratorFeeAmount - protocolFeeAmount` = `100 - 60 - 60`, which underflows and reverts every time, for both `withdraw` and `publicWithdraw` [7](#0-6) .
4. The maker can never receive destination funds from this escrow; only the taker can reclaim the deposited tokens via `cancel` after the timelock [5](#0-4) , while the source-side escrow remains redeemable by the taker with the known secret.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
