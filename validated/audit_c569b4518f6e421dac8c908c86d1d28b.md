### Title
Stale `instantWithdrawsRequestsByEpoch` receipt bricks the epoch queue after same-epoch borrower default - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` counter when paying a funded instant withdrawal; it never clears the per-epoch ledgers `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. If the same epoch later ends in a borrower default, `_claimDefaultedInstantWithdrawRequest` resurrects the already-paid receipt and underflows on `instantWithdrawsRequests[_user] -= claimBasis`, permanently reverting every subsequent `claimInstantWithdrawRequest` call — which in `IdleCDOEpochQueue.processWithdrawalClaims` permanently freezes the queue's `pendingClaims` flag and blocks all future withdrawal processing.

### Finding Description
`requestInstantWithdraw` records the request in three places: the aggregate `instantWithdrawsRequests[_user]`, the per-user/per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the global per-epoch `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

When the instant receipt is funded and claimed, the "resource" is not fully cleared — only the aggregate is zeroed:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [2](#0-1) 

Neither `instantWithdrawsRequestsByEpoch[_user][epoch]` nor `instantWithdrawClaimsByEpoch[epoch]` is decremented (contrast `collectInstantWithdrawFunds`, which also only touches `pendingInstantWithdraws` [3](#0-2) ).

After a default is finalized, `claimInstantWithdrawRequest` unconditionally routes through `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and then performs `instantWithdrawsRequests[_user] -= claimBasis` [4](#0-3) [5](#0-4) . If the funded instant claim and the default share the same epoch number, `claimBasis` is the stale, already-paid amount while `instantWithdrawsRequests[_user]` is `0`, so the subtraction underflows and the whole call reverts — permanently, since no path clears the stale per-epoch entry.

### Impact Explanation
Permanent freezing of unclaimed withdrawals for all users of an `IdleCDOEpochQueue`. The sequence requires no malicious privileged role:

1. Epoch N runs with instant withdrawals enabled. Any KYC'd user (or the queue via `processWithdrawRequests`) makes an instant withdrawal and claims it at par. The queue's `instantWithdrawsRequestsByEpoch[queue][N]` remains `> 0`.
2. Epoch N ends and the borrower defaults; `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = N`, `defaultRecoveryFinalized` and `defaultInstantWithdrawsFinalized`.
3. Any later `claimInstantWithdrawRequest()` by the queue hits the stale `claimBasis` and reverts on underflow.
4. `IdleCDOEpochQueue.processWithdrawalClaims(_epoch)` calls `_cdo.claimInstantWithdrawRequest()` for instant epochs [6](#0-5) , so it reverts; `epochPendingClaims` and `pendingClaims` can never be reset [7](#0-6) .
5. `processWithdrawRequests` reverts on `pendingClaims` [8](#0-7) , and processed user withdrawals cannot be deleted (`epochWithdrawPrice` is set) or claimed (`epochPendingClaims != 0` gates `claimWithdrawRequest` [9](#0-8) ). All tranche tokens already surrendered to the queue, plus the underlying claim amount sitting at the vault, are permanently frozen. The same stale receipt also permanently blocks that user's own `claimInstantWithdrawRequest` in the vault.

The broken invariant is "one receipt one payout / cleared resource": a consumed receipt is left in the per-epoch ledger and later re-interpreted as an unpaid defaulted-epoch claim.

### Likelihood Explanation
Requires (a) instant withdrawals enabled, (b) at least one funded instant withdrawal claimed during an epoch, and (c) that same epoch ending in borrower default instead of a healthy `stopEpoch`. Defaults are a designed-for state of a credit vault (`_handleBorrowerDefault`/`finalizeDefaultRecovery` exist precisely for this), and the attacker needs no special position — any unprivileged user requesting an instant withdrawal arms the stale entry. No existing guard prevents it: the `NotAllowed` checks gate *when* claims run, but nothing clears or bounds-checks the per-epoch ledger against the aggregate before the subtraction.

### Recommendation
In `claimInstantWithdrawRequest` (funded path), clear the per-epoch records alongside the aggregate: delete `instantWithdrawsRequestsByEpoch[_user][claimEpoch]` and decrement `instantWithdrawClaimsByEpoch[claimEpoch]` for the epochs being settled (the request epoch should be tracked, e.g. via `lastInstantRequestEpoch`, or settled at request time). Additionally, make `_claimDefaultedInstantWithdrawRequest` defensive: cap `claimBasis` at `instantWithdrawsRequests[_user]` or skip when the aggregate is smaller, so a stale entry can never revert the claim path.

### Proof of Concept
Foundry fork test outline (mirroring `test/foundry/IdleCDOEpochQueue.t.sol` instant-withdraw setup):

```solidity
function testStaleInstantReceiptFreezesQueueAfterDefault() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);              // now in epoch #1 buffer

    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    address user = makeAddr('user');
    _depositWithUser(user, 100e6);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // queued instant withdrawal processed during epoch #1
    _requestWithdrawWithUser(user, /*tranches*/);
    vm.warp(block.timestamp + 101);
    vm.prank(manager);
    queue.processWithdrawRequests();              // records epoch #1 as instant
    vm.prank(manager);
    queue.processWithdrawalClaims(1);             // funded claim paid; per-epoch ledger stays dirty
    assertEq(strategy.instantWithdrawsRequests(address(queue)), 0);
    assertGt(strategy.instantWithdrawsRequestsByEpoch(address(queue), 1), 0); // stale resource

    // same epoch ends in borrower default (no repay)
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);                     // triggers default path
    // manager finalizes default recovery -> defaultRecoveryEpoch == 1

    // new epoch: queue's next instant claim now reverts forever on stale receipt
    vm.expectRevert(); // arithmetic underflow: instantWithdrawsRequests -= stale claimBasis
    queue.processWithdrawalClaims(2);

    assertTrue(queue.pendingClaims());            // never cleared -> queue frozen
}
```

Key assertion: `instantWithdrawsRequestsByEpoch[queue][1]` remains non-zero after the funded claim, and post-finalization every `claimInstantWithdrawRequest` by the queue reverts, leaving `pendingClaims == true` and blocking `processWithdrawRequests` permanently.
