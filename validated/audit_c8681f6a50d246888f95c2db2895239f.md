### Title
Missing on-chain binding of reserve-side token accounts (`reserve_liquidity_supply`, `reserve_collateral_mint`, `reserve_collateral_supply`) to the bank-approved `integration_acc_1` reserve in `solend_init_obligation` - ([File: programs/marginfi/src/instructions/solend/init_obligation.rs])

### Summary
`SolendInitObligation` binds `integration_acc_1` (the Solend reserve) to the bank via `has_one` [1](#0-0) , but the three reserve-side token accounts passed alongside it — `reserve_liquidity_supply`, `reserve_collateral_mint`, `reserve_collateral_supply` — carry no constraint tying them to `integration_acc_1`'s own stored `liquidity_supply_pubkey`, `collateral_mint_pubkey`, or `collateral_supply_pubkey` fields [2](#0-1) . All three are only annotated `/// CHECK: validated by the Solend program`, meaning marginfi relies entirely on the external Solend program to catch a mismatch.

### Finding Description
The `SolendMinimalReserve` struct that backs `integration_acc_1` does store the exact pubkeys these accounts should equal: `liquidity_supply_pubkey`, `collateral_mint_pubkey`, and `collateral_supply_pubkey` [3](#0-2) . Despite this, none of `reserve_liquidity_supply`, `reserve_collateral_mint`, `reserve_collateral_supply` in `SolendInitObligation` have a `constraint =` or `has_one` check against these fields [4](#0-3) . The instruction passes these accounts directly into the `DepositReserveLiquidityAndObligationCollateral` CPI call built in `cpi_solend_deposit` [5](#0-4) , so marginfi itself performs no verification that these belong to the same reserve as `integration_acc_1` before signing and forwarding the CPI as the bank's `liquidity_vault_authority` PDA. The same gap exists in `solend_deposit` and `solend_withdraw` [6](#0-5) [7](#0-6) , confirming this is a systemic pattern rather than an isolated oversight, and `init_obligation.rs` additionally lacks even the `is_stale()` reserve check that the other two instructions have.

### Impact Explanation
If the Solend program's own account-binding checks were ever incomplete for a given CPI call (e.g. an edge case, an unaudited code path, or a future Solend upgrade), marginfi provides no independent defense — the bank-approved `liquidity_vault_authority` PDA would sign a CPI depositing/reading state on a mismatched reserve, corrupting per-reserve accounting or misdirecting collateral state tied to the wrong reserve's supply/mint accounts. This is a durable protocol inconsistency because it is baked into an `init`-time PDA and persists across future deposit/withdraw calls that also rely on `integration_acc_1` alone for authorization while trusting caller-supplied reserve token accounts.

### Likelihood Explanation
Exploitability is entirely gated on the actual Solend program's internal validation of these three accounts, which the marginfi codebase does not itself perform or document verifying. Under the current architecture, an unprivileged caller can freely supply `reserve_liquidity_supply`/`reserve_collateral_mint`/`reserve_collateral_supply` from an arbitrary Solend reserve while keeping `integration_acc_1` correct; whether this succeeds depends solely on Solend, not marginfi.

### Recommendation
Add explicit `constraint =` checks in `SolendInitObligation` (and equivalently in `SolendDeposit`/`SolendWithdraw`) binding each reserve-side account to `integration_acc_1.load()?.liquidity_supply_pubkey`, `.collateral_mint_pubkey`, and `.collateral_supply_pubkey` respectively, so marginfi does not depend solely on the external Solend program for this invariant.

### Proof of Concept
Rust integration test plan:
1. Set up two distinct Solend reserves (`reserve_A`, `reserve_B`) with distinct liquidity/collateral supply and mint accounts, and a bank configured with `integration_acc_1 = reserve_A`.
2. Call `solend_init_obligation` with `integration_acc_1 = reserve_A` (correct) but `reserve_liquidity_supply`, `reserve_collateral_mint`, `reserve_collateral_supply` pointed at `reserve_B`'s accounts.
3. Assert that the transaction is rejected at the marginfi program level (not merely by the downstream Solend mock/program) — i.e., expect a marginfi-defined error such as a new `InvalidSolendReserveAccount` prior to CPI dispatch.
4. Currently, no such marginfi-side assertion exists; the test would show the instruction proceeds to CPI without any local check, demonstrating reliance solely on `solend_mocks`/external program validation as coded in `cpi_solend_deposit` [5](#0-4) .
