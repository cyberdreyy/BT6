### Title
Global SQL query logging can be silently toggled without a corresponding audit event, poisoning the audit trail - ([File: core/web/log_controller.go])

### Summary
`LogController.Patch` applies `SetLogSQL(*request.SQLEnabled)` unconditionally whenever `SQLEnabled` is present in the request body, but only emits the `audit.ConfigSqlLoggingEnabled`/`ConfigSqlLoggingDisabled` audit events when `request.Level == "debug"`. A caller can flip the node-wide SQL logging setting while sending no `level` field (or a non-"debug" level), causing the state change to occur with zero audit record.

### Finding Description
In `Patch` [1](#0-0) , the SQL logging flag is set as soon as `request.SQLEnabled != nil`, independent of `request.Level`. The audit emission logic is gated separately: [2](#0-1)  only calls `Audit(audit.ConfigSqlLoggingEnabled/Disabled, ...)` inside an `if request.Level == "debug"` block. A request such as `PATCH /v2/log {"sqlEnabled": true}` (with `level` omitted or set to any value other than `"debug"`) passes the initial validation check `if request.Level == "" && request.SQLEnabled == nil` (this only rejects when *both* are empty) [3](#0-2) , proceeds to line 82, flips `SetLogSQL(true)` globally, and returns a 200 response — but the `if request.Level == "debug"` guard at line 98 never executes, so no `ConfigSqlLoggingEnabled`/`Disabled` audit event is written. Only the unconditional `audit.GlobalLogLevelSet` event fires at line 96, which carries the (empty) `logLevel` value and does not reflect the SQL logging state change at all.

### Impact Explanation
This is a global, node-wide configuration change (enabling verbose SQL statement logging, which can leak secrets/bind parameters into logs) that occurs with no attributable audit trail entry, breaking the completeness/integrity guarantee that every sensitive config mutation is logged (audit trail poisoning / gap). Downstream auditors or SIEM pipelines relying on `ConfigSqlLoggingEnabled`/`ConfigSqlLoggingDisabled` events to detect when SQL logging was turned on (a precursor to secret leakage via logs) will miss this change entirely.

### Likelihood Explanation
Any principal authorized to call the `/v2/log` PATCH endpoint (which is reached via `v2Routes` in `router.go` under the standard session/API-token authenticated group) can trigger this deterministically and repeatably with a single crafted request body omitting or altering `level`. No race condition or special timing is required — this is a straightforward logic gap in the audit gating condition.

### Recommendation
Decouple the audit call from the `level == "debug"` condition: emit `audit.ConfigSqlLoggingEnabled`/`ConfigSqlLoggingDisabled` any time `request.SQLEnabled != nil` (immediately after/alongside the `SetLogSQL` call at line 82), independent of what `request.Level` is set to.

### Proof of Concept
Go handler-level test plan (extending `core/web/log_controller_test.go`):
1. Construct a mock `chainlink.Application` / audit logger (spy) that records all `Audit(eventID, data)` calls.
2. Send `PATCH /v2/log` with body `{"sqlEnabled": true}` (no `level` field).
3. Assert `cc.App.GetConfig().SetLogSQL(true)` was invoked (verify `Database().LogSQL()` returns `true` afterward).
4. Assert that the audit spy's recorded events do **NOT** contain `audit.ConfigSqlLoggingEnabled` (demonstrating the current bug), while `SetLogSQL(true)` was applied — proving the state change occurred without the audit record.
5. Add/repeat with `level: "debug"` to confirm the audit event fires in that branch, highlighting the inconsistency.
6. After the fix, assert the audit event is emitted unconditionally whenever `SQLEnabled != nil`, regardless of `Level`.
