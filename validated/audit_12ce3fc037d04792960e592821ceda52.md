**Binding claimed to break:** `last_total_balance == real contract NEAR balance` (staked + unstaked, i.e. `env::account_locked_balance() + env::account_balance()`), maintained across calls.

Tracing `internal_withdraw`: [1](#0-0) 

`internal_withdraw(amount)` performs `account.unstaked -= amount`, schedules `Promise::new(account_id).transfer(amount)`, and does `self.last_total_balance -= amount` — using the exact same `amount` value on every side of the operation. There is no share-price conversion, no U256 rounding pair, and no `staked_amount_from_num_shares_rounded_*` call anywhere in this function. Unlike `internal_stake`/`inner_unstake`, which explicitly compute a `charge_amount`/`receive_amount` via rounded share-price math and rely on the `STAKE_SHARE_PRICE_GUARANTEE_FUND` to absorb rounding, `internal_withdraw` never rounds: the amount subtracted from `account.unstaked`, the amount transferred, and the amount subtracted from `last_total_balance` are all the identical `amount` input.

Because withdrawal is a linear 1:1 operation (no division, no share conversion), repeating it — even at 1 yoctoNEAR granularity, and regardless of how much of `total_stake_shares` the caller holds — cannot introduce or accumulate any divergence between `last_total_balance` and the real balance. Each call decreases both sides by the exact same integer `amount`; there is no rounding term to drift. The only rounding-prone code paths in this contract are `stake`/`unstake` (via `num_shares_from_staked_amount_rounded_down/up` and `staked_amount_from_num_shares_rounded_down/up` in `staking-pool/src/internal.rs`), which are explicitly designed with a price-guarantee fund and a rounding pair (round down on charge, round up on total) specifically to prevent this kind of drift — and this design is unrelated to `withdraw`.

The scenario also ignores that `withdraw`/`withdraw_all` call `internal_ping` first, which resyncs `last_total_balance` to `env::account_locked_balance() + env::account_balance() - env::attached_deposit()` every time the epoch changes, further preventing any latent drift from persisting across epochs.     pub(crate) fn internal_ping(&mut self) -> bool {
        let epoch_height = env::epoch_height();
        if self.last_epoch_height == epoch_height {
            return false;
        }
        self.last_epoch_height = epoch_height;

        // New total amount (both locked and unlocked balances).
        // NOTE: We need to subtract `attached_deposit` in case `ping` called from `deposit` call
        // since the attached deposit gets included in the `account_balance`, and we have not
        // accounted it yet.
        let total_balance =
            env::account_locked_balance() + env::account_balance() - env::attached_deposit();

        assert!(
            total_balance >= self.last_total_balance,
            "The new total balance should not be less than the old total balance"
        );
