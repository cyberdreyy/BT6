### Title
Post-default instant-withdraw receipts alias the defaulted epoch slot, double-decrementing claim accounting and draining the recovery reserve — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2021-47563 is a refcount-underflow: the same `bpf_prog` pointer is treated as both the new and the old program during VSI rebuild, so `bpf_prog_put` is called on a still-referenced object. The direct analog in `IdleCreditVault` is epoch-slot aliasing in the instant-withdraw claim path: `requestInstantWithdraw` records receipts under `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and after default finalization `epochNumber` stays frozen at `defaultRecoveryEpoch`. A post-default instant request therefore writes into the same epoch bucket that `_claimDefaultedInstantWithdrawRequest` interprets as a *defaulted* receipt, so one receipt is swapped between "new funded claim" and "old defaulted claim" accounting — the same object-as-new-and-old confusion as the CVE.

### Finding Description
`requestInstantWithdraw` unconditionally adds the request to `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws`, with no `defaultRecoveryFinalized` gate or post-default bucket like `postDefaultRequests` used by the normal withdraw path [1](#0-0) .

`finalizeDefaultRecovery` snapshots `defaultRecoveryEpoch = epochNumber` and sizes `defaultRecoveryReserve` to cover `defaultPendingClaimBasis()` (pendingWithdraws + current-epoch instant claims) at `defaultRecoveryPrice` [2](#0-1) .

Because `epochNumber` is never incremented after default, a subsequent `requestInstantWithdraw` lands in `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`. When the user calls `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` reads that whole mixed bucket as `claimBasis`, zeroes it, subtracts it from `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws`, burns the receipt tokens, and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` out of `defaultRecoveryReserve` [3](#0-2) . The post-default portion was never part of the finalized `totalBasis` and added zero backing to the reserve — yet it is paid from it, and it is also double-counted in the global `instantWithdrawClaimsByEpoch`/`pendingInstantWithdraws` decrements.

### Impact Explanation
The reserve is sized exactly for finalized defaulted claims. Every post-default instant receipt paid through `_transferDefaultRecovery` withdraws unbacked funds from `defaultRecoveryReserve`, so legitimate defaulted-epoch claimants (normal and instant) find the reserve depleted and their `_transferDefaultRecovery` reverts — permanent freezing/theft of their unclaimed recovery proportional to the attacker's post-default request size, bounded only by the attacker's tranche balance (which can be acquired post-default at haircut prices via `postDefaultRequests`/tranche transfers). Loss: up to the full `defaultRecoveryReserve` for a sufficiently large attacker position.

### Likelihood Explanation
Requires only an unprivileged tranche holder calling the public `claimInstantWithdrawRequest`/`requestInstantWithdraw` path after `finalizeDefault`. Preconditions: `allowInstantWithdraw` still enabled and the CDO still routes requests post-default (no explicit guard on `defaultRecoveryFinalized` exists in `requestInstantWithdraw`, unlike the `postDefaultRequests` handling in `requestWithdraw`). No privileged misbehavior needed; honest manager/owner calls sequence the attack.

### Recommendation
Mirror the normal-withdraw fix: in `requestInstantWithdraw`, when `defaultRecoveryFinalized`, route the receipt to a post-default bucket (e.g. reuse `postDefaultRequests` or a `postDefaultInstantRequests` map) instead of `instantWithdrawsRequestsByEpoch[epochNumber]`, or revert post-default instant requests entirely. Additionally, in `_claimDefaultedInstantWithdrawRequest`, cap `claimBasis` at the pre-finalization snapshot (store `instantWithdrawClaimsByEpoch` at finalization into a dedicated `defaultInstantClaimsByEpoch`) so late writes to the same epoch slot cannot alias defaulted accounting.

### Proof of Concept
Foundry fork PoC (sketch):

```solidity
// Setup: pool running, user1 requests instant withdraw in epoch N,
// borrower defaults, manager calls finalizeDefault(recovered, manager)
// with recovered < totalBasis -> defaultRecoveryPrice < RECOVERY_FULL.
// defaultRecoveryEpoch == epochNumber (frozen).

// Attacker (unprivileged): holds/obtains tranche tokens post-default.
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(amount); // lands in instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch]

uint256 reservePre = vault.defaultRecoveryReserve();
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();   // paid from defaultRecoveryReserve at recoveryPrice
uint256 stolen = underlying.balanceOf(attacker);
assertGt(stolen, 0);
assertEq(vault.defaultRecoveryReserve(), reservePre - stolen);

// Victim: defaulted-epoch instant claimant now reverts / receives 0.
vm.prank(victim);
vm.expectRevert(); // reserve depleted
cdoEpoch.claimInstantWithdrawRequest();
```

Note: I could not fully confirm within available tooling whether `IdleCDOEpochVariant.requestInstantWithdraw` blocks post-default calls upstream; if it does not (nothing in `IdleCreditVault.requestInstantWithdraw` itself guards `defaultRecoveryFinalized`, unlike `requestWithdraw`'s explicit post-default branch), the exploit holds as described.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
