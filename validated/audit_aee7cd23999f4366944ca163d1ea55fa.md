### Title
Loss-haircutted withdraw receipts are paid at par when the user files a later request - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The kernel bug class is "a buffer captured under one regime is consumed under another" — here, a per-epoch withdraw receipt recorded under a loss-adjusted (haircutted) epoch is later claimed through the funded-at-par path because `_claimLossAdjustedWithdrawRequest` only inspects the *latest* request epoch (`lastWithdrawRequest[_user]`). Older haircutted receipts silently remain in `withdrawsRequests[_user]` and are paid 1:1, spending underlying that `collectWithdrawFunds` never transferred to the strategy.

### Finding Description
When `stopEpochWithDuration` is called with `_lossAmount > 0` and pending receipts exist, `previewLossAdjustedWithdrawFunds` computes a haircut and `collectWithdrawFunds` pulls only the reduced amount, zeroing `pendingWithdraws` and storing `lossRecoveryPriceByEpoch[epochNumber]` < 1e18 [1](#0-0) .

Receipt owners are supposed to be paid `claimBasis * lossRecoveryPrice / 1e18` via `_claimLossAdjustedWithdrawRequest`. But that function derives the claim epoch solely from `lastWithdrawRequest[_user]` [2](#0-1) :

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```

Nothing prevents a user from calling `requestWithdraw` again in a later buffer period; `requestWithdraw` overwrites `lastWithdrawRequest[_user] = currentEpoch` and adds a second `withdrawsRequestsByEpoch[_user][newEpoch]` entry while the old haircutted basis stays inside the aggregate `withdrawsRequests[_user]` [3](#0-2) .

On the next `claimWithdrawRequest`, the loss-adjusted path looks up `lossRecoveryPriceByEpoch[newEpoch]` — which is 0 if that epoch funded fully — and returns early. Execution falls through to `_claimFundedWithdrawRequest`, which pays the full `withdrawsRequests[_user]` aggregate (including the haircutted old basis) at par [4](#0-3) . The same flaw exists in the default path: `_claimDefaultedWithdrawRequest` only clears `defaultRecoveryEpoch`, and if `lastWithdrawRequest` was overwritten to a later epoch the defaulted-epoch receipt is still inside the funded aggregate.

### Impact Explanation
Direct theft / insolvency. The strategy only received `basis * price` for the loss epoch (or `reserve` for defaults), yet pays `basis` at par. The excess `basis * (1 - price)` is taken from underlying reserved for other claimants and the `defaultRecoveryReserve` guard in `_transferFundedClaim` only protects the reserve, not other funded receipts [5](#0-4) . With a 50% loss price on a 10,000-underlying receipt, the attacker extracts an extra 5,000 underlying belonging to other pending claimants, making the last claimants unpayable.

### Likelihood Explanation
Fully attacker-controlled sequencing: an unprivileged tranche holder (1) requests a withdraw during a buffer period, (2) the manager honestly calls `stopEpochWithDuration` with a realized loss, (3) the user requests a second withdraw in the following buffer — allowed since `requestWithdraw` has no existing-request check — and (4) claims after that epoch stops funded. All actors except the user are honest; no privileged misbehavior required.

### Recommendation
In `_claimLossAdjustedWithdrawRequest` and `_claimDefaultedWithdrawRequest`, iterate/scan all epochs with non-zero `lossRecoveryPriceByEpoch` / the default epoch rather than trusting `lastWithdrawRequest[_user]`, or subtract any cleared-epoch basis from `withdrawsRequests[_user]` regardless of which epoch is latest. Alternatively, revert `requestWithdraw` when the user has a receipt in an epoch with a stored recovery price that has not been claimed.

```solidity
function testLossReceiptPaidAtParAfterSecondRequest() external {
    // user holds AA tranches
    vm.startPrank(user);
    uint256 req1 = cdoEpoch.requestWithdraw(userBal / 2, address(AAtranche)); // epoch N receipt

    // manager stops epoch N with a 50% loss on pending receipts
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(newApr, 0, duration, lossAmount); // lossRecoveryPriceByEpoch[N] = 0.5e18

    // user files a second request in the new buffer
    vm.prank(user);
    cdoEpoch.requestWithdraw(userBal / 4, address(AAtranche)); // lastWithdrawRequest[user] = N+1

    // epoch N+1 runs and stops fully funded
    _startEpochAndCheckPrices(N + 1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // claim: loss-adjusted path checks epoch N+1 (price 0) -> falls through
    // to _claimFundedWithdrawRequest which pays req1 at PAR instead of 0.5x
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    // assert user received req1 + req2 instead of req1*price + req2
}
```

```text
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();

      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
