### Title
Stale `instantWithdrawsRequestsByEpoch` basis blocks post-default instant claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The Linux bug reverts a "double free" fix and instead leaks the N-th allocation: one cleanup path frees `0..N-1` while a second path believed the N-th was already freed. The direct analog in `IdleCreditVault` is the two-tier receipt accounting for instant withdrawals: `claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` but leaves the per-epoch record `instantWithdrawsRequestsByEpoch[_user][epoch]` behind — a "leaked" claim basis. If that same epoch is later finalized as defaulted, `_claimDefaultedInstantWithdrawRequest` trusts the stale per-epoch basis and underflows on the aggregate, permanently reverting the user's claim.

### Finding Description
- `requestInstantWithdraw` (IdleCreditVault.sol:356-375) records the receipt twice: `instantWithdrawsRequests[_user] += _amount` and `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount`. [1](#0-0) 
- `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393) burns the aggregate and zeroes it, but never clears `instantWithdrawsRequestsByEpoch`. The per-epoch entry survives as stale ("unfreed") state. [2](#0-1) 
- On borrower default, `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` and `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` (IdleCreditVault.sol:661-710). [3](#0-2) 
- The next `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest` (IdleCreditVault.sol:842-856), which computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — including the already-claimed leaked amount — then executes `instantWithdrawsRequests[_user] -= claimBasis`. Since the aggregate only holds the new request, this underflows and the whole call reverts, before the funded-claim fallback can pay. [4](#0-3) 

Attack sequence (unprivileged tranche holder):
1. During running epoch N, attacker requests instant withdraw of amount X, claims it once funded → aggregate 0, `ByEpoch[N] = X` (leaked).
2. Still in epoch N, attacker requests instant withdraw again for amount Y → `ByEpoch[N] = X+Y`, aggregate = Y.
3. Borrower funding fails; owner finalizes default for epoch N with `pendingInstantWithdraws != 0`.
4. Attacker's (and any identically-situated user's) `claimInstantWithdrawRequest` always reverts via `SafeMath` underflow; the Y receipt is unclaimable even though it is backed by `defaultRecoveryReserve`.

### Impact Explanation
Permanent freezing of the user's second instant-withdraw receipt (Y underlying) that is nominally covered by the default recovery reserve. The invariant "one receipt one payout" degrades to "one payout plus one bricked receipt" because the cleared aggregate and the stale per-epoch basis diverge — the exact split-brain cleanup of the kernel leak. Broken invariant: receipt bookkeeping consistency / claimability of funded receipts. Estimated loss: up to the full value of post-claim re-requested instant withdrawals in a defaulted epoch.

### Likelihood Explanation
Requires `allowInstantWithdraw` mode, a user who claims and re-requests within the same epoch, and a subsequent borrower default with unfunded instant receipts. Each condition is plausible in production; the freezing is deterministic once they coincide. No privileged attacker is needed — the victim can even be the attacker proving the revert.

### Recommendation
Mirror the kernel fix direction: make the two cleanup paths consistent. Either (a) clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` inside `claimInstantWithdrawRequest` when the aggregate is zeroed, or (b) compute the defaulted claim basis from the aggregate rather than the per-epoch map, e.g. `claimBasis = min(instantWithdrawsRequestsByEpoch[_user][defaultEpoch], instantWithdrawsRequests[_user])`. Also decrease `instantWithdrawClaimsByEpoch[epochNumber]` on successful funded claims so the epoch total stays consistent with per-user records.

### Proof of Concept
Reproducible Foundry fork PoC outline (instant-withdraw-enabled vault):
```solidity
// epoch N running, allowInstantWithdraw = true
cdoEpoch.requestInstantWithdraw(X, AAtranche);   // user
// borrower/manager funds instant queue; user claims
cdoEpoch.claimInstantWithdrawRequest();          // aggregate -> 0, ByEpoch[N] still = X
cdoEpoch.requestInstantWithdraw(Y, AAtranche);   // ByEpoch[N] = X+Y, aggregate = Y
// borrower defaults; recovery finalized with pendingInstantWithdraws > 0
vm.prank(owner); cdoEpoch.finalizeDefault(...);
// victim call
vm.prank(user);
vm.expectRevert();                               // underflow at instantWithdrawsRequests[_user] -= X+Y
cdoEpoch.claimInstantWithdrawRequest();          // Y permanently frozen
```

Caveat: I could not fully verify whether `IdleCDOEpochVariant.requestInstantWithdraw` adds a guard preventing a second instant request while a per-epoch record exists in the same epoch; if such a guard exists only on the aggregate (which is 0 after the claim), the PoC stands as written.

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
