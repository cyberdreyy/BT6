### Title
V1 signer duplicate-tenure-block check omits locally-signed-but-not-globally-accepted blocks, allowing double-signing in mixed v1/v2 signer sets - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` in the v1 chainstate module only queries `signer_db.get_last_globally_accepted_block` to detect an already-signed block in the same tenure, whereas the v2 chainstate module (`GlobalStateView::validate_tenure_change_payload`) was hardened to query `signer_db.get_last_signed_block`, which also covers locally-signed (but not yet globally accepted) blocks. During a mixed v1/v2 signer-set window (e.g., spanning a protocol-upgrade reward cycle), an attacker who wins a single miner slot can get a v1 signer to sign two conflicting blocks for the same tenure.

### Finding Description
The equality claimed is: `get_last_globally_accepted_block(tenure) == get_last_signed_block(tenure)` for duplicate-tenure-change detection. This equality is false whenever a block has been individually signed by a signer but has not (yet, or ever) reached the global 70% signature threshold.

In `stacks-signer/src/chainstate/v1.rs`, `validate_tenure_change_payload` performs: [1](#0-0) 
This only rejects a competing tenure-change proposal if a block in the same tenure was *globally* accepted.

In `stacks-signer/src/chainstate/v2.rs`, the equivalent check was changed to: [2](#0-1) 
and the accompanying comment makes explicit that this change is intentional: only blocks the signer has itself signed (locally or globally accepted) should count as "already signed" for the reorg/duplicate guard, because a pre-committed-but-unsigned block carries no signature and is safe to replace.

Root cause: v1's guard is stale relative to v2 — it fails to treat a locally-signed block as "already signed," so a v1 signer can be induced to sign two different, conflicting blocks for the same tenure-change slot.

Exploit flow:
1. Attacker wins a single sortition (their own BTC), becoming the tenure's miner.
2. Attacker proposes Block A (a tenure-change block) for tenure T. Enough v1 (and/or v2) signers evaluate and sign it individually via `check_proposal`, so each signer's local `SignerDb` records A as signed for T — but the aggregate signature never reaches the global-acceptance threshold (e.g., due to network timing/partial participation), so no signer observes A as globally accepted.
3. Attacker crafts a second, competing tenure-change Block B for the same tenure T (different fork/parent choice, still passing `check_parent_tenure_choice`/`confirms_expected_parent`) and gossips it as a new `BlockProposal`.
4. A v1 signer evaluates B via `check_proposal` → `validate_tenure_change_payload`. `get_last_globally_accepted_block(T)` returns `None` (A was never globalized), so the duplicate check is skipped and the v1 signer signs B too — despite already having signed A for the same tenure.
5. A v2 signer evaluating the same B calls `get_last_signed_block(T)`, finds A, and correctly returns `RejectReason::DuplicateBlockFound`.

This breaks the per-tenure equivocation/uniqueness guard specifically for v1 signers, allowing them to produce signatures for two conflicting blocks in the same tenure.

### Impact Explanation
This is a chain-safety violation: a signer signs a conflicting block (equivocates) for the same tenure slot, which is exactly the Critical category "a signer signing an invalid, non-canonical, or conflicting block." If enough v1 signers are induced to sign both A and B, an attacker can potentially assemble two independently-valid aggregate signatures for competing tenure-start blocks, undermining canonicity/uniqueness guarantees the signer protocol is meant to enforce. The exploit is repeatable per tenure in which the attacker holds the miner slot during the mixed-version window.

### Likelihood Explanation
Preconditions are non-trivial but plausible: they require a live period where the signer set is mixed v1/v2 (a real historical state given `chainstate/v1.rs` and `chainstate/v2.rs` coexist for the protocol upgrade), a tenure where the attacker controls the miner slot (achievable by any qualifying miner with their own BTC), and a first block that gets individually signed by at least one v1 signer without reaching global acceptance (achievable via normal network timing/partial signer participation, not requiring any privileged access). The attacker needs only their own miner slot plus the ability to gossip two competing `BlockProposal` messages — consistent with the unprivileged threat model.

### Recommendation
Update `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` to use `signer_db.get_last_signed_block` (matching v2's semantics) instead of `get_last_globally_accepted_block`, so that any block the signer has locally signed for a tenure — not only globally-accepted ones — blocks a competing tenure-change proposal for that same tenure.

### Proof of Concept
```rust
// stacks-signer/src/chainstate/tests/v1.rs (new test)
#[test]
fn v1_allows_double_sign_when_first_block_only_locally_signed() {
    // Setup: signer_db with a block A for consensus_hash `tenure_ch`
    // recorded as "signed" (state = LOCALLY_ACCEPTED or SIGNED, not GLOBALLY_ACCEPTED)
    let mut signer_db = SignerDb::new_in_memory();
    let block_a = make_tenure_change_block(tenure_ch, /*parent=*/ prior_tenure_ch);
    signer_db.insert_block_signed(&block_a); // marks locally signed, NOT globally accepted

    // sanity: v2 semantics would find it
    assert!(signer_db.get_last_signed_block(&tenure_ch).unwrap().is_some());
    // v1 semantics miss it
    assert!(signer_db.get_last_globally_accepted_block(&tenure_ch).unwrap().is_none());

    // Attacker crafts competing tenure-change block B for same tenure_ch
    let block_b = make_tenure_change_block(tenure_ch, /*parent=*/ prior_tenure_ch);

    let mut view = SortitionsView { /* cur_sortition matching tenure_ch, etc */ };
    let result = view.check_proposal(&client, &mut signer_db, &block_b, false, ReplayTransactionSet::none());

    // BUG: v1 accepts the duplicate/conflicting tenure-change block
    assert!(result.is_ok(), "v1 should have rejected duplicate but did not");

    // Compare against v2 GlobalStateView::check_proposal on the same signer_db/state,
    // which is expected to return Err(RejectReason::DuplicateBlockFound).
}
```
This test asserts the divergence directly: `get_last_signed_block` finds the conflict while `get_last_globally_accepted_block` does not, and drives `SortitionsView::check_proposal` (v1) to demonstrate it wrongly accepts (`Ok(())`) a proposal that `GlobalStateView::check_proposal` (v2) correctly rejects with `RejectReason::DuplicateBlockFound`.
