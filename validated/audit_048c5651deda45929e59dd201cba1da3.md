### Title
Coordinator double-counts a signer's weight across `total_weight_approved` and `total_weight_rejected` when a signer equivocates - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` (the node-side signature coordinator) tallies signer weight for a block proposal into two running counters, `BlockStatus.total_weight_approved` and `BlockStatus.total_weight_rejected`, guarded by two *different* dedup sets. A single signer can be counted in both buckets by first rejecting, then accepting (or vice versa) the same block, because the "already counted" check for acceptance looks at `gathered_signatures` while the "already counted" check for rejection looks at `responded_signers`, and neither branch removes the signer's weight from the other bucket. This is analogous to the reported Bitcoin Core `cachedCoinsUsage` bug: an incrementally-maintained accounting counter that is updated inconsistently relative to another piece of state tracking the same entity, corrupting the aggregate.

### Finding Description
`BlockStatus` in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` maintains, per proposed block, independent running sums for approvals and rejections: [1](#0-0) 

For an `Accepted` message, the code only adds the signer's weight to `total_weight_approved` if `gathered_signatures` does not yet contain that `slot_id`, then unconditionally inserts into both `gathered_signatures` and `responded_signers`: [2](#0-1) 

For a `Rejected` message, the code adds weight to `total_weight_rejected` only if `responded_signers.insert(slot_id)` returns `true` (i.e., the slot was not previously in `responded_signers`): [3](#0-2) 

Consider a signer that first sends `Rejected` for a block: `responded_signers` gains the slot, and `total_weight_rejected` is incremented by that signer's weight. The same signer then sends `Accepted` for the same block (a valid message it is fully entitled to send, e.g., after re-evaluating, or a malicious/buggy signer intentionally equivocating). In the `Accepted` branch, the guard checks `gathered_signatures`, not `responded_signers` — and `gathered_signatures` does *not* yet contain this slot. So the code adds the signer's weight to `total_weight_approved` as well, without ever subtracting it from `total_weight_rejected`.

The result: the same signer's weight is now counted in *both* `total_weight_approved` and `total_weight_rejected` simultaneously. The invariant that each signer's weight should be attributed to at most one of the two mutually-exclusive tallies (`total_weight_approved + total_weight_rejected <= total_weight`) is broken, exactly as `cachedCoinsUsage` no longer reflected the true state of `cacheCoins` after the flawed early-decrement in `AddCoin()`.

### Impact Explanation
This is a "rejection recounted as an accept" class bug per the accepted impact categories. `signer_coordinator.rs::get_block_status` uses these two counters directly to decide the block's fate: [4](#0-3) 

Because a single equivocating signer's weight persists in `total_weight_rejected` even after that signer switches to `Accepted`, the coordinator's rejection tally is inflated with weight that no longer reflects that signer's current vote, while the approval tally is inflated by weight that is simultaneously present in the rejection bucket. Near the 70%/30% boundary, this lets a single signer's stale rejection continue to count toward the ">30% weight" rejection cutoff at the same time its current acceptance counts toward the "≥70% weight" approval cutoff — corrupting the accounting invariant the coordinator relies on to decide between "block accepted" and "block rejected," which is the exact analog of the underflow/miscount class in the reported Bitcoin Core commit.

### Likelihood Explanation
This requires only a single signer (one StackerDB slot) sending two conflicting messages (`Rejected` then `Accepted`, or vice versa) for the same block over StackerDB gossip — well within a one-slot signer's own capability, no majority or other signer's key is needed.

### Recommendation
Use a single, unified dedup/tracking structure (e.g., one map from `slot_id` to the signer's most recent verdict) to gate both weight additions, and when a signer's verdict changes, move their weight between buckets atomically (subtract from the old bucket, add to the new one) rather than gating the two counters on two independent sets (`gathered_signatures` vs `responded_signers`).

### Proof of Concept
1. Node coordinator (`StackerDBListener`) tracks a proposed block with `BlockStatus::default()`-like initial state (`total_weight_approved = 0`, `total_weight_rejected = 0`).
2. Signer S (slot `k`, weight `w`) sends `BlockResponse::Rejected` for the block. `responded_signers.insert(k)` returns `true` → `total_weight_rejected += w`.
3. Signer S then sends `BlockResponse::Accepted` for the same block (same `signer_signature_hash`). `gathered_signatures.contains_key(k)` is `false` (never inserted there before) → `total_weight_approved += w`; `gathered_signatures.insert(k, signature)`; `responded_signers.insert(k)` (no-op, already present).
4. Now `total_weight_approved == w` and `total_weight_rejected == w` for the same signer's weight — double counted across both tallies, breaking `approved + rejected <= total_weight`, and corrupting the coordinator's accept/reject decision logic in `signer_coordinator.rs`.
