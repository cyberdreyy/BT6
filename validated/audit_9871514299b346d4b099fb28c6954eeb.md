### Title
ERC4626 liquidity exhaustion can temporarily freeze epoch settlement and LP withdrawals - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
`ProgrammableBorrower` treats vault-share value as available collateral but relies on a synchronous `vault.withdraw` during `stopEpoch`. An unprivileged user of the shared ERC4626 vault can consume the withdrawable liquidity immediately before settlement, causing the hook to revert even though `convertToAssets` still reports sufficient shares. Repeating the action keeps the epoch running and prevents queued withdrawals or pool closure from being funded.

### Finding Description
`onStartEpoch` deposits all on-hand underlying into the external ERC4626 vault, while `epochPendingWithdraws` is only an internal borrowing reserve and is not segregated from other vault liquidity consumers. [1](#0-0) [2](#0-1) 

At epoch end, `IdleCDOEpochVariant` synchronously calls `onStopEpoch`; reverts from that hook intentionally bubble out of `stopEpoch`. [3](#0-2) 

Inside the hook, `convertToAssets` is only used to distinguish insolvency from a liquidity failure. If shares nominally cover the shortfall, the contract calls `vault.withdraw(shortfall)` and reverts with `StopEpochVaultLiquidityUnavailable` whenever the external vault cannot currently release that amount. [4](#0-3) 

Therefore, a vault LP or an unprivileged borrower in the vault’s underlying liquidity venue can front-run an honest `stopEpoch` transaction and consume enough liquidity that the borrower’s withdrawal reverts. Repeating the liquidity exhaustion before each settlement attempt keeps `isEpochRunning == true`, leaves `pendingWithdraws` unpaid, and prevents a close-pool recall.

The issue is analogous to the referenced PAC/OCSP failure: a required external resource may remain economically backed but temporarily unreachable, causing the dependent security operation—in this case epoch settlement—to fail.

### Impact Explanation
For a normal stop, the frozen amount is `IdleCreditVault.pendingWithdraws`, so pending receipt holders cannot claim their principal plus settled interest. For a close-pool stop, `_totBorrowed` is added to the amount pulled, so the temporary freeze extends to active LP principal plus epoch interest. [5](#0-4) 

The quantified temporary loss is the delayed claim amount:

```solidity
normalStopFrozen  = pendingWithdraws;
closePoolFrozen   = pendingWithdraws + activePrincipal + epochInterest;
```

The attacker does not receive pool funds and cannot make the freeze permanent by itself. However, the invariant that a completed epoch can be settled and funded receipts claimed is violated for as long as the attacker can maintain the vault liquidity shortage.

### Likelihood Explanation
Likelihood depends on the selected ERC4626 vault having shared, finite withdrawal liquidity or borrowable underlying-market liquidity. The attacker needs enough vault shares, lending-market collateral, or borrowing capacity to leave less liquidity than `amountRequired`, but needs no privileged role in `IdleCDOEpochVariant`, `IdleCreditVault`, or `ProgrammableBorrower`.

The existing solvency check does not prevent this case: when `shortfall <= _currentVaultAssets()`, the code deliberately attempts the external withdrawal and reverts on failure rather than completing settlement or isolating the unpaid amount. [6](#0-5) 

### Recommendation
Do not treat the shared ERC4626 liquidity pool as a reserved source for epoch obligations:

- Keep `epochPendingWithdraws` as on-hand underlying instead of redeploying that portion into the vault during `onStartEpoch`.
- For close-pool settlement, begin vault unwinding during the buffer or otherwise separate the liquidity-recall phase from final epoch settlement.
- Add a bounded two-phase settlement path so `vault.withdraw` can be retried without requiring the entire epoch transition to succeed in one transaction.
- After a defined liquidity-recall window, enter an explicit recovery/default path rather than leaving users exposed to an indefinitely repeating settlement race.
- For MetaMorpho-style vaults, monitor underlying-market liquidity in addition to `convertToAssets`; share value alone does not prove synchronous withdrawability.

### Proof of Concept
This Foundry fork test uses an actual unprivileged ERC4626 vault LP to consume shared liquidity before the honest manager calls `stopEpoch`. The setup helpers and fork constants are those in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`; `vaultLp` should be set to a non-privileged `GAUNTLET_USDC_PRIME` shareholder with sufficient shares at the fixed fork block.

```solidity
function testVaultLiquidityDrainBlocksEpochSettlement() external {
    _setUpProgrammableBorrowerCreditVault(
        GAUNTLET_FORK_BLOCK,
        GAUNTLET_USDC_PRIME
    );

    IERC4626 externalVault = IERC4626(GAUNTLET_USDC_PRIME);
    uint256 depositAmount = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(depositAmount);

    // Queue a normal withdrawal before epoch start. In programmable mode this
    // uses pendingWithdraws rather than instant withdrawals.
    uint256 requested =
        cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));

    _startEpochAndCheckPrices(0);

    uint256 pendingWithdraws = strategy.pendingWithdraws();
    assertEq(pendingWithdraws, requested);
    assertGt(pendingWithdraws, 0);

    // An existing, unprivileged vault LP exits immediately before settlement.
    // Replace with a real GAUNTLET_USDC_PRIME LP address selected at the fork.
    // The transaction itself is an ordinary ERC4626 redeem, not a privileged call.
    address vaultLp = REAL_VAULT_LP_AT_FORK;
    uint256 lpShares = externalVault.balanceOf(vaultLp);
    assertGt(lpShares, 0);

    vm.prank(vaultLp);
    externalVault.redeem(lpShares, vaultLp, vaultLp);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // The programmable borrower's shares may still cover pendingWithdraws via
    // convertToAssets, but the vault cannot currently return the assets.
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
    assertEq(strategy.pendingWithdraws(), pendingWithdraws);
}
```

For a close-pool variant, omit the withdrawal request and call `stopEpoch(0, 1)` after draining liquidity. In that case the frozen amount includes the CDO’s active strategy-token principal as well as the epoch interest.
