### Title
Missing timeout on `SequencerClient` HTTP transport used to forward raw transactions to the sequencer - (File: crates/execution/rpc/src/sequencer.rs)

### Summary
`SequencerClient::new_with_headers` builds the reqwest client used to forward `eth_sendRawTransaction` requests to the sequencer without configuring any request timeout, mirroring the reported `iso-filecoin` `RPC.call` bug class (a `fetch`/HTTP client used for an RPC round trip with no timeout).

### Finding Description
`SequencerClient::new_with_headers` constructs the outbound HTTP client with `alloy_reqwest::Client::builder().use_rustls_tls()` and, when headers are present, `.default_headers(...)`, then calls `.build()` — no `.timeout(...)` is ever set on the builder. [1](#0-0) 
This client is stored in `SequencerClientInner` and used by `SequencerClient::request`/`forward_raw_transaction` to POST JSON-RPC calls (including `eth_sendRawTransaction`) to the sequencer endpoint. [2](#0-1) 
`forward_raw_transaction` is invoked synchronously, in the request-handling path, every time an unprivileged client submits a transaction via `eth_sendRawTransaction` and the node is configured with a `raw_tx_forwarder` (`SequencerClient`): `send_pool_transaction` awaits `client.forward_raw_transaction(&tx).await` before returning a result to the RPC caller. [3](#0-2) 
Because there is no client-level (or per-request) timeout on this reqwest client, if the sequencer endpoint stalls (network partition, TCP connect hang, slow/stuck backend), the underlying HTTP request can hang indefinitely. Other RPC/network clients throughout the codebase are consistently built with explicit timeouts (e.g. `HttpClientBuilder::default().request_timeout(...)` in `basectl`, or `Client::builder().timeout(...)` for the challenger metrics scraper), showing this is the established pattern the `SequencerClient` transport deviates from. [4](#0-3) [5](#0-4) 

### Impact Explanation
Every unprivileged transaction sender's `eth_sendRawTransaction` call that reaches a node configured to forward to the sequencer will hold the Tokio task (and any associated RPC-server resources/connection slots) for the duration of the stalled request when the sequencer is slow or unreachable. Because reqwest's default (no) timeout applies, this can lead to indefinite task accumulation, connection-pool exhaustion, and eventual denial of the `eth_sendRawTransaction` RPC surface on the affected node — i.e., "an RPC the node can no longer serve," consistent with the accepted impact categories.

### Likelihood Explanation
This is reachable by any external client sending a normal transaction submission to a node running with `raw_tx_forwarder` set — no privileged access is required. Triggering it only requires the sequencer endpoint (or the network path to it) to become slow or unresponsive, which is a realistic operational condition (sequencer overload, network blip, TLS handshake stall), not a contrived edge case.

### Recommendation
Set an explicit timeout on the reqwest client built in `SequencerClient::new_with_headers` (e.g. `.timeout(Duration::from_secs(N))`), and/or wrap `forward_raw_transaction`/`request` calls with `tokio::time::timeout`, consistent with the pattern already used elsewhere in the codebase (`basectl`'s `HttpClientBuilder::request_timeout`, `tx-manager`'s `RuntimeTimeout::run` around nonce RPC fetches).

### Proof of Concept
1. Configure a node with `raw_tx_forwarder` pointing at a `SequencerClient` built via `SequencerClient::new_with_headers` against an HTTP endpoint.
2. Make the sequencer endpoint stall (e.g., a TCP listener that accepts but never responds, or drop packets after `SYN`).
3. Submit `eth_sendRawTransaction` from any unprivileged client; observe that `send_pool_transaction` → `client.forward_raw_transaction(&tx).await` blocks indefinitely because the underlying `reqwest::Client` has no `.timeout(...)` configured. [1](#0-0) [3](#0-2) 
4. Repeat concurrently to exhaust available request-handling resources, denying `eth_sendRawTransaction` service on the node.
