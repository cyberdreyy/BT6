### Title
Unprivileged withdrawal-request inflation forces borrower default and freezes all LP funds for a full recovery cycle - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary

CVE-2020-1763 is an unauthenticated, zero-cost input that crashes the pluto daemon (it respawns, i.e., temporary loss of availability). The closest analog in this codebase is an unprivileged, KYC-passing lender who inflates the global `pendingWithdraws` obligation via `requestWithdraw`, so that when the honest manager later calls `stopEpoch`, the borrower's repayment cannot cover `pendingWithdraws + expectedEpochInterest`. The vault then takes the default path (`_handleBorrowerDefault`), pausing normal operations and freezing every LP's funds until `finalizeDefault`/`finalizeDefaultRecovery` completes — a temporary freezing of all vault TVL caused by crafted but otherwise legitimate calls.

### Finding Description

`IdleCDOEpochVariant.requestWithdraw` (contracts/IdleCDOEpochVariant.sol:739) accepts any amount from any allowed wallet holding tranche tokens and calls `IdleCreditVault.requestWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:243). For each request the vault does: [1](#0-0) 

`pendingWithdraws` is a *global* aggregate that `stopEpoch` must source from the borrower via `collectWithdrawFunds` (contracts/strategies/idle/IdleCreditVault.sol:411): [2](#0-1) 

There is no cap linking cumulative `pendingWithdraws` to the borrower's demonstrated repayment capacity or on-hand liquidity. `_guarded(_amount)` in `_deposit` only limits total TVL, not the fraction of TVL that can be converted into mandatory epoch-end cash obligations. An attacker can therefore:

1. Pass KYC (`isWalletAllowed` is the only gate at IdleCDOEpochVariant.sol:741-744).
2. Deposit a large position (AA or BB) during the buffer.
3. Immediately call `requestWithdraw(0, tranche)`, converting the entire deposit into a `pendingWithdraws` obligation that the borrower must repay in cash at `stopEpoch`, on top of `expectedEpochInterest`.
4. Repeat across many sybil KYC wallets or tranche-token transfers (receipts are per-user, but multiple users compound the same `pendingWithdraws` bucket).

If the aggregate `pendingWithdraws + interest` exceeds what the honest borrower can source (e.g., funds already drawn down on the credit facility), the `safeTransferFrom`/repayment at `stopEpoch` fails and the pool enters the default flow: `defaulted = true`, `_updateAccounting` reverts `Default()` for subsequent deposits/withdrawals (IdleCDO.sol:291), and all claims are blocked until `finalizeDefault` and `finalizeDefaultRecovery` run and users claim through `lossRecoveryPriceByEpoch`/`_claimDefaultedWithdrawRequest`.

### Impact Explanation

Temporary freezing of the entire vault TVL (all pending receipts + all active NAV) for the duration of the default/finalization process — directly analogous to the daemon crash-and-respawn DoS in the CVE. The attacker's own deposit is frozen too, so this is griefing rather than theft, but the loss imposed on victims (queued withdrawals unclaimable, forced into the recovery process, time-value loss on all TVL) is quantifiable as `TVL × duration-of-recovery`, and it costs the attacker nothing beyond gas and the same lockup they impose on others.

### Likelihood Explanation

- Attacker requirements are minimal: a single KYC-passing wallet (explicitly an in-scope attacker class), plus capital equal to the obligation they want to force. No privileged role needed.
- The trigger is entirely attacker-controlled sequencing around honest manager calls (`startEpoch`/`stopEpoch`), which is permitted by the rules.
- Guards do not stop it: `_skimDonatedAssets` only handles raw token donations; the loss-recovery guard at IdleCreditVault.sol:263-271 only blocks *repeat* requests by the same user after a loss epoch; `pendingWithdraws` has no bound against borrower liquidity; and the default flow is the designed response to underfunding, so nothing reverts the attacker's setup transactions.
- Mitigating factor: the attacker's own capital is frozen in the same default, so this is a griefing vector rather than profitable theft — consistent with a "High" DoS-class finding rather than a Critical theft.

Caveat: whether a concrete fork PoC shows a *permanent* freeze depends on whether `finalizeDefaultRecovery` can run against an honest borrower who simply lacked liquidity at stop time; based on `postDefaultRequests`/`DefaultDistributor` plumbing the freeze is most likely temporary (recovery via reserve claim), matching the CVE's crash/respawn semantics.

### Recommendation

- Bound `pendingWithdraws` relative to borrower-side liquidity: at request time, or at `startEpoch` via `onStartEpoch(_pendingWithdraws)`, reject/queue requests that exceed a configurable fraction of the facility's repayable balance.
- Alternatively, charge a request-time reserve or require `stopEpoch` to treat underfunded `pendingWithdraws` as a loss-adjusted epoch (`lossRecoveryPriceByEpoch`) instead of a hard default, so a liquidity shortfall degrades to a haircut rather than freezing all LPs.
- Rate-limit or epoch-cap the aggregate withdraw-request bucket per epoch.

### Proof of Concept

```solidity
// Fork test sketch (Foundry, mainnet fork as in test/foundry/IdleCreditVault.t.sol)
function testWithdrawInflationForcesDefault() external {
    // attacker: KYC-passed EOA
    address attacker = makeAddr("attacker");
    _allowWallet(attacker); // KeyringIdleWhitelist / isWalletAllowed

    uint256 tvl = cdoEpoch.getContractValue();
    // attacker deposits a position sized so pendingWithdraws + interest
    // exceeds borrower's available repayment liquidity
    uint256 attackDeposit = borrowerFreeLiquidity() + 1; // > what borrower can repay at stop
    deal(defaultUnderlying, attacker, attackDeposit);
    vm.startPrank(attacker);
    underlying.approve(address(idleCDO), attackDeposit);
    idleCDO.depositAA(attackDeposit);
    // convert the whole position into a mandatory epoch-end cash claim
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.stopPrank();

    assertGt(
        IdleCreditVault(address(strategy)).pendingWithdraws()
            + cdoEpoch.expectedEpochInterest(),
        borrowerFreeLiquidity(),
        "obligation exceeds borrower liquidity"
    );

    // honest manager tries to settle the epoch
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // borrower repayment underfunds pendingWithdraws

    assertTrue(cdoEpoch.defaulted(), "pool forced into default");

    // victim LP funds are frozen: normal claim path reverts/diverts to recovery
    vm.expectRevert();
    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest(); // or pays only via lossRecoveryPriceByEpoch
}
```

The broken invariant is availability/solvency-at-settlement: the epoch state machine treats `pendingWithdraws` as unconditionally fundable, but it is an attacker-influenced aggregate, letting an unprivileged lender "crash" the vault into the default flow at will — the same effect class as the unauthenticated IKEv1 packet that crashes pluto.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;

      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
