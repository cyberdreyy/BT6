### Title
Vote transactions share the same block/account cost-tracker limits as ordinary transactions, letting congestion from unprivileged user transactions block leader vote inclusion - (File: `cost-model/src/cost_tracker.rs`)

### Summary
`CostTracker::would_fit` is the single gate that decides whether *any* transaction — including the leader's own consensus vote — can be added to the block being built. It enforces a global `block_cost` ceiling and a per-writable-account `account_cost` ceiling identically for every transaction type, with no reserved capacity or bypass for vote transactions. [1](#0-0) 

### Finding Description
The reported GTE-perps bug is a class of "shared gate blocks the backstop/critical path" issue: a divergence-band check meant to protect normal makers is applied unmodified to the BACKSTOP liquidation path, so when the book runs out of in-band liquidity the *last-resort* mechanism halts exactly when it is needed most.

The analogous structure exists in Agave's cost metering. `CostTracker::would_fit` checks `block_cost + cost > limits.block_cost` and, per writable account, `chained_cost + cost > limits.account_cost`, and returns `WouldExceedBlockMaxLimit` / `WouldExceedAccountMaxLimit` with no special-casing for vote transactions. [1](#0-0) 

This is confirmed by an explicit unit test asserting that vote transactions are subject to the *regular* limits rather than a reserved/exempt pool: `test_cost_tracker_vote_transactions_use_regular_limits` builds two vote transactions and shows they are gated by the same `account_cost`/`block_cost` capacity as any other transaction. [2](#0-1) 

Although Agave has a dedicated vote-transaction ingestion/scheduling path (`core/src/banking_stage/vote_worker.rs`), that pipeline still must call into the same per-bank `CostTracker` to actually commit a vote into the block, so any capacity already consumed by ordinary, unprivileged user transactions (submitted over TPU/QUIC and admitted into the block ahead of the vote) directly reduces the remaining budget available to the leader's own vote transaction. There is no reserved "vote lane" analogous to bypassing the divergence band for BACKSTOP orders — the same numeric ceiling (`limits.block_cost`, `limits.account_cost`) is shared between "standard" user traffic and the "backstop" vote transaction that the validator must land to participate in consensus for that slot. [3](#0-2) 

### Impact Explanation
Just as GTE's shared divergence gate can leave the protocol unable to liquidate exactly when it is under stress, a shared cost gate can leave the leader unable to fit its own vote transaction into a block when ordinary transaction volume has already consumed the block's compute budget or saturated the write-lock cost of an account touched by the vote path. Because vote landing is the mechanism by which a validator's stake is credited toward consensus/finality for a slot, denial of vote inclusion under adversarial or organically heavy transaction load degrades the availability of that "backstop"/critical path precisely under the congestion conditions the reporter describes for liquidation — increasing the chance of missed votes, reduced finalization throughput, and cascading effects on cluster liveness under sustained load. This is reachable purely from ordinary, unprivileged user transaction submission (no special privilege required to fill block cost capacity).

### Likelihood Explanation
Filling a block's `MAX_BLOCK_UNITS` compute budget or a specific hot account's `MAX_WRITABLE_ACCOUNT_UNITS` with unprivileged transactions is a well-known, cheap, and repeatable action (transaction spam / hot-account contention), and requires no special stake or key material — only fee-payer funds and ordinary QUIC/TPU access, making the preconditions for this shared-gate starvation realistic during genuine network congestion.

### Recommendation
Reserve a portion of block/account cost capacity exclusively for vote transactions (i.e., give the vote path its own budget/limit that is checked and consumed independently of `limits.block_cost` / `limits.account_cost`, and is never exhausted by ordinary transactions), analogous to bypassing the divergence-band check for BACKSTOP liquidation orders in the referenced report. Alternatively, always reserve headroom in `would_fit` sufficient to admit at least the leader's own vote transaction before applying block/account limits to non-vote transactions.

### Proof of Concept
1. Leader begins building a block; ordinary user transactions are streamed in via TPU/QUIC and processed by the regular banking pipeline, calling `CostTracker::try_add` → `would_fit`. [4](#0-3) 
2. Unprivileged senders submit enough transactions (or transactions writing to a specific hot account) to push `block_cost` (or that account's cost) to just under `limits.block_cost` / `limits.account_cost`.
3. When the leader's own vote transaction reaches the same `CostTracker::would_fit` check, it is evaluated with the identical, non-reserved limits shown in `test_cost_tracker_vote_transactions_use_regular_limits`, and can be rejected with `WouldExceedBlockMaxLimit`/`WouldExceedAccountMaxLimit` exactly like any other transaction. [2](#0-1) 
4. The vote for that slot is dropped from the block, mirroring the "backstop halts when most needed" failure mode described in the source report.

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // check each account against account_cost_limit,
        for account_key in tx_cost.writable_accounts() {
            match self.cost_by_writable_accounts.get(account_key) {
                Some(chained_cost) => {
                    if chained_cost.saturating_add(cost) > self.limits.account_cost {
                        return Err(CostTrackerError::WouldExceedAccountMaxLimit);
                    } else {
                        continue;
                    }
                }
                None => continue,
            }
        }

        Ok(())
    }
