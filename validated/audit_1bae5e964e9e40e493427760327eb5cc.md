### Title
`resolver.Resolve` invokes GCP STS/Secret Manager calls with `context.Background()`, unbounded by job cancellation or timeout - ([File: helpers/secrets/resolvers/gcp_secret_manager/resolver.go])

### Summary
`resolver.Resolve` calls `v.client.GetSecret(context.Background(), v.secret.GCPSecretManager)`, detaching the outbound HTTP calls to the STS token-exchange endpoint and Secret Manager API from any job-scoped context. Because `sts.NewService(ctx, ...)`, `stsService.V1.Token(...).Do()`, and `sm.NewClient`/`AccessSecretVersion` all inherit this background context with no deadline, a slow or hanging backend response can block indefinitely.

### Finding Description
`resolver.Resolve` at [1](#0-0)  calls `GetSecret` with `context.Background()` rather than a context derived from the build/job context. Inside `Client.GetSecret`, [2](#0-1) , this same unbounded context flows into `getToken` (`sts.NewService(ctx, ...)` and `stsService.V1.Token(stsTokenRequest).Do()`) at [3](#0-2)  and into `access` (`sm.NewClient(ctx, ...)` / `smClient.AccessSecretVersion(ctx, ...)`) at [4](#0-3) . Neither the underlying Google client libraries nor this code impose a timeout — `option.WithoutAuthentication()` and `option.WithTokenSource(source)` only affect auth, not deadlines. The `Audience` string embedded in the STS request is built directly from attacker-controllable `secret.Server.ProjectNumber`, `secret.Server.WorkloadIdentityFederationPoolId`, and `secret.Server.WorkloadIdentityFederationProviderID` fields via `stsAudience` at [5](#0-4) , but these values only affect what the STS server does with the request — the network calls themselves have no runner-imposed bound regardless of the payload.

Higher up, `defaultSecretsResolver.Resolve` (in `common/secrets.go`) synchronously calls `sr.Resolve()` at [6](#0-5)  per secret with no context/cancellation plumbing at all — the `SecretResolver.Resolve()` interface at [7](#0-6)  takes no context argument whatsoever, so even if `resolver.Resolve` wanted to honor a job-scoped context, the interface provides no way to pass one down from the build's cancellation/timeout context. This confirms the context detachment is structural, not just a call-site oversight — there is no mechanism in the `SecretResolver` abstraction to bound or cancel a resolver's work from the build lifecycle.

### Impact Explanation
If the GCP STS or Secret Manager endpoint (or a malicious/compromised network intermediary responding to the crafted, attacker-supplied `WorkloadIdentityFederationPoolId`/`ProviderID`/`ProjectNumber` values) never responds, `GetSecret`'s HTTP call blocks forever with no timeout. Since `handleSecret`/`Resolve` is called synchronously in the job's secret-resolution stage, the goroutine executing that job's `BuildStageResolveSecrets` step is stuck. Depending on runner concurrency configuration (`concurrent`, `limit`), this can consume one of a finite number of worker slots indefinitely, delaying or starving other jobs queued for the same runner, and preventing that job's own timeout/cleanup logic from acting on this particular execution path since there's no cancellable context to short-circuit the blocked call.

### Likelihood Explanation
The precondition that a pipeline author controls `GCPSecretManagerServer` fields (via CI variable expansion in `.gitlab-ci.yml` secrets configuration) is plausible for CI configs. However, actually causing the *network call itself* to hang indefinitely requires control over, or the ability to interfere with, the actual DNS/network path to Google's STS/Secret Manager endpoints (`sts.NewService` defaults to Google's real service endpoint) — an unprivileged CI job author cannot redirect these fixed API endpoints to an attacker-controlled slow server just by supplying bad pool/provider IDs; a non-existent audience would typically produce a fast error response from Google's server, not an indefinite hang. Reliably triggering a hang purely via job input fields, without additional network-level interference (DNS poisoning, MITM, or attacker control of runner's network egress — which are out of scope per the rules on external service compromise), is not demonstrated by this code path alone.

### Recommendation
Introduce a bounded, cancellable context: extend `SecretResolver.Resolve()` to accept a `context.Context` derived from the build's context (with a sane secret-resolution timeout, e.g. via `context.WithTimeout`), thread it through `defaultSecretsResolver.Resolve` → `handleSecret` → resolver implementations → `service.Client.GetSecret`, replacing the hardcoded `context.Background()` in `resolver.Resolve`.

### Proof of Concept
Unit test: inject a `getTokenFunc` stub or an httptest server that never responds to `stsService.V1.Token(...).Do()`, call `Client.GetSecret` with a context that has a short deadline (e.g. `context.WithTimeout(ctx, 500*time.Millisecond)`), and assert `GetSecret` returns within the deadline with a context-deadline-exceeded error — currently, calling `resolver.Resolve()` (which uses `context.Background()`) against the same slow stub would hang past any reasonable test timeout, demonstrating the missing bound. Assertion: `resolver.Resolve()` completes (or errors) within N seconds instead of blocking indefinitely.

However, given the analysis above, the root cause (missing context propagation / no interface support for cancellation) is real and verifiable in code, but the specific "attacker-controlled slow STS backend via crafted audience fields" exploit trigger is not established as reachable without additional network-level compromise, which the rules exclude. I present this as a **partially valid** finding: the missing-timeout/context-detachment defect is real, but the attacker-triggerability of an indefinite hang purely through job-controlled `WorkloadIdentityFederationPoolId`/`ProviderID` values (without external network compromise) is unproven.

func (c Client) GetSecret(ctx context.Context, secret *spec.GCPSecretManagerSecret) (string, error) {
	tokenResponse, err := c.getToken(ctx, secret)
	if err != nil {
		return "", fmt.Errorf("failed to exchange sts token: %w", err)
	}

	tokenSource := toTokenSource(tokenResponse)

	accessSecretVersionResponse, err := c.accessSecret(ctx, secret, tokenSource)

	if err != nil {
		return "", fmt.Errorf("failed to get secret: %w", err)
	}

	if accessSecretVersionResponse.Payload == nil {
		return "", common.ErrSecretNotFound
	}

	if !validChecksum(accessSecretVersionResponse.Payload) {
		return "", fmt.Errorf("data corruption detected")
	}

	return string(accessSecretVersionResponse.Payload.Data), nil
}

func getToken(ctx context.Context, secret *spec.GCPSecretManagerSecret) (*sts.GoogleIdentityStsV1ExchangeTokenResponse, error) {
	// option.WithoutAuthentication() is required for STS service.
	// https://cloud.google.com/iam/docs/reference/sts/rest/v1/TopLevel/token
	// specifies clients NOT to send `Authorization` header. Without this option,
	// the request would include `Authorization` header and the request would fail.
	stsService, err := sts.NewService(ctx, option.WithoutAuthentication())
	if err != nil {
		return nil, fmt.Errorf("unable to create sts service client: %w", err)
	}

	stsTokenRequest := &sts.GoogleIdentityStsV1ExchangeTokenRequest{
		Audience:           stsAudience(secret),
		GrantType:          grantType,
		RequestedTokenType: requestedTokenType,
		Scope:              gcpAuthScope,
		SubjectToken:       secret.Server.JWT,
		SubjectTokenType:   subjectTokenTypeOIDC,
	}

	return stsService.V1.Token(stsTokenRequest).Do()
}

func stsAudience(secret *spec.GCPSecretManagerSecret) string {
	return fmt.Sprintf(
		"//iam.googleapis.com/projects/%s/locations/global/workloadIdentityPools/%s/providers/%s",
		secret.Server.ProjectNumber,
		secret.Server.WorkloadIdentityFederationPoolId,
		secret.Server.WorkloadIdentityFederationProviderID)
}

func access(ctx context.Context, secret *spec.GCPSecretManagerSecret, source oauth2.TokenSource) (*smpb.AccessSecretVersionResponse, error) {
