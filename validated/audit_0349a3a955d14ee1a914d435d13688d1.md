### Title
Unbounded password length accepted on login causes CPU-exhaustion DoS via unauthenticated `bcrypt.CompareHashAndPassword` call - (File: core/utils/utils.go, core/sessions/localauth/orm.go)

### Summary
The Chainlink node's local-auth login path (`POST /sessions`) accepts a JSON `password` field of unbounded length (bounded only by the global body-size limit) and passes it straight into `bcrypt.CompareHashAndPassword` via `utils.CheckPasswordHash`, with no length validation performed beforehand. This is the direct analog of the reported Nextcloud issue: a password-length cap is enforced only on the *account-creation/password-change* path, not on the *login-verification* path, allowing an unauthenticated client to submit very large passwords that get fed into expensive password-hashing primitives on every login attempt.

### Finding Description
Chainlink defines a maximum password length constant explicitly to avoid bcrypt cost issues: [1](#0-0) 

and enforces it in `ValidateAndHashPassword`, which is used only for `NewUser` (account creation) and indirectly for password updates: [2](#0-1) 

However, the **login verification path** never calls `ValidateAndHashPassword` or performs any length check on the incoming plaintext password. It calls `utils.CheckPasswordHash` directly against the raw `sr.Password` value bound from the client's JSON body: [3](#0-2) 

`CheckPasswordHash` is a thin wrapper around `bcrypt.CompareHashAndPassword` with no length guard: [4](#0-3) 

The same unguarded pattern exists in the OIDC local-admin fallback login and LDAP/OIDC `TestPassword` code paths, all of which call `utils.CheckPasswordHash` on unbounded input: [5](#0-4) [6](#0-5) 

The HTTP route is public/unauthenticated and reachable by any network client, gated only by a generic request-count rate limiter and a global request body size limit (not password-length specific): [7](#0-6) [8](#0-7) 

Unlike `bcrypt.GenerateFromPassword`, which rejects passwords over 72 bytes before doing any hashing work, `bcrypt.CompareHashAndPassword` in `golang.org/x/crypto/bcrypt` does not perform this length check — it proceeds directly to the expensive Blowfish key-expansion routine (`expensiveBlowfishSetup`/`blowfish.ExpandKey`) over the *entire* supplied password buffer, once per `1<<cost` rounds (default cost 10 → 1024 rounds). Feeding it a very large password therefore multiplies the per-request CPU cost far beyond the intended bcrypt cost factor, since the key-expansion loop scans the whole password buffer on every round instead of the fixed ~72-byte key Chainlink intends.

### Impact Explanation
An unauthenticated attacker can send POST requests to `/sessions` with an oversized `password` field (up to whatever `WebServer.HTTPMaxSize` allows), forcing the node to run 1024 rounds of Blowfish key expansion over the full attacker-controlled buffer on every request. Because this occurs before any authentication succeeds, and the endpoint is explicitly designed to be reachable pre-auth, repeated requests can consume significant CPU, degrading availability of the node's web/API server for legitimate operators — the same "Improper Restriction of Authentication Attempts / password length" DoS class described in the source report.

### Likelihood Explanation
This requires no privileges — it is reachable by any unprivileged client capable of sending HTTP requests to the node's API port and is not blocked by any existing control:
- The unauthenticated rate limiter only throttles by request count/period, not payload cost, so a low number of expensive requests per window can still be issued repeatedly and indefinitely.
- `MaxBcryptPasswordLength` protects only the write path (account creation / password change), leaving the read/verification (login) path unprotected.
- Any deployment exposing `/sessions` to the network (which is required for the login UI/API to function) is affected.

### Recommendation
Apply the same length restriction used on password creation (`sessions.MaxBcryptPasswordLength`, 50 bytes / bcrypt's 72-byte hard limit) to all inbound plaintext passwords **before** they reach `utils.CheckPasswordHash`/`bcrypt.CompareHashAndPassword`, specifically in:
- `core/sessions/localauth/orm.go` (`CreateSession`, `TestPassword`)
- `core/sessions/oidcauth/oidc.go` (`localLoginFallback`, `TestPassword`)
- `core/sessions/ldapauth/ldap.go` (equivalent login/testpassword checks)

Reject (with a generic `401 Invalid password`, to avoid leaking the exact validation reason) any login/`TestPassword` request whose password exceeds the maximum allowed length, before invoking bcrypt.

### Proof of Concept
```
POST /sessions HTTP/1.1
Host: <chainlink-node>
Content-Type: application/json

{"email":"someuser@example.com","password":"AAAAAAAAAA...<hundreds of KB up to HTTPMaxSize>...AAAA"}
```
Each such request causes `SessionsController.Create` → `AuthenticationProvider().CreateSession` → `utils.CheckPasswordHash(sr.Password, ...)` → `bcrypt.CompareHashAndPassword` to run full Blowfish key expansion over the entire oversized password, without any prior length rejection, unlike the account-creation path which would reject the same string via `ValidateAndHashPassword`'s `MaxBcryptPasswordLength` check.

// ValidateAndHashPassword is the single point of logic for user password validations
func ValidateAndHashPassword(plainPwd string) (string, error) {
	if err := utils.VerifyPasswordComplexity(plainPwd); err != nil {
		return "", pkgerrors.Wrapf(err, "password insufficiently complex:\n%s", utils.PasswordComplexityRequirements)
	}
	if len(plainPwd) > MaxBcryptPasswordLength {
		return "", pkgerrors.Errorf("must enter a password less than %v characters", MaxBcryptPasswordLength)
	}

	pwd, err := utils.HashPassword(plainPwd)
	if err != nil {
		return "", err
	}

	return pwd, nil
}

func (o *orm) TestPassword(ctx context.Context, email string, password string) error {

	if err := o.ds.GetContext(ctx, &hashedPassword, "SELECT hashed_password FROM users WHERE lower(email) = lower($1)", email); err != nil {

	}

		return pkgerrors.New("passwords don't match")
	}
	return nil

// HashPassword wraps around bcrypt.GenerateFromPassword for a friendlier API.
func HashPassword(password string) (string, error) {
	bytes, err := bcrypt.GenerateFromPassword([]byte(password), bcrypt.DefaultCost)
	return string(bytes), err
}

// CheckPasswordHash wraps around bcrypt.CompareHashAndPassword for a friendlier API.
func CheckPasswordHash(password, hash string) bool {
	err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
	return err == nil
}

func sessionRoutes(app chainlink.Application, r *gin.RouterGroup) {
	config := app.GetConfig()
	rl := config.WebServer().RateLimit()
	unauth := r.Group("/", rateLimiter(
		rl.UnauthenticatedPeriod(),
		rl.Unauthenticated(),
	))
	sc := NewSessionsController(app)
	unauth.POST("/sessions", sc.Create)
	auth := r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	auth.DELETE("/sessions", sc.Destroy)
}
