### Title
Nested Post-Interaction Reentrancy in Escrow Deployment - (`contracts/BaseEscrowFactory.sol`)

### Summary
The `BaseEscrowFactory._postInteraction` function allows an unprivileged actor (a Resolver) to trigger a nested call to an arbitrary contract via the `tail` data before the factory completes its own state updates and escrow deployment. In the `allowMultipleFills` mode, the factory relies on `lastValidated` state from `MerkleStorageInvalidator` to determine the current `hashlock`. Because the nested `postInteraction` call occurs before the factory verifies the escrow's balance and emits the `SrcEscrowCreated` event, a malicious contract can re-enter the Limit Order Protocol to fill the same order again. If the nested call is manipulated to process a different part of a Merkle-tree order, the factory may deploy escrows with inconsistent state or allow the drainage of safety deposits that were intended for a single atomic swap sequence.

### Finding Description
In `BaseEscrowFactory.sol`, the `_postInteraction` function is designed to be called by the 1inch Limit Order Protocol (LOP) after an order is filled. The function includes a hook to call an external `IPostInteraction` contract if the `tail` data contains a target address: [1](#0-0) 

This external call is performed **before** the factory updates its own logic for multiple fills and **before** it deploys the actual escrow contract. Specifically, for orders allowing multiple fills, the `hashlock` is retrieved from the `lastValidated` mapping, which is updated by the `MerkleStorageInvalidator.takerInteraction` function (called by LOP during the same transaction): [2](#0-1) 

The root cause is a violation of the Checks-Effects-Interactions pattern. By placing the `IPostInteraction(...).postInteraction(...)` call before the escrow deployment and the final validation of the `lastValidated` index, the protocol allows a malicious resolver to trigger a nested fill of the same `orderHash`. This can lead to a scenario where the `lastValidated` state is mutated in a reentrant call, causing the outer execution context to use an outdated or unexpected `hashlock` for the current `makingAmount`, potentially leading to protocol insolvency or misrouted funds.

### Impact Explanation
**High/Critical**: This vulnerability allows for the manipulation of the atomic swap's fundamental invariant: the deterministic binding between a specific fill amount and its corresponding hashlock. An attacker can:
1. Trigger a nested fill that completes the order, causing the `lastValidated` index to increment.
2. The outer call then continues, potentially deploying a second escrow for the same "slot" or using an incorrect secret index.
3. This breaks the safety deposit accounting, as the `InsufficientEscrowBalance` check at the end of `_postInteraction` only checks the balance of the *currently* deployed clone, not the global state of the order's funding.
4. It can result in the theft of user funds in motion or the freezing of funds if the Merkle indices become desynchronized between the source and destination chains.

### Likelihood Explanation
**Medium**: Exploitation requires the Maker to have signed an order allowing multiple fills (Merkle-based). The attacker must be a Resolver (unprivileged but requires being in the whitelist if one exists) and must provide a malicious `postInteraction` target in the `extension` data of the LOP order. Since the LOP allows arbitrary extensions, this is a reachable path for any active resolver.

### Recommendation
Move the external `postInteraction` call to the very end of the `_postInteraction` function, after the escrow has been successfully deployed and all internal state validations (including the `InsufficientEscrowBalance` check) are complete. Alternatively, implement a reentrancy guard specifically for the `orderHash` being processed to prevent nested fills of the same order.

### Proof of Concept
1. **Setup**: A Maker signs a cross-chain order for 100 USDC with `allowMultipleFills` enabled, using a Merkle tree of 2 secrets.
2. **Attack**: The Resolver calls `fillOrder` for 50 USDC. In the `extension` data, the Resolver sets the `tail` of the `extraData` to a malicious contract address.
3. **Execution**:
    - LOP calls `BaseEscrowFactory._postInteraction`.
    - `BaseEscrowFactory` calls the Malicious Contract's `postInteraction`.
    - The Malicious Contract re-enters LOP to fill the remaining 50 USDC of the *same* order.
    - The nested call completes, deploying `EscrowSrc_2`.
    - The original call resumes and deploys `EscrowSrc_1`.
4. **Outcome**: The `lastValidated` index is now inconsistent with the deployment order, or the safety deposits (which must be pre-sent to the deterministic address) are consumed in an order that allows the Resolver to claim them without fulfilling the destination side of the swap.
