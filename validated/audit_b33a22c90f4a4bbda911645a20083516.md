### Title
Unvalidated EIP-1559 denominator/elasticity from L1 SystemConfig updates can propagate a zero-denominator into L2 block headers, halting derivation on other nodes - ([File: crates/common/genesis/src/updates/eip1559.rs])

### Summary
`Eip1559Update::apply` and the `SystemConfig.eip1559_denominator`/`eip1559_elasticity` fields it sets are populated straight from data emitted in an L1 `SystemConfigUpdate` log, with no check that the denominator is non-zero. This value is later fed into the Holocene/Jovian extra-data encoding used to build L2 payload attributes. Elsewhere in the same codebase (the block-header decode path and the fee/genesis constructors) a zero EIP-1559 denominator is explicitly treated as an invalid, must-be-rejected value because it causes a division by zero in base-fee computation. The `SystemConfig` update path lacks this same guard, so a denominator of `0` written into the L1 `SystemConfig` update log can flow, unchecked, into the sequencer's construction of L2 block header extra-data / payload attributes.

### Finding Description
`Eip1559Update::try_from` decodes an arbitrary `uint64` payload from an L1 `SystemConfigLog` and splits it into `eip1559_denominator`/`eip1559_elasticity` with no bounds checking: [1](#0-0) 
`apply()` then writes these values directly into `SystemConfig` unconditionally: [2](#0-1) 

Compare this with the codebase's own explicit safety invariant, documented and enforced when *decoding the same value out of the L2 block header*: a zero denominator is treated as a protocol violation because it would cause a division by zero in base-fee math, and is rejected with `Eip1559ValidationError::ZeroDenominator`: [3](#0-2) 
and again in the chain-spec base fee derivation, where `elasticity == 0 || denominator == 0` (but not both) is rejected as `EIP1559ParamError::InvalidParams`: [4](#0-3) 

However, the `SystemConfig` used to *build* a new block's payload attributes (`eip_1559_params`, consumed in `prepare_payload_attributes`) is populated from the L1-derived `Eip1559Update` without any equivalent zero-check: [5](#0-4) 
The same unguarded assignment also occurs when reconstructing `SystemConfig` from an L1 deposit/log-derived block during protocol conversion: [6](#0-5) 

Additionally, the Denim gas-scaling transition multiplies `eip1559_denominator` by a scaling factor without checking it is non-zero to begin with: [7](#0-6) 

This is the analog of the reported `MixinStakingPool._setParams` bug: a privileged parameter update path (`_setParams`/`Eip1559Update`) writes attacker/operator-controlled values into critical protocol state (`cobbDouglasAlpha*` / `eip1559_denominator`) without the same sanity checks enforced elsewhere in the system for structurally identical values, creating an asymmetry between "trusted" and "derived" data paths.

### Impact Explanation
If a denominator of `0` is written into the on-chain L1 `SystemConfig` (via the `SystemConfigUpdate` log for the EIP-1559 update type), any node deriving payload attributes propagates this zero denominator into the block header's Holocene/Jovian extra-data field via `sys_config.eip_1559_params(...)`. Downstream, every node that decodes that header's extra data through `decode_holocene_eip_1559_params_block_header` / `decode_jovian_eip_1559_params_block_header` will explicitly reject it with `ZeroDenominator`, since those paths *do* enforce the invariant that the block-header-encoded denominator is never zero. This produces a divergence: block building/derivation logic that trusts the L1-derived `SystemConfig` value can construct or accept a block that consensus-critical execution/derivation code elsewhere refuses to process, resulting in a node halt or a chain split between components that check the invariant and those that don't. This satisfies the "node halt / chain split" impact bar.

### Likelihood Explanation
The `SystemConfigUpdate` log data originates from L1 (the OP-stack `SystemConfig` contract), which is explicitly called out as an in-scope, attacker-writable input category ("derivation of attacker-written L1 deposit and system-config data"). Reaching this path requires only that an update of kind `Eip1559` be emitted with a zero denominator packed into the high 32 bits of the `uint64` payload — there is no on-chain or off-chain validation preventing this value from being written or from being consumed by `Eip1559Update::try_from`/`apply`. Given that the encoding/decoding split (`>> 32` / lower 32 bits) is simple and the check is trivially omittable, likelihood is Medium: it requires a malformed/malicious L1 system-config update (the same threat class the bug report itself assumes for `_setParams`), not a fully unprivileged L2 transaction.

### Recommendation
Add the same "denominator must be non-zero" validation to `Eip1559Update::try_from` (and to `system_config_from_transaction` in `crates/consensus/protocol/src/utils.rs`, and to the Denim scaling logic in `crates/consensus/derive/src/attributes/stateful.rs`) that is already enforced in `crates/proof/executor/src/util.rs` and `crates/execution/chainspec/src/basefee.rs`. Reject or safely fall back (e.g., to the chain's default `BaseFeeParams`) whenever a decoded `SystemConfigUpdate` would set `eip1559_denominator == 0`, and add regression tests asserting the sequencer/derivation pipeline never accepts a zero-denominator update. Long term, centralize EIP-1559 parameter validation into a single shared constructor/type used by every code path that consumes decoded `(elasticity, denominator)` pairs so a future addition cannot bypass the invariant again.

### Proof of Concept
1. Craft an L1 `SystemConfigUpdate` event with `kind = Eip1559` and payload `uint64` value `0x00000000_00000006` (denominator = 0, elasticity = 6), matching the encoding consumed at: [8](#0-7) 
2. Emit this log from the configured `l1_system_config_address` during an epoch that the derivation pipeline processes; `StatefulAttributesBuilder::prepare_payload_attributes` calls `sys_config.update_with_receipts(...)`, applying `Eip1559Update::apply` unconditionally (as exercised by the existing test `test_epoch_update_applies_to_parent_system_config_seed` / `test_denim_gas_transition_applies_after_l1_system_config_updates`, which show updates flowing straight through without validation): [9](#0-8) 
3. `sys_config.eip_1559_params(...)` is called with `eip1559_denominator = Some(0)` and embedded into the constructed block header's extra data via the payload attributes: [5](#0-4) 
4. Any node subsequently decoding that header's extra data through `decode_holocene_eip_1559_params_block_header` hits the explicit zero-denominator rejection: [10](#0-9) 
producing a hard failure/divergence between the block-building path (which accepted denominator=0) and the execution/derivation path (which rejects it) — a node halt or chain-split condition.

Note: I was not able to fully trace whether every sequencer/builder code path re-validates `eip1559_denominator` before writing it into the produced header's extra data (i.e., whether some intermediate guard exists between `SystemConfig` construction and header encoding that I didn't locate); this should be confirmed by tracing `sys_config.eip_1559_params()`'s full call graph in a live session, since the index may not contain every consuming file.

```rust
pub(crate) fn decode_holocene_eip_1559_params_block_header(
    header: &Header,
) -> ExecutorResult<BaseFeeParams> {
    let (elasticity, denominator) = HoloceneExtraData::decode(header.extra_data())?;

    // Check for potential division by zero.
    // In the block header, the denominator is always non-zero.
    // <https://github.com/ethereum-optimism/specs/blob/main/specs/protocol/holocene/exec-engine.md#eip-1559-parameters-in-block-header>
    if denominator == 0 {
        return Err(ExecutorError::InvalidExtraData(Eip1559ValidationError::ZeroDenominator));
    }

    Ok(BaseFeeParams {
        elasticity_multiplier: elasticity.into(),
        max_change_denominator: denominator.into(),
    })
}
```

```rust
fn base_fee_params_from_extra_data(
    chain_spec: impl EthChainSpec,
    timestamp: u64,
    elasticity: u32,
    denominator: u32,
) -> Result<BaseFeeParams, EIP1559ParamError> {
    if elasticity == 0 && denominator == 0 {
        Ok(chain_spec.base_fee_params_at_timestamp(timestamp))
    } else if elasticity == 0 || denominator == 0 {
        Err(EIP1559ParamError::InvalidParams)
    } else {
        Ok(BaseFeeParams::new(denominator as u128, elasticity as u128))
    }
}
```
