## Title
Single hostile recipient can grief and permanently block a privileged `batchMint` call on the B20 asset precompile - (File: `crates/common/precompiles/src/b20_asset/logic/v1.rs`, `crates/common/precompiles/src/b20_asset/logic/v2.rs`)

### Summary
The B20 asset precompile's `batch_mint` function mints to an array of recipients in a single call, but a single recipient whose mint fails (e.g. because that recipient's mint-receiver policy check rejects the transfer) reverts the entire batch, blocking all other unrelated recipients in the same call. This mirrors the CrabNetting bug class: one uncooperative/adversarial party embedded in an all-or-nothing batch of otherwise-independent operations can grief the whole operation.

### Finding Description
`batch_mint` iterates over `(recipient, amount)` pairs and calls `self.mint(...)` for each with the `?` operator, so any single failure aborts the whole call: [1](#0-0) 

The same all-or-nothing loop exists in the V2 implementation: [2](#0-1) 

Test comments confirm each individual mint inside the batch still runs the recipient-controlled `MintReceiver` policy check even though the caller is privileged for the batch: [3](#0-2) 

Because this policy is per-recipient and externally configurable (a "policy manager" gate, the same mechanism referenced elsewhere for policy-gated actors), a single targeted recipient among many in one `batchMintCall` can make its own policy check fail (e.g. reject the mint, or consume all remaining gas/revert unconditionally), which propagates an error out of the loop via `?` and reverts the entire precompile call — including the credits meant for every *other*, cooperative recipient in that same batch.

This is architecturally the same failure mode flagged in the CrabNetting report: a batch/auction operation that aggregates data from multiple independent parties is executed all-or-nothing, so a single adversarial or merely misconfigured party can repeatedly cause the whole batch to fail, even though the "batch owner" (the minter/auction operator) did nothing wrong and has no way to atomically skip the bad entry.

### Impact Explanation
An address that knows (or arranges) it will be included in a future `batchMint` recipient list can configure its `MintReceiver` policy to always reject, causing every batch-mint call that includes it to revert. This is a griefing/denial-of-service vector against a privileged token-distribution operation (e.g., payroll, airdrop, or reward distribution via `batchMint`): the mint-role holder must detect and evict the malicious recipient and resubmit, and the attack can be repeated against any future batch by including that same recipient. Because the check runs even when `privileged` is `true` (i.e., even trusted callers cannot bypass it), the operator has no way to force-include an uncooperative recipient without re-splitting the batch — this is analogous to the "auction owner must ensure all orders are valid" operational burden in the original report, and it degrades reliability of a core B20 token-distribution primitive. This is a Medium-severity griefing/DoS issue, not a fund-loss or consensus-safety issue.

### Likelihood Explanation
Likelihood is moderate: any account can obtain B20 mint-role status designation as a target recipient of a batch operation it does not control (e.g. a public airdrop, an on-chain reward distribution announced or computed off-chain), then unilaterally configure a rejecting policy. No special privilege or timing is required beyond being an intended recipient, and the effect (full-batch revert) is deterministic and repeatable, matching the CrabNetting report's framing of the market maker "griefing" scenario.

### Recommendation
Change `batch_mint` to isolate per-recipient failures instead of propagating them with `?`: catch policy/mint errors for each entry, skip (and optionally emit an event/return value for) failed entries, and continue processing the remaining recipients, so one hostile or misconfigured recipient cannot block unrelated mints in the same call — mirroring the audit's recommendation to skip invalid orders in `withdrawAuction`/`depositAuction` rather than reverting the whole operation.

### Proof of Concept
1. Recipient `R` (any address) sets its B20 `MintReceiver` policy (via the policy manager mechanism referenced by the "inner mints enforce the MintReceiver policy even when privileged" comment) to unconditionally reject incoming mints.
2. A mint-role holder calls `batchMintCall { recipients: [A, B, R, C], amounts: [...] }` intending to distribute tokens to `A`, `B`, `R`, and `C`.
3. The loop in `batch_mint` reaches `R`'s entry, `self.mint(token, caller, R, amount, true)` fails the policy check and returns an error via `?`.
4. The whole `batch_mint` call reverts — `A`, `B`, and `C` receive nothing despite being valid, cooperative recipients, and the mint-role holder must remove `R` and resubmit. [4](#0-3) 

**Uncertainty note:** I was not able to fully read the `mint()` implementation and the exact `MintReceiver`/policy-manager gating logic before running out of tool iterations, so I could not confirm the precise mechanism by which a recipient makes their own mint revert (e.g., whether it requires prior configuration, a specific policy contract call, or simply being on a deny-list). The `batch_mint` all-or-nothing loop structure and the explicit test comment about per-recipient policy enforcement under `privileged` calls are confirmed directly from the code cited above.

    fn batch_mint(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        recipients: Vec<Address>,
        amounts: Vec<U256>,
        privileged: bool,
    ) -> Result<()> {
        // The pause and role guards below are the sole authorization gate for the batch: the inner
        // mints run privileged to avoid re-checking per recipient. Do not remove or conditionalize
        // these guards. Check order: PAUSE -> ROLE -> INPUT -> BUSINESS.
        B20Guards::ensure_not_paused(token, IB20::PausableFeature::MINT)?;
        if !privileged {
            B20Guards::ensure_token_role(token, caller, B20TokenRole::Mint)?;
        }
        if recipients.len() != amounts.len() {
            return Err(BasePrecompileError::revert(IB20Asset::LengthMismatch {
                leftLen: U256::from(recipients.len()),
                rightLen: U256::from(amounts.len()),
            }));
        }
        if recipients.is_empty() {
            return Err(BasePrecompileError::revert(IB20Asset::EmptyBatch {}));
        }
        for (recipient, amount) in recipients.into_iter().zip(amounts) {
            self.mint(token, caller, recipient, amount, true)?;
        }
        Ok(())
