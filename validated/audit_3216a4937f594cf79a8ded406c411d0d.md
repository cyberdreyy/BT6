In `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-383`), the gateway validates a client-supplied `payload.Timestamp` only for a lower bound (staleness), exactly mirroring the reported bug class: a check exists for "too old" but no check exists for "too far in the future."

### Title
Missing upper-bound (future) timestamp validation on unprivileged web-API trigger requests allows stale-message check bypass and unbounded callback lifetime abuse - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The gateway's `HandleLegacyUserMessage` validates a client-controlled `payload.Timestamp` field against only a lower bound (`now - MaxAllowedMessageAgeSec > timestamp` ⇒ reject as "stale"), but never checks that the timestamp is not unreasonably far in the future. This is the same class of bug as the reported nimiq-blockchain issue: validation only enforces `timestamp >= lowerBound` with no `timestamp <= upperBound` check.

### Finding Description
`HandleLegacyUserMessage` unmarshals a client-supplied `webapicap.TriggerRequestPayload` and validates its `Timestamp` field: [1](#0-0) 

The only check performed is:
```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    // reject as "stale message"
}
```
This rejects timestamps that are too old, but there is no corresponding check that `payload.Timestamp` is not far in the future (e.g., `payload.Timestamp > now + tolerance`). This entry point is reached directly from an unprivileged, unauthenticated-by-session external HTTP client — `HandleLegacyUserMessage` is invoked from the gateway's legacy user-message path and forwards the trigger to all DON nodes via `don.SendToNode` [2](#0-1) . Note that message *authenticity* is separately verified elsewhere via signature (`msg.Sign`/`ValidatedRequestFromMessage`), but the *timestamp value itself* is attacker-controlled content within a validly-signed message, and the code trusts it for freshness-window arithmetic. Because `uint` arithmetic is used, an attacker-supplied timestamp far in the future does not just "bypass" freshness — it can also cause the subtraction `now - MaxAllowedMessageAgeSec` to safely evaluate as always-less than an arbitrarily large future timestamp, guaranteeing the message is always treated as "fresh" regardless of the gateway's actual configured freshness window.

By contrast, other timestamp/expiry validations in the same codebase (e.g., JWT `iat`/`exp` handling in `core/utils/jwt.go`, and `RejectsJWTReplayDuringValidationLeewayWindow` in `core/capabilities/vault/jwt_based_auth_test.go`) explicitly validate both a maximum future-issuance tolerance and expiry ceiling. This handler lacks the equivalent future-bound check for the trigger payload timestamp.

### Impact Explanation
An unprivileged external caller sending a web-API trigger request can set `payload.Timestamp` to an arbitrary large value, always passing the staleness check regardless of the operator-configured `MaxAllowedMessageAgeSec` freshness window. This is a request-validation/input-validation weakness in an internet-facing gateway path, undermining the freshness guarantee the field's own documentation promises ("needs to be within certain freshness to be processed", per `event_trigger-schema.json`) and allowing forged/old requests to be perpetually treated as fresh, which downstream consumers (workflow engines relying on trigger event timestamps) may use for staleness or ordering decisions.

### Likelihood Explanation
High likelihood of triggering: the check is a simple, always-reachable arithmetic comparison on a fully client-controlled integer field in an unauthenticated-content (though signature-verified-envelope) request path; no special privileges are required to hit it.

### Recommendation
Add an explicit upper-bound check, e.g.:
```go
now := uint(time.Now().Unix())
if uint(payload.Timestamp) > now + h.config.MaxAllowedMessageAgeSec {
    // reject: timestamp too far in the future
}
```
and perform the staleness comparison using signed integers/`time.Duration` rather than raw `uint` subtraction to avoid underflow/wraparound edge cases.

### Proof of Concept
1. Craft a `webapicap.TriggerRequestPayload` (as in `triggerRequest` test helper, `core/services/gateway/handlers/capabilities/handler_test.go:193-234`) with `Timestamp: time.Now().Unix() + 10_000_000_000`.
2. Sign the message and submit via the legacy user message path handled by `HandleLegacyUserMessage`.
3. Observe the staleness check `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` evaluates false (since RHS is huge), so the message passes as "fresh" and is dispatched to all DON nodes via `don.SendToNode`, regardless of actual freshness intent.
