### Title
Stale Confirmations From Removed Multisig Members Are Still Counted Toward The Approval Threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` (and its `multisig` counterpart, `DeleteKey`) only purges pending **requests that the removed member itself authored**, but never scans `confirmations` for requests authored by *other* members that the removed member had already confirmed. As a result, a confirmation cast by a member who is later removed from the multisig continues to count toward `num_confirmations` forever, letting a request execute with fewer currently-valid approvers than the configured threshold.

### Finding Description
`confirm()` decides whether to execute a request purely by comparing the *size* of the stored `confirmations: HashSet<String>` against `num_confirmations`: [1](#0-0) 

`delete_member()` is the only place that mutates `confirmations` when membership changes, and it filters strictly by `r.member == member` — i.e. it only deletes requests **authored by** the removed member, then removes the confirmation set for *those* requests. It never inspects confirmation sets belonging to requests authored by someone else that the removed member had confirmed: [2](#0-1) 

So the invariant the protocol relies on — "a request executes only once `num_confirmations` *current* members have approved it" — is not actually enforced. The real binding should be:

```
live_members_who_confirmed(request) >= num_confirmations
```

but the code enforces:

```
confirmations.len() >= num_confirmations
```

where `confirmations` can contain identities that are no longer members.

The same design flaw exists in the older `multisig` contract: `DeleteKey` only clears requests where `r.signer_pk == pk` (i.e., requests *created* by that key), not confirmation sets of other pending requests that key had confirmed: [3](#0-2) 

### Impact Explanation
This breaks the multisig's authorization threshold binding. A request (e.g., `Transfer` moving NEAR out of the multisig account, `AddKey`, `FunctionCall`, etc.) can be executed once the confirmation count reaches `num_confirmations`, even though one or more of the "confirming" identities have since been removed as members. That means fewer *live* members than the documented `K` actually approved the action that ultimately moves funds or changes multisig configuration — matching the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
Member turnover (removing an access key or account from a multisig) is a normal, expected multisig operation, not an attacker precondition requiring a victim key or social engineering. Any long-lived multisig that rotates members while it has outstanding, not-yet-fully-confirmed requests is exposed. No privileged access beyond ordinary membership is required to trigger the flaw — it happens automatically as a side effect of legitimate `DeleteMember`/`DeleteKey` requests combined with normal pending-request activity.

### Recommendation
When removing a member (`delete_member` / `DeleteKey` action), iterate over **all** pending requests' confirmation sets (not just requests authored by the removed member) and strip the removed member's/key's confirmation from each. Alternatively, when counting confirmations in `confirm()`, filter `confirmations` against the current `self.members` set (or `self.num_requests_pk`/live key list) before comparing to `num_confirmations`, so stale approvals from ex-members are never counted.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request` with a `Transfer` action (request `R`, not auto-confirmed).
3. `B` calls `confirm(R)` → `confirmations(R) = {B}`.
4. `C` calls `confirm(R)` → `confirmations(R) = {B, C}` (2 of 3 needed).
5. Separately, members reach threshold on a `DeleteMember { member: B }` request and it executes — `B` is removed from `self.members`, but `confirmations(R)` is untouched because `delete_member` only clears requests where `r.member == B` (R was authored by `A`, not `B`).
6. `D` calls `confirm(R)` → `confirmations(R).len() + 1 == 3 >= num_confirmations` → `R` executes and the `Transfer` is scheduled, even though only `C` and `D` are currently-valid members who actually approved it (`B`'s stale confirmation counted toward the 3-of-4 threshold after `B` was removed).

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
