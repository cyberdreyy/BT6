### Title
Loss-adjusted withdraw receipts are keyed to the post-stop epoch while `lastWithdrawRequest` stores the request epoch, so haircutted receipts claim at par and drain the funded reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.collectWithdrawFunds` records a partial-funding haircut under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` is already incremented inside `deposit()` when the CDO calls it during `stopEpoch` (`epochNumber += 1` when `isEpochRunning()` is still true). Withdraw requests, however, store `lastWithdrawRequest[_user] = epochNumber` from the *request* epoch — one less than the epoch key under which the loss price is stored. Both the new-request guard in `requestWithdraw` and `_claimLossAdjustedWithdrawRequest` look up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, which therefore always reads `0` ("no loss-adjusted epoch") for every affected receipt. The receipts then fall through to `_claimFundedWithdrawRequest`, which pays them in full at par even though the borrower only funded `pendingToFund < pendingBasis` underlying.

### Finding Description
Bug-class mapping: the Drools report is improper input validation of attacker-controlled serialized data; the vault analog is an unvalidated/stale epoch index used to select the accounting path for a withdraw receipt.

Flow:
1. During a running epoch `N`, users call `IdleCDOEpochVariant.requestWithdraw`, which calls `IdleCreditVault.requestWithdraw`. The vault records `withdrawsRequests[_user] += _amount`, `withdrawsRequestsByEpoch[_user][N] += _amount`, `lastWithdrawRequest[_user] = N`, and `pendingWithdraws += _amount` (IdleCreditVault.sol:282-293).
2. At `stopEpoch`, the borrower under-funds the receipts (e.g., `stopEpochWithDuration` realized loss). Inside the same transaction, `deposit()` sees `isEpochRunning() == true` and executes `epochNumber += 1`, so `epochNumber` is now `N+1` before funds are collected (IdleCreditVault.sol:607-614).
3. `collectWithdrawFunds(pendingToFund)` with `pendingToFund < pendingWithdraws` stores `lossRecoveryPriceByEpoch[N+1] = pendingToFund * 1e18 / pendingBasis` and zeroes `pendingWithdraws` (IdleCreditVault.sol:411-421). Only `pendingToFund` underlying is transferred into the strategy.
4. When the user calls `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user] = N` and `lossRecoveryPriceByEpoch[N]`, which is `0`, so it returns early (IdleCreditVault.sol:790-792).
5. `_claimFundedWithdrawRequest` then runs: the gate `epochNumber (N+1) <= lastWithdrawRequest (N)` is false, so it pays `withdrawsRequests[_user]` in full at par via `_transferFundedClaim` (IdleCreditVault.sol:326-349).
6. The same lookup miss defeats the guard in `requestWithdraw` (IdleCreditVault.sol:262-271), so users are also never forced to claim the haircutted receipt before opening new requests.

The broken invariant is "one receipt, one payout at the recorded recovery ratio": every receipt of the loss epoch is paid at 100% while the reserve only holds `pendingToFund`.

### Impact Explanation
Direct theft plus insolvency. Suppose `pendingBasis` = 1,000,000 USDC across several receipts and a stop-epoch loss makes `pendingToFund` = 600,000 USDC (`lossRecoveryPrice` = 0.6e18). The first claimants draw the full 1,000,000-face-value receipts FIFO until the 600,000 USDC is exhausted; later claimants' claims revert on the underlying transfer (`safeTransfer` insufficient balance), permanently freezing their share. Early claimants receive ~1.67x their fair haircutted value — stolen directly from later claimants. The same first-come-first-served drain applies to the instant-withdraw path analogously if the epoch keying mismatch is mirrored, and to any future legitimate funded claims since `_transferFundedClaim` only protects `defaultRecoveryReserve`, not the unfunded shortfall.

### Likelihood Explanation
Likelihood is conditional on two things:

- Ordering: this requires `deposit()` (which bumps `epochNumber`) to run before `collectWithdrawFunds` inside the same `stopEpoch` flow. `deposit()`'s own comment confirms it increments `epochNumber` on stopEpoch, and the queue tests confirm `epochNumber` is already the next epoch when users claim. If the CDO instead calls `collectWithdrawFunds` before any `deposit`, the keying is consistent and the bug collapses — this ordering must be confirmed against `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` in `contracts/IdleCDOEpochVariant.sol`, which I could not fully trace within this session.
- Preconditions: a realized stop-epoch loss (`stopEpochWithDuration(_lossAmount)` / borrower under-funding via `collectWithdrawFunds`) with at least one pending withdraw receipt — an ordinary, expected code path, not an edge case, and executable while the attacker is only a KYC-passing lender requesting a normal withdraw.

No existing guard stops it: the `requestWithdraw` loss-receipt guard reads the same wrong key, `_transferFundedClaim` only ring-fences `defaultRecoveryReserve`, and `_claimFundedWithdrawRequest`'s epoch gate (`epochNumber <= lastWithdrawRequest`) passes because `epochNumber` has advanced.

### Recommendation
Key the loss price by the epoch in which the receipts were requested, not the incremented counter: store `lossRecoveryPriceByEpoch[epochNumber - 1]` (or capture `epochNumber` before `deposit()` bumps it and pass it into `collectWithdrawFunds`), and equally store `instantWithdrawClaimsByEpoch` / `defaultRecoveryEpoch` consistently. Alternatively, make `lastWithdrawRequest` and `lossRecoveryPriceByEpoch` use the same "settlement epoch" convention everywhere and add a consistency check in `collectWithdrawFunds` that every pending receipt's `lastWithdrawRequest` epoch resolves to a non-zero recovery price.

### Proof of Concept
Foundry fork test (solidity 0.8.10), based on the existing harness in `test/foundry/IdleCreditVault.t.sol`:

```solidity
function testLossAdjustedReceiptsClaimAtPar() external {
    uint256 amount = 100_000 * ONE_SCALE;
    // two lenders deposit into AA
    uint256 trancheA = idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);
    uint256 trancheB = _depositWithUser(user2, amount); // helper from harness

    _startEpochAndCheckPrices(0);

    // both request full withdraw during running epoch N
    uint256 reqA = cdoEpoch.requestWithdraw(trancheA, address(AAtranche));
    vm.prank(user2);
    uint256 reqB = cdoEpoch.requestWithdraw(trancheB, address(AAtranche));
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    uint256 pendingBasis = vault.pendingWithdraws(); // ~ reqA + reqB

    // borrower funds only 50% of pending receipts via stopEpochWithDuration loss path
    uint256 pendingToFund = pendingBasis / 2;
    deal(defaultUnderlying, borrower, pendingToFund + cdoEpoch.expectedEpochInterest());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, _lossAmountCoveringHalfOfPending); // loss applied to pending bucket

    // BUG: recovery price was stored under epochNumber AFTER deposit() bumped it,
    // while lastWithdrawRequest[user] is the pre-stop epoch, so the loss lookup misses.
    uint256 userLossEpoch = vault.lastWithdrawRequest(address(this));
    assertEq(vault.lossRecoveryPriceByEpoch(userLossEpoch), 0); // haircut invisible to the claim path

    // first claimer drains funded reserve at par instead of 50%
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(address(this)) - balPre;
    assertEq(got, reqA);            // received 100%, fair value was reqA / 2
    assertGt(got, pendingToFund / 2);

    // second claimer's identical receipt now reverts / is frozen: reserve exhausted
    vm.prank(user2);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```

Expected result: `user1` receives the full receipt value while `user2`'s claim is unpayable, demonstrating insolvency and theft of the haircut difference. If the test instead shows `lossRecoveryPriceByEpoch[userLossEpoch] != 0`, the call ordering in `stopEpoch` keys the price under the request epoch and this finding does not hold — that ordering check in `contracts/IdleCDOEpochVariant.sol` is the single remaining verification step.
