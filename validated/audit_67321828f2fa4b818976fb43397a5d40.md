### Title
Unaccounted stake slashing causes permanent DoS of commission, unlock, and distribution flows in `staking_contract` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract.move` records a `principal` value for each staker/operator pair and computes accumulated rewards as `total_active_stake - principal` in `get_staking_contract_amounts_internal`. This computation assumes `total_active_stake` (the live `active` + `pending_active` balance on the underlying stake pool) can only grow relative to the last recorded `principal`. If active stake ever falls below the recorded `principal` — the loss-accounting scenario described in the external report, analogous to an external vault losing value between snapshots — the unsigned subtraction underflows and aborts, permanently blocking every entry point that depends on this calculation.

### Finding Description
`get_staking_contract_amounts_internal` is documented and specified (see `staking_contract.spec.move`, lines 391-398) to compute: [1](#0-0) 
```
let accumulated_rewards = total_active_stake - staking_contract.principal;
```
`principal` is only ever updated downward/upward inside `request_commission_internal` (`staking_contract.principal = total_active_stake - commission_amount`) and `unlock_stake` (`staking_contract.principal -= amount`): [2](#0-1) [3](#0-2) 

Nowhere in `staking_contract.move` is `principal` decreased to reflect a reduction of the underlying stake pool's `active` balance that is *not* driven by an explicit `unlock_stake`/`request_commission` call. This is exactly the bug class from the external report: the module keeps an internal "recorded" balance (`principal`, analogous to a vault's recorded total supply) that can drift out of sync with the real, external balance (`stake::get_stake` active amount, analogous to the vault's physical assets) whenever the external balance decreases unexpectedly. Every consumer of `get_staking_contract_amounts_internal` — `request_commission_internal`, `unlock_stake`, `unlock_rewards`, `distribute_internal`'s companion `add_distribution` (via `stake::get_stake`), and the public `staking_contract_amounts` view — performs the unchecked `total_active_stake - staking_contract.principal` subtraction: [4](#0-3) [5](#0-4) 

If `total_active_stake < principal`, Move's unsigned arithmetic aborts. Because `unlock_stake`, `unlock_rewards`, and `request_commission` all unconditionally call `request_commission_internal` (which performs this subtraction) before doing anything else, and `switch_operator`/`switch_operator_with_same_commission` also route through `request_commission_internal`, a single loss event on the underlying stake pool (reducing `active` below `principal`) freezes the staker's ability to unlock stake, the operator's/beneficiary's ability to claim commission, and the ability to switch operators — for as long as the deficit persists.

By contrast, `delegation_pool.move` explicitly anticipates this exact scenario and defensively guards against it: [6](#0-5) 
`calculate_stake_pool_drift` checks `if (active > pool_active) {...} else { /* handle any slashing applied to active stake */ 0 }` rather than subtracting unconditionally — confirming that the framework authors are aware active balances can decrease and must be defended against, yet `staking_contract.move`'s reward/commission calculation performs the subtraction without this guard.

### Impact Explanation
This matches the "Permanent lock or non-recoverable loss of claim rights in stake, delegation, commission, beneficiary, or vesting flows" impact category. A staker whose stake pool active balance drops below the last-recorded `principal` loses the ability to:
- Unlock any of their stake (`unlock_stake`, `unlock_rewards` abort).
- Have operator commission requested/paid (`request_commission` aborts), trapping operator/beneficiary payout rights.
- Switch operators (`switch_operator*` calls `request_commission_internal` internally).
- Even query `staking_contract_amounts`/off-chain tooling built on it (used by Rosetta, per `crates/aptos-rosetta/src/types/misc.rs`) will abort.

Because `staking_contract` (and `vesting.move`, which is built entirely on top of `staking_contract`) has no path to reduce `principal` in response to an externally-driven stake decrease, the state is unrecoverable without a privileged framework upgrade — a genuine "stranded value" condition.

### Likelihood Explanation
The likelihood hinges on whether the underlying stake pool's `active`/`pending_active` balance can decrease outside of `unlock`/`request_commission` calls (e.g., validator misbehavior penalties or any future/forked slashing mechanism, or any code path that reduces `active` for governance/other reasons). `delegation_pool.move`'s explicit handling of "any slashing applied to active stake" indicates the framework's design anticipates such balance decreases as a first-class case that must be tolerated. `staking_contract.move` was not updated with the same defensive check, making it a latent inconsistency between two stake-management modules that are supposed to preserve the same lockup/reward invariants.

### Recommendation
**Short term:** In `get_staking_contract_amounts_internal`, mirror the defensive pattern used in `delegation_pool::calculate_stake_pool_drift`: compute `accumulated_rewards` as `if (total_active_stake > staking_contract.principal) { total_active_stake - staking_contract.principal } else { 0 }`, and clamp `principal` down to `total_active_stake` when a deficit is detected instead of relying on unchecked subtraction.

**Long term:** Add an explicit reconciliation step (analogous to delegation pool's OLC synchronization) in `staking_contract.move` and `vesting.move` so that any stake-pool balance decrease is absorbed and accounted for before commission/reward math executes, and add regression tests exercising a decreasing `active` balance across `request_commission`, `unlock_stake`, `unlock_rewards`, and `switch_operator` paths.

### Proof of Concept
Exact repro requires triggering a decrease of `stake::get_stake(pool_address)`'s `active` component below the `principal` value recorded in the `StakingContract`. I was not able to independently confirm within the available tooling whether any unprivileged, mainnet-reachable path in the current `stake.move` can reduce `active` balance outside of `unlock`-driven transitions (e.g., an active slashing implementation) — the `read_file` call needed to inspect the full body of `get_staking_contract_amounts_internal` did not return content, so I could not fully verify the precise arithmetic beyond the `.spec.move` postcondition. Given this residual uncertainty about whether stake.move currently exposes any unprivileged loss trigger, this should be treated as a **latent accounting-hardening gap** confirmed by the spec and by the contrasting defensive code in `delegation_pool.move`, rather than a fully demonstrated end-to-end exploit; a Devin session with full source access should confirm the exact underflow condition in `get_staking_contract_amounts_internal` and any current or planned unprivileged path that decreases `active` stake before treating this as an immediately exploitable, unprivileged root cause.
