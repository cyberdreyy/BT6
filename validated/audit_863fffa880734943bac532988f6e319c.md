### Title
Reject-then-accept ordering double-counts a single signer's weight across both `total_weight_approved` and `total_weight_rejected` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` tallies signer responses for a proposed block using two separate bookkeeping structures: `gathered_signatures` (accept-only) and `responded_signers` (meant to be the union of accept+reject, used to prevent double counting). The `Accepted` branch gates its weight addition on `gathered_signatures`, while the `Rejected` branch gates on `responded_signers`. Because these two guards are not the same set, a signer that first rejects and later legitimately accepts the same block has its weight counted into *both* `total_weight_rejected` and `total_weight_approved`.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, the `Accepted` handling path is: [1](#0-0) 

and it gates the weight addition on `!block.gathered_signatures.contains_key(&slot_id)`, then unconditionally inserts into both `gathered_signatures` and `responded_signers`.

The `Rejected` handling path is: [2](#0-1) 

and it gates the weight addition on `block.responded_signers.insert(slot_id)` returning `true` (i.e., first time seen in `responded_signers`).

`BlockStatus` defines these as two independent collections: [3](#0-2) 

Because the two branches consult different sets, the guard is asymmetric depending on message order for the *same signer, same block*:
- Accept-then-Reject: `responded_signers` already contains the slot id from the accept, so the reject's `insert` returns `false` and `total_weight_rejected` is correctly *not* incremented (a bearer signature cannot be revoked — this is the intended one-way behavior documented in `docs/signer-flows.md` around the "signature is a bearer instrument" note).
- Reject-then-Accept: the reject adds the slot id to `responded_signers` (but not to `gathered_signatures`). When the accept later arrives from the same signer for the same block, the check `!block.gathered_signatures.contains_key(&slot_id)` is still true (it only ever checked `gathered_signatures`, not `responded_signers`), so `total_weight_approved` is *also* incremented for that signer's weight — even though that same signer's weight was already added to `total_weight_rejected`.

This breaks the intended invariant (implicit in the design, and explicit in `responded_signers`' doc comment "Set of the slot ids of signers who have responded") that a signer's weight should be attributed to exactly one side of the tally. The consequence is that `total_weight_rejected + total_weight_approved` can exceed `total_weight`, i.e. the aggregated tallies no longer correspond to a partition of verified, distinct-signer responses — analogous to the ECC report's core defect: a value computed correctly under one representation is silently reused under a mismatched second representation (here, `gathered_signatures` vs `responded_signers`) because of an asymmetric/redundant guard, and nothing currently forces the two branches' bookkeeping to stay consistent.

### Impact Explanation
The tallies feed directly into the coordinator's decision logic in `signer_coordinator.rs`: [4](#0-3) 

The rejection branch is evaluated first. If a signer initially rejects (contributing stale weight to `total_weight_rejected` that is never retracted even after that signer later accepts), that stale rejection weight can combine with other genuine rejecters to cross the `> self.total_weight - weight_threshold` "blocking minority" bound even though, in reality, that signer has since accepted and the true current rejecting weight is lower. This can cause the coordinator to wrongly conclude the block is dead (`SignersRejected`), unnecessarily temporarily/permanently exclude transactions (`temporarily_excluded_txids`/`permanently_excluded_txids`), and abort block assembly — a liveness degradation of the mining/signing state machine driven by a single equivocating (or simply slow-to-change-its-mind) signer, not requiring a majority of the signer set.

### Likelihood Explanation
This requires only one signer (whose message ordering is not otherwise anomalous — a signer legitimately can reject first and accept later once "a rival is still alive" scenarios resolve, per the documented signer flow) to have its two responses processed by the node in the order reject-then-accept, which is a realistic, unprivileged, single-actor scenario reachable purely via normal StackerDB gossip.

### Recommendation
Use a single, consistent set to gate weight addition for both accept and reject paths (e.g., always check/insert into `responded_signers` before adding weight in either branch, and derive `gathered_signatures` purely as a data store rather than as the guard), so that a signer's weight is added to exactly one of `total_weight_approved` / `total_weight_rejected` regardless of message arrival order.

### Proof of Concept
1. Node receives a `Rejected` message (slot `S`, weight `W`) for block `B`. `responded_signers` gains `S`; `total_weight_rejected += W`.
2. The same signer `S` later sends a valid `Accepted` message for the same block `B` (e.g., after re-evaluating once a competing block went stale, per the documented sign-later behavior).
3. In the `Accepted` branch, the check `!block.gathered_signatures.contains_key(&slot_id)` is `true` (this signer never appeared in `gathered_signatures`), so `total_weight_approved += W` is also executed.
4. Now `total_weight_rejected` and `total_weight_approved` both include `W` for the same signer `S`, violating the intended exclusivity and potentially triggering `SignersRejected`/tx-exclusion logic in `signer_coordinator.rs` using stale/duplicated rejection weight.
