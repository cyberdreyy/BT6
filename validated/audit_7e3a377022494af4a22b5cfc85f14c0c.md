### Title
Unbounded Flashblocks state-update queue allows memory-exhaustion / node halt under sustained queue lag - ([File: crates/execution/flashblocks/src/state.rs])

### Summary
`FlashblocksState` merges canonical-block notifications and flashblock payloads into a single `tokio::mpsc::unbounded_channel` (`StateUpdate` queue) that is drained by a single-threaded `StateProcessor`. The crate's own documentation and code comments acknowledge that this queue has no capacity bound: "The update queue is unbounded... a sustained burst of payloads that are all ahead of the tip still grows memory. A hard bound on the queue is separate work." This mirrors CVE-2023-6516's root cause in BIND9: an asynchronous cleanup/maintenance mechanism (there, cache-eviction records; here, `StateUpdate` entries) is queued for later, ordered processing, but nothing caps the queue's size, so when the producer (flashblock/canonical arrival) outpaces the consumer (the processor thread), the backlog — and the node's memory footprint — grows without the configured bound (`max_pending_blocks_depth`) actually limiting anything but the *published* snapshot's staleness, not the underlying queue's memory.

### Finding Description
`FlashblocksState::new` creates the queue with `mpsc::unbounded_channel::<StateUpdate>()`: [1](#0-0) 

`StateProcessor::effective_canonical_number` and surrounding comments explicitly document that "Canonical and flashblock updates share one unbounded queue applied FIFO, so the height of a queued notification can be far behind the height the node has actually reached": [2](#0-1) 

The crate README states plainly that the bound (`max_pending_blocks_depth`, default 3) only governs how stale a *published* pending snapshot may be — it does not bound the queue itself — and that a sustained burst of ahead-of-tip payloads still grows memory without limit: [3](#0-2) 

The mitigation implemented (dropping superseded flashblocks before they are queued, and dropping stale published snapshots) reduces the *steady-state* backlog shape that caused the referenced 2026-08-20 incident, but explicitly does not cap the queue's absolute memory usage when updates arrive faster than the single processor task can apply them — exactly the "asynchronous cleanup queued for later processing, with no size cap" pattern in CVE-2023-6516: [4](#0-3) 

The processor drains this queue on a single task via `while let Some(update) = self.rx.lock().await.recv().await`, applying updates strictly FIFO, so any lag between arrival rate and per-update processing cost (execution of pending state, reorg detection, cache lookups) directly translates into queue growth: [5](#0-4) 

### Impact Explanation
Uncontrolled growth of the `StateUpdate` queue consumes heap memory proportional to the backlog. Since this queue underlies pending-state RPCs (`eth_getBlockByNumber("pending")`, `eth_call`, `eth_estimateGas`, `eth_simulateV1`, `eth_sendRawTransactionSync`, and the `newFlashblocks`/`pendingLogs`/`newFlashblockTransactions` subscriptions), sustained queue growth degrades or halts the flashblocks-enabled RPC node — a node-halt / RPC-can-no-longer-be-served condition, matching the accepted impact classes for this scan.

### Likelihood Explanation
This is a documented, acknowledged limitation in the shipped code (the README explicitly calls out "A hard bound on the queue is separate work"), and the queue-lag failure mode has already manifested once as a real production incident referenced directly in the test suite (`crates/execution/flashblocks-node/tests/state.rs:855-857`, "the 2026-08-20 mainnet incident where canonical and flashblock updates piled up in the shared unbounded queue"). Any condition that causes the processor to fall behind the arrival rate of canonical/flashblock updates for a sustained interval reproduces unbounded growth, so likelihood is high given prior real-world occurrence.

### Recommendation
Replace the unbounded channel backing `FlashblocksState`'s update queue with a bounded channel (`tokio::sync::mpsc::channel` with a fixed capacity) and define an explicit backpressure/drop policy (e.g., drop-oldest or drop-new with metrics) once the bound is reached, analogous to how `FlashblockCache` already bounds cached entries via `MAX_CACHE_AHEAD_BLOCKS`. Track queue depth in metrics and alert operators before memory exhaustion occurs.

### Proof of Concept
1. Run a flashblocks-enabled node subscribed to a flashblocks WS feed.
2. Induce sustained lag between the arrival rate of `StateUpdate::Flashblock`/`StateUpdate::Canonical` events and the processor's ability to apply them (e.g., by driving high per-block/per-flashblock processing cost, or by replaying a burst of payloads that remain ahead of the tip, as reproduced in `advance_tip_without_processing` / `test_stale_pending_dropped_once_node_advances_past_it`).
3. Observe queue depth (unbounded `mpsc` channel) growing without bound as documented in `crates/execution/flashblocks/README.md:100-102`, consuming increasing memory until the process is OOM-killed or becomes unresponsive to RPC requests. [6](#0-5)

    /// Processes updates from the queue until the channel closes.
    pub async fn start(&self) {
        while let Some(update) = self.rx.lock().await.recv().await {
            let prev_pending_blocks = self.load_pending_or_drop_stale();
            match update {
                StateUpdate::Canonical(block) => {
                    debug!(message = "processing canonical block", block_number = block.number);
                    match self.process_canonical_block(prev_pending_blocks, &block) {
                        Ok(new_pending_blocks) => {
                            self.pending_blocks.swap(new_pending_blocks);

                            let mut cache = self.cache.lock().await;
                            cache.update_canonical(block.number);
                            let cached = cache.drain(block.number + 1);
                            drop(cache);

                            if !cached.is_empty() {
                                debug!(
                                    message = "replaying cached flashblocks after canonical block",
                                    canonical_block = block.number,
                                    cached_count = cached.len(),
                                );
                                for flashblock in cached {
                                    let fb_prev = self.load_pending_or_drop_stale();
                                    self.apply_flashblock(fb_prev, flashblock).await;
                                }
                            }
                        }
                        Err(e) => {
                            error!(message = "could not process canonical block", error = %e);
                        }
                    }
                }
                StateUpdate::Flashblock(flashblock) => {
                    debug!(
                        message = "processing flashblock",
                        block_number = flashblock.metadata.block_number,
                        flashblock_index = flashblock.index
                    );
                    self.apply_flashblock(prev_pending_blocks, flashblock).await;
                }
            }
        }
    }
