### Title
`parse_config` accepts single-key Config accounts lacking any validator identity/signer, unlike CLI's `parse_validator_info`, causing `jsonParsed` RPC responses to misrepresent unauthenticated data as validator info - ([File: account-decoder/src/parse_config.rs])

### Summary
`parse_config` (dispatched via `PARSABLE_PROGRAM_IDS` keyed on `config::id()` account owner in `account-decoder/src/parse_account_data.rs`) only requires `key_list.keys[0].0 == validator_info::id()` to treat account data as `ConfigAccountType::ValidatorInfo`, with no check that a second (identity/signer) key exists. [1](#0-0)  The CLI's `parse_validator_info`, by contrast, additionally requires `key_list.keys.len() > 1` and reads `key_list.keys[1]` as the validator identity/signer, returning `None` when only the `validator_info::id()` marker key is present. [2](#0-1) 

### Finding Description
An attacker can create (own and fund) a Config-program account whose owner is `config::id()`/`solana_config_interface::id()` and whose serialized `ConfigKeys` contains exactly one entry: `[(validator_info::id(), false)]`, followed by arbitrary bincode-serialized JSON `ValidatorInfo` payload data. When an RPC client calls `getAccountInfo` with `jsonParsed` encoding, the account-decoder dispatch table routes based on the account owner equal to `config::id()` to `parse_config` (`account-decoder/src/parse_account_data.rs` lines 24-46, using `ParsableAccount::Config`). `parse_config` deserializes `ConfigKeys`, checks only that `keys` is non-empty and `keys[0].0 == validator_info::id()` (`account-decoder/src/parse_config.rs` line 15), then calls `parse_config_data` which maps every key (here, just the single `validator_info::id()` marker with `signer: false`) into `UiConfigKey`s and successfully parses the trailing bytes as `config_data: Value` if it happens to bincode-deserialize as a JSON string. It returns `Ok(ConfigAccountType::ValidatorInfo(UiConfig{ keys, config_data }))` — a fully "valid" parsed result with `keys.len() == 1` and no signer key at all.

This is inconsistent with the CLI-side notion of a valid "validator info" record: `parse_validator_info` in `cli/src/validator_info.rs` explicitly requires `keys.len() > 1` (line 138) and extracts the validator identity/signer status from `keys[1]`; a single-key account is rejected (returns `None`, tested by `test_parse_validator_info_empty_key_list`, lines 634-650). Thus the two code paths disagree on what constitutes a valid ValidatorInfo record: `parse_config` will happily "faithfully" report the raw single-key account as a `ValidatorInfo`-typed object via the read API, even though it represents no actual registered validator identity and carries no signer key, while the CLI (and the semantic invariant it encodes — that a validator info entry must be tied to an identity key at index 1) would treat the same bytes as not a valid validator info account at all.

### Impact Explanation
This falls into the "wrong data returned by a read API" category: `jsonParsed` responses for `getAccountInfo`/`getProgramAccounts` on Config-program accounts will report `ConfigAccountType::ValidatorInfo` with a `keys` array of length 1 and no identity/signer entry, misleading any RPC consumer that assumes ValidatorInfo-typed jsonParsed output always corresponds to a real, signer-authenticated validator identity (as the CLI's stricter `parse_validator_info` guarantees for equivalent data). This is a data-integrity/misreporting issue exposed purely through the read API (`account-decoder/src/parse_config.rs`), reachable by any unprivileged party who can fund a Config-owned account with attacker-chosen bytes and have it read back via a single `getAccountInfo` call — no validator/leader control, gossip, or multiple calls required.

### Likelihood Explanation
Fully attacker-controlled and trivially reproducible: the attacker only needs to submit a standard `create_account`+`store` sequence to the Config program (owned by `solana_config_interface::id()`) with `keys = [(validator_info::id(), false)]` and any bincode-serializable JSON string as `config_data`, then issue one `getAccountInfo` call with `jsonParsed` encoding — well within the "one call" budget and requiring no special account state, staking, or timing.

### Recommendation
Align `parse_config`'s acceptance criteria with the semantic guarantee that a `ValidatorInfo` record represents a real registered identity: require `key_list.keys.len() > 1` (and ideally validate that `keys[1]` looks like a real, distinct pubkey) before returning `ConfigAccountType::ValidatorInfo`, mirroring `cli/src/validator_info.rs::parse_validator_info`'s `keys.len() > 1` check. Alternatively, if the decoder is intended to be a purely structural decode of raw bytes (not implying identity), the discrepancy should be documented and RPC clients should be warned not to treat `jsonParsed` ValidatorInfo entries as validated identities; but as-is, the divergence from the CLI's stricter interpretation is a data-integrity inconsistency that should be fixed in the decoder.

pub fn parse_config(data: &[u8], _pubkey: &Pubkey) -> Result<ConfigAccountType, ParseAccountError> {
    let parsed_account = deserialize::<ConfigKeys>(data).ok().and_then(|key_list| {
        if !key_list.keys.is_empty() && key_list.keys[0].0 == validator_info::id() {
            parse_config_data::<String>(data, key_list.keys).and_then(|validator_info| {
                Some(ConfigAccountType::ValidatorInfo(UiConfig {
                    keys: validator_info.keys,
                    config_data: serde_json::from_str(&validator_info.config_data).ok()?,
                }))
            })
        } else {
            None
        }
    });

fn parse_validator_info(
    account: &Account,
) -> Option<(Pubkey, bool, Map<String, serde_json::value::Value>)> {
    if account.owner != solana_config_interface::id() {
        return None;
    }
    let key_list: ConfigKeys = deserialize(&account.data).ok()?;
    if key_list.keys.len() > 1 {
        let (validator_pubkey, is_signed) = key_list.keys[1];
        let validator_info_string: String =
            get_config_data(&account.data).and_then(deserialize).ok()?;
        let validator_info: Map<_, _> = serde_json::from_str(&validator_info_string).ok()?;
        Some((validator_pubkey, is_signed, validator_info))
    } else {
        None
    }
}
