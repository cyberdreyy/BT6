## Analysis

The code path is real and traceable:

- `runRunSteps` in `functions/concrete/run/runner.go` derives `scriptCtx` from `jobCtx` via `r.withTimeout`, which uses `context.WithCancel` when `r.config.ScriptTimeout <= 0` [1](#0-0) , and registers that cancel func via `r.setCancel(cancel)` so `Cancel()` (or job-level deadline/UI cancel) tears down `scriptCtx` immediately [2](#0-1) .
- `runUserSteps` passes that same `scriptCtx` straight into `cli.RunAndFollow(ctx, req, out)` with no other cancellation signaling [3](#0-2) .
- `buildRunRequest` only sets `req.Timeout` when `r.config.ScriptTimeout > 0`; when it's `0` (or unset), `req.Timeout` stays `nil`, so the step-runner side has no server-enforced deadline for that nested tenant job [4](#0-3) .
- Contrast this with the top-level dispatch path in `steps/execute.go`: it explicitly wires `Options.RegisterCancel` so that when the outer context is cancelled, a dedicated callback fires an explicit `c.Cancel(cancelCtx, request.Id)` gRPC call to the step-runner server [5](#0-4) . The doc comment explains this exists precisely so "step-runner runs its post-cancel phases... before exiting" [6](#0-5) . The tests (`TestExecute_RegisterCancel_TriggersCancelRPC`) confirm that without this explicit `Cancel` RPC, cancellation is not communicated to the server [7](#0-6) .
- `runUserSteps` (nested `run:` dispatch) has **no equivalent `RegisterCancel`/explicit `Cancel` RPC wiring** — it relies solely on the client-side `ctx` passed to `RunAndFollow` being cancelled, i.e., the gRPC stream context ending client-side, not an explicit instruction to the server to abort the tenant's job.
- `steps/localserver/localserver.go` explicitly documents that the shared server's "lifetime is bound to Stop, not any caller context: it may outlive the build that started it" [8](#0-7) , and tenant/job state inside it is tracked by `di.Container`'s `StepRunnerService`, keyed by the request `Id` (`r.config.ID + "-run"`) rather than torn down alongside the client connection [9](#0-8) [10](#0-9) .

This asymmetry (explicit-Cancel-RPC pattern used for the top-level job, but absent for nested `run:` dispatch) combined with `req.Timeout` being omittable is a real, reachable gap. However, I cannot fully confirm from this repo alone whether the vendored `extended.RunAndFollow`/step-runner gRPC client automatically issues a server-side abort on local `ctx` cancellation as part of its stream-teardown semantics (that logic lives in the `step-runner` dependency, outside this repo's index). Given the codebase's own design precedent in `steps/execute.go` — which deliberately adds an explicit `Cancel` RPC specifically because context cancellation alone is documented as insufficient to stop a step-runner job gracefully — the omission of that same mechanism in `runUserSteps` is a credible, concrete gap rather than a purely theoretical one.

### Title
Nested `run:` step dispatch omits explicit Cancel RPC to step-runner on job cancellation/timeout - ([File: functions/concrete/run/run_steps.go])

### Summary
`runUserSteps` cancels only the local Go context passed to `RunAndFollow` when a job is cancelled or times out, but never issues the explicit `Cancel` RPC that `steps/execute.go` uses for the top-level job dispatch to instruct the shared step-runner server to abort the corresponding tenant job. Combined with `req.Timeout` being `nil` whenever `ScriptTimeout <= 0`, a nested job's server-side execution state on the long-lived shared unix-socket server has no guaranteed teardown trigger tied to the outer job's cancellation.

### Finding Description
`runRunSteps` derives `scriptCtx` from `jobCtx` and wires `Cancel()`/timeout to cancel it [1](#0-0) . `runUserSteps` only forwards that `ctx` into `cli.RunAndFollow(ctx, req, out)` [11](#0-10) , with no `RegisterCancel`-style callback issuing an explicit `Cancel` RPC to the server, unlike `steps/execute.go`'s pattern [5](#0-4) . `buildRunRequest` also leaves `req.Timeout` unset when `r.config.ScriptTimeout <= 0` [12](#0-11) , removing the only other server-enforced bound on the nested job's runtime. The shared server backing this dispatch is explicitly documented to outlive any individual build [8](#0-7) , and tenant state is tracked by request ID inside `di.Container`'s service, not torn down by client disconnect alone.

### Impact Explanation
If the underlying `RunAndFollow` gRPC stream teardown on local context cancellation does not itself trigger the server to abort the corresponding tenant job (as the codebase's own `steps/execute.go` precedent implies is necessary via an explicit `Cancel` RPC), a cancelled or timed-out job with nested `run:` steps and `ScriptTimeout` unset/0 can leave orphaned execution state/goroutines on the shared step-runner server, consuming resources that persist across subsequent tenants sharing that same server process.

### Likelihood Explanation
Preconditions are trivial and attacker-controllable: any pipeline author can use the `run:` keyword with nested steps and rely on default/unset `script_timeout`, then trigger job cancellation via the UI/API or let the job hit its outer `Timeout`. No special privileges are required beyond authoring a normal `.gitlab-ci.yml` job.

### Recommendation
Add the same `RegisterCancel`-style explicit `Cancel(ctx, req.Id)` RPC wiring to `runUserSteps`/`buildRunRequest` that `steps/execute.go` uses for top-level dispatch, ensuring the nested tenant job is explicitly told to abort (and its server-side state cleaned up) whenever the outer `scriptCtx`/`jobCtx` is cancelled — independent of whether `req.Timeout` was set.

### Proof of Concept
Extend `steps/stepstest`-style fake server usage into `functions/concrete/run/run_steps_test.go`: start a fake step-runner service that records `Run`/`Cancel` calls; invoke `runUserSteps` with a context cancelled mid-flight and `ScriptTimeout` set to 0; assert that a `Cancel` RPC for the nested request `Id` was received by the fake server. Currently no such assertion exists for the nested `run:` path (only `steps/execute_test.go` pins this contract for the top-level path), so this test should fail against current code, demonstrating the gap.
