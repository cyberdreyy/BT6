### Title
Mid-epoch deposits mint tranches at a price excluding accrued fixed-APR interest, diluting existing lenders' yield - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
CVE-2020-8625 is a crash/RCE reachable only through a code path (GSS-TSIG) that is disabled in the default configuration and exposed solely when an operator explicitly enables the feature. The closest analog in idle-tranches is `depositDuringEpoch` in `IdleCDOEpochVariant`: the path is disabled by default (`isDepositDuringEpochDisabled = true` set in `_additionalInit`, contracts/IdleCDOEpochVariant.sol:86) and becomes reachable only when the owner explicitly flips the flag via `setIsDepositDuringEpochDisabled` (contracts/IdleCDOEpochVariant.sol:150-153). When enabled, a lender can deposit mid-epoch and receive tranche tokens priced on `lastNAV`-based `virtualPrice`, which excludes the fixed-APR interest that has already accrued for the elapsed fraction of the epoch but is only crystallized at `stopEpoch`.

### Finding Description
In fixed-APR mode, `expectedEpochInterest` is computed once at `startEpoch` as `_calcInterest(getContractValue())` plus the over/under-performance adjustment (contracts/IdleCDOEpochVariant.sol:260-262). It is a fixed amount owed by the borrower for the whole epoch, regardless of when capital entered.

Mid-epoch deposits go through `depositDuringEpoch`, which mints strategy tokens to the CDO without moving underlyings through `deposit()` — the strategy's `mintStrategyTokens` mints 1:1 strategy tokens with no underlying pulled (contracts/strategies/idle/IdleCreditVault.sol:621-624), because the underlying is sent straight to the borrower. Tranche tokens are minted at the current `virtualPrice`, which reflects `lastNAVAA`/`lastNAVBB` — i.e., NAV as of the last `stopEpoch`/`startEpoch` checkpoint, not NAV plus elapsed epoch interest.

At `stopEpoch`, the borrower pays `expectedEpochInterest` (computed on the pre-deposit TVL), `_updateAccounting`/`_forceUpdateAccounting` folds it into NAV, and `virtualPrice` rises for every outstanding tranche token. The attacker who deposited at time `t < epochEndDate` holds `D / (T + D)` of all tranche tokens and therefore captures that same fraction of the entire epoch's interest — including interest that accrued on other lenders' capital during the `[epochStart, t)` window when the attacker had no funds at risk. In the extreme, depositing at `t → epochEndDate` (just before `stopEpoch`) captures a pro-rata share of nearly a full epoch of interest for zero holding time. This is a classic vault share-inflation/stale-price mint: the broken invariant is fair mint/burn — shares are issued at a stale price that omits already-accrued, borrower-guaranteed yield.

Existing guards do not stop it: `_skimDonatedAssets` only skims raw underlying donations; KYC/whitelist checks only gate *who* may deposit (the attacker is a legitimate KYC-passing lender); `maxApr`, epoch gating and `isEpochRunning` flags are all satisfied because the deposit happens inside a running epoch exactly as the feature intends.

### Impact Explanation
Direct theft of unclaimed yield from existing tranche holders. Quantified: with TVL `T`, epoch interest `I = expectedEpochInterest`, and attacker deposit `D` at time `t`, the attacker extracts `I * (epochEndDate - t)/epochDuration` of "unearned" interest, bounded by `I * D/(T + D)`. With `D ≈ T` and `t` near epoch end, the attacker steals ≈ 50% of the epoch's fixed interest while bearing almost no time-weighted exposure — and can request withdrawal in the next buffer window, making it a repeatable per-epoch drain. Impact scales linearly with `D`, so it is bounded only by attacker capital and any pool `limit`.

### Likelihood Explanation
Requires the non-default configuration `isDepositDuringEpochDisabled = false` (exactly the CVE pattern: safe by default, vulnerable when explicitly enabled — this flag exists and is settable, and the prefunded variant disables the function entirely, showing the path is real in the standard variant). It also requires the honest borrower to keep paying only `expectedEpochInterest`-based interest (i.e., the stop uses the precomputed value or an override that does not retroactively compensate old holders — either way the fixed pie is split pro-rata over the diluted supply). No privileged misbehavior is needed; owner/manager calls (`startEpoch`, `stopEpoch`) are simply sequenced around. The attacker's only requirements are passing KYC and holding capital for a fraction of the epoch.

### Recommendation
When `isDepositDuringEpochDisabled = false`, price mid-epoch mints against NAV plus interest accrued to the deposit timestamp: compute `accrued = _calcInterestWithApr(getContractValue(), scaledApr) * (block.timestamp - epochStart) / epochDuration` and mint tranches at `(lastNAV + accrued) / totalSupply` (or credit the depositor a reduced tranche amount equivalent to `D * supply / (NAV + accrued)`), so new shares cannot claim interest earned before entry. Alternatively keep the path disabled (current default) and document that enabling it is unsafe in fixed-APR mode.

### Proof of Concept
Foundry fork PoC sketch (standard `IdleCDOEpochVariant`, fixed-APR, non-minted mode):

```solidity
function testMidEpochDepositInterestDilution() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);            // epoch #1 buffer, APR 10%

    // Enable the non-default mid-epoch deposit path (honest owner action)
    vm.prank(manager);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);

    // Honest LP deposits all TVL and epoch starts
    address lp = makeAddr("lp");
    _depositWithUser(lp, 100e6);
    vm.prank(manager);
    cdoEpoch.startEpoch();                       // expectedEpochInterest fixed on 100e6

    // Attacker deposits equal TVL just before epoch end
    address attacker = makeAddr("attacker");
    skip(epochDuration - 1 hours);
    deal(address(underlying), attacker, 100e6);
    vm.startPrank(attacker);
    underlying.approve(address(cdoEpoch), 100e6);
    uint256 attackerTranches = cdoEpoch.depositDuringEpoch(100e6, address(tranche));
    vm.stopPrank();

    // Manager stops epoch; borrower pays expectedEpochInterest on the ORIGINAL TVL only
    _stopCurrentEpochWithApr(10e18);

    // Attacker owns ~50% of supply but was in for <1 hour of the epoch;
    // virtualPrice now includes a full epoch of interest.
    uint256 supply = tranche.totalSupply();
    uint256 interestShare = cdoEpoch.lastEpochInterest() * attackerTranches / supply;
    // attacker claims ~half of the full-epoch interest despite ~0 time at risk
    assertGt(interestShare, 100e6 * apr / 100 * (1 hours) / 365 days * 10, "no dilution");
}
```

Expected result: `attackerTranches ≈ supply/2` minted at the stale pre-interest `virtualPrice`, so `interestShare ≈ lastEpochInterest/2` — roughly half of an entire epoch's fixed interest is siphoned from `lp` for ~1 hour of capital exposure. The assertion on `epochPendingClaims`/`virtualPrice` growth confirms the stolen basis. (Uncertain detail: if the deployed `depositDuringEpoch` implementation already adjusts the mint price for accrued interest, the finding is invalid — I was unable to read that function's body within the search budget; the analysis above is based on `mintStrategyTokens` minting 1:1 with no NAV adjustment, contracts/strategies/idle/IdleCreditVault.sol:621-624, and interest being crystallized only at `stopEpoch`.)
