### Title
`block.number`-based reward vesting in `BaseStrategy._lockedTokens` releases harvested yield prematurely on L2s, enabling harvest sandwiching - ([File: contracts/strategies/BaseStrategy.sol](contracts/strategies/BaseStrategy.sol))

### Summary
`BaseStrategy` (and its copies in `ConvexBaseStrategy`, `IdleMStableStrategy`, `IdleTokenFungible` and the Optimism variant) locks harvested rewards for `releaseBlocksPeriod` blocks (default `6400`, ~1 day on mainnet) measured with `block.number` via `latestHarvestBlock`/`_lockedTokens`. On Optimism pre-Bedrock each transaction is its own block and on Arbitrum L2 blocks are produced every ~0.25 s, so the lock can elapse in seconds-to-minutes instead of a day. A KYC'd lender can sandwich `redeemRewards` — deposit through the `IdleCDO` just before the harvest and withdraw right after — and capture yield that the release period was designed to distribute only to existing holders.

### Finding Description
In `contracts/strategies/BaseStrategy.sol`:

- `redeemRewards` stores the harvest block: `latestHarvestBlock = uint128(block.number)` (line 214) and sets `totalTokensLocked = underlyingsStaked` (line 215).
- `_lockedTokens` computes the locked portion as `_totalLockedTokens * (_releaseBlocksPeriod - _blocksSinceLastHarvest) / _releaseBlocksPeriod` where `_blocksSinceLastHarvest = block.number - latestHarvestBlock` (lines 257–266).
- `price()` excludes locked tokens: `(totalTokensStaked - _lockedTokens()) * EXP_SCALE / _totalSupply` (line 253).

The release period is a timing assumption that 6400 blocks ≈ 1 day (Ethereum ~12 s blocks). On Optimism pre-Bedrock every transaction mined its own block, so an attacker could advance `block.number` past `releaseBlocksPeriod` with ~6400 cheap no-op transactions in a single burst — with zero real time elapsed. On Arbitrum, ~4 blocks/second means the full release completes in ~27 minutes rather than 24 hours. Neither chain guarantees `block.number` tracks wall-clock time the way mainnet does; Arbitrum docs explicitly warn that block-number timing is unreliable on short horizons.

The same pattern is duplicated in `contracts/strategies/convex/ConvexBaseStrategy.sol` (5 `block.number` uses) and `contracts/strategies/mstable/IdleMStableStrategy.sol`, and the repo ships an Optimism deployment variant (`contracts/optimism/IdleTokenFungibleOptimism.sol`), so L2 deployment is in scope.

### Impact Explanation
The unlock schedule exists so that freshly harvested rewards are not immediately reflected in `price()` — otherwise anyone could deposit right before a harvest and instantly own a pro-rata share of it. If the lock evaporates almost instantly on L2, an unprivileged KYC'd lender (allowed attacker role) can:

1. Deposit underlying into the `IdleCDO` (receiving AA/BB tranche tokens / strategy shares priced before the harvest).
2. Wait for the keeper/owner to call `redeemRewards` (harvests are publicly scheduled/observable).
3. Pad `block.number` past `releaseBlocksPeriod` (Optimism pre-Bedrock: batch transactions; Arbitrum: wait ~27 min or exploit sync behavior).
4. Withdraw at the now-inflated `price()`, skimming harvested yield that should have vested to long-term holders.

Loss is bounded by the harvest size minus withdrawal fees, but it directly dilutes honest tranche holders on every harvest — repeated theft of yield, qualifying as direct theft of unclaimed/vesting rewards.

### Likelihood Explanation
Requires a strategy using `BaseStrategy`-style reward vesting deployed on an L2 where `block.number` advances faster than mainnet time (Optimism pre-Bedrock: trivially; Arbitrum: ~30 min per harvest) and a harvest of meaningful size. Deposits require passing Keyring KYC, which an attacker can satisfy. No privileged-role collusion is needed; `onlyIdleCDO` is satisfied by going through normal deposit/withdraw flows. Mitigations like `isWalletAllowed` don't prevent a whitelisted user, and there is no timestamp-based fallback or minimum-time check in `_lockedTokens`.

### Recommendation
Measure the release period in `block.timestamp` rather than `block.number` (e.g., `releasePeriod` in seconds, `latestHarvestTimestamp`), identical to the resolution adopted by Tigris Trade for the analogous issue. All copies of the vesting logic (`BaseStrategy`, `ConvexBaseStrategy`, `IdleMStableStrategy`, Optimism/Polygon variants) must be updated consistently.

### Proof of Concept
Foundry fork (Optimism pre-Bedrock or simulated `block.number` acceleration):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "../contracts/strategies/BaseStrategy.sol"; // concrete strategy instance
import "../contracts/IdleCDO.sol";

contract BlockNumberReleasePOC is Test {
    // strategy = concrete BaseStrategy impl on the fork
    // idleCDO  = corresponding IdleCDO
    // attacker = KYC-whitelisted lender address (vm.prank with a passing wallet)

    function testHarvestSandwich() public {
        // 1. Attacker deposits via IdleCDO shortly before scheduled harvest
        //    minting strategy shares at pre-harvest price()
        vm.prank(attacker);
        idleCDO.depositAA(depositAmount); // or depositBB

        // 2. Owner/keeper harvests rewards: redeemRewards sets
        //    latestHarvestBlock = block.number, totalTokensLocked = gain
        vm.prank(idleCDOAddr); // via IdleCDO.harvest path
        strategy.redeemRewards(harvestData);

        uint256 priceAfterHarvest = strategy.price();
        assertLt(priceAfterHarvest, fullPrice); // locked portion excluded

        // 3. On Optimism pre-Bedrock each tx = one block: pad 6400 blocks
        //    in a burst; on Arbitrum simulate fast L2 block production.
        vm.roll(block.number + strategy.releaseBlocksPeriod() + 1);
        // NOTE: on the real L2 this needs ~6400 txs (Optimism) or ~27 min
        // (Arbitrum), NOT ~24h — no block.timestamp advance required.

        // 4. price() now includes fully vested rewards; attacker redeems
        assertEq(strategy.price(), fullPrice);
        vm.prank(attacker);
        idleCDO.withdrawAA(attackerShares); // captures pro-rata harvested yield
    }
}
```

The key assertion: `block.timestamp` barely advances between steps 2 and 4 while `price()` fully reflects the harvest, demonstrating that the `block.number`-based vesting provides no real protection on L2s.
