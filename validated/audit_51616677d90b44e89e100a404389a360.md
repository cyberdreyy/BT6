## Analysis

I found a concrete analog of the reported bug class in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`. The `BlockStatus` struct tracks `total_weight_approved` and `total_weight_rejected` as two independent, monotonically-increasing counters keyed off two disjoint code paths (`BlockResponse::Accepted` and `BlockResponse::Rejected`), with no mechanism to retract a signer's weight from one bucket when that same signer later flips to the other bucket.

### Title
Signer vote flip-flop causes double-counted weight in miner's block tally - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The v0 signer protocol explicitly permits a signer to revise its verdict on a block: `BlockInfo::check_state` allows `LocallyRejected --> LocallyAccepted` transitions ("re-evaluated"), and `should_reevaluate_block`/`should_reevaluate_reject_reason` drive a signer to re-send an acceptance after a prior rejection once the reject reason is no longer applicable. The miner-side `StackerDBListener`, however, tallies `total_weight_approved` and `total_weight_rejected` as independent additive counters that are never reconciled against each other for the same signer slot.

### Finding Description
`StackerDBListener::run` processes `BlockResponse::Rejected` by inserting the slot into `block.responded_signers` and unconditionally adding `signer_entry.weight` to `block.total_weight_rejected`: [1](#0-0) 

Separately, `BlockResponse::Accepted` is gated only on `!block.gathered_signatures.contains_key(&slot_id)` — it does **not** check `responded_signers`, and it does not subtract anything from `total_weight_rejected`: [2](#0-1) 

Because the v0 signer legitimately re-evaluates and can move from `LocallyRejected` to `LocallyAccepted` (as documented and exercised by the state machine and by `should_reevaluate_block`'s pre-commit re-evaluation path), a single signer's weight can end up counted in **both** `total_weight_approved` and `total_weight_rejected` for the same block, with the rejection weight never retracted: [3](#0-2) [4](#0-3) 

This is the same bug class as the `perp_withdraw` report: a state variable (`total_weight_rejected`) that once reflected a signer's live verdict is left stale after that verdict changes, and the caller's decision logic trusts the stale aggregate instead of re-deriving the signer's *current* vote.

The consumer of this state, `SignerCoordinator`, checks the rejection tally **first**: [5](#0-4) [6](#0-5) 

Because `total_weight_rejected` can be inflated by a signer who has since flipped to accept, `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` can become true even when the *current* set of live signer verdicts would actually reach the 70% approval threshold. Since rejection is checked before approval, the miner concludes the block is globally rejected (`SignersRejected`) even though, if only current verdicts were counted, ≥70% weight approves it.

### Impact Explanation
This breaks the "aggregated-weight vs verified-current-accepts" equality: the miner's local tally no longer reflects the true, current set of signer decisions once any signer revises a rejection into an acceptance. The practical effect is a liveness wedge — a legitimately signable block (one that would reach the 70% threshold under current votes) is discarded by the miner as `SignersRejected`, forcing a re-propose/retry cycle and stalling tenure progress. This matches the "wedge the state machine... aggregated-weight vs verified-accepts" class called out as in-scope. It requires no majority of signers and no key compromise — a single signer legitimately changing its vote (a normal, documented, protocol-supported event) is sufficient to corrupt the miner's tally for that block.

### Likelihood Explanation
The re-evaluation path (`LocallyRejected -> LocallyAccepted`) is a normal, expected occurrence — it happens whenever a signer's earlier rejection reason becomes stale/inapplicable and it is re-proposed (`should_reevaluate_reject_reason`, `should_reevaluate_block`) or via a proposal timeout retry. No adversarial signer collusion or majority is needed; a single honest signer flipping its vote (which the protocol is designed to allow) is enough to place stale weight into `total_weight_rejected` that is never cleared, so the corrupted tally can occur under ordinary operating conditions, not just adversarial ones.

### Recommendation
Track each signer slot's current verdict (accept/reject/none) in a single map rather than two independent additive counters. On receiving a new `BlockResponse` for a slot that already has a recorded verdict of the opposite kind, subtract the old weight from the corresponding bucket before adding it to the new one (or recompute both `total_weight_approved`/`total_weight_rejected` from the current per-slot verdict map on each update), so the miner's tally always reflects only the most recent verdict per signer.

### Proof of Concept
1. Miner proposes block B; signer S evaluates B and — due to a stale/incorrect check (e.g., `check_block_against_signer_db_state` momentarily failing, or a reject-reason that is later re-evaluable) — sends `BlockResponse::Rejected`. `StackerDBListener` adds S's weight to `total_weight_rejected` and marks S in `responded_signers`.
2. Total rejected weight across a minority of signers (including S) approaches, but does not yet exceed, the blocking minority (`total_weight - weight_threshold`).
3. S receives a new proposal for the same block (miner re-sends after a timeout) and, per `should_reevaluate_block`/`should_reevaluate_reject_reason`, S determines the reject reason no longer applies and sends `BlockResponse::Accepted` instead.
4. `StackerDBListener`'s `Accepted` branch adds S's weight to `total_weight_approved` — but S's weight is never removed from `total_weight_rejected`.
5. If enough additional signers behave similarly (or already had signed), `total_weight_approved` can reach `weight_threshold` while `total_weight_rejected` (still containing S's stale rejection weight, plus contributions from any other signer who also flipped) simultaneously satisfies `total_weight_rejected + weight_threshold > total_weight`.
6. `wait_for_block_acceptance` in `signer_coordinator.rs` evaluates the rejection branch first and returns `Err(NakamotoNodeError::SignersRejected {...})`, discarding a block that in fact has enough *current* approving weight to be validly signed — a liveness stall caused purely by the double-counted stale rejection weight.

**Note on verification limits:** I was not able to execute an end-to-end test to numerically confirm the exact threshold arithmetic under all rounding/edge cases (e.g., whether `saturating_add` boundary conditions always trigger in every configuration of signer weights), and I could not find an explicit reconciliation step anywhere else in the codebase (I searched `stackerdb_listener.rs` in full and found no decrement/removal logic for `total_weight_rejected` or `total_weight_approved` tied to a slot's prior verdict). This should be validated with a concrete weight distribution/test harness if pursued further.
