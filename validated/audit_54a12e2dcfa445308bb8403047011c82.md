### Title
`getLargestAccounts` cache key omits `commitment`, causing wrong-commitment/stale-slot data to be returned - (File: rpc/src/rpc.rs, rpc/src/rpc_cache.rs)

### Summary
The `LargestAccountsCache` used by the `getLargestAccounts` JSON-RPC method is keyed only by the `filter` (`Circulating`/`NonCirculating`/`None`) and expires purely by wall-clock TTL, never by `commitment` or bank/slot identity. This is the same class of bug as `AbstractRewardMine.setRewardToken`: a state-defining parameter (there, the reward token; here, the requested `commitment` level) can change between calls while a dependent accumulated/cached value (there, `totalDeclaredReward`/padding; here, the cached `(slot, accounts)` snapshot) is not invalidated, producing internally inconsistent results.

### Finding Description
`get_largest_accounts` in [1](#0-0)  resolves a bank using the caller-supplied `commitment` via `self.bank(config.commitment)`, but then checks the cache using only `config.filter`: [2](#0-1) 

```
fn get_cached_largest_accounts(&self, filter: &Option<RpcLargestAccountsFilter>) -> ... {
    ...
    largest_accounts_cache.get_largest_accounts(filter)
}
fn set_cached_largest_accounts(&self, filter: &Option<RpcLargestAccountsFilter>, slot: u64, accounts: &[RpcAccountBalance]) { ... }
```

The underlying cache struct confirms the key is `Option<RpcLargestAccountsFilter>` only, with a duration-based (not slot-based) expiry: [3](#0-2) 

Because `commitment` is not part of the cache key or the freshness check, once an entry is populated for a given `filter` at some commitment level/slot, any subsequent `getLargestAccounts` call with the *same filter* but a *different commitment* (e.g., `processed` vs. `finalized`) within the TTL window will be served the previously cached `(slot, accounts)` pair — computed against a possibly different, older, or even non-rooted bank — instead of being recomputed against the bank selected for the new commitment level.

This mirrors the reported bug: `setRewardToken` changes a defining state variable (the token) yet leaves the accumulated `totalDeclaredReward`/padding stale, creating an inconsistency between the "current" configuration and the cached accumulated state. Here, `commitment` (the defining "which chain state to read" parameter) changes, but the cached accounts/slot snapshot computed for a different commitment/bank is returned unchanged.

### Impact Explanation
An RPC client legitimately switching commitment levels between two ordinary, unprivileged `getLargestAccounts` requests can receive a response whose `slot` and `value` were computed at a different, unrelated bank state (e.g., a `processed` bank instead of the requested `finalized` bank, or vice versa). This is "wrong-slot/fork/account data returned from a query" as defined in the validation criteria: the caller asked for data at commitment X but silently received the cached answer computed at commitment Y, with no error or warning, and the `context.slot` in the response will reflect the stale computation's slot, misleading downstream consumers (e.g., wallets, exchanges) about balances/state as of the slot they actually requested.

### Likelihood Explanation
This requires no adversarial input and no elevated privileges — a normal RPC consumer issuing two back-to-back `getLargestAccounts` calls with different `commitment` values (a common pattern, e.g. checking both `processed` and `finalized` views) within the cache TTL window will trigger the mismatch deterministically. The cache TTL is configured when `JsonRpcRequestProcessor`/`LargestAccountsCache` is constructed in `rpc/src/rpc_service.rs`, and no code path invalidates the cache on commitment changes.

### Recommendation
Include `commitment` (or the resolved bank's slot) as part of the `LargestAccountsCache` key, or bypass the cache entirely when the requested commitment differs from the commitment used to populate the cached entry. At minimum, validate that the cached entry's slot is consistent with the currently rooted/confirmed/processed slot boundary implied by the requested commitment before returning it.

### Proof of Concept
1. Client calls `getLargestAccounts` with `{"commitment": "processed"}`. Server computes accounts against the current processed bank at slot `S1` and populates `largest_accounts_cache` keyed by `filter = None`.
2. Before the cache TTL expires, client calls `getLargestAccounts` with `{"commitment": "finalized"}` and the same (default `None`) filter.
3. `get_largest_accounts` resolves `bank = self.bank(Some(finalized))` (a different, older, rooted bank at slot `S0 < S1`), but `get_cached_largest_accounts(&None)` still returns the entry cached in step 1 (`slot = S1`, computed from the processed bank).
4. The RPC response reports `context.slot = S1` and account balances computed at the processed bank, even though the client explicitly requested `finalized` commitment — the returned data does not correspond to the finalized/rooted chain state the client asked for.

    async fn get_largest_accounts(
        &self,
        config: Option<RpcLargestAccountsConfig>,
    ) -> RpcCustomResult<RpcResponse<Vec<RpcAccountBalance>>> {
        let config = config.unwrap_or_default();
        let bank = self.bank(config.commitment);

        if let Some((slot, accounts)) = self.get_cached_largest_accounts(&config.filter) {
            Ok(RpcResponse {
                context: RpcResponseContext::new(slot),
                value: accounts,
            })
        } else {
            let (addresses, address_filter) = if let Some(filter) = config.clone().filter {
                let non_circulating_supply = self
                    .calculate_non_circulating_supply(&bank)
                    .await
                    .map_err(|e| RpcCustomError::ScanError {
                        message: e.to_string(),
                    })?;
                let addresses = non_circulating_supply.accounts.into_iter().collect();
                let address_filter = match filter {
                    RpcLargestAccountsFilter::Circulating => AccountAddressFilter::Exclude,
                    RpcLargestAccountsFilter::NonCirculating => AccountAddressFilter::Include,
                };
                (addresses, address_filter)
            } else {
                (HashSet::new(), AccountAddressFilter::Exclude)
            };
            let accounts = self
                .runtime
                .spawn_blocking({
                    let bank = Arc::clone(&bank);
                    move || {
                        bank.get_largest_accounts(NUM_LARGEST_ACCOUNTS, &addresses, address_filter)
                    }
                })
                .await
                .expect("Failed to spawn blocking task")
                .map_err(|e| RpcCustomError::ScanError {
                    message: e.to_string(),
                })?
                .into_iter()
                .map(|(address, lamports)| RpcAccountBalance {
                    address: address.to_string(),
                    lamports,
                })
                .collect::<Vec<RpcAccountBalance>>();

            self.set_cached_largest_accounts(&config.filter, bank.slot(), &accounts);
            Ok(new_response(&bank, accounts))
        }
    }

#[derive(Debug, Clone)]
pub struct LargestAccountsCache {
    duration: u64,
    cache: HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>,
}

#[derive(Debug, Clone)]
struct LargestAccountsCacheValue {
    accounts: Vec<RpcAccountBalance>,
    slot: u64,
    cached_time: SystemTime,
}

impl LargestAccountsCache {
    pub(crate) fn new(duration: u64) -> Self {
        Self {
            duration,
            cache: HashMap::new(),
        }
    }

    pub(crate) fn get_largest_accounts(
        &self,
        filter: &Option<RpcLargestAccountsFilter>,
    ) -> Option<(u64, Vec<RpcAccountBalance>)> {
        self.cache.get(filter).and_then(|value| {
            if let Ok(elapsed) = value.cached_time.elapsed()
                && elapsed < Duration::from_secs(self.duration)
            {
                return Some((value.slot, value.accounts.clone()));
            }
            None
        })
    }
