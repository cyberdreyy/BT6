### Title
Dust queued deposit causes division by zero in `processDeposits`, permanently freezing all pending epoch deposits - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The GoBGP panic is a zero-value input (`softwareVersionLen`) that crashes processing of a whole batch of otherwise valid messages. The closest analog is `IdleCDOEpochQueue.processDeposits`, which computes `epochPrice[_epoch] = _pending * ONE_TRANCHE / _trancheMinted` with no guard for `_trancheMinted == 0`. An unprivileged user can enqueue a dust `requestDeposit` that mints zero tranche tokens; the owner/manager call to `processDeposits` then reverts on division by zero for every subsequent attempt, and because the revert happens before `epochPendingDeposits[_epoch]` is cleared, the whole epoch's queued deposits (including honest users' funds) are stuck.

### Finding Description
`requestDeposit` lets any KYC-passing lender queue underlying into `epochPendingDeposits[_epoch]` and `userDepositsEpochs`. During the buffer period the owner/manager calls `processDeposits`, which deposits the aggregated `_pending` amount into the CDO via `depositAA`/`depositBB` and then prices the epoch as `_pending * ONE_TRANCHE / _trancheMinted` [1](#0-0) .

Tranche minting rounds down: for a sufficiently small aggregated deposit (or a tranche price above the deposited underlying amount per unit), `depositAA`/`depositBB` can return `_trancheMinted == 0`. Unlike the prefunded path, which explicitly handles a zero-mint result by falling back to `virtualPrice` (`_prefundedMinted == 0 ? _cdo.virtualPrice(tranche) : ...`) [2](#0-1) , the standard path divides by zero and reverts.

An attacker calls `requestDeposit(1)` (or the smallest amount whose aggregate mint rounds to zero) as the only depositor of an epoch on a fresh/empty tranche side where the implied price makes `_pending * ONE_TRANCHE / _trancheMinted` unreachable. Every subsequent `processDeposits` call reverts at the division, so `epochPendingDeposits[_epoch]` is never reset and `epochPrice[_epoch]` stays 0, which also permanently bricks `claimDepositRequest` for that epoch since it requires `epochPrice[_epoch] != 0` [3](#0-2) .

### Impact Explanation
Any honest user who deposited into the same queue epoch has their underlying locked in the queue: deposits cannot be priced, tranche tokens cannot be claimed, and (absent a per-user deposit cancellation path that refunds before pricing) funds are frozen. If the pool is later paused/deprecated, freezing becomes permanent. Impact class: permanent freezing of queued deposits.

### Likelihood Explanation
Requires a fresh tranche/epoch configuration where a dust aggregate deposit mints zero shares — plausible when a queue side has no existing supply or the virtual price is high relative to `ONE_TRANCHE`, or when the attacker is the sole depositor with a sub-unit amount. No privileged misbehavior is needed; the trigger is a single unprivileged `requestDeposit`. The codebase itself acknowledges the zero-mint case as realistic in the prefunded branch comment ("it's possible that the tranche minting results in 0 shares due to rounding"), confirming the scenario is reachable rather than hypothetical.

Caveat I could not fully verify within the indexed context: if `depositAA`/`depositBB` internally revert when zero shares would be minted (e.g. an `Is0`/`NotAllowed` check in `_mintSharesAtCurrPrice`), the revert still occurs inside `processDeposits` before the pending counters are cleared, so the freeze outcome is unchanged — only the revert type differs.

### Recommendation
Mirror the prefunded fix in `processDeposits`: when `_trancheMinted == 0`, either set `epochPrice[_epoch] = _cdo.virtualPrice(tranche)` and clear `epochPendingDeposits[_epoch]`, or refund users directly (reset `epochPendingDeposits` and return underlying pro-rata via `claimDepositRequest`-style accounting). Additionally enforce a `minDeposit` in `requestDeposit` that guarantees a non-zero mint at current `virtualPrice`.

### Proof of Concept
Foundry fork PoC sketch (queue already wired to `cdoEpoch`/`strategy`, attacker is KYC-passing):

```solidity
// attacker: sole depositor in epoch N with a dust amount
deal(address(underlying), attacker, 1);
vm.startPrank(attacker);
underlying.approve(address(queue), 1);
queue.requestDeposit(1);            // epochPendingDeposits[N] = 1
vm.stopPrank();

// honest manager tries to process the epoch's deposits
vm.prank(manager);
vm.expectRevert();                  // panic: division by zero at _pending * ONE_TRANCHE / _trancheMinted
queue.processDeposits();

// state is stuck: pending not cleared, epochPrice stays 0
assertEq(queue.epochPendingDeposits(strategy.epochNumber()), 1);
assertEq(queue.epochPrice(strategy.epochNumber()), 0);

// any second depositor is bricked too
queue.requestDeposit(1_000e6);      // succeeds but can never be claimed
// processDeposits still reverts; claimDepositRequest reverts on epochPrice == 0
```

Precondition: the aggregated `_pending` must mint zero tranches at the current `virtualPrice` (true for dust deposits on an empty or high-price tranche side), matching the acknowledged zero-mint rounding case handled in `processPrefundedDeposits`.

  function claimDepositRequest(uint256 _epoch) external {
    // Deposits can be claimed only after the epoch has been finalized and priced.
    _checkNotAllowed(
      epochPrice[_epoch] == 0 ||
      epochPendingDeposits[_epoch] != 0 ||
      epochPrefundedDeposits[_epoch] != 0
    );

    uint256 amount = userDepositsEpochs[msg.sender][_epoch];
    if (amount == 0) {
      return;
    }
    // reset user deposit for the epoch
    userDepositsEpochs[msg.sender][_epoch] = 0;
    // transfer tranche tokens to user based on the price of that epoch
    IERC20Detailed(tranche).safeTransfer(msg.sender, amount * ONE_TRANCHE / epochPrice[_epoch]);
