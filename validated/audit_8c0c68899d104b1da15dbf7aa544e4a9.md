### Title
APR0 withdraw request permanently bricks `stopEpoch` once borrower sets a non‑zero APR — all vault funds locked - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report's bug class — *a decrease/exit path locks user funds with no way to release them* — maps onto `IdleCreditVault.requestWithdraw` in APR0 mode. A withdraw request made while `unscaledApr == 0` moves the user's principal into the `apr0Users`/`apr0TotalPrincipal` bucket instead of the normal `withdrawsRequests` path. At epoch end, `prepareStopEpochWithApr0` unconditionally reverts `NotAllowed` whenever `apr0TotalPrincipal != 0 && unscaledApr != 0`. Because nothing else clears `apr0TotalPrincipal` and the borrower legitimately changes APR over time, a single unprivileged APR0 withdraw request can permanently prevent `stopEpoch` from executing, freezing every lender's funds in the vault.

### Finding Description
In `IdleCreditVault.requestWithdraw`, when `unscaledApr == 0` and the pool is not closed, the request is routed to `_requestWithdrawApr0` rather than `withdrawsRequests`:

```solidity
// IdleCreditVault.sol
if (unscaledApr == 0 && !isClosed) {
  _requestWithdrawApr0(_amount, _user);
} else {
  withdrawsRequests[_user] += _amount;
  withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
}
```

The user's tranche tokens are already burned in `IdleCDOEpochVariant.requestWithdraw` (`_withdrawOps(_amount, principal, _tranche)`), so the funds are "locked" into the APR0 pending bucket — the direct analog of `lockForAnOrder` being invoked on a decrease.

At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which contains a hard guard:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

`apr0TotalPrincipal` is only reset to `0` at the *end* of this same function — i.e., only on the path that does **not** revert. There is no alternative code path (no claim, no admin escape, no epoch transition) that decrements `apr0TotalPrincipal` while `unscaledApr != 0`. `claimWithdrawRequest`/`_settleApr0` only settle user-level `apr0Users` data (`_reqEpoch >= epochNumber` returns early before settlement anyway) and never touch `apr0TotalPrincipal` outside of the default-finalization path in `_clearWithdrawClaimForEpoch`.

So once the borrower raises the APR while an APR0 principal bucket is open, every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts, forever.

### Impact Explanation
- **Permanent freezing of all lender funds.** With `stopEpoch` permanently reverting, the epoch never ends: `epochNumber` never advances, `epochEndDate` never resets, pending withdraw receipts can never be claimed (`epochNumber <= lastWithdrawRequest` guard in `_claimFundedWithdrawRequest` stays true), and deposits/withdrawals tied to the epoch lifecycle are bricked. The attacker loses only their own (already-burned) tranche value; every other lender's entire NAV is locked indefinitely.
- Broken invariants: *solvency of the epoch state machine* (the epoch can never transition out of "running") and *one receipt → one payout* (receipts can never mature).

### Likelihood Explanation
- The attacker is fully unprivileged: any KYC-passing tranche holder can call `IdleCDOEpochVariant.requestWithdraw` during an epoch where `unscaledApr == 0` (APR0 mode is a supported deployment mode per the prompt's own mapping).
- The trigger is an *honest* borrower action: changing `unscaledApr` to a non-zero value is a routine operation (e.g., loan renegotiation at epoch rollover). The rules explicitly allow sequencing around honest privileged calls.
- The window is wide: the attacker can even request during epoch N with APR 0 and simply wait — any honest APR increase before the next `stopEpoch` finalizes bricks the pool.

### Recommendation
Make `prepareStopEpochWithApr0` tolerant of an APR change instead of reverting: e.g., settle APR0 principal at a zero (or last-recorded) rate and clear `apr0TotalPrincipal`, or treat the bucket as normal `pendingWithdraws` when `unscaledApr != 0`. Alternatively, forbid mid-lifecycle APR transitions in `setApr`/`updateAPR` while `apr0TotalPrincipal != 0`, or let the APR0 request settle atomically so the bucket cannot outlive the zero-APR epoch.

### Proof of Concept
```solidity
// Foundry fork test sketch — run against a live IdleCreditVault deployment in APR0 mode
function testApr0RequestLocksStopEpoch() public {
  // 1. Epoch running, unscaledApr == 0 (APR0 deployment mode).
  assertEq(vault.unscaledApr(), 0);

  // 2. Unprivileged KYC'd lender requests a withdraw during the APR0 epoch.
  vm.startPrank(LP);
  tranche.approve(address(cdoEpoch), type(uint256).max);
  cdoEpoch.requestWithdraw(1e18, address(tranche)); // burns tranches, fills apr0Users[LP]
  vm.stopPrank();
  assertGt(vault.apr0TotalPrincipal(), 0);

  // 3. Honest borrower updates APR to a non-zero value (normal operation).
  vm.prank(borrower);
  vault.setApr(NEW_APR); // unscaledApr != 0 now

  // 4. Warp to epoch end; every stopEpoch attempt reverts -> funds permanently locked.
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.expectRevert(NotAllowed.selector);
  cdoEpoch.stopEpoch(0);

  // 5. No recovery path: apr0TotalPrincipal is never cleared, so retries revert forever.
  vm.expectRevert(NotAllowed.selector);
  cdoEpoch.stopEpoch(0);
}
```

**Uncertainty note:** I verified the revert in `prepareStopEpochWithApr0` and the APR0 routing in `requestWithdraw` from the indexed code, but I could not fully read `_requestWithdrawApr0` and the `setApr`/orchestrator path within the available iterations. If `setApr` is owner/borrower-gated *and* blocked while `apr0TotalPrincipal != 0`, or if another function clears the bucket, the attack collapses to a self-lock only. The core defect — a permanently reverting `stopEpoch` reachable through a user-controlled bucket — stands on the cited code.
