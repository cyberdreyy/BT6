### Title
Zero-value token balance misreported as absent after storage-proto round-trip - ([File: storage-proto/src/convert.rs])

### Summary
`impl From<generated::TokenBalance> for TransactionTokenBalance` (lines 688-715) reconstructs `ui_amount: Option<f64>` from a raw `f64` protobuf field by testing whether it differs from `0.0` by more than `f64::EPSILON`. Because a legitimate zero balance (`Some(0.0)`) is serialized identically to an absent balance in the paired `From<TransactionTokenBalance> for generated::TokenBalance` (`.unwrap_or_default()` at line 677), a real, present zero balance is silently converted into `None` on the way back out.

### Finding Description
When a `TransactionTokenBalance` with `ui_token_amount.ui_amount == Some(0.0)` (a perfectly valid, meaningful zero balance, as produced by `token_amount_to_ui_amount_v3` in `account-decoder/src/parse_token.rs`, which explicitly returns `Some(0.0)` for a zero-amount, zero-decimals-adjustable token) is converted to the protobuf `generated::TokenBalance` for long-term storage, `value.ui_token_amount.ui_amount.unwrap_or_default()` at [1](#0-0)  collapses both `None` and `Some(0.0)` to the same wire value `0.0`, losing the distinction between "balance is exactly zero" and "balance is unknown/absent."

On the reverse path, `impl From<generated::TokenBalance> for TransactionTokenBalance` reconstructs `ui_amount` using an epsilon comparison against `f64::default()` (`0.0`): [2](#0-1) . Since the stored value is exactly `0.0`, `(0.0 - 0.0).abs() > f64::EPSILON` is `false`, so the code always returns `None` instead of `Some(0.0)`. This means a client that later calls `getTransaction` for an archived (BigTable-backed) transaction whose token balance was truly `0` will receive `ui_amount: null` for `uiTokenAmount`, even though the original balance data explicitly encoded `Some(0.0)`.

This is triggerable by an ordinary unprivileged actor: any user who transfers out their full SPL token balance (leaving `amount: 0`) causes `pre_token_balances`/`post_token_balances` in the transaction metadata to contain `ui_amount: Some(0.0)`. Once that transaction's block ages out of the local blockstore and is served from BigTable long-term storage (`storage-bigtable`/`storage-proto`), a single `getTransaction` RPC call for that transaction will return a `TransactionTokenBalance` with the zero balance silently turned into a null/absent value, misreporting the account's true historical balance.

Regarding the NaN/Infinity portion of the question: NaN cannot realistically arise from the legitimate computation path (`token_amount_to_ui_amount_v3` never divides by zero), so an attacker cannot naturally cause NaN to appear here through the normal client-triggerable flow described in the question (this function operates on internally-computed metadata, not on attacker-supplied raw protobuf bytes). Infinity values (which can legitimately occur for extreme interest-bearing-token calculations) are handled correctly by the epsilon check since `Infinity > f64::EPSILON` is true, so no misreporting occurs for that case.

### Impact Explanation
This is a data-integrity/misreporting bug: a single, unprivileged `getTransaction` (or any path that deserializes `generated::TokenBalance` from stored protobuf) can return an incorrect `ui_amount` (`null` instead of `0`) for historical token balances that were truly zero. It matches the "wrong account data returned" bounty category for RPC responses, scoped to a single low-rate query with no consensus or availability impact.

### Likelihood Explanation
Highly feasible and fully reproducible: any user can create a transaction that zeroes out a token account balance (a completely ordinary token transfer), and once that transaction is archived to long-term (BigTable) storage, every subsequent `getTransaction` query for it will exhibit the bug deterministically. No special privileges, timing races, or malicious protobuf crafting are required — a normal zero balance is enough.

### Recommendation
Do not use a lossy sentinel-value (`0.0` collapsed for both `None` and `Some(0.0)`) round-trip through the protobuf `f64` field. Instead, use `Option<f64>`-preserving wire representation (e.g., protobuf's `optional double`, or a wrapper message / oneof, or a separate boolean "is_none" flag) so that `None` and `Some(0.0)` can be distinguished on deserialization, mirroring how other `Option`-carrying fields elsewhere in the schema are typically handled.

        ui_token_amount: UiTokenAmount {
            ui_amount: Some(0.0), // a real, present zero balance

            ui_amount_string: "0".to_string(),

    let proto: generated::TokenBalance = original.clone().into();
    let roundtripped: TransactionTokenBalance = proto.into();

    // BUG: expected Some(0.0), but the round-trip silently produces None,
    // misreporting a present zero balance as absent.

        roundtripped.ui_token_amount.ui_amount,
        Some(0.0),

Expected (current buggy) result: the assertion fails because `roundtripped.ui_token_amount.ui_amount` is `None`, demonstrating the misreporting described.
