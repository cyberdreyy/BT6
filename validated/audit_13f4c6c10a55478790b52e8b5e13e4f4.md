### Title
Unbounded `name`/`symbol` length in B-20 token creation and updates enables permanent, unbounded-size on-chain metadata (DoS analog to MantisBT CVE-2025-46556) - ([File: crates/common/precompiles/src/b20_factory/logic/v1.rs])

### Summary
MantisBT's flaw was the lack of server-side length validation on user-supplied note text, letting an attacker permanently corrupt an issue's activity stream with a multi-megabyte note that downstream consumers cannot render. Base's B-20 token factory and metadata-update paths have the analogous gap: `name` and `symbol` (and other free-form `String` fields such as `contract_uri`) accepted from an unprivileged token creator or metadata-role holder are stored via the generic keccak256-chunked `String` storage backend with no length cap, then permanently re-served to every RPC consumer via `name()`/`symbol()` view calls and baked into the `B20Created` log.

### Finding Description
`FactoryV1::validate_asset` and `TokenCreateParams::validate_stablecoin` only check `decimals` bounds and stablecoin `currency` format — they impose no length limit on `name` or `symbol`: [1](#0-0) 

`B20StablecoinStorage::initialize` validates only `currency` (non-empty, A–Z) before writing `name`/`symbol` straight to storage: [2](#0-1) 

`B20AssetStorage::initialize` writes `name`/`symbol` with no validation at all: [3](#0-2) 

Post-creation metadata updates (`updateName`/`updateSymbol`, gated only by the `Metadata` role, not by length) have the same gap: [4](#0-3) 

The underlying `String` storage type has no size ceiling: it stores short strings inline and arbitrarily long strings via keccak256-derived chunk slots, accepting any length that fits in calldata: [5](#0-4) 

Existing tests confirm the factory explicitly permits empty strings and impose no upper bound, underscoring that length was never a validated invariant: [6](#0-5) 

### Impact Explanation
A single `createB20` (or `updateName`/`updateSymbol`) transaction from any unprivileged sender can permanently write an oversized `name`/`symbol` string into precompile-backed EVM storage. This string is: (1) re-served on every future `eth_call` to `name()`/`symbol()`, which wallets, block explorers, bridges, and token-list indexers invoke and often do not bound; and (2) permanently embedded in the `B20Created` event log content that every `eth_getLogs`/`eth_getTransactionReceipt` caller for that token must retrieve and decode. Because there is no length cap, a hostile token creator can force every downstream consumer of that token's metadata to repeatedly process an outsized payload — the same class of persistent "corrupt the record so nothing can render it" DoS described in the MantisBT advisory, but here directed at any RPC client or indexing service that queries the token rather than at the Base node process itself.

### Likelihood Explanation
The path is directly reachable by any address that can submit a transaction: deploying a B-20 token via `IB20Factory::createB20` or, for an already-deployed token, holding the `Metadata` role and calling `updateName`/`updateSymbol`. No special privilege beyond normal token-creator/role-holder access is required, and no additional validation blocks an oversized string; the only practical limit is the calldata/tx gas cost, which still allows attacker-chosen strings large enough to be operationally disruptive for naive downstream consumers.

### Recommendation
Add an explicit maximum length check (mirroring the existing `currency` validation pattern) for `name`, `symbol`, and other free-form metadata strings (e.g. `contract_uri`) in `TokenCreateParams::validate_asset`/`validate_stablecoin`, `B20AssetStorage::initialize`, `B20StablecoinStorage::initialize`, and the `update_name`/`update_symbol` logic, rejecting inputs above a reasonable bound (e.g. tens to a couple hundred bytes) with a dedicated revert error.

### Proof of Concept
1. Attacker calls `IB20Factory::createB20` with `B20AssetCreateParams { name: <N-byte string>, symbol: <M-byte string>, ... }`, choosing `N`/`M` as large as the transaction's gas limit allows.
2. `FactoryV1::create_b20` → `validate_asset` (no length check) → `init_asset_token` → `B20AssetStorage::initialize` stores the oversized `name`/`symbol` via the unbounded `String` storage backend.
3. The `B20Created` event is emitted carrying the full oversized `name`/`symbol`.
4. Any subsequent `eth_call` to the token's `name()`/`symbol()`, or any `eth_getLogs`/`eth_getTransactionReceipt` covering the creation transaction, returns the oversized payload to the caller, which most client tooling does not defend against.

    pub fn initialize(&mut self, init: B20StablecoinInit) -> Result<()> {
        if init.currency.is_empty() {
            return Err(BasePrecompileError::revert(IB20Factory::MissingRequiredField {
                field: String::from("currency"),
            }));
        }
        if !init.currency.bytes().all(|b| b.is_ascii_uppercase()) {
            return Err(BasePrecompileError::revert(IB20Factory::InvalidCurrency {
                code: init.currency,
            }));
        }
        self.b20.name.write(init.name)?;
        self.b20.symbol.write(init.symbol)?;
        self.b20.supply_cap.write(init.supply_cap)?;
        self.stablecoin.currency.write(init.currency)
    }

#[inline]
fn store_bytes_like<S: StorageOps>(bytes: &[u8], storage: &mut S, base_slot: U256) -> Result<()> {
    let new_length = bytes.len();
    let new_chunks = if new_length <= 31 { 0 } else { calc_chunks(new_length) };

    if storage.storage_features().dynamic_storage_tail_cleanup_enabled() {
        // Cobalt intentionally charges an old-metadata SLOAD on every bytes-like write so
        // shrinking values can be detected, including when reusing storage written pre-fork.
        storage.ensure_writable()?;
        clear_stale_long_tail(storage, base_slot, new_chunks)?;
    }

    if new_length <= 31 {
        storage.store(base_slot, encode_short_string(bytes))
    } else {
        storage.store(base_slot, encode_long_string_length(new_length))?;
        let slot_start = calc_data_slot(base_slot);

        for i in 0..new_chunks {
            let slot =
                slot_start.checked_add(U256::from(i)).ok_or(BasePrecompileError::SlotOverflow)?;
            let chunk_start = i * 32;
            let chunk_end = (chunk_start + 32).min(new_length);
            let chunk = &bytes[chunk_start..chunk_end];
            let mut chunk_bytes = [0u8; 32];
            chunk_bytes[..chunk.len()].copy_from_slice(chunk);
            storage.store(slot, U256::from_be_bytes(chunk_bytes))?;
        }

        Ok(())
    }
}
