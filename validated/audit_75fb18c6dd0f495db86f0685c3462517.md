### Title
Builder index reuse (`get_index_for_new_builder`) does not account for outstanding, unsettled `BuilderPendingPayment`s, allowing a stale builder payment obligation to be misdirected onto an unrelated new builder - (File: specs/gloas/beacon-chain.md)

### Summary
`get_index_for_new_builder` allows a `BuilderIndex` slot to be reassigned to a brand-new builder as soon as the previous occupant's `balance == 0` and `withdrawable_epoch` has passed. This reuse check only looks at the builder's *current* balance and *settled* pending withdrawals (`get_pending_balance_to_withdraw_for_builder`, used only by `process_builder_exit_request`); it never checks the rotating `state.builder_pending_payments` queue, which can hold an as-yet-unresolved payment obligation referencing that same `builder_index` for up to two epochs. If that obligation later reaches quorum and is converted into a `BuilderPendingWithdrawal`, it is settled purely by `builder_index` (not by pubkey), so the debit lands on whichever builder now occupies that index — potentially an unrelated party who never made the bid.

### Finding Description
Builder payments flow through three data structures, all addressed by `BuilderIndex`:

1. `process_execution_payload_bid` records a `BuilderPendingPayment` (weight starts at 0) keyed by `builder_index` when a builder wins a slot's bid, **without deducting anything from `builder.balance` yet**: [1](#0-0) 

2. Every epoch, `process_builder_pending_payments` only promotes payments whose `weight >= quorum` into `state.builder_pending_withdrawals`; anything below quorum is silently dropped when the two-epoch window rotates: [2](#0-1) 

3. `process_builder_exit_request` — the only gate on a builder exiting — checks `get_pending_balance_to_withdraw_for_builder`, i.e., only *already-settled* withdrawals, not the in-flight `builder_pending_payments` queue that can still resolve into a debit up to two epochs later: [3](#0-2) 

4. Once the builder is exited and fully swept (balance driven to 0, `withdrawable_epoch` in the past), `get_index_for_new_builder` allows the slot to be handed to a brand new builder with a different pubkey: [4](#0-3) 
`process_builder_deposit_request`/`add_builder_to_registry` will then place the new builder's `Builder` record at that exact index: [5](#0-4) 

The explicit spec comment even documents that indices are reused across different pubkeys: [6](#0-5) 

The equality that breaks: a `BuilderPendingWithdrawal.builder_index` is supposed to identify the specific builder that made the bid and thus owes the payment. Because the reuse check in `get_index_for_new_builder` inspects only the *current* balance/withdrawable_epoch snapshot and never cross-references `state.builder_pending_payments` for outstanding obligations tied to that index, a builder can (a) place a winning bid, (b) immediately request exit (passing the `process_builder_exit_request` check, since that in-flight bid is not yet in `builder_pending_withdrawals`), and (c) have its balance fully swept to zero once exit/withdrawable epoch passes — all while the bid's payment obligation is still sitting, unresolved, in the rotating `builder_pending_payments` queue. If attester weight later reaches quorum, the payment is converted to a `BuilderPendingWithdrawal` keyed by that same, now-reused, `builder_index`. When `process_withdrawals` eventually dequeues and applies it, the debit is taken from `state.builders[builder_index].balance` of whichever new builder now occupies that slot — a party that never signed or authorized the original bid.

### Impact Explanation
This is a Gwei-misdirection bug: a payment obligation created by builder A's bid is settled by decrementing builder B's balance (B having deposited into the same, reused index later) and the corresponding amount is paid out to A's chosen `fee_recipient`. This is "a builder payment or withdrawal misdirected... escaped" from A's perspective (A exits without ever paying) and Gwei taken from a non-owner (B) — matching the High/Critical impact categories (Gwei paid to a non-owner / builder payment misdirected without authority).

### Likelihood Explanation
The attacking builder (A) is fully in control of steps (a)-(c): submitting its own winning bid and requesting its own exit are unprivileged, single-actor operations requiring no coalition, malicious peer, or client bug. The only external dependency is that PTC/attester weight for the bid crosses quorum after A has already exited and been swept — plausible given the two-epoch settlement window and the fact that quorum is driven by honest attesters reporting payload availability, independent of A's own continued participation. The reused index being claimed by an unrelated depositor before the stale withdrawal is dequeued is also plausible, since `builder_pending_withdrawals` is processed at limited throughput per slot (as seen in withdrawal-priority ordering tests), while a slot can be reused as soon as the balance is zero.

### Recommendation
Before allowing `get_index_for_new_builder` to reuse a slot (or before allowing `process_builder_exit_request` to succeed), also verify there is no outstanding, unresolved `BuilderPendingPayment` referencing that `builder_index` in `state.builder_pending_payments` — not just the already-settled `builder_pending_withdrawals`. Alternatively, reserve/lock the pending payment amount against the builder's balance immediately when the bid is accepted (mirroring how validators track `get_pending_balance_to_withdraw`), so a full-balance sweep cannot zero out funds that are already earmarked for a pending obligation, and so the slot cannot be marked reusable while any obligation for it remains outstanding.

### Proof of Concept
1. Builder A registers via `process_builder_deposit_request`, gets `builder_index = i`.
2. A submits a winning `ExecutionPayloadBid` for slot `S` with `value = V`, `fee_recipient = A_ADDR`. `process_execution_payload_bid` records a `BuilderPendingPayment(builder_index=i, amount=V, weight=0)` — A's balance is untouched (per `test_process_execution_payload_bid_sufficient_balance_with_pending_payments`).
3. Immediately after, A submits a `BuilderExitRequest`. `process_builder_exit_request` calls `get_pending_balance_to_withdraw_for_builder(state, i)`, which is 0 (the bid payment hasn't reached quorum/settled yet), so the exit succeeds — [7](#0-6) .
4. A's remaining balance is fully swept via `process_withdrawals` once `withdrawable_epoch` passes; `state.builders[i].balance == 0`.
5. In the epoch-processing window, attesters push the pending payment's weight to quorum; `process_builder_pending_payments` converts it into `state.builder_pending_withdrawals.append(BuilderPendingWithdrawal(builder_index=i, amount=V, fee_recipient=A_ADDR))` — [8](#0-7) .
6. Meanwhile, `get_index_for_new_builder` sees `builders[i].balance == 0` and `withdrawable_epoch <= current_epoch`, so a new, unrelated builder B deposits and is assigned the same index `i` via `add_builder_to_registry` — [9](#0-8) .
7. When `process_withdrawals` later dequeues the withdrawal from step 5, it decrements `state.builders[i].balance` (now B's balance) by `V` and pays `V` to `A_ADDR` — B loses `V` Gwei for a bid B never made.

Note: this chain depends on precise timing (exit + sweep completing before the pending payment resolves, and a new depositor claiming the slot before the stale withdrawal is dequeued). I was not able to retrieve the exact definition of `get_pending_balance_to_withdraw_for_builder` or the full-withdrawal sweep routine in this pass to confirm there is no additional implicit reservation of `V` against A's balance before the sweep; if such a reservation exists elsewhere in the spec, it would close this gap and should be verified directly in `specs/gloas/beacon-chain.md`.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

###### New `get_index_for_new_builder`

```python
def get_index_for_new_builder(state: BeaconState) -> BuilderIndex:
    for index, builder in enumerate(state.builders):
        if builder.withdrawable_epoch <= get_current_epoch(state) and builder.balance == 0:
            return BuilderIndex(index)
    return BuilderIndex(len(state.builders))

###### New `process_builder_deposit_request`

*Note*: Builder indices are reusable. When a builder exits, its index may later
be reassigned to a different builder with a new public key. Any deposit sent to
an exited builder will be withdrawn to the builder’s execution address. Exited
builders cannot be reactivated, although a newly registered builder’s public key
may have previously appeared in the builder set. Implementations that rely on
caching should account for this behavior.

```python
def process_builder_deposit_request(state: BeaconState, request: BuilderDepositRequest) -> None:
    # Ignore deposits with unexpected withdrawal credential prefixes
    if not is_builder_withdrawal_credential(request.withdrawal_credentials):
        return

    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        if is_valid_builder_deposit_signature(request):
            add_builder_to_registry(
                state,
                request.pubkey,
                PAYLOAD_BUILDER_VERSION,
                ExecutionAddress(request.withdrawal_credentials[12:]),
                request.amount,
                state.slot,
            )
    else:
        builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
        builder = state.builders[builder_index]

        # If exited and swept, reset the withdrawable epoch
        if builder.withdrawable_epoch != FAR_FUTURE_EPOCH and builder.balance == 0:
            epoch = get_current_epoch(state)
            builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY

        # Increase balance by deposit amount
        builder.balance += request.amount

def process_builder_exit_request(state: BeaconState, request: BuilderExitRequest) -> None:
    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        return

    builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
    builder = state.builders[builder_index]

    if not is_active_builder(state, builder_index):
        return
    if builder.execution_address != request.source_address:
        return
    if get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0:
        return

    initiate_builder_exit(state, builder_index)
