### Title
Symlink target is never validated before `os.Open` in `raw` archiver, allowing unprivileged job authors to exfiltrate files outside `c.wd` - (File: `commands/helpers/archive/raw/raw_archiver.go`)

### Summary
`fileArchiver.process`/`findRelativePathInProject` in `commands/helpers/file_archiver.go` only validate the *literal* path string of a matched directory entry against `c.wd`; they use `os.Lstat` (not `os.Stat`) in `add()` so a symlink is registered by its own location, never by where it points. `raw.archiver.Archive` in `commands/helpers/archive/raw/raw_archiver.go` then calls `os.Open(pathname)` on that key, and `os.Open` follows the symlink at the OS level, reading whatever file the symlink target points to, with no re-check that the target stays inside `c.wd`.

### Finding Description
- `fileArchiver.processPath` (`commands/helpers/file_archiver.go:146-189`) globs `--path` patterns with `doublestar.WithNoFollow()` and walks each match with `filepath.Walk`, calling `process(path)` for every visited entry.
- `process()` (`commands/helpers/file_archiver.go:65-101`) computes `absolute = filepath.Abs(match)` and `relative = filepath.Rel(c.wd, absolute)`. `filepath.Abs`/`filepath.Rel` are purely lexical string operations — they do **not** resolve symlinks. So if `match` is `subdir/link` and `link` is a symlink pointing to `/etc/passwd` or another project's build directory, `relative` is simply `subdir/link`; it never contains `..` and the containment check at line 77 passes.
- `add()` (`commands/helpers/file_archiver.go:127-138`) calls `os.Lstat(path)`, which returns info about the symlink itself (mode bit `os.ModeSymlink`), not the target. This is why the check never even notices a boundary crossing — the entry stored in `c.files["subdir/link"]` is syntactically valid and inside `c.wd`.
- `raw.archiver.Archive` (`commands/helpers/archive/raw/raw_archiver.go:35-51`) later iterates `files` and does `f, err := os.Open(pathname)`. `os.Open` is symlink-following by default at the OS level: the kernel resolves `subdir/link` to its target and returns that file's content, regardless of where the target actually resides. There is no `Lstat`/`ModeSymlink` check, no `filepath.EvalSymlinks` + containment re-verification, and no refusal to follow symlinks in this archiver, unlike `tarzstd.archiver.Archive` which at least detects `fi.Mode()&os.ModeSymlink != 0` and stores a symlink header via `os.Readlink` instead of reading file content (`commands/helpers/archive/tarzstd/tarzstd_archiver.go:86-91,106-108`).
- Net effect: the documented invariant in `archive.NewArchiver` ("the archiver will ensure that files to be archived are children of the directory provided") is violated for the `raw` format specifically, because the boundary check is applied to the *path string of the symlink* and never to its *resolved target*.

Note: the exact mechanism differs slightly from the question's framing — `c.files` never actually contains an absolute/out-of-`wd` string; the escape happens purely at `os.Open()` time when the kernel follows the on-disk symlink. The scoped impact (unauthorized file read exfiltrated via the archive stream) is nonetheless real and reachable through this exact code path.

### Impact Explanation
A job author who can create a symlink inside the checked-out workspace (e.g., via a script step, a repository-committed symlink, or an untracked file combined with `--untracked`) and reference it via `--path`/artifacts `paths:` can cause the `raw` archiver to read and stream the contents of an arbitrary file reachable by the runner/helper process (host secrets, other files on the shared filesystem, or another job's directory on a shared runner) into the artifact/cache upload body. This is a file-read/exfiltration primitive scoped to whatever the runner process/container user can read, not a sandbox escape by itself.

### Likelihood Explanation
Preconditions are cheap for an unprivileged pipeline author: create a symlink in the job workspace (trivial via `ln -s` in a `script:` step before the artifact/cache upload stage) pointing at a target reachable from the runner's filesystem view, then configure a single-path artifact/cache entry that resolves to that symlink so the `raw` format's one-file constraint is satisfied. This is easily reproducible in CI and deterministic (no race/TOCTOU needed, since Lstat/glob's `WithNoFollow` never inspect the target, so there's no window to close between check and open).

### Recommendation
In `fileArchiver.process`/`add`, detect `info.Mode()&os.ModeSymlink != 0` from the `Lstat` result and either (a) resolve the symlink with `filepath.EvalSymlinks` and re-run the `c.wd` containment check against the resolved target before accepting the entry, or (b) reject/skip symlinks entirely for archivers that don't have explicit, safe symlink semantics (as `tarzstd` does by storing a link record instead of following it). Additionally, `raw.archiver.Archive` should use `os.Lstat` + reject `ModeSymlink` (or use `os.OpenFile` with `O_NOFOLLOW` where supported) before calling `os.Open`, rather than relying solely on upstream path checks that don't account for symlink targets.

### Proof of Concept
Go test (place in `commands/helpers/file_archiver_test.go` or a new test file):
```go
func TestFileArchiver_SymlinkEscapesWorkdir(t *testing.T) {
    wd := t.TempDir()
    outside := t.TempDir()
    secret := filepath.Join(outside, "secret.txt")
    require.NoError(t, os.WriteFile(secret, []byte("TOP-SECRET"), 0o600))

    require.NoError(t, os.Symlink(secret, filepath.Join(wd, "link")))

    chdir(t, wd) // helper to os.Chdir(wd) and restore afterward

    c := &fileArchiver{Paths: []string{"link"}}
    require.NoError(t, c.enumerate())

    // Assert the archiver still queued the symlink under a within-wd key
    info, ok := c.files["link"]
    require.True(t, ok)
    require.True(t, info.Mode()&os.ModeSymlink != 0)

    // Now feed c.files into the raw archiver and show it reads the OUTSIDE file
    var buf bytes.Buffer
    a, err := raw.NewArchiver(&buf, wd, archive.DefaultCompression)
    require.NoError(t, err)
    require.NoError(t, a.Archive(context.Background(), c.files))

    // BUG: content read is from outside c.wd
    require.Equal(t, "TOP-SECRET", buf.String())
}
```
Expected (buggy) result: the test passes, proving `raw.archiver.Archive` reads and streams `outside/secret.txt` content even though `secret.txt` is outside `wd`. After applying the recommended fix (symlink-target containment check or `ModeSymlink` rejection), the test should fail to produce the secret content (either `enumerate()` excludes the entry, or `Archive` returns an error).
