### Title
View-role sessions can bulk-harvest bridge OutgoingToken credentials via unrestricted GET /v2/bridge_types - ([File: core/web/bridge_types_controller.go])

### Summary
`GET /v2/bridge_types` is wrapped only with `paginatedRequest(bt.Index)` and no `auth.RequiresEditRole`/`RequiresAdminRole` wrapper, so any authenticated user of any role — including `view` — can call it. `Index` builds a `presenters.BridgeResource` for every bridge via `presenters.NewBridgeResource`, which unconditionally sets `OutgoingToken` from `bridges.BridgeType.OutgoingToken` with no redaction, allowing a single paginated request to dump every configured bridge's name, URL, and outgoing token.

### Finding Description
The route registration shows no role gate on the bridge listing endpoint: [1](#0-0) 

`BridgeTypesController.Index` fetches all bridges for the page and converts each into a `BridgeResource`: [2](#0-1) 

`presenters.NewBridgeResource` copies `OutgoingToken` directly into the JSON-serializable resource with no role check or redaction, and the field lacks `omitempty`/masking: [3](#0-2) 

`OutgoingToken` is the credential the node sends to the external bridge adapter (`X-Bridge-Access-Key`-style secret), the analogous credential to what `Create` explicitly asserts must be non-empty in `TestBridgeTypesController_Create_Success`: [4](#0-3) 

`Show` (`GET /v2/bridge_types/:BridgeName`) is also unwrapped and exposes the same `OutgoingToken` field for one bridge at a time: [5](#0-4) 

Because `authv2` middleware only requires *any* authenticated user (session or token) via `auth.Authenticate`, and `Index`/`Show` add no `RequiresEditRole`/`RequiresAdminRole`/`RequiresRunRole` wrapper, a `view`-role session (the lowest privilege level defined in `UserRoleView`) passes straight through to the handler: [6](#0-5) [7](#0-6) 

Both `Index` and `Show` apply identical (lack of) redaction — the "invariant" holds in the sense that there is no double standard between them — but `Index` is strictly worse for an attacker because it does not require prior knowledge of bridge names: a single `GET /v2/bridge_types?size=1000` call enumerates every bridge's name, URL, and `OutgoingToken` in one response, whereas `Show` requires the caller to already know each bridge name to retrieve one credential at a time.

### Impact Explanation
This is bridge outgoing-token disclosure: a low-privilege (`view`-role) authenticated user or restricted API-token holder can retrieve every configured bridge's `URL` and `OutgoingToken` in a single bulk request, without needing edit/admin privileges or prior knowledge of bridge names. This maps to a credential/secret disclosure impact — the harvested `OutgoingToken` values can be used to impersonate the node when calling external bridge adapters or to probe/attack those adapters directly, and the harvested `URL`s reveal internal adapter infrastructure topology.

### Likelihood Explanation
Preconditions are minimal: only an authenticated session or API token of any role (including `view`) is required — no edit/admin/run role, no special network position, no misconfiguration. The request is a single unauthenticated-in-role GET call (`GET /v2/bridge_types?size=1000`), fully repeatable and requires no timing/race conditions. This is a straightforward, deterministic exploit path reachable by the lowest-privileged legitimate account type in the system.

### Recommendation
Add a role gate (at minimum `auth.RequiresEditRole`, matching the gate already applied to `Create`/`Update`/`Destroy`) to both `GET /v2/bridge_types` (`Index`) and `GET /v2/bridge_types/:BridgeName` (`Show`), or strip `OutgoingToken` from `BridgeResource` for callers below `edit` role. Since `Create` treats `IncomingToken` as sensitive-and-shown-once (`bta.IncomingToken` only returned on `Create`, `omitempty` tag), `OutgoingToken` should receive equivalent treatment — never returned to `view`/`run`-role sessions in `Index` or `Show`, consistent with the redaction already used for `IncomingToken`.

### Proof of Concept
1. Go handler-level integration test in `core/web/bridge_types_controller_test.go`:
   - Create an application (`cltest.NewApplication`), create two `bridges.BridgeType` records with distinct `OutgoingToken` values via `app.BridgeORM().CreateBridgeType`.
   - Create a user session/API token with `sessions.UserRoleView` (using existing test helpers for view-role sessions, mirroring patterns in `core/web/auth/auth_test.go`).
   - Issue `client.Get("/v2/bridge_types?size=1000")` using the view-role-scoped client.
   - Assert response status `200 OK` and parse the paginated `presenters.BridgeResource` list; assert `resources[i].OutgoingToken` is non-empty and equals the seeded token for each bridge — demonstrating credential leakage to a `view`-role principal.
2. Presenter-level unit test in `core/web/presenters/bridges_test.go`:
   - Extend `TestBridgeResource` (or add a new test) to assert that `NewBridgeResource` always populates `OutgoingToken` regardless of any caller-role parameter (there currently is none), proving the presenter itself has no role-awareness/redaction logic — the root cause enabling both `Index` and `Show` to leak the secret to any authenticated caller.

// Index lists Bridges, one page at a time.
func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
