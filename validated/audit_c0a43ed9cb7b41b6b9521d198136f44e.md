### Title
Deleveraging withdrawal cap bypassed via zero price when account is in deleverage but not receivership - ([File: programs/marginfi/src/instructions/solend/withdraw.rs])

### Summary
In `solend_withdraw`, the price used for both rate limiting and deleverage-cap accounting is only fetched from the oracle when `in_receivership || group_rate_limit_enabled`; otherwise `price` is hardcoded to `I80F48::ZERO`. Since the deleverage cap check at line 142-149 only depends on `ACCOUNT_IN_DELEVERAGE` (not on `group_rate_limit_enabled`), an account flagged `ACCOUNT_IN_DELEVERAGE` but not `ACCOUNT_IN_RECEIVERSHIP`, withdrawing while the group rate limiter is disabled, gets `withdrawn_equity = calc_value(collateral_amount, ZERO, ...) = 0`, trivially satisfying `check_deleverage_withdraw_limit` regardless of the amount withdrawn.

### Finding Description
The code path is: [1](#0-0) 
which computes `in_receivership` strictly from `ACCOUNT_IN_RECEIVERSHIP`, and only fetches a real oracle price when `in_receivership || group_rate_limit_enabled` is true; otherwise `price` is forced to zero with no restriction tied to `ACCOUNT_IN_DELEVERAGE`.

The deleverage accounting block then unconditionally uses this `price`: [2](#0-1) 
`calc_value(collateral_amount, price=0, ...)` returns 0, so `withdrawn_equity` is 0 no matter how large `collateral_amount` is, and `group.check_deleverage_withdraw_limit(0, ...)` (in `programs/marginfi/src/state/marginfi_group.rs` lines 236-256) always passes since `projected <= daily_limit` trivially holds for a zero addition.

Authorization for the call is via `is_signer_authorized`, wired in the account constraints: [3](#0-2) 
This allows the normal account authority (not just a receiver/liquidator) to call `solend_withdraw` as long as the account isn't disabled or frozen — there is no additional restriction requiring `group_rate_limit_enabled` be on, nor does the deleverage flag itself force a non-zero price. Thus, once risk_admin sets `ACCOUNT_IN_DELEVERAGE` on an account (via `start_deleverage`) without the account also being in receivership, and if the group's rate limiter happens to be disabled (`group.rate_limiter.is_enabled() == false`), the normal authority can call `solend_withdraw` with a large `amount` (or `withdraw_all = true`), and the accounted `outflow_usd` in `DeleverageWithdrawFlowEvent` and the daily-limit tracker will register 0 regardless of the true USD value withdrawn.

### Impact Explanation
This defeats the deleverage daily-withdrawal-limit circuit breaker that risk_admin relies on to bound outflow from an account undergoing risk-admin-initiated deleveraging. An account holder can drain their full collateral position through Solend withdrawals while the group's on-chain accounting records zero outflow, allowing them to bypass `DailyWithdrawalLimitExceeded` and undermine the deleverage safety mechanism. This is a state-integrity/value-accounting bug (`NO_VALUE_REDIRECTION` invariant violation) reachable by an unprivileged authority under normal instruction access, not requiring any admin/oracle-operator control to trigger the exploit path itself (only the pre-existing state where risk_admin has started deleverage and the rate limiter is off).

### Likelihood Explanation
Requires: (1) risk_admin has flagged the account `ACCOUNT_IN_DELEVERAGE` without concurrent `ACCOUNT_IN_RECEIVERSHIP`, and (2) `group.rate_limiter.is_enabled()` is false at the time of the call. Both are plausible operational states — the rate limiter can be legitimately disabled (e.g., not configured, or intentionally turned off), and `start_deleverage` does not appear to force `ACCOUNT_IN_RECEIVERSHIP` to also be set. Given these preconditions, the exploit itself is trivial and fully repeatable — the unprivileged authority simply calls `solend_withdraw` with `withdraw_all = true` and omits `remaining_accounts` oracle references, exactly as the code allows since price isn't even fetched in this branch.

### Recommendation
Fetch a real oracle price (and validate it as non-zero) whenever `ACCOUNT_IN_DELEVERAGE` is set, in addition to `in_receivership || group_rate_limit_enabled`. That is, change the price-fetch condition at line 94 to also include `marginfi_account.get_flag(ACCOUNT_IN_DELEVERAGE)`, and enforce `check!(price > I80F48::ZERO, ...)` for the deleverage case too, so `withdrawn_equity` reflects true USD value regardless of the rate limiter's on/off state. Apply the same fix to the equivalent code in `programs/marginfi/src/instructions/juplend/withdraw.rs`, `programs/marginfi/src/instructions/kamino/withdraw.rs`, `programs/marginfi/src/instructions/drift/withdraw.rs`, and `programs/marginfi/src/instructions/marginfi_account/withdraw.rs`, which share the identical `in_receivership || group_rate_limit_enabled` pattern.

### Proof of Concept
Rust unit test (in `programs/marginfi/tests` harness or a targeted unit test around `solend_withdraw`):
1. Set up a group with `rate_limiter` disabled (`group.rate_limiter.is_enabled() == false`, e.g., unconfigured/default).
2. Create a marginfi account with a Solend collateral balance, set `ACCOUNT_IN_DELEVERAGE` flag via the equivalent of `start_deleverage`, and ensure `ACCOUNT_IN_RECEIVERSHIP` is NOT set.
3. Set `group.deleverage_withdraw_window_cache.daily_limit` to a small non-zero value (e.g., 100).
4. As the normal account authority (not risk_admin), call `solend_withdraw` with `withdraw_all = true` for a `collateral_amount` whose true USD value vastly exceeds the daily limit; omit `remaining_accounts` oracle account.
5. Assert: the call succeeds without error (`check_deleverage_withdraw_limit` does not return `DailyWithdrawalLimitExceeded`), and that the emitted `DeleverageWithdrawFlowEvent.outflow_usd == 0` despite the large `collateral_amount`.
6. Assert: `group.deleverage_withdraw_window_cache.withdrawn_today` remains 0 or unchanged after the call, confirming the daily cap tracker never observed the true withdrawn value.
