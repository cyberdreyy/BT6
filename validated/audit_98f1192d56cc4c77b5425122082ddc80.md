### Title
Node-side signer weight double-counting after a reject→accept flip allows a single signer to wedge the block-acceptance/rejection decision - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tallies `BlockStatus.total_weight_approved` and `BlockStatus.total_weight_rejected` using two independently-gated boolean checks instead of a single authoritative "current vote" set. A signer that first rejects a block and later accepts the same `signer_signature_hash` has its weight added to `total_weight_rejected` *and* (again) to `total_weight_approved`, because the "already counted" guard for acceptances only checks `gathered_signatures`, not the shared `responded_signers` set that the rejection path already populated. This is the same class of bug as the Rack advisory: one code path (`check_query_string`'s `&`-only count) enforces a limit using criteria that don't match the actual authoritative parsing (`[&;]` split), letting the real state diverge from what's counted.

### Finding Description
`BlockStatus` tracks: [1](#0-0) 

On `Accepted`, the increment is gated only by `gathered_signatures.contains_key(&slot_id)`: [2](#0-1) 

On `Rejected`, the increment is gated by `responded_signers.insert(slot_id)`, and the accepted branch also inserts into that same `responded_signers` set (line 465) even though it does not consult it when deciding whether to add weight: [3](#0-2) 

Because the two branches use different membership sets to decide "have we already counted this signer's weight," the sequence Reject → Accept from the same signer for the same `signer_signature_hash` causes:
- Reject: `responded_signers.insert(slot_id)` succeeds → `total_weight_rejected += weight`.
- Accept (later, same slot/hash): `gathered_signatures.contains_key(&slot_id)` is still `false` (never touched by the reject branch) → `total_weight_approved += weight` as well.

The signer's weight is now counted in *both* pools; the reject weight is never retracted. The stacks-signer side legitimately allows a signer to change its verdict on the very same block hash after re-evaluation (`should_reevaluate_block` / `should_reevaluate_reject_reason`), so this reject→accept flip for one unchanged `signer_signature_hash` is a normal, reachable flow, not a contrived edge case: [4](#0-3) 

The coordinator consumes these two counters to decide the miner's next action, checking rejection first: [5](#0-4) 

Because `total_weight_rejected` can retain stale weight from a signer who has since switched to acceptance, the aggregated rejection weight no longer reflects the verified/current set of votes ("aggregated-weight vs verified-accepts"). Since the reject branch is evaluated before the accept branch, a block that has genuinely reached the 70% acceptance threshold can still be misreported as having crossed the blocking->30% rejection threshold using stale, already-superseded weight, causing the coordinator to return `SignersRejected` for a block that current signer weight actually supports.

### Impact Explanation
This lets a single non-majority signer (one whose vote transiently flips from reject to accept on the same block hash — a state transition the signer protocol explicitly supports) corrupt the node-side weight tally so that `total_weight_rejected` and `total_weight_approved` no longer partition the total signer weight. Depending on timing, this can cause the miner/coordinator to treat a legitimately-approvable block as globally rejected (excluding transactions, restarting mining), i.e. a liveness wedge on the block-acceptance decision that requires no majority collusion, matching the "liveness wedge" impact class in scope.

### Likelihood Explanation
No malicious majority is required — a single signer that rejects a proposal and later accepts a re-proposal of the identical `signer_signature_hash` (a normal re-evaluation flow already exercised in the codebase's own sibling/re-proposal tests) is sufficient to trigger the double count. This only requires ordinary gossip timing (a rejection response arriving before an acceptance response for the same block).

### Recommendation
Gate the `Accepted` branch's weight increment on the same authoritative membership set used for `Rejected` (e.g., check-and-set `responded_signers` once per slot for the *whole* `BlockStatus`, or otherwise ensure a signer's weight is retracted from whichever pool it was previously counted in before being added to the other) so that `total_weight_approved + total_weight_rejected` can never exceed `total_weight` and a signer's weight is always reflected under its current vote only.

### Proof of Concept
1. Node begins collecting responses for `block_sighash` with `weight_threshold` set to 70% of `total_weight`.
2. Signer S (slot `k`, weight `w`) sends `BlockResponse::Rejected` for `block_sighash`: `responded_signers.insert(k)` succeeds → `total_weight_rejected += w`.
3. S's local signer re-evaluates the same proposal (e.g. after `should_reevaluate_reject_reason` allows reconsideration) and later sends `BlockResponse::Accepted` for the identical `block_sighash`.
4. In the accepted-branch handling, `block.gathered_signatures.contains_key(&k)` is `false` (untouched by step 2) → `total_weight_approved += w` is executed, and `block.responded_signers.insert(k)` (already present) is a no-op.
5. Now `total_weight_rejected` still includes `w` from step 2, and `total_weight_approved` also includes `w` from step 4 — `w` is double counted across the two mutually-exclusive tallies, so `total_weight_approved + total_weight_rejected` can exceed `total_weight`, and the stale rejection weight can trip the `SignersRejected` branch in `signer_coordinator.rs` even though current signer weight supports acceptance.
