## Title
Legacy v1 signer's `DuplicateBlockFound` check misses locally-accepted (signed) blocks, permitting a competing tenure-start proposal to be validated and re-signed - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
`SortitionState::validate_tenure_change_payload` in the v1 chainstate module rejects a duplicate tenure-change proposal by checking `SignerDb::get_last_globally_accepted_block`, which only sees blocks that have already reached the network-wide 70% signature threshold. A block the signer itself already locally accepted (i.e., already signed, via `mark_locally_accepted`) but that has not yet gathered global acceptance is invisible to this check.

### Finding Description
This is the exact bug class from the external report: a value computed under one context (globally-accepted state) is compared against a question that actually needs a different context (has this signer already signed something in this tenure). In `stacks-signer/src/chainstate/v1.rs`, `validate_tenure_change_payload` does: [1](#0-0) 

This uses `get_last_globally_accepted_block`, whose doc comment on `SignerDb` explicitly says it only returns blocks that reached `GloballyAccepted` state, unlike `get_last_signed_block`, which also includes `LocallyAccepted` blocks: [2](#0-1) 

`stacks-signer/src/chainstate/v2.rs`'s equivalent function was fixed to use `get_last_signed_block` instead, precisely to close this gap, and a regression test documents the exact incorrect-pass scenario that this fix addresses: [3](#0-2) [4](#0-3) 

The project's own internal documentation calls this out directly as a known v1/v2 divergence, confirming v1 was never patched: [5](#0-4) 

The `DuplicateBlockFound` check runs only once, at proposal arrival inside `check_proposal`; it is never re-evaluated later in the block's lifecycle (pre-commit, or at signing time): [6](#0-5) 

## Explored but inconclusive
I traced the full downstream consequence and it is likely (but I could not fully confirm within the remaining iterations) that the pre-commit-stage guard in `stacks-signer/src/v0/signer.rs::handle_block_pre_commit`, which queries `SignerDb::get_signed_conflicts` by Stacks height across *all* tenures, independently catches a same-height sibling and would refuse to place a second signature even if the proposal-time `DuplicateBlockFound` check is bypassed: [7](#0-6) [8](#0-7) 

If that guard indeed always fires for a same-height competing tenure-change block, then the v1 `DuplicateBlockFound` gap is redundant/cosmetic rather than a standalone double-sign vector, and the impact would be limited to: (a) an invalid proposal being unnecessarily submitted to the stacks-node for validation (wasted validation round-trip / minor liveness cost), and (b) inconsistent rejection reasons/telemetry between v1 and v2 signers. I was not able to fully verify, given the available context, whether there exists any edge case (e.g., timing where the local acceptance record has not yet reached `signed_self`/`signed_group`, or a race between `check_proposal` and `get_signed_conflicts` before `add_block_pre_commit`) where the section-5 guard's height-based lookup would fail to catch the sibling for a v1-configured signer, which would be needed to elevate this to a true "signer signs a conflicting block" (Critical) finding rather than a lesser inconsistency.

### Impact Explanation
If the section-5 `get_signed_conflicts`/own-tenure guard does *not* universally cover this gap for v1 signers (unconfirmed), the impact would be Critical: a signer could end up validating and eventually signing two different tenure-start blocks in the same tenure at the same height, i.e., signing a conflicting block. If the guard does cover it (more likely, based on the code read), the practical impact is reduced to unnecessary re-validation work and inconsistent rejection semantics between v1 and v2 — not a standalone safety break.

### Likelihood Explanation
Triggerable by a single miner (one slot, no majority of signers needed): the miner simply needs to submit two different tenure-change block proposals for the same tenure before the first is globally accepted by the network, which is directly under a lone miner's control. Whether this manifests as a full safety break depends on the unconfirmed interaction with the pre-commit conflict guard described above.

### Recommendation
Change `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` to use `SignerDb::get_last_signed_block` (matching the v2 fix) instead of `get_last_globally_accepted_block`, so that a block this signer has already locally accepted (signed) in the tenure is treated as a duplicate at proposal time, consistent with v2's behavior and with the semantics documented in `signerdb.rs`.

### Proof of Concept
1. Miner proposes tenure-start block A for tenure T; a v1-configured signer validates it, pre-commits, and — once the pre-commit threshold is reached — signs it via `mark_locally_accepted`, without A yet reaching global (network-wide) acceptance.
2. Before A is globally accepted, the same miner proposes a second, different tenure-start block B for the same tenure T (e.g., with different transactions).
3. The v1 signer's `handle_block_proposal` → `check_block_against_state` → `SortitionState::check_proposal` → `validate_tenure_change_payload` calls `get_last_globally_accepted_block(&block.header.consensus_hash)`, which returns `None` because A is only `LocallyAccepted`, so the `DuplicateBlockFound` rejection is not raised for B.
4. B is then submitted to the stacks-node for validation and proceeds down the normal proposal pipeline, whereas a v2-configured signer would have rejected B outright at step 3 via `get_last_signed_block` finding A. [1](#0-0)

    /// Return the last signed block in a tenure (identified by its consensus hash).
    /// A block is considered signed if it is locally or globally accepted. Blocks that
    /// have only been pre-committed are excluded, because a pre-commit does not put a
    /// signature over the block and may be safely superseded by a competing proposal.
    ///
    /// This answers "what is the tenure's signed tip?", a different question from
    /// [`SignerDb::has_signed_block_in_tenure`]'s "does a signature bind us to this tenure?",
    /// which is why the predicates deliberately differ on rejected blocks (see there).
    pub fn get_last_signed_block(
        &self,
        tenure: &ConsensusHash,
    ) -> Result<Option<BlockInfo>, DBError> {
        let query = "SELECT block_info FROM blocks WHERE consensus_hash = ?1 AND state IN (?2, ?3) ORDER BY stacks_height DESC LIMIT 1";
        let args = params![
            tenure,
            &BlockState::GloballyAccepted.to_string(),
            &BlockState::LocallyAccepted.to_string(),
        ];
        let result: Option<String> = query_row(&self.db, query, args)?;

        try_deserialize(result)
    }

    /// Return every signed block at or above the given Stacks height, in ANY tenure, excluding
    /// the block with the given signer signature hash, ordered by height (highest first). A
    /// block is considered signed if a signature was ever put over it, ours (`signed_self`)
    /// or the observed group's (`signed_group`). Blocks that were only pre-committed carry no
    /// signature and are never returned. Each row carries the most recent endorsement time
    /// (`signed_self`/`signed_group`, whichever is later) so the caller can judge freshness per
    /// conflict.
    ///
    /// The search deliberately spans all tenures: two blocks at the same height are siblings
    /// no matter which tenure they belong to (e.g. a tenure-start block conflicts with the
    /// previous tenure's block at the same height), so a signature over either may conflict
    /// with a fresh signature over the other.
    ///
    /// Blocks in tenures whose reorg we sanctioned under the reorg-timing rules (see
    /// [`SignerDb::mark_tenure_superseded`]) are still returned, but annotated with the
    /// permitting tenure's sortition (`superseded_by_*`): the permit only holds while that
    /// sortition is canonical, which the caller derives from the node per evaluation (see
    /// `Signer::reorg_permit_stands`) -- like every other question about whether a conflict is
    /// still *live* (`Signer::conflict_still_blocks`), it is not recorded.
    pub fn get_signed_conflicts(
        &self,
        height: u64,
        excluded_signer_signature_hash: &Sha512Trunc256Sum,
    ) -> Result<Vec<SignedConflictInfo>, DBError> {
        let query = "SELECT b.consensus_hash, b.signer_signature_hash, b.stacks_height, b.state,
                MAX(COALESCE(b.signed_self, 0), COALESCE(b.signed_group, 0)) AS last_endorsed,
                st.superseded_by_consensus_hash, st.superseded_by_burn_block_hash
            FROM blocks b
            LEFT JOIN superseded_tenures st ON st.consensus_hash = b.consensus_hash
            WHERE (b.signed_self IS NOT NULL OR b.signed_group IS NOT NULL)
                AND b.stacks_height >= ?1
                AND b.signer_signature_hash != ?2
            ORDER BY b.stacks_height DESC";
        let args = params![
            u64_to_sql(height)?,
            excluded_signer_signature_hash.to_string(),
        ];
        query_rows(&self.db, query, args)
    }
