### Title
Non-constant-time Prometheus metrics token comparison enables timing side-channel token recovery - ([File: core/web/router.go])

### Summary
The `prometheusHandler` function compares the client-supplied `Authorization` header directly against the expected `Bearer <token>` string using Go's `!=` operator, which performs a byte-wise, early-exit comparison. Because the `/metrics` endpoint is mounted directly on the unauthenticated gin engine (not behind session/token auth middleware or the authenticated rate limiter group), an attacker with only network access can repeatedly probe this comparison and use response-time variance to incrementally recover the correct Prometheus scrape token.

### Finding Description
`prometheusUse` registers the metrics route directly on the raw `*gin.Engine` before any of the authenticated route groups or rate limiting are applied: `e.GET(p.MetricsPath, prometheusHandler(p.Token, h))` at [1](#0-0) , and this is wired up in `NewRouter` prior to the session/auth middleware groups being constructed: [2](#0-1) . Inside `prometheusHandler`, the token check builds the expected value as `"Bearer " + token` and compares it to the request header using the standard string inequality operator: [3](#0-2) . Go's `!=` on strings short-circuits at the first mismatching byte, so the time taken to reject a guess is proportional to the length of the correct prefix shared with the real token. Since this route has no gin session dependency, no `auth.Authenticate*` middleware, and is not behind the `rateLimiter` group (which is only attached to the `api` group, not the raw engine), an unauthenticated network client can send an unbounded number of requests with candidate tokens and statistically infer the correct token byte-by-byte from timing measurements.

### Impact Explanation
Successful exploitation discloses the configured Prometheus scrape token without any credentials, mapping to a secret/credential disclosure impact. Since Prometheus metrics can reveal internal operational data (job counts, queue depths, DB/rpc latencies, potentially chain/account related labels) that is meant to be restricted to authorized monitoring systems, disclosure of the token grants an outside attacker persistent read access to this operational telemetry, which is a "sensitive information disclosure" class within Chainlink's bounty scope.

### Likelihood Explanation
Exploitation requires no privileges beyond network reachability to the node's HTTP port, matching the "unauthenticated client of the node API" attacker profile. In practice, however, real-world timing attacks over a network are difficult due to jitter/noise; achieving reliable byte-level recovery requires large numbers of samples per byte position and statistical averaging, and is further complicated by TLS/proxy layers, gin/ginprom overhead, and lack of any obvious constant-time boundary elsewhere in the stack (the comparison itself is cheap and fast, making the signal small). This lowers real-world feasibility versus the theoretical soundness gap, but the code path itself is confirmed reachable and unauthenticated.

### Recommendation
Replace the direct string comparison with a constant-time comparison, e.g. using `subtle.ConstantTimeCompare` on byte slices of equal, fixed length (or first checking length equality out-of-band and then comparing via `crypto/subtle`), similar to the pattern:
```go
if subtle.ConstantTimeCompare([]byte(header), []byte(bearer)) != 1 {
    c.String(http.StatusUnauthorized, ginprom.ErrInvalidToken.Error())
    return
}
```
Additionally, consider applying rate limiting to the `/metrics` route to reduce the number of timing samples an attacker can collect.

### Proof of Concept
Go benchmark/unit test plan for `core/web/router_test.go`:
1. Construct `prometheusHandler(token, dummyHandler)` with a fixed long token (e.g., 64 chars).
2. Build two candidate headers: one sharing a long correct prefix with the real token (differing only in the last byte), and one differing in the first byte.
3. Run each through the handler via `httptest.NewRecorder()`/`gin.CreateTestContext()` thousands of times in a tight loop, measuring elapsed wall-clock time with `time.Now()`/`time.Since()` for each invocation, discarding outliers, and averaging.
4. Assert that the mean processing time for the "long correct prefix" case is statistically distinguishable (e.g., consistently higher by more than measurement noise) from the "wrong first byte" case, demonstrating the timing signal from the `header != bearer` early-exit comparison — then show that replacing it with `subtle.ConstantTimeCompare` removes the measurable timing difference between the two cases.
