### Title
Unprotected `BridgeCommittee.initializeConfig()` Enables Frontrunning to Inject Malicious Bridge Config — (File: `bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig()` carries no caller restriction and is invoked in a separate on-chain transaction from the proxy deployment. Any observer can frontrun that transaction to register an attacker-controlled `BridgeConfig` address, permanently corrupting the token-address and chain-ID registry that `SuiBridge` relies on for every token transfer.

---

### Finding Description

`BridgeCommittee.initializeConfig()` is declared `external` with only a single guard:

```solidity
require(address(config) == address(0), "BridgeCommittee: Config already initialized");
config = IBridgeConfig(_config);
``` [1](#0-0) 

There is no `onlyOwner`, no `initializer` modifier, and no deployer check — any EOA can call it as long as `config` is still `address(0)`.

The deployment script `deploy_bridge.s.sol` runs inside a single `vm.startBroadcast()` / `vm.stopBroadcast()` block, but each `Upgrades.deployUUPSProxy(...)` call and each subsequent external call is a **separate on-chain transaction**. The sequence is:

1. **Tx 1** – Deploy `BridgeCommittee` proxy (with `initialize()` called atomically inside `deployUUPSProxy`). After this tx, `config == address(0)`.
2. **Tx 2** – Deploy `BridgeConfig` proxy.
3. **Tx 3** – `BridgeCommittee(bridgeCommittee).initializeConfig(address(bridgeConfig))` ← **frontrunnable window**.
4. **Tx 4** – `committeeImplementation.initializeConfig(address(bridgeConfig))` (on the bare implementation). [2](#0-1) 

Between Tx 1 and Tx 3 there is a publicly observable mempool window. An attacker who sees Tx 1 (or Tx 3 in the mempool) can submit a higher-gas call to `initializeConfig(maliciousConfig)` and win the race. Once set, the slot is permanently locked by the `config != address(0)` guard, so the legitimate Tx 3 reverts.

The `CommitteeUpgradeable` constructor calls `_disableInitializers()`, which protects `initialize()` on the implementation, but `initializeConfig` is entirely outside that protection. [3](#0-2) 

---

### Impact Explanation

`SuiBridge.transferBridgedTokensWithSignatures` reads `committee.config()` to resolve:
- the **target chain ID** (used to validate incoming bridge messages), and
- the **ERC-20 token address** for each token ID (used to pull funds from `BridgeVault`). [4](#0-3) 

If the attacker's malicious `BridgeConfig` maps token IDs to attacker-controlled contracts or marks every chain as supported, the bridge will:
- accept messages from unsupported chains, enabling illegitimate token unlocks from the vault, or
- transfer vault funds to wrong token contracts under attacker control.

At minimum, the deployer cannot complete deployment without a full redeployment of the `BridgeCommittee` proxy, causing a DoS identical in structure to H-08.

---

### Likelihood Explanation

The attack requires only:
1. Watching the Ethereum mempool for the `BridgeCommittee` proxy deployment transaction.
2. Submitting a single `initializeConfig(maliciousAddress)` call with a higher gas price before Tx 3 lands.

No special privilege, stake, or committee membership is needed. The window exists on every deployment and redeployment.

---

### Recommendation

Combine the proxy deployment and `initializeConfig` call into a single atomic transaction, or restrict `initializeConfig` to the deployer address recorded in the constructor. The simplest fix is to pass the `BridgeConfig` address directly into `initialize()` and remove the separate `initializeConfig` entry point entirely:

```solidity
function initialize(
    address[] memory committee,
    uint16[] memory stake,
    uint16 minStakeRequired,
    address _config          // add this
) external initializer {
    ...
    config = IBridgeConfig(_config);
}
```

Alternatively, record `msg.sender` during `initialize()` and gate `initializeConfig` with `require(msg.sender == _deployer)`.
