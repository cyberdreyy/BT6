### Title
External initiator credentials bypass job-binding via forged run-role User context, allowing arbitrary job execution - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` injects a synthetic `clsessions.User{Role: clsessions.UserRoleRun}` into the gin context for any valid external-initiator (EI) credential, with no reference to which job/bridge the EI is bound to. `PipelineRunsController.Create` uses `auth.GetAuthenticatedUser` to decide whether the caller may trigger a run by numeric job ID, but that check cannot distinguish a genuine session/API-token user from an EI-forged user, so any EI credential can trigger `RunJobV2` on an arbitrary numeric job ID with no ownership/binding check.

### Finding Description
The `userOrEI` route group wraps `POST /v2/jobs/:ID/runs` with `auth.RequiresRunRole(prc.Create)`, and is reachable via `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, or `auth.AuthenticateBySession`: [1](#0-0) 

`AuthenticateExternalInitiator` authenticates the EI token/secret against the DB-stored `ExternalInitiator` record, but then sets the exact same `SessionUserKey` context value that user auth would set — a hardcoded `User{Role: UserRoleRun}` with no linkage to which bridge/job the EI belongs to: [2](#0-1) 

`RequiresRunRole` only checks `user.Role != UserRoleView`, so the forged EI user passes: [3](#0-2) 

Inside `PipelineRunsController.Create`, the code intends to restrict numeric-ID job runs to real users ("EIs not allowed" per the comment), but it uses `auth.GetAuthenticatedUser(c)` to make that determination — the same context key that `AuthenticateExternalInitiator` also populates: [4](#0-3) 

Because `GetAuthenticatedUser` simply reads `SessionUserKey` without checking whether the request was actually authenticated via `AuthenticateExternalInitiator` (a separate helper `GetAuthenticatedExternalInitiator` exists but is never consulted in `Create`), `isUser` evaluates to `true` for an EI-authenticated request too. The numeric-ID branch then unconditionally calls `prc.App.RunJobV2(ctx, jobID, nil)` for whatever `:ID` the attacker supplied — there is no check that the job belongs to a bridge/spec the calling EI was registered against. The UUID/webhook branch is dead for exploitation of *other* jobs (webhook job type removed, per `job.ErrJobTypeRemoved`), but the numeric-ID branch has no equivalent protection at all.

### Impact Explanation
An external-initiator credential — the lowest-privilege node credential class, meant only to trigger runs for the bridge/job it was registered against — can trigger a pipeline run (`RunJobV2`) on **any** job in the node by numeric job ID, regardless of which job/bridge the EI was bound to. This is unauthorized action on another job/resource, matching the "unauthorized job run" bounty impact class. Depending on job type (e.g., transaction-sending jobs, OCR jobs, direct-request jobs with side effects), this could trigger unintended fund movement or unwanted operational actions.

### Likelihood Explanation
The only precondition is possession of one valid EI access key/secret pair (the lowest privilege credential in the system) and knowledge/guessing of a target numeric job ID (job IDs are small sequential integers, easily enumerable via `/v2/jobs` if any read access exists, or brute-forceable). No admin/edit/view role is needed — just the EI's own registered credentials. The flaw is deterministic and repeatable on every request.

### Recommendation
In `PipelineRunsController.Create`, explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and reject (or properly scope) EI-authenticated requests instead of relying on `GetAuthenticatedUser`, which is populated identically by both user and EI authentication. If EI-triggered runs by numeric ID are intended to be supported at all, verify the specific EI record is bound to the target job/bridge before invoking `RunJobV2`. Alternatively, stop overloading `SessionUserKey` for EI authentication; use a distinct context flag so downstream handlers can differentiate real users from EI callers.

### Proof of Concept
Handler/integration test plan:
1. Start an app with `JobPipeline.ExternalInitiatorsEnabled = true`.
2. Create job X (any non-webhook job type, e.g. a `directrequest` or the OCR job used in `setupPipelineRunsControllerTests`) and note its numeric `jobID_X`.
3. Register external initiator `A` via `cltest.CreateExternalInitiatorViaWeb`, obtaining `eip.AccessKey`/`eip.Secret`. EI `A` has no relation to job X.
4. Send `POST /v2/jobs/<jobID_X>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to EI A's credentials (no session/API token).
5. Assert (current buggy behavior) the response is `200 OK` with a `pipelineRun` resource created for job X, and `pipeline_runs` count increments for job X, even though EI A was never bound to job X.
6. Expected fixed behavior: response should be `401 Unauthorized`/`422` because EI credentials should not be permitted to trigger runs on jobs they are not bound to via numeric ID.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
