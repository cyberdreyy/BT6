## Finding: Ed25519/Secp256k1 precompiles accept a degenerate zero-signature instruction as "verified" with no cryptographic check performed

### Title
Ed25519 and Secp256k1 precompile `verify()` return `Ok(())` for a degenerate zero-signature instruction, authenticating nothing while being reported as verified - (File: `precompiles/src/ed25519.rs`, `precompiles/src/secp256k1.rs`)

### Summary
The bug class from the external report is: a signed-data container with an empty signer set (`signerInfos`) passes verification because the verifier's loop over signers is simply empty, so "verified" is reported despite zero signatures being checked. The same pattern exists in agave's ed25519 and secp256k1 precompiles: an instruction whose declared signature count is `0`, with instruction data sized to exactly the minimum header, passes the length/size guard and then the `for i in 0..num_signatures` verification loop executes zero times, returning `Ok(())` with no cryptographic operation ever performed.

### Finding Description
In `precompiles/src/ed25519.rs::verify`, the zero-signature guard only fires when there is *extra* trailing data: [1](#0-0) 

If `data = [0, 0]` (exactly `SIGNATURE_OFFSETS_START` bytes, `num_signatures = 0`), then:
- `data.len() < SIGNATURE_OFFSETS_START` is false,
- `num_signatures == 0 && data.len() > SIGNATURE_OFFSETS_START` is false (`2 > 2` is false),
- `expected_data_size = SIGNATURE_OFFSETS_START`, and `data.len() < expected_data_size` is false,
- the `for i in 0..num_signatures` loop body (lines 30-77, containing the actual `verify_strict` call) never executes,
- the function returns `Ok(())`.

The same structural gap exists in `precompiles/src/secp256k1.rs::verify`: [2](#0-1) 

With `data = [0]` (`count = 0`, no trailing bytes), `count == 0 && data.len() > 1` is false, `expected_data_size = 1`, the loop `for i in 0..count` never runs, and the function returns `Ok(())`.

By contrast, `precompiles/src/secp256r1.rs::verify` unconditionally rejects `num_signatures == 0` regardless of trailing data length: [3](#0-2) 

This inconsistency (secp256r1 hard-rejects zero signatures; ed25519/secp256k1 only reject zero signatures when *padding* data happens to be present) shows the zero-signature-passes-with-no-verification case in ed25519/secp256k1 is an unintended gap rather than deliberate design, mirroring exactly the wolfSSL bug: a degenerate, signer-less container is treated as "verified."

These `verify()` functions are wired in as the canonical precompile-checking entry point used by `verify_if_precompile` / bank transaction verification: [4](#0-3) 

Both are registered in the static precompile table with no additional gating feature (`None` = always enabled): [5](#0-4) 

No existing test in the repository exercises the "exactly-minimum-size, zero signatures" boundary case for ed25519 or secp256k1 (the existing zero-signature tests for secp256k1 use `DATA_START`-sized buffers, which fall into the "extra data" branch and correctly error), so this gap is not covered/caught by CI: [6](#0-5) 

### Impact Explanation
A single unprivileged transaction sender can append a minimal `[0, 0]` (ed25519) or `[0]` (secp256k1) instruction to any transaction. The runtime's precompile-verification pass will mark this instruction as successfully "verified" without performing any signature check. Any on-chain program that relies on the well-established Solana idiom of inspecting the Instructions sysvar to confirm "a preceding ed25519/secp256k1 precompile instruction executed successfully" as proof that an external signature was checked (a common cross-program authentication/meta-transaction pattern) can be tricked into treating an unauthenticated, signer-less instruction as cryptographic proof of authorization — enabling CPI privilege escalation / unauthorized action execution in downstream program logic that trusts this precompile's success signal.

### Likelihood Explanation
Trivially reachable: constructing a 1-2 byte instruction with a zero signature count requires no special privilege, no race condition, and no leader/network cooperation — it is fully attacker-controlled instruction data in a single transaction.

### Recommendation
Change `verify()` in `precompiles/src/ed25519.rs` and `precompiles/src/secp256k1.rs` to unconditionally reject `num_signatures == 0` (matching the unconditional guard already present in `precompiles/src/secp256r1.rs`), rather than only rejecting it when trailing data happens to be present.

### Proof of Concept
Construct an ed25519 precompile instruction with data `[0u8, 0u8]` (i.e. `num_signatures = 0`, padding byte `0`) and no signature/pubkey/message payload, and call `agave_precompiles::ed25519::verify(&[0,0], &[&[0,0]], &FeatureSet::all_enabled())` — it returns `Ok(())`. Equivalently for secp256k1, `agave_precompiles::secp256k1::verify(&[0u8], &[&[0u8]], &FeatureSet::all_enabled())` returns `Ok(())`. In both cases no signature, public key, or message is ever inspected, yet the instruction is reported as verified by `verify_if_precompile`.

/// Check that a program is precompiled and if so verify it
pub fn verify_if_precompile(
    program_id: &Pubkey,
    precompile_instruction: &CompiledInstruction,
    all_instructions: &[CompiledInstruction],
    feature_set: &FeatureSet,
) -> Result<(), PrecompileError> {
    for precompile in PRECOMPILES.iter() {
        if precompile.check_id(program_id, |feature_id| feature_set.is_active(feature_id)) {
            let instruction_datas: Vec<_> = all_instructions
                .iter()
                .map(|instruction| instruction.data.as_ref())
                .collect();
            return precompile.verify(
                &precompile_instruction.data,
                &instruction_datas,
                feature_set,
            );
        }
    }
    Ok(())
}
