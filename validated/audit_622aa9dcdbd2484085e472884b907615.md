### Title
Front-runnable, permissionless lockup deployment allows an attacker to squat a victim's canonical lockup account with an attacker-controlled staking-pool whitelist - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the lockup account address deterministically from the `owner_account_id` argument alone, with no restriction on who may call it and no binding of the deployment to the intended owner or funder. Because the function also lets the caller override `staking_pool_whitelist_account_id`, anyone can pre-empt (front-run) the legitimate deployment of a victim's lockup, permanently occupying the victim's canonical lockup account with attacker-chosen configuration—most importantly, a whitelist contract the attacker controls.

### Finding Description
`create()` computes the lockup account id purely from `owner_account_id`, independent of `env::predecessor_account_id()`: [1](#0-0) 

There is no `assert!` requiring `env::predecessor_account_id() == owner_account_id` (or any other authorization), and the caller may freely choose `whitelist_account_id`, which is used as-is instead of the factory's default when supplied: [2](#0-1) 

This mirrors the reported bug class exactly: the deployment "salt" (here, the deterministic account name) is bound to the *victim's identity* (`owner_account_id`) but not to who is allowed to trigger the deployment or what parameters they may set. Just like the PRB proxy report describes an attacker using `deployFor()`/`transferOwnership()` to force state onto a victim before their legitimate transaction lands, an attacker here can call `create(owner_account_id: <victim>, ..., whitelist_account_id: Some(<attacker_whitelist>))` with the minimum required deposit before the victim's genuine funder (e.g. the foundation) does. Since the target account name is deterministic and depends only on the victim's id, this single front-run permanently claims the canonical lockup address for that victim (the legitimate creation attempt afterwards will simply fail at `create_account` and be refunded, per `on_lockup_create`): [3](#0-2) 

The victim's lockup now trusts an attacker-controlled `staking_pool_whitelist_account_id`. This value is later used, unchanged, as the sole authority the lockup contract consults before delegating funds to a staking pool: [4](#0-3) 

This directly breaks the custody binding described in the rules: "an account trusted as a pool or whitelist versus the code and arguments that trust was granted for." The whitelist is supposed to represent NEAR Foundation-vetted staking pools (per the whitelist contract's stated purpose): [5](#0-4) 

but the attacker substitutes their own whitelist contract at deployment time, which they can populate with a malicious "staking pool" that never honors the withdrawal guarantee the whitelist contract exists to enforce.

The factory's own documentation confirms this is an explicitly permissionless flow with no owner/funder binding check: "Lockups can be funded from any account... No need to have access to the foundation keys to create lockup": [6](#0-5) 

### Impact Explanation
This is a "wrongly whitelisted or wrongly parameterised deployment" (explicitly a Critical-severity category): the attacker can force a lockup account with a chosen `owner_account_id` to be permanently created with an attacker-controlled staking-pool whitelist. If the legitimate funder subsequently funds this pre-existing account (which docs state can be done "from any account," including a plain NEAR transfer rather than re-invoking `create`), the owner will later select what they believe is a vetted staking pool from `is_whitelisted` checks that are actually controlled by the attacker, and can delegate/lose the locked NEAR to a malicious "staking pool" contract that never returns it—defeating the entire guarantee the lockup/whitelist system is built on (per `whitelist/README.md`: "the lockup contract should be able to recover delegated tokens back to the lockup from a staking pool").

### Likelihood Explanation
The lockup account name is fully deterministic and publicly computable from `owner_account_id` (`sha256(owner_account_id)[..20]` + factory suffix), so an attacker can precompute the target address for any known/expected victim ahead of time and race a pending legitimate creation transaction with only `MIN_ATTACHED_BALANCE` (3.5 NEAR) at stake. No special privileges, keys, or insider access are required—only mempool visibility of the intended `create` call, which is the same class of front-running the external report describes.

### Recommendation
Bind the deployment to the caller's identity rather than only the target owner, e.g. require `env::predecessor_account_id() == owner_account_id.as_ref()` (or otherwise restrict who can create a lockup for a given owner), and/or restrict `whitelist_account_id` overrides to the foundation account. Alternatively, make the lockup account name depend on both `owner_account_id` and `predecessor_account_id`/a caller-supplied salt so a victim's canonical address cannot be squatted by an unrelated party.

### Proof of Concept
1. Foundation/funder prepares to call `lockup-factory.create({owner_account_id: "victim.near", ...})` with no `whitelist_account_id` override (intending the default, trusted whitelist).
2. Attacker observes the pending transaction (or simply predicts the deterministic address for `"victim.near"`) and front-runs with `lockup-factory.create({owner_account_id: "victim.near", lockup_duration: ..., whitelist_account_id: Some("evil-whitelist.attacker.near")})`, attaching only `MIN_ATTACHED_BALANCE` (3.5 NEAR).
3. The attacker's transaction lands first, creating the lockup account (deterministically named from `"victim.near"`) with `staking_pool_whitelist_account_id = "evil-whitelist.attacker.near"`.
4. The legitimate funder's later `create` call fails at `create_account` (account already exists) and is refunded via `on_lockup_create`.
5. Believing the address is genuine (it matches the expected deterministic naming scheme), the funder/foundation instead tops up the existing account via a plain NEAR transfer.
6. The victim owner later calls `select_staking_pool` on their lockup; `is_whitelisted` is checked against the attacker's `evil-whitelist.attacker.near`, which the attacker has populated with a malicious "staking pool" contract.
7. The owner deposits/stakes NEAR to the malicious pool, which never returns the delegated funds—resulting in a loss of the victim's lockup NEAR.

```rust
    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
```

```markdown
# Whitelist contract for staking pools

The purpose of this contract is to maintain the whitelist of the staking pool contracts account IDs that are approved
by NEAR Foundation.

In order for the lockup contracts to be able delegate to a staking pool, the staking pool should faithfully implement the spec.
The staking pool should guarantee that the delegated tokens can not be lost or locked, such as the lockup contract should be
able to recover delegated tokens back to the lockup from a staking pool. In order to enforce this, only approved (whitelisted)
accounts of staking pool contracts can receive delegated tokens from lockup contracts.
```
