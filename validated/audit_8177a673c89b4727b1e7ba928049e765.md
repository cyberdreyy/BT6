### Title
Post-default instant-withdraw requests merge into the defaulted-epoch claim bucket and drain the recovery reserve without funding - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The NanoMQ report is a use-after-free: state attached to a freed session is reused when the same ClientID reconnects, corrupting shared accounting. The credit-vault analog is a *stale claim slot reuse*: after `finalizeDefaultRecovery`, `requestInstantWithdraw` does not perform the pending-receipt hygiene check that `requestWithdraw` does, and it records new requests under the unchanged `epochNumber` — the same bucket (`instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`) that the default-claim path treats as "already funded by the recovery reserve". A new, completely unfunded request is paid out of `defaultRecoveryReserve` at `defaultRecoveryPrice`, stealing reserve earmarked for legitimate defaulted-epoch claimants.

### Finding Description
- `requestWithdraw` post-default explicitly refuses users with any pending receipt and routes the request to the isolated `postDefaultRequests` bucket, so it can never contaminate the defaulted-epoch claim (`IdleCreditVault.sol:247-257`).
- `requestInstantWithdraw` performs no equivalent check. After `defaultRecoveryFinalized`, it still does `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount` (`IdleCreditVault.sol:371`). `epochNumber` is not advanced by default finalization, so this new request lands in `defaultRecoveryEpoch`'s bucket.
- `claimInstantWithdrawRequest` → `_claimDefaultedInstantWithdrawRequest` pays `instantWithdrawsRequestsByEpoch[_user][defaultEpoch] * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve` (`IdleCreditVault.sol:842-855`), unconditionally — it never checks that the basis was actually present (and funded/counted) at finalization.
- Post-default, the attacker burns strategy tokens worth `_amount` to mint the receipt, but the payout `A * defaultRecoveryPrice` comes from the reserve with zero underlying ever collected for `A` (no `collectInstantWithdrawFunds`/`getInstantWithdrawFunds` funding is required by the defaulted-claim path). If post-default strategy tokens trade at or below the haircut implied by `defaultRecoveryPrice` (they do — `finalizeDefault` lowers `virtualPrice` first, per the comment at `IdleCreditVault.sol:253`), the attacker roughly breaks even on the burn while extracting pure reserve; the real cost is borne by other claimants whose reserve is depleted.
- `pendingInstantWithdraws` is clamped to 0 rather than reverting (`IdleCreditVault.sol:852`), so accounting silently absorbs the inconsistency.

### Impact Explanation
Direct theft of the isolated default-recovery reserve. Each call lets an unprivileged attacker (any tranche/strategy-token holder after default) convert an unfunded receipt into reserve underlyings. Repeating with fresh tranche purchases drains `defaultRecoveryReserve`, causing legitimate defaulted-epoch instant and normal claimants to revert on `_transferDefaultRecovery` (insolvency of the reserve) — permanent loss of their recovery proceeds, quantified as up to the full remaining reserve.

### Likelihood Explanation
Requires: pool defaulted, `finalizeDefaultRecovery` executed with `defaultInstantWithdrawsFinalized`, and instant withdrawals still callable post-default (the codebase explicitly supports post-default instant claims, e.g. `testFinalizeDefaultClaimsFundedAndDefaultedInstantRedeemsInOneCall`). The attacker needs only to hold tranche tokens post-default — acquirable on the open market. No privileged cooperation is needed.

### Recommendation
Mirror the `requestWithdraw` post-default guard in `requestInstantWithdraw`: revert if `_hasWithdrawRequest(_user) || instantWithdrawsRequests[_user] != 0 || postDefaultRequests[_user] != 0`, or record post-default instant requests in a separate bucket (analogous to `postDefaultRequests`) that is paid via `_transferFundedClaim` only after `collectInstantWithdrawFunds`. At minimum, cap `_claimDefaultedInstantWithdrawRequest` basis to a snapshot taken at finalization (e.g. an immutable `defaultedInstantBasis[user]`) rather than the mutable per-epoch map.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testPostDefaultInstantRequestDrainsRecoveryReserve() external {
  // 1. Normal epoch: honest user deposits and files an instant withdraw request.
  _depositWithUser(honestUser, amount, true);
  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());
  vm.prank(honestUser);
  cdoEpoch.requestWithdraw(0, address(AAtranche));

  // 2. Default + finalizeDefaultRecovery(recovered, ...) as in existing tests.
  _startEpochAndCheckPrices(1);
  _checkDefault();
  // manager finalizes with recoveryRatio < 1e18
  cdoEpoch.finalizeDefault(recovered, manager);

  // 3. Attacker buys cheap post-default tranches / already holds a defaulted receipt,
  //    then files a NEW instant withdraw request (no funding ever collected for it).
  vm.prank(attacker);
  cdoEpoch.requestInstantWithdraw(attackAmount); // mints receipt, bumps instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch]

  // 4. Attacker claims: paid attackAmount * defaultRecoveryPrice / RECOVERY_FULL
  //    out of defaultRecoveryReserve even though pendingInstantWithdraws contribution
  //    was never collected.
  vm.prank(attacker);
  cdoEpoch.claimInstantWithdrawRequest();

  // assert attacker received underlying and defaultRecoveryReserve decreased by
  // attackAmount * defaultRecoveryPrice / RECOVERY_FULL without any transferFrom(idleCDO).
  // Subsequent honest claim reverts: reserve insolvent.
}
```

The broken invariant is "one receipt, one funded payout": a receipt created after the recovery snapshot consumes reserve priced for pre-snapshot receipts — the same stale-state reuse as the UAF in the reference report.
