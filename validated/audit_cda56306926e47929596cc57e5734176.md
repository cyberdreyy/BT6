### Title
Stale confirmations from removed multisig members still count toward execution threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` only removes pending requests whose *creator* was the deleted member, but never scans/prunes the `confirmations` map for entries where the deleted member had confirmed a request created by someone else. `confirm` then counts these stale confirmations toward `num_confirmations`, letting a request execute with fewer than K currently-live, authorized confirmers.

### Finding Description
The multisig invariant should be: `num_confirmations` (K) live, current members must approve a request before execution — i.e. `|{live members} ∩ {confirmers}| >= K`. The code instead checks `confirmations.len() >= num_confirmations` [1](#0-0) , where `confirmations` is a `HashSet<String>` populated at confirm time and never re-validated against current membership.

When a member is removed via `DeleteMember`, `delete_member` cleans up:
- requests *created* by that member (`r.member == member`) — both the request and its confirmation set are deleted [2](#0-1) 
- the member's `num_requests_pk` entry and its membership record [3](#0-2) 

But it never iterates `self.confirmations` to remove that member's identifier from confirmation sets of requests *created by other members*. Any pending request that the now-removed member had already confirmed keeps that stale confirmation entry.

### Impact Explanation
Suppose a K-of-N multisig has member M confirm a pending `Transfer`/`FunctionCall`/`AddKey` request (1 of K confirmations). M is later removed (e.g., compromised key rotation) via a separate `DeleteMember` request. The pending request still shows M's confirmation. If the remaining live members later add (K-1) more confirmations, `confirm` executes the request, satisfied by `confirmations.len() >= num_confirmations`, even though only (K-1) *currently live* members actually authorized it. This breaks the "confirmations counted versus live members" custody binding: a request is executed below the intended live-member threshold, allowing unauthorized transfers, deploys, key additions, etc. from the account the multisig protects.

### Likelihood Explanation
This requires a normal, expected multisig lifecycle event (removing a member, e.g., after suspected key compromise) combined with a pre-existing pending request that the removed member had confirmed. This is a realistic operational sequence for any long-lived multisig with membership rotation, not a contrived edge case, and doesn't require any privileged or out-of-scope actor beyond the normal K-of-N confirmation flow already permitted by the contract.

### Recommendation
In `delete_member`, iterate `self.confirmations` and strip the deleted member's identifier from every request's confirmation set (not just requests it created), or re-validate at `confirm`/execution time that every entry in `confirmations` still `self.members.contains(...)`.

### Proof of Concept
1. Deploy `multisig2` with 3 members `{A, B, C}` and `num_confirmations = 2`.
2. `A` calls `add_request_and_confirm` for a `Transfer` request (confirmations = `{A}`).
3. Members confirm and execute `DeleteMember { member: A }` via a separate self-request (requires 2 confirmations from B/C, unrelated to the pending transfer) — `delete_member` runs, `self.members` no longer contains `A`, but the transfer request's `confirmations` set still contains `A`.
4. `B` calls `confirm` on the pending transfer request: `confirmations.len() + 1 == 2 >= num_confirmations`, so the request executes with `A` (no longer a member) + `B` — i.e., only one live member truly authorized it while the contract believes threshold 2 was met by two live signers.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
