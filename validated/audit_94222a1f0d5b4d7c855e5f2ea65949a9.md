## Analog Found: Unvalidated `decimals` Field in `*Checked` SPL-Token Instruction Parsing Leads to Misreported Token Amounts

### Title
Unvalidated `decimals` in `TransferChecked`/`ApproveChecked`/etc. instruction parsing causes misreported `tokenAmount` in `jsonParsed` transaction/instruction output - (File: `transaction-status/src/parse_token.rs`)

### Summary
The reported bug class is a scale/decimal-mismatch error: a value is computed assuming the wrong number of decimal places relative to the token's real decimals, producing a result that is off by many orders of magnitude. The same class of bug exists in agave's SPL-token instruction parser used by `jsonParsed` transaction/instruction encoding: the `decimals` value used to compute the human-readable `tokenAmount` (`ui_amount`/`ui_amount_string`) is taken directly, unvalidated, from attacker-controlled instruction data rather than from the actual on-chain mint.

### Finding Description
For "checked" SPL Token instructions (`TransferChecked`, `ApproveChecked`, `MintToChecked`, `BurnChecked`, etc.), the instruction wire format itself carries a `decimals` field supplied by whoever built the transaction. This field exists so the on-chain SPL Token program can sanity-check it against the real mint decimals at execution time and abort the instruction if it doesn't match.

However, `parse_token` in [1](#0-0)  builds the JSON-RPC `jsonParsed` representation of the instruction using that same untrusted `decimals` value directly, via `SplTokenAdditionalDataV2::with_decimals(decimals)` and `token_amount_to_ui_amount_v3`, with no access to or cross-check against the bank's actual mint account:

```
TokenInstruction::TransferChecked { amount, decimals } => {
    check_num_token_accounts(&instruction.accounts, 4)?;
    let additional_data = SplTokenAdditionalDataV2::with_decimals(decimals);
    ...
    "tokenAmount": token_amount_to_ui_amount_v3(amount, &additional_data),
```

`token_amount_to_ui_amount_v3` ( [2](#0-1) ) purely does `amount as f64 / 10^decimals`, so any decimals value chosen by the transaction author is reflected verbatim in the RPC response.

This differs from the RPC "live account" path (`get_token_account_balance`, `get_token_supply`, `get_parsed_token_account`) which correctly fetches decimals from the bank's mint account via `get_mint_owner_and_additional_data`/`get_additional_mint_data` ( [3](#0-2) ). The instruction-parsing path in `transaction-status` has no such verification, because it only receives the `CompiledInstruction` and `AccountKeys`, not bank state.

### Impact Explanation
Any unprivileged user can submit (or even just simulate) a transaction containing a `TransferChecked`/`ApproveChecked`/`MintToChecked`/`BurnChecked` instruction with a `decimals` value that intentionally mismatches the real mint's decimals (e.g., real mint has 9 decimals, attacker crafts instruction claiming `decimals: 0` or `decimals: 18`). When any client queries that transaction via `getTransaction`/`getConfirmedTransaction`/`getBlock` with `encoding: jsonParsed`, or subscribes and receives parsed instruction data, the returned `tokenAmount.uiAmount`/`uiAmountString` will be wrong by orders of magnitude (billions of times larger or smaller), exactly mirroring the external report's "HARD_CAP is 1,000,000,000 times larger than intended" scenario. This is a decoder misreporting bug: wrong (attacker-controlled) data is returned from a read-only RPC query, which can mislead wallets, explorers, and automated tooling that trust the parsed RPC value instead of re-deriving it from the mint.

### Likelihood Explanation
Trivial to trigger: build any `TransferChecked`-family instruction with a bogus `decimals` byte in the instruction data and submit/broadcast it (it may even fail on-chain due to the token program's own decimals check, but the transaction and its instruction are still recorded and served via `getTransaction`/`getBlock` regardless of success/failure, since RPC parses and displays sent instructions independent of execution outcome). No special privileges, validator role, or multiple calls are required — a single `getTransaction` call with `jsonParsed` encoding is sufficient to reproduce the misreported value.

### Recommendation
For `jsonParsed` encoding of `*Checked` SPL Token instructions, either (a) clearly label the emitted `decimals`/`tokenAmount` as attacker-supplied/unverified data distinct from the mint's actual decimals, or (b) where bank/mint state is available at parse time (e.g., in `rpc/src/parsed_token_accounts.rs` call sites that already resolve mint data), cross-check the instruction's declared decimals against the actual mint decimals and flag/replace mismatches rather than blindly trusting instruction-supplied `decimals` for computing `ui_amount`.

### Proof of Concept
1. Construct a `TransferChecked` (or `ApproveChecked`/`MintToChecked`/`BurnChecked`) instruction for a real mint known to use 9 decimals, but set the instruction's `decimals` field to `0`.
2. Submit the transaction (it may fail on-chain due to the SPL Token program's internal decimals check — this does not prevent the transaction/instruction from being stored and later fetched).
3. Call `getTransaction`/`getConfirmedTransaction` with `{"encoding": "jsonParsed"}` for that signature.
4. Observe the returned `tokenAmount.uiAmount`/`uiAmountString` in the parsed instruction reflects the attacker-chosen `decimals: 0` (e.g., raw amount `5000000000` reported as ui amount `5000000000` instead of the true `5.0`), confirming the misreported, order-of-magnitude-wrong value flows directly from untrusted instruction data through [1](#0-0)  and [2](#0-1)  into the RPC response.

pub fn token_amount_to_ui_amount_v3(
    amount: u64,
    additional_data: &SplTokenAdditionalDataV2,
) -> UiTokenAmount {
    let decimals = additional_data.decimals;
    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =
        additional_data.interest_bearing_config
    {
        let ui_amount_string =
            interest_bearing_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else if let Some((scaled_ui_amount_config, unix_timestamp)) =
        additional_data.scaled_ui_amount_config
    {
        let ui_amount_string =
            scaled_ui_amount_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else {
        let ui_amount = 10_usize
            .checked_pow(decimals as u32)
            .map(|dividend| amount as f64 / dividend as f64);
        (ui_amount, real_number_string_trimmed(amount, decimals))
    };
    UiTokenAmount {
        ui_amount,
        decimals,
        amount: amount.to_string(),
        ui_amount_string,
    }
}

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}
