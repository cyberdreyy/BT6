This confirms the vulnerability. The vote-tracking logic in `stackerdb_listener.rs` never removes a signer's weight from `total_weight_rejected` when that signer later flips to Accepted, and the coordinator in `signer_coordinator.rs` checks the rejection threshold *before* the acceptance threshold, using this permanently-inflated value.

### Title
Stale rejection weight is never cleared when a signer switches from Reject to Accept, permanently inflating `total_weight_rejected` and causing valid blocks to be wrongly treated as rejected - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`BlockStatus::total_weight_rejected` and `BlockStatus::total_weight_approved` are two independent monotonically-increasing counters keyed off two different membership tests (`responded_signers` for rejections, `gathered_signatures` for acceptances). When a single signer changes its vote from `Rejected` to `Accepted` for the same block, the code correctly avoids double-counting the *approval* side in some orders, but it never subtracts the earlier rejection weight from `total_weight_rejected`. The two counters can therefore both contain weight from the same signer simultaneously, and `total_weight_rejected` can never shrink. `signer_coordinator.rs::gather_signatures` checks the rejection threshold first, so this stale, permanently-inflated rejection weight can incorrectly drive a valid, currently-approved block to `NakamotoNodeError::SignersRejected`.

### Finding Description
`BlockStatus` in [1](#0-0)  tracks `responded_signers`, `gathered_signatures`, `total_weight_approved`, and `total_weight_rejected` per block.

On an `Accepted` message, weight is only added to `total_weight_approved` if the slot is not already present in `gathered_signatures`, and then the slot is inserted into both `gathered_signatures` and `responded_signers`: [2](#0-1) 

On a `Rejected` message, weight is only added to `total_weight_rejected` if `responded_signers.insert(slot_id)` returns `true` (i.e., the slot wasn't already in the set): [3](#0-2) 

Consider a signer that first sends a `Rejected` response, then later (for the same block, e.g. after reconsidering per `should_reevaluate_reject_reason`) sends an `Accepted` response:
1. First message (Reject): `responded_signers.insert(slot_id)` returns `true` → `total_weight_rejected` += signer weight. `responded_signers` now contains `slot_id`. `gathered_signatures` is untouched.
2. Second message (Accept): the acceptance branch checks `!block.gathered_signatures.contains_key(&slot_id)`, which is still `true` (the slot was never added to `gathered_signatures` by the rejection path) → `total_weight_approved` += signer weight again.

At no point is the signer's weight removed from `total_weight_rejected`. This is exactly the `paramOffsets`-style bug: an update to an existing entry (the signer's vote) causes an unconditional addition to a separate tracking structure without correcting/removing the value that was already recorded for that same entry, breaking the invariant that each signer's weight should count toward at most one side (aggregated-weight vs verified-accepts equality is violated — `total_weight_approved + total_weight_rejected` can exceed `total_weight`, and specifically `total_weight_rejected` retains dead weight indefinitely).

### Impact Explanation
`gather_signatures` in `signer_coordinator.rs` evaluates the rejection condition before the acceptance condition every polling loop: [4](#0-3) 

Because `total_weight_rejected` never decreases, if enough weight (potentially including stale, already-reverted rejections) accumulates such that `total_weight_rejected + weight_threshold > total_weight`, the coordinator returns `NakamotoNodeError::SignersRejected` — even if every signer that originally rejected has since sent an `Accepted` response and the true, current approval weight has crossed the acceptance threshold. This is a liveness wedge: a legitimate, currently-approved block can be permanently prevented from being signed/broadcast because of vote history that is no longer the signer's actual position, and the rejection check runs before the acceptance check so accepted weight cannot rescue it once the stale rejection threshold is crossed.

### Likelihood Explanation
This requires only a single signer (well within a one-slot-miner/gossip trigger; no majority required) to send a `Rejected` `BlockResponse` for a block and later send an `Accepted` response for the same `signer_signature_hash` — a legitimate and expected occurrence per `should_reevaluate_reject_reason`/`should_reevaluate_block` in `stacks-signer/src/v0/signer.rs`, which explicitly allows a signer to reconsider and change its response to a previously-rejected block. Any one signer flipping its vote is sufficient to leave permanently stale weight in `total_weight_rejected`.

### Recommendation
Track vote weight per signer with a single source of truth (e.g., a `HashMap<u32, Vote>` recording each signer's current position), and recompute `total_weight_approved`/`total_weight_rejected` from that map, or explicitly subtract the previous contribution before adding the new one when a signer's vote changes — mirroring the `borgCore.sol` recommendation of not mutating an accumulation structure when an existing entry is merely being updated rather than newly added.

### Proof of Concept
1. Node proposes block `B`; signer weight threshold is 70%, and signer `S` has weight `w` such that current `total_weight_rejected` for other signers is already close to (but below) the blocking threshold.
2. Signer `S` sends `BlockResponse::Rejected` for `B` — `total_weight_rejected += w` in `stackerdb_listener.rs`.
3. Signer `S` later re-evaluates (e.g., a chainstate condition it used to reject on resolves) and sends `BlockResponse::Accepted` for the same `B` — `total_weight_approved += w`, but `total_weight_rejected` still includes `w` from step 2.
4. If other signers' rejection weight plus this stale `w` crosses `total_weight - weight_threshold`, `gather_signatures` returns `SignersRejected` for `B` even though the current, live tally of signer opinions has `S` (and possibly enough others) accepting — the block is wedged despite having legitimate support.
