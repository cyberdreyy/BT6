### Title
`get_locked_amount` under-locks tokens when `lockup_timestamp + release_duration` overflows `u64` - (File: `lockup/src/getters.rs`)

### Summary
`get_locked_amount` computes `end_timestamp` with a saturating add of `lockup_timestamp` and `release_duration`, but then divides by the *unsaturated* `release_duration` when computing `unreleased_amount`. When an attacker picks `lockup_timestamp` and `release_duration` such that their sum exceeds `u64::MAX`, `time_left` is silently truncated below the true `release_duration`, causing `unreleased_amount` to be smaller than `lockup_amount` at the very instant the release period begins — breaking the invariant that crossing `lockup_timestamp` (or enabling transfers) should never immediately reduce the locked balance below the full amount.

### Finding Description
The invariant that should hold is: at `block_timestamp == lockup_timestamp` (the instant the release window opens), `get_locked_amount()` must equal `lockup_amount - termination_withdrawn_tokens` (i.e. `unreleased_amount == lockup_amount`), exactly matching the value returned by the fall-through branch for any `block_timestamp < lockup_timestamp` [1](#0-0) .

Inside the enabled branch:
```
let end_timestamp = lockup_timestamp.saturating_add(release_duration);
...
let time_left = U256::from(end_timestamp - block_timestamp);
let unreleased_amount = U256::from(lockup_amount) * time_left / U256::from(release_duration);
``` [2](#0-1) 

`end_timestamp` is computed with `saturating_add`, so if `lockup_timestamp + release_duration > u64::MAX`, `end_timestamp` clips to `u64::MAX` instead of the true (larger) sum. At `block_timestamp == lockup_timestamp`, `time_left = u64::MAX - lockup_timestamp`, which is strictly smaller than the actual `release_duration` used as the divisor. This makes `unreleased_amount = lockup_amount * time_left / release_duration < lockup_amount` — some tokens appear released the moment the lockup opens, even though zero time has actually elapsed in the release schedule.

The `lockup-factory` `create` entrypoint lets any unprivileged caller choose `lockup_timestamp` and `release_duration` freely for their own lockup account [3](#0-2) , and these are passed straight through to `LockupInformation` without any bound checking on their sum relative to `u64::MAX` [4](#0-3) . No existing guard (`assert_owner`, `assert_transfers_enabled`, etc.) validates that `lockup_timestamp + release_duration` fits in `u64`, so the saturation silently corrupts the release math.

Once `unreleased_amount` is deflated this way, `get_owners_balance`/`get_liquid_owners_balance` report the deflated locked amount as available [5](#0-4) , letting the owner call `transfer` to move the prematurely-unlocked NEAR out of the lockup account before the schedule should permit it.

### Impact Explanation
Locked/unvested lockup NEAR is released and can be transferred out earlier than the schedule dictates, which matches the "locked or unvested lockup tokens released early" Critical impact category. The attacker can tune `lockup_timestamp` and `release_duration` so the gap `(lockup_timestamp + release_duration) - u64::MAX` approaches `release_duration`, driving the deflated `unreleased_amount` towards zero — i.e., nearly the entire `lockup_amount` becomes immediately liquid at the exact opening of the release window instead of only the first infinitesimal slice. This is repeatable on any lockup contract instantiated with these crafted parameters.

### Likelihood Explanation
The attacker only needs to call the public, unprivileged `LockupFactory::create` with a self-chosen `lockup_timestamp` and `release_duration` whose sum exceeds `u64::MAX` nanoseconds, and the minimum attached deposit (`MIN_ATTACHED_BALANCE`). No foundation, owner, or multisig role is required — the caller becomes the `owner_account_id` of their own freshly-deployed lockup. This is fully attacker-controlled and deterministic once the two parameters are chosen; the exploit is testable purely with `get_locked_amount`.

### Recommendation
Reject lockups at construction time where `lockup_timestamp.checked_add(release_duration)` (or the equivalent for `transfers_timestamp + lockup_duration + release_duration`) would overflow `u64`, or perform the `end_timestamp`/`time_left` computation entirely in `U256` (as already done for the multiplication) so no saturation/truncation occurs before dividing by the original `release_duration`.

### Proof of Concept
```rust
// lockup/src/getters.rs unit test (add under #[cfg(test)])
#[test]
fn test_saturating_release_duration_underlocks() {
    let lockup_timestamp: u64 = u64::MAX - 100; // near max
    let release_duration: u64 = 1_000; // lockup_timestamp + release_duration overflows u64::MAX

    let lockup_amount: u128 = 1_000_000_000_000_000_000_000_000; // 1_000 NEAR

    let contract = LockupContract {
        lockup_information: LockupInformation {
            lockup_amount,
            termination_withdrawn_tokens: 0,
            lockup_duration: 0,
            release_duration: Some(release_duration),
            lockup_timestamp: Some(lockup_timestamp),
            transfers_information: TransfersInformation::TransfersEnabled {
                transfers_timestamp: lockup_timestamp.into(),
            },
        },
        vesting_information: VestingInformation::None,
        staking_information: None,
        foundation_account_id: None,
    };

    // Set block_timestamp exactly at lockup_timestamp: the release window has just opened,
    // zero time has elapsed, so unreleased amount MUST equal lockup_amount.
    testing_env!(VMContextBuilder::new()
        .block_timestamp(lockup_timestamp)
        .finish());

    let locked = contract.get_locked_amount().0;

    // Binding under test: locked == lockup_amount at t == lockup_timestamp.
    assert_eq!(
        locked, lockup_amount,
        "Locked amount dropped below full lockup_amount immediately at release start due to saturating_add overflow: got {}, expected {}",
        locked, lockup_amount
    );
}
```
Running this test demonstrates `locked < lockup_amount` (the assertion fails), confirming that `unreleased_amount` is deflated purely due to the `saturating_add` overflow in `end_timestamp` combined with dividing by the un-clipped `release_duration`.

/// Contains information about token lockups.
#[derive(BorshDeserialize, BorshSerialize)]
pub struct LockupInformation {
    /// The amount in yocto-NEAR tokens locked for this account.
    pub lockup_amount: Balance,
    /// The amount of tokens that were withdrawn by NEAR foundation due to early termination
    /// of vesting.
    /// This amount has to be accounted separately from the lockup_amount to make sure
    /// linear release is not being affected.
    pub termination_withdrawn_tokens: Balance,
    /// [deprecated] - the duration in nanoseconds of the lockup period from
    /// the moment the transfers are enabled. During this period tokens are locked and
    /// the release doesn't start. Instead of this, use `lockup_timestamp` and `release_duration`
    pub lockup_duration: Duration,
    /// If present, it is the duration when the full lockup amount will be available. The tokens
    /// are linearly released from the moment tokens are unlocked, defined by:
    /// `max(transfers_timestamp + lockup_duration, lockup_timestamp)`.
    /// If not present, the tokens are not locked (though, vesting logic could be used).
    pub release_duration: Option<Duration>,
    /// The optional absolute lockup timestamp in nanoseconds which locks the tokens until this
    /// timestamp passes. Until this moment the tokens are locked and the release doesn't start.
    /// If not present, `transfers_timestamp` will be used.
    pub lockup_timestamp: Option<Timestamp>,
    /// The information about the transfers. Either transfers are already enabled, then it contains
    /// the timestamp when they were enabled. Or the transfers are currently disabled and
    /// it contains the account ID of the transfer poll contract.
    pub transfers_information: TransfersInformation,
}
