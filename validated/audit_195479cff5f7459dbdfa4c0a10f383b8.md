### Title
Tranche holder can front-run `stopEpoch`/`getInstantWithdrawFunds` with dust withdraw requests to block epoch settlement or force a spurious borrower default - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
This is the same griefing class as the Muon nonce front-run: an unprivileged user watches the mempool for a privileged settlement transaction whose execution-time preconditions/amounts were computed against an older state, and invalidates it with a near-free state change. Here the privileged transaction is the manager's `stopEpoch`/`getInstantWithdrawFunds`, and the cheap invalidation is `requestWithdraw` with a dust amount while instant withdrawals are enabled.

### Finding Description
`_stopEpoch` hard-reverts if any instant-withdraw basis is still pending:

- `IdleCDOEpochVariant.sol:338-351` — `_checkNotAllowed(... || _pendingInstant() != 0 || ...)` inside `_stopEpoch`.
- `IdleCreditVault.sol:356-375` — `requestInstantWithdraw` burns the caller's strategy tokens, mints an equal claimable receipt, and increments `pendingInstantWithdraws`. The requester loses nothing economically (the receipt is later redeemable at par via `claimInstantWithdrawRequest`, `IdleCreditVault.sol:380-393`), so the attack costs only gas plus a temporary receipt.
- `IdleCDOEpochVariant.sol:558-573` — `getInstantWithdrawFunds` pulls `_pendingInstant()` from the borrower via `transferFrom`; the catch path calls `_handleBorrowerDefault`.
- `IdleCDOEpochVariant.sol:577-599` — `_handleBorrowerDefault` sets `defaulted = true`, pauses the pool, stops the epoch, and disables withdraw requests.

Attack flow:

1. Pool is in a running epoch with instant withdrawals enabled; borrower has approved `getFundsFromBorrower` (or manager intends to call `getInstantWithdrawFunds` for a computed amount).
2. Attacker (any KYC'd tranche holder) sees the manager's `stopEpoch` in the mempool and front-runs it with `cdoEpoch.requestWithdraw(dust, AAtranche)`/`requestWithdraw` routed to the instant path. `pendingInstantWithdraws` becomes non-zero and `stopEpoch` reverts on the `_pendingInstant() != 0` check.
3. The manager's fallback is `getInstantWithdrawFunds`, which pulls exactly `pendingInstantWithdraws` at execution time. If the borrower's allowance to the CDO was sized for the previously observed amount, the front-run dust request makes `transferFrom` revert, the catch block fires, and the pool enters `_handleBorrowerDefault` even though the borrower is solvent — a wrongful default.
4. Even without the allowance shortfall, the attacker can repeat step 2 each time the manager clears instant requests and retries `stopEpoch`, indefinitely delaying epoch settlement at gas-only cost.

### Impact Explanation
Two distinct impacts:

- Temporary freezing of all user funds: every `stopEpoch` reverts while `_pendingInstant() != 0`, so the epoch cannot close, interest cannot be accrued, and pending normal withdraw receipts cannot be funded (`collectWithdrawFunds` is only reached inside a successful stop). All tranche holders' funds stay locked for as long as the attacker wins the ordering race — griefing cost is gas-only since the dust receipt is redeemable at par.
- Wrongful borrower default: if `getFundsFromBorrower` reverts on an under-sized allowance inside `getInstantWithdrawFunds` or `stopEpoch` (`_amountToPullFromBorrower + _pendingWithdraws`, `IdleCDOEpochVariant.sol:408`), `defaulted` is set and the pool is paused, pushing all claimants into the recovery/haircut path (`defaultRecoveryPrice`) even though the borrower did not actually fail to pay.

### Likelihood Explanation
Requires instant withdrawals enabled on the variant and a tranche position (KYC'd lender — in-scope unprivileged role). The attacker only needs to observe `stopEpoch`/`getInstantWithdrawFunds` in the public mempool and submit a dust request; on L2s with public mempools this is cheap and repeatable. The default-forcing variant additionally depends on the borrower's allowance being sized to the exact expected pull rather than unlimited — an operational detail the attacker can often observe on-chain before attacking.

### Recommendation
- Record instant-withdraw basis at a snapshot point (e.g., `instantWithdrawDeadline`) rather than reading the live `pendingInstantWithdraws` in `stopEpoch`, or treat requests submitted after the deadline as next-epoch requests that do not block settlement.
- In `getInstantWithdrawFunds`/`stopEpoch`, do not treat an ERC20 `transferFrom` failure (allowance/balance) identically to a borrower refusal — distinguish `onStopEpoch`/`transferFrom` revert reasons, or pull `min(pending, allowance/balance)` before declaring default.
- Optionally add a minimum instant-withdraw amount or a per-epoch request cutoff to raise the griefing cost.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers `_startEpochAndCheckPrices`, `_depositWithUser`):

```solidity
function testFrontRunStopEpochGrief() external {
    // enable instant withdrawals with a delay < epoch duration
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    address attacker = makeAddr('attacker');
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);              // pool liquidity
    _depositWithUser(attacker, amount, true); // attacker gets AA tranches
    uint256 attackerTranches = IERC20Detailed(address(AAtranche)).balanceOf(attacker);

    _startEpochAndCheckPrices(0);

    // epoch ends; manager calls stopEpoch
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // attacker front-runs: dust instant withdraw request keeps pendingInstant != 0
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche));
    assertGt(strategy.pendingInstantWithdraws(), 0);

    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0); // reverts on _pendingInstant() != 0

    // manager tries getInstantWithdrawFunds; borrower approved only the pre-front-run amount (0)
    // or exactly the observed pending -> dust inflates pull -> transferFrom reverts -> default
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();     // catch -> _handleBorrowerDefault
    assertTrue(cdoEpoch.defaulted());        // wrongful default
}
```

The second leg assumes the borrower's allowance to the CDO does not cover the extra dust; if it does, the attacker simply repeats the dust request after the pull and before the retried `stopEpoch`, sustaining the freeze.
