## Finding

### Title
Node-side `StackerDBListener` double-counts a signer's weight in both `total_weight_rejected` and `total_weight_approved` when the signer switches its vote from reject to accept, causing the mining coordinator to spuriously abandon a block that has (or will) reach real consensus - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The `StackerDBListener` on the mining node tallies signer weight for a proposed block into two independent counters, `total_weight_approved` and `total_weight_rejected`, gated by two *different* membership sets. A signer that legitimately changes its vote from `Rejected` to `Accepted` — an explicitly supported transition in the signer state machine (`LocallyRejected -> LocallyAccepted`) — has its weight added to `total_weight_approved` without its earlier contribution ever being subtracted from `total_weight_rejected`. This breaks the aggregated-weight-vs-verified-accepts equality that `SignerCoordinator::start_waiting_for_signatures` relies on to decide whether a block is dead ("globally rejected") or complete ("globally accepted"), and the rejection check is evaluated first, so it can wrongly declare the block rejected.

### Finding Description
`BlockStatus` in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` tracks per-block vote state: [1](#0-0) 

On receiving a `BlockResponse::Accepted`, the weight is only added if the slot is not yet present in `gathered_signatures`: [2](#0-1) 

On receiving a `BlockResponse::Rejected`, the weight is only added if `responded_signers.insert(slot_id)` returns `true` (i.e., first response ever): [3](#0-2) 

These two guards use different sets (`gathered_signatures` vs `responded_signers`), and neither branch removes a signer's weight from the *other* counter when the vote changes:

- Reject → Accept: `responded_signers` already contains the slot (added during the reject), but the Accepted branch never checks `responded_signers` — it only checks `gathered_signatures`, which is still empty for that slot. So the weight is added to `total_weight_approved` *in addition to* the weight already counted in `total_weight_rejected`. The signer's weight is now counted on both sides simultaneously, and `total_weight_rejected` is never decremented.
- Accept → Reject: correctly protected, because `responded_signers.insert(slot_id)` (already present from the earlier accept) returns `false`, so the Rejected branch's weight increment is skipped.

This is asymmetric handling of vote revision, and the resulting inflated `total_weight_rejected` is exactly the quantity `SignerCoordinator::start_waiting_for_signatures` uses to decide the block is dead, checked *before* the acceptance-threshold branch: [4](#0-3) 

By contrast, the individual signer's own bookkeeping in `signerdb.rs` does correctly retract a stale rejection once a signature for the same address is later recorded (verified by the existing regression test `reject_then_accept`): [5](#0-4) 

...and the signer protocol explicitly allows and expects vote revision from reject to accept as conditions change: [6](#0-5) 

So the *signer-side* ground truth ("this signer's current opinion") is correctly revocable, but the *node-side coordinator's aggregate* is not — the two views of "who has rejected this block" diverge, and the coordinator's stale, inflated `total_weight_rejected` can trip the `>30%`-blocking-minority check even when the true, current set of rejecting signers no longer supports it (because one or more of them already flipped to accepting).

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality that the coordinator depends on to decide block life/death. Concretely: a block that a signer initially rejected (e.g., because a rival tenure/proposal briefly looked live) and then legitimately re-evaluated and accepted once the rival went stale — a normal, sanctioned state transition per the signer flow — leaves stale weight counted against it forever in the node's tally. If that stale weight, combined with genuine current rejections, pushes `total_weight_rejected` over the blocking-minority threshold, `SignerCoordinator::start_waiting_for_signatures` returns `Err(NakamotoNodeError::SignersRejected{..})` even though the signer set's *actual current* votes may already meet or be about to meet the 70% acceptance threshold. This wastes the block-production round (miner must discard the block and re-propose), and if the same reject→accept pattern recurs across proposals (e.g., during a chain-tip race that gets resolved slowly), it can repeatedly stall block production — a protocol availability/liveness impact, without requiring a majority of malicious signers or key compromise.

### Likelihood Explanation
No malicious signer is required — the flip from reject to accept is an explicitly documented, legitimate transition (`LocallyRejected -> LocallyAccepted : re-evaluated`) that happens whenever a signer's earlier rejection reason becomes stale (e.g., a conflicting/rival block it saw dies out). Any block proposal race or reorg-adjacent scenario naturally produces early rejections followed by later acceptances from the same signers, so a single-slot miner does not need any special capability beyond normal proposal/gossip timing to trigger this path; it is a bookkeeping bug on the node side that fires under ordinary operating conditions.

### Recommendation
Track per-signer current vote state (e.g., a `HashMap<u32, VoteKind>` or by removing the slot's weight from `total_weight_rejected` whenever an `Accepted` message supersedes a prior `Rejected` for the same slot, mirroring what `signerdb.rs`'s `add_block_signature`/rejection-clearing logic already does for the signer-side state). The Accepted branch should check (and, if present, retract from) `total_weight_rejected` — not just add to `total_weight_approved` — whenever the slot was previously counted as a rejection, and vice versa, so `total_weight_approved` and `total_weight_rejected` always reflect each signer's most recent vote exactly once.

### Proof of Concept
1. Miner proposes block `B`. Two signers, `S1` (weight 40) and `S2` (weight 40), out of `total_weight = 100`, `weight_threshold = 70` (so blocking minority = 30).
2. `S1` initially sees a rival block as live and sends `BlockResponse::Rejected` for `B`. `stackerdb_listener` records: `responded_signers = {S1}`, `total_weight_rejected = 40`.
3. Shortly after, the rival dies out; per the signer's own re-evaluation logic, `S1` legitimately flips to `BlockResponse::Accepted` for `B` (an explicitly supported `LocallyRejected -> LocallyAccepted` transition).
4. In `stackerdb_listener.rs`'s Accepted handler, `gathered_signatures.contains_key(&S1_slot)` is `false` (this is `S1`'s first *acceptance*), so `total_weight_approved` becomes `40` — while `total_weight_rejected` is never decremented and stays at `40`.
5. `S2` (weight 40, genuinely still opposed) sends `BlockResponse::Rejected`. `responded_signers.insert(S2_slot)` succeeds (first response), so `total_weight_rejected = 40 + 40 = 80`.
6. `SignerCoordinator::start_waiting_for_signatures` evaluates `total_weight_rejected (80) + weight_threshold (70) > total_weight (100)` → true → returns `Err(SignersRejected)`, discarding block `B` — even though the *actual current* opinion is only `S2` (weight 40) rejecting, i.e., only 40/100, well under the 30% blocking minority, and `S1`'s accept (40) plus any further accepts could still reach 70% consensus had the tally been correct.
