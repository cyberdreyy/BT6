### Title
Zip Slip path traversal in ExtractZipArchive allows cross-project file write and arbitrary Lchown via crafted cache/artifact zip - (File: helpers/archives/zip_extract.go, helpers/archives/zip_extra_unix.go)

### Summary
`extractZipFile`/`extractZipFileEntry` in `helpers/archives/zip_extract.go` use `file.Name` from the zip `FileHeader` directly in `os.MkdirAll`, `os.OpenFile`, `os.Symlink`, and `os.Mkdir` calls with no path-traversal sanitization, and `ExtractZipArchive` subsequently calls `processZipExtra` → `processZipUIDGidField` (`helpers/archives/zip_extra_unix.go`), which calls `os.Lchown(file.Name, UID, GID)` on the same unsanitized name. The only existing check, `errorIfGitDirectory`, only blocks names beginning with `.git` and does nothing to prevent `../` traversal.

### Finding Description
`ExtractZipArchive` (`helpers/archives/zip_extract.go:85-110`) iterates `archive.File` and for each entry calls `extractZipFile(file)`, which does:
- `os.MkdirAll(filepath.Dir(file.Name), 0o777)` (`zip_extract.go:63`)
- `os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, ...)` in `extractZipFileEntry` (`zip_extract.go:41-59`)
- `os.Symlink(string(data), file.Name)` in `extractZipSymlinkEntry` (`zip_extract.go:22-39`)
- `os.Mkdir(file.Name, ...)` in `extractZipDirectoryEntry` (`zip_extract.go:12-20`)

None of these paths call `filepath.Clean`, reject absolute paths, or verify the resolved path stays within the extraction root. The single guard applied, `errorIfGitDirectory` (`path_check_helper.go:13-19`), only checks whether the first path segment equals `.git`; it does not detect or block `..` segments anywhere in the path. This is the classic "Zip Slip" vulnerability pattern.

After all files are written, `ExtractZipArchive` runs a second loop (`zip_extract.go:98-107`) calling `lchmod(file.Name, ...)` and `processZipExtra(&file.FileHeader)`. `processZipExtra` (`zip_extra.go:96-122`) parses the entry's Extra field; if it finds a `ZipUIDGidFieldType` (`0x7875`) record, it calls `processZipUIDGidField` (`zip_extra_unix.go:37-49`), which parses attacker-supplied UID/GID and calls `os.Lchown(file.Name, UID, GID)` — again using the unsanitized, traversal-containing `file.Name`.

Exploit flow: an unprivileged job creates its own cache/artifact zip containing a `FileHeader.Name` such as `../../other-project/.git/config` (or any other path outside the job's working directory) with a crafted `ZipUIDGidField` extra record, and uploads it via `CacheArchiverCommand`/artifacts upload. When a victim job (or the same runner host on a later pipeline sharing the same cache key/artifact path or workspace layout) downloads and extracts it via `CacheExtractorCommand`/`ArtifactsDownloaderCommand` → `ExtractZipFile` → `ExtractZipArchive`, the runner will write the file outside the intended checkout/cache/artifact root and then `Lchown` it to an attacker-chosen UID/GID.

### Impact Explanation
This allows a job to write files (and change file ownership via `Lchown`) at arbitrary paths reachable by the runner process's filesystem permissions, outside the job's own workspace — e.g., overwriting another project's checkout files, cache state, or shared runner/helper files, and changing their ownership. This is a concrete violation of the invariant that a job must stay confined to its own workspace/artifacts.

### Likelihood Explanation
Feasible and repeatable: producing a zip with a traversal `FileHeader.Name` and a `ZipUIDGidFieldType` extra record only requires low-level use of `archive/zip`'s raw writer API (or manual byte construction), which is well within reach of any user who controls a CI job's cache/artifact contents. No special runner privileges are needed to create such a zip; the only precondition is that a victim job (or the runner) later extracts it. Actual cross-project impact depends on shared filesystem paths/permissions on the runner host (e.g., a shared build directory or writable location reachable via `..` from the job's `CI_PROJECT_DIR`), which constrains but does not eliminate exploitability in shared-runner deployments where job workspaces are siblings on the same filesystem.

### Recommendation
Sanitize every `file.Name` before use in `extractZipFile`/`extractZipFileEntry`/`extractZipDirectoryEntry`/`extractZipSymlinkEntry`: reject absolute paths, `filepath.Clean` the joined destination path, and verify (e.g., via `filepath.Rel` or prefix comparison) that the resulting absolute path remains within the extraction root before performing any `Mkdir`/`OpenFile`/`Symlink`/`Lchown`/`Chtimes`/`lchmod` operation. Apply the same containment check before `processZipUIDGidField`'s `os.Lchown` and `processZipTimestampField`'s `os.Chtimes` calls, since these also use `file.Name` directly.

### Proof of Concept
Go unit test in `helpers/archives`:
```go
func TestExtractZipArchive_RejectsPathTraversal(t *testing.T) {
    tmpDir := t.TempDir()
    origWd, _ := os.Getwd()
    require.NoError(t, os.Chdir(tmpDir))
    defer os.Chdir(origWd)

    var buf bytes.Buffer
    zw := zip.NewWriter(&buf)
    fh := &zip.FileHeader{Name: "../outside/evil.txt", Method: zip.Deflate}
    fh.SetMode(0o644)
    // append a ZipUIDGidField extra record
    var extra bytes.Buffer
    binary.Write(&extra, binary.LittleEndian, ZipExtraField{Type: ZipUIDGidFieldType, Size: 9})
    binary.Write(&extra, binary.LittleEndian, ZipUIDGidField{1, 4, 1000, 4, 1000})
    fh.Extra = extra.Bytes()
    w, err := zw.CreateHeader(fh)
    require.NoError(t, err)
    w.Write([]byte("payload"))
    zw.Close()

    r, err := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, err)
    _ = ExtractZipArchive(r)

    // Assert no file was created outside tmpDir
    _, err = os.Stat(filepath.Join(filepath.Dir(tmpDir), "outside", "evil.txt"))
    require.True(t, os.IsNotExist(err), "file must not be written outside extraction root")
}
```
Expected (current) result: the file is written outside `tmpDir` and the test fails, confirming the traversal and demonstrating that the `Lchown` call would also execute against the out-of-bounds path.
