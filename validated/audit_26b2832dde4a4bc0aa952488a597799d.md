### Title
Withdraw share-burn does not shrink to match vault-capped transfer amount, silently destroying user value under `TOKENLESS_REPAYMENTS_COMPLETE` - (File: programs/marginfi/src/instructions/marginfi_account/withdraw.rs)

### Summary
In the non-`withdraw_all` path of `lending_account_withdraw`, the number of asset shares burned from the user's balance is computed from the full requested/pre-clamp amount, but the actual token amount transferred out is later clamped down to whatever is actually available in the bank's liquidity vault when the bank is flagged `TOKENLESS_REPAYMENTS_COMPLETE`. The share burn is never recomputed to reflect the smaller, clamped amount.

### Finding Description
At [2](#0-1)  the function computes `amount_pre_fee` and immediately calls `bank_account.withdraw(I80F48::from_num(amount_pre_fee))`, which burns `share_amount` shares from the user's balance and decrements `bank.total_asset_shares` accordingly — this is a final, committed state mutation.

Only afterward, at [3](#0-2) , does the code check whether `bank.get_flag(TOKENLESS_REPAYMENTS_COMPLETE)` is set. If so, it re-derives `amount_pre_fee` as `u64::min(amount_pre_fee, actual)` where `actual` is the bank's real liquidity-vault token balance. This smaller, clamped `amount_pre_fee` is what is actually transferred to the user via `bank.withdraw_spl_transfer(...)` at [4](#0-3)  and what is emitted in `LendingAccountWithdrawEvent.amount` at [5](#0-4) , but the previously-burned `share_amount` is never adjusted to match.

This is structurally identical to the Hyperdrive `overestimatedProceeds` bug: an initial estimate (shares corresponding to full `amount_pre_fee`) is used to mutate accounting state, then a later correction (`min(amount_pre_fee, actual)`) discovers the estimate was too high, but the correction is applied only to the outgoing payment, not to the internal accounting delta that was already committed. The excess value (the difference between the shares burned and the shares that should have been burned for the actually-paid amount) is not credited back anywhere — it is destroyed rather than being clawed back or refunded, mirroring the "shareProceeds should be reduced by the overestimatedProceeds" recommendation from the report, applied in the opposite direction (shares should be *reduced* to match the actual, capped payout, or the deficit refunded).

### Impact Explanation
A user invoking a partial withdraw while their bank is in the `TOKENLESS_REPAYMENTS_COMPLETE` state (a bankruptcy/deleverage completion state, per the code comment "If in deleverage mode and deleverage is complete, you get what's left!") loses the difference between their requested withdrawal amount and the actual vault balance permanently: their book position is fully debited for the requested amount, but they are paid only the smaller `actual` amount, with no accounting adjustment (e.g., no re-crediting of the shortfall as a claim). This is a durable, direct loss of user funds/accounting integrity.

### Likelihood Explanation
This requires reaching the `TOKENLESS_REPAYMENTS_COMPLETE` bank state, which appears tied to bankruptcy/deleverage settlement flows (name suggests "tokenless repayments" have completed, i.e., some socialized-loss end-state). I could not fully confirm from the available index how commonly or easily this flag is set relative to a bank still holding less liquidity than users' book value — this needs further investigation via a Devin session with full repo access, but the code path is unconditionally reachable by any user calling the standard withdraw instruction once the flag and the low-liquidity condition co-occur.

### Recommendation
After computing the clamped `amount_pre_fee = u64::min(amount_pre_fee, actual)`, recompute (or partially reverse) the `share_amount`/shares burned so that the user's internal asset-share balance only decreases by the amount corresponding to what is actually paid out; the remainder should either remain as a claim on the user's balance or be handled via an explicit, accounted write-down (e.g., routed to `collected_insurance_fees_outstanding` or a similar bad-debt bucket, as is done elsewhere in `withdraw_all`/`close_balance`), rather than silently vanishing from both the user's and the bank's books.

### Proof of Concept
1. Bring a bank into the `TOKENLESS_REPAYMENTS_COMPLETE` state (post-bankruptcy/deleverage settlement) where its liquidity vault balance is less than the sum of remaining users' book asset value.
2. As a user with a large book balance, call `lending_account_withdraw` (non-`withdraw_all`) requesting `amount` such that `amount_pre_fee` (computed at line 128) exceeds the vault's actual balance.
3. Observe: `bank_account.withdraw(amount_pre_fee)` burns shares for the full `amount_pre_fee` at line 128.
4. The subsequent clamp at line 141 reduces the transferred amount to `actual`, but no shares are restored.
5. Compare emitted `LendingAccountWithdrawEvent.amount` (the clamped, smaller value) against the shares burned (corresponding to the larger, pre-clamp value) to confirm the user's book position was debited more than they were paid.
