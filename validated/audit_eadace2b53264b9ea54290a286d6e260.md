### Title
APR0 withdraw receipt escapes `stopEpochWithDuration` loss haircut via settlement during a later `requestWithdraw` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug drops a temporary reference before unlinking a queued socket, so the final queue reference frees the object while it is still used. The analog in `IdleCreditVault` is the same shape: the guard that pins a loss-adjusted receipt to its epoch (`apr0Users[_user].principalEpoch == lossEpoch`) only watches the *open* APR0 bucket. `_requestWithdrawApr0` calls `_settleApr0`, which moves `principal` into `settledPrincipal`/`settledInterest` and zeroes `principalEpoch` — i.e., it drops the epoch "reference" before the new request is linked — so the loss-epoch guard in `requestWithdraw` is bypassed and the haircut receipt is later paid at par.

### Finding Description
`requestWithdraw` blocks a user from opening a new request while they hold an unclaimed loss-adjusted receipt from epoch `lossEpoch = lastWithdrawRequest[_user]`: [1](#0-0) 

The APR0 side of that check inspects `apr0Users[_user].principal != 0 && apr0Users[_user].principalEpoch == lossEpoch`. However, when `unscaledApr == 0`, a new request routes into `_requestWithdrawApr0`, which first calls `_settleApr0`: [2](#0-1) 

`_settleApr0` moves `principal` to `settledPrincipal`, converts the per-epoch rate into `settledInterest`, and clears `principal`/`principalEpoch`: [3](#0-2) 

So the sequence inside one `requestWithdraw` call is: (1) guard evaluates `apr0Users.principal == 0` after settlement (or the guard runs before settlement — either way `withdrawsRequestsByEpoch[_user][lossEpoch]` is never written for APR0 requests, since the APR0 branch skips it, and `principal`/`principalEpoch` are cleared by settlement), (2) `lastWithdrawRequest[_user]` is overwritten to the new epoch, (3) the loss-epoch receipt survives only as untagged `settledPrincipal`/`settledInterest`.

Later, `claimWithdrawRequest` resolves the loss claim via `_claimLossAdjustedWithdrawRequest`, which looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — now the *new* epoch, where price is 0 — and falls through to `_claimFundedWithdrawRequest`, which pays `settledPrincipal + settledInterest` at par: [4](#0-3) [5](#0-4) 

Note the guard comment in `requestWithdraw` states the intent ("A loss-adjusted receipt must be claimed before opening a later request, otherwise `lastWithdrawRequest` would stop pointing to the epoch that stores its haircut"), but it does not cover the settled APR0 bucket.

### Impact Explanation
When `stopEpochWithDuration`/`collectWithdrawFunds` funds pending receipts below `pendingWithdraws`, it stores `lossRecoveryPriceByEpoch[epochNumber]` and only pulls `_amount < pendingBasis` underlying: [6](#0-5) 

An attacker holding an APR0 receipt from that epoch is owed `basis * lossRecoveryPrice`, but by re-requesting before claiming they receive `settledPrincipal + settledInterest` at par from `_transferFundedClaim`. The excess `basis * (1 - lossRecoveryPrice)` is paid out of underlying that belongs to active LPs/other claimants — a direct loss-waterfall escape and theft of the difference, proportional to their APR0 principal and the realized loss ratio.

### Likelihood Explanation
Requirements: `unscaledApr == 0` mode (APR0 pools are a supported configuration), an epoch ending with a partial `collectWithdrawFunds` funding (realized borrower shortfall without full default — honest manager/borrower sequence), and the attacker simply calls `cdoEpoch.requestWithdraw` again instead of claiming. No privileged collusion needed; the attacker is an ordinary KYC'd lender. The path is deterministic once a loss epoch exists.

### Recommendation
In `requestWithdraw`'s loss-receipt guard, also revert when `apr0Users[_user].settledPrincipal != 0` or `settledInterest != 0` attributable to `lossEpoch` — or simpler, tag the settled bucket with its epoch (e.g., keep a `settledEpoch` field) so the haircut can still be applied. Alternatively, apply `lossRecoveryPriceByEpoch` inside `_settleApr0`/`_claimFundedWithdrawRequest` to settled amounts whose request epoch has a recorded loss price, mirroring `_withdrawClaimAmountsForEpoch`.

### Proof of Concept
Foundry fork scenario (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// APR0 mode
cdoEpoch.setIsAYSActive(false);              // owner
IdleCreditVault(address(strategy)).setAprs(0, 0); // manager

// 1. Attacker deposits and requests withdraw in epoch 0 (buffer phase)
uint256 amt = 10_000 * ONE_SCALE;
_depositWithUser(attacker, amt, true);
vm.prank(attacker);
uint256 basis = cdoEpoch.requestWithdraw(0, address(AAtranche));

// 2. Epoch 0 runs; borrower returns only part of pendingWithdraws.
//    Manager calls stopEpochWithDuration -> collectWithdrawFunds(partial)
//    => lossRecoveryPriceByEpoch[0] = 0.5e18 (say)
_startEpochAndCheckPrices(0);
// ... borrower repays partial amount ...
// cdoEpoch.stopEpochWithDuration(...)/collectWithdrawFunds(partial)
assertGt(IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(0), 0);

// 3. Attacker does NOT claim. In epoch 1 buffer, requests again.
//    _requestWithdrawApr0 -> _settleApr0 clears principal/principalEpoch,
//    guard sees apr0Users.principal == 0 and passes.
vm.prank(attacker);
cdoEpoch.requestWithdraw(0, address(AAtranche)); // must hold tranche tokens for 2nd request

// 4. After epoch 1 stops and is funded, attacker claims once.
//    _claimLossAdjustedWithdrawRequest looks up
//    lossRecoveryPriceByEpoch[lastWithdrawRequest == 1] == 0 -> skipped.
//    _claimFundedWithdrawRequest pays settledPrincipal + settledInterest at par.
_startEpochAndCheckPrices(1);
_stopEpochAndCheckPrices(1, 0, /* funded */ );

uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();

// Received basis + interest at par instead of basis * 0.5
uint256 stolen = basis / 2; // haircut avoided
assertGe(underlying.balanceOf(attacker) - balPre, basis);
```

Key assertion to encode: `IdleCreditVault(address(strategy)).apr0Users(attacker)` shows `settledPrincipal == basis` while `lossRecoveryPriceByEpoch[0] != 0` was never applied, and the strategy's underlying balance is drained by `basis * (1 - lossRecoveryPrice)` more than the haircut schedule allows, shortchanging remaining claimants.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _settleApr0(address _user) internal {
    Apr0UserData storage _apr0User = apr0Users[_user];
    uint256 _principal = _apr0User.principal;
    if (_principal == 0) {
      return;
    }
    uint256 _reqEpoch = _apr0User.principalEpoch;
    // Settle only after stopEpoch bumped epochNumber (ie after one full wait epoch).
    if (_reqEpoch >= epochNumber) {
      return;
    }
    // Move principal from "open APR0 bucket" to "settled bucket" (same principal, not duplicated).
    _apr0User.settledPrincipal += _principal;
    uint256 _rate = apr0RateByEpoch[_reqEpoch];
    if (_rate != 0) {
      // Convert per-epoch rate to claimable underlying interest.
      _apr0User.settledInterest += (_principal * _rate) / 1e18;
    }
    _apr0User.principal = 0;
    _apr0User.principalEpoch = 0;
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
