### Title
BridgeCreated audit log entry omits caller/session identifier, preventing attribution of state-changing bridge-create actions - ([File: core/web/bridge_types_controller.go])

### Finding Description
`BridgeTypesController.Create` authenticates the caller through the standard `auth.Authenticate` middleware, which sets the authenticated user on the gin context via `c.Set(auth.SessionUserKey, &user)`, retrievable through `auth.GetAuthenticatedUser(c)`. [1](#0-0)  Despite the authenticated user being available in the request context, the audit log call in `Create` only records `bridgeName`, `bridgeConfirmations`, `bridgeMinimumContractPayment`, and `bridgeURL` — with no user/session/email field: [2](#0-1) . This is inconsistent with other controllers in the same codebase that do include the acting principal in their audit data, e.g. `UserController.UpdatePassword` includes `"user": user.Email` and `SessionsController.Destroy` includes `"sessionID"` [3](#0-2) [4](#0-3) .

### Impact Explanation
This is a logging/forensics completeness gap, not an authorization or authentication bypass. `ValidateBridgeTypeNotExist` already prevents two callers from creating a bridge with the exact same name — a duplicate `bridgeName` insert fails with a JSON API error before the audit call is reached [5](#0-4) , so the "colliding bridge names / cross-user token takeover" premise in the question does not hold as stated; it is not achievable through this endpoint alone. What remains is a genuine but narrower issue: if incident response needs to determine which authenticated principal issued a specific `BridgeCreated` event (e.g., during a post-hoc investigation of a bridge configuration that turned out to be malicious or mistaken), the audit entry alone cannot answer that question, whereas correlating with the HTTP access log / session store could still recover it externally. This does not itself grant unauthorized access, expose secrets, or allow one authenticated user to act as another — it only weakens auditability/attributability of an already-authorized action.

### Likelihood Explanation
Any caller holding bridge-create privilege (edit or admin role via `RequiresEditRole`, per the router wiring of this endpoint referenced in `core/web/router.go`) triggers this on every successful bridge creation, so the missing-identifier condition is deterministic and always reproducible — but it depends on the reviewer/operator needing to distinguish requesters purely from the audit stream, which is an operational/forensic limitation rather than an exploitable attack path reachable by an unprivileged/external attacker.

### Recommendation
Include the authenticated principal in the audit payload for consistency with other controllers, e.g., pull the user via `auth.GetAuthenticatedUser(c)` (or the equivalent session/API-token identity) and add a `"user"` or `"requestedBy"` field to the `audit.BridgeCreated`, `audit.BridgeUpdated`, and `audit.BridgeDeleted` calls in `core/web/bridge_types_controller.go`.

### Proof of Concept
Go handler-level test plan (`core/web/bridge_types_controller_test.go`):
1. Instantiate a mocked `audit.AuditLogger` (already used elsewhere, e.g. `audit.NoopLogger`/mock) and inject via `App.GetAuditLogger()`.
2. Perform `POST /v2/bridge_types` with an authenticated session/API token for `userA`.
3. Assert the mock's `Audit(audit.BridgeCreated, data)` call args: `data["bridgeName"]` is present but no key equivalent to `user`/`email`/`sessionID` exists in `data`, confirming the gap.
4. Optionally repeat with `userB` (different session) creating a different bridge and confirm both `BridgeCreated` audit entries are indistinguishable except by `bridgeName`, demonstrating that log-based attribution relies solely on the bridge name rather than the caller identity.
