## Title
Gas subtraction underflow starving `new` on `multisig-factory::create` with no failure-recovery callback, permanently stranding the attached deposit - (File: `multisig-factory/src/lib.rs`)

## Summary
`MultisigFactory::create` computes `env::prepaid_gas() - CREATE_CALL_GAS` and passes the result directly as the gas budget for the `new` call in a single batched promise (`create_account`, `deploy_contract`, `transfer`, `function_call`), with no callback to verify success and no refund path. [1](#0-0)  If a caller supplies `prepaid_gas` at or below `CREATE_CALL_GAS`, or a value only marginally above it, the `new` call either fails the gas subtraction/budget check or is starved of gas and fails to write state, while the deposit already handed to the batched receipt cannot be recovered because the factory exposes no refund/callback logic, unlike its siblings.

## Finding Description
The binding that should hold is: for any `create` call, either the multisig account ends up fully initialized (state written by `new`) and holds the deposit, **or** the deposit is returned to the caller — i.e. `deposit_transferred == deposit_returned_or_initialized`. `multisig-factory::create` breaks this because it batches `create_account().deploy_contract(CODE).transfer(deposit).function_call("new", ..., env::prepaid_gas() - CREATE_CALL_GAS)` into one receipt and returns that `Promise` with no `.then()` callback, unlike `lockup-factory::create` and `staking-pool-factory::create_staking_pool`, which both attach an `on_*_create` callback that calls `is_promise_success()` and refunds `attached_deposit` to the predecessor if the `new` call failed. [2](#0-1) [3](#0-2) 

In `multisig-factory`, if `new` fails — whether from the gas subtraction underflowing/being starved, or from any other failure of `new` (e.g. `members.len() < num_confirmations` per the `assert` in `multisig2::new`) — the whole batched receipt's outcome is treated as a failure and there is no compensating logic to move the deposit back to the caller. [4](#0-3)  Since the deposit is attached to the original `#[payable] create` call (added to the factory account's own balance) and the factory contract has no owner, no withdraw method, and no other code path to move funds out, any deposit that fails to reach a successfully-initialized multisig is stranded permanently on the factory account. This matches the "half-initialized multisig / frozen funds" concern in the question, though the root issue is the missing refund callback rather than the raw underflow arithmetic alone.

Regarding the specific underflow mechanic: whether `env::prepaid_gas() - CREATE_CALL_GAS` panics (if `overflow-checks` were enabled) or wraps to a huge `u64` (release default), either the WASM execution panics or the runtime rejects the resulting function-call gas as exceeding the receipt's gas budget — both abort the `create` execution before any receipt is committed, so genuinely no half-initialized account is created from underflow *specifically*. The realistic exploitable path is instead a **low, non-underflowing** remainder of gas (`prepaid_gas` slightly above `CREATE_CALL_GAS`) that is insufficient for `new` to complete, letting `create_account`/`deploy_contract`/`transfer` succeed while `new` runs out of gas mid-execution and never writes contract state (the struct uses `PanicOnDefault`, so an uninitialized account with deployed code and a transferred deposit is left behind, and I could not fully verify from the available tests whether the whole receipt is then reported as failed or whether the earlier actions are considered committed independently — this determines whether the deposit is stuck in the new account instead of the factory).

## Impact Explanation
If the batched receipt fails as a unit, the caller's deposit remains on the factory contract's balance with no path to reclaim it — funds are frozen permanently, matching the Critical impact category. If instead the earlier actions (create_account/deploy/transfer) are committed independently of the failing `function_call`, the deposit lands on an uninitialized (`PanicOnDefault`) multisig account, and since `new` is a public `#[init]` method with no owner check, *anyone* (attacker or otherwise) could subsequently call `new` on that account to become its sole member and later drain the stranded deposit via `confirm`. Either way, the caller who attached the deposit loses control of it. This is only "attacker gain at another party's expense" if a victim (not the attacker) is the one who calls `create` and ends up on the losing side — the attacker cannot force a victim's own transaction to use insufficient gas, so this is primarily a footgun for a genuine user rather than a directly attacker-triggerable theft from a third party.

## Likelihood Explanation
The precondition (a `create` call with `prepaid_gas` close to or below `CREATE_CALL_GAS`) is entirely under the caller's own control — an attacker can trigger this failure mode cheaply and repeatably against their **own** deposit, but cannot force another account's transaction to under-provision gas. Absent evidence that a victim is coerced into calling `create` with insufficient gas, the "unprivileged attacker profits from someone else's funds" framing in the question is not demonstrated by the available code; what is demonstrated is a design gap (missing refund callback) that a careless legitimate user could self-inflict.

## Recommendation
Add a `.then()` callback to `multisig-factory::create` analogous to `on_staking_pool_create`/`on_lockup_create`: check `is_promise_success()`, and if `new` failed, refund `env::attached_deposit()` back to `env::predecessor_account_id()`. Additionally, assert `env::prepaid_gas() > CREATE_CALL_GAS` (and require a sane minimum remainder) before performing the subtraction, so under-funded calls fail fast in the factory's own execution rather than producing an ambiguous partially-applied receipt.

## Proof of Concept
Not reproducible as a clear-cut theft-from-a-third-party scenario from the code alone. A `near-workspaces`/`near-sdk-sim` test could demonstrate the self-inflicted freeze:
1. Deploy `multisig-factory` and `multisig2` WASM.
2. Call `create(name, members, num_confirmations)` with `attached_deposit = N` and `prepaid_gas` set to `CREATE_CALL_GAS + small_amount` (small enough to starve `new`).
3. Assert: `name.factory` account exists (`create_account`/`deploy_contract`/`transfer` succeeded) — e.g. query its balance and code hash.
4. Assert: calling any view/state-reading method (e.g. `get_num_confirmations`) on `name.factory` panics ("not initialized"), proving `new` never wrote state.
5. Assert: the caller's balance after the call is `initial_balance - N` (deposit not returned) and there is no method on `multisig-factory` to reclaim it — demonstrating the stuck-funds invariant break, with the missing-callback root cause rather than the underflow arithmetic per se.

    /// Callback after a staking pool was created.
    /// Returns the promise to whitelist the staking pool contract if the pool creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
