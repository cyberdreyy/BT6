`getSupply` JSON-RPC handler underflows on unchecked subtraction between capitalization and non-circulating supply - (File: rpc/src/rpc.rs)

### Summary
The `getSupply` RPC method computes `circulating` supply with a plain, non-saturating subtraction `total_supply - non_circulating_supply.lamports` [1](#0-0) , whereas the functionally identical computation used by the `/v0/circulating-supply` REST endpoint explicitly guards the same subtraction with `saturating_sub` [2](#0-1) . This is the same bug class as the external report: an assumed-safe subtraction of two related magnitudes without an invariant check or defensive arithmetic, reachable by any unprivileged caller through a JSON-RPC method.

### Finding Description
`get_supply` in `JsonRpcRequestProcessor` (exposed as the `getSupply` JSON-RPC method) reads `total_supply` from `bank.capitalization()` and `non_circulating_supply.lamports` from `calculate_non_circulating_supply`, which sums `bank.get_balance(pubkey)` over a `HashSet<Pubkey>` built from a hard-coded non-circulating account list plus stake accounts matched by lockup/withdraw-authority predicates [3](#0-2) . The result is then subtracted with plain `u64` subtraction:

```rust
circulating: total_supply - non_circulating_supply.lamports,
``` [4](#0-3) 

The invariant relied upon — that the sum of a subset of account balances never exceeds `bank.capitalization()` — is only true if `capitalization` is always perfectly synchronized with every account's lamport balance at the exact bank snapshot used for both computations. `non_circulating_supply` is computed asynchronously via `self.calculate_non_circulating_supply(&bank)`, which internally does `spawn_blocking` and performs an accounts-db scan [5](#0-4) , while `total_supply` is read synchronously immediately afterward on the (immutable, frozen) `bank` reference. Any place where this invariant is not provably enforced by the type system (i.e., not using `checked_sub`/`saturating_sub`) is a latent panic vector, exactly analogous to the reported `totalAmountToSplit` underflow in `OracleFeeDistributor`, where an assumption about relative magnitudes silently broke down under certain configurations.

The fact that the exact same subtraction is written defensively (`saturating_sub`) in the parallel `/v0/total-supply` / `/v0/circulating-supply` REST code path [2](#0-1)  but not in the JSON-RPC `getSupply` handler indicates an inconsistent/missed hardening — the same signal pattern the external report calls out (a missing invariant-enforcing check at one of several call sites that assume the same relationship).

### Impact Explanation
If `non_circulating_supply.lamports` ever exceeds `total_supply` for the bank snapshot used (e.g., due to a race between the async scan and a concurrently advancing bank/capitalization update, or any future change that adds an account to the non-circulating set without a corresponding capitalization guarantee), the subtraction panics. Since this arithmetic executes directly inside the request-handling task spawned by `jsonrpc_core`'s `MetaIoHandler`/tokio runtime for `getSupply`, a panic here would abort that request-handling thread; depending on panic-hook/threading configuration in the RPC runtime this can degrade or crash the JSON-RPC service for a public, unauthenticated `getSupply` call — a query-triggered validator/RPC-process condition, not merely bad output.

### Likelihood Explanation
The likelihood is lower than the original report because, under normal single-threaded synchronous bookkeeping, `capitalization()` should always be greater than or equal to any subset-of-accounts balance sum for the *same* bank state. However, `calculate_non_circulating_supply` and the read of `bank.capitalization()` are not part of one atomic operation — the scan runs on a background thread via `spawn_blocking` — introducing at least a theoretical window and, more importantly, a clear code-hygiene divergence from the parallel path that already anticipated and guarded against this exact edge case with `saturating_sub`. I could not find a proof that a concrete external input (e.g., crafted stake-account data) can force `non_circulating_supply.lamports > total_supply` today, so likelihood should be treated as plausible-but-unconfirmed rather than proven.

### Recommendation
Change `rpc/src/rpc.rs`'s `get_supply` to use `total_supply.saturating_sub(non_circulating_supply.lamports)` (matching `rpc_service.rs`), removing the unguarded subtraction and eliminating the inconsistency between the two call sites that compute the same value.

### Proof of Concept
Not established with a concrete unprivileged input. This report is based on: (1) the structural analogy to the reported Solidity underflow (an unguarded subtraction of two “supposedly always compatible” magnitudes, exposed to any unprivileged caller via `getSupply`), and (2) the fact that the codebase itself already treats the identical computation as unsafe enough to warrant `saturating_sub` in `rpc_service.rs` but not in `rpc.rs`. Full confirmation would require demonstrating a validator state where the accounts-db scan used by `calculate_non_circulating_supply` can return a lamport sum exceeding `bank.capitalization()` for the same bank snapshot, which I was not able to construct or find test coverage for within the indexed code.

pub fn calculate_non_circulating_supply(bank: &Bank) -> ScanResult<NonCirculatingSupply> {
    debug!("Updating Bank supply, epoch: {}", bank.epoch());
    let mut non_circulating_accounts_set: HashSet<Pubkey> = HashSet::new();

    for key in non_circulating_accounts() {
        non_circulating_accounts_set.insert(key);
    }
    let withdraw_authority_list = withdraw_authority();

    let clock = bank.clock();
    let stake_accounts = if bank
        .rc
        .accounts
        .accounts_db
        .account_indexes
        .contains(&AccountIndex::ProgramId)
    {
        bank.get_filtered_indexed_accounts(
            &IndexKey::ProgramId(stake::program::id()),
            // The program-id account index checks for Account owner on inclusion. However, due to
            // the current AccountsDb implementation, an account may remain in storage as a
            // zero-lamport Account::Default() after being wiped and reinitialized in later
            // updates. We include the redundant filter here to avoid returning these accounts.
            |account| account.owner() == &stake::program::id(),
            None,
        )?
    } else {
        bank.get_program_accounts(&stake::program::id())?
    };

    for (pubkey, account) in stake_accounts.iter() {
        let stake_account = account
            .deserialize_data::<StakeStateV2>()
            .unwrap_or_default();
        match stake_account {
            StakeStateV2::Initialized(meta)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            StakeStateV2::Stake(meta, _stake, _stake_flags)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            _ => {}
        }
    }

    let lamports = non_circulating_accounts_set
        .iter()
        .map(|pubkey| bank.get_balance(pubkey))
        .sum();

    Ok(NonCirculatingSupply {
        lamports,
        accounts: non_circulating_accounts_set.into_iter().collect(),
    })
}
