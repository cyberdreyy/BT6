### Title
TOCTOU race in JWT replay-cache check-then-act allows single-use gateway JWT to authorize concurrent duplicate workflow execution - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks `h.jwtCache.isReplay(claims.ID)` and later calls `h.jwtCache.recordUsage(claims.ID)` as two separate, independently-locked operations rather than a single atomic check-and-set. Two concurrent `Authorize` calls carrying the same JWT (`jti`) can both observe `isReplay == false` before either records usage, allowing both to pass the replay check and both requests to be authorized from a single signed, single-use JWT.

### Finding Description
`isReplay` takes an `RLock`, reads the map, and releases the lock; `recordUsage` is only called afterward, at the end of `Authorize`, after other validation (signature verification and authorized-key lookup) succeeds, and takes its own `Lock` to write the entry: [1](#0-0) . Between the `isReplay` read and the `recordUsage` write in `Authorize`, there is no lock held across the whole check-then-act sequence: [2](#0-1) . If two requests carrying the identical valid JWT (same `jti`, same signature) arrive concurrently, both can call `isReplay` before either calls `recordUsage`, so both will see "not a replay," both will pass signer/authorized-key checks (which are independent of the replay cache), and both will return a valid `*gateway.AuthorizedKey`, effectively authorizing two workflow executions with what is documented and intended to be a single-use signed authorization.

However, the exploitability of this race depends on how the gateway invokes `Authorize` for a given `workflows.execute` request. Attempts to trace the exact caller chain (e.g. `http_trigger_handler.go`) to confirm whether concurrent calls into `Authorize` for the same request/session are actually reachable from an unprivileged external request path were inconclusive in this pass — the caller `http_trigger_handler.go` references `Authorize` but the surrounding dispatch/locking context (whether the gateway serializes requests per workflow/connection before calling `Authorize`, or whether raw concurrent HTTP requests map directly into concurrent `Authorize` calls) could not be fully verified with the tools available in this session.

### Impact Explanation
If reachable as described, this breaks the "one JWT authorizes exactly one execution" invariant, enabling replay-based duplicate/unauthorized workflow triggering — matching the "unauthorized job run" bounty impact class. The race window is narrow (only between the `isReplay` read and the `recordUsage` write, which excludes JWT verification and authorized-key lookup time), so the practical window for duplicate execution is limited to genuinely concurrent requests with identical tokens, not general replay after the fact.

### Likelihood Explanation
An attacker needs only one valid, unexpired JWT already authorized for a workflow (a precondition explicitly stated in the question), which is consistent with the threat model of "attacker holds one valid JWT." No elevated privileges beyond holding that single token are required. Exploitability requires the attacker to be able to fire two requests with identical token/jti at (or close to) the same time and have them processed concurrently on the gateway/handler side — this is plausible given standard HTTP concurrency, but I could not confirm from the code inspected whether any upstream serialization (e.g., per-connection locking in `http_trigger_handler.go` or a queueing layer) prevents concurrent `Authorize` invocations for the same request stream, which would reduce or eliminate the practical window.

### Recommendation
Make the replay check-and-record atomic under a single lock acquisition: add a method like `checkAndRecord(jti string) bool` on `jwtReplayCache` that takes the write lock once, checks existence, and if not present inserts the timestamp and returns `true` (allowed) or `false` (replay), and call it instead of the separate `isReplay`/`recordUsage` calls in `Authorize`. This eliminates the check-then-act gap:

```go
func (cache *jwtReplayCache) checkAndRecord(jti string) bool {
    cache.mu.Lock()
    defer cache.mu.Unlock()
    if _, exists := cache.cache[jti]; exists {
        return false
    }
    cache.cache[jti] = time.Now()
    return true
}
```

And in `Authorize`, replace the early `isReplay` check with a call to `checkAndRecord` performed immediately (or move the atomic check to occur before/atomically with the point where authorization is finalized) so no two concurrent calls with the same `jti` can both pass.

### Proof of Concept
Go concurrency test plan (to be run against `jwtReplayCache`/`WorkflowMetadataHandler.Authorize`):
1. Construct a `WorkflowMetadataHandler` with a workflow ID registered with one authorized signer key (as done in `workflow_metadata_handler_test.go`).
2. Generate a single valid JWT (with a fixed `jti`) signed by the authorized key, valid for the target `workflowID` and request payload.
3. Launch N (e.g., 50) goroutines that all call `h.Authorize(workflowID, token, req)` simultaneously with the identical token/request, using a `sync.WaitGroup` and a channel/atomic counter to record how many calls return `nil` error (success).
4. Assert that in the current implementation, more than one goroutine can succeed (flaky over repeated runs / detectable with `-race` and stress iterations), demonstrating the TOCTOU gap between `isReplay` and `recordUsage`.
5. Apply the atomic `checkAndRecord` fix and re-run the same test, asserting exactly one success across all concurrent calls, every run.

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
