### Title
Panic on malformed BigTable-backed `ConfirmedBlock` transaction aborts entire `getBlock` read instead of degrading gracefully - ([File: storage-proto/src/convert.rs])

### Summary
`TryFrom<generated::ConfirmedBlock> for ConfirmedBlock` maps every transaction via `tx.try_into()` and short-circuits on the first error with `?`, but the per-transaction conversion `TryFrom<generated::ConfirmedTransaction> for TransactionWithStatusMeta` does not always return an `Err` for malformed data — it panics via `.expect("transaction is required")` and `.expect("meta is required for versioned transactions")`. A single malformed transaction among many attacker-controlled protobuf transactions therefore either aborts the whole block decode via early return, or crashes the RPC-serving process outright.

### Finding Description
`ConfirmedBlock`'s conversion iterates all transactions and collects into a `Result`, aborting on the first error: [1](#0-0) 

The per-transaction conversion, however, is not panic-free. If the protobuf-decoded `generated::ConfirmedTransaction.transaction` field is `None` (a value fully controllable by whoever writes the stored protobuf bytes, since protobuf `optional message` fields are trivially omittable), the code panics instead of returning `Self::Error`: [2](#0-1) 

Similarly, if `meta` is `None` and the transaction is a versioned (non-legacy) transaction, `.into_legacy_transaction().expect(...)` panics rather than erroring out.

This conversion is used by `storage-bigtable`'s `get_confirmed_block`, which reads a protobuf cell and calls `.try_into()`, converting any `DecodeError` into a `bigtable::Error::ObjectCorrupt`, but this only catches the `Err` path — it cannot catch a panic: [3](#0-2) 

Because BigTable is the storage backend for `getBlock`/`getConfirmedBlock` history queries when a validator or RPC node is run with BigTable secondary ledger storage enabled, an attacker who can write (or has previously written) a malformed `ConfirmedBlock` protobuf cell reachable through a single `getBlock` call can trigger this panic on read, taking down the RPC-serving process thread (or the whole process, depending on panic-handling configuration).

Even in the non-panicking case (e.g., a bad `meta` field causing `meta.try_into()?` to propagate a `DecodeError`), the `?` in `TryFrom<ConfirmedBlock>` at line 219 aborts the *entire* block, discarding thousands of otherwise-valid transactions — a correctness/availability issue distinct from, but related to, the panic issue.

### Impact Explanation
This matches the "decoder panic" bounty category: a single malformed entry among many valid transactions in a stored block causes either (a) a hard panic in the RPC-serving process on a benign `getBlock` call, which is a validator/RPC-process crash from one request, or (b) silent discarding of an entire block's transaction history on the first bad entry rather than a bounded/partial degrade. Both are direct violations of the stated invariant that "decoders handle arbitrary attacker bytes without panicking; parsed output faithfully represents raw data."

### Likelihood Explanation
Reachability depends on whether the malformed `ConfirmedBlock` protobuf bytes can be introduced into BigTable storage by an unprivileged party and then read back via one `getBlock`/`getConfirmedBlock` RPC call. This code path is only exercised when the node is configured with `--enable-rpc-bigtable-ledger-storage` (BigTable secondary storage), which is an operator-configuration precondition; I was not able to fully trace, within the available tool budget, the exact write path proving that an unprivileged single-caller can *write* the malicious protobuf bytes into BigTable without operator/administrative BigTable write access (the upload path in `storage-bigtable/src/lib.rs` writes `confirmed_block.into()` derived from validator-produced ledger data, not directly from attacker-supplied bytes). If the write path requires privileged BigTable write access (not achievable via a single unprivileged JSON-RPC call), this finding would fall outside the stated threat model ("attacker is unprivileged only ... writing on-chain data that is later returned through those APIs"), since the malformed protobuf bytes are not something obviously derivable from ordinary on-chain transaction data — they require a structurally invalid `ConfirmedTransaction` (missing `transaction` field), which the normal `From<VersionedTransactionWithStatusMeta> for generated::ConfirmedTransaction` conversion always populates.

### Recommendation
Replace the `.expect(...)` panics in `TryFrom<generated::ConfirmedTransaction> for TransactionWithStatusMeta` (storage-proto/src/convert.rs:254 and :260) with proper `Err(DecodeError { .. })` returns so malformed entries produce a `Result::Err` instead of crashing the process. Additionally, consider having `TryFrom<generated::ConfirmedBlock> for ConfirmedBlock` skip and log malformed transactions (with a bounded count/size) rather than aborting the whole block via `?`, if partial-block degrade is an acceptable product behavior; otherwise ensure the resulting single `Err` is surfaced as a clean RPC error rather than an internal panic.

### Proof of Concept
```rust
// storage-proto/src/convert.rs (unit test)
#[test]
fn test_malformed_confirmed_transaction_does_not_panic() {
    use crate::convert::generated;
    // Missing `transaction` field entirely (attacker-controlled/corrupted protobuf bytes)
    let malformed = generated::ConfirmedTransaction {
        transaction: None,
        meta: None,
    };
    let result: std::result::Result<TransactionWithStatusMeta, _> = malformed.try_into();
    // Expected: a clean Err, not a panic.
    assert!(result.is_err());
}

#[test]
fn test_confirmed_block_with_one_bad_tx_among_many() {
    let mut transactions = Vec::new();
    for _ in 0..10_000 {
        transactions.push(valid_confirmed_transaction()); // helper producing a valid generated::ConfirmedTransaction
    }
    transactions.push(generated::ConfirmedTransaction { transaction: None, meta: None });

    let block = generated::ConfirmedBlock {
        previous_blockhash: "11111111111111111111111111111111".to_string(),
        blockhash: "11111111111111111111111111111111".to_string(),
        parent_slot: 0,
        transactions,
        rewards: vec![],
        num_partitions: None,
        block_time: None,
        block_height: None,
    };

    // Expected: Err(DecodeError), not a panic, and ideally not full data loss.
    let result: std::result::Result<ConfirmedBlock, _> = block.try_into();
    assert!(result.is_err());
}
```
Run with `cargo test -p solana-storage-proto` under `catch_unwind` or with `#[should_panic]` removed to demonstrate the current code panics instead of returning `Err`.

impl TryFrom<generated::ConfirmedTransaction> for TransactionWithStatusMeta {
    type Error = DecodeError;
    fn try_from(value: generated::ConfirmedTransaction) -> std::result::Result<Self, Self::Error> {
        let meta = value.meta.map(|meta| meta.try_into()).transpose()?;
        let transaction = value.transaction.expect("transaction is required").into();
        Ok(match meta {
            Some(meta) => Self::Complete(VersionedTransactionWithStatusMeta { transaction, meta }),
            None => Self::MissingMetadata(
                transaction
                    .into_legacy_transaction()
                    .expect("meta is required for versioned transactions"),
            ),
        })
    }
}
