### Title
Job-controlled Vault secret path can escape the configured KV v2 mount via `../` traversal in `path.Join` - ([File: helpers/vault/secret_engines/kv_v2/engine.go])

### Summary
`engine.dataPath` and `engine.metadataPath` build the Vault API path by calling `path.Join(e.path, "data"/"metadata", p)` where `p` is the job-controlled `secret.SecretPath()` value (ultimately derived from a `.gitlab-ci.yml`/CI-variable-controlled `VaultSecret.Path`). Because `path.Join` internally calls `path.Clean`, sufficient `../` segments in `p` can walk past both the `"data"`/`"metadata"` segment and the entire `e.path` mount prefix, producing a request path outside the intended mount boundary. There is no validation or containment check on `p` before it is handed to `client.Read`/`client.Write`/`client.Delete`.

### Finding Description
`engine.Get(path)` at [1](#0-0)  calls `e.dataPath(path)`, and `dataPath` is implemented purely as: [2](#0-1) 

`path.Join` normalizes the joined string with `path.Clean`, which resolves `..` segments lexically. Given `e.path = "secret"` (an admin-configured mount) and job-controlled `p = "../../other-project/secret"`, the join resolves as:

```
Join("secret", "data", "../../other-project/secret")
= Clean("secret/data/../../other-project/secret")
= "other-project/secret"
```

The two `..` segments consume both `"data"` and the mount segment `"secret"` itself, so the resulting path no longer has the intended mount prefix at all. The same logic applies to `metadataPath` (used by `Delete`) and to `Put`. `p` originates from `secretDetails.SecretPath()` in `defaultVault.GetField`/`Put`/`Delete` ( [3](#0-2) ), which is populated from the job's `spec.Secret`/`VaultSecret.Path` field, a value under the pipeline author's control (resolved via `common/secrets.go` `defaultSecretsResolver.handleSecret` → `SecretResolver.Resolve()`). No sanitization, prefix-check, or `strings.HasPrefix(cleaned, e.path)` validation exists anywhere in this call chain before the path reaches the Vault client.

### Impact Explanation
An unprivileged pipeline author who can set a `vault` secret's `path` (or any variable that flows into it) can cause the Runner to issue Vault API reads/writes/deletes at a path outside the admin-configured mount, e.g. reading secrets from a different Vault mount or logical namespace that Runner's Vault token has access to. This is a concrete violation of the stated invariant that job-controlled input must not escape the configured mount/project boundary, independent of whatever coarse-grained Vault ACL the operator has configured for the Runner's role — Runner performs no defense-in-depth containment of its own.

### Likelihood Explanation
This requires only standard, unprivileged control over `.gitlab-ci.yml` `secrets:` configuration (or a CI/CD variable feeding that path) — no special runner or admin privileges. The traversal is deterministic and trivially reproducible with any number of `..` segments; feasibility of actual data exfiltration further depends on the Vault token's ACL scope, but the Runner-side path-construction bug itself is unconditionally reproducible.

### Recommendation
In `dataPath`/`metadataPath`, clean the job-supplied `p` independently first, reject any resulting value containing `..` or an absolute path, and verify the final joined path still has `e.path` as a strict prefix before calling the Vault client (e.g., `filepath.Rel`/`strings.HasPrefix` check on the cleaned segments), returning an error instead of silently escaping.

```go
func FuzzEngineDataPath(f *testing.F) {
    f.Add("../../leak")
    f.Add("/etc/passwd")
    f.Add("%2e%2e/%2e%2e/leak")

        e := &engine{path: "secret"}

        if !strings.HasPrefix(got, "secret/") {
            t.Errorf("path %q escaped configured mount, got %q", p, got)
        }
    })
}
```
Expected: with the current implementation, the first assertion fails (`got == "other-project/secret"`), demonstrating the mount-escape bug; after adding containment validation, the test should pass or `dataPath`/`Get` should return an error for such inputs.

```go
func (v *defaultVault) GetField(engineDetails Engine, secretDetails Secret) (interface{}, error) {
	engine, err := v.getSecretEngine(engineDetails)
	if err != nil {
		return nil, err
	}

	secret, err := engine.Get(secretDetails.SecretPath())
	if err != nil {
		return nil, fmt.Errorf("reading secret: %w", err)
	}

	field := secretDetails.SecretField()
	for key, data := range secret {
		if key != field {
			continue
		}

		return data, nil
	}

	return nil, nil
}
```
