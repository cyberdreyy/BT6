### Title
External Initiator credentials can trigger runs on arbitrary jobs via POST /v2/jobs/:ID/runs - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` sets the same `SessionUserKey` context value that real user-authentication methods set, granting any valid EI credential a synthetic `User{Role: UserRoleRun}`. `PipelineRunsController.Create` uses `auth.GetAuthenticatedUser(c)` presence alone (`isUser`) to decide whether a request may run a job by integer ID, but this check cannot distinguish a real user session/token from an EI-faked user object, so the intended restriction ("EIs not allowed" for int-ID runs) is bypassed and an EI credential can invoke `RunJobV2` for any job ID unrelated to the EI's own binding.

### Finding Description
`AuthenticateExternalInitiator` (core/web/auth/auth.go) authenticates a request purely from the EI access key/secret and, on success, unconditionally does: [1](#0-0) 
This sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` with no binding at all to which job/bridge the EI is associated with — the same context key (`SessionUserKey`) that `AuthenticateBySession` and `AuthenticateByToken` set for genuine, DB-authenticated users. [2](#0-1) [3](#0-2) 

`GetAuthenticatedUser` simply reads whatever is stored at `SessionUserKey`, with no way to tell it apart from the EI-synthesized user: [4](#0-3) 

`PipelineRunsController.Create` relies on this ambiguous signal to gate whether integer job IDs may be run, with an explicit comment stating EIs should not be allowed to use this path: [5](#0-4) 

Because `isUser` is derived from `auth.GetAuthenticatedUser(c)` and that function returns `ok=true` for both real users and EI-authenticated requests (both populate `SessionUserKey`), the "EIs not allowed" comment does not reflect actual behavior: a request authenticated solely via valid EI-A access key/secret headers will have `isUser == true`, pass the `RequiresRunRole` role-based middleware wrapper (which only checks `user.Role != UserRoleView`, and the synthetic user has `Role: UserRoleRun`), and proceed to call `prc.App.RunJobV2(ctx, jobID, nil)` for whatever integer job ID is in the URL — with zero verification that job ID belongs to, or is associated with, EI-A's bridge/webhook binding.

### Impact Explanation
This is an authorization/role-bypass vulnerability enabling unauthorized job runs (Chainlink bounty impact class: "unauthorized job run"). An attacker holding valid credentials for one external initiator can trigger pipeline runs on any job in the node addressable by integer ID, regardless of which job/bridge the EI credential was actually provisioned for. Depending on job task graphs, this could cause unintended on-chain transactions, resource exhaustion, unauthorized data submission, or interference with other integrations' jobs — a violation of the intended "one sender bound to one authorized job" invariant.

### Likelihood Explanation
Preconditions are minimal: an attacker only needs a single valid EI access key/secret pair (the lowest external-initiator privilege level) and knowledge/guessability of a target job's integer ID (job IDs are small sequential integers, often discoverable via job listing endpoints or predictable enumeration). No admin/operator access or extra privileges are required, and exploitation is fully repeatable — every POST to `/v2/jobs/:ID/runs` with EI headers and an int ID job will be processed the same way.

### Recommendation
In `PipelineRunsController.Create`, do not use `auth.GetAuthenticatedUser` presence alone to permit int-ID runs. Instead, explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and reject the request (403) whenever an EI context is present, regardless of the synthetic `SessionUserKey`. More robustly, avoid overloading `SessionUserKey` for EI authentication altogether — introduce a distinct context flag/type (e.g., a wrapped `AuthenticatedSubject` interface or a separate `IsExternalInitiator` bool) so downstream handlers can unambiguously distinguish EI-derived pseudo-users from real authenticated users, and additionally verify that any job run triggered by an EI is scoped to the specific job/bridge the EI is bound to (e.g., by validating against `bridges.ExternalInitiator.Name`/associated job ID) rather than trusting an arbitrary URL path parameter.

### Proof of Concept
Go handler-level integration test plan (extends `core/web/pipeline_runs_controller_test.go`):
1. Set up two jobs, Job-A and Job-B (e.g., webhook/direct-request jobs), and create External Initiator EI-A bound/created for use with Job-A only (via bridges/external initiator flow).
2. Obtain EI-A's access key and secret (as returned at EI creation).
3. Send `POST /v2/jobs/<Job-B-ID>/runs` with headers `X-Chainlink-EA-AccessKey: <EI-A key>` and `X-Chainlink-EA-Secret: <EI-A secret>` (no session cookie, no API token).
4. Assert current (vulnerable) behavior: response is `200/201` with a `pipelineRun` resource for Job-B, and `prc.App.RunJobV2` was invoked with Job-B's ID — despite EI-A never being associated with Job-B.
5. Expected/fixed behavior: response should be `401/403`, since EI credentials should never be permitted to trigger arbitrary int-ID job runs, or should be restricted strictly to the job the EI is bound to.
6. Additionally add a unit test for `auth.AuthenticateExternalInitiator` + `auth.GetAuthenticatedUser`/`GetAuthenticatedExternalInitiator` asserting that after EI authentication, `GetAuthenticatedExternalInitiator` returns `ok=true` while a fixed `isUser` check (once patched) correctly distinguishes and rejects run-by-int-ID for EI-only auth contexts.

func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}
