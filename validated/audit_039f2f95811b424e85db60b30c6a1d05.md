### Title
Signer vote-flip weight double-count corrupts miner's aggregated approve/reject tallies, causing wrongful block abandonment - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The mining node's `StackerDBListener` tallies signer votes into a single shared `BlockStatus` struct with two independently-guarded counters, `total_weight_approved` and `total_weight_rejected`. The guard used to decide whether to add a signer's weight to the *reject* bucket (`responded_signers.insert(slot_id)`) is different from, and not reconciled with, the guard used for the *approve* bucket (`gathered_signatures.contains_key(&slot_id)`). A signer that first rejects and later legitimately signs (accepts) the same block has its weight counted into `total_weight_rejected` **and** `total_weight_approved`, permanently, because nothing ever decrements `total_weight_rejected` when the same slot subsequently appears in `gathered_signatures`. This is the same class of bug as the PoolTogether `H-08` finding: one ledger (`_reserve`) was incremented without keeping the other ledger (`_accountedBalance`) in sync, so a single value ends up double-counted across two totals that are supposed to reconcile.

### Finding Description
`BlockStatus` is defined at [1](#0-0)  with `total_weight_approved`, `total_weight_rejected`, `gathered_signatures`, and `responded_signers` as separate fields on the same block-tracking record.

On receipt of an accepted signature, the code updates `total_weight_approved` gated on `gathered_signatures` membership, then unconditionally marks the slot as `responded_signers`: [2](#0-1) 

On receipt of a rejection, the code updates `total_weight_rejected` gated on `responded_signers.insert(slot_id)` — i.e., "first message ever seen from this slot": [3](#0-2) 

Because `responded_signers` is a single shared set used by both branches but the approve branch keys its weight increment off `gathered_signatures` instead, the two counters are not mutually exclusive per signer:

1. Signer `S` (weight `w`) sends `Rejected` first. `responded_signers.insert(slot_id)` returns `true` → `total_weight_rejected += w`.
2. Signer `S` later sends a valid `Accepted` signature for the same block (e.g., after a re-proposal, retry, or after the signer's local rejection is superseded — the signer-side code explicitly allows revising a prior rejection, see `should_reevaluate_reject_reason`/`store_and_process_block_signature` in `stacks-signer/src/v0/signer.rs`). Since `gathered_signatures` does not yet contain `slot_id`, `total_weight_approved += w` is applied. `responded_signers.insert(slot_id)` is a no-op (already present) — but nothing undoes the earlier `total_weight_rejected += w`.

The result: `S`'s weight `w` is now counted in *both* `total_weight_approved` and `total_weight_rejected` permanently. The invariant that a signer's weight should count toward exactly one side of the tally is broken — an "aggregated weight" that no longer corresponds to the set of verified, live votes.

### Impact Explanation
`SignerCoordinator::get_block_status` uses these two aggregated counters directly to decide the miner's fate for the block: it aborts and excludes transactions if `total_weight_rejected + weight_threshold > total_weight`, or succeeds if `total_weight_approved >= weight_threshold`: [4](#0-3) 

Because a single flipping signer's weight is never removed from `total_weight_rejected`, that phantom weight can combine with other, unrelated signers' honest rejections to cross the abandonment threshold (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`) even though the real, current, verifiable vote count would not have crossed it. This wedges the miner into wrongly aborting an otherwise-signable block and can trigger `temporarily_excluded_txids`/`permanently_excluded_txids` punishment of transactions based on stale rejection reasons: [5](#0-4) . This is a liveness wedge on block production reachable by a single signer's vote flip plus ordinary gossip traffic — no majority or privileged access is required, matching the "High" impact bucket (a wedge affecting the miner's ability to accept validly-signed blocks).

### Likelihood Explanation
Any one-slot signer can trigger this by sending a `Rejected` response for a proposal and later sending a valid `Accepted` signature for the same `signer_signature_hash` — a normal occurrence given the signer state machine explicitly supports re-evaluating a previously rejected block (`should_reevaluate_block`, `should_reevaluate_reject_reason` per `docs/signer-flows.md`). No collusion, majority, or malicious signature forgery is needed; only ordinary StackerDB message flow through the existing miner-side listener.

### Recommendation
Reconcile the two counters against a single per-slot "current vote" state instead of two independently-guarded increments. When a slot transitions from `Rejected` to `Accepted` (or vice versa), subtract the previously-counted weight from the stale bucket before/while adding it to the new one, e.g., track `votes: HashMap<slot_id, Vote>` and recompute `total_weight_approved`/`total_weight_rejected` as pure functions of that map, or explicitly do:
```rust
if let Some(prev) = block.votes.insert(slot_id, Vote::Accepted) {
    if prev == Vote::Rejected {
        block.total_weight_rejected = block.total_weight_rejected.saturating_sub(signer_entry.weight);
    }
}
```
applied symmetrically in the Rejected branch.

### Proof of Concept
1. Miner proposes block `B`; signer `S` (weight `w`) initially evaluates `B` as invalid and broadcasts `Rejected` — `StackerDBListener` records `total_weight_rejected += w` via the `responded_signers.insert` guard at `stackerdb_listener.rs:515-518`.
2. A subsequent event (re-proposal or delayed pre-commit threshold) leads `S` to sign `B` and broadcast `Accepted`. The listener applies `total_weight_approved += w` via the `gathered_signatures` guard at `stackerdb_listener.rs:443-446`, leaving `total_weight_rejected` unchanged.
3. `w` is now double-booked into both totals. If other signers independently reject `B` with combined weight `r` such that `r + w + weight_threshold > total_weight` (which would *not* hold using only genuinely-still-rejecting weight `r`), `SignerCoordinator::get_block_status` incorrectly concludes the block is rejected (`signer_coordinator.rs:509-518`) and aborts, even though `S` has a valid, current signature over `B`.
