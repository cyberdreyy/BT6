### Title
Instant-withdraw receipts escape the default haircut when `epochNumber` moves between request recording and default finalization — epoch-keyed ownership is read at finalization epoch instead of request epoch (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2025-58145 is a TOCTOU: a page's type/ownership is checked under a lock, but the lock is dropped before the reference is taken, so the object can change in between. The analog in `IdleCreditVault` is an epoch-keyed ownership mismatch: `requestInstantWithdraw` records claim basis under `instantWithdrawsRequestsByEpoch[user][epochNumber]` at *request time*, but both `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest` read the mapping under `instantWithdrawsRequestsByEpoch[user][epochNumber]`/`defaultRecoveryEpoch` evaluated at *finalization time*. If `epochNumber` increments (it is bumped inside `deposit`, called by the CDO during the stop/start epoch flow) between the instant request and `finalizeDefaultRecovery`, the receipt's epoch key changes under it — it is excluded from the haircut basis yet remains payable at par.

### Finding Description
- `requestInstantWithdraw` writes `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` using the *current* epochNumber, and adds `_amount` to `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`).
- `epochNumber` is mutated in `deposit` (`epochNumber += 1` when the epoch is running, `IdleCreditVault.sol:607-614`), which the CDO calls during `stopEpoch`.
- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` — evaluated at finalization epoch, not request epoch (`IdleCreditVault.sol:644-649`).
- `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` and `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` (`IdleCreditVault.sol:690-696`).
- `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — the finalization epoch (`IdleCreditVault.sol:842-856`).

Sequence: while epoch N runs, an attacker (any KYC'd tranche holder) calls `requestInstantWithdraw`. Epoch N stops with insufficient repayment → `defaulted`, and `epochNumber` becomes N+1. `finalizeDefaultRecovery` runs in epoch N+1: `instantWithdrawClaimsByEpoch[N+1] == 0`, so the requester's basis is excluded from `defaultPendingClaimBasis` — the recovery price is computed over a smaller total basis — while `defaultInstantWithdrawsFinalized` is still set true because `pendingInstantWithdraws != 0`. On claim, `_claimDefaultedInstantWithdrawRequest` returns 0 (nothing stored under epoch N+1), so the full `instantWithdrawsRequests[_user]` falls through to `_transferFundedClaim` and is paid **at par** instead of at `defaultRecoveryPrice`.

### Impact Explanation
Broken invariant: loss waterfall / recovery pro-rata. An unfunded instant receipt that was never included in the recovery basis is paid 1:1 from `defaultRecoveryReserve`/strategy underlyings. Two outcomes depending on balance:
1. If reserve is sufficient, the attacker drains reserve allocated to haircutted claimants — direct theft of recovery funds (quantified as `claimBasis - claimBasis * defaultRecoveryPrice / 1e18` per receipt).
2. If `balance - defaultRecoveryReserve < amount`, `_transferFundedClaim` reverts — the claim is permanently frozen since the epoch-keyed path can never clear it (receipt is under epoch N, `defaultRecoveryEpoch` is N+1).

### Likelihood Explanation
Requires a running epoch where instant withdrawals are enabled, a subsequent `stopEpoch` that leaves the pool defaulted and bumps `epochNumber`, and `finalizeDefaultRecovery` in the next epoch — all driven by honest manager/owner calls. The attacker only needs to hold tranche tokens and call `requestInstantWithdraw` during the epoch. The gap exists whenever default finalization occurs in a later epoch than the instant request, which is the normal flow for a borrower default discovered at `stopEpoch`.

### Recommendation
Resolve instant-claim basis against the *request epoch* stored per user, not `epochNumber`/`defaultRecoveryEpoch` at finalization time: either iterate `instantWithdrawClaimsByEpoch` across epochs when computing `defaultPendingClaimBasis`, or fold all pending instant receipts into `defaultRecoveryEpoch` at finalization (e.g., migrate `instantWithdrawsRequestsByEpoch[user][reqEpoch]` entries, or track a per-user `lastInstantWithdrawRequest` epoch analogous to `lastWithdrawRequest`).

### Proof of Concept
Foundry fork PoC outline (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):
```solidity
// 1. Attacker deposits AA, epoch N starts.
// 2. Attacker calls cdoEpoch.requestInstantWithdraw(amount, AAtranche)
//    -> instantWithdrawsRequestsByEpoch[attacker][N] = amount
// 3. Manager stops epoch with borrower underpaying -> defaulted;
//    deposit() inside stopEpoch increments epochNumber to N+1.
// 4. Owner finalizes default recovery (finalizeDefaultRecovery via CDO)
//    -> defaultRecoveryEpoch = N+1; basis excludes attacker's instant claim;
//       defaultInstantWithdrawsFinalized = true.
// 5. Attacker calls cdoEpoch.claimInstantWithdrawRequest()
//    -> _claimDefaultedInstantWithdrawRequest reads epoch N+1 -> 0
//    -> falls through to _transferFundedClaim paying `amount` at par
//       (or reverting if reserve-guarded), instead of amount * defaultRecoveryPrice.
assertEq(underlying.balanceOf(attacker), amount); // haircut bypassed
```

Uncertainty note: this conclusion relies on `epochNumber` being incremented (in `deposit`) before `finalizeDefaultRecovery` runs after a defaulting `stopEpoch`, and on instant-withdraw requests being permitted during the running epoch. I could not fully trace the CDO-side `stopEpoch`/`finalizeDefault` ordering within the iteration budget; if the CDO guarantees finalization in the same epoch as all pending instant requests, the mismatch cannot occur and the finding reduces to a latent fragility rather than an exploitable bug.
