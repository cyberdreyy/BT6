### Title
Internal DON topology (DON names/IDs) leaked to vault API callers via unredacted `FatalError` when vault capability is registered under multiple DONs - (`core/services/gateway/handlers/vault/aggregator.go`, `core/services/gateway/handlers/vault/handler.go`)

### Summary
When the capabilities registry has 2+ DONs hosting the vault capability and `vaultHandlerDonID` (`DONConfig.DonId`) is empty or does not match any of them, `baseAggregator.donForVaultCapability` returns a `fmt.Errorf` whose text includes `summarizeVaultRegistryDONs(dons)` — the `name`/`id` of every registered vault DON [1](#0-0) . This error propagates unredacted through `handler.HandleNodeMessage` as an `api.FatalError` and is serialized verbatim into the JSON-RPC error response sent back to the requesting client [2](#0-1) [3](#0-2) . The "silent routing to an unintended DON's signer set" part of the hypothesis is **not** what happens — the code fails closed (returns an error, never returns a `DONWithNodes` for the wrong DON) when `handlerDonID` is empty or matches zero DONs.

### Finding Description
- Any authorized vault client request (e.g., `MethodSecretsList`, reachable by any credential holder who passes `requestProcessor.ProcessRequest` authorization — not necessarily an admin) is fanned out to nodes via `fanOutToVaultNodes` [4](#0-3) .
- When node responses arrive, `HandleNodeMessage` calls `aggregator.Aggregate`, which first resolves the DON via `donForVaultCapability` [5](#0-4) .
- If the registry (server-side state, not directly attacker-set) has misregistered the vault capability under 2+ DONs and `vaultHandlerDonID` is empty, `donForVaultCapability` returns an error string embedding `summarizeVaultRegistryDONs(dons)`, i.e., `name=%q id=%d` for every vault DON in the registry [6](#0-5) .
- `HandleNodeMessage`'s error branch treats any non-`errInsufficientResponsesForQuorum` error as fatal and forwards it directly to the user via `h.errorResponse(ar.req, api.FatalError, err, nil)` [7](#0-6) .
- Inside `errorResponse`, the `case api.FatalError:` branch is empty — unlike `NodeReponseEncodingError`, `InvalidParamsError`, etc., it performs **no redaction** of `err.Error()` before encoding it into the JSON-RPC response payload sent to the caller [3](#0-2) .
- Result: the raw internal registry error, including every vault DON's `name` and numeric `id`, is returned to the unprivileged (but authorized) API caller who merely triggered a normal vault request while this misregistration condition existed server-side.

This is a genuine information-disclosure path distinct from — and narrower than — the "wrong DON signer validation" scenario in the question: the code does **not** proceed to validate signatures against an unintended DON when `handlerDonID` is empty; it errors out before ever calling `validateUsingSignatures`. Signature validation is never weakened in this specific empty-`handlerDonID` path.

### Impact Explanation
Impact is limited to disclosure of internal vault-DON topology (DON names and numeric registry IDs) to any client that can issue an authorized vault request while the described misregistration state exists. This maps to a low-severity information-disclosure class (internal infrastructure metadata exposure), not a key/secret disclosure or signature-bypass/request-impersonation. No node signer keys, vault secrets, or private key material are exposed, and requests are not routed to or validated against the wrong DON's signer set — the aggregator fails closed rather than silently mis-binding.

### Likelihood Explanation
Requires a specific server-side precondition (registry misregistration: the vault capability advertised by 2+ DONs while the gateway's configured `DonId` is empty or non-matching) that is not attacker-controlled. Given that precondition, however, exploitation is trivial and repeatable: any authorized vault client (e.g., one holding valid allow-list/JWT vault auth) can trigger it by issuing a normal `MethodSecretsList`/`MethodSecretsCreate`/etc. request, since the resulting node response triggers `HandleNodeMessage` → `Aggregate` → `donForVaultCapability` on every call while the misconfiguration persists.

### Recommendation
Redact the `donForVaultCapability` error before returning it to the end user in `errorResponse`'s `api.FatalError` branch — log the full error (including `summarizeVaultRegistryDONs` output) server-side only, and return a generic message (e.g., "internal server error, unable to process vault request") to the caller, consistent with how `NodeReponseEncodingError` is already handled.

### Proof of Concept
Go handler-level test plan (extending `TestAggregator_MultipleRegistryDONs_*` style tests in `core/services/gateway/handlers/vault/aggregator_test.go` plus a handler test in `handler_test.go`):
1. Configure a fake `capabilitiesRegistry` whose `DONsForCapability` returns 2 `DONWithNodes` entries (distinct `Name`/`ID`) for `vaultcommon.CapabilityID`.
2. Construct `baseAggregator{vaultHandlerDonID: ""}` and call `Aggregate` (or `donForVaultCapability` directly) — assert the returned error's `Error()` string contains both DON names/ids exactly as produced by `summarizeVaultRegistryDONs`.
3. At the `handler` level, wire this aggregator into `handler.aggregator`, issue a `MethodSecretsList` request through `HandleJSONRPCUserMessage`, feed a node response through `HandleNodeMessage`, and capture the `UserCallbackPayload` sent via the callback.
4. Assert: `ErrorCode == api.FatalError` and the decoded JSON-RPC error `message` field contains the leaked DON `name`/`id` strings — confirming the information disclosure.
5. Separately, assert (as the question also requests) that in this empty-`handlerDonID` path, `validateUsingSignatures` is never invoked with a `DON`/`Nodes` pair from the wrong/second DON — i.e., no response is ever produced with `Result != nil` bound to an unintended DON's signer set, confirming the fail-closed behavior and that the "wrong-DON signer validation" portion of the hypothesis does not hold.

func summarizeVaultRegistryDONs(dons []capabilities.DONWithNodes) string {
	var b strings.Builder
	for i, d := range dons {
		if i > 0 {
			b.WriteString("; ")
		}
		_, _ = fmt.Fprintf(&b, "name=%q id=%d", d.DON.Name, d.DON.ID)
	}
	return b.String()
}
