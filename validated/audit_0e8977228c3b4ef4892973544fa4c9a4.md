### Title
Emergency shutdown is a silent no-op in `IdleCDOCreditVault`: deposits/mints stay open after `emergencyShutdown()` and after a forced BB-wipe shutdown - (File: contracts/IdleCDOCreditVault.sol)

### Summary
The external report concerns a vault that allows minting during an emergency exit, letting users/attackers lock fresh funds or mint claims while the vault is compromised. The direct analog exists in `IdleCDOCreditVault`: `emergencyShutdown()` delegates to `_emergencyShutdown(bool)`, which is an **empty function**, and `restoreOperations()` is empty as well. Calling `emergencyShutdown()` therefore pauses nothing, sets no flags, and leaves `depositAA`/`depositBB` (i.e. tranche-token minting) fully operational — the exact bug class reported (minting during emergency).

### Finding Description
In `contracts/IdleCDOCreditVault.sol`:

```solidity
function emergencyShutdown() external {
  _checkOnlyOwnerOrGuardian();
  _emergencyShutdown(false);
}

function _emergencyShutdown(bool) internal virtual {}

function restoreOperations() external virtual {}
``` [1](#0-0) 

Compare with the legacy `IdleCDO`, where `_emergencyShutdown` actually pauses deposits, disables withdrawals, and sets `skipDefaultCheck`: [2](#0-1) 

`IdleCDOEpochVariant` overrides the hook and correctly pauses + sets `skipDefaultCheck` (which also blocks `depositDuringEpoch`), but the base credit-vault runtime `IdleCDOCreditVault` does not. Two consequences:

1. **Explicit emergency is ineffective.** A guardian/owner calling `emergencyShutdown()` on an `IdleCDOCreditVault` deployment changes no state: `paused()` stays false, no flag is set, and `depositAA`/`depositBB` continue to mint tranche tokens (`_deposit` only has `whenNotPaused`). There is not even a "shutdown" marker — `skipDefaultCheck` is never set.

2. **Automatic shutdown path is ineffective.** `_updateAccounting()` detects a BB wipe (or full AA-only wipe) and calls `_emergencyShutdown(true)` when `skipDefaultCheck` is set (e.g. via `updateAccounting()`/`_forceUpdateAccounting`). In `IdleCDOCreditVault` this call does nothing, so after the loss is crystallized the vault remains open. Subsequent deposits no longer revert with `Default()` (the loss is already booked), so an attacker can keep minting AA shares into a vault whose BB tranche was just wiped. [3](#0-2) 

### Impact Explanation
- During a security incident (strategy/borrower compromise), the guardian's `emergencyShutdown()` does not stop inflows. Unaware users — or an attacker — continue depositing and minting tranche tokens against a compromised vault, locking fresh funds in the loss pool (same impact class as the reference finding: increased financial loss during a security incident).
- After a forced BB-wipe shutdown, newly minted tranche shares become extra claims on the residual NAV / defaulted-recovery distribution (`DefaultDistributor` pays out by tranche balance), diluting the recovery of existing holders. Attacker cost: deposit at the post-loss `priceAA`, receive proportional claims on any recovery — direct dilution/theft of recovery proportional to the deposit size.

### Likelihood Explanation
- `emergencyShutdown()` is precisely the function called during an incident; its silent failure means the intended mitigation never applies. Any EOA (or KYC-passing lender for wallet-gated flows) can deposit at that moment — `depositAA` has no gating beyond `whenNotPaused`, and `depositBB` beyond `isBBDepositEnabled`.
- The forced-shutdown path (`_forceUpdateAccounting` → `_emergencyShutdown`) is exercised whenever a loss exhausts BB; the no-op hook leaves the vault open in exactly the state where the design intends it closed.
- Caveat: `IdleCDOCreditVault` itself exposes deposits but no withdrawals (those live in `IdleCDOEpochVariant`, which correctly overrides the hook). If this contract is only ever used as a base and never deployed/upgraded-to directly, the exploit window is limited to the BB-wipe residual-deposit scenario rather than a standalone broken `emergencyShutdown`. The contract is not `abstract` and its storage layout is explicitly designed for existing proxies to upgrade to it, so it is a plausible production target.

### Recommendation
Implement `_emergencyShutdown` in `IdleCDOCreditVault` mirroring `IdleCDO` behavior for the credit-vault surface:

```solidity
function _emergencyShutdown(bool) internal virtual override {
  if (!paused()) {
    _pause();
  }
  skipDefaultCheck = true;
}
```

and implement `restoreOperations()` to clear `skipDefaultCheck` and unpause (with the same `defaulted`/`priceAA == 0` guards used in `IdleCDOEpochVariant.restoreOperations`). Alternatively mark `IdleCDOCreditVault` `abstract` so it can never be deployed with no-op emergency hooks. If minting during a BB-wipe shutdown is ever intentionally desired (analogous to "minting against credit"), gate it explicitly rather than relying on an empty hook.

### Proof of Concept
Foundry fork test outline (mirroring `testEmergencyShutdown` in `test/foundry/IdleCreditVault.t.sol`, but against an `IdleCDOCreditVault` instance):

```solidity
function testEmergencyShutdownNoOp() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);          // seed vault

    vm.prank(owner);
    idleCDO.emergencyShutdown();        // owner triggers emergency exit

    // BUG: nothing happened
    assertFalse(idleCDO.paused());                 // still unpaused
    assertFalse(idleCDO.skipDefaultCheck());       // no shutdown flag

    // attacker/user can still mint tranche tokens during the "emergency"
    address user = makeAddr('user');
    deal(underlying, user, amount);
    vm.startPrank(user);
    IERC20(underlying).approve(address(idleCDO), amount);
    uint256 minted = idleCDO.depositAA(amount);    // succeeds — minting during emergency
    assertGt(minted, 0);
    vm.stopPrank();
}

function testBBWipeShutdownNoOp() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount * 9 / 10);
    idleCDO.depositBB(amount / 10);

    _createLoss(20_000);                          // wipe BB
    vm.prank(owner);
    idleCDO.updateAccounting();                   // _emergencyShutdown(true) is a no-op

    assertFalse(idleCDO.paused());                // vault still open
    // fresh AA deposits still succeed and mint claims on residual NAV/recovery
    idleCDO.depositAA(ONE_SCALE);                 // does not revert
}
```

Both tests pass on the current code for a deployment whose runtime is `IdleCDOCreditVault`, demonstrating that minting is not prevented during emergency exit.
