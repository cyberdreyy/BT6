### Title
Manipulable ERC4626 valuation mints unbacked epoch interest - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
A programmable-borrower vault prices its ERC4626 position using the vault’s current `convertToAssets` result [1](#0-0) . An unprivileged vault user who can temporarily skew that conversion inflates `totalInterestDueNow()`, which `IdleCDOEpochVariant` then mints as strategy-token interest without receiving corresponding cash [2](#0-1) [3](#0-2) .

### Finding Description
`ProgrammableBorrower.totalInterestDueNow()` treats the current spot delta between `convertToAssets(shares)` and epoch principal as realized yield [4](#0-3) . During a normal programmable-borrower stop, the CDO resolves interest directly from this view and, when `isInterestMinted` is enabled, calls `mintStrategyTokens(_grossInterest)` instead of pulling the reported interest as underlying [5](#0-4) [3](#0-2) . Credit-vault NAV then counts those strategy tokens one-for-one as underlying [6](#0-5) .

An attacker who is both a permitted tranche holder and an ordinary user of the configured ERC4626 vault can:

1. Wait for the owner or manager to start an epoch, causing the programmable borrower to snapshot `epochStartVaultAssets` and park idle assets in the vault [7](#0-6) .
2. Temporarily increase the ERC4626 share price returned by `convertToAssets`, for example by manipulating the pool-reserve state that a spot-priced vault uses.
3. Let the honest manager call `stopEpoch`.
4. The inflated `vaultInterest` is minted to the CDO and distributed into tranche NAV.
5. Revert the external pool manipulation after the stop.
6. Request withdrawal at the inflated tranche price during the buffer.

The CDO’s `_skimDonatedAssets()` only removes raw underlying held directly by the CDO before accounting [8](#0-7) [9](#0-8) . It cannot detect value manufactured inside the ERC4626 share conversion.

### Impact Explanation
The fair-mint invariant is broken: strategy tokens are minted as if borrower yield were received, although the temporary vault valuation cannot necessarily be redeemed. Once `_updateAccounting()` crystallizes the gain, tranche prices and future withdrawal-request bases are inflated. Reversing the valuation leaves the CDO with excess strategy-token liabilities relative to recoverable vault assets.

The quantified loss is the attacker’s pro-rata portion of the phantom minted interest; if the phantom amount exceeds BB NAV, subsequent accounting triggers the BB wipe/default path and creates pool insolvency [10](#0-9) [11](#0-10) .

### Likelihood Explanation
Likelihood depends entirely on the configured ERC4626 vault. A vault whose conversion is backed by durable assets is not vulnerable; a vault whose `convertToAssets` derives from spot reserves, manipulable liquidity, or non-redeemable balances is. The attacker needs no privileged protocol role: the only required protocol actions are being a KYC-passed tranche holder and an ordinary external-vault user, while the honest manager performs `stopEpoch`.

### Recommendation
Do not account ERC4626 `convertToAssets` spot output as earned interest unless the value is independently known to be redeemable. Prefer basing vault PnL on actual `deposit`, `withdraw`, and `redeem` deltas, redeeming/mark-to-realizing gains before minting interest, or restricting programmable borrowers to ERC4626 integrations with manipulation-resistant, audited share pricing. If spot valuation must remain, compare `convertToAssets` against a conservative redeemability measure and cap reportable gains by assets that can actually be withdrawn.

### Proof of Concept
A Foundry mainnet-fork regression can extend the programmable-borrower test setup in `test/foundry/ProgrammableBorrowerCreditVault.t.sol` and substitute an ERC4626 whose `convertToAssets` reflects a manipulable pool reserve:

```solidity
function testSpotConvertToAssetsInflatesMintedInterest() external {
    uint256 amount = 10_000 * oneScale;
    uint256 phantom = 1_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);

    uint256 shares = vault.balanceOf(address(programmableBorrower));
    uint256 assetsBefore = vault.convertToAssets(shares);
    uint256 interestBefore = programmableBorrower.totalInterestDueNow();

    // Unprivileged vault user skews the ERC4626 spot conversion.
    // The vault still cannot necessarily redeem assetsBefore + phantom.
    spotVault.manipulateRate(phantom);

    uint256 inflatedInterest = programmableBorrower.totalInterestDueNow();
    assertEq(inflatedInterest, interestBefore + phantom);

    uint256 aaPriceBefore = cdoEpoch.virtualPrice(address(aaTranche));

    // Honest manager settles the epoch while the valuation is inflated.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // `phantom` was minted as strategy-token interest and crystallized in AA NAV.
    assertGt(cdoEpoch.virtualPrice(address(aaTranche)), aaPriceBefore);
    assertEq(strategy.balanceOf(address(cdoEpoch)), amount + inflatedInterest);

    // Revert the external spot valuation; the minted claims remain.
    spotVault.restoreRate();
    assertLt(vault.convertToAssets(shares), assetsBefore + phantom);

    // Attacker's withdraw request is now based on the inflated tranche price.
    uint256 requested = cdoEpoch.requestWithdraw(
        aaTranche.balanceOf(attacker),
        address(aaTranche)
    );
    assertGt(requested, amount * attackerShare / ONE_TRANCHE_TOKEN);
}
```

The essential assertions are that `totalInterestDueNow()` increases by the manipulated conversion amount, `stopEpoch` mints that amount through `mintStrategyTokens`, and the vault cannot redeem the corresponding assets after the spot value is restored.

  function _virtualPriceAux(
    address _tranche,
    uint256 _nav,
    uint256 _lastNAV,
    uint256 _lastTrancheNAV,
    uint256 _trancheAPRSplitRatio
  ) internal virtual view returns (uint256 _virtualPrice, int256 _totalTrancheGain) {
    // A zero supply identifies a tranche that was never initialized. A non-zero supply with
    // zero NAV is an economically wiped tranche and must keep its saved zero price.
    uint256 trancheSupply = _trancheSupply(_tranche);
    if (trancheSupply == 0) return (oneToken, 0);
    if (_lastNAV == 0 && _nav == 0) return (0, 0);

    // In order to correctly split the interest generated between AA and BB tranche holders
    // (according to the trancheAPRSplitRatio) we need to know how much interest/loss we gained
    // since the last price update (during a depositXX/withdrawXX)
    // To do that we need to get the current value of the assets in this contract
    // and the last saved one (always during a depositXX/withdrawXX)
    // Calculate the total gain/loss
    int256 totalGain = int256(_nav) - int256(_lastNAV);
    // Ordinary zero-delta interactions keep their saved price for compatibility. Forced
    // accounting recomputes NAV per share, which is required after discounted mid-epoch deposits.
    if (totalGain == 0 && !skipDefaultCheck) return (_tranchePrice(_tranche), 0);

    // Remove performance fee for gains
    if (totalGain > 0) {
      totalGain -= totalGain * int256(fee) / int256(FULL_ALLOC);
    }

    bool _isAATranche = _tranche == AATranche;
    // A class with no saved NAV cannot be revived by later gains. If only this class has saved
    // NAV, it receives the full gain or loss; otherwise both classes participate.
    if (_lastTrancheNAV == 0) {
      _totalTrancheGain = 0;
    } else if (_lastNAV == _lastTrancheNAV) {
      _totalTrancheGain = totalGain;
    } else {
      if (totalGain > 0) {
        // Split the net gain, according to _trancheAPRSplitRatio, with precision loss favoring the AA tranche.
        int256 totalBBGain = totalGain * int256(FULL_ALLOC - _trancheAPRSplitRatio) / int256(FULL_ALLOC);
        // The new NAV for the tranche is old NAV + total gain for the tranche
        _totalTrancheGain = _isAATranche ? (totalGain - totalBBGain) : totalBBGain;
      } else {
        int256 maxBBLoss = -int256(lastNAVBB);
        int256 totalBBLoss = totalGain > maxBBLoss ? totalGain : maxBBLoss;
        _totalTrancheGain = _isAATranche ? totalGain - totalBBLoss : totalBBLoss;
      }
    }
    // Split the new NAV (_lastTrancheNAV + _totalTrancheGain) per tranche token
    _virtualPrice = uint256(int256(_lastTrancheNAV) + _totalTrancheGain) * ONE_TRANCHE_TOKEN / trancheSupply;
