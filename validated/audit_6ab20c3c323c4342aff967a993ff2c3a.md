Confirmed: `get_builder_withdrawals` (specs/gloas/beacon-chain.md:1802-1834) constructs the `Withdrawal.amount` directly from `withdrawal.amount` (the raw, uncapped requested amount stored in `state.builder_pending_withdrawals`), while `apply_withdrawals` (specs/gloas/beacon-chain.md:1920-1932) deducts only `min(withdrawal.amount, builder_balance)` from the builder's CL-tracked balance. This is exactly analogous to the reported Solidity bug: an amount is trusted/propagated to an external payout (the EL withdrawal credited to `fee_recipient`) without being validated against the actual backing balance at the point the payment is committed. This matches the confirmed test `test_builder_withdrawal_insufficient_balance` (tests/core/pyspec/eth_consensus_specs/test/gloas/block_processing/test_process_withdrawals.py:116-155), which explicitly documents `withdrawal.amount == 5 ETH (requested amount)` while `builders[0].balance` is capped to `0` — i.e., the EL-facing `Withdrawal.amount` field is asserted, by the test itself, to remain the uncapped/requested value even though the CL-side deduction is capped.

### Title
Builder pending-withdrawal `amount` is not capped to builder balance before being committed to the execution-payload `Withdrawal` — (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` emits a `Withdrawal` object whose `amount` equals the raw value stored in `state.builder_pending_withdrawals[i].amount`, not `min(amount, builder.balance)`. `apply_withdrawals` then caps only the *beacon-state* deduction to the available `builder.balance`, but the beacon block still commits (via `payload_expected_withdrawals`) to the uncapped `Withdrawal.amount`, which the execution layer is required to honor as an unconditional credit to `withdrawal.address`.

### Finding Description
- `get_builder_withdrawals` (specs/gloas/beacon-chain.md:1802-1834) builds each `Withdrawal` with `amount=withdrawal.amount` taken verbatim from `state.builder_pending_withdrawals`.
- `apply_withdrawals` (specs/gloas/beacon-chain.md:1920-1932) only decreases `state.builders[builder_index].balance` by `min(withdrawal.amount, builder_balance)` — i.e., the *consensus-layer* accounting saturates at the available balance.
- However, `process_withdrawals` sets `state.payload_expected_withdrawals` to the *uncapped* withdrawal list (specs/gloas/beacon-chain.md, `update_payload_expected_withdrawals`), and per the withdrawals model (as in Capella/Electra/Gloas), the execution layer credits `withdrawal.amount` gwei to `withdrawal.address` unconditionally, because withdrawals are a commitment the block "must honor" (see the note at specs/gloas/beacon-chain.md:1969-1990: "any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals in the execution layer").
- A builder's pending withdrawal `amount` originates from `builder_pending_payments`/bids that were validated against `can_builder_cover_bid` *at bid time* (specs/gloas/beacon-chain.md `can_builder_cover_bid`, lines ~1167-1179), but the builder's balance can be reduced between bid-acceptance and withdrawal-settlement time by any of: additional bids being accepted concurrently in the same or later slot, other pending payments/withdrawals being queued and processed first in the same withdrawal-processing pass (priority order is builder-pending > partial > builder-sweep > validator-sweep, so an earlier entry can drain the balance an entry later in the same list expected to use), or multiple entries in `builder_pending_withdrawals` for the same builder (explicitly tested in `test_duplicate_builder_index_in_pending_withdrawals`).
- When the balance is insufficient, `state.builders[i].balance` correctly saturates to 0, but the `Withdrawal.amount` field sent to the EL still equals the full, unbacked requested amount. This breaks the equality "Gwei paid to fee_recipient == Gwei actually available/backed in builder.balance": the EL will mint/credit ETH to `fee_recipient` that was never actually held by the builder.

### Impact Explanation
This is a direct Gwei-creation bug: the execution layer would credit an address with Gwei that has no corresponding decrease anywhere in the consensus state once the builder's balance is exhausted (it can only go to 0, not negative). This satisfies the Critical impact bar ("Gwei created ... paid to a non-owner") since `fee_recipient` receives value not backed by any deposit or existing balance.

### Likelihood Explanation
Likelihood depends on whether this divergence (uncapped `Withdrawal.amount` vs. capped state deduction) is reachable under the spec's own invariants without requiring a malicious peer, coalition, or client bug — i.e., whether a single builder (its own bidder) or an adversarial builder can legitimately end up with `builder_pending_withdrawals` amounts exceeding its balance at settlement time purely through spec-following block production (e.g., queuing multiple payments against a shrinking balance, or balance draining from a concurrent sweep/exit). The test suite explicitly exercises and appears to accept this exact scenario (`test_builder_withdrawal_insufficient_balance`), asserting `withdrawal_amounts_builders={builder_index: withdrawal_amount}` (the full requested amount) as the *expected*, passing outcome — suggesting this behavior may be an intentionally-accepted design characteristic (i.e., the EL-side Withdrawal is defined/expected to carry the pre-cap amount) rather than an actual bug, OR that the real safety net exists elsewhere (e.g., a stronger invariant enforced earlier that prevents `builder_pending_withdrawals` amounts from ever exceeding balance in practice, given `can_builder_cover_bid` gates bid acceptance). I could not fully verify from the indexed context whether some invariant elsewhere in the state machine (e.g., a hard assertion that `sum of pending amounts for a builder <= balance` is maintained at all times) prevents this divergence from ever manifesting, nor whether the "amount" field semantics for builder withdrawals are explicitly documented as "the EL applies min(amount, balance) too" (mirroring the CL) rather than crediting the raw amount. ### Recommendation
Clarify (and if necessary fix) the semantics of builder-pending-withdrawal amounts so that the `Withdrawal.amount` field committed to the execution payload is always `min(requested_amount, builder.balance_at_settlement)`, matching the capped CL-side deduction, so the execution layer never credits more Gwei than the builder actually had. This likely requires either (a) capping the amount inside `get_builder_withdrawals` itself using a running/simulated balance across the list of pending withdrawals for that builder, or (b) explicitly documenting that the execution layer must independently cap the credited amount to the CL-committed balance decrease, and verifying this is enforced by consensus rules (not just by convention).

### Proof of Concept
Given a builder `B` with `balance = 1 ETH`, and two entries appended to `state.builder_pending_withdrawals` for `B`: `[{amount: 1 ETH}, {amount: 1 ETH}]` (e.g., from two separate bids each individually satisfying `can_builder_cover_bid` at different times before the balance dropped), `get_builder_withdrawals` emits two `Withdrawal` objects each with `amount = 1 ETH` (total 2 ETH committed to the EL). `apply_withdrawals` decreases `B.balance` by `min(1 ETH, 1 ETH) = 1 ETH` for the first, then `min(1 ETH, 0) = 0` for the second — CL-side, only 1 ETH total is deducted, yet the execution payload commits to crediting 2 ETH total to the respective `fee_recipient`s, creating 1 ETH of Gwei with no corresponding CL-side backing.

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
