### Title
Multisig request execution below intended threshold via stale confirmations from removed members - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` counts confirmations previously recorded against a `request_id` without ever re-validating that the signer/member who cast each confirmation is still an authorized signer of the multisig at execution time. When a member/key is removed via a `DeleteKey`/`DeleteMember` action, any confirmation that member already placed on a *different*, still-open request is never purged. That stale confirmation continues to count toward `num_confirmations`, letting a request execute with fewer currently-authorized signers than the configured threshold.

### Finding Description
Confirmations are stored per `request_id` in a set (`self.confirmations`) that is only touched in two places: `confirm()` (adds the caller's key/member) and `remove_request()` (wipes the set, but only for the request being executed or deleted) [1](#0-0) . Removing a member from the multisig (`DeleteKey`/`DeleteMember`) is handled purely as an `execute_request` side effect for the request that removes the member [2](#0-1) ; there is no logic anywhere that iterates over other outstanding `requests`/`confirmations` to strip out confirmations belonging to the member being removed.

`confirm()` in both `multisig` and `multisig2` performs a purely numeric threshold check: it takes whatever is already stored in `confirmations` for the given `request_id` and compares its cardinality to `num_confirmations`:
```
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
}
``` [3](#0-2) 
There is no check that every entry already in `confirmations` still corresponds to a live `MultisigMember`/access key. This mirrors exactly the class of bug in the reference report: a recorded claim (a confirmation "counted" toward the threshold) is not kept in sync with the actual live custody set (currently authorized signers) after that set changes.

Concretely:
1. Members A, B, C run a 2-of-3 multisig. B adds a `Transfer` request `X` and confirms it (`confirmations[X] = {B}`), but a second confirmation is not yet supplied, so `X` stays pending.
2. Separately, A and C use a second request to remove B (`DeleteMember`/`DeleteKey`) because B's key is considered compromised or is being rotated out. This request only manipulates `requests`/`confirmations` for *that* removal request; `confirmations[X]` still contains `{B}`.
3. The multisig is now supposed to be governed only by A and C (2-of-2, or still 2-of-3 with B invalid). A (a single live signer) calls `confirm(X)`. Because `confirmations[X].len() + 1 = 2 >= num_confirmations (2)`, request `X` executes and moves funds, even though only **one** currently-live member (A) actually approved it — B's stale confirmation, cast before removal, is silently reused as if it were still a valid, live confirmation.

This breaks the intended equality "confirmations counted == confirmations from currently live members" and lets a `Transfer`/`FunctionCall`/`AddKey` request execute below the real, current threshold — this is explicitly one of the "Critical" impacts in scope ("a multisig request executed below threshold").

The README's own "Gotchas" note only discusses the *opposite* failure mode (too many keys removed so the contract can never reach `num_confirmations` again) [4](#0-3) , and does not address that stale confirmations from removed members are never invalidated for other in-flight requests.

### Impact Explanation
Critical: this allows a multisig-controlled account to authorize a `Transfer`, `AddKey`/`AddMember` (with full-access-key escalation), `FunctionCall`, or `DeployContract` action with fewer currently-authorized approvals than the configured `num_confirmations`. In the worst case, NEAR held by the multisig account can move, or the multisig's key/member set can be further modified, based on approval from a set of signers that is smaller than the account's actual security threshold — a direct threshold-bypass on custody of funds.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that rotates or removes members/keys while requests are pending — a normal operational event (e.g., offboarding a team member, rotating a compromised key) rather than an edge case. Any request left open (unconfirmed) at the time of a member removal permanently retains the departed member's confirmation weight until that request is confirmed/executed or explicitly deleted.

### Recommendation
When executing a `DeleteKey`/`DeleteMember` action, iterate over all outstanding requests and strip confirmations belonging to the removed member/key (or, alternatively, validate at `confirm()`/execution time that every entry in `confirmations` for the request still corresponds to a currently valid member before counting it toward `num_confirmations`).

### Proof of Concept
Conceptual sequence (see `multisig2/src/lib.rs` `confirm`/`execute_request`) [3](#0-2) :
1. Initialize with 3 members `{A, B, C}`, `num_confirmations = 2`.
2. `B` calls `add_request_and_confirm` for `Transfer{amount}` → request `X` has `confirmations[X] = {B}`.
3. `A` and `C` create and confirm a separate `DeleteMember{B}` request, which executes and removes `B` from the member set.
4. `A` calls `confirm(X)`. `confirmations[X].len() + 1 == 2 >= num_confirmations`, so `X` executes and the transfer is sent — approved effectively by only one live member (`A`), with `B`'s stale, pre-removal confirmation still being counted.

Note: I could not fully trace the `DeleteMember`/`DeleteKey` handler bodies beyond the `execute_request` dispatch shown, so I cannot rule out that some other layer purges stale confirmations elsewhere in the file; based on everything reachable via the index, no such purge logic exists in `confirm`, `remove_request`, or the `execute_request` match arms for `AddMember`/`DeleteMember`/`AddKey`/`DeleteKey`. Given index size limits, a full manual review of `multisig/src/lib.rs` and `multisig2/src/lib.rs` in a Devin session is recommended to confirm no purge step exists elsewhere.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
