### Title
Stale Confirmations From Removed Multisig Members Are Still Counted Toward Execution Threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges the requests *created by* the removed member, but never scrubs that member's confirmation entries from other, still-pending requests created by *other* members. Because `confirm()` counts confirmations purely by set size (`confirmations.len() as u32 + 1 >= self.num_confirmations`) without checking that every recorded confirmer is still a current member, a member who is later removed can have their earlier "yes" vote silently counted toward executing a request after they are no longer authorized. This lets a request execute with fewer live, currently-authorized approvals than `num_confirmations` requires.

### Finding Description
`confirm()` records confirmations keyed by `request_id -> HashSet<String>` where each string is `MultisigMember::to_string()`: [1](#0-0) 

When a member is removed, `delete_member` cleans up requests keyed by that member as *requester*, but does not touch confirmation sets on requests created by *other* members where the removed member had already voted: [2](#0-1) 

`remove_request`/`confirm` never re-validate that each string stored in a request's confirmation `HashSet` still corresponds to a member in `self.members`: [3](#0-2) 

The invariant that should hold is:
```
confirmations.len() (counted toward threshold) == number of *currently authorized* members who approved
```
This invariant is violated: a stale confirmation from a since-removed member remains in the set and is still counted, so:
```
confirmations counted > confirmations from live members
```

**Concrete scenario (root cause proven step by step):**
1. Multisig has members `{A, B, C, D}`, `num_confirmations = 3`.
2. `B` calls `add_request` for request `R1` (e.g., `Transfer` to an attacker-controlled account). `A` calls `confirm(R1)` — `confirmations[R1] = {A}` (1/3, not yet executed) — per `confirm()` logic at [4](#0-3) .
3. Separately, `B`, `C`, `D` (3 confirmations, satisfying threshold) execute a `DeleteMember { member: A }` request. `A` is removed from `self.members`, but `R1`'s confirmation set `{A}` is untouched because `delete_member`'s cleanup loop only targets requests where `r.member == A` (i.e., requests *authored* by `A`), and `R1` was authored by `B` — see filter at [5](#0-4) .
4. Now members are `{B, C, D}`. `B` calls `confirm(R1)` → `confirmations[R1] = {A, B}` (2). `C` calls `confirm(R1)` → set size reaches 3, `3 >= num_confirmations`, and `R1` (the transfer) executes — even though only `B` and `C`, i.e., 2 of the 3 currently live members, actually approved it in real time. `A`'s stale, revoked approval was counted as the third vote.

This breaks the custody/authorization binding the multisig is supposed to enforce: a transaction should only execute once *live* members currently in `self.members` provide `num_confirmations` approvals; instead a departed member's historical vote can be recycled to reach quorum.

### Impact Explanation
This matches the Critical impact category "a multisig request executed below threshold." A high-value action (`Transfer`, `AddKey`/full-access-key grant, `DeployContract`, `FunctionCall`, etc.) can be pushed through with one fewer genuinely live approver than the multisig's configured `num_confirmations`, effectively lowering the real security threshold of the account without any of the current members explicitly consenting to that reduction. In the extreme (e.g., `num_confirmations = 2` and one stale vote already recorded), a single currently-authorized member could unilaterally execute an arbitrary action such as transferring the account's entire NEAR balance or adding a full access key, since the removed member's leftover vote supplies the "second" confirmation.

### Likelihood Explanation
No privileged role is required beyond being one of the existing members (which is the standard, expected multisig actor) — no foundation, redeploy, victim key, or social engineering is needed. The sequence (pending un-executed request + a later, unrelated member-removal + resumed confirming) is a realistic and plausible ordering of routine multisig operations (rotating/removing signers while other requests are in flight), not a contrived edge case, and it is fully reachable through the public `add_request`, `confirm`, and `DeleteMember`-action `execute_request` flow.

### Recommendation
In `confirm()` (and/or in `delete_member`), validate that every string in a request's confirmation set still corresponds to a `MultisigMember` present in `self.members` before counting it toward `num_confirmations`; alternatively, when removing a member in `delete_member`, iterate *all* pending requests (not only those authored by that member) and strip that member's entry from each confirmation set, or discard requests entirely if the resulting live-confirmation count could no longer legitimately reach threshold organically.

```rust
let mut c = MultiSigContract::new(vec![member_a(), member_b(), member_c(), member_d()], 3);

// Step 1: B creates R1 (transfer to attacker), A confirms it (1/3)
testing_env!(ctx_for(member_b()));
let r1 = c.add_request(transfer_request(attacker(), amount));
testing_env!(ctx_for(member_a()));
c.confirm(r1); // confirmations[r1] = {A}

// Step 2: B, C, D remove A via DeleteMember (their own 3-of-3 quorum among B,C,D+prior state)
testing_env!(ctx_for(member_b()));
let r2 = c.add_request(delete_member_request(member_a()));
c.confirm(r2);
testing_env!(ctx_for(member_c()));
c.confirm(r2);
testing_env!(ctx_for(member_d()));
c.confirm(r2); // executes DeleteMember{A}; members now {B,C,D}
// r1's confirmations set still contains "A" — untouched by delete_member's cleanup,
// since delete_member only purges requests where r.member == A (r1 was authored by B).

// Step 3: B and C (only 2 *live* members) push R1 over threshold using stale "A" vote
testing_env!(ctx_for(member_b()));
c.confirm(r1); // confirmations[r1] = {A, B} -> size 2
testing_env!(ctx_for(member_c()));
c.confirm(r1); // confirmations[r1] size reaches 3 >= num_confirmations(3) -> R1 EXECUTES
// Transfer executes though only 2 currently-live members (B, C) approved in real time.
```
This demonstrates that `remove_request`/`confirm` at [1](#0-0)  and the incomplete cleanup in `delete_member` at [2](#0-1)  together allow a request to execute below the intended live-member confirmation threshold.

```rust
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
```

```rust
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
```

```rust
    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .unwrap_or_else(|| env::panic_str("Failed to remove existing element"));
        // decrement num_requests for original request signer
        let original_member = request_with_signer.member;
        let mut num_requests = self
            .num_requests_pk
            .get(&original_member.to_string())
            .unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_member.to_string(), &num_requests);
        // return request
        request_with_signer.request
    }
```
