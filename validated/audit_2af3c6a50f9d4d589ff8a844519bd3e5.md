### Title
Bank interest silently skipped via `update_bank_cache` advancing `last_update` without accruing interest in Drift/Kamino/JupLend/Solend integration deposit/withdraw paths - (File: `programs/marginfi/src/instructions/drift/deposit.rs`, `programs/marginfi/src/state/bank.rs`)

### Summary
This is the same bug class as the Taiko `anchor()` issuance flaw: the time-tracking field used to compute the period for interest/fee accrual (`last_update`) is advanced in a location that is decoupled from the accrual math itself, causing part of the elapsed time to never be charged interest.

### Finding Description
`Bank::accrue_interest` computes `time_delta = current_timestamp - self.last_update`, applies interest for that period, and only then sets `self.last_update = current_timestamp` [1](#0-0) . This coupling is correct when both operations happen together.

However, `Bank::update_bank_cache` independently overwrites `self.last_update = Clock::get()?.unix_timestamp;` at the end of its own execution, entirely outside of `accrue_interest` [2](#0-1) .

In `drift_deposit`, the instruction calls `bank.update_bank_cache(&group)` but never calls `bank.accrue_interest(...)` in this instruction path [3](#0-2) . Since `update_bank_cache` unconditionally sets `last_update` to the current clock timestamp, any elapsed time since the bank's last real accrual is silently discarded — the next call to `accrue_interest` will compute `time_delta` from this artificially advanced `last_update`, permanently losing the interest that should have accrued for the skipped interval. This mirrors the root cause in the Taiko report: a time/period-tracking variable (`lastSyncedBlock` in Taiko, `last_update` in marginfi) is advanced by a code path that is not synchronized with the actual accrual/issuance calculation, corrupting the elapsed-period accounting used by that calculation.

Other integration instructions (`kamino/deposit.rs`, `kamino/withdraw.rs`, `juplend/deposit.rs`, `juplend/withdraw.rs`, `solend/deposit.rs`, `solend/withdraw.rs`, `drift/withdraw.rs`) all call `update_bank_cache` and would need to be checked individually for whether `accrue_interest` is also invoked in the same instruction; `drift_deposit` was confirmed to lack it.

### Impact Explanation
Unlike Taiko (which halts the chain due to a strict base-fee equality check), marginfi has no equivalent consistency check on `last_update`/accrued interest, so this does not halt the chain. However, it causes a durable, unrecoverable loss of interest income for lenders and understatement of liabilities for borrowers on the affected bank for every period a Drift deposit occurs without an intervening `accrue_interest` call. Since interest accrual underpins asset/liability share values used throughout health checks, liquidations, and withdrawals, this represents an exploitable misvaluation with financial effect: repeated interaction via `drift_deposit` timed to occur before other instructions trigger `accrue_interest` would suppress interest charges on borrowers and yield to lenders.

### Likelihood Explanation
Likelihood is moderate-to-high: `drift_deposit` is a normal permissionless user action (any user with a Drift-tagged bank can call it), requires no special privileges, and simply needs to be the first instruction to touch a bank in a given period to suppress that period's accrual. Because `update_bank_cache` is called in many integration paths, this pattern could recur across all Drift/Kamino/JupLend/Solend deposit and withdraw instructions, increasing the practical likelihood that some accrual-skipping window exists in normal operation.

### Recommendation
Ensure `update_bank_cache` never advances `self.last_update` independently of `accrue_interest`. Either remove the `self.last_update = Clock::get()?.unix_timestamp;` line from `update_bank_cache` (letting only `accrue_interest` own that field), or require every instruction that calls `update_bank_cache` to call `accrue_interest` first (as `lending_pool_accrue_bank_interest` and `lending_pool_emissions_deposit` correctly do [4](#0-3) ), and add an assertion/CI check that flags any call site of `update_bank_cache` lacking a preceding `accrue_interest` call on the same bank.

### Proof of Concept
1. Bank B has outstanding assets and liabilities; `last_update = T0`.
2. Time passes to `T1` without any `accrue_interest` call on B.
3. A user calls `drift_deposit` on B. This path calls only `bank.update_bank_cache(&group)` [5](#0-4) , which sets `bank.last_update = T1` via `Clock::get()?.unix_timestamp` [6](#0-5) , without ever computing/crediting interest for the `[T0, T1]` interval.
4. The next `accrue_interest` call (e.g., at `T2`) only accrues for `[T1, T2]`, permanently losing interest for `[T0, T1]`.

Note: I was not able to fully verify within the available tool budget whether Kamino/JupLend/Solend deposit/withdraw instructions also call `update_bank_cache` without a preceding `accrue_interest`; each should be individually reviewed to confirm the same pattern.
