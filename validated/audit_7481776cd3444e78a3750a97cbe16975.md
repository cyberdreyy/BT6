### Title
Permissionless, race-able `init_global_fee_state` allows an attacker to seize the global fee admin role - ([File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs])

### Summary
`init_global_fee_state` (the `InitFeeState` accounts struct) initializes the program-wide `FeeState` PDA, whose seeds are the constant `FEE_STATE_SEED` only — there is exactly one such account per deployed program. The instruction accepts arbitrary `admin_key` / `fee_wallet` arguments from any caller and writes them directly into the account with no check that the caller is the program's deployer or any other privileged party. This is the same bug class as the reported NoteERC20 issue: a state-defining "initializer" that anyone can race to call first, permanently seizing a privileged role, because there is no mechanism forcing initialization to happen atomically with, or restricted to, deployment.

### Finding Description
`init_global_fee_state` is documented as "(Runs once per program)" and its account context has no admin/authority gate: [1](#0-0) 

```
pub struct InitFeeState<'info> {
    /// Pays the init fee
    #[account(mut)]
    pub payer: Signer<'info>,

    #[account(
        init,
        seeds = [FEE_STATE_SEED.as_bytes()],
        bump,
        payer = payer,
        space = 8 + FeeState::LEN,
    )]
    pub fee_state: AccountLoader<'info, FeeState>,

    pub system_program: Program<'info, System>,
}
```

`payer` is just any `Signer`, and `fee_state` is derived from a fixed, program-wide seed with no per-deployer or per-authority component. The handler then writes the attacker-supplied `admin_key` and `fee_wallet` straight into the new account: [2](#0-1) 

```
pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    ...
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    ...
```

I confirmed via a repo-wide search that no instruction anywhere checks the BPF upgrade authority, a hardcoded deployer pubkey, or any other privileged constraint before allowing this call — the only gate is Anchor's `init` constraint, which merely fails if the PDA already exists (i.e., it prevents re-initialization, but not initialization by an unauthorized party).

Because the `FeeState` PDA address is fully deterministic from the immutable program ID (`Pubkey::find_program_address(&[FEE_STATE_SEED], program_id)`), an attacker does not even need to observe a specific pending transaction to front-run — as soon as the program is deployed/upgraded to include this instruction (or on a fresh deployment), anyone can submit `init_global_fee_state` and win the race to become `global_fee_admin`, exactly mirroring the front-runnable `initialize()` pattern described in the report (a two-step "create-then-initialize" object where initialization is unauthenticated).

This mirrors the external report's root cause precisely: (1) a privileged singleton object, (2) whose initializing call is publicly invocable, (3) with no atomicity/authorization tying it to the legitimate deployer.

### Impact Explanation
`global_fee_admin` is a high-privilege role. It can:
- Redirect protocol fees by setting `global_fee_wallet` to itself via `edit_global_fee_state` [3](#0-2) 
- Set `program_fee_fixed` / `program_fee_rate` to the attacker's advantage.
- Pause/unpause the entire protocol via `panic_pause`/`panic_unpause`, which are gated to `global_fee_admin`/`pause_delegate_admin` [4](#0-3) , causing a protocol-wide denial of service.
- Since `FeeState` cannot be reinitialized once created (Anchor's `init` will fail on an existing PDA) and there is no "close/replace" path for this genesis object, the legitimate team's only recovery would be to redeploy under a new program ID — an unrecoverable-cost DoS identical in spirit to the report's conclusion ("preventing... contract deployment... unrecoverable gas expenses").

### Likelihood Explanation
This requires no privileged access, staked capital, or complex preconditions — only observing that the program has been deployed (or upgraded to add this ix, if it wasn't present before) and submitting one transaction with attacker-controlled arguments before the legitimate operator's transaction lands. On a public network this is a straightforward race/front-run and is analogous to well-known "unprotected initializer" vulnerabilities. It is fully reachable by any unprivileged actor.

### Recommendation
Restrict `init_global_fee_state` (and `init_global_fee_state_v2`) to a hardcoded authority (e.g., verify `payer.key()` against the program's BPF upgrade authority read from the program-data account, or a compile-time constant deployer pubkey) rather than accepting an arbitrary `admin_key`/`payer`. Alternatively, deploy and initialize in the same atomic transaction as part of the program's release tooling and add a defensive check requiring the initializing signer to match a known constant before the account is written.

### Proof of Concept
1. Attacker monitors the chain (or simply knows the immutable `marginfi::ID` once the program binary is deployed).
2. Attacker derives the deterministic PDA: `Pubkey::find_program_address(&[FEE_STATE_SEED.as_bytes()], &marginfi::ID)`.
3. Attacker submits `init_global_fee_state(admin_key = attacker, fee_wallet = attacker_wallet, ...)` signed only by their own keypair as `payer`, exactly as shown in the test harness call pattern: [5](#0-4) .
4. If this lands before the legitimate team's own `init_global_fee_state` call, the `FeeState` PDA is now permanently owned by the attacker (`global_fee_admin = attacker`), and the legitimate team's subsequent call fails because the `init` constraint requires the account not already exist.
5. Attacker now calls `edit_global_fee_state` to redirect fees to `attacker_wallet` and/or `panic_pause` to halt the protocol.
