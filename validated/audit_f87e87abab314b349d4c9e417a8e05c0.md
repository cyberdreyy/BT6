### Title
JWT replay cache TOCTOU race allows concurrent replay of a captured signed request - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`(*WorkflowMetadataHandler).Authorize` checks `h.jwtCache.isReplay(claims.ID)` and later calls `h.jwtCache.recordUsage(claims.ID)`, but these are two independent lock acquisitions (`RLock`/`RUnlock` then separate `Lock`/`Unlock`) with authorization logic executed in between, so there is no atomic check-and-set. Two concurrent `Authorize` calls presenting the identical previously-observed JWT can both pass `isReplay` before either calls `recordUsage`, allowing the same signed request to be processed twice.

### Finding Description
`Authorize` in [1](#0-0)  verifies the JWT signature, then calls `h.jwtCache.isReplay(claims.ID)` to reject already-used `jti`s, performs authorized-key lookups, and only afterward calls `h.jwtCache.recordUsage(claims.ID)`. The cache implementation uses separate lock scopes for the read-check and the write-record: [2](#0-1) 

Because `isReplay` (RLock) and `recordUsage` (Lock) are not combined into a single atomic critical section, and there's a non-trivial amount of work (authorized-key map lookup, string operations, logging) between them, two goroutines calling `Authorize` with the same `jti` concurrently can both observe `isReplay == false` before either calls `recordUsage`. Both then pass the authorization check and return the same `AuthorizedKey`, and both proceed to `HandleUserTriggerRequest` in [3](#0-2) , which independently resolves the workflow and calls `authorizeRequest` → `Authorize` ( [4](#0-3) ), then proceeds to rate-limiting, execution-ID generation, and dispatch to the DON via `sendWithRetries`.

The attacker precondition is possession of a previously-observed valid signed JWT (e.g., replayed from a network capture or log, per the question's stated precondition). Firing two such requests concurrently (same `req.Auth` token, same body/signature) exploits the race window between `isReplay` and `recordUsage`, since nothing in `HandleUserTriggerRequest`'s pipeline (request-ID uniqueness check in `setupCallback`, rate limiting) deterministically blocks two identical replays from reaching the underlying DON dispatch layer if their `req.ID` (request ID) also matches — though note that `setupCallback`'s `h.callbacks[requestID]` uniqueness check ( [5](#0-4) ) would reject a second concurrent request bearing the *same* `req.ID`, since it holds `callbacksMu` for its whole check-and-insert. This means a full duplicate execution of the *identical* JSON-RPC request would additionally require an identical `req.ID`, which is only possible if the two concurrent submissions are literally the same request replayed at the JSON-RPC transport layer.

### Impact Explanation
This is a real TOCTOU bug in the JWT anti-replay mechanism: the two-phase check-then-record pattern is not atomic, matching the CWE-367 (Time-of-check Time-of-use) pattern. However, the exploitable end-to-end impact is constrained by `setupCallback`'s separately-locked, atomic request-ID uniqueness check, which serializes duplicate `req.ID`s under `callbacksMu` and will reject the second concurrent identical request before it reaches shard dispatch. So while `Authorize` itself can be bypassed twice for the same `jti`, the downstream idempotency guard largely prevents duplicate workflow execution for identical requests. This still represents a genuine authentication-soundness weakness — the JWT replay-prevention guarantee ("this token can be used exactly once") is violated at the `Authorize` layer, and if request IDs are ever attacker-chosen to differ (though `Authorize` verifies the JWT covers the whole `req` via `utils.VerifyRequestJWT(token, *req)`, meaning changing `req.ID` invalidates the signature) — this closes off most practical avenues for divergent duplicate execution. The scoped impact under the stated invariant (AUTHENTICATION_SOUNDNESS / no replay) is best characterized as a narrow race window rather than a full "duplicate/unauthorized workflow execution impersonating another signer," because the signature covers the full request body including `req.ID`, and `setupCallback`'s atomicity blocks the identical-ID duplicate from causing two separate DON dispatches.

### Likelihood Explanation
Precondition requires the attacker to have observed/intercepted a genuine, previously-issued valid JWT for an authorized signer — this is an unusual precondition (the question specifies it, e.g. via log/timing side channel, which is outside what's verifiable from this code alone). Given that precondition, firing two goroutine-concurrent `Authorize` calls with the identical token is trivially reproducible in a race-mode unit test, since the RLock/Lock window is real and unguarded by a single mutex or `sync.Map`-style atomic `LoadOrStore`.

### Recommendation
Replace the separate `isReplay`/`recordUsage` calls with a single atomic check-and-set operation guarded by one lock (or use `sync.Map.LoadOrStore`), e.g. add a `checkAndRecord(jti string) bool` method on `jwtReplayCache` that acquires `mu.Lock()` once, checks existence, and inserts atomically, returning whether it was already present. Call this single atomic method from `Authorize` instead of the current two-step check-then-record pattern.

### Proof of Concept
Go test in `workflow_metadata_handler_test.go`:
1. Construct a `jwtReplayCache` (or full `WorkflowMetadataHandler` with a stubbed `authorizedKeys` map and a valid signed JWT/`jti`).
2. Launch two goroutines that concurrently call `cache.isReplay(jti)` followed by `cache.recordUsage(jti)` (mirroring `Authorize`'s exact sequence), with a synchronization barrier (e.g. both goroutines call `isReplay` before either calls `recordUsage`, using a `sync.WaitGroup`/channel to force interleaving).
3. Assert that both goroutines observe `isReplay(jti) == false`, demonstrating the TOCTOU window exists at the cache level.
4. Additionally write a handler-level test calling `(*WorkflowMetadataHandler).Authorize` twice concurrently with the same token/req and confirm that under `-race` with forced goroutine scheduling (e.g. inserting a `sync.WaitGroup` hook between `isReplay` and `recordUsage` for test purposes), both calls can return `nil` error — proving the check-then-act race, independent of whether `setupCallback`'s separate request-ID lock ultimately prevents duplicate execution.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)
}

	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
