### Title
Cross-user response hijacking via attacker-controlled `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each pending callback in `h.savedCallbacks` keyed solely by the client-supplied `msg.Body.MessageId`, with no binding to the sender/signer of the message. Because `MessageId` is fully attacker-controlled and the gateway performs no allowlisting of senders (explicitly marked `// TODO: apply allowlist and rate-limiting here`), any unauthenticated party holding an arbitrary private key can submit a signed `web_api_trigger` message reusing a victim's in-flight `MessageId`, overwriting the victim's callback entry and redirecting the eventual DON response to the attacker.

### Finding Description
The gateway's `ProcessRequest` (`core/services/gateway/gateway.go`) decodes and `Validate()`s an incoming `api.Message`, which only checks signature format/length and populates `Body.Sender` from the recovered signer — it does not verify the sender against any allowlist for the DON before dispatching to `HandleLegacyUserMessage`. [1](#0-0) 

Inside `HandleLegacyUserMessage`, after minimal payload/timestamp/method validation, the handler stores the callback keyed only by `msg.Body.MessageId`: [2](#0-1) 

`MessageId` is a plain client-supplied string field (`api.MessageBody.MessageId`), not derived from the sender or generated by the gateway: [3](#0-2) 

When the DON later responds, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `msg.Body.MessageId` — again with no check that the response corresponds to the same sender/request that originally registered the callback: [4](#0-3) 

Exploit flow:
1. Victim submits `Message{MessageId:"M", Sender: victim}`. Handler stores `savedCallbacks["M"] = victimCallback` and forwards the request to all DON members.
2. Before the DON responds, attacker (any signer, no allowlist required at this stage) submits `Message{MessageId:"M", Sender: attacker}`. Handler overwrites `savedCallbacks["M"] = attackerCallback` and forwards its own request to the DON members.
3. When a node eventually replies with `MethodWebAPITrigger` and `MessageId:"M"` (in response to either the victim's or the attacker's original request), `handleWebAPITriggerMessage` retrieves whatever callback currently occupies key `"M"` — now the attacker's — and delivers the response there via `savedCb.SendResponse(...)`.
4. The victim's callback is silently discarded (its `Wait()` will eventually time out), and the attacker receives a response tied to a request/execution that isn't theirs, or the victim's legitimate response is dropped entirely (DoS).

The existing test `savedCallbacks stored only when message is valid` only asserts that invalid messages don't leave residue in the map; it never asserts per-sender isolation of a shared `MessageId`. [5](#0-4) 

### Impact Explanation
This is a cross-user response confusion vulnerability: an attacker can hijack another user's pending web API trigger callback, gaining a delivery point for the DON's execution response, or cause denial of service by discarding the victim's response entirely. This matches Chainlink bounty impact classes around unauthorized access to another user's request/response data and request impersonation within the gateway.

### Likelihood Explanation
No authentication/authorization beyond a valid ECDSA signature is required to reach `HandleLegacyUserMessage` — any private key works, since sender allowlisting is explicitly not implemented yet (`// TODO: apply allowlist and rate-limiting here`). The only precondition is knowing or guessing a victim's in-flight `MessageId` before the DON responds (a race window of up to `CallbackMaxAgeSec`, default 120s). Many client/workflow implementations use predictable or sequential `MessageId` schemes, making collision feasible; even without prediction, this is a straightforward correctness bug that could be triggered by an accidental collision as well as a deliberate attack, and is fully reproducible with a unit test.

### Recommendation
Bind the `savedCallbacks` map key to both `MessageId` and the requester's identity (e.g. key by `Sender + ":" + MessageId`, or store the original `Sender` in `savedCallback` and verify it matches before overwriting an existing entry or before delivering the response). Reject/ignore new registrations that would overwrite an existing non-expired entry for the same `MessageId` unless the sender matches, and implement the pending sender allowlist/rate-limit TODO before dispatching to DON nodes.

### Proof of Concept
Go test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build handler via `setupHandler(t)`.
2. Create `victimMsg := triggerRequest(t, victimKey, ..., messageID="M")` and `cbVictim := hc.NewCallback()`; call `handler.HandleLegacyUserMessage(ctx, victimMsg, cbVictim)`.
3. Assert `handler.savedCallbacks["M"].Callback == cbVictim` (or equivalent identity check).
4. Craft `attackerMsg` with same `MessageId="M"` but signed by a different key, and `cbAttacker := hc.NewCallback()`; call `handler.HandleLegacyUserMessage(ctx, attackerMsg, cbAttacker)`.
5. Assert `handler.savedCallbacks["M"].Callback == cbAttacker` — confirming the victim's callback was silently overwritten.
6. Simulate the DON's response to the victim's original request via `hc.ValidatedResponseFromMessage(victimMsg)` and call `handler.HandleNodeMessage(ctx, resp, nodes[0].Address)`.
7. Assert that `cbAttacker.Wait(ctx)` receives the response (hijack succeeded) while `cbVictim.Wait(ctx)` times out/never resolves (victim's response lost) — demonstrating cross-sender callback confusion, which the current test suite does not check for.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
