### Title
Bridge Pause Duration Silently Consumes the 48-Hour Limiter-Maturity Window, Allowing Unlimited Minting on Unpause — (`File: crates/sui-framework/packages/bridge/sources/bridge.move`)

---

### Summary

`claim_token_internal` in `bridge.move` decides whether to bypass the transfer-rate limiter by comparing the current clock against the V2 message's embedded deposit timestamp:

```
bypass_limiter = clock.timestamp_ms() > timestamp + 48 * 3600000;
```

The bridge also has an emergency pause that blocks all claims and approvals. During a pause the Sui `Clock` keeps advancing, but no claims can be processed. If the pause lasts longer than 48 hours, every pending V2 message whose deposit timestamp predates `(unpause_time − 48 h)` will be treated as "mature" the instant the bridge reopens, and the limiter will be skipped entirely for those transfers. No `unpause_time` is stored; the maturity check has no awareness of the pause interval.

**`approve_token_transfer` is also blocked during a pause**, so for Ethereum → Sui transfers the `BridgeRecord` is not even inserted until after the unpause, yet the timestamp inside the message is the original Ethereum `block.timestamp`: [4](#0-3) 

**The stated purpose of the limiter** (from the primer and inline comments) is to give the system time to respond to bugs *outside* the VM layer. A bridge pause is itself a response to such a bug; the pending messages were deposited before or during the incident and have not been reviewed under normal operating conditions. [5](#0-4) 

---

### Impact Explanation

Upon unpause after a >48-hour incident, every queued V2 transfer (Ethereum → Sui or Sui → Ethereum) whose deposit timestamp is older than 48 hours bypasses `check_and_record_sending_transfer` entirely. An attacker who deposited a large amount on Ethereum just before (or during) the pause can call the public `claim_and_transfer_token` immediately after unpause and receive an unlimited mint on Sui, defeating the rate-limiting invariant the limiter is designed to enforce. [6](#0-5) 

The minted tokens are backed by real EVM-vault deposits, so this is not a free-mint. The harm is that the limiter — the only on-chain mechanism giving the team time to react to a cross-chain bug — is silently nullified for the entire backlog of transfers that accumulated during the pause.

---

### Likelihood Explanation

Any bridge pause lasting more than 48 hours (plausible during a serious incident requiring governance coordination) automatically triggers this condition for all pending V2 messages. No special attacker capability is required beyond being an ordinary bridge user with a pending transfer. `claim_and_transfer_token` is callable by anyone. [7](#0-6) 

---

### Recommendation

Store an `unpause_time_ms: u64` in `BridgeInner` (defaulting to `0`). Set it inside `execute_emergency_op` when `op == emergency_op_unpause()`. In `claim_token_internal`, replace the maturity check with:

```move
let effective_start = if (unpause_time_ms > timestamp) { unpause_time_ms } else { timestamp };
bypass_limiter = clock.timestamp_ms() > effective_start + 48 * 3600000;
```

This mirrors the fix applied to TaikoL1 (`unpauseTime` + `max(ts.timestamp, unpauseTime) + cooldownWindow`) and ensures the 48-hour review window is measured from the later of the deposit time or the most recent unpause, whichever is later. [8](#0-7) 

---

### Proof of Concept

1. **Setup:** Bridge is live; limiter route limit is set to, e.g., $3 000 USD per 24-hour window.
2. **Deposit:** Attacker calls `SuiBridgeV2.bridgeERC20V2` on Ethereum, depositing 40 ETH (~$120 000). The event carries `block.timestamp = T`.
3. **Pause:** Bridge committee issues an emergency pause (legitimate governance action). `inner.paused = true`. The Sui `Clock` continues advancing.
4. **Wait:** Pause lasts 49+ hours. `Clock.timestamp_ms()` is now `T + 49h`.
5. **Unpause:** Committee unpauses. `inner.paused = false`. No `unpause_time` is recorded.
6. **Approve:** Bridge node (or attacker, if they hold the signatures) calls `approve_token_transfer` with the V2 message. The record is inserted with `timestamp = T`.
7. **Claim:** Attacker calls `claim_and_transfer_token<ETH>(bridge, clock, eth_chain, seq_num, ctx)`.
   - `claim_token_internal` evaluates: `clock.timestamp_ms() > T + 48h` → **true** → `bypass_limiter = true`.
   - `check_and_record_sending_transfer` is skipped.
   - 40 ETH worth of bridged tokens are minted to the attacker on Sui, far exceeding the $3 000 limit.

The existing test `test_v2_mature_message_bypasses_limiter` already demonstrates that a message with `deposit_timestamp = current_time − 48h − 1s` bypasses the limiter; the pause scenario is mechanically identical but arises from a legitimate operational event rather than a crafted timestamp. [9](#0-8)

    let op = payload.emergency_op_type();
    if (op == message::emergency_op_pause()) {
        assert!(!inner.paused, EBridgeAlreadyPaused);

        inner.paused = false;
        event::emit(EmergencyOpEvent { frozen: false });
    } else {
        abort EUnexpectedOperation
    };

## Limiter Bypass V2 Update

Commits after `fe3abe3a8c (VM Limiter Bypass)` introduce a timestamp-aware "V2" bridge flow. The **purpose of the limiter is to give the system time to respond to bugs outside the VM layer**. Fresh transfers (< 48h old) are rate-limited to allow time for issue detection, while mature transfers (> 48h old) can bypass the limiter since any problems would have been identified by then.

**Key principle:** Fresh messages (< 48h) → APPLY limiter; Mature messages (> 48h) → BYPASS limiter.
