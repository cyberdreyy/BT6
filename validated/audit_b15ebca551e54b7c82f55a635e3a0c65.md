### Title
Stale confirmations from removed multisig keys let a request execute below the live signer threshold - ([File: multisig/src/lib.rs])

### Summary
`MultiSigContract::execute_request`'s `DeleteKey` action only purges requests *created* by the removed public key; it never removes that key's `confirmations` entries on *other, still-pending* requests. Because `confirm()` counts entries in the `confirmations` `HashSet<PublicKey>` without checking whether each key is still a valid signer on the account, a request can accumulate the required `num_confirmations` count even though one or more of the counted confirmations belong to a key that has since been deleted from the account. This breaks the binding "confirmations counted == live members confirming" and allows a request to execute with fewer *currently authorized* signers than `num_confirmations` requires.

### Finding Description
`confirm()` reads the confirmation set for a request and, once `confirmations.len() + 1 >= num_confirmations`, executes the request: [1](#0-0) 

The only place stale confirmations for a public key are cleaned up is inside the `DeleteKey` action handler, and it is scoped to requests the removed key itself *created*, not requests it merely *confirmed*: [2](#0-1) 

`remove_request` (used by both `confirm` on execution and `delete_request`) also only clears confirmations for the request being removed/executed, and only decrements `num_requests_pk` for the *original request signer*, not for every key present in `confirmations`: [3](#0-2) 

Because `confirm` never re-validates that a public key in the `confirmations` set is still a live access key on the account (there is no on-chain way to enumerate current access keys from within the contract, as acknowledged in `multisig/README.md`'s "Gotchas" section), a confirmation cast by key `K` before `K` was removed remains valid and counted forever, unless the specific request happens to have been created by `K`.

**Root cause equality that breaks:** the contract implicitly assumes `confirmations_count(request) == live_signers_who_confirmed(request)`. In reality, once a key is deleted via a completed `DeleteKey` request, `confirmations_count(request)` can still include that now-nonexistent key, so `confirmations_count(request) > live_signers_who_confirmed(request)`.

### Impact Explanation
This is Critical impact per the defined categories: "a multisig request executed below threshold." A request (e.g., a `Transfer` moving NEAR out of the multisig account, or an `AddKey`/`DeployContract`) can be executed with fewer than `num_confirmations` *currently authorized* signers actually approving it, because a stale confirmation from a removed key is counted toward the threshold.

### Likelihood Explanation
This requires no attacker with special privileges beyond being (or having been) one of the existing multisig signers, and the sequence is a normal operational flow for any multisig that rotates keys (a common security practice): a pending, under-threshold request is left open while a separate, unrelated `DeleteKey` request executes to remove a departing member's key. The departing member's earlier confirmation on the pending request is never invalidated. Any remaining members who continue confirming that pending request will unknowingly reach threshold with the stale vote of the removed party. Given key rotation is expected practice and the contract's own documentation notes it lacks the ability to validate live keys, this is a realistic and repeatable scenario, not a contrived edge case.

### Recommendation
When a `DeleteKey` (or, in `multisig2`, `RemoveMember`) action executes, iterate over **all** pending requests' confirmation sets (not just requests created by that key) and remove the deleted key/member from each. Alternatively, validate at `confirm()`/execution time that every public key/member counted in `confirmations` is still present in the current key/member set before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(3)` with 4 valid access keys: A, B, C, D.
2. Key A calls `add_request` to create Request X (e.g., `Transfer`). `confirmations[X] = {}`.
3. Key B calls `confirm(X)`. `confirmations[X] = {B}` (1 of 3, not yet executed).
4. Separately, keys A, C, D create and confirm a `DeleteKey { public_key: B }` request to completion. This executes `execute_request`'s `DeleteKey` branch: it removes only requests where `signer_pk == B` (i.e., requests B *created*, not X, since A created X) and calls `promise.delete_key(B)`. `confirmations[X]` is untouched and still contains `B`.
5. Key A calls `confirm(X)`: `confirmations[X].len() == 1` (`{B}`), `1 + 1 = 2 < 3`, so it inserts A: `confirmations[X] = {A, B}`.
6. Key C calls `confirm(X)`: `confirmations[X].len() == 2`, `2 + 1 = 3 >= 3` → `execute_request(X)` fires.
7. Request X executes with the recorded confirmation set `{A, B, C}`, satisfying `num_confirmations = 3`, even though `B`'s key was deleted in step 4 and only `A` and `C` are currently live signers who explicitly approved. The transfer/action in X is executed with only 2 live approvals against a 3-signer threshold. [4](#0-3)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .expect("Failed to remove existing element");
        // decrement num_requests for original request signer
        let original_signer_pk = request_with_signer.signer_pk;
        let mut num_requests = self.num_requests_pk.get(&original_signer_pk).unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_signer_pk, &num_requests);
        // return request
        request_with_signer.request
    }
