### Title
Permissionless `propagate_staked_settings` Lets an Unprivileged Caller Mutate a Staked Bank's `oracle_max_age` (and Oracle Key) at Will, Enabling Stale/Favorable-Price Exploitation - (File: `programs/marginfi/src/instructions/marginfi_group/propagate_staked_settings.rs`)

### Summary
The bug class described in the Oval report — a mutable oracle-staleness parameter (`maxAge`) that can be changed to make the same oracle wiring return inconsistent stale/fresh price data — has a direct analog in marginfi. `BankConfig.oracle_max_age` is not immutable; it is re-read on every price fetch via `bank.config.get_oracle_max_age()`, and it can be mutated not only by the group admin (`lending_pool_configure_bank`) but also through a fully **permissionless** instruction, `propagate_staked_settings`, which copies `StakedSettings.oracle_max_age` (and the oracle key) onto any staked-collateral `Bank` with no signer/authority check and no `FREEZE_SETTINGS` gate.

### Finding Description
`propagate_staked_settings` is declared with no signer requirement at all — its `Accounts` struct only contains `AccountLoader`s for `marginfi_group`, `staked_settings`, and `bank`: [1](#0-0) 

The instruction body directly overwrites the bank's oracle configuration, including `oracle_max_age`, and only re-validates the oracle setup if the oracle key changed (not if only `oracle_max_age` changed): [2](#0-1) 

Unlike the standard admin path (`lending_pool_configure_bank_oracle` / `configure_bank`), which explicitly refuses to change oracle settings when `FREEZE_SETTINGS` is set on the bank, `propagate_staked_settings` performs no such check: [3](#0-2) 

`oracle_max_age` is read fresh at every oracle price fetch (not cached/pinned per-transaction across instructions), so any instruction composed after a `propagate_staked_settings` call in the same transaction sees the newly-propagated, looser value: [4](#0-3) [5](#0-4) 

The only bound enforced on `oracle_max_age` is a floor (`ORACLE_MIN_AGE`, 10 seconds); there is no ceiling, and validation is generic and unaware of the previous value: [6](#0-5) 

Because `StakedSettings` is an admin-controlled account whose values are pushed to individual banks only when someone chooses to call the permissionless propagate instruction, the *timing* of that push is fully attacker-controlled: any unprivileged user can wait until a Pyth/Switchboard feed for a staked-collateral bank goes stale (in the attacker's favor), then call `propagate_staked_settings` in the same transaction as a borrow/withdraw to install a looser `oracle_max_age` (already configured in `StakedSettings` for legitimate reasons, e.g. broader tolerance) that happens to legitimize a stale-but-favorable price for that specific bank at that specific moment, exactly mirroring the Oval finding: "in such a case, the newest price data is returned... it means that in the same block, the oracle adapter may return the most recent data and then the stale data" — except here the attacker, not an admin mistake, chooses the moment.

### Impact Explanation
An attacker can atomically compose `propagate_staked_settings` with a borrow/withdraw/liquidation-avoidance transaction to selectively accept a stale price for a staked-collateral bank that would otherwise be rejected as stale (`PythPushStalePrice`/`SwitchboardStalePrice`), as demonstrated by the existing test `bank_oracle_staleness_test`/`re_one_oracle_stale_failure`, which show that loosening `oracle_max_age` is precisely what turns a `RiskEngineInitRejected` failure into a successful borrow: [7](#0-6) 
If the stale price happens to overvalue the attacker's collateral (or undervalue their liability) relative to the current market price, this enables over-borrowing/under-collateralized positions or evasion of a would-be-correct liquidation — a durable, financially exploitable misvaluation. It also bypasses the `FREEZE_SETTINGS` protection the admin relies on to lock down bank configuration.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a staked-collateral bank whose underlying oracle can become stale relative to `StakedSettings.oracle_max_age`, and (b) that `StakedSettings.oracle_max_age` is set looser than the bank's current live value at the moment of exploitation. Because `propagate_staked_settings` is permissionless and composable in a single transaction with the exploit instruction, no special access or race condition beyond normal transaction construction is needed once such a mismatch exists.

### Recommendation
- Require the same `FREEZE_SETTINGS` check in `propagate_staked_settings` that other oracle-mutating instructions enforce.
- Consider requiring `validate_oracle_setup`/full revalidation whenever `oracle_max_age` changes, not only when the oracle key changes.
- Consider caching/pinning `oracle_max_age` (and other staleness-relevant bank config) for the duration of a transaction, or disallowing composing config-propagation instructions with balance-affecting instructions in the same transaction, to avoid the "inconsistent stale/fresh price in the same transaction" pattern identified by the Oval report.

### Proof of Concept
1. Group admin configures `StakedSettings` with a large `oracle_max_age` for legitimate reasons via `edit_staked_settings` (see `programs/marginfi/src/instructions/marginfi_group/edit_stake_settings.rs`).
2. A staked bank currently has a tighter `oracle_max_age` (has not yet been propagated), and its Pyth feed has gone stale in a way that would currently reject a borrow (as in `bank_oracle_staleness_test`).
3. Attacker submits one transaction containing:
   - `propagate_staked_settings` (permissionless, no signer required) — instantly overwrites the target bank's `oracle_max_age` with the looser `StakedSettings` value, per `propagate_staked_settings.rs` lines 10-32.
   - Immediately followed by `lending_pool_borrow` (or withdraw) using the same stale oracle price, which now passes the staleness check with the newly-loosened `oracle_max_age`, per `bank_config.rs` `get_oracle_max_age` / `price.rs` `try_from_bank`.
4. The borrow succeeds using a stale price snapshot that the protocol would otherwise have rejected, at a time chosen entirely by the unprivileged attacker.

pub fn propagate_staked_settings(ctx: Context<PropagateStakedSettings>) -> Result<()> {
    let settings = ctx.accounts.staked_settings.load()?;
    let mut bank = ctx.accounts.bank.load_mut()?;

    let (oracle_before, oracle_after) = (bank.config.oracle_keys[0], settings.oracle);

    bank.config.oracle_keys[0] = settings.oracle;
    bank.config.asset_weight_init = settings.asset_weight_init;
    bank.config.asset_weight_maint = settings.asset_weight_maint;
    bank.config.deposit_limit = settings.deposit_limit;
    bank.config.total_asset_value_init_limit = settings.total_asset_value_init_limit;
    bank.config.oracle_max_age = settings.oracle_max_age;
    bank.config.risk_tier = settings.risk_tier;
    bank.flags &= !STAKED_ORACLE_FLAGS;
    bank.flags |= settings.flags & STAKED_ORACLE_FLAGS;

    // Only validate the oracle info if it has changed
    if oracle_before != oracle_after {
        bank.config
            .validate_oracle_setup(ctx.remaining_accounts, None, None, None)?;
    }

    bank.config.validate()?;
