### Title
Mid-epoch APR change is not propagated to withdraw-request accounting, letting a tranche holder lock retroactively mispriced interest and socialize the shortfall to other LPs - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.setApr()`/`setAprs()`/`setAprsWithBuffer()` update `lastApr`/`unscaledApr` instantly, but nothing re-syncs `expectedEpochInterest`, `interestForOverUnderPerformance`, or already-minted withdraw receipts. In `IdleCDOEpochVariant.requestWithdraw`, `_calcInterestWithdrawRequest()` prices the *entire* epoch's interest using the strategy APR current at request time (`_calcInterest` → `_getStrategyApr()`), not the APR that was in force while the epoch ran. An unprivileged tranche holder can therefore request a withdraw right after an APR increase and mint a receipt that claims the full-epoch interest at the new higher rate — including elapsed time that accrued at the old lower rate — while the borrower only owes interest funded through `pendingWithdraws`/`collectWithdrawFunds` based on what is actually collected at `stopEpoch`. The over-issued receipt value is paid out of the same pool as other lenders' claims; when funding falls short, `collectWithdrawFunds` records a `lossRecoveryPriceByEpoch` haircut or the loss is pushed onto remaining active LPs via the BB-first waterfall.

### Finding Description
- `contracts/strategies/idle/IdleCreditVault.sol:206-235` — `setAprs`, `setAprsWithBuffer` and `setApr` write `unscaledApr`/`lastApr` with no accrual or reconciliation step. Only CDO or manager may call, but they are honest roles sequencing, not the attacker.
- `contracts/IdleCDOEpochVariant.sol:856-878` — `_calcInterestWithdrawRequest` computes `totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer)` where `_calcInterest` (lines 800-809) uses `_getStrategyApr()`, i.e. the *current* `lastApr`. The receipt `_amount` is minted 1:1 to the user in `requestWithdraw` (IdleCreditVault.sol:273-279, `_mint(_user, _amount)` and `pendingWithdraws += _amount`) at the moment of the request.
- `expectedEpochInterest` is fixed at the previous `stopEpoch` under the *old* APR and is only adjusted by `interestForOverUnderPerformance` per-request (lines 780-784); it does not account for a mid-epoch APR jump applied retroactively to the full epoch duration.
- Resulting mismatch: receipts minted after an APR increase claim interest for time that economically accrued at the old rate. At the next `stopEpoch`, the borrower funds `pendingWithdraws` only up to what is collected; the deficit either triggers a `lossRecoveryPriceByEpoch` haircut shared by all pending receipts (IdleCreditVault.sol:411-430) or reduces NAV distributed to AA/BB LPs.
- Symmetric case: an APR *decrease* mid-epoch leaves already-minted receipts priced at the old high rate for the full remaining epoch, while the borrower's obligation drops — same insolvency direction, attacker simply keeps his pre-change receipt.

### Impact Explanation
Direct theft/insolvency: the attacker's receipt is over-issued in strategy tokens 1:1 and claims real underlying at `claimWithdrawRequest` (`_claimFundedWithdrawRequest`, lines 319-350) once the next epoch rolls. Quantified loss ≈ `amount * (newApr − oldApr) * elapsedTime / 365 days` worth of over-minted interest per epoch, borne pro-rata by other pending receipt holders (via `lossRecoveryPriceByEpoch`) or by remaining tranche LPs through the loss waterfall. On a leveraged venue with frequent APR updates the over-claim can exceed the epoch's true interest margin and convert into a realized bad-debt-style shortfall at `stopEpoch`.

### Likelihood Explanation
Requirements are modest: the vault must be in a running epoch (`epochEndDate != 0`, `epochDuration > 0` so `_calcInterestWithdrawRequest` returns nonzero), the attacker must be a KYC-passed tranche holder (`isWalletAllowed`), and the honest manager/CDO must change the APR mid-epoch — a routine operation exposed via `setApr`/`setAprsWithBuffer`. The attacker merely calls `requestWithdraw` after observing the APR-increase transaction; no front-running is needed because the retroactive mispricing favors any request made while `lastApr` is high relative to the APR that governed elapsed time. Guards do not stop it: `_onlyIdleCDO` is satisfied (request goes through the CDO), `lossRecoveryPriceByEpoch` checks only gate *re-opening* requests, and `maxApr` caps the absolute rate, not the retroactive application.

### Recommendation
When `setApr`/`setAprs`/`setAprsWithBuffer` is called mid-epoch, re-anchor the accounting: accrue/settle interest for the elapsed portion at the old APR (or record a per-epoch APR-change timestamp and have `_calcInterestWithdrawRequest` integrate elapsed time at `lastEpochApr` and only the remainder at the new rate). Alternatively, snapshot the APR used for withdraw-request pricing at `stopEpoch` into an immutable epoch variable so mid-epoch `setApr` cannot retroactively reprice full-epoch interest.

pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";

// Fork test: mainnet fork of an IdleCDOEpochVariant + IdleCreditVault deployment.
contract StaleAprWithdrawPoC is Test {
    IdleCDOEpochVariant cdo;
    IdleCreditVault vault;   // strategy()
    IERC20 under;
    address manager;
    address attacker;        // KYC'd AA tranche holder

    function setUp() public {
        vm.createSelectFork(vm.envString("MAINNET_RPC"));
        cdo    = IdleCDOEpochVariant(/* deployed CDO */);
        vault  = IdleCreditVault(cdo.strategy());
        under  = IERC20(cdo.token());
        manager = vault.manager();
        // attacker: deposit during buffer, epoch starts at apr_old (e.g. 5%)
        // ...standard depositAA / startEpoch flows...
    }

    function test_RetroactiveInterestTheft() public {
        // Epoch is running at oldApr. Manager (honest) raises APR mid-epoch.
        uint256 oldApr = vault.unscaledApr();
        uint256 newApr = oldApr * 2; // e.g. 5% -> 10%

        // Attacker captures his claimable amount *before* the change for baseline.
        uint256 baseline = cdo.maxWithdrawable(attacker, cdo.AATranche());

        vm.prank(manager);
        vault.setAprsWithBuffer(newApr, cdo.epochDuration(), cdo.bufferPeriod());

        // _calcInterestWithdrawRequest now prices the WHOLE epochDuration at newApr,
        // including elapsed time that accrued at oldApr.
        vm.prank(attacker);
        uint256 receipt = cdo.requestWithdraw(0, cdo.AATranche()); // full balance
        assertGt(receipt, baseline); // over-issued by ~ amount*(newApr-oldApr)*elapsed/365d

        // Next stopEpoch: borrower funds only interest at the new rate going forward;
        // pendingWithdraws > funded amount -> lossRecoveryPriceByEpoch haircut
        // or NAV loss pushed onto remaining LPs.
        vm.warp(cdo.epochEndDate());
        // borrower repays principal + interest at newApr for remaining time only
        // ... stopEpochWithDuration(_lossAmount=0) ...
        // attacker claims inflated receipt; other requesters/LPs absorb the gap.
    }
}
