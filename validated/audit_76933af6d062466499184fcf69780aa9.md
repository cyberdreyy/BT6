### Title
Unbounded per-notification encoding cost for account/program pubsub notifications: `data_slice` config is silently ignored in the `notify_watchers` hot path - ([File: rpc/src/rpc_subscriptions.rs])

### Summary
`AccountSubscriptionParams` and `ProgramSubscriptionParams` both carry a `data_slice` field intended to cap the amount of account data returned per notification, but `filter_account_result` and `filter_program_results` — the functions actually invoked from `notify_watchers` on every commitment/slot update — hardcode `None` for `data_slice_config` when calling `encode_ui_account`. This means a single `accountSubscribe`/`programSubscribe` call cannot bound its own per-tick encoding cost, and that cost scales with the size of the underlying account, which an unprivileged attacker fully controls by writing a large account (up to `MAX_PERMITTED_DATA_LENGTH`) via ordinary transactions.

### Finding Description
The subscription parameter structs explicitly define a `data_slice` field to bound response size: [1](#0-0) [2](#0-1) 

These are populated correctly from the client-supplied `RpcAccountInfoConfig`/`RpcProgramAccountsConfig` at subscribe time: [3](#0-2) [4](#0-3) 

However, the actual per-notification encoding path used by `notify_watchers` for `SubscriptionParams::Account` and `SubscriptionParams::Program` calls `filter_account_result` and `filter_program_results` respectively: [5](#0-4) [6](#0-5) 

Both of these functions hardcode `None` for the `data_slice_config` argument to `encode_ui_account`, discarding `params.data_slice` entirely: [7](#0-6) [8](#0-7) 

`encode_ui_account` then encodes the *entire* `account.data()` (base58/base64/base64+zstd/json-parsed) proportional to `account.data().len()`, since `slice_data` is only applied when a `data_slice_config` is actually passed: [9](#0-8) 

An unprivileged attacker can:
1. Write a large account (approaching `MAX_PERMITTED_DATA_LENGTH`) owned by an arbitrary `program_id` via a normal system/allocate transaction.
2. Issue a single `programSubscribe(program_id)` call — even with a `dataSlice` configured, it is silently ignored server-side.
3. Repeatedly modify that one account with their own subsequent transactions (or even a single modification followed by ongoing commitment-level re-evaluation).

Every time `notify_watchers` runs (on each slot/commitment update, driven by validator ticking, not attacker rate), the full-size account is re-encoded server-side for that subscription, with CPU/memory cost proportional to the attacker-chosen account size rather than any explicit RPC-configured cap. The `data_slice` feature exists specifically to prevent this, but is dead code on this path — it is functional for the request/response `getAccountInfo`/`getProgramAccounts` REST API (`rpc/src/rpc.rs` uses `data_slice_config` correctly), but not for pubsub notifications.

### Impact Explanation
This causes unbounded (attacker-data-size-driven) CPU and memory cost for a single subscription's per-tick notification generation, since the intended mitigation (`data_slice`) is inert on the pubsub notify path. This matches the "RPC DoS with a single low-rate call" bounty category: the attacker uses exactly one `programSubscribe`/`accountSubscribe` call and ordinary account writes, and the validator repeatedly performs large encodes (base58/base64/zstd/json-parse) each commitment tick regardless of the client's requested `dataSlice`, degrading pubsub service performance for that node.

### Likelihood Explanation
Highly feasible with only unprivileged actions: creating a large account and subscribing are both permitted by ordinary account/CU rent-exemption/transaction-size rules (subject to the normal system-level `MAX_PERMITTED_DATA_LENGTH` cap on a single account), and one subscription call is sufficient. The cost recurs on every `notify_watchers` invocation (per slot/commitment update) as long as the subscription remains open, without requiring further attacker action beyond the initial write(s).

### Recommendation
Thread `params.data_slice` through to `encode_ui_account` in both `filter_account_result` and `filter_program_results` (mirroring how `rpc/src/rpc.rs::get_program_accounts` already passes `data_slice_config`), so pubsub notifications honor the client's configured slice and so a hard server-side cap can also be enforced independent of client input (e.g., clamp `data_slice`/full-data encoding to a maximum byte size regardless of what the client specifies, to guard against clients that omit `dataSlice`).

```rust
pub fn encode_ui_account<T: ReadableAccount>(
    pubkey: &Pubkey,
    account: &T,
    encoding: UiAccountEncoding,
    additional_data: Option<AccountAdditionalDataV3>,
    data_slice_config: Option<UiDataSliceConfig>,
) -> UiAccount {
    let space = account.data().len();
    let data = match encoding {
        UiAccountEncoding::Binary => {
            let data = encode_bs58(account, data_slice_config);
            UiAccountData::LegacyBinary(data)
        }
        UiAccountEncoding::Base58 => {
            let data = encode_bs58(account, data_slice_config);
            UiAccountData::Binary(data, encoding)
        }
        UiAccountEncoding::Base64 => UiAccountData::Binary(
            BASE64_STANDARD.encode(slice_data(account.data(), data_slice_config)),
            encoding,
        ),
        UiAccountEncoding::Base64Zstd => {
            let mut encoder = zstd::stream::write::Encoder::new(Vec::new(), 0).unwrap();
            match encoder
                .write_all(slice_data(account.data(), data_slice_config))
                .and_then(|()| encoder.finish())
            {
                Ok(zstd_data) => UiAccountData::Binary(BASE64_STANDARD.encode(zstd_data), encoding),
                Err(_) => UiAccountData::Binary(
                    BASE64_STANDARD.encode(slice_data(account.data(), data_slice_config)),
                    UiAccountEncoding::Base64,
                ),
            }
        }
        UiAccountEncoding::JsonParsed => {
            if let Ok(parsed_data) =
                parse_account_data_v3(pubkey, account.owner(), account.data(), additional_data)
            {
                UiAccountData::Json(parsed_data)
            } else {
                UiAccountData::Binary(
                    BASE64_STANDARD.encode(slice_data(account.data(), data_slice_config)),
                    UiAccountEncoding::Base64,
                )
            }
        }
    };
```
