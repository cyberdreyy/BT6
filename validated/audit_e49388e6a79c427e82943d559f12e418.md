### Title
Non-constant-time Bearer token comparison in `/metrics` endpoint enables timing side-channel token guessing - ([File: core/web/router.go])

### Summary
`prometheusHandler` in `core/web/router.go` compares the caller-supplied `Authorization` header against the expected `"Bearer " + token` string using Go's native `!=` operator instead of a constant-time comparison. Since Go's string equality short-circuits on the first mismatching byte, an unauthenticated attacker who can reach the `/metrics` endpoint can, in principle, measure response-time differences to infer the token byte-by-byte.

### Finding Description

The critical line is `if header != bearer`, which uses the standard Go string comparison. This comparison is not constant-time: it compares length first, then compares bytes sequentially and returns as soon as a mismatch is found. No middleware upstream of this handler (rate limiting, session auth, `auth.Authenticate*`) enforces constant-time comparison for this specific route — the metrics route is registered directly on the `gin.Engine` (`e.GET(p.MetricsPath, prometheusHandler(...))`), bypassing the `api` router group's rate limiter and session middleware entirely, so there is no additional friction against repeated timing probes.

An attacker with no credentials can send repeated HTTP requests to `/metrics` with varying `Authorization: Bearer <guess>` headers and, in theory, use response latency to determine correct-prefix matches, incrementally recovering the token.

### Impact Explanation
If practically exploitable, the impact is disclosure of the Prometheus metrics token, which grants access to `/metrics` (internal operational counters/gauges — no direct fund movement or private key exposure). This corresponds to a low-severity "sensitive information disclosure via authentication weakness" class rather than key/fund compromise, since `/metrics` does not expose private keys or job secrets directly, only internal counters.

### Likelihood Explanation
Exploitability is low in practice: successful timing attacks against short (single round-trip) HTTP comparisons require an attacker with very low, stable network jitter (e.g., same host or same LAN as the node) and typically thousands to millions of samples to overcome scheduler/OS/network noise, especially against a byte comparison of a small fixed-length token where the amount of leaked information per byte is minimal. No route-specific rate limiting is applied to `/metrics` (bypasses `api` group's `rateLimiter`), which somewhat increases feasibility by allowing high request volume, but the underlying signal is very weak over a real network path. This still requires the token endpoint (`/metrics`) to be network-reachable by the attacker, which is often restricted to internal monitoring networks in typical deployments (though that is a deployment/config consideration, not required for the code-level flaw to exist).

### Recommendation
Replace the direct string comparison with a constant-time comparison, e.g.:
```go
import "crypto/subtle"
...
if subtle.ConstantTimeCompare([]byte(header), []byte(bearer)) != 1 {
    c.String(http.StatusUnauthorized, ginprom.ErrInvalidToken.Error())
    return
}
```
Additionally, consider applying rate limiting to the `/metrics` route consistent with other unauthenticated routes to reduce the volume of probing an attacker can perform.

### Proof of Concept
Go handler-level test plan:
1. Build a `gin.Engine` with `prometheusHandler(token, dummyHandler)` mounted on `GET /metrics`, using a token of realistic length (e.g., 32 chars).
2. Craft a set of candidate tokens: one identical to the real token, several with increasing correct-byte prefixes (0,25%,50%,75%,99% correct prefix followed by wrong bytes), and one fully random/wrong token.
3. For each candidate, issue N (e.g., 10,000) requests via `httptest.NewRecorder()`/`ServeHTTP` directly (bypassing network jitter) and record wall-clock latency using `time.Now()`/`time.Since()` around the call to `engine.ServeHTTP`.
4. Compute median/mean latency per candidate group and assert that latency does not scale with prefix-match length beyond noise threshold (e.g., statistically significant correlation test, or assert max latency delta < some small epsilon relative to full request time).
5. Expected result with current code: measurable (even if small, in the nanosecond-to-microsecond range at the in-process level with GOMAXPROCS=1 and repeated sampling) latency correlation with prefix length, confirming non-constant-time behavior at the function level — demonstrating the root cause even though real-network exploitation feasibility is separately bounded by network jitter.
6. After applying `subtle.ConstantTimeCompare`, re-run the same test and assert no statistically significant timing correlation with prefix length.

```go
func prometheusHandler(token string, h http.Handler) gin.HandlerFunc {
	return func(c *gin.Context) {
		if token == "" {
			h.ServeHTTP(c.Writer, c.Request)
			return
		}

		header := c.Request.Header.Get("Authorization")

		if header == "" {
			c.String(http.StatusUnauthorized, ginprom.ErrInvalidToken.Error())
			return
		}

		bearer := "Bearer " + token

		if header != bearer {
			c.String(http.StatusUnauthorized, ginprom.ErrInvalidToken.Error())
			return
		}

		h.ServeHTTP(c.Writer, c.Request)
	}
```
