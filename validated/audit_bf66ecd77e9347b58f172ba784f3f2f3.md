### Title
Loss-adjusted withdraw receipts can be claimed at par by adding a later-epoch request, bypassing `lossRecoveryPriceByEpoch` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The go-attestation bug (CVE-2022-0317) is an input-validation flaw where a Quote covering only *some* PCRs passes `Verify`, while a downstream consumer (`Eventlog.Verify`) treats the whole set as authenticated. The analog in idle-tranches is `IdleCreditVault.claimWithdrawRequest`: the loss-haircut check in `_claimLossAdjustedWithdrawRequest` authenticates only the user's *latest* request epoch (`lastWithdrawRequest[_user]`), but the subsequent funded-claim path pays the *entire aggregate* `withdrawsRequests[_user]` at par. A lender can therefore hide a haircutted receipt behind a dust request made in a later epoch and claim it unhaircutted, exactly mirroring "verify a subset, consume the whole set".

### Finding Description
When `stopEpochWithDuration(_lossAmount)` realizes a loss, `IdleCDOEpochVariant` calls `IdleCreditVault.collectWithdrawFunds` with `_amount < pendingWithdraws`. The strategy records a per-epoch haircut `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws` (IdleCreditVault.sol:411-430).

At claim time:

- `_claimLossAdjustedWithdrawRequest` looks up the haircut using *only* `lastWithdrawRequest[_user]` as the epoch key and returns early if `lossRecoveryPriceByEpoch[lossEpoch] == 0` (IdleCreditVault.sol:789-801). It never scans `withdrawsRequestsByEpoch[_user][*]` for other epochs.
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — the aggregate across all epochs — at par, gated solely by `epochNumber > lastWithdrawRequest[_user]` (IdleCreditVault.sol:319-350).
- `requestWithdraw` sets `lastWithdrawRequest[_user] = currentEpoch` and accumulates into `withdrawsRequestsByEpoch[_user][currentEpoch]` / `withdrawsRequests[_user]` (IdleCreditVault.sol:282-294). A new request unconditionally overwrites the marker.

Sequence (attacker = an ordinary KYC'd lender, no privilege):

1. Epoch N running: attacker calls `requestWithdraw(X)` → `withdrawsRequestsByEpoch[attacker][N] = X`, `lastWithdrawRequest = N`.
2. `stopEpochWithDuration` realizes a loss → `lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL`, `pendingWithdraws = 0`. Attacker's receipt is now only worth `X * p`.
3. Epoch N+1 running: attacker calls `requestWithdraw(1 wei)` (or any dust) → `lastWithdrawRequest = N+1`, `withdrawsRequests = X + dust`.
4. Epoch N+2 (wait satisfied since `epochNumber > N+1`): attacker calls `claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[N+1] == 0` → returns 0 without clearing epoch-N basis. `_claimFundedWithdrawRequest` pays `X + dust` at par via `_transferFundedClaim`.

The epoch-N receipt was "verified" only against the N+1 key — the haircut on the actual subset epoch is never applied, yet the payout covers it.

### Impact Explanation
Direct theft / insolvency: the attacker redeems `X * (RECOVERY_FULL - p) / RECOVERY_FULL` more underlying than entitled. These underlyings come from the funded-claim balance of the strategy, which is earmarked for *other* users' matured receipts and the default-recovery reserve (`_transferFundedClaim` deliberately avoids the reserve but spends funded liquidity). If enough haircutted claimants do this, later legitimate claimants' `safeTransfer` calls revert for lack of balance — permanent loss socialized onto honest withdrawers, and the loss waterfall invariant (pending receipts bear `pendingLoss`) is broken.

Quantification: attacker steals `claimBasis_N * (1 - p)`. With a 20% loss and a 1M USDC receipt, that's 200k USDC overpaid.

### Likelihood Explanation
- Attacker needs only to be a tranche-token holder who made a withdraw request in the loss epoch — fully in scope (lender, unprivileged).
- Requires a `stopEpochWithDuration` loss event (borrower shortfall), which is a designed code path, not an edge case. The dust `requestWithdraw` in the next epoch costs ~1 wei of underlying value plus gas.
- No existing guard stops it: `_skimDonatedAssets`, default reverts, and epoch gating are orthogonal; the funded-claim path explicitly intends to pay the aggregate at par and has no per-epoch haircut reconciliation. The only mitigation is `lastWithdrawRequest` being a single-epoch marker, which is precisely the flawed "verify latest only" check.
- Caveat: correctness of the intended flow assumes `collectWithdrawFunds` keys `lossRecoveryPriceByEpoch` on the *request* epoch (i.e., `epochNumber` is incremented after collection inside `stopEpochWithDuration`), consistent with `requestWithdraw` marking the pre-increment epoch and the funded-claim wait check. If the key were the post-increment epoch, the haircut would never apply at all — an even more severe variant of the same defect.

### Recommendation
Apply the haircut to *every* epoch in the user's receipt set, not just the latest marker — i.e., `VerifyAll` semantics instead of `Verify`:

- Iterate (or boundedly track) the set of epochs with `withdrawsRequestsByEpoch[_user][e] != 0` that have `lossRecoveryPriceByEpoch[e] != 0`, clearing each at its own recovery price inside `claimWithdrawRequest` before falling through to the funded path; or
- Store a per-user `mapping(epoch => receipt)` list and require `lastWithdrawRequest` to be reset only after all haircutted epochs are cleared; or
- Simplest: prevent `requestWithdraw` from overwriting `lastWithdrawRequest` while an uncleared loss-adjusted epoch receipt exists (revert, forcing the user to claim the haircutted receipt first), or key the loss lookup off the per-epoch map directly rather than the single marker.

### Proof of Concept
Foundry fork test (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testLossHaircutBypassedByLaterRequest() external {
    uint256 amountWei = 1_000_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amountWei);

    _startEpochAndCheckPrices(0);
    // attacker requests withdraw of full position in epoch N
    uint256 requested = cdoEpoch.requestWithdraw(mintedAA, address(AAtranche));

    // stopEpochWithDuration realizes a loss -> lossRecoveryPriceByEpoch[N] = p < 1e18
    uint256 loss = requested / 5; // 20% loss on pending receipts
    _stopEpochWithLoss(loss); // helper: manager stops with _lossAmount so collectWithdrawFunds gets _amount < pendingWithdraws

    // epoch N+1 running: attacker adds dust request, overwriting lastWithdrawRequest
    _startEpochAndCheckPrices(1);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // dust tranche amount

    // epoch N+2: wait satisfied
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());
    _startEpochAndCheckPrices(2); // or simply advance epochNumber > N+1

    IdleCreditVault strat = IdleCreditVault(address(strategy));
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 got = IERC20Detailed(defaultUnderlying).balanceOf(address(this)) - balPre;

    uint256 haircutted = requested * strat.lossRecoveryPriceByEpoch(1) / strat.RECOVERY_FULL();
    // BUG: payout equals full par amount, not the haircutted value
    assertGt(got, haircutted, "attacker escaped the loss haircut");
    assertApproxEqAbs(got, requested + 1, 2, "paid at par");
}
```

Expected result: `got ≈ requested + dust` instead of `requested * p / 1e18`, demonstrating the haircutted epoch-N receipt was paid at par because the loss lookup keyed only on the overwritten `lastWithdrawRequest`.
