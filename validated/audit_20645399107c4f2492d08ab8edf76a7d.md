### Title
Unstaked balance is debited before the NEAR transfer is confirmed in `internal_withdraw`, permanently desyncing accounting from actual funds held on transfer failure - ([File: staking-pool/src/internal.rs])

### Summary
`StakingContract::internal_withdraw` decrements the user's `unstaked` balance and the pool's `last_total_balance` and then fires a bare `Promise::new(account_id).transfer(amount)` with no `.then()` callback and no check of the promise's outcome.

### Finding Description
`internal_withdraw` in `staking-pool/src/internal.rs` performs the following sequence: it asserts the account has enough unstaked balance, subtracts `amount` from `account.unstaked`, persists the account, decrements `self.last_total_balance -= amount`, and only after these state mutations schedules `Promise::new(account_id).transfer(amount)`: [1](#0-0) 

There is no `.then(ext_self::on_withdraw(...))` callback and no `is_promise_success()` check anywhere in this path, unlike other transfer flows in the same codebase which do check outcomes and roll back state on failure, e.g. `lockup-factory`'s `on_lockup_create` which refunds and reverts on failure: [2](#0-1) 
and `lockup`'s `foundation_callbacks.rs::on_withdraw_unvested_amount`, which restores `TerminationStatus::ReadyToWithdraw` if `is_promise_success()` is false: [3](#0-2) 

Because `internal_withdraw` has none of this, if the scheduled NEAR `transfer` action fails for any reason at the runtime level (e.g. the target `account_id` no longer exists having been deleted between call submission and receipt execution, or any other transfer-action failure), the NEAR remains in the staking-pool contract's own balance, yet the contract's ledger (`account.unstaked` and `last_total_balance`) has already been permanently decremented as if the withdrawal succeeded. The equality that should hold, `sum(account.unstaked) + total_staked_balance == actual NEAR balance retained by the contract`, is broken: the contract retains NEAR that its own accounting no longer reflects, and the user's claim on that amount is permanently lost since there is no retry, refund, or restoration path.

### Impact Explanation
This is a High-severity accounting divergence: the withdrawing user's recorded claim is erased from `unstaked`/`last_total_balance` regardless of whether the NEAR transfer actually lands in the user's account. On transfer failure the user's funds become permanently unaccounted for (frozen/lost from the user's perspective) while the contract silently keeps the NEAR balance, meaning the pool's own solvency bookkeeping no longer matches the NEAR it actually holds — exactly the "claims versus assets held" divergence class called out in the rules.

### Likelihood Explanation
No attacker action is required to trigger the accounting break; it happens whenever the `transfer` action itself fails to complete for the receiver account (e.g., a deleted/invalid receiving account at execution time), which is a normal, unprivileged runtime occurrence rather than a contrived edge case. `withdraw`/`withdraw_all` are ordinary user-callable methods, so any unstaking delegator can be exposed to this failure mode.

### Recommendation
Move the state mutation (`account.unstaked -= amount; self.internal_save_account(...); self.last_total_balance -= amount;`) into a callback attached via `.then(ext_self::on_withdraw(...))`, gated on `is_promise_success()`, so the ledger is only updated after the transfer is confirmed to have succeeded — mirroring the pattern already used in `lockup-factory::on_lockup_create` and `lockup::foundation_callbacks::on_withdraw_unvested_amount`.

### Proof of Concept
1. Delegator unstakes and, after the unlock delay, calls `withdraw(amount)` on the staking pool.
2. `withdraw` invokes `internal_withdraw`, which immediately reduces `account.unstaked` and `self.last_total_balance` by `amount` and fires `Promise::new(account_id).transfer(amount)` with no completion check. [4](#0-3) 
3. If the `transfer` action fails at execution (e.g. the delegator's account no longer exists), the NEAR is retained by the staking-pool contract, but the delegator's `unstaked` balance and the pool's `last_total_balance` are already permanently decremented with no callback to reverse them.
4. The delegator's on-chain claim to `amount` is now unrecoverable through the contract's public interface, while the contract's actual NEAR balance no longer matches `last_total_balance`, breaking the pool's solvency invariant.

    pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        assert!(
            account.unstaked >= amount,
            "Not enough unstaked balance to withdraw"
        );
        assert!(
            account.unstaked_available_epoch_height <= env::epoch_height(),
            "The unstaked balance is not yet available due to unstaking delay"
        );
        account.unstaked -= amount;
        self.internal_save_account(&account_id, &account);

        env::log(
            format!(
                "@{} withdrawing {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );

        Promise::new(account_id).transfer(amount);
        self.last_total_balance -= amount;
    }

    /// Called after the foundation tried to withdraw the terminated unvested balance.
    pub fn on_withdraw_unvested_amount(
        &mut self,
        amount: WrappedBalance,
        receiver_id: AccountId,
    ) -> bool {
        assert_self();

        let withdraw_succeeded = is_promise_success();
        if withdraw_succeeded {
            env::log(
                format!(
                    "Termination Step: The withdrawal of the terminated unvested amount of {} to @{} succeeded.",
                    amount.0, receiver_id
                )
                    .as_bytes(),
            );
            // Decreasing lockup amount after withdrawal.
            self.lockup_information.termination_withdrawn_tokens += amount.0;
            let unvested_amount = self.get_terminated_unvested_balance().0;
            if unvested_amount > amount.0 {
                // There is still unvested balance remaining.
                let remaining_balance = unvested_amount - amount.0;
                self.vesting_information =
                    VestingInformation::Terminating(TerminationInformation {
                        unvested_amount: remaining_balance.into(),
                        status: TerminationStatus::ReadyToWithdraw,
                    });
                env::log(
                    format!(
                        "Termination Step: There is still terminated unvested balance of {} remaining to be withdrawn",
                        remaining_balance
                    )
                        .as_bytes(),
                );
                if self.get_account_balance().0 == 0 {
                    env::log(b"The withdrawal is completed: no more balance can be withdrawn in a future call");
                }
            } else {
                self.foundation_account_id = None;
                self.vesting_information = VestingInformation::None;
                env::log(b"Vesting schedule termination and withdrawal are completed");
            }
        } else {
            self.set_termination_status(TerminationStatus::ReadyToWithdraw);
            env::log(
                format!(
                    "Termination Step: The withdrawal of the terminated unvested amount of {} to @{} failed",
                    amount.0, receiver_id,
                )
                .as_bytes(),
            );
        }
        withdraw_succeeded
    }
