The reported bug class relies on token/contract addresses that remain valid in multiple letter-case representations (e.g., checksummed vs. lowercase hex/bech32 addresses on Secret Network), letting an attacker register the "same" pair twice by varying case. This repository's identity boundary is `AccountId`, and every account-comparison path I found (`whitelist/src/lib.rs` `is_whitelisted`/`add_staking_pool`/`add_factory`, `staking-pool-factory/src/lib.rs` `new`/`on_staking_pool_create`, `lockup/src/owner.rs` `select_staking_pool`) is gated by `env::is_valid_account_id`, which enforces the NEAR account ID grammar (lowercase letters/digits/separators only, no uppercase permitted). [1](#0-0) [2](#0-1) [3](#0-2) 

Because an uppercase or mixed-case variant of an account ID is rejected outright by `is_valid_account_id` before it ever reaches an equality check (`LookupSet::contains`, `UnorderedSet::contains`, `assert_eq!`), there is no reachable path in this codebase's in-scope contracts (`staking-pool`, `lockup`, `lockup-factory`, `staking-pool-factory`, `multisig-factory`, `whitelist`, `voting`, `multisig`, `multisig2`, `w-near`, `state-manipulation`) where two textually-different-but-semantically-equal identifiers could both pass validation and be treated as distinct in a whitelist, multisig membership set (`multisig2/src/lib.rs` `MultisigMember`), or staking-pool selection binding. The root cause of the external report — case-insensitive-but-not-normalized address comparison — has no analog here because NEAR's account ID validation removes the ambiguity at the input boundary, so no custody/authorization binding can be broken this way.
