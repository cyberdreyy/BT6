### Title
Signer weight double-counted in both `total_weight_approved` and `total_weight_rejected` when a signer flips Reject→Accept - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener`'s handling of `BlockResponse::Accepted` and `BlockResponse::Rejected` messages guards duplicate weight-counting with two *different* keys: the rejection path gates on `block.responded_signers.insert(slot_id)`, while the acceptance path gates on `block.gathered_signatures.contains_key(&slot_id)`. Because these are separate sets, a signer that first rejects and later accepts the same block (a flow the codebase explicitly supports, e.g. `signer_can_accept_rejected_block`) has its weight added to `total_weight_rejected` once and then, unconditionally, added again to `total_weight_approved` — with no corresponding decrement of `total_weight_rejected`. This breaks the aggregated-weight-vs-verified-accepts equality that `SignCoordinator::wait_for_signatures` in `signer_coordinator.rs` relies on to decide whether a block is approved or rejected.

### Finding Description
In the `Accepted` arm: [1](#0-0) 
the code only checks `!block.gathered_signatures.contains_key(&slot_id)` before adding `signer_entry.weight` to `total_weight_approved`, then unconditionally inserts into both `gathered_signatures` and `responded_signers`.

In the `Rejected` arm: [2](#0-1) 
the guard for adding weight to `total_weight_rejected` is `block.responded_signers.insert(slot_id)` returning `true` (i.e., first time this slot_id is seen in `responded_signers`, regardless of which branch put it there).

Sequence that produces the bug:
1. Signer S rejects block B. `responded_signers.insert(slot_id)` succeeds (first time) → `total_weight_rejected += w(S)`. `gathered_signatures` is untouched.
2. Signer S later re-evaluates B (e.g. block re-proposed) and accepts it. In the `Accepted` arm, `gathered_signatures.contains_key(&slot_id)` is `false` (S never had an entry there), so `total_weight_approved += w(S)` fires again, and `responded_signers.insert(slot_id)` is called (already present, no-op, and its boolean result is discarded/unused here).

Result: `w(S)` is now present in *both* `total_weight_approved` and `total_weight_rejected` simultaneously. `total_weight_rejected` is never decremented when a signer flips.

`SignCoordinator::wait_for_signatures` in `signer_coordinator.rs` consumes these two counters independently and checks rejection first: [3](#0-2) 
Because `total_weight_rejected` retains stale weight from a signer who has since accepted, the miner can incorrectly conclude the block was rejected by a blocking minority (`total_weight_rejected + weight_threshold > total_weight`) even though that signer's current, verified position is acceptance — i.e., the aggregated rejected-weight no longer corresponds to the set of signers actually still rejecting. This is a violation of the aggregated-weight-vs-verified-accepts/rejects equality described in scope.

### Impact Explanation
This is a liveness/state-consistency issue on the miner side: a single signer flipping its vote (a supported, expected scenario) can cause the miner to treat a block as globally rejected based on stale rejection weight that should have been retracted, or conversely inflate approved weight past what distinct signers actually contributed. Per the scope's High-impact bucket, this can wedge a correct block from being accepted (miner spuriously aborts with `SignersRejected`, forcing costly re-proposal/re-mining) even though a sufficient weight of signers has, in the current state, actually approved the block — a mismatch between aggregated weight and the true set of verified accepts/rejects.

### Likelihood Explanation
This requires no majority collusion and no signer's private key — it can be triggered by a single signer that legitimately changes its vote from reject to accept for the same block hash (a normal, protocol-supported occurrence, e.g. re-proposal after the block becomes valid or after a stale rejection is retried). The `stackerdb_listener.rs` code path is exercised on every block proposal round, so the condition is reachable in ordinary operation whenever any signer's local decision flips.

### Recommendation
Use a single per-slot “current vote” map (or track weight contribution per slot_id explicitly) instead of two independently-gated accumulators. When a signer's vote flips from reject to accept (or vice versa), subtract its previously counted weight from the old bucket before adding it to the new bucket, so `total_weight_approved` and `total_weight_rejected` always reflect the signer's most recent verified response only.

### Proof of Concept
1. Miner proposes block B; Signer S (weight w) sends `BlockResponse::Rejected` for B. `stackerdb_listener.rs` records `total_weight_rejected += w` via `responded_signers.insert(slot_id)` at line 515.
2. B is re-proposed (or S reprocesses) and S now sends `BlockResponse::Accepted` for the same `signer_signature_hash`. In the `Accepted` arm, `gathered_signatures.contains_key(&slot_id)` is false, so `total_weight_approved += w` at line 444, while `total_weight_rejected` still retains `w` from step 1 (never decremented).
3. `SignCoordinator::wait_for_signatures` reads `block_status.total_weight_rejected` and `block_status.total_weight_approved` independently; if enough other signers also flip similarly (or combined with legitimate rejecters), `total_weight_rejected` can cross `self.total_weight - self.weight_threshold` purely due to this stale double-counted weight, causing the miner to abort a block that a sufficient number of signers have, in their current/latest state, actually accepted.
