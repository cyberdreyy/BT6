### Title
Hardcoded `UserRoleRun` grant in `AuthenticateExternalInitiator` lets any authenticated external initiator trigger runs on any job ID, without per-EI job scoping - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` unconditionally sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` for every successfully authenticated external initiator (EI), granting full `run`-role privileges to the request context. The only `RequiresRunRole` route reachable via the EI-enabled `userOrEI` group, `POST /v2/jobs/:ID/runs` → `PipelineRunsController.Create`, does not verify that the requesting EI is actually associated with the target job ID before invoking it.

### Finding Description
In `core/web/auth/auth.go`, `AuthenticateExternalInitiator` (lines 119-151) authenticates the EI credential against `store.FindExternalInitiator`/`bridges.AuthenticateExternalInitiator`, then does: [1](#0-0) 
This grants the generic `clsessions.UserRoleRun` to any EI, with no reference to which job(s) that specific EI is permitted to invoke.

In `core/web/router.go`, the `userOrEI` group wires this in: [2](#0-1) 
Note that this is the **only** `RequiresRunRole`-gated route mounted on `userOrEI`; the other `RequiresRunRole` routes (`/replay_from_block/:number`, `/find_lca`, `/lp_skip_to_block`, `/execute_capability`) live in the `authv2` group, which is authenticated only via `AuthenticateByToken`/`AuthenticateBySession` — not `AuthenticateExternalInitiator` — so EIs cannot reach those. The framing "any RequiresRunRole route" in the question is therefore inaccurate; the real exposure is limited to this one route.

The handler `PipelineRunsController.Create` (`core/web/pipeline_runs_controller.go`, lines 89-128) checks only: [3](#0-2) 
`isUser` is true for both real users **and** EIs, because `AuthenticateExternalInitiator` also populates `SessionUserKey`. The code path then calls `prc.App.RunJobV2(ctx, jobID, nil)` for whatever `:ID` was supplied in the URL — it never consults `auth.GetAuthenticatedExternalInitiator(c)` to confirm the EI is scoped/authorized to run that specific job. The webhook-specific job/EI linkage mechanism (matched by UUID) has been removed (`job.ErrJobTypeRemoved`), so for the remaining int32-ID job type there is no scoping check left at all between an EI credential and the job it triggers.

### Impact Explanation
Any holder of a valid external-initiator access key/secret pair (a low-privilege, narrowly-scoped credential intended only to trigger its own associated job) can call `POST /v2/jobs/:ID/runs` with an arbitrary job ID and start a pipeline run for a job it has no legitimate relationship to. This is an authorization-scope bypass: unauthorized triggering of another job's execution, which for jobs performing on-chain writes (VRF fulfillment, keeper/automation jobs, direct-request jobs with transmit tasks, etc.) can lead to unauthorized transactions/fund movement or unwanted external effects. This matches the "unauthorized job run" bounty impact class.

### Likelihood Explanation
- Precondition: attacker must already possess valid EI access-key/secret credentials for *some* external initiator registered on the node (a low, non-admin credential).
- No additional privilege, session, or admin action needed once that credential is held.
- The exploit is a single unauthenticated-role HTTP POST — trivially repeatable and requires no timing/race conditions.

### Recommendation
In `PipelineRunsController.Create`, when the caller authenticated as an external initiator (`auth.GetAuthenticatedExternalInitiator(c)`), verify that the target job ID is one the EI is authorized to trigger (e.g., re-introduce or restore an EI-to-job association check) before calling `RunJobV2`, instead of relying solely on the generic `isUser`/`RequiresRunRole` check which conflates real users and EIs.

### Proof of Concept
Handler-level integration test plan:
1. Seed two jobs, JobA and JobB, and one external initiator EI1 (only intended to trigger JobA, if such an association exists/existed).
2. Authenticate as EI1 using its access key/secret against `POST /v2/jobs/:ID/runs`.
3. Call the endpoint with `:ID` = JobB's ID (a job unrelated to EI1).
4. Assert the request succeeds (`200 OK`, a `pipelineRun` resource is returned for JobB) rather than being rejected with `403 Forbidden`/`401 Unauthorized`, demonstrating that `AuthenticateExternalInitiator`'s hardcoded `UserRoleRun` grant plus the missing EI-to-job scoping check allows cross-job invocation.
5. Additionally assert (negative control) that EI1 cannot reach `authv2`-only `RequiresRunRole` routes like `/v2/replay_from_block/:number`, confirming the escalation is confined to `/v2/jobs/:ID/runs`.
