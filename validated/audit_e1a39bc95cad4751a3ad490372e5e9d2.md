### Title
Unauthenticated MessageId flood causes eviction of legitimate subscriber's pending callback - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` accepts any structurally-valid legacy trigger message and stores a per-`MessageId` callback in the shared `h.savedCallbacks` map with an explicit `// TODO: apply allowlist and rate-limiting here` marker, meaning no per-caller quota exists. `pruneCallbacks` evicts the oldest half of `savedCallbacks` once the map exceeds `MaxSavedCallbacks`, so an attacker who submits enough distinct `MessageId` requests can force eviction of an older, still-pending legitimate subscriber's callback before the DON responds.

### Finding Description
`gateway.ProcessRequest` routes any legacy (DON-ID-bearing) JSON-RPC request through `msg.Validate()` and dispatches it to `h.HandleLegacyUserMessage` [1](#0-0) . `Validate()` performs structural/staleness checks only; there is no per-sender allowlist or identity binding enforced before the message reaches the handler. Inside `HandleLegacyUserMessage`, after basic payload/timestamp checks, the code explicitly notes the missing control: [2](#0-1) 

Every accepted request is stored keyed only by `msg.Body.MessageId` in the shared map, with no bound on distinct MessageIds per caller: [3](#0-2) 

`pruneCallbacks`, run on a timer, deletes expired entries first, then — if the map still exceeds `MaxSavedCallbacks` (default 20000) — sorts remaining entries by `createdAt` and deletes all but the newest `maxSize/2`, i.e. it evicts the *oldest* half regardless of whether those callbacks are legitimate and still awaiting a DON response: [4](#0-3) 

Because there is no per-user/per-identity cap (only the global `MaxSavedCallbacks`) and no allowlist/rate-limit gate before insertion, an attacker can submit a burst of distinct-`MessageId` legacy trigger requests (well within `MaxAllowedMessageAgeSec`/timestamp checks) faster than the DON can respond, pushing the map size above `MaxSavedCallbacks`. Since eviction is strictly oldest-first, any legitimate subscriber's callback submitted before the attacker's flood — and still pending because the DON hasn't answered yet — gets deleted from `h.savedCallbacks`. When the DON's real response later arrives for that victim `MessageId`, `handleWebAPITriggerMessage`'s lookup fails (`found == false`) and the response is silently dropped: [5](#0-4) 

The victim's original HTTP request (blocked in `callback.Wait(ctx)` in `gateway.ProcessRequest`) will eventually time out and receive a `RequestTimeoutError`, rather than the correct DON response — a denial of legitimate response delivery. There is no code path that would let one MessageId's response be delivered to a different caller (the map is keyed by MessageId and the callback found is deleted atomically under `h.mu` before use in `handleWebAPITriggerMessage`), so the "cross-user response confusion via ID collision" branch of the question does not hold — that requires an attacker to *guess or collide* a victim's exact MessageId, which is a separate (and much narrower) attack not demonstrated by mere flooding with distinct IDs.

### Impact Explanation
This is a denial-of-service against a legitimate DON-response delivery path (per-request response loss for arbitrary web API trigger users) caused by lack of a per-caller/per-identity quota and rate limiting on `savedCallbacks` insertion, matching Chainlink's "Denial of Service" bounty impact class for gateway/off-chain services. It does not achieve request impersonation, fund movement, or key/secret disclosure, and cross-user response delivery would additionally require MessageId collision, which is not enabled by this flooding mechanism alone.

### Likelihood Explanation
The precondition is explicitly acknowledged as missing in the code itself (`// TODO: apply allowlist and rate-limiting here`) [6](#0-5) , and the user-facing HTTP endpoint accepts legacy requests from any caller able to construct a validly-formed message satisfying `msg.Validate()` and non-stale timestamp checks [7](#0-6) . Reaching `MaxSavedCallbacks` (default 20000, configurable) requires sustained volume, but is feasible for an attacker without any privileged credential, and is fully repeatable since each attack request only needs a unique `MessageId`.

### Recommendation
Implement per-caller (e.g., per-sender/authenticated key) rate limiting and/or a maximum number of concurrently pending callbacks per identity before inserting into `h.savedCallbacks`, as flagged by the existing TODO. Consider making `pruneCallbacks` eviction identity-aware (e.g., cap per-sender share of the map) rather than purely oldest-first, and/or reject new insertions when the map is at capacity instead of silently evicting legitimate pending entries.

### Proof of Concept
Go unit test plan for `pruneCallbacks` in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with `config.MaxSavedCallbacks = N` (small, e.g. 10) and `CallbackMaxAgeSec` large enough that nothing expires during the test.
2. Insert one "legitimate" `savedCallback` with an early `createdAt` timestamp and a callback that records if `SendResponse` is invoked.
3. Insert `N` additional "attacker" `savedCallback` entries with later `createdAt` timestamps and distinct fabricated `MessageId`s, simulating a flood via repeated `HandleLegacyUserMessage` calls (or directly populating `h.savedCallbacks` to isolate `pruneCallbacks` behavior).
4. Call `h.pruneCallbacks()` directly.
5. Assert that the legitimate entry's ID is no longer present in `h.savedCallbacks` (demonstrating eviction of the oldest/legitimate entry ahead of newer attacker entries).
6. Simulate the DON response arriving afterward for the legitimate `MessageId` via `handleWebAPITriggerMessage` and assert `found == false`, i.e., the legitimate callback's `SendResponse` is never invoked and the original caller would time out — confirming the DoS impact without any cross-user response leakage (assert no other callback receives the victim's payload).

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
