### Title
APR0 withdraw receipt permanently reverts `stopEpoch` after an honest APR change, freezing the vault - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is an unauthenticated request to an edge-case resource that crashes shared request processing (mod_authz_svn DoS). The analog: any KYC'd tranche holder can place the strategy into a state (`apr0TotalPrincipal > 0` while `unscaledApr != 0`) where every subsequent `stopEpoch` call reverts unconditionally, halting the epoch lifecycle and freezing all user funds.

### Finding Description
`_stopEpoch` in `IdleCDOEpochVariant` unconditionally calls `IdleCreditVault.prepareStopEpochWithApr0(_interest)` on every stop, for every mode. In `IdleCreditVault.prepareStopEpochWithApr0` (lines 499–508):

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

`apr0TotalPrincipal` is only increased in `_requestWithdrawApr0`, reachable by any user calling `IdleCDOEpochVariant.requestWithdraw` while `unscaledApr == 0`. It is only decreased inside the same reverting function (line 540) or inside `_clearWithdrawClaimForEpoch` with `_isClearingApr0 = true`, which is only reachable via the post-default claim path (`defaultRecoveryFinalized`).

Attack sequence:
1. During an APR0 epoch (`unscaledApr == 0`), attacker calls `cdoEpoch.requestWithdraw(...)`. `requestWithdraw` mints a receipt and sets `apr0TotalPrincipal > 0` (lines 285–286, 567–577).
2. The honest manager sets a non-zero APR for the next epoch via `setAprs` (a routine operation; `stopEpoch(_newApr, ...)` with `_newApr != 0` is even the documented signature, and tests call `setAprs` directly mid-epoch).
3. At `epochEndDate`, `stopEpoch` is called. `prepareStopEpochWithApr0` sees `apr0TotalPrincipal != 0` and `unscaledApr != 0` and reverts `NotAllowed`. Every retry reverts identically — the state is self-reinforcing because the revert happens before `apr0TotalPrincipal` can be cleared.

The user cannot unbrick it either: `claimWithdrawRequest` → `_claimFundedWithdrawRequest` reverts at line 326 (`epochNumber <= lastWithdrawRequest`) and `_settleApr0` returns early while `reqEpoch >= epochNumber`, so the receipt is stuck until a `stopEpoch` succeeds — which is exactly what is bricked.

### Impact Explanation
All epoch transitions halt: `epochNumber` never advances, `pendingWithdraws` are never collected, no withdraw receipt (normal, instant follow-on, or APR0) can be claimed, and the entire pool NAV (attacker's dust request can be arbitrarily small relative to TVL) is frozen. The pool remains frozen until the manager discovers the cause and restores `unscaledApr == 0` — i.e., a single cheap `requestWithdraw` lets an unprivileged lender veto any APR increase and hold the whole vault hostage, with all borrower funds and lender claims locked for the duration. This is temporary freezing of funds with a quantified impact equal to full TVL plus all pending withdraw receipts.

### Likelihood Explanation
Requires only a standard tranche-holder `requestWithdraw` during an APR0 epoch plus an ordinary, honest `setAprs`/non-zero `_newApr` action by the manager — both routine operations with no privileged collusion, default, or exotic mode needed. The revert path has no guard that stops it: the check at line 506 is itself the bug (it protects accounting consistency by bricking the only clearing path).

### Recommendation
Do not hard-revert on `apr0TotalPrincipal != 0 && unscaledApr != 0`. Instead, settle the stale APR0 bucket gracefully in `prepareStopEpochWithApr0` — e.g., record `apr0RateByEpoch[epochNumber] = 0` (or last realized rate) and zero `apr0TotalPrincipal`, letting `_settleApr0` pay principal-only claims afterward. Alternatively, gate `setAprs`/non-zero `_newApr` to revert when `apr0TotalPrincipal != 0` so the APR change (a recoverable, pre-stop action) is refused rather than the epoch stop itself.

### Proof of Concept
Foundry fork PoC (against the existing `IdleCreditVault.t.sol` harness, AA tranche, `unscaledApr = 0` epoch):

```solidity
function testApr0ReceiptBricksStopEpochAfterAprRaise() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);          // APR0 pool

    idleCDO.depositAA(10000 * ONE_SCALE);
    _transferBurnedTrancheTokens(address(this), true);
    _startEpochAndCheckPrices(0);
    _stopCurrentEpoch();                                       // epoch 1 buffer, APR0

    // attacker: ordinary withdraw request while unscaledApr == 0
    uint256 principal = cdoEpoch.requestWithdraw(1e18, address(AAtranche)); // dust
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // honest manager decides to re-enable a normal APR for next epoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(5e18, 5e18);    // unscaledApr != 0

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, 10000 * ONE_SCALE);

    // every stopEpoch reverts; epochNumber can never advance, claims are frozen
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 1);                                  // close-pool path also bricked

    // receipt cannot be cleared user-side either
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimWithdrawRequest();
}
```

Key assertions: `stopEpoch` reverts for all `_interest` values including the `== 1` recall sentinel, `apr0TotalPrincipal` remains non-zero, and `claimWithdrawRequest` reverts — demonstrating vault-wide fund freezing caused by a dust `requestWithdraw` sequenced before a routine honest APR change.
