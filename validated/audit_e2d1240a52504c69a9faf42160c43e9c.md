### Title
`setTrancheAPRSplitRatio` applies the new AA/BB yield split retroactively to all accrued-but-unsplit gain, letting a tranche holder sequence a deposit to steal yield from the other tranche - ([File: contracts/IdleCDO.sol](contracts/IdleCDO.sol))

### Summary
`setTrancheAPRSplitRatio()` (and `setMinAprSplitAYS()`) overwrite `trancheAPRSplitRatio` immediately without first running `_updateAccounting()`. The next `_updateAccounting()` — triggered by any `depositAA`/`depositBB`/`withdrawAA`/`withdrawBB` — splits the entire gain accrued since `lastNAVAA + lastNAVBB` was saved using the **new** ratio, not the ratio in force while the gain accrued. This is the same bug class as the external report: a rate parameter is changed without settling accrued rewards under the old rate, so the new rate is applied to past time. An unprivileged tranche holder can front-run/sequence a deposit around the honest owner's ratio change to capture the misallocated yield.

### Finding Description
In `IdleCDO.sol`:

```solidity
/// @param _trancheAPRSplitRatio new apr split ratio
function setTrancheAPRSplitRatio(uint256 _trancheAPRSplitRatio) external virtual {
  _checkOnlyOwner();
  _checkAmountTooHigh((trancheAPRSplitRatio = _trancheAPRSplitRatio) > FULL_ALLOC);
}
``` [1](#0-0) 

There is no `_updateAccounting()` before the overwrite (compare `setMintRate` in the external report). All accrued gain is split in `_updateAccounting()` → `_virtualPriceAux`, which computes `totalGain = nav - lastNAV` for the whole interval since the last saved NAV and splits it under the *current* stored ratio:

```solidity
int256 totalBBGain = totalGain * int256(FULL_ALLOC - _trancheAPRSplitRatio) / int256(FULL_ALLOC);
_totalTrancheGain = _isAATranche ? (totalGain - totalBBGain) : totalBBGain;
``` [2](#0-1) 

The same retroactive-split logic exists in the credit-vault variant (`IdleCDOCreditVault.sol:324-328`), which splits `totalGain` by `trancheAPRSplitRatio` on any deposit/withdraw.

Attack path (running epoch, fixed-APR mode, `isAYSActive == false` so the ratio is owner-set):
1. Gain `G` accrues between `lastNAV` and `getContractValue()` without an accounting update — e.g. the borrower repays interest or sends tokens directly to the CDO/strategy, or a harvest moves value in (the direct-token-sender and borrower-repayment flows leave `lastNAV` stale until the next deposit/withdraw).
2. The honest owner calls `setTrancheAPRSplitRatio(newRatio)` that shifts split toward BB (or AA).
3. The attacker — a tranche-token holder in the favored tranche (or a KYC'd lender who can deposit into it) — calls `depositAA`/`depositBB`. `_deposit` runs `_updateAccounting()` first, splitting all of `G` under `newRatio`, then mints attacker shares at the inflated/deflated price.
4. The attacker redeems; their gain is the delta `G * |newRatio - oldRatio| / FULL_ALLOC` that, under correct ordering, belonged to the opposite tranche's existing holders.

No guard stops this: `_checkOnlyOwner` is satisfied by the honest owner, `depositAA/BB` are open to allowed/KYC'd lenders, and `_checkDefault`/skim logic does not isolate ordinary accrued-but-unsplit yield. The docstring on `_getAARatio`/`getCurrentAARatio` confirms the split is meant to apply going forward from the last accounting point, not backward over pending gain.

### Impact Explanation
Direct misallocation of unclaimed yield between AA and BB tranche holders, quantifiable as `G * Δratio`. With a large accrued `G` (e.g. a full epoch's borrower interest repaid before `stopEpoch` accounting, or strategy value growth in non-epoch variants), an attacker holding even a modest position in the favored tranche extracts yield belonging to the other tranche's holders. The violated invariant is fair mint/burn and correct yield split: "past-time gain priced at the ratio in force while it accrued" is broken exactly as the external "past interval priced at the new rate" invariant.

### Likelihood Explanation
Requires: (a) a pool operating in fixed-split mode or before `_updateSplitRatio` re-derives the ratio (when `isAYSActive` the ratio is recomputed on each deposit/withdraw, shrinking the window but `setMinAprSplitAYS` still shifts the retroactive clamp), (b) a non-zero unaccrued `G` when the owner changes the ratio — routine when the owner tunes splits while interest has accrued since the last user action or `stopEpoch`, and (c) an unprivileged actor able to hold/deposit into the favored tranche (KYC'd lender or existing holder) who triggers the next accounting call. All roles involved on the privileged side are honest; the attacker's only action is a normal deposit. Likelihood is moderate: it needs a real accrued-gain window coinciding with a ratio change, but owner ratio tuning is a normal operation.

### Recommendation
Call `_updateAccounting()` (or `_forceUpdateAccounting()`) inside `setTrancheAPRSplitRatio`, `setMinAprSplitAYS`, and `setIsAYSActive` before mutating any parameter that feeds `_virtualPriceAux`, so accrued gain is crystallized under the old ratio — the same fix pattern as `_updateRewardIndex(); mintRate = newMintRate;`.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// assume: credit vault CDO with AA+BB holders, isAYSActive == false
// 1) state: lastNAVAA = 90e18, lastNAVBB = 10e18, trancheAPRSplitRatio = 50_000
// 2) borrower repays / direct send: vault balance -> nav = lastNAV + G, G = 10e18
//    (getContractValue() - (lastNAVAA+lastNAVBB) == 10e18, no accounting yet)
// 3) owner calls setTrancheAPRSplitRatio(0)  // all future split to BB
// 4) BB holder calls cdo.depositBB(1e18)     // triggers _updateAccounting
//    -> _virtualPriceAux splits ALL 10e18 of G at ratio 0 -> BB gets 10e18
//       correct result: BB should get only 5e18 of the pre-change G
// 5) attacker withdraws BB: profit ~= 5e18 stolen from AA holders
assertGt(bbGain, expectedBbGainAtOldRatio);
```

Note: I verified the missing `_updateAccounting()` in `setTrancheAPRSplitRatio`/`setMinAprSplitAYS` and the retroactive split in `_virtualPriceAux`; I did not fully trace which caller paths can produce a large stale `nav > lastNAV` gap inside the epoch-variant (vs. non-epoch `IdleCDO` variants where harvest/deposit flows clearly can), so the exact source of `G` should be confirmed when writing the PoC — `harvest()`, borrower repayments, or direct token sends are the candidates.
