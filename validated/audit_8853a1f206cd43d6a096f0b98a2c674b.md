### Title
Owner case mismatch between authorization check and stored/keyed secret identifier in Vault gateway pipeline - ([File: core/capabilities/vault/gateway_vault_request_processor.go])

### Summary
The Vault capability's gateway request pipeline validates that a client-supplied secret owner matches the authorized workflow owner using a **case-insensitive** comparison (`vaultutils.NormalizeOwner`), but the value that actually gets **stamped into the request ID / used as the storage key** (`authResult.AuthorizedOwner()`) is not itself guaranteed to be canonically normalized, and the client-supplied `SecretIdentifier.Owner` field embedded in the payload is never rewritten to a canonical form before being persisted. This is the same address-canonicalization class of bug as the external cw20-base report: comparisons are normalized, but storage/keying is not, so the same logical owner can end up represented under different byte-for-byte strings depending on case.

### Finding Description
`vaultutils.NormalizeOwner` explicitly documents that "**All comparison sites must use this function**" and that a future flag (`VaultOwnerAddressCanonicalizationEnabled`) will "supersede comparison-site calls" once ingress-level normalization exists [1](#0-0) . This comment is itself an acknowledgment that canonicalization is not yet enforced at ingress.

The authorizer's owner-binding check (`validateSecretOwnersMatchAuthorized` and its helpers) only uses `NormalizeOwner` to *compare* the client-supplied `SecretIdentifier.Owner`/`ListSecretIdentifiersRequest.Owner` against `authResult.AuthorizedOwner()` — it never rewrites the identifier itself: [2](#0-1) [3](#0-2) 

Downstream, `GatewayVaultRequestProcessor.authorizeAndStamp` takes the raw `authResult.AuthorizedOwner()` string (whatever case the underlying auth mechanism happened to produce) and uses it verbatim as a prefix for the request ID, which becomes the effective storage/routing key for the secret: [4](#0-3) 

Crucially, the `stamp` callbacks for create/update/delete only overwrite `RequestId` — they never rewrite `createReq.EncryptedSecrets[i].Id.Owner` (or the delete/list equivalents) to the canonical/authorized form: [5](#0-4) [6](#0-5) 

This is confirmed by a test asserting that a client-supplied mixed-case owner (`"0xAbC"`) survives unchanged into the payload sent to the secrets service, with only the request ID getting the (separately-sourced) authorized-owner prefix: [7](#0-6) 

Because `NormalizeOwner` lower-cases and strips the `0x` prefix purely for the comparison, while the actual `Owner` field written into storage keys / secret identifiers keeps the client's original casing, two requests for the "same" owner address in different letter-casing pass the authorization gate identically but can produce **different literal owner strings** in persisted secret identifiers and in the `authorizedOwner`-based request-ID prefix. This is the same root cause as the cw20-base bug: comparison operations are canonicalized, mutation/storage operations are not.

### Impact Explanation
If the authorization-mechanism-derived owner (allowlist path or JWT-derived workflow owner) and the client-supplied owner field can differ in case (e.g., an allowlist entry stored in mixed/checksummed case vs. a client sending an all-lowercase address, or vice versa), then:
- Secrets created/updated/listed/deleted under one case variant of an address may not be found when the same logical owner is later resolved to a different case variant elsewhere in the pipeline (e.g., workflow execution requesting secrets via `LocalSecretOverrideOwnerKey`/`normalizeOwner` in `core/services/workflows/v2/secrets.go`, which uses a *different* normalization scheme — `common.HexToAddress(owner).Hex()` checksummed form — than the lowercase-based `vaultutils.NormalizeOwner`). Two different canonicalization conventions coexisting in the same trust boundary is itself a red flag for silent owner-key divergence.
- This can cause an owner's own secrets to become effectively "locked"/unreadable under a mismatched case key — directly analogous to the reported "funds locked" impact for cw20-base transfers to an uppercase address — and, in the create/update path, could allow a client to smuggle a differently-cased `Id.Owner` into the stored secret identifier that a same-owner subsequent list/delete request (using a different case) fails to match, causing orphaned secrets or apparent secret loss.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an unprivileged client deliberately submitting mixed/upper-case owner addresses in `SecretIdentifier.Owner`/`ListSecretIdentifiersRequest.Owner` fields (which the API accepts, since owner binding only checks case-insensitive equality), and (b) some other component in the pipeline performing an exact-string or differently-canonicalized comparison/lookup on that owner value. The existence of at least two distinct normalization functions in the codebase (`vaultutils.NormalizeOwner` lower-casing without `0x`, and `secrets.go`'s `normalizeOwner`/`common.HexToAddress(...).Hex()` producing EIP-55 checksummed case) increases the chance of a mismatch somewhere in the full create→store→fetch lifecycle, though I was not able to fully trace the OCR2 vault plugin's on-chain/off-chain storage keying logic within the remaining budget to confirm a concrete cross-component mismatch (e.g., whether the plugin ORM keys secrets by the raw `Id.Owner` string or by a canonicalized form).

### Recommendation
Canonicalize the owner value at the earliest ingress point (as the code comment in `vaultutils/owner.go` already anticipates) and rewrite the `SecretIdentifier.Owner` / `ListSecretIdentifiersRequest.Owner` fields to that canonical form as part of `GatewayVaultRequestProcessor.authorizeAndStamp`, rather than only using `NormalizeOwner` for comparison. Ensure a single canonicalization convention (e.g., lower-case, `0x`-stripped, as used by `vaultutils.NormalizeOwner`) is used consistently across all owner-keyed storage, lookup, and request-ID prefixing code paths, including `core/services/workflows/v2/secrets.go`'s `normalizeOwner`, to eliminate the possibility of the same logical owner mapping to different storage keys.

### Proof of Concept
Not independently reproduced end-to-end; based on static code reading, a client could:
1. Be authorized (via allowlist or JWT) as owner `0xabc...` (lower-case, as returned by `AuthResult.AuthorizedOwner()`).
2. Submit a `vault.secrets.create` request whose `EncryptedSecrets[0].Id.Owner = "0xABC..."` (upper-case). `validateEncryptedSecretOwnerMismatch` passes because `NormalizeOwner("0xABC...") == NormalizeOwner("0xabc...")` [2](#0-1) .
3. The stamped request forwarded to `SecretsService.CreateSecrets` retains `Id.Owner = "0xABC..."` unchanged [8](#0-7) , while the request-ID prefix uses `authorizedOwner` (`"0xabc..."`) verbatim [9](#0-8) .
4. If any downstream storage/lookup path keys by exact `Id.Owner` string rather than a normalized form, a later `vault.secrets.list`/`vault.secrets.delete` request from the same real owner (using the "canonical" lower-case address) will not find the secret created in step 2 — verification of this exact downstream mismatch in the OCR2 vault plugin ORM was not completed within the available search budget.

package vaultutils

import "strings"

// NormalizeOwner lowercases an Ethereum owner address for case-insensitive comparison.
// All comparison sites must use this function. When VaultOwnerAddressCanonicalizationEnabled
// is introduced, normalization at ingress will supersede comparison-site calls here.
func NormalizeOwner(owner string) string {
	return strings.ToLower(strings.TrimPrefix(owner, "0x"))
}

func validateEncryptedSecretOwnerMismatch(encryptedSecrets []*vaultcommon.EncryptedSecret, workflowOwner string) error {
	if len(encryptedSecrets) == 0 {
		return errors.New("request batch must contain at least 1 item")
	}
	for idx, encryptedSecret := range encryptedSecrets {
		if encryptedSecret == nil {
			return fmt.Errorf("encrypted secret must not be nil at index %d", idx)
		}
		if encryptedSecret.Id == nil {
			return fmt.Errorf("secret ID must not be nil at index %d", idx)
		}
		if vaultutils.NormalizeOwner(encryptedSecret.Id.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("encrypted secret owner at index %d %q does not match authorized workflow owner %q", idx, encryptedSecret.Id.Owner, workflowOwner)
		}
	}
	return nil
}

func (p *GatewayVaultRequestProcessor) processCreateSecretsRequest(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	publicKey *tdh2easy.PublicKey,
) (*AuthorizedGatewayVaultRequest, error) {
	if req.Params == nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: errors.New("request params must not be nil")}
	}

	var createReq vaultcommon.CreateSecretsRequest
	if err := json.Unmarshal(*req.Params, &createReq); err != nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
	}
	if p.stripOwnerPrefixForAuth {
		createReq.RequestId = req.ID
		if err := marshalVaultParams(req, &createReq); err != nil {
			return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
		}
	} else {
		createReq.RequestId = coalesceRequestID(createReq.RequestId, req.ID)
	}

	skipLabelValidation := publicKey == nil
	if err := p.validator.ValidateCreateSecretsRequest(ctx, publicKey, &createReq, skipLabelValidation); err != nil {
		return nil, p.validationError(req, err)
	}

	return p.authorizeAndStamp(ctx, req, func(prefixedRequestID string) error {
		createReq.RequestId = prefixedRequestID
		vaultutils.ApplyEncryptedSecretNamespaceDefaults(createReq.EncryptedSecrets)
		return marshalVaultParams(req, &createReq)
	})
}

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID

	if err := stamp(prefixedRequestID); err != nil {
		p.lggr.Errorw("failed to stamp authorized request params", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, fmt.Errorf("failed to stamp authorized request params: %w", err)
	}

	p.lggr.Debugw("authorized gateway vault request", "method", req.Method, "requestID", req.ID, "owner", authorizedOwner, "orgID", authResult.OrgID(), "workflowOwner", authResult.WorkflowOwner())
	return &AuthorizedGatewayVaultRequest{
		Req:        *req,
		AuthResult: authResult,
	}, nil
}
