### Title
Reorg permit checked only for sortition liveness, not conflict identity — `reorg_permit_stands` misapplies a stale permit to an unrelated conflicting tenure - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`SignerDb::get_signed_conflicts` annotates any signed block in a superseded tenure with the *latest* permit ever recorded for that tenure (`superseded_by_consensus_hash`/`superseded_by_burn_block_hash`), keyed only by the superseded tenure's own consensus hash. `Signer::reorg_permit_stands` then decides whether that permit "stands" purely by asking whether the recorded permitting sortition is still canonical on the burnchain — it never checks that the tenure currently being pre-committed/signed is that permitting tenure (or descends from it). This lets an unrelated, never-vetted conflicting tenure ride on a permit that was granted for a completely different conflict.

### Finding Description
The uniqueness property that must hold is: *a second signature at the same height is only excused if the specific conflict (this signed block vs. this new proposal) was explicitly permitted by `check_parent_tenure_choice`*. The code breaks this:

- `SignerDb::mark_tenure_superseded` records, per superseded tenure `A`, only the sortition of whichever tenure most recently reorged it (`INSERT OR REPLACE ... WHERE consensus_hash = A`) [1](#0-0) .
- `SignerDb::get_signed_conflicts` joins any signed block back to `superseded_tenures` solely by the *block's own tenure* hash, and returns whatever permit is currently on file for that tenure — regardless of which tenure is actually being evaluated as the new conflicting proposal [2](#0-1) .
- `Signer::reorg_permit_stands` only checks that the recorded permitting sortition (`superseded_by.burn_block_hash`) is still canonical; it takes no argument identifying the block/tenure currently being signed and never compares it to `superseded_by.consensus_hash` [3](#0-2) .
- The pre-commit guard in `handle_block_pre_commit` calls `reorg_permit_stands(stacks_client, conflict)` for every fresh conflict at height ≥ h, and treats a "standing" permit as sufficient to exclude the conflict entirely, without any tie-back to the tenure of the block it is about to sign [4](#0-3) .

Root cause: the permit is stored and checked at the granularity of "superseded tenure" only, not at the granularity of the (superseded tenure, superseding tenure) pair. Because `get_signed_conflicts`/`reorg_permit_stands` is explicitly documented as the backstop for conflicts the primary chainstate re-check (`check_block_against_signer_db_state`) cannot see — i.e. a signed sibling in a *third* tenure that is neither the new proposal's own tenure nor its immediate parent tenure — this is exactly the class of conflict for which no fresh, proposal-specific validation of the reorg ever runs. The stale permit (granted earlier for tenure `A` superseded by `X`) is silently reused to excuse a same-height conflict against a completely different, never-vetted tenure `Z`, as long as `X`'s sortition happens to still be canonical.

Exploit flow: tenure `A` mines and gets a block `N` signed; at some later point (a benign, ordinary occurrence) tenure `X` legitimately reorgs `A` under the timing rules, and `mark_tenure_superseded(A, ..., superseded_by=X)` is recorded. `X`'s sortition, being real history, remains canonical for a long time (up to `MAX_FORK_DEPTH` = 100 burn blocks). An attacker who wins one later, independent miner slot for tenure `Z` — whose own parent tenure is neither `A` nor `X`'s chain, so `Z`'s tenure-start block never triggers `check_parent_tenure_choice` against `A` at all — can craft a `BlockProposal`/tenure whose block lands at the same Stacks height as `N` (a genuine parallel-fork sibling, the exact "third tenure" scenario the docs call out as invisible to the primary re-check). When that proposal's pre-commit threshold is reached, `get_signed_conflicts` returns `N` annotated with `superseded_by = X`, and `reorg_permit_stands` reports the permit stands (since `X`'s sortition is canonical) — even though nobody ever validated that `Z`'s specific conflict with `A`/`N` was a sanctioned reorg. The conflict is excluded, and the signer signs `Z`'s block.

### Impact Explanation
This breaks chain safety: a signer can end up placing a valid signature on two conflicting blocks at the same Stacks height (`N` in tenure `A`, and the attacker's block in tenure `Z`), where the second signature was excused by a permit that was never granted for that specific pair. If enough signers hit the same stale record (it is shared global signer-db state derived from identical prior events), this can contribute signatures toward finalizing an equivocating/non-canonical block, i.e. exactly the "signer signing a conflicting block" Critical category. It is repeatable for as long as the stale `superseded_tenures` row survives (up to 100 burn blocks, and refreshed as long as no fresher permit for `A` overwrites it).

### Likelihood Explanation
Preconditions: a superseded-tenure record must already exist for the victim tenure (an ordinary, non-malicious occurrence from a prior legitimate reorg), and its permitting sortition must still be canonical. The attacker needs only one miner slot to construct the conflicting proposal in a tenure that is a "third tenure" relative to the victim block (not its own tenure, not its parent) — exactly the blind spot `check_block_against_signer_db_state` is documented to have. No majority of signers, no privileged role, and no auth token are required; the attacker only crafts a `BlockProposal` and lets normal gossip/pre-commit flow proceed. This is feasible whenever the natural pre-condition (a stale-but-still-canonical permit) exists, and is repeatable across every such stale record until pruning.

### Recommendation
Tie the permit check to the specific conflicting pair: when recording (`mark_tenure_superseded`) and when checking (`reorg_permit_stands`), require that the tenure of the block currently under evaluation is exactly `superseded_by.consensus_hash` (or is provably a descendant of it in the currently validated chain), not merely that the recorded permitting sortition remains canonical. `reorg_permit_stands` should take the current block's tenure/consensus hash as a parameter and reject the permit if it doesn't match `conflict.superseded_by.consensus_hash`.

### Proof of Concept
```rust
// signerdb.rs test, extending the existing get_signed_conflicts suite
#[test]
fn stale_reorg_permit_not_honored_for_unrelated_conflict() {
    let mut db = SignerDb::new(":memory:").unwrap();
    // tenure A produces block N (signed), tenure C is unrelated (also signed at same height)
    insert_block(&mut db, /* tenure = A, height = H, hash = N */);
    insert_block(&mut db, /* tenure = C, height = H, hash = C_block */);

    // Tenure A was legitimately superseded by tenure B (a different conflict entirely)
    let ch_b = ConsensusHash([0xBB; 20]);
    let bbh_b = BurnchainHeaderHash([0xBB; 32]);
    db.mark_tenure_superseded(&consensus_hash_a, 10, &ch_b, &bbh_b).unwrap();

    // Query conflicts for tenure C's block: A's block N is returned, annotated superseded_by = B
    let conflicts = db.get_signed_conflicts(H, &c_block_hash).unwrap();
    let n_conflict = conflicts.iter().find(|c| c.consensus_hash == consensus_hash_a).unwrap();
    assert_eq!(n_conflict.superseded_by.as_ref().unwrap().consensus_hash, ch_b);

    // Assert this permit must NOT apply to tenure C's proposal: B never permitted a reorg
    // against C, only against B's own original conflict with A.
    // (Today, `reorg_permit_stands` has no way to detect this: it only checks that B's
    // sortition is canonical, not that the current proposal's tenure is B.)
    assert_ne!(n_conflict.superseded_by.as_ref().unwrap().consensus_hash, consensus_hash_c);
    // EXPECTED FIX: reorg_permit_stands(client, n_conflict, /*current_tenure=*/ &consensus_hash_c)
    // must return false because consensus_hash_c != superseded_by.consensus_hash,
    // even though B's sortition is still canonical.
}
```
This demonstrates the equality violation directly at the `signerdb.rs` layer: the permit recorded for the pair (A, B) is returned unchanged for an entirely different pair (A, C), and nothing in `get_signed_conflicts`/`reorg_permit_stands` distinguishes the two.
