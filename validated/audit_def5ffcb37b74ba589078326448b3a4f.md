### Title
Signer permanently stuck refusing to sign a now-valid pre-committed block once its conflicting sibling goes stale, if no new pre-commit/re-proposal event ever arrives — ([File: stacks-signer/src/v0/signer.rs])

### Summary
The bug class in the external report is: a queue/state that needs periodic re-evaluation is only re-evaluated from one specific trigger point, so once that trigger stops firing, the state is never advanced again. The stacks-signer codebase has a structural analog in the pre-commit → signature path: the "conflict guard" that decides whether a pre-committed block may still be signed is a pure per-evaluation question (`conflict_still_blocks`/freshness check), deliberately **not recorded** anywhere, and is only re-run when `handle_block_pre_commit` is invoked again by a fresh incoming message (another peer's pre-commit, or a re-proposal). There is no tick/periodic re-check of blocks parked in the "refuse to sign for now" (`HOLD1`) branch.

### Finding Description
`handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs`, around L1250–L1374) is the only function that can promote a `PreCommitted` block to `LocallyAccepted` (i.e., produce our signature) once the ≥70% pre-commit weight threshold is reached. Per the documented flow (`docs/signer-flows.md` L229–298), when a conflicting signed block exists that is still "fresh" (`last_endorsed > cutoff`) and canonical, the signer takes the `HOLD1`/`HOLD2` branch: it silently declines to sign, on the theory that it "may sign once conflict is stale."

Crucially, "freshness" and "still blocks" are **derived per evaluation, not recorded** (explicitly stated at L288–297: "Deriving this here — instead of recording it when a fork is observed — is deliberate... a question asked per evaluation self-corrects on the next pre-commit or re-proposal"). That means the *only* way this signer re-examines whether it can now sign is if `handle_block_pre_commit` is invoked again — which happens only when:
1. A new `BlockPreCommit` message arrives from a peer for that block hash, or
2. A new block acceptance from a peer that never pre-committed is reinterpreted as a pre-commit (`store_and_process_block_signature`, L2462–2466), or
3. The block is re-proposed by the miner.

`process_event`'s per-tick housekeeping (`docs/signer-flows.md` L80–86) — "retire a timed-out validation submission, submit the next queued proposal, settle any pending state-machine update... check current miner for inactivity, and consider capitulating the miner view" — does **not** include re-running the pre-commit/conflict check for blocks parked in `PreCommitted` state. There is no analog of the "external `updateWithdrawalQueue`" fix from the report: no tick-driven or externally-triggerable re-evaluation of a stuck pre-committed block.

Once the rest of the signer set has already reached 70% pre-commit weight and moved on (each of them individually signed via their own `handle_block_pre_commit` call before this signer's conflict went stale), there is no structural reason for any further `BlockPreCommit` message or re-proposal to be sent for that block hash — the miner has no reason to re-propose a block that already has enough signatures, and other signers have no reason to re-broadcast a pre-commit they already sent. This signer's stored `PreCommitted` `BlockInfo` (L152–162 chainstate lifecycle in `docs/signer-flows.md`) is then wedged: valid, willing, above-threshold, but never re-evaluated, so `signed_self` never gets set for that block.

### Impact Explanation
This matches the High-severity liveness class explicitly allowed by the rules: "a signer wedged into never signing valid blocks." The affected signer never contributes its signature/weight to that block (and by extension to that tenure's chain of validity, since `check_latest_block_in_tenure` consults `get_last_signed_block`), even though the block is valid and correctly pre-committed. If several signers converge on the same conflict-then-stale timing (plausible since the miner/gossip pattern that triggers it — proposing near-simultaneous sibling blocks at the same height — is symmetric across the signer set), a meaningful fraction of signer weight could be permanently withheld from future height/tenure validity computations (`get_last_signed_block`, `get_signed_conflicts`) until the process restarts.

### Likelihood Explanation
Reachable by a one-slot miner (or malicious relay) proposing two conflicting blocks at the same height in the miner's own tenure — one of which is signed first, creating the "own-tenure conflict" state that routes the *other* to `HOLD2`/`HOLD1`. No majority of signers or additional keys are needed; only ordinary gossip/proposal traffic that a single miner can produce. The wedge condition ("no further pre-commit or re-proposal ever arrives for that hash after the conflict times out") depends on the rest of the network's behavior, which is plausible in steady state once the block already reached its own signature threshold without this signer's participation.

### Recommendation
Add a mechanism analogous to the fix in the external report: periodically (from the `process_event` tick loop, alongside `check_miner_inactivity`) re-invoke the pre-commit/conflict evaluation for any block still sitting in `PreCommitted` state with `signed_self` unset, rather than relying exclusively on inbound `BlockPreCommit`/re-proposal messages to trigger `handle_block_pre_commit`.

### Proof of Concept
Not independently reproducible from static analysis alone; the above is derived from the documented state-machine semantics in `docs/signer-flows.md` L229–298 and the message-triggered-only call sites of `handle_block_pre_commit` in `stacks-signer/src/v0/signer.rs` (L1250, L2464).     fn handle_block_pre_commit(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        stacker_address: &StacksAddress,
        block_hash: &Sha512Trunc256Sum,
    ) {
        let Some(mut block_info) = self.block_lookup_by_reward_cycle(block_hash) else {
            // A pre-commit for a block we have not seen proposed yet means the proposal
            // has not reached us. Log it at INFO: it is a direct signal that our view of
            // the proposal stream is behind the rest of the signer set.
            info!("{self}: Received block pre-commit for an unknown block, storing as pending";
                "signer_address" => %stacker_address,
                "signer_signature_hash" => %block_hash,
                "signer_weight" => self.signer_weights.get(stacker_address).copied().unwrap_or(0),
            );
            if let Err(e) = self
                .signer_db
                .add_pending_block_pre_commit_response(block_hash, stacker_address)
            {
                warn!("{self}: Failed to save pending block pre-commit response: {e:?}");
            }
            return;
        };
        // Always save the pre-commit - we will need to store signer responses for determining which
        // are misbehaving, offline, etc.
        // commit message is from a valid sender! store it
        self.signer_db
            .add_block_pre_commit(block_hash, stacker_address)
            .unwrap_or_else(|_| panic!("{self}: Failed to save block pre-commit"));

        let block_hash = block_info.block.header.signer_signature_hash();
        // do we have enough pre-commits to reach consensus?
        // i.e. is the threshold reached?
        //
        // Tally this up front, before the early returns below, so that every pre-commit we
        // receive can be logged with the running weight. Crossing this threshold is what
        // triggers our block response, so without it the wait for the threshold, which can
        // be minutes and is the bulk of a stalled block's latency, leaves no trace at all.
        let committers = self
            .signer_db
            .get_block_pre_committers(&block_hash)
            .unwrap_or_else(|_| panic!("{self}: Failed to load block commits"));

        let commit_weight = self.compute_signature_signing_weight(committers.iter());
        let total_weight = self.compute_signature_total_weight();

        let min_weight = NakamotoBlockHeader::compute_voting_weight_threshold(total_weight)
            .unwrap_or_else(|_| {
                panic!("{self}: Failed to compute threshold weight for {total_weight}")
            });

        info!("{self}: Received block pre-commit";
            "signer_address" => %stacker_address,
            "signer_signature_hash" => %block_hash,
            "consensus_hash" => %block_info.block.header.consensus_hash,
            "block_height" => block_info.block.header.chain_length,
            "signer_weight" => self.signer_weights.get(stacker_address).copied().unwrap_or(0),
            "pre_commit_weight" => commit_weight,
            "pre_commit_weight_required" => min_weight,
            "total_weight" => total_weight,
            "pre_commit_threshold_reached" => commit_weight >= min_weight,
            "already_signed" => block_info.signed_self.is_some(),
        );

        if block_info.signed_self.is_some() {
            debug!(
                "{self}: Received pre-commit for a block that we have already signed. Doing nothing...",
            );
            return;
        }

        if !block_info.valid.unwrap_or(false) {
            // We received a pre-commit for a block that we have not validated or we have already marked this block as invalid.
            // We should not do anything further as we do not know what our response should be and we do not change our votes on rejected
            // blocks unless we receive a new block proposal for it and the reject reason allows us to reconsider.
            debug!(
                "{self}: Received a pre-commit for a block that we have not determined to be valid: {:?}. Doing nothing...", block_info.valid
            );
            return;
        }

        if min_weight > commit_weight {
            debug!(
                "{self}: Not enough pre-committed to block {block_hash} (have {commit_weight}, need at least {min_weight}/{total_weight})"
            );
            return;
        }
