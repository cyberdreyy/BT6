### Title
Unvalidated `parameters` fee data in `createDstEscrow` allows a taker to permanently brick destination withdrawals via arithmetic underflow - (File: `contracts/BaseEscrowFactory.sol`)

### Summary
`BaseEscrowFactory.createDstEscrow()` accepts a fully caller-supplied `IBaseEscrow.Immutables` struct, including the `parameters` bytes field that encodes `protocolFeeAmount`, `integratorFeeAmount`, `protocolFeeRecipient`, and `integratorFeeRecipient`. Unlike the equivalent source-side path, `createDstEscrow` performs no validation that `protocolFeeAmount + integratorFeeAmount < amount`. This missing bounds check is the same root-cause class as the reported `Gateway.query()` issue: struct fields that flow into later logic are accepted without being checked for sane/valid ranges before being locked into deployed state.

### Finding Description
On the source chain, `BaseEscrowFactory._postInteraction()` explicitly guards against bad fee accounting: [1](#0-0) 

On the destination chain, `createDstEscrow()` takes the full `dstImmutables` (including `parameters`) directly from `msg.sender` (any unprivileged taker) and deploys the clone with no equivalent check: [2](#0-1) 

The `parameters` bytes are later decoded via `ImmutablesLib.protocolFeeAmountCd`/`integratorFeeAmountCd` and consumed in `EscrowDst._withdraw()`: [3](#0-2) 

Line `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` is unchecked-by-design arithmetic in Solidity 0.8, which reverts on underflow if `integratorFeeAmount + protocolFeeAmount > immutables.amount`. Since a taker fully controls `parameters` at `createDstEscrow` time, and the immutables hash committed at deployment (via `ImmutablesLib.hash`/`hashMem`) locks these values for the life of the escrow, a taker can deploy a destination escrow whose `withdraw()` and `publicWithdraw()` will unconditionally revert for every caller (maker, taker, or public-withdraw access-token holder), because `_withdraw` is reached only after `onlyValidImmutables` succeeds and then always underflows.

`cancel()` on `EscrowDst` is unaffected by this corrupted field, so after the `DstCancellation` timelock the taker can still reclaim their own deposited destination funds via `cancel()`: [4](#0-3) 

Meanwhile the source-chain `EscrowSrc.withdraw()` has no dependency on destination-chain escrow state — it only checks `onlyCaller(taker)`, timelocks, and the secret hash: [5](#0-4) [6](#0-5) 

This breaks the intended cross-chain atomicity invariant that a taker can only claim the maker's source funds if the maker actually receives their destination funds (or funds are cancelled back through the intended paths); here the destination-side withdrawal path can be made permanently unusable by the taker at deployment time.

### Impact Explanation
This is a taker/unprivileged-user-triggered broken invariant reachable purely through the public `createDstEscrow` entry point named explicitly as an attack surface in scope. The concrete effect: maker's expected destination-chain proceeds become **permanently unwithdrawable** (both `withdraw` and `publicWithdraw` revert forever due to the underflow), while the taker can still `cancel()` and recover their own deposited funds after the timelock. This is at minimum a "temporary freezing of funds during the live swap lifecycle" (funds are locked from deployment until the `DstCancellation` timelock elapses, and even then only the taker — not the maker — recovers value), and depending on whether the resolver/maker off-chain protocol has already revealed the secret in anticipation of a successful destination withdrawal, it can escalate to permanent loss of the maker's intended destination-side value, since the maker never receives the swapped tokens through any code path in this contract.

### Likelihood Explanation
High likelihood: `createDstEscrow` is a normal, public, unprivileged entry point that any resolver/taker calls to fund the destination side of a swap; setting `parameters` such that `protocolFeeAmount + integratorFeeAmount >= amount` requires no special access and costs the attacker nothing extra beyond the safety deposit/token amount they must supply anyway (which they later reclaim via `cancel()`).

### Recommendation
Add the same guard used in `_postInteraction` to `createDstEscrow` before deployment, e.g.:
```solidity
uint256 protocolFeeAmount = ImmutablesLib.protocolFeeAmountCd(dstImmutables);
uint256 integratorFeeAmount = ImmutablesLib.integratorFeeAmountCd(dstImmutables);
if (protocolFeeAmount + integratorFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();
```
placed in `contracts/BaseEscrowFactory.sol` inside `createDstEscrow`, mirroring the existing check at [7](#0-6) .

### Proof of Concept
1. Taker (attacker) prepares `dstImmutables.parameters = abi.encode(protocolFeeAmount, integratorFeeAmount, protocolFeeRecipient, integratorFeeRecipient)` such that `protocolFeeAmount + integratorFeeAmount >= dstImmutables.amount`.
2. Taker calls `BaseEscrowFactory.createDstEscrow{value: nativeAmount}(dstImmutables, srcCancellationTimestamp)` — no on-chain validation rejects the malformed fee data; the escrow is deployed and funded per `contracts/BaseEscrowFactory.sol` lines 165-185.
3. Once the withdrawal window opens, any attempt to call `EscrowDst.withdraw()` or `EscrowDst.publicWithdraw()` reaches `_withdraw()` and reverts on the underflow at `contracts/EscrowDst.sol` line 92, for every caller, permanently.
4. After `DstCancellation` timelock passes, the taker calls `cancel()` and reclaims their own deposited token/native amount, per `contracts/EscrowDst.sol` lines 64-73, while the maker never receives any destination-chain funds through this escrow.

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```

```text
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```
