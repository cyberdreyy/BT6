### Title
User enumeration via timing side-channel in `localLoginFallback` - ([File: core/sessions/oidcauth/oidc.go])

### Summary
`localLoginFallback` short-circuits on a DB lookup miss before ever invoking `utils.CheckPasswordHash`, while a login attempt against a real (existing) email always incurs the cost of a bcrypt comparison. This creates a large, easily measurable latency gap between "email not found" and "email found, wrong password" responses, allowing an unauthenticated attacker to enumerate valid local-admin email addresses.

### Finding Description
`CreateSession` calls `localLoginFallback` [1](#0-0) , which:
1. Queries `SELECT * FROM users WHERE lower(email) = lower($1)` and returns immediately with `sql.ErrNoRows` (or a similar driver error) if no user matches [2](#0-1) .
2. Only if a row is found does it proceed to `constantTimeEmailCompare` and then `utils.CheckPasswordHash(sr.Password, string(user.HashedPassword))` [3](#0-2) .

`constantTimeEmailCompare` itself is constant-time by design (fixed 256-byte padding) [4](#0-3) , so it does not leak anything — that mitigation works as intended. The real leak is structural: bcrypt hashing (`utils.CheckPasswordHash`) is deliberately expensive (tens of milliseconds), and it is only ever invoked when the email exists in the `users` table. A request for a non-existent email returns after a cheap indexed SQL lookup (sub-millisecond to low-millisecond), while a request for a valid email always pays the bcrypt cost regardless of whether the password is correct. An attacker who sends `CreateSession` requests for a list of candidate emails can distinguish "exists" vs "does not exist" purely from response latency, without needing to guess the password or rely on error-string differences.

The error messages themselves (`errors.New("invalid email")`, `errors.New("invalid password")`, and the raw `sql.ErrNoRows`-derived error for missing users) are also textually distinct at the `localLoginFallback` level, but I was unable to confirm from the code inspected whether `core/web/sessions_controller.go` forwards these distinct error strings verbatim to the HTTP client or normalizes them into a single generic message — this should be verified separately. Regardless, the timing side-channel exists independent of what the controller does with the error text, since it is observable purely from wall-clock response time.

### Impact Explanation
This enables account/email enumeration for the local-admin login path exposed via the node's session endpoint. Confirmed valid admin emails materially narrow the search space for follow-on credential stuffing or targeted brute force against the Chainlink node's admin UI/API, which controls job, key, and fund-related operations. This maps to Chainlink's "user enumeration facilitating targeted credential stuffing" impact class — a real but lower-severity information-disclosure issue rather than direct authentication bypass.

### Likelihood Explanation
No credentials or privileges are required — this is reachable by any unauthenticated client that can send local-login `CreateSession` requests to the node's HTTP session endpoint. The attack is trivially repeatable (statistical timing sampling over many requests per candidate email), requires no race conditions, and network jitter can be averaged out with repeated sampling, making it practically feasible against a node without additional rate limiting.

### Recommendation
Ensure constant work is performed regardless of whether the email is found: e.g., always perform a dummy/constant-cost bcrypt comparison against a fixed reference hash when the user is not found, so that both "user not found" and "wrong password" paths take equivalent time. Additionally, normalize all failure responses from `CreateSession`/`localLoginFallback` (email not found, email mismatch, wrong password) into a single generic "invalid credentials" error before returning it to the HTTP layer, and apply rate limiting/backoff on repeated login attempts per source IP or per email.

### Proof of Concept
Go unit test plan for `core/sessions/oidcauth/oidc_test.go`:
1. Seed the `users` table with one known local-admin user (with a valid bcrypt-hashed password).
2. Case A: call `localLoginFallback` (or `CreateSession`) with the known email and an incorrect password; measure elapsed time over N iterations (e.g., N=50), record mean/median.
3. Case B: call the same function with a random, non-existent email and any password; measure elapsed time over the same N iterations.
4. Assert that the mean time for Case A is significantly greater than Case B (e.g., by more than one bcrypt-hash duration, such as >20ms difference), demonstrating a statistically reliable distinguisher.
5. Optionally assert on the returned error values/strings from both cases to document whether they differ (`sql.ErrNoRows`-wrapped error vs `errors.New("invalid password")`), for completeness given the audit's identity-existence-leak invariant.

func constantTimeEmailCompare(left, right string) bool {
	const constantTimeEmailLength = 256
	length := mathutil.Max(constantTimeEmailLength, len(left), len(right))
	leftBytes := make([]byte, length)
	rightBytes := make([]byte, length)
	copy(leftBytes, left)
	copy(rightBytes, right)
	return subtle.ConstantTimeCompare(leftBytes, rightBytes) == 1
}
