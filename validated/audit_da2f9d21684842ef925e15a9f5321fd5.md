### Title
Per-account cost-tracker limit allows a low-cost griefing attack to block legitimate transactions to a shared/hot account for an entire block - ([File: cost-model/src/cost_tracker.rs])

### Summary
The GMX/PirexGmx bug is a "shared cooldown resource" issue: an attacker can cheaply and repeatedly trigger a low-cost operation that resets a shared per-user rate-limit window, permanently starving legitimate users of the ability to complete a state-changing operation (redeem) on that shared resource. The closest reachable analog in Agave is the per-writable-account cost limit enforced by `CostTracker::would_fit` / `add_transaction_cost` in [1](#0-0) , combined with `MAX_WRITABLE_ACCOUNT_UNITS` from `cost-model/src/block_cost_limits.rs`. Any account that is write-locked by many unrelated user transactions in the same block (a "hot account": a shared program state account, PDA, pool, escrow, etc.) has a single shared CU budget for the entire block. An attacker can cheaply and repeatedly submit low-cost transactions that write-lock that same account, filling its per-account CU budget for the block, causing legitimate transactions from other users that also need to write to that account (e.g., a withdrawal/redeem instruction against a shared vault/pool account) to be rejected with `WouldExceedAccountMaxLimit` for the remainder of the block — a recurring, cheap, block-by-block denial of service against anyone needing to interact with that account.

### Finding Description
`CostTracker` tracks CU cost per writable account in `cost_by_writable_accounts: HashMap<Pubkey, u64>` and enforces `account_cost <= MAX_WRITABLE_ACCOUNT_UNITS` (the account limit is a fraction of `MAX_BLOCK_UNITS`) as seen in `CostTrackerLimits::default()` [2](#0-1) . In `would_fit`, once a transaction's writable accounts have already accumulated cost close to `account_cost` limit, any further transaction that write-locks the same account is rejected with `CostTrackerError::WouldExceedAccountMaxLimit` [3](#0-2) , which maps to `TransactionError::WouldExceedMaxAccountCostLimit` [4](#0-3) .

Because this limit is per-account and per-block, and it is refilled/reset every new block (new `CostTracker::new_from_parent_limits`, cost_by_writable_accounts starts empty each new block) [5](#0-4) , an ordinary user (attacker) can, at the start of every new block/leader slot, cheaply submit transactions that write-lock a target "shared" account (e.g., a popular program's global state account, a liquidity pool, or any account that legitimate withdraw/redeem transactions must also write to) until that account's CU budget for the block is exhausted. Any subsequent transaction in that block that also needs to write that account — including a legitimate user's withdrawal — will fail to be scheduled/executed with `WouldExceedMaxAccountCostLimit`, and this can be repeated block after block. This mirrors the GMX bug pattern exactly: a shared, per-resource rate-limit/budget that is consumed by cheap, repeated attacker activity, permanently starving other users who need to touch the same shared account, at low and predictable cost to the attacker (ordinary transaction fees), reachable purely via normal user transaction submission (no privileged access needed).

This is a well-known class of issue in Solana referred to as "hot account contention" / "account-cost-limit griefing," and is architecturally inherent to the per-account CU budget design, not a coding bug per se, but the reachability path (ordinary transactions from any account holder) and its recurring, cheap nature match the GMX report's bug class precisely.

### Impact Explanation
An attacker can, for the cost of ordinary transaction fees (and possibly minimal priority fees to guarantee scheduling), repeatedly write-lock a shared account (e.g., a lending-pool vault, an AMM pool state account, a bridge/escrow account) with cheap transactions to consume the account's `MAX_WRITABLE_ACCOUNT_UNITS` CU budget every block. This prevents any other legitimate transaction that must write that same shared account (e.g., withdrawals/redemptions from that pool) from being included in that block, and the attack can be sustained block after block, effectively denying withdrawal-like functionality for any protocol whose critical write path funnels through a single hot account. This is a state-mutation-denial (ingest/scheduling starvation) impact reachable by any ordinary user without requiring privileged access, matching the "ingest starvation" / "metering bypass"-adjacent category permitted by the scan rules.

### Likelihood Explanation
Likelihood is significant for any protocol design that concentrates many users' state-changing writes onto a single hot account (common in DeFi-style programs on Solana: shared vault/pool/global-state accounts). The attack requires no special privileges — any funded keypair can submit these transactions — and the per-account cost limit and its full-block reset behavior are core, well-documented parts of `CostTracker`. The primary mitigating factors are: (1) the per-account CU budget (`MAX_WRITABLE_ACCOUNT_UNITS`) is large enough that filling it entirely with cheap transactions in a single block requires enough transaction volume/fees to be economically nontrivial for high-value targets, and (2) well-designed programs may shard state across multiple accounts to avoid a single point of write contention. Nonetheless, the underlying mechanism is directly reachable and requires no validator/privileged access, matching an "ordinary user transaction" path as required by the scan rules.

### Recommendation
- Document/flag the hot-account cost-limit griefing risk for program developers (avoid funneling all user state-changing writes through a single global account when possible; shard/partition state).
- Consider evaluating whether per-account cost limits should scale dynamically with account importance/usage, or whether priority-fee-based scheduling sufficiently mitigates the ability of low-fee attackers to systematically starve a specific account across many consecutive blocks.
- Consider reserving/prioritizing a fraction of an account's per-block CU budget for high-priority-fee transactions to make sustained griefing economically costly, analogous to the GMX report's own suggested mitigation of reserving specific time/resource windows for legitimate operations.

### Proof of Concept
1. Identify a shared program account `V` (e.g., a pool/vault account) that both benign user withdrawal transactions and cheap attacker transactions must write-lock.
2. At the start of a block, attacker submits N cheap transactions (e.g., no-op writes, small transfers, or minimal-CU program calls) that each write-lock `V`, using `CostTracker::add_transaction_cost` bookkeeping shown at [6](#0-5)  to accumulate cost against `V` in `cost_by_writable_accounts`.
3. Once the accumulated cost for `V` approaches `MAX_WRITABLE_ACCOUNT_UNITS`, any further transaction (including a legitimate user's withdrawal) that also writes `V` will fail `would_fit`'s per-account check [7](#0-6)  and be rejected with `WouldExceedMaxAccountCostLimit`.
4. Because `CostTracker`'s writable-account map resets each new block [5](#0-4) , the attacker repeats steps 2–3 every block to sustain the denial-of-service against transactions touching `V`.

Note: I was unable to fully verify the exact numeric value of `MAX_WRITABLE_ACCOUNT_UNITS` and `MAX_BLOCK_UNITS` from `cost-model/src/block_cost_limits.rs` within the available tool calls (the file content itself was not returned by the final read attempt), so the precise economic cost of sustaining this attack (number of transactions/fees required per block) could not be quantified here and would need further investigation in a full session.

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // check each account against account_cost_limit,
        for account_key in tx_cost.writable_accounts() {
            match self.cost_by_writable_accounts.get(account_key) {
                Some(chained_cost) => {
                    if chained_cost.saturating_add(cost) > self.limits.account_cost {
                        return Err(CostTrackerError::WouldExceedAccountMaxLimit);
                    } else {
                        continue;
                    }
                }
                None => continue,
            }
        }

        Ok(())
    }

    // Returns the highest account cost for all write-lock accounts `TransactionCost` updated
    fn add_transaction_cost(&mut self, tx_cost: &TransactionCost<impl TransactionWithMeta>) -> u64 {
        self.allocated_accounts_data_size += tx_cost.allocated_accounts_data_size();
        self.transaction_count += 1;
        self.transaction_signature_count += tx_cost.num_transaction_signatures();
        self.secp256k1_instruction_signature_count +=
            tx_cost.num_secp256k1_instruction_signatures();
        self.ed25519_instruction_signature_count += tx_cost.num_ed25519_instruction_signatures();
        self.secp256r1_instruction_signature_count +=
            tx_cost.num_secp256r1_instruction_signatures();
        self.add_transaction_execution_cost(tx_cost, tx_cost.sum())
    }
