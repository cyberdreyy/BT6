### Title
Post-default withdraw receipts are paid 1:1 from the finite `defaultRecoveryReserve`, stealing recovery funds owed to already-defaulted claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` mints a par-valued receipt for requests made after `defaultRecoveryFinalized` and `_claimPostDefaultWithdrawRequest` pays it out of `defaultRecoveryReserve`. That reserve was sized at `finalizeDefaultRecovery` as `recoveryPrice * totalBasis`, where `totalBasis` only covered claims existing at finalization (`activeBasis + pendingBasis`). Post-default receipts therefore double-spend a reserve that was already fully allocated — a use-after-free analog where claims draw on backing that has economically already been "freed" and distributed to prior claimants.

### Finding Description
In `requestWithdraw`, when `defaultRecoveryFinalized` is true the vault burns `_amount` strategy tokens from the CDO and mints an equal receipt to the user, recorded in `postDefaultRequests[_user]` [1](#0-0) . `claimWithdrawRequest` then routes to `_claimPostDefaultWithdrawRequest`, which pays the full receipt amount from the recovery reserve via `_transferDefaultRecovery` [2](#0-1) .

The reserve was fixed at finalization: `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, where `totalBasis = activeBasis + pendingBasis` [3](#0-2) . Post-default requests are *not* part of `totalBasis`, yet they consume the same reserve at par. The receipt minted in `requestWithdraw` is `_amount` in underlying units priced at the post-haircut `virtualPrice`, so each unit paid 1:1 removes roughly `recoveryPrice`-equivalent of backing that belongs to defaulted-epoch receipts (`withdrawsRequestsByEpoch`/`instantWithdrawsRequestsByEpoch` claims paid at `defaultRecoveryPrice`) and to active tranche holders claiming through `DefaultDistributor`.

### Impact Explanation
Any tranche-token holder can, immediately after `finalizeDefaultRecovery`, call `requestWithdraw` then `claimWithdrawRequest` and drain `defaultRecoveryReserve` at par. Each unit withdrawn reduces the reserve below what is needed to honor the fixed `defaultRecoveryPrice` for all pre-default claimants. Honest defaulted-epoch withdrawers and active tranche holders then find `_transferDefaultRecovery` underfunded — direct theft plus permanent freezing of unclaimed recovery yield. The theft is bounded only by the attacker's tranche balance but scales to the entire residual reserve if the attacker is a large holder or acquires tranche tokens cheaply post-default (their market price already reflects the haircut, while the payout is funded from the shared reserve).

### Likelihood Explanation
Requires only an unprivileged tranche-token holder acting after default finalization — a normal, reachable state (`defaulted()` → `finalizeDefault` → `finalizeDefaultRecovery`). No privileged cooperation needed; owner/manager merely execute honest default-finalization calls. The guard at lines 247–251 only forces claiming *old* receipts first; it does not restrict new post-default requests or cap total post-default payouts against the reserve. No existing check reconciles `postDefaultRequests` payouts with remaining `defaultRecoveryPrice` obligations. Confirmed uncertainty: the exact insolvency behavior depends on whether `_transferDefaultRecovery` reverts or underpays when the reserve is exhausted — either outcome is a loss to honest claimants (theft if paid first-come-first-served, permanent freezing if it reverts).

### Recommendation
Either (a) exclude post-default receipts from drawing on `defaultRecoveryReserve` — fund them only from post-finalization inflows tracked in a separate bucket — or (b) include a conservative allowance for post-default claims in `totalBasis` at finalization and pay post-default receipts at `defaultRecoveryPrice`, not par. At minimum, cap `_claimPostDefaultWithdrawRequest` so that `reserve >= (remaining defaulted claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` is preserved before honoring post-default payouts.

### Proof of Concept
Foundry fork test outline (against `IdleCreditVault` + `IdleCDOEpochVariant`):

```solidity
// 1. Users deposit; manager startEpoch(); warp past epochEndDate.
// 2. Honest user H calls cdoEpoch.requestWithdraw(...) -> pendingWithdraws set.
// 3. stopEpoch with insufficient borrower funds -> cdoEpoch.defaulted() == true.
// 4. manager calls finalizeDefaultRecovery(recovered, source) with recovered < basis
//    -> defaultRecoveryPrice < RECOVERY_FULL, reserve fixed.
// 5. Attacker A (tranche holder, no pending receipts) calls:
//       cdoEpoch.requestWithdraw(trancheBalance, tranche);
//       cdoEpoch.claimWithdrawRequest();
//    A receives postDefaultRequests[A] paid 1:1 from defaultRecoveryReserve.
// 6. Honest H calls claimWithdrawRequest() -> _claimDefaultedWithdrawRequest
//    computes claimBasis * defaultRecoveryPrice, but _transferDefaultRecovery
//    now reverts/underpays because reserve < required amount.
// assertLt(underlying paid to H, claimBasis * defaultRecoveryPrice / RECOVERY_FULL);
```

Run with `forge test --fork-url $RPC` mirroring the setup in `test/foundry/IdleCreditVault.t.sol` (`_startEpochAndCheckPrices`, `deal(defaultUnderlying, manager, recovered)`, `cdoEpoch.finalizeDefault(...)`).

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
    _transferDefaultRecovery(_user, amount);
  }
