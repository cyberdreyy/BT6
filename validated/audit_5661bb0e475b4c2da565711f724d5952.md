### Title
Re-requesting a withdrawal after a loss-adjusted epoch resets `lastWithdrawRequest` and lets the haircutted receipt claim at par — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The KRACK bug class is a *reinstallation/replay* flaw: an already-consumed handshake state is replayed because a fresh message resets the key/nonce tracking. The vault analog lives in `IdleCreditVault.requestWithdraw` / `claimWithdrawRequest`. `requestWithdraw` unconditionally overwrites the single-slot pointer `lastWithdrawRequest[_user] = currentEpoch`, while loss-haircut bookkeeping is keyed by epoch in `lossRecoveryPriceByEpoch[epoch]` and per-epoch basis in `withdrawsRequestsByEpoch[_user][epoch]`. `_claimLossAdjustedWithdrawRequest` only ever looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. A user whose receipt was haircutted by a `stopEpochWithDuration` loss can simply file a *new* withdraw request; the new epoch number overwrites the loss-epoch pointer, the loss-adjusted path returns 0, and `_claimFundedWithdrawRequest` then pays the aggregate `withdrawsRequests[_user]` — which still includes the haircutted basis — at par.

### Finding Description
Relevant code:

- `requestWithdraw` records the receipt and resets the marker: `lastWithdrawRequest[_user] = currentEpoch; withdrawsRequests[_user] += _amount; withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;` — `contracts/strategies/idle/IdleCreditVault.sol` lines 282–293.
- On a `stopEpochWithDuration` loss, the CDO calls `collectWithdrawFunds(pendingToFund)` with `pendingToFund < pendingWithdraws`; the vault sets `pendingWithdraws = 0` and `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` — lines 411–421. Note the haircut is *not* written into `withdrawsRequests` / `withdrawsRequestsByEpoch`; those still hold the full pre-loss basis.
- `_claimLossAdjustedWithdrawRequest` derives the epoch solely from `lastWithdrawRequest[_user]` — lines 789–800.
- `_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]` (aggregate, all epochs) at par once `epochNumber > lastWithdrawRequest[_user]` — lines 319–350.

Attack trace (epoch phases labeled):

1. **Buffer of epoch E1**: attacker (KYC'd lender, unprivileged) calls `cdoEpoch.requestWithdraw(trancheAmt, AA)` → vault mints receipt `_amount`, sets `lastWithdrawRequest[attacker] = E1`, `withdrawsRequestsByEpoch[attacker][E1] = _amount`, `pendingWithdraws += _amount`.
2. **Running → stop of E1**: owner calls `stopEpoch(_interest, _lossAmount)`; `previewLossAdjustedWithdrawFunds` returns `pendingToFund < pendingBasis`; `collectWithdrawFunds(pendingToFund)` stores `lossRecoveryPriceByEpoch[E1] = p < 1e18` and zeroes `pendingWithdraws`. The attacker does **not** claim (claiming now would route through the haircut and clear the receipt).
3. **Buffer of E2**: attacker calls `requestWithdraw` again with the remainder of their tranche tokens. `lastWithdrawRequest[attacker]` is overwritten to `E2`; `withdrawsRequests[attacker]` now aggregates `E1_basis + E2_basis`. The code comments explicitly allow stacking requests ("requests another withdraw, he will have to wait for another epoch"), so no guard stops this.
4. **After epoch E2 stops** (normally funded): `claimWithdrawRequest()` → `defaultRecoveryFinalized == false` → `_claimLossAdjustedWithdrawRequest` computes `lossEpoch = E2`, `lossRecoveryPriceByEpoch[E2] == 0` → returns 0 *without clearing anything* → `_claimFundedWithdrawRequest` pays `E1_basis + E2_basis` at par and burns the receipts.

Broken invariant: **one receipt, one (haircut-adjusted) payout** / loss waterfall. The E1 receipt was already loss-assigned; the strategy only pulled `pendingToFund = pendingBasis * p` for it. Paying it at par spends `E1_basis * (1 - p)` of underlying that was never funded.

The reinstallation mechanism is exactly analogous to KRACK: `lastWithdrawRequest` is the "nonce/key" that decides which accounting regime a receipt belongs to; issuing a new request "reinstalls" the pointer to a clean epoch, so the replayed (haircutted) receipt is treated as fresh.

### Impact Explanation
Direct theft / insolvency. The attacker extracts `E1_basis * (1 - lossRecoveryPrice)` more underlying than funded. Since `collectWithdrawFunds` only transferred the haircutted total for E1, the excess comes from underlying backing other users' pending claims or active NAV — either draining the reserve so later honest claimers' transactions revert (temporary freezing of unclaimed funds) or imposing a socialized loss equal to the stolen amount. Loss scales with the attacker's E1 basis and the epoch's realized loss; e.g., 50% loss on a 100k receipt yields ~50k underlying stolen per attack.

### Likelihood Explanation
- Attacker needs only tranche tokens and an allowed wallet — a normal KYC'd lender qualifies; no privileged role is abused (owner/manager perform ordinary `stopEpoch` with loss and ordinary funding).
- Requires a `stopEpochWithDuration`-style partial-loss epoch (`_lossAmount > 0` with pending withdrawals), which is a normal, reachable code path: `previewLossAdjustedWithdrawFunds` + `collectWithdrawFunds` exist precisely for it.
- No existing guard blocks it: `_claimFundedWithdrawRequest`'s only gate is the epoch-wait check; `withdrawsRequests`/`withdrawsRequestsByEpoch` are never reduced by the haircut; `_skimDonatedAssets`, default flags, and `_onlyIdleCDO` are irrelevant here. The only mitigation is the user voluntarily claiming the haircutted receipt before re-requesting — which the attacker simply skips.

### Recommendation
In `requestWithdraw`, do not let a new request overwrite a pending loss-adjusted marker: either revert if `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` (forcing the user to claim/clear the haircutted receipt first), or settle `_claimLossAdjustedWithdrawRequest(_user)` inline before recording the new request. Alternatively, store the haircut per `(user, epoch)` receipt value rather than relying on the single-slot `lastWithdrawRequest` pointer, so the funded-claim path can never see a haircutted basis.

### Proof of Concept
Foundry sketch against the existing `IdleCreditVault.t.sol` harness (fork environment with real USDC/IdleCDO stack as the suite already does):

```solidity
function testLossReceiptReinstalledAtPar() external {
    uint256 amount = 100_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);

    // Epoch E0: request withdraw for half
    uint256 e1Basis = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));

    // Run epoch, stop with realized loss so pending receipts are haircutted
    _startEpochAndCheckPrices(0);
    uint256 loss = /* >0 such that previewLossAdjustedWithdrawFunds gives pendingToFund < pendingBasis */;
    _stopEpochAndCheckPrices(0, initialProvidedApr, loss);

    uint256 e1 = IdleCreditVault(address(strategy)).epochNumber() - 1; // request epoch
    uint256 p  = IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(e1);
    assertLt(p, 1e18, 'receipt was not haircutted');

    // Do NOT claim. Next epoch: re-request -> lastWithdrawRequest overwritten
    cdoEpoch.requestWithdraw(mintedAA / 4, address(AAtranche));

    // Run and stop another epoch, fully funded
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 got = IERC20Detailed(defaultUnderlying).balanceOf(address(this)) - balPre;

    // Vulnerable: E1 basis paid at par instead of at price p
    uint256 expectedE2 = /* second request funded amount */;
    assertEq(got, e1Basis + expectedE2, 'par payout of haircutted receipt');
    // Correct behavior would pay e1Basis * p / 1e18 + expectedE2
}
```

Caveat: I verified the write/read paths of `lastWithdrawRequest`, `lossRecoveryPriceByEpoch`, `withdrawsRequestsByEpoch`, `collectWithdrawFunds` and the claim pipeline in `IdleCreditVault.sol`, but I did not read the exact `stopEpoch`/`stopEpochWithDuration` call sites in `IdleCDOEpochVariant.sol` in this session, so the precise owner-call sequence to reach the loss branch may differ slightly; the vault-side state transitions above are confirmed by the code and by `test/foundry/IdleCDOEpochQueue.t.sol` flows that exercise these paths.
