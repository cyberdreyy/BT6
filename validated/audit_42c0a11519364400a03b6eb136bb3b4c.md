### Title
Missing `chain_id` binding in `BlockAccepted` signature payload allows cross-network signature replay - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockAccepted` (`libsigner/src/v0/messages.rs:1657-1711`) signs and serializes only `signer_signature_hash` plus response metadata, with no `chain_id` field in the struct or in the signed payload, unlike `BlockRejection`, whose `hash()` method explicitly folds `chain_id` into the SIP-018 domain tuple via `make_structured_data_domain("block-rejection", "1.0.0", self.chain_id)` (`messages.rs:1802-1807`, `chain_id` field at `messages.rs:1725`). This asymmetry means an identical signature over an identical `signer_signature_hash` is valid evidence of acceptance on any network sharing that hash, with no cryptographic binding preventing cross-chain replay.

### Finding Description
`BlockRejection` deliberately domain-separates its signature by embedding `self.chain_id` into the SIP-018 structured-data domain before hashing and signing (`messages.rs:1732-1814`), so a rejection signed under `CHAIN_ID_TESTNET` produces a different `signature_hash()` than the same rejection signed under `CHAIN_ID_MAINNET`, even for an identical `signer_signature_hash`. `BlockAccepted` has no such field: its struct (`messages.rs:1657-1666`) and `consensus_serialize`/`consensus_deserialize` (`messages.rs:1668-1689`) only carry `signer_signature_hash`, `signature`, `metadata`, and `response_data`. `BlockAccepted::new` (`messages.rs:1693-1710`) simply stores a signature that was computed elsewhere, at the signer.rs call site — and unlike `BlockRejection::sign`/`BlockRejection::hash`, no `make_structured_data_domain`/`structured_data_message_hash` usage (the SIP-018 domain-separation helpers) appears anywhere in `stacks-signer/src/v0/signer.rs`, indicating the acceptance signature is produced without chain-id domain separation.

Consequently, if two networks (e.g. mainnet and a testnet/mocknet sharing byte-identical `NakamotoBlock` headers, or a testnet fork) produce the same `signer_signature_hash`, and a signer's operator key happens to be enrolled as a registered signer in both reward sets (a realistic scenario for testnet/mocknet operators who commonly reuse the same keys across environments), the exact same `BlockAccepted` bytes recovered from one StackerDB slot are a valid, verifiable acceptance vote on the other network's `.signers-N-1` contract. `Signer::handle_block_response -> store_and_process_block_signature (signer.rs:2442) -> add_block_signature -> mark_locally_accepted` performs weight tally purely from the recovered public key and `signer_signature_hash`; it has no chain-id check to reject a signature that was produced for a different chain.

### Impact Explanation
This breaks the safety property that a signer's acceptance vote is scoped to a single chain/network context. A replayed acceptance signature can count toward a threshold on a network the original signer never intended to vote for, allowing a bad or unintended block to accumulate signer weight and finalize on the wrong network context — matching the Critical category ("a signature valid across chain/cycle/tenure boundaries").

### Likelihood Explanation
Exploitation requires: (1) two networks/forks whose `NakamotoBlock` headers happen to be byte-identical so `signer_signature_hash()` collides, and (2) at least one signer whose key is registered as a signer on both the source and target networks/reward cycles. Condition (1) is the harder precondition and generally only realistic in test/mocknet/staging setups that share genesis/config, or deliberately constructed forks — it is not trivially achievable against Stacks mainnet vs. an independent testnet with distinct chainstate. Given those preconditions, the attacker's only required actions are gossiping the captured `BlockAccepted` bytes to the target's `.signers-N-1` StackerDB contract, which fits the "one slot plus gossip" cost model and is repeatable per occurrence of hash collision.

### Recommendation
Add a `chain_id` field to `BlockAccepted` (mirroring `BlockRejection`) and bind it into the signed payload via the same SIP-018 domain separation (`make_structured_data_domain("block-accepted", "1.0.0", chain_id)` + `structured_data_message_hash`) instead of signing the raw `signer_signature_hash`. Update `consensus_serialize`/`consensus_deserialize` to include `chain_id`, and update all verification call sites (block-response aggregation, `store_and_process_block_signature`, StackerDB message validation) to require `chain_id` to match the signer's own configured network before counting the vote.
