### Title
Loss-adjusted withdraw receipts escape the haircut when a later request overwrites `lastWithdrawRequest` — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` applies the `stopEpochWithDuration` loss haircut only to the receipt recorded at `lastWithdrawRequest[_user]`, the *most recent* request epoch. A user who had a pending receipt in the loss epoch can make a new `requestWithdraw` in a later epoch; this overwrites `lastWithdrawRequest[_user]`, so the older haircutted receipt is never routed through `lossRecoveryPriceByEpoch` and is instead paid in full at par by `_claimFundedWithdrawRequest`. This is the same class of bug as JLSEC-2026-1373: a fixed-size "window" (single epoch key) is consumed without first verifying that all out-of-scope data (earlier loss epochs recorded in `withdrawsRequestsByEpoch`) has been accounted for.

### Finding Description
In `requestWithdraw`, each request updates `lastWithdrawRequest[_user] = currentEpoch` and accumulates per-epoch and aggregate accounting [1](#0-0) .

When the borrower short-funds a stop epoch, `collectWithdrawFunds` writes a haircut price only for the epoch that was pending: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` and clears `pendingWithdraws` [2](#0-1) .

On claim, `_claimLossAdjustedWithdrawRequest` looks up the haircut solely via `uint256 lossEpoch = lastWithdrawRequest[_user]` [3](#0-2) . If the user subsequently filed another request, `lastWithdrawRequest` now points to a later epoch whose `lossRecoveryPriceByEpoch` is zero, the function returns 0, and `_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]` — which still includes the loss-epoch amount because `_clearWithdrawClaimForEpoch` never ran for it — at full par value [4](#0-3) . The code comments acknowledge the aggregate "may also include older funded receipts" but assume anything left is fully funded, which is false for a haircutted epoch [5](#0-4) .

### Impact Explanation
The loss-adjusted pool only contains `pendingToFund = pendingBasis - pendingLoss` underlyings for all epoch-N receipts. An attacker who escapes the haircut withdraws `claimBasis` instead of `claimBasis * lossRecoveryPrice / RECOVERY_FULL`, draining the shared funded pool. Other loss-epoch claimants (and later funded claimants) then cannot be paid: `_transferFundedClaim` reverts when the balance cannot cover the claim without touching `defaultRecoveryReserve` [6](#0-5) . Result: direct theft of up to `claimBasis * (1 - lossRecoveryPrice)` plus temporary/permanent freezing of other users' claims. Broken invariant: every receipt in a loss epoch must settle at `lossRecoveryPriceByEpoch[lossEpoch]`.

### Likelihood Explanation
Requires only an unprivileged user (KYC-passing lender) with two `requestWithdraw` calls bracketing a `stopEpochWithDuration(_lossAmount > 0)` executed by the honest manager during borrower underperformance — a normal, anticipated vault mode. No privileged misbehavior needed; the extra request is explicitly permitted (the code notes a user "requests another withdraw"). Likelihood is moderate: it needs a loss-adjusted stop to occur while the attacker holds a pending receipt and then files a second request before claiming.

### Recommendation
Do not key the loss-adjusted claim off `lastWithdrawRequest[_user]` alone. Iterate (or checkpoint) all epochs with non-zero `lossRecoveryPriceByEpoch` for which `withdrawsRequestsByEpoch[_user][epoch] != 0`, clearing each through `_clearWithdrawClaimForEpoch`; alternatively, block new `requestWithdraw` while the user still has an unclaimed receipt in a loss-priced epoch, or store a per-user set/bitmap of loss epochs at request time.

    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
