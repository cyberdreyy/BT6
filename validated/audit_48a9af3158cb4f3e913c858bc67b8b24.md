Based on my investigation, I found a valid analog to the CoinFabrik "optional finalize agent" bug class: a feature that is documented/configured as disabled-by-default (`ExternalInitiatorsEnabled`) still exposes a live, unauthenticated-adjacent authentication path (`AuthenticateExternalInitiator`) that grants a privileged role, independent of that config flag.

### Title
External Initiator authentication path grants `Run` role and bypasses `ExternalInitiatorsEnabled` config gate - (File: core/web/auth/auth.go)

### Summary
Similar to the CoinFabrik `Crowdsale` finalize-agent ambiguity — where an "optional" component (`finalizeAgent`) was actually load-bearing for a state transition, and the code path was never gated consistently — Chainlink's `ExternalInitiatorsEnabled` config flag is documented as controlling the "External Initiator feature," but only gates the *creation* endpoint (`POST /v2/external_initiators`), not the authentication/authorization middleware `AuthenticateExternalInitiator` wired permanently into the router at [1](#0-0) .

### Finding Description
`ExternalInitiatorsController.Create` checks `ExternalInitiatorsEnabled()` before allowing new external initiators to be created: [2](#0-1) . The config doc even states this feature is "Unused" in the current version: [3](#0-2) , and the legacy `webhook` job type that consumed External Initiator triggers has been removed (`ErrJobTypeRemoved`), as validated in tests at [4](#0-3)  and enforced in `core/services/job/orm.go` / `core/web/pipeline_runs_controller.go`.

Despite this, the router unconditionally mounts `auth.AuthenticateExternalInitiator` as an active authentication method on `/v2/ping` and `/v2/jobs/:ID/runs` regardless of the `ExternalInitiatorsEnabled` flag: [1](#0-0) . Any previously-created (or, if the flag was ever briefly enabled or an EI record persists from before) External Initiator credential pair can still authenticate via `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers, and upon success the middleware unconditionally assigns the elevated `UserRoleRun` to the request: [5](#0-4) . This grants access to `auth.RequiresRunRole` protected endpoints such as `POST /v2/jobs/:ID/runs` (triggering pipeline runs) at [6](#0-5) , and other `RequiresRunRole`-gated endpoints like `/replay_from_block`, `/find_lca`, `/lp_skip_to_block` at [7](#0-6) .

This mirrors the CoinFabrik report's core issue: a component described as "optional"/disabled is not actually decoupled from the security-relevant code path, creating ambiguity about whether the control is enforced. Here, disabling `ExternalInitiatorsEnabled` gives operators a false sense that the External-Initiator attack surface is closed, when in fact any existing/leaked EI credential continues to authenticate and assume the `Run` role indefinitely, and the feature-disable toggle provides no actual authorization boundary at the middleware/router level.

### Impact Explanation
An attacker in possession of a stale or leaked External Initiator `AccessKey`/`Secret` pair (created before the feature was "disabled," or from a decommissioned integration) can still authenticate as a `Run`-role principal even though the operator believes the External Initiator feature is turned off. This is an authentication/role-bypass relative to the operator's configured security posture: the `Run` role can trigger job runs and other run-role-gated actions such as `replay_from_block` (chain reorg-related admin action) with no session or user-token authentication required — only header-based EI credentials.

### Likelihood Explanation
Requires the attacker to possess valid EI credentials (access key + secret), which is a real constraint — this is not a fully unauthenticated bypass. However, likelihood is elevated because: (1) the config flag being labeled "Unused"/disabled creates operator confusion about whether this credential type is still honored (directly analogous to the CoinFabrik "is this optional or mandatory" confusion); (2) there is no mechanism found to disable/enforce the flag at the authentication-middleware layer, so any credential created historically remains valid forever unless explicitly deleted via `DELETE /v2/external_initiators/:Name`; (3) EI secrets are stored/transmitted similarly to API keys and are subject to the same leakage risks as any credential.

### Recommendation
Make `AuthenticateExternalInitiator` consult `ExternalInitiatorsEnabled()` (or an equivalent explicit feature flag) and fail closed when disabled, consistent with the `Create` endpoint's behavior at [8](#0-7) . Since the underlying webhook job type has been removed entirely, consider removing the `AuthenticateExternalInitiator` authMethod and the `/v2/jobs/:ID/runs` / `/v2/ping` EI-based auth route from `core/web/router.go` altogether, and purging/invalidating any existing `external_initiators` table rows, to eliminate the dangling privileged credential class.

### Proof of Concept
1. Note that config `JobPipeline.ExternalInitiatorsEnabled` documentation states the feature is "Unused" ( [3](#0-2) ), implying operators may assume EI-based access is disabled.
2. Obtain (or have previously provisioned) an `ExternalInitiator` record's `AccessKey`/`Secret`, e.g. via `bridges.NewExternalInitiator` as shown in test setup at [9](#0-8) .
3. Send `POST /v2/jobs/:ID/runs` with headers `X-Chainlink-EA-AccessKey` and `X-Chainlink-EA-Secret` set to the EI credentials.
4. `AuthenticateExternalInitiator` succeeds regardless of the `ExternalInitiatorsEnabled` setting (no check exists in `core/web/auth/auth.go`), and the request context is set with `UserRoleRun`, permitting the run-triggering action even if the operator believes External Initiators are disabled.

// AuthenticateExternalInitiator authenticates an external initiator request.
//
// Implements authMethod
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
