### Title
Signer weight double-counted in both accept and reject tallies when a signer equivocates (reject-then-accept) - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The miner-side `StackerDBListener` (which feeds `SigningCoordinator::wait_for_signer_signatures_or_rejections` in `stacks-node/src/nakamoto_node/signer_coordinator.rs`) tallies each signer's weight into either `total_weight_approved` or `total_weight_rejected` as `BlockResponse` messages arrive over StackerDB, per `BlockStatus` [1](#0-0) . The intent is that each signer's weight should be attributed to exactly one side of the vote for a given block. The rejection-handling branch enforces this correctly via a single `responded_signers` set shared across both message kinds, but the acceptance-handling branch does not check that set, so the guard is one-directional.

### Finding Description
When a `BlockResponse::Accepted` arrives, the code only checks `gathered_signatures.contains_key(&slot_id)` before crediting `total_weight_approved`, and unconditionally inserts the slot into `responded_signers` afterward: [2](#0-1) 

When a `BlockResponse::Rejected` arrives, the code guards the weight update with `if block.responded_signers.insert(slot_id)` — i.e. it only counts the rejection if this signer has never responded (accepted or rejected) before: [3](#0-2) 

This makes the guard asymmetric:
- **Accept-then-Reject**: blocked. Once a signer accepts, `responded_signers` already contains their slot, so a later rejection from the same signer is silently dropped and `total_weight_rejected` is not incremented.
- **Reject-then-Accept**: *not* blocked. A signer's rejection is recorded (weight added to `total_weight_rejected`, slot added to `responded_signers`), but a subsequent `Accepted` for the same block from the same signer is only checked against `gathered_signatures` (not yet populated for this signer), so it is credited to `total_weight_approved` as well.

The net effect is that a single signer's weight can appear in **both** `total_weight_approved` and `total_weight_rejected` simultaneously for the same block, breaking the invariant that `total_weight_approved + total_weight_rejected <= total_weight` and that a signer's stance is counted on only one side of the vote. This is functionally the same bug class as the referenced external report: an actor is able to have the same underlying weight recognized twice under two different accounting buckets by changing state (there: unstake/restake to move a locked position between identities; here: sending a later, contradictory message that isn't checked against the earlier one).

`signer_coordinator.rs` consumes exactly these two counters to decide whether to declare a block globally rejected or accepted: [4](#0-3) 
Because the rejection branch is evaluated first, a signer's earlier (and possibly stale/reconsidered) rejection weight remains baked into `total_weight_rejected` even after that same signer later signals acceptance, corrupting the coordinator's view of how much distinct weight is actually opposed to the block.

### Impact Explanation
This does not let an attacker sign an invalid block, nor forge someone else's signature — the exploited signer uses only their own key and their own genuine (if contradictory) messages. However, it breaks the accounting equality the whole tally mechanism depends on: a rejection is effectively "recounted" alongside an acceptance instead of being superseded by it, inflating `total_weight_rejected` with weight that no longer represents current opposition. In borderline scenarios (weight distributions near the 30%/70% split), this can materially skew whether the coordinator declares `SignersRejected` versus proceeding to gather enough approvals, and it corrupts the per-txid `failed_txids` weight bookkeping used to decide which transactions get temporarily/permanently excluded from future proposals (also gated on `blocking_minority`). This falls under the "a rejection recounted as an accept"/miscounted-response impact category from the rules, at a High-to-Critical severity depending on how close the reward-set weight distribution is to the threshold.

### Likelihood Explanation
Reachable by a single one-slot signer (the reported class of actor): simply send a `Rejected` `BlockResponse` for a proposal, then later send an `Accepted` `BlockResponse` for the exact same block (same `signer_signature_hash`) from the same signer key. No majority, no other signer's key, and no node/consensus bug is required — only ordinary StackerDB message posting, which any registered signer can already do. A signer might do this either through legitimate reconsideration (many state-machine paths in `stacks-signer/src/v0/signer.rs` allow a signer to change its mind about a block, e.g. `handle_block_pre_commit`'s conflict-staleness logic) or deliberately.

### Recommendation
Make the acceptance branch symmetric with the rejection branch: before crediting `total_weight_approved`, check `!block.responded_signers.contains(&slot_id)` (or equivalently check `gathered_signatures` together with a check that the slot isn't already recorded in `responded_signers` due to a prior rejection), matching the same-slot dedup logic used for rejections. Alternatively, track each signer's latest response state as a single enum keyed by slot id (`Accepted`/`Rejected`), and recompute `total_weight_approved`/`total_weight_rejected` from that single source of truth rather than two independently-guarded increment paths, guaranteeing the invariant `total_weight_approved + total_weight_rejected <= total_weight` always holds and only a signer's most recent response counts.

### Proof of Concept
Not independently executable without live StackerDB infrastructure, but the code trace is:
1. Signer `S` (slot `k`, weight `w`) sends `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for block `B`. This matches `stackerdb_listener.rs:486` and enters `block.responded_signers.insert(slot_id)` → `true`, so `total_weight_rejected += w` at [5](#0-4) .
2. The same signer `S` later sends `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same block `B` with a valid signature. This matches `stackerdb_listener.rs:386`, and since `block.gathered_signatures` does not yet contain `slot_id`, `total_weight_approved += w` executes at [6](#0-5) .
3. Result: `BlockStatus.total_weight_approved` and `BlockStatus.total_weight_rejected` both now include `w` for the same signer `S` on the same block, so `total_weight_approved + total_weight_rejected` for block `B` exceeds what a correct 1-vote-per-signer tally should allow, corrupting the threshold math consumed in `signer_coordinator.rs` at [4](#0-3) .
