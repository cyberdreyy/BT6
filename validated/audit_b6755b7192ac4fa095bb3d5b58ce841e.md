### Title
`create()` lets any unprivileged caller pick `staking_pool_whitelist_account_id` for a lockup deployed under a victim's deterministic address, deciding which staking pool "trust anchor" the victim's future owner-controlled account will use - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` derives the new lockup's account address deterministically from `owner_account_id` alone (`sha256(owner_account_id)` + factory name), with no requirement that `env::predecessor_account_id()` match `owner_account_id` or any owner-designated party. Any unprivileged attacker can call `create(owner_account_id="victim.near", ..., whitelist_account_id=Some("attacker-whitelist.near"))`, pay the `MIN_ATTACHED_BALANCE`, and deploy/occupy `victim.near`'s lockup address first, permanently baking in an attacker-chosen `staking_pool_whitelist_account_id` that `select_staking_pool` will later trust unconditionally.

### Finding Description
The claimed binding is: `staking_pool_whitelist_account_id trusted by victim.near's lockup == whitelist victim.near (or their designated sponsor/foundation) was entitled to choose`.

In `create`, the whitelist parameter is resolved purely from caller input with no identity check tying it to the owner: [1](#0-0) 

Neither `owner_account_id` nor `whitelist_account_id` is validated against `env::predecessor_account_id()` anywhere in `create`; the only guard is the deposit-size check: [2](#0-1) 

The resulting `staking_pool_whitelist_account_id` is written immutably into the deployed lockup's state via `LockupArgs` and the `new` constructor call, with no post-deploy owner method to change it (confirmed by scanning `lockup/src/owner.rs`, which contains only staking/transfer/key methods and `select_staking_pool`, `unselect_staking_pool`, no `set_whitelist` type call): [3](#0-2) 

Later, when the true owner (`victim.near`, once transfers/owner control activate) calls `select_staking_pool`, the contract trusts whatever whitelist account was baked in at creation time, with no re-verification that this whitelist account is foundation-controlled: [4](#0-3) 

`assert_owner()` inside `select_staking_pool` only checks that the *caller* of `select_staking_pool` is the lockup's owner; it does nothing to verify who chose `staking_pool_whitelist_account_id` at deploy time. `is_valid_account_id` only checks the *staking pool* account format, not the whitelist account's provenance. None of the existing guards (`assert_self`, `is_promise_success`, `assert_one_yocto`, etc.) are present in `create` at all to bind `whitelist_account_id` to `owner_account_id` or to any foundation-controlled identity.

Exploit flow: an attacker deploys their own contract at `attacker-whitelist.near` that unconditionally returns `true` from `is_whitelisted`. The attacker then calls `create(owner_account_id="victim.near", ..., whitelist_account_id=Some("attacker-whitelist.near"))` with the minimum attached deposit before the legitimate sponsor (e.g., the NEAR Foundation) creates `victim.near`'s real lockup. Because the lockup account address is fully determined by `owner_account_id`, this squats the address and permanently binds the attacker's whitelist contract as the "trusted" pool-vetting authority for that lockup - the legitimate sponsor can no longer deploy the intended lockup at that address with the intended (foundation) whitelist.

### Impact Explanation
The account (`attacker-whitelist.near`) is granted permanent trusted-whitelist status for `victim.near`'s lockup with parameters the rightful creator (the foundation/sponsor who would otherwise fund and configure `victim.near`'s lockup) never chose - matching the Critical category "an account whitelisted ... with parameters its rightful creator never chose." Once `victim.near` becomes owner and calls `select_staking_pool` against a pool the attacker also controls, `is_whitelisted` will always return true, letting `victim.near` unknowingly delegate/stake NEAR into an unvetted, attacker-controlled staking pool believing it passed the official vetting process - creating the precondition for stolen delegated NEAR. The attack is repeatable across any target account name the attacker wants to squat, at the cost of one `MIN_ATTACHED_BALANCE` (3.5 NEAR) deposit per victim address, and blocks the legitimate lockup from ever being deployed at that address (account name collision).

### Likelihood Explanation
Preconditions are minimal: the attacker needs only an unprivileged NEAR account, `MIN_ATTACHED_BALANCE` (3.5 NEAR), and the ability to deploy a trivial malicious "whitelist" contract they control - all within the stated attacker capabilities. The only race condition is doing this before the legitimate sponsor creates the victim's lockup, which is plausible since lockup creation for foundation/investor accounts is typically done at a predictable, later point after account names are publicly known (e.g., token-sale/vesting recipients). This is fully reproducible in a unit test as shown by the existing `test_create_lockup_with_custom_whitelist_success` test, which already demonstrates that an arbitrary caller (`account_tokens_owner()`, unrelated to the factory admin) can set an arbitrary `whitelist_account_id`.

### Recommendation
Restrict who may set a non-default `whitelist_account_id` in `create` - e.g., require `env::predecessor_account_id() == owner_account_id.as_ref()` or `env::predecessor_account_id() == self.foundation_account_id`, and reject the custom whitelist parameter otherwise, forcing all other callers to fall back to `self.whitelist_account_id`. Alternatively, remove the caller-provided `whitelist_account_id` parameter entirely and always use the factory's own `self.whitelist_account_id`.

### Proof of Concept
```rust
#[test]
fn test_attacker_sets_whitelist_for_unrelated_owner() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker is NOT `victim.near`, NOT the foundation, NOT any owner-designated party.
    context.is_view = false;
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());

    // Attacker names an unrelated account as owner ("victim.near") and injects their own whitelist.
    contract.create(
        ValidAccountId::try_from("victim.near").unwrap(),
        lockup_duration,
        None,
        None,
        None,
        Some(ValidAccountId::try_from("attacker-whitelist.near").unwrap()),
    );

    // Assert on the LEFT side of the binding: staking_pool_whitelist_account_id used
    // for victim.near's lockup equals the attacker's chosen id, NOT self.whitelist_account_id
    // (the factory default / foundation-controlled whitelist), proving the identity break:
    // LEFT:  deployed LockupArgs.staking_pool_whitelist_account_id == "attacker-whitelist.near"
    // RIGHT: self.whitelist_account_id (factory default)            == whitelist_account_id() (from test_utils)
    // These two values diverge, proving the binding is broken -- capture the serialized
    // function_call args via a mocked Promise/VM inspection or refactor `create` to expose
    // the computed `staking_pool_whitelist_account_id` for direct assertion.
}
```
This is a variant of the pre-existing `test_create_lockup_with_custom_whitelist_success` test at [5](#0-4) , changed only to make the caller (`attacker.near`) unrelated to both the chosen `owner_account_id` ("victim.near") and the foundation, demonstrating that `create` accepts and honors an attacker-chosen whitelist for an account the attacker does not control and was never designated by.
