### Title
EI credentials bypass "EIs not allowed" restriction and can trigger arbitrary job runs via `RunJobV2` - (File: core/web/pipeline_runs_controller.go)

### Summary
`AuthenticateExternalInitiator` sets the same `SessionUserKey` context value that regular session/token-authenticated users get (with `Role: clsessions.UserRoleRun`), so `PipelineRunsController.Create`'s `isUser := auth.GetAuthenticatedUser(c)` check — whose comment explicitly states "only users are allowed to run jobs using int IDs - EIs not allowed" — actually evaluates true for EI-authenticated requests. This lets an external-initiator credential holder POST an arbitrary integer job ID to `/v2/jobs/:ID/runs` and have `prc.App.RunJobV2` execute it, with no verification that the job is bound to that initiator.

### Finding Description
`auth.AuthenticateExternalInitiator` (core/web/auth/auth.go:119-151) authenticates the EI token/secret pair and then does: [1](#0-0) 
which stores a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` under the same `SessionUserKey` used by `AuthenticateBySession`/`AuthenticateByToken`.

`PipelineRunsController.Create` (core/web/pipeline_runs_controller.go:109-125) then does: [2](#0-1) 
The comment states EIs should not be allowed to trigger runs via integer job IDs, but `auth.GetAuthenticatedUser(c)` only checks presence of `SessionUserKey`, which is set identically regardless of whether the caller authenticated via session/token or as an EI. Since `isUser` becomes `true` for an EI-authenticated request, the integer-ID branch executes and calls `prc.App.RunJobV2(ctx, jobID, nil)` for whatever `jobID` is supplied — with no check that the ID corresponds to a job tied to the authenticated `ExternalInitiator` (there is no lookup of `GetAuthenticatedExternalInitiator(c)` or any initiator-to-job binding check in this code path at all).

This confirms the flaw: the EI-vs-user distinction the comment assumes does not actually exist in the authenticated-context representation, so the "isUser" gate is not an effective EI exclusion.

### Impact Explanation
An EI-credential holder — a low-privilege, narrowly-scoped credential intended only to trigger its own bound webhook job — can trigger `RunJobV2` for **any** job ID on the node, not just the job(s) associated with its own initiator binding. This is unauthorized cross-tenant job execution: `RunJobV2` executes the job's pipeline (including tasks like ETH transactions, bridge calls, VRF request simulation, etc., depending on job type), so an attacker holding only an EI credential could trigger execution of jobs belonging to other users/services, corresponding to "unauthorized job run" impact.

However, this is meaningfully mitigated by `ChainlinkApplication.RunJobV2` itself: [3](#0-2) 
which unconditionally rejects the call with `build.IsProd()` returning true (`"manual job runs not supported on secure builds"`). Since production/secure builds set this flag, the practical exploitability of the authorization bypass is limited to non-production (dev/test) builds where manual runs are permitted at all. The authorization logic itself is still broken independent of this build gate, and would become directly exploitable if the `build.IsProd()` guard were ever removed, weakened, or bypassed in a future change, or on any build where it evaluates false.

### Likelihood Explanation
- Precondition: possession of any valid EI access-key/secret pair (`X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers) — a low, non-admin credential class.
- No initiator-job relationship check exists at all in the reachable code path, so once an attacker has any EI credential, they can attempt this against any integer job ID.
- The `build.IsProd()` check in `RunJobV2` fully blocks the resulting execution on secure/production builds, which substantially reduces real-world likelihood on hardened deployments, but the vulnerable authorization logic exists in code shipped and reachable regardless of build type.

### Recommendation
In `PipelineRunsController.Create`, do not rely solely on `auth.GetAuthenticatedUser` to gate the integer-ID branch. Explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and reject (or route separately) when an EI principal is present, matching the stated intent "EIs not allowed" for integer job IDs. Alternatively, give EI-derived sessions a distinct marker/role (not indistinguishable from a real logged-in run-role user) so `isUser` correctly reflects "authenticated as a human/API-token user" versus "authenticated as an external initiator."

### Proof of Concept
Handler-level integration test plan (Go, using `cltest` helpers similar to `TestRunner_WebhookJobRemoved`):
1. Start a `TestApplication` with `JobPipeline.ExternalInitiatorsEnabled = true` and (for the PoC to actually observe `RunJobV2` executing) run in a **non-prod** build context (or stub `build.IsProd()` via test build tag) — otherwise assert on the intermediate authorization decision instead of final execution.
2. Create `ExternalInitiator` EI1 via `cltest.CreateExternalInitiatorViaWeb`, capturing its `AccessKey`/`Secret`.
3. Create an unrelated job `jobUnrelated` (e.g., a simple `direct-request` or OCR job) via `cltest.CreateJobViaWeb`, with no EI attached.
4. Send `POST /v2/jobs/{jobUnrelated.ID}/runs` with headers `X-Chainlink-EA-AccessKey: EI1.AccessKey`, `X-Chainlink-EA-Secret: EI1.Secret` (using `cltest.UnauthenticatedPost` like the existing `TestRunner_WebhookJobRemoved`).
5. Assert: unlike the "EIs not allowed" comment implies, the request reaches `RunJobV2` for `jobUnrelated.ID` — either assert a `pipeline_runs` row was created for that job ID (`cltest.AssertCountIncreased` on `pipeline_runs` filtered by that job), or (in prod-simulated builds) assert the specific error returned is the `build.IsProd()` message rather than an authorization/"bad job ID" error, proving the authorization check itself did not block the request — only the build gate did.
6. Contrast with expected correct behavior: the request should be rejected at the authorization layer (e.g., 401/403 "EIs not allowed to run jobs by integer ID") regardless of build type, which the current code does not do.
