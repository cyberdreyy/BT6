### Title
Stale per-epoch instant-withdraw accounting is never cleared on claim, inflating default recovery basis and trapping recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` but leaves `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` populated. If the borrower defaults later in the same epoch after only partially funding the instant-withdraw queue, `finalizeDefaultRecovery` reuses the stale per-epoch amounts: `defaultPendingClaimBasis` double-counts already-paid claims and `_defaultPrefundedInstantReserve` counts already-transferred underlyings as reserve. The recovery price is inflated beyond what the real balance supports, so early claimants are overpaid and later claimants' claims revert on reserve underflow.

### Finding Description
In `claimInstantWithdrawRequest` the strategy burns the receipt, zeroes `instantWithdrawsRequests[_user]`, and transfers funded underlyings, but never clears the per-epoch ledgers:

- `contracts/strategies/idle/IdleCreditVault.sol:380-393` — sets `instantWithdrawsRequests[_user] = 0` only; `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` remain.
- `contracts/strategies/idle/IdleCreditVault.sol:644-649` — `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0`, including amounts already claimed.
- `contracts/strategies/idle/IdleCreditVault.sol:716-723` — `_defaultPrefundedInstantReserve()` treats `instantBasis - pendingInstant` as underlyings already held by the strategy, even though part of `instantBasis` was already paid out and no longer sits in the contract.

This mirrors the libcurl bug: the "clear" operation (claiming) fails to clear the internal per-epoch state, and the stale value is erroneously reused in a subsequent security-critical computation (default recovery finalization).

### Impact Explanation
Sequence, all by unprivileged users plus honest manager calls:

1. Epoch N stops with an APR drop, enabling instant withdrawals. Attacker requests an instant withdraw for `X`.
2. `startEpoch` for N+1; `getInstantWithdrawFunds` collects only part of `pendingInstantWithdraws` from the borrower (partial funding leaves `pendingInstantWithdraws > 0` and sets `allowInstantWithdraw`).
3. Attacker calls `claimInstantWithdrawRequest`, receives `X` underlyings. Aggregate cleared; `instantWithdrawsRequestsByEpoch[attacker][N+1] = X` and `instantWithdrawClaimsByEpoch[N+1]` still include `X`.
4. Borrower fails to repay the remainder before `instantWithdrawDeadline`; default is declared and `finalizeDefaultRecovery` runs.

At finalization, `instantBasis` (line 719) still includes the paid `X`, so `prefundedReserve = X - pendingInstant` is overstated by exactly the claimed amount, inflating `reserveAmount`/`recoveryPrice` (line 686-688) with phantom tokens, and `defaultPendingClaimBasis` adds `X` again to `totalBasis`. When the attacker (who also holds a defaulted normal withdraw receipt, e.g., from a same-epoch `requestWithdraw`) calls `claimWithdrawRequest` first, `_transferDefaultRecovery` pays them at the inflated price. Subsequent claimants' `_transferDefaultRecovery` (line 912-916) reverts on `defaultRecoveryReserve -= _amount` underflow or insufficient balance, permanently freezing their recovery share. Quantified loss: up to the full stale `X` (the attacker's instant-withdraw amount), stolen from / frozen out of other recovery claimants. The stranded reserve is unrecoverable since no sweep exists.

### Likelihood Explanation
Requires only a partially-funded instant-withdraw epoch followed by a same-epoch default — a path explicitly supported (`pendingInstantWithdraws` remainder, `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` at line 696). The attacker needs no privilege: request instant withdraw, claim when funded, hold any defaulted-epoch receipt, claim first. The guard `instantWithdrawsRequests[_user] -= claimBasis` in `_claimDefaultedInstantWithdrawRequest` (line 848) protects the already-claimed user from double-claiming, but does nothing to stop the basis/reserve inflation that harms everyone else. No existing skim, flag, or epoch gate covers this.

### Recommendation
In `claimInstantWithdrawRequest`, also clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount, so already-paid claims are excluded from `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`. Add a regression test: partial instant funding → user claims → same-epoch default → assert recovery price ignores the claimed amount.

```solidity
function testStaleInstantBasisInflatesDefaultRecovery() external {
    // enable instant withdrawals, deposit AA+BB
    _setFeeParams(TL_MULTISIG, 10000, FULL_ALLOC, cdoEpoch.managementFee());
    cdoEpoch.setInstantWithdrawParams(3 days, 1e18, false);
    uint256 mintedAA = idleCDO.depositAA(10000 * ONE_SCALE);
    idleCDO.depositBB(10000 * ONE_SCALE);

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // attacker requests instant withdraw X and a normal withdraw in the same epoch
    uint256 X = mintedAA / 3;
    cdoEpoch.requestWithdraw(X, address(AAtranche));          // routes to instant bucket
    uint256 normalReq = cdoEpoch.requestWithdraw(X, address(AAtranche)); // normal

    _startEpochAndCheckPrices(1);
    // borrower funds only the attacker's instant portion, not the rest
    // (drive partial collectInstantWithdrawFunds so pendingInstantWithdraws > 0)
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    _getInstantFunds();                                       // partial funding path
    cdoEpoch.claimInstantWithdrawRequest();                   // attacker paid X; by-epoch entries stay stale

    // borrower defaults in the same epoch; manager finalizes recovery
    _checkDefault();
    // finalizeDefaultRecovery via IdleCDOEpochVariant with recoveredAmount
    // assert: IdleCreditVault.defaultPendingClaimBasis() still counts X
    // assert: attacker claimWithdrawRequest() succeeds at inflated price
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    // attacker payout > normalReq * fairRecoveryPrice
    // a second claimant's _transferDefaultRecovery reverts on reserve underflow
}
```

Key assertions: after `claimInstantWithdrawRequest`, `strategy.instantWithdrawsRequestsByEpoch(attacker, epoch)` is still `X` (the stale value); `defaultPendingClaimBasis()` after finalization exceeds the true unpaid basis by `X`; final claimants revert with reserve underflow while the attacker is overpaid by up to `X`.
