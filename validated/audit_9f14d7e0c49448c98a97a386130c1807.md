### Title
Cache key metacharacters ($()/backticks) survive into `CACHE_METADATA` and are shell-expanded via an unquoted heredoc in `DotEnvVariables` — command injection in the cache-stage script - ([File: shells/bash.go], [File: shells/abstract.go], [File: cache/cachekey/cachekey.go], [File: helpers/shell_escape.go])

### Summary
`cachekey.Sanitize` only normalizes path separators/traversal/whitespace and never strips shell metacharacters such as `$()`, backticks, or `!`. The sanitized (or, under `FF_HASH_CACHE_KEYS`, entirely unsanitized) key is embedded as `"cachekey"` in the `CACHE_METADATA` JSON built in `addCacheUploadCommand` [1](#0-0) , and this env map is serialized to disk by `BashWriter.DotEnvVariables` using an **unquoted** heredoc delimiter (`cat << EOF`), which the POSIX shell will still expand for `$(...)`/backtick command substitution before the redirected `cat` even executes [2](#0-1) . `helpers.DotEnvEscape`, the only escaping applied to values, only escapes backslash, double-quote, `\n`, and `\r` — it explicitly leaves `$` untouched (confirmed by the "Value with dollar signs" test case) [3](#0-2) [4](#0-3) .

### Finding Description
The exploitable path is:

1. Attacker (pipeline author) sets `cache: key:` (or `CACHE_FALLBACK_KEY`) to a value containing `$(...)` or backticks, e.g. `key: "pwn$(touch /tmp/pwned)"`.
2. `archiveCache`/`cacheExtractor` call `newCacheConfig`, which expands the key via `build.GetAllVariables().ExpandValue(userKey)` and then sanitizes it with `cachekey.Sanitize` [5](#0-4) . `Sanitize` only rewrites path separators/traversal segments and trims trailing whitespace — it does not touch `$`, `(`, `)`, or `` ` `` (verified against its full test matrix) [6](#0-5) . Under `FF_HASH_CACHE_KEYS`, the sanitizer is even a no-op identity function, so the raw key is used verbatim as `HumanKey` [7](#0-6) .
3. `addCacheUploadCommand` places this `HumanKey` into `metadata["cachekey"]`, JSON-marshals it into `env["CACHE_METADATA"]` [1](#0-0) , merges in any adapter-provided credential env vars (e.g. S3 `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` from `s3CredentialsAdapter.GetCredentials`) [8](#0-7) , and calls `b.writeCacheExports(w, env)` → `w.DotEnvVariables(...)` [9](#0-8) [10](#0-9) .
4. `BashWriter.DotEnvVariables` emits `cat << EOF > <file>\n<escaped values>\nEOF\n` [2](#0-1) . Because the heredoc delimiter `EOF` is unquoted, bash performs parameter/command substitution on the heredoc body before writing it to the file. Since `$` and backticks are not escaped by `DotEnvEscape`, any `$(...)`/backtick sequence surviving from the cache key is executed by the shell that is running the generated cache-archive/extract script — not merely written as inert text.
5. Existing protections (`Sanitize`'s path-traversal handling, `DotEnvEscape`'s quote/backslash/newline escaping, `isValidDotEnvKey` for keys) do not address shell metacharacters in values, and none of them quote the heredoc delimiter.

### Impact Explanation
For split-container executors (Docker, Docker-autoscaler, Kubernetes), the cache-archive/cache-extract stage script runs in the **helper container/context** — separate from the build container — and is the stage where cache upload/download credentials (e.g., S3 keys returned by `GetCredentials`) and other CI job variables (exported earlier by `writeExports`, called from `cacheArchiver`) are present in the process environment. Arbitrary command execution injected at this stage via the cache key lets the attacker execute code in that helper context (before the actual `cache-archiver`/`cache-extractor` binary invocation), potentially reading/exfiltrating job variables/secrets available to that stage, tampering with cache upload/download logic, or writing to shared volumes with the helper's privileges — a stage the attacker does not directly script via `script:`. Even for single-container/shell executors, this at minimum causes early, non-obvious command execution embedded in "trusted" runner-generated script sections outside the user's own `script:` block, which can defeat expectations about when/where a job's commands run and can corrupt or bypass later `IfCmdWithOutput` checks.

### Likelihood Explanation
Fully reachable by an unprivileged pipeline author: cache `key`/`CACHE_FALLBACK_KEY` values are standard, commonly-used `.gitlab-ci.yml`/CI-variable-controlled fields, expanded via `ExpandValue` before any sanitization. No admin action or special runner configuration is required beyond the runner supporting cache upload/extraction (S3/GoCloud), which is a default runner feature. The bug is deterministic and reproducible on every job that sets such a key.

### Recommendation
- Escape `$` and backtick characters in `helpers.DotEnvEscape` (in addition to backslash/quote/newline/CR), and/or
- Change `BashWriter.DotEnvVariables` to use a quoted heredoc delimiter (`cat << 'EOF' > file`) so the shell does not perform parameter/command substitution on heredoc content, and
- Consider rejecting/escaping shell metacharacters in `cachekey.Sanitize` regardless of `FF_HASH_CACHE_KEYS`, since `HumanKey` is used in generated shell content even when hashing is enabled.

### Proof of Concept
Go unit test (add to `shells/bash_test.go`) asserting the heredoc is not exploitable:

```go
func Test_BashWriter_DotEnvVariables_NoCommandSubstitution(t *testing.T) {
    w := BashWriter{TemporaryPath: "foo/bar"}
    w.DotEnvVariables("test", map[string]string{
        "CACHE_METADATA": `{"cachekey":"pwn$(touch /tmp/pwned)"}`,
    })
    script := w.String()
    // The heredoc delimiter must be quoted to prevent shell expansion of $()/`` inside it.
    assert.Contains(t, script, "cat << 'EOF' >")
    assert.NotContains(t, script, "cat << EOF >")
}
```

Integration-style PoC job:
```yaml
job:
  script: [echo hi]
  cache:
    key: "pwn$(touch /tmp/pwned)"
    paths: [build/]
```
Run this job on a shell/docker executor and check the runner-generated cache-archive script/log for evidence that `touch /tmp/pwned` executed during the "Creating cache" stage (e.g., presence of `/tmp/pwned` in the helper/build filesystem after job completion), asserting command execution occurred outside the user's `script:` section.

```go
func DotEnvEscape(variables map[string]string) string {
	var sb strings.Builder

	// Sort variables to get deterministic output
	keys := make([]string, 0, len(variables))
	for key := range variables {
		keys = append(keys, key)
	}
	sort.Strings(keys)

	for _, key := range keys {
		if !isValidDotEnvKey(key) {
			// Skip invalid keys
			continue
		}

		value := variables[key]
		fmt.Fprintf(&sb, "%s=\"%s\"\n", key, escapeDotEnvValue(value))
	}

	return sb.String()
}
```

```go
func Sanitize(cacheKey string) (string, error) {
	if cacheKey == "" {
		return "", nil
	}

	// Decode percent-encoded chars and normalise separators, then
	// resolve traversals against a virtual root so ".." can never
	// escape beyond the root.
	cleaned := path.Clean("/" + normaliser.Replace(cacheKey))

	// Strip the leading "/" we added, split into segments, then walk
	// backwards trimming trailing whitespace from the rightmost
	// segments—dropping any that become empty.
	parts := strings.Split(cleaned[1:], "/")
	n := len(parts)
	for n > 0 {
		parts[n-1] = strings.TrimRightFunc(parts[n-1], unicode.IsSpace)
		if parts[n-1] != "" {
			break
		}
		n--
	}

	key := strings.Join(parts[:n], "/")

	if key == "" {
		return "", fmt.Errorf("cache key %q could not be sanitized", cacheKey)
	}

	return key, nil
}
```
