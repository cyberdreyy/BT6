### Title
Missing reciprocal programmable-borrower attachment can freeze epoch settlement - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`IdleCDOEpochVariant.setIsProgrammableBorrower` enables programmable-borrower mode without checking that the strategy’s configured borrower is a `ProgrammableBorrower` bound to the same CDO. If the flag is enabled while `IdleCreditVault.borrower` is still an EOA or an incompatible contract, `stopEpoch` unconditionally invokes `onStopEpoch` on that address and reverts. Because the flag cannot be disabled while the epoch is running, normal settlement remains blocked until privileged intervention changes the strategy borrower or upgrades the system.

### Finding Description
`setIsProgrammableBorrower` records only a boolean and does not validate the required counterpart relationship. [1](#0-0) 

A valid `ProgrammableBorrower` is not merely an address that receives funds. It must implement the CDO hooks and reject calls unless `msg.sender == idleCDO`. [2](#0-1) [3](#0-2) 

The factory correctly establishes the two-way relationship by deploying a `ProgrammableBorrower` with `idleCDO = address(cv)`, assigning it as the strategy borrower, and then enabling `isProgrammableBorrower`. [4](#0-3) 

However, the CDO does not preserve that invariant when the flag is changed directly. Once `isProgrammableBorrower` is true, `stopEpoch` calls `IProgrammableBorrower(_borrower()).onStopEpoch(...)` before it attempts to pull repayment. [5](#0-4) 

For an EOA, the call succeeds but returns no ABI-encoded `bool`, causing decoding to revert. For an incompatible contract, the hook call itself reverts. Since `setIsProgrammableBorrower(false)` is prohibited while `isEpochRunning`, the ordinary flag cannot be used to recover after the epoch starts. [6](#0-5) 

### Impact Explanation
An unprivileged lender can deposit while the pool is in buffer phase. When the honest manager later starts the epoch, lender underlyings are transferred to the configured borrower. [7](#0-6) 

After `epochEndDate`, every ordinary `stopEpoch` or `stopEpochWithDuration` call reaches the mandatory `onStopEpoch` hook and reverts. The vault remains paused, `isEpochRunning` remains true, and withdrawal requests remain disabled because those state updates occur only after successful settlement. [8](#0-7) 

The temporary freezing affects the full active strategy-token NAV plus any pending withdrawal obligations. If no compatible borrower contract was already deployed and funded, the owner must either install a replacement borrower capable of completing or intentionally failing the hook, or perform an implementation-level recovery. Neither action is exposed through `setIsProgrammableBorrower`, so the missing attachment causes an operational settlement freeze rather than merely a rejected configuration transaction.

### Likelihood Explanation
This requires an honest owner or deployment flow to enable `isProgrammableBorrower` without also setting `IdleCreditVault.borrower` to a `ProgrammableBorrower` whose `idleCDO` is this CDO. The factory performs the pairing correctly, so the issue primarily affects manual deployment, migration, borrower replacement, or recovery workflows that call the CDO setter directly. Existing checks validate only timing and mode requirements; they do not verify the reciprocal borrower attachment.

### Recommendation
In `setIsProgrammableBorrower(true)`, require:

```solidity
address borrower = IdleCreditVault(strategy).borrower();
require(borrower != address(0), "invalid borrower");
require(IProgrammableBorrower(borrower).idleCDO() == address(this), "borrower not attached");
require(isInterestMinted, "programmable requires minted interest");
```

The `IProgrammableBorrower` interface should expose `idleCDO()`. Ideally, deployment should use a single atomic wiring function so the strategy borrower, programmable borrower’s CDO reference, minted-interest mode, and CDO flag cannot enter an inconsistent state. `ProgrammableBorrower.initialize` could also verify that the supplied CDO’s strategy borrower is the initializing proxy once the proxy address is available through a two-step registration/finalization pattern.

### Proof of Concept
The following Foundry test can be added to the existing programmable-borrower fixture. It assumes the fixture already exposes `cdoEpoch`, `strategy`, `AAtranche`, `underlying`, `manager`, `owner`, `defaultUnderlying`, `ONE_SCALE`, and the deposit helper used by the suite.

```solidity
function testProgrammableFlagWithoutAttachedBorrowerFreezesStop() external {
    address lender = makeAddr("lender");
    address plainBorrower = makeAddr("plainBorrower");

    // Strategy borrower is a plain EOA, not a ProgrammableBorrower.
    vm.prank(owner);
    strategy.setBorrower(plainBorrower);

    // Missing reciprocal-attachment check: this succeeds anyway.
    vm.prank(owner);
    cdoEpoch.setIsProgrammableBorrower(true);

    // Required mode is enabled, so startEpoch is accepted.
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    _depositWithUser(lender, 100_000 * ONE_SCALE, true);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    assertTrue(cdoEpoch.isEpochRunning());
    assertEq(
        IERC20Detailed(defaultUnderlying).balanceOf(plainBorrower),
        100_000 * ONE_SCALE
    );

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // EOA returns no ABI-encoded bool, so decoding onStopEpoch reverts.
    vm.prank(manager);
    vm.expectRevert();
    cdoEpoch.stopEpoch(0, 0);

    // The ordinary recovery switch is unavailable once the epoch is live.
    vm.prank(owner);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.setIsProgrammableBorrower(false);

    assertTrue(cdoEpoch.isEpochRunning());
    assertTrue(cdoEpoch.paused());
    assertEq(strategy.balanceOf(address(cdoEpoch)), 100_000 * ONE_SCALE);
}
```

The exact revert may be Solidity’s ABI-decoding failure rather than `NotAllowed`; the important behavior is that settlement cannot proceed through the normal `stopEpoch` path even though the borrower holds the entire `100_000 * ONE_SCALE` epoch principal.

  /// @notice Hook called by IdleCDOEpochVariant when a new epoch starts.
  /// It deposits all on-hand assets into the vault and starts accounting.
  /// @param _pendingWithdraws pending withdraw requests amount to reserve for epoch end.
  function onStartEpoch(uint256 _pendingWithdraws) external nonReentrant {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // Reserve the amount IdleCDO expects to pull back at stopEpoch before the real borrower can draw again.
    epochPendingWithdraws = _pendingWithdraws;
    uint256 currentVaultAssets = _currentVaultAssets();
    uint256 bufferStartAssets = bufferStartVaultAssets;
    // Carry vault PnL generated while the pool was in the buffer into the new active epoch so it
    // is eventually realized in tranche prices at the next stopEpoch.
    bufferedVaultDelta = int256(currentVaultAssets) - int256(bufferStartAssets);
    bufferStartVaultAssets = 0;
    // Snapshot total assets before re-depositing idle cash so the epoch principal baseline uses the
    // exact pre-deposit amount instead of a post-deposit share-conversion round-down.
    uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets;
    // Any idle balance left on the contract between epochs is parked immediately into the vault.
    _depositToVault(underlyingToken.balanceOf(address(this)), 0);
    // Reset the epoch accounting baseline from the exact pre-start total assets so the new epoch
    // does not treat the just-deposited idle balance as fresh vault profit or loss.
    epochStartVaultAssets = startAssets;
    epochDepositedToVault = 0;
    epochWithdrawnFromVault = 0;
    epochAccountingActive = true;
    emit EpochAccountingStarted(startAssets);
