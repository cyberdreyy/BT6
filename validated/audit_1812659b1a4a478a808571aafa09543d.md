### Title
Stale confirmations from removed multisig members still count toward the execution threshold, enabling requests to execute with fewer than the current required number of live-member confirmations - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in the multisig2 contract only strips confirmations from requests that were *created* by the member being removed. It never scans the `confirmations` map for other pending requests that the removed member had already confirmed. `confirm()` then counts confirmations purely by set size (`confirmations.len() as u32 + 1 >= self.num_confirmations`) without re-validating that every entry in the set still belongs to `self.members`. This lets a request execute counting a confirmation from an account/key that is no longer an authorized member at the moment of execution — a multisig request executed below the *actual* live-member threshold.

### Finding Description
The bug class mirrors the FIAT DAO `increaseUnlockTime` finding: a value that should be re-derived from the *current* state (the live member set at execution time) is instead trusted as a stale snapshot recorded earlier (the confirmation given while the confirmer was still a member), and that stale value is fed directly into a threshold/settlement computation.

Concretely:

- `confirm()` counts confirmations using `confirmations.len()` and compares against `self.num_confirmations`, without checking that each confirming identity is still in `self.members`: [1](#0-0) 

- `delete_member()` only removes confirmations/requests for requests where `r.member == member`, i.e. requests *added* by the removed member. It does not touch the `confirmations` HashSet of any other request that the removed member may have already confirmed: [2](#0-1) 

- `assert_valid_request()` (called by `confirm`) only validates that the *caller* is currently a member; it performs no validation of the members already recorded inside `confirmations`: [3](#0-2) 

Binding that should hold: `confirmations recorded and counted at execution == confirmations from accounts that are members of self.members at execution time`. Before the attack: a pending request R (created by member A, not by M) has confirmations `{M, ...}` where M is currently a live member, so the equality holds. After M is removed via a separate `DeleteMember` request (which cleans up only requests *created* by M, per lines 361-371), the equality breaks: `confirmations` for R still contains M, but M ∉ `self.members`. If a further legitimate confirmation is added, `confirmations.len() + 1 >= num_confirmations` can become true and `execute_request` fires, even though only `num_confirmations - 1` of the counted confirmers are still authorized members.

### Impact Explanation
This crosses the "a multisig request executed below threshold" critical-impact boundary explicitly called out in scope: the contract executes a `Transfer`, `AddKey`, `FunctionCall`, etc. with fewer than K currently-authorized confirmations, because a removed member's stale confirmation is still counted. Since multisig accounts hold and move NEAR (and can grant full access keys / deploy code), this can result in unauthorized transfer of funds or unauthorized privilege escalation (e.g. adding a full access key) with less real authorization than the configured K-of-N policy requires.

### Likelihood Explanation
No special privilege is needed beyond normal multisig operation: any member can create/confirm requests, and `DeleteMember` is a standard, expected multisig action (e.g. removing a departing employee or a suspected-compromised key). The scenario requires only ordinary usage patterns — a pending request confirmed by a member who is later removed via `DeleteMember` before the first request is fully confirmed/executed. No malicious deployment, no owner/foundation collusion, no redeploy is required; it's a straightforward sequencing of two contract-native operations.

### Recommendation
When executing `DeleteMember`, iterate over **all** pending requests (not just those originated by the removed member) and remove the removed member's entry from each request's `confirmations` set. Alternatively, re-validate membership of every entry in `confirmations` at the time `confirm()` computes whether the threshold has been reached, discarding/ignoring confirmations from accounts/keys no longer in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, M}` and `num_confirmations = 3`.
2. Member A calls `add_request` to create request R = `Transfer{...}` (receiver != M's own request; `r.member == A`).
3. Member M calls `confirm(R)` → `confirmations[R] = {M}` (1/3).
4. Member B calls `confirm(R)` → `confirmations[R] = {M, B}` (2/3), request still pending (below threshold, not yet executed).
5. Separately, members create and fully confirm a `DeleteMember{member: M}` request to remove M (e.g. because M's key is suspected compromised, or M left the org). `delete_member` runs: it filters `self.requests` for `r.member == M` — R was created by A, so it is *not* matched, and `confirmations[R]` remains `{M, B}` untouched. M is removed from `self.members`.
6. Member C calls `confirm(R)`. `confirmations.len() (2) + 1 >= num_confirmations (3)` → true. `execute_request` fires and R (the `Transfer`) executes, even though only B and C (2 live members) plus a ghost confirmation from removed member M were counted — i.e., the request executed with only 2 of 3 *currently authorized* confirmations, violating the K-of-N guarantee.     /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
