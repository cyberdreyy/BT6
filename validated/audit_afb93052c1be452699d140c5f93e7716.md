This is a confirmed, real bug in the state machine of `URLSanitizer.Write`. I traced the exact byte-level exploit path.

### Title
Chunked-write boundary bug in URLSanitizer causes x-amz-security-token value to bypass masking - (File: common/buildlogger/internal/urlsanitizer/urlsanitizer.go)

### Summary
`URLSanitizer.Write` resets its in-progress key match buffer (`s.match`) whenever `len(s.match) == cap(s.match)`, but this check fires unconditionally at the top of the loop before the terminator character (`=`) is inspected. Because `cap(s.match)` is sized to exactly `len("x-amz-security-token")+1` (the longest recognized key), a `?x-amz-security-token` prefix that is fully consumed byte-by-byte (via the `off == -1` fallback path) fills `s.match` to exactly `cap`, and the very next `Write()` call — which begins with `=<value>` — triggers the reset before the key can be matched against `tokenParamKeys`, so masking never engages and the credential value is written verbatim.

### Finding Description
`New()` sizes the match buffer as `max = len(longestToken) + 1` (the `+1` accounts for the leading `?`/`&`), giving `cap(s.match) == 21` for `"x-amz-security-token"` (20 chars). [1](#0-0) 

When a Write() call's remaining bytes contain no `=`, `?`, or `&`, the code appends bytes into `s.match` one at a time via the `off == -1` fallback rather than computing the whole key length in one shot: [2](#0-1) 

If the input is split such that a full `?x-amz-security-token` (delimiter + 20 chars = 21 bytes) is consumed entirely inside this fallback path across one or more `Write()` calls, `len(s.match)` reaches exactly `cap(s.match)` with no terminator yet seen. On the *next* `Write()` call (which starts with `=<secret>`), the top-of-loop check fires before the terminator can be checked: [3](#0-2) 

This resets `s.match` to empty, silently discarding the fully-matched `"x-amz-security-token"` key. The fast path then searches for `?`/`&` in `=<secret>...`, finds none, and passes the entire remainder (the `=` and the secret value) straight through to the underlying writer without ever reaching the `tokenParamKeys` lookup: [4](#0-3) [5](#0-4) 

This is the root cause: the cap-based reset conflates "an invalid oversized/garbage match that must be discarded" with "a valid, exactly-maximal-length key match that is legitimately awaiting its terminator." Only the single longest key (`x-amz-security-token`) can hit this exact boundary, since for every shorter key, `delimiter+key length < cap`, so this off-by-one only affects that one token — which is precisely the highest-value one for a real privilege-impersonation-style scoped impact (STS token). `URLSanitizer` is wired into every job trace stream in `Logger.wrap`, sitting between `tokensanitizer` and `masker`, so it processes real job stdout/stderr that an unprivileged job author fully controls. [6](#0-5) 

The existing fuzz harness in `build_logger_fuzz.go` does exercise `urlsanitizer.New` with randomly-sized chunked writes, but its assertions only check for leaked `phrases`/`secretSuffixes` (masker/tokensanitizer secrets) — it never asserts on `x-amz-security-token`/`private_token` values, so this gap is untested. [7](#0-6) 

### Impact Explanation
An unprivileged job author who can control job output that is echoed into the CI trace (e.g., `echo` of a URL containing `?x-amz-security-token=...` or `?private_token=...`) can, if the trace pipeline happens to split writes at the specific 21-byte boundary immediately after the key name (before the `=`), cause the sensitive value to appear in cleartext in the job trace/log instead of `[MASKED]`. Since `x-amz-security-token` is explicitly called out in the source as an "Amazon temporary security token from STS," a leaked value grants whoever reads the trace (any user with trace-read access, or anyone the job author shares the log with) the ability to impersonate that AWS identity outside the job's intended scope — matching the "leaked identity token enables privilege impersonation" scoped impact.

### Likelihood Explanation
Exploitability depends on the runner's I/O plumbing splitting `Write()` calls exactly at the 21-byte key boundary (key fully consumed via the one-byte-at-a-time fallback, with `=` starting a separate call). This is plausible but not fully attacker-controlled, since chunk boundaries are set by upstream buffering/transport (pipe reads, PTY behavior, network framing) rather than directly by job script timing. It is deterministically reproducible in a unit test by calling `Write()` directly with attacker-chosen chunk boundaries, which is a realistic proxy for cases where the underlying transport does fragment at inconvenient points (e.g., slow/partial reads, small buffer readers, or network-induced fragmentation of trace upload payloads).

### Recommendation
Fix the state machine so the cap-reset only discards genuinely invalid/overflowing matches, not a match that has just legitimately reached exactly the longest known key length while still awaiting its terminator. For example, track whether the current `s.match` length corresponds to a still-viable prefix of any `tokenParamKeys` entry (or simply allow one extra byte of slack in the buffer size, e.g. `max+1`, so a fully-matched maximal-length key does not equal `cap` until the terminator has been examined), and only reset when a genuinely oversized/non-matching key is detected (as is already done at line 122 via the `off+len(s.match) > cap` check for the single-call path).

### Proof of Concept
```go
func TestURLSanitizer_ChunkedMaxLengthKeyBypassesMask(t *testing.T) {
    buf := &bytes.Buffer{}
    s := urlsanitizer.New(internal.NewNopCloser(buf)) // io.WriteCloser wrapping buf

    // Split "?x-amz-security-token" so the full key (21 bytes incl. '?')
    // is consumed via the byte-by-byte fallback path with no terminator
    // visible in the same Write() call.
    _, err := s.Write([]byte("?x-amz-security-token"))
    require.NoError(t, err)

    // '=' and secret value arrive in a separate Write() call.
    _, err = s.Write([]byte("=AQoDYXdzEJr...SECRET_STS_TOKEN"))
    require.NoError(t, err)

    require.NoError(t, s.Close())

    // Expected: secret should be replaced with [MASKED].
    assert.NotContains(t, buf.String(), "SECRET_STS_TOKEN")
    assert.Contains(t, buf.String(), "[MASKED]")
}
```
Running this against current code fails the `NotContains` assertion, confirming the secret value leaks verbatim into the trace buffer.
