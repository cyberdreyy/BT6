### Title
Stale per-epoch instant-withdraw basis is never cleared on funded claims, inflating default recovery basis and phantom reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` removes a paid receipt from the aggregate `instantWithdrawsRequests` but leaves `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` untouched. If the borrower later defaults in the same `epochNumber`, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` re-count the already-paid basis — the exact analog of the kernel bug where a device was removed from the work list only after cancellation, letting a global requeue resurrect removed work.

### Finding Description
In `IdleCreditVault.requestInstantWithdraw`, a receipt is recorded in three places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

When the CDO funds the queue via `getInstantWithdrawFunds` → `collectInstantWithdrawFunds`, only `pendingInstantWithdraws` is decremented [2](#0-1) . When the user then claims through `claimInstantWithdrawRequest`, only the aggregate `instantWithdrawsRequests[_user]` is zeroed — the per-epoch entries persist [3](#0-2) . The per-epoch entries are only ever cleared inside `_claimDefaultedInstantWithdrawRequest` [4](#0-3) .

If the epoch stops with a borrower default while `epochNumber` is still the epoch of the stale receipt, and `pendingInstantWithdraws != 0` (e.g. a new instant request arrived after the funding), then:

- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]`, which still contains the already-claimed-and-paid basis, into `totalBasis` [5](#0-4) .
- `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstant`, treating the already-paid-out underlyings as reserve still held by the strategy [6](#0-5) .
- `finalizeDefaultRecovery` then sets `defaultRecoveryPrice = reserveAmount / totalBasis` and `defaultRecoveryReserve` to a value that includes phantom (already-transferred) funds [7](#0-6) .
- The stale user calling `claimInstantWithdrawRequest` post-finalization hits `instantWithdrawsRequests[_user] -= claimBasis` with a zeroed aggregate, causing an underflow revert; real claimants draw on a reserve that is short by the phantom amount, so the last claimants' `_transferDefaultRecovery` reverts on insufficient balance [8](#0-7) .

### Impact Explanation
Permanent freezing of unclaimed recovery yield plus dilution: the phantom basis is double-counted (once paid at par pre-default, once inside `totalBasis`), so `defaultRecoveryPrice` is mispriced and `defaultRecoveryReserve` overstates real holdings by the stale amount. Quantified loss equals the stale claimed basis `S`: reserve shortfall of `S` underlyings, meaning claimants totaling up to `S` of recovery can never withdraw (transactions revert), and every recovery claimant's price is distorted. Attacker is an ordinary tranche-token holder who simply claims a funded instant withdraw during the epoch that later defaults — no privileged action required.

### Likelihood Explanation
Requires a specific but realistic sequence within one epoch: instant withdraw funded after `instantWithdrawDeadline`, user claims, a further instant request leaves `pendingInstantWithdraws != 0`, then borrower defaults at `stopEpoch`. Instant withdraws are a supported non-programmable flow and defaults are an anticipated event in this design. The trigger needs no malicious privileged role — honest manager/borrower sequencing suffices.

### Recommendation
Mirror the kernel fix — remove the item from the per-epoch lists at claim time, not only at default claim time. In `claimInstantWithdrawRequest`, iterate/clear `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` for the funded claim (a per-user list of request epochs or a single `lastInstantWithdrawRequest` marker, analogous to `lastWithdrawRequest`, is needed). Alternatively, make `collectInstantWithdrawFunds` decrement `instantWithdrawClaimsByEpoch` at funding time and skip funded receipts in `defaultPendingClaimBasis`.

### Proof of Concept
Foundry fork PoC sketch (fork a live vault or use the existing test harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// Epoch N running, instantWithdrawDeadline passed
cdoEpoch.requestInstantWithdraw(100e6, tranche); // user A
vm.prank(manager);
cdoEpoch.getInstantWithdrawFunds();              // pendingInstantWithdraws -> 0
vm.prank(A);
cdoEpoch.claimInstantWithdrawRequest();          // A paid; per-epoch basis stays

cdoEpoch.requestInstantWithdraw(50e6, tranche);  // user B; pendingInstantWithdraws = 50
// borrower defaults at stopEpoch of the same epochNumber N
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(apr, interest, duration, 0); // defaulted
vm.prank(manager);
cdoEpoch.finalizeDefault(recovered, manager);
// instantWithdrawClaimsByEpoch[N] = 150 but only 50 is a real claim;
// prefundedReserve counts A's already-paid 100 as held reserve.
// B's claim via claimInstantWithdrawRequest draws on short reserve;
// subsequent recovery claims revert (permanent freezing) / price diluted.
```

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
