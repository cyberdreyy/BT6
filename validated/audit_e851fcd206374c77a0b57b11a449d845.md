### Title
Response cache key is scoped only by `WorkflowOwner`, not `WorkflowID`, allowing cross-workflow cache poisoning/confusion for cached HTTP action responses - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
The HTTP Handlers V2 gateway caches outbound HTTP action responses keyed by `req.Hash()`. Per the design docs, the cache is intended to provide "Workflow Isolation" so that "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage." [1](#0-0)  However, the actual `Hash()` implementation and the test suite explicitly confirm that `WorkflowID` is excluded from the hash while only `WorkflowOwner` (and method/URL/headers/body) participate: “having different workflowID results in same Hash” / “Hash should be the same regardless of WorkflowID.” [2](#0-1) 

### Finding Description
The `responseCache` struct comment itself states the cache key is derived from "method, URL, headers, body, workflowOwner" — `WorkflowID` is not part of it. [3](#0-2) 

`Fetch` and `Set` both key exclusively off `req.Hash()`: [4](#0-3) [5](#0-4) 

This is called from `makeOutgoingRequest` in the gateway handler, which builds the `OutboundHTTPRequest` directly from an untrusted node message (`req` fields including `WorkflowID`/`WorkflowOwner` are attacker/node-controlled input parsed via `json.Unmarshal`), and dispatches to `Fetch`/`Set` using only that hash for cache scoping. [6](#0-5) 

Because `WorkflowID` is dropped from the hash but `WorkflowOwner` remains, any two different workflows/executions belonging to the same owner that issue an HTTP action with the same method/URL/headers/body will collide on the same cache entry. This is the direct structural analog of the Band price feed bug: a cache/observation lookup silently falls back to and returns data associated with a different, unintended context (a stale/mismatched "observation") instead of reverting or fetching fresh, correctly-scoped data — resulting in a workflow receiving a cached HTTP response that was actually fetched for a different workflow execution under the same owner.

### Impact Explanation
A workflow (execution A) with `CacheSettings.Store = true` can populate the shared cache entry for a given method/URL/headers/body combination. A second, unrelated workflow (execution B) belonging to the same `WorkflowOwner` that issues a request with the same method/URL/headers/body and non-zero `CacheSettings.MaxAgeMs` will receive execution A's cached response instead of performing its own fetch. This breaks the documented workflow isolation guarantee and can cause cross-workflow response confusion: stale, wrong-context, or unexpected data (potentially containing information intended only for a different workflow's logic) is delivered to another workflow silently, with no error or revert — mirroring the reported class of bug where stale/wrong data is returned instead of failing loudly.

### Likelihood Explanation
Both `WorkflowID` and `WorkflowOwner` are attacker/node-supplied fields parsed from an unmarshaled JSON-RPC payload with no independent authentication tying them to the reporting node's true workflow context at the cache layer [7](#0-6) . Any owner running multiple workflows that call the same external endpoint with identical parameters (a common pattern for shared bridges/heartbeat data) will trigger the collision as soon as `CacheSettings.Store`/`MaxAgeMs` are used, since these are the default caching settings promoted in the V2 handler README. [8](#0-7) 

### Recommendation
Include `WorkflowID` (in addition to `WorkflowOwner`) in the `OutboundHTTPRequest.Hash()` computation so that cache entries are truly scoped per-workflow, matching the documented isolation guarantee, and add a regression test asserting that different `WorkflowID`s produce different hashes.

### Proof of Concept
1. Workflow A (owner `O`) issues an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", CacheSettings:{Store:true}}` with `WorkflowID = "wf-A"`, `WorkflowOwner = "O"`. The gateway fetches and caches the response under `req.Hash()`. [9](#0-8) 
2. Workflow B (owner `O`, `WorkflowID = "wf-B"`) issues an identical `OutboundHTTPRequest` (same method/URL/headers/body) with `CacheSettings.MaxAgeMs > 0`.
3. Because `Hash()` ignores `WorkflowID`, `Fetch` returns workflow A's cached response to workflow B without making a new HTTP call — confirmed directly by the existing unit test asserting `hash1 == hash2` when only `WorkflowID` differs. [2](#0-1)

## 3. HTTP Action Message Handling

### 3.1 Process Flow

1. **Request Reception**: Gateway receives HTTP action request from a workflow node
2. **Rate Limiting**: Validates node rate limits
3. **Request Parsing**: Extracts `OutboundHTTPRequest` from the JSON-RPC message
4. **Cache Check**: Determines if request should use cached response or fetch fresh data
5. **HTTP Execution**: Makes actual HTTP request to external endpoint
6. **Response Caching**: Stores cacheable responses (2xx, 4xx status codes) only if `CacheSettings.Store` is `true`
7. **Node Response**: Sends HTTP response back to requesting node

### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.
- **Cache TTL**: Configurable, default 10 minutes
- **Cache Key**: Generated from workflow ID and request hash
- **Cache Invalidation**: Time-based expiration with periodic cleanup
- **Cache Strategy**: All cacheable responses are cached; Non-zero `CacheSettings.MaxAgeMs` determines whether to return a cached value or make a fresh request
- **Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
