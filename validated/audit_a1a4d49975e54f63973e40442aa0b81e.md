### Title
Loss-adjusted withdraw receipts claimable at par due to epoch index mismatch in `lossRecoveryPriceByEpoch` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to CVE-2016-5315 (an index used past its valid bound reads unrelated data), `IdleCreditVault` records a stop-epoch loss haircut under the post-increment `epochNumber`, but reads it back under the user's request epoch stored in `lastWithdrawRequest`. The loss-adjusted price is therefore never found, and haircut receipts fall through to the funded path which pays 1:1, draining funded underlyings and leaving later claimants unable to withdraw.

### Finding Description
`requestWithdraw` stores the request epoch in `lastWithdrawRequest[_user] = currentEpoch` (`IdleCreditVault.sol:282`). `epochNumber` is incremented inside `deposit()` whenever it is called while `isEpochRunning()` is still true (`IdleCreditVault.sol:607-610`), i.e. during `stopEpoch`/`stopEpochWithDuration` when repaid funds are deposited back to the CDO.

`collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]` (`IdleCreditVault.sol:421`). Because `collectWithdrawFunds` pulls underlyings via `safeTransferFrom(idleCDO, ...)` (`IdleCreditVault.sol:428`), it can only execute after the CDO received the borrower repayment — which happens through `deposit()`, the call that already incremented `epochNumber`. Consequently the haircut for receipts requested in epoch `N` is stored under key `N+1`.

On the claim side, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. key `N`, finds `0`, and returns without applying the haircut (`IdleCreditVault.sol:790-795`). Execution then reaches `_claimFundedWithdrawRequest`, which only checks `epochNumber <= lastWithdrawRequest[_user]` (`IdleCreditVault.sol:326`) — satisfied after the increment — and pays `withdrawsRequests[_user]` at par via `_transferFundedClaim` (`IdleCreditVault.sol:341-349`).

The same wrong-index read also defeats the guard in `requestWithdraw` (`IdleCreditVault.sol:262-271`), which is supposed to block new requests until a loss-adjusted receipt is claimed; it reads `lossRecoveryPriceByEpoch[N]` = 0 and lets the user stack new requests.

### Impact Explanation
After any `stopEpochWithDuration(_lossAmount)` (or a partially funded `collectWithdrawFunds`), the strategy holds only the funded `_amount`, but every pending receipt from the request epoch claims 100%. The first claimant(s) — an attacker who made a large `requestWithdraw` in that epoch — withdraw at par, stealing the haircut that should have been socialized across all pending receipts. Later claimants' transfers revert (insolvency of the funded bucket): direct theft plus permanent freezing of the remaining honest users' claims, quantified as `pendingBasis - fundedAmount` (the intended loss) plus redistribution of the funded remainder.

### Likelihood Explanation
Requires a realized epoch loss (`stopEpochWithDuration` with `_lossAmount > 0`, or borrower underfunding in `collectWithdrawFunds`) and at least one pending withdraw request — a normal operating mode, not an edge case. The attacker is any unprivileged user with a withdraw request in the loss epoch; claim ordering is first-come-first-served, so the attacker just calls `claimWithdrawRequest` promptly. No privileged or malicious role is needed. The `defaultRecoveryInitialized` guard only gates legacy receipts; fresh deployments have it set in `initialize` (`IdleCreditVault.sol:147`).

### Recommendation
Key `lossRecoveryPriceByEpoch` by the same epoch identifier used at request time. Either capture the pre-increment epoch (`epochNumber - 1` semantics) when storing the haircut in `collectWithdrawFunds`, or store `lossRecoveryPriceByEpoch` before incrementing, or have `requestWithdraw`/`_claimLossAdjustedWithdrawRequest` map request epoch → settlement epoch consistently (e.g. store `lastWithdrawRequest` as `epochNumber` of the *settling* epoch). Add a regression test asserting that receipts pending during a lossy `stopEpochWithDuration` claim exactly `claimBasis * lossRecoveryPrice / 1e18`.

### Proof of Concept
Foundry fork sketch (against the repo's existing `IdleCreditVault.t.sol` harness):

```solidity
function testLossReceiptClaimsAtPar() external {
  uint256 amount = 10_000 * ONE_SCALE;
  idleCDO.depositAA(amount);
  _startEpochAndCheckPrices(0);

  // Attacker requests withdraw during the epoch (lastWithdrawRequest = epochNumber = N)
  cdoEpoch.requestWithdraw(0, address(AAtranche));
  uint256 receipt = vault.withdrawsRequests(address(this));

  // Borrower repays with a loss: stopEpochWithDuration(_lossAmount)
  vm.warp(cdoEpoch.epochEndDate() + 1);
  uint256 loss = receipt / 2; // 50% loss on the epoch
  vm.prank(manager);
  cdoEpoch.stopEpochWithDuration(loss, /* borrower funding of pending - loss */);

  // epochNumber is now N+1; haircut stored at lossRecoveryPriceByEpoch[N+1]
  assertEq(vault.lossRecoveryPriceByEpoch(cdoEpoch_epochBeforeStop), 0);
  assertGt(vault.lossRecoveryPriceByEpoch(vault.epochNumber()), 0);

  // Attacker claims: loss-adjusted path reads key N -> 0, falls through to par claim
  uint256 balPre = underlying.balanceOf(address(this));
  cdoEpoch.claimWithdrawRequest();
  // BUG: paid `receipt` (par) instead of `receipt * lossRecoveryPrice / 1e18`
  assertEq(underlying.balanceOf(address(this)) - balPre, receipt);
}
```

Uncertainty note: I could not open `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` within the tool-call budget to display the exact call ordering, but the ordering is forced by the funds flow — `collectWithdrawFunds` does `safeTransferFrom(idleCDO, ...)`, so the CDO must already hold the repaid underlyings, which only arrive via `deposit()`, the same call that increments `epochNumber` while `isEpochRunning()` is still true. If the actual ordering stores the haircut before the increment (i.e. keyed consistently with `lastWithdrawRequest`), the finding collapses; confirming the `stopEpoch` sequence in `IdleCDOEpochVariant.sol` is the single check needed.
