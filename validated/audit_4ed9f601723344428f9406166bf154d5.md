### Title
Guardian `pause()` unintentionally blocks user redemptions/withdrawals via `MultiDepositorVault.exit()` `whenNotPaused` guard - ([File: v3/src/core/MultiDepositorVault.sol])

### Summary
`BaseVault.pause()` is documented only as "halting the ability for guardians to submit" [1](#0-0) , but `MultiDepositorVault.enter()`/`exit()` both carry the same `whenNotPaused` modifier from the shared `Pausable` state [2](#0-1) . Since `ProvisionerV2` routes `redeem()`, `withdraw()`, `refundDeposit()`, and `solveRequestsVault()` all through `IMultiDepositorVault.exit()`, an `onlyAuthOrGuardian` pause (which any guardian can trigger, not just an owner/admin) freezes every one of these user-facing withdrawal paths, not just new guardian `submit()` operations.

### Finding Description
`BaseVault.pause()` is callable by `onlyAuthOrGuardian` [3](#0-2) [4](#0-3)  and its NatSpec states the intent is only to stop guardian `submit()` calls: "Pause the vault, halting the ability for guardians to submit" [1](#0-0) . However `Pausable` state is shared across the whole vault contract, and `MultiDepositorVault.enter()`/`exit()` — the only functions that actually mint/burn vault shares and move tokens for depositors — are also gated by `whenNotPaused` [2](#0-1) .

`ProvisionerV2.redeem()` and `withdraw()` (sync flows) ultimately call `_syncRedeem`, which invokes `IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).exit(...)`; their own guard is `solvingNotPaused(token)`, which only checks the `ISolvingGate` and does not check `BaseVault`'s `paused()` state [5](#0-4) [6](#0-5) . Likewise `solveRequestsVault` performs `IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).exit` internally via `_solveRequestsVault` [7](#0-6) , and `refundDeposit` calls `exit()` to return an unconfirmed sync deposit [8](#0-7) . None of these Provisioner-level guards check `BaseVault.paused()`, so a guardian pause silently reverts them at the `exit()` call with `Pausable: paused` even though the caller passed every Provisioner-level check.

This mirrors the ECG finding pattern exactly: a pause flag intended only to stop new/privileged actions (guardian `submit`) is applied at a shared-state level that also blocks the unrelated user withdrawal code path (`exit`), with no dedicated guard in the withdrawal function itself flagging this dependency.

### Impact Explanation
While a vault is guardian-paused, users cannot: sync `redeem`/`withdraw` their tokens, have async redeem/deposit requests solved against vault liquidity via `solveRequestsVault`, or reclaim funds via `refundDeposit` for an unconfirmed sync deposit — all revert on the underlying `exit()`/`enter()` `whenNotPaused` check. This is a temporary freeze of user funds tied directly to `MultiDepositorVault.enter`/`exit`, consistent with a Medium-severity "temporary freezing of user funds" bounty impact, since one path (`solveRequestsDirect`, using solver liquidity peer-to-peer and explicitly bypassing the vault, per its own code comment) remains available if a willing solver exists [9](#0-8) [10](#0-9) .

### Likelihood Explanation
Requires only that any address holding a whitelisted guardian role (or an authorized address) call `pause()` — a routine, expected operational action per the documented "halt guardian submit" purpose — while users hold vault shares and attempt `redeem`/`withdraw`/`solveRequestsVault`/`refundDeposit`. No malicious guardian collusion is required to trigger the freeze; it is a direct, deterministic consequence of the shared `Pausable` state, so likelihood is high whenever a legitimate pause occurs for its intended purpose.

### Recommendation
Decouple the withdrawal/exit path from the guardian-submission pause: either (a) remove `whenNotPaused` from `MultiDepositorVault.exit()` (and `refundDeposit`'s reliance on it) so redemptions remain possible while only `submit()`/`enter()` are frozen, or (b) introduce a separate pause flag specific to guardian `submit()` distinct from the one gating `enter`/`exit`, matching the documented intent that pausing should stop new guardian actions but not user withdrawals.

### Proof of Concept
1. Deploy `MultiDepositorVault` + `ProvisionerV2` via the standard factory setup; whitelist a guardian and have a user `deposit()`/sync-mint vault units normally.
2. As the guardian, call `BaseVault.pause()` (`onlyAuthOrGuardian`), confirming `paused() == true`.
3. As the user, call `ProvisionerV2.redeem(token, unitsIn, minTokensOut, receiver)` (or `withdraw(...)`): assert the call reverts with `Pausable: paused` bubbling from `MultiDepositorVault.exit()`, despite `solvingNotPaused(token)` succeeding.
4. Repeat with a queued async redeem request solved via `solveRequestsVault`: assert it also reverts for the same reason.
5. Confirm `solveRequestsDirect` (peer-to-peer, no `exit()` call) still succeeds for the same request, demonstrating the inconsistency between the "full-freeze" `PriceAndFeeCalculator` pause and the guardian `pause()` that inadvertently blocks vault-mediated withdrawals.

        // Effects: mint units to the recipient

        // Log the enter event
