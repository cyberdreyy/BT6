### Title
Ed25519 Signature Malleability Allows TPU Ingest Deduplication Bypass — ([File: perf/src/sigverify.rs])

### Summary
`solana_signature::Signature::verify` (invoked from `perf/src/sigverify.rs::verify_packet`, the core transaction-level ed25519 check used at TPU ingest) uses standard "cofactored" ed25519 verification, not the strict/cofactorless verification that Agave itself has already applied elsewhere to close this exact malleability class. Because of this, a single valid signature can be turned into multiple byte-distinct signatures over the *same* message/pubkey that all pass `verify_packet`, letting them evade the raw-byte packet Deduper and duplicate ingest-pipeline load — the same "multiple valid encodings for one signed message" bug class as CVE-2021-21405.

### Finding Description
Agave already recognizes and mitigates ed25519 malleability in two places:
- The ed25519 precompile program calls `publickey.verify_strict(message, &signature)` and has an explicit regression test, `test_ed25519_malleability`, demonstrating that a non-canonical signature (small-order `R`) passes plain `verify()` but is rejected by `verify_strict()`. [1](#0-0) [2](#0-1) 
- Gossip's CRDS signature path also deliberately uses `verify_strict` for the same reason. [3](#0-2) 

However, the core transaction signature-verification routine used at the TPU/ingest boundary (`perf/src/sigverify.rs::verify_packet`) still uses the non-strict `Signature::verify`: [4](#0-3) 
The equivalent parallel batch-verify path in `entry/src/entry.rs` (`UnverifiedSignatures::verify`, used to validate entries) also calls the non-strict `signature.verify(...)`: [5](#0-4) 

Immediately upstream of this signature check, packets are deduplicated by a probabilistic Bloom-filter `Deduper` keyed on the *raw packet bytes* (which include the signature bytes), not on message identity: [6](#0-5) [7](#0-6) 

Because non-strict ed25519 verification accepts multiple distinct `(R, S)` byte encodings for one message/pubkey (e.g., `R` shifted by an 8-torsion point, as shown in the precompile's own malleability test), an ordinary user holding a single valid signature can locally derive several syntactically different but semantically identical signature byte strings for the same transaction. Each variant produces a distinct packet under the Deduper's raw-byte hash, so all variants bypass the ingest-level dedup filter and are individually admitted into the (expensive) parallel ed25519 verification and the banking-stage scheduler.

The eventual double-spend/replay outcome is blocked further downstream, since the status cache keys on `message_hash` rather than the raw signature: [8](#0-7) [9](#0-8) 
and this is explicitly regression-tested (`test_tx_already_processed` mutates `tx.signatures[0]` and confirms `AlreadyProcessed` is still returned): [10](#0-9) 

So the impact is confined to the *ingest* layer: duplicate, but individually-valid-signature, copies of the same logical transaction can consume sigverify CPU time, dedup-filter capacity, and banking-stage scheduling slots multiple times before the redundant copies are rejected as `AlreadyProcessed`.

### Impact Explanation
This is a resource-amplification / ingest-starvation vector rather than a fund-loss or consensus-divergence bug: the status-cache's message-hash key (not signature) prevents any actual double-execution or double-spend. The concrete effect is that the TPU dedup filter (`perf/src/deduper.rs`) can be bypassed by a bounded number of self-generated signature variants per transaction, forcing the leader's sigverify/banking-stage pipeline to redundantly verify and schedule copies of the same transaction. This wastes ingest bandwidth and CPU/lock-acquisition resources that the probabilistic Deduper is specifically meant to conserve, and does so without requiring the attacker to produce any additional valid signatures (all variants are cheap deterministic byte transformations of one signature the attacker already possesses).

### Likelihood Explanation
Likelihood is moderate-to-low in practice: the number of distinct malleable encodings per signature is small (bounded by the ed25519 cofactor/torsion structure, not an unbounded amplification), and the ultimate transaction still only executes once. Exploitation requires no privileged access — any user who can submit a transaction can compute this locally — but the payoff is limited to modest amplification of ingest-stage work rather than a high-impact state or consensus bug.

### Recommendation
Switch the transaction-level ed25519 verification paths (`perf/src/sigverify.rs::verify_packet`, `entry/src/entry.rs::batch_verify`) to strict/cofactorless verification consistent with what Agave already does for the ed25519 precompile (`precompiles/src/ed25519.rs`) and gossip CRDS values (`gossip/src/crds_value.rs`), or otherwise dedupe/key on a canonicalized message identity earlier in the ingest pipeline rather than raw signature bytes.

### Proof of Concept
Conceptual PoC (cannot be fully executed without repo access to run):
1. Sign a normal transaction with a valid keypair, obtaining `(R, S)`.
2. Apply the same transformation demonstrated in `precompiles/src/ed25519.rs::test_ed25519_malleability` (adding an 8-torsion point to `R`) to derive a second byte-distinct signature that still verifies under non-strict `ed25519_dalek`/`solana_signature::Signature::verify`.
3. Submit both packets to the TPU. Because `perf/src/deduper.rs::Deduper::dedup` hashes raw packet bytes, both packets pass the Bloom-filter dedup check (`core/src/sigverify.rs::run_transaction_task` lines 282-298) and both proceed through the CPU-bound `verify_packet` (`perf/src/sigverify.rs` lines 20-63), which accepts both since it uses non-strict verification.
4. Both packets flow into banking stage; the second is only rejected once it reaches `Bank::check_transactions`/`check_status_cache`, which matches on `message_hash` (`runtime/src/bank/check_transactions.rs` lines 302-347), returning `TransactionError::AlreadyProcessed` — after already having consumed sigverify and scheduling resources.

impl CrdsValue {
    /// Verify the signature, short-circuiting on a previously-verified value
    /// hash and otherwise reusing a cached decompressed verifying key. Both
    /// caches are populated only after `verify_strict` succeeds, so neither can
    /// be seeded with arbitrary entries to evict useful ones.
    pub(crate) fn verify_with_cache(&self, cache: &SigVerifyCache) -> bool {
        if cache.verified_values.contains(&self.hash) {
            return true;
        }
        let pubkey = self.pubkey();
        let signable_data = self.signable_data();
        let message = signable_data.borrow();
        let sig_bytes: [u8; 64] = self.signature.into();
        let signature = ed25519_dalek::Signature::from_bytes(&sig_bytes);
        let verified = match cache.verifying_keys.get(&pubkey) {
            Some(vk) => vk.verify_strict(message, &signature).is_ok(),
            None => {
                let Ok(vk) = ed25519_dalek::VerifyingKey::try_from(pubkey.as_ref()) else {
                    return false;
                };
                if vk.verify_strict(message, &signature).is_err() {
                    return false;
                }
                cache.verifying_keys.insert(pubkey, vk);
                true
            }
        };
        if verified {
            cache.verified_values.insert(self.hash);
        }
        verified
    }

pub fn dedup_packets_and_count_discards<const K: usize>(
    deduper: &Deduper<K, [u8]>,
    batches: &mut [PacketBatch],
) -> u64 {
    batches
        .iter_mut()
        .flat_map(|batch| batch.iter_mut())
        .map(|mut packet| {
            if !packet.meta().discard()
                && packet
                    .data(..)
                    .map(|data| deduper.dedup(data))
                    .unwrap_or(true)
            {
                packet.meta_mut().set_discard(true);
            }
            u64::from(packet.meta().discard())
        })
        .sum()
}
