### Title
`escapeDotEnvValue`'s fixed 4-entry replacer omits `$`, enabling godotenv-style variable expansion / secret exfiltration when the generated `.env` output is re-parsed - (File: helpers/shell_escape.go)

### Summary
`escapeDotEnvValue` only escapes `\`, `"`, `\n`, and `\r` before wrapping a value in double quotes for `DotEnvEscape` output, but the `joho/godotenv`-compatible parser it targets performs `${VAR}`/`$VAR` expansion on double-quoted values after unescaping. Since `$` is never escaped, a job-controlled variable value containing `$OTHER_VAR` or `${OTHER_VAR}` is written verbatim into the generated dotenv content and will be substituted with another variable's value (potentially a secret) whenever that content is parsed back with expansion enabled.

### Finding Description
`escapeDotEnvValue` is defined as a `strings.NewReplacer` with exactly four escape pairs and is explicitly documented as targeting the unescape behavior of the `joho/godotenv` parser: [1](#0-0) 
`DotEnvEscape` uses this replacer to build `KEY="value"\n` lines for arbitrary job-supplied values, keyed by variable name: [2](#0-1) 

The comment acknowledges the author cross-referenced the specific unescape logic in godotenv's parser and even noted `\t` is intentionally excluded because it isn't unescaped there. However, `godotenv`'s value parsing does two independent things for double-quoted values: (1) strips backslash-escapes generically, and (2) performs `${VAR}`/`$VAR` expansion against the environment map being built as the file is parsed. `escapeDotEnvValue` addresses only the quote/backslash/newline concerns needed to keep the produced string a syntactically valid double-quoted token — it does nothing to neutralize `$`. Any job variable value containing a literal `$SOME_NAME` or `${SOME_NAME}` substring passes through untouched, gets embedded inside the double-quoted value, and will be expanded against whatever variables are visible in that same parse pass when a godotenv-compatible consumer reads the file back.

### Impact Explanation
If the generated dotenv content is later parsed with variable expansion enabled (the exact target behavior this function is written against), an unprivileged job can define one of its own output/custom variables with a value like `${CI_JOB_TOKEN}` or `${SOME_MASKED_VAR}`. When re-parsed, that reference resolves to the real value of another variable present in the same environment/file, and the substituted secret ends up stored in the attacker's own variable — which the attacker fully controls the downstream use of (e.g., printed to job log, exported to a script, or exposed via whatever consumes the escaped values). This is a scoped-secrets-leak primitive: masked/secret values can cross variable boundaries within a job's own visible variable set due to a missing single-character escape.

### Likelihood Explanation
Preconditions are minimal: an attacker only needs to control the *value* of any variable that is later serialized through `DotEnvEscape` and needs another variable (e.g., a secret) to be present in the same parse context. No special executor privileges or admin cooperation are required — this is reachable purely through normal CI variable definitions. The bug is deterministic and repeatable: the same `$`-containing value always survives escaping unmodified.

### Recommendation
Add `$` to the `escapeDotEnvValue` replacer (e.g., `"$", "\\$"`) so that literal dollar signs in job-supplied values are escaped before being wrapped in the dotenv-style double-quoted string, matching the exact escape set that a variable-expansion-aware, godotenv-compatible consumer requires to avoid unintended `${VAR}`/`$VAR` substitution. Audit all consumers of `DotEnvEscape`'s output to confirm whether expansion is enabled during parsing, and add a regression test asserting `$`-bearing values round-trip literally.

### Proof of Concept
Go unit test addition to `helpers/shell_escape_test.go`:
```go
func TestDotEnvEscape_DollarSignNotEscaped(t *testing.T) {
    variables := map[string]string{
        "SECRET":  "top-secret-value",
        "ATTACKER": "${SECRET}", // attacker-controlled value referencing another var
    }
    output := DotEnvEscape(variables)
    // Currently fails: "$" passes through unescaped
    assert.NotContains(t, output, `ATTACKER="${SECRET}"`,
        "dollar sign in job-controlled value must be escaped to prevent variable expansion on re-parse")
}
```
Expected assertion: after the fix, the emitted line should be `ATTACKER="\$\{SECRET\}"` (or equivalent escaped form) so that a godotenv-compatible parser treats it as a literal string rather than expanding it to `SECRET`'s value.

func DotEnvEscape(variables map[string]string) string {
	var sb strings.Builder

	// Sort variables to get deterministic output
	keys := make([]string, 0, len(variables))
	for key := range variables {
		keys = append(keys, key)
	}
	sort.Strings(keys)

	for _, key := range keys {
		if !isValidDotEnvKey(key) {
			// Skip invalid keys
			continue
		}

		value := variables[key]
		fmt.Fprintf(&sb, "%s=\"%s\"\n", key, escapeDotEnvValue(value))
	}

	return sb.String()
}
