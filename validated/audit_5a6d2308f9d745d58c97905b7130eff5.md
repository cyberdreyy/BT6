### Title
Missing `state_exists` guard lets anyone re-run `LockupContract::new` on an already-initialized (even `Terminating`) lockup, overwriting `vesting_information`/`termination_withdrawn_tokens` and handing control of the remaining balance to a new party - (File: `lockup/src/lib.rs`)

### Summary
`LockupContract::new` at `lockup/src/lib.rs` never checks `env::state_exists()` before constructing and persisting a fresh `Self`, unlike every sibling contract in this repo (`whitelist`, `multisig`, `staking-pool-factory`, `lockup-factory`) which all explicitly `assert!(!env::state_exists(), ...)` in their `#[init]` `new`. Because the `new` method has no owner/predecessor check and `#[near_bindgen]`'s `#[init]` attribute in this near-sdk version performs no automatic re-init protection, any unprivileged account can call `new` a second time on an existing, already-initialized lockup account - including one that is mid-termination (`vesting_information == Terminating`, `termination_withdrawn_tokens > 0`) - and completely overwrite its state.

### Finding Description
The broken binding: `state_exists(lockup_account) == true` should imply `new()` panics ("already initialized"), the same invariant enforced in every other contract in this repo: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

`LockupContract::new` has no such assertion: [5](#0-4) 

Because the method is a plain public `#[near_bindgen]` method with no `assert_eq!(env::predecessor_account_id(), ...)` guard, and because `#[init]` in this near-sdk version does not itself prevent re-invocation, any account (the attacker) can submit a `FunctionCall` transaction targeting `new` on any deployed lockup account they don't own. On successful return, `near_bindgen` persists the returned `Self` unconditionally, overwriting the prior `owner_account_id`, `lockup_information` (including `termination_withdrawn_tokens`, which is reset to `0`), `vesting_information` (which the attacker can set to `VestingInformation::None` by passing `vesting_schedule: None`), `staking_information` (reset to `None`), and `foundation_account_id` (which the attacker can set to `None` since it's only required when a vesting schedule is supplied).

Exploit flow: attacker waits until (or targets) a lockup account whose vesting is `Terminating` with `termination_withdrawn_tokens != 0` - i.e., the foundation has already recovered part of the unvested tokens and the remainder is still locked in the account pending completion of termination. Attacker sends a transaction calling `new` on that account with `owner_account_id` set to an account they control, `vesting_schedule: None`, `foundation_account_id: None`, and `lockup_timestamp`/`release_duration` chosen so tokens are immediately unlocked. Since `lockup_amount` is recomputed as `env::account_balance()` at call time, the new state legitimizes the remaining balance as a plain, already-unlocked lockup owned by the attacker, erasing the in-flight termination and the foundation's claim over the unvested remainder.

None of the existing guards intercept this: `assert_owner`, `assert_no_termination`, and `assert_valid_request` are owner/foundation-method guards on other entrypoints, not on `new`; `assert_self()` is irrelevant since this isn't a promise callback; there is no `is_promise_success()` gate; `env::state_exists()` is simply never called in this function.

### Impact Explanation
The attacker (or the party they designate as `owner_account_id`) gains full control of, and can transfer out, the remaining NEAR balance held in the lockup account - funds that were locked/unvested and, in the `Terminating` scenario, legally owed in part to the NEAR Foundation. This is a direct instance of "locked or unvested tokens released early" / "a lockup deployed with parameters its rightful creator never chose," matching the Critical impact category. The attack is repeatable against any deployed lockup account (not just ones in `Terminating` state) since the missing guard applies universally; the blast radius covers every lockup contract instance created by the `lockup-factory`.

### Likelihood Explanation
Preconditions: the target lockup account must already exist (any lockup deployed by the factory qualifies) and be enough that the attacker knows its account ID (deterministically derivable from `owner_account_id` per `lockup-factory`'s account-naming scheme, so any lockup's address is public/computable). No deposit or attached balance is strictly required for `new` (it is not `#[payable]`), and no special key or role is needed since `new` is a public function call with no predecessor check. This is trivially reachable by any funded NEAR account and is fully repeatable across every lockup account in existence, making likelihood high once discovered.

### Recommendation
Add `assert!(!env::state_exists(), "The contract is already initialized");` as the first statement of `LockupContract::new` in `lockup/src/lib.rs`, mirroring the pattern already used in `lockup-factory/src/lib.rs`, `multisig/src/lib.rs`, `staking-pool-factory/src/lib.rs`, and `whitelist/src/lib.rs`.

### Proof of Concept
```rust
// lockup/src/lib.rs test module
#[test]
#[should_panic(expected = "already initialized")]
fn test_reinit_over_existing_state_is_blocked() {
    let context = basic_context();
    testing_env!(context.clone());

    // First initialization - legitimate owner via factory batch.
    let vesting_schedule = new_vesting_schedule(0);
    let mut contract = new_contract(true, Some(vesting_schedule.clone()), None, true);

    // Simulate mid-termination: Terminating with non-zero termination_withdrawn_tokens.
    contract.vesting_information = VestingInformation::Terminating(TerminationInformation {
        unvested_amount: to_yocto(100),
        status: TerminationStatus::VestingTerminatedWithDeficit,
    });
    contract.lockup_information.termination_withdrawn_tokens = to_yocto(50);

    // ATTACKER re-runs `new` on the same account, unprivileged, no state_exists guard.
    let attacker_owned_contract = LockupContract::new(
        /* owner_account_id */ AccountId::from("attacker"),
        to_nanos(0).into(),
        None,
        TransfersInformation::TransfersEnabled { transfers_timestamp: to_ts(GENESIS_TIME_IN_DAYS).into() },
        None,          // vesting_schedule = None -> wipes out Terminating state
        None,
        AccountId::from("whitelist"),
        None,          // foundation_account_id = None
    );

    // Binding check (would fail today because there is no panic before this runs):
    // Before: contract.vesting_information == Terminating, termination_withdrawn_tokens == 50 NEAR
    // After:  attacker_owned_contract.vesting_information == VestingInformation::None
    //         attacker_owned_contract.owner_account_id == "attacker"
    //         attacker_owned_contract.lockup_information.termination_withdrawn_tokens == 0
    assert_ne!(
        attacker_owned_contract.owner_account_id,
        contract.owner_account_id,
        "state was re-initialized by a non-owner, breaking the once-only invariant"
    );
}
```
Expected today: the test fails to panic (no `state_exists` guard exists), demonstrating the vulnerability; after applying the recommended fix, the second `LockupContract::new` call panics with `"The contract is already initialized"`, and the `should_panic` assertion in the test passes.

    pub fn new(
        owner_account_id: AccountId,

        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,

        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),

        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {

                assert!(
                    foundation_account_id.is_none(),

                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(

                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
