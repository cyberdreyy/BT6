Let me check the CDO side of instant-withdraw funding and default finalization.### Title
Stale per-epoch instant-withdraw ledger is double-counted as recovery basis and prefunded reserve at default finalization, inflating `defaultRecoveryPrice` and freezing/draining the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The analog of the binder shrinker UAF is a stale-pointer read: `claimInstantWithdrawRequest` clears the aggregate receipt `instantWithdrawsRequests[user]` but never clears the per-epoch ledgers `instantWithdrawsRequestsByEpoch[user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]`. If the borrower defaults in the same epoch, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` dereference that stale ledger as if the already-claimed amounts were still outstanding claims *and* still-held cash — the vault equivalent of using `alloc->vma` after munmap freed it.

### Finding Description

`requestInstantWithdraw` records three things (`IdleCreditVault.sol:356-375`): the aggregate `instantWithdrawsRequests[user]`, the per-epoch `instantWithdrawsRequestsByEpoch[user][epochNumber]`, and the epoch total `instantWithdrawClaimsByEpoch[epochNumber]`. `collectInstantWithdrawFunds` (`:398-403`) only decrements `pendingInstantWithdraws` — the code comments confirm it is deliberately "only the unfunded remainder," so partial prefunding is a designed state.

On a funded claim, `claimInstantWithdrawRequest` (`:380-393`) burns and zeroes the aggregate but leaves both per-epoch entries untouched:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
// instantWithdrawsRequestsByEpoch[user][epoch] and
// instantWithdrawClaimsByEpoch[epoch] are never decremented
```

If `finalizeDefaultRecovery` (`:661-710`) runs while `pendingInstantWithdraws != 0` in the same epoch, `defaultPendingClaimBasis()` (`:644-649`) adds `instantWithdrawClaimsByEpoch[epochNumber]` — which still contains already-paid claims — to the haircut basis, and `_defaultPrefundedInstantReserve()` (`:716-723`) counts `instantBasis - pendingInstant` as underlying the strategy already holds, even though that cash was already transferred out to earlier claimants:

```solidity
uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber]; // stale: includes paid claims
if (instantBasis > pendingInstant) prefundedReserve = instantBasis - pendingInstant;
```

The result is `reserveAmount = _recoveredAmount + ghostPrefunded + defaultRecoveryReserve` and `recoveryPrice = reserveAmount * 1e18 / totalBasis` priced against phantom funds.

### Impact Explanation

Direct theft plus permanent freezing of unclaimed recovery. Let the stale (already-claimed) instant amount be `G`. The recovery price is computed as if `G` extra underlying existed in the strategy. Every defaulted-epoch receipt holder (normal withdraws via `_claimDefaultedWithdrawRequest`, instant via `_claimDefaultedInstantWithdrawRequest`, post-default via `_claimPostDefaultWithdrawRequest`) is paid `claimBasis * inflatedPrice / 1e18` from `defaultRecoveryReserve` (`:912-917`). Early claimants — the attacker — extract more than their fair share of the real reserve; once the real tokens are gone, `defaultRecoveryReserve -= _amount` underflows and reverts, permanently freezing the remaining claimants' recovery. Quantified loss: up to `G`, i.e., the entire prefunded-and-claimed instant volume of the defaulted epoch, stolen from later claimants; residual claims are frozen forever since `defaultRecoveryFinalized` is already true and cannot be re-run.

### Likelihood Explanation

The attacker is an ordinary instant withdrawer (any tranche-token holder / KYC-passing lender); no privileged role misbehaves. Requirements:

1. Instant withdrawals enabled (manager sets params — honest, routine configuration).
2. At least two instant requests in the same epoch, with the CDO funding them partially/sequentially — the code comments ("partially prefunded instant requests," `pendingInstantWithdraws` as unfunded remainder) confirm this state is reachable, and a funded claim leaves the epoch ledger stale.
3. The borrower defaults in that same epoch and the CDO finalizes recovery while `pendingInstantWithdraws != 0` — precisely the path `defaultPendingClaimBasis`/`defaultInstantWithdrawsFinalized` (`:696`) was written to handle.

No existing guard stops it: `_ensureDefaultRecoveryInitialized` only checks `pendingInstantWithdraws != 0` on upgrade paths, the reserve guard in `_transferFundedClaim` (`:897-907`) doesn't apply to the pre-finalization funded claims, and nothing ever decrements `instantWithdrawClaimsByEpoch` outside `_claimDefaultedInstantWithdrawRequest`.

One caveat I could not fully verify within the available context: the exact sequencing inside `IdleCDOEpochVariant.claimInstantWithdrawRequest`/`_handleBorrowerDefault` (whether the CDO always fully collects before each claim, and whether finalization is reachable mid-epoch). The strategy code is explicitly written to tolerate partial funding, so the stale-ledger state is reachable under honest owner/manager sequencing.

### Recommendation

Keep the per-epoch ledgers consistent with the aggregate: in `claimInstantWithdrawRequest` (or in `collectInstantWithdrawFunds`), decrement `instantWithdrawsRequestsByEpoch[user][requestEpoch]` and `instantWithdrawClaimsByEpoch[requestEpoch]` for each funded claim. Because the aggregate does not retain per-request-epoch identity, this likely requires tracking the request epoch per user (e.g., an `instantRequestEpoch` slot analogous to `lastWithdrawRequest`, rejecting a second instant request in a different epoch before the first is claimed), or attributing collections per epoch. Alternatively, compute the default-time instant basis as `min(instantWithdrawClaimsByEpoch[epochNumber], pendingInstantWithdraws + actually-held prefunded balance)` measured from the token balance rather than the stale ledger.

### Proof of Concept

Foundry fork sketch against `test/foundry/IdleCreditVault.t.sol` harness (instant-enabled epoch variant, fixed-APR, prefunded mode):

```solidity
function testStaleInstantLedgerInflatesRecovery() external {
  _useStandardEpochVariant();
  _stopCurrentEpochWithApr(10e18);                 // now epoch 1 (buffer)
  vm.prank(manager);
  cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

  address alice = makeAddr('alice');
  address bob   = makeAddr('bob');
  _depositWithUser(alice, 100e6);
  _depositWithUser(bob,   100e6);
  vm.prank(manager); cdoEpoch.startEpoch();        // epoch running

  // both request instant withdrawals (receipts of 100e6 each)
  _requestInstantWithdrawWithUser(alice, 100e6);
  _requestInstantWithdrawWithUser(bob,   100e6);
  // pendingInstantWithdraws = 200e6, instantWithdrawClaimsByEpoch[E] = 200e6

  // CDO collects only Alice's share and she claims
  deal(address(underlying), address(cdoEpoch), 100e6);
  vm.prank(manager); // or CDO flow
  // cdoEpoch transfers 100e6 via collectInstantWithdrawFunds(100e6)
  vm.prank(alice); cdoEpoch.claimInstantWithdrawRequest();
  // stale state: instantWithdrawClaimsByEpoch[E] == 200e6,
  // pendingInstantWithdraws == 100e6, strategy balance == 0

  // borrower defaults in the same epoch; finalization:
  // basis += 200e6 (includes Alice's paid 100e6)
  // prefundedReserve = 200e6 - 100e6 = 100e6 counted as held cash
  // recoveryPrice inflated by ghost 100e6
  _handleBorrowerDefaultAndFinalize(/* recovered = real reserve only */);

  // Bob claims at inflated price: overpays vs real reserve;
  // a second claim then reverts on defaultRecoveryReserve underflow
  vm.prank(bob); cdoEpoch.claimInstantWithdrawRequest();
  vm.expectRevert(); // any further defaulted/post-default claim frozen
}
```

Key assertions: `strategy.instantWithdrawClaimsByEpoch(epoch)` remains `200e6` after Alice's funded claim (stale-pointer evidence), `finalizeDefaultRecovery` produces a `defaultRecoveryPrice` higher than `realReserve * 1e18 / realBasis`, and the last claimant's `claimWithdrawRequest`/`claimInstantWithdrawRequest` reverts, permanently freezing unclaimed recovery.
