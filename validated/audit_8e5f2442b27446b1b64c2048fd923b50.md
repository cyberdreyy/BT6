### Title
Stale confirmations from removed multisig members/keys still count toward `num_confirmations` threshold - ([File: multisig/src/lib.rs], [File: multisig2/src/lib.rs])

### Summary
Both `multisig` and `multisig2` allow a request to execute as soon as `confirmations.len() + 1 >= num_confirmations`, but `DeleteKey`/`DeleteMember` only purge requests *originated* by the removed signer — they never scrub that signer's pre-existing confirmation entries left on *other* still-pending requests. A request can therefore be executed using a confirmation cast by a key/member that has since been deleted from the multisig, meaning fewer live, currently-authorized signers actually approved it than `num_confirmations` requires.

### Finding Description
In `multisig/src/lib.rs`, `confirm()` checks the threshold purely by counting entries in the `confirmations` `HashSet<PublicKey>` for a request: [1](#0-0) 

When a key is removed via the `DeleteKey` action, the code only removes requests where `r.signer_pk == pk` (i.e., requests *created* by that key) and clears `num_requests_pk` for it — it does not scan other pending requests' `confirmations` sets to strip out that key's prior confirmation: [2](#0-1) 

`assert_valid_request()` also never re-validates that every entry already stored in `confirmations` still corresponds to a currently active key — it only checks that the *caller* of the current call is the contract's own account: [3](#0-2) 

The identical pattern exists in `multisig2/src/lib.rs`: `delete_member()` only purges requests whose `member == member`, not stale confirmation entries left by that member on unrelated requests, and `confirm()`/`assert_valid_request()` never re-validate the confirmations set against the current `members` set: [4](#0-3) [5](#0-4) [6](#0-5) 

This is the direct analog of the external report's bug class: a control (price band cap / here, "confirmation must come from a live member") is enforced on the primary path (adding a new confirmation from a currently valid signer) but not enforced on the path that consumes accumulated state to authorize a privileged action (counting stale confirmations toward execution threshold). The invariant that should be an equality — `confirmations counted == confirmations from currently live members` — is broken because deleted members'/keys' confirmations persist in state and are still tallied.

### Impact Explanation
This breaks the multisig authorization threshold binding directly: a request (e.g., `Transfer`, `AddKey`/`AddMember`, `FunctionCall`) can be executed with confirmations from fewer live, currently-authorized signers than `num_confirmations` mandates, because one or more of the counted confirmations belong to a key/member that has already been removed. This falls squarely into the listed Critical impact category "a multisig request executed below threshold," since it undermines the fundamental K-of-N security guarantee the contract exists to provide (arbitrary fund transfers, key additions, or contract upgrades gated by a weaker-than-configured threshold).

### Likelihood Explanation
Requires a specific but realistic sequence, no privileged capability beyond normal operation of the multisig itself:
1. A pending request `R` exists and has been confirmed by member/key `M` (but not yet enough confirmations to execute).
2. Member `M` is later removed via a separate, properly-confirmed `DeleteKey`/`DeleteMember` request (a routine operation, e.g., off-boarding a team member or rotating compromised keys) while `R` is still outstanding.
3. A remaining valid signer confirms `R`; the stale confirmation from `M` plus the new confirmation reaches `num_confirmations`, and `R` executes — despite only one truly live signer having approved it (for `num_confirmations == 2`) or generally fewer live approvals than required.

This is not an attacker needing special access — it can happen as an unintended consequence of ordinary key-rotation/member-removal operations combined with any long-lived pending request, and does not require an admin mistake or documented invariant violation to trigger (unlike the escalation debate in the source report).

### Recommendation
When executing `DeleteKey`/`DeleteMember`, iterate over **all** pending requests' confirmation sets (not just those originated by the removed signer) and remove the deleted key/member's entry from each. Alternatively, validate confirmations against the current member/key set at the time of tallying in `confirm()` (i.e., only count confirmations whose signer is still a member) before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize `multisig` with 3 keys (K1, K2, K3) and `num_confirmations = 2`.
2. K1 calls `add_request` to create request `R1` (e.g., `Transfer`).
3. K2 calls `confirm(R1)` → `confirmations(R1) = {K2}` (1 confirmation, below threshold of 2, not yet executed).
4. Separately, K1 and K3 create+confirm a `DeleteKey { public_key: K2 }` request (self-request, 2 confirmations reached) → K2 is removed from the multisig (`num_requests_pk` cleared for K2, but `R1`'s confirmations set is untouched because `R1` was authored by K1, not K2 — see `filter(|(_k, r)| r.signer_pk == pk)` at `multisig/src/lib.rs:205`).
5. K3 calls `confirm(R1)`: `confirmations(R1).len() (=1, containing stale K2) + 1 = 2 >= num_confirmations (2)` → `R1` executes, even though only K1 (request author, implicitly) and K3 are actually live confirming signers and K2's stale confirmation from before its removal was reused to meet the 2-of-3 threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
