### Title
Draining the shared ERC4626 vault's liquidity permanently blocks `stopEpoch`, freezing all LP withdraws - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower` parks all undrawn pool capital in an external ERC4626 vault (`vault`). At epoch end, `IdleCDOEpochVariant._stopEpoch` calls `onStopEpoch(_amountRequired, ...)`, which must withdraw the shortfall from that vault via `vault.withdraw(shortfall, ...)`. If the vault lacks *redeemable liquidity* (as opposed to share value), the withdrawal reverts and `onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable`. The revert bubbles through `IdleCDOEpochVariant._stopEpoch` (it is outside the `try this.getFundsFromBorrower` block), so the epoch can never be stopped while vault liquidity is unavailable. Any unprivileged user of the same ERC4626 vault — e.g. a co-depositor redeeming or a borrower draining the vault's lending markets (flash-loanable) — can keep the vault illiquid and permanently grief every `stopEpoch` call, freezing all pending and future LP withdrawals even though the pool's shares are fully backed.

### Finding Description
The external report's bug class is "flash-loan drains the rehypothecation vault; the recall path does not redeploy/rebalance, leaving the vault without tokens → DoS". The direct analog here is the inverse-direction recall: funds are rehypothecated into `vault`, and `stopEpoch` cannot complete unless the vault coughs up cash on demand.

Relevant flow:

- `IdleCDOEpochVariant._stopEpoch` calls `IProgrammableBorrower(_borrower()).onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)` and lets reverts propagate deliberately so "transient ERC4626 liquidity failures can be retried" (IdleCDOEpochVariant.sol:395-404).
- `ProgrammableBorrower.onStopEpoch` computes `shortfall = _amountRequired - onHand`. The only early-exit guard is `if (shortfall > _currentVaultAssets()) return true;` — this compares the shortfall to the *share-denominated economic value* (`convertToAssets`), not to the vault's actually withdrawable liquidity (`maxWithdraw`). A vault position can be fully backed by shares yet have zero withdrawable liquidity (lending vaults, capped markets, utilization = 100%).
- When `shortfall <= _currentVaultAssets()` but `shortfall > vault.maxWithdraw(...)`, `vault.withdraw` reverts and `onStopEpoch` reverts `StopEpochVaultLiquidityUnavailable` (ProgrammableBorrower.sol:239-253).
- Because the revert escapes `_stopEpoch`, none of the stop transitions execute: `isEpochRunning` stays true, `collectWithdrawFunds`/`mintStrategyTokens`/`_updateAccounting` never run, and `defaulted` is never set — so `_handleBorrowerDefault`, `finalizeDefault`, and any recovery path are unreachable. Ordinary deposits, withdraw requests, and claims stay gated (`_pause()` was applied at `startEpoch`, `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are false during a running epoch).

Broken invariant: pending withdraw receipts and LP principal must be claimable at epoch end against fully-backed assets; instead solvency is intact but settlement is gated on a third-party vault's instantaneous liquidity.

### Impact Explanation
An unprivileged attacker — explicitly allowed by the threat model as "a user of the programmable borrower's ERC4626 vault" — borrows or redeems the vault's free liquidity (atomically, with a flash loan, in the same block as `stopEpoch`, or persistently by keeping utilization at ~100%). Every `stopEpoch`/`stopEpochWithDuration` call then reverts. Effects:

- Pending withdraw-request holders (`withdrawsRequestsByEpoch`) cannot be paid: `collectWithdrawFunds` is never reached, so `claimWithdrawRequest` reverts.
- All tranche NAV is frozen inside the epoch: requests are disabled while `isEpochRunning`, and there is no path to default/finalize because a reverting `onStopEpoch` never reaches `_handleBorrowerDefault` (unlike the `return false` / `transferFrom`-failure paths which do default the pool).
- Since the hook reverts rather than returns `false`, the pool cannot even enter the default recovery flow — the freeze can be extended indefinitely every block for the cost of a flash-loan fee, and normal buffer/close-pool operations (including `_interest == 1` full recall) are equally blocked.

Quantified loss: 100% of pool NAV (all tranche holder principal + pending withdraw requests + accrued interest) is frozen for the duration of the liquidity drain; with repeated draining this is effectively permanent until the vault's liquidity organically returns, which the attacker can prevent while utilization stays high.

### Likelihood Explanation
Requires only that the configured ERC4626 vault is shared (i.e. its liquidity is borrowable/redeemable by third parties — the standard case for Morpho-style or lending vaults) and that at the moment of `stopEpoch`, withdrawable liquidity < `shortfall` while share value ≥ `shortfall`. The attacker needs no role: no owner/manager/borrower/keeper action is subverted — the manager calls `stopEpoch` honestly and the tx reverts. The guard `shortfall > _currentVaultAssets()` only protects against *undercollateralization*, not *illiquidity*, so the design intentionally converts an illiquidity event into a hard revert instead of either (a) withdrawing what is available and proceeding, or (b) returning `false` to trigger the default path.

Note: the `catch { revert StopEpochVaultLiquidityUnavailable(); }` and the comment "transient ERC4626 liquidity failures can be retried" show the retry behavior was considered, but retryability does not mitigate an attacker who keeps the vault drained, nor does it provide any escape hatch — `rescueTokens` cannot move vault shares' underlying and `emergencyExitVault` hits the same illiquidity wall.

### Recommendation
In `ProgrammableBorrower.onStopEpoch`, cap the withdrawal by `vault.maxWithdraw(address(this))` (and/or use `redeem` on the share amount actually withdrawable) instead of reverting:

```solidity
uint256 withdrawable = vault.maxWithdraw(address(this));
uint256 toWithdraw = shortfall > withdrawable ? withdrawable : shortfall;
if (toWithdraw != 0) {
    try vault.withdraw(toWithdraw, address(this), address(this)) returns (uint256 shares) {
        if (epochAccountingActive) epochWithdrawnFromVault += toWithdraw;
        emit WithdrawnFromVault(toWithdraw, shares, address(this));
    } catch { /* leave it to IdleCDO's transferFrom result */ }
}
```

Then let `getFundsFromBorrower`/`transferFrom` fail naturally, which routes through the existing `try/catch` → `_handleBorrowerDefault`, so an illiquid vault results in a proper default (with the vault shares still recoverable later via `finalizeDefault`/recovery) instead of an unrecoverable revert loop. Alternatively, return `false` on uncovered shortfall so close-pool settlement enters the default path rather than reverting.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";

// Setup: IdleCDOEpochVariant (programmable mode, minted interest) ->
//   strategy = IdleCreditVault -> borrower() = ProgrammableBorrower ->
//   vault = a real shared ERC4626 (e.g. a Morpho vault on a mainnet fork) that
//   also lends to third parties.

contract StopEpochVaultLiquidityDosTest is Test {
    // cdo, strategy, pb, vault, underlying, manager, attacker are wired on a
    // mainnet fork against the deployed/shared ERC4626 vault.

    function test_DrainVaultLiquidity_BlocksStopEpoch() external {
        // 1. LPs depositAA/depositBB; several requestWithdraw -> pendingWithdraws = P.
        // 2. manager.startEpoch(): surplus sent to ProgrammableBorrower, which
        //    deposits (almost) everything into `vault` via onStartEpoch/_depositToVault.
        // 3. Attacker (any vault co-user): flash-borrows / redeems so that
        //    vault.maxWithdraw(address(pb)) == 0 while
        //    vault.convertToAssets(pb.vaultSharesBalance()) >= required shortfall.
        // 4. warp past epochEndDate; manager calls stopEpoch(0, 0).
        vm.warp(cdo.epochEndDate() + 1);
        vm.prank(manager);
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        cdo.stopEpoch(0, 0);   // revert bubbles out of onStopEpoch

        // 5. State is unchanged: epoch still running, no default, no path forward.
        assertTrue(cdo.isEpochRunning());
        assertFalse(cdo.defaulted());

        // 6. Even close-pool recall reverts the same way.
        vm.prank(manager);
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        cdo.stopEpoch(0, 1);

        // 7. Pending withdraw holders cannot claim: collectWithdrawFunds never ran.
        vm.prank(lp);
        vm.expectRevert(); // no funded epoch claims
        cdo.claimWithdrawRequest();

        // 8. Attacker repeats the drain in every block (or keeps utilization at
        //    100%), extending the freeze indefinitely at flash-loan cost, while
        //    pool NAV remains fully backed by vault shares.
    }
}
```

Invariant broken: `stopEpoch` must be able to settle a fully-backed epoch; instead it is gated on the external vault's instantaneous withdrawable liquidity, which any unprivileged vault user can force to zero on demand.
