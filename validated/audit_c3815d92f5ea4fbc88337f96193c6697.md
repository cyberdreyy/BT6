### Title
Loss-adjusted withdraw receipts escape their haircut when the recorded loss epoch does not match the user's request epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration`/`stopEpoch` only partially funds pending withdraw receipts, `collectWithdrawFunds` records the haircut under `lossRecoveryPriceByEpoch[epochNumber]` using the *current* counter. Claiming, however, looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. the epoch in which the user *requested*. Any receipt whose request epoch differs from the epoch under which the haircut was stored bypasses `_claimLossAdjustedWithdrawRequest` entirely and is paid at par by `_claimFundedWithdrawRequest`, over-draining the funded pool and leaving later claimants unpayable.

### Finding Description
- `requestWithdraw` tags a user with `lastWithdrawRequest[_user] = epochNumber` at request time and stores the basis under `withdrawsRequestsByEpoch[_user][epochNumber]` (IdleCreditVault.sol:282-293).
- At a lossy stop, `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` and zeroes `pendingWithdraws` (IdleCreditVault.sol:411-421), i.e. the haircut is indexed by the epoch counter *at stop time*, not by each receipt's request epoch.
- `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which only fires when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` (IdleCreditVault.sol:789-801). If the haircut was stored under a different epoch key than the user's `lastWithdrawRequest`, this returns 0 and `_claimFundedWithdrawRequest` then pays the *full* `withdrawsRequests[_user]` at par via `_transferFundedClaim` (IdleCreditVault.sol:338-349), even though `pendingWithdraws` was zeroed and the vault only received the haircutted `_amount`.
- The same epoch-key mismatch exists on the default path: `_claimDefaultedWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest` look up per-epoch basis under `defaultRecoveryEpoch` (set to `epochNumber` at finalization), while request-side basis was recorded under the request-time `epochNumber` (IdleCreditVault.sol:693, 772-784, 842-855). `epochNumber` is incremented inside `deposit()` during the stop flow (IdleCreditVault.sol:607-614), so any bookkeeping keyed before vs. after that bump is off by one.

### Impact Explanation
A KYC'd lender whose receipt is tagged with an epoch key different from the recorded `lossRecoveryPriceByEpoch`/`defaultRecoveryEpoch` key claims their full un-haircutted amount from the funded underlyings. Because the vault only received `pendingBasis * lossRecoveryPrice`, each such claim directly steals the share belonging to correctly-haircutted claimants; once the funded balance is exhausted, remaining receipt holders' claims revert or pay less than the recovery price — i.e. direct theft plus permanent freezing of the residual claim value, quantified by `(1 - lossRecoveryPrice) * claimBasis` per escaping receipt.

### Likelihood Explanation
Reachable by an ordinary unprivileged lender who simply requests a withdraw in an epoch that ends with `stopEpochWithDuration(_lossAmount > 0)` or a defaulted/finalized epoch, whenever the counter used in `collectWithdrawFunds`/`finalizeDefaultRecovery` diverges from the request-time counter (notably if `deposit()`'s `epochNumber += 1` executes before the loss write, or when requests from an earlier epoch remain pending into a later lossy stop). No privileged role is required; the attacker only calls `requestWithdraw` and later `claimWithdrawRequest`. The existing guards (`NotAllowed` on re-request before claiming a loss-adjusted receipt, `defaultRecoveryInitialized`, `_transferFundedClaim` reserve check) do not detect the key mismatch — they only guard re-request and reserve isolation, not index equality.

### Recommendation
Key loss/recovery prices by the request epoch of each receipt rather than a single mutable `epochNumber`, or maintain a `pendingWithdrawEpoch` recorded when receipts are created and use it for both the write in `collectWithdrawFunds`/`finalizeDefaultRecovery` and the reads in the claim functions. Alternatively, store the effective recovery price per user/receipt at claim time by iterating the epochs present in `withdrawsRequestsByEpoch[_user]`, and add an invariant test asserting `sum(claimed) <= fundedAmount` after any partial-funding stop.

### Proof of Concept
Foundry fork PoC sketch (on the in-scope `IdleCDOEpochVariant` + `IdleCreditVault` deployment):

```solidity
function testLossEpochMismatchClaimsAtPar() public {
    // epoch N: user requests withdraw during buffer -> lastWithdrawRequest[u] = N
    vm.prank(user); cdo.requestWithdraw(amount, AA);

    // stop epoch N with a loss: borrower funds < pendingBasis
    // NOTE: verify ordering — if deposit() bumps epochNumber to N+1 before
    // collectWithdrawFunds, the haircut is stored under N+1, not N.
    vm.prank(manager); cdo.stopEpochWithDuration(lossAmount, ...);

    // user claims: lossRecoveryPriceByEpoch[N] == 0 -> skips haircut path,
    // _claimFundedWithdrawRequest pays full withdrawsRequests[u].
    uint256 balBefore = underlying.balanceOf(user);
    vm.prank(user); cdo.claimWithdrawRequest();
    assertEq(underlying.balanceOf(user) - balBefore, fullBasis); // not haircutted

    // a second user with a correctly-tagged receipt now finds the vault
    // underfunded: their claim at lossRecoveryPrice reverts on transfer.
    vm.prank(user2);
    vm.expectRevert(); // or receives < basis * lossRecoveryPrice / 1e18
    cdo.claimWithdrawRequest();
}
```

**Caveat:** the exploit's viability hinges on the exact ordering of `epochNumber += 1` inside `deposit()` relative to `collectWithdrawFunds`/`finalizeDefaultRecovery` in `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration`/`finalizeDefault`, which I could not fully trace within the available context. If the counter bump always precedes the loss write and requests are always tagged pre-bump, the off-by-one is systematic and every loss-adjusted/defaulted receipt escapes its haircut; if the indices happen to align, the residual risk is only for cross-epoch pending receipts. This ordering must be confirmed in the PoC before treating the finding as valid.
