### Title
Missing in-progress epoch guard lets `startEpoch` run while the previous epoch was never stopped, skipping settlement of pending withdraw receipts - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.startEpoch` never checks `isEpochRunning`. It only verifies that `block.timestamp >= epochEndDate + bufferPeriod`, the pool is not closed, and the borrower is not defaulted. Once the buffer period elapses, a new epoch can be started while the previous epoch's `stopEpoch` was never executed — the exact analog of the NEAR bug: the protocol resumes normal operation even though a prior multi-step operation (epoch settlement) was started but never completed, instead of forcing the operator to finish/resume it first.

### Finding Description
At `contracts/IdleCDOEpochVariant.sol:233-239`, the gate is:

```solidity
_checkNotAllowed(defaulted || block.timestamp < (epochEndDate + bufferPeriod) || _epochDuration == 0);
```

There is no `isEpochRunning` check. The unstated invariant is that `stopEpoch`/`stopEpochWithDuration` is always called before the next `startEpoch`, because only `_stopEpoch` performs the settlement steps:

- pulls `_amountToPullFromBorrower + _pendingWithdraws` from the borrower (`getFundsFromBorrower`, line 408),
- funds pending receipts via `_strategy.collectWithdrawFunds(_pendingWithdraws)` (line 410),
- accrues interest into tranche prices via `_updateAccounting` (line 436),
- resets `isEpochRunning`, `expectedEpochInterest`, and `pendingWithdrawFees` (lines 474-476).

If `stopEpoch` is never called (operator error, stuck `onStopEpoch` retries in programmable mode, or a forced sequencing choice), `startEpoch` at line 244 still sets `isEpochRunning = true` (already true — silently overwriting the unfinished state), recomputes `expectedEpochInterest` at line 262 using stale `pendingWithdrawFees` from the unsettled epoch, sets a fresh `epochEndDate`, and pushes `lastEpochInterest + totEpochDeposits` to the strategy at line 274. The receipts recorded in `IdleCreditVault.pendingWithdraws` from the skipped epoch were never funded by `collectWithdrawFunds`, and the borrower is never asked to repay the skipped epoch's `expectedEpochInterest` — that interest liability is silently dropped when `expectedEpochInterest` is overwritten.

Note: I could not fully verify inside `IdleCreditVault` whether `claimWithdrawRequest` gates on `epochNumber` incremented at `startEpoch` vs. at `collectWithdrawFunds`. If receipt maturity is keyed to epoch starts, users holding receipts from the skipped epoch could claim against cash that was never collected for them — draining funds earmarked for instant-withdraw funding or buffer deposits held in the strategy — i.e., direct theft between receipt holders. If maturity is keyed to stops, the impact is at minimum an indefinite freeze of those receipts plus permanent loss of the skipped epoch's interest to LPs.

### Impact Explanation
- Pending withdraw receipts from the unfinished epoch are never funded at the epoch boundary they were priced for; depending on `IdleCreditVault` epoch accounting, claims either pay out against unrelated strategy balances (theft from other LPs/receipt holders) or remain unclaimable until a later stop — a temporary-to-permanent freeze with no recovery path short of a manual reconcile.
- The skipped epoch's `expectedEpochInterest` is overwritten at line 262, so the borrower keeps one full epoch+buffer of interest that was owed to tranche holders — a quantified solvency/fair-yield break equal to `_calcInterest(getContractValue())` for one period.
- Stale `pendingWithdrawFees` are folded into the new `expectedEpochInterest`, corrupting the next settlement's fee accounting.

### Likelihood Explanation
Requires a privileged caller (owner/manager) to invoke `startEpoch` after `epochEndDate + bufferPeriod` without a prior `stopEpoch`. The honest-privileged-actor assumption limits this to operational error rather than malice, but the contract explicitly comments that the guard relies on `epochEndDate` being set "and epoch is not running" — an assumption that is false once the buffer window passes, which is precisely when the operator is most likely to retry after a failed/stuck stop. The NEAR fix exists for exactly this operational-error scenario.

### Recommendation
Add an explicit in-progress guard in `startEpoch`, e.g. extend line 239 to also revert when `isEpochRunning` is true, so that an unfinished epoch must be completed via `stopEpoch`/`stopEpochWithDuration` (or an explicit resume path) before a new epoch can begin.

```solidity
_checkNotAllowed(
  defaulted || isEpochRunning ||
  block.timestamp < (epochEndDate + bufferPeriod) || _epochDuration == 0
);
```

Also consider asserting `IdleCreditVault(strategy).pendingWithdraws() == 0` or documenting that a skipped stop is impossible.

### Proof of Concept
Foundry fork PoC sketch (against `test/foundry/IdleCreditVault.t.sol` fixtures):

```solidity
// Setup: deposit AA, requestWithdraw during buffer, startEpoch normally.
idleCDO.depositAA(10_000 * ONE_SCALE);
cdoEpoch.requestWithdraw(0, address(AAtranche)); // creates pendingWithdraws + pendingWithdrawFees
vm.prank(manager);
cdoEpoch.startEpoch();

// BUG: warp past epochEndDate + bufferPeriod WITHOUT calling stopEpoch.
vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() + 1);

// startEpoch succeeds even though isEpochRunning is still true and
// collectWithdrawFunds was never called for the previous epoch's receipts.
vm.prank(manager);
cdoEpoch.startEpoch(); // does not revert; expectedEpochInterest overwritten

// Observe: previous epoch interest liability dropped; pendingWithdraws still
// unfunded (no collectWithdrawFunds ran), and pendingWithdrawFees were
// re-added into the new expectedEpochInterest.
assertGt(IdleCreditVault(address(strategy)).pendingWithdraws(), 0);
```

Caveat: whether this escalates from accounting corruption/frozen receipts to direct payout theft depends on `IdleCreditVault`'s `claimWithdrawRequest` epoch-maturity check, which I was unable to read in this session; that file should be inspected before final severity assignment.
