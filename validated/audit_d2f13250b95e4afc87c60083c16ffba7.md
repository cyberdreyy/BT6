### Title
Missing `rewards_pool` sufficiency guard in `redeem_fungible_staked_sui` causes permanent fund lock for `FungibleStakedSui` holders — (`crates/sui-framework/packages/sui-system/sources/staking_pool.move`)

---

### Summary

`staking_pool::redeem_fungible_staked_sui` calls `pool.rewards_pool.split(rewards_amount)` without first capping `rewards_amount` to the actual available balance. The sibling function `withdraw_rewards` acknowledges the same scenario with a `TODO` comment and guards against it with `.min(pool.rewards_pool.value())`. The missing guard in `redeem_fungible_staked_sui` causes the transaction to abort whenever the computed `rewards_amount` exceeds the pool's actual `rewards_pool` balance — a condition that can arise from accumulated integer-division rounding. For inactive validator pools (which never receive new reward deposits), this abort is permanent, locking the user's `FungibleStakedSui` tokens indefinitely.

---

### Finding Description

`withdraw_rewards` (the path taken by `request_withdraw_stake`) explicitly handles the case where the rewards pool balance is less than the calculated reward:

```move
// staking_pool.move:436-440
// This may happen when we are withdrawing everything from the pool and
// the rewards pool balance may be less than reward_withdraw_amount.
// TODO: FIGURE OUT EXACTLY WHY THIS CAN HAPPEN.
reward_withdraw_amount = reward_withdraw_amount.min(pool.rewards_pool.value());
pool.rewards_pool.split(reward_withdraw_amount)
``` [1](#0-0) 

`redeem_fungible_staked_sui` takes a different code path and has no equivalent guard:

```move
// staking_pool.move:220-221
let mut sui_out = fungible_staked_sui_data.principal.split(principal_amount);
sui_out.join(pool.rewards_pool.split(rewards_amount));   // ← no .min() cap
``` [2](#0-1) 

`rewards_amount` is produced by `calculate_fungible_staked_sui_withdraw_amount`, which derives it from the stored exchange rate via `mul_div` (floor division):

```move
// staking_pool.move:257-261
let rewards_withdraw_amount = mul_div!(
    fungible_staked_sui_value,
    total_rewards,
    fungible_staked_sui_data_total_supply,
);
``` [3](#0-2) 

The exchange-rate-derived `total_rewards` can exceed `pool.rewards_pool.value()` because `pool.sui_balance` (used to build the exchange rate) is updated by integer arithmetic in `process_pending_stake` and `process_pending_stake_withdraw`, while `rewards_pool` holds the actual SUI. Accumulated rounding means `sui_balance` can be 1–2 MIST higher than `principal + rewards_pool.value()`, making `rewards_amount` exceed the real balance.

`balance::split` asserts `self.value >= value` and aborts with `ENotEnough` when the condition is violated: [4](#0-3) 

The public entry point is `sui_system::redeem_fungible_staked_sui`, callable by any ordinary SUI holder who owns a `FungibleStakedSui` object:

```move
// sui_system.move:286-292
public fun redeem_fungible_staked_sui(
    wrapper: &mut SuiSystemState,
    fungible_staked_sui: FungibleStakedSui,
    ctx: &TxContext,
): Balance<SUI> {
    wrapper.load_system_state_mut().redeem_fungible_staked_sui(fungible_staked_sui, ctx)
}
``` [5](#0-4) 

---

### Impact Explanation

When the abort fires, the entire transaction is rolled back, so the `FungibleStakedSui` object is not destroyed. However, the user cannot redeem it:

- **Active pool**: temporary lock until the next epoch's `deposit_rewards` call adds enough SUI to cover the rounding gap.
- **Inactive pool**: `deposit_rewards` is never called again after deactivation. The rounding gap is permanent, so the user's `FungibleStakedSui` tokens are permanently unredeemable — a permanent fund lock matching the Medium impact class.

The `validator_set::redeem_fungible_staked_sui` explicitly supports inactive pools:

```move
// validator_set.move:357-360
} else {
    // This is an inactive pool.
    assert!(self.inactive_validators.contains(staking_pool_id), ENoPoolFound);
    self.inactive_validators[staking_pool_id].load_validator_maybe_upgrade()
};
``` [6](#0-5) 

This confirms the function is intended to work on inactive pools, yet the missing guard makes it permanently broken for them when rounding occurs.

---

### Likelihood Explanation

The `withdraw_rewards` `TODO` comment confirms the developers have already observed this condition in practice. The same arithmetic path (`get_sui_amount` → `mul_div` floor division) is used in both functions. Any pool where the last or near-last `FungibleStakedSui` holder redeems after the pool becomes inactive is susceptible. The rounding gap is at most a few MIST, but `balance::split` is strict and will abort on any positive discrepancy.

---

### Recommendation

Apply the same `.min()` cap used in `withdraw_rewards`:

```move
// staking_pool.move:220-221 — proposed fix
let mut sui_out = fungible_staked_sui_data.principal.split(principal_amount);
let capped_rewards = rewards_amount.min(pool.rewards_pool.value());
sui_out.join(pool.rewards_pool.split(capped_rewards));
```

This mirrors the existing guard at line 439 and is consistent with the acknowledged invariant that the rewards pool can be slightly less than the exchange-rate-derived amount. [7](#0-6) 

---

### Proof of Concept

1. Validator pool is active. Alice stakes 1 000 000 001 MIST and receives `StakedSui`.
2. One epoch passes with 1 000 000 000 MIST in rewards deposited. Exchange rate becomes `sui_amount = 3_000_000_001, pool_token_amount = 1_500_000_000` (confirmed by the existing test at line 421–422).
3. Alice calls `convert_to_fungible_staked_sui`; she receives `FungibleStakedSui { value: 500_000_000 }` due to floor rounding (confirmed by the test comment "rounding!" at line 428).
4. The validator is deactivated. No further `deposit_rewards` calls occur.
5. Alice calls `redeem_fungible_staked_sui`. `calculate_fungible_staked_sui_withdraw_amount` computes `rewards_amount` from the stored exchange rate. Due to the rounding introduced in step 3, `rewards_amount` can exceed `pool.rewards_pool.value()` by 1 MIST.
6. `pool.rewards_pool.split(rewards_amount)` aborts with `ENotEnough`.
7. Alice's `FungibleStakedSui` tokens are permanently unredeemable because the inactive pool will never receive new rewards.

The existing test at line 435–437 documents that this path "used to error" and was fixed for the principal side, but the rewards-pool sufficiency check was never added: [8](#0-7)

public(package) fun redeem_fungible_staked_sui(
    pool: &mut StakingPool,
    fungible_staked_sui: FungibleStakedSui,
    ctx: &TxContext,
): Balance<SUI> {
    let FungibleStakedSui { id, pool_id, value } = fungible_staked_sui;
    assert!(pool_id == object::id(pool), EWrongPool);

    id.delete();

    let latest_exchange_rate = pool.pool_token_exchange_rate_at_epoch(ctx.epoch());
    let fungible_staked_sui_data: &mut FungibleStakedSuiData =
        &mut pool.extra_fields[FungibleStakedSuiDataKey {}];

    let (
        principal_amount,
        rewards_amount,
    ) = latest_exchange_rate.calculate_fungible_staked_sui_withdraw_amount(
        value,
        fungible_staked_sui_data.principal.value(),
        fungible_staked_sui_data.total_supply,
    );

    fungible_staked_sui_data.total_supply = fungible_staked_sui_data.total_supply - value;

    let mut sui_out = fungible_staked_sui_data.principal.split(principal_amount);
    sui_out.join(pool.rewards_pool.split(rewards_amount));

    pool.pending_total_sui_withdraw = pool.pending_total_sui_withdraw + sui_out.value();
    pool.pending_pool_token_withdraw = pool.pending_pool_token_withdraw + value;

    sui_out
}
```
