### Title
Stale per-epoch instant-withdraw receipts are never cleared on the funded claim path, corrupting default recovery accounting - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The kernel bug is a missing `iso_exit()` on unload: a registration made at init is never unregistered, so stale state corrupts the next init. The analog in `IdleCreditVault` is identical in shape: `requestInstantWithdraw` "registers" a receipt in `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`, but the normal funded claim path `claimInstantWithdrawRequest` only clears the aggregate `instantWithdrawsRequests[user]` — it never unregisters the per-epoch entries. If the epoch later defaults and is finalized in the *same* `epochNumber`, the stale entries are counted again in the recovery basis and in the prefunded reserve, inflating `defaultRecoveryReserve` with funds that were already paid out.

### Finding Description
`requestInstantWithdraw` writes three counters: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` (plus `pendingInstantWithdraws`). [1](#0-0) 

When the CDO funds the request via `collectInstantWithdrawFunds`, only `pendingInstantWithdraws` is decremented. [2](#0-1) 

`claimInstantWithdrawRequest` then pays the user and zeroes only the aggregate mapping — the per-epoch receipt and per-epoch claim total remain permanently set. [3](#0-2) 

The only place those per-epoch entries are cleared is `_claimDefaultedInstantWithdrawRequest`, which runs once during post-default claims — too late, because finalization already consumed the stale values. [4](#0-3) 

At finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0`, and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as already-held reserve. A claimed-and-paid receipt of amount `X` therefore inflates both `totalBasis` and `reserveAmount` by `X` of underlying that no longer exists in the strategy. [5](#0-4) [6](#0-5) 

### Impact Explanation
`defaultRecoveryPrice = reserveAmount / totalBasis` uses the phantom `X` on both sides, but only `reserveAmount` maps to real transfers: `_transferDefaultRecovery` decrements `defaultRecoveryReserve` and pushes underlying to claimants. Since `X` was already paid out to the first claimant, the reserve overstates the strategy's actual backing by `X`. Defaulted-epoch and post-default claimants can collectively withdraw `X` more than the recovery fund holds — the excess is drained from strategy underlying belonging to active LPs, or the final claims revert, permanently freezing the last claimants' recovery share. Loss is quantified exactly by the stale claimed amount `X`.

Additionally, the stale `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` exceeds the cleared `instantWithdrawsRequests[user]` for that user, so `instantWithdrawsRequests[_user] -= claimBasis` underflows and reverts — permanently blocking that user's `claimInstantWithdrawRequest`.

### Likelihood Explanation
Requires: (1) instant-withdraw requests enabled, (2) a user whose instant receipt is funded and claimed inside the same epoch, (3) at least one other instant request left unfunded so `pendingInstantWithdraws != 0` at finalization, and (4) a borrower default finalized in that same epoch. All steps use only honest privileged calls (fund via `getInstantWithdrawFunds`, `finalizeDefault`) and an unprivileged claimer. `epochNumber` does not change within an epoch, so the stale registration lands exactly on `defaultRecoveryEpoch`. No existing guard stops it: `_transferFundedClaim`'s reserve check runs against the pre-finalization reserve, and nothing validates `instantWithdrawClaimsByEpoch` consistency at finalization.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch entries alongside the aggregate: record the request epoch per user (or iterate/write `instantWithdrawsRequestsByEpoch[_user][epochNumber] -= amount` and `instantWithdrawClaimsByEpoch[epochNumber] -= amount`). The claim needs the request's epoch stored per user (e.g. an `instantWithdrawRequestEpoch[user]` marker set in `requestInstantWithdraw`) since `epochNumber` may differ at claim time. Alternatively, zero the entries in `collectInstantWithdrawFunds` at funding time if receipt-per-epoch ownership is only needed while unfunded.

### Proof of Concept
Foundry fork PoC (modeled on `test/foundry/IdleCreditVault.t.sol` helpers such as `_depositWithUser`, `_startEpochAndCheckPrices`, `_getInstantFunds`, `_checkDefault`):

```solidity
function testStaleInstantReceiptCorruptsDefaultRecovery() external {
    // enable instant withdraws
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(delay, delta, true);

    address alice = makeAddr('alice'); // funded instant claimer
    address bob   = makeAddr('bob');   // unfunded instant claimer
    _depositWithUser(alice, 10_000e6, true);
    _depositWithUser(bob,   10_000e6, true);

    _startEpochAndCheckPrices(0);

    // Alice requests instant X and gets funded inside the same epoch
    vm.prank(alice);
    cdoEpoch.requestInstantWithdraw(5_000e6, address(AAtranche)); // exact fn name per CDO API
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    _getInstantFunds();               // collectInstantWithdrawFunds(5_000e6)
    vm.prank(alice);
    cdoEpoch.claimInstantWithdrawRequest(); // paid; but ByEpoch entries stay stale

    IdleCreditVault v = IdleCreditVault(address(strategy));
    uint256 epoch = v.epochNumber();
    assertEq(v.instantWithdrawsRequestsByEpoch(alice, epoch), 5_000e6, 'stale per-epoch receipt');
    assertEq(v.instantWithdrawClaimsByEpoch(epoch), 5_000e6, 'stale epoch total');

    // Bob requests instant Y in the SAME epoch; it stays unfunded
    vm.prank(bob);
    cdoEpoch.requestInstantWithdraw(5_000e6, address(AAtranche));
    assertEq(v.pendingInstantWithdraws(), 5_000e6);

    // borrower defaults; owner finalizes with R recovered
    _checkDefault();
    uint256 recovered = 8_000e6;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // reserve was inflated by Alice's already-claimed 5_000e6
    assertEq(v.defaultRecoveryReserve(), recovered + 5_000e6, 'phantom prefunded reserve');
    // strategy only holds `recovered` (+ any unrelated underlying); last claims revert or drain LP funds
    assertLt(underlying.balanceOf(address(strategy)), v.defaultRecoveryReserve(), 'reserve exceeds real backing');
}
```

Expected result: `defaultRecoveryReserve` exceeds actual strategy underlying by Alice's claimed 5_000e6, and Alice's subsequent `claimInstantWithdrawRequest` calls revert on the underflow in `instantWithdrawsRequests[_user] -= claimBasis`.
