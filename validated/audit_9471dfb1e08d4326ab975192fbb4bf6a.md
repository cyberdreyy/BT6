### Title
Cross-workflow response cache confusion in Gateway HTTP Action handler due to Hash() ignoring WorkflowID - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The external report describes a class of bug where stale/unvalidated data is used as if it were fresh and correctly scoped, causing miscalculation across unrelated consumers. The applicable analog in this repository is in the Gateway's HTTP Action response cache: the cache key is derived from `OutboundHTTPRequest.Hash()`, which the codebase's own tests confirm intentionally excludes `WorkflowID`, while only including `WorkflowOwner`. This contradicts the documented design intent ("Cache Key: Generated from workflow ID and request hash" / "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage") and results in cached HTTP action responses being shared across different workflows that happen to share the same `WorkflowOwner` and issue requests with identical method/URL/headers/body.

### Finding Description
The `responseCache` used by the internet-facing gateway's HTTP capability handler caches outbound HTTP action responses keyed by `req.Hash()`: [1](#0-0) 

The `Fetch`/`Set`/`isExpiredOrNotCached` methods all use this single hash as the cache key without any additional per-workflow namespacing: [2](#0-1) [3](#0-2) 

The unit tests explicitly document that `Hash()` is *designed* to ignore `WorkflowID` — "Hash should be the same regardless of WorkflowID" — while it does vary by `WorkflowOwner`: [4](#0-3) 

However, the module's own `README.md` documents the intended security property as workflow-level isolation, not owner-level isolation: "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage": [5](#0-4) 

Because the `OutboundHTTPRequest` (method, URL, headers, body, `WorkflowOwner`) is fully controlled/submitted by an unprivileged workflow node via the internet-facing gateway (`gatewayHandler.HandleNodeMessage` → `makeOutgoingRequest` → `responseCache.Fetch`/`Set`), any two workflows registered under the same owner (a very common scenario — a single owner running multiple concurrent workflows) that issue outbound HTTP action requests with identical request parameters will read and write the same cache entry. A response fetched (and possibly containing workflow-A-specific data returned by a third-party API keyed off request body/headers set by workflow-A) can be served to workflow B without re-fetching, and vice versa — this is exactly the "cross-user response confusion" class called out in the review criteria, and it directly maps to the root-cause pattern in the external report: data that is not properly scoped/validated (there: staleness; here: workflow identity) is trusted and reused across contexts that assumed isolation.

### Impact Explanation
This allows unauthorized cross-workflow data leakage/response confusion for workflows sharing an owner: one workflow can receive a cached HTTP action response that was actually fetched (and possibly cached with `Store=true`) on behalf of a different workflow. Since the response body is returned directly to the requesting workflow's execution and may include workflow-A-specific data (e.g., resulting from parameterized queries encoded in headers/body that are nonetheless identical byte sequences, or cache poisoning from an untrusted/malicious workflow deliberately warming the cache with a crafted response before a victim workflow requests the "same" URL), this breaks the documented workflow-isolation guarantee. This is a confidentiality/integrity issue between workflows, not simply a performance quirk, since the design document explicitly promises workflow-level isolation that the implementation does not provide.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where a single workflow owner operates multiple distinct workflows (a common and expected pattern in CRE), since no additional attacker action beyond normal workflow-node HTTP action requests is required — the cache is populated and read purely through the ordinary `HandleNodeMessage` flow that unprivileged workflow nodes are expected to invoke.

### Recommendation
Include `WorkflowID` (or workflow execution scope, matching the documented design) in `OutboundHTTPRequest.Hash()` so cache entries are correctly isolated per-workflow as the README specifies, rather than only per-owner. Add/adjust unit tests so that "different workflowID results in different Hash" replaces the current test asserting the opposite, and audit all callers relying on the current owner-only scoping assumption.

### Proof of Concept
1. Register two workflows, W1 and W2, both owned by the same `WorkflowOwner` address.
2. From W1, issue an `OutboundHTTPRequest` with `Method=GET`, `URL=https://api.example.com/data`, no distinguishing headers/body, `CacheSettings={Store:true, MaxAgeMs:600000}` via the gateway HTTP action flow (`gatewayHandler.HandleNodeMessage`).
3. The gateway fetches the response from the real endpoint and stores it in `responseCache` keyed by `req.Hash()` (method+URL+headers+body+WorkflowOwner — not WorkflowID), per [6](#0-5) .
4. From W2 (different `WorkflowID`, same `WorkflowOwner`), issue an identical `OutboundHTTPRequest` (same method/URL/headers/body) with `MaxAgeMs>0`.
5. `responseCache.Fetch` computes the same `cacheKey` (since `Hash()` ignores `WorkflowID`, as proven by [7](#0-6) ) and returns W1's cached response to W2 without making a new outbound HTTP call — demonstrating cross-workflow response reuse in violation of the documented isolation guarantee.

// isExpiredOrNotCached returns true if the cached response is expired or not cached.
// IMPORTANT: this method does not lock the cache map. MUST be called with cacheMu write-locked.
func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.
- **Cache TTL**: Configurable, default 10 minutes
- **Cache Key**: Generated from workflow ID and request hash
- **Cache Invalidation**: Time-based expiration with periodic cleanup
- **Cache Strategy**: All cacheable responses are cached; Non-zero `CacheSettings.MaxAgeMs` determines whether to return a cached value or make a fresh request
- **Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage
