### Title
Claimed instant-withdraw receipts leave stale per-epoch basis that is re-read as a defaulted-epoch claim, inflating recovery basis and bricking claims - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The MongoDB bug class is *reading residual/uninitialized memory that was never cleared*. The closest analog in `IdleCreditVault` is the instant-withdraw ledger: `claimInstantWithdrawRequest` pays out and zeroes only the aggregate `instantWithdrawsRequests[_user]`, but never clears the per-epoch entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` that were written in `requestInstantWithdraw`. That stale residue is later re-read by default-recovery accounting as if it were a live defaulted-epoch claim.

### Finding Description
`requestInstantWithdraw` records both the aggregate and per-epoch basis: [1](#0-0) 

`claimInstantWithdrawRequest` burns and pays the aggregate, but leaves `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` non-zero forever: [2](#0-1) 

Only `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws`; nothing ever decrements the per-epoch ledgers on a normal (funded) claim.

When the borrower defaults while `epochNumber` is still that same epoch (default finalization keys off the *current* `epochNumber`, and the design intends "current-epoch instant receipts" to be included), the stale residue is consumed twice:

1. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` — including amounts already paid out — into `totalBasis` used for `recoveryPrice` in `finalizeDefaultRecovery`: [3](#0-2) [4](#0-3) 

2. `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` and counts that phantom amount as *already-held* reserve, inflating `reserveAmount`/`recoveryPrice` without any backing tokens: [5](#0-4) 

3. After finalization, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, which still contains the already-claimed amount plus any new same-epoch request. Since `byEpoch[user][E] > instantWithdrawsRequests[user]` whenever a stale entry exists, `instantWithdrawsRequests[_user] -= claimBasis` underflows and reverts — permanently bricking `claimInstantWithdrawRequest` for that user: [6](#0-5) 

`instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch` are never cleared anywhere in the contract (only decremented on the defaulted-claim path itself), so the stale read is guaranteed once the epochs collide.

### Impact Explanation
- **Reserve insolvency**: `prefundedReserve` counts already-paid instant claims as held backing, so `defaultRecoveryReserve`/`recoveryPrice` are set as if more underlying exists than the strategy actually holds. Later claimants' `underlyingToken.safeTransfer` calls fail once the real balance is exhausted — direct insolvency of the recovery reserve proportional to all instant claims paid out during the defaulted epoch.
- **Permanent freezing**: any user whose `instantWithdrawsRequestsByEpoch` has stale residue in the default epoch has `claimInstantWithdrawRequest` revert on underflow forever (the state is never cleared), permanently freezing their legitimate receipt and their share of the reserve.
- Alternatively, if no prefunded remainder exists the inflated `totalBasis` in `defaultPendingClaimBasis` dilutes `recoveryPrice`, systematically underpaying every default claimant.

### Likelihood Explanation
Conditional but realistic. Requires: (a) an unprivileged user performs an instant withdrawal that is funded and claimed during a running epoch — the intended instant-withdraw flow; (b) the borrower defaults and `finalizeDefaultRecovery` runs while `epochNumber` still equals that receipt epoch (the code's own comments assume current-epoch instant receipts share the default epoch; if `epochNumber` were bumped on a defaulted `stopEpoch`, the whole `instantWithdrawClaimsByEpoch[epochNumber]` accounting would never match any receipt, which the passing tests contradict). No privileged actor misbehavior is needed; honest owner/manager calls suffice. One caveat I could not fully confirm within available context: the exact `epochNumber` bump ordering in `IdleCDOEpochVariant.stopEpoch` on the default path — if it increments before finalization, the stale read targets a past epoch and the impact reduces to basis dilution via `defaultPendingClaimBasis` only. A fork PoC should confirm the ordering.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers alongside the aggregate: subtract `amount` from `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` (or track and delete the user's per-epoch entries). Ensure `instantWithdrawClaimsByEpoch[epoch]` always equals the sum of *unclaimed* per-epoch receipts so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only see live claims.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
