### Title
`depositDuringEpoch` credits and forwards the stated `_amount` instead of the actual amount received, breaking accounting for fee-on-transfer underlyings - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`depositDuringEpoch` pulls the underlying with `_transferUnderlyingsFrom(msg.sender, address(this), _amount)` but never measures the received delta. All subsequent accounting — the minted tranche tokens, `expectedEpochInterest`, the `mintStrategyTokens` call and the onward transfer of `_amount` to the borrower — is computed from the *stated* `_amount`, mirroring the fee-on-transfer bug class of the external report. The normal `_deposit` path in the same codebase already demonstrates the correct pattern (balance-before/after delta), so this is an inconsistency, not a design choice.

### Finding Description
In `IdleCDOEpochVariant.depositDuringEpoch` (contracts/IdleCDOEpochVariant.sol:656-733):

```solidity
// line 685
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
...
uint256 interest = _calcInterest(_amount) * (remaining + buffer) / (epochDuration + buffer); // L693
...
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal; // L724
_mintShares(_tranche, msg.sender, _minted, _amount);                        // L725
expectedEpochInterest += interest;                                          // L728
IdleCreditVault(strategy).mintStrategyTokens(_amount);                      // L730
_transferUnderlyings(_borrower(), _amount);                                 // L732
```

If `token` charges a transfer fee `f` (e.g., USDT with its fee enabled), the vault actually receives `_amount - f`, but:

1. The depositor is minted tranche tokens worth `_amount + trancheInterest` at epoch end — i.e., principal they never fully paid plus interest on it.
2. `_transferUnderlyings(_borrower(), _amount)` sends the *full* `_amount` to the borrower, funded `f` short by the vault's existing liquidity (previous depositors' buffer balance).
3. `expectedEpochInterest` and `mintStrategyTokens(_amount)` record obligations on money that was never received.

Compare with `IdleCDO._deposit` (contracts/IdleCDO.sol:250-253) and `IdleCDOCreditVault._deposit` (contracts/IdleCDOCreditVault.sol:203-206), which mint on `_contractTokenBalance(_token) - _preBal`. The same FoT inconsistency also exists in `IdleCDOCreditVault._deposit` line 211, where `IIdleCDOStrategy(strategy).deposit(_amount)` pulls the stated `_amount` even though only `_amount - f` was received — the shortfall is silently taken from vault liquidity and minted shares reflect only the received amount, desyncing `lastNAV`/`getContractValue` from actual backing by `f` per deposit.

The existing guards do not stop this:
- `_skimDonatedAssets()` (called at L679) only removes *raw donations* before the transfer; it cannot distinguish a fee shortfall, and nothing re-measures balance after `transferFrom`.
- `isWalletAllowed` KYC gating does not help — a KYC-passing lender is a permitted attacker per scope.
- The function is reachable in the normal fixed-APR epoch-running mode (`isEpochRunning`, not `isProgrammableBorrower`, not `isAYSActive`, `block.timestamp < epochEndDate`), which is the standard operating phase.

### Impact Explanation
Every mid-epoch deposit with a fee-on-transfer underlying creates a deficit of `f` that is socialized across existing tranche holders and, at epoch end, the borrower repayment waterfall: the attacker redeems shares priced at `_amount + trancheInterest` while having paid only `_amount - f`, and the borrower received `_amount`. Net effect is a direct theft of `f` per call, repeatable each epoch — quantified loss = `fee% × deposited amount × iterations`. For a 1%-fee token configuration and repeated deposits, this can drain the entire buffer/liquidity earmarked for instant withdrawals and loss coverage, producing vault insolvency.

### Likelihood Explanation
Likelihood is medium-low and asset-dependent: it requires the credit vault's `token` to be (or become) a fee-on-transfer ERC20. USDT — a canonical underlying for private-credit vaults — contains a fee mechanism that can be enabled by its owner without any code change in this protocol. The attack path itself (`depositDuringEpoch`) is a normal user-facing flow requiring only KYC, so no privileged cooperation, timing race, or donation precondition is needed; a whitelisted lender can execute it in a single transaction during any running epoch.

### Recommendation
Measure the actual received amount and use it everywhere downstream:

```solidity
uint256 _preBal = _contractTokenBalance(token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
uint256 _received = _contractTokenBalance(token) - _preBal;
```

then compute `interest`, `_minted`, `expectedEpochInterest`, `mintStrategyTokens` and `_transferUnderlyings(_borrower(), _received)` from `_received`. Apply the same fix to `IdleCDOCreditVault._deposit` line 211 by passing the received delta to `strategy.deposit`. Alternatively, explicitly document/enforce that only non-fee-on-transfer tokens may be used as `token` (e.g., revert if `received != _amount`).
