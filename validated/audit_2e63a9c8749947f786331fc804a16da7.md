### Title
Builder payment quorum check bypassed on long payload-application delay, allowing a builder to be paid without PTC quorum - (File: specs/gloas/beacon-chain.md)

### Summary
In the Gloas (ePBS) fork, whether a builder gets paid for a revealed execution payload is supposed to depend on the Payload Timeliness Committee (PTC) reaching a `weight >= quorum` threshold, as enforced in `process_builder_pending_payments`. However, `apply_parent_execution_payload` contains a fallback branch that pays the builder unconditionally from `parent_bid.value` when the parent block is more than one epoch old, bypassing the quorum check entirely. This breaks the equality that builder payment == "PTC confirmed the payload was actually available," letting Gwei be paid to a builder who never obtained network confirmation.

### Finding Description
The normal builder-payment path is `process_builder_pending_payments`, run every epoch during `process_epoch`: [1](#0-0) 
It only queues a `builder_pending_withdrawals` entry if `payment.weight >= quorum` (the PTC quorum threshold from `get_builder_payment_quorum_threshold`); otherwise the payment is silently dropped after two epoch transitions.

The `weight` field is accumulated from PTC payload attestations (via `state.builder_pending_payments[...]`, updated by payload-attestation processing) and represents whether enough PTC members observed and confirmed the payload. This is the "correct" signal analogous to the "latest valid oracle price" in the Perennial bug — it's the value the state-transition process is supposed to rely on before paying anyone.

The bug is in `apply_parent_execution_payload`, called from `process_parent_execution_payload` whenever a following block reveals that its parent was FULL: [2](#0-1) 
Specifically:
```
if parent_epoch == get_current_epoch(state):
    payment_index = SLOTS_PER_EPOCH + parent_slot % SLOTS_PER_EPOCH
    settle_builder_payment(state, payment_index)
elif parent_epoch == get_previous_epoch(state):
    payment_index = parent_slot % SLOTS_PER_EPOCH
    settle_builder_payment(state, payment_index)
elif parent_bid.value > 0:
    # Parent is older than the previous epoch, its payment entry has been
    # evicted from builder_pending_payments. Append the withdrawal directly.
    state.builder_pending_withdrawals.append(
        BuilderPendingWithdrawal(
            fee_recipient=parent_bid.fee_recipient,
            amount=parent_bid.value,
            builder_index=parent_bid.builder_index,
        )
    )
``` [3](#0-2) 

`process_epoch` (and thus `process_builder_pending_payments`) advances deterministically with slot processing, independent of whether blocks are actually proposed: [4](#0-3) 

So if two or more epoch boundaries elapse between a block with a value-bearing bid and the next actual (non-empty) child block that references it as its parent, the `BuilderPendingPayment` entry for that slot is evicted by `process_builder_pending_payments` — correctly, without payment, if `weight < quorum` (i.e., PTC never confirmed the payload). But when the delayed child block finally arrives and confirms `bid.parent_block_hash == parent_bid.block_hash` (parent was FULL), `apply_parent_execution_payload` falls into the third branch and pays the builder unconditionally based on `parent_bid.value > 0`, with no reference to `weight` or quorum at all. The quorum-gating check that the normal path enforces is simply not reachable once the entry has already been evicted, and the code does not remember "was quorum reached" before dropping it.

This is confirmed as an intended/tested code path by the repo's own test: [5](#0-4) 
which explicitly builds a scenario "2+ epochs of missed blocks" and asserts the builder is paid via this fallback path — but it does not test/assert the PTC-quorum condition at all in that scenario, i.e., the test does not verify that the payment is contingent on the payload actually having achieved quorum.

### Impact Explanation
This breaks the intended equality "a builder is paid the bid value if and only if PTC quorum confirmed the payload was available/revealed." A builder can receive a `BuilderPendingWithdrawal` (ultimately a real Gwei payout via the withdrawal-processing pipeline) even when the network never reached PTC quorum on their payload — i.e., Gwei paid without the protocol-required authorization/condition being met. Under the categories in scope, this is a "payment ... applied that the block did not commit to [via quorum]" / Gwei paid to a party that did not earn it according to spec logic, since the PTC quorum mechanism exists specifically to prevent payment for payloads that were withheld or not properly confirmed by the committee (a core anti-withholding safeguard of ePBS design).

### Likelihood Explanation
Requires 2+ consecutive epochs of missed/empty blocks between the bid-bearing block and the next block that references it as parent (i.e., a proposer skip/liveness gap of at least ~64+ slots), combined with the payload failing to reach PTC quorum during that window (e.g., payload withheld from most of the committee, or committee members offline). This is a narrow but concrete and reachable condition — it does not require a malicious peer/coalition, only ordinary liveness gaps plus insufficient PTC attestation, both of which occur naturally on a live network. Gloas is a future/unshipped fork, so this cannot currently be exploited on mainnet, but as written the spec text contains the flaw.

### Recommendation
`apply_parent_execution_payload`'s "older than previous epoch" branch should not pay `parent_bid.value` unconditionally. Either (a) retain and check the last known `weight` for the evicted payment before falling back to direct payment, or (b) simply drop the payment (pay nothing) in this branch, matching what would have happened had `process_builder_pending_payments` had the chance to evaluate quorum, consistent with how it handles the normal case.

### Proof of Concept
1. Builder B submits a valid, signed, value-bearing (`bid.value = V > 0`) execution payload bid for the block at slot `S`; this creates `BuilderPendingPayment(weight=0, withdrawal=..., proposer_index=...)` at the appropriate slot index, per `process_execution_payload_bid`.
2. The payload is never confirmed by enough PTC members (e.g., builder withholds envelope from most of PTC, or network partition/liveness issue prevents quorum) so `payment.weight` stays `< quorum` throughout.
3. No block is proposed with parent hash referencing block `S` for 2+ full epochs (empty/skipped slots). During this time, `process_epoch` runs at each epoch boundary via `process_slots`, and `process_builder_pending_payments` evicts the entry for slot `S` without paying (since `weight < quorum`), per [6](#0-5) .
4. A proposer eventually proposes a block whose `signed_execution_payload_bid.message.parent_block_hash` equals `bid.block_hash` from block `S` (declaring the parent was FULL) and includes `parent_execution_requests` matching `parent_bid.execution_requests_root`.
5. `process_parent_execution_payload` calls `apply_parent_execution_payload`; since `parent_epoch` is now older than `get_previous_epoch(state)`, execution falls to the `elif parent_bid.value > 0` branch, appending a `BuilderPendingWithdrawal(amount=V, builder_index=B, fee_recipient=...)` unconditionally — paying builder B despite quorum never having been reached.

Confirming exactly how `weight` is incremented via payload attestations was not directly retrieved in this session (only `get_builder_payment_quorum_threshold`'s signature was seen before the tool budget was exhausted), so the precise attestation-processing code path that increments `payment.weight` should be independently verified by a reviewer with full repository access, though the eviction/quorum-check logic in `process_builder_pending_payments` and the unconditional fallback in `apply_parent_execution_payload` are directly confirmed from the cited spec text.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

def apply_parent_execution_payload(
    state: BeaconState,
    requests: ExecutionRequests,
) -> None:
    parent_bid = state.latest_execution_payload_bid
    parent_slot = state.latest_block_header.slot
    parent_epoch = compute_epoch_at_slot(parent_slot)

    assert len(requests.withdrawals) <= MAX_WITHDRAWAL_REQUESTS_PER_PAYLOAD
    assert len(requests.consolidations) <= MAX_CONSOLIDATION_REQUESTS_PER_PAYLOAD
    assert len(requests.builder_deposits) <= MAX_BUILDER_DEPOSIT_REQUESTS_PER_PAYLOAD
    assert len(requests.builder_exits) <= MAX_BUILDER_EXIT_REQUESTS_PER_PAYLOAD

    # Process execution requests from parent's payload. The execution
    # requests are processed at state.slot (child's slot), not the parent's slot.
    def for_ops(operations: Sequence[Any], fn: Callable[[BeaconState, Any], None]) -> None:
        for operation in operations:
            fn(state, operation)

    for_ops(requests.deposits, process_deposit_request)
    for_ops(requests.withdrawals, process_withdrawal_request)
    for_ops(requests.consolidations, process_consolidation_request)
    for_ops(requests.builder_deposits, process_builder_deposit_request)
    for_ops(requests.builder_exits, process_builder_exit_request)

    # Settle the builder payment
    if parent_epoch == get_current_epoch(state):
        payment_index = SLOTS_PER_EPOCH + parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_epoch == get_previous_epoch(state):
        payment_index = parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_bid.value > 0:
        # Parent is older than the previous epoch, its payment entry has been
        # evicted from builder_pending_payments. Append the withdrawal directly.
        state.builder_pending_withdrawals.append(
            BuilderPendingWithdrawal(
                fee_recipient=parent_bid.fee_recipient,
                amount=parent_bid.value,
                builder_index=parent_bid.builder_index,
            )
        )

    # Update parent payload availability and latest block hash
    state.execution_payload_availability[parent_slot % SLOTS_PER_HISTORICAL_ROOT] = Boolean(True)
    state.latest_block_hash = parent_bid.block_hash

@with_gloas_and_later

def test_builder_payment_after_missed_epochs(spec, state):
    """
    Test that a builder is correctly charged when their canonical payload
    is processed after 2+ epochs of missed blocks.
    """
    # Advance to get finalization
    for _ in range(4):
        next_epoch_with_full_participation(spec, state)
    assert state.finalized_checkpoint.epoch == 2

    # Build Block 1 with a non-zero value bid from a builder
    block_1 = build_empty_block_for_next_slot(spec, state)
    builder_index = 0
    value = spec.Gwei(1000000)  # 0.001 ETH
    fee_recipient = b"\xab" * 20
    block_hash = spec.Hash32(b"\x42" * 32)

    bid = block_1.body.signed_execution_payload_bid.message
    bid.block_hash = block_hash
    bid.builder_index = builder_index
    bid.value = value
    bid.fee_recipient = fee_recipient
    bid.execution_requests_root = spec.hash_tree_root(spec.ExecutionRequests())

    # Sign the bid with the builder's private key
    signature = spec.get_execution_payload_bid_signature(
        state, bid, builder_privkeys[builder_index]
    )
    block_1.body.signed_execution_payload_bid = spec.SignedExecutionPayloadBid(
        message=bid,
        signature=signature,
    )

    # Ensure builder can cover the bid
    state.builders[builder_index].balance = spec.MIN_DEPOSIT_AMOUNT + value

    yield "pre", state

    # Process Block 1 — creates a pending payment for the builder
    signed_block_1 = state_transition_and_sign_block(spec, state, block_1)

    # Verify pending payment was created
    payment_idx = spec.SLOTS_PER_EPOCH + block_1.slot % spec.SLOTS_PER_EPOCH
    payment = state.builder_pending_payments[payment_idx]
    assert payment.withdrawal.amount == value
    assert payment.withdrawal.builder_index == builder_index
    assert payment.weight == 0

    pre_builder_balance = state.builders[builder_index].balance

    # Build Block 2 with 2+ epochs of missed slots. During the slot advancement,
    # process_builder_pending_payments runs at each epoch boundary:
    #   1st boundary: shifts payment from second half to first half
    #   2nd boundary: checks quorum on first half — weight 0 < quorum → evicted
    # When Block 2 is processed, parent is FULL so apply_parent_execution_payload
    # runs. Since parent_epoch is older than previous_epoch, payment_index is None.
    # The fix creates the withdrawal directly from the bid in this case.
    block_1_epoch = spec.compute_epoch_at_slot(block_1.slot)
    block_2_slot = spec.compute_start_slot_at_epoch(block_1_epoch + 2) + 1
    block_2 = build_empty_block(spec, state, slot=block_2_slot)
    block_2.body.signed_execution_payload_bid.message.parent_block_hash = block_hash
    signed_block_2 = state_transition_and_sign_block(spec, state, block_2)

    yield "blocks", [signed_block_1, signed_block_2]
    yield "post", state

    # Verify apply_parent_execution_payload actually ran (parent was FULL)
    parent_slot_index = bid.slot % spec.SLOTS_PER_HISTORICAL_ROOT
    assert state.execution_payload_availability[parent_slot_index]

    # Verify the builder was charged — balance decreased by the bid value
    assert state.builders[builder_index].balance == pre_builder_balance - value
