## Title
Writable-account cost-tracker griefing enables a cheap "gas war" DoS against victims needing to land a defensive transaction - (File: `cost-model/src/cost_tracker.rs`)

### Summary
The Kleidi report describes an asymmetric-cost griefing attack: an attacker can flood a protocol with many cheap malicious transactions/proposals, forcing the victim to spend disproportionately more resources to cancel/block them, ultimately creating a race the victim cannot always win because gas/cost is limited relative to the reward. Agave has a directly analogous per-account resource-exhaustion primitive: the leader-side `CostTracker` enforces a hard per-writable-account compute-unit budget (`MAX_WRITABLE_ACCOUNT_UNITS = 24_000_000`) per block [1](#0-0) , shared by every transaction that write-locks that account regardless of whether the transaction ultimately succeeds [2](#0-1) . An attacker who only needs to pay the base signature fee and a minimal write-lock cost can flood a hot/shared account to saturate this per-account limit for consecutive blocks, blocking any victim transaction that also writes to that account (e.g. a "cancel", "withdraw", or "pause" instruction) from being included — mirroring the report's gas-war/DoS dynamic where the attacker's cost-per-attempt is far lower than the resource the victim must burn to get a defensive transaction through.

### Finding Description
`CostModel::get_write_lock_cost` charges a fixed `WRITE_LOCK_UNITS` (300 CU) per write-locked account regardless of the instruction's actual behavior, and this cost is charged even when the account write-lock is on a demoted/system account, confirming the charge is driven purely by locking, not real work [3](#0-2) [4](#0-3) .

`CostTracker::would_fit`/`add_transaction_cost` enforce and accumulate a per-writable-account cost against `CostTrackerLimits::account_cost` (default `MAX_WRITABLE_ACCOUNT_UNITS`), and any transaction whose cumulative write-lock cost on a given account would exceed that ceiling is rejected with `WouldExceedAccountMaxLimit` for the remainder of that block [2](#0-1) [5](#0-4) . Because this check runs per writable account irrespective of the transaction's payload/success, any unprivileged sender who knows a target account's pubkey can submit many cheap, minimally-instructioned transactions that write-lock that account, driving its cumulative cost toward the 24M CU ceiling within a single block, and repeating this across consecutive blocks the attacker controls timing for (since they only need to keep re-submitting cheap transactions each slot).

`banking_stage::consumer` applies this same tracker when packing/committing transactions (`try_add_processed_transaction_costs`), and a `WouldExceedAccountMaxLimit`/`WouldExceedMaxBlockCostLimit` failure causes the transaction to be treated as retryable rather than dropped, meaning a victim's transaction targeting a contended account is repeatedly bumped to later blocks while the attacker keeps re-flooding [6](#0-5) . The forwarding/prioritization logic explicitly computes priority as reward divided by cost [7](#0-6) , so the only way for the victim to overcome sustained flooding of "their" account is to keep raising the priority fee attached to their own transaction across blocks — an explicit "gas war," directly analogous to the Kleidi report's core griefing dynamic where the defender must keep outbidding the attacker in a resource competition that the attacker can seed far more cheaply than the value at stake.

### Impact Explanation
If a victim protocol relies on a single shared writable account (e.g., a vault, a pause/config account, or a nonce account) to submit a defensive/cancel transaction, an attacker with modest funds (enough to pay signature fees and small priority fees across a few blocks) can occupy that account's entire per-block cost budget with garbage write-locking transactions, delaying the victim's time-sensitive defensive transaction by one or more blocks. If the victim's exploit window (e.g., before an attacker's competing state-changing transaction lands) is tight, this can allow the attacker's own competing transaction on the same account to land first, exactly mirroring the Kleidi "attacker keeps outracing the defender's cancel." This is a liveness/censorship-style griefing rather than a direct fund-theft primitive in the base protocol, so impact is bounded by how much value is gated behind a single hot account's inclusion timing.

### Likelihood Explanation
The attack requires only ordinary unprivileged transactions (any signer, minimal balance for signature fees) and knowledge of the target account's pubkey — no special permissions, no compromised keys are needed, unlike the original Kleidi scenario which required leaked owner keys. This makes the analog easier to mount than the original report, though it is still probabilistic/multi-block (the attacker must win the leader's cost-tracker race each slot) and the base per-account limit (24M CU, i.e. up to 80,000 write-locking transactions worth of cost per account per block) makes flooding a specific account non-trivial but plausible for a sustained/funded attacker, particularly on a heavily-used hot account.

### Recommendation
Consider decoupling "per-account congestion" from a single hard global ceiling shared indiscriminately among all senders — e.g., reserving per-account cost headroom for a small number of high-priority-fee transactions, or exposing/encouraging application-level designs (e.g., avoid single hot "pause" or "cancel" accounts) that are less susceptible to this pattern. At minimum, this is a known modeled limit rather than a bug per se; documentation/guidance should flag that any protocol relying on timely inclusion of a transaction against a specific account should be aware this account's per-block CU budget can be exhausted by unprivileged flooding, and should design fee/priority strategies (e.g., automatic fee escalation) accordingly.

### Proof of Concept
The existing unit tests already demonstrate the mechanics: `test_cost_tracker_chain_reach_limit` shows that once an account's `account_cost` budget is consumed, a second transaction targeting the same account is rejected within the same block [8](#0-7) , and `test_cost_tracker_try_add_is_atomic` shows the same rejection when a shared account approaches its per-block cost ceiling [9](#0-8) . An attacker can reproduce the griefing scenario by repeatedly submitting minimal-instruction transactions that write-lock the victim's target account until `cost_by_writable_accounts[victim_account]` approaches `MAX_WRITABLE_ACCOUNT_UNITS`, at which point the victim's own transaction touching that account will be rejected with `TransactionError::WouldExceedMaxAccountCostLimit` for that block, per the mapping in `CostTrackerError -> TransactionError` [10](#0-9) .

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // check each account against account_cost_limit,
        for account_key in tx_cost.writable_accounts() {
            match self.cost_by_writable_accounts.get(account_key) {
                Some(chained_cost) => {
                    if chained_cost.saturating_add(cost) > self.limits.account_cost {
                        return Err(CostTrackerError::WouldExceedAccountMaxLimit);
                    } else {
                        continue;
                    }
                }
                None => continue,
            }
        }

        Ok(())
    }

    fn test_cost_tracker_try_add_is_atomic() {
        let acct1 = Pubkey::new_unique();
        let acct2 = Pubkey::new_unique();
        let acct3 = Pubkey::new_unique();
        let cost = 100;
        let account_max = cost * 2;
        let block_max = account_max * 3; // for three accts

        let mut testee = CostTracker::new(account_max, block_max);

        // case 1: a tx writes to 3 accounts, should success, we will have:
        // | acct1 | $cost |
        // | acct2 | $cost |
        // | acct3 | $cost |
        // and block_cost = $cost

            let tx_cost = simple_transaction_cost(&transaction, cost);
            assert!(testee.try_add(&tx_cost).is_ok());
            let (_costliest_account, costliest_account_cost) = testee.find_costliest_account();
            assert_eq!(cost, testee.block_cost());
            assert_eq!(3, testee.cost_by_writable_accounts.len());
            assert_eq!(cost, costliest_account_cost);
        }

        // case 2: add tx writes to acct2 with $cost, should succeed, result to
        // | acct1 | $cost |
        // | acct2 | $cost * 2 |
        // | acct3 | $cost |
        // and block_cost = $cost * 2

            let transaction = WritableKeysTransaction::new(vec![acct2]);
            let tx_cost = simple_transaction_cost(&transaction, cost);
            assert!(testee.try_add(&tx_cost).is_ok());

            assert_eq!(cost * 2, testee.block_cost());
            assert_eq!(3, testee.cost_by_writable_accounts.len());
            assert_eq!(cost * 2, costliest_account_cost);
            assert_eq!(acct2, costliest_account);

        // we should still have:

            assert_eq!(3, testee.cost_by_writable_accounts.len());

    /// Returns `(added_transaction_costs, retryable_indexes)`.
    ///
    /// `added_transaction_costs` has one entry per input transaction. `Some(cost)` means
    /// the processed transaction's actual cost was added to the cost tracker.
    /// `None` means no cost added for that transaction due to: the transaction was
    /// not processed, its cost was rejected by the cost tracker, a prior
    /// cost-tracker rejection canceled the rest of the batch, or an
    /// all-or-nothing cost failure rolled back the batch.
    fn try_add_processed_transaction_costs<'a, Tx: TransactionWithMeta>(
        bank: &Bank,
        transactions: &'a [Tx],
        mut transaction_costs: Vec<Option<TransactionCost<'a, Tx>>>,
        processing_results: &mut [TransactionProcessingResult],
        processed_counts: &mut ProcessedTransactionCounts,
        error_counters: &mut TransactionErrorMetrics,
        all_or_nothing: bool,
    ) -> (Vec<Option<TransactionCost<'a, Tx>>>, Vec<RetryableIndex>) {
        let mut retryable_transaction_indexes = Vec::with_capacity(processing_results.len());
        let mut all_or_nothing_error = None;
        let mut remaining_batch_error = None;
        let mut cost_tracker = bank.write_cost_tracker().unwrap();

        for (index, transaction_cost) in transaction_costs.iter_mut().enumerate() {
            let Some(cost) = transaction_cost.as_ref() else {
                continue;
            };

            match cost_tracker.try_add(cost) {
                Ok(_) => {}
                Err(err) => {
                    let transaction_error = TransactionError::from(err);
                    *transaction_cost = None;
                    if all_or_nothing {
                        all_or_nothing_error = Some((index, transaction_error));
                        break;
                    } else {
                        remaining_batch_error = Some((index, transaction_error));
                        break;
                    }
                }
            }
        }

        if let Some((failed_index, transaction_error)) = all_or_nothing_error {
            for transaction_cost in transaction_costs[..failed_index].iter().flatten() {
                cost_tracker.remove(transaction_cost);
            }
            transaction_costs.iter_mut().for_each(|cost| *cost = None);
            retryable_transaction_indexes.clear();

            Self::cancel_processed_transactions_for_retry(
                transactions,
                processing_results,
                processed_counts,
                error_counters,
                &mut retryable_transaction_indexes,
                failed_index,
                &transaction_error,
                0,
            );
        } else if let Some((failed_index, transaction_error)) = remaining_batch_error {
            transaction_costs[failed_index..]
                .iter_mut()
                .for_each(|cost| *cost = None);

            Self::cancel_processed_transactions_for_retry(
                transactions,
                processing_results,
                processed_counts,
                error_counters,
                &mut retryable_transaction_indexes,
                failed_index,
                &transaction_error,
                failed_index,
            );
        }

        (transaction_costs, retryable_transaction_indexes)
    }

/// P = R / (1 + C)
/// where P is the priority, R is the reward,
/// and C is the cost towards block-limits.
///
/// Current minimum costs are on the order of several hundred,
/// so the denominator is effectively C, and the +1 is simply
/// to avoid any division by zero due to a bug - these costs
/// are estimate by the cost-model and are not direct
/// from user input. They should never be zero.
/// Any difference in the prioritization is negligible for
/// the current transaction costs.
fn calculate_priority(
    transaction: &RuntimeTransaction<SanitizedTransactionView<&[u8]>>,
    bank: &Bank,
) -> Option<u64> {
    let transaction_configuration = transaction
        .transaction_configuration(&bank.feature_set)
        .ok()?;

    // Manually estimate fee here since currently interface doesn't allow a on SVM type.
    // Doesn't need to be 100% accurate so long as close and consistent.
    let prioritization_fee = transaction_configuration.priority_fee_lamports;
    let signature_details = transaction.signature_details();
    let signature_fee = signature_details
        .total_signatures()
        .saturating_mul(bank.fee_structure().lamports_per_signature);
    let fee_details = FeeDetails::new(signature_fee, prioritization_fee);

    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    let cost = CostModel::estimate_cost(
        transaction,
        transaction.program_instructions_iter(),
        transaction.num_requested_write_locks(),
        &bank.feature_set,
    );

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    Some(
        MULTIPLIER
            .saturating_mul(reward)
            .wrapping_div(cost.sum().saturating_add(1)),
    )
}
