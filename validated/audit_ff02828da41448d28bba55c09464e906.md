**Analysis:** The proof idea in the question is exactly what the code does — it is not exploitable.

`unlock_stake` is gated on the staker's own `Store` resource, keyed by `operator` in `SimpleMap<address, StakingContract>` [1](#0-0) . Before touching any contract, it calls `assert_staking_contract_exists`, which requires `staking_contracts.contains_key(&operator)` and aborts with `ENO_STAKING_CONTRACT_FOUND_FOR_OPERATOR` otherwise [2](#0-1) .

`switch_operator_with_same_commission` (the only operator-switch entrypoint in this module) performs `staking_contracts.remove(&old_operator)`, moves the extracted `StakingContract` value under the `new_operator` key via `staking_contracts.add(new_operator, staking_contract)`, and updates the pool's on-chain operator via `stake::set_operator_with_cap` [3](#0-2) . This means the `old_operator` key is fully deleted from the `SimpleMap`, not left as a stale/duplicate entry — there is no key collision or residual mapping to a live stake pool under the old operator address.

Consequently, calling `unlock_stake(staker, old_operator, amount)` after a switch will hit `assert_staking_contract_exists`, find `contains_key(&old_operator)` is `false`, and abort with `ENO_STAKING_CONTRACT_FOUND_FOR_OPERATOR` — precisely the behavior the submitter proposed as the expected (safe) outcome. There is no path by which an unprivileged staker could unlock, reactivate, or redirect stake belonging to a pool they no longer reference, since the `SimpleMap` guarantees at most one live entry per operator key per staker, and the stake pool itself is bound to a single current owner/operator via `stake::set_operator_with_cap` and the `OwnerCapability` held inside the (now relocated) `StakingContract` struct [4](#0-3) .
