### Title
`claimInstantWithdrawRequest` never removes the per-epoch receipt entries, inflating default-recovery claim basis — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When a lender claims a funded instant-withdraw receipt, `claimInstantWithdrawRequest` zeroes `instantWithdrawsRequests[_user]` but leaves the parallel per-epoch records `instantWithdrawsRequestsByEpoch[_user][epoch]` and the aggregate `instantWithdrawClaimsByEpoch[epoch]` untouched. These stale entries are exactly what `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` later read to compute the default recovery denominator and reserve. This is the same bug class as the external report: a "removal" path that updates one storage slot but not its index-linked counterpart, corrupting later aggregate accounting. [1](#0-0) [2](#0-1) 

### Finding Description
`requestInstantWithdraw` records three coupled pieces of state: `instantWithdrawsRequests[user]`, `instantWithdrawsRequestsByEpoch[user][epochNumber]`, and `instantWithdrawClaimsByEpoch[epochNumber]`. [3](#0-2) 

`claimInstantWithdrawRequest` clears only the first:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

No code deletes `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. By contrast, the default-path claim `_claimDefaultedInstantWithdrawRequest` does clear both — showing the per-epoch entries are meant to represent live claims. [4](#0-3) 

When the borrower later fails to fund (transfer failure in `getInstantWithdrawFunds`/`stopEpoch` catch, or `onStopEpoch` returning false for a programmable borrower), `finalizeDefaultRecovery` computes:

- `basis = pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` — inflated by the already-claimed stale amount.
- `prefundedReserve = instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` — inflated, but this part self-corrects since it is counted as reserve.

The net effect: `recoveryPrice = reserveAmount / totalBasis` is computed against a `totalBasis` that includes claims already paid out at par. [5](#0-4) 

### Impact Explanation
Every legitimate recovery claimant is diluted. Suppose instant requests of 1000 in epoch N: user A (600) is fully funded at `startEpoch` and claims at par; user B (400) stays pending. `instantWithdrawClaimsByEpoch[N]` remains 1000 instead of 400. At `finalizeDefault`, `totalBasis` is 600 too high, so `recoveryPrice` drops and B plus all `pendingWithdraws` receipt holders and active LPs (whose NAV is minted to `activeBasis * recoveryPrice / 1e18`) are haircut more than intended. The corresponding reserve share is never claimable: A's stale entry only causes an underflow revert in `_claimDefaultedInstantWithdrawRequest` (`instantWithdrawsRequests[A] -= 600` on a zeroed slot), so the excess reserve is permanently stranded in the strategy (recoverable only via owner `transferToken`). This is a direct value-loss misallocation, not a post-default freeze.

### Likelihood Explanation
Requires: (a) instant withdraws enabled and partially funded at `startEpoch` (occurs whenever buffer deposits + interest don't cover the instant queue — the code path explicitly handles `pendingInstant > totUnderlyings`), (b) at least one claimant redeeming at par while others remain pending, (c) a subsequent borrower funding failure in the same epoch followed by `finalizeDefault`. The preconditions are normal protocol mechanics, not attacker-dependent; the attacker needs only to be an ordinary KYC'd lender claiming a legitimately funded receipt in the right order. Caveat: a fully honest, solvent borrower repays, so realization requires a genuine funding shortfall, which lowers likelihood but is a standard default-risk assumption the default-recovery code exists for.

### Recommendation
In `claimInstantWithdrawRequest`, delete the per-epoch accounting the same way `_claimDefaultedInstantWithdrawRequest` does: find the request epoch (store it at request time, e.g. a `lastInstantWithdrawRequest[user]` marker or iterate via the stored epoch), set `instantWithdrawsRequestsByEpoch[_user][epoch] -= amount` and `instantWithdrawClaimsByEpoch[epoch] -= amount` when the receipt is paid at par. Since only the current request epoch's receipts can be funded-and-claimable, keying by the epoch recorded at `requestInstantWithdraw` time is sufficient.

### Proof of Concept
Foundry fork PoC sketch (two Keyring-whitelisted lenders, honest manager/borrower sequence):

```solidity
// test: stale instant-claim basis dilutes default recovery
function test_StaleInstantClaimDilutesRecovery() public {
    // 1. Epoch N-1 ends; APR dropped > instantWithdrawAprDelta so both
    //    lenders' requestWithdraw calls route to requestInstantWithdraw.
    vm.prank(alice); cdo.requestWithdraw(0, AATranche); // 600 basis
    vm.prank(bob);   cdo.requestWithdraw(0, AATranche); // 400 basis
    assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), 1000);

    // 2. startEpoch: CDO holds only 600 -> collectInstantWithdrawFunds(600),
    //    pendingInstantWithdraws = 400, surplus sent to borrower.
    vm.prank(manager); cdo.startEpoch();

    // 3. Alice claims her funded receipt at par.
    vm.prank(alice); cdo.claimInstantWithdrawRequest();
    assertEq(strategy.instantWithdrawsRequests(alice), 0);
    // BUG: per-epoch entries still alive
    assertEq(strategy.instantWithdrawsRequestsByEpoch(alice, epoch), 600);
    assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), 1000); // should be 400

    // 4. instantWithdrawDeadline passes; borrower funding fails (insolvency)
    //    -> getInstantWithdrawFunds catch -> _handleBorrowerDefault.
    vm.warp(strategy.instantWithdrawDeadline() + 1);
    // ... force borrower transfer failure (e.g., revoke allowance / drain) ...
    vm.prank(manager); cdo.getInstantWithdrawFunds();
    assertTrue(cdo.defaulted());

    // 5. finalizeDefault: totalBasis inflated by 600 ->
    //    recoveryPrice lower; bob and pending-withdraw claimants haircut extra.
    vm.prank(owner); cdo.finalizeDefault(recovered, recoverySource);
    vm.prank(bob); cdo.claimInstantWithdrawRequest();
    // bob received less than recovered * 400 / (trueBasis)
    // and ~600 * recoveryPrice of reserve is stranded forever:
    assertGt(strategy.defaultRecoveryReserve(), 0); // unclaimable dust
}
```

Expected fix behavior: after step 3, `instantWithdrawClaimsByEpoch(epoch) == 400`, and at finalization the full reserve is distributed across genuinely outstanding claims.

    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
