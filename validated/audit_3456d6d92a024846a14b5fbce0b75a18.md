### Title
Mid-epoch withdraw requests are not re-reserved in `ProgrammableBorrower`, so the borrower can drain funds owed to pending receipts and force a spurious default - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The analog of CVE-2018-19278 (buffer sized for the *compressed* length while the payload expands) is the programmable-borrower liquidity reservation: `epochPendingWithdraws` is sized once at `onStartEpoch` for the withdraw obligations known at that instant, but the actual obligation (`IdleCreditVault.pendingWithdraws`) expands every time a lender calls `requestWithdraw` during the running epoch. `availableToBorrow()` only subtracts the stale, smaller reservation, so the honest borrower can draw liquidity that stopEpoch will later need. When IdleCDO pulls the expanded `pendingWithdraws` amount, the `transferFrom` fails and the epoch settles through the default path even though the borrower is solvent.

### Finding Description
- `onStartEpoch(_pendingWithdraws)` snapshots the reservation a single time: `epochPendingWithdraws = _pendingWithdraws` [1](#0-0) 
- `availableToBorrow()` = `underlying.balanceOf(this) + _currentVaultAssets() - epochPendingWithdraws`; `borrow()`/`_borrow` lets the borrower pull everything above that stale reserve, withdrawing the shortfall from the ERC4626 vault itself [2](#0-1) [3](#0-2) 
- Meanwhile `IdleCreditVault.requestWithdraw` increases `pendingWithdraws += _amount` for any request made while the pool is not closed — there is no epoch-phase gate on the strategy side [4](#0-3) , and the CDO's `requestWithdraw` only checks the allow-flags and KYC, not `isEpochRunning` [5](#0-4) .
- Nothing ever pushes the grown `pendingWithdraws` back into `epochPendingWithdraws` mid-epoch. At `stopEpoch`, IdleCDO computes the amount to pull including *all* pending receipts, calls `onStopEpoch` (which only tops up on-hand cash from the vault up to what shares cover), then does `transferFrom` for the expanded amount [6](#0-5) . If the borrower legitimately drew the delta, the pull underflows → CDO treats it as repayment failure → `_handleBorrowerDefault` / loss socialization path instead of a clean stop.

The "buffer size matches compressed length, payload is expanded length" mapping is direct: the reservation equals the request-queue length at epoch start; the queue grows during the epoch; the settlement buffer is never re-expanded.

### Impact Explanation
A KYC-passed lender (unprivileged attacker) requests a withdraw during a running epoch *after* the borrower has already drawn `availableToBorrow()`. The new receipt inflates `pendingWithdraws` but not `epochPendingWithdraws`. At epoch end the CDO cannot source the full receipt amount from the borrower contract; the stop path degrades into default handling, marking a solvent facility as defaulted. Consequences: BB tranche absorbs a spurious loss first, `virtualPrice`/NAV is haircut, `defaultRecoveryPrice` machinery engages, and all remaining lenders take an unnecessary haircut or have claims locked behind `finalizeDefaultRecovery`. Quantified loss ≈ the unreserved withdraw amount (up to the borrower's drawn balance), socialized across tranche holders.

### Likelihood Explanation
Requirements: programmable-borrower deployment (`isProgrammableBorrower`), an epoch running with borrowable liquidity, and a borrower that draws (its normal function — the attacker does not control it, but sequencing around an honest borrow is allowed by the rules). The attacker only needs one `requestWithdraw` mid-epoch. Not blocked by skim, KYC, only-CDO, or epoch gating. Uncertainty I could not fully verify: whether the deployment's epoch flow forbids withdraw requests while `isEpochRunning` off-chain (the contracts do not), and whether `stopEpoch` passes a re-queried `pendingWithdraws` that includes mid-epoch requests — from the code visible, `onStopEpoch` receives `_amountRequired` computed from the strategy's current `pendingWithdraws`, which does include them, while the reservation does not.

### Recommendation
Keep the reservation synchronized with the obligation: either (a) have `IdleCreditVault.requestWithdraw` (via the CDO) call into the programmable borrower to increase `epochPendingWithdraws` whenever a mid-epoch request is accepted, or (b) compute `availableToBorrow` against a live value pushed by the CDO, or (c) disallow `requestWithdraw` during a running programmable epoch so the compressed reservation can never diverge from the expanded obligation.

  function availableToBorrow() public view returns (uint256) {
    uint256 totalAssets = underlyingToken.balanceOf(address(this)) + _currentVaultAssets();
    // Interest is minted (not pulled as cash), so only pending withdraw requests need reservation.
    uint256 reserved = epochPendingWithdraws;
    return totalAssets <= reserved ? 0 : totalAssets - reserved;
  }
