### Title
Unauthorized nonce-account eviction DOS in banking-stage nonce dedup tracking - (File: core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs)

### Summary
The reported VotingEscrow bug is a case of an unprivileged actor filling a bounded, per-victim resource slot to block that specific victim's legitimate operation (delegation/lock creation), with no economic loss to the attacker beyond gas. The closest reachable analog in this Agave codebase is the banking stage's durable-nonce transaction admission/eviction tracking in `TransactionViewReceiveAndBuffer::handle_packet_batch_message`, which maintains exactly one "in-flight" queued transaction per nonce-account address and allows any transaction — not just one signed by the nonce account's authorized authority — to occupy or evict that slot.

### Finding Description
`handle_packet_batch_message` extracts a nonce address purely structurally, before any signature/authority validation: [1](#0-0) 

It then validates the transaction only for nonce-state/blockhash consistency via `check_transaction_without_status_cache`, and if that succeeds, unconditionally evicts whatever transaction currently occupies that nonce address's single tracked slot in the container and replaces it with the incoming one: [2](#0-1) 

The container exposes exactly one tracked priority-queue slot per nonce address (`get_nonce_transaction_priority_id` / `set_nonce_transaction_priority_id`), analogous to VotingEscrow's per-user `MAX_DELEGATES` slot count — except here the "capacity" is 1 and, critically, nothing in this admission path checks that the submitter is the nonce account's authorized nonce authority. Authority is only enforced later, during actual instruction execution (`system_instruction::advance_nonce_account`), which is well after the scheduler has already evicted the legitimate transaction from the buffer.

This means any unprivileged party who can observe a target's durable-nonce account state (nonce accounts and their current blockhash are public on-chain data readable via RPC) can construct and submit a transaction that: (a) references the victim's nonce account in the `AdvanceNonceAccount` instruction, (b) uses the correct current nonce value as `recent_blockhash` so it passes `check_transaction_without_status_cache`, and (c) is signed only by the attacker as fee payer/"authority" — an authority mismatch that will only be caught deep in program execution, not during this early admission check. Because the attacker's transaction is fully validated at the admission layer (nonce state + blockhash match), it is inserted into `container` and evicts the victim's legitimate, correctly-authorized nonce transaction if the victim's queued priority is lower or equal: [3](#0-2) 

Test coverage confirms the eviction behavior exists and is triggered purely by priority comparison over the shared nonce-address key, with no authority check present in this code path: [4](#0-3) 

### Impact Explanation
An attacker can repeatedly submit low-cost spoofed nonce transactions (paying only their own transaction fee, never the victim's funds) referencing a victim's durable nonce account with a competitive/higher priority fee, causing the scheduler to continuously evict the victim's legitimate durable-nonce transactions from the buffered priority queue before they can be executed. This is a griefing/denial-of-service against a specific victim's durable-nonce-based transaction flow (a common pattern used by wallets, offline-signing flows, and programs relying on nonce accounts for replay protection), with no profit motive required from the attacker — directly mirroring the reported bug class (an unprivileged party filling a bounded, victim-keyed resource to block that victim's legitimate operation). This maps to the "ingest starvation" / TPU ingest limits impact category.

### Likelihood Explanation
Likelihood is moderate: nonce account addresses and their current stored blockhash are public, so no privileged information is required. The attack only requires crafting a syntactically valid `AdvanceNonceAccount` instruction referencing the victim's nonce account with a plausible (but unauthorized) signer, and paying a competitive priority fee. Because the eviction/admission check in this file is purely structural + nonce-state-based (no authority check), this is straightforward to automate.

### Recommendation
Perform (or at minimum partially validate) the nonce-authority check before allowing a transaction to occupy or evict another transaction's slot in the per-nonce-address tracking table in `handle_packet_batch_message`/`TransactionViewStateContainer`. At minimum, before evicting an existing `existing_nonce_priority_id`, verify that the incoming transaction's nonce-authorizing signer matches the nonce account's stored `authority`, so that only the legitimate account owner (or their authorized delegate) can preempt an in-flight transaction for that nonce address.

### Proof of Concept
Conceptual (not executed, no sandbox access in this session):
1. Query a victim's durable nonce account via RPC (`getAccountInfo`) to read its current `blockhash` value (used as the nonce).
2. Craft `tx_spoof`: fee payer = attacker, instructions = `[system_instruction::advance_nonce_account(victim_nonce_pubkey, attacker_pubkey), ...]`, `recent_blockhash` = victim nonce's current value, signed only by attacker (not the true nonce authority), with a compute-unit price higher than the victim's typical priority.
3. Submit `tx_spoof` to the TPU repeatedly, timed to precede or race the victim's real nonce transaction submissions.
4. Observe via `receive_and_buffer_packets` that `num_evicted_on_nonce_dedup` increments and the victim's queued transaction (tracked via `get_nonce_transaction_priority_id`) is removed by `container.remove_by_id`, as exercised by the existing test `test_receive_and_buffer_nonce_capacity_eviction`, while `tx_spoof` itself later fails at execution due to authority mismatch (a cost the attacker bears, not the victim).

Note: I was not able to fully trace `check_transaction_without_status_cache` in `runtime/src/bank/check_transactions.rs` within this session to conclusively confirm it never validates nonce-authority signer identity (only nonce-state/blockhash matching). This is the key assumption underlying the finding and should be verified against that function's implementation before treating this as confirmed; if it does enforce authority matching, this specific analog does not hold.

    // when a nonce transaction is bumped for capacity, its nonce map entry is cleared
    #[test]
    fn test_receive_and_buffer_nonce_capacity_eviction() {
        let (sender, receiver) = bounded(1024);
        let (bank_forks, mint_keypair) = test_bank_forks_with_fee();
        let (mut receive_and_buffer, _container) =
            setup_transaction_view_receive_and_buffer(receiver, bank_forks.clone());
        let mut container = TransactionViewStateContainer::with_capacity(1);
        let (nonce_pubkey, durable) = create_nonce_identity(&bank_forks, &mint_keypair.pubkey());

        send_transactions(
            &sender,
            &[create_nonce_transaction(
                &mint_keypair,
                &nonce_pubkey,
                0,
                durable,
            )],
        );
        assert_eq!(
            receive(&mut receive_and_buffer, &mut container).num_buffered,
            1
        );

        let nonce_entry = container
            .get_nonce_transaction_priority_id(&nonce_pubkey)
            .cloned()
            .unwrap();

        // the previous txn is 0 priority, so this evicts it, even with 0 priority
        let transaction = transfer(
            &mint_keypair,
            &Pubkey::new_unique(),
            1,
            bank_forks.read().unwrap().root_bank().last_blockhash(),
        );

        send_transactions(&sender, &[transaction]);
        let stats = receive(&mut receive_and_buffer, &mut container);
        assert_eq!(stats.num_buffered, 1);
        assert_eq!(stats.num_dropped_on_capacity, 1);
        assert_eq!(stats.num_evicted_on_nonce_dedup, 0);

        assert!(
            container
                .get_nonce_transaction_priority_id(&nonce_pubkey)
                .is_none()
        );
        assert!(!container.is_queued(&nonce_entry));

        verify_container(&mut container, 1);
    }
