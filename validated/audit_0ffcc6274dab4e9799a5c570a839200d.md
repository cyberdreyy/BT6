### Title
Zip-slip path traversal in legacy zip extractor (`ziplegacy`/`helpers/archives/zip_extract.go`) — no containment check on `zip.File.Name` unlike tarzstd/fastzip - ([File: helpers/archives/zip_extract.go])

### Summary
`helpers/archives/zip_extract.go`'s `extractZipFile`/`extractZipFileEntry`/`extractZipSymlinkEntry`/`extractZipDirectoryEntry` use `file.Name` directly in `os.Mkdir`, `os.OpenFile`, `os.Symlink`, and `os.MkdirAll(filepath.Dir(file.Name))` with zero path-canonicalization or containment check. `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go` stores a `dir` field but never uses it (calls `archives.ExtractZipArchive(zr)`, ignoring `e.dir`), so the intended "extract into build/cache dir root" containment never happens for this code path, in stark contrast to `commands/helpers/archive/tarzstd/tarzstd_extractor.go:57-64`, which explicitly computes `filepath.Abs(filepath.Join(e.dir, hdr.Name))` and rejects any path failing `strings.HasPrefix(path, e.dir+separator)`.

### Finding Description
Both `commands/helpers/cache_extractor.go` (cache download/extraction) and `commands/helpers/artifacts_downloader.go` (artifact download/extraction) call `archive.NewExtractor(format, f, size, wd)`, passing the intended extraction root (`wd`, the job's working directory) via the `Extractor` interface's `dir` parameter [1](#0-0) , and this attacker-adjacent archive content comes from a job's own uploaded cache/artifact archive (job-controlled zip entries), or from `CacheExtractorCommand.File`/`URL` which a job can influence via cache key configuration. For the `zip`/`zipzstd` format when the legacy (non-fastzip) extractor is registered, `ziplegacy.NewExtractor` builds an `extractor{r, size, dir}` but `Extract()` never uses `dir`: [2](#0-1) 
It instead calls `archives.ExtractZipArchive(zr)`, which has no directory/root parameter at all: [3](#0-2) 
Inside, `extractZipFile` computes `filepath.Dir(file.Name)` for `MkdirAll` and dispatches to entry handlers that call `os.Mkdir(file.Name, ...)`, `os.Symlink(data, file.Name)`, and `os.OpenFile(file.Name, ...)` — using the raw, attacker-controlled zip entry name verbatim, with no `filepath.Abs`/`HasPrefix`-style check that `tarzstd_extractor.go:57-64` and the underlying `fastzip` library apply: [4](#0-3) 
Only one narrow check exists (`.git` directory rejection via `errorIfGitDirectory` / `helpers/archives/path_check_helper.go:13-19`), which does not stop `../` traversal or absolute-path entries. Consequently, a crafted zip with an entry named e.g. `../../../../etc/cron.d/evil` or an absolute-path entry (`/etc/passwd`) extracted by the legacy zip extractor writes outside the CWD/build directory, whereas the exact same payload run through `tarzstd_extractor.go` or `fastzip` (which uses `saracen/fastzip`, itself zip-slip safe) is rejected or safely contained. This is exactly the divergence the question describes: `tarzstd_extractor.go`'s `HasPrefix` check vs. `zip_extract.go`'s total absence of containment.

### Impact Explanation
An unprivileged pipeline author who controls the contents of a job's cache or artifacts (both of which end up as zip archives fed into this extractor) can craft a zip with `../`-traversal or absolute-path entry names. When later extracted by a job/runner using the legacy zip extractor (the default when `FF_USE_FASTZIP` is not enabled — `commands/helpers/archiver.go:19-37` only swaps in fastzip conditionally), files can be written outside the intended build/cache root on the executor filesystem — for shell/host-backed executors this means writing arbitrary files anywhere the runner process has permissions (e.g., overwriting other jobs' cached files, planting files picked up by subsequent tooling, or corrupting shared paths), violating the "file operations must stay within intended build/cache/artifact roots" invariant.

### Likelihood Explanation
Fully attacker-controlled and repeatable: any job can produce and upload a cache/artifact zip with crafted entry names, no special privileges required, and the vulnerable code path (`ziplegacy` extractor) is the default whenever `FF_USE_FASTZIP` is off, which is a common/legacy configuration. It is deterministic — every extraction of such an archive with `ziplegacy` triggers the traversal write.

### Recommendation
Add the same canonicalization+containment check to `helpers/archives/zip_extract.go`/`ExtractZipArchive` that `tarzstd_extractor.go` already implements: thread the extraction root `dir` through `ExtractZipArchive`/`ExtractZipFile`/`extractZipFile`, compute `filepath.Abs(filepath.Join(dir, file.Name))` for every entry, and reject (or skip with a warning, matching existing `pathErrorTracker` behavior) any resolved path that does not have `dir` as a prefix, before performing `os.Mkdir`, `os.OpenFile`, or `os.Symlink`. Also wire `ziplegacy.extractor.dir` (currently unused) into this check so the parameter isn't silently dropped.

func extractZipDirectoryEntry(file *zip.File) (err error) {
	err = os.Mkdir(file.Name, file.Mode().Perm())

	// The "directory does exist" error is not an error for us
	if os.IsExist(err) {
		err = nil
	}
	return
}

func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}

func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}
