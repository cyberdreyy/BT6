### Title
Unauthenticated attacker can trigger disclosure of raw internal error text via `AuthenticateExternalInitiator` DB-error path - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` only converts `sql.ErrNoRows` into the generic `auth.ErrorAuthFailed`; any other error returned by `store.FindExternalInitiator` is wrapped with `errors.Wrap(err, "finding external initiator")` and propagated unchanged to `Authenticate`, which passes it straight into `jsonAPIError`. Because `jsonAPIError` falls back to `models.NewJSONAPIErrorsWith(err.Error())` for any error that isn't already a `*models.JSONAPIErrors`, the raw wrapped error string — including whatever the underlying driver/DB produced — is serialized verbatim into the 401 response body sent to an unauthenticated caller.

### Finding Description
- `AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) calls `store.FindExternalInitiator(ctx, eia)` using attacker-supplied `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers.
- On error, only `sql.ErrNoRows` is normalized to `auth.ErrorAuthFailed` (line 128-130); every other error (context deadline exceeded, connection failure, constraint violation, driver-specific error, etc.) is returned as `errors.Wrap(err, "finding external initiator")` (line 132), preserving the original error text.
- `Authenticate` (line 157-175) treats any non-`auth.ErrorAuthFailed` result as terminal (it does not fall through to try other auth methods) and calls `jsonAPIError(c, http.StatusUnauthorized, err)` with that wrapped error. [1](#0-0) [2](#0-1) 
- `jsonAPIError` in `core/web/auth/helpers.go` does not treat this wrapped error specially: since it's not a `*models.JSONAPIErrors`, it calls `err.Error()` and serializes that string directly into the JSON response body returned to the client. [3](#0-2) 

This means any transient/unexpected DB-layer failure while resolving the external-initiator access key (e.g., a query timeout, connection pool exhaustion, or a driver-level error) causes the node to echo internal error text (potentially including SQL driver messages, column/table names, or other backend details) back to an unauthenticated caller in the HTTP response body.

### Impact Explanation
This is an information-disclosure issue: an unauthenticated attacker probing the external-initiator endpoints during a DB hiccup (or by inducing one, e.g., via load) can receive internal error strings that reveal implementation details of the persistence layer, aiding further reconnaissance/credential-guessing attempts against the External Initiator authentication scheme. It does not itself grant authentication bypass or direct secret leakage (the `AccessKey`/`Secret` values submitted by the attacker are not echoed back by the DB layer in ordinary failure modes), but it violates the principle that failed-auth responses should be a uniform, generic `auth.ErrorAuthFailed` message and can leak schema/driver details to an unprivileged network attacker.

### Likelihood Explanation
Requires the `FindExternalInitiator` DB call to fail with something other than `sql.ErrNoRows` (e.g., transient DB outage, connection exhaustion, timeout) while an attacker is sending unauthenticated requests to any route protected by `AuthenticateExternalInitiator`. This is not attacker-controlled on demand under normal operation, but is fully reachable by any unauthenticated caller during normal operational error conditions, and the leak is deterministic whenever such an error occurs — no privileges are required.

### Recommendation
In `AuthenticateExternalInitiator`, avoid returning the wrapped raw error to the HTTP layer. Log the wrapped error server-side (e.g., via `logger`) and return a generic `auth.ErrorAuthFailed` (or a fixed opaque error) to the caller for all failure branches, mirroring the pattern already used in `AuthenticateByToken`. Additionally, `jsonAPIError` should not directly serialize arbitrary internal `error.Error()` strings for 401 responses; consider mapping all non-`ErrorAuthFailed` failures from auth methods to a single generic unauthorized message before reaching `jsonAPIError`.

### Proof of Concept
Handler-level integration test:
1. Build a mock `Authenticator` whose `FindExternalInitiator` returns a non-`sql.ErrNoRows` error, e.g. `errors.New("dial tcp: connection refused")` or a fabricated `pq.Error` string containing recognizable DB detail.
2. Wrap `Authenticate(mockStore, AuthenticateExternalInitiator)` in a gin test router and issue a request with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers set to arbitrary values.
3. Assert the response status is `401`.
4. Assert the response JSON body's `errors[0].detail` (per `models.JSONAPIErrorsWith`) equals the generic auth-failure string and does NOT contain the substring `"finding external initiator"` or the injected DB error text (`"dial tcp"` / `"connection refused"`).
5. Currently this assertion fails because the body contains `"finding external initiator: dial tcp: connection refused"`, demonstrating the leak; after the fix it should contain only the generic message.

```go
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
```

```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```
