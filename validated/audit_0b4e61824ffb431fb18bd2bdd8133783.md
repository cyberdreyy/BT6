### Title
v1 signer's `DuplicateBlockFound` guard checks `get_last_globally_accepted_block` while v2 checks `get_last_signed_block`, letting a v1 signer sign a second, different tenure-start block after only local (non-quorum) acceptance of the first - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` (v1) rejects a second tenure-start proposal for the same tenure only if a prior block in that tenure has already reached **global** acceptance [1](#0-0) , whereas `GlobalStateView::validate_tenure_change_payload` (v2) rejects it whenever a prior block has merely been **signed** (locally or globally accepted) [2](#0-1) . The v2 code comment explicitly documents this as a deliberate tightening of the guard, which implies the v1 behavior it replaces is weaker [3](#0-2) . During a rollout window where some signers still run v1-only software while others have upgraded to v2 (`SortitionStateVersion::from_protocol_version`) [4](#0-3) , a single miner-slot winner can present two different tenure-start blocks for the same sortition; v1 signers who only locally accepted the first block will not detect it as a duplicate and can sign the second, while v2 signers reject the second as `DuplicateBlockFound`.

### Finding Description
The uniqueness property the audit targets is: "at most one signed block per (cycle, tenure, height) across the whole signer set." This is enforced solely by the `last_in_current_tenure` lookup inside `validate_tenure_change_payload`:

- v1: `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` [5](#0-4) 
- v2: `signer_db.get_last_signed_block(&block.header.consensus_hash)` [6](#0-5) 

"Globally accepted" requires the reward-set weight threshold to have been reached; "signed" includes a block this individual signer (or the group) has merely locally accepted/signed without reaching that threshold. Consequently, if a tenure-start block `A` has been signed/locally-accepted by some signers but has not yet crossed the global-acceptance threshold, and the same miner (who owns the single sortition slot) then proposes a different tenure-start block `B` for the identical `consensus_hash`:

- Any signer still running the v1 chainstate path finds `get_last_globally_accepted_block == None` (since `A` never went global) and does **not** trigger `RejectReason::DuplicateBlockFound`; it proceeds to the other checks (`prev_tenure_consensus_hash` match, `check_tenure_change_confirms_parent`, `check_parent_tenure_choice`), none of which detect that a *different, already-locally-signed* first block exists for the same tenure [7](#0-6) .
- Any signer on v2 finds `get_last_signed_block == Some(A)` and rejects `B` with `DuplicateBlockFound` [8](#0-7) .

This produces exactly the split verdict the question describes: v1-population signers may go on to sign `B` while v2-population signers have already signed/endorsed `A`, so the two populations move toward endorsing two different, conflicting first blocks for the same tenure.

The mixed-version condition is not merely theoretical: `SortitionStateVersion::from_protocol_version` derives V1/V2 per the currently-active protocol version threshold `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION` [4](#0-3) , and the codebase carries both `v1` and `v2` chainstate implementations side-by-side specifically to support a staged migration [9](#0-8) , so a network in the middle of this migration will legitimately contain signers evaluating proposals under different rules simultaneously.

### Impact Explanation
This breaks the **UNIQUENESS** safety property: distinct signer sub-populations can be steered by a single unprivileged miner into signing two different candidate blocks for the same tenure-start slot. If each sub-population's accumulated signature weight is later combined or independently reaches its own required threshold (e.g., via stale-cache resets, differing observed reward-set membership, etc.), this can finalize conflicting blocks at the same (tenure, height) — a Critical chain-safety violation ("a signer signing an invalid, non-canonical, or conflicting block"). It is repeatable by any miner-slot winner for as long as the mixed v1/v2 population persists in a reward cycle.

### Likelihood Explanation
Preconditions: (1) attacker wins a single miner (sortition) slot — an explicitly allowed capability; (2) the signer set is in a genuine v1/v2 mixed state during a protocol version rollout, which is an expected transitional condition given the codebase's staged migration design; (3) the first proposed block reaches local (non-global) signing by at least one signer before the second, competing tenure-start block is gossiped. No signer key, auth_token, or majority-signer control is required — only crafting two block proposals and gossiping them, which is within the stated one-slot-plus-gossip attacker model. Feasibility is bounded by the duration of the version-migration window, but is repeatable each tenure the attacker wins during that window.

### Recommendation
Backport the v2 fix to v1: change `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` to use `get_last_signed_block` (or an equivalent "signed at all, local or global" lookup) instead of `get_last_globally_accepted_block`, so both versions apply the identical, stricter duplicate-detection rule regardless of a signer's protocol version. Alternatively, gate proposal evaluation so no signer runs the v1 path once any block in a tenure has been locally signed, ensuring the weaker guard can never diverge from the v2 guard within the same tenure.

#[test]
fn v1_vs_v2_duplicate_tenure_start_divergence() {
    // 1. Build a shared SignerDb.
    let mut signer_db = SignerDb::new(":memory:").unwrap();

    // 2. Construct tenure-start block A for consensus_hash CH, and mark it
    //    as LOCALLY accepted/signed (signed_self set) but NOT globally accepted
    //    (i.e., do not call mark_globally_accepted / do not exceed threshold).
    let block_a = make_tenure_start_block(CH, /*chain_length=*/1);
    let mut info_a = BlockInfo::from(block_a.clone());
    info_a.mark_locally_accepted(false).unwrap(); // signed_self set, not globally accepted
    signer_db.insert_block(&info_a).unwrap();

    // 3. Construct a DIFFERENT tenure-start block B for the same consensus_hash CH.
    let block_b = make_tenure_start_block(CH, /*chain_length=*/1); // different miner nonce/tx set -> different hash

    // 4. V1 check: expect NOT DuplicateBlockFound (bug).
    let v1_state = /* build SortitionState::V1 wrapping data for CH */;
    let v1_result = v1_state.validate_tenure_change_payload(
        &ProposedBy::CurrentSortition(&v1_state),
        block_b.get_tenure_change_tx_payload().unwrap(),
        &block_b,
        &mut signer_db,
        &client,
    );
    assert!(v1_result.is_ok(), "v1 wrongly allows a second tenure-start block after only local acceptance");

    // 5. V2 check: expect DuplicateBlockFound (correct).
    let v2_result = GlobalStateView::validate_tenure_change_payload(
        block_b.get_tenure_change_tx_payload().unwrap(),
        &block_b,
        &parent_tenure_id,
        &mut signer_db,
        &client,
        &config,
    );
    assert_eq!(v2_result, Err(RejectReason::DuplicateBlockFound));

    // 6. Assert the divergence: one version accepts, the other rejects the same
    //    competing tenure-start block over the same locally-signed predecessor.
    assert_ne!(v1_result.is_ok(), v2_result.is_ok());
}
