### Title
Unbounded blocking loop over DON members in Vault gateway handler allows a single unresponsive node to stall/DoS user requests - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
`fanOutToVaultNodes` in the internet-facing Vault gateway handler iterates over `h.donConfig.Members` and calls `h.don.SendToNode(ctx, node.Address, &ar.req)` synchronously in a `for` loop with no per-node timeout, unlike the sibling `confidentialrelay` handler which explicitly bounds each send and fans out concurrently to avoid exactly this problem.

### Finding Description
`fanOutToVaultNodes` sends the same request to every DON member sequentially: [1](#0-0) 

Each iteration calls `h.don.SendToNode(ctx, node.Address, &ar.req)` directly against the shared `ctx` — there is no per-node `context.WithTimeout` wrapping the send, and the loop is sequential rather than parallel with a `errgroup`/goroutine fan-out. If `SendToNode` blocks (e.g., a node's websocket connection accepts no writes / send buffer is full), the loop stalls on that node and never proceeds to send to the remaining members until the outer context is cancelled or the write eventually times out at a lower layer.

This is the same DoS pattern as the "external calls in loop" report: an unbounded/insufficiently-bounded iteration performing external I/O (a call to a remote peer) per element, where one failing/slow element degrades or blocks the whole operation for other, healthy members.

Critically, the codebase already recognizes and fixed this exact class of bug in the neighboring `confidentialrelay` handler: `fanOutToNodes` explicitly wraps all sends with a shared `nodeSendTimeout` context and dispatches to nodes concurrently via `errgroup`, with a code comment stating: *"Each send is bounded independently. A node whose websocket accepts no writes blocks until its context is cancelled, and because the caller only reads the response callback after this function returns, an unbounded send would hold the request open until the client gives up, discarding a bundle that already reached quorum."* [2](#0-1) 

There is a dedicated regression test, `TestConfidentialRelayHandler_BlockedNodeDoesNotStallFanOut`, verifying that a blocked node does not stall the fan-out in `confidentialrelay`: [3](#0-2) 

The Vault handler's `fanOutToVaultNodes`, however, has no equivalent per-node timeout or concurrency — it performs the loop with a single shared `ctx` and sequential blocking calls: [1](#0-0) 

### Impact Explanation
Because the Vault handler is reachable directly from unprivileged/external clients (the internet-facing gateway forwards user JSON-RPC requests to the DON), a single slow or unresponsive vault node connection can cause `fanOutToVaultNodes` to block indefinitely (bounded only by the outer request's overall context, if any), delaying or discarding responses to legitimate user requests even after enough of the healthy nodes could have produced a quorum. Depending on how the caller-level context/timeout is configured, this can manifest as a denial-of-service for Vault-capability calls: requests silently fail or hang instead of completing once quorum is otherwise reachable, and if handled synchronously with limited concurrency in the gateway, a backlog of stuck requests could exhaust request-handling capacity.

### Likelihood Explanation
Likelihood is moderate: it does not require a malicious external client — it only requires one DON member's websocket connection to become slow/blocked (e.g., due to network congestion, a slow node, or a stalled TCP write), which is a normal, low-privilege operational condition already anticipated and mitigated in the sibling `confidentialrelay` handler. The fact that the fix pattern already exists in an adjacent handler in the same package strongly suggests this is an overlooked instance of the same known issue rather than a hypothetical one.

### Recommendation
Apply the same mitigation used in `confidentialrelay.fanOutToNodes` to `vault.fanOutToVaultNodes`:
- Wrap each `SendToNode` call with a per-node timeout context (e.g., `context.WithTimeout(ctx, h.nodeSendTimeout)`).
- Fan out to all DON members concurrently (e.g., via `errgroup.Group` or a `sync.WaitGroup`) instead of a sequential loop, so a single blocked node cannot delay delivery to the rest of the DON.
- Add a regression test analogous to `TestConfidentialRelayHandler_BlockedNodeDoesNotStallFanOut` for the Vault handler.

### Proof of Concept
1. Configure a Vault DON with N members, where the connection manager (`h.don`) for one member's `SendToNode` blocks indefinitely (simulating a node whose websocket accepts no writes, as done in `confidentialrelay/handler_test.go`'s `blockedDON` mock).
2. Submit a normal user request that triggers `fanOutToVaultNodes`.
3. Observe that the loop stalls on the blocked node and does not proceed to send to subsequent, healthy nodes within a bounded time, unlike the equivalent `confidentialrelay` fan-out, which completes and reaches quorum despite one blocked node (as shown in `TestConfidentialRelayHandler_BlockedNodeDoesNotStallFanOut`).

Note: I could not fully verify the exact blocking semantics of the concrete `donConnectionManager.SendToNode` implementation (i.e., whether it internally applies any write deadline) since the deeper connection-manager send-path implementation was not fully retrieved before the tool budget was exhausted; this affects the precise severity/likelihood but not the core structural finding that `fanOutToVaultNodes` lacks the per-node timeout and concurrency safeguard present in the sibling handler.

func (h *handler) fanOutToVaultNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var nodeErrors []error
	for _, node := range h.donConfig.Members {
		err := h.don.SendToNode(ctx, node.Address, &ar.req)
		if err != nil {
			nodeErrors = append(nodeErrors, err)
			l.Errorw("error sending request to node", "node", node.Address, "error", err)
		}
	}

	if len(nodeErrors) == len(h.donConfig.Members) && len(nodeErrors) > 0 {
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.FatalError, errors.New("failed to forward user request to nodes"), nil))
	}

	l.Debugw("successfully forwarded request to Vault nodes")
	return nil
}

func (h *handler) fanOutToNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var (
		group      errgroup.Group
		nodeErrors atomic.Uint32
	)

	// Each send is bounded independently. A node whose websocket accepts no writes blocks
	// until its context is cancelled, and because the caller only reads the response callback
	// after this function returns, an unbounded send would hold the request open until the
	// client gives up, discarding a bundle that already reached quorum.
	sendCtx, cancel := context.WithTimeout(ctx, h.nodeSendTimeout)
	defer cancel()

	for _, node := range h.donConfig.Members {
		group.Go(func() error {
			err := h.don.SendToNode(sendCtx, node.Address, &ar.req)
			if err != nil {
				nodeErrors.Add(1)
				l.Errorw("error sending request to node", "node", node.Address, "error", err)
			}
			return nil
		})
	}

	_ = group.Wait()

func TestConfidentialRelayHandler_BlockedNodeDoesNotStallFanOut(t *testing.T) {
	t.Parallel()
	lggr := logger.Test(t)
	don := &blockedDON{blockedAddr: "0x0002"}
	donConfig := &config.DONConfig{
		DonId: "test_relay_don",
		F:     1,
		Members: []config.NodeConfig{
			{Name: "node0", Address: "0x0000"},
			{Name: "node1", Address: "0x0001"},
			{Name: "node2", Address: "0x0002"},
			{Name: "node3", Address: "0x0003"},
		},
	}

	methodConfig, err := json.Marshal(Config{RequestTimeoutSec: 30})
	require.NoError(t, err)
	limitsFactory := limits.Factory{Settings: cresettings.DefaultGetter, Logger: lggr}
	h, err := NewHandler(methodConfig, donConfig, don, lggr, clockwork.NewFakeClock(), limitsFactory)
	require.NoError(t, err)
	// Shortened so the test exercises the bound without waiting the production default.
	h.nodeSendTimeout = 50 * time.Millisecond

	params := json.RawMessage(`{"workflow_id":"wf1"}`)
	req := jsonrpc.Request[json.RawMessage]{
		ID:     "req-blocked-node",
		Method: MethodCapabilityExec,
		Params: &params,
	}

	done := make(chan error, 1)
	start := time.Now()
	go func() {
		done <- h.HandleJSONRPCUserMessage(t.Context(), req, common.NewCallback())
	}()

	select {
	case fanOutErr := <-done:
		// Three of four nodes still received the request, so quorum remains possible and the
		// blocked node is reported as a node error rather than a request failure.
		require.NoError(t, fanOutErr)
	case <-time.After(5 * time.Second):
		t.Fatal("fan-out stalled on the blocked node instead of bounding the send")
	}

	assert.Less(t, time.Since(start), h.requestTimeout, "fan-out must return well inside the request timeout")
	assert.Equal(t, 3, don.deliveredCount(), "healthy nodes should all receive the request")
}
