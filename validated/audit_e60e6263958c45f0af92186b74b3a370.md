### Title
ERC4626 liquidity withdrawal failure can indefinitely block programmable-borrower epoch settlement - ([File: `contracts/strategies/idle/ProgrammableBorrower.sol`])

### Summary
`ProgrammableBorrower.onStopEpoch` treats nominally sufficient ERC4626 share value as proof that liquidity can be withdrawn. If the vault cannot actually return the requested assets, the hook reverts and the enclosing `stopEpoch` call also reverts, leaving the epoch running and withdrawals disabled. [1](#0-0) [2](#0-1) 

### Finding Description
During an active programmable-borrower epoch, idle facility assets are held in an external ERC4626 vault and `totalInterestDueNow()` prices pool interest from the vault’s `convertToAssets` valuation. [3](#0-2) 

When `stopEpoch` is called, the borrower hook compares the required cash shortfall with `_currentVaultAssets()`. If the share valuation covers the shortfall, it calls `vault.withdraw(shortfall, ...)`; any ERC4626 withdrawal failure is caught and converted to `StopEpochVaultLiquidityUnavailable`. [1](#0-0) 

The enclosing `_stopEpoch` intentionally does not catch hook reverts, so the entire epoch settlement rolls back. [2](#0-1) 

An unprivileged participant in the external vault ecosystem can create this state by exhausting the vault’s currently withdrawable liquidity while the programmable borrower’s shares still have sufficient accounting value. For an allocated-liquidity vault such as MetaMorpho, share value can include outstanding or illiquid market positions even though an immediate withdrawal fails. Repeating that liquidity drain before each manager retry repeatedly blocks settlement.

### Impact Explanation
All LP funds represented by the programmable borrower’s vault position remain unavailable while the condition persists. Because the epoch remains running, normal withdrawal requests remain closed and pending receipts are not funded. [4](#0-3) 

This is temporary freezing of the entire shortfall and associated LP redemption value. If the external vault remains permanently unable to satisfy the withdrawal, the freeze becomes permanent: `setVault` cannot be called while epoch accounting is active or old shares remain, and `emergencyExitVault` uses the same illiquid vault redemption path. [5](#0-4) [6](#0-5) 

### Likelihood Explanation
The attack requires a programmable-borrower deployment whose ERC4626 vault can have accounting assets exceeding immediately withdrawable liquidity. That condition is normal for vaults that allocate capital to underlying lending markets.

Likelihood is bounded by the attacker’s ability to consume the vault’s available liquidity before the manager’s `stopEpoch` transaction. No privileged Idle role is required: a vault shareholder, underlying-market borrower, or other unprivileged account that can remove vault liquidity can establish the condition. The failure can be repeated until the liquidity constraint clears.

### Recommendation
Do not treat `convertToAssets(shares) >= shortfall` as proof that `withdraw(shortfall)` will succeed. Query `maxWithdraw`, cap the withdrawal to available liquidity, and return a recoverable partial-liquidity status or route a genuine economic shortfall into the existing borrower-default path. A privileged recovery path should also allow epoch termination when vault liquidity remains unavailable for a configured period.

### Proof of Concept
The following fork test is adapted to the existing programmable-borrower harness and deterministically exercises the production failure branch. A real vault integration can replace `MockStopEpochLiquidityVault.setWithdrawLimit` with the corresponding liquidity-draining transaction.

```solidity
// test/foundry/ProgrammableBorrowerStopEpochLiquidity.t.sol
function testAttackerCanTemporarilyFreezeEpochSettlement() external {
    MockStopEpochLiquidityVault constrainedVault =
        new MockStopEpochLiquidityVault(USDC);

    _setUpProgrammableBorrowerCreditVault(
        FORK_BLOCK,
        address(constrainedVault)
    );

    uint256 lpAmount = 10_000 * oneScale;

    idleCDO.depositAA(lpAmount);
    _startEpochAndCheckPrices(0);

    // Ensure the borrower does not have enough idle underlying on hand.
    // Its vault shares still account for substantially all LP principal.
    uint256 required = lpAmount / 2;
    vm.prank(revolvingBorrower);
    programmableBorrower.borrow(required);

    assertGt(
        programmableBorrower.vaultSharesBalance(),
        0,
        "borrower should retain vault shares"
    );
    assertGt(
        programmableBorrower.vaultInterestAccrued() + lpAmount,
        required,
        "share valuation should nominally cover epoch liabilities"
    );

    // Models an unprivileged external-vault participant draining the currently
    // withdrawable liquidity. Share accounting value remains non-zero, but the
    // ERC4626 withdraw operation now reverts.
    constrainedVault.setWithdrawLimit(0);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning(), "epoch must remain unsettled");
    assertFalse(cdoEpoch.allowAAWithdrawRequest(), "AA requests remain frozen");
    assertFalse(cdoEpoch.allowBBWithdrawRequest(), "BB requests remain frozen");

    // A second attempt remains impossible while the liquidity drain persists.
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Once external liquidity returns, settlement is again possible.
    constrainedVault.setWithdrawLimit(type(uint256).max);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertFalse(cdoEpoch.isEpochRunning(), "epoch should settle after liquidity returns");
}
```
