## Finding [1](#0-0) [2](#0-1) 

### Title
Missing fee-sum validation in `createDstEscrow` allows any unprivileged taker to permanently DoS `EscrowDst.withdraw`/`publicWithdraw` via arithmetic underflow, freezing maker funds - (File: contracts/EscrowDst.sol / contracts/BaseEscrowFactory.sol)

### Summary
This is the same root-cause pattern as the external report: two different code paths compute/validate the same fee-related arithmetic inconsistently, and the path lacking validation causes an unconditional revert (panic) later in the lifecycle. On the source side, `BaseEscrowFactory._postInteraction` explicitly guards against fee amounts exceeding the escrowed amount before emitting the immutables used to build the destination escrow. `BaseEscrowFactory.createDstEscrow`, however, accepts a caller-supplied `Immutables` struct — including the embedded `parameters` blob that encodes `protocolFeeAmount`/`integratorFeeAmount` — without repeating that check.

### Finding Description
In `_postInteraction` (source escrow creation), the factory computes fee amounts and enforces:
```solidity
if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();
``` [3](#0-2) 

This guard exists precisely because `EscrowDst._withdraw` later performs an unchecked subtraction:
```solidity
uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
``` [4](#0-3) 

However, `createDstEscrow` — the function that actually deploys and funds the `EscrowDst` clone with a caller-supplied `Immutables calldata dstImmutables` — never re-validates the fee sum against `amount`:
```solidity
function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
    address token = dstImmutables.token.get();
    uint256 nativeAmount = dstImmutables.safetyDeposit;
    if (token == address(0)) {
        nativeAmount += dstImmutables.amount;
    }
    if (msg.value != nativeAmount) revert InsufficientEscrowBalance();
    ...
``` [1](#0-0) 

`protocolFeeAmount`/`integratorFeeAmount` are read straight out of the raw `parameters` bytes with no bound checking beyond a minimum length: [5](#0-4) 

Since `createDstEscrow` has no access restriction limiting it to a whitelisted resolver and lets `msg.sender` supply arbitrary `dstImmutables` (as long as they fund the corresponding CREATE2 address hash and safety deposit/amount), any unprivileged actor can set `protocolFeeAmount + integratorFeeAmount > amount` when deploying the destination escrow. Once deployed, `_withdraw` will always underflow and panic-revert (`Panic(0x11)`), for both `withdraw` and `publicWithdraw`, because the subtraction is unconditional and unguarded by a try/catch or prior validation.

### Impact Explanation
The destination escrow becomes permanently un-withdrawable during its entire withdrawal window (private and public withdrawal periods) — the maker can never redeem the secret to receive `dstToken`, exactly mirroring the external report's DoS-on-cancellation pattern but here manifesting as DoS-on-withdrawal. This is a "temporary freezing of funds during the live swap lifecycle" for the maker's expected destination-chain proceeds, matching the in-scope **High** impact criteria (temporary freezing of funds during the live swap lifecycle), triggerable entirely by an unprivileged taker/depositor with no special role required.

### Likelihood Explanation
`createDstEscrow` is a permissionless, publicly callable function; any caller who funds the safety deposit/amount can pass an arbitrary `parameters` payload. No production code path re-derives or re-validates `protocolFeeAmount + integratorFeeAmount < amount` at destination-escrow-creation time, so the condition is trivially reachable without race conditions, privileged roles, or reliance on external actors.

### Recommendation
Add the same guard used in `_postInteraction` to `createDstEscrow`, e.g.:
```solidity
uint256 protocolFeeAmount = dstImmutables.protocolFeeAmount();
uint256 integratorFeeAmount = dstImmutables.integratorFeeAmount();
if (protocolFeeAmount + integratorFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();
```
before deploying/funding the clone, ensuring the same invariant enforced at source-escrow creation also holds for destination-escrow creation, so `_withdraw`'s subtraction can never underflow.

### Proof of Concept
1. Attacker (any address, no whitelist/role needed) crafts `dstImmutables` with `amount = 100`, and `parameters` encoding `protocolFeeAmount = 60`, `integratorFeeAmount = 60` (recipients arbitrary), `hashlock`, `taker = attacker`, etc.
2. Attacker calls `createDstEscrow{value: safetyDeposit (+ amount if native)}(dstImmutables, srcCancellationTimestamp)` — succeeds since no fee-sum check exists; the clone is deployed and funded per `IEscrowFactory.createDstEscrow` and `_deployEscrow`. [6](#0-5) 
3. When the maker later calls `withdraw(secret, immutables)` with the correct secret during the withdrawal window, `_withdraw` computes `immutables.amount - integratorFeeAmount - protocolFeeAmount` = `100 - 60 - 60`, which underflows and reverts with `Panic(0x11)` for every call, including `publicWithdraw`. [4](#0-3) 
4. The maker cannot obtain their `dstToken` proceeds for the entire withdrawal period; only after `DstCancellation` can the taker reclaim the deposited amount via `cancel`, which does not perform the fee subtraction.

        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);

    }

    function protocolFeeAmountCd(IBaseEscrow.Immutables calldata immutables) external pure returns (uint256 ret) {
        bytes calldata parameters = immutables.parameters;

        assembly ("memory-safe") {
            ret := calldataload(parameters.offset)
        }
    }

    /**
     * @notice Returns the integrator fee amount from the immutables (calldata version).
     * @param immutables The immutables to extract the fee from.
     * @return ret The integrator fee amount.

    function integratorFeeAmountCd(IBaseEscrow.Immutables calldata immutables) external pure returns (uint256 ret) {
        bytes calldata parameters = immutables.parameters;
        if (parameters.length < 0x40) revert IndexOutOfRange();
        assembly ("memory-safe") {
            ret := calldataload(add(parameters.offset, 0x20))
        }
    }
