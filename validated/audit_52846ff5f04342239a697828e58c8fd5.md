### Title
Node-RPC failure fails open in the same-tenure duplicate-block guard, allowing a signer to sign two conflicting blocks in one tenure — ([File: stacks-signer/src/v0/signer.rs])

### Summary
`Signer::handle_block_pre_commit` contains a guard meant to stop a signer from signing two different blocks inside the *same tenure* once the pre-commit threshold is reached. That guard's only remaining check — "has the node's canonical tip for this tenure already reached/passed this block's height?" — is implemented via `stacks_client.get_tenure_tip(...)`. When that RPC call errors, the code does not refuse to sign (the safe/blocking outcome); it logs a warning and falls through to the signing path, exactly the "failed call goes unnoticed and normal execution continues" pattern from the referenced Solidity finding (`_safeTransferAVAX` continuing as if the transfer succeeded when the callee doesn't exist).

### Finding Description
The `DuplicateBlockFound` check that would normally reject a second, conflicting block proposal in the same tenure only runs once, at proposal arrival, in `check_proposal` [1](#0-0) . If a second conflicting block for the same tenure clears that initial screen (e.g., because it arrives and is queued/validated before the first one settles) and later independently reaches the ≥70% pre-commit weight threshold, the *only* remaining backstop is the "own tenure" branch inside `handle_block_pre_commit`: [2](#0-1) 

Here, `conflicts.iter().any(...)` selects conflicts whose `consensus_hash` equals the proposed block's own tenure and whose reorg permit does not stand — i.e. same-tenure equivocation candidates. The code then asks the node for the tenure's canonical tip via `get_tenure_tip`. Only the `Ok(tip)` branch with `tip_height >= chain_length` causes an early `return` (refuse to sign). The `Err(e)` branch just logs "Treating the tenure as unconfirmed" and does **not** return — execution falls through to the code that proceeds to `SIGN: mark_locally_accepted, handle_block_signature, broadcast acceptance` [3](#0-2) .

This is a deliberate design asymmetry documented in `docs/signer-flows.md`: for cross-tenure conflicts (`conflict_still_blocks`/`reorg_permit_stands`), a node error is treated conservatively — keep blocking — because "blocking is the direction that can be taken back" [4](#0-3) . But for the *own-tenure* duplicate-block guard, the documentation explicitly states the opposite choice was made: "For the own-tenure question below, an unreachable node is instead treated as unconfirmed and the signature goes out" [5](#0-4) . Unlike the cross-tenure case, failing open here does not merely delay a stale-signature cleanup — it produces an actual second signature over a conflicting block in the same tenure, which is precisely the equivocation this guard exists to prevent.

### Impact Explanation
This breaks the "one signed block per tenure" invariant that the own-tenure guard is supposed to enforce. If the guard fails open, a single signer can end up having signed two different, conflicting blocks within the same tenure once each independently gathers pre-commit weight. That is a Critical-class outcome per the rules: "a signer signing an invalid, non-canonical, or conflicting block." Because this failure mode is per-signer (each signer independently queries its own node), if enough signers experience the failure-open path around the same narrow race window, competing blocks could both accumulate enough weight-bearing signatures to be viable, undermining the safety property that only one block per tenure position is ever signable.

### Likelihood Explanation
Triggering the race requires: (1) a miner proposing two conflicting blocks for the same tenure close enough together that the second is not rejected outright by the one-time `DuplicateBlockFound` check at proposal arrival, and (2) the signer's own `get_tenure_tip` RPC call to fail or time out at the moment the second block crosses the pre-commit threshold. A single miner (plus normal gossip) fully controls condition (1) by crafting/timing two competing block proposals in one tenure. Condition (2) does not require compromising a majority of signers or their keys — any transient node RPC failure (timeout, node restart, load spike, or a burst of proposal-validation traffic saturating the node) at the right moment is sufficient, and this is an accepted "normal" occurrence the code explicitly special-cases rather than something exotic. This keeps the likelihood realistic without requiring a majority of signers or key compromise, matching the report's rules.

### Recommendation
Make the own-tenure duplicate-block guard fail closed, symmetric with `conflict_still_blocks`/`reorg_permit_stands`: on `Err(e)` from `get_tenure_tip`, refuse to sign (return) rather than falling through to sign, and retry when the node becomes reachable again on a subsequent pre-commit re-evaluation. This trades a temporary liveness delay (like the cross-tenure case) for eliminating the risk of an unrecoverable double-signature.

### Proof of Concept
1. Miner controls tenure T. It builds two conflicting Nakamoto blocks B1 and B2 at/overlapping the same chain height within tenure T.
2. Miner proposes B1; signers validate, pre-commit, and B1 nears/reaches the 70% pre-commit threshold.
3. Before the one-time `DuplicateBlockFound` proposal-arrival check can catch B2 as a duplicate for tenure T (e.g., B2 is broadcast to a signer whose earlier proposal-time state didn't yet reflect B1, or timing allows B2 through), B2 also accumulates enough pre-commit weight independently.
4. When a given signer's `handle_block_pre_commit` evaluates B2 crossing threshold, it detects a same-tenure conflict (B1) and calls `stacks_client.get_tenure_tip(consensus_hash_of_T)` [6](#0-5) .
5. If that RPC call errors (transient node unavailability), the `Err(e)` arm only warns and does not return; execution proceeds to sign B2 [7](#0-6) .
6. The signer has now signed both B1 and B2 within the same tenure T — a conflicting-block signature, the exact Critical-impact scenario defined by the rules.
