### Title
Authenticated External Initiator can trigger a run for any int32-ID job, not just the webhook job it was registered for - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create`, reached via `userOrEI.POST('/jobs/:ID/runs')` wrapped by `auth.RequiresRunRole`, only checks whether *any* authenticated identity is present (`auth.GetAuthenticatedUser(c)`), and `auth.AuthenticateExternalInitiator` always injects a synthetic `User{Role: UserRoleRun}` into the same session key used by real users. As a result, for any job identified by an int32 ID, `isUser` is true for both real users and any authenticated EI, and the code proceeds to call `prc.App.RunJobV2(ctx, jobID, nil)` without ever cross-referencing `auth.GetAuthenticatedExternalInitiator(c).Name` against the target job's spec/owner.

### Finding Description
Route registration in `core/web/router.go`: [1](#0-0) 
wires `POST /v2/jobs/:ID/runs` behind `auth.Authenticate` with three possible methods — `AuthenticateExternalInitiator`, `AuthenticateByToken`, `AuthenticateBySession` — and then `auth.RequiresRunRole(prc.Create)`.

`AuthenticateExternalInitiator` sets both the EI object and a synthetic run-role `User` into the gin context: [2](#0-1) 

`RequiresRunRole` only inspects that synthetic `User.Role`, never the EI identity: [3](#0-2) 

Inside `PipelineRunsController.Create`, the controller rejects UUID-style job IDs outright (webhook job type has been removed from the codebase, `job.ErrJobTypeRemoved`): [4](#0-3) 

For non-UUID (int32) IDs, the code checks `isUser := auth.GetAuthenticatedUser(c)` — which is true for both real users and EI-authenticated requests (since the EI middleware sets the same `SessionUserKey`) — and if true, parses the ID as int32 and unconditionally calls `RunJobV2`: [5](#0-4) 

The comment "only users are allowed to run jobs using int IDs - EIs not allowed" describes intended behavior that the code does not actually enforce, because `isUser` cannot distinguish a real `User` session/token from an EI-derived synthetic `User`. There is no call to `auth.GetAuthenticatedExternalInitiator(c)` anywhere in `Create` to verify the EI's name matches the target job's `ExternalInitiatorWebhookSpec` (or any ownership/allow-list check at all) before invoking `RunJobV2` on an arbitrary int32 job ID.

Because webhook jobs (UUID-addressed) have been entirely removed from the system, the practical exploit is not "EI A running EI B's webhook job" (that specific webhook path is blocked), but a broader issue: any credential that authenticates via the EI method can trigger a run of **any** job addressable by int32 ID (e.g., OCR, VRF, Keeper, DirectRequest jobs) it has no association with whatsoever, since `RunJobV2` is invoked without any job-ownership or EI-name check.

### Impact Explanation
This matches the "unauthorized job run triggering" / fund-affecting job execution impact class: an EI credential — a low-privilege, narrowly-scoped credential meant only to post webhook-triggered runs — can force execution of arbitrary jobs by numeric ID, including jobs it has no legitimate relationship to. Triggering unintended pipeline runs can cause unwanted on-chain transactions (VRF fulfillment, Keeper upkeep execution, DirectRequest fulfillment) depending on job type, which is a fund-affecting action.

### Likelihood Explanation
Precondition: attacker must hold a valid EI credential (`AccessKey`/`Secret`) for any single external initiator registered on the node — a credential that is meant only to authorize job runs for the webhook job it was attached to. Given that, the attack is a single unauthenticated-role HTTP POST to `/v2/jobs/:jobID/runs` with an arbitrary int32 `:jobID`, fully repeatable and requiring no further precondition or job-B-specific secret (job IDs are small sequential integers, easily enumerable).

### Recommendation
In `PipelineRunsController.Create`, explicitly reject EI-authenticated requests from the int32-ID code path (check `auth.GetAuthenticatedExternalInitiator(c)` and fail if present, rather than inferring identity type from the synthetic run-role `User`), or track authentication method distinctly (e.g., a separate context key) so `isUser` truly means "human user/API token," not "EI acting as run-role user." If EI-triggered runs by int32 ID are ever intended to be supported again, cross-reference the EI's `Name` against the target job's spec before calling `RunJobV2`.

### Proof of Concept
1. Register two jobs with int32 IDs, e.g. an OCR job A and a Keeper job B (or two arbitrary non-webhook jobs).
2. Register/authenticate an external initiator EI `X` (only ever intended to trigger webhook job A, if any exists) via `/v2/external_initiators`.
3. As EI `X`, `POST /v2/jobs/{B.ID}/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to EI X's credentials and no body.
4. Assert: current code returns `200` with a created pipeline run for job B (`prc.App.RunJobV2` succeeds) — expected/fixed behavior should be `401`/`403` since EI X has no relationship to job B.
5. Complement with a unit test on `auth.RequiresRunRole` + `PipelineRunsController.Create` verifying `auth.GetAuthenticatedExternalInitiator(c)` is checked and rejected for the int32-ID path.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
