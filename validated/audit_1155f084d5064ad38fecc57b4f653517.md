Based on my investigation, I found a concrete analog of the reported bug class: a missing "already tallied" guard that lets a single signer's weight be counted twice across two mutually-exclusive vote buckets, breaking the aggregated-weight ↔ verified-accepts equality that the mining coordinator relies on to decide whether a block has real 70% signer approval.

### Title
Signer weight can be double-counted into both `total_weight_approved` and `total_weight_rejected` for the same block — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` tallies per-slot signer votes for a proposed block into two counters, `total_weight_approved` and `total_weight_rejected`, which the coordinator later compares against `weight_threshold` to decide "block accepted" or "signers rejected". The de-duplication guard that prevents a signer's weight from being counted twice is asymmetric: it protects the "accept-then-reject" ordering but not the "reject-then-accept" ordering, so a single signer switching its vote from Reject to Accept for the same block has its weight added into both tallies.

### Finding Description
In the `Accepted` branch, the weight is only added if the slot hasn't already produced an accepted signature: [1](#0-0) 

`block.responded_signers.insert(slot_id)` is also called here, which is intended to prevent a later duplicate. In the `Rejected` branch, the weight is only added if `responded_signers.insert(slot_id)` returns `true` (i.e., first time seen): [2](#0-1) 

This means:
- If a signer's Accepted message is processed first, `responded_signers` already contains `slot_id`, so a later Rejected message is correctly ignored (no double count).
- If a signer's Rejected message is processed first, `responded_signers` gets `slot_id` inserted and `total_weight_rejected` is incremented. A later Accepted message for the *same block* only checks `gathered_signatures.contains_key(&slot_id)` — which is still `false` at that point — so `total_weight_approved` is *also* incremented with the same signer's weight.

The result is that one signer's weight ends up counted in **both** `total_weight_approved` and `total_weight_rejected` for the same block, which breaks the invariant the coordinator depends on: that `total_weight_approved` reflects only weight from signers who verifiably accepted the block.

### Impact Explanation
The mining coordinator (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) treats `total_weight_approved >= self.weight_threshold` as proof that ≥70% of signer weight validated and accepted the block, and will broadcast/finalize it as signed: [3](#0-2) 

If a signer's weight is phantom-duplicated into the approved tally via the Reject→Accept ordering, the node can believe it has reached the 70% threshold while the actual distinct weight of signers that accepted is lower than reported, i.e. an inflated aggregated-weight vs. the real set of verified accepts — matching the "aggregated-weight vs verified-accepts" equality-break category. Near the threshold boundary, this can let the coordinator declare consensus reached with less real signer weight than the protocol requires.

### Likelihood Explanation
This requires only a single signer (not a majority) to emit two StackerDB chunk updates for the same block — first a `Rejected` message, then an `Accepted` message — which are each dispatched as separate `messages` in the listener's per-event loop: [4](#0-3) 

Nothing in the listener rejects a later message from a signer that already responded in the opposite direction, so a buggy or adversarial signer client can trigger this deterministically by simply writing its slot twice with opposite verdicts before the coordinator resolves the block.

### Recommendation
Make the duplicate-response guard symmetric: check `responded_signers.contains(&slot_id)` (or equivalently `gathered_signatures.contains_key` OR reject-recorded) before adding weight in **both** the `Accepted` and `Rejected` branches, so a signer's weight can only ever land in one of `total_weight_approved` / `total_weight_rejected`, matching the external report's recommendation to add an explicit guard rather than relying on an implicit ordering assumption.

### Proof of Concept
1. Node proposes block `B`; `StackerDBListener` inserts an entry into `self.blocks` for `B`'s sighash.
2. Signer `S` (weight `w`) writes a `Rejected` StackerDB chunk for `B`. Listener processes it: `responded_signers.insert(slot_id)` → `true`, so `total_weight_rejected += w`.
3. Signer `S` then writes an `Accepted` chunk for the same `B` (e.g., re-evaluated proposal, race, or malicious client). Listener processes it: `gathered_signatures.contains_key(&slot_id)` is `false` (never accepted before), so `total_weight_approved += w` as well.
4. Now both `total_weight_rejected` and `total_weight_approved` include `w`, even though only one real, current vote (`Accepted`) should count. If other signers' legitimate approvals plus this duplicated `w` push `total_weight_approved` over `weight_threshold`, the coordinator in `signer_coordinator.rs` will treat the block as having reached the 70% acceptance threshold even though the true distinct accepting weight is `w` less than reported.
