### Title
`requestWithdraw` loss-receipt guard looks up `lossRecoveryPriceByEpoch` at the latest request epoch instead of the epoch holding the receipt, letting a loss-adjusted receipt be claimed at par - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.requestWithdraw` is supposed to block a user from opening a new withdraw request while they still hold an unclaimed receipt from an epoch that was haircut by `collectWithdrawFunds`/`lossRecoveryPriceByEpoch`. The guard computes `lossEpoch = lastWithdrawRequest[_user]` and only checks `lossRecoveryPriceByEpoch[lossEpoch]` plus the per-epoch entries at that single epoch. If the user makes a second `requestWithdraw` *after* the loss epoch but before claiming, `lastWithdrawRequest` is overwritten to the new epoch, the lookup misses the haircut stored under the old epoch, and the old receipt is later paid at par through `_claimFundedWithdrawRequest`. This mirrors the CVE: the code checks the wrong key (`/..` instead of `../`) — it validates the latest epoch marker rather than the epoch where the loss actually lives.

### Finding Description
Relevant code (`contracts/strategies/idle/IdleCreditVault.sol:259-294`):


On claim, `_claimLossAdjustedWithdrawRequest` (lines 789-801) again uses `lastWithdrawRequest[_user]` as the epoch key:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
(uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
```

`_clearWithdrawClaimForEpoch` only zeroes `withdrawsRequestsByEpoch[_user][_claimEpoch]` and subtracts that epoch's piece from `withdrawsRequests[_user]` (lines 815-820). Multiple sequential requests are explicitly supported — `withdrawsRequests[_user] += _amount` and the comment at line 323 "if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests."

Attack sequence (unprivileged KYC'd lender, `stopEpochWithDuration` loss mode):

1. Epoch N running → attacker calls `cdoEpoch.requestWithdraw(X, tranche)` → `withdrawsRequestsByEpoch[attacker][N] = X`, `lastWithdrawRequest = N`, receipt tokens minted.
2. `stopEpochWithDuration(_lossAmount)` runs with a partial loss → `collectWithdrawFunds` is called with `_amount < pendingBasis`, storing `lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL` and zeroing `pendingWithdraws` (lines 411-421). `epochNumber` becomes N+1.
3. In the buffer, before claiming, attacker calls `requestWithdraw(Y, tranche)` again. Guard computes `lossEpoch = lastWithdrawRequest = N`, `lossRecoveryPriceByEpoch[N] = p ≠ 0`, `withdrawsRequestsByEpoch[N] ≠ 0` → reverts? No — the guard reads `lastWithdrawRequest` *before* it is updated, so this first post-loss request is correctly blocked only if the attacker requests in the *same* lookup epoch. The escape is: the attacker makes the second request in epoch N+1 **after**... — wait, the guard is evaluated against `lastWithdrawRequest` which is still N at step 3, so it correctly reverts at step 3.

Re-examining: the actual gap is the **APR0 branch** and the **ordering inside the guard**. The guard requires `withdrawsRequestsByEpoch[_user][lossEpoch] != 0` OR `apr0.principalEpoch == lossEpoch` — but it never checks `apr0Users[_user].settledPrincipal`/`settledInterest`, and it checks `principalEpoch` only against `lossEpoch`. A user whose APR0 request was settled into `settledPrincipal` at a later epoch, then hit by a loss epoch recorded under a *different* key, escapes. More directly: if the attacker had a **normal** request in epoch N and an **APR0** request whose `principalEpoch` is M ≠ N, and a loss is applied to epoch M's bucket, `lastWithdrawRequest` (=N) does not point at M, so `lossRecoveryPriceByEpoch[M]` is never consulted — the M-epoch APR0 receipt is later paid at par via `_claimFundedWithdrawRequest` (`normalAmount + apr0PrincipalAmount + apr0InterestAmount`, lines 338-349).

There is also a pure ordering bypass: `requestWithdraw` checks the guard against the *old* `lastWithdrawRequest` and then unconditionally overwrites it. If a loss-adjusted receipt exists under epoch N but the user's `lastWithdrawRequest` was already moved to N+1 by an earlier non-loss request (normal request in N, APR0/normal request in N+1 before the loss finalized — both requests coexist because the guard only fires when the *current* `lastWithdrawRequest` epoch itself has a loss price), then when the loss lands on epoch N the pointer no longer references it. The subsequent claim path at line 790 reads `lastWithdrawRequest = N+1`, finds `lossRecoveryPriceByEpoch[N+1] == 0`, skips `_claimLossAdjustedWithdrawRequest`, and `_claimFundedWithdrawRequest` pays the entire `withdrawsRequests[_user]` aggregate — including the epoch-N receipt — at par.

### Impact Explanation
Direct theft of other users' funded withdrawal liquidity: the attacker redeems a receipt that should pay `claimBasis * lossRecoveryPrice / RECOVERY_FULL` at 100% instead. Quantified loss = `claimBasis * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL` per affected epoch receipt, taken from underlying held by the strategy for other pending/funded claims (or from `defaultRecoveryReserve` if set, which `_transferFundedClaim` deliberately avoids — so the shortfall falls on later claimants and active LPs). The loss-waterfall invariant (pending receipts share realized losses pro rata) is broken for anyone who holds receipts across two epochs.

### Likelihood Explanation
Requires: an attacker with tranche tokens (any KYC-passing lender), at least two open withdraw requests in different epochs, and an honest manager triggering `stopEpochWithDuration(_lossAmount)` or a borrower underfunding `collectWithdrawFunds` — i.e., a realized loss event, which is the scenario this code path exists for. No privileged misbehavior needed; the attacker only sequences ordinary `requestWithdraw`/`claimWithdrawRequest` calls around the manager's honest `stopEpoch` calls.

### Recommendation
Track loss-adjusted epochs independently of the single `lastWithdrawRequest` pointer: e.g., store per-user the earliest unclaimed epoch, or iterate/check `lossRecoveryPriceByEpoch` for every epoch with a nonzero `withdrawsRequestsByEpoch`/`apr0Users.principalEpoch` before allowing a new request and before the funded-claim path. At minimum, in `requestWithdraw`, also revert when `apr0Users[_user].principalEpoch` or any prior request epoch has a nonzero `lossRecoveryPriceByEpoch`, and in `_claimLossAdjustedWithdrawRequest` resolve the loss epoch from per-epoch receipt data rather than `lastWithdrawRequest`.
