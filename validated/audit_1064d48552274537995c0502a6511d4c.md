### Title
Use-after-free via stale VM memory region when account data buffer is realloc'd during CPI entry before callee execution - (File: program-runtime/src/cpi.rs)

### Summary
`update_callee_account` in `program-runtime/src/cpi.rs` can call `callee_account.set_data_length(post_len)` at CPI entry (before `invoke_context.process_instruction()` runs the callee), which can reallocate the underlying account data buffer, but the corresponding `memory_mapping.replace_region()` fix-up (`update_caller_account_region`) is only performed after `process_instruction()` returns, at CPI exit. Because `account_data_direct_mapping` maps VM memory regions directly onto the account's backing `Vec<u8>` and shares a single `MemoryMapping` instance across the whole CPI stack, the callee executes with a region that can be pointing at freed/moved memory.

### Finding Description
`translate_type_mut_for_cpi` and `translate_slice_mut_for_cpi` in `program-runtime/src/memory.rs` intentionally erase the lifetime tie to `&MemoryMapping`, delegating the "does not outlive backing data" invariant entirely to callers [1](#0-0) [2](#0-1) . `cpi.rs` relies on this to build `CallerAccount<'a>` fields like `serialized_data: &'a mut [u8]` and `ref_to_len_in_vm: &'a mut u64` [3](#0-2) .

In `cpi_common`, at CPI entry, `update_callee_account` is invoked for each translated account before `process_instruction()` runs the callee [4](#0-3) . Inside `update_callee_account`, when `virtual_address_space_adjustments` is set and `prev_len != post_len`, `callee_account.set_data_length(post_len)` is called unconditionally (regardless of `account_data_direct_mapping`), setting `must_update_caller = true` but performing no region fix-up itself [5](#0-4) .

The actual region fix-up, `update_caller_account_region`, which calls `memory_mapping.replace_region()` to repoint the VM region at the (possibly moved) backing buffer, is only invoked in the loop *after* `process_instruction()` returns, i.e. at CPI exit, gated on `translated_account.update_caller_account_region` [6](#0-5) [7](#0-6) .

Under `account_data_direct_mapping`, `create_memory_region_of_account`/`modify_memory_region_of_account` map the VM region directly onto the account's live data buffer, and the developer's own comment flags this exact hazard: *"for `cpi.rs` callsite this is not as easy to prove and relies on careful coordination between any code that might increase the account data buffer length"* [8](#0-7) . Since `MemoryMapping` is shared across the CPI stack (regions are patched in place via `replace_region` rather than re-serialized per call), if `set_data_length` at entry triggers the backing `Vec<u8>` to reallocate/move, the stale region persists through `process_instruction()`, meaning the invoked (callee) program's own reads/writes to that account through the VM address space during its execution use a region describing the *old* buffer location — a use-after-free / dangling-region read-write, not merely a caller-side dangling reference.

### Impact Explanation
This is a memory-safety violation (UAF/dangling VM memory region) reachable from ordinary CPI account-data resizing, matching the "process crash or memory corruption" category. It occurs entirely inside `program-runtime` (native host code), not the sBPF interpreter or Loader V4, so it is not excluded by SECURITY.md scope exclusions. A successful trigger of a stale region access could corrupt other account memory, crash the validator process, or leak/mangle memory across accounts within a single instruction.

### Likelihood Explanation
The precondition is a single attacker-controlled BPF program that: (1) is invoked via CPI with `account_data_direct_mapping` and `virtual_address_space_adjustments` enabled (current mainnet feature state must be confirmed), (2) causes the callee's account data length to shrink/grow relative to what the caller has cached, forcing `set_data_length` to run at CPI entry before `process_instruction`. This requires only a single `simulateTransaction` / transaction submission by an unprivileged actor deploying their own program — no validator/operator control needed. However, whether `set_data_length` actually reallocates/moves the backing buffer's address (versus in-place truncation with stable pointer) in the current `AccountSharedData`/`transaction_accounts.rs` implementation could not be fully confirmed from the available index; this determines whether the dangling region is truly reachable or only a latent risk documented by the code's own safety comment.

### Recommendation
Perform the `update_caller_account_region`-equivalent region fix-up synchronously inside `update_callee_account` immediately after any `set_data_length` call that can move the account's backing buffer, before `process_instruction()` executes the callee — rather than deferring all region repair to CPI exit. Alternatively, make `set_data_length`/account buffer growth path always preserve buffer address stability (e.g., pre-reserve capacity) when direct mapping is active, or add an explicit region re-sync call at the top of `process_instruction` prior to entering the callee's VM execution.

### Proof of Concept
Integration test plan (extending `programs/sbf/rust/realloc_invoke` and `programs/sbf/tests/programs.rs`):
1. Enable `account_data_direct_mapping` and `virtual_address_space_adjustments` feature gates.
2. Deploy a caller program that: (a) holds an `AccountInfo` for account `A`, (b) invokes (CPI) a callee program passing `A` with a different data length than the caller's cached copy so that `update_callee_account` triggers `set_data_length` growing `A`'s buffer beyond its previous capacity (forcing a `Vec` reallocation/move).
3. The callee program, upon entry, immediately writes to the full extent of `A`'s data (via its own `AccountInfo`/`SolAccountInfo`), exercising the shared `MemoryMapping` region for `A`.
4. Run under Miri/ASan (or a `MemoryRegion` instrumentation crate) inside a `mock_invoke_context!`-based unit test in `program-runtime/src/cpi.rs` tests, asserting that the region's `host_buffer` pointer used during the callee's write matches the *current* (post-realloc) address of `A`'s backing storage rather than the pre-resize address; a mismatch or ASan-reported heap-use-after-free confirms the vulnerability.
5. Expected failing assertion (pre-fix): the region address read by the callee equals the *stale* pre-resize pointer, or ASan reports a UAF read/write.

/// # Safety
///
/// The the account data pointed to by `callee_account` must outlive the uses of the
/// [`MemoryMapping`].
unsafe fn update_caller_account_region(
    memory_mapping: &mut MemoryMapping,
    check_aligned: bool,
    caller_account: &CallerAccount,
    callee_account: &mut BorrowedInstructionAccount<'_, '_>,
    account_data_direct_mapping: bool,
) -> Result<(), Error> {
    let is_caller_loader_deprecated = !check_aligned;
    let address_space_reserved_for_account = if is_caller_loader_deprecated {
        caller_account.original_data_len
    } else {
        caller_account
            .original_data_len
            .saturating_add(MAX_PERMITTED_DATA_INCREASE)
    };

    if address_space_reserved_for_account > 0 {
        // We can trust vm_data_addr to point to the correct region because we
        // enforce that in CallerAccount::from_(sol_)account_info.
        let (region_index, region) = memory_mapping
            .find_region(caller_account.vm_data_addr)
            .ok_or_else(|| Box::new(InstructionError::MissingAccount) as Error)?;
        // vm_data_addr must always point to the beginning of the region
        let region_start_vm_addr = region.vm_addr_range().start;
        debug_assert_eq!(region_start_vm_addr, caller_account.vm_data_addr);
        let mut new_region;
        if !account_data_direct_mapping {
            new_region = region.clone();
            modify_memory_region_of_account(callee_account, &mut new_region);
        } else {
            new_region = create_memory_region_of_account(callee_account, region_start_vm_addr)?;
        }
        unsafe {
            // SAFETY: the lifetime invariants are delegated to the callers of this function. Both
            // `modify_memory_region_of_account` and `create_memory_region_of_account` create memory
            // regions pointing to valid buffers by the virtue of the region being produced out of
            // an intermediate slice, which itself must be wholly valid.
            memory_mapping.replace_region(region_index, new_region)?;
        }
    }

    Ok(())
}

/// Modifies the memory mapping in serialization and CPI return for virtual_address_space_adjustments
pub fn modify_memory_region_of_account(
    account: &mut BorrowedInstructionAccount<'_, '_>,
    region: &mut MemoryRegion,
) {
    let data_ptr = region.host_buffer().ptr() as *mut u8;
    let new_buffer = std::ptr::slice_from_raw_parts_mut(data_ptr, account.get_data().len());
    if account.can_data_be_changed().is_ok() {
        unsafe {
            // SAFETY:
            // Contract from `MemoryRegion::redirect`: The memory pointed to by the MemoryRegions
            // must point to a valid object live for the duration of this MemoryMapping.
            //
            // TODO(nagisa): Local reasoning for this contract is infeasible. In particular for the
            // `serialization.rs` code it is pretty easy to see that the regions passed in will
            // always be larger than `account.get_data().len()`. However for `cpi.rs` callsite this
            // is not as easy to prove and relies on careful coordination between any code that
            // might increase the account data buffer length.
            region.redirect(new_buffer);
        }
        region.access_violation_handler_payload = Some(account.get_index_in_transaction());
    } else {
        unsafe {
            // SAFETY:
            //
            // Contract from `MemoryRegion::redirect`: same as for the call above.
            // Evidence: same as for the call above.
            region.redirect(new_buffer.cast_const());
        }
        region.access_violation_handler_payload = None;
    }
}
