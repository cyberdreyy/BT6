### Title
Fee-on-transfer underlying inflates strategy-token supply and NAV — `IdleCreditVault.deposit` mints `_amount` regardless of tokens actually received - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCDOCreditVault._deposit` correctly measures the received underlying via a balance delta when minting tranche shares (`_mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, ...)`), but then calls `IIdleCDOStrategy(strategy).deposit(_amount)` with the nominal amount. `IdleCreditVault.deposit` pulls `_amount` from the CDO and unconditionally mints `_amount` strategy tokens to the CDO. With a fee-on-transfer (FoT) underlying (e.g. USDT with fees enabled, or any future FoT pool currency), the strategy receives `_amount - fee` while crediting the CDO with `_amount` of claim basis. The same assumption exists in `collectWithdrawFunds`, `collectInstantWithdrawFunds`, `finalizeDefaultRecovery` and `ProgrammableBorrower._repay`/`_depositToVault`, all of which account the requested amount rather than the received amount.

### Finding Description [1](#0-0) [2](#0-1) 

Step trace (running epoch, cash mode):

1. A KYC'd lender calls `depositAA(x)` on `IdleCDOCreditVault`.
2. `_deposit` measures `balAfter - balBefore = x - f` and mints the user the correct (smaller) number of tranche shares — fair to the depositor.
3. `_deposit` then calls `strategy.deposit(x)`. `IdleCreditVault.deposit` does `safeTransferFrom(CDO, strategy, x)` — strategy receives `x - f` — and mints `x` strategy tokens to the CDO.
4. `IdleCreditVault.price()` is constant `oneToken` (line 174–176), so `getContractValue()` counts `x` strategy tokens at par: NAV = `x`, real cash held = `x - f`.
5. On the next `_updateAccounting`, the phantom `f` is booked as a gain and split between `lastNAVAA`/`lastNAVBB` via `_virtualPriceAux` (lines 222–236), inflating `virtualPrice` for all existing tranche holders.

The identical defect hits the withdrawal-funding path: `collectWithdrawFunds(_amount)` sets `pendingWithdraws = pendingBasis - _amount` and `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` based on the requested `_amount`, but only `_amount - f` lands in the contract (lines 411–430). Funded receipts are then marked claimable at a haircut computed against money that never arrived, so the last claimants' `safeTransfer` in `_transferFundedClaim` reverts on insufficient balance — permanent freezing of unclaimed yield/principal.

`ProgrammableBorrower._repay` (`underlyingToken.safeTransferFrom(borrower, address(this), assets)` at line 482) similarly clears `borrowerPrincipal`/`borrowerInterestDebt` by the nominal `assets`, letting debt be extinguished with fewer real tokens — but since borrower is a trusted role this is secondary to the depositor-facing issue.

### Impact Explanation
Direct insolvency: every deposit of a FoT underlying creates `f` unbacked strategy tokens booked as NAV. Tranche prices rise without real yield, senior/junior NAVs are overstated, and withdraw-request funding math (`collectWithdrawFunds`, `lossRecoveryPriceByEpoch`) assumes cash that was taxed away. Loss scales with deposit volume: with a 1% transfer fee, each 1M deposit leaks ~10k of phantom NAV; terminal claimants absorb the cumulative shortfall as a permanent freeze/loss.

### Likelihood Explanation
The vault's `token` is set once in `initialize` and the design targets fixed pool currencies like USDC/USDT. USDT has a built-in fee mechanism currently set to zero; if enabled (or if a new vault is pointed at an FoT token), the bug triggers deterministically on every deposit and every `stopEpoch` funding pull. No privileged misbehavior is required — ordinary lender deposits cause it. The `_skimDonatedAssets` / balance-delta guards elsewhere do not cover these paths because the strategy mints against the parameter, not the balance.

### Recommendation
Measure received amount in every pull:
- In `IdleCreditVault.deposit`: `uint256 pre = underlyingToken.balanceOf(address(this)); safeTransferFrom(...); uint256 received = balanceOf(this) - pre; _mint(msg.sender, received);` and return `received`.
- In `collectWithdrawFunds` / `collectInstantWithdrawFunds`: compute funding from the balance delta, not `_amount`, before updating `pendingWithdraws`/`lossRecoveryPriceByEpoch`.
- In `finalizeDefaultRecovery` and `ProgrammableBorrower._repay`: use balance deltas when crediting reserve/debt.
- Alternatively, explicitly document/enforce that `token` must be a non-FoT asset at `initialize`/factory level.

### Proof of Concept
Foundry fork sketch against an FoT asset (or a fork test deploying the vault with a fee-enabled token):

```solidity
// test/foundry/FeeOnTransferDeposit.t.sol
function testFoTDepositInflatesNAV() public {
    // deploy IdleCDOCreditVault + IdleCreditVault with FoTToken (1% fee) as `token`
    uint256 amount = 1_000_000e6;
    fotToken.approve(address(cdo), amount);

    uint256 cdoNavBefore = cdo.getContractValue();
    cdo.depositAA(amount); // KYC'd lender

    uint256 expected = amount;            // NAV credited
    uint256 strategyBal = fotToken.balanceOf(address(strategy)); // = amount - 1%

    assertEq(strategy.strategyToken().balanceOf(address(cdo)), expected); // minted at par
    assertEq(strategyBal, amount * 99 / 100);
    // NAV = strategyTokens * price() = amount  ->  phantom `amount/100` gain
    // booked to lastNAVAA/lastNAVBB on next _updateAccounting()
    assertEq(cdo.getContractValue() - cdoNavBefore, expected);
    assertLt(strategyBal, expected); // real backing short by the fee
}
```

For the claim path: request a withdraw, let `stopEpoch` call `collectWithdrawFunds(pendingBasis)` — strategy receives `pendingBasis - f` while `pendingWithdraws` is cleared to zero, so the final `claimWithdrawRequest` → `_transferFundedClaim` reverts on insufficient balance, permanently freezing the last `f` of claims.

    external

    if (IIdleCDOEpochVariant(idleCDO).isEpochRunning()) {

      totEpochDeposits = 0;
