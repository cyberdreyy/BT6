### Title
Instant withdrawal boundary check excludes the documented minimum APR delta, forcing healthy requests into a locked normal-withdraw queue - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The bug class in the external report is a boundary check that uses strict `>` where `>=` is semantically required, so an action reverts (or is denied) even when the account/condition is exactly at the allowed threshold. The same pattern exists in `IdleCDOEpochVariant.requestWithdraw`: `instantWithdrawAprDelta` is documented as the *minimum* APR change that should trigger an instant withdrawal, but the check `lastEpochApr > (currentApr + instantWithdrawAprDelta)` rejects equality, so a withdrawal made after an APR drop exactly equal to the minimum delta is silently routed to the normal withdraw path and locked for a full epoch.

### Finding Description
In `requestWithdraw`, when instant withdrawals are enabled, the vault compares the previous epoch's unscaled APR against the new unscaled APR plus `instantWithdrawAprDelta`:

```solidity
// contracts/IdleCDOEpochVariant.sol, ~L762-769
uint256 currentApr = creditVault.unscaledApr();
if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
    creditVault.requestInstantWithdraw(_underlyings, msg.sender);
    _withdrawOps(_amount, _underlyings, _tranche);
    return _underlyings;
}
```

The storage comment defines `instantWithdrawAprDelta` as the "min apr change to trigger instant withdraw" (`IdleCDOEpochVariant.sol` L37-38). A minimum threshold is inclusive by definition: a drop of exactly `instantWithdrawAprDelta` should qualify. The strict `>` makes it exclusive — the same `>` vs `>=` boundary error as `return (ratio > MIN_COL_RATIO)` in the Taurus report.

When equality holds, execution falls through to the normal `requestWithdraw` path (`IdleCreditVault.requestWithdraw`), which mints a receipt that cannot be claimed until after the *next* `stopEpoch` (`_claimFundedWithdrawRequest` reverts while `epochNumber <= lastWithdrawRequest[_user]`, `IdleCreditVault.sol` L326). The user's funds are therefore locked for an entire epoch (~`epochDuration`, default 30 days) instead of being claimable after `instantWithdrawDelay` (~3 days).

### Impact Explanation
Any lender whose withdraw request coincides with an APR reduction exactly equal to `instantWithdrawAprDelta` has their full requested amount (`_underlyings` = tranche balance × tranche price) frozen for one epoch rather than one delay period. This is temporary freezing of user funds with a quantified magnitude (100% of the requested amount for `epochDuration`). Because the fixed-APR borrower repays at epoch end, the user also loses the instant-receipt optionality that the delta parameter is documented to grant them.

### Likelihood Explanation
The boundary requires the manager to set a new scaled APR whose unscaled value is exactly `lastEpochApr - instantWithdrawAprDelta`. This is not a rare rounding artifact: managers set APRs in round numbers and `instantWithdrawAprDelta` is itself configured in round numbers, so equality is a plausible normal operation point. No attacker action beyond a normal `requestWithdraw` is needed; the window is open throughout the buffer period after `stopEpoch` sets the new APR. Likelihood is low-to-moderate since it needs the exact equality, but it is a deterministic, reproducible misclassification rather than an edge-case revert.

### Recommendation
Make the documented minimum inclusive:

```solidity
// contracts/IdleCDOEpochVariant.sol, requestWithdraw
if (lastEpochApr >= (currentApr + instantWithdrawAprDelta)) {
```

Note that with `instantWithdrawAprDelta == 0` the semantics change (any non-decrease, including equal APRs, would qualify); if "strictly lower APR plus delta" is the intended behavior, the fix is `lastEpochApr > currentApr && lastEpochApr >= currentApr + instantWithdrawAprDelta` — i.e., keep a strict decrease requirement but make the delta itself inclusive. Add a unit test covering `lastEpochApr - currentApr == instantWithdrawAprDelta`.

### Proof of Concept
Reproducible Foundry case (schematic, based on existing `test/foundry` epoch vault harness):

```solidity
function testInstantWithdrawBoundary() external {
    // setup: user deposits AA, epoch 1 runs and stops at apr A1
    _depositAA(user, 10_000e6);
    _startAndStopEpoch(A1);

    // epoch 2: manager sets new unscaled apr A2 = A1 - instantWithdrawAprDelta
    vm.prank(manager);
    idleCDO.setInstantWithdrawParams(3 days, DELTA, false); // instantWithdrawAprDelta = DELTA
    _startEpoch();
    vm.prank(manager);
    idleCDO.stopEpoch(A1 - DELTA, 0); // boundary: drop == DELTA

    uint256 balAA = AAtranche.balanceOf(user);
    vm.prank(user);
    idleCDO.requestWithdraw(balAA, address(AAtranche));

    // BUG: user got a normal request, not an instant receipt
    assertGt(strategy.withdrawsRequests(user), 0);
    assertEq(strategy.instantWithdrawsRequests(user), 0); // should be > 0 per "min delta" doc

    // user cannot claim until next epoch end: frozen for epochDuration
    vm.expectRevert();
    vm.prank(user);
    idleCDO.claimWithdrawRequest();
}
```

Uncertainty note: I could not inspect the existing Foundry test suite for this vault within the available iterations, so the PoC harness names are approximate. Also, if `instantWithdrawAprDelta` is intended as a strict exclusion threshold rather than an inclusive minimum (the NatSpec wording is ambiguous), the issue reduces to a documentation inconsistency rather than a freezing bug — but the name and comment ("min apr change to trigger") favor `>=`.
