### Title
B20 token factory permits `initialAdmin = address(0)`, permanently freezing role administration - ([File: crates/common/precompiles/src/b20_factory/logic/v1.rs])

### Summary
The B-20 token factory precompile (`FactoryV1::init_stablecoin`, and the parallel path used for the Asset variant) accepts a caller-supplied `initialAdmin` address and only grants the `DefaultAdmin` role when that address is non-zero, silently skipping role assignment when `initialAdmin == address(0)`. This mirrors the reported analog bug class in `PassThroughWalletFactory`/`PassThroughWalletImpl` — an owner/admin field is taken directly from an external-transaction parameter with no non-zero validation, and once the zero value is committed, there is no way to ever recover privileged control.

### Finding Description
`FactoryV1::init_stablecoin` builds the new token, emits `B20Created`, and then conditionally grants the `DefaultAdmin` role: [1](#0-0) 

If `common.initial_admin` is `Address::ZERO`, the `grant_role_unchecked` call is skipped entirely, so `role_member_count(DefaultAdmin)` stays at `U256::ZERO` for the newly created token. The same "grant only if non-zero" pattern and the resulting zero-admin-member state are explicitly exercised for the Asset variant: [2](#0-1) 

Every subsequent privileged mutation on the token (granting roles, setting role admins, policy updates gated to `DefaultAdmin`, etc.) is guarded by `ensure_role_admin_mutations_available`, which explicitly reverts once `role_member_count(DefaultAdmin) == 0`: [3](#0-2) [4](#0-3) 

This is confirmed by the golden test asserting that an admin-less token permanently reverts `grantRole`: [5](#0-4) 

Because there is no mechanism to bootstrap a `DefaultAdmin` from zero (unlike ownership-transfer patterns where a non-zero prior owner could reassign), a token created with `initialAdmin = address(0)` becomes permanently unmanageable: no address can ever grant `Mint`, `Pause`, `Metadata`, `Seize` or any other role, nor call `updatePolicy` gated to `DefaultAdmin`. This is directly analogous to the reported issue: an external, single-transaction call (here, `createB20` invoked by any B-20 token creator through the factory precompile) accepts an unchecked zero address for the owner/admin role, and the missing zero-address guard converts what should be a valid initialization parameter into a permanent loss of administrative capability.

### Impact Explanation
The impact is a permanent freezing of the token's administrative capability: once `initialAdmin = address(0)` is passed to `createB20`, no account can ever be granted `DefaultAdmin`, `Mint`, `Pause`, `Metadata`, `Seize`, or any other privileged role for that token instance, and no policy requiring `DefaultAdmin` gating can ever be updated. This is a protocol-level "permanent freezing of funds/functionality" class issue (the token becomes unmanageable for its entire lifetime — e.g., minting, pausing in an emergency, or seizure/compliance actions can never be authorized), matching the "permanent freezing of funds" acceptance criterion. The severity is bounded by the fact that this only affects the specific newly-created token instance (not the whole chain or other tokens), but for that token it is a complete, irreversible loss of privileged administrative control.

### Likelihood Explanation
Likelihood is significant: `createB20` is a public precompile entry point reachable by any transaction sender ("B20 token creator") who supplies `B20AssetCreateParams`/`B20StablecoinInit`-style parameters including `initialAdmin`. No special privilege is required to trigger this — a user could pass `address(0)` for `initialAdmin` either by mistake (e.g. a misconfigured deployment script or front-end default) or, in more benign cases, attempt to create an "ownerless" token unaware that it permanently disables all future administrative actions on that specific token, including responses that might be needed (e.g., pausing a compromised deployment or updating compliance policies).

### Recommendation
Reject zero-address `initialAdmin` in the B20 factory initialization path (`FactoryV1::init_stablecoin`, and the corresponding Asset-variant path) by validating `!common.initial_admin.is_zero()` before proceeding, and reverting the `createB20` call (e.g., with an `IB20::InvalidAdmin`-style error) rather than silently creating an admin-less token. This mirrors the recommended fix from the reported analog — validating a non-zero owner/admin at the point of initialization rather than after the fact.

### Proof of Concept
1. Caller (any unprivileged transaction sender) calls the B20 factory precompile's `createB20` with `variant = ASSET` (or `STABLECOIN`) and `params.initialAdmin = address(0)`.
2. `FactoryV1::init_stablecoin` (or the Asset-variant equivalent) executes; because `common.initial_admin.is_zero()` is true, the `grant_role_unchecked(DefaultAdmin, …)` call at [1](#0-0)  is skipped.
3. The new token is created successfully with `role_member_count(DefaultAdmin) == 0`, as directly demonstrated by the golden test at [2](#0-1) .
4. Any subsequent call to `grantRole`, `setRoleAdmin`, or other `DefaultAdmin`-gated operation on this token reverts with `AccessControlUnauthorizedAccount` permanently, as shown at [5](#0-4) , confirming the token can never regain an administrator.

    /// Ensures role-admin mutations are still reachable.
    fn ensure_role_admin_mutations_available<S: AssetAccounting, A: PolicyAccounting>(
        &self,
        token: &B20AssetToken<S, A>,
        caller: Address,
    ) -> Result<()> {
        let admin_role = B20TokenRole::DefaultAdmin.id();
        if token.accounting().role_member_count(admin_role)? == U256::ZERO {
            return Err(BasePrecompileError::revert(IB20::AccessControlUnauthorizedAccount {
                account: caller,
                neededRole: admin_role,
            }));
        }
        Ok(())
    }
