### Title
Instruction-supplied `decimals` field trusted without mint verification causes misreported token amounts in parsed transactions - (File: transaction-status/src/parse_token.rs)

### Summary
`parse_token` builds the JSON-RPC "parsed" representation of SPL Token `*Checked` instructions (`TransferChecked`, `ApproveChecked`, `MintToChecked`, `BurnChecked`) by taking the `decimals` value directly from the raw, attacker-controlled instruction data and using it to compute `tokenAmount.uiAmount`/`uiAmountString`, without ever cross-checking it against the real decimals of the referenced mint account.

### Finding Description
For `TransferChecked` and `ApproveChecked`, the parser does: [1](#0-0) 
and for `MintToChecked`/`BurnChecked`: [2](#0-1) 

In each case, `SplTokenAdditionalDataV2::with_decimals(decimals)` is constructed purely from the `decimals` field embedded in the instruction's raw byte payload — a value fully controlled by whoever crafts the transaction message — and is fed straight into `token_amount_to_ui_amount_v3` to compute the displayed `uiAmount`/`uiAmountString`: [3](#0-2) 

On-chain, the SPL Token program's `*Checked` instructions are supposed to validate that the caller-supplied `decimals` matches the real mint's `decimals`, rejecting the transaction if it doesn't. However, `parse_token` performs purely **client-side/RPC-side decoding for display purposes** (used by `jsonParsed` encoding in `getTransaction`, `getBlock`, `getConfirmedSignaturesForAddress2`, etc.) and never fetches or validates against the actual mint account's decimals — it blindly trusts the instruction payload. This mirrors the reported bug class exactly: the conversion precision (`decimals`) is decoupled from the authoritative mint state, and no runtime check enforces they must match.

This differs from the correctly-implemented, bank-state-aware paths in `rpc/src/rpc.rs`'s `get_token_account_balance`/`get_token_supply` and `rpc/src/parsed_token_accounts.rs`, which fetch `get_mint_owner_and_additional_data` from the live `Bank` to obtain true decimals: [4](#0-3) 

### Impact Explanation
Any user submitting a transaction (even one that will fail on-chain, since instruction parsing operates on the raw message and is independent of execution outcome) can pick an arbitrary `decimals` value in a `TransferChecked`/`ApproveChecked`/`MintToChecked`/`BurnChecked` instruction. When any RPC consumer queries that transaction/block with `encoding=jsonParsed`, the returned `tokenAmount.uiAmount`/`uiAmountString` will reflect the attacker-chosen decimals rather than the mint's real decimals — e.g. an amount of `1` raw unit with a legitimate mint of 9 decimals could be displayed as `1` (decimals=0) instead of `0.000000001`, or vice versa, an arbitrarily inflated/deflated "human readable" amount. This is a decoder misreporting issue: any downstream tool, exchange, explorer, or wallet relying on Agave's own `jsonParsed` instruction data for a "Checked" instruction's human-readable amount can be misled about the true value transferred/approved/minted/burned, purely as a read-only side effect of parsing a transaction that touches unprivileged, user-supplied instruction data.

### Likelihood Explanation
High likelihood: this requires no privileged role, no special account setup beyond crafting any transaction (or even a transaction guaranteed to fail on-chain) containing a `*Checked` SPL Token instruction with a deliberately wrong `decimals` byte, and one single `jsonParsed` RPC query to trigger the misreporting.

### Recommendation
`parse_token` should not compute a display "amount" using a caller-supplied decimals figure without validating it. Either drop the derived `uiAmount`/`uiAmountString` computation for `*Checked` instructions when no separately-verified mint decimals are available, or explicitly document/flag in the parsed output that `decimals` originates from unverified instruction data (as opposed to the mint's actual state) so that consumers do not misinterpret it as ground truth.

### Proof of Concept
1. Craft a transaction containing an SPL Token `TransferChecked` instruction where the real mint has `decimals = 9`, but encode the instruction's `decimals` field as `0`.
2. Submit (or simply construct and simulate/fail) the transaction and fetch it back via `getTransaction`/`getBlock` with `encoding: "jsonParsed"`.
3. Observe that the parsed instruction's `info.tokenAmount.uiAmount` is computed using `decimals = 0`, e.g. a raw `amount = 1000000000` is reported as `uiAmount: 1000000000` / `"1000000000"` instead of the true `1.0`, matching the code path at [1](#0-0)  feeding straight into [5](#0-4) , with no lookup of the actual mint's decimals anywhere in this code path.

pub fn token_amount_to_ui_amount_v3(
    amount: u64,
    additional_data: &SplTokenAdditionalDataV2,
) -> UiTokenAmount {
    let decimals = additional_data.decimals;
    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =
        additional_data.interest_bearing_config
    {
        let ui_amount_string =
            interest_bearing_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else if let Some((scaled_ui_amount_config, unix_timestamp)) =
        additional_data.scaled_ui_amount_config
    {
        let ui_amount_string =
            scaled_ui_amount_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else {
        let ui_amount = 10_usize
            .checked_pow(decimals as u32)
            .map(|dividend| amount as f64 / dividend as f64);
        (ui_amount, real_number_string_trimmed(amount, decimals))
    };
    UiTokenAmount {
        ui_amount,
        decimals,
        amount: amount.to_string(),
        ui_amount_string,
    }
}

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
