### Title
Mid-epoch deposits mint tranche shares and strategy tokens on the nominal `_amount`, not the received balance delta — fee-on-transfer underlying inflates NAV and blocks end-of-epoch payouts - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.depositDuringEpoch` pulls `_amount` of underlying from the depositor but mints tranche tokens and strategy tokens against the full nominal `_amount`, without measuring the balance delta. Unlike `IdleCDO._deposit` / `IdleCDOCreditVault._deposit`, which mint on `_contractTokenBalance(_token) - _preBal`, the mid-epoch path never validates what was actually received. For an underlying that takes a fee on transfer, the vault receives less than `_amount` while crediting principal plus prorated interest on `_amount`, creating unbacked shares and an inflated `expectedEpochInterest`. This is the same virtual-balance vs actual-balance mismatch class as the external report: at epoch end the real balance cannot cover the claims, so `collectWithdrawFunds` / borrower repayment accounting reverts or honest tranche holders absorb the shortfall.

### Finding Description
In `depositDuringEpoch` the flow is:

```solidity
_transferUnderlyingsFrom(msg.sender, address(this), _amount);   // no delta measured
...
uint256 interest = _calcInterest(_amount) * (remaining + buffer) / (epochDuration + buffer);
...
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
_mintShares(_tranche, msg.sender, _minted, _amount);
expectedEpochInterest += interest;
IdleCreditVault(strategy).mintStrategyTokens(_amount);          // full _amount credited
``` [1](#0-0) 

By contrast the base deposit path is explicitly delta-based:

```solidity
uint256 _preBal = _contractTokenBalance(_token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
_minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, msg.sender, _tranche);
``` [2](#0-1) 

So the epoch-variant deposit assumes `received == _amount`. With a fee-on-transfer token (fee `f`), each call:

- transfers in only `_amount - f`,
- mints `( _amount + trancheInterest ) * supply / expectedFinal` tranche shares — i.e. claims priced on the full `_amount` plus interest,
- increments `expectedEpochInterest` by interest computed on `_amount`,
- mints `_amount` of strategy tokens via `mintStrategyTokens`, so `getContractValue()`/NAV treats `_amount` as deployed principal while only `_amount - f` exists.

`_skimDonatedAssets()` is called before the deposit, so the shortfall is not absorbed as a donation — it is silently booked into tranche NAV. None of the guards in `depositDuringEpoch` (`isEpochRunning`, `isWalletAllowed`, `isDepositDuringEpochDisabled`, `_guarded`, `_trancheTotSupply == 0` check) measure the received delta. The same nominal-vs-actual pattern exists in `TrancheWrapper._deposit` / `IdleTokenWrapper._deposit` and `IdleTokenFungible.mintIdleToken` (`lastNAV += _amount` after an unmeasured `safeTransferFrom`), which compound the mismatch for depositors entering through the wrappers.

### Impact Explanation
Broken invariant: fair mint/burn and solvency — one deposited unit must back at most one claim. A KYC-passed lender (or any EOA once `isWalletAllowed` gates pass) deposits `_amount` of a fee-on-transfer underlying mid-epoch, pays `f` in transfer tax, and receives tranche shares redeemable for approximately `_amount + trancheInterest` at epoch end. The `f` deficit is socialized: either the borrower repayment plus real deposits are insufficient to pay all `collectWithdrawFunds` claims (last withdrawers/liquidation-equivalent payouts revert — the same "withdrawal blocked by balance mismatch" impact as the external issue), or earlier withdrawers drain funds belonging to later claimants. Loss is `f` plus the interest credited on the never-received `f`, per malicious deposit, and can be repeated every epoch.

### Likelihood Explanation
Likelihood is conditional: it requires the vault's `token` to charge a fee (or otherwise deflate) on transfer. The contracts make no non-FoT assumption — `_transferUnderlyingsFrom` is a plain `safeTransferFrom` with no delta assertion on this path — and the base `_deposit` already demonstrates the protocol intends delta-based accounting, so the mid-epoch path is simply missing that protection. The attacker needs only to be wallet-allowed (KYC-passing lender is in the unprivileged-attacker set) and an epoch running with `isDepositDuringEpochDisabled == false`. One caveat not fully verified in this scan: whether deployed pool currencies are enumerable FoT tokens; however the audit class targets the missing defensive check itself, and the accounting corruption also applies to any rebasing/deflationary underlying behavior.

### Recommendation
Measure the received delta in `depositDuringEpoch`, mirroring `IdleCDO._deposit`: record `_preBal` before `_transferUnderlyingsFrom`, compute `_received = _contractTokenBalance(_token) - _preBal` after it (and after `_skimDonatedAssets`), and use `_received` instead of `_amount` for `_calcInterest`, the `_minted` formula, `_mintShares`, `expectedEpochInterest`, and `mintStrategyTokens`. Apply the same delta accounting in `TrancheWrapper._deposit`, `IdleTokenWrapper._deposit`, and `IdleTokenFungible.mintIdleToken` (which currently does `lastNAV += _amount` without a delta check), or explicitly revert on `received != _amount` if FoT underlyings are not supported.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// fork mainnet, deploy/attach to a live IdleCDOEpochVariant + IdleCreditVault pair
// Deploy MockFeeOnTransfer underlying (or use an FoT token if the vault's token is one)
FeeOnTransferToken foT;  // e.g. 1% burn on transfer
address attacker = kycLender;

// setup: honest lender seeds tranche so _trancheTotSupply > 0
vm.prank(honestLender); vault.depositAA(1_000_000e6);   // buffer phase
vm.prank(manager); vault.startEpoch(...);               // epoch running

uint256 amount = 100_000e6;
uint256 balBefore = foT.balanceOf(address(vault));
uint256 aaSupplyBefore = IERC20(vault.AATranche()).totalSupply();

vm.prank(attacker);
vault.depositDuringEpoch(amount, vault.AATranche());

uint256 received = foT.balanceOf(address(vault)) - balBefore;
assertLt(received, amount);                              // fee taken, vault got less

// attacker minted shares priced on `amount + trancheInterest`
uint256 minted = IERC20(vault.AATranche()).balanceOf(attacker);
// claim value at epoch end:
uint256 claim = minted * vault.virtualPrice(vault.AATranche()) / 1e18;
assertGt(claim, received);                               // unbacked ~ fee + interest on fee

// strategy tokens minted for full amount -> NAV inflated
assertEq(IERC20(strategy).balanceOf(address(vault)), amount);

// end of epoch: stopEpoch, borrower repays real principal+interest,
// then honest + attacker collectWithdrawFunds; last claimant reverts or is shorted
vm.prank(borrower); strategy.repay(...);
vm.expectRevert(); // or assert honest < expected payout
vault.collectWithdrawFunds();
```

The assertion `claim > received` demonstrates direct theft-by-dilution; the final revert demonstrates the blocked-payout impact identical to the external report's frozen liquidation. Note: a runnable PoC requires the vault's `token` to actually be FoT or a mock vault wired to an FoT token; if deployed pools only use non-FoT currencies (e.g., plain USDC), the impact is latent rather than currently exploitable, and severity should be downgraded accordingly.

      // the time the depositor actually participates (remaining epoch + full buffer)

      // the total time baked into the scaled APR (epoch + buffer).

    uint256 pendingFees = pendingWithdrawFees;

    // interest this deposit will earn for the tranche over the remaining time (net of fees)

      _netGainAfterFees(interest, _calculateManagementFee(_amount, remaining)),
      _tranche

    // pre-deposit expected final NAV for existing holders.
    // This won't ever be zero as we checked _trancheTotSupply and we seed initial NAV at tranche creation
