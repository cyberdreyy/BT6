### Title
Storage-fee bypass for Global Contract deployment when a later action in the same receipt fails and triggers rollback - ([File: runtime/runtime/src/global_contracts.rs::action_deploy_global_contract], [File: runtime/runtime/src/lib.rs::apply_action_receipt])

### Summary
`action_deploy_global_contract` only refuses to create a `GlobalContractDistributionReceipt` when *its own* balance check fails (`global_contracts.rs:40-47`), which is correct. However, once it succeeds it merges `tokens_burnt` and pushes the distribution receipt into the receipt-level `ActionResult` (`initiate_distribution`, `global_contracts.rs:52-59`), and the surrounding `apply_action_receipt` loop in `runtime/runtime/src/lib.rs` unconditionally forwards `result.new_receipts` and unconditionally folds `result.tokens_burnt` into the outcome's `tokens_burnt`, even when a *later* action in the same receipt causes the whole receipt to fail and `state_update.rollback()` to be invoked.

### Finding Description
In `apply_action_receipt` (`runtime/runtime/src/lib.rs:891-951`), actions of a receipt are executed sequentially; each action's `ActionResult` is merged into the receipt-level `result` via `result.merge(new_result)?` (`lib.rs:927`) *before* the loop checks for a later error and `break`s (`lib.rs:947-950`). This means that if action *N* (`DeployGlobalContract`) succeeds — debiting `storage_cost` from the in-memory `account`, adding it to `result.tokens_burnt`, and pushing a `GlobalContractDistributionReceipt` into `result.new_receipts` via `initiate_distribution` (`global_contracts.rs:34-59`) — and a subsequent action *N+1* in the same receipt fails (or the post-loop `check_storage_stake` at `lib.rs:955-975` fails, e.g. because a `Stake` action moved the remaining balance into `locked`), then:

- `account` is never persisted back to the trie via `set_account` (only done when `result.result.is_ok()`, `lib.rs:958-959`), so the storage-cost debit never reaches state.
- `state_update.rollback()` (`lib.rs:1031-1033`) discards any direct trie writes made during the receipt, including the nonce increment written by `increment_nonce` (`global_contracts.rs:162,186`).
- Nevertheless, `result.tokens_burnt` (already merged from the successful deploy action) is unconditionally folded into `tx_burnt_amount`/`tokens_burnt` for the outcome at `lib.rs:1048` — this line is *not* gated on `result.result` being `Ok`.
- `result.new_receipts` (which contains the `GlobalContractDistributionReceipt`) is unconditionally drained and forwarded via `receipt_sink.forward_or_buffer_receipt` at `lib.rs:1139-1184` — again, not gated on `result.result`.

The consequence: the account never actually pays for the global-contract storage (the debit is rolled back / never committed), yet (a) the ledger accounting records the storage cost as burnt, and (b) a `GlobalContractDistributionReceipt` is emitted and will proceed to persist the contract code into global storage across shards via `apply_global_contract_distribution_receipt` / `apply_distribution_current_shard` (`global_contracts.rs:110-234`), independent of the parent receipt's failure and rollback.

### Impact Explanation
This is a fee-payment bypass: an attacker can get a global contract published to on-chain global storage (real state growth on every shard that processes the forwarded distribution receipt) without the storage cost ever being actually debited from their account, because the parent receipt that would have charged them fails and rolls back. Simultaneously it creates a value-conservation/accounting divergence — `tokens_burnt` is counted for supply/burn bookkeeping purposes for tokens that were never actually removed from any account balance, which is exactly the invariant violation the question targets (no distribution receipt should exist without its cost being actually charged and persisted).

### Likelihood Explanation
Precondition is only that the attacker controls the ordering/content of actions within a single receipt they submit (a normal capability of any unprivileged client). The attacker needs: sufficient balance to reach the `DeployGlobalContract` action successfully, and a subsequent action in the same receipt engineered to make the overall receipt fail (e.g., a `Stake` action that moves the remaining `amount` into `locked` so the post-loop `check_storage_stake` at `lib.rs:955-975` fails with `LackBalanceForState`, or any other action-level failure after the deploy action has already succeeded). This is cheap and repeatable. I was not able to fully verify the internals of `ActionResult::merge` (not inspected) to rule out any special-case stripping of `new_receipts`/`tokens_burnt` on eventual failure, nor did I execute the PoC — this residual uncertainty should be resolved by an actual unit/integration test.

### Recommendation
Gate the emission of `result.new_receipts` and the inclusion of `result.tokens_burnt` in the outcome's burnt-token accounting on `result.result.is_ok()` (mirroring the `state_update.rollback()`/`commit()` branch at `lib.rs:1024-1034`), so that when a receipt fails and its state is rolled back, any receipts and token debits that were tentatively staged by earlier successful actions in the same batch are discarded along with the trie state, not silently forwarded/counted.

### Proof of Concept
Add a runtime integration test (e.g. under `runtime/runtime/src/tests` or `test-loop-tests/src/tests/global_contracts.rs`) that:
1. Funds an account with balance just above the global-contract storage cost.
2. Submits a receipt/transaction with actions `[DeployGlobalContract(code), Stake(amount = remaining_balance)]` where the `Stake` action moves enough of the account's spendable `amount` into `locked` so that the post-loop `check_storage_stake` fails with `LackBalanceForState`.
3. Asserts the execution outcome status is `Failure(ActionError::LackBalanceForState)`.
4. Asserts that the account's on-chain balance is fully restored to its pre-receipt value (no residual debit).
5. Asserts `result.new_receipts`/emitted receipts do **not** contain a `GlobalContractDistributionReceipt`, and that no such contract code is ever persisted at `TrieKey::GlobalContractCode` on any shard.

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}
