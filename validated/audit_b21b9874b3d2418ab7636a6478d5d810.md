### Title
Stale confirmations from deleted keys still count toward `num_confirmations`, letting a multisig request execute below the live-member threshold - (File: `multisig/src/lib.rs`)

### Summary
The `MultiSigContract` in `multisig/src/lib.rs` stores confirmations per `request_id` as a `HashSet<PublicKey>` and only checks `confirmations.len() + 1 >= self.num_confirmations` to decide whether to execute a request. When a key is deleted via `MultiSigRequestAction::DeleteKey`, the cleanup logic only removes *requests originated by* that key, not that key's *confirmations left on other pending requests*. This breaks the intended equality "confirmations counted == confirmations from currently-live members," letting a request execute with contributions from a revoked key, i.e., below the live threshold.

### Finding Description
`confirm()` increments/consults a per-request `HashSet<PublicKey>` and compares its size to `num_confirmations`: [1](#0-0) 

When a `DeleteKey` action is executed, the cleanup only removes requests whose *originating* `signer_pk` equals the deleted key, and removes the deleted key's `num_requests_pk` counter — it does **not** scan and purge that key's public key from the `confirmations` sets of any *other* pending requests it had merely confirmed (not originated): [2](#0-1) 

Consequently, a request `X` originated by key A and confirmed by key B before B is removed retains `{A, B}` in `confirmations[X]` even after B ceases to be a valid signer. A subsequent confirmation by key C reaches `len() == num_confirmations` (e.g. 3) and triggers execution via `execute_request`, even though only 2 of the 3 confirming public keys (A, C) are currently live members — B's stale confirmation is what pushed the count over the threshold.

This is the direct analog of the reported Yeti Finance bug: there, a caller-provided value (`_collateral`) was trusted without checking it against the whitelist actually governing behavior, and `getIndex` silently fell back to index 0, corrupting accounting for a token that was never validated. Here, a caller-provided/stored value (a revoked `PublicKey`) is trusted as a valid confirming member without being checked against the current, live key set, silently counting toward the `num_confirmations` threshold. In both cases a value that should have been re-validated against the authoritative set (whitelist / live keys) is instead accepted implicitly, corrupting an authorization/accounting invariant.

The binding broken:
`confirmations[request_id].len() >= num_confirmations` was intended to imply `|{live members who confirmed}| >= num_confirmations`, but the code only guarantees `|{public keys that confirmed, live or not}| >= num_confirmations`.

### Impact Explanation
This matches the Critical impact category "a multisig request executed below threshold." Any privileged multisig action — `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc. — can be executed with effectively fewer live, authorized approvals than `num_confirmations` mandates, because a revoked key's earlier confirmation is never invalidated on requests it did not itself originate. This directly undermines the K-of-N custody guarantee the contract exists to provide, and can move funds (`Transfer`) or grant access (`AddKey`) with insufficient live authorization.

### Likelihood Explanation
This requires only ordinary, expected multisig operation, no compromised owner, no bypassed initialization: a key holder confirms a pending request, is later removed via a normal `DeleteKey` request (e.g., off-boarding an employee, rotating a compromised key), and the previously-pending request is later pushed over threshold by one more live confirmation. This is a realistic, foreseeable sequence for any long-lived multisig with pending requests during key rotation — not a contrived edge case requiring privileged access beyond normal key-holder actions already granted to legitimate members.

### Recommendation
When executing `DeleteKey`, also purge the deleted public key from every entry in `self.confirmations` (not just requests it originated), or alternatively re-validate at `confirm()`/execution time that every public key in `confirmations[request_id]` is still a member of the multisig's current key set (e.g., by checking against `AccessKey`s on the account) before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(3)` with 4 access keys: A, B, C, D.
2. Key A calls `add_request_and_confirm(request_X)` where `request_X` is e.g. `Transfer { amount }` to an attacker-controlled/arbitrary receiver. `confirmations[X] = {A}`.
3. Key B calls `confirm(X)`. `confirmations[X] = {A, B}` (2/3, not yet executed).
4. Separately, the legitimate owners create and fully confirm a `DeleteKey { public_key: B }` request (requiring 3 confirmations from A, C, D) to revoke B (e.g., B's device was lost). This executes `execute_request`'s `DeleteKey` branch: [2](#0-1) 
   Only requests *originated* by B are deleted; request `X` (originated by A) is untouched, and `confirmations[X]` still contains B's key.
5. Key C — the only other live signer — calls `confirm(X)`. `confirmations[X].len() + 1 == 3 >= num_confirmations(3)`, so `execute_request(request_X)` fires and the `Transfer` executes.
6. Result: `request_X` executed with only 2 currently-live confirming members (A, C) out of the intended 3-of-4 live scheme — B's confirmation, from a key already revoked, was silently counted, violating the "confirmations counted == live-member confirmations" invariant and moving funds with an under-threshold authorization set.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
