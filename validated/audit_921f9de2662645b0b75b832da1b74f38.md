### Title
Unprotected `initializeConfig` on `BridgeCommittee` Proxy Allows Any Caller to Inject a Malicious `BridgeConfig`, Corrupting Bridge Governance and Enabling Illegitimate Token Unlocks — (`File: bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig()` has no access control. The deployment script (`deploy_bridge.s.sol`) deploys the `BridgeCommittee` proxy in one transaction and calls `initializeConfig` in a later, separate transaction. During the window between those two transactions, any unprivileged caller can frontrun the deployer and permanently bind the committee to a malicious `BridgeConfig` contract, corrupting chain-ID domain separation and token-address resolution for the entire bridge.

---

### Finding Description

`BridgeCommittee.initializeConfig` is declared `external` with only a single guard:

```solidity
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
``` [1](#0-0) 

There is no `onlyOwner`, `initializer`, or any other caller restriction. The `config` field starts as `address(0)` after the proxy's `initialize()` call, so the guard passes for any caller until the deployer's `initializeConfig` transaction lands.

The deployment script issues these as distinct broadcast transactions:

1. **Tx A** – `Upgrades.deployUUPSProxy("BridgeCommittee.sol", abi.encodeCall(BridgeCommittee.initialize, ...))` — proxy is live, `config == address(0)`.
2. **Tx B** – `Upgrades.deployUUPSProxy("BridgeConfig.sol", ...)` — config contract is deployed.
3. **Tx C** – `BridgeCommittee(bridgeCommittee).initializeConfig(address(bridgeConfig))` ← **frontrunnable**.
4. **Tx D** – `committeeImplementation.initializeConfig(address(bridgeConfig))` ← **also frontrunnable**. [2](#0-1) 

Between Tx A and Tx C the proxy's `config` slot is `address(0)`. An attacker who observes Tx A in the mempool can submit a higher-gas call to `initializeConfig(maliciousConfig)` and win the race. Because the guard then permanently blocks any second call (`"Config already initialized"`), the deployer's Tx C reverts and the bridge is permanently bound to the attacker's contract.

The `config` object is consumed in two critical paths:

**Chain-ID validation** (every non-TOKEN_TRANSFER governance message):
```solidity
require(
    message.chainID == committee.config().chainID(), "MessageVerifier: Invalid chain ID"
);
``` [3](#0-2) 

**Token-address resolution** (every ERC-20 unlock):
```solidity
uint256 erc20AdjustedAmount = BridgeUtils.convertSuiToERC20Decimal(
    IERC20Metadata(config.tokenAddressOf(tokenTransferPayload.tokenID)).decimals(), ...
);
_transferTokensFromVault(...);
``` [4](#0-3) 

---

### Impact Explanation

A malicious `BridgeConfig` can:

1. **Return an arbitrary `chainID()`** — breaking chain-ID domain separation. If the attacker's config returns the chain ID of another EVM chain where the same committee keys are used, signed messages from that chain pass the chain-ID check on this chain, enabling cross-chain replay and illegitimate token unlocks from the vault.

2. **Return attacker-controlled `tokenAddressOf()`** — redirecting vault withdrawals to attacker-controlled ERC-20 contracts, enabling theft of bridged assets.

3. **Permanently DoS all governance operations** — if the malicious config returns a chain ID that never matches any real message, every `updateBlocklistWithSignatures`, `upgradeWithSignatures`, and `executeEmergencyOpWithSignatures` call reverts forever, bricking bridge governance.

This matches the Critical impact class: **bridge governance bypass that enables illegitimate mint or unlock**.

---

### Likelihood Explanation

- The attack requires only a standard Ethereum account and the ability to observe the mempool (no special privilege).
- The vulnerable window exists on every fresh deployment of the bridge.
- The `initializeConfig` function is publicly visible in the ABI and trivially callable.
- The one-time-set guard means a single successful frontrun is sufficient and irreversible. [5](#0-4) 

---

### Recommendation

Merge `initializeConfig` into the `initialize` function so that the committee and its config are set atomically in a single transaction:

```solidity
function initialize(
    address[] memory committee,
    uint16[] memory stake,
    uint16 minStakeRequired,
    address _config          // add config here
) external initializer {
    __CommitteeUpgradeable_init(address(this));
    __UUPSUpgradeable_init();
    // ... existing stake setup ...
    config = IBridgeConfig(_config);
}
```

This eliminates the uninitialized window entirely. If a two-step deployment is unavoidable, restrict `initializeConfig` to the deployer address (e.g., `onlyOwner` or a deployer role set during `initialize`).

### Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "../contracts/BridgeCommittee.sol";
import "../contracts/interfaces/IBridgeConfig.sol";

contract MaliciousConfig is IBridgeConfig {
    // Returns chain ID 0 — matches no legitimate chain, DoS-ing all governance,
    // OR returns the chain ID of another bridge deployment to enable replay.
    function chainID() external pure override returns (uint8) { return 0; }
    function tokenAddressOf(uint8) external pure override returns (address) {
        return address(0xDEAD); // attacker-controlled token contract
    }
    // ... other IBridgeConfig stubs ...
}

contract FrontrunAttack {
    function attack(address bridgeCommitteeProxy) external {
        MaliciousConfig malicious = new MaliciousConfig();
        // config == address(0) after proxy deployment, before deployer's initializeConfig tx
        BridgeCommittee(bridgeCommitteeProxy).initializeConfig(address(malicious));
        // Now committee.config() == malicious permanently.
        // Deployer's subsequent initializeConfig call reverts with
        // "BridgeCommittee: Config already initialized".
    }
}
```

After the attack:
- `committee.config().chainID()` returns the attacker's value, breaking chain-ID checks in `MessageVerifier`.
- `committee.config().tokenAddressOf(id)` returns the attacker's address, redirecting vault withdrawals.
- `initializeConfig` cannot be called again — the corruption is permanent. [1](#0-0) [6](#0-5) [3](#0-2)
