## Analysis

The report's root cause — an unguarded low-level `.call{value: amount}("")` that reverts the entire state transition (mint/burn/transfer) whenever the recipient is a contract that rejects ETH — has a direct analog in this repository's destination-escrow withdrawal path.

### Title
Malicious maker can permanently block `EscrowDst.withdraw`/`publicWithdraw` for native-token swaps by using a non-payable contract as the receiving address, freezing the resolver's escrowed funds - (File: `contracts/EscrowDst.sol`)

### Summary
`EscrowDst._withdraw` unconditionally sends the destination-chain swap amount to `immutables.maker.get()` via `_uniTransfer` → `_ethTransfer`, which uses a raw `.call` and reverts on failure with no fallback or escrow mechanism, exactly like the reported `LibAddress.transferEth` pattern.

### Finding Description
In `_withdraw`, after fee transfers, the remaining `amount` is sent to the maker's address: [1](#0-0) 

`_ethTransfer` uses a bare `.call` and reverts the whole transaction if the recipient rejects the transfer: [2](#0-1) 

The `maker` value embedded in the destination escrow's `Immutables` originates from `order.receiver` (or `order.maker` if unset), which is set by the order maker — an unprivileged party — at order-creation time on the source chain: [3](#0-2) 

The resolver later reconstructs `dstImmutables` (including this `maker` field, unchanged) from the `SrcEscrowCreated` event data and calls `createDstEscrow`, funding the escrow with native ETH when `token == address(0)`: [4](#0-3) 

If the maker sets their receiving address to a contract with no `receive`/`fallback` function (or one that always reverts), then both `withdraw` (private, taker-only) and `publicWithdraw` (any access-token holder) on `EscrowDst` will unconditionally revert for the full withdrawal window, because both routes funnel into the same `_withdraw` function that pays `immutables.maker.get()`: [5](#0-4) 

There is no `withdrawTo`-style override on `EscrowDst` (unlike `EscrowSrc.withdrawTo`) that would let the resolver redirect the payout to a different, valid address, so the swap can never be completed via the withdrawal path once such a maker address is chosen.

### Impact Explanation
Because withdrawal can never succeed, the resolver's capital (the destination-chain native amount they deposited plus their safety deposit) is locked in the `EscrowDst` clone for the entire interval between `DstWithdrawal`/`DstPublicWithdrawal` and `DstCancellation`. Funds are only recoverable once `cancel()` becomes callable after the cancellation timelock, at which point tokens are returned to `taker` (the resolver), not the maker: [6](#0-5) 

This is a temporary freezing of funds during the live swap lifecycle triggered entirely by an unprivileged maker's chosen receiving address — matching the bounty's High-severity criterion for "temporary freezing of funds during the live swap lifecycle." It does not enable outright theft (funds return via `cancel`), but it denies the intended atomic-swap settlement path and forces resolvers to eat the full timelock delay whenever a maker (deliberately or accidentally) supplies an incompatible contract address.

### Likelihood Explanation
Any order maker can set `order.receiver` to an arbitrary contract address without validation anywhere in `_postInteraction` or `createDstEscrow`. No code-size, EOA, or "can-receive-ETH" check exists on `maker`/`order.receiver`. Native-token destination swaps (`token == address(0)`) are a normal, supported configuration, so the trigger condition is trivial and fully reachable by an unprivileged user through the standard order-fill flow.

### Recommendation
For `EscrowDst._withdraw` (and any other maker-directed native transfer), avoid making the overall withdrawal atomic with the maker's ETH acceptance:
- Wrap the native transfer to the maker in a try/catch (or check the low-level call's success without reverting the whole function), and on failure deposit the amount into WETH (or an internal claimable balance) credited to the maker, allowing the maker to claim it separately later.
- Alternatively, require `order.receiver`/`maker` code-size/EOA validation at order creation for native-token destination legs, or expose a resolver-controlled fallback recipient path analogous to `EscrowSrc.withdrawTo`.

### Proof of Concept
1. Maker creates a Fusion order with `receiver` set to a contract `Grief` with no `receive`/`fallback` (or one that always `revert()`s), and `dstToken == address(0)` (native destination asset).
2. Resolver fills the order on the source chain (`fillOrderArgs`), triggering `_postInteraction`, which records `immutablesComplement.maker = Grief`.
3. Resolver deploys `EscrowDst` via `createDstEscrow{value: amount + safetyDeposit}(dstImmutables, srcCancellationTimestamp)`, funding the clone with native ETH.
4. After `DstWithdrawal` start, resolver (or, after `DstPublicWithdrawal`, any access-token holder) calls `withdraw(secret, immutables)` / `publicWithdraw(secret, immutables)`.
5. `_withdraw` reaches `_uniTransfer(address(0), Grief, amount)` → `_ethTransfer` → `Grief.call{value: amount}("")` fails → `NativeTokenSendingFailure()` reverts the whole withdrawal, for every subsequent attempt during the entire withdrawal window.
6. Resolver's escrowed capital is locked until `DstCancellation` timelock is reached, at which point `cancel()` must be used to recover funds — the swap cannot be atomically completed as designed.

        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
