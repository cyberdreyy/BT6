### Title
Drift-bank deposits bypass `deposit_limit` enforcement via `deposit_no_repay` - ([File: programs/marginfi/src/instructions/drift/deposit.rs])

### Summary
`drift_deposit` never calls `bank.get_remaining_deposit_capacity()` or any deposit-cap check before crediting the user's balance via `bank_account.deposit_no_repay(scaled_balance_change_i80f48)`, unlike `lending_account_deposit`, which explicitly caps the deposit amount using `bank.get_remaining_deposit_capacity()` when `deposit_up_to_limit` is set, and (per the integration test suite) enforces `BankAssetCapacityExceeded` otherwise. This lets an unprivileged user push a Drift bank's total assets arbitrarily far past `bank.config.deposit_limit`.

### Finding Description
`drift_deposit` in <cite repo="Thankgod67Ikhide/marginfi-v2--019" path="programs/marginfi/src/instructions/drift/deposit.rs" start="45|=|58" end="100" /> updates Drift interest, computes `expected_scaled_balance_change`, performs the CPI transfer and CPI `deposit` into Drift, and finally credits the marginfi account with `bank_account.deposit_no_repay(scaled_balance_change_i80f48)` — with no call anywhere in the function to `bank.get_remaining_deposit_capacity()` or `bank.config.is_deposit_limit_active()`.

In contrast, `lending_account_deposit` in [1](#0-0)  explicitly bounds the deposited amount using `bank.get_remaining_deposit_capacity()` when `deposit_up_to_limit` is requested, and per the test suite, fails with `BankAssetCapacityExceeded` when the cap would otherwise be exceeded without that flag set (see `programs/marginfi/tests/user_actions/deposit.rs` and `tests/specs/basic/07_deposit.spec.ts`).

Notably, `Bank::get_remaining_deposit_capacity` in [2](#0-1)  contains explicit logic to scale the limit for `ASSET_TAG_DRIFT` banks via `scale_drift_deposit_limit`, which strongly indicates the `deposit_limit` config is intended to bound Drift-bank exposure as well — yet this capacity function is never invoked from `drift_deposit`. The same pattern (calling `deposit_no_repay` with no capacity check) also appears in `kamino_deposit` and `solend_deposit`, indicating this is a systemic gap across all "integration" deposit paths, not just Drift.

An unprivileged user holding a valid, non-disabled marginfi account can call `drift_deposit` repeatedly (or with a single large `amount`) against a Drift bank whose admin configured a low `config.deposit_limit`, and the deposit will succeed without any cap enforcement, growing the bank's on-chain and Drift-side exposure without bound.

### Impact Explanation
This is an unauthorized bypass of an admin-configured, bank-scoped risk control (deposit cap), allowing the bank's total exposure to a single external integration (Drift) to grow without the bound the admin intended. This directly matches the "bank-configuration bypass allowing unbounded exposure to a single external integration" scope, and is a real state-transition/config-enforcement gap rather than a pure liquidity or oracle issue.

### Likelihood Explanation
Fully reachable by any unprivileged signer with a non-disabled, non-frozen marginfi account and a valid Drift bank/spot-market/user setup — no admin, oracle, or leaked-key preconditions required beyond the admin having set `deposit_limit` (a normal operational configuration). The bypass is deterministic and repeatable on every call to `drift_deposit`.

### Recommendation
Before calling `bank_account.deposit_no_repay(...)` in `drift_deposit` (and equivalently in `kamino_deposit` / `solend_deposit`), check `bank.get_remaining_deposit_capacity()` against the deposited amount (or the resulting total asset value) and either cap the deposit or reject with `BankAssetCapacityExceeded`, mirroring the enforcement in `lending_account_deposit`. Since integration paths already CPI into the external protocol before crediting the local balance, the check should ideally occur pre-CPI (validate `amount` against remaining capacity) to avoid depositing into Drift then failing the whole transaction on the local check — though even a post-CPI failure is safe since the transaction reverts atomically.

### Proof of Concept
Integration test plan (Rust, `programs/marginfi/tests/`):
1. Set up a Drift bank via `setup_bank` test helpers with `config.deposit_limit` set to a low value (e.g., 100 tokens native).
2. Fund a user token account with an amount far exceeding the limit (e.g., 10,000 tokens).
3. Call `drift_deposit` with `amount = 10,000`.
4. Assert the call currently succeeds (`res.is_ok()`) and that `bank.total_asset_shares * bank.asset_share_value` (or the Drift-side scaled balance) now exceeds `bank.config.deposit_limit` — demonstrating the cap was not enforced.
5. Contrast with an equivalent `lending_account_deposit` test on a default-tag bank with the same `deposit_limit`, which fails with `MarginfiError::BankAssetCapacityExceeded` (or caps the amount when `deposit_up_to_limit = true`), confirming the behavioral divergence.
