### Title
Early return in `taskTerminate` skips runner console/Ctrl-handler restoration when `AttachConsole` fails, permanently breaking console-based termination for future jobs - (File: helpers/process/killer_windows.go)

### Summary
`taskTerminate` in `helpers/process/killer_windows.go` calls `FreeConsole()` to detach the runner from its own console before attaching to the target job's console. If the subsequent `AttachConsole(pid)` call fails, the function returns immediately, never executing the "always attempt to restore" block that re-attaches the runner to its parent's console and restores its `Ctrl-C` handler. The runner process is left permanently detached from any console for the remainder of the service's lifetime.

### Finding Description
The relevant code path is: [1](#0-0) 

When `UseWindowsLegacyProcessStrategy` is enabled, `taskTerminate` does:
1. `freeConsole(...)` — detaches the runner from its current console. If this fails, return (no console change happened, safe).
2. `attachConsole(..., uintptr(pid))` — attaches to the target job process's console. **If this fails, the function returns the error at line 85, before reaching the recovery block at lines 92–104.**
3. `setConsoleCtrlHandler(...)` — only reached if step 2 succeeded.

Only after successfully completing all three of the above does the code reach the "always attempt to restore" section: [2](#0-1) 

That comment ("always attempt to restore console and Ctrl-C handler ... so collect any errors together instead of returning early") is contradicted by the actual control flow above it: the early `return err` statements on lines 82, 85, and 88 bypass this restoration block entirely if any of the three preceding calls fail. The question's framing (restoration "attempted but ignored via multierror") is not quite what happens — the restoration calls (`AttachConsole(MaxUint32)`, `SetConsoleCtrlHandler` restore) are never invoked at all in this failure branch, which is a more severe version of the same root cause.

`AttachConsole(pid)` fails in well-documented Windows scenarios that a job script fully controls: if the target process has already exited, or has called `FreeConsole`/`AllocConsole` on itself to manage its own console. A CI job running on a Windows shell/custom executor with `UseWindowsLegacyProcessStrategy` enabled can trigger this deterministically (e.g., a PowerShell script using P/Invoke to call `FreeConsole` or `AllocConsole`, or simply exiting/detaching before the runner's cancellation/timeout logic invokes `Terminate()`).

The caller, `Terminate()`, only logs the error via `Warn` and falls back to `ForceKill()`; it never checks or restores the runner's console state: [3](#0-2) 

Nothing else in the codebase re-attaches the runner to a console after this point — the runner process instance remains without a console for its entire remaining lifetime.

### Impact Explanation
Once the runner process has no console, later `taskTerminate` calls for unrelated, subsequent jobs going through the `UseWindowsLegacyProcessStrategy` path will have their own `FreeConsole`/`AttachConsole`/`GenerateConsoleCtrlEvent` sequence behave unpredictably (e.g. `FreeConsole` at line 81 may itself fail since there is no console to free, or `GenerateConsoleCtrlEvent` may not reach the intended process because the runner isn't properly attached). This degrades graceful termination (`Ctrl-C`/`Ctrl-Break`) for future jobs on that runner process, forcing them onto the `ForceKill` (`taskkill /F /T`) path instead of a clean signal-based shutdown — a persistent, cross-job side effect caused by a single job's console manipulation. This matches the scoped impact: one job's process silently degrades termination behavior for later, unrelated jobs on the same runner process.

### Likelihood Explanation
This is reachable with unprivileged job-script content alone: it requires only (a) the admin-configured `UseWindowsLegacyProcessStrategy` option being enabled for the executor (a legitimate, documented runner config, not itself the vulnerability) and (b) a job script that exits before the timeout/cancel cycle calls `Terminate()`, or that calls `AllocConsole`/`FreeConsole` on itself — both trivially achievable from a normal CI job on Windows. It is deterministic given Windows' documented `AttachConsole` failure semantics for exited or console-detached target processes, and repeatable on every subsequent job run on that same runner process instance.

### Recommendation
Restructure `taskTerminate` so that the recovery/restoration calls (`GenerateConsoleCtrlEvent`, `FreeConsole`, `AttachConsole(math.MaxUint32)`, `SetConsoleCtrlHandler` restore) are executed unconditionally via `defer` (or an explicit `defer`-based cleanup function) immediately after the initial `FreeConsole` call succeeds, rather than being gated behind successful completion of `AttachConsole(pid)` and `SetConsoleCtrlHandler`. This guarantees the runner's own console/Ctrl-handler state is restored regardless of whether attaching to the target process's console succeeds.

### Proof of Concept
Go unit test outline (Windows-only, using the existing `killer_windows_test.go`/`killer_integration_test.go` scaffolding):
1. Start a dummy process, then kill/exit it (or have it call `FreeConsole` on itself) before invoking `taskTerminate(pid, true)`.
2. Assert `taskTerminate` returns an error (from failed `AttachConsole`).
3. After the call, use `GetConsoleWindow()`/`kernel32.GetConsoleCP` (or attempt `AllocConsole`, expecting `ERROR_ACCESS_DENIED` if a console is already attached, vs. success if none is attached) in the test process to verify whether the runner process still has a console attached and whether its `Ctrl-C` handler was restored to the pre-call baseline.
4. Run a second, independent `taskTerminate` call against a normal, live process and assert that `GenerateConsoleCtrlEvent` succeeds — expected to fail/misbehave after step 2, proving the cross-job regression.
