### Title
Unbounded per-account parsing cost in `getMultipleAccounts` with `encoding: jsonParsed` allows single-call CPU/memory amplification - ([File: rpc/src/rpc.rs])

### Summary
`JsonRpcRequestProcessor::get_multiple_accounts` only bounds the *number* of pubkeys (`max_multiple_accounts`, default 100) but not the cost of encoding each account's data, so an attacker who pre-populates up to `max_multiple_accounts` accounts with maximal data size (accounts can hold up to `MAX_PERMITTED_DATA_LENGTH`, 10MiB) owned by a parsable program (e.g. `address_lookup_table` or `bpf_loader_upgradeable`) can force `parse_account_data_v3` to do disproportionate work per call relative to the explicit count-based limit. This lets one bounded request (within all documented count/body-size limits) consume much more CPU/memory than a request with the same account count but small/unparsed accounts.

### Finding Description
`get_multiple_accounts` resolves a single bank and loops sequentially over each pubkey, awaiting `spawn_blocking(move || get_encoded_account(&bank, &pubkey, encoding, data_slice, None))` for every account [1](#0-0) . The only guard on cost is the count check `pubkey_strs.len() > max_multiple_accounts` in the `AccountsData::get_multiple_accounts` RPC handler [2](#0-1) ; there is no check on the size or complexity of the underlying account data before invoking the encoder.

`get_encoded_account` routes `UiAccountEncoding::JsonParsed` accounts (not SPL token) to `encode_account` → `encode_ui_account`, which for `JsonParsed` calls `parse_account_data_v3(pubkey, account.owner(), account.data(), additional_data)` [3](#0-2) [4](#0-3) . Unlike the `Binary`/`Base58` paths, which explicitly reject data larger than `MAX_BASE58_BYTES` (128 bytes) [5](#0-4) , `JsonParsed` has no size cap and processes the full account `data` regardless of size.

For accounts owned by `address_lookup_table::id()` or `bpf_loader_upgradeable::id()`, `parse_account_data_v3` dispatches to `parse_address_lookup_table` or `parse_bpf_upgradeable_loader` [6](#0-5) :
- `parse_address_lookup_table` deserializes the raw bytes into an `AddressLookupTable` and then converts every address entry into a `String` via `.to_string()` in `UiLookupTable::from`, an O(n) allocation-heavy operation over up to ~327k pubkeys for a 10MiB account [7](#0-6) .
- `parse_bpf_upgradeable_loader`'s `Buffer`/`ProgramData` variants base64-encode the entire remaining account data via `BASE64_STANDARD.encode(&data[offset..])` [8](#0-7) .

Since the loop in `get_multiple_accounts` processes pubkeys sequentially (awaiting each `spawn_blocking` before starting the next), an attacker with up to `max_multiple_accounts` (default 100, configurable via `--rpc-max-multiple-accounts`) accounts, each padded to the maximum permitted account size and owned by a parsable program, can force the validator to do up to ~100× the parsing/encoding/JSON-serialization work of a single large account within one `getMultipleAccounts` call — cost that scales with attacker-controlled data size, not with the explicit per-call limits (`max_multiple_accounts`, `max_request_body_size`).

### Impact Explanation
This is a single-call, unbounded-cost RPC resource-consumption issue: a legitimate, rate-compliant client (one call, well within `max_multiple_accounts`) can cause the RPC blocking thread pool to spend outsized CPU/memory on base64 encoding and pubkey-to-string conversions for attacker-authored account data, up to the on-chain maximum account size times the account count limit. This matches the "single RPC call causing unbounded cost disproportionate to explicit limits" bounty category (soft DoS / RPC resource exhaustion), not multi-call or multi-client DoS, and does not require privileged control of the validator.

### Likelihood Explanation
Feasible and repeatable with unprivileged access: an attacker only needs to fund and populate on-chain accounts (address-lookup-table entries or BPF-upgradeable buffer/programdata accounts) up to the maximum account size, then issue a single `getMultipleAccounts` call with `encoding: "jsonParsed"` naming those pubkeys (count ≤ `max_multiple_accounts`). No special privileges, leaked keys, or multiple calls are required; this can be repeated at the permitted single-call rate.

### Recommendation
Impose an explicit, size-aware bound before invoking `parse_account_data_v3` in the `JsonParsed` path (analogous to the `MAX_BASE58_BYTES` check for `Binary`/`Base58`), e.g. cap the account data length eligible for JSON parsing, or track/limit cumulative bytes-to-be-parsed across all pubkeys in a single `get_multiple_accounts`/`get_account_info` call, falling back to `Binary` encoding (as already done on parse failure) when the size threshold is exceeded.

    pub async fn get_multiple_accounts(
        &self,
        pubkeys: Vec<Pubkey>,
        config: Option<RpcAccountInfoConfig>,
    ) -> Result<RpcResponse<Vec<Option<UiAccount>>>> {
        let RpcAccountInfoConfig {
            encoding,
            data_slice,
            commitment,
            min_context_slot,
        } = config.unwrap_or_default();
        let bank = self.get_bank_with_config(RpcContextConfig {
            commitment,
            min_context_slot,
        })?;
        let encoding = encoding.unwrap_or(UiAccountEncoding::Base64);

        let mut accounts = Vec::with_capacity(pubkeys.len());
        for pubkey in pubkeys {
            let bank = Arc::clone(&bank);
            accounts.push(
                self.runtime
                    .spawn_blocking(move || {
                        get_encoded_account(&bank, &pubkey, encoding, data_slice, None)
                    })
                    .await
                    .expect("rpc: get_encoded_account panicked")?,
            );
        }
        Ok(new_response(&bank, accounts))
    }

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}

pub fn parse_account_data_v3(
    pubkey: &Pubkey,
    program_id: &Pubkey,
    data: &[u8],
    additional_data: Option<AccountAdditionalDataV3>,
) -> Result<ParsedAccount, ParseAccountError> {
    let program_name = PARSABLE_PROGRAM_IDS
        .get(program_id)
        .ok_or(ParseAccountError::ProgramNotParsable)?;
    let additional_data = additional_data.unwrap_or_default();
    let parsed_json = match program_name {
        ParsableAccount::AddressLookupTable => {
            serde_json::to_value(parse_address_lookup_table(data)?)?
        }
        ParsableAccount::BpfUpgradeableLoader => {
            serde_json::to_value(parse_bpf_upgradeable_loader(data)?)?
        }
        ParsableAccount::Config => serde_json::to_value(parse_config(data, pubkey)?)?,
        ParsableAccount::Nonce => serde_json::to_value(parse_nonce(data)?)?,
        ParsableAccount::SplToken | ParsableAccount::SplToken2022 => serde_json::to_value(
            parse_token_v3(data, additional_data.spl_token_additional_data.as_ref())?,
        )?,
        ParsableAccount::Stake => serde_json::to_value(parse_stake(data)?)?,
        ParsableAccount::Sysvar => serde_json::to_value(parse_sysvar(data, pubkey)?)?,
        ParsableAccount::Vote => serde_json::to_value(parse_vote(data, pubkey)?)?,
    };
