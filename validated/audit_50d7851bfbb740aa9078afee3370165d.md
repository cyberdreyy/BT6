### Title
Lockup address is derived solely from `owner_account_id` with no caller authorization, allowing pre-emptive squatting of any victim's lockup with attacker-chosen `LockupArgs` - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the lockup contract's account id as a pure function of the caller-supplied `owner_account_id` (`sha256(owner_account_id)[..20]` + master account), with no check that the caller is the owner, the foundation, or otherwise authorized. Any unprivileged account can call `create(owner_account_id=<victim>, lockup_duration=<attacker-chosen>, vesting_schedule=<attacker-chosen>, ...)` and occupy that deterministic address first, funding it with their own NEAR under terms the rightful creator never chose.

### Finding Description
The broken binding: `deployed_LockupArgs(lockup_account_id) == intended_LockupArgs_of_rightful_creator(owner_account_id)`.

`create()` computes the target account deterministically: [1](#0-0) 

and then unconditionally creates/deploys/funds/initializes it with whatever `LockupArgs` the *caller* passed in: [2](#0-1) 

There is no `assert_owner`, `assert_called_by_foundation`, or any check that `env::predecessor_account_id()` matches `owner_account_id`, the foundation, or any pre-registered relationship. The only guard is `MIN_ATTACHED_BALANCE`, which any attacker can pay from their own funds: [3](#0-2) 

Exploit flow: attacker computes `hex::encode(sha256(b"victim.testnet")[..20])` off-chain (same formula used in tests), then calls `create(owner_account_id="victim.testnet", lockup_duration=<attacker value>, vesting_schedule=<attacker value>, ...)` attaching `MIN_ATTACHED_BALANCE` from their own account, before the employer/foundation ever calls `create()` for that owner. Since NEAR account names are globally unique, this occupies `<hash>.lockup.near` first. When the legitimate employer later calls `create()` for the same `owner_account_id`, the `Promise::new(lockup_account_id).create_account()` fails because the account already exists, `is_promise_success()` returns `false` in `on_lockup_create`, and the employer's deposit is simply refunded: [4](#0-3) 

The employer's legitimate lockup for that owner can never be created at the canonical address again — the address is permanently occupied by a lockup contract whose `LockupArgs` (duration, vesting schedule, release schedule, whitelist, foundation account) were chosen by the attacker, not the rightful creator. `LockupContract::new` performs only basic format validation (`is_valid_account_id`), not authorization of who is allowed to set these parameters for a given owner: [5](#0-4) 

None of the existing guards (`assert_self`, `is_promise_success`, `MIN_ATTACHED_BALANCE` check) address this, since they only check promise success/self-call, not authorization of `owner_account_id` binding to caller.

### Impact Explanation
This directly matches the listed Critical impact category "a lockup deployed with parameters its rightful creator never chose." Any known future employee/investor account name can be pre-emptively squatted with attacker-chosen `lockup_duration`, `vesting_schedule`, `release_duration`, and `staking_pool_whitelist_account_id`, permanently preventing the legitimate employer/foundation from ever deploying the canonical lockup contract for that owner at that address (the address space is a pure function of `owner_account_id`, so no alternate address exists via `create()`). This is repeatable for every known future grant recipient's account name and does not require any privilege — only the ability to submit a transaction with `MIN_ATTACHED_BALANCE` (3.5 NEAR).

### Likelihood Explanation
Low cost, fully feasible: computing the target address only requires `sha256` of a known/guessable/leaked future employee or investor account name, and any attacker can front-run the employer by simply submitting `create()` first with `MIN_ATTACHED_BALANCE` of their own NEAR. No special timing, keys, or privileges are needed — only knowledge (or a guess) of the intended owner account id, which is often predictable (e.g., `alice.near`, `bob.near`) or discoverable ahead of the actual grant.

### Recommendation
Restrict who may call `create()` for a given `owner_account_id` — e.g., require `env::predecessor_account_id() == owner_account_id.as_ref()` or restrict `create()` to be callable only by the foundation/master account, and/or incorporate the predecessor account id or an authorization token into the lockup account id derivation so it cannot be pre-computed and squatted by an unrelated party.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
