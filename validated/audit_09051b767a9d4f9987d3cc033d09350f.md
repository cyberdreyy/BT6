### Title
Stale per-epoch instant-withdraw basis is double-counted into default recovery, diluting `defaultRecoveryPrice` and permanently stranding recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays out a user's aggregated instant receipt (`instantWithdrawsRequests[_user]`) but never clears the per-epoch accounting `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. If a default is later finalized while `pendingInstantWithdraws != 0`, `defaultPendingClaimBasis()` re-reads `instantWithdrawClaimsByEpoch[epochNumber]`, which still contains basis for receipts that were already funded and paid out. The stale basis inflates `totalBasis` in `finalizeDefaultRecovery`, lowers `defaultRecoveryPrice` for every legitimate claimant, and the corresponding share of `defaultRecoveryReserve` can never be claimed — it is permanently locked in the strategy.

### Finding Description
- `requestInstantWithdraw` records both the aggregate receipt and per-epoch basis (`instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]`).
- `claimInstantWithdrawRequest` only zeroes the aggregate `instantWithdrawsRequests[_user]`; the per-epoch entries persist after a successful claim.
- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` (the current epoch's entire recorded basis, including already-claimed receipts) whenever `pendingInstantWithdraws != 0`.
- `finalizeDefaultRecovery` divides the real reserve (`_recoveredAmount + prefunded + defaultRecoveryReserve`) by this inflated `totalBasis`, computing a recovery price lower than warranted.
- When the already-paid user later calls `claimInstantWithdrawRequest` via the CDO, `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = X` (stale) and then executes `instantWithdrawsRequests[_user] -= claimBasis`, which underflows because the aggregate is already 0 — the call reverts, so the stale basis is never actually paid. The leftover `X * defaultRecoveryPrice` of reserve has no claimant and is stranded forever (the reserve is only decremented in `_transferDefaultRecovery`).

Concretely: user A requests and successfully claims an instant withdrawal during epoch N (leaving `instantWithdrawClaimsByEpoch[N] = X`). User B has an instant request in the same epoch that stays unfunded (`pendingInstantWithdraws = Y > 0`). The borrower defaults; manager finalizes recovery. The basis becomes `pendingWithdraws + X + Y` instead of `pendingWithdraws + Y`.

### Impact Explanation
Every legitimate defaulted-epoch claimant (normal and instant) receives `claimBasis * defaultRecoveryPrice / 1e18` with a strictly smaller `defaultRecoveryPrice`, so they recover less than entitled. The difference is not redistributed to anyone — it remains in `defaultRecoveryReserve` as unclaimable dust, i.e., permanent freezing of recovery funds. Quantified loss: fraction `X / (activeBasis + pendingBasis + X)` of the whole recovery reserve is stranded, and real claimants lose `X / (totalBasis)` proportionally on every claim.

### Likelihood Explanation
Requires only ordinary user actions: an instant withdraw requested and claimed within the same `epochNumber` window that later defaults with another unfunded instant request pending (`pendingInstantWithdraws != 0` is exactly the condition that includes the instant basis). No privileged role is needed to plant the stale entries; the epoch and instant-withdraw machinery is a normal operating mode. The stale state persists indefinitely until a default, so the bug is latent rather than timing-dependent.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch records alongside the aggregate, e.g. delete `instantWithdrawsRequestsByEpoch[_user]` entries for all epochs in which the user has receipts and decrement `instantWithdrawClaimsByEpoch` accordingly — or track the epoch of open instant requests and clear `instantWithdrawsRequestsByEpoch[_user][reqEpoch]` and `instantWithdrawClaimsByEpoch[reqEpoch]` on claim. Alternatively, in `_claimDefaultedInstantWithdrawRequest`/`defaultPendingClaimBasis`, only count basis for users whose aggregate `instantWithdrawsRequests` is still non-zero.
