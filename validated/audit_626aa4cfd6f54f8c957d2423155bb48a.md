### Title
`ProgrammableBorrower.onStartEpoch` force-deposits all idle underlying into the ERC4626 vault without a failure path, permanently bricking `startEpoch` if the vault stops accepting deposits - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` parks idle capital in an external ERC4626 `vault`. At every epoch start, `onStartEpoch` calls `_depositToVault(underlyingToken.balanceOf(address(this)), 0)`, which unconditionally calls `vault.deposit` on the entire on-hand balance with no `try/catch`, no skip flag, and no minimum-amount guard. If the vault's deposits are disabled (paused, deposit cap reached, deprecated/removed pool), `vault.deposit` reverts, `onStartEpoch` reverts, and therefore `IdleCDOEpochVariant.startEpoch` reverts. An unprivileged attacker can guarantee the vulnerable path is reached by directly transferring 1 wei of underlying to `ProgrammableBorrower` during the buffer period, since donations to the borrower contract are never skimmed (the donation-isolation `_skimDonatedAssets` only covers the IdleCDO's own token balance, `contracts/IdleCDOEpochVariant.sol:242`).

The design already acknowledges that ERC4626 vault operations can fail transiently: `onStopEpoch` wraps `vault.withdraw` in `try/catch` and reverts with a retryable `StopEpochVaultLiquidityUnavailable` (lines 246-253). No equivalent protection exists for the deposit direction at epoch start. There is also no way to tell the contract "keep excess funds as cash instead of depositing to the vault" — the exact recommendation in the external report.

Cash accumulates on `ProgrammableBorrower` during the buffer period through legitimate flows: `_repay` only redeploys repaid funds into the vault when `epochAccountingActive` (lines 524-532), so any borrower repayment of settled debt or interest during the buffer leaves the tokens as raw on-hand balance. Additionally, any EOA can `transfer` underlying directly to the contract — there is no donation defense at this layer.

Attack/failure sequence:

1. Epoch N ends; the pool is in the buffer period. The vault's governance pauses deposits, a deposit cap is hit, or the pool is deprecated (the EigenLayer strategy-removal analog).
2. Borrower repays during the buffer (funds stay as cash, `epochAccountingActive == false`), or any unprivileged sender transfers 1 wei of underlying to `ProgrammableBorrower`.
3. Manager calls `IdleCDOEpochVariant.startEpoch()` → `_startEpochProgrammableBorrower` → `ProgrammableBorrower.onStartEpoch` → `_depositToVault(balance)` → `vault.deposit` reverts.
4. `startEpoch` can never succeed while the vault rejects deposits: `emergencyExitVault` only redeems shares (not the cash re-deposit path), `setVault` requires `vault.balanceOf == 0` **and** would still leave the same forced-deposit behavior on the new vault, and `rescueTokens` is the only escape — an owner-only emergency action that requires pulling lender funds out of the accounting system.

### Impact Explanation
Permanent freezing of all pool funds with direct fund impact, not a gas/DoS-only issue. While `startEpoch` is bricked, the pool stays in a stopped-but-not-running state: tranche holders cannot withdraw (`requestWithdraw`/`claim*` are gated on epoch transitions), queued deposits in `IdleCDOEpochQueue` cannot be processed, and pending withdrawal funds already sent to `IdleCreditVault` remain locked against the next epoch. Recovery requires the owner to invoke `rescueTokens` to strip the on-hand balance (donated dust plus any buffer-period borrower repayments) out of `ProgrammableBorrower`, which writes those funds out of pool accounting entirely — a quantified loss equal to the rescued amount, plus the vault sleeve is at risk of being orphaned because `setVault` refuses to run while shares remain (line 165). Broken invariant: the epoch state machine must always be able to transition from buffer back to running regardless of the external vault's deposit policy.

### Likelihood Explanation
Medium. The trigger requires the integrated ERC4626 vault to disable deposits, which is a third-party administrative event — exactly the same class of dependency as the EigenLayer `StrategyManager` whitelist removal in the source report, and the codebase itself treats external-vault stress as a real scenario (try/catch around `vault.withdraw`, `onDefault` deliberately avoiding `convertToAssets` "even if the external vault's valuation view is unavailable during stress", lines 295-297). The attacker requirement is minimal: a direct token transfer to `ProgrammableBorrower` or an honest buffer-period repayment is enough to put a nonzero cash balance on the contract, and both are unprivileged actions. The only reason this is not a unilateral attacker exploit is that the vault deposit failure itself is environmental, matching the source report's medium severity.

### Recommendation
Apply the source report's recommendation to the vault sleeve: introduce a flag (e.g. `skipVaultDeposit` / `depositsToVaultEnabled`) so `onStartEpoch` and `_repay` can leave excess underlying as on-hand cash instead of forcing `vault.deposit`, and/or wrap the `vault.deposit` call in `try/catch` in `_depositToVault` so a rejecting vault cannot block the epoch transition. A failed-deposit event should be emitted so operators can react. Note that `epochStartVaultAssets` must still be computed from the pre-deposit balance (as it already is at line 214) so undeposited cash is not miscounted as vault profit.
