### Title
Claiming an APR0 withdraw receipt in a closed pool deletes the user's `apr0Users` entry but never decrements `apr0TotalPrincipal`, leaving a ghost principal bucket that permanently diverts APR0 interest to unclaimable `pendingWithdraws` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

CVE-2024-5845 is a use-after-free: a freed object is later consumed by logic that still trusts it. The credit-vault analog is `IdleCreditVault._claimFundedWithdrawRequest`: it pays out a user's still-open APR0 principal and then `delete apr0Users[_user]` frees the per-user struct, but the global `apr0TotalPrincipal` — the accounting object that `prepareStopEpochWithApr0` later "uses" to allocate pro-rata APR0 interest — is never decremented for that freed principal. The stale bucket survives the free, is consumed again by the next `stopEpoch`, and causes interest to be booked into `pendingWithdraws` for receipt holders who no longer exist.

### Finding Description

`requestWithdraw` on an APR=0 pool records per-user state via `_requestWithdrawApr0`, which increments both `apr0Users[_user].principal` and the global `apr0TotalPrincipal` (`IdleCreditVault.sol:567-577`).

In `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:319-350`):

```solidity
uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
...
_burn(_user, normalAmount + apr0PrincipalAmount);
withdrawsRequests[_user] = 0;
lastWithdrawRequest[_user] = 0;
if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
    delete apr0Users[_user];
}
```

Two observations:

1. The claim includes `_apr0User.principal` — the *still-open* APR0 bucket — not just `settledPrincipal`. The code comments explicitly acknowledge this is reachable: "still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement for the current request epoch (reqEpoch >= epochNumber)" (lines 333-336). `_settleApr0` returns early when `_reqEpoch >= epochNumber` (lines 552-555), and the claim gate `epochNumber <= lastWithdrawRequest[_user]` is skipped entirely when `epochEndDate() == 0` (line 326). So in the closed-pool path a user can claim an *unsettled* APR0 request.

2. When that happens, `delete apr0Users[_user]` frees the per-user struct, but `apr0TotalPrincipal` is never reduced by the claimed `principal`. The only places `apr0TotalPrincipal` is written are `+=` in `_requestWithdrawApr0` (line 576), `= 0` at the end of `prepareStopEpochWithApr0` (line 540), the partial decrement in `_clearWithdrawClaimForEpoch` (line 827, used only on the default path), and `= 0` in `_ensureDefaultRecoveryInitialized` (line 931, only when `pendingWithdraws != 0`). None of these run on the closed-pool claim path — the pool never reaches another `stopEpoch`, so `prepareStopEpochWithApr0` never closes the bucket.

This is the UAF shape: per-user memory is freed (struct deleted, receipt tokens burned, funds paid), yet the aggregate object retains a reference to the freed principal and is consumed later.

The stale bucket is exploited mechanically. If the vault is reopened (a new epoch with APR = 0 after `restoreOperations`/re-lending), the next `prepareStopEpochWithApr0` sees `apr0TotalPrincipal = ghost + honest` and computes `apr0RateByEpoch[epochNumber] = _apr0NetInterest * 1e18 / _principal` over the inflated denominator, while booking the full `_apr0NetInterest` into `pendingWithdraws` (lines 521-537). The ghost share of that interest is owed to deleted accounts that can never claim it, and honest APR0 users' per-epoch rate is diluted by `ghost/(ghost+honest)`.

### Impact Explanation

- Permanent freezing of funds: the ghost-principal share of `_apr0NetInterest` is added to `pendingWithdraws`, obligating the borrower/CDO to fund it via `collectWithdrawFunds`, yet no `withdrawsRequestsByEpoch`/`apr0Users` entry exists to claim it. The funded underlying sits in the strategy forever (it cannot even be spent by funded claims — `_transferFundedClaim` only guards `defaultRecoveryReserve`, but there is no path that releases orphan `pendingWithdraws` backing).
- Theft/dilution of unclaimed yield: honest APR0 claimants' `settledInterest` is reduced pro-rata by the ghost weight.

Quantified: for ghost principal `G` and honest principal `H`, the frozen/lost yield is `_apr0NetInterest * G / (G + H)` per affected epoch. An attacker can maximize `G` cheaply: request a large APR0 withdraw during a buffer period, wait for pool close (`epochEndDate == 0`), claim at immediate par (principal returned, struct deleted, bucket retained), repeat across successive request epochs if the pool reopens, compounding the ghost weight.

### Likelihood Explanation

- Attacker is unprivileged (any KYC-passing lender); the honest-side actions required (pool close via the `_interest == 1` sentinel in `stopEpoch`, later reopening with APR = 0) are normal operator flows, not adversarial.
- All existing guards miss it: the claim gate is bypassed by `epochEndDate == 0`; the loss-epoch guard in `requestWithdraw` (lines 261-270) only checks `lossRecoveryPriceByEpoch`; `_clearWithdrawClaimForEpoch` correctly decrements `apr0TotalPrincipal` but is only invoked on default/loss-adjusted paths, never on the funded path that performs the `delete`.
- One uncertainty I could not fully verify within this pass: the exact `IdleCDOEpochVariant` close-and-reopen sequence (whether `epochEndDate` returns to non-zero and APR0 epochs can resume on the same strategy). If closed pools are permanently terminal, the stale bucket is unreachable and the severity collapses — this precondition should be confirmed in the PoC.

### Recommendation

In `_claimFundedWithdrawRequest`, before `delete apr0Users[_user]`, decrement the open bucket for any still-unsettled principal:

```solidity
uint256 openPrincipal = _apr0User.principal; // captured before _settleApr0/delete
if (openPrincipal != 0) {
    apr0TotalPrincipal = openPrincipal >= apr0TotalPrincipal ? 0 : apr0TotalPrincipal - openPrincipal;
}
```

Alternatively, forbid claiming while `apr0Users[_user].principal != 0 && principalEpoch >= epochNumber` (mirroring `_settleApr0`'s rule), or clear `apr0TotalPrincipal` as part of the pool-close flow since no further accrual is possible.
