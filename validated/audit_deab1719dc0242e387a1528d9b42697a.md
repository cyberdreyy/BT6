### Title
External-Initiator credentials can trigger arbitrary jobs by integer ID via `POST /v2/jobs/:ID/runs`, bypassing the "EIs not allowed" restriction - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` unconditionally sets `SessionUserKey` to a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` on successful EI credential verification. `PipelineRunsController.Create` gates the integer-job-ID run path solely on `auth.GetAuthenticatedUser(c)` returning `ok`, which does not distinguish a real user session/token from a synthetic EI-derived user, contradicting its own comment that "only users are allowed to run jobs using int IDs - EIs not allowed".

### Finding Description
The route is registered in `core/web/router.go`: [1](#0-0) 
This chains `auth.AuthenticateExternalInitiator` before `auth.AuthenticateByToken`/`auth.AuthenticateBySession`, and wraps `prc.Create` only with `auth.RequiresRunRole`.

In `core/web/auth/auth.go`, when EI credentials (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret`) validate: [2](#0-1) 
it sets `SessionUserKey` to a fabricated `User{Role: UserRoleRun}` — with no `Email`/`ID` tying it to any real user, and no restriction to the specific EI or its owned jobs.

`RequiresRunRole` only checks that `GetAuthenticatedUser` returns `ok=true` and role != view: [3](#0-2) 
Since the EI-derived user has `Role: UserRoleRun` (not `View`), this check passes.

Inside `PipelineRunsController.Create`, the int-ID job-run path is gated only on `isUser` from `GetAuthenticatedUser`: [4](#0-3) 
Because `AuthenticateExternalInitiator` also populates `SessionUserKey`, `isUser` is `true` for EI-authenticated requests too, so the comment's intended restriction ("EIs not allowed") is not actually enforced by the code — any successfully-authenticated EI credential can call `prc.App.RunJobV2(ctx, jobID, nil)` for **any** integer job ID, not just jobs associated with that specific external initiator.

### Impact Explanation
This is an authorization/request-binding bypass: a holder of any valid EI AccessKey/Secret pair (a low-privilege credential intended only to trigger its own webhook-linked job via a UUID) can invoke `RunJobV2` against arbitrary numeric job IDs belonging to any job on the node, not just their own. This constitutes an unauthorized-job-run vulnerability — potentially triggering DON/OCR jobs, transaction-sending jobs, or other pipeline jobs outside the EI's intended authorization scope, which matches Chainlink's bounty class of "unauthorized job run" / role-authorization bypass.

### Likelihood Explanation
Preconditions: attacker only needs any valid EI AccessKey/Secret credential (these are commonly distributed to lower-trust integrators/external initiators, not full node users). No user session, API token, or elevated role is required. The request is a straightforward, repeatable HTTP POST to `/v2/jobs/{intJobID}/runs` with EI headers set — no timing or race conditions needed. This is fully feasible and repeatable for anyone who has EI credentials.

### Recommendation
In `PipelineRunsController.Create`, do not rely solely on `GetAuthenticatedUser` returning `ok`. Distinguish real user sessions/tokens from EI-derived pseudo-users — e.g., check that `GetAuthenticatedExternalInitiator(c)` is NOT set (or explicitly reject if it is) before permitting the integer-job-ID run path, restoring the comment's stated intent that EIs cannot run jobs via `/jobs/:ID/runs` with int IDs. Alternatively, give the synthetic EI user a distinct marker/role (not indistinguishable from a real run-role user) that `Create` explicitly excludes.

### Proof of Concept
Handler-level integration test plan (Go, using `httptest` + gin router as built by `web.NewRouter`):
1. Seed a node DB fixture with: (a) one `ExternalInitiator` with known `AccessKey`/`Secret`, and (b) an unrelated job `job.Job` (e.g., a Cron or DirectRequest job) with a known int32 ID, not associated with the EI created above.
2. Send `POST /v2/jobs/{jobID}/runs` setting only headers `X-Chainlink-EA-AccessKey` and `X-Chainlink-EA-Secret` to the EI's credentials (no session cookie, no `X-API-KEY`/`X-API-SECRET`).
3. Assert the response is `200 OK` with a `pipelineRun` resource (i.e., `RunJobV2` executed), NOT a `422 Unprocessable Entity` "bad job ID" (which would be expected if EI truly could not use int IDs per the code comment).
4. Unit-level assertion: call `auth.AuthenticateExternalInitiator(c, mockStore)` directly, then `auth.GetAuthenticatedUser(c)`, and assert `ok == true` and `user.Role == clsessions.UserRoleRun`, demonstrating the same code path `PipelineRunsController.Create` relies on to gate int-ID execution is satisfied by EI-only credentials.

```go
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
