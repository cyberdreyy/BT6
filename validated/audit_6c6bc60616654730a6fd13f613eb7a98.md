### Title
Permissionless SPL-token burn of a Staked-Collateral bank's LST mint can inflate the `StakedWithPythPush` oracle price and enable over-borrowing - (File: `programs/marginfi/src/state/price.rs`)

### Summary
The SKALE report (M-07) describes a bug class where an unprivileged actor can manipulate a supply/mint-accounting value that a protocol trusts as ground truth, causing a value mismatch between two sides of the system (mainnet lock vs. Schain mint) that lets the attacker drain real value. In marginfi's `OracleSetup::StakedWithPythPush` path, the price of a staked-collateral LST is derived as `pool_nav / lst_mint.supply`, and `lst_mint.supply` is read live and unauthenticated from the SPL Token mint account [1](#0-0) . Because burning SPL tokens requires only the token-account owner's signature (no `MINTER_ROLE`/mint-authority check, analogous to how `ERC20OnChain.mint` in the report is unprivileged), anyone holding LST tokens for a given `spl-single-pool` can shrink `lst_mint.supply` independently of the actual staked SOL backing it.

### Finding Description
The staked-collateral price feed computes:
```
multiplier = sol_pool_adjusted_balance / lst_supply
adjusted_price = feed.price.price * sol_pool_adjusted_balance / lst_supply
``` [2](#0-1) 

`lst_supply` is taken directly from `Account::<Mint>::try_from(&ais[1]).supply` with only a zero-check (`ZeroSupplyInStakePool`) [1](#0-0) . `sol_pool_adjusted_balance` (the numerator, i.e., actual lamports staked/on-ramped) is validated against the native stake program and on-ramp PDA [3](#0-2) , but the *denominator* — total LST supply — has no such coupling check. `spl-single-pool` LST mints are ordinary SPL Token mints; `burn` only requires the token-account owner to sign, not the mint authority (which, in `spl-single-pool`, belongs to a pool PDA, not a general "unprivileged" role, but the *burn* permission itself is decoupled from that mint authority entirely and is available to any token holder). Burning LST outside of the pool's own withdraw-and-burn instruction reduces `lst_supply` without reducing `sol_pool_adjusted_balance`, inflating the computed exchange rate for every unburned LST token still in circulation — including tokens already deposited as collateral in a marginfi staked bank.

This mirrors the SKALE bug class precisely: an unprivileged/permissionless supply-changing action (mint on Schain / burn on marginfi's LST) that the protocol implicitly trusts to reflect real backing, causing a valuation mismatch that can be exploited for value extraction.

### Impact Explanation
If an attacker can atomically (or near-atomically) reduce `lst_supply` for a staked bank's LST mint after having deposited a large LST position as collateral, the derived price used in `lending_account_borrow`/`lending_account_withdraw` (and liquidation) health checks would be inflated, allowing the attacker to borrow more than the true backing justifies. Because `StakedWithPythPush` pricing is recomputed live from `ais[1]` (the mint) on every risk-check call rather than from a time-weighted or checkpointed value, a single-transaction manipulation is possible in principle. `total_asset_value_init_limit` and `oracle_max_confidence` exist as generic per-bank caps, but they cap the *counted USD value at bank-add time*, not the exchange-rate manipulation itself, and staked banks created permissionlessly via `lending_pool_add_bank_permissionless` set `borrow_limit: 0` (staked collateral cannot itself be borrowed against directly as a liability) but is still usable as *collateral* for borrowing other assets (e.g., regular SOL), so inflated pricing directly increases borrowing power against other banks.

### Likelihood Explanation
Exploitability is constrained economically: burning B tokens destroys their full value to gain only a fractional price increase on the remaining deposited D tokens (`gain ≈ D·NAV·B/S² < loss = B·NAV/S` for `D < S`), so a naive single-actor attack is a net loss unless `D` approaches the full circulating supply of that specific validator's single-pool LST — realistic for low-liquidity or newly-listed validator stake pools, which is exactly the permissionless-bank scenario this feature targets (`lending_pool_add_bank_permissionless` lets any validator's stake pool become a marginfi bank with no admin gate [4](#0-3) ). This raises likelihood specifically for thinly-held validator LSTs shortly after bank creation, but is not a trivially profitable, capital-free attack in the general case, and I could not verify from the indexed code whether any TWAP/anti-manipulation safeguard exists beyond the confidence/init-limit checks already reviewed. This is a credible but not conclusively proven exploitable path from static review alone; on-chain testing (e.g., in the `s0x_*` staked test suite) would be needed to confirm whether a same-slot deposit+borrow+burn sequence bypasses existing caps.

### Recommendation
- Do not treat `spl-single-pool` LST `mint.supply` as fully trusted for pricing; either derive the exchange rate exclusively through the single-pool program's own state/CPI (which keeps burn and stake-withdrawal atomic) or add a floor/ceiling sanity check comparing the newly observed exchange rate against a recent checkpoint (e.g., reject price moves beyond X% per slot for staked banks).
- Consider tightening `total_asset_value_init_limit`/`oracle_max_confidence` defaults specifically for permissionlessly-added staked banks, and/or require a minimum bank "seasoning" period or minimum LST supply before permitting full borrowing power against it.
- Add an explicit invariant test exercising "external burn of LST supply between deposit and borrow" analogous to the existing `s05_solAppreciates.spec.ts` appreciation tests, to confirm actual protocol behavior under this scenario.

### Proof of Concept
1. Attacker acquires (via staking or purchase) a large fraction of a specific validator's single-pool LST supply `S`, where the pool is a marginfi staked-collateral bank added via `lending_pool_add_bank_permissionless`.
2. Attacker deposits `D` LST as collateral into their marginfi account via `lending_account_deposit` against that bank.
3. In the same or a follow-up transaction (before other market participants react), attacker calls the SPL Token `burn` instruction directly on a separate holding of `B` LST tokens they still control (not going through the single-pool program's atomic burn+withdraw), reducing `lst_mint.supply` without reducing the underlying staked SOL (`sol_pool_adjusted_balance`).
4. Attacker calls `lending_account_borrow` (or increases withdrawal against another bank) packing the manipulated `[bank, pyth_push_oracle, lst_mint, sol_pool, pool_onramp]` remaining accounts per `programs/marginfi/src/state/price.rs`; the risk engine recomputes `multiplier = sol_pool_adjusted_balance / lst_supply` with the now-smaller `lst_supply`, inflating the USD value of the attacker's deposited `D` LST and permitting a larger borrow than the true backing supports.
5. Whether step 4 nets a genuine profit depends on the ratio `D/S` and the specific caps (`total_asset_value_init_limit`, health-check tolerances) in force for that bank — this was not verified end-to-end against a running test environment and would need confirmation via the existing bankrun test harness (`tests/specs/staked/*`).
