### Title
Normal instant-withdraw claims never decrement `instantWithdrawClaimsByEpoch`, inflating default-recovery basis and reserve and permanently freezing unclaimed yield - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external Bribe bug is a missing aggregate decrement: `deposit()` increases `totalVoting` but `withdraw()` never decreases it, so the stale aggregate distorts pro-rata distribution and a portion of rewards becomes permanently stuck. The direct analog in `IdleCreditVault.sol` is the instant-withdraw aggregate `instantWithdrawClaimsByEpoch[epoch]`: it is incremented in `requestInstantWithdraw` and decremented in `_claimDefaultedInstantWithdrawRequest`, but the normal funded claim path `claimInstantWithdrawRequest` only clears `instantWithdrawsRequests[_user]` and burns the receipt — it never removes the user's basis from `instantWithdrawClaimsByEpoch` (nor from `instantWithdrawsRequestsByEpoch`). If the borrower later defaults in that same epoch, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` count already-paid-out claims as both outstanding basis and phantom prefunded reserve, corrupting `defaultRecoveryPrice` in `finalizeDefaultRecovery`.

### Finding Description
`requestInstantWithdraw` tracks two aggregates per epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]`, plus the global `pendingInstantWithdraws` [1](#0-0) . On a normal (funded) claim, `claimInstantWithdrawRequest` burns the user's receipt and pays out, but the visible code only reads `instantWithdrawsRequests[_user]` and burns it — there is no decrement of `instantWithdrawClaimsByEpoch` or `instantWithdrawsRequestsByEpoch` [2](#0-1) . By contrast, the defaulted-claim path does clean up all three aggregates: `instantWithdrawsRequestsByEpoch`, `instantWithdrawsRequests`, `pendingInstantWithdraws`, and `instantWithdrawClaimsByEpoch` [3](#0-2) . This is the same asymmetry as Bribe's `deposit()`/`withdraw()` pair: one aggregate lifetime is tracked on entry but not on the normal exit.

The stale aggregate feeds directly into default accounting. `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` [4](#0-3) , and `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstant` as "already-held underlying reserved for those claims" [5](#0-4) . An already-claimed instant withdrawal leaves `instantBasis` inflated, so the computed `prefundedReserve` counts tokens that were already transferred out of the strategy.

In `finalizeDefaultRecovery`, `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` [6](#0-5) . The phantom reserve inflates both numerator (reserve that does not exist) and denominator (claim basis for receipts already paid). The stored `defaultRecoveryReserve` then exceeds the real balance, and `_transferDefaultRecovery` / `_transferFundedClaim` will fail or drain real funds for earlier claimants, leaving the tail of legitimate defaulted-epoch receipts permanently unclaimable — the same "remaining share stuck in the pool forever" outcome as the Bribe report.

### Impact Explanation
Permanent freezing of unclaimed yield. After a same-epoch default, `defaultRecoveryReserve` is overstated by the already-claimed instant amount `X`, while `totalBasis` is also overstated by `X`. Real underlying is short by `X`; the last claimant(s) of defaulted normal/APR0/instant receipts cannot be paid (`safeTransfer` reverts or the reserve accounting silently strands the difference), and there is no recovery mode to sweep or correct the overcounted basis. Loss magnitude equals the total instant-withdraw amount claimed normally between the epoch's funding and the default finalization.

### Likelihood Explanation
Requires a specific sequence within one epoch: (a) an instant-withdraw request is funded and claimed, (b) another instant request (or the same funded bucket) leaves `pendingInstantWithdraws != 0` at default, and (c) the borrower defaults and the CDO calls `finalizeDefaultRecovery` in the same `epochNumber`. Attacker-facing preconditions are modest — any KYC-passed lender can request and claim an instant withdrawal — but the loss crystallization depends on an honest borrower default and timely finalization, which are environmental, not attacker-controlled. No existing guard prevents it: `defaultInstantWithdrawsFinalized` only gates the defaulted-claim path, and nothing reconciles `instantWithdrawClaimsByEpoch` against actual claims before `finalizeDefaultRecovery`.

Caveat: I could not view the tail of `claimInstantWithdrawRequest` (approximately lines 390–400) in this pass, so there is residual uncertainty whether `instantWithdrawClaimsByEpoch[currentEpoch]` or `instantWithdrawsRequestsByEpoch` are cleared further down in that function or in a helper. If they are cleared there, this finding collapses and the analog does not hold.

### Recommendation
In `claimInstantWithdrawRequest`, mirror the cleanup done in `_claimDefaultedInstantWithdrawRequest`: when a funded instant receipt is claimed, decrement `instantWithdrawsRequestsByEpoch[_user][requestEpoch]` and `instantWithdrawClaimsByEpoch[requestEpoch]` by the claimed basis, so the epoch aggregates only ever reflect live, unclaimed receipts. Alternatively, have `_defaultPrefundedInstantReserve()` and `defaultPendingClaimBasis()` derive the live instant basis from `instantWithdrawsRequests` sums rather than a never-decremented epoch counter. Also add an invariant test: `sum(instantWithdrawsRequests) == sum over epochs of instantWithdrawClaimsByEpoch` for the current epoch.

### Proof of Concept
Foundry-style PoC sketch (against `IdleCreditVault` + a mock CDO/borrower as in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleInstantBasisInflatesRecovery() public {
    // Epoch N running; Alice (lender) deposits via CDO.
    _depositAsAlice(100e18);

    // Alice requests an instant withdraw of 40e18.
    _requestInstantWithdraw(alice, 40e18);
    assertEq(vault.instantWithdrawClaimsByEpoch(vault.epochNumber()), 40e18);

    // CDO funds the instant queue (getInstantWithdrawFunds path) and Alice claims.
    _fundInstantWithdraws(40e18);
    _claimInstantWithdraw(alice);

    // BUG: per-epoch aggregate still counts the paid claim.
    assertEq(vault.instantWithdrawsRequests(alice), 0);
    assertEq(vault.instantWithdrawClaimsByEpoch(vault.epochNumber()), 40e18); // stale

    // Bob requests a new instant withdraw in the SAME epoch (unfunded part).
    _depositAsBob(50e18);
    _requestInstantWithdraw(bob, 10e18);
    // pendingInstantWithdraws = 10e18, instantBasis = 50e18 (40 stale + 10 real)

    // Borrower defaults; CDO finalizes recovery in same epoch.
    _borrowerDefault();
    vault.finalizeDefaultRecovery(recovered, recoverySource);

    // prefundedReserve counted = 50e18 - 10e18 = 40e18 of nonexistent funds,
    // so defaultRecoveryReserve and totalBasis are each inflated by 40e18.
    // Contract balance is short by exactly 40e18: the last defaulted receipt
    // claim (e.g., Bob's) reverts on safeTransfer / is stranded forever.
    vm.expectRevert();
    _claimDefaultedInstantWithdraw(bob);
}
```

The assertion `instantWithdrawClaimsByEpoch(epoch) == 40e18` immediately after Alice's successful claim is the core check — it should be `0` if the aggregate tracked only live receipts.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
