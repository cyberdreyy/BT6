### Title
Shared global/per-node relay rate limiters silently drop node responses with no per-caller isolation, letting an unprivileged flooder degrade quorum for other users' requests on the same DON - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`handler.HandleNodeMessage` gates every incoming node response through a single DON-wide `globalNodeRateLimiter` and per-node `perNodeRateLimiters`, and on throttling it silently returns `nil` instead of an error. Because these buckets are shared across all requests to the DON with no accounting for which caller's traffic consumed them, an unprivileged user who repeatedly calls `HandleJSONRPCUserMessage` (each fan-out producing one node response per DON member) can exhaust the shared buckets and cause a victim's concurrent, legitimate request to silently lose node responses, risking the request never reaching `2F+1`/`F+1` quorum before `requestTimeout`.

### Finding Description
`fanOutToNodes`/`HandleJSONRPCUserMessage` creates an `activeRequest` and fans the request out to all `donConfig.Members` [1](#0-0) . Each DON member's reply flows back through `HandleNodeMessage`, which checks the per-node limiter and then the DON-wide `globalNodeRateLimiter` before recording the response and feeding the bundler: [2](#0-1) 

Both throttle checks return `nil` (not an error), meaning a throttled node response is dropped without any signal to the caller, the requester, or the bundling logic that data was lost, and without ever exposing "who" triggered the throttle. The limiters are single, DON-wide instances shared by every in-flight `activeRequest` for that DON [3](#0-2)  — there is no per-caller/per-requestID quota, so any legitimate high-volume caller consumes the same shared budget as everyone else on that DON. `fanOutToNodes` itself does not fail fast on a partial-answer condition; the request simply waits for quorum readiness or expiry via `removeExpiredRequests`/`forwardBundleOrTerminateIfReady`, and if the collected responses become viable it forwards a (possibly reduced) bundle rather than an outright failure [4](#0-3) .

This satisfies the stated attack pattern in principle: many requests to the shared DON (each producing many node responses) exhaust `globalNodeRateLimiter`/`perNodeRateLimiters`, and a concurrently-processed victim request's responses get silently dropped. However, this requires no privilege beyond being able to submit ordinary signed requests through the gateway (calling `HandleJSONRPCUserMessage` at a high rate) — there is no evidence of any authorization bypass, credential exposure, or cross-user data leakage; it is a resource-exhaustion/availability issue rooted in the absence of per-caller fairness on a shared limiter, not a confidentiality/integrity break.

### Impact Explanation
This is a scoped denial-of-service / degraded-availability issue: an unprivileged flooder can cause other legitimate callers' relay requests routed through the same DON to lose node responses and potentially miss quorum until timeout, without any explicit error attributing the cause. This falls under a "temporary/degraded denial of service via shared, unpartitioned rate limiting" class rather than fund loss, key/secret disclosure, or authentication/authorization bypass.

### Likelihood Explanation
The only precondition is the ability to submit signed gateway requests at a rate sufficient to make the DON send enough responses to exhaust the shared global/per-node buckets before they refill — no operator, admin, or malicious-node access is required. Feasibility depends heavily on the actual `cresettings.Default.GatewayConfidentialRelayGlobalRate`/`GatewayConfidentialRelayPerNodeRate` values (not inspected here) and on how many DON members/requests are needed to exhaust them; these could be tuned high enough to make this impractical in practice, which I could not verify from the code retrieved.

### Recommendation
Attribute rate-limit consumption/backoff to the originating request/owner rather than only to a DON-wide shared bucket (e.g., a per-requestID or per-owner quota in addition to the DON-wide guard), and have `HandleNodeMessage` surface throttling distinctly (e.g., via metrics/logging already present, plus optionally still counting the response toward the request's collected set) so that a single high-volume caller cannot silently starve unrelated requests on the same DON.

### Proof of Concept
1. Unit test in `core/services/gateway/handlers/confidentialrelay/handler_test.go`: create a `handler` with `globalNodeRateLimiter` set to a very low fixed rate (as in `TestGatewayHandler_MakeOutgoingRequest_NodeRateLimiting`'s "global rate limiting" pattern) and multiple DON members.
2. Simulate an "attacker" by calling `HandleNodeMessage` repeatedly for one request ID to exhaust `globalNodeRateLimiter.Allow`.
3. Then call `HandleJSONRPCUserMessage` for a second "victim" request ID and simulate node responses via `HandleNodeMessage` for that ID.
4. Assert that the victim's node responses are dropped (`HandleNodeMessage` returns `nil` but `ar.responses` for the victim's `activeRequest` never gets populated), and that the victim's request only resolves via `removeExpiredRequests` timeout path rather than quorum, demonstrating degraded service caused purely by unrelated traffic with no per-caller isolation.

func (h *handler) removeExpiredRequests(ctx context.Context) {
	h.mu.RLock()
	var expiredRequests []*activeRequest
	now := h.clock.Now()
	for _, userRequest := range h.activeRequests {
		if now.Sub(userRequest.createdAt) > h.requestTimeout {
			expiredRequests = append(expiredRequests, userRequest)
		}
	}
	h.mu.RUnlock()

	for _, er := range expiredRequests {
		responses := er.copiedResponses()
		l := logger.With(h.lggr, "method", er.req.Method, "requestID", er.req.ID)
		l.Debugw("request expired, evaluating collected relay responses",
			"collected", len(responses),
			"nodes", len(h.donConfig.Members),
			"unanswered", len(h.donConfig.Members)-len(responses),
		)
		summary, err := h.bundler.Bundle(er.req, responses, l)
		if err != nil {
			l.Errorw("failed to build relay response bundle", "error", err)
			if sendErr := h.sendResponseAndClearRequest(ctx, er, h.constructErrorResponse(er.req, api.FatalError, err)); sendErr != nil {
				l.Errorw("error returning bundle failure on expiry", "error", sendErr)
			}
			continue
		}
		// Expiry makes further responses unavailable to this request. The common
		// readiness path forwards a viable partial bundle or returns a timeout.
		if err := h.forwardBundleOrTerminateIfReady(ctx, l, er, summary, 0, true); err != nil {
			l.Errorw("error forwarding bundle on expiry", "error", err)
		}
	}

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	l := logger.With(h.lggr, "method", resp.Method, "requestID", resp.ID, "nodeAddr", nodeAddr)
	l.Debugw("handling node response")

	nodeRateLimiter, ok := h.perNodeRateLimiters[nodeAddr]
	if !ok {
		return fmt.Errorf("received message from unexpected node %s", nodeAddr)
	}
	if !nodeRateLimiter.Allow(ctx) {
		l.Debugw("node is rate limited", "nodeAddr", nodeAddr)
		return nil
	}
	if !h.globalNodeRateLimiter.Allow(ctx) {
		l.Debug("global relay rate limit exceeded")
		return nil
	}
