### Title
`get_token_account_balance` skips the mint-owner (`is_known_spl_token_id`) check that its sibling RPC methods perform, allowing misreported decimals/UI amount when a mint account is repurposed - ([File: rpc/src/rpc.rs])

### Summary
`JsonRpcRequestProcessor::get_token_account_balance` calls `get_mint_owner_and_additional_data` but discards the returned mint-account owner (`let (_, data) = get_mint_owner_and_additional_data(&bank, mint)?;`), unlike `get_token_supply`, `get_token_largest_accounts`, and `get_token_program_id_and_mint`, which all explicitly verify `is_known_spl_token_id(&mint_owner)` before trusting the unpacked `Mint` data. As a result, decimals/scaling data returned to the client for a token account can come from any account that merely unpacks as a `Mint`-shaped byte layout, regardless of which program currently owns it.

### Finding Description
The vulnerable path:
- `rpc/src/rpc.rs` `get_token_account_balance` (lines 2013-2035) validates only that the **token account itself** is owned by a known SPL token program (`is_known_spl_token_id(account.owner())`), unpacks it via `StateWithExtensions::<TokenAccount>::unpack`, extracts `token_account.base.mint`, and calls `get_mint_owner_and_additional_data(&bank, mint)`, discarding the returned owner: [1](#0-0) 
- `get_mint_owner_and_additional_data` in `rpc/src/parsed_token_accounts.rs` (lines 92-108) fetches the account at `mint`, and if it can be unpacked as a `Mint` via `get_additional_mint_data`/`StateWithExtensions::<Mint>::unpack`, returns `(*mint_account.owner(), mint_data)` — **without itself validating that owner is a recognized token program**: [2](#0-1) 
- Compare this to `get_token_supply` (lines 2037-2053) and `get_token_largest_accounts`/`get_token_program_id_and_mint` (lines 2076-2087, 2705-2719), which all explicitly check `is_known_spl_token_id(&mint_owner)` (or `mint_account.owner()`) before trusting the decoded mint data: [3](#0-2) [4](#0-3) 

Because the real SPL Token/Token-2022 program enforces `mint.owner == program_id` inside `InitializeAccount`, a token account cannot be *initially* created referencing an invalid mint. However, a mint account's ownership/content is not immutable for its lifetime: a mint created with the `MintCloseAuthority` extension can be closed (once supply is zero), freeing its address; the underlying keypair holder can then recreate an account at that same address, assign it to an arbitrary (attacker-controlled) program, and have that program write bytes matching the raw `Mint` layout (82-byte `Mint::LEN`) with fabricated `decimals`. Any pre-existing token account that still references that mint pubkey in `base.mint` will now have `get_token_account_balance` decode “decimals” from this attacker-controlled, non-token-program-owned account, since the missing owner check never rejects it.

### Impact Explanation
This causes `get_token_account_balance` to return a `UiTokenAmount` whose `decimals`/`ui_amount`/`ui_amount_string` are derived from data that is not actually validated as belonging to a legitimate SPL Token/Token-2022 mint, silently misreporting wrong-slot/wrong-account data to any RPC consumer (wallets, exchanges, integrators) that rely on `getTokenAccountBalance` decimals being authoritative. This matches the "wrong account data returned" scoped impact category, and represents an inconsistency/regression relative to the equivalent, correctly-guarded `get_token_supply` path in the same file.

### Likelihood Explanation
Exploitation requires only standard, unprivileged transactions: create a mint with `MintCloseAuthority`, create a token account against it, close the mint once supply is zero (reclaiming the address), recreate an account at that same pubkey assigned to an attacker-deployed program, and have that program write crafted `Mint`-shaped bytes. All of these are ordinary client-issued transactions with no validator/leader control, and the subsequent `getTokenAccountBalance` call is a single, low-rate JSON-RPC request, satisfying the unprivileged single-call precondition.

### Recommendation
In `get_token_account_balance` (`rpc/src/rpc.rs`), use the mint-owner value returned by `get_mint_owner_and_additional_data` and reject the request (or otherwise fail closed) if `!is_known_spl_token_id(&mint_owner)`, mirroring the guard already present in `get_token_supply` and `get_token_largest_accounts`.

### Proof of Concept
Rust unit test plan added to the `rpc.rs` token-account test module (mirroring the existing `getTokenAccountBalance` test around [5](#0-4) ):
1. Store a genuine token account `TA` owned by `spl_token_2022_interface::id()` with `base.mint = M` and `amount = 420`.
2. Store account `M` initially as a valid `Mint` owned by the token program with `decimals = 2`; call `getTokenAccountBalance(TA)` and assert `decimals == 2` (baseline, matches existing test).
3. Overwrite account `M` in the bank with the **same pubkey** but `owner` set to an arbitrary non-token program id (simulating post-close reuse), and raw data bytes matching `Mint::LEN` (82 bytes) with `decimals = 255` and `is_initialized = true`.
4. Call `getTokenAccountBalance(TA)` again and assert that it either:
   - returns an RPC error (consistent with what `getTokenSupply(M)` would return via its `is_known_spl_token_id` check), or
   - if it returns `Ok`, that `decimals != 255` / matches only genuinely-validated mint data.
5. Current code fails this assertion: it returns `Ok` with `decimals == 255`, proving the missing owner check.

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}
