### Title
Response cache key omits `WorkflowID`, causing cross-workflow HTTP response confusion for outbound HTTP actions - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
The HTTP Handlers V2 gateway documents that cached outbound HTTP responses are "scoped by workflow ID to prevent cross-workflow data leakage" [1](#0-0) , but the actual cache key computed by `OutboundHTTPRequest.Hash()` deliberately excludes `WorkflowID` and only differentiates by method, URL, headers, body and `WorkflowOwner` [2](#0-1) . This is confirmed by an explicit test asserting the hash is identical for two different `WorkflowID` values [3](#0-2) . As a result, two distinct workflows belonging to the same owner that issue the same outbound HTTP request (same method/URL/headers/body) will read and write the same cache entry, so a response fetched for workflow A can be returned to workflow B and vice versa.

### Finding Description
This mirrors the analog bug class from the report: state (yield, in the original report; here a cached HTTP response) is committed under a key/domain that omits a required differentiator (chain, in the original; `WorkflowID`, here), so state legitimately belonging to one context is applied to another.

The gateway's `gatewayHandler.makeOutgoingRequest` unmarshals an `OutboundHTTPRequest` coming from a capability node's outbound HTTP action and, when `CacheSettings.MaxAgeMs > 0`, calls `responseCache.Fetch` keyed by `req.Hash()` [4](#0-3) . The `Fetch`/`Set` implementation stores and retrieves entries strictly by this hash [5](#0-4) . Since `WorkflowID` is not part of the hash, any workflow under the same `WorkflowOwner` making an identical outbound HTTP request will collide with any other workflow's cached response for that same request, regardless of the two workflows being logically distinct and isolated units of execution.

### Impact Explanation
A workflow can unintentionally (or, if an owner runs multiple workflows with attacker-influenced URL/body parameters, deliberately) receive a cached HTTP response that was actually fetched on behalf of a different workflow. This breaks the documented workflow isolation guarantee and can lead to a workflow acting on stale or wrong external data that was never fetched for it — a direct analog to the original report's cross-chain accounting confusion, where state generated in one domain is consumed as if it belonged to another. Because HTTP action responses can feed subsequent workflow logic (including on-chain writes/targets), this cross-workflow response confusion can propagate incorrect data into workflow execution and downstream consequences.

### Likelihood Explanation
Reachable from any workflow node under a shared `WorkflowOwner` issuing outbound HTTP requests via the standard capability flow — no privileged or malicious-node behavior is required, and no special network position is needed. The collision is deterministic whenever method/URL/headers/body match and `CacheSettings.MaxAgeMs`/`Store` are used, which is a normal capability configuration.

### Recommendation
Include `WorkflowID` (and/or `WorkflowExecutionID` as appropriate) in the cache key computed by `Hash()` in `core/services/gateway/handlers/capabilities/v2/response_cache.go`, consistent with the documented "Workflow Isolation" behavior, so that cached responses cannot cross workflow boundaries even when the outbound request content and owner are identical.

### Proof of Concept
1. Workflow A (owner `0xAbC`) issues an `OutboundHTTPRequest{Method:"GET", URL:"https://api.example.com/data", CacheSettings:{Store:true, MaxAgeMs:600000}}`; the gateway fetches and caches the response keyed by `req.Hash()` (method+URL+headers+body+owner) [6](#0-5) .
2. Workflow B, a different `WorkflowID` but same owner `0xAbC`, issues an identical `OutboundHTTPRequest` (same method/URL/headers/body) with `CacheSettings.MaxAgeMs > 0`.
3. Because `Hash()` ignores `WorkflowID` [3](#0-2) , Workflow B's request hits the cache entry stored for Workflow A and receives Workflow A's response without ever issuing its own HTTP request, confirming cross-workflow response confusion.

## 3. HTTP Action Message Handling

### 3.1 Process Flow

1. **Request Reception**: Gateway receives HTTP action request from a workflow node
2. **Rate Limiting**: Validates node rate limits
3. **Request Parsing**: Extracts `OutboundHTTPRequest` from the JSON-RPC message
4. **Cache Check**: Determines if request should use cached response or fetch fresh data
5. **HTTP Execution**: Makes actual HTTP request to external endpoint
6. **Response Caching**: Stores cacheable responses (2xx, 4xx status codes) only if `CacheSettings.Store` is `true`
7. **Node Response**: Sends HTTP response back to requesting node

### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.
- **Cache TTL**: Configurable, default 10 minutes
- **Cache Key**: Generated from workflow ID and request hash
- **Cache Invalidation**: Time-based expiration with periodic cleanup
- **Cache Strategy**: All cacheable responses are cached; Non-zero `CacheSettings.MaxAgeMs` determines whether to return a cached value or make a fresh request
- **Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond

		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async

		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
