## Title
Missing re-initialization guard in `LockupContract::new` allows ownership hijack and loss of custody of locked/staked NEAR - (File: `lockup/src/lib.rs`)

### Summary
`LockupContract::new` is the `#[init]` constructor for the lockup contract, but unlike every other contract in this repository it never checks `env::state_exists()` before writing state. Any account can therefore call `new` again on an already-deployed, already-funded lockup contract and completely overwrite its owner, lockup schedule, vesting information and staking pointer.

### Finding Description
Every other `#[init]` constructor in this repository explicitly guards against re-initialization with `assert!(!env::state_exists(), ...)`:

- `lockup-factory::new` [1](#0-0) 
- `multisig::new` [2](#0-1) 
- `staking-pool-factory::new` [3](#0-2) 
- `staking-pool::new` [4](#0-3) 
- `whitelist::new` [5](#0-4) 

`LockupContract::new`, however, has no such guard: it validates arguments but never asserts `!env::state_exists()` before constructing and returning a fresh `Self`, which `near_bindgen` will persist over the existing state. [6](#0-5) 

This is the direct analog of the reported bug class: an upgradable/initializable contract that forgot to guard its initializer, letting an unprivileged caller re-run initialization and seize control (the report's `_guardInitializeOwner` omission causing `Ownable` hijack). Here the missing `state_exists` check plays the exact same role for the NEAR `#[init]` pattern.

The binding broken is:
`owner_account_id (and lockup_information/vesting_information/staking_information)` recorded in contract state **must equal** the values fixed at the one legitimate deployment-time initialization. After a malicious re-init call, `owner_account_id` can be set to an attacker-controlled account while `lockup_information.lockup_amount` is recomputed from `env::account_balance()` (the NEAR that is still physically held/staked by the account), and `staking_information` is reset to `None`, erasing any record of NEAR already delegated to a staking pool even though that NEAR is still out there under the (now attacker-controlled) account's identity.

### Impact Explanation
This is Critical: it is a wrongly-parameterized/hijacked deployment enabling unauthorized movement of NEAR. Since `LockupContract` methods gated by `assert_owner()` style checks compare against `self.owner_account_id` (set from the corrupted state), calling `new` again with `owner_account_id` = attacker lets the attacker subsequently invoke all owner-only lockup functions (`transfer`, `select_staking_pool`, `deposit_and_stake`, `unstake`, `withdraw`, etc.), fully capturing the NEAR held by (or staked from) the lockup account — funds that legitimately belong to the original lockup beneficiary.

### Likelihood Explanation
High/trivial to exploit: `new` is a plain public function call requiring no special permission — any account can send a `FunctionCall` transaction with method name `new` and attacker-chosen arguments to the deployed lockup contract account at any time after deployment, since nothing prevents re-entry into the constructor.

### Recommendation
Add the same guard used throughout the rest of the repo at the top of `LockupContract::new`:
```rust
assert!(!env::state_exists(), "The contract is already initialized");
```
in `lockup/src/lib.rs`, mirroring `staking-pool/src/lib.rs`, `whitelist/src/lib.rs`, `multisig/src/lib.rs`, `lockup-factory/src/lib.rs`, and `staking-pool-factory/src/lib.rs`.

### Proof of Concept
1. Deploy `lockup-contract` normally with `owner_account_id = alice`, funded with `N` NEAR (as shown in the factory's deployment flow, `lockup-factory/src/lib.rs` `create`). [7](#0-6) 
2. Attacker (`mallory`) calls `new` directly on the same deployed lockup account:
```
near call <lockup_account> new '{"owner_account_id":"mallory", "lockup_duration":"0", "lockup_timestamp":null, "transfers_information":{"TransfersEnabled":{"transfers_timestamp":"0"}}, "vesting_schedule":null, "release_duration":null, "staking_pool_whitelist_account_id":"<whitelist>", "foundation_account_id":null}' --accountId mallory
```
Because `LockupContract::new` never checks `env::state_exists()`, this call succeeds and overwrites `owner_account_id` to `mallory`, resets `lockup_information` (recomputed from the account's current balance, unlocked immediately since `lockup_duration`/`lockup_timestamp` are attacker-chosen) and clears `staking_information`.
3. `mallory` now calls owner-only methods (e.g. `transfer`) to withdraw the NEAR held by the lockup account, which previously belonged to `alice`.

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
