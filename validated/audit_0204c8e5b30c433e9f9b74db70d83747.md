### Title
ERC4626 liquidity injection lets any vault share holder brick `stopEpoch`, freezing all lender funds - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
The command-injection analog: `stopEpoch` treats the shared ERC4626 vault's liquidity as a trusted input and unconditionally executes `vault.withdraw(shortfall)` inside `ProgrammableBorrower.onStopEpoch`. An unprivileged holder of shares in that external vault can "inject" a hostile liquidity state — draining the vault's free underlying in the same block — so `withdraw` reverts and the whole `stopEpoch` transaction rolls back via `StopEpochVaultLiquidityUnavailable`. Repeatable every time liquidity returns, this keeps the epoch un-stoppable and all tranche holders' principal and yield locked.

### Finding Description
In `IdleCDOEpochVariant.stopEpoch`, when `isProgrammableBorrower` is set the flow calls `IProgrammableBorrower.onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)` and lets hook reverts bubble (explicitly "so transient ERC4626 liquidity failures can be retried") [1](#0-0) . Inside `onStopEpoch`, whenever the requested cash exceeds the contract's on-hand balance, it calls `vault.withdraw(shortfall, ...)` and reverts `StopEpochVaultLiquidityUnavailable` on failure [2](#0-1) . The check `shortfall > _currentVaultAssets() return true` does not help: `convertToAssets` still reports full share value even when the vault's cash buffer is empty [3](#0-2) .

An attacker who holds shares of the same ERC4626 vault (a permitted attacker class) front-runs the honest manager's `stopEpoch` with `vault.withdraw(max)` / `redeem(all)`, leaving near-zero free liquidity. `onStopEpoch`'s `withdraw` then reverts, the revert propagates out of `stopEpoch`, and `isEpochRunning`, `allowInstantWithdraw`, and tranche prices all stay frozen. The attacker re-supplies liquidity only while no `stopEpoch` is pending (or simply redeems again after each deposit), sustaining the freeze at the cost of temporarily parking capital.

### Impact Explanation
Temporary freezing of all lender principal and yield in the credit vault: deposits are paused during a running epoch and withdrawal requests/claims are gated behind `stopEpoch`, so while the vault stays drained no AA/BB holder can exit. The freeze duration is attacker-controlled (as long as liquidity is kept drained) and scales to the full pool TVL, e.g. 10M USDC locked for the duration. No privileged role misbehavior is needed; only an ordinary ERC4626 vault user transacting normally.

### Likelihood Explanation
Requires only that the configured ERC4626 vault is shared/public (e.g., a Morpho/ERC4626 vault, as in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`) and that the attacker can acquire vault shares or flash-borrow-like redeemable liquidity. The design intentionally makes these reverts retryable rather than falling back to the default path, so there is no recovery branch: `shortfall <= _currentVaultAssets()` forces a `withdraw` attempt that must succeed. Any single transaction ordering where liquidity is missing causes a full revert — one monitoring bot suffices.

### Recommendation
Don't let external vault liquidity be a hard dependency of `stopEpoch`. Either: (a) catch the `withdraw` failure inside `onStopEpoch` and return `false`/partial so IdleCDO proceeds with available cash or routes to `_handleBorrowerDefault`, or (b) pre-pull a reserve of underlying equal to `epochPendingWithdraws + expectedInterest` at `onStartEpoch` into the borrower's own balance so epoch-end obligations never depend on the vault's instantaneous free liquidity.

### Proof of Concept
Foundry fork sketch (modeled on `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
// Setup: IdleCDOEpochVariant + IdleCreditVault + ProgrammableBorrower on a real Morpho ERC4626 vault
idleCDO.depositAA(10_000e6);            // honest lender
cdoEpoch.startEpoch();                  // PB.onStartEpoch deposits surplus into vault
// Attacker (vault share holder, unprivileged) front-runs stopEpoch:
vm.prank(attacker);
morphoVault.withdraw(morphoVault.maxWithdraw(attacker), attacker, attacker); // drain liquidity
vm.prank(manager);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 0);               // reverts via onStopEpoch -> vault.withdraw catch
// Repeat drain each time liquidity returns -> epochEndDate passes, pool un-closable,
// claimWithdrawRequest / claimInstantWithdrawRequest remain disabled: funds frozen.
```
