### Title
ERC4626 share-inflation lets a vault user steal `ProgrammableBorrower` principal while IdleCDO preserves the stolen NAV - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower._depositToVault()` trusts the configured ERC4626 vault’s `deposit()` result and never validates that the borrower received economically meaningful shares. An unprivileged vault user can perform the standard share-price inflation attack so the epoch deposit mints zero vault shares, then redeem their own shares and receive the vault’s donation plus the entire `ProgrammableBorrower` deposit.

The stolen principal remains recorded as `epochStartVaultAssets`, while the CDO continues to value the corresponding strategy tokens at par because the programmable-borrower integration only consumes `totalInterestDueNow()`, which floors losses at zero instead of reporting principal impairment.

### Finding Description
During `onStartEpoch`, the borrower snapshots `underlyingToken.balanceOf(address(this)) + _currentVaultAssets()` into `epochStartVaultAssets`, then deposits all idle underlying into the configured vault. [1](#0-0) 

`_depositToVault` calls `vault.deposit(_assetAmount, address(this))` and only updates accounting; it does not check `shares`, compare the returned share value with `_assetAmount`, or enforce a minimum shares-out value. [2](#0-1) 

For a first or attacker-dominated vault position, an attacker can deposit one unit, donate enough underlying to make one share worth more than the upcoming epoch deposit, and cause the borrower’s deposit to round down to zero shares under ordinary ERC4626 conversion math. The attacker then redeems their one share and receives both their donated assets and the borrower’s deposit.

Afterward, `_currentVaultAssets()` is zero because the borrower has zero shares. [3](#0-2) 

`_vaultNetInterest()` correctly computes the resulting principal loss, but `totalInterestDueNow()` returns zero once the loss exceeds gains rather than exposing the principal shortfall. [4](#0-3) 

IdleCDO uses that returned value as the resolved epoch result and does not independently reconcile it with the principal originally sent to the borrower. [5](#0-4) 

The CDO’s NAV is still based on its strategy-token balance and raw underlying, not on the actual assets recoverable from the programmable borrower’s vault position. [6](#0-5) 

If no withdrawal or close-pool recall requires immediate cash, `stopEpoch` can therefore complete successfully with zero reported interest while the stolen principal remains accounted as live pool NAV. [7](#0-6) 

When the pool eventually needs the missing principal, `getFundsFromBorrower` fails and the code enters the borrower-default path. [8](#0-7) [9](#0-8) 

### Impact Explanation
Let the programmable borrower receive `A` underlying at epoch start.

The attacker deposits `1 wei` into an empty ERC4626 vault, donates `D > A`, and therefore owns one share worth approximately `D`. When `onStartEpoch` deposits `A`, the vault mints `A * 1 / (D + 1) == 0` shares to the borrower.

The attacker redeems one share and receives approximately `A + D`, recovering their donation and taking the full `A`. The credit pool loses `A`, while the CDO still carries `A` strategy tokens and reports zero epoch interest rather than reducing NAV.

For example, with `A = 500,000 USDC` and `D = 1,000,000 USDC`, the attacker obtains the entire `500,000 USDC` epoch deposit in addition to their recoverable donation. Subsequent withdrawals or close-pool settlement are undercollateralized by `500,000 USDC` and must default or socialize the loss.

### Likelihood Explanation
The attack is permissionless from the perspective of the ERC4626 vault: any user can deposit and donate underlying to alter the asset-per-share ratio. The owner and manager remain honest and merely configure a valid vault and start the epoch.

The precondition is that the attacker controls all or almost all vault shares, or that the configured vault has sufficiently low existing liquidity for share-price inflation to make the borrower’s deposit mint uneconomically few or zero shares. This is most practical for newly configured or thinly capitalized ERC4626 vaults; highly liquid vaults with many independent shareholders make the attack substantially more expensive.

No malicious borrower, owner, manager, guardian, queue, or vault implementation is required: the attacker only performs ordinary deposits, donations, and redemptions as a vault user.

### Recommendation
Validate ERC4626 deposits against the expected execution result rather than trusting the returned object implicitly:

```solidity
uint256 expectedShares = vault.previewDeposit(_assetAmount);
uint256 minShares = expectedShares * (10_000 - maxDepositSlippageBps) / 10_000;
uint256 shares = vault.deposit(_assetAmount, address(this));
if (shares < minShares || vault.convertToAssets(shares) < _assetAmount - maxDepositDust) {
    revert InvalidAmount();
}
```

Also expose a signed or principal-aware programmable-borrower settlement value. If `borrowerPrincipal + vault.convertToAssets(vault.balanceOf(address(this))) + underlyingToken.balanceOf(address(this))` is below the principal baseline, `IdleCDOEpochVariant` should realize that principal loss through the loss-burn/default path rather than treating `totalInterestDueNow() == 0` as a successful zero-interest epoch.

### Proof of Concept
The following Foundry test uses a standard OpenZeppelin ERC4626 implementation and requires no malicious vault code. It can run on a mainnet fork because the attack depends only on permissionless ERC4626 deposits and donations.

```solidity
// test/foundry/ProgrammableBorrowerShareInflation.t.sol
function test_shareInflationStealsEpochDeposit() public {
    vm.createSelectFork(vm.envString("MAINNET_RPC_URL"));

    uint256 epochDeposit = 500_000e6;
    uint256 donation = 1_000_000e6;

    MockERC20 underlying = new MockERC20("USDC", "USDC", 6);
    InflationVault vault = new InflationVault(IERC20(address(underlying)));

    ProgrammableBorrower impl = new ProgrammableBorrower();
    MockIdleCDO idleCDO = new MockIdleCDO(address(underlying));

    ProgrammableBorrower borrower = ProgrammableBorrower(
        address(
            new TransparentUpgradeableProxy(
                address(impl),
                address(this),
                abi.encodeWithSelector(
                    ProgrammableBorrower.initialize.selector,
                    address(vault),
                    address(idleCDO),
                    address(this),
                    manager,
                    honestBorrower,
                    0
                )
            )
        )
    );

    // CDO sends the epoch's capital to the programmable borrower.
    underlying.mint(address(borrower), epochDeposit);

    // Attacker creates the only vault share and inflates its price.
    underlying.mint(attacker, donation + 1);
    vm.startPrank(attacker);
    underlying.approve(address(vault), 1);
    vault.deposit(1, attacker);          // 1 share
    underlying.transfer(address(vault), donation);
    vm.stopPrank();

    // Honest manager starts the epoch through IdleCDO.
    vm.prank(address(idleCDO));
    borrower.onStartEpoch(0);

    // The deposit rounded down to zero shares.
    assertEq(vault.balanceOf(address(borrower)), 0);
    assertEq(borrower.epochStartVaultAssets(), epochDeposit);

    // Attacker redeems the only share and receives donation + epoch deposit.
    vm.prank(attacker);
    vault.redeem(1, attacker, attacker);

    assertEq(underlying.balanceOf(attacker), donation + epochDeposit + 1);
    assertEq(borrower.totalInterestDueNow(), 0);
    assertEq(borrower.totalUnderlying(), 0);
}
```

The decisive assertion is that `epochStartVaultAssets == epochDeposit` while `totalUnderlying() == 0`: the borrower’s accounting still preserves the stolen principal baseline even though the vault user extracted the assets.
