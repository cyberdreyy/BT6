### Title
Stale per-epoch instant-withdraw counters inflate default recovery basis and permanently lock recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug class is "data that was never (re)initialized being read by later logic" — the ppp driver left a header byte uninitialized and a crafted reader consumed it. `IdleCreditVault` has the same shape: `claimInstantWithdrawRequest` clears the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch records `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. If a default is later finalized in the same epoch, `defaultPendingClaimBasis` reads those stale counters as if the receipts were still unfunded, inflating the recovery denominator and stranding the corresponding share of `defaultRecoveryReserve` forever.

### Finding Description
- `requestInstantWithdraw` writes both the aggregate and per-epoch records: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (IdleCreditVault.sol:367-374).
- `claimInstantWithdrawRequest` only zeroes `instantWithdrawsRequests[_user]`; the per-epoch fields are left untouched (IdleCreditVault.sol:387-392). They are only cleared in `_claimDefaultedInstantWithdrawRequest`, which runs solely on the post-default path (IdleCreditVault.sol:844-853).
- At finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the claim basis whenever `pendingInstantWithdraws != 0` (IdleCreditVault.sol:644-648). `finalizeDefaultRecovery` then computes `recoveryPrice = reserveAmount * 1e18 / totalBasis` using that inflated basis (IdleCreditVault.sol:679-692).

Attack sequence (running epoch, partially funded instant queue, then borrower default):
1. Attacker and victim each call `requestInstantWithdraw` for 100 (via the CDO), same epoch: `instantWithdrawClaimsByEpoch[epoch] = 200`, `pendingInstantWithdraws = 200`.
2. Honest borrower/CDO funds partially: `collectInstantWithdrawFunds(150)` → `pendingInstantWithdraws = 50`, strategy holds 150 underlying.
3. Attacker calls `claimInstantWithdrawRequest` and receives 100 underlying. His `instantWithdrawsRequests` is 0 but `instantWithdrawsRequestsByEpoch[attacker][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` still hold his already-paid 100.
4. Borrower defaults; owner calls the CDO default flow → `finalizeDefaultRecovery(R, source)`. Basis includes the stale 200 instant claims instead of the real 100 unfunded (victim's). `recoveryPrice` is therefore roughly halved; the victim's `_claimDefaultedInstantWithdrawRequest` pays `100 * recoveryPrice`, and the share of the reserve earmarked for the attacker's phantom claim is never claimable (a later call would underflow `instantWithdrawsRequests[attacker] -= 100`), so it remains locked in the strategy permanently.

### Impact Explanation
Broken invariant: one receipt, one payout. An already-paid instant receipt is double-counted into the default recovery denominator. Every other defaulted-epoch and post-default claimant's `defaultRecoveryPrice` is diluted pro rata (direct loss of recovery proceeds), and the reserve fraction attributed to stale claims can never be withdrawn — `defaultRecoveryReserve` only decreases via `_transferDefaultRecovery`, so the excess underlying is permanently frozen in the strategy. The loss scales linearly with the amount of instant withdrawals claimed between `collectInstantWithdrawFunds` and `finalizeDefaultRecovery`; a large instant claimant can dilute the recovery price arbitrarily toward the funded-vs-pending ratio.

### Likelihood Explanation
Requires no malicious privileged role: the attacker is an ordinary KYC'd lender using the instant-withdraw path. The triggering conditions are (a) a partially funded instant queue, (b) at least one funded claim executed before default finalization, and (c) a default finalized in the same `epochNumber`. Partial instant funding is an explicit supported mode (`pendingInstantWithdraws` tracks the unfunded remainder, and `_defaultPrefundedInstantReserve` exists precisely for it). The victim cannot avoid it; the dilution applies automatically at finalization.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch records alongside the aggregate: subtract the claimed amount from `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` (tracking the request epoch, or clearing all epochs up to the current one), so `defaultPendingClaimBasis` only ever counts still-unpaid receipts.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (against contracts/strategies/idle/IdleCreditVault.sol)
// Setup: vault with idleCDO set, underlying funded, epoch running.
function test_StaleInstantReceiptDilutesDefaultRecovery() public {
    // attacker and victim each request 100e6 instant withdraw via CDO
    vm.prank(cdo); vault.requestInstantWithdraw(100e6, attacker);
    vm.prank(cdo); vault.requestInstantWithdraw(100e6, victim);
    assertEq(vault.instantWithdrawClaimsByEpoch(vault.epochNumber()), 200e6);

    // CDO partially funds the instant queue: 150 of 200
    deal(address(underlying), cdo, 150e6);
    vm.startPrank(cdo);
    underlying.approve(address(vault), 150e6);
    vault.collectInstantWithdrawFunds(150e6); // pendingInstantWithdraws = 50
    vm.stopPrank();

    // attacker claims his fully-funded receipt BEFORE any default
    vm.prank(cdo); vault.claimInstantWithdrawRequest(attacker);
    assertEq(underlying.balanceOf(attacker), 100e6);
    // stale per-epoch records remain:
    assertEq(vault.instantWithdrawsRequestsByEpoch(attacker, vault.epochNumber()), 100e6);

    // borrower defaults; owner finalizes with external recovery R = 100e6
    // (simplified: no active basis, only instant receipts)
    vm.prank(cdo);
    vault.finalizeDefaultRecovery(100e6, recoverySource);

    // recoveryPrice = 100e6 * 1e18 / 200e6 = 0.5e18 instead of 1e18
    assertEq(vault.defaultRecoveryPrice(), 0.5e18);

    // victim claims only 50e6 though his receipt was the only unfunded one
    vm.prank(cdo); vault.claimInstantWithdrawRequest(victim);
    assertEq(underlying.balanceOf(victim), 50e6);

    // attacker re-claiming the stale entry reverts (underflow on aggregate),
    // and the remaining 50e6 of reserve is permanently locked in the vault.
    vm.prank(cdo);
    vm.expectRevert();
    vault.claimInstantWithdrawRequest(attacker);
    assertEq(underlying.balanceOf(address(vault)), 50e6 + vault.defaultRecoveryReserve());
}
```
