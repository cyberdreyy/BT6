### Title
Withdraw confidential-transfer parser mislabels a proof-context account as "owner" when account count is insufficient for the claimed offsets - ([File: transaction-status/src/parse_token/extension/confidential_transfer.rs])

### Summary
In the `Withdraw` arm of `parse_confidential_transfer_instruction`, the offsets consumed for `instructionsSysvar`, `equalityProofContextStateAccount`, and `rangeProofContextStateAccount` are each gated only by `offset < account_indexes.len().saturating_sub(1)`, with no validation that the account list actually contains enough entries for the combination of `equality_proof_instruction_offset` and `range_proof_instruction_offset` claimed in the (attacker-controlled) instruction data. When an attacker crafts a Withdraw instruction whose account list is one account short of what the offsets imply, the trailing bounds check silently drops the `rangeProofContextStateAccount` field and the account that is semantically the range-proof context account is instead consumed by `parse_signers` and reported as `"owner"`.

### Finding Description
The relevant code is in `parse_confidential_transfer_instruction`'s `Withdraw` arm [1](#0-0) . Only `check_num_token_accounts(account_indexes, 4)` is enforced, i.e. a floor of 4 accounts, regardless of what `equality_proof_instruction_offset`/`range_proof_instruction_offset` require [2](#0-1) . Both offsets and the amount/decimals/balance fields come straight from `WithdrawInstructionData`, decoded from raw, attacker-supplied instruction bytes with no cross validation against `account_indexes` length semantics [3](#0-2) .

Walking the logic with `account_indexes.len() == 4` (the checked minimum) and `equality_proof_instruction_offset == 0`, `range_proof_instruction_offset == 0` (i.e. attacker claims *both* proofs are supplied via separate context-state accounts, which per real protocol semantics requires 5 accounts: account, mint, eq-ctx, range-ctx, owner):

- `offset` starts at 2, `has_sysvar` is `false` (both offsets are 0), so the sysvar branch is skipped.
- `equality_proof_instruction_offset == 0` and `2 < 4 - 1 (=3)` → true, so `account_indexes[2]` is labeled `"equalityProofContextStateAccount"`, `offset` becomes 3.
- `range_proof_instruction_offset == 0` and `3 < 3` → **false**, so the `"rangeProofContextStateAccount"` field is **silently omitted** even though the offset value says a context account is required.
- `parse_signers(map, offset=3, ...)` then treats `account_indexes[3]` — the account that per protocol semantics should be the range-proof context-state account — as `"owner"` [4](#0-3) .

This is a parse-fidelity violation: the JSON output claims `rangeProofInstructionOffset: 0` (context-account mode) but omits `rangeProofContextStateAccount` entirely, and instead reports the true range-proof context account's pubkey under the `"owner"` field — an authority misattribution. The existing bounds check (`offset < len - 1`) only prevents index-out-of-range panics; it does not verify that the number of accounts actually matches what the claimed offset combination requires, so nothing stops this mislabeling.

The instruction is reachable by any unprivileged client: submit a transaction invoking the SPL Token-2022 program's `ConfidentialTransferExtension`/`Withdraw` sub-instruction with a crafted account list (4 accounts) and `equality_proof_instruction_offset = 0`, `range_proof_instruction_offset = 0` in the instruction data, then call `getTransaction` with `encoding: jsonParsed`. `parse_token` → `parse_confidential_transfer_instruction` is invoked on the stored instruction independent of whether the transaction succeeded on-chain (the real Token-2022 program would likely fail such an under-provisioned instruction with an account-count error, but the failed transaction is still stored and returned by `getTransaction`, and the parser runs regardless of `meta.err`).

### Impact Explanation
This falls under the "misreported program/authority/amount/decimals/owner" scope: `getTransaction`'s `jsonParsed` encoding can return a pubkey under the `"owner"` field that is not actually an authority/owner but is the range-proof context-state account, while the `rangeProofContextStateAccount` field is missing. Any client, explorer, or indexer relying on RPC-parsed instruction data for this instruction type can be misled about which account is the withdrawal authority versus which account is a proof-context account. No consensus, funds, or validator-crash impact — this is a decoding/parse-fidelity correctness bug in `transaction-status`.

### Likelihood Explanation
Fully attacker-controlled and requires no privilege: only a single signed transaction (which need not even succeed on-chain) referencing the Token-2022 program with a `Withdraw` confidential-transfer instruction, followed by one `getTransaction(jsonParsed)` call. The offset bytes and account list are entirely within the attacker's control, and the minimum-account check (`check_num_token_accounts(..., 4)`) does not scale with the number of proof accounts implied by the offsets, making the mismatch trivially reproducible.

### Recommendation
In the `Withdraw` (and analogous `Transfer`/`TransferWithFee`) arms, compute the exact expected account count from `equality_proof_instruction_offset`/`range_proof_instruction_offset` (number of context-state accounts needed + optional sysvar + trailing owner/signers) and enforce it via `check_num_token_accounts` (or an equivalent explicit check) before consuming accounts, rather than relying solely on the generic `offset < len - 1` guard. If the account count doesn't match what the offsets imply, return `ParseInstructionError::InstructionNotParsable` instead of silently omitting a field and misattributing the account to `"owner"`.

### Proof of Concept
Add to `transaction-status/src/parse_token/extension/confidential_transfer.rs` test module:

```rust
#[test]
fn test_withdraw_underprovisioned_accounts_mislabels_owner() {
    let token_account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let range_ctx_should_be = Pubkey::new_unique(); // actually intended as range-proof ctx
    let account_keys = vec![token_account, mint, Pubkey::new_unique(), range_ctx_should_be];

    // Craft compiled instruction data manually: WithdrawInstructionData with
    // equality_proof_instruction_offset = 0, range_proof_instruction_offset = 0,
    // but only 4 accounts supplied (one short of the 5 required for two
    // context-state accounts + owner).
    let data = build_withdraw_data(/* amount */ 1, /* decimals */ 0,
        /* eq_offset */ 0, /* range_offset */ 0);
    let instruction = CompiledInstruction {
        program_id_index: 0, // token-2022 program index
        accounts: vec![0, 1, 2, 3],
        data,
    };

    let parsed = parse_confidential_transfer_instruction(
        &instruction.data[1..],
        &instruction.accounts,
        &AccountKeys::new(&account_keys, None),
    )
    .unwrap();

    // Bug: rangeProofContextStateAccount is missing even though
    // rangeProofInstructionOffset == 0 implies it should be present.
    assert!(parsed.info.get("rangeProofContextStateAccount").is_none());

    // Bug: the account that should be the range-proof context state account
    // is instead reported as "owner".
    assert_eq!(
        parsed.info["owner"],
        json!(range_ctx_should_be.to_string())
    );
}
```
Expected (buggy) result: the assertions pass, demonstrating `rangeProofContextStateAccount` is dropped and its pubkey is relabeled `"owner"`. A fixed implementation should instead return `Err(ParseInstructionError::InstructionNotParsable(ParsableProgram::SplToken))` for this malformed account/offset combination.
