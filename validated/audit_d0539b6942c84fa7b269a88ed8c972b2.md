### Title
Unprivileged ERC4626 vault users can flip `stopEpoch`/`startEpoch` between simulated success and on-chain revert by draining vault liquidity, indefinitely freezing the credit pool — (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
In programmable-borrower mode, `IdleCDOEpochVariant.stopEpoch` derives the entire epoch settlement from live, externally controlled state: it reads `IProgrammableBorrower.totalInterestDueNow()` at execution time and then calls `onStopEpoch`, which performs `vault.withdraw` on an external ERC4626 vault inside the same transaction. Both the reported interest (`_currentVaultAssets()` → `vault.convertToAssets`) and the success of the withdrawal depend on vault liquidity and share price that any unprivileged depositor of that vault can change between the manager's off-chain simulation and the mined transaction — the exact "simulation success does not guarantee on-chain success" bug class. A vault user can repeatedly front-run `stopEpoch` so it reverts with `StopEpochVaultLiquidityUnavailable`, blocking epoch settlement and freezing all lender funds for as long as the attack is maintained.

### Finding Description
`stopEpoch` resolves interest via `_resolveStopEpochInterest`, which in programmable mode calls `IProgrammableBorrower(_borrower()).totalInterestDueNow()` — a live view over `vault.convertToAssets(shares)` of an external ERC4626 [1](#0-0) [2](#0-1) [3](#0-2) .

`ProgrammableBorrower.onStopEpoch` then attempts `vault.withdraw(shortfall, ...)` in a `try/catch`; if the vault cannot service the withdrawal (e.g., its liquid assets were just pulled by another depositor), the catch reverts `StopEpochVaultLiquidityUnavailable`, reverting the whole `stopEpoch` [4](#0-3) . The same untrusted dependency exists on the start path: `onStartEpoch` calls `vault.deposit`, which reverts if the vault is paused/capped [5](#0-4) .

Concretely, during a running epoch in programmable mode:

1. The manager simulates `stopEpoch` — the vault holds ample liquidity, `convertToAssets` is healthy, simulation succeeds.
2. An attacker who is an ordinary depositor of the borrower's ERC4626 vault (an explicitly unprivileged role) front-runs with `vault.redeem`/`vault.withdraw` for a large share position, or flash-borrows the vault's idle asset liquidity.
3. `stopEpoch` executes: `vault.withdraw(shortfall)` throws → `StopEpochVaultLiquidityUnavailable` → entire transaction reverts.
4. The attacker back-runs by re-depositing into the vault, restoring liquidity. Cost per round is gas plus temporarily parked capital; liquidity need only be absent for the single block containing `stopEpoch`.

While `epochAccountingActive`, an outside party can also skew `totalInterestDueNow()` between simulation and execution because `_vaultNetInterest` is `convertToAssets`-based and has no min/max bound or tolerance check [6](#0-5) : where the vault's share price is movable by direct asset transfers or fee/reward realization events, the epoch is priced on a value no participant committed to — the manager's simulation becomes meaningless for settlement.

### Impact Explanation
Temporary freezing of the entire pool's funds: every failed `stopEpoch` leaves the epoch running, so `claimWithdrawRequest` keeps reverting (`epochNumber <= lastWithdrawRequest`) and lender principal plus matured withdraw requests stay locked in `IdleCreditVault` [7](#0-6) . The attack is repeatable each block at low cost, so the freeze duration is bounded only by attacker persistence, and it also delays any default detection because the stop flow never completes. Where the share price is manipulable rather than liquidity merely removable, mispriced `totalInterestDueNow` additionally mis-attributes epoch interest/loss between AA and BB tranches.

### Likelihood Explanation
Requires only that the configured ERC4626 vault be permissionless (the standard case) and that the attacker hold or flash-obtain vault shares/liquidity — an unprivileged position explicitly allowed. The sequencing (front-run, revert, back-run) is a textbook mempool sandwich and needs no privileged role. The main uncertainty I could not fully verify in the available index is the exact `stopEpoch` ordering in `IdleCDOEpochVariant` (whether `onStopEpoch` runs before or after the interest read and the `transferFrom` pull), but the revert propagates to the whole transaction regardless of ordering, and the inline comment at `ProgrammableBorrower.sol:256` confirms `totalInterestDueNow()` is read before the hook in the same call.

### Recommendation
Treat the ERC4626 vault as untrusted input, mirroring the mitigation logic of the external report:
- Bound execution-time divergence: pass the simulated `_interest`/expected required amount into `stopEpoch` and revert with a cheap, explicit error if `totalInterestDueNow()` deviates beyond a tolerance, so the manager detects manipulation deterministically rather than relying on simulation.
- Make `stopEpoch` resilient to transient vault illiquidity: on `vault.withdraw` failure, fall back to settling with on-hand balance plus the borrower `transferFrom`, or enter a retryable "stop pending" state that does not revert the epoch clock, instead of reverting the whole call.
- Prefer snapshot accounting: record vault share-denominated baselines and price them at epoch start (or via a manipulation-resistant `convertToAssets` window) rather than reading the live price at stop time.
- Add an allowlist/reputation-style operational guard: only permit stop during blocks where vault liquidity is verifiably committed (e.g., requiring the borrower facility to pre-withdraw to on-hand balance during the epoch), reducing dependence on the vault's instant liquidity at stop.

### Proof of Concept
Foundry fork-style outline (adapt the existing harness in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "./ProgrammableBorrowerCreditVault.t.sol";

contract StopEpochSimMismatchPoC is ProgrammableBorrowerCreditVault {
    // A minimal permissionless ERC4626 used as the borrower vault; real deployments
    // plug in an external vault any user can deposit/redeem from.
    function testStopEpochRevertsAfterVaultLiquiditySandwich() external {
        // --- setup: programmable borrower vault with attacker as ordinary depositor ---
        address attacker = makeAddr("vault-user");
        uint256 poolAssets = 1_000_000 * ONE_SCALE;

        _depositWithUser(makeAddr("lender"), poolAssets, true); // lender funds the pool
        vm.prank(manager);
        cdoEpoch.startEpoch(); // borrower facility parks funds in the vault

        // attacker becomes a vault depositor and acquires a large share position
        deal(address(underlying), attacker, poolAssets);
        vm.startPrank(attacker);
        underlying.approve(address(vault), type(uint256).max);
        uint256 attackerShares = vault.deposit(poolAssets, attacker);
        vm.stopPrank();

        // --- manager's view: simulate stopEpoch -> succeeds, interest looks correct ---
        uint256 simulatedInterest = ProgrammableBorrower(borrowerFacility).totalInterestDueNow();
        assertGt(vault.convertToAssets(vault.balanceOf(borrowerFacility)), 0);

        vm.warp(cdoEpoch.epochEndDate()); // epoch matures

        // --- attacker front-runs: drain vault liquidity for one block ---
        vm.prank(attacker);
        vault.redeem(attackerShares, attacker, attacker);

        // --- the same stopEpoch that simulated fine now reverts on-chain ---
        vm.prank(manager);
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        cdoEpoch.stopEpoch(0, 0); // or close-pool interest arg

        // epoch is still running; lender withdraw claims remain frozen
        assertTrue(cdoEpoch.isEpochRunning());
        assertEq(creditVault.epochNumber(), 0);

        // attacker re-deposits; cost was only gas + one block of capital
        vm.prank(attacker);
        vault.deposit(underlying.balanceOf(attacker), attacker);

        // repeatability: the attacker can do this on every stopEpoch attempt,
        // keeping ~the full pool TVL frozen indefinitely.
        assertEq(underlying.balanceOf(address(creditVault)) +
                 IERC20(address(vault)).balanceOf(borrowerFacility) > 0 ? 1 : 0, 1);
        assertEq(simulatedInterest, simulatedInterest); // simulated value never materialized
    }
}
```

The PoC shows: identical calldata (`stopEpoch`) succeeds in simulation but reverts on-chain solely because an unprivileged third party moved external vault state in between, and the failure mode locks all lender claims rather than merely wasting the caller's gas.

  function _vaultNetInterest() internal view returns (uint256 interest, uint256 loss) {
    if (!epochAccountingActive) return (0, 0);
    uint256 earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault;
    uint256 principalAssets = epochStartVaultAssets + epochDepositedToVault;
    int256 netDelta = bufferedVaultDelta + int256(earnedAssets) - int256(principalAssets);
    if (netDelta > 0) {
      interest = uint256(netDelta);
    } else {
      loss = uint256(-netDelta);
    }
  }
