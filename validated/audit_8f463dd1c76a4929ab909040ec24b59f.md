### Title
`getTokenLargestAccounts` silently treats unparsable token accounts as zero balance, misreporting largest holders - (File: `rpc/src/rpc.rs`)

### Summary
The reported bug class is about ignoring a critical return value (`transfer`/`transferFrom` return value) rather than checking it, allowing the caller to proceed with an assumption that doesn't hold, leading to state that doesn't match reality. The closest reachable analog in this codebase is in `JsonRpcRequestProcessor::get_token_largest_accounts`, where the return value of `StateWithExtensions::<TokenAccount>::unpack(...)` is discarded via `.unwrap_or(0)` instead of being propagated/checked, causing accounts that fail to unpack to be silently reported as holding `0` tokens rather than being excluded or flagged as an error.

### Finding Description
In `rpc/src/rpc.rs`, `get_token_largest_accounts` iterates candidate token accounts filtered by mint and computes each account's balance for ranking: [1](#0-0) 

```
for (address, account) in self
    .get_filtered_spl_token_accounts_by_mint(...)
    .await?
{
    let amount = StateWithExtensions::<TokenAccount>::unpack(account.data())
        .map(|account| account.base.amount)
        .unwrap_or(0);
    ...
}
```

The `Result` returned by `StateWithExtensions::<TokenAccount>::unpack` is not checked/propagated with `?` — its `Err` branch is discarded and replaced with a hardcoded `0` via `.unwrap_or(0)`. This is directly analogous to the "transfer return value is ignored" bug class: a fallible operation's outcome is discarded, and the code proceeds as if the fallback value ("0", analogous to assuming `transfer` succeeded) were the ground truth, rather than surfacing the error or excluding the account from consideration.

Because `get_filtered_spl_token_accounts_by_mint` filters accounts only by `owner == token program id` and `mint` matching bytes at a fixed offset (it does not fully validate that the account unpacks as a valid `TokenAccount`, e.g., due to `token-2022` extensions/data-size or corruption), any account that passes the mint filter but fails `StateWithExtensions::unpack` (e.g., malformed data, unsupported extension layout, or an account resized/reallocated in a way inconsistent with the base `TokenAccount` struct) is included in the ranking with an assumed balance of 0.

### Impact Explanation
This causes `getTokenLargestAccounts`, an unprivileged read-only JSON-RPC method, to return incorrect account data to any client: an account holding a large balance can be silently misreported as holding zero tokens if its data fails to unpack cleanly, while a genuinely-zero-balance account could occupy a spot in the top-N list ahead of the real top holder. This matches the "wrong-slot/fork/account data returned" acceptance criterion for a query, since the RPC response returns fabricated (`0`) balance data instead of an error or the actual amount, with no way for downstream consumers (explorers, monitoring tools, other validators via inter-node RPC calls) to detect the misreporting.

The severity is data-integrity/correctness for an RPC-only computation (no consensus or fund-loss impact), consistent with the original external report being judged "Medium" severity (data/behavior discrepancy rather than a crash or fund loss).

### Likelihood Explanation
Likelihood is moderate: it requires an SPL Token / Token-2022 mint that has at least one account matching the mint's byte-prefix filter but whose account data fails `StateWithExtensions::<TokenAccount>::unpack` — e.g., because of a corrupted/partially-initialized token-2022 account, or a non-standard account layout that nonetheless matches the raw mint bytes at the expected offset. This is plausible for Token-2022 extension accounts with unusual state, and is triggerable with a single unprivileged `getTokenLargestAccounts` call — no elevated privileges, multiple calls, or race conditions are needed.

### Recommendation
Propagate the unpack error instead of silently defaulting to `0`:
- Use `?` (or a `try_fold`/`filter_map` that logs and skips) so that unparsable accounts are either excluded from ranking or the RPC call returns an internal error, rather than contributing a fabricated `0` balance.
- Alternatively, explicitly skip (continue) accounts that fail to unpack while emitting a debug/warn log, so operators can detect data corruption, and document that such accounts are excluded from the "largest accounts" computation rather than counted as zero.

### Proof of Concept
1. Create an SPL Token mint and mint a large balance into a token account whose underlying account data is subsequently truncated/corrupted (or use a Token-2022 mint/account combination whose extension layout makes `StateWithExtensions::<TokenAccount>::unpack` fail) while still passing the mint-prefix filter used by `get_filtered_spl_token_accounts_by_mint`.
2. Call the `getTokenLargestAccounts` RPC method for that mint from an unauthenticated client.
3. Observe that the corrupted/large-balance account is included in the response with `amount = 0` (or is silently omitted from the top-N in favor of lower-ranked legitimate accounts), instead of the RPC returning an error or the account's true balance — demonstrating that the ignored `unpack` `Result` leads to misreported account data to an unprivileged caller.
