### Title
`MultisigFactory::create` permanently locks the attached deposit when the target sub-account already exists, unlike its sibling factories - (`multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create()` batches `create_account()`, `deploy_contract()`, `transfer()` and `function_call()` into a single promise with no completion callback. If the target sub-account name is already taken (e.g. re-submitted transaction, accidental name collision, or a front-run by an unprivileged third party), the whole receipt fails atomically and the attached NEAR deposit is refunded to the *predecessor of the failed receipt* — the `MultisigFactory` contract itself — not to the original caller. Because `MultisigFactory` is a stateless struct with no owner/withdraw method, those funds become permanently unrecoverable.

### Finding Description
`MultisigFactory::create` issues one promise with `create_account().deploy_contract(CODE.to_vec()).transfer(env::attached_deposit()).function_call(...)` and returns it directly with no `.then(...)` callback: [1](#0-0) 

Compare this to `LockupFactory::create` and `StakingPoolFactory::create_staking_pool`, which both attach a callback (`on_lockup_create` / `on_staking_pool_create`) that checks `is_promise_success()` and explicitly refunds `attached_deposit` back to `predecessor_account_id` if the sub-account creation fails: [2](#0-1) [3](#0-2) 

`StakingPoolFactory` additionally guards against duplicate names up front with `assert!(self.staking_pool_account_ids.insert(&staking_pool_account_id), ...)`: [4](#0-3) 

`MultisigFactory` has neither the pre-check nor the callback — it holds no persisted state at all: [5](#0-4) 

If the target `account_id = "{name}.{multisig-factory}"` already exists on-chain, the `create_account()` action inside the batched receipt fails, which fails the whole receipt atomically (including the `transfer` action). Under NEAR's protocol semantics, the deposit that failed to transfer is refunded to the account that originated the failed receipt, i.e. the `MultisigFactory` contract's own balance — not back to the caller who attached the deposit. Since the contract exposes no getter/withdraw method, that NEAR is now stuck in the factory's balance indefinitely.

The custody binding broken: **value debited (caller's attached deposit) versus value delivered (neither to the intended new multisig account nor refunded to the caller)**.

### Impact Explanation
Attached NEAR deposits sent to `create()` can be permanently frozen with no possible recovery path once a name collision occurs, matching the Critical impact tier ("funds permanently frozen"). This is directly analogous to the underlying bug class in the external report: the code hard-fails on an "already deployed"/name-collision condition instead of gracefully handling it, and — unlike its sibling factories in the same repository — provides no fallback to return value to the rightful owner.

### Likelihood Explanation
No privileged role is required. The collision can occur from:
- A resubmitted/duplicate `create` transaction with the same `name`.
- Two unrelated callers independently choosing the same `name` prefix.
- Any account with that literal `name.multisig-factory-account` already existing on NEAR for unrelated reasons.

Given `MultisigFactory` performs no uniqueness check before issuing the promise (unlike `StakingPoolFactory`), this is easily triggered in normal operation, not just via an adversarial setup.

### Recommendation
Add a completion callback to `MultisigFactory::create`, mirroring `LockupFactory::on_lockup_create` / `StakingPoolFactory::on_staking_pool_create`: check `is_promise_success()` and, on failure, `Promise::new(predecessor_account_id).transfer(attached_deposit)` to refund the caller. Optionally also track requested names to fail fast with a clear assertion before attempting sub-account creation, avoiding the wasted batched receipt entirely.

### Proof of Concept
1. Deploy `MultisigFactory` as `mf.testnet`.
2. Attacker (or an accidental duplicate call) creates account `alice.mf.testnet` directly (e.g. via a plain `CreateAccount` transaction) before Alice's call lands.
3. Alice calls `mf.testnet.create(name="alice", members=[...], num_confirmations=...)` with an attached deposit of `X` NEAR.
4. `create_account()` for `alice.mf.testnet` fails because the account already exists → the entire batched receipt (`create_account`, `deploy_contract`, `transfer(X)`, `function_call`) fails.
5. The `X` NEAR refunds to `mf.testnet` (the factory contract), not to Alice.
6. `MultisigFactory` has no method to withdraw or query this balance — the `X` NEAR is permanently stuck in the factory contract.

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }

    /// Callback after a staking pool was created.
    /// Returns the promise to whitelist the staking pool contract if the pool creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",

                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
