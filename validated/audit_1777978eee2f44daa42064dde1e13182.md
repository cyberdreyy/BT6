### Title
Reorg-permit self-whitelisting in `check_parent_tenure_choice` lets a single miner proposal void a signer's own equivocation guard - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides, on the basis of a *single* miner's block proposal, whether a tenure reorg is legitimate, and — if so — permanently records the reorged tenure as `superseded` via `record_superseded_tenure`/`mark_tenure_superseded`. This record is later consumed by `Signer::reorg_permit_stands` to *exclude* the signer's own previously-placed signature from the conflict guard in `handle_block_pre_commit`. The legitimacy test only inspects the network-observed `GloballyAccepted` count for the reorged tenure, not whether the local signer (or any subset of the signer set below threshold) already put a signature on a competing block there. A miner can therefore steer this signer into self-whitelisting away its own equivocation guard and get it to sign two conflicting blocks at overlapping heights.

### Finding Description
`check_parent_tenure_choice` ( [1](#0-0) ) is invoked whenever a miner's tenure choice does not build off the prior sortition — a condition entirely controlled by the miner's block-commit / tenure-change payload, requiring no other signer's cooperation. For each reorged tenure it checks: [2](#0-1) 

Only `globally_accepted_blocks` (from `get_globally_accepted_block_count_in_tenure`) gates whether the reorg is disallowed for "already mined blocks," and it only rejects when `> 1`. It says nothing about whether *this* signer, or a still-unaggregated majority of the signer set, has already placed a signature on a block in that tenure that is `LocallyAccepted`/`PreCommitted` but not yet `GloballyAccepted` (global acceptance is only recorded once the node itself reports the chain tip advanced, per `docs/signer-flows.md:367-372,380-383`). If the reorged tenure produced its first block "close enough" to the next sortition (`first_proposal_burn_block_timing`), the reorg is sanctioned even though a network-wide (but not yet locally-observed) 70%-signature threshold could already exist for that block: [3](#0-2) 

Once sanctioned, every reorged tenure — including one this signer already signed — is recorded superseded: [4](#0-3) 

That record is exactly the self-whitelist: it is written by this signer, about this signer's own conflict list, triggered by a single non-majority actor (the miner), and it is later trusted unconditionally by `reorg_permit_stands`/`conflict_still_blocks` to strip that tenure's signed block out of the conflict set used in `handle_block_pre_commit`: [5](#0-4) [6](#0-5) 

The doc itself states the design intent plainly — "so its own signature over what they built does not then block the replacement it just permitted" (`docs/signer-flows.md:496-511`) — but the legitimacy test that authorizes this self-exemption is keyed only to node-observed `GloballyAccepted` state, which is a laggy, node-side signal, not to whether *a* signature (ours or others', below threshold) already exists on the reorged block. Because a signature is explicitly treated elsewhere in this codebase as "a bearer instrument… that can still be aggregated toward the 70% threshold if rejecting/pending signers change their minds" (`docs/signer-flows.md:513-518`, `stacks-signer/src/signerdb.rs:4140-4147`), voiding the conflict guard here breaks the very equivocation invariant that guard exists to protect.

### Impact Explanation
If exploited, this signer ends up placing valid signatures over two blocks that conflict at the same/overlapping chain height — one it signed before the "permit" was minted, and one it signs afterward via the excluded-conflict path in `handle_block_pre_commit`. Because signatures remain aggregable bearer instruments (not revoked by later local state changes), both blocks could independently accumulate enough weight from the rest of the signer set to reach the 70% global-acceptance threshold, i.e., a rejection/consensus outcome recount is not required — this is a genuine equivocation by one signer across two conflicting blocks. This is a Critical-class break of the "one signature per height/tenure" equality that underlies fork-choice safety for the signer set.

### Likelihood Explanation
Triggering the miner-controlled precondition (tenure not building off `prior_sortition`, with the reorged tenure's first block proposed close to the sortition boundary) requires only a single miner acting alone — no majority of signers, no signer key, no auth_token. The only additional condition is a timing race between when the local signer observes global acceptance (node-dependent) versus network-wide off-chain signature aggregation, which is a plausible operational window (mixed-version fleets, node lag, or a signer restart resetting its view of global acceptance) rather than an artificial constraint.

### Recommendation
Extend the legitimacy check in `check_parent_tenure_choice` (and the data it uses to gate `record_superseded_tenure`) to also block the reorg permit whenever *this* signer (or, if obtainable, any known partial signature-weight tally) has placed a signature (`signed_self`/`signed_group` set, i.e. `BlockState::LocallyAccepted` or higher) over a block in the tenure being reorged — not just when the node has marked it `GloballyAccepted`. Equivalently, `reorg_permit_stands`/`conflict_still_blocks` should refuse to exclude a conflict that this signer personally signed, regardless of any recorded permit, since a self-issued permit must never override the signer's own non-equivocation guarantee.

### Proof of Concept
1. Signer A validates and signs (locally accepts) block `B1` in tenure `T1` at height `h`, proposed shortly before a new sortition. `T1` has zero `GloballyAccepted` blocks recorded locally (node hasn't yet observed threshold consensus, even though most of the signer set may already have signed `B1` off-chain).
2. The next miner's sortition proposes a competing tenure `T2` whose tenure-change does *not* build off `T1` (a reorg), with a block `B2` at height `h`.
3. `check_parent_tenure_choice` evaluates `T1`: `globally_accepted_blocks == 0` (≤1), and `B1`'s `approved_time` was close enough to the sortition boundary to satisfy `first_proposal_burn_block_timing` ⇒ reorg permitted, `T1` marked `superseded`.
4. `B2` reaches the pre-commit threshold; `handle_block_pre_commit` calls `get_signed_conflicts`, finds `B1` as a conflict, but `reorg_permit_stands` returns `true` (the permitting sortition for `T2` is canonical) ⇒ conflict excluded ⇒ Signer A signs `B2`.
5. Signer A has now signed both `B1` and `B2`, conflicting blocks at the same height `h`; if the rest of the signer set's earlier signatures on `B1` (already >70% off-chain) surface/aggregate, `B1` reaches global consensus too, alongside `B2`'s independent threshold — an equivocation by Signer A across two conflicting blocks.

    /// Whether a reorg permit recorded for this conflict's tenure still stands.
    ///
    /// `check_parent_tenure_choice` records a permit when the reorg-timing rules sanction a
    /// later tenure replacing what the conflict's tenure built (see
    /// [`SignerDb::mark_tenure_superseded`]). A standing permit excludes the conflict entirely:
    /// our signature must not stand in the way of a replacement we sanctioned. But the permit
    /// is only as alive as the sortition it was granted to: if a burnchain fork orphaned the
    /// permitting sortition, the reorg we sanctioned can no longer happen, and the record must
    /// not keep suppressing the conflict.
    ///
    /// A false 404 here (e.g. from a node still catching up) only restores a conflict the
    /// permit could have excluded, which at worst delays the replacement, so unlike
    /// `conflict_still_blocks` no tip-height guard is needed. A node error voids the permit for
    /// the same reason: blocking is the direction that can be taken back.
    fn reorg_permit_stands(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
    ) -> bool {
        let Some(superseded_by) = &conflict.superseded_by else {
            return false;
        };
        match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
            Ok(_) => true,
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                info!("{self}: The tenure we permitted to reorg a conflicting block's tenure was itself orphaned by a burnchain fork. The permit no longer excludes the conflict.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                    "superseded_by_burn_block_hash" => %superseded_by.burn_block_hash,
                );
                false
            }
            Err(e) => {
                warn!("{self}: Failed to check whether the sortition that permitted a reorg is still canonical: {e:?}. Treating the permit as void.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                );
                false
            }
        }

        // only while the sortition the permit was granted to is still canonical
        // (`check_parent_tenure_choice` records the permit, `reorg_permit_stands` re-derives
        // its validity from the node); every other question about whether a conflict is
        // still live is derived from the node in `conflict_still_blocks`.
        //
        // Unlike the chainstate check above, a refusal here is "for now" rather than a
        // broadcast rejection: a later pre-commit re-evaluation may still sign the block once
        // the conflicting signature has gone stale.
        let conflicts = match self
            .signer_db
            .get_signed_conflicts(block_info.block.header.chain_length, &block_hash)
        {
            Ok(conflicts) => conflicts,
            Err(e) => {
                warn!("{self}: Failed to query the signed blocks. Refusing to sign block {block_hash}: {e:?}");
                return;
            }
        };

            self.proposal_config
                .tenure_last_block_proposal_timeout
                .as_secs(),

        // chain: see `conflict_still_blocks`, which asks the node whether it is. Check

        // and `conflict_still_blocks` each query the node, so stale conflicts cost no

                "conflicting_consensus_hash" => %conflict.consensus_hash,
            );
            return;
