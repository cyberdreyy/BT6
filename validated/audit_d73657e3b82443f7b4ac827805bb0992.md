## Title
v1 (pre-global-state) chainstate's tenure-duplicate check evaluates a different, weaker predicate (`get_last_globally_accepted_block`) than the actual signing-time truth (`signed_self`/`signed_group`), letting a checker-time analysis miss an already-signed sibling that the runtime state already contains - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` (v1 chainstate, `stacks-signer/src/chainstate/v1.rs:461-519`) rejects a proposed tenure-start block as `DuplicateBlockFound` only if `SignerDb::get_last_globally_accepted_block` returns a block in the tenure. The v2 equivalent, `GlobalStateView::validate_tenure_change_payload` (`stacks-signer/src/chainstate/v2.rs:306-359`), was patched to use `get_last_signed_block`, which also matches `LocallyAccepted`/blocks the signer itself has put a signature on but that have not yet reached group consensus. This asymmetry is explicitly documented as a fixed regression for v2 (test `check_tenure_change_rejects_when_locally_accepted_block_exists`, `stacks-signer/src/chainstate/tests/v2.rs:748-850`, whose comment states "previously, the check used `get_last_globally_accepted_block`, which would miss blocks in `LocallyAccepted`... state") but the same fix was never applied to v1.

### Finding Description
The check-time predicate ("has a block already been accepted in this tenure?") is computed two different ways depending on which chainstate implementation is active:

- v1: `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` — only true once the block reaches the 70% *group* signature threshold (`BlockState::GloballyAccepted`). [1](#0-0) 

- v2: `signer_db.get_last_signed_block(&block.header.consensus_hash)` — true once the signer's own `signed_self` OR the group's `signed_group` timestamp is set, i.e. as soon as this signer has *locally* signed a block in the tenure. [2](#0-1) 

The v2 test suite proves this matters in practice: a block that is only `LocallyAccepted` (signer has already put a signature on it, but the network as a whole has not yet reached the 70% threshold) is exactly the state where the old (v1-style) query silently returns `None`, and `validate_tenure_change_payload` therefore treats a competing sibling tenure-start block as "not a duplicate," letting `check_proposal` continue toward submission/validation instead of failing fast with `DuplicateBlockFound`. [3](#0-2) 

This is the direct analog of the reported bug class: one code path (the "allowlist"/analysis stage — here, the proposal-time duplicate-tenure-start check) uses a narrower/looser predicate than the one that actually reflects the signer's committed state (whether *this signer* has already signed something in the tenure). The mismatch is exploitable by structuring the timing of proposals exactly the way the CVE structures its payload: get the signer to lock in a signature on block A while it is only `LocallyAccepted` (not yet `GloballyAccepted`), then immediately propose sibling B for the same tenure. Under v1, `check_proposal`'s `validate_tenure_change_payload` no longer sees A (because it queries only globally-accepted state) and lets B proceed past the proposal-time gate that exists specifically to enforce the one-tenure-start-per-tenure invariant.

Whether this can be escalated all the way to a second signature depends on the independent pre-commit-time backstop in `stacks-signer/src/v0/signer.rs` (`handle_block_pre_commit`, `get_signed_conflicts`/`conflict_still_blocks`, lines ~1383-1457), which is chainstate-version-agnostic and re-derives conflicts from `signed_self`/`signed_group` directly rather than through the v1/v2 abstraction: [4](#0-3) 
That backstop is documented as existing specifically because "the `DuplicateBlockFound` check that would catch a second block in the same tenure lives in `check_proposal` and runs only at proposal arrival, never again," which is a tacit admission that the proposal-time gate (the one v1 weakens) is not purely redundant — it is the fast, first-line defense, and the backstop is a secondary, timing-and-freshness-dependent safety net (it only blocks while the earlier signature is "fresh," per `tenure_last_block_proposal_timeout`, and it stops blocking once conflicts go stale or the tenure's canonical tip has not yet reached the conflicting height). [5](#0-4) 

### Impact Explanation
If v1 remains the active chainstate path for any signer in the network (pre-global-state-activation signers, or any deployment still running the pre-global-state protocol version), this weakens the check that is supposed to reject a second tenure-start proposal for a tenure the signer has already accepted, at exactly the layer designed to catch it early (proposal time). It degrades the "one signed tenure-start block per tenure" invariant from a always-checked property to a property that depends on freshness timing and on the pre-commit backstop firing correctly — i.e., it removes one of the two independent layers of the same defense, increasing the risk that a byzantine or buggy/slow miner can get a signer to place a second signature over a conflicting tenure-start sibling once the first signature's freshness window elapses or under any edge case the backstop does not cover (e.g., timing races addressed by the "async sibling validation" test suite, which cover the backstop's known blind spots for the *validation-timing* gap, not this *globally-vs-locally-accepted* gap).

### Likelihood Explanation
Reaching `LocallyAccepted`-but-not-`GloballyAccepted` state is routine, not exotic: any tenure-start block for which the local signer alone reaches its own signature but the rest of the set is slow, offline, or split will sit in this state, and a single one-slot miner or its stand-in can immediately re-propose a sibling for the same tenure. No majority collusion or key compromise is required to trigger the mismatch itself — it is a pure timing/proposal-structuring exercise, matching the "one-slot miner (plus gossip)" threat model.

### Recommendation
Change `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, mirroring the v2 fix, so that the proposal-time `DuplicateBlockFound` gate is consistent with the network's actual committed (signed) state regardless of which chainstate protocol version is active. Add a v1-equivalent of the regression test `check_tenure_change_rejects_when_locally_accepted_block_exists` to lock in the fix.

### Proof of Concept
1. Configure a signer set running the pre-global-state (v1 `SortitionsView`) proposal-check path.
2. Miner proposes tenure-start block A. Enough signers (but not the full weighted set) sign quickly so that, from this particular signer's perspective, A becomes `LocallyAccepted` (`signed_self` set) but the network-wide 70% weight has not yet been reached, so A is not `GloballyAccepted`.
3. Miner (or an equivalent byzantine actor) immediately proposes a conflicting sibling tenure-start block B for the same tenure (same `consensus_hash`, different transactions/parent choice).
4. On this signer, `check_proposal` → `validate_tenure_change_payload` calls `get_last_globally_accepted_block(consensus_hash)`, which returns `None` (A is only locally accepted), so the `DuplicateBlockFound` rejection at `stacks-signer/src/chainstate/v1.rs:510-518` never fires, and B is treated as a fresh, non-duplicate proposal and passed on to node validation and pre-commit.
5. Whether B is ultimately signed then depends entirely on the pre-commit-stage freshness/backstop timing (`conflicts.iter().find(... last_endorsed > freshness_cutoff ...)` in `stacks-signer/src/v0/signer.rs:1403-1421`) rather than on the proposal-time invariant that is supposed to guarantee this can never happen — demonstrating that the v1 path has lost its primary, timing-independent defense against signing two tenure-start siblings in one tenure.

**Note on confidence:** I could not fully verify from the index whether v1 (`SortitionsView`) is still reachable in the current production protocol-version negotiation logic (`stacks-signer/src/v0/signer.rs` mode-selection code, `check_block_against_local_state` vs `check_block_against_global_state`), since I was not able to trace the exact protocol-version gating before running out of turns. If v1 is fully retired in the currently deployed protocol version, this finding would be latent/dead-code rather than exploitable; if v1 is still reachable during any transition/mixed-version period, the finding stands as described. I recommend confirming this via a Devin session with full repo access if precise reachability matters for triage.

/// (but not globally-accepted) block already exists in the same tenure.
///
/// This is a regression test: previously, the check used
/// `get_last_globally_accepted_block`, which would miss blocks in
/// `LocallyAccepted` or `PreCommitted` state and incorrectly allow
/// a duplicate tenure change.
#[test]
fn check_tenure_change_rejects_when_locally_accepted_block_exists() {
    let MockServerClient {
        server,
        client: stacks_client,
        config: _,
    } = MockServerClient::new();
    let rand_int = server.local_addr().unwrap().port();

    let (_stacks_client, mut signer_db, block_sk, mut block, cur_sortition, _, sortitions_view) =
        setup_test_environment(&format!("{}_{rand_int}", function_name!()));

    // Set up the block in the current tenure
    block.header.consensus_hash = cur_sortition.data.consensus_hash.clone();
    let parent_block_header = make_parent_header_meta(&block_sk, &mut block);
    let response = crate::client::tests::build_get_tenure_tip_response(&parent_block_header);

    // Insert a locally-accepted block in the same tenure (same consensus_hash).
    // This simulates a miner's first tenure-start block that the signer has
    // locally accepted but that hasn't yet gathered enough signatures to be
    // globally accepted. In practice this block would contain a tenure-change
    // and coinbase tx, but we omit them here because `get_last_accepted_block`
    // only queries by consensus_hash and block state — the block's transactions
    // are irrelevant to the duplicate check.
    let existing_block_proposal = BlockProposal {
        block: NakamotoBlock::new(
            NakamotoBlockHeader {
                version: 1,
                chain_length: 10,
                burn_spent: 10,
                consensus_hash: cur_sortition.data.consensus_hash.clone(),
                parent_block_id: StacksBlockId([0; 32]),
                tx_merkle_root: Sha512Trunc256Sum([0; 32]),
                state_index_root: TrieHash([0; 32]),
                timestamp: 11,
                miner_signature: MessageSignature::empty(),
                signer_signature: vec![],
                pox_treatment: BitVec::ones(1).unwrap(),
                problematic_txs: vec![],
            },
            vec![],
        ),
        burn_height: 2,
        reward_cycle: 1,
        block_proposal_data: BlockProposalData::empty(),
    };
    let mut existing_block_info = BlockInfo::from(existing_block_proposal);
    existing_block_info.mark_locally_accepted(false).unwrap();
    signer_db.insert_block(&existing_block_info).unwrap();

    // Now build a *second* tenure-start block proposal for the same tenure.
    // This simulates the miner attempting to replace their first block (e.g.,
    // with different transactions). The tenure change tx must have
    // cause=BlockFound with a coinbase to be recognized as a tenure-start block.
    let tenure_change_payload = TenureChangePayload {
        tenure_consensus_hash: cur_sortition.data.consensus_hash.clone(),
        prev_tenure_consensus_hash: cur_sortition.data.parent_tenure_id.clone(),
        burn_view_consensus_hash: cur_sortition.data.consensus_hash.clone(),
        previous_tenure_end: block.header.parent_block_id.clone(),
        previous_tenure_blocks: 1,
        cause: TenureChangeCause::BlockFound,
        pubkey_hash: Hash160::from_node_public_key(&StacksPublicKey::from_private(&block_sk)),
    };
    let tenure_change_tx = make_tenure_change_tx(tenure_change_payload);
    let coinbase_tx = StacksTransaction::new(
        TransactionVersion::Testnet,
        TransactionAuth::Standard(TransactionSpendingCondition::new_initial_sighash()),
        TransactionPayload::Coinbase(CoinbasePayload([0; 32]), None, Some(VRFProof::empty())),
    );
    *block.executed_and_skipped_txs_mut() = vec![tenure_change_tx, coinbase_tx];
    block.header.sign_miner(&block_sk).unwrap();

    let exit_flag = Arc::new(AtomicBool::new(false));
    let moved_exit_flag = exit_flag.clone();

    let serve = std::thread::spawn(move || {
        crate::client::tests::write_response_nonblockinig(
            &server,
            response.as_bytes(),
            moved_exit_flag,
        );
    });

    let result = sortitions_view.check_proposal(&stacks_client, &mut signer_db, &block);

    exit_flag.store(true, Ordering::SeqCst);
    serve.join().unwrap();

    // The proposal should be rejected because there's already a locally-accepted
    // block in this tenure. Before the fix, this would have incorrectly passed
    // because get_last_globally_accepted_block would not find the locally-accepted block.
    assert!(
        matches!(result, Err(RejectReason::DuplicateBlockFound)),
        "Expected DuplicateBlockFound rejection when a locally-accepted block exists in the tenure, got: {result:?}"
    );
}

Two things belong to the proposal path only and are **not** re-run at validate-ok
or at signing:

- `validate_tenure_change_payload` rejects with `DuplicateBlockFound` when we
  have already accepted a block in the tenure a tenure-change block is starting.
  v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1
  counts only globally accepted ones (`get_last_globally_accepted_block`).
- the v2 `check_proposal` wrapper checks miner pubkey hash, consensus hash, the
  pox bitvec, and tenure-extend rules before delegating here.

Because the duplicate check never runs again, a block that crosses the pre-commit
threshold long after it was proposed relies on section 5's own-tenure conflict
guard to cover the same ground.
