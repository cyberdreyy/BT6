### Title
Dust APR=0 withdraw request permanently reverts `stopEpoch` once APR is restored, freezing the vault - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

Like the ModSecurity DoS, which only fires when two features combine (`application/json` + a `sanitiseMatchedBytes` rule), `IdleCreditVault` has a denial of service that only fires when two states combine: a non-zero `apr0TotalPrincipal` bucket and a non-zero `unscaledApr`. `prepareStopEpochWithApr0` reverts `NotAllowed` whenever both hold, and it is called on every `stopEpoch`/`stopEpochWithDuration` path by `IdleCDOEpochVariant`. Any unprivileged lender can create the `apr0TotalPrincipal` side with a dust-sized withdraw request during an APR=0 epoch; the moment the (honest) manager restores a non-zero APR, every epoch stop reverts and the vault cannot progress.

### Finding Description

The vulnerable sequence:

1. Vault is in an APR=0 regime (`unscaledApr == 0`). Epoch N is running or in buffer.
2. An unprivileged KYC-passing lender deposits a dust amount and calls `requestWithdraw` on the CDO. Because `unscaledApr == 0`, the strategy routes the request through `_requestWithdrawApr0`, which sets `apr0Users[user].principal`, `apr0Users[user].principalEpoch = epochNumber`, and adds the amount to the global `apr0TotalPrincipal` (contracts/strategies/idle/IdleCreditVault.sol:285-286, 567-577).
3. The manager (honest, per threat model) later restores a normal APR via `setAprsWithBuffer`/`setApr`, setting `unscaledApr != 0` (IdleCreditVault.sol:217-235).
4. Every subsequent `stopEpoch` call flows into `prepareStopEpochWithApr0`, which hits the guard:
   ```solidity
   if (unscaledApr != 0) {
     revert NotAllowed();
   }
   ```
   (IdleCreditVault.sol:506-508), because `apr0TotalPrincipal != 0` skipped the fast-path return at line 502.

There is no way to clear `apr0TotalPrincipal` while APR is non-zero:
- It is only reset inside `prepareStopEpochWithApr0` (line 540), which is the function that reverts.
- `_settleApr0` only migrates the per-user bucket during `claimWithdrawRequest`, and only after `stopEpoch` has already bumped `epochNumber` (lines 553-555) — a circular dependency.
- `requestWithdraw` cannot route the dust request into the normal `withdrawsRequests` bucket while `apr0Users[user].principalEpoch` points at a live epoch either, since a new request while `unscaledApr != 0` goes to the normal bucket but leaves the stale APR0 principal in place.

The user request is tiny (1 wei of underlying suffices — `requestWithdraw` has no minimum beyond `_amount == 0`, line 246), so attack cost is negligible.

### Impact Explanation

While `apr0TotalPrincipal != 0` and `unscaledApr != 0`, `stopEpoch`, `stopEpochWithDuration` and any prefunded variant stop path all revert. Consequences until the configuration is unwound:

- No epoch can end, so `epochNumber` never advances: all normal withdraw claims are frozen behind the `epochNumber <= lastWithdrawRequest` gate in `_claimFundedWithdrawRequest` (line 326), and all APR0 claims freeze in `_settleApr0` (line 553).
- The loss-adjusted claim gate in `requestWithdraw` (lines 263-270) compounds it: a user whose receipt epoch gets a `lossRecoveryPriceByEpoch` entry can never re-request, and can never claim because claims need an epoch boundary that can no longer be reached.
- Interest accounting is frozen at the old epoch — borrower repayment, fee accrual, and instant-withdraw funding are all stalled for the entire freeze duration.

Recovery requires the manager to set `unscaledApr` back to 0, run a full `stopEpoch` at zero interest (depriving all LPs of that epoch's yield and effectively forcing `apr0RateByEpoch` to record a zero rate), and only then restore the APR. The attacker can repeat the griefing cycle: during each forced APR=0 window they open another dust APR0 request, forcing the vault to stay at APR=0 to ever stop epochs again. This is a quantifiable temporary freezing of all vault funds plus forced loss of interest for at least one epoch per cycle, caused by an unprivileged user.

### Likelihood Explanation

- Attacker cost: one dust deposit + one `requestWithdraw` while `unscaledApr == 0`; no privileged role needed (KYC-passing lender is in the allowed set).
- Trigger: APR=0 pools exist precisely to offer zero-yield epochs (the APR0 flow is a first-class feature with dedicated accounting), and restoring APR afterwards is a routine honest manager action, not an edge case.
- The revert is unconditional once both states hold; there is no guard, cap, or escape hatch in `prepareStopEpochWithApr0`, `requestWithdraw`, or `_settleApr0` that resolves it under non-zero APR.
- Caveat: I could not fully verify whether `IdleCDOEpochVariant.stopEpoch` has an alternate path that bypasses `prepareStopEpochWithApr0` when `apr0TotalPrincipal` is stale-only (the grep confirmed the 8 call-site matches exist in that file but line-level reads were not available in the remaining iterations). If the CDO gates the call on `apr0TotalPrincipal != 0` itself, the same DoS still holds because the bucket cannot be cleared from outside.

### Recommendation

Do not revert on the `unscaledApr != 0` + `apr0TotalPrincipal != 0` combination. Options:

1. In `prepareStopEpochWithApr0`, when `unscaledApr != 0`, treat the APR0 bucket as settling at zero rate: write `apr0RateByEpoch[epochNumber] = 0` (or skip writing), clear `apr0TotalPrincipal`, and return unadjusted interest/fees. Users simply receive their principal without APR0 interest — the same outcome as a zero-interest epoch.
2. Alternatively, allow `requestWithdraw`/`claimWithdrawRequest` to migrate a stale `apr0Users[user].principal` into `settledPrincipal` whenever `unscaledApr != 0` at the start of a new epoch, so the global bucket can be drained without waiting for a stop.
3. At minimum, make the revert reachable only while the APR0 request's own `principalEpoch` is still the current epoch, so a restored APR never bricks a request from a previous epoch.

### Proof of Concept

Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testApr0DustRequestBlocksStopAfterAprRestore() external {
    // APR = 0 regime
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // unscaledApr = 0

    // honest LP deposits so the vault has funds
    uint256 amount = 100_000 * ONE_SCALE;
    _depositWithUser(makeAddr('lp'), amount, false);

    _startEpochAndCheckPrices(0);

    // attacker: KYC-passing lender, dust deposit + withdraw request in APR0 window
    address attacker = makeAddr('apr0-griefer');
    _depositWithUser(attacker, 1 * ONE_SCALE, false);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    _stopEpochAndCheckPrices(0, 0, _expectedFundsEndEpoch());

    // manager legitimately restores APR for the next epoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, initialProvidedApr); // unscaledApr != 0
    _startEpochAndCheckPrices(1);

    // every stopEpoch now reverts -> epoch frozen, all claims frozen
    vm.warp(block.timestamp + cdoEpoch.epochDuration() + cdoEpoch.bufferPeriod());
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    vm.prank(manager);
    cdoEpoch.stopEpoch(0);

    // attacker cycles: setting APR back to 0 unblocks stop,
    // but a new dust request in the next APR0 window re-bricks the vault.
}
```

If `stopEpoch` internally calls `prepareStopEpochWithApr0` unconditionally (consistent with the 8 references in `IdleCDOEpochVariant.sol`), the `expectRevert` confirms the freeze; both users' pending claims remain unclaimable until `unscaledApr` is forced back to 0.
