### Title
Missing DON subscription/allowlist enforcement lets any signer trigger a configured DON's capability execution via the legacy gateway path - ([File: core/services/gateway/api/message.go])

### Summary
`Message.Validate()` in `core/services/gateway/api/message.go` only checks length/null-suffix formatting of `DonId` and verifies the ECDSA signature over the message, it never checks whether the recovered signer is a subscriber/allowlisted member for that `DonId`. `gateway.ProcessRequest` in `core/services/gateway/gateway.go` uses `msg.Body.DonId` verbatim as `handlerKey` to look up a live `handlers.Handler` and forwards the request to `handler.HandleLegacyUserMessage`, and `capabilities/handler.go`'s `HandleLegacyUserMessage` fans the request out to every member of `donConfig.Members` with an explicit `// TODO: apply allowlist and rate-limiting here` comment marking the missing check.

### Finding Description
The attacker-controlled request enters via `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-262`). When the JSON-RPC request contains a non-empty `msg.Body.DonId`, the gateway treats it as a "legacy request," calls `msg.Validate()`, and on success sets `handlerKey := msg.Body.DonId`, looking the value up directly in `g.handlers` map: [1](#0-0) 

`Message.Validate()` (`core/services/gateway/api/message.go:54-88`) performs only structural checks — signature hex length, message ID/method/DonId length and null-suffix checks, receiver length — and then recovers the signer address via `ExtractSigner()` and records it as `Body.Sender`. There is no check that the recovered `Sender` is authorized/subscribed for the given `DonId`: [2](#0-1) 

Once routed, `capabilities/handler.go`'s `HandleLegacyUserMessage` validates payload shape (JSON decode, timestamp freshness) but explicitly skips authorization at the line marked `// TODO: apply allowlist and rate-limiting here`, then unconditionally fans the message to every configured node in `h.donConfig.Members`: [3](#0-2) 

Because any ECDSA keypair can produce a valid signature, and `DonId` is treated as a routing key rather than an authorization scope, an attacker who knows (or brute-forces/enumerates) any active, correctly-configured `DonId` string can submit a signed legacy message that the gateway will accept and forward to that DON's full node membership — regardless of whether the attacker's address has any subscription, allowlist entry, or prior relationship with that DON. This is corroborated by the existing unit test suite (`handler_test.go`) which shows `HandleLegacyUserMessage` succeeding purely on signature + payload validity with a `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated` comment confirming sender validation is not yet implemented: [4](#0-3) 

### Impact Explanation
This allows unauthorized resource consumption: an unauthenticated/non-subscribed attacker can force a target DON's node set to expend compute processing capability-trigger requests (e.g., dispatching messages to all `donConfig.Members`, and further downstream capability execution) purely by knowing a valid `DonId`. This matches the "unauthorized DON resource consumption / capability execution abuse by non-subscribed senders" impact class — a denial-of-service / resource-abuse vector against DON operators and legitimate subscribers, not an authentication or fund-movement bypass but a genuine authorization-exactness gap (DON-ID binding checked for well-formedness only, not membership).

### Likelihood Explanation
Preconditions are minimal: the attacker needs no credentials beyond generating any ECDSA keypair, and knowledge of a real `DonId` string (these can be public/known from documentation, on-chain config, or observed traffic). No operator/admin access is required. The exploit is fully reproducible via a single signed JSON-RPC request to the gateway's public HTTP endpoint.

### Recommendation
Add a subscription/allowlist check in the legacy-message path before dispatching to `donConfig.Members`: after `msg.Validate()` recovers `msg.Body.Sender`, verify that the sender is present in an allowlist/subscription registry scoped to `msg.Body.DonId` (mirroring the intent of the `// TODO: apply allowlist and rate-limiting here` comment in `capabilities/handler.go`), and reject with an authorization error otherwise. This check should occur both in `gateway.ProcessRequest`'s legacy branch and/or centrally in `Handler.HandleLegacyUserMessage` before any fan-out to DON members.

### Proof of Concept
1. In `core/services/gateway/handlers/capabilities/handler_test.go`, extend `setupHandler` test fixtures to configure a DON (`donID := "workflow_don_1"`) with a known allowlist of member/sender addresses that does **not** include a freshly generated key.
2. Generate a new unrelated `ecdsa.PrivateKey` not in `nodes` and not part of any subscription config.
3. Build a `triggerRequest` message using this attacker key with `DonId: "workflow_don_1"` (an active, real DON ID in the test DON config).
4. Call `handler.HandleLegacyUserMessage(ctx, msg, cb)` directly (mirroring `TestHandlerReceiveHTTPMessageFromClient`) and assert that `don.SendToNode` is invoked for DON members — i.e., the request is fanned out — despite the sender not belonging to any subscriber/allowlist for that DON.
5. Expected (vulnerable) result: `err == nil` and `don.EXPECT().SendToNode(...)` is called for all `donConfig.Members`, confirming the request was processed and resources consumed without any authorization check tied to `DonId` subscription.
6. After the fix, the same test should instead assert an authorization error response via `callback.SendResponse` with an appropriate error code, and `don.SendToNode` should never be called.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
