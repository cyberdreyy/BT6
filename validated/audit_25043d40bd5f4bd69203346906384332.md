## Title
Unbounded allocation via unbounded `Vec<AccountChange>` decode in EIP-8130 transactions (CWE-770) - (File: `crates/common/consensus/src/transaction/eip8130/tx.rs`)

### Summary
`TxEip8130::rlp_decode_fields` decodes the `calls` field through a custom `decode_calls` helper that explicitly caps the number of items at `Eip8130Constants::MAX_CALL_PHASES_PER_TX` (1,024) to close a pre-authentication allocation-amplification vector, but the sibling `account_changes` field on the very same struct is decoded with the generic, unbounded `Decodable::decode(buf)?` for `Vec<AccountChange>`, with no equivalent count cap. [1](#0-0) 

### Finding Description
`TxEip8130` is the EIP-8130 account-abstraction transaction body. Its RLP field decoder is:

```rust
pub fn rlp_decode_fields(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
    Ok(Self {
        ...
        account_changes: Decodable::decode(buf)?,
        calls: Self::decode_calls(buf)?,
        ...
    })
}
``` [2](#0-1) 

`decode_calls` explicitly documents and enforces the count bound this class of bug requires:
```rust
fn decode_calls(buf: &mut &[u8]) -> alloy_rlp::Result<Vec<Vec<Call>>> {
    ...
    while !payload.is_empty() {
        if phases.len() >= Eip8130Constants::MAX_CALL_PHASES_PER_TX {
            return Err(alloy_rlp::Error::Custom("too many EIP-8130 call phases"));
        }
        phases.push(Vec::<Call>::decode(&mut payload)?);
    }
    ...
}
``` [3](#0-2) 

with the corresponding constant and rationale defined as:
```rust
pub const MAX_CALL_PHASES_PER_TX: usize = 1_024;
``` [4](#0-3) 

`account_changes`, however, goes straight through `alloy_rlp`'s generic `Vec<T>::decode`, which allocates one `AccountChange` per RLP list item with no cap on item count before the whole vector is materialized. `AccountChange` itself is a multi-field enum (`Create`, `ConfigChange`, `Delegation`) whose smallest variant still requires only a handful of wire bytes (list header + type byte + minimal payload), but each decoded item consumes a full enum-sized heap slot in the growing `Vec<AccountChange>`. This is exactly the "attacker declares many cheap items, decoder allocates one heavy struct per item" allocation-amplification pattern that the codebase's own comments (on `decode_calls`, on the SSZ `BoundedTransactions`, and on the CWE-770 regression test) identify and defend against elsewhere: [5](#0-4) 

This decode path is reached directly from an unprivileged, anonymous `eth_sendRawTransaction` (or any raw-tx ingestion / txpool admission path) submitting an EIP-8130-typed transaction, since `rlp_decode_fields` is the canonical unsigned-body decoder used to reconstruct `TxEip8130` before validity/authorization checks run.

### Impact Explanation
An attacker can craft a single EIP-8130 transaction whose `account_changes` list contains as many minimal-size `AccountChange::Delegation` (or similarly minimal) entries as the transaction's own byte-size budget allows, forcing the node to allocate and grow a `Vec<AccountChange>` with no count guard, unlike the parallel `calls` field which was hardened for exactly this reason. Depending on the actual per-item heap footprint versus wire footprint (not independently measured here), this can amplify a comparatively small transaction payload into a substantially larger in-memory allocation during pre-admission RLP decode, which is the resource-exhaustion pattern this whole file's design otherwise defends against.

### Likelihood Explanation
The `rlp_decode_fields` function is on the transaction ingestion hot path for any submitted EIP-8130 transaction (RPC, block building, txpool admission), so the trigger requires nothing beyond composing a valid RLP-encoded `TxEip8130` body — a single unprivileged, anonymous transaction submission is sufficient to reach this code.

### Recommendation
Introduce a `MAX_ACCOUNT_CHANGES_PER_TX` constant (mirroring `MAX_CALL_PHASES_PER_TX`) and decode `account_changes` through a bounded helper analogous to `decode_calls`, rejecting the transaction as soon as the running item count exceeds the limit, before the rest of the list is materialized.

### Proof of Concept
Not independently constructed/verified in this pass — this analysis is based on static code reading and could not be validated with a runtime allocation-measurement harness (as exists for the `decode_v4` SSZ case) within this session. I could not confirm the exact heap-size-per-item of `AccountChange` versus its minimal wire encoding, nor whether some upstream layer (e.g. mempool max transaction byte-size limits in `crates/execution/txpool/src/validator.rs`) already bounds the practical amplification to a low, non-impactful multiple. Given the codebase's otherwise very consistent and deliberate hardening against this exact CWE-770 pattern in every other decode path examined (SSZ payload/transactions, snappy envelope, span-batch bits, blob decode, deposit decode, upgrade-signal ABI length, validity predicates, and `calls` itself), this should be treated as a **Medium-confidence** structural gap rather than a confirmed, quantified High-severity DoS, and warrants confirmation via a targeted allocation-measurement test (as already used for `decode_v4`) before triage.

    fn decode_calls(buf: &mut &[u8]) -> alloy_rlp::Result<Vec<Vec<Call>>> {
        let header = Header::decode(buf)?;
        if !header.list {
            return Err(alloy_rlp::Error::UnexpectedString);
        }
        if buf.len() < header.payload_length {
            return Err(alloy_rlp::Error::InputTooShort);
        }

        let (mut payload, rest) = buf.split_at(header.payload_length);
        let mut phases = Vec::new();
        while !payload.is_empty() {
            if phases.len() >= Eip8130Constants::MAX_CALL_PHASES_PER_TX {
                return Err(alloy_rlp::Error::Custom("too many EIP-8130 call phases"));
            }
            phases.push(Vec::<Call>::decode(&mut payload)?);
        }
        *buf = rest;
        Ok(phases)
    }
