### Title
Confidential-relay gateway request IDs are not namespaced per requester, allowing cross-tenant DoS via `req.ID` collision - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Finding Description
`newActiveRequest` keys the in-flight request table solely on the caller-supplied `req.ID`, with no namespace or owner binding: [1](#0-0) 

`HandleJSONRPCUserMessage` only validates that `req.ID` is non-empty and ≤200 characters before calling `newActiveRequest`; there is no authentication, authorization, or per-caller/per-owner prefixing of the ID anywhere in this handler or file: [2](#0-1) 

Any authorization/attestation checks (`verifyAttestationHash`, `verifyWorkflowAuthorization`, owner matching) happen later, at the DON node side in `core/capabilities/confidentialrelay/handler.go`, not in this gateway handler. By contrast, the sibling vault gateway pipeline explicitly guards against exactly this cross-tenant ID collision by prefixing the authenticated owner onto the request ID before it is used as a lookup/storage key: `prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID` in `authorizeAndStamp`, confirmed by the vault handler's own "duplicate requestId" test which show request-ID reuse is expected to be scoped per owner.

Since the confidentialrelay handler has no equivalent step, two different requesters (from different owners/workflows) submitting the same raw `req.ID` value collide directly on the same `h.activeRequests` map key. The second submission is rejected with `"request ID already exists: " + req.ID"` while the first request's `activeRequest` (and its pending callback/response state) is untouched — meaning the second (potentially malicious) requester can trivially predict/guess or intentionally reuse a victim's chosen ID to prevent the victim's request from being retried under that ID, or to have their own competing request rejected/observed as a probe of ID usage.

### Impact Explanation
Concrete impact is limited to denial-of-service of a specific pending confidential-relay request: an attacker who submits a request with the same `req.ID` as a currently-active victim request receives (and can force) an "already exists" error, and if attempted repeatedly can block a victim's legitimate confidential-relay flow (secrets fetch / capability execution) from being retried with that identifier for the lifetime of `RequestTimeoutSec`. This matches a griefing/DoS impact class rather than fund loss or secret disclosure — the underlying secrets/attestation checks in `core/capabilities/confidentialrelay/handler.go` still prevent unauthorized data access.

### Likelihood Explanation
Exploitability requires only the ability to submit a JSON-RPC request to this gateway's `MethodSecretsGet`/`MethodCapabilityExec` route with an attacker-chosen `req.ID` matching a target's ID, and knowledge/guessability of that ID (workflow/execution-scoped IDs may be predictable or observable by a colluding/lower-trust party sharing the same DON/gateway). No admin or operator access is needed, and the collision check is fully reachable pre-authorization, since `newActiveRequest` runs before any attestation/ownership verification.

### Recommendation
Namespace `activeRequests` keys by an authenticated identity (e.g., owner/workflow ID derived from request auth) concatenated with the caller-supplied `req.ID`, mirroring the `authorizedOwner + RequestIDSeparator + originalRequestID` pattern already used in `core/capabilities/vault/gateway_vault_request_processor.go`'s `authorizeAndStamp`, so that ID collisions can only occur within a single authorized owner's namespace.

### Proof of Concept
Go test in `core/services/gateway/handlers/confidentialrelay/handler_test.go`:
1. Construct two `jsonrpc.Request[json.RawMessage]` values with identical `ID = "shared-id"` but different simulated originating identities/params (representing two unrelated owners/workflows).
2. Call `h.HandleJSONRPCUserMessage` (or directly `h.newActiveRequest`) for request A with callback A; assert success and that `h.activeRequests["shared-id"]` is set to A's `activeRequest`.
3. Call the same for request B (different owner) with callback B before A completes; assert it returns `"request ID already exists: shared-id"`.
4. Assert callback A's state/response channel is unaffected (no response sent, `completed` still false) — demonstrating cross-tenant DoS/blocking without any authorization check having run.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
