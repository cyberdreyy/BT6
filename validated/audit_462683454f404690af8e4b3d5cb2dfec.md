### Title
Instant-withdraw claims pay the full receipt regardless of collected funding, letting the first claimant drain the shared instant pool - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
CVE-2019-12448 is a race condition caused by the gvfs admin backend acting on a file without a `query_info_on_read/write` check — it performs an operation on state that was never re-queried for the current transaction. The analog in idle-tranches is `IdleCreditVault.claimInstantWithdrawRequest`: it pays out the user's entire `instantWithdrawsRequests` balance without querying how much of the aggregate instant pool (`pendingInstantWithdraws`) was actually collected via `collectInstantWithdrawFunds`. When the instant bucket is only partially funded, the claim order — not the funding — decides who gets paid.

### Finding Description
`requestInstantWithdraw` burns the CDO's strategy tokens, mints a 1:1 receipt to the user, and adds the amount to both `instantWithdrawsRequests[_user]` and the global `pendingInstantWithdraws` (IdleCreditVault.sol:356-375). Funding arrives later when the CDO calls `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and pulls the underlying from the CDO (IdleCreditVault.sol:398-403).

`claimInstantWithdrawRequest` then does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

(IdleCreditVault.sol:387-392)

Unlike normal withdraw claims, which gate on `epochNumber <= lastWithdrawRequest[_user]` and per-epoch receipt state (`_claimFundedWithdrawRequest`, IdleCreditVault.sol:319-350), the instant claim performs no query of:

- whether this user's epoch was funded at all,
- how much of `pendingInstantWithdraws` remains (underfunding), or
- which epoch the receipt belongs to (`instantWithdrawsRequestsByEpoch` is written but never read on this path).

The code acknowledges this hole indirectly: `defaultPendingClaimBasis` and `defaultInstantWithdrawsFinalized` exist precisely because "a non-zero pending instant bucket means current-epoch instant receipts were not fully funded" (IdleCreditVault.sol:694-696) — but that hair cutting only happens after `finalizeDefaultRecovery`. In the non-default path, partial collection simply leaves the shortfall socialized to whichever claimant arrives last.

### Impact Explanation
Scenario (running epoch → `stopEpoch`, buffer phase): two users each hold 100 receipt tokens in `instantWithdrawsRequests`. The borrower/epoch flow only results in the CDO transferring 100 underlying via `collectInstantWithdrawFunds` (e.g., the borrower repaid only part before `instantWithdrawDeadline`, or the CDO funded only a portion while `pendingInstantWithdraws` stays positive). User A calls `claimInstantWithdrawRequest` first: the strategy holds 100 underlying, A's burn of 100 receipt tokens succeeds, and A receives the full 100 — the entire funded pool. User B's claim of 100 then reverts on the transfer (strategy balance is 0), permanently freezing B's funded share even though B's receipt was economically identical to A's. The invariant "one receipt, one payout" is broken in favor of "first receipt, all payouts": quantified loss equals the unfunded portion of the instant bucket, up to the full second claimant's principal.

### Likelihood Explanation
Likelihood is moderate: it requires an epoch in which instant withdrawals were requested and the CDO funds less than the aggregate `pendingInstantWithdraws` while not entering the `defaulted`/`defaultRecoveryFinalized` path. The prefunded-epoch and programmable-borrower flows explicitly contemplate partial instant funding (`_defaultPrefundedInstantReserve`, IdleCDOEpochVariant stopEpoch collecting `_pendingWithdraws` separately from instant buckets), and `instantWithdrawDeadline` exists because instant funding is expected to sometimes arrive late or short. Because payout order is determined by transaction ordering, any unprivileged receipt holder can front-run another claimant.

I could not fully confirm whether `IdleCDOEpochVariant.claimInstantWithdrawRequest` (the `_onlyIdleCDO` caller) compensates for the shortfall before forwarding the claim — its gating uses `allowInstantWithdraw`/`disableInstantWithdraw` flags, which appear to gate timing rather than per-user funded amounts. If the CDO caps each claim at the strategy's actual balance, the impact degrades to a revert (temporary freezing) rather than theft; this is the main uncertainty in the finding.

### Recommendation
Make the instant claim funding-aware, mirroring the normal-claim path:

- Track funded vs. unfunded instant receipts per epoch (e.g., an `instantFundedPriceByEpoch` analogous to `lossRecoveryPriceByEpoch` in `collectWithdrawFunds`, IdleCreditVault.sol:411-430).
- In `claimInstantWithdrawRequest`, cap `amount` to the user's funded pro-rata share of the epoch's collected instant funds instead of paying `instantWithdrawsRequests[_user]` in full.
- Alternatively, have `collectInstantWithdrawFunds` record a per-epoch recovery price whenever `_amount < pendingInstantWithdraws`, so partial funding produces an explicit haircut rather than a silent first-come race.

### Proof of Concept
Foundry fork PoC outline (against `test/foundry/IdleCreditVault.t.sol` harness):

1. Deposit AA so the CDO holds strategy tokens; `startEpoch` via manager.
2. Two distinct users (or the CDO on behalf of two lenders via queue receipts) call `requestInstantWithdraw(100)` each → `instantWithdrawsRequests[A] = instantWithdrawsRequests[B] = 100`, `pendingInstantWithdraws = 200`.
3. Simulate underfunding: borrower repays only interest + 100; `stopEpoch`/`collectInstantWithdrawFunds` pulls only 100 into the strategy, leaving `pendingInstantWithdraws = 100`.
4. Prank A → `cdo.claimInstantWithdrawRequest()`: A burns 100 receipts and receives 100 underlying (the entire funded pool).
5. Prank B → same call reverts on the underlying transfer (strategy balance 0). Assert `instantWithdrawsRequests[B] == 100` is unclaimable despite B holding a valid, identical receipt.
6. Assert expected outcome after fix: A and B each receive 50.
