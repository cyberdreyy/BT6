### Title
Unbounded reorg-attempt activity crediting when no block is ever globally accepted - keeps a non-producing miner's tenure alive past `is_timed_out` (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`check_latest_block_in_tenure` credits "miner activity" for any low/conflicting-height reorg-shaped proposal whenever the existing best-known block in that tenure has no `signed_group` timestamp, with no time bound in that branch. Since `signed_group` is only set once a block is *globally accepted*, a miner who never produces a validly-accepted block can keep resubmitting reorg-shaped proposals indefinitely and never fall outside the intended `reorg_attempts_activity_timeout` window, because that timeout is only checked when `signed_group` is `Some`.

### Finding Description
The guarded branch is:
```rust
if info.signed_group.is_none_or(|signed_time| {
    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
}) {
    // ...treat any attempt to reorg a locally accepted block as valid miner activity...
    signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())?;
``` [1](#0-0) 

`Option::is_none_or` returns `true` immediately when the option is `None`, without evaluating the time predicate at all. That means the `reorg_attempts_activity_timeout` bound is only enforced in the case where the tenure's last known block *was already globally accepted* (`signed_group: Some(_)`). If the tenure has never had a block reach global acceptance, `info.signed_group` stays `None` forever, so every low-height/conflicting proposal from that tenure's miner unconditionally refreshes `update_last_activity_time` for that tenure's consensus hash, with no expiry — the comment "treat any attempt to reorg... as valid miner activity" applies without the intended time bound. [2](#0-1) 

Combined with `check_miner_inactivity`, which only advances past the current `ActiveMiner` tenure once `SortitionState::is_timed_out` returns true (driven by last-activity freshness), a miner who wins a slot and never produces a globally-accepted block, but continuously gossips low-height/conflicting `BlockProposal`s for their own tenure, would keep the activity timer refreshed indefinitely, preventing `check_miner_inactivity` from ever reverting to the prior valid tenure. [3](#0-2) 

### Impact Explanation
This is a liveness concern, not a safety break: no invalid block is ever signed, and no equivocation/canonicity guard is broken. If exploitable end-to-end, it would fall into the "signer wedged into never signing valid blocks (liveness)" category, since the fallback path in `check_miner_inactivity` (`make_miner_state` reverting to the prior tenure) would never trigger for the affected tenure.

### Likelihood Explanation
I could not fully verify, within the available tool budget, whether `is_timed_out` (in `chainstate/v1.rs` / `chainstate/v2.rs`) keys its freshness check on the exact same tenure identifier that `update_last_activity_time` is called with in this code path, nor whether other independent timeout checks inside `is_timed_out` (e.g., against `block_proposal_timeout` rather than solely `last_activity_time`) would still force a timeout regardless of this credited activity. Without confirming that exact equality, I cannot confirm the wedge is real end-to-end (as opposed to being caught by an orthogonal timeout check elsewhere in `is_timed_out`).

### Recommendation
Not able to give a fully confident recommendation without confirming the `is_timed_out` linkage, but the immediate code smell is clear: `info.signed_group.is_none_or(...)` should not unconditionally return `true` when `signed_group` is `None`. If the intent is "give an extra grace window for unsigned/locally-only-accepted blocks," that grace window should still be bounded (e.g., measured from `first proposal received time` or `approved_time`) rather than being open-ended for the `None` case.

### Proof of Concept
Given the incomplete verification of `is_timed_out`'s exact keying, a definitive Rust PoC test plan cannot be finalized with confidence. It would need to:
1. Instantiate a `SignerDb` and `ProposalEvalConfig` with a small `reorg_attempts_activity_timeout` and `block_proposal_timeout`.
2. Simulate a tenure with a locally-accepted (not globally-accepted) block so `signed_group` is `None`.
3. Loop calling `SortitionData::check_latest_block_in_tenure` with fixed-cadence, always-too-low-height reorg proposals across multiple `reorg_attempts_activity_timeout` windows.
4. Call `LocalStateMachine::check_miner_inactivity` after each round and assert whether it ever reverts `current_miner` away from the attacker's tenure via `make_miner_state`.
5. Cross-check against `SortitionState::is_timed_out`'s source in `chainstate/v1.rs`/`v2.rs` to confirm which timeout value(s) gate the transition, to be certain no other bound intervenes.

Given the incompleteness of step 5 in this investigation, I cannot assert this finding with full confidence as a confirmed exploitable vulnerability — it is a credible code-level issue (the `is_none_or` short-circuit) but the full state-machine wedge claimed in the question is not fully traced end-to-end here.
