### Title
Stale/retracted signer rejections are never subtracted from the miner coordinator's rejection tally, causing a permanently inflated `total_weight_rejected` that can kill an otherwise-signable block - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The `StackerDBListener` on the mining node tallies signer votes for a proposed block into two independent, monotonically-increasing counters, `total_weight_approved` and `total_weight_rejected`. The v0 signer protocol explicitly allows a signer to change a prior `Rejected` verdict into an `Accepted` one for the *same* block once the reason for rejection no longer holds (`LocallyRejected -> LocallyAccepted: re-evaluated` in the signer's own state machine). When that happens, the coordinator correctly adds the signer's weight to `total_weight_approved`, but it never removes that signer's weight from `total_weight_rejected`. The rejection weight is therefore never retracted, permanently overstating how much weight is against the block.

### Finding Description
In the accept branch of the StackerDB message handler, a signer's weight is added to `total_weight_approved` the first time its signature is seen, gated only on `gathered_signatures` not yet containing the slot: [1](#0-0) 

In the reject branch, weight is added to `total_weight_rejected` the first time a rejection is seen from that slot, gated on `responded_signers`: [2](#0-1) 

Both branches insert the slot into `responded_signers`/`gathered_signatures` independently and neither branch clears the other side's tally. So the sequence Reject(slot) → Accept(slot) for the *same* block leaves the slot's weight counted in **both** `total_weight_rejected` and `total_weight_approved`. Crucially, nothing in this file ever decrements `total_weight_rejected` when a later valid signature supersedes an earlier rejection.

This is inconsistent with the signer's own protocol semantics, where a signer is expected to be able to retract a stale rejection and later sign (`LocallyRejected --> LocallyAccepted : re-evaluated`, `docs/signer-flows.md` lines 142-147), and with the signer-side local bookkeeping of *other* signers' votes, which does clean up stale rejection records when a newer signature supersedes them: [3](#0-2) 

`add_block_signature` explicitly deletes the corresponding `block_rejection_signer_addrs` row for that signer before inserting the new signature — i.e. the per-signer bookkeeping treats a later acceptance as retracting an earlier rejection. The mining node's own coordinator tally (`stackerdb_listener.rs`) has no equivalent retraction logic, so it silently drifts from the true, current state of signer intent.

The consumer of this tally, `signer_coordinator.rs`, treats `total_weight_rejected` as ground truth for declaring the block dead: [4](#0-3) 

If enough signers (just over the 30% blocking minority — not a majority) reject a proposal and then change their mind and sign it (a legitimate, protocol-sanctioned re-evaluation), the stale rejection weight from before the flip is never removed. `total_weight_rejected.saturating_add(weight_threshold) > total_weight` can therefore evaluate true (or stay true) purely on outdated data, causing the coordinator to declare the block `SignersRejected`/dead even though a sufficient, currently-valid set of acceptances exists or is about to.

### Impact Explanation
This breaks the equality between "aggregated weight recorded by the coordinator" and "actually-verified, currently-standing accept/reject responses from signers." A block that the signer set would legitimately approve can be wrongly and permanently treated by the miner as globally rejected because of rejection weight that no longer reflects any signer's current position, wedging that specific block-production attempt on stale state. This requires only slightly over 30% of signer weight to have transiently rejected before flipping to accept — not a majority — matching the required threshold for in-scope findings.

### Likelihood Explanation
This can occur any time validation timing causes some signers to reject on a first pass (e.g., stale/too-old proposal, timing race in `should_reevaluate_reject_reason`) and then legitimately accept once conditions change, which the signer-flows documentation shows is an expected, designed-for path (`LocallyRejected -> LocallyAccepted: re-evaluated`). No malicious behavior or majority collusion is needed — it's a byproduct of normal signer re-evaluation combined with a coordinator-side bookkeeping gap.

### Recommendation
When a valid signature/acceptance is recorded for a slot that had previously been counted in `total_weight_rejected` (i.e., present in `responded_signers` due to an earlier rejection), subtract that signer's weight from `total_weight_rejected` (and vice versa if a later rejection supersedes an earlier acceptance), mirroring the retraction logic already implemented in `SignerDb::add_block_signature`. Alternatively, track per-slot current vote (accept/reject) in a single map and recompute aggregate weights from it, rather than maintaining two independently-incrementing, never-decrementing counters.

### Proof of Concept
1. Miner proposes block B; broadcasts to N signers with `weight_threshold` set to 70% of `total_weight`.
2. Signers holding slightly over 30% of total weight initially reject B (e.g., due to a timing-sensitive check such as `ProposalTooOld` or a transient view mismatch) — `stackerdb_listener.rs` records this into `total_weight_rejected`, crossing `total_weight_rejected + weight_threshold > total_weight`.
3. Those same signers subsequently re-evaluate (as the signer-flows model explicitly allows) and sign B, sending `BlockResponse::Accepted`.
4. `stackerdb_listener.rs` adds their weight to `total_weight_approved` (lines 443-465) but never removes it from `total_weight_rejected`.
5. `signer_coordinator.rs`'s wait loop (lines 505-519) observes `total_weight_rejected` already over the blocking-minority threshold from step 2 and returns `NakamotoNodeError::SignersRejected`, discarding block B even though it now has legitimate accepting signatures potentially reaching `weight_threshold`.

    /// Record an observed block signature
    pub fn add_block_signature(
        &self,
        block_sighash: &Sha512Trunc256Sum,
        signer_addr: &StacksAddress,
        signature: &MessageSignature,
    ) -> Result<bool, DBError> {
        // Remove any block rejection entry for this signer and block hash
        let del_qry = "DELETE FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1 AND signer_addr = ?2";
        let del_args = params![block_sighash, signer_addr.to_string()];
        self.db.execute(del_qry, del_args)?;

        // Insert the block signature
        let qry = "INSERT OR IGNORE INTO block_signatures (signer_signature_hash, signer_addr, signature) VALUES (?1, ?2, ?3);";
        let args = params![
            block_sighash,
            signer_addr.to_string(),
            serde_json::to_string(signature).map_err(DBError::SerializationError)?
        ];
        let rows_added = self.db.execute(qry, args)?;

        let is_new_signature = rows_added > 0;
        if is_new_signature {
            debug!("Added block signature.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %signer_addr,
                "signature" => %signature
            );
        } else {
            debug!("Duplicate block signature.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %signer_addr,
                "signature" => %signature
            );
        }
        Ok(is_new_signature)
    }
