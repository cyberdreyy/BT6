### Title
Withdrawal reverts when accrued management fee exceeds position value, permanently locking tranche funds - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
Analogous to the Uniswap `position.update` underflow, `IdleCDOEpochVariant` computes "value minus accrued fees owed" with a plain checked subtraction. The fee delta can legitimately be larger than the remaining position value (fees accrue on time, not on profit), yet the subtraction reverts instead of saturating at zero, so the withdrawal path bricks for affected users.

### Finding Description
In `maxWithdrawable` the user's withdrawable amount is computed as:

```solidity
currentUnderlyings = _trancheToUnderlyings(_userTrancheBal(_user, _tranche), _tranche);
currentUnderlyings -= _calculateManagementFee(currentUnderlyings, block.timestamp - latestHarvestBlock);
(uint256 interest, ) = _calcInterestWithdrawRequest(currentUnderlyings, _tranche);
currentUnderlyings = currentUnderlyings + interest - _totalWithdrawFees(currentUnderlyings, interest);
``` [1](#0-0) 

`_calculateManagementFee` grows linearly with `block.timestamp - latestHarvestBlock` while `currentUnderlyings` is fixed (or shrinking after losses). Once the accrued fee exceeds the position's underlying value, `currentUnderlyings -= fee` underflows and panics. Like the Uniswap case where `feeGrowthInside - feeGrowthInsideLast` can be negative, "balance minus owed fees" can legitimately be negative here — the correct answer is 0, but the code reverts.

The same signed-arithmetic assumption appears in `writeOffDeposit`, where `expectedEpochInterest -= interest` reverts if the computed interest exceeds the checkpointed expectation [2](#0-1) , though that path is borrower-only.

### Impact Explanation
A lender whose tranche position has been accruing management fees longer than its underlying value grew — e.g., long-lived positions in low-APR or APR0 epochs, or positions after a loss reduced NAV — gets a revert on the withdrawal-quoting path and on any claim path that applies the same `value - fees` subtraction. Because `block.timestamp - latestHarvestBlock` only increases, the condition does not self-heal: the position reverts every time, i.e., permanently locked funds (same impact class as the source report).

### Likelihood Explanation
Requires no attacker action beyond holding a position through epochs where management fee accrual outpaces interest; APR0 epochs (`apr0Users` flow) and post-loss states make `fee > balance` reachable faster. No privileged role misbehavior is needed — `latestHarvestBlock`, `managementFee`, and epoch timing are all set by honest actors.

### Recommendation
Mirror the Uniswap fix direction: do not revert on negative fee deltas. Compute withdrawable amounts as saturating subtraction — `currentUnderlyings = fee > currentUnderlyings ? 0 : currentUnderlyings - fee` — and cap `_totalWithdrawFees` at `principal + interest` instead of allowing the subtraction to underflow.

### Proof of Concept
```solidity
// Fork a live credit vault with managementFee != 0.
// 1. User deposits into AA during buffer; epoch starts and stops normally.
// 2. vm.warp far forward so _calculateManagementFee(balance, block.timestamp - latestHarvestBlock) > balance
//    (management fee accrues continuously; the tranche balance does not).
// 3. idleCDO.maxWithdrawable(user, aaTranche) -> arithmetic underflow revert at
//    `currentUnderlyings -= _calculateManagementFee(...)`.
// 4. Any withdrawal/quote path using the same subtraction reverts identically,
//    and the condition worsens monotonically with time -> funds permanently locked.
```
Note: I could not confirm within available iterations whether the state-changing `requestWithdraw` in `IdleCDOEpochVariant`/`IdleCDOCreditVault` inlines the identical `balance - managementFee` subtraction or delegates to `maxWithdrawable`; if it only performs it inside the request flow, the permanent-lock impact applies to that path directly.
