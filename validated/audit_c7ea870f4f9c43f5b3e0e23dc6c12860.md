### Title
Virgin/first stake to a vote account can claim all pre-accumulated `pending_delegator_rewards` - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The Alpenglow block-revenue-sharing mechanism accrues `pending_delegator_rewards` on a vote account independently of how much stake is currently delegated to it, then distributes that pool pro-rata to whatever stake happens to be delegated at the reward epoch. Because the deposit path is permissionless and stake-independent, a staker who delegates a trivial amount to a vote account with little/no prior delegated stake can capture the entire previously-accumulated `pending_delegator_rewards` balance in the very first epoch their stake becomes effective — the same "virgin stake claims all drops" pattern described in the referenced wxETH finding.

### Finding Description
`pending_delegator_rewards` is a field on the vote account that anyone can top up via the permissionless `deposit_delegator_rewards` instruction, which only requires the *source* account (not the vote/withdraw authority) to sign: [1](#0-0) 

This deposit simply transfers lamports and increments `pending_delegator_rewards` — it has no relationship whatsoever to `total_active_stake` for the vote account, so it can (and does) accumulate while the vote account has zero or near-zero delegated stake: [2](#0-1) 

At the reward-epoch boundary, `calculate_block_reward` distributes this entire pool pro-rata to whatever stake is delegated to that vote account *at the reward epoch*, using `total_active_stake` (the sum of delegated stake as of that epoch) as the denominator: [3](#0-2) 

The only existing guard is `if total_active_stake == 0 { 0 }` — this is exactly the mitigation pattern recommended in the wxETH report (`don't drip when totalSupply == 0`), but it only protects the case where stake is *exactly* zero. It does not protect the case where `pending_delegator_rewards` accumulates over one or more epochs while stake is zero (or negligible), and then a "virgin" staker delegates a trivial amount of stake that becomes the *sole* (or dominant) `total_active_stake` for that vote account in the very next reward epoch. In that case:
```
block_reward = pending_delegator_rewards * stake / total_active_stake
```
with `stake == total_active_stake` (the virgin staker is the only delegator), yielding `block_reward = pending_delegator_rewards` — the entire previously accumulated reserve, regardless of how briefly or how little the staker has actually staked.

This mirrors the reward/points calculation for inflation as well, where `calculate_alpenglow_points` divides earned credits*stake by the total delegated stake for the reward epoch, with no requirement that the claiming stake actually existed while the underlying value accrued: [4](#0-3) 

### Impact Explanation
An attacker (or an unrelated party who intended to reward a broader future delegator base of a validator) can have their deposited/accumulated `pending_delegator_rewards` fully captured by a single virgin staker who delegates only a nominal amount just before/at the point the reward-epoch snapshot is taken. This is a direct value-misappropriation vector: funds meant to be shared among the vote account's actual delegator base (present and future) can be siphoned entirely by whoever is first (or the only one) to stake once a reserve has built up, at the expense of anyone attempting to bootstrap delegator rewards for a newly-created or currently unstaked validator. Since the deposit path is permissionless and stake-independent while distribution is not gated by any minimum stake duration/amount proportionality across the accrual period, this allows disproportionate reward extraction relative to actual contribution/duration of stake.

### Likelihood Explanation
Likelihood is comparable to the original finding: it requires (1) a vote account currently having zero or very low `total_active_stake` for a reward epoch, and (2) `pending_delegator_rewards` having been deposited (by anyone) during that window, and (3) a staker delegating before/at the next reward-epoch snapshot. New/low-stake validators (a very common state on any network) and the fully permissionless nature of `deposit_delegator_rewards` make this a realistically reachable scenario, especially for grief/self-dealing by validator operators bootstrapping their own vote accounts.

### Recommendation
Do not allow rewards to be claimed disproportionately to the delegator's actual contribution/duration during accrual. Options include:
- Track `pending_delegator_rewards` accrual against a stake-weighted-time basis (similar to `credits_observed`) rather than a flat pool distributed by the reward epoch's snapshot stake, so a staker only shares in rewards that accrued while their stake was actually delegated and active.
- Require a minimum "seasoning" period (multiple epochs) of active stake before a delegator is eligible to receive a share of `pending_delegator_rewards`, or cap the amount payable per epoch relative to the newly-activated stake's tenure.
- At minimum, extend the existing `total_active_stake == 0` guard to also suppress/carry-forward payout when `total_active_stake` has been zero for the deposit's entire dwell time, rather than only checking the instantaneous value at the reward epoch.

### Proof of Concept
1. Vote account `V` currently has `total_active_stake == 0` (e.g., newly created, or all prior stake deactivated).
2. Anyone submits `VoteInstruction::DepositDelegatorRewards { deposit: X }` against `V` repeatedly/over time, growing `V.pending_delegator_rewards` to `X_total`, per `deposit_delegator_rewards`: [5](#0-4) .
3. An attacker delegates a minimal stake amount to `V` (a normal `CreateAccount`/`DelegateStake` sequence). After warm-up, this stake becomes `V`'s entire `total_active_stake` for the next `rewarded_epoch`.
4. At the reward-epoch boundary, `calculate_block_reward` computes `pending_delegator_rewards * stake / total_active_stake` with `stake == total_active_stake`, yielding the full `X_total` paid to the attacker's stake account: [6](#0-5) .
5. The attacker's stake account, having contributed no duration/amount proportional to the accrued deposits, has captured the entire pool and can deactivate/withdraw it.

```rust
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
```

```rust
    pub(crate) fn add_pending_delegator_rewards(
        &mut self,
        amount: u64,
    ) -> Result<(), InstructionError> {
        match &mut self.target_state {
            TargetVoteState::V4(v4) => {
                v4.pending_delegator_rewards = v4
                    .pending_delegator_rewards
                    .checked_add(amount)
                    .ok_or(InstructionError::ArithmeticOverflow)?;
                Ok(())
            }
        }
    }
```
