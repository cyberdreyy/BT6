### Title
Fee-on-transfer deposits inflate credit-vault accounting and drain existing assets - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`depositDuringEpoch` credits the requested `_amount` instead of the amount actually received after `transferFrom`. [1](#0-0)  For a fee-on-transfer underlying, the depositor receives tranche shares, NAV, expected interest, and strategy tokens based on the gross `_amount`, while the vault transfers the same gross `_amount` to the borrower. [2](#0-1)  The missing transfer fee is therefore paid out of pre-existing pool assets, allowing an allowed lender to extract value from other tranche holders. [3](#0-2) 

### Finding Description
During a running epoch, `depositDuringEpoch` can be enabled for a non-programmable, non-AYS vault, and any wallet passing `isWalletAllowed` can call it. [4](#0-3)  The function pulls `_amount` from the caller but does not compare the contract's token balance before and after the transfer. [1](#0-0)  It calculates interest from `_amount`, mints shares from `_amount`, increases tranche NAV by `_amount`, mints `_amount` of strategy-token backing, and then sends `_amount` to the borrower. [5](#0-4) 

This differs from the normal `_deposit` flow, which snapshots the token balance and mints shares using only the actual balance delta. [6](#0-5)  `_skimDonatedAssets` protects against unsolicited balance inflation, but it cannot correct a shortfall caused by a transfer fee. [7](#0-6) 

For example, with a token charging a 10% transfer fee, an allowed depositor calls `depositDuringEpoch(100, AA)`; the vault receives 90, while tranche NAV, expected borrower funding, and strategy-token backing are recorded as 100. [8](#0-7)  The subsequent borrower transfer of 100 consumes the newly received 90 plus 10 units belonging to the existing pool. [9](#0-8) 

### Impact Explanation
The broken invariant is fair mint/burn and solvency: the attacker mints claims against 100 units while contributing only 90 net units. [10](#0-9)  Each deposit directly moves the transfer-fee shortfall to the honest borrower-recipient while leaving the vault with inflated strategy-token backing and NAV. [11](#0-10)  With a 10% fee token, every 1,000-unit nominal deposit transfers 100 units of value out of existing vault holdings; repeated deposits scale the loss until the pre-existing liquid balance is exhausted or withdrawals become underfunded. [12](#0-11) 

### Likelihood Explanation
The issue requires the vault's underlying ERC20 to charge a transfer fee or otherwise deliver less than the requested amount. [1](#0-0)  It also requires mid-epoch deposits to be enabled and the attacker to pass the configured wallet credential check, both of which are supported unprivileged operating modes rather than malicious privileged behavior. [4](#0-3)  Existing guards do not prevent it because the code explicitly permits deposits during a running epoch and never computes `received = balanceAfter - balanceBefore`. [13](#0-12) 

### Recommendation
Measure the actual amount received around the inbound transfer and use that value for guarded limits, interest calculation, share minting, NAV accounting, strategy-token minting, and the outbound borrower transfer. [14](#0-13)  Revert if the received amount is zero, and calculate `trancheInterest`, `expectedFinal`, `expectedEpochInterest`, and `mintStrategyTokens` from `received`, not from `_amount`. [15](#0-14)  The same received amount should be forwarded to `IIdleCDOStrategy(strategy).deposit` in normal deposits so the downstream strategy is not instructed to pull more than the vault received. [16](#0-15) 

### Proof of Concept
The following Foundry fork scenario assumes a deployed epoch vault whose configured `token` applies a 10% transfer fee and whose owner has enabled `depositDuringEpoch`; the attacker is a KYC-passing lender. [4](#0-3) 

```solidity
function test_feeOnTransfer_midEpochDeposit_drainsPool() public {
    uint256 nominal = 1_000e6;
    uint256 feeBps = 1_000;

    uint256 vaultBefore = token.balanceOf(address(cdo));
    uint256 borrowerBefore = token.balanceOf(borrower);
    uint256 navBefore = cdo.lastNAVAA();

    deal(address(token), attacker, nominal);
    feeToken.setTransferFeeBps(feeBps);

    vm.startPrank(attacker);
    token.approve(address(cdo), nominal);
    uint256 minted = cdo.depositDuringEpoch(nominal, cdo.AATranche());
    vm.stopPrank();

    uint256 received = nominal - (nominal * feeBps / 10_000);

    assertEq(token.balanceOf(attacker), 0);
    assertEq(token.balanceOf(address(cdo)), vaultBefore + received - nominal);
    assertEq(token.balanceOf(borrower), borrowerBefore + nominal);
    assertEq(cdo.lastNAVAA(), navBefore + nominal);
    assertGt(minted, 0);
}
```

The assertion demonstrates the invariant violation: the borrower is credited `nominal`, while the depositor supplied only `received`, leaving the remaining `nominal - received` funded by prior vault assets. [12](#0-11)  If the test environment only has a plain ERC20 available on the fork, the same behavior can be reproduced by pointing the vault at a fee-on-transfer token or a local fee-charging token with identical transfer semantics; the vulnerable production path itself is the missing balance delta at lines 684–685 and the subsequent gross-amount accounting at lines 724–732. [17](#0-16)

      // the time the depositor actually participates (remaining epoch + full buffer)
      (remaining + buffer) /
      // the total time baked into the scaled APR (epoch + buffer).
      (epochDuration + buffer);

    uint256 pendingFees = pendingWithdrawFees;

    // interest this deposit will earn for the tranche over the remaining time (net of fees)

    // This won't ever be zero as we checked _trancheTotSupply and we seed initial NAV at tranche creation

    // A mid‑epoch depositor should get _amount + trancheInterest at epoch end.
