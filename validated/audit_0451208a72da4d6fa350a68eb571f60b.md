### Title
Unvalidated attacker-supplied `fec_set_count` leads to `u32` addition overflow panic in `BlockIdRepairService::process_block_id_repair_response`'s `FecSetRoot` arm - (File: `core/src/repair/block_id_repair_service.rs`)

### Finding Description
The `ParentFecSetCount` response arm builds a series of `FecSetRoot` requests using unchecked multiplication of an attacker-controlled `fec_set_count` value: [1](#0-0) 

`fec_set_count` comes directly from the peer's `BlockIdRepairResponse::ParentFecSetCount` and is not bounded against the block's actual FEC set count before use, other than being verified as a properly signed/matched repair response by `register_response`. For any `i` in `0..fec_set_count`, `fec_set_index = i * DATA_SHREDS_PER_FEC_BLOCK as u32` is computed; for large `i` (near `u32::MAX / DATA_SHREDS_PER_FEC_BLOCK`) this value can approach `u32::MAX` without itself overflowing the multiplication.

Later, when the node receives the corresponding `BlockIdRepairResponse::FecSetRoot` for one of these large-`fec_set_index` requests, the code computes: [2](#0-1) 

`end_index = fec_set_index + DATA_SHREDS_PER_FEC_BLOCK as u32` is a plain `+` with no `checked_add`/`saturating_add`. If `fec_set_index` is within `DATA_SHREDS_PER_FEC_BLOCK` of `u32::MAX` (which is reachable from an attacker-chosen `fec_set_count`), this addition overflows `u32`. On builds with overflow checks enabled this panics the thread running `BlockIdRepairService::run`, and even without overflow checks, wraparound would corrupt the subsequent `(start_index..end_index)` range, producing an empty or nonsensical range of `ShredForBlockId` requests.

The request is legitimately validated via `state.outstanding_requests.register_response(...)` (matching nonce/request), so the check that "this is a response we actually asked for" passes; there is no independent bound on `fec_set_index` itself before the addition.

### Impact Explanation
This is a single-peer-reachable node-process crash: an attacker (any repair peer the node queries) that responds to a `ParentAndFecSetCount` request with a large `fec_set_count`, followed by responding to the resulting `FecSetRoot` request, can drive `fec_set_index + DATA_SHREDS_PER_FEC_BLOCK` past `u32::MAX`, causing an arithmetic overflow panic in `BlockIdRepairService`'s processing thread. This matches the "validator-process crash from chained single low-rate responses" impact category.

### Likelihood Explanation
Feasibility requires: (1) the node has already issued a `ParentAndFecSetCount` request to the attacker-controlled peer (normal repair flow, triggerable by the attacker simply appearing as a repair peer for a slot the node is repairing), (2) the attacker replies with a large `fec_set_count`, which the node accepts without an upper bound check other than that the response matches an outstanding request, (3) the node subsequently sends a `FecSetRoot` request for the resulting large `fec_set_index` and the attacker answers it. Generating a `fec_set_count` large enough to produce `fec_set_index` values near `u32::MAX` also forces the node to materialize a very large number of pending `FecSetRoot` entries in `state.pending_repair_requests` (up to `fec_set_count` entries), which is itself a resource-consumption concern that occurs before the overflow is even reached, but does not stop the overflow from being reachable once enough entries are processed/sent.

### Recommendation
- Bound `fec_set_count` in the `ParentFecSetCount` arm to a sane maximum (e.g., derived from a known max block size / max FEC sets per slot) before iterating `0..fec_set_count`.
- Replace the unchecked `+` at `end_index = fec_set_index + DATA_SHREDS_PER_FEC_BLOCK as u32` with `fec_set_index.checked_add(DATA_SHREDS_PER_FEC_BLOCK as u32)` (or `saturating_add`), and drop/log the response instead of panicking if the addition would overflow.
- Similarly guard the multiplication at `i * DATA_SHREDS_PER_FEC_BLOCK as u32` with `checked_mul`/`saturating_mul` to avoid relying on build-specific overflow-check behavior.

fn fec_set_root_end_index_overflow() {
    // Simulate a FecSetRoot request whose fec_set_index was derived from an

    // choosing i near u32::MAX / DATA_SHREDS_PER_FEC_BLOCK so that
    // fec_set_index is within DATA_SHREDS_PER_FEC_BLOCK of u32::MAX.
    let fec_set_index: u32 = u32::MAX - (DATA_SHREDS_PER_FEC_BLOCK as u32 - 1);

    // let end_index = fec_set_index + DATA_SHREDS_PER_FEC_BLOCK as u32;

    // Expected fix: no panic, either bounded response rejected or checked arithmetic used.
    let end_index = fec_set_index.checked_add(DATA_SHREDS_PER_FEC_BLOCK as u32);
    assert!(end_index.is_none(), "addition should overflow for this crafted fec_set_index");
    // Assert that process_block_id_repair_response(), when fed a crafted
    // FecSetRoot response matching this fec_set_index, does not panic and
    // instead drops the response / increments invalid_packets stat.
}
