### Title
Keyring whitelist check in `requestWithdraw` makes it impossible in practice to de-whitelist a lender with an open tranche position — ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`IdleCDOEpochVariant.requestWithdraw` reverts unless `isWalletAllowed(msg.sender)` passes the Keyring credential check. `IdleCDOEpochQueue.requestWithdraw` applies the same check via `_checkAllowed`. This mirrors the UXD bug class: because the *exit* path is gated by the whitelist, removing a lender's credential strands their tranche principal — the admin cannot practically revoke access for any lender holding a material position without permanently freezing that lender's funds.

### Finding Description
In `IdleCDOEpochVariant.sol`, `requestWithdraw` reverts when `!isWalletAllowed(msg.sender)`:

```solidity
function requestWithdraw(uint256 _amount, address _tranche) external returns (uint256 _underlyings) {
    _checkTranche(_tranche);
    _checkNotAllowed(
      (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
      !isWalletAllowed(msg.sender)
    );
```
`IdleCDOEpochVariant.sol` lines 739–744.

`isWalletAllowed` delegates to `IKeyring(keyring).checkCredential(keyringPolicyId, _user)` whenever a keyring address is set (lines 984–987). The queue contract repeats the same gate in `IdleCDOEpochQueue.requestWithdraw` → `_checkAllowed` (`IdleCDOEpochQueue.sol` lines 131–143 and 415–421).

Consider the scenario, symmetric to the UXD report: a KYC-passed lender deposits a large amount (say 10M USDC) into AA tranches. Later the Keyring admin legitimately revokes the lender's credential (sanctions, policy change, off-boarding). From that moment:

- `requestWithdraw` on the CDO reverts with `NotAllowed`.
- `requestWithdraw` on `IdleCDOEpochQueue` reverts with `NotAllowed`.
- `depositDuringEpoch` and `_deposit` correctly also revert — that part is the intended gate.

The lender's tranche position cannot be converted into a withdraw request. The withdraw *claim* paths (`claimWithdrawRequest`, `claimInstantWithdrawRequest`, queue `claimWithdrawRequest`/`claimDepositRequest`) do not check the whitelist, but they only release funds for requests that were already opened while the user was credentialed.

This is a *design* flaw, not an attacker action: the Keyring admin is honest in the threat model, yet exercising the honest "remove lender" action produces a frozen-funds outcome, so in practice a lender holding a large position can never be de-whitelisted — the exact impracticality described in the UXD finding.

### Impact Explanation
Permanent freezing of user funds. A de-credentialed lender's tranche tokens cannot enter the only redemption paths (`requestWithdraw` on the CDO or on the queue). The loss is bounded only by the lender's full deposited principal (e.g., the entire 10M USDC position in the scenario above), since epochs run continuously and there is no fallback redemption path for a non-allowed wallet.

Partial mitigation exists: tranche tokens are transferable ERC20s and the `WriteOffEscrow` secondary-sale flow (`fullfillWriteOffRequest`) lets a non-KYC'd holder sell tranche tokens to a buyer — but the existing test `testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw` confirms even the *buyer* cannot withdraw afterward, so this only shifts the trapped position at a discount rather than unlocking it. The vault therefore cannot practically remove any lender with a meaningful balance, exactly the "cannot un-whitelist in practice" impact from the external report.

### Likelihood Explanation
Medium. The trigger is a routine, honest administrative action (Keyring credential revocation or `KeyringIdleWhitelist.setWhitelistStatus(entity, false)`) that any deployment using `setKeyringParams` must be able to perform. No attacker is required; the broken invariant (whitelist revocation should not strand committed funds) is violated deterministically the moment a funded lender's credential is revoked. Whether a pool enables keyring at all depends on `keyring != address(0)`, but keyring enforcement is the intended operating mode for these credit vaults.

### Recommendation
Do not gate withdrawal requests on `isWalletAllowed`. Concretely:

- Remove `!isWalletAllowed(msg.sender)` from `IdleCDOEpochVariant.requestWithdraw` (keep it in `_deposit` and `depositDuringEpoch`).
- Remove `cdoEpoch.isWalletAllowed(wallet)` from `IdleCDOEpochQueue._checkAllowed` for the withdraw path (split `_checkAllowed` into deposit-only and shared epoch-running checks).
- If policy requires blocking claims too, implement a separate redeem-side whitelist so that de-whitelisting for new activity never strands an existing position.

### Proof of Concept
Foundry-style PoC (adapt to the harness used in `test/foundry/IdleCreditVault.t.sol`, which already has `testOnlyKeyringUsersCanInteract` showing the same revert path at lines 5315–5337):

```solidity
function testDeWhitelistedLenderCannotRequestWithdraw() external {
    address keyring = address(1);
    address lender = makeAddr("lender");

    // enable keyring and credential the lender
    vm.prank(owner);
    cdoEpoch.setKeyringParams(keyring, 1);
    vm.mockCall(
        keyring,
        abi.encodeWithSelector(IKeyring.checkCredential.selector, 1, lender),
        abi.encode(true)
    );

    // lender deposits into AA tranche during buffer period
    deal(address(underlying), lender, 1_000_000e6);
    vm.startPrank(lender);
    underlying.approve(address(idleCDO), type(uint256).max);
    uint256 tranches = idleCDO.depositAA(1_000_000e6);
    vm.stopPrank();
    assertGt(tranches, 0);

    // keyring admin revokes the lender's credential (honest action)
    vm.mockCall(
        keyring,
        abi.encodeWithSelector(IKeyring.checkCredential.selector, 1, lender),
        abi.encode(false)
    );

    // lender can no longer open a withdraw request: funds are stranded
    vm.prank(lender);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.requestWithdraw(tranches, address(AAtranche));

    // nor via the epoch queue
    vm.prank(lender);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    queue.requestWithdraw(tranches);
}
```

Expected result: both `requestWithdraw` calls revert, demonstrating that revoking a credential permanently prevents the lender from initiating redemption of a previously deposited position, so a lender with a large balance cannot be de-whitelisted in practice.
