### Title
Permissionless `refundRequest`/`cancelRequest` in ProvisionerV2 can never succeed for a blacklisted requester whose refund fallback targets themselves - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2` async deposit/redeem requests are refunded via `_transferWithFallback`, which is meant to protect against a `receiver` transfer reverting (e.g. blacklist) by falling back to the original `requester`. However, when `receiver == requester` (the default for every request created via the standard `requestDeposit`/`requestRedeem` overloads, which set `receiver = msg.sender`), the function skips the protected `trySafeTransfer` path entirely and executes an unprotected `safeTransfer` directly to that same address. If that address is later blacklisted by the underlying ERC20 (e.g. USDC), the transfer reverts unconditionally and permanently, exactly mirroring the Notional M-5 pattern where an unprotected push-transfer inside a supposedly permissionless action blocks it forever.

### Finding Description
`_transferWithFallback` is the shared refund helper used by `refundRequest`, `cancelRequest`, and the deadline-expiry branches of `_solveDepositVaultAutoPrice`/`_solveDepositVaultFixedPrice`/`_solveRedeemVaultAutoPrice`/`_solveRedeemVaultFixedPrice`/`_solveRequestDirect`: [1](#0-0) 

```solidity
function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
    // Interactions: transfer to receiver, fallback to requester on transfer failure
    if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
        token.safeTransfer(requester, amount);
    }
}
```

The intent is: try the safe (non-reverting) transfer to `receiver`; if that fails, fall back to `requester` with a reverting `safeTransfer`. But the `receiver == requester` short-circuit means that for the overwhelmingly common case (a user requests for themselves), the code never even attempts the `trySafeTransfer` path — it goes straight to the unprotected `safeTransfer(requester, amount)`. There is no further fallback if that reverts.

`refundRequest` is fully permissionless (callable by anyone once `request.deadline < block.timestamp`): [2](#0-1) 

It routes into `_clearHashAndTransferRefund` → `_transferWithFallback`: [3](#0-2) 

Requests are created with `receiver = msg.sender` by default via the legacy overloads: [4](#0-3) 

If a user's address (or the tokens they hold rights to, e.g. USDC) becomes blacklisted after creating a deposit request (holding their escrowed `token`) or a redeem request (holding their escrowed vault units), any attempt — by anyone — to refund or cancel that specific request via `refundRequest`/`cancelRequest` will revert unconditionally at `token.safeTransfer(requester, amount)`, because `receiver == requester` skips the safe-try path. The `asyncRequestHashes` entry is only cleared atomically with a successful transfer, so the revert leaves the request permanently un-refundable and the escrowed tokens/units permanently stuck in the contract, with no alternate withdrawal path exposed to ordinary users.

### Impact Explanation
The user's escrowed deposit tokens (for a pending deposit request) or vault units (for a pending redeem request) become permanently frozen in `ProvisionerV2` with no way for the user, a solver, or any third party to retrieve them through any public function, since every refund/cancel path for that request funnels through the same unprotected `_transferWithFallback` self-transfer. This matches a live Immunefi "freezing of user funds" impact (funds locked without recourse), consistent with Medium/High severity depending on duration and permanence of the freeze.

### Likelihood Explanation
Requires only that: (1) a user creates a standard async deposit or redeem request (the default path sets `receiver == msg.sender`), and (2) that user/address is later blacklisted by the deposit/redeem ERC20 (USDC blacklisting is a well-known, frequently exercised real-world event, not a hypothetical). No privileged role, collusion, or unusual gas/oracle assumptions are needed — this is a standard ordinary-user flow using an in-scope, bounty-relevant asset (USDC-style tokens are explicitly supported deposit/redeem tokens for `ProvisionerV2`).

### Recommendation
Do not skip the safe-try step when `receiver == requester`; instead attempt `trySafeTransfer` to the target address regardless, and if that also fails, provide an authorized/admin recovery path (e.g., allow `requiresAuth` to redirect the refund to an alternate address, or hold the funds in an internal claimable balance mapping keyed by the frozen address that can be claimed to any address the user controls) rather than reverting the entire refund transaction unconditionally.

### Proof of Concept
1. Deploy `ProvisionerV2` wired to a `MultiDepositorVault` with a mock USDC-like ERC20 that supports `blacklist(address)` and reverts `transfer`/`transferFrom` to/from blacklisted addresses.
2. As user `alice`, call `requestDeposit(token, tokensIn, minUnitsOut, solverTip, deadline, maxPriceAge, isFixedPrice)` (legacy overload) — this stores an `asyncRequestHashes` entry with `receiver == alice`.
3. Blacklist `alice` on the mock token.
4. Let `request.deadline` elapse, then call `refundRequest(token, request)` from any address (e.g. `bob`).
5. Assert the call reverts (e.g. `vm.expectRevert()`), and assert `asyncRequestHashes[requestHash]` is still `true` and the token balance held by the Provisioner for `alice`'s escrowed amount is unchanged and unrecoverable via `cancelRequest` (also reverts, same root cause) — demonstrating the funds are permanently frozen.

    function refundRequest(IERC20 token, RequestV2 calldata request) external nonReentrant {
        // Requirements: deadline is in the past or authorized
        require(
            request.deadline < block.timestamp || isAuthorized(msg.sender, msg.sig),
            Aera__DeadlineInFutureAndUnauthorized()
        );

        if (_isRequestTypeDeposit(request.requestType)) {
            // Effects + interactions: clear hash, emit refund event, and transfer full token amount with fallback
            _clearHashAndTransferRefund(token, request, request.user, request.tokens, token);

            // Effects + interactions: clear hash, emit refund event, and transfer full unit amount with fallback
            _clearHashAndTransferRefund(token, request, request.user, request.units, IERC20(MULTI_DEPOSITOR_VAULT));
        }
    }

    function _clearHashAndTransferRefund(
        IERC20 token,
        RequestV2 calldata request,
        address requester,
        uint256 amount,
        IERC20 transferToken
    ) internal {
        bytes32 requestHash = _getRequestHash(token, request);
        // Requirements: hash has been set
        require(asyncRequestHashes[requestHash], Aera__HashNotFound());
        // Effects: unset hash as used
        asyncRequestHashes[requestHash] = false;
        // Interactions: transfer amount to receiver, fallback to requester on transfer failure
        _transferWithFallback(transferToken, requester, request.receiver, amount);

        // Log refund event
        if (_isRequestTypeDeposit(request.requestType)) {
            emit DepositRefunded(requestHash);
        } else {
            emit RedeemRefunded(requestHash);
        }
    }
