### Title
ERC-777 deposit hook reentrancy inflates mid-epoch tranche minting - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
`depositDuringEpoch` accepts an attacker-controlled token-transfer callback before it mints tranche tokens, while it has already cached the pre-callback tranche supply. A KYC-passed attacker can reenter `requestWithdraw`, burn nearly their entire existing tranche balance, and cause the outer deposit to mint shares using stale supply against post-withdrawal NAV. This can mint substantially more tranche tokens than the deposit should receive and divert future vault recoveries from honest claimants.

### Finding Description
`depositDuringEpoch` reads `_trancheTotSupply` before calling `_transferUnderlyingsFrom`, but calculates and mints shares only after that external token call returns [1](#0-0) [2](#0-1) . Neither `depositDuringEpoch` nor `requestWithdraw` carries a `nonReentrant` modifier [3](#0-2) [4](#0-3) .

With an ERC-777-style underlying, the `transferFrom` callback can invoke `requestWithdraw(0, AATranche)`. That request resolves the caller’s entire tranche balance, registers the receipt in `IdleCreditVault`, and then `_withdrawOps` burns the tranche and reduces live NAV [5](#0-4) [6](#0-5) . The resumed deposit still uses the pre-callback supply while `expectedFinal` is derived from the reduced post-withdrawal NAV, so `_minted` can be inflated by approximately `oldSupply / remainingSupply`, potentially without bound if the attacker withdraws nearly all of their pre-existing position [7](#0-6) .

### Impact Explanation
The broken invariant is fair minting and solvency: the attacker contributes only `_amount`, while the inflated tranche balance represents a materially larger claim on borrower repayments and strategy recovery. At epoch settlement, those excess shares dilute honest tranche holders and can claim assets that were reserved for legitimate withdrawals; the direct loss is approximately the excess minted shares multiplied by the post-stop tranche price [8](#0-7) . The receipt created during reentrancy is separately cleared before payout, so this is not merely a second use of the same receipt [9](#0-8) .

### Likelihood Explanation
The attacker only needs a KYC-allowed wallet, an existing tranche position, and a configured underlying that invokes sender or recipient transfer hooks. The vulnerable mode requires an active epoch, mid-epoch deposits enabled, AYS disabled, fixed-APR rather than programmable-borrower mode, and nonzero expected epoch interest to preserve a post-withdrawal denominator [10](#0-9) [11](#0-10) . KYC, epoch gating, donation skimming, and accounting updates do not prevent the nested call because both entry points are authorized and unguarded [12](#0-11) .

### Recommendation
Apply `nonReentrant` to `depositDuringEpoch`, `requestWithdraw`, deposit claims, withdrawal claims, and other externally reachable mutable paths that can call an ERC-777-style token. More narrowly, move the external transfer until after all pricing inputs are post-transfer state, or read supply, NAV, expected interest, and remaining time only after `_transferUnderlyingsFrom` returns. Prefer balance-delta accounting as in the ordinary deposit path rather than trusting the requested amount [13](#0-12) .

### Proof of Concept
```solidity
// Foundry fork test sketch for a hooking underlying deployment.
function testMidEpochDepositReentrancyInflatesMint() public {
    // Pool is fixed-APR, non-programmable, AYS disabled,
    // depositDuringEpoch enabled, epoch running, expectedEpochInterest > 0.
    uint256 initial = 1_000e6;
    uint256 depositAmount = 1e6;

    token.mint(attacker, initial + depositAmount);
    vm.startPrank(attacker);
    token.approve(address(cdo), type(uint256).max);

    // Before epoch start, attacker owns a material AA position.
    cdo.depositAA(initial);
    vm.stopPrank();
    startEpoch();

    // ERC777 tokensToSend hook invokes attack() during transferFrom.
    HookToken(address(token)).setCallback(
        attacker,
        abi.encodeCall(IdleCDOEpochVariant.requestWithdraw, (0, address(aaTranche)))
    );

    vm.prank(attacker);
    uint256 minted = cdo.depositDuringEpoch(depositAmount, address(aaTranche));

    // The outer call used supply cached before requestWithdraw burned the position.
    assertGt(minted, expectedSequentialMint);
}
```

The hook executes `requestWithdraw(0, AATranche)` while the outer call is paused at `transferFrom`; `0` selects the attacker’s full tranche balance [5](#0-4) . After stopping the epoch and funding claims, compare the attacker’s aggregate payout with the sequential `withdraw-then-deposit` result; the reentrant path’s excess tranche balance and payout quantifies the theft.
