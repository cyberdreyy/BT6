### Title
Stale per-epoch instant-withdraw basis is never cleared on normal claim, permanently freezing recovery claims after a same-epoch default - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays the aggregate `instantWithdrawsRequests[_user]` and zeroes it, but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. If the borrower later defaults in that same epoch, `_claimDefaultedInstantWithdrawRequest` "dequeues" the already-consumed (freed) per-epoch receipt again, underflows on `instantWithdrawsRequests[_user] -= claimBasis` / `_burn(_user, claimBasis)`, and reverts — permanently freezing the user's legitimate defaulted-epoch instant recovery claim and corrupting `instantWithdrawClaimsByEpoch`/reserve accounting. This is the credit-vault analog of CVE-2025-37823's hfsc UAF: a node removed from the live list is still reachable through a stale per-epoch pointer.

### Finding Description
In the normal claim path (`IdleCreditVault.sol` L380-393):

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedFundsClaim(_user, amount);
```

only the aggregate counter is reset. The per-epoch records written in `requestInstantWithdraw` (L371-372) — `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` — are left populated, like a class node dequeued from the active list but still linked in the scheduler tree.

After a default is finalized for epoch `E`, `claimInstantWithdrawRequest` first runs `_claimDefaultedInstantWithdrawRequest` (L842-856), which reads the stale entry:

```solidity
claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
...
instantWithdrawsRequests[_user] -= claimBasis;   // underflow if prior claim zeroed it
_burn(_user, claimBasis);                        // burns already-consumed receipt tokens
```

If the user claimed a funded instant withdrawal in epoch `E` and then opened a new instant request in the same epoch `E` before the borrower defaulted at that epoch's `stopEpoch`, `claimBasis` includes the already-paid amount while `instantWithdrawsRequests[_user]` and the user's strategy-token balance only reflect the newer request. Both the subtraction and the burn revert under checked arithmetic, so `claimInstantWithdrawRequest` can never succeed for that user.

The same stale entry also inflates `instantWithdrawClaimsByEpoch[defaultEpoch]` (only decremented on default claim), so default-finalization accounting that treats `defaultEpoch` instant claims as pending over-reserves `defaultRecoveryReserve`, shrinking what other claimants can recover.

### Impact Explanation
- Permanent freezing of unclaimed recovery: any user who made ≥2 instant-withdraw requests in the defaulted epoch and claimed an earlier funded one can never execute `_claimDefaultedInstantWithdrawRequest` — the function always reverts, so their legitimate haircutted recovery payout from `defaultRecoveryReserve` is frozen forever (no admin recovery path exists for per-epoch claim state).
- Reserve misallocation: `instantWithdrawClaimsByEpoch[defaultEpoch]` permanently overcounts pending instant claims by the already-paid amount, causing default finalization to over-reserve for instant claimants and under-distribute to normal withdraw claimants (loss borne by other users' recovery share).
- Quantified loss: the full defaulted-epoch instant claim basis of affected users, e.g. a 100k USDC second request in the default epoch yields a frozen claim of `100k * defaultRecoveryPrice / 1e18`.

### Likelihood Explanation
No malicious privileged role is required. The trigger sequence uses only honest flows: instant withdrawals enabled, a user claims one funded instant withdrawal mid-epoch, requests a second instant withdrawal in the same epoch, and the borrower honestly fails to repay at that epoch's `stopEpoch` (the default/finalizeDefaultRecovery path, an accepted in-scope scenario). `requestInstantWithdraw` has no guard preventing a second request after a claim, and nothing clears the per-epoch basis on the funded path. Any default occurring in an epoch where at least one instant claim was already consumed hits the revert or the inflated `instantWithdrawClaimsByEpoch`.

### Recommendation
In the non-default branch of `claimInstantWithdrawRequest`, clear the per-epoch records alongside the aggregate: iterate or track the user's instant-request epochs and set `instantWithdrawsRequestsByEpoch[_user][epoch] = 0` and decrement `instantWithdrawClaimsByEpoch[epoch]` (or subtract the claimed amount from the current `epochNumber` bucket at claim time, mirroring `instantWithdrawsRequestsByEpoch`). Alternatively, make `_claimDefaultedInstantWithdrawRequest` cap `claimBasis` at `instantWithdrawsRequests[_user]` / the user's receipt-token balance so stale slices are skipped instead of reverting.

### Proof of Concept
Foundry fork sketch (mode: instant withdrawals enabled; epoch phase: running → defaulted → finalized):

```solidity
// Setup: epoch E running, instant withdrawals enabled via setInstantWithdrawParams
// 1. Attacker/victim U (KYC'd, deposited, holds tranches)
cdoEpoch.requestInstantWithdraw(100e6, address(tranche));   // req A, epoch E
// borrower/manager fund instant claims
vm.prank(manager); cdoEpoch.getInstantWithdrawFunds();      // or collectInstantWithdrawFunds flow
cdoEpoch.claimInstantWithdrawRequest();                      // U paid; instantWithdrawsRequests[U]=0
assert(strategy.instantWithdrawsRequestsByEpoch(U, E) == 100e6); // stale entry remains

// 2. Same epoch E: second instant request
cdoEpoch.requestInstantWithdraw(50e6, address(tranche));     // req B

// 3. Borrower honestly defaults at end of epoch E
vm.warp(cdoEpoch.epochEndDate() + 1);
// finalizeDefaultRecovery path sets defaultRecoveryEpoch = E,
// defaultRecoveryFinalized = true, defaultInstantWithdrawsFinalized = true

// 4. U tries to claim defaulted instant receipt
vm.expectRevert(); // underflow: instantWithdrawsRequests[U](50e6) -= claimBasis(150e6)
cdoEpoch.claimInstantWithdrawRequest();
// Claim permanently frozen; instantWithdrawClaimsByEpoch[E] overcounts by 100e6
```

Note: I verified the stale-entry write (L371), the aggregate-only clear (L387-392), and the defaulted-epoch reread (L844-848), but could not fully trace `finalizeDefaultRecovery` in `IdleCDOEpochVariant.sol` within the search budget to confirm whether `instantWithdrawClaimsByEpoch` is snapshotted at finalization or consumed lazily — either way the per-user underflow in `_claimDefaultedInstantWithdrawRequest` stands on the code shown above.
