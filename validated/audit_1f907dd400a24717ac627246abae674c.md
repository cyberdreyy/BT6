### Title
Any External-Initiator credential can trigger runs of arbitrary jobs by numeric ID via `POST /v2/jobs/:ID/runs` - (File: `core/web/pipeline_runs_controller.go`)

### Summary
`PipelineRunsController.Create` distinguishes "user" callers from "EI" callers by checking the Go type stored at `SessionUserKey`, but `AuthenticateExternalInitiator` also stores a `*clsessions.User{Role: UserRoleRun}` at that same key. As a result, any valid external-initiator credential is treated as `isUser == true` and can trigger `RunJobV2` for any job addressed by its integer ID, with no check that the job is bound to that (or any) external initiator.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered in the `userOrEI` group with `auth.RequiresRunRole(prc.Create)`, authenticated via `AuthenticateExternalInitiator`, `AuthenticateByToken`, or `AuthenticateBySession` [1](#0-0) .

`RequiresRunRole` only checks that `c.user.Role >= Run`; it does not distinguish between a real user session and a pseudo-session created for an EI credential [2](#0-1) .

`AuthenticateExternalInitiator` authenticates the EI token and then sets **both** `SessionExternalInitiatorKey` and `SessionUserKey` to a synthetic `*clsessions.User{Role: clsessions.UserRoleRun}` [3](#0-2) .

In `PipelineRunsController.Create`, the code attempts to gate integer-ID job runs to "users only" via:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
``` [4](#0-3) 

`GetAuthenticatedUser` merely does a type assertion `obj.(*clsessions.User)` on whatever is stored at `SessionUserKey` [5](#0-4) . Because `AuthenticateExternalInitiator` stores the exact same type there, `isUser` evaluates to `true` for EI callers too — the comment's stated intent ("EIs not allowed") is not enforced by the code. No subsequent code path checks `GetAuthenticatedExternalInitiator(c)` to reject this branch, and `RunJobV2` itself takes only a raw `jobID` with no external-initiator binding parameter, so it will attempt to run whatever job that ID maps to regardless of type (cron, OCR, flux monitor, keeper, etc.), not just webhook/EI-bound jobs.

Note that the legacy webhook-by-UUID path has been explicitly removed and returns `422 job.ErrJobTypeRemoved` for any UUID-style ID [6](#0-5) , and this is confirmed by `TestRunner_WebhookJobRemoved`, which shows an EI POST to a webhook job's UUID route yields `422` and no pipeline run is created [7](#0-6) . However, that test only exercises the UUID (webhook) branch. It does not cover the integer-ID branch, where the `isUser` bypass described above allows an EI credential to reach `RunJobV2` for **any** job type addressable by an int32 ID — there is no equivalent test asserting rejection of an EI-authenticated request against a non-webhook job's integer ID, and no code that would produce that rejection.

### Impact Explanation
An attacker holding any external-initiator credential (even for a low-trust, unrelated initiator never associated with the target job) can force execution of arbitrary jobs identified by their integer ID — including OCR, flux-monitor, cron, or keeper jobs that were never intended to accept external triggers. This breaks the invariant that "requests are bound to exactly one authorized job" and can cause unauthorized pipeline executions, potentially resulting in unwanted on-chain transactions, resource exhaustion, or interference with scheduled job cadence — matching the "unauthorized job run" impact class.

### Likelihood Explanation
The only precondition is possession of any valid external-initiator credential pair (`OCR-EI-ACCESSKEY` / `OCR-EI-SECRET` equivalent headers), which is a low-trust credential by design (meant only to trigger webhook jobs). No admin/operator access is required. The exploit is a single unauthenticated-relative-to-jobs HTTP POST with a numeric job ID, fully repeatable and requiring no timing or race conditions.

### Recommendation
In `PipelineRunsController.Create`, explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and reject (or separately re-verify EI-to-job binding) before allowing the integer-ID `RunJobV2` path — i.e., use a dedicated context flag/type (not reusing `*clsessions.User`) to distinguish EI-derived pseudo-sessions from genuine user sessions, and/or verify that the target job's spec type accepts external triggers and is explicitly bound to the presented EI identity before calling `RunJobV2`.

### Proof of Concept
1. Create a non-webhook job (e.g., a cron or fluxmonitor job spec) via `POST /v2/jobs` as an edit-role user; record its integer `ID`.
2. Register/insert an external initiator unrelated to that job (e.g., via `cltest.MustInsertExternalInitiator` / `CreateExternalInitiatorViaWeb`), obtaining `AccessKey`/`Secret`.
3. Send `POST /v2/jobs/{ID}/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` (per `static.ExternalInitiatorAccessKeyHeader/SecretHeader`) set to the EI credentials from step 2, and no session/API-token headers.
4. Assert current (vulnerable) behavior: HTTP 200 with a `pipelineRun` resource created for the cron/fluxmonitor job (`prc.App.RunJobV2` succeeds), i.e. `cltest.AssertCount(t, db, "pipeline_runs", 1)`.
5. Expected secure behavior: the server should reject the run with `401/403` because the job type does not accept external-initiator triggers or is not bound to the presented EI, and `pipeline_runs` count should remain `0` (mirroring the assertion pattern used in `TestRunner_WebhookJobRemoved`) [8](#0-7) .

func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
