### Title
PowerShell here-string interpolation in `PsWriter.DotEnvVariables` allows command injection via unescaped `$`/backtick in dotenv variable values - (File: shells/powershell.go)

### Summary
`PsWriter.DotEnvVariables` embeds the output of `helpers.DotEnvEscape` directly inside a PowerShell double-quoted here-string (`@"..."@`), which PowerShell still expands for `$variable` and `$(...)` subexpressions. `DotEnvEscape` only escapes characters required by the `.env`/godotenv format (`\`, `"`, `\n`, `\r`) and does not neutralize PowerShell metacharacters, so a crafted variable value containing `$(...)` is executed as PowerShell code when the generated script runs.

### Finding Description
`helpers.DotEnvEscape` (helpers/shell_escape.go:146-167) escapes only backslashes, double quotes, `\n`, and `\r` via `escapeDotEnvValue` (helpers/shell_escape.go:139-144), matching what the `godotenv` parser needs to safely round-trip a `.env` file. It performs no escaping of PowerShell-significant characters such as `$` or the backtick `` ` ``.

`PsWriter.DotEnvVariables` (shells/powershell.go:465-472) takes this escaped text and writes it verbatim into a PowerShell script using a double-quoted here-string: [1](#0-0) 

In PowerShell, `@"..."@` (double-quoted here-string) is subject to the same expansion rules as a double-quoted string: `$name` variable expansion and `$(expression)` subexpression evaluation are both performed, unlike a single-quoted here-string (`@'...'@`), which is verbatim. Every other quoting helper in this file (`psDoubleQuote`, `psQuoteVariable`, `psSingleQuote`) is aware of this and escapes `` ` `` and `$` before interpolation-sensitive contexts, e.g. `psQuoteVariable` at shells/powershell.go:245-250. `DotEnvVariables` is the only writer method that bypasses this quoting discipline by concatenating raw, non-PowerShell-aware escaped text into an interpolating here-string.

If a variable value contains `$(<PowerShell command>)`, e.g. a key/value produced from a job's `artifacts:reports:dotenv` output or any other map fed into `DotEnvVariables`, that subexpression survives `DotEnvEscape` untouched (it contains no `\`, `"`, `\n`, or `\r`) and is evaluated by PowerShell at the moment the generated `[System.IO.File]::WriteAllText(...)` line executes — before the file is even written to disk.

### Impact Explanation
Arbitrary PowerShell command execution in the build's shell context at the point the dotenv file is (re)written, triggered purely by the *content* of variable values rather than by any script the job author explicitly wrote. Since dotenv-style variables (e.g. from `artifacts:reports:dotenv`) are documented as being treated as plain string values, not executable code, a downstream consumer of such a map (any code path that re-serializes a variables map through `DotEnvVariables`) gets unintended code execution driven by data that is supposed to be inert.

### Likelihood Explanation
Exploitation only requires an unprivileged pipeline author to set a variable/dotenv value containing `$(...)`, e.g. `MYVAR=$(Remove-Item -Recurse -Force C:\)`. No special CI configuration, admin access, or non-default settings are needed beyond using the PowerShell/pwsh shell (Windows shell or docker-windows executor) and a code path that calls `DotEnvVariables` with attacker-influenced content. This is straightforward and repeatable.

### Recommendation
Do not embed raw `DotEnvEscape` output inside a PowerShell double-quoted here-string. Either:
- Switch to a single-quoted (verbatim) here-string `@'...'@` and adjust escaping to only double embedded single quotes (PowerShell verbatim-string rule), or
- Pass the dotenv content through `psQuoteVariable`/backtick-escaping (or write it via a base64-encoded byte array, as is already done in `generateSaveScript`) so `$` and `` ` `` cannot trigger expansion regardless of the surrounding quoting construct.

### Proof of Concept
Go unit test extending `shells/powershell_test.go`:
```go
func TestDotEnvVariables_NoPowerShellInjection(t *testing.T) {
    w := &PsWriter{Shell: SNPwsh, EOL: "\n", TemporaryPath: `C:\tmp`}
    vars := map[string]string{
        "EVIL": `$(Write-Output INJECTED)`,
    }
    w.DotEnvVariables("out.env", vars)
    script := w.String()

    // The raw, unescaped subexpression must not appear verbatim inside
    // an interpolating here-string.
    assert.NotContains(t, script, `$(Write-Output INJECTED)`)
}
```
This test fails against the current implementation because the here-string is double-quoted (`@"..."@`) and `DotEnvEscape` does not neutralize `$(...)`. A fuller integration PoC would execute the generated script with a mocked `pwsh`/`powershell.exe` and assert that `INJECTED` is printed to stdout, proving code execution driven purely by variable content.

func (p *PsWriter) DotEnvVariables(baseFilename string, variables map[string]string) string {
	p.MkDir(p.TemporaryPath)
	dotEnvFile := p.TmpFile(baseFilename)

	p.Linef("[System.IO.File]::WriteAllText(%s, @\"\n%s\n\"@)", p.resolvePath(dotEnvFile), helpers.DotEnvEscape(variables))

	return dotEnvFile
}
