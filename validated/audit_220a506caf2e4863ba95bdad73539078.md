### Title
Accrued yield is retroactively re-split when `setTrancheAPRSplitRatio` changes the AA/BB split without first settling accounting — (File: contracts/IdleCDO.sol)

### Summary
`IdleCDO.setTrancheAPRSplitRatio()` overwrites `trancheAPRSplitRatio` without calling `_updateAccounting()` first. Because `_virtualPriceAux` splits the *entire* gain accumulated since the last settlement (`getContractValue() - lastNAV`) using the *current* `trancheAPRSplitRatio`, any yield accrued under the old ratio is redistributed under the new one at the next deposit/withdraw/harvest. A holder of the newly favored tranche captures yield that economically belongs to the other tranche class — the same bug class as `CouncilMember.updateID()`/`updateTarget()` mutating stream parameters without calling `_retrieve()`.

### Finding Description
In `IdleCDO.sol`, `_updateAccounting()` snapshots `trancheAPRSplitRatio` and passes it to `_virtualPriceAux`, which computes `totalGain = nav - lastNAV` (all interest accrued since the previous settlement) and splits it: `totalBBGain = totalGain * (FULL_ALLOC - _trancheAPRSplitRatio) / FULL_ALLOC`. The ratio stored at settlement time therefore applies retroactively to yield earned while a different ratio was in force.

`setTrancheAPRSplitRatio` (IdleCDO.sol:899-903) does only:

```solidity
function setTrancheAPRSplitRatio(uint256 _trancheAPRSplitRatio) external virtual {
  _checkOnlyOwner();
  _checkAmountTooHigh((trancheAPRSplitRatio = _trancheAPRSplitRatio) > FULL_ALLOC);
}
```

There is no `_updateAccounting()` call before the write, so a pending, unsplit gain survives the parameter change and is distributed under the new split. Contrast with `setFeeParams` in `IdleCDOCreditVault.sol` (lines 461-470), which correctly calls `_accrueManagementFee()` *before* updating `fee`/`feeSplit`/`managementFee` — the codebase itself acknowledges the settle-before-mutate invariant for management fees, but the analogous protection is missing for the yield split ratio (and for `setMinAprSplitAYS`/`setIsAYSActive`, which can also flip the effective split via `_updateSplitRatio`).

Attack path (running epoch, AYS disabled so the owner-managed ratio is live):

1. Lenders have deposited into AA and BB; `lastNAVAA`/`lastNAVBB`/`priceAA`/`priceBB` are settled. The strategy accrues a gain `G` that sits unsplit between `lastNAV` and `getContractValue()`.
2. The honest owner executes a planned rebalance: `setTrancheAPRSplitRatio(newRatio)` where `newRatio < oldRatio` (more yield to BB).
3. An unprivileged attacker holding BB (a normal KYC-passed tranche holder) simply waits. On the next user interaction, `_updateAccounting()` runs and splits all of `G` under `newRatio`, so the attacker and other BB holders receive `G * (oldRatio - newRatio) / FULL_ALLOC` of AA's accrued yield.
4. The attacker calls `withdrawBB(0)`, burning at the inflated `priceBB` and redeeming more underlying than they are owed; AA holders' `priceAA` is permanently lower by the same amount.

The broken invariant is fair mint/burn / yield attribution: interest must be split under the ratio in force while it accrued. No guard prevents this: `_checkDefault` passes (gain, not loss), `skipDefaultCheck` is irrelevant, and `_updateSplitRatio` is bypassed because AYS is off.

### Impact Explanation
Direct redistribution/theft of unclaimed yield. Loss magnitude is exactly `G * |newRatio - oldRatio| / FULL_ALLOC`, where `G` is the unsplit gain. With e.g. a 10,000e18 pending gain and a 20% ratio shift, ~2,000e18 underlying moves from AA holders to BB holders at the next settlement. The favored-tranche holder (the attacker) withdraws the stolen amount; the disfavored tranche's loss is permanent.

### Likelihood Explanation
Requires an honest owner call to `setTrancheAPRSplitRatio` (or a `setMinAprSplitAYS`/`setIsAYSActive` change that moves the effective split) while an unsplit gain exists — a routine configuration action — and an attacker holding the favored tranche, which needs only to be a pre-existing holder (or to have deposited in a prior settlement window). No privileged attacker, no oracle manipulation, no default needed. It cannot be exploited *on demand* (the attacker cannot trigger the parameter change), so likelihood is moderate rather than high.

### Recommendation
Call `_updateAccounting()` (via `_forceUpdateAccounting()` semantics if the default path must be tolerated) at the top of `setTrancheAPRSplitRatio`, `setMinAprSplitAYS`, and `setIsAYSActive` so all accrued yield/loss is crystallized under the old parameters before they change — mirroring the `_accrueManagementFee()`-first pattern already used in `setFeeParams`.

### Proof of Concept
Reproducible Foundry fork/unit PoC outline (against `contracts/IdleCDO.sol`):

```solidity
// test/SetSplitRatioRetroactive.t.sol
function test_retroactiveSplit_stealsAccruedYield() public {
    // 1. Setup: IdleCDO with isAYSActive = false, fee = 0 for clarity.
    //    Alice deposits 1_000_000e6 into AA, attacker deposits 1_000_000e6 into BB.
    //    trancheAPRSplitRatio = 50_000 (50% of gain to AA).
    idleCDO.setIsAYSActive(false);
    idleCDO.setTrancheAPRSplitRatio(50_000);
    depositAA(alice, 1_000_000e6);
    depositBB(attacker, 1_000_000e6);
    // settlement: lastNAVAA = lastNAVBB = 1e6, priceAA = priceBB = 1e18

    // 2. Strategy gains 200_000e6 (mock strategy price increase);
    //    NO deposit/withdraw/harvest yet -> gain is unsplit.
    mockStrategy.setPrice(/* +10% => getContractValue() = 2_200_000e6 */);

    // Baseline: if accounting ran now, AA gets 50%: priceAA ~ 1.1e18.
    uint256 priceAAExpected = idleCDO.virtualPrice(AATranche);

    // 3. Owner rebalance: drop AA split to 30_000 WITHOUT settling.
    idleCDO.setTrancheAPRSplitRatio(30_000);

    // 4. Attacker triggers settlement with a dust deposit (or any user does),
    //    then withdraws all BB.
    depositBB(attacker, 1e6);
    uint256 bbBal = IERC20(BBTranche).balanceOf(attacker);
    uint256 redeemed = withdrawBB(attacker, bbBal);

    // 5. Assertions: AA price is now ~1.06e18 instead of ~1.10e18;
    //    the 80_000e6 delta moved to BB holders.
    assertLt(idleCDO.virtualPrice(AATranche), priceAAExpected);
    assertGt(redeemed, 1_000_000e6 + 100_000e6 - dustTolerance);
    // i.e. attacker captured > his 50% share (100k) — ~140k total.
}
```

Notes/caveats: the parameter mutation is an honest-owner action per scope rules; the unprivileged attacker merely holds the favored tranche and sequences their withdrawal after the owner's call. The same retroactive-parameter class applies to `setMinAprSplitAYS`/`setIsAYSActive` (ratio changes through `_updateSplitRatio`) and, partially, to the `fee` leg of `setFeeParams` (the management fee is settled first but the performance `fee` applies to the whole pending gain at the next `_updateAccounting`). I verified the code path in `contracts/IdleCDO.sol` and `contracts/IdleCDOCreditVault.sol`; the exact setter inventory on `IdleCDOCreditVault` (lines before 420) was not fully read, so whether the credit vault exposes an equivalent unsettled ratio setter is not confirmed — the finding stands on `IdleCDO.sol` either way.
