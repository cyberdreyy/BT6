## Analysis: Hardcoded prefix limit in `tokensanitizer.New` silently disables secret masking beyond 15 entries

The Convex report describes a hardcoded array-size ceiling (2 vs. up to 12) that silently limits functionality without erroring, forcing redeployment for excess items. The equivalent pattern class ("hardcoded cap silently drops legitimate extra items") does exist in GitLab Runner's build log masking pipeline.

### Title
Silent truncation of secret-masking token prefixes beyond a hardcoded limit of 15 - (File: `common/buildlogger/internal/tokensanitizer/token_masker.go`)

### Summary
`tokensanitizer.New` caps the number of token prefixes it will build masking writers for at 15, silently discarding any prefixes beyond that count instead of erroring or warning. [1](#0-0)  Since the effective prefix list is the union of GitLab's built-in default prefixes and any additional job-supplied `MaskTokenPrefixes`, any prefixes beyond the 15th slot are never masked in job output.

### Finding Description
`New` builds one filtering writer per prefix, but truncates the input slice with `count := min(len(prefixes), 15)`, and the code comment itself acknowledges the trade-off ("We only allow 10 token prefixes at the moment. Everything else is being silently ignored" — note the comment says 10 while the code enforces 15, indicating the limit has been bumped before without full review). [1](#0-0) 

The prefix list passed into `New` is constructed in `buildlogger.New` as the union of job-configured `opts.MaskTokenPrefixes` and GitLab's `DefaultTokenPrefixes`: [2](#0-1) 

`DefaultTokenPrefixes` alone already contributes up to 14 entries when `MaskAllDefaultTokens` is enabled (`glpat-` plus 13 more prefixes such as `gloas-`, `gldt-`, `glrt-`, etc.): [3](#0-2)  This leaves only one free slot before the hardcoded 15 ceiling is reached. Any additional prefixes supplied via job configuration (`Options.MaskTokenPrefixes`, populated from `common/build.go`) beyond that single remaining slot are dropped without any log, error, or fallback masking strategy.

### Impact Explanation
If the combined prefix count (defaults + job-supplied) exceeds 15, the excess prefixes are effectively unprotected: any secret matching those dropped prefixes will be written to the job trace/log in plaintext instead of being replaced with `[MASKED]`. Job traces can be visible to a wider audience than the secret owner intended (e.g., other project members, or wider audiences on public projects), so an unmasked secret leaking into logs is a genuine credential-disclosure risk, structurally analogous to the reward-token truncation in the original report where excess configured items were silently unsupported.

### Likelihood Explanation
Likelihood is low-to-moderate and requires a specific condition: `MaskAllDefaultTokens` enabled (bringing 14 built-in prefixes) combined with the job supplying 2 or more custom `MaskTokenPrefixes`, or a future increase in GitLab's built-in prefix list (`allTokenPrefixes`) that isn't matched by raising the runner-side 15 cap. Because the cap and default-prefix count are both defined runner-side and could silently drift apart (as evidenced by the stale "10" vs actual "15" comment), this is a maintenance/reachability risk rather than a directly attacker-triggerable one — it depends on GitLab-side configuration (job payload) rather than a hostile input from an untrusted party, so it does not meet a "trusted-role compromise" bar, but it is a real, concretely reachable code path within normal runner operation.

### Recommendation
Remove the hardcoded 15-prefix ceiling in `tokensanitizer.New`, or at minimum emit an explicit warning/error when the prefix list is truncated so operators are aware some secrets will not be masked. Additionally, keep the function's doc comment accurate and add a test asserting that `len(DefaultTokenPrefixes(true)) + expected custom prefixes` never approaches the enforced limit, or make the limit configurable/unbounded to track additions to `allTokenPrefixes`.

### Proof of Concept
1. Configure a runner job with `MaskAllDefaultTokens: true` (14 default prefixes) and add 2 custom `MaskTokenPrefixes` (e.g., `"myorg-secret-"`, `"myorg-secret2-"`) via the job's masking configuration in `common/build.go`.
2. `buildlogger.New` merges these into a 16-entry `maskTokenPrefixes` slice. [4](#0-3) 
3. `tokensanitizer.New` is called with this 16-entry slice; `count := min(len(prefixes), 15)` truncates it to 15, so the 16th prefix (`"myorg-secret2-"`) never gets a `tokenSanitizer` writer built for it. [5](#0-4) 
4. Any log line containing `myorg-secret2-<token>` is written to the job trace in cleartext, unmasked, while lines matching the other 15 prefixes are correctly masked.

```go
func DefaultTokenPrefixes(maskAllDefaultTokens bool) []string {
	tokenPrefixes := []string{"glpat-"}
	if maskAllDefaultTokens {
		tokenPrefixes = append(tokenPrefixes, allTokenPrefixes...)
```

```go
// New returns a new TokenSanitizer.
// We only allow 10 token prefixes at the moment. Everything else is being silently ignored
func New(w io.WriteCloser, prefixes [][]byte) *TokenSanitizer {
	m := &TokenSanitizer{}
	m.next = w

	count := min(len(prefixes), 15)

	for i := 0; i < count; i++ {
		m.next = &tokenSanitizer{next: m.next, prefix: prefixes[i]}
	}

	return m
}
```
