### Title
Stale `builder_pending_withdrawals` entries keep referencing a swept `builder_index`, so slot reuse lets a queued payment drain a new builder's balance to a stranger's `fee_recipient` - (File: specs/gloas/beacon-chain.md)

### Summary
`state.builder_pending_withdrawals` entries carry only a `builder_index` pointer plus the payout `fee_recipient`/`amount`, not the builder's pubkey. `get_index_for_new_builder` allows a builder slot to be reused as soon as `withdrawable_epoch <= current_epoch and balance == 0` — the same "index/slot never cleared of related ledgers" pattern flagged in the Salty report, where an unwhitelisted pool's `_arbitrageProfits` survived to be inherited on re-whitelisting. Here, a stale queued withdrawal that still references the *old* builder's index can be applied against the *new* builder that now occupies that same index, deducting the new builder's Gwei and paying it to the old builder's `fee_recipient`.

### Finding Description
Reuse eligibility is checked only against the builder's current `balance` field: [1](#0-0) 

A builder's full remaining `balance` (which still includes amounts already committed to `builder_pending_withdrawals` but not yet drained from the FIFO queue, since a bid commitment does not decrement `balance` immediately) can be zeroed in one shot by the round‑robin exit sweep: [2](#0-1) 

This sweep runs before the deep FIFO backlog of `builder_pending_withdrawals` (capped per block by `MAX_WITHDRAWALS_PER_PAYLOAD - 1`) has necessarily drained every earlier-queued entry for that builder: [3](#0-2) 

Once `balance == 0` and `withdrawable_epoch <= current_epoch`, `process_builder_deposit_request`/`add_builder_to_registry` will place a brand-new builder into that exact slot: [4](#0-3) 

When the FIFO queue later reaches the stale entry, `apply_withdrawals` resolves the destination `builder_index` purely from the withdrawal's `validator_index` (i.e., the old index), and debits whoever currently occupies that slot: [5](#0-4) 

Nothing in `get_index_for_new_builder`, `add_builder_to_registry`, or `process_builder_deposit_request` checks whether `state.builder_pending_withdrawals` still contains an entry referencing the index being recycled. This mirrors the Salty bug class exactly: an "exit" (unwhitelist / builder exit+sweep) does not clear a per-key ledger (`_arbitrageProfits` / `builder_pending_withdrawals` entries keyed by index), and a subsequent "re-entry" (re-whitelist / new builder deposit reusing the index) inherits stale state that was never meant for it.

### Impact Explanation
This breaks the equality "a builder mutated (its balance decreased) without its authority" and "Gwei paid to a non-owner": the new builder Y's `balance` is unilaterally decremented by `apply_withdrawals` for a debt Y never incurred, and the withdrawn Gwei is sent to `withdrawal.fee_recipient`, which is the old (exited) builder X's designated recipient — a party with no claim on Y's funds. Per the rules, this is a Critical-class impact ("Gwei created, destroyed or paid to a non-owner").

### Likelihood Explanation
Reachability requires: (1) a builder X exits and is swept to `balance == 0` while `builder_pending_withdrawals` still holds an older entry for X that has not yet cycled through the FIFO (plausible when the queue backlog exceeds the per-block processing cap `MAX_WITHDRAWALS_PER_PAYLOAD - 1`); (2) a new builder Y deposits and is assigned X's now-reusable index; (3) the FIFO eventually reaches the stale entry. All three steps are driven purely by ordinary, honest protocol usage (builder deposits/exits/bids) — no malicious peer, coalition, or client bug is needed, only specific timing of deposits/exits relative to queue depth. I could not find, within the portions of `specs/gloas/beacon-chain.md` retrieved, any explicit invariant guaranteeing the pending-withdrawal queue is fully drained for a builder before its slot becomes reusable; this could not be fully confirmed against `settle_builder_payment`'s complete body, which was only partially indexed for this session.

### Recommendation
Either (a) prevent slot reuse while any `builder_pending_withdrawals` entry still references that `builder_index` (scan and reject reuse, or fully drain/settle those entries before considering the index free), or (b) resolve withdrawal destinations and debits by builder pubkey/identity rather than by raw index, so a recycled index cannot be conflated with a different builder's committed payment.

### Proof of Concept
Conceptual sequence over specs/gloas/beacon-chain.md semantics:
1. Builder X (index 5) commits several payload bids; each records a `BuilderPendingWithdrawal(builder_index=5, fee_recipient=X_addr, amount=A)` into `state.builder_pending_withdrawals` via `process_execution_payload_bid`/`settle_builder_payment` faster than the per-block cap can drain them, producing a backlog.
2. X calls `process_builder_exit_request`; `withdrawable_epoch` is set. Later, `get_builders_sweep_withdrawals` (round-robin, independent of FIFO position) finds `builder.withdrawable_epoch <= epoch and balance > 0` for index 5 and withdraws the *entire* current `balance` to `X.execution_address`, setting `state.builders[5].balance = 0` — while the earlier-queued `builder_index=5` FIFO entries are still un-processed further back in `state.builder_pending_withdrawals`.
3. `get_index_for_new_builder` now returns `5` (balance==0, withdrawable_epoch<=epoch). A new builder Y deposits via `process_builder_deposit_request`, and `add_builder_to_registry` places Y at index 5 with `balance = deposit_amount`.
4. On a subsequent block, `get_builder_withdrawals` finally reaches the stale entry `builder_index=5, fee_recipient=X_addr, amount=A`. `apply_withdrawals` computes `builder_index = 5` (now Y), reads `state.builders[5].balance` (Y's balance), and executes `state.builders[5].balance -= min(A, Y_balance)`, sending `A` to `X_addr`.
5. Result: Y's balance is reduced by `A` Gwei with no action or authorization from Y, and that Gwei is paid to X's `fee_recipient` — a direct violation of "Gwei paid to a non-owner" / "builder mutated without its authority".

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],

    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)

    return withdrawals, withdrawal_index, processed_count

def get_builders_sweep_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    epoch = get_current_epoch(state)
    builders_limit = min(len(state.builders), MAX_BUILDERS_PER_WITHDRAWALS_SWEEP)
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    builder_index = state.next_withdrawal_builder_index
    for _ in range(builders_limit):
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder = state.builders[builder_index]
        if builder.withdrawable_epoch <= epoch and builder.balance > 0:
            withdrawals.append(
                Withdrawal(
                    index=withdrawal_index,
                    validator_index=convert_builder_index_to_validator_index(builder_index),
                    address=builder.execution_address,
                    amount=builder.balance,
                )
            )
            withdrawal_index += 1

        builder_index = (builder_index + 1) % len(state.builders)
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

def get_index_for_new_builder(state: BeaconState) -> BuilderIndex:
    for index, builder in enumerate(state.builders):
        if builder.withdrawable_epoch <= get_current_epoch(state) and builder.balance == 0:
            return BuilderIndex(index)
    return BuilderIndex(len(state.builders))

###### New `process_builder_deposit_request`

*Note*: Builder indices are reusable. When a builder exits, its index may later
be reassigned to a different builder with a new public key. Any deposit sent to
an exited builder will be withdrawn to the builder’s execution address. Exited
builders cannot be reactivated, although a newly registered builder’s public key
may have previously appeared in the builder set. Implementations that rely on
caching should account for this behavior.

```python
def process_builder_deposit_request(state: BeaconState, request: BuilderDepositRequest) -> None:
    # Ignore deposits with unexpected withdrawal credential prefixes
    if not is_builder_withdrawal_credential(request.withdrawal_credentials):
        return

    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        if is_valid_builder_deposit_signature(request):
            add_builder_to_registry(
                state,
                request.pubkey,
                PAYLOAD_BUILDER_VERSION,
                ExecutionAddress(request.withdrawal_credentials[12:]),
                request.amount,
                state.slot,
            )
    else:
        builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
        builder = state.builders[builder_index]

        # If exited and swept, reset the withdrawable epoch
        if builder.withdrawable_epoch != FAR_FUTURE_EPOCH and builder.balance == 0:
            epoch = get_current_epoch(state)
            builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY

        # Increase balance by deposit amount
        builder.balance += request.amount
