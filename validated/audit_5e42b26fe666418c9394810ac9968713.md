### Title
Multi-epoch pending withdraw receipts escape `stopEpochWithDuration` haircut and are paid at par, draining the funded claim pool - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` socializes a realized loss across the *aggregate* `pendingWithdraws` basis but records the recovery ratio under a single epoch key (`lossRecoveryPriceByEpoch[epochNumber]`). `_claimLossAdjustedWithdrawRequest` only looks up that price via `lastWithdrawRequest[_user]`, so a receipt whose basis sits in a *different* pending epoch is never haircut: `_clearWithdrawClaimForEpoch` clears only the `lastWithdrawRequest` epoch, and the remaining basis in `withdrawsRequests[_user]` is then paid at par by `_claimFundedWithdrawRequest`. Like the kernel bug (freeing only the pointed-to object while leaking the rest), only the latest epoch's receipt is loss-adjusted while earlier pending basis "leaks" out unfunded.

### Finding Description
- `requestWithdraw` accumulates every request into the global `pendingWithdraws` and into `withdrawsRequestsByEpoch[_user][currentEpoch]`, while `lastWithdrawRequest[_user]` is overwritten with the newest request epoch (`IdleCreditVault.sol:279-293`). Nothing forces a user to claim or fund older pending receipts before adding a new one (the guard at lines 263-271 only triggers when a loss price *already* exists for the last epoch).
- On a lossy `stopEpochWithDuration`, `collectWithdrawFunds` receives `_amount < pendingWithdraws` where `pendingWithdraws` spans *all* pending epochs, stores `pendingWithdraws = 0` and a single `lossRecoveryPriceByEpoch[epochNumber]` (`IdleCreditVault.sol:411-430`).
- On claim, `_claimLossAdjustedWithdrawRequest` reads only `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and `_clearWithdrawClaimForEpoch` clears only that epoch's `withdrawsRequestsByEpoch` slice (`IdleCreditVault.sol:789-837`). The other epochs' basis survives in the `withdrawsRequests[_user]` aggregate.
- `_claimFundedWithdrawRequest` then pays `normalAmount + apr0PrincipalAmount + apr0InterestAmount` — including the never-haircutted earlier-epoch basis — at par via `_transferFundedClaim` (`IdleCreditVault.sol:338-349`, `897-907`).

Broken invariant: loss waterfall / funded-pool solvency. The strategy received `pendingToFund < pendingWithdraws` underlyings, yet claimants whose basis predates `lastWithdrawRequest` withdraw as if fully funded.

### Impact Explanation
An unprivileged tranche holder (or any user able to hold withdraw receipts across two pending epochs) extracts the unfunded haircut difference at par. Concretely: if pending basis is A (epoch N) + B (epoch M) and the borrower funds `(A+B)*(1-h)`, the multi-epoch claimant takes `B*(1-h) + A` — i.e., `A*h` more than funded. That overpayment is borne by the shared funded-claim balance, so later claimants (other users' withdraw receipts, instant-withdraw claimants via `claimInstantWithdrawRequest`, or CDO withdrawals) face an under-reserved vault: their claims revert on insufficient balance. This is direct insolvency/permanent freezing of unclaimed withdrawals, quantified as the sum of pre-last-epoch pending basis times the haircut ratio.

### Likelihood Explanation
Requires pending withdraw receipts from at least two distinct request epochs to coexist when a loss is realized — i.e., a stop that does not fully fund pending receipts (which is precisely the `stopEpochWithDuration(_lossAmount)` mode this code was built for), followed by a user who requested in both epochs. The attacker needs only to hold tranche tokens and call `requestWithdraw` twice across epochs; no privileged role is involved. Note a caveat I could not fully verify within the tool budget: the finding additionally strengthens if `epochNumber` is incremented inside `stopEpoch` before `collectWithdrawFunds` runs, because then even a single-epoch receipt's `lastWithdrawRequest` would not match the `lossRecoveryPriceByEpoch` key and the entire haircut is skipped — this ordering should be confirmed when writing the PoC.

### Recommendation
Track loss recovery per pending epoch rather than per "last" epoch, or iterate all epochs with nonzero `withdrawsRequestsByEpoch[_user]` when claiming, applying `lossRecoveryPriceByEpoch` wherever it is set. Alternatively, store per-epoch global pending basis (`pendingWithdrawsByEpoch`) so `collectWithdrawFunds` can distribute the haircut across every epoch contributing to `pendingWithdraws`, and revert (as `requestWithdraw` already does for the last epoch) whenever a user has *any* pending receipt in an epoch with a recorded loss price and a differing request epoch.

```solidity
// 1. Deposit as attacker (KYC-allowed wallet), receive AA tranche tokens.
// 2. Manager startEpoch(); attacker requestWithdraw(A, tranche) -> lastWithdrawRequest = N.
// 3. Manager stopEpoch / borrower repays interest only so A stays pending
//    (or use a stop that leaves pendingWithdraws unfunded), epochNumber -> N+1.
// 4. Manager startEpoch(); attacker requestWithdraw(B, tranche) -> lastWithdrawRequest = M.
//    Guard at lines 263-271 passes: no lossRecoveryPrice yet.
// 5. Warp past epochEndDate; borrower funds pendingToFund < pendingWithdraws.
//    Manager stopEpochWithDuration(apr, interest, duration, lossAmount)
//    -> collectWithdrawFunds stores lossRecoveryPriceByEpoch[M] = price, pendingWithdraws = 0.
// 6. Attacker calls claimWithdrawRequest via CDO:
//    - _claimLossAdjustedWithdrawRequest pays B * price (haircut applied), clears epoch M,
//      lastWithdrawRequest -> 0.
//    - _claimFundedWithdrawRequest pays A at PAR although it was inside the haircutted
//      pendingWithdraws basis.
// 7. Assert attacker received B*price + A > (A+B)*price, i.e. extracted A*(1-price) of
//    unfunded value; assert a second pending claimant's claim then reverts or is
//    underpaid because the strategy's underlying balance is drained.
```

Key assertions: `strategy.lossRecoveryPriceByEpoch(M) != 0`, `strategy.withdrawsRequestsByEpoch(attacker, N)` still nonzero before step 6, and the strategy's token balance after step 6 is below the remaining funded-claim obligations.
