### Title
Instant-withdraw receipts requested in the buffer epoch are keyed to the wrong epoch at default finalization, permanently freezing their unfunded claim - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`requestInstantWithdraw` records receipts under the *current* `epochNumber` (`instantWithdrawsRequestsByEpoch[_user][epochNumber]`), but `epochNumber` is bumped inside `deposit()` during the *next* `stopEpoch` — including a defaulting stop. When a borrower defaults in the epoch during which an instant withdrawal was only partially funded at `startEpoch`, `defaultRecoveryEpoch` is set to the bumped epoch while the receipt lives under the previous one. `defaultPendingClaimBasis()` then misses the instant basis entirely, and `_claimDefaultedInstantWithdrawRequest` finds zero basis for the user, so the claim falls through to the funded path, which reverts against the reserve guard — permanently freezing the user's unfunded instant claim.

### Finding Description
The external bug is a crash caused by a delayed renegotiation response producing an inconsistent dual state (both audio and T.38 offered, then T.38 declined). The analog is a delayed/partially-funded instant withdrawal straddling an epoch boundary, producing inconsistent dual accounting (receipt recorded in epoch N, recovery keyed to epoch N+1), then the default ("declined") path freezing the claim.

Concretely, in `contracts/strategies/idle/IdleCreditVault.sol`:

1. `requestInstantWithdraw` stores the receipt at `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` (lines 367-372). During the buffer, `epochNumber` is the upcoming epoch N.

2. At `startEpoch`, the CDO calls `collectInstantWithdrawFunds` for whatever cash is available. If the borrower send consumed most funds, only part of the instant queue is funded: `pendingInstantWithdraws` stays > 0 (lines 398-403).

3. The epoch runs and the borrower defaults. `stopEpoch` calls `deposit`, which increments `epochNumber` because `isEpochRunning()` is still true inside the deposit (lines 607-610). `epochNumber` is now N+1.

4. `finalizeDefault` → `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` = N+1 and computes `pendingBasis = defaultPendingClaimBasis()`, which reads `instantWithdrawClaimsByEpoch[epochNumber]` = `instantWithdrawClaimsByEpoch[N+1]` = 0 (lines 644-648, 693). The unfunded instant basis is excluded from `totalBasis`, and `_defaultPrefundedInstantReserve()` also returns 0, so the already-collected instant funds are not reserved (lines 716-723).

5. When the user claims, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` = `[N+1]` = 0 and returns (lines 842-845). It then proceeds to pay `instantWithdrawsRequests[_user]` in full via `_transferFundedClaim`. Since only the partial funded amount F (< claim C, because `pendingInstantWithdraws > 0` implies F < C) sits outside the reserve, the guard `balance - reserve < _amount` reverts with `NotAllowed` (lines 900-904).

### Impact Explanation
Permanent freezing of user funds. Any unprivileged lender whose instant-withdraw request was only partially funded at `startEpoch`, and whose epoch then ends in borrower default, can never claim: `_claimDefaultedInstantWithdrawRequest` clears nothing (wrong epoch key), and the fallback full-claim path reverts because the unfunded remainder (C − F) was never collected into the strategy nor included in `defaultRecoveryReserve`. The receipt tokens and underlying remain locked forever. Additionally, excluding the instant basis from `totalBasis` inflates `defaultRecoveryPrice` for all other claimants, mispricing the recovery distribution.

### Likelihood Explanation
Requires (a) an instant-withdraw request open when `startEpoch` runs, (b) insufficient CDO cash so `collectInstantWithdrawFunds` only partially funds it (borrower draw consumes the rest — a normal occurrence since `startEpoch` sends pooled funds to the borrower), and (c) a borrower default at that epoch's `stopEpoch`. All steps use only honest privileged flows plus ordinary borrower default; the attacker-victim is any KYC'd lender. No attacker action beyond requesting an instant withdrawal is needed.

### Recommendation
Key instant-receipt default accounting by the epoch in which the receipt was created, not the post-stop `epochNumber`. Options: (a) snapshot the pending-instant epoch when `collectInstantWithdrawFunds` runs or when the request is made, and have `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve`/`_claimDefaultedInstantWithdrawRequest` use `epochNumber - 1` (or the stored request epoch) whenever `defaulted()` and the epoch was just bumped; or (b) iterate/merge `instantWithdrawClaimsByEpoch` entries across the last two epochs when `pendingInstantWithdraws != 0` at finalization. Also ensure the prefunded remainder `instantWithdrawClaimsByEpoch[reqEpoch] - pendingInstantWithdraws` is added to `defaultRecoveryReserve` so the funded part is paid at `defaultRecoveryPrice`, not par.

### Proof of Concept
```solidity
// Foundry fork PoC sketch against test/foundry/IdleCreditVault.t.sol harness
function testInstantWithdrawFrozenAfterEpochBumpDefault() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);

    // buffer of epoch 0: user1 requests instant withdraw for half
    vm.prank(user1);
    idleCDO.depositAA(amount);
    uint256 instantAmt = 5_000 * ONE_SCALE;
    // request instant withdraw (CDO-side entrypoint used in tests)
    vm.prank(user1);
    cdoEpoch.requestInstantWithdraw(instantAmt, address(AAtranche));

    // startEpoch: borrower draw leaves only partial cash for instant queue,
    // so collectInstantWithdrawFunds funds only F < instantAmt
    vm.prank(manager);
    cdoEpoch.startEpoch(); // pendingInstantWithdraws stays > 0

    // epoch runs, borrower defaults at stopEpoch -> deposit() bumps epochNumber
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, 0); // borrower repays nothing
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    assertTrue(cdoEpoch.defaulted());

    // finalize recovery with partial recovered amount
    vm.prank(owner);
    cdoEpoch.finalizeDefault(recoveredAmount, recoverySource);

    // user1's receipt was keyed under pre-bump epoch; defaulted claim finds 0,
    // funded-claim path reverts on reserve guard -> claim permanently frozen
    vm.prank(user1);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimInstantWithdrawRequest();
}
```
The assertion that `IdleCreditVault.instantWithdrawsRequestsByEpoch(user1, strategy.defaultRecoveryEpoch()) == 0` while `instantWithdrawsRequests(user1) > 0` confirms the epoch-key mismatch.
