### Title
Node-unreachability in `check_latest_block_in_tenure` causes a signer to sign/pre-commit a block that does not actually confirm the expected tenure tip - (File: stacks-signer/src/chainstate/mod.rs)

### Summary
`SortitionData::check_latest_block_in_tenure` is the shared gate that answers "does this proposed block confirm at least as much of a tenure as we know about?" at proposal time, at validate-ok, and at signing. When it cannot resolve the tenure's tip from the local signer DB, it asks the stacks-node via `client.get_tenure_tip(tenure_id)`. If that RPC call fails for *any* reason (including the node being temporarily unreachable, not just a legitimate 404), the function does not fail closed — it returns `Ok(true)`, i.e. treats the proposal as automatically confirming the tenure's tip.

This mirrors the report's bug class exactly: a call whose failure/inability-to-answer is silently interpreted as a positive result ("success"), rather than causing the caller to fail safe. In the Solidity report, a `call()` to a non-existent contract returns `success = true` by EVM design, and the pool treats that as "the transfer happened." Here, an unreachable/erroring node causes `get_tenure_tip` to be treated as "the tip confirms" — the caller (`check_latest_block_in_tenure`) returns `Ok(true)` exactly as if the node had answered affirmatively.

This return value feeds directly into the equality the rules describe (approved-parent vs. canonical / one-per-height): `check_latest_block_in_tenure`'s result gates whether a tenure-change block's `check_tenure_change_confirms_parent` passes, and whether a same-tenure block's `confirms_latest_block_in_same_tenure` passes, at three separate points:
- proposal validation (`check_proposal`)
- post-validate-ok recheck (`check_block_against_signer_db_state`, called from `handle_block_validate_ok`) [2](#0-1) 
- the final pre-commit-threshold recheck before a signature is emitted (also via `check_block_against_signer_db_state`, called from the pre-commit path) [3](#0-2) 

The design comment in the code itself frames the assumption as a deliberate backstop ("the node's proposal endpoint will validate it anyway"), which is a reasonable defense-in-depth argument. However, the same silent-optimistic-default pattern also appears in the signing-time own-tenure conflict check: [4](#0-3) 
```
OWN -- yes --> TIP{"own tenure confirmed
at ≥ this height?
get_tenure_tip(own tenure)"}
TIP -- yes --> HOLD2["refuse to sign"]:::hold
TIP -- "no — never confirmed" --> SIGN
TIP -- "node unreachable" --> SIGN
```
Here `get_tenure_tip` returning an error (unreachable node) is folded into the same branch as "tip never confirmed," which leads directly to `SIGN` — i.e., the equivocation guard (never sign twice at the same height in the same tenure) is bypassed on a benign network hiccup rather than a genuine safety determination, because the code cannot distinguish "the node truly has no record" from "I couldn't ask."

### Impact Explanation
If the signer's own node is temporarily unreachable or errors while the signer is finishing a pre-commit-threshold recheck or signing-time conflict check, the "assume higher" / "assume unconfirmed" default lets checks that exist specifically to prevent conflicting/duplicate signatures pass silently instead of holding back. Combined with the "own-tenure conflict" TIP branch treating "node unreachable" the same as "never confirmed," a signer could emit a signature for a block that its own tenure's tip actually already supersedes, purely because a query transiently failed — this is the exact class the rules flag as Critical (a signer signing a conflicting block) if the local node's error state can be induced or coincides with a genuine conflict. At minimum it is a soundness gap: a check whose entire purpose is to prevent an equivocation/duplicate signature degrades to "assume OK" on RPC failure instead of "assume not OK" (fail closed), which is the safer default for a check that gates an irrevocable action (a bearer signature, as the code's own documentation states).

### Likelihood Explanation
This does not require a majority of signers or any signer's key — it only requires the local stacks-node RPC call `get_tenure_tip` to fail or time out at the specific moment a proposal/pre-commit/sign-time recheck runs, which is plausible under normal operational conditions (node restart, load, network blip) and is within a single miner's/gossip's ability to time a proposal against, per the analog rules (an attacker/miner can grind proposal timing to coincide with an observed node hiccup on a target signer, especially in low-connection-count deployments). It does not require compromising the node — only exploiting a transient unavailability window.

### Recommendation
- Fail closed on `get_tenure_tip` errors in `check_latest_block_in_tenure`: only treat a definitive 404 ("no blocks in this tenure yet") as evidence, and treat all other errors (connectivity, timeout, 5xx) as `ConnectivityIssues`/rejection rather than `Ok(true)`.
- In the signing-time own-tenure conflict path, do not conflate "node unreachable" with "never confirmed": these should route to distinct outcomes — an unreachable node should hold the signature (as the pre-commit/parent-tenure conflict path already does for other unreachable-node cases), not release it.
- Audit other `Err(...) => return Ok(true)`-style optimistic defaults on node RPC failures in `stacks-signer/src/chainstate/*` and `stacks-signer/src/v0/signer.rs` for the same silent-success-on-failure pattern.

### Proof of Concept
1. A signer receives a tenure-change (or same-tenure) block proposal `B` for tenure `T` whose parent/own-tenure tip is actually higher/equal to `B` on the canonical chain, but the signer's local `signer_db` has no fresher signed/pre-committed record of that tip (e.g., signer restarted or was just added).
2. During `check_latest_block_in_tenure`, the signer's own stacks-node becomes transiently unreachable (restart, disk I/O stall, or induced by flooding — excluded here, but any organic transient failure suffices) when `client.get_tenure_tip(tenure_id)` is called.
3. Per [1](#0-0) , the function returns `Ok(true)`, i.e., "proposal is higher/confirms," bypassing the intended veto.
4. The block proceeds to pre-commit and, at the sign-time own-tenure conflict recheck, the "node unreachable" branch again routes to `SIGN` per [4](#0-3) , so the signer emits a signature over a block it should have held back on, without ever getting an authoritative answer from its node that the block truly confirms the correct tip.
