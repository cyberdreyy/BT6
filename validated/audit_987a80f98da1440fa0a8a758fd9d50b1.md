### Title
Loss-adjusted withdraw receipts escape the haircut boundary via epoch index mismatch in `collectWithdrawFunds` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Archive_Tar bug is a symlink target escaping the extraction root. The in-scope analog is a withdraw receipt escaping its intended *epoch boundary*: `collectWithdrawFunds` records a stop-epoch loss under `lossRecoveryPriceByEpoch[epochNumber]`, while the user's receipt marker `lastWithdrawRequest[_user]` was recorded under the pre-increment epoch. Because `deposit` (called during `stopEpoch` while `isEpochRunning` is still true) already bumps `epochNumber`, the haircut is stored under `epoch N+1` while the receipt sits under epoch `N`. `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest]` (epoch `N`), finds zero, and the receipt falls through to `_claimFundedWithdrawRequest`, which pays the full basis at par.

### Finding Description
- `requestWithdraw` stores `lastWithdrawRequest[_user] = epochNumber` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` at request time (epoch N buffer) (IdleCreditVault.sol:282-293).
- `deposit` increments `epochNumber` when `isEpochRunning` is still true, i.e. during `stopEpoch` (IdleCreditVault.sol:607-610).
- `collectWithdrawFunds` computes the haircut and stores `lossRecoveryPriceByEpoch[epochNumber]` (IdleCreditVault.sol:411-421). If this executes after the epoch increment inside `stopEpoch`, the price is keyed to `N+1`, not `N`.
- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. epoch `N`, gets 0, and returns without clearing anything (IdleCreditVault.sol:789-795).
- `_claimFundedWithdrawRequest` then only requires `epochNumber > lastWithdrawRequest[_user]` (`N+1 > N`, true) and pays `withdrawsRequests[_user]` at par from funded underlyings (IdleCreditVault.sol:326-349).
- The guard in `requestWithdraw` only blocks when `lossRecoveryPriceByEpoch[lastWithdrawRequest] != 0`, so it does not stop a later request either (IdleCreditVault.sol:262-271).

### Impact Explanation
Every loss-adjusted receipt claims 100% instead of `lossRecoveryPrice`, while `stopEpoch` only funded `pendingToFund = pendingBasis - pendingLoss`. The strategy's underlying balance is short by the aggregate `pendingLoss`: early claimants are paid in full at the expense of later receipt holders and active LP NAV — direct theft/insolvency of unclaimed yield, proportional to `_lossAmount * pendingBasis / totalBasis`.

### Likelihood Explanation
Requires a `stopEpochWithDuration`/loss path where pending receipts exist and `collectWithdrawFunds` runs after the epoch increment. Attacker is any KYC-passing lender with a pending request in the loss epoch; no privileged collusion needed. Likelihood hinges on the intra-`stopEpoch` call ordering between `deposit` and `collectWithdrawFunds`, which should be confirmed; if the order is reversed the keying is correct and the issue does not trigger.

### Recommendation
Key the loss price to the epoch the receipts belong to: capture `epochNumber` before any increment (e.g. `epochNumber - 1` semantics, or pass the receipt epoch from `IdleCDOEpochVariant.stopEpoch`), or store `lossRecoveryPriceByEpoch` before calling `deposit` in `stopEpoch`. Alternatively make `collectWithdrawFunds` take an explicit epoch parameter validated against `lastWithdrawRequest` usage.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
