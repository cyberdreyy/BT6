### Title
Stale cached LDAP/OIDC session and API-token roles allow continued privileged access after upstream role revocation - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`ldapAuthenticator.AuthorizedUserWithSession` and `ldapAuthenticator.FindUserByAPIToken` (and the OIDC equivalents) authorize every subsequent request purely from a **role value cached locally** at login/token-creation time, rather than re-checking the upstream LDAP/OIDC identity provider on each request. The only mechanism that reconciles this local role cache with upstream reality is a background sync job gated by `UpstreamSyncInterval`, which defaults to `'0s'` and, contrary to what the config documentation states, is only executed once at node startup rather than on every login/logout. Consequently, if an LDAP/OIDC administrator demotes or deactivates a user (e.g., removes them from the `NodeAdmins` group), any session or API token issued to that user before the change continues to authorize with the old, stale, more-privileged role for the full `SessionTimeout`/`UserAPITokenDuration` window.

and to the OIDC driver's `AuthorizedUserWithSession`/`FindUserByAPIToken`, which read `user_role` from `oidc_sessions`/`oidc_user_api_tokens` populated once at sign-in:
<cite repo="Thankgod67Ikhide/chainlink--003" path="core/sessions/oidcauth/oidc.go" start="349="391" />

The only code path that re-derives roles from the upstream provider and patches these cached tables is `LDAPServerStateSyncer.Work`, run either on a ticker (`UpstreamSyncInterval` non-zero) or once at `Start` if the interval `IsInstant()` (i.e., `'0s'`, the documented default): [2](#0-1) 

The package-level doc comment claims "This sync happens for every auth endpoint hit, and via the defined sync interval" — but no call site invokes `Work`/`Sync` from the authentication request path (`AuthorizedUserWithSession`, `FindUserByAPIToken`); it is only ever invoked from the `LDAPServerStateSyncer`'s own `Start`/`run` ticker loop: [3](#0-2) 

This is the same root-cause pattern as the `TribalChief` bug: a per-user value (multiplier / role) is snapshotted locally at an earlier point in time (deposit / login) and is not re-evaluated against the authoritative, governor/administrator-controlled source (`rewardMultipliers` / upstream LDAP-OIDC group membership) on every subsequent privileged operation (withdraw / authenticated request). Unlike the reported contract bug (which only mishandles multiplier *increases*), here the asymmetric failure runs in the security-critical direction: a role *decrease* (revocation/demotion) silently fails to take effect on already-issued sessions/tokens.

### Impact Explanation
A user demoted from Admin/Edit/Run to a lower role, or fully deactivated/removed from all LDAP/OIDC groups by an administrator, retains their previous elevated role for any session cookie or API token that was issued before the change, for up to `SessionTimeout` (default 15m) or `UserAPITokenDuration` (default 240h/10 days) — unless the operator has separately configured a non-zero, short `UpstreamSyncInterval`. This is an authorization/role-bypass condition: `RequiresAdminRole`/`RequiresEditRole` middleware and GraphQL resolvers such as `authenticateUserIsAdmin` trust the cached role verbatim:

<cite repo="Thankgod67Ikhide/chainlink--003" path="core/web/resolver/auth.go" start="45="55" />

allowing continued admin/edit-level API access (job/spec/key management) for the stale token's lifetime after revocation.

### Likelihood Explanation
Reachable by any already-authenticated, unprivileged-relative-to-current-state actor: no attacker action beyond having previously obtained a valid session/API token before their role was downgraded is required. Because `UpstreamSyncInterval = '0s'` is the documented default and is only run once at node `Start()` (not on a recurring basis, and not per-request despite the doc comment's claim), most deployments that don't explicitly configure a short sync interval are exposed for the entire session/token lifetime.

### Recommendation
Re-validate the user's role against the upstream LDAP/OIDC source (or at minimum, perform the sync `Work()` check) on every `AuthorizedUserWithSession`/`FindUserByAPIToken` call, or enforce a mandatory, short, non-zero default for `UpstreamSyncInterval` and additionally trigger a sync check inline with authentication requests rather than solely from the background ticker, so that role reductions and deactivations take effect immediately rather than being deferred to `SessionTimeout`/`UserAPITokenDuration` expiry.

### Proof of Concept
1. Configure `WebServer.LDAP.UpstreamSyncInterval = '0s'` (default).
2. Admin user logs in; `CreateSession` caches `user_role = 'admin'` into `ldap_sessions`. [4](#0-3) 
3. LDAP administrator removes the user from the `NodeAdmins` group (demotes to `view`).
4. The user's existing session cookie continues to be accepted by `AuthorizedUserWithSession`, which returns the stale cached `admin` role from `ldap_sessions` without contacting the LDAP server: [5](#0-4) 
5. `RequiresAdminRole`-gated endpoints continue to authorize the now-demoted user until the session expires (`SessionTimeout`, default 15m) or `UpstreamSyncInterval` is manually configured and elapses.

func (l *LDAPServerStateSyncer) Start(ctx context.Context) error {
	// If enabled, start a background task that calls the Sync/Work function on an
	// interval without needing an auth event to trigger it
	// Use IsInstant to check 0 value to omit functionality.
	if !l.config.UpstreamSyncInterval().IsInstant() {
		l.lggr.Info("LDAP Config UpstreamSyncInterval is non-zero, sync functionality will be called on a timer, respecting the UpstreamSyncRateLimit value")
		go l.run()
	} else {
		// Ensure upstream server state is synced on startup manually if interval check not set
		l.Work(ctx)
	}
	return nil
}
