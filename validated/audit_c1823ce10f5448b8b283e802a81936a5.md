### Title
`pause()` does not stop user actions: `depositDuringEpoch` and `requestWithdraw` remain callable while the vault is paused - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOCreditVault.pause()` / `emergencyShutdown()` are the guardian's circuit breakers, but on the epoch variant only the ERC4626-style `_deposit` path is gated by `whenNotPaused`. Mid-epoch deposits via `depositDuringEpoch` and queued/instant withdrawals via `requestWithdraw` are gated only by separate flags (`skipDefaultCheck`, `allowAAWithdrawRequest`/`allowBBWithdrawRequest`), which a plain `pause()` does not set. As a result, after the guardian pauses the contract during an emergency, users can still deposit and file withdrawal requests, defeating the pause.

### Finding Description
`pause()` only calls `_pause()` (`contracts/IdleCDOCreditVault.sol:518-521`). The deposit gate is `whenNotPaused` on `_deposit` (`contracts/IdleCDOEpochVariant.sol:644`), so `depositAA`/`depositBB` correctly revert while paused.

However, `depositDuringEpoch` (`contracts/IdleCDOEpochVariant.sol:656-669`) never checks `paused()`. Its guard list is: `isBBDepositEnabled`, `isDepositDuringEpochDisabled`, `skipDefaultCheck`, `isProgrammableBorrower`, `isAYSActive`, `!isEpochRunning`, `block.timestamp >= epochEndDate`, `!isWalletAllowed`. During a running epoch with `isDepositDuringEpochDisabled == false`, none of these change when `pause()` is called, so a whitelisted user can deposit while the contract is paused. Note the code intentionally keeps `paused() == true` during a restored epoch (`restoreOperations` returns early without unpausing when `isEpochRunning`, lines 626-629), confirming `paused()` and "deposits allowed" are deliberately decoupled — so `paused()` must be checked explicitly in `depositDuringEpoch`, and it is not.

Similarly, `requestWithdraw` (guard at lines 740-744) only checks `allowAAWithdrawRequest`/`allowBBWithdrawRequest` and `isWalletAllowed`. `pause()` does not clear those flags (only `_emergencyShutdown` and `_handleBorrowerDefault` do, lines 595-596 and 609-612). So a plain guardian `pause()` leaves withdrawal requests fully open — including the instant-withdraw path at lines 761-769, which burns tranche tokens and creates an instant claim via `creditVault.requestInstantWithdraw`. Any reliance on `pause()` alone (rather than full `emergencyShutdown`) fails to halt user activity.

### Impact Explanation
The pause mechanism is the primary emergency response for an unprivileged-actor-triggered incident (e.g., discovered exploit, oracle/price anomaly detected off-chain by the guardian). While paused, an attacker or any KYC'd user can:

- Continue depositing mid-epoch via `depositDuringEpoch`, minting tranche tokens at the discounted price and gaining a claim on epoch interest that honest users cannot match (deposits are supposed to be halted). If the pause was triggered because of a pending loss or mispriced NAV (`priceAA`/`priceBB` stale), the attacker mints at an unfair price, diluting existing holders.
- File `requestWithdraw` (including the instant-withdraw branch when APR dropped) while paused, locking in principal + projected interest receipts ahead of a loss crystallization. A front-running withdrawal request burns tranche tokens at pre-loss NAV and creates a fixed receipt, escaping loss socialization that the pause was meant to freeze in place.

Loss magnitude: bounded by the tranche NAV that can be exited or deposited at stale prices during the pause window — i.e., up to the difference between pre-loss and post-loss tranche value for the exiting/entering amount, which in a full BB wipe can approach the entire AA exposure that manages to exit before `updateAccounting` is forced.

### Likelihood Explanation
Requires a running epoch with `depositDuringEpoch` enabled (owner-configured) or open withdraw-request flags, plus a guardian/owner `pause()` without `emergencyShutdown`. `pause()` exists precisely as the lighter-weight action ("Pauses deposits" per its NatSpec), so the gap is reachable whenever the guardian pauses without intending a full shutdown. The inconsistency is confirmed by the test at `test/foundry/IdleCreditVault.t.sol:4986-5008`, which only verifies the `emergencyShutdown` flag-clearing path, not a bare `pause()`.

### Recommendation
Add an explicit `paused()` check to `depositDuringEpoch` (revert `NotAllowed` or `Pausable: paused` when `paused()` is true and `skipDefaultCheck` is the emergency state), and either have `pause()` also clear `allowAAWithdrawRequest`/`allowBBWithdrawRequest` or add a `whenNotPaused` guard to `requestWithdraw`. Ensure `requestInstantWithdraw`/`claimWithdrawRequest`/`claimInstantWithdrawRequest` paths in `IdleCreditVault` honor the same pause state so that a single pause truly halts all user-facing flows.

### Proof of Concept
Foundry fork test sketch (based on `test/foundry/IdleCreditVault.t.sol` setup, `_startEpochAndCheckPrices` helper):

```solidity
function testPauseDoesNotStopEpochActions() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);

    vm.startPrank(owner);
    cdoEpoch.setIsAYSActive(false);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);
    vm.stopPrank();
    _startEpochAndCheckPrices(0);

    // Guardian pauses (light action, not emergencyShutdown)
    vm.prank(owner);
    cdoEpoch.pause();
    assertTrue(cdoEpoch.paused());

    // Ordinary deposits are blocked
    vm.expectRevert(bytes("Pausable: paused"));
    idleCDO.depositAA(ONE_SCALE);

    address user = makeAddr('paused-user');
    deal(defaultUnderlying, user, 1_000 * ONE_SCALE);
    vm.startPrank(user);
    underlying.approve(address(cdoEpoch), type(uint256).max);
    _whitelist(user);

    // BUG: mid-epoch deposit succeeds while paused
    cdoEpoch.depositDuringEpoch(1_000 * ONE_SCALE, address(AAtranche));
    assertGt(AAtranche.balanceOf(user), 0, 'deposit minted while paused');

    // BUG: withdraw request succeeds while paused
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.stopPrank();
}
```

Expected: both calls revert while `paused()` is true. Actual: both succeed because neither function consults `paused()` nor the flags set by `pause()`.
