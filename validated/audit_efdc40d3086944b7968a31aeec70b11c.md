### Title
Cheap, repeated invalid reorg-attempt proposals let the current miner indefinitely refresh signer-side "miner activity" and stall tenure-idle/inactivity handling - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_latest_block_in_tenure` treats *any* block proposal that fails its height/ordering check — including a proposal that is a reorg attempt against an already-signed/pre-committed block — as valid "miner activity" and unconditionally refreshes `last_activity_time` via `signer_db.update_last_activity_time(...)`, even though the proposal itself is rejected. Because this check runs at proposal arrival (before the expensive per-block validation step), a single miner who currently holds the sortition slot can cheaply spam many trivially-invalid, header-only block proposals to keep the signer-side activity timer perpetually fresh, defeating the idle/inactivity-based liveness mechanisms that depend on that timer (e.g. `tenure_idle_timeout`).

### Finding Description
`check_latest_block_in_tenure` in `stacks-signer/src/chainstate/mod.rs` is the shared check used at proposal arrival, at validate-ok, and at signing time (per the flow described in `docs/signer-flows.md` section 7) to decide whether a proposed block confirms the tip the signer expects. [1](#0-0) 

When the proposed block does not exceed the chain length of the last signed/tracked block in that tenure — i.e. it looks like a reorg attempt — the function does not simply reject silently. It checks whether the conflicting block's `signed_group` time is still within `reorg_attempts_activity_timeout`, and if so (or if there is no `signed_group` timestamp yet, i.e. the block is only locally accepted) it calls `signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())` — explicitly documented in-line as "count this invalid block proposal towards valid miner activity" — before returning `Ok(false)` (rejecting the proposal). [2](#0-1) 

A second branch does the same for conflicts with a merely pre-committed (unsigned) block, again stamping activity time even though the proposal is rejected. [3](#0-2) 

Per `docs/signer-flows.md`, this check is executed at proposal arrival, before the node is asked to actually execute/validate the block — i.e. it is one of the cheapest points in the whole pipeline for the sender to hit: [4](#0-3) 

This mirrors the report's bug class exactly: a cheap, repeatable action (here: a signed-but-invalid, near-empty block header proposal, analogous to the "near-zero amount" trades in the Tracer report) is fed into a signer-side aggregate/state variable (`last_activity_time`, analogous to `hourlyTracerPrices[currentHour].trades`) that is meant to represent genuine, meaningful activity. Because every failing reorg-attempt proposal counts equally regardless of its (lack of) real cost or validity, the sole party who can currently produce a validly-signed proposal for this tenure — the winning miner of that sortition slot — can spam such proposals to keep `last_activity_time` perpetually "fresh," even though it is never producing a valid, advancing block.

### Impact Explanation
`last_activity_time` is the input to the idle/inactivity timeout logic (`tenure_idle_timeout`, `reorg_attempts_activity_timeout` and related state-machine capitulation/mining timeout paths referenced throughout `chainstate/mod.rs`, `signerdb.rs`, and `v0/signer_state.rs`). If a stalled or malicious miner can keep this timer artificially fresh by repeatedly sending cheap, provably-invalid reorg-attempt proposals, the signer set is wedged into treating a non-productive miner as "active" indefinitely. This blocks the liveness path that exists specifically to let the network recover from an unresponsive/misbehaving miner (tenure-extend / miner-replacement / capitulation logic), which is a liveness wedge in the sense called out by the rules ("a signer wedged into never signing valid blocks ... or losing the equivocation guard"). It does not require any signer collusion or majority — only the miner already holding the current tenure slot, i.e. exactly the "one-slot miner" actor permitted by the rules.

### Likelihood Explanation
The proposal-time check runs before the expensive block-execution validation (`postblock_proposal.rs`'s `validate`), so the cost to the attacking miner of generating each spam proposal is low relative to producing a real, valid block. The only requirement is possession of the current tenure's mining key (which the attacker already has, being the legitimate winner of the sortition slot for that tenure) and the ability to sign successive minimal block headers that intentionally regress/duplicate height so as to hit the "reorg attempt" branch repeatedly. This is a realistic, low-cost, single-actor action.

### Recommendation
Do not treat a rejected (height-non-advancing / conflicting) proposal as unconditional "miner activity." At minimum, rate-limit or deduplicate activity-time updates per tenure (e.g., only the first such invalid-reorg-attempt proposal in a given time window should refresh `last_activity_time`), or require that activity credit be tied to some proof of real effort (e.g., only fresh, distinct, well-formed candidate blocks that pass all cheap static checks) rather than to every proposal that merely fails the height-ordering check.

### Proof of Concept
1. Miner M wins the sortition for tenure T and is the legitimate proposer.
2. Signer S signs/locally-accepts (or pre-commits to) block B1 at height h in tenure T.
3. M repeatedly crafts and signs new minimal block proposals B2, B3, … at height ≤ h (or otherwise conflicting) in tenure T and broadcasts them to signers.
4. For each Bi, `check_latest_block_in_tenure` rejects it (`Ok(false)`) but first calls `signer_db.update_last_activity_time(...)`, refreshing `last_activity_time` for tenure T. [5](#0-4) 
5. As long as M sends a new such proposal more often than `tenure_idle_timeout`/`reorg_attempts_activity_timeout`, the signer's inactivity/idle-timeout logic never fires for M's tenure, even though M never produces a valid advancing block.

Note: I was unable to fully trace, within the remaining tool budget, the exact downstream consumer function(s) that read `last_activity_time` to gate `tenure_idle_timeout`-based miner replacement/tenure-extend (only partial matches were found in `signerdb.rs`, `v0/signer_state.rs`, `chainstate/v1.rs`/`v2.rs`, and `runloop.rs`), so the precise liveness consequence (which specific timeout/extension path is stalled) should be confirmed by reading `stacks-signer/src/signerdb.rs`'s `get_last_activity_time`/timeout-check functions and `v0/signer_state.rs`'s `check_miner_inactivity`/`capitulate_viewpoint` in full.

    pub fn check_latest_block_in_tenure(
        tenure_id: &ConsensusHash,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        tenure_last_block_proposal_timeout: Duration,
        reorg_attempts_activity_timeout: Duration,
    ) -> Result<bool, ClientError> {
        let last_block_info = SortitionData::get_tenure_last_block_info(
            tenure_id,
            signer_db,
            tenure_last_block_proposal_timeout,
        )?;

        if let Some(info) = last_block_info {
            // N.B. this block might not be the last globally accepted block across the network;
            // it's just the highest one in this tenure that we know about.  If this given block is
            // no higher than it, then it's definitely no higher than the last globally accepted
            // block across the network, so we can do an early rejection here.
            if block.header.chain_length <= info.block.header.chain_length {
                warn!(
                    "Miner's block proposal does not confirm as many blocks as we expect";
                    "proposed_block_consensus_hash" => %block.header.consensus_hash,
                    "signer_signature_hash" => %block.header.signer_signature_hash(),
                    "proposed_chain_length" => block.header.chain_length,
                    "expected_at_least" => info.block.header.chain_length + 1,
                );
                if info.signed_group.is_none_or(|signed_time| {
                    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
                }) {
                    // Note if there is no signed_group time, this is a locally accepted block (i.e. tenure_last_block_proposal_timeout has not been exceeded).
                    // Treat any attempt to reorg a locally accepted block as valid miner activity.
                    // If the call returns a globally accepted block, check its globally accepted time against a quarter of the block_proposal_timeout
                    // to give the miner some extra buffer time to wait for its chain tip to advance
                    // The miner may just be slow, so count this invalid block proposal towards valid miner activity.
                    if let Err(e) = signer_db.update_last_activity_time(
                        &block.header.consensus_hash,
                        get_epoch_time_secs(),
                    ) {
                        warn!("Failed to update last activity time: {e}");
                    }
                }
                return Ok(false);
            }
        }
