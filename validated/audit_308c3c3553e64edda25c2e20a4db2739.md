### Title
Post-default withdraw requests are paid 1:1 from `defaultRecoveryReserve` without adding claim basis, draining defaulted claimants' recovery and permanently bricking their claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug class is "global debt/claim counter incremented by one path but only repaid up to a per-entity cap, leaving a permanent residual that bricks a claim path gated on that counter." The idle-tranches analog lives in `IdleCreditVault`: after `finalizeDefault`, new `requestWithdraw` calls create `postDefaultRequests` that are paid **1:1** from `defaultRecoveryReserve`, even though the reserve was sized at finalization as `recoveryPrice * totalBasis` and contains no backing for these post-default requests. Each such claim over-consumes the reserve, so the last defaulted/post-default claimants' transfers revert permanently (`defaultRecoveryReserve -= _amount` underflows / `safeTransfer` fails), permanently freezing their unclaimed recovery yield.

### Finding Description
At `finalizeDefaultRecovery`, the reserve is fixed once:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:686-691
uint256 reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve;
uint256 recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis;
defaultRecoveryReserve = reserveAmount;
```

So `defaultRecoveryReserve == defaultRecoveryPrice * totalBasis / 1e18` — exactly enough to pay every basis unit at the haircut ratio, nothing more.

After finalization, `requestWithdraw` creates a post-default claim with **no basis added and no haircut applied**:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:247-257
if (defaultRecoveryFinalized) {
  if (_hasWithdrawRequest(_user) || ...) revert NotAllowed();
  _burn(msg.sender, _amount);
  _mint(_user, _amount);
  postDefaultRequests[_user] = _amount;
  return;
}
```

The comment says the CDO "passes an already-haircut amount because finalization lowered virtualPrice" — i.e. the tranche tokens burned are worth `basis * recoveryPrice`, but the reserve then pays out the **full** `_amount`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:760-766
amount = postDefaultRequests[_user];
...
_burn(_user, amount);
_transferDefaultRecovery(_user, amount); // pays 1:1, decrements reserve by full amount
```

versus defaulted receipts which only draw `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` (line 782, 855). Since the reserve holds only `recoveryPrice` per unit of basis, paying a post-default claim 1:1 extracts `1/recoveryPrice` times the reserve units per unit of claim — over-consuming the finite reserve. Once the reserve is depleted, remaining `_transferDefaultRecovery` calls revert (subtraction underflow at line 915), permanently bricking `claimWithdrawRequest`/`claimInstantWithdrawRequest` for everyone left — the same "claim path permanently DoS-ed by accounting drift" shape as the Wise Lending finding.

Attacker is unprivileged: any KYC-passed tranche holder. After default finalization (`finalizeDefault` sets `allowAAWithdrawRequest`/`allowBBWithdrawRequest = true`), they call `requestWithdraw` on the CDO for a large tranche amount and then `claimWithdrawRequest`, receiving par value from a reserve that only holds haircut value.

### Impact Explanation
- Direct theft: a post-default withdrawer recovers more underlying per unit of burned claim basis than defaulted-epoch receipt holders (who are capped at `recoveryPrice`).
- Permanent freezing: once over-claimed, `defaultRecoveryReserve` is exhausted and subsequent claims via `_transferDefaultRecovery` revert forever (solidity 0.8 underflow), so remaining claimants' recovery yield is permanently locked — mirroring `claimFeesBeneficial` being permanently bricked by irreducible `totalBadDebtETH`.

### Likelihood Explanation
Requires a hard default followed by `finalizeDefault` — the same "bad debt must exist" external condition as the original finding, which judges there accepted as fair. Once finalized, any tranche holder can trigger it permissionlessly (post-default requests are explicitly enabled via `allowAAWithdrawRequest`/`allowBBWithdrawRequest`), and even honest post-default withdrawals cause the drain. Not mitigated by skim, guards, or `onlyIdleCDO` — the path is the designed flow.

### Recommendation
Either (a) apply the same `defaultRecoveryPrice` haircut to post-default payouts (`amount * defaultRecoveryPrice / RECOVERY_FULL`), consistent with other reserve claims, or (b) fund post-default claims from a separate source by adding them to a tracked basis at request time — but never pay 1:1 from the fixed default-recovery reserve. Also consider accounting post-default claims separately so the reserve invariant `reserve >= Σ remaining claims * recoveryPrice` always holds.

### Proof of Concept
Foundry fork outline (against `IdleCreditVault.t.sol` fixture):

```solidity
// setup: deposit AA/BB, startEpoch, then force default + finalizeDefault(recovered < basis)
// so defaultRecoveryPrice = 0.5e18 and defaultRecoveryReserve = 0.5 * totalBasis.

// attacker: a tranche holder with active tranche tokens post-finalization
uint256 trancheAmt = aaTranche.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.requestWithdraw(trancheAmt, address(aaTranche)); // creates postDefaultRequests[attacker]

vm.prank(attacker);
cdoEpoch.claimWithdrawRequest(); // receives full haircut-adjusted amount 1:1 from reserve
// even though reserve only holds recoveryPrice (50%) per claim unit

// victim: defaulted-epoch withdraw receipt holder
vm.prank(victim);
vm.expectRevert(); // defaultRecoveryReserve underflow in _transferDefaultRecovery
cdoEpoch.claimWithdrawRequest();
```

Key assertion: `strategy.defaultRecoveryReserve()` becomes negative-needed — i.e., the sum of paid claims exceeds `recoveryPrice * totalBasis`, leaving `underlyingToken.balanceOf(strategy) < remaining claims * recoveryPrice`, so remaining claims revert permanently.
