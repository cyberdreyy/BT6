This confirms the analog. The JIT (unsequenced Local) `AuthorizeActor` grant is explicitly documented as "replayable — last-write-wins on its slot until the local epoch moves" [1](#0-0) , with the check gate only validating epoch matches and skipping the sequence check entirely for `UNSEQUENCED` batches [2](#0-1) . A `RevokeActor` op applied on a *different* batch (e.g. sequenced, or another JIT batch) does not itself bump `local_epoch` — only an explicit `IncrementLocalEpoch` op does that [3](#0-2) . This means a previously-broadcast, still-valid (non-lapsed, i.e. `expiry == 0` or in the future) JIT `AuthorizeActor` signature can be resubmitted at any time to reinstall an actor grant that the account owner already revoked, exactly analogous to the CVE's retransmission-triggered reinstallation of stale keying material.

### Title
Replayable JIT `AuthorizeActor` grants allow reinstatement of a revoked actor after retransmission - (File: crates/execution/eip8130/src/apply.rs)

### Summary
An EIP-8130 account can authorize an actor (session key) via an unsequenced ("JIT") `Local`-channel `AuthorizeActor` change. This batch type intentionally consumes no sequence counter so it stays replayable "until the local epoch moves" [4](#0-3) . If the account owner later revokes that same actor via a separate `RevokeActor` change without also issuing an `IncrementLocalEpoch` op, the original signed JIT grant remains cryptographically valid and can be resubmitted by anyone in a brand-new top-level transaction, silently reinstating the revoked actor's authorization.

### Finding Description
The unsequenced/JIT path is detected purely from `(channel, sequence)`: `Local` channel with `sequence low-half == UNSEQUENCED` [5](#0-4) . Its only replay-defense is an expiry check that drops a grant whose `config.expiry` has already lapsed [6](#0-5) ; a grant with `expiry == 0` (no-expiry sentinel) or a still-future expiry is *never* skipped and is applied unconditionally as an upsert via `authorize_actor_with_account_state`, which overwrites whatever the actor's current config is [7](#0-6) .

The authorization gate for this batch type only checks that the embedded epoch half matches `state.local_epoch`; when the sequence low-half equals `UNSEQUENCED`, the sequence check itself is skipped entirely [8](#0-7) , confirmed by the test `unsequenced_local_batch_skips_sequence_check` which shows the same JIT signature authorizes "regardless of the account's current local sequence" [9](#0-8) .

Crucially, this authorization is verified purely from the account and the digest of the embedded `SignedAccountChanges` payload — not from the enclosing transaction's sender or its top-level nonce. An attacker (any unprivileged transaction sender) who has observed the original JIT `AuthorizeActor` calldata on-chain (transaction calldata is public) can copy that exact `SignedChange`/`SignedAccountChanges` payload into a brand-new EIP-8130 transaction (with its own fresh, unrelated top-level nonce) addressed at the victim account. Because the batch is still unsequenced and the local epoch has not moved, it re-authenticates and re-applies, restoring the actor's grant — even though the owner explicitly issued a `RevokeActor` for that same `actor_id` in the interim. The only mitigation is that the account owner must remember to separately issue `IncrementLocalEpoch` whenever revoking a JIT-granted actor, which is not enforced by `revoke_actor`/`revoke_actor_with_account_state` [10](#0-9) .

This mirrors CVE-2020-17497's bug class: a previously-valid, legitimately-observed protocol message (Msg4/4 in the CVE; here, the signed JIT authorize batch) can be retransmitted by a third party to force the victim's state machine to reinstall stale/should-be-revoked authorization material, silently undoing an explicit revocation.

### Impact Explanation
If the reinstalled actor still holds meaningful scope (e.g. `SCOPE_OPERATOR`/unrestricted, or a spending policy grant that hasn't separately been invalidated), the attacker can cause the victim's revoked session key/actor to become live again, potentially enabling unauthorized transaction execution and theft of funds from the account if that actor's authenticator key was compromised (the very reason for the revoke). Because the reinstatement is exact — same scope, same policy, same expiry as originally granted — it fully undoes the account owner's revocation with a single trivially-replayed transaction, independent of the tx-level nonce/replay protections.

### Likelihood Explanation
High: exploitation requires only observing a previously-broadcast (necessarily public) JIT `AuthorizeActor` payload and resubmitting it verbatim inside a new transaction with a fresh valid top-level nonce — no signing key, special privilege, or timing constraint is required beyond the grant's `expiry` (which defaults to `0`, meaning "no expiry", per the no-expiry sentinel logic [11](#0-10) ) and the account not yet having bumped its `local_epoch`.

### Recommendation
Consider making `RevokeActor` (or a subsequent authorize/revoke targeting the same `actor_id`) invalidate outstanding JIT grants for that slot, e.g. by tracking a per-actor "epoch"/nonce that JIT grants must match, or by documenting/enforcing that any revoke of a JIT-authorized actor must be paired atomically with `IncrementLocalEpoch` in the same signed batch so the old grant can never re-land.

### Proof of Concept
1. Account owner signs and broadcasts a `Local`, unsequenced (`sequence low-half = UNSEQUENCED`) `AuthorizeActor` batch granting `actor_id = X` scope `SCOPE_OPERATOR`, `expiry = 0`. It lands on-chain (calldata now public).
2. Owner later signs and broadcasts a separate `RevokeActor` batch for `actor_id = X` (without `IncrementLocalEpoch`); `X`'s `actor_config` slot is cleared.
3. Attacker copies the exact `SignedAccountChanges` bytes from step 1 (same channel/sequence/changes/signature) into a new EIP-8130 transaction with its own top-level nonce, and submits it.
4. `ConfigChangeAuthorizer::authorize_with_account_state` re-validates the epoch (unchanged) and skips the sequence check (JIT), re-authenticates the same signature, and `AccountChangeApplier::apply_config_change` re-installs `actor_id = X` with its original scope — reinstating the revoked actor without the owner's consent.

    /// Applies an `IncrementLocalEpoch` op, mirroring `_applyIncrementLocalEpoch`:
    /// a strict `local_epoch += 1` (rejecting the terminal `u32::MAX`) that also
    /// resets `local_sequence` to 0, retiring every unlanded local signature (each
    /// commits the full 64-bit `localEpoch ‖ localSequence` word). Allowed on
    /// either channel — a Multichain batch may bump the local epoch without a
    /// separate Local batch. The payload MUST be empty.
    fn apply_increment_local_epoch(
        payload: &[u8],
        state: &mut AccountState,
    ) -> Result<(), ApplyError> {
        if !payload.is_empty() {
            return Err(ApplyError::InvalidChangePayload);
        }
        // `local_epoch` stores a `uint32`; only the terminal value cannot advance
        // (the epoch half has no reserved sentinel).
        if state.local_epoch == u64::from(u32::MAX) {
            return Err(ApplyError::EpochSaturated);
        }
        state.local_epoch += 1;
        state.local_sequence = 0;
        Ok(())
    }

    pub fn revoke_actor_with_account_state(
        storage: &mut AccountConfigurationStorage<'_>,
        account: Address,
        actor_id: B256,
        state: &mut AccountState,
    ) -> Result<u32, ApplyError> {
        let config = storage.actor_config_slot(account, actor_id)?;
        let is_self = actor_id == AccountConfigurationStorage::self_actor_id(account);
        if config.authenticator != Address::ZERO {
            Self::revoke_explicit_actor(storage, account, actor_id, config)?;
            // Defense-in-depth: an explicit self actor is necessarily non-k1, and
            // `authorize_actor_with_account_state`/`apply_create` already set
            // DEFAULT_EOA_REVOKED and zeroed the inline scope/expiry when it was
            // installed. Re-assert that invariant here (a no-op on the in-tree
            // install paths) instead of depending on the authorize path, so a
            // future direct `set_actor_config` writer cannot leave a live inline
            // secp256k1 home behind an explicit self entry. `state` is already
            // loaded and flushed by the caller, so this adds no storage access.
            // This clears a populated explicit `actor_config`, so it is not the
            // discounted inline-self shape.
            if is_self {
                Self::disable_inline_self(state);
            }
            return Ok(0);
        }
        if !is_self || state.default_eoa_revoked() {
            // Idempotent: the actor is already absent — no explicit `actor_config`
            // entry, and either a non-self id or a self whose inline secp256k1 key
            // is revoked. Mirrors `_applyRevoke`'s `if (!_isAuthorized(...)) return;`
            // (eip-8130 #100): no state change and no `ActorRevoked` event. All
            // three conservatively reset-priced revoke slots (`actor_config` and
            // both policy slots) are empty for an absent actor, so the whole revoke
            // is discounted.
            return Ok(3);
        }

        // The inline self's `actor_config` slot is always empty (a zero-to-zero
        // reset no-op). Its two policy slots are written verbatim at authorize
        // time and may be zero even when the self is policy-gated (`slice_policy`
        // permits a zero manager and/or commitment), so a zero slot is likewise a
        // no-op. Count each actually-empty slot from the raw storage before
        // `clear_policy` zeroes them; only the non-zero slots stay at the
        // conservative reset price. The gate bit is not a reliable proxy here.
        let mut empty_slots = 1; // `actor_config`
        if storage.get_policy_manager(account, actor_id)?.is_zero() {
            empty_slots += 1;
        }
        if storage.get_policy_commitment(account, actor_id)?.is_zero() {
            empty_slots += 1;
        }
        storage.clear_actor_config(account, actor_id)?;
        storage.clear_policy(account, actor_id)?;
        Self::disable_inline_self(state);
        AccountConfigurationEvents::emit_actor_revoked(storage, account, actor_id)?;
        Ok(empty_slots)
    }
