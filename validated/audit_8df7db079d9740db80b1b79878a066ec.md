## #Vulnerability Found

### Title
Unauthorized third party can grief a validator's vote-account withdrawal by front-running with an unauthenticated `DepositDelegatorRewards` deposit - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The `DepositDelegatorRewards` vote instruction (SIMD-0123) lets *any* signer of an arbitrary `source` account transfer lamports into *any* vote account and bump its `pending_delegator_rewards` field, with no authorization check tying the caller to the vote account's authorized voter/withdrawer. Because the `withdraw` instruction refuses to fully close a vote account (or to withdraw below `rent_exempt_minimum + pending_delegator_rewards`) while `pending_delegator_rewards > 0`, an attacker can grief a legitimate withdrawer by injecting a negligible deposit that forces their subsequent close/withdraw transaction to fail — mirroring the FIVA report's pattern where an unprivileged actor completes/derails another user's pending multi-step operation by supplying attacker-controlled parameters to a permissionless "second step."

### Finding Description
`deposit_delegator_rewards` only requires that the `source` account sign the lamport transfer; it performs no check that the caller is the vote account's `authorized_withdrawer` or `authorized_voter`: [1](#0-0) 

The instruction handler in `vote_processor.rs` likewise only enforces `check_number_of_instruction_accounts(2)` and feature-gating, forwarding to `deposit_delegator_rewards` with the vote account and source account indices — no owner/authority relationship between them is validated: [2](#0-1) 

Once `pending_delegator_rewards` is nonzero, `withdraw` behaves as follows:
- Full-close (`remaining_balance == 0`) is rejected outright while `pending_delegator_rewards > 0`.
- Partial withdrawals must leave at least `rent_exempt_minimum + pending_delegator_rewards` in the account. [3](#0-2) 

This is directly analogous to the FIVA `add_liquidity`/`Deposit` bug: a permissionless "complete the pending operation" message (there, `add_liquidity`; here, `DepositDelegatorRewards`) can be triggered by anyone with attacker-chosen amounts and no linkage/authorization check to the intended beneficiary's identity, letting the attacker corrupt the outcome of the victim's own subsequent transaction (there, minting few LP tokens; here, causing `withdraw`/account-close to revert).

### Impact Explanation
An attacker can, for the cost of a single lamport (`deposit` can be as small as `1`, and even `deposit: 0` is accepted as a no-op per the test at lines 5186-5217) plus one transaction fee, unilaterally set any vote account's `pending_delegator_rewards` to a nonzero value. This:
1. Blocks the authorized withdrawer's attempt to fully close/deactivate the vote account (`InsufficientFunds` instead of success), which is a real operational griefing vector for validators trying to decommission a vote account.
2. Silently raises the minimum balance the withdrawer must leave behind on any partial withdrawal, without their consent, potentially causing a withdrawer's carefully-computed withdrawal transaction (built assuming `pending_delegator_rewards == 0`) to fail unexpectedly — the exact "slippage/parameter" bypass pattern described in the source report, except here the attacker denies rather than diverts value.

This does not enable direct unsigned fund theft (the deposited lamports do go toward legitimate future delegator-reward distribution), so it falls short of "concrete unsigned fund movement," but it is a transaction-triggered griefing/DoS of a specific target's state-transition, reachable by any unprivileged signer against any vote account.

### Likelihood Explanation
Trivial and cheap to trigger: requires only a `System::transfer`-capable signer account and knowledge of the target vote account's public key (public information), with `commission_rate_in_basis_points`, `custom_commission_collector`, and `block_revenue_sharing` features active (SIMD-0123/0232/0291/0185). No special privilege, timing precision beyond "before the victim's withdraw transaction lands," or large capital is needed.

### Recommendation
- **Short term:** Restrict who may call `DepositDelegatorRewards` against a given vote account (e.g., require the transaction to be signed by the vote account's `authorized_voter`/`authorized_withdrawer`, or otherwise scope deposits to a delegator-authorized source), removing the ability for an arbitrary unrelated signer to mutate another account's `pending_delegator_rewards`.
- **Long term:** Document and enforce the full state-machine for `pending_delegator_rewards` (who can increment it, when it decrements, and its interaction with `withdraw`) so that a withdrawer's outcome cannot be altered by an unauthenticated third party between transaction construction and execution.

### Proof of Concept
1. Victim owns vote account `V` with `authorized_withdrawer = W` and currently `pending_delegator_rewards = 0`.
2. Attacker submits `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` with accounts `[V (writable), attacker_source (signer, writable), system_program]` — no signature from `W` or `V`'s authorized voter is required, per `deposit_delegator_rewards`'s only check being `verify_authorized_signer(&source_address, signers)` on the *source*, not the vote account authority: [4](#0-3) 
3. `V.pending_delegator_rewards` becomes `1`.
4. `W` submits a previously-prepared `Withdraw` instruction intending to fully close `V` (withdraw all lamports). It now fails with `InstructionError::InsufficientFunds` due to the `pending_delegator_rewards > 0` check: [5](#0-4) 
5. `W`'s intended account-closure operation is griefed by the attacker's unauthorized, low-cost deposit — the same class of "unprivileged third party disrupts a user's intended pending action via a permissionless completion/step message" described in the source report.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
