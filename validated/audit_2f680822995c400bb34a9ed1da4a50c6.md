### Title
Stale rejection weight is never decremented when a signer flips to acceptance, inflating `total_weight_rejected`/`total_weight_approved` past the true tally - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener`'s block-status tally (`BlockStatus::total_weight_approved` / `total_weight_rejected`) is updated asymmetrically for the two message kinds it processes. A `Rejected` message adds a signer's weight to `total_weight_rejected` gated only by insertion into `responded_signers`; a later `Accepted` message from the *same* signer for the *same* block is gated only by `gathered_signatures`, a completely separate map, and adds the signer's weight to `total_weight_approved` without ever removing it from `total_weight_rejected`. The signer's weight ends up permanently double-counted across both totals, exactly mirroring the external report's pattern: the code path that increases a counter is present and correct, but the corresponding decrease when the underlying condition reverses is missing.

### Finding Description
`BlockStatus` tracks two independent accounting structures: [1](#0-0) 

For an `Accepted` response, the code adds the signer's weight to `total_weight_approved` only the first time that `slot_id` appears in `gathered_signatures`, then unconditionally records the slot in both `gathered_signatures` and `responded_signers`: [2](#0-1) 

For a `Rejected` response, the weight is added to `total_weight_rejected` only if `responded_signers.insert(slot_id)` returns `true` (i.e., the slot has never responded before, for *either* kind of message): [3](#0-2) 

Consider the sequence: a signer rejects a proposal first (e.g. because its local chainstate view was momentarily stale — a fully legitimate, protocol-sanctioned outcome, since the signer state machine explicitly allows `LocallyRejected -> LocallyAccepted` on re-evaluation, as documented for `signerdb.rs`'s `BlockInfo::check_state`), then on re-proposal or re-evaluation the same signer validates and signs, broadcasting `Accepted`.

- On the reject: `responded_signers.insert(slot_id)` returns `true` (first response) → `total_weight_rejected += weight`.
- On the later accept: the check is `!block.gathered_signatures.contains_key(&slot_id)`, which is `true` (first *acceptance*) → `total_weight_approved += weight`. Nothing in this branch inspects or decrements `total_weight_rejected`, even though `responded_signers` already contains this slot.

The result: this single signer's weight is now counted in *both* `total_weight_approved` and `total_weight_rejected` simultaneously, for the lifetime of that `BlockStatus` entry (it is only ever reset by `reset_rejections` on an explicit timeout, not on a legitimate vote flip). Note the asymmetry is one-directional: the reverse case (accept-then-reject) is correctly guarded, since `responded_signers.insert(slot_id)` after an acceptance already returns `false` on the follow-up rejection, so no re-add occurs. This exactly mirrors the external report's shape — the "increase" path is defended but the corresponding "decrease" (or here, correction) is simply absent.

This breaks the intended invariant that each signer's weight is counted at most once toward the outcome the miner-side coordinator (`SigningCoordinator`, `stacks-node/src/nakamoto_node/signer_coordinator.rs`) uses to decide whether a block is `SignersRejected` or accepted: [4](#0-3) 

### Impact Explanation
`total_weight_rejected` is used directly to decide whether a block should be declared dead (`SignersRejected`) once it plus the acceptance threshold exceeds `total_weight` (i.e., >30% blocking minority reached). Because a single signer's stale rejection weight is never cleared after that signer flips to a genuine acceptance/signature, `total_weight_rejected` can be inflated above its true, currently-held value. If other signers' genuine (still-standing) rejections are close to the 30% blocking-minority boundary, this stale extra weight can tip the coordinator into concluding the block is globally rejected even though the real, current opinion of the signer set does not actually block it — a liveness wedge that can stall block production/miner tenures without requiring a majority of signers, matching the "signer wedged" / miscounted-response class of impact.

### Likelihood Explanation
No majority collusion, no other signer's key, and no privileged access is required: a single signer legitimately re-evaluating a proposal (rejecting due to a transient chainstate mismatch, then accepting once it revalidates) is enough to trigger the double count. This re-evaluation path is a normal, documented part of the signer's own state machine, so the trigger condition arises under ordinary operation, not just adversarial action, making this readily reachable in practice.

### Recommendation
When processing an `Accepted` message, check whether the slot is already present with rejected weight counted (e.g., track per-slot outcome instead of two independent maps) and subtract the signer's weight from `total_weight_rejected` if it was previously counted there, mirroring the recommended pattern in the external report: correct the "decrease" side of the calculation instead of only ever incrementing. Concretely, maintain a single `HashMap<u32, Verdict>` per slot (accept vs. reject) so a flip can both add to the new bucket and remove from the old one atomically, or recompute both totals from the current per-slot map rather than maintaining separately incremented running counters.

### Proof of Concept
1. Node acting as coordinator tracks a `BlockStatus` for proposal `H` with `weight_threshold` = 70% of `total_weight`.
2. Signer `S` (weight `w_S`) sends `BlockResponse::Rejected` for `H`. `total_weight_rejected` becomes `w_S` (plus any other genuine rejecters).
3. Signer `S` later re-validates `H` (e.g., a re-proposal, or its local view catches up) and signs, sending `BlockResponse::Accepted` for `H`.
4. In the `Accepted` handler, `block.gathered_signatures` does not yet contain `S`'s slot, so `total_weight_approved += w_S`. `total_weight_rejected` is left unchanged at its earlier value including `w_S`.
5. Now `total_weight_approved + total_weight_rejected` exceeds `total_weight` by `w_S`; if genuine rejecters other than `S` already sit near `total_weight - weight_threshold`, this stale `w_S` addition can push `total_weight_rejected + weight_threshold > total_weight`, causing `SigningCoordinator::wait_for_signatures` to return `Err(NakamotoNodeError::SignersRejected)` for a block that, based on current signer opinions, should not have been blocked.
