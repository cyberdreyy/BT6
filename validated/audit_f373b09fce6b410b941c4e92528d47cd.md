### Title
`SignerDb::block_lookup` omits the `reward_cycle` key component, letting a cross-cycle `BlockInfo` row be treated as this signer's own decision - ([File: stacks-signer/src/signerdb.rs])

### Summary
`blocks` rows are keyed by the composite primary key `(reward_cycle, signer_signature_hash)` [1](#0-0) , and the schema comment explicitly asserts that the `signer_signature_hash` alone is "sufficient to uniquely identify the block across all burnchain, PoX, and stacks forks" [2](#0-1) . That assumption is used inconsistently: `SignerDb::block_lookup` fetches a row by `signer_signature_hash` alone, dropping the `reward_cycle` component of the key entirely [3](#0-2) , while the wrapper `block_lookup_by_reward_cycle` was added precisely to re-add that missing check by filtering the returned row against `self.reward_cycle` [4](#0-3) . The existence of this second, safety-checking wrapper is itself evidence that the raw `block_lookup` is unsafe to use when more than one reward-cycle context can be live, which the runloop explicitly supports (`running_signers: Vec<u64>` tracks multiple concurrently-running per-reward-cycle `Signer` instances sharing infrastructure) [5](#0-4) .

### Finding Description
`BlockProposal.reward_cycle` is a field of the message envelope, not of the `NakamotoBlockHeader` that `signer_signature_hash` is computed over [6](#0-5) . A miner (or relayed gossip) can therefore send the *same* block body wrapped in two `BlockProposal` messages that differ only in the declared `reward_cycle`, at the reward-cycle boundary when both the outgoing (N) and incoming (N+1) signer instances are simultaneously running in the same node process. Each instance independently passes its own reward-cycle gate at `handle_block_proposal` (`block_proposal.reward_cycle != self.reward_cycle` check) [7](#0-6)  and stores its own `BlockInfo` via `insert_block`, producing two distinct rows keyed `(N, H)` and `(N+1, H)` for the identical `signer_signature_hash` `H`.

When the node later emits a `SignerEvent::NewBlock` carrying that same `signer_sighash`, the handler calls the *unscoped* `self.signer_db.block_lookup(signer_sighash)` directly, with no reward-cycle equality check, and unconditionally marks whatever row is returned as globally accepted and re-inserts it: [8](#0-7) . Because SQLite returns an arbitrary matching row when the `WHERE` clause omits part of the composite key, the cycle-(N+1) signer instance can retrieve and mutate the cycle-N row (or vice versa). This is the same "insufficiently-derived cache key" root cause as the Composer CVE: the lookup key (`signer_signature_hash` only) is not the full identity key of the record (`reward_cycle, signer_signature_hash`), so a value cached/stored under one context is served into another context.

Downstream, `check_submitted_block_proposal` treats `has_reached_consensus()` on whatever `BlockInfo` was returned by an unscoped lookup as authoritative and stops re-evaluating [9](#0-8) , so a signer instance can end up treating a block as globally accepted/decided based on state that was never validated or voted on within its own reward-cycle context (wrong signer weights/threshold), breaking the "aggregated-weight vs verified-accepts" equality the state machine is supposed to preserve.

### Impact Explanation
This is a cross-context state contamination bug: a signer instance for reward-cycle N+1 can be made to adopt block-acceptance state computed under reward-cycle N's signer set/threshold without independently validating or counting weight under its own context, satisfying the "acting on a stale reward set/threshold" High-impact category from the analog rules. It also risks short-circuiting a signer's own consensus evaluation (`has_reached_consensus` early-return) for a block it never actually processed under its own reward cycle.

### Likelihood Explanation
Triggering requires only a miner/relay controlling the `reward_cycle` field of two `BlockProposal` envelopes around a normal reward-cycle boundary (a period the protocol is expected to handle, with both signer instances legitimately alive) — no majority of signers, no key compromise, and no auth token are needed. The precondition of two `BlockInfo` rows sharing a hash under different `reward_cycle`s is a natural consequence of the boundary-overlap design combined with `reward_cycle` living outside the hashed header.

### Recommendation
Make `block_lookup` reward-cycle-aware (accept and filter on `reward_cycle`, matching the table's actual primary key) or, at minimum, replace the raw `self.signer_db.block_lookup(signer_sighash)` call in the `SignerEvent::NewBlock` handler with the existing `block_lookup_by_reward_cycle` helper so every read path enforces the same `(reward_cycle, signer_signature_hash)` identity that the schema and `block_lookup_by_reward_cycle` already assume is required.

### Proof of Concept
1. At a reward-cycle boundary, run signer instances for cycle N and N+1 in the same process (normal operation per `running_signers`).
2. Craft one `NakamotoBlock` body B with sighash H.
3. Send `BlockProposal{block: B, reward_cycle: N}` to the cycle-N signer's StackerDB slot and `BlockProposal{block: B, reward_cycle: N+1}` to the cycle-(N+1) signer's slot. Both pass their local `reward_cycle` gate and each is stored via `insert_block`, producing rows `(N, H)` and `(N+1, H)`.
4. Trigger (or wait for) a `SignerEvent::NewBlock` with `signer_sighash = H` delivered to both instances.
5. Observe that `self.signer_db.block_lookup(H)` in the cycle-(N+1) instance can return the cycle-N row, causing `mark_globally_accepted`/`insert_block` to operate on state that was never validated by the cycle-(N+1) signer set. [8](#0-7)

    /// Helper for getting the block info from the db while accommodating for reward cycle
    pub fn block_lookup_by_reward_cycle(
        &self,
        block_hash: &Sha512Trunc256Sum,
    ) -> Option<BlockInfo> {
        let block_info = self
            .signer_db
            .block_lookup(block_hash)
            .inspect_err(|e| {
                error!("{self}: Failed to lookup block hash {block_hash} in signer db: {e:?}");
            })
            .ok()
            .flatten()?;
        if block_info.reward_cycle == self.reward_cycle {
            Some(block_info)
        } else {
            None
        }
    }
