### Title
Shell/argument injection via Go `%q` mis-quoting of `TmpProjectDir()` in `CmdLine` construction - (File: shells/proxy_exec.go)

### Summary
`ProxyExecShell.GetConfiguration` builds a shell command line by quoting the temp/project directory with Go's `fmt.Sprintf("%q", ...)`, then string-concatenating it into `CmdLine`. Go's `%q` produces Go-syntax double-quoted escaping, not POSIX-shell or Windows `cmd.exe` quoting, so if the directory string contains shell metacharacters (e.g. `$()`, backticks, `;`) they are **not** neutralized when the resulting `CmdLine` is later interpreted by a real shell.

### Finding Description
In `shells/proxy_exec.go`:

```go
tempDir := fmt.Sprintf("%q", info.Build.TmpProjectDir())
...
CmdLine: info.RunnerCommand + " proxy-exec --temp-dir " + tempDir + " " + base.CmdLine,
``` [1](#0-0) 

`%q` wraps the value in double quotes and escapes only Go-string-literal-special characters (`"`, `\`, control chars). It does **not** escape POSIX-shell-special characters such as `$`, `` ` ``, `;`, `(`, `)`. When a POSIX shell (`sh -c "..."`) later parses a double-quoted string, `$(...)` command substitution and `$VAR` expansion still occur *inside* double quotes — Go's quoting therefore does not provide shell-safety guarantees, only Go-source-safety guarantees.

The other two fields (`Arguments`, `DockerCommand`) pass `info.Build.TmpProjectDir()` as a discrete slice element (safe, since it's handed to `exec.Cmd.Args` and not re-parsed by a shell), but `CmdLine` is a flat string intended for shell-based executors, making it the vulnerable sink.

Whether this is practically exploitable hinges on whether `TmpProjectDir()`'s value can contain attacker-influenced characters. `TmpProjectDir()`/project directory paths are typically derived from the concurrency ID, runner short token, and project namespace/name — values that GitLab's server-side slug validation constrains to a restricted character set (alnum, `-`, `_`, `.`). If, however, a job can influence the build directory name through directory-related variables (e.g. `GIT_CLONE_PATH`) that are not filtered for shell metacharacters before being folded into the temp/project path, an attacker-controlled string containing `$(...)` could reach this sink.

### Impact Explanation
If reachable, arbitrary command injection inside the shell that executes `CmdLine`, occurring in the context of the `gitlab-runner-helper`/shell executor process for that job. This would allow escaping the intended `proxy-exec` sandboxing wrapper the feature is meant to enforce.

### Likelihood Explanation
I was unable to fully confirm, within the available tooling, (a) the exact implementation of `Build.TmpProjectDir()`/its upstream directory-name inputs, and (b) whether GitLab Runner's existing `GIT_CLONE_PATH`/custom-build-dir validation already rejects shell-metacharacters before they can reach this path. Server-side project namespace/path slugs are normally restrictive, which would make the primary attacker-controlled vector (`GIT_CLONE_PATH`) the only plausible route, and Runner does perform some validation on that variable (must remain under `CI_BUILDS_DIR`) — but I could not verify from the available index whether that validation also excludes arbitrary shell metacharacters. This uncertainty limits confidence in exploitability but does not eliminate the underlying code defect: **using `%q` (Go quoting) as a stand-in for shell quoting is unsafe on any platform where `CmdLine` is executed via a shell**, independent of whether a concrete injection path exists today.

### Recommendation
Replace `fmt.Sprintf("%q", ...)` with a proper shell-escaping routine appropriate to the target shell (POSIX vs Windows `cmd.exe`/PowerShell), or avoid building `CmdLine` as a flattened string altogether — pass `TmpProjectDir()` through the `Arguments` mechanism only (already done safely), or use an escaping library (e.g. `github.com/mattn/go-shellwords`-style quoting, or explicit POSIX single-quote wrapping with `'`→`'\''` escaping) matched to the shell each `CmdLine` value is actually parsed by. Additionally, audit/harden `GIT_CLONE_PATH` and other custom-build-dir inputs to reject shell metacharacters before they can propagate into any directory value used in shell-interpreted command strings.

### Proof of Concept
Because I could not confirm the exact upstream constraints on `TmpProjectDir()` inputs, a full PoC job cannot be asserted with certainty. A Go unit test can at least demonstrate the mis-quoting defect in isolation:

```go
func TestProxyExecShell_GetConfiguration_UnsafeQuoting(t *testing.T) {
    dir := `foo"; $(touch /tmp/pwned) #`
    quoted := fmt.Sprintf("%q", dir)
    // Assert quoted still contains shell-special sequence unescaped for POSIX sh
    assert.Contains(t, quoted, "$(touch /tmp/pwned)")
}
```
This confirms `%q` passes `$(...)` through unescaped. A full end-to-end PoC would additionally require confirming/bypassing Runner's `GIT_CLONE_PATH` validation to inject such a string into `TmpProjectDir()`, which was not verifiable within this investigation.
