## Title
Stale confirmations from removed multisig members are never purged from pending requests, allowing a request to execute below the live-member confirmation threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
Both multisig contracts track approvals for a pending request in a `confirmations` set keyed only by `request_id`, and count toward the execution threshold using the raw size of that set. When a member/key is removed via `DeleteMember` (V2) or `DeleteKey` (V1), the contract only purges requests that member *originally created*; it never scans other pending requests to strip that member's *confirmation* entries. A confirmation recorded by a member who has since been removed therefore keeps counting toward `num_confirmations`, letting a request execute with fewer currently-authorized approvals than the multisig's configured threshold — the same class of bug as the ENS finding, where one authority record (`ens.owner`) was left unchecked while only the other (`registrar.ownerOf`) was patched.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member` cleans up only requests whose creator (`r.member`) equals the member being removed: [1](#0-0) 

It does not iterate over `self.requests`/`self.confirmations` to remove entries where the removed member appears as a *confirmer* of a request created by someone else. `confirm` then counts approvals purely by `HashSet` cardinality, with no re-validation that every entry in the set still corresponds to a current member: [2](#0-1) 

`current_member()` is only used to authorize the *caller* of `confirm`/`add_request`, not to re-validate historical confirmations already stored in the `confirmations` map: [3](#0-2) 

The legacy V1 contract has the identical gap: `DeleteKey` removes only requests created by the deleted key, not confirmations that key gave to other members' requests, and `confirm` counts the raw `HashSet<PublicKey>` size: [4](#0-3) [5](#0-4) 

The binding that should hold is:
`confirmations recorded for a request` ⊆ `members currently in self.members` (V2) / `currently valid access keys` (V1)

The code breaks this equality: a confirmation from a member who is later deleted stays in the set forever (or until the request itself is deleted/executed), so `confirmations.len()` can exceed the number of *live* approvals for that request.

### Impact Explanation
This matches the "Critical - a multisig request executed below threshold" impact category. A request can be pushed to execution (transfer, `AddKey`/`AddMember`, `FunctionCall`, `DeployContract`, etc.) with real, live authorization from fewer members than `num_confirmations` requires, because one or more of the counted confirmations belong to accounts/keys that are no longer members of the multisig. This directly undermines the K-of-N security guarantee the contract is meant to provide, e.g. it could let a minority of current members move funds or redeploy the contract's own code that a full K-of-N quorum never actually approved.

### Likelihood Explanation
No redeploy, foundation intervention, or social engineering is needed — only normal contract operations already exposed by the multisig's own API:
1. A pending request accumulates a confirmation from a member.
2. That member is later removed through the standard `DeleteMember`/`DeleteKey` request flow (a routine, expected operational action, e.g. off-boarding an employee or rotating a compromised key) while the earlier request is still pending (not yet executed or deleted).
3. Because `delete_member`/`DeleteKey` execution only cleans requests *created* by that member, the stale confirmation silently survives on any other still-pending request.
4. A subsequent live member's `confirm()` call on that older pending request pushes `confirmations.len() + 1 >= num_confirmations`, executing the request with support from fewer live members than the configured threshold.

Since member turnover and request confirmation don't have to happen in lockstep (there's no requirement to resolve all pending requests before deleting a member), this scenario is straightforward to trigger in normal usage, not merely theoretical.

### Recommendation
When removing a member (`delete_member` in V2, the `DeleteKey` branch in V1), iterate all pending requests' confirmation sets and strip the removed member/key from each, rather than only deleting requests the removed member created. Alternatively, validate membership of every entry in `confirmations` against the current `members` set at the time `confirm()` counts them, so stale/removed-member confirmations never contribute to reaching `num_confirmations`.

### Proof of Concept
Using `multisig2::MultiSigContract` with members `{A, B, C, D}` and `num_confirmations = 3`:
1. `A.add_request(R)` — creates pending request `R` (e.g. `Transfer` of funds), `confirmations = {}`.
2. `B.confirm(R)` — `confirmations = {B}` (1/3).
3. Separately, `D.add_request_and_confirm(remove_B)` then `C.confirm(remove_B)` executes `DeleteMember{ member: B }`. Because `delete_member` ( [6](#0-5) ) only removes requests where `r.member == B` (i.e., requests *B created*), request `R` (created by `A`) is untouched — `confirmations` for `R` still contains `B`, even though `B` is no longer in `self.members`.
4. Now only 3 live members remain: `A, C, D`. `C.confirm(R)` runs: `confirmations.len() as u32 + 1 == 2 + 1 == 3 >= num_confirmations (3)`, so `execute_request(R)` fires.
5. Result: `R` executed with confirmations `{B, C}` plus the triggering call — but `B` is not a live member. Only one genuinely live member (`C`) plus the caller ever approved `R`; the third "confirmation" is a ghost from a deleted member, so the request executed below the real live-member threshold.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn current_member(&self) -> Option<MultisigMember> {
        let member = if env::current_account_id() == env::predecessor_account_id() {
            MultisigMember::AccessKey {
                public_key: env::signer_account_pk()
                    .try_into()
                    .unwrap_or_else(|_| env::panic_str("Failed to deserialize public key")),
            }
        } else {
            MultisigMember::Account {
                account_id: env::predecessor_account_id(),
            }
        };
        if self.members.contains(&member) {
            Some(member)
        } else {
            None
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
