### Title
RPC `sanitize_transaction`/`simulate_transaction` path omits the `enable_tx_v1` feature-gate check enforced by `verify_packet` and `Bank::verify_transaction`, causing divergent accept/reject behavior for V1 transactions - ([File: rpc/src/rpc.rs])

### Summary
The RPC handlers for `sendTransaction`/`simulateTransaction` sanitize incoming `VersionedTransaction`s via `sanitize_transaction` → `RuntimeTransaction::try_create`, which contains no `enable_tx_v1` feature-gate check. In contrast, the network/TPU ingestion path (`verify_packet` in `perf/src/sigverify.rs`) and the leader/replay processing path (`Bank::verify_transaction`/`verify_transaction_with_serialized_message` in `runtime/src/bank.rs`, and `check_transaction_without_status_cache`/`filter_v1_transactions` in `runtime/src/bank/check_transactions.rs`) all explicitly reject V1 transactions when `enable_tx_v1` is inactive. A single unprivileged client sending one V1-encoded `VersionedTransaction` to `simulateTransaction` (or `sendTransaction` with preflight enabled) while the feature is cluster-wide disabled can get it sanitized and simulated/preflighted by the RPC node even though every other code path (packet ingestion, on-chain execution) would reject it with `TransactionError::UnsupportedVersion`.

### Finding Description
- `sanitize_transaction` in `rpc/src/rpc.rs` calls `RuntimeTransaction::try_create` directly: [1](#0-0) 
- `RuntimeTransaction::try_create` (`runtime-transaction/src/runtime_transaction/sdk_transactions.rs`) performs instruction-count/account-count sanitization but has no `enable_tx_v1` awareness whatsoever: [2](#0-1) 
- Both `send_transaction` and `simulate_transaction` RPC handlers call this same ungated `sanitize_transaction` before doing anything else, and `simulate_transaction` proceeds to `transaction.verify()` (signature-only) and `bank.simulate_transaction(...)` (execution) without ever consulting `feature_set.enable_tx_v1`: [3](#0-2) 
- Compare this to the two paths that DO enforce the gate:
  - Network/TPU packet verification (`perf/src/sigverify.rs::verify_packet`), which rejects V1 packets outright when the gate is off: [4](#0-3) 
  - Bank-level verification used for actual transaction execution/replay: [5](#0-4) [6](#0-5) 
  - And the leader-only pre-execution age/status check plus batch filtering, which independently re-enforce the same gate: [7](#0-6) [8](#0-7) 

Root cause: the `enable_tx_v1` gate was added at multiple *specific* enforcement points (`Bank::verify_transaction`, `check_transaction_without_status_cache`, `filter_v1_transactions`, `verify_packet`) but the RPC ingress `sanitize_transaction`/`decode_and_deserialize` path was never updated to consult the feature set before sanitizing/simulating a V1 transaction. This means the RPC's own "is this transaction valid" answer (accept + simulate) can diverge from what every consensus-relevant path (packet sigverify, bank replay) would answer (`UnsupportedVersion`) for byte-identical input, purely depending on which entry point received the bytes.

### Impact Explanation
This is an RPC correctness/misreporting bug: `simulateTransaction` (and preflight in `sendTransaction`) can successfully sanitize, signature-verify, and execute a V1 transaction against the current bank state and return a plausible-looking simulation result (logs, balances, compute units, etc.) for a transaction type that the cluster does not actually support while `enable_tx_v1` is disabled. Any real submission of that same transaction would be discarded at TPU ingestion (`verify_packet`) or rejected during replay/processing (`Bank::verify_transaction` → `UnsupportedVersion`). This is a decoder/RPC misreporting issue (wrong preflight/simulation outcome returned to the caller) rather than a consensus-state mutation, matching the "wrong ... data returned" / "decoder ... misreporting" bounty category. It does not by itself let a V1 transaction land on-chain, since the gate is still enforced independently at the bank/packet layers before actual inclusion.

### Likelihood Explanation
Highly feasible and fully reachable by a single unprivileged client: one `simulateTransaction` (or `sendTransaction` without `skipPreflight`) JSON-RPC call carrying a V1-encoded `VersionedTransaction`, with no special privileges, staking, or multiple calls required. It is deterministic and repeatable as long as `enable_tx_v1` is inactive on the target cluster, satisfying the "single call" rate constraint.

### Recommendation
Add an explicit `enable_tx_v1` feature-gate check in the RPC ingress path before sanitizing/simulating a transaction — e.g., in `sanitize_transaction` (or immediately before it is called in `send_transaction`/`simulate_transaction`) — mirroring the check already present in `Bank::verify_transaction`/`verify_transaction_with_serialized_message` and `verify_packet`: if `!bank.feature_set.snapshot().enable_tx_v1 && matches!(tx.version(), TransactionVersion::Number(1))`, return `TransactionError::UnsupportedVersion` (translated to the appropriate RPC `invalid_params`/simulation error) before any sanitize/verify/simulate work occurs.

### Proof of Concept
```rust
// rpc/src/rpc.rs (test module) — differential test
#[test]
fn test_rpc_accepts_v1_tx_while_gate_disabled_diverges_from_verify_packet() {
    // 1. Build a V1 VersionedTransaction (message::v1::Message) signed correctly.
    let versioned_tx = build_v1_transfer_tx(); // analogous to make_v1_transaction in bank/tests.rs

    // 2. Ensure enable_tx_v1 feature is NOT active on the bank used by the RPC handler.
    let bank = Bank::new_for_tests(&genesis_config);
    assert!(!bank.feature_set.snapshot().enable_tx_v1);

    // 3a. RPC path: encode + call simulateTransaction.
    let data = BASE64_STANDARD.encode(wincode::serialize(&versioned_tx).unwrap());
    let req = format!(
        r#"{{"jsonrpc":"2.0","id":1,"method":"simulateTransaction","params":["{data}", {{"encoding":"base64","sigVerify":true}}]}}"#
    );
    let res = io.handle_request_sync(&req, meta.clone());
    // EXPECTED (if bug present): result is Ok / a simulation result, NOT an "UnsupportedVersion" error.

    // 3b. Network path: feed identical wire bytes into verify_packet with enable_tx_v1=false.
    let wire_bytes = wincode::serialize(&versioned_tx).unwrap();
    let mut packet = BytesPacket::from_bytes(None, Bytes::from(wire_bytes));
    let verified = sigverify::verify_packet(&mut packet.as_mut(), /*reject_non_vote=*/false, /*enable_tx_v1=*/false);
    assert!(!verified); // network path rejects it.

    // Assert divergence: RPC accepted/simulated it while verify_packet rejected the same bytes.
    assert!(matches!(
        parse_rpc_error(&res),
        None /* success */
    ), "RPC should have rejected the V1 tx like verify_packet does, but it did not");
}
```
Expected assertion: the network path (`verify_packet`) rejects the V1 packet (`verified == false`) while the RPC path returns a non-error simulation result — demonstrating the accept/reject inconsistency across ingress paths for identical bytes.

    pub fn try_create(
        tx: VersionedTransaction,
        message_hash: MessageHash,
        is_simple_vote_tx: Option<bool>,
        address_loader: impl AddressLoader,
        reserved_account_keys: &HashSet<Pubkey>,
    ) -> Result<Self> {
        if tx.message.instructions().len()
            > solana_transaction_context::MAX_INSTRUCTION_TRACE_LENGTH
        {
            return Err(solana_transaction_error::TransactionError::SanitizeFailure);
        }

        for instr in tx.message.instructions() {
            if instr.accounts.len() > solana_transaction_context::MAX_ACCOUNTS_PER_INSTRUCTION {
                return Err(solana_transaction_error::TransactionError::SanitizeFailure);
            }
        }

        let statically_loaded_runtime_tx =
            RuntimeTransaction::<SanitizedVersionedTransaction>::try_from(
                SanitizedVersionedTransaction::try_from(tx)?,
                message_hash,
                is_simple_vote_tx,
            )?;
        Self::try_from(
            statically_loaded_runtime_tx,
            address_loader,
            reserved_account_keys,
        )
    }
