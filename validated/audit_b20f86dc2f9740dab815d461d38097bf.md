### Title
Stale confirmations from removed multisig members are counted toward the approval threshold, allowing execution below the live-member quorum - ([File: multisig2/src/lib.rs])

### Summary
Both `multisig` and `multisig2` implement a K-of-N confirmation scheme where a request executes once `confirmations.len() + 1 >= num_confirmations`. When a member/key is deleted via `DeleteMember`/`DeleteKey`, the contract only purges confirmations and requests that were *authored* by that member (filtered by `r.member == member` / `r.signer_pk == pk`). It does **not** scan and strip that member's confirmations from *other* pending requests they had already confirmed but did not author. Those stale confirmation entries remain in the `confirmations` set and continue to count toward the threshold in a later `confirm()` call.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` computes the quorum purely from the size of the stored `HashSet<String>` for the request: [1](#0-0) 

`delete_member()` only removes requests *created by* the removed member and clears `num_requests_pk` for them; it never touches `self.confirmations` entries for requests created by *other* members that the removed member had already confirmed: [2](#0-1) 

The equivalent v1 contract (`multisig/src/lib.rs`) has the identical gap: `DeleteKey` purges only requests where `r.signer_pk == pk`, leaving the deleted key's confirmation strings intact in `confirmations` maps of requests it did not create: [3](#0-2) 

The intended custody binding for a K-of-N multisig is: `confirmations counted == confirmations from currently live members`. Because stale confirmations from removed members are never invalidated, this binding is broken — the contract can execute a request using fewer than K live-member approvals, treating a removed member's earlier confirmation as still valid.

### Impact Explanation
This directly breaks the multisig's authorization guarantee that a request (including `Transfer`, `FunctionCall`, `AddKey`, etc.) requires K independent live approvals. A member whose key/access is later revoked (e.g., because it was suspected compromised, or the member left/was fired) can still contribute a "ghost" approval toward any request they confirmed before removal. If a colluding minority of currently-valid members (fewer than K) combine with such a stale confirmation, they can push a `Transfer` request past the nominal threshold and move NEAR funds out of the multisig account, or execute other privileged actions (adding a new access key, deploying new code), despite not having the intended number of live signers. This is a Critical-class outcome: NEAR moved by parties not entitled to move it under the account's own confirmed security policy (K-of-N).

### Likelihood Explanation
The precondition is realistic and commonly occurs in multisig lifecycle management: members/keys get rotated or revoked over time. An unprivileged party does not need special access beyond being a *former* member who confirmed a pending request before being removed — no owner privilege, no redeploy, and no social engineering is required beyond normal governance actions that already happen (removing a member). The remaining live members simply need to confirm the same still-pending request to cross threshold using the stale vote; this is entirely within normal contract usage/flow, making the likelihood substantial once request lifetimes overlap with membership changes.

### Recommendation
When a member/key is deleted, iterate over all entries in `confirmations` (not just requests authored by that member) and remove the deleted member's identifier from every confirmation set, re-checking or invalidating any request whose remaining count no longer meets a re-derived, live-membership-aware threshold. Alternatively, validate at `confirm()`-execution time that every account/key credited in the stored `confirmations` set is still a current member before counting it toward quorum (i.e., recompute `confirmations.iter().filter(|m| self.members.contains(m)).count()`), rather than trusting the raw stored set size.

### Proof of Concept
1. Deploy `multisig2` with 4 members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` creates request `R` = `Transfer{amount: X}` to an attacker-controlled account, and confirms it (`confirmations[R] = {A}`).
3. Members execute a separate `DeleteMember{member: A}` request (reaches 3-of-4 confirmations from B, C, D) to remove `A` — `delete_member` only filters and removes requests where `r.member == A`; since `R` was authored by `A`, it *is* removed in this specific case... 

   To bypass this and hit the exact gap, use the scenario where `A` confirms a request authored by someone else:
   - `B` creates request `R2` = `Transfer{amount: X}`.
   - `A` (not the author) calls `confirm(R2)` → `confirmations[R2] = {A}` (1/3).
   - `A` is subsequently removed via `DeleteMember{member: A}`. Since `R2.member == B`, the filter in `delete_member` does not touch `R2`, so `confirmations[R2]` still contains `A`'s stale entry.
4. Now with only `A`(stale) + `C` + `D` = 3 confirmations recorded, but `A` is no longer a member — `D` calls `confirm(R2)`, `confirmations.len() as u32 + 1 == 3 >= num_confirmations`, and `execute_request` fires the transfer, even though only 2 currently-live members (`C`, `D`) plus one no-longer-valid stale vote actually approved it.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
