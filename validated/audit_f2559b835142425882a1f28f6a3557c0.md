### Title
Loss-recovery haircut is keyed to `epochNumber` at funding time while the claim/escape guard is keyed to `lastWithdrawRequest[_user]`, letting a pending receipt skip its haircut — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
CVE-2017-15951 is a race between *updating* and *finding* a "negative" key: a lookup can return a negative/absent result for a key that is concurrently being created. The credit-vault analog lives in `IdleCreditVault`: the stop-epoch loss haircut is *written* under `lossRecoveryPriceByEpoch[epochNumber]` inside `collectWithdrawFunds`, but both the re-request guard in `requestWithdraw` and the payout path in `_claimLossAdjustedWithdrawRequest` *find* the haircut via `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. the epoch in which the user's request was recorded. Because a withdraw request is recorded during the buffer under the pre-stop epoch while `collectWithdrawFunds` executes inside `stopEpochWithDuration` (after/beside the `epochNumber` bump), the update and the lookup use different keys — a "negative" (`0`) lookup coexists with a stored haircut. An unprivileged lender exploits this to have a loss-hit receipt paid at par.

### Finding Description
`requestWithdraw` records receipts per request epoch and stamps `lastWithdrawRequest[_user] = currentEpoch` (buffer epoch N), and only blocks a new request when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` and that epoch still holds a receipt. [1](#0-0) 

`collectWithdrawFunds`, called by the CDO during `stopEpochWithDuration`, writes the haircut under `epochNumber` **at collect time**, which is the already-bumped epoch N+1 — not the request epoch N that `lastWithdrawRequest` stores. [2](#0-1) 

In the next buffer the attacker calls `requestWithdraw` again. The guard reads `lossRecoveryPriceByEpoch[N]` → `0` ("negative" key), so it does not revert, and `lastWithdrawRequest[_user]` is overwritten to the new epoch. On claim, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — it finds at most the haircut for the *new* small request, then `_claimFundedWithdrawRequest` pays the residual `withdrawsRequests[_user]` (which still contains the old loss-hit amount, because `_clearWithdrawClaimForEpoch` only subtracts the entry for the looked-up epoch) at par via `_transferFundedClaim`. [3](#0-2) [4](#0-3) 

The `pendingWithdraws` bucket that `stopEpochWithDuration` funded was already reduced by the loss (`previewLossAdjustedWithdrawFunds` computes `pendingToFund < pendingBasis`), so paying the old receipt at par consumes underlyings that were never collected — the missing amount is borne by remaining LPs / later claimants. [5](#0-4) 

### Impact Explanation
Direct theft / insolvency: the attacker escapes the pro-rata stop-epoch loss applied to all other pending receipts and is paid the un-haircut amount. The shortfall is socialized onto other withdraw requesters and active tranche holders, breaking the loss-waterfall and solvency invariants. Loss magnitude = `(RECOVERY_FULL - lossRecoveryPrice) * claimBasis / RECOVERY_FULL` per escaped receipt — e.g. with a 20% pending loss and a 1M USDC receipt, ~200k USDC is overpaid.

### Likelihood Explanation
Requires (a) a `stopEpochWithDuration` realizing a loss on the pending-withdraw bucket (borrower underpays / credit loss — a supported, in-scope path) and (b) the haircut being stored under an epoch different from the victim-receipt's `lastWithdrawRequest`, which occurs whenever `epochNumber` is bumped before `collectWithdrawFunds` inside the same `stopEpochWithDuration` call — or whenever a request is re-opened in a later buffer while an older haircut entry exists under a different key. Only an unprivileged lender is needed; all privileged actors (manager stopping the epoch, borrower funding) behave honestly. Existing guards (`NotAllowed` on zero price, the claim-before-re-request check) do not fire because they consult the wrong (negative) key — precisely the CVE bug class. Confidence caveat: the exploit hinges on the ordering of `epochNumber` increment vs. `collectWithdrawFunds` inside `IdleCDOEpochVariant.stopEpochWithDuration`, which should be confirmed when building the PoC; if they share the same epoch number, the equivalent escape is via a second request epoch differing from the stored loss epoch (the lookup still only ever checks `lastWithdrawRequest`).

### Recommendation
Key the loss-recovery price by the *receipt's* epoch rather than a single lookup: store `lossRecoveryPriceByEpoch` under the epoch each pending receipt was requested in (or maintain a per-user set of unclaimed loss epochs), and make both `requestWithdraw`'s guard and `_claimLossAdjustedWithdrawRequest` scan/derive the correct epoch instead of trusting `lastWithdrawRequest[_user]` as the sole index. Alternatively, record request epoch = `epochNumber` and forbid the `epochNumber` bump between request accounting and `collectWithdrawFunds`, and revert in `requestWithdraw` whenever *any* non-claimed `withdrawsRequestsByEpoch` entry has a nonzero `lossRecoveryPriceByEpoch`.

function testLossHaircutEscape() external {
    address attacker = makeAddr("attacker");
    // 1. Epoch N buffer: attacker deposits AA and requests withdraw of amount A
    _depositWithUser(attacker, 1_000_000 * ONE_SCALE, true);
    uint256 reqEpoch = vault.epochNumber();              // == N
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));     // lastWithdrawRequest=N, withdrawsRequestsByEpoch[att][N]=A

    // 2. startEpoch N, borrower underpays -> stopEpochWithDuration(_lossAmount>0)
    vm.prank(manager); cdoEpoch.startEpoch();
    deal(underlying, borrower, _expectedFundsEndEpoch() - LOSS);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager); cdoEpoch.stopEpochWithDuration(APR, LOSS, DUR);
    // collectWithdrawFunds wrote lossRecoveryPriceByEpoch[N+1] (epochNumber bumped), NOT [N]

    // 3. New buffer: attacker opens a small second request R2
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(SMALL, address(AAtranche)); // guard reads price[N]==0 -> passes; lastWithdrawRequest=N+1... 
    // 4. After next stop funds R2: attacker claims
    _runOneMoreEpochFullyFunded();
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    assertGt(underlying.balanceOf(attacker) - balPre, expectedHaircutAmount);

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  /// @notice Clear a normal/APR0 withdraw receipt for one request epoch.
  /// @dev This does not move funds or burn receipt tokens. Default claims also decrease
  /// `apr0TotalPrincipal`; loss-adjusted claims do not because stopEpoch already closed that bucket.
  /// @param _user address of the user
  /// @param _claimEpoch epoch whose receipt should be cleared
  /// @param _isClearingApr0 true when clearing an open APR0 default claim
  /// @return claimBasis claim amount before applying the recovery ratio
  /// @return burnAmount strategy-token receipt amount to burn
  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }
