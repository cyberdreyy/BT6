### Title
Lockup contract accepts unvalidated `VestingSchedule` at initialization, permanently bricking balance/getter functions and freezing owner funds - (File: `lockup/src/lib.rs`)

### Summary
The `LockupContract::new` initializer never calls `VestingSchedule::assert_valid()` when a plaintext `VestingScheduleOrHash::VestingSchedule` is supplied, even though that validation method exists specifically to enforce `start_timestamp <= cliff_timestamp <= end_timestamp` and `start_timestamp < end_timestamp`. Because the check is skipped at construction time, a caller can deploy a lockup contract whose vesting schedule produces a division-by-zero panic inside `get_unvested_amount`/`get_locked_amount` for the entire "vesting in progress" window, permanently freezing the tokens locked in that account. This mirrors the reported bug class: parameters accepted at creation time cause every subsequent "distribution"/getter call to revert, trapping the contract.

### Finding Description
`LockupContract::new` builds `vesting_information` directly from the caller-supplied schedule without validation: [1](#0-0) 

The validation helper `VestingSchedule::assert_valid()` exists and enforces the invariants needed for the arithmetic in the getters to be safe, but it is defined and simply never invoked from `new`: [2](#0-1) 

The unvalidated schedule is later consumed by `get_unvested_amount`, which divides by `total_time = end_timestamp - start_timestamp`: [3](#0-2) 

If an attacker sets `start_timestamp == end_timestamp` (with `cliff_timestamp` strictly less than `end_timestamp`), then for the entire time range `cliff_timestamp <= block_timestamp < end_timestamp` the code reaches the `else` branch and computes `total_time = 0`, causing every call to `get_unvested_amount` — and consequently `get_locked_amount`, which calls it — to panic: [4](#0-3) 

`get_locked_amount` is used pervasively to gate transfers, staking, and termination flows, so once it panics deterministically, the owner (and the foundation, in a termination scenario) can no longer compute a usable balance for that lockup account, freezing its NEAR indefinitely — the same "trapped contract" outcome described in the ERC20 report where `faceValueRemaining` reverts and blocks `distributeBonds`.

This is reachable by an unprivileged party: the lockup factory documents that "any user" can fund and create a lockup contract for an arbitrary `owner_account_id`, forwarding the caller-supplied `vesting_schedule` (including a plaintext `VestingSchedule`) straight to `LockupContract::new` without the factory performing the missing validation either.

### Impact Explanation
This breaks the custody binding between "tokens locked for owner X" and "tokens the owner (or foundation) can actually retrieve." Once such a schedule is deployed, `get_locked_amount`/`get_unvested_amount` deterministically panic for a large portion (or all) of the lockup account's lifetime, so the owner cannot transfer, stake, or withdraw, and the foundation cannot compute `unvested_amount` to terminate and reclaim funds either. Per the impact classification, locked/unvested tokens becoming permanently unreachable maps to "funds permanently frozen," a Critical-severity outcome.

### Likelihood Explanation
Any account can call the lockup factory's public `create` method (or directly deploy+init a lockup contract) supplying a plaintext `VestingSchedule` for any target `owner_account_id`. No victim key, foundation privilege, or special deployment condition is required — only a crafted set of three u64 timestamps satisfying `start_timestamp == end_timestamp` and `cliff_timestamp < end_timestamp`. This is a low-effort, fully attacker-controlled precondition.

### Recommendation
Call `vesting_schedule.assert_valid()` inside `LockupContract::new` for the `VestingScheduleOrHash::VestingSchedule` branch before constructing `VestingInformation::VestingSchedule`, mirroring the validation already implemented but unused. Additionally, guard the division in `get_unvested_amount` (and any similar arithmetic in `get_locked_amount`) against a zero `total_time` denominator as defense in depth.

### Proof of Concept
1. Attacker calls the lockup factory's `create` (or directly the lockup contract's `new`) with:
   - `owner_account_id`: any target account name (no key required)
   - `vesting_schedule`: `{"VestingSchedule": {"start_timestamp": "1000", "cliff_timestamp": "0", "end_timestamp": "1000"}}`
   - other parameters minimally valid (valid whitelist account, no lockup_duration conflicts)
2. Contract initializes successfully because `assert_valid()` is never called (`lockup/src/lib.rs:216-228`).
3. At any `block_timestamp` in `[0, 1000)`, any subsequent call to `get_unvested_amount`/`get_locked_amount` computes `total_time = end_timestamp - start_timestamp = 0` and panics on division by zero (`lockup/src/getters.rs:140-145`), permanently blocking owner transfers/staking and foundation termination against this account's locked NEAR.

impl VestingSchedule {
    pub fn assert_valid(&self) {
        assert!(
            self.start_timestamp.0 <= self.cliff_timestamp.0,

    /// Returns the amount of tokens that are locked in the account due to lockup or vesting.
    pub fn get_locked_amount(&self) -> WrappedBalance {
        let lockup_amount = self.lockup_information.lockup_amount;
        if let TransfersInformation::TransfersEnabled {
            transfers_timestamp,
        } = &self.lockup_information.transfers_information
        {
            let lockup_timestamp = std::cmp::max(
                transfers_timestamp
                    .0
                    .saturating_add(self.lockup_information.lockup_duration),
                self.lockup_information.lockup_timestamp.unwrap_or(0),
            );
            let block_timestamp = env::block_timestamp();
            if lockup_timestamp <= block_timestamp {
                let unreleased_amount =
                    if let &Some(release_duration) = &self.lockup_information.release_duration {
                        let end_timestamp = lockup_timestamp.saturating_add(release_duration);
                        if block_timestamp >= end_timestamp {
                            // Everything is released
                            0
                        } else {
                            let time_left = U256::from(end_timestamp - block_timestamp);
                            let unreleased_amount = U256::from(lockup_amount) * time_left
                                / U256::from(release_duration);
                            // The unreleased amount can't be larger than lockup_amount because the
                            // time_left is smaller than total_time.
                            unreleased_amount.as_u128()
                        }
                    } else {
                        0
                    };

                let unvested_amount = match &self.vesting_information {
                    VestingInformation::VestingSchedule(vs) => self.get_unvested_amount(vs.clone()),
                    VestingInformation::Terminating(terminating) => terminating.unvested_amount,
                    // Vesting is private, so we can assume the vesting started before lockup date.
                    _ => U128(0),
                };
                return std::cmp::max(
                    unreleased_amount
                        .saturating_sub(self.lockup_information.termination_withdrawn_tokens),
                    unvested_amount.0,
                )
                .into();
            }
        }
        // The entire balance is still locked before the lockup timestamp.
        (lockup_amount - self.lockup_information.termination_withdrawn_tokens).into()
    }

    pub fn get_unvested_amount(&self, vesting_schedule: VestingSchedule) -> WrappedBalance {
        let block_timestamp = env::block_timestamp();
        let lockup_amount = self.lockup_information.lockup_amount;
        match &self.vesting_information {
            VestingInformation::Terminating(termination_information) => {
                termination_information.unvested_amount
            }
            VestingInformation::None => U128::from(0),
            _ => {
                if block_timestamp < vesting_schedule.cliff_timestamp.0 {
                    // Before the cliff, nothing is vested
                    lockup_amount.into()

                    // After the end, everything is vested
                    0.into()

                    // cannot overflow since block_timestamp < vesting_schedule.end_timestamp

                        vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0,

                    // The unvested amount can't be larger than lockup_amount because the
                    // time_left is smaller than total_time.
                    unvested_amount.as_u128().into()
