## Title
Stale rejection weight is never cleared when a signer switches from reject to accept, permanently inflating the miner's aggregated rejection tally beyond real signer opinion - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tallies signer votes for a block proposal into `BlockStatus.total_weight_approved` and `BlockStatus.total_weight_rejected`, which `SignerCoordinator` polls to decide whether a block is approved, rejected, or should keep waiting [1](#0-0) . When a signer flips its vote for the *same* block hash from `Rejected` to `Accepted`, the accept path correctly adds the signer's weight to `total_weight_approved`, but nothing ever removes that signer's earlier weight contribution from `total_weight_rejected`. The rejected tally is monotonically increasing per unique responding slot and is never reconciled with a signer's later, superseding vote, unlike the signer-side `SignerDb`, which explicitly deletes a stale rejection row once a signature is recorded for the same signer/block [2](#0-1) .

### Finding Description
On receiving a `BlockResponse::Accepted` message, the weight is added to `total_weight_approved` only if the slot is not already present in `gathered_signatures`, and the slot is also inserted into `responded_signers`: [3](#0-2) 

On receiving a `BlockResponse::Rejected` message, weight is added to `total_weight_rejected` only if the slot was not already present in `responded_signers` (i.e., a de-dup on the same set used by both accept and reject): [4](#0-3) 

There is no code path anywhere in `stackerdb_listener.rs` that decrements or clears `total_weight_rejected` for a slot that has since sent an `Accepted` response, and no path that clears a slot's `gathered_signatures`/`total_weight_approved` if it later rejects either (the latter is a deliberate design choice, per the comment in `reset_rejections`) [5](#0-4) . `reset_rejections` only clears rejection weight when the *entire proposal* times out and is retried; it does not run on a per-signer reject→accept transition [6](#0-5) .

This is the exact bug class from the external report: a "receipt" (rejection weight already tallied for a slot) is left in the aggregate state after the underlying condition it represented (the signer's opposition to the block) has been withdrawn/superseded, so a later check against that aggregate (`total_weight_rejected` vs. `weight_threshold`) is evaluated against a stale, inflated value rather than the signers' verified/live opinions.

By contrast, the signer-local `SignerDb::add_block_signature` explicitly deletes the corresponding `block_rejection_signer_addrs` row for that signer/block when a signature supersedes a prior rejection, which is validated by the `reject_then_accept` test [7](#0-6) . The node-side coordinator/listener aggregation was never given the analogous cleanup.

### Impact Explanation
`total_weight_rejected` crossing `total_weight - weight_threshold` causes the coordinator to immediately abandon the current block proposal with `NakamotoNodeError::SignersRejected` [8](#0-7) . Because rejected weight only accumulates and never reflects a signer's subsequent, corrected `Accepted` vote for that same block, a set of signers whose weight is individually below the blocking minority but who each transiently reject (e.g., due to timing differences in validation, restart replay, or benign flapping) and then accept can cumulatively push `total_weight_rejected` past the blocking-minority threshold well before the real, live opinion of the signer set would ever have blocked the block. This forces the miner to discard a proposal that in reality has (or would have) reached the acceptance threshold, wedging tenure progress and forcing repeated re-proposals — a liveness impact on block production that requires no majority of colluding signers, only ordinary vote flapping by a minority.

### Likelihood Explanation
Reject→accept transitions for the same block are an explicitly supported, non-adversarial signer behavior (the signer's own `SignerDb` and docs describe rejection as "a revocable opinion") [9](#0-8) , and can be triggered by ordinary conditions such as a signer re-validating a block after a transient failure, a delayed pre-commit interpreted as a rejection, or benign timing races among the ~30+ mainnet signers. No majority collusion, key access, or privileged position is required — a small number of signers whose combined weight approaches (but does not need to reach) the blocking-minority threshold is sufficient.

### Recommendation
Mirror the fix pattern already used in `SignerDb::add_block_signature` [2](#0-1) : when processing a `BlockResponse::Accepted` for a slot that is already present in `responded_signers` due to a prior rejection, subtract that signer's weight from `total_weight_rejected` (and remove any per-txid `failed_txids` contribution attributed to that signer) before adding it to `total_weight_approved`, so the aggregated tallies always reflect only the signer's most recent, live vote.

### Proof of Concept
1. Miner proposes block `B` and calls `StackerDBListenerComms::insert_block(B)`, initializing `total_weight_approved = 0`, `total_weight_rejected = 0` [10](#0-9) .
2. Signers `S1..Sk`, whose combined weight is just under the blocking-minority threshold (`total_weight - weight_threshold`), each transiently send `BlockResponse::Rejected(B)` (e.g., due to a brief validation hiccup). Each is a new slot in `responded_signers`, so each adds its weight to `total_weight_rejected` [4](#0-3) .
3. All of `S1..Sk` then re-validate and send `BlockResponse::Accepted(B)`. Each adds its weight to `total_weight_approved` (since none had a `gathered_signatures` entry yet) — but `total_weight_rejected` is never reduced [3](#0-2) .
4. A disjoint signer `S_extra`, holding just enough weight to bridge the remaining gap to the blocking-minority threshold, sends a single genuine `Rejected(B)`. Because `S1..Sk`'s stale rejected weight from step 2 was never removed, `total_weight_rejected(S1..Sk, S_extra) + weight_threshold > total_weight` is now true even though the live/current opinion is `S1..Sk` = accept, only `S_extra` = reject (well under the real blocking minority).
5. `SignerCoordinator::wait_for_signatures` observes this and returns `Err(NakamotoNodeError::SignersRejected)` [8](#0-7) , causing the miner to abandon block `B` even though the real, current signer weight opposing it does not constitute a blocking minority — reproducing the "stale receipt breaks the aggregate/verified-state equality" pattern from the external report.

impl StackerDBListenerComms {
    /// Insert a block into the block status map with initial values.
    pub fn insert_block(&self, block: &NakamotoBlockHeader) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        let block_status = BlockStatus {
            responded_signers: HashSet::new(),
            gathered_signatures: BTreeMap::new(),
            total_weight_approved: 0,
            total_weight_rejected: 0,
            failed_txids: HashMap::new(),
        };
        blocks.insert(block.signer_signature_hash(), block_status);
    }

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
