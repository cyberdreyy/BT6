### Title
Attacker-controlled MessageId collision causes cross-user response hijacking/loss in WebAPI capabilities gateway handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The gateway's legacy WebAPI trigger handler stores each in-flight user request's callback in a shared map keyed solely by `msg.Body.MessageId`, a value taken verbatim from the client-supplied JSON-RPC request ID. Because this ID is never checked for uniqueness against other concurrently pending requests, one unprivileged client can supply a `MessageId` that collides with another (victim) client's currently pending request, overwriting the victim's saved callback and diverting/losing the victim's asynchronous response — analogous to how `LimitOrderRegistry` fails to segregate one user's pending assets from another's, letting an unrelated actor's action wipe out a victim's holdings.

### Finding Description
`HandleLegacyUserMessage` stores the caller's callback keyed only by the message ID supplied in the request: [3](#0-2) 

This `MessageId` originates entirely from the untrusted request: `DecodeJSONRequest` copies `request.ID` (the JSON-RPC `id` field, fully attacker-controlled) into `msg.Body.MessageId`: [1](#0-0) 

`Message.Validate` only enforces length bounds and a null-terminator check on `MessageId` — it does not verify it is unique, unpredictable, or bound to the sender: [2](#0-1) 

When node responses come back, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageId`, then routes the *first* response with that ID to whichever callback is currently stored there: [4](#0-3) 

Attack flow:
1. Victim A submits a WebAPI trigger request; the gateway registers `savedCallbacks[X] = victimA_callback` and forwards the request to DON members.
2. Before the DON responds, attacker B submits their own (unrelated) WebAPI trigger request but sets the JSON-RPC request `id` to the same value `X` that victim A is using (or brute-forces/observes it, since there's no server-side randomization or per-sender namespacing of the key).
3. `savedCallbacks[X]` is overwritten with `attackerB_callback`, silently discarding victim A's callback reference (no error, no collision detection).
4. When the DON's response for victim A's original job arrives tagged with message id `X`, `handleWebAPITriggerMessage` matches it against `savedCallbacks[X]`, which now points to attacker B's HTTP connection, and sends victim A's response payload to attacker B instead. Victim A's request meanwhile hangs until pruned/timed out.

This is a direct cross-user response confusion: an unprivileged actor can hijack or destroy another unprivileged user's pending request/response purely by choosing a colliding client-supplied identifier, with no authentication or ownership check tying the callback slot to the sender.

### Impact Explanation
This breaks isolation between unprivileged users of the same DON-facing gateway service:
- **Response hijacking**: an attacker can receive another user's private workflow-trigger response data.
- **Denial/loss for the victim**: the victim's original request never resolves for them (delivered elsewhere), which for any downstream job-run or fund-moving workflow triggered via `web_api_trigger` constitutes unauthorized diversion of a user's expected result — the same "assets go to the wrong party, victim gets nothing" pattern as the source report.
Because callback delivery is only first-response-wins and unauthenticated by sender identity, this could be exploited at scale against any concurrent user of the shared WebAPI trigger handler.

### Likelihood Explanation
Likelihood is high for any deployment exposing the legacy `web_api_trigger` handler to multiple untrusted external callers concurrently, since:
- The colliding value is a plain client-supplied string with no requirement of randomness or entropy (just needs to match an in-flight ID, and IDs are bounded to 128 bytes with only trivial validation).
- No rate limiting or verification ties an ID to a specific sender before or after registration in `savedCallbacks`.
- The race window is the full round-trip time to the DON, typically at least tens/hundreds of milliseconds, giving ample opportunity for an attacker who can guess or observe IDs (e.g., sequential/predictable IDs from a shared client library) to collide.

### Recommendation
Namespace the `savedCallbacks` key by sender identity (or a server-generated nonce) in addition to `MessageId`, e.g. `key := {sender, messageId}` similar to the pattern already used in `common/requestcache.go`'s `globalId{sender, id}` [5](#0-4) , and reject/error on collision rather than silently overwriting an existing entry. Additionally consider generating the tracking ID server-side rather than trusting the client-controlled JSON-RPC `id` for internal state-map keys.

### Proof of Concept
1. Client A sends a legacy `web_api_trigger` message with `body.message_id = "abc"`, properly signed; gateway stores `savedCallbacks["abc"] = A's callback` and forwards to DON members.
2. Before DON responds, Client B (unrelated, unprivileged) sends its own legacy `web_api_trigger` message, also setting `body.message_id = "abc"` (valid signature over its own payload — signature covers `MessageId`, but nothing prevents reusing the same string value across different senders since uniqueness isn't enforced); this overwrites `savedCallbacks["abc"]` with B's callback (`HandleLegacyUserMessage` line 412).
3. DON node responds to the original request tagged with `message_id="abc"`; `handleWebAPITriggerMessage` (lines 148-162) looks up `savedCallbacks["abc"]`, finds B's callback, and delivers A's response data to B while A's connection never receives anything until it eventually times out via `pruneCallbacks`.

	msg.Body.Method = request.Method

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

type globalId struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
