### Title
Missing re-initialization guard in `LockupContract::new` allows unauthorized owner takeover and instant release of locked/vesting NEAR - (File: `lockup/src/lib.rs`)

### Summary
`LockupContract::new` is a public `#[init]` function that anyone can invoke via a normal function-call transaction against the deployed lockup account, and — unlike every other contract in this codebase (`staking-pool`, `whitelist`, `voting`, `multisig`, `multisig2`, `lockup-factory`, `staking-pool-factory`) — it has no `assert!(!env::state_exists(), ...)` guard and no caller/admin restriction. This is the exact bug class described in the reference report (`NoteInterest.initialize` re-callable), but here it maps onto a contract that literally custodies NEAR and enforces a lockup/vesting schedule, so re-initialization is far more severe: it lets an unprivileged attacker overwrite `owner_account_id` and reset the lockup/vesting bookkeeping, then drain the account's liquid balance as the new "owner". [1](#0-0) 

### Finding Description
`LockupContract::new` builds `owner_account_id`, `lockup_information` (using `env::account_balance()` as `lockup_amount`, `termination_withdrawn_tokens: 0`), `vesting_information`, `staking_information: None`, and `foundation_account_id` purely from caller-supplied arguments, with the only checks being format validation of account IDs — no check on `env::predecessor_account_id()` and no check that the contract was not already initialized: [2](#0-1) 

Contrast this with every sibling contract in the repo, which explicitly guards against re-initialization: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

This confirms the SDK version used here does not automatically prevent `#[init]` re-invocation — each contract must add the `env::state_exists()` assertion itself, and `LockupContract::new` is the one contract that omits it.

Every privileged "owner" operation in `lockup/src/owner.rs` (e.g. `transfer`, `add_full_access_key`, staking operations) is gated solely by: [9](#0-8) 

i.e. `predecessor_account_id == self.owner_account_id`. Because `owner_account_id` is fully attacker-controlled on re-init, calling `new` again with `owner_account_id = attacker` makes `assert_owner()` pass for the attacker on all subsequent owner methods.

Binding broken (equality that should hold but doesn't):
`locked_amount_reported_by_get_locked_amount() == NEAR that is actually restricted by the original lockup/vesting schedule and only movable by the original owner`

Before attack: `owner_account_id = O`, `lockup_information.lockup_amount = A` (original locked amount), possibly `vesting_information = VestingSchedule(vs)` with a cliff/end far in the future, `transfers_information` possibly `TransfersDisabled`.

After attacker calls `new(attacker, 0, None, TransfersInformation::TransfersEnabled{transfers_timestamp: 0}, None /* vesting_schedule */, None, whitelist_id, None)`:
- `owner_account_id = attacker`
- `vesting_information = VestingInformation::None` (since attacker passes no vesting schedule) ⇒ `get_unvested_amount` returns 0 unconditionally: [10](#0-9) 
- `lockup_information.lockup_amount = env::account_balance()` at call time, `lockup_duration = 0`, `lockup_timestamp = None`, `release_duration = None`, `transfers_timestamp = 0` ⇒ in `get_locked_amount`, `lockup_timestamp <= block_timestamp` is true immediately, `release_duration` is `None` so `unreleased_amount = 0`, and `unvested_amount = 0` ⇒ `get_locked_amount()` returns `0`: [11](#0-10) 

With `get_locked_amount() == 0`, `get_owners_balance()` and `get_liquid_owners_balance()` report the (almost) full account balance as freely transferable: [12](#0-11) 

The attacker (now `owner_account_id`) then calls `transfer(amount, attacker_receiver)`, which only checks `assert_owner`, transfer-enabled, no staking pool busy, no termination, and the liquid-balance bound computed above — all of which the attacker just set to permit a full drain: [13](#0-12) 

### Impact Explanation
This is Critical severity under the stated rubric: "NEAR ... moved by a party not entitled to it" and "locked or unvested tokens released early." A previously-locked/vesting lockup contract's entire NEAR balance (minus `MIN_BALANCE_FOR_STORAGE`) can be seized by an arbitrary unprivileged account that was never the owner, foundation, or whitelist — simply by sending one function-call transaction re-invoking `new`, followed by `transfer`. This breaks the core custody invariant the entire `lockup` contract exists to enforce (funds are inaccessible until the lockup/vesting schedule permits release, and only the designated owner may withdraw).

### Likelihood Explanation
Likelihood is high given the vulnerability requires only a single unauthenticated function call to a deployed lockup contract — no privileged role, no race condition dependent on validators, and no dependency on any other contract's misbehavior. The only precondition is that the lockup contract's `new` method remains callable post-deployment, which is true for the entire lifetime of the contract (no code path removes or disables `new`, and `#[init]` in this SDK version does not implicitly block re-invocation).

### Recommendation
Add `assert!(!env::state_exists(), "Already initialized");` as the first statement of `LockupContract::new`, mirroring the guard already present in `staking-pool`, `whitelist`, `voting`, `multisig`, `lockup-factory`, and `staking-pool-factory`. This is the correct, minimal fix and is a design pattern the codebase already applies everywhere else — it was simply missed in `lockup/src/lib.rs`.

### Proof of Concept
1. `LockupFactory::create` deploys and initializes a lockup contract `L` for owner `O` with a multi-year vesting schedule and NEAR locked in it: [14](#0-13) 
2. Attacker `A` (any account, no special key) sends a function call transaction to `L` invoking `new` with:
   - `owner_account_id = A`
   - `transfers_information = TransfersEnabled { transfers_timestamp: 0 }`
   - `vesting_schedule = None`
   - `lockup_duration = 0`, `release_duration = None`
   This succeeds because `LockupContract::new` has no re-init guard: [1](#0-0) 
3. `L`'s state is overwritten: `owner_account_id = A`, `vesting_information = None`, `lockup_information.lockup_amount = current balance`, transfers immediately "enabled" since epoch 0.
4. `get_locked_amount()` now evaluates to `0`: [11](#0-10) 
5. Attacker calls `L.transfer(amount, A)` — passes `assert_owner()` (since `owner_account_id == A`), passes `assert_transfers_enabled()`, and the `get_liquid_owners_balance()` bound now covers nearly the whole account balance: [13](#0-12) 
6. NEAR that was supposed to remain locked/vesting for years is transferred out to the attacker.

    /// Returns the amount of tokens that are locked in the account due to lockup or vesting.
    pub fn get_locked_amount(&self) -> WrappedBalance {
        let lockup_amount = self.lockup_information.lockup_amount;
        if let TransfersInformation::TransfersEnabled {
            transfers_timestamp,
        } = &self.lockup_information.transfers_information
        {
            let lockup_timestamp = std::cmp::max(
                transfers_timestamp
                    .0
                    .saturating_add(self.lockup_information.lockup_duration),
                self.lockup_information.lockup_timestamp.unwrap_or(0),
            );
            let block_timestamp = env::block_timestamp();
            if lockup_timestamp <= block_timestamp {
                let unreleased_amount =
                    if let &Some(release_duration) = &self.lockup_information.release_duration {
                        let end_timestamp = lockup_timestamp.saturating_add(release_duration);
                        if block_timestamp >= end_timestamp {
                            // Everything is released
                            0
                        } else {
                            let time_left = U256::from(end_timestamp - block_timestamp);
                            let unreleased_amount = U256::from(lockup_amount) * time_left
                                / U256::from(release_duration);
                            // The unreleased amount can't be larger than lockup_amount because the
                            // time_left is smaller than total_time.
                            unreleased_amount.as_u128()
                        }
                    } else {
                        0
                    };

                let unvested_amount = match &self.vesting_information {
                    VestingInformation::VestingSchedule(vs) => self.get_unvested_amount(vs.clone()),
                    VestingInformation::Terminating(terminating) => terminating.unvested_amount,
                    // Vesting is private, so we can assume the vesting started before lockup date.
                    _ => U128(0),
                };
                return std::cmp::max(
                    unreleased_amount
                        .saturating_sub(self.lockup_information.termination_withdrawn_tokens),
                    unvested_amount.0,
                )
                .into();
            }
        }
        // The entire balance is still locked before the lockup timestamp.
        (lockup_amount - self.lockup_information.termination_withdrawn_tokens).into()
    }
