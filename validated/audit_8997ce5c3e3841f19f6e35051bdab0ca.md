### Title
Signer weight double-counted across accept/reject tallies when a signer flips its vote - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`BlockStatus.total_weight_approved` and `BlockStatus.total_weight_rejected` are two independently-incremented running totals maintained by the node's StackerDB listener as `BlockResponse` messages arrive from signers. Unlike the ReseedSilo bug (where a per-account update failed to flow into a global aggregate), here the bug is the mirror case: a per-signer state change (switching a vote) is allowed to flow into *both* aggregates instead of maintaining a single consistent global invariant (`total_weight_approved + total_weight_rejected <= total_weight`, one weight contribution per signer). A signer that first rejects and later accepts the same block gets its weight added to `total_weight_rejected` and then, independently, to `total_weight_approved`, because the guard on the accept path only checks `gathered_signatures` (empty for a signer who only rejected before) and never checks `responded_signers`/prior rejection state.

### Finding Description
In `stackerdb_listener.rs`, the `BlockResponse::Rejected` arm gates the increment with: [1](#0-0) 

`responded_signers.insert(slot_id)` returns `true` only the first time this `slot_id` is seen for this block, so a prior Accept correctly blocks a later double-counted Reject.

However, the `BlockResponse::Accepted` arm gates its increment differently: [2](#0-1) 

The check is `!block.gathered_signatures.contains_key(&slot_id)`, not a check against `responded_signers`. If the signer's first message for this block was a `Rejected` (which inserts the slot into `responded_signers` but *not* into `gathered_signatures`), then a subsequent `Accepted` message from the same signer passes the `!gathered_signatures.contains_key(&slot_id)` check and adds the signer's weight to `total_weight_approved` a second time — on top of the weight already added to `total_weight_rejected`. The `responded_signers` set is shared as a general "has responded" set but the two vote-tally paths (`total_weight_approved` vs `total_weight_rejected`) use inconsistent membership checks (`gathered_signatures` vs `responded_signers`), breaking the intended invariant that a signer's weight is attributed to at most one side of the tally.

This is precisely a "rejection recounted as an accept" pattern: the signer's earlier Reject vote is never retracted from `total_weight_rejected`, yet the same weight is separately recounted into `total_weight_approved`.

### Impact Explanation
`SignerCoordinator::get_block_status` (in `signer_coordinator.rs`) uses these two counters directly to decide the miner's outcome for a proposed block: [3](#0-2) 

Because a single flipping signer inflates *both* sides simultaneously, the aggregated-weight vs. verified-accepts equality that the miner relies on to decide accept/reject is broken:
- `total_weight_rejected` can retain stale weight from a signer who has since switched to Accept, causing the node to spuriously treat the block as rejected (`SignersRejected`, dropping/banning transactions) even though the true, current willing-to-accept weight might already satisfy the 70% threshold.
- Conversely, it also means the acceptance path can be reached while a phantom rejection weight lingers, corrupting the miner's rejection-timeout/backoff logic (`rejections` tracking in `get_block_status`) and the per-txid failed/problematic-tx accounting that is keyed off `total_weight_rejected`/`blocking_minority`.

This is a liveness/miscount defect reachable by a single misbehaving or flapping signer controlling only its own StackerDB slot — no majority is required — and it corrupts the miner-side vote tally that gates whether a block is treated as globally accepted or globally rejected.

### Likelihood Explanation
Any single signer (malicious, buggy, or simply reconsidering after a state update) can trigger this by writing two sequential `BlockResponse` chunks to its own StackerDB slot for the same block: first `Rejected`, then `Accepted`. This requires no coordination with other signers, no majority weight, and no privileged access — only the signer's own signing key and normal StackerDB write access, which is exactly the "one slot + gossip" threat model in scope.

### Recommendation
Use a single, consistent per-slot "which side did this signer's weight land on" record (or reuse `responded_signers`) for *both* the accept and reject increment guards, and make vote-switching an explicit transition: if a slot's weight was previously counted toward `total_weight_rejected`, either (a) refuse to also add it to `total_weight_approved`, or (b) subtract it from `total_weight_rejected` before adding it to `total_weight_approved` (and vice versa), so the invariant `total_weight_approved + total_weight_rejected <= total_weight` always holds and each signer's weight contributes to at most one side of the tally at any point in time.

### Proof of Concept
1. Miner proposes block `B`; `SignerCoordinator` begins `get_block_status(B)`, and the `stackerdb_listener` initializes `BlockStatus { total_weight_approved: 0, total_weight_rejected: 0, gathered_signatures: {}, responded_signers: {} }` for `B`.
2. Signer `S` at `slot_id = k` (weight `w`) writes a `BlockResponse::Rejected` chunk for `B` to its own slot.
   - `responded_signers.insert(k)` → `true` ⇒ `total_weight_rejected += w`.
3. Signer `S` then writes a `BlockResponse::Accepted` chunk for `B` to the same slot (e.g., after reconsidering, or deliberately to attack the tally).
   - Guard checks `!gathered_signatures.contains_key(&k)` → `true` (never inserted for a Reject) ⇒ `total_weight_approved += w`.
   - `gathered_signatures.insert(k, signature)`; `responded_signers.insert(k)` (no-op, already present).
4. Now `total_weight_approved + total_weight_rejected = 2w` counted from a single signer of weight `w`, violating the intended one-vote-per-signer invariant and corrupting both the acceptance-threshold check and the rejection/timeout logic in `SignerCoordinator::get_block_status`.
