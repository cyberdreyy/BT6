### Title
`defaultPendingClaimBasis` reads only the current-epoch instant-withdraw bucket, so stale instant receipts from earlier epochs are excluded from the default recovery basis — inflating `defaultRecoveryPrice` and permanently stranding older claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Analog of the NTLM type-2 bug: a caller-controlled "length + offset" pair that is never bounds-checked. Here, the claim basis is a length and the epoch index is an offset. `defaultPendingClaimBasis()` dereferences `instantWithdrawClaimsByEpoch[epochNumber]` (the current offset) while `pendingInstantWithdraws` — the unfunded remainder used as the reachability flag — is an aggregate over *all* epochs. When instant receipts older than the default epoch remain unfunded, the basis is read from the wrong "offset" (out-of-bounds accounting read), `defaultRecoveryPrice` is computed against a truncated basis, and the stranded claimants can never be paid.

### Finding Description
`pendingInstantWithdraws` is decremented only by `collectInstantWithdrawFunds` (line 398-403) and by `_claimDefaultedInstantWithdrawRequest` (line 852). If the CDO underfunds the instant queue at a `stopEpoch` (borrower returned less than requested), the unfunded remainder of `instantWithdrawsRequests` survives into the next epoch unchanged. Those receipts were recorded under `instantWithdrawsRequestsByEpoch[user][oldEpoch]` / `instantWithdrawClaimsByEpoch[oldEpoch]` (lines 371-372).

At default finalization, `finalizeDefaultRecovery` → `defaultPendingClaimBasis()` (lines 644-649) computes:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber]; // current epoch only
}
```

Any instant basis recorded under older epochs is silently dropped even though `pendingInstantWithdraws != 0` flags it as unfunded. Consequences:

- `recoveryPrice = reserveAmount * 1e18 / totalBasis` (line 688) is overstated — potentially `> 1e18`, paying included claimants above par from a fixed reserve.
- `_claimDefaultedInstantWithdrawRequest` (lines 842-856) only clears `instantWithdrawsRequestsByEpoch[user][defaultEpoch]`; older-epoch receipts return `claimBasis == 0`, then fall through to `claimInstantWithdrawRequest`'s par payout of `instantWithdrawsRequests[user]` via `_transferFundedClaim` — which is guarded to never spend `defaultRecoveryReserve` (lines 897-905). Since these receipts were never funded, the claim either reverts on the reserve guard or drains reserve that belongs to defaulted-epoch claimants, and once `defaultRecoveryReserve` is depleted `defaultRecoveryReserve -= _amount` (line 915) underflows, freezing all remaining recovery claims.
- Likewise `_defaultPrefundedInstantReserve` (lines 716-723) uses `instantBasis > pendingInstant` on the same wrong-epoch index, misclassifying funded vs unfunded instant cash.

### Impact Explanation
Direct theft and permanent freezing. Claimants whose instant receipts sit in the defaulted epoch receive an inflated recovery price and can extract the entire `defaultRecoveryReserve` (potentially above par), while claimants with identical unfunded receipts from earlier epochs receive nothing — their claims are permanently stranded because the receipt accounting (`instantWithdrawsRequests`) persists but no funded or reserve-backed payout path exists for them. Loss is bounded by the stale instant receipt total; every underlying unit in `defaultRecoveryReserve` is either overpaid to epoch-N claimants or frozen.

### Likelihood Explanation
Requires: (a) an unfunded instant-withdraw remainder surviving a `stopEpoch`/`startEpoch` boundary (borrower underfunds the instant queue — plausible whenever instant demand exceeds returned cash), and (b) a subsequent borrower default finalized via `finalizeDefaultRecovery`. All attacker-facing actions (`requestInstantWithdraw`, claims) are unprivileged KYC-lender calls; the honest borrower/manager merely sequence the epochs. No guard catches it: `defaultRecoveryInitialized` is set at `initialize` (line 147), and `_ensureDefaultRecoveryInitialized` explicitly refuses to clear `pendingInstantWithdraws` (line 926), so the stale bucket reaches finalization intact.

### Recommendation
In `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, compute the instant basis from `pendingInstantWithdraws + already-funded remainder` (i.e., total outstanding `instantWithdrawsRequests` across users) rather than `instantWithdrawClaimsByEpoch[epochNumber]`, or track a global `instantWithdrawClaimsTotal` incremented at request time. In `_claimDefaultedInstantWithdrawRequest`, clear the user's full outstanding `instantWithdrawsRequests[user]` basis (capped at what finalization actually counted) instead of only the `defaultEpoch` slice, so receipts from every epoch share the recovery pro rata.

contract StaleInstantEpochBasis is Test {
    function test_staleInstantReceiptExcludedFromRecovery() public {
        // --- Epoch N ---
        // alice deposits AA, bob deposits AA (or BB), epoch runs.
        // alice calls requestInstantWithdraw(X); strategy mints receipt,
        //   instantWithdrawsRequests[alice] = X,
        //   instantWithdrawsRequestsByEpoch[alice][N] = X,
        //   instantWithdrawClaimsByEpoch[N]   = X, pendingInstantWithdraws = X.
        // borrower returns less than the instant queue at stopEpoch:
        //   collectInstantWithdrawFunds(Y) with Y < X  => pendingInstantWithdraws = X - Y > 0
        //   (alice cannot claim; her receipt is unfunded)
        // --- Epoch N+1 ---
        // startEpoch/stopEpoch increments epochNumber to N+1.
        // carol makes instantWithdraw Z in epoch N+1, also partially unfunded:
        //   pendingInstantWithdraws = (X-Y) + Z
        //   instantWithdrawClaimsByEpoch[N+1] = Z
        // --- Default & finalize ---
        // borrower defaults; owner calls finalizeDefault / CDO calls
        //   finalizeDefaultRecovery(R, recoverySource):
        //   defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[N+1]
        //                              = pendingWithdraws + Z        // alice's X-Y MISSING
        //   recoveryPrice = reserve * 1e18 / basis  // inflated by missing X-Y
        // --- Assertions ---
        // assert: carol.claimInstantWithdrawRequest() pays Z * recoveryPrice / 1e18,
        //         which is MORE than her pro-rata share of reserve.
        // assert: alice.claimInstantWithdrawRequest() ->
        //   _claimDefaultedInstantWithdrawRequest reads [alice][N+1] == 0,
        //   falls through to par claim of X-Y via _transferFundedClaim:
        //   either reverts on `balance - reserve < amount` (frozen forever),
        //   or drains defaultRecoveryReserve belonging to other claimants.
        // assertEq(strategy.defaultRecoveryReserve(), /* leftover locked */ >0)
        //   once reserve hits 0 all further claims revert via underflow at line 915.
    }
}
