### Title
Missing role enforcement on `/v2/debug/pprof/*` routes allows any authenticated user (including UserRoleView) to obtain full process memory/goroutine/CPU dumps - ([File: core/web/router.go])

### Summary
`v2Routes` mounts `metricRoutes(authv2)` at line 446 inside the `authv2` group, which only enforces `auth.Authenticate` (token or session) with no minimum role. Unlike every other sensitive endpoint in the same group, the pprof handlers are never wrapped in `auth.RequiresEditRole` or `auth.RequiresAdminRole`, so a `UserRoleView` session or API token can reach `GET /v2/debug/pprof/heap`, `/goroutine`, `/profile`, and `/trace`.

### Finding Description
`metricRoutes` registers the standard `net/http/pprof` handlers directly on the `authv2` router group: [1](#0-0) 

It is invoked unconditionally from inside the `authv2` block: [2](#0-1) [3](#0-2) 

The `authv2` group's only middleware is `auth.Authenticate(..., auth.AuthenticateByToken, auth.AuthenticateBySession)`, which merely validates that the request is authenticated with *some* user/token and sets `SessionUserKey` — it performs no role check: [4](#0-3) 

Every other route in `v2Routes` that exposes sensitive data or capability is explicitly wrapped with `auth.RequiresEditRole` or `auth.RequiresAdminRole` (e.g. key export/import, user management, log level patching), which check `user.Role` against `clsessions.UserRoleView`/`UserRoleRun`/`UserRoleAdmin` and return 401/403 for insufficiently privileged roles: [5](#0-4) 

Because `metricRoutes(authv2)` skips this wrapping, a `UserRoleView` session or a low-privileged API token passes `Authenticate` and reaches the raw `net/http/pprof` handlers directly (`pprof.Handler("heap")`, `pprof.Handler("goroutine")`, `pprof.Trace`, `pprof.Profile`), with no role gate at all.

### Impact Explanation
`/debug/pprof/heap` and `/debug/pprof/goroutine` dumps expose the full contents of process memory/goroutine stacks, which for a Chainlink node can include decrypted private keys, database connection strings/credentials, other users' session tokens, and OCR/CSA key material held in memory. `/debug/pprof/profile` and `/debug/pprof/trace` additionally allow a low-privileged caller to force the node into extended CPU-profiling/tracing windows (resource exhaustion / DoS potential on a production oracle node). This matches the bounty class of "key or secret disclosure" / "credential exposure" via unauthorized access, reachable by the least-privileged authenticated role (`UserRoleView`), which was intended to only have read access to job/config data, not process internals.

### Likelihood Explanation
The only precondition is possession of any valid session or API token, including the lowest role (`UserRoleView`) or a restricted API token — no admin/edit privilege is required. The path is a single unauthenticated-role-check-away GET request; it is fully reproducible and deterministic, requiring no race condition or special configuration.

### Recommendation
Wrap the pprof route handlers in `metricRoutes` with `auth.RequiresAdminRole` (or at minimum `auth.RequiresEditRole`), consistent with how other sensitive endpoints (key export, log level patch, user management) are protected in `v2Routes`. For example, change each `pprofGroup.GET(...)` call to pass the handler through `auth.RequiresAdminRole(...)`.

### Proof of Concept
Add a table-driven test in `core/web/router_test.go` (or extend the existing RBAC routemap test) mirroring `TestRBAC_Routemap_ViewOnly`:
1. Set up a test app/router via `NewRouter`, create a session/user with `clsessions.UserRoleView`.
2. Authenticate as that view-role user (session cookie or API token).
3. Issue `GET /v2/debug/pprof/heap`, `/v2/debug/pprof/goroutine`, `/v2/debug/pprof/profile` (with short `?seconds=1`), and `/v2/debug/pprof/trace`.
4. Assert the response status is `200 OK` (proving the vulnerability) rather than the expected `401`/`403` that other view-role-restricted routes return.
5. After applying the fix (wrapping handlers with `auth.RequiresAdminRole`/`RequiresEditRole`), assert the same requests now return `401`/`403` for the view-role user, and `200` for an admin/edit-role user.

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
