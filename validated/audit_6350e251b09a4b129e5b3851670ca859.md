### Title
Uninitialized ERC4626 vault share-price inflation can drain programmable-borrower principal - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower` permits an operator to configure any ERC4626 vault sharing the underlying asset, but does not require an initialized share supply, minimum vault liquidity, or a nonzero/minimum number of shares from deposits. An unprivileged user of an empty donation-susceptible vault can become its first depositor, donate enough underlying to make the pool's subsequent deposit mint zero shares, and redeem their single share for both the donation and the pool's principal. [1](#0-0) [2](#0-1) 

### Finding Description
During `startEpoch`, `IdleCDOEpochVariant` transfers available underlying to the configured programmable borrower and invokes `onStartEpoch`. `onStartEpoch` snapshots the pre-deposit asset value as `epochStartVaultAssets`, then calls `_depositToVault` for the entire on-hand balance. [3](#0-2) 

`_depositToVault` calls `vault.deposit(_assetAmount, address(this))` and accepts the returned share amount unconditionally. There is no `previewDeposit`, `minSharesOut`, share-balance delta check, or minimum existing vault liquidity check. [2](#0-1) 

For a standard donation-susceptible ERC4626 with zero supply:

1. Attacker deposits `1` wei and receives one vault share.
2. Attacker transfers `A` underlying directly to the vault.
3. The vault's price per share becomes approximately `A + 1`.
4. An honest manager starts the epoch and `ProgrammableBorrower` deposits `A` pool assets.
5. The pool deposit mints zero shares because `A / (A + 1) == 0`.
6. Attacker redeems the only vault share and receives approximately `2A + 1` assets.

The programmable borrower is left with the strategy-token principal tracked by the CDO but no ERC4626 shares or usable underlying. Later accounting recognizes the missing vault assets as `vaultLoss`, because `_currentVaultAssets()` is near zero while `epochStartVaultAssets` included the deposited principal. [4](#0-3) 

On close-pool settlement, `onStopEpoch` intentionally returns success when the vault position cannot cover the shortfall, deferring the inevitable `transferFrom` failure to the CDO's default path. `IdleCDOEpochVariant` then calls `_handleBorrowerDefault`, leaving LPs to recover only whatever is later supplied through default recovery. [5](#0-4) [6](#0-5) 

### Impact Explanation
The attacker can steal essentially the entire first programmable-borrower deposit routed through a vulnerable empty ERC4626 vault. With pool deposit `A`, attacker cost is `A + 1`, and redemption proceeds are approximately `2A + 1`, yielding profit near `A` because the donated `A` is recovered together with the pool's `A`. [7](#0-6) 

The broken invariant is fair external-vault share minting and solvency: `A` underlying leaves the CDO, but the programmable borrower receives zero claim on the vault. The loss is ultimately crystallized through borrower default and borne by tranche holders according to the default-recovery process. [8](#0-7) [9](#0-8) 

### Likelihood Explanation
The attack requires the configured ERC4626 vault to be empty or nearly empty and vulnerable to donation/share-price inflation, including permitting a zero-share deposit. `setVault` only verifies a nonzero address and matching asset; it does not check `totalSupply`, `totalAssets`, share decimals/offset behavior, or minimum initial liquidity. [10](#0-9) 

No privileged actor performs the attack. The owner or manager only configures a vulnerable vault and later invokes the normal `startEpoch`; an unprivileged ERC4626 vault user performs the first-deposit, donation, and redemption steps. [11](#0-10) 

### Recommendation
Reject vaults that have not been safely initialized, or require protocol-controlled seed liquidity that cannot be diluted by an attacker's first deposit. At minimum, verify both `vault.totalSupply()` and `vault.totalAssets()` meet configured thresholds during `setVault`. [1](#0-0) 

Add slippage protection to `_depositToVault`: calculate expected shares with `previewDeposit`, require at least a caller/protocol-defined `minSharesOut`, and measure the actual share-balance delta after deposit. Revert if it is zero or materially below the expected amount. Epoch entry should fail atomically rather than registering a deposit that received no shares. [12](#0-11) 

For existing deployments, migrate only to vaults with inflation-resistant initialization or virtual-share offsets and make `setVault` enforce a minimum liquidity invariant rather than relying on operator procedure. [13](#0-12) 

### Proof of Concept
The following Foundry sequence reproduces the issue against a configured ERC4626 vault that uses asset-balance accounting and permits a zero-share deposit. It assumes `cdoEpoch`, `programmableBorrower`, `underlying`, and `vault` are initialized using the existing programmable-borrower test fixture, and `ATTACK_AMOUNT` is the first pool deposit routed to `ProgrammableBorrower`.

```solidity
function testFirstDepositorDrainsProgrammableBorrowerDeposit() external {
    address attacker = makeAddr("attacker");
    uint256 depositAmount = 10_000e6;

    // Configure the programmable borrower against an empty donation-susceptible ERC4626.
    // Vault invariant: totalSupply == 0 and totalAssets == underlying.balanceOf(vault).
    assertEq(vault.totalSupply(), 0);
    assertEq(vault.totalAssets(), 0);

    // Attacker creates one share and inflates its price above the upcoming pool deposit.
    deal(address(underlying), attacker, depositAmount + 1);
    vm.startPrank(attacker);
    underlying.approve(address(vault), 1);
    vault.deposit(1, attacker);
    underlying.transfer(address(vault), depositAmount);
    vm.stopPrank();

    assertEq(vault.balanceOf(attacker), 1);
    assertGt(vault.convertToAssets(1), depositAmount);

    // An honest LP deposits and the honest manager starts the epoch.
    deal(address(underlying), lender, depositAmount);
    vm.startPrank(lender);
    underlying.approve(address(cdoEpoch), depositAmount);
    cdoEpoch.depositAA(depositAmount);
    vm.stopPrank();

    vm.warp(block.timestamp + cdoEpoch.bufferPeriod() + 1);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // ProgrammableBorrower deposited its entire balance but received no vault shares.
    assertEq(vault.balanceOf(address(programmableBorrower)), 0);
    assertEq(programmableBorrower.vaultSharesBalance(), 0);

    // The attacker redeems the only share for donation + pool deposit.
    uint256 attackerBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    vault.redeem(1, attacker, attacker);
    assertGe(
        underlying.balanceOf(attacker) - attackerBefore,
        (2 * depositAmount) - 1
    );

    // Accounting now sees principal as vault loss.
    assertEq(programmableBorrower.vaultLoss(), depositAmount);

    // Closing the pool cannot pull the stolen principal and enters the default path.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 1);

    assertTrue(cdoEpoch.defaulted());
}
```

This reproduces the core broken accounting state: the CDO sends principal to `ProgrammableBorrower`, `ProgrammableBorrower` deposits it into the ERC4626 vault, receives zero shares, and subsequent pool settlement defaults because neither underlying nor vault shares are available to satisfy the recall.
