### Title
Cross-user response confusion via MessageId-only keyed savedCallbacks map in WebAPI capabilities handler - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The legacy WebAPI trigger handler stores pending callbacks in `h.savedCallbacks` keyed **only** by `msg.Body.MessageId`, with no sender/address component in the key, unlike the newer `common.RequestCache` which correctly keys by `globalId{sender, id}`. Since `MessageId` is fully attacker-controlled (up to 128 bytes, only null-suffix restricted) and not required to be globally unique, an attacker can submit a request with the same `MessageId` as a victim's in-flight request to overwrite the victim's saved callback and receive (or corrupt) the victim's response.

### Finding Description
`gateway.ProcessRequest` (`core/services/gateway/gateway.go:266-269`) creates a fresh `callback := handlerscommon.NewCallback()` per request and calls `h.HandleLegacyUserMessage(ctx, msg, callback)`. For the WebAPI capabilities handler, `HandleLegacyUserMessage` stores this callback in a map keyed only by message ID: [1](#0-0) 

```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
```

The map is `map[string]*savedCallback` — see the field declaration at [2](#0-1) . There is no sender component in the key. Retrieval in `handleWebAPITriggerMessage` (invoked from node responses) also looks up purely by `msg.Body.MessageId`: [3](#0-2) 

`Message.Validate()` (`core/services/gateway/api/message.go:54-88`) only checks signature validity, MessageId length (1–128 bytes) and null-suffix restriction — it does not enforce per-sender uniqueness or any global uniqueness of `MessageId`: [4](#0-3) 

Because `Message.Sign` derives `Sender` from the signer's own key [5](#0-4) , any signer can freely choose an arbitrary `MessageId`, including one they observed being used by a victim in a concurrent in-flight request to the same DON/handler. If a second signed request with the same `MessageId` arrives at the gateway before the victim's request resolves, `h.savedCallbacks[msg.Body.MessageId]` in `HandleLegacyUserMessage` (guarded only by `h.mu`, not compared against any existing sender) is overwritten with the attacker's callback, discarding the victim's callback reference. When the (or any) node later responds with that `MessageId`, `handleWebAPITriggerMessage` looks the entry up by `MessageId` alone, finds the attacker's saved callback, and delivers whichever response arrives first to whichever callback is currently stored under that key — decoupling the response from the correct requester.

Notably, the codebase already contains the correct pattern elsewhere: `common.RequestCache` explicitly keys pending requests by `globalId{sender, id}` and rejects duplicate keys with `"request already exists"` [6](#0-5) , showing the WebAPI capabilities handler's `savedCallbacks` map is missing this same sender-scoping.

### Impact Explanation
This is a real cross-user response confusion vulnerability: an unprivileged (but signature-capable) attacker who can guess or observe a victim's `MessageId` for an in-flight `web_api_trigger` request can hijack or corrupt the victim's callback slot, causing the victim to either receive the attacker's crafted response body or never receive their own (denial), and the attacker to potentially receive the victim's response payload if the roles were positioned so the attacker's callback is invoked with the victim's node response. This matches the "cross-user response confusion" / request impersonation impact class named in the audit scope.

### Likelihood Explanation
Exploitability requires: (1) the attacker can submit a signed legacy message to the same DON/handler (any holder of a signing key that the gateway's node/DON accepts as a "sender" for user messages — no special privilege beyond being able to construct and sign a `Message`), and (2) the attacker knows or predicts a currently pending victim `MessageId`. `MessageId` is client-chosen and not enforced unique across senders at the gateway, DON, or handler layer, so this is straightforward to trigger deterministically by racing two signed requests with the same `MessageId` — no timing luck beyond a narrow but achievable request-overlap window, and no reliance on network/host-level or operator misconfiguration.

### Recommendation
Key `savedCallbacks` (and the corresponding lookup in `handleWebAPITriggerMessage`) by a composite `{Sender, MessageId}` (or `{DonId/Receiver, Sender, MessageId}`) tuple, mirroring `common.RequestCache`'s `globalId{sender, id}` pattern, and reject/collapse duplicate keys instead of silently overwriting. Ideally, migrate the WebAPI capabilities handler to use `common.RequestCache` directly instead of maintaining its own `savedCallbacks` map.

### Proof of Concept
Go handler-level integration test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Set up the handler with a mocked `DON` as in existing tests (`setupHandler`).
2. Create two `triggerRequest` messages signed by two different keys (`victimKey`, `attackerKey`) but with the **same** `MessageId` (e.g., `"dup-id"`).
3. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCb)` then, before resolving, call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCb)` — both use `hc.NewCallback()` per request as in `gateway.ProcessRequest`.
4. Assert internally (or via reflection/exported test hook) that `h.savedCallbacks["dup-id"]` now points to `attackerCb`, i.e., `victimCb` was silently overwritten.
5. Simulate a node response for `MessageId = "dup-id"` via `handler.HandleNodeMessage`/`handleWebAPITriggerMessage` and assert that `victimCb.Wait(ctx)` times out or never resolves (or resolves with the attacker's data) while `attackerCb.Wait(ctx)` receives the node's response — demonstrating the victim's response was misdirected/overwritten instead of isolated per sender+MessageId.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

type globalId struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
