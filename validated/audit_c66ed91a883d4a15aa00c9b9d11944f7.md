### Title
Stale `lastWithdrawRequest` pointer lets a loss-adjusted withdraw receipt be claimed twice — once haircut-skipped, once at par — draining funded vault reserves - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The FFmpeg CVE is a use-after-free: a stale pointer to freed/replaced demuxer state is dereferenced and paid out. The credit-vault analog is `IdleCreditVault._claimLossAdjustedWithdrawRequest`, which locates a user's loss-adjusted receipt via the single mutable pointer `lastWithdrawRequest[_user]`. A second `requestWithdraw` overwrites that pointer, "freeing" the bookkeeping link to the older loss-adjusted epoch. The old haircutted receipt is then never routed through the loss-adjusted path and is instead paid **at par** by `_claimFundedWithdrawRequest`, even though the borrower only funded the post-haircut amount.

### Finding Description
- `requestWithdraw` always overwrites `lastWithdrawRequest[_user] = currentEpoch` (line 282) and accumulates `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][currentEpoch]` (lines 292-293).
- `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest` (line 312), which reads `lossEpoch = lastWithdrawRequest[_user]` and looks up `lossRecoveryPriceByEpoch[lossEpoch]` (lines 789-792). If the user's *latest* request epoch has no loss price, the function returns 0 — the earlier loss-epoch receipt is never cleared by `_clearWithdrawClaimForEpoch`, so `withdrawsRequests[_user]` still contains its full pre-haircut basis.
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` at par via `_transferFundedClaim` (lines 338-349), gated only by `epochNumber > lastWithdrawRequest[_user]` — satisfied once one more epoch rolls.

Attack sequence (attacker = KYC'd lender / tranche holder):
1. Epoch N buffer: attacker calls `requestWithdraw`, receipt basis `B` recorded under epoch N.
2. Honest manager calls `stopEpochWithDuration(_lossAmount)` → `lossRecoveryPriceByEpoch[N] = p < 1e18`; borrower funds only `B * p` for that bucket (`pendingWithdraws` cleared at stop).
3. Epoch N+1 buffer: attacker calls `requestWithdraw` again → `lastWithdrawRequest` overwritten to N+1.
4. Epoch N+1 stops normally → `epochNumber = N+2`.
5. Attacker calls `claimWithdrawRequest`: loss path keyed on N+1 finds price 0; funded path pays `B` (epoch-N basis) **plus** the N+1 receipt at par. Attacker receives `B` instead of `B * p`, extracting `(1 - p) * B` of other users' funded underlyings.

The invariant "one receipt, loss-adjusted payout" is broken because clearing is keyed to a single overwritten pointer rather than iterated over all epochs with `lossRecoveryPriceByEpoch` set. `_transferFundedClaim`'s reserve guard only protects `defaultRecoveryReserve`, not ordinary funded claim underlyings.

### Impact Explanation
Direct theft of vault underlyings equal to the haircut that should have been applied: `(B - B*p)` per affected receipt, paid from funds belonging to other funded claimants/LPs (insolvency for later claimants). Reproducible by any unprivileged tranche holder sequencing two withdraw requests around a loss-adjusted stop.

### Likelihood Explanation
Requires a `stopEpochWithDuration` partial-loss event (honest manager action, a normal operating mode per the lossRecoveryPriceByEpoch flow) plus two withdraw requests by the same user in different epochs — a common pattern explicitly contemplated by the code comments ("if a user does not claim a withdraw request and instead requests another withdraw"). No privileged collusion needed.

### Recommendation
- Iterate `lossRecoveryPriceByEpoch` over all epochs in `withdrawsRequestsByEpoch[_user]` rather than keying solely on `lastWithdrawRequest[_user]`, or store a per-epoch loss flag consumed in `_claimFundedWithdrawRequest` so any residual basis in a loss epoch is paid at `lossRecoveryPrice`.
- Alternatively, revert in `requestWithdraw` when the user has an uncleared loss-adjusted receipt, forcing claim-first ordering.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVault.t.sol harness style
function testLossReceiptDoublePaidAfterPointerOverwrite() external {
    address user = makeAddr('attacker');
    _depositWithUser(user, 20_000 * ONE_SCALE, true);
    uint256 half = IERC20(AAtranche).balanceOf(user) / 2;

    // Epoch N: request half; stop with partial loss => lossRecoveryPriceByEpoch[N] = p < 1e18
    vm.prank(user);
    uint256 lossBasis = cdoEpoch.requestWithdraw(half, address(AAtranche));
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, lossAmount); // sets lossRecoveryPriceByEpoch[N]
    uint256 p = strategy.lossRecoveryPriceByEpoch(0);

    // Epoch N+1: second request overwrites lastWithdrawRequest[user]
    vm.prank(user);
    uint256 secondBasis = cdoEpoch.requestWithdraw(half, address(AAtranche));
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // Claim: loss path keyed on epoch N+1 (price 0) skips; funded path pays BOTH bases at par
    uint256 balPre = underlying.balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(user) - balPre;

    uint256 expected = lossBasis * p / 1e18 + secondBasis;
    assertGt(paid, expected); // overpaid by lossBasis * (1 - p)
}
```
