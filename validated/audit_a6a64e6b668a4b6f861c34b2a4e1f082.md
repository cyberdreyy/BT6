### Title
Missing uniqueness/ownership check on `savedCallbacks[MessageId]` allows cross-user response hijacking via MessageId collision - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Finding Description
`HandleLegacyUserMessage` unconditionally stores each user's callback keyed only by the attacker-controlled `msg.Body.MessageId`, with no check for whether that key is already in use and no binding to session/sender: [1](#0-0) 

`MessageId` is fully attacker-controlled: `api.Message.Validate()` only checks length/format constraints (non-empty, ≤128 bytes, no trailing null byte) and never enforces uniqueness or ties the ID to a caller identity — it just extracts the signer into `Body.Sender` for logging/routing purposes, not for MessageId ownership. [2](#0-1) 

Because the gateway fans the trigger request out to every DON member, multiple nodes independently answer the same `MessageId` via `handleWebAPITriggerMessage`, which pops the map entry on a "first response wins" basis: [3](#0-2) 

Exploit flow: an attacker who observes/guesses a victim's `MessageId` (e.g. a predictable or previously seen ID, since nothing enforces global uniqueness) can submit their own signed request reusing that same `MessageId` while the victim's original fan-out is still in flight. `HandleLegacyUserMessage` blindly overwrites `h.savedCallbacks[MessageId]` with the attacker's own `Callback`, discarding the victim's callback reference. When any DON node responds for that `MessageId` (including a node answering the victim's original forwarded request), `handleWebAPITriggerMessage` looks up by `MessageId` alone, finds the attacker's callback now installed under that key, and delivers the response to the attacker instead of the victim — or vice versa, silently dropping the victim's real response. This is a genuine cross-user response-confusion bug because the map key has no per-request/session binding beyond the freely chosen `MessageId`, and insertion never checks `found` before overwriting.

### Impact Explanation
This results in cross-user response/request confusion: an attacker can receive a callback response related to another user's in-flight `web_api_trigger` request (or vice versa cause the victim to silently lose their response), and can disrupt/deny a victim's Gateway request by ID collision. This maps to the "unauthorized action on another user's job/request" / cross-user data confusion class in the Chainlink bounty program, though severity is limited by the fact that the `web_api_trigger` response payload (`TriggerResponsePayload`) generally only carries `Status`/`ErrorMessage` metadata rather than raw DON output, so the leaked information is limited (success/failure status/error text of another user's request) rather than full response body disclosure — the outgoing-message methods (`MethodWebAPITarget`/`MethodComputeAction`/`MethodWorkflowSyncer`) that do carry response bodies are handled by `handleWebAPIOutgoingMessage`, which does not use `savedCallbacks` and is not affected by this issue.

### Likelihood Explanation
Exploitability requires the attacker to know or guess a `MessageId` that collides with an in-flight victim request and to win a timing race against the DON's fan-out/response window (default handler config has short callback TTLs, `defaultCallbackMaxAgeSec = 120s`, giving a reasonably wide window). No special credentials are needed — any unauthenticated caller able to submit a signed Gateway message (signature only proves the sender's own key, not exclusive rights to a `MessageId`) can attempt the collision. Reliability is race-dependent (requires overlap with a still-in-flight victim request) rather than deterministic replay of an already fully completed cycle, since a completed cycle immediately deletes its map entry in `handleWebAPITriggerMessage` (`delete(h.savedCallbacks, msg.Body.MessageId)` runs before the "found" check).

### Recommendation
- In `HandleLegacyUserMessage`, check `if _, exists := h.savedCallbacks[msg.Body.MessageId]; exists { return error/conflict }` before inserting, similar to the "duplicate request ID" / in-flight conflict handling already implemented in `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`.
- Derive the `savedCallbacks` key from a tuple that includes the message sender/signature (or a gateway-generated nonce) in addition to `MessageId`, rather than trusting the client-supplied `MessageId` alone.
- Reject reused `MessageId`s from different senders explicitly, returning a conflict error to the second submitter.

### Proof of Concept
Go handler-level test plan (extending `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Build two signed `api.Message`s (`victimMsg`, `attackerMsg`) with different private keys but the identical `MessageId` value (`"shared-id"`), both `MethodWebAPITrigger`.
2. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)` — assert `don.SendToNode` called for each DON member with the victim's request.
3. Before any node responds, call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)` with the same `MessageId` — assert it succeeds (no conflict error) and `h.savedCallbacks["shared-id"]` now points to `attackerCallback`.
4. Simulate a node response for `MessageId="shared-id"` (as if replying to the victim's forwarded request) via `handler.HandleNodeMessage(ctx, resp, nodeAddr)`.
5. Assert `attackerCallback.Wait(ctx)` receives the response (`handlers.UserCallbackPayload`) instead of `victimCallback`, and that `victimCallback.Wait(ctx)` times out/never resolves — demonstrating cross-user response delivery caused by the unconditional overwrite in `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}`.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
