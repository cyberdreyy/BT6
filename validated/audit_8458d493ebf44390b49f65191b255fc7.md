### Title
`simulateTransaction` RPC method can panic (crash the validator process) via `assert!(self.is_frozen(), "simulation bank must be frozen")` - ([File: runtime/src/bank.rs])

### Summary
`Bank::simulate_transaction()` asserts that the target bank is frozen before it is used to simulate a transaction. The public JSON-RPC `simulateTransaction` handler fetches a bank via `meta.get_bank_with_config()` (which, for `processed` commitment, can return the validator's own currently-building working bank) and passes it directly into `bank.simulate_transaction()` without first checking/forcing `is_frozen()`. If a client issues a `simulateTransaction` request while the local validator's working bank for that slot has not yet been frozen (e.g., the validator is itself building/leading that slot and hasn't reached the last tick), the `assert!` fires and panics the whole process — a full validator crash triggered by a single unprivileged RPC call.

### Finding Description
`Bank::simulate_transaction` unconditionally asserts the frozen invariant: [1](#0-0) 

This function is called directly from the RPC `simulate_transaction` handler using whatever bank `get_bank_with_config` resolves for the requested (or default) commitment: [2](#0-1) 

Nothing in this call path calls `bank.freeze()` before invoking `bank.simulate_transaction()`. The test suite is fully aware that this invariant is not automatically guaranteed and manually freezes the bank before every simulateTransaction test to avoid hitting the assert: [3](#0-2) [4](#0-3) 

The comment on the latter test — "Freeze bank 0 to prevent a panic in `run_transaction_simulation()`" — makes explicit that production code paths rely on the bank being frozen by *some other* actor (replay stage / PoH once the slot's last tick is recorded), not by the RPC path itself. `Bank::freeze()` is only called from block-production/replay code once a slot's processing completes: [5](#0-4) 

This mirrors the structure of the referenced report: a hard invariant (`is_frozen()` in the single-bank mental model used by unit tests, analogous to “LUSD balance ≤ collateral debt” in the single-collateral model) that no longer universally holds once the system is considered in its full, more complex operating context (multiple banks concurrently existing — a rooted/frozen bank, an optimistically-confirmed bank, and the validator's own actively-building, unfrozen working bank when it is the current leader for that slot). The RPC layer can select the unfrozen working bank (via `processed`/default commitment resolution in `get_bank_with_config`) and hand it straight to code that assumes frozen-only usage, exactly as the report describes a check that assumes an invariant from a simpler model but is violated in the richer, real system.

### Impact Explanation
An `assert!` panic in Rust aborts the thread; in the JSON-RPC service this propagates and can bring down the whole validator process, since the panic occurs on the calling thread inside `Bank::simulate_transaction`, invoked synchronously from the RPC request handler. A single unprivileged `simulateTransaction` JSON-RPC call, sent while the local node's working bank for the current slot is not yet frozen (which happens routinely while a validator is producing/leading its own slot, prior to the last PoH tick), can crash the validator. This is a concrete validator-process crash triggered by one unprivileged request, matching the required “Accept” criteria.

### Likelihood Explanation
Any RPC-enabled validator that is periodically the leader will, during normal operation, have windows where its own working bank is unfrozen while it is being actively built. The commitment resolution logic used by `simulateTransaction` (`get_bank_with_config`) can hand back this unfrozen bank for `processed` commitment (the level explicitly designed to reflect the very latest, not-yet-finalized state). No special timing manipulation, multiple RPC calls, or malicious cluster state is required — a single, ordinary `simulateTransaction` call issued at the "wrong" moment (which recurs naturally every time the node leads a slot) is sufficient to trigger the assert.

### Recommendation
Do not assert on frozen state inside the shared `Bank::simulate_transaction` API used by externally reachable RPC code. Either:
- Have `JsonRpcRequestProcessor::simulate_transaction` explicitly select/require a frozen bank (e.g., reject with a proper RPC error, or fall back to the highest already-frozen bank) instead of passing through whatever bank `get_bank_with_config` returns, or
- Replace the `assert!` in `Bank::simulate_transaction` with a `Result`/graceful error path so that an unfrozen bank produces an RPC error response rather than panicking the process, consistent with `simulate_transaction_unchecked`'s existing non-panicking design intended for use with not-necessarily-frozen banks.

### Proof of Concept
The existing unit test in the repository already demonstrates the crash condition using the identical code path exercised by production RPC: [3](#0-2) 
It shows that calling `simulateTransaction` (via `io.handle_request_sync`) against a bank returned by `meta.get_bank_with_config` that has not been frozen results directly in the `"simulation bank must be frozen"` panic originating from `Bank::simulate_transaction`. In production, this same condition is met whenever the resolved bank for the request's commitment level (e.g. `processed`, or whatever default `get_bank_with_config` uses) happens to be the validator's own currently-unfrozen working bank, which requires no special access — just an ordinarily-timed `simulateTransaction` RPC call.

    pub fn freeze(&self) {
        // This lock prevents any new commits from BankingStage
        // `Consumer::execute_and_commit_transactions_locked()` from
        // coming in after the last tick is observed. This is because in
        // BankingStage, any transaction successfully recorded in
        // `record_transactions()` is recorded after this `hash` lock
        // is grabbed. At the time of the successful record,
        // this means the PoH has not yet reached the last tick,
        // so this means freeze() hasn't been called yet. And because
        // BankingStage doesn't release this hash lock until both
        // record and commit are finished, those transactions will be
        // committed before this write lock can be obtained here.
        let mut hash = self.hash.write().unwrap();
        if *hash == Hash::default() {
            // finish up any deferred changes to account state
            self.distribute_transaction_fee_details();
            self.update_slot_history();
            self.run_incinerator();

            // freeze is a one-way trip, idempotent
            self.freeze_started.store(true, Relaxed);
            // updating the accounts lt hash must happen *outside* of hash_internal_state() so
            // that rehash() can be called and *not* modify self.accounts_lt_hash.
            self.finish_accounts_lt_hash_updates();
            *hash = self.hash_internal_state();
            self.rc.accounts.accounts_db.mark_slot_frozen(self.slot());
        }
    }
