### Title
Stale per-epoch instant-withdraw basis inflates default recovery claims and DoSes `claimInstantWithdrawRequest` via underflow - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The ClamAV bug is a crafted input that crashes the processing engine mid-scan — an analog is a user-controlled transaction sequence that corrupts `IdleCreditVault`'s receipt accounting so that later claims permanently revert or are mispriced. `claimInstantWithdrawRequest` pays out `instantWithdrawsRequests[_user]` but never clears the per-epoch buckets `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` ( [1](#0-0) ). If the user then re-requests an instant withdrawal in the same epoch and the epoch later defaults, `_claimDefaultedInstantWithdrawRequest` subtracts the full (stale + new) basis from `instantWithdrawsRequests[_user]`, causing an arithmetic underflow that permanently reverts the claim ( [2](#0-1) ). Simultaneously, `defaultPendingClaimBasis` counts the already-paid amount in the recovery denominator, diluting `defaultRecoveryPrice` for every other victim ( [3](#0-2) ).

### Finding Description
`requestInstantWithdraw` records each request twice: in the aggregate `instantWithdrawsRequests[_user]` and per-epoch in `instantWithdrawsRequestsByEpoch[_user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]` ( [4](#0-3) ). The funded claim path `claimInstantWithdrawRequest` only zeroes the aggregate (`instantWithdrawsRequests[_user] = 0`) and leaves both per-epoch mappings intact ( [5](#0-4) ).

Attack sequence (running epoch N, non-programmable mode so instant withdraws are enabled):

1. Attacker (KYC'd lender) calls `requestInstantWithdraw(X)` → byEpoch[N] = X, claimsByEpoch[N] = X.
2. Manager calls `getInstantWithdrawFunds` after `instantWithdrawDeadline`; funds move to the strategy and `pendingInstantWithdraws -= X` ( [6](#0-5) ).
3. Attacker claims X (paid in full). `instantWithdrawsRequests[attacker] = 0` but `instantWithdrawsRequestsByEpoch[attacker][N]` still equals X.
4. Attacker calls `requestInstantWithdraw(Y)` again in the same epoch N → `instantWithdrawsRequests[attacker] = Y`, `instantWithdrawsRequestsByEpoch[attacker][N] = X + Y`, `instantWithdrawClaimsByEpoch[N] = X + Y`.
5. Borrower fails to fund `stopEpoch`; `_handleBorrowerDefault` runs and `finalizeDefaultRecovery` executes while `pendingInstantWithdraws != 0`.

At finalization, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[N]` (= X + Y) to the basis, but only Y is real unpaid debt — X was already paid out. `defaultRecoveryReserve` / `defaultRecoveryPrice` are computed on an inflated basis ( [7](#0-6) ). When the attacker later calls `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = X + Y` and executes `instantWithdrawsRequests[_user] -= claimBasis`, i.e., `Y - (X + Y)`, which underflows and reverts in Solidity 0.8 ( [8](#0-7) ).

### Impact Explanation
- The attacker's claim permanently reverts (the stale epoch entry is never cleared before the underflow), and — more importantly — `instantWithdrawClaimsByEpoch[N]` remains over-counted, so the recovery price is permanently diluted: every defaulted receipt holder and active LP recovers proportionally less underlying than the reserve should pay per unit of real debt. X is effectively counted as debt twice (once paid at par, once inside the recovery denominator), stealing recovery value from all other claimants.
- Since `defaultRecoveryReserve` is only sized for the inflated basis, `defaultRecoveryReserve -= _amount` in `_transferDefaultRecovery` ( [9](#0-8) ) can also revert for the last claimants once earlier claims drain the reserve, permanently freezing tail claims.
- Broken invariants: one-receipt-one-payout (receipt X is paid and also kept as recovery basis) and fair recovery distribution (recovery price diluted by phantom basis).

### Likelihood Explanation
Requires instant withdrawals enabled (non-programmable borrower), a same-epoch re-request after a funded claim, and a subsequent default in that same epoch — a sequence reachable by any KYC'd lender without privileged help beyond the honest manager's normal `getInstantWithdrawFunds` call. The underflow is deterministic once state is set up; no guards (`_ensureDefaultRecoveryInitialized`, flags, epoch gating) clear the stale per-epoch entries. Uncertainty: whether the CDO blocks `requestInstantWithdraw` for a user who already claimed within the same epoch needs verification in the full CDO request path, which I could not fully trace within the available iterations — if the CDO re-requests via a different wrapper the strategy-level inconsistency still stands.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch receipt entries alongside the aggregate: when the funded claim fully drains `instantWithdrawsRequests[_user]`, also zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and subtract from `instantWithdrawClaimsByEpoch[epoch]` for every outstanding epoch entry (or track and clear the current-epoch bucket). Alternatively, move the per-epoch bookkeeping into a claim path that mirrors `_clearWithdrawClaimForEpoch` for instant receipts, so funded and defaulted claims cannot diverge between the aggregate and per-epoch views.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
