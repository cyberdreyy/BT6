### Title
Uncapped builder withdrawal amount lets execution layer mint more Gwei than the CL deducts from the builder's balance - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` builds each `Withdrawal` using the raw, previously-queued `withdrawal.amount` from `state.builder_pending_withdrawals` without clamping it to the builder's *current* balance, while `apply_withdrawals` clamps the actual balance deduction with `min(withdrawal.amount, builder_balance)`. Because the beacon block's `payload_expected_withdrawals` (the uncapped amount) is what the execution layer is contractually required to honor/mint to `fee_recipient`, a builder whose balance has fallen below an already-queued withdrawal amount causes the EL to mint more Gwei than the CL actually removes from the builder — a direct violation of the "no Gwei created from nothing" invariant.

### Finding Description
`get_builder_withdrawals` ( [1](#0-0) ) iterates `state.builder_pending_withdrawals` and, for each entry, appends:
```python
Withdrawal(
    index=withdrawal_index,
    validator_index=convert_builder_index_to_validator_index(builder_index),
    address=withdrawal.fee_recipient,
    amount=withdrawal.amount,
)
```
with no comparison against `state.builders[builder_index].balance`. Contrast this with `get_pending_partial_withdrawals` and `get_validators_sweep_withdrawals`, which explicitly clamp: `withdrawal_amount = min(balance - MIN_ACTIVATION_BALANCE, withdrawal.amount)` ( [2](#0-1) ).

This uncapped `Withdrawal.amount` is placed into `state.payload_expected_withdrawals`, which per the spec's own note the execution layer "is required to honor ... in the execution layer" ( [3](#0-2) ) — i.e., the EL mints `withdrawal.amount` to `fee_recipient` for every entry.

Meanwhile, `apply_withdrawals` only decreases the CL-side builder balance by the clamped amount:
```python
builder_balance = state.builders[builder_index].balance
state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
``` [4](#0-3) 

If `withdrawal.amount > builder_balance`, the CL deducts only `builder_balance` (down to 0), but the EL is committed to minting the full `withdrawal.amount`. The difference (`withdrawal.amount - builder_balance`) is Gwei created out of thin air on the execution layer with no corresponding CL-side backing.

This exact scenario is validated as expected/passing behavior by the test suite itself: [5](#0-4) 
which explicitly sets `builder_withdrawal_amounts={builder_index: MIN_DEPOSIT_AMOUNT+123}` against `builder_balances={builder_index: MIN_DEPOSIT_AMOUNT+122}` and asserts `withdrawal_amounts_builders={builder_index: withdrawal_amount}` (the full, uncapped requested amount) is what appears in the committed withdrawal, while `builders[0].balance` goes to `0`.

### Impact Explanation
This breaks the equality "amount minted by EL == amount deducted on CL" for builder withdrawals. Per the severity table, "Gwei created ... or paid to a non-owner" is a Critical-impact class. Here, EL-side new Gwei is minted to the `fee_recipient` address specified in the (already-queued) `BuilderPendingWithdrawal`, without a matching CL-side balance reduction — a supply invariant break reachable purely through spec-defined state transitions, not requiring any client bug, foreign key, or coalition.

### Likelihood Explanation
The precondition is that a builder's `balance` drops below the sum of its already-queued `builder_pending_withdrawals`/`builder_pending_payments` amounts between the time the payment/withdrawal was queued and the time `get_builder_withdrawals` processes it. `can_builder_cover_bid` ( [6](#0-5) ) only checks sufficiency at bid-submission time, using `get_pending_balance_to_withdraw_for_builder` ( [7](#0-6) ) to sum currently pending amounts — it does not re-verify or lock the balance for the lifetime of the pending withdrawal. Whether normal spec-following state transitions (e.g., concurrent bids across payment slots, multiple builder deposits/exits interleaving with payment settlement) can actually drive `builder.balance` below an already-committed pending amount could not be fully confirmed within the available context/tool budget — this would need to be traced through `settle_builder_payment`, `process_builder_deposit_request`, and `process_builder_exit_request` to establish the concrete attack sequence.

### Recommendation
Clamp the withdrawal amount to the builder's current balance at the point `get_builder_withdrawals` constructs the `Withdrawal`, mirroring the pattern used by `get_pending_partial_withdrawals`:
```python
amount = min(withdrawal.amount, state.builders[builder_index].balance)
```
so that the committed (EL-minted) amount can never exceed what `apply_withdrawals` actually deducts from the builder's CL balance.

### Proof of Concept
Using the existing test harness pattern from `test_builder_withdrawal_insufficient_balance_realistic_bounds` ( [5](#0-4) ):
1. Set `state.builders[0].balance = MIN_DEPOSIT_AMOUNT + 122`.
2. Queue `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, amount=MIN_DEPOSIT_AMOUNT + 123, fee_recipient=<attacker-controlled address>)]`.
3. Run `process_withdrawals(state)`.
4. Observe: `state.payload_expected_withdrawals[0].amount == MIN_DEPOSIT_AMOUNT + 123` (committed to EL for minting) while `state.builders[0].balance == 0` (only `MIN_DEPOSIT_AMOUNT + 122` was actually deducted) — a 1 Gwei discrepancy that the EL will mint without CL backing. This is the exact assertion the existing test confirms as passing/expected behavior, demonstrating the gap is present in the current spec logic rather than being hypothetical.

```python
def get_pending_balance_to_withdraw_for_builder(
    state: BeaconState, builder_index: BuilderIndex
) -> Gwei:
    balance = Gwei(0)
    for withdrawal in state.builder_pending_withdrawals:
        if withdrawal.builder_index == builder_index:
            balance += withdrawal.amount
    for payment in state.builder_pending_payments:
        if payment.withdrawal.builder_index == builder_index:
            balance += payment.withdrawal.amount
    return balance
```

def can_builder_cover_bid(
    state: BeaconState, builder_index: BuilderIndex, bid_amount: Gwei
) -> bool:
    builder_balance = state.builders[builder_index].balance
    pending_withdrawals_amount = get_pending_balance_to_withdraw_for_builder(state, builder_index)
    min_balance = MIN_DEPOSIT_AMOUNT + pending_withdrawals_amount
    if builder_balance < min_balance:
        return False
    return builder_balance - min_balance >= bid_amount

##### New `get_builder_withdrawals`

```python
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
```
