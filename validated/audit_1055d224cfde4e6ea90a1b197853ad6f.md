### Title
pprof debug endpoints registered under authv2 lack role checks, allowing view/run-role users to dump process heap/goroutine memory - ([File: core/web/router.go])

### Summary
`metricRoutes` registers `/v2/debug/pprof/*` handlers (index, cmdline, profile, symbol, trace, allocs, block, goroutine, heap, mutex, threadcreate) directly on the `authv2` group, which only requires successful authentication (session or API token), with no `auth.RequiresEditRole`/`auth.RequiresAdminRole` wrapper applied to any of these routes. Any authenticated user regardless of role, including the lowest `view` role, can therefore hit `GET /v2/debug/pprof/heap`, `GET /v2/debug/pprof/goroutine`, or `POST /v2/debug/pprof/symbol` and receive a full in-process memory/goroutine dump.

### Finding Description
`v2Routes` builds `authv2` with only base authentication: [1](#0-0) 
Every other sensitive action registered on `authv2` is explicitly wrapped with `auth.RequiresEditRole`, `auth.RequiresRunRole`, or `auth.RequiresAdminRole` (e.g. key export/import, job create/update, config changes), but `metricRoutes(authv2)` is called with no such wrapper: [2](#0-1) 
and the routes it registers are unguarded stdlib pprof handlers: [3](#0-2) 
`auth.Authenticate` only checks that one of the given auth methods succeeds (session cookie or API token) and sets `SessionUserKey`; it performs no role comparison: [4](#0-3) 
Role gating only happens in `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole`, none of which are applied to the pprof routes: [5](#0-4) 
Since a `UserRoleView` session or token passes `auth.Authenticate` fine (role is irrelevant there), the request reaches the raw `net/http/pprof` handlers (`pprof.Handler("heap")`, `pprof.Handler("goroutine")`, `pprof.Symbol`, `pprof.Profile`, `pprof.Trace`, `pprof.Cmdline`), which return full heap dumps, goroutine stacks (potentially containing arguments/keys held in memory), and allow triggering CPU/execution traces — all normally considered operator/admin-only diagnostic capabilities.

### Impact Explanation
A view-role (read-only) or run-role user can retrieve `/v2/debug/pprof/heap` and `/v2/debug/pprof/goroutine` dumps of the running chainlink node process. These dumps can contain sensitive in-memory data such as decrypted private keys, session tokens, database connection strings, or other secrets that were resident in memory at request time, and `/v2/debug/pprof/profile` and `/v2/debug/pprof/trace` allow a low-privileged user to induce non-trivial CPU load (minor DoS/resource-exhaustion vector). This matches a credential/secret disclosure and authorization-bypass impact class, since the intended authorization model in this router explicitly treats debug/instrumentation access as more sensitive than plain read-only API use (contrast with `/v2/debug/vars` on the `/debug` group, gated only by base auth as well, but pprof exposes richer raw memory content than expvar).

### Likelihood Explanation
Exploitation requires only the lowest possible privilege: any valid session cookie or API token for a `view`-role or `run`-role user (or even the fact that no explicit role check exists means literally any authenticated principal, including `edit`/`admin`, can hit it, but the notable finding is that the *lowest* privilege tier is sufficient). No special network position, admin credentials, or misconfiguration is needed — this is a straightforward missing-authorization-wrapper bug reachable via a single authenticated HTTP GET/POST. It is fully repeatable and deterministic.

### Recommendation
Wrap the pprof routes registered by `metricRoutes` with an appropriate role check (at minimum `auth.RequiresAdminRole`, consistent with other sensitive diagnostic/export endpoints such as key export in the same router), e.g.:
```go
pprofGroup.GET("/heap", auth.RequiresAdminRole(ginHandlerFromHTTP(pprof.Handler("heap").ServeHTTP)))
```
applied uniformly to all pprof sub-routes (`/`, `/cmdline`, `/profile`, `/symbol`, `/trace`, `/allocs`, `/block`, `/goroutine`, `/heap`, `/mutex`, `/threadcreate`), or alternatively make pprof exposure opt-in via a dedicated config flag/separate internal-only listener rather than exposing it on the general authenticated `/v2` API surface.

### Proof of Concept
Handler-level integration test plan (using the existing test harness style in `core/web`):
1. Set up the test app/router via the existing `setupWeb...` test helper used elsewhere in `core/web` tests, seeding a user with `sessions.UserRoleView`.
2. Authenticate via `POST /sessions` (or construct a session cookie directly) to obtain a `view`-role session.
3. Issue `GET /v2/debug/pprof/heap` with that session cookie; assert HTTP status is `200` (not `401`/`403`) and response `Content-Type` is `application/octet-stream` (pprof profile format), confirming the dump is returned.
4. Issue `GET /v2/debug/pprof/goroutine?debug=2` with the same session; assert `200` and that response body contains readable goroutine stack text.
5. Issue `POST /v2/debug/pprof/symbol` with the same session and a body like `b=0x0`; assert `200`.
6. As a control, repeat step 3 against `POST /v2/keys/eth/export/:address` (an `auth.RequiresAdminRole`-protected route) with the same view-role session and assert `403 Forbidden` is returned, demonstrating the inconsistency: admin-gated routes correctly reject the view-role user while pprof routes do not.

// Authenticate is middleware which authenticates the request by attempting to
// authenticate using all the provided methods.
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
