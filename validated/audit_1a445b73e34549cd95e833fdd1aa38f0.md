### Title
Lockup address squatting via caller-controlled `owner_account_id` with no existence check - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` derives the deterministic lockup account id solely from `sha256(owner_account_id)[..20]` with no verification that `owner_account_id` is an already-registered NEAR account or that the caller is entitled to create a lockup for it. Any unprivileged caller who pays `MIN_ATTACHED_BALANCE` can pre-create the lockup contract for any `owner_account_id` string, choosing `lockup_duration`, `vesting_schedule`, `release_duration`, and `staking_pool_whitelist_account_id`, permanently occupying that address before the legitimate employer/foundation acts.

### Finding Description
The intended binding is: `sha256(owner_account_id)[..20].<factory> == LockupArgs chosen by the party entitled to grant owner_account_id's lockup` (the employer/foundation). The actual code enforces only: [1](#0-0) 

`owner_account_id` is a `ValidAccountId`, which only validates NEAR account-id syntax, not existence or authorization — no `is_valid_account_id`-style existence check, no restriction on `env::predecessor_account_id()` relative to `owner_account_id`, and no reservation/allowlist mechanism. `MIN_ATTACHED_BALANCE` is a fixed deposit threshold, not an authorization check.

Exploit flow:
1. Attacker learns/predicts a future employee's intended NEAR account name `future_employee` (a string that has not yet been registered as an account, or simply one the attacker wants to squat regardless of registration).
2. Attacker calls `create(owner_account_id="future_employee", lockup_duration=0, vesting_schedule=None, release_duration=None, whitelist_account_id=Some(attacker_whitelist))` with `attached_deposit >= MIN_ATTACHED_BALANCE`.
3. `Promise::new(lockup_account_id).create_account().deploy_contract(...).transfer(...).function_call("new", LockupArgs{...})` executes and succeeds because no account exists yet at `sha256("future_employee")[..20].<factory>`.
4. The lockup contract is now deployed at the deterministic address with `owner_account_id = "future_employee"` but with lockup parameters (`lockup_duration`, `vesting_schedule`, `staking_pool_whitelist_account_id`) chosen entirely by the attacker, not by the employer.
5. When the legitimate employer later calls `create` for the same `owner_account_id`, the `create_account()` action fails at the receipt level (account already exists), the whole batched receipt fails, and `on_lockup_create`'s `is_promise_success()` returns `false`: [2](#0-1) 

The employer's deposit is refunded, but the intended lockup with the employer-chosen vesting schedule and parameters can never be created at that address — the attacker's parameters are permanently bound to that account name instead.

None of the existing guards prevent this: `assert_self()` and `is_promise_success()` only govern the callback's own authorization and promise-result handling; there is no `assert_owner`, `assert_called_by_foundation`, or account-existence check gating `create` itself.

### Impact Explanation
This results in "a lockup deployed with parameters its rightful creator never chose," bound to the victim's future account name — a Critical-category outcome per the stated impact rules. The employer/foundation permanently loses the ability to set the intended vesting schedule, lockup duration, and staking-pool whitelist for that employee's grant; the attacker (or the resulting contract, owned nominally by `future_employee`) instead controls those terms (e.g., zero vesting, attacker-chosen whitelist restricting which staking pools the eventual owner can use). This is repeatable for any account name the attacker can predict, and the denial is address-specific and permanent (the factory cannot recreate an account that already exists).

### Likelihood Explanation
Preconditions are minimal: the attacker needs only knowledge/prediction of the target account-id string (a common pattern for known-to-be-hired employees, e.g. `alice.near`) and `MIN_ATTACHED_BALANCE` (3.5 NEAR) plus gas — both attacker capabilities are within the unprivileged threat model. No special timing dependency on chain state beyond the target lockup address not yet existing. The attack is straightforward to execute with a single transaction and is fully repeatable across any number of target account names.

### Recommendation
Require the lockup creation to be authorized by the account named in `owner_account_id` itself, or restrict `create` to be callable only by `foundation_account_id` / an authorized allowlist, or require a signed/attached proof that `env::predecessor_account_id() == owner_account_id.as_ref()` (or another explicit binding between caller and the account the lockup is being created for) before proceeding with `create_account`.

### Proof of Concept
```rust
// cargo test in lockup-factory
#[test]
fn test_owner_account_id_squatting() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker (never appeared as predecessor before) squats the address for
    // "future_employee", an account id that has never been registered/used.
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        ValidAccountId::try_from("future_employee").unwrap(),
        LOCKUP_DURATION_ZERO.into(),
        None,     // no lockup_timestamp
        None,     // attacker picks NO vesting schedule
        None,
        Some(attacker_whitelist_account_id()), // attacker-chosen whitelist
    );
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    assert!(contract.on_lockup_create(
        lockup_account_for("future_employee"),
        ntoy(30).into(),
        String::from("attacker.near"),
    ));

    // Employer later tries to create the REAL lockup with vesting for the same owner.
    context.predecessor_account_id = String::from("employer.near");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        ValidAccountId::try_from("future_employee").unwrap(),
        REAL_LOCKUP_DURATION.into(),
        None,
        Some(real_vesting_schedule()),
        None,
        None,
    );
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    // create_account fails because the address is already occupied by attacker's contract
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let created = contract.on_lockup_create(
        lockup_account_for("future_employee"),
        ntoy(35).into(),
        String::from("employer.near"),
    );
    // Assert both sides of the binding diverge: address is bound to attacker's LockupArgs,
    // not the employer's, and the employer's create is permanently denied.
    assert_eq!(created, false);
}
```

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
