### Title
Claimed instant-withdraw receipts remain in default-recovery accounting and inflate the recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary

`claimInstantWithdrawRequest` burns the user's strategy-token receipt and clears `instantWithdrawsRequests`, but it does not clear the per-epoch receipt ledgers `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch`. If a funded instant withdrawal is claimed in the same epoch in which a later unfunded instant request remains pending, default finalization counts the already-claimed receipt again as both outstanding claim basis and prefunded reserve. The attacker can then recover their new request using a reserve that is inflated by phantom, already-paid funds.

### Finding Description

An attacker requests an instant withdrawal during a running epoch. Once the IdleCDO collects the instant-withdraw funds, `pendingInstantWithdraws` is reduced and the attacker can claim immediately. The claim burns the receipt and clears only the aggregate `instantWithdrawsRequests` ledger: [1](#0-0) 

The request-time per-epoch ledgers remain populated: [2](#0-1) 

If another instant request in the same epoch remains unfunded, `pendingInstantWithdraws != 0`, so default finalization treats the entire epoch's `instantWithdrawClaimsByEpoch` value—including the attacker's already-claimed first receipt—as pending default-recovery basis: [3](#0-2) 

The same stale basis is then interpreted as already-held recovery collateral because `_defaultPrefundedInstantReserve` subtracts only the still-unfunded remainder: [4](#0-3) 

That phantom amount is included in `defaultRecoveryReserve` during `finalizeDefaultRecovery`: [5](#0-4) 

The first receipt has therefore been “freed” by `claimInstantWithdrawRequest`, but its stale per-epoch accounting is reused during default finalization—the closest analog to a use-after-free object lifetime bug.

### Impact Explanation

This causes insolvency and unfair recovery distribution. For example:

1. Attacker instant-withdraws `100`.
2. IdleCDO funds the request and attacker claims `100`.
3. Attacker requests another instant withdrawal of `10`, which remains unfunded.
4. The borrower defaults in the same epoch.
5. `instantWithdrawClaimsByEpoch[epoch]` is still `110`, while `pendingInstantWithdraws` is `10`.
6. `_defaultPrefundedInstantReserve` reports `100` of supposedly already-held recovery collateral, even though that `100` was already paid to the attacker.
7. The attacker recovers the new `10` request at a recovery ratio inflated by phantom collateral, extracting assets that should remain available to active LPs and other default claimants.

The invariant violated is “one receipt, one payout”: after the first payout, the receipt remains alive in epoch-level recovery accounting. The resulting reserve overstatement can directly redirect recovery assets to the attacker.

### Likelihood Explanation

The sequence requires instant withdrawals to be enabled, a funded instant claim, a subsequent unfunded instant receipt in the same epoch, and borrower default/finalization in that epoch. Borrower default is external to the attacker, but the stale-accounting state is created entirely by ordinary unprivileged request and claim transactions. No privileged caller needs to make a mistaken state transition.

### Recommendation

When a funded instant withdrawal is claimed, clear the user's per-epoch receipt and decrement the epoch-level instant claim basis. The claim should locate the request epoch—potentially by storing a `lastInstantWithdrawRequest` epoch or tracking funded instant claims explicitly—and execute the equivalent of:

```solidity
uint256 requestEpoch = ...;
instantWithdrawsRequestsByEpoch[_user][requestEpoch] = 0;
instantWithdrawClaimsByEpoch[requestEpoch] -= amount;
instantWithdrawsRequests[_user] = 0;
_burn(_user, amount);
_transferFundedClaim(_user, amount);
```

If multiple funded instant receipts can exist in the same epoch, subtract the claimed amount rather than blindly zeroing the user's epoch entry. Ensure `_defaultPrefundedInstantReserve` only includes unfunded-but-already-collateralized receipts, never receipts already paid to users.

### Proof of Concept

A Foundry test can reproduce the accounting flaw against the credit-vault fixture used by `test/foundry/IdleCreditVault.t.sol`:

```solidity
function testClaimedInstantReceiptInflatesDefaultRecovery() external {
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    uint256 currentEpoch = vault.epochNumber();

    // Attacker creates an instant receipt of 100 through the CDO.
    uint256 firstReceipt = 100 * ONE_SCALE;
    cdoEpoch.requestWithdraw(firstReceipt, address(AAtranche));

    // CDO collects the full instant amount and attacker claims it.
    deal(defaultUnderlying, address(cdoEpoch), firstReceipt);
    vm.prank(address(cdoEpoch));
    vault.collectInstantWithdrawFunds(firstReceipt);
    vm.prank(address(cdoEpoch));
    vault.claimInstantWithdrawRequest(attacker);

    assertEq(vault.instantWithdrawsRequests(attacker), 0);

    // Stale lifetime state remains after the payout.
    assertEq(
        vault.instantWithdrawsRequestsByEpoch(attacker, currentEpoch),
        firstReceipt
    );
    assertEq(
        vault.instantWithdrawClaimsByEpoch(currentEpoch),
        firstReceipt
    );

    // A second instant receipt is created but remains unfunded.
    uint256 secondReceipt = 10 * ONE_SCALE;
    cdoEpoch.requestWithdraw(secondReceipt, address(AAtranche));

    assertEq(vault.pendingInstantWithdraws(), secondReceipt);
    assertEq(
        vault.instantWithdrawClaimsByEpoch(currentEpoch),
        firstReceipt + secondReceipt
    );

    // Mark the pool defaulted, then finalize with no external recovery.
    // The finalization path sees:
    //   basis            = firstReceipt + secondReceipt
    //   prefundedReserve = firstReceipt
    // even though firstReceipt was already paid.
    _finalizeDefaultWithNoRecovery();

    assertEq(vault.defaultRecoveryReserve(), firstReceipt);
}
```

The precise helper names depend on the fixture, but the state assertions are directly reproducible from production storage getters. They demonstrate that a receipt already burned and paid remains included in both the default claim basis and the calculated prefunded reserve.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
