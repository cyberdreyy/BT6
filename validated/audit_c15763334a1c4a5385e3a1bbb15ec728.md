### Title
Global signer-state agreement threshold rounds down instead of up, letting a signer capitulate its miner-view/protocol-version/tx-replay-set consensus below the true 70% supermajority - ([File: libsigner/src/v0/signer_state.rs])

### Summary
`GlobalStateEvaluator::reached_agreement` / `reached_disagreement` compute the 70%/30% supermajority thresholds by **truncating** (`total_weight * 7 / 10`), while the authoritative, chain-enforced threshold formula `NakamotoBlockHeader::compute_voting_weight_threshold` in `stackslib/src/chainstate/nakamoto/mod.rs` explicitly **rounds up** (`(total_weight*7)/10 + ceil`). Whenever `total_weight * 7` is not evenly divisible by 10 - the common case - the two formulas disagree by exactly one weight unit, so the signer-side "global agreement" check can fire on strictly less than the true 70% supermajority.

### Finding Description
The exact same "70%" concept is computed two different ways in this codebase:

- **Authoritative / chain-enforced** (`stackslib/src/chainstate/nakamoto/mod.rs`, `compute_voting_weight_threshold`):
```rust
let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
u32::try_from((total_weight * threshold) / 10 + ceil)
```
This is used both to validate block signatures (`verify_signer_signatures`) and by the signer itself to gate pre-commit → signature promotion (`stacks-signer/src/v0/signer.rs`, `handle_block_pre_commit`, `min_weight = NakamotoBlockHeader::compute_voting_weight_threshold(total_weight)`). It rounds **up**, so it is a true supermajority (≥70%, never less).

- **libsigner global state evaluator** (`libsigner/src/v0/signer_state.rs`):
```rust
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight) >= u64::from(self.total_weight)
        .strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD) / 10
}
pub fn reached_disagreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight) > u64::from(self.total_weight)
        .strict_mul(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD) / 10
}
```
This rounds **down** (integer division with no ceiling). For any `total_weight` where `total_weight * 7 % 10 != 0`, `reached_agreement` returns `true` for a `vote_weight` that is one unit below the value `compute_voting_weight_threshold` would require. E.g. `total_weight = 11`: the authoritative threshold is `ceil(11*7/10) = 8`, but `reached_agreement` already returns `true` at `vote_weight = 7` (`7 >= 77/10 = 7`).

`reached_agreement`/`determine_global_state`/`determine_latest_supported_signer_protocol_version`/`determine_global_burn_view`/`find_majority_prefix_replay_set` are the exact mechanism the signer uses to decide the network-wide "equality key" documented in `docs/signer-flows.md` §8: *"the whole miner state ... is the equality key for global agreement"*. This value drives `capitulate_viewpoint`/`handle_state_machine_update` in `stacks-signer/src/v0/signer.rs`, which decides which miner the signer treats as canonical, which supported protocol version is active, and which tx-replay set is adopted.

Because this rounding-down is a pure integer-division artifact of `total_weight` (not attacker-controlled key material), it requires **no majority and no malicious actor** to occur: it can be reached purely from honest peers' state-machine-update broadcasts whenever the current reward cycle's `total_signing_weight` isn't a multiple of 10 (a common, naturally occurring case, e.g. any signer set whose weights sum to 11, 13, 17, 21, ... reward slots). This exactly parallels the reported bug class: a precision/rounding truncation silently weakens a threshold check that must equal (or exceed) a canonically-enforced value, breaking the intended equality between "signer-computed agreement" and "70% supermajority."

### Impact Explanation
This does not directly let a single signer forge a block signature - actual signature aggregation for block validity still goes through the correctly-rounded `compute_voting_weight_threshold` in `NakamotoBlockHeader::verify_signer_signatures` and in `handle_block_pre_commit`. However, it degrades the guarantee behind the signer's *miner-view* state machine (who is the current miner, which parent tenure to build on, which protocol version/tx-replay set is active) below the intended 70% supermajority. A signer can `capitulate_viewpoint` to (and subsequently sign/propose against) a miner/tenure view that was only supported by slightly less than the real 70% threshold, i.e. it is "acting on a stale/incorrect threshold" for the consensus-visible state that other flows (section 5's conflict/pre-commit checks, tenure-extend logic) depend on. This matches the High-severity category: *"a signer ... acting on a stale reward set/threshold."* It is a systemic rounding inconsistency reachable by ordinary peer gossip, not requiring a majority or key compromise.

### Likelihood Explanation
High reachability, low complexity: it triggers automatically whenever `total_weight * 7 % 10 != 0`, which is the common case for realistic reward-slot totals, and requires no special signer behavior beyond normal `StateMachineUpdate` gossip already exchanged over StackerDB. No majority, no forged signatures, and no local access are needed - only that the weighted votes for a particular view happen to land at `floor(total*7/10)` rather than `ceil(total*7/10)`.

### Recommendation
Make `GlobalStateEvaluator::reached_agreement` and `reached_disagreement` use the same ceiling-rounding formula as `NakamotoBlockHeader::compute_voting_weight_threshold` (ideally by calling that function directly, or a shared helper), so the "global agreement" threshold used for miner-view/protocol-version/tx-replay-set consensus is provably ≥ the same 70% supermajority enforced on-chain for block signatures, eliminating the divergence for non-multiple-of-10 total weights.

### Proof of Concept
Analytical proof (integer arithmetic, no chain interaction needed):
```
total_weight = 11
NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD = 7

// Authoritative (stackslib) threshold:
compute_voting_weight_threshold(11) = ceil(11*7/10) = ceil(7.7) = 8

// libsigner GlobalStateEvaluator threshold:
reached_agreement(vote_weight = 7)
  => 7 >= (11 * 7) / 10   // = 77/10 = 7 (integer division, truncated)
  => 7 >= 7 => true
```
With `total_weight = 11` and honest signer weights summing to exactly 7 in support of a given `SignerStateMachine`/protocol version/burn view, `determine_global_state`/`determine_latest_supported_signer_protocol_version` will report "agreement reached" one full weight unit before the true 70% supermajority (8/11) is actually met, causing `capitulate_viewpoint` to adopt that view prematurely.
