### Title
Unauthenticated user enumeration via distinguishable error messages and timing in `POST /sessions` login flow - ([File: core/web/sessions_controller.go](core/web/sessions_controller.go))

### Summary
`SessionsController.Create` forwards the raw error from `AuthenticationProvider().CreateSession` directly into the HTTP response body via `jsonAPIError(c, http.StatusUnauthorized, err)`, and the underlying `localauth`/`oidcauth`/`ldapauth` implementations return textually different errors for "user not found" (raw SQL/driver error, e.g. `sql: no rows in result set`) versus "wrong password" (`Invalid password`), while also taking measurably different amounts of time (bcrypt hashing only happens when a user record is found). An unauthenticated attacker can use this to enumerate valid operator email accounts before mounting a targeted credential-stuffing/password-guessing attack.

### Finding Description
In `core/web/sessions_controller.go`, `Create` does: [1](#0-0) 
which passes any error from `CreateSession` straight to `jsonAPIError`, and `jsonAPIError` serializes `err.Error()` into the JSON body unmodified: [2](#0-1) 

The local auth implementation (`core/sessions/localauth/orm.go`) looks up the user first, and if not found returns immediately with the raw database error, before any bcrypt comparison is performed: [3](#0-2) 

For a known email with a wrong password, the code performs `utils.CheckPasswordHash`, which wraps `bcrypt.CompareHashAndPassword` (an intentionally slow, ~100ms-class operation), and returns the distinct error text `"Invalid password"`: [4](#0-3) 

The `oidcauth` and `ldapauth` fallback paths have the identical pattern (`localLoginFallback`), returning `"invalid email"` vs `"invalid password"` with the same asymmetric bcrypt-timing characteristic: [5](#0-4) [6](#0-5) 

Because the controller does not normalize the error message or status code, and does not enforce constant-time responses across the "unknown user" and "wrong password" branches, an unauthenticated attacker reaching `POST /sessions` can distinguish:
- Unknown email → fast response, raw driver/ORM error text (e.g., `sql: no rows in result set`).
- Known email + wrong password → slower response (bcrypt cost), distinct error text (`Invalid password` / `invalid password`).

This is a textbook user-enumeration oracle usable to build a target list of valid operator/admin emails prior to a credential-stuffing or password-spraying attack against the node's admin API.

### Impact Explanation
This does not by itself grant node takeover — the finding only establishes which emails are valid accounts, it does not bypass authentication, disclose passwords, or grant a session without correct credentials. The realistic impact is reconnaissance that meaningfully improves the efficiency and success probability of a subsequent offline/targeted password-guessing attack, which historically Chainlink/Immunefi programs class as lower severity than direct authentication bypass (i.e., this alone does not meet the "Critical: node takeover" bar claimed in the question — that requires a chained credential attack, which is a separate step with its own preconditions such as password guessability or reuse).

### Likelihood Explanation
Precondition is only unauthenticated network access to the node's API port (`POST /sessions`), no credentials or roles required, and the difference in response body and timing is deterministic and repeatable across every request. This makes it trivial for any attacker with network reachability to enumerate accounts, but exploitation to actual node compromise still depends on a follow-on credential attack succeeding (weak/reused password), which is outside the scope of `NewSessionsController` itself.

### Recommendation
- Return a uniform, generic error message and identical HTTP status code (401) regardless of whether the email exists or the password is wrong, at both the `SessionsController.Create` level and within each `AuthenticationProvider.CreateSession` implementation (`localauth`, `oidcauth`, `ldapauth`).
- Avoid propagating raw driver/ORM errors (e.g., `sql.ErrNoRows`) into `jsonAPIError`; wrap them into a single sentinel error such as `errors.New("invalid credentials")` before it reaches the controller.
- Equalize timing by always performing a constant-cost dummy bcrypt comparison when the user is not found, so the "unknown user" and "wrong password" code paths take statistically indistinguishable time.
- Apply consistent rate limiting per-IP/per-email on `/sessions` to blunt enumeration/brute-force regardless of message/timing parity.

### Proof of Concept
Go table/handler-level test plan (extending `core/web/sessions_controller_test.go`):
1. Create one known user via `app.AuthenticationProvider().CreateUser`.
2. Issue `POST /sessions` with:
   - (a) known email + wrong password
   - (b) unknown email + any password
3. For each request, capture: HTTP status code, full response body string, and wall-clock latency (using `time.Now()` around `client.Do`).
4. Assert failure: `assert.NotEqual(t, bodyA, bodyB)` (currently true, since bodies differ, e.g., `"Invalid password"` vs a raw SQL error string) — this test should fail after the fix (bodies should be identical, e.g., both `"invalid credentials"`).
5. Repeat each case ~20–50 times, average latency, and assert `latency(b) < latency(a)` significantly (bcrypt cost dominates in the wrong-password case) — after the fix, average latencies should converge within a small tolerance.
6. Run the same table test against `core/sessions/oidcauth/oidc_test.go` and `core/sessions/ldapauth/ldap_test.go` `localLoginFallback` paths to confirm the same body/timing asymmetry (`"invalid email"` vs `"invalid password"`).

// jsonAPIError adds an error to the gin context and sets
// the JSON value of errors.
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})

// CheckPasswordHash wraps around bcrypt.CompareHashAndPassword for a friendlier API.
func CheckPasswordHash(password, hash string) bool {
	err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
	return err == nil
}
