### Title
Deleverage withdraw daily-cap bypass via zero-price when `ACCOUNT_IN_DELEVERAGE` is set without receivership/order-execution and the group rate limiter is disabled - ([File: programs/marginfi/src/instructions/kamino/withdraw.rs])

### Summary
In `kamino_withdraw`, the oracle price used for both rate-limiting and deleverage-cap accounting is only fetched when `ACCOUNT_IN_RECEIVERSHIP`/`ACCOUNT_IN_ORDER_EXECUTION` is set or the group rate limiter is enabled; otherwise `price` is hard-coded to `I80F48::ZERO`. Because the deleverage-limit check `group.check_deleverage_withdraw_limit` is gated only on `ACCOUNT_IN_DELEVERAGE` (independent of the price-fetch condition), an account that carries `ACCOUNT_IN_DELEVERAGE` after receivership has ended (e.g., post `liquidate_end`) can withdraw arbitrary collateral through `kamino_withdraw` while the daily deleverage cap silently records `withdrawn_equity = 0`.

### Finding Description
The relevant logic [1](#0-0)  computes `price` as `I80F48::ZERO` whenever the account is not currently flagged `ACCOUNT_IN_RECEIVERSHIP`/`ACCOUNT_IN_ORDER_EXECUTION` and `group.rate_limiter.is_enabled()` is false. Separately, the deleverage-cap check is keyed purely off `ACCOUNT_IN_DELEVERAGE`: [2](#0-1) . These two conditions are decoupled: nothing in this function guarantees `ACCOUNT_IN_DELEVERAGE` is only ever true while `ACCOUNT_IN_RECEIVERSHIP`/`ACCOUNT_IN_ORDER_EXECUTION` is also true.

The comment "we only care about the withdraw limit in case of deleverage" indicates the deleverage flag is intended to persist as an independent, longer-lived marker (tracking the account's ongoing deleverage-cap window) that can outlive the receivership/order-execution episode that originally triggered it — for example, after `liquidate_end` clears `ACCOUNT_IN_RECEIVERSHIP` while `ACCOUNT_IN_DELEVERAGE` remains set for continued cap tracking. In that state, if the group's USD rate limiter (`group.rate_limiter`) happens to be disabled (a normal, reachable admin/group configuration — rate limiting is opt-in), the account authority — an ordinary signer authorized via `is_signer_authorized` on the account — can call the public `kamino_withdraw` instruction directly. `price` is forced to `I80F48::ZERO`, so `withdrawn_equity = calc_value(collateral_amount, 0, ...) = 0`, and `group.check_deleverage_withdraw_limit(0, ts)` always succeeds regardless of `collateral_amount`. The same pattern is replicated identically in `drift/withdraw.rs`, `juplend/withdraw.rs`, `solend/withdraw.rs`, and `marginfi_account/withdraw.rs`.

### Impact Explanation
The deleverage daily-USD cap exists to bound how much value an at-risk/deleveraging account can withdraw in a rolling window, protecting the group/bank from uncontrolled outflow during a deleverage episode. Because the price-gating logic and the deleverage-accounting logic use different, decoupled conditions, the cap can be rendered a permanent no-op for any account that retains `ACCOUNT_IN_DELEVERAGE` outside of active receivership/order-execution while the group rate limiter is off — letting the account owner withdraw unlimited collateral value with zero recorded outflow. This is an unsafe-settlement / broken-invariant issue: accounting state (`withdrawn_equity`) is decoupled from real economic value withdrawn.

### Likelihood Explanation
Requires: (1) an account state where `ACCOUNT_IN_DELEVERAGE` is set but `ACCOUNT_IN_RECEIVERSHIP`/`ACCOUNT_IN_ORDER_EXECUTION` is cleared — plausible if this flag is designed to persist across/after a liquidation or order-execution episode for continued cap tracking (as implied by the standalone check and comment), and (2) the group's rate limiter being disabled, which is a normal (non-default-enforced) group configuration. Once both hold, the call is fully permissionless and repeatable by the account's own authorized signer with no privileged action needed at exploit time.

### Recommendation
Decouple the price requirement from the receivership/order-execution flag and tie it to whether deleverage-cap accounting is needed: fetch (and require non-zero) price whenever `ACCOUNT_IN_DELEVERAGE` is set, not only when `ACCOUNT_IN_RECEIVERSHIP`/`ACCOUNT_IN_ORDER_EXECUTION` is set or the rate limiter is enabled. E.g. change the condition to `in_receivership_or_order_execution || group_rate_limit_enabled || marginfi_account.get_flag(ACCOUNT_IN_DELEVERAGE)`, and enforce `price > 0` whenever `ACCOUNT_IN_DELEVERAGE` is set (mirroring the existing receivership zero-price guard). Apply the same fix consistently across `drift/withdraw.rs`, `juplend/withdraw.rs`, `solend/withdraw.rs`, and `marginfi_account/withdraw.rs`.

### Proof of Concept
Rust integration/invariant test plan:
1. Construct a `MarginfiAccount` with `ACCOUNT_IN_DELEVERAGE` set and `ACCOUNT_IN_RECEIVERSHIP`/`ACCOUNT_IN_ORDER_EXECUTION` cleared (simulating post-`liquidate_end` state where deleverage tracking continues).
2. Configure the group with `rate_limiter` disabled (`max_outflow = 0` on both hourly/daily windows).
3. Call `kamino_withdraw` with a large `amount` of collateral.
4. Assert: `price == I80F48::ZERO` inside the function, `withdrawn_equity == I80F48::ZERO`, and `group.check_deleverage_withdraw_limit` returns `Ok` despite the large withdrawal.
5. Fuzz over all 8 combinations of `{ACCOUNT_IN_DELEVERAGE, ACCOUNT_IN_RECEIVERSHIP|ACCOUNT_IN_ORDER_EXECUTION, group_rate_limiter enabled}` and assert the invariant: whenever `ACCOUNT_IN_DELEVERAGE` is set and `collateral_amount > 0`, `withdrawn_equity` must never be zero (`NO_VALUE_REDIRECTION`). The test should fail on current code for the `{DELEVERAGE=true, RECEIVERSHIP/ORDER=false, rate_limiter=false}` case.
