### Title
Missing zero-value validation in `createWriteOffRequest` lets anyone steal escrowed tranche tokens for free - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` validates that `amount != 0` but never validates `underlyingsRequested`. A write-off request with `underlyings == 0` can be fulfilled by any unprivileged caller for 0 underlying tokens, and the fulfiller receives the full escrowed tranche balance. This mirrors the advisory's bug class: an attacker-supplied parameter passes through a handler that validates some fields (`amount`, epoch state) but skips a symmetric check on another (`underlyingsRequested`), and the downstream path (`fullfillWriteOffRequest`) trusts the stored value instead of re-checking it.

### Finding Description
In `createWriteOffRequest` (line 86-102):

```solidity
if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
if (amount == 0) revert NotAllowed();
// underlyingsRequested is never validated
IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
```

In `fullfillWriteOffRequest` (line 123-151) the only consistency check is:

```solidity
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
  revert WrongRequest();
}
```

When `currentRequest.underlyings == 0`, the condition `_underlyings < 0` is impossible, so any `_underlyings` — including `0` — satisfies the check. The fulfiller calls `fullfillWriteOffRequest(victim, tranches, 0)`, transfers `0` underlying (minus a `0` exit fee), and receives `currentRequest.tranches` escrowed tranche tokens (line 151: `IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches)`).

The asymmetric validation is the bug: `amount == 0` is rejected (line 90) precisely because a zero-amount request is meaningless/abusable, but the equivalent zero check on the price leg (`underlyingsRequested`) was missed — the same "missed check on one of several sibling parameters" pattern as GHSA-585v-hcgf-jhfr, where five SDM handlers lacked the `IsValidSupi` check present in `HandleGetAmData`.

Additionally, `createWriteOffRequest` can be called while the victim already has a request open, so a request whose price leg is partially zero (first call with `underlyingsRequested = 0`) is stored as-is; there is no "price must cover tranche value" or even `> 0` sanity anywhere.

### Impact Explanation
Direct theft of escrowed tranche tokens. Any write-off request stored with `underlyings == 0` (user error, a partially-front-run transaction, or a lender who set a nonzero price on a first `createWriteOffRequest` call but whose second call the attacker observes doesn't matter — the simplest case is a request the lender priced at 0, or a UI/relayer bug) can be drained by any EOA: the fulfiller pays nothing and receives the full tranche balance, which is redeemable for underlying via `requestWithdraw`/`claimWithdrawRequest` or sellable. The loss equals the full underlying value of the escrowed tranche tokens (e.g., 100,000 USDC worth of AA tranches stolen for 0 USDC), while the lender receives `0 - fee` underlying.

Even absent a "fat-finger" lender, the missing check enables griefing: an attacker who sees a pending `createWriteOffRequest` priced in a follow-up call can... — more concretely, the invariant broken is "one receipt, fair payout": escrowed principal is released without any consideration, which the contract's own `WrongRequest` check is explicitly designed to prevent but fails to for the zero-price edge case.

### Likelihood Explanation
- Attacker requirements: none beyond a standard EOA. `fullfillWriteOffRequest` is permissionless ("this function can be called by any wallet", line 122).
- Trigger condition: a `WriteOffRequest` with `underlyings == 0` existing in `userRequests`. This is reachable only through `createWriteOffRequest`, which itself accepts `underlyingsRequested = 0` — the same missing validation. There is no epoch-phase requirement beyond `isEpochRunning()` at creation; fulfillment is phase-agnostic.
- No existing guard stops it: `nonReentrant` doesn't help, `WrongRequest` is satisfied, `pendingUnderlyings` bookkeeping (line 134) clamps at 0, and `emergencyWithdraw`/`setExitFee` are owner-only and irrelevant to the theft path.

The scenario requires a requester to store a zero-price request, which is plausibly a user/integration mistake rather than something an attacker can force on an arbitrary victim — this lowers likelihood versus a self-contained attack, but the contract-level missing-validation flaw and the free-claim path it opens are real and unconditional once such a request exists.

### Recommendation
Add a symmetric zero check in `createWriteOffRequest`, matching the existing `amount == 0` guard:

```solidity
if (amount == 0 || underlyingsRequested == 0) revert NotAllowed();
```

Optionally also enforce in `fullfillWriteOffRequest` that `currentRequest.underlyings != 0` (defense-in-depth for legacy/upgraded escrow instances that may already hold zero-priced requests — note the code at lines 112 and 134 already carries explicit handling for "legacy requests" from upgraded deployments, so unvalidated historical state is a documented concern).

### Proof of Concept
Foundry fork PoC (against an upgraded escrow wired to a live `IdleCDOEpochVariant`/`IdleCreditVault`, or a minimal harness deploying `IdleCreditVaultWriteOffEscrow` with mock tranche/underlying):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVaultWriteOffEscrow} from "../contracts/IdleCreditVaultWriteOffEscrow.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract WriteOffZeroPriceSteal is Test {
    IdleCreditVaultWriteOffEscrow escrow; // deployed & initialized with a live CDO epoch
    address lender = makeAddr("lender");
    address attacker = makeAddr("attacker");
    IERC20Detailed tranche;
    IERC20Detailed underlying;

    function test_stealTranchesForFree() public {
        tranche = IERC20Detailed(escrow.tranche());
        underlying = IERC20Detailed(escrow.underlying());

        // epoch is running (escrow.createWriteOffRequest requires isEpochRunning)
        uint256 trancheAmount = 100_000e18;
        deal(address(tranche), lender, trancheAmount);

        // 1. Lender creates a request with underlyingsRequested = 0 (no validation rejects it)
        vm.startPrank(lender);
        tranche.approve(address(escrow), trancheAmount);
        escrow.createWriteOffRequest(trancheAmount, 0); // succeeds: only amount==0 is checked
        vm.stopPrank();

        assertEq(tranche.balanceOf(address(escrow)), trancheAmount);
        assertEq(underlying.balanceOf(attacker), 0);

        // 2. Attacker fulfills the request paying 0 underlying
        //    WrongRequest check: _underlyings (0) < currentRequest.underlyings (0) is false -> passes
        vm.prank(attacker);
        escrow.fullfillWriteOffRequest(lender, trancheAmount, 0);

        // 3. Attacker received ALL escrowed tranche tokens for free; lender got nothing
        assertEq(tranche.balanceOf(attacker), trancheAmount);
        assertEq(underlying.balanceOf(lender), 0);
        assertEq(tranche.balanceOf(address(escrow)), 0);
    }
}
```

Expected result: the fulfill call succeeds, `attacker` ends with `trancheAmount` tranche tokens (redeemable at tranche price), `lender` receives `0` underlying, and no approval or capital is needed from the attacker beyond gas.
