### Title
Removed multisig member's stale confirmation still counts toward quorum, allowing requests to execute below the live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges requests **originated** by the removed member, but never scrubs that member's entries from the `confirmations` set of requests originated by *other* members. Since `confirm()` counts entries in that set toward `num_confirmations` without checking whether the confirming identity is still a current member, a request can later be executed using a confirmation cast by an account that is no longer part of the multisig — i.e., fewer live, currently-trusted members actually signed off than `num_confirmations` requires.

### Finding Description
The invariant the multisig is supposed to enforce is: *a request executes only once `num_confirmations` distinct **current** members have confirmed it* — i.e. `confirmations.len() >= num_confirmations` should equal `live_member_confirmations.len() >= num_confirmations`.

`confirm()` checks quorum purely by counting strings in the `HashSet<String>` for the request: [1](#0-0) 

`delete_member()` removes the member from `self.members` and deletes only the requests *added* by that member, along with those requests' confirmation sets. It does not touch the `confirmations` sets of requests added by *other* members that the removed member may have already confirmed: [2](#0-1) 

Because of this, once member `B` confirms a request `X` that was added by member `A`, and `B` is later removed via a `DeleteMember` request, `B`'s confirmation string remains inside `confirmations[X]`. `B` is no longer in `self.members`, so `current_member()` would reject any *new* action from `B`, but the *already-recorded* confirmation from `B` is never invalidated: [3](#0-2) 

When the remaining members later add their own confirmations to `X`, the stale entry from the removed `B` is counted, letting the request reach `num_confirmations` and execute even though fewer than `num_confirmations` *current* members actually approved it.

### Impact Explanation
This breaks the equality the contract is meant to guarantee: `confirmations counted == live members who approved`. A multisig request (which can be an arbitrary `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc.) can be executed with fewer than the configured threshold of live, currently-trusted confirmations. This maps directly to the Critical impact category: "a multisig request executed below threshold." An account removed for being compromised or malicious can still contribute a binding, persistent "vote" toward authorizing fund transfers or key changes after its removal, defeating the purpose of `DeleteMember`.

### Likelihood Explanation
This requires no attacker privilege beyond being (or having been) a normal multisig member at some point — a very plausible real-world flow: a member's key is suspected compromised, the remaining members vote to remove it, but any request that member had already confirmed retains that confirmation forever. No special timing manipulation, no external contract, and no reliance on foundation/owner actions is needed; it simply falls out of the normal `add_request` → `confirm` → `DeleteMember` → `confirm` sequence available to any set of multisig members.

### Recommendation
When executing `DeleteMember`, iterate over **all** outstanding requests (not just those added by the removed member) and remove the deleted member's entry from each request's `confirmations` set, or alternatively re-validate at `confirm()`/`execute_request()` time that every entry in the confirmations set still corresponds to a current member (filtering out stale/non-member confirmations before comparing against `num_confirmations`).

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. `A` calls `add_request` to create request `X` (e.g. `Transfer`). `A`'s confirmation is implicit only if using `add_request_and_confirm`; assume `A` uses `add_request_and_confirm` → `confirmations[X] = {A}`.
3. `B` calls `confirm(X)` → `confirmations[X] = {A, B}` (2/3, not yet executed).
4. Members detect `B` is compromised. `A`, `C`, `D` create and confirm a `DeleteMember{member: B}` request (separate request `Y`), which reaches quorum and executes `delete_member`, removing `B` from `self.members`. Per [4](#0-3) , only requests where `r.member == B` (requests *added* by B) are purged — `X` was added by `A`, so it is untouched, and `confirmations[X]` still contains `B`.
5. `C` calls `confirm(X)` → `confirmations[X] = {A, B, C}`. `confirmations.len() == 3 == num_confirmations`, so `execute_request(X)` runs via [5](#0-4) , even though `B` is no longer a member and only `A` and `C` are the live members who ever confirmed `X`.

Result: request `X` executes with confirmations from only 2 live members (`A`, `C`) plus one stale confirmation from a removed member `B`, despite `num_confirmations = 3`, breaking the threshold guarantee.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
