## Analysis

The Autonomint bug pattern is: an aggregate accounting value is decremented/computed using an amount denominated in the wrong unit (a collateral-token amount used as if it were an ETH-equivalent amount), corrupting downstream calculations. The strongest analog in marginfi-v2 is in the Kamino/Solend integration withdraw flows, where `record_withdrawal_outflow` feeds a **collateral-token amount** into both the bank-level native-token rate limiter and the group-level USD value calculation as if it were the actual underlying liquidity amount transferred.

### Title
Kamino/Solend withdrawal rate-limit accounting uses collateral-token amount instead of redeemed liquidity amount, corrupting outflow tracking - ([File: programs/marginfi/src/instructions/kamino/withdraw.rs])

### Summary
`kamino_withdraw` and `solend_withdraw` accept an `amount` parameter denominated in **collateral tokens** (shares of the Kamino/Solend reserve), which appreciate in value relative to the underlying liquidity token over time [1](#0-0) . Both instructions pass this same collateral-token `amount` (or `collateral_amount` for `withdraw_all`) directly into `record_withdrawal_outflow` as `native_amount`/`balance_amount`, which then feeds the bank-level native-token rate limiter and the USD value calc used for the group-level rate limiter [2](#0-1) [3](#0-2) .

### Finding Description
`record_withdrawal_outflow` records `native_amount` on the bank's native-token rate limiter and computes a USD value via `calc_value(balance_amount, price, bank.get_balance_decimals(), None)` for the group-level rate limiter, using the price and decimals of the bank's underlying mint (e.g., USDC) [4](#0-3) .

However, per the Kamino integration documentation, withdraw and liquidate instructions operate on **collateral token amounts**, not liquidity token amounts, and "since collateral tokens appreciate in value relative to the liquidity token as interest accumulates, liquidators and withdrawers must manually convert from collateral token amounts to liquidity token amounts using the current exchange rate" [5](#0-4) .

In `kamino_withdraw`, the `rate_limit_amount` fed into `record_withdrawal_outflow` is exactly this raw collateral-token `amount`/`collateral_amount`, not the actual liquidity amount that leaves the reserve and is transferred to the user (`received`, computed later from vault balance deltas) [6](#0-5) . The same pattern exists in `solend_withdraw` [7](#0-6) .

This is the same class of bug as the Autonomint report: a value in one denomination (collateral/share units) is substituted for a value that should be in another denomination (underlying/liquidity units) when updating an aggregate accounting/limiting variable, because the exchange rate between the two is not 1:1 and drifts over time as interest accrues (the collateral-to-liquidity conversion function itself documents this: "collateral tokens appreciate... as interest accumulates" and round-trip conversions are lossy [8](#0-7) , and the actual conversion utility `collateral_to_liquidity`/`liquidity_to_collateral` exists precisely to bridge this gap but is not used for rate-limit accounting [9](#0-8) ).

By contrast, the corresponding deposit flow correctly passes the liquidity-denominated `amount` into `record_deposit_inflow` [10](#0-9) , creating an asymmetry between inflow (liquidity units) and outflow (collateral units) accounting on the same bank-level and group-level rate limiters, which are documented as tracking "native token net outflow" and "USD net outflow across the whole group" respectively [11](#0-10) .

### Impact Explanation
Because Kamino/Solend collateral tokens appreciate relative to the liquidity token as interest accrues (exchange rate > 1 over time), a withdrawal of `N` collateral tokens redeems **more** than `N` liquidity tokens. Recording only `N` (the smaller, collateral-denominated figure) into:
1. The bank-level native rate limiter under-counts the true native outflow, allowing users to bypass the bank's configured hourly/daily withdrawal caps by an amount proportional to the accrued exchange-rate premium.
2. The group-level USD rate limiter (`calc_value(balance_amount, price, decimals, None)`) under-values the outflow in the same way, since `price` is the underlying asset's price but `balance_amount` is not actually that many underlying tokens — allowing bypass of the group-wide hourly/daily USD outflow cap, which is explicitly described as "a defense if the risk workflow is abused or compromised" [12](#0-11) .

This degrades a security control (rate limiting) rather than directly stealing funds, but it has a durable financial-safety effect: the protocol's defense-in-depth outflow caps (used to protect against draining during oracle/risk-workflow compromise) can be silently under-enforced specifically through the Kamino/Solend withdrawal paths, in proportion to how much the reserve's collateral/liquidity exchange rate has diverged from 1:1.

### Likelihood Explanation
This is triggered by any ordinary, unprivileged user calling `kamino_withdraw` or `solend_withdraw` — no special privileges are required, and it occurs whenever the group or bank rate limiter is enabled and the Kamino/Solend reserve's collateral exchange rate has moved away from 1:1 (which happens naturally over time as interest accrues) [2](#0-1) . The magnitude of the discrepancy grows with reserve age/interest accrual, and is directly demonstrated by the protocol's own test showing collateral/liquidity conversions diverge over repeated operations [8](#0-7) .

### Recommendation
In `record_withdrawal_outflow` calls from `kamino_withdraw` and `solend_withdraw`, convert the collateral-token amount to the actual liquidity/native amount (using `collateral_to_liquidity`, already computed elsewhere in these functions as `expected_liquidity_amount`/`received`) before passing it as `native_amount`/`balance_amount`, so that both the bank-level native rate limiter and the group-level USD value calculation reflect the true amount of underlying tokens leaving the vault, consistent with how deposits record liquidity-denominated inflows.

### Proof of Concept
Not directly executable from available context (would require a live test harness with a Kamino/Solend reserve whose collateral exchange rate has appreciated, plus rate limiter configuration, to demonstrate the under-recorded outflow numerically) — the root-cause code path (passing `collateral_amount`/`amount` directly to `record_withdrawal_outflow` instead of the converted liquidity amount) is confirmed by direct reading of `kamino_withdraw` [6](#0-5)  and `solend_withdraw` [7](#0-6) .

/// Records withdrawal outflow on bank-level rate limiter and validates against
/// group-level rate limits (read-only). Emits a `RateLimitFlowEvent` for the
/// delegate flow admin to aggregate off-chain and update the group
/// rate limiter via
/// `update_group_rate_limiter`.
pub fn record_withdrawal_outflow(
    group_rate_limit_enabled: bool,
    native_amount: u64,
    balance_amount: u64,
    price: I80F48,
    bank: &mut Bank,
    group: &MarginfiGroup,
    group_key: Pubkey,
    bank_key: Pubkey,
    marginfi_account: &MarginfiAccount,
    clock: &Clock,
) -> MarginfiResult<()> {
    // Rate limiting tracks net outflow; skip for flashloan/liquidation/deleverage flows.
    if !should_skip_rate_limit(marginfi_account.account_flags) {
        if bank.rate_limiter.is_enabled() {
            bank.rate_limiter
                .try_record_outflow(native_amount, clock.unix_timestamp)?;
        }

        // Group-level rate limiting: read-only validation + event emission.
        // The admin aggregates events off-chain and calls update_group_rate_limiter.
        if group_rate_limit_enabled {
            check!(price > I80F48::ZERO, MarginfiError::InvalidRateLimitPrice);

            let value = calc_value(
                I80F48::from_num(balance_amount),
                price,
                bank.get_balance_decimals(),
                None,
            )?;
            if group.rate_limiter.hourly.is_enabled() {
                let remaining = group
                    .rate_limiter
                    .hourly
                    .effective_remaining_capacity(clock.unix_timestamp);
                if value.to_num::<i64>() > remaining {
                    return Err(MarginfiError::GroupHourlyRateLimitExceeded.into());
                }
            }
            if group.rate_limiter.daily.is_enabled() {
                let remaining = group
                    .rate_limiter
                    .daily
                    .effective_remaining_capacity(clock.unix_timestamp);
                if value.to_num::<i64>() > remaining {
                    return Err(MarginfiError::GroupDailyRateLimitExceeded.into());
                }
            }

            emit!(RateLimitFlowEvent {
                group: group_key,
                bank: bank_key,
                mint: bank.mint,
                flow_direction: 0, // outflow
                native_amount,
                mint_decimals: bank.mint_decimals,
                current_timestamp: clock.unix_timestamp,
            });
        }
    }
    Ok(())
}

## Deleverage Withdraw Limit Flow

This is separate from the normal borrow/withdraw rate limiter.

It exists to cap how much USD value can be withdrawn from a group through forced deleveraging in a
day, as a defense if the risk workflow is abused or compromised.

### 1. Configuration

The daily cap is set with `configure_deleverage_withdrawal_limit`.

- The configured limit is a USD integer (`u32`).
- The instruction requires a non-zero value.
- Internally, the runtime still treats `0` as unlimited for backward compatibility when checking
  cached state.
