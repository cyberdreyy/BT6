### Title
`depositDuringEpoch` credits/forwards the nominal `_amount` instead of the actual received amount, so a fee-on-transfer underlying lets a depositor mint shares and push funds to the borrower that were never received - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external bug class is "received volume may be less than (or zero vs) the nominal amount" for fee-on-transfer tokens. The credit-vault analog lives in `IdleCDOEpochVariant.depositDuringEpoch`: unlike `_deposit` (both in `IdleCDO.sol` and `IdleCDOCreditVault.sol`), which measures the balance delta, `depositDuringEpoch` never measures what actually arrived. It transfers `_amount` in, computes interest and minted shares from `_amount`, mints `_amount` strategy tokens, and then transfers the full `_amount` to the borrower. With a fee-on-transfer (or deflationary) underlying, the vault receives `_amount - fee` — possibly 0 — yet pays out and accounts for `_amount`, directly socializing the shortfall onto honest depositors. The same nominal-vs-received mismatch exists in `IdleCDOCreditVault._deposit`, which mints shares on the delta but then calls `IIdleCDOStrategy(strategy).deposit(_amount)` with the full nominal amount, pulling the missing fee out of the unlent reserve belonging to other depositors.

No `preBal`/`postBal` measurement exists anywhere in this function — contrast with the base `_deposit`, which correctly mints on the received delta: [3](#0-2) 

Because strategy tokens are minted 1:1 (`getContractValue` counts `strategyToken` balance + raw balance, `contracts/IdleCDOCreditVault.sol:125-128`), minting `_amount` strategy tokens while only `_amount - fee` underlyings arrived inflates NAV. Then `_transferUnderlyings(_borrower(), _amount)` sends the full `_amount` out — funded partly by pre-existing vault balance. `lastNAVAA/BB` is increased by `_amount` via `_mintShares` (`contracts/IdleCDOCreditVault.sol:355-363`), so the missing fee is hidden until withdrawals.

In `IdleCDOCreditVault._deposit` the analogous residual issue is `IIdleCDOStrategy(strategy).deposit(_amount)` at line 211 using the nominal amount rather than `received = _contractTokenBalance(_token) - _preBal`, so the strategy pull overdraws the unlent reserve by the transfer fee.

### Impact Explanation
Direct insolvency proportional to the token's transfer fee, repeatable every deposit. In the extreme analog of the external report — a token whose fee consumes a small transfer entirely (received = 0) — `depositDuringEpoch` still mints `(0 + trancheInterest)-adjusted` shares, adds `_amount` to `lastNAV`, mints `_amount` strategy tokens, and sends `_amount` of other depositors' money to the borrower. The deficit is socialized across all tranche holders at epoch end / withdrawal; in a default or instant-withdraw race the loss lands on whoever exits last. There is no guard: `_skimDonatedAssets` only sweeps unsolicited surplus, `_guarded` only caps the limit, and `isWalletAllowed`/KYC does not stop an allowed lender from depositing a fee-charging token.

### Likelihood Explanation
Requires the vault's `token` (`_guardedToken` set at initialize) to charge a transfer fee or otherwise deliver less than `transferFrom` requested — e.g., USDT with fee enabled, or any deflationary token chosen as underlying for a new vault via `IdleCreditVaultFactory`. `depositDuringEpoch` also requires `isDepositDuringEpochDisabled == false`, a running epoch, non-empty tranche supply, and a KYC-allowed caller — all normal operating conditions. The `_deposit` strategy-pull mismatch (line 211) requires only a normal deposit, no epoch running.

### Recommendation
Measure the received amount and use it everywhere downstream:

```solidity
// depositDuringEpoch
uint256 _preBal = _contractTokenBalance(token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
uint256 _received = _contractTokenBalance(token) - _preBal;
require(_received > 0); // analog of "volumeReceived > 0"
// compute interest, _minted, mintStrategyTokens, and the borrower transfer on _received
```

And in `IdleCDOCreditVault._deposit`, pass the measured delta to `IIdleCDOStrategy(strategy).deposit(received)` instead of `_amount`. Alternatively, revert in `_transferUnderlyingsFrom` if the balance delta differs from `_amount` to exclude fee-on-transfer underlyings entirely.

### Proof of Concept
Foundry fork PoC sketch (modeled on `testDepositDuringEpochNumericalAA` in `test/foundry/IdleCreditVault.t.sol`):

1. Deploy a mock ERC20 `FeeToken` that burns e.g. 10% (or 100% below a threshold) on `transferFrom`; initialize the credit vault with `token = FeeToken`.
2. Seed: `depositAA(1000e18)` with fee disabled or pre-funded, `setIsAYSActive(false)`, `startEpoch`, warp to mid-epoch, `setIsDepositDuringEpochDisabled(false)`.
3. Attacker (KYC-allowed) calls `depositDuringEpoch(1000e18, AATranche)`:
   - Vault receives 900e18, but `minted = (1000 + trancheInterest) * supply / expectedFinal`, `lastNAVAA += 1000e18`, `mintStrategyTokens(1000e18)`, and `borrower` is transferred the full 1000e18.
4. Assert `FeeToken.balanceOf(cdo)` increased by only 900e18 while `strategyToken.balanceOf(cdo)` increased by 1000e18 and borrower gained 1000e18 — a 100e18 unbacked liability.
5. `stopEpoch` and withdraw: last redeemer's `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` shows a ~100e18 shortfall vs. their virtualPrice entitlement — quantified loss equal to the fee per deposit.

For the zero-received edge: set the fee to consume the whole transfer (received = 0) and repeat — the borrower still receives `_amount` and shares are still minted, demonstrating the exact `volumeReceived == 0` analog.

One caveat: I could not read `contracts/strategies/idle/IdleCreditVault.sol` (its `deposit`/`mintStrategyTokens` internals) within the iteration limit, so the claim that `strategy.deposit(_amount)` pulls/mints 1:1 on the nominal amount rests on `getContractValue` treating strategy tokens 1:1 and the test assertion `strategyTokenBal + depositAmount` in `testDepositDuringEpochNumericalAA`.
