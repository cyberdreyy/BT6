### Title
Paid instant-withdraw receipts are never cleared from `instantWithdrawsRequestsByEpoch`, inflating default-recovery basis with phantom claims and stranding/stealing recovery funds - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` burns the aggregate `instantWithdrawsRequests[_user]` and pays out the funded claim, but it never clears the per-epoch records `instantWithdrawsRequestsByEpoch[_user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]` [1](#0-0) . When a borrower default is later finalized in that same epoch while some other instant receipt remains unfunded (`pendingInstantWithdraws != 0`), `defaultPendingClaimBasis` re-counts already-paid receipts as outstanding claim basis [2](#0-1) , and `_defaultPrefundedInstantReserve` treats the paid-out amount as underlying still held in the strategy [3](#0-2) . The finalized `defaultRecoveryReserve` and `defaultRecoveryPrice` are therefore computed against funds that no longer exist, permanently freezing or stealing recovery payouts for real claimants.

### Finding Description
This is the credit-vault analog of "attacker-controlled write to an arbitrary path": an unprivileged user writes a stale claim record that the protocol later treats as an outstanding liability.

Sequence:

1. During the buffer phase of epoch N (instant withdrawals enabled, fixed-APR mode), attacker calls `requestWithdraw` on `IdleCDOEpochVariant` and triggers `requestInstantWithdraw(X)`, and a victim requests instant `Y`. Both write `instantWithdrawsRequestsByEpoch[user][N]` and increase `instantWithdrawClaimsByEpoch[N]` by `X + Y` [4](#0-3) .
2. Honest manager calls `startEpoch`; the CDO only has enough cash to fund `X`. `collectInstantWithdrawFunds(X)` reduces `pendingInstantWithdraws` to `Y` but does not touch the per-epoch mappings [5](#0-4) .
3. Attacker calls `claimInstantWithdrawRequest` via the CDO and is paid `X`. `instantWithdrawsRequests[attacker]` is zeroed, but `instantWithdrawsRequestsByEpoch[attacker][N]` and `instantWithdrawClaimsByEpoch[N]` still hold `X` — the stale write [1](#0-0) .
4. The epoch ends and the borrower (honest but unable to repay) fails to return funds; `_handleBorrowerDefault`/`stopEpoch` marks `defaulted`. Owner calls `finalizeDefault(_recoveredAmount, source)` → `finalizeDefaultRecovery`.
5. `defaultPendingClaimBasis` returns `pendingWithdraws + instantWithdrawClaimsByEpoch[N]` = victim's `Y` plus attacker's already-paid `X` [2](#0-1) .
6. `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant = (X + Y) - Y = X` and adds this phantom `X` to `reserveAmount`, even though the strategy already transferred `X` to the attacker [3](#0-2) . `defaultRecoveryReserve` is then set to a value exceeding the contract's real underlying balance [6](#0-5) .
7. When the victim calls `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` pays `Y * defaultRecoveryPrice / 1e18` from a reserve that is `X` short of accounted value. If the strategy's actual balance is insufficient, `safeTransfer` reverts and the victim's recovery is permanently frozen; if other claimants draw first, the accounting still pays out more than exists, and `_transferDefaultRecovery` bookkeeping permanently diverges from real balances [7](#0-6) .

Note: the attacker cannot personally double-claim — `instantWithdrawsRequests[_user] -= claimBasis` would underflow since the aggregate was already zeroed. The loss instead materializes for other claimants (dilution and frozen recovery), which still satisfies the impact criteria.

### Impact Explanation
Every instant receipt that was fully funded and claimed inside the defaulted epoch permanently inflates `instantWithdrawClaimsByEpoch` and the prefunded-reserve term. Quantified: with attacker claim `X` and victim unfunded claim `Y`, `defaultRecoveryReserve` is overstated by exactly `X` underlying units and `defaultRecoveryPrice` is computed against `X + Y` of instant basis instead of `Y`. The victim's recovery payout is either diluted across phantom basis or reverts entirely once the strategy's real balance is exhausted — direct loss/permanent freezing of unclaimed recovery equal to up to `X` (attacker-controlled, bounded only by the instant liquidity funded at epoch start).

### Likelihood Explanation
Requires (a) instant withdrawals enabled, (b) at least one claimed instant receipt and one unfunded instant receipt in the same epoch, and (c) a borrower default finalized in that epoch. Condition (b) occurs naturally whenever instant demand exceeds CDO cash at `startEpoch`; (c) is the protocol's designed failure path (`_handleBorrowerDefault`, `finalizeDefault`). No privileged or malicious role is needed — all attacker steps (`requestWithdraw` instant path, `claimInstantWithdrawRequest`) are permissionless user calls. Existing guards (`_onlyIdleCDO`, `nonReentrant`, `defaultInstantWithdrawsFinalized` gate) do not prevent it because the flaw is missing cleanup of per-epoch state, not an access failure.

### Recommendation
In `claimInstantWithdrawRequest`, after paying a funded claim, decrement `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount (care needed if a claim spans the epoch boundary — alternatively track a per-epoch "funded" vs "claimed" split so `defaultPendingClaimBasis` only counts receipts not yet paid out). Equivalently, make `defaultPendingClaimBasis` derive pending instant basis from actual unclaimed receipts rather than a cumulative per-epoch counter.

### Proof of Concept
Foundry fork PoC sketch (against the existing `IdleCreditVault.t.sol` harness):

```solidity
// setup: idleCDO deposits, epoch configured with instant withdraws enabled
// 1. buffer phase of epoch N:
vm.prank(attacker); cdoEpoch.requestWithdraw(amountA, AAtranche); // triggers requestInstantWithdraw when apr delta hit, or directly via instant path
vm.prank(victim);   cdoEpoch.requestWithdraw(amountV, AAtranche);
// 2. ensure CDO cash funds only amountA
vm.prank(manager);  cdoEpoch.startEpoch();   // collectInstantWithdrawFunds(amountA), pendingInstantWithdraws = amountV
// 3. attacker claims funded receipt
vm.prank(attacker); cdoEpoch.claimInstantWithdrawRequest();
assertEq(strategy.instantWithdrawsRequests(attacker), 0);
// BUG: stale per-epoch record remains
assertGt(strategy.instantWithdrawsRequestsByEpoch(attacker, strategy.epochNumber()), 0);
// 4. epoch ends, borrower fails to repay -> default, then finalize
vm.warp(cdoEpoch.epochEndDate() + 1);
// manager calls stopEpoch / borrower default path -> defaulted == true
vm.prank(manager);  cdoEpoch.stopEpoch(0, /* interest such that default triggers */0);
vm.prank(owner);    cdoEpoch.finalizeDefault(recovered, recoverySource);
// 5. assertion of inflated basis
uint256 basis = strategy.pendingWithdraws() + strategy.instantWithdrawClaimsByEpoch(strategy.defaultRecoveryEpoch());
// basis includes attacker's already-paid amountA -> defaultRecoveryReserve > strategy balance
// 6. victim claim either pays diluted amount or reverts
vm.prank(victim);
cdoEpoch.claimInstantWithdrawRequest(); // expectRevert / underpaid recovery
```

Key assertion: `strategy.instantWithdrawsRequestsByEpoch(attacker, epoch)` is non-zero after the funded claim, and `defaultRecoveryReserve` exceeds `underlying.balanceOf(strategy)` by `amountA` post-finalization.

Caveat: I could not read `_transferDefaultRecovery`/`_transferFundedClaim` in full (lines ~897+) to confirm whether funded claims draw down `defaultRecoveryReserve` when non-zero; if they do, the stale write may also let the phantom reserve be drained by later funded claims, strengthening the theft primitive. A full PoC should verify the exact payout ordering on the deployed bytecode.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
