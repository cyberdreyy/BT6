### Title
Miner can indefinitely delay its own `block_proposal_timeout` invalidation by spamming reorg-attempt proposals - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
This is an analog of the reported "undercollateralized position avoids liquidation" bug class: an attacker (a single sortition winner acting alone, no majority needed) repeatedly triggers an activity-timestamp update meant for a legitimate purpose, and thereby indefinitely defeats the timeout check that is supposed to mark it invalid/inactive. Here the "lastUpdateTime" analog is the signer's per-tenure activity timestamp (`last_activity_time`), and the "stopTrade" analog is `SortitionState::is_timed_out`, which gates whether a signer falls back away from a stalled/invalid miner.

### Finding Description
`SortitionState::is_timed_out` decides whether the current sortition's miner should be marked invalid due to inactivity, based on `db.get_last_activity_time(sortition)` (falling back to the sortition's burn-block-receive time) compared against `block_proposal_timeout`: [1](#0-0) 

The only way `last_activity_time` gets refreshed for a tenure that has not yet had any block signed is via `SortitionData::check_latest_block_in_tenure`, invoked while evaluating an incoming block proposal. When a newly-proposed block does not extend the chain further than the last known block of the tenure (i.e., a "reorg attempt" that gets rejected), the code still calls `signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())` as long as the last known block either has no `signed_group` timestamp yet, or was signed within `reorg_attempts_activity_timeout`: [2](#0-1) 

Crucially, the `consensus_hash` passed to `update_last_activity_time` is `block.header.consensus_hash` — i.e., the tenure of the *proposed* block, which for a currently-active-but-stalled miner is the attacker's own tenure. This means a miner that has won a sortition but never gets a valid block signed can keep resetting its own tenure's `last_activity_time` merely by repeatedly submitting block proposals that fail the "confirms enough of the tenure" check (`chain_length <= info.block.header.chain_length`), each one being rejected with `Ok(false)`/`RejectReason::InvalidParentBlock`, yet still counted as "activity." Each such rejected proposal is gossiped via the miner→signers/StackerDB channel that any single sortition winner already controls — no majority of signers, no secret key beyond the miner's own, and no node-side change is required.

As long as the attacker resends a new (or even the same non-advancing) proposal at intervals shorter than `reorg_attempts_activity_timeout` (default per config, e.g. tens of seconds), `is_timed_out` never observes an `elapsed > block_proposal_timeout` gap, because `last_activity_time` is perpetually bumped. This is structurally identical to the reported bug: a cheap, repeatable, attacker-controlled action (submitting a proposal / calling `updateTPAndSL`) resets a liveness/safety timer (`last_activity_time` / `lastUpdateTime`) that is supposed to be gated by real progress (an accepted block / actual liquidation eligibility), letting the attacker indefinitely postpone the consequence (miner invalidation / position liquidation).

### Impact Explanation
This breaks the liveness guard described in scope: "a signer wedged into never signing valid blocks, acting on stale reward set/threshold." Concretely, signers are supposed to fall back from an unresponsive/invalid current miner to the previous miner's tenure once `block_proposal_timeout` elapses without real activity (`SortitionsView::check_proposal` in `stacks-signer/src/chainstate/v1.rs:144-163` uses exactly this check to flip `miner_status` to `InvalidatedBeforeFirstBlock`). If a malicious sortition winner can suppress this timeout indefinitely by spamming self-rejecting reorg proposals, the signer network is wedged: it cannot revert to the canonical previous miner, and tenure production stalls while the network waits on a miner that never intends to produce a valid block — a High-severity liveness wedge triggerable by a single (one-slot) miner plus ordinary gossip.

### Likelihood Explanation
High. The action required (repeatedly broadcasting a block proposal for one's own tenure that doesn't extend the last known chain length) is exactly the message flow a normal miner already performs, and requires no cryptographic secret beyond the sortition-winning miner key that the attacker already possesses by having won the sortition. No signer majority, no auth token, no local access is needed — it is purely a gossip/message-timing exploit against the signer's activity bookkeeping, matching the "one-slot miner (plus gossip)" threat model in scope.

### Recommendation
Decouple the inactivity timer from any signal that the miner itself fully controls without making real progress. Specifically:
- Only refresh `last_activity_time` for a tenure when a proposal that could plausibly become a globally/locally accepted block is received (e.g., a proposal that passes the equality/height checks and enters real validation), not merely because it arrived within `reorg_attempts_activity_timeout` of an unsigned/never-signed last block.
- Consider bounding how many times a single miner's repeated non-advancing proposals can refresh the activity timer within one `block_proposal_timeout` window, or basing the "activity" signal on burn-chain-derived time (as is already partially done via `received_time` fallback) rather than on receipt of attacker-supplied messages.

### Proof of Concept
1. Attacker wins a sortition and becomes the current miner (one-slot miner), with `cur_sortition.miner_status == Valid`.
2. Attacker crafts a `BlockProposal` for its own tenure whose `chain_length` does not exceed the last known block in that tenure (or simply never gets it signed/accepted), guaranteeing rejection via `check_latest_block_in_tenure` → `Ok(false)` (`stacks-signer/src/chainstate/mod.rs:395-419`).
3. Because no `signed_group` time exists yet for the tenure (nothing has been globally accepted), the `info.signed_group.is_none_or(...)` branch is true, and `signer_db.update_last_activity_time` is called, resetting the clock used by `SortitionState::is_timed_out`.
4. Attacker repeats step 2 at an interval shorter than `reorg_attempts_activity_timeout` (and, transitively, shorter than `block_proposal_timeout`), indefinitely.
5. `SortitionState::is_timed_out` (`stacks-signer/src/chainstate/v1.rs:55-94`) never observes `elapsed > block_proposal_timeout`, so `SortitionsView::check_proposal` never flips `miner_status` to `InvalidatedBeforeFirstBlock`, and signers never fall back to the previous miner's tenure — the tenure is wedged for as long as the attacker chooses to keep spamming rejected proposals.

    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
