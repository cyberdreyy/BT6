## Title
Vote account withdraw authority can instantly spike `BlockRevenue` commission with no epoch-delay protection, diluting stakers' already-accrued block-reward pool - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
This is the strongest reachable agave analog to the Ocean Protocol `Splitter.addPayee`/`adjustShare` bug class: an account owner unilaterally changes a payout ratio and, because there are already unclaimed/pending funds sitting in a shared pool, the change immediately dilutes the claims of existing beneficiaries who did nothing wrong. In agave, the vote-account withdraw authority plays the role of the "owner," `inflation_rewards_commission_bps`/`block_revenue_commission_bps` play the role of "shares," and `pending_delegator_rewards` plays the role of the Splitter's "unclaimed funds" pool that is later split pro-rata among stakers.

### Finding Description
Agave already has a purpose-built mitigation for exactly this bug class on the **inflation-rewards** side: SIMD-0249 ("Delay Commission Updates"). When `delay_commission_updates` is active, the reward-redemption path in `redeem_delegation_rewards` never uses the vote account's *current* commission; it always looks up the commission from `snapshot_epoch_vote_accounts`, a snapshot taken up to two epochs earlier [1](#0-0) . This means a withdraw authority can call `update_commission`/`update_commission_bps` at will, but the change cannot retroactively dilute stakers' already-accrued-but-unclaimed inflation rewards for the epoch in progress.

That protection is explicitly *not* extended to the `BlockRevenue` commission introduced by SIMD-0123/SIMD-0291. `update_commission_bps` handles both `CommissionKind::InflationRewards` and `CommissionKind::BlockRevenue` through the same code path, and the function comment says plainly: *"No commission update rule, per SIMD-0249 and SIMD-0291"* — i.e. unlike the legacy `update_commission` (which is gated by `is_commission_update_allowed`/epoch-half check when the delay feature is off), `update_commission_bps` imposes **no time restriction at all**, for either commission kind [2](#0-1) . Only a signature from the authorized withdrawer is required [3](#0-2) .

Crucially, on the block-revenue side the actual reward accrual path never re-derives commission from any delayed snapshot the way inflation rewards do. `calculate_block_reward` computes each stake account's share purely as `pending_delegator_rewards * stake / total_active_stake`, i.e. it splits whatever lamports are currently sitting in the vote account's `pending_delegator_rewards` pool pro-rata by stake — it contains no lookup of `block_revenue_commission_bps` and no snapshot/delay logic whatsoever [4](#0-3) . `pending_delegator_rewards` is populated incrementally via the `DepositDelegatorRewards` instruction/`deposit_delegator_rewards` (SIMD-0123), which is reachable by an ordinary, permissionless transaction [5](#0-4) .

Because `block_revenue_commission_bps` can be changed instantly and without any epoch-boundary restriction, and because the block-reward pool that stakers are ultimately paid from is accumulated over time in `pending_delegator_rewards` before being split pro-rata, a withdraw authority can raise the `BlockRevenue` commission to the maximum immediately before commission is taken out of newly-arriving block rewards, capturing a larger cut of funds that were effectively already implicitly owed to existing stakers holding a claim on that shared, not-yet-distributed pool — the exact "owner dilutes existing shareholders via administrative share-adjustment on unclaimed funds" pattern from the Splitter report, but here applied to validator commission economics rather than an explicit payee list.

### Impact Explanation
A validator operator (vote-account withdraw authority) can unilaterally and instantly increase their share of block-revenue rewards without any epoch delay, at the expense of every staker delegated to that vote account, with no staker consent and no cooldown. This is a concrete unauthorized-fund-diversion risk on real, live staking rewards, reachable by any vote-account withdraw authority (not privileged validator/node code) via an ordinary signed transaction.

### Likelihood Explanation
This requires only owning the withdraw authority of a vote account — something every validator operator legitimately has — and calling `UpdateCommissionBps` with `kind = BlockRevenue` at will. No feature-gate bypass or race condition beyond normal transaction submission is needed, since the instruction is intentionally exempted from any update-rate restriction. The main uncertainty is the precise commission-deduction point inside `deposit_delegator_rewards` (I could not fully inspect its body within the available search budget), so I cannot state with certainty exactly how often/at what granularity commission is applied to the pool versus purely at deposit time; this should be verified directly in `programs/vote/src/vote_state/mod.rs`'s `deposit_delegator_rewards` function and its callers before treating this as fully confirmed.

### Recommendation
Extend the SIMD-0249 delayed-commission mechanism (or an equivalent snapshot/epoch-boundary restriction) to `CommissionKind::BlockRevenue` the same way it already applies to `CommissionKind::InflationRewards`, so that a `block_revenue_commission_bps` change cannot affect commission already accrued into `pending_delegator_rewards` for stake that funded the current, in-flight reward pool. At minimum, apply the commission calculation using a commission rate snapshotted prior to the deposit window rather than the value in effect at the instant of `DepositDelegatorRewards`.

### Proof of Concept
1. Validator operator holds the withdraw authority for vote account `V` participating in block-revenue sharing (SIMD-0123 enabled).
2. Stake accounts delegate to `V`; blocks are produced and rewards begin accumulating in `V`'s `pending_delegator_rewards` via `DepositDelegatorRewards` calls.
3. Before the next `DepositDelegatorRewards` call (or before rewards are redeemed at epoch boundary), the withdraw authority signs and submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10_000, kind: BlockRevenue }` — this succeeds immediately per `update_commission_bps` [2](#0-1) , since there is no epoch-half or delay check for this instruction.
4. Subsequent commission deduction on newly deposited block rewards uses the new, inflated commission rate with no waiting period, while `calculate_block_reward` still splits the resulting `pending_delegator_rewards` pro-rata by stake with no compensating snapshot [4](#0-3) , reducing the payout that pre-existing stakers receive relative to what they would have received under the previous commission rate.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
