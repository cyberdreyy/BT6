### Title
Prefunded queue accepts deposits when `prefundedDepositWindow == 0` but `processDepositsToBorrower`/`processPrefundedDeposits` permanently reject them, allowing a dust deposit to brick epoch finalization - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The external report describes a timestamp-validation mismatch where a valid token is rejected as expired, breaking an authenticated flow. The idle-tranches analog is a cutoff-window mismatch in `IdleCDOEpochQueue`: `requestDeposit` only enforces the prefunded subscription cutoff when `prefundedDepositWindow != 0`, while `processDepositsToBorrower` hard-reverts whenever the window is 0. A wallet that passes `isWalletAllowed` can therefore place a deposit that is "valid" under the deposit path's timestamp rules but can never be forwarded to the borrower nor settled by the prefunded stop flow, permanently blocking `stopEpochWithDuration` and freezing all LP funds.

### Finding Description
Two paths disagree on the validity domain of the same timestamp check:

- `requestDeposit` accepts the deposit as long as `prefundedDepositWindow != 0 && block.timestamp + window >= epochEndDate` is false. With `prefundedDepositWindow == 0` the cutoff is skipped entirely, so deposits are accepted for the whole epoch (contracts/IdleCDOEpochQueue.sol:109-118).
- `processDepositsToBorrower` reverts via `_checkNotAllowed(_prefundedWindow == 0 || block.timestamp + _prefundedWindow < epochEndDate)`, so with `window == 0` it can *never* succeed — the queued deposits can never reach the borrower (contracts/IdleCDOEpochQueue.sol:162-164).
- The stop-epoch settlement path then requires `epochPendingDeposits[_epoch] == 0` and `epochPrefundedDeposits[_epoch] != 0`: `processPrefundedDeposits` reverts on `epochPendingDeposits[_epoch] != 0 || _prefunded == 0` (contracts/IdleCDOEpochQueue.sol:261-265) and `prefundedDepositsToProcess` reverts on `epochPendingDeposits[_epoch] != 0` (contracts/IdleCDOEpochQueue.sol:277-282).

So on a prefunded `IdleCDOEpochVariantPrefunded` where `epochQueue` is set but `prefundedDepositWindow` is 0 (a state reachable either by config or because the window was never set after enabling the queue), a KYC'd lender calls `requestDeposit(1)` during the running epoch. The deposit is accepted (its timestamp check passes vacuously), `epochPendingDeposits[nextEpoch] = 1`, and:

- `processDepositsToBorrower` reverts forever (`window == 0` branch).
- `stopEpoch`/`stopEpochWithDuration` revert forever through `prefundedDepositsToProcess`/`processPrefundedDeposits` (`epochPendingDeposits != 0`, and even if the attacker cooperated, `_prefunded == 0` would still revert).
- `deleteRequest` is only callable by the depositor themselves (contracts/IdleCDOEpochQueue.sol:184-199); neither owner nor manager can clear someone else's pending deposit.

The epoch can never be stopped, so `isEpochRunning` stays true, deposits stay paused, withdraw requests stay disabled, and all underlying held by the strategy/borrower is unreachable. Broken invariant: epoch state machine liveness (a valid user action permanently wedges the running epoch).

### Impact Explanation
A single wei of underlying deposited by any KYC-passing lender permanently freezes every LP's funds in the CDO — tranche tokens can't be withdrawn (requests disabled mid-epoch, and even in the next buffer `processWithdrawRequests` and `claimWithdrawRequest` can never be reached because the epoch never ends), and the borrower flow is deadlocked. Impact is permanent freezing of all vault funds at dust cost, matching the "availability of authenticated flows" character of the reference bug.

### Likelihood Explanation
Requires a prefunded deployment where `setEpochQueue` was called but `prefundedDepositWindow` remains 0 — the code explicitly treats `window == 0` as "no cutoff" for deposits yet "impossible" for processing, so the two paths were clearly intended to share one validity domain and don't. Attacker needs only Keyring clearance and 1 unit of underlying; no privileged cooperation. Mitigation: if the invariant tests/deploy scripts always set the window together with the queue this is config-dependent, but nothing on-chain enforces it — `setPrefundedDepositWindow` and queue enablement are independent calls.

### Recommendation
Align the two timestamp-validity checks so a deposit that passes `requestDeposit`'s cutoff can always be prefunded or settled. Either:

- Reject deposits in `requestDeposit` when `prefundedDepositWindow == 0` on an enabled AA prefunded queue, and/or revert `setEpochQueue`/enablement until a non-zero window is configured; or
- Drop the `_prefundedWindow == 0` arm in `processDepositsToBorrower` so a zero window means "no cutoff, prefund any time," matching the deposit-side semantics.

Also consider letting the manager clear stale `epochPendingDeposits` (e.g., a forced `deleteRequest`) as an escape hatch.

### Proof of Concept
Foundry fork PoC sketch (prefunded variant, `epochQueue` set, `prefundedDepositWindow` left at 0):

```solidity
// setup: deposits, manager calls startEpoch() so isEpochRunning == true
// attacker: KYC-passed lender
deal(address(underlying), attacker, 1);
vm.startPrank(attacker);
underlying.approve(address(aaQueue), 1);
aaQueue.requestDeposit(1);           // succeeds — window==0 skips cutoff check
vm.stopPrank();

// manager can never prefund
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
aaQueue.processDepositsToBorrower(); // reverts on prefundedDepositWindow == 0

// epoch can never be stopped
vm.warp(cdo.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdo.stopEpochWithDuration(0, interest, duration, 0); // prefundedDepositsToProcess reverts: epochPendingDeposits != 0

// attacker never calls deleteRequest -> permanent freeze of all LP funds
```

Note: I could not fully read `IdleCDOEpochVariantPrefunded.sol` to confirm the stop flow calls `prefundedDepositsToProcess` unconditionally whenever `epochQueue` is set (rather than skipping when both counters are zero). If the prefunded stop path short-circuits when `epochPrefundedDeposits == 0`, the attack degrades to locked queued funds only; verify that call site before finalizing severity.
