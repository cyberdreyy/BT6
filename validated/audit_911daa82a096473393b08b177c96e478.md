### Title
Stale confirmations from revoked keys let a multisig request execute below the live signer threshold - (File: `multisig/src/lib.rs`)

### Summary
The `multisig` contract (`MultiSigContract`) authorizes a request once `confirmations.len() + 1 >= num_confirmations` [1](#0-0) . Confirmations are recorded per `request_id` as a `HashSet<PublicKey>` and are never invalidated when the confirming key is later removed from the account via `DeleteKey`, except for requests that key itself *created* [2](#0-1) . This breaks the equality the contract is supposed to enforce: `number of confirmations counted == number of currently-live signing keys that approved`. A request can therefore execute with fewer live/authorized signers than `num_confirmations` requires, because one or more of the "confirming" public keys were revoked after confirming but before execution.

### Finding Description
Confirmation bookkeeping is entirely keyed by `request_id`, storing raw `PublicKey`s in a `HashSet` [3](#0-2) . When a key is removed via the `DeleteKey` action, `execute_request` only purges requests whose `signer_pk` (i.e., the *creator*) matches the deleted key, along with that request's confirmations and its `num_requests_pk` entry: [2](#0-1) 

It does **not** scan `self.confirmations` for entries where the deleted key merely *confirmed* (but did not create) a still-pending, different request. `confirm()` itself only checks that the *current* signer hasn't already confirmed - it never re-validates that the *previously recorded* confirming keys in the set are still valid access keys on the account: [4](#0-3) 

`assert_valid_request` also performs no such re-validation - it only checks that the request and its confirmation set still exist: [5](#0-4) 

Concretely, with `num_confirmations = 3` and keys `K1..K4`:
1. `K1` calls `add_request_and_confirm` on a malicious `Transfer` request `R` (1 confirmation: `K1`).
2. `K2` calls `confirm(R)` (2 confirmations: `K1`, `K2`).
3. The group later legitimately revokes `K2` (e.g. because it is compromised) via a separate, properly-confirmed `DeleteKey{public_key: K2}` request. `execute_request`'s `DeleteKey` branch only removes requests *created by* `K2`; `R` was created by `K1`, so `R`'s confirmation set — which still contains `K2` — is left untouched.
4. `K3` calls `confirm(R)`. The count is now `{K1, K2, K3}.len() = 3 >= num_confirmations (3)`, so `R` executes via `execute_request` and the transfer is sent — even though `K2` no longer exists as a valid access key on the account.

Only two currently-live keys (`K1`, `K3`) actually approved `R` at execution time, yet the contract believed three did. This exactly mirrors the reported bug class: an external, unilateral state change (operator undelegating / key being revoked) is not reflected in the contract's internal accounting (delegated total / confirmation count), letting a stale record be exploited to cross a protection boundary (ratio inflation / threshold bypass).

### Impact Explanation
This is a Critical-severity issue per the in-scope impact list: "a multisig request executed below threshold." Any `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, or other privileged action queued by an attacker-controlled or subsequently-revoked key can be pushed to execution with fewer genuinely live/authorized approvals than `num_confirmations` mandates, i.e., NEAR (or other actions) can be moved by a party set that was not actually entitled to authorize it at execution time.

### Likelihood Explanation
Likelihood is realistic in normal multisig operation: key rotation/removal (revoking a departing, compromised, or malicious member) is an expected, routine multisig action, and nothing in `add_request`, `confirm`, or `DeleteKey` prevents or warns about this scenario. A malicious or soon-to-be-removed keyholder only needs to pre-confirm (or create-and-confirm) a request before their own removal is finalized; no special privilege beyond being one of the N legitimate keys is required to plant the stale confirmation.

### Recommendation
When executing `DeleteKey` (or any key-removal action), scan `self.confirmations` for all request IDs where the removed public key appears in the confirmation set (not just where it is the `signer_pk`), and remove that key from those sets (recomputing whether the request still meets threshold, but never auto-executing it as a side effect of removal). Alternatively, revalidate at `confirm()`/execution time that every public key in a request's confirmation set is still a valid access key on `env::current_account_id()` before counting it toward `num_confirmations`.

### Proof of Concept
Using the existing test harness pattern (`multisig/src/lib.rs` test module, e.g. `test_multi_3_of_n`):
1. Initialize `MultiSigContract::new(3)`.
2. As `K1`, call `add_request_and_confirm(R)` for a `Transfer` request (1 confirmation).
3. As `K2`, call `confirm(request_id)` (2 confirmations, request still pending since 2 < 3).
4. Simulate revocation: execute a separate confirmed `DeleteKey{public_key: K2}` request (this only removes requests created by `K2`; `R`'s confirmation set, `{K1, K2}`, is untouched — verify via `get_confirmations(request_id)`).
5. As `K3`, call `confirm(request_id)`. Assert the request executes (`requests.len() == 0`), even though only `K1` and `K3` are still valid keys — 2 live confirmations satisfied a "3 of N" threshold. [6](#0-5)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
