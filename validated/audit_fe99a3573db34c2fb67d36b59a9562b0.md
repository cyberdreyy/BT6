### Title
Unbounded per-attacker flooding of `savedCallbacks` enables oldest-first eviction DoS against a victim's pending capability response - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` stores every validly-signed, non-stale trigger request into a shared, globally-capped `savedCallbacks` map without any allowlist, per-sender quota, or rate limit (the TODO at line 384 confirms this is unimplemented). `pruneCallbacks` evicts strictly by age (oldest-first) when the map exceeds `MaxSavedCallbacks`, so an attacker who can sign requests with their own key can flood the map to evict a victim's older, legitimate pending callback before the DON responds, causing the eventual genuine response to be silently dropped in `handleWebAPITriggerMessage`.

### Finding Description
The reachable path is: HTTP request → `gateway.ProcessRequest` (only calls `msg.Validate()`, which checks structural fields and signature format/extractability, not any allowlist) → `h.HandleLegacyUserMessage` → unconditional insertion into `h.savedCallbacks`. The handler itself explicitly marks allowlisting/rate-limiting as unimplemented (`// TODO: apply allowlist and rate-limiting here`, line 384), meaning any address capable of producing a validly-formatted signature for a reachable `DonId` can register arbitrarily many entries, bounded only by `nodeRateLimiter`, which applies to node→gateway outgoing messages, not to this user-message ingestion path. Once `len(savedCallbacks) > MaxSavedCallbacks`, `pruneCallbacks` sorts purely by `createdAt` and deletes the oldest half — with no concept of "sender" recorded on `savedCallback` at all, so there is no way to apply per-sender fairness even if desired. If the victim's entry was created before the attacker's flood, it is deleted along with other old entries; when the DON's genuine response later arrives for that `MessageId`, `handleWebAPITriggerMessage`'s map lookup misses and the response is dropped without any explicit error being surfaced.

### Impact Explanation
This causes denial-of-service/response-loss for a legitimate subscribed user's capability execution — the victim's request appears to "hang" and eventually times out client-side (via `callback.Wait(ctx)` deadline) instead of receiving the actual DON result, violating the expected isolation property that one user's traffic should not affect another's pending request/response delivery.

### Likelihood Explanation
Preconditions are low: the attacker needs only their own valid signing key and knowledge of a reachable `DonId`/DON member set, both of which are attacker-controlled/discoverable, with no privileged credentials required. `MaxSavedCallbacks` defaults to 20000 (`defaultMaxSavedCallbacks`), which is a large but finite, purely time-ordered structure; flooding to evict a target requires only sending more than the remaining eviction headroom before the DON's real response returns (bounded by `CallbackMaxAgeSec`, default 120s), which is feasible for an automated client with no other node-side pushback on this specific ingestion path.

### Recommendation
Implement the allowlist/rate-limiting noted in the TODO at `handler.go:384` before storing callbacks — e.g., per-sender concurrent-callback quotas recorded alongside `savedCallback` (add a `sender` field), and/or apply `nodeRateLimiter`-style per-sender rate limiting keyed by `msg.Body.Sender` at the start of `HandleLegacyUserMessage`, so a single sender cannot consume more than a fixed share of the global `MaxSavedCallbacks` budget and cannot force eviction of other senders' entries.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with a small `MaxSavedCallbacks` (e.g., 10) via `HandlerConfig`.
2. Insert one "victim" callback via `HandleLegacyUserMessage` with an early `createdAt` (or sleep briefly before subsequent inserts to guarantee ordering).
3. As "attacker" (different private key), call `HandleLegacyUserMessage` repeatedly (more than `MaxSavedCallbacks/2` times) with distinct `MessageId`s to populate `savedCallbacks` past the threshold.
4. Directly invoke `handler.pruneCallbacks()`.
5. Assert (with `handler.mu.Lock()`) that the victim's `MessageId` is no longer present in `h.savedCallbacks`, while several attacker entries remain.
6. Simulate the DON's genuine response for the victim's `MessageId` via `HandleNodeMessage`/`handleWebAPITriggerMessage` and assert the victim's callback never receives a response (i.e., `cb.Wait` times out / no `SendResponse` call occurs), confirming silent response loss.
