### Title
Confirmations from removed members remain valid, allowing request execution below the live-member confirmation threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member()` in `multisig2/src/lib.rs` only purges pending requests that were *originated* by the removed member, and clears `num_requests_pk` for that member. It never scans other members' pending requests to strip out confirmations that the removed member previously cast on them. Because `confirmations` is keyed only by `request_id -> HashSet<String>` of member identity strings, a confirmation recorded by a member before removal remains a permanent, valid entry in that set even after the member is deleted from `self.members`.

### Finding Description
The contract maintains two logically-linked structures that must stay synchronized for the multisig's authorization guarantee to hold:
- `members: UnorderedSet<MultisigMember>` — the current, live set of authorized signers.
- `confirmations: LookupMap<RequestId, HashSet<String>>` — the recorded approvals per request, whose *count* is compared against `num_confirmations` in `confirm()`. [2](#0-1) 

`confirm()` treats `confirmations.len()` as the number of valid, current-member approvals and executes the request once that count reaches `num_confirmations`. This is only sound if every entry in `confirmations` corresponds to a currently-live member.

`delete_member()`, however, only cleans up requests where `r.member == member` (i.e., requests *added* by the member being removed): [3](#0-2) 

It does not iterate over `confirmations` for requests added by *other* members to strip out the removed member's prior approval. So the invariant "every confirmation belongs to a live member" — the multisig analog of "asset_list.len() == expiration.len()" in the reported bug — is silently broken, exactly like `add_assets()` letting `asset_list` and `expiration` drift out of sync in the original finding.

**Concrete sequence:**
1. Multisig has members `{A, B, C}` with `num_confirmations = 3`.
2. Member `B` creates request `R` (`receiver_id` = contract, action = `Transfer` or `AddKey`/`FunctionCall` to attacker).
3. Member `C` calls `confirm(R)` → `confirmations[R] = {C}` (1/3).
4. Separately, members execute a `DeleteMember { member: C }` request (a legitimate governance action, e.g. rotating out a departing signer) — this succeeds since `delete_member` only checks requests *added by* `C`, and `R` was added by `B`, so `confirmations[R]` is untouched and still contains `C`.
5. Now `members = {A, B}`, but `num_confirmations` is still `3` (unless separately updated) — however even if the admins correctly lower `num_confirmations` to `2` to match the new 2-member set, `R`'s confirmation set already contains former-member `C`'s stale approval (1/2).
6. Member `B` calls `confirm(R)` → `confirmations[R].len() == 2 >= num_confirmations (2)` → the request executes, having received only **1 confirmation from a currently live member (B)** plus 1 stale confirmation from a removed, no-longer-trusted member (`C`).

This is a direct violation of the "confirmations counted versus live members" binding: the code counts `confirmations[R].len()` as if it equals "number of live members who approved," but after any `DeleteMember` action, that equality can be false whenever the removed member had previously confirmed a *still-pending* request added by someone else.

### Impact Explanation
This is Critical: a multisig request (e.g., a `Transfer` of contract funds, or an `AddKey`/`AddFullAccessKey` action) can be executed with fewer live-member confirmations than `num_confirmations` requires, because a stale confirmation from a removed member is counted toward the threshold. This directly breaks the multisig's core custody guarantee — "a multisig request executed below threshold" — since the effective quorum among *current* signers is lower than configured, and an attacker/former-member's already-cast vote continues to count toward moving funds or adding keys even after they've lost their signing rights.

### Likelihood Explanation
Any multisig that ever performs a routine `DeleteMember` action while an unrelated request is pending and already has stale confirmations is affected — this is a normal, expected multisig lifecycle event (rotating out a departed team member or compromised key), not an edge case requiring attacker-controlled deployment parameters. Any current member (including the one whose removal triggered the desync, if they act quickly, or a colluding member) can exploit the leftover confirmation by simply calling `confirm()` on the still-pending request once the member count drops such that the stale entry pushes the count over threshold.

### Recommendation
When deleting a member, iterate over **all** pending requests (not just ones added by the removed member) and remove the member's identity string from every `confirmations[request_id]` set, e.g.:
```rust
for (request_id, _) in self.requests.iter() {
    if let Some(mut confs) = self.confirmations.get(&request_id) {
        if confs.remove(&member.to_string()) {
            self.confirmations.insert(&request_id, &confs);
        }
    }
}
```
Alternatively, validate at `confirm()`-time (and at execution) that every entry in the confirmation set still corresponds to a member in `self.members`, discarding/ignoring stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. `MultiSigContract::new(vec![A, B, C], 3)`.
2. As `B`: `add_request(R)` with a `Transfer` action.
3. As `C`: `confirm(R)` → `confirmations[R] = {C}`.
4. As `A`/`B`/`C` (via separate confirmed request): execute `DeleteMember { member: C }` — succeeds because `delete_member` only purges requests where `r.member == C` (none, since `R.member == B`); `confirmations[R]` still contains `"C"`.
5. Execute another confirmed request lowering `num_confirmations` to `2` (or the deployment already used `num_confirmations = 2` with a 3rd member added later — either ordering works).
6. As `B`: `confirm(R)` → `confirmations[R].len() == 2 >= 2` → `execute_request(R)` runs the `Transfer`, even though only `B` (one live member) actually approved it post-removal; `C`'s stale, no-longer-authorized confirmation supplied the second vote.

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
