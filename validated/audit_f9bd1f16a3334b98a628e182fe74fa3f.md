### Title
`getLargestAccounts` RPC serves stale cached slot/account balances beyond bank changes - (File: `rpc/src/rpc_cache.rs`)

### Summary
The `LargestAccountsCache` used by the `getLargestAccounts` JSON-RPC method caches account balances keyed only by the `filter` parameter and serves them to any unprivileged caller for a fixed `duration` window, regardless of how much the underlying bank state has changed in the meantime. This mirrors the `TapOracle.sol` bug class: a hardcoded/parameterized staleness window that is not tied to the actual rate of underlying-data change, so callers can receive outdated (stale) results well past the point the real chain state has moved on.

### Finding Description
`LargestAccountsCache::get_largest_accounts` returns a cached `(slot, accounts)` tuple as long as `elapsed < Duration::from_secs(self.duration)`, with no re-validation against the current bank/slot: [1](#0-0) 

This cache is consumed directly by the unprivileged `getLargestAccounts` RPC handler in `JsonRpcRequestProcessor::get_largest_accounts`. When a cache hit occurs, the handler immediately returns the cached `slot` and `accounts` wrapped in `RpcResponseContext::new(slot)`, without checking whether the currently requested bank/commitment corresponds to a different (newer) slot: [2](#0-1) 

Only on a cache miss does it perform the actual accounts scan via `bank.get_largest_accounts` and refresh the cache with `self.set_cached_largest_accounts(&config.filter, bank.slot(), &accounts)`: [3](#0-2) 

Because the cache key is only `Option<RpcLargestAccountsFilter>` (i.e., `None`, `Circulating`, or `NonCirculating`) — not bank slot, commitment, or fork — a single populated cache entry is served to every subsequent caller with the same filter until `duration` seconds elapse, even if several new slots/forks have been finalized and account balances have materially changed. This is directly analogous to `TapOracle.sol`'s `FETCH_TIME` interval being too coarse for the underlying volatility of the data it serves: the cache TTL is a fixed time constant unrelated to the actual bank/slot cadence, so an unprivileged RPC caller can receive wrong-slot/wrong-balance data for the full duration of the window.

### Impact Explanation
Any unprivileged client calling `getLargestAccounts` can receive account balances tied to an old `slot` that no longer reflects the current bank state (e.g., large transfers/burns after the cache was populated), while the RPC response's `context.slot` still reports the older cached slot as if it were current. This is a "wrong-slot/account data returned" condition from a single low-cost RPC query, consistent with the accepted impact categories (wrong-slot/fork/account data returned) for this analysis.

### Likelihood Explanation
Likelihood is contingent on request timing: because a single call after any refresh repopulates the cache for `duration` seconds, any client issuing `getLargestAccounts` within that window — which is trivially reachable by any RPC user without special privileges — will get the stale data. The only variable is how large `duration` is configured to be in `rpc/src/rpc_service.rs` (the constructor call `LargestAccountsCache::new`); I could not confirm the exact configured value from the available index, so likelihood scales with that (unknown) configured TTL, similar to how the original report's severity depended on the length of `FETCH_TIME`.

### Recommendation
Tie cache invalidation to actual bank/slot changes rather than (or in addition to) a fixed wall-clock duration — e.g., invalidate the cache entry when the requested bank's `slot()` differs from the cached `slot`, or reduce/tune the TTL to match realistic account-balance change frequency, and document the effective staleness bound in the RPC docs so callers can rely on `context.slot` being current for the given commitment level.

### Proof of Concept
1. Call `getLargestAccounts` (or with a `filter`); this populates `LargestAccountsCache` with `(slot, accounts)` at time T via `set_cached_largest_accounts` (`rpc.rs:1116`).
2. Within the cache's configured `duration`, submit transactions that materially change large account balances (e.g., transfer significant lamports into/out of a top account), advancing the bank several slots.
3. Call `getLargestAccounts` again with the same filter before `duration` elapses: `get_cached_largest_accounts` (`rpc_cache.rs:30-42`) returns the old `(slot, accounts)` pair unchanged, and the handler returns it directly (`rpc.rs:1074-1078`) — the caller receives balances/slot that no longer match the current bank state, despite `RpcResponseContext` implying the data is as of `slot`. use {
    solana_rpc_client_api::{config::RpcLargestAccountsFilter, response::RpcAccountBalance},
    std::{
        collections::HashMap,
        time::{Duration, SystemTime},
    },
};

#[derive(Debug, Clone)]
pub struct LargestAccountsCache {
    duration: u64,
    cache: HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>,
}

#[derive(Debug, Clone)]
struct LargestAccountsCacheValue {
    accounts: Vec<RpcAccountBalance>,
    slot: u64,
    cached_time: SystemTime,
}

impl LargestAccountsCache {
    pub(crate) fn new(duration: u64) -> Self {
        Self {
            duration,
            cache: HashMap::new(),
        }
    }

    pub(crate) fn get_largest_accounts(
        &self,
        filter: &Option<RpcLargestAccountsFilter>,
    ) -> Option<(u64, Vec<RpcAccountBalance>)> {
        self.cache.get(filter).and_then(|value| {
            if let Ok(elapsed) = value.cached_time.elapsed()
                && elapsed < Duration::from_secs(self.duration)
            {
                return Some((value.slot, value.accounts.clone()));
            }
            None
        })
    }

    pub(crate) fn set_largest_accounts(
        &mut self,
        filter: &Option<RpcLargestAccountsFilter>,
        slot: u64,
        accounts: &[RpcAccountBalance],
    ) {
        self.cache.insert(
            filter.clone(),
            LargestAccountsCacheValue {
                accounts: accounts.to_owned(),
                slot,
                cached_time: SystemTime::now(),
            },
        );
    }
}

    async fn get_largest_accounts(
        &self,
        config: Option<RpcLargestAccountsConfig>,
    ) -> RpcCustomResult<RpcResponse<Vec<RpcAccountBalance>>> {
        let config = config.unwrap_or_default();
        let bank = self.bank(config.commitment);

        if let Some((slot, accounts)) = self.get_cached_largest_accounts(&config.filter) {
            Ok(RpcResponse {
                context: RpcResponseContext::new(slot),
                value: accounts,
            })
        } else {
            let (addresses, address_filter) = if let Some(filter) = config.clone().filter {
                let non_circulating_supply = self
                    .calculate_non_circulating_supply(&bank)
                    .await
                    .map_err(|e| RpcCustomError::ScanError {
                        message: e.to_string(),
                    })?;
                let addresses = non_circulating_supply.accounts.into_iter().collect();
                let address_filter = match filter {
                    RpcLargestAccountsFilter::Circulating => AccountAddressFilter::Exclude,
                    RpcLargestAccountsFilter::NonCirculating => AccountAddressFilter::Include,
                };
                (addresses, address_filter)
            } else {
                (HashSet::new(), AccountAddressFilter::Exclude)
            };
            let accounts = self
                .runtime
                .spawn_blocking({
                    let bank = Arc::clone(&bank);
                    move || {
                        bank.get_largest_accounts(NUM_LARGEST_ACCOUNTS, &addresses, address_filter)
                    }
                })
                .await
                .expect("Failed to spawn blocking task")
                .map_err(|e| RpcCustomError::ScanError {
                    message: e.to_string(),
                })?
                .into_iter()
                .map(|(address, lamports)| RpcAccountBalance {
                    address: address.to_string(),
                    lamports,
                })
                .collect::<Vec<RpcAccountBalance>>();

            self.set_cached_largest_accounts(&config.filter, bank.slot(), &accounts);
            Ok(new_response(&bank, accounts))
        }
    }
