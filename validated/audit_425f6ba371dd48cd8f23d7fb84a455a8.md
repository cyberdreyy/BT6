### Title
Rebasing underlying breaks claim bookkeeping in `IdleCreditVault`: funded withdraw/instant claims overdraw the real balance and revert - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` pays withdrawal claims from fixed internal counters (`withdrawsRequests`, `instantWithdrawsRequests`, `postDefaultRequests`, `defaultRecoveryReserve`) that are funded once via `collectWithdrawFunds` / `collectInstantWithdrawFunds` and never re-synced to `underlyingToken.balanceOf(address(this))`. If the vault's underlying is a rebasing token whose balance can shrink, already-funded claims transfer more tokens than the contract holds. Early claimants drain the balance, later `claimWithdrawRequest` / `claimInstantWithdrawRequest` calls revert, and once `defaultRecoveryReserve != 0` the `balance - reserve < _amount` guard in `_transferFundedClaim` reverts for every funded claim until the shortfall is topped up.

### Finding Description
The receipt lifecycle is:

1. `requestWithdraw` / `requestInstantWithdraw` mint a strategy-token receipt to the user and record `withdrawsRequestsByEpoch` / `instantWithdrawsRequestsByEpoch` plus `pendingWithdraws` / `pendingInstantWithdraws` (IdleCreditVault.sol L243-295, L356-375).
2. At `stopEpoch`/`startEpoch`, `IdleCDOEpochVariant` calls `collectWithdrawFunds` / `collectInstantWithdrawFunds`, which pull exactly `pendingBasis` (or the loss-adjusted amount) of underlying into the vault (L411-430, L398-403). From then on, solvency of claims rests on the assumption that `balanceOf(vault)` never decreases below the tracked claim basis.
3. `claimWithdrawRequest` and `claimInstantWithdrawRequest` burn the receipt and transfer the full recorded amount via `_transferFundedClaim` → `underlyingToken.safeTransfer(_user, _amount)` (L301-314, L380-393, L897-907). No check verifies the real balance covers the aggregate of all open claims.

With a negatively-rebasing underlying (e.g. an elastic-supply pool currency), a rebase between funding and claiming shrinks `balanceOf(vault)` while `withdrawsRequests`, `instantWithdrawsRequests` and `defaultRecoveryReserve` stay fixed. Because payouts are first-come-first-served, the first claimants receive the full recorded amount; once the residual balance drops below the next claim, `safeTransfer` reverts. Worse, after `finalizeDefaultRecovery` sets `defaultRecoveryReserve > 0`, `_transferFundedClaim` enforces `balance - reserve >= _amount` (L899-905), so even pre-default funded receipts revert whenever the rebased balance falls below the reserve — a hard revert on every funded claim. `_skimDonatedAssets` on the CDO side only protects against positive balance drift; nothing handles a downward drift of the strategy balance.

### Impact Explanation
A single negative rebase of magnitude `r` freezes up to `r` worth of aggregate claim basis: the last claimants whose cumulative receipts exceed the rebased balance can no longer claim, so funded principal+interest is stuck in the vault. In the post-default configuration the freeze is total for funded receipts (`balance < reserve` revert) and recovery claimants race each other for the diminished `defaultRecoveryReserve`, so the last claimant's payout is permanently reduced by the full rebase amount. Impact = temporary freezing of user funds (up to permanent shortfall for the last recovery claimant); quantified loss equals the rebase delta on the vault's held balance, bounded by `pendingWithdraws + pendingInstantWithdraws-funded + defaultRecoveryReserve`.

### Likelihood Explanation
Requires the vault to be deployed with an underlying whose `balanceOf` can decrease without transfers (rebasing / elastic-supply token). Idle credit vaults are designed around stablecoin pool currencies, but nothing in `initialize` or elsewhere validates that the underlying is non-rebasing, and the bookkeeping is unconditionally balance-vs-ledger inconsistent. No privileged or attacker action is needed beyond ordinary claims — the broken invariant (recorded claims ≤ held balance) is triggered by the token's own rebase. Requires a Foundry fork PoC with a rebasing token deployment; likelihood is conditional on token selection rather than attacker economics.

### Recommendation
Either explicitly document/validate at `initialize` that `token` must not be rebasing (and reject rebasing underlyings at deployment), or make claims self-healing: cap each payout to `min(recordedAmount, availableBalance - defaultRecoveryReserve)` and/or re-sync claim bases to the actual balance at claim/finalization time, so a negative rebase socializes the shortfall instead of reverting on the last claimants.

```solidity
// 1. Deploy IdleCreditVault + IdleCDOEpochVariant with a rebasing ERC20 `rebaseToken`.

//    Vault balance == 2000, aggregate claim basis == 2000.

// 6. A calls IdleCDO.claimWithdrawRequest(A) -> succeeds, receives 1000.
// 7. B calls IdleCDO.claimWithdrawRequest(B) -> _transferFundedClaim ->
//    safeTransfer(B, 1000) on a balance of 800 -> revert.
//    B's funded claim is frozen until someone tops up 200.
// 8. Variant: same flow but finalizeDefault() first sets
//    defaultRecoveryReserve > 0; after the rebase,
//    `balance < reserve` in _transferFundedClaim makes every funded
//    claim revert deterministically.
```
