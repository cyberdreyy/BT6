## Analysis

Confirmed root cause in `multisig2/src/lib.rs`: the `delete_member` function only removes requests (and their confirmations) that were **created** (`add_request`) by the deleted member — it filters `self.requests` where `r.member == member`. It does **not** scan `self.confirmations` for requests created by *other* members that the deleted member had already confirmed. `confirm()` at line 304 treats the raw confirmation-set size (`confirmations.len() as u32 + 1 >= self.num_confirmations`) as equivalent to "K of currently-live N members," but a stale confirmation from a since-removed member remains counted toward that threshold on any request they confirmed before being removed.

This directly matches the allowed analog class: "confirmations counted versus live members."

### Title
Stale confirmations from removed multisig members still count toward the K-of-N threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in the multisig2 contract only purges requests and confirmations for requests that the removed member originally *created* (`r.member == member`), not confirmations the removed member cast on requests created by other members. `confirm()` counts entries in the `confirmations` `HashSet` for a request without re-validating that each entry is still a current `self.members` entry. As a result, a member who is removed from the multisig after confirming a pending request continues to contribute a "vote" toward `num_confirmations`, allowing a request to execute with fewer live, authorized confirmations than the configured threshold.

### Finding Description
`confirm()` (`multisig2/src/lib.rs:292-315`) does:
```
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
}
```
It relies purely on the *size* of the stored `confirmations: HashSet<String>` for the request, with no cross-check against the live `self.members` set at the moment of execution.

`delete_member()` (`multisig2/src/lib.rs:355-379`) only cleans up:
```
let request_ids: Vec<u32> = self.requests.iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```
This removes requests *authored* by the deleted member, but any request authored by a different member that the now-deleted member had previously `confirm`ed retains that confirmation entry in `self.confirmations`, untouched.

Binding broken: the contract's documented guarantee is "K of N live members must confirm," i.e. `confirmations ⊆ current_members` and `|confirmations ∩ current_members| >= K`. After a `DeleteMember` executes, this invariant is not re-established for outstanding requests — `confirmations` can contain entries no longer present in `self.members`, yet `confirm()` still counts them.

### Impact Explanation
This breaks the threshold-authorization guarantee itself (Critical: "a multisig request executed below threshold"). A request can execute with fewer authorizing signatures from currently-authorized members than `num_confirmations` requires, because a stale confirmation from a removed member is counted as if it were still valid. Since `MultiSigRequestAction::Transfer` and other privileged actions (`AddKey`, `DeployContract`, `AddMember`/`DeleteMember` itself) are gated purely by this counter, this can lead to unauthorized movement of NEAR held by the multisig account, or unauthorized privileged actions being executed with an effectively lower threshold than configured.

### Likelihood Explanation
Requires no privileged access beyond being (or having been) a legitimate multisig member — no foundation, redeploy, or external victim key is needed:
1. A member (attacker or compromised member) confirms a pending request R (created by someone else), pushing confirmations toward, but not yet meeting, threshold.
2. Later, that member is removed via a legitimate `DeleteMember` request (e.g., as part of routine membership rotation, or if the member is later considered compromised and removed).
3. R's confirmation set still contains the removed member's entry because `delete_member` never scans confirmations of requests authored by *other* members.
4. Any remaining members confirming R now only need to reach the residual count to trip `confirmations.len() + 1 >= num_confirmations`, effectively lowering the number of *currently live* confirmers required below the intended `num_confirmations`.

This is a straightforward "confirm before removal, remove member, subsequent confirmations complete the now-understaffed threshold" sequence, requiring only ordinary multisig operations already exposed by the contract's own API — no privilege escalation or external interference is needed.

### Recommendation
When removing a member in `delete_member`, iterate over **all** outstanding requests' `confirmations` sets (not just requests authored by that member) and strip the removed member's entry from each. Additionally, `confirm()` should validate, at execution time, that all entries counted in `confirmations` are still members of `self.members` (e.g., recompute `confirmations.iter().filter(|m| self.members.contains(m)).count()`), so removed members can never contribute to reaching the threshold, regardless of when they confirmed relative to their removal.

### Proof of Concept
Given `num_confirmations = 3`, members `{A, B, C, D}`:
1. `A` calls `add_request` creating request `R` (receiver `multisig` itself, e.g. a `Transfer`). Confirmations for `R` = `{}`.
2. `B` calls `confirm(R)` → confirmations = `{B}` (1 < 3, not yet executed).
3. `A` (as a member, via a separate already-confirmed `DeleteMember{B}` request reaching threshold through other members `C`,`D`,`A`) removes `B` from the multisig. `delete_member` only removes requests where `r.member == B` (i.e., requests *authored* by B); `R` was authored by `A`, so `R`'s confirmations set `{B}` is left untouched even though `B` is no longer in `self.members`.
4. `C` calls `confirm(R)` → confirmations = `{B, C}`, size 2, `2+1 >= 3` → threshold met → `R` executes.

Result: `R` executed with only `A` (author, not counted as confirmer) and `C` as genuinely current, live confirming members plus a stale confirmation from removed member `B` — i.e., only 1 live confirmation contributed toward the "2 additional confirmations" requirement, executing a request that should have required 3 confirmations from currently active members.
