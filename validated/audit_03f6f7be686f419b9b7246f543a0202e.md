### Title
Stale rejection weight is never retracted when a signer later accepts, letting `total_weight_rejected` and `total_weight_approved` both include the same signer's weight for one block - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run_loop` tallies `BlockAccepted`/`BlockResponse::Rejected` messages for a given `signer_signature_hash` into two independent counters (`total_weight_approved`, `total_weight_rejected`), each gated by a *different* de-duplication map (`gathered_signatures` for accepts, `responded_signers` for rejects). A signer that rejects a block first and later accepts the very same block (identical `signer_signature_hash`) gets counted in **both** totals, because the accept-path guard only checks `gathered_signatures`, which the reject path never touches. The reverse order (accept-then-reject) is correctly guarded via `responded_signers`, but reject-then-accept is not. Since `NakamotoSigningCoordinator::wait_for_signatures` (in `signer_coordinator.rs`) evaluates the rejection threshold *before* the approval threshold on every poll, a block that ultimately gathers enough weight to be approved can still be treated as globally rejected if enough signers transiently rejected before flipping to acceptance.

### Finding Description
`stacks-signer/src/v0/signer.rs`'s `should_reevaluate_reject_reason` (lines 2706-2739) intentionally allows several reject reasons to be revisited on a re-proposal of the *same* block content — `UnknownParent`, `NotFoundError`, `NoSortitionView`, `ConnectivityIssues`, `ConsensusHashMismatch`, `NoSignerConsensus`, `TestingDirective`, `InvalidTenureExtend`, `Unknown`. These are exactly the kind of reasons a miner can trigger transiently and controllably (e.g. proposing a block before its parent/tenure info has propagated to a given signer's node, which yields `UnknownParent`/`NotFoundError`/`NoSortitionView`). `handle_block_proposal` (lines 1592-1604, `should_reevaluate_block` at 1481-1572) routes such a re-proposal through a fresh validation, which can end in `mark_locally_accepted`/`send_block_response(Accepted)` even though this same signer already broadcast a `Rejected` response for the identical `signer_signature_hash` earlier.

On the node side, `stackerdb_listener.rs` keeps a single `BlockStatus` keyed by `signer_signature_hash` for the whole life of that proposal:
- Accept path (lines 443-465): only increments `total_weight_approved` `if !block.gathered_signatures.contains_key(&slot_id)`.
- Reject path (lines 486-518): only increments `total_weight_rejected` `if block.responded_signers.insert(slot_id)`.

Because these are two separate maps, a signer who rejects first (weight goes into `total_weight_rejected`, and `responded_signers` now contains its slot) and later accepts (weight goes into `total_weight_approved`, because `gathered_signatures` was never touched by the earlier rejection) ends up counted in *both* running totals for that block, permanently. There is no code path that ever subtracts a signer's earlier-recorded rejection weight from `total_weight_rejected` once it flips to acceptance.

`NakamotoSigningCoordinator::wait_for_signatures` (`stacks-node/src/nakamoto_node/signer_coordinator.rs`, ~lines 505-545) polls this same `BlockStatus` and checks the rejection condition **first**:
```
if block_status.total_weight_rejected.saturating_add(blocking_minority) > self.total_weight { … return Err(SignersRejected …) }
else if block_status.total_weight_approved >= self.weight_threshold { … return Ok(...) }
```
Because stale rejection weight from flipped signers is never purged, the aggregated `total_weight_rejected` no longer reflects the set of signers *currently* rejecting the block. This breaks the "aggregated-weight vs verified-accepts" equality the coordinator relies on: it can declare a block rejected using weight contributed by signers who have already switched to accepting that exact block.

### Impact Explanation
This falls under the "acting on a stale reward set/threshold" class of High-impact findings: the coordinator's aggregated rejection weight can remain permanently inflated by signers who no longer hold that position, causing the coordinator to reject a block (`SignersRejected`) that a sufficient, currently-live set of signers would otherwise approve. Repeated triggering (a miner that reliably induces the reevaluable reject reasons, e.g. by proposing slightly ahead of chain-tip propagation and then re-proposing) can be used to force spurious rejections/timeouts on legitimate blocks, a liveness degradation on the mining side that a single miner slot can trigger without needing any signer's key or a signer majority — it only requires ordinary, permitted proposal timing.

### Likelihood Explanation
The reevaluable reject reasons (`UnknownParent`, `NotFoundError`, `NoSortitionView`, `ConnectivityIssues`) are common, naturally-occurring conditions tied to network/DB propagation timing that a miner can influence by choosing when to broadcast (e.g. proposing before a signer's node has ingested the parent block, then re-proposing shortly after). No majority-signer collusion or key compromise is required; it relies purely on existing signer/proposal mechanics that this repo already exercises in its own tests (e.g. `stacks-node/src/tests/signer/v0/missing_burn_block_proposal.rs`'s `signer_reevaluates_proposal_with_missing_burn_view` explicitly demonstrates the reject → reconsider path).

### Recommendation
Track a signer's vote for a given `signer_signature_hash` as a single, mutually-exclusive state (e.g. one map keyed by `slot_id` storing "Accepted" or "Rejected") and recompute `total_weight_approved`/`total_weight_rejected` from that authoritative state, removing/adjusting the previous contribution whenever a signer's recorded vote changes, instead of using two independently-gated additive counters.

### Proof of Concept
1. Miner proposes block `B` (fixed `signer_signature_hash = H`) at a moment when signer `S`'s node has not yet ingested `B`'s parent, causing `check_block_has_valid_parent`/tenure lookups to fail with `UnknownParent`/`NotFoundError`. `S` broadcasts `BlockResponse::Rejected(H, …)`.
2. Node's `StackerDBListener` records this in `blocks[H]`: `responded_signers.insert(S)` and `total_weight_rejected += weight(S)` (`stackerdb_listener.rs` lines 515-518).
3. Miner (or normal StackerDB replication) re-delivers the identical proposal `B` shortly after `S`'s node has caught up. `should_reevaluate_reject_reason` returns `true` for `UnknownParent`/`NotFoundError` (`signer.rs` lines 2709-2711), so `S` re-validates `B`, this time succeeds, and eventually calls `send_block_response(Accepted(H, …))`.
4. Node's `StackerDBListener` processes the accept: `gathered_signatures` does not yet contain `S`'s slot, so `total_weight_approved += weight(S)` (`stackerdb_listener.rs` lines 443-446) — while `total_weight_rejected` from step 2 is never decremented.
5. `blocks[H]` now shows `S`'s weight counted in both `total_weight_rejected` and `total_weight_approved`. If enough signers go through the same reject→accept flip (individually, without collusion) so that the stale `total_weight_rejected` crosses the blocking-minority threshold, `NakamotoSigningCoordinator::wait_for_signatures` (`signer_coordinator.rs`, rejected-check evaluated first) returns `Err(SignersRejected)` even though the same signers have already (or will shortly) supply enough weight to satisfy `total_weight_approved >= weight_threshold`.     /// Determine if an already tracked block should be re-evaluated based on a new block proposal for it.
    /// Returns true if the block should be re-evaluated, false if it should be ignored.
    fn should_reevaluate_block(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &BlockInfo,
        block_proposal: &BlockProposal,
    ) -> bool {
        let signer_signature_hash = block_info.block.header.signer_signature_hash();
        if block_info.globally_approved_and_responded() {
            info!("{self}: received a block proposal for a globally accepted block to which we have already responded. Ignoring.";
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_info.block.block_id(),
                "block_height" => block_info.block.header.chain_length,
                "burn_height" => block_proposal.burn_height,
                "consensus_hash" => %block_info.block.header.consensus_hash,
                "timestamp" => block_info.block.header.timestamp,
                "signed_group" => block_info.signed_group,
                "signed_self" => block_info.signed_self,
                "valid" => ?block_info.valid
            );
            return false;
        }
        if !should_reevaluate_reject_reason(block_info) {
            if block_info.state == BlockState::PreCommitted {
                // We validated this block but haven't signed it. Signing requires the
                // pre-commit threshold and the conflict checks in `handle_block_pre_commit`.
                // Re-broadcast our pre-commit and re-run that evaluation instead of
                // responding with a signature directly, so a re-proposed block can't
                // bypass those checks.
                info!(
                    "{self}: received a block proposal for a block we have pre-committed to but not signed. Re-evaluating the pre-commit.";
                    "signer_signature_hash" => %signer_signature_hash,
                    "block_id" => %block_info.block.block_id(),
                    "block_height" => block_info.block.header.chain_length,
                    "burn_height" => block_proposal.burn_height,
                    "consensus_hash" => %block_info.block.header.consensus_hash
                );
                self.send_block_pre_commit(signer_signature_hash.clone());
                let address = self.stacks_address.clone();
                self.handle_block_pre_commit(
                    stacks_client,
                    sortition_state,
                    &address,
                    &signer_signature_hash,
                );
                return false;
            }
            if let Some(block_response) = self.determine_response(block_info) {
                self.send_block_response(&block_info.block, block_response);
                return false;
            } else {
                let is_pending = self
                    .signer_db
                    .has_pending_block_validation(&signer_signature_hash)
                    .unwrap_or_else(|e| {
                        warn!("{self}: Failed to load pending block validations: {e:?}");
                        false
                    });
                if is_pending {
                    debug!(
                        "{self}: received a block proposal for a block for which we is already pending validation. Do nothing.";
                        "signer_signature_hash" => %block_info.block.header.signer_signature_hash(),
                        "block_id" => %block_info.block.block_id()
                    );
                    return false;
                } else {
                    info!(
                        "{self}: received a block proposal for this block before, but we do not have a pending validation for it.";
                        "reject_reason" => ?block_info.reject_reason,
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %block_info.block.block_id(),
                        "block_height" => block_info.block.header.chain_length,
                        "burn_height" => block_proposal.burn_height,
                        "consensus_hash" => %block_info.block.header.consensus_hash
                    );
                }
            }
        } else {
            info!(
                "{self}: received a block proposal for this block before, but our rejection reason allows us to reconsider";
                "reject_reason" => ?block_info.reject_reason,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_proposal.block.block_id(),
                "block_height" => block_proposal.block.header.chain_length,
                "burn_height" => block_proposal.burn_height,
                "consensus_hash" => %block_proposal.block.header.consensus_hash
            );
        }
        true
    }

/// Determine if a block should be re-evaluated based on its rejection reason˝
fn should_reevaluate_reject_reason(block_info: &BlockInfo) -> bool {
    if let Some(reject_reason) = &block_info.reject_reason {
        match reject_reason {
            RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
            | RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
            | RejectReason::NoSortitionView
            | RejectReason::ConnectivityIssues(_)
            | RejectReason::TestingDirective
            | RejectReason::InvalidTenureExtend
            | RejectReason::ConsensusHashMismatch { .. }
            | RejectReason::NoSignerConsensus
            | RejectReason::NotRejected
            | RejectReason::Unknown(_) => true,
            RejectReason::ValidationFailed(_)
            | RejectReason::RejectedInPriorRound
            | RejectReason::SortitionViewMismatch
            | RejectReason::ReorgNotAllowed
            | RejectReason::InvalidBitvec
            | RejectReason::PubkeyHashMismatch
            | RejectReason::InvalidMiner
            | RejectReason::NotLatestSortitionWinner
            | RejectReason::InvalidParentBlock
            | RejectReason::DuplicateBlockFound
            | RejectReason::IrrecoverablePubkeyHash
            | RejectReason::ProblematicTransactions
            | RejectReason::ProposalTooOld => {
                // No need to re-validate these types of rejections.
                false
            }
        }
    } else {
        false
    }
}
