### Title
Repointing `idleCDO` via `setWhitelistedCDO` orphans all user receipt state and permanently freezes tranche-holder funds - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` stores all per-user credit state — normal withdraw receipts (`withdrawsRequestsByEpoch`), APR0 positions (`apr0Users`), instant-withdraw receipts (`instantWithdrawsRequestsByEpoch`), and the strategy tokens that represent active deposits — against a single `idleCDO` pointer. The owner can repoint `idleCDO` at any time via `setWhitelistedCDO`, but every state-mutating path is gated by `_onlyIdleCDO()` (`msg.sender == idleCDO`). Once the pointer moves, the old CDO can no longer call `deposit`, `requestWithdraw`, `claimWithdrawRequest`, `claimInstantWithdrawRequest`, or default-recovery claims, and the new CDO has no link to the receipts or strategy tokens minted to the old one. This is the direct analog of the Nouns `MetadataRenderer` swap: user-facing attributes/receipts live in a replaceable contract, and replacing the pointer discards them with no migration path.

### Finding Description
In `IdleCreditVault.sol`:

- `idleCDO` is the sole authorized caller for all user fund flows (`_onlyIdleCDO()`, and `_transfer` at line ~939 requires `msg.sender == idleCDO`).
- `setWhitelistedCDO` (lines ~954-957) lets the owner overwrite `idleCDO` with a single call:

```solidity
function setWhitelistedCDO(address _cdo) external onlyOwner {
  require(_cdo != address(0), "IS_0");
  idleCDO = _cdo;
}
```

- All receipt state is stored in the strategy keyed by user/epoch: `withdrawsRequestsByEpoch`, `apr0Users`, `instantWithdrawsRequestsByEpoch`, `postDefaultRequests`, `lossRecoveryPriceByEpoch`, plus strategy tokens minted to `idleCDO` (receipts that are non-transferable, enforced by the `_transfer` override).
- There is no guard requiring `pendingWithdraws == 0`, `pendingInstantWithdraws == 0`, `apr0TotalPrincipal == 0`, or `balanceOf(oldCdo) == 0` before the pointer is swapped, and no function exists to migrate or re-attribute receipts to a new CDO. The code itself acknowledges this class of problem in `_ensureDefaultRecoveryInitialized` (lines ~919-935): "Legacy pending receipts must first be fully funded because their per-epoch ownership cannot be reconstructed after an implementation upgrade" — the same reasoning applies to a `idleCDO` swap, yet no equivalent protection exists.

### Impact Explanation
After the swap, every tranche holder of the old CDO permanently loses the ability to:

- claim pending withdraw receipts (`claimWithdrawRequest` reverts via `_onlyIdleCDO` when routed through the old CDO; calling the strategy directly also reverts since the user is not `idleCDO`),
- claim instant-withdraw receipts and APR0 principal/interest (`apr0Users`, `settledPrincipal`, `settledInterest` are unreachable),
- redeem active positions, since the strategy tokens representing them are held by the old CDO and cannot be moved (`_transfer` reverts unless `msg.sender == idleCDO`).

The underlying remains locked in the strategy/borrower with no recovery path — permanent freezing of all user funds routed through the vault, up to the full vault NAV. This violates the "one receipt one payout" and solvency invariants: liabilities remain recorded, but no authorized path can settle them.

### Likelihood Explanation
The trigger is an honest owner call (`setWhitelistedCDO`), which is a plausible operational action — e.g., migrating a pool to a new CDO variant (the codebase ships multiple variants: `IdleCDOEpochVariant`, `IdleCDOCreditVault`, `IdleCDOUsualVariant`) or fixing a misconfigured CDO address. Unlike the acknowledged implementation-upgrade case that `_ensureDefaultRecoveryInitialized` guards, nothing here prevents the swap while funds/receipts are live, and there is no `DefaultDistributor`-style unwind path that would let users exit first. An unprivileged user does not initiate the change but bears the full loss, consistent with the trust model.

### Recommendation
Guard `setWhitelistedCDO` so the pointer can only be changed when the vault is fully unwound:

```solidity
require(balanceOf(idleCDO) == 0, 'ACTIVE_NAV');
require(pendingWithdraws == 0 && pendingInstantWithdraws == 0, 'PENDING');
require(apr0TotalPrincipal == 0 && postDefaultRequestsTotal == 0, 'PENDING');
```

Alternatively, provide an explicit migration that re-attributes receipt ownership and transfers the strategy-token balances to the new CDO atomically, rather than relying on an unrecoverable post-hoc state.

### Proof of Concept
A Foundry fork PoC (pattern mirrors `test/foundry/IdleCreditVault.t.sol`):

```solidity
// setup: existing IdleCDOEpochVariant `cdoEpoch` wired to `strategy` (IdleCreditVault)

// 1. user deposits during buffer and gets tranche tokens
uint256 tranches = _depositWithUser(user, 100e6);

// 2. epoch runs, user requests withdraw -> receipt recorded in strategy
vm.prank(manager);
cdoEpoch.startEpoch();
_requestWithdrawWithUser(user, tranches);
_stopCurrentEpoch(); // receipt now claimable next epoch

// 3. owner migrates to a new CDO
address newCdo = address(new IdleCDOEpochVariant());
vm.prank(strategy.owner());
strategy.setWhitelistedCDO(newCdo);

// 4. user can no longer claim: old CDO path reverts, direct call reverts
vm.prank(user);
vm.expectRevert(NotAllowed.selector); // msg.sender != idleCDO
strategy.claimWithdrawRequest();

vm.prank(user);
vm.expectRevert(); // old CDO is no longer strategy.idleCDO
cdoEpoch.claimWithdrawRequest();

// strategy tokens / receipts for `user` are stranded forever:
// balanceOf(oldCdo) > 0 and _transfer requires msg.sender == idleCDO (new CDO)
assertGt(strategy.balanceOf(address(cdoEpoch)), 0); // frozen NAV
```

Caveat: I could not fully verify whether `setWhitelistedCDO` is used in deployment scripts as a post-init fixer only (`tasks/` may set it before any deposits), which would reduce practical likelihood, but the code provides no enforcement, so the freeze invariant is not protected.
