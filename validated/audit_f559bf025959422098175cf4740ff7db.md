### Title
ERC4626 liquidity check bypass in `onStopEpoch` — solvency check uses `convertToAssets` while `withdraw` reverts on illiquidity, freezing epoch settlement - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
`ProgrammableBorrower.onStopEpoch` mirrors the SSRF-redirect bug class: like a request validator that checks the first URL but not the redirect target, it validates that the withdrawal shortfall is *economically covered* by the vault position via `_currentVaultAssets()` (`convertToAssets`), but then unconditionally calls `vault.withdraw(shortfall, ...)` without checking `maxWithdraw`/`maxRedeem` — the property that actually determines whether the second hop succeeds. On an illiquid-but-solvent ERC4626 vault (e.g. a lending vault whose cash has been borrowed out), the coverage check passes, `withdraw` reverts, the `catch` rethrows `StopEpochVaultLiquidityUnavailable`, and the whole `stopEpoch` flow reverts. Any unprivileged user of the external vault can drain its liquidity and force this state, blocking epoch settlement and freezing all lender funds.

### Finding Description
In `onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:231-268), when on-hand balance is insufficient:

```solidity
uint256 shortfall = _amountRequired - onHand;
if (shortfall > _currentVaultAssets()) return true;   // solvency check (convertToAssets)
try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
} catch {
    revert StopEpochVaultLiquidityUnavailable();      // liquidity failure → hard revert
}
```

The two-hop problem:
- **Hop 1 (checked):** `shortfall <= _currentVaultAssets()` verifies share *valuation*, not withdrawability. This is the analogue of resolving the DNS name of the request URL.
- **Hop 2 (unchecked):** `vault.withdraw` is where the real asset movement happens — the "redirect target". ERC4626 vaults routinely have `maxWithdraw < convertToAssets(shares)` (utilization caps, locked funds, borrowed liquidity, withdrawal queues). Nothing in `onStopEpoch`, `_borrow` (line 450-457, same pattern), `availableToBorrow`, or `emergencyExitVault` consults `maxWithdraw`.

When `withdraw` reverts, the `catch` block reverts the entire transaction instead of degrading to the default path (`return true` → `transferFrom` fails → IdleCDO handles it as a default with loss socialization). Solvent-but-illiquid is treated as a hard failure rather than the settlement outcome the accounting already supports (a vault loss is priced into `totalInterestDueNow` via `_vaultNetInterest`).

The same latent desync exists in `availableToBorrow`/`_borrow`: borrowable liquidity is computed from `convertToAssets`, so a borrow that would require an illiquid vault withdrawal reverts at `vault.withdraw` (uncaught) — confirming the contract systematically confuses valuation with liquidity.

### Impact Explanation
Any user of the configured ERC4626 vault — an explicitly in-scope unprivileged attacker ("a user of the programmable borrower's ERC4626 vault") — can make the vault illiquid (withdraw all idle assets, borrow all lent liquidity, or trigger the vault's withdrawal gate). From that moment:

- Every `stopEpoch` call where `onHand < _amountRequired` reverts with `StopEpochVaultLiquidityUnavailable`, so the epoch cannot close, withdraw requests cannot be honored, and lender capital is frozen.
- `emergencyExitVault` (vault.redeem) also reverts under the same illiquidity, so the honest owner/manager cannot unwind the position.
- `borrow` reverts uncaught at `vault.withdraw`.

This is temporary freezing of the entire pool NAV that persists exactly as long as the attacker keeps the vault drained (renewable indefinitely while the position is parked), and becomes effectively permanent loss/insolvency if vault liquidity only returns at impaired terms — precisely the "blind" impact of the reference bug: the attacker cannot extract the funds, but can force requests to an internal target (the vault's withdrawal path) that the protocol cannot observe or refuse ahead of time.

### Likelihood Explanation
- Attacker preconditions: none beyond being a vault user — the vault is an external permissionless ERC4626; no KYC, role, or tranche position is required to drain its liquidity.
- Trigger conditions: any epoch with a shortfall (`_amountRequired > onHand`), which is the normal case since `onStartEpoch` deposits the full idle balance into the vault (line 216). During the buffer/close flow (`_isRequestingAllFunds`), nearly all funds come from the vault.
- Existing guards do not stop it: `nonReentrant` is irrelevant, `_checkOnlyIdleCDO` only gates the caller, the `shortfall > _currentVaultAssets()` check intentionally *proceeds* exactly in the illiquid-solvent case, and the try/catch deliberately reverts rather than degrading. `onDefault`/`rescueTokens` cannot recover a position locked inside an illiquid vault.

### Recommendation
Check the redirect target, not just the origin — validate liquidity before attempting the withdrawal:

```solidity
uint256 maxOut = vault.maxWithdraw(address(this));
if (shortfall > _currentVaultAssets()) return true;              // insolvency → default path
if (shortfall > maxOut) { /* treat as settlement shortfall */ }
```

Either (a) return `true` and let `transferFrom` fail into the default path (socializing the shortfall as a vault loss, consistent with `_vaultNetInterest`), or (b) withdraw only `min(shortfall, maxOut)` and surface the residual so IdleCDO can record a loss instead of reverting. Apply the same `maxWithdraw` bound inside `availableToBorrow()` so `borrow` does not report phantom borrowable liquidity, and prefer a bounded `redeem`/`withdraw` amount in `emergencyExitVault`.

### Proof of Concept
Foundry fork/local PoC sketch (uses the repo's existing `MockInvariantVault` harness pattern from `test/foundry/ProgrammableBorrowerEpochInvariant.t.sol`, which already exposes `setWithdrawLimit`/`maxWithdraw` and a revert-on-illiquidity `withdraw` at lines 64-99):

```solidity
// Setup: pool running an epoch; ProgrammableBorrower holds vault shares
// covering the stopEpoch pull; on-hand cash < _amountRequired.

// 1. Attacker (any vault user) drains vault liquidity, e.g. on the mock:
//    vault.setWithdrawLimit(0);            // real vault: borrow/withdraw all cash
//    solvency is unchanged: convertToAssets(poolShares) still >= shortfall

// 2. Keeper/owner calls IdleCDOEpochVariant.stopEpoch(...)
//    -> reads totalInterestDueNow()          (unchanged; shares still fully valued)
//    -> ProgrammableBorrower.onStopEpoch(_amountRequired, false)
//       shortfall = _amountRequired - onHand;                 // > 0
//       assert(shortfall <= _currentVaultAssets());           // passes — solvent
//       vault.withdraw(shortfall, ...) reverts "insufficient-liquidity"
//       catch { revert StopEpochVaultLiquidityUnavailable(); } // whole tx reverts

// 3. Repeat stopEpoch — always reverts while vault is illiquid.
//    Lender withdraw requests / epoch close are blocked; TVL frozen.
//    Attacker repeats the drain each time liquidity returns (temporary→indefinite freeze).
```

Key assertions: `vault.convertToAssets(shares) >= shortfall` (check passes), `vault.maxWithdraw(borrower) == 0` (actual hop fails), `stopEpoch` reverts rather than entering the default/loss path.

*Uncertainty note:* I verified the revert propagation in `ProgrammableBorrower` directly; I could not fully trace `IdleCDOEpochVariant.stopEpoch`'s surrounding retry/gating logic in the available iterations, so the exact freeze duration depends on that flow — but `onStopEpoch` reverting blocks the settlement path regardless.
