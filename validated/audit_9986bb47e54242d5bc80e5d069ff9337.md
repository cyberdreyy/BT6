### Title
`PipelineRunsController.Create` allows any authenticated External Initiator to trigger runs on arbitrary job IDs, not just its own bound job - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` validates only the EI's own secret and never associates the authenticated EI's identity with a specific job ID; it simply elevates the request to a synthetic user with `UserRoleRun`. `PipelineRunsController.Create` then dispatches `RunJobV2(ctx, jobID, nil)` for any numeric job ID without checking that the job belongs to, or is bound to, the caller's identity. As a result, any valid EI credential (or any Run-role token/session) can trigger a run on any job in the node by supplying its integer ID.

### Finding Description
`AuthenticateExternalInitiator` (core/web/auth/auth.go) authenticates the EI's `X-Chainlink-EA-AccessKey`/`Secret` against its own `bridges.ExternalInitiator` record via `bridges.AuthenticateExternalInitiator`, then does: [1](#0-0) 
which sets the session user to `&clsessions.User{Role: clsessions.UserRoleRun}` — a generic Run-role identity with no linkage back to which job(s) that specific EI is authorized to trigger.

The route `POST /v2/jobs/:ID/runs` accepts this identity (or a token/session user) and only requires the Run role: [2](#0-1) 

`PipelineRunsController.Create` then does: [3](#0-2) 
The only check performed is `isUser` (whether *any* `SessionUserKey` is set) — which is true for EI-authenticated, token-authenticated, and session-authenticated requests alike, since `AuthenticateExternalInitiator` sets that same key. No code compares `GetAuthenticatedExternalInitiator(c)` against the job's owning EI, and no such binding is queried at all. `RunJobV2` is invoked directly with attacker-supplied `jobID` with zero ownership/authorization scoping.

Note: the legacy `webhook` job type (the type historically bound to a specific `ExternalInitiator` via join records) has been fully removed from job creation, and UUID-style webhook job IDs are explicitly rejected with `job.ErrJobTypeRemoved`: [4](#0-3) 
This means the codebase no longer has a live concept of "a job bound to EI B" for any newly created job — so the exact EI-A-vs-EI-B-webhook scenario as posed cannot be reproduced through job creation today. However, the broken authorization is broader and still exploitable: the integer-ID path performs **no** job-to-caller binding check for **any** job type, so a valid EI credential holder (or a restricted Run-role token) can trigger a run for any job ID in the system, not just jobs associated with it.

### Impact Explanation
This is an authorization/access-control bypass: an external-initiator credential (a low-privilege, single-purpose credential meant to trigger a specific integration's job) can be used to trigger job runs for jobs it has no relationship to, since `RunJobV2` is called without any ownership check. This maps to Chainlink's "unauthorized job run" bounty impact class — an attacker with narrow EI credentials can cause execution of arbitrary node job pipelines by ID.

### Likelihood Explanation
Requires only valid credentials for one `ExternalInitiator` record (a low-privilege secret, not admin/session credentials), and knowledge/guessing of a target job's small integer ID (job IDs are sequential integers, easily enumerable). No additional preconditions are needed; the flaw is directly reachable via `POST /v2/jobs/:ID/runs`.

### Recommendation
In `PipelineRunsController.Create`, when the caller is authenticated via `GetAuthenticatedExternalInitiator`, verify that the target job is actually associated with/owned by that EI before invoking `RunJobV2` (or reject EI-triggered runs entirely now that webhook jobs are removed, since there is no legitimate EI-to-job binding left to authorize). Do not rely on `GetAuthenticatedUser` presence alone to gate `RunJobV2`, since `AuthenticateExternalInitiator` populates the same session key as regular users.

### Proof of Concept
1. Create two `bridges.ExternalInitiator` records, EI-A and EI-B, and two jobs, Job-A and Job-B (non-webhook types, e.g. `directrequest`/OCR), with integer IDs.
2. Authenticate as EI-A using its `X-Chainlink-EA-AccessKey`/`Secret`.
3. Issue `POST /v2/jobs/<Job-B's-ID>/runs` using EI-A's credentials.
4. Assert: current code returns `200 OK` with a pipeline run resource for Job-B (unauthorized trigger), because `prc.Create` never checks that Job-B belongs to EI-A.
5. Expected secure behavior: the request should be rejected with `401/403` since EI-A has no relationship to Job-B.
