### Title
`capitulate_miner_view` treats a bare 30%+1 blocking-minority weight as sufficient to switch the local miner viewpoint whenever the candidate tenure already has ≥1 globally-accepted block, instead of requiring the documented 70% supermajority - ([File: stacks-signer/src/v0/signer_state.rs])

### Summary
`LocalStateMachine::capitulate_miner_view` decides which miner/tenure the signer should build on and sign for next. The intended rule, per `docs/signer-flows.md` ("adopt a threshold view..."), is that a competing miner view should only be adopted once it reaches global agreement (70% weight). Instead, for any candidate tenure that already has at least one globally-accepted block, the code accepts the candidate once it merely clears the *blocking-minority* threshold (`reached_disagreement`, >30%), never re-checking `reached_agreement` (70%) for it.

### Finding Description
In `capitulate_miner_view`: [1](#0-0) 

```
let entry = miners.entry(miner_state).or_insert(0);
*entry += weight;
if !eval.reached_disagreement(*entry) {
    // We don't even see a blocking minority threshold. Ignore.
    continue;
}

let nmb_blocks = signerdb
    .get_globally_accepted_block_count_in_tenure(tenure_id)
    .unwrap_or(0);
if nmb_blocks == 0 && !eval.reached_agreement(*entry) {
    continue;
}
```

`reached_disagreement` returns true once weight exceeds ~30% of total signing weight [2](#0-1) , while `reached_agreement` requires the full 70% supermajority [3](#0-2) .

The gating logic is: a candidate miner-state entry only needs to clear 70% agreement if its tenure has **zero** globally-accepted blocks recorded locally (`nmb_blocks == 0`). If the tenure already has one or more globally-accepted blocks, the `if nmb_blocks == 0 && !reached_agreement` branch is false, so the candidate is admitted into `potential_matches` on the strength of the earlier `reached_disagreement` check alone — i.e., on just over 30% weight, not 70%.

`potential_matches` is then sorted by `block_height` and the entry with the *highest* parent-tenure block height is chosen unconditionally as the new miner view: [4](#0-3) 

The candidate that wins is the one that has been *validated* least (it required only >30% support) rather than the one the network has actually converged on (70%+). This is analogous to the Yearn `lockedProfit` bug in the report: an unvested/partial quantity (a bare blocking-minority opinion) is treated by the accounting logic as though it were a fully-realized, agreed-upon value, because a superficially-related but insufficient condition (nmb_blocks > 0, i.e., "this tenure already produced *some* confirmed block at some point") is used as a proxy for "the network has already vetted this specific miner-state." Having *any* globally-accepted block in the tenure says nothing about whether the *current* claimed `parent_tenure_last_block`/`parent_tenure_last_block_height` in this specific `StateMachineUpdate` is the one the network has actually converged on.

`capitulate_miner_view` is invoked from `capitulate_viewpoint`, which is called on every event-loop pass (rate-limited by `capitulate_miner_view_timeout`), and directly mutates the signer's `LocalStateMachine` (its notion of "current miner" and `parent_tenure_last_block`) when the returned view differs from the local one: [5](#0-4) 

This miner viewpoint feeds directly into `StateMachineUpdate` broadcasts (the consensus-visible "equality key for global agreement" per the docs) and into block-proposal acceptance/sortition checks used to decide whether to sign a given block.

### Impact Explanation
Because only ~30%+1 signing weight (well below a majority, and reachable by a small coalition or by stale/laggard signers whose updates simply haven't caught up) is enough to flip a signer's `current_miner`/`parent_tenure_last_block` view whenever the competing tenure has any historical globally-accepted block, different honest signers can be driven to different local miner viewpoints depending on message arrival order and HashMap iteration order over `eval.address_updates`. This breaks the "aggregated-weight vs. verified-accepts" equality the state machine relies on for the network to converge on one canonical `current_miner`/parent-tenure view, and can:
- cause the signer set to fracture into two miner viewpoints instead of converging on the 70%-agreed one, stalling block signing (a liveness wedge), and
- cause a signer to act on a stale/attacker-influenced view of the parent tenure with materially weaker validation than the documented 70% bar, which feeds into tenure-change/parent-confirmation checks used before signing.

This matches the "High" impact category: a signer acting on a stale/under-verified threshold for the reward-set/miner-view rather than the verified 70% agreement.

### Likelihood Explanation
This does not require a majority of signers or any signer's private key — a signer (or a small coalition/minority) simply needs to broadcast `StateMachineUpdate` messages claiming an `ActiveMiner` state for a tenure that already happens to have at least one globally-accepted block (which is a common, easily satisfied condition once any tenure has produced even one confirmed block), and hold ~30%+1 of the signing weight advocating that view. This can occur organically during a normal viewpoint disagreement/reorg-adjacent period, not only via a deliberate attack, making it a reasonably likely trigger in practice, especially during tenure-change races.

### Recommendation
Require `eval.reached_agreement(*entry)` (the full 70% threshold) unconditionally before admitting a candidate miner-state to `potential_matches`, regardless of `nmb_blocks`. If a lower bar for tenures with existing globally-accepted blocks is intentional, it should be re-justified and bounded so that it can never let a sub-70% (specifically, ≤70%) minority override the state the network has already converged on for the *current* claimed tip, not merely "some past block in this tenure."

### Proof of Concept
1. Configure a signer set where address weights sum to `total_weight`.
2. Have a coalition (or naturally lagging subset) controlling slightly more than 30% of `total_weight` broadcast `StateMachineUpdate` messages with `ActiveMiner { tenure_id: T, parent_tenure_last_block_height: H, ... }`, where tenure `T` already has ≥1 globally-accepted block recorded in `signerdb` (satisfied by any tenure that has produced a single confirmed block).
3. Call `capitulate_miner_view` on a signer whose current view differs from `T`/`H`. Because `nmb_blocks > 0` for `T`, the `!reached_agreement` branch is skipped, and the >30% entry is added to `potential_matches` without ever needing 70% agreement (as unit-tested behavior is only asserted for the ≥70%/`reached_agreement` and disagreement-only "returns None" cases; the `nmb_blocks > 0` bypass path is not covered by an assertion that requires 70%): [6](#0-5) .
4. If this candidate has the highest `block_height` among `potential_matches`, `capitulate_miner_view` returns it and the signer flips its `LocalStateMachine` to it, even though only ~30% of the network's weight supports that specific tip claim.
