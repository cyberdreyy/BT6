### Title
Dust queued-withdrawal permanently bricks `processWithdrawRequests` via `Is0()` revert - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The Keycloak report maps to the "improper validation of a specified quantity" class: an attacker supplies an edge-case quantity that the system never validates, and downstream processing fatally fails. In `IdleCDOEpochQueue`, `requestWithdraw` accepts any nonzero dust amount of tranche tokens. When `processWithdrawRequests` later computes the epoch price as `_underlyingsRequested * ONE_TRANCHE / _pending`, a request that the credit vault settles to `0` underlyings forces a `revert Is0()` every time it is called — permanently blocking the whole epoch's withdrawal processing and freezing all other users' queued tranche tokens.

### Finding Description
`requestWithdraw` in `IdleCDOEpochQueue.sol:131-143` pulls `amount` tranche tokens from the caller with no minimum check:

```solidity
IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
userWithdrawalsEpochs[msg.sender][nextEpoch] += amount;
epochPendingWithdrawals[nextEpoch] += amount;
```

In `processWithdrawRequests` (`IdleCDOEpochQueue.sol:315-328`):

```solidity
uint256 _underlyingsRequested = _cdo.requestWithdraw(_pending, tranche);
uint256 _epochPrice = _underlyingsRequested * ONE_TRANCHE / _pending;
if (_epochPrice == 0) {
  revert Is0();
}
```

`IdleCreditVault.requestWithdraw` (`IdleCreditVault.sol:243-295`) early-returns when `_amount == 0` (line 246) — it does **not** revert, and it still burns `_principal` on the CDO side before that check is reached. When the aggregated `_pending` in tranche terms converts (through `requestWithdraw`'s price/interest math) to a zero underlying receipt, the CDO call returns `0`, making `_epochPrice == 0` and the queue reverts `Is0()`.

Because the revert happens before any state is written, `epochPendingWithdrawals[_epoch]` stays nonzero, `epochWithdrawPrice[_epoch]` stays `0`, and `pendingClaims` never flips. Every subsequent `processWithdrawRequests` call hits the same revert deterministically — the same class of guaranteed-failure processing as the Keycloak malformed-response crash.

Key points:
- `deleteWithdrawRequest` (`IdleCDOEpochQueue.sol:203-218`) only lets `msg.sender` remove their own request, so the manager cannot evict the attacker's dust entry.
- `processWithdrawalClaims` is gated on `epochPendingClaims[_epoch]`, which is only set by the now-reverting function — no recovery path exists in-contract.
- The tranche tokens of honest queued users sit locked in the queue forever; they cannot claim (`epochWithdrawPrice == 0` sentinel means "not processed" and blocks `claimWithdrawRequest`) and cannot delete someone else's request.

### Impact Explanation
Permanent freezing of all tranche tokens queued for that epoch. A victim who queued 100,000 tranche tokens (≈ underlying value at `epochWithdrawPrice`) alongside the attacker's dust permanently loses access to the full amount; the tokens are held by the queue with no admin escape hatch since the queue has no sweep/rescue function for `tranche`. Loss = total `epochPendingWithdrawals[epoch]` minus the attacker's dust (the attacker's cost is only the dust tranche amount).

### Likelihood Explanation
- Attacker needs only a KYC-passing wallet (allowed persona) and a dust amount of tranche tokens — obtainable via a minimal deposit or secondary transfer.
- No privileged role, oracle manipulation, or timing precision required; the dust request can be placed at any point during the running epoch.
- The one uncertainty I could not fully verify: the exact `_pending` value for which `_cdo.requestWithdraw` returns `0` underlyings. The vault's `_amount == 0` early return exists (`IdleCreditVault.sol:246`), and `_amount` derives from a multiplication by `tranchePrice` / interest math, so a sufficiently small `_pending` (or a sole dust request, which the attacker controls by being first/only requester) yields `_underlyingsRequested == 0`. The `Is0` guard was clearly added because the authors anticipated this zero case, but they made it a hard revert rather than handling it.

### Recommendation
- In `requestWithdraw`, enforce a minimum request size (e.g., require the implied underlying value ≥ 1 unit, or a configured `minWithdrawAmount`).
- In `processWithdrawRequests`, handle the zero-value outcome like the already-added `isEpochWithdrawZero` terminal path (set the flag, zero the pending amount, let users clear claims) instead of reverting `Is0()` — the same pattern used for zero-priced claims at `IdleCDOEpochQueue.sol:355-360` should apply to processing.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";

contract DustWithdrawBrickTest is Test {
    // fork mainnet, deploy cdoEpoch + AA queue per test/foundry/IdleCDOEpochQueue.t.sol setup

    function testDustWithdrawBricked() external {
        // epoch running; victim (KYC'd) deposits 1000e6 USDC, receives tranches,
        // queues a normal withdraw of all tranches.
        uint256 victimTranches = _depositWithUser(victim, 1000e6);
        _requestWithdrawWithUser(victim, victimTranches); // queue.requestWithdraw(victimTranches)

        // attacker (KYC'd) deposits dust and queues 1 wei of tranche
        // (or is the sole requester so _pending stays at dust size)
        uint256 dust = _depositWithUser(attacker, 1e6);
        _requestWithdrawWithUser(attacker, 1); // 1 wei tranche

        // epoch ends -> buffer period
        _stopCurrentEpoch();

        // manager attempts to process; the CDO returns 0 underlyings for the
        // dust-scaled request -> _epochPrice == 0 -> revert Is0()
        vm.prank(manager);
        vm.expectRevert(Is0.selector);
        queue.processWithdrawRequests();

        // retrying always reverts; victim's tranches are stuck in the queue
        vm.prank(manager);
        vm.expectRevert(Is0.selector);
        queue.processWithdrawRequests();

        // victim cannot self-rescue: delete is blocked only for their own entry,
        // and claims are blocked because epochWithdrawPrice[epoch] == 0
        assertEq(tranche.balanceOf(address(queue)), victimTranches + 1);
        assertEq(queue.epochPendingWithdrawals(epoch), victimTranches + 1);
    }
}
```

Caveat: if the tranche-to-underlying conversion returns nonzero for the sole dust request in a given deployment's price regime, the attacker instead waits for the smallest victim batch or uses an epoch where `virtualPrice` rounding zeroes the receipt. The revert path is unconditional once `_underlyingsRequested == 0` reaches `processWithdrawRequests`.
