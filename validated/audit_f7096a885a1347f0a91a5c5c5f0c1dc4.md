### Title
Own-signed block silently drops out of tenure-tip/duplicate-block checks once >30% peer rejections flip it to GloballyRejected - (File: stacks-signer/src/signerdb.rs)

### Summary
A signer that has already signed block A (state `LocallyAccepted`, `signed_self` set, its acceptance broadcast) can have that same local `BlockInfo` transition to `GloballyRejected` purely because a blocking minority (>30% weight) of other signers rejected it, even though the signer's own signature is out on the network and can still be aggregated toward the 70% threshold if any of those rejecting signers change their mind. Once in `GloballyRejected` state, `SignerDb::get_last_signed_block` — which filters on `state IN (GloballyAccepted, LocallyAccepted)` — stops returning block A, even though `signed_self` is still set on it. This silently disables two consensus-critical guards that depend on it: the same/parent-tenure "confirms latest block" check (`check_latest_block_in_tenure`) and the tenure-change `DuplicateBlockFound` guard.

### Finding Description
`get_last_signed_block` is documented and designed to return "every signed block", keyed off `signed_self`/`signed_group`, but it actually queries `state IN (?GloballyAccepted, ?LocallyAccepted)` [1](#0-0) . Contrast this with `get_signed_conflicts`, which is deliberately state-agnostic and keys purely off `signed_self IS NOT NULL OR signed_group IS NOT NULL` so that "rejection does not clear a conflict" [5](#0-4) . `get_last_signed_block` was clearly meant to have the same invariant (the docs explicitly say "a rejection is a revocable opinion, while a signature is a bearer instrument"), but its `state` filter breaks that invariant for exactly one of the two lookups.

The state machine allows the flip: `check_state` permits `LocallyAccepted -> GloballyRejected` (only `GloballyAccepted -> GloballyRejected` is blocked) [3](#0-2) . `store_and_process_block_rejection` reaches `mark_globally_rejected()` purely from peer-rejection weight crossing the blocking-minority threshold, with only a `has_reached_consensus()` guard at the top (true only for `GloballyAccepted`/`GloballyRejected`) — it never checks `block_info.signed_self` [4](#0-3) . So: signer S validates and signs block A (broadcasts `BlockAccepted`, state becomes `LocallyAccepted`), then before A reaches 70% weight, >30% of other signers (a blocking minority, not a majority) broadcast `BlockRejected` for A (this happens naturally under network partitions/timeouts, not just malice). S's local `BlockInfo` for A flips to `GloballyRejected`.

From that point:
- `get_tenure_last_block_info` (chainstate/mod.rs:330-364) returns `None` for A's tenure, even though S still has a live signature over A.
- `check_latest_block_in_tenure` (chainstate/mod.rs:376-478), used at proposal arrival, at validate-ok, and at signing time (per docs section 7 [6](#0-5) ), therefore no longer sees A as the tenure tip, and treats a new conflicting proposal at the same/lower height as if there were no signed tip to confirm.
- `validate_tenure_change_payload`'s `DuplicateBlockFound` check (v1/v2), which exists specifically to stop a signer re-signing a second block in a tenure it already signed, calls the same `get_last_signed_block` and also returns `None`, so the duplicate check silently no-ops [2](#0-1) .

The remaining safety net is the own-tenure conflict guard in `handle_block_pre_commit` (section 5), which uses `get_signed_conflicts` — that one is state-agnostic and still sees A. But that guard only fires at the pre-commit-threshold recheck, and only "for now" (it can be satisfied once the conflicting signature goes stale, per `conflict_still_blocks`/freshness cutoff) [7](#0-6) . It does not restore the tenure-tip check or the `DuplicateBlockFound` check at proposal-arrival time, both of which have already silently passed because they specifically rely on the broken `get_last_signed_block`.

### Impact Explanation
This breaks the "signed vs. tracked correctly" equality the tenure-tip/duplicate-block guards are supposed to enforce: a signer that has genuinely signed a block in a tenure can be made, by ordinary rejection gossip (not requiring any signer's private key or a majority), to act as if it never signed anything in that tenure. That opens the door for it to sign a second, conflicting tenure-change or same-tenure block that `DuplicateBlockFound`/`check_latest_block_in_tenure` exist specifically to block — i.e., a signer signing a conflicting block after having already signed a different block in that tenure, matching the Critical "signer signing a ... conflicting block" impact category. Because A's own signature is still a live bearer instrument that can reach 70% independently later, both A and its conflicting successor could end up independently reachable toward global acceptance.

### Likelihood Explanation
No majority is required — only a blocking minority (>30% weight) rejecting A, which the design explicitly anticipates as a normal, non-Byzantine occurrence (temporary validation disagreement, network timing, node-side transient failures), combined with a miner (one slot) re-proposing a conflicting block for the same tenure/height, which is squarely within the "one-slot miner plus gossip" trigger model. The rejecting signers do not need to collude with the miner or hold any of S's keys; they just need to have genuinely (or falsely) rejected A for their own reasons.

### Recommendation
Change `SignerDb::get_last_signed_block` to match `get_signed_conflicts`'s semantics: select on `signed_self IS NOT NULL OR signed_group IS NOT NULL` (optionally still preferring `GloballyAccepted`/`LocallyAccepted` ordering) rather than filtering on `state`, so a block the signer actually signed is never lost from tenure-tip and duplicate-block checks merely because local bookkeeping later marked it `GloballyRejected` due to peer rejections. Alternatively/additionally, prevent `mark_globally_rejected` from being applied to a `BlockInfo` that already has `signed_self` set (mirroring the existing protection against `GloballyAccepted -> GloballyRejected`), so the state machine cannot flip a self-signed block into a fully "rejected" bucket at all.

### Proof of Concept
1. Miner proposes block A in tenure T at height h. Signer S validates A successfully, signs it, and broadcasts `BlockAccepted` for A (`store_and_process_block_signature` runs before threshold is met, so `mark_locally_accepted(false)` sets `signed_self`, state = `LocallyAccepted`) [8](#0-7) .
2. Before A reaches 70% weight, other signers holding >30% weight broadcast `BlockRejected` for A (this can be due to independent legitimate rejection reasons, e.g. `ConnectivityIssues`/timing). S processes these via `handle_block_rejection` → `store_and_process_block_rejection`, which computes `total_reject_weight` ≥ blocking-minority threshold and calls `block_info.mark_globally_rejected()`, succeeding because `LocallyAccepted -> GloballyRejected` is allowed by `check_state` [9](#0-8) [3](#0-2) . A's `BlockInfo` still has `signed_self = Some(t)`.
3. The miner now proposes block B, a competing tenure-change (or same-tenure) block at height h/h+1 that conflicts with A. S's `handle_block_proposal` → `check_block_against_state` → `check_proposal` calls `validate_tenure_change_payload`/`check_latest_block_in_tenure`, both of which call `signer_db.get_last_signed_block(T)` [10](#0-9) . Because A is now `GloballyRejected`, the query returns `None`, so `DuplicateBlockFound` is not raised and the tenure-tip check treats T as having no prior signed tip.
4. S proceeds to validate and, absent any other live guard (the pre-commit-time `get_signed_conflicts` recheck may itself resolve in favor of signing once A's rejection or staleness conditions are satisfied per `conflict_still_blocks`), can sign B — producing two independently-signable, conflicting blocks in tenure T, one of which S itself endorsed twice against the guard mechanisms meant to prevent exactly this.

Note: I could not fully trace every intermediate call path from `check_block_against_state`/`should_reevaluate_block` down to `validate_tenure_change_payload` in this pass (only the `check_proposal`/chainstate anchors were confirmed via docs and direct code reads), so the precise sequencing of guard bypass at proposal time vs. at the pre-commit recheck should be validated with a live/unit test (e.g. extending `stacks-signer/src/signerdb.rs`'s existing `reject_then_accept`/`accept_then_reject` tests, which currently only cover `block_signatures`/`block_rejection_signer_addrs`, not `BlockState` transitions) before remediation.

    pub fn get_tenure_last_block_info(
        consensus_hash: &ConsensusHash,
        signer_db: &SignerDb,
        tenure_last_block_proposal_timeout: Duration,
    ) -> Result<Option<BlockInfo>, ClientError> {
        // Get the last signed block in the tenure
        let last_signed_block = signer_db
            .get_last_signed_block(consensus_hash)
            .map_err(|e| ClientError::InvalidResponse(e.to_string()))?;

        let Some(block_info) = last_signed_block else {
            return Ok(None);
        };

        // `approved_time` may hold the pre-commit time; use the actual signature time.
        let Some(signed_over_time) = block_info.signed_self.max(block_info.signed_group) else {
            return Ok(None);
        };

        if signed_over_time.saturating_add(tenure_last_block_proposal_timeout.as_secs())
            > get_epoch_time_secs()
        {
            // The last accepted block is not timed out, return it
            Ok(Some(block_info))
        } else {
            // The last accepted block is timed out
            info!(
                "Last accepted block has timed out";
                "signer_signature_hash" => %block_info.block.header.signer_signature_hash(),
                "signed_over_time" => signed_over_time,
                "state" => %block_info.state,
            );
            Ok(None)
        }
    }
