### Title
Unfunded instant-withdraw receipts are paid at par through the aggregate claim in `claimInstantWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Mon（ad） fix shares a node pointer only between requests with the same parent (same ownership root). The analog here is the instant-withdraw claim path: `claimInstantWithdrawRequest` treats the aggregate counter `instantWithdrawsRequests[_user]` as a single fungible "receipt pointer," paying it out in full even though only a prefix of that aggregate was ever funded by `collectInstantWithdrawFunds`. Requests made in different epochs do not share the same funding "parent," yet the claim lumps them together — exactly the broken ownership-sharing invariant the upstream commit fixes.

### Finding Description
- `requestInstantWithdraw` burns CDO strategy tokens, mints a receipt to the user, and increases `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]`, and `pendingInstantWithdraws` (IdleCreditVault.sol:356-375). It performs **no** check that the user has no prior unclaimed instant receipt, and no check on the request epoch.
- Funding is tracked only as an aggregate: `collectInstantWithdrawFunds(_amount)` decrements `pendingInstantWithdraws` and pulls tokens into the strategy (IdleCreditVault.sol:398-403). Individual receipts are never marked funded; funding state exists only implicitly via `pendingInstantWithdraws` vs `instantWithdrawClaimsByEpoch`.
- `claimInstantWithdrawRequest` (outside default handling) reads `instantWithdrawsRequests[_user]` — the entire aggregate across all epochs — burns it, zeroes it, and calls `_transferFundedClaim(_user, amount)` (IdleCreditVault.sol:380-393). `_transferFundedClaim` only guards `defaultRecoveryReserve` (line 897-907); there is no check that the claimed amount was actually funded (i.e., no comparison against the funded remainder `instantWithdrawClaimsByEpoch[epoch] - pendingInstantWithdraws` or per-epoch accounting).

Attack sequence (running epoch, instant mode enabled):
1. Attacker requests instant withdraw of `X` in epoch N. `pendingInstantWithdraws = X`.
2. Honest manager calls `stopEpoch`; CDO calls `collectInstantWithdrawFunds(X)` → `pendingInstantWithdraws = 0`, strategy holds `X` earmarked for the receipt.
3. Before claiming, attacker calls `requestInstantWithdraw(Y)` (epoch N+1). Now `instantWithdrawsRequests[attacker] = X + Y`, `pendingInstantWithdraws = Y` (unfunded).
4. Attacker calls `claimInstantWithdrawRequest()` → receives `X + Y` underlying, burning only receipt tokens. `Y` was never funded; it is paid out of strategy underlyings belonging to other claimants/reserve.

The code itself acknowledges this funded/unfunded mix (`pendingInstantWithdraws is only the unfunded remainder`, lines 850-851) but only resolves it inside the default-finalization path (`_claimDefaultedInstantWithdrawRequest`); the normal path pays the aggregate unconditionally.

### Impact Explanation
Direct theft of `Y` underlying from the credit vault: the unfunded portion is paid out of tokens held for other withdraw claims, APR0 settlements, or (post-default) would be blocked only incidentally by the reserve guard. In the worst case the attacker drains up to the strategy's liquid balance, causing insolvency for honest claimants whose receipts were actually funded.

### Likelihood Explanation
Requires only an unprivileged KYC-passing lender able to call `requestInstantWithdraw` twice sandwiching a `collectInstantWithdrawFunds` call by the honest CDO — a normal epoch boundary, not a rare edge. The guard that prevents analogous reuse for normal withdraws (`requestWithdraw` reverts on unclaimed loss-adjusted receipts, lines 263-271) has no counterpart on the instant path. Caveat: exploitability depends on `IdleCDOEpochVariant` exposing `claimInstantWithdrawRequest`/`requestInstantWithdraw` to users without its own funded-amount gating — the CDO-side call path should be verified, since the vault itself enforces nothing.

### Recommendation
Key instant claims by their funding parent, mirroring the upstream fix: track funded instant basis per epoch (or a per-user funded watermark set in `collectInstantWithdrawFunds`) and have `claimInstantWithdrawRequest` pay only the funded portion, keeping unfunded `instantWithdrawsRequestsByEpoch` entries pending until their epoch's collection. Alternatively, revert in `requestInstantWithdraw` when `instantWithdrawsRequests[_user] != 0` so no receipt can be created while an earlier one is unclaimed.

### Proof of Concept
Foundry fork PoC sketch (against `IdleCreditVault` + `IdleCDOEpochVariant` deployment):
```solidity
// attacker: KYC'd AA lender
vm.prank(attacker);
cdo.requestInstantWithdraw(X);            // epoch N, unfunded
// honest epoch stop; CDO collects X into strategy
vm.prank(owner);
cdo.stopEpoch(...);                        // triggers collectInstantWithdrawFunds(X)
vm.prank(attacker);
cdo.requestInstantWithdraw(Y);            // epoch N+1, unfunded
uint256 balPre = token.balanceOf(attacker);
vm.prank(attacker);
cdo.claimInstantWithdrawRequest();        // pays X + Y
assertEq(token.balanceOf(attacker) - balPre, X + Y);
// strategy balance now short by Y vs pendingInstantWithdraws accounting
assertEq(strategy.pendingInstantWithdraws(), Y); // still owed to nobody with funds
```
