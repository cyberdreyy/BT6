### Title
Cross-user response misdelivery via MessageId collision in gateway `savedCallbacks` map keyed by MessageId only - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The `capabilities` gateway handler's `savedCallbacks` map is keyed solely by the client-chosen `msg.Body.MessageId`, not by `(sender, MessageId)` as is correctly done elsewhere in the same package (`common.RequestCache`'s `globalId{sender, id}`). Any low-privileged client can pick an arbitrary `MessageId` (only length/format checked, no uniqueness enforcement, and the same handler comment admits allowlisting/rate-limiting is a TODO), colliding with another in-flight victim request to the same DON, so the DON node's response is delivered to the attacker's callback instead of the victim's.

### Finding Description
`ValidatedRequestFromMessage` (`core/services/gateway/handlers/common/message_util.go:83-104`) sets the outgoing JSON-RPC request `ID` directly from `msg.Body.MessageId [1](#0-0) `, with no DON-scoping or per-sender nonce mixed in.

`HandleLegacyUserMessage` in the capabilities handler stores the pending user callback keyed only by `msg.Body.MessageId`: [2](#0-1) 

When the DON node responds, `handleWebAPITriggerMessage` looks the callback back up and deletes it using the same bare `MessageId` key: [3](#0-2) 

Unlike this map, the `RequestCache` used elsewhere in the gateway correctly disambiguates by both sender and id: [4](#0-3) [5](#0-4) 

`Message.Validate()` only checks `MessageId` length/format, not per-sender uniqueness, and `Sender` is cryptographically derived from the signature (so it cannot be spoofed), but nothing prevents two different signers from choosing the identical `MessageId` string: [6](#0-5) 

The handler itself acknowledges no allowlist/rate-limit is enforced at this entry point yet: [7](#0-6) 

Exploit flow:
1. Victim (client V) submits a `MethodWebAPITrigger` request to DON `X` via `HandleLegacyUserMessage` with `MessageId="abc"`. The gateway stores `savedCallbacks["abc"] = V's callback` and forwards a JSON-RPC request with `ID="abc"` to all DON members.
2. Attacker (client A, distinct key/sender) submits their own `HandleLegacyUserMessage` request to the same DON, choosing the same `MessageId="abc"`, before V's response arrives. This overwrites `savedCallbacks["abc"] = A's callback`.
3. When any DON node responds to the original request (response `ID="abc"`), `HandleNodeMessage`/`handleWebAPITriggerMessage` looks up `savedCallbacks["abc"]`, finds A's callback (since it clobbered V's), and delivers V's trigger response data to A.
4. V's original callback is now orphaned and never resolves (until pruning/timeout), a denial of service for V; A illegitimately receives V's response payload, a cross-user response disclosure.

The `msg.Body.Sender != nodeAddr` check in `HandleNodeMessage` only verifies the responding node's signature matches its claimed network address; it does nothing to bind the response back to the original requester, so it does not stop this attack.

### Impact Explanation
This is a genuine cross-user response confusion / information disclosure and DoS: an unprivileged client can, without any special access, receive response data destined for another user's job/trigger request by colliding on a client-controlled `MessageId`, and can simultaneously deny the victim their own response. This matches "cross-user response confusion" / unauthorized disclosure of another user's request/response data in the bounty program's impact classes.

### Likelihood Explanation
Preconditions are minimal: two distinct unauthenticated/low-privilege signer keys able to reach the same DON's `HandleLegacyUserMessage` route with attacker-chosen `MessageId` values, and rough timing to submit the colliding request while the victim's is still in flight (a small race window, easily won by an attacker who can observe or predict request timing, e.g., by flooding with many candidate MessageIds). No allowlist/rate-limiting currently blocks this (explicitly marked TODO in the code), making the attack straightforward and repeatable.

### Recommendation
Change `savedCallbacks` (and any related maps in `capabilities/handler.go` and `handlers/handler.dummy.go`) to key by a composite `(sender, MessageId)` tuple, mirroring the `globalId{sender, id}` pattern already implemented correctly in `common.RequestCache`. Additionally, incorporate DON-scoping/sender into the outbound JSON-RPC `ID` generated in `ValidatedRequestFromMessage`, or otherwise ensure the callback lookup on node response always validates the responder is answering the correct sender's request before delivering the payload.

### Proof of Concept
Go test plan (handler-level, in `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Set up the handler with a mocked `DON` (as in existing `setupHandler`).
2. Create victim request `msgV` signed by key V with `MessageId="collide"`, and call `handler.HandleLegacyUserMessage(ctx, msgV, cbV)`.
3. Before responding, create attacker request `msgA` signed by a different key A, same DonId, same `MessageId="collide"`, and call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)`.
4. Assert `handler.savedCallbacks` has only one entry for `"collide"` (demonstrating the overwrite).
5. Simulate the DON node responding to the original request V (`resp.ID = "collide"`) via `handler.HandleNodeMessage(ctx, resp, nodes[0].Address)`.
6. Assert that `cbA.Wait(ctx)` receives the response payload (proving misdelivery to attacker) while `cbV.Wait(ctx)` times out/never resolves (proving victim DoS) — expected (buggy) behavior confirming the vulnerability, versus the desired fixed behavior where each callback is keyed by `(sender, MessageId)` and only the true requester’s callback receives its response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
