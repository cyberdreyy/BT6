## Title
Unchecked fee-amount subtraction in `EscrowDst::_withdraw` allows permissionless underflow DoS of the destination withdrawal path - (File: `contracts/EscrowDst.sol`)

### Summary
`EscrowDst._withdraw` computes `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` without ever verifying that the fee sum does not exceed `immutables.amount`. Unlike the source-chain path, where `BaseEscrowFactory._postInteraction` explicitly guards this invariant with `if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();`, the permissionless `createDstEscrow` entrypoint accepts an arbitrary calldata `Immutables` struct — including the fee `parameters` bytes — with no equivalent check. This is the same root cause as the reported `LLMOracleCoordinator::finalizeValidation` bug: an unchecked subtraction that assumes an ordering invariant the caller fully controls. [1](#0-0) [2](#0-1) 

### Finding Description
`createDstEscrow` is a permissionless, unprivileged-user entrypoint that deploys a destination escrow clone from a caller-supplied `IBaseEscrow.Immutables` struct. The only checks performed are on `msg.value`/native amount and the cancellation-timing relationship — nothing validates the encoded `protocolFeeAmount`/`integratorFeeAmount` in `immutables.parameters` against `immutables.amount`: [3](#0-2) 

The escrow's identity/address and stored state are fully determined by the hash of these caller-supplied immutables (`immutables.hashMem()`), so whatever fee values the caller embeds become permanently baked into the deployed escrow. On the source chain, the analogous fee amounts are bounds-checked before being embedded into `DstImmutablesComplement.parameters`: [4](#0-3) 

But this check is enforced only for the *source*-side computation against `takingAmount`, using `FeeTaker._getFeeAmounts`. Nothing forces the taker who later calls `createDstEscrow` to submit consistent values — the taker directly assembles and signs the calldata immutables themselves. If a caller (acting as "taker") submits `integratorFeeAmount + protocolFeeAmount >= immutables.amount`, then every subsequent `withdraw`/`publicWithdraw` call reaches:

```
uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
```

which underflows and reverts with panic `0x11`, exactly mirroring the external report's `_mean - _stddev` underflow pattern. [5](#0-4) 

Because `Immutables` fields (including `parameters`) are immutable once hashed/deployed and validated via `onlyValidImmutables`, there is no recovery path for `withdraw`/`publicWithdraw` — the arithmetic will always revert for the lifetime of that escrow.

### Impact Explanation
This breaks the designed safety valve of the protocol: `publicWithdraw` exists specifically so that any access-token holder can force-complete a swap with the revealed secret, protecting the maker even if the taker becomes unresponsive. By deliberately embedding a fee sum `>= amount` when calling `createDstEscrow`, an unprivileged taker guarantees that **no one** — not the maker, not the taker, not a public keeper — can ever successfully call `withdraw` or `publicWithdraw` on that destination escrow, regardless of whether the correct secret is presented. The only remaining path is `cancel`, which does not use the fee subtraction and simply returns `immutables.amount` + `safetyDeposit` to the taker after the cancellation timelock. This forces every outcome for that escrow into cancellation, defeating the public-withdrawal safety mechanism and freezing the maker's expected destination funds for the entire withdrawal/public-withdrawal window — a "temporary freezing of funds during the live swap lifecycle" (High-severity impact per the bounty scope).

### Likelihood Explanation
`createDstEscrow` is explicitly permissionless and takes the full `Immutables` struct (including `parameters`) as untrusted calldata from `msg.sender`; no on-chain check ties the encoded fee amounts to `immutables.amount`. Any unprivileged account willing to fund the escrow (paying `msg.value`/ERC20 transfer) can trigger this at will, with no dependency on governance, oracles, or race conditions — it is a deterministic, single-transaction condition.

### Recommendation
Enforce the same invariant on the destination side that already exists on the source side. In `createDstEscrow` (or in `EscrowDst._withdraw`), validate that `integratorFeeAmount + protocolFeeAmount < immutables.amount` before deployment/funding, reverting with `InvalidFeeAmounts()` otherwise — mirroring the existing guard in `BaseEscrowFactory._postInteraction`:
```solidity
uint256 integratorFeeAmount = dstImmutables.integratorFeeAmountCd();
uint256 protocolFeeAmount = dstImmutables.protocolFeeAmountCd();
if (integratorFeeAmount + protocolFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();
```
placed inside `createDstEscrow` prior to `_deployEscrow`, so a malformed escrow can never be created in the first place.

### Proof of Concept
1. Attacker (any unprivileged account acting as "taker") crafts `dstImmutables` with `amount = 100`, `parameters` encoding `protocolFeeAmount = 60`, `integratorFeeAmount = 60` (sum `120 > 100`), and a valid `hashlock`.
2. Attacker calls `createDstEscrow{value: nativeAmount}(dstImmutables, srcCancellationTimestamp)` — passes because only `msg.value`/timing checks apply [3](#0-2) .
3. Once the withdrawal window opens, anyone (taker via `withdraw`, or an access-token holder via `publicWithdraw`) presents the correct secret; `_withdraw` computes `100 - 60 - 60`, underflows, and reverts [6](#0-5) .
4. This holds for every call throughout `DstWithdrawal` and `DstPublicWithdrawal` stages; the escrow can only ever be resolved via `cancel()` after `DstCancellation`, returning capital to the taker while the maker never receives the destination funds.

        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
