### Title
Group-level rate limiter can be gamed by splitting one large outflow into many smaller ones because the check is validated read-only against stale state - ([File: programs/marginfi/src/utils/general.rs])

### Summary
The group-level rate limiter is designed to cap aggregate USD outflow across an entire marginfi group (a bank-run/oracle-attack mitigation), but the check performed inside `record_withdrawal_outflow` validates each withdraw/borrow against the group's *currently persisted* (and, by design, stale) `rate_limiter` state rather than against a running total that reflects outflows already executed in the same settlement window. Because the group account is only mutated later by an off-chain-aggregated `update_group_rate_limiter` call, any number of withdraw/borrow instructions submitted before that settlement each pass the same "remaining capacity" check independently, exactly like the reported `LargeBet` issue where a single-action-in-isolation check is defeated by splitting the action into many smaller ones.

### Finding Description
`record_withdrawal_outflow` performs the group-level check as a read-only comparison, explicitly documented as such: [1](#0-0) 

The bank-level limiter is mutated synchronously (`bank.rate_limiter.try_record_outflow`), but the group-level limiter is *not* updated in the same instruction — it is only checked via `effective_remaining_capacity`, and the actual `group.rate_limiter` state is advanced later by the delegated flow admin aggregating `RateLimitFlowEvent`s off-chain and calling `update_group_rate_limiter`: [2](#0-1) 

This design is explicitly intentional ("avoids serializing all activity in a group through one writable group account"), but it means the group's `remaining capacity` value used for each individual check is a snapshot that only advances when the admin bothers to settle it: [3](#0-2) 

The same "N independent checks against a single stale limit, with no in-transaction/in-window aggregation" pattern used by `lending_account_withdraw`, `lending_account_borrow`, and the `kamino/drift/juplend/solend` withdraw variants: [4](#0-3) [5](#0-4) 

This mirrors exactly the `LargeBet` root cause: the protective check ("this single bet/outflow must not exceed X") is evaluated per-instruction against a fixed reference value instead of against the true running total of all outflows that have already occurred but not yet been "settled" into the checked state. Splitting one large withdrawal into many smaller ones (via multiple instructions in one transaction, or many transactions submitted back-to-back before the off-chain worker's periodic `update_group_rate_limiter` call) lets each individual check see the same unconsumed `effective_remaining_capacity`, so the sum of actual outflows can vastly exceed `hourly_max_outflow_usd` / `daily_max_outflow_usd`.

### Impact Explanation
Medium: the group rate limiter is explicitly documented as an oracle-attack/bank-run mitigation, and this gap breaks the invariant that group-wide USD outflow stays bounded within a window. In the worst case (a delayed or backlogged delegate flow admin, or an admin batching only periodically as documented "every ~10 minutes"), an attacker or coordinated set of users can withdraw/borrow far beyond the intended cap while the group account still shows near-zero recorded outflow, giving a false sense of protection exactly as in the source report.

### Likelihood Explanation
Medium: no special privilege is needed — any account holder using the standard permissionless `lending_account_withdraw`/`lending_account_borrow` (or the Kamino/Drift/JupLend/Solend withdraw variants) can trigger this. The gap is inherent to the settlement design (checked read-only, updated only periodically off-chain), so it is reliably exploitable within any settlement window, though there is limited direct profit incentive absent a broader attack (e.g., paired with an oracle manipulation or a run scenario), consistent with the "gameable but low direct incentive" characterization in the source report.

### Recommendation
Change validation so the group-level cap accounts for outflows that occurred since the last settlement, not just the last persisted `update_group_rate_limiter` snapshot — e.g., maintain a per-window running total that is incremented synchronously (even if approximately) at the time of each outflow-triggering instruction rather than relying solely on periodic off-chain aggregation, or shrink the settlement interval and cross-check emitted `RateLimitFlowEvent`s so no more than one settlement-window's worth of unaccounted outflow can occur before the cap is enforced against real-time state.

### Proof of Concept
1. Admin configures `configure_group_rate_limits` with `hourly_max_outflow_usd = 10`.
2. Multiple accounts (or one account across multiple transactions) each borrow/withdraw an amount valued at just under $10 in the same hour, before the delegate flow admin calls `update_group_rate_limiter`.
3. Each instruction's `record_withdrawal_outflow` check reads the same unadvanced `group.rate_limiter.hourly.effective_remaining_capacity(...)` (still ~10, since nothing has been recorded on-chain yet), so every individual withdraw/borrow passes.
4. Aggregate outflow across all these instructions can reach `N * ~10` USD instead of the intended `10` USD cap, as demonstrated by the existing test harness pattern in `tests/specs/basic/17_rateLimiter.spec.ts` where multiple borrows execute successfully back-to-back and only fail once the admin has actually called `update_group_rate_limiter` to advance the persisted state: [6](#0-5)

### 2. User transaction path

During a withdraw or borrow:

- The bank rate limiter is updated immediately on the writable bank account.
- The group rate limiter is only checked read-only.
- The protocol converts the flow to USD using the instruction price/oracle path.
- If the projected group hourly or daily capacity is exceeded, the user instruction fails.
- A `RateLimitFlowEvent` is emitted for off-chain aggregation.

Important details:

- Flashloans, liquidations, and deleverages skip the normal rate-limit accounting path.
- `RateLimitFlowEvent` is an indexing aid, not a source of truth. Solana log truncation can drop
  events, so the off-chain worker must reconcile gaps instead of assuming no event means no flow.
```

### 3. Admin settlement path

The off-chain worker batches the observed flows and calls `update_group_rate_limiter`.

Inputs:

- `outflow_usd`
- `inflow_usd`
- `update_seq`
- `event_start_slot`
- `event_end_slot`

Rules enforced on-chain:

- At least one of `outflow_usd` or `inflow_usd` must be present.
- `event_start_slot <= event_end_slot`
- `event_start_slot > last_admin_update_slot`
- `event_end_slot <= current slot`
- The batch must not be stale (`<= 1500` slots old)
- `update_seq` must equal `last_admin_update_seq + 1`

Application order matters:

- Inflow is applied first.
- Outflow is applied second.

That lets a single batch include both releases and consumptions of capacity.
```
