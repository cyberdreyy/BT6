### Title
No oracle fallback in `stopEpoch`/`startEpoch` — a stale Chainlink USD0++ feed permanently freezes all tranche withdrawals - (File: contracts/IdleCDOUsualVariant.sol)

### Summary
`IdleCDOUsualVariant` routes its epoch lifecycle through `IdleUsualStrategy.getChainlinkPrice()`, which hard-reverts when the single Chainlink USD0++ feed (`USD0ppOracle`, a fixed immutable address) returns data older than 24 hours. During a running epoch, deposits and withdrawals are paused (`_pause()`, `allowAAWithdraw = allowBBWithdraw = false`), and the only exit path — `stopEpoch()` — unconditionally calls `getChainlinkPrice()` first. If the feed misses a heartbeat or is halted/deprecated, `stopEpoch` can never execute and user funds remain locked in the vault. There is no secondary oracle, no TWAP fallback, and no time-based escape hatch in the epoch state machine.

### Finding Description
In `IdleUsualStrategy`, the staleness guard reverts instead of degrading:

```solidity
// contracts/strategies/usual/IdleUsualStrategy.sol:164-172
function getChainlinkPrice() public view returns (uint256) {
    (,int256 answer,,uint256 updatedAt,) = IOracle(USD0ppOracle).latestRoundData();
    require(updatedAt > block.timestamp - 24 hours, "Stale price");
    return uint256(answer) * 1e10;
}
```

`USD0ppOracle` is a hardcoded constant (`0xFC9e30Cf89f8A00dba3D34edf8b65BCDAdeCC1cB`, line 48), so the feed cannot be swapped. The same function is invoked by:

- `startEpoch()` (`IdleCDOUsualVariant.sol:63`) — a stale feed blocks epoch start (mild).
- `stopEpoch()` (`IdleCDOUsualVariant.sol:77`) — a stale feed permanently blocks epoch termination.

While the epoch is running, `startEpoch` has already executed `_pause()` and set `allowAAWithdraw = false` / `allowBBWithdraw = false` (lines 52–55). Withdrawal-enabling code lives only inside `stopEpoch` (lines 80–82), which is gated behind the reverting oracle call at line 77. Even the loss-computation branch (lines 87–99) is unreachable without a fresh price. `harvest` is also gated (line 183) but that is secondary.

Note the check is tight against the feed's own documented behavior: the feed has a 24-hour heartbeat and 50-bips deviation threshold (comment at lines 165–167), so a single missed heartbeat — or any delay pushing `updatedAt` past `block.timestamp - 24 hours` — makes the check revert even though the price is still usable.

### Impact Explanation
All tranche holders' funds are frozen for as long as the Chainlink feed is stale. The vault holds 100% of TVL as strategy tokens minted 1:1 in `startEpoch` (line 66); seniors cannot exit at the promised $1 parity and juniors cannot exit at all. If the feed is permanently halted (Chainlink deprecates feeds regularly), the freeze is permanent through the intended path — the only recovery would be emergency shutdown mechanics, which socialize/force losses rather than honoring the designed senior-parity waterfall, so loss of the senior depeg protection is a direct fund impact. Quantified worst case: 100% of vault TVL locked; under emergency recovery, seniors lose the junior-funded parity top-up the product exists to provide.

### Likelihood Explanation
No attacker action is required — the failure mode is triggered by a single missed 24h heartbeat or feed deprecation on a long-duration (per NatSpec, ~6 month) disposable epoch. The staleness window is set equal to the heartbeat, giving zero tolerance margin. Likelihood is low-to-moderate per epoch, but the vault is explicitly single-epoch, so each deployment gets exactly one exposure window at its most critical moment (epoch settlement). Existing guards do not help: `onlyOwner` on `stopEpoch` cannot bypass the internal oracle revert, and `oraclePrice`/`setOraclePrice` (lines 155–161) is never consumed for the withdrawal path — the live `getChainlinkPrice()` call at line 77 is unavoidable.

### Recommendation
- In `stopEpoch`, wrap the price fetch in a fallback: try `getChainlinkPrice()`, and on revert/staleness fall back to the stored `oraclePrice`, the USD0++ `getFloorPrice()` (already used in `setOraclePrice`, line 159), or a `priceAtStartEpoch`-based conservative value.
- Relax the stale check to `>=` a slightly larger window than the 24h heartbeat (e.g., 25–26h) or use `answeredInRound`/round completeness checks rather than a hard revert.
- Add an owner/guardian `forceStopEpoch(uint256 _price)` escape that lets the epoch settle at a manually supplied, floor-bounded price after a staleness timeout, so withdrawals can be re-enabled even if the feed never recovers.

### Proof of Concept
Foundry fork PoC (extend `test/foundry/IdleUsualStrategy.t.sol`, mainnet fork block 21767467):

```solidity
function testStaleOracleFreezesStopEpoch() external {
    // 1. Deposit into AA and BB tranches (reuse existing helpers in TestIdleCDOLossMgmt)
    _depositAAandBB(); // deposits USD0++ into both tranches

    // 2. Owner starts the epoch -> deposits/withdraws paused
    vm.prank(owner);
    idleCDO.startEpoch(180 days);

    // 3. Warp past epoch end
    vm.warp(block.timestamp + 180 days + 1);

    // 4. Simulate stale feed: USD0ppOracle returns updatedAt older than 24h
    vm.mockCall(
        0xFC9e30Cf89f8A00dba3D34edf8b65BCDAdeCC1cB,
        abi.encodeWithSelector(IOracle.latestRoundData.selector),
        abi.encode(uint80(1), int256(95_000_000), uint256(0), block.timestamp - 25 hours, uint80(1))
    );

    // 5. stopEpoch reverts -> withdrawals never re-enabled
    vm.prank(owner);
    vm.expectRevert(bytes("Stale price"));
    IdleCDOUsualVariant(address(idleCDO)).stopEpoch();

    // 6. Withdrawals still blocked: funds frozen
    assertFalse(idleCDO.allowAAWithdraw());
    assertFalse(idleCDO.allowBBWithdraw());
    vm.expectRevert();
    idleCDO.withdrawAA(ONE_TRANCHE);
}
```

Caveat: I was unable to fully verify the `_emergencyShutdown`/`restoreOperations` path in `IdleCDO.sol` within the iteration budget. If emergency shutdown re-enables withdrawals at a loss-adjusted price, the freeze is temporary rather than permanent, but the senior-parity guarantee (the vault's core invariant) is still broken because the junior top-up computation at `IdleCDOUsualVariant.sol:93-96` never runs.
