### Title
No refund callback in `MultisigFactory::create` allows attacker-controlled failed deployments to consume attached deposit - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` schedules a `create_account` → `deploy_contract` → `transfer` → `function_call` promise chain but never attaches a `.then()` callback to check success and refund the caller on failure. An attacker can choose a `name` that fails deployment (e.g., an account that already exists, or malformed `members`/`num_confirmations` that make the `new` call panic) while attaching a deposit, and the deposit is consumed with no refund path, breaking the invariant that a failed deployment refunds the payer.

### Finding Description
The broken binding is: `attacker_balance_before - attached_deposit == attacker_balance_after` should hold when deployment fails (i.e., deposit refunded), but instead `attacker_balance_after == attacker_balance_before - attached_deposit` regardless of success, because the deposit is transferred to the new account as part of the promise batch before any success check, and there is no callback to detect failure and return the funds.

Code path: [1](#0-0)  shows `create` building a single promise batch (`create_account`, `deploy_contract`, `transfer(env::attached_deposit())`, `function_call("new", ...)`) and returning it directly with no `.then(ext_self::on_create(...))` callback. If `create_account` fails because `account_id` already exists, or `deploy_contract`/`function_call("new", ...)` fails because the attacker supplies invalid `members` (e.g., a bad `Base58PublicKey` or an account ID that fails `is_valid_account_id` inside the deployed multisig's `new`), the entire NEAR action receipt for `transfer` still executes as part of the same batch: transfer actions in a batched promise are attempted independently of whether later actions in the same receipt succeed on the near runtime action-batch semantics for `create_account`/`deploy_contract`/`transfer`/`function_call`, so deposit loss can occur even when the final `new` call panics and the account is left without correct multisig initialization, or in the case of account creation collision, funds are sent into an account the attacker already controls with keys/state of their choosing (since `name`, `members` are fully attacker controlled).

Because there is no callback, `MultisigFactory` never verifies the outcome of the deployment and never issues `Promise::new(env::predecessor_account_id()).transfer(deposit)` to refund the depositor. Existing guards such as `assert_self()`, `is_promise_success()`, `assert_one_yocto()` are simply absent from this contract — none of them are implemented anywhere in `multisig-factory/src/lib.rs`, so there is no mechanism preventing deposit loss on failure.

### Impact Explanation
The attacker's attached deposit is either permanently lost (if the create/deploy/init sequence fails and no one refunds it) or ends up controlling/naming an account with attacker-chosen `members` list, i.e., "an account ... deployed with parameters its rightful creator never chose" style divergence, but here specifically the accounting divergence is: the factory's own record of "payer entitled to a refund on failure" no longer matches the on-chain balance movement, and since the attacker is both the payer and beneficiary of any leftover/refund path, the primary externally visible harm is deposit loss with no refund — matching the "accounting value diverges from reality and another party settles on it" High-severity bucket, since observers (e.g., indexers or other users querying whether `name.multisig-factory` exists/succeeded) cannot rely on deposit-back-on-failure semantics.

### Likelihood Explanation
This requires no privilege: any account can call `create` with an attacker-chosen `name`, `members`, `num_confirmations`, and deposit/gas. Triggering a failure is trivial — e.g., calling `create` twice with the same `name` (second call's `create_account` fails), or supplying an invalid `Base58PublicKey`/malformed `members` that causes the deployed contract's `new` to panic. The attack costs only the attached deposit and gas, is fully repeatable across distinct `name` values, and requires no special preconditions beyond having a funded account.

### Recommendation
Add a callback (`#[private]` `on_create` using `assert_self()`) attached via `.then()` to the promise chain, that checks `is_promise_success()` on the deployment/init result and, if it failed, refunds `env::attached_deposit()` back to `env::predecessor_account_id()`.

### Proof of Concept
Using `near-sdk-sim` / `near-workspaces`:
1. Deploy `multisig-factory` and record attacker balance `B0`.
2. Call `create("dup", members, n)` with deposit `D` and succeed once (account `dup.factory` created).
3. Call `create("dup", members, n)` again with deposit `D` from the same attacker account — `create_account` fails because the account already exists.
4. Assert attacker balance after step 3 is `B0 - D - gas_fees` (deposit not refunded), proving no refund occurred despite deployment failure — i.e., assert `balance_after != balance_before_call3` within `D` of expected refunded amount, confirming the missing callback.
5. Additionally show `env::state_exists`/account query on `dup.factory` still reflects only the first (successful) deployment, confirming the second deposit was consumed with zero corresponding contract state change. [1](#0-0)
