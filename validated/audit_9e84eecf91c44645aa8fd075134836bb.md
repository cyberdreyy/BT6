### Title
Multisig sub-account deposits are not refunded when creation fails, permanently freezing user funds - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` in `multisig-factory/src/lib.rs` forwards the caller's entire `attached_deposit` to a newly-created sub-account as part of a single batched promise (`create_account → deploy_contract → transfer → function_call`), but unlike the sibling factories in this same codebase, it never attaches a callback to check whether the batch succeeded, and never refunds the deposit if it fails. [1](#0-0) 

### Finding Description
Both `lockup-factory` and `staking-pool-factory` in this repo follow the same pattern of "create sub-account, transfer attached deposit, deploy code, call `new`", and both explicitly attach a `.then(ext_self::on_..._create(...))` callback that checks `is_promise_success()` and, on failure, transfers the recorded `attached_deposit` back to `predecessor_account_id`: [2](#0-1) [3](#0-2) [4](#0-3) 

This callback exists precisely because on NEAR, if any action in the batched receipt fails (e.g. `CreateAccount` fails because the target account name is already taken, or the subsequent `function_call` to `new` panics), the NEAR that was transferred as part of that batch is not automatically routed back to the original transaction signer — it must be refunded manually by the factory contract, since the factory (not the original caller) is the account that issued the transfer.

`MultisigFactory::create`, however, does the exact same kind of batched operation — `create_account`, `deploy_contract`, `transfer(env::attached_deposit())`, `function_call(... "new" ...)` — but returns the raw `Promise` with no `.then()` callback at all: [5](#0-4) 

If the batch fails for any reason — e.g., another account (attacker or otherwise) has already created `name.<factory>` (front-running the sub-account name), or the `new` initializer on `multisig2` panics on invalid `members`/`num_confirmations` — the caller's attached NEAR is not returned to them and is not held by any usable account: the custody binding "value debited from caller == value delivered to a working multisig (or refunded)" is broken with no recovery path, since `MultisigFactory` has no refund logic and no other method to reclaim the deposit.

### Impact Explanation
This falls under the "funds permanently frozen" / "value debited versus value delivered" impact category. A user who calls `create` with a legitimate deposit can lose that NEAR permanently if the underlying batched receipt fails, with no code path in the contract to return it. Because sub-account names are public and predictable (`name.<multisig-factory-account>`), this is trivially triggerable by an unprivileged party front-running a `name` value the victim intends to use, or simply happens by an honest user's own bad init arguments — in either case the loss is real, permanent, and not a griefing/DoS scenario but a concrete loss of funds.

### Likelihood Explanation
High. No special privileges are required to create a same-named sub-account ahead of a victim's transaction, and this factory contract deploys/initializes an external contract (`multisig2`) whose `new()` can panic on invalid arguments supplied at the outer call. Both are ordinary, reachable failure paths for the batched `Promise` in `create`, unlike the mitigated behavior implemented in `lockup-factory`/`staking-pool-factory`.

### Recommendation
Mirror the pattern already used elsewhere in this repository: attach an `ext_self` callback (`.then(...)`) to the `Promise` returned by `create`, check `is_promise_success()`, and if the sub-account/init failed, transfer the recorded `attached_deposit` back to `predecessor_account_id`, exactly as done in `lockup-factory::on_lockup_create` and `staking-pool-factory::on_staking_pool_create`.

### Proof of Concept
1. Attacker observes (or predicts) that a victim intends to call `multisig-factory.create(name="team", members=[...], num_confirmations=2)`.
2. Attacker creates `team.<multisig-factory-account>` directly beforehand (or otherwise causes the sub-account name to already exist).
3. Victim calls `create` with `name="team"` and attaches, e.g., 5 NEAR for the new multisig's storage/balance.
4. The batched promise's `create_account` action fails because `team.<multisig-factory-account>` already exists; the whole receipt fails.
5. Because `create` in `multisig-factory/src/lib.rs` has no `.then()` callback, the factory never checks for this failure and never refunds the 5 NEAR to the victim. The deposit is lost with no method in `MultisigFactory` to recover it. [1](#0-0)

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }

    /// Callback after a staking pool was created.
    /// Returns the promise to whitelist the staking pool contract if the pool creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }
