### Title
Empty-password LDAP bind may be accepted as a valid "unauthenticated bind," allowing session creation - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`ldapAuthenticator.CreateSession` and `TestPassword` in `core/sessions/ldapauth/ldap.go` pass the user-supplied `sr.Password` directly to `conn.Bind(searchBaseDN, sr.Password)` without ever checking whether the password is empty or whitespace-only before the bind call. Per RFC 4513 §5.1.2, an LDAP simple bind with a non-empty DN and a zero-length password is defined as an "unauthenticated bind," and many LDAP servers/directories will return a success response for such a bind unless the operator has explicitly hardened the server to reject it. Because the local code treats `conn.Bind(...) == nil` as proof of a valid credential check, this can let an attacker who knows (or guesses/enumerates) any valid directory email log in with an empty password if the upstream directory is not hardened against unauthenticated binds.

### Finding Description
`POST /sessions` is handled by `SessionsController.Create` [1](#0-0) , which calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` with the attacker-supplied `sessions.SessionRequest{Email, Password}` from the raw JSON body [2](#0-1) . When the configured `AuthenticationProviderName` is `LDAPAuth`, this dispatches to `ldapAuthenticator.CreateSession`:

```go
if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
    ...
    returnErr = errors.New("unable to log in with LDAP server. Check credentials")
}
``` [3](#0-2) 

There is no check anywhere in the request path (`SessionsController.Create`, `sessions.SessionRequest`, or `ldapAuthenticator.CreateSession`/`TestPassword`) that rejects an empty or whitespace-only password before it reaches `conn.Bind`. `core/sessions/session.go`'s `SessionRequest` struct performs no validation on `Password` [4](#0-3) , and the same unguarded pattern exists in `TestPassword` [5](#0-4) .

If the bind succeeds (`err == nil`), the code proceeds to call `l.FindUser(ctx, escapedEmail)` to look up the user's role and, if found, creates a fully authenticated `ldap_sessions` row with that user's role [6](#0-5) . Whether an unauthenticated bind (empty password) is treated as success is a property of the upstream LDAP/Active Directory server configuration, not something Chainlink's `AuthenticationProviderName`/LDAP client controls or rejects — the go-ldap `conn.Bind` call used here does not distinguish or reject unauthenticated binds locally.

Because `core/sessions/authentication.go`'s `AuthenticationProviderName` interface is the shared abstraction behind every `/v2` authenticated endpoint (`AuthorizedUserWithSession` is invoked by the session/auth middleware for every subsequent authenticated request), a session created via this path grants full access commensurate with the resolved role (potentially admin if the bound DN belongs to an admin-mapped LDAP group).

### Impact Explanation
If the underlying directory does not explicitly disable unauthenticated binds (a common oversight, and the historical default behavior for many LDAP servers per RFC 4513), an attacker who knows any valid user email (often guessable/enumerable, e.g. `admin@company.com`) can obtain a valid, fully privileged Chainlink node session without knowing any password. This matches "Critical – node takeover" since gaining an admin-role session allows key export, job/bridge modification, and unauthorized transaction submission through the `/v2` API surface protected by `AuthenticationProvider`.

### Likelihood Explanation
Exploitability depends entirely on the operator's LDAP server configuration: it requires that the configured LDAP/AD server accept unauthenticated (empty-password) simple binds for the target DN, which is not the default-secure configuration on modern hardened directories (e.g., Active Directory rejects this by default in current versions) but is a known-risky and still-encountered misconfiguration in legacy/OpenLDAP deployments. The Chainlink-side code performs no defense-in-depth check, so exploitability is solely gated on upstream server posture — this is a missing-hardening/defense-in-depth gap in the local code, not a guaranteed bypass against any deployment. Given the rules exclude "misconfiguration-only" paths from being treated as standalone critical findings, this weakens the case, but the root cause here is the local application's failure to defensively reject empty passwords before delegating trust decisions to an external system, which is squarely an application-layer bug independent of whether every specific server is misconfigured.

### Recommendation
In `core/sessions/ldapauth/ldap.go`, reject empty or whitespace-only passwords in `CreateSession` and `TestPassword` before calling `conn.Bind`, e.g.:
```go
if strings.TrimSpace(sr.Password) == "" {
    return "", errors.New("password cannot be empty")
}
```
Apply the same guard in `TestPassword`. Additionally consider validating this at the `SessionsController.Create` / `SessionRequest` level so all `AuthenticationProvider` implementations share the same defense-in-depth check regardless of upstream directory hardening.

### Proof of Concept
Go table test in `core/sessions/ldapauth/ldap_test.go` (extending `TestORM_CreateSession_UpstreamBind`):
1. Configure `mockLdapConnProvider.On("Bind", mock.Anything, "")` and `mockLdapConnProvider.On("Bind", mock.Anything, "   ")` to `Return(nil)` (simulating a directory that accepts unauthenticated binds).
2. Call `ldapAuthProvider.CreateSession(ctx, sessions.SessionRequest{Email: user1.Email, Password: ""})` and `Password: "   "`.
3. Assert `require.Error(t, err)` and that no session ID is returned — currently this would incorrectly succeed given `Bind` mock returns nil, demonstrating the missing guard.
4. Add the same table cases to `TestPassword` tests.
After the fix, both cases must return an error before `conn.Bind` is ever invoked (verify via `mockLdapConnProvider.AssertNotCalled(t, "Bind", ...)`).

func (sc *SessionsController) Create(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()
	sc.App.GetLogger().Debugf("TRACE: Starting Session Creation")

	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)
	if err != nil {
		sc.App.GetLogger().Errorf("Error loading user WebAuthn data: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}
