## Title
Precompile signature verification (secp256k1/ed25519/secp256r1) is executed inside SVM instruction processing without any per-instruction compute-unit metering, decoupling actual CPU cost from the compute budget the sender pays for - ([File: program-runtime/src/invoke_context.rs])

### Summary
When precompile verification was moved into the SVM (feature `move_precompile_verification_to_svm`, SIMD-0159), the actual signature-verification work for `secp256k1`, `ed25519`, and `secp256r1` programs runs via `InvokeContext::process_precompile` [1](#0-0) , which calls straight into `epoch_stake_callback.process_precompile(...)` → the crypto `verify()` routines in `precompiles/src/secp256k1.rs`, `precompiles/src/ed25519.rs`, and `precompiles/src/secp256r1.rs`. Unlike every other syscall in the codebase (e.g. `SyscallAltBn128`, `SyscallBigModExp`, `SyscallPoseidon` all explicitly call `invoke_context.compute_meter.consume_checked(cost)` before doing expensive work [2](#0-1) [3](#0-2) ), `process_precompile` never touches `invoke_context.compute_meter` at all.

### Finding Description
Each precompile's `verify()` loops over an attacker-controlled signature count taken directly from instruction data:
- secp256k1: `count = data[0]` (u8, up to 255), looping `libsecp256k1::recover` + keccak hashing per iteration [4](#0-3) 
- ed25519: `num_signatures = data[0]` (u8, up to 255, **no upper bound check** unlike secp256r1), looping `ed25519_dalek` `verify_strict` per iteration [5](#0-4) 
- secp256r1: `num_signatures = data[0]` capped at 8, looping OpenSSL `EcGroup`/`EcPoint`/ECDSA verify (P-256) per iteration [6](#0-5) 

All three use offset-based indirection (`Ed25519SignatureOffsets`, `SecpSignatureOffsets`, `Secp256r1SignatureOffsets`) that let every one of the up-to-255 (or 8) "signatures" reference the *same* small signature/pubkey/message bytes elsewhere in the transaction's instruction data [7](#0-6) . This means a small, cheap transaction payload can force the validator to redundantly perform up to 255 real elliptic-curve verifications per instruction, across all precompile instructions present.

Crucially, `process_precompile` performs this work with zero compute-unit deduction — no call to `consume_checked` exists in that path, in contrast to the pattern used everywhere else in the codebase for CPU-intensive syscalls (`SyscallAltBn128`, `SyscallBigModExp`, `SyscallPoseidon`, `SyscallGetStackHeight`, etc.). The only place these signature counts are priced at all is `CostModel::get_signature_cost` in `cost-model/src/cost_model.rs`, which applies a flat per-signature constant (`SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, `SECP256R1_VERIFY_COST`) [8](#0-7)  used purely for leader-side block-cost-limit accounting during scheduling — it is disconnected from the transaction's own `compute_unit_limit` enforcement during actual SVM execution of the instruction.

This is the direct analog of the JWE `p2c` bug: an attacker-controlled iteration count/parameter (`num_signatures`, and to a lesser extent `message_data_size`) drives real, expensive cryptographic computation, but the mechanism meant to bound/price that computation for the entity paying for it (the transaction's compute-unit budget) never actually charges for it.

### Impact Explanation
Because the compute meter isn't charged, a transaction can declare an artificially low `compute_unit_limit` (and thus pay a low priority/compute fee) while still forcing the validator to execute substantial real cryptographic work (up to 255 EC point/signature verifications per precompile instruction, multiplied across however many precompile instructions fit in the transaction/instruction-trace limits) during normal transaction replay/execution. This is a compute-cost/fee mismatch that lets unprivileged senders impose CPU load disproportionate to what they pay, a leader-side and validator-side CPU DOS vector reachable from a single submitted transaction.

### Likelihood Explanation
High reachability: any unprivileged transaction sender can include `secp256k1_program`, `ed25519_program`, or `secp256r1_program` instructions with maximal signature counts and offset-aliasing tricks. No special privileges, CPI, or leader/validator cooperation are required — the exploit purely depends on how the transaction is constructed and processed by `process_precompile`.

### Recommendation
Charge `invoke_context.compute_meter.consume_checked(...)` inside `process_precompile` (or before dispatching to it) using a cost that scales with the actual declared `num_signatures`/`count` and, ideally, the referenced message sizes, mirroring the metering pattern already used for other CPU-heavy syscalls (`SyscallAltBn128`, `SyscallBigModExp`, `SyscallPoseidon`). Ensure this metering is enforced against the transaction's real-time compute budget, not merely reflected in the leader's cost-model estimate used for block-cost-limit scheduling. Also add an explicit upper bound on `num_signatures` for the ed25519 precompile (currently uncapped at the protocol level, unlike secp256r1's `<= 8` check) to reduce worst-case amplification.

### Proof of Concept
Construct a single transaction with one `ed25519_program` instruction whose data has `num_signatures = 255` (max u8) and whose 255 `Ed25519SignatureOffsets` entries all reference the *same* small signature/pubkey/message bytes packed elsewhere in the instruction data (well within the ~1232-byte packet limit). Submitting this transaction causes `process_precompile` → `precompiles::ed25519::verify` to perform 255 real `ed25519_dalek::verify_strict` calls [9](#0-8)  during SVM execution, with the compute meter (`invoke_context.compute_meter`) never being charged for this work in `process_precompile` [1](#0-0) , decoupling the CPU cost incurred from the compute-unit budget the sender is required to pay for.

**Uncertainty note:** I was not able to directly confirm (within available tool budget) whether some other code path outside `process_precompile`/`InvokeContext` separately deducts compute units for precompile signature verification before or after this call (e.g., in `svm/src/transaction_processor.rs` around instruction execution loop), nor could I fully trace `epoch_stake_callback.process_precompile` implementations in `runtime/src/bank.rs` and `svm-callback/src/lib.rs` to rule out additional metering there. A background Devin session with full repo access should verify this end-to-end before treating this as fully confirmed.

    fn get_signature_cost(transaction: &impl TransactionMeta) -> u64 {
        let signatures_count_detail = transaction.signature_details();

        signatures_count_detail
            .num_transaction_signatures()
            .saturating_mul(SIGNATURE_COST)
