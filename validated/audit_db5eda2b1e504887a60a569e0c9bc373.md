## Title
Response-Channel Hijacking via Attacker-Controlled MessageId in Gateway Legacy Trigger Handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The LayerZero report describes a channel-isolation failure: any UA can inject a message into another UA's packet slot because the relayer does not scope/isolate message channels per sender before delivery, and the invalid packet is only rejected *after* it has already occupied (and frozen) the shared queue. The Chainlink Gateway's legacy WebAPI trigger handler has the same class of flaw: pending-response "channels" (`savedCallbacks`) are keyed only by a caller-supplied `MessageId`, with no ownership/ isolation check, and no per-request uniqueness enforcement before a slot is overwritten.

### Finding Description
In `HandleLegacyUserMessage`, the gateway stores the caller's response callback keyed solely by `msg.Body.MessageId`, which is a field taken directly from the untrusted, unauthenticated-by-identity user request body (its only validation is length/non-null-suffix in `Message.Validate()`, not uniqueness or ownership): [1](#0-0) 

There is no check whether `msg.Body.MessageId` already has a saved callback before overwriting it: [2](#0-1) 

When a DON node later responds with that same message ID, the handler looks the ID up in the shared map and forwards whatever response is found to whichever callback is currently registered under that key, with no verification that the response actually corresponds to the request that registered it: [3](#0-2) 

`Message.Validate()` only bounds-checks `MessageId` length and forbids a trailing null byte — it performs no uniqueness or ownership binding: [4](#0-3) 

This mirrors the audited bug's root cause exactly: the relayer/gateway does not isolate message "channels" per requester before admitting a message into the shared processing structure (the LayerZero `packet queue` ↔ the gateway's `savedCallbacks` map), so an unprivileged party can collide with another party's channel. The code even has an open TODO acknowledging this gap: [5](#0-4) 
and a test file explicitly flags the missing sender/allowlist validation as unresolved: [6](#0-5) 

### Impact Explanation
Any unprivileged client that can reach the gateway's legacy WebAPI trigger endpoint can pick an arbitrary `MessageId` (bounded only by length/format). If that ID collides with an ID already in-flight for a different, unrelated user request:
- The victim's later legitimate response gets delivered to the attacker's registered callback (or vice-versa) — cross-user response confusion, potentially leaking response payload data intended for another user.
- Alternatively, the victim's callback entry is silently overwritten and their request is never resolved (denial of service until the request times out), analogous to the described "frozen" channel in the bridge.

This is reachable from unprivileged client requests reaching a DON member (no privileged/operator access required), matching the required threat model (unprivileged actor via the internet-facing gateway message envelope/handler path).

### Likelihood Explanation
Exploitation requires only sending two gateway requests with the same `MessageId` while one is still pending (within the `CallbackMaxAgeSec` window, default 120s), which is trivial for any client capable of calling the gateway's legacy trigger endpoint. No special privileges, node compromise, or network-layer position is required — only knowledge/guessing or forced collision of another in-flight `MessageId`, which is entirely attacker-controlled input.

### Recommendation
Bind each `savedCallbacks` entry to the identity of the request's committer (e.g., a gateway-generated unique key, or a composite key of `(MessageId, Sender/session identity)`), reject/queue rather than silently overwrite on collision, and validate on response delivery that the responding node/message context matches the original registrant, not merely that a `MessageId` exists in the map.

### Proof of Concept
1. Client A sends a legacy WebAPI trigger request with `MessageId = "X"`. The gateway calls `HandleLegacyUserMessage`, forwards to DON members, and stores `savedCallbacks["X"] = callbackA` (handler.go:411-419).
2. Before a DON node responds, Client B sends its own legacy trigger request also using `MessageId = "X"`. The gateway overwrites `savedCallbacks["X"] = callbackB` with no collision check.
3. A DON node responds to Client A's original trigger (still echoing `MessageId = "X"`, since node's response method logic does not tie response back to originating requester beyond the message id). `handleWebAPITriggerMessage` finds `savedCallbacks["X"]` (now `callbackB`) and sends the DON node's response — meant for Client A — back to Client B (handler.go:148-161). Client A's callback either never fires (hangs to timeout) or later races and receives Client B's response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
