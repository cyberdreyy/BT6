### Title
V1 asset multiplier setter omits the `type(uint128).max` bound enforced by V2 and documented as an invariant - (File: crates/common/precompiles/src/b20_asset/logic/v1.rs)

### Summary
The B-20 asset precompile's `multiplier` field is documented and interface-declared as bounded by `type(uint128).max` (the `InvalidMultiplier` error doc explicitly states this), and this bound is enforced by `AssetV2::update_multiplier`/`update_ui_multiplier`. However, `AssetV1::update_multiplier` — the only multiplier setter reachable on a V1 token — never checks the upper bound, only rejecting zero.

### Finding Description
The `IB20Asset` ABI doc comment states the invariant explicitly: "A multiplier setter (`updateMultiplier`) was called with a multiplier of zero or above the `type(uint128).max` overflow guard" triggers `InvalidMultiplier`. [1](#0-0) 

V2's implementation of `update_multiplier` enforces exactly that bound:
```
if new_multiplier.is_zero() || new_multiplier > Self::MAX_UI_MULTIPLIER {
    return Err(BasePrecompileError::revert(IB20Asset::InvalidMultiplier {}));
}
``` [2](#0-1) 

But V1's `update_multiplier` — the only privileged setter available on a V1-deployed token, dispatched directly from `dispatch.rs`'s `SC::updateMultiplier` arm — only checks for zero, never checking the upper bound:
```
fn update_multiplier(
    &self,
    token: &mut B20AssetToken<S, A>,
    caller: Address,
    new_multiplier: U256,
    privileged: bool,
) -> Result<()> {
    self.ensure_operator_role(token, caller, privileged)?;
    if new_multiplier.is_zero() {
        return Err(BasePrecompileError::revert(IB20Asset::InvalidMultiplier {}));
    }
    token.accounting_mut().set_multiplier(new_multiplier)?;
    ...
``` [3](#0-2) 

The underlying storage slot for `multiplier` is a full `U256` word (unlike the ERC-8056 `pending_multiplier`, which is explicitly typed `u128`), so an operator can write any `U256` value, including values far above `type(uint128).max`, into `multiplier` on a V1 token: [4](#0-3) [5](#0-4) 

Dispatch routes an `updateMultiplier` call directly to `logic.update_multiplier(...)` with no version-independent bound enforcement layered on top: [6](#0-5) 

This exactly mirrors the reported bug class: an invariant ("maxInvocation"/multiplier bound of 1e6/uint128::max) is implied and documented, and enforced in one code path (`FantiumMinterV1` / `AssetV2`) but not enforced in the sibling setter that actually mutates the shared value (`FantiumNFTV1` setters / `AssetV1::update_multiplier`).

### Impact Explanation
Once a value above `type(uint128).max` is stored in `multiplier`, arithmetic that depends on the multiplier fitting a `uint128` (implicitly assumed elsewhere in the codebase, as evidenced by V2's guard and the `to_scaled_balance` overflow tests) can silently misbehave. Downstream `to_scaled_balance`/`to_raw_balance` conversions multiply raw balances by `multiplier` and divide by WAD; with an out-of-range multiplier the computation can overflow `U256` (causing every scaled-balance/transfer computation depending on the multiplier to permanently revert, effectively freezing all transfers, minting, and balance reads for the token) or produce balances/UI amounts that are wildly incorrect relative to the documented invariant, corrupting displayed/computed supply and balances for a live B-20 asset token. Because `update_multiplier` requires `OPERATOR_ROLE`, this is not exploitable by an arbitrary unprivileged caller, but it is a real correctness/DoS hazard reachable by any account holding the `OPERATOR_ROLE` for that token (a legitimate but constrained privileged actor, analogous to the "setter function" callers in the original report), and it breaks parity between the documented multi-version invariant and actual V1 enforcement — a straightforward "wrong provable output"/permanent-freezing-of-funds class impact once triggered.

### Likelihood Explanation
Likelihood is moderate: it requires an OPERATOR_ROLE-holding account (the only account able to call `updateMultiplier`) to submit a value above `type(uint128).max`, which is a single, ordinary signed transaction with no other preconditions — no race condition, no complex sequence, and V1 assets are a live product code path since decode/dispatch treat V1 as a fully supported precompile version. The absence of any validation makes accidental misuse plausible as well (e.g., an operator meaning to set a smaller value but fat-fingering the WAD-scaled multiplier), since nothing in the setter rejects out-of-range input the way the documented invariant and V2's implementation would suggest.

### Recommendation
Add the same upper-bound check used in `AssetV2::update_multiplier` to `AssetV1::update_multiplier`:
```
if new_multiplier.is_zero() || new_multiplier > U256::from(u128::MAX) {
    return Err(BasePrecompileError::revert(IB20Asset::InvalidMultiplier {}));
}
```
This should be applied consistently to every multiplier-mutating path (both `AssetV1::update_multiplier` and `AssetV2::update_multiplier`/`update_ui_multiplier`) so the enforced bound matches the documented `InvalidMultiplier` invariant declared in the shared ABI comment.

### Proof of Concept
1. Deploy/create a V1 B-20 asset token (pre-Cobalt fork logic, `AssetV1`).
2. Grant `OPERATOR_ROLE` to an address (as is required for any legitimate multiplier update).
3. Call `updateMultiplier(newMultiplier)` with `newMultiplier = U256::MAX` (or any value `> type(uint128).max`).
4. Observe that `AssetV1::update_multiplier` (`crates/common/precompiles/src/b20_asset/logic/v1.rs:630-645`) only checks `is_zero()` and accepts the call, persisting the out-of-range value via `token.accounting_mut().set_multiplier(new_multiplier)`.
5. Subsequent calls to `toScaledBalance`/`scaledBalanceOf`/`totalSupplyUI`-equivalent reads on that V1 token now operate on a multiplier that violates the documented `uint128::max` bound, risking `U256` overflow (permanent revert/freeze of transfer-related reads) or a value that grossly misrepresents scaled balances relative to the codebase's stated invariant — contrast this with the identical call against an `AssetV2` token, which is correctly rejected with `InvalidMultiplier` per `crates/common/precompiles/src/b20_asset/logic/v2.rs:734-736`.
