But `calculate_non_circulating_supply` never even accepts or forwards this parameter — it's structurally impossible to bound, regardless of validator configuration.### Title
`getSupply`/`getLargestAccounts` bypass accounts-index scan byte limit via `calculate_non_circulating_supply` - ([File: runtime/src/non_circulating_supply.rs])

### Summary
`calculate_non_circulating_supply` unconditionally passes `None` as the `byte_limit_for_scan` argument when scanning stake-program accounts, unlike the sibling code path in `rpc.rs::get_filtered_indexed_accounts` which forwards the operator-configured `scan_results_limit_bytes`. Because `getSupply` and `getLargestAccounts` both call `calculate_non_circulating_supply`, a single unprivileged RPC call triggers a fully unbounded index scan and per-account deserialization whose cost scales with however many stake accounts exist on-chain.

### Finding Description
`calculate_non_circulating_supply` calls `bank.get_filtered_indexed_accounts(&IndexKey::ProgramId(stake::program::id()), filter, None)` [1](#0-0)  — the byte-limit parameter is hardcoded to `None`. Compare this with `JsonRpcRequestProcessor::get_filtered_indexed_accounts`, which explicitly reads `self.config.scan_results_limit_bytes` and forwards it as the scan's byte-limit guard [2](#0-1) .

Downstream, `Accounts::load_by_index_key_with_filter` only aborts the scan when `byte_limit_for_scan` is `Some`; with `None`, `accumulate_and_check_scan_result_size` always returns `false` and the scan can never be aborted regardless of accumulated result size [3](#0-2) [4](#0-3) .

Both `getSupply` and `getLargestAccounts` (when a `filter` is specified) call this function directly: `self.calculate_non_circulating_supply(&bank)` [5](#0-4) [6](#0-5) , as does the unauthenticated REST endpoint `/v0/circulating-supply` via `calculate_circulating_supply_async` [7](#0-6) .

For every account returned from the index scan, the code additionally performs `account.deserialize_data::<StakeStateV2>()` [8](#0-7) , so cost scales with both scan size and per-account deserialization work, entirely driven by attacker-authored on-chain data (the number/size of stake accounts) rather than any validator-enforced bound.

Notably, this is not merely a config gap: even when the `ProgramId` secondary index is *disabled*, the fallback path `bank.get_program_accounts(&stake::program::id())` also has no size limit — `Accounts::load_by_program` has no filter/byte-limit parameter at all [9](#0-8) . So the unboundedness is intrinsic to `calculate_non_circulating_supply`, not just a missing config forward, though the ProgramId-index-scan variant described in the question specifically hits `load_by_index_key_with_filter` with `None`.

### Impact Explanation
A single low-rate `getSupply` (or `getLargestAccounts` with a non-circulating filter, or the unauthenticated `/v0/circulating-supply` REST endpoint) call forces the validator to scan and deserialize every stake account in accounts-db, with no cap on scan result bytes. This matches the "unbounded cost for a single low-rate call" impact category — an attacker-controlled volume of on-chain data (many/large stake accounts) directly and unboundedly inflates the CPU/memory cost of one RPC request, independent of the `scan_results_limit_bytes` validator setting that is supposed to bound exactly this class of scan.

### Likelihood Explanation
The attack requires only: (1) an RPC-enabled validator exposing `getSupply`/`getLargestAccounts`/`/v0/circulating-supply` (default-enabled RPC methods, no special flag needed), and (2) the attacker being able to fund creation of many stake accounts, each of which just needs to be a rent-exempt account owned by the stake program (`create_account` + `Initialize` stake instruction, standard permissionless operations). No secondary-index configuration by the operator is required to trigger unboundedness, since even the non-indexed fallback path lacks any limit. This is fully within the unprivileged attacker model (single client, one query per slot-time budget, on-chain data write followed by an RPC read) and is repeatable indefinitely as long as stake accounts persist.

### Recommendation
Thread the configured scan byte limit into `calculate_non_circulating_supply` (e.g., add a `byte_limit_for_scan: Option<usize>` parameter propagated from `JsonRpcConfig::scan_results_limit_bytes`, mirroring what `rpc.rs::get_filtered_indexed_accounts` already does), and apply the same abort-on-exceed behavior. Additionally, apply an equivalent byte/count limit to the non-indexed fallback (`bank.get_program_accounts`) so unboundedness doesn't persist for validators without the ProgramId secondary index enabled.
