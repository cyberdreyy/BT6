### Title
Cross-user response delivery via colliding client-controlled `MessageId` in `handleWebAPITriggerMessage` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Finding Description
`HandleLegacyUserMessage` (the public gateway user endpoint for web-API trigger requests) stores a pending callback for the caller keyed **solely** by the client-supplied `msg.Body.MessageId`: [1](#0-0) 

`MessageId` originates directly from the JSON-RPC request `ID` field supplied by the requester and is never derived from, or bound to, the requester's signer address: [2](#0-1) 

`Message.Validate()` computes `m.Body.Sender` from the signature (`ExtractSigner`), but this `Sender` field is excluded from any map key — it's only used for signature verification/authorization of that individual message, not for keying the response-routing table: [3](#0-2) 

When a DON node later responds, `handleWebAPITriggerMessage` looks the callback up **again purely by `MessageId`**, deletes it, and forwards the response to whichever callback is currently stored under that key: [4](#0-3) 

Because `MessageId` is attacker-chosen (any string up to 128 bytes, only constrained by `Validate()`'s length/null-byte checks), any two distinct signed requests — from two different EOAs — that happen to use the same `MessageId` value will collide in the `savedCallbacks` map. If attacker A sends a trigger request with `MessageId = "X"`, and before the DON responds, attacker/victim B sends any other trigger request also with `MessageId = "X"`, B's callback overwrites A's entry in `h.savedCallbacks["X"]`. When the DON node eventually responds to A's original request (echoing `MessageId = "X"`), `handleWebAPITriggerMessage` delivers that response to B's callback instead of A's, since the map lookup only depends on the colliding `MessageId`, not on the original sender. The signature check on the request only proves who *signed* a given message; it does not prevent two different signers from independently choosing the same message ID.

### Impact Explanation
This is a cross-user response confusion: one user's trigger response (including whatever payload the DON node returns, potentially containing another user's secrets/data flowing through the outgoing-request/target methods that reuse the same `savedCallbacks`/message-id keying pattern) can be delivered to a different, unrelated requester who merely picked (or guessed/brute-forced) the same `MessageId`. This is an authorization/isolation bypass — the invariant that a response can only be routed back to the party that made the corresponding authenticated request is broken because the routing key (`MessageId`) is not bound to the sender. Whether this reaches the "Critical: vault/DKG secret disclosure" tier depends on what payload flows through the trigger response path in a given deployment, but at minimum it constitutes unauthorized disclosure of another user's gateway response data — a request/response impersonation and cross-user data leak.

### Likelihood Explanation
No privilege beyond the ability to sign and send a gateway `web_api_trigger` message is required — this matches the described unprivileged "any internet client with an arbitrary EOA" attacker model. The attacker only needs to choose (or race to guess) the same `MessageId` string as a concurrent legitimate request; if client SDKs use predictable/sequential/short IDs (e.g., counters, UUID-like reused values, or IDs derived from public/observable parameters), collision is trivial to engineer deliberately by simply copying an observed or predicted `MessageId`. The race window is the interval between a legitimate request being saved and its DON response returning, which is normal request latency — easily exploitable by an attacker who can observe or predict ID reuse and time submissions.

### Recommendation
Derive the `savedCallbacks` key (and the ID validated against a node's response) from a combination of `MessageId` **and** the authenticated `Sender` (and ideally `DonId`/method), e.g. `key = sender + ":" + messageId`, so that two different signers can never collide, and validate on the response path that the responding node's message actually corresponds to the same sender that originated the callback.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct two signed `api.Message`s from two different ECDSA keys (`senderA`, `senderB`) but with an identical `Body.MessageId` value.
2. Call `handler.HandleLegacyUserMessage` for A's message with callback `cbA` (a stub capturing whatever response it receives), then for B's message with callback `cbB`, before invoking the node-response path.
3. Simulate the DON node responding to A's original request by constructing an `api.Message`/`jsonrpc.Response` with the same colliding `MessageId`, method `MethodWebAPITrigger`, signed as if from a DON node, and call `handler.HandleNodeMessage`.
4. Assert that `cbB.SendResponse` is invoked (not `cbA`), proving A's response was delivered to B — i.e., assert `savedCallbacks` lookup used only `MessageId`, causing cross-sender response delivery, and that no assertion in the code ties the returned response back to sender A.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
