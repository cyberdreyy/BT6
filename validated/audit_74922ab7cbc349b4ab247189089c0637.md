Note that the Olympus report describes a pure griefing/DoS pattern (blocking future proposals for a grace period), which is explicitly out of scope for this repository per the rules. However, mapping the underlying bug *class* — a low-authority actor causing an authorization mechanism to diverge from its intended live-membership guarantee — to this repo surfaces a genuine, in-scope custody-binding break in the multisig contracts: stale confirmations from removed members are never purged from requests they did not create, letting a request execute while short of real, live-member approvals.

### Title
Stale confirmations from removed multisig members are not invalidated, allowing requests to execute below the live-member confirmation threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
The multisig contracts track approvals in a `confirmations: HashSet` per request and execute the request once `confirmations.len() + 1 >= num_confirmations` [1](#0-0) . When a member (or key) is removed via `DeleteMember`/`DeleteKey`, the cleanup logic only purges confirmations belonging to requests *created* by the removed member — it does not scrub that member's confirmation entries from other requests where they only confirmed [2](#0-1) . As a result, a stale confirmation recorded by a since-removed member still counts toward the threshold, breaking the equality `count(confirmations) == count(confirmations from currently-live members)` that `confirm()` implicitly relies on.

### Finding Description
`delete_member` in `multisig2/src/lib.rs` performs this cleanup:
```
let request_ids: Vec<u32> = self.requests.iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
``` [3](#0-2) 

This filter only matches requests where the removed member is the *original signer/creator* (`r.member == member`); it never inspects or scrubs the `confirmations: HashSet<String>` of requests created by *other* members but confirmed by the member being removed. The identical pattern (`r.signer_pk == pk`) exists in the legacy `multisig/src/lib.rs` `DeleteKey` handler [4](#0-3) .

Meanwhile, `confirm()` never re-validates that existing entries in `confirmations` still correspond to current members — it only checks that the *current* caller is a member and that they haven't already confirmed:
```
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let member = self.current_member()...;
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    assert(!confirmations.contains(&member.to_string()), ...);
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } ...
}
``` [5](#0-4) 

`assert_valid_request` only checks that the *caller* is a member, not that prior confirmers still are [6](#0-5) .

### Impact Explanation
This directly matches the rubric's "confirmations counted versus live members" custody binding. A request (e.g. `Transfer`, `AddKey`, `FunctionCall`) can execute with fewer than `num_confirmations` distinct *current* members approving it, because a stale confirmation left behind by a member removed after confirming (but before the request finished collecting confirmations) is still tallied. This is a multisig request executed below the intended threshold — explicitly listed as a Critical impact (funds moved by a party/quorum not actually entitled to authorize it).

### Likelihood Explanation
Any time a multisig removes a member (turnover, key rotation, compromise response) while other requests are still pending with that member's confirmation attached, this condition arises. Membership changes and pending unconfirmed requests coexisting is an ordinary, expected multisig operational pattern, not an edge case requiring privileged/foundation access beyond normal multisig operation — the remaining members simply need to reach `num_confirmations` counting the stale entry, which requires one fewer live confirmation than intended.

### Recommendation
When removing a member, iterate over *all* pending requests' `confirmations` sets (not just those the member created) and strip any confirmation entries belonging to the removed member. Alternatively, `confirm()` should recompute the confirmation count by filtering `confirmations` against `self.members` before comparing to `num_confirmations`, ensuring only live members' approvals are counted.

### Proof of Concept
1. Deploy multisig with members `[A, B, C, D]`, `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(Transfer{...})` → `confirmations = {A}`.
3. `B` calls `confirm(request_id)` → `confirmations = {A, B}` (2/3).
4. The group executes a separate, properly-confirmed `DeleteMember{B}` request (e.g. B is leaving/compromised) → membership becomes `[A, C, D]`. Because the removed-member cleanup in `delete_member` only targets requests where `B` was the *creator*, the pending Transfer request's confirmations set `{A, B}` is left untouched [3](#0-2) .
5. `C` calls `confirm(request_id)` → `confirmations.len() + 1 = 3 >= num_confirmations(3)` → `execute_request` runs the Transfer, even though only `A` and `C` are actually current members who approved it — one short of the real 3-of-3 (now 3-of-3 live) requirement.
