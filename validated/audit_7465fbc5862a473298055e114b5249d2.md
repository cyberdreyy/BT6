### Title
Loss-adjusted withdraw receipts escape their haircut and are paid at par when a newer request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` looks up the loss-adjusted epoch exclusively via `lastWithdrawRequest[_user]`, which `requestWithdraw` overwrites on every new request. A user who holds a loss-haircutted receipt from epoch `E` can simply file a second withdraw request in epoch `E+1`; the stale epoch-E receipt is then invisible to the loss-adjusted path and is paid out at full par by `_claimFundedWithdrawRequest`, because it remains inside the aggregate `withdrawsRequests[_user]`. This mirrors the kernel bug class: per-epoch claim metadata is effectively "freed" (orphaned) while the underlying entitlement is still live and consumed later through a different handler.

### Finding Description
When `stopEpochWithDuration` underfunds pending receipts, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws` [1](#0-0) . Individual users' claims for that epoch stay in `withdrawsRequestsByEpoch[user][E]` and in the aggregate `withdrawsRequests[user]`, to be settled later by `_claimLossAdjustedWithdrawRequest`, which reads `lossEpoch = lastWithdrawRequest[_user]` [2](#0-1) .

`requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` and adds the new amount to the same aggregate `withdrawsRequests[_user]` [3](#0-2) . Attack sequence (buffer phase, APR > 0 mode):

1. Attacker calls `cdoEpoch.requestWithdraw(amount, tranche)` in epoch E.
2. Honest manager calls `stopEpochWithDuration` with a loss; borrower underfunds → `lossRecoveryPriceByEpoch[E] < RECOVERY_FULL`, `pendingWithdraws = 0`.
3. Attacker calls `requestWithdraw` again in epoch E+1 → `lastWithdrawRequest = E+1`.
4. After one more epoch, attacker calls `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[E+1] == 0` and returns 0 — the epoch-E haircutted receipt is skipped [4](#0-3) .
   - `_claimFundedWithdrawRequest` passes the gate (`epochNumber > lastWithdrawRequest`) and pays `withdrawsRequests[user]`, which still includes the full epoch-E basis, at par via `_transferFundedClaim` [5](#0-4) .

No guard in `requestWithdraw` or `_claimFundedWithdrawRequest` checks for an outstanding earlier loss-adjusted epoch. The same shadowing applies to `_claimDefaultedWithdrawRequest`, which only clears `withdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` [6](#0-5) .

### Impact Explanation
The attacker recovers `claimBasis_E * (1 - lossRecoveryPrice/RECOVERY_FULL)` more than entitled — the exact loss that was supposed to be socialized across pending redeemers. The payout comes from strategy-held underlying backing other users' funded receipts or the isolated `defaultRecoveryReserve` (the reserve guard in `_transferFundedClaim` only protects the reserve bucket, not other claimants' funded balances) [7](#0-6) . Result: direct theft/insolvency proportional to the attacker's share of the loss-adjusted epoch — quantified as `pendingLoss * attackerBasis / pendingBasis`.

### Likelihood Explanation
Requires a `stopEpochWithDuration` loss event (honest manager action) and a second request by the attacker — both routine, unprivileged operations in normal buffer phases. The only precondition is that the attacker held a pending receipt during a loss epoch, which any KYC'd lender can arrange.

### Recommendation
Iterate all epochs with receipts for the user rather than keying off `lastWithdrawRequest`, or track per-epoch loss-adjusted claims independently (e.g., a `lossEpochs` set / flag on `withdrawsRequestsByEpoch`). Alternatively, revert in `requestWithdraw` when `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0` and the receipt is unclaimed, forcing settlement of the haircutted receipt before a new request can shadow it.

function testLossAdjustedReceiptPaidAtPar() external {
    uint256 amount = 10_000 * ONE_SCALE;
    _depositWithUser(attacker, amount, true);
    _startEpochAndCheckPrices(0);

    // epoch E: attacker requests withdraw
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    uint256 basis = IdleCreditVault(address(strategy)).pendingWithdraws();

    // honest manager stops epoch with a loss: borrower underfunds pending receipts
    uint256 funded = basis / 2; // 50% loss on pending receipts
    deal(defaultUnderlying, borrower, funded + _activeShortfall());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, _lossAmount()); // sets lossRecoveryPriceByEpoch[E]

    // epoch E+1: attacker files a new request, shadowing lastWithdrawRequest
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, apr, _expectedFundsEndEpoch());

    // claim: receives full basis for both receipts at par instead of 50% haircut on E
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    assertGt(underlying.balanceOf(attacker) - balPre,
             basis + basis / 2 - 1, 'loss-adjusted receipt escaped haircut');
}

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
