### Title
APR0 withdraw requester can permanently DoS `stopEpoch` once APR is set non‑zero - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analog of "computed amount exceeds cap → unconditional revert → reward/flow permanently blocked". In `IdleCreditVault.prepareStopEpochWithApr0`, any epoch in which `apr0TotalPrincipal != 0` and `unscaledApr != 0` reverts with `NotAllowed()`. Since `apr0TotalPrincipal` is only cleared inside that same function, once it reverts there is no code path that ever resets it, so `stopEpoch` reverts forever while the APR is non‑zero. An unprivileged KYC'd lender arms the trap by making a normal `requestWithdraw` during an APR‑0 epoch; the revert is then triggered by an honest manager's legitimate APR update plus `stopEpoch`.

### Finding Description
`requestWithdraw` routes APR‑0 requests through `_requestWithdrawApr0`, which increments `apr0TotalPrincipal` (<cite> tag: contracts/strategies/idle/IdleCreditVault.sol lines 567-577). At epoch end, the CDO calls `prepareStopEpochWithApr0`, which contains:

```solidity
if (_principal == 0) { return ...; }
if (unscaledApr != 0) { revert NotAllowed(); }   // lines 502-508
```

and only later does `apr0TotalPrincipal = 0;` (line 540). Therefore:

1. Manager sets APR to 0 (APR0 mode).
2. Attacker (KYC'd lender) deposits and calls `requestWithdraw` → `apr0TotalPrincipal > 0`.
3. Manager legitimately raises APR (`setAprs`/`setAprsWithBuffer`) for the next epoch — a routine, honest action.
4. `stopEpoch` calls `prepareStopEpochWithApr0`, hits the `unscaledApr != 0` revert, and reverts.
5. Every subsequent `stopEpoch` reverts identically, because `apr0TotalPrincipal` can never be cleared — there is no settle/cancel path for an unsettled APR0 bucket outside this function. `_settleApr0` only moves `principal` to `settledPrincipal` per user and does not touch `apr0TotalPrincipal`; it is only zeroed at line 540, which is unreachable once the revert at line 507 fires.

This mirrors the gauge bug: the honest path to recover (the analogue of "burn veRAAC and re‑vote") is for the manager to set APR back to 0 and stop the epoch — i.e., the vault is frozen at least until APR is forced to 0, and if APR is required non‑zero for the pool's economics, the freeze is permanent. No existing guard prevents this: `_onlyIdleCDO` does not help (the CDO legitimately calls it), there is no expiry on the APR0 bucket, and `epochNumber` gating in `_settleApr0` cannot run because settlement only happens inside request flows, while `apr0TotalPrincipal` is only decremented at the unreachable line 540.

### Impact Explanation
Temporary (potentially permanent) freezing of the entire epoch flow: `stopEpoch` cannot complete, so borrowers cannot repay, interest cannot be accounted, no new epoch can start, and all queued withdraw/instant-withdraw claims plus LP deposits are stuck. The entire contract TVL is frozen for as long as the manager cannot or does not set `unscaledApr` back to 0. If APR is locked > 0 by governance or by configuration requirements, freezing is permanent.

### Likelihood Explanation
Low‑to‑medium. Requires an APR0 epoch to be active (a supported mode per `prepareStopEpochWithApr0` docs) and a manager to later set a non‑zero APR while an APR0 request is pending — a routine operational sequence. The attacker only needs to pass KYC and place one `requestWithdraw`, which is a normal user action, to arm the grief.

### Recommendation
Cap/settle rather than revert (same fix shape as the external report). Either:
- settle the APR0 bucket at the last known `apr0RateByEpoch`/zero rate instead of reverting when `unscaledApr != 0`, then still execute `apr0TotalPrincipal = 0`; or
- revert the APR change itself (`setApr` should revert if `apr0TotalPrincipal != 0 && _apr != 0`), keeping the two state transitions atomic so the manager gets immediate feedback instead of bricking `stopEpoch` later.

### Proof of Concept
A Foundry fork PoC (adapt the harness used in `test/foundry/IdleCreditVault.t.sol`, e.g. the APR0 tests around `testStopEpochMintInterestWithPendingWithdraws`):

```solidity
// 1. owner/manager configures APR0 mode
vm.prank(manager);
cv.setAprs(0, 0);               // unscaledApr = 0

// 2. KYC'd attacker deposits and requests withdraw during APR0 epoch
_depositWithUser(attacker, 10_000 * ONE_SCALE, true);
_startEpochAndCheckPrices(0);
vm.prank(attacker);
cdoEpoch.requestWithdraw(0, address(AAtranche));
assertGt(cv.apr0TotalPrincipal(), 0);

// 3. honest manager raises APR for the next cycle
vm.prank(manager);
cv.setAprs(10e18, scaledApr);

// 4. epoch matures; stopEpoch reverts — and reverts forever
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(10e18, 0);

// 5. repeat: still reverts, apr0TotalPrincipal never cleared
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(10e18, 0);
assertGt(cv.apr0TotalPrincipal(), 0); // bucket can never be closed while APR > 0
```

Uncertainty: this assumes the CDO's `stopEpoch` calls `prepareStopEpochWithApr0` unconditionally (it is `_onlyIdleCDO` and reads `apr0TotalPrincipal`, which holds pending APR0 requests across epochs). I could not fully read `IdleCDOEpochVariant.stopEpoch` in this session — the grep confirmed the functions exist but not the call site; if `prepareStopEpochWithApr0` is only invoked under a flag that the manager can toggle off, the DoS is mitigable but still requires APR=0 or flag manipulation to unfreeze.
