### Title
v1 `validate_tenure_change_payload` misses locally-accepted-only tenure blocks, splitting signers from v2 during a version transition - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
`v1.rs`'s `validate_tenure_change_payload` queries `signer_db.get_last_globally_accepted_block` to detect a duplicate tenure-change block, while `v2.rs`'s equivalent queries `signer_db.get_last_signed_block` (which additionally covers `LocallyAccepted`). During a mixed v1/v2 rollout, a block that has crossed the 70% signature threshold (`LocallyAccepted`) but has not yet been processed/confirmed by the node (`GloballyAccepted`) is invisible to v1's check but visible to v2's, so the two active-version cohorts can reach opposite `DuplicateBlockFound` verdicts on the same competing tenure-change proposal for the same tenure.

### Finding Description
`SignerDb::get_last_signed_block` matches `state IN (GloballyAccepted, LocallyAccepted)` [1](#0-0) , while `SignerDb::get_last_globally_accepted_block` matches only `state = GloballyAccepted` [2](#0-1) .

`v1::SortitionsView::validate_tenure_change_payload` uses the globally-accepted-only lookup to decide `DuplicateBlockFound` for a tenure-change block targeting `block.header.consensus_hash` [3](#0-2) . `v2::GlobalStateView::validate_tenure_change_payload` uses `get_last_signed_block` for the identical check and its own comment explains the rationale: only signed blocks (locally or globally accepted) should count, because a pre-commit carries no signature [4](#0-3) . The v2 test suite explicitly documents this as a fix for a real gap in the old (v1-style) logic: "previously, the check used `get_last_globally_accepted_block`, which would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change" [5](#0-4) . `docs/signer-flows.md` independently documents the same semantic split between v1 and v2 [6](#0-5) .

Exploit flow: the attacker (a single winning miner slot) proposes tenure-change block A for tenure T and gossips it broadly; enough signer weight signs A so it reaches `LocallyAccepted` in many signers' `signer_db`, but the node has not yet processed it (`GloballyAccepted` still absent). Before that settles, the attacker gossips a second, competing tenure-change block B for the same tenure T (e.g., different transaction set) to the network. `determine_active_signer_protocol_version` is computed independently per signer from gossiped `StateMachineUpdate`s and can transiently disagree across the fleet during a version rollout (a separately-documented condition assumed as a precondition here). Signers currently active on v1 call `get_last_globally_accepted_block(T)` → `None` → the `DuplicateBlockFound` guard is skipped, and B proceeds to the remaining (potentially passing) checks. Signers active on v2 call `get_last_signed_block(T)` → finds A (`LocallyAccepted`) → correctly rejects B with `DuplicateBlockFound`. The v1 cohort's `check_block_against_state` no longer distinguishes it from a legitimate proposal, so those signers can proceed to sign B while the v2 cohort has already signed/is signing A — two conflicting, signed tenure-change blocks for the same tenure T exist in the wild.

### Impact Explanation
This breaks the uniqueness/canonicity property that only one tenure-change block should ever be validly signed per tenure. If the v1-active weight is sufficient, block B can independently reach the 70% signature threshold, giving the network two "signed" competing blocks for the same tenure T (A signed by v2 signers, B signed by v1 signers) — a chain-safety violation matching the Critical category ("a signer signing an invalid, non-canonical, or conflicting block"). The condition is repeatable for every tenure boundary that falls inside the version-transition window, not a one-shot glitch.

### Likelihood Explanation
Preconditions: (1) an active v1/v2 mixed signer fleet mid-rollout, (2) transient disagreement in `determine_active_signer_protocol_version` across signers (a separately-flagged, real condition since each signer computes this independently from gossiped `StateMachineUpdate`s with no atomic synchronization), and (3) one block in the tenure reaching `LocallyAccepted` before global acceptance — the ordinary/expected state during normal block signing, not attacker-engineered. The attacker only needs to win a single miner slot and gossip two competing tenure-change proposals, both attacker capabilities explicitly in scope. No signer key, auth token, or majority collusion is required — the vulnerable signers act per their own (buggy) protocol logic.

### Recommendation
Make v1's `validate_tenure_change_payload` duplicate-block check use the same signed-block semantics as v2 (`get_last_signed_block` instead of `get_last_globally_accepted_block`), or gate the entire tenure-change duplicate check on a version-independent shared helper so both v1 and v2 signers always agree on `DuplicateBlockFound` for identical signer_db state. Alternatively, disable/skip v1 validation entirely once any node in the fleet has moved past a version threshold that requires this semantic, ensuring no cohort runs the weaker check during a transition.
