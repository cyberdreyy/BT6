### Title
Cost-tracker `block_cost` uses wrapping `AtomicU64::fetch_sub` while per-account costs use `saturating_sub`, allowing a mismatched remove to silently wrap `block_cost` to a huge value and permanently jam a bank's cost tracker - (File: cost-model/src/cost_tracker.rs)

### Summary
`CostTracker::sub_transaction_execution_cost` decrements per-account costs with `saturating_sub` but decrements the shared `block_cost` counter with a raw `AtomicU64::fetch_sub`, which wraps on underflow instead of saturating. [1](#0-0) 
This is structurally the same bug class as the yVaultLPFarming report: a value that is expected to only move consistently with its counterpart (there, `previousBalance` vs `currentBalance`; here, `block_cost` vs `cost_by_writable_accounts`) can be pushed inconsistent by an external caller, and the resulting broken invariant then poisons all future operations that depend on it (there, `withdraw`; here, `would_fit`/transaction admission for the rest of the slot).

### Finding Description
`CostTracker` tracks both a global `block_cost` (an `AtomicU64` wrapped in `SharedBlockCost`) and a `HashMap<Pubkey, u64>` of per-writable-account costs. Both are supposed to move in lock-step: `add_transaction_execution_cost` adds the same `adjustment` to both, and `sub_transaction_execution_cost` is supposed to subtract the same `adjustment` from both. [2](#0-1) 

However, the two counters use different underflow semantics:
- Per-account costs: `account_cost.saturating_sub(adjustment)` — clamps at 0.
- `block_cost`: `self.block_cost.fetch_sub(adjustment)` via `SharedBlockCost::fetch_sub`, which is a plain `AtomicU64::fetch_sub` — wraps around on underflow (standard Rust `u64` wrapping arithmetic for atomics, no panic, no saturation). [3](#0-2) 

`remove()`/`remove_transaction_cost()` is called with the exact `tx_cost.sum()` that was previously added via `try_add()` in the normal path (`try_add_processed_transaction_costs` in banking_stage) and this looks internally consistent, but this is only guaranteed to be correct when calls to `add` and `remove` are always exactly paired 1:1 with identical costs, on the same `CostTracker` instance, in the order the code assumes. The code path is not internally protected against any mismatch (e.g. an `adjustment` passed to `remove`/`sub_transaction_execution_cost` that is larger than what was actually added to `block_cost` for that entity) — there is no assertion, checked/saturating arithmetic, or invariant check comparing `block_cost.load()` against the corresponding `cost_by_writable_accounts` totals. Because of the wrapping subtraction, any discrepancy silently produces a `block_cost` value near `u64::MAX` instead of erroring loudly.

Once `block_cost` wraps to a huge value, `would_fit()` computes `self.block_cost().saturating_add(cost) > self.limits.block_cost`, which will now be true for essentially any transaction cost, causing `CostTrackerError::WouldExceedBlockMaxLimit` to be returned for every subsequent transaction attempted against that bank/slot's cost tracker instance. [4](#0-3) 
This mirrors the reported bug class exactly: an unexpected, ill-guarded decrease/mutation of a value that other logic (`would_fit`, i.e. the equivalent of `withdraw`) unconditionally trusts, breaking all subsequent legitimate operations dependent on it — in this case starving the block/slot of further transaction ingestion via `check_block_cost_limits` in the replay/execute path. [5](#0-4) 
and via `try_add_processed_transaction_costs`/`remove_added_transaction_costs` in the banking stage leader path. [6](#0-5) [7](#0-6) 

### Impact Explanation
If any code path removes a transaction's cost from the tracker with an `adjustment` value larger than what remains attributed to `block_cost` for that tracker instance (due to any future refactor, a race, or a logic bug in matching add/remove calls across the `all_or_nothing`, `remaining_batch_error`, and `remove_added_transaction_costs` rollback branches), `block_cost` silently wraps to a near-`u64::MAX` value with no panic and no logged error. From that point forward, every transaction submitted to that specific bank/cost-tracker will be rejected with `WouldExceedMaxBlockCostLimit`, effectively halting transaction ingestion/production for the remainder of that slot — a self-inflicted denial-of-service on block production/replay that is silent (no crash, no obvious log signal) and hard to diagnose. This is analogous in severity to the H-06 finding: a quiet accounting inconsistency that breaks a downstream, security-critical gate (`would_fit`) for the remaining lifetime of the object.

The exploitability today hinges entirely on whether the current call sites keep add/remove perfectly paired; from what is reachable in the index, the shipped call sites (`try_add_processed_transaction_costs`, `remove_added_transaction_costs`, `check_block_cost_limits`) appear to pair costs 1:1 by construction. I was not able to fully trace every retry/rollback and cross-batch interleaving (e.g., interaction between banking-stage retry paths and the replay-stage `execute_batch` path operating on the same bank) to prove a concrete reachable mismatch, so likelihood/reachability of an actual trigger cannot be confirmed with the available index.

### Likelihood Explanation
Low-to-uncertain under current call sites, since adds and removes appear to be paired by construction in the code that was inspected. However, the underlying defect — using non-saturating (wrapping) arithmetic for `block_cost` while using saturating arithmetic for the semantically equivalent per-account costs — is a real inconsistency that provides no defense-in-depth: any future code change, additional call site, or subtle interleaving bug that breaks the add/remove pairing invariant will manifest as a silent, slot-long denial of transaction admission rather than a loud, easily-diagnosed failure.

### Recommendation
Make `SharedBlockCost::fetch_sub` (and by extension `sub_transaction_execution_cost`) use `saturating_sub` semantics consistent with the per-account cost tracking, e.g. via a compare-and-swap loop or `fetch_update` that clamps at zero, matching `cost_by_writable_accounts`'s `saturating_sub` behavior. Additionally, add a debug-assertion or metrics counter when a subtraction would have underflowed, so any add/remove pairing bug is surfaced immediately instead of silently corrupting the block-cost gate for the rest of the slot.

### Proof of Concept
Not independently reproducible from the indexed code alone since all visible call sites pair `add`/`remove` with identical `tx_cost.sum()` values; however, the underflow behavior itself can be demonstrated directly against the unit:
```rust
// Minimal illustration of the wrap using existing SharedBlockCost API
let shared = SharedBlockCost::new(10);
shared.fetch_sub(50); // wraps: load() now returns u64::MAX - 39 instead of saturating at 0
assert!(shared.load() > u64::MAX / 2); // block_cost now effectively "full" forever
``` [8](#0-7) 
Any downstream code path that ever calls `CostTracker::remove`/`sub_transaction_execution_cost` with a cost larger than what is currently tracked for `block_cost` (whether via a future bug, a race between concurrent removal paths, or a logic error in one of the retry/rollback branches in `consumer.rs`) will trigger this wraparound and permanently degrade block production via `would_fit`. [9](#0-8)

    fn add_transaction_execution_cost(
        &mut self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
        adjustment: u64,
    ) -> u64 {
        let mut costliest_account_cost = 0;
        for account_key in tx_cost.writable_accounts() {
            let account_cost = self
                .cost_by_writable_accounts

            costliest_account_cost = costliest_account_cost.max(*account_cost);

        costliest_account_cost
    }

/// Wrapper around blockcost to allow fast sharing of the value without locking.
/// Value is read-only outside of cost-tracker.
#[derive(Debug, Clone)]
pub struct SharedBlockCost(Arc<AtomicU64>);

impl SharedBlockCost {
    pub fn new(value: u64) -> Self {
        Self(Arc::new(AtomicU64::new(value)))
    }

    fn fetch_add(&self, value: u64) -> u64 {
        self.0.fetch_add(value, Ordering::Release)
    }

    fn fetch_sub(&self, value: u64) -> u64 {
        self.0.fetch_sub(value, Ordering::Release)
    }

    pub fn load(&self) -> u64 {
        self.0.load(Ordering::Acquire)
    }
}

fn check_block_cost_limits<Tx: TransactionWithMeta>(
    bank: &Bank,
    tx_costs: &[Option<TransactionCost<'_, Tx>>],
) -> TransactionResult<()> {
    let mut cost_tracker = bank.write_cost_tracker().unwrap();
    for tx_cost in tx_costs.iter().flatten() {
        cost_tracker
            .try_add(tx_cost)
            .map_err(TransactionError::from)?;
    }

    Ok(())

    fn try_add_processed_transaction_costs<'a, Tx: TransactionWithMeta>(
        bank: &Bank,
        transactions: &'a [Tx],
        mut transaction_costs: Vec<Option<TransactionCost<'a, Tx>>>,
        processing_results: &mut [TransactionProcessingResult],
        processed_counts: &mut ProcessedTransactionCounts,
        error_counters: &mut TransactionErrorMetrics,
        all_or_nothing: bool,
    ) -> (Vec<Option<TransactionCost<'a, Tx>>>, Vec<RetryableIndex>) {
        let mut retryable_transaction_indexes = Vec::with_capacity(processing_results.len());
        let mut all_or_nothing_error = None;
        let mut remaining_batch_error = None;
        let mut cost_tracker = bank.write_cost_tracker().unwrap();

        for (index, transaction_cost) in transaction_costs.iter_mut().enumerate() {
            let Some(cost) = transaction_cost.as_ref() else {
                continue;
            };

            match cost_tracker.try_add(cost) {
                Ok(_) => {}
                Err(err) => {
                    let transaction_error = TransactionError::from(err);
                    *transaction_cost = None;
                    if all_or_nothing {
                        all_or_nothing_error = Some((index, transaction_error));
                        break;
                    } else {
                        remaining_batch_error = Some((index, transaction_error));
                        break;
                    }
                }
            }
        }

        if let Some((failed_index, transaction_error)) = all_or_nothing_error {
            for transaction_cost in transaction_costs[..failed_index].iter().flatten() {
                cost_tracker.remove(transaction_cost);
            }
            transaction_costs.iter_mut().for_each(|cost| *cost = None);
            retryable_transaction_indexes.clear();

            Self::cancel_processed_transactions_for_retry(
                transactions,
                processing_results,
                processed_counts,
                error_counters,
                &mut retryable_transaction_indexes,
                failed_index,
                &transaction_error,
                0,
            );
        } else if let Some((failed_index, transaction_error)) = remaining_batch_error {
            transaction_costs[failed_index..]
                .iter_mut()
                .for_each(|cost| *cost = None);

            Self::cancel_processed_transactions_for_retry(
                transactions,
                processing_results,
                processed_counts,
                error_counters,
                &mut retryable_transaction_indexes,
                failed_index,
                &transaction_error,
                failed_index,
            );
        }

        (transaction_costs, retryable_transaction_indexes)
    }
