### Title
Unprivileged shareholder can reset another shareholder's beneficiary mapping in `vesting::reset_beneficiary` - (File: `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary
`reset_beneficiary(account, contract_address, shareholder)` is meant to let either the contract admin, or the specific shareholder themselves, clear their own beneficiary entry. The authorization check, however, only verifies that the caller (`signer::address_of(account)`) is *some* shareholder registered in the vesting contract's pool — via `assert_shareholder(contract_address, addr)` — rather than verifying that the caller *is* the `shareholder` argument being targeted for reset.

### Finding Description
The function pattern is:
```
let addr = signer::address_of(account);
let vesting_contract = borrow_global<VestingContract>(contract_address);
if (addr != vesting_contract.admin) {
    assert_shareholder(contract_address, addr);
};
...
simple_map::remove(&mut vesting_account.beneficiaries, &shareholder);
```
`assert_shareholder` only checks that `addr` (the caller) participates in the pool, without cross-checking `addr == shareholder`. This means any of the multiple shareholders in a shared vesting contract can call `reset_beneficiary(contract_address, other_shareholder_addr)` and clear that other shareholder's beneficiary mapping, even though they have no admin role and are not that shareholder.

### Impact Explanation
Removing another shareholder's beneficiary entry causes future `distribute`/vest payouts for that shareholder to fall back to the shareholder's own account (the default), which by itself isn't a direct theft, but it does constitute unauthorized, wrong-role control over another shareholder's beneficiary configuration — satisfying the "Wrong-role control over ... beneficiary state without already holding that role" impact category. If a shareholder had deliberately configured a beneficiary (e.g., a custodial/payout wallet) for operational reasons, an unrelated co-shareholder can silently undo that configuration, potentially misdirecting subsequent distributions away from the intended payout destination.

### Likelihood Explanation
Any account already listed as a shareholder in the same vesting contract (a low, easily obtainable privilege in vesting pools with multiple shareholders) can trigger this with a single unprivileged entry-function call — no admin key or special role needed.

### Recommendation
In `reset_beneficiary`, change the non-admin branch to require `addr == shareholder` in addition to (or instead of) `assert_shareholder(contract_address, addr)`, i.e.:
```
if (addr != vesting_contract.admin) {
    assert!(addr == shareholder, error::permission_denied(ENOT_ADMIN_OR_SHAREHOLDER));
    assert_shareholder(contract_address, addr);
};
```
