### Title
Unprivileged APR0 withdraw receipt permanently reverts `stopEpoch` once APR is raised - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` hard-reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0` [1](#0-0) . Any KYC-passing lender can open an APR0 withdraw receipt during a 0%-APR epoch via `IdleCDOEpochVariant.requestWithdraw` → `IdleCreditVault.requestWithdraw` → `_requestWithdrawApr0`, which credits `apr0Users[_user]` and `apr0TotalPrincipal` [2](#0-1) . When the honest manager later sets a non-zero APR for the next epoch (a routine, expected action), `prepareStopEpochWithApr0` reverts inside the stop-epoch flow, so `stopEpoch`/`stopEpochWithDuration` cannot complete while that receipt is open — freezing all vault funds and all queued withdrawals. This is the credit-vault analog of CVE-2026-50889: a small, crafted attacker input (a dust APR0 withdraw request) poisons a global state-transition routine.

### Finding Description
The epoch state machine assumes APR0 receipts only exist while `unscaledApr == 0`, but nothing enforces that invariant across epochs:

1. `requestWithdraw` routes to `_requestWithdrawApr0` only when `unscaledApr == 0`, recording per-user `principal`/`principalEpoch` and incrementing `apr0TotalPrincipal` [3](#0-2) .
2. The receipt stays "open" for a full epoch: `_settleApr0` returns early while `reqEpoch >= epochNumber`, and `apr0TotalPrincipal` is only cleared inside `prepareStopEpochWithApr0` at the *end* of the stop-epoch path [4](#0-3) [5](#0-4) .
3. `prepareStopEpochWithApr0` checks the fast-path `_principal == 0` first, then reverts if `unscaledApr != 0` [1](#0-0) .
4. APR for the next epoch is set via `setAprsWithBuffer`/`setApr`, which writes `unscaledApr` with only a `maxApr` upper bound and no check that open APR0 receipts exist [6](#0-5) .

An attacker holding any tranche balance requests a withdraw (dust amount suffices, e.g. 1 wei of tranche → `_requestWithdrawApr0` still sets `apr0TotalPrincipal > 0`). After `epochEndDate`, the manager calls `stopEpoch(_apr, _interest)` with a positive APR. Any ordering in which `unscaledApr` is non-zero when `prepareStopEpochWithApr0` runs — either because the manager/orchestrator pre-sets the next epoch APR via `setAprsWithBuffer`, or because `stopEpoch` writes the APR before calling `prepareStopEpochWithApr0` — makes the whole transaction revert. The attacker front-runs/griefs every stop attempt for the cost of one dust request per epoch; the request itself can be recycled each epoch since it is never force-settled.

### Impact Explanation
Temporary freezing of all vault funds: while the revert holds, no stopEpoch can finalize, so no withdraw receipt can mature (`_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest` [7](#0-6) ), no new epoch can start, and the entire TVL plus pending/queued withdrawals in `IdleCDOEpochQueue` remain locked. The freeze persists until either the APR0 requester claims (which itself requires a settled epoch — circular) or the honest manager discovers and applies the workaround of setting `unscaledApr` back to 0 via `setAprs(0, ...)`, which forfeits the intended yield for that epoch and may itself be impossible if APR is only written inside the same reverting `stopEpoch` call. Loss is the full TVL duration-locked plus forfeited interest, with zero attacker cost beyond a dust tranche position.

### Likelihood Explanation
Medium-high. Attacker requirements are minimal: a KYC-passing wallet (or none if keyring is unset [8](#0-7) ) and a dust tranche balance during any epoch configured at 0% APR (APR0 mode is a first-class supported configuration per `setAprs`/`_requestWithdrawApr0`). The trigger condition — manager raising APR above 0 — is the normal way pools exit an APR0 configuration, so the poisoned state is encountered in the ordinary course of operations rather than requiring exotic sequencing. Caveat: the exact revert depends on whether `stopEpoch` updates `unscaledApr` before or after `prepareStopEpochWithApr0`; if it always writes APR after, the attack additionally requires the manager/orchestrator (`IdleCreditVaultManagerOrchestrator` exposes `setAprsWithBuffer`) to pre-stage the next APR, which is a documented workflow.

### Recommendation
In `prepareStopEpochWithApr0`, do not revert on `unscaledApr != 0` when APR0 principal is open. Instead settle the open bucket at the realized rate for its request epoch (or at zero interest if the APR change invalidates it) before closing `apr0TotalPrincipal`, mirroring how `apr0RateByEpoch[epochNumber]` already handles the accrual [9](#0-8) . Alternatively, gate `setApr`/`setAprsWithBuffer` to reject non-zero APR while `apr0TotalPrincipal != 0`, pushing the constraint to the privileged action rather than the permissionless state transition — but ensure `stopEpoch` can always proceed by settling the residual bucket at 0.

### Proof of Concept
Foundry fork PoC sketch against `IdleCreditVault` + `IdleCDOEpochVariant` (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testPocApr0ReceiptBlocksAprRaise() external {
    // 1. Configure vault at APR 0 (as in testApr0WithdrawGetsInterestAtStopEpoch)
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    // 2. Honest LP deposits; attacker deposits dust
    uint256 amount = 10000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    address attacker = makeAddr("attacker");
    _depositWithUser(attacker, 1, true); // dust

    // 3. Epoch 0 runs at APR 0
    _startEpochAndCheckPrices(0);

    // 4. Attacker files a dust APR0 withdraw request -> apr0TotalPrincipal > 0
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // 5. Manager sets next-epoch APR > 0 (routine exit from APR0 config)
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(initialProvidedApr, initialProvidedApr);

    // 6. stopEpoch reverts inside prepareStopEpochWithApr0 -> epoch cannot close
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(initialProvidedApr, 0);
    // All TVL + pending withdrawals frozen while unscaledApr != 0 && apr0TotalPrincipal != 0
}
```

Note: I could not fully verify the internal ordering of APR update vs. `prepareStopEpochWithApr0` inside `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` within this pass; step 5 assumes the manager-orchestrated pre-set flow (or a stopEpoch that writes APR before preparing APR0). If `stopEpoch` always writes APR strictly after `prepareStopEpochWithApr0` and never reads a pre-set value, the attack degrades to forcing a one-time revert whenever ops pre-stage APR — still a valid temporary-freeze analog, but the PoC should confirm the call order first.
