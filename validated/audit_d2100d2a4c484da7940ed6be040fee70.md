### Title
Threshold-triggered signature aggregation broadcasts a block without re-validating against local chainstate, unlike the pre-commit/validate-ok paths — ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_pre_commit` and `handle_block_validate_ok` both re-check the block against the signer's current chainstate view (`check_block_against_signer_db_state` / the conflict/freshness logic) *immediately before* transitioning a block to `LocallyAccepted`/`PreCommitted` and signing/broadcasting it. The threshold-triggered acceptance path, `store_and_process_block_signature`, does not. It reaches the 70% weight threshold purely from previously-collected `block_signatures` rows (which may include entries replayed from `signer_pending_signature_responses` — signatures that arrived and were parked *before* this signer had ever seen or evaluated the block), and on reaching threshold calls `block_info.mark_locally_accepted(true)` and `broadcast_signed_block` with no re-check that this block doesn't conflict with something the signer has already accepted/signed for the same height/tenure.

### Finding Description
The state-machine has an explicit rule, applied consistently in two of the three "sign/accept" chokepoints, but missing in the third:

- `handle_block_validate_ok` (`stacks-signer/src/v0/signer.rs:1946-1959`) calls `check_block_against_signer_db_state` right before `mark_pre_committed()`.
- `handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs:1345-1421`) calls `check_block_against_signer_db_state` *and* an additional conflict/freshness check (`get_signed_conflicts`, `reorg_permit_stands`, `conflict_still_blocks`) right before `mark_locally_accepted(false)` — explicitly commented as necessary because "the chain and signer db state may have changed materially since this block passed the proposal-time checks."
- `store_and_process_block_signature` (`stacks-signer/src/v0/signer.rs:2443-2538`) performs **no equivalent recheck**. It only checks `block_info.signed_group.is_some()` (already-processed guard) and the raw signature-weight threshold, then calls `block_info.mark_locally_accepted(true)` and `broadcast_signed_block`.

Compounding this, the signatures counted toward that threshold are not necessarily fresh, real-time votes cast against a validated view of the chain: `handle_block_signature` stores any signature whose signer address is `is_valid_signer` for the reward cycle into `signer_pending_signature_responses` when the block itself is not yet known locally (`add_pending_block_signature_response`, `stacks-signer/src/signerdb.rs:2520-2544`). These are later replayed verbatim via `process_pending_responses_for_block` → `store_and_process_block_signature` (`stacks-signer/src/v0/signer.rs:1720-1725`, `1766-1779`) the instant a matching-hash proposal arrives — i.e., analogous to the ERC-20 report's "fake balance parked for a not-yet-existing token that activates the moment the real token appears": stale/early signatures are parked for a not-yet-known block and are trusted at face value the moment a block with that hash is proposed, with no re-verification that the chainstate is still consistent with signing it.

Because `mark_locally_accepted(true)` (the `group_signed` branch) does not set `self.valid`, a block can be moved to `BlockState::LocallyAccepted` and broadcast by this signer while `block_info.valid` is still `None` (i.e., this signer's own node has not even returned a validation verdict) or while the signer's own DB state has since accepted a conflicting sibling block at the same height. `check_state` (`stacks-signer/src/signerdb.rs:314-329`) permits the `Unprocessed -> LocallyAccepted` transition, so nothing in the state machine itself blocks this.

### Impact Explanation
This breaks the "aggregated-weight vs. verified-accepts" equality: reaching the 70% signature-weight threshold should mean the local signer independently confirms the block is still consistent with its own chainstate before treating it as accepted and broadcasting it (as is done at the pre-commit and validate-ok chokepoints). Instead, the final signature-aggregation gate skips this recheck, allowing a signer to broadcast (and cause the node to be pushed) a block that conflicts with a block it has already locally/globally accepted at the same height/tenure, purely because stale or delayed signatures accumulated past threshold. This falls under the specified Critical impact category: "a signer signing an invalid, non-canonical, or conflicting block."

### Likelihood Explanation
Triggering this only requires normal gossip timing/latency (pending-signature caching is a first-class, always-on code path) plus a proposal reorg/conflict scenario that the pre-commit path is explicitly designed to guard against (per the code comments at lines 1368-1382, 1398-1401). No majority of signers or key compromise is required beyond what any legitimate signer subset already provides through ordinary signature gossip; the flaw is the absence of a recheck at one specific aggregation chokepoint, not a forgery.

### Recommendation
Add the same chainstate/conflict recheck (`check_block_against_signer_db_state`, and ideally the `get_signed_conflicts`/`reorg_permit_stands`/`conflict_still_blocks` freshness logic used in `handle_block_pre_commit`) inside `store_and_process_block_signature` immediately before calling `mark_locally_accepted(true)` and `broadcast_signed_block`, so that reaching the signature-weight threshold from possibly-stale or gossip-replayed signatures cannot bypass the conflict checks enforced everywhere else in the state machine.

### Proof of Concept
1. Signer S receives (or has parked in `signer_pending_signature_responses` from earlier gossip) enough valid, correctly-signed `BlockAccepted` messages for hash `H` (block B) from other signers, reaching ≥70% weight, but S has not yet itself validated B (`handle_block_proposal` for B arrives late, or was recently proposed and pending validation).
2. Concurrently, S has already `mark_locally_accepted`/pre-committed a different, conflicting block B′ at the same `chain_length`/tenure (a legitimate scenario the pre-commit path defends against via `get_signed_conflicts`).
3. When B's proposal reaches S, `process_pending_responses_for_block` replays the stashed signatures into `store_and_process_block_signature` (`stacks-signer/src/v0/signer.rs:1766-1779`).
4. Threshold is already met from the replayed signatures; `store_and_process_block_signature` calls `block_info.mark_locally_accepted(true)` and `broadcast_signed_block` (`stacks-signer/src/v0/signer.rs:2528-2537`) without ever calling `check_block_against_signer_db_state` or the conflict checks used in `handle_block_pre_commit`.
5. S broadcasts B as accepted/pushes it to the node even though it conflicts with B′, which S has already accepted — a signer participating in relaying/asserting acceptance of a conflicting block, contrary to the equivocation-guard behavior enforced at the other two chokepoints.
