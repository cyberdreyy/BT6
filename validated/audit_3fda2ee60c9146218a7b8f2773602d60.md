### Title
Race window between process creation and job-object assignment allows early-forked children to escape job-object containment - (File: helpers/process/job_windows.go)

### Summary
`osCmd.Start()` starts the process with `c.internal.Start()` and only *afterwards* calls `AssignPidToJobObject` to attach it to the Windows job object; any child processes the job's root process spawns before that assignment completes are never made members of the job. Since `windowsKiller.ForceKill`'s `closeJobObject()` only terminates processes that are members of the job object, such early-spawned children are not guaranteed to be killed by job-object teardown.

### Finding Description
In `helpers/process/job_windows.go`: [1](#0-0) 

`c.internal.Start()` uses the standard (non-suspended) Windows `CreateProcess` semantics, meaning the job's entrypoint binary begins executing immediately. Only after `Start()` returns does the runner call `AssignPidToJobObject(c.internal.Process.Pid, c.jobObject)`. If the entrypoint script/binary forks or execs a detached child during this window, that child is created before the parent is a member of the job object, so it is never captured — Windows job-object semantics only auto-associate children of processes that are *already* job members at the time the child is spawned. On failure or delay, the assignment error is only logged via `Logger.Warn` and otherwise ignored: [2](#0-1) 

When the job is cancelled, `windowsKiller.ForceKill` (`helpers/process/killer_windows.go`) calls `taskKill` (which invokes `taskkill /F /T /PID <pid>`) and then `pk.cmd.closeJobObject()`: [3](#0-2) 

`closeJobObject()` calls `windows.CloseHandle(c.jobObject)`, which (combined with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) only terminates processes that are actual members of that job object: [4](#0-3) [5](#0-4) 

This is a real, narrow race condition inherent to the chosen `CreateProcess` → `AssignProcessToJobObject` ordering. The canonical, race-free approach on Windows is to create the process suspended (`CREATE_SUSPENDED`), assign it to the job object, and only then resume its main thread — no such suspend/resume logic exists anywhere in this codebase (confirmed no `CREATE_SUSPENDED`/`ResumeThread` usage).

However, `taskKill` invokes `taskkill /F /T /PID <pid>`, where `/T` instructs Windows to also terminate the entire descendant process tree rooted at that PID (as tracked by parent-PID bookkeeping), independent of job-object membership. This is a mitigating, best-effort control that runs *before* `closeJobObject()` in `ForceKill`, and would catch most children spawned in the race window as long as the parent-PID record is still valid (i.e., no PID has been reused in the interim). This significantly narrows — but does not formally eliminate — the exploitability of the race, since `taskkill /T`'s parent-PID tracking is a best-effort Windows mechanism, not a hard guarantee (e.g., a child that immediately re-parents itself via `CREATE_BREAKAWAY_FROM_JOB`-style detachment, double-forks, or otherwise obscures its parent PID before `taskkill /T` runs could still survive).

### Impact Explanation
If exploited, a job-controlled entrypoint script that spawns a detached child in the microsecond-scale window between `Start()` returning and `AssignPidToJobObject` completing could leave that child running on the shared runner host after job cancellation, consuming host resources (CPU, memory, disk, network) indefinitely and potentially interfering with other tenants' jobs scheduled on the same host — matching the scoped "persistent disruption" impact.

### Likelihood Explanation
The window between `c.internal.Start()` returning and `AssignPidToJobObject` completing is extremely small (typically sub-millisecond), and `AssignPidToJobObject` itself does not fail silently under normal conditions — the `Logger.Warn`-only handling matters only if assignment errors, which is uncommon (e.g., transient `OpenProcess` failure). Reliable exploitation additionally requires the attacker's spawned child to survive the fallback `taskkill /F /T` tree-kill, which is a non-trivial additional hurdle (requires PID-reuse timing or explicit process detachment techniques). This makes the finding a genuine but low-probability, hard-to-reliably-trigger race rather than a deterministically reproducible bug; it is a legitimate defense-in-depth gap in the primary containment mechanism (job object), partially compensated by the secondary `taskkill /T` mechanism.

### Recommendation
Eliminate the race by creating the job's root process suspended (`CREATE_SUSPENDED` via `SysProcAttr.CreationFlags`), calling `AssignProcessToJobObject`/`AssignPidToJobObject` while the process is still suspended (guaranteeing no code — and thus no forked children — can run before job assignment), and only then resuming the main thread with `ResumeThread`. This removes any window in which the process can spawn children outside job-object containment, making job-object teardown (`closeJobObject`) a complete guarantee independent of the best-effort `taskkill /T` fallback.

### Proof of Concept
Integration test plan (Windows-only, mirroring `helpers/process/killer_windows_integration_test.go` patterns):
1. Build a small helper Go/PowerShell test binary that, immediately on start, spawns a detached long-lived child process (e.g., `powershell -Command "Start-Sleep -Seconds 300"` launched with `DETACHED_PROCESS`/no parent wait) before doing anything else.
2. In the test, artificially delay `AssignPidToJobObject` (e.g., via a test hook or by injecting latency) so the detached child is guaranteed to spawn before assignment completes.
3. Start the command via `osCmd.Start()` with `UseWindowsJobObject: true`, then immediately call `windowsKiller.ForceKill()`.
4. Assert: the root process is terminated, but query for the detached child's PID/process object and assert it is `still running` after `ForceKill` returns — proving it escaped both job-object containment and the `taskkill /T` fallback.
5. Expected failing assertion demonstrating the bug: `assert.False(t, isProcessRunning(childPID))` fails because the child is still alive.

	})

func (pk *windowsKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := taskKill(pk.cmd.Process().Pid)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}

	pk.cmd.closeJobObject()
}
