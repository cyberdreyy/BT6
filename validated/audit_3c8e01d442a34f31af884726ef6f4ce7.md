### Title
ETH sent to `withdrawAA`/`withdrawBB` is permanently locked in the `EthenaCooldownRequest` clone - (File: contracts/IdleCDOEthenaVariant.sol)

### Summary
In the Ethena CDO variant, the withdrawal path deploys an `EthenaCooldownRequest` clone via `cooldownImpl.clone(abi.encodePacked(address(this), msg.sender), msg.value)` [1](#0-0) . In `ClonesWithImmutableArgs`, the second argument is the wei value attached to the `CREATE` call, so any `msg.value` carried into `withdrawAA`/`withdrawBB` is forwarded as an ETH balance to the freshly deployed clone. The clone's only recovery hook, `rescue(address _token)`, performs an ERC20 `transfer` and cannot move native ETH [2](#0-1) . The ETH is therefore locked forever. This is the same bug class as the Dahlia report: a payable path that accepts value it never uses, with no withdrawal mechanism for that value.

### Finding Description
- `IdleCDOEthenaVariant._withdraw` is reached from the public `withdrawAA`/`withdrawBB` entry points of `IdleCDO` and reads `msg.value` [3](#0-2) .
- The value is not used for any protocol purpose. It is passed verbatim as the `value` argument of the clone deployment [1](#0-0) .
- The deployed `EthenaCooldownRequest` clone has three external functions: `startCooldown` (only-CDO), `unstake` (sends sUSDe → USDe to the user, never ETH) and `rescue` (multisig-only, ERC20 only) [4](#0-3) . There is no `receive`/ETH sweep and no selfdestruct; `rescue` on a zero token address would call `transfer` on `address(0)` and revert.
- Net effect: any nonzero `msg.value` supplied with a withdraw on the Ethena variant is deposited into a per-request clone address with no reachable code path that can send ETH out — permanently locked.

### Impact Explanation
Permanent freezing of user funds with a quantified loss equal to `msg.value`. Any caller (tranche-token holder executing a normal cooldown withdraw) who attaches ETH — accidentally, via a wallet with an ETH-value field, or via a multicall/router that bundles value — loses the full amount. The clone is deterministic per `(cdo, user)` args, but even reusing it provides no recovery since no function releases ETH. Loss is unbounded per transaction and compounds per withdraw call. This is not a donation to the pool and is not recoverable by the `TL_MULTISIG` rescue path, which is ERC20-only [2](#0-1) .

### Likelihood Explanation
Likelihood is low-to-moderate: it requires a user (or an integrating contract/router calling `withdrawAA`/`withdrawBB` on the user's behalf) to attach a nonzero `msg.value`. Because the sUSDe withdraw flow is conceptually a cooldown "request", frontends or aggregators could plausibly treat it as a payable call. No privileged actor is needed, no epoch phase gating prevents it — it works in the normal running phase whenever `cooldownDuration() != 0` [5](#0-4) . The impact per occurrence is a 100% loss of the attached value, matching the "permanently locked funds" severity class of the external report.

### Recommendation
Two options, either suffices:
- Remove `msg.value` from the clone call: `cooldownImpl.clone(abi.encodePacked(address(this), msg.sender))`, and make `withdrawAA`/`withdrawBB` non-payable (or add `require(msg.value == 0)` in the Ethena variant's `_withdraw`) so ETH cannot enter this path.
- Additionally/instead, add an ETH sweep to `EthenaCooldownRequest` (e.g., extend `rescue` to send `address(this).balance` when `_token == address(0)`), so future accidental transfers to clones are recoverable.

### Proof of Concept
Foundry fork PoC (mainnet, sUSDe cooldown enabled, i.e. `IStakedUSDeV2.cooldownDuration() != 0`):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "../contracts/IdleCDOEthenaVariant.sol";
import "../contracts/IdleCDOTranche.sol";

contract LockedEthWithdrawTest is Test {
    IdleCDOEthenaVariant cdo = IdleCDOEthenaVariant(payable(<CDO_ADDRESS>));

    function testEthLockedInCooldownClone() public {
        address user = makeAddr("user");
        // fund user with USDe, deposit BB so they hold BB tranche tokens
        deal(<USDE>, user, 1000e18);
        vm.startPrank(user);
        IERC20Detailed(<USDE>).approve(address(cdo), 1000e18);
        cdo.depositBB(1000e18);
        vm.roll(block.number + 1);

        uint256 balBefore = user.balance;
        // user withdraws and accidentally attaches 1 ETH
        vm.deal(user, 1 ether);
        vm.recordLogs();
        cdo.withdrawBB{value: 1 ether}(0); // full redeem
        vm.stopPrank();

        // recover clone address from NewCooldownRequestContract event
        // (topic0 match, decode 'contractAddress')
        address clone = /* decoded from logs */;
        assertEq(address(clone).balance, 1 ether);   // ETH sits in clone
        assertEq(user.balance, 0);                    // user lost 1 ETH

        // rescue cannot recover ETH: token transfer on address(0) reverts
        vm.prank(0xFb3bD022D5DAcF95eE28a6B07825D4Ff9C5b3814); // TL_MULTISIG
        vm.expectRevert();
        EthenaCooldownRequest(clone).rescue(address(0));
        // No other function on the clone can move ETH -> permanently locked
    }
}
```

The clone address is emitted in `NewCooldownRequestContract` [6](#0-5) , making the locked balance directly assertable.

Caveat: I could not verify the exact `payable` declaration on `withdrawAA`/`withdrawBB` in `contracts/IdleCDO.sol` (the filtered grep returned only match counts), but `msg.value` is consumed in `_withdraw`, which requires a payable entry point; if the entry points are non-payable the issue reduces to dead code and should still be cleaned up.
