### Title
Equivocation guard's freshness window drops cross-tenure conflict protection, allowing a signer to sign two conflicting blocks at the same height - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The pre-commit-to-signature path in `handle_block_pre_commit` gates its cross-tenure double-sign guard behind a fixed local "freshness" timeout (`tenure_last_block_proposal_timeout`, default **30 seconds**). Once a previously-signed conflicting block's endorsement ages past this cutoff, the guard treats the conflict as void for *any* tenure other than the proposed block's own tenure — even though the earlier chainstate re-check (`check_block_against_signer_db_state`) never covers third-tenure siblings at all. This lets a signer sign a second, conflicting block at the same Stacks height once the 30-second window has elapsed, breaking the "one-per-height" signature invariant the whole mechanism exists to enforce.

### Finding Description
`check_block_against_signer_db_state` re-validates a pre-commit-threshold block against only **one** tenure: the parent tenure for a tenure-change block, or the block's own tenure otherwise [1](#0-0) . The `docs/signer-flows.md` itself documents this as a "blind spot": *"the re-check only ever looks at one tenure... so a signed sibling at the same height in a third tenure is invisible to it"* [2](#0-1) .

The only other safeguard is the cross-tenure conflict check in `handle_block_pre_commit`, which queries `get_signed_conflicts` for any signed block at or above the proposed height in **any** tenure [3](#0-2) . But this guard only blocks if the conflict is "fresh":

```
let freshness_cutoff = get_epoch_time_secs().saturating_sub(
    self.proposal_config.tenure_last_block_proposal_timeout.as_secs(),
);
if let Some(conflict) = conflicts.iter().find(|conflict| {
    conflict.last_endorsed > freshness_cutoff
        && !self.reorg_permit_stands(stacks_client, conflict)
        && self.conflict_still_blocks(...)
}) { ... refuse to sign ... }
``` [4](#0-3) 

`tenure_last_block_proposal_timeout` defaults to **30 seconds** [5](#0-4) . After that window, the fresh-conflict check is skipped entirely for cross-tenure conflicts. The remaining fallback check only re-examines a stale conflict if it is **in the block's own tenure**:

```
if conflicts.iter().any(|conflict| {
    conflict.consensus_hash == block_info.block.header.consensus_hash
        && !self.reorg_permit_stands(stacks_client, conflict)
}) { ... check own-tenure tip ... }
``` [6](#0-5) 

A stale conflict belonging to a **different** (third) tenure is not re-examined by this fallback at all, and is explicitly waved through: *"None of those conflicts still blocks it. Signing the replacement."* [7](#0-6) 

The code comment rationalizes this by claiming *"whether this block may replace what another tenure built is settled by the chainstate checks above"* [8](#0-7)  — but that is exactly the blind spot the documentation itself identifies: the chainstate check never inspects a third tenure. So once 30 seconds elapse since the earlier signature, **no check anywhere** verifies whether the third-tenure sibling is dead before the signer signs the new one.

### Impact Explanation
This breaks the equality the guard exists to protect: "one signature per signer per height." A one-slot miner (plus ordinary gossip of proposals/pre-commits) can trigger the sequence below without needing any other signer's key or a signer majority, by simply timing a second, competing proposal in a different tenure to arrive/cross the pre-commit threshold more than 30 seconds after the signer's earlier local signature. The result is the signer producing two signatures over conflicting, same-height blocks in different tenures — a direct equivocation. This matches the "Critical" impact criterion: a signer signing a conflicting block due to a rejection/conflict-recount analog of the underlying "insufficient session expiration" bug class (a stale but still-valid guard state expiring too early, permitting the analogous unauthorized action to proceed).

### Likelihood Explanation
The trigger conditions are entirely within a one-slot miner's control plus normal gossip: mine/produce a first block at height H in tenure A that a signer signs, then — more than `tenure_last_block_proposal_timeout` (30s default) later — mine or re-propose a competing block at the same height H in tenure B (e.g., after a burnchain fork, a tenure-change race, or simply a re-organized tenure sequence) and let it cross the 70% pre-commit threshold. No majority of signers, no other signer's key, and no auth_token access are required; only ordinary proposal/pre-commit gossip that miners routinely produce during forks or contested tenure transitions. The 30-second default window is short relative to realistic network/tenure-transition delays, making the stale-but-still-live scenario plausible in normal operation, not just a crafted edge case.

### Recommendation
Extend the fallback (post-freshness) conflict check to cover conflicts in **any** tenure at or above the proposed height, not only the proposed block's own tenure — i.e., re-run (or approximate) the equivalent of `conflict_still_blocks` for stale cross-tenure conflicts before signing, rather than unconditionally treating a stale cross-tenure conflict as resolved by the (tenure-scoped) chainstate re-check. Alternatively, ensure `check_block_against_signer_db_state` is extended to detect same-height siblings across all tenures, closing the blind spot the freshness guard was compensating for.

### Proof of Concept
1. Signer S is part of a `k`-of-n signer set. Miner tenure A proposes block A at Stacks height H; S pre-commits and signs A (`signed_self` set, `last_endorsed = t0`).
2. A burnchain event (fork/next sortition) starts tenure B, whose miner proposes a competing block B also targeting Stacks height H (a sibling of A, in a different tenure) — e.g., B is a tenure-change block that does not build on A's tenure, or an equal-height block from a subsequent, unrelated tenure.
3. Delay pre-commit threshold crossing for B until `t0 + tenure_last_block_proposal_timeout + ε` (≥30s by default) — trivially achievable via normal signer/miner message timing, network delay, or a deliberately slow-to-collect pre-commit round.
4. In `handle_block_pre_commit` for B: `check_block_against_signer_db_state` does not inspect tenure A (it only checks B's own tenure or B's parent tenure) [1](#0-0) ; `get_signed_conflicts` returns A as a conflict, but `A.last_endorsed (t0) <= freshness_cutoff`, so the fresh-conflict closure short-circuits to `false` [9](#0-8) ; the own-tenure fallback does not apply since A's `consensus_hash` differs from B's [10](#0-9) .
5. S signs B, logging *"None of those conflicts still blocks it. Signing the replacement."* [7](#0-6)  — S now holds signatures over two conflicting same-height blocks A and B in different tenures.

Note: I was unable to execute this scenario in a live/integration test within this session; the analysis is based on static code reading of `stacks-signer/src/v0/signer.rs`, `stacks-signer/src/signerdb.rs`, `stacks-signer/src/chainstate/mod.rs`, and the design documentation in `docs/signer-flows.md`, which explicitly describes both the chainstate re-check's single-tenure blind spot and the freshness-cutoff semantics used above.
