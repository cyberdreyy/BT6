### Title
Confirmations from removed multisig members remain counted toward the approval threshold, allowing requests to execute below the live-member quorum - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges pending requests that were *authored* by the removed member; it never scrubs that member's entries from the `confirmations` map of requests authored by *other* members. Because `confirm()` counts `confirmations.len()` without re-validating that every recorded confirmer is still a current member, a stale confirmation left behind by a since-removed member can still be tallied toward `num_confirmations`, letting a request execute with fewer *live* member approvals than the configured threshold.

### Finding Description
`add_request` stores the request together with an empty confirmation set keyed by `request_nonce`, and any member can later call `confirm` to add their identity to that set: [1](#0-0) 

`confirm` never checks whether the identities already present in `confirmations` are still members — it only validates that the *current caller* is a member via `assert_valid_request`: [2](#0-1) 

When a member is removed, `delete_member` only cleans up requests where `r.member == member` (i.e. requests the removed member *authored*). It does not scan `self.confirmations` for entries where the removed member appears as a *confirmer* on requests authored by someone else: [3](#0-2) 

Consequently, once a member is removed, any confirmation they previously cast on a request they did not author remains in `self.confirmations` and continues to count toward `self.num_confirmations` in future `confirm()` calls, even though that member no longer exists in `self.members`. This breaks the intended binding "confirmations counted == live members who approved."

The same structural flaw exists in the legacy `multisig` contract's `DeleteKey` action, which likewise only removes requests authored by the deleted key and never scrubs that key's confirmations on requests authored by others (`multisig/src/lib.rs`, `MultiSigRequestAction::DeleteKey` handling, lines 198-216).

### Impact Explanation
This allows a multisig request (e.g. a `Transfer`, `AddKey`/`AddMember`, or arbitrary `FunctionCall`) to execute with fewer genuinely live approving members than `num_confirmations` requires, because a stale confirmation from a removed member is silently counted as a live vote. This is a threshold-bypass on custody-controlling operations (fund transfers, key/member management), matching the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
The scenario only requires the normal, expected lifecycle of a multisig: a member confirms a pending request, and is later removed (e.g. due to offboarding or key rotation) before the request accumulates enough live confirmations. No compromise of any key beyond ordinary member operation is required, and the removed member's earlier, legitimately-cast confirmation is exploited purely by the accounting gap in `delete_member`/`confirm`. This can happen unintentionally in normal operations, and can also be leveraged deliberately by a remaining member who times request creation/confirmation around a planned member removal.

### Recommendation
When removing a member in `delete_member` (and `DeleteKey` in the legacy `multisig` contract), scan all requests' `confirmations` sets (not only requests authored by the removed member) and strip the removed member's entry from each. Alternatively, have `confirm()` re-validate, at tally time, that every identity present in `confirmations` for a request is still a current member of `self.members`, discounting any stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{Alice, Bob, Carol, Dave}` and `num_confirmations = 3`.
2. Alice calls `add_request` with a `Transfer` action to an attacker-controlled account → `request_id = 0`, `confirmations = {}`.
3. Bob calls `confirm(0)` → `confirmations.len()+1 = 1 < 3`, so `confirmations = {Bob}` is stored (not yet executed).
4. Via a separate, properly-approved request, the multisig removes Bob (`delete_member(Bob)`). `delete_member` only inspects requests authored by Bob (`r.member == Bob`); request `0` was authored by Alice, so its `confirmations = {Bob}` set is left untouched. `members` is now `{Alice, Carol, Dave}`.
5. Carol calls `confirm(0)` → `confirmations.len() (1, "Bob") + 1 = 2 < 3` → `confirmations = {Bob, Carol}`.
6. Dave calls `confirm(0)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → the transfer request **executes**.
7. In reality only Carol and Dave (2 live members) approved the request; Bob's stale confirmation from before his removal was counted as the third vote, so the transfer executed below the live-member quorum required by the multisig's own threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
