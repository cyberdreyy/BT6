### Title
Rebinding `IdleCreditVault.idleCDO` to a fresh `IdleCDOEpochVariant` lets stale withdraw receipts claim instantly at par, skipping epoch gating and stopEpoch funding - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault` keeps all per-user withdraw-receipt state (`withdrawsRequests`, `lastWithdrawRequest`, `withdrawsRequestsByEpoch`) while the epoch/session identity (`epochEndDate`, `isEpochRunning`, `defaulted`) is read dynamically from whichever CDO is currently whitelisted via `setWhitelistedCDO`. This is the same bug class as the external report: a shared contract (the strategy) is reused across "session" instances (CDO #1 → CDO #2), and state belonging to the old session is interpreted under the new session's counters. When the strategy is repointed to a fresh CDO whose `epochEndDate() == 0`, a pending withdraw request from the previous CDO becomes immediately claimable at par, without a `stopEpoch` ever funding it.

### Finding Description
`requestWithdraw` and `claimWithdrawRequest` gate behavior on `IIdleCDOEpochVariant(idleCDO).epochEndDate()`:

- `requestWithdraw` (IdleCreditVault.sol:259-280): `isClosed = epochEndDate() == 0` → if closed, `pendingWithdraws` is **not** incremented, so no future `stopEpoch` will ever source underlying for the minted receipt.
- `_claimFundedWithdrawRequest` (IdleCreditVault.sol:326): the "wait one epoch" check `epochEndDate() != 0 && epochNumber <= lastWithdrawRequest[_user]` is fully bypassed when `epochEndDate() == 0`.

`setWhitelistedCDO` (IdleCreditVault.sol:954-957) is `onlyOwner` and can be called at any time to repoint `idleCDO` to a new CDO instance (e.g., a CDO redeployment/migration — the deploy task `tasks/cdo-factory.js` explicitly supports re-whitelisting a new CDO on an existing strategy). A freshly initialized `IdleCDOEpochVariant` has `epochEndDate == 0`, `isEpochRunning() == false`, and `defaulted() == false`, but the strategy still holds all receipts created under the previous CDO.

Attack sequence (attacker = ordinary KYC'd lender, sequencing around an honest owner repoint):

1. CDO #1 epoch N is running; borrower holds the funds. Attacker calls `requestWithdraw` → receipt minted, `lastWithdrawRequest[attacker] = N`, `pendingWithdraws += amount`. The receipt is unfunded (underlying is lent out).
2. Owner deploys CDO #2 (fresh) and calls `strategy.setWhitelistedCDO(cdo2)` — an honest, supported operation.
3. Attacker calls `cdo2.claimWithdrawRequest()`. `_onlyIdleCDO` passes since `idleCDO == cdo2`. Because `cdo2.epochEndDate() == 0`, the epoch-wait guard is skipped and `_claimFundedWithdrawRequest` pays `withdrawsRequests[attacker]` at par via `_transferFundedClaim` directly from the strategy's underlying balance — funds that were never sourced by a `stopEpoch`, i.e., new deposits / residual balance belonging to CDO #2 or other users.

Equivalently, `epochNumber` keeps increasing in the strategy but the new CDO's epoch machinery restarts from its own zero state, so `withdrawsRequestsByEpoch` entries and `lossRecoveryPriceByEpoch` bookkeeping from CDO #1 are interpreted under CDO #2's phase machine (the exact analog of `results[questionId][player]` colliding across `SessionManager` instances).

### Impact Explanation
Direct theft / insolvency: an unfunded pending withdraw receipt is paid at par immediately, consuming strategy underlying that belongs to the new CDO's depositors (or to other still-waiting claimants). Loss magnitude = the attacker's `withdrawsRequests` balance, bounded only by the strategy's transferable underlying. It also breaks the "one receipt, one funded payout" invariant because `pendingWithdraws` was already counted in CDO #1's books and is never decremented by a funding event.

### Likelihood Explanation
Requires an honest owner repointing the strategy to a new CDO instance — a supported, non-privileged-abuse operation explicitly anticipated by `tasks/cdo-factory.js` ("Setting whitelisted CDO" when `strategy.idleCDO() != idleCDO`). Any user holding a pending or loss-adjusted receipt at repoint time, or any depositor in the window before the new CDO's first `startEpoch` (while `epochEndDate == 0`), can trigger the instant-claim path with a single call. No guard prevents `setWhitelistedCDO` while `pendingWithdraws`, `withdrawsRequests`, or `apr0Users` are non-empty.

### Recommendation
- Treat the strategy↔CDO binding as one-to-one for life: revert in `setWhitelistedCDO` if `idleCDO != 0`, or deploy a fresh `IdleCreditVault` per CDO (mirrors the report's fix).
- Alternatively, gate repointing on a quiesced state: require `pendingWithdraws == 0 && pendingInstantWithdraws == 0` and all `withdrawsRequests`/receipt tokens settled before allowing `setWhitelistedCDO`.
- Add regression tests exercising: pending request under CDO #1 → repoint → `claimWithdrawRequest` must revert or stay epoch-gated.

### Proof of Concept
```solidity
// test/foundry/RepointedCDOClaim.t.sol — extend TestIdleCDOBase fork setup
function testClaimAfterStrategyRepointedToFreshCDO() external {
    uint256 amount = 100_000 * ONE_SCALE;

    // CDO #1: deposit and run an epoch so funds are lent to borrower
    _depositWithUser(address(this), amount, true);
    _startEpochAndCheckPrices(0);

    // attacker requests withdraw; receipt is pending & unfunded
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertEq(strategy.pendingWithdraws(), requested);

    // honest owner deploys CDO #2 and re-whitelists the same strategy
    IdleCDO cdo2 = _deployCDO();
    stdstore.target(address(cdo2)).sig(cdo2.token.selector).checked_write(address(0));
    cdo2.initialize(0, defaultUnderlying, address(this), owner, rebalancer,
                    address(strategy), 100000);
    vm.prank(owner);
    IdleCreditVault(address(strategy)).setWhitelistedCDO(address(cdo2));

    // CDO #2 has never started an epoch: epochEndDate == 0
    assertEq(IdleCDOEpochVariant(address(cdo2)).epochEndDate(), 0);

    // attacker claims instantly, skipping the one-epoch wait and stopEpoch funding
    uint256 balPre = underlying.balanceOf(address(this));
    cdo2.claimWithdrawRequest();               // routed through new idleCDO
    assertEq(underlying.balanceOf(address(this)) - balPre, requested);
    // paid at par from strategy balance that was never sourced for this receipt
}
```

Broken invariant: queued withdrawal funding (receipts are payable only after `stopEpoch` sources their underlying). Existing guards (`_onlyIdleCDO`, epoch gating, `NotAllowed` checks) all pass because the guard inputs are read from the *new* CDO instance while the receipt data belongs to the *old* one — precisely the cross-instance ID collision described in the external report.
