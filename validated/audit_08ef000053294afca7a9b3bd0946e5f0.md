### Title
External Initiator identity is never bound to the target job's webhook spec, allowing any registered EI to trigger any webhook job's run - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` authenticates the caller's EI credentials, stores the resolved `bridges.ExternalInitiator` in the gin context, then unconditionally grants a hardcoded `UserRoleRun` session regardless of which job is being targeted. The only accessor of the stored EI object, `GetAuthenticatedExternalInitiator`, is not invoked anywhere in the job/run controllers, so the run-creation code path has no way to verify that the authenticated EI is the one referenced by the target job's `ExternalInitiatorWebhookSpec.ExternalInitiatorID`.

### Finding Description
`AuthenticateExternalInitiator` (core/web/auth/auth.go:119-151) looks up the EI by access key/secret, validates the HMAC via `bridges.AuthenticateExternalInitiator`, and on success does: [1](#0-0) 
It sets `SessionExternalInitiatorKey` to the resolved EI, but grants a static `UserRoleRun` role irrespective of *which* job is targeted by the request URL. Downstream authorization only checks role level via `RequiresRunRole`: [2](#0-1) 
which merely rejects `UserRoleView`, with no notion of "run role scoped to job X". The job model does carry a binding — `ExternalInitiatorWebhookSpec.ExternalInitiatorID` (core/services/job/models.go) — meant to associate a webhook job with exactly one EI. However, `GetAuthenticatedExternalInitiator`, the only function that retrieves the EI identity set during authentication, has no call sites in the job/pipeline-run controllers (`core/web/pipeline_runs_controller.go`, `core/web/jobs_controller.go`) based on repository search. This means the EI identity resolved during authentication is discarded after granting the run role, and the run-creation handler for `/v2/webhook/:jobID`-style routes cannot compare the caller's `EI.ID` to the target job's `ExternalInitiatorWebhookSpecID`/`ExternalInitiatorID`.

I was not able to directly view the full body of `core/web/pipeline_runs_controller.go` in this session to show the exact handler code that creates the run, so I cannot 100% confirm the binding check is absent versus performed via some mechanism not surfaced by the search (e.g., a repository-layer filter). This is a limitation of the current investigation — the claim rests on: (a) `AuthenticateExternalInitiator` hardcoding the role without job context, and (b) `GetAuthenticatedExternalInitiator` having zero call sites outside `auth.go` in the indexed codebase.

### Impact Explanation
If confirmed, this allows any entity holding valid credentials for External Initiator "A" to trigger job runs for any other webhook-type job "B" it is not bound to, by simply POSTing to `/v2/webhook/<jobB-UUID>` with EI A's headers. This is an authorization/binding bypass enabling unauthorized job execution, which could trigger unintended on-chain actions, unauthorized off-chain data submission, or fund-moving job pipelines, matching a "broken access control / unauthorized job run" bounty class.

### Likelihood Explanation
Given the code shown, the precondition is only "attacker possesses valid credentials for any one registered EI" — a relatively low bar since EI credentials are commonly distributed to external initiator operators, not treated as highly privileged secrets. If the run-creation handler indeed does not call `GetAuthenticatedExternalInitiator` to cross-check against the job's spec, the bypass would be trivially and repeatably exploitable via a single crafted HTTP request.

### Recommendation
In the job-run/webhook creation handler, after authentication, call `auth.GetAuthenticatedExternalInitiator(c)` and explicitly compare `ei.ID` against the target job's `WebhookSpec.ExternalInitiatorWebhookSpecs[].ExternalInitiatorID` before creating a run; reject with 401/403 on mismatch.

### Proof of Concept
Handler-level integration test plan:
1. Create two webhook jobs, JobA bound to `ExternalInitiator{ID: eiA.ID}` and JobB bound to `ExternalInitiator{ID: eiB.ID}`.
2. Authenticate using `eiA`'s access key/secret headers.
3. POST to `/v2/webhook/<JobB.ExternalJobID>`.
4. Assert expected behavior: request should be rejected (401/403); if the current code instead returns 200/201 and a new `PipelineRun` is created for JobB, this confirms the binding bypass.
5. Repeat with `eiB` credentials against JobA's endpoint to confirm symmetry.

Note: I could not fully confirm the absence of the binding check by reading the complete body of `core/web/pipeline_runs_controller.go` within this session due to tool/iteration limits; a Devin session with full file access should verify the exact handler logic before treating this as a confirmed, exploitable finding.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
