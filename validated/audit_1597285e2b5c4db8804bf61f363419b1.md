## Title
Multisig confirmations from removed members still count toward the approval threshold, allowing request execution with fewer live approvers than `num_confirmations` - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

## Summary
Both the `multisig` and `multisig2` contracts remove a member's *outstanding requests* when that member is deleted, but never purge the *confirmations that member already cast on other members' requests*. `confirm()` counts `confirmations.len()` unconditionally, without checking whether each confirming identity is still in the current `members` set. This breaks the binding "confirmations counted == live members who approved," letting a request execute once the raw count of confirmations reaches `num_confirmations`, even though one or more of those confirmations belong to accounts/keys that have since been removed from the multisig.

## Finding Description
`confirm()` in both contracts only validates the request and checks that the *current* signer hasn't already confirmed; it never re-validates the *existing* confirmers against the live `members` set: [1](#0-0) 

Member removal (`delete_member` / the `DeleteKey` handler in `multisig`) only scrubs requests *created by* the removed member, and removes `num_requests_pk` bookkeeping — it does not scan `self.confirmations` to strip the removed member's prior confirmations from *other* pending requests: [2](#0-1) 

The equivalent logic in the original `multisig` contract has the same gap (`DeleteKey` branch only filters requests where `r.signer_pk == pk`): [3](#0-2) 

and `confirm()` there likewise trusts the raw stored confirmation count: [4](#0-3) 

Concretely, with `num_confirmations = 2` and members `{A, B, C}`:
1. `A` creates request `R` (e.g., `Transfer` to `A`).
2. `B` confirms `R` → `confirmations[R] = {B}` (count 1, below threshold).
3. The multisig (via a separate, properly-threshold-confirmed `DeleteMember`/`DeleteKey` request) removes `B` — e.g., because `B` is suspected compromised. `R`'s stored confirmation set is untouched since `R` wasn't created by `B`.
4. `A` confirms `R` → `confirmations[R].len() + 1 == 2 >= num_confirmations`, so `execute_request(R)` runs.

`R` executes with only one genuinely live member (`A`) having approved it, while the threshold of `2` is nominally satisfied only because of `B`'s now-stale confirmation. The contract's own claimed invariant — "K signatures from current members required" — diverges from the actual live-approval count that authorized the transfer/key-add/function-call.

## Impact Explanation
This is a multisig request executed below the effective (live-member) threshold, matching the Critical impact criterion "a multisig request executed below threshold." Any `MultiSigRequestAction` — including `Transfer`, `AddKey`/`AddMember` (full access key grant), or `FunctionCall` — can be pushed through with fewer genuinely-authorizing members than `num_confirmations` requires, undermining the entire security model of the multisig (funds/control moved by a party set that doesn't meet the configured authorization bar).

## Likelihood Explanation
The precondition — removing a member who has an outstanding confirmation on some other pending request — is a normal, foreseeable multisig operational sequence (e.g., revoking a suspected-compromised or departing member while other requests are mid-flight). No foundation, redeploy, or external privileged actor is needed beyond the multisig's own documented member-management flow; the bug is purely in the contract's failure to invalidate stale confirmations on removal.

## Recommendation
When removing a member (`delete_member` in `multisig2`, the `DeleteKey` branch in `multisig`), iterate all pending requests' confirmation sets and strip the removed member's identity from each, not just from requests the removed member created. Alternatively, validate at `confirm()`-execution time that every entry in the stored `confirmations` set for the request still belongs to `self.members` (recomputing the live count) before comparing against `num_confirmations`.

## Proof of Concept
Using `multisig2/src/lib.rs` semantics (analogous in `multisig/src/lib.rs`):
1. Deploy with `members = [A, B, C]`, `num_confirmations = 2`.
2. `A` calls `add_request({receiver_id: multisig_account, actions: [Transfer{amount: X}]})` → `request_id = R`.
3. `B` calls `confirm(R)` → stored `confirmations[R] = {B}` (1 confirmation, below threshold; request stays pending).
4. Separately, `A` and `C` create and confirm a `DeleteMember{member: B}` request (reaching threshold 2 via their own confirmations) → `B` is removed from `members`; `R` is untouched because `R.member != B`.
5. `A` calls `confirm(R)` → `confirmations[R].len() (=1, still containing B) + 1 = 2 >= num_confirmations` → `execute_request` fires the `Transfer` of `X` to `multisig_account`, authorized effectively by only one live member (`A`), not two. [1](#0-0) [2](#0-1)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
