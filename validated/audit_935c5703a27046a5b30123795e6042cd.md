### Title
Time-based freshness cutoff lets a signer sign a conflicting sibling block, breaking the one-signature-per-height invariant - (File: stacks-signer/src/v0/signer.rs, `handle_block_pre_commit`)

### Summary
The stale-liability bug class in the SukukFi report (a value computed once and then treated as immutable/final even though the underlying state it depended on keeps moving) has an analog in the signer's pre-commit conflict check: whether a *previously signed* conflicting block at the same/higher Stacks height still "counts" is decided by a pure wall-clock freshness cutoff (`last_endorsed > freshness_cutoff`) rather than by re-deriving the true state of the chain. If a signer's own earlier signature ages past `tenure_last_block_proposal_timeout`, it is discarded as "stale" and no longer blocks a *new, conflicting* sibling block from also being signed — even though the first block could still become canonical. This can make a single signer put valid signatures over two conflicting blocks at the same height, across two different tenures/forks.

### Finding Description
In `handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs:1383-1421`), once the pre-commit weight threshold is reached for a proposed block, the signer looks up all previously-signed blocks at the same or higher height in *any* tenure via `SignerDb::get_signed_conflicts` (`stacks-signer/src/signerdb.rs:1606-1625`). A conflict only blocks the new signature if all of these hold:

```
conflict.last_endorsed > freshness_cutoff
    && !self.reorg_permit_stands(stacks_client, conflict)
    && self.conflict_still_blocks(stacks_client, conflict, block_info.block.header.chain_length)
```
(`stacks-signer/src/v0/signer.rs:1403-1411`)

`freshness_cutoff` is `get_epoch_time_secs() - tenure_last_block_proposal_timeout` (`stacks-signer/src/v0/signer.rs:1393-1397`), i.e. a purely local timestamp comparison against when the signer *itself* last endorsed the conflicting block (`signed_self`/`signed_group`, see `SignerDb::get_signed_conflicts` docstring, `stacks-signer/src/signerdb.rs:1587-1605`). This "went stale" state is not re-derived from the node's chainstate — it's simply an elapsed-time check, exactly analogous to SukukFi locking in a PPS value at fulfillment time instead of repricing against current state. The code comment itself says this is deliberate for round-trip cost, but the consequence is that a genuinely-still-live conflicting signature is disregarded purely because enough wall-clock time passed:

> "Freshness alone is not enough to hold a signature back, because a signature can outlive the block it covers... a fact recorded once at observation time can be silently wrong, while a question asked per evaluation self-corrects..." (`docs/signer-flows.md:288-297`)

That reasoning covers the case where staleness incorrectly *withholds* a signature (liveness-favoring), but the same one-directional check also means the freshness gate can incorrectly *release* a real conflict from blocking a new signature: if `last_endorsed <= freshness_cutoff`, the `find` predicate short-circuits to `false` and neither `reorg_permit_stands` nor `conflict_still_blocks` (the two node-truth checks) are ever consulted (`stacks-signer/src/v0/signer.rs:1403-1411`). So an old-but-still-canonical-track conflict is waved through with zero re-validation against the node, unlike the "OWN tenure" fallback path a few lines below, which does re-query `get_tenure_tip` even for stale, same-tenure conflicts (`stacks-signer/src/v0/signer.rs:1432-1457`). Only same-tenure stale conflicts get that fallback re-check; a stale conflict in a *different* tenure gets no re-check at all once it ages out, and the block is signed:

> "A stale conflict in another tenure in particular no longer speaks for us: whether this block may replace what another tenure built is settled by the chainstate checks above." (`stacks-signer/src/v0/signer.rs:1424-1426`)

But the "chainstate checks above" (`check_block_against_signer_db_state`) only validate the *new* proposal's parent/tenure relationship — they do not re-examine whether the *old* signed sibling block is still reachable/pending on the canonical fork. If a slow miner keeps a competing tenure alive past `tenure_last_block_proposal_timeout` (a config value the signer itself controls, potentially small), a signer that signed block A at height H in tenure T1 can, once `last_endorsed` for A ages past the cutoff, sign a conflicting block B at height H in tenure T2 without the node-truth `conflict_still_blocks`/`get_tenure_tip` check ever running, purely because of elapsed wall-clock time and the "different tenure" carve-out.

### Impact Explanation
This breaks the one-signature-per-height equality the pre-commit conflict logic exists to enforce. If the earlier block A is still capable of becoming canonical (e.g., its tenure's sortition is still valid and the node hasn't pruned it), the same signer now holds live signatures over two conflicting Stacks blocks at the same height in different tenures — a signer equivocation. Depending on aggregate weight distribution, this can contribute to two conflicting blocks each separately reaching the `verify_signer_signatures` threshold (`stackslib/src/chainstate/nakamoto/mod.rs:1097-1189`), i.e. a fork where multiple blocks at the same height are each accepted by enough weight — the Critical-tier "signer signing a conflicting block" outcome called out in the task rules.

### Likelihood Explanation
This requires no majority collusion and no key compromise — a single miner/tenure that stalls past `tenure_last_block_proposal_timeout` (which is a locally-configured, and in some deployments possibly short, duration) combined with a re-proposed sibling block at the same height is sufficient to trigger the stale-conflict carve-out. It is entirely within reach of "a one-slot miner plus gossip" re-proposing a competing block after the timeout window, satisfying the in-scope rule for this analog.

### Recommendation
Do not let a purely time-based `last_endorsed` cutoff bypass the node-truth checks (`reorg_permit_stands`, `conflict_still_blocks`, or at minimum `get_tenure_tip`) for cross-tenure conflicts. Either (a) always ask `conflict_still_blocks`/`get_tenure_tip` regardless of freshness, using freshness only to prioritize which round-trip to make first, or (b) require that a conflict be provably dead (sortition orphaned, tenure superseded) before it can be excluded, rather than merely "old by the wall clock."

### Proof of Concept
1. Signer S validates and signs block A (height H, tenure T1) via `handle_block_pre_commit`, recording `signed_self` at time t0 in `SignerDb` (`get_signed_conflicts` will later report `last_endorsed = t0`).
2. Tenure T1's miner stalls; a new miner starts tenure T2 and proposes block B at the same height H, which reaches S's pre-commit threshold at time `t1 > t0 + tenure_last_block_proposal_timeout`.
3. In `handle_block_pre_commit`, `get_signed_conflicts(H, hash(B))` returns A with `last_endorsed = t0`. Since `t0 <= freshness_cutoff` (because `t1 - t0 > tenure_last_block_proposal_timeout`), the `find` predicate at `stacks-signer/src/v0/signer.rs:1403-1411` evaluates to `false` without ever calling `conflict_still_blocks` or `reorg_permit_stands` for A.
4. Because A's `consensus_hash` (T1) differs from B's `consensus_hash` (T2), the same-tenure fallback check at `stacks-signer/src/v0/signer.rs:1432-1457` also does not apply to A.
5. S proceeds to `mark_locally_accepted` and signs B (`stacks-signer/src/v0/signer.rs:1467-1478`), even though tenure T1/block A may still be canonical-track on the node — S now holds signatures over two conflicting blocks at height H.
