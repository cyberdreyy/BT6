## Title
Signer weight double-counted across Accept and Reject tallies in the miner's `StackerDBListener`, causing the miner-side voting equality (`aggregated-weight` vs `verified-accepts`) to break — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
This is a real analog of the InitCapital bug class: a "provided" tally value (aggregated weight bucket) is trusted without reconciling it against the *actual* per-signer state (which bucket that signer currently belongs to), so weight that should be exclusive to one bucket leaks into both, breaking the arithmetic invariant `total_weight_approved + total_weight_rejected <= total_weight`.

### Finding Description
`StackerDBListener::run_until_stopped` maintains a `BlockStatus` per proposed block with two independently-guarded weight tallies: `total_weight_approved` and `total_weight_rejected`, plus a `responded_signers: HashSet<u32>` and `gathered_signatures: BTreeMap<u32, MessageSignature>` [1](#0-0) .

When a `BlockResponse::Accepted` arrives, weight is only added if the signer's slot is **not already in `gathered_signatures`**, and after that the code unconditionally records the slot into *both* `gathered_signatures` and `responded_signers`: [2](#0-1) 

When a `BlockResponse::Rejected` arrives, weight is only added if `responded_signers.insert(slot_id)` returns `true` (i.e., the slot had never appeared in `responded_signers` before): [3](#0-2) 

These two guards check **different sets** (`gathered_signatures` vs `responded_signers`), so the ordering of a signer's messages determines whether double counting occurs:

- Reject-then-Accept: signer first sends `Rejected` → `responded_signers` gets the slot, `total_weight_rejected` increases. Later the same signer sends `Accepted` (e.g. after `store_and_process_block_signature` in `stacks-signer` legitimately allows signing even after a prior local rejection, since "we should still store signatures even on consensus reached blocks for auditing purposes" [4](#0-3) ). At the miner, the Accept path only checks `gathered_signatures`, which does **not** yet contain the slot, so `total_weight_approved` is also incremented — the signer's weight now counts in **both** buckets simultaneously, and the reject weight is never rolled back.

This breaks the equality the miner's threshold logic depends on: each signer's weight should count toward exactly one of "approved" or "rejected", not both.

### Impact Explanation
In `SignCoordinator`/`signer_coordinator.rs`, the reject-threshold check is evaluated **before** the approve-threshold check on every loop iteration: [5](#0-4) [6](#0-5) 

Because a single flip-flopping (or reordered-message) signer can inflate `total_weight_rejected` without that weight ever being deducted, `block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` can become true purely from double counting — even though the *same* signer's later legitimate signature already exists in `gathered_signatures` and could otherwise have carried the block over `total_weight_approved >= weight_threshold`. Since the reject branch is checked first and returns `Err(NakamotoNodeError::SignersRejected { .. })`, the miner discards a block proposal that in fact has (or would have) enough real, distinct signer signatures to reach consensus, forcing it to abandon and rebuild — a liveness wedge in the miner's block-acceptance state machine driven purely by an accounting bug, not by an actual signer majority rejecting the block.

### Likelihood Explanation
No majority of signers or malicious key is required — a single honest signer that reconsiders (rejects first based on a stale local view, then genuinely signs once its state settles) is sufficient to trigger the double count, since `stacks-signer`'s own logic explicitly permits recording a signature after a rejection has already been recorded for audit purposes. Message reordering/gossip delay alone (no equivocation needed) can produce this ordering at the miner.

### Recommendation
Track each signer's response using a single canonical state (e.g. `responded_signers: HashMap<u32, Vote>` mapping slot → last decision), and when a signer's vote changes, first subtract their weight from the bucket they previously counted toward before adding it to the new bucket, keeping `total_weight_approved + total_weight_rejected <= total_weight` as an enforced invariant.

### Proof of Concept
1. Miner proposes block `B`; signer `S` (slot `k`, weight `w`) sends `BlockResponse::Rejected` — `responded_signers = {k}`, `total_weight_rejected = w`.
2. `S` later (per `stacks-signer/src/v0/signer.rs::store_and_process_block_signature`) legitimately signs `B` and sends `BlockResponse::Accepted` with a valid signature.
3. At the miner, `gathered_signatures` does not contain `k`, so `total_weight_approved += w` as well.
4. Now `total_weight_approved + total_weight_rejected` counts `w` twice, while `self.total_weight` (denominator) counts it once — inflating both aggregate percentages beyond what real distinct signer weight supports and potentially triggering `NakamotoNodeError::SignersRejected` in `signer_coordinator.rs` ahead of the legitimate approval path.
