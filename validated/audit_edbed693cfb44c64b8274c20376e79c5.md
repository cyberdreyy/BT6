## Finding

A single malicious/equivocating signer can have its weight counted in **both** `total_weight_approved` and `total_weight_rejected` simultaneously in the node-side signer-response tally, breaking the aggregated-weight accounting invariant that each signer's weight should count toward at most one side of the 70%/30% threshold decision. This is analogous in effect to the CVE's "uncontrolled/unchecked accumulation" class: the tally has no de-duplication guard shared between the two response paths.

### Root cause

In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, `StackerDBListener`'s message-processing loop maintains, per block, `gathered_signatures` (keyed by `slot_id`), `responded_signers` (a `HashSet<u32>`), `total_weight_approved`, and `total_weight_rejected` [1](#0-0) .

- The `Accepted` arm only guards the weight addition with `!block.gathered_signatures.contains_key(&slot_id)`, and only afterwards inserts into `responded_signers` — it never checks whether that slot already appears in `responded_signers` from a prior rejection: [2](#0-1) 
- The `Rejected` arm guards weight addition with `block.responded_signers.insert(slot_id)` (true only the first time that slot is seen in `responded_signers`), and never checks `gathered_signatures`: [3](#0-2) 

Since the two arms use different, uncoordinated de-duplication sets, the sequence Reject-then-Accept from the same `slot_id` passes both guards:
1. `Rejected` first: `responded_signers.insert(slot_id)` → `true` (first insertion) → `total_weight_rejected += weight`.
2. `Accepted` later (same signer, valid signature over the same block): `gathered_signatures.contains_key(&slot_id)` → `false` (never inserted) → `total_weight_approved += weight`, then `gathered_signatures.insert(slot_id, ...)` and `responded_signers.insert(slot_id)` (now a no-op).

The signer's weight is now present in both tallies. The `Accepted -> Rejected` order is correctly blocked (the `Rejected` arm's `responded_signers.insert` returns `false` the second time), but the reverse order is not.

### Where it's consumed

`SignerCoordinator::get_block_status` in `stacks-node/src/nakamoto_node/signer_coordinator.rs` uses these two counters as if they were mutually exclusive to decide the outcome: it first checks whether `total_weight_rejected + weight_threshold > total_weight` (declares `SignersRejected`), and otherwise checks `total_weight_approved >= weight_threshold` (declares acceptance) [4](#0-3) . Because the two counters are not exclusive, a single signer can inflate the "rejected" side of the sum using weight that has also been legitimately spent on the "approved" side, effectively lowering — by that signer's own weight — the amount of *other* genuine rejecting weight needed to cross the 30% blocking-minority line, i.e. an attacker needs less than a true blocking minority of the reward set to force `NakamotoNodeError::SignersRejected` and stall/rewrite the block-proposal loop.

### Why this matches the analog

- Reachable by one signer (no majority needed) sending two ordinary, individually-valid StackerDB messages (Reject then Accept) for the same block — no forged signature, no access to another signer's key.
- Breaks the "aggregated-weight vs verified-accepts" equality the task calls out: the sum of the two disjoint tallies can exceed `total_weight`, which the coordinator's threshold logic assumes cannot happen.
- Consequence is a liveness/safety-adjacent wedge on the miner side: it can push a block into (or hold it at) `SignersRejected` using less real dissenting weight than the protocol's 30% blocking-minority requirement, which can be repeated by the same signer on every subsequent proposal in the tenure.

### Title
Asymmetric weight de-duplication in `StackerDBListener` lets one signer double-count its weight across `total_weight_approved` and `total_weight_rejected` — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side StackerDB response listener tracks approval and rejection weight in two separately-guarded counters (`gathered_signatures`/`total_weight_approved` and `responded_signers`/`total_weight_rejected`). A signer that sends `Rejected` before `Accepted` for the same block passes both guards, so its weight is added to both tallies, breaking the assumption in `SignerCoordinator::get_block_status` that the two are mutually exclusive shares of `total_weight`.

### Finding Description
See root-cause analysis above: `Rejected` arm gates on `responded_signers.insert(slot_id)`; `Accepted` arm gates on `!gathered_signatures.contains_key(slot_id)`. These are different sets, so a `Rejected`-then-`Accepted` sequence from the same slot is not deduplicated, unlike the reverse order which is correctly blocked by the shared `responded_signers` check on the `Accepted` path having already been populated. [2](#0-1) [3](#0-2) 

### Impact Explanation
`get_block_status` treats `total_weight_rejected` as the complement of `total_weight_approved` when it decides between `SignersRejected` and acceptance [4](#0-3) . Double-counting one signer's weight into `total_weight_rejected` while that same weight is legitimately present in `total_weight_approved` lets a single dishonest signer reduce, by its own weight, the amount of independent rejecting weight required to reach the 30% blocking-minority threshold — a liveness wedge reachable without a majority of signers, matching the High-severity bar in the task (a signer/miner-triggerable break of an aggregated-weight vs verified-accepts equality with no majority requirement).

### Likelihood Explanation
Requires only one registered signer behaving adversarially by sending its two ordinary protocol messages (`Rejected` then `Accepted`) for the same block proposal — both individually valid and signable with that signer's own key. No collusion, no cryptographic forgery, no access to another party's secrets.

### Recommendation
Use a single shared per-slot decision record (e.g., one `HashMap<u32, Decision>` storing Accepted/Rejected) instead of two independently-guarded structures (`gathered_signatures`/`responded_signers`), and reject/ignore any second, conflicting response from the same slot for the same block regardless of order, so a signer's weight can only ever be counted in one of `total_weight_approved` / `total_weight_rejected`.

### Proof of Concept
1. Node proposes block `B`; `StackerDBListener` tracks its `BlockStatus`.
2. Signer `S` (slot `k`, weight `w`) publishes a `Rejected` StackerDB message for `B` → `responded_signers` gains `k`, `total_weight_rejected += w`.
3. Signer `S` subsequently publishes a valid `Accepted` message (self-signed) for `B` → since `gathered_signatures` never contained `k`, `total_weight_approved += w`.
4. `S`'s weight `w` is now counted in both `total_weight_approved` and `total_weight_rejected`; repeated by other equivocating signers, `total_weight_rejected` can cross the `> total_weight - weight_threshold` bound with less independent honest-minority weight than the protocol intends, per `signer_coordinator.rs`'s check at lines 509-513.
