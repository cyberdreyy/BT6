### Title
Non-default-epoch instant withdraw receipts bypass the default recovery haircut and are paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` applies the default-recovery haircut only to receipts recorded under `defaultRecoveryEpoch` (`instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`), but then pays out the *aggregate* `instantWithdrawsRequests[_user]` — which lumps together receipts from every epoch — at par through `_transferFundedClaim`. This is the same shape as the GraphQL Armor bug: a classification check keys on a single label (the default-epoch bucket, analogous to `node.name == '__schema'`) while the affected object can be one of several kinds (receipts from many epochs, analogous to `FieldNode | OperationDefinitionNode | ...`), so a receipt carrying a different "label" escapes the cost/haircut entirely.

### Finding Description
When the borrower defaults, `finalizeDefaultRecovery` computes the recovery basis via `defaultPendingClaimBasis()`, which only adds `instantWithdrawClaimsByEpoch[epochNumber]` — instant receipts created in the *current* (defaulted) epoch:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```

Instant receipts requested in an earlier epoch that were only partially funded at that epoch's `stopEpoch` (`pendingInstantWithdraws` stayed > 0, but `instantWithdrawClaimsByEpoch[oldEpoch]` still holds the user's basis) are never added to the recovery basis and get no `defaultRecoveryPrice` haircut.

However, `claimInstantWithdrawRequest` only strips the `defaultRecoveryEpoch` bucket:

```solidity
if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
  _claimDefaultedInstantWithdrawRequest(_user); // clears only instantWithdrawsRequestsByEpoch[user][defaultEpoch]
}
uint256 amount = instantWithdrawsRequests[_user]; // aggregate across ALL epochs
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);            // paid at par, only reserve is guarded
```

`_transferFundedClaim` only protects `defaultRecoveryReserve`; any other underlying sitting in the strategy (borrower repayments routed through `sendInterestAndDeposits`/direct sends, or funds collected for other claims) can be spent at par. An old-epoch receipt therefore:

- escapes the `defaultRecoveryPrice` haircut applied to default-epoch claimants, and
- either drains strategy underlyings it was never backed by (diluting/stealing from defaulted-epoch claimants whose reserve is a fixed `recoveryPrice` of a basis that excluded them), or, if the strategy is underfunded, causes `_transferFundedClaim` to revert — permanently freezing the user's legitimately funded claim portion too, since the claim path cannot be split.

The attacker path is fully unprivileged: a KYC'd lender requests an instant withdraw in epoch N; the borrower only partially repays at `stopEpoch` (manager/borrower actions are honest sequencing, not attacker-controlled malice — partial funding occurs whenever the returned amount is insufficient, which is the exact scenario `pendingInstantWithdraws` exists for); epoch N+1 starts and the borrower defaults. The attacker then calls the CDO's claim path, which invokes `claimInstantWithdrawRequest` and pays the entire aggregate at par.

### Impact Explanation
Broken invariant: loss socialization / fair recovery distribution. Defaulted-epoch instant claimants receive `claimBasis * defaultRecoveryPrice / 1e18`, while a holder of an equally-unfunded receipt from an earlier epoch receives 100% — paid out of underlyings that effectively belong to the recovery pool's ecosystem. Loss equals the attacker's unfunded old-epoch instant receipt amount (up to the full `instantWithdrawsRequests` balance), taken at par instead of at `defaultRecoveryPrice`. Alternatively, if strategy funds are insufficient, all of the user's instant claims (including funded ones) revert permanently — freezing of funds.

### Likelihood Explanation
Requires: an instant withdraw request that remains partially unfunded across an epoch boundary, followed by a borrower default in a later epoch. Partial funding is a normal, expected protocol state (it is precisely why `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch` exist). No privileged misbehavior needed. The code comment at `_claimDefaultedInstantWithdrawRequest` even acknowledges multiple-epoch claims exist ("the extra amount was already counted as prefunded reserve") but only handles the default epoch's bucket.

### Recommendation
In `claimInstantWithdrawRequest`, when `defaultRecoveryFinalized`, iterate/settle all non-default-epoch instant receipt buckets before paying at par, and either (a) include all outstanding instant claim basis (across epochs) in `defaultPendingClaimBasis`, or (b) haircut any receipt whose `instantWithdrawsRequestsByEpoch[user][e]` was not fully funded at its own epoch's `collectInstantWithdrawFunds`. Alternatively track per-epoch funded vs unfunded portions so the claim path cannot conflate them — i.e., assert the "kind" of each receipt, not just whether the default-epoch bucket is empty.
