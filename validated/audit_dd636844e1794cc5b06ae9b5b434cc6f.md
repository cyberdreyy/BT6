Confirmed. The `confirmations` HashSet is keyed only by `RequestId` and stores raw `PublicKey`s [1](#0-0) . In `confirm()`, the threshold check only compares the size of this set to `num_confirmations`, with no re-validation that each key in the set is still an active access key [2](#0-1) . When `DeleteKey` executes, it only purges requests/confirmations for requests where that key was the **original submitter** (`r.signer_pk == pk`); it never scans `confirmations` for other still-pending requests where that key appears only as a **confirming** party [3](#0-2) . That stale confirmation entry persists and still counts toward the threshold on a later `confirm()` call, exactly mirroring the source bug's pattern of un-cleared state ("approval"/ownership) surviving destruction of the underlying entity and being reused to bypass an intended check.

### Title
Multisig request executes below quorum via stale confirmation from a deleted key - (File: `multisig/src/lib.rs`)

### Summary
`confirm()` counts entries in the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map to decide whether `num_confirmations` has been reached [2](#0-1) . The `DeleteKey` action removes a revoked key's own outstanding requests and their confirmation sets, and removes the key's `num_requests_pk` entry, but it does **not** strip that key from `confirmations` sets belonging to other requests it had previously confirmed as a non-submitting signer [3](#0-2) . This is the same class of bug as the ArtGobblers legendary-mint issue: state recording an authorization (an approval / a confirmation) is not invalidated when the underlying credential (an owned NFT / an access key) is destroyed, and it can later be "replayed" to satisfy a check it should no longer satisfy.

### Finding Description
Binding that should hold: `confirmations counted for request R == number of currently-live members who actually approved R`. The vulnerable code breaks this equality.

Walkthrough:
1. Contract initialized with `num_confirmations = 3` and members with keys `{A, B, C, D}`.
2. Key `A` calls `add_request` to create request `R1` (e.g. a `Transfer` action) — `R1`'s `confirmations` set starts empty [4](#0-3) .
3. Keys `B` and `C` call `confirm(R1)`. Since `2 < 3`, their public keys are simply inserted into `confirmations[R1]` [5](#0-4) . `R1` is still pending with `confirmations[R1] = {B, C}`.
4. Separately, members `A`, `C`, `D` submit and confirm a `DeleteKey { public_key: B }` request to revoke `B` (e.g., `B` is compromised or offboarded). This executes and calls `promise.delete_key(B)`, and the multisig internal bookkeeping only removes requests where `signer_pk == B` (`B` never submitted any request) and clears `num_requests_pk[B]` [3](#0-2) . Crucially, `confirmations[R1]` is left untouched — it still contains `B`.
5. `B`'s on-chain access key is now deleted, so `B` can no longer act. Yet `confirmations[R1] = {B, C}` still exists.
6. Member `D` now calls `confirm(R1)`. `assert_valid_request` only checks the request and confirmation-map entries exist — it performs no liveness check on the keys already inside the set [6](#0-5) . `confirmations.len() + 1 == 3 >= num_confirmations`, so `R1` executes with `execute_request` [2](#0-1) .
7. The transfer/action executes with only 2 genuinely live signers (`C`, `D`) plus one stale, now-deleted key (`B`) — one fewer live approver than the configured `num_confirmations = 3` threshold.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." An attacker or a colluding minority of remaining members can revoke a member's key after it has already contributed confirmations to pending requests, then wait for (or coordinate) one more confirmation from an active key to push a request over threshold using the dead key's stale confirmation credit. This lets requests (including `Transfer`, `FunctionCall`, `AddKey`/`DeleteKey`, `DeployContract`) execute with fewer live-authorized signers than the contract's configured quorum, undermining the fundamental multisig security guarantee [7](#0-6) .

### Likelihood Explanation
No special privilege beyond normal multisig membership is required, and this is a realistic operational sequence: rotating/removing a signer's key (e.g., due to compromise, employee offboarding, hardware loss) is an expected multisig maintenance action, and having several requests pending simultaneously is normal given the contract's own design (`active_requests_limit` allows up to 12 concurrent unconfirmed requests per key) [8](#0-7) . The only requirement is that a confirming key be deleted while it has outstanding confirmations on other pending requests — no attacker-controlled timing trick or race condition beyond ordinary usage is needed.

### Recommendation
When executing `DeleteKey`, iterate over **all** entries in `confirmations` (not just requests where the key was `signer_pk`) and remove the deleted public key from every confirmation set, recomputing whether any request now needs to remain below threshold. Alternatively, validate liveness of each key in a `confirmations` set at `confirm()` time (e.g., check that removed keys are not counted) before comparing against `num_confirmations`, or maintain multisig membership as an explicit set (as `multisig2` does with `members: UnorderedSet<MultisigMember>` [9](#0-8)  — note the same underlying gap exists there too, since `delete_member` also only clears confirmations for requests submitted by the removed member, not requests it merely confirmed).

```rust
    fn execute_request(&mut self, request: MultiSigRequest) -> PromiseOrValue<bool> {
        let mut promise = Promise::new(request.receiver_id.clone());
        let receiver_id = request.receiver_id.clone();
        let num_actions = request.actions.len();
        for action in request.actions {
            promise = match action {
                MultiSigRequestAction::Transfer { amount } => promise.transfer(amount.into()),
                MultiSigRequestAction::CreateAccount => promise.create_account(),
                MultiSigRequestAction::DeployContract { code } => {
                    promise.deploy_contract(code.into())
                }
                MultiSigRequestAction::AddKey {
                    public_key,
                    permission,
                } => {
                    self.assert_self_request(receiver_id.clone());
                    if let Some(permission) = permission {
                        promise.add_access_key(
                            public_key.into(),
                            permission
                                .allowance
                                .map(|x| x.into())
                                .unwrap_or(DEFAULT_ALLOWANCE),
                            permission.receiver_id,
                            permission.method_names.join(",").into_bytes(),
                        )
                    } else {
                        // wallet UI should warn user if receiver_id == env::current_account_id(), adding FAK will render multisig useless
                        promise.add_full_access_key(public_key.into())
                    }
                }
                MultiSigRequestAction::DeleteKey { public_key } => {
                    self.assert_self_request(receiver_id.clone());
                    let pk: PublicKey = public_key.into();
                    // delete outstanding requests by public_key
                    let request_ids: Vec<u32> = self
                        .requests
                        .iter()
                        .filter(|(_k, r)| r.signer_pk == pk)
                        .map(|(k, _r)| k)
                        .collect();
                    for request_id in request_ids {
                        // remove confirmations for this request
                        self.confirmations.remove(&request_id);
                        self.requests.remove(&request_id);
                    }
                    // remove num_requests_pk entry for public_key
                    self.num_requests_pk.remove(&pk);
                    promise.delete_key(pk)
                }
                MultiSigRequestAction::FunctionCall {
                    method_name,
                    args,
                    deposit,
                    gas,
                } => promise.function_call(
                    method_name.into_bytes(),
                    args.into(),
                    deposit.into(),
                    gas.into(),
                ),
                // the following methods must be a single action
                MultiSigRequestAction::SetNumConfirmations { num_confirmations } => {
                    self.assert_one_action_only(receiver_id, num_actions);
                    self.num_confirmations = num_confirmations;
                    return PromiseOrValue::Value(true);
                }
                MultiSigRequestAction::SetActiveRequestsLimit {
                    active_requests_limit,
                } => {
                    self.assert_one_action_only(receiver_id, num_actions);
                    self.active_requests_limit = active_requests_limit;
                    return PromiseOrValue::Value(true);
                }
            };
        }
        promise.into()
    }

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
```

```markdown
### State machine

Per each request, multisig maintains next state machine:
 - `add_request` adds new request with empty list of confirmations.
 - `add_request_and_confirm` adds new request with 1 confirmation from the adding key.
 - `delete_request` deletes request and ends state machine.
 - `confirm` either adds new confirmation to list of confirmations or if there is more than `num_confirmations` confirmations with given call - switches to execution of request. `confirm` fails if request is already has been confirmed and already is executing which is determined if `confirmations` contain given `request_id`.
 - each step of execution, schedules a promise of given set of actions on `receiver_id` and puts a callback.
 - when callback executes, it checks if promise executed successfully: if no - stops executing the request and return failure. If yes - execute next transaction in the request if present.
 - when all transactions are executed, remove request from `requests` and with that finish the execution of the request.
```
