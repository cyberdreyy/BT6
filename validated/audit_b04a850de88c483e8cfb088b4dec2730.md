### Title
`NakamotoBlockProposal::validate` resolves the TenureChange-Extend burn view via `get_block_snapshot_consensus` instead of the canonical sortition tip, letting a non-canonical burn view drive tenure/parent validation - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
`NakamotoBlockProposal::validate` computes `burn_view_consensus_hash` from the block's `TenureChange` payload via `NakamotoChainState::get_block_burn_view`, then resolves `sort_tip` with a plain `SortitionDB::get_block_snapshot_consensus` lookup and builds all subsequent canonicity checks (`check_block_has_valid_tenure`, `check_block_has_valid_parent`, `get_expected_burns`) on a `SortitionHandleConn` rooted at that `sort_tip`. Nothing in this path compares `sort_tip` against `SortitionDB::get_canonical_burn_chain_tip`, unlike the analogous consensus-path function `validate_nakamoto_tenure_snapshot`, which explicitly re-derives the real canonical tip and checks ancestor continuity against it.

### Finding Description
The broken equality: **`sort_tip` used by `validate()` must equal the SortitionDB's actual canonical burnchain tip's ancestry, not merely "some snapshot that shares an ancestor with the parent."**

- `NakamotoChainState::get_block_burn_view` (stackslib/src/chainstate/nakamoto/mod.rs:2201-2262) accepts `tenure_change.burn_view_consensus_hash` as long as `get_ancestor_sort_id` shows that this candidate's ancestry at the parent's burn-view height equals the parent's actual `sortition_id`. This is only a **shared-ancestor** check; it says nothing about which of possibly-multiple descendant forks past that height is the one the network currently considers canonical. [1](#0-0) 

- `NakamotoBlockProposal::validate` (stackslib/src/net/api/postblock_proposal.rs:587-602) then resolves `sort_tip` with `SortitionDB::get_block_snapshot_consensus(sortdb.conn(), &burn_view_consensus_hash)` — a direct-by-consensus-hash lookup that returns whatever snapshot matches, canonical or not — and immediately builds `db_handle = sortdb.index_handle(&sort_tip.sortition_id)` to run `check_block_has_valid_tenure` and `check_block_has_valid_parent`. [2](#0-1) 

- By contrast, the equivalent consensus-critical function `validate_nakamoto_tenure_snapshot` (used elsewhere in real block-append processing) explicitly fetches `SortitionDB::get_canonical_burn_chain_tip(db_handle)` and rejects if the tenure snapshot's ancestor at that height diverges from the actual canonical sortition id. [3](#0-2) 

Root cause: the signer-facing `validate()` path never performs this canonical-tip anchoring for the TenureChange-Extend's `burn_view_consensus_hash`; it only checks that the claimed burn view descends from the same ancestor as the parent, which is satisfied equally by the canonical branch and any sibling (losing) branch past a fork point.

Attacker's exact proposal: a miner who has legitimately won one tenure (attacker-controlled BTC spend, single slot) crafts a `NakamotoBlock` whose `TenureChange` has `cause = Extended` and `burn_view_consensus_hash` set to a `ConsensusHash` that is present in `SortitionDB` (e.g. from a Bitcoin fork/reorg boundary) but is not on the chain the rest of the network currently treats as canonical. They gossip this `BlockProposal` via StackerDB as normal miner traffic (no privileged role, no auth_token needed — this is the signer's own node call using the signer's own credentials). The victim signer's node runs `validate()`, resolves `sort_tip` to the non-canonical snapshot, and both `check_block_has_valid_tenure`/`check_block_has_valid_parent` succeed because they only check ancestry local to that (wrong) `sort_tip`, not against the real canonical tip. `validate()` returns `Ok`, and the signer signs.

Existing guards do not close this: `check_block_has_valid_tenure` (stackslib/src/net/api/postblock_proposal.rs:454-472) only checks `db_handle.has_consensus_hash(tenure_id)` relative to whatever root the caller supplied — it has no independent canonical-tip cross-check of its own. [4](#0-3) 

### Impact Explanation
This breaks canonicity (chain safety): a signer can approve/sign a Nakamoto block whose burn view has been validated against a non-canonical sortition fork rather than the network's actual tip. If the referenced fork later definitively loses (as it already does at signing time in the described scenario), the signer has produced a valid threshold signature share for a block anchored to state the rest of the network will not accept as canonical — this is exactly the "signer signing an invalid, non-canonical, or conflicting block" Critical-severity category. It is repeatable at every future reorg/fork boundary the attacker's own tenure straddles, without needing majority signer collusion or the auth_token.

### Likelihood Explanation
Preconditions: attacker must win one sortition normally (single miner slot, self-funded BTC — already an allowed capability) and there must exist, near a Bitcoin reorg boundary, at least two sortition snapshots in `SortitionDB` sharing a common ancestor with the parent's burn view. Reorg-adjacent forks of this kind occur naturally on Bitcoin and are recorded by the sortition DB's fork-tracking design, so the precondition is not exotic. The attacker only needs to control the `TenureChange` payload's `burn_view_consensus_hash` field of their own proposal and gossip it — one signer-slot equivalent of "miner" capability plus normal StackerDB gossip, no privileged role, no auth_token, and no access to other signers' keys. This is repeatable each time the attacker's tenure spans a fork boundary.

### Recommendation
In `NakamotoBlockProposal::validate` (and/or `NakamotoChainState::get_block_burn_view`), after resolving `sort_tip` from `burn_view_consensus_hash`, explicitly verify it against `SortitionDB::get_canonical_burn_chain_tip` the same way `validate_nakamoto_tenure_snapshot` does: fetch the true canonical tip, compute the ancestor of the canonical tip at `sort_tip.block_height`, and reject the proposal unless that ancestor's `sortition_id` equals `sort_tip.sortition_id`. This closes the gap between the "shares an ancestor with parent" check in `get_block_burn_view` and true current-canonicity.

### Proof of Concept
Rust test plan (stackslib, `postblock_proposal` test module):
1. Build a `SortitionDB` test harness with a burnchain fork: mine sortitions up to height `H` (shared ancestor), then fork into branch A (made canonical, e.g. by giving it more subsequent work/blocks) and branch B (orphaned but still recorded), each producing a distinct `ConsensusHash` at height `H+1`.
2. Have the attacker win a tenure on the shared history before `H`, and record `parent_header_info.burn_view` pointing at the canonical branch-A tip.
3. Craft a `NakamotoBlock` with a `TenureChangePayload { cause: Extended, burn_view_consensus_hash: <branch-B's H+1 consensus hash>, .. }`.
4. Call `NakamotoBlockProposal::validate(...)`.
5. Assert-before-fix: `validate()` returns `Ok(BlockValidateOk)` even though `SortitionDB::get_canonical_burn_chain_tip` reports branch A, not branch B, as canonical (`sort_tip.sortition_id != canonical_tip.sortition_id` at height `H+1`).
6. Assert-after-fix: `validate()` returns `Err(BlockValidateRejectReason { reason_code: ValidateRejectCode::NonCanonicalTenure, .. })` because the added canonical-ancestor check on `sort_tip` fails.

    pub(crate) fn check_block_has_valid_tenure(
        db_handle: &SortitionHandleConn,
        tenure_id: &ConsensusHash,
    ) -> Result<(), BlockValidateRejectReason> {
        // Verify that the block's tenure is on the canonical sortition history
        if !db_handle.has_consensus_hash(tenure_id)? {
            warn!(
                "Rejected block proposal";
                "reason" => "Block's tenure consensus hash is not on the canonical Bitcoin fork",
                "consensus_hash" => %tenure_id,
            );
            return Err(BlockValidateRejectReason {
                reason_code: ValidateRejectCode::NonCanonicalTenure,
                reason: "Tenure consensus hash is not on the canonical Bitcoin fork".into(),
                failed_txid: None,
            });
        }
        Ok(())
    }
