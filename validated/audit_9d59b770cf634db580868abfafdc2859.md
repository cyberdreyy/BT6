### Title
Integration deposit paths (JupLend/Kamino/Solend/Drift) don't account for SPL Token-2022 transfer fees, unlike the core deposit/withdraw/repay/borrow paths - (File: programs/marginfi/src/instructions/juplend/deposit.rs)

### Summary
This is a valid analog of the reported bug class. marginfi's core `lending_account_deposit` correctly compensates for Token-2022 transfer-fee mints by computing a pre-fee transfer amount via `calculate_pre_fee_spl_deposit_amount` before calling `deposit_spl_transfer` [1](#0-0) . However, the integration paths (JupLend, and by the same pattern Kamino/Solend/Drift) that move funds from the user into the bank's liquidity vault and then on into the external protocol never apply this compensation — they call `transfer_checked(cpi_ctx, amount, decimals)` with the raw user-supplied `amount` and then re-use that same `amount` in the downstream protocol CPI and in expected-share calculations [2](#0-1) .

### Finding Description
`juplend_deposit` computes `expected_shares` from the raw `amount` using `expected_shares_for_deposit_from_rates`, then calls `cpi_transfer_user_to_liquidity_vault(amount)` (a plain `transfer_checked` for `amount`) and `cpi_juplend_deposit(amount, ...)`, requiring the fTokens minted to exactly equal `expected_shares` computed from the full, pre-fee `amount` [3](#0-2) . The `cpi_transfer_user_to_liquidity_vault` helper is a bare `transfer_checked` with no fee-awareness [4](#0-3) . If the underlying mint is Token-2022 with a nonzero `TransferFeeConfig`, the liquidity vault would receive `amount - fee`, not `amount`; since the subsequent JupLend CPI-deposit and `expected_shares` calculation both assume the vault holds/moves the full `amount`, the transaction would fail with `JuplendDepositFailed` on any transfer-fee mint (insufficient balance / share mismatch), rather than silently mis-accounting. The same pattern (raw `transfer_checked(amount)` immediately followed by a downstream CPI keyed on the same `amount`) is used in `programs/marginfi/src/instructions/solend/deposit.rs`, `programs/marginfi/src/instructions/kamino/deposit.rs`, and `programs/marginfi/src/instructions/drift/deposit.rs` [5](#0-4) .

Crucially — unlike the core `PositionManager`-analog path — I could not find any explicit guard (equivalent to `nonzero_fee`/`has_transfer_fee`, used in `lending_pool_emissions_deposit` [6](#0-5) ) that rejects transfer-fee mints when creating JupLend/Kamino/Solend/Drift banks (`lending_pool_add_bank_juplend` performs no such check) [7](#0-6) . This means an admin could configure an integration bank on a fee-bearing Token-2022 mint, and every deposit into it would revert (functional break, `JuplendDepositFailed`), rather than an exploitable mis-accounting like the Morpho report describes — because the shares/CPI-amount checks are strict-equality (`require_eq!`), causing hard failure instead of silent value loss.

### Impact Explanation
Given the strict `require_eq!` checks tying CPI-transferred/received amounts to expected values, a fee-on-transfer mint used for these integration banks would cause deposits (and correspondingly withdrawals, which also move `amount` raw via `transfer_checked`) to always fail rather than create exploitable value redirection or misvaluation. This differs from the original Morpho report where mis-accounted balances directly under-collateralize repayments/supplies. The impact here is closer to Denial-of-Service for any integration bank erroneously configured on a fee-bearing mint, not a fund-draining or under-collateralization bug, since deposits with fee-bearing mints will revert rather than silently succeed with a wrong balance.

### Likelihood Explanation
Low. This requires: (1) marginfi admin to configure a JupLend/Kamino/Solend/Drift bank on a Token-2022 mint with an active `TransferFeeConfig`, which is an operational/governance choice, not something an unprivileged attacker can trigger; and (2) as noted, this class of bank creation isn't blocked by an explicit `nonzero_fee` check the way `lending_pool_emissions_deposit` is. In practice, mrgn's own asset-listing process (as referenced in the original report's Morpho response) would need to approve such a mint, and the resulting failure mode is a hard revert, not a stealthy value-extraction bug.

### Recommendation
Add an explicit guard rejecting Token-2022 mints with nonzero transfer fees (reusing `utils::nonzero_fee`) at `lending_pool_add_bank_juplend`, `lending_pool_add_bank_kamino`, `lending_pool_add_bank_solend`, and `lending_pool_add_bank_drift`, consistent with the check already present in `lending_pool_emissions_deposit`. Alternatively, if fee-bearing mints must be supported for these integrations, mirror the core deposit/withdraw pattern of computing pre-fee/post-fee amounts (`calculate_pre_fee_spl_deposit_amount` / `calculate_post_fee_spl_deposit_amount`) before invoking downstream integration CPIs.

### Proof of Concept
Not independently exploitable to extract value based on available code — the strict `require_eq!` checks in `juplend_deposit`/`juplend_withdraw` (and analogous integration modules) would cause any deposit into a bank backed by a Token-2022 mint with nonzero `TransferFeeConfig` to revert with `JuplendDepositFailed`/`JuplendWithdrawFailed` rather than succeed with mis-accounted shares. I was unable to fully verify whether Kamino/Solend/Drift add-bank paths contain equivalent strict-equality post-CPI checks (only JupLend's deposit/withdraw code was read in full); confirming that across all four integrations, and confirming there truly is no mint-fee guard at bank-creation time for each, would require further review of `kamino/add_pool.rs`, `solend/add_pool.rs`, and `drift/add_pool.rs` in full, which time did not permit in this pass.

pub fn juplend_deposit(ctx: Context<JuplendDeposit>, amount: u64) -> MarginfiResult {
    let authority_bump: u8;
    {
        let marginfi_account = ctx.accounts.marginfi_account.load()?;
        let bank = ctx.accounts.bank.load()?;
        authority_bump = bank.liquidity_vault_authority_bump;

        validate_asset_tags(&bank, &marginfi_account)?;
        validate_bank_state(&bank, InstructionKind::FailsIfPausedOrReduceState)?;
    }

    // Refresh the exchange price (interest/rewards) for this slot.
    ctx.accounts.cpi_update_rate()?;

    let expected_shares = {
        let lending = ctx.accounts.integration_acc_1.load()?;
        // Compute expected shares minted (round-down) using the same math as JupLend.
        expected_shares_for_deposit_from_rates(
            amount,
            lending.liquidity_exchange_price,
            lending.token_exchange_price,
        )
        .ok_or_else(|| error!(MarginfiError::MathError))?
    };

    let pre_f_token_balance = accessor::amount(&ctx.accounts.integration_acc_2.to_account_info())?;

    // Move underlying into the vault and deposit into JupLend.
    ctx.accounts.cpi_transfer_user_to_liquidity_vault(amount)?;
    ctx.accounts.cpi_juplend_deposit(amount, authority_bump)?;

    let post_f_token_balance = accessor::amount(&ctx.accounts.integration_acc_2.to_account_info())?;
    let minted_shares = post_f_token_balance
        .checked_sub(pre_f_token_balance)
        .ok_or_else(|| error!(MarginfiError::MathError))?;

    // Exact match required.
    require_eq!(
        minted_shares,
        expected_shares,
        MarginfiError::JuplendDepositFailed
    );

pub fn lending_pool_add_bank_juplend(
    ctx: Context<LendingPoolAddBankJuplend>,
    bank_config: JuplendConfigCompact,
    bank_seed: u64,
) -> MarginfiResult {
    // Note: JupLend banks don't need to debit the flat SOL fee because these will always be
    // first-party pools owned by mrgn and never permissionless pools
    let LendingPoolAddBankJuplend {
        bank_mint,
        bank: bank_loader,
        integration_acc_1,
        integration_acc_2,
        ..
    } = ctx.accounts;

    let mut bank = bank_loader.load_init()?;
    let mut group = ctx.accounts.group.load_mut()?;
    let lending_key = integration_acc_1.key();
    let f_token_vault_key = integration_acc_2.key();

    // Validate that we're using a supported Juplend oracle setup type
    require!(
        matches!(
            bank_config.oracle_setup,
            OracleSetup::JuplendPythPull | OracleSetup::JuplendSwitchboardPull
        ),
        MarginfiError::JuplendInvalidOracleSetup
    );

    let config = bank_config.to_bank_config(lending_key);

    let liquidity_vault_bump = ctx.bumps.liquidity_vault;
    let liquidity_vault_authority_bump = ctx.bumps.liquidity_vault_authority;
    let insurance_vault_bump = ctx.bumps.insurance_vault;
    let insurance_vault_authority_bump = ctx.bumps.insurance_vault_authority;
    let fee_vault_bump = ctx.bumps.fee_vault;
    let fee_vault_authority_bump = ctx.bumps.fee_vault_authority;

    *bank = Bank::new(
        ctx.accounts.group.key(),
        config,
        bank_mint.key(),
        bank_mint.decimals,
        ctx.accounts.liquidity_vault.key(),
        ctx.accounts.insurance_vault.key(),
        ctx.accounts.fee_vault.key(),
        Clock::get().unwrap().unix_timestamp,
        liquidity_vault_bump,
        liquidity_vault_authority_bump,
        insurance_vault_bump,
        insurance_vault_authority_bump,
        fee_vault_bump,
        fee_vault_authority_bump,
        bank_seed,
    );
    bank.flags |= BANK_SEED_KNOWN;
    if bank_mint.to_account_info().owner == &anchor_spl::token_2022::ID {
        bank.flags |= IS_T22;
    }

    // Set JupLend-specific fields
    // - integration_acc_2: protocol fToken vault (PDA token account)
    // - integration_acc_3: withdraw intermediary ATA expected by JupLend's withdraw constraints
    bank.integration_acc_1 = lending_key;
    bank.integration_acc_2 = f_token_vault_key;
    bank.integration_acc_3 = get_associated_token_address_with_program_id(
        &ctx.accounts.liquidity_vault_authority.key(),
        &bank_mint.key(),
        &ctx.accounts.token_program.key(),
    );

    log_pool_info(&bank);

    group.add_bank()?;

    bank.config.validate()?;
    bank.config
        .validate_oracle_setup(ctx.remaining_accounts, None, None, None)?;

    emit!(LendingPoolBankCreateEvent {
        header: GroupEventHeader {
            marginfi_group: ctx.accounts.group.key(),
            signer: Some(group.admin)
        },
        bank: bank_loader.key(),
        mint: bank_mint.key(),
    });

    Ok(())
}
