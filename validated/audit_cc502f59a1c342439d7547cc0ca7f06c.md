### Title
Punitive `seizeWithMemo()` on B20 tokens can be frontrun via an ordinary `transfer()` before the seize lands - ([File: crates/common/precompiles/src/b20_asset/logic/v2.rs])

### Summary
The Sherlock report describes `StakingModule.slash()` being frontrun by a malicious user calling `fullClaimAndExit()` before the penalizing transaction lands, because the punitive action and the user's escape hatch are both ordinary mempool transactions with no atomicity or freeze between them. Base's B20 token precompile framework has a structurally identical punitive primitive, `seizeWithMemo`, which moves a target's balance to a receiver as a compliance/enforcement action [1](#0-0) , and the account whose funds are about to be seized retains an unrestricted ability to `transfer()` out its balance in the interim, since Base runs a standard visible transaction pool that a target address can observe before inclusion.

### Finding Description
`seize_with_memo` gates on the caller's `Seize` role and on the target `from` address being "seizable" — i.e., NOT authorized by the `SeizeExempt` policy scope — via `B20Guards::ensure_seizable` [2](#0-1) . Crucially, this seizability check is entirely independent of the `TransferSender` policy that would ordinarily need to be set to block a compromised/flagged account from moving funds — the codebase's own tests explicitly document this independence: an account can be "seizable" while still fully authorized to `transfer()` normally [3](#0-2) .

Because seizure and any account freeze (via `updateBlocklist`/`TransferSender` policy) are separate, non-atomic on-chain calls (as demonstrated by the two-step blocklist-then-transfer workflow in the test harness) [4](#0-3) , a target account under investigation can watch the public mempool for the compliance operator's freeze/seize transaction(s) and submit a normal, ordinary `transfer()` call with a higher priority fee (or via FIFO ordering, simply first) to move its balance to an address it controls before the seize transaction executes.

Base's transaction pool is a standard, externally observable mempool: transactions transition through `Pending`/`Queued` states that are broadcast via pool event listeners and tracked for lifecycle timing before block inclusion [5](#0-4) , and the builder selects `best_transactions()` from this same pool for inclusion [6](#0-5) , ordered either by priority fee (`CoinbaseTip`) or FIFO (`Timestamp`) [7](#0-6) . Either ordering scheme is trivially frontrunnable by an attacker willing to pay a higher tip or simply race submission, exactly mirroring the mempool-visibility precondition in the original `slash()` report.

### Impact Explanation
An account targeted for compliance-driven seizure (e.g., a hacked/sanctioned/fraudulent holder of a B20 stablecoin or asset token) can escape the seizure entirely by moving its balance out via a plain `transfer()` before `seizeWithMemo` executes, because `move_balance` operates on the balance present at execution time and there is no mechanism (freeze-before-notify, atomic bundling, or balance snapshot) preventing this race. This defeats the intended enforcement/compliance guarantee of the seize primitive on both `B20Asset` and `B20Stablecoin` tokens, allowing sophisticated malicious actors — the very users this control targets — to reliably bypass it.

### Likelihood Explanation
High likelihood for any attacker actively monitoring their own address for compliance action: submitting a `transfer()` transaction is a normal, unprivileged operation requiring no special role, and Base's txpool exposes pending transactions and standard fee-based/FIFO ordering that any user can outbid or race. No additional guard couples `seizeWithMemo` to a prior/atomic freeze of `TransferSender` for the same account.

### Recommendation
Do not rely on `seizeWithMemo` alone as an unstoppable enforcement primitive. Before/atomically with initiating a seizure, set the target's `TransferSender` policy to deny (or otherwise freeze the account) in the same transaction/bundle as the seize call so no transfer-out window exists, or have `seize_with_memo` itself force-deny transfers for `from` as part of its guard sequence rather than treating `SeizeExempt` and `TransferSender` as fully independent scopes.

### Proof of Concept
1. Compliance operator observes suspicious activity on address `A` holding a B20 token balance and prepares an `updateAllowlist`/`updateBlocklist` (freeze) transaction and/or a `seizeWithMemo(from=A, to=treasury, amount=balance)` transaction and submits it to the public mempool.
2. Address `A` (or an automated bot monitoring the mempool for calls referencing `A`) observes the pending transaction and immediately submits `transfer(to=B, amount=balance)` with a higher priority fee (or simply faster in FIFO mode) from account `A`.
3. `A`'s `transfer()` is included first, since `ensure_seizable` in `seize_with_memo` [8](#0-7)  only checks the `SeizeExempt` policy scope and not the live balance/`TransferSender` state, and no atomicity ties the freeze and seize together.
4. When the operator's `seizeWithMemo` transaction lands afterward, `move_balance` finds `A`'s balance reduced or zero, so the seizure captures little or nothing, exactly mirroring the `fullClaimAndExit()` frontrun of `slash()` in the referenced report.

    fn seize_with_memo(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        from: Address,
        to: Address,
        amount: U256,
        memo: B256,
    ) -> Result<()> {
        B20Guards::ensure_not_paused(token, IB20::PausableFeature::SEIZE)?;
        B20Guards::ensure_token_role(token, caller, B20TokenRole::Seize)?;
        // `to != 0` guards against a disguised burn; `from != 0` guards against a disguised mint
        // (`Transfer(0x0, to, ...)`), matching `transfer_inner`.
        if to == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidReceiver { receiver: to }));
        }
        if from == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidSender { sender: from }));
        }
        if from == to {
            return Err(BasePrecompileError::revert(IB20::InvalidReceiver { receiver: to }));
        }
        B20Guards::ensure_seizable(token, from)?;
        // Gate the destination like `mint` gates `MintReceiver`: an unset scope is always-allow, so a
        // treasury need not be allowlisted by default.
        B20Guards::ensure_policy_type(token, B20PolicyType::SeizeReceiver, to)?;
        self.move_balance(token, from, to, amount)?;
        // `Memo` must immediately follow the `Transfer` (from `move_balance`), before `Seized`.
        self.emit_memo(token, caller, memo)?;
        token
            .accounting_mut()
            .emit_event(IB20::Seized { caller, from, to, amount }.encode_log_data())
    }

    /// Ensures `account` is seizable, i.e. NOT authorized by the current seize-exempt policy.
    ///
    /// Mirrors [`Self::ensure_blocked`] but consults `SEIZE_EXEMPT_POLICY` instead of the
    /// transfer-sender policy: accounts authorized by that scope are exempt from seizure, so an
    /// account is seizable only when the configured registry policy does not authorize it, and
    /// the unset always-allow default keeps seizure closed until an issuer configures the slot.
    /// Used by `seizeWithMemo`. Enforced unconditionally, including in the factory bootstrap
    /// window. Reverts `AccountNotSeizable` (distinct from `ensure_blocked`'s `AccountNotBlocked`)
    /// so the seize path and the deprecated `burnBlocked` report separately.
    pub fn ensure_seizable<T: Token + ?Sized>(token: &T, account: Address) -> Result<()> {
        let policy_scope = B20PolicyType::SeizeExempt.id();
        let policy_id = token.accounting().policy_id(policy_scope)?;
        if token.policy().is_authorized(token.policy_storage(), policy_id, account)? {
            Err(BasePrecompileError::revert(IB20::AccountNotSeizable { account }))
        } else {
            Ok(())
        }
    }

The ordering strategy is configurable via `--rollup.txpool-ordering` and defined in
[`ordering.rs`](https://github.com/base/base/blob/main/crates/execution/txpool/src/ordering.rs):

```rust
pub enum BaseOrdering<T> {
    CoinbaseTip(CoinbaseTipOrdering<T>),
    Timestamp(TimestampOrdering<T>),
}
```

`CoinbaseTip` is the standard Ethereum ordering where transactions with higher priority fees get
included first. `Timestamp` is a rollup-specific FIFO ordering where transactions are prioritized by
arrival time regardless of fee. The timestamp ordering can be useful for fairer transaction
sequencing.
