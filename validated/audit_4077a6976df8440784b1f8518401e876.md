Based on my investigation, I can confirm part of the described mechanism in code, but I was unable to fully verify the exploit's claimed elevated-privilege impact within available tool calls.

### Title
InternalImages exact-match bypass in `VerifyAllowedImage` allows job to select disallowed helper image as main/service image - (File: common/allowed_images.go)

### Summary
`VerifyAllowedImage` in [1](#0-0)  contains an unconditional exact-match branch that grants approval whenever `options.Image` equals any entry in `options.InternalImages`, independent of the configured `AllowedImages` glob list. Since `docker.go` builds and passes an `InternalImages` list (containing the helper image reference) into the same generic verification function used for validating the job's main `image:` and `services:` fields, an unprivileged job author can set `image:` to the exact helper-image string and have it pass the allowed-images check even though it is not present in `AllowedImages`.

### Finding Description
`VerifyAllowedImage` first tries to match `options.Image` against each glob pattern in `AllowedImages` via `doublestar.Match` [2](#0-1) . If none match, it falls through to a second loop that grants approval on exact string equality with any `InternalImages` entry, with no distinction between "this is being checked because the runner itself needs to pull its own helper image" versus "the job specified this image string directly" [1](#0-0) . Because the function only receives strings (`options.Image`, `options.AllowedImages`, `options.InternalImages`) and has no caller-context flag distinguishing "verifying the helper image on the runner's behalf" from "verifying a job-supplied image/service name," a job that names the helper image reference verbatim in its `image:` or `services:` config will satisfy this branch and bypass the `AllowedImages` restriction entirely.

However, I was not able to fully trace `executors/docker/docker.go`'s container-creation logic (`createContainer` vs. the dedicated helper-container creation path) within this session's tool budget to confirm whether a main/service container built from an image string equal to the helper image reference receives any of the helper container's special treatment (e.g., additional binds, docker.sock access, or elevated capabilities). Architecturally in GitLab Runner, such privileges are normally wired to the *container's role* (helper vs. build container) in `docker.go`, not to the image string itself, and executor-wide settings like `privileged`, volumes, and capabilities apply identically to every container regardless of which image is used. If that holds here, using the helper image as a job image would just run an ordinary, non-privileged container with attacker-controlled command/entrypoint — not a privilege-escalated or sandbox-broken container — meaning the exploit only achieves an allowlist bypass, not an "executor breakout or stronger permissions" as required by this question's scoped impact.

### Impact Explanation
Confirmed impact: an operator-configured `allowed_images`/`allowed_services` restriction can be bypassed for the specific case of the helper image string, letting a job run a container using an image that was not authorized by the runner administrator. Unconfirmed/unverified impact: whether that container gains any additional privileges, mounts, or isolation weaker than any other permitted job image (this would require tracing the full `docker.go` container-role/privilege wiring, which I could not complete in this session).

### Likelihood Explanation
Preconditions are realistic and match the question's scenario (`allowed_images` configured with a restrictive list; `InternalImages` non-empty, e.g. containing the helper image path). The exact-match check is unconditional and easy to trigger by simply setting `image: <helper-image-reference>` in `.gitlab-ci.yml`, requiring no special access beyond normal pipeline authorship.

### Recommendation
Do not reuse `VerifyAllowedImage`'s `InternalImages` exact-match branch for job-supplied `image:`/`services:` verification. Separate the "runner pulling its own internal helper image" check from the "job specifying image/service name" check — e.g., verify internal image usage through a dedicated code path (or a boolean flag on `VerifyAllowedImageOptions` indicating an internal-only check) so job input can never match against `InternalImages`.

### Proof of Concept
```go
// common/allowed_images_test.go
func TestVerifyAllowedImage_JobCannotUseInternalImageToBypassAllowedImages(t *testing.T) {
    opts := VerifyAllowedImageOptions{
        Image:          "registry.gitlab.com/gitlab-org/gitlab-runner/gitlab-runner-helper:x86_64-latest",
        OptionName:     "images",
        AllowedImages:  []string{"alpine:*", "golang:1.2*"},
        InternalImages: []string{"registry.gitlab.com/gitlab-org/gitlab-runner/gitlab-runner-helper:x86_64-latest"},
    }
    err := VerifyAllowedImage(opts, buildlogger.New(...))
    // Expected: err should be ErrDisallowedImage because the image is not in AllowedImages
    // and was only supplied as the job's `image:` field, not as an internal-only lookup.
    assert.ErrorIs(t, err, ErrDisallowedImage)
}
```
This test currently fails against the existing implementation (returns `nil` instead of `ErrDisallowedImage`), confirming the allowlist bypass. A full confirmation of "executor breakout or stronger permissions" would additionally require a Docker executor integration test asserting that a container created from this image via the job's `image:` field receives no additional binds/capabilities beyond a normal job container — this part remains unverified in this session and should be checked against `executors/docker/docker.go`'s container-creation code before treating the impact as more than an allowlist bypass.
