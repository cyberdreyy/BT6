### Title
Reorg-timing check silently underflows to "poorly timed" via `saturating_sub`, letting a miner force signers to sanction a reorg of an already-established tenure - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_parent_tenure_choice` decides whether a new tenure is allowed to reorg (replace) a prior tenure that already produced a signed block. The decision hinges on `proposal_to_sortition = sortition_state_received_time.saturating_sub(approved_at)` being smaller than the configured `first_proposal_burn_block_timing`. Because the subtraction uses `saturating_sub` on two independently-timestamped wall-clock values, any situation where the local `approved_at` timestamp (when *this* signer stamped its own approval of the prior tenure's first block) lands at or after `sortition_state_received_time` (when this signer recorded the new burn block) collapses the measured gap to `0`, which is always below the timeout. This causes the signer to treat a tenure that was in fact properly and long-since established as "poorly timed," and to sanction (permit) its reorg - the exact analog to the DYAD report's TOCTOU/timing-race class: a locally-recorded, attacker-influenceable timestamp comparison is used as ground truth for a security decision, and an adversary that can influence relative event ordering/timing can force the check down the permissive branch.

### Finding Description
`check_parent_tenure_choice` (stacks-signer/src/chainstate/mod.rs, ~line 170) is invoked from `check_proposal` (v1) and `validate_tenure_change_payload`/`check_proposal` (v2) whenever a new tenure's parent tenure is not the immediately prior sortition - i.e., whenever a reorg is being proposed. For each reorged tenure that already produced exactly one globally-accepted block, the code computes: [1](#0-0) 

```rust
let checked_proposal_timing = if let Some(sortition_state_received_time) = sortition_state_received_time {
    let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {
        sortition_state_received_time.saturating_sub(approved_at)
    } else {
        // "we did not sign it ourselves" -> treated as late-arriving, proposal_to_sortition = 0
        0
    };
    if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
        // ... permits the reorg, tenure pushed into `superseded_tenures`
    }
    ...
```

`sortition_state_received_time` is `signer_db.get_burn_block_receive_time(&self.burn_block_hash)` - the *new* sortition's burn-block arrival time as locally recorded by *this* signer - and `approved_at` is `local_block_info.approved_time`, stamped locally at pre-commit or local acceptance of the tenure being reorged's first block (whichever comes first). [2](#0-1) 

The intended semantic is "how much lead time did the established tenure's first block have before the next sortition arrived; if very little, it's fair to let the new miner reorg it (it didn't have time to RBF)". This is a legitimate, intentionally documented and tested mechanism (`first_proposal_burn_block_timing_secs`, tests `check_parent_tenure_choice_reorg_timing_ok/bad`, `allow_reorg_within_first_proposal_burn_block_timing_secs`). The bug is in the *implementation* of that intent: the subtraction assumes `approved_at <= sortition_state_received_time`. Nothing in the code enforces or checks this ordering, and `saturating_sub` silently floors any inversion to `0`, which is indistinguishable from "the tenure's block truly arrived at essentially the same instant as the sortition." A `0` result is always `< first_proposal_burn_block_timing` (any positive configured value), so the check unconditionally falls into the "poorly timed -> permit reorg" branch whenever the local approval timestamp is recorded at or after the new burn-block-receipt timestamp - regardless of how long the tenure had actually been running.

Such an inversion is entirely plausible without requiring any majority, other signers' keys, or node access: a signer's local `approved_time` is only stamped when its own processing pipeline gets around to marking the block pre-committed/locally-accepted, and event processing (validation round-trips, StackerDB message arrival, event-loop scheduling) is asynchronous relative to burn-block arrival. A miner who deliberately delays broadcasting (or is slow to have its tenure's first block accepted, e.g. because the block was queued behind other pending validations) can cause `approved_at` for that tenure to be recorded moments after the next burn block/sortition is received by the same signer, even though the tenure itself was live, canonical, and its block genuinely produced well before the sortition in real (bitcoin/network) time. From the signer's point of view, the only ordering it can observe is these two local timestamps, and the arithmetic misreads a late *recording* as a late *event*.

Once misclassified, `record_superseded_tenure` marks the victim tenure as `superseded_tenures`, which causes `get_signed_conflicts`/`reorg_permit_stands` to stop treating this signer's own already-cast signature over the victim block as a conflict: [3](#0-2) 

This is precisely the equivocation-guard bypass the mechanism exists to gate: the signer is induced to sign a new, conflicting/reorging block that supersedes a tenure it had already signed and that was, in reality, properly established - i.e., signing a non-canonical/conflicting block relative to what should have remained canonical.

### Impact Explanation
This breaks the "approved-parent vs. canonical" / equivocation-guard equality that the reorg-timing rule and `reorg_permit_stands`/`get_signed_conflicts` machinery are designed to enforce: the signer sanctions (and later signs) a reorg of a tenure it already validated and signed, based on a corrupted/underflowed timing measurement rather than the real elapsed time. This matches the Critical impact bucket: "a signer signing an invalid, non-canonical, or conflicting block." Because every honest signer independently evaluates `check_parent_tenure_choice` against its own local clocks, and the exploit condition (local approval timestamp landing after local burn-block-receipt timestamp) is plausible under ordinary asynchronous processing delays that a single miner can amplify by delaying block broadcast, a lone miner (plus normal gossip/propagation) can potentially cause a threshold of signers to sanction and sign an improper reorg without needing any other signer's cooperation, key, or a majority coalition.

### Likelihood Explanation
The exploit requires the attacking miner to control (or influence) the relative timing between (a) when it finally gets its first tenure block accepted by signers and (b) when it wins/produces the very next sortition, such that the signers' local `approved_at` stamp lands at or after their local `sortition_state_received_time` stamp. This is a timing condition rather than a pure logic guarantee - it depends on real-world latencies (validation round-trip time, StackerDB propagation, event-loop scheduling) that a miner can nudge (e.g., by delaying block broadcast, or by working to win back-to-back sortitions quickly) but not perfectly dictate across all signers simultaneously. It is therefore a plausible-but-condition-dependent race rather than a trivially deterministic exploit, and it is the type of edge case that would not necessarily be caught by the existing tests (`check_parent_tenure_choice_reorg_timing_ok/bad`), which construct `sortition_timing_secs` values that are always assumed positive relative to proposal time and never exercise the inverted-timestamp underflow path.

### Recommendation
Do not rely on unchecked `saturating_sub` between two independently-stamped local wall-clock values to infer "elapsed time until sortition." Explicitly detect and handle the inversion case (`approved_at > sortition_state_received_time`): treat it as "cannot determine timing" (analogous to the existing "no local knowledge" branch, which conservatively refuses the reorg: `return Ok(false)`), rather than silently interpreting the saturated `0` as evidence of poor timing. More generally, prefer a monotonic/consensus-visible timestamp (e.g., derived from burn-chain timestamps rather than each signer's own local processing clock) for this decision so that processing delays on one signer cannot bias its verdict on whether a reorg is fair.

### Proof of Concept
1. Miner M produces the first (and only) block of tenure A; several signers pre-commit/locally-accept it, each stamping their own `approved_time` at that moment (`t0`).
2. M deliberately delays finalizing/broadcasting or otherwise causes at least one signer's block-validation/acceptance pipeline for tenure A's block to be queued/delayed so that its local `approved_time` for A does not get stamped until `t1`.
3. M quickly wins the next sortition (tenure B) and that signer records `sortition_state_received_time = t2`, where `t0 < t2 <= t1` (the signer's local approval bookkeeping for A completes at/after B's burn block is recorded, even though A was genuinely produced well before B's sortition in real time).
4. M proposes tenure B's first block, reorging tenure A. `check_parent_tenure_choice` computes `proposal_to_sortition = t2.saturating_sub(t1) = 0` (since `t1 >= t2`), which is `< first_proposal_burn_block_timing`, so tenure A is added to `superseded_tenures` and the reorg is permitted.
5. The signer signs B, and per `record_superseded_tenure`/`get_signed_conflicts`, its earlier signature over A's block no longer blocks B - the signer has now signed a block that reorgs a tenure it should have protected, despite A having been properly established (not actually poorly timed).

Note: Exact reproducibility of step 2/3's exploitable ordering under real network conditions was not verified end-to-end in this review (it depends on scheduler/validation timing that could not be measured from static code alone); this PoC describes the code path and the precise arithmetic condition that triggers it, based on [1](#0-0) .
