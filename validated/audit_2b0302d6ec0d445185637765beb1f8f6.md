### Title
Multisig Factory `create()` has no uniqueness check or refund callback, permanently freezing NEAR deposits when the target account name is front-run - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` derives the new multisig account solely from a caller-supplied `name` (`format!("{}.{}", name, env::current_account_id())`) with no check that the name is unused and no `.then()` callback to detect and refund a failed deployment, unlike the sibling `lockup-factory` and `staking-pool-factory` contracts in the same repository, which both implement this safeguard. [1](#0-0) 

### Finding Description
`create` builds the deterministic account id purely from the attacker/user-controlled `name` parameter — it is never bound to `members` or `num_confirmations`, and there is no on-chain registry (like `staking_pool_account_ids` in `staking-pool-factory`) preventing the same `name` from being submitted twice: [2](#0-1) 

The batched promise (`create_account().deploy_contract(...).transfer(deposit).function_call("new", ...)`) is a single receipt sent to `account_id`. If that account already exists (e.g., because another party — attacker or otherwise — raced ahead and created `name.factory` first with different `members`/`num_confirmations`), the `create_account` action fails and the whole receipt fails atomically; none of its actions (including the `.transfer(env::attached_deposit())`) execute. Because `MultisigFactory::create` returns the promise directly with **no `.then()` callback**, there is no logic analogous to `on_lockup_create` in `lockup-factory` that detects `is_promise_success()` and returns the deposit to `predecessor_account_id`: [3](#0-2) 

`staking-pool-factory` similarly protects itself by tracking every created `staking_pool_account_id` in an `UnorderedSet` and asserting uniqueness before ever creating a promise, so a duplicate name is rejected up-front and the deposit is never spent: [4](#0-3) 

`multisig-factory` has neither of these protections. This is the direct analog of the ERC4337 report's binding failure: the deterministic destination address (`account_id`/salt) is not cryptographically tied to the identity that is supposed to control the resulting account (`members`), so whoever's transaction lands first on a given `name` claims that account, while the loser's attached NEAR silently disappears from user control.

### Impact Explanation
When the raced `create()` call fails because the account already exists, the receipt (and its `.transfer()` action) never executes. NEAR's protocol refunds any unspent deposit from a failed receipt back to the *predecessor of that receipt* — which is the `multisig-factory` contract itself, not the original caller. Because there is no callback to forward that refund on to `env::predecessor_account_id()`, the caller's attached NEAR becomes stuck in the factory's own balance with no method exposed to recover it. This satisfies the "funds permanently frozen" Critical impact: a user's deposited NEAR is retained by the factory, inaccessible to the depositor.

### Likelihood Explanation
`name` is entirely caller-chosen and unchecked, so any two parties (malicious or simply uncoordinated, e.g. two users independently trying to name their multisig "treasury") can collide on the same prefix. An attacker specifically watching the mempool for `create()` calls with an attractive `name` and a non-trivial attached deposit can trivially front-run with the same `name`, guaranteeing the victim's subsequent `create_account` action fails and their deposit becomes stranded in the factory.

### Recommendation
Add the same safeguards already present elsewhere in this repository:
1. Maintain a persistent set of already-created multisig account ids (like `staking_pool_account_ids`) and `assert!` that the derived `account_id` is not already registered before issuing the promise.
2. Add a `.then()` callback (mirroring `on_lockup_create`/`on_staking_pool_create`) that checks `is_promise_success()` and refunds `env::attached_deposit()` to `env::predecessor_account_id()` if the underlying account creation failed.

### Proof of Concept
1. Alice calls `create({ "name": "treasury", "members": [alice_key], "num_confirmations": 1 })` on `multisig-factory` with an attached deposit, intending to create `treasury.multisigfactory`.
2. Bob observes Alice's pending transaction and submits `create({ "name": "treasury", "members": [bob_key], "num_confirmations": 1 })` with a minimal deposit, and it lands first.
3. `treasury.multisigfactory` is created and controlled by Bob.
4. Alice's transaction executes afterward; the `create_account` action for `treasury.multisigfactory` fails because the account already exists, so the entire batched receipt (including the `.transfer()` of Alice's deposit) fails.
5. Because `MultisigFactory::create` has no `.then()` refund callback, Alice's attached NEAR is absorbed into the factory contract's own balance and is not returned to her — permanently frozen from her perspective, with `treasury.multisigfactory` now controlled solely by Bob instead of Alice as intended.

    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())

                    .as_bytes()
                    .to_vec(),
                0,

            )
    }

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
