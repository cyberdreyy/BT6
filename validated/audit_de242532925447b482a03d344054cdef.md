### Title
Unauthenticated mutation of `BlockRejection` reason/reason-code fields — signature does not cover them - ([File: libsigner/src/v0/messages.rs])

### Summary
The bug class in the external report is that a bundled sub-transaction is individually signed but nothing binds it to the bundle it was submitted in, so it can be extracted and replayed in a different context while its signature still verifies. The structural analog in this repo is `BlockRejection`: the signer's signature covers only `signer_signature_hash` and `chain_id`, not the `reason`, `reason_code`, or `response_data` (which carries the actual `RejectReason` consumed by the state machine). Anyone relaying the StackerDB chunk — the miner, another node, or any StackerDB observer — can rewrite those unsigned fields while the signature still verifies successfully.

### Finding Description
`BlockRejection::hash()` builds the signed digest from only two inputs: [1](#0-0) 

`verify()`/`recover_public_key()` recompute this same restricted digest: [2](#0-1) 

But the struct carries much more consensus-relevant state that is never part of the signed preimage: `reason` (free-form string), `reason_code` (`RejectCode`, which can encode a `ValidateRejectCode`), and `response_data` (which embeds the actual `RejectReason` used downstream): [3](#0-2) 

On the receiving signer, `handle_block_rejection` first authenticates the signature, then unconditionally trusts `rejection.response_data.reject_reason` (an unsigned field) to drive the local state machine: [4](#0-3) 

Because `reason`, `reason_code`, and `response_data` (including `reject_reason`) sit outside the signed digest, a relayer can take a genuine, validly-signed rejection from signer S for block B and swap in a different `reason_code`/`reject_reason` (e.g., turn a transient `ConnectivityIssues` into a terminal validation failure, or vice versa) without invalidating `signature`. `is_valid_signer`/`recover_public_key` will still attest the message as authentically from S, even though S never actually rejected the block for that reason.

This is exactly the auction-transaction pattern: a component (the reject reason) that is logically part of a signed statement is not actually inside the cryptographic commitment, so it can be detached and resubstituted by anyone who can observe/relay the message, without needing the signer's key or a signer majority.

### Impact Explanation
`RejectReason`/`reason_code` values feed the reject-reevaluation logic (`should_reevaluate_reject_reason`, documented in `docs/signer-flows.md` sections 2–3) and downstream monitoring/decision paths in the node's `stackerdb_listener.rs` and `stacks-signer` state machine. A relayer that can rewrite the reason on an authentic-looking rejection can:
- Make a rejection appear as a non-re-evaluable/terminal rejection when it was actually a transient one (e.g., `ConnectivityIssues`), potentially causing peers to treat a signer's stance as more permanent/authoritative than it is and skip re-evaluating a block that should be reconsidered — a liveness degradation for that block/proposal.
- Or the reverse: downgrade a substantive rejection reason to one that other signers treat as re-evaluable, encouraging repeated re-submission/re-validation cycles.

This does not directly let an attacker forge an *acceptance* signature or make a signer sign an invalid block, so it does not reach the "Critical" bar (signing invalid/non-canonical/conflicting block, rejection recounted as acceptance, cross-context-valid *acceptance* signature). It falls short of the strict "rejection recounted as an accept" because the message is still recognized and processed as a rejection — only its stated *reason* is forgeable, not its outcome. Given the strict output bar requiring a concrete safety break (invalid/non-canonical/conflicting signature, miscounted response, or cross-context signature) or a liveness wedge, and given I could not fully trace `should_reevaluate_reject_reason`'s exact branching to confirm a genuine wedge (my final tool-call budget ran out before reading that function body in `stacks-signer/src/v0/signer.rs`), I cannot certify this as meeting the required High/Critical bar with the evidence gathered.

### Likelihood Explanation
Uncertain/incomplete — requires confirming that `should_reevaluate_reject_reason` (and any other consumer of `RejectCode`/`RejectReason` from a peer's `BlockRejection`) can be driven into a liveness-relevant branch purely by an unsigned reason substitution, and confirming there is no additional binding check I missed. I was not able to view that function's body before running out of iterations.

### Recommendation
Include `reason_code`, `response_data` (or at minimum its `reject_reason`/timestamps), and `chain_id`-dependent fields inside the `BlockRejection::hash()` preimage so the full semantic content of the rejection is authenticated, not just the block hash being rejected. Apply the same audit to `BlockAccepted`/`BlockResponseData` to ensure no other "outcome vs. metadata" split exists (e.g., `metadata.server_version`, `response_data.tenure_extend_timestamp` are also unsigned; confirm they are not treated as trust-bearing for correctness-relevant decisions).

### Proof of Concept
Not independently exercised in this pass. Conceptually: capture a genuine `BlockRejection` chunk broadcast by signer S for a block (signature valid over `hash()` = domain(`block-rejection`,`chain_id`) ⊕ `signer_signature_hash`), then modify `reason`, `reason_code`, and `response_data.reject_reason` in the re-serialized chunk before it reaches other signers/observers. Because `verify()` only recomputes the digest from `signer_signature_hash`/`chain_id`, the tampered rejection still verifies as signed by S, per [5](#0-4) .     /// The signature hash for the block rejection
    pub fn hash(&self) -> Sha256Sum {
        let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
        let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
        structured_data_message_hash(data, domain_tuple)
    }

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
