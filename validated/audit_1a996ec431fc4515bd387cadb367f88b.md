### Title
JWT replay-protection check-then-act race in Gateway HTTP Trigger authorization allows single JWT to authorize multiple concurrent workflow trigger requests - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize()` — the JWT-authentication gate for the internet-facing HTTP Trigger capability handler in the Gateway — checks whether a JWT ID (`jti`) has been used via `jwtCache.isReplay()` and later marks it used via `jwtCache.recordUsage()`, but these are two independent, separately-locked operations rather than one atomic check-and-set. This mirrors the report's bug class: two mutating/reading operations on shared state that are individually safe but not coordinated with each other, creating a race window.

### Finding Description
`jwtReplayCache` guards its map with a `sync.RWMutex`, but exposes `isReplay` (RLock) and `recordUsage` (Lock) as separate methods, each acquiring and releasing the lock independently: [1](#0-0) 

`Authorize()` calls them non-atomically, with unrelated authorization work (workflow lookup, signer authorization) happening in between: [2](#0-1) 

Because `isReplay` releases its lock before `recordUsage` acquires its own, two (or more) concurrent calls to `Authorize()` with the same JWT (`claims.ID`) can both observe `isReplay(claims.ID) == false` before either has called `recordUsage`. Both calls then proceed to pass the signer-authorization check and both return a valid `AuthorizedKey`, i.e., the replay guard is bypassed under concurrency — exactly the same "two independently-safe but uncoordinated operations create a race window" pattern flagged in the external report for `addPendingCommission`/`resetPendingCommission`.

This function is reached directly from unprivileged network input: `httpTriggerHandler.authorizeRequest()` calls `workflowMetadataHandler.Authorize()` as part of handling every inbound `HandleUserTriggerRequest` from the Gateway's user-facing HTTP endpoint: [3](#0-2) [4](#0-3) 

Since the request is dispatched to the DON before the JWT is registered as used, an attacker fully controls the timing by simply sending the same signed request multiple times in parallel — no privileged access, node compromise, or network-layer manipulation is required.

### Impact Explanation
JWT `jti`-based replay protection exists specifically to prevent a single signed trigger authorization from being used more than once. Bypassing it via concurrent submission allows an unprivileged caller in possession of one valid signed JWT to trigger the same workflow execution multiple times concurrently ("unauthorized job run" / duplicate execution), which can cause duplicate state changes, redundant external side effects, or resource exhaustion depending on what the workflow does. The impact is bounded by the fact that the caller must already have a validly-signed request (this is not a full authentication bypass), so severity is Medium rather than Critical.

### Likelihood Explanation
Likelihood is Medium: the race window only requires two ordinary HTTP requests carrying the identical JWT to arrive close together (attacker fully controls this, no other conditions are required), and Go's default `RWMutex` behavior does not serialize this check-then-set sequence. No node compromise or non-standard access is needed — any client capable of obtaining/replaying one signed JWT can attempt the race.

### Recommendation
Merge `isReplay` + `recordUsage` into a single atomic "check-and-set" operation performed under one lock acquisition, e.g.:
```go
func (cache *jwtReplayCache) checkAndRecord(jti string) bool {
    cache.mu.Lock()
    defer cache.mu.Unlock()
    if _, exists := cache.cache[jti]; exists {
        return false
    }
    cache.cache[jti] = time.Now()
    return true
}
```
and call this once in `Authorize()` immediately after JWT verification (before doing further authorization work), returning the "already used" error if it returns `false`. This closes the TOCTOU window entirely, consistent with the report's recommendation to use a single atomic read-and-mutate operation rather than two independently-coordinated calls.

### Proof of Concept
1. Attacker signs one valid `HTTPTriggerRequest` JWT with a fresh `jti` for an authorized workflow signer.
2. Attacker fires N (e.g., 10) concurrent HTTP requests to the Gateway's user-facing HTTP Trigger endpoint using the identical JSON-RPC request/JWT.
3. Each request lands in `httpTriggerHandler.HandleUserTriggerRequest` → `authorizeRequest` → `WorkflowMetadataHandler.Authorize`.
4. Multiple goroutines execute `isReplay(claims.ID)` before any of them executes `recordUsage(claims.ID)`, since these are separate lock acquisitions with authorization/workflow-lookup work interleaved.
5. More than one request passes authorization and is forwarded to the DON as a legitimate trigger, despite carrying the same one-time JWT — demonstrating the replay-protection bypass.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)

	}
	return key, nil
}
