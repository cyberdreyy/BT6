### Title
Unprivileged lender permanently/temporarily bricks prefunded `stopEpochWithDuration` with a dust `requestDeposit` - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
In the prefunded-epoch variant, `stopEpochWithDuration` atomically settles the AA prefunded queue via `IdleCDOEpochVariantPrefunded._afterStopEpochWithDuration`, which calls `IdleCDOEpochQueue.prefundedDepositsToProcess()`. That view reverts whenever `epochPendingDeposits[epoch] != 0` — even when there is nothing prefunded to settle — reverting the entire stop transaction. Any KYC-passing lender can leave a 1-wei `requestDeposit` in the AA queue; once `prefundedDepositWindow` has not been reached (or is configured as `0`, its default, which permanently disables `processDepositsToBorrower`), there is no way to clear the pending deposit, so the epoch can never be stopped.

### Finding Description
The external report is a resource-exhaustion / gating DoS. The on-chain analog is a gating DoS on the epoch state machine, where the gate is a queue invariant rather than a connection table.

Relevant flow:

- `IdleCDOEpochQueue.requestDeposit(amount)` takes underlying from any allowed (epoch running + `isWalletAllowed`) wallet and increments `epochPendingDeposits[nextEpoch]` (lines 103–127). For the AA prefunded queue, deposits are blocked only after `epochPrefundedDeposits[nextEpoch] != 0` or once `block.timestamp + prefundedDepositWindow >= epochEndDate` (lines 111–117). There is no minimum amount and no cap on the number of depositors — 1 wei suffices.
- `IdleCDOEpochQueue.processDepositsToBorrower()` is the only way to convert `epochPendingDeposits` into `epochPrefundedDeposits`, and it is owner/manager-only and reverts unless `block.timestamp + prefundedDepositWindow >= epochEndDate` and `prefundedDepositWindow != 0` (lines 149–179). With `prefundedDepositWindow == 0` (the storage default; `setPrefundedDepositWindow` accepts any value, line 95–99), this path is permanently dead.
- `IdleCDOEpochQueue.prefundedDepositsToProcess()` reverts on `epochPendingDeposits[_epoch] != 0` unconditionally (lines 277–282), before `_afterStopEpochWithDuration` can check `_prefunded == 0` and return early (contracts/IdleCDOEpochVariantPrefunded.sol lines 76–78).
- `IdleCDOEpochVariantPrefunded._afterStopEpochWithDuration()` runs inside `stopEpochWithDuration`, so the queue revert bubbles up and reverts the whole stop (lines 72–89). The direct `stopEpoch` selector is blocked whenever a queue is configured (`_beforeStopEpoch`, lines 39–48), leaving no alternate stop path.
- `deleteRequest` cannot clear the attacker entry for anyone but the attacker, and the attacker simply does not call it (lines 184–199).

Broken invariant: the epoch state machine must always be able to transition running → buffer, and "a single dust queued deposit must not halt settlement." An unprivileged KYC'd lender controls a storage flag that vetoes the privileged `stopEpochWithDuration`.

### Impact Explanation
- Temporary freezing of all vault funds: while `block.timestamp + prefundedDepositWindow < epochEndDate` (the majority of the epoch when the window is a small tail cutoff, e.g. 5 days of a 90-day epoch), the manager cannot stop the epoch — cannot recall principal, realize losses, settle accounting, or process withdrawals — because the attacker's dust pending deposit makes `prefundedDepositsToProcess` revert, and prefunding is itself gated until the window. The attacker can re-dust every epoch for ~1 wei each.
- Permanent freezing in the `prefundedDepositWindow == 0` configuration: `processDepositsToBorrower` can never run, `requestDeposit` never closes, so the first pending deposit permanently bricks `stopEpochWithDuration`; borrower principal and all pending/queued withdrawals are frozen until governance removes `epochQueue` entirely (stranding all queue users' deposits/withdraw requests).
- Mirrors the advisory's shape: the mitigation is operational (manager must prefund and time stops), not a code fix, and the attack cost is negligible versus the frozen TVL.

### Likelihood Explanation
- Attacker profile is in scope: `_checkAllowed` only requires the epoch to be running and `isWalletAllowed` — any KYC-passing lender qualifies.
- Cost is 1 wei of underlying plus gas; `userDepositsEpochs`/`epochPendingDeposits` accept arbitrary small amounts with no minimum.
- Guard review: `_skimDonatedAssets` is irrelevant (these are accounted deposits, not raw donations); `checkPrefunding`/`_guarded` do not bound depositor count or minimums; the `EpochNotRunning` gate doesn't help because requests are placed mid-epoch and persist; `epochPrefundedDeposits != 0` blocks *new* deposits after prefunding but cannot remove the pending entry that already exists, and prefunding is unavailable before the window.
- The only escape is owner unsetting `epochQueue` (losing queue accounting) or waiting for the window — a real freeze, not a self-DoS.

### Recommendation
- In `IdleCDOEpochQueue.prefundedDepositsToProcess()` / `processPrefundedDeposits()`, treat small pending remnants as cancellable: allow `stopEpochWithDuration` to proceed when pending deposits exist by refunding `epochPendingDeposits[_epoch]` pro-rata back to `userDepositsEpochs` claimable state (e.g., keep entries claimable via `deleteRequest`), instead of reverting.
- Alternatively, enforce a minimum `requestDeposit` amount and/or snapshot-and-close the AA queue automatically at `stopEpoch` (move any residual pending deposits to a refundable state), and forbid `prefundedDepositWindow == 0` in `setPrefundedDepositWindow` when the prefunded queue is enabled.

### Proof of Concept
```solidity
// test/foundry/PrefundedStopEpochDos.t.sol
// Attacker: any KYC-passing EOA (`isWalletAllowed` true, mocked Keyring).
function testDustDepositBlocksStopEpoch() external {
    address attacker = makeAddr("attacker");
    vm.prank(manager);
    cdoEpoch.setEpochQueue(address(queue));
    // Case A: window left at default 0 -> processDepositsToBorrower can never run
    // Case B: window > 0 but not yet reached (now < epochEndDate - window)

    // Epoch running; attacker queues a 1-wei AA deposit for the next epoch
    deal(address(underlying), attacker, 1);
    vm.startPrank(attacker);
    underlying.approve(address(queue), 1);
    queue.requestDeposit(1);            // epochPendingDeposits[nextEpoch] = 1
    vm.stopPrank();

    // Manager cannot clear it before the window:
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    queue.processDepositsToBorrower();   // reverts: window==0 or window not reached

    // Attacker refuses deleteRequest; manager tries to stop the epoch:
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), 0);
    // -> _afterStopEpochWithDuration -> prefundedDepositsToProcess()
    //    reverts on epochPendingDeposits != 0. Epoch never stops:
    // borrower principal and all withdrawals frozen.
}
```

Uncertainty: whether `prefundedDepositWindow == 0` is a reachable production configuration depends on `IdleCreditVaultFactory`/orchestrator defaults, which I could not fully verify within the iteration budget; the temporary-freeze variant (window > 0, stop attempted before the cutoff) holds regardless of configuration.
