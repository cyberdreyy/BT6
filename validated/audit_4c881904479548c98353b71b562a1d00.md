Based on my investigation, I found a genuine analog of the "pause only blocks future writes, not previous state" bug class in the `WorkflowMetadataHandler`'s authorized-key revocation path for HTTP Trigger requests.

### Title
Revoked HTTP Trigger authorized keys remain valid until the aggregator's observation naturally expires, allowing continued impersonation with a revoked key - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The gateway's `WorkflowMetadataHandler` grants JWT-signing authorization to a workflow's `authorizedKeys` set via Byzantine fault-tolerant aggregation of node-reported metadata [1](#0-0) . When a workflow owner rotates/revokes a signing key (the "pause" analog), the revocation is not applied by actively removing the old key — it only takes effect once the aggregator's prior quorum observation for that key ages out via `reapObservations` and a fresh sync cycle occurs. Meanwhile, `Authorize()` continues accepting any signer present in the last-synced `authorizedKeys` map, with no revocation/version check.

### Finding Description
`WorkflowMetadataHandler.Authorize` checks only three things: JWT signature validity, JWT-ID replay, and membership of the signer's key in the currently cached `authorizedKeys[workflowID]` map [2](#0-1) . That cache is populated purely by `syncMetadata`, which pulls from per-shard `WorkflowMetadataAggregator.Aggregate()` results [3](#0-2) .

The aggregator itself is append-only per digest: `Collect` adds a node's vote for a specific `WorkflowMetadata` digest (which includes the whole `AuthorizedKeys` list) and only removes a node's vote for that digest when `reapObservations` detects the vote is older than `cleanupInterval` [4](#0-3) . There is no explicit "this key was removed / this metadata was superseded" signal — an old, revoked-key metadata observation simply stays above threshold and keeps being returned by `Aggregate()` until it individually times out from every reporting node's per-node `observedAt` map.

This is structurally identical to the NFTFloorOracle bug: `setPause`/key-rotation is meant to invalidate a previously-granted trust decision, but the read path (`Authorize`) keeps trusting the stale, cached "authorized" state for a window determined by cache/reap timing rather than being denied immediately. There is no cross-check against a canonical, current source of truth (e.g., a fresh workflow-registry lookup) at authorization time; `Authorize` trusts only the locally cached snapshot.

### Impact Explanation
An unprivileged actor holding a revoked/rotated private key can continue signing valid JWTs and successfully invoke `MethodWorkflowExecute` HTTP-trigger requests against the workflow, impersonating the workflow, until the stale observation is reaped and the metadata handler's next sync cycle removes the old key. This is a genuine authentication/authorization bypass window for a specific, previously-legitimate key that the owner explicitly intended to disable — mirroring the "pause only affects future" pattern from the report (write-path decision does not retroactively invalidate the read/auth-path's cached trust).

### Likelihood Explanation
This requires (a) an actor already possessing (or having compromised) a previously-valid signing key for a workflow, and (b) acting within the reap/sync window after the owner revokes/rotates keys. It is not a trivial always-exploitable bug, but it is a real design gap reachable by any external, unprivileged HTTP-trigger caller who already has an old key — no privileged/gateway/operator access is needed to exploit the window, only knowledge of the compromised key, which is exactly the scenario a revocation is meant to close.

### Recommendation
Do not rely solely on the locally aggregated/cached `authorizedKeys` snapshot for authorization decisions. Either (1) version/generation-stamp each `WorkflowMetadata` observation and always compare against the *most recently observed* generation per workflow rather than allowing an old cached digest to remain valid, explicitly evicting older key sets for a workflow ID once a newer one reaches quorum, or (2) reduce `cleanupInterval`/aggregation cadence and treat "authorized" as best-effort, or (3) add a live authorization double-check against a canonical, near-real-time source for sensitive/high-value trigger executions, analogous to adding `whenNotPaused` to the read path in the referenced report.

### Proof of Concept
1. Workflow `W` registers with authorized signing key `K1`; `syncMetadata` populates `authorizedKeys[W] = {K1}` after quorum is reached [5](#0-4) .
2. The workflow owner rotates the key (compromise response) to `K2`, and pushes new metadata with `AuthorizedKeys=[K2]`. Nodes report this new metadata; the aggregator adds a new digest observation for `K2`'s metadata, but the old `K1` digest observation is not proactively deleted — it only stops being counted once every reporting node's vote ages past `cleanupInterval` in `reapObservations` [4](#0-3) .
3. Because `Aggregate()` returns *all* digests still meeting threshold (sorted by sequence, newest first) and `syncMetadata`'s "Case 1: idExists" logic only appends a shard to `workflowShards` for a matching workflow reference — it does not de-duplicate/replace by workflow ID when two different digests (old K1 metadata vs new K2 metadata) exist for the same reference simultaneously (see Case 1 vs Case 3 logic) [6](#0-5) , the ordering/timing of which observation "wins" for `authorizedKeys[W]` during the transition period is dependent on cache/reap timing, not an explicit revocation signal.
4. Until the old observation is reaped, an attacker holding `K1` can still produce a validly-signed request accepted by `Authorize()`.

**Uncertainty**: I was not able to fully trace whether `syncMetadata`'s per-shard `Aggregate()` guarantees a strict "newest observation per workflow ID always overwrites older ones in the same tick" ordering (sequence-based sort suggests newest-first is attempted), or whether both an old and new key set could coexist as separate quorum-satisfying digests during the transition and be non-deterministically combined/dropped. Confirming the exact window size and whether `K1` can be used *simultaneously* with `K2` being valid would require tracing `reapObservations`'s per-node timing more closely or running the actual aggregator code, which is best done with a full Devin session that can execute the tests in `core/services/gateway/common/aggregation/workflow_metadata_aggregator_test.go` and `workflow_metadata_handler_test.go`.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

// syncMetadata aggregates the authorized keys and workflow selectors from each
// shard's WorkflowMetadataAggregator and updates the local cache. A workflow is
// considered assigned to a shard once that shard's aggregator reports it (i.e.
// F+1 of the shard's nodes observed it).
func (h *WorkflowMetadataHandler) syncMetadata(ctx context.Context) {
	authorizedKeys := make(map[string]map[gateway.AuthorizedKey]struct{})
	workflowRefToID := make(map[workflowReference]string)
	workflowIDToRef := make(map[string]workflowReference)
	workflowShards := make(map[string][]*shardEndpoint)

	for _, shard := range h.shards {
		agg := h.aggs[shard.donID]
		metadata := agg.Aggregate()
		for _, data := range metadata {
			workflowID := data.WorkflowSelector.WorkflowID
			workflowRef := workflowReference{
				workflowOwner: data.WorkflowSelector.WorkflowOwner,
				workflowName:  data.WorkflowSelector.WorkflowName,
				workflowTag:   data.WorkflowSelector.WorkflowTag,
			}

			// Case 1: this workflow ID was already registered. If the reference
			// matches, this is the same workflow reported by another shard —
			// append the shard to its fan-out list. If the reference differs,
			// it's a conflicting observation; drop it.
			if existingRef, idExists := workflowIDToRef[workflowID]; idExists {
				if existingRef == workflowRef {
					workflowShards[workflowID] = append(workflowShards[workflowID], shard)
				} else {
					h.lggr.Debugw("Duplicate workflow ID with conflicting reference, dropping",
						"workflowID", workflowID, "existingRef", existingRef, "conflictingRef", workflowRef)
				}
				continue
			}

			// Case 2: this workflow reference was already registered under a
			// different workflow ID. First-wins by reference; drop the duplicate.
			if _, refExists := workflowRefToID[workflowRef]; refExists {
				h.lggr.Debugw("Duplicate workflow reference found, dropping",
					"workflowRef", workflowRef, "workflowID", workflowID)
				continue
			}

			// Case 3: new workflow ID and reference — register it.
			workflowIDToRef[workflowID] = workflowRef
			workflowRefToID[workflowRef] = workflowID
			authorizedKeys[workflowID] = make(map[gateway.AuthorizedKey]struct{})
			for _, key := range data.AuthorizedKeys {
				authorizedKeys[workflowID][key] = struct{}{}
			}
			workflowShards[workflowID] = append(workflowShards[workflowID], shard)
		}
	}

func (agg *WorkflowMetadataAggregator) reapObservations(ctx context.Context) {
	agg.mu.Lock()
	defer agg.mu.Unlock()
	now := time.Now()
	var expiredCount int
	for node, digestObservedAt := range agg.observedAt {
		for digest, observedAt := range digestObservedAt {
			if now.Sub(observedAt) > agg.cleanupInterval {
				delete(agg.observedAt[node], digest)
				if len(agg.observedAt[node]) == 0 {
					delete(agg.observedAt, node)
				}
				_, ok := agg.observations[digest]
				if !ok {
					agg.lggr.Warnw("Observation digest not found in observations", "digest", digest, "node", node)
					continue
				}
				agg.observations[digest].nodes.Remove(node)
				if len(agg.observations[digest].nodes) == 0 {
					delete(agg.observations, digest)
				}
				expiredCount++
			}
		}
	}
	if expiredCount > 0 {
		agg.metrics.IncrementMetadataObservationsCleanUpCount(ctx, int64(expiredCount), agg.lggr)
		agg.lggr.Debugw("Removed expired callbacks", "count", expiredCount)
	}
	agg.metrics.RecordMetadataObservationsCount(ctx, int64(len(agg.observations)), agg.lggr)
}
