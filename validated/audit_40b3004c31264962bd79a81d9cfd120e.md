### Title
Vault gateway replay guard is recorded at authorization time, before secret-store execution, permanently blocking legitimate retries after transient failures - ([File: core/capabilities/vault/authorizer.go], [File: core/capabilities/vault/request_replay_guard.go], [File: core/capabilities/vault/gw_handler.go])

### Summary
The Vault gateway request pipeline records a request's replay-guard digest as "seen" during `AuthorizeRequest`, which runs *before* the actual secret-store operation (`CreateSecrets`/`UpdateSecrets`/`DeleteSecrets`) executes on the node. If that downstream operation fails for any transient reason (secrets-service error, gateway-to-node timeout, node crash), the client's identical retry with the same request digest is rejected with `ErrRequestAlreadySeen`, even though the original operation never completed. This is structurally the same bug class as the reported TOTP-lock issue: a single-use dedup/lock token is set on the "attempt" step rather than on confirmed success, permanently defeating retries and potentially leaving the client unable to ever re-submit that exact request.

### Finding Description
The gateway-routed Vault pipeline is documented as: `ValidateStructureBeforeAuth → AuthorizeRequest → Prefix ID → StampAuthorizedParams` [1](#0-0) .

`AuthorizeRequest` calls the replay guard's `CheckAndRecord` using the request digest, and immediately records the digest as seen if not already present — this happens before any secret is actually created/updated/deleted: [2](#0-1) 

`RequestReplayGuard.CheckAndRecord` unconditionally marks the digest "seen" on the first call and returns `ErrRequestAlreadySeen` on any later call with the same digest before expiry — there is no mechanism to un-record a digest if the downstream operation subsequently fails: [3](#0-2) 

After authorization succeeds, the actual work happens later in `GatewayHandler.HandleGatewayMessage`, which calls `handleSecretsCreate` / `handleSecretsUpdate` / `handleSecretsDelete`, each of which can fail independently of authorization (e.g. `h.secretsService.CreateSecrets` returning an error) and only then returns an error response to the client: [4](#0-3) [5](#0-4) 

Because the digest is recorded at the authorization step (which precedes the actual `secretsService` call), a client that receives an error response for `MethodSecretsCreate`/`Update`/`Delete` and retries with the *same* JSON-RPC request/digest (the natural way to retry an idempotent-looking write) will hit `ErrRequestAlreadySeen` — not because the original write succeeded, but merely because it was *authorized* once. This is confirmed by test-harness code that explicitly special-cases this exact failure mode, and by the surrounding comment which describes the known effect: retries after a gateway-to-node timeout "just hit the vault replay guard ('request was already authorized previously')": [6](#0-5) 

This exactly mirrors the external report's root cause: the "already used" marker (TOTP lock / replay-guard digest) is set on the first *attempt*, not on confirmed completion of the underlying operation, so BullMQ-style (or client-side) retries after a transient downstream failure are permanently blocked.

### Impact Explanation
Impact is medium: legitimate secret-management requests (create/update/delete) that fail transiently after authorization (secrets-service error, node crash, gateway/DON communication timeout) cannot be retried with the original request — the client is stuck with `ErrRequestAlreadySeen` even though no secret was actually written/updated/deleted. This can cause silent write failures perceived as “stuck” by the caller (loss of availability/reliability for secret operations), and forces the caller to fabricate a new request ID/digest to work around the guard, which weakens the intended replay-protection semantics. It does not directly grant unauthorized access or leak secrets, so it falls short of a full compromise, but it is a legitimate reliability/availability defect reachable by any authorized-but-unlucky client.

### Likelihood Explanation
Likelihood is medium: any transient failure between authorization and completion of the secrets operation (a documented, expected class of failures per the test harness's `shouldRetryGatewayRequest`/timeout handling) triggers this condition. Given DON communication over an unreliable gateway relay and independent secrets-service calls, such transient failures are a normal operational occurrence, not a rare edge case.

### Recommendation
Move the replay-guard "commit" (`CheckAndRecord`) to occur only after the underlying secrets operation has been confirmed to succeed, or use a two-phase scheme: mark digest as "in-flight" at authorization time, but roll it back (or never commit permanently) if `handleSecretsCreate`/`Update`/`Delete` returns an error, so a genuinely failed request can be retried. Alternatively, decouple authorization/replay dedup from execution success by keying idempotency on completion rather than authorization, mirroring the report's recommendation to validate/lock only immediately before commit rather than at the start of a retryable attempt.

### Proof of Concept
1. Client sends a `vault.secrets.create` (or update/delete) JSON-RPC request through the gateway to a node.
2. `AuthorizeRequest` succeeds and `RequestReplayGuard.CheckAndRecord(digest, expiresAt)` records the digest as seen [7](#0-6) .
3. `handleSecretsCreate` then calls `h.secretsService.CreateSecrets(ctx, ...)`, which fails (e.g., transient DB/service error) and returns an error response to the gateway/client [8](#0-7) .
4. Client, believing the create failed, retries with the identical request (same digest, same request ID).
5. `AuthorizeRequest` is invoked again; `CheckAndRecord` finds the digest already present (not yet expired) and returns `ErrRequestAlreadySeen`, so the retry is rejected even though the secret was never actually created [9](#0-8) .
6. This matches the documented behavior in the test infrastructure explicitly built to avoid retrying into this exact guard [10](#0-9) .

func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
}

var ErrRequestAlreadySeen = errors.New("request was already authorized previously")

// RequestReplayGuard prevents replay of already-processed requests by tracking
// request digests with expiry timestamps. It is safe for concurrent use.
//
// Used by both the AllowListBasedAuth flow and the JWTBasedAuth flow to ensure
// that a given request digest is only accepted once.
type RequestReplayGuard struct {
	mu      sync.Mutex
	seen    map[string]int64 // digest → unix expiry timestamp
	nowFunc func() time.Time // injectable for testing
}

// NewRequestReplayGuard creates a replay guard for authorized Vault requests.
func NewRequestReplayGuard() *RequestReplayGuard {
	return &RequestReplayGuard{
		seen:    make(map[string]int64),
		nowFunc: time.Now,
	}
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func (h *GatewayHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) (err error) {
	reqLggr := h.requestLogger(req, gatewayID)
	reqLggr.Debugw("received message from gateway", "req", req)

	var response *jsonrpc.Response[json.RawMessage]
	var authResult *AuthResult

	switch req.Method {
	case vaulttypes.MethodSecretsCreate, vaulttypes.MethodSecretsUpdate:
		publicKey, pkErr := h.getMasterPublicKey(ctx)
		if pkErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pkErr)
			break
		}
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, publicKey)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodSecretsDelete, vaulttypes.MethodSecretsList:
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, nil)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodPublicKeyGet:
		response = h.handlePublicKeyGet(ctx, gatewayID, req)
	default:
		response = h.errorResponse(ctx, gatewayID, req, api.UnsupportedMethodError, errors.New("unsupported method: "+req.Method))
	}

	if response == nil {
		switch req.Method {
		case vaulttypes.MethodSecretsCreate:
			response = h.handleSecretsCreate(ctx, gatewayID, req)
		case vaulttypes.MethodSecretsUpdate:
			response = h.handleSecretsUpdate(ctx, gatewayID, req)
		case vaulttypes.MethodSecretsDelete:
			response = h.handleSecretsDelete(ctx, gatewayID, req)
		case vaulttypes.MethodSecretsList:
			response = h.handleSecretsList(ctx, gatewayID, req, authResult)
		}
	}

func (h *GatewayHandler) handleSecretsCreate(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	vaultCapRequest := vaultcommon.CreateSecretsRequest{}
	if err := json.Unmarshal(*req.Params, &vaultCapRequest); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}

	h.lggr.Debugw("Processing authorized create secrets request", "request", vaultCapRequest.String())
	vaultCapResponse, err := h.secretsService.CreateSecrets(ctx, &vaultCapRequest)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.FatalError, err)
	}

	jsonResponse, err := toJSONResponse(vaultCapResponse, req.Method)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.NodeReponseEncodingError, err)
	}
	return jsonResponse
}

func shouldRetryGatewayRequest(statusCode int, body []byte) bool {
	if isGatewayNotAllowlistedError(body) {
		return true
	}
	switch statusCode {
	case http.StatusServiceUnavailable, http.StatusBadGateway, http.StatusGatewayTimeout:
		// Gateway-to-DON timeout: the gateway gave up relaying the response, but the DON likely
		// already processed the request. Retrying the same request body just hits the vault
		// replay guard ("request was already authorized previously"). Don't retry these.
		if bytes.Contains(body, []byte("Request timed out")) {
			return false
		}
		return true
	default:
		return false
	}
}
