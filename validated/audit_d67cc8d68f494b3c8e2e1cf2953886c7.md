### Title
Multisig request executed below effective confirmation threshold due to stale confirmations surviving key/member removal - ([File: multisig/src/lib.rs], [File: multisig2/src/lib.rs])

### Summary
`DeleteKey` (in `multisig/src/lib.rs`) and `DeleteMember` (in `multisig2/src/lib.rs`) only purge outstanding **requests originated by** the removed key/member, and only clear the `confirmations` set **for those same requests**. They never scan the `confirmations` map of *other* pending requests to strip out confirmations that were previously cast by the key/member being removed. Since `confirm()` counts `confirmations.len()` directly against `self.num_confirmations` without re-validating that every entry in the set still corresponds to a currently live member/key, a request can reach and pass the confirmation threshold while one or more of the counted "confirmations" belong to accounts/keys that are no longer members of the multisig at execution time.

### Finding Description
The invariant the multisig is supposed to enforce is:
```
confirmations_counted_for(request) == confirmations_from_currently_live_members(request)
```
This equality is broken as follows:

1. Member/key `M` confirms request `R` that was added by a different member (`confirm()` inserts `M`'s identity into `self.confirmations[R]`). [5](#0-4) 
2. The multisig later removes `M` via a `DeleteMember`/`DeleteKey` action (e.g., because `M`'s key was thought compromised, or as routine membership rotation). `delete_member`/`DeleteKey`'s cleanup only removes requests where `r.member == member` (i.e., requests *added* by `M`), and clears confirmations for *those* request IDs only — `R` (added by someone else) is left untouched, still containing `M`'s stale confirmation entry. [3](#0-2) [1](#0-0) 
3. `assert_valid_request()` only checks that the request/confirmations map entries exist and that the *current caller* is a live member — it never re-validates the historical entries already stored in `confirmations[R]` against the current member set. [6](#0-5) 
4. When remaining live members continue confirming `R`, `confirm()` computes `confirmations.len() as u32 + 1 >= self.num_confirmations` using the raw stored set size, which still includes `M`'s stale entry, and executes the request as soon as the threshold is nominally reached — even though only `num_confirmations - 1` (or fewer) *currently live* members actually participated. [4](#0-3) 

The same pattern exists identically in the plain-key `multisig` contract, where `DeleteKey` only removes requests signed by the deleted `pk`, not that `pk`'s confirmations recorded on other members' requests. [7](#0-6) 

### Impact Explanation
This is a direct instance of the rules' named binding: "confirmations counted versus live members." A pending, not-yet-threshold-met request retains a phantom confirmation from a member who has since been removed. If that member is removed (for any legitimate governance reason — suspected key compromise, employee offboarding, membership rotation) while a malicious or already-approved-but-incompletely-supported `Transfer`/`FunctionCall`/`AddKey` request is still pending, the remaining members' subsequent confirmations can push the request to execution while it was, in reality, only supported by `num_confirmations - 1` currently authorized parties. This lets a multisig request execute below its configured threshold, moving funds or granting access with less authorization than the contract is supposed to guarantee — a Critical impact per the rules ("a multisig request executed below threshold").

### Likelihood Explanation
No privileged action or redeploy is required beyond the multisig's own normal, documented operations (adding requests, confirming, and removing a member/key) — all of which are expected lifecycle events for any long-lived multisig. The attack requires a request to be pending confirmation across a membership change, which is a realistic operational scenario (e.g., rotating a suspected-compromised key while other requests are in flight, or an insider deliberately timing a benign-looking confirmation before requesting their own removal).

### Recommendation
When deleting a key/member, iterate over **all** pending requests' `confirmations` sets (not just requests originated by that key/member) and remove the deleted identity from each. Alternatively, when counting confirmations in `confirm()`/before executing a request, filter `confirmations` to only those entries whose corresponding key/member is still present in the current member/key set, and compare that filtered count against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request` to create request `R` (e.g., `Transfer` funds to an external account).
3. `D` calls `confirm(R)` → `confirmations[R] = {D}` (1/3).
4. Separately, the group agrees to remove `D` (e.g., suspected key leak) via a `DeleteMember` request for `D`, which is confirmed and executed. `delete_member` removes `D` from `self.members` and deletes requests where `r.member == D`, but `R` was added by `A`, so `R`'s stored `confirmations[R] = {D}` is untouched.
5. `B` calls `confirm(R)` → `confirmations[R] = {D, B}` (2/3).
6. `C` calls `confirm(R)` → count becomes `3 >= num_confirmations`, and `R` executes — transferring funds — even though only `A` (implicitly, as request author), `B`, and `C` are currently live members, and `D`'s stale confirmation (from before removal) was counted toward the threshold instead of a confirmation from a genuinely live fourth party.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);

        assert!(

            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************

            ********************************/

        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
