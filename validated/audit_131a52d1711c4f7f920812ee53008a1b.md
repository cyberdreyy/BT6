### Title
Stale confirmations from removed multisig members count toward execution threshold, allowing requests to execute with fewer than `num_confirmations` live members - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
Both `multisig2` and `multisig` implement a K-of-N confirmation scheme where a `MultiSigRequest` executes once `confirmations.len() + 1 >= num_confirmations`. When a member (or key) is removed via `DeleteMember`/`DeleteKey`, the contract only purges requests *created by* that member/key, but never scrubs that member's *confirmations already cast on other outstanding requests*. Those stale confirmations remain in the `confirmations` set and continue to count toward the threshold even though the confirming party is no longer a member, breaking the equality `confirmations counted == live members who confirmed`.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` checks the request's confirmation set size against `self.num_confirmations` without validating that every entry in that set still belongs to a current member: [1](#0-0) 

`delete_member()` only removes confirmations/requests for requests where `r.member == member` (i.e. requests the removed member *authored*), and separately clears `num_requests_pk` for that member — it never iterates `self.confirmations` to strip that member's vote from requests authored by *other* members: [2](#0-1) 

The v1 `multisig` contract has the analogous gap: `DeleteKey` in `execute_request` removes only requests where `r.signer_pk == pk`, and `remove_request`/`assert_valid_request` never re-validate that stored confirmations still correspond to current key holders: [3](#0-2) [4](#0-3) 

The binding that should hold is: `count(confirmations for request R) == count(distinct current members who confirmed R)`. Once a member is deleted, this equality is violated — the confirmation count still includes the departed member, while the actual number of live, currently-authorized confirmers is one less.

### Impact Explanation
This is a Critical-impact issue under "a multisig request executed below threshold." Concretely, with `num_confirmations = 2` and members `{A, B, C}`:
1. `A` creates request `R` (e.g., `Transfer` to an attacker-controlled account) via `add_request`.
2. `B` calls `confirm(R)` — confirmations = `{B}` (1 of 2, not yet executable).
3. Separately, members execute a `DeleteMember{B}` request (e.g., because `B`'s key was compromised or `B` is being rotated out) — this reaches its own 2-confirmation threshold and executes `delete_member`, removing `B`'s access key/membership. Because `R` was authored by `A` (not `B`), `delete_member` does not touch `R`'s confirmation set, so `{B}` remains stored against `R`.
4. Now only `{A, C}` are live members. `C` calls `confirm(R)`. `confirmations.len() + 1 = 2 >= num_confirmations (2)` → `R` executes, transferring funds, even though only one currently-live member (`C`) actually authorized it in real time (`A` created it, `B`'s stale approval is being reused after `B` lost authority).

This effectively lets a request execute with fewer live authorizing members than the configured threshold requires, moving funds/actions (`Transfer`, `AddKey`, `FunctionCall`, etc.) without the intended K-of-N approval — a direct threshold-bypass on custody of the multisig-controlled account's NEAR balance.

### Likelihood Explanation
No privileged access is required beyond being (or having been) an ordinary multisig member with an outstanding unconfirmed request — a realistic operational scenario is member rotation/compromise-response, where a key is deleted precisely because it's no longer trusted, yet its prior confirmation on any pending, unrelated request silently survives and can later be combined with a fresh confirmation to reach threshold. This requires only normal contract usage (create request, confirm, later remove a member) with no external actor, contract owner, or edge-case deployment assumption — well within the unprivileged-attacker/normal-member analog scope.

### Recommendation
When removing a member (`delete_member`/`DeleteKey`), iterate all outstanding `requests`/`confirmations` (not only those authored by that member) and strip the removed member's entry from every confirmation set, re-checking whether any request now needs recount. Alternatively, validate at `confirm()` time that every account/key in the stored confirmation set is still `self.members.contains(...)` before counting it toward the threshold.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. As `A`: `add_request({receiver_id: multisig, actions:[Transfer{amount}]})` → `request_id = R`.
3. As `B`: `confirm(R)` → stored confirmations for `R` = `{B}`.
4. As `A`+`C` (2 confirmations): create and confirm `DeleteMember{member: B}` → executes `delete_member(B)`; members now `{A, C}`; `R`'s confirmations untouched (`{B}` still present because `R.member == A`, not `B`).
5. As `C`: `confirm(R)` → `confirmations.len() + 1 == 2 >= num_confirmations (2)` → `execute_request(R)` runs the `Transfer`, despite `B` no longer being a member and only one live member (`C`) having confirmed in the current membership state. [5](#0-4) [6](#0-5)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
