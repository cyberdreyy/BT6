### Title
Unfunded instant-withdrawal receipts can consume another user’s funded withdrawal balance - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays the caller’s aggregate `instantWithdrawsRequests` balance without distinguishing receipts already funded by `collectInstantWithdrawFunds` from receipts created afterward. Because `requestWithdraw` can create an additional instant receipt whenever the current APR has fallen by `instantWithdrawAprDelta`, an attacker can add an unfunded receipt after borrower funding has already been collected and then claim the combined amount. If the strategy still holds underlying for another user’s funded-but-unclaimed instant withdrawal, the attacker’s later receipt is paid from that balance, breaking the “one funded receipt, one payout” invariant.

### Finding Description
An instant withdrawal request mints the full `_amount` as a strategy-token receipt and adds it to both `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` [1](#0-0) . Funding is tracked only globally: `collectInstantWithdrawFunds(_amount)` decreases `pendingInstantWithdraws` and transfers that amount from the CDO to the strategy, but it does not associate the funded amount with individual users or epochs [2](#0-1) . Claiming then reads the entire `instantWithdrawsRequests[_user]`, burns that amount, clears it, and transfers the full aggregate to the user [3](#0-2) . There is no per-user funded balance, request timestamp, claimable epoch, or comparison against the amount that was actually collected for that receipt [3](#0-2) .

`IdleCDOEpochVariant.requestWithdraw` routes a normal request into instant mode whenever instant withdrawals are enabled and `lastEpochApr > currentApr + instantWithdrawAprDelta` [4](#0-3) . The claim path itself only checks `allowInstantWithdraw` and then delegates to the strategy, without checking that the specific receipt was funded or that the instant-withdrawal funding deadline elapsed [5](#0-4) .

This creates the relevant ordering failure: a receipt created after the funding collection is treated identically to the receipt that caused the collection. The strategy merely requires sufficient token balance at transfer time; `_transferFundedClaim` only isolates `defaultRecoveryReserve`, and only when that reserve is nonzero [6](#0-5) . It does not reserve balances for other users’ funded instant claims.

### Impact Explanation
An unprivileged KYC-passing tranche holder can steal funded instant-withdrawal proceeds belonging to another user.

A concrete sequence is:

1. Victim requests an instant withdrawal of `V` underlying during an APR-decrease phase.
2. The honest epoch flow funds the strategy with `V` through `collectInstantWithdrawFunds`.
3. Before the victim claims, the attacker creates its own instant request for `A`; the attacker then creates a second instant request for `B` while instant mode remains available.
4. The attacker calls `claimInstantWithdrawRequest`.
5. The strategy calculates `A + B` from `instantWithdrawsRequests[attacker]`, burns both receipts, and transfers `A + B` from the strategy balance.
6. If the strategy contains only `A + V` funded instant-withdrawal liquidity and `B <= V`, the transfer succeeds and consumes `B` of the victim’s funded balance.
7. The victim’s later claim either reverts on insufficient balance or transfers less than its receipt amount; the attacker has obtained `B` underlying without corresponding funding.

The invariant is not merely temporary liquidity ordering: the attacker’s `B` receipt is permanently paid even though `pendingInstantWithdraws` still records it as unfunded, while the victim’s already-funded claim loses the backing that was collected for it.

### Likelihood Explanation
Likelihood depends on deployment timing and configuration rather than privileged misconduct. The attacker must hold or acquire tranche tokens, pass any configured wallet credential, and operate while instant withdrawals are enabled and the APR decrease exceeds `instantWithdrawAprDelta` [4](#0-3) . A victim funded claim must remain unclaimed, or another funded instant-withdrawal balance must remain in the strategy, so the excess claim has assets to consume. No owner, manager, borrower, guardian, queue, or oracle manipulation is required for the accounting flaw itself.

### Recommendation
Track funded and unfunded instant receipts separately instead of paying the aggregate receipt balance.

A robust fix should include:

- Store per-user funded instant-claim balances, for example `fundedInstantWithdrawsRequests[user]`.
- Move receipts from unfunded to funded when `collectInstantWithdrawFunds` is called, or retain an explicit funded cursor/waterline by epoch.
- Make `claimInstantWithdrawRequest` claim only the funded balance, not `instantWithdrawsRequests[_user]`.
- Alternatively, record the funded amount and funded cutoff epoch globally and let each user claim only receipts created before that cutoff.
- Add a regression test where a user creates a second instant request after funding and attempts to claim before the second request is funded; the claim must pay only the first amount and preserve the victim’s funded balance.

### Proof of Concept
The following Foundry test skeleton captures the exploit sequence. Concrete helper names may need to be adapted to the deployment fixture, but the state transitions map directly to the production functions.

```solidity
function testUnfundedInstantReceiptConsumesFundedClaim() public {
    uint256 victimAmount = 100e6;
    uint256 attackerA = 10e6;
    uint256 attackerB = 20e6;

    // Lower APR so requestWithdraw selects the instant-withdrawal path.
    _stopCurrentEpochWithApr(lowerApr);

    // Victim and attacker create instant receipts.
    vm.prank(victim);
    cdo.requestWithdraw(victimTrancheAmount, address(AAtranche));

    vm.prank(attacker);
    cdo.requestWithdraw(attackerTrancheAmountA, address(AAtranche));

    // Honest epoch flow funds the currently pending instant receipts.
    vm.prank(manager);
    cdo.startEpoch();
    _fundInstantWithdrawals(victimAmount + attackerA);

    uint256 fundedBalance =
        underlying.balanceOf(address(strategy));
    assertEq(fundedBalance, victimAmount + attackerA);

    // Attacker adds a receipt after funding has already been collected.
    vm.prank(attacker);
    cdo.requestWithdraw(attackerTrancheAmountB, address(AAtranche));

    // The claim uses the aggregate A+B receipt balance.
    vm.prank(attacker);
    cdo.claimInstantWithdrawRequest();

    assertEq(
        underlying.balanceOf(attacker),
        attackerA + attackerB,
        "attacker received unfunded amount"
    );

    // Only the victim's funded claim minus the stolen B remains.
    assertEq(
        underlying.balanceOf(address(strategy)),
        victimAmount - attackerB,
        "victim funding consumed"
    );

    vm.prank(victim);
    vm.expectRevert(); // insufficient funded balance / ERC20 transfer failure
    cdo.claimInstantWithdrawRequest();
}
```
