### Title
Deleting a multisig key does not purge that key's confirmations on requests it did not originate, allowing a request to execute with a stale confirmation from a revoked signer - (File: `multisig/src/lib.rs`)

### Summary
`MultiSigRequestAction::DeleteKey` only removes requests that were *created* by the deleted key; it does not scrub that key's `confirmations` entries from other pending requests it merely *confirmed*. A confirmation added by a signer before that signer's key is revoked keeps counting toward the `num_confirmations` threshold forever, so a request can later execute having received fewer confirmations from currently-live keys than `num_confirmations` requires.

### Finding Description
`MultiSigContract::confirm` tallies confirmations per `RequestId` in `self.confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` and executes the request once `confirmations.len() + 1 >= self.num_confirmations`: [1](#0-0) 

When a key is removed via `MultiSigRequestAction::DeleteKey`, the cleanup logic only removes requests whose **original signer** (`r.signer_pk`) equals the deleted key, deleting those requests and their confirmation sets wholesale; it also clears `num_requests_pk` for that key: [2](#0-1) 

Crucially, if the deleted key had only *confirmed* other still-pending requests (originated by a different signer), those confirmation entries are never touched. The `HashSet<PublicKey>` for those requests still contains the now-revoked key, and `confirm()` has no notion of "live" vs "revoked" signers - it just compares set size to `num_confirmations`.

The invariant that should hold is:
```
confirmations_counted_toward_threshold(request) ⊆ currently_valid_access_keys(account)
```
Deleting a key breaks this equality for any request the deleted key confirmed-but-did-not-create: the stale confirmation remains counted even though the key is no longer a valid signer on the account.

### Impact Explanation
This falls squarely into the "multisig request executed below threshold" Critical impact category. If `num_confirmations = k`, a request can execute having received confirmations from only `k-1` currently-live keys plus one confirmation from a key that has since been deleted/revoked (e.g., because it was compromised or the signer departed). This effectively lowers the real security threshold of the multisig below its configured value, and since `MultiSigRequestAction::Transfer`/`FunctionCall`/`AddKey` actions move funds or grant access, an attacker who controlled the now-revoked key (or a colluding former signer) can get a malicious pending request executed after their key has ostensibly been cut off.

### Likelihood Explanation
This requires no privileged action beyond the normal, expected multisig workflow: a key is added as signer, confirms a pending request, and is later deleted (e.g., employee offboarding, compromised-key rotation) while that request remains open (`add_request` allows requests to remain unconfirmed/pending indefinitely, subject only to the `active_requests_limit` and `REQUEST_COOLDOWN` for deletion). No special privileges, victim key theft, or social engineering is required to trigger the bug itself - it triggers automatically the next time enough live keys confirm the stale request.

### Recommendation
When executing `DeleteKey`, iterate over **all** entries in `self.confirmations` (not just requests originated by the deleted key) and remove the deleted public key from every confirmation set, e.g.:
```rust
MultiSigRequestAction::DeleteKey { public_key } => {
    ...
    let pk: PublicKey = public_key.into();
    for (request_id, mut confs) in self.confirmations.iter() {
        if confs.remove(&pk) {
            self.confirmations.insert(&request_id, &confs);
        }
    }
    ...
}
```
Alternatively, re-validate at `confirm()` time that every public key in the confirmation set is still a valid access key on the account before counting it toward the threshold.

### Proof of Concept
1. Initialize `MultiSigContract::new(2)` (`num_confirmations = 2`) with keys A, B, C as full-access keys on the account.
2. Key A calls `add_request` with a `Transfer` action to an attacker-controlled account - request `R` is created (`signer_pk = A`), `confirmations[R] = {}`.
3. Key B calls `confirm(R)` → `confirmations[R] = {B}` (1 < 2, not yet executed).
4. Owner detects key B was compromised and submits/confirms a separate multisig request with `MultiSigRequestAction::DeleteKey{ public_key: B }`, executed via `execute_request`:
   - `self.requests` is filtered for entries with `signer_pk == B`; request `R` was created by A, so it is **not** removed.
   - `self.confirmations[R]` still equals `{B}`.
   - Key B is removed from the account's access keys (`promise.delete_key(pk)`).
5. Key C, believing R still needs one more confirmation from a *live* signer, calls `confirm(R)`:
   - `confirmations[R].len() + 1 == 2 >= num_confirmations` → request executes.
   - But the counted confirmations are `{B (revoked), C (live)}` - only one live signer besides the request creator ever approved it, even though `num_confirmations = 2` was intended to require two currently-authorized keys.
6. The transfer to the attacker's account executes despite the multisig no longer trusting key B, demonstrating that `confirmations` counted at execution time diverges from the set of live members, violating the intended `k`-of-`n` custody guarantee.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
