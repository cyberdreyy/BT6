### Title
ETH sent with Ethena-variant withdrawals is forwarded to a per-request clone and permanently locked with no refund path - (contracts/IdleCDOEthenaVariant.sol)

### Summary
The external report describes a `msg.value` overpayment problem: ETH forwarded to an external call (`pyth.updatePriceFeeds`) in excess of the required fee is never refunded. The closest analog in this codebase is `IdleCDOEthenaVariant._withdraw`, which forwards the caller's entire `msg.value` to a newly created `EthenaCooldownRequest` clone via `clones-with-immutable-args` `clone(impl, data, msg.value)`. The clone has no mechanism to return ETH to the user, so any native token sent along with a withdraw is locked in the clone contract.

### Finding Description
In `IdleCDOEthenaVariant._withdraw`, the cooldown-request clone is created with:

```solidity
EthenaCooldownRequest clone = EthenaCooldownRequest(cooldownImpl.clone(
  abi.encodePacked(address(this), msg.sender),
  msg.value
));
``` [1](#0-0) 

The third argument to `clone` is an ETH value forwarded to the clone's address. There is no functional reason for the clone to receive ETH: it only calls `cooldownShares`/`unstake` on sUSDe, which are ERC20 operations. Any `msg.value` sent by the withdrawer — intentionally or by accident — is transferred to the clone's balance.

The clone contract (`EthenaCooldownRequest`) exposes only:

- `startCooldown()` — gated to the CDO, performs `sUSDe.cooldownShares(...)`, no ETH handling.
- `unstake()` — calls `sUSDe.unstake(user)`, sends sUSDe/USDe to the user, not ETH.
- `rescue(token)` — callable only by `TL_MULTISIG`, recovers ERC20 tokens. [2](#0-1) 

There is no `receive`/`fallback` refund, no ETH withdrawal callable by the user, and the CDO itself never tracks or returns the forwarded value. The withdraw path still succeeds, so the user's tranche burn and cooldown proceed normally while the ETH is silently stranded — exactly the "overpayment not refunded" bug class from the report.

Caveat: whether `withdrawAA`/`withdrawBB` on this variant are actually `payable` could not be fully confirmed within the available context. The explicit forwarding of `msg.value` in the clone call strongly implies the entry points are intended to accept ETH, and if any payable path (including `receive`/multicall-style wrappers) reaches `_withdraw` with nonzero `msg.value`, the loss occurs.

### Impact Explanation
Any ETH attached to a withdrawal transaction is permanently locked in the ephemeral clone contract. The loss is 100% of the ETH sent, borne by the withdrawer, with the only recovery route being the privileged `TL_MULTISIG` `rescue()` — which cannot even extract native ETH since `rescue` operates on `IERC20Detailed` token balances (`balanceOf`/`transfer`), so ETH in the clone is effectively unrecoverable even by the multisig.

### Likelihood Explanation
Likelihood depends on a user attaching ETH to a withdraw call. Since the function signature silently accepts and forwards `msg.value`, any interface, wallet, or aggregator that sends ETH alongside the call (e.g., reusing a payable multicall pattern, or a frontend that misattaches value) triggers the loss with no warning. There is no guard such as `require(msg.value == 0)` or a refund of the forwarded amount.

### Recommendation
Do not forward user-supplied ETH to the clone. Either revert on nonzero value or pass `0` explicitly:

```diff
  EthenaCooldownRequest clone = EthenaCooldownRequest(cooldownImpl.clone(
    abi.encodePacked(address(this), msg.sender),
-   msg.value
+   0
  ));
```

and mark the external withdraw entry points non-payable (or add `require(msg.value == 0, "no-eth")`). If ETH support is ever needed, refund the full `msg.value` to `msg.sender` at the end of `_withdraw`.

### Proof of Concept
A reproducible Foundry PoC (mainnet fork) would:

1. Deploy/attach to `IdleCDOEthenaVariant` (sUSDe strategy on mainnet) with a funded tranche holder.
2. Call the withdraw entry point with `msg.value = 1 ether` attached.
3. Capture the `NewCooldownRequestContract` event to get the clone address.
4. Assert `clone.balance == 1 ether`, `withdrawer` received no ETH, and no user-callable function on the clone can return it; `rescue(ETH-placeholder)` fails because `IERC20Detailed.balanceOf` on a non-token address reverts.
5. Confirm tranche burn and sUSDe cooldown proceeded normally, demonstrating the ETH loss is silent and additive.
