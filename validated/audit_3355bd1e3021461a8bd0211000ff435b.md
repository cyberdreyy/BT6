### Title
Phantom interest theft: unvalidated ERC4626 share price in ProgrammableBorrower lets an unprivileged vault depositor inflate `totalInterestDueNow` and overbill the honest borrower - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The Cinny bug combines (1) trusting attacker-controlled input where a validated value was expected (`pack.meta.avatar` used without MXC validation) and (2) a privileged credential being attached based on a weak "contains" check rather than strict origin verification. The credit-vault analog is `ProgrammableBorrower` consuming the external ERC4626 `vault`'s manipulable `convertToAssets` share price — a value any unprivileged vault user can inflate via a direct-underlying donation — as part of `vaultInterestAccrued`/`totalInterestDueNow`, which `IdleCDOEpochVariant._resolveStopEpochInterest` then trusts verbatim as the epoch interest the borrower must repay (`IdleCDOEpochVariant.sol:1001-1005`).

### Finding Description
In programmable-borrower mode, `IdleCDOEpochVariant.stopEpoch` resolves interest via `_resolveStopEpochInterest`, which unconditionally calls `IProgrammableBorrower(_borrower()).totalInterestDueNow()` [1](#0-0) . `ProgrammableBorrower` tracks its vault position through `_depositToVault` / `emergencyExitVault`, which wrap `vault.deposit`/`vault.redeem` and record `epochDepositedToVault`/`epochWithdrawnFromVault` baselines [2](#0-1) . Interest accrued inside the vault is therefore derived from `vault.convertToAssets(vault.balanceOf(this))` minus the tracked baseline — i.e., it trusts the vault's live share price.

An ERC4626 vault's share price is manipulable by any holder of the underlying: a direct `transfer` of underlying into the vault (a donation, minting no shares) raises `convertToAssets` for every existing share. The protocol's own donation guard, `_skimDonatedAssets`, only protects the CDO's raw token balance [3](#0-2) ; it cannot see donations inside the external vault. The result is the same broken invariant as Cinny: an attacker-controllable value is consumed as authoritative, and a sensitive obligation (the borrower's repayment) is attached to it without an origin/sanity check.

Attack trace (running epoch, programmable mode):
1. Epoch running; borrower deployed `D` assets into `vault` via `_depositToVault`.
2. Attacker (an unprivileged user of the programmable borrower's ERC4626 vault, and separately a KYC-passing AA lender) deposits a small amount into `vault` to hold shares, then `underlying.transfer(vault, X)` — a pure donation inflating `convertToAssets`.
3. `vaultInterestAccrued`/`totalInterestDueNow` now reports roughly `X·(borrowerShares/totalShares)` of phantom interest.
4. Manager (honest, routine call) calls `stopEpoch`; `_resolveStopEpochInterest` returns the inflated figure; the borrower is billed interest they never earned and repays it to the CDO.
5. The phantom interest is distributed to tranche holders through normal epoch accounting; the attacker recovers their donation by redeeming their vault shares and collects the overbilled interest pro-rata via `claimWithdrawRequest`/tranche redemption.

### Impact Explanation
Direct theft from the honest borrower: every donated unit that lands in the borrower's share valuation is re-reported as borrower-owed interest and must be repaid out of the borrower's own funds. If the borrower cannot cover the inflated repayment, the pool is pushed toward `_handleBorrowerDefault`, causing BB-first loss socialization for all LPs. A quantified example: attacker donates 100k USDC into the vault while holding ~1% of vault shares and ~95% of AA tranches; `totalInterestDueNow` inflates by ~99k, the borrower overpays ~99k, the attacker recoups ~1k via their shares plus ~94k (post-fee) as LP yield — net theft ≈ 93k USDC per epoch.

### Likelihood Explanation
Requirements are all satisfied by allowed attacker profiles: no privileged role is needed — only (a) the ability to transfer underlying into the external ERC4626 vault (any EOA) and (b) a KYC-passing lender position to harvest the inflated yield. The donation is atomic and repeatable each epoch. No existing guard stops it: `_skimDonatedAssets` only skims tokens sent directly to the CDO, `maxApr` caps configured APR but not vault-reported interest, and `_resolveStopEpochInterest` performs no bounds check against `expectedEpochInterest` in programmable mode [4](#0-3) .

### Recommendation
Validate the external value rather than trusting it — the strict-origin analog of Cinny's fix:
- In `ProgrammableBorrower`, compute `vaultInterestAccrued` against an internal cost basis updated on every `deposit`/`redeem`, and cap the reported interest (e.g., clamp `totalInterestDueNow` to a configured max or to `assets * maxApr * elapsed / YEAR`).
- Track vault PPS checkpointed at `onStartEpoch` and treat any upward PPS jump not attributable to tracked flows as suspicious (pause or clamp), mirroring `_skimDonatedAssets` semantics for indirect donations.
- Optionally wrap vault exposure through a share-balance diff (`shares * ppsAtCheckpoint`) instead of live `convertToAssets`.

### Proof of Concept
Foundry fork PoC outline (concrete addresses depend on the deployed programmable-borrower vault; exact `vaultInterestAccrued` internals should be confirmed against the full contract, as the indexed file was truncated before that function's body):

```solidity
// test/foundry/ProgrammableBorrowerDonation.t.sol
function test_DonatedVaultAssetsInflateInterest() public {
  // state: epoch running, borrower deployed D into `vault`, attacker holds AA tranches
  IERC20Detailed underlying = IERC20Detailed(cdo.token());
  IERC4626 vault = ProgrammableBorrower(strategy.borrower()).vault();

  uint256 interestBefore =
    IProgrammableBorrower(strategy.borrower()).totalInterestDueNow();

  // attacker (any EOA) donates underlying directly to the vault -> pps inflation
  deal(address(underlying), attacker, 100_000e6);
  vm.prank(attacker);
  underlying.transfer(address(vault), 100_000e6);

  uint256 interestAfter =
    IProgrammableBorrower(strategy.borrower()).totalInterestDueNow();
  assertGt(interestAfter, interestBefore); // phantom interest

  // honest manager stops the epoch; borrower is billed the inflated amount
  vm.prank(manager);
  cdo.stopEpoch(0);

  uint256 borrowerBalAfter = underlying.balanceOf(borrower);
  // borrower overpaid ~interestAfter - interestBefore vs real owed interest
  // attacker then redeems vault shares (recovering donation) and claims
  // inflated AA yield via claimWithdrawRequest / tranche redeem.
}
```

Note: the exploitability rests on `vaultInterestAccrued`/`totalInterestDueNow` deriving interest from live `convertToAssets` minus `epochDepositedToVault` baselines rather than from loan terms alone. The indexed code confirms the baseline tracking (`epochDepositedToVault`, `epochWithdrawnFromVault`) and the CDO-side consumption at `IdleCDOEpochVariant.sol:1004`, but the full `totalInterestDueNow` body was not in the indexed excerpt; if that function counts only loan interest (`borrowerPrincipal * apr`) and excludes vault appreciation entirely, this analog does not hold and the correct output would be no vulnerability.
