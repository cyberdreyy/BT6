### Title
A dust withdrawal receipt permanently DoSes loss-adjusted `stopEpochWithDuration` via zero-recovery-price revert - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.collectWithdrawFunds` computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` and hard-reverts `NotAllowed` when the result rounds to 0. An unprivileged lender can create a dust-sized withdraw receipt (1 wei of `pendingWithdraws`) during the buffer phase. Once such a receipt exists, any borrower underpayment that requires a loss-adjusted `stopEpoch`/`stopEpochWithDuration` causes `collectWithdrawFunds` to revert unconditionally — the funded amount `_amount` can never exceed `pendingBasis * RECOVERY_FULL` when `pendingBasis` is 1 wei and a loss occurred. Because `pendingWithdraws` is never cleared on that revert path and there is no other code path that removes a pending receipt during a loss, the epoch can never be stopped, permanently freezing the entire pool's active and pending funds. ### Finding Description
The analog of CVE-2021-20217 (a crafted CGI request triggering an assertion failure → DoS) is a crafted withdraw request triggering a revert in a protocol-critical path. `requestWithdraw` accepts any nonzero `_amount` — there is no minimum — and records `pendingWithdraws += _amount` plus `withdrawsRequestsByEpoch[_user][epochNumber] += _amount`. At `stopEpochWithDuration`, when the borrower repays less than the pending basis (any realized loss), `IdleCDOEpochVariant` calls `collectWithdrawFunds(_amount)` with `_amount < pendingBasis`, which computes the recovery price and reverts if it is zero. With `pendingBasis == 1`, any `_amount < RECOVERY_FULL` (i.e., any realistic funded amount after a loss) yields `lossRecoveryPrice == 0` → `revert NotAllowed()`. The revert propagates up through `stopEpoch`/`stopEpochWithDuration`, so `epochEndDate` is never cleared, `epochNumber` never increments, and neither pending receipts nor active tranche holders can withdraw. The existing guard that reverts on zero price (intended to avoid storing an indistinguishable zero value) is itself the DoS gadget; `previewLossAdjustedWithdrawFunds` only computes a split and does not prevent the dust-receipt precondition.

### Impact Explanation
Broken invariant: epoch state machine liveness / one receipt one payout. A single dust request converts every future loss-adjusted epoch stop into a revert, permanently freezing all underlying held for active LPs plus pending receipts (potentially the entire vault TVL). The attacker's cost is one dust deposit/withdraw request (a few wei of underlying, locked). Acceptable impact class: permanent freezing of user funds with quantified loss equal to pool value at the moment of the blocked stop.

### Likelihood Explanation
The attacker leg is fully unprivileged and cheap: deposit dust → `requestWithdraw(1 wei)` during the buffer phase. The trigger requires a subsequent realized loss (borrower underpayment / `stopEpochWithDuration(_lossAmount > 0)`), which is outside attacker control since borrower/manager are honest — but credit vaults exist precisely because losses are a real scenario, and when one occurs, the freeze is unconditional: no honest sequence of manager/borrower calls can clear a 1-wei `pendingWithdraws` under partial funding, since `collectWithdrawFunds` reverts before mutating state. There is no documented escape hatch (emergency shutdown would abandon the epoch rather than settle it). The dust precondition persists across epochs until fully funded, so a single request poisons all future loss events.

### Recommendation
Enforce a minimum withdraw-request amount in `requestWithdraw`/`requestInstantWithdraw` (e.g., revert if `_amount` below a dust threshold such that `RECOVERY_FULL`-scaled recovery price cannot round to zero), or handle the zero-price case gracefully: store an explicit zero-payout marker (analogous to the queue's `isEpochWithdrawZero` handling) and set `pendingWithdraws = 0` instead of reverting, so the epoch can close and the dust receipt claim resolves to 0. Alternatively, allow the CDO to force-clear residual `pendingWithdraws` below a bound during `collectWithdrawFunds`.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
