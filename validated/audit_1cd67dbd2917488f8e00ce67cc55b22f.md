### Title
Unsigned `reason_code`/`response_data` fields in `BlockRejection` let a single signer re-attribute another signer's genuine rejection into a different (consensus-relevant) category - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection`'s cryptographic signature covers only `signer_signature_hash` and `chain_id`. The `reason`, `reason_code`, and the entire `response_data` struct (`reject_reason`, `failed_txid`, `tenure_extend_timestamp`, etc.) are carried alongside the signature but are never part of the signed digest. Downstream consumers, however, trust these unsigned fields as if they were authenticated attributes of the signer's decision, using them to (a) flip a miner to `InvalidatedBeforeFirstBlock` and (b) permanently/temporarily ban transaction IDs from future blocks. This is structurally the same class of bug as the Aztec `numRealTxs` issue: a field that lives *outside* the cryptographically bound region is nonetheless used to drive a consequential accounting/consensus decision.

### Finding Description
`BlockRejection::hash()` and `sign()`/`verify()`/`recover_public_key()` compute the signed digest from only two fields: [1](#0-0) 

```
pub fn hash(&self) -> Sha256Sum {
    let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
    let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
    structured_data_message_hash(data, domain_tuple)
}
```

The full `BlockRejection` struct, however, carries much more state that is *not* part of that hash: [2](#0-1) 

- `reason: String`
- `reason_code: RejectCode`
- `response_data: BlockResponseData` (`reject_reason`, `failed_txid`, `tenure_extend_timestamp`, `tenure_extend_read_count_timestamp`)

Because the signature is computed purely as a function of `(signer_signature_hash, chain_id)`, any `signature` value a signer ever legitimately produced for a given block hash remains valid for **any** other `(reason, reason_code, response_data)` combination attached to that same `signer_signature_hash`/`chain_id`. Anyone who observes one honest signer's broadcast rejection (rejections are gossiped in plaintext over StackerDB) can copy the raw `signature` bytes and wrap them in a freshly-constructed `BlockRejection` with a different `reason_code`/`response_data`, then rebroadcast that forged object from their own (legitimately owned) StackerDB slot. `recover_public_key()`/`verify()` will still report the message as authentically signed by the original signer, since the hash they check is unaffected by the tampered fields.

Two concrete downstream consumers treat these unsigned fields as trustworthy, consensus-relevant data:

1. **Miner invalidation via reject-reason category.** `store_and_process_block_rejection` tallies rejection weight per `RejectReasonPrefix` and, once the `ReorgNotAllowed` category alone crosses the blocking-minority threshold, marks the current miner as invalid: [3](#0-2) 
This filtering is done over `rejection_addrs` (addresses recovered from stored signatures) combined with the *stored* reject-reason code — which is taken from the message's unsigned `response_data`/`reason_code`, not from anything the signature actually commits to.

2. **Transaction exclusion via `failed_txid`.** On the node/coordinator side, `total_weight_rejected`/`failed_txids` bookkeeping is built directly from `rejected_data.response_data.failed_txid` and `rejected_data.reason_code`: [4](#0-3) 
and that per-txid weight later decides which transactions get temporarily or permanently excluded from block-building: [5](#0-4) 

In both cases the "vote category" attributed to a legitimately-signing signer can be rewritten by anyone who can observe that signer's original rejection and rebroadcast a forged variant through their own slot — no majority and no other signer's private key is required, only the ability to re-emit a message under one's own valid StackerDB identity (in-scope: "a one-slot miner (plus gossip)").

### Impact Explanation
This breaks the equality between "aggregated weight the protocol believes it has for a given rejection category" and "what signers actually verified/signed." A single malicious participant can:
- Re-bucket other signers' genuine-but-unrelated rejections into `ReorgNotAllowed`, artificially crossing the 30%-blocking-minority threshold and causing `store_and_process_block_rejection` to mark the sortition's miner `InvalidatedBeforeFirstBlock` — a liveness wedge that can stall tenure production without ever obtaining a majority of signer weight or keys.
- Re-bucket other signers' rejections onto an arbitrary `failed_txid` with `ProblematicTransaction`/`BadTransaction`, hijacking their weight to permanently or temporarily exclude a transaction from block templates — a miscounted-response class impact (rejections recounted under a category the signer never actually asserted).

Both fall within the stated Critical/High impact classes: a rejection recounted as something it wasn't (mis-attributed rejection reason), and a signature that is valid in one context (a plain "I reject this block" attestation) being reused/accepted in a broader context it never committed to (a specific, consensus-affecting rejection *reason*).

### Likelihood Explanation
The only prerequisites are: (1) being a legitimate signer able to write to one's own StackerDB slot (ordinary capability, not a majority or another signer's key), and (2) observing one publicly gossiped `BlockRejection` from a target signer for the block in question — which is guaranteed to be visible, since rejections are broadcast to the whole signer set as part of normal protocol operation. Constructing the forged message is a pure re-serialization exercise; no cryptography needs to be broken, since the copied `signature` bytes remain valid under the unchanged `hash()` domain.

### Recommendation
Bind `reason_code` and all of `response_data` (at minimum `reject_reason` and `failed_txid`) into the `BlockRejection` signature domain (e.g., include them in the `structured_data_message_hash` input, or hash the full serialized struct minus the signature field), so that a signature is only valid for the exact rejection reason/category the signer actually asserted. Apply the analogous fix to `BlockAccepted`/other response types if their extra fields (`response_data`) are similarly excluded from the signed digest. Downstream weight-tallying code (`store_and_process_block_rejection`, `stackerdb_listener.rs`) should never treat unauthenticated fields as inputs to consensus-affecting decisions.

### Proof of Concept
1. Signer B observes block proposal `P` (hash `H`) and broadcasts a legitimate `BlockRejection{ reason_code: ConnectivityIssues, response_data: { reject_reason: ConnectivityIssues, failed_txid: None, .. }, signer_signature_hash: H, chain_id: C, signature: S }`, where `S = sign(hash(H, C))`.
2. Attacker (any other signer, C_atk) observes this broadcast on StackerDB (public gossip) and extracts `S`.
3. Attacker constructs `BlockRejection'{ reason_code: ValidationFailed(ReorgNotAllowed) /* or ProblematicTransaction with a target failed_txid */, response_data: { reject_reason: ReorgNotAllowed, failed_txid: Some(target_txid), .. }, signer_signature_hash: H, chain_id: C, signature: S }` — same `H`, `C`, `S`, different `reason_code`/`response_data`.
4. `BlockRejection'.verify(B_pubkey)` succeeds because `hash()` only depends on `H` and `C`, both unchanged.
5. Attacker broadcasts `BlockRejection'` via their own StackerDB slot. Every honest signer/node that recovers `signer_address = B` from `BlockRejection'.recover_public_key()` will record B's weight under the forged `ReorgNotAllowed` category (`store_and_process_block_rejection`) or against `target_txid` (`stackerdb_listener.rs`), even though B never rejected the block for that reason.

Note: I was unable to fully trace the exact parameter path from `handle_block_response` into `store_and_process_block_rejection` within the available iterations (function bodies for `handle_block_response`/`handle_block_rejection` in `stacks-signer/src/v0/signer.rs` were not retrieved in full); the analysis above is based on the confirmed signature-domain code, the confirmed struct layout, and the confirmed downstream consumers of `reason_code`/`response_data`, plus the documented flow anchors (`handle_block_response`, `handle_block_rejection`, `store_and_process_block_rejection` in `docs/signer-flows.md`).
