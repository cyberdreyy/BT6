### Title
Unauthenticated attacker can trigger disclosure of raw DB/driver error text via `AuthenticateExternalInitiator` error wrapping - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` wraps any non-`sql.ErrNoRows` error from `store.FindExternalInitiator` with `errors.Wrap(err, "finding external initiator")` and returns it up through `Authenticate`, which passes it unmodified to `jsonAPIError`. `jsonAPIError` calls `err.Error()` and places the full string directly into the JSON response body sent to the caller.

### Finding Description
In `core/web/auth/auth.go`, `AuthenticateExternalInitiator` (lines 119-151) calls `store.FindExternalInitiator(ctx, eia)` with attacker-controlled `AccessKey`/`Secret` header values [1](#0-0) . If the returned error is not `sql.ErrNoRows`, the code does `return errors.Wrap(err, "finding external initiator")` — this preserves and forwards the original underlying error (e.g. a Postgres driver error such as a type/length/encoding error caused by an oversized or malformed `AccessKey`) instead of collapsing it into a generic `auth.ErrorAuthFailed`.

`Authenticate` (lines 157-175) runs this method and, if the returned error is not `auth.ErrorAuthFailed`, immediately calls `jsonAPIError(c, http.StatusUnauthorized, err)` [2](#0-1) . `jsonAPIError`, in `core/web/auth/helpers.go`, calls `err.Error()` and puts the resulting string directly into `models.NewJSONAPIErrorsWith(err.Error())`, which is serialized as the HTTP response body: [3](#0-2) .

Because `errors.Wrap` from `github.com/pkg/errors` concatenates the wrap message with the original error's `.Error()` output, any raw SQL/driver error text (e.g., pq error codes, column/type details, or malformed-query diagnostics) is embedded verbatim in the client-visible message. There is no auth-middleware, role wrapper, or presenter step between this and the HTTP response that redacts or generalizes the message — `jsonAPIError` is the terminal step that writes the response.

### Impact Explanation
This matches the Chainlink bounty impact class of **information disclosure without authentication** — an unauthenticated attacker sending crafted `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers can potentially trigger a DB/driver-level error (not merely "no rows"), and receive verbatim internal error text (e.g., database column types, driver name, malformed query info) in the 401 response body. This is useful for backend fingerprinting/reconnaissance (DB engine, schema hints, ORM/driver behavior) but does not by itself grant authentication bypass, credential disclosure, or fund movement — it is a scoped internal-error-detail leak, not privilege escalation.

### Likelihood Explanation
No credentials or role are required — this is reachable by anyone able to send an HTTP request to an EI-authenticated endpoint (`AuthenticateExternalInitiator` is registered as an auth middleware `authMethod`). Feasibility depends on whether `FindExternalInitiator`'s underlying query actually can produce non-`ErrNoRows` errors from attacker-supplied header values (e.g., a query parameter with an invalid type/format causing a driver error rather than a clean "not found"). This depends on the SQL query implementation in `core/bridges/orm.go`'s `FindExternalInitiator`, which could not be fully inspected in this session due to index truncation — whether the `AccessKey` is used in a way that could trigger a type-mismatch/length DB error (as opposed to a parameterized string comparison that always safely returns `ErrNoRows` on non-match) is unconfirmed. If the query only does a straightforward string equality lookup, most malformed inputs would simply yield `sql.ErrNoRows` (already suppressed) and this path would rarely trigger. This is repeatable if a DB-error-triggering input can be found.

### Recommendation
Do not forward raw errors from `FindExternalInitiator` to the client. Log the wrapped error server-side, but return a generic `auth.ErrorAuthFailed` (or another opaque unauthorized error) to the caller for any error type, mirroring the pattern already used in `AuthenticateByToken` for `sql.ErrNoRows`/`ErrUserSessionExpired`. E.g.:
```go
ei, err := store.FindExternalInitiator(ctx, eia)
if err != nil {
    if !errors.Is(err, sql.ErrNoRows) {
        logger.Errorw("error finding external initiator", "err", err)
    }
    return auth.ErrorAuthFailed
}
```

### Proof of Concept
1. Add a Go handler-level test in `core/web/auth` that constructs a `gin.Context` with `X-Chainlink-EA-AccessKey` set to an oversized/malformed string designed to trigger a non-`ErrNoRows` DB error from a mocked `Authenticator.FindExternalInitiator` (e.g., mock returns a `*pq.Error` or generic DB error).
2. Call `Authenticate(mockStore, AuthenticateExternalInitiator)` middleware against the context.
3. Assert the HTTP response status is 401 and inspect the JSON body — expected (failing) result: body contains `"finding external initiator: <raw db error text>"`.
4. After the fix, assert the JSON body only contains a generic message (e.g., `"invalid API key"` from `auth.ErrorAuthFailed`) and does not contain `err.Error()` substrings from the injected DB error.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()

	}

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
