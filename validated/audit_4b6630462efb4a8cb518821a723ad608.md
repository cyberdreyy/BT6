### Title
Signers can be tricked into equivocating (signing two mutually-conflicting sibling blocks at the same height) by a miner who withholds a fully-endorsed block past its freshness window - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The signer's "conflict" guard, which is supposed to prevent the signer set from ever placing a valid signature over two different blocks at the same height/tenure slot, only blocks a *stale* same-tenure conflict if the node's tenure tip has already reached that height. A single dishonest miner can exploit the ambiguity the code itself documents — "a block is not handed to the node until the whole signer set has signed it, so [the node not knowing about it] may mean 'not yet seen' rather than 'dead'" — by simply never submitting the first fully-signed block to the node. Once `tenure_last_block_proposal_timeout` elapses, honest signers conclude the first block is dead and sign a second, conflicting sibling. Because a collected signer signature is explicitly treated as a "bearer instrument" that stays valid forever (nothing revokes it once it is public), the miner can still surface the first, fully-signed block later, producing two independently signer-endorsed, mutually exclusive blocks for the same slot. This is the direct analog of the Monero multisig report: a single malicious party silently "sits on" one signed artifact, claims it failed, gets the honest quorum to produce a second one, and can later reveal the first.

### Finding Description
The staleness/liveness heuristic is implemented in `conflict_still_blocks` and the pre-commit-threshold signing path in `stacks-signer/src/v0/signer.rs`: [1](#0-0) 

For a conflict in the block's **own tenure** once it has gone stale, the guard asks the node whether the tenure's tip already reaches that height: [2](#0-1) 

If the node reports the tenure's tip below the proposed height — which is exactly what happens when the miner simply never pushes the first signed block — the signer proceeds to sign the replacement: [3](#0-2) 

The freshness window itself is derived purely from local timestamps of when *this* signer (or the observed group) put a signature over the block, not from any proof that the block was ever actually delivered to the network: [4](#0-3) 

Crucially, the design explicitly acknowledges the exact ambiguity being exploited, and documents that it deliberately resolves it in favor of allowing a new signature once stale: [5](#0-4) 

And it explicitly documents that a signature, once produced, is a permanent "bearer instrument" — nothing in the protocol revokes it: [6](#0-5) 

`get_signed_conflicts`/`SignedConflictInfo` confirm that "conflict" bookkeeping is purely local/advisory to decide whether *this* signer will place a *new* signature — it has no bearing on the validity of a signature set already collected for the first block: [7](#0-6) [8](#0-7) 

**Attack path (single miner, no signer collusion needed):**
1. Miner proposes tenure-start block A. Signers pre-commit, then sign (`store_and_process_block_signature`), reaching the 70% signature weight, so A is fully certified — but the miner (who normally relays the assembled signature set / block to the stacks node) simply never submits it, or a signer acting as relay silently drops it.
2. `tenure_last_block_proposal_timeout` elapses. Every signer's local `signed_self`/`signed_group` timestamp for A ages past the freshness cutoff (`get_tenure_last_block_info`, `get_signed_conflicts`).
3. The miner proposes sibling block B at the same height/tenure. Because the node's tenure tip is still below A's height (A was never delivered), `check_block_against_signer_db_state`'s own-tenure branch in `validate_tenure_change_payload`/`check_latest_block_in_tenure` treats A as if it had failed to be confirmed, and the stale-conflict branch of `handle_block_pre_commit` (lines 1432–1457/1458–1466 above) lets the signer set sign B as well.
4. B now also reaches the 70% signature threshold and is pushed to and adopted by the network (`broadcast_signed_block` → `handle_post_block`).
5. The miner (or any party who holds it) now has a fully certified, never-invalidated signature set over A, and the network has a fully certified, adopted B for the very same slot/tenure — two conflicting, signer-endorsed blocks exist simultaneously, exactly the "double-sign" scenario the guard's own comments say it exists to prevent.

This requires only a single dishonest actor controlling block relay/submission timing (a "one-slot miner" per the stated scope), not a majority of signers, and does not need any signer's private key.

### Impact Explanation
This breaks the core safety equality the pre-commit/signature scheme is built to guarantee: at most one signed block per height/tenure slot. The result is a signer signing a conflicting block — a certified, still-valid signature exists over a block (A) that conflicts with another block (B) the same signer set also certified and which became canonical. This matches the Critical impact category "a signer signing an invalid, non-canonical, or conflicting block." Depending on when/whether A's certified form is later surfaced, this can also manifest as a stall/fork risk once A's holder chooses to reveal it against a chain that has already built on B.

### Likelihood Explanation
The trigger condition is fully within the described one-slot miner's control: simply not delivering the first signed block to the stacks node before the fixed `tenure_last_block_proposal_timeout`. No other signer needs to cooperate, no majority is needed, and the mechanism is explicitly acknowledged in the code's own documentation as an accepted trade-off ("not yet seen" vs "dead" cannot be distinguished, and the code chooses to let a new signature go out rather than stall forever).

### Recommendation
Before allowing the stale-conflict own-tenure branch to sign a replacement, require positive proof that the first block is actually dead (e.g., proof the tenure's sortition was orphaned, or an explicit, verifiable retraction/timeout mechanism that also renders the already-collected signature set unusable), rather than inferring "not yet seen" ⇒ "safe to replace" purely from the node's tip lagging behind. Alternatively, bind block signatures to a nonce/expiry that the node enforces at acceptance time so that a stale-but-later-revealed signature set for A can never be adopted once B has been confirmed at the same height, closing off the "bearer instrument never expires" property that lets a withheld block resurface after a sibling has been finalized.

### Proof of Concept
1. Configure a Nakamoto test network with a single miner and N signers, `tenure_last_block_proposal_timeout` set low (as in `run_sibling_scenario` in `stacks-signer/src/v0/tests.rs`).
2. Have the miner propose tenure-start block A; let all signers sign it (weight ≥ 70%), but intercept/suppress the miner's/relay's push of A to the stacks node (simulating `stale_sibling_replaced_when_canonical_tip_below`'s `serve_sibling_as_tip = false` condition, i.e., node's tenure tip stays at the parent height).
3. Wait past `tenure_last_block_proposal_timeout`.
4. Have the miner propose sibling block B at the same height/tenure/parent; observe (as the existing test `stale_sibling_replaced_when_canonical_tip_below` demonstrates) that signers sign B, reaching `LocallyAccepted`/`signed_self`.
5. Confirm B is pushed and adopted by the node.
6. Demonstrate that A's previously-collected signature set (weight ≥ 70%) remains cryptographically valid and unrevoked — nothing in `signerdb`/`SignerMessage` protocol invalidates it — so it could be replayed/submitted at a later point, producing two independently signer-certified blocks for the same slot.

    /// Get the last signed block from the given tenure if it has not timed out.
    /// Even globally accepted blocks are allowed to be timed out, as that
    /// triggers the signer to consult the Stacks node for the latest globally
    /// accepted block. This is needed to handle Bitcoin reorgs correctly.
    ///
    /// The timeout window is measured from the last time a signature actually covered the
    /// block: our own (`signed_self`) or the observed group/global acceptance
    /// (`signed_group`), whichever is later, matching how `get_signed_conflicts` measures
    /// endorsement freshness. `approved_time` is deliberately not used: it is stamped at
    /// pre-commit, which carries no signature, so it would close the window early. This also
    /// means a globally accepted block we never signed ourselves gets a full window from the
    /// time its acceptance was observed, rather than timing out instantly for lack of a
    /// timestamp.
    pub fn get_tenure_last_block_info(
        consensus_hash: &ConsensusHash,
        signer_db: &SignerDb,
        tenure_last_block_proposal_timeout: Duration,
    ) -> Result<Option<BlockInfo>, ClientError> {
        // Get the last signed block in the tenure
        let last_signed_block = signer_db
            .get_last_signed_block(consensus_hash)
            .map_err(|e| ClientError::InvalidResponse(e.to_string()))?;

        let Some(block_info) = last_signed_block else {
            return Ok(None);
        };

        // `approved_time` may hold the pre-commit time; use the actual signature time.
        let Some(signed_over_time) = block_info.signed_self.max(block_info.signed_group) else {
            return Ok(None);
        };

        if signed_over_time.saturating_add(tenure_last_block_proposal_timeout.as_secs())
            > get_epoch_time_secs()
        {
            // The last accepted block is not timed out, return it
            Ok(Some(block_info))
        } else {
            // The last accepted block is timed out
            info!(
                "Last accepted block has timed out";
                "signer_signature_hash" => %block_info.block.header.signer_signature_hash(),
                "signed_over_time" => signed_over_time,
                "state" => %block_info.state,
            );
            Ok(None)
        }
    }

    /// the block with the given signer signature hash, ordered by height (highest first). A
    /// block is considered signed if a signature was ever put over it, ours (`signed_self`)
