Based on my analysis, this question describes a real weakness in the code's design.

### Title
Taker can use `rescueFunds` to steal the maker's un-cancelled source principal after `RESCUE_DELAY` - (File: `contracts/BaseEscrow.sol`, `contracts/EscrowSrc.sol`)

### Summary
`rescueFunds` is guarded only by `onlyCaller(taker)` and `onlyAfter(rescueStart)`, with `rescueStart` computed purely as `deployedAt + RESCUE_DELAY`, independent of whatever withdrawal/cancellation stage the escrow is actually in. It performs an unconditional `_uniTransfer(token, msg.sender, amount)` for whatever `token`/`amount` the caller supplies, with no check that the requested asset is "excess"/accidental rather than the live, unclaimed maker principal. [1](#0-0) [2](#0-1) 

### Finding Description
On `EscrowSrc`, once the private/public withdrawal periods and private cancellation period pass, `publicCancel` becomes callable by any access-token holder — but it has no upper time bound (`onlyAfter` only, no `onlyBefore`), so it theoretically remains available forever: [3](#0-2) 

If the taker withholds the secret and no access-token holder calls `cancel`/`publicCancel` before `RESCUE_DELAY` elapses (measured strictly from deployment time, unrelated to the cancellation stage timers), the taker — and only the taker, since `rescueFunds` is `onlyCaller(taker)` — can call `rescueFunds(immutables.token, immutables.amount, immutables)` and pull out the exact maker principal still sitting in the clone, since nothing distinguishes "accidentally stuck" balance from the live swap principal: [4](#0-3) 

This lets a malicious taker who filled the order, deposited the safety deposit, but withheld the secret and outrun any `publicCancel` caller, seize the maker's original locked tokens instead of letting them flow back to the maker via cancellation — a direct violation of the atomic-swap invariant that undelivered principal always returns to the maker.

### Impact Explanation
This is direct theft of user (maker) funds at rest, matching the bounty's Critical impact category — the maker's escrowed principal, which should be returned via `cancel`/`publicCancel`, is instead captured by the taker.

### Likelihood Explanation
Exploitability depends entirely on the taker's own unprivileged actions (withhold secret, avoid calling cancel, wait for `RESCUE_DELAY`, then call `rescueFunds` before any access-token holder calls `publicCancel`). No admin/governance/relayer trust is required — only that the taker, a normal swap participant, behaves maliciously and wins the race against permissionless `publicCancel` callers. Since `RESCUE_DELAY` is a fixed deployment parameter and the taker knows exactly when it opens, they can submit `rescueFunds` proactively/atomically, making the race winnable in practice.

### Recommendation
`rescueFunds` should not be able to pull the live swap principal once it is still recoverable through the normal cancel/withdraw paths. Options: track per-escrow whether the principal has already been settled (withdrawn/cancelled) and block rescue of `immutables.token`/`immutables.amount` while unsettled; or restrict `rescueFunds` to only the excess balance beyond `immutables.amount + immutables.safetyDeposit`; or require that cancellation has already occurred (or force principal auto-return) before rescue is allowed on the principal token.

### Proof of Concept
1. Taker fills the source order for a maker with a non-zero receiver, funding `EscrowSrc` clone with `immutables.amount` (maker principal) and `immutables.safetyDeposit`.
2. Taker never reveals the secret; withdrawal, public withdrawal, private cancellation, and public cancellation windows all elapse with no `cancel`/`publicCancel` call from any party.
3. Taker waits until `block.timestamp >= immutables.timelocks.rescueStart(RESCUE_DELAY)` (`deployedAt + RESCUE_DELAY`), independent of the cancellation stages.
4. Taker calls `rescueFunds(immutables.token, immutables.amount, immutables)` from the taker address; `onlyCaller(taker)` and `onlyAfter(rescueStart)` both pass, and `_uniTransfer` sends the full maker principal to the taker instead of it returning to the maker via `cancel`. [1](#0-0)
