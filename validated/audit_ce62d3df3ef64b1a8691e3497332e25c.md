## Title
Multisig `confirm()` counts confirmations from deleted keys, allowing execution below the live-member threshold - (File: `multisig/src/lib.rs`)

### Summary
The `MultiSigContract::confirm()` function in `multisig/src/lib.rs` authorizes execution of a pending request purely by comparing the *stored* `confirmations` set size against `num_confirmations`, without re-validating that each already-recorded confirming public key is still a live access key on the account. When a key is removed via `DeleteKey`, the code only purges *requests originated* by that key — it never scrubs that key's stale confirmation entries from *other* still-pending requests. This breaks the intended equality `confirmations_from_live_members == num_confirmations` and lets a request execute using a mix of stale (revoked) and live confirmations that never actually reached K live signers.

### Finding Description
`confirm()` reads the confirmation `HashSet<PublicKey>` for a request and executes once `confirmations.len() + 1 >= num_confirmations`: [1](#0-0) 

The only place confirmations get cleaned up in relation to key removal is inside `execute_request`'s `DeleteKey` branch, and it only removes **requests whose original signer_pk matches the deleted key** — it does not touch the `confirmations` sets of other pending requests that the deleted key may have already confirmed: [2](#0-1) 

Because `PublicKey`s are stored as raw bytes in a `HashSet` with no link back to "is this key still an active access key on the account," a confirmation given by key `B` remains valid forever in the `confirmations` map for any request `B` confirmed but did not originate, even after `B` is deleted via a separate `DeleteKey` request. If a request accumulates confirmations from keys that are later removed, and then a live key adds one more confirmation, `confirm()` will execute the request even though the number of currently-valid (live) confirming keys is below `num_confirmations`.

This directly matches the analog called out in scope: "confirmations counted versus live members."

### Impact Explanation
This allows a `MultiSigRequest` (e.g. a `Transfer` of NEAR funds, an `AddKey`/`DeleteKey`, or a `FunctionCall`) to be executed with fewer live/authorized confirmations than the configured `K` threshold, i.e. "a multisig request executed below threshold" — an explicitly listed Critical impact. Since `MultiSigRequestAction::Transfer` moves NEAR out of the account, this can result in funds being moved by a set of signers that no longer satisfies the account's own K-of-N security policy.

### Likelihood Explanation
This is not a contrived edge case — key rotation (removing a departed/compromised signer) is a normal multisig operation explicitly supported by `DeleteKey`. Any workflow where a request is left pending (not yet at threshold) while a confirming key is later removed will silently leave a stale confirmation counted toward quorum. No malicious redeploy, foundation privilege, or external party is required — this is a latent flaw in the shipped `confirm()`/`DeleteKey` logic itself.

### Recommendation
When a key is removed via `DeleteKey` (or `DeleteMember` in `multisig2`), iterate all outstanding `confirmations` entries and remove the deleted key from every set, not just requests it originated. Alternatively, validate at `confirm()`-time (or at execution time) that every public key in the stored confirmation set still corresponds to a currently-valid access key/member before counting it toward `num_confirmations`.

### Proof of Concept
Conceptual reproduction using the contract's own APIs (analogous to the existing `add_key_delete_key_storage_cleared` test in `multisig/src/lib.rs`):

1. Initialize `MultiSigContract::new(2)` with three valid keys `A`, `B`, `C` already added as access keys on the account (2-of-3).
2. Key `A` calls `add_request` to create `request1` (e.g. `Transfer { amount }`) — 0 confirmations.
3. Key `B` calls `confirm(request1)` — 1 confirmation recorded for `B`, threshold (2) not yet met, `request1` stays pending.
4. Separately, key `A` and key `C` create+confirm a `DeleteKey { public_key: B }` request (2-of-3, valid) — `B`'s key is removed from the account. Per `execute_request`'s `DeleteKey` branch, only requests *originated* by `B` are purged; `request1` (originated by `A`, merely confirmed by `B`) is untouched, and `B`'s stale confirmation remains in `request1`'s `confirmations` set.
5. Key `C` calls `confirm(request1)`. `confirmations.len()` is still 1 (from the now-deleted `B`) + 1 (from `C`) `== 2 >= num_confirmations`, so `execute_request(request1)` fires and the transfer executes — even though only `A` and `C` (2 live keys) exist and only `C` actually confirmed with a currently valid key.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
