### Title
External initiator credentials bypass the "EIs not allowed" guard and can trigger `RunJobV2` on arbitrary integer job IDs - ([File: core/web/pipeline_runs_controller.go])

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered under the `userOrEI` group with `auth.Authenticate(..., auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` and wrapped only by `auth.RequiresRunRole(prc.Create)`, with no additional binding check between the calling initiator and the target job [1](#0-0) .

`AuthenticateExternalInitiator` authenticates purely against an `ExternalInitiator` record via `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers, and then unconditionally sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` in addition to `SessionExternalInitiatorKey` [2](#0-1) . `RequiresRunRole` only checks that `user.Role != UserRoleView`, so this synthetic run-role user passes [3](#0-2) .

Inside `PipelineRunsController.Create`, the code comment claims "only users are allowed to run jobs using int IDs - EIs not allowed", and gates the int-ID path on `_, isUser := auth.GetAuthenticatedUser(c)` [4](#0-3) . `GetAuthenticatedUser` does a type assertion on `SessionUserKey` to `*clsessions.User` and returns `ok=true` for any value of that type [5](#0-4) . Since `AuthenticateExternalInitiator` also stores a `*clsessions.User` under `SessionUserKey`, `isUser` is `true` for EI-authenticated requests too - the intended distinction between "real user" and "external initiator" sessions does not exist at this check. As a result, an EI credential holder reaches `prc.App.RunJobV2(ctx, jobID, nil)` for any integer job ID with no verification that the job is bound to that (or any) external initiator.

This is compounded by the fact that webhook jobs (the only job type previously tied to an `ExternalInitiator`) have been removed - `Create` immediately rejects UUID-style IDs with `job.ErrJobTypeRemoved` [6](#0-5) . This means every job currently addressable via integer ID (OCR, cron, flux monitor, keeper, etc.) can be triggered by an external initiator credential, none of which have any legitimate relationship to that job.

### Impact Explanation
Any holder of a valid `ExternalInitiator` access key/secret (a low-privilege credential meant only to notify webhook jobs, which no longer exist) can force a run of any job on the node by integer ID via `RunJobV2`, regardless of that job's type or intended trigger source. This is an authorization-bypass leading to unauthorized triggering of pipeline runs, potentially causing unwanted on-chain transactions, resource exhaustion, or interference with OCR/cron/keeper jobs - matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Preconditions are minimal: only a valid `ExternalInitiator` row (accesskey/secret) is required, which is a comparatively low-privilege credential type designed only for triggering removed webhook jobs. No knowledge of a specific job's binding is required; the attacker can enumerate integer job IDs directly. The exploit is deterministic and repeatable via a single HTTP POST.

### Recommendation
In `PipelineRunsController.Create`, explicitly distinguish EI-authenticated requests from real user sessions (e.g., check `auth.GetAuthenticatedExternalInitiator(c)` and reject, or use a separate context key/flag set only by `AuthenticateBySession`/`AuthenticateByToken`) before allowing the integer-ID `RunJobV2` path, so the existing code comment's intent ("EIs not allowed") is actually enforced. Since webhook jobs are already removed, consider removing `auth.AuthenticateExternalInitiator` from the `POST /v2/jobs/:ID/runs` route entirely.

### Proof of Concept
1. Handler/integration test in `core/web/pipeline_runs_controller_test.go`:
   - Set up an app with a non-webhook job (e.g. the OCR job used in `setupPipelineRunsControllerTests`).
   - Create an `ExternalInitiator` record via the ORM/test helper (`cltest` equivalent of `bridges.NewExternalInitiator`), unrelated to that job.
   - Issue `POST /v2/jobs/<int-jobID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to the EI's credentials (no session cookie, no API token).
   - Assert current (buggy) behavior: response is `200 OK` with a `pipelineRun` resource, and `App.RunJobV2` was invoked for that job ID — demonstrating that `isUser` was `true` for an EI-authenticated request.
   - Expected/fixed behavior: response should be `401`/`422` and `RunJobV2` should never be called for EI-authenticated requests targeting an int-ID job it isn't bound to.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
