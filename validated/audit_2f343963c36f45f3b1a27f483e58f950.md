### Title
Partial secret bytes buffered at stream close are flushed unmasked by `masker.Close` - ([File: common/buildlogger/internal/masker/masker.go])

### Summary
`masker.Close` (used by `buildlogger.Logger.Close`, invoked from `Build.Run`'s `defer b.logger.Close()`) flushes any bytes that were withheld pending a phrase match, in cleartext, whenever the trace stream ends mid-phrase. Because the withheld bytes are byte-for-byte identical to a prefix of the secret value, a job that ends its output exactly N-1 (or fewer) bytes into a masked secret causes that prefix to be written to the trace unmasked.

### Finding Description
The masker maintains per-phrase state (`matching`) that counts how many contiguous bytes of a phrase have been matched so far, withholding those bytes from `m.next` until either a full match is found (replaced by `[MASKED]`) or the match breaks (withheld bytes are released unmodified) [1](#0-0) .

When the stream ends while a partial match is still pending (`0 < m.matching < len(m.phrase)`), `Write()` never gets a chance to resolve it, so `Close()` is the only place that flushes it:
```go
func (m *masker) Close() error {
	var werr error

	if m.matching == len(m.phrase) {
		_, werr = m.next.Write(mask)
	} else {
		_, werr = m.next.Write(m.phrase[:m.matching])
	}
	...
``` [2](#0-1) 

`m.phrase[:m.matching]` is the exact byte sequence of the secret's prefix (by construction it is what was compared equal against the incoming bytes), so this line writes real secret bytes to the trace, unmasked, instead of masking or discarding them. The in-code comment only anticipates the "full match" branch as an "undiscovered edge case," and does not address the partial-match branch's cleartext-flush behavior at all [3](#0-2) .

This is reachable end-to-end: `Logger.wrap` stacks a `masker.New` writer in the trace pipeline for every job [4](#0-3) , and `Build.Run` defers `b.logger.Close()` which propagates down through `Masker.Close → masker.Close` on every job termination, including immediate process exit after the executor finishes [5](#0-4) .

No existing check mitigates this: `Write()` only withholds partial matches speculatively, and `Close()`'s only defensive branch covers the (supposedly unreachable) full-match case, not the very common case of a stream ending mid-phrase.

### Impact Explanation
A job whose last emitted bytes are a prefix of a value the runner is supposed to mask (CI/CD variable value, masked custom variable, `urlsanitizer`/`tokensanitizer` phrases follow a similar but distinct code path — this finding is specific to the generic phrase `masker`) will have that prefix appear in cleartext in the job trace/log at job termination. Depending on how much of the phrase matched before the stream ended, up to `len(phrase)-1` bytes of the secret can be exposed — in the worst case nearly the entire secret value, leaving only the last byte unknown. Since job traces are typically readable by a broader audience (other project members, CI viewers) than those who should know the secret's value, this breaks the "masked values must never be emitted in cleartext" invariant and leaks sensitive data to unauthorized viewers of the job log.

### Likelihood Explanation
This is straightforward and repeatable for any pipeline author/job script author who can control the tail of the job's stdout/stderr output and the moment the job exits (any GitLab CI job): craft the script so the very last output bytes are a known-length prefix of the secret (e.g., piping a variable through `head -c N-1` as the last command, or simply having a script/tool print an error containing a truncated secret right before crashing). No special privileges beyond normal pipeline authorship are required, and the outcome is deterministic given attacker-controlled precondition (last write = phrase prefix, then process exit).

### Recommendation
In `masker.Close`, when `0 < m.matching < len(m.phrase)`, do not flush the withheld bytes unmodified. Either:
- Replace them with `[MASKED]` (safer default, matching the "full match" branch's behavior), or
- At minimum, only release them if it can be proven they cannot be a genuine partial secret occurrence (not generally provable), so masking on close should be the safe default.
Apply the same review to the sibling `tokenSanitizer.Close` fallback branch (`common/buildlogger/internal/tokensanitizer/token_masker.go:216`), which has an analogous unmasked flush of `m.prefix[:m.matching]`.

### Proof of Concept
```go
// common/buildlogger/internal/masker/masker_test.go
func TestMaskingPartialMatchAtClose(t *testing.T) {
    buf := new(bytes.Buffer)
    secret := "supersecretvalue123"
    m := New(internal.NewNopCloser(buf), internal.Unique([]string{secret}))

    // Write everything except the last byte of the secret, simulating a job
    // whose final stdout write is truncated exactly before completing the phrase.
    partial := secret[:len(secret)-1]
    n, err := m.Write([]byte(partial))
    require.NoError(t, err)
    assert.Equal(t, len(partial), n)

    require.NoError(t, m.Close())

    // Assert the secret prefix is NOT present unmasked in the flushed output.
    assert.NotContains(t, buf.String(), partial)
}
```
Expected (buggy) result: the assertion fails because `buf.String()` contains `partial` verbatim, proving `masker.Close` leaked the unmasked secret prefix.

// Close flushes any remaining data and closes the underlying writer.
func (m *masker) Close() error {
	var werr error

	if m.matching == len(m.phrase) {
		// this mask is added to avoid a potential undiscovered edge-case:
		// this should be unreachable as we replace full matches immediately in
		// Write().
		_, werr = m.next.Write(mask)
	} else {
		_, werr = m.next.Write(m.phrase[:m.matching])
	}

	err := m.next.Close()
	if err == nil {
		return werr
	}

	return err
}
