## Finding

### Title
Unbounded growth of per-sender rate-limiter map leads to memory exhaustion — (File: `core/services/workflows/ratelimiter/ratelimiter.go`)

### Summary
`RateLimiter.Allow` in the workflow rate-limiting package inserts a new `*rate.Limiter` into a `perSender` map keyed by an arbitrary caller-supplied string, and no code path ever deletes entries from that map. This mirrors the CKB advisory's root cause: a map keyed by an attacker-influenced, monotonically-growing identifier that is never pruned, causing unbounded memory growth.

### Finding Description
`RateLimiter` wraps a global limiter and a per-sender limiter map: [1](#0-0) 

`NewRateLimiter` initializes `perSender` as an empty map with no capacity bound or eviction policy: [2](#0-1) 

`Allow` looks up the map by `sender`; if absent, it unconditionally creates and stores a brand-new `*rate.Limiter` for that key, and this entry is never removed by any subsequent code (no TTL, no reaper, no LRU, no max-size check): [3](#0-2) 

This is instantiated for real production use as `WorkflowRateLimiter` in the CRE service setup, using configured (not necessarily capped) sender/global RPS values: [4](#0-3) 

and is threaded into the workflow syncer's `eventHandler` as the `ratelimiter` field, alongside per-owner metadata such as `WorkflowOwner`/organization ID that is derived from event payloads (attacker-influenced, since workflow registration is a permissionless on-chain action): [5](#0-4) [6](#0-5) 

Contrast this with every other cache/map-based construct found elsewhere in the codebase that accepts external keys — all of which implement bounding or reaping:
- `core/services/gateway/handlers/common/requestcache.go` enforces `maxCacheSize` and per-entry timeouts.
- `core/capabilities/vault/request_replay_guard.go` expires and clears stale entries on every call.
- `core/services/gateway/handlers/capabilities/handler.go` has `MaxSavedCallbacks`/`CallbackPruneIntervalSec`.
- `core/sessions/oidcauth/reaper.go` periodically deletes stale sessions.
- `core/services/pipeline/bridgeconn/bridge_conn_manager.go` uses an `observationTTL`.

The `ratelimiter.RateLimiter.perSender` map is the only one of these examined that has no bound and no cleanup mechanism whatsoever — an unmitigated structural analog of the CKB `misbehavior` HashMap bug.

### Impact Explanation
If an unprivileged/permissionless actor can cause `Allow` to be invoked repeatedly with distinct `sender` values (e.g. by registering many distinct workflow owners/senders, or any code path that calls `Allow(sender)` with attacker-influenced strings), the `perSender` map grows without bound for the lifetime of the process. Since each entry holds a `*rate.Limiter` object and is never evicted, sustained or repeated activity from many distinct senders will continuously increase heap usage, eventually degrading performance or crashing the node — the same failure mode described in the CKB advisory (map growth → OOM/panic or OS kill).

### Likelihood Explanation
Exploitability depends on how cheaply an attacker can generate new "sender" values that reach `Allow`. In the workflow syncer, this could be triggered by legitimate on-chain workflow registration events (requires gas but is otherwise permissionless), which is a materially higher barrier than the CKB bug's free P2P-message vector. I was not able to conclusively locate the exact call site invoking `eh.ratelimiter.Allow(sender)` within the available search budget — only the field wiring in `NewEventHandler`/`core/services/cre/cre.go` was confirmed. This weakens certainty about the precise trigger frequency and cost per attacker-controlled entry, and should be verified further (e.g., is `Allow` called once per workflow event, or per message/request from workflow-related senders, and how cheap is minting a new "sender" identity).

### Recommendation
Add bounded storage and/or reaping to `RateLimiter.perSender` in `core/services/workflows/ratelimiter/ratelimiter.go`: introduce either (a) a periodic sweep that removes idle per-sender limiters (similar to `oidcauth/reaper.go` or the gateway `CallbackPruneIntervalSec` pattern), or (b) an LRU/bounded map (as `requestcache.go` does with `maxCacheSize`) that caps the number of tracked senders and evicts the least-recently-used entries once the cap is reached.

### Proof of Concept
Not independently verified end-to-end due to inability to confirm the exact call site invoking `Allow(sender)` with attacker-controlled values in the time available. Conceptually: repeatedly invoke the code path that calls `ratelimiter.RateLimiter.Allow(sender)` (via the `WorkflowRateLimiter`/`eventHandler.ratelimiter` wiring in `core/services/cre/cre.go` and `core/services/workflows/syncer/v2/handler.go`) with a continuously incrementing/never-repeating `sender` string; each call permanently adds one entry to `perSender` with no eviction, causing linear, unbounded memory growth proportional to the number of distinct senders observed over the node's lifetime.

func NewRateLimiter(cfg Config) (*RateLimiter, error) {
	if cfg.GlobalRPS <= 0.0 || cfg.PerSenderRPS <= 0.0 {
		return nil, errors.New("RPS values must be positive")
	}
	if cfg.GlobalBurst <= 0 || cfg.PerSenderBurst <= 0 {
		return nil, errors.New("burst values must be positive")
	}

	return &RateLimiter{
		global:    rate.NewLimiter(rate.Limit(cfg.GlobalRPS), cfg.GlobalBurst),
		perSender: make(map[string]*rate.Limiter),
		config:    cfg,
	}, nil
}

```go
func (rl *RateLimiter) Allow(sender string) (senderAllow bool, globalAllow bool) {
	rl.mu.Lock()
	senderLimiter, ok := rl.perSender[sender]
	if !ok {
		senderLimiter = rate.NewLimiter(rate.Limit(rl.config.PerSenderRPS), rl.config.PerSenderBurst)
		rl.perSender[sender] = senderLimiter
	}
	rl.mu.Unlock()

	senderAllow = senderLimiter.Allow()
	globalAllow = rl.global.Allow()
	return senderAllow, globalAllow
}
```
