## Title
Stale confirmations from removed multisig members are counted toward the approval threshold, allowing requests to execute below the true quorum - (File: `multisig2/src/lib.rs`)

### Summary
The `MultiSigContract::confirm` function in `multisig2/src/lib.rs` counts every entry in a request's `confirmations` set toward `num_confirmations`, but `delete_member` only purges confirmations for requests that the *removed* member originally *created* — not confirmations that member cast on requests created by someone else. Once a member is removed from the multisig, any confirmation they already placed on a still-pending request remains valid and continues to count toward the threshold, even though that account is no longer a member.

### Finding Description
`confirm()` computes whether a request should execute purely from the size of the stored confirmation set: [1](#0-0) 

`delete_member()` is the only place confirmations are cleaned up when membership changes, and it scopes the cleanup to requests where `r.member == member`, i.e. requests *created* by the removed member — it does not scan `confirmations` for entries where the removed member appears as a *confirmer* of someone else's request: [2](#0-1) 

Concretely:
1. Member `A` creates request `R` (e.g. a `Transfer` action moving NEAR out of the multisig account).
2. Member `B` calls `confirm(R)`. Since `confirmations.len()+1 < num_confirmations`, `B`'s vote is stored in the `confirmations` set for `R` and execution is deferred.
3. The multisig, through an unrelated legitimate `DeleteMember` request, later removes `B` (e.g. because `B`'s key is rotated out or considered compromised).
4. `delete_member` purges requests `B` *created*, but `R` was created by `A`, so `R`'s confirmation set still contains `B`.
5. Any subsequent confirmer(s) push `confirmations.len()+1 >= num_confirmations` and `R` executes — counting `B`'s stale confirmation as if `B` were still a live member.

This breaks the equality the contract is supposed to preserve: `confirmations counted == live members who confirmed`. After removal, the left side still includes the departed member, so a request can execute with strictly fewer *currently authorized* signers than `num_confirmations` requires.

### Impact Explanation
This is a threshold-bypass on the core custody mechanism of the multisig: a `Transfer`, `FunctionCall`, `AddKey`, or `DeployContract` request can execute while backed by fewer live, currently-authorized confirmations than `num_confirmations` mandates. Since `Transfer` actions move NEAR directly out of the account and `AddKey`/`DeployContract` can grant control of the account, this maps to "a multisig request executed below threshold," which is explicitly a Critical-severity outcome for this scan.

### Likelihood Explanation
The precondition is a normal, expected multisig operational sequence: member turnover (key rotation, offboarding, revoking a suspected-compromised key) is a documented use case of `DeleteMember`, and it is entirely plausible for a member to have already confirmed a pending request before being removed. No malicious deployment, victim key theft, or foundation privilege is required beyond routine multisig membership churn that this contract is designed to support; the bug is in the bookkeeping gap between `delete_member` and the `confirmations` map, not in any attacker capability.

### Recommendation
When removing a member in `delete_member`, also scan all outstanding `confirmations` entries (not just requests the member created) and strip the removed member's vote from every set it appears in, e.g.:
```rust
for (request_id, mut confirmations) in self.confirmations.iter() {
    if confirmations.remove(&member.to_string()) {
        self.confirmations.insert(&request_id, &confirmations);
    }
}
```
Alternatively, validate membership of every entry in the confirmation set at `confirm()`-time (filtering out non-members before comparing against `num_confirmations`) so stale confirmations can never count toward execution.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request` creating `R = Transfer{ amount, receiver_id: attacker }`.
3. `B` calls `confirm(R)` → `confirmations[R] = {B}` (1 < 3, not yet executed) — see `confirm` at [3](#0-2) .
4. The multisig later executes a `DeleteMember{ member: B }` request (reaching the real threshold with `A, C, D`) — see `delete_member` at [4](#0-3) . `confirmations[R]` is untouched because `R.member == A`, not `B`.
5. `C` calls `confirm(R)` → `confirmations[R] = {B, C}`, size 2, `+1 = 3 >= num_confirmations(3)` → `R` executes, transferring funds to `attacker`, even though only `A`(creator, unconfirmed)/`C` are live confirmers and `B` is no longer a member — one fewer live confirmation than the configured threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
