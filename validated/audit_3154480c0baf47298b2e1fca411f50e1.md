### Title
Multisig `DeleteMember`/`DeleteKey` fails to purge stale confirmations left on requests created by other members, allowing a request to be executed with fewer than `num_confirmations` *live* approvals - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`delete_member` (multisig2) and the `DeleteKey` action (multisig v1) only remove outstanding **requests created by** the removed member/key, and clean up the `num_requests_pk` counter for that member. Neither implementation scans the `confirmations` map to strip that member's stale confirmation entry from *other* requests (created by different members) that the removed member had already confirmed. This is the same class of bug as the Curve oracle report: the code assumes a stored value (a confirmation set) still faithfully reflects live state (current membership) without re-validating it, and that stale assumption is later used to compute a security-critical threshold.

### Finding Description
`confirm()` counts confirmations purely from the `confirmations: LookupMap<RequestId, HashSet<String>>` structure and compares its length against `self.num_confirmations`: [1](#0-0) 

It never re-checks that each entry in the `HashSet` still corresponds to a **current** member — it trusts the historical set blindly, exactly as `CurveTricryptoOracle` trusted `tokens[2]` to still be WETH.

`delete_member` is the only place membership removal happens, and it cleans up only requests where the removed member is the **creator** (`r.member == member`); it does not touch `self.confirmations` for requests created by anyone else: [2](#0-1) 

The same gap exists in multisig v1: `DeleteKey` in `execute_request` removes requests whose `signer_pk == pk`, but never scans other requests' `confirmations` sets for the deleted key: [3](#0-2) 

and `confirm()`/`remove_request()` in v1 likewise trust the raw confirmation count: [4](#0-3) 

**Attack/failure sequence (multisig2, 3 members A, B, C, `num_confirmations = 2`):**
1. Member A creates request `R1` (e.g. `Transfer`) via `add_request`. `confirmations[R1] = {}`.
2. Member B confirms `R1` via `confirm(R1)`. Since `0 + 1 < 2`, B's identifier is stored: `confirmations[R1] = {B}` — no execution yet.
3. Through a separate, properly-confirmed self-request, B is removed as a member (`DeleteMember{B}`), e.g. because B's key was compromised. `delete_member` removes B from `members`, deletes requests *created by* B, but `R1` (created by A) is untouched — `confirmations[R1]` still contains B.
4. Member C now calls `confirm(R1)`. `confirmations.len() (1, stale "B") + 1 (C) = 2 >= num_confirmations (2)` → `execute_request` runs `R1`.

`R1` executes with the equality `num_confirmations == 2` satisfied only because a since-removed member's stale approval is still counted — the actual set of **live** approvers is just `{C}` (1), not 2. This breaks the intended custody binding: *confirmations counted == live members who confirmed*.

### Impact Explanation
This directly matches the "Critical" bucket defined by the rules: **a multisig request executed below threshold**. `R1` can be an arbitrary self-request action (`Transfer`, `AddKey` with a full-access key, `DeployContract`, `AddMember`), so NEAR funds held by the multisig account, or full control of the account, can be moved/granted with effectively one fewer live confirmation than the contract's own security parameter requires. Because removing a compromised or departing member is the normal, expected governance action (not a misuse), this can occur without any attacker action beyond having earlier obtained one confirmation before being legitimately removed — e.g. a malicious or compromised member deliberately confirms several pending requests before being caught and removed, "banking" ghost approvals that later combine with a single honest confirmation to push otherwise-blocked requests through.

### Likelihood Explanation
Requires a normal, foreseeable operational sequence: (1) a member confirms a pending request, (2) that member is later removed via `DeleteMember`/`DeleteKey` (the exact scenario the contract is designed to support, e.g. key rotation, offboarding, compromise response), (3) a remaining request the removed member had confirmed is still outstanding. No abnormal permissions or victim cooperation are needed beyond the multisig's documented member-management flow; the flaw is triggered by legitimate use of `DeleteMember`/`DeleteKey`, making it moderately likely in any multisig with membership churn and multiple concurrently open requests.

### Recommendation
When removing a member/key, iterate `self.confirmations` for **all** outstanding requests (not just ones created by the removed member) and remove the departing member's identifier/public key from every confirmation set. Alternatively, revalidate at `confirm()`-time / execution-time that every entry in a request's confirmation set still belongs to `self.members` before counting it toward `num_confirmations`, discarding stale entries.

### Proof of Concept
```
// multisig2, 3 members: A, B, C ; num_confirmations = 2

// 1. A creates a Transfer request to an attacker-controlled account.
add_request_and_confirm is NOT used; A calls:
add_request({ receiver_id: multisig_account, actions: [Transfer{ amount: X }] })
=> request_id R1, confirmations[R1] = {}

// 2. B confirms (not enough yet, just recorded)
confirm(R1)   // as B
=> confirmations[R1] = {"B"} ; 1 < 2, no execution

// 3. Separately, members legitimately vote to remove B (e.g. suspected compromise)
add_request_and_confirm({ receiver_id: multisig_account,
                           actions: [DeleteMember{ member: B }] })
// executes with 2 real confirmations -> delete_member(B) runs:
//   - members.remove(B)
//   - deletes requests created BY B (none, since A created R1)
//   - confirmations[R1] is NOT touched -> still {"B"}

// 4. C confirms R1
confirm(R1)   // as C
=> confirmations[R1].len() == 1 (stale "B") + 1 (C) == 2 >= num_confirmations (2)
=> execute_request(R1) fires: Transfer of X executes
// Only C is a live, current member who approved; B's approval is stale/ghost.
// The transfer executed with 1 live confirmation, not the required 2.
```

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************

            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
