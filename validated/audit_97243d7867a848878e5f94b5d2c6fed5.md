### Title
Blacklisted redeem receiver blocks entire solver batch in `solveRequestsVault` - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`_solveRedeemVaultAutoPrice` and `_solveRedeemVaultFixedPrice` transfer redeem proceeds directly to `request.receiver` via a bare `token.safeTransfer(request.receiver, ...)` with no fallback, unlike the refund path which uses `_transferWithFallback`. Because `solveRequestsVault` processes an array of `RequestV2` entries in a single loop/transaction, one request whose `receiver` is blacklisted for `token` (e.g., a blacklistable stablecoin like USDC) will revert the entire batch, blocking settlement for every other unrelated request in that call.

### Finding Description
In `_solveRedeemVaultAutoPrice` (and the fixed-price twin), the "not expired" branch calls `IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).exit(...)` followed by `token.safeTransfer(request.receiver, tokenOutAfterTip);` [1](#0-0) , and similarly in the fixed-price path [2](#0-1) . Both use a direct `safeTransfer` to `request.receiver` rather than the fallback-safe helper `_transferWithFallback` that is used elsewhere (e.g. in `_clearHashAndTransferRefund`) [3](#0-2) . `solveRequestsVault` iterates over an array of user-submitted `RequestV2` structs and calls `_solveRequestsVault`, invoking these per-request solve functions inside a loop (confirmed at lines ~900-927) [4](#0-3) . If any single request's `receiver` address is blacklisted by the underlying token contract, the `safeTransfer` call reverts, and since there is no try/catch around it (unlike the refund branch), the entire `solveRequestsVault` transaction reverts — including proceeds for all other, unrelated users batched in the same call.

### Impact Explanation
This causes temporary freezing of redemption proceeds for third parties: any user who submits a redeem request for a blacklistable asset can be griefed if a solver batches their request together with one from an address that becomes blacklisted (or a malicious "receiver" set by an attacker to a self-blacklisted address). Because solving is typically batched for gas efficiency, this can repeatedly stall settlement of legitimate user redemptions, denying access to funds/yield until the transaction is reorganized (excluding the bad entry) — matching a Medium-severity temporary freezing-of-funds impact.

### Likelihood Explanation
Feasibility depends on whether `request.receiver` can be set by the requester to an arbitrary address (self or third-party) at `requestRedeem` time; I was unable to fully confirm this parameter's mutability/authorization from the retrieved code before running out of investigation budget. If receiver is attacker-controlled, the attack is trivial and requires no privileged role — just submitting a redeem request whose receiver is a blacklisted address (or becomes blacklisted) before the batch is solved. This makes it a plausible but not fully confirmed ordinary-user-triggerable griefing vector.

### Recommendation
Wrap the `token.safeTransfer(request.receiver, ...)` calls in `_solveRedeemVaultAutoPrice` and `_solveRedeemVaultFixedPrice` with the existing `_transferWithFallback` helper (transfer to receiver, fallback to `request.user`/escrow on failure) so that a single blacklisted receiver cannot block settlement of the rest of the batch, consistent with how refunds are already handled.

### Proof of Concept
Not fully constructable without confirming (a) that `receiver` in `requestRedeem` is settable independent of `msg.sender`, and (b) the exact `solveRequestsVault` batching entry point signature. Recommend a Devin session with fork access to: deploy `ProvisionerV2` against a mainnet fork with USDC as the redeem token, submit two `requestRedeem` calls (one with a normal receiver, one with a receiver that is later blacklisted via USDC's `blacklister`), call `solveRequestsVault` with both requests, and assert the whole transaction reverts, blocking the legitimate redeemer's payout.

    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
