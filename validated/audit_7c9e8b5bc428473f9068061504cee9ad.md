## Analog Found

### Title
Stale-conflict freshness heuristic lets a signer sign a conflicting sibling block that is still canonical, breaking the one-signature-per-height equivocation guard - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
The pre-commit → signature path uses a purely local, wall-clock timestamp comparison (`last_endorsed > freshness_cutoff`) to decide whether a previously signed conflicting block at the same Stacks height is even worth asking the node about. Once a conflict is judged "stale" by this clock check, the code never queries the node to confirm whether that earlier, conflicting block is still part of the canonical chain — exactly like the OCSP bug, where a purely time-based "was this ever good" fact is trusted forever instead of being re-verified, and once "stale" per the local clock, the underlying live/likely-still-valid state is never re-checked for cross-tenure conflicts.

### Finding Description
`Signer::send_block_pre_commit`'s consensus-threshold branch in `stacks-signer/src/v0/signer.rs` loads every previously signed block at or above the candidate's height, in *any* tenure, via `SignerDb::get_signed_conflicts`: [1](#0-0) 

Each row carries `last_endorsed` — the most recent time *this* signer or the observed group actually signed that conflicting block — with no on-chain liveness information attached.

The signing decision then gates the expensive, node-derived liveness check (`conflict_still_blocks`, which asks `/v3/sortitions` and the tenure tip) behind a purely local freshness comparison: [2](#0-1) 

If `conflict.last_endorsed <= freshness_cutoff` (i.e. the timestamp is merely old), the conflict is excluded from the `find()` predicate via short-circuit evaluation — `conflict_still_blocks` is never called for it, no matter whether the conflicting block is still fully canonical and globally accepted on the node.

The only remaining safety net after that (lines 1432–1457) re-derives liveness from the node, but it is scoped exclusively to conflicts sharing the *same* `consensus_hash` as the block currently being signed (i.e. the signer's own tenure): [3](#0-2) 

A stale conflict that lives in a *different, third* tenure — one that is neither the candidate block's own tenure nor its parent tenure — is therefore never re-checked against the node at all. It is treated as dead purely because the local clock says the endorsement is old, exactly as a stale-but-still-signed OCSP "GOOD" response is treated as valid purely because no freshness window is enforced.

The earlier chainstate re-check (`check_block_against_signer_db_state`) cannot fill this gap either: per the documented design, it only inspects one tenure at a time (a tenure-change block's parent, or a normal block's own tenure), so a signed sibling sitting in an unrelated third tenure is invisible to it: [4](#0-3) 

The freshness window used to gate this is `tenure_last_block_proposal_timeout`, an attacker-influenceable/observable duration (network delay, or a miner simply waiting), and the design explicitly acknowledges that "signatures... not pre-commits... are what pin the view," relying on the *node* to re-derive liveness — except that, as shown above, this only happens for same-tenure conflicts once staleness is reached.

### Impact Explanation
This breaks the "signed once per height" equivocation guard that the whole pre-commit/conflict machinery exists to enforce (see docs/signer-flows.md §5, which states the entire purpose of this code is "to stop us endorsing two blocks that could both end up in the chain"). A signer can be induced to place a second valid signature over a conflicting block B at the same height H as an earlier block A that it (or the observed group) already signed and that is still fully live/canonical on the node, purely because A's endorsement timestamp has aged past `tenure_last_block_proposal_timeout` and B sits in a tenure unrelated to A's. Because every signer applies the same local wall-clock heuristic against the same default configuration, this is not a one-off local anomaly: any signer that experienced the delay independently reaches the same "stale, skip liveness check" state, so the same flaw can be replayed across the signer set, contributing toward — or completing — a genuine double-sign/equivocation at height H. This matches the "Critical" impact bucket (a signer signing a conflicting block).

### Likelihood Explanation
No majority of signers, no other signer's key, and no auth token access are required to trigger the underlying per-signer logic flaw: a single miner (potentially the reachable one-slot miner) can produce block A in tenure T1 at height H, let it get signed/globally accepted, then wait out `tenure_last_block_proposal_timeout` (a config value, default in the tens of seconds, and further extendable by ordinary network delay) before proposing a conflicting block B at height H in an unrelated tenure T3. Every signer that independently observes this timing will skip the liveness re-check for A when evaluating B, because A's tenure (T1) never matches B's own tenure (T3) in the lines 1432–1457 recheck, and A is excluded from the lines 1403–1411 `find()` due to staleness. This requires only ordinary miner behavior (a delayed second proposal) and no majority coordination among signers, only that they use the same default timeout, which they do.

### Recommendation
Do not use local endorsement-age as the sole condition for skipping the node-derived liveness check (`conflict_still_blocks`) on cross-tenure conflicts. Either (a) always run `conflict_still_blocks`/`reorg_permit_stands` for every returned conflict, not just "fresh" ones, before allowing a sign, or (b) extend the own-tenure-only recheck at lines 1432–1457 to cover every conflict returned by `get_signed_conflicts` regardless of tenure, mirroring the same-tenure liveness check with a node round-trip against each conflicting tenure's tip/sortition instead of trusting staleness alone.

### Proof of Concept
1. Miner produces tenure `T1` block `A` at Stacks height `H`; the signer set reaches the 70% pre-commit/signature threshold, `A` becomes `GloballyAccepted` (per `mark_globally_accepted`), `signed_self`/`signed_group` on `A` is stamped with the current time.
2. Miner (or ordinary network delay) waits longer than `tenure_last_block_proposal_timeout` before its next proposal — no code path refreshes `last_endorsed` for `A` during this wait.
3. Miner starts a new tenure `T3` (a fresh sortition, e.g. following a natural Bitcoin block) whose tenure-change parent is some tenure `T2` unrelated to `T1`, and proposes block `B` at the same height `H`.
4. `check_block_against_signer_db_state` only inspects `B`'s own tenure `T3` / parent tenure `T2`; it never sees `A` in `T1`, so it passes.
5. `get_signed_conflicts(H, sighash_B)` returns `A` as a conflict (any-tenure, height ≥ H) with `last_endorsed` now older than `freshness_cutoff`.
6. In `send_block_pre_commit`, the `find()` predicate at lines 1403–1411 short-circuits `A` out because `last_endorsed <= freshness_cutoff`; `conflict_still_blocks` (which would ask the node whether `A`'s tenure/block is still canonical) is never invoked for `A`.
7. The follow-up recheck at lines 1432–1457 only matches conflicts whose `consensus_hash == T3`; `A`'s `consensus_hash == T1` so it is skipped entirely.
8. The signer proceeds to sign `B`, producing a second valid signer signature at height `H` while `A` is still fully canonical/globally accepted — a double-sign at the same height.

```rust
    pub fn get_signed_conflicts(
        &self,
        height: u64,
        excluded_signer_signature_hash: &Sha512Trunc256Sum,
    ) -> Result<Vec<SignedConflictInfo>, DBError> {
        let query = "SELECT b.consensus_hash, b.signer_signature_hash, b.stacks_height, b.state,
                MAX(COALESCE(b.signed_self, 0), COALESCE(b.signed_group, 0)) AS last_endorsed,
                st.superseded_by_consensus_hash, st.superseded_by_burn_block_hash
            FROM blocks b
            LEFT JOIN superseded_tenures st ON st.consensus_hash = b.consensus_hash
            WHERE (b.signed_self IS NOT NULL OR b.signed_group IS NOT NULL)
                AND b.stacks_height >= ?1
                AND b.signer_signature_hash != ?2
            ORDER BY b.stacks_height DESC";
        let args = params![
            u64_to_sql(height)?,
            excluded_signer_signature_hash.to_string(),
        ];
        query_rows(&self.db, query, args)
    }
```

```markdown
Order matters here: the chainstate re-check runs first and produces an explicit
(sticky) rejection when the block now conflicts with a signed one. The conflict
guard behind it is the silent backstop for what that re-check cannot see, and
silence keeps the door open to sign later once the conflict goes stale. Two
blind spots make the guard necessary:

- the re-check only ever looks at _one_ tenure (a tenure-change block's parent,
  or any other block's own), so a signed sibling at the same height in a third
  tenure is invisible to it;
- the `DuplicateBlockFound` check that would catch a second block in the same
  tenure lives in `check_proposal` and runs only at proposal arrival, never
  again. A block that crosses the pre-commit threshold minutes later has no
  other guard, which is what the own-tenure branch above covers.
```
