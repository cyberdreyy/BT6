### Title
Reward-sniping via ping timing: staking a deposit within a skipped-ping window lets a late entrant capture rewards accrued before their stake existed - (File: `staking-pool/src/internal.rs`)

### Summary
`internal_ping` only fires when `env::epoch_height()` differs from the previously recorded `last_epoch_height`, so any number of epochs can be skipped and their combined reward flushed as one lump sum priced at whichever share ratio (`total_staked_balance` / `total_stake_shares`) exists at the moment the flush finally runs. Because `deposit`, `deposit_and_stake`, `stake`, `unstake` and `withdraw` all call `internal_ping()` and, when the epoch hasn't changed yet, proceed to mint/burn shares at the *stale* pre-reward price, an attacker can buy shares cheaply during the skipped window and then trigger (or wait for) the flush to receive a pro-rata slice of reward that accrued entirely before their capital was in the pool.

### Finding Description
The invariant the contract is supposed to maintain is:

`for every epoch e, reward_e is distributed to shareholder i in proportion to shares_i_during_e / total_shares_during_e`

What the code actually implements in `internal_ping` is:

`(sum of reward_e for all skipped epochs) is distributed in proportion to shares_i_at_flush_time / total_shares_at_flush_time` [1](#0-0) 

These two are only equal if the share distribution is unchanged for the whole skipped window. `total_stake_shares` and individual `account.stake_shares` are mutated by `internal_stake`/`inner_unstake`, which are *not* gated on the epoch having changed — they simply run after whatever `internal_ping()` decided (fire or no-op): [2](#0-1) [3](#0-2) 

Exploit flow:
1. Owner/foundation/other delegators stop calling `ping` (nobody is obligated to call it every epoch), so several epochs' rewards `R = R_1 + R_2 + ... + R_n` accumulate unflushed in the pool's real NEAR balance while `last_total_balance` and `total_staked_balance` remain stale.
2. The attacker calls `deposit_and_stake` (or `deposit` then `stake`) at any point *before* the next flush happens, i.e. while `env::epoch_height() == self.last_epoch_height`. `internal_ping()` returns `false` immediately (no-op) at [4](#0-3) , so the attacker's shares are minted via `internal_stake` at the *old*, pre-reward share price computed from the unrefreshed `total_staked_balance`/`total_stake_shares` [5](#0-4) . Their own deposited amount is correctly folded into `last_total_balance` by `internal_deposit` [6](#0-5) , so it is not itself double-counted as reward.
3. Once the epoch height advances (naturally, or the attacker simply waits one block), any call to `ping`/`deposit`/`stake`/`unstake`/`withdraw` — including one made by the attacker themselves — causes `internal_ping` to fire and flush the entire accumulated `R` against the *current* `total_stake_shares`, which now includes the attacker's newly, cheaply bought shares. The attacker collects `R*(1-fee)*S/(T+S)` of reward that was earned entirely before their `S` was staked, diluting the fair share owed to delegators who held stake throughout the skipped epochs.

None of the existing guards stop this: `internal_ping`'s only assertion is `total_balance >= last_total_balance` (a monotonicity sanity check, not a fairness check) [7](#0-6) ; there is no minimum holding period, no per-epoch snapshotting of shares, and `ping` is `pub` and callable by anyone with no `assert_owner`/`assert_self` gate [8](#0-7) .

### Impact Explanation
Existing delegators who kept capital staked through the skipped epochs receive less reward than they earned; the attacker, who only needed capital in the pool for a few blocks (subject to the normal 4-epoch unstake delay to realize it as withdrawable NEAR, but the gain is already baked into their `stake_shares` value immediately), receives reward attributed to them instead of the rightful stakers. This is a misattribution of staking rewards between parties — matching the High severity category ("rewards ... attributed to the wrong party"). The magnitude scales with how large a `S` the attacker can stake relative to pool size `T`, and with how much reward `R` has piled up (worse the longer ping is skipped), and the attack is repeatable every time a skip window opens on any staking pool deployed from this contract.

### Likelihood Explanation
No special privilege is needed — any account that can deposit and stake NEAR into the pool can execute this. The only precondition is a window where nobody has called `ping` since the previous epoch (which can occur naturally on low-traffic pools, or the attacker can simply act as soon as they observe the epoch height is stale relative to the last flush). The attacker's cost is only their own staked capital (which they keep, plus the pulled-in reward) and gas; there is no need to hit an exact block — any point within the un-flushed window works, they just need their stake call to land before the next flush.

### Recommendation
Make `internal_ping` unconditionally flush reward whenever it is invoked and is about to be followed by a share-changing action within the same call, or better: snapshot/checkpoint per-epoch reward against the shares that existed at the start of that epoch instead of shares at flush time. At minimum, disallow `stake`/`deposit_and_stake` from minting shares at a price that predates a pending un-flushed reward window — i.e., force `internal_ping` to always account for `env::epoch_height()` advancing relative to validator reward accrual regardless of whether it equals `last_epoch_height`, or require pool operators/anyone to be incentivized/forced to ping every epoch (e.g., via automatic protocol-level trigger) so the skip window cannot be manufactured.

### Proof of Concept
Using the existing `Emulator` test harness in `staking-pool/src/lib.rs` (see `test_stake_with_fee`) as a base:
1. Initialize pool, have `alice` deposit and stake `X` NEAR, ping once so `last_epoch_height` is current.
2. Advance several epochs (`emulator.skip_epochs(n)`), and increase `emulator.locked_amount` each simulated epoch to represent real validator reward accrual `R_1..R_n`, but do **not** call `ping` in between (simulate a skipped-ping window ending with a large unflushed `R`).
3. Before calling `ping`, have attacker `bob` call `deposit_and_stake(S)` — assert that `bob`'s minted `stake_shares` are computed from the stale `total_staked_balance/total_stake_shares` (i.e., `internal_ping()` returned `false`).
4. Then call `ping()` (from `bob` or anyone) — assert `bob`'s resulting `get_account_staked_balance` grew by more than `S` (i.e., he received a slice of `R` he never contributed capital toward), and assert `alice`'s resulting balance is less than what she would have received had `ping` been called every epoch (compute the per-epoch compounding baseline for comparison).
5. Compare the two runs (per-epoch pings vs. skip-then-flush-after-bob's-stake) to show the divergence in `alice`'s and `bob`'s final `get_account_staked_balance`, demonstrating the binding `reward_e distributed by shares_during_e` is violated.

    pub(crate) fn internal_stake(&mut self, amount: Balance) {
        assert!(amount > 0, "Staking amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);

        // Calculate the number of "stake" shares that the account will receive for staking the
        // given amount.
        let num_shares = self.num_shares_from_staked_amount_rounded_down(amount);
        assert!(
            num_shares > 0,
            "The calculated number of \"stake\" shares received for staking should be positive"
        );
        // The amount of tokens the account will be charged from the unstaked balance.
        // Rounded down to avoid overcharging the account to guarantee that the account can always
        // unstake at least the same amount as staked.
        let charge_amount = self.staked_amount_from_num_shares_rounded_down(num_shares);
        assert!(
            charge_amount > 0,
            "Invariant violation. Calculated staked amount must be positive, because \"stake\" share price should be at least 1"
        );

        assert!(
            account.unstaked >= charge_amount,
            "Not enough unstaked balance to stake"
        );
        account.unstaked -= charge_amount;
        account.stake_shares += num_shares;
        self.internal_save_account(&account_id, &account);

        // The staked amount that will be added to the total to guarantee the "stake" share price
        // never decreases. The difference between `stake_amount` and `charge_amount` is paid
        // from the allocated STAKE_SHARE_PRICE_GUARANTEE_FUND.
        let stake_amount = self.staked_amount_from_num_shares_rounded_up(num_shares);

        self.total_staked_balance += stake_amount;
        self.total_stake_shares += num_shares;

    pub(crate) fn internal_ping(&mut self) -> bool {
        let epoch_height = env::epoch_height();
        if self.last_epoch_height == epoch_height {
            return false;
        }
        self.last_epoch_height = epoch_height;

        // New total amount (both locked and unlocked balances).
        // NOTE: We need to subtract `attached_deposit` in case `ping` called from `deposit` call
        // since the attached deposit gets included in the `account_balance`, and we have not
        // accounted it yet.
        let total_balance =
            env::account_locked_balance() + env::account_balance() - env::attached_deposit();

        assert!(
            total_balance >= self.last_total_balance,
            "The new total balance should not be less than the old total balance"
        );
        let total_reward = total_balance - self.last_total_balance;
        if total_reward > 0 {
            // The validation fee that the contract owner takes.
            let owners_fee = self.reward_fee_fraction.multiply(total_reward);

            // Distributing the remaining reward to the delegators first.
            let remaining_reward = total_reward - owners_fee;
            self.total_staked_balance += remaining_reward;
