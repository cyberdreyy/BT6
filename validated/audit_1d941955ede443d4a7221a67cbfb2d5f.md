### Title
Unbounded per-notification CPU cost in `accountSubscribe`/`programSubscribe` JsonParsed path scales with attacker-controlled account size - ([File: account-decoder/src/lib.rs], [File: account-decoder/src/parse_bpf_loader.rs], [File: rpc/src/rpc_subscriptions.rs])

### Summary
An unprivileged attacker who owns an account parsable under `UiAccountEncoding::JsonParsed` (e.g. a `Buffer`/`ProgramData` account owned by the BPF Upgradeable Loader) can size that account up to the protocol max and mutate it via ordinary transactions, forcing every bank-commitment notification for a single `accountSubscribe`/`programSubscribe` subscription to redo full JSON/base64 encoding of the account's raw data. Unlike the `Base58`/`Binary` path, which explicitly rejects encoding data over `MAX_BASE58_BYTES`, the `JsonParsed` path (and its base64 fallback) has no equivalent size gate, so CPU cost per notification scales linearly with attacker-chosen account size with no throttle beyond the account's raw storage limit.

### Finding Description
`RpcSolPubSubImpl::account_subscribe`/`program_subscribe` accept `UiAccountEncoding::JsonParsed` from any caller without restriction [1](#0-0) . Every time `notify_watchers` runs (once per bank-commitment update), it calls `check_commitment_and_notify` -> `filter_account_result`, which invokes `encode_ui_account(&params.pubkey, &account, params.encoding, None, None)` whenever the account's `last_modified_slot` differs from `last_notified_slot` [2](#0-1) [3](#0-2) .

`encode_ui_account` dispatches to `parse_account_data_v3` for `JsonParsed`, but unlike `encode_bs58` — which explicitly bails with an error string if `slice.len() > MAX_BASE58_BYTES` — there is no size cap applied before parsing/encoding: [4](#0-3) .

For account owners registered in `PARSABLE_PROGRAM_IDS` (which includes `bpf_loader_upgradeable`, `stake`, `vote`, `system_program`/nonce, `spl_token`), `parse_account_data_v3` dispatches to the relevant parser using the full raw account data [5](#0-4) . In particular, `parse_bpf_upgradeable_loader` base64-encodes the *entire remaining buffer/program data* into the JSON result with no length check [6](#0-5) . An attacker fully controls a `Buffer` account they create (owned by `bpf_loader_upgradeable`), including its size (up to the protocol's max account data length) and its raw bytes, and can mutate it via ordinary transactions (e.g. `Write`/close-reopen) at slot cadence. Each such mutation causes the next `notify_watchers` pass for any subscriber watching that account/program with `encoding: jsonParsed` to re-run the full base64 encode of the (potentially multi-megabyte) buffer, synchronously inside the shared pubsub notification worker (`notify_watchers`'s `rayon` parallel iterator over all subscriptions) [7](#0-6) .

The Base58/Binary encoding path already recognizes this exact risk and defends against it via `MAX_BASE58_BYTES` [8](#0-7) , but the `JsonParsed`/Base64-fallback path applies no analogous bound, so a single subscription's per-notification cost is proportional to attacker-chosen account size rather than being capped by an RPC-level guard.

### Impact Explanation
This falls under "unbounded cost for a single low-rate call": one client's single long-lived subscription (`accountSubscribe`/`programSubscribe` with `jsonParsed`) causes the validator's RPC pubsub notification thread(s) to repeatedly perform CPU work (base64 encoding / struct parsing) proportional to the attacker's account size on every relevant bank-commitment update, with no explicit RPC-side size cap analogous to `MAX_BASE58_BYTES`. Because `notify_watchers` iterates over all subscriptions in a shared rayon pool, sustained large-account encoding work for one subscription can degrade notification latency/throughput for other pubsub subscribers on the same node.

### Likelihood Explanation
Fully attacker-controlled and requires no special privileges: the attacker creates a `Buffer` account they own (a normal `bpf_loader_upgradeable` operation), sizes it near the maximum permitted account data length, subscribes to it with `encoding: "jsonParsed"`, and periodically mutates it with ordinary `Write`/close+recreate transactions at normal slot cadence (not exceeding one notification per slot, consistent with how bank-commitment notifications are naturally triggered). No commitment/subscription-quota/length-check guard in the RPC pubsub or account-decoder code currently limits the size of data eligible for JsonParsed/base64 encoding.

### Recommendation
Add an explicit size gate before invoking `parse_account_data_v3` / the base64 fallback in `encode_ui_account`, mirroring `MAX_BASE58_BYTES` for the `Binary`/`Base58` path — e.g., return an error/placeholder for `JsonParsed` when `account.data().len()` exceeds a bounded threshold, and/or cap the amount of raw bytes that `parse_bpf_upgradeable_loader` (and similar parsers with unbounded data copies) will base64-encode per notification.

### Proof of Concept
Rust integration test plan (extends existing `rpc/src/rpc_subscriptions.rs` test harness, e.g. near `test_account_subscribe_with_encoding` at line 986):
1. Create a `Buffer` account (owned by `bpf_loader_upgradeable`) with `authority_address = Some(attacker)` and data length `N`, for `N` in `{1 KiB, 1 MiB, 10 MiB}`.
2. Subscribe via `rpc.account_subscribe(buffer_pubkey, RpcAccountInfoConfig { encoding: Some(UiAccountEncoding::JsonParsed), .. })`.
3. For each `N`, process a transaction that mutates the buffer (e.g., a `Write` instruction changing one byte) and call `subscriptions.notify_subscribers(commitment_slots)`.
4. Wrap the `notify_watchers`/`encode_ui_account` call (or measure wall-clock around `receiver.recv()`) with `solana_measure::measure::Measure` and assert that CPU time scales roughly linearly with `N`, with no early bail/size cap analogous to `MAX_BASE58_BYTES` triggered — i.e., assert `UiAccountData::Json(..)` is returned (not an error/truncated placeholder) even at `N = MAX_PERMITTED_DATA_LENGTH`, confirming the absence of a bound.

pub const MAX_BASE58_BYTES: usize = 128;

fn encode_bs58<T: ReadableAccount>(
    account: &T,
    data_slice_config: Option<UiDataSliceConfig>,
) -> String {
    let slice = slice_data(account.data(), data_slice_config);
    if slice.len() <= MAX_BASE58_BYTES {
        bs58::encode(slice).into_string()
    } else {
        "error: data too large for bs58 encoding".to_string()
    }
}

pub fn encode_ui_account<T: ReadableAccount>(
    pubkey: &Pubkey,
    account: &T,
    encoding: UiAccountEncoding,
    additional_data: Option<AccountAdditionalDataV3>,
    data_slice_config: Option<UiDataSliceConfig>,
) -> UiAccount {
    let space = account.data().len();
    let data = match encoding {
        UiAccountEncoding::Binary => {
            let data = encode_bs58(account, data_slice_config);
            UiAccountData::LegacyBinary(data)
        }
        UiAccountEncoding::Base58 => {
            let data = encode_bs58(account, data_slice_config);
            UiAccountData::Binary(data, encoding)
        }
        UiAccountEncoding::Base64 => UiAccountData::Binary(
            BASE64_STANDARD.encode(slice_data(account.data(), data_slice_config)),
            encoding,
        ),
        UiAccountEncoding::Base64Zstd => {
            let mut encoder = zstd::stream::write::Encoder::new(Vec::new(), 0).unwrap();
            match encoder
                .write_all(slice_data(account.data(), data_slice_config))
                .and_then(|()| encoder.finish())
            {
                Ok(zstd_data) => UiAccountData::Binary(BASE64_STANDARD.encode(zstd_data), encoding),
                Err(_) => UiAccountData::Binary(
                    BASE64_STANDARD.encode(slice_data(account.data(), data_slice_config)),
                    UiAccountEncoding::Base64,
                ),
            }
        }
        UiAccountEncoding::JsonParsed => {
            if let Ok(parsed_data) =
                parse_account_data_v3(pubkey, account.owner(), account.data(), additional_data)
            {
                UiAccountData::Json(parsed_data)
            } else {
                UiAccountData::Binary(
                    BASE64_STANDARD.encode(slice_data(account.data(), data_slice_config)),
                    UiAccountEncoding::Base64,
                )
            }
        }

pub fn parse_account_data_v3(
    pubkey: &Pubkey,
    program_id: &Pubkey,
    data: &[u8],
    additional_data: Option<AccountAdditionalDataV3>,
) -> Result<ParsedAccount, ParseAccountError> {
    let program_name = PARSABLE_PROGRAM_IDS
        .get(program_id)
        .ok_or(ParseAccountError::ProgramNotParsable)?;
    let additional_data = additional_data.unwrap_or_default();
    let parsed_json = match program_name {
        ParsableAccount::AddressLookupTable => {
            serde_json::to_value(parse_address_lookup_table(data)?)?
        }
        ParsableAccount::BpfUpgradeableLoader => {
            serde_json::to_value(parse_bpf_upgradeable_loader(data)?)?
        }
        ParsableAccount::Config => serde_json::to_value(parse_config(data, pubkey)?)?,
        ParsableAccount::Nonce => serde_json::to_value(parse_nonce(data)?)?,
        ParsableAccount::SplToken | ParsableAccount::SplToken2022 => serde_json::to_value(
            parse_token_v3(data, additional_data.spl_token_additional_data.as_ref())?,
        )?,
        ParsableAccount::Stake => serde_json::to_value(parse_stake(data)?)?,
        ParsableAccount::Sysvar => serde_json::to_value(parse_sysvar(data, pubkey)?)?,
        ParsableAccount::Vote => serde_json::to_value(parse_vote(data, pubkey)?)?,
    };
    Ok(ParsedAccount {
        program: format!("{program_name:?}").to_kebab_case(),
        parsed: parsed_json,
        space: data.len() as u64,
    })
}
