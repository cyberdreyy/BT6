### Title
V1 signer chainstate's tenure-duplicate guard checks only globally-accepted blocks, letting a locally-signed tenure-start block be bypassed by a conflicting proposal — ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`validate_tenure_change_payload` in the v1 signer chainstate module rejects a tenure-change proposal as `DuplicateBlockFound` only if `SignerDb::get_last_globally_accepted_block` finds a prior block in that tenure. This mirrors the Capsule bug pattern: the guard checks for a narrow "confirmed ownership" marker (global acceptance) instead of the broader "already committed/signed" state (local *or* global acceptance), so an object (block) that has already been individually signed but not yet globally confirmed slips past the check — exactly like a namespace lacking an `ownerReference` slipping past the webhook that only checks that field.

### Finding Description
`SortitionsView::validate_tenure_change_payload` (v1) does: [1](#0-0) 
i.e. it queries only `get_last_globally_accepted_block(&block.header.consensus_hash)`.

The v2 equivalent was explicitly hardened to use the broader predicate: [2](#0-1) 
using `get_last_signed_block`, which returns a block in `GloballyAccepted` **or** `LocallyAccepted` state: [3](#0-2) 

A regression test in the v2 suite documents that this exact gap was previously a live bug ("Before the fix, this would have incorrectly passed because `get_last_globally_accepted_block` would not find the locally-accepted block."): [4](#0-3) 

The v1 module was **not** updated to match — it still calls the narrower `get_last_globally_accepted_block`, so a signer still running the v1 protocol (the "pre-global signer state activation path", explicitly documented as still reachable code): [5](#0-4) 
will not reject a second, conflicting tenure-start proposal for a tenure in which it has already produced its own signature (`signed_self` set via `mark_locally_accepted`) but that block has not yet been confirmed by the node (`GloballyAccepted`).

Because "the duplicate check never runs again" at validate-ok or at signing time (per the documented design), this v1-only gap means the *only* guard against equivocation for that signer becomes the generic own-tenure conflict logic in the pre-commit/signing path (`handle_block_pre_commit` / `get_signed_conflicts` / `reorg_permit_stands`), which is stale-time-gated: it only permits signing a fresh, still-live sibling to be blocked (`HOLD1`), but once the signature is judged "stale" per `tenure_last_block_proposal_timeout`, or if the node cannot yet answer the tenure-tip query, the guard falls through to signing the replacement. This makes the impact of the v1 gap timing-dependent, but it removes the fast, unconditional, proposal-time rejection that is supposed to hold this equality: "the signer must not sign two conflicting tenure-start blocks for the same tenure."

### Impact Explanation
This breaks the intended invariant that a signer never signs two conflicting (sibling) blocks for the same tenure. If exploited during the staleness window (miner delays/withholds propagation of the first, already-signed block from the stacks-node, or the node is momentarily unreachable to the signer), a v1-protocol signer can be induced to place its signature on a second, conflicting tenure-start block for a tenure it already signed — a same-signer equivocation. If enough v1 signers hit this, it can contribute toward a conflicting/non-canonical block reaching the aggregate signature threshold, which maps to the "Critical" bucket in the rubric (signer signing a conflicting block) if a sufficient window/majority combination occurs, or at minimum a liveness/consistency wedge for that signer once the tenure has to be reconciled.

### Likelihood Explanation
Reachability requires: (1) a signer still on the v1 protocol path (pre-global-state activation — a real, currently-shipped code path, not deprecated test-only code), and (2) a single miner (with normal gossip/propagation control, no majority or other signers' keys needed) delaying/withholding the first signed block from the node long enough for its local signature to be treated as stale, or a transient node-connectivity gap at the tenure-tip query. Both conditions are attacker-controllable by a single miner without needing collusion from other signers, satisfying the "one-slot miner + gossip" threat model. The exact staleness/timeout interaction with `tenure_last_block_proposal_timeout` could not be fully re-verified with the remaining tool budget (the definitions of `get_signed_conflicts`/`reorg_permit_stands`/`get_tenure_last_block_info` in `chainstate/mod.rs` were not retrieved in the final pass), so the precise timing window and whether it fully neutralizes real-world exploitability of the v1 gap is not fully confirmed.

### Recommendation
Update `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` to use `SignerDb::get_last_signed_block` (as v2 already does) instead of `get_last_globally_accepted_block`, so the early tenure-duplicate rejection is consistent across both chainstate versions and does not depend on the downstream stale-timeout fallback as the sole equivocation guard.

### Proof of Concept
1. Run a signer configured to use the v1 chainstate path (before global signer state activation for its reward cycle).
2. Miner proposes tenure-start block A for tenure T (`TenureChangePayload.cause = BlockFound`); it is validated, pre-committed, and reaches the pre-commit weight threshold, causing this signer to call `mark_locally_accepted` (sets `signed_self`, state `LocallyAccepted`). The miner withholds/delays broadcasting A to the stacks-node so it never reaches `GloballyAccepted` from this signer's perspective.
3. Miner proposes a second, conflicting tenure-start block B for the same tenure T (same `consensus_hash`, different transactions/parent).
4. In v1, `validate_tenure_change_payload(B)` calls `signer_db.get_last_globally_accepted_block(&T)`, which returns `None` (A is only `LocallyAccepted`), so the `DuplicateBlockFound` check is skipped and B passes this gate — unlike v2, where `get_last_signed_block` would catch A and reject B immediately.
5. B is forwarded to the node for validation; whether the signer ultimately signs B depends on the (stale-timeout-gated) own-tenure conflict check in the pre-commit/signing path rather than on this proposal-time guard, so the early, intended safety check is bypassed for v1 signers.

    /// Check if block should be rejected based on the local view of the sortition state
    /// Will return a BlockRejection if the block is invalid, none otherwise.
    /// This is the pre-global signer state activation path.
    fn check_block_against_local_state(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block: &NakamotoBlock,
    ) -> Option<BlockRejection> {
        let signer_signature_hash = block.header.signer_signature_hash();
        let block_id = block.block_id();
        // Get sortition view if we don't have it
        if sortition_state.is_none() {
            *sortition_state =
                SortitionsView::fetch_view(self.proposal_config.clone(), stacks_client)
                    .inspect_err(|e| {
                        warn!(
                            "{self}: Failed to update sortition view: {e:?}";
                            "signer_signature_hash" => %signer_signature_hash,
                            "block_id" => %block_id,
                        )
                    })
                    .ok();
        }

        // Check if proposal can be rejected now if not valid against sortition view
        if let Some(sortition_state) = sortition_state {
            match sortition_state.check_proposal(
                stacks_client,
                &mut self.signer_db,
                block,
                true,
                self.global_state_evaluator
                    .get_global_tx_replay_set()
                    .unwrap_or_default(),
            ) {
                // Error validating block
                Err(RejectReason::ConnectivityIssues(e)) => {
                    warn!(
                        "{self}: Error checking block proposal: {e}";
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %block_id,
                    );
                    Some(self.create_block_rejection(RejectReason::ConnectivityIssues(e), block))
                }
                // Block proposal is bad
                Err(reject_code) => {
                    warn!(
                        "{self}: Block proposal invalid";
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %block_id,
                        "reject_reason" => %reject_code,
                        "reject_code" => ?reject_code,
                    );
                    Some(self.create_block_rejection(reject_code, block))
                }
                // Block proposal passed check, still don't know if valid
                Ok(_) => None,
            }
        } else {
            warn!(
                "{self}: Cannot validate block, no sortition view";
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_id,
            );
            Some(self.create_block_rejection(RejectReason::NoSortitionView, block))
        }
    }
