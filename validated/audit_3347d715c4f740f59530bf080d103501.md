### Title
Instruction-parser trusts attacker-controlled `decimals` field on `*Checked` SPL-Token instructions instead of the mint's true decimals, producing misreported `uiAmount`/`uiAmountString` in JSON-RPC output - (File: transaction-status/src/parse_token.rs)

### Summary
The Entangle report describes `buyForLP` computing a synth-mint amount using an assumed (hardcoded) decimal scale instead of the LP token's actual decimals, producing a wrong result that is presented as correct. The equivalent bug class in agave is in the "checked" SPL-Token instruction decoder used by the JSON-RPC transaction/instruction parsers: instead of resolving a token's real decimals from the on-chain mint account, the parser blindly trusts the `decimals` field embedded in the instruction bytes — a field fully controlled by whoever built/submitted the transaction — and uses it to compute the human-readable `uiAmount`.

### Finding Description
`parse_token` in `transaction-status/src/parse_token.rs` handles `TransferChecked`, `ApproveChecked`, `MintToChecked`, and `BurnChecked` by constructing `SplTokenAdditionalDataV2::with_decimals(decimals)` directly from the `decimals` field carried inside the instruction data, then calling `token_amount_to_ui_amount_v3(amount, &additional_data)` to compute `uiAmount`/`uiAmountString`: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

This `decimals` value comes straight from the raw compiled instruction, not from a lookup of the actual mint account. Contrast this with the correct pattern used elsewhere in the codebase, where decimals are fetched from the mint's on-chain state before formatting an amount: `get_mint_owner_and_additional_data`/`get_additional_mint_data` in `rpc/src/parsed_token_accounts.rs` read `mint.base.decimals` from the unpacked `Mint` account, and `rpc/src/rpc.rs::get_token_account_balance`/`get_token_supply` do the same: [5](#0-4) [6](#0-5) 

`parse_token` is registered as the handler for all SPL Token program IDs via `ParsableProgram::SplToken` in `transaction-status/src/parse_instruction.rs`, so it runs for every SPL-Token instruction in every transaction that gets parsed for JSON-RPC consumers (e.g. `getTransaction`/`getConfirmedTransaction` with `jsonParsed` encoding), which is an unprivileged, no-auth JSON-RPC surface: [7](#0-6) 

Because the real SPL-Token/Token-2022 program enforces that the `decimals` argument of `TransferChecked`/`ApproveChecked`/`MintToChecked`/`BurnChecked` matches the mint's actual decimals only at execution time, a transaction can be submitted (and included in a block, either succeeding trivially or failing) with a `decimals` value that does not match the mint. The RPC-side instruction parser has no way to validate this and simply echoes back whatever "ui" amount the wrong decimals produce, exactly mirroring the Entangle bug where an assumed/attacker-influenced decimal count led to a fabricated “correct-looking” numeric output.

### Impact Explanation
This causes wrong-data misreporting to any client relying on the `jsonParsed` encoding of transactions/instructions returned by public JSON-RPC calls: block explorers, wallets, and indexers that surface `tokenAmount.uiAmount`/`uiAmountString` from parsed `TransferChecked`/`ApproveChecked`/`MintToChecked`/`BurnChecked` instructions can display an amount that is off by many orders of magnitude relative to the token's real decimal precision, without any indication of an error. This matches the "decoder panic and misreporting" acceptance criterion — it is a decoder (not consensus) issue, but it produces incorrect financial data from a single unprivileged RPC call over data that is normal, valid transaction content (no malicious snapshot or crafted account state required).

### Likelihood Explanation
Any user can build and submit a transaction containing a `TransferChecked`-family instruction whose `decimals` field disagrees with the mint's actual decimals (the transaction may fail on-chain, but failed transactions are still retrievable and parsed via `getTransaction`). No special privileges, validator role, or multi-request timing is needed — a single call to a public RPC node with `encoding: jsonParsed` on such a transaction reproduces the mismatch deterministically.

### Recommendation
When parsing `TransferChecked`/`ApproveChecked`/`MintToChecked`/`BurnChecked` (and any other "*Checked" token instructions) in `transaction-status/src/parse_token.rs`, do not trust the instruction-embedded `decimals` field as the sole source for UI formatting. Either clearly label the value as "instruction-declared" versus resolving it against the referenced mint account (as `rpc/src/parsed_token_accounts.rs::get_mint_owner_and_additional_data` already does elsewhere) when the mint account state is available to the caller, or emit an explicit warning/flag in the parsed output when the instruction is a failed transaction so downstream consumers do not treat `uiAmount` as ground truth.

### Proof of Concept
1. Create a Token-2022 mint with `decimals = 9`.
2. Submit a transaction containing a `TransferChecked` (or `MintToChecked`) instruction against that mint with the `decimals` argument set to `0` and `amount = 1_000_000_000` (this will fail on-chain due to the decimals check enforced by the token program, but the transaction is still recorded and retrievable).
3. Call `getTransaction` with `{"encoding": "jsonParsed"}` on that signature.
4. Observe that `parse_token`'s output for the `transferChecked`/`mintToChecked` instruction reports `tokenAmount: {"amount": "1000000000", "decimals": 0, "uiAmount": 1000000000, "uiAmountString": "1000000000"}` instead of the value implied by the mint's real 9 decimals (`1.0`), because `token_amount_to_ui_amount_v3` in `transaction-status/src/parse_token.rs` at lines 365-373 uses the attacker-supplied `decimals` field verbatim rather than the mint's on-chain decimals.

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })

    pub fn get_token_account_balance(
        &self,
        pubkey: &Pubkey,
        commitment: Option<CommitmentConfig>,
    ) -> Result<RpcResponse<UiTokenAmount>> {
        let bank = self.bank(commitment);
        let account = bank.get_account(pubkey).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find account".to_string())
        })?;

        if !is_known_spl_token_id(account.owner()) {
            return Err(Error::invalid_params(
                "Invalid param: not a Token account".to_string(),
            ));
        }
        let token_account = StateWithExtensions::<TokenAccount>::unpack(account.data())
            .map_err(|_| Error::invalid_params("Invalid param: not a Token account".to_string()))?;
        let mint = &Pubkey::from_str(&token_account.base.mint.to_string())
            .expect("Token account mint should be convertible to Pubkey");
        let (_, data) = get_mint_owner_and_additional_data(&bank, mint)?;
        let balance = token_amount_to_ui_amount_v3(token_account.base.amount, &data);
        Ok(new_response(&bank, balance))
    }
