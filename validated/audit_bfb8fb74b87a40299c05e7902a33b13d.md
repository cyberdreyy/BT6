### Title
Missing role gate on pprof debug routes allows view-role users to dump process heap/goroutine memory - ([File: core/web/router.go])

### Summary
The `metricRoutes` function mounts `net/http/pprof` handlers (`/v2/debug/pprof/heap`, `/goroutine`, `/symbol`, etc.) inside the `authv2` route group, which only requires session/token authentication via `auth.Authenticate(...)` — no `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` wrapper is applied, unlike every other sensitive route in the same group. Any authenticated user, including the lowest-privilege `UserRoleView` role, can therefore call these endpoints and dump full process heap/goroutine stacks.

### Finding Description
In `core/web/router.go`, `v2Routes` builds `authv2` with `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` [1](#0-0)  and then calls `metricRoutes(authv2)` under the comment "Debug routes accessible via authentication" [2](#0-1) . `metricRoutes` registers the standard `net/http/pprof` handlers directly with no additional role check: [3](#0-2) . Contrast this with every other endpoint in `authv2`, which is explicitly wrapped with `auth.RequiresRunRole`, `auth.RequiresEditRole`, or `auth.RequiresAdminRole`, e.g. `authv2.POST("/replay_from_block/:number", auth.RequiresRunRole(rc.ReplayFromBlock))` [4](#0-3) . The `Authenticate` middleware only verifies identity and sets the user in context; it performs no role check itself [5](#0-4) . Role gating is only enforced by the `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` wrapper functions, none of which are applied to the pprof routes [6](#0-5) . Consequently, a user with `clsessions.UserRoleView` — the lowest role, which `RequiresRunRole` itself explicitly excludes — can hit `GET /v2/debug/pprof/heap?debug=1`, `GET /v2/debug/pprof/goroutine`, or `POST /v2/debug/pprof/symbol` and receive a full 200 response with heap/goroutine dumps.

### Impact Explanation
`pprof` heap and goroutine dumps can contain in-memory secrets: decrypted key material, bridge credentials, DB connection strings/passwords, session tokens, or other sensitive data held in process memory at the time of capture. This matches the Chainlink bounty impact class of in-memory secret disclosure / sensitive information exposure through an authorization bypass (role-exactness violation), reachable by the lowest-privileged authenticated role rather than being restricted to admin/edit users as the rest of the debug/admin surface is.

### Likelihood Explanation
Exploitation only requires a valid view-role session or API token — the lowest privilege tier a node operator can grant (e.g., to a read-only dashboard user or auditor). No special timing, network position, or admin access is needed; the request is a single unauthenticated-to-role GET/POST against a stable, always-mounted route. This is trivially repeatable at will by any view-role credential holder.

### Recommendation
Wrap the `metricRoutes` pprof handlers with at least `auth.RequiresAdminRole` (consistent with other debug/admin functionality such as `/log` PATCH and `/users` management), e.g. `pprofGroup.GET("/heap", auth.RequiresAdminRole(ginHandlerFromHTTP(pprof.Handler("heap").ServeHTTP)))`, applied to all routes registered in `metricRoutes`.

### Proof of Concept
Go handler-level integration test plan:
1. Build a test `gin.Engine` using `web.NewRouter` (or directly call `v2Routes`) with a mocked `chainlink.Application`/`AuthenticationProvider` that authenticates a user with `Role: clsessions.UserRoleView`.
2. Issue `GET /v2/debug/pprof/heap?debug=1` with valid session cookie/API token for that view-role user.
3. Assert HTTP response status is `200 OK` and body contains pprof heap profile data (e.g., contains `"heap profile:"` or valid pprof binary/text markers), confirming no `401`/`403` is returned.
4. Repeat for `GET /v2/debug/pprof/goroutine` and `POST /v2/debug/pprof/symbol`, asserting `200` responses.
5. As a control, assert that a similarly-constructed request to `authv2.POST("/replay_from_block/:number", ...)` (wrapped with `RequiresRunRole`) with the same view-role user returns `401 Unauthorized`, demonstrating the inconsistency and confirming the pprof routes lack the equivalent role gate.

// Authenticate is middleware which authenticates the request by attempting to
// authenticate using all the provided methods.
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {

	}

	}
