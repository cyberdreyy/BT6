### Title
Pending APR0 withdraw requests permanently brick `stopEpoch` if the pool APR is later raised — epoch freeze and fund lockup - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The Exiv2 bug is an out-of-bounds read reachable only through a rarely-used code path (ICC-profile printing via `-p C`) that crashes the process — a conditional, rarely-exercised path that turns a crafted input into a denial of service. The closest credit-vault analog is the APR=0 withdraw-request path in `IdleCreditVault`: a rarely-used accounting mode that, once populated, makes `prepareStopEpochWithApr0` revert unconditionally whenever the pool APR has become non-zero, permanently preventing `stopEpoch` and freezing all LP and pending-withdrawal funds.

### Finding Description
When `unscaledApr == 0`, `requestWithdraw` routes into `_requestWithdrawApr0`, which records the request in `apr0Users[_user]` and adds the amount to the global `apr0TotalPrincipal` bucket [IdleCreditVault.sol:285-294, 567-577]. At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which returns early only when `apr0TotalPrincipal == 0`; otherwise it enforces `unscaledApr == 0` and reverts `NotAllowed` otherwise [IdleCreditVault.sol:499-508]. `apr0TotalPrincipal` is only cleared on the success path at the end of the same function [IdleCreditVault.sol:540] or via default-epoch claim clearing — there is no way to cancel or settle an APR0 request before its epoch ends (`_settleApr0` returns early while `reqEpoch >= epochNumber` [IdleCreditVault.sol:551-555]).

So the sequence is:

1. Manager (honest) runs the pool with `unscaledApr == 0` — a supported configuration exercised in tests (`testApr0WithdrawGetsInterestAtStopEpoch`).
2. An unprivileged KYC'd lender calls `requestWithdraw` on their tranche. `apr0TotalPrincipal` becomes non-zero.
3. The manager (honest, allowed: `setApr`/`setAprsWithBuffer` may be called by the manager at any time [IdleCreditVault.sol:217-235]) sets a normal non-zero APR for the next epoch — a routine operation.
4. Every subsequent `stopEpoch` call reverts at the `unscaledApr != 0` check, because `apr0TotalPrincipal` can never return to zero without a successful `stopEpoch` or a default.

The revert is permanent: no privileged or unprivileged action can clear the bucket, so the epoch can never be stopped. This mirrors the advisory pattern — a rarely-exercised feature path (APR0 mode) that, once entered, crashes the critical operation rather than handling the state.

### Impact Explanation
Permanent freezing of funds. With `stopEpoch` bricked, `epochNumber` never advances, so `_claimFundedWithdrawRequest` keeps reverting on `epochNumber <= lastWithdrawRequest[_user]` [IdleCreditVault.sol:326-328], deposits sit in an epoch that can never end, and neither active LPs nor pending receipt holders can exit. All vault TVL and all pending withdraw receipts are frozen indefinitely. The quantified loss equals the full contract value at the time the APR was raised.

### Likelihood Explanation
Requires the APR0 mode (rarely used) plus an honest APR change while APR0 requests are pending — a plausible operational sequence, since managers legitimately reprice APRs between epochs and a single small APR0 withdraw request (attacker-controlled, dust-sized) is enough to arm the trap. The attacker only needs to be a KYC-passing lender; everything else is honest-role sequencing.

### Recommendation
Instead of reverting when `unscaledApr != 0`, either (a) settle APR0 requests at zero interest and clear `apr0TotalPrincipal`, or (b) treat the APR0 bucket as ordinary pending withdraws once the APR regime changes. Alternatively, disallow APR changes while `apr0TotalPrincipal != 0` in `setAprsWithBuffer`/`setApr`, so the invariant is enforced at the entry point rather than at `stopEpoch`.

### Proof of Concept
A Foundry fork PoC replicating `testApr0WithdrawGetsInterestAtStopEpoch` in `test/foundry/IdleCreditVault.t.sol`:

```solidity
// setup: deploy credit vault CDO, manager sets APR to 0
vm.prank(manager);
IdleCreditVault(address(strategy)).setAprs(0, 0);

idleCDO.depositAA(amount);                    // attacker is a KYC lender
uint256 principal = cdoEpoch.requestWithdraw(trancheAmt, address(AAtranche)); // arms apr0TotalPrincipal

// honest manager reprices APR for next epoch
vm.prank(manager);
IdleCreditVault(address(strategy)).setAprs(5_000, 5_000);

// every stopEpoch now reverts NotAllowed -> permanent freeze
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert();
cdoEpoch.stopEpoch(0, 0);
```

Uncertainty note: I could not fully verify the exact `stopEpoch` call path in `IdleCDOEpochVariant.sol` within the available iterations (the grep returned match counts without excerpts). The finding assumes `stopEpoch` calls `prepareStopEpochWithApr0` unconditionally per the interface shown; if the CDO gates that call behind `unscaledApr == 0` or a try/catch, the issue reduces to stale APR0 accounting rather than a freeze, and the severity drops accordingly.
