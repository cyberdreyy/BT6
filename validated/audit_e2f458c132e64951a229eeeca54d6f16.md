### Title
`getVoteAccounts` performs unbounded O(n) work over every stored vote account on a single unprivileged RPC call - (File: `rpc/src/rpc.rs`)

### Summary
`JsonRpcRequestProcessor::get_vote_accounts` iterates over the *entire* `bank.vote_accounts()` map and performs per-account parsing/formatting work for every vote account that has ever been created on-chain, with no cap on the number of accounts processed. Every sibling RPC method that accepts or touches a user-controllable list (`getMultipleAccounts`, `getSignatureStatuses`, `getInflationReward`, `getSlotLeaders`, `getProgramAccounts` filters) enforces an explicit `MAX_*` bound, but `getVoteAccounts` has none. This mirrors the Union Finance `getFrozenInfo` bug class: an unbounded-size, user-inflatable array is fully traversed and processed in one call/transaction.

### Finding Description
`get_vote_accounts` fetches `bank.vote_accounts()` [1](#0-0)  and then runs a `.filter_map(...).partition(...)` over the *entire* map, doing per-vote-account work (vote state view deserialization, `epoch_credits_iter`, `to_string()` on pubkeys, commission math, etc.) for every entry [2](#0-1) .

Vote accounts are cheap and unprivileged to create: any user can call the vote program to initialize a new `VoteStateV4` account paying only the rent-exempt minimum, with zero delegated stake required. Once created, the account remains in `bank.vote_accounts()` (the `StakesCache`'s `VoteAccountsHashMap`) permanently, as confirmed by the existing test where a zero-stake vote account is created and immediately reflected in `bank.vote_accounts().len()` [3](#0-2) . The stake/activation filtering (`keep_unstaked_delinquents`, `activated_stake > 0`) is applied only *after* the full O(n) `filter_map`/`partition` pass has already executed over every account [4](#0-3) .

By contrast, every other RPC method that could scale with attacker-controlled input enforces an explicit bound:
- `getMultipleAccounts` → `MAX_MULTIPLE_ACCOUNTS` [5](#0-4) 
- `getSignatureStatuses` → `MAX_GET_SIGNATURE_STATUSES_QUERY_ITEMS` [6](#0-5) 
- `getInflationReward` → `MAX_GET_INFLATION_REWARD_ADDRESSES` (verified via test) [7](#0-6) 
- `getSlotLeaders` → `MAX_GET_SLOT_LEADERS` [8](#0-7) 

`getVoteAccounts` has no analogous cap on the number of vote accounts it will process, even though the underlying collection's size is directly grown by unprivileged, low-cost user transactions (creating new vote accounts).

### Impact Explanation
As more vote accounts accumulate on-chain (which any user can create cheaply and which never get removed automatically), every subsequent `getVoteAccounts` call — a single, low-rate, unprivileged JSON-RPC request — does strictly more CPU work, unboundedly, on any RPC-serving validator node. An attacker can inflate `bank.vote_accounts()` with a large number of zero-stake vote accounts (rent-exempt cost only, no stake needed) to make `getVoteAccounts` arbitrarily expensive for that node's RPC thread pool, degrading availability of RPC service without needing repeated calls or multiple clients — the cost is baked into on-chain state and paid once by the attacker, then imposed on every future caller of `getVoteAccounts`.

### Likelihood Explanation
Likelihood is high: creating a vote account requires only a `VoteInit`-style program call and the rent-exempt minimum balance for a `VoteStateV4` account; no stake delegation or validator identity permission is required. This is fully within reach of an unprivileged user and is unbounded (repeatable at will), analogous to how `vouchees` grows via ordinary user calls in the referenced report.

### Recommendation
Add an explicit bound/pagination to `get_vote_accounts`, analogous to the `MAX_*` constants used by other RPC methods — e.g., cap the number of vote accounts scanned/returned per call, or require callers to pass a `vote_pubkey` filter for large clusters, and/or move the stake-based filtering *before* the expensive per-account work (e.g., skip accounts with zero stake before deserializing vote state) so unstaked "junk" vote accounts don't materially increase call cost.

### Proof of Concept
1. Submit many low-cost transactions that create new vote accounts (system_instruction::create_account + vote_instruction::initialize_account) with zero stake delegated, each only paying the rent-exempt minimum for `VoteStateV4`.
2. Observe `bank.vote_accounts().len()` grow unboundedly, as demonstrated in the existing unit test pattern [9](#0-8) .
3. Call `getVoteAccounts` repeatedly; measure that per-call latency/CPU scales linearly with the number of created vote accounts, since `get_vote_accounts` has no limit on the number of entries it processes [2](#0-1) , unlike comparable RPC methods that reject overly large inputs.
