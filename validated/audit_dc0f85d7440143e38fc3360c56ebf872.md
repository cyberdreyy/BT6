### Title
Zip-slip / path traversal in legacy ZIP cache extractor allows writing files outside job working directory - ([File: helpers/archives/zip_extract.go])

### Summary
The `ExtractZipArchive`/`extractZipFile` path used by the legacy zip extractor (`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go` → `helpers/archives/zip_extract.go`) writes each zip entry using `file.Name` directly with no path sanitization, no join against the `dir` passed to `archive.NewExtractor`, and no `../`/absolute-path check. Since `CacheExtractorCommand.downloadParallel` (and the sequential path) write attacker-controlled bytes directly into the file that is later handed to this extractor, a malicious cache backend can place `../` or absolute paths in zip entries and write files anywhere the runner process has permission, entirely outside the job working directory `wd`.

### Finding Description
`CacheExtractorCommand.Execute` computes `wd` and calls `archive.NewExtractor(format, f, size, wd)` then `extractor.Extract(ctx)` [1](#0-0) . Both `downloadParallel` (writing chunks via `meter.NewWriter(file).WriteAt` from `transfer.ParallelRangeDownload`) and the sequential `downloadAndSaveCache` path stage raw, fully attacker-controlled bytes (from the attacker's own cache backend responding to range/GET requests) into `c.File` before it is opened and handed to the extractor [2](#0-1) [3](#0-2) .

For the **tar+zstd** extractor, path confinement IS enforced: `path, err = filepath.Abs(filepath.Join(e.dir, hdr.Name))` followed by `strings.HasPrefix(path, e.dir+string(filepath.Separator))` rejects traversal [4](#0-3) .

However, the **legacy zip** extractor (`ziplegacy.extractor.Extract`) discards the `dir` field entirely and calls `archives.ExtractZipArchive(zr)` with no directory argument at all [5](#0-4) . Inside, `extractZipFile`/`extractZipFileEntry`/`extractZipSymlinkEntry`/`extractZipDirectoryEntry` all operate on `file.Name` verbatim — `os.MkdirAll(filepath.Dir(file.Name), ...)`, `os.OpenFile(file.Name, ...)`, `os.Symlink(string(data), file.Name)` — with **no** `filepath.Clean`, no traversal check, no confinement to any working directory [6](#0-5) [7](#0-6) . A zip entry named `../../../../tmp/evil.sh` or an absolute path, or a symlink entry pointing anywhere, will be written/created wherever the process's actual OS-level relative path resolves to (i.e., outside `wd`), because the only relevant path is `file.Name` interpreted relative to the OS process cwd, not to `wd` as intended.

This directly satisfies the question's exploit chain: the attacker fully controls the archive bytes staged via `downloadParallel`/`fetchChunk` from their own cache backend, and `archive.NewExtractor`/`extractor.Extract` for the zip legacy format does not confine paths to `wd` — unlike the tar+zstd extractor, which does enforce this invariant. The vulnerability is independent of whether the parallel or sequential downloader staged the bytes; the root cause is purely in the zip-legacy extraction logic, which the question's attack path reaches by controlling the cache archive contents end-to-end.

### Impact Explanation
A pipeline author whose job restores an attacker/self-controlled cache (or an attacker who can substitute cache content, e.g. via a compromised/poisoned cache backend under their control as stipulated by the question) can write arbitrary files to arbitrary filesystem locations reachable by the runner process user — including creating executable files outside the job workspace. If any later job step, shell generator predefined script, or cleanup logic globs/executes files from a predictable location outside `wd` (or if the write lands in a location later sourced/executed, e.g. shell rc files, cron directories, or other job working directories on a shared shell-executor host), this becomes remote code execution or cross-job compromise, subject to OS file permissions of the runner process user.

### Likelihood Explanation
Fully feasible and repeatable: the attacker only needs to control the bytes returned for their own project's cache request (already an assumed capability per the "attacker action/data" rule — a normal user configuring a custom cache backend, or a pipeline author, controls cache content). No additional privilege or race condition is required; any job that runs `cache-extractor` against a crafted zip using the legacy (non-fastzip) extractor path is affected. The bug is deterministic — the traversal executes on every extraction of a matching zip entry name, regardless of parallel or sequential download being used.

### Recommendation
Add the same path-confinement check used in `tarzstd_extractor.go` to the legacy zip extraction path: before creating/opening/symlinking any entry, compute `path := filepath.Join(dir, file.Name)`, resolve to absolute form, and reject (or skip with a warning) any entry whose resolved path is not a descendant of `dir` (including checking `filepath.Clean`-ed relative components for `..`, and rejecting absolute paths in `file.Name`). Pass `dir` from `ziplegacy.extractor.Extract` into `archives.ExtractZipArchive`/`extractZipFile` instead of discarding it, and apply the check uniformly to directory, file, and symlink entries (symlink targets should also be validated to prevent writing symlinks that later resolve outside `dir`).

### Proof of Concept
Go test plan (`helpers/archives/zip_extract_test.go` or new test):
1. Build an in-memory `zip.Writer` containing one entry named `../../../../tmp/gr_zipslip_poc` (or `/tmp/gr_zipslip_poc` on POSIX) with executable content.
2. Call `archives.ExtractZipArchive` (or drive the full path via `ziplegacy.NewExtractor(r, size, tmpJobDir).Extract(ctx)`), passing `tmpJobDir` as intended confinement root.
3. Assert that no file exists at the traversal path (`/tmp/gr_zipslip_poc` or whatever it resolves to) — currently the test would FAIL because the file is created there.
4. For full end-to-end reproduction matching the question's proof idea: stand up a fake HTTP server serving the crafted zip with `Accept-Ranges: bytes`/`206 Partial Content` support, set `c.URL` to it, enable `FF_USE_PARALLEL_CACHE_TRANSFER`, run `CacheExtractorCommand.Execute`, and assert (a) no file is created outside `wd`, and (b) `wd`'s contents match only the intended cache entries.

// downloadParallel writes content via concurrent range fetches using WriteAt at chunk offsets (bounded memory); the meter counts bytes via WriteAt. fetchChunk returns a reader for the given byte range; caller closes it.
func (c *CacheExtractorCommand) downloadParallel(contentLength int64, modTime time.Time, etag, cleanedURL string, metadata map[string]string, fetchChunk func(offset, length int64) (io.ReadCloser, error)) error { //nolint:gocognit
	file, err := os.CreateTemp(filepath.Dir(c.File), "cache")
	if err != nil {
		return err
	}
	tmpName := file.Name()
	defer func() {
		_ = os.Remove(tmpName)
	}()

	name := strings.TrimSuffix(filepath.Base(c.File), filepath.Ext(c.File))
	if etag != "" {
		logrus.WithField(logFieldHTTPETag, etag).Infoln("Downloading", name, "from", cleanedURL, "(parallel)")
	} else {
		logrus.Infoln("Downloading", name, "from", cleanedURL, "(parallel)")
	}

	writer := meter.NewWriter(
		file,
		c.TransferMeterFrequency,
		meter.LabelledRateFormat(os.Stdout, "Downloading cache", contentLength),
	)
	// writer.Close() closes the underlying file; we must not call file.Close() and we close writer only once (on each exit path below)

	chunkSize := int64(c.effectiveParallelChunkSize())
	concurrency := max(c.Concurrency, 1)

	destAt, ok := writer.(io.WriterAt)
	if !ok {
		_ = writer.Close()
		return fmt.Errorf("parallel cache download requires destination that implements io.WriterAt")
	}

	err = transfer.ParallelRangeDownload(contentLength, chunkSize, concurrency, destAt, fetchChunk)
	if err != nil {
		_ = writer.Close()
		return retryableErr{err: err}
	}

	if err := writer.Close(); err != nil {
		return err
	}
	// file is closed by writer.Close(); do not call file.Close()
	if err := os.Chtimes(tmpName, time.Now(), modTime); err != nil {
		return err
	}
	if err := os.Rename(tmpName, c.File); err != nil {
		return fmt.Errorf("renaming: %w", err)
	}
	return writeCacheMetadataFile(c.File, metadata)
}

func ParallelRangeDownload(contentLength, chunkSize int64, concurrency int, dest io.WriterAt, fetchChunk FetchChunk) error {
	chunkSize, concurrency, err := normalizeParallelDownloadInputs(contentLength, chunkSize, concurrency)
	if err != nil {
		return err
	}
	chunks := parallelDownloadRanges(contentLength, chunkSize)

	worker := &parallelRangeWorker{dest: dest, fetchChunk: fetchChunk}
	sem := make(chan struct{}, concurrency)
	var wg sync.WaitGroup

	for _, cnk := range chunks {
		wg.Add(1)
		sem <- struct{}{}
		go func(offset, length int64) {
			defer wg.Done()
			defer func() { <-sem }()
			worker.downloadChunk(offset, length)
		}(cnk.offset, cnk.length)
	}
	wg.Wait()
	return worker.firstErr
}

func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}

func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}

func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}
