### Title
Deterministic account actor_id is incorrectly promoted via implicit-transfer path, enabling unauthorized `AddKey` in the same receipt - ([File: runtime/runtime/src/actions.rs])

### Summary
`action_implicit_account_creation_transfer` unconditionally sets `*actor_id = account_id.clone()` before dispatching on `AccountType`, so this promotion also happens for `AccountType::NearDeterministicAccount`, contradicting the explicit design guarantee documented in `create_deterministic_account` that "Actor id remains the predecessor... preventing `AddKey`". An attacker who crafts a receipt with `[Transfer(deposit, det_id), DeterministicStateInitAction(..., det_id), AddKey(det_id)]` targeting a not-yet-existing `0s` deterministic id they derived themselves can make `actor_id == account_id` after the first action, letting the subsequent `AddKey` pass `check_actor_permissions` even though the attacker never owned any key for that account.

### Finding Description
`create_deterministic_account` in `runtime/runtime/src/deterministic_account_id.rs` (lines 96-112) is documented with an explicit invariant: [1](#0-0)  — "this account creation does not change actor_id... preventing `AddKey`... that only the account owner is permitted to do." This guarantee holds for the `DeterministicStateInitAction` path (`action_deterministic_state_init`) because that function only mutates `maybe_account`, never `actor_id`. [2](#0-1) 

However, `action_implicit_account_creation_transfer` (the Transfer path invoked when a `Transfer` action targets a not-yet-existing implicit/deterministic account) does the opposite: it sets `*actor_id = account_id.clone();` at the top of the function, before branching on `AccountType`, so the assignment also applies to the `AccountType::NearDeterministicAccount` branch: [3](#0-2) 

This means for a receipt whose action list is `[Transfer(deposit, det_id), DeterministicStateInitAction(state_init, deposit2), AddKey(...)]` targeting the same non-existent `0s` id:
1. Action 0 (`Transfer`) triggers `action_implicit_account_creation_transfer`, which both creates the account via `create_deterministic_account` and sets `actor_id = det_id` (line 224), even though this branch is semantically identical in account shape to the path that is supposed to preserve the predecessor as actor.
2. Action 1 (`DeterministicStateInitAction`) proceeds against the now-existing account (`maybe_account` is `Some`), deploying the state-init contract/data — `actor_id` is untouched by this step, remaining `det_id` from step 1.
3. Action 2 (`AddKey`) is checked with `actor_id == det_id == account_id`, so the owner-gated permission check that normally blocks arbitrary callers from adding keys to someone else's/system's account is satisfied, because `actor_id` equals `account_id` — the exact same mechanism intentionally used for `CreateAccountAction` (line 203) to allow `[CreateAccount, Transfer, AddKey, DeployContract]` batches, is unintentionally triggered here for deterministic accounts, which by NEP-616 design must never hold access keys.

Since the attacker derives the `0s` id themselves (deterministic ids are computed from a public/derivable seed, not owned by any specific key), and only needs to be the predecessor of a receipt with this 3-action sequence, no signature, nonce, or access-key check stops this: the receipt itself is validly signed by the attacker for actions on an account that does not yet exist, and the runtime's actor_id-based authorization is the only gate for `AddKey` — and that gate is bypassed by the bug.

### Impact Explanation
This breaks the authorization-exactness invariant that a promise/receipt actor should never gain privileges (like adding an access key) for an account it does not own. Successfully adding an access key to a deterministic account violates NEP-616's guarantee that such accounts are controlled solely by their deterministic state-init/contract logic and never via access keys, letting an attacker who merely knows/derives the `0s` id seize unauthorized signing control over any future balance sent to that address — an authorization-escalation / unauthorized-transaction class impact.

### Likelihood Explanation
Preconditions are cheap and fully within an ordinary unprivileged user's ability: derive a `0s` deterministic account id (deterministic, public derivation), submit one receipt/promise batch with the 3 actions listed, and pay ordinary gas/deposit fees. No validator, node-operator, or leaked-key access is required, and the sequence is repeatable against any not-yet-existing deterministic id the attacker chooses to target before its legitimate owner initializes it.

### Recommendation
In `action_implicit_account_creation_transfer` (`runtime/runtime/src/actions.rs`), do not unconditionally set `*actor_id = account_id.clone()` before the `match account_id.get_account_type()`. Move the assignment into only the `AccountType::NearImplicitAccount` and `AccountType::EthImplicitAccount` branches (where the created account's own access key/contract is the intended immediate owner), and explicitly exclude `AccountType::NearDeterministicAccount`, matching the documented invariant already enforced in `create_deterministic_account`.

### Proof of Concept
Add a test-loop integration test (e.g., alongside `test-loop-tests/src/tests/account_cost_increase.rs` or a new deterministic-account test module) that:
1. Derives a fresh `0s` deterministic account id not yet present in state.
2. Submits a single receipt/promise batch from an attacker-controlled account with actions `[Transfer(deposit, det_id), DeterministicStateInitAction(valid_state_init, deposit2), AddKey(det_id, some_public_key, FullAccess)]`.
3. Executes the batch and asserts:
   - The `AddKey` action does **not** fail with an actor-permission error (currently it likely succeeds/`AddKeyAlreadyExists` is not returned, since no key existed).
   - Reading the resulting account's access keys via the trie shows the injected `some_public_key` is present, proving that an access key was added to a deterministic account — a state no legitimate NEP-616 flow should ever produce.
4. Compare against a control case where actions are ordered `[DeterministicStateInitAction(..., deposit), AddKey(...)]` without a preceding `Transfer` — this should fail with an actor-permission error, demonstrating the discrepancy solely caused by the Transfer path's `actor_id` promotion.

pub(crate) fn action_implicit_account_creation_transfer(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    fee_config: &RuntimeFeesConfig,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    account_id: &AccountId,
    deposit: Balance,
    block_height: BlockHeight,
    epoch_info_provider: &dyn EpochInfoProvider,
) {
    *actor_id = account_id.clone();
    match account_id.get_account_type() {
        AccountType::NearImplicitAccount => {
            let mut access_key = AccessKey::full_access();
            access_key.nonce = initial_nonce_value(block_height);

            // unwrap: here it's safe because the `account_id` has already been determined to be implicit by `get_account_type`
            let public_key = PublicKey::from_near_implicit_account(account_id).unwrap();

            *account = Some(Account::new(
                deposit,
                Balance::ZERO,
                AccountContract::None,
                fee_config.storage_usage_config.num_bytes_account
                    + public_key.trie_id_len() as u64
                    + borsh::object_length(&access_key).unwrap() as u64
                    + fee_config.storage_usage_config.num_extra_bytes_record,
            ));

            set_access_key(state_update, account_id.clone(), public_key, &access_key);
        }
        // Invariant: The `account_id` is implicit.
        // It holds because in the only calling site, we've checked the permissions before.
        AccountType::EthImplicitAccount => {
            let chain_id = epoch_info_provider.chain_id();

            // Use a deployed global contract for ETH implicit accounts.
            let global_contract_hash = eth_wallet_global_contract_hash(&chain_id);
            let storage_usage = fee_config.storage_usage_config.num_bytes_account
                + global_contract_hash.as_bytes().len() as u64;

            *account = Some(Account::new(
                deposit,
                Balance::ZERO,
                AccountContract::Global(global_contract_hash),
                storage_usage,
            ));
        }
        AccountType::NearDeterministicAccount => {
            *account = Some(create_deterministic_account(
                deposit,
                &apply_state.config.fees.storage_usage_config,
            ));
        }
