### Title
Claimed instant-withdraw receipts are never removed from `instantWithdrawClaimsByEpoch`/`instantWithdrawsRequestsByEpoch`, inflating the default-recovery reserve and freezing or stealing recovery funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The kernel bug is a refcount leak: `smc_ib_find_route()` acquires a neighbour and an rtable reference but returns without releasing them, so the resource is permanently accounted but never freed. The analog in `IdleCreditVault` is a receipt-accounting leak: `claimInstantWithdrawRequest()` pays the user and clears the aggregate `instantWithdrawsRequests[_user]`, but never clears the per-epoch counters `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` that were incremented in `requestInstantWithdraw()`. On default finalization, those stale counters are treated as already-held ("prefunded") reserve, crediting `defaultRecoveryReserve` with underlying that has already been paid out.

### Finding Description
`requestInstantWithdraw()` records three things per request: `instantWithdrawsRequests[_user] += _amount`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` [1](#0-0) .

The normal claim path only clears the aggregate:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:387-392
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are only decremented in the defaulted-claim path `_claimDefaultedInstantWithdrawRequest` [2](#0-1) , which runs exclusively after `defaultRecoveryFinalized`.

The stale counters become load-bearing at default finalization. `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0` [3](#0-2) , and `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstantWithdraws` as underlying already held by the strategy [4](#0-3) . `finalizeDefaultRecovery()` then sets `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` — i.e. it counts the already-claimed instant payouts as reserve it still holds [5](#0-4) .

So a successfully claimed instant withdrawal leaves a "leaked" receipt: it is paid out once via `_transferFundedClaim`, then counted again as prefunded recovery reserve, inflating `recoveryPrice` and `defaultRecoveryReserve` with tokens that no longer exist in the contract.

### Impact Explanation
Direct fund impact, two modes depending on token balance:

- **Theft from other recovery claimants**: `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is inflated by the phantom prefunded amount, so early claimants through `_claimDefaultedWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest` receive more than their fair share of the real reserve.
- **Permanent freezing**: once the real balance is drained, later `_transferDefaultRecovery` calls either revert on `defaultRecoveryReserve -= _amount` underflow or on `safeTransfer` failure, permanently freezing unclaimed default recovery [6](#0-5) .

Quantified: the leaked amount equals all instant withdrawals requested in the default epoch that were claimed before finalization (bounded by `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` plus the stale claimed portion). No privileged actor is needed: any KYC-passing tranche holder can `requestInstantWithdraw` + `claimInstantWithdrawRequest`; the borrower (honest, per scope) simply fails to fully fund the instant queue at `startEpoch`, and a subsequent default finalization crystallizes the leak.

### Likelihood Explanation
Requires `allowInstantWithdraw` pools where `startEpoch`/`collectInstantWithdrawFunds` only partially funds the instant queue (so `pendingInstantWithdraws != 0` at default, otherwise the stale basis is skipped). In that state every user who claims an instant withdrawal during the epoch inflates the recovery accounting. Default finalization then hard-codes the over-counted reserve with no guard — `_transferFundedClaim` explicitly tries to protect the reserve [7](#0-6)  but nothing validates that `instantWithdrawClaimsByEpoch` reflects only unclaimed receipts.

### Recommendation
In `claimInstantWithdrawRequest()`, clear the per-epoch counters alongside the aggregate: subtract `amount`'s per-epoch components from `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (or the recorded request epoch) and `instantWithdrawClaimsByEpoch[epochNumber]`, so that default-time basis and prefunded-reserve math only count unclaimed receipts. Alternatively, track per-user request epoch for instant withdrawals analogously to `lastWithdrawRequest` for normal withdrawals.

### Proof of Concept
Foundry fork PoC outline (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testInstantClaimLeakInflatesRecovery() external {
    _useInstantWithdrawVariant();            // allowInstantWithdraw = true

    // userA deposits AA, epoch starts
    _depositWithUser(userA, 100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // epoch ends, buffer phase: userA requests instant withdraw of 40k
    vm.prank(userA);
    cdoEpoch.requestInstantWithdraw(40_000 * ONE_SCALE, address(AAtranche));

    // manager startEpoch: borrower partially funds instant queue
    // -> collectInstantWithdrawFunds(10_000) ; pendingInstantWithdraws = 30_000
    // while instantWithdrawClaimsByEpoch[epoch] = 40_000 (prefunded part = 10_000)

    // userA claims during running epoch (funded part)
    vm.prank(userA);
    cdoEpoch.claimInstantWithdrawRequest();  // receives underlying
    // BUG: instantWithdrawsRequestsByEpoch[userA][e] and
    //      instantWithdrawClaimsByEpoch[e] still == 40_000

    // borrower defaults mid-epoch; manager triggers _handleBorrowerDefault
    // -> finalizeDefaultRecovery sees prefundedReserve = 40_000 - 30_000 = 10_000
    //    but only (10_000 - alreadyPaidToA) is actually held → reserve overstated

    uint256 reserve = IdleCreditVault(address(strategy)).defaultRecoveryReserve();
    uint256 bal = underlying.balanceOf(address(strategy));
    assertGt(reserve, bal, "reserve counts already-paid instant claims");

    // Later defaulted claimants' _transferDefaultRecovery reverts (underflow)
    // → their recovery is permanently frozen.
}
```

Key assertions: `instantWithdrawClaimsByEpoch[epoch]` remains non-zero after a successful `claimInstantWithdrawRequest`, and `defaultRecoveryReserve` post-finalization exceeds the strategy's actual underlying balance by the claimed amount.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
