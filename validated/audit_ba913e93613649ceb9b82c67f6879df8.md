### Title
`IdleCreditVault.claimInstantWithdrawRequest` never decrements `instantWithdrawClaimsByEpoch`, double-counting already-paid instant claims in the default recovery basis - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the ksmbd leak (`argv` allocated but not freed on the wakeup/failure path), `IdleCreditVault.requestInstantWithdraw` allocates three pieces of receipt accounting — `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]`, and the epoch-level `instantWithdrawClaimsByEpoch[epoch]` — but the successful funded-claim path in `claimInstantWithdrawRequest` only clears the per-user aggregate. The per-epoch bucket `instantWithdrawClaimsByEpoch` is "leaked" (never decremented on a normal claim), and it is exactly the variable `defaultPendingClaimBasis` uses to size borrower recovery claims at default finalization. Stale claims therefore inflate the recovery basis, dilute `defaultRecoveryPrice`, and let early claimants drain the reserve at the expense of later ones.

### Finding Description
`requestInstantWithdraw` increments `instantWithdrawClaimsByEpoch[currentEpoch]` alongside the per-user receipt. [1](#0-0) 

`collectInstantWithdrawFunds` reduces only `pendingInstantWithdraws`. [2](#0-1) 

`claimInstantWithdrawRequest` burns the receipt, zeroes `instantWithdrawsRequests[_user]` and pays out — but touches neither `instantWithdrawsRequestsByEpoch` nor `instantWithdrawClaimsByEpoch`. [3](#0-2) 

The only place `instantWithdrawClaimsByEpoch` is decremented is the post-default path `_claimDefaultedInstantWithdrawRequest`. [4](#0-3) 

At default finalization, `defaultPendingClaimBasis()` adds the full `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, i.e., while *any other* user's instant request is still unfunded in the same epoch. [5](#0-4)  `finalizeDefaultRecovery` then computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` over this inflated basis. [6](#0-5)  Later, `_claimDefaultedInstantWithdrawRequest` pays `claimBasis * defaultRecoveryPrice` from the reserve — claims against basis that was already paid out at par before default, so the reserve is exhausted early and remaining defaulted-epoch claimants are underpaid or permanently frozen.

### Impact Explanation
Within a single epoch an attacker (any tranche-token holder) can: request an instant withdraw, have it funded via the CDO's `collectInstantWithdrawFunds`/`getInstantWithdrawFunds` flow, claim it at par, then leave another user's unfunded instant request pending in the same epoch when the borrower defaults. `finalizeDefaultRecovery` counts the attacker's already-paid claim again in `totalBasis`, so `defaultRecoveryPrice` is set too low and the `defaultRecoveryReserve` is insufficient for the remaining defaulted claims — direct theft of recovery proceeds by early claimants and permanent freezing/underpayment of later ones, scaling with the size of the stale funded claims (up to the epoch's instant-withdraw volume).

### Likelihood Explanation
Requires no privileged misbehavior: an epoch with both funded-and-claimed instant withdrawals and an unfunded instant remainder, followed by a borrower default in that same epoch. Instant-withdraw mode plus mid-epoch partial funding is a supported configuration, and attacker sequencing (request → funded → claim) uses only public user flows.

### Recommendation
In `claimInstantWithdrawRequest` (and `_claimFundedWithdrawRequest`-style symmetric cleanup), decrement `instantWithdrawClaimsByEpoch[requestEpoch]` and `instantWithdrawsRequestsByEpoch[_user][requestEpoch]` for each funded receipt paid, or clear the per-epoch entries when `instantWithdrawsRequests[_user]` is zeroed, so the epoch-level default basis reflects only truly outstanding claims.

### Proof of Concept
Foundry fork sketch:
1. Start epoch N on an instant-withdraw-enabled `IdleCDOEpochVariant` + `IdleCreditVault`.
2. `requestInstantWithdraw(A_amt, attacker)` and `requestInstantWithdraw(B_amt, victim)`; fund only A via `collectInstantWithdrawFunds` (partial funding), so `pendingInstantWithdraws = B_amt` and `instantWithdrawClaimsByEpoch[N] = A_amt + B_amt`.
3. `claimInstantWithdrawRequest(attacker)` pays A at par; assert `instantWithdrawClaimsByEpoch[N]` still equals `A_amt + B_amt`.
4. Borrower defaults; `finalizeDefaultRecovery(recovered, source)` → `totalBasis` includes `A_amt` twice-counted; `defaultRecoveryPrice` is diluted.
5. `claimInstantWithdrawRequest(victim)` → victim receives `(B_amt * dilutedPrice)/RECOVERY_FULL` or reverts on drained reserve, while attacker already took `A_amt` fully — net reserve shortfall of `A_amt * recoveryPrice`.

    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }

    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
