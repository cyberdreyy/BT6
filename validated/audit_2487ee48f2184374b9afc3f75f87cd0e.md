### Title
Path traversal in `(p *PsWriter) TmpFile`/`Variable` allows a file-type job variable Key to escape `TmpProjectDir()` - (File: shells/powershell.go)

### Summary
`PsWriter.Variable` writes file-type job variables via `TmpFile(variable.Key)`, which simply does `p.Join(p.TemporaryPath, name)` without any sanitization of `name`. Because `Join` uses `path.Join`/`filepath.Join` (both of which lexically collapse `..` segments), a `variable.Key` containing traversal sequences (e.g. `..\..\ProgramData\x`) resolves to a path outside `TemporaryPath`, and `[System.IO.File]::WriteAllText` writes attacker-controlled content there — regardless of whether `resolvePaths` (`UsePowershellPathResolver`) is on or off.

### Finding Description
`shells/powershell.go`: [1](#0-0) 

`TmpFile` does not validate `name` before joining it to `p.TemporaryPath`. Both branches route through `p.Join`: [2](#0-1) 

`path.Join`/`filepath.Join` call `Clean` internally, which lexically resolves `..` components without any bounds checking against the base directory. So `Join("C:\foo\bar", "..\..\ProgramData\x")` yields `C:\ProgramData\x` — completely outside `TemporaryPath`. The only "containment" helper, `isTmpFile`, is a prefix check used for a different purpose (rewriting *values* that reference the tmp dir), not for validating the `Key` used to *build* the tmp file path: [3](#0-2) 

`Variable` then unconditionally calls `TmpFile(variable.Key)` for file-type variables and writes to it: [4](#0-3) 

Notably, the codebase already has a **precedent for defending against exactly this class of input** in `helpers/shell_escape.go`, where dotenv keys are explicitly restricted to `^[A-Za-z_][A-Za-z0-9_]*$` before being trusted: [5](#0-4) 
No equivalent restriction exists for `spec.Variable.Key` in `TmpFile`/`Variable`.

Both the `resolvePaths=true` and `resolvePaths=false` paths are affected:
- `resolvePaths=false`: `TmpFile` calls `cleanPath(Join(...))`, and `cleanPath`/`Absolute` do not re-validate that the result stays under `TemporaryPath` — they only prepend `$CurrentDirectory` for relative paths.
- `resolvePaths=true`: `TmpFile` returns the raw joined path, later wrapped by `resolvePath` in `GetUnresolvedProviderPathFromPSPath(...)`, which resolves relative segments (including `..`) using normal filesystem semantics.

The remaining question is reachability: does an unprivileged pipeline author fully control `Variable.Key` with traversal characters reaching `Variable()`? `spec.Variable.Key` for CI/CD variables is normally the variable name, and GitLab's Rails backend enforces variable naming rules (letters/digits/underscore) *before* variables are sent to Runner — this constraint lives outside this repository and cannot be verified here. Within the Runner codebase itself, however, there is **no enforcement** at this layer; `TmpFile`/`Variable` trust `Key` completely. This makes the Runner code a single-layer-of-defense situation: if the upstream naming validation is ever bypassed, changes, or a different job-variable source (e.g. an internal/dynamic variable, or a future feature) supplies a `Key` with these characters, this code path has no independent guard, unlike the dotenv code path which explicitly guards against invalid keys.

### Impact Explanation
If reached, this allows overwriting/creating an arbitrary file readable/writable by the job's OS user outside `TmpProjectDir()`, e.g., `C:\ProgramData\x`, or with a shared-host multi-tenant executor (e.g. shell executor on Windows), potentially a location later read by another project's job on the same host, persisting after the originating job ends. This matches the "file operations must stay within intended build/cache/artifact roots" invariant.

### Likelihood Explanation
The exploit logic in `TmpFile`/`Join` is real and trivially demonstrable in isolation (as shown by `filepath.Join`/`path.Join`'s `..`-collapsing behavior) — this part is proven. However, whether an *unprivileged* pipeline author can actually supply a `Variable.Key` containing `..`, absolute-path, or drive-qualified segments through GitLab's normal CI/CD-variable or `.gitlab-ci.yml` variable definition flow depends on server-side (GitLab Rails) validation that is outside this repository and not verifiable from the Runner source alone. Given the "Reject … admin-only, leaked-key… purely theoretical issues" and "attacker is unprivileged … controlling job inputs accepted by Runner" framing, and since I cannot confirm within this codebase that Runner receives an unsanitized `Key` from a reachable, unprivileged-controllable field (the only confirmed *unvalidated* variable-name-like path, dotenv, is explicitly guarded elsewhere), likelihood is uncertain/low-to-medium rather than clearly proven end-to-end.

### Recommendation
Add an explicit allowlist check on `variable.Key` (and any other externally-influenced `name` argument) inside `TmpFile`, mirroring `isValidDotEnvKey`, and/or verify post-join that the resolved path's prefix (after `filepath.Clean`) still equals `p.TemporaryPath` before performing `MkDir`/`WriteAllText`; reject or sanitize otherwise, in `shells/powershell.go`'s `TmpFile` (lines 406-412) and equivalent shell writers (`bash.go`, `cmd.go`) for consistency.

### Proof of Concept
```go
func Test_PsWriter_TmpFile_PathTraversal(t *testing.T) {
    tests := []struct{ resolvePaths bool }{{true}, {false}}
    for _, tc := range tests {
        w := &PsWriter{TemporaryPath: `C:\builds\proj.tmp`, resolvePaths: tc.resolvePaths}
        got := w.TmpFile(`..\..\ProgramData\x`)
        assert.True(t, strings.HasPrefix(got, w.TemporaryPath),
            "TmpFile escaped TemporaryPath: got %q (resolvePaths=%v)", got, tc.resolvePaths)
    }
}
```
Expected today: assertion fails, showing `got` resolves to `C:\ProgramData\x`, confirming the path escapes `TemporaryPath`/`TmpProjectDir()`. A fuzz test over `Variable.Key` (`../`, absolute paths, UNC paths, drive letters) asserting `strings.HasPrefix(w.TmpFile(key), w.TemporaryPath)` would similarly demonstrate the gap in the Runner's own code, independent of whether GitLab's backend currently blocks such keys before they reach Runner.
