### Title
Panic during cooperative program loading leaves stale `loading_entries` placeholder and permanently hangs waiting threads - (File: `program-runtime/src/loaded_programs.rs`, `svm/src/transaction_processor.rs`)

### Summary
`ProgramCache::extract()` inserts a placeholder into `loading_entries` under lock to claim the cooperative-loading task for a program key, then returns it to the caller. `TransactionBatchProcessor::replenish_program_cache()` drops the cache lock, calls `load_program_with_pubkey(...).expect("called load_program_with_pubkey() with nonexistent account")`, and only after that re-locks the cache and calls `finish_cooperative_loading_task()`, which removes the `loading_entries` placeholder and calls `loading_task_waiter.notify()`. If the `.expect()` panics (or the thread otherwise aborts/exits) between the unlock and the re-lock, the placeholder in `loading_entries` is never removed and `notify()` is never called.

### Finding Description [1](#0-0) 
marks a program address as "being loaded" in `loading_entries` and returns it as `cooperative_loading_task` while other transaction-processing threads that need the same program key skip claiming the task themselves (they see the entry already `Entry::Occupied`) and instead go to sleep via [2](#0-1)  calling `task_waiter.wait(task_cookie)`.

The thread that "won" the cooperative-loading race releases the `global_program_cache` read lock at [3](#0-2)  and then performs `load_program_with_pubkey(...).expect(...)` at [4](#0-3) . Only if this succeeds does it re-lock the cache and call `finish_cooperative_loading_task()`, which is the only code path that removes the `loading_entries[key]` placeholder and calls `self.loading_task_waiter.notify()`: [5](#0-4) 

If `load_program_with_pubkey` returns `None`/`Err` and the `.expect()` panics, the panic unwinds out of `replenish_program_cache` before `finish_cooperative_loading_task`/`notify()` ever run. The stale `loading_entries` entry for that program key is left in place permanently (the cache is process-global and outlives the panicking task/thread if it's caught elsewhere, e.g. a panic-catching executor or thread pool boundary), and any other thread that is or later becomes blocked in `task_waiter.wait(task_cookie)` for that key will never be woken because `notify()` is never called and no other code path clears that specific `loading_entries` key. This mirrors the rippled bug class exactly: an item is inserted into a shared collection under lock, the lock is dropped, work is done that can throw, and only on success is the lock re-acquired to remove the item — an exception during the unlocked work window causes permanent state corruption and blocks other waiters indefinitely.

### Impact Explanation
Any thread cooperatively waiting on the same missing program (i.e., multiple transaction batches referencing the same not-yet-loaded program concurrently) can hang forever in `task_waiter.wait()`, since the condition variable is only notified from `finish_cooperative_loading_task`. In a validator/RPC node context this manifests as transaction processing threads stuck indefinitely, effectively halting execution progress for any batch depending on that program — a replay/execution livelock triggered by an ordinary account-loading failure path (e.g., a program account being closed/rewritten out from under the loader between `extract()` and the actual load) hitting the `.expect()` panic.

### Likelihood Explanation
This requires the race window between `extract()` marking a program as "loading" and `load_program_with_pubkey()` actually reading the account to be hit with an account state change (e.g., program account closed) that causes `load_program_with_pubkey` to return `None`, at which point `.expect()` panics. The comment at line 953-955 in `transaction_processor.rs` even acknowledges "there is an error in assigning a program to a cache slot. It is not possible to mock this error for SVM unit tests purposes," indicating the failure path exists but is considered hard to trigger deterministically — it is not a routine occurrence but is reachable via ordinary transaction/program deployment activity racing with program cache loading, without requiring any privileged access.

### Recommendation
Use an RAII guard (or a `defer`/scope-guard pattern) that removes the `loading_entries[key]` placeholder and calls `loading_task_waiter.notify()` unconditionally — including on panic — rather than only on the success path inside `finish_cooperative_loading_task()`. Alternatively, replace the `.expect()` in `replenish_program_cache` with proper error propagation that still routes through a cleanup path that clears `loading_entries` and notifies waiters before returning/propagating the error, matching the rippled fix's move away from ad hoc unlock/relock helpers toward guaranteed-cleanup scope guards.

### Proof of Concept
Not directly demonstrable without modifying account state mid-load in a controlled test harness, but conceptually:
1. Thread A calls `replenish_program_cache` for program `P`, which is missing from the cache; `extract()` claims the cooperative-loading task for `P` and inserts `loading_entries[P]`.
2. Concurrently, thread B also needs program `P`; its `extract()` call sees `loading_entries[P]` already occupied and thread B calls `task_waiter.wait(cookie)`.
3. Before thread A's `load_program_with_pubkey(...)` call executes, the account for `P` is closed/removed (e.g., by another transaction in a concurrently executing batch), causing `load_program_with_pubkey` to return `None`.
4. Thread A's `.expect("called load_program_with_pubkey() with nonexistent account")` panics; `finish_cooperative_loading_task` and `loading_task_waiter.notify()` are never called.
5. Thread B remains blocked in `task_waiter.wait()` indefinitely, and `loading_entries[P]` remains permanently occupied, blocking all future cooperative loaders of `P`.
