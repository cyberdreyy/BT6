### Title
`solveRequestsVault` batch reverts entirely if any redeem request's receiver is blacklisted by the redeem token (e.g. USDC), freezing all other users' async requests in the same batch - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2._solveRequestsVault` iterates over an array of `RequestV2` structs supplied by the solver/guardian and fulfills active (non-expired) async redeems by calling `token.safeTransfer(request.receiver, ...)` directly, with no try/catch or fallback. Because this loop processes many independent users' requests in a single transaction, a single request whose `receiver` is blacklisted by the transfer token (e.g. USDC) causes the entire `safeTransfer` call to revert, reverting the whole batch and blocking settlement of every other user's request bundled in that same call, mirroring the exact "blacklisted address bricks batched settlement" pattern from the Sentiment M-12 report.

### Finding Description
In `_solveRedeemVaultFixedPrice` and `_solveRedeemVaultAutoPrice`, the active (pre-deadline) branch does: [1](#0-0) 
i.e. `IMultiDepositorVault(...).exit(...)` followed by a bare `token.safeTransfer(request.receiver, request.tokens)` — no try/catch, no fallback recipient.

This is called from `_solveRequestsVault`, which loops over the **entire** `requests` array supplied to `solveRequestsVault`/`solveRequestsDirect... wait, vault path` in a single for-loop with no isolation between requests: [2](#0-1) 

By contrast, the *expired/refund* branch of the same functions explicitly guards against exactly this scenario using `_transferWithFallback`, which retries to the original requester if the transfer to `receiver` fails: [3](#0-2) [4](#0-3) 

The inconsistency is the root cause: the "happy path" fulfillment (non-expired request) has no equivalent protection, while the refund path does. `request.receiver` is an arbitrary address chosen by the ordinary user when calling `requestRedeem(...)` — any account can specify any `receiver`, including their own address: [5](#0-4) 

If that receiver becomes blacklisted by the redeem token (USDC and other centrally-blacklistable stablecoins are exactly the "bounty-listed" tokens intended to be supported per `setTokenDetails`/`TokenDetailsV2` async-redeem configuration), the `safeTransfer` in the fulfillment branch reverts unconditionally, which propagates up through `_solveRequestsVault` and reverts the **entire** `solveRequestsVault` transaction — including all other, unrelated users' deposit/redeem requests batched together for gas efficiency by the solver/guardian.

### Impact Explanation
This freezes settlement (deposit minting and redeem payout) for every other user whose request was included in the same solver batch, not just the blacklisted user. Until the solver identifies and excludes the poisoned request (requiring off-chain monitoring/blacklist-checking that the protocol does not perform on-chain), no user in that batch can have their async request solved via `solveRequestsVault`, i.e., a live temporary freezing of user funds/yield-bearing unit conversions, consistent with Immunefi's Medium severity for temporary freezing of funds.

### Likelihood Explanation
Any ordinary user can call `requestRedeem` with `receiver` set to their own or any other address, then take an action that causes that specific address to be blacklisted by the transfer token (self-inflicted or externally imposed, as extensively argued in the referenced report). Because `solveRequestsVault` is designed to batch multiple users' requests for efficiency, an attacker only needs one blacklisted receiver mixed into a batch to grief all co-batched users. No privileged role, oracle failure, or third-party fault is required — only that the async-redeem-enabled token supports blacklisting (e.g. USDC) and a normal user can get their own `receiver` blacklisted or supply an already-blacklisted address as `receiver`.

### Recommendation
Wrap the `token.safeTransfer(request.receiver, ...)` calls in `_solveRedeemVaultFixedPrice` and `_solveRedeemVaultAutoPrice` (and the equivalent transfers in `_solveRequestDirect`'s active branch) with the same `_transferWithFallback` pattern already used for refunds, or isolate each request's processing (e.g. via low-level call + try/catch per request, emitting a failure event and skipping/refunding that specific request) so that one poisoned receiver cannot revert the entire batch.

### Proof of Concept
1. On a local fork, deploy/configure `ProvisionerV2` with an async-redeem-enabled token that is a blacklistable ERC20 mock (mint/burn semantics like USDC, with an owner-controlled `blacklist(address)` that makes `transfer`/`transferFrom` revert for that address).
2. User A calls `requestRedeem(token, unitsIn, minTokensOut, ..., receiver = userA)`.
3. User B calls `requestRedeem(token, unitsIn, minTokensOut, ..., receiver = userB)`.
4. Blacklist `userA` on the mock token (simulating either self-inflicted or externally-imposed blacklisting).
5. Solver calls `solveRequestsVault(token, [requestA, requestB], "", "")` with both requests included, both still within deadline (fixed or auto price, non-expired).
6. Assert the transaction reverts (`token.safeTransfer` to `userA` reverts inside the loop), and assert that `requestB` (a legitimate, non-blacklisted user) also fails to settle in this call despite having no defect of its own — demonstrating the freeze of `userB`'s funds/yield conversion caused solely by `userA`'s blacklisted receiver.
7. Show that removing `requestA` from the batch (solver must react out-of-band) is required for `requestB` to settle, proving the shared-batch DoS/freeze.

    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
    }
