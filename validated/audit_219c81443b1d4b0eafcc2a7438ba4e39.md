### Title
Closed-pool `requestWithdraw` records a claimable receipt without adding to `pendingWithdraws`, letting a later requester steal earlier funded withdrawals - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`requestWithdraw` skips `pendingWithdraws += _amount` when the pool is closed (`epochEndDate == 0`), but still records `withdrawsRequests[_user]`, `withdrawsRequestsByEpoch[_user][epoch]` and `lastWithdrawRequest[_user]`, and mints the user a strategy-token receipt. Because `_claimFundedWithdrawRequest` waives the one-epoch wait when the pool is closed, the new requester can claim immediately and `_transferFundedClaim` pays out of the vault's raw underlying balance — which includes underlying previously collected via `collectWithdrawFunds`/`collectInstantWithdrawFunds` for earlier, still-unclaimed receipts. The accounting leak (receipt recorded, liability counter not incremented) mirrors the reference-count leak: state is incremented on a path where the matching funding obligation is never created.

### Finding Description
In `requestWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:277-294):

```solidity
if (!isClosed) {
  pendingWithdraws += _amount;
}
lastWithdrawRequest[_user] = currentEpoch;
if (unscaledApr == 0 && !isClosed) {
  _requestWithdrawApr0(_amount, _user);
} else {
  withdrawsRequests[_user] += _amount;
  withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
}
```

When the pool is closed the per-user claim basis is still recorded and `_amount` receipt tokens are minted (line 275), but the global `pendingWithdraws` is never increased, so no funding will ever be sourced for this receipt — the borrower has already repaid and there is no later `stopEpoch`.

In `_claimFundedWithdrawRequest` (lines 326-349) the epoch-wait check `epochNumber <= lastWithdrawRequest[_user]` is skipped entirely when `epochEndDate() == 0`, so the receipt is instantly claimable. `_transferFundedClaim` (lines 897-907) only protects `defaultRecoveryReserve`; any other underlying sitting in the strategy — crucially, funds collected for earlier funded-but-unclaimed withdraw/instant receipts — is fair game.

### Impact Explanation
Direct theft of funded, unclaimed withdrawal proceeds. After pool close, user A has a funded receipt whose underlying sits in the vault awaiting `claimWithdrawRequest`. Attacker B (any unprivileged tranche holder) calls `requestWithdraw` through the CDO: burns `_principal` of CDO strategy tokens, gets `_amount ≈ principal + interest` recorded and minted as receipt, then calls `claimWithdrawRequest` in the same transaction and is paid `amount` out of A's funded underlying. A's later claim reverts on insufficient balance — permanent loss of A's principal and yield up to the vault's unreserved balance, while B recovers principal plus the interest spread. Broken invariant: one receipt one payout / funded-claim isolation.

### Likelihood Explanation
Requires the vault to be in closed mode (`epochEndDate == 0`), i.e., borrower repaid in full / pool wound down — a normal terminal state. Attacker needs only a tranche position to call `requestWithdraw` via the CDO; no privileged role. The only precondition is that some earlier receipt holder has not yet claimed, which is common since claims are pull-based. The guard added for loss-adjusted epochs (lines 263-271) only blocks users with unclaimed *loss-adjusted* receipts, not ordinary funded receipts.

### Recommendation
In `requestWithdraw`, either revert entirely when `epochEndDate == 0`, or skip recording `withdrawsRequests`/`withdrawsRequestsByEpoch`/`lastWithdrawRequest` and the receipt mint whenever `pendingWithdraws` is not incremented, so receipt state and the funding counter stay balanced. Alternatively, track a funded-claim reserve and make `_transferFundedClaim` spend only amounts attributed to the caller's own funded receipts.

### Proof of Concept
Foundry fork PoC (scaffolding matches `test/foundry/IdleCreditVault.t.sol`):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "./IdleCreditVault.t.sol";

contract ClosedPoolReceiptDrainPoC is IdleCreditVaultTest {
  function testClosedPoolRequestStealsFundedClaim() public {
    // --- epoch runs, user A requests withdraw, epoch stops and is funded ---
    uint256 depA = 100_000 * ONE;
    _depositCDO(address(AATranche), depA);        // A deposits, gets AA tranche
    _startEpochAndFund();

    vm.prank(address(cdo));
    strategy.requestWithdraw(depA / 2, alice, depA / 2); // simplified via CDO redeem path

    _stopEpochAndRepay();                       // borrower repays; collectWithdrawFunds
                                                // pulls funded amount into strategy
    // Pool is then closed: cdo.epochEndDate() == 0 (manager/borrower close flow)
    _closePool();

    uint256 fundedBal = underlying.balanceOf(address(strategy));
    assertGt(fundedBal, 0);                     // A's funded claim sits in the vault

    // --- attacker B, holding tranche tokens, requests withdraw post-close ---
    address bob = address(0xB0B);
    _depositCDO(address(AATranche), 10_000 * ONE); // pre-close deposit for bob (or existing holder)
    uint256 bobBalBefore = underlying.balanceOf(bob);

    vm.prank(address(cdo));
    strategy.requestWithdraw(10_000 * ONE, bob, 10_000 * ONE);
    // pendingWithdraws unchanged (closed pool), but withdrawsRequests[bob] recorded

    vm.prank(address(cdo));
    uint256 paid = strategy.claimWithdrawRequest(bob); // no epoch wait when closed

    assertGt(paid, 0);
    assertGt(underlying.balanceOf(bob), bobBalBefore); // bob paid immediately

    // A's funded claim can no longer be honored
    vm.prank(address(cdo));
    vm.expectRevert();                           // insufficient unreserved balance
    strategy.claimWithdrawRequest(alice);
  }
}
```

Key assertions: after B's post-close `requestWithdraw`, `strategy.pendingWithdraws()` is unchanged while `strategy.withdrawsRequests(bob) > 0`; B's `claimWithdrawRequest` succeeds immediately and reduces the vault balance below the sum of outstanding funded receipts, making A's claim revert.
