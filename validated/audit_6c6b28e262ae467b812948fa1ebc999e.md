### Title
Unbounded per-key growth of the SPL-token-owner secondary index enables a griefing DoS against `getTokenAccountsByOwner`/`getProgramAccounts` scans - (File: `accounts-db/src/accounts_index/secondary.rs`)

### Summary
The `--account-index spl-token-owner` secondary index maps an SPL token account "owner" field (attacker-controlled, unauthenticated data taken from token-account bytes) to an unbounded `HashSet<Pubkey>` of token-account keys. Any unprivileged user can create arbitrary numbers of SPL token accounts whose `owner` field is set to a victim pubkey, without that victim's signature, growing the victim's secondary-index bucket without limit. This is structurally the same bug class as the reported Alchemix `MAX_DELEGATES` griefing: a size-limited (here, size-*unlimited*) attacker-appendable list keyed by a victim identity, whose later per-victim operations (index-key scan, insert, iteration, metrics logging) become O(n) in attacker-controlled `n`.

### Finding Description
`update_spl_token_secondary_indexes` inserts a `(owner_pubkey, token_account_pubkey)` pair into `spl_token_owner_index` purely from the on-chain token-account bytes at account-store time, with no cap on how many token accounts a single owner key can be associated with: [1](#0-0) 

The insertion path, `SecondaryIndex::insert`, unconditionally grows the per-key `RwLockSecondaryIndexEntry`'s `HashSet<Pubkey>` on every new token account observed for that owner — there is no `MAX_*` bound analogous to the `MAX_DELEGATES` cap in the reported Solidity bug: [2](#0-1) [3](#0-2) 

Because SPL token account creation/initialization does not require the "owner" address itself to sign (owner is just an arbitrary pubkey embedded in the account data, checked only by the token program at spend-time, not by anything that gates who may be named as owner), an attacker can create an unbounded number of throwaway token accounts naming any victim pubkey as owner. Each such account causes `spl_token_owner_index.insert(owner_key, pubkey)` to add one more entry to that victim's bucket.

This bucket is later fully materialized any time a client queries by that owner, e.g. via `get_filtered_spl_token_accounts_by_owner`, which — when the `SplTokenOwner` index is enabled — calls `get_index_key_pubkeys`/`index_scan_accounts`, iterating and loading every pubkey in the (now attacker-inflated) bucket: [4](#0-3) [5](#0-4) [6](#0-5) 

This mirrors the reported issue precisely in shape: a costless/cheap attacker action (creating garbage token accounts referencing a victim's key) causes every future legitimate operation referencing that victim's key (RPC lookups, `do_load` for each returned pubkey, periodic `log_secondary_indexes` metrics scan) to become linear in the number of attacker-inserted entries, with no upper bound comparable to the `MAX_DELEGATES=1024` cap that (even though insufficiently tight) at least existed in the reported contract.

### Impact Explanation
Any validator/RPC node operator who enables `--account-index spl-token-owner` (a supported, documented production configuration for indexing) exposes its RPC users to an unbounded griefing cost increase: a victim's `getTokenAccountsByOwner` RPC calls, and the node's own periodic secondary-index scans/logging (`log_secondary_indexes`, `purge_secondary_indexes_for_dead_keys`), scale linearly with attacker-created noise accounts tied to the victim's pubkey. Because rent-exemption for a minimal SPL token account is cheap relative to the compute/IO cost imposed on RPC infra for every subsequent owner-indexed query, this is a genuine asymmetric griefing vector against RPC availability/latency for a targeted owner key — directly analogous to the "100x cost increase, no profit motive" impact described in the report. It does not cause unauthorized fund movement, but it degrades RPC service (ingest/indexing category) for a targeted key, and can also inflate node memory (unbounded `HashSet`/`Vec` growth in `index` and `reverse_index` DashMaps) over time.

### Likelihood Explanation
High for any deployment that enables the SPL-token-owner secondary index (a config knob explicitly exposed and tested, see `validator/src/commands/run/args/account_secondary_indexes.rs`). The attack requires no special privilege: only the ability to submit ordinary `CreateAccount` + SPL Token `InitializeAccount`-class transactions naming an arbitrary owner, which is a completely permissionless, standard operation. No signature from the targeted owner is needed.

### Recommendation
- Impose a per-owner-key cap (analogous to `MAX_DELEGATES`, but tuned much lower given each entry costs a full account load) on the number of inner keys the `spl_token_owner_index` (and other secondary indexes) will track for a single outer key, rejecting/dropping further index insertions once the cap is hit while still tracking the accounts in the primary index.
- Alternatively/additionally, bound and paginate `index_scan_accounts`/`get_filtered_spl_token_accounts_by_owner` result sets and cost-account for RPC purposes so that a single indexed key cannot force unbounded work per request.
- Consider requiring the token account's declared owner to be validated against a minimum balance / rent-exemption+dust economic disincentive, or emit metrics/alerts when a single index key's inner-key count crosses an anomalous threshold so operators can react (the existing `log_secondary_indexes`/`num_inner_keys` stat already tracks this per-key growth but takes no protective action).

### Proof of Concept
Not independently executed against a live validator in this review; the following outlines the reachable path validated purely from source review (no live/dynamic verification was performed given tool constraints):
1. Start (or use) a validator/RPC node with `--account-index spl-token-owner` enabled.
2. Repeatedly submit permissionless transactions creating new SPL Token accounts (`CreateAccount` + `InitializeAccount`) whose `owner` field is set to a fixed victim pubkey `V` that never signs any of these transactions.
3. Each such account store triggers `AccountsIndex::update_secondary_indexes` → `update_spl_token_secondary_indexes` → `SecondaryIndex::insert(V, new_token_account_pubkey)` (`accounts-db/src/accounts_index.rs:557-580`, `accounts-db/src/accounts_index/secondary.rs:132-171`), growing `spl_token_owner_index`'s bucket for `V` without limit.
4. Issue `getTokenAccountsByOwner` for `V` (routed through `get_filtered_spl_token_accounts_by_owner` → `get_index_key_pubkeys`/`index_scan_accounts`, `rpc/src/rpc.rs:2310-2356`, `accounts-db/src/accounts_db.rs:3358-3421`) and observe that the number of `do_load` calls (and thus RPC latency/CPU cost) scales linearly with the number of attacker-created noise accounts, with no cap analogous to `MAX_DELEGATES` preventing this growth.

impl SecondaryIndexEntry for RwLockSecondaryIndexEntry {
    fn insert_if_not_exists(&self, key: &Pubkey, inner_keys_count: &AtomicU64) {
        if self.account_keys.read().unwrap().contains(key) {
            // the key already exists, so nothing to do here
            return;
        }

        let was_newly_inserted = self.account_keys.write().unwrap().insert(*key);
        if was_newly_inserted {
            inner_keys_count.fetch_add(1, Ordering::Relaxed);
        }
    }

    /// Inserts `inner_key` into `key`'s map.
    pub fn insert(&self, key: &Pubkey, inner_key: &Pubkey) {
        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.
        let reverse_index_entry = self
            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
        let mut outer_keys = reverse_index_entry.write().unwrap();

        // Now insert into the index.
        // Note, we do this get()-then-unwrap instead of calling entry() directly, because
        // get() is a read lock whereas entry() is a write lock.  We assume `key` already has
        // a map created, so optimize for the common case and only take a read lock.
        self.index
            .get(key)
            .unwrap_or_else(|| self.index.entry(*key).or_default().downgrade())
            .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);

        if !outer_keys.contains(key) {
            outer_keys.push(*key);
        }

        // explicitly drop the locks so we don't hold them while reporting metrics
        drop(outer_keys);
        drop(reverse_index_entry);

        if self.stats.last_report.should_update(1000) {
            datapoint_info!(
                self.metrics_name,
                ("num_secondary_keys", self.index.len(), i64),
                (
                    "num_inner_keys",
                    self.stats.num_inner_keys.load(Ordering::Relaxed),
                    i64
                ),
                ("num_reverse_index_keys", self.reverse_index.len(), i64),
            );
        }
    }

    pub(crate) fn index_scan_accounts<F>(
        &self,
        ancestors: &Ancestors,
        bank_id: BankId,
        index_key: IndexKey,
        mut scan_func: F,
        config: &ScanConfig,
    ) -> ScanResult<bool>
    where
        F: FnMut(Option<(&Pubkey, AccountSharedData, Slot)>),
    {
        let key = match &index_key {
            IndexKey::ProgramId(key) => key,
            IndexKey::SplTokenMint(key) => key,
            IndexKey::SplTokenOwner(key) => key,
        };
        if !self.account_indexes.include_key(key) {
            // the requested key was not indexed in the secondary index, so do a normal scan
            let used_index = false;
            self.scan_accounts(ancestors, bank_id, scan_func, config)?;
            return Ok(used_index);
        }

        // Register this scan so that slots needed by the scan are not cleaned out from under us.
        let scan_guard = ScanGuard::try_new(&self.scan_tracker, bank_id, || self.max_root())
            .ok_or(ScanError::SlotRemoved {
                slot: ancestors.max_slot(),
                bank_id,
            })?;

        // If the scan's ancestors are all rooted, drop them and scan roots only
        // Scan Guard max root must be used as the scan guard guarantees that
        // the account state as of max root is persisted in the database
        let max_root_ancestors = Ancestors::from(vec![scan_guard.max_root()]);
        let ancestors = if scan_guard.should_use_ancestors(ancestors) {
            ancestors
        } else {
            &max_root_ancestors
        };

        for pubkey in self.accounts_index.get_index_key_pubkeys(&index_key) {
            if config.is_aborted() {
                break;
            }
            if let Some((account, slot)) = self.do_load(
                ancestors,
                &pubkey,
                LoadHint::Unspecified,
                PopulateReadCache::False,
            ) {
                scan_func(Some((&pubkey, account, slot)));
            }
        }

        // Check whether the bank was removed while the scan was in progress.
        if scan_guard.was_scan_corrupted() {
            return Err(ScanError::SlotRemoved {
                slot: ancestors.max_slot(),
                bank_id,
            });
        }
        let used_index = true;
        Ok(used_index)
    }
