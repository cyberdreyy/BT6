### Title
`requestInstantWithdraw` misses the post-default and loss-adjustment guards present in `requestWithdraw`, letting post-default receipts merge into the defaulted-epoch bucket and drain `defaultRecoveryReserve` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Like the simple-git CVE — where the `--upload-pack` injection fix covered `git fetch` but not the equivalent `git clone` vector — `IdleCreditVault.requestWithdraw` carries two protective branches that were never replicated in the sibling entrypoint `requestInstantWithdraw`:

1. the `defaultRecoveryFinalized` branch that routes post-default receipts into `postDefaultRequests` and rejects users with any pending request (`_hasWithdrawRequest`, `instantWithdrawsRequests`, `postDefaultRequests`) — `contracts/strategies/idle/IdleCreditVault.sol:247-257`;
2. the `lossRecoveryPriceByEpoch` guard that forbids opening a new request while the user still holds an unclaimed loss-adjusted receipt — `IdleCreditVault.sol:261-271`.

`requestInstantWithdraw` (`IdleCreditVault.sol:356-375`) has neither. It unconditionally mints a receipt into `instantWithdrawsRequests[_user]` and, critically, into `instantWithdrawsRequestsByEpoch[_user][epochNumber]` using the *current* `epochNumber` — which is frozen at `defaultRecoveryEpoch` after default finalization because `stopEpoch`/`epochNumber++` can no longer run.

### Finding Description
After `finalizeDefault`/`finalizeDefaultRecovery` sets `defaultRecoveryFinalized` and `defaultInstantWithdrawsFinalized`, the pool keeps servicing `CDO.requestWithdraw`. When the instant-withdraw path is reachable (`_isInstantWithdrawEnabled()` and `lastEpochApr > unscaledApr + instantWithdrawAprDelta`, which is realistic in a defaulted pool whose new APR was cut), the CDO calls `creditVault.requestInstantWithdraw(_underlyings, msg.sender)` (`IdleCDOEpochVariant.sol:765`).

That call:
- skips the `defaultRecoveryFinalized` → `postDefaultRequests` routing entirely;
- increments `instantWithdrawsRequestsByEpoch[user][epochNumber]` where `epochNumber == defaultRecoveryEpoch`, so a **brand-new post-default receipt is indistinguishable from a defaulted-epoch receipt**;
- increments `pendingInstantWithdraws`, which post-default is supposed to be only the unfunded defaulted remainder.

On `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` (`IdleCreditVault.sol:842-856`) reads `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` — now including the attacker's post-default amount — burns the receipt, decrements `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch[defaultEpoch]`, and pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` via `_transferDefaultRecovery`, which debits `defaultRecoveryReserve` (`IdleCreditVault.sol:912-917`).

Broken invariant: **reserve isolation / one-receipt-one-payout**. The isolated recovery reserve, sized at finalization exactly for defaulted-epoch claimants, is spent on post-default receipts that were never part of the haircut basis. Additionally, if the attacker still holds an unclaimed loss-adjusted `lastWithdrawRequest` epoch, the missing `lossRecoveryPrice` guard lets instant requests proceed in states that `requestWithdraw` explicitly forbids.

### Impact Explanation
- Direct theft of unclaimed recovery yield: each post-default instant receipt of amount `A` extracts `A * defaultRecoveryPrice / RECOVERY_FULL` underlying from `defaultRecoveryReserve`, which was sized to cover exactly the defaulted-epoch receipts. Every unit the attacker drains short-changes honest defaulted claimants — the last claimants' `_transferDefaultRecovery` underflows/reverts, so the loss is permanent for them.
- Accounting corruption: `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch[defaultEpoch]` are decremented by amounts they never rightfully contained, so reserve solvency can break earlier than the nominal haircut math suggests.
- Quantified loss: up to `instantAmount * defaultRecoveryPrice / RECOVERY_FULL` per attacker tranche position, repeatable per account; bounded only by post-default deposits and reserve size.

### Likelihood Explanation
Requires: a defaulted and finalized vault (not rare — the codebase has a full default-recovery lifecycle), instant withdrawals enabled, and a post-finalization APR drop exceeding `instantWithdrawAprDelta` so `requestWithdraw` takes the instant branch — a defaulted borrower typically triggers exactly such an APR cut. The attacker needs only to be a KYC-passed tranche holder (unprivileged per scope). No privileged collusion needed. The main uncertainty is whether `_isInstantWithdrawEnabled()` remains true after default finalization in the specific deployment mode; the function is gated by flags and programmable-borrower exclusion rather than epoch state, and `IdleCreditVault.requestWithdraw`'s own post-default branch demonstrates the designers intended request/claim UX to remain live post-default.

### Recommendation
Mirror the `requestWithdraw` guards in `requestInstantWithdraw`:
- when `defaultRecoveryFinalized`, either revert `NotAllowed()` or route the receipt into `postDefaultRequests` (checking `_hasWithdrawRequest`, `instantWithdrawsRequests`, `postDefaultRequests` first);
- enforce the `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` unclaimed-receipt check before minting;
- alternatively, record post-default instant receipts under a dedicated bucket rather than `instantWithdrawsRequestsByEpoch[user][epochNumber]` so they can never merge with `defaultRecoveryEpoch` claims.
