### Title
A de-whitelisted (suspended) lender can bypass the Keyring credential gate and exit with funds, directly or via a whitelisted colluder — (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant` enforces the Keyring whitelist (`isWalletAllowed`) only on the deposit side. Withdrawal request and claim paths — `requestWithdraw`, `claimWithdrawRequest`, `claimInstantWithdrawRequest`, and the queue's `claimWithdrawRequest` — never re-check `isWalletAllowed`, and `IdleCDOTranche` tokens are freely transferable ERC20s. A user whose Keyring credential is revoked (the analog of Symmetrical's suspended PartyA) can therefore still pull all underlying out of the vault, either directly or by transferring tranche tokens to a still-whitelisted colluder who requests and claims on their behalf.

### Finding Description
- `isWalletAllowed` consults `IKeyring.checkCredential` (Keyring revocation removes access) at `contracts/IdleCDOEpochVariant.sol:984-987`.
- The only enforcement is in `_deposit` at `contracts/IdleCDOEpochVariant.sol:644-650` (`_checkNotAllowed(!isWalletAllowed(msg.sender))`).
- `claimWithdrawRequest` (lines 967-971) and `claimInstantWithdrawRequest` (lines 975-979) forward `msg.sender` to `IdleCreditVault` with no credential check; the vault's `_transferFundedClaim` sends underlying straight to that `_user` (`contracts/strategies/idle/IdleCreditVault.sol:301-350`, `901-906`).
- Strategy-token receipt claims are deliberately address-bound (`_transfer` reverts unless `msg.sender == idleCDO`, `IdleCreditVault.sol:939-942`), but the *tranche* tokens themselves are ordinary transferable ERC20s, so the position itself can be moved to a colluding whitelisted wallet, which then requests and claims the withdrawal — the exact collusion pattern from the source report.
- There is no `suspendedAddresses`/blocklist mechanism and no re-validation of credentials at withdrawal time, so the intended "de-KYC'd users cannot take funds out" invariant is broken in both directions: the suspended user can self-claim existing receipts, and can fully exit principal by transferring tranche tokens to an allowed counterparty.

### Impact Explanation
The compliance/suspension guarantee is void: a user flagged by Keyring (sanctions, fraud, offboarding) retains full ability to withdraw all principal and yield, directly or via any whitelisted colluder who can receive tranche tokens trustlessly (atomic swap). For a regulated credit vault this is a direct bypass of the intended fund-freezing effect of credential revocation — equivalent in severity to the source Medium finding (suspended party exits with funds).

### Likelihood Explanation
High whenever credential revocation is actually used: Keyring revocation is the designed suspension mechanism (`checkCredential` returns false), and both bypass routes require no privileged action — the user calls `requestWithdraw`/`claimWithdrawRequest` themselves in the buffer phase, or transfers `IdleCDOTranche` tokens to any whitelisted EOA/contract in a single transaction. No timing or collusion with privileged roles is needed.

### Recommendation
Apply `isWalletAllowed` checks consistently to exit paths: gate `requestWithdraw`, `claimWithdrawRequest`, and `claimInstantWithdrawRequest` (and the epoch queue's user-facing claim functions) on `isWalletAllowed(msg.sender)`, or introduce an explicit suspended-address mapping honored by all fund-moving entry points. Optionally gate `IdleCDOTranche` transfers so tranche tokens cannot be moved to a different credential status class without redemption, mirroring the source recommendation to "restrict accepting of pending quotes of suspended users."

### Proof of Concept
Foundry fork PoC sketch (against the existing harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// Buffer phase: user deposits while credentialed
uint256 trancheBal = _depositWithUser(suspendedUser, amount, true);

// Admin/Keyring revokes credential -> isWalletAllowed(suspendedUser) == false
keyring.setCredential(policyId, suspendedUser, false);
assertFalse(cdoEpoch.isWalletAllowed(suspendedUser));

// 1) Direct bypass: suspended user requests and later claims
vm.prank(suspendedUser);
cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));
// run epoch
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, apr, expectedFunds);
vm.prank(suspendedUser); // succeeds despite revoked credential
cdoEpoch.claimWithdrawRequest();
assertGt(underlying.balanceOf(suspendedUser), 0);

// 2) Collusion bypass: suspended user transfers tranches to whitelisted colluder
vm.prank(suspendedUser);
AAtranche.transfer(colluder, trancheBal);
vm.prank(colluder);
cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));
// next epoch
vm.prank(colluder);
cdoEpoch.claimWithdrawRequest();
// colluder sends underlying back to suspendedUser -> suspended user exits with funds
```

Note: I confirmed the absence of `isWalletAllowed` on the claim entry points in `IdleCDOEpochVariant.sol:967-979` and on the queue's `claimWithdrawRequest` (`IdleCDOEpochQueue.sol:393-411`, where `_checkAllowed` is only applied to deposit requests). One residual uncertainty: if a separate blocklist exists elsewhere in the periphery (not found in this index), the direct path may be covered — but the tranche-transfer/collusion path is not, since tranche tokens carry no credential check on transfer.
