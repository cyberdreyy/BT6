### Title
Unprotected job can force `config.Protected=true` via `-protected`-suffixed cache key and collide with a genuinely protected build's cache volume/host path - ([File: executors/docker/volume.go])

### Summary
`createVolumesManager` sets `config.Protected` to `true` whenever any `spec.Cache.Key` in the job ends with `-protected` (and not `-non_protected`), regardless of the actual ref protection state. Because the resulting cache volume name / host-cache path is derived only from `ManagerConfig.UniqueName` (project-scoped, not ref-scoped) and `hashPath(destination)` plus this boolean-controlled suffix, an unprotected-branch job can compute and use the identical volume name / host directory that a legitimately protected-ref build of the same project would use, obtaining read/write access to that cache location.

### Finding Description
In `createVolumesManager` (`executors/docker/volume.go:14-28`), `protectedKeyIdx` is computed purely from attacker-controlled `.gitlab-ci.yml` `cache:key` strings:
```go
protectedKeyIdx := slices.IndexFunc(e.Build.Cache, func(c spec.Cache) bool {
    return strings.HasSuffix(c.Key, "-protected") && !strings.HasSuffix(c.Key, "-non_protected")
})
...
Protected: e.Build.IsProtected() || protectedKeyIdx >= 0,
```
This flag is later used in `manager.withProtected` (`executors/docker/internal/volumes/manager.go:294-299`) to append a fixed `"-protected"` suffix to either:
- the Docker named-volume name in `createCacheVolume` (`manager.go:209-218`): `withProtected(fmt.Sprintf("%s-cache-%s", name, hashedDestination))`, where `name = m.config.UniqueName` for reusable volumes, or
- the host-based cache directory in `createHostBasedCacheVolume` (`manager.go:169-191`): `dir := m.withProtected(hashPath(destination)); hostPath := Join(CacheDir, UniqueName, dir)`.

Both `UniqueName` (`e.Build.ProjectRealUniqueName()`) and `hashPath(destination)` (an MD5 of the container path) are deterministic and depend only on the project/build slot and the cache mount destination — not on which ref or protection state produced the build. Therefore, for the same project and the same cache `destination`, a build with `IsProtected()==true` and a build with `IsProtected()==false` but a cache key crafted to end in `-protected` produce the exact same `volumeName`/`hostPath`. Since these volumes/host directories are declared reusable/persistent cache storage (not per-build ephemeral), whichever job writes to it first, and whichever reads afterward, share the same underlying storage. No existing check validates that the caller is actually running on a protected ref before honoring the `-protected` suffix — the suffix match on the cache key string is the *only* signal used, and it is fully attacker-controlled input from `.gitlab-ci.yml`.

### Impact Explanation
An unprivileged pipeline author on an unprotected branch can, purely by choosing a cache key ending in `-protected` in their own `.gitlab-ci.yml`, cause their job's cache volume or host-cache directory to resolve to the same identifier that legitimate protected-ref builds of the same project use. This grants the unprotected job read and write access to what is intended to be an isolated, protected-ref-only cache store — i.e., a concrete cross-protection-boundary cache read/write, letting an unprotected job read cache contents produced by protected pipelines (potential secret/credential leakage) or write/poison the cache that a subsequent protected pipeline will later consume.

### Likelihood Explanation
Fully feasible and repeatable: the only precondition is that the attacker can define `cache:key` values in `.gitlab-ci.yml` for a project and run pipelines on an unprotected branch (a normal capability of any contributor able to open a pipeline/merge request). No special runner configuration, admin action, or race condition is needed — the mapping from cache key suffix to `config.Protected` and from `config.Protected` to volume/path naming is deterministic and always reachable via `createVolumesManager` → `createCacheVolume`/`createHostBasedCacheVolume` → `withProtected(hashPath(destination))`.

### Recommendation
Do not let job-supplied cache key strings alone toggle `config.Protected`. If the `-protected`/`-non_protected` cache-key convention must be supported at all, it should only take effect when combined with a server-verified indicator, not a client-suppliable string equality check. At minimum, ensure `config.Protected` is derived exclusively from `e.Build.IsProtected()` (a value asserted by GitLab, not the job's own YAML), or bind the volume/path naming to a value that differs between protected and unprotected refs (e.g., mix in the actual protection bit and ref name/project visibility state verified server-side) so that no attacker-chosen string can force a name collision with a genuinely protected build's storage.

### Proof of Concept
```go
func TestCreateVolumesManager_CacheKeySuffixForgesProtected(t *testing.T) {
    destination := "/cache"

    // Build A: genuinely protected ref, ordinary cache key.
    protectedBuild := &common.Build{
        JobResponse: common.JobResponse{
            GitInfo: common.GitInfo{Ref: "main", RefType: common.RefTypeBranch},
        },
    }
    // IsProtected() == true via server-verified field, no "-protected" key needed.
    cfgA := volumes.ManagerConfig{
        UniqueName: "runner-x-project-1-concurrent-0",
        Protected:  true, // e.Build.IsProtected() == true
    }

    // Build B: unprotected ref, but attacker sets cache key "foo-protected".
    cfgB := volumes.ManagerConfig{
        UniqueName: "runner-x-project-1-concurrent-0", // same project/slot
        Protected:  false || (indexOfProtectedSuffix([]string{"foo-protected"}) >= 0), // == true
    }

    mgrA := newManagerWithConfig(cfgA)
    mgrB := newManagerWithConfig(cfgB)

    nameA := mgrA.WithProtectedForTest(hashPath(destination)) // exported test helper wrapping withProtected
    nameB := mgrB.WithProtectedForTest(hashPath(destination))

    // BUG: names collide even though build B never ran on a protected ref.
    assert.Equal(t, nameA, nameB, "unprotected job forged the protected cache volume name")
}
```
Expected assertion on a fixed codebase: `nameA` and `nameB` must differ (e.g., by incorporating a server-verified protection token distinct from a client-suppliable cache key), proving the unprotected build cannot compute the same storage identifier as the genuinely protected build.
