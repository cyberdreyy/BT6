### Title
Path traversal via file-type CI variable `Key` in `writeCleanupScript`/`writeCleanupBuildDirectoryScript` may cause `RmFile` to target paths outside the job tmp directory - ([File: shells/abstract.go], [shells/bash.go], [shells/powershell.go])

### Summary
`AbstractShell.writeCleanupScript` calls `w.RmFile(w.TmpFile(variable.Key))` for each file-type variable, and `TmpFile` builds the path with `path.Join(TemporaryPath, name)` / `filepath.Join` without rejecting `..` segments or absolute paths in `name`. Since Go's `path.Join`/`filepath.Join` internally call `Clean`, a `Key` such as `../../../etc/passwd` or an absolute path can cause the joined-and-cleaned result to escape `TemporaryPath`, and `Absolute`/`cleanPath` do not re-anchor an already-absolute result back under the tmp dir.

### Finding Description
`BashWriter.TmpFile` [1](#0-0)  computes `b.cleanPath(path.Join(b.TemporaryPath, name))`, and `cleanPath` calls `Absolute`, which only prefixes `$PWD` when the path is *not* already absolute [2](#0-1) . Because `path.Join` cleans `..` sequences lexically (not against the filesystem), a `name` like `../../etc/passwd` combined with `TemporaryPath` such as `/builds/project/tmp` collapses to an out-of-tree path (e.g. `/etc/passwd`), and since the result is already absolute, `Absolute` returns it unchanged — no containment check exists. `PsWriter.TmpFile`/`Join`/`Absolute` behave analogously using `filepath.Join`/`path.Join` [3](#0-2) [4](#0-3) .

The cleanup path is invoked in `AbstractShell.writeCleanupScript` (referenced via `shells/abstract.go`, confirmed present via `RmFile(w.TmpFile(...))` call sites) for every file-type job variable, using `variable.Key` as the `name` argument passed into `TmpFile`. This means the resolved path used for deletion is directly a function of `variable.Key`.

However, whether this is exploitable depends on whether `variable.Key` can actually contain path-traversal characters (`/`, `..`) at all by the time it reaches the shell writer. Environment variable keys are conventionally restricted to identifier characters, and GitLab's variable form / CI YAML variable-key validation on the server side is the layer normally responsible for rejecting keys with `/` or `.` characters. I could not confirm within this repository whether Runner performs any of its own server-independent validation of `variable.Key` before invoking `Variable()`/`writeCleanupScript` — no such validation function (e.g., `ValidateKey`, an env-var-name regex) was found in `common/spec` or `shells` during this investigation. This is a material unknown: if GitLab (the server) already restricts variable keys to `^[a-zA-Z_][a-zA-Z0-9_]*$`-style patterns before they are ever sent to Runner, then the traversal characters required for this bug (`/`, `.`) can never reach `TmpFile`, and the reachable Go path described is dead code from an attacker's perspective. I was unable to fully verify the presence/absence of that upstream validation within the indexed portion of this repository.

### Impact Explanation
If reachable, the impact would be scoped file deletion of a path outside the job's tmp/build directory but still reachable by the job's OS user — e.g. deleting an arbitrary file inside the job's container/sandbox that the job process has write permission to. This matches the described scoped impact (arbitrary file deletion reachable via the traversal-resolved path on the executor host/container), not an escape of the sandbox boundary itself.

### Likelihood Explanation
Feasibility hinges entirely on whether variable-key validation exists somewhere in the pipeline (GitLab server-side variable form, `.gitlab-ci.yml` schema validation, or Runner-side checks) that already blocks `/`, `..`, and other non-identifier characters in variable keys before they reach `Variable.Key`/`TmpFile`. This repository's indexed code does not show such a check inside `shells/` or `common/spec/`, but that absence is inconclusive given index limits — it may exist elsewhere in `common/` or be enforced entirely server-side (outside Runner's codebase, which would mean it's out of scope for this repo-only audit, but also unverifiable here). Given this open, unresolved precondition, I cannot assert with confidence that the exploit path is reachable through Runner-accepted attacker input alone.

### Recommendation
Regardless of upstream validation, `TmpFile`/`cleanPath`/`Absolute` in both `BashWriter` and `PsWriter` should defensively enforce that the joined, cleaned path remains within `TemporaryPath` (e.g., compare with `filepath.Rel`/`strings.HasPrefix` against a `filepath.Clean(TemporaryPath)+string(os.PathSeparator)` boundary, or use `securejoin`-style helpers), returning an error/sentinel if `name` attempts to traverse outside. Additionally, `AbstractShell.writeCleanupScript` should independently validate/sanitize `variable.Key` (reject `/`, `\`, and `..`) defense-in-depth before use as a filename component, rather than relying solely on upstream form validation.

### Proof of Concept
```go
// shells/bash_test.go (or a new test)
func TestBashWriter_TmpFile_PathTraversal(t *testing.T) {
    w := &BashWriter{TemporaryPath: "/builds/project/tmp"}
    got := w.TmpFile("../../../etc/passwd")
    assert.True(t, strings.HasPrefix(got, w.TemporaryPath),
        "TmpFile escaped TemporaryPath: got %q", got)
}

func TestPsWriter_TmpFile_PathTraversal(t *testing.T) {
    p := &PsWriter{TemporaryPath: `C:\builds\project\tmp`}
    got := p.TmpFile(`..\..\..\Windows\System32\drivers\etc\hosts`)
    assert.True(t, strings.HasPrefix(got, p.TemporaryPath),
        "TmpFile escaped TemporaryPath: got %q", got)
}
```
A fuzz test over `variable.Key` values (`../..`, absolute paths, `..%2f..`, backslash sequences on Windows) feeding into `AbstractShell.writeCleanupScript` → `RmFile(w.TmpFile(key))` should assert the generated `rm -f`/`Remove-Item` argument always resolves under `TemporaryPath`. Before landing this as a confirmed vulnerability report, the PoC must also demonstrate that GitLab (or Runner) actually accepts and forwards such a `Key` value as a file-type variable end-to-end — this precondition remains unverified in this audit.
