### Title
Cost model's `allocated_accounts_data_size` estimate ignores CPI-based `CreateAccount`, allowing per-block accounts-data growth accounting to be silently under-counted - ([File: cost-model/src/cost_model.rs])

### Finding Description
`CostModel::calculate_allocated_accounts_data_size` (and its caller `calculate_transaction_cost`) only iterates `transaction.program_instructions_iter()`, i.e. the transaction's top-level instructions, and inspects only those whose `program_id` equals `system_program::id()` [1](#0-0) . The per-instruction allocation size is then summed and clamped to `MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION` and returned as `TransactionCost::allocated_accounts_data_size` [2](#0-1) . If an attacker's own BPF program is the sole top-level instruction and it CPIs `system_instruction::create_account` internally, the top-level `program_id` is the attacker's program (not the system program), so `calculate_account_data_size_on_instruction` returns `SystemProgramAccountAllocation::None` and the transaction's estimated `allocated_accounts_data_size` is `0`, even though the CPI actually grows an account's data by up to `space` bytes.

`CostTracker::would_fit`/`add_transaction_cost` use exactly this static, pre-execution field (`tx_cost.allocated_accounts_data_size()`) to enforce `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100 MB) against the running per-block total `self.allocated_accounts_data_size` [3](#0-2) ; there is no reconciliation step afterward that substitutes the real, post-execution accounts-data delta (`accounts_resize_delta`) into this per-block accounting - `calculate_cost_for_executed_transaction` also only re-derives cost from `transaction.program_instructions_iter()`, i.e. the same top-level-only view [4](#0-3) .

The comment in the code explicitly acknowledges this limitation for transactions containing custom BPF instructions ("it's tricky to know whether a newly allocated account will be freed... so we shouldn't assume...") [5](#0-4) , confirming this is a known, by-design approximation rather than a bank-hash-affecting bug: since the estimate is computed deterministically from the sanitized transaction's bytes (not from actual execution results), leader and any replaying/validating node compute the identical (under-)estimate, so there is no leader/validator *disagreement* as hypothesized in the question - both sides are equally blind to CPI-driven growth.

Separately, actual data growth is still bounded per transaction (not per block) by `TransactionAccounts::can_data_be_resized`, which enforces `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` (`= MAX_ACCOUNT_DATA_LEN * 2` = 20 MB) via the transaction-wide `resize_delta` counter regardless of CPI depth [6](#0-5)  and [7](#0-6) . This means each individual transaction's real growth is capped at 20 MB, but that hard cap is invisible to `CostTracker`'s block-level 100 MB budget when the growth happens via CPI.

### Impact Explanation
This is a compute/cost metering gap (`allocated_accounts_data_size` underestimation), matching the "compute/cost metering bypass" category. The concrete, scoped effect is that the `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` block-level safety budget - intended to bound how much real accounts-db growth a single block can cause - can be exceeded because CPI-driven `CreateAccount`/`Allocate` calls are never added to `CostTracker::allocated_accounts_data_size`. With enough transactions in a block each performing a CPI-based allocation (bounded individually to 20 MB by `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`, and in practice further limited by the block's CU budget, `MAX_BLOCK_UNITS`), the leader can pack a block whose true accounts-data growth is far larger than the 100 MB the cost tracker believes it admitted. This causes unbounded (up to CU-budget-limited) accounts-db growth beyond the resource-exhaustion guardrail the limit was designed to enforce. It is not, however, a bank-hash/consensus divergence bug, because both leader and validators derive the same (wrong) estimate deterministically from the transaction bytes rather than from execution results, so the originally hypothesized "leader vs. replaying-validator disagreement" does not occur.

### Likelihood Explanation
Fully reachable by an unprivileged attacker: deploy an owned SBF program, have it as the sole top-level instruction, and have it CPI `system_instruction::create_account`/`allocate` with large `space`; repeat across many transactions targeting the same leader's block. No special keys, config, or node privileges are required - only funding a keypair, deploying a program, and submitting transactions, all within the stated attacker capability. The main practical constraint is compute-unit cost of executing enough CPI calls within one block's `MAX_BLOCK_UNITS`, which throttles but does not eliminate the effect.

### Recommendation
Extend accounts-data-size cost accounting to cover inner instructions, not just `transaction.program_instructions_iter()` - either by including CPI-issued system-program instructions when they are statically inspectable at scheduling time (not fully possible pre-execution), or, more robustly, by re-deriving `allocated_accounts_data_size` from the *actual* post-execution `accounts_resize_delta` (already computed in `runtime/src/bank.rs::update_accounts_data_size_delta_on_chain`) and feeding that back into `CostTracker`'s running per-block total after each transaction executes, rather than relying solely on the static pre-execution estimate for block-fitting decisions.

fn test_cpi_create_account_not_counted_in_allocated_accounts_data_size() {

    // system program directly; the attacker's on-chain program is assumed
    // to internally CPI `system_instruction::create_account(space = 9_000_000)`.
    let attacker_program_id = Pubkey::new_unique();
    let transaction = Transaction::new_unsigned(Message::new(
        &[Instruction::new_with_bincode(
            attacker_program_id,
            &(),          // opaque instruction data for attacker's program
            vec![],
        )],
        Some(&Pubkey::new_unique()),
    ));
    let sanitized_tx = RuntimeTransaction::from_transaction_for_tests(transaction);

    // Cost model sees zero allocation, even though the program will actually
    // grow an account by ~9MB via CPI during execution.
    assert_eq!(
        CostModel::calculate_allocated_accounts_data_size(
            sanitized_tx.program_instructions_iter(),
            &FeatureSet::all_enabled()
        ),
        0
    );
    // Compare against a top-level `create_account` of the same size, which
    // *is* correctly counted:
    let top_level_tx = Transaction::new_unsigned(Message::new(
        &[system_instruction::create_account(
            &Pubkey::new_unique(),
            &Pubkey::new_unique(),
            1,
            9_000_000,
            &Pubkey::new_unique(),
        )],
        Some(&Pubkey::new_unique()),
    ));
    let sanitized_top_level = RuntimeTransaction::from_transaction_for_tests(top_level_tx);
    assert_eq!(
        CostModel::calculate_allocated_accounts_data_size(
            sanitized_top_level.program_instructions_iter(),
            &FeatureSet::all_enabled()
        ),
        9_000_000
    );
}

    /// eventually, potentially determine account data size of all writable accounts
    /// at the moment, calculate account data size of account creation
    fn calculate_allocated_accounts_data_size<'a>(
        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
        feature_set: &FeatureSet,
    ) -> u64 {
        let mut tx_attempted_allocation_size = Saturating(0u64);
        for (program_id, instruction) in instructions {
            match Self::calculate_account_data_size_on_instruction(
                program_id,
                instruction,
                feature_set,
            ) {
                SystemProgramAccountAllocation::Failed => {
                    // If any system program instructions can be statically
                    // determined to fail, no allocations will actually be
                    // persisted by the transaction. So return 0 here so that no
                    // account allocation budget is used for this failed
                    // transaction.
                    return 0;
                }
                SystemProgramAccountAllocation::None => continue,
                SystemProgramAccountAllocation::Some(ix_attempted_allocation_size) => {
                    tx_attempted_allocation_size += ix_attempted_allocation_size;
                }
            }
        }

        // The runtime prevents transactions from allocating too much account
        // data so clamp the attempted allocation size to the max amount.
        //
        // Note that if there are any custom bpf instructions in the transaction
        // it's tricky to know whether a newly allocated account will be freed
        // or not during an intermediate instruction in the transaction so we
        // shouldn't assume that a large sum of allocations will necessarily
        // lead to transaction failure.
        (MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION as u64)
            .min(tx_attempted_allocation_size.0)
    }

            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // check each account against account_cost_limit,
        for account_key in tx_cost.writable_accounts() {
            match self.cost_by_writable_accounts.get(account_key) {
                Some(chained_cost) => {
                    if chained_cost.saturating_add(cost) > self.limits.account_cost {
                        return Err(CostTrackerError::WouldExceedAccountMaxLimit);
                    } else {
                        continue;
                    }
                }
                None => continue,
            }
        }

        Ok(())
    }

    pub(crate) fn update_accounts_resize_delta(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        let accounts_resize_delta = self.resize_delta.get();
        self.resize_delta.set(
            accounts_resize_delta.saturating_add((new_len as i64).saturating_sub(old_len as i64)),
        );
        Ok(())
    }

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }
