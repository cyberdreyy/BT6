### Title
Unrestricted disclosure of full DKG result package via /vault/dkg_results/export to any authenticated session role - ([File: core/web/vault_controller.go])

### Summary
`VaultController.ExportDKGResult` performs no role check beyond generic session authentication before returning the complete hex-encoded `ReportWithResultPackage` for any `instanceId` supplied in the request body. The presenter `NewExportDKGResultResource` unconditionally embeds the full secret package and its SHA, with no redaction logic tied to the caller's role.

### Finding Description
`ExportDKGResult` decodes the request body for `instanceId`, looks up the DKG result via `vault.NewVaultORM(vc.App.GetDB()).ReadResultPackage`, and if found, hex-encodes the raw `v.ReportWithResultPackage` bytes and returns them via `presenters.NewExportDKGResultResource(hexPackage, shaStr)` [1](#0-0) . There is no capability, admin, or role check performed inside the handler itself — only whatever the router group applies generically to all `/v2/*` authenticated routes. The presenter itself has zero conditional redaction logic: it always sets `HexDKGResultPackage: hexResult` [2](#0-1) . Because `instanceId` is attacker-supplied and there is no ownership/ACL check tying the requesting session to the DKG instance, any session-authenticated caller who can guess or enumerate a valid `instanceId` and reach this route receives the raw secret-bearing package.

I was unable to fully verify, within the available tool budget, the exact role-requirement middleware wrapping this specific route in `v2Routes`/`router.go` (i.e., whether it is restricted to admin-only or accepts any authenticated role including view/run). The router-level registration for `/v2/vault/dkg_results/export` was not fully inspected before tool access ended, so I cannot conclusively confirm whether route-level role gating (e.g. `sessions.RequireRole`) already blocks view/run-role tokens before reaching the handler.

### Impact Explanation
If route-level role gating does not specifically restrict this endpoint to elevated roles, any authenticated user (including a minimal view/run role) can retrieve the complete DKG `ReportWithResultPackage` for any known or enumerated `instanceId`, potentially enabling recovery of oracle secret shares — a direct secret-disclosure impact matching Chainlink's key/secret disclosure bounty class.

### Likelihood Explanation
Exploitability depends entirely on the unresolved question of route-level role gating. If the route only requires generic session authentication (not an elevated/admin role), exploitation requires only a valid low-privilege session and a guessable/enumerable `instanceId`, making it trivially repeatable. If the router already restricts this route to an admin/run-privileged role via middleware, the described attack path does not apply.

### Recommendation
Explicitly require an elevated role for `/v2/vault/dkg_results/export` and `/v2/vault/dkg_results/verify` at the router registration in `core/web/router.go`, and additionally enforce that check inside `ExportDKGResult` itself (defense in depth) rather than relying solely on route-level middleware, given the sensitivity of the returned material.

### Proof of Concept
1. Add a handler-level Go test in `core/web/vault_controller_test.go` that constructs a test app/router with a session token assigned only the minimal (view/run) role.
2. Seed a DKG result package into the vault ORM for a known `instanceId`.
3. POST `/v2/vault/dkg_results/export` with `{"instanceId": "<known>"}` using the view/run-role session.
4. Assert the actual behavior: if response is 200 and body contains `hexDKGResultPackage` with full-length hex data, the endpoint is improperly exposed to low-privileged roles; if response is 401/403, the finding is not exploitable and role gating is already enforced upstream.

Given that the router-level role enforcement for this specific route could not be confirmed with the available context, this should be treated as **unconfirmed pending verification** of the `v2Routes`/vault route registration and its middleware in `core/web/router.go`.

```go
func (vc *VaultController) ExportDKGResult(c *gin.Context) {
	var req ExportDKGResultRequest
	err := json.NewDecoder(c.Request.Body).Decode(&req)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("could not parse request body"))
		return
	}

	if req.InstanceID == "" {
		jsonAPIError(c, http.StatusBadRequest, errors.New("instanceId is required"))
		return
	}

	orm := vault.NewVaultORM(vc.App.GetDB())
	v, err := orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	if v == nil {
		jsonAPIError(c, http.StatusNotFound, errors.New("DKG result not found"))
		return
	}

	hexPackage := hex.EncodeToString(v.ReportWithResultPackage)
	sha := sha256.Sum256(v.ReportWithResultPackage)
	shaStr := hex.EncodeToString(sha[:])
	jsonAPIResponse(c, presenters.NewExportDKGResultResource(hexPackage, shaStr), "exportDKGResult")
```
