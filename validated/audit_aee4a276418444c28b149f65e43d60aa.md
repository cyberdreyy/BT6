## Finding

### Title
Integer underflow in `rlp_list_element_length()` during untrusted MPT node decoding causes fault-proof program panic/DoS - (File: `crates/proof/mpt/src/util.rs`)

### Summary
`rlp_list_element_length()` in the `base-proof-mpt` crate subtracts an attacker-controlled RLP `payload_length` field from the remaining buffer length without first checking that the payload actually fits in the buffer, mirroring the exact bug class in `soup_multipart_new_from_message()` (CVE-2025-4948): an internal length calculation subtracts an untrusted/oversized length from a smaller buffer size, producing an integer underflow that leads to a crash.

### Finding Description
`rlp_list_element_length()` decodes an RLP header and then computes: [1](#0-0) 

```
let header = Header::decode(buf)?;
...
let len_after_consume = buf.len() - header.payload_length;
```

`Header::decode` only parses the RLP length-prefix bytes into `header.payload_length`; it does not verify that `payload_length` is less than or equal to the remaining bytes in `buf`. If a crafted MPT node preimage declares a `payload_length` larger than the actual remaining slice, `buf.len() - header.payload_length` underflows `usize`. In a build with overflow checks enabled this panics; without them it silently wraps to a value near `usize::MAX`, corrupting the subsequent element-walking loop.

This function is called from `TrieNode::decode`, the core decoder used to parse Merkle Patricia Trie node preimages throughout the fault-proof MPT crate: [2](#0-1) 

`TrieNode::decode` is reached whenever the fault-proof program (or any consumer of `base-proof-mpt`, e.g. `TrieNode::unblind` fetching preimages via `TrieProvider`) decodes a node preimage that is not fully trusted — this is precisely the "open untrusted node data during trie traversal" path a fault-proof program exercises when it walks L1/L2 state proofs supplied through the preimage oracle. A malformed/adversarial preimage — either injected by a malicious counterparty in a dispute game or corrupted L1 witness data — can trigger the underflow before any other validation catches the malformed length.

### Impact Explanation
A single malformed trie-node preimage reaching `TrieNode::decode`/`rlp_list_element_length` can panic the process (or corrupt the decode loop) inside the fault-proof program that computes the provable output root during dispute resolution. This can halt proof generation or dispute-game execution, denying service to the proving/dispute pipeline — directly matching the in-scope "node halt" / "wrong provable output root" categories, and structurally identical to the libsoup underflow-to-crash bug class cited in the report.

### Likelihood Explanation
The check is missing entirely (no `checked_sub` / no bound check on `header.payload_length` vs `buf.len()`), so any caller that feeds attacker-influenced or corrupted bytes into `TrieNode::decode`/`rlp_list_element_length` — such as during dispute-game trie traversal over externally supplied preimages — can trigger it with a single crafted node whose outer RLP list header declares a payload length exceeding the actual remaining bytes.

### Recommendation
In `rlp_list_element_length()`, validate `header.payload_length <= buf.len()` (returning an RLP decode error, e.g. `alloy_rlp::Error::InputTooShort`, instead of subtracting) before computing `len_after_consume`, mirroring the pattern already used defensively elsewhere in the codebase (e.g., `checked_add`/bounds checks in `crates/proof/tee/registrar/src/planner.rs` and `crates/consensus/protocol/src/deposits.rs`).

### Proof of Concept
Construct a byte buffer whose outer RLP header is a list header (`0xc0`-range prefix or long-form list prefix) declaring a `payload_length` value larger than the number of bytes actually following it (e.g., a long-form list header claiming length `0xFF` bytes while only supplying a few trailing bytes), and pass it to `TrieNode::decode(&mut bytes.as_slice())`. This reaches `rlp_list_element_length`, computing `buf.len() - header.payload_length` where `header.payload_length > buf.len()`, underflowing `usize` and panicking (debug/overflow-checked builds) or corrupting the subsequent loop bound (release builds). pub(crate) fn rlp_list_element_length(buf: &mut &[u8]) -> alloy_rlp::Result<usize> {
```rust
    let header = Header::decode(buf)?;
    if !header.list {
        return Err(alloy_rlp::Error::UnexpectedString);
    }
    let len_after_consume = buf.len() - header.payload_length;

    let mut list_element_length = 0;
    while buf.len() > len_after_consume {
        let header = Header::decode(buf)?;
        buf.advance(header.payload_length);
        list_element_length += 1;
    }
    Ok(list_element_length)
}
```

```rust
impl Decodable for TrieNode {
    /// Attempts to decode the [`TrieNode`].
    fn decode(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
        // Peek at the header to determine the type of Trie node we're currently decoding.
        let header = Header::decode(&mut (**buf).as_ref())?;

        if header.list {
            // Peek at the RLP stream to determine the number of elements in the list.
            let list_length = rlp_list_element_length(&mut (**buf).as_ref())?;

            match list_length {
                BRANCH_LIST_LENGTH => {
                    let list = Vec::<Self>::decode(buf)?;
                    Ok(Self::Branch { stack: list })
                }
                LEAF_OR_EXTENSION_LIST_LENGTH => {
                    // Advance the buffer to the start of the list payload.
                    buf.advance(header.length());
                    // Decode the leaf or extension node's raw payload.
                    Self::try_decode_leaf_or_extension_payload(buf)
                        .map_err(|_| alloy_rlp::Error::UnexpectedList)
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }
```
