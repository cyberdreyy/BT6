## Finding: Unsynchronized concurrent map access in `WorkflowMetadataHandler.Authorize` (gateway HTTP-trigger auth path)

### Title
Data race on `authorizedKeys` map between `Authorize` (unlocked read) and `syncMetadata` (locked write) can crash the Gateway or produce stale authorization decisions — ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler` protects `authorizedKeys`, `workflowRefToID`, `workflowIDToRef`, and `workflowShards` with `h.mu` everywhere *except* in `Authorize`, which is the function invoked on every inbound HTTP-trigger request from an external, unauthenticated caller.

### Finding Description
`Authorize` reads `h.authorizedKeys[workflowID]` directly, with no `h.mu.RLock()`: [1](#0-0) 

Every other accessor of the same struct fields takes `h.mu`:
- `syncMetadata` rebuilds and swaps `h.authorizedKeys` (and the other maps) under `h.mu.Lock()`: [2](#0-1) 
- `WorkflowShards` and `GetWorkflowID`/`GetWorkflowReference` correctly take `h.mu.RLock()`: [3](#0-2) [4](#0-3) 

`syncMetadata` runs on a periodic background ticker for the lifetime of the service (started in `Start`): [5](#0-4) [6](#0-5) 

`Authorize` is invoked from `http_trigger_handler.go` on the request path that handles inbound HTTP trigger calls; per the package README, HTTP triggers are "inbound requests that trigger workflow executions" authenticated via JWT, i.e. reachable directly from unprivileged external clients hitting the Gateway: [7](#0-6) 

Because `Authorize` reads `h.authorizedKeys` map without holding `h.mu`, while `syncMetadata` reassigns the same map field (`h.authorizedKeys = authorizedKeys`) under `h.mu.Lock()` roughly once per `MetadataAggregationIntervalMs` (default 1 minute), any concurrent inbound HTTP-trigger request that races with a sync cycle is a genuine Go data race: an unlocked map read concurrent with a locked map write/reassignment. This is precisely the same class of bug as the referenced Lighthouse commit — a shared, mutable counted/keyed state that requires a write-lock to read safely, where one code path skips locking.

### Impact Explanation
In Go, a map read racing with a write (even via variable reassignment, since the old map object may still be undergoing GC/finalization or be read stale) can trigger the Go runtime's `fatal error: concurrent map read and map write`, which is unrecoverable and crashes the entire node process — a remotely triggerable denial of service from any unauthenticated caller able to send HTTP trigger requests. Even absent a hard crash, the unlocked read introduces undefined behavior on the authorization decision (`keys, exists := h.authorizedKeys[workflowID]`), which could yield stale/incorrect membership results during a metadata swap, i.e. cross-request confusion in an authentication-critical map lookup.

### Likelihood Explanation
`syncMetadata` runs continuously on a fixed interval for the entire lifetime of the Gateway service, and `Authorize` is on the hot path for every single inbound HTTP-trigger request from external clients. No privileged access or special timing manipulation is required — an attacker only needs to send trigger requests continuously while the periodic sync ticks, which is a normal, always-occurring background operation. This makes the race highly likely to eventually be triggered under realistic production traffic.

### Recommendation
Acquire `h.mu.RLock()`/`RUnlock()` around the read of `h.authorizedKeys` in `Authorize`, consistent with `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`.

### Proof of Concept
Not applicable in ask-only mode (no execution environment available); however the root cause is directly evidenced by comparing `Authorize` (unlocked, lines 92-96) against `syncMetadata` (locked write of the same field, lines 164-178) in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`. A `go test -race` run exercising concurrent `Authorize` calls alongside a running `syncMetadata` ticker would reproduce the detected data race.

func (h *WorkflowMetadataHandler) runTicker(period time.Duration, fn func(ctx context.Context)) {
	h.wg.Go(func() {
		ctx, cancel := h.stopCh.NewCtx()
		defer cancel()
		ticker := time.NewTicker(period)
		defer ticker.Stop()
		for {
			select {
			case <-ticker.C:
				fn(ctx)
			case <-ctx.Done():
				return
			}
		}
	})
}

func (h *WorkflowMetadataHandler) GetWorkflowID(workflowOwner, workflowName, workflowTag string) (string, bool) {
	h.mu.RLock()
	defer h.mu.RUnlock()
	workflowRef := workflowReference{
		workflowOwner: workflowOwner,
		workflowName:  workflowName,
		workflowTag:   workflowTag,
	}
	workflowID, exists := h.workflowRefToID[workflowRef]
	if !exists {
		return "", false
	}
	return workflowID, true
}
