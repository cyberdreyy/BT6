### Title
Non-constant-time session token comparison enables timing side-channel token recovery - (File: `session/session.go`)

### Summary
`Session.withAuthorization` compares the secret session `Token` against the client-supplied `Authorization` header using Go's native string inequality operator (`s.Token != r.Header.Get("Authorization")`), which is not constant-time. An attacker who can reach a job's session endpoint (`/exec` or `/proxy/`) can in principle use per-byte timing differences to narrow the search space for another job's session token below its full entropy, and once recovered, attach to that job's interactive terminal or proxy.

### Finding Description
`session.NewSession` generates the token via `helpers.GenerateRandomUUID(32)` [1](#0-0)  and stores it on the `Session` struct [2](#0-1) . All requests to the session mux (`/proxy/` and `/exec`) are wrapped by `withAuthorization`, which performs the comparison:

```go
if s.Token != r.Header.Get("Authorization") {
``` [3](#0-2) 

Go's `!=` on strings lowers to a length check followed by a byte/word-wise memory comparison that returns as soon as a mismatch is found (`runtime.memequal`/`cmpstring`), so requests whose header matches a longer correct prefix of the token take marginally longer to reject than requests that mismatch early. There is no use of `crypto/subtle.ConstantTimeCompare` or an HMAC-based check, and there is no rate limiting or lockout at this layer — every failed attempt just returns `401 Unauthorized` from `http.Error` immediately after the comparison, with no artificial delay or attempt counting [4](#0-3) . The comparison is the only gate protecting `execHandler` (interactive terminal attach) and `proxyHandler` (proxied access to build services) [5](#0-4) .

### Impact Explanation
If timing differences are statistically distinguishable over the attacker's vantage point (same host/LAN as the runner's session server, per the stated precondition), a successful byte-by-byte recovery of `Token` would let the attacker forge the `Authorization` header for a session they don't own and hijack another concurrently running job's interactive terminal (`/exec`) or its service proxy (`/proxy/`), matching the "cross-job session/terminal hijack" scoped impact.

### Likelihood Explanation
Exploitability hinges entirely on whether the timing signal is measurable through real-world network/OS jitter for a 64-hex-character (256-bit) secret, which is a strict precondition already stated in the question (attacker network-adjacent to `SessionServer.AdvertiseAddress`, able to send many repeated requests). No additional mitigating control exists in this code path (no constant-time compare, no rate limiting, no delay), so if the timing channel is measurable at all, nothing else in `withAuthorization` prevents incremental token recovery. Feasibility over a real network remains a strong practical constraint (comparison cost differences are on the order of nanoseconds vs. typical network RTT jitter of microseconds-to-milliseconds), but the code itself provides no defense-in-depth against this class of attack.

### Recommendation
Replace the direct string comparison with a constant-time comparison, e.g.:
```go
tokensEqual := subtle.ConstantTimeCompare([]byte(s.Token), []byte(r.Header.Get("Authorization"))) == 1
if !tokensEqual {
    ...
}
```
Also consider adding basic rate limiting/backoff on failed authorization attempts to the session server to defend against both timing and brute-force attacks.

### Proof of Concept
Go statistical timing fuzz test:
1. Start a `Session` with a known `Token`.
2. Issue N requests with `Authorization` headers that share an increasing correct prefix length with `Token` (e.g., 0, 16, 32, 48, 63 correct leading hex chars, rest random) directly to `withAuthorization`-wrapped handler (bypass the network to isolate CPU-level effect, then repeat over loopback HTTP to include network overhead).
3. Measure response latency distributions (median of ≥10k samples per prefix length) for each prefix length.
4. Assert whether latency correlates with prefix length (e.g., via linear regression or Welch's t-test) with `p < 0.01`; if no statistically significant correlation is found in the network-facing test even though correlation may exist in the pure in-process comparison benchmark, this demonstrates the code-level defect exists but is masked by network noise in this test setup — the fix (`subtle.ConstantTimeCompare`) should still be applied to remove the underlying defect regardless of the measured exploitability threshold.

func (s *Session) withAuthorization(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		logger := s.log.WithField("uri", r.RequestURI)
		logger.Debug("Endpoint session request")

		if s.Token != r.Header.Get("Authorization") {
			logger.Error("Authorization header is not valid")
			http.Error(w, http.StatusText(http.StatusUnauthorized), http.StatusUnauthorized)
			return
		}

		next.ServeHTTP(w, r)
	})
}
```
