### Title
Cross-user response delivery via unscoped `savedCallbacks[msg.Body.MessageId]` map in gateway legacy WebAPI trigger handler - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each pending user callback in `h.savedCallbacks` keyed solely by the attacker-controlled `msg.Body.MessageId`, without binding the entry to the signer/sender address. Any unauthenticated client can sign a `web_api_trigger` message with an arbitrary `MessageId` and its own keypair; if that `MessageId` collides with another in-flight request (from any other signer), the second write silently overwrites the first callback in the map, and `handleWebAPITriggerMessage` later delivers whichever node response arrives to whatever callback currently occupies that map slot — with no verification that the response corresponds to the original requester's signed payload.

### Finding Description
The legacy gateway path is reachable by anyone able to POST a signed JSON-RPC request to the gateway (`ProcessRequest` → `HandleLegacyUserMessage`), since `msg.Validate()` at [1](#0-0)  only checks signature well-formedness and recovers `Sender` from an arbitrary ECDSA signature — it does not check any allowlist. The code even flags this explicitly: `// TODO: apply allowlist and rate-limiting here` at [2](#0-1) . Thus any keypair can produce a valid, arbitrary-`MessageId` trigger message.

The callback is stored keyed purely by `MessageId`: [3](#0-2) 
There is no association with `msg.Body.Sender` or with the specific `req` bytes sent to nodes.

When a node responds, the lookup/delete/dispatch is also purely by `MessageId`, with no cross-check against the original sender or request content: [4](#0-3) 

Because `MessageId` is fully attacker-controlled (bounded only by length checks in `Validate`, [5](#0-4) ), two concurrent legacy requests from two different signers using the same `MessageId` will race on the map write. The last writer's callback occupies the slot. Any subsequent `HandleNodeMessage`→`handleWebAPITriggerMessage` call for that `MessageId` — regardless of which original request it was actually answering — delivers its `RawResponse` to whatever callback is currently stored, and deletes the entry. This causes:
1. **Response misdelivery**: the victim's node-computed response can be routed to the attacker's callback.
2. **DoS by overwrite**: the victim's original callback reference is lost, so `callback.Wait(ctx)` in `gateway.ProcessRequest` (`core/services/gateway/gateway.go:278`) will time out, producing a request-timeout error for the legitimate caller even though their request was processed by the DON.

No signature/sender check exists anywhere in this dispatch path to prevent it.

### Impact Explanation
This breaks per-request isolation guarantees of the gateway: a request meant for one caller can be delivered to a different, unrelated caller, and/or the legitimate caller can be denied their response (DoS). This maps to Chainlink's "unauthorized access to another user's data/response" and "denial of service via request/response confusion" bounty impact classes. The severity is bounded by the fact that the attacker cannot choose the response content, and by resource limits (`MaxSavedCallbacks`, `CallbackMaxAgeSec`), but the mechanism itself constitutes a genuine isolation-boundary violation reachable without credentials.

### Likelihood Explanation
Precondition is only the ability to generate an ECDSA keypair and sign a message (`msg.Sign`), no allowlist or authenticated session is enforced before `HandleLegacyUserMessage` is reached. Exploitation additionally requires the attacker to guess/observe another concurrent caller's `MessageId` and win a timing race against that caller's in-flight request and the DON's response — this narrows real-world exploitability against a specific victim (since `MessageId` values are typically caller-chosen/random), but the underlying isolation defect is deterministic and trivially demonstrable in a two-goroutine test as described in the question.

### Recommendation
Scope `savedCallbacks` entries by `(sender, MessageId)` (or a server-generated unique correlation key independent of client input) instead of `MessageId` alone, and verify in `handleWebAPITriggerMessage`/`HandleNodeMessage` that the responding node's message sender/payload actually corresponds to the stored callback's original request (e.g., store and compare the original `Sender` and/or a hash of the outbound `req` alongside the callback), rejecting or logging mismatches instead of blindly overwriting/dispatching by `MessageId`.

### Proof of Concept
Go test plan (extends `handler_test.go`):
1. Build two signed `triggerRequest` messages with identical `MessageId` ("dup-id") but signed by two different `*ecdsa.PrivateKey` (attacker vs. victim), each with distinct payload content that is easily distinguishable in the response.
2. Concurrently (two goroutines) call `handler.HandleLegacyUserMessage(ctx, msgAttacker, cbAttacker)` and `handler.HandleLegacyUserMessage(ctx, msgVictim, cbVictim)`.
3. Assert (via lock/inspection or deterministic ordering with a small sleep) that `h.savedCallbacks["dup-id"]` now only contains one of the two callbacks (last-writer-wins), proving the overwrite.
4. Simulate node responses for both original requests via `handler.HandleNodeMessage(ctx, respForVictimNode, victimNodeAddr)` and `handler.HandleNodeMessage(ctx, respForAttackerNode, attackerNodeAddr)`.
5. Assert that `cbAttacker.Wait(ctx)` and/or `cbVictim.Wait(ctx)` receive a response that does not correspond to their own original signed request (cross-delivery), or that one of the two callbacks never receives a response at all (times out), demonstrating both the response-misdelivery and DoS-by-overwrite outcomes.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
