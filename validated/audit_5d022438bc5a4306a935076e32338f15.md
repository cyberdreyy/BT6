### Title
Loss-adjusted withdraw receipts for older epochs are silently upgraded to par payment when a user accumulates requests across two loss epochs - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks a user's withdraw-request epoch only through the single scalar `lastWithdrawRequest[_user]`. When a stop-epoch loss is realized, `collectWithdrawFunds` stores a per-epoch haircut in `lossRecoveryPriceByEpoch[epochNumber]`, but the claim path only ever consults `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (`_claimLossAdjustedWithdrawRequest`, `IdleCreditVault.sol:789-801`). If a user holds receipts from two different loss epochs, the older receipt is never settled through its haircut price: `_clearWithdrawClaimForEpoch` clears only the latest epoch and resets `lastWithdrawRequest` to 0 (`IdleCreditVault.sol:832-836`), after which the stale per-epoch balance remains inside `withdrawsRequests[_user]` and is paid in full at par by `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:338-349`). The comment at `IdleCreditVault.sol:833-835` explicitly assumes "any remaining receipt is older and already funded," which is false when the older epoch was itself loss-adjusted.

This is the same bug class as the TrufVesting report: the claimable/claim-settlement logic fails to account for how much of a receipt was already (or should be) haircut, letting a claimant extract more than their entitlement.

### Finding Description
Sequence:

1. Attacker deposits into the AA or BB tranche of an `IdleCDOEpochVariant` / `IdleCDOCreditVault` and calls `requestWithdraw` during the buffer of epoch N. The strategy records `withdrawsRequests[user] += amount` and `withdrawsRequestsByEpoch[user][N] += amount` and sets `lastWithdrawRequest[user] = N` (`IdleCreditVault.sol:282-294`).
2. The epoch ends with a partial borrower repayment: the manager calls `stopEpochWithDuration` / the CDO calls `collectWithdrawFunds(amount < pendingBasis)`, which sets `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL` and zeroes `pendingWithdraws` (`IdleCreditVault.sol:414-421`). The attacker's epoch-N receipt is now only worth `claimBasis * lossRecoveryPrice[N]`.
3. The attacker does **not** claim. In a later epoch M they call `requestWithdraw` again; `lastWithdrawRequest[user]` is overwritten to M and the new amount is added to the same aggregate `withdrawsRequests[user]`.
4. Epoch M also ends with a loss (`lossRecoveryPriceByEpoch[M]` set).
5. The attacker calls `claimWithdrawRequest` once. `_claimLossAdjustedWithdrawRequest` uses `lossEpoch = lastWithdrawRequest[user] = M`, clears only epoch M via `_clearWithdrawClaimForEpoch`, applies the M haircut, and resets `lastWithdrawRequest` to 0. It never looks at `lossRecoveryPriceByEpoch[N]`.
6. Execution continues into `_claimFundedWithdrawRequest`, which computes `normalAmount = withdrawsRequests[user]` — still containing the epoch-N receipt — and pays it at par through `_transferFundedClaim`, burning the corresponding strategy-token receipt.

The epoch-N receipt's haircut is therefore never enforced: `lossRecoveryPriceByEpoch[N]` stays set but unreachable because `lastWithdrawRequest` no longer points to N. There is no guard that forces settlement of all outstanding loss-adjusted epochs before paying the aggregate at par.

### Impact Explanation
Direct overpayment / insolvency. The attacker receives `claimBasis_N` instead of `claimBasis_N * lossRecoveryPrice_N / RECOVERY_FULL`, i.e. steals `claimBasis_N * (1 - lossRecoveryPrice_N)` of funded underlying. The loss that `collectWithdrawFunds` intended to socialize across epoch-N pending receipts is instead fully paid to the attacker out of the strategy's funded-claim balance, reducing what remains for other users' funded claims and post-default reserve. Loss equals the un-applied haircut on the stale epoch receipt; with a 50% recovery price and a large epoch-N request the attacker roughly doubles that receipt's payout.

### Likelihood Explanation
Requires two epochs that each end in a realized loss (`stopEpochWithDuration`/`collectWithdrawFunds` with `_amount < pendingBasis`) with the same user holding unclaimed requests in both. Loss epochs are honest-manager actions, so the attacker cannot force them, but nothing prevents a requester from simply not claiming between two such epochs — the code comments even note that delaying claims is expected behavior. Once the condition exists, the overpayment is deterministic and repeatable for every user in that position. Likelihood is moderate-low but the accounting flaw is unconditional once triggered.

### Recommendation
Track loss-adjusted claims per epoch rather than relying on the single `lastWithdrawRequest` marker, or iterate/settle all epochs with a non-zero `lossRecoveryPriceByEpoch` for the user before falling through to `_claimFundedWithdrawRequest`. Concretely, `_claimFundedWithdrawRequest` should exclude (or first settle at their recovery price) any `withdrawsRequestsByEpoch[user][e]` where `lossRecoveryPriceByEpoch[e] != 0`, instead of paying the whole `withdrawsRequests[user]` aggregate at par.

### Proof of Concept
Foundry fork PoC sketch (setup mirrors `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testDoubleLossEpochPaidAtPar() external {
    // 1. Deposit, then requestWithdraw during buffer of epoch N
    uint256 req1 = cdoEpoch.requestWithdraw(trancheBal / 2, address(AAtranche));

    // 2. Manager stops epoch N with partial funding: lossRecoveryPrice[N] = 50%
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(_lossAmount); // borrower repays half of pendingWithdraws
    assertEq(strategy.lossRecoveryPriceByEpoch(N), RECOVERY_FULL / 2);

    // 3. User does NOT claim; requests again in epoch M
    _startEpochAndCheckPrices(M - 1);
    uint256 req2 = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // 4. Epoch M also ends in a loss
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(_lossAmount2);

    // 5. Single claim
    uint256 balPre = underlying.balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(user) - balPre;

    // BUG: epoch-N receipt paid at par instead of at lossRecoveryPriceByEpoch[N]
    uint256 expected = req1 * RECOVERY_FULL / 2 / RECOVERY_FULL
                     + req2 * strategy.lossRecoveryPriceByEpoch(M) / RECOVERY_FULL;
    assertGt(paid, expected); // paid includes req1 un-haircut
}
```

Note on verification limits: I confirmed the state transitions and claim-path logic from `IdleCreditVault.sol` lines 271–430 and 721–900, but I could not fully trace the `IdleCDOEpochVariant.stopEpochWithDuration`/`requestWithdraw` wrappers to confirm no additional guard prevents requesting while an older loss-adjusted receipt is unclaimed. If such a guard exists on the CDO side, the finding's reachability would be reduced; the stale-`lastWithdrawRequest` design itself is still the weak point.
