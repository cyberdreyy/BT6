### Title
Miner-side signer coordinator never retracts stale rejection weight when a signer flips a Reject to an Accept for the same block, permanently corrupting the rejection tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`stackerdb_listener.rs` tracks `BlockStatus::total_weight_approved` and `total_weight_rejected` as independent, monotonically-increasing accumulators, exactly like the reported `ValidatorManager` pattern that only ever adds and never subtracts. A signer is explicitly allowed by the protocol to change its verdict on the same block (`LocallyRejected --> LocallyAccepted : re-evaluated`, per the documented `BlockState` machine), but the listener has no path to undo a previously-tallied rejection weight when that signer subsequently accepts. The rejection bucket is therefore permanently "stuck," analogous to the Oracle case where a decrease is silently ignored and only upticks are recorded.

### Finding Description
`BlockStatus` holds two independently accumulated weights: [1](#0-0) 

On `SignerMessageV0::BlockResponse(BlockResponse::Accepted(..))`, weight is added to `total_weight_approved` keyed off `gathered_signatures` membership, and `responded_signers.insert(slot_id)` is called unconditionally (regardless of what bucket the signer was already counted in): [2](#0-1) 

On `SignerMessageV0::BlockResponse(BlockResponse::Rejected(..))`, weight is added to `total_weight_rejected` only when `responded_signers.insert(slot_id)` returns `true` (i.e., first response ever from that slot for this block): [3](#0-2) 

This produces an asymmetry:
- Accept → Reject (same signer, same block): the later `Rejected` message finds `responded_signers` already containing the slot, so `total_weight_rejected` is **not** incremented — the stale rejection is silently dropped, and the accepted weight also never gets removed even though the signer changed its mind toward rejection.
- Reject → Accept (same signer, same block): the later `Accepted` message only checks `gathered_signatures.contains_key(&slot_id)` (false, since this is the first accept), so `total_weight_approved` **is** incremented. Meanwhile `total_weight_rejected`, already incremented by the earlier reject, is never decremented.

In both directions the earlier vote's contribution to its bucket is never retracted; only the later vote's target bucket can be updated on top of it. This is the same bug class as the Oracle report: decreases (vote retractions) are not accounted for in `reportRewardEvent`/`reportSlashingEvent`'s analog here — the miner-side "reject" and "approve" accumulators — so the `ValidatorManager`-equivalent state (the coordinator's weight tally used to decide the block's fate) permanently diverges from the true, current state of signer opinions.

This tally is consumed directly by `signer_coordinator.rs`'s decision loop, which finalizes a block as globally rejected once `total_weight_rejected + weight_threshold > total_weight`: [4](#0-3) 

Because `total_weight_rejected` can never shrink, weight from signers who legitimately re-evaluated a stale/transient rejection (a scenario the signer state machine explicitly supports — see `LocallyRejected --> LocallyAccepted : re-evaluated`) permanently remains counted against the block, even after every signer currently supports it.

### Impact Explanation
This is a liveness wedge on block production, not a majority-controlled attack: any single signer that legitimately reconsiders (transient chain-state mismatch, a delayed `NewBlock` observation, etc., all cases the protocol's own re-evaluation logic is designed to handle) contributes weight to `total_weight_rejected` that can never be retracted. If enough such transient rejections accumulate across the tenure's retries — even from signers who have since switched to accepting — the blocking-minority threshold (`total_weight - weight_threshold`) can be crossed purely from stale weight, causing the coordinator to declare `SignersRejected` and abandon the block even though the live, current signer opinions would clear the 70% acceptance threshold. This matches the "wedged into never signing/accepting valid blocks" class of High-impact liveness issues: block production for the tenure can stall on a block that the signer set, as of the present moment, actually supports.

### Likelihood Explanation
No majority collusion or key compromise is required — a single signer naturally re-evaluating its own vote (a first-class, documented behavior of the state machine) is sufficient to trigger the asymmetric accumulation. Because the coordinator's rejection threshold check runs on every message and only needs cumulative stale rejection weight (from any subset of signers over the lifetime of the proposal, including retries) to cross the 30% blocking-minority line, this is readily reachable in ordinary network conditions (message reordering, retries after `check_burn_tip_changed`, or a signer re-validating a block after a delayed catch-up) without any adversarial majority.

### Recommendation
Track only the *current* vote per slot instead of two independently-accumulating buckets: store `responded_signers` as a map from slot_id to its latest verdict (Accepted or Rejected) with weight, and recompute `total_weight_approved`/`total_weight_rejected` by summing over the current verdict map whenever a message updates it (removing the old contribution before adding the new one), mirroring how the signer-side `store_and_process_block_signature`/`store_and_process_block_rejection` in `stacks-signer/src/v0/signer.rs` recompute weight fresh from the DB-stored signature/rejection set on every event rather than incrementally accumulating.

### Proof of Concept
1. Node proposes block B (`signer_signature_hash = H`) to the signer set via the coordinator/listener.
2. Signer S evaluates B, temporarily fails `check_block_against_signer_db_state` (e.g., due to a brief node-tip lag), and broadcasts `BlockResponse::Rejected` for H. `stackerdb_listener` records `responded_signers.insert(S)=true` and `total_weight_rejected += weight(S)`.
3. Node's local chain view catches up; S's own re-evaluation logic (`should_reevaluate_block`/`LocallyRejected -> LocallyAccepted`) flips S's local verdict, and S broadcasts `BlockResponse::Accepted` for the same H.
4. `stackerdb_listener` sees `gathered_signatures` does not yet contain S's slot, so it adds `weight(S)` to `total_weight_approved` as well — but `total_weight_rejected` still retains `weight(S)` from step 2, unremoved.
5. Repeat with additional signers whose transient rejections are superseded by later acceptances (plausible during any tenure/chain-tip flap). Once accumulated stale `total_weight_rejected` crosses `total_weight - weight_threshold`, the coordinator (`signer_coordinator.rs` L509-540) declares the block `SignersRejected` and aborts, even though every signer currently holds an `Accepted` verdict for H — a liveness wedge that forces the miner to abandon a block the live signer set actually supports.
