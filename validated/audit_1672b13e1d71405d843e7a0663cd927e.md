## Analysis

The bug-class from H‑1 (Ajna) is that an on‑the‑fly accounting value used to gate a reward/threshold can be updated by one side of a transition (take) but not symmetrically cleaned up on the other, so weight/credit accumulates inconsistently across a sequence of small actions instead of reflecting the current, true state. The reachable analog in stacks-core is in the node-side signer response tally, `StackerDBListener`.

`stacks-node/src/nakamoto_node/stackerdb_listener.rs` maintains, per proposed block, a `BlockStatus { gathered_signatures: BTreeMap<u32, MessageSignature>, responded_signers: HashSet<u32>, total_weight_approved, total_weight_rejected, .. }` [1](#0-0) .

For an `Accepted` response, the dedup gate that decides whether to add the signer's weight to `total_weight_approved` is `!block.gathered_signatures.contains_key(&slot_id)` [2](#0-1) .

For a `Rejected` response, the dedup gate that decides whether to add the signer's weight to `total_weight_rejected` is `block.responded_signers.insert(slot_id)` [3](#0-2) .

These two gates use different sets. If a signer first sends `Rejected` (populates `responded_signers`, adds weight to `total_weight_rejected`, but never touches `gathered_signatures`) and later sends `Accepted` for the same block, the accept-side check `!gathered_signatures.contains_key(&slot_id)` is still true, so the signer's weight is added a second time to `total_weight_approved`, while the stale weight in `total_weight_rejected` is never removed. The reverse order (`Accepted` then `Rejected`) is correctly guarded, because the reject gate checks `responded_signers`, which was already populated by the earlier accept — but the accept path's independent gate makes the reject→accept direction exploitable. This is a single-signer-triggerable inconsistency (one slot's own two messages via StackerDB gossip), not requiring a majority. [4](#0-3) 

### Title
Stale rejection weight is never cleared when a signer flips to Accept, letting one signer's weight be counted in both `total_weight_approved` and `total_weight_rejected` - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener::poll` tallies `BlockResponse::Accepted`/`Rejected` messages into `BlockStatus.total_weight_approved`/`total_weight_rejected` using two different dedup keys: `gathered_signatures` for accepts and `responded_signers` for rejects. A signer that first rejects and later accepts the same block has its weight counted into `total_weight_rejected` (from the reject) and then a second time into `total_weight_approved` (from the accept), because the accept-path gate never checks `responded_signers`/rejection history.

### Finding Description
`handle_signer_message`'s `BlockResponse::Accepted` arm adds `signer_entry.weight` to `block.total_weight_approved` guarded only by `!block.gathered_signatures.contains_key(&slot_id)` [5](#0-4) . Its `BlockResponse::Rejected` arm adds weight to `block.total_weight_rejected` guarded by `block.responded_signers.insert(slot_id)` [3](#0-2) . Both arms insert the slot into `responded_signers` unconditionally elsewhere (accept path line 465), but the accept path's counting decision never consults `responded_signers`, and neither path removes a previously counted weight from the opposite tally when a signer's vote changes.

Sequence exploitable by a single signer (one StackerDB slot):
1. Signer S (slot `k`, weight `w`) sends `Rejected` for block X → `responded_signers.insert(k)` succeeds → `total_weight_rejected += w`.
2. Signer S later sends a validly-signed `Accepted` for the same block X → `gathered_signatures.contains_key(k)` is false (never touched by the reject path) → `total_weight_approved += w` as well.
3. `total_weight_rejected` still contains `w` from step 1; it is never decremented. Both tallies now include the same signer's weight simultaneously, so `total_weight_approved + total_weight_rejected` can exceed the true weight held by distinct opinions, and neither tally accurately reflects "verified accepts" vs "verified rejects" at the current moment.

This breaks the intended equality that a signer's weight should count toward at most one side of the tally at any time — i.e., the aggregated-weight tallies no longer match the set of currently-held (non-stale) verified responses. This is functionally a rejection being retained/recounted alongside a later accept, rather than being superseded by it.

### Impact Explanation
The coordinator (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) uses these same tallies to decide outcomes: `total_weight_rejected.saturating_add(weight_threshold) > total_weight` triggers `NakamotoNodeError::SignersRejected` (excluding txids, tenure_extend, etc.), while `total_weight_approved >= weight_threshold` signals the block is signed [6](#0-5) [7](#0-6) . Because a stale rejection weight from a signer who has since accepted is never cleared, a block can be pushed toward the rejection branch (temporarily/permanently excluding transactions, or causing the coordinator to treat the round as blocked) using padded weight that no longer represents a live rejection — this is a liveness impact on the coordinator's decision logic, driven purely by an accounting inconsistency reachable by any single signer flipping its own vote.

### Likelihood Explanation
Triggerable by any single signer sending two legitimately-signed StackerDB messages (`Rejected` then `Accepted`) for the same block — no majority, no other signer's key, and no node/auth bypass required. Signers are expected to be able to re-evaluate and change their response for a block (the codebase's own re-evaluation logic, e.g. `should_reevaluate_reject_reason`, explicitly allows reconsideration for several reject reasons) [8](#0-7) , so a reject→accept sequence for the same block hash is a normal, expected occurrence, not a contrived edge case.

### Recommendation
Use a single per-signer vote record (e.g., a `HashMap<u32, VoteKind>` or reuse `responded_signers` consistently for both paths) that stores the signer's current vote and, on a vote change, subtracts the previously counted weight from the old tally before adding it to the new one, so `total_weight_approved` and `total_weight_rejected` never simultaneously include the same signer's weight.

### Proof of Concept
In `StackerDBListener`'s message loop:
1. Send `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for `block_sighash` from slot `k` (weight `w`) → observe `block.total_weight_rejected` increases by `w`, `responded_signers` contains `k`.
2. Send `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same `block_sighash` from the same slot `k`, with a valid signature → observe `block.total_weight_approved` also increases by `w` (because `gathered_signatures` did not contain `k`), while `block.total_weight_rejected` remains unchanged, i.e. still includes the stale `w` from step 1.
3. Assert `block.total_weight_approved + block.total_weight_rejected > self.total_weight` when only one signer of weight `w` responded, proving the same weight is double-counted across the two tallies.
