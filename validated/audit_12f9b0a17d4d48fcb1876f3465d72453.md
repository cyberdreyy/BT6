### Title
Malicious miner can indefinitely extend its own "activity" via invalid re-proposals, preventing signers from ever timing out an unresponsive/malicious tenure - (File: stacks-signer/src/chainstate/mod.rs)

### Summary
`SortitionData::check_tenure_change_confirms_parent` (and the sibling non-tenure-change path) records "miner activity" via `signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())` whenever a miner submits a block proposal that does not advance the tenure's tip far enough, as long as the tenure hasn't yet reached a fresh `signed_group` timestamp within `reorg_attempts_activity_timeout`. This activity timestamp feeds `check_miner_inactivity` / `is_timed_out` (v1/v2), which is the sole gate that lets the signer set fall back to a prior/competing tenure when the current miner goes idle. [1](#0-0) 

### Finding Description
A miner (one slot, one crafted proposal stream, no majority of signers required) can repeatedly submit non-advancing or otherwise "provably-not-higher" block proposals for its own tenure's `consensus_hash`. Each such submission is treated as legitimate miner activity and resets `last_activity_time` for that consensus hash, so long as the tenure has not already produced a `signed_group`-timestamped block outside the `reorg_attempts_activity_timeout` window: [2](#0-1) 

Because `check_miner_inactivity`/`is_timed_out` (documented in `docs/signer-flows.md` as measuring "time since the last activity... against `block_proposal_timeout`") is the only mechanism by which the signer set considers the current miner dead and falls back to a prior tenure, an attacker-controlled miner that never intends to produce a genuinely valid, advancing block can nonetheless keep resetting this clock by spamming cheap, invalid or stale re-proposals. This blocks the `MinerSet`/coordinator from ever timing out to allow a legitimate successor miner's tenure, since `has_signed_block_in_tenure` doesn't need to be true — only the activity timer needs to keep getting bumped. [3](#0-2) 

### Impact Explanation
This maps to the accepted "High" impact category: a signer wedged (via a stuck/never-timing-out miner-inactivity check) into never accepting a valid successor block, i.e., a liveness wedge triggerable by a single miner with only StackerDB gossip access, no signer keys or majority required.

### Likelihood Explanation
Moderate-to-uncertain. I was able to verify the call site and its guarding condition directly, but I could **not** verify (due to running out of tool calls) whether `is_timed_out`/`check_miner_inactivity` in `stacks-signer/src/signerdb.rs` and `chainstate/v1.rs`/`v2.rs` impose any additional validity requirement on the proposal that generated the activity bump (e.g., requiring it to at least pass static/tenure checks), which could already mitigate this. The comment at the call site suggests this is an intentional design tradeoff ("miner may just be slow, so count this invalid block proposal towards valid miner activity") rather than an oversight, which weakens confidence that this is a genuine, unmitigated vulnerability versus accepted behavior.

### Recommendation
Have a Devin session verify, with full access to `stacks-signer/src/signerdb.rs::is_timed_out`/`update_last_activity_time` and `chainstate/v1.rs`/`v2.rs::is_timed_out`, whether activity credit is granted for proposals that fail proposal-time static/tenure validity checks (not just height checks), and if so, gate `update_last_activity_time` on the proposal at least passing `check_block_against_state`'s static/consensus checks before crediting it as liveness activity.

### Proof of Concept
Not independently confirmed end-to-end due to incomplete visibility into `is_timed_out`'s exact formula; would need a Devin session with full read access to `stacks-signer/src/signerdb.rs` to construct a concrete repro (a malicious miner tenure that repeatedly proposes a non-advancing/duplicate block at a fixed height, observing that `check_miner_inactivity` never fires and a competing valid tenure is never adopted).
