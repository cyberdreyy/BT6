### Title
Signer weight double-counted across accept and reject tallies when a signer's response flips for the same block — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side vote tally in `stackerdb_listener.rs` dedups a signer's `Accepted` weight against `gathered_signatures` but dedups `Rejected` weight against a *shared* `responded_signers` set that both branches touch. This asymmetry means a signer that broadcasts `Rejected` for a block hash first and later broadcasts `Accepted` for the *same* block hash has its weight counted into **both** `total_weight_approved` and `total_weight_rejected`, breaking the invariant that a signer's weight should only ever back one verdict per block. This mirrors the audited "irreversible action executed before all invariant-preserving steps complete" bug class from the external report (there: lamport transfer before CPI completion breaks atomicity; here: an accept is tallied without checking whether that same signer already banked a reject for the identical hash).

### Finding Description
In `stackerdb_listener.rs`'s per-message handling loop:
- For `BlockAccepted`, the weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`, and then `block.responded_signers.insert(slot_id)` is called unconditionally afterward. [1](#0-0) 
- For `BlockResponse::Rejected`, the weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., it wasn't already present). [2](#0-1) 

If `Rejected` arrives first for a slot, `responded_signers` gains that slot and its weight is added to `total_weight_rejected`. If `Accepted` arrives afterward for the *same block hash*, the check performed is against `gathered_signatures` (empty for that slot, since it never signed an accept), so the weight is *also* added to `total_weight_approved`, and only then is `responded_signers` touched again (a no-op insert). The reverse ordering (accept-then-reject) is correctly guarded because the reject branch's dedup set already contains the slot from the accept branch — but the accept branch has no corresponding check against a prior reject.

A legitimate, non-malicious path to trigger the reject→accept sequence for one signature hash exists on the signer side. In `stacks-signer/src/v0/signer.rs`, `check_submitted_block_proposal` marks the block locally rejected and calls `send_block_response` (broadcasting the rejection over StackerDB) *before* persisting that state via `self.signer_db.insert_block(&block_info)`. [3](#0-2) 
If the signer process restarts between the broadcast and the DB write (crash, OOM kill, panic elsewhere in the same tick), its local view no longer reflects that this block was rejected (`valid` stays `None`), so on the next proposal/validation cycle it can independently validate and legitimately sign the very same block hash, broadcasting `Accepted` afterward — a second, later message for a hash it already told the network it rejected. All other analogous paths in `signer.rs` write to `signer_db` before broadcasting (e.g. `handle_block_validate_ok`, `handle_block_validate_reject`, `store_and_process_block_signature`), explicitly commented "have to save … after the block info" — `check_submitted_block_proposal` is the one place that inverts this order. [4](#0-3) [5](#0-4) 

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality the coordinator relies on: `signer_coordinator.rs` decides acceptance once `total_weight_approved >= weight_threshold` and rejection once `total_weight_rejected` makes the threshold unreachable. [6](#0-5) 
Double-counting one signer's weight into `total_weight_approved` after it was already counted in `total_weight_rejected` (or vice versa, if the ordering were reversed) lets the sum of "votes" exceed the real weight held by responding signers, letting the miner assemble/consider a signature set as having crossed the 70% threshold using contribution that should not exist twice. This is a Critical-class concern per the given rubric ("aggregated-weight vs verified-accepts" mismatch), because it can let a block be treated as sufficiently signed/rejected based on inflated tallies rather than genuine distinct signer weight.

### Likelihood Explanation
The trigger does not require a malicious majority or another signer's key — a single honest signer restarting at an unlucky moment (crash between broadcast and DB write in `check_submitted_block_proposal`) is sufficient to produce a reject-then-accept sequence for the same hash. However, the crash must land in a narrow synchronous window between two adjacent statements, which lowers likelihood; I could not find a *deterministic* (non-crash) code path in the time available that lets one signer legitimately flip from a broadcast `Rejected` to a broadcast `Accepted` for the identical `signer_signature_hash` without an intervening restart — I attempted to inspect `should_reevaluate_reject_reason` to check for such a designed reconsideration path but could not retrieve its body before running out of tool iterations, so this aspect is unverified.

### Recommendation
- In `stackerdb_listener.rs`, gate the `Accepted` weight addition on the same `responded_signers` set (or an equivalent per-slot "already voted" record) used by the `Rejected` branch, so a signer's weight is added to at most one of `total_weight_approved` / `total_weight_rejected` for a given block hash, regardless of message order.
- In `stacks-signer/src/v0/signer.rs::check_submitted_block_proposal`, swap the order to persist `self.signer_db.insert_block(&block_info)` before calling `self.send_block_response(...)`, consistent with the pattern used elsewhere in the file.

### Proof of Concept
1. Signer S's `submitted_block_proposal` times out; `check_submitted_block_proposal` broadcasts `Rejected` for hash `H`, then crashes before `insert_block` persists `mark_locally_rejected`. [3](#0-2) 
2. Coordinator's `stackerdb_listener` records S's weight into `total_weight_rejected` for `H`. [2](#0-1) 
3. S restarts; its DB shows block `H` as `Unprocessed`/`valid = None`. On the next validation cycle S validates `H` as fine and signs it, broadcasting `Accepted` for the same `H`.
4. `stackerdb_listener` checks only `gathered_signatures` (empty for S) and adds S's weight into `total_weight_approved` for `H` as well. [1](#0-0) 
5. Both tallies now include S's weight simultaneously for the same block, inflating the apparent approval/rejection totals beyond what the true set of distinct signer weights supports.
