### Title
Missing per-request audit logging in VaultController.ExportDKGResult / VerifyDKGResult enables undetected cross-instance DKG package extraction - ([File: core/web/vault_controller.go])

### Summary
`VaultController.ExportDKGResult` and `VaultController.VerifyDKGResult` read and return DKG result packages for an arbitrary `instanceId` supplied in the request body but never call `App.GetAuditLogger().Audit(...)`, unlike every other sensitive export/verify handler in this codebase (e.g. `CSAKeysController.Export`, `ETHKeysController.Export`, `keysController.Export`, `OCR2KeysController.Export`, `OCRKeysController.Export`, `VRFKeysController.Export`). This breaks the established audit-trail convention and removes the only after-the-fact mechanism to detect a lower-privileged authenticated user repeatedly probing/exfiltrating other jobs' DKG result packages via distinct `instanceId` values.

### Finding Description
`ExportDKGResult` (core/web/vault_controller.go:91-119) and `VerifyDKGResult` (core/web/vault_controller.go:35-83) accept a caller-supplied `instanceId` (and `masterPublicKey` for verify), look it up via `vault.NewVaultORM(vc.App.GetDB()).ReadResultPackage(ctx, instanceId)` with no ownership/ACL check tying the instance to the caller, and return the raw hex-encoded `ReportWithResultPackage` (export) or a verification result/hash (verify) in the JSON response. Neither handler emits an `audit.AuditLogger.Audit(...)` call, whereas every comparable "Export"/sensitive-read handler elsewhere in `core/web` (CSA, ETH, generic `keysController`, OCR, OCR2, P2P, VRF key exporters, and job creation/deletion/dismissal) does emit a structured audit event identifying the action and target resource ID, e.g. `core/web/eth_keys_controller.go:252-255` and `core/web/keys_controller.go:149-152`. Because these two vault endpoints skip this convention, there is no structured, queryable record correlating "who" (authenticated user/API token identity) accessed "which" `instanceId` and "when." If access control on these routes is role-gated (e.g. edit/run role) rather than scoped to the job/instance owner, a user with legitimate but lower-scoped credentials could iterate over `instanceId` values belonging to other jobs and extract their DKG result packages with zero audit trail, making such abuse indistinguishable from normal use in logs/SIEM tooling.

### Impact Explanation
This is an audit/observability gap, not a direct authorization bypass provable from this code alone — the actual authorization check for these routes lives in `router.go` route registration, which was not fully confirmed to require instance-level ownership (only role-based gating was found for other vault-adjacent routes in the codebase, and the specific auth wrapper on `/vault/dkg_results/*` could not be fully located within available tool budget). Given the security-audit framing, the confirmed defect is: no audit log entry (containing caller identity, `instanceId`, and action) is produced for export/verify, unlike all sibling export handlers. This matches a "missing security control / insufficient logging & monitoring" class finding rather than a demonstrated privilege escalation, since exploiting cross-instance access additionally requires that the role check itself doesn't already scope access per job/instance — which was not verified to be broken in this trace.

### Likelihood Explanation
If the route-level role check for `/vault/dkg_results/export` and `/vault/dkg_results/verify` is a generic role gate (e.g. `RequiresEditRole`) rather than a per-instance ownership check, any authenticated user holding that role for any job can query arbitrary `instanceId` values and repeatedly do so undetected, since there's no audit trail to flag repeated or cross-job access. This requires only a valid, appropriately-roled session/API token — no admin or host access — making it feasible and repeatable if the underlying authorization is role-only.

### Recommendation
Add `vc.App.GetAuditLogger().Audit(...)` calls to both `ExportDKGResult` and `VerifyDKGResult`, following the pattern used elsewhere (e.g. `core/web/eth_keys_controller.go:252-255`), logging at minimum the authenticated caller's identity, the requested `instanceId`, the action (export/verify), and the result (success/failure/hash). Additionally verify and, if missing, add per-instance/job ownership checks so that a role-holder cannot query `instanceId`s outside jobs they are authorized to manage.

### Proof of Concept
Go handler-level integration test plan (in `core/web/vault_controller_test.go`):
1. Set up a test `chainlink.Application` with a mock/fake `audit.AuditLogger` that records calls (`Audit(eventID, data)`).
2. Seed a DKG result package for a known `instanceId` via `vault.NewVaultORM`.
3. As an authenticated edit/run-role user, POST to `/v2/vault/dkg_results/export` with `{"instanceId": "<id>"}`.
4. Assert HTTP 200 and that the response contains the expected package.
5. Assert that the mock audit logger's `Audit` method was invoked exactly once with an event capturing `instanceId` and caller identity (e.g. email/role from context) — this assertion currently fails because no `Audit` call exists in `ExportDKGResult`/`VerifyDKGResult`, confirming the finding.
6. Repeat for `/v2/vault/dkg_results/verify`.
