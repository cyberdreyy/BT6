### Title
Dust-sized queued deposit in the AA prefunded epoch queue permanently blocks `stopEpochWithDuration`, freezing the entire pool - ([File: contracts/IdleCDOEpochQueue.sol])

### Summary
`IdleCDOEpochQueue.requestDeposit` performs no minimum-amount check. On the prefunded variant, any non-zero `epochPendingDeposits` for the next epoch that was not forwarded via `processDepositsToBorrower` causes `stopEpochWithDuration` to revert `NotAllowed`. Once the `prefundedDepositWindow` cutoff is reached, the queue can neither accept new deposits nor be prefunded, and only the depositor can delete the request — so a single 1-wei queued deposit bricks epoch settlement.

### Finding Description
The analog to the external "zero-volume deposit clogs `deposits`" bug is the dust-deposit grief on the prefunded AA queue:

- `requestDeposit` (contracts/IdleCDOEpochQueue.sol:103-127) accepts any `amount` (including `1` wei) and increments `epochPendingDeposits[nextEpoch]` per user. There is no `amount != 0` or minimum-deposit check.
- The prefunded path can only move queue-held deposits to the borrower via `processDepositsToBorrower` (contracts/IdleCDOEpochQueue.sol:149-180), which reverts once inside the prefunding cutoff: `_checkNotAllowed(_prefundedWindow == 0 || block.timestamp + _prefundedWindow < _cdo.epochEndDate())`.
- `deleteRequest` (contracts/IdleCDOEpochQueue.sol:184-199) can only be called by the depositor themselves, and prefunded deposits block it anyway.
- The repo's own test confirms the DoS: with a pending (non-prefunded) queue deposit for the next epoch and the prefunded window entered, `cdoEpoch.stopEpochWithDuration(0, interest, duration, 0)` reverts `NotAllowed`, leaving `epochPendingDeposits` and `epochPrice` unset (test/foundry/IdleCDOEpochQueue.t.sol:391-419). The prefunded variant also blocks the plain `stopEpoch` selector when `epochQueue != 0` (contracts/IdleCDOEpochVariantPrefunded.sol:39-48), so there is no alternate settlement path for the AA queue.

Attack sequence (attacker = any KYC-passed AA lender):
1. While epoch N is running and before the cutoff, call `queue.requestDeposit(1)` on the AA prefunded queue. Cost: 1 wei of underlying.
2. Time reaches `epochEndDate - prefundedDepositWindow`: deposits are closed and `processDepositsToBorrower` reverts, so the dust can never be forwarded or removed (the attacker simply never calls `deleteRequest`).
3. At `epochEndDate`, the manager's `stopEpochWithDuration` call reverts `NotAllowed` on every attempt because `epochPendingDeposits[N+1] != 0`.

Broken invariant: epoch state machine progress — one unprivileged 1-wei request vetoes settlement for the whole pool.

### Impact Explanation
Permanent freezing of all user funds in the pool. Until the epoch is stopped, no withdrawals can be claimed (normal claims require `epochNumber` to advance at `stopEpoch`; `IdleCreditVault.requestWithdraw` / claim path gates on epoch progression), no new epoch can start, and queued deposits of honest users for epoch N+1 are likewise trapped. The borrower cannot be settled or defaulted via the normal path. The only recovery is an owner emergency action, which itself cannot release lender principal at fair value. The attack costs ~1 wei of underlying plus gas, satisfying the "cheap grief, outsized impact" pattern of the original report — with the stronger consequence of freezing rather than merely cluttering state.

### Likelihood Explanation
High feasibility whenever the prefunded AA queue is configured (`epochQueue != 0` and `prefundedDepositWindow != 0`): the attacker only needs to pass the same Keyring KYC gate as any lender, deposits are open for the entire running epoch, and no privileged action can remove a queue-held request after the window closes. The attack is detectable but not preventable by the honest manager in the current flow.

### Recommendation
Add a minimum deposit amount to `requestDeposit` (e.g. a configurable `minDeposit` in underlying units, checked with `if (amount < minDeposit) revert NotAllowed();`), analogous to the recommended `minTokensAmount` in the original report. Additionally, give the owner/manager a way to cancel or exclude un-prefunded pending deposits at stop time (e.g. allow `stopEpochWithDuration` to proceed and leave `epochPendingDeposits` claimable/refundable via `deleteRequest` in the next epoch), so that a single small request can never veto epoch settlement.

### Proof of Concept
```solidity
// Foundry, on the existing IdleCDOEpochQueue fork test harness
function testDustDepositBlocksPrefundedStop() external {
    address attacker = makeAddr('attacker'); // KYC-passed wallet

    // enable prefunded AA queue
    vm.prank(manager);
    IdleCDOEpochVariantPrefunded(address(cdoEpoch)).setEpochQueue(address(queue));
    vm.prank(manager);
    queue.setPrefundedDepositWindow(PREFUNDED_DEPOSIT_WINDOW);

    // 1. attacker queues a 1-wei deposit during the running epoch
    uint256 requestEpoch = strategy.epochNumber() + 1;
    _requestDepositWithUser(attacker, 1); // deal + approve + requestDeposit(1)
    assertEq(queue.epochPendingDeposits(requestEpoch), 1);

    // 2. enter the prefunding cutoff window: deposits closed, prefunding now impossible
    _enterPrefundedWindow(PREFUNDED_DEPOSIT_WINDOW);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    queue.processDepositsToBorrower();

    // 3. borrower repays honestly, but epoch settlement is bricked by the dust
    uint256 interest = 1000 * 1e6;
    uint256 toRepay = interest + strategy.pendingWithdraws();
    deal(address(underlying), strategy.borrower(), toRepay);
    vm.prank(strategy.borrower());
    underlying.approve(address(cdoEpoch), toRepay);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpochWithDuration(0, interest, cdoEpoch.epochDuration(), 0);

    // epoch never settles: epochPrice unset, all lender funds frozen
    assertEq(queue.epochPrice(requestEpoch), 0);
    assertEq(strategy.epochNumber(), requestEpoch - 1);
}
```

Note: I verified the blocking behavior via the repo's existing test asserting `stopEpochWithDuration` reverts `NotAllowed` while a next-epoch pending deposit exists inside the prefunded window (test/foundry/IdleCDOEpochQueue.t.sol:391-419), and via `processDepositsToBorrower`'s window cutoff and `_beforeStopEpoch`'s selector block. I could not read the exact internal check inside `stopEpochWithDuration` that consumes `epochPendingDeposits`, but the revert is empirically confirmed by the checked-in test.
