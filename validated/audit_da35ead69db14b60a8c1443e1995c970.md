### Title
Loss-adjusted withdraw receipt is paid at par after a later `requestWithdraw` overwrites `lastWithdrawRequest` — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimWithdrawRequest` decides whether a pending receipt must be haircut by looking up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. Because `requestWithdraw` unconditionally overwrites `lastWithdrawRequest` with the *current* epoch, an unclaimed loss-adjusted receipt from an older epoch silently becomes a "funded" receipt and is paid 1:1 by `_claimFundedWithdrawRequest`, draining underlyings that were never funded for it.

### Finding Description
When a user calls `requestWithdraw`, the vault burns the CDO's principal tokens, mints a receipt, increments `pendingWithdraws`, and stores `lastWithdrawRequest[_user] = currentEpoch` (`IdleCreditVault.sol:282-293`).

If the epoch ends via `stopEpochWithDuration(_lossAmount)` with a loss, the borrower only funds `claimBasis * lossRecoveryPriceByEpoch[epoch]`, and `pendingWithdraws` is cleared at the reduced amount. The haircut is only applied at claim time inside `_claimLossAdjustedWithdrawRequest`, which keys the lookup on `lastWithdrawRequest[_user]`:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```
(`IdleCreditVault.sol:789-800`)

`claimWithdrawRequest` then calls `_claimFundedWithdrawRequest`, whose only gate is `epochNumber <= lastWithdrawRequest[_user]`. It pays the *aggregate* `withdrawsRequests[_user]` at par (`IdleCreditVault.sol:326-349`) — and `withdrawsRequests` still contains the unclaimed loss-epoch amount, since `_clearWithdrawClaimForEpoch` only decrements the epoch it is invoked for (`IdleCreditVault.sol:815-819`).

Attack sequence (running epoch, `stopEpochWithDuration` loss mode):

1. Epoch L: attacker calls `cdoEpoch.requestWithdraw(amount)`. `lastWithdrawRequest[attacker] = L`, `withdrawsRequestsByEpoch[attacker][L] = amount`.
2. `stopEpochWithDuration` ends epoch L with a loss; `lossRecoveryPriceByEpoch[L] = p < 1`. Only `amount * p` is funded.
3. Attacker does **not** claim. Epoch L+1 (M): attacker calls `requestWithdraw` again (even for 1 wei of tranche tokens, or a second deposit first). `lastWithdrawRequest[attacker] = M`.
4. After epoch M stops, attacker calls `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[M] == 0` and returns 0 — the epoch-L haircut is skipped.
   - `_claimFundedWithdrawRequest` sees `epochNumber > M`, computes `amount = withdrawsRequests[attacker]` (which still includes the full epoch-L `amount`), burns receipts, and transfers `amount` **at par**.

The attacker receives the full pre-loss value for a receipt that was only funded at `p`, stealing `amount * (1 - p)` from the strategy's funded underlyings.

### Impact Explanation
Direct theft / insolvency. The overpayment `claimBasis * (1 - lossRecoveryPrice)` is paid from underlyings belonging to other funded claimants and active LPs. With a 50% loss epoch and a 10,000 token receipt, the attacker extracts ~5,000 extra tokens; with a near-total loss, essentially the entire receipt is stolen. The extra spend can also push the strategy below what later funded claimants are owed, permanently freezing their payouts.

### Likelihood Explanation
Any tranche-token holder (unprivileged) can execute this; no privileged role is needed. The preconditions — a `stopEpochWithDuration` loss followed by a new epoch where the user requests again — are a normal operating path (the code comments explicitly allow a second request before claiming). No guard stops it: `_transferFundedClaim` only protects `defaultRecoveryReserve`, the `NotAllowed` gate is bypassed because `lastWithdrawRequest` now points at a non-loss epoch, and `lossRecoveryPriceByEpoch[L]` is never re-checked. The analogous flaw also exists for a user who has both a loss-epoch receipt and a defaulted-epoch receipt: `_clearWithdrawClaimForEpoch` resets `lastWithdrawRequest` to 0 (`IdleCreditVault.sol:832-835`), again skipping the loss lookup.

### Recommendation
Track claim basis per epoch rather than keying the loss lookup on `lastWithdrawRequest`. In `claimWithdrawRequest`, iterate or otherwise check every epoch with a non-zero `withdrawsRequestsByEpoch[_user][epoch]` against `lossRecoveryPriceByEpoch[epoch]` before falling through to the par-funded path — e.g., store a per-user set/linked list of request epochs, or have `_claimFundedWithdrawRequest` sum only epochs whose `lossRecoveryPriceByEpoch` is zero. Alternatively, revert in `requestWithdraw` when an unclaimed receipt exists in a loss epoch.
