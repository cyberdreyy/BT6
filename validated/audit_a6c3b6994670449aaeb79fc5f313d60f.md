### Title
`get_multiple_accounts` RPC handler fails the entire batch when a single account cannot be encoded - (File: rpc/src/rpc.rs)

### Summary
### Finding Description
`JsonRpcRequestProcessor::get_multiple_accounts` iterates over every pubkey supplied by the caller and calls `get_encoded_account()` for each one, propagating any error with `?` inside the loop: [1](#0-0) 

`get_encoded_account()` in turn calls `encode_account()`, which returns an `Err(...)` (an `InvalidRequest` JSON-RPC error) whenever the requested encoding is `Binary`/`Base58` and the account's data (after the data-slice) exceeds `MAX_BASE58_BYTES`: [2](#0-1) 

Because the loop in `get_multiple_accounts` uses `?` on each individual account lookup, a single pubkey in the batch whose data is too large to base58-encode causes the `?` to short-circuit and abort the whole request — every other account in the batch, regardless of size or validity, is discarded and the caller receives a single JSON-RPC error instead of the array of results. This mirrors the reported bug class: an aggregate/batch operation over a list of independent items reverts entirely because one item is "inactive"/unusable, instead of continuing to process the valid items.

This differs from the single-account `getAccountInfo` path, where rejecting the request due to encoding size makes sense because there is nothing else to return; for `getMultipleAccounts`, the same check discards potentially many perfectly valid, already-resolved account results.

### Impact Explanation
An unprivileged RPC caller invoking `getMultipleAccounts` with `encoding: "base58"` (or `"binary"`) and a batch that happens to include one address whose account exceeds `MAX_BASE58_BYTES` (up to 128 accounts per call, see `MAX_MULTIPLE_ACCOUNTS`/`max_multiple_accounts` checked earlier in the handler) gets zero results back for the entire batch, even though the other accounts could have been encoded successfully. There is no indication in the error of which pubkey caused the failure, so the caller cannot simply drop the offending key and retry without probing individually. This is a functional correctness/misreporting bug reachable via a single, ordinary JSON-RPC call from any client — no elevated privileges required, and the affected accounts are ordinary on-chain state (e.g., program accounts that have grown via reallocation past the base58 size limit).

### Likelihood Explanation
Any account whose data exceeds `MAX_BASE58_BYTES` is a legitimate, naturally occurring condition on a live cluster (accounts can be up to 10MB via `realloc`), so this is trivially triggerable by any client that mixes such an address into a base58/binary-encoded `getMultipleAccounts` call — accidentally or deliberately.

### Recommendation
In `get_multiple_accounts`, do not propagate a per-account encoding error with `?` for the whole batch. Instead, catch the error for the individual pubkey and place a per-item error/`None` in the corresponding slot of the response array (as the top-level `Result<Vec<Option<UiAccount>>>` already implies per-slot optionality), so that valid entries are still returned. Alternatively, validate encoding compatibility per-slot before assembling the response and surface which specific account triggered the failure, matching the recommended mitigation pattern of continuing to process the valid items rather than aborting the entire operation.

### Proof of Concept
1. Store a large account (e.g., data length > `MAX_BASE58_BYTES`) plus one or more small, valid accounts on a running validator/test-validator.
2. Call `getMultipleAccounts` with `encoding: "base58"` and an array containing the large account's pubkey together with the valid pubkeys.
3. Observe that the RPC call returns a single JSON-RPC `InvalidRequest` error for the whole call (per `encode_account` at [3](#0-2) ), and none of the other, otherwise valid, account data is returned — compare with the same accounts requested individually via `getAccountInfo`, which succeed for the small accounts.

fn get_encoded_account(
    bank: &Bank,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
    // only used for simulation results
    overwrite_accounts: Option<&HashMap<Pubkey, AccountSharedData>>,
) -> Result<Option<UiAccount>> {
    match account_resolver::get_account_from_overwrites_or_bank(pubkey, bank, overwrite_accounts) {
        Some(account) => {
            let response = if is_known_spl_token_id(account.owner())
                && encoding == UiAccountEncoding::JsonParsed
            {
                get_parsed_token_account(bank, pubkey, account, overwrite_accounts)
            } else {
                encode_account(&account, pubkey, encoding, data_slice)?
            };
            Ok(Some(response))
        }
        None => Ok(None),
    }
}

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
