### Title
Broken EI-vs-User authorization check in `PipelineRunsController.Create` allows external-initiator credentials to trigger runs on arbitrary jobs by integer ID - (File: core/web/pipeline_runs_controller.go)

### Summary
`PipelineRunsController.Create` intends to block External Initiator (EI) credentials from running jobs via integer job IDs ("EIs not allowed", per its own comment), gating on `auth.GetAuthenticatedUser(c)`. However, `auth.AuthenticateExternalInitiator` also populates `SessionUserKey` with a synthetic run-role `User`, so `GetAuthenticatedUser` returns `ok=true` for EI-authenticated requests exactly the same as for real session/token users, defeating the intended check.

### Finding Description
In `core/web/pipeline_runs_controller.go`, `Create` does: [1](#0-0) 
The only gate distinguishing "user" from "EI" callers is `_, isUser := auth.GetAuthenticatedUser(c)`. But `auth.AuthenticateExternalInitiator` (the middleware that authenticates EI credentials via the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers) explicitly sets the same `SessionUserKey` used by real users: [2](#0-1) 
`GetAuthenticatedUser` simply checks for the presence of that key: [3](#0-2) 
So after a successful EI authentication, `isUser` is `true` (the synthetic user has `Role: UserRoleRun`), and the code proceeds to parse the path `:ID` as an int32 job ID and directly call `prc.App.RunJobV2(ctx, jobID, nil)` with no check that the job is associated with, or was created by, the authenticating EI 'A'. There is no lookup of any external-initiator-to-job binding anywhere in this handler. Any route-level role wrapper (`auth.RequiresRunRole`) also passes, since it only checks `user.Role != UserRoleView`, and the EI's synthetic user has `Role: UserRoleRun`.

The net effect: the comment in the code ("only users are allowed to run jobs using int IDs - EIs not allowed") describes intended behavior that the implementation does not actually enforce, because the check used to detect "is this a real user" is satisfied by EI authentication too.

### Impact Explanation
An attacker holding valid credentials for any single External Initiator can trigger a job run (`RunJobV2`) on any arbitrary job in the node by integer ID, not just jobs tied to that EI. Depending on job type, this can cause unauthorized re-execution of pipelines with side effects (e.g., VRF fulfillment attempts, Keeper/Upkeep execution paths, external HTTP calls, bridge webhook side effects), unwanted resource consumption, and cross-tenant unauthorized actions on jobs the EI credential holder has no legitimate relationship to. This matches the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Minimal precondition: possession of any single valid EI accesskey/secret pair (a low-privilege credential type explicitly intended to only trigger its own associated webhook runs). The exploit is a single unauthenticated-role POST request with a guessed/enumerated integer job ID; job IDs are small sequential integers, making enumeration straightforward. No admin/session/user credentials are required, only the pre-existing EI credential.

### Recommendation
Fix the check in `Create` to explicitly distinguish EI-authenticated requests from genuine user (session/token) requests — e.g., by checking `auth.GetAuthenticatedExternalInitiator(c)` and rejecting if it is present, instead of relying solely on `GetAuthenticatedUser`. Additionally, do not have `AuthenticateExternalInitiator` populate `SessionUserKey` with a role that satisfies downstream "is a user" checks meant to exclude EIs, or provide a dedicated context flag (e.g., `SessionIsEI`) that all such gates check consistently.

### Proof of Concept
Go handler-level integration test plan:
1. Start a `cltest.TestApplication`.
2. Create EI 'A' via `bridges.NewExternalInitiator` + `app.BridgeORM().CreateExternalInitiator` (as in `core/web/router_test.go` `TestTokenAuthRequired_TokenCredentials`) [4](#0-3) .
3. Create an unrelated job (e.g., an OCR job as in `setupPipelineRunsControllerTests`) not associated with EI 'A' in any way [5](#0-4) .
4. Send `POST /v2/jobs/<jobID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to EI 'A' credentials.
5. Assert expected secure behavior: `401`/`403` (rejected due to missing EI-job binding).
6. Actual behavior per code trace: request succeeds (`200`) and a new pipeline run resource is returned, because `isUser` is `true` for EI-authenticated calls and `RunJobV2` executes unconditionally on the target job ID.
