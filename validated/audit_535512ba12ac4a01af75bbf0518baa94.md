### Title
Dust queued withdrawal request permanently reverts `processWithdrawRequests` and freezes the whole epoch's queued withdrawals - ([File: contracts/IdleCDOEpochQueue.sol])

### Summary
`IdleCDOEpochQueue.requestWithdraw` accepts a `uint256 amount` with no minimum check. Any KYC-passing wallet can queue a 1-wei tranche withdrawal. When the manager later calls `processWithdrawRequests`, the queue invokes `IdleCDOEpochVariant.requestWithdraw(_pending, tranche)`, which returns `_underlyings = principal + interest - totalFees`. For a dust amount the tranche-to-underlying conversion `_amount * _tranchePrice / ONE_TRANCHE_TOKEN` rounds to 0 and fees are 0, so `_underlyingsRequested == 0`. The queue then computes `_epochPrice = 0 * ONE_TRANCHE / _pending = 0` and hits `revert Is0()` (IdleCDOEpochQueue.sol:319-321). Because the revert happens *after* `_cdo.requestWithdraw` inside the same transaction, the whole call reverts atomically — `epochPendingWithdrawals[_epoch]` remains non-zero forever and every subsequent `processWithdrawRequests` call for that epoch reverts identically.

### Finding Description
The analog to "send null data at resource creation to poison all subsequent operations" is a dust ("effectively null") withdraw request created via `requestWithdraw(amount)` (IdleCDOEpochQueue.sol:131-143), which performs `safeTransferFrom` of the tranche token and increments `userWithdrawalsEpochs`/`epochPendingWithdrawals` with no zero/minimum guard.

The poisoned record is consumed in `processWithdrawRequests` (lines 301-329):

```solidity
uint256 _underlyingsRequested = _cdo.requestWithdraw(_pending, tranche);
uint256 _epochPrice = _underlyingsRequested * ONE_TRANCHE / _pending;
if (_epochPrice == 0) {
  revert Is0();
}
```

With `_pending = 1` (or any dust amount whose underlying value rounds to 0 at current `virtualPrice`), `_underlyingsRequested == 0`, `_epochPrice == 0`, and the call reverts. The attacker never deletes the request (only `msg.sender`'s own requests can be deleted via `deleteWithdrawRequest`), so `epochPendingWithdrawals[_epoch]` can never reach 0 through manager actions — `processWithdrawRequests` reverts unconditionally, `pendingClaims` stays false, `epochPendingClaims`/`epochWithdrawPrice` are never set, and `processWithdrawalClaims` early-returns.

### Impact Explanation
All tranche tokens queued by honest users for that epoch are frozen inside the queue contract: they cannot be processed into claims because the pricing step always reverts on the attacker's dust contribution to `_pending`. Broken invariant: one receipt one payout — a single dust request blocks the aggregate payout path for every requester in the epoch. Honest users can eventually recover their tranche tokens only by individually calling `deleteWithdrawRequest` (allowed while `epochWithdrawPrice == 0`), so the freeze is temporary but requires every affected user to discover and execute an unwind, and the manager cannot force resolution. Classified as temporary freezing of user funds with a permanently bricked epoch-processing path.

### Likelihood Explanation
- Attacker needs only `isWalletAllowed` (Keyring KYC pass) — explicitly in scope as an unprivileged lender.
- Cost is ~1 wei of tranche tokens plus gas; no privileged cooperation needed.
- No existing guard stops it: `requestWithdraw` has no amount check, `_checkAllowed` only verifies epoch-running + KYC, and the `Is0` revert exists precisely because the zero-price case was anticipated but is triggered instead of filtered.
- Caveat reducing severity: honest users retain an exit via `deleteWithdrawRequest`, so this is not permanent loss of principal.

### Recommendation
- Reject zero/dust requests in `requestWithdraw` (e.g., `if (amount == 0) revert Is0();` and/or a minimum tranche amount).
- Alternatively, in `processWithdrawRequests`, skip/reclaim requests whose `_underlyingsRequested` resolves to 0 rather than reverting the entire batch — e.g., mark the epoch with `isEpochWithdrawZero` when `_epochPrice == 0` instead of reverting, symmetric to the handling already added in `processWithdrawalClaims`.

### Proof of Concept
Foundry-style PoC sketch against the fork test harness (`test/foundry/IdleCDOEpochQueue.t.sol` conventions):

```solidity
function testDustRequestBlocksProcessWithdrawRequests() external {
  // epoch running, attacker is KYC-allowed
  address attacker = makeAddr("attacker");
  deal(address(tranche), attacker, 1); // 1 wei tranche token
  vm.startPrank(attacker);
  tranche.approve(address(queue), 1);
  queue.requestWithdraw(1);            // dust request lands in nextEpoch
  vm.stopPrank();

  // honest users also queued: epochPendingWithdrawals[nextEpoch] > 1
  // ... stop epoch so epochNumber advances ...
  _stopCurrentEpochWithApr(10e18);

  vm.prank(manager);
  vm.expectRevert(Is0.selector);
  queue.processWithdrawRequests();     // _underlyingsRequested == 0 -> price 0 -> revert

  assertEq(queue.pendingClaims(), false);
  assertGt(queue.epochPendingWithdrawals(strategy.epochNumber()), 0); // stuck forever
}
```
