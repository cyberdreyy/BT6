### Title
Global block-rejection tally silently drops a signer's valid vote once that signer has rejected any other block — `block_rejection_signer_addrs` table keyed by `signer_addr` alone ([File: stacks-signer/src/signerdb.rs])

### Summary
`block_rejection_signer_addrs` is keyed only on the signer's address, not on `(signer_signature_hash, signer_addr)`. Because a signer legitimately rejects multiple distinct block proposals over the life of a tenure (retries, competing proposals, etc.), the second and every subsequent verified rejection from the same signer for a *different* block hash collides with the existing primary key and is treated as a duplicate, so it is silently dropped and never counted toward that block's rejection tally. This is the same class of bug as the ENS report: an on-chain/off-chain accounting equality ("aggregated rejected weight" == "set of verified rejections actually received for this block") is broken because state that should be scoped per-object (per-block) is instead collapsed into a single global slot per signer, and the caller trusts the boolean result without noticing the scope mismatch.

### Finding Description
The table is created with a primary key on `signer_addr` only, even though it also stores `signer_signature_hash`: [1](#0-0) 

Rejection-weight aggregation reads this table filtered by a specific `signer_signature_hash`: [2](#0-1) 

The write path in `store_and_process_block_rejection` treats the insert's boolean result as "already have this exact signature, don't process again": [3](#0-2) 

Because the underlying table's primary key is `signer_addr` alone (not the composite `signer_signature_hash + signer_addr`), a second, cryptographically-valid rejection from the same signer for a *different* block collides with the row already occupied by that signer's earlier rejection of a *different* block. The insert either no-ops or rewrites the row's `signer_signature_hash` to the new block, in both cases the code path treats it via `Ok(false) => return` as a "duplicate, do nothing" case — even though this is the first (and only) rejection that signer ever cast for the *current* block. The rejection is therefore never added to `total_reject_weight` for the current block, and the guard "have we already processed this exact vote" incorrectly fires for a vote it has never actually processed for this block.

This breaks the intended equality: "aggregated `total_reject_weight` for block X == sum of weights of signers who verified-rejected block X." Once a signer has rejected any earlier proposal in the tenure, that signer's weight becomes permanently invisible to every later block's rejection tally (until, if ever, a stale row happens to get overwritten back to the new hash — which then in turn silently erases the earlier block's row).

### Impact Explanation
`store_and_process_block_rejection` uses this tally to decide when `(set-size − threshold + 1)` weight has rejected a block and to call `mark_globally_rejected`: [4](#0-3) 

If enough of the signers who reject block B previously rejected a different block A earlier in the same tenure (a very plausible scenario, e.g. a miner reproposing after an earlier rejected attempt), their votes for B never get counted. The genuinely-rejecting weight can exceed 30% of total stake in reality while the signer's own bookkeeping believes it is far below threshold. That wedges the tenure: the block is never marked `GloballyRejected` on the signer side even though a supermajority-minority has, in fact, rejected it, and the coordinator/node keeps waiting on a decision that the signer set's local state can never produce correctly. This is a liveness wedge on the rejection path — an aggregated-weight-vs-verified-rejects equality break, which is one of the explicitly in-scope safety/liveness break categories (aggregated weight vs verified accepts/rejects).

### Likelihood Explanation
No majority collusion, no additional keys, and no special network conditions are required — a single miner (as allowed by the analog rules, "a one-slot miner plus gossip") proposing two or more distinct blocks in sequence within a tenure (a routine occurrence, e.g. retry after a rejected proposal, or a tenure-extend re-proposal) is sufficient to make honest signers cast rejections against more than one block hash, tripping this collision. This requires no attacker-controlled key material, no majority of signers, and no auth token — it is triggered purely by the signer's own bookkeeping schema.

### Recommendation
Change the primary key of `block_rejection_signer_addrs` to the composite `(signer_signature_hash, signer_addr)` (matching the pattern already used correctly for `block_signatures`, which keys on the signature itself and therefore never collides across blocks). Update `add_block_rejection_signer_addr` and its callers so the "is this a duplicate" check is scoped per `(block_hash, signer_addr)` rather than per `signer_addr` alone, and add a migration/index accordingly (mirroring `CREATE_INDEXES_3`).

### Proof of Concept
1. Tenure T: miner proposes block A (`hash_A`). Signer S validates and rejects it; `add_block_rejection_signer_addr(hash_A, S, reason)` inserts a row `{signer_signature_hash: hash_A, signer_addr: S}` — the only row for primary key `S`.
2. Miner reproposes at the same height with a different transaction set: block B (`hash_B`). Signer S (and other signers) independently, cryptographically verify and reject B.
3. `store_and_process_block_rejection` calls `add_block_rejection_signer_addr(hash_B, S, reason)`. Because the table's primary key is `signer_addr` alone and `S` already owns a row, the insert cannot create an independent `(hash_B, S)` row; the call returns a result treated by the caller as `Ok(false) => return` ("we already have this signature, do not process it again") — even though S has never before voted on `hash_B`.
4. `get_block_rejection_signer_addrs(hash_B)` (queried by `signer_signature_hash = hash_B`) therefore never reflects S's vote, so `total_reject_weight` for block B is undercounted by S's weight, and analogously by the weight of every other signer who previously rejected `hash_A` (or any other earlier block hash) before rejecting B.
5. If enough signers fall into this state, the true rejecting weight for block B exceeds the 30%-of-total-weight threshold in reality, but the tallied `total_reject_weight` computed from `block_rejection_signer_addrs` never crosses it, so `mark_globally_rejected` is never invoked, wedging resolution of block B for that signer.
