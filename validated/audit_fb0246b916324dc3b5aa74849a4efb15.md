### Title
Global-state agreement threshold uses floor rounding while the on-chain/local block-signing threshold uses ceiling rounding — a single signer's vote can be double-counted into a false "global agreement" - (File: libsigner/src/v0/signer_state.rs)

### Summary
`GlobalStateEvaluator::reached_agreement` computes the 70% consensus threshold with integer floor division (`total_weight * 70 / 10`), whereas every other threshold computation in the codebase that is supposed to represent the same "70% of signer weight" quantity — `NakamotoBlockHeader::compute_voting_weight_threshold` (used to verify block signatures on-chain) and the analogous Clarity `get-threshold-weight` (`(/ (+ (* total-weight threshold-consensus) u99) u100)`, a ceiling division) — round up (ceiling). This mirrors the H01 bug class: two computations of what should be the *same* threshold diverge because one floors and the other ceils, so a value that fails one check can pass the other. ### Finding Description
`reached_agreement`/`reached_disagreement` are used by `GlobalStateEvaluator::determine_global_state` (invoked from `LocalStateMachine::capitulate_viewpoint` / `capitulate_miner_view` in `stacks-signer/src/v0/signer_state.rs`) to decide whether "the signer set" has reached consensus on a `SignerStateMachine` (which miner to build for, `parent_tenure_last_block`, and the tx-replay set): [4](#0-3) 

The threshold arithmetic in `reached_agreement` is `vote_weight >= total_weight * 7 / 10` (floor), diverging from `compute_voting_weight_threshold`, which explicitly adds a `ceil` adjustment when the division is not exact: [5](#0-4) 

For any `total_weight` where `total_weight * 7` is not a multiple of 10 (e.g. `total_weight = 3`: `3*7/10 = 2` under floor, but `ceil(3*7/10) = 3`), the two thresholds disagree by one unit of weight. This means a candidate miner-state view that has exactly `2` weight out of `3` can be treated by `GlobalStateEvaluator` as having "reached agreement" (66.7% ≥ 60%-truncated-floor number) even though it is below the 70%-rounded-up bar that the rest of the protocol (block-signature verification, the Clarity DKG-vote contract) treats as the real supermajority line.

Because `capitulate_miner_view`/`capitulate_viewpoint` uses this looser threshold to switch the signer's local `current_miner`/`parent_tenure_last_block` view — the very state that is serialized as the consensus-visible `StateMachineUpdate` and that gates which blocks a signer treats as building on the correct parent — a one-slot-weight minority (which a single miner or a small number of colluding/compromised signers plus gossip can supply) can push individual signers to capitulate to a view that has not actually cleared the intended 70% supermajority. This can cause a signer to adopt (and subsequently sign block proposals against) a `parent_tenure_last_block`/miner view backed by less real support than the protocol's actual approval bar, i.e., an equality break between "signed/agreed-upon view" and "verified/threshold-cleared view."

### Impact Explanation
This falls under the "aggregated-weight vs verified-accepts" equality-break class: the local state machine's notion of "the global state has reached agreement" (used to decide which miner/tenure view to build proposals against and pre-commit/sign) is computed with a laxer (floor) rounding than the canonical weight-threshold function used for actual block-signature verification (ceiling). A view that would not clear the real 70% bar can still be adopted as "the" global state by individual signers, potentially causing them to sign or pre-commit against a miner/tenure view that a strict majority did not actually approve — a precursor to signing on the wrong parent tenure / non-canonical fork.

### Likelihood Explanation
The divergence occurs deterministically whenever `total_weight * 7` is not evenly divisible by 10 (i.e., most real-world weight distributions, since individual signer weights are integers derived from stacked amounts). A miner (who controls proposal broadcast/timing and can craft `StateMachineUpdate` traffic reaching only ~66-69% weight support) combined with normal gossip of `StateMachineUpdate` messages from existing signers is sufficient to trigger the off-by-one weight gap — no majority collusion or key compromise is required, matching the "one-slot miner plus gossip" threat model.

### Recommendation
Make `reached_agreement`/`reached_disagreement` use the same ceiling-division formula as `NakamotoBlockHeader::compute_voting_weight_threshold` (and the Clarity contract's `get-threshold-weight`), e.g. compute `threshold = (total_weight * 7 + 9) / 10` (ceiling) instead of floor `total_weight * 7 / 10`, so the global-state agreement bar exactly matches the on-chain block-signature approval threshold.

### Proof of Concept
1. Construct a reward set/`GlobalStateEvaluator` with `total_weight = 3` (three signers, weight 1 each) — this is directly testable via the existing `generate_global_state_evaluator` test helper in `libsigner/src/tests/signer_state.rs`.
2. Have 2 of the 3 signers' `address_updates` agree on a candidate `SignerStateMachine` (`vote_weight = 2`).
3. Call `reached_agreement(2)`: `2 >= 3*7/10 = 2` → `true` — global agreement declared with only 66.7% weight.
4. Meanwhile, `NakamotoBlockHeader::compute_voting_weight_threshold(3)` returns `ceil(3*7/10) = 3`, i.e. actual block-signature verification would require all 3 signers' weight to approve a block — a 1-weight gap between what `GlobalStateEvaluator` considers "global agreement" for the miner/tenure view versus what the chain requires for a block signature, demonstrating the inconsistent threshold semantics.         u64::from(vote_weight)
            >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)

        u64::from(vote_weight)

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
