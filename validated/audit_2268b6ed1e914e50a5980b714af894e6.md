### Title
Claimed instant-withdraw receipts are never cleared from per-epoch accounting, inflating default-recovery basis and permanently locking recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` zeroes only the aggregate `instantWithdrawsRequests[_user]`; the per-epoch records `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are never decremented on a successful claim. Like the Privoxy leak (state allocated per request but never freed), already-paid instant receipts keep accumulating in the epoch-level claim basis. If the borrower defaults in the same epoch while `pendingInstantWithdraws != 0`, `defaultPendingClaimBasis()` counts the stale, already-claimed basis again, diluting `defaultRecoveryPrice` for all genuine claimants and leaving a permanently unclaimable share of `defaultRecoveryReserve` stranded in the contract. [1](#0-0) 

### Finding Description
- `requestInstantWithdraw` records three pieces of state per request: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the epoch aggregate `instantWithdrawClaimsByEpoch[currentEpoch]`, plus `pendingInstantWithdraws`. [2](#0-1) 
- `collectInstantWithdrawFunds` only reduces `pendingInstantWithdraws` when the CDO funds the queue. [3](#0-2) 
- `claimInstantWithdrawRequest` burns the user receipt, zeroes `instantWithdrawsRequests[_user]`, and pays out — but never touches `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch`. The per-epoch basis of a fully paid receipt leaks. [4](#0-3) 
- At default, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, and `_defaultPrefundedInstantReserve()` computes prefunded cash as `instantBasis - pendingInstant`. [5](#0-4) 
- Scenario: users A and B request instant withdrawals in epoch N. The CDO funds only A's amount (`collectInstantWithdrawFunds(A)`), so `pendingInstantWithdraws = B`. A claims and is paid in full, but `instantWithdrawClaimsByEpoch[N]` still equals `A + B`. The borrower then defaults and `finalizeDefaultRecovery` runs in the same epoch: `pendingBasis` includes `A + B` instead of just `B`, so `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is computed over a phantom basis inflated by A's already-paid claim. [6](#0-5) 
- B and active tranche holders receive `claimBasis * recoveryPrice` each, so the reserve portion attributed to A's ghost receipt is never claimed. `defaultRecoveryReserve` is decremented only on real claims (`_transferDefaultRecovery`), so the excess stays locked in the strategy forever — no function sweeps it. [7](#0-6) 
- Additionally, if A calls `claimInstantWithdrawRequest` again (e.g., to collect a separate older funded receipt), `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = instantWithdrawsRequestsByEpoch[A][N] > 0` and then executes `instantWithdrawsRequests[A] -= claimBasis` on a zeroed aggregate — an underflow revert that permanently DoS-es that function for A. [8](#0-7) 
- The same leak applies to `withdrawsRequestsByEpoch` in `_claimFundedWithdrawRequest`, which zeroes `withdrawsRequests[_user]` but not the per-epoch entry; there it is partially mitigated because `lastWithdrawRequest` is reset and the default path only reads `defaultRecoveryEpoch`, but the instant-withdraw path has no such guard since `instantWithdrawClaimsByEpoch[epochNumber]` is read globally. [9](#0-8) 

### Impact Explanation
Direct loss/dilution of default recovery plus permanent freezing of funds. With A = 100k USDC instant claim already paid and B = 100k pending, `totalBasis` is inflated by 100k, so `defaultRecoveryPrice` is understated proportionally; the reserve slice backing the phantom claim (up to the full recovered value attributable to A's basis) can never be claimed by anyone and is locked in `IdleCreditVault` permanently. All honest claimants (B and active AA/BB holders via `finalizeDefaultRecovery`'s NAV burn/mint) recover less than entitled — a quantified loss equal to `recoveredShare(phantomBasis)`. [10](#0-9) 

### Likelihood Explanation
Requires only ordinary user behavior: an instant-withdraw requester who is funded and claims, plus at least one still-unfunded instant requester in the same epoch, followed by a borrower default that epoch — none of which requires any privileged or malicious role; the attacker can simply be an ordinary tranche holder whose claimed receipt leaves stale basis behind. Partial instant-queue funding is an expected flow (`collectInstantWithdrawFunds` takes an arbitrary `_amount`), so the precondition is a routine sequence, not an edge case.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch records when the aggregate is paid out: iterate/track the request epoch (e.g., store `lastInstantWithdrawEpoch[_user]`) and decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount. Alternatively, maintain per-user instant request epoch analogous to `lastWithdrawRequest` and clear it on claim, mirroring `_clearWithdrawClaimForEpoch`. Ensure `instantWithdrawClaimsByEpoch` always equals the sum of unfunded/unclaimed instant receipts so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` never see stale basis.

### Proof of Concept
Foundry fork test (in `test/foundry/IdleCreditVault.t.sol` harness style):

```solidity
function testStaleInstantBasisDilutesDefaultRecovery() external {
    // setup: deposits, epoch running, users A and B
    address A = makeAddr("A"); address B = makeAddr("B");
    _depositWithUser(A, 100_000e6, true);
    _depositWithUser(B, 100_000e6, true);
    _startEpochAndCheckPrices(0);

    // both request instant withdraw of full balance in epoch N
    vm.prank(A); cdoEpoch.requestInstantWithdraw(...AA amount A...);
    vm.prank(B); cdoEpoch.requestInstantWithdraw(...AA amount B...);
    uint256 epoch = IdleCreditVault(address(strategy)).epochNumber();
    assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), 200_000e6);

    // CDO funds only A's request; pendingInstantWithdraws = 100k (B)
    // ... getInstantWithdrawFunds / collectInstantWithdrawFunds for A's amount ...
    vm.prank(A); cdoEpoch.claimInstantWithdrawRequest(); // A paid in full
    // leaked: instantWithdrawClaimsByEpoch[epoch] still == 200_000e6

    // borrower defaults in same epoch, manager finalizes with recoveredAmount R
    // _handleBorrowerDefault -> finalizeDefaultRecovery(R, source)
    uint256 basis = strategy.defaultPendingClaimBasis();
    // BUG: basis includes A's already-paid 100k -> recoveryPrice deflated
    // assert: B's claim < (100k * R_true / totalBasis_true)
    // assert: reserve dust == A's phantom share remains locked forever

    // also: any further claimInstantWithdrawRequest for A reverts via underflow
    vm.expectRevert();
    vm.prank(A); cdoEpoch.claimInstantWithdrawRequest();
}
```

Expected: `instantWithdrawClaimsByEpoch[epoch]` retains the claimed amount, `defaultRecoveryPrice` is diluted, and the reserve corresponding to the phantom basis is unclaimable — permanent freeze of recovered funds.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
