### Title
Stale confirmations from removed multisig members still count toward the confirmation threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` removes a member from `self.members` and deletes only the *requests they authored*, but it does not scan existing `confirmations` entries to strip that member's confirmation from requests authored by *other* members. `confirm()` counts `confirmations.len()` against `self.num_confirmations` without re-validating that every entry in the set still belongs to a current, live member.

### Finding Description
The binding that should hold is: `confirmations counted for a request == confirmations from currently live members`. `delete_member` breaks this equality.

Walk-through:
1. Multisig has members A, B, C with `num_confirmations = 2`.
2. A calls `add_request` to create request R (e.g., a `Transfer` or `AddKey` action). `add_request` inserts an empty `confirmations` set for R, keyed by `request_id`. [3](#0-2) 
3. B calls `confirm(R)`. Since `confirmations.len() + 1 (1) < num_confirmations (2)`, B's member string is inserted into the confirmations set for R, and R stays pending. [4](#0-3) 
4. Members later execute a separate multisig request removing B (`DeleteMember { member: B }`). `delete_member` only deletes requests where `r.member == B` (i.e., requests B authored) — R was authored by A, so R and its confirmations set (still containing B's stale entry) are left untouched. `self.members.remove(&member)` removes B from the live member set, but `self.confirmations` for R is never touched. [5](#0-4) 
5. B's access key is deleted from the account (`promise.delete_key`), so B can no longer act, but B's confirmation string is still present in the stored `HashSet<String>` for R.
6. Now only A (or any other live member) needs to call `confirm(R)` once more: `confirmations.len() (1) + 1 = 2 >= num_confirmations (2)`, so the request executes — with only 1 truly live-member confirmation (A) plus one stale/phantom confirmation from removed member B.

This effectively lowers the live-member threshold from `K` to `K-1` (or fewer, if multiple confirmers are later removed), for any request that was confirmed before the confirming member was removed.

### Impact Explanation
This breaks the "confirmations counted versus live members" custody binding explicitly called out as in-scope. A request (including `Transfer`, `AddKey` with full access permission, `FunctionCall`, `DeployContract`) can be executed by the multisig with fewer genuinely live/authorized confirmations than `num_confirmations` requires. Since multisig `Transfer` actions move NEAR out of the account and `AddKey`/`DeployContract` actions can grant control of the account, this is a threshold-bypass that can lead to unauthorized movement of NEAR funds or unauthorized takeover of the account — matching the Critical impact category ("a multisig request executed below threshold").

### Likelihood Explanation
No privileged actor, foundation intervention, or malicious validator is required — this only needs: (a) a request created and partially confirmed by a legitimate member, (b) a routine `DeleteMember` action (e.g., normal key rotation/offboarding, or removing a compromised key) executed afterward, and (c) one more `confirm` call from any remaining live member. Multisig member turnover (revoking a lost/compromised key) is an ordinary, expected operational event, making the stale-confirmation window realistically reachable, not merely theoretical.

### Recommendation
When removing a member in `delete_member`, iterate over all entries in `self.confirmations` (not just requests authored by the removed member) and remove the removed member's string from every confirmation set. Alternatively, validate confirmers against current membership at `confirm`-time (i.e., recompute confirmations count by filtering the stored set against `self.members` before comparing to `num_confirmations`), so a removed member's earlier confirmation can never count toward execution.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. As A: `add_request` for `{receiver_id: multisig, actions: [{"type":"Transfer","amount": "..."}]}` → `request_id = 0`.
3. As B: `confirm(0)` → confirmations = `{B}` (1 of 2), request pending.
4. As A+C (2 confirmations): `add_request_and_confirm`/`confirm` a `DeleteMember { member: B }` request → executes, removing B from `self.members` and deleting B's access key; request 0's confirmations set (`{B}`) is untouched because request 0 was authored by A, not B.
5. As A: `confirm(0)` → `confirmations.len() (1) + 1 = 2 >= num_confirmations (2)` → request 0 (the `Transfer`) executes, funded on the strength of A's confirmation plus B's stale, now-invalid confirmation, i.e., only 1 truly live confirmation for a threshold of 2.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
