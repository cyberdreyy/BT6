### Title
Router discovery cache (and its TLSData) is keyed only by time, not by `RunnerConfig`, allowing cross-config TLS material reuse - (File: `router/client.go`)

### Summary
`Client.getRouterDiscovery` caches a single `*common.RouterDiscovery` (`c.disco`) on the `Client` struct with only a time-based TTL guard, even though it is called per-`RunnerConfig` and the discovery result is config-specific. `parseJobResponse` then unconditionally stamps `response.TLSData = disco.TLSData` onto every job produced by that `Client` instance, so if one `Client` instance is used to poll for more than one `RunnerConfig`/token within the 1-hour TTL, a job requested under config B can receive TLS identity material that was actually discovered/cached while servicing config A.

### Finding Description
`getRouterDiscovery` guards its cache purely by `c.discoExpiresAt`: [1](#0-0) 
There is no check that the cached `c.disco` was obtained for the same `config` as the current caller — the `config` parameter is used only to call `c.delegate.GetRouterDiscovery(ctx, config)` on a cache miss, never to validate a cache hit. The fact that `GetRouterDiscovery` accepts a `RunnerConfig` at all (see the `Delegate` interface) indicates its result — including `TLSData` — is intended to be specific to that identity/token, not a global, config-agnostic value: [2](#0-1) 

`RequestJob` calls `getRouterDiscovery(ctx, config)` for whatever `config` it was invoked with, then unconditionally passes the (possibly stale, possibly cross-config) `disco` into `parseJobResponse`: [3](#0-2) [4](#0-3) 

The critical line is: [5](#0-4) 
which attaches `disco.TLSData` to the job regardless of which `config` requested it.

Note: the security-audit prompt names `router/internal/wstunnel/client.go` as the location of `parseJobResponse`/the cache — that file only contains `DialerForGRPC`/`NetConn` helpers and has no `parseJobResponse`, no `disco`, and no TLS caching logic: [6](#0-5) 
The actual code in question lives in `router/client.go`, as analyzed above.

**Unresolved architectural question:** whether a single `*Client` (created via `NewClient`, `router/client.go:77-87`) is ever reused across multiple distinct `RunnerConfig`/token identities in production. I was not able to locate, within the available index, the production call site that constructs `router.Client` and wires it into the multi-runner polling loop (the only `NewClient(` matches found were the constructor itself and test files). If, as is standard in `gitlab-runner`'s architecture, a single `network.GitLabClient`-style delegate/`Client` serves many `[[runners]]` entries from one process, this cache-sharing bug is reachable exactly as described. If instead a distinct `Client` is instantiated per `RunnerConfig`, the vulnerability does not manifest because `c.disco` would never span two identities.

### Impact Explanation
If reachable, a runner process configured with multiple `[[runners]]` tokens/projects sharing one `Client` would attach one project's cached router `TLSData` (CA chain / client auth cert / client auth key, per `common/spec/spec.go:536-540`) to jobs pulled for a different project's token, for up to `discoveryTTL` = 1 hour. This is a genuine identity-scoping violation: TLS/cert material tied to config A's discovery could be presented on behalf of config B's job, which is exactly the "TLS/cert material must be scoped per-config, never shared across differing RunnerConfig/token identities" invariant the prompt describes.

### Likelihood Explanation
Preconditions: (1) a single `Client` instance must in fact be shared to serve `RequestJob` for two or more different `RunnerConfig` objects, and (2) the second config's poll must land within the first config's 1-hour discovery TTL window — both quite plausible in any multi-runner-token GitLab Runner deployment, since 1 hour is long relative to typical polling intervals (seconds). No attacker-controlled CI job input is required to trigger this; it is a structural/timing race in the runner's own polling logic, not something a pipeline author needs to manipulate. This weakens the "attacker action/data" requirement in the audit rules — this is not exploitable by an unprivileged pipeline author; it is a runner-operator-configuration-dependent internal-caching correctness bug, not a user-triggered exploit path.

### Recommendation
Key the discovery cache by `RunnerConfig` identity (e.g., token/short token hash) instead of a single struct field, or instantiate one `router.Client` per `RunnerConfig` so `c.disco`/`c.discoExpiresAt` can never span two identities. At minimum, `getRouterDiscovery` should validate that the cached discovery corresponds to the `config` passed in before returning it on a "hit".

### Proof of Concept
```go
func TestGetRouterDiscovery_DoesNotLeakAcrossConfigs(t *testing.T) {
    delegate := new(mockDelegate)
    configA := common.RunnerConfig{RunnerCredentials: common.RunnerCredentials{Token: "tokenA"}}
    configB := common.RunnerConfig{RunnerCredentials: common.RunnerCredentials{Token: "tokenB"}}

    discoA := &common.RouterDiscovery{ServerURL: "routerA", TLSData: common.TLSData{AuthCert: "certA"}}
    discoB := &common.RouterDiscovery{ServerURL: "routerB", TLSData: common.TLSData{AuthCert: "certB"}}

    delegate.On("GetRouterDiscovery", mock.Anything, configA).Return(discoA)
    delegate.On("GetRouterDiscovery", mock.Anything, configB).Return(discoB)

    c := NewClient(delegate, "", "ua")

    gotA := c.getRouterDiscovery(context.Background(), configA)
    gotB := c.getRouterDiscovery(context.Background(), configB) // still within TTL

    // FAILS today: gotB == gotA (discoA), i.e. configB gets configA's TLSData
    assert.Equal(t, discoB.TLSData, gotB.TLSData)
}
```
Expected assertion failure on current code demonstrates that the second call, made before `discoveryTTL` expiry with a *different* `config`, returns the first config's cached `disco` (and thus `TLSData`) instead of re-resolving for `configB`.

Given the unresolved question of whether `Client` is actually shared across multiple `RunnerConfig` identities in the production wiring (which I could not confirm from the indexed code), I present this as a **conditionally valid** finding — the caching logic itself is verifiably identity-unaware, but real-world exploitability depends on deployment/instantiation details not fully confirmed here.

func parseJobResponse(job *rpc.GetJobResponse, responseMD metadata.MD, disco *common.RouterDiscovery, requestCorrelationID string, config common.RunnerConfig) (*spec.Job, bool) {
	if len(job.JobResponse) == 0 {
		return nil, true
	}
	var response spec.Job
	if err := json.Unmarshal(job.JobResponse, &response); err != nil {
		config.Log().WithError(err).Error("json.Unmarshal()")
		return nil, false
	}
	response.TLSData = disco.TLSData
	if correlationIDs := responseMD[requestIDMetadataKey]; len(correlationIDs) > 0 {
		requestCorrelationID = correlationIDs[0]
	}
	response.JobRequestCorrelationID = requestCorrelationID
	return &response, true

func (c *Client) getRouterDiscovery(ctx context.Context, config common.RunnerConfig) *common.RouterDiscovery {
	c.mu.Lock()
	defer c.mu.Unlock()
	if c.discoExpiresAt.After(time.Now()) {
		c.metrics.recordCacheEvent(cacheHit)
		return c.disco
	}
	c.metrics.recordCacheEvent(cacheMiss)
	c.disco = c.delegate.GetRouterDiscovery(ctx, config)
	c.discoExpiresAt = time.Now().Add(discoveryTTL)
	if c.disco != nil {
		config.Log().Info("Using job router at " + c.disco.ServerURL)
	}
	return c.disco
}

package wstunnel

import (
	"context"

	"github.com/gorilla/websocket"

// DialerForGRPC can be used as an adapter between "ws"/"wss" URL scheme that the websocket library wants and
// gRPC target naming scheme.
func DialerForGRPC(readLimit int64, dialer websocket.Dialer, requestHeader http.Header) func(context.Context, string) (net.Conn, error) {
	return func(ctx context.Context, address string) (net.Conn, error) {
		conn, _, err := dialer.DialContext(ctx, address, requestHeader) //nolint: bodyclose
		if err != nil {
			return nil, err
		}
		if readLimit != 0 {
			conn.SetReadLimit(readLimit)
		}
		return NetConn(conn), nil
	}
}
