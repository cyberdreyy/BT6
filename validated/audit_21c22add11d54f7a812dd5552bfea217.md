### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing requests to execute below quorum - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in the multisig contract removes a departing member from the member set and deletes only the *requests that member originated*, but it never scrubs that member's confirmations recorded on requests originated by *other* members. `confirm()` later counts the size of the stored confirmation set against `num_confirmations` without verifying every entry still belongs to a current member, so a stale confirmation from a removed member can push a request over the threshold even though only `num_confirmations - 1` live members actually agreed.

### Finding Description
`delete_member` only cleans up requests keyed by `r.member == member` (requests the removed member created) and their confirmations: [1](#0-0) 

It does not iterate `self.confirmations` to strip the removed member's identity (`member.to_string()`) from confirmation sets belonging to requests created by *other* members. Those `HashSet<String>` entries persist untouched.

`confirm()` then authorizes execution purely by counting set size: [2](#0-1) 

There is no re-validation that every string in `confirmations` corresponds to a member still present in `self.members`. The intended binding is:

`live_member_confirmations(request) >= num_confirmations` ⇒ execute

but the actual enforced binding is:

`stored_confirmations(request).len() >= num_confirmations` ⇒ execute

where `stored_confirmations` can contain entries for accounts/keys no longer in `self.members`. This is the same class of issue as the Hats Protocol linked-tophat bug: an admin action meant to strip a party's ongoing influence (linking a tophat to reset its `eligibility`/`toggle`, or here, removing a misbehaving multisig member) fails to fully unwind a stale grant of authority, leaving the removed party's prior approval still binding.

The v1 `multisig/src/lib.rs` contract has the analogous gap: `DeleteKey` only removes confirmations/requests where `r.signer_pk == pk` (requests the deleted key created), not confirmations that key placed on other members' requests: [3](#0-2) 

### Impact Explanation
This crosses the "confirmations counted versus live members" authorization boundary called out in scope. A request (e.g., a `Transfer` of NEAR funds, an `AddKey`, or a `DeployContract`) can be executed with fewer genuinely live confirmations than `num_confirmations` requires, because a removed member's stale approval is still tallied. This directly matches the Critical impact category: "a multisig request executed below threshold." Funds can be moved, or full-access keys added, by effectively less than the required quorum of live members.

### Likelihood Explanation
This requires no privileged access beyond being a legitimate multisig participant at the time confirmations were placed — a normal, expected workflow: a member confirms a pending request, then is later removed (e.g., for misbehavior, offboarding, or key rotation) via a separate `DeleteMember`/`DeleteKey` request. Any remaining member simply needs to add one more confirmation to the still-pending request to trigger execution using the removed member's leftover confirmation. No malicious deployment, redeploy, or out-of-scope actor is needed — only the ordinary sequence of confirm → remove-member → confirm.

### Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate all pending requests' confirmation sets and remove any confirmation entry belonging to the departing member's identity (not just requests the member originated). Alternatively, when checking the threshold in `confirm()`, filter the stored confirmation set against `self.members` before comparing its length to `num_confirmations`, so only confirmations from currently-live members count.

### Proof of Concept
1. Deploy multisig with members `A, B, C, D` and `num_confirmations = 3` via `MultiSigContract::new`.
2. `A` calls `add_request_and_confirm` to create request `R` (e.g., `Transfer` of contract funds to an attacker-controlled account) — confirmations(`R`) = `{A}`.
3. `B` calls `confirm(R)` — confirmations(`R`) = `{A, B}` (2/3, not yet executed).
4. Separately, a quorum executes a `DeleteMember { member: B }` request (e.g., `B` was misbehaving and is being offboarded). `delete_member` (`multisig2/src/lib.rs:356-379`) removes `B` from `self.members` and deletes only requests `B` originated — `R` (created by `A`) is untouched, and `B`'s confirmation entry inside `confirmations(R)` is never removed.
5. `C` calls `confirm(R)`. `confirmations(R).len() + 1 = 3 >= num_confirmations (3)` — see `confirm()` at `multisig2/src/lib.rs:292-315` — so `execute_request(R)` runs and the transfer executes, even though only `A` and `C` are live members who actually approved it (2 live confirmations instead of the required 3).

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
