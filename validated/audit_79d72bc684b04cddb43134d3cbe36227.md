### Title
Missing `whenNotPaused` on `withdraw`/`getReward`: staking is frozen but funds still leave - (File: contracts/StakingRewards.sol)

### Summary
`StakingRewards` (the Synthetix-style contract used to stake tranche tokens and pay rewards, with `stakeFor` wired to IdleCDO's `rewardsDistribution`) guards `_stake` with `whenNotPaused`, but `withdraw`, `getReward`, and `exit` are callable while the contract is paused — the same bug class as the GPToke `collectRewards` finding.

### Finding Description
In `contracts/StakingRewards.sol`:

- `_stake` is gated: `function _stake(...) internal nonReentrant whenNotPaused updateReward(_user)` (line 92).
- `withdraw` (line 100), `getReward` (line 108), and `exit` (lines 117–120) have only `nonReentrant`/`updateReward` — no pause check.
- `pause()`/`unpause()` are owner-controlled (`Pausable`), so pausing only blocks new stakes, not exits.

The identical pattern exists in `contracts/DelegateStakingRewardsIDLE.sol` (lines 89, 98, 107, 117–120).

When the owner pauses the contract (e.g., in response to an incident affecting tranche tokens or the reward pipeline), any unprivileged staker can still:

1. Call `withdraw(_balances[msg.sender])` to pull out their full staked `stakingToken` (tranche tokens).
2. Call `getReward()` to drain accrued `rewardsToken`, or `exit()` to do both atomically.

### Impact Explanation
Pause is intended to freeze fund movements, but stakers can fully exit principal and rewards during the pause window. If pause was triggered by a security event (e.g., a compromised rewards distribution or a bad tranche-token state), users extract stake and rewards while the protocol is meant to be frozen, and `updateReward` still crystallizes `rewards[account]` on every call. Loss is bounded to each user's own stake plus accrued rewards — this is a protocol-behavior inconsistency / emergency-control bypass, not an inflation or theft-of-others' funds bug, matching the Medium severity of the source report.

### Likelihood Explanation
Requires the owner to pause while users hold stake and accrued rewards — a plausible emergency scenario, which is exactly when the missing guard matters. No attacker privilege is needed; any staker can call `exit()`.

### Recommendation
Add `whenNotPaused` to the exit paths (or at minimum to `getReward`, mirroring the GPToke recommendation):

```solidity
function withdraw(uint256 amount) public nonReentrant whenNotPaused updateReward(msg.sender) { ... }
function getReward() public nonReentrant whenNotPaused updateReward(msg.sender) { ... }
```

Apply the same fix to `DelegateStakingRewardsIDLE.sol`. If intentional that users can always exit principal, at least gate `getReward` so reward distribution halts during a pause.

### Proof of Concept
Foundry-style PoC sketch:

```solidity
// user stakes tranche tokens
vm.prank(user);
stakingRewards.stake(amount);

// rewards accrue / owner pauses due to an incident
vm.prank(owner);
stakingRewards.pause();

// stake is blocked
vm.prank(user);
vm.expectRevert("Pausable: paused");
stakingRewards.stake(amount);

// but exits still work — principal and rewards leave during pause
vm.prank(user);
stakingRewards.exit(); // withdraw(balance) + getReward() succeed
assertEq(stakingToken.balanceOf(user), amount);
```
