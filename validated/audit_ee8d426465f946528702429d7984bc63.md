### Title
Scheduled `updateUIMultiplier` corporate-action rebases can be front-run by transferring balance in just before `effectiveAt` and out right after - ([File: crates/common/precompiles/src/b20_asset/logic/v2.rs])

### Summary
The B20 `AssetV2` precompile implements a rebasing "Scaled UI Amount" mechanism (ERC-8056) where an operator schedules a `newMultiplier` that becomes effective at a public `effectiveAt` timestamp. Any account holding raw balance at that timestamp instantly gets its externally-visible (`scaledBalanceOf`/`balanceOfUI`) value multiplied, with no minimum holding period. This mirrors the GPToke `addWETHRewards()` bug class: a value-distribution event that applies instantly/uniformly to whoever holds balance at the trigger moment, letting capital move in right before the event and out right after to capture a disproportionate share of the appreciation.

### Finding Description
`update_ui_multiplier` schedules a pending multiplier and a future `effective_at` timestamp, guarded only by the operator role, and stores it in plain, publicly-readable storage: [1](#0-0) 

The `effective_at`/`multiplier` become externally readable at any time via `newUIMultiplier()`/`effectiveAt()`, and the multiplier "lazily" flips once `now >= effective_at`: [2](#0-1) 

All UI-facing balance/supply views scale uniformly by this multiplier with no snapshot or vesting mechanism tied to how long a holder has held raw balance: [3](#0-2) [4](#0-3) 

The ABI documentation confirms the intended use case is exactly a value-distribution/corporate-action event ("splits, reinvested dividends"): [5](#0-4) 

The golden test demonstrates the exact mechanic: a holder's `balanceOfUI` doubles the instant `effectiveAt` is reached, purely because they held raw balance at that moment: [6](#0-5) 

Because `effectiveAt` is scheduled in advance and publicly readable (unlike GPToke's fully-instant `addWETHRewards`, this is even more predictable — no mempool race is even required), any unprivileged token holder can acquire raw balance (via an ordinary `transfer`/swap) shortly before `effectiveAt`, hold it through the rebase, and move it out immediately after, capturing the full proportional increase in scaled/UI value that the multiplier represents — exactly analogous to an attacker locking `GPToke` stake right before `addWETHRewards()` and unlocking right after the minimum duration.

### Impact Explanation
When an operator uses `updateUIMultiplier` to reflect a real economic event (e.g., interest/yield accrual represented by the multiplier), value that should accrue to holders who bore exposure over the accrual period is instead redirectable to short-term capital that only needs to hold raw balance at the single `effective_at` instant. This lets sophisticated actors extract a disproportionate share of the distributed value, diluting the effective yield captured by genuine long-term holders — a fund-appropriation / unjust-enrichment issue affecting an unprivileged B20 asset holder's economic position.

### Likelihood Explanation
High: `effective_at` and `newMultiplier` are public on-chain state readable well before maturity via `newUIMultiplier()`/`effectiveAt()`, so the attack requires no front-running skill or mempool visibility — any holder can simply time an ordinary transfer to arrive at or before the known maturity timestamp and exit right after.

### Recommendation
Introduce a holding-period/snapshot mechanism for multiplier-based value distributions (e.g., checkpoint balances prior to scheduling, or accrue value pro-rata over the vesting window rather than applying the full multiplier atomically at `effectiveAt`), consistent with the recommendation in the referenced report to use a time-based distribution model rather than an instantaneous one.

### Proof of Concept
1. Operator calls `updateUIMultiplier(newMultiplier, effectiveAt)` (visible on-chain immediately, per `crates/common/precompiles/src/b20_asset/logic/v2.rs:970-1020`).
2. Attacker, having had no raw balance during the accrual period, acquires a large raw balance via an ordinary transfer just before `effectiveAt`.
3. At `effectiveAt`, `effective_multiplier` flips (`crates/common/precompiles/src/b20_asset/logic/v2.rs:928-939`), and `scaledBalanceOf`/`balanceOfUI` for the attacker's freshly-acquired raw balance instantly reflects the full new multiplier, as shown in the golden test `golden_balance_of_ui_and_total_supply_ui_scale_by_effective_multiplier` (`crates/common/precompiles/tests/b20_asset_v2_golden.rs:2532-2570`).
4. Attacker immediately transfers the raw balance back out, having captured the rebase gain without bearing exposure during the accrual window.

```rust
    fn multiplier(&self, token: &B20AssetToken<S, A>) -> Result<U256> {
        self.effective_multiplier(token)
    }

    fn effective_multiplier(&self, token: &B20AssetToken<S, A>) -> Result<U256> {
        let now = token.accounting().timestamp()?;
        let effective_at = token.accounting().pending_effective_at()?;
        if effective_at != 0 && now >= U256::from(effective_at) {
            let pending = token.accounting().pending_multiplier()?;
            // Both setters reject zero, so a stored pending is never zero. Do not fall back to WAD:
            // the Solidity reference also returns the raw pending value.
            debug_assert!(pending != 0, "matured pending multiplier must be non-zero");
            return Ok(U256::from(pending));
        }
        token.accounting().multiplier()
    }
```

```rust
    fn update_ui_multiplier(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        new_multiplier: U256,
        effective_at: U256,
        privileged: bool,
    ) -> Result<()> {
        let now = token.accounting().timestamp()?;
        self.ensure_operator_role(token, caller, privileged)?;
        if new_multiplier.is_zero() || new_multiplier > Self::MAX_UI_MULTIPLIER {
            return Err(BasePrecompileError::revert(IB20Asset::InvalidMultiplier {}));
        }
        if effective_at <= now {
            return Err(BasePrecompileError::revert(IB20Asset::EffectiveAtInPast {
                effectiveAt: effective_at,
            }));
        }
        if effective_at > U256::from(u64::MAX) {
            return Err(BasePrecompileError::revert(IB20Asset::EffectiveAtTooFar {
                effectiveAt: effective_at,
            }));
        }

        let pending_effective_at = token.accounting().pending_effective_at()?;
        // A live pending blocks a new schedule.
        if U256::from(pending_effective_at) > now {
            return Err(BasePrecompileError::revert(IB20Asset::UIMultiplierUpdateExists {
                effectiveAt: U256::from(pending_effective_at),
            }));
        }
        // Fold a matured pending into the current multiplier before overwriting it.
        if pending_effective_at != 0 {
            let matured = U256::from(token.accounting().pending_multiplier()?);
            token.accounting_mut().set_multiplier(matured)?;
        }

        let old = token.accounting().multiplier()?;
        // Narrowing is safe because the guards above enforce the storage field bounds.
        token
            .accounting_mut()
            .set_pending_and_effective_at(new_multiplier.to::<u128>(), effective_at.to::<u64>())?;
        token.accounting_mut().emit_event(
            IB20Asset::UIMultiplierUpdated {
                oldMultiplier: old,
                newMultiplier: new_multiplier,
                effectiveAtTimestamp: effective_at,
            }
            .encode_log_data(),
        )
    }
```

```rust
#[test]
fn golden_balance_of_ui_and_total_supply_ui_scale_by_effective_multiplier() {
    let mut s = fresh();
    seed(&mut s, |t| {
        fund(t, ALICE, u(100));
        give_role(t, operator_role(), ADMIN);
    });
    warp(&mut s, u(1));
    op(
        &mut s,
        ADMIN,
        FakePolicyAccounting::new(),
        IB20Asset::updateUIMultiplierCall {
            newMultiplier: B20AssetStorage::WAD * u(2),
            effectiveAt: u(1_000),
        }
        .abi_encode(),
    )
    .unwrap();

    let pre_maturity = op(
        &mut s,
        ALICE,
        FakePolicyAccounting::new(),
        IB20Asset::balanceOfUICall { account: ALICE }.abi_encode(),
    )
    .unwrap();
    assert_eq!(pre_maturity, Bytes::from(u(100).abi_encode()));

    warp(&mut s, u(1_000));
    let post_maturity = op(
        &mut s,
        ALICE,
        FakePolicyAccounting::new(),
        IB20Asset::balanceOfUICall { account: ALICE }.abi_encode(),
    )
    .unwrap();
    assert_eq!(post_maturity, Bytes::from(u(200).abi_encode()));
```
