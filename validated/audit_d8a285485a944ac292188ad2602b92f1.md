### Title
Miner can indefinitely refresh `last_activity_time` via unconfirmed pre-commits/reorg attempts, wedging the inactivity fallback and stalling the chain - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_latest_block_in_tenure` calls `signer_db.update_last_activity_time()` whenever a competing/conflicting proposal arrives at the same or lower height, as long as either (a) the existing signed block is still "fresh" (`reorg_attempts_activity_timeout`), or (b) there is a fresh but never-signed `PreCommitted` block (`tenure_last_block_proposal_timeout`). Because `is_timed_out` (in `chainstate/v1.rs` and `chainstate/v2.rs`) measures inactivity purely as `now - last_activity_time`, a single miner that repeatedly submits new, locally-valid-but-never-signed block proposals at the same height can keep resetting this timer forever, without ever producing a block that reaches the 70% signature threshold. [1](#0-0) [2](#0-1) 

### Finding Description
This mirrors the flash-loan pattern in the report: an actor manufactures transient, "legitimate-looking" state (open a trove with borrowed collateral → get counted for rewards → close in the same transaction) to repeatedly extract value from a check that assumes real, lasting participation. Here the analogous transient state is a `PreCommitted` block: it requires no signature and no majority, only that this signer's local node validates the proposal OK (`mark_pre_committed`), which stamps `approved_time`. As long as the miner submits a new proposal (e.g. bump `timestamp`) faster than `tenure_last_block_proposal_timeout` (default 30s) or, once one block is signed, faster than `reorg_attempts_activity_timeout` (default 200s), each new submission satisfies `is_fresh_pre_commit` and calls `update_last_activity_time(now)` again: [3](#0-2) 

`is_timed_out` in both v1 and v2 sortition state derives its verdict solely from `last_activity_time` vs. `block_proposal_timeout` (default 120s), and explicitly treats the miner as never timed out if it has produced a signed block at all — but the inactivity clock itself can be held open indefinitely by never-signed pre-commits/rejected reorg attempts: [4](#0-3) [5](#0-4) 

`check_miner_inactivity` in `v0/signer_state.rs` is the only path that lets the signer set fall back to a prior tenure's miner; it is gated entirely on `SortitionState::is_timed_out` returning `true`: [6](#0-5) 

The developers were already aware that pre-commits must not be treated as "signed" for timeout purposes (fixing the opposite failure mode where a stalled pre-commit could block fallback forever): [7](#0-6) 

However, the fix left in place the companion mechanism that treats *any* fresh pre-commit or reorg attempt as valid "activity," resetting the clock on every single evaluation — without any bound on how many times, or any requirement that the miner ever make real progress (reach 70% signatures). A miner who unilaterally controls its own tenure's block proposals can keep the tenure "active" from the point of view of this check forever, purely by resubmitting slightly different, locally-valid proposals at the same height, without any collusion, majority, or actual chain progress.

### Impact Explanation
This is a liveness wedge matching the "High" impact category: a signer (indeed, the whole signer set, since each signer independently derives and refreshes its own `last_activity_time`) can be kept from ever timing out an unproductive/malicious miner and falling back to a prior, live miner. Since `is_timed_out` never fires, `check_miner_inactivity` never demotes the current miner, and the chain can stall indefinitely at that tenure boundary even though a perfectly good prior miner is available and canonical.

### Likelihood Explanation
Only the single sortition-winning miner is required — no majority of signers, no additional keys, and no StackerDB/transport exploitation, only ordinary proposal gossip. The miner only needs to keep constructing new, syntactically/semantically valid Nakamoto blocks at the same height (trivial: bump the header timestamp) faster than the relevant timeout window, and to avoid ever letting one reach the 70% pre-commit/signature threshold (e.g., by not broadcasting widely enough, or by splitting delivery so no single block ever accumulates enough weight). This requires only miner-side control over proposal timing/broadcast, which is well within a single miner's capability.

### Recommendation
Bound the number of times / total duration for which unconfirmed pre-commits or rejected reorg attempts can refresh `last_activity_time` for a given tenure — e.g., track the tenure's *first* proposal time and enforce an absolute deadline (analogous to `first_proposal_burn_block_timing`) after which `is_timed_out` fires regardless of how recently the last (still-unsigned) proposal arrived. Alternatively, only count a proposal as "activity" if it plausibly could still reach the signature threshold (e.g., if no proposal from this tenure has ever failed to reach threshold within its own freshness window), so that a miner cannot manufacture indefinite fresh-but-never-completed pre-commits.

### Proof of Concept
1. Miner M wins the sortition for tenure T.
2. M proposes block B0 at height H. Signers validate B0 OK and `mark_pre_committed(B0)`, stamping `approved_time`. M intentionally avoids gathering the 70% pre-commit/signature threshold (e.g., broadcasts to only a rotating subset of signers).
3. Before `tenure_last_block_proposal_timeout` (30s default) elapses, M proposes B1 at the same height H with a bumped `timestamp` (different `signer_signature_hash`). Each signer validates B1 OK; `check_latest_block_in_tenure` sees the still-fresh pre-commit of B0/B1 and calls `signer_db.update_last_activity_time(T, now)` [8](#0-7) .
4. M repeats step 3 indefinitely, always resubmitting before the freshness window expires.
5. `SortitionState::is_timed_out` for tenure T never observes `elapsed > block_proposal_timeout` because `last_activity_time` keeps being refreshed [9](#0-8) .
6. `check_miner_inactivity` never falls back to the prior sortition's miner, and the tenure never produces a globally signed block — the chain stalls at this tenure indefinitely even though a valid alternative miner exists.

    /// Check if the given sortition identified by its ConsensusHash has timed out based on current signed blocks
    /// and the time at which the burn block for it was first recorded in the provided signerdb
    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {

                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()

Do not let a block that was only pre-committed suppress the miner inactivity timeout. A pre-commit was treated as a signed block, so signers that pre-committed to a tenure-start block which never reached the pre-commit threshold could never time the miner out and fall back to the prior tenure, stalling the chain until the next burn block.
