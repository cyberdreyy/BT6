### Title
Signer can re-sign a conflicting block at a height it already signed once the prior signature goes stale and the node is unreachable/behind - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_pre_commit` is the only place a v0 signer converts pre-commit weight into an actual block signature [1](#0-0) . The "one signed block per height per tenure" invariant is strongly enforced only once, at proposal arrival, via the `DuplicateBlockFound` check inside `check_proposal` [2](#0-1) . At the later, consequential moment — the pre-commit-threshold check that actually produces the signature — that invariant is downgraded to a purely time-based "freshness" heuristic plus a remote node liveness check, both of which a slow/unreachable node and elapsed time can defeat, allowing the signer to sign a second, conflicting block at a height (and tenure) it already signed.

### Finding Description
When pre-commit weight crosses threshold, `handle_block_pre_commit` looks up all previously *signed* conflicts at height ≥ the proposed block's height, in any tenure, via `get_signed_conflicts` [3](#0-2) . It then computes a `freshness_cutoff` purely from wall-clock time (`tenure_last_block_proposal_timeout`) [4](#0-3) .

For conflicts still judged "fresh," the code asks the node whether the conflicting tenure is still canonical and still live (`conflict_still_blocks`) before refusing to sign [5](#0-4) . But for a conflict in the block's *own* tenure that has gone "stale" (no fresh endorsement within the timeout), the guard collapses to a single question: does the node's current view of that tenure's tip already reach or exceed the proposed height?

```rust
if conflicts.iter().any(|conflict| {
    conflict.consensus_hash == block_info.block.header.consensus_hash
        && !self.reorg_permit_stands(stacks_client, conflict)
}) {
    match stacks_client.get_tenure_tip(&block_info.block.header.consensus_hash) {
        Ok(tip) => {
            let tip_height = tip.anchored_header.height();
            if tip_height >= block_info.block.header.chain_length {
                // refuse to sign
                return;
            }
        }
        Err(e) => {
            // "Treating the tenure as unconfirmed." — falls through to SIGN
        }
    }
}
``` [6](#0-5) 

If the node cannot answer (unreachable, timing out, momentarily behind) or simply hasn't yet observed the earlier signed block landing at that height, the signer proceeds straight to `SIGN: mark_locally_accepted, handle_block_signature, broadcast acceptance` [7](#0-6) , producing a signature over a *different* block at a height it already signed once, in the same tenure.

The staleness gate itself is a purely local timer comparison (`last_endorsed > freshness_cutoff`) with no cross-check against whether the rest of the signer set has actually abandoned the first block — a network delay or a slow signer is functionally indistinguishable from an abandoned block. The code's own documentation acknowledges this is a known blind spot rather than a proposal-time-equivalent guard: "the DuplicateBlockFound check that would catch a second block in the same tenure lives in `check_proposal` and runs only at proposal arrival, never again" [2](#0-1) . Consistent with that, `should_reevaluate_reject_reason` treats `DuplicateBlockFound` as a terminal, non-re-evaluable rejection at proposal time [8](#0-7) , i.e. the strong check exists only on the proposal path, and the signing path relies on the weaker fallback shown above.

This is structurally the same bug class as the Craft CMS report: a strict invariant/permission is enforced at one entry point (`check_proposal` / `actionMoveFolder`'s peer check) but the equivalent, more consequential cascading action (`handle_block_pre_commit`'s SIGN step / `actionDeleteFolder`'s cascade delete) only re-derives a weaker approximation of that guarantee, which can be bypassed via timing and a slow/unreachable dependency (the stacks-node) rather than any cryptographic or majority-vote break.

### Impact Explanation
This breaks the safety property that a signer never puts a second signature over a conflicting block at a height it already signed in the same tenure — the "one-per-height" equality. This falls squarely in the Critical bucket: "a signer signing an invalid, non-canonical, or conflicting block." A single misbehaving/adaptive miner producing two different block bodies at the same height, spaced far enough apart in time, can get an individual signer to double-sign; contributed across multiple signers under similar network conditions, this directly threatens chain-fork safety, which the pre-commit/threshold design is meant to prevent.

### Likelihood Explanation
Reachable by a single miner (one StackerDB slot) without needing any other signer's key, majority collusion, or local access: propose block A at height H, let its pre-commit/signature go stale (wait past `tenure_last_block_proposal_timeout`), then propose block B at the same height H in the same tenure. The window in which the node is unreachable, slow, or simply hasn't yet observed A landing (`get_tenure_tip` returning below H, or erroring) is a realistic, commonly-occurring operational condition (node restarts, RPC hiccups, or A never actually making it into the chain), not a contrived edge case.

### Recommendation
Do not let a purely local, time-based "staleness" heuristic combined with an unreachable/lagging node's tip answer stand in for the same strength of duplicate-detection applied at proposal time. Either: (1) persist and re-check the `DuplicateBlockFound`-equivalent decision at signing time regardless of conflict freshness or node reachability (fail closed — refuse to sign — on node errors instead of treating the tenure as "unconfirmed" and proceeding to sign), or (2) require positive confirmation from the node that the earlier conflicting block is provably dead (e.g., via `conflict_still_blocks`'s canonical/live derivation) before permitting a stale, same-tenure conflict to be overridden, closing the asymmetry between the proposal-time and signing-time enforcement of the one-per-height invariant.

### Proof of Concept
1. Miner proposes block A at height H in tenure T; signer set exchanges pre-commits but does not reach the 70% signing threshold quickly (or does, but the block never makes it to the node) — Signer S locally signs A and records it via `mark_locally_accepted`/`add_block_signature`.
2. Miner waits longer than `tenure_last_block_proposal_timeout` (so `last_endorsed` for A's conflict record ages past `freshness_cutoff`), then proposes a different block B, also at height H in tenure T (e.g., built on the same parent but with different transactions).
3. B passes `check_proposal`/validation and reaches the pre-commit threshold at Signer S. `get_signed_conflicts` returns A as a same-tenure, stale conflict [9](#0-8) .
4. At the moment S evaluates the same-tenure branch, S's `stacks_client.get_tenure_tip` call either errors (node restart/RPC hiccup) or returns a tip below H because the node has not yet processed A [10](#0-9) .
5. S proceeds to `SIGN` and broadcasts a signature over B [11](#0-10) , despite already holding a signature over the conflicting block A at the same height in the same tenure.
