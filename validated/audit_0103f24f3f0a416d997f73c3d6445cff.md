## Title
Stale/evicted builder payments are re-paid unconditionally (double-payment / quorum-bypass) in `apply_parent_execution_payload` - (File: specs/gloas/beacon-chain.md)

### Summary
`apply_parent_execution_payload` settles a proposer's committed builder payment via `settle_builder_payment` when the parent block is within the current or previous epoch. When the parent block is *older* than the previous epoch, the function falls back to unconditionally appending `parent_bid.value` to `state.builder_pending_withdrawals`, regardless of whether that payment was already resolved (paid or discarded) by the periodic epoch-processing routine `process_builder_pending_payments`. This breaks the invariant that a given builder payment is settled exactly once and only when quorum (sufficient attester weight) was reached.

### Finding Description
`process_builder_pending_payments` runs unconditionally every epoch as part of `process_epoch` [1](#0-0) . It evaluates `state.builder_pending_payments[:SLOTS_PER_EPOCH]` (the lower half of the 2×`SLOTS_PER_EPOCH`-length buffer), appending a withdrawal only `if payment.weight >= quorum`, and then unconditionally rotates the buffer, shifting the upper half down and zeroing the upper half: [2](#0-1) 

Separately, `apply_parent_execution_payload` (called once per block, for the immediately preceding beacon block as "parent") settles the same payment using `settle_builder_payment`, which pays out unconditionally if `payment.withdrawal.amount > 0` (no quorum check at all) when the parent falls in the current or previous epoch: [3](#0-2) [4](#0-3) 

If, however, the parent block predates the previous epoch (i.e. the chain went through at least one fully empty epoch with no new beacon blocks between the parent and the child that finally references it), the code falls into:
```
elif parent_bid.value > 0:
    state.builder_pending_withdrawals.append(
        BuilderPendingWithdrawal(fee_recipient=parent_bid.fee_recipient, amount=parent_bid.value, builder_index=parent_bid.builder_index)
    )
``` [5](#0-4) 

This branch's comment states the payment entry "has been evicted from `builder_pending_payments`", implying it was never settled. But because `process_builder_pending_payments` runs on *every* epoch transition independent of block proposals, the payment entry created for the parent's slot is guaranteed to have already been evaluated (paid if `weight >= quorum`, discarded otherwise) by the time two full epochs have elapsed since the parent's slot — before the eventual child block (with the stale parent) is ever processed. The "eviction" branch does not check whether the amount was already paid via `process_builder_pending_payments`, nor does it respect the quorum requirement that gates all other builder payments.

Consequently:
- If quorum *was* reached for that slot's payment, it gets paid once automatically via `process_builder_pending_payments`, and then paid **again** in full via this fallback branch — a genuine double payment (Gwei created and paid to the builder that was never committed twice).
- If quorum was *not* reached (the normal, expected outcome when an epoch is otherwise empty and no attestations accrue weight for that slot), `process_builder_pending_payments` correctly discards the payment, but the fallback branch pays it anyway — bypassing the quorum-gate entirely, i.e. a payment applied that the on-chain attestation-based settlement explicitly rejected.

This breaks the state-transition equality "a builder is paid its committed payload value if and only if quorum weight was reached exactly once," resulting in Gwei created/paid to a non-owner (or paid twice) without corresponding authority (attester quorum).

### Impact Explanation
This is a Critical-class issue under the given rubric: Gwei is created/paid to a builder beyond what the block/attestation quorum actually committed to, either by double-crediting a legitimately quorum-approved payment or by paying out a payment that failed to reach quorum. Because `process_epoch` executes deterministically for every state regardless of whether blocks are proposed, every conforming client reaches the same (buggy) result — so this is not a client divergence bug, but a spec-level invariant violation where Gwei is minted/paid outside the intended payment authorization path.

### Likelihood Explanation
Triggering requires the beacon chain to go through at least one entire epoch (`SLOTS_PER_EPOCH` slots) with no beacon block proposed at all after the payment-bearing parent block, before the next actual block is included, i.e. reachable purely via network liveness failure — no attacker collusion, majority stake, or malicious peer is required, only the passage of empty epochs, which is an explicitly-handled path in the spec code itself (the `elif parent_bid.value > 0` branch exists specifically to handle this "evicted" case). Because the spec must handle this state transition correctly for *any* possible sequence of slots/epochs (per the "Uint64 overflow/underflow" and exhaustive-state-transition philosophy stated in the spec), this is a legitimate reachable edge case, albeit requiring an unusual (multi-epoch) liveness gap.

### Recommendation
Track whether a given parent's builder payment has already been settled (e.g. persist a "settled" flag, or make `process_builder_pending_payments` aware that a slot's payment may later still need direct settlement, and have `apply_parent_execution_payload` check this state rather than assuming eviction implies "never settled"). At minimum, the fallback "evicted" branch should not pay unconditionally on `parent_bid.value > 0`; it should replicate the same quorum-gating logic (or definitively track that `process_builder_pending_payments` has not already resolved this exact payment) before appending to `state.builder_pending_withdrawals`.

### Proof of Concept
Conceptual state-transition sequence (not runnable code, but a description of the reachable sequence per spec semantics):
1. At slot `S` in epoch `E`, a full block is included; `process_execution_payload_bid` creates `state.builder_pending_payments[SLOTS_PER_EPOCH + S % SLOTS_PER_EPOCH]` with `withdrawal.amount = parent_bid.value` and `weight = 0` (or some initial weight from same-slot attestations).
2. Suppose subsequent attestations (processed via `process_attestation`, shown accumulating weight in [6](#0-5) ) push `weight >= quorum` before end of epoch `E`.
3. At the epoch `E→E+1` transition, `process_builder_pending_payments` shifts the entry to the lower half (not yet evaluated, since it was in the upper half during epoch E).
4. Suppose epoch `E+1` has **zero** proposed blocks (full liveness gap — no attacker coalition needed, simply an offline validator set / network partition of proposers).
5. At the epoch `E+1→E+2` transition, `process_builder_pending_payments` evaluates the lower half: `weight >= quorum` holds (from step 2), so it appends a `BuilderPendingWithdrawal` for the full `parent_bid.value` to `state.builder_pending_withdrawals`, and clears the entry.
6. Eventually a block is proposed in epoch `E+2` (or later); its `parent_slot` is still `S` (last included block), so `parent_epoch = E`. Since `E != get_current_epoch(state)` and `E != get_previous_epoch(state)`, execution falls into the `elif parent_bid.value > 0` branch in `apply_parent_execution_payload`, appending **another** `BuilderPendingWithdrawal` for the same `parent_bid.value`/`fee_recipient`/`builder_index`.
7. `state.builder_pending_withdrawals` now contains two entries for the same original payment, which `process_withdrawals`/`apply_withdrawals` will pay out sequentially, doubling the Gwei paid to the builder's `fee_recipient` for a single committed payload.

Note: I was unable to fully trace the exact slot-to-index mapping used at `process_execution_payload_bid` initialization (to confirm the precise off-by-one alignment between upper/lower halves) within the available context; the index-window rotation logic and the "elif ... evicted" comment in the spec text itself, however, directly confirm that a stale/evicted payment can no longer be distinguished from an already-settled one, which is the root cause of this class of bug.

def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)

    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
