### Title
Vault paper value (`convertToAssets`) is treated as withdrawable liquidity, so "trapped" ERC4626 collateral freezes `stopEpoch` - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
The external report describes collateral accounting that counts "trapped" collateral which cannot actually be withdrawn. The analog in `ProgrammableBorrower` is `_currentVaultAssets()`, which values the facility's ERC4626 position via `vault.convertToAssets(shares)` — the vault's *paper* value — rather than the *realizable* value (`vault.maxWithdraw`/`maxRedeem`/`previewWithdraw`). Both `availableToBorrow()` and the `onStopEpoch` solvency gate treat this paper value as liquid collateral, so any ERC4626 position that is nominally solvent but temporarily illiquid (utilization ~100% in a lending vault, withdrawal caps, queued redemptions) is counted as withdrawable when it is trapped.

### Finding Description
In `ProgrammableBorrower.sol`:

```solidity
function _currentVaultAssets() internal view returns (uint256) {
    uint256 shares = vault.balanceOf(address(this));
    return shares == 0 ? 0 : vault.convertToAssets(shares);
}
```

`availableToBorrow()` (lines 350-355) computes borrowable liquidity as `balanceOf(this) + _currentVaultAssets() - epochPendingWithdraws`. `onStopEpoch` (lines 239-253) uses the same paper value to decide whether a shortfall is covered:

```solidity
if (shortfall > _currentVaultAssets()) return true;      // paper value < shortfall -> default path
try vault.withdraw(shortfall, ...) returns (...) { ... }
catch { revert StopEpochVaultLiquidityUnavailable(); }   // paper value >= shortfall but illiquid -> revert
```

An unprivileged user of the ERC4626 vault can make the vault's assets trapped without reducing `convertToAssets`: e.g., borrowing all available liquidity out of the vault (a normal lending-vault borrow), keeping utilization at 100%, so every `withdraw` reverts even though shares still convert to full notional. This mirrors the report exactly: reported collateral exceeds realizable collateral because trapped collateral is not excluded.

The same paper-value assumption feeds `_vaultNetInterest()`/`totalInterestDueNow()` (lines 330-347): trapped/accrued-but-unrealizable vault value is included in the pool-facing interest figure that `IdleCDOEpochVariant.stopEpoch` reads to price the epoch, so tranche prices are updated against collateral that cannot actually be pulled.

### Impact Explanation
- **Temporary freezing of all LP funds**: while the vault is illiquid-but-solvent, `onStopEpoch` hits the `catch` branch and reverts `StopEpochVaultLiquidityUnavailable()`, so `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` cannot complete. Epoch end is blocked, `epochEndDate` passes, and no withdrawals can be processed. An attacker who keeps the vault at ~100% utilization (rolling a borrow, paying only the vault's own borrow interest) can extend the freeze arbitrarily. This is the direct consequence of `shortfall > _currentVaultAssets()` using paper value: a correct realizable-liquidity check would route to the default path (`return true` → `transferFrom` fails → `_handleBorrowerDefault`) instead of an unbounded retry loop.
- **Overstated collateral for epoch obligations**: because `availableToBorrow` counts trapped assets, the borrower can draw against collateral that leaves `epochPendingWithdraws` nominally reserved but physically unredeemable; at stop time the paper-valued interest inflates `expectedEpochInterest`, forcing a larger pull that can tip a covered stop into `_handleBorrowerDefault` and socialize a loss that proper liquidity-aware accounting would have surfaced earlier.

Quantified worst case: all tranche NAV (`lastNAVAA + lastNAVBB`) is locked for the duration of the induced vault illiquidity; if the illiquidity coincides with vault losses materializing before a retry, the delayed stop converts a temporary freeze into realized LP losses through the default waterfall.

### Likelihood Explanation
- Requires only that the chosen ERC4626 vault can become redeem-blocked while `convertToAssets` stays constant — the normal state of any lending-based vault at high utilization. No privileged role is needed: the attacker is an ordinary user of the vault ("a user of the programmable borrower's ERC4626 vault" is an allowed attacker class).
- The cost to sustain the freeze is the vault's own borrow rate, which the attacker already pays for their own purposes; during stress events (exactly when LPs most need to exit) vault illiquidity is common organically, so the freeze can trigger even without an attacker.
- No existing guard prevents it: `skipDefaultCheck`, skim, KYC, and `onlyIdleCDO` are irrelevant; the `try/catch` around `vault.withdraw` acknowledges the failure mode but converts it into a revert rather than a liquidity-aware decision. `maxWithdraw`/`maxRedeem` are never consulted anywhere in the contract.

### Recommendation
Use realizable liquidity instead of paper value at decision points:
- In `onStopEpoch`, compare `shortfall` against `vault.maxWithdraw(address(this))` (and/or attempt `redeem` of the exact shares) so a genuinely unrecoverable position falls through to the default path instead of reverting `StopEpochVaultLiquidityUnavailable` forever.
- In `availableToBorrow`, cap `_currentVaultAssets()` at `vault.maxWithdraw(address(this))` so the borrower cannot draw more than is actually redeemable, keeping `epochPendingWithdraws` truly reserved.
- Consider pricing epoch interest in `_vaultNetInterest`/`totalInterestDueNow` on realizable value, or documenting that vault paper gains may be unrealizable at stop.

### Proof of Concept
Foundry fork PoC sketch (requires a real ERC4626 lending vault whose `withdraw` reverts at full utilization, e.g., a Morpho/Euler/AAVE-style vault on the fork):

```solidity
// Setup: IdleCDOEpochVariant pool with ProgrammableBorrower as borrower,
// `vault` = lending ERC4626, epoch active, pendingWithdraws = W > 0.

// 1. Attacker (any EOA) borrows nearly all liquidity from `vault`
//    directly on the underlying lending market, driving utilization to ~100%.
//    vault.convertToAssets(poolShares) is unchanged; vault.maxWithdraw(programmableBorrower) == ~0.

// 2. Warp past epochEndDate; borrower repays nothing (has no draw).
// 3. manager calls cdoEpoch.stopEpoch(apr, _interest):
//      - totalInterestDueNow() = small positive number (paper value intact)
//      - onStopEpoch: onHand < amountRequired, shortfall <= _currentVaultAssets()
//        -> vault.withdraw(shortfall) reverts (no liquidity)
//        -> catch -> revert StopEpochVaultLiquidityUnavailable()
// 4. Every subsequent stopEpoch call reverts identically while the attacker
//    maintains the borrow; LPs cannot exit via requestWithdraw claims since
//    epochNumber never advances / pendingWithdraws never funded.

// Variant B (overstated collateral):
// 1. Attacker keeps utilization high during the epoch while convertToAssets
//    accrues paper interest -> _vaultNetInterest() reports interest I that is
//    trapped; expectedEpochInterest includes I.
// 2. Honest borrower has drawn funds; at stop, required pull = I + pendingWithdraws
//    exceeds realizable cash -> default path -> BB-first loss socialization
//    even though the facility is only illiquid, not insolvent.
```

Key assertions: `cdoEpoch.stopEpoch(...)` reverts with `StopEpochVaultLiquidityUnavailable`; `strategy.pendingWithdraws()` remains > 0; `vault.convertToAssets(shares) > 0` while `vault.maxWithdraw(address(programmableBorrower)) == 0`.
