### Title
Global shared request cache with no per-sender quota allows any signed sender to exhaust `maxCacheSize` and deny new pending requests from other senders - ([File: core/services/gateway/handlers/common/requestcache.go])

### Summary
`requestCache.NewRequest` enforces a single global `len(c.cache) >= maxCacheSize` check with no per-sender limit or eviction policy, so a single authenticated-but-unprivileged gateway client can fill the shared cache with unique `MessageId` values (paired with its own `sender`) and cause `NewRequest` to return `"request cache is full"` for every other sender's requests until the flooder's entries expire via `timeoutTimer`. The `TestRequestCache_MaxSize` test in `core/services/gateway/handlers/common/requestcache_test.go` already demonstrates the single-sender fill-to-capacity behavior with `maxCacheSize=2`, confirming the mechanism.

### Finding Description
`NewRequest` keys entries by `globalId{sender, id}` [1](#0-0) , but capacity is enforced only against the total map size, not per-sender count [2](#0-1) . Any signer of a gateway message (`request.Body.Sender`, derived from `Message.Validate()`'s signature-recovery step, not from a privileged role) can call `NewRequest` repeatedly with distinct `MessageId`s until `len(c.cache) == maxCacheSize`. Because entries are only removed on `ProcessResponse` completion or on timer-driven timeout (`time.AfterFunc(c.timeout, ...)` in `NewRequest`), the flooder can hold slots for up to `c.timeout` regardless of whether it ever intends to complete the requests, and other senders' calls will fail with `"request cache is full"` for that whole window. This is a genuine availability/isolation gap: the resource (cache capacity) is shared across all senders without quota or eviction ordering favoring fairness.

However, this requires only a valid signature over the message body (any sender), not any additional privilege — it is a resource-quota design flaw rather than an authentication/authorization bypass, key/secret disclosure, or cross-user data leak.

Regarding the "stale-entry reuse collision" sub-question: since `pendingRequest.timeoutTimer` fires per-entry independently and `deleteAndSendOnce` performs an atomic `c.mu.Lock(); delete(c.cache, key); ...` before releasing the lock [3](#0-2) , entries are only removed one at a time under the mutex — there is no mechanism to reuse an ID before its own timer fires, and no cross-entry race is introduced by the capacity check itself. The `ok` early-return in `NewRequest` for duplicate `(sender, id)` keys also prevents a sender from overwriting/reusing a not-yet-expired slot [4](#0-3) . So no collision/ID-reuse-before-timeout vulnerability exists; only the exhaustion/DoS aspect is real.

### Impact Explanation
This is a **denial-of-service on the shared pending-request cache** for the affected `RequestCache[T]` instance (e.g., the gateway's HTTP capability handler in `core/services/gateway/handlers/capabilities/v2/http_handler.go`), not a privilege escalation, secret disclosure, or fund-movement bug. Impact is bounded to temporary unavailability of new request registration for other senders sharing the same cache/DON, lasting up to the configured `timeout` duration. This matches a low/medium "Denial of Service - degraded availability" class rather than a critical node-compromise class under Chainlink's bounty program, since no authentication bypass, cross-user data exposure, or fund risk exists.

### Likelihood Explanation
Feasible in principle for any client able to send correctly signed messages to the gateway, requiring no elevated privilege — only the ability to generate unique `MessageId`s and sign them. However, real-world exploitability depends on gateway-level factors not modified by this function alone (e.g., `incomingRateLimiter`/per-sender rate limiting upstream of `NewRequest`, as seen in related handlers such as `OutgoingConnectorHandler` which applies `ratelimit.RateLimiter` with `PerSenderRPS`/`PerSenderBurst` before requests reach processing). Whether such a rate limiter sits in front of every `RequestCache` consumer (specifically `http_handler.go`) could not be fully confirmed from the retrieved context, so the practical likelihood of an attacker reaching `maxCacheSize` before being throttled elsewhere is uncertain.

### Recommendation
Add a per-sender quota (e.g., max pending entries per sender, separate from the global cap) inside `NewRequest`, and/or apply eviction of a sender's own oldest entries before rejecting new ones from other senders. Ensure per-sender rate limiting is enforced upstream of every `RequestCache` consumer.

### Proof of Concept
Extend `TestRequestCache_MaxSize` in `core/services/gateway/handlers/common/requestcache_test.go`:
1. Create `cache := common.NewRequestCache[requestState](time.Hour, N)`.
2. Loop `N` times calling `cache.NewRequest` with a single `sender="attacker"` and unique `MessageId`s; assert all succeed.
3. Call `cache.NewRequest` with `sender="victim"`, a fresh `MessageId`; assert it returns `"request cache is full"`.
4. Assert this denial persists until either (a) the attacker's entries time out (`time.Sleep` past `timeout`, or use short `timeout` in test) and then `victim`'s `NewRequest` succeeds, or (b) `ProcessResponse` completes an attacker entry, freeing a slot for `victim`.
5. Additionally verify no premature reuse: attempt `victim.NewRequest` with the same `MessageId` as an attacker's pending (non-expired) entry using `sender="attacker"` again — expect `"request already exists"`, confirming no collision window before timer fires.

```go
func (c *requestCache[T]) deleteAndSendOnce(key globalId, callbackResponse handlers.UserCallbackPayload) error {
	c.mu.Lock()
	entry, deleted := c.cache[key]
	delete(c.cache, key)
	c.mu.Unlock()
	if deleted {
		entry.timeoutTimer.Stop()
		return entry.SendResponse(callbackResponse)
	}
```
