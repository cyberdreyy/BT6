### Title
Rejected signer's weight is never removed before being recounted as approved, letting a signer's flip-flop double-count into both `total_weight_approved` and `total_weight_rejected` - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` tallies per-block signer weight into two independent running counters, `total_weight_approved` and `total_weight_rejected`, keyed by `slot_id`. The guard that prevents double-adding to `total_weight_approved` only checks `block.gathered_signatures.contains_key(&slot_id)`, never `block.responded_signers`. Because `responded_signers` is shared between the accept and reject paths but the accept path's anti-double-count check does not consult it, a signer who previously sent a `Rejected` response for a block and later sends an `Accepted` response for the *same* `signer_signature_hash` has its weight added to `total_weight_approved` while its weight remains in `total_weight_rejected` — exactly the class of bug in the report ("previous delegate" balance not cleared before crediting the new delegate).

### Finding Description
In `handle_...` message processing (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`):

- `Rejected` branch: gated by `if block.responded_signers.insert(slot_id) { block.total_weight_rejected = ...saturating_add(signer_entry.weight); ... }` [1](#0-0) 
- `Accepted` branch: gated by `if !block.gathered_signatures.contains_key(&slot_id) { block.total_weight_approved = ...saturating_add(signer_entry.weight); ... }`, followed unconditionally by `block.gathered_signatures.insert(slot_id, signature); block.responded_signers.insert(slot_id);` [2](#0-1) 

These are two separate maps/sets used as independent "have we already counted this signer" checks for two different counters (`total_weight_approved` vs `total_weight_rejected`). The `Accepted` branch's check (`gathered_signatures`) has nothing to do with whether the same slot already contributed weight to `total_weight_rejected`; it will happily add the signer's weight to `total_weight_approved` even though that same weight is still sitting inside `total_weight_rejected` from an earlier `Rejected` message for the same block hash. Unlike the delegate-balance bug's `_prevBalance - userBalance` (over-subtraction), this is the mirror failure mode: the "old bucket" (`total_weight_rejected`) is never decremented when the signer moves to the "new bucket" (`total_weight_approved`), so the same weight now lives in both buckets simultaneously.

This is reachable by a single signer's own message stream (StackerDB gossip, requiring no majority and no other signer's key), because the signer protocol explicitly allows a signer to revisit a previously-rejected block: `stacks-signer/src/v0/signer.rs` contains logic that "does not change our votes on rejected blocks unless we receive a new block proposal for it and the reject reason allows us to reconsider" — i.e., under the right reject-reason and a later re-proposal for the identical block, the signer can legitimately transition from `Rejected` to `Accepted` for the same `signer_signature_hash`, and both StackerDB messages get delivered to `StackerDBListener`.

### Impact Explanation
The invariant the miner-side `SignCoordinator` relies on (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) is that `total_weight_approved` and `total_weight_rejected` are disjoint tallies over distinct signers, bounded by `self.total_weight`:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight { ... reject ... }
else if block_status.total_weight_approved >= self.weight_threshold { ... accept, return signatures ... }
``` [3](#0-2) 

When one signer's weight is double-counted into both totals, `total_weight_approved + total_weight_rejected` can exceed `self.total_weight`, breaking the "aggregated-weight vs verified-accepts" equality the threshold math depends on. This lets the miner's coordinator observe `total_weight_approved >= weight_threshold` sooner than the number of *distinct, currently-approving* signers actually warrants (the flipped signer's weight is being counted even though it was also counted against rejection, i.e., the true set of signers whose *current* vote is "accept" can be smaller than what `total_weight_approved` claims). Depending on timing this can also cause a legitimately-recoverable block to instead be prematurely marked `SignersRejected` while approval weight is simultaneously accruing, producing an inconsistent decision. This falls under "aggregated-weight vs verified-accepts" and, in the accept-crossing direction, is effectively "a rejection recounted as an accept" without properly retracting the rejection.

### Likelihood Explanation
Requires only one signer (the report's rule set explicitly allows "one-slot miner (plus gossip)" scale bugs) to send a `Rejected` then later an `Accepted` `BlockResponse` for the identical `signer_signature_hash` — a flow the signer client itself supports intentionally (vote reconsideration on re-proposal). No majority, no other signer's key, and no malicious behavior is even required — a normal reconsideration sequence during a live re-proposal round is sufficient to trigger the double count.

### Recommendation
Use a single per-slot "current vote" state (e.g., an enum `Accepted`/`Rejected` keyed by `slot_id`) instead of two independently-guarded counters. When a signer transitions vote, subtract the previous contribution from whichever counter previously held it before adding the new contribution to the other counter — mirroring the report's fix pattern (`if _prevBalance > 0 && _userDelegate != msg.sender`): here, `if let Some(prev) = block.vote_by_slot.get(&slot_id) { retract prev weight from its bucket }` before crediting the new bucket, and only then insert the slot into whichever tracking set/map is used for the new vote.

### Proof of Concept
1. Miner requests signatures for block `B` (`signer_signature_hash = H`) via `SignCoordinator`.
2. Signer `S` (slot `k`, weight `w`) evaluates `B`, fails a check, and sends `BlockResponse::Rejected` for `H`. `StackerDBListener` runs the `Rejected` branch: `responded_signers.insert(k)` succeeds → `total_weight_rejected += w`.
3. The miner re-proposes the identical block `B` (same `H`) later in the same tenure round (e.g., after re-validation clears the earlier objection) — supported by the signer's "reconsider on re-proposal" logic in `stacks-signer/src/v0/signer.rs`.
4. Signer `S` now sends `BlockResponse::Accepted` for the same `H`. In the `Accepted` branch, `block.gathered_signatures.contains_key(&k)` is `false` (this map was never touched by the earlier `Rejected` message), so the check passes and `total_weight_approved += w` — even though `w` is still counted in `total_weight_rejected` from step 2.
5. Now `block_status.total_weight_approved` and `block_status.total_weight_rejected` both include signer `S`'s weight `w` for the same block, violating the intended invariant that they are disjoint sums bounded by `self.total_weight`, and can cause `SignCoordinator::run` in `signer_coordinator.rs` to reach an accept or reject decision based on inflated/duplicated weight rather than the true distinct-signer tally.
