### Title
Deterministic account initialization does not purge pre-existing AccessKey entries, allowing a squatter to retain full control of a legitimately-initialized `0s…` account - (File: runtime/runtime/src/deterministic_account_id.rs)

### Summary
`action_deterministic_state_init` and `deploy_deterministic_account` only ever touch `Account.contract()`/`storage_usage` and `TrieKey::ContractData`; they never inspect or clear `TrieKey::AccessKey` entries for the target id. If an attacker manages to get an `Account` record with `AccountContract::None` created at the exact `0s…` id that a legitimate deployer will later derive (e.g. via `CreateAccount`+`AddKey`, since that id is long enough to be a self-registrable top-level account and is not filtered by `check_account_existence`'s implicit-account guard), any access key the attacker installed there remains valid after the legitimate `DeterministicStateInitAction` runs.

### Finding Description
`action_deterministic_state_init` (runtime/runtime/src/deterministic_account_id.rs:15) treats the `uninit -> active` transition purely as a function of `account.contract().is_none()`: [1](#0-0) 

When true, it calls `deploy_deterministic_account` (runtime/runtime/src/deterministic_account_id.rs:121), which only performs two mutations: `use_global_contract` (sets `AccountContract`, accounts for storage) and writing `TrieKey::ContractData` entries from `state_init.data()`: [2](#0-1) 

Neither function reads, iterates, or deletes any `TrieKey::AccessKey` entry for `account_id`. The receiver-pinning check in `validate_deterministic_state_init` (runtime/runtime/src/action_validation.rs:435) only verifies that `derive_near_deterministic_account_id(&action.state_init) == receiver_id`; it says nothing about the pre-existing state of that account beyond `contract().is_none()`: [3](#0-2) 

Attacker flow: the attacker races to submit a `CreateAccount` (accepted because a `0s`-prefixed 42-char id satisfies `account_id.is_top_level()` and is long enough to bypass the registrar-only restriction, per `action_create_account`, runtime/runtime/src/actions.rs:167) followed by `AddKey` with a full-access key in the same transaction, targeting the exact `0s…` id the legitimate deployer will later derive from its known `DeterministicAccountStateInit`. `check_account_existence` (runtime/runtime/src/actions.rs:787) does not reject `CreateAccount` for near-deterministic-typed ids — its implicit-account guard only fires for near-implicit/eth-implicit hex ids: [4](#0-3) 

The `AccessKey` is written under a completely separate trie column (`TrieKey::AccessKey`) from the columns that `deploy_deterministic_account` touches, so nothing about the later, legitimate `DeterministicStateInitAction` disturbs it. When the rightful deployer submits the correct `DeterministicStateInitAction`, `account.contract().is_none()` is still true (the squatter never deployed a contract), so `deploy_deterministic_account` runs and installs the contract/data on top of the existing `Account` record — but the attacker's access key row survives untouched in the trie.

### Impact Explanation
This is an authorization-escalation vulnerability: an unprivileged attacker who never received any delegation from the deterministic account's deriving owner ends up holding a full-access key over that account after it becomes "active." Once initialized, the account can hold funds/storage (attached deposit, future transfers), and the attacker's surviving `FullAccess` key lets it execute `FunctionCall`, `Transfer`, `DeleteKey`, and `DeleteAccount` against it — i.e., theft of any funds or state value later associated with the account. This matches the "Authorization escalation across accounts" / "Unauthorized transaction" bounty category.

### Likelihood Explanation
Preconditions: the attacker must predict (or be told) the deployer's `DeterministicAccountStateInit` in advance (code hash / `GlobalContractIdentifier` + `data`) in order to compute the exact `0s…` id via `derive_near_deterministic_account_id`, and must race a `CreateAccount`+`AddKey` transaction to that id before the deployer's `DeterministicStateInitAction` lands. Cost is a single ordinary transaction (self-registrable top-level account, no registrar privilege needed since the derived id is 42 characters, above `min_allowed_top_level_account_length`). This is fully repeatable for any deterministic account whose `state_init` becomes known/predictable ahead of deployment (e.g. contract templates with well-known code hash and default/empty `data`).

### Recommendation
In `action_deterministic_state_init`/`deploy_deterministic_account`, when transitioning `uninit -> active` on a pre-existing `Account` record (i.e., `maybe_account` was `Some` before this action ran), explicitly enumerate and remove any existing `TrieKey::AccessKey` (and other owner-controlled state such as postponed receipts) for `account_id` before or as part of installing the deterministic state, so that no third party can retain authority that was not part of the derived `state_init`. Alternatively, reject `CreateAccount`/`AddKey` targeting ids of `AccountType::NearDeterministic` the same way implicit accounts are protected in `check_account_existence`, closing the squatting vector at its source.

### Proof of Concept
1. Runtime/test-loop test: submit `CreateAccount` + `AddKey(attacker_pubkey, FullAccess)` in one transaction targeting a precomputed `0s…` id derived from a known `DeterministicAccountStateInit` (global contract id + data map), asserting success (mirrors `action_create_account`/`action_add_key` paths, no implicit-account rejection triggers).
2. Submit the legitimate `DeterministicStateInitAction` transaction with the matching `state_init` to the same `0s…` receiver; assert it succeeds (`assert_success()`), and that `get_account_state(det_account).contract` now reflects the deployed global contract/data.
3. Call `get_access_key(det_account, attacker_pubkey)` and assert it still resolves to the previously-added `FullAccess` key.
4. Sign a `FunctionCall`/`Transfer`/`DeleteKey` transaction with the attacker's key against `det_account` and assert it executes successfully, demonstrating retained unauthorized control post-initialization.

fn deploy_deterministic_account(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    state_init: &DeterministicAccountStateInit,
    result: &mut ActionResult,
    storage_usage_config: &StorageUsageConfig,
) -> Result<(), RuntimeError> {
    // Step 1: set contract code (includes storage usage accounting)
    use_global_contract(state_update, account_id, account, state_init.code(), result)?;
    if result.result.is_err() {
        return Ok(());
    }

    // Step 2: insert provided key-value pairs
    let mut required_storage_usage = account.storage_usage();
    for (key, value) in state_init.data() {
        let trie_key = TrieKey::ContractData { account_id: account_id.clone(), key: key.to_vec() };

        let value_bytes = value.len() as u64;
        let key_bytes = key.len() as u64;
        let extra_per_record_bytes = storage_usage_config.num_extra_bytes_record;

        let new_bytes = value_bytes
            .checked_add(key_bytes)
            .and_then(|acc| acc.checked_add(extra_per_record_bytes))
            .ok_or(IntegerOverflowError {})?;
        state_update.set(trie_key, value.clone());
        required_storage_usage =
            required_storage_usage.checked_add(new_bytes).ok_or(IntegerOverflowError {})?;
    }
    account.set_storage_usage(required_storage_usage);

    Ok(())
}
