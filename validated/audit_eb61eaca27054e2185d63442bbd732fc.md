### Title
`parse_token_v3` Multisig `signers` filter silently drops legitimate signers whose value equals `Pubkey::default()` - ([File: account-decoder/src/parse_token.rs])

### Summary
`parse_token_v3`'s `Multisig` branch filters the raw 11-slot `signers` array by comparing each entry to `Pubkey::default()` to strip unused/padding slots, but it does not distinguish padding slots (indices `>= n`) from a genuinely configured signer that an attacker deliberately sets to the all-zero pubkey. Because the account data is fully attacker-controlled (it is their own on-chain `Multisig` account), the attacker can construct a multisig where one of the first `n` "valid" signer slots is `Pubkey::default()`, causing the returned `signers` vector to have fewer entries than `num_valid_signers` while `num_valid_signers` still reports the true `n`.

### Finding Description
In `account-decoder/src/parse_token.rs`, the multisig parsing path is: [1](#0-0) 

`multisig.signers` is a fixed `[Pubkey; 11]` array where the SPL Token program only treats the first `n` entries as meaningful and leaves the remaining `11 - n` slots as `Pubkey::default()` padding. The parser's `filter_map` treats *any* array entry equal to `Pubkey::default()` as padding and removes it — it has no way to know whether a given zero entry is at index `< n` (a "real" signer slot) or `>= n` (padding). Since an SPL Token `Multisig` account is just packed on-chain data that any account owner can construct (the SPL Token program itself does not reject `Pubkey::default()` as a signer value when initializing a multisig, since `Pubkey::default()` is a syntactically valid 32-byte pubkey), an attacker can set `signers[1] = Pubkey::default()` while `n = 3`, and the on-chain data will unpack successfully via `Multisig::unpack`.

When any RPC client queries this account with `getAccountInfo`/`getProgramAccounts` (`jsonParsed` encoding), `parse_account_data_v3` routes to `parse_token_v3`, which returns a `UiMultisig` where `num_valid_signers == 3` but `signers.len() == 2`, because the middle default-valued signer is silently dropped. The `signers` list is used by wallets/integrators to determine which pubkeys are permitted signers for the multisig; a discrepancy here means a configured signer (even if by mistake or design set to the zero key) is invisible in the reported list, while the "3 signers required/present" count claims full fidelity.

### Impact Explanation
This is a decoder misreporting bug: it produces an internally-inconsistent `UiMultisig` (`signers.len() != num_valid_signers`) returned to any client calling read-only RPC methods (`getAccountInfo`, `getProgramAccounts`, `getMultipleAccounts` with `jsonParsed`), which matches the "decoder panic and misreporting" scoped-impact category. It does not affect validator consensus, cause a crash, or allow unbounded compute — it is purely a data-fidelity/misreporting issue for downstream integrators inspecting SPL Token multisig accounts through JSON-parsed RPC responses.

### Likelihood Explanation
This is trivially reproducible: any account owner/attacker can pack an SPL Token `Multisig` account (a 355-byte account layout, no special permissions required beyond being able to write arbitrary bytes to an account they own) with `signers[i] = Pubkey::default()` for some `i < n`. No validator, leader, or privileged access is required — this is achievable with a single unprivileged account write followed by a single `getAccountInfo(jsonParsed)` RPC call.

### Recommendation
In `parse_token_v3`'s `Multisig` branch, only inspect/emit the first `multisig.n as usize` entries of `multisig.signers` rather than filtering the whole 11-element array by equality to `Pubkey::default()`. For example, take `multisig.signers[..multisig.n as usize]` and map each entry to its string representation directly (or, if defending against corrupted `n`, still filter but only within the `n`-length slice), rather than relying on the value-based heuristic that conflates "padding" with "a legitimately configured but degenerate zero signer."

### Proof of Concept
```rust
// account-decoder/src/parse_token.rs (test module)
#[test]
fn test_multisig_zero_signer_in_valid_range_is_dropped() {
    let signer1 = Pubkey::new_from_array([1; 32]);
    let signer3 = Pubkey::new_from_array([3; 32]);
    let mut multisig_data = vec![0; Multisig::get_packed_len()];
    let mut signers = [Pubkey::default(); 11];
    signers[0] = signer1;
    signers[1] = Pubkey::default(); // attacker sets a "valid" slot (< n) to the zero pubkey
    signers[2] = signer3;
    let mut multisig = Multisig::unpack_unchecked(&multisig_data).unwrap();
    multisig.m = 2;
    multisig.n = 3; // n=3 claims 3 configured signers
    multisig.is_initialized = true;
    multisig.signers = signers;
    Multisig::pack(multisig, &mut multisig_data).unwrap();

    let parsed = parse_token_v3(&multisig_data, None).unwrap();
    if let TokenAccountType::Multisig(ui) = parsed {
        assert_eq!(ui.num_valid_signers, 3);
        // Bug: only 2 signers are reported even though num_valid_signers == 3
        assert_ne!(ui.signers.len(), ui.num_valid_signers as usize);
        assert_eq!(ui.signers, vec![signer1.to_string(), signer3.to_string()]);
    } else {
        panic!("expected Multisig variant");
    }
}
```
Expected result: the assertion `ui.signers.len() != ui.num_valid_signers as usize` passes, demonstrating the fidelity gap — the legitimate (attacker-chosen) zero-value signer at index 1 is indistinguishable from padding and silently dropped from the reported `signers` list.
