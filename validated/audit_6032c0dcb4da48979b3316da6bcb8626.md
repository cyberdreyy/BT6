### Title
Instant-withdraw requests can permanently block `stopEpoch`, freezing all pool funds with the borrower - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`_stopEpoch` treats any nonzero pending instant-withdraw amount as a hard revert condition (`_checkNotAllowed(_pendingInstant() != 0)`), analogous to the XFS validator that flags a valid state as corrupt and shuts the filesystem down. Any tranche-token holder can keep `pendingInstantWithdraws` nonzero across the `getInstantWithdrawFunds` → `stopEpoch` sequence, so the epoch can never be stopped, no new epoch can start, and user funds stay lent to the borrower indefinitely.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch` the guard reverts the entire epoch settlement whenever an instant request is pending:

```solidity
// contracts/IdleCDOEpochVariant.sol:338-345
_checkNotAllowed(
  !isEpochRunning ||
  block.timestamp < epochEndDate ||
  // pending instant withdraws must have been resolved by getInstantWithdrawFunds
  _pendingInstant() != 0 ||
  ...
);
```

The intended remediation is for the manager to call `getInstantWithdrawFunds` (which pulls liquidity into `IdleCreditVault` and clears `pendingInstantWithdraws`) and then call `stopEpoch`. However, these are two separate manager transactions, and `requestWithdraw` during a running epoch (while `allowInstantWithdraw` is true — it is set in `startEpoch`, line 292) lets any tranche holder register a new instant request. An attacker holding even a small tranche balance can therefore:

1. Wait for `epochEndDate` to pass.
2. Watch the mempool: whenever `getInstantWithdrawFunds` clears the pending amount, submit a new instant `requestWithdraw` (or pre-seed one between the two manager calls).
3. `stopEpoch` reverts on `_pendingInstant() != 0`.
4. Repeat each time the manager retries — the epoch can never close.

This mirrors CVE-2020-14385: a *valid* user-creatable state (a legitimate instant-withdraw receipt) is treated as fatal by the settlement path, producing a denial of service that persists until operator-level intervention ("remount" = manual forced accounting/emergency shutdown, which itself socializes losses).

### Impact Explanation
Temporary freezing of the entire pool's TVL. While `isEpochRunning` is true: ordinary deposits are paused, withdrawal requests are disabled (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` are only re-enabled inside the success path of `_stopEpoch`, lines 478-483), `_beforeUnpause` reverts (line 636), and `requestWithdraw` for normal redemptions is gated. Principal remains with the borrower and only becomes recoverable if the honest owner triggers `emergencyShutdown`/`_updateAccounting` — which crystallizes the epoch at a loss-bearing state and still cannot pull funds back from the borrower. Attack cost is one instant request per manager retry (requesting a small amount of already-owned tranche tokens); the instant request itself remains claimable, so the attacker's capital is not at risk. Quantified loss: 100% of pool NAV is frozen for the duration of the griefing, plus forced-loss accounting if the owner unwinds via emergency path.

### Likelihood Explanation
High feasibility under the stated threat model: the attacker only needs to be a tranche-token holder (unprivileged). The sequence requires no privileged cooperation — the honest manager's own remediation (`getInstantWithdrawFunds`) creates the window the attacker exploits, since clearing `pendingInstantWithdraws` and closing the epoch are not atomic. The only preconditions are `isEpochRunning`, `allowInstantWithdraw == true`, and `disableInstantWithdraw == false`, all normal operating states. Uncertainty: whether the instant request path is additionally gated by `instantWithdrawDelay`/deadline semantics in `requestWithdraw` could narrow the window, but nothing in `_stopEpoch` distinguishes a fresh request from a stale one — any nonzero value reverts.

### Recommendation
Make instant-request settlement and epoch stopping atomic, or make `stopEpoch` tolerate pending instants:
- Have `stopEpoch` internally invoke the instant-funding logic (`getInstantWithdrawFunds`) before checking `_pendingInstant()`, so a request that arrives mid-sequence is funded rather than fatal.
- Alternatively, close instant withdrawal requests for the epoch when `block.timestamp >= epochEndDate`, so no new instant receipts can be created once the epoch is stoppable.

### Proof of Concept
Reproducible Foundry outline (against the existing `IdleCreditVault.t.sol` harness):

```solidity
function testInstantRequestBlocksStopEpoch() external {
  address attacker = makeAddr("attacker");
  idleCDO.depositAA(10_000 * ONE_SCALE);
  _depositWithUser(attacker, 100 * ONE_SCALE, true); // attacker holds AA tranche

  _startEpochAndCheckPrices(0); // allowInstantWithdraw = true

  // attacker registers an instant withdraw during the epoch
  uint256 attackerShares = AAtranche.balanceOf(attacker);
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(attackerShares / 2, address(AAtranche));

  vm.warp(cdoEpoch.epochEndDate() + 1);

  // manager tries to settle: fund pending instants
  _getInstantFunds(); // clears pendingInstantWithdraws

  // attacker re-registers a fresh instant request before stopEpoch lands
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(AAtranche.balanceOf(attacker), address(AAtranche));

  // stopEpoch reverts — epoch can never close while attacker repeats this
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  vm.prank(manager);
  cdoEpoch.stopEpoch(initialProvidedApr, 0);

  assertTrue(cdoEpoch.isEpochRunning(), "epoch still running");
  assertTrue(cdoEpoch.paused(), "deposits still paused");
  assertFalse(cdoEpoch.allowAAWithdrawRequest(), "withdraw requests still closed");
}
```

Notes/caveats: the exact instant-request entry conditions (deadline/delay gating inside `requestWithdraw` and `getInstantWithdrawFunds`) were not fully verified in the available context; the PoC assumes the standard epoch configuration where instant withdraws are enabled. If instant requests cannot be opened after `epochEndDate` or after funding, the attack window collapses and this would reduce to a single-revert nuisance rather than a repeatable freeze.
