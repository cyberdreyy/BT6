### Title
Signer restart silently drops in-progress Tx Replay state, letting the restarted signer sign blocks the rest of the signer set would reject as non-canonical - (File: `stacks-signer/src/v0/signer.rs`, `stacks-signer/src/v0/signer_state.rs`)

### Summary
`Signer::new` and `LocalStateMachine::new` always reconstruct the local state machine from an empty/`None` Tx-Replay context on process start, even if a Tx Replay was in progress before the crash/restart. This is the same bug class as the NEAR fix ("panic on new if trie_state_resharder in progress"): an in-progress, not-yet-completed protocol operation is silently forgotten across a restart instead of being resumed or blocking startup, letting the node act as if the operation never started.

### Finding Description
When a Bitcoin fork forces the signer set into "Tx Replay" mode, the signer tracks two pieces of state:
- `tx_replay_set` — the set of transactions that must be replayed, part of the persisted-view `SignerStateMachine`.
- `tx_replay_scope` — the burn-block boundaries of the replay, explicitly documented as **not persisted**, living only as a field on the in-memory `Signer` struct: [1](#0-0) 

`ReplayState::infer_state` treats a non-empty `tx_replay_set` with a missing `scope` as an invalid/unrecoverable state and returns `None`: [2](#0-1) 

On process restart, `Signer::new` unconditionally sets `tx_replay_scope: None` and delegates state machine construction to `LocalStateMachine::new`, which builds the machine from `Self::Uninitialized` and a bare `place_holder()` (i.e. `tx_replay_set: ReplayTransactionSet::none()`), rather than any persisted view of an in-progress replay: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Consequently, a signer that restarts mid-replay comes back up believing `ReplayState::Unset` — no replay is in progress — while every other signer that stayed online continues to enforce `ReplayState::InProgress(tx_replay_set, scope)`. Nothing in `bitcoin_block_arrival` re-derives the lost scope/set from the node or from peers before the signer resumes normal proposal evaluation; the guard in `ReplayState::infer_state` only fires (and only would abort with `SignerChainstateError::LocalStateMachineNotReady`) in the narrow case where the in-memory set is non-empty but the scope is missing, which restart bypasses entirely because the whole `SignerStateMachine` is rebuilt from the empty placeholder: [7](#0-6) 

The system does have a *designed* failsafe — `reset_replay_set_after_fork_blocks` — that clears a stalled replay set for signers that keep it, but that failsafe assumes all signers agree on being "in replay"; it does nothing to correct a signer that has already unilaterally forgotten the replay on restart, since that signer's local view is `Unset` from the very next `bitcoin_block_arrival` call. Docs corroborate that `tx_replay_scope` is process-local, non-persisted state used to gate proposal validation: [8](#0-7) 

### Impact Explanation
`tx_replay_set`/`tx_replay_scope` drive `validate_with_replay_tx` block-proposal checks, which restrict which transactions may legally appear in a post-fork tenure. A restarted signer that has silently reverted to `Unset` will validate and sign a block proposal exactly as it would in normal (non-replay) operation, ignoring the transaction-replay restriction that the rest of the signer set is still enforcing. This is a single-signer-triggerable divergence in which one signer's notion of "canonical/valid" content for a tenure disagrees with the group's, which the report's rules classify as Critical: a signer signing a non-canonical/conflicting block relative to what the still-informed portion of the signer set accepts.

### Likelihood Explanation
The trigger requires only:
1. A Bitcoin fork that puts the signer set into Tx Replay mode (miner/attacker-observable, not privileged).
2. A restart of any one signer's `stacks-signer` process (crash, operator restart, upgrade) while that replay is still in progress.

Both conditions are ordinary operational events — no majority collusion, no other signer's key, and no auth-token access is needed, satisfying the report's "one-slot miner (plus gossip)" scope. Given how frequently signer processes are restarted in production (upgrades, host maintenance) relative to how long a Tx Replay window can remain open (deep forks, `reset_replay_set_after_fork_blocks` not yet reached), this is a plausible, non-theoretical operational hazard.

### Recommendation
Persist `tx_replay_scope` (and reconcile it with `tx_replay_set`) in `SignerDb` the same way other block/agreement state is persisted, and have `LocalStateMachine::new`/`Signer::new` reload it on startup instead of defaulting to `place_holder()`/`None`. If persisted state cannot be trusted (e.g., corrupted), the signer should refuse to participate in proposal signing until it has re-synced global state via `capitulate_viewpoint`/peer `StateMachineUpdate`s, mirroring the NEAR fix's approach of refusing to proceed rather than silently resuming from a wrong baseline.

### Proof of Concept
1. Configure a 5-signer test network with `validate_with_replay_tx = true` and `miner.replay_transactions = true` (as in the existing `tx_replay_*` integration tests, e.g. `tx_replay_starts_correctly`).
2. Submit a transaction, then trigger a Bitcoin fork so the signer set enters Tx Replay mode; confirm via `wait_for_replay_set_eq` that all signers, including signer X, hold a non-empty `tx_replay_set`.
3. Kill and restart signer X's process (simulating a crash/upgrade) while the replay set is still non-empty on the other signers.
4. Observe that signer X's freshly constructed `LocalStateMachine` starts from `place_holder()` with `tx_replay_set: ReplayTransactionSet::none()` and `tx_replay_scope: None` [6](#0-5) , so it no longer enforces the replay restriction, while the other 4 signers still do [9](#0-8) .
5. Have the miner propose a block that violates the still-active replay restriction (contains a non-replay tx ahead of the required replay txs); verify signer X accepts/signs it while the other signers reject it, demonstrating the safety divergence.

impl ReplayState {
    /// Infers the appropriate `ReplayState` based on the contents of the replay transaction set
    /// and the optional scope.
    ///
    /// # Arguments
    ///
    /// * `replay_set` - A reference to a set of transactions intended for replay.
    /// * `scope_opt` - An optional scope defining the boundaries or context for the replay.
    ///
    /// # Returns
    ///
    /// * `Some(ReplayState::Unset)` if the `replay_set` is empty.
    /// * `Some(ReplayState::InProgress)` if the `replay_set` is non-empty and a `scope` is provided.
    /// * `None` if the `replay_set` is non-empty but no `scope` is provided.
    ///   - Possibly caused by the scope being a local state in the `Signer` struct, which is not persisted.
    fn infer_state(replay_set: &ReplayTransactionSet, scope_opt: &ReplayScopeOpt) -> Option<Self> {
        if replay_set.is_empty() {
            return Some(Self::Unset);
        }

        scope_opt
            .as_ref()
            .map(|scope| Self::InProgress(replay_set.clone(), scope.clone()))
    }
