### Title
Transient ERC4626 illiquidity blocks epoch settlement and freezes withdrawal payouts - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
In programmable-borrower mode, `stopEpoch` delegates liquidity recall to `ProgrammableBorrower.onStopEpoch`, which compares the required shortfall only against the vault’s `convertToAssets` valuation before attempting a real withdrawal. [1](#0-0) [2](#0-1)  An ERC4626 participant can make the vault temporarily illiquid while the programmable borrower’s shares still report enough asset value, causing `vault.withdraw` to revert and forcing the epoch stop transaction to revert with `StopEpochVaultLiquidityUnavailable`. [3](#0-2)  This leaves `isEpochRunning` active and prevents pending withdrawal receipts from being funded until sufficient vault liquidity returns. [4](#0-3) 

### Finding Description
`IdleCDOEpochVariant._stopEpoch` intentionally lets hook reverts propagate so transient ERC4626 failures can be retried rather than treated as defaults. [5](#0-4)  `ProgrammableBorrower.onStopEpoch` treats the borrower as economically covered whenever `shortfall <= _currentVaultAssets()`, then calls `vault.withdraw` for the full shortfall. [6](#0-5)  The economic check does not verify currently withdrawable liquidity through a liquidity-aware value such as `maxWithdraw`, so a revert inside the external vault aborts the entire stop operation. [3](#0-2) 

The relevant sequence is:

1. LP deposits are parked in the ERC4626 vault by `onStartEpoch`. [7](#0-6) 
2. A tranche holder creates a normal withdrawal request, increasing `pendingWithdraws`. [8](#0-7) 
3. An external vault participant removes the vault’s currently withdrawable cash while the programmable borrower’s share valuation remains sufficient. [3](#0-2) 
4. The honest manager calls `stopEpoch`, the hook reaches `vault.withdraw(shortfall, ...)`, and the revert prevents epoch accounting from completing. [9](#0-8) [10](#0-9) 
5. Pending withdrawal receipts remain unfunded because `collectWithdrawFunds` is never reached. [10](#0-9) 

### Impact Explanation
This is a temporary freezing of LP settlement funds equal to `pendingWithdraws` plus any cash interest that must be pulled from the borrower. [11](#0-10)  While the condition persists, the epoch cannot stop normally, withdrawal receipts cannot be funded, and requesters cannot claim matured underlying payouts. [4](#0-3)  The issue does not directly transfer protocol funds to the attacker, but it lets an unprivileged ERC4626 participant keep a nominally covered recall in a reverting state. [3](#0-2) 

### Likelihood Explanation
The attack requires an external ERC4626 vault whose reported asset value can exceed immediately withdrawable liquidity, which is a normal property of vaults that allocate assets into underlying markets. [2](#0-1)  The attacker must control enough vault shares, borrowing capacity, or market activity to remove at least the shortfall required by `onStopEpoch`. [6](#0-5)  No privileged Idle role is required because the condition is created entirely inside the configured external vault. [12](#0-11) 

### Recommendation
Check withdrawable liquidity before calling `vault.withdraw`, such as by capping the attempted amount to `vault.maxWithdraw(address(this))`, and return `false` only when the borrower ledger is actually incapable of satisfying settlement. [2](#0-1)  Alternatively, treat an otherwise-covered ERC4626 withdrawal failure as a borrower-default condition inside `onStopEpoch` rather than reverting indefinitely, while preserving a retryable path for transient failures if that distinction is operationally required. [1](#0-0)  The implementation should also avoid making successful epoch settlement depend on a single exact-amount ERC4626 withdrawal when partial withdrawals could satisfy the CDO transfer. [2](#0-1)

// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;

import "./ProgrammableBorrowerCreditVault.t.sol";

contract ProgrammableBorrowerVaultIlliquidityPoC is ProgrammableBorrowerCreditVault {
    function testVaultIlliquidityFreezesEpochSettlement() external {
        uint256 amount = 10_000 * oneScale;
        address vaultLiquidityManipulator = makeAddr("vaultLiquidityManipulator");

        vm.prank(owner);
        cdoEpoch.setIsInterestMinted(true);

        idleCDO.depositAA(amount);

        // Create a normal withdrawal request that must be funded at stopEpoch.
        uint256 requestShares = aaTranche.balanceOf(address(this)) / 2;
        cdoEpoch.requestWithdraw(requestShares, address(aaTranche));

        _startEpochAndCheckPrices(0);
        vm.warp(cdoEpoch.epochEndDate() + 1);
        _accrueMorphoVaultInterest();

        uint256 required =
            IdleCreditVault(address(strategy)).pendingWithdraws();
        uint256 shortfall =
            required - underlying.balanceOf(address(programmableBorrower));

        // On the mainnet fork, vaultLiquidityManipulator is a pre-existing
        // holder of the configured MetaMorpho vault's shares. The holder redeems
        // enough shares to leave less than `shortfall` immediately withdrawable,
        // while PB's shares still convert to at least `shortfall` assets.
        vm.startPrank(vaultLiquidityManipulator);
        morphoVault.redeem(
            morphoVault.balanceOf(vaultLiquidityManipulator),
            vaultLiquidityManipulator,
            vaultLiquidityManipulator
        );
        vm.stopPrank();

        assertGe(programmableBorrower.totalInterestDueNow(), 0);
        assertGe(
            morphoVault.convertToAssets(
                morphoVault.balanceOf(address(programmableBorrower))
            ),
            shortfall,
            "PB must remain economically covered"
        );
        assertLt(
            morphoVault.maxWithdraw(address(programmableBorrower)),
            shortfall,
            "test requires temporarily illiquid vault"
        );

        // The covered-position check passes, but the real withdrawal reverts and
        // bubbles through IdleCDOEpochVariant.stopEpoch.
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        vm.prank(manager);
        cdoEpoch.stopEpoch(0, 0);

        assertTrue(cdoEpoch.isEpochRunning(), "epoch must remain running");
        assertEq(
            IdleCreditVault(address(strategy)).pendingWithdraws(),
            required,
            "withdrawal receipts remain unfunded"
        );
    }
}
