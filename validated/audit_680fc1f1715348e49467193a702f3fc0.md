### Title
Attacker-controlled proof-instruction-offset fields let a malicious transaction shift which account is decoded as `owner`/`authority`/context-state accounts in SPL-Token-2022 confidential-extension instruction parsing - (File: `transaction-status/src/parse_token/extension/confidential_mint_burn.rs`)

### Summary
The bug-class described in the 1inch `OrderMixin` report is that attacker-supplied dynamic data can shift the byte offset at which subsequent "static" fields are decoded, causing the wrong data to be interpreted as trusted values. The Agave analog is in the JSON-RPC transaction-status instruction decoders for SPL-Token-2022 confidential extensions: the *position* (`offset` variable) used to pick which `account_indexes[i]` is labeled `owner`, `authority`, `instructionsSysvar`, or `*ProofContextStateAccount` is walked forward conditionally based on `equality_proof_instruction_offset`, `ciphertext_validity_proof_instruction_offset`, and `range_proof_instruction_offset` fields that come straight out of attacker-controlled instruction data. Since these are just integer fields decoded from raw bytes with no cross-check against the actual number of supplied accounts or real on-chain semantics, a transaction sender can pick values that desynchronize the offset walk from the real account layout, causing an unprivileged RPC client's `getTransaction`/`getBlock` result to report the wrong account address for a given semantic role.

### Finding Description
In `parse_confidential_mint_burn_instruction` (and the structurally identical `parse_confidential_transfer_instruction`, `parse_confidential_transfer_fee_instruction`, `parse_permissioned_burn` extension parsers), the code does: [1](#0-0) 

and then walks a mutable `offset` index into `account_indexes`, conditionally consuming a slot for `instructionsSysvar`, then for each of the three `*ProofContextStateAccount` fields, purely based on whether the corresponding `*_instruction_offset` value (deserialized straight from the raw instruction bytes via `decode_instruction_data`) is zero or non-zero: [2](#0-1) [3](#0-2) 

The only bound-check performed before indexing is `offset < account_indexes.len().saturating_sub(1)`, which prevents an out-of-bounds panic, but does nothing to ensure the offset field values are internally consistent with each other or with the real number of accounts supplied by the instruction. `check_num_token_accounts` only enforces a *minimum* account count: [4](#0-3) 

Because `decode_instruction_data`/`decode_instruction_type` merely deserialize the byte layout without validating that the offsets are realistic, an attacker who submits a transaction (which does not even need to succeed on-chain — transaction-status parsing occurs for both successful and failed transactions included in a block) can pick any combination of the three offset fields being zero/non-zero. This changes which `account_indexes[offset]` element is attributed to `instructionsSysvar` vs. `equalityProofContextStateAccount` vs. `ciphertextValidityProofContextStateAccount` vs. `rangeProofContextStateAccount` vs., finally, `owner`/`multisigOwner` via `parse_signers`. This directly parallels the 1inch bug: a value the attacker fully controls (the proof-instruction-offset fields, analogous to the dynamic `getTakerAmount`/`getMakerAmount` bytes) determines where in the account list the "static" role assignments (owner, authority) are read from.

### Impact Explanation
This is reachable from any unprivileged JSON-RPC caller of `getTransaction`/`getBlock`/`getConfirmedTransaction` for any transaction that references the SPL-Token-2022 program with these confidential-extension instructions, including transactions that fail at runtime but still land in a block (fee paid, no special privilege required to submit). The result is that the RPC-parsed `"parsed"` JSON for the instruction reports the wrong account as `owner`, `authority`, or one of the `*ProofContextStateAccount`/`instructionsSysvar` fields — i.e., wrong-account data returned from a read-only query, which can mislead wallets/block explorers/monitoring tooling relying on the parsed representation into believing a different account owns/authorizes the confidential operation than actually appears in the raw account list order.

### Likelihood Explanation
High likelihood of triggering: any account (no elevated privilege) can construct and submit (or even just build without submitting, since parsing only needs the compiled instruction bytes/accounts) a transaction targeting the token-2022 program ID with a `ConfidentialMintBurnInstruction::Mint`/`Burn`/analogous confidential-transfer instruction, with a handcrafted combination of the three offset fields, and a minimal accounts list satisfying only the "minimum count" check. A single RPC query to fetch/parse that transaction is sufficient to reproduce the misreport — this fits within the single-call reachability constraint.

### Recommendation
Do not let attacker-supplied offset fields alone determine which physical account slot is semantically labeled. Instead:
- Validate that the number of supplied accounts (`account_indexes.len()`) is exactly consistent with the *specific* combination of proof-instruction-offset flags before assigning any labels, and fail parsing (return `InstructionNotParsable`) rather than silently attributing accounts when the combination is inconsistent/ambiguous.
- Where possible, cross-validate offset field semantics (e.g., that at most one sysvar slot is expected, and that "zero" truly implies a local context-state account per the real program's instruction-processing logic) instead of trusting the raw decoded struct values directly for control flow that decides output attribution.

### Proof of Concept
1. Construct a `TokenInstruction`/`ConfidentialMintBurnInstruction::Mint` compiled instruction for the SPL-Token-2022 program ID with only the minimum required accounts (`destination`, `mint`, one additional account) and instruction data whose `equality_proof_instruction_offset`, `ciphertext_validity_proof_instruction_offset`, and `range_proof_instruction_offset` fields are set to a combination that does not correspond to any accounts the sender actually intends to supply for those roles (e.g., set `equality_proof_instruction_offset = 0` and the other two non-zero, while providing only 3 accounts total).
2. Submit (or simply serialize, since only compiled-instruction bytes matter for the parser) this transaction; on-chain it will fail with an SPL-Token-2022 program error but will still be included in the block along with its parsed `CompiledInstruction`.
3. Call `getTransaction`/`getBlock` via JSON-RPC for that transaction and observe that `parse_confidential_mint_burn_instruction` labels the wrong `account_keys[...]` entry as `equalityProofContextStateAccount`/`owner` compared to what the actual instruction accounts array intends, because the offset walk (`transaction-status/src/parse_token/extension/confidential_mint_burn.rs:115-164`) is driven entirely by attacker-chosen offset field values rather than the true account layout.
