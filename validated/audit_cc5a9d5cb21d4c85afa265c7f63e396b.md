### Title
Signer never persists `reject_reason` on the `check_block_against_signer_db_state` override path, permanently freezing a valid block behind `RejectedInPriorRound` - (File: stacks-signer/src/v0/signer.rs)

### Summary
`handle_block_validate_ok` and `handle_block_pre_commit` both call `check_block_against_signer_db_state`, and when it returns a rejection (e.g. `SortitionViewMismatch` or `ConnectivityIssues`, which are transient, chain-view-dependent verdicts) they call `block_info.mark_locally_rejected()` and store the block, but never assign `block_info.reject_reason`. Because `reject_reason` stays `None`, `should_reevaluate_reject_reason` treats the rejection as non-re-evaluable, so an identical re-proposal of the same block is answered forever with a stale `RejectedInPriorRound` rejection instead of being re-validated.

### Finding Description
The equality that should hold is: *"if the original rejection came from a reason class marked re-evaluable in `should_reevaluate_reject_reason`, a subsequent identical `BlockProposal` for the same `signer_signature_hash` must be re-checked against current chain state."* This equality is broken because the reason is never recorded in the first place.

- `check_block_against_signer_db_state` (`stacks-signer/src/v0/signer.rs:1803-1880`) returns a `BlockRejection` carrying `RejectReason::SortitionViewMismatch` (derived from `check_tenure_change_confirms_parent` / `check_latest_block_in_tenure`, which the accompanying docs describe explicitly as a "moving target" check tied to node tip advancement — `docs/signer-flows.md:391-423`) or `RejectReason::ConnectivityIssues` (a reason explicitly listed as re-evaluable in `should_reevaluate_reject_reason`, `stacks-signer/src/v0/signer.rs:2705-2718`).
- In `handle_block_validate_ok` (`stacks-signer/src/v0/signer.rs:1946-1959`), when this rejection fires, the code does:
  ```
  block_info.mark_locally_rejected();
  self.signer_db.insert_block(&block_info);
  self.handle_block_rejection(&block_rejection, sortition_state);
  self.send_block_response(&block_info.block, block_rejection.into());
  ```
  `block_info.reject_reason` is never set. Compare this to `handle_block_validate_reject` (`stacks-signer/src/v0/signer.rs:2045`), which explicitly does `block_info.reject_reason = Some(block_rejection.response_data.reject_reason.clone());` before inserting — the fix pattern already exists elsewhere in the file but is missing here.
- The identical omission occurs in `handle_block_pre_commit`'s chainstate re-check branch (`stacks-signer/src/v0/signer.rs:1345-1366`).
- `BlockInfo::from(BlockProposal)` initializes `reject_reason: None` (`stacks-signer/src/signerdb.rs:233-250`), and this is never overwritten on these two paths, so the persisted `BlockInfo.reject_reason` stays `None`.
- `should_reevaluate_reject_reason` (`stacks-signer/src/v0/signer.rs:2705-2739`) has: `if let Some(reject_reason) = &block_info.reject_reason { match ... } else { false }`. A `None` reject_reason always evaluates to `false` (non-re-evaluable), regardless of what the *actual* underlying rejection reason was (even one on the "should be re-evaluable" list such as `ConnectivityIssues`).
- Consequently, when the miner re-broadcasts the byte-identical `BlockProposal` (same `signer_signature_hash`), `handle_block_proposal` → `should_reevaluate_block` (`stacks-signer/src/v0/signer.rs:1481-1572`) takes the `!should_reevaluate_reject_reason` branch, the state is not `PreCommitted`, so it falls to `determine_response(block_info)` (`stacks-signer/src/v0/signer.rs:458-471`), which reads `block_info.valid == Some(false)` and unconditionally returns `Some(Rejected(RejectReason::RejectedInPriorRound))`. The signer never calls `submit_block_for_validation` again, so the local, node-side, and pre-commit chainstate re-checks that would resolve the transient condition (e.g., the tenure tip catching up) never run again for this block hash.
- No existing guard rescues this: `block_lookup_by_reward_cycle` finds the same tracked `BlockInfo` by `signer_signature_hash`; `globally_approved_and_responded()` is false (block was rejected, not accepted); there is no timeout or expiry that resets `reject_reason` or `valid` back to `None` for a `LocallyRejected` block absent a fresh proposal that actually changes `should_reevaluate_reject_reason`'s answer — and the answer can never change here because the field is permanently `None`.

### Impact Explanation
This is a liveness break matching the High-severity category "a signer wedged into never signing valid blocks." A single valid, canonical block that happened to race the check at validate-ok/pre-commit time (e.g., the node's tenure tip not yet reflecting a just-signed parent, or a transient `ConnectivityIssues` blip) gets permanently marked `LocallyRejected` in that signer's `SignerDb`, keyed by `signer_signature_hash`. Any later re-delivery of the identical proposal (which miners do routinely on rejection/timeout, and which the audited class allows an attacker to trigger via ordinary gossip of the same crafted `BlockProposal`) is answered with a stale `RejectedInPriorRound` without ever re-submitting to the node or re-running the chainstate checks. The affected signer's vote is permanently withheld from that specific block for the life of the process (the signer DB entry persists), reducing the effective voting weight available for that block and potentially preventing it from reaching the 70% threshold if enough signers are affected by the same race. This is repeatable per-block and does not require majority signer weight, node compromise, or the auth_token.

### Likelihood Explanation
The precondition is a benign race that is not attacker-exotic: the node's tenure tip lagging the signer's own bookkeeping (or a fetch error) at exactly the moment `check_block_against_signer_db_state` runs during `handle_block_validate_ok` or `handle_block_pre_commit`. This is the same class of race the `NotFoundError`/`UnknownParent` handling in `should_reevaluate_reject_reason` was designed to fix (see `stacks-node/src/tests/signer/v0/missing_burn_block_proposal.rs:64-67` for the intended re-evaluable behavior), but `SortitionViewMismatch`/`ConnectivityIssues` produced via this specific code path never even get their reason recorded, so they can't benefit from that mechanism. An attacker with a single miner slot can increase the likelihood of hitting this race (e.g., by proposing tenure-change blocks quickly relative to node processing, or by re-gossiping proposals at moments likely to race validation), and once triggered the effect is deterministic and permanent for that `signer_signature_hash` on the affected signer(s), with no cost beyond crafting/gossiping the proposal.

### Recommendation
Persist the actual `RejectReason` on `block_info` on both override paths before `insert_block`/response, mirroring `handle_block_validate_reject`:
- In `handle_block_validate_ok`'s `check_block_against_signer_db_state` branch (`stacks-signer/src/v0/signer.rs:1946-1959`), add `block_info.reject_reason = Some(block_rejection.response_data.reject_reason.clone());` before `mark_locally_rejected()`/`insert_block`.
- In `handle_block_pre_commit`'s equivalent branch (`stacks-signer/src/v0/signer.rs:1345-1366`), do the same.
This restores the intended invariant that `should_reevaluate_reject_reason` can correctly classify the rejection and allow re-validation once the underlying (transient) condition changes.

### Proof of Concept
Rust unit test plan (in `stacks-signer/src/v0/tests.rs`, alongside `run_sibling_scenario`/`run_cross_tenure_scenario` helpers):
1. Construct a `Signer` + mock node such that `handle_block_validate_ok` for block `B` triggers the `check_block_against_signer_db_state` branch returning `Some(BlockRejection { reason_code: SortitionViewMismatch, .. })` (e.g., mock `get_tenure_tip` so `check_latest_block_in_tenure` returns `Ok(false)`).
2. Call `node.signer.process_event(..., Some(&validate_ok(&hash_b)), ...)`.
3. Assert via `signer_db.block_lookup(&hash_b)` that `state == LocallyRejected`, `valid == Some(false)`, and **assert `reject_reason.is_none()`** (demonstrating the missing persistence — this is the bug reproduction).
4. Change the mock so `check_latest_block_in_tenure` would now return `Ok(true)` (simulating the transient condition resolving, e.g., node tip caught up).
5. Re-deliver the byte-identical `BlockProposal` for `B` via `process_event(..., Some(&SignerEvent::MinerMessages(vec![proposal_b])), ...)`.
6. Assert that the signer's outgoing `BlockResponse` for `hash_b` is `Rejected(RejectedInPriorRound)` (stale) and that **no** new call to `submit_block_for_validation`/node validation endpoint occurred (e.g., via a call-counter on the mock client) — proving the signer never re-submits this valid canonical block despite the underlying condition having resolved.
7. Contrast with the fix: after adding the `reject_reason` assignment, step 3's assertion changes to `reject_reason == Some(RejectReason::SortitionViewMismatch)`, and step 6 shows `should_reevaluate_reject_reason` returning `true` (since `SortitionViewMismatch` needs to be added to the re-evaluable list) or at minimum a correctly-classified reason, restoring re-validation.
