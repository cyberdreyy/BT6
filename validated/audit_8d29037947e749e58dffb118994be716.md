### Title
Direct token donation to `IdleCDOCreditVault` inflates tranche price via `getContractValue`, enabling a first-depositor share-inflation attack that steals subsequent depositors' funds - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault.getContractValue` computes NAV as `balanceOf(strategyToken) + balanceOf(token) - unclaimedFees` ( [1](#0-0) ). The raw `token` balance is manipulable by any unprivileged sender via a direct ERC20 `transfer`. `_updateAccounting` consumes this inflated NAV on every deposit/withdraw ( [2](#0-1) ), so a donation is booked as a gain and pushed into `priceAA`/`priceBB` through `_virtualPriceAux`. Combined with share minting that floors at `_amount * ONE_TRANCHE_TOKEN / _tranchePrice` and never reverts on zero minted shares ( [3](#0-2) ), an attacker holding the entire supply can donate to make the share price exceed a victim's deposit, causing the victim to receive 0 tranche tokens while their underlying remains in the NAV owned by the attacker.

### Finding Description
The external report (Real Wagmi `Multipool`) flags `balanceOf(address(this))` as an undependable reserve because anyone can transfer tokens in. The same pattern exists here:

- `_contractTokenBalance` is a raw `balanceOf(address(this))` ( [4](#0-3) ).
- `getContractValue` includes the raw `token` balance in NAV, even though the code comments elsewhere acknowledge raw underlyings "are excluded because unsolicited transfers are skimmed" — that exclusion only applies to `_managedContractValue`, which `virtualPrice` uses, while the state-changing path `_updateAccounting` uses `getContractValue` ( [5](#0-4) ).
- In `_virtualPriceAux`, a positive `totalGain` (donation minus performance fee) is allocated to tranches; when only one tranche class has NAV, `_totalTrancheGain = totalGain` for that class ( [6](#0-5) ), so `priceAA` becomes `(1 wei NAV + donation) / 1 wei supply`.
- `_deposit` measures the received amount by balance delta (`_contractTokenBalance(_token) - _preBal`) and mints at the manipulated price ( [7](#0-6) ). There is no `require(_minted > 0)` and no dead-share/minimum-liquidity protection: when supply is zero, `_tranchePrice` returns `oneToken` ( [8](#0-7) ).

Attack sequence (epoch buffer / running phase, fixed-APR or AYS mode; attacker is a KYC-passing lender, all privileged roles honest):

1. Attacker is the first depositor: `depositAA(1)` → minted 1 wei of AA tranche at price `oneToken`; `lastNAVAA = 1`.
2. Attacker directly transfers `D` of `token` to the CDO (no skim in `_deposit`; strategy only ever pulls the explicit `_amount`).
3. Victim calls `depositAA(A)` where `A < ~D`. `_updateAccounting` computes `nav ≈ 1 + D`, books the gain (minus fee), sets `priceAA ≈ D`. `_mintSharesAtCurrPrice` computes `A * 1e18 / D = 0` shares. `IdleCDOTranche.mint(victim, 0)` succeeds; `lastNAVAA += A`.
4. The victim's `A` stays as raw token balance inside `getContractValue`, so the attacker's single share now claims essentially the whole NAV (`~1 + D + A`). The attacker later exits via the normal withdraw/claim path, recovering `D` plus stealing `A`.

Existing guards do not stop it: there is no skim of donated underlyings on the CDO deposit path, no minimum first-deposit/dead-share lock, no zero-mint revert, and `skipDefaultCheck`/`Default` logic is irrelevant since the donation registers as a gain, not a loss.

### Impact Explanation
The entire deposit of each subsequent depositor smaller than the donation-scaled price is stolen. With `D` chosen large (e.g., an amount comparable to expected first real deposits), the attacker captures the victim's full principal. Loss is direct theft of user funds, quantified as `A` per victim; the attacker's only cost is the performance fee on `D` (which accrues to honest `feeReceiver`/owner) plus gas.

### Likelihood Explanation
Requires the attacker to be the first depositor (or to dominate supply while a tranche class is near-empty) and to pass KYC/allowlisting, which the threat model permits. No privileged cooperation, no oracle manipulation, and no loss event is needed — only the ordering of the first deposits. Front-running the vault's first real deposit after deployment/unpause is the realistic window.

### Recommendation
- In `_deposit` (and any epoch deposit path), skim raw `token` donations before `_updateAccounting` — e.g., compute NAV from `strategyToken` balance only (`_managedContractValue`) and sweep unsolicited `token` into the strategy or a separate escrow — or track NAV internally rather than via `balanceOf`.
- Revert when `_minted == 0` in `_mintSharesAtCurrPrice`, and/or mint a minimum amount of dead shares on initialization to make inflation attacks uneconomical.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

// Foundry fork test against a live IdleCDOCreditVault (AA-only vault assumed;
// symmetric for BB when isBBDepositEnabled). `vault` = IdleCDOCreditVault proxy,
// `underlying` = vault.token(), `aa` = vault.AATranche().

function test_donationInflation_stealsFirstRealDeposit() public {
    address attacker = makeAddr("attacker"); // KYC-passed lender
    address victim   = makeAddr("victim");   // KYC-passed lender

    uint256 D = 1_000_000e6;   // donation, scaled to expected deposits
    uint256 A = 500_000e6;     // victim deposit (< effective price/share)

    deal(address(underlying), attacker, D + 1);
    deal(address(underlying), victim, A);

    // 1) Attacker seeds supply with 1 wei
    vm.startPrank(attacker);
    underlying.approve(address(vault), type(uint256).max);
    vault.depositAA(1);
    assertEq(aa.balanceOf(attacker), 1);
    // 2) Donation: raw token balance enters getContractValue()
    underlying.transfer(address(vault), D);
    vm.stopPrank();

    // 3) Victim deposits at manipulated price -> 0 shares minted
    vm.startPrank(victim);
    underlying.approve(address(vault), type(uint256).max);
    uint256 minted = vault.depositAA(A);
    vm.stopPrank();
    assertEq(minted, 0);
    assertEq(aa.balanceOf(victim), 0);

    // 4) Attacker's single share claims ~the whole NAV (1 + D + A - fees)
    uint256 nav = vault.getContractValue();
    uint256 attackerValue = aa.balanceOf(attacker) * vault.virtualPrice(address(aa)) / 1e18;
    assertGt(attackerValue, D);            // recovered donation + victim's A (minus fee)
    assertApproxEqAbs(attackerValue, nav, nav / 100);
}
```
Note: exact exit mechanics depend on the vault's epoch mode (buffer/running/stopped); the attacker completes the theft via the normal `requestWithdraw`/`claimWithdrawRequest` flow or instant withdraw, since the donated/victim funds remain NAV-backed. I was not able to confirm within this iteration whether `IdleCDOEpochVariant` or `IdleCreditVault` adds a `_skimDonatedAssets` step on the epoch deposit path; if such a skim runs *before* `_updateAccounting` on every deposit entry point, the practical exploitability narrows to paths that skip it — that should be verified before severity assignment.
