One more check on the post-default request path and CDO gating.### Title
Post-default withdraw requests pay par from the recovery reserve, draining funds reserved for haircutted claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
After `finalizeDefaultRecovery`, `defaultRecoveryReserve` is denominated in "basis × recoveryPrice" units — it only covers defaulted claimants at the haircut `defaultRecoveryPrice`. But `_claimPostDefaultWithdrawRequest` pays post-default receipts 1:1 out of that same reserve without ever adding them to `totalBasis`. A tranche holder can convert a haircut-priced claim into a par-paid receipt and withdraw more than their fair share, leaving the reserve underfunded so later defaulted claimants' claims permanently revert on underflow.

### Finding Description
The external bug is an accounting-units mismatch (a struct read past its real size, producing a value that was never backed). The analog here is the same class: two different claim denominations share one reserve pool.

1. `finalizeDefaultRecovery` sizes the reserve as `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` and stores `defaultRecoveryReserve = reserveAmount` (IdleCreditVault.sol:686-692). At a haircut (`recoveryPrice < RECOVERY_FULL`), total legitimate obligations equal `totalBasis * recoveryPrice / RECOVERY_FULL ≈ reserveAmount` — the reserve is exactly exhausted by haircutted claims.

2. After finalization, `requestWithdraw` (IdleCreditVault.sol:247-257) lets any user with no open request burn `_amount` of (already haircut-priced, via `virtualPrice`) value and record `postDefaultRequests[_user] = _amount`. The CDO path is reachable because the default/close path re-enables `allowAAWithdrawRequest`/`allowBBWithdrawRequest` and zeroes `epochDuration` (IdleCDOEpochVariant.sol:217-224), so `_calcInterestWithdrawRequest` returns zero interest and `requestWithdraw` passes roughly the haircut principal straight through.

3. `claimWithdrawRequest` → `_claimPostDefaultWithdrawRequest` (IdleCreditVault.sol:760-767) pays the full `amount` via `_transferDefaultRecovery`, which does `defaultRecoveryReserve -= _amount` (line 915) — in raw underlying units, not haircut units.

So each post-default claim consumes `1/recoveryPrice` times what a same-sized defaulted claim consumes. The reserve was never sized for this: post-default basis was never added to `totalBasis`. Once early claimants drain it, `_transferDefaultRecovery` underflows on the subtraction and all remaining defaulted/post-default claims revert permanently — the recovery reserve is stolen/locked, not merely delayed.

### Impact Explanation
Direct theft plus permanent freezing of unclaimed recovery. Example: `totalBasis = 200`, `reserveAmount = 100` → `recoveryPrice = 0.5`. Attacker's tranche claim is worth 50 post-haircut. They request post-default withdraw of 50 and claim 50 at par — 2x the 25 they'd get as a defaulted claimant. Reserve left = 50 for the remaining 150 basis of defaulted claims (owed 75); the last claimants' claims revert on underflow forever. Attacker needs only KYC-passed tranche tokens, an unprivileged role.

### Likelihood Explanation
Requires a borrower default followed by `finalizeDefaultRecovery` — a privileged-but-honest sequence the rules explicitly allow sequencing around. After that, any tranche holder can call `requestWithdraw`/`claimWithdrawRequest` permissionlessly; no timing race or additional privileged action is needed. The only unverified detail is whether any `defaulted`-state revert in the CDO's `requestWithdraw` path (e.g., inside `_updateAccounting` or fee accounting) blocks new requests — the code shows no explicit `defaulted` check in `requestWithdraw`, and the vault explicitly implements the post-default request branch (lines 247-257), indicating this flow is intended to be live.

### Recommendation
Pay post-default claims from a separately tracked reserve, or fund them at request time: in `requestWithdraw`'s post-default branch, either (a) immediately escrow `amount` into a new `postDefaultReserve` incremented with each request and decremented on claim, keeping `defaultRecoveryReserve` untouched, or (b) require the claim to be funded by newly deposited underlying rather than the recovery pool. At minimum, decrement `defaultRecoveryReserve` in basis units or revert if post-default claims would consume reserve allocated to pre-default claimants.
