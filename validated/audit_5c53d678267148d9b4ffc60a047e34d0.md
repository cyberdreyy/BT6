### Title
Stale `instantWithdrawClaimsByEpoch` counts already-claimed instant receipts in `defaultPendingClaimBasis`, diluting and permanently locking default-recovery funds - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When an instant-withdraw receipt is funded and claimed before a default, `claimInstantWithdrawRequest` clears the user's aggregate `instantWithdrawsRequests` but never decrements the per-epoch totals `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`. If the borrower defaults later in that same epoch while other instant receipts remain unfunded, `defaultPendingClaimBasis()` adds the full stale epoch total to the recovery basis. `finalizeDefaultRecovery` then computes `defaultRecoveryPrice` over an inflated `totalBasis`, so every legitimate claimant is underpaid and the excess recovery stays locked in `defaultRecoveryReserve` forever — a use-after-free style bug where a "freed" (already-paid) claim is counted again.

### Finding Description
`requestInstantWithdraw` records both per-user and per-epoch basis:

```
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
``` [1](#0-0) 

But the normal funded-claim path clears only the aggregate:

```
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [2](#0-1) 

Neither `instantWithdrawsRequestsByEpoch[_user][epoch]` nor `instantWithdrawClaimsByEpoch[epoch]` is decremented, even though the doc comment describes it as "total *outstanding* instant-withdraw receipt basis per request epoch" [3](#0-2) .

At default finalization the stale epoch total is folded into the recovery denominator whenever any instant receipt is still unfunded:

```
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
``` [4](#0-3) 

and

```
uint256 totalBasis = activeBasis + pendingBasis;
uint256 recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis;
``` [5](#0-4) 

`_claimDefaultedInstantWithdrawRequest` pays each still-unclaimed user `claimBasis * defaultRecoveryPrice` from the reserve, so a claim that was already paid at par pre-default is counted a second time in the denominator [6](#0-5) .

### Impact Explanation
Attack sequence (attacker = any KYC'd instant-withdraw user):

1. Epoch N starts. Attacker A calls `requestInstantWithdraw(X)`; victim B calls `requestInstantWithdraw(Y)`. `instantWithdrawClaimsByEpoch[N] = X + Y`.
2. Manager's `getInstantWithdrawFunds` only pulls enough for A (`collectInstantWithdrawFunds(X)`), leaving `pendingInstantWithdraws = Y`. A claims `X` at par — aggregate cleared, per-epoch `X` stays.
3. Epoch N ends with borrower default (`stopEpoch(0,0)` → `defaulted()`).
4. `finalizeDefaultRecovery` computes `totalBasis` including the stale `X`. `defaultRecoveryPrice` is diluted by a factor of `(realBasis + X) / realBasis`.
5. B (and defaulted normal withdrawers) each recover proportionally less; `X * defaultRecoveryPrice` worth of underlying remains permanently stranded in `defaultRecoveryReserve` because no claim function can ever consume the phantom basis — `postDefaultRequests` payouts 1:1 and defaulted claims are capped by their real per-user basis.

Broken invariant: the recovery denominator must equal exactly the outstanding claims. Result: permanent freezing of up to `X` (scaled by the recovery price) of recovered funds, and underpayment of all legitimate default claimants. The attacker profits indirectly only if they also hold a defaulted claim (they requested `X` before default — it was already paid at par, so the main loss is locked yield; combining with a genuine defaulted receipt still nets underpayment for everyone).

### Likelihood Explanation
Requires: instant withdrawals enabled, partial prefunding of the instant queue in the defaulted epoch, one claimant who claims before default while another stays unfunded, then `finalizeDefaultRecovery`. This is a realistic sequencing — the code explicitly anticipates "mixed funded and unfunded instant claims" in the same epoch (see test `testFinalizeDefaultClaimsFundedAndDefaultedInstantRedeemsInOneCall`), but that test only covers receipts still *unclaimed* at finalization. Nothing prevents a user from completing a funded claim first, which is exactly when the stale epoch basis is left behind. Likelihood is moderate: the timing window (claim between `collectInstantWithdrawFunds` and epoch-end default) is attacker-controllable only insofar as they can watch the mempool for the default.

### Recommendation
In `claimInstantWithdrawRequest`, after computing `amount`, decrement the per-epoch trackers when the claim is paid at par (track which epoch(s) the funded portion belongs to, or subtract from `instantWithdrawClaimsByEpoch` for the epoch in which the request was made). Alternatively, in `defaultPendingClaimBasis`, add only the unfunded portion — e.g. cap the instant basis at `pendingInstantWithdraws` plus outstanding unclaimed funded receipts, rather than the lifetime epoch total. Add a regression test: user A's instant claim fully paid pre-default, user B unfunded, then default + `finalizeDefault`, asserting `defaultRecoveryPrice` is computed on B's basis only.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `_checkDefault`):

```solidity
function testStaleInstantBasisDilutesRecovery() external {
    address userA = makeAddr('stale-instant-A');
    address userB = makeAddr('victim-instant-B');
    uint256 amountA = 10_000 * ONE_SCALE;
    uint256 amountB = 10_000 * ONE_SCALE;
    _depositWithUser(userA, amountA, true);
    _depositWithUser(userB, amountB, true);

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // buffer: both request instant withdraw in epoch 1
    vm.prank(userA);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // routed to instant per config
    vm.prank(userB);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(1);
    IdleCreditVault cv = IdleCreditVault(address(strategy));

    // manager funds only A's instant request
    uint256 basisA = cv.instantWithdrawsRequests(userA);
    // ... call getInstantWithdrawFunds with only A's amount via manager/cdoEpoch ...

    // A claims at par; instantWithdrawClaimsByEpoch[1] still includes A's basis
    vm.prank(userA);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(cv.instantWithdrawsRequests(userA), 0);
    assertGt(cv.instantWithdrawsRequestsByEpoch(userA, 1), 0); // stale basis remains

    // borrower defaults in epoch 1
    deal(defaultUnderlying, borrower, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _checkDefault();

    // finalize: totalBasis inflated by A's already-paid claim
    uint256 inflatedBasis = cv.defaultPendingClaimBasis(); // includes A's stale X
    uint256 recovered = /* enough for B's real basis at e.g. 70% */;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // B is underpaid; dust remains locked in defaultRecoveryReserve
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(userB);
    vm.prank(userB);
    cdoEpoch.claimInstantWithdrawRequest();
    // assert B received less than basisB * intendedPrice and reserve retains ~basisA * price
    assertGt(cv.defaultRecoveryReserve(), 0); // permanently stranded
}
```

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
