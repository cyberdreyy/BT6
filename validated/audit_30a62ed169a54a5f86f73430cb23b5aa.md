### Title
Cross-sender response hijacking via unkeyed `savedCallbacks` map in dummy handler - ([File: core/services/gateway/handlers/handler.dummy.go])

### Summary
`dummyHandler` stores pending user callbacks in `d.savedCallbacks` keyed solely by `msg.Body.MessageId`, with no sender/requester binding, unlike the sender-aware `globalId{sender, id}` keying used elsewhere in the gateway (e.g. `common/requestcache.go`). A client-controlled `MessageId` (the JSON-RPC request `ID`, or legacy `msg.Body.MessageId`) let an attacker overwrite another in-flight requester's map entry and receive the response destined for that requester, or redirect the attacker's forged response into the victim's callback.

### Finding Description
`gateway.ProcessRequest` decodes the client's JSON-RPC request and passes the client-supplied `jsonRequest.ID` straight through as the message identifier: for legacy requests it validates `msg.Body.MessageId` is present via `msg.Validate()` and dispatches to `HandleLegacyUserMessage`; for new-style requests `HandleJSONRPCUserMessage` sets `msg.Body.MessageId = jsonRequest.ID` [1](#0-0) [2](#0-1) .

In `dummyHandler.HandleLegacyUserMessage`, the callback is stored keyed only by `msg.Body.MessageId`, with no binding to the caller's signer/sender identity: [3](#0-2) 

When the DON's response arrives, `HandleNodeMessage` only checks that `nodeAddr == msg.Body.Sender` (i.e., that the responding node is a legitimate DON member) — it performs no check tying the response back to the specific original requester who submitted the message with that ID: [4](#0-3) 

Because the map key has no sender component, if a victim submits a request with `MessageId = "dup"` and, before the DON responds, an attacker submits a distinct signed request also using `MessageId = "dup"`, the attacker's `savedCallback` overwrites the victim's entry in `d.savedCallbacks["dup"]`. When the DON later returns the response for the victim's original request (with matching `nodeAddr`/`Sender` — both are the legitimate node, so that check does not detect the substitution), `HandleNodeMessage` looks up `d.savedCallbacks["dup"]`, finds the attacker's callback, deletes the entry, and delivers the victim's response to the attacker. The same overwrite also allows the reverse: an attacker's own forged request's eventual response could be steered to a victim's still-registered callback if timing/keys align.

The comparable `common/requestcache.go` used by the capabilities handler package avoids exactly this problem by keying on `globalId{sender, id}` rather than `id` alone, confirming this is a design regression specific to `handler.dummy.go`, not an inherent constraint of the gateway's message model.

### Impact Explanation
This is cross-user response confusion / unauthorized disclosure: an attacker with only a valid signing key can hijack another party's gateway response, potentially exfiltrating data intended for a different job/user, or cause response mixups that could be leveraged for job-run confusion in DON-routed workflows. This is a "leaking sensitive information" / "request impersonation" style disclosure between two node clients of the same gateway instance.

### Likelihood Explanation
Exploitability requires only: (1) the ability to send a signed gateway message (no privileged role needed — "any address sending signed gateway requests" is explicitly an in-scope unprivileged attacker), and (2) knowledge or a guess of a currently pending victim `MessageId`. `MessageId` is fully client-supplied (the JSON-RPC `ID` field) and only bounded by a length check (`<= 200` chars) — there is no uniqueness/collision protection beyond what the map itself would provide if it were sender-scoped. If message IDs are predictable (sequential counters, timestamps, or a fixed value used by an integration), collision is trivial; even for random IDs, an attacker who can observe outbound traffic or coordinate with the victim's client (e.g., shared infra, replay of an intercepted ID) can trigger it. The window is a normal DON round-trip, which is not instantaneous, making the race practically feasible. However, this only applies when `DummyHandlerType` is configured (`core/services/gateway/handler_factory.go`), which by its own naming/comments appears intended as a reference/dummy implementation rather than a hardened handler, so the exposure is limited to deployments using this handler type.

### Recommendation
Bind `savedCallbacks` entries to both `MessageId` and requester identity, mirroring `common/requestcache.go`'s `globalId{sender, id}` keying: key the map by `(msg.Body.Sender, msg.Body.MessageId)` (using the signer address recovered/validated during message signature verification), and in `HandleNodeMessage` require the DON's echoed sender/receiver metadata to match the same composite key before delivering to the stored callback. Reject/overwrite protection should also detect duplicate in-flight `MessageId`s from different senders and return an error rather than silently overwriting.

### Proof of Concept
1. In `core/services/gateway/handlers/handler.dummy_test.go`, extend `TestDummyHandler_BasicFlow`:
   - Create two distinct signed `api.Message` objects (`victimMsg`, `attackerMsg`) with the same `Body.MessageId = "dup"` but different signers/`Sender`.
   - Concurrently (goroutine 1 and 2) call `dummyHandler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)` and `HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)`, synchronized so the attacker's call runs after the victim's map insert but before the node response.
   - Assert (via test hook or small sleep/sync) that `d.savedCallbacks["dup"]` now points to the attacker's callback, overwriting the victim's.
   - Simulate the DON's response for the victim's original request by calling `HandleNodeMessage(ctx, victimResponse, nodeAddr)`.
   - Assert `victimCallback.Wait()` never receives a response (or times out) while `attackerCallback.Wait()` incorrectly receives the victim's response — demonstrating the hijack.
   - Expect this test to fail against current code (attacker receives victim's data) and to pass once composite `(sender, id)` keying is implemented.

func (d *dummyHandler) HandleJSONRPCUserMessage(ctx context.Context, jsonRequest jsonrpc.Request[json.RawMessage], callback Callback) error {
	var msg api.Message
	if jsonRequest.Params != nil {
		if err := json.Unmarshal(*jsonRequest.Params, &msg); err != nil {
			return err
		}
	}
	msg.Body.MessageId = jsonRequest.ID
	if msg.Body.Method == "" {
		msg.Body.Method = jsonRequest.Method
	}
	if msg.Body.DonId == "" {
		msg.Body.DonId = d.donConfig.DonId
	}
	return d.HandleLegacyUserMessage(ctx, &msg, callback)
}

func (d *dummyHandler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	var msg api.Message
	err := json.Unmarshal(*resp.Result, &msg)
	if err != nil {
		return err
	}
	msg.Body.MessageId = resp.ID
	err = msg.Validate()
	if err != nil {
		return err
	}
	if nodeAddr != msg.Body.Sender {
		return fmt.Errorf("node address %s does not match message sender %s", nodeAddr, msg.Body.Sender)
	}
	d.mu.Lock()
	savedCb, found := d.savedCallbacks[msg.Body.MessageId]
	delete(d.savedCallbacks, msg.Body.MessageId)
	d.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(&msg), ErrorCode: api.NoError})
	}
