### Title
Missing `return` After Email-Claim Extraction Failure Lets OIDC Login Continue with Empty Owner Identity - (File: core/sessions/oidcauth/oidc.go)

### Summary
`handleTokenExchange` in `core/sessions/oidcauth/oidc.go` mirrors the reported `CoreLib.delegateCall()` bug class: an error/failure branch performs error handling (logging + writing an HTTP response) but does not halt execution, so the function "continues to execute" past a failed operation, exactly as the report describes for the missing revert on `delegatecall` failure.

### Finding Description
In `handleTokenExchange`, after the OIDC ID token is verified and claims are parsed, the code extracts the user's email: [1](#0-0) 
```
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
```
Unlike every other failure branch in this function (e.g. the `id_token` extraction check at [2](#0-1) , the claims-parsing check at [3](#0-2) , or the role-mapping check at [4](#0-3) ), this branch is missing a `return` statement. Execution falls through with `email == ""`, and the function proceeds to:
- Map the (still valid) group claims to an RBAC role via `IDClaimsToUserRole` [5](#0-4) 
- Create a new session and insert it into `oidc_sessions` with the empty email [6](#0-5) 
- Audit-log a successful login [7](#0-6) 
- Set the session cookie and return `200 OK` with `Success: true` to the browser [8](#0-7) 

This is structurally identical to the reported bug: a failure condition is detected and "handled" (an error response is written), but because execution is not halted, the surrounding logic proceeds as if the operation succeeded — the same "incomplete error handling" root cause called out in the delegatecall report ("does not revert on failure ... continues to execute").

### Impact Explanation
A valid, attested OIDC identity token that simply lacks a top-level `email` claim (or where the IdP's discovery/scope configuration does not surface `email` as a plain string — e.g., returns it nested, omits it, or the provider doesn't include `email` in the `id_token`, which is common when only `openid profile` scopes are effectively granted) results in the DON creating and cookie-authenticating a live, role-bearing session tied to an empty-string owner (`user_email = ''` in `oidc_sessions`). Any RBAC role (including `UserRoleAdmin`, if the caller's provider group claims map to the admin claim) can be attached to this identity-less session. Because the HTTP response still claims `Success: true` with `200 OK` and a valid session cookie is set, the client ends up authenticated to the node's web/API surface (session-cookie-authenticated GraphQL/REST endpoints) without a real, attributable user identity — undermining node-operator authentication/audit invariants and potentially colliding with any other session that also has an empty email, since `oidc_sessions` rows are looked up/reaped by `user_email`.

### Likelihood Explanation
This is directly reachable by any external, unprivileged client that can complete an OIDC authorization-code exchange with the configured identity provider — no chainlink-node privilege is required to trigger it, only control (or misconfiguration) over what claims the ID token contains. Because Go's `,ok` type-assertion silently returns `false` for any claim that's missing, `nil`, or of the wrong JSON type, this can be triggered by many benign real-world IdP configurations (not just malicious ones), making it moderately likely to occur in practice.

### Recommendation
Add a `return` immediately after the `c.String(http.StatusInternalServerError, "Failed to get email from claims")` call, consistent with every sibling error branch in this function:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Additionally, consider validating that `email != ""` before proceeding, and reviewing the analogous fire-and-forget error branch a few lines later at the `oidc_sessions` INSERT failure path [9](#0-8) , which has the same missing-`return` pattern and would let a failed session-insert still proceed to set an authenticated cookie referencing a non-persisted session.

### Proof of Concept
1. Configure the chainlink node with OIDC auth (`webauth` OIDC driver) against an IdP/test provider whose `id_token` claims omit the `email` field (or set it to a non-string type), while still supplying whatever group/claim value maps to a permitted RBAC role via `ClaimName()`.
2. As an unauthenticated client, perform the standard OIDC flow: hit `handleSignIn` to get `state`/redirect, complete the provider's login, then POST the resulting `code`/`state` to the token-exchange endpoint backed by `handleTokenExchange`.
3. Observe that despite `claims["email"].(string)` failing (`ok == false`) and an `Internal Server Error` string being written to the response body, execution continues: the response is overwritten with a final `200 OK` `{"success":true}` JSON body, and a valid session cookie (`SessionIDKey`) is set.
4. Use the returned cookie against a session-authenticated endpoint (e.g. `AuthenticateBySession` / `AuthenticateGQL` in `core/web/auth/auth.go` and `core/web/auth/gql.go`) and confirm the request is treated as authenticated with the mapped role, despite no real email/user identity ever being validated or stored correctly.
