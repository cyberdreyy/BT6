The strongest analog candidate: re-calling `requestWithdraw` after a loss epoch to move `lastWithdrawRequest` forward and escape the loss haircut. Let me verify the relevant logic.### Title
Re-requesting a withdrawal after a loss epoch escapes the loss-adjusted haircut and is paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` unconditionally overwrites `lastWithdrawRequest[_user]` with the current epoch. `_claimLossAdjustedWithdrawRequest` only looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. only the *latest* request epoch. A user whose receipt sits in a loss epoch (priced via `lossRecoveryPriceByEpoch` by `stopEpochWithDuration(_lossAmount)`) can submit a new `requestWithdraw` in a later epoch, moving `lastWithdrawRequest` forward so the loss-adjusted path early-returns (`lossRecoveryPrice == 0`), and the old receipt — never cleared via `_clearWithdrawClaimForEpoch` — remains inside `withdrawsRequests[_user]` and is paid at par by `_claimFundedWithdrawRequest`. Same bug class as the Carapace report: an unguarded repeat of the normal entry point bypasses a restricted settlement path.

### Finding Description
- `requestWithdraw` burns CDO strategy tokens, mints a 1:1 receipt to the user, adds `_amount` to `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]`, and sets `lastWithdrawRequest[_user] = currentEpoch` with no check on prior pending receipts [1](#0-0) .
- `claimWithdrawRequest` tries `_claimDefaultedWithdrawRequest`/`_claimPostDefaultWithdrawRequest` (only after `defaultRecoveryFinalized`), then `_claimLossAdjustedWithdrawRequest`, then `_claimFundedWithdrawRequest` [2](#0-1) .
- `_claimLossAdjustedWithdrawRequest` derives the epoch solely from `lastWithdrawRequest[_user]`; any epoch ≠ latest is skipped forever [3](#0-2) .
- `_claimFundedWithdrawRequest` pays the entire remaining `withdrawsRequests[_user]` at par once `epochNumber > lastWithdrawRequest[_user]` [4](#0-3) .
- `_clearWithdrawClaimForEpoch` is the only place the old epoch's share is removed from `withdrawsRequests[_user]`; because the lookup epoch moved, it is never invoked for the loss epoch [5](#0-4) .

Attack trace (loss mode, non-APR0):
1. Running epoch N: attacker calls `IdleCDOEpochVariant.requestWithdraw` → `IdleCreditVault.requestWithdraw`; receipt recorded at `withdrawsRequestsByEpoch[attacker][N]`, `lastWithdrawRequest = N`.
2. Borrower repays with shortfall; manager calls `stopEpochWithDuration(_lossAmount)` → `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL`; `epochNumber` bumps to N+1.
3. New epoch N+1 starts. Attacker calls `requestWithdraw` again with a dust amount → `lastWithdrawRequest = N+1`.
4. Epoch N+1 ends (`stopEpoch`, borrower funds normally). Now `epochNumber (N+2) > lastWithdrawRequest (N+1)`, so `_claimFundedWithdrawRequest` pays `withdrawsRequests[attacker]` — which still contains the full epoch-N receipt — at par via `_transferFundedClaim`, while the haircut `lossRecoveryPriceByEpoch[N]` is never applied.

### Impact Explanation
The attacker escapes the loss waterfall: a receipt that should pay `claimBasis * lossRecoveryPrice / RECOVERY_FULL` is paid 1:1, so the realized epoch-N loss is socialized onto the other withdrawing users/remaining NAV instead of the attacker's share. This is direct over-payment of funded underlying (theft relative to the designed haircut), proportional to the loss percentage and the attacker's epoch-N receipt size.

### Likelihood Explanation
Requires a `stopEpochWithDuration(_lossAmount)` (borrower partial default that does not trigger full default/finalization) and a subsequent running epoch in which the attacker can submit any new withdraw request — both unprivileged, ordinary protocol flows. The only acknowledged behavior nearby is that re-requesting *delays* claims (code NOTE at lines 323-324); the loss-epoch haircut escape is not guarded.

### Recommendation
Track loss-epoch receipts independently of `lastWithdrawRequest`, or iterate all `withdrawsRequestsByEpoch[_user]` entries with a nonzero `lossRecoveryPriceByEpoch` before the funded path. Minimal fix: in `requestWithdraw`, refuse or first settle when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0`, or have `_claimLossAdjustedWithdrawRequest` scan/settle outstanding per-epoch receipts rather than only the latest epoch.

function testLossEpochReceiptPaidAtParAfterRerequest() external {
    // epoch N: deposit AA, start epoch, requestWithdraw(AA balance)
    uint256 receipt = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)), address(AAtranche));

    // stop epoch N with a loss: borrower repays principal - loss
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, fundedAmountExcludingLoss);
    vm.prank(manager);
    cdoEpoch.stopEpoch(lossAmount, 0); // sets lossRecoveryPriceByEpoch[N] < RECOVERY_FULL

    // epoch N+1 running: attacker re-requests a dust withdraw -> lastWithdrawRequest = N+1
    vm.prank(manager);
    cdoEpoch.startEpoch();
    cdoEpoch.requestWithdraw(1, address(AAtranche));

    // epoch N+1 ends normally, fully funded
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, pendingWithdraws + interest);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, interest);

    // claim: pays epoch-N receipt at par instead of lossRecoveryPrice haircut
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;
    uint256 haircutExpected = receipt * strategy.lossRecoveryPriceByEpoch(N) / RECOVERY_FULL;
    assertGt(paid, haircutExpected); // BUG: par payout of a haircut receipt
}

Uncertainty note: index access did not confirm whether `stopEpochWithDuration` (loss path) leaves the pool in a state where a fresh `requestWithdraw` in the following epoch is permitted (e.g., a `Default`/pause gate). If the loss path always forces default finalization or blocks new requests, the precondition fails; otherwise the escape above holds. Verification of `stopEpochWithDuration`'s post-state flags is required in the PoC run.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
