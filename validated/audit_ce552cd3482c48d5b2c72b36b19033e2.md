### Title
Any user can wedge `stopEpoch` permanently by leaving an APR0 withdraw request open when the manager raises the APR - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report (CVE-2016-2848) is a "crafted input reaches an assertion and kills the process" bug class. The closest credit-vault analog is an assertion-style `NotAllowed()` revert inside `IdleCreditVault.prepareStopEpochWithApr0`, which is invoked from the epoch-stop path. A single unprivileged lender who opens a withdraw request while `unscaledApr == 0` creates a persistent `apr0TotalPrincipal` balance. The moment the manager later sets a non-zero APR — a routine, honest operation — every subsequent `stopEpoch`/`stopEpochWithDuration` reverts, freezing all deposits and pending withdraws until the APR is manually returned to 0.

### Finding Description
`requestWithdraw` routes requests into the APR0 bucket whenever `unscaledApr == 0` and the pool is not closed:

- `requestWithdraw` calls `_requestWithdrawApr0(_amount, _user)` when `unscaledApr == 0 && !isClosed` [1](#0-0) 
- `_requestWithdrawApr0` increments `apr0TotalPrincipal` [2](#0-1) 
- `prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0` [3](#0-2) 
- `apr0TotalPrincipal` is only cleared at the end of `prepareStopEpochWithApr0` (line 540), which is unreachable once the revert fires, and is never decremented by `_settleApr0` or by claims — only `prepareStopEpochWithApr0` itself or the default-claim path in `_clearWithdrawClaimForEpoch` touch it [4](#0-3) 

`setApr`/`setAprs`/`setAprsWithBuffer` update `unscaledApr` with no check on `apr0TotalPrincipal`, and the CDO calls `setAprsWithBuffer` when stopping/starting epochs [5](#0-4) .

Attack sequence (APR0 vault, running epoch):

1. Manager/owner configures the vault with `unscaledApr = 0` (APR0 mode is a supported configuration; the bucket logic exists only for it).
2. Attacker (any KYC'd lender) deposits AA and calls `requestWithdraw` on the CDO for any nonzero amount. `apr0TotalPrincipal` becomes `> 0`.
3. Manager later sets a non-zero APR for the next epoch via `setAprs`/`setAprsWithBuffer` — a normal operation.
4. Every `stopEpoch`/`stopEpochWithDuration` call now reverts at the `unscaledApr != 0` check, because `apr0TotalPrincipal` can never be cleared (the only clearing line is after the revert).
5. The epoch cannot be stopped: all lender principal and pending withdraws are frozen, including instant-withdraw and queued-claim flows that depend on epoch rollover.

The guard was presumably intended to prevent APR0 accounting corruption, but it converts a user-creatable state into a permanent revert, exactly the "assertion on attacker-influenced state" pattern of the CVE.

### Impact Explanation
Temporary freezing of all vault funds. While `unscaledApr != 0 && apr0TotalPrincipal > 0`, no epoch can be stopped, so no withdraw request can be claimed, no interest settlement occurs, and deposits are locked. Recovery requires the manager/owner to call `setAprs(0, 0)` (or `setApr(0)`-equivalent restoring `unscaledApr` to 0) before stopping the epoch — but there is no indication this remediation is intended, and any subsequent APR change re-bricks the pool while any APR0 request is pending. All funds in the vault (potentially the entire TVL) are frozen for the duration.

### Likelihood Explanation
Reachable by any unprivileged lender able to call `requestWithdraw` during an epoch where `unscaledApr == 0`. It additionally requires the manager to later set a non-zero APR while the request is unsettled — a plausible operational sequence (APR changes are the normal per-epoch flow). No privileged misbehavior, oracle manipulation, or market condition is needed. Caveat: I could not fully verify in this pass whether `prepareStopEpochWithApr0` is invoked unconditionally on every `stopEpoch` path in `IdleCDOEpochVariant` (the grep confirmed the symbol exists in `IdleCDOEpochVariant.sol` and `IdleCreditVaultManagerOrchestrator.sol`, but I did not read the exact call site before the iteration limit). If the call is gated on `apr0TotalPrincipal != 0` or `unscaledApr == 0`, severity may differ.

### Recommendation
Instead of reverting, either (a) settle/zero `apr0TotalPrincipal` and pay out APR0 principal without interest when `unscaledApr != 0` at stop time, or (b) reject `setApr`/`setAprs`/`setAprsWithBuffer` changes to a non-zero `unscaledApr` while `apr0TotalPrincipal != 0`, so the inconsistent state is prevented at the admin boundary rather than asserted at the epoch-stop boundary. Option (b) is the minimal fix matching the existing invariant ("APR0 principal is only valid while APR is 0 for that request lifecycle").

### Proof of Concept
Source-level PoC (Foundry fork, not executed in this session):

```solidity
function test_Apr0PrincipalBricksStopEpoch() external {
    // vault configured with unscaledApr == 0 (APR0 mode)
    vm.prank(manager);
    cv.setAprs(0, 0);

    // attacker: deposit + requestWithdraw during running epoch
    deal(underlying, attacker, amount);
    vm.startPrank(attacker);
    IERC20(underlying).approve(address(idleCDO), amount);
    idleCDO.depositAA(amount);
    idleCDO.requestWithdraw(amount, address(AATranche)); // -> apr0TotalPrincipal > 0
    vm.stopPrank();

    assertGt(cv.apr0TotalPrincipal(), 0);

    // honest manager raises APR for next epoch
    vm.prank(manager);
    cv.setAprs(newApr, scaledApr); // unscaledApr != 0

    // borrower repays; manager tries to stop epoch -> always reverts
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    idleCDO.stopEpoch();
}
```

The revert is permanent until `unscaledApr` is reset to 0, because the revert precedes the only `apr0TotalPrincipal = 0` write reachable in normal operation.
