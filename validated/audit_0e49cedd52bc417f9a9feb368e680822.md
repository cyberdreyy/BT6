### Title
Griefing freeze of `stopEpoch` via third-party ERC4626 liquidity drain — any EOA can block epoch settlement and lock all pool funds - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`IdleCDOEpochVariant` delegates idle-fund custody to `ProgrammableBorrower`, which in turn deposits pool assets into an arbitrary external ERC4626 vault (`vault`). At epoch stop, `ProgrammableBorrower.onStopEpoch` must synchronously `vault.withdraw()` the shortfall between its on-hand balance and the amount IdleCDO will pull. If that withdrawal reverts — for example because a third-party lending vault's liquid balance was temporarily drained — `onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable`, reverting the entire `stopEpoch` call. Any unprivileged actor can create this condition by borrowing/redeeming the external vault's available liquidity, freezing all deposits, interest settlement, and withdrawal payouts for as long as they keep the liquidity drained.

### Finding Description
In `onStopEpoch`, when `IdleCDO` requests `_amountRequired` greater than the borrower's on-hand balance, the contract checks the shortfall against the vault's *reported* position value, then attempts a live withdrawal:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol:240-253
if (shortfall > _currentVaultAssets()) return true;
try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
} catch {
    revert StopEpochVaultLiquidityUnavailable();
}
```

`_currentVaultAssets()` is `vault.convertToAssets(shares)` (line 546-549) — the vault's *book* value, which for lending-style ERC4626 vaults (e.g., MetaMorpho, used in the production configuration per `test/foundry/ProgrammableBorrowerCreditVault.t.sol`) includes assets lent out and not withdrawable. The actual withdrawable amount is `vault.maxWithdraw`, which is never consulted.

Two exploitable consequences follow:

1. **Revert path (liquidity drain):** if `convertToAssets`-valued shares cover the shortfall but the vault's idle liquidity is below it, `vault.withdraw` reverts and `onStopEpoch` propagates `StopEpochVaultLiquidityUnavailable` up through `IdleCDOEpochVariant.stopEpoch`. Epoch settlement, interest minting, and pending withdrawal payouts are all blocked. Any EOA can create and maintain this state cheaply by borrowing or withdrawing the external vault's idle assets (a standard, unprivileged action against the third-party vault), then optionally repaying and re-draining to keep the freeze going.

2. **Misvaluation path:** if `convertToAssets` overstates the position (third-party vault valuation inconsistency), the `shortfall > _currentVaultAssets()` early return never fires, so the same revert-based freeze applies instead of the intended graceful default.

This mirrors the FixedFloat incident's bug class — compromise/manipulation of a third-party dependency — realized here as unprivileged control over the external vault's liquidity state that Idle tranches treats as trusted infrastructure.

### Impact Explanation
While the external vault's liquidity is kept below the shortfall, `stopEpoch` cannot be executed by the (honest) manager: pending withdraw requests are never paid, borrower interest is never settled, and the entire pool TVL (potentially all user deposits parked in the external vault via `onStartEpoch` → `_depositToVault(underlyingToken.balanceOf(...))`, line 216) is frozen. Loss is quantifiable as the full pool principal plus accrued yield for the duration of the freeze; the attacker's cost is only the borrow/funding cost in the third-party market, which can be near zero if the vault's liquidity is drained via flash-funded positions within transactions timed around the manager's `stopEpoch` attempts. No privileged role is involved; the honest manager's retry attempts simply keep reverting.

### Likelihood Explanation
- The trigger requires no privilege: any EOA can borrow against or redeem the external vault's idle liquidity.
- The condition is cheap to induce around `epochEndDate` since `stopEpoch` timing is publicly predictable (`epochEndDate` is on-chain).
- Nothing in `onStopEpoch`, `IdleCDOEpochVariant.stopEpoch`, or `_depositToVault` bounds the exposure to third-party liquidity; the code explicitly chose revert-on-failure (`StopEpochVaultLiquidityUnavailable`) making the freeze a deterministic consequence rather than an edge case.
- Likelihood is bounded by the attacker needing to sustain the liquidity drain, which has ongoing cost, so this is a griefing/temporary-freeze rather than permanent theft.

### Recommendation
- In `onStopEpoch`, cap the attempted withdrawal to `vault.maxWithdraw(address(this))` instead of relying on `convertToAssets` for the coverage check, and treat "shares are solvent but liquidity is temporarily unavailable" as a graceful `return false`/partial-withdraw path rather than reverting, so `stopEpoch` can settle what is available or defer cleanly.
- Alternatively, withdraw `maxWithdraw` in the try block, pull the remainder in a later settlement call, and make `IdleCDOEpochVariant.stopEpoch` tolerate partial proceeds rather than requiring one atomic pull.
- Document and bound the trust assumption on the external vault: an emergency redemption path (`emergencyExitVault`) already exists, but it is owner-only, so it cannot resolve a freeze during a live stop without governance latency.

### Proof of Concept
A Foundry fork PoC (extending `test/foundry/ProgrammableBorrowerCreditVault.t.sol`, which already wires `ProgrammableBorrower` to the live MetaMorpho `morphoVault`):

```solidity
function testStopEpochFrozenByVaultLiquidityDrain() external {
    uint256 amount = 10_000 * oneScale;
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);           // funds parked into morphoVault

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Attacker (any EOA): drain the vault's idle liquidity so that
    // maxWithdraw < shortfall even though convertToAssets covers it.
    // On a Morpho fork: open a borrow against each funded market until
    // vault.idleLiquidity < shortfall; or redeem all attacker-held shares
    // sized to leave insufficient idle assets.
    address attacker = makeAddr("attacker");
    _drainMorphoIdleLiquidity(attacker);    // leaves < shortfall withdrawable

    vm.prank(manager);
    vm.expectRevert(
        ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector
    );
    cdoEpoch.stopEpoch(0, 0);               // settlement blocked, TVL frozen
}
```

The revert originates inside `onStopEpoch`'s catch block (lines 246-253) and propagates through the CDO's stop call; because `_currentVaultAssets()` still reports full coverage, the graceful early-return branch is skipped and every retry reverts until the third-party vault's liquidity is replenished.
