## Analog Found: `JuplendWithdraw.destination_token_account` is unconstrained, allowing withdrawal proceeds to be redirected away from the intended recipient

### Title
Unchecked `destination_token_account` in `juplend_withdraw` allows redirection of withdrawn funds - (File: `programs/marginfi/src/instructions/juplend/withdraw.rs`)

### Summary
Similar to the Stargate `participate()` bug where the destination address for bridged tokens was not properly bound to the intended recipient (`StargateLbpHelper` on the host chain) and was instead an attacker/caller-controllable value, `JuplendWithdraw` accepts a `destination_token_account` that is explicitly documented as completely unchecked, and the underlying withdrawn tokens are transferred directly to whatever account is passed in.

### Finding Description
The `JuplendWithdraw` account struct defines the recipient of withdrawn funds with no ownership or identity constraint: [1](#0-0) 

The instruction itself performs the transfer of the withdrawn underlying token amount straight to this account via a signed CPI from the bank's liquidity vault authority: [2](#0-1) 

Authorization to call `juplend_withdraw` is gated only by `is_signer_authorized`, which (per the codebase's account-delegation model exercised elsewhere, e.g. the order-execution flow in `tests/specs/limits/m04_orderLimits.spec.ts` where an `executor` distinct from the account owner drives withdraw instructions on the user's behalf) permits callers other than the marginfi account's owning wallet to invoke the withdrawal: [3](#0-2) 

Because the `destination_token_account` is never checked against the marginfi account's `authority`, its ATA, or any other canonical recipient, any signer authorized to invoke the withdraw (which, per the order-execution/delegate flow, is not restricted to only the account's direct owner) can set the destination to an account they control, redirecting the withdrawn underlying tokens away from the marginfi account owner. This is functionally identical to the Stargate root cause: the code performs a value-moving operation (a token transfer / cross-domain swap) to a caller-suppliable address instead of one cryptographically bound to the intended beneficiary.

### Impact Explanation
Medium-to-high impact: withdrawn principal (real underlying tokens, not just accounting) can be diverted to an address the account owner does not control, with no on-chain remedy since the CPI-signed transfer is final. This directly causes the marginfi account owner to lose funds that should have returned to them.

### Likelihood Explanation
The likelihood is contingent on whether `is_signer_authorized` in this codebase allows any entity other than the account's exact owner (e.g., a delegate, order-execution bot, or other permissioned-but-not-owner signer) to invoke `juplend_withdraw` while supplying a `destination_token_account` different from the owner's ATA. Given the codebase explicitly documents this field as `WARN: Completely unchecked!`, and other integrations follow a similar "user free to choose destination" pattern intentionally for the owner-initiated case, this is a design smell that becomes exploitable specifically in any flow where the withdraw is executed by someone other than the owning wallet (e.g., automated order execution) without the caller-supplied destination being independently validated against the account/owner.

### Recommendation
Constrain `destination_token_account` to a value cryptographically tied to the marginfi account (e.g., require it match the account `authority`'s canonical ATA for the mint, or add a `has_one`/`token::authority` constraint), or require any delegate-driven withdraw path to pass the owner-registered destination rather than an arbitrary account, mirroring the fix recommended for `StargateLbpHelper.participate()` (make the destination an explicitly validated parameter, not implicitly trusted from the caller).

### Proof of Concept
1. Attacker/executor holds delegated/authorized signer rights over a victim's `marginfi_account` sufficient to pass `is_signer_authorized` for a withdraw (e.g., via an order-execution or automation flow).
2. Attacker calls `juplend_withdraw` supplying their own wallet's token account as `destination_token_account` instead of the victim's ATA.
3. `cpi_transfer_withdraw_intermediary_ata_to_destination` executes a signed transfer of the withdrawn underlying tokens to the attacker's account.
4. Victim's on-chain lending position is decremented as if they received the funds, but the tokens land in the attacker's wallet.

Note: I could not fully verify, within this session, the exact set of principals for which `is_signer_authorized` returns true (i.e., whether it includes non-owner delegates in all deployed flows) or whether callers elsewhere in the stack (e.g., the order-execution instruction) additionally re-validate the destination before invoking this instruction. This should be confirmed by inspecting `is_signer_authorized` in `state/marginfi_account.rs` and the callers of `juplend_withdraw` in the order-execution/deleverage code paths.

    pub fn cpi_transfer_withdraw_intermediary_ata_to_destination(
        &self,
        amount: u64,
        authority_bump: u8,
    ) -> MarginfiResult {
        let program = self.token_program.to_account_info();
        let accounts = TransferChecked {
            from: self.integration_acc_3.to_account_info(),
            to: self.destination_token_account.to_account_info(),
            authority: self.liquidity_vault_authority.to_account_info(),
            mint: self.mint.to_account_info(),
        };

        let signer_seeds: &[&[&[u8]]] =
            bank_signer!(BankVaultType::Liquidity, self.bank.key(), authority_bump);
        let cpi_ctx = CpiContext::new_with_signer(program.key(), accounts, signer_seeds);
        transfer_checked(cpi_ctx, amount, self.mint.decimals)?;
        Ok(())
    }
