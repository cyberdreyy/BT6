### Title
`RevokeActor` is keyed by an arbitrary, admin-chosen `actorId` slot with no "last admin" guard, so a Multichain-replayed revoke can clobber a different actor on each chain and permanently brick an account - (File: `crates/execution/eip8130/src/apply.rs`)

### Summary
EIP-8130's `RevokeActor` change op mirrors the original `removeOwnerAtIndex` bug class: the op payload only carries an opaque identifier (`actorId`) and revokes "whatever is currently authorized at that identifier," without binding to *which* authenticator/config it expects to remove. Combined with the `Multichain` replay channel (which binds `chain_id == 0` and is valid on every chain by design) and the absence of any "cannot remove the last admin" invariant, a signer who configures actors differently per chain via the `Local` channel and later issues a `Multichain` `RevokeActor` can unintentionally revoke a different actor on each chain, up to and including bricking the account on a chain where that slot happens to hold the only remaining admin actor.

### Finding Description
`ChangeType::RevokeActor`'s payload is `abi.encode(actorId)` only [1](#0-0) . The `actorId` for a non-self actor is admin-chosen at `AuthorizeActor` time — it is not derived from the authenticator, so a user could (intentionally or not) authorize a *different* authenticator under the *same* `actorId` on different chains via independent `Local`-channel batches. `authorize_non_self_actor` simply upserts whatever `(actorId, config)` pair it is given, with no requirement that `actorId` be content-addressed to `config.authenticator` [2](#0-1) .

`revoke_actor_with_account_state` / `revoke_explicit_actor` then unconditionally clear whatever is currently stored at that `actorId` slot, without checking that the caller intended to remove that specific authenticator/config: `let config = storage.actor_config_slot(account, actor_id)?; ... Self::revoke_explicit_actor(storage, account, actor_id, config)` [3](#0-2) , and `revoke_explicit_actor` clears the slot unconditionally once it is non-empty [4](#0-3) . This is structurally identical to the Coinbase Smart Wallet bug: `removeOwnerAtIndex(index)` removed "whatever owner is at `index`" rather than a specific, caller-verified owner — the fix there was to also require the caller to pass the expected owner value and check it against the value found at the index before removing it. Here, no equivalent check exists: `RevokeActor` never compares the currently-stored `ActorConfig` against an expected value before clearing it.

The `AccountChangeChannel::Multichain` channel is explicitly designed to be replayed verbatim across every chain that shares the signer's account (it binds `chain_id == 0`) [5](#0-4) , and the native executor's chain-id equality check is scoped to the *transaction's* `chain_id` field, not to per-op consistency of what a Multichain `RevokeActor` will match on each chain [6](#0-5) . So a legitimately signed Multichain `RevokeActor(actorId=X)` batch is valid to include on any chain, and will revoke whatever `actorId=X` currently resolves to there — which can differ from chain to chain if the user's account drifted via independent `Local` operations.

Additionally, no code path in the apply/authorize pipeline enforces a "cannot remove the account's only/last admin actor" invariant (searched broadly for last-owner/last-admin guards in the eip8130 apply/authorize/account_config code; none exists). This mirrors the original report's second necessary ingredient: "lack of last owner guard," which the judge cited as the reason the bug was escalated to High severity (a well-defined path to permanent loss of account control), not merely Medium.

### Impact Explanation
If a wallet's actors diverge across chains (e.g., the user adds an owner/admin actor via `Local`-channel batches independently on Base, Ethereum, and Optimism, landing different `(actorId, authenticator)` pairings at the same `actorId` slot on each chain — a realistic outcome of sporadic, per-chain administration over the account's lifetime) and the user later issues a Multichain `RevokeActor(actorId)` intending to remove one specific actor, replay of that same signed batch removes a *different* actor's authorization on each chain. Because there is no guard preventing removal of the account's last live admin actor, this can (a) silently revoke unintended actors on chains the user did not intend to touch, and, in the worst case, (b) revoke the sole surviving admin actor on some chain, permanently locking the account out of all future `AuthorizeActor`/`RevokeActor` administration on that chain (no owner-recovery path exists once every actor is revoked). This is a loss of access to funds/control on an L2 account — a concrete unauthorized-operation / permanent-freezing-of-funds outcome, matching the accepted High-severity classification of the original finding.

### Likelihood Explanation
The precondition — a long-lived smart account whose owner/actor set is administered independently per chain via `Local` (single-chain) `AuthorizeActor` batches, and later "cleaned up" via a `Multichain` (cross-chain-replayable) `RevokeActor` — is a natural, expected usage pattern for account abstraction: EIP-8130 explicitly supports both channels for exactly this purpose (single-chain-specific admin vs. account-wide replayable admin), and nothing in the protocol nudges users away from mixing them. No attacker action beyond broadcasting a legitimately user-signed transaction to additional chains is required (the Multichain channel is replayable by design, by any relayer, once signed). This mirrors the original report's own PoC scenarios almost exactly. Likelihood is assessed as Medium-High for sophisticated multi-chain wallet users/integrators managing owners chain-by-chain over time, though it does require the actor-authorization divergence to already exist.

### Recommendation
- Change the `RevokeActor` payload to also commit to the actor's expected current configuration (e.g., `abi.encode(actorId, expectedAuthenticator)` or a hash/commitment of the expected `ActorConfig`), and have `apply.rs::revoke_actor_with_account_state` / `revoke_explicit_actor` verify the on-chain config matches before clearing it — mirroring Coinbase's fix of adding the `owner` argument to `removeOwnerAtIndex` and checking it against the value found at the index.
- If a mismatch is found on a given chain, treat the op as a no-op (return without reverting) rather than clearing an unintended actor, so the batch remains safely replayable elsewhere.
- Add a structural invariant preventing `RevokeActor` from clearing the account's last remaining live admin-scoped actor (a "last admin" guard), independent of the identifier-matching fix above, to eliminate permanent lockout even for a correctly-targeted revoke.

### Proof of Concept
1. Alice's smart account has actors administered via three chains.
2. On Chain A, Alice signs a `Local` `AuthorizeActor` batch installing `actorId = X` bound to `authenticator = keyA` (an EOA/authenticator she controls only on Chain A).
3. On Chain B, independently, Alice signs a different `Local` `AuthorizeActor` batch that happens to reuse `actorId = X` (e.g., tooling/wallet software reused the identifier) bound to `authenticator = keyB`, her *only* remaining admin actor on Chain B.
4. Later, Alice wants to revoke `keyA` on Chain A because it was compromised, and signs a `Multichain` `RevokeActor(actorId = X)` batch, intending it to apply only meaningfully on Chain A.
5. Because the `Multichain` channel is replayable on every chain by design, and `RevokeActor`'s apply logic (`apply.rs`, `revoke_actor_with_account_state`/`revoke_explicit_actor`) blindly clears whatever `ActorConfig` currently sits at `actorId = X` with no comparison to an expected value, the same signed batch, when included on Chain B, revokes `keyB` — Alice's only remaining admin actor there — with no "last admin" guard to stop it, permanently locking her out of administering the account on Chain B.

    /// Revokes an actor represented by an explicit `actor_config` entry.
    pub fn revoke_explicit_actor(
        storage: &mut AccountConfigurationStorage<'_>,
        account: Address,
        actor_id: B256,
        config: ActorConfig,
    ) -> Result<(), ApplyError> {
        if config.authenticator == Address::ZERO {
            // Idempotent: an absent actor is a no-op (no clear, no event), mirroring
            // `_applyRevoke`'s early return when `!_isAuthorized` (eip-8130 #100).
            return Ok(());
        }
        storage.clear_actor_config(account, actor_id)?;
        storage.clear_policy(account, actor_id)?;
        AccountConfigurationEvents::emit_actor_revoked(storage, account, actor_id)?;
        Ok(())
    }
