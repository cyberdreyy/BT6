## Analog Found

### Title
Governance `setImplementation` on the dispute-game verifier can permanently stall the AnchorStateRegistry updater - (File: `crates/proof/challenge/src/anchor.rs`)

### Summary
The Base fault-proof challenger contains an `AnchorUpdater` that advances the L1 `AnchorStateRegistry` by looking up the next dispute game via a UUID derived from `(block_interval, intermediate_block_interval)`. These intervals are resolved from the *current* `DisputeGameFactory.gameImpls` entry rather than from the game itself when the successor game does not yet exist. This is the same failure mode as the reported issue: an upgrade of the underlying "gauge" (here, the `AggregateVerifier` implementation behind the factory) can desynchronize the caller's expectations from an already-created dependent object, and the mismatch is not self-healing.

### Finding Description
`AnchorUpdater::next_game` computes the UUID lookup key for the successor game using intervals resolved via `resolve_intervals`, which reads `factory_client.game_impls(game_type)` — the factory's *current* implementation — and applies its interval pair to compute the expected `(rootClaim, extraData)` key [1](#0-0) . The code explicitly documents the resulting bug: [2](#0-1) 

If a governance `setImplementation` call changes the interval pair on the `AggregateVerifier` implementation registered in `DisputeGameFactory`, and the successor game was already created under the *old* pair (e.g., created before the upgrade landed on-chain, or during a race window), the keyed factory lookup (`factory_client.games(...)`) will use the new pair to compute the UUID, which will never match the existing game's UUID computed under the old pair. The lookup returns `Address::ZERO`, logged only as "next anchor game not found" [3](#0-2) , and `poll()` simply returns without error each cycle [4](#0-3) .

Unlike the proposer/scanner paths, which read intervals through the *game's own proxy* once it exists — a CWIA clone whose interval pair is fixed at creation regardless of later `setImplementation` calls [5](#0-4)  — the anchor updater has no game to read through yet at the point it must compute the lookup key, so it is forced to guess using the factory's current implementation. The code comment itself states this stall "which a restart no longer clears" [6](#0-5) , meaning the condition is durable, not transient.

### Impact Explanation
If this desync occurs, the `AnchorStateRegistry` anchor stops advancing entirely for that game type. Since the anchor is the reference point the proposer and challenger use for finality/eligibility checks (`anchor_preflight`, `is_game_finalized`) [7](#0-6) , a permanently stuck anchor blocks finalization progress for the dispute game system tied to withdrawals and output-root settlement on this game type — a freezing condition analogous to the reported veAsset gauge-upgrade issue, where an upgrade to an underlying dependency (gauge / verifier implementation) desynchronizes and freezes the dependent system, requiring manual intervention (here, the documented fix is to add factory-index scanning as a fallback, which does not currently exist).

### Likelihood Explanation
The trigger is a legitimate governance action (`setImplementation` on the `DisputeGameFactory` for the game type) that changes `BLOCK_INTERVAL`/`INTERMEDIATE_BLOCK_INTERVAL`, combined with an in-flight successor game already created under the old pair — exactly the kind of upgrade the Denim-interval-switch mechanism was built to support and that the report's underlying bug class (upgradeable gauge/token pairs breaking staker assumptions) describes as "not hypothetical." The code's own inline comment acknowledges this is a known, unresolved limitation rather than a theoretical concern.

### Recommendation
When the keyed lookup in `next_game` misses (`Address::ZERO`), fall back to scanning the factory from the anchor game's index forward (as the comment itself suggests) instead of only trying the current-implementation-derived key, so an implementation upgrade between game creation and anchor advancement cannot permanently desynchronize the lookup.

### Proof of Concept
1. Game type `T` anchor is at block `N`, with `AggregateVerifier` implementation `I1` having `(block_interval=100, intermediate_block_interval=100)`.
2. A successor game for `T` is created at block `N+100` under `I1`'s pair, registered in the factory under UUID `U1 = hash(rootClaim, extraData(I1-pair))`.
3. Governance calls `DisputeGameFactory.setImplementation(T, I2)` where `I2` has `(block_interval=50, intermediate_block_interval=25)` (mirroring the Denim-style interval change already supported in this codebase).
4. `AnchorUpdater::next_game` is invoked again; `resolve_intervals` now reads `I2`'s pair from the factory (since it reads `game_impls` fresh every call) and computes a different UUID `U2 != U1`.
5. `factory_client.games(T, key.root_claim, key.extra_data)` returns `Address::ZERO` because the registered game is keyed under `U1`, not `U2` — logged as "next anchor game not found" — and the anchor never advances for this game type, even across restarts, until manual code changes are deployed.

    async fn next_game(
        &self,
        verifier_client: &dyn AggregateVerifierClient,
        anchor_root: AnchorRoot,
        anchor_game: Address,
    ) -> Option<Address> {
        // Resolved from the anchor block, which is where the next game's range starts:
        // the verifier switches to a shorter cadence at the Denim activation block, so a
        // pair cached at startup silently stops matching any game past the boundary.
        //
        // Known limitation: this reads the factory's *current* implementation, but the
        // successor game may already exist and have been created with an older pair. Across a
        // `setImplementation` that changes the pair the keyed lookup never matches and the
        // anchor stalls at "next anchor game not found", which a restart no longer clears.
        // Denim itself does not trigger it (the pair is a function of the starting block,
        // not of which implementation is current). Fix by scanning the factory from the
        // anchor index when the keyed lookup misses, if it ever bites.
        let (block_interval, intermediate_block_interval) = match resolve_intervals(
            self.factory_client.as_ref(),
            verifier_client,
            self.game_type,
            anchor_root.l2_block_number,
        )
        .await
        {
            Ok(intervals) => intervals,
            Err(e) => {
                warn!(error = %e, "failed to resolve anchor update intervals");
                return None;
            }
        };
