### Title
Owner `setTrancheAPRSplitRatio` / `setFeeParams` changes can be sandwiched via instant withdrawal to lock in a stale yield split and steal accrued tranche interest - (File: contracts/strategies/idle/IdleCreditVault.sol, contracts/IdleCDOCreditVault.sol)

### Summary
Idle credit vaults recompute each tranche's share of accrued epoch interest at claim time, reading `trancheAPRSplitRatio` and `fee` from storage at that moment. An unprivileged tranche holder who observes a pending owner transaction that reduces their tranche's APR share (or raises `fee`) can front-run it with an instant/withdraw-request claim to realize the whole epoch's accrued interest under the old, more favorable parameters, then re-enter. This is the same bug class as the external report: a risk-parameter setter whose economic effect is applied retroactively over already-accrued value, with no buffer or epoch-boundary enforcement, making it sandwichable by any holder.

### Finding Description
- `IdleCDOCreditVault.setTrancheAPRSplitRatio` and `setMinAprSplitAYS` are `onlyOwner` setters that write the split ratio directly, with no timelock, no epoch-phase gating, and no accrual snapshot (`contracts/IdleCDOCreditVault.sol:479`, `contracts/IdleCDO.sol:900`).
- When a withdraw request is claimed (instant via `claimInstantWithdrawRequest`, or normal via `claimWithdrawRequest` in `contracts/strategies/idle/IdleCreditVault.sol`), the interest owed is computed in `_calcInterestWithdrawRequest` by multiplying total epoch interest by the *current* `trancheAPRSplitRatio`/`aprRatio` and charging `fee()` read live from storage — the test helper mirrors this exactly: `totTrancheinterest = totInterest * _trancheAprRatio / FULL_ALLOC` and `fees = interest * cdoEpoch.fee() / FULL_ALLOC` (`test/foundry/IdleCreditVault.t.sol:3572-3589`).
- In fixed-APR mode (`isAYSActive == false`), an owner-set `trancheAPRSplitRatio` persists until the next setter call, so the stale value is actually used; in AYS mode the same exposure exists for `fee`/`feeSplit`/`managementFee` changes via `setFeeParams` (`contracts/IdleCDOCreditVault.sol:461-470`), which only accrues the management fee but does not crystallize performance fees owed to `feeReceiver` on already-accrued interest.
- Attack sequence (running or buffer phase): (1) owner broadcasts `setTrancheAPRSplitRatio` lowering the AA share (or `setFeeParams` raising `fee`); (2) attacker, an AA tranche holder, front-runs with `claimInstantWithdrawRequest`/withdraw claim, which prices all epoch-accrued interest at the old high AA share and old low fee; (3) after the owner's tx lands, attacker redeposits (`depositAA`/`depositDuringEpoch`). Interest for the full elapsed epoch was paid at parameters that should only have applied prospectively.

### Impact Explanation
Direct theft of yield: the spread `(oldRatio - newRatio) * totalEpochInterest` (or `(newFee - oldFee) * accruedInterest`) is paid to the attacker's claim at the expense of the opposite tranche holders (whose NAV/price gets correspondingly less interest) or of `feeReceiver`/`owner` (whose accrued performance fee is bypassed). Because `_calcInterestWithdrawRequest` re-prices the *entire* accrued interest of the epoch — not just future accrual — the quantified loss scales with epoch duration and attacker NAV, up to the full fee delta or split delta on all epoch interest attributable to the attacker's share. No guard prevents it: deposits/withdrawals are not paused around these setters, and there is no accrual-crystallization on parameter change (`setFeeParams` only calls `_accrueManagementFee`, not a full `_updateAccounting`).

### Likelihood Explanation
Medium. Requires (a) the vault to be in fixed-APR mode for the split-ratio variant (the fee variant works in any mode), (b) the owner to broadcast a mempool-observable parameter change, and (c) claim/instant-withdraw liquidity being available in the current epoch phase. All attacker roles used are explicitly permitted (tranche-token holder). The preconditions are operational rather than attacker-controlled, matching the external report's "operative risk" classification, but the economic extraction is concrete and reproducible on a fork.

### Recommendation
Crystallize accounting before mutating risk parameters: call `_forceUpdateAccounting()` (or a snapshot of `priceAA`/`priceBB` including accrued interest under the old ratio) inside `setTrancheAPRSplitRatio`, `setMinAprSplitAYS`, and `setFeeParams` so that already-accrued interest is locked under the old parameters. Additionally, restrict such changes to epoch boundaries (e.g., only during buffer phase or via `stopEpochWithDuration`), or route them through `Timelock`, so holders can exit before the new regime applies rather than being retroactively re-priced.

### Proof of Concept
Foundry fork sketch (in the style of `test/foundry/IdleCreditVault.t.sol`):

```solidity
// assume fixed-APR mode: isAYSActive == false, epoch running, instant withdraws enabled
uint256 oldRatio = cdoEpoch.trancheAPRSplitRatio();

// attacker holds AA tranche tokens accrued over most of the epoch
uint256 atkTranches = AAtranche.balanceOf(attacker);

// owner broadcasts a split reduction (e.g., 70% -> 30% AA share)
uint256 newRatio = 30_000; // FULL_ALLOC = 100_000

// 1) attacker front-runs the owner tx: claim instant withdraw at old ratio
vm.prank(attacker);
uint256 claimed = vault.claimInstantWithdrawRequest(...); // interest priced with oldRatio & old fee

// 2) owner tx lands
vm.prank(owner);
cdoEpoch.setTrancheAPRSplitRatio(newRatio);

// 3) attacker redeposits the principal
vm.startPrank(attacker);
underlying.approve(address(cdoEpoch), claimed);
cdoEpoch.depositAA(claimed);
vm.stopPrank();

// assertion: attacker's realized interest uses oldRatio; compare against a control
// claim executed after the ratio change using _calcInterestForTranche helper:
// delta = (oldRatio - newRatio) * totInterest / FULL_ALLOC on attacker share,
// which is extracted from BB holders' expected priceBB accrual.
```

The same pattern applies to `setFeeParams` with `claimInstantWithdrawRequest` front-running a `fee` increase, extracting `(newFee - oldFee) * accruedInterest` from `feeReceiver`/`owner`, since `_calcInterestForTranche` charges `cdoEpoch.fee()` read at claim time.

Note: I was limited to ABI and grep-level confirmation of `IdleCreditVault`'s claim functions and could not fully trace `claimInstantWithdrawRequest`'s liquidity/phase checks within the iteration budget; the PoC assumes instant withdrawals are available in the current epoch phase — if they are only available in the buffer phase, the attack still holds whenever the owner changes parameters during the buffer phase.
