### Title
Response cache key in HTTP capability gateway handler omits `WorkflowID`, causing cross-workflow cached-response confusion - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The `responseCache` used by the HTTP Handlers V2 gateway (`gatewayHandler`) keys cached outbound-HTTP responses using `gateway_common.OutboundHTTPRequest.Hash()`, which is documented and implemented to include only method, URL, headers, body, and `WorkflowOwner` — explicitly excluding `WorkflowID` [1](#0-0) . This is the same root-cause pattern as the reported Uniswap `poolFee` bug: a shared lookup key omits a dimension that should distinguish separate logical resources, causing one context's stored data to be served in place of another's.

### Finding Description
`responseCache.Fetch` and `responseCache.Set` both use `req.Hash()` as the sole cache key [2](#0-1) [3](#0-2) . The test suite explicitly documents and asserts that requests with different `WorkflowID` values but the same method/URL/headers/body/`WorkflowOwner` produce **the same hash**: [4](#0-3) 

Meanwhile the module's own design documentation claims the opposite guarantee — that the cache key is generated from workflow ID and enforces "Workflow Isolation... to prevent cross-workflow data leakage": [5](#0-4) 

This is invoked from `gatewayHandler.makeOutgoingRequest`, which is reached directly from unprivileged workflow-DON nodes sending `OutboundHTTPRequest` HTTP-action messages through the gateway with `CacheSettings.Store`/`MaxAgeMs` under the requester's control [6](#0-5) .

### Impact Explanation
Because the same `WorkflowOwner` can run multiple distinct workflows, two unrelated workflows belonging to the same owner (or, if `WorkflowOwner` is ever empty/absent, potentially different owners) that issue an HTTP action with the same method/URL/headers/body will collide on the same cache entry. A response fetched and cached on behalf of one workflow can be returned to a completely different workflow's HTTP-action request — a cross-workflow response confusion — contradicting the isolation guarantee the code claims to provide. Depending on what the cached response contains (e.g., workflow-specific tokens, personalized data, or state used downstream to trigger fund-moving or job-execution logic), this could lead one workflow to act on data intended for another.

### Likelihood Explanation
Likelihood is Medium: it requires two workflows under the same owner (a common, unprivileged, self-service scenario since any workflow owner can deploy many workflows) to make outbound HTTP actions to the same URL/method/headers/body while caching is enabled (`CacheSettings.Store=true` or `MaxAgeMs>0`), which are both request-controlled and plausible in normal usage (e.g., shared utility/config endpoints, oracle price feeds, etc.).

### Recommendation
Include `WorkflowID` in the cache key hash (e.g., alongside `WorkflowOwner`) in `gateway_common.OutboundHTTPRequest.Hash()`, matching the isolation behavior already documented in the README, so cached responses are strictly scoped per-workflow rather than per-owner.

### Proof of Concept
1. Workflow A (owner `0xOwner1`, workflow ID `wf-A`) sends an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", CacheSettings: {Store: true}}` through the gateway; the response `{"secret":"A-data"}` is cached under `Hash(method, url, headers, body, "0xOwner1")`.
2. Workflow B (same owner `0xOwner1`, different workflow ID `wf-B`) sends an identical `OutboundHTTPRequest` with `CacheSettings: {MaxAgeMs: 600000}`.
3. Because `Hash()` ignores `WorkflowID`, `responseCache.Fetch` in `core/services/gateway/handlers/capabilities/v2/response_cache.go` returns Workflow A's cached response to Workflow B without making a new outbound call — demonstrated directly by the existing test asserting equal hashes across differing `WorkflowID` values [4](#0-3) .

func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
