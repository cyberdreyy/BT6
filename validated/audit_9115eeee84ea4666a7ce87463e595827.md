### Title
Retroactive `trancheAPRSplitRatio` update reallocates accrued epoch yield - (`contracts/IdleCDO.sol`)

### Summary
`setTrancheAPRSplitRatio` changes the AA/BB yield split without first checkpointing accrued NAV in `_updateAccounting`. When the next deposit, withdrawal request, or epoch settlement runs, the new ratio is applied to the entire uncheckpointed gain rather than only to yield accrued after the change. A tranche holder can therefore receive yield earned while another split ratio was in force.

### Finding Description
`_updateAccounting` reads the current `trancheAPRSplitRatio` before calculating the gain between `lastNAVAA + lastNAVBB` and the current contract value. [1](#0-0)  Positive gains are split between the tranches using that stored ratio in `_virtualPriceAux`. [2](#0-1) 

The owner-facing setter updates `trancheAPRSplitRatio` directly and performs no accounting checkpoint. [3](#0-2)  Deposits and withdrawal requests call `_updateAccounting`, and epoch settlement also calls it after borrower interest is made available. [4](#0-3) [5](#0-4) [6](#0-5) 

For example, with equal AA and BB NAV and the old ratio at 100%, an honest owner reduces the ratio to 0% during a running epoch. The full interest produced by that epoch is still pending in `expectedEpochInterest`, which is computed when the epoch starts. [7](#0-6)  At `stopEpoch`, the entire pending gain is distributed using the new 0% ratio, so BB receives all yield that accrued while the configured split was 100% AA. [8](#0-7) 

### Impact Explanation
A BB holder can receive yield belonging to AA holders when the AA split is lowered, or an AA holder can receive yield belonging to BB holders when it is raised. The transferred amount is `pendingGain * abs(newRatio - oldRatio) / FULL_ALLOC` for positive pending gains, before fees. This violates fair mint/burn accounting and produces direct theft of unclaimed yield; no privileged actor needs to be malicious, because the owner or manager may simply intend the parameter to apply prospectively.

### Likelihood Explanation
The issue is reachable whenever a valid split-ratio update occurs while `getContractValue() > lastNAVAA + lastNAVBB`. No default, emergency, malformed input, oracle failure, or external protocol defect is required. In an epoch deployment, the owner may update the ratio while the epoch is running, after which the manager’s ordinary `stopEpoch` call crystallizes the retroactive redistribution. [9](#0-8)  The only requirement on the beneficiary is being an unprivileged holder of the favored tranche.

### Recommendation
Call the appropriate accounting checkpoint before assigning a new `trancheAPRSplitRatio`. For credit-vault deployments, preserve and restore `skipDefaultCheck` as `_forceUpdateAccounting` already does, and skim donated assets where required by the concrete variant. [10](#0-9) [11](#0-10)  Applying that pattern inside `setTrancheAPRSplitRatio` ensures accrued yield is allocated under the old ratio and only subsequent yield uses the new ratio.

### Proof of Concept
The following Foundry fork test can be added to `test/foundry/IdleCreditVault.t.sol`, whose setup deploys an `IdleCDOEpochVariant`, enables both tranches, disables Keyring, and configures a fixed-APR borrower. [12](#0-11) [13](#0-12) 

```solidity
function testRetroactiveAprSplitStealsEpochYield() external {
  uint256 amount = 10_000 * ONE_SCALE;
  address owner = idleCDO.owner();

  deal(defaultUnderlying, address(this), 2 * amount);
  IERC20Detailed(defaultUnderlying).approve(address(idleCDO), type(uint256).max);

  idleCDO.depositAA(amount);
  idleCDO.depositBB(amount);

  // Checkpoint with no pending gain, then set the ratio that should govern the epoch.
  vm.prank(owner);
  cdoEpoch.setTrancheAPRSplitRatio(FULL_ALLOC); // 100% to AA

  _toggleEpoch(true, initialProvidedApr, 0);

  // Honest parameter update intended to affect only the next epoch.
  vm.prank(owner);
  cdoEpoch.setTrancheAPRSplitRatio(0); // 0% to AA, 100% to BB

  uint256 aaBefore = cdoEpoch.lastNAVAA();
  uint256 bbBefore = cdoEpoch.lastNAVBB();
  uint256 pendingGain = cdoEpoch.expectedEpochInterest();

  _toggleEpoch(false, initialProvidedApr, pendingGain);

  // Expected under the ratio active while the epoch accrued:
  // AA receives pendingGain and BB receives zero.
  //
  // Actual result:
  // BB receives the entire pendingGain because stopEpoch reads the new ratio.
  assertEq(cdoEpoch.lastNAVAA(), aaBefore, "AA yield was stolen");
  assertEq(cdoEpoch.lastNAVBB(), bbBefore + pendingGain, "BB received retroactive yield");
}
```

The helper `_toggleEpoch(false, ...)` funds the borrower, warps past `epochEndDate`, and calls `stopEpoch`. [14](#0-13)  This produces a quantifiable transfer of `pendingGain` from AA holders to BB holders under the stated 100%-to-0% transition.

  function _toggleEpoch(bool _start, uint256 newApr, uint256 funds) internal {
    IdleCDOEpochVariant _vault = IdleCDOEpochVariant(address(idleCDO));
    address _owner = IdleCreditVault(_vault.strategy()).manager();
    vm.startPrank(_owner); 
    if (_start) {
      if (_vault.epochEndDate() != 0) {
        vm.warp(block.timestamp + _vault.bufferPeriod() + 1);
      }
      _vault.startEpoch();
    } else {
      deal(defaultUnderlying, borrower, funds);
      vm.warp(_vault.epochEndDate() + 1);
      uint256 pendingFees = _vault.pendingWithdrawFees();
      uint256 expectedInterest = _vault.expectedEpochInterest();
      uint256 netExpected = expectedInterest;
      if (netExpected > pendingFees) {
        netExpected -= pendingFees;
      } else {
        netExpected = 0;
      }
      uint256 fees = _vault.fee() * netExpected / FULL_ALLOC;
      uint256 pendingWithdraws = IdleCreditVault(address(strategy)).pendingWithdraws();
      vm.expectEmit(address(_vault));
      if (funds < expectedInterest + pendingWithdraws) {
        emit BorrowerDefault(expectedInterest + pendingWithdraws);
      } else {
        emit AccrueInterest(expectedInterest, fees + pendingFees);
      }
      _vault.stopEpoch(newApr, 0);
    }
