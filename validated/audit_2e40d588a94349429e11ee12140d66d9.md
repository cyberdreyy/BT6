### Title
Miner-side signer weight tallies double-count a signer that flips from Reject to Accept, permanently biasing toward rejection - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The analog to the vesting bug is a "delta not re-derived, stale increment kept" defect: just as `LinearVesting` computed each claim increment against the wrong baseline instead of `total*(elapsed/duration) - already_claimed`, the miner-side `StackerDBListener` accumulates `total_weight_approved` / `total_weight_rejected` as running sums keyed off two *different, non-exclusive* guards instead of a single per-signer "current vote" ledger. A signer's weight can end up counted in both tallies simultaneously, and once counted as rejected it is never removed even if that same signer later signs (accepts).

### Finding Description
In `handle_signer_message` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`), the two branches use different guard sets:

- `BlockResponse::Rejected` guards on `block.responded_signers.insert(slot_id)` [1](#0-0) 
- `BlockResponse::Accepted` guards only on `!block.gathered_signatures.contains_key(&slot_id)`, never checking `responded_signers` [2](#0-1) 

Sequence that breaks the invariant "each signer's weight should attribute to exactly one side of the tally":
1. Signer S sends `Rejected` for block B. `responded_signers` gets `slot_id`, `total_weight_rejected += S.weight` (per the code at lines 515-518).
2. S later reconsiders (the signer flow explicitly allows revisiting a rejection when "the reject reason ... allows us to reconsider", per `docs/signer-flows.md` and `handle_block_pre_commit`/`handle_block_validate_*` in `stacks-signer/src/v0/signer.rs`) and sends `Accepted` for the same block B.
3. In the `Accepted` branch, `gathered_signatures` does not yet contain `slot_id` (S never accepted before), so the check at line 443 passes and `total_weight_approved += S.weight` is applied [3](#0-2) .
4. Nothing decrements `total_weight_rejected`. S's weight is now permanently counted in *both* `total_weight_rejected` and `total_weight_approved`.

The coordinator's threshold loop checks rejection before acceptance:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight { ... reject ... }
else if block_status.total_weight_approved >= self.weight_threshold { ... accept ... }
``` [4](#0-3) 

Because the stale rejection weight from S is never cleared, it keeps contributing to the "blocking minority" check even after S has switched to approving. Combined with other genuine rejecters, this stale weight can push `total_weight_rejected` over the blocking-minority line even though the *current* position of the signer set (correctly attributed) would have reached the 70% approval threshold instead.

### Impact Explanation
This is a liveness wedge on the miner side: a single signer legitimately changing its vote from reject to accept (a behavior the signer protocol explicitly permits per the "reconsider" path documented in `docs/signer-flows.md`) is enough to corrupt the two aggregate counters so they are no longer a correct partition of responded weight. Because the rejection branch of `wait_for_signer_signatures_from_stackerdb` is evaluated first, this can cause a genuinely-signable block to be declared dead (`NakamotoNodeError::SignersRejected`) even though the live, correctly-attributed weight of signer support meets the 70% threshold — a rejection tally effectively "stuck" with a stale weight while acceptance weight is also inflated in a way that never fixes the rejection side. This matches the "rejection recounted / miscounted response causing an equality/threshold break" class called out in scope, and requires no majority of signers or key compromise — a single ordinary signer flipping its vote (which the protocol itself permits) is sufficient to trigger the miscount.

### Likelihood Explanation
No majority or malicious behavior is required: the flip from Reject → Accept for the same block by one honest signer, in the ordinary course of re-evaluating a block after a reject reason becomes stale, is enough. The bug is purely in the miner-side accounting and is deterministic given that sequence of two legitimate signer messages.

### Recommendation
Track a single "current vote" per `slot_id` (e.g., an enum `Accepted(weight)` / `Rejected(weight)` map keyed by `slot_id`) instead of two independently-incremented running sums. On each new message, if the signer previously voted the other way, subtract their weight from the old tally before adding it to the new one (or simply recompute both `total_weight_approved` and `total_weight_rejected` from the map of current votes, mirroring the correct recomputation approach already used in `stacks-signer/src/v0/signer.rs`'s `compute_signature_signing_weight`/`compute_signature_total_weight`, which fold over the *current* set of signatures rather than incrementally patching stale running sums).

### Proof of Concept
1. Signer set has signers `A` (weight 40) and `B` (weight 65), threshold = 70% of 100 (≥70).
2. `B` sends `Rejected` for block `H`. `total_weight_rejected = 65`. Blocking-minority check: `65 + 70 > 100` → true, but wait — actually this alone already trips rejection; use smaller weight to illustrate lingering effect: `B` has weight 25 instead. `total_weight_rejected = 25`. Not yet over blocking minority (`25 + 70 = 95 ≤ 100`).
3. Another signer `C` (weight 10) also rejects: `total_weight_rejected = 35`. Still ≤ 100 (`35+70=105>100` triggers reject) — pick weights so it's borderline: assume `weight_threshold = 70`, blocking minority is `>30`. `B`(25)+`C`(10)=35 > 30 → block would already be rejected without needing the flip. To show the flip's specific effect, have `B` reject first while the tally is still under 30 (`B` alone = 25, not over 30), then `A`(40) approves, then `B` flips to accept: `total_weight_approved` becomes `40+25=65` (correctly ≥70? not quite—adjust numbers), while `total_weight_rejected` still shows `25` from B's stale rejection. Any subsequent single small rejecter (e.g., weight 6) pushes `total_weight_rejected` to `31 > 30`, causing the coordinator to declare the block dead via `SignersRejected`, even though `B`'s real, current, and only vote is "accept" and the true rejecting weight (excluding B) is only 6 — far below the 30% blocking minority.

This scenario is exactly the code path at `stacks-node/src/nakamoto_node/stackerdb_listener.rs` lines 443-465 (accept branch not clearing/checking prior rejection) combined with the threshold check ordering in `stacks-node/src/nakamoto_node/signer_coordinator.rs` lines 509-545 that evaluates rejection before acceptance.

Note: I was not able to fully trace whether an equivalent "flip" (Accept → Reject) is symmetric-safe; based on the code read, the `Rejected` branch guards on `responded_signers`, which is already set once a signer has accepted, so a later reject from an already-accepted signer is correctly ignored — the asymmetry is one-directional (Reject → Accept is undercounted-on-clear; Accept → Reject is a no-op). This asymmetry is consistent with the finding above and does not change the conclusion.
