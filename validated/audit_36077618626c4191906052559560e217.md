### Title
Deterministic account-address squatting/front-running via lamport pre-funding permanently blocks legitimate `CreateAccount`/`CreateAccountWithSeed` (and any PDA-derived account creation) - (File: `programs/system/src/system_processor.rs`)

### Summary
The Fraxlend bug lets an attacker occupy a deterministically-derived address before the legitimate deployer, causing the legitimate creation to permanently revert with an "already in use" error. Agave's System Program has the exact same primitive: `create_account`/`create_account_with_seed` derive a target address from public, predictable inputs (a `base` pubkey + string `seed`, or a program-derived address from fixed seeds) and refuse to proceed if the target already holds any lamports. Because a plain SOL transfer to an uninitialized account requires no signature from that account, anyone watching the mempool who can compute the same address can "squat" it first and permanently DoS the intended account creation at that address.

### Finding Description
`create_account` in `programs/system/src/system_processor.rs` guards against re-initialization purely by checking the lamport balance of the destination: [1](#0-0) 

The destination address itself, however, can be fully deterministic and public before the creating transaction lands, either via `CreateAccountWithSeed` (`Address::create` re-derives `Pubkey::create_with_seed(base, seed, owner)` and only requires the `base` — not the derived `to` account — to sign): [2](#0-1) [3](#0-2) 

or via a program-derived address computed from fixed seeds, as `bpf_loader_upgradeable`'s `DeployWithMaxDataLen` does for the ProgramData account (`find_program_address(&[new_program_id.as_ref()], program_id)`), then calls the very same vulnerable `system_instruction::create_account` internally through `native_invoke_signed`: [4](#0-3) 

Because an ordinary `system_instruction::transfer` can add lamports to *any* pubkey without that pubkey signing (no account initialization is required to receive lamports), an attacker who can predict the target address (from a public `base`/`seed`, a public `program_id`, or a public sequence-derived seed as used by `stake-accounts`/`accounts-cluster-bench`) can front-run the honest creation transaction with a 1-lamport transfer. When the honest `CreateAccount`/`CreateAccountWithSeed` instruction later executes, `to.get_lamports() > 0` is true and the instruction fails with `SystemError::AccountAlreadyInUse`, exactly mirroring the Fraxlend `deployedPairsBySalt` collision revert.

Agave developers have already recognized and partially remediated this exact class with the newer `CreateAccountAllowPrefund` instruction, which intentionally drops the `lamports() > 0` guard: [5](#0-4) [6](#0-5) 

However, this opt-in instruction only helps callers who explicitly migrate to it; the legacy `CreateAccount` and `CreateAccountWithSeed` paths — still used pervasively (BPF Loader Upgradeable deploy flow, `stake-accounts`, `cli` nonce/stake account creation, `accounts-cluster-bench`) — remain squattable.

### Impact Explanation
Any unprivileged actor observing the mempool (or simply knowing a public base key / program id / deterministic seed scheme in advance) can grief account creation for a specific target address: the legitimate transaction reverts, wastes fees/compute, and the derived address becomes permanently unusable for that base+seed (or that specific program id's ProgramData PDA), forcing the victim to regenerate keys/seeds and retry. For automated or scripted deployment/staking flows that assume a specific deterministic address (e.g., program deploys keyed to a publicly announced program id, or seed-indexed stake account splitting), this is a reliable, repeatable denial-of-service against the intended state mutation — directly analogous to the Fraxlend salt-squatting DoS.

### Likelihood Explanation
The attack requires only an ordinary `system_instruction::transfer` (no elevated privileges, no CPI, no special program access) and knowledge of a deterministic address derivable from public data (base key + seed string, or `find_program_address` seeds). This is trivially reachable from any user's transaction and is broadly documented as a known Solana ecosystem gotcha, which is corroborated by Agave's own introduction of `CreateAccountAllowPrefund` specifically to work around it — but only for adopters of the new instruction.

### Recommendation
- Encourage/require migration of all internal `create_account`/`create_account_with_seed` call sites that create deterministic (predictable) target addresses — especially `bpf_loader_upgradeable`'s ProgramData creation in `DeployWithMaxDataLen`/`DeployWithMaxDataLen2`, and the `stake-accounts`/CLI seed-derived flows — to `CreateAccountAllowPrefund`, or otherwise tolerate pre-existing lamports on the target account instead of treating any positive balance as fatal "already in use".
- Where the destination must remain a fresh account (not intended to tolerate prefunding), require accompanying proof that the account has no executable data/owner state rather than relying solely on `lamports() > 0`.

### Proof of Concept
1. Observe a pending transaction (or infer in advance) that will call `system_instruction::create_account_with_seed(from, to, base, seed, ..)` or trigger `bpf_loader_upgradeable::DeployWithMaxDataLen` for a known `program_id`.
2. Compute the deterministic destination: `to = Pubkey::create_with_seed(base, seed, owner)` (as done in `system_processor.rs::Address::create`, [7](#0-6) ) or `find_program_address(&[program_id.as_ref()], bpf_loader_upgradeable::id())` (as in `programs/bpf_loader/src/lib.rs` line 281).
3. Submit a plain `system_instruction::transfer(attacker, to, 1)` with higher priority fee so it lands first.
4. When the victim's `CreateAccount`/`CreateAccountWithSeed`/`DeployWithMaxDataLen` transaction executes, `create_account` sees `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse`, permanently blocking creation at that address (test coverage for the equivalent legitimate-failure path exists in `test_create_already_in_use`, [8](#0-7) , confirming the exact check being exploited).
