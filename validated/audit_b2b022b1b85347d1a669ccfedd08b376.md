### Title
Changing APR away from 0 while an APR0 withdraw receipt is pending bricks `stopEpoch` (revert) and freezes the epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug reads a per-CPU value that does not exist when the SMP feature is off, crashing instead of returning a safe value. The analog in `IdleCreditVault` is `prepareStopEpochWithApr0`: the `apr0TotalPrincipal` bucket is only meaningful while the strategy operates in APR0 mode (`unscaledApr == 0`), yet the function unconditionally reverts `NotAllowed` when the bucket is non-zero and `unscaledApr != 0`. Since `stopEpoch` calls it before doing anything else, a pending APR0 receipt plus any later non-zero APR makes every epoch stop revert, freezing the pool.

### Finding Description
- `requestWithdraw` routes requests into the APR0 bucket whenever `unscaledApr == 0` and the pool is not closed: `_requestWithdrawApr0` increments `apr0TotalPrincipal` [1](#0-0) [2](#0-1) .
- `prepareStopEpochWithApr0` fast-paths only when `apr0TotalPrincipal == 0`; otherwise it reverts if `unscaledApr != 0` [3](#0-2) .
- `stopEpoch`/`_stopEpoch` invokes `prepareStopEpochWithApr0` at the start of settlement, before funds are pulled and before `_setScaledApr(_newApr)` can change the APR [4](#0-3) .
- `setAprs`/`setApr` (callable by the manager) mutate `unscaledApr` freely and contain no guard against `apr0TotalPrincipal != 0` [5](#0-4) .

Sequence (APR0 vault): user requests a normal withdraw during the buffer of an APR0 epoch → `apr0TotalPrincipal > 0`. The epoch runs; manager (honest, in-scope) raises APR via `setAprs(x, xScaled)` mid-epoch — a routine operation. At epoch end, every `stopEpoch` call reverts `NotAllowed` inside `prepareStopEpochWithApr0`, regardless of `_newApr`, because the check reads the stale-mode bucket value. `apr0TotalPrincipal` is only cleared by a successful `stopEpoch` (line 540) or a default finalization, so there is no forward path while APR is non-zero.

### Impact Explanation
Temporary freezing of funds: while the revert stands, the epoch cannot be stopped, no withdraw requests (normal, APR0, instant) can be funded or claimed, and `pendingWithdraws`/`apr0TotalPrincipal` cannot be unwound. The freeze persists for the entire window in which `unscaledApr != 0` and an APR0 receipt is pending; it is resolved only if the manager restores `unscaledApr` to 0 (or the borrower defaults and default finalization clears receipts). Loss is bounded by the duration of the freeze × frozen NAV (all `pendingWithdraws` plus deposits awaiting the next epoch).

### Likelihood Explanation
Low-to-medium. Triggering requires the honest manager to set a non-zero APR while an APR0 request is pending — plausible operationally but not attacker-controlled. An unprivileged user can only create the precondition (a cheap `requestWithdraw` during an APR0 epoch), which makes a routine APR change fatal. The comment indicates the revert was a deliberate consistency guard rather than an accident, so the finding is a design-level fragility (like `!CONFIG_SMP` reading `pcpu_hot`): a lifecycle-scoped value is consulted in a mode where it has no valid semantics, and the chosen fallback is a hard revert on the liveness-critical path.

### Recommendation
Handle the mode transition instead of reverting: in `prepareStopEpochWithApr0`, when `apr0TotalPrincipal != 0 && unscaledApr != 0`, settle the bucket at zero interest (or pro-rata using the last valid APR0 rate) and clear `apr0TotalPrincipal`, mirroring the kernel fix of inlining a safe `return 0` for the unavailable case. Alternatively, block APR changes while `apr0TotalPrincipal != 0` inside `setAprs`, keeping the revert but moving it off the epoch-critical path.

### Proof of Concept
Foundry fork/test sketch (extends `test/foundry/IdleCreditVault.t.sol` harness helpers):

```solidity
function testApr0ReceiptBlocksStopAfterAprChange() external {
    IdleCreditVault cv = IdleCreditVault(address(strategy));
    // APR0 vault: manager sets APR to 0
    vm.prank(manager);
    cv.setAprs(0, 0);

    address user = makeAddr("apr0-user");
    _depositWithUser(user, 10_000 * ONE_SCALE, true);

    // user opens a withdraw request while APR == 0 -> apr0TotalPrincipal > 0
    vm.prank(user);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(cv.apr0TotalPrincipal(), 0);

    _startEpochAndCheckPrices(0);

    // honest manager raises APR mid-epoch
    vm.prank(manager);
    cv.setAprs(10e18, _scaleAprWithBuffer(10e18));

    // every stopEpoch reverts in prepareStopEpochWithApr0: epoch is frozen
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // funds remain locked: no claim possible
    vm.prank(user);
    vm.expectRevert(); // epoch never advanced past request epoch
    cdoEpoch.claimWithdrawRequest();

    // only recovery: manager restores APR 0
    vm.prank(manager);
    cv.setAprs(0, 0);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // now succeeds
}
```

    address _cdo = idleCDO;

    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
