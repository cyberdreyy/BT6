### Title
Compliance `seizeWithMemo` can be front-run and permanently DOSed by the seized account — ([File: crates/common/precompiles/src/b20_asset/logic/v2.rs])

### Summary
The B-20 asset/stablecoin `seizeWithMemo` precompile operation force-moves a fixed `amount` of tokens from a target account `from` to `to`, gated only by the `SeizeExempt` policy scope, which is deliberately independent from the `TransferSender`/`TransferReceiver` transfer policy scopes. Because of this independence, an account that is seizable (not exempt from seizure) can still be fully authorized to transfer under `TransferSender`. This lets the targeted account front-run a pending `seizeWithMemo` transaction with an ordinary `transfer` that drains its balance, causing the seize to revert with `InsufficientBalance` — the same class of amount-vs-balance front-running DOS described in the JOJO liquidation report.

### Finding Description
`seize_with_memo` in `AssetV2`/`StablecoinV2` enforces only `B20Guards::ensure_seizable` (the `SeizeExempt` policy scope) on `from`, then calls `move_balance`, which reverts if `token.accounting().balance_of(from) < amount`: [1](#0-0) 

`move_balance` performs the exact same "amount must not exceed current balance" check that the JOJO report flags: [2](#0-1) 

Crucially, `ensure_seizable` and the transfer-sender authorization used by ordinary `transfer` are two independent policy scopes — `SeizeExempt` vs `TransferSender`. The unit test explicitly documents and proves this independence: an account that is not seize-exempt (i.e., "seizable") is not automatically blocked from initiating transfers: [3](#0-2) [4](#0-3) 

By contrast, `burn_blocked` uses `ensure_blocked`, which is tied to the same `TransferSender` scope that gates ordinary transfers, so a blocked account genuinely cannot move funds out before a forced burn — that path is not vulnerable. `seizeWithMemo`, however, has no such coupling: `from`'s ability to transfer is entirely orthogonal to whether it is "seizable," so a seize target that still holds transfer authorization can always race a compliance seize transaction.

### Impact Explanation
`seizeWithMemo` is a compliance/asset-recovery primitive (e.g., recovering stolen or sanctioned stablecoin/asset funds) gated behind the `Seize` role — it is meant to guarantee an issuer can freeze/recover funds from a designated account regardless of that account's wishes. Because the balance check is a hard equality-style requirement (`from_balance < amount` reverts the whole call) and `from` retains ordinary transfer rights, the targeted account (or an accomplice with knowledge of the mempool) can observe the pending `seizeWithMemo` transaction and front-run it with a `transfer`/`transferFrom` moving the funds to another address it controls before the seize executes. The seize call then reverts, and the funds have already left the seizable account. This defeats the entire purpose of the seize mechanism — permanent evasion of an asset freeze/recovery action, which is the intended remedy for hacks, exploits, or sanctioned activity on these B-20 tokens. This is the direct analog of the JOJO liquidation DOS: a fund-recovery/enforcement action rendered unreliable by a value that must equal (or be bounded by) a balance the target fully controls.

### Likelihood Explanation
Any account subject to seizure retains full, unrestricted ability to submit ordinary transfers unless the issuer has also separately restricted it via the `TransferSender` policy. Since `SeizeExempt` and `TransferSender` are independently configured policy scopes (as proven by `test_ensure_seizable_is_independent_of_transfer_sender_policy`), issuers commonly configuring seize policy will not automatically also block transfers for the same account. An attacker/compromised account needs only mempool visibility of the pending seize transaction (a public compliance action, typically not hidden) and enough gas to front-run it — a low-cost, repeatable action requiring no special privilege.

### Recommendation
Do not hard-revert `seizeWithMemo`/`move_balance` when `amount` exceeds the target's current balance in the seize path; instead, cap the seized amount to `min(amount, balance_of(from))`, or re-derive/clamp the transferable amount atomically within the same precompile call rather than trusting a caller-supplied fixed value. Alternatively, couple `SeizeExempt` accounts to an automatic freeze of `TransferSender`/`TransferReceiver` authorization so a seizable account cannot move funds out before the seize lands.

### Proof of Concept
1. Admin holds the `Seize` role on a B-20 asset/stablecoin token; account `Alice` (`from`) is not `SeizeExempt`, so `B20Guards::ensure_seizable` passes for her, but she is still authorized under `TransferSender`/`TransferReceiver` (default `ALWAYS_ALLOW`, or explicitly authorized).
2. Admin submits `seizeWithMemo(from: Alice, to: Treasury, amount: ALICE_BALANCE, memo)` to recover Alice's entire balance (see call path at [1](#0-0) ).
3. Alice observes this transaction in the mempool and front-runs it with `transfer(to: SomeOtherWallet, amount: 1)` (or any nonzero amount), reducing her balance below `ALICE_BALANCE`.
4. Admin's `seizeWithMemo` transaction is now processed against a reduced balance; `move_balance` computes `from_balance < amount` and reverts with `InsufficientBalance` ( [2](#0-1) ), so the seize transaction fails on-chain.
5. Alice repeats this front-running strategy indefinitely (or drains the account entirely via ordinary transfers before the seize is retried with a corrected amount), permanently evading the intended asset-recovery/freeze action.

    fn seize_with_memo(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        from: Address,
        to: Address,
        amount: U256,
        memo: B256,
    ) -> Result<()> {
        B20Guards::ensure_not_paused(token, IB20::PausableFeature::SEIZE)?;
        B20Guards::ensure_token_role(token, caller, B20TokenRole::Seize)?;
        // `to != 0` guards against a disguised burn; `from != 0` guards against a disguised mint
        // (`Transfer(0x0, to, ...)`), matching `transfer_inner`.
        if to == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidReceiver { receiver: to }));
        }
        if from == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidSender { sender: from }));
        }
        if from == to {
            return Err(BasePrecompileError::revert(IB20::InvalidReceiver { receiver: to }));
        }
        B20Guards::ensure_seizable(token, from)?;

        // treasury need not be allowlisted by default.

    /// Ensures `account` is seizable, i.e. NOT authorized by the current seize-exempt policy.
    ///
    /// Mirrors [`Self::ensure_blocked`] but consults `SEIZE_EXEMPT_POLICY` instead of the
    /// transfer-sender policy: accounts authorized by that scope are exempt from seizure, so an
    /// account is seizable only when the configured registry policy does not authorize it, and
    /// the unset always-allow default keeps seizure closed until an issuer configures the slot.
    /// Used by `seizeWithMemo`. Enforced unconditionally, including in the factory bootstrap
    /// window. Reverts `AccountNotSeizable` (distinct from `ensure_blocked`'s `AccountNotBlocked`)
    /// so the seize path and the deprecated `burnBlocked` report separately.
    pub fn ensure_seizable<T: Token + ?Sized>(token: &T, account: Address) -> Result<()> {
        let policy_scope = B20PolicyType::SeizeExempt.id();
        let policy_id = token.accounting().policy_id(policy_scope)?;
        if token.policy().is_authorized(token.policy_storage(), policy_id, account)? {
            Err(BasePrecompileError::revert(IB20::AccountNotSeizable { account }))
        } else {
            Ok(())
        }
    }

    fn test_ensure_seizable_is_independent_of_transfer_sender_policy() {
        // A token with the transfer-sender policy set must NOT make an account seizable: the
        // seizable scope is unset (ALWAYS_ALLOW), so every account is authorized => not seizable.
        let allowed = Address::repeat_byte(0xaa);
        let denied = Address::repeat_byte(0xbb);
        let token = token_with_transfer_sender_policy(allowed);

        // `allowed` is authorized by transfer-sender AND by unset seizable (ALWAYS_ALLOW).
        assert_eq!(
            B20Guards::ensure_seizable(&token, allowed).unwrap_err(),
            BasePrecompileError::revert(IB20::AccountNotSeizable { account: allowed })
        );

        // `denied` is NOT authorized by transfer-sender, but still not seizable because the
        // seizable policy is unset (ALWAYS_ALLOW) — proving the two scopes are independent.
        assert_eq!(
            B20Guards::ensure_seizable(&token, denied).unwrap_err(),
            BasePrecompileError::revert(IB20::AccountNotSeizable { account: denied })
        );
    }
