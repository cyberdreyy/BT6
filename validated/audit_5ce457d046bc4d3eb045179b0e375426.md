Confirmed. The vulnerability is a stale-confirmation / removed-member bypass in the multisig contracts, structurally analogous to the PSP22 approve race: a value (confirmation count) is checked against a threshold without re-validating that the underlying authorization (membership) is still current at execution time.

### Title
Multisig Request Can Execute Below the Live-Member Confirmation Threshold via Stale Confirmations from Removed Members - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` and `multisig/src/lib.rs` authorizes execution of a pending request purely by counting the size of the `confirmations` `HashSet` recorded against a `request_id`, without re-checking that every account/key in that set is still a current member of the multisig at execution time. `delete_member` (multisig2) / the `DeleteKey` action (multisig) only purges *requests originated by* the removed member, but never purges *confirmations cast by* that member on requests originated by someone else. This lets a request execute with fewer than `num_confirmations` *live* members having actually approved it — breaking the core custody guarantee: `confirmations_from_current_members >= num_confirmations` before any `Transfer`, `AddKey`, `FunctionCall`, etc. is executed.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` decides to execute a request solely from cardinality: [1](#0-0) 

The confirmations are stored keyed only by `request_id`, as raw stringified `MultisigMember` values with no link back to current membership at check time: [2](#0-1) 

`delete_member` cleans up only requests where the removed member was the *requester* (`r.member == member`), not requests where the removed member had merely *confirmed*: [3](#0-2) 

Attack sequence:
1. Multisig has members `{A, B, C}` with `num_confirmations = 2`.
2. `A` calls `add_request` for a sensitive action (e.g. `Transfer` or `AddKey`) targeting `receiver_id`. This creates request `R` with an empty confirmations set.
3. `B` calls `confirm(R)`. Since `confirmations.len() + 1 (=1) < 2`, `B`'s membership string is inserted into the confirmations set for `R`; `R` is not yet executed.
4. Members execute a separate, properly-confirmed request that removes `B` via `DeleteMember { member: B }`. `delete_member` only scans `self.requests` for entries whose *originating* `member == B` — request `R` was originated by `A`, so it is untouched, and `B`'s stale confirmation entry inside `self.confirmations.get(&R)` is never cleared.
5. `B` is now not in `self.members`; the live threshold should logically require 2 *current* members to approve.
6. `C` (or even `A` again is blocked by the "already confirmed" check, so it must be a third distinct member, or simply `C`) calls `confirm(R)`. `confirm` reads `confirmations.get(&R)` → `{B}`, checks `!contains(C)` → true, then `confirmations.len() as u32 + 1 (=2) >= num_confirmations (2)` → **executes** `execute_request(R)`.
7. The request executes with `execute_request` using `A`'s original request and only `C`'s live confirmation plus `B`'s stale, no-longer-valid confirmation — i.e., only 1 currently-valid member (`C`) plus the original proposer `A`'s implicit intent, but never 2 *live, still-valid-member* confirmations were required to have both been checked against current `self.members`.

The identical flaw exists in the legacy `multisig/src/lib.rs`, where `DeleteKey` purges only requests keyed by `r.signer_pk == pk` (the requester), leaving confirmations made *by* that key on other requests intact: [4](#0-3) [5](#0-4) 

This is the direct analog of the PSP22 `approve` double-spend: an authorization value (`allowance` / `confirmations` count) is mutated/consumed based on stale state instead of being re-validated at the moment of use, allowing the acting party to spend/execute against a stale snapshot of trust.

### Impact Explanation
This crosses the explicitly listed Critical impact category: "a multisig request executed below threshold." A `Transfer` action can move NEAR out of the multisig-controlled account, or an `AddKey`/`AddMember` action can grant a malicious actor control of the account, having been approved by fewer live, currently-trusted members than `num_confirmations` requires. Since the multisig contract is meant to gate all outgoing NEAR movement and privilege changes, this directly breaks the equality `confirmations_by_current_members >= num_confirmations` that the whole security model rests on.

### Likelihood Explanation
The scenario requires collusion or misbehavior by a member who is about to be removed (or was already compromised, which is often exactly the reason for removing them) plus timing around a `delete_member`/`DeleteKey` action. This is a very plausible operational pattern for a multisig (removing a member for cause, e.g. suspected key compromise, while old pending requests exist) — a removed member's prior "confirm" on some other pending request remains valid indefinitely since there is no expiry/invalidation tied to membership changes.

### Recommendation
In `confirm()`, before counting/executing, filter the confirmations set to members that are still present in `self.members` (or, upon any `delete_member`/`DeleteKey` action, iterate all confirmation sets and strip entries matching the removed member, not just requests originated by them). The threshold check should be based on the count of confirmations from currently valid members only:
```rust
let live_confirmations = confirmations.iter()
    .filter(|m| self.members.contains(&MultisigMember::from_string(m)))
    .count();
```
or, simpler and more robust, purge stale confirmations whenever membership changes.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. As `A`: `add_request({receiver_id: multisig_account, actions: [Transfer{amount: X}]})` → `request_id = R`.
3. As `B`: `confirm(R)` → confirmations for `R` = `{B}` (not yet executed, since 1 < 2).
4. As `A` + `C` (2 confirmations, a separate properly threshold-met request): execute `DeleteMember{member: B}` — removes `B` from `self.members`, deletes only requests *originated* by `B` (none), leaves `R`'s confirmation set `{B}` untouched.
5. As `C`: `confirm(R)` → `confirmations.len() (1) + 1 = 2 >= num_confirmations (2)` → `execute_request(R)` runs, transferring `X` NEAR — despite only `A` (proposer) and `C` (confirmer) being *current* members who ever interacted with `R`, with `B`'s stale confirmation counted toward the threshold after `B` was removed.

        self.assert_valid_request(request_id);

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
