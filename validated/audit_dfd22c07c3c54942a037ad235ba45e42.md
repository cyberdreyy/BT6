### Title
Stale confirmations from removed multisig members are never purged, allowing requests to execute below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in the `multisig2` contract only deletes *requests originated by* the removed member; it never scrubs that member's *confirmations* that they cast on requests originated by someone else. Those stale confirmations remain in the `confirmations` set and are still counted by `confirm()` toward `num_confirmations`, so a request can execute with fewer genuinely live, currently-authorized members confirming than the configured threshold requires.

### Finding Description
`confirm()` counts confirmations purely by set membership/length: [1](#0-0) 

`assert_valid_request()` only validates that the *caller* confirming right now is a current member, the request exists, and the confirmations map exists — it never re-validates that the confirmations already stored in the set still belong to current members: [2](#0-1) 

`delete_member()` removes the departing member from `self.members`, deletes the access key/promise, clears `num_requests_pk` for that member, and deletes *only the requests that member itself created* — but it does not iterate over `self.confirmations` to strip that member's confirmation entries from requests created by other members: [3](#0-2) 

Because of this gap, a confirmation cast by a member who is later removed continues to count toward the threshold `num_confirmations` on any request that member confirmed but did not create.

Concrete trace of the binding break (equality: `confirmations counted == live members who actually approved`):
- 5 members {A,B,C,D,E}, `num_confirmations = 3`.
- Member B creates a malicious/self-serving request R (`add_request`).
- Member A confirms R → `confirmations(R) = {A}`.
- The multisig executes a `DeleteMember{A}` request (guard `members.len()-1 >= num_confirmations` → `4 >= 3`, passes) — A is removed from `self.members`, but `confirmations(R) = {A}` is left untouched because R was created by B, not A.
- Members = {B,C,D,E} now, threshold still 3.
- C confirms R → `confirmations(R) = {A, C}`, length 2, `2+1 >= 3` false, stored.
- D confirms R → `confirmations(R).len()+1 = 3 >= 3` → true → `execute_request(R)` runs.

R executes having received real approval from only C and D (2 currently-live members) plus a stale approval from A, who is no longer a member — i.e., the request executed below the actual live-member threshold of 3-of-4.

### Impact Explanation
This breaks the core custody/authorization guarantee of the multisig: execution is supposed to require `num_confirmations` distinct *currently authorized* approvals. Because stale approvals from removed members persist and still count, an attacker (a member scheduled for or in the process of removal, or one who colludes before being purged) can get a `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, or `DeployContract` request executed with fewer live approvals than intended. This matches the "Critical: a multisig request executed below threshold" impact category, since it can directly move funds or grant access rights that should have required broader current consensus.

### Likelihood Explanation
The scenario requires no special privilege beyond being (or having recently been) a legitimate multisig member — a realistic situation whenever a compromised or malicious member is removed via governance while a pending request they confirmed is still outstanding. No redeploy, foundation action, or external actor is needed; it is triggered purely through the contract's own `add_request` → confirm → `delete_member` → confirm sequence.

### Recommendation
When removing a member in `delete_member`, iterate over all pending requests in `self.confirmations` and strip the removed member's entry from every confirmation set (not just requests they authored), or re-validate at `confirm()`/execution time that every entry in a request's `confirmations` set still corresponds to a current `self.members` entry before counting it toward `num_confirmations`.

### Proof of Concept
Using the existing test scaffolding in `multisig2/src/lib.rs` tests module (e.g., `context_with_key`, `members()`):
```rust
// members = 5 accounts/keys, num_confirmations = 3
let mut c = MultiSigContract::new(members(), 3);

// B creates request R
testing_env!(context_with_account(member_b(), amount));
let request_id = c.add_request(transfer_request());

// A confirms R
testing_env!(context_with_account(member_a(), amount));
c.confirm(request_id);

// Multisig removes A via DeleteMember (requires separate confirmed request, 3 confirms)
// ... run through add_request/confirm x3 for DeleteMember{A} ...
// after execution, self.members no longer contains A, but confirmations(request_id) still contains A

// C confirms R
testing_env!(context_with_account(member_c(), amount));
c.confirm(request_id); // confirmations = {A, C}, len 2

// D confirms R -> triggers execution with only 2 live approvals (C, D) + 1 stale (A)
testing_env!(context_with_account(member_d(), amount));
c.confirm(request_id); // executes despite only 2-of-4 live members truly approving
assert_eq!(c.requests.len(), 0); // request executed
```
This demonstrates R executes with `num_confirmations = 3` nominally satisfied, but only 2 of the 4 currently live members actually approved it.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
