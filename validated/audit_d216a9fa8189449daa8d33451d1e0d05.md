## Title
Operator commission earned before `switch_operator` permanently bypasses the operator's configured beneficiary on distribution - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::switch_operator` unlocks the outgoing operator's pending commission and records it in the `distribution_pool` under the outgoing operator's raw address, then re-keys the `StakingContract` under the *new* operator. When that commission is later paid out via `distribute`/`distribute_internal`, the beneficiary redirect logic only checks the distribution recipient against the *current* operator parameter, so the outgoing operator's commission is paid to their raw account instead of their configured beneficiary, and this cannot be fixed after the fact.

### Finding Description
`switch_operator` flushes already-inactive funds and then calls `request_commission_internal(old_operator, &mut staking_contract)` to unlock any newly accrued (not-yet-inactive) commission before re-assigning the stake pool to `new_operator`: [1](#0-0) 

`request_commission_internal` records this pending commission with `recipient = operator` (the *old* operator address) inside `staking_contract.distribution_pool`, via `add_distribution`: [2](#0-1) 

Once the lockup expires, anyone can call the permissionless `distribute` entry function, which resolves the `StakingContract` under the *current* map key (`new_operator`) and calls `distribute_internal(staker, new_operator, staking_contract)`: [3](#0-2) 

Inside `distribute_internal`, the beneficiary redirect only triggers when the stored distribution `recipient` equals the `operator` argument passed in: [4](#0-3) 

Because the `distribution_pool` entry for the pre-switch commission is keyed to the *old* operator's address while `distribute_internal` is invoked with the *new* operator's address, `recipient == operator` is false, so `beneficiary_for_operator(recipient)` is never consulted. The old operator's commission is deposited to their raw account instead of the beneficiary they configured via `set_beneficiary_for_operator`. Because the `StakingContract` is now stored under `new_operator`'s key in the `SimpleMap`, `distribute(staker, old_operator)` will abort (`assert_staking_contract_exists` fails), so there is no way to ever route this specific commission chunk through the old operator's beneficiary — the misrouting is permanent.

### Impact Explanation
This corrupts commission-payout accounting: value that should go to the operator's designated beneficiary is instead credited to a different address (the outgoing operator's own account) with no recovery path. This matches the required impact "Operator commission, beneficiary payout, or share-accounting corruption that credits the wrong account or traps value." If the beneficiary mechanism is relied upon for custody separation (e.g., a validator operator key with limited trust routing rewards to a secure treasury beneficiary), this silently defeats that separation for any commission pending at the moment of an operator switch.

### Likelihood Explanation
`switch_operator`/`switch_operator_with_same_commission` are normal, expected staker operations documented as convenience functions to change operators without unstaking. Any commission percentage > 0 accrued at switch time triggers `request_commission_internal`, which always creates this stranded distribution entry. `distribute` is explicitly a permissionless entry function ("Allow anyone to distribute already unlocked funds"), so any third party can trigger the mis-routed payout once the lockup expires — no special privilege is required to realize the corruption, only patience for the normal unlock/lockup cycle.

### Recommendation
When recording distributions in `add_distribution`/`request_commission_internal`, store the resolved beneficiary address (or resolve/redirect at `switch_operator` time by immediately distributing any pending commission to the correct beneficiary before switching) instead of deferring the beneficiary lookup to a later `distribute_internal` call keyed by the then-current operator. Alternatively, `distribute_internal` should redirect any recipient found to `beneficiary_for_operator(recipient)` unconditionally (for any address recorded as an operator-commission recipient), rather than only when `recipient == operator`.

### Proof of Concept
1. Staker creates a staking contract with `operator1` and commission > 0.
2. `operator1` calls `set_beneficiary_for_operator(operator1, beneficiary1)`.
3. Stake pool earns rewards (epoch passes), so `operator1` has unpaid commission.
4. Staker calls `switch_operator(staker, operator1, operator2, new_commission)`. This internally calls `request_commission_internal(operator1, ...)`, which adds a `distribution_pool` entry for `operator1`'s pending commission and unlocks it, then re-keys the `StakingContract` under `operator2`.
5. Wait for lockup expiration; anyone calls `distribute(staker_address, operator2)`.
6. `distribute_internal` runs with `operator = operator2`; the `operator1` distribution entry doesn't match, so `aptos_account::deposit_coins` sends the commission to `operator1` directly — `beneficiary1` never receives it, and there is no longer any way to call `distribute(staker, operator1)` to fix it since that key no longer exists in the `Store`.

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );
