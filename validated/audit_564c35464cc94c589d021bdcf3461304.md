### Title
Node-side stale rejection weight is never retracted when a signer flips from Reject to Accept, causing spurious `SignersRejected` on a fully-signed block - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run` tracks per-block signer weight in a shared `BlockStatus` using two independent counters — `total_weight_approved` and `total_weight_rejected` — gated by two *different* de-duplication sets: the approve path gates on `gathered_signatures` while the reject path gates on `responded_signers`. Because a single signer's slot can be present in `responded_signers` (from an earlier rejection) without yet being present in `gathered_signatures`, that signer's weight can be added to `total_weight_rejected` and later *also* added to `total_weight_approved` when the same signer legitimately re-evaluates and signs. The reverse direction (reject after accept) is correctly blocked, but reject weight is never decremented or cleared when a signer subsequently accepts. This lets `total_weight_rejected` remain permanently elevated by stale data, which is compared against `weight_threshold` independently of `total_weight_approved` in `SignerCoordinator::get_block_status`.

### Finding Description
`BlockStatus` (stacks-node/src/nakamoto_node/stackerdb_listener.rs:70-82) holds:
```
pub responded_signers: HashSet<u32>,
pub gathered_signatures: BTreeMap<u32, MessageSignature>,
pub total_weight_approved: u32,
pub total_weight_rejected: u32,
```

On `BlockResponse::Accepted` (lines 386-465), the weight-add guard is:
```rust
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
```

On `BlockResponse::Rejected` (lines 486-518), the weight-add guard is:
```rust
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
```

Sequence that breaks the equality "aggregated weight == distinct signer weight that currently supports/opposes the block":
1. Signer S (slot `k`, weight `w`) sends `Rejected` for block B first. `responded_signers.insert(k)` succeeds → `total_weight_rejected += w`. `gathered_signatures` is untouched.
2. This is a normal, sanctioned transition: per `docs/signer-flows.md` §2 (`BlockState`), `LocallyRejected → LocallyAccepted` is an explicit, allowed re-evaluation path, and `stacks-signer/src/v0/signer.rs` (`should_reevaluate_block`/`should_reevaluate_reject_reason`) is designed precisely to let a signer change a prior rejection into an acceptance for the *same* `signer_signature_hash` once conditions change (e.g., prior conflict goes stale, node re-validates OK).
3. Signer S later sends `Accepted` for the same block B. Check is `!gathered_signatures.contains_key(k)` — true, since `k` was never inserted into `gathered_signatures` (only into `responded_signers`). So `total_weight_approved += w` fires.
4. Result: `total_weight_approved + total_weight_rejected` now double-counts signer S's weight `w`; `total_weight_rejected` is never decremented despite S no longer rejecting.

This value is consumed unconditionally in `SignerCoordinator::get_block_status` (stacks-node/src/nakamoto_node/signer_coordinator.rs:509-513):
```rust
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected { ... });
}
```
This check runs on every loop iteration independent of `total_weight_approved`, and is checked *before* the approval-threshold check. Because rejection weight is monotonic (never decreases) while a single signer's earlier, now-superseded rejection remains baked in, a block that has since reached full/valid signature weight (>= `weight_threshold`) from the *current* votes of every signer can still trip the reject-threshold path first if stale rejected weight (from since-reversed signers) plus `weight_threshold` exceeds `total_weight`.

### Impact Explanation
This is a liveness wedge (High) on the miner/coordinator side: a valid, ultimately-approved block can be treated as globally rejected (`SignersRejected`) due to leftover weight from signers who already reversed their vote to Accept, because the two counters are not mutually exclusive/consistent. This can force the miner to discard transactions, apply erroneous per-txid exclusions (the same code path drives `temporarily_excluded_txids`/`permanently_excluded_txids` based on `total_weight_rejected` — stacks-node/src/nakamoto_node/signer_coordinator.rs:509-540), and repeatedly fail to get otherwise-valid blocks accepted, stalling tenure progress. It requires only ordinary, permitted signer behavior (one signer rejecting then later accepting the same proposal, which the signer's own state machine explicitly supports) rather than a majority of colluding/faulty signers.

### Likelihood Explanation
The reject→accept flip is not an edge case requiring adversarial signers: `docs/signer-flows.md`'s `BlockState` diagram and `stacks-signer/src/v0/signer.rs`'s `should_reevaluate_block`/`should_reevaluate_reject_reason` logic explicitly implement and encourage this transition (e.g., a signer initially rejects because of a stale/refuted conflict or an async-validation timing gap, then later signs the same block once the node's view is re-confirmed). Any single signer taking this normal path against a block the miner is waiting on can trigger the described inconsistency, making this readily reachable in ordinary network conditions (slow validation responses, timing races described in `stacks-signer/src/v0/tests.rs`'s `async_sibling_validation` module) without requiring a majority.

### Recommendation
Make the two counters consistent by using a single per-slot “decision” state (e.g., store the last decision — Accept or Reject — per slot, gated by one canonical set) so that:
- Weight is added to `total_weight_approved` or `total_weight_rejected` exactly once per slot, based on the *latest* decision, and
- Switching a slot's decision moves its weight between the counters (decrementing the old one, incrementing the new one) instead of only ever incrementing.
Concretely, replace the independent `gathered_signatures`/`responded_signers` guards with a single `HashMap<u32, Decision>` (Decision::Accepted(sig) | Decision::Rejected) and recompute/adjust `total_weight_approved`/`total_weight_rejected` transactionally whenever a slot's decision changes.

### Proof of Concept
1. Configure a reward set with signers S1..Sn where S1 has weight `w1`, and `weight_threshold` is 70% of total weight; suppose other signers already reject enough weight such that `total_weight_rejected + weight_threshold` is close to but below `total_weight`, with S1 not yet having voted.
2. S1 sends `BlockResponse::Rejected` for block B (e.g., due to a locally-detected but soon-stale conflict, per `stacks-signer/src/v0/signer.rs` conflict-freshness logic) → `total_weight_rejected += w1` in `StackerDBListener` (stackerdb_listener.rs:515-518).
3. S1's local conflict goes stale / node re-validates OK, and per the documented `LocallyRejected → LocallyAccepted` re-evaluation path, S1 later sends `BlockResponse::Accepted` for the same `signer_signature_hash` with a valid signature.
4. In the listener, `gathered_signatures` does not yet contain S1's slot, so `total_weight_approved += w1` fires (stackerdb_listener.rs:443-464), while `total_weight_rejected` still contains `w1` from step 2 (never decremented).
5. If `total_weight_rejected` (inflated by S1's earlier, now-reversed vote combined with any other genuinely-rejecting signers) satisfies `total_weight_rejected + weight_threshold > total_weight` in `SignerCoordinator::get_block_status`, the miner returns `SignersRejected` even though `total_weight_approved` may independently have already reached `weight_threshold` from currently valid signatures — demonstrating the aggregated-weight-vs-current-verified-accepts equality break and the resulting liveness wedge.
