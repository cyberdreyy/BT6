### Title
Funded instant-withdraw claims never clear per-epoch receipt accounting, inflating `defaultPendingClaimBasis` and permanently locking default-recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The kernel bug removes an object from its pending list while it is still referenced, so a concurrent teardown frees backing that a walk still uses. The analog here is the inverse bookkeeping leak: `claimInstantWithdrawRequest` pays (consumes) an instant receipt through the funded path but only zeroes the aggregate `instantWithdrawsRequests[_user]` — it never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. The receipt is "paid" but remains registered as an outstanding claim in the per-epoch tables that default finalization later walks.

### Finding Description
In `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393), the funded claim path does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

It does not touch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` or `instantWithdrawClaimsByEpoch[currentEpoch]`, which were both incremented in `requestInstantWithdraw` (lines 371-372). `collectInstantWithdrawFunds` (line 401) decrements `pendingInstantWithdraws` when the CDO collects, but the per-epoch claim tables are only ever cleared inside `_claimDefaultedInstantWithdrawRequest` (lines 847-853) — a path reachable only after default finalization.

`defaultPendingClaimBasis` (lines 644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0` at finalization. If some instant claimants already withdrew via the funded path during the epoch (strategy held collected cash), their paid-out amounts are still counted in the basis. The result in `finalizeDefaultRecovery` (lines 685-692):

- `recoveryPrice = reserveAmount * 1e18 / totalBasis` is computed against a basis inflated by already-paid claims → the recovery ratio is too low for every genuine claimant.
- After all real claims execute (`_claimDefaultedInstantWithdrawRequest` reverts for already-paid users on the `instantWithdrawsRequests[_user] -= claimBasis` underflow at line 848, so they can never re-claim), the reserve retains the phantom share with no possible claimant.

### Impact Explanation
Permanent freezing of recovery funds and diluted payouts. Example with numbers: two users each request 100e6 instant in epoch N; the strategy collects 100e6 (pendingInstantWithdraws = 100e6 remaining unfunded... concretely: user A claims his funded 100e6 while `instantWithdrawClaimsByEpoch[N]` stays 200e6). At default finalization with `pendingInstantWithdraws = 100e6`, basis includes 200e6 of instant claims instead of 100e6. With 150e6 reserve against real total basis of, say, 300e6, the inflated 400e6 basis yields price 0.375e18 instead of 0.5e18 — every defaulted receipt holder is underpaid by 25%, and the excess reserve is stranded forever since no clearing path exists for the phantom basis. This is a direct loss socialization error caused by stale claim records — the same class as the kernel's "object still walked after teardown."

### Likelihood Explanation
Requires: (1) instant withdrawals partially funded during an epoch such that some users claim via `claimInstantWithdrawRequest` while `pendingInstantWithdraws` remains non-zero, and (2) a subsequent borrower default in that same epoch (`epochNumber` unchanged at finalization). Both are normal operational states: partial instant funding is explicitly handled by `_defaultPrefundedInstantReserve`, and defaults are a designed-for flow. Any unprivileged user claiming a funded instant receipt triggers the stale accounting; no privileged collusion needed.

### Recommendation
In `claimInstantWithdrawRequest`, when paying the funded claim, also clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the paid amount (mirroring `_claimDefaultedInstantWithdrawRequest`), so `defaultPendingClaimBasis` only counts genuinely outstanding receipts.
