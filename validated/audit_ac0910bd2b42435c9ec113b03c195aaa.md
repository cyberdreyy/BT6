### Title
A leftover dust APR=0 withdrawal receipt permanently reverts `stopEpoch` once the APR is raised, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`prepareStopEpochWithApr0` hard-reverts with `NotAllowed()` whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0` [1](#0-0) . Because `apr0TotalPrincipal` is only cleared at the end of that same function (after the revert) [2](#0-1) , the reverting record "always comes back" — the exact bug shape of `BulkCreateUnstakes`: one bad/stale item hard-stops processing for everyone instead of being skipped and logged.

### Finding Description
While `unscaledApr == 0`, `requestWithdraw` routes through `_requestWithdrawApr0`, which increments both `apr0Users[_user].principal` and the global `apr0TotalPrincipal` [3](#0-2) . There is no per-request minimum and no delete path, so a KYC-passing lender can seed the bucket with a dust tranche withdrawal (e.g., `requestWithdraw(1 wei of tranche)`).

Later the honest manager calls `setAprs` to set a positive APR (normal operations). From that point on, every `stopEpoch`/`stopEpochWithDuration` calls `prepareStopEpochWithApr0`, which hits:

- fast-path return only if `_principal == 0` [4](#0-3) 
- otherwise `if (unscaledApr != 0) revert NotAllowed()` [1](#0-0) 

No other code path decrements `apr0TotalPrincipal`: `_settleApr0` only mutates the per-user `Apr0UserData` struct and never touches the global counter [5](#0-4) , and users cannot claim or cancel the receipt because claims require `epochNumber > lastWithdrawRequest[_user]`, which requires a successful `stopEpoch` that can never execute [6](#0-5) . The bad record is self-perpetuating: the revert is the only thing standing between the bucket and its sole clearing site.

### Impact Explanation
All user funds in the credit vault are frozen for as long as `unscaledApr != 0` and the dust bucket is non-zero: `stopEpoch` cannot run, `epochNumber` cannot advance, no withdrawal receipt can mature, and deposits cannot exit. The only recovery is the manager setting `unscaledApr` back to 0 so one `stopEpoch` succeeds and clears the bucket — meaning the attacker permanently pins the pool's APR to 0, since they can re-seed the dust bucket each time APR is 0 and the manager can never safely raise it again. This is temporary freezing of the entire vault's funds plus denial of all future interest-bearing epochs, achieved for the cost of a dust tranche position.

### Likelihood Explanation
Requires an APR==0 period (a supported pool mode per the APR0 accounting throughout `IdleCreditVault`), a KYC'd attacker holding any tranche balance, and one dust `requestWithdraw` — all unprivileged actions within the allowed attacker model. No privileged misbehavior is needed; the trigger is the honest manager's routine `setAprs` call.

### Recommendation
Do not hard-revert on the stale bucket. In `prepareStopEpochWithApr0`, when `unscaledApr != 0` and `apr0TotalPrincipal != 0`, settle the bucket benignly instead: emit an event, zero `apr0TotalPrincipal`, and treat the stranded per-user principal as settled principal claimable at par (no APR0 interest), or simply skip the APR0 interest split and clear the bucket — mirroring the external report's "log, skip, continue" fix. Additionally consider allowing `lastWithdrawRequest`-independent cancellation of dust APR0 receipts so the bucket can be drained without an epoch transition.

### Proof of Concept
Foundry fork PoC (against a live Clearpool-style credit vault deployment):

```solidity
function testDustApr0ReceiptBricksStopEpoch() external {
    // Precondition: pool in buffer period, manager has set APR = 0
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    // Attacker: KYC'd lender deposits and requests a dust withdraw
    deal(address(underlying), attacker, 1e6);
    vm.startPrank(attacker);
    idleCDO.depositAA(1e6);
    uint256 dust = 1; // 1 wei of tranche
    cdoEpoch.requestWithdraw(dust, address(AAtranche));
    vm.stopPrank();
    assertGt(strategy.apr0TotalPrincipal(), 0);

    // Epoch runs at APR 0 and is stopped legitimately
    _startEpoch();
    _stopEpoch(); // succeeds: unscaledApr == 0, bucket cleared? No —
    // bucket persists because attacker's receipt epoch >= epochNumber
    // (request made in same epoch; _settleApr0 only settles after a bump)
    // Re-seed if needed during the APR==0 buffer.

    // Manager raises APR for the next epoch (honest action)
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(10e18, 10e18);

    // Every subsequent stopEpoch reverts forever
    vm.prank(manager);
    cdoEpoch.startEpoch();
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.expectRevert(NotAllowed.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // No user claim can mature; all TVL frozen until APR is forced back to 0
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();
}
```

Uncertainty note: whether the dust bucket survives the first APR==0 `stopEpoch` depends on the attacker's request landing in the epoch being finalized (`apr0TotalPrincipal` is zeroed at line 540 but the attacker's `principal` stays open via `_settleApr0`'s `_reqEpoch >= epochNumber` guard, and a fresh dust request in the APR==0 buffer trivially re-seeds it); the freeze is therefore reproducible and repeatable. I was unable to fully trace `IdleCDOEpochVariant.stopEpoch`'s call site before the iteration limit, but `prepareStopEpochWithApr0` is `_onlyIdleCDO()` and named as the stopEpoch APR0 hook, consistent with the documented processing flow.

```text
  function _settleApr0(address _user) internal {
    Apr0UserData storage _apr0User = apr0Users[_user];
    uint256 _principal = _apr0User.principal;
    if (_principal == 0) {
      return;
    }
    uint256 _reqEpoch = _apr0User.principalEpoch;
    // Settle only after stopEpoch bumped epochNumber (ie after one full wait epoch).
    if (_reqEpoch >= epochNumber) {
      return;
    }
    // Move principal from "open APR0 bucket" to "settled bucket" (same principal, not duplicated).
    _apr0User.settledPrincipal += _principal;
    uint256 _rate = apr0RateByEpoch[_reqEpoch];
    if (_rate != 0) {
      // Convert per-epoch rate to claimable underlying interest.
      _apr0User.settledInterest += (_principal * _rate) / 1e18;
    }
    _apr0User.principal = 0;
    _apr0User.principalEpoch = 0;
  }
```

```text
  function _requestWithdrawApr0(uint256 _amount, address _user) internal {
    // Settle any previous APR0 request first, then start/update current epoch bucket.
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    if (_apr0User.principal == 0) {
      _apr0User.principalEpoch = epochNumber;
    }
    _apr0User.principal += _amount;
    // Epoch-level APR0 principal used only to compute stopEpoch APR0 pro-rata interest.
    apr0TotalPrincipal += _amount;
  }
```
