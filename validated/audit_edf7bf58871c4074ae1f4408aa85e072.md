### Title
Loss-adjusted withdraw haircut bypassed for receipts from earlier epochs — only `lastWithdrawRequest` epoch is checked - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a validation that must confirm two things match (asset AND USDC) but uses OR, so it passes when only the "always present" side matches. The analog lives in `IdleCreditVault`: the loss-adjusted receipt validation only consults the single epoch stored in `lastWithdrawRequest[_user]`. A loss haircut applies to the aggregate `pendingWithdraws` bucket (all pending receipts, regardless of their request epoch), but both the re-request guard and the claim path key the haircut off only `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. A user whose latest request predates the loss epoch has `lossRecoveryPriceByEpoch[oldEpoch] == 0`, so the "is this receipt loss-adjusted" check silently passes and the receipt is paid at par from the already-reduced funded pool — identical failure mode: a check that should match the actual affected item validates only an unrelated, always-present counterpart.

### Finding Description
When `collectWithdrawFunds(_amount)` is called with `_amount < pendingBasis`, the whole `pendingWithdraws` aggregate is haircutted and `lossRecoveryPriceByEpoch[epochNumber]` is set (lines 411-421). The haircut is epoch-keyed to the *current* epoch, but every pending receipt — including ones requested in older epochs and recorded under `withdrawsRequestsByEpoch[_user][oldEpoch]` — loses value, because `pendingWithdraws` is zeroed for the full aggregate basis.

On the claim side, `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` and `lossRecoveryPriceByEpoch[lossEpoch]` (lines 790-792). For a user whose last (and only) request was made in an earlier epoch `M < N`, `lossRecoveryPriceByEpoch[M] == 0`, so the function returns 0 and execution falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` **at par** via `_transferFundedClaim` (lines 338-349, 897-907). The re-request guard in `requestWithdraw` (lines 261-271) has the same blind spot — it only inspects `lastWithdrawRequest[_user]`, so it cannot catch receipts haircutted in a different epoch either.

Result: the user burns `normalAmount` receipt tokens and withdraws the full un-haircutted amount, while the strategy only received the haircutted `_amount` from the borrower/CDO. The excess is paid out of underlying that was funded to cover other users' haircutted receipts — the same "validation succeeds because only one leg of the pair was checked" bug as `_validateSpotMarket`.

### Impact Explanation
Direct theft / insolvency of the withdrawal reserve. The attacker extracts `(1 - lossRecoveryPrice) * receiptAmount` more than entitled; the last claimants of epoch `N`'s haircutted pool find the strategy's funded balance short by that amount and their `claimWithdrawRequest` reverts on ERC20 transfer or pays less — permanent loss of other users' funded withdrawals, quantified as `receiptAmount * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL`.

### Likelihood Explanation
Requires: (1) a user requests a withdraw in epoch `M` and deliberately does not claim after `stopEpoch` bumps `epochNumber` past `M` (no cost — claims stay valid indefinitely, and `_claimFundedWithdrawRequest` only reverts while `epochNumber <= lastWithdrawRequest[_user]`); (2) a later epoch ends with partial borrower funding via `stopEpochWithDuration`/`collectWithdrawFunds` shortfall, which is an ordinary protocol flow, not an attacker-dependent event. An unprivileged KYC-passed lender can hold a stale receipt and wait; no privileged-role misbehavior needed. Not stopped by `_transferFundedClaim`'s reserve guard (that only protects `defaultRecoveryReserve`), not by the Default revert paths, and not by the `requestWithdraw` guard, which checks the same wrong epoch.

### Recommendation
Track loss-adjusted epochs per receipt rather than per user. Either store a bitmap/set of pending loss epochs per user and have both `requestWithdraw` and `claimWithdrawRequest` iterate/reject when *any* epoch with a nonzero basis has `lossRecoveryPriceByEpoch[epoch] != 0`, or key `lossRecoveryPriceByEpoch` lookups per request epoch inside `_clearWithdrawClaimForEpoch`/`_withdrawClaimAmountsForEpoch` so each epoch's basis is settled at its own recovery price — the equivalent of checking both `tokens[0]` and `tokens[1]` instead of OR-ing on one index.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

// Fork test against a live IdleCDOEpochVariant + IdleCreditVault pair.
contract LossEpochBypassPoC is Test {
    IdleCDOEpochVariant cdo;
    IdleCreditVault strategy;
    IERC20Detailed under;
    address aaTranche;
    address lender;   // attacker: KYC-passed AA holder
    address lender2;  // victim: another AA holder

    function setUp() public {
        // fork mainnet, load deployed cdo / strategy / tranche / underlying
        // lender, lender2 = seeded AA tranche holders (isWalletAllowed passed)
    }

    function testStaleReceiptEscapesHaircut() public {
        uint256 amount = 100_000e6;

        // --- Epoch M (running): both lenders request withdraw ---
        vm.prank(lender);  cdo.requestWithdraw(amount);   // records epoch M basis
        vm.prank(lender2); cdo.requestWithdraw(amount);

        // borrower funds epoch M fully; stopEpoch bumps epochNumber to M+1
        _runEpochToStop(/* full funding */);
        // attacker deliberately does NOT claim; claim window stays open forever.

        // --- Epoch N (> M): lender2 (or others) still have pending receipts ---
        vm.prank(lender2); cdo.requestWithdraw(amount);   // new pending bucket

        // Epoch N stops with a shortfall: borrower funds only 50% of pendingWithdraws
        // -> strategy.collectWithdrawFunds(pending/2) sets
        //    lossRecoveryPriceByEpoch[N] = 0.5e18, pendingWithdraws = 0
        _runEpochToStopWithPartialFunding();

        // --- Attacker claims: stale epoch-M receipt escapes the epoch-N haircut ---
        // _claimLossAdjustedWithdrawRequest uses lossEpoch = lastWithdrawRequest[lender] = M
        // lossRecoveryPriceByEpoch[M] == 0  ->  falls through to funded path, paid at PAR
        uint256 before = under.balanceOf(lender);
        vm.prank(lender); cdo.claimWithdrawRequest();
        uint256 attackerGot = under.balanceOf(lender) - before;

        assertEq(attackerGot, amount);               // full amount, no 50% haircut
        // assert: strategy funded balance is now short by amount * (1 - 0.5)
        // => lender2's claim of amount*0.5 reverts on transfer (insolvency)
        vm.expectRevert();
        vm.prank(lender2); cdo.claimWithdrawRequest();
    }
}
```
