### Title
Loss-adjusted withdraw receipts are claimed at par when the user makes a second request — over-claim of unfunded basis (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The slirp over-read reads beyond the real packet length; the analog here is `claimWithdrawRequest` paying a *larger* receipt than was actually funded. When a borrower's `stopEpochWithDuration` under-funds pending withdraws, `collectWithdrawFunds` stores a haircut in `lossRecoveryPriceByEpoch[epoch]` but leaves `withdrawsRequests[_user]` at full basis. `_claimLossAdjustedWithdrawRequest` only looks up `lastWithdrawRequest[_user]` (the *latest* request epoch), so if the same user submits a second withdraw request in a later epoch, the earlier loss-adjusted receipt is never haircut and is paid at par through `_claimFundedWithdrawRequest`, draining funds belonging to other claimants.

### Finding Description
- `collectWithdrawFunds` (`IdleCreditVault.sol:411-430`): when `_amount < pendingBasis`, it zeroes `pendingWithdraws` and records `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis`. Only the funded `_amount` of underlying is transferred in. Per-user `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][epoch]` remain at full basis.
- `_claimLossAdjustedWithdrawRequest` (`IdleCreditVault.sol:789-801`): computes `lossEpoch = lastWithdrawRequest[_user]` and returns early if `lossRecoveryPriceByEpoch[lossEpoch] == 0`. It only ever checks the *last* request epoch — there is no iteration over earlier epochs.
- `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:319-350`): after the `epochNumber > lastWithdrawRequest[_user]` gate passes, it pays `withdrawsRequests[_user]` — the aggregate across **all** epochs — at par via `_transferFundedClaim`.

Attack sequence (running → stopped-with-loss → buffer → running):
1. Attacker (any KYC'd tranche holder) calls `IdleCDOEpochVariant.requestWithdraw` for a large amount in epoch N.
2. `stopEpochWithDuration(_lossAmount)` runs; borrower under-funds receipts, so `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL` and only the funded portion lands in the strategy.
3. Attacker calls `requestWithdraw` again for a dust amount in epoch N+1, setting `lastWithdrawRequest[attacker] = N+1`.
4. Epoch N+1 ends normally; borrower funds the dust receipt. Now `epochNumber > lastWithdrawRequest[attacker]`.
5. `claimWithdrawRequest`: `_claimLossAdjustedWithdrawRequest` checks `lossRecoveryPriceByEpoch[N+1] == 0` → returns 0 without clearing epoch-N basis. `_claimFundedWithdrawRequest` then pays `withdrawsRequests[attacker]` = full epoch-N basis + dust at par.

Existing guards do not stop this: the epoch-wait check passes legitimately; the loss-adjusted path exists but is keyed only to the last request epoch; the code comment at `:323` explicitly permits stacking requests ("he will have to wait for another epoch to claim both requests").

### Impact Explanation
The strategy contract only received `_amount` (haircut value) for epoch-N receipts plus the dust funding for epoch N+1, yet pays out the full unhaircut basis. The excess `(basis − funded)` is paid from underlying that belongs to other users' funded receipts or to active NAV → direct theft / insolvency of the vault. Quantified: attacker with a receipt of basis B funded at recovery price p steals `B × (1 − p)`; with a 50% loss on a 100k receipt, the attacker extracts ~50k underlying that was never funded.

### Likelihood Explanation
Requires an honest-manager `stopEpochWithDuration` partial-loss event (a defined, reachable code path, not a privileged attack — the borrower under-repays). The attacker then needs only two normal `requestWithdraw` calls and one epoch wait. No privileged cooperation needed. Likelihood is bounded by how often loss-adjusted stops occur, but the exploit is fully permissionless once one does.

### Recommendation
Track loss-adjusted receipts per epoch rather than keying off `lastWithdrawRequest`. In `claimWithdrawRequest`, either iterate the user's request epochs to find any `lossRecoveryPriceByEpoch[e] != 0`, or record the user's loss-epoch separately (e.g., `lossAdjustedEpoch[_user]` set at funding time, or per-epoch receipt enumeration), and always clear/haircut epoch-N basis before falling through to `_claimFundedWithdrawRequest`. Alternatively, mark `withdrawsRequestsByEpoch[_user][lossEpoch]` as settled at haircut price in `collectWithdrawFunds`.

### Proof of Concept
```solidity
// test/foundry/PocLossAdjustDoubleClaim.t.sol — fork test against deployed vault
function testLossAdjustedReceiptPaidAtPar() external {
    // epoch N running; attacker deposits AA and requests full withdraw
    idleCDO.depositAA(100_000e6);
    cdoEpoch.startEpoch();
    uint256 req = cdoEpoch.requestWithdraw(0, address(AAtranche)); // say 100_000e6

    // borrower under-funds: stopEpochWithDuration with 50% loss on pending receipts
    // -> collectWithdrawFunds(50_000e6); lossRecoveryPriceByEpoch[N] = RECOVERY_FULL/2
    cdoEpoch.stopEpochWithDuration(loss);

    // attacker files a second dust request in epoch N+1
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // lastWithdrawRequest = N+1
    cdoEpoch.startEpoch();
    // borrower fully funds the new epoch; stopEpoch bumps epochNumber > N+1
    cdoEpoch.stopEpoch(0, interest);

    uint256 balPre = underlying.balanceOf(attacker);
    cdoEpoch.claimWithdrawRequest();
    // expected (correct): ~50_000e6 + dust ; actual: 100_000e6 + dust paid at par
    assertGt(underlying.balanceOf(attacker) - balPre, fundedAmount);
    // strategy underlyings now insufficient to cover remaining claimants -> insolvency
}
```
