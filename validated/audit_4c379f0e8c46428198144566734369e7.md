### Title
`SortitionsView::validate_tenure_change_payload` (v1 protocol) checks only globally-accepted blocks, not locally-signed ones, for a same-tenure duplicate — [File: `stacks-signer/src/chainstate/v1.rs`]

### Summary
The v1 (local sortition-state) protocol's tenure-change duplicate check in `stacks-signer/src/chainstate/v1.rs:505-518` still queries `get_last_globally_accepted_block(&block.header.consensus_hash)` to decide whether a competing tenure-start block should be rejected as a `DuplicateBlockFound`. The v2 (global-state) equivalent in `stacks-signer/src/chainstate/v2.rs:344-357` was already fixed to use `get_last_signed_block`, which also counts `LocallyAccepted` blocks, because — per the regression test at `stacks-signer/src/chainstate/tests/v2.rs:748-850` — the globally-accepted-only version "would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change." This exact class of check ("did this signer already put a signature on a competing block in this tenure?") is weaker in v1 than in v2, an asymmetry between two code paths that are supposed to enforce the same invariant. ### Finding Description
`check_proposal` (v1) delegates tenure-start blocks to `validate_tenure_change_payload`, which is documented as running only at proposal arrival and never again (`docs/signer-flows.md:425-431`). This proposal-time gate is meant to reject a second, competing tenure-start block for a tenure the signer has already signed a block in. In v1 it does so with:
```rust
let last_in_current_tenure = signer_db
    .get_last_globally_accepted_block(&block.header.consensus_hash)...
```
which only recognizes a prior block as "already signed" once the whole signer set has produced a globally accepted signature bundle, not once *this* signer itself locally accepted (i.e., signed) an earlier tenure-start block. [4](#0-3) 

Compare to the v2 fix, which explicitly changed the equality being tested from "globally accepted" to "signed (locally or globally)" specifically because a signer's own signature is the safety-relevant fact, not global consensus:
```rust
let last_in_current_tenure = signer_db
    .get_last_signed_block(&block.header.consensus_hash)...
``` [5](#0-4) 

The regression test that motivated the v2 fix reproduces exactly the same scenario that remains reachable through the v1 path: a signer has locally accepted (signed) a tenure-start block, that block has not yet reached global acceptance, and a second tenure-start block for the same tenure is proposed. Under v1's `get_last_globally_accepted_block` check, `check_proposal` incorrectly treats the second proposal as non-duplicate and passes it on to node validation and pre-commit collection. [6](#0-5) 

Note on the downstream defense-in-depth gate: the shared final signing gate in `stacks-signer/src/v0/signer.rs` (`handle_block_pre_commit` → `get_signed_conflicts` / `conflict_still_blocks`, `stacks-signer/src/v0/signer.rs:1374-1421`, `stacks-signer/src/signerdb.rs:1606-1625`) independently re-checks for a fresh, still-live sibling signature before the signer actually signs. For a *single* signer that itself signed the first block, this gate is documented to still block the second signature (a locally-accepted, not-yet-globally-accepted sibling at the same height keeps the conflict "live" per `docs/signer-flows.md:259-261` and the `conflict_still_blocks` logic at `stacks-signer/src/v0/signer.rs:1192-1206`). This means the v1 proposal-time weakness does not, by itself, let the *same* signer sign both competing blocks — it only removes the early, explicit `DuplicateBlockFound` rejection at proposal time, letting the malformed/duplicate proposal proceed further (consuming a validation slot, being stored, and being pre-committed/gossiped) than it should for the local sortition-state (v1) code path, before the final gate (if reached) catches it.

### Impact Explanation
This is an authorization/validation-boundary asymmetry between two supposedly-equivalent code paths (v1 vs v2), matching the CWE-863 class of the reference report: a security check (duplicate/one-per-tenure enforcement) is correctly scoped in one path but incorrectly scoped (too narrow — "globally accepted" instead of "signed") in the other. Concretely, on the v1 (local sortition-state) protocol path, a miner can get past the proposal-time `DuplicateBlockFound` rejection for a second, competing tenure-start block in a tenure where a signer has already locally accepted (signed) a first tenure-start block but where that first block has not yet reached global acceptance. The direct, provable consequence is a reduction from a Critical, sticky, broadcast rejection (`DuplicateBlockFound` at proposal time, matching v2 behavior) to reliance solely on the best-effort, node-dependent `conflict_still_blocks`/freshness heuristic at pre-commit time — a heuristic that can itself return "not live" (and thus allow signing) if the conflicting block goes stale, or if the node cannot be reached the same way, or once `last_endorsed > freshness_cutoff` no longer holds. I could not fully confirm, within the time available, a concrete path where the final gate is guaranteed to fail (e.g., after the freshness cutoff has passed the original signer could legitimately re-sign a replacement, which is by design), so I am not asserting a full signature-safety break with certainty — only that the v1 path's weaker proposal-time equality check is a real, demonstrable narrowing of an authorization-relevant condition, matching the report's bug class, whose full end-to-end consequence depends on timing/staleness conditions in the final gate that I could not exhaustively trace here.

### Likelihood Explanation
This requires only a single miner (the one-slot actor allowed by the rules) proposing two competing tenure-start blocks for the same tenure with some minimal timing (the first proposal locally accepted/signed by a signer, but not yet globally accepted, before proposing the second). No majority of signers or another signer's key is needed to trigger the code path difference; the divergence in behavior between v1 and v2 is purely a function of which protocol version the signer is running.

### Recommendation
Change `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` (as v2 already does) instead of `get_last_globally_accepted_block`, so that a locally-accepted (self-signed) block in the current tenure is also treated as a same-tenure duplicate at proposal time, matching v2's fixed behavior and closing the asymmetry. ### Proof of Concept
Conceptual reproduction (mirrors the existing v2 regression test, but exercised against the unpatched v1 path):
1. Run a signer configured to use the v1 (local sortition-state) protocol path (`check_block_against_local_state` → `SortitionsView::check_proposal`, `stacks-signer/src/v0/signer.rs:875-939`).
2. Miner proposes tenure-start block B1 for tenure T; the signer validates it, pre-commits, and eventually reaches `mark_locally_accepted` (signs B1), while B1 does not (yet) reach global (whole-signer-set) acceptance.
3. Miner proposes a second tenure-start block B2 for the same tenure T (e.g., with different transactions), same as the existing v2 test setup at `stacks-signer/src/chainstate/tests/v2.rs:805-838` but run through v1's `check_proposal`.
4. Because v1's `validate_tenure_change_payload` calls `get_last_globally_accepted_block` (which returns `None` since B1 is only locally accepted), the `DuplicateBlockFound` rejection at proposal time does not fire — unlike the patched v2 behavior, which correctly rejects B2 immediately (`stacks-signer/src/chainstate/tests/v2.rs:846-849`).
5. B2 is stored and forwarded into the validation/pre-commit pipeline instead of being rejected outright at proposal time, relying solely on the separate, timing-dependent `conflict_still_blocks` heuristic to prevent an eventual double-signature — a materially weaker guarantee than the explicit, sticky rejection the v2 path provides for the identical scenario.
