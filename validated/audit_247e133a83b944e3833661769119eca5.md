### Title
Missing allowlist enforcement in `HandleLegacyUserMessage` allows unauthorized fan-out of user requests to all DON nodes - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` validates message parsing, payload timestamp/staleness, and method name, but explicitly skips authorization/allowlist checks (marked by `// TODO: apply allowlist and rate-limiting here`) before broadcasting the caller-supplied JSON-RPC request to every member of the DON. Any signed message accepted by `common.ValidatedRequestFromMessage` reaches all `donConfig.Members` via `don.SendToNode`, regardless of whether the sender/workflow is allowlisted.

### Finding Description
The legacy user-message path is: gateway HTTP endpoint → `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-292`) → `handlers.Handler.HandleLegacyUserMessage` (routed via `multiHandler.HandleLegacyUserMessage`, `core/services/gateway/multihandler.go:53-60`) → the capabilities `handler.HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`).

In `HandleLegacyUserMessage`, the checks performed before forwarding are only:
1. JSON unmarshal of `webapicap.TriggerRequestPayload` [1](#0-0) 
2. Non-zero timestamp [2](#0-1) 
3. Message-age/staleness check [3](#0-2) 
4. Method-name check (`MethodWebAPITrigger`) [4](#0-3) 

Immediately after these, the code comment `// TODO: apply allowlist and rate-limiting here` (line 384) sits directly above the method check, and no allowlist/authorization lookup keyed on sender or workflow ID is ever performed. The request is then converted via `common.ValidatedRequestFromMessage` (which only checks that `MessageId`/`Method` are non-empty — see `core/services/gateway/handlers/common/message_util.go:82-105`, no authorization logic) and unconditionally fanned out to every DON member: [5](#0-4) .

Upstream, `gateway.ProcessRequest` only calls `msg.Validate()` for legacy requests, which is a structural/signature-format validation, not an allowlist check [6](#0-5) . No sender-to-workflow allowlist gate exists anywhere on this path, so any caller who can produce a validly-signed `api.Message` (any address, since `msg.Validate()` just checks the signature matches the claimed sender, not that the sender is authorized) can trigger delivery of an arbitrary `web_api_trigger` payload to all DON node addresses in `h.donConfig.Members`.

### Impact Explanation
This corresponds to the "allowlist/quota bypass" and "unauthorized job/workflow run" impact classes: an attacker who is not part of any workflow's allowlist can still cause their JSON-RPC trigger payload to be broadcast to and processed by every node in the DON, effectively bypassing the intended access-control gate that should restrict who can invoke workflow triggers through the gateway. This can lead to unauthorized workflow execution fan-out and resource consumption across the whole DON.

### Likelihood Explanation
Preconditions are minimal: the attacker needs no special credential beyond the ability to sign a message with any keypair (the message is self-signed by the sender, not by a privileged party) and reach the gateway's legacy user-message HTTP endpoint. The request just needs to pass basic structural validation (non-empty method/ID, fresh timestamp, correct `web_api_trigger` method, valid `TriggerRequestPayload` JSON), all of which are attacker-controlled. This is trivially repeatable for any request.

### Recommendation
Implement the allowlist/authorization check called out by the TODO before line 397: verify that `msg.Body.Sender` (or the workflow/owner identified in the `TriggerRequestPayload`) is present in a configured allowlist for the DON/handler, and enforce per-sender rate limiting, before calling `common.ValidatedRequestFromMessage` and fanning the request out to `don.SendToNode`. Reject and respond with an authorization error (e.g. a new `api.ErrorCode` such as `Unauthorized`) for senders not present in the allowlist.

### Proof of Concept
Go unit test plan (extending `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Use `setupHandler(t)` to construct a `handler` with a `donConfig.Members` list and a mocked `handlers.DON`.
2. Build a legacy `api.Message` with `Method: MethodWebAPITrigger`, a valid `TriggerRequestPayload` (fresh timestamp, non-empty params), signed by a private key/address that is not part of any known workflow allowlist configuration (no allowlist config exists in `HandlerConfig` at all currently).
3. Set `don.EXPECT().SendToNode(mock.Anything, mock.Anything, mock.Anything).Return(nil)` for each `donConfig.Members` entry.
4. Call `handler.HandleLegacyUserMessage(ctx, msg, callback)`.
5. Assert that `SendToNode` was invoked once per DON member (i.e., `don.AssertExpectations(t)` / `don.AssertNumberOfCalls(t, "SendToNode", len(donConfig.Members))`) despite the sender not being allowlisted anywhere — demonstrating the fan-out proceeds unconditionally, confirming the missing allowlist enforcement described by the TODO.
