I found a valid analog in the original multisig contract's `DeleteKey` action, which crosses the same "authorisation binding" class as the reported BAMM issue: an action is executed without re-validating that the operation still leaves the trust boundary (confirmation threshold vs. live signer set) intact.

### Title
`DeleteKey` execution can drop the live-key count below `num_confirmations`, permanently locking the multisig funds - (File: `multisig/src/lib.rs`)

### Summary
`multisig/src/lib.rs` implements a K-of-N multisig where any `num_confirmations` distinct access keys can authorize a `MultiSigRequestAction::DeleteKey` action that removes one of the multisig's own access keys. Unlike the newer `multisig2` contract, which explicitly asserts `self.members.len() - 1 >= self.num_confirmations` before removing a member [1](#0-0) , the original `multisig` contract's `DeleteKey` branch performs no such check [2](#0-1) .

### Finding Description
The binding this contract is supposed to maintain is: `number of live access keys >= num_confirmations` (the K-of-N invariant), so that `confirm()` can always reach the threshold and execute pending/future requests. `DeleteKey` mutates the "N" side of this binding without checking it against `num_confirmations`:
```
MultiSigRequestAction::DeleteKey { public_key } => {
    self.assert_self_request(receiver_id.clone());
    let pk: PublicKey = public_key.into();
    // delete outstanding requests by public_key
    ...
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
``` [2](#0-1) 

`self.num_confirmations` is a value the contract tracks internally and can only be changed via `SetNumConfirmations` [3](#0-2) , but the contract has no way to query the blockchain for the actual number of live access keys on the account (acknowledged explicitly in the contract's own README) [4](#0-3) . Because `DeleteKey` requests are executed through the normal `confirm()` flow — the same K-of-N threshold used for transfers — any K keyholders (which could be fewer than a majority of stakeholders, or the result of key compromise/collusion among K holders) can submit and confirm enough `DeleteKey` requests to reduce the live key count below `num_confirmations`, making it impossible for future `confirm()` calls to reach the threshold.

### Impact Explanation
Once live keys < `num_confirmations`, no request (including `Transfer`, `AddKey`, or `SetNumConfirmations`) can ever be confirmed again, since `confirm()`'s only path to lowering `num_confirmations` itself requires reaching the (now unreachable) threshold [5](#0-4) . This matches the "Critical - funds permanently frozen" impact category: any NEAR balance held by the multisig account becomes permanently inaccessible, with no recovery path since the contract account cannot regain full-access control either.

### Likelihood Explanation
This requires no privileged role — any set of K existing signers (the minimum threshold already entitled to authorize actions) can trigger it, whether by mistake (deleting a key without realizing it drops below threshold, exactly the scenario the project's own README warns about) or by malicious collusion among exactly K of the N keyholders to intentionally freeze funds or grief remaining stakeholders. It is a straightforward one-transaction sequence: `add_request` + K `confirm` calls with a `DeleteKey` action targeting one of the remaining keys.

### Recommendation
Before executing `DeleteKey` (and any other action that reduces the multisig's live key set), assert that the resulting key count remains `>= num_confirmations`, mirroring the guard already present in `multisig2::delete_member` [1](#0-0) . Since `near-sdk` at this version has no way to query live access keys from within the contract, the contract needs to track the key count itself (as `multisig2` does via its `members` collection) rather than relying solely on `promise.delete_key`.

### Proof of Concept
1. Deploy `multisig` with `num_confirmations = 2` and exactly 2 access keys, `pk1` and `pk2`.
2. `pk1` calls `add_request` with `receiver_id = <multisig account>`, `actions = [DeleteKey { public_key: pk2 }]`.
3. `pk1` calls `confirm(request_id)` — only 1 confirmation exists so far (`confirmations.len() + 1 = 1 < 2`), so the request is *not* yet executed; a second confirmation is needed. This is the flaw: `confirm()` for a 2-of-2 setup still needs `pk2`'s own confirmation, which `pk2` will not give to delete itself — so this particular self-attack needs adjustment.
4. Correct PoC: use 3 keys `pk1, pk2, pk3` with `num_confirmations = 2`. `pk1` and `pk2` jointly confirm a `DeleteKey{public_key: pk3}` request — reducing keys to 2, still `>= 2`, no freeze yet. Then `pk1` and `pk2` jointly confirm a second `DeleteKey{public_key: pk1}` (or `pk2`) request, reducing live keys to 1 while `num_confirmations` remains 2. After this, `confirm()` from the sole remaining key can never reach `confirmations.len() + 1 >= 2` with only one live key participating, permanently freezing the account's funds and any future `SetNumConfirmations` recovery attempt (which itself needs the unreachable threshold).

**Note:** I explored the `w-near`, `staking-pool`, `lockup`, and `whitelist` contracts for a closer analog to the "receive-function revert" custody-binding pattern described in the report, but their deposit/withdraw and trust-delegation paths (`near_deposit`/`near_withdraw`, `internal_deposit`/`internal_ping`, `is_whitelisted`/`add_staking_pool`) all correctly gate custody and trust with proper checks (`assert_one_yocto`, `assert_called_by_foundation`, factory-success callbacks before whitelisting, etc.), so no exploitable divergence was found there. The `multisig` vs `multisig2` `DeleteKey`/`DeleteMember` discrepancy was the strongest reachable analog matching the required "threshold crossed without check" custody-binding class.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
