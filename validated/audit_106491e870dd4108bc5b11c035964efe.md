### Title
EI-authenticated caller bypasses "users only" integer job-ID guard in `PipelineRunsController.Create` and triggers arbitrary job runs - (File: core/web/pipeline_runs_controller.go)

### Summary
`prc.Create` intends to restrict integer-job-ID run triggering to real dashboard/API users, explicitly commenting "EIs not allowed," but the check `_, isUser := auth.GetAuthenticatedUser(c)` only tests the Go type of the session object, not its origin. Because `AuthenticateExternalInitiator` stores a synthesized `*clsessions.User{Role: UserRoleRun}` under the same `SessionUserKey`, `isUser` is `true` for EI callers too, letting any external-initiator credential holder run any job by numeric ID with no ownership/ACL check.

### Finding Description
`AuthenticateExternalInitiator` authenticates the EI's access key/secret and then sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` [4](#0-3) , mimicking a real user session so that `RequiresRunRole`/`RequiresEditRole` wrappers work uniformly. `GetAuthenticatedUser` simply type-asserts the stored object to `*clsessions.User` and returns `ok=true` regardless of whether it came from a session cookie, API token, or EI synthesis [5](#0-4) .

`prc.Create` uses exactly this boolean to gate the "run job by arbitrary int32 ID" branch: `_, isUser := auth.GetAuthenticatedUser(c); if isUser { ... prc.App.RunJobV2(ctx, jobID, nil) ... }` with the comment "only users are allowed to run jobs using int IDs - EIs not allowed" [6](#0-5) . Since the EI-synthesized value is indistinguishable from a real user at this call site, `isUser` is `true`, and the int-ID branch executes for EI callers — precisely the scenario the comment says should be rejected.

The route is reachable via `POST /v2/jobs/:ID/runs`, registered with `auth.AuthenticateExternalInitiator` as the first authentication method tried, followed only by `auth.RequiresRunRole` (role ≥ run) before calling `prc.Create` [1](#0-0) . `RequiresRunRole` checks only `user.Role == clsessions.UserRoleView` to reject; `UserRoleRun` passes [2](#0-1) . `RunJobV2` itself is called with only `jobID`/`nil` meta, with no check that the job is associated with, or was created for, the calling external initiator [7](#0-6) .

### Impact Explanation
Any external-initiator credential holder (a lower-trust integration credential, not an operator/admin) can trigger execution of any job on the node by numeric job ID — including jobs unrelated to that EI, potentially OCR/VRF/keeper or other jobs with side effects (on-chain transactions, external HTTP calls, task execution) — bypassing the intended EI-to-webhook-job scoping. This is an authorization bypass / unauthorized job run, matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
The only precondition is possession of one valid external-initiator access key/secret (a low-privilege credential intentionally scoped to run webhook-style jobs), which is far weaker than a full user session/API token. The exploit is a single unauthenticated-style POST request with a guessable/enumerable small integer job ID; no ownership, ACL, or job-EI-association check exists anywhere in this path, making it fully reproducible and repeatable.

### Recommendation
Change the check in `prc.Create` to positively verify the authenticated principal is a real user (not a synthesized EI user), e.g., by tracking session origin explicitly (a separate context key/flag set only by `AuthenticateBySession`/`AuthenticateByToken`), or by checking `auth.GetAuthenticatedExternalInitiator(c)` and rejecting when present, rather than relying on the coincidental Go type of the stored session value.

### Proof of Concept
Go handler-level test in `core/web/pipeline_runs_controller_test.go`:
1. Set up a gin context/router with `PipelineRunsController.Create` behind the same middleware chain as production (`auth.Authenticate(..., auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` then `auth.RequiresRunRole`).
2. Create/store a valid `bridges.ExternalInitiator` with known access key/secret, unrelated to any job.
3. Insert a job (e.g., via `app.AddJobV2`) not associated with that EI.
4. Send `POST /v2/jobs/<jobID>/runs` with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers (EI credentials) and no session cookie/API token.
5. Assert response is `200 OK` with a `pipelineRun` resource returned, and that `app.RunJobV2` was invoked for that job ID — proving the EI triggered a run of a job it has no association with, contradicting the "EIs not allowed" comment in `prc.Create`.
