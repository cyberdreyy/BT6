### Title
Updating a vote account's commission collector silently resets the *other* collector's authorized value when the account is still V3-serialized - (File: programs/vote/src/vote_state/handler.rs / programs/vote/src/vote_state/mod.rs)

### Summary
`update_commission_collector` (SIMD-0232) is reachable by any transaction that carries a `VoteInstruction` targeting a vote account, gated only by the vote account's authorized withdrawer signature. [1](#0-0)  When invoked against a vote account whose on-chain data is still stored in the legacy `V3` (or `V1_14_11`) format, the update path first migrates the account to `VoteStateV4` in-memory via `get_vote_state_handler_checked` → `try_convert_to_vote_state_v4`, mutates only the requested collector field, and writes the whole V4 struct back to the account. [2](#0-1) 

### Finding Description
`try_convert_to_vote_state_v4` does not have a real "block_revenue_collector"/"inflation_rewards_collector" field in V3/V1_14_11 source states, so on migration it fabricates defaults: `inflation_rewards_collector = *vote_pubkey` and `block_revenue_collector = state.node_pubkey`, unconditionally, for every V3→V4 conversion. [3](#0-2)  Because `update_commission_collector` performs this conversion transparently as part of processing a single-field update instruction, calling it with `CommissionKind::InflationRewards` against a still-V3 account causes the account to be rewritten as V4 with `inflation_rewards_collector` set to the new value the caller requested, but `block_revenue_collector` silently overwritten to the fabricated default (`node_pubkey`) rather than preserved/left unset — even though the vote account had never explicitly authorized any block-revenue collector value at all (the concept didn't exist under V3). This is the exact "mass update clears other fields" bug class described in the Tuleap CVE: a targeted update to one field, when it triggers an implicit whole-record conversion/rewrite, clobbers unrelated fields that the caller neither intended to touch nor was authorized to set for that value.

This is proven and explicitly documented by the repository's own test comment: "V3 -> V4 auto-conversion side-effect: updating one collector against a V3-serialized account causes the 'other' collector to be written as its V4 default ... per try_convert_to_vote_state_v4," and the test asserts the block-revenue collector unexpectedly becomes `v3_node_pubkey` as a side effect of only updating the inflation-rewards collector. [4](#0-3) 

By contrast, when the account is already V4, the same call path correctly leaves the untouched collector unchanged, as shown in the first sub-test. [5](#0-4)  The divergent behavior is purely a function of the account's on-disk serialization version, which the caller may not control or even know about, and the value written is not derived from any prior authorization — it's a fabricated default coming from `try_convert_to_vote_state_v4`.

### Impact Explanation
The `block_revenue_collector` (or `inflation_rewards_collector`, depending on which kind is updated) ends up pointing at `node_pubkey` (the validator identity) instead of whatever the vote account's actual/intended collector should be, without any explicit authorization instruction for that specific field. Since the commission-collector fields determine where staking/block-revenue rewards lamports are ultimately paid, this causes reward lamports to be redirected to an address the withdraw authority did not consent to for that specific commission kind — a form of unauthorized fund-destination corruption reachable by a single transaction sent by the vote account's authorized withdrawer against any vote account that has not yet been migrated to V4. Because vote-account commission/collector state feeds directly into reward distribution/stake accounting at the SVM/bank level, this can also produce state that differs from validator operator expectations (an unintended change with no explicit signer intent for that specific field), which is a state-corruption analog of the Tuleap "silently clears/overwrites data via mass update" bug class.

### Likelihood Explanation
Any vote account that has not yet had its state format upgraded to V4 (the default for older accounts, since V4/SIMD-0185 is a newer rollout) is affected the first time either `update_commission_collector` call (`InflationRewards` or `BlockRevenue` kind) is issued against it. The authorized withdrawer only needs to invoke the instruction meant to update one collector; they need not intend or know that the sibling field will be overwritten. This requires no special privilege beyond the normal withdrawer authority already needed to call the instruction, and is exercised via a completely ordinary, single, unprivileged (from the protocol's perspective, withdrawer-signed) transaction.

### Recommendation
`try_convert_to_vote_state_v4` should not fabricate `block_revenue_collector`/`inflation_rewards_collector` defaults blindly on every conversion path used by field-level update instructions; instead, `update_commission_collector` (and any other single-field updater that internally may trigger a version upgrade) should detect that a V3→V4 conversion occurred and, for the field kind *not* being explicitly updated in this call, either (a) reject the operation and require the caller to migrate the account explicitly first, or (b) preserve/initialize the untouched collector using a value that reflects no change in authorized recipient (e.g., require both collectors to be set together on first migration, or make the "unset" default explicit and distinguishable so it isn't confused with an authorized value). At minimum, this migration side effect must be clearly signed off by all commission kinds at once rather than silently expanding the scope of a single-field update instruction.

### Proof of Concept
The repository's own unit test demonstrates the issue end-to-end: [6](#0-5) 
1. Construct a max-sized `VoteStateV3` vote account (`v3`) with `node_pubkey = v3_node_pubkey`, serialize it as `VoteStateVersions::V3` into an account sized for V4.
2. Call `update_commission_collector(..., CommissionKind::InflationRewards, ...)` with a new collector account, signed by the V3 account's authorized withdrawer.
3. Observe: `inflation_rewards_collector` is set to the caller-provided `new_collector` (expected), but `block_revenue_collector` — which the caller never touched — is now `v3_node_pubkey` (the validator identity), a value fabricated by `try_convert_to_vote_state_v4`'s default and written to the account with no explicit authorization instruction for that field.

/// Update the vote account's commission collector (SIMD-0232).
pub fn update_commission_collector<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    new_collector: NewCommissionCollector,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    rent: &Rent,
) -> Result<(), InstructionError> {
    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let new_collector_key = new_collector.validate_and_resolve_key(vote_account, rent)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_collector(new_collector_key);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_collector(new_collector_key);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

            node_pubkey: state.node_pubkey,
            authorized_withdrawer: state.authorized_withdrawer,
            inflation_rewards_collector: *vote_pubkey,
