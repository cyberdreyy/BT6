### Title
JWT Replay Guard in HTTP Trigger `Authorize()` Has a Check-Then-Act Race Allowing Token Reuse - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

### Summary
`WorkflowMetadataHandler.Authorize()` calls `h.jwtCache.isReplay(claims.ID)` and, only after several unrelated checks succeed, calls `h.jwtCache.recordUsage(claims.ID)`. Because these are two separate calls into the cache rather than one atomic check-and-record operation, concurrent requests carrying the same JWT (same `jti`) can both pass the replay check before either records usage, similar to how the reported `TributeAccrual` bug let two claimants both read a stale, unincremented total and both succeed in claiming amounts that summed to more than intended.

### Finding Description
`Authorize` in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go:80-108` performs: [1](#0-0) 

The sequence is: verify JWT → `h.jwtCache.isReplay(claims.ID)` → look up workflow authorized keys → verify signer is authorized → `h.jwtCache.recordUsage(claims.ID)`. The "check" (`isReplay`) and the "record" (`recordUsage`) are two distinct calls with unrelated work (map lookups, signer verification) in between. If the underlying `jwtReplayCache` only takes its lock independently inside each of `isReplay` and `recordUsage` (rather than the whole check-and-record sequence being a single atomic critical section, as is correctly done in the analogous `RequestReplayGuard.CheckAndRecord` used elsewhere in the vault authorizer at `core/capabilities/vault/request_replay_guard.go:35-47`), two goroutines processing the same JWT concurrently can both observe "not yet replayed" and both proceed to be authorized and have their trigger requests dispatched to the DON before either marks the `jti` as used.

This mirrors the external report's root cause exactly: a shared piece of state meant to gate/limit access (conviction score total / JWT-used-marker) is read and then separately updated, and the window between read and update is exploitable by whichever caller races through it, defeating the single-use guarantee that the JWT replay protection is supposed to provide.

By contrast, the vault package's `RequestReplayGuard.CheckAndRecord` correctly combines the check and the record into one lock-held operation, showing the project is aware of this exact race class and mitigates it in one place but not (verifiably, without further inspection) in the HTTP trigger metadata handler's `jwtReplayCache`.

### Impact Explanation
If `jwtReplayCache`'s internal locking does not span the full check-then-record window (only verifiable by reading the unlisted `isReplay`/`recordUsage` bodies, which I could not fully confirm from the index), an unprivileged workflow node/client could replay a single JWT to trigger the same workflow execution twice concurrently, defeating the intended single-use/anti-replay guarantee documented in the handler's own comment ("JWT token has already been used. Please generate a new one with new id (jti)"). This could lead to duplicate/unintended workflow executions (unauthorized job run) from a single authorized trigger token.

### Likelihood Explanation
Exploitability depends on the internal implementation of `jwtReplayCache.isReplay`/`recordUsage`, which I was not able to fully view in this session due to index limitations. If the check and record use independent short-lived locks rather than a single held lock across the whole `Authorize` decision, the race is trivially triggerable by sending two copies of the same signed JWT trigger request in parallel — something any client holding a valid (but single-use) trigger JWT can do.

### Recommendation
Refactor `WorkflowMetadataHandler.Authorize` (or `jwtReplayCache`) to expose a single atomic `CheckAndRecord`-style method — mirroring `vault.RequestReplayGuard.CheckAndRecord` — that holds one lock across the entire "is this `jti` already used?" check and the "mark it used" write, with the workflow/signer-authorization checks performed either before entering that atomic section (using a value not usable for bypass) or moved so no unlocked window exists between check and record.

### Proof of Concept
Conceptual PoC (needs verification against actual `jwtReplayCache` lock granularity, which could not be confirmed here):
1. Obtain one valid, signed, single-use JWT trigger token for a workflow.
2. Fire two (or more) concurrent HTTP trigger requests to the gateway using the identical token/`jti`.
3. If `isReplay` and `recordUsage` are independently locked (not combined), both goroutines can pass `isReplay` == false before either calls `recordUsage`, resulting in both requests being authorized and dispatched — a JWT replay bypass.

Note: due to index size limits, I could not retrieve the full body of `jwtReplayCache.isReplay`/`recordUsage` in `workflow_metadata_handler.go` to definitively confirm whether the lock is held across both calls or independently per call. func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
