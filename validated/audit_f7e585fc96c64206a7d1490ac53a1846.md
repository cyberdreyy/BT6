### Title
Removed multisig members' stale confirmations still count toward `num_confirmations`, allowing request execution below live-member threshold - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
Both the `multisig` and `multisig2` contracts allow a request to execute once `confirmations.len() + 1 >= num_confirmations`. When a member/key is removed via `DeleteMember`/`DeleteKey`, the contract only purges *requests that member originally created* — it never purges confirmations that member previously cast on requests *created by other members*. Those stale confirmations remain in the `confirmations` set and continue to count toward the threshold, letting a request execute with fewer live, currently-authorized confirmers than `num_confirmations` requires.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member()` only cleans up requests filtered by `r.member == member` (requests the removed member authored): [1](#0-0) 

It never scans the `confirmations: LookupMap<RequestId, HashSet<String>>` map for entries containing the removed member's identifier on requests created by *other* members. The threshold check in `confirm()` blindly trusts the stored confirmation count: [2](#0-1) 

The same pattern exists in the original `multisig` contract: `DeleteKey` only removes requests where `r.signer_pk == pk`, leaving that key's confirmations on other members' requests intact: [3](#0-2) [4](#0-3) 

This is the same bug class as the reported `_vote()` issue: an entity (`gauge`/multisig member) that has become "dead" (removed) still has its prior contribution (`claimable`/confirmation) counted toward an aggregate (`totalWeight`/`num_confirmations` threshold) that only "live" entities should influence.

The binding that should hold is:
```
live_confirmations(request) == confirmations.get(request).filter(|m| members.contains(m)).count()
```
but the contract instead uses the raw stored `confirmations.len()`, which can include confirmers no longer in `self.members`.

### Impact Explanation
This breaks the multisig's core authorization guarantee — that any executed request (including `Transfer`, `AddKey`/`AddMember` granting full access, or `DeployContract`) has been approved by at least `num_confirmations` *currently authorized* members. A request can be executed with fewer live approvals than the configured threshold, i.e. "a multisig request executed below threshold," which the rules classify as Critical impact (funds moved, or an access key/member added, without sufficient live authorization).

### Likelihood Explanation
Exploitability requires no privileged access beyond normal multisig operation: any sequence where (a) a request is partially confirmed, (b) a confirming member is later removed (a routine multisig operation, e.g. key rotation or offboarding), and (c) the request is left pending and later confirmed by remaining members, will trigger the flaw. This is a plausible, even likely, operational sequence for any active multisig with member turnover — not a contrived edge case.

### Recommendation
When removing a member/key (`delete_member` in `multisig2`, `DeleteKey` in `multisig`), iterate all pending requests' `confirmations` sets and strip any confirmation belonging to the removed member/key, not just requests they authored. Alternatively, validate confirmer membership at `confirm()`/execution time by filtering the confirmations set against the current `members`/valid keys before comparing to `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. `A` calls `add_request(R)` where `R.actions = [Transfer{amount}]` (or `AddMember{attacker}`).
3. `B` calls `confirm(R)` → `confirmations[R] = {B}` (1 < 2, pending).
4. `A` and `C` submit and confirm a `DeleteMember{member: B}` request (2 confirmations, reaches threshold, executes) — `members` becomes `[A, C]`; since `B` authored no requests, `delete_member` does not touch `confirmations[R]`, which still equals `{B}`.
5. `C` calls `confirm(R)` → `confirmations[R].len() + 1 = 2 >= num_confirmations(2)` → `execute_request(R)` runs, executing the transfer/AddMember with only `C` as a genuinely live confirmer, despite the contract requiring 2 live confirmations. [5](#0-4) [1](#0-0)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);

        );

            confirmations.insert(member.to_string());

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
