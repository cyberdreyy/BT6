### Title
v1 SortitionState's `DuplicateBlockFound` guard checks only global acceptance, letting a v1 signer equivocate on a locally-accepted tenure-start block - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` in `v1.rs` guards against re-signing a tenure-start block by calling `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`, which only returns `Some` once a block has reached network-wide (threshold) acceptance [1](#0-0) . `GlobalStateView::validate_tenure_change_payload` in `v2.rs` performs the same guard with `signer_db.get_last_signed_block(...)`, which the code explicitly documents as covering blocks the signer has "signed (locally or globally accepted)" [2](#0-1) . A v1-configured signer that has already locally signed block A for tenure T (but A has not yet reached global acceptance) will not detect that fact when a second tenure-change block B for the same T is proposed, and will proceed to sign B as well.

### Finding Description
The intended safety property is: a signer must never sign two different tenure-start blocks for the same tenure (its own local equivocation guard). Both `v1.rs` and `v2.rs` implement this guard as the last check inside `validate_tenure_change_payload`, right before returning `Ok(())` and letting the caller (`check_proposal` → `submit_block_for_validation` → sign) proceed.

- v1 (`stacks-signer/src/chainstate/v1.rs:505-518`) queries `get_last_globally_accepted_block(consensus_hash)`. This function only returns a block once it has been *globally* accepted (i.e., threshold-signed across the whole signer set), not merely locally accepted/signed by this signer itself.
- v2 (`stacks-signer/src/chainstate/v2.rs:344-357`) queries `get_last_signed_block(consensus_hash)` instead, and the surrounding comment states this was deliberately changed so that "blocks we have signed (locally or globally accepted)" block a competing tenure-start proposal [3](#0-2) . This is corroborated by `SortitionData::get_tenure_last_block_info`, which explicitly reads `get_last_signed_block` and reasons about `signed_self`/`signed_group` timestamps as the two ways a block can be "signed" [4](#0-3) .

Exploit flow for a v1-configured signer:
1. Attacker (single miner slot) wins a sortition, crafts tenure-start block A for tenure T, and proposes it via `handle_block_proposal`. The v1 signer's `validate_tenure_change_payload` finds no globally accepted block yet (`get_last_globally_accepted_block(T) == None`), passes, and the signer proceeds to submit and sign A. A is now recorded in the signer's own DB as locally signed but has not (yet) reached global acceptance (e.g., other signers are slow, or the reward set is mixed-version so consensus stalls).
2. The same attacker crafts a second, distinct tenure-start block B also carrying a `TenureChangePayload` for the same tenure T (same `consensus_hash`), and gossips it to the same v1 signer.
3. `validate_tenure_change_payload` runs again: `get_last_globally_accepted_block(T)` is still `None` (A never reached global acceptance), so the duplicate check does not fire, and the function returns `Ok(())`.
4. No other check in `check_proposal`/`validate_tenure_change_payload` inspects the signer's *own* prior signature within tenure T for this path (`check_tenure_change_confirms_parent` only checks the *parent* tenure's last block, not the current tenure) [5](#0-4) .
5. The v1 signer signs B, having previously signed A for the same tenure T — an equivocation the v2 logic would have caught via `get_last_signed_block`.

### Impact Explanation
This breaks the "at most one signed tenure-start block per tenure" equivocation guard for any signer running the v1 `SortitionState`. If enough v1 signers exhibit this behavior (or if v1 signers' extra signatures combine with signatures already gathered for A from other signers, v1 or v2, before global acceptance propagated), two conflicting tenure-start blocks (A and B) for the same tenure can each accumulate valid signer signatures, i.e., a signer signing a conflicting block — the Critical chain-safety category defined in scope. This is repeatable by the same attacker for every tenure in which they win a sortition slot, as long as a mixed-version signer set with delayed global-acceptance propagation exists.

### Likelihood Explanation
Preconditions: (1) the signer set (or at least the target signer) is running v1 `SortitionState` (`SortitionStateVersion::V1`, chosen when the signer's protocol version is below `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`) [6](#0-5) ; (2) block A has been locally signed by that v1 signer but has not yet reached global acceptance (a normal, non-adversarial timing window, e.g., during slow gossip/threshold aggregation); (3) the attacker can win one sortition (or otherwise obtain a valid miner slot) and gossip two distinct BlockProposals for the same tenure to the target v1 signer — well within the "one miner slot plus gossip" attacker model. No majority-signer collusion, no auth_token, and no local host access is needed.

### Recommendation
In `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload`, replace the `get_last_globally_accepted_block` call with `get_last_signed_block` (mirroring the v2 fix), so that a signer's own prior local signature within the same tenure is also treated as a duplicate/equivocation trigger, regardless of whether global acceptance has been reached yet.

### Proof of Concept
Rust test plan (to be placed alongside `stacks-signer/src/chainstate/tests/v2.rs`'s `check_tenure_change_rejects_when_locally_accepted_block_exists`, mirrored for v1):
```rust
#[test]
fn v1_tenure_change_should_reject_when_locally_accepted_block_exists() {
    // Setup: SortitionStateV1-based SortitionsView, empty SignerDb.
    // 1. Insert block A into signer_db as locally-signed (signed_self = Some(ts)),
    //    but NOT globally accepted (state != GloballyAccepted, signed_group = None),
    //    for tenure consensus_hash `ch`.
    // 2. Build block B: a distinct NakamotoBlock with a TenureChangePayload whose
    //    header.consensus_hash == ch (same tenure), different content/hash than A.
    // 3. Call sortitions_view.validate_tenure_change_payload(&proposed_by, &tenure_change, &B, &mut signer_db, &client).
    // 4. EXPECTED (matching v2's stricter behavior): Err(RejectReason::DuplicateBlockFound).
    // ACTUAL (v1 bug): Ok(()) is returned because get_last_globally_accepted_block(ch) == None,
    //    proving the guard is bypassable while A is only locally accepted.
    assert!(matches!(result, Err(RejectReason::DuplicateBlockFound)), "v1 must reject duplicate tenure-start block even when the earlier block is only locally accepted, matching v2 semantics");
}
```
This test currently fails against the code in `stacks-signer/src/chainstate/v1.rs:505-518`, confirming the guard gap; the equivalent v2 test using `get_last_signed_block` passes, demonstrating the asymmetry.

    pub fn get_tenure_last_block_info(
        consensus_hash: &ConsensusHash,
        signer_db: &SignerDb,
        tenure_last_block_proposal_timeout: Duration,
    ) -> Result<Option<BlockInfo>, ClientError> {
        // Get the last signed block in the tenure
        let last_signed_block = signer_db
            .get_last_signed_block(consensus_hash)
            .map_err(|e| ClientError::InvalidResponse(e.to_string()))?;

        let Some(block_info) = last_signed_block else {
            return Ok(None);
        };

        // `approved_time` may hold the pre-commit time; use the actual signature time.
        let Some(signed_over_time) = block_info.signed_self.max(block_info.signed_group) else {
            return Ok(None);
        };
