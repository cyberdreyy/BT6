### Title
Missing role guard on `GET /v2/external_initiators` allows any authenticated user (including view-role) to list `AccessKey`/`OutgoingToken` for all External Initiators - ([File: core/web/router.go], [File: core/web/external_initiators_controller.go])

### Summary
`router.go:264` registers `authv2.GET("/external_initiators", paginatedRequest(eia.Index))` with only the base `auth.Authenticate` middleware and no `auth.RequiresEditRole`/`RequiresAdminRole` wrapper, unlike `Create`/`Destroy` on the same resource. As a result, any authenticated principal — including a `view`-role user or an EI-derived `run`-role session — can call `ExternalInitiatorsController.Index` and receive every external initiator's `AccessKey` and `OutgoingToken`.

### Finding Description
`ExternalInitiatorsController.Index` (`core/web/external_initiators_controller.go:50-59`) fetches all external initiators via `BridgeORM().ExternalInitiators` and serializes them with `presenters.NewExternalInitiatorResource`. The `ExternalInitiatorResource` type (`core/web/presenters/external_initiators.go:57-77`) includes `Name`, `URL`, `AccessKey`, `OutgoingToken`, `CreatedAt`, `UpdatedAt`. [1](#0-0) 

Note: `OutgoingSecret` and `HashedSecret` are **not** part of this resource type (they only appear in `ExternalInitiatorAuthentication`, returned solely at `Create` time), so those two specific fields are not disclosed by `Index` as the question's proof idea assumes. [2](#0-1) 

However, the route itself has no role guard at all, in contrast to its sibling endpoints on the same resource: [3](#0-2) 

`auth.Authenticate` only verifies the caller has *some* valid session/token and sets the user in context; it performs no role check. [4](#0-3) 

Role checks are only enforced by explicit wrappers (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole`), which compare `user.Role` against `UserRoleView`/`UserRoleRun`/`UserRoleAdmin`. [5](#0-4) 

Since `Index` is not wrapped by any of these, a `view`-role user's session (the lowest privilege tier) passes `auth.Authenticate` and reaches `Index` unimpeded, returning every EI's `AccessKey` and `OutgoingToken` in the JSON:API response. The existing test confirms both fields are populated in the response body. [6](#0-5) 

### Impact Explanation
This is a cross-privilege information disclosure: a low-privilege (`view`-role) authenticated user can enumerate `AccessKey` and `OutgoingToken` for all external initiators configured on the node, which the operator likely intended to be restricted to edit/admin roles (as enforced on `Create`/`Destroy`). `AccessKey` is the identifier an EI uses to authenticate inbound requests to the node, and `OutgoingToken` is one half of the credential pair (`OutgoingToken`/`OutgoingSecret`) the node is meant to use when calling back external services. Disclosure of `AccessKey`/`OutgoingToken` alone does not achieve full impersonation (the paired secrets `HashedSecret`/`OutgoingSecret` are correctly excluded from this presenter), so the impact is scoped to partial credential/metadata disclosure rather than full request forgery.

### Likelihood Explanation
Highly likely to be reachable: it requires only a valid `view`-role session or API token — the lowest privilege level supported by the node — with no special preconditions. The route is always registered regardless of configuration.

### Recommendation
Wrap the `Index` route with an explicit role guard consistent with `Create`/`Destroy`, e.g. `authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))`, or at minimum `RequiresRunRole` if broader read access is intended, in `core/web/router.go:264`.

### Proof of Concept
1. In `core/web/external_initiators_controller_test.go`, add a test that creates an app, seeds a user/API token with `clsessions.UserRoleView`, and an admin creates one `ExternalInitiator` via `borm.CreateExternalInitiator`.
2. Authenticate the HTTP client as the view-role user (`app.NewHTTPClient` with view-role token, mirroring patterns in `sessions_controller_test.go`/`user_controller_test.go` for role-based clients).
3. Call `client.Get("/v2/external_initiators")`.
4. Assert `http.StatusOK` (not `401`/`403`) is returned and that `AccessKey`/`OutgoingToken` fields are present and non-empty in the parsed `presenters.ExternalInitiatorResource` list — demonstrating the missing role guard, while separately asserting `OutgoingSecret`/`HashedSecret` remain absent from the JSON (confirming those specific fields are already safe).

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
