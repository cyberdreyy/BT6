### Title
ERC4626 liquidity shortage in `ProgrammableBorrower` indefinitely blocks epoch settlement and withdrawals - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
A public withdrawal from the programmable borrower’s configured ERC4626 vault can leave the vault economically solvent but temporarily illiquid. When the manager later calls `IdleCDOEpochVariant.stopEpoch`, `ProgrammableBorrower.onStopEpoch` attempts to withdraw the entire cash shortfall in one call. If the vault reverts because insufficient liquidity is currently withdrawable, `onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable`, preventing `stopEpoch` from completing and keeping withdrawal receipts frozen until liquidity returns. [1](#0-0) 

### Finding Description
`IdleCDOEpochVariant._stopEpoch` computes both the epoch amount due and pending withdrawal funding, then calls `IProgrammableBorrower.onStopEpoch`. [2](#0-1) 

`onStopEpoch` compares the required cash amount with the borrower’s local balance. For a shortfall, it checks that the shortfall is no greater than `_currentVaultAssets()`, which is an accounting valuation of the borrower’s vault shares rather than the amount currently withdrawable. It then calls `vault.withdraw(shortfall, address(this), address(this))`. [3](#0-2) 

An ERC4626 vault can report share value exceeding its currently available liquidity. In that case, the solvency check passes while the actual `withdraw` reverts. The catch block deliberately converts that liquidity failure into `StopEpochVaultLiquidityUnavailable`. [4](#0-3) 

Because this revert occurs before `IdleCDOEpochVariant` reaches its borrower-transfer `try/catch`, the normal borrower-default path is not entered. The epoch remains running even after `epochEndDate`, so users cannot make normal withdrawal requests or claim receipts funded by that epoch’s settlement. [5](#0-4) 

The issue is analogous to a failing strategy blocking a withdrawal queue: one external liquidity source can prevent settlement for every tranche holder even though other accounting indicates that the position is covered.

### Impact Explanation
An unprivileged participant in the configured ERC4626 vault can consume the vault’s readily withdrawable liquidity during a running epoch. If the remaining liquidity is below the `stopEpoch` shortfall while `convertToAssets` still values the borrower’s shares above that shortfall, every subsequent `stopEpoch` call reverts.

The frozen amount is at least:

```solidity
amountToPullFromBorrower + pendingWithdraws
```

This includes pending withdrawal receipts and, depending on accounting mode, epoch interest or recalled principal. The freeze persists until the external vault regains enough withdrawable liquidity. There is no alternate vault withdrawal path, redemption queue, or fallback in `onStopEpoch`, and `setVault` cannot move the position while the borrower still owns vault shares. [6](#0-5) 

### Likelihood Explanation
The attacker only needs to be an ordinary shareholder/user of the configured ERC4626 vault and make normal withdrawals while the credit epoch is running. No privileged credit-vault role is required.

Execution depends on the integrated vault having less immediately withdrawable liquidity than its reported asset value. This is possible for vaults that allocate deposits into external markets or otherwise expose redemption limits. The failure is temporary rather than permanent if the vault later replenishes liquidity, but the attacker can repeatedly withdraw newly available liquidity to extend the freeze.

The existing guard correctly distinguishes economic insufficiency from liquidity failure, but it does not prevent that liquidity failure from blocking the entire epoch transition. [7](#0-6) 

### Recommendation
Add an explicit liquidity-shortage settlement path instead of allowing the external vault revert to leave the epoch indefinitely running.

A robust design should:

1. Query `vault.maxWithdraw(address(this))` before attempting the withdrawal.
2. Withdraw only the currently available amount when doing so cannot violate accounting.
3. Record the uncovered shortfall in a dedicated retryable state.
4. Allow a subsequent settlement call to complete the epoch once liquidity returns.
5. Alternatively, provide a bounded liquidity grace period after which the uncovered amount can enter an explicit loss/default path rather than remaining in an undefined running state.

At minimum, avoid requiring one monolithic `vault.withdraw(shortfall)` call to succeed before the epoch can transition.

### Proof of Concept
The following Foundry fork test uses the repository’s programmable-borrower setup with a real ERC4626 vault. `attacker` is an unprivileged vault shareholder that withdraws enough liquidity after the CDO starts its epoch.

```solidity
function testVaultLiquidityShortageBlocksStopEpoch() external {
    uint256 poolDeposit = 10_000 * oneScale;
    uint256 attackerSeed = 20_000 * oneScale;

    address attacker = makeAddr("vault-user");

    // Attacker is an ordinary ERC4626 participant and obtains shares before
    // the credit pool parks its funds in the same vault.
    deal(USDC, attacker, attackerSeed, true);
    vm.startPrank(attacker);
    underlying.approve(address(morphoVault), attackerSeed);
    morphoVault.deposit(attackerSeed, attacker);
    vm.stopPrank();

    // Honest user deposits into the credit pool.
    idleCDO.depositAA(poolDeposit);

    // Manager starts the epoch; ProgrammableBorrower deposits its idle cash
    // into the configured ERC4626 vault.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // During the running epoch, the attacker performs a normal vault exit.
    // For a vault whose accounting assets exceed immediately withdrawable
    // liquidity, this consumes the liquidity needed by onStopEpoch.
    uint256 attackerAssets = morphoVault.maxWithdraw(attacker);
    vm.prank(attacker);
    morphoVault.withdraw(attackerAssets, attacker, attacker);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // The borrower share position still economically covers the shortfall,
    // so onStopEpoch attempts vault.withdraw(shortfall). The vault's
    // liquidity check reverts, which becomes StopEpochVaultLiquidityUnavailable
    // and leaves the epoch running.
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());

    // The same settlement can be retried, but it remains unavailable while
    // the ERC4626 vault lacks withdrawable liquidity.
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);
}
```

The relevant production path is `IdleCDOEpochVariant._stopEpoch` → `ProgrammableBorrower.onStopEpoch` → `vault.withdraw`. The first revert prevents `collectWithdrawFunds`, `_updateAccounting`, `isEpochRunning = false`, and the re-enabling of withdrawal requests from executing. [8](#0-7)
