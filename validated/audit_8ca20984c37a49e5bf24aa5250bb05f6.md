### Title
Attacker-triggerable `panic!` in signer-db write paths turns any block-response/validation event into a process-killing DoS on the signer's single-threaded event loop - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`insert_block()` failures are converted to a `panic!` via `handle_insert_block_error`, and this helper is invoked on nearly every attacker-influenced message-handling path in the v0 signer event loop, mirroring the free5GC bug class: an unauthenticated/low-trust-boundary input reaches a validation/persistence step whose only error handling is "abort the whole process."

### Finding Description
`SignerDb::insert_block` writes several `u64` fields into SQLite via `u64_to_sql`, which fails if a value exceeds `i64::MAX`: [1](#0-0) 

The caller-side pattern used throughout `stacks-signer/src/v0/signer.rs` is:
```rust
self.signer_db.insert_block(&block_info).unwrap_or_else(|e| self.handle_insert_block_error(e));
```
and `handle_insert_block_error` itself calls `panic!`: [2](#0-1) 

This exact call is reached from, among others:
- `handle_block_proposal` (miner-supplied `BlockProposal`, gossip-reachable, no signer key required to trigger dispatch since it is a `MinerMessages` event): [3](#0-2) 
- `handle_block_validate_ok` / `handle_block_validate_reject` (node validation responses, but block content originates from the miner's proposal): [4](#0-3) 
- `handle_block_pre_commit`, `handle_block_signature` (both reachable from other signers' gossip messages, and self-triggered on the local signer's own path): [5](#0-4) 

There is a static guard, `check_static_valid_block`, meant to prevent exactly the overflow case that would make `u64_to_sql` fail: [6](#0-5) 
It is checked before some but not all `insert_block` calls, and even where checked, it only bounds `chain_length`, `burn_block_height`, and `reward_cycle` — not every field passed into `params![...]` in `insert_block` (e.g. `proposed_time`, `validation_time_ms`, `approved_time` are not validated by `check_static_valid_block` at all, yet several are written as plain values, not via `u64_to_sql`, so the actual failure surface for those specific columns is unclear from the code I could inspect).

Unlike the free5GC report — where `Fatalf` is unambiguously `os.Exit(1)` — a Rust `panic!` in a non-main thread ordinarily just unwinds that thread unless `panic = "abort"` is configured or the thread is the process's only worker. I was **not able to verify** from the available code slices whether the v0 signer's event loop runs on the main thread with no `catch_unwind` wrapper (which would make this a full process-kill, closely matching the CVE's Availability impact) or whether a supervising thread would restart it (which would make this "only" a state-machine wedge until restart). This distinction matters for severity and I could not confirm it with the indexed content — the code that drives `process_event` from `runloop.rs`/`main.rs` was not returned in the search results.

### Impact Explanation
If the panic is not caught, this is a High/Critical liveness break: "a signer wedged into never signing valid blocks" (or an outright process death), matching the plan's High-impact bucket, because the panic path is reachable from block-content the *miner* controls (chain_length, burn_block_height, reward_cycle, timestamps carried in `BlockInfo`) without needing any other signer's key, mirroring the free5GC advisory's "single unauthenticated request kills the whole process" pattern. Even if some deployment catches the panic per-thread, an attacker (miner or another signer) can repeatedly resend a proposal/response that trips `insert_block` to keep the signer stuck rejecting/failing every subsequent event tied to that path, since `process_event`'s per-tick housekeeping (`check_submitted_block_proposal`, `check_pending_block_validations`) itself calls into the same insertion path.

### Likelihood Explanation
I could not confirm a concrete, always-reachable overflow value that survives `check_static_valid_block` for every `insert_block` call site — some call sites (e.g. inside `handle_block_proposal`) run after the guard, others (e.g. `handle_block_validate_ok`'s first `insert_block` call at line 1928-1930) run *before* `check_static_valid_block` is invoked again, but the `block_info` there was already validated at proposal time, so a fresh overflow is unlikely on that specific path without also finding a state where `block_info.block.header.chain_length`/`burn_block_height`/`reward_cycle` diverges from the value checked earlier. Because I could not identify a field bypassing the guard with certainty from the visible code, I can't assert this is concretely exploitable with high confidence — it requires further code-reading (full `signerdb.rs`, `u64_to_sql`, and the fields written without going through it) that exceeded what the index surfaced.

### Recommendation
- Replace every `unwrap_or_else(|e| self.handle_insert_block_error(e))` / `panic!` pair around `signer_db.insert_block` with a warn-and-return (or warn-and-retry) path, consistent with how most other DB write failures in the same file are already handled (e.g. `add_pending_block_pre_commit_response`, `insert_pending_block_validation`).
- Extend `check_static_valid_block` (or add an equivalent check in `insert_block` itself) to bound *every* `u64` field it serializes, not just `chain_length`, `burn_block_height`, and `reward_cycle`.
- Audit whether the v0 signer's `process_event` loop runs with a panic boundary (`catch_unwind` or a supervising restart thread); if not, treat any of these `panic!` sites as a full-process DoS.

### Proof of Concept
I could not construct a concrete end-to-end PoC (a specific attacker-crafted `BlockProposal`/`BlockResponse` byte sequence that reaches an `insert_block` failure) with the information retrieved, because:
1. The exact bypass of `check_static_valid_block` for a field written by `insert_block` (e.g. via `u64_to_sql` overflow) was not confirmed for a call site that runs without that guard having already run on the same data.
2. Whether a `panic!` here kills the whole signer process (vs. just the handling thread) could not be verified from the fragments retrieved (the signer's threading/panic-handling setup in `runloop.rs`/`main.rs` was not available).

Given these two unresolved points, I'm not confident enough in a fully "concrete" exploit chain to assert a definitive vulnerability per the strict validation bar requested. If you want, a follow-up pass reading `stacks-signer/src/signerdb.rs` in full (the `u64_to_sql` helper and all `insert_block` parameter types) and `stacks-signer/src/runloop.rs`/`main.rs` (panic-handling around `process_event`) would let me confirm or refute this analog with certainty.

```rust
    /// Perform static checks on the BlockInfo and determine if it is syntactically valid.
    /// Specifically, all integer values must be less than i64::MAX, since these values get stored
    /// in the sqlite DB via u64_to_sql()
    pub fn check_static_valid_block(&self) -> bool {
        let max_val = u64::try_from(i64::MAX).expect("infallible");
        if self.block.header.chain_length >= max_val {
            return false;
        }
        if self.burn_block_height >= max_val {
            return false;
        }
        if self.reward_cycle >= max_val {
            return false;
        }
        true
    }
```
