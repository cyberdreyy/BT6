### Title
Legacy gateway user messages are not deduplicated by MessageId/Sender, allowing replay of a captured signed message to trigger duplicate DON execution - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` in the web-api-capabilities handler accepts any structurally-valid, signed `api.Message` whose `payload.Timestamp` is within `MaxAllowedMessageAgeSec`, and unconditionally forwards it to every DON member node. It never checks whether the exact same `MessageId`/`Sender` pair (or signature) has already been processed, so a captured signed message can be resent to the gateway's `/user` HTTP endpoint multiple times within the allowed age window, causing the DON to execute the same trigger repeatedly.

### Finding Description
The reachable path is: gateway HTTP endpoint → `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-292`) → for legacy (DonId-bearing) requests, `msg.Validate()` (`core/services/gateway/api/message.go:54-88`) is called, which only checks structural fields and signature well-formedness, then extracts `Sender` from the signature — it does **not** check for previously-seen `MessageId`/`Sender` combinations.

The request is then routed to `handler.HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`). The only anti-replay control present is the age check: [1](#0-0) 
This only rejects messages older than `MaxAllowedMessageAgeSec`; it does not prevent a **still-fresh** captured message from being replayed.

After the age/method checks pass, the handler stores the callback keyed by `MessageId` and fans the message out to every DON node with no existence/duplicate check: [2](#0-1) 
`h.savedCallbacks[msg.Body.MessageId] = ...` simply **overwrites** any prior entry rather than rejecting it, and once the original response is delivered the entry is deleted from the map (freeing the `MessageId` for reuse). Contrast this with sibling handlers that explicitly enforce request uniqueness: `confidentialrelay` handler rejects duplicates with `"request ID already exists"` and vault handler rejects with `"request was already authorized previously"`/`"in-flight request"`: [3](#0-2) [4](#0-3) 
No equivalent check exists in `HandleLegacyUserMessage`, so a byte-for-byte replay of a previously captured signed `Message` (same `MessageId`, `Sender`, `Signature`, `Timestamp`) — sent again while still inside `MaxAllowedMessageAgeSec` — passes `Validate()`, passes the staleness check, and is forwarded to all DON nodes exactly as a fresh request would be, triggering a second execution of the same web-API trigger/workflow.

The `connectionmanager.go`/`network/handshake.go` timestamp-tolerance checks referenced in the question relate to node-to-gateway websocket handshake authentication (`AuthTimestampToleranceSec`), which is a separate, unrelated mechanism from the per-message anti-replay logic; that handshake path is not where the vulnerability lives, but the underlying pattern (using a timestamp/age window without a nonce/uniqueness tracking) recurs in the user-message path examined here.

### Impact Explanation
An attacker with only network visibility into a previously captured signed gateway message (no private key, no credential) can cause duplicate DON workflow/trigger execution attributable to the original subscriber. Depending on downstream billing/metering tied to trigger executions, this results in unauthorized resource consumption and quota charges against another user's subscription, and duplicate side effects (e.g., duplicate external HTTP calls, duplicate on-chain writes if the workflow performs them) — matching the "unauthorized action on another user's job/subscription" impact class.

### Likelihood Explanation
The only precondition is network reachability to the gateway's public user endpoint plus possession of one previously observed valid signed message (attacker does not need the signing key). The replay window is bounded by `MaxAllowedMessageAgeSec` (e.g., configured as 1000 seconds in default gateway job configs), which is generous enough to make repeated replay trivially feasible and repeatable any number of times within that window.

### Recommendation
Track processed `(MessageId, Sender)` (or full message hash) persistently for at least `MaxAllowedMessageAgeSec` after completion, not just while the callback is in-flight, and reject any duplicate before forwarding to DON nodes — following the same pattern already implemented in the vault and confidentialrelay handlers (`"request ID already exists"` / `"request was already authorized previously"`).

### Proof of Concept
Handler-level Go test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build a valid signed `api.Message` with `Method: MethodWebAPITrigger`, valid `payload.Timestamp` within `MaxAllowedMessageAgeSec`.
2. Call `handler.HandleLegacyUserMessage(ctx, &msg, callback1)`; assert `don.SendToNode` was called once per DON member (e.g., 2 times for 2 members) and the callback eventually resolves successfully (simulate `HandleNodeMessage` response).
3. Immediately replay the exact same `msg` (same `MessageId`, `Signature`, `Timestamp`) via `handler.HandleLegacyUserMessage(ctx, &msg, callback2)`.
4. Assert (current buggy behavior) that `don.SendToNode` is invoked again for every member — i.e., total send count doubles — proving the DON executes the identical request twice instead of the call returning a duplicate/conflict error as vault/confidentialrelay handlers do.
5. Expected fixed behavior: second call should return an error (e.g., `"message already processed"`) and `don.SendToNode` call count should remain unchanged after step 2.
