### Title
Whitelisted factory can whitelist an arbitrary account it did not deploy - (File: whitelist/src/lib.rs)

### Summary
The external report describes an "operator" that is both trusted to attest facts (asset transfer success) and to act as a transacting party, with no binding enforced between the two roles. The analogous binding in this repository is between the `whitelist` contract's trust in a `factory` and the actual staking-pool code/arguments that trust was supposed to cover. `WhitelistContract::add_staking_pool` only checks that the caller is a whitelisted factory; it never verifies that the `staking_pool_account_id` argument corresponds to an account the factory actually deployed with the vetted `staking_pool.wasm` code.

### Finding Description
`add_staking_pool` in `whitelist/src/lib.rs` enforces only a caller check: [1](#0-0) 
It does not constrain the `staking_pool_account_id` parameter to an account that the calling factory actually created. Meanwhile, `staking-pool-factory/src/lib.rs`'s `create_staking_pool`/`on_staking_pool_create` flow deploys a fixed, vetted `staking_pool.wasm` and then calls `add_staking_pool` with the deterministic account it just created: [2](#0-1) 
The README explicitly states the trust binding that is supposed to hold: whitelisted accounts must "faithfully implement the spec" so that "delegated tokens can not be lost or locked... the lockup contract should be able to recover delegated tokens back to the lockup from a staking pool": [3](#0-2) 
However, nothing in `add_staking_pool` cross-checks that binding — the whitelist trusts *any* account ID a whitelisted factory submits, with no code-hash or provenance check. If a factory account (once approved and whitelisted by the foundation) is compromised, buggy, or behaves maliciously — the same "trusted role misuses its granted power" pattern as the operator in the original report — it can call `add_staking_pool(attacker_account_id)` for an account that never ran `create_staking_pool` and does not run the vetted staking-pool code at all.

Downstream, `lockup` contracts rely solely on `is_whitelisted` before delegating NEAR: [4](#0-3) 
Once `attacker_account_id` is whitelisted, any lockup owner selecting it as a staking pool and depositing/staking funds sends real NEAR to an account whose code was never vetted, breaking the equality "whitelisted account == account running audited staking-pool code that guarantees recoverability of delegated funds."

### Impact Explanation
This matches the "wrongly whitelisted... deployment" Critical impact category directly. Funds delegated by any lockup contract to the illegitimately-whitelisted account can be permanently lost, since the whitelist's only guarantee (spec-compliant, fund-recoverable code) no longer holds for that entry.

### Likelihood Explanation
Requires a whitelisted factory account to misbehave (be malicious or compromised) — this is not an unprivileged attacker starting from zero privilege, but it exactly mirrors the report's core class of bug: a role trusted to act only within a narrow, code-enforced boundary (factory calling `add_staking_pool` immediately after deploying vetted code) has no on-chain enforcement of that boundary, so the boundary is purely a social/off-chain assumption rather than a code-enforced invariant.

### Recommendation
Have the whitelist contract verify provenance before trusting a factory-submitted account — e.g., require the factory to prove (via a promise/callback pattern like `on_staking_pool_create`, or by having the whitelist itself invoke a deploy through the factory) that the account's deployed code hash matches the audited `staking_pool.wasm`, rather than accepting an arbitrary `AccountId` argument from any whitelisted factory.

### Proof of Concept
1. NEAR Foundation whitelists `factory.near` as a factory via `add_factory`.
2. `factory.near` becomes compromised or acts maliciously (analogous to a malicious "operator").
3. Attacker (via the compromised factory) calls `whitelist.add_staking_pool("attacker.near")` directly — bypassing `create_staking_pool` entirely — since `add_staking_pool` only checks `env::predecessor_account_id()` is in `factory_whitelist`, per `whitelist/src/lib.rs:75-88`.
4. `attacker.near` is now whitelisted despite never running `staking_pool.wasm`.
5. Any lockup owner calls `select_staking_pool("attacker.near")`, which succeeds because `is_whitelisted` returns `true` per `lockup/src/owner.rs:12-41`, then deposits and stakes NEAR into `attacker.near`, which can withhold/never return the funds.

```rust
    pub fn add_staking_pool(&mut self, staking_pool_account_id: AccountId) -> bool {
        assert!(
            env::is_valid_account_id(staking_pool_account_id.as_bytes()),
            "The given account ID is invalid"
        );
        // Can only be called by a whitelisted factory or by the foundation.
        if !self
            .factory_whitelist
            .contains(&env::predecessor_account_id())
        {
            self.assert_called_by_foundation();
        }
        self.whitelist.insert(&staking_pool_account_id)
    }
```

```rust
                staking_pool_account_id,
```

```markdown
# Whitelist contract for staking pools

The purpose of this contract is to maintain the whitelist of the staking pool contracts account IDs that are approved
by NEAR Foundation.

In order for the lockup contracts to be able delegate to a staking pool, the staking pool should faithfully implement the spec.
The staking pool should guarantee that the delegated tokens can not be lost or locked, such as the lockup contract should be
able to recover delegated tokens back to the lockup from a staking pool. In order to enforce this, only approved (whitelisted)
accounts of staking pool contracts can receive delegated tokens from lockup contracts.
```

```rust
    pub fn select_staking_pool(&mut self, staking_pool_account_id: AccountId) -> Promise {
        self.assert_owner();
        assert!(
            env::is_valid_account_id(staking_pool_account_id.as_bytes()),
            "The staking pool account ID is invalid"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();

        env::log(
            format!(
                "Selecting staking pool @{}. Going to check whitelist first.",
                staking_pool_account_id
            )
            .as_bytes(),
        );

        ext_whitelist::is_whitelisted(
            staking_pool_account_id.clone(),
            &self.staking_pool_whitelist_account_id,
            NO_DEPOSIT,
            gas::whitelist::IS_WHITELISTED,
        )
        .then(ext_self_owner::on_whitelist_is_whitelisted(
            staking_pool_account_id,
            &env::current_account_id(),
            NO_DEPOSIT,
            gas::owner_callbacks::ON_WHITELIST_IS_WHITELISTED,
        ))
    }
```
