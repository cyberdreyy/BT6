### Title
Loss-adjusted `stopEpoch` haircut is only applied to the user's latest request epoch; older pending receipts in the same haircutted funding round still claim at par, causing insolvency/theft - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary

Analog of CVE-2018-20354 (use-after-free / stale-pointer read): `collectWithdrawFunds` frees the entire `pendingWithdraws` aggregate and records the haircut under a single epoch key (`lossRecoveryPriceByEpoch[epochNumber]`), but `_claimLossAdjustedWithdrawRequest` later "dereferences" that price only through the stale pointer `lastWithdrawRequest[_user]`. Receipts the same user recorded under an earlier epoch — which were haircutted in the same funding round — are then claimed at par through `_claimFundedWithdrawRequest`, paying out more underlying than was ever funded.

### Finding Description

`requestWithdraw` records each request under the *current* epoch: `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and overwrites `lastWithdrawRequest[_user] = currentEpoch`, while `pendingWithdraws += _amount` is a single global aggregate [1](#0-0) . A user can accumulate funded-but-unclaimed receipts across multiple epochs (the code comment explicitly notes both requests wait together).

When `stopEpochWithDuration` underfunds, `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` over the **entire aggregate** `pendingWithdraws` (all users, all epochs), zeroes `pendingWithdraws`, and stores the price under only `lossRecoveryPriceByEpoch[epochNumber]` [2](#0-1) .

On claim, `_claimLossAdjustedWithdrawRequest` looks up the haircut only via `lastWithdrawRequest[_user]` and clears only that epoch's slice via `_clearWithdrawClaimForEpoch` [3](#0-2) . The remaining older-epoch balance in `withdrawsRequests[_user]` then flows into `_claimFundedWithdrawRequest`, which pays it at par (`_transferFundedClaim(_user, amount)` with no haircut) [4](#0-3) .

Existing guards do not stop this: `requestWithdraw` only reverts if the *previous* `lastWithdrawRequest` epoch already has a `lossRecoveryPriceByEpoch` entry [5](#0-4)  — it cannot know a future stopEpoch will haircut the aggregate.

### Impact Explanation

The strategy only received `_amount < pendingBasis` underlying for the whole receipt pool, but users whose receipts span two epochs redeem their older slice at 100% while only the latest-epoch slice takes the haircut. Each such user extracts `(1 - lossRecoveryPrice) * olderReceiptAmount` of unbacked underlying, draining the strategy's funded reserve and leaving later claimants (other users' funded receipts) unpayable — direct theft from other LPs plus solvency break. Loss scales with the haircut severity and the attacker's older-epoch receipt size, which the attacker fully controls.

### Likelihood Explanation

Requires: an unprivileged KYC'd lender makes withdraw requests in two consecutive buffer periods without claiming in between (explicitly supported per the NOTE in `_claimFundedWithdrawRequest`), and the honest manager/borrower subsequently triggers a partial-loss `stopEpochWithDuration` (a normal, intended code path for borrower underpayment). No privileged misbehavior, timing luck, or external manipulation needed; any realized loss epoch creates the discrepancy.

### Recommendation

Attribute the loss haircut per request epoch, not only to the latest: e.g., apply `lossRecoveryPriceByEpoch` to every epoch slice present in the haircutted `pendingBasis` (store per-epoch funded prices, or track a per-user list/set of open request epochs and apply the prevailing loss price to each slice during claim). Alternatively, force users to claim all older funded receipts before opening a new request (extend the existing `NotAllowed` guard to any nonzero prior `withdrawsRequests`/`withdrawsRequestsByEpoch` entry), so `lastWithdrawRequest` is always the only open epoch.

### Proof of Concept

```solidity
// Foundry fork PoC sketch (IdleCreditVault.t.sol harness style)
// Setup: AYS disabled or fixed-APR mode; user = attacker (KYC'd AA holder).

// 1. Attacker deposits and requests withdraw W1 during buffer of epoch E1.
uint256 w1 = cdoEpoch.requestWithdraw(bal / 2, address(AAtranche));
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, apr, expectedFunds); // E1 funded at par

// 2. Attacker does NOT claim; requests W2 during buffer of epoch E2.
uint256 w2 = cdoEpoch.requestWithdraw(bal / 4, address(AAtranche));
// withdrawsRequestsByEpoch[user][E1]=w1, [E2]=w2; lastWithdrawRequest=E2
// pendingWithdraws = w1 + w2 (+ other users)

// 3. Epoch E2 runs; borrower underfunds -> stopEpochWithDuration loss.
//    collectWithdrawFunds receives funded < pendingBasis:
//    lossRecoveryPriceByEpoch[E2] = funded * RECOVERY_FULL / pendingBasis  (e.g. 0.5e18)
//    pendingWithdraws = 0, but strategy only holds `funded` underlying.

// 4. Attacker claims:
cdoEpoch.claimWithdrawRequest();
//  _claimLossAdjustedWithdrawRequest: pays w2 * 0.5  (correct haircut on E2 slice)
//  _claimFundedWithdrawRequest: pays w1 * 1.0         (BUG: E1 slice escapes haircut)

// Expected: attacker receives w1 + w2*0.5 > funded-attributable share (w1+w2)*0.5.
// The excess (1 - price) * w1 is paid from other users' funded receipts ->
// strategy underlyings insufficient; subsequent claimWithdrawRequest by an
// honest user reverts on safeTransfer or pays less than entitled.
```

Key assertion: after the attacker's claim, `underlyingToken.balanceOf(address(creditVault))` is lower than the sum of remaining claim entitlements for other users, demonstrating reserve insolvency caused by the unhaircutted stale-epoch slice.

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
