## Title
Stale confirmations from removed multisig members count toward the execution threshold, allowing requests to execute with fewer than `num_confirmations` live signers — (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm()` tallies a request's approval purely by comparing `confirmations.len()` against `self.num_confirmations` [1](#0-0) . When a member is removed via the `DeleteMember` action, `delete_member()` only purges requests that the *removed member itself created* (`r.member == member`); it never scans other pending requests to strip that member's existing confirmation from their `confirmations` set [2](#0-1) . A removed member's earlier confirmation therefore keeps counting toward the threshold of any request created by someone else, letting that request execute with one fewer live, currently-authorized confirmation than `num_confirmations` actually requires. The identical pattern exists in the original `multisig` contract's `DeleteKey` handler, which only cleans up requests keyed by the deleted signer's own `signer_pk`, not confirmations that signer left on other requests [3](#0-2) .

### Finding Description
The binding that must hold is: `confirmations counted on a request == confirmations from members currently in self.members`. In practice, the contract violates this because:

1. `confirm()` records a confirming member's identity into the `confirmations: LookupMap<RequestId, HashSet<String>>` for a request [4](#0-3) .
2. `delete_member()` is invoked when a `DeleteMember` action is executed (e.g., a legitimate governance action to remove a compromised or departing member) [5](#0-4) .
3. Inside `delete_member()`, the cleanup logic only removes requests where the request's *creator* (`r.member`) equals the member being removed — confirmations that member placed on requests created by *other* members are left untouched [6](#0-5) .
4. When tallying, `confirm()` never re-validates that every entry already in the `confirmations` set is still a member of `self.members` — it simply checks `confirmations.len() as u32 + 1 >= self.num_confirmations` [7](#0-6) .

So a removed member's "ghost" confirmation is treated as equivalent to a live member's confirmation, exactly analogous to the HSG report's stale-threshold problem, except here it's the confirmation set (not the threshold) that goes stale relative to live membership.

### Impact Explanation
This crosses the "multisig request executed below threshold" Critical bucket explicitly listed in scope. Concretely: an outgoing `Transfer` (or `FunctionCall`, `AddKey`, `DeployContract`) request can be executed by the promise pipeline in `execute_request()` [8](#0-7)  using fewer than `num_confirmations` *currently authorized* approvals, because one "slot" is filled by a member who has already been removed. This lets NEAR move out of the multisig-controlled account without the intended number of live signers agreeing, i.e., a move by a party (set of parties) not entitled to authorize it under the current membership.

### Likelihood Explanation
No privileged bypass or malicious deployment is required — it only needs the contract's own, documented member lifecycle to be exercised in the ordinary order: a member confirms a pending request, is later removed for any legitimate reason, and the pending request is then confirmed to completion by the remaining members. Since `add_request`/`confirm` deliberately support long-lived pending requests (bounded only by `active_requests_limit` and `REQUEST_COOLDOWN` for deletion, not automatically expunged when membership changes), this ordering is easily reachable in normal operation and does not depend on ignoring documented initialization or requiring any victim key/social engineering.

### Recommendation
Before tallying in `confirm()` (and ideally also right after any `DeleteMember`/`DeleteKey` execution), filter the stored `confirmations` set to only members currently present in `self.members`, i.e., recompute/prune confirmations against live membership prior to comparing against `num_confirmations` — mirroring the recommended fix of calling a reconciliation step (`reconcileSignerCount()`-equivalent) before the threshold check in the referenced HSG report. Concretely, `delete_member()` should also iterate all pending requests' `confirmations` sets and remove the deleted member's entry, not just requests the member itself created.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `D` calls `add_request_and_confirm` is not required; instead `B` creates request `R` (a `Transfer` to an attacker-controlled account) via `add_request`. `D` calls `confirm(R)` — `confirmations[R] = {D}` (1/3).
3. Separately, the group legitimately removes `D` via a `DeleteMember{member: D}` request that reaches 3 confirmations from `A, B, C` and executes — `delete_member()` runs, but since `R`'s creator is `B` (not `D`), `R` and its confirmation set `{D}` are left intact [6](#0-5) .
4. Now only `A` and `C` remain as live members besides `B`. `A` calls `confirm(R)` → `confirmations[R] = {D, A}` (2/3). `C` calls `confirm(R)` → `confirmations[R].len()+1 = 3 >= num_confirmations` → `execute_request(R)` fires the `Transfer`.
5. Result: the transfer executed with confirmations from `B` (creator, uncounted until confirm), `A`, `C`, and a stale confirmation from `D`, who was no longer a member at execution time — i.e., only 2 live confirming members (`A`, `C`) plus the creator actually authorized a transfer that required 3 live confirmations.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
