### Title
Stale block-rejection weight is never retracted when a signer later accepts, letting a signer's weight double-count across both tallies - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener`'s per-block vote tally uses two different membership sets to decide whether to add a signer's weight: the `Accepted` branch gates on `gathered_signatures` (keyed on slot_id → signature), while the `Rejected` branch gates on `responded_signers`. A signer that first rejects a proposal and later legitimately switches to accepting it (a state transition the signer-side FSM explicitly allows) gets its weight added to `total_weight_approved` on the second message without ever being subtracted from `total_weight_rejected`, because the `Accepted` branch never consults `responded_signers`. The same signer's weight is now counted on both sides of the ledger simultaneously.

### Finding Description
`BlockStatus` tracks two independent weight counters plus a `responded_signers` set meant to make each signer's vote count exactly once overall: [1](#0-0) 

On `Rejected`, the code correctly gates the weight add on the shared "have we heard from this signer" set: [2](#0-1) 

But on `Accepted`, the weight add is gated on a *different* set (`gathered_signatures`, keyed on slot_id → signature), not on `responded_signers`: [3](#0-2) 

If a signer's slot_id is already in `responded_signers` because it earlier sent a `Rejected` (which added its weight to `total_weight_rejected`), that fact is invisible to the `Accepted` branch: `gathered_signatures` is still empty for that slot, so the `if !block.gathered_signatures.contains_key(&slot_id)` guard passes and `total_weight_approved` is incremented too. The signer's weight is now attributed to both `total_weight_rejected` and `total_weight_approved`, which should be mutually exclusive views of the same fixed pool of signer weight (`self.total_weight`).

This reject→accept transition is not an implementation accident to be dismissed as impossible; it is a first-class, documented path in the signer's own state machine (`BlockState::LocallyRejected → BlockState::LocallyAccepted` is explicitly allowed by `BlockInfo::check_state`, and the CHANGELOG documents "For some rejection reasons, a signer will reconsider a block proposal that it previously rejected"): [4](#0-3) 

So a single, honest signer flipping its own vote (using only its own key) via `should_reevaluate_reject_reason`/re-proposal is enough to trigger the miner-side double count - no majority, no other signer's key, and no malice required.

### Impact Explanation
The miner-side decision loop checks the rejection condition before the approval condition: [5](#0-4) 

Because a flipped signer's weight is never removed from `total_weight_rejected`, that counter can retain (or accumulate) weight that no longer reflects any live, standing rejection. This breaks the intended equality between the *aggregated weight* the coordinator tracks and the *verified, current set of accepts/rejects* among signers. Concretely:
- The stale rejected-weight can push `total_weight_rejected` past the blocking-minority threshold even after enough of those very signers have switched to accepting and the block has legitimately reached the 70% approval threshold, causing the miner to treat an actually-approved block as `SignersRejected` (the `else if total_weight_approved >= weight_threshold` branch is checked second and never reached).
- This also feeds `failed_txids`-based transaction banning off of stale, retracted opinions, since the rejection weight backing a `SignersRejected` outcome is inflated by votes that have already changed.
- The net effect is a liveness wedge on block production: valid blocks with a genuine supermajority get discarded and the miner is forced to re-mine, and the failure can recur every time signers legitimately reconsider a rejection, since nothing ever "un-counts" a stale rejection.

### Likelihood Explanation
This requires no coordination or majority - a single signer following its own documented reconsideration path (rejecting on a transient condition, then accepting once the condition clears, e.g. via `should_reevaluate_reject_reason`) is sufficient to desynchronize the two counters. Any environment where a rejection reason is reconsiderable (already a supported, in-scope feature) will hit this on ordinary operation, not just adversarial input.

### Recommendation
Gate the `Accepted` branch's weight-add on the same `responded_signers` membership check used by `Rejected` (or otherwise reconcile the two counters), and when a signer's vote flips, subtract its weight from `total_weight_rejected` before/while adding it to `total_weight_approved`, so a signer's weight is only ever attributed to the tally matching its most recent, verified response.

### Proof of Concept
1. Configure signer weights so `weight_threshold` (70%) and blocking minority (30%) are both crossable by a subset of signers, e.g. total_weight = 100, weight_threshold = 70.
2. Have signer S (weight 31) send `BlockResponse::Rejected` for proposal P with a reconsiderable reason (e.g. `RejectCode::ValidationFailed` transient case, or `ProposalTooOld` per `should_reevaluate_reject_reason`). `total_weight_rejected` becomes 31, `responded_signers = {S}`.
3. The condition preventing further evaluation from being reached is not yet met alone (31 ≤ 30 is false actually - pick a smaller weight, e.g. weight 5, so it's under blocking minority initially but still gets recorded); other signers accept normally, bringing `total_weight_approved` to 65 (below 70 because S hasn't accepted yet).
4. Signer S later reconsiders (e.g. the proposal is re-sent and the earlier rejection reason no longer applies) and sends `BlockResponse::Accepted` for the same P.
5. In `stackerdb_listener.rs`, the `Accepted` branch sees `slot_id` for S absent from `gathered_signatures`, so it adds S's weight (5) to `total_weight_approved` (→70, reaching threshold) - but never removes 5 from `total_weight_rejected` (still 5, or accumulated further if more signers behave this way).
6. Verify via logs/state that `total_weight_rejected + total_weight_approved > self.total_weight` for the block, demonstrating the same signer's weight was credited to both tallies - i.e. the aggregated weight no longer matches the verified, current set of distinct signer opinions.

    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
