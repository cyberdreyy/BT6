### Title
EI credentials satisfy the `isUser` check in `PipelineRunsController.Create`, allowing external initiators to trigger arbitrary integer-ID job runs - (File: core/web/pipeline_runs_controller.go)

### Summary
`AuthenticateExternalInitiator` stores a real `*clsessions.User{Role: UserRoleRun}` under the same `SessionUserKey` used for genuine user sessions/tokens. Because `GetAuthenticatedUser` only performs a type assertion on that key, it cannot distinguish an EI-authenticated request from a real user session, so `isUser` evaluates to `true` for EI callers too. This defeats the explicit intent of the code comment "only users are allowed to run jobs using int IDs - EIs not allowed" and lets any valid EI credential trigger `App.RunJobV2` for an arbitrary integer job ID.

### Finding Description
- `AuthenticateExternalInitiator` (core/web/auth/auth.go:119-151) authenticates solely via the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers against the `external_initiators` table, and on success sets: [1](#0-0) 
  This places `&clsessions.User{Role: clsessions.UserRoleRun}` under `SessionUserKey` — the exact same key and Go type (`*clsessions.User`) used by `AuthenticateBySession`/`AuthenticateByToken` for real user logins.
- `GetAuthenticatedUser` (core/web/auth/auth.go:178-187) retrieves the value from `SessionUserKey` and performs `obj.(*clsessions.User)`. Since the EI path stores that exact type, the type assertion succeeds and `ok` (i.e., "isUser") is `true` for EI-only authenticated requests, indistinguishable from a real user. [2](#0-1) 
- In `PipelineRunsController.Create`, the code explicitly intends to gate the integer-job-ID branch to real users only: [3](#0-2) 
  Because `isUser` is wrongly `true` for EI callers, an EI credential holder can send `POST /v2/jobs/5/runs` with only EI headers (no user session/API token) and reach `prc.App.RunJobV2(ctx, jobID, nil)` for any integer job ID, with no check that the job is associated with that specific EI (that association logic previously existed for the now-removed webhook/UUID job type per the comment at line 103-107, and is not re-implemented for the int-ID path).
- The correct approach would be to check for EI presence via `auth.GetAuthenticatedExternalInitiator(c)` first, or otherwise reject/branch when `SessionExternalInitiatorKey` is also set, rather than relying solely on `GetAuthenticatedUser`'s type assertion, which cannot differentiate role origin.

### Impact Explanation
An attacker holding only a valid EI (external initiator) credential — a lower-trust "Run"-scoped credential intended to trigger only its own webhook job — can invoke `App.RunJobV2` for any integer job ID on the node, including jobs it has no ownership/association with. This is an authorization/role bypass leading to unauthorized job execution across tenants/jobs, potentially causing unintended on-chain transactions, fund movement, or interference with jobs belonging to other users/initiators — matching Chainlink's "unauthorized job run" bounty impact class.

### Likelihood Explanation
Requires only a valid EI access key/secret (the lowest-privilege credential type explicitly modeled in the system) and knowledge/guessing of a target job's integer ID. No user session, API token, or admin access is needed. The flow is fully reachable through the public `/v2/jobs/:ID/runs` HTTP route and is deterministic/repeatable.

### Recommendation
Distinguish EI-only authentication from genuine user authentication before allowing the integer-ID run path. For example, check `auth.GetAuthenticatedExternalInitiator(c)` and reject (or route to EI-specific, job-association-checked logic) when an EI context is present, instead of relying purely on `GetAuthenticatedUser`'s type assertion on a shared `SessionUserKey`. Alternatively, store a distinct principal type/flag (e.g., `IsExternalInitiator bool`) at authentication time so `isUser` can be computed accurately.

### Proof of Concept
Go handler-level integration test plan:
1. Set up a `gin.Context` and app mocks; register an `ExternalInitiator` in the mock authenticator's `FindExternalInitiator`.
2. Run `auth.AuthenticateExternalInitiator(c, mockAuthr)` with valid EI headers only (no session cookie, no API token headers).
3. Call `auth.GetAuthenticatedUser(c)` and assert `ok == true` (demonstrating the type-confusion) and `user.Role == clsessions.UserRoleRun`.
4. Invoke `PipelineRunsController.Create(c)` with `c.Param("ID") = "5"` where job `5` belongs to a different tenant/EI (or none), and mock `App.RunJobV2` to record its call arguments.
5. Assert `App.RunJobV2` was invoked with `jobID == 5` and that a `201`/successful pipeline run response was returned, despite the caller only possessing EI credentials and no ownership of job `5` — proving cross-tenant/unauthorized job triggering via the integer-ID branch intended to be restricted to real users.
