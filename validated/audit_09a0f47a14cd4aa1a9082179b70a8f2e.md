### Title
Unbounded growth of `TwoDNoncePool` lanes lets an attacker force O(n) linear scans on every block/flashblock build, degrading block production - (File: `crates/execution/txpool/src/two_d_nonce_pool.rs`)

### Summary
The reported Sherlock bug is a classic "attacker-controlled unbounded array/loop" DoS: a caller can grow a collection with no bound, and every later call that iterates the full collection becomes progressively more expensive until it exceeds a resource budget. The closest reachable analog in this Base repo is the EIP-8130 "2D nonce" sidecar pool, `TwoDNoncePool`, which is keyed by `(sender, nonce_key)` where `nonce_key` is an attacker-chosen `U256` field of every EIP-8130 transaction.

### Finding Description
`TwoDNoncePool` stores one `NonceLane` entry per distinct `(sender, nonce_key)` pair in a `HashMap<LaneId, NonceLane<T>>`: [1](#0-0) 

`nonce_key` is a free-form `U256` field on `TxEip8130` chosen entirely by the sender of the transaction, with no evidence in the reviewed code of a cap on the number of distinct `nonce_key` values a single account (or many funded senders) may use: [2](#0-1) 

Every lane insertion goes through `insert_validated`, which does `self.lanes.entry(lane_id).or_insert_with(...)` — i.e., a brand-new lane is created for any never-before-seen `(sender, nonce_key)` pair, with no bound on the total number of lanes tracked by the pool: [3](#0-2) 

Several read paths then iterate over **every** lane in the map linearly, independent of how many lanes actually contain useful (pending/queued) transactions:
- `pending_and_queued_txn_count` iterates `self.lanes.values()`
- `pending_transactions` iterates `self.lanes.values()`
- `queued_transactions` iterates `self.lanes.values()`
- `all_transactions` iterates `self.lanes.values()`
- `unique_senders` iterates `self.lanes.keys()` [4](#0-3) [5](#0-4) 

These sidecar methods are wired into the top-level `BasePool` trait implementation that the builder and RPC layers consume, merging protocol-pool results with the sidecar on every call (`pending_transactions`, `queued_transactions`, `all_transactions`, `all_transaction_hashes`, `pending_and_queued_txn_count`, `get_transactions_by_sender`, `get_pending_transactions_with_predicate`): [6](#0-5) [7](#0-6) 

Because none of these read methods filter by usefulness before allocating/iterating, a lane that is empty of pending work (or contains only far-future/expired transactions never mined) is still visited on every single call. The builder's payload/flashblock loop repeatedly calls into the pool (`self.pool.best_transactions_with_attributes_and_parking(...)`) once per flashblock, per the flashblock construction loop: [8](#0-7) 

Combined, an attacker who can get many distinct `(sender, nonce_key)` EIP-8130 transactions admitted into the pool (each is a normal, independently-payable signed transaction, so this doesn't require special privilege — only the ability to submit many transactions with unique `nonce_key` values, which costs only tx fees/deposit balance to the payer, not increasing linearly with lane count on the read side) causes the `lanes` map to grow without bound over time. This directly parallels the reported bug class: an "operator" (here, the txpool/builder) doing full linear scans over a structure whose size is fully attacker-controlled and unbounded, eventually pushing per-call cost past what the block/flashblock production time budget can tolerate.

### Impact Explanation
This matches the "Resource starvation" and "Flashblock loop, deadline, and publish failures" critical scenarios documented for this codebase: if pool query methods used inside the flashblock/payload-building hot path become slow due to unbounded lane growth, the sequencer can repeatedly miss its flashblock/payload deadline, producing empty or underfilled flashblocks, or stalling block production — a node-halt/DoS class of impact permitted by the validation rules (node halt via resource exhaustion in the reachable txpool/block-building path).

### Likelihood Explanation
Likelihood is Medium: the attack requires only ordinary access to submit signed EIP-8130 transactions with distinct `nonce_key` values (no special role), and the cost to the attacker is the normal transaction fee/deposit per submitted transaction — no protocol-level cap on distinct `nonce_key` counts was found in the reviewed sidecar-pool code. However I could not fully verify within the available tooling budget whether an upstream admission-layer limit (e.g., a global or per-sender pool-size cap enforced in `validator.rs` or pool configuration) indirectly bounds the number of lanes that can accumulate; if such a limit exists and is enforced strictly per-lane (not just per aggregate tx count), the practical severity would be lower. This should be verified against the full transaction-pool admission/eviction code before treating this as confirmed exploitable at scale.

### Recommendation
- Bound the number of distinct `(sender, nonce_key)` lanes tracked by `TwoDNoncePool`, either per sender or globally, and evict/reject new lanes once the limit is reached (mirroring standard txpool per-account slot limits).
- Add pruning of lanes that have gone stale (no pending transactions, `next_nonce` unchanged for a long time, or replaying/expired nonce-free entries) so the read methods only ever touch live lanes.
- Consider maintaining an auxiliary index of "lanes with live pending/queued transactions" so `pending_transactions`/`queued_transactions`/`all_transactions`/`unique_senders` do not need to scan every lane, only the active subset.

### Proof of Concept
Conceptual PoC (not executed):
1. Fund/control an account and repeatedly submit valid EIP-8130 transactions, each with a fresh, never-reused `nonce_key` value (a `U256`), targeting the mempool.
2. Because `insert_validated` creates a new `NonceLane` for every unseen `(sender, nonce_key)`, each submission grows `TwoDNoncePool::lanes` by one entry, with no observed eviction of "dead" lanes in the reviewed code.
3. Repeat at scale (thousands to millions of distinct `nonce_key` values across one or more funded senders).
4. Every subsequent call to `pending_transactions`, `queued_transactions`, `all_transactions`, `unique_senders`, or `pending_and_queued_txn_count` — invoked by the builder during payload/flashblock construction and by RPC txpool-status endpoints — now performs an O(lanes) scan, increasing wall-clock cost of each block/flashblock build attempt as the lane count grows, eventually threatening the flashblock/payload deadline.

    /// Returns the number of pending and queued transactions.
    pub(crate) fn pending_and_queued_txn_count(&self) -> (usize, usize) {
        let mut pending = 0;
        let mut queued = 0;
        for lane in self.lanes.values() {
            let pending_in_lane = lane.consecutive_pending_len();
            let live_in_lane = lane.live_transactions().count();
            pending += pending_in_lane;
            queued += live_in_lane.saturating_sub(pending_in_lane);
        }
        pending += self.nonce_free.len();
        (pending, queued)
    }

    /// Returns all pending transactions.
    pub(crate) fn pending_transactions(&self) -> Vec<Arc<ValidPoolTransaction<T>>> {
        let mut transactions = Vec::new();
        for lane in self.lanes.values() {
            for transaction in lane.consecutive_pending_transactions() {
                transactions.push(Arc::clone(transaction));
            }
        }
        transactions.extend(self.nonce_free.values().cloned());
        transactions
    }

    /// Returns all queued transactions.
    pub(crate) fn queued_transactions(&self) -> Vec<Arc<ValidPoolTransaction<T>>> {
        let mut transactions = Vec::new();
        for lane in self.lanes.values() {
            for transaction in lane.queued_transactions() {
                transactions.push(Arc::clone(transaction));
            }
        }
        transactions
    }

        let mut transactions = Vec::new();
        for lane in self.lanes.values() {
            transactions.extend(lane.live_transactions().cloned());
        }
        transactions.extend(self.nonce_free.values().cloned());

    fn pending_transactions_max(
        &self,
        max: usize,
    ) -> Vec<Arc<ValidPoolTransaction<Self::Transaction>>> {
        let mut transactions = self.protocol_pool.pending_transactions_max(max);
        if transactions.len() >= max {
            return transactions;
        }

        let remaining = max - transactions.len();
        transactions
            .extend(self.nonce_pool.read().pending_transactions().into_iter().take(remaining));
        transactions
    }

    fn queued_transactions(&self) -> Vec<Arc<ValidPoolTransaction<Self::Transaction>>> {
        let mut transactions = self.protocol_pool.queued_transactions();
        transactions.extend(self.nonce_pool.read().queued_transactions());
        transactions
    }

    fn pending_and_queued_txn_count(&self) -> (usize, usize) {
        let (pending, queued) = self.protocol_pool.pending_and_queued_txn_count();
        let (sidecar_pending, sidecar_queued) =
            self.nonce_pool.read().pending_and_queued_txn_count();
        (pending + sidecar_pending, queued + sidecar_queued)
    }

    fn all_transactions(&self) -> AllPoolTransactions<Self::Transaction> {
        let mut transactions = self.protocol_pool.all_transactions();
        let nonce_pool = self.nonce_pool.read();

        transactions.queued.extend(nonce_pool.queued_transactions());
        transactions
    }
