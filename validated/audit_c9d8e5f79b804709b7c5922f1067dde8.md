### Title
Standing unlimited approval to the ERC4626 vault lets anyone steal idle underlying via `vault.deposit(assets, attacker)` - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
The external report's bug class — guarding only the canonical `approve`/`setApprovalForAll` paths while other, unenumerated functions can still move or enlarge spending power — maps directly onto `ProgrammableBorrower`. The contract models fund movement as possible only through `borrow`/`repay`/`_depositToVault`/`emergencyExitVault`, all gated to `borrower`, `authorizedExecutors`, or owner/manager. But `initialize` grants the external ERC4626 `vault` a standing `type(uint256).max` allowance over the contract's underlying token, and ERC4626 `deposit(uint256 assets, address receiver)` is a permissionless function that performs `transferFrom(msg.sender == ProgrammableBorrower ...)` internally and mints shares to an arbitrary `receiver`. Any EOA can therefore call `vault.deposit(x, attacker)` and pull the contract's on-hand underlying through the pre-existing allowance, receiving vault shares (redeemable for the underlying) in their own wallet.

### Finding Description
In `ProgrammableBorrower.initialize`, the contract executes `_allowUnlimitedSpend(_underlyingToken, _vault)` and `_allowUnlimitedSpend(_underlyingToken, _idleCDO)`, giving both integrations unlimited allowance over its underlying balance [1](#0-0) . `_allowUnlimitedSpend` is implemented as `safeIncreaseAllowance(_spender, type(uint256).max)` [2](#0-1) .

The contract's own transfer paths are carefully gated: `_borrow` reverts unless the caller is `borrower` or an authorized executor and delivers funds only to `borrower` [3](#0-2) , `repay`/`executeRepay` are similarly restricted [4](#0-3) , and `emergencyExitVault`/`rescueTokens` require owner or manager [5](#0-4) . The implicit invariant is "underlying held here can only leave via these restricted functions."

That invariant is broken by the standing approval: the vault's `deposit` is itself an unrestricted entry point that consumes the allowance. Concretely, for any ERC4626 vault `V` and any attacker `A`, `A` calls `V.deposit(amount, A)`; the vault executes `underlying.safeTransferFrom(ProgrammableBorrower, V, amount)` (allowed, since allowance is max) and mints vault shares to `A`. `A` immediately calls `V.redeem`/`V.withdraw` to convert the shares to underlying. The result is equivalent to the report's scenario: a function the guard never enumerated (`deposit` on the approved spender, rather than `approve` on the token) moves the funds past every access check in the contract.

Epoch-phase reachability: this works whenever `underlyingToken.balanceOf(ProgrammableBorrower) > 0`, which occurs (a) during the buffer phase before `_depositToVault` is invoked, (b) after `emergencyExitVault` redeems shares back to the contract, (c) after a borrower `repay` when epoch accounting is inactive (funds sit idle on-contract since repayment redeployment only happens "when an epoch is active" [6](#0-5) ), and (d) for any direct token sender depositing into the contract. Notably `availableToBorrow` explicitly counts `underlyingToken.balanceOf(address(this))` as live facility assets [7](#0-6) , so this is tracked pool money, not stray dust. The theft is also unmeasured: `_vaultNetInterest` only tracks `epochDepositedToVault`/`epochWithdrawnFromVault` deltas, so assets drained through the vault's allowance produce a vault share position held by the attacker while `epochStartVaultAssets`-style accounting still counts them as deployed principal — effectively a realized loss socialized to tranche holders at `stopEpoch`/`_updateAccounting`.

No existing guard stops this: `nonReentrant` is irrelevant (single tx), there is no selector allowlist on how the allowance is consumed, and the deposit does not route through any `onlyIdleCDO`/borrower check.

### Impact Explanation
Direct theft of all underlying held by `ProgrammableBorrower` at the moment of the call, up to its full on-hand balance, by any unprivileged EOA. If the theft happens mid-epoch while accounting is active, the stolen assets remain counted in `epochStartVaultAssets + epochDepositedToVault`, so the loss manifests as vault "loss" in `_vaultNetInterest`/`vaultLoss`, is socialized across AA/BB tranche holders via the normal loss waterfall, and reduces `totalInterestDueNow`. Magnitude equals the idle balance — potentially the entire facility during the buffer phase.

### Likelihood Explanation
Medium-low. It requires a nonzero idle underlying balance on `ProgrammableBorrower`. In steady state most funds sit inside the vault (held as shares on the contract, not spendable via the token allowance), so the window is: buffer periods, post-`emergencyExitVault`, post-repay with inactive epoch accounting, and any donations. Any bot can monitor the balance and execute the call atomically, so exploitation needs only one unprivileged transaction during such a window. It does not require any privileged misbehavior.

### Recommendation
Do not grant the ERC4626 vault a standing unlimited allowance over the contract's underlying. Either:
- approve exactly the amount needed inside `_depositToVault` (`underlyingToken.safeApprove(_vault, 0)` then `safeApprove(_vault, _assetAmount)` before `vault.deposit`, mirroring the pattern already used in `IdleClearpoolStrategy._depositToVault` [8](#0-7) ), or
- keep a helper `depositToVault(uint256)` that performs approve-then-deposit in one transaction so the residual allowance is always zero.

The `idleCDO` approval should be reviewed the same way — any permissionless path on the CDO/strategy that does `transferFrom(ProgrammableBorrower, ...)` has the same exposure — though the vault path is the clearest since `deposit` mints shares to a caller-chosen `receiver`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";

interface IERC4626 {
    function deposit(uint256 assets, address receiver) external returns (uint256);
    function redeem(uint256 shares, address receiver, address owner) external returns (uint256);
    function balanceOf(address) external view returns (uint256);
    function asset() external view returns (address);
}

contract ApprovalDrainPoC is Test {
    // mainnet fork: set ProgrammableBorrower, its configured vault, and USDC
    address constant PB    = address(0xProgrammableBorrower);
    IERC4626 constant VAULT = IERC4626(address(0xMorphoVault)); // programmableBorrower.vault()

    function testDrainIdleUnderlying() public {
        address attacker = makeAddr("attacker");
        IERC20 under = IERC20(VAULT.asset());

        // simulate a buffer-phase state: PB holds idle underlying
        uint256 idle = 500_000e6;
        deal(address(under), PB, idle);

        uint256 attackerBefore = under.balanceOf(attacker);
        vm.prank(attacker, attacker);
        // no role needed: ERC4626.deposit pulls via PB's standing max allowance
        uint256 shares = VAULT.deposit(idle, attacker);
        vm.prank(attacker, attacker);
        VAULT.redeem(shares, attacker, attacker);

        assertEq(under.balanceOf(PB), 0, "PB underlying drained");
        assertApproxEqAbs(under.balanceOf(attacker), attackerBefore + idle, 2, "attacker profited");
    }
}
```
