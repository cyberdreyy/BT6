### Title
APR0 withdrawal requests can freeze epoch settlement after APR reactivation - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
An unprivileged, wallet-allowed tranche holder can create an APR0 withdrawal bucket while the strategy APR is zero. If the manager subsequently reactivates a nonzero APR before the next epoch is stopped, `stopEpoch` and `stopEpochWithDuration` always revert in `prepareStopEpochWithApr0`, temporarily freezing all pool funds until the operator manually resets the APR to zero.

### Finding Description
`IdleCreditVault.requestWithdraw` routes a withdrawal into `apr0Users` and increases `apr0TotalPrincipal` whenever `unscaledApr == 0`. During `IdleCDOEpochVariant._stopEpoch`, `prepareStopEpochWithApr0` is called before the borrower is paid or epoch state is closed. If `apr0TotalPrincipal` is nonzero but `unscaledApr` has become nonzero, the strategy unconditionally reverts with `NotAllowed`. Because this check sits outside the borrower-funding `try/catch`, the default-recovery path is not reached and the epoch remains running.

This mirrors the external bug class: two independently valid operating modes—APR0 withdrawal accounting and APR reactivation—combine into a hard assertion at epoch settlement.

### Impact Explanation
All active LP principal and all pending withdrawal receipts remain locked in the running epoch while the incompatible state persists. The freeze covers the full vault NAV. Recovery requires an operator to recognize the accounting conflict and call `setAprs(0, 0)` before stopping the epoch; normal settlement cannot proceed while the nonzero APR remains active.

### Likelihood Explanation
The attacker only needs to be an allowed tranche holder and submit a withdrawal while APR is zero. The freeze is triggered by an otherwise permitted manager action: changing the strategy APR before the APR0 request has completed its settlement epoch. No privileged-role compromise, borrower default, oracle manipulation, or external vault failure is required.

### Recommendation
Carry the request-time APR or an explicit APR0 lifecycle flag with the bucket and settle outstanding APR0 principal independently of the currently configured APR. Alternatively, forbid changing `unscaledApr` away from zero while `apr0TotalPrincipal != 0`, but revert at the APR-change call rather than during epoch settlement. The incompatibility should not surface as an epoch-close assertion.

### Proof of Concept
A Foundry regression test should follow this sequence:

```solidity
// Buffer phase, strategy APR is zero.
strategy.setAprs(0, 0);
cdo.requestWithdraw(amount, address(aaTranche));
assertGt(strategy.apr0TotalPrincipal(), 0);

// Manager reactivates APR before the request has settled.
strategy.setAprs(newApr, scaledNewApr);
cdo.startEpoch();

vm.warp(cdo.epochEndDate() + 1);
vm.expectRevert(NotAllowed.selector);
cdo.stopEpoch(0, 0);
```

The revert originates at the `unscaledApr != 0` check in `prepareStopEpochWithApr0`. Setting the APR back to zero before calling `stopEpoch` demonstrates that the funds are temporarily, rather than permanently, frozen.
