#No Vulnerability found for this question.

Based on the code, `vm_hash()` (`runtime/near-vm-runner/src/wasmtime_runner/mod.rs:558-567`) is only ever consumed as an input to `get_contract_cache_key` (`runtime/near-vm-runner/src/cache.rs:53-65`), which builds the `ContractCacheKey::Version5` used purely to namespace the on-disk/in-memory compiled-artifact cache [1](#0-0) . All call sites of `self.vm_hash()` (`compile_and_cache`, `try_compile_and_cache`, `with_compiled_and_loaded`, `contract_cached`) use it exclusively to compute this cache key, never to influence gas counting or `VMOutcome` fields [2](#0-1) [3](#0-2) [4](#0-3) .

`VMOutcome` (burnt_gas, used_gas, compute_usage, return_data) is instead computed by `compute_outcome`/`GasCounter`, driven entirely by `Config` (ext costs, wasm op costs, limits) and the finite-wasm gas instrumentation baked into the prepared wasm bytes — none of which reference `vm_hash` or `precompile_compatibility_hash` [5](#0-4) . The `precompile_compatibility_hash` reflects the *native code generation target* (used solely to decide whether a cached compiled artifact can be safely reused on this host), while the gas-charging semantics are determined by the deterministic wasm instrumentation/host-function cost tables, which are identical regardless of which CPU produced the underlying machine code. Two validators with different CPU feature sets would simply get separate cache-key namespaces (forcing independent compilation), but the *executed* gas-metering logic and resulting `VMOutcome` remain a pure function of `Config` and the wasm bytes, so no divergence in `burnt_gas`/`compute_usage` results from this. Since there is no reachable path where `vm_hash` feeds into gas accounting or outcome construction, this does not constitute a consensus-divergence vulnerability.

### 5. Gas metering
Two categories of gas are metered, both through `GasCounter`:
- **WASM instruction cost.** finite-wasm instrumentation calls `finite_wasm_gas`/`gas_opcodes` (`logic.rs:319`, `:1960`) charging `opcodes * regular_op_cost`; bulk memory/table ops use `linear_gas` (`:323`). Stack accounting is done by `finite_wasm_stack`/`_unstack` (`:384`) against `remaining_stack`.
- **Host-function `ExtCosts`.** Each host fn charges via `pay_base`/`pay_per` (`gas_counter.rs:306`, `:291`) — e.g. every host fn starts with `pay_base(base)`. Action-shaped costs (creating receipts) go through `pay_action_accumulated` (`gas_counter.rs:323`), which also accumulates `send_action_compute_usage`.

Burnt vs. used: `burn_gas` (`gas_counter.rs:148`) adds to `fast_counter.burnt_gas`, capped by `gas_limit = min(max_gas_burnt, prepaid_gas)`. `deduct_gas` (`:119`) splits a `(burnt, used)` pair, moving the difference into `promises_gas` (gas reserved for prepaid promise execution) and shrinking `gas_limit` accordingly (`:132`). `used_gas = burnt_gas + promises_gas` (`:385`). On limit crossing, `process_gas_limit` (`:169`) clamps burnt to `min(prepaid_gas, max_gas_burnt)` and returns `GasLimitExceeded` (max-burnt crossed) or `GasExceeded` (prepaid crossed), preferring `GasLimitExceeded`. In view mode `prepaid_gas` is forced to `Gas::MAX` (`:94`).

`compute_outcome` (`logic.rs:131`) computes `compute_usage` from the profile via `total_compute_usage` (NEP-455 compute costs), decoupled from gas.
