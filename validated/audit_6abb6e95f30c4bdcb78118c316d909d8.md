### Title
Dust queued deposit minting zero tranche shares causes a reachable division-by-zero panic that permanently blocks `processDeposits` and freezes queued deposits - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The gRPC advisory is a "reachable assertion": a specific, cheap-to-send input drives the implementation into an unconditional `abort()`. The credit-vault analog is a reachable arithmetic panic in `IdleCDOEpochQueue.processDeposits()`: when queued deposits for an epoch are processed during the buffer period, the contract computes the epoch price as `_pending * ONE_TRANCHE / _trancheMinted` with no zero-check on `_trancheMinted`. An unprivileged KYC-passing lender can queue a dust deposit that mints 0 tranche shares, turning every subsequent `processDeposits()` call for that epoch into a hard revert (Panic 0x12), exactly like the gRPC `abort()`.

### Finding Description
In `contracts/IdleCDOEpochQueue.sol`, `deposit()` lets any allowed wallet queue an arbitrary `amount` of underlying for `nextEpoch` with no minimum:

```solidity
// contracts/IdleCDOEpochQueue.sol:121-126
IERC20Detailed(underlying).safeTransferFrom(msg.sender, address(this), amount);
userDepositsEpochs[msg.sender][nextEpoch] += amount;
epochPendingDeposits[nextEpoch] += amount;
```

During the buffer period the honest owner/manager calls `processDeposits()`, which deposits the aggregate `_pending` into the CDO and derives the redemption price by dividing by the minted tranche amount:

```solidity
// contracts/IdleCDOEpochQueue.sol:237-245
if (tranche == _cdo.AATranche()) {
  _trancheMinted = _cdo.depositAA(_pending);
} else {
  _trancheMinted = _cdo.depositBB(_pending);
}
epochPrice[_epoch] = _pending * ONE_TRANCHE / _trancheMinted;
epochPendingDeposits[_epoch] = 0;
```

`_trancheMinted` can be 0: `IdleCDO._mintSharesAtCurrPrice` computes shares as `amount * ONE_TRANCHE / price` (integer division), so a `_pending` of a few wei — or more realistically, a single-user dust `_pending` below `virtualPrice / ONE_TRANCHE` underlying units — mints zero tranche tokens. The division then panics.

The protocol itself acknowledges this exact failure mode in the newer prefunded path, which carries an explicit guard:

```solidity
// contracts/IdleCDOEpochQueue.sol:268-270
// In case of very small prefunded deposits, it's possible that the tranche minting results in 0 shares due to rounding.
// This should not block epoch finalization...
epochPrice[_epoch] = _prefundedMinted == 0 ? _cdo.virtualPrice(tranche) : _prefunded * ONE_TRANCHE / _prefundedMinted;
```

The same rounding condition was left unguarded in the legacy `processDeposits()` path.

### Impact Explanation
Once the panic triggers, the state is unrecoverable for that epoch: `epochPendingDeposits[_epoch]` is never zeroed (the division precedes the write) and `epochPrice[_epoch]` stays 0. Every retry of `processDeposits()` re-executes `_cdo.depositAA/BB(_pending)`, and even if the CDO call succeeded it would revert again on the same division. `deleteRequest()` cannot rescue it — it reverts only when `epochPrice` is set, but the attacker simply does not delete, and the manager cannot remove another user's request. `processDepositsToBorrower()` is unavailable for non-prefunded queues (`_checkNotAllowed(_isPrefundedQueueEnabled())` blocks the reverse direction too — it reverts when the prefunded flag is *not* set... the prefunded path requires `isPrefundedQueueEnabled`, so on a non-prefunded queue there is no alternate route). The attacker's dust (a few wei of USDC) permanently freezes all honest users' queued deposits for that epoch inside the queue contract: the underlying is locked, requests cannot be claimed or deleted, and epoch processing is bricked. Loss quantified: 100% of `epochPendingDeposits[epoch]` contributed by other users.

### Likelihood Explanation
The attacker needs only to be a KYC-passed wallet (`_checkAllowed`) and place the sole queued deposit, or enough dust that aggregate `_pending` mints 0 shares — feasible when the queue has no other pending deposits that epoch, or by front-running `processDeposits` conditions where `virtualPrice(tranche)` exceeds `_pending` in share terms. Cost is a few wei of underlying plus gas. The honest manager's routine `processDeposits()` call is the abort trigger, mirroring the gRPC flow where a normal request after the crafted header hits `abort()`.

### Recommendation
Mirror the prefunded-path guard in `processDeposits()`: when `_trancheMinted == 0`, either price the epoch at `_cdo.virtualPrice(tranche)` and still sweep `_pending`, or skip the price write while zeroing `epochPendingDeposits[_epoch]` and handling the dust via the feeReceiver/skim path so a zero-mint deposit cannot wedge the epoch.

### Proof of Concept
Foundry fork PoC (against a deployed non-prefunded `IdleCDOEpochQueue`, e.g. an AA or BB queue):

```solidity
function testProcessDepositsZeroMintPanic() external {
    // --- setup: attacker is KYC-allowed (Keyring whitelist) ---
    address attacker = makeAddr("attacker");
    _keyringAllow(attacker);
    address victim = makeAddr("victim");
    _keyringAllow(victim); // victim optional; attack also works solo

    // buffer period of epoch N: queue is empty
    uint256 dust = 1; // 1 wei underlying -> mints 0 tranche shares
    deal(underlying, attacker, dust);
    vm.startPrank(attacker);
    IERC20Detailed(underlying).approve(address(queue), dust);
    queue.deposit(dust);            // epochPendingDeposits[N+1] = 1
    vm.stopPrank();

    // stay in buffer period; epoch boundary passes, epoch N+1 begins buffer
    // honest manager processes deposits for the epoch containing the dust
    vm.prank(manager);
    vm.expectRevert(); // Panic(0x12) division by zero at epochPrice[_epoch] = _pending * 1e18 / 0
    queue.processDeposits();

    // retry reverts identically -> permanent freeze; pending never cleared
    vm.prank(manager);
    vm.expectRevert();
    queue.processDeposits();

    assertGt(queue.epochPendingDeposits(targetEpoch), 0); // funds stuck
    assertEq(queue.epochPrice(targetEpoch), 0);
}
```

The dust deposit's underlying remains in the queue and any co-queued honest deposits are frozen with it, reproducing the reachable-assert crash with permanent fund impact.
