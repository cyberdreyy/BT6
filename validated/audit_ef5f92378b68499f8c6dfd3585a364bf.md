## Title
Permissionless `distribute()` in `staking_contract`/`vesting` can be permanently DoS'd by a single unpaid shareholder, freezing all other shareholders' unlocked stake - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

## Summary
`distribute_internal` in `staking_contract.move` pays out **every** shareholder in the `distribution_pool` inside one atomic loop, with no isolation between recipients — directly analogous to the reported `liquidateToken()` bug where a single unchecked/failing sub-transfer traps funds for everyone. Because a Move transaction is all-or-nothing, if the payout to *any one* shareholder aborts, the entire `distribute()` call reverts, and the withdrawal that was already pulled out of the stake pool via `stake::withdraw_with_cap` is never delivered to anyone — leaving the coins logically "stuck" in the staking-contract's pending withdrawal state and permanently blocking distribution for the staker, prior operators, and the current operator alike.

## Finding Description
`distribute_internal` withdraws all currently withdrawable stake in one shot and then loops over `distribution_pool` shareholders, calling `aptos_account::deposit_coins` for each recipient without any isolation or fallback: [1](#0-0) 

`aptos_account::deposit_coins` aborts (rather than gracefully falling back) when the recipient exists but has not registered `CoinStore<AptosCoin>` and has opted out of unsolicited coin transfers: [2](#0-1) 

The opt-out mechanism (`set_allow_direct_coin_transfers(false)`) is a fully permissionless, unprivileged action any account can invoke on itself: [3](#0-2) 

Critically, `distribution_pool` shareholders in `staking_contract` are not limited to the staker: `switch_operator` inserts the **old operator** as a shareholder to receive pending unpaid commission, and this old operator can be an arbitrary, no-longer-trusted third party the staker previously delegated to: [4](#0-3) 

Once a shareholder's payout aborts, the `while (distribution_pool.shareholders_count() > 0)` loop can never complete for *any* shareholder in that call, because the abort reverts the whole transaction (including the `stake::withdraw_with_cap` extraction and all `redeem_shares` calls already performed in that same call). Since `distribute()` is `public entry` and callable by anyone for any staker/operator pair, but always attempts to pay out the *entire* shareholder set atomically, one uncooperative/malicious shareholder can indefinitely block distribution of legitimately-earned, already-unlocked stake belonging to the staker and any other operators in the same pool. The `vesting` module inherits this exact behavior since `vesting::distribute` and `vesting::admin_withdraw` call into `staking_contract::distribute`/`distribute_internal`-equivalent flows: [5](#0-4) 

This mirrors the external report's root cause precisely: an unchecked/failing sub-transfer inside a batch operation, with no catch/skip logic, causes funds that have already left the "source of truth" (the stake pool) to become permanently unrecoverable.

## Impact Explanation
This breaks the "Unlock, reactivate, withdraw ... paths must not redirect value or strand it permanently" invariant. A single hostile or merely uncooperative shareholder (e.g., a former operator who deliberately calls `set_allow_direct_coin_transfers(false)` and avoids registering `CoinStore<AptosCoin>`, or simply an account that has never registered `AptosCoin` and refuses to) can permanently strand the staker's own already-unlocked/inactive stake and any co-shareholders' commission in the `StakingContract`/`Staker` resource — value that is otherwise fully earned and eligible for withdrawal. This is a high-severity denial-of-value: legitimate stakers lose access to funds they own with no on-chain recovery path (no admin override exists to selectively skip one shareholder), matching the "Permanent lock or non-recoverable loss of claim rights" impact category.

## Likelihood Explanation
The precondition (an old operator or other distribution-pool shareholder that has not registered `CoinStore<AptosCoin>` and disables arbitrary transfers) requires only unprivileged, self-directed actions available to any account, and does not require the attacker to already control the staker's or victim's role. It does require that the griefing address either never registered `AptosCoin` (plausible for smart-contract/resource accounts that only exist via fungible-asset flows) or a similar path exists to keep it unregistered while opting out — this specific precondition could not be fully validated within the scope of this pass (I did not confirm all code paths that create an "existing but AptosCoin-unregistered" account under the current coin/FA migration), so likelihood should be treated as plausible-but-not-fully-proven rather than certain.

## Recommendation
In `distribute_internal`, wrap each per-recipient deposit so a failure for one shareholder does not block payouts to the others — e.g., use a best-effort/deferred-payout pattern (re-add the failed recipient's shares back to the pool or move the funds to a per-recipient claimable balance) instead of a single atomic loop over all shareholders. At minimum, allow permissionless retry/skip of individual failed shareholders rather than reverting the entire distribution.

## Proof of Concept
1. Staker creates a staking contract with `operator_1`, stakes, `operator_1` accrues commission.
2. Staker calls `switch_operator` to `operator_2`; `operator_1` is inserted into `distribution_pool` as a pending-commission shareholder (per `staking_contract.move:781-805`).
3. `operator_1` (already an existing account without `CoinStore<AptosCoin>`, e.g., managed purely through fungible-asset primary stores) calls `aptos_account::set_allow_direct_coin_transfers(false)`.
4. Stake lockup expires; staker or anyone calls `staking_contract::distribute(staker, operator_2)`.
5. `distribute_internal` withdraws all inactive stake, then in its shareholder loop reaches `operator_1` and calls `aptos_account::deposit_coins(operator_1, ...)`, which aborts under `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
6. The entire `distribute` transaction reverts — the staker's own unlocked stake (and `operator_2`'s legitimate commission) remains undistributed, and every future call to `distribute` for this staking contract fails identically, permanently.

Note: full verification of the exact conditions under which an existing account can lack a registered `CoinStore<AptosCoin>` under the current coin/fungible-asset migration was not completed in this pass due to tool-call limits; this should be validated in a live/test environment before treating this as fully confirmed.
