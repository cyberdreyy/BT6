### Title
Signed gateway trigger requests can be replayed to re-trigger duplicate capability execution because `MessageId` consumption is not persisted beyond an in-memory pending-callback map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` only rejects a message as "stale" based on the signed `payload.Timestamp` compared against `HandlerConfig.MaxAllowedMessageAgeSec`; it does not maintain any persistent record of already-processed `MessageId`s. The `savedCallbacks` map is purely a transient "pending response" tracker: an entry is deleted as soon as the first DON node responds (`handleWebAPITriggerMessage`) or when it is pruned after `CallbackMaxAgeSec`/`MaxSavedCallbacks`. Once an entry is gone (either because the original request already completed, or because it was pruned), the exact same previously captured signed bytes can be resubmitted and will be accepted as a brand-new request as long as `payload.Timestamp` is still within `MaxAllowedMessageAgeSec`, causing the gateway to forward the trigger to all DON members again.

### Finding Description
`HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`) performs these checks, in order:
1. Unmarshal `TriggerRequestPayload` from `msg.Body.Payload`.
2. Reject if `payload.Timestamp == 0`.
3. Reject as "stale message" only if `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` (`handler.go:372-383`).
4. Reject unsupported method.
5. `common.ValidatedRequestFromMessage(msg)` — validates the ECDSA signature over the message body.
6. Store a fresh `savedCallback` keyed by `msg.Body.MessageId` (`handler.go:411-414`), **overwriting any prior entry unconditionally**, and forward the request to every DON member.

There is no check anywhere in this path that the `MessageId` (or the whole signed payload) has been seen/consumed before. The only "consumption" mechanism is `savedCallbacks`, which exists solely to route the first DON response back to the calling HTTP/gateway connection:
- It is deleted immediately when the first node responds, in `handleWebAPITriggerMessage` (`handler.go:148-162`, delete at line 151), i.e., a normal, successful request's `MessageId` becomes free for reuse within seconds of completion — well before `MaxAllowedMessageAgeSec` (e.g., default 1000s, `deployment/cre/jobs/pkg/gateway_job.go:331`; test default 30s, `handler_test.go:42`) expires.
- Alternatively, it is deleted by `pruneCallbacks()` after `CallbackMaxAgeSec` elapses (`handler.go:299-339`).

Either way, once the map entry is gone, an attacker who has captured the full signed `api.Message` (valid signature, valid timestamp still within the allowed age window) can resend it verbatim. Because step 6 always writes a new entry regardless of whether one previously existed, and no prior-consumption ledger is consulted, the message passes every check and is re-dispatched to all DON nodes, causing the trigger action to execute a second time and the attacker's own connection (the one submitting the replay) to receive the new response.

The signature check (`common.ValidatedRequestFromMessage`) only proves who signed the bytes — it provides no freshness/single-use guarantee beyond the coarse timestamp window, which by design (existing tests use e.g. `MaxAllowedMessageAgeSec: 30`, and production defaults use 1000 seconds) leaves a meaningful replay window after the original request already completed.

### Impact Explanation
This allows an attacker who has merely observed a legitimate user's previously-transmitted signed trigger request (e.g., via logs/proxy) to force a duplicate execution of that user's web-API trigger capability action within the configured `MaxAllowedMessageAgeSec` window, without needing to forge any signature. This maps to Chainlink's "unauthorized job run" / duplicated-execution impact class: the capability's webhook/trigger fires again attributed to the original signer's identity, and the attacker (as the new caller) receives the corresponding response. Depending on what the downstream capability does (e.g., a `web-api-trigger` workflow action with side effects), this can cause duplicate state changes, quota/rate consumption, or unintended re-triggering of workflow logic tied to the original sender.

### Likelihood Explanation
Feasibility is moderate to high: the attacker needs only network/log visibility into a previously sent, fully valid signed request (no cryptographic break required) and the ability to submit it again to the gateway's user-facing endpoint feeding into `HandleLegacyUserMessage`. No elevated privileges are needed — the same "low-privileged" ability to submit signed gateway messages that any client of this endpoint already has is sufficient. The replay window is bounded by `MaxAllowedMessageAgeSec` (configurable, production example uses 1000 seconds — over 16 minutes), which is a comfortably practical window, and reuse is immediately possible after the original request completes (deletion from `savedCallbacks` happens as soon as the first node responds), not only after `CallbackMaxAgeSec` pruning.

### Recommendation
Add persistent replay protection independent of the transient `savedCallbacks` pending-response map, e.g.:
- Maintain a separate "seen `MessageId`" (or hash-of-signed-message) set with TTL at least as long as `MaxAllowedMessageAgeSec`, and reject `HandleLegacyUserMessage` calls whose `MessageId`/payload has already been processed within that window, regardless of whether the pending callback was already resolved or pruned.
- Alternatively, bind message freshness/uniqueness enforcement to the signed timestamp with a strictly monotonic or single-use nonce requirement per sender, rejecting exact duplicate `(sender, MessageId, timestamp)` tuples seen before.
- Ensure `CallbackMaxAgeSec` semantics are documented as unrelated to anti-replay, and add an explicit replay-nonce cache with its own dedicated lifetime tied to `MaxAllowedMessageAgeSec`.

### Proof of Concept
Go test plan (in `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Use `setupHandler` with `MaxAllowedMessageAgeSec` set to a reasonably large value (e.g., 30s, as in existing tests).
2. Build a signed trigger request via `triggerRequest(...)` as in `TestHandlerReceiveHTTPMessageFromClient`.
3. Call `handler.HandleLegacyUserMessage(ctx, msg, cb1)`; simulate a DON node response via `handler.HandleNodeMessage(ctx, resp, nodes[0].Address)` so the first `savedCallbacks` entry for that `MessageId` is deleted (simulating "already consumed").
4. Assert `cb1.Wait(...)` receives the expected successful response and `handler.savedCallbacks` no longer contains the `MessageId`.
5. Without altering the signed bytes, replay the exact same `msg` a second time: `handler.HandleLegacyUserMessage(ctx, msg, cb2)`.
6. Assert (current buggy behavior) that `don.SendToNode` is invoked again for all DON members with the identical `MessageId`/payload, and `handler.savedCallbacks` again contains an entry for that `MessageId` — i.e., the replay is treated as a fresh, valid request rather than rejected.
7. A fixed implementation should instead assert that the second call returns an error/rejection (e.g., "message already processed" / replay detected) and that `don.SendToNode` is NOT called a second time.
