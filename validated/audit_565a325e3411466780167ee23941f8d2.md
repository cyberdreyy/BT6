### Title
External-initiator fake User object bypasses "EIs not allowed" check in job-run trigger endpoint - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Finding Description
`AuthenticateExternalInitiator` authenticates a request purely via `External-Initiator-Access-Key`/`Secret` headers, then sets both `SessionExternalInitiatorKey` and a synthetic `SessionUserKey` value: `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` [1](#0-0) . This synthetic `User` has no `Email` or `ID`, and is indistinguishable from a "real" authenticated session/token user to any consumer of `GetAuthenticatedUser`, which simply type-asserts whatever is stored under `SessionUserKey` [2](#0-1) .

`PipelineRunsController.Create` (the handler behind job-run-triggering requests) relies on exactly this distinction to gate integer-ID job runs: `_, isUser := auth.GetAuthenticatedUser(c)` followed by the comment "only users are allowed to run jobs using int IDs - EIs not allowed" [3](#0-2) . Because `AuthenticateExternalInitiator` also populates `SessionUserKey`, `isUser` evaluates to `true` for an EI-authenticated request, defeating the intended restriction. If the code path that authenticates this endpoint chains `AuthenticateExternalInitiator` alongside `AuthenticateByToken`/`AuthenticateBySession` (as the explicit "EIs not allowed" comment implies it must, since this check would be dead code otherwise), an EI-only credential holder can supply an arbitrary integer job ID and have `prc.App.RunJobV2(ctx, jobID, nil)` executed for that job — with no check that the job is the one the EI is registered/bound to.

This directly matches `REQUEST_BINDING` violation: an EI credential intended to trigger only its own webhook job can instead trigger any job by ID, because the fake `User{Role: UserRoleRun}` has no identity fields tying it back to the specific EI or job, and no code path re-validates job-to-EI ownership before calling `RunJobV2`.

### Impact Explanation
An external-initiator credential (a narrowly-scoped, machine-to-machine credential meant only to trigger its own bound webhook job) can trigger unrelated jobs owned by other users/specs on the node, since the run-role check and the `isUser` "EI-block" check are both satisfied by the synthetic user object. This is an authorization/ownership-binding bypass leading to unauthorized job execution, matching Chainlink's "unauthorized job run" bounty impact class.

### Likelihood Explanation
Requires only possession of valid EI access-key/secret headers for any single registered external initiator — no admin/session/token credentials needed. The synthetic-user substitution happens unconditionally on every successful EI authentication, so the flaw is deterministic and repeatable given valid EI credentials and knowledge/guessing of a target job's integer ID.

### Recommendation
Do not set `SessionUserKey` in `AuthenticateExternalInitiator`; introduce a distinct, explicit signal (e.g., a boolean/context flag) for "authenticated as external initiator" that `RequiresRunRole` can check without conflating it with a real `clsessions.User`. Update `PipelineRunsController.Create` (and any other handler relying on `GetAuthenticatedUser` to distinguish EIs from users) to use `GetAuthenticatedExternalInitiator` explicitly for the "EIs not allowed" branch instead of inferring it from the absence/presence of a `User` object.

### Proof of Concept
1. Register a valid `ExternalInitiator` with access key/secret in a test DB fixture.
2. Create a job with an integer ID belonging to a different user/spec, unrelated to the EI.
3. Send `POST /v2/jobs/{integerJobID}/runs` with only `External-Initiator-Access-Key`/`Secret` headers (no session cookie, no API token).
4. Assert (currently failing invariant) that the request is rejected with 422 "bad job ID" or 401, per the intended "EIs not allowed" comment in `pipeline_runs_controller.go`.
5. Additionally add a handler-level unit test for `PipelineRunsController.Create` where `c.Set(auth.SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` and `c.Set(auth.SessionExternalInitiatorKey, ei)` are both set (mirroring `AuthenticateExternalInitiator`'s behavior) and assert `isUser` should be `false` in this case, or that `RunJobV2` is never invoked for a job the EI is not bound to.

Note: I was unable to fully confirm within the available tool budget the exact router.go middleware chain (whether `POST /v2/jobs/:ID/runs` is wired with `auth.AuthenticateExternalInitiator` alongside token/session auth) due to running out of iterations; this should be verified directly in `core/web/router.go`'s job-routes registration before treating this as fully confirmed. The internal contradiction between `auth.go:148` and the explicit "EIs not allowed" comment in `pipeline_runs_controller.go:110` strongly suggests this code path is EI-reachable, but exact route wiring should be double-checked.
