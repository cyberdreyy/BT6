### Title
Instant-withdraw requests bypass all management and performance fees, draining fee revenue that the upfront-fee invariant is meant to capture - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`requestWithdraw` charges upfront management and performance fees on the normal path via `_totalWithdrawFees`, but the instant-withdraw branch (taken when the new epoch APR dropped by more than `instantWithdrawAprDelta`) returns early with the full `_underlyings` amount and never deducts or accounts for any fee. The code's own stated invariant — receipts that leave live NAV must pay management fees for the time they wait outside NAV — is violated for instant receipts, which also wait outside live NAV (for `instantWithdrawDelay` plus funding latency) yet pay nothing.

### Finding Description
In `requestWithdraw` (contracts/IdleCDOEpochVariant.sol:739-791), the instant branch executes before any fee logic:

```solidity
if (_isInstantWithdrawEnabled()) {
  uint256 currentApr = creditVault.unscaledApr();
  if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
    creditVault.requestInstantWithdraw(_underlyings, msg.sender);
    _withdrawOps(_amount, _underlyings, _tranche);
    return _underlyings;          // full principal + accrued, zero fees
  }
}
uint256 principal = _underlyings;
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;
pendingWithdrawFees += totalFees;
```

The comment at line 786-787 states the design rule: "The receipt is fixed now and leaves live NAV. Charge management fees upfront for the time it waits outside live NAV: remaining buffer plus the next epoch." An instant receipt is equally fixed at request time, is minted to the user as strategy tokens in `IdleCreditVault.requestInstantWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:356), and sits outside live NAV until `claimInstantWithdrawRequest` is callable — at minimum `instantWithdrawDelay` after the next `startEpoch`, and potentially a full epoch if liquidity must be recalled via `getInstantWithdrawFunds`. Yet `_totalWithdrawFees` is skipped entirely: no management fee on the wait, no performance fee on accrued interest, and no `pendingWithdrawFees` accrual, so `feeReceiver`/owner receive nothing.

### Impact Explanation
Any KYC-passed lender holding tranche tokens can exit with gross-of-fees value whenever `lastEpochApr > unscaledApr + instantWithdrawAprDelta` — a state the honest manager/borrower creates routinely by lowering APR at `stopEpoch`. The loss is the fee spread between the two paths: for a withdrawal of `P` with projected interest `I`, the user keeps `P + I_accrued` instead of `P + I - _mgmtFee - perfFee`. With a 10% performance fee and nonzero `managementFee` (as configured in tests, e.g. `testRequestWithdrawInstant`), the feeReceiver and remaining LPs permanently lose the management fee on `epochDuration + wait` plus the performance fee on `I`. Repeated exits compound the revenue loss; the skipped `pendingWithdrawFees` also means stopEpoch accounting never attempts to recover it.

### Likelihood Explanation
The trigger requires only that the manager lowers APR by more than `instantWithdrawAprDelta` at a stop — a normal operational event (rate reductions are the designed trigger for instant exits). No privileged misbehavior, donation, or default is needed; the attacker is an ordinary tranche holder calling `requestWithdraw` during the buffer/running epoch after the APR cut. The only mitigation is that instant mode can be disabled via `disableInstantWithdraw`, but the variant is explicitly built to support it (`_isInstantWithdrawEnabled`, `allowInstantWithdraw`, `instantWithdrawDelay` machinery).

### Recommendation
Apply the same fee model in the instant branch: compute `(interest, diff) = _calcInterestWithdrawRequest(_underlyings, _tranche)`, deduct `_totalWithdrawFees(principal, interest)` (with the duration reflecting the actual wait, e.g. `instantWithdrawDelay` plus remaining buffer), add it to `pendingWithdrawFees`, and pass the net amount to `requestInstantWithdraw`. Alternatively, if fee-free instant exit is intended, document it and exclude instant receipts from the "leaves live NAV ⇒ pays management fee" invariant — but then `maxWithdrawable` and fee accounting should be reconciled so both paths price identically per unit of wait time.

### Proof of Concept
Foundry fork PoC (pattern follows `testRequestWithdrawInstant` in test/foundry/IdleCreditVault.t.sol:3627):

```solidity
function testInstantWithdrawSkipsFees() external {
    _setFeeParams(FEE_RECEIVER, 10000, FULL_ALLOC, mgmtFee); // 10% perf fee + mgmt fee

    idleCDO.depositAA(10000 * ONE_SCALE);

    _startEpochAndCheckPrices(0);
    // stop epoch with APR drop > instantWithdrawAprDelta -> instant mode enabled
    _stopEpochAndCheckPrices(0, initialProvidedApr - (cdoEpoch.instantWithdrawAprDelta() + 1), _expectedFundsEndEpoch());

    uint256 trancheBal = AAtranche.balanceOf(address(this));
    uint256 gross = trancheBal * cdoEpoch.virtualPrice(address(AAtranche)) / ONE_TRANCHE_TOKEN;

    uint256 pendingFeesPre = cdoEpoch.pendingWithdrawFees();
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Instant path: user receives gross value, no fee deducted, no pendingWithdrawFees accrued
    assertEq(requested, gross);
    assertEq(cdoEpoch.pendingWithdrawFees(), pendingFeesPre); // feeReceiver gets 0

    // Compare: a normal requestWithdraw of same size would deduct
    // _totalWithdrawFees = mgmtFee(principal, epochDuration + bufferRemainder) + perfFee(interest)
}
```

The assertion `pendingWithdrawFees` unchanged + `requested == gross` demonstrates the fee bypass versus the documented charging rule for receipts leaving live NAV.
