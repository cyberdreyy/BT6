### Title
Vote commission changes are applied to the entire prior epoch's inflation rewards instead of the commission rate in effect when rewards accrued - ([File: runtime/src/inflation_rewards/mod.rs])

### Summary
Agave's inflation-reward distribution redeems an entire epoch's worth of accrued voting credits at the epoch boundary and splits the resulting inflation reward between voter and staker using a single `commission_bps` value read from the vote account. When `delay_commission_updates` is not active, this commission is read from the vote account's *current* state at distribution time rather than the rate that was actually in effect while the credits were being earned throughout the epoch — the same root cause identified in the Thruster `setYieldCut` finding, where a changed rate parameter is retroactively applied to an entire prior accrual period instead of being prorated.

### Finding Description
Rewards are calculated once per epoch, in bulk, for all outstanding stake/vote credits accumulated during `rewarded_epoch`. The split between the validator (voter) and delegator (staker) portions of that reward is computed by `commission_split`/`commission_split_preserve_lamports` using a single `voter_commission_bps` value: [1](#0-0) 

That single commission value is fetched from the *current* vote-account state at distribution time in `redeem_delegation_rewards`, unless the `delay_commission_updates` feature is active, in which case it instead looks back at a snapshot taken earlier in the epoch: [2](#0-1) 

This is structurally identical to the Thruster bug: an entire accrual period's yield (here, an entire epoch's worth of vote credits/inflation reward) is split using whatever rate is active "now," rather than the rate(s) that were actually in force while the yield was accruing. A validator operator can raise (or lower) `commission` via the vote program's `UpdateCommission` instruction, processed in `programs/vote/src/vote_processor.rs`, at any point during the epoch, and that single new value will retroactively govern the whole epoch's payout once `redeem_delegation_rewards` runs at the epoch boundary.

The existence of the `delay_commission_updates`, `commission_rate_in_basis_points`, and `custom_commission_collector` feature-gated code paths in `calculate_stake_rewards_and_commissions`/`redeem_delegation_rewards` confirms this is a recognized issue class that the protocol has been incrementally mitigating (mirroring Thruster's own acknowledgement that they "acknowledge the issue" rather than fully solve it): [3](#0-2) 

I was not able to fully confirm from the index whether `delay_commission_updates` is unconditionally active on current mainnet-beta (i.e., whether the mitigated path is always taken today), since that depends on the feature-set activation status which isn't fully visible from the indexed snippets. This should be verified directly against the feature-set state before treating the un-delayed path as currently reachable in production.

### Impact Explanation
If the un-delayed path (`delay_commission_updates == false`) is reachable, a validator can change its commission at any point and have that new rate applied to the entire epoch's already-earned inflation rewards for all its delegators, rather than only rewards accruing going forward. This lets an operator retroactively redirect delegator rewards to themselves (raise commission just before distribution) or, conversely, delegators lose the benefit of a previously-lower commission for work already done. This is a fund-misallocation issue affecting the correctness of inflation reward distribution across the entire validator's delegated stake for an epoch.

### Likelihood Explanation
Likelihood is low-to-moderate: the change requires an `UpdateCommission` transaction signed by the vote account's authorized withdrawer/authority, and its impact is bounded by whether `delay_commission_updates` is active for the relevant cluster/epoch. If the feature is already active on the target network, this reduces to the same "acknowledged, low severity" outcome Thruster itself reached, since the delay window limits the practical effect to a single epoch's timing edge case rather than a full retroactive rewrite.

### Recommendation
Confirm whether `delay_commission_updates` (and related bps/commission-collector features) are unconditionally active on the target network. If any code path can still compute commission from the vote account's state *at distribution time* rather than a rate snapshotted before/during the reward-accrual epoch, that path should be removed or feature-gated off, matching the delayed-commission design already present in `calculate_stake_rewards_and_commissions`.

### Proof of Concept
1. Delegate stake to a vote account with a low commission (e.g., 0%) for a full epoch, accruing full staker rewards.
2. Just before the epoch-boundary reward distribution runs (i.e., after credits for the epoch have been earned but before `redeem_delegation_rewards` executes), submit `VoteInstruction::UpdateCommission` to raise commission to a high value (e.g., 100%), via `programs/vote/src/vote_processor.rs`.
3. If `delay_commission_updates` is not active for the relevant network/epoch, `redeem_delegation_rewards` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` reads the new, higher commission and applies it via `commission_split`/`commission_split_preserve_lamports` in `runtime/src/inflation_rewards/mod.rs` to the entire epoch's already-earned reward, redirecting delegator rewards to the voter account instead of the rate that was in effect while credits were earned.
