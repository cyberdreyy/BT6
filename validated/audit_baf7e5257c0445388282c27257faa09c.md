### Title
`claimWithdrawRequest()` and `claimInstantWithdrawRequest()` remain callable during emergency shutdown, letting funded receipts drain the reserve while the vault is locked - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.emergencyShutdown()` pauses deposits and disables new withdraw requests (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` = false), matching the intended "no funds in, no funds out" lock. However, neither `claimWithdrawRequest()` nor `claimInstantWithdrawRequest()` checks `paused()`, `skipDefaultCheck`, or any emergency flag, so users holding already-funded withdraw receipts can still pull underlying out of `IdleCreditVault` while the vault is locked — the same bug class as the reported missing `whenNotLocked()` modifier.

### Finding Description
In `IdleCDOEpochVariant`, the emergency lockdown is enforced by:

- `emergencyShutdown()` → `_emergencyShutdown()` which pauses the contract, sets `allowAAWithdrawRequest = false` / `allowBBWithdrawRequest = false`, and sets `skipDefaultCheck = true` (`contracts/IdleCDOEpochVariant.sol:601-615`).
- `requestWithdraw()` is blocked via those flags, and `_deposit()` via `whenNotPaused` (`contracts/IdleCDOEpochVariant.sol:644`).
- `depositDuringEpoch()` is blocked via `skipDefaultCheck` (`contracts/IdleCDOEpochVariant.sol:661`).
- `unpause()` is blocked by `_beforeUnpause()` while `skipDefaultCheck` is set (`contracts/IdleCDOEpochVariant.sol:635-637`).

But the two user-facing claim exits have no such guard:

```solidity
// contracts/IdleCDOEpochVariant.sol
function claimWithdrawRequest() external {
    IdleCreditVault(strategy).claimWithdrawRequest(msg.sender); // no paused/skipDefaultCheck check
}

function claimInstantWithdrawRequest() external {
    _checkNotAllowed(!allowInstantWithdraw); // flag never cleared by _emergencyShutdown
    IdleCreditVault(strategy).claimInstantWithdrawRequest(msg.sender);
}
```

`_emergencyShutdown` never touches `allowInstantWithdraw`, so if it was enabled for the running epoch it stays enabled through the emergency. Downstream, `IdleCreditVault.claimWithdrawRequest` → `_claimFundedWithdrawRequest` → `_transferFundedClaim` transfers reserved underlying to the user, gated only by epoch timing (`epochEndDate != 0 && epochNumber <= lastWithdrawRequest`) — during the buffer phase after `stopEpoch`, or once `epochNumber` has advanced, this check passes regardless of the emergency (`contracts/strategies/idle/IdleCreditVault.sol:301-350`, `380-393`).

The existing test `testEmergencyShutdown` only asserts deposits and `requestWithdraw` revert; claims are never exercised under shutdown (`test/foundry/IdleCreditVault.t.sol:4986-5008`), confirming the gap is untested rather than intentional.

### Impact Explanation
During an emergency declared because of a suspected strategy/borrower problem or an unaccounted loss, any holder of a matured (funded) withdraw receipt — an unprivileged tranche-token holder — can claim at par on a first-come-first-served basis, draining the funded reserve held by `IdleCreditVault`. This breaks the "fully locked" invariant the shutdown is meant to enforce: losses that should be socialized or resolved before reopening exits are instead borne by later claimants and remaining LPs. For instant withdrawals, `allowInstantWithdraw` surviving the shutdown means instant receipts can also be paid out while everything else is frozen. Loss is bounded by total funded pending/instant claims, i.e. up to `pendingWithdraws`/`pendingInstantWithdraws` worth of underlying.

### Likelihood Explanation
An emergency shutdown is precisely the scenario where racing to exit matters most, and the receipt holders needed to exploit it already exist in normal operation (anyone who called `requestWithdraw` an epoch earlier). It requires no privileged role and no special market condition — only that the owner/guardian call `emergencyShutdown()` while funded claims are outstanding, which is a realistic sequence.

### Recommendation
Add the emergency check to the claim entry points in `IdleCDOEpochVariant`, e.g. revert when `paused()` or `skipDefaultCheck` is set in `claimWithdrawRequest()`, and clear `allowInstantWithdraw` inside `_emergencyShutdown()` (or apply the same check in `claimInstantWithdrawRequest()`), so no underlying leaves the vault until `restoreOperations()`.

### Proof of Concept
```solidity
// Foundry fork test against the existing test harness (test/foundry/IdleCreditVault.t.sol)
function testClaimDuringEmergencyShutdown() external {
    uint256 amount = 10000 * ONE_SCALE;
    idleCDO.depositAA(amount);

    // epoch 0 runs and stops; request becomes funded at stop
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    uint256 requested = cdoEpoch.requestWithdraw(mintedAA, address(AAtranche));

    // epoch 1 runs and stops -> request is now mature/funded in IdleCreditVault
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // owner triggers emergency: deposits paused, new requests disabled
    vm.prank(owner);
    cdoEpoch.emergencyShutdown();
    assertTrue(cdoEpoch.paused());
    assertFalse(cdoEpoch.allowAAWithdrawRequest());

    // BUG: funded receipt still pays out at par while vault is locked
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest(); // succeeds, transfers `requested` underlying out of strategy
    assertEq(IERC20Detailed(defaultUnderlying).balanceOf(address(this)) - balPre, requested);
}
```

Note: I was unable to verify every internal branch of `_claimDefaultedWithdrawRequest`/`_claimLossAdjustedWithdrawRequest` within the iteration limit, but the funded-claim path (`_claimFundedWithdrawRequest` → `_transferFundedClaim`) contains no emergency gating, which is sufficient for the PoC above.
