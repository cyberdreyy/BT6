Instant-withdraw receipts are keyed to the request epoch, but default recovery reads `instantWithdrawClaimsByEpoch[epochNumber]` at finalization, silently dropping prior-epoch claims and leaving collateral stuck - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` mirrors the H-20 bug class: two different "index" counters are used for the same logical record. Instant-withdraw receipts are written under the `epochNumber` at request time (`requestInstantWithdraw`), but default-recovery accounting reads them under the `epochNumber` at finalization time (`defaultPendingClaimBasis`, `_claimDefaultedInstantWithdrawRequest`). When the epoch counter has advanced between request and finalization — which happens every `stopEpoch` via `deposit()` — the claims are indexed under the wrong epoch, the recovery basis undercounts them, and the `defaultRecoveryReserve` is underfunded while per-user receipts remain, so later claimants' collateral is permanently stuck.

### Finding Description
In `requestInstantWithdraw`, the receipt is recorded under the *current* epoch:

```solidity
uint256 currentEpoch = epochNumber;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
``` [1](#0-0) 

`epochNumber` is incremented inside `deposit()` when the epoch is running, i.e., during `stopEpoch` — not when the withdraw request is made:

```solidity
if (IIdleCDOEpochVariant(idleCDO).isEpochRunning()) {
    totEpochDeposits = 0;
    epochNumber += 1;
}
``` [2](#0-1) 

But the recovery basis and the per-user defaulted-claim path both look up the bucket at the *finalization-time* `epochNumber` / `defaultRecoveryEpoch` (which is set to `epochNumber` at finalization, line 693):

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
    basis += instantWithdrawClaimsByEpoch[epochNumber];
}
``` [3](#0-2) 

```solidity
uint256 defaultEpoch = defaultRecoveryEpoch;
claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
``` [4](#0-3) 

If an instant request was made in epoch `N` and `stopEpoch` ran (bumping `epochNumber` to `N+1`) before the borrower defaulted and the owner finalizes recovery, `instantWithdrawClaimsByEpoch[N+1]` reads `0` even though real receipts exist under epoch `N`. `defaultPendingClaimBasis` therefore excludes them, `recoveryPrice` is computed over too small a basis, and `defaultRecoveryReserve` is funded to cover only `pendingWithdraws`. `_claimDefaultedInstantWithdrawRequest` also reads epoch `N+1` and returns `0`, but the user's aggregate `instantWithdrawsRequests[_user]` is still non-zero, so `claimInstantWithdrawRequest` falls through to `_transferFundedClaim`, which reverts or pays out of funds reserved for others — breaking the "one receipt one payout" and donation-isolation invariants.

### Impact Explanation
Direct fund impact. The recovery reserve is sized using a wrong (stale vs. incremented) epoch index, so holders of unfunded instant receipts from the request epoch either (a) get zero via the defaulted path while their receipts are never cleared, or (b) drain underlyings belonging to other claimants through `_transferFundedClaim`. In case (a) the collateral is permanently stuck — exactly the H-20 impact class (index mismatch → record overwritten/unreachable → stuck collateral). Loss equals the full unfunded instant-withdraw amount requested in the earlier epoch.

### Likelihood Explanation
Requires: an instant withdraw request in epoch N that remains unfunded (`pendingInstantWithdraws > 0` is realistic when the borrower has the funds), the epoch stopping (manager/owner `stopEpoch`, which always bumps `epochNumber`), then a borrower default and `finalizeDefaultRecovery`. The manager/owner/borrower are honest per the rules — this only needs the normal sequence of their calls plus an ordinary unprivileged user's instant request. No privileged misbehavior needed.

One caveat I could not fully verify within the tool limit: whether the CDO always finalizes default in the same epoch in which instant receipts were created, or whether a `stopEpoch` can interleave. The prefunded-instant path (`_defaultPrefundedInstantReserve`, lines 716–723) acknowledges partially funded instant buckets can persist across the default boundary, which supports that `pendingInstantWithdraws` can survive a stop while `instantWithdrawClaimsByEpoch` stays keyed to the request epoch.

### Recommendation
Use a single consistent index for instant claims, the same way the report's fix uses `omniChainData.noOfLiquidations`. Concretely: track the *request* epoch for instant withdrawals (e.g., a `lastInstantRequestEpoch`/per-user epoch marker like `lastWithdrawRequest`) or store instant claims under a bucket key that survives `epochNumber` increments (e.g., accumulate all outstanding instant claims in one aggregate `instantWithdrawClaimsTotal`), and have `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest` iterate/clear all epochs with non-zero basis rather than only `defaultRecoveryEpoch`.

### Proof of Concept
Foundry fork PoC outline (mainnet fork per repo's `foundry.toml`):

```solidity
// 1. Start epoch via IdleCDOEpochVariant.startEpoch (owner/manager, honest).
// 2. user (KYC'd AA depositor) calls requestInstantWithdraw via CDO:
//    instantWithdrawsRequestsByEpoch[user][N] = X; instantWithdrawClaimsByEpoch[N] = X;
//    pendingInstantWithdraws = X; borrower only partially refunds, pending > 0.
// 3. manager calls stopEpoch -> strategy.deposit() runs while epoch running ->
//    epochNumber becomes N+1. pendingInstantWithdraws still = X.
// 4. borrower defaults; owner calls the CDO default flow -> strategy.finalizeDefaultRecovery:
//    defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[N+1]
//    = pendingWithdraws + 0   // X silently dropped from basis
//    defaultRecoveryEpoch = N+1; defaultInstantWithdrawsFinalized = true.
// 5. user calls claimInstantWithdrawRequest via CDO:
//    _claimDefaultedInstantWithdrawRequest reads
//    instantWithdrawsRequestsByEpoch[user][N+1] == 0 -> returns 0,
//    then pays instantWithdrawsRequests[user] = X via _transferFundedClaim,
//    which either reverts (balance < reserve + X) or steals from the
//    under-reserved recovery pool -> other claimants' collateral stuck.
```

Assert: after step 4, `defaultRecoveryReserve < sum(all receipt claimBasis)` and step 5 either reverts in `_transferFundedClaim` or leaves a later defaulted-epoch claimant unable to withdraw — demonstrating permanent freezing/stuck collateral caused by the epoch-index mismatch.
