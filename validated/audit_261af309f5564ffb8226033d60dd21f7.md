### Title
Duplicate members in `MultiSigContract::new` bypass the members-vs-confirmations sanity check, permanently freezing multisig funds - (File: multisig2/src/lib.rs)

### Summary
`MultisigFactory::create` is a permissionless, unprivileged entry point that forwards attacker-supplied `members` and `num_confirmations` directly into `MultiSigContract::new`. `new()` validates reachability of the confirmation threshold using the raw length of the `members` vector, but the members are then inserted into a de-duplicating `UnorderedSet`. An attacker can pass a `members` list with repeated entries so the raw-length check passes while the actual number of distinct members is smaller than `num_confirmations`, producing a multisig whose confirmation threshold can never be reached.

### Finding Description
`MultisigFactory::create` lets any caller deploy a fresh `multisig2` contract with an arbitrary `members` list and `num_confirmations`, with no filtering of the arguments: [1](#0-0) 

`MultiSigContract::new` only checks `members.len() >= num_confirmations` on the raw input vector, then inserts each member into `self.members`, an `UnorderedSet`: [2](#0-1) 

`add_member` performs `self.members.insert(&member.clone().into())` with no duplicate check or return-value validation, so passing the same `MultisigMember` (e.g., the same `account_id` or `public_key`) multiple times silently collapses to a single stored member: [5](#0-4) 

At runtime, `confirm()` tracks confirmations in a `HashSet<String>` keyed by `member.to_string()`, explicitly rejecting a member confirming twice ("Already confirmed this request with this key"), so the maximum achievable confirmations for any request equals the number of *distinct* members, not the raw list length used at construction time: [4](#0-3) 

Consequently the binding the contract is supposed to guarantee — `num_confirmations <= count(distinct members)` — is checked against `len(raw members list)` instead, and duplicates let `num_confirmations` exceed the true reachable maximum. Because `delete_member` re-validates `self.members.len() - 1 >= self.num_confirmations` on removal but there is no equivalent re-validation at construction, the invariant can be violated from the very first block.

### Impact Explanation
If `num_confirmations` ends up strictly greater than the number of distinct members after deduplication, no request — including a `SetNumConfirmations` action meant to fix the threshold — can ever collect enough confirmations, since `SetNumConfirmations` itself requires reaching the (unreachable) threshold to execute. Any NEAR transferred into such a multisig account is then permanently frozen, matching the Critical impact category "funds permanently frozen." Other members who joined believing the declared "M of N" security model would have no recourse.

### Likelihood Explanation
The path is fully unprivileged: `multisig-factory/src/lib.rs`'s `create` requires no special role and forwards caller-supplied arguments verbatim. An attacker (or anyone who mis-specifies members, adversarially or by mistake) can trigger this in a single call to the factory with no additional preconditions.

### Recommendation
In `MultiSigContract::new`, validate the number of *unique* members (e.g., insert into the set first, then check `self.members.len() >= num_confirmations as u64`) rather than validating the raw input vector length. Reject the initialization if duplicate entries reduce the effective member count below `num_confirmations`.

### Proof of Concept
1. Attacker calls `MultisigFactory::create` with:
   - `name = "attacker-ms"`
   - `members = [Account{"attacker"}, Account{"attacker"}, Account{"victim1"}]`
   - `num_confirmations = 3`
2. The factory deploys `attacker-ms.<factory>` and calls `new(members, 3)`.
3. `assert(members.len() >= num_confirmations)` → `3 >= 3` passes.
4. The loop over `members` calls `add_member` three times; `self.members` (an `UnorderedSet`) ends up with only `{attacker, victim1}` — 2 distinct members.
5. `victim1` and others deposit NEAR into `attacker-ms.<factory>` believing 3 confirmations are required/achievable.
6. Any `add_request` + `confirm` sequence can gather at most 2 distinct confirmations (`attacker`, `victim1`), since `confirm()` disallows the same member confirming twice.
7. `confirmations.len() + 1 >= num_confirmations` (`2 + 1 >= 3`... actually max is `1 (attacker) + 1 (victim1) = 2` confirmations total, never reaching 3) is never satisfied — no request, including `SetNumConfirmations`, can ever execute, permanently freezing all funds held by the account.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
