### Title
Fee-on-transfer underlying breaks deposit flow and under-delivers claim funding pulls, inflating credited amounts over actual balances - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The external report's bug class — crediting the nominal `_amount` of a transfer instead of the actual post-fee balance delta — maps onto the credit vault's funding pulls. The codebase is inconsistent: `IdleCDO._deposit` and `IdleCDOCreditVault._deposit` mint shares using a balance delta (`_contractTokenBalance(_token) - _preBal`), but every subsequent inbound `safeTransferFrom` — the strategy pull, the epoch funding pulls, and the default-recovery pull — still books the nominal `_amount`. With a fee-on-transfer underlying (e.g., USDT with fee enabled), deposits revert or silently under-deliver, breaking solvency and the "one receipt one payout" invariant.

### Finding Description
`IdleCDOCreditVault._deposit` correctly mints tranche shares on the received delta, but then calls `IIdleCDOStrategy(strategy).deposit(_amount)` with the full nominal amount [1](#0-0) . `IdleCreditVault.deposit` pulls `_amount` from the CDO and mints `_amount` strategy tokens [2](#0-1) . Since the CDO only received `_amount - fee` from the user, the strategy's `safeTransferFrom` reverts unless the CDO happens to hold at least `fee` units of pre-existing idle float — in which case the shortfall is drained from other LPs' NAV instead of the depositor. The same pattern repeats on the funding side: `collectWithdrawFunds` prices `lossRecoveryPriceByEpoch` and clears `pendingWithdraws` against nominal `_amount` while receiving `_amount - fee` [3](#0-2) , `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` by the nominal amount [4](#0-3) , and `finalizeDefaultRecovery` sets `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` while the external pull only delivers `_recoveredAmount - fee` [5](#0-4) . `ProgrammableBorrower._repay` likewise clears `assets` of borrower debt while only `assets - fee` arrives, and then tries to redeposit the full `assets` into the ERC4626 vault [6](#0-5) .

### Impact Explanation
If a credit vault is deployed with a fee-on-transfer underlying, claims are funded short: `defaultRecoveryReserve` is credited `fee` more than the balance, so the last recovery/funded claimants' `_transferDefaultRecovery`/`_transferFundedClaim` calls revert — permanent freezing of unclaimed claims worth the cumulative fee under-delivery. Deposits either revert outright (deposit flow dead) or drain `fee` units of pooled float per deposit. With a percentage-based FoT token the loss scales with amounts, not a fixed dust.

### Likelihood Explanation
Likelihood is conditional: it requires the vault `token` to be fee-on-transfer. The underlying is fixed at `initialize` with no restriction [7](#0-6) , and deployments target stablecoins like USDT which can enable transfer fees. No guard (skim, flags, `onlyIdleCDO`) compensates; the mismatch is silent under-delivery on honest manager/borrower actions, not attacker-triggered. This is a Medium-severity incompatibility rather than a high-value exploit.

### Recommendation
Either explicitly document/reject fee-on-transfer underlyings at deployment, or measure received amounts via balance deltas: in `IdleCreditVault.deposit`, `collectWithdrawFunds`, `collectInstantWithdrawFunds`, `finalizeDefaultRecovery`, and `ProgrammableBorrower._repay`/`_depositToVault`, record `balanceAfter - balanceBefore` and use that for strategy-token minting, `defaultRecoveryReserve`, `pendingWithdraws` clearing, and debt accounting; in `IdleCDOCreditVault._deposit`/`IdleCDO._deposit`, pass the delta (not `_amount`) to `strategy.deposit`.

### Proof of Concept
Fork-test outline (Foundry): deploy `IdleCreditVault` + `IdleCDOCreditVault` with a fee-on-transfer ERC20 as `token` (use the report's `TransferFeeToken`, fee = 1e14 per transfer).

```solidity

    // CDO balance is `amount - fee` -> safeTransferFrom reverts -> deposit bricked
    vm.expectRevert(); // IERC20: insufficient-balance inside IdleCreditVault.deposit

    // strategy receives `recoveredAmount - fee` but sets
    // defaultRecoveryReserve = recoveredAmount (+ prefunded)
    // two claimants each claim claimBasis * defaultRecoveryPrice;
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
```

```text
        emit Repaid(assets, assets, 0);
        if (epochAccountingActive) {
          // While an epoch is active, even partial repayments are parked back into the vault immediately.
          // This repayment only clears previously-fronted debt, so it should not count as new epoch profit.
          _depositToVault(assets, assets);
        }
        return (assets, 0);
      }
    }

    // Then clear interest accrued but not yet fronted by IdleCDO.
    uint256 accruedInterestDue = borrowerInterestAccrued;
    if (assets >= accruedInterestDue) {
      interestPaid += accruedInterestDue;
      currentEpochInterestPaid = accruedInterestDue;
      borrowerInterestAccrued = 0;
      assets -= accruedInterestDue;

      // Only after all interest is covered can the remainder reduce outstanding principal.
      uint256 principalDue = borrowerPrincipal;
      principalPaid = assets > principalDue ? principalDue : assets;
      borrowerPrincipal = principalDue - principalPaid;
    } else {
      interestPaid += assets;
      currentEpochInterestPaid = assets;
      borrowerInterestAccrued = accruedInterestDue - assets;
    }

    if (epochAccountingActive) {
      // Current-epoch borrower interest must remain visible as profit at stopEpoch, while principal,

      _depositToVault(totalRepaidAssets, totalRepaidAssets - currentEpochInterestPaid);
```
