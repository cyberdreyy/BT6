### Title
Instant-withdraw claims pay out receipts that were never funded — new requests made after funding are aggregated into `instantWithdrawsRequests` and claimed at par — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the quiche bug where ACK frames could cover packet numbers that were never sent, `IdleCreditVault.claimInstantWithdrawRequest` pays out the *aggregate* `instantWithdrawsRequests[_user]` balance, even though funding (`collectInstantWithdrawFunds`) only ever covers receipts that existed at `startEpoch` time. A user can hold a funded instant receipt, add a new unfunded instant request during the buffer period, and then claim the full combined amount — receiving underlyings for a receipt that was never funded by the CDO/borrower. This directly steals funds reserved for other users' receipts or the vault's default-recovery reserve.

### Finding Description
`requestInstantWithdraw` mints the user a 1:1 strategy-token receipt and only increments accounting counters: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws` [1](#0-0) . No underlyings move at request time.

Funding happens exactly once per epoch: `startEpoch` calls `collectInstantWithdrawFunds(min(pendingInstant, totUnderlyings))`, which decrements `pendingInstantWithdraws` and pulls tokens from the CDO [2](#0-1) [3](#0-2) . Receipts created after that point carry no funding.

The claim path does not distinguish funded from unfunded receipts: it reads the whole `instantWithdrawsRequests[_user]` balance, burns it, and transfers the full amount [4](#0-3) . The per-epoch maps (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`) exist only for default haircuts, not for funding checks.

On the CDO side, `requestWithdraw` gates on `allowAAWithdrawRequest`/`allowBBWithdrawRequest` (true during the buffer) and the instant path only checks `_isInstantWithdrawEnabled()` — `!disableInstantWithdraw && !isProgrammableBorrower` — which says nothing about whether the previous instant batch was already funded [5](#0-4) [6](#0-5) . `allowInstantWithdraw` is set to `true` when a fully-funded epoch starts and is not cleared when a new unfunded request is added.

### Impact Explanation
Broken invariant: one receipt, one funded payout. Because the claim pays the aggregate balance, a receipt backed only by burned principal (strategy tokens burned from the CDO, no underlyings collected) is paid out of the strategy's token balance at par. Those underlyings are the reserve meant for other users' funded receipts and `defaultRecoveryReserve`. An attacker who deposits, requests an instant withdraw, waits for `startEpoch` funding, then submits a second instant request during the buffer can claim principal twice per unit deposited — direct theft of other users' funded claims, up to the full balance held by the strategy.

### Likelihood Explanation
Requires only a KYC-passing lender (an unprivileged attacker per scope). Preconditions: instant withdrawals enabled (`!disableInstantWithdraw`, non-programmable borrower, APR-decrease trigger satisfied per `lastEpochApr > currentApr + instantWithdrawAprDelta`), and at least one funded epoch so `allowInstantWithdraw == true`. The attacker controls all transactions; no privileged role misbehaves. The residual uncertainty is the exact `allowInstantWithdraw`/deadline gating in `IdleCDOEpochVariant.claimInstantWithdrawRequest`, which I could not fully read — if that function additionally checks `instantWithdrawDeadline` or blocks claims while unfunded `pendingInstantWithdraws` exist, the window narrows (but the aggregate-claim flaw remains for any receipt funded in an earlier epoch and claimed after a new request).

### Recommendation
Track funded vs unfunded instant receipts separately: either pay only `min(instantWithdrawsRequests[_user], fundedAmount)` computed from a per-user funded basis, or revert requests that arrive while `pendingInstantWithdraws` has not been re-funded (e.g., require `allowInstantWithdraw` to be cleared whenever `pendingInstantWithdraws` increases after funding). Alternatively, decrement a `fundedInstantWithdraws` counter in `collectInstantWithdrawFunds` and cap each claim at that funded amount.

### Proof of Concept
```solidity
// Foundry fork PoC (IdleCreditVault.t.sol style)
// Epoch N: attacker deposits via depositAA and triggers instant withdraw
// requestWithdraw -> requestInstantWithdraw(_underlyings, attacker)
// manager.startEpoch(): pendingInstant <= totUnderlyings, so
//   collectInstantWithdrawFunds(pendingInstant) fully funds it and
//   allowInstantWithdraw = true.
// Buffer period (allowAAWithdrawRequest == true, allowInstantWithdraw still true):
//   attacker calls requestWithdraw again -> instant path ->
//   requestInstantWithdraw mints receipt #2; pendingInstantWithdraws += amt2,
//   but NO collectInstantWithdrawFunds happens.
//   attacker calls claimInstantWithdrawRequest(attacker):
//     amount = instantWithdrawsRequests[attacker]  // = amt1 + amt2
//     _burn + _transferFundedClaim pays amt1 + amt2
//   amt2 was never funded: it is paid out of other users' funded
//   instant receipts / defaultRecoveryReserve held by the strategy.
// Assert: strategy token balance decreased by amt2 more than the
//   attacker ever funded; other users' claims now under-collateralized.
```

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
