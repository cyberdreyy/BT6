### Title
Signer weight double-counted across accept and reject tallies when a rejection is later reversed - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side `StackerDBListener` (called from `signer_coordinator.rs`) maintains a single `BlockStatus` accumulator per proposed block that separately tracks `total_weight_approved` and `total_weight_rejected`. The two branches that update these fields use inconsistent "have we already counted this signer" gates. This is the same class of bug as the `GaugeExtraRewarder` report: two tallies that are supposed to stay in lockstep with a single underlying truth (a signer's current vote) can drift apart because a later state change (a signer switching its vote) is not reconciled against the earlier one, letting the same signer's weight land in both buckets.

### Finding Description
`BlockStatus` tracks per-block consensus with two counters and one `responded_signers: HashSet<u32>` gate [1](#0-0) .

- For `BlockResponse::Rejected`, the weight is only added the first time a slot id is seen, gated by `block.responded_signers.insert(slot_id)` [2](#0-1) .
- For `BlockResponse::Accepted`, the weight is added when `!block.gathered_signatures.contains_key(&slot_id)`, i.e. gated by a *different* map (`gathered_signatures`, not `responded_signers`) [3](#0-2) .

Because the accept-path gate checks `gathered_signatures` and not `responded_signers`, a signer who first sent a `Rejected` response (which only inserts into `responded_signers`, not `gathered_signatures`) and later sends an `Accepted` response for the *same block hash* will pass the `!contains_key` check and have its weight added to `total_weight_approved` as well — on top of the weight it already contributed to `total_weight_rejected`. The single source of truth ("what is this signer's current vote on this block?") is never reconciled; the rejection accounting is never rolled back when the signer's vote flips to acceptance, exactly analogous to `GaugeExtraRewarder` never reconciling its cached share count against the gauge's real balance after a state change.

A single miner can trigger this without needing a majority of signers or any other signer's key: the miner controls when and how many times it (re)submits the identical block bytes (same `signer_signature_hash`) to the signer set over StackerDB. On the signer side, `handle_block_proposal`/`should_reevaluate_block` permits reconsideration of a rejected block when `should_reevaluate_reject_reason` returns true (transient/reconsiderable reasons such as `ConnectivityIssues`) [4](#0-3) . A miner can therefore engineer a first submission that a signer transiently rejects for a reconsiderable reason (broadcasting one `Rejected` response, counted into `total_weight_rejected` on the node), then re-submit the same bytes once conditions clear so the signer's fresh evaluation results in `Accepted` (broadcasting a second, `Accepted` response for the same hash, counted into `total_weight_approved` on the node). The coordinator's `BlockStatus` for that hash now double-counts that signer's weight in both totals.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality the coordinator relies on. The miner-side threshold logic derives outcomes purely from the two saturating totals [5](#0-4) : it rejects the block (`SignersRejected`) once `total_weight_rejected + weight_threshold > total_weight`, and treats it as approved once `total_weight_approved >= weight_threshold`. With the same signer's weight artificially inflating both sides:
- A block that legitimately reached the ≥70% accept threshold can still trip the reject branch first (or vice versa) purely because of stale rejection weight from a vote the signer already reversed, producing an inconsistent/incorrect consensus outcome for that block — a rejection recounted alongside a valid accept path, or a miscounted aggregate that does not reflect current signer intent.
- This directly maps to the required Critical impact class: an aggregated-weight vs verified-accepts mismatch that can cause the coordinator to act on the wrong side of consensus for a block, without any majority of colluding signers, using only a normal, non-malicious signer whose vote legitimately flips due to transient conditions.

### Likelihood Explanation
This requires only:
1. One signer whose per-block verdict flips from `Rejected` to `Accepted` for an identical block (a routine possibility given `should_reevaluate_reject_reason`'s explicit design to allow reconsideration of transient rejection reasons).
2. The miner re-broadcasting/re-triggering re-evaluation of the same proposal bytes, which is fully within a single miner's control (no other signer's key, no majority, no auth token needed).

Because reconsideration of rejections is an intended, documented signer behavior (`docs/signer-flows.md` section 3, `should_reevaluate_reject_reason`), and the coordinator's tallying code path is exercised on every signer response, this is readily reachable in normal operation, not just a contrived edge case.

### Recommendation
Make the two counters mutually exclusive and reconciled against a single "current vote per signer" map, mirroring the recommendation in the referenced report ("piggyback off of a single accounting source rather than tracking in two places"). Concretely:
- Track one `HashMap<u32, Vote>` (Accepted/Rejected) per block instead of two independently-gated aggregates.
- When a new response for a slot id arrives, subtract that signer's weight from whichever bucket it was previously counted in (if any) before adding it to the new bucket, so `total_weight_approved` and `total_weight_rejected` always reflect only the signer's most recent decision.

### Proof of Concept
1. Miner proposes block `B` (hash `H`) to the signer set.
2. Signer S evaluates `B`, hits a reconsiderable rejection (e.g., a transient error causing `RejectReason::ConnectivityIssues`), and broadcasts `BlockResponse::Rejected(H)`.
3. Node's `StackerDBListener` processes this: `block.responded_signers.insert(slot_S)` succeeds, so `total_weight_rejected += weight_S` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:515-518`).
4. Miner re-submits the identical bytes for `H`. Signer S's `should_reevaluate_block`/`should_reevaluate_reject_reason` permits re-evaluation because the prior reject reason was reconsiderable; S's fresh evaluation now validates and eventually signs, broadcasting `BlockResponse::Accepted(H)`.
5. Node's `StackerDBListener` processes this: `block.gathered_signatures` does not yet contain `slot_S` (S was never in `gathered_signatures`, only in `responded_signers` from step 3), so the `!contains_key` check at line 443 is true and `total_weight_approved += weight_S` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:443-465`).
6. Result: signer S's weight is now counted in *both* `total_weight_rejected` and `total_weight_approved` for the same block `H`, inflating both totals beyond what the actual, current signer votes justify, and the coordinator's threshold decision (`stacks-node/src/nakamoto_node/signer_coordinator.rs:487-541`) is computed on this inconsistent state.
