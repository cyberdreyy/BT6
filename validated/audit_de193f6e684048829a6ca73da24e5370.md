### Title
Unauthenticated `message_id` collision in legacy Gateway WebAPI trigger handler allows cross-user response hijacking - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The legacy Gateway `web_api_trigger` handler stores pending callbacks in a map keyed **only** by the client-supplied `MessageId`, with no per-sender scoping and no check for an existing in-flight entry. An unprivileged client can submit a request using a `MessageId` that collides with another in-flight request, silently overwriting the original caller's callback. When the DON node's response for that message ID arrives, it is delivered to the attacker's callback instead of the legitimate requester's — a cross-user response confusion analogous to the LPDA bug where an attacker could re-trigger a completed/duplicate state transition to redirect funds intended for others.

### Finding Description
`HandleLegacyUserMessage` stores the callback in a bare map indexed by `msg.Body.MessageId` with no existence check and no sender binding: [2](#0-1) 

`MessageId` is entirely attacker-controlled — it's a free-form string set by the client when constructing the signed message, as shown in the CLI tool and tests: [3](#0-2) [4](#0-3) 

When the corresponding DON node response arrives, `handleWebAPITriggerMessage` looks the callback up **solely by `MessageId`** and delivers the first response received to whatever callback is currently stored under that ID, with no verification that the responding message actually corresponds to the original caller/session: [5](#0-4) 

By contrast, the newer/rewritten gateway components explicitly address this exact class of bug:
- `RequestCache.NewRequest` keys on `globalId{sender, id}` and rejects duplicate in-flight IDs: [6](#0-5) 
- The v2 HTTP trigger handler explicitly validates and rejects duplicate/in-flight request IDs with `ErrConflict`, as covered by its own test: [7](#0-6) 

The legacy `capabilities.handler` (used for `MethodWebAPITrigger`/`MethodWebAPITarget`/`MethodComputeAction`/`MethodWorkflowSyncer`) never received this hardening: it neither binds the saved callback to the sender nor rejects a colliding, still-pending `MessageId`.

### Impact Explanation
An unprivileged gateway client (any party able to reach the internet-facing gateway HTTP endpoint) can race or predict another in-flight request's `MessageId` and overwrite the `savedCallbacks` entry for that ID. The legitimate caller's response is then silently redirected to the attacker's connection instead of the intended requester, while the original caller receives no response (until eventual timeout/pruning). This is a concrete cross-user response confusion / request impersonation primitive: whichever payload/response was destined for the legitimate workflow trigger call is instead disclosed to, or consumed by, an unrelated attacker. Depending on what data flows through `web_api_trigger`/`web_api_target` responses (which can include workflow-triggered HTTP action results), this can leak response bodies not meant for the attacker.

### Likelihood Explanation
Exploitation requires only knowledge (or successful guessing/racing) of another client's `MessageId`, which is not secret, is transmitted in the request body, and is often deterministic/sequential in client implementations (e.g., the CLI defaults it to a fixed literal `"12345"`). No authentication bypass, signature forgery, or privileged access is required — only crafting a competing message with the colliding ID before the legitimate response is processed. This is a straightforward unprivileged-actor race condition reachable directly through the internet-facing gateway.

### Recommendation
- Key `savedCallbacks` by `(sender, MessageId)` rather than by `MessageId` alone, mirroring `RequestCache`'s `globalId`.
- Reject new requests whose `(sender, MessageId)` key already has a live, unexpired callback entry (return a conflict error to the caller), matching the `v2` `httpTriggerHandler` behavior.
- Consider migrating the legacy `capabilities.handler` webapi-trigger path onto the same `RequestCache`/duplicate-ID-rejection abstraction already used elsewhere in the gateway.

### Proof of Concept
1. Attacker sends a legitimate-looking `web_api_trigger` message with `MessageId = "X"` to the gateway; the gateway registers `savedCallbacks["X"] = attackerCallback` per [2](#0-1) , immediately after (or racing with) a legitimate user's own request that also happens to use `MessageId = "X"` (e.g., both clients default to a fixed/sequential ID, or the attacker observes/guesses the value).
2. Whichever request registers last in the map wins; the earlier caller's callback reference is overwritten and lost.
3. When the DON node responds with `MessageId = "X"`, `handleWebAPITriggerMessage` looks it up and delivers the response to whichever callback is currently registered — the attacker's, per [8](#0-7) .
4. The legitimate caller never receives a response (times out per pruning logic), while the attacker receives the response intended for the legitimate request.

type globalId struct {
	sender string
	id     string

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
