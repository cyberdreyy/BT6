### Title
Claimed instant-withdraw receipts are never removed from `instantWithdrawClaimsByEpoch`, inflating default-recovery basis and insolventing the recovery reserve - ([contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analog of the refcount leak (`of_node_put()` missing after `of_find_compatible_node()`): `requestInstantWithdraw` increments four counters (`instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, `pendingInstantWithdraws`), but the normal claim path `claimInstantWithdrawRequest` decrements only one of them. The two per-epoch counters are "leaked" — never released on a successful claim — and are later consumed by `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` during `finalizeDefaultRecovery`, where they are double-counted as both recovery basis and recovery reserve.

### Finding Description
In `requestInstantWithdraw`, the strategy records the receipt per epoch:

```solidity
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
``` [1](#0-0) 

A funded instant claim then clears only the aggregate balance and burns the receipt:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [2](#0-1) 

`instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are left untouched — the missing decrement. They are only cleared in the defaulted path `_claimDefaultedInstantWithdrawRequest` [3](#0-2) .

The stale values are then reused at default finalization:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
``` [4](#0-3) 

and the prefunded-reserve computation treats `instantBasis - pendingInstant` (including the already-claimed amount) as underlying actually held by the strategy [5](#0-4) . `finalizeDefaultRecovery` then computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` with `reserveAmount` inflated by phantom, already-paid-out funds [6](#0-5) .

Additionally, when the stale user later calls `claimInstantWithdrawRequest` after finalization, `_claimDefaultedInstantWithdrawRequest` executes `instantWithdrawsRequests[_user] -= claimBasis` where `claimBasis` is the stale per-epoch value exceeding the zeroed aggregate — an underflow revert that permanently bricks that user's claim path [7](#0-6) .

### Impact Explanation
Broken invariant: one receipt, one payout / solvency of the recovery reserve. In a running epoch with instant withdrawals enabled:

1. Attacker requests an instant withdraw of `X`; the CDO funds it via `collectInstantWithdrawFunds` (decrementing `pendingInstantWithdraws`), and the attacker claims `X` underlying. `instantWithdrawClaimsByEpoch[epoch]` still contains `X`.
2. Any other user's instant request `Y` remains unfunded, so `pendingInstantWithdraws = Y > 0`.
3. Borrower defaults in the same epoch; `finalizeDefaultRecovery` counts `X + Y` as instant claim basis but also books `X` as "prefunded reserve" that no longer exists in the contract — the attacker already withdrew it.
4. `defaultRecoveryPrice` is therefore computed against a reserve `X` larger than the real balance. Every defaulted-epoch claim is paid `claimBasis * price` from `_transferDefaultRecovery` [8](#0-7) ; total payouts exceed actual holdings by `X * price`, so later claimants' transfers revert — permanent freezing of their recovery share — and/or the reserve is drained insolvent. The attacker's own stale receipt simultaneously underflow-reverts, permanently locking their share of the reserve in the contract.

Loss is quantified: `X` underlying of phantom reserve per claimed instant receipt, directly diluting or freezing every defaulted-epoch claimant's payout.

### Likelihood Explanation
Requires the default-epoch instant bucket to be non-zero at finalization (`defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0`), which is a routine state whenever any instant request is unfunded when the borrower defaults. The attacker's setup needs only a normal instant request, a funded claim, and a subsequent default in the same epoch — all unprivileged actions around honest manager/borrower calls. No existing guard (`_ensureDefaultRecoveryInitialized`, `NotAllowed` checks, `_onlyIdleCDO`) stops it; the leak exists precisely because the normal claim path was never updated to touch the per-epoch records added for default accounting.

### Recommendation
In `claimInstantWithdrawRequest`, decrement the per-epoch records symmetrically with the aggregate, e.g. track/derive the user's request epoch and execute `instantWithdrawsRequestsByEpoch[_user][reqEpoch] -= amount` and `instantWithdrawClaimsByEpoch[reqEpoch] -= amount` before clearing `instantWithdrawsRequests[_user]`. If requests can span epochs, store a `lastInstantWithdrawRequest` epoch marker analogous to `lastWithdrawRequest`. Add a regression test asserting `instantWithdrawClaimsByEpoch[epoch] == 0` after all funded instant claims for that epoch.

### Proof of Concept
Foundry fork PoC sketch (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// epoch running, instant withdraws enabled via setInstantWithdrawParams
// 1. attacker deposits, then requests instant withdraw of X
cdoEpoch.requestInstantWithdraw(X, address(AAtranche)); // via tranche flow
// 2. honest CDO/manager funds it: getInstantWithdrawFunds -> collectInstantWithdrawFunds(X)
// 3. attacker claims normally
cdoEpoch.claimInstantWithdrawRequest();
assertEq(strategy.instantWithdrawsRequests(attacker), 0);          // cleared
assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, epoch), X); // LEAKED
assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), X);              // LEAKED
// 4. victim requests instant withdraw Y, left unfunded
// 5. borrower defaults; manager calls finalizeDefault / finalizeDefaultRecovery
// assert: strategy.defaultPendingClaimBasis() == pendingWithdraws + X + Y (X double counted)
// assert: defaultRecoveryReserve counts X that was already paid out
// 6. victim's defaulted instant claim pays out more than the real balance supports;
//    last claimant's _transferDefaultRecovery reverts -> recovery funds frozen.
// 7. attacker.claimInstantWithdrawRequest() underflow-reverts in
//    _claimDefaultedInstantWithdrawRequest (stale basis > aggregate) -> permanently bricked.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
