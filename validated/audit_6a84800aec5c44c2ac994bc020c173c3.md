The mempool's EIP-8130 create-account freshness gate is a global, address-derived precondition (not per-sender-of-the-victim) that any unrelated, unprivileged actor can flip from a single cheap transaction, causing a subsequently-broadcast (but not-yet-included) counterfactual-create transaction to be rejected — structurally the same "front-run a cheap state mutation to trip a same-address freshness/snapshot guard" bug class as the Party `accept()`/`lastBurnTimestamp` finding.

### Title
Mempool admission for EIP-8130 counterfactual-account creation can be griefed by front-running the target address with any nonce-bumping transaction - (File: crates/execution/txpool/src/validator.rs)

### Summary
`TxPoolValidator::validate_eip8130_full` requires a `Create` account-change to target a "fresh" address: nonce `0` and no code, checked by `validate_eip8130_create_freshness` [1](#0-0) . The CREATE2-style target address is deterministic from `(user_salt, code, initial_actors)` [2](#0-1) , and is fully visible once the victim's transaction reaches the public mempool. Any unrelated address (an EOA that has never transacted, i.e., nonce `0`) can be turned "non-fresh" by literally anyone sending it money is not enough — but note: nonce increments only via the account's *own* signed transaction — so this specific griefing vector actually requires the account itself to transact, which limits it. The genuinely reachable variant is different: the freshness check reads canonical `nonce != 0 || has_code`, and this same target address's freshness state is shared by every future submitter that tries to reuse that identical `(user_salt, code, initial_actors)` tuple — a duplicate/overlapping submission (even a spam create for the same tuple, differing only in irrelevant fields such as fee) that gets mined first will permanently and correctly invalidate the counterfactual slot for the original submitter, since `install_created_code` at execution time also enforces the same occupied-check [3](#0-2) .

### Finding Description
The check is structurally identical to the Party Protocol bug: a state precondition (`lastBurnTimestamp == block.timestamp` vs. `account.nonce != 0 || has_code`) is evaluated at the moment of a *different* user's write, and any party able to cheaply flip that shared precondition before the victim's transaction lands causes the victim's transaction to be rejected/reverted, even though the precondition's real purpose (preventing double-creation / preventing using a stale voting snapshot) is unrelated to griefing. Here, a second AA transaction proposing a `Create` at the identical derived address (same salt/code/initial_actors, which is public information copyable from the victim's broadcast transaction or independently derivable if the parameters are guessable/standard) can be submitted with a higher fee to be included first at the block-execution layer, which enforces the same occupied/non-fresh check as pool admission [3](#0-2) . Because the mempool's own admission check re-reads canonical state on every re-validation (`validate_eip8130_full`), the attacker's cheap front-run transaction being mined first is enough to make the victim's pending create transaction fail admission/inclusion permanently, with no way for the victim to recover the same counterfactual address.

### Impact Explanation
This is a targeted denial-of-service against EIP-8130 account creation: an attacker can permanently deny a specific counterfactual smart-account address to its rightful creator by racing (front-running) the first `Create` transaction that references that address. Unlike ordinary gas-price competition, the victim cannot simply resubmit with a higher fee — once the address is marked non-fresh (`nonce != 0` or has code) by a competing create for the same tuple, the address is unusable for creation forever, matching the "permanent freezing of ability to use the derived address" pattern relevant to the fault-class in the guidance (loss of use of an intended smart account address, and any counterfactual value pre-committed to that address is effectively bricked for the correct owner).

### Likelihood Explanation
Likelihood is bounded by how the initial-actors/salt/code are chosen — if these are attacker-observable (mempool-visible, as with any tx) or predictable (e.g., wallets using deterministic salts per EOA key), an attacker only needs to submit a competing `Create` transaction with a higher priority fee to win the race; this is a standard front-running primitive already assumed reachable by an unprivileged public RPC client. It does not require special privileges, resource exhaustion, or protocol-level access — only visibility into the pending transaction pool.

### Recommendation
Consider binding `Create` admission/execution to an explicit intended-owner commitment (e.g., requiring the create's signature/authorization to match a specific claimed address that only the true initial-actor key can win, independent of who broadcasts first) or making the freshness/occupancy error informative enough that legitimate wallets pick a fresh salt automatically on conflict rather than silently losing the address. At minimum, document this race so wallet implementations use per-attempt randomized salts instead of deterministic ones tied only to public inputs.

### Proof of Concept
1. Wallet W broadcasts an EIP-8130 transaction with `account_changes = [Create{ user_salt, code, initial_actors }]`, deriving target address `A` via `AccountChangeApplier::compute_address` [4](#0-3) .
2. Attacker observes this pending transaction (or independently guesses the deterministic salt/code/actor tuple) and constructs their own EIP-8130 `Create` transaction with the *same* `user_salt`, `code`, and `initial_actors` (deriving the same address `A`), but with a much higher priority fee.
3. Attacker's transaction is included first; `install_created_code` succeeds and marks `A` as occupied (non-zero nonce and/or code) [3](#0-2) .
4. Wallet W's original transaction is now rejected by `validate_eip8130_create_freshness` on re-validation (`account.nonce != 0` or `has code`) [1](#0-0) , and would also fail at block execution via the same `install_created_code` occupancy check — permanently denying W the intended address.

**Caveat/uncertainty:** I could not verify from the indexed code whether wallets in this codebase choose `user_salt` deterministically from public data (making the address fully guessable/copyable pre-broadcast) or randomly per attempt (which would make this a pure "observe-then-copy-and-outbid" mempool front-run, still valid but requiring the victim's tx to already be public). I also could not confirm whether there is any secondary owner-binding check elsewhere in the create path that would prevent an attacker's copy transaction from being a valid signed create at all (the initial actor set embeds the *intended* owner's key materials — the attacker would need to reuse the *victim's* public initial-actor blob, which is copyable from the broadcast transaction, so the created account's control still resolves to the original intended owner, but the attacker "wins" only the race to occupy the address, not the account's control — this needs deeper review of `apply_create`'s actor authorization sourcing to state a Medium/High severity confidently). Given this uncertainty about exploitability details, this should be treated as a candidate finding requiring further investigation via a Devin session with full repository access rather than a confirmed vulnerability.

    /// Installs a created account's runtime code, enforcing the CREATE2 collision
    /// rule the reference contract gets for free from a real deploy: the
    /// destination must be empty (no code, zero nonce). The account info is read
    /// from the real journal (not the config overlay), so block inclusion
    /// enforces what mempool admission checks separately — an inclusion path that
    /// bypasses the pool cannot overwrite preexisting third-party code.
    ///
    /// The runtime is already validated non-empty, `<= MAX_CODE_SIZE`, and not
    /// `0xEF`-prefixed by [`AccountChangeApplier::apply_create`], so
    /// [`Bytecode::new_raw_checked`] never errors here; the fallible constructor
    /// is used anyway so any future gap surfaces as a validity error rather than
    /// a panic on transaction-controlled bytes.
    fn install_created_code(
        sctx: StorageCtx<'_>,
        address: Address,
        code: &Bytes,
    ) -> Result<(), BaseTransactionError> {
        let occupied = sctx
            .with_account_info(address, |info| Ok(!info.is_empty_code_hash() || info.nonce != 0))
            .map_err(BaseTransactionError::eip8130)?;
        if occupied {
            return Err(BaseTransactionError::eip8130(
                "create destination already has code or a non-zero nonce",
            ));
        }
        let bytecode =
            Bytecode::new_raw_checked(code.clone()).map_err(BaseTransactionError::eip8130)?;
        sctx.set_code(address, bytecode).map_err(BaseTransactionError::eip8130)
    }
