Based on my research, I found a concrete analog: the `TrieNode::decode` implementation in the fault-proof MPT crate performs unbounded mutually-recursive descent when parsing attacker-influenceable trie preimages, with no depth limit — directly analogous to the CVE-2020-36374 stack-overflow-via-unbounded-recursive-parser pattern.

### Title
Unbounded recursive descent in `TrieNode::decode` allows stack-overflow DoS of the fault-proof program via crafted MPT preimages - (File: `crates/proof/mpt/src/node.rs`)

### Summary
`TrieNode::decode` and its helper `try_decode_leaf_or_extension_payload` recursively parse RLP-encoded Merkle-Patricia-Trie nodes with no bound on nesting depth, mirroring the `parse_comparison` stack-overflow bug class in the CVE (recursive-descent parser with unbounded recursion on attacker input causing DoS via crafted input).

### Finding Description
`TrieNode::decode` inspects the RLP header and, for a 2-element list, calls `try_decode_leaf_or_extension_payload`, which for an `Extension` node calls `Self::decode(buf)` recursively on the remaining bytes of the *same* buffer to decode the embedded child node inline (no depth counter, no recursion limit): [1](#0-0) 
For a 17-element list (`Branch`), `Vec::<Self>::decode(buf)` decodes each of the 17 children by calling `TrieNode::decode` again on each element, which can itself be another `Branch` or `Extension`: [2](#0-1) 
Because the RLP encoding used by `TrieNode` embeds child nodes directly inline whenever they are smaller than 32 bytes (rather than always going through a keccak-blinded hash lookup), an attacker can construct a single top-level buffer containing thousands of nested `Extension`/`Branch` wrappers, each just large enough to be a valid 2-element or 17-element RLP list, causing thousands of nested Rust stack frames from one `TrieNode::decode` call — with no depth guard anywhere in the crate (`grep` for `MAX_DEPTH`/`recursion`/`stack` in `crates/proof/` shows only the CBOR parser in the unrelated TEE registrar has a depth cap; the MPT decoder has none).

This decoder is invoked by the stateless trie DB used by the fault-proof program/executor, e.g. `TrieDB::get_trie_account` opens the account trie and decodes fetched account/storage node bytes: [3](#0-2) 
and by the L1 chain provider used during derivation inside the fault-proof client: [4](#0-3) 
Both paths source the raw bytes from a preimage oracle keyed by hash (`PreimageKeyType::Keccak256`), and in the dispute-game/fault-proof model, preimage data for a given hash is supplied off-chain by a dispute-game participant (the actual preimage isn't constrained beyond matching the hash the program requests) — the fault-proof program (op-program style client run via `FaultProofDriver`/`StatelessL2Builder`) decodes whatever bytes are handed back as long as they hash correctly: [5](#0-4) 

### Impact Explanation
A stack overflow in the fault-proof program's native/host execution path aborts the process, halting the fault-proof program mid-execution. Since this program computes the L2 output root used to resolve dispute games, a crash prevents the honest party from producing a valid execution trace for that step of the dispute, which can stall or corrupt dispute-game resolution — a node/proof-generation halt with direct consequences for the correctness of on-chain fault-proof outcomes. This satisfies the "node halt / wrong provable output root" impact bar.

### Likelihood Explanation
Reaching this path requires only supplying a trie-node preimage (an account/storage MPT node, or an L1 receipts/state trie node during derivation) whose bytes decode into deeply nested inline `Extension`/`Branch` structures. Any participant in the fault-proof/dispute-game preimage-supply flow can shape such bytes, since the only constraint on a preimage is that it hashes to the requested key — trivially satisfiable by hashing the crafted nested-node blob itself. No signature or special privilege is required beyond acting as a preimage/data provider in the derivation or account/storage trie path, which is within the fault-proof program's threat model as an untrusted input source.

### Recommendation
Add an explicit recursion/nesting-depth counter to `TrieNode::decode` (and thread it through `try_decode_leaf_or_extension_payload`), similar to the `MAX_CBOR_NESTING_DEPTH` guard already used in `crates/proof/tee/registrar/src/cbor.rs`, and reject inputs exceeding a sane bound (e.g., 64) with a decode error rather than recursing further. Alternatively/additionally, convert the recursive decode into an explicit iterative work-stack to make stack usage independent of input structure.

### Proof of Concept
Construct RLP bytes representing a chain of nested 2-element lists, each satisfying the `Extension` node "list of 2, first item's high nibble = 0/1" shape, where each `Extension`'s child field is itself another inline `Extension` node (all small enough to avoid the 32-byte blinding threshold), repeated N times (e.g., N = 100,000, well within the channel/RLP byte budget referenced elsewhere in the codebase, e.g. `Channel::MAX_RLP_BYTES` in `crates/consensus/protocol/src/batch/tx_data/eip8130.rs:57`). Feed this single blob as the preimage response for any account-proof or L1-trie-node hint request consumed by `TrieNode::decode` (e.g., via `TrieDB::get_trie_account` or `OracleL1ChainProvider::trie_node_by_hash`). The resulting call chain `TrieNode::decode` → `try_decode_leaf_or_extension_payload` → `TrieNode::decode` → … recurses N times, exhausting the call stack and crashing the fault-proof program process before it can produce a valid claim.
