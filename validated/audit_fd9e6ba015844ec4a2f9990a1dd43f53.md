### Title
Post-default withdraw requests pay 1:1 from the isolated default recovery reserve without any funding, stealing recovery from defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The CVE analog is "writes proceed past the bounds of an exhausted allocation pool". In `IdleCreditVault`, `defaultRecoveryReserve` is a fixed pool sized at `finalizeDefaultRecovery` to exactly cover defaulted-epoch claims (`reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve`, priced as `reserveAmount * RECOVERY_FULL / totalBasis`, `IdleCreditVault.sol:686-692`). After finalization, `requestWithdraw` lets any tranche holder open a new receipt that mints `postDefaultRequests[_user] = _amount` (lines 247-257) and `_claimPostDefaultWithdrawRequest` pays it 1:1 via `_transferDefaultRecovery`, which does `defaultRecoveryReserve -= _amount` (lines 760-767, 912-916). No code path ever adds backing to the reserve for post-default requests: `reserveDefaultRecovery` reverts once `defaultRecoveryFinalized` is true (lines 629-633), and `collectWithdrawFunds`/`_transferFundedClaim` only move underlyings into the contract without crediting the reserve.

The reserve is sized only for `totalBasis` = active basis + `defaultPendingClaimBasis()` (pending normal + current-epoch instant receipts) at lines 674-688. Post-default receipts are outside `totalBasis`, yet every post-default claim decrements the same reserve. Each post-default claim of `X` therefore removes `X` underlying that belongs pro-rata to defaulted-epoch claimants; once cumulative post-default claims exceed the reserve's surplus over outstanding default claims, `_claimDefaultedWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest` revert on the underflow at `defaultRecoveryReserve -= _amount`, permanently freezing the remaining unclaimed recovery.

The reserve-exhaustion guard in `_transferFundedClaim` (lines 897-906) protects the reserve from funded claims, but nothing protects it from post-default claims, which are routed to `_transferDefaultRecovery` unconditionally. `one receipt one funded payout` and `donation/reserve isolation` invariants are broken.

### Impact Explanation
Direct theft plus permanent freezing of unclaimed yield. A tranche-token holder (unprivileged, KYC'd) who deposits/requests withdraw after default finalization mints a receipt and immediately claims it at par from `defaultRecoveryReserve`, extracting underlying that was recovered for defaulted-epoch claimants. Loss is quantified as `min(postDefaultRequests claimed, defaultRecoveryReserve)`; once the reserve is depleted below the outstanding defaulted-epoch claim amount, those claimants' claims revert permanently — the recovered funds were already stolen, so even an underflow revert cannot make them whole.

### Likelihood Explanation
Requires only: a borrower default has been finalized (`defaultRecoveryFinalized == true`, honest privileged flow), then any unprivileged user with tranche tokens calls `requestWithdraw` on the CDO and then `claimWithdrawRequest`. No race, no privileged misbehavior, no oracle dependence. The post-default request/claim path is an explicitly supported UX ("Preserve request/claim UX after default", line 252), so it is reachable in normal operation whenever a defaulted vault still accepts tranche-holders' requests.

### Recommendation
Either fund post-default requests before paying them (e.g., require `collectWithdrawFunds` to also credit `defaultRecoveryReserve` for post-default epochs, or add a dedicated `postDefaultReserve` incremented when the CDO pulls repayment), or pay post-default claims through `_transferFundedClaim` against actual newly-received underlyings rather than the isolated recovery reserve. At minimum, gate `_claimPostDefaultWithdrawRequest` on `underlyingToken.balanceOf(this) - defaultRecoveryReserve >= amount` so post-default claims can never consume the defaulted-epoch reserve.

### Proof of Concept
Foundry fork sketch (mainnet fork, real USDC credit vault):

```solidity
// Setup: running epoch, borrowers defaulted, finalizeDefaultRecovery executed.
// Reserve R = defaultRecoveryReserve sized for totalBasis of defaulted claims.
IdleCreditVault vault = IdleCreditVault(strategy);
uint256 reserve = vault.defaultRecoveryReserve();

// Attacker: unprivileged tranche holder post-default.
uint256 trancheBal = AAtranche.balanceOf(attacker);
vm.prank(attacker);
cdo.requestWithdraw(trancheBal, address(AAtranche)); // mints postDefaultRequests[attacker]

vm.prank(attacker);
cdo.claimWithdrawRequest(); // _claimPostDefaultWithdrawRequest -> _transferDefaultRecovery

// Attacker received 1:1 underlying drawn from the recovery reserve.
assertEq(underlying.balanceOf(attacker), vaultAmountRequested);
assertEq(vault.defaultRecoveryReserve(), reserve - vaultAmountRequested);

// Victim: defaulted-epoch claimant with basis worth ~reserve after attacker drains it.
vm.prank(victim);
vm.expectRevert(); // underflow on defaultRecoveryReserve -= _amount
cdo.claimWithdrawRequest();
```

Note: I could not fully trace the CDO-side post-default `requestWithdraw`/`claimWithdrawRequest` plumbing in `IdleCDOEpochVariant.sol` within the available iterations; the strategy-side accounting shown above (reserve sizing at finalization, post-default mint path, `_transferDefaultRecovery` decrement, `reserveDefaultRecovery` revert post-finalization) is sufficient to establish that no funding leg exists for post-default receipts.

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
