### Title
Bridge `OutgoingToken` secret disclosed to view-role users via `GET /v2/bridge_types/:BridgeName` - ([File: core/web/bridge_types_controller.go])

### Summary
`BridgeTypesController.Show` retrieves the full `bridges.BridgeType` record and serializes it with `presenters.NewBridgeResource`, which unconditionally copies the plaintext `OutgoingToken` field into the JSON response for every caller, regardless of session role. Since the `Show` route is not gated by `RequiresEditRole`/`RequiresRunRole` (unlike `Create`/`Update`/`Destroy` on the same resource), a session user with only the `view` role can retrieve this secret.

### Finding Description
`BridgeTypesController.Show` looks up the bridge by name and returns `presenters.NewBridgeResource(bt)` directly [1](#0-0) . `NewBridgeResource` maps `b.OutgoingToken` straight into the `OutgoingToken` field of the resource with no redaction, and that field is JSON-tagged without `omitempty`, so it is always emitted [2](#0-1) . `BridgeType.OutgoingToken` is stored in plaintext in the DB/struct (unlike `IncomingTokenHash`, which is hashed) [3](#0-2) , and it is generated once at bridge creation via `utils.NewSecret(24)` and persisted verbatim [4](#0-3) . Because the `Show`/`Index` handlers reuse the same presenter as `Create`/`Update`/`Destroy`, and only `Show`/`Index` lack an edit/run role requirement (per the question's stated route registration), any authenticated view-role session can read this outgoing secret merely by calling `GET /v2/bridge_types/:BridgeName` or listing bridges via `Index`.

By contrast, `IncomingToken` (the plaintext incoming credential) is only populated transiently inside `Create` from the one-time `BridgeTypeAuthentication` struct returned by `NewBridgeType` and is never persisted or reloaded from storage [5](#0-4) ; this design intentionally prevents it from resurfacing on `Show`. `OutgoingToken`, however, has no analogous protection — it is stored in cleartext on the `BridgeType` struct itself and is re-emitted on every read.

### Impact Explanation
This corresponds to a credential/secret disclosure vulnerability. The `OutgoingToken` is a credential the Chainlink node uses to authenticate itself to the external adapter (bridge) endpoint. Disclosure of this secret to a low-privileged (view-role) user allows that user to impersonate the node when calling the external adapter directly, potentially manipulating adapter responses/data feeding into the node's job pipeline, or performing actions on the adapter side attributable to the node.

### Likelihood Explanation
Precondition is only a valid view-role session — the lowest privilege session role in the system. The attack is a single unauthenticated-relative-to-role GET request: `GET /v2/bridge_types/<name>`. No other gate (rate limit, edit-role check, CSRF-equivalent) stands in the way based on the code examined; the vulnerability is fully reproducible and repeatable for any existing bridge.

### Recommendation
Redact `OutgoingToken` (and any other adapter secret) from `presenters.BridgeResource` for read paths (`Show`/`Index`), mirroring how `IncomingToken` is already excluded from persisted-record reads. If `OutgoingToken` must be exposed to operators for legitimate reasons, gate `Show`/`Index` behind `RequiresEditRole` (or a dedicated admin-only role) or add a separate presenter/field for privileged responses only, ensuring view-role sessions never receive the raw token value.

### Proof of Concept
1. In `core/web/bridge_types_controller_test.go` (or a new integration test using `cltest`), create an authenticated app client with `sessions.UserRoleView`.
2. Create a bridge as an admin/edit-role client via `POST /v2/bridge_types`, capturing the generated `OutgoingToken` from the `BridgeType` stored in DB (via `bridges.ORM.FindBridge`).
3. Using the view-role session, issue `GET /v2/bridge_types/<bridgeName>`.
4. Assert the HTTP response succeeds (200) and that the JSON body's `attributes.outgoingToken` equals the plaintext token stored in the DB — proving disclosure to a view-role user.
5. Expected secure behavior (post-fix): the `outgoingToken` field should be omitted/redacted in the response for non-privileged roles, and the test should assert its absence or emptiness.

func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

func NewBridgeType(btr *BridgeTypeRequest) (*BridgeTypeAuthentication,
	*BridgeType, error,
) {
	incomingToken := utils.NewSecret(24)
	outgoingToken := utils.NewSecret(24)
	salt := utils.NewSecret(24)

	hash, err := incomingTokenHash(incomingToken, salt)
	if err != nil {
		return nil, nil, err
	}

	return &BridgeTypeAuthentication{
		Name:                   btr.Name,
		URL:                    btr.URL,
		Confirmations:          btr.Confirmations,
		IncomingToken:          incomingToken,
		OutgoingToken:          outgoingToken,
		MinimumContractPayment: btr.MinimumContractPayment,
		UseConnectionManager:   btr.UseConnectionManager,
	}, &BridgeType{
		Name:                   btr.Name,
		URL:                    btr.URL,
		Confirmations:          btr.Confirmations,
		IncomingTokenHash:      hash,
		Salt:                   salt,
		OutgoingToken:          outgoingToken,
		MinimumContractPayment: btr.MinimumContractPayment,
		UseConnectionManager:   btr.UseConnectionManager,
	}, nil
}
