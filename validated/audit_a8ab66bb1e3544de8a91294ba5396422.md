### Title
Single unregistered/opt-out recipient in `distribute_internal`'s shared payout loop permanently locks all co-mingled stake and commission distributions - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`distribute_internal` unlocks and withdraws the *entire* pending distributable balance of a staking contract in one atomic call, then loops over every shareholder in `distribution_pool` (staker + any current/former operators with pending commission) paying them out via `aptos_account::deposit_coins`. If any single shareholder's account cannot accept the deposit, the whole transaction — and thus every other shareholder's payout bundled in the same call — reverts.

### Finding Description
`distribute_internal` withdraws the full `total_potential_withdrawable` amount from the stake pool and distributes it to all shareholders recorded in `staking_contract.distribution_pool` in a single loop: [1](#0-0) 

Each payout goes through `aptos_account::deposit_coins`, which aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient has not registered a `CoinStore` for `AptosCoin` and has explicitly opted out of direct transfers via `set_allow_direct_coin_transfers(false)`: [2](#0-1) [3](#0-2) 

`set_allow_direct_coin_transfers` is a fully unprivileged, self-only entry function — any account (including an operator or a *former* operator still holding a pending commission distribution from a prior `switch_operator` call) can call it on their own address at any time.

Because `distribution_pool` can contain multiple shareholders sharing the same withdrawn lump sum (the staker plus current/former operators, capped only by `MAXIMUM_PENDING_DISTRIBUTIONS`) as seen in `create_staking_contract`: [4](#0-3) 

a single unregistered/opt-out shareholder blocks `distribute()` for *everyone* in that staking contract, since Move transactions are atomic and the loop has no error-isolation or skip logic.

Notably, the codebase shows the team is aware of exactly this bug class and mitigated it — but only for the vesting `set_beneficiary` path, not for the default staker/operator distribution path in `staking_contract.move`: [5](#0-4) 
The comment there states explicitly: "This is a requirement so `distribute()` wouldn't fail and block all other accounts from receiving APT if one beneficiary is not registered." No equivalent guard exists for the operator/beneficiary added into `staking_contract`'s `distribution_pool` via `request_commission_internal`/`add_distribution`, nor is there any guard preventing a shareholder from calling `set_allow_direct_coin_transfers(false)` after already being added as a distribution recipient.

**Important caveat / unverified dependency:** I could not read the contents of `coin.move` in this session (index size limits truncated the file), so I could not confirm whether `AptosCoin`'s migration to the fungible-asset backend causes `coin::is_account_registered<AptosCoin>` to always return `true` (which would bypass the `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` gate entirely for APT and neutralize this issue). This is the single biggest unknown affecting whether this is exploitable on current mainnet APT, and would need to be confirmed by reading `coin.move` and `fungible_asset.move`'s coin-migration logic directly.

### Impact Explanation
If exploitable, this permanently locks the staker's own principal/rewards and any operator's earned commission that are bundled in the same `distribution_pool` snapshot, with no owner-only recovery path (there is no privileged function to remove a bad shareholder from `distribution_pool` or force a partial distribution). This matches the "Required Impacts" criterion of permanent, non-recoverable loss of claim rights in a stake/commission accounting flow triggered by an unprivileged actor's own account configuration.

### Likelihood Explanation
Likelihood is uncertain and hinges on the unverified AptosCoin/FA-migration behavior noted above. If `coin::is_account_registered<AptosCoin>` can return `false` for a real account (e.g., one that never explicitly registered a CoinStore and is not auto-migrated), then the griefing path requires only one unprivileged transaction (`set_allow_direct_coin_transfers(false)`) by any current or former operator on the affected staking contract, making it trivially triggerable, including possibly by accident.

### Recommendation
Do not treat this as confirmed without further verification of `coin.move`'s AptosCoin/FA-migration registration semantics. If confirmed exploitable, apply the same mitigation already used in `vesting::set_beneficiary` — require `assert_account_is_registered_for_apt` for every address added to `distribution_pool` (operator, beneficiary, staker) at the time of `add_distribution`, and/or make `distribute_internal` resilient to a single failing recipient (e.g., skip-and-retry logic or per-recipient try/fallback deposit into an escrow) so one recipient cannot block payouts to all others sharing the same pool.

### Proof of Concept
Conceptual PoC (contingent on the coin.move behavior described above):
1. Staker creates a staking contract with Operator A (`create_staking_contract`).
2. Staker calls `switch_operator` to Operator B; Operator A still has a pending commission distribution recorded under `distribution_pool` (see `switch_operator`/`distribute_internal` at lines 781-805 shown in the retrieved snippet).
3. Operator A, before ever registering a `CoinStore`, calls `aptos_account::set_allow_direct_coin_transfers(false)` on their own account.
4. Anyone calls `distribute(staker, operator_B)` (or any code path invoking `distribute_internal` for that staking contract) once inactive stake is withdrawable.
5. `distribute_internal`'s loop reaches Operator A's recipient entry, `aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`, and the entire transaction — including the staker's own payout — reverts, permanently blocking distribution until Operator A's account state changes (which Operator A, as a malicious/uncooperative actor, has no incentive to do).

Full exploitability confirmation requires reading `coin.move` (and `fungible_asset.move`'s coin-migration bridging) to verify `coin::is_account_registered<AptosCoin>` semantics, which was not accessible in this session due to indexing limits — I recommend a Devin session with full file access to confirm or refute this before treating it as a confirmed vulnerability.

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
