## Title
Multisig `confirm` counts stale confirmations from deleted members, allowing execution of a request below the live-member threshold - (File: multisig2/src/lib.rs)

### Summary
The external report's bug class is: an action ignores whether the authorization/entitlement it relies on ("listed" state) is still valid, so a stale piece of state lets an unentitled party complete a transaction. The direct analog in this repo is `multisig2`'s `confirm`/`delete_member` flow, where confirmations recorded by a member are never invalidated when that member is removed, so a request can execute using a mix of confirmations from members that are no longer part of the multisig.

### Finding Description
`MultiSigContract::confirm` in `multisig2/src/lib.rs` counts the size of the `confirmations` set for a request and executes the request once `confirmations.len() + 1 >= self.num_confirmations`: [1](#0-0) 

Confirmations are stored keyed only by `RequestId`, as a `HashSet<String>` of member identifiers, with no cross-reference enforcing that every entry in that set is still a current member at execution time: [2](#0-1) 

When a member is removed via `DeleteMember`, `delete_member` only cleans up: (a) requests *originated* by that member (`r.member == member`), and (b) `num_requests_pk` for that member. It removes the member from `self.members`, but it does **not** scan other still-pending requests to strip that member's confirmation from their `confirmations` set: [3](#0-2) 

Consequently, the binding that should hold is:

`num_confirmations` == count of confirmations from accounts currently in `self.members` at execution time

But the actual code only enforces:

`num_confirmations` == `confirmations.len()` (regardless of whether every confirming identity is still in `self.members`)

Scenario:
1. Multisig has members A, B, C, D with `num_confirmations = 3`.
2. Member A creates request R and confirms it (1/3). Member B confirms (2/3, still pending — not yet executed).
3. Before a third confirmation, the group (using a separate, already-fully-confirmed request) executes `DeleteMember { member: A }` — e.g., because A's key was compromised or A left the organization. `delete_member` only removes requests where A was the *original requester*; since R was requested by A itself, in this particular ordering R would actually be deleted by `delete_member`'s cleanup — but if a *different* member (e.g., B) is the original requester of R and A merely added a confirmation to it, R is **not** touched by the cleanup, and A's confirmation for R silently remains valid in `confirmations`.
4. Now member C confirms R. `confirmations.len()` becomes 3 (A, B, C) which meets `num_confirmations = 3`, and `execute_request` fires — even though A is no longer a member of the multisig and never should have contributed to quorum for that request.

This breaks the "confirmations counted versus live members" custody binding: the contract executes a privileged action (`Transfer`, `AddKey`, `FunctionCall`, etc.) using a quorum that includes a party whose authorization was explicitly revoked.

### Impact Explanation
This crosses an authorization/threshold boundary described in the rules ("a multisig request executed below threshold"): the effective number of *currently authorized* confirmers is below `num_confirmations` (only B and C are live members, i.e., 2 valid confirmations, not 3), yet the request executes as if fully authorized. Because `execute_request` can perform `Transfer` (moving NEAR/funds), `AddKey`/`FunctionCall` (arbitrary privileged calls on the multisig's own account), this can result in unauthorized movement of funds or unauthorized privileged operations being carried out with a stale, revoked signer's contribution counted toward quorum. This matches the Critical impact category: "a multisig request executed below threshold."

### Likelihood Explanation
Exploiting this requires: a pending (unconfirmed-to-completion) request that was not requested by the removed member but was confirmed by them, and a `DeleteMember` action being executed before that pending request accumulates enough *live* confirmations. This is a plausible and realistic sequence in normal multisig operation (member removal for key rotation/compromise is an expected event, and the 15-minute request cooldown before deletion, together with `active_requests_limit` of 12 pending requests per member, means multiple concurrently pending requests are the norm). No attacker input/deposit is required beyond normal multisig usage by members who are, at the time they confirm, legitimate members — the vulnerability is purely a missing invalidation, not a crafted malicious input, making it a structural, high-likelihood defect within realistic multisig lifecycles (member turnover).

### Recommendation
When a member is removed (`delete_member`), iterate over all pending requests' `confirmations` sets and remove the deleted member's identifier from every one of them (not just requests they authored). Equivalently, at `confirm`/execution time, filter `confirmations` to only those entries still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
Conceptual reproduction (matching existing test harness patterns in `multisig2/src/lib.rs`'s `#[cfg(test)] mod tests`):
1. Initialize `MultiSigContract::new(members: [A, B, C, D], num_confirmations: 3)`.
2. As B: `add_request_and_confirm(request_R)` where `request_R` is e.g. a `Transfer` — this adds R with 1 confirmation (B).
3. As A: `confirm(request_R_id)` — 2 confirmations (B, A), still pending.
4. Execute a separate fully-confirmed request that performs `DeleteMember { member: A }` — this removes A from `self.members` but does not touch R's confirmation set (R was requested by B, not A, so it is not in the `delete_member` cleanup filter).
5. As C: `confirm(request_R_id)` — `confirmations.len()` is now 3 (B, A, C) which is `>= num_confirmations (3)`, so `execute_request` runs the `Transfer`, even though A is no longer a valid member and only B and C (2 live members) actually authorized it at this point.

This demonstrates the request executing below the effective/live-member threshold, matching the "confirmations counted versus live members" custody binding described in the task rules.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
