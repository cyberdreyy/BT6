Stale confirmations from a removed multisig member still count toward execution threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`delete_member` / `DeleteKey` only purge confirmations on requests that the removed member *authored*, never confirmations that removed member left as a *confirmer* on requests authored by other members. `confirm()` then treats those stale confirmations as valid votes toward `num_confirmations`, letting a request execute (including a `Transfer`) with fewer genuinely-current-member approvals than the configured threshold. This is a direct structural analog to the reported bug: an entity whose authority has been revoked ("previous operator") retains the power to finalize an action because the contract never re-validates the recorded approval against the currently authoritative set.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` (lines 292-315) accepts a confirmation and checks only the *size* of the confirmation set: [1](#0-0) 
It never re-verifies that each account/key already present in `self.confirmations.get(&request_id)` is still `self.members.contains(...)`.

`delete_member` (lines 355-379) removes access keys/accounts from `self.members`, and cleans up outstanding *requests authored by* the removed member: [2](#0-1) 
but it does not scan `self.confirmations` for entries where the removed member appears as a *confirmer* of a request created by someone else. Those stale confirmations remain in the `HashSet<String>` for that request and continue to count toward `num_confirmations`.

The same pattern exists in v1, `multisig/src/lib.rs`: `DeleteKey` (lines 198-216) filters `requests` by `r.signer_pk == pk` (author) only, and removes that pk's own outstanding requests/confirmations sets, but never strips that pk's confirmation entries off other members' pending requests: [3](#0-2) 
and `confirm()` (lines 246-266) likewise only counts set size, never re-checking key liveness: [4](#0-3) 

The security property this contract is supposed to guarantee is "K of the *current* N members must approve." What actually gets checked is "K entries (possibly stale) exist in a HashSet." This is the exact same class of bug as the reported issue: authority recorded at one point in time (a confirmation, analogous to the "operator" snapshot) is never revoked when the underlying principal (member/key) is removed, and the contract later trusts that stale authority to finalize a state-changing, fund-moving action.

### Impact Explanation
This crosses the "multisig request executed below threshold" boundary explicitly called out as Critical impact: a `Transfer` (or `AddKey`/`FunctionCall`/`DeployContract`) request can be pushed to execution using confirmations that include a since-removed (e.g. compromised-key) member, meaning the number of currently-authorized approvers backing the executed request is strictly less than `num_confirmations`. This directly breaks the intended K-of-N custody binding: `count(distinct current members who approved) == num_confirmations` is violated; the contract instead enforces `count(recorded confirmation entries, live or stale) == num_confirmations`.

### Likelihood Explanation
This requires no exploitation of cryptography or timing tricks — it is a straightforward sequence available to any multisig operator's normal workflow: (1) a member confirms a pending request, (2) that member is later removed (e.g., precisely because their key was deemed compromised — the same trigger scenario as the original report), (3) the still-pending request is finished off by fewer *live* members than the threshold. Because member removal is a routine, expected operational action (rotating out a compromised or departing signer) while requests can remain outstanding for extended periods (up to the `active_requests_limit`/cooldown windows), this scenario is readily reachable in normal multisig lifecycle, not merely theoretical.

### Recommendation
When deleting a member/key, iterate over `self.confirmations` for *all* pending requests (not only those authored by the removed member) and remove that member's/key's confirmation entry from each set; if this drops any request below the number of confirmers needed, leave it pending (do not auto-fail, but do not let it silently execute later on stale votes). Alternatively/additionally, `confirm()` should re-validate, at confirmation-processing time, that every entry in the stored confirmation set for a request is still present in `self.members` before counting it toward `num_confirmations`, discarding stale entries and persisting the pruned set.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 4)`.
2. `A` calls `add_request_and_confirm` with a `Transfer{amount}` request targeting an attacker-controlled receiver — confirmations = `{A}` (1/4).
3. `B` calls `confirm(request_id)` — confirmations = `{A, B}` (2/4).
4. `C`'s key is flagged as compromised. The remaining members execute a `DeleteMember{member: C}` request (itself properly reaching 4 confirmations via a separate request) — `C` is removed from `self.members`, but the earlier `Transfer` request's confirmation set is untouched because that request was authored by `A`, not `C` (matches `delete_member` filter at `multisig2/src/lib.rs:362-366`, which only matches on `r.member == member`).

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);

        );

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
