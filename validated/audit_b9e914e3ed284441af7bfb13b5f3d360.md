### Title
Re-proposal of an already-signed block silently erases its own-tenure signature record, letting the signer double-sign a conflicting sibling - ([File: stacks-signer/src/v0/signer.rs])

### Summary
When a miner (or gossip) re-sends a `BlockProposal` for a `signer_signature_hash` the signer already tracks, `handle_block_proposal` decides whether to re-evaluate it via `should_reevaluate_block`/`should_reevaluate_reject_reason`. If the tracked `BlockInfo` carries a "re-evaluable" `reject_reason` (e.g. `ConnectivityIssues`, `NoSortitionView`, `NoSignerConsensus`, `ConsensusHashMismatch`, `Unknown`, or `ValidationFailed(NotFoundError/UnknownParent)`), the signer discards the entire prior `BlockInfo` and builds a brand-new one straight from the proposal: [1](#0-0) 

That new `BlockInfo::from(block_proposal)` resets `signed_self`, `signed_group`, `valid`, and `state` back to `Unprocessed`/`None`, and is written straight into `SignerDb` via `INSERT OR REPLACE` on the primary key `(reward_cycle, signer_signature_hash)`: [2](#0-1) [3](#0-2) 

For a window between that reset and any subsequent re-signing, the DB row for this exact block no longer shows `signed_self`/`signed_group`. Any other in-flight sibling proposal at the same height that queries `get_signed_conflicts` during its own pre-commit evaluation will not see this block as a live signature, because the query only matches rows where `signed_self IS NOT NULL OR signed_group IS NOT NULL`: [4](#0-3) 

This directly breaks the invariant the codebase itself documents as load-bearing: "Rejection, even global rejection, does NOT clear the commitment... a signature is a bearer instrument... a block we signed binds us to its tenure no matter what state it later fell to": [5](#0-4) 

### Finding Description
The block-lifecycle contract in this codebase is: once `signed_self` is set (`mark_locally_accepted`), it must never be cleared, because a signature is a public bearer instrument that other logic (`get_signed_conflicts`, `has_signed_block_in_tenure`) relies on to prevent the signer from later signing a conflicting sibling at the same height: [6](#0-5) 

The state machine explicitly allows `LocallyAccepted -> LocallyRejected` ("re-evaluated") without clearing `signed_self`, and `mark_locally_rejected` only sets `valid = Some(false)`: [7](#0-6) [8](#0-7) 

That is by design supposed to preserve the "commitment" even while locally re-rejecting a previously-signed block. However, `handle_block_proposal`'s re-proposal path does not go through `mark_locally_rejected`/`mark_locally_accepted` at all for a re-evaluable reject reason - it wholesale replaces the tracked `BlockInfo`, which the code itself flags with the comment "Creating a new proposal will overwrite any prior proposal info on the block if it exists, e.g. validity, signed_timestamps, etc.": [9](#0-8) 

The set of "re-evaluable" reasons deliberately includes transient/connectivity-style codes: [10](#0-9) 

`ConnectivityIssues` and `NoSignerConsensus` in particular are reachable both before and after a signature has been produced for a block (e.g. any DB/node lookup failure during a later re-check `check_block_against_signer_db_state`, or a protocol-version-consensus failure at proposal time). If any such path sets `reject_reason` on an already-signed `BlockInfo` and moves it to `LocallyRejected` (a transition the state machine explicitly permits and the docs describe as legitimate: `LocallyAccepted --> LocallyRejected : re-evaluated`), a subsequent re-proposal of the identical block (same `signer_signature_hash`, i.e. same miner slot re-broadcasting) will hit the `FRESH` branch and wipe the `signed_self`/`signed_group` timestamps from the DB row for that block, even though the signer's signature is already public and irrevocable.

### Impact Explanation
While the reset window is open, a competing sibling block at the same height (from the same tenure or an adjacent one, per `get_signed_conflicts`'s "any tenure" search) can pass the pre-commit conflict check that would otherwise have blocked it, because the query no longer finds the previously-signed block's row. The signer can then place a second, conflicting signature at the same height - the exact "signing an invalid/conflicting block" outcome the rules classify as Critical, since two signatures over sibling blocks from the same signer at the same height is a double-sign that undermines the one-per-height safety guarantee the whole pre-commit/conflict machinery (`get_signed_conflicts`, `conflict_still_blocks`) exists to enforce.

### Likelihood Explanation
Triggering requires only: (1) a block this signer already signed, (2) that block subsequently transitioning to `LocallyRejected` with a re-evaluable `reject_reason` while `signed_self` remains set (a transition the `BlockInfo::check_state` state machine and the project's own lifecycle documentation explicitly allow), and (3) the same miner slot (plus ordinary gossip of a re-proposal) re-sending the identical block proposal. All three conditions are reachable by a single, otherwise-honest miner replaying its own earlier proposal plus a normal fork/gossip race producing a sibling block - no majority collusion, no other signer's key, and no StackerDB-transport-level exploit is needed. The precise production call site that re-transitions an already-*signed* block to `LocallyRejected` with one of the re-evaluable reasons was not fully traced in this review (the paths inspected, e.g. `handle_block_validate_ok`'s recheck and the pre-commit `RECHECK` in `signer.rs:1345-1366`, both run *before* signing occurs on that pass), so this should be treated as a probable-but-not-fully-confirmed trigger path; the reset mechanism itself and its consequence for `get_signed_conflicts` is fully confirmed in code.

### Recommendation
Do not build a brand-new `BlockInfo` on re-proposal. Instead, preserve `signed_self`, `signed_group`, and `state` from the prior tracked `BlockInfo` when re-evaluating a re-evaluable rejection, only resetting `valid`/`reject_reason` and re-running the checks - mirroring the CVE's fix recommendation of only replacing security-relevant attributes when it is safe to do so, i.e. never discard a signature timestamp that other consistency checks (`get_signed_conflicts`) depend on.

### Proof of Concept
1. Signer signs block A at height H (`mark_locally_accepted`, `signed_self = Some(t)`).
2. A later re-check on A (e.g. `check_block_against_signer_db_state` erroring out due to a transient node/DB issue) calls `mark_locally_rejected()` and sets `reject_reason = Some(RejectReason::ConnectivityIssues(..))`, per `should_reevaluate_reject_reason` at [11](#0-10) . State is now `LocallyRejected`, but `signed_self` is still `Some(t)`.
3. The miner (same slot) re-broadcasts the identical `BlockProposal` for A. `should_reevaluate_block` finds `reject_reason` re-evaluable and returns `true` (`stacks-signer/src/v0/signer.rs:1560-1571`).
4. `handle_block_proposal` executes `let mut block_info = BlockInfo::from(block_proposal.clone());` (`stacks-signer/src/v0/signer.rs:1654`) and `insert_block` (`:1717-1719`), overwriting A's DB row with `signed_self = None`.
5. Before A is re-signed, a sibling block B at height H is proposed/gossiped. B's pre-commit evaluation calls `get_signed_conflicts(H, B_hash)` (`stacks-signer/src/signerdb.rs:1606-1625`), which no longer returns A (its `signed_self`/`signed_group` are `NULL`), so B's conflict guard is bypassed and the signer signs B - producing two signatures (A and B) over conflicting siblings at height H from the same signer.

            | RejectReason::NoSortitionView
            | RejectReason::ConnectivityIssues(_)
            | RejectReason::TestingDirective

    pub fn mark_locally_accepted(&mut self, group_signed: bool) -> Result<(), String> {
        if group_signed {
            self.signed_group.get_or_insert(get_epoch_time_secs());
        } else {
            self.valid = Some(true);
            self.approved_time.get_or_insert(get_epoch_time_secs());
            self.signed_self.get_or_insert(get_epoch_time_secs());
        }
        self.move_to(BlockState::LocallyAccepted)
    }

    /// Mark this block's signed group time if not already set and attempt to mark it as globally accepted.
    pub fn mark_globally_accepted(&mut self) -> Result<(), String> {
        self.signed_group.get_or_insert(get_epoch_time_secs());
        self.move_to(BlockState::GloballyAccepted)
    }

    /// Mark this block as invalid and attempt to mark it as locally rejected
    pub fn mark_locally_rejected(&mut self) -> Result<(), String> {
        self.valid = Some(false);

    pub fn get_signed_conflicts(
        &self,
        height: u64,
        excluded_signer_signature_hash: &Sha512Trunc256Sum,
    ) -> Result<Vec<SignedConflictInfo>, DBError> {
        let query = "SELECT b.consensus_hash, b.signer_signature_hash, b.stacks_height, b.state,
                MAX(COALESCE(b.signed_self, 0), COALESCE(b.signed_group, 0)) AS last_endorsed,
                st.superseded_by_consensus_hash, st.superseded_by_burn_block_hash
            FROM blocks b
            LEFT JOIN superseded_tenures st ON st.consensus_hash = b.consensus_hash
            WHERE (b.signed_self IS NOT NULL OR b.signed_group IS NOT NULL)
                AND b.stacks_height >= ?1
                AND b.signer_signature_hash != ?2
            ORDER BY b.stacks_height DESC";
        let args = params![
            u64_to_sql(height)?,
            excluded_signer_signature_hash.to_string(),
        ];
        query_rows(&self.db, query, args)
    }
