## Analog Vulnerability Found

### Title
Missing mint-owner validation in token RPC handlers allows misreporting of token balances via mismatched Mint account - (File: `rpc/src/parsed_token_accounts.rs`, `rpc/src/rpc.rs`)

### Summary
The DODO bug pattern is: a privileged/trusted field (`zrc20`) is special-cased (`_ETH_ADDRESS_`) to skip a required validation (`msg.value` check), while a second, attacker-controlled field (the decoded `message.targetZRC20`) is used downstream without being cross-checked against the first, letting an attacker make the contract act on a mismatched, unvalidated reference. The same class of bug — trusting an attacker-influenced reference field without validating it against the actual, authoritative account state — is reachable in Agave's token-balance RPC/decoding path.

### Finding Description
`get_mint_owner_and_additional_data` in `rpc/src/parsed_token_accounts.rs` resolves a `mint` pubkey to its owning program and decimals/extension config, but never verifies that the returned mint account's owner matches the token-program that actually owns the *token account* being priced: [1](#0-0) 

This function is called from `get_token_account_balance`, where the `mint` value is taken directly from the raw, attacker-influenceable bytes of a token account looked up by pubkey (`token_account.base.mint`), with no check that this mint's owner equals `account.owner()` (the token account's own program): [2](#0-1) 

The same unchecked pattern recurs in `get_token_largest_accounts` and `get_token_program_id_and_mint` (used by `getTokenAccountsByOwner`/`getTokenAccountsByDelegate`), and in `get_parsed_token_account`/`get_parsed_token_accounts` (used for `jsonParsed` encoding in `getAccountInfo`/`getProgramAccounts`), all of which call `get_mint_owner_and_additional_data`/`get_additional_mint_data` without an owner-consistency check: [3](#0-2) [4](#0-3) 

`get_additional_mint_data`/`StateWithExtensions::<Mint>::unpack` parses raw bytes as a `Mint` with no owner check at all: [5](#0-4) [6](#0-5) 

Notably, the codebase itself demonstrates the *correct* pattern elsewhere: `SvmTokenInfo::unpack_token_account` in `svm/src/transaction_balances.rs`, used for computing pre/post token balances in transaction metadata, explicitly requires `*mint_account.owner() != program_id` to fail before trusting the mint's decimals: [7](#0-6) 

The RPC/account-decoder token-balance path omits this exact check.

The `token_amount_to_ui_amount_v3` function then computes the displayed UI amount purely from the attacker-influenced decimals/extension config: [8](#0-7) 

An attacker who can create/own an account of arbitrary bytes shaped like a `Mint` (with, e.g., an extreme `decimals` value, or a `ScaledUiAmountConfig`/`InterestBearingConfig` extension with an arbitrary multiplier) can get that account referenced as the `mint` field of a real token account (or simply pass its own pubkey as the `mint` parameter to `getTokenSupply`/`getTokenLargestAccounts`), causing the RPC layer to compute and return a wildly wrong `UiTokenAmount` (`ui_amount`, `ui_amount_string`, even `NaN`/`Infinity` via `10_usize.checked_pow(decimals)` overflow) for a real, correctly-amounted token account, without any transaction or consensus-affecting artifact — purely at the RPC decode/serve layer.

### Impact Explanation
This falls under the explicitly accepted "decoder panic and misreporting" impact category: a single unprivileged, low-rate JSON-RPC call (`getTokenAccountBalance`, `getTokenSupply`, `getTokenLargestAccounts`, or `getAccountInfo`/`getProgramAccounts` with `jsonParsed` encoding) can be made to return a UI-displayed token amount/decimals that do not correspond to the actual token-program-validated mint of the account, misleading any client, wallet, or downstream service relying on the RPC response for balance/supply display. It does not corrupt validator state or consensus, but the wrong-data output is a direct decoder-misreporting bug reachable by any unprivileged RPC caller with a single call.

### Likelihood Explanation
High likelihood of reachability: no special privileges are required — any user can call `getTokenAccountBalance`/`getTokenSupply`/`getTokenLargestAccounts` with an arbitrary pubkey, and can create/own an account whose data happens to unpack as a `Mint` (this only requires the byte layout to match, not program ownership, since `StateWithExtensions::<Mint>::unpack` performs no ownership check). Constructing a real token account under the legitimate token program that embeds such a mismatched `mint` reference is a matter of a couple of setup transactions.

### Recommendation
Add an owner-consistency check analogous to the one already used in `svm/src/transaction_balances.rs::SvmTokenInfo::unpack_token_account`: after resolving a mint account, verify `mint_account.owner() == token_account.owner()` (the actual program that owns the token account being priced) before using its decimals/extension configuration in `get_mint_owner_and_additional_data`, `get_token_account_balance`, `get_token_supply`, `get_token_largest_accounts`, `get_token_program_id_and_mint`, and `get_parsed_token_account`/`get_parsed_token_accounts`. Reject or error out (as `Invalid param`) when the mint's owner does not match the expected token program.

### Proof of Concept
1. Create account `M` owned by any program (or even the attacker's own program) whose raw data is length/layout-valid as an SPL `Mint` (e.g., `decimals = 200`, or with a `ScaledUiAmountConfig`/`InterestBearingConfig` extension using an attacker-chosen multiplier), i.e., something `StateWithExtensions::<Mint>::unpack` in `account-decoder/src/parse_token.rs:24-34` will accept.
2. Create a legitimate SPL Token account `T` owned by `spl_token_interface::id()` whose embedded `mint` field is set to `M`'s pubkey, with a real `amount` (e.g., 1_000_000).
3. Call the JSON-RPC method `getTokenAccountBalance` with `T`'s pubkey — `rpc/src/rpc.rs:2013-2035` reads `token_account.base.mint` (= `M`), calls `get_mint_owner_and_additional_data(bank, M)` (`rpc/src/parsed_token_accounts.rs:92-108`), which unpacks `M`'s attacker-chosen decimals/extension config with no owner check, then feeds it into `token_amount_to_ui_amount_v3` (`account-decoder/src/parse_token.rs:125-164`).
4. Observe the returned `UiTokenAmount.ui_amount`/`ui_amount_string` reflects the attacker-chosen decimals/multiplier rather than any value validated against `T`'s actual owning token program, demonstrating misreporting of a real account's balance for any RPC caller.

    mint: &Pubkey,

        Ok((*mint_account.owner(), mint_data))
    }

/// id and optional Mint
fn get_token_program_id_and_mint(
    bank: &Bank,
    token_account_filter: TokenAccountsFilter,
) -> Result<(Pubkey, Option<Pubkey>)> {
    match token_account_filter {
        TokenAccountsFilter::Mint(mint) => {
            let (mint_owner, _) = get_mint_owner_and_additional_data(bank, &mint)?;
            if !is_known_spl_token_id(&mint_owner) {
                return Err(Error::invalid_params(
                    "Invalid param: not a Token mint".to_string(),
                ));
            }
            Ok((mint_owner, Some(mint)))
        }
        TokenAccountsFilter::ProgramId(program_id) => {
            if is_known_spl_token_id(&program_id) {
                Ok((program_id, None))
            } else {
                Err(Error::invalid_params(
                    "Invalid param: unrecognized Token program id".to_string(),
                ))
            }
        }
    }
}

pub fn token_amount_to_ui_amount_v3(
    amount: u64,
    additional_data: &SplTokenAdditionalDataV2,
) -> UiTokenAmount {
    let decimals = additional_data.decimals;
    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =
        additional_data.interest_bearing_config
    {
        let ui_amount_string =
            interest_bearing_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else if let Some((scaled_ui_amount_config, unix_timestamp)) =
        additional_data.scaled_ui_amount_config
    {
        let ui_amount_string =
            scaled_ui_amount_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else {
        let ui_amount = 10_usize
            .checked_pow(decimals as u32)
            .map(|dividend| amount as f64 / dividend as f64);
        (ui_amount, real_number_string_trimmed(amount, decimals))
    };
    UiTokenAmount {
        ui_amount,
        decimals,
        amount: amount.to_string(),
        ui_amount_string,
    }
}
