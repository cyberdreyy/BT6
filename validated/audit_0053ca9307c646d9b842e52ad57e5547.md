### Title
Loss-adjusted withdraw receipt escapes its haircut and is paid at par when the user makes a new withdraw request — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
A use-after-free analog: `lastWithdrawRequest[_user]` is reused both as the "wait one epoch" marker and as the lookup key into `lossRecoveryPriceByEpoch`. When a user whose receipt was loss-adjusted in epoch N makes a *new* withdraw request in a later epoch, `lastWithdrawRequest[_user]` is overwritten before the old receipt is cleared (its per-epoch entry in `withdrawsRequestsByEpoch` is never deleted). The stale loss-adjusted receipt is then silently re-classified as a fully-funded par receipt and paid 1:1, letting the attacker escape the realized loss and drain funds reserved for honest claimants.

### Finding Description
In `requestWithdraw` (`IdleCreditVault.sol:282`), `lastWithdrawRequest[_user] = currentEpoch` is written on every request, and the amount is appended to both `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` (lines 292-293).

When `stopEpochWithDuration`/`collectWithdrawFunds` underfunds pending receipts, `lossRecoveryPriceByEpoch[epochNumber]` is set (lines 411-421) — the epoch when `collectWithdrawFunds` runs equals the request epoch of the affected receipts, i.e. `lastWithdrawRequest` of those users.

On claim, `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (lines 789-794). Then `_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]` at par (lines 338-349).

Attack sequence:

1. Epoch N ends; attacker calls `requestWithdraw` → `lastWithdrawRequest = N`, `withdrawsRequestsByEpoch[user][N] = X`, `withdrawsRequests[user] = X`.
2. Manager runs `stopEpochWithDuration(_lossAmount)`; borrower funds only `pendingToFund < pendingBasis`; `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[N] = r < RECOVERY_FULL` and pulls only `X*r/RECOVERY_FULL` worth for the attacker's receipt share.
3. Epoch N+1 runs and ends normally. The attacker calls `requestWithdraw` again with a small amount in epoch N+1 (or the buffer epoch): `lastWithdrawRequest[user] = N+1`, `withdrawsRequests[user] = X + Y`.
4. Epoch N+2 begins (`epochNumber > lastWithdrawRequest`). Attacker calls `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[N+1] == 0` → returns 0. The epoch-N entry `withdrawsRequestsByEpoch[user][N]` is never cleared.
   - `_claimFundedWithdrawRequest` passes its gate (`epochNumber > N+1`), computes `amount = X + Y`, burns `X + Y` receipt tokens and transfers `X + Y` underlying at par.

The attacker received `X` at par while the vault only collected `X * r / RECOVERY_FULL` for that receipt. The shortfall `X * (1 - r/RECOVERY_FULL)` is paid out of underlying belonging to other funded claimants / the strategy, i.e. the realized loss is socialized onto honest users instead of the receipt holder.

The same overwrite applies to the APR0 path (`_requestWithdrawApr0` sets `principalEpoch` once; `lastWithdrawRequest` is still overwritten by the second request), and to any sequence of loss epochs: only the *latest* request epoch's haircut is ever applied, all earlier unclaimed loss-adjusted receipts are paid at par.

### Impact Explanation
Direct theft / insolvency: each unclaimed loss-adjusted receipt can be upgraded to a par claim by spending a dust-sized second request. Attacker profit equals `receiptAmount * (1 - lossRecoveryPrice)`, paid from vault underlying reserved for other users' funded claims, permanently impairing solvency for remaining claimants. No privileged misbehavior required — only the honest manager executing a normal `stopEpochWithDuration` loss and epochs continuing.

### Likelihood Explanation
Requires a `stopEpochWithDuration` loss event (borrower underfunding), which is a designed operating mode, and a user who holds a receipt in that epoch and places another withdraw request — a normal, permitted action (the code comments explicitly note users may request again instead of claiming). The attack is deterministic once the loss epoch exists and costs only gas plus a small second receipt.

### Recommendation
Track loss-adjusted claims per epoch rather than via the mutable `lastWithdrawRequest` pointer. E.g., iterate/queue the user's loss-epoch entries, or store a per-user set of loss epochs (or a `firstLossEpoch`/bitmap) so `claimWithdrawRequest` clears *all* epochs with `lossRecoveryPriceByEpoch != 0` before paying the remainder at par. Alternatively, block `requestWithdraw` while the user has an unclaimed loss-adjusted receipt, or apply `lossRecoveryPriceByEpoch` lookups to every epoch present in `withdrawsRequestsByEpoch[user]` at claim time.

### Proof of Concept
Foundry fork PoC outline (test harness exists in `test/foundry/IdleCreditVault.t.sol`, e.g. `testClaimWithdrawRequestEpochRunning` and loss tests using `stopEpoch(0, interest)` with underfunded borrower):

```solidity
function testLossReceiptEscapesHaircut() external {
    // setup: deposit AA for attacker, start epoch 0, stop epoch 0 normally
    uint256 minted = idleCDO.depositAA(10_000 * ONE_SCALE);

    // epoch 0 buffer: attacker requests withdraw of X
    uint256 req1 = cdoEpoch.requestWithdraw(minted / 2, address(AAtranche)); // epochNumber == 0

    // epoch 1 runs, borrower underfunds -> stopEpochWithDuration(loss)
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    // deal borrower only partial funds so collectWithdrawFunds gets _amount < pendingBasis
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    deal(underlying, borrower, pending / 2);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(lossAmount, fundedAmount); // sets lossRecoveryPriceByEpoch[1]

    // attacker does NOT claim; instead requests another withdraw in the post-loss buffer
    uint256 req2 = cdoEpoch.requestWithdraw(1, address(AAtranche)); // lastWithdrawRequest overwritten

    // run and stop one more clean epoch so epochNumber > lastWithdrawRequest
    _startEpochAndCheckPrices(2);
    _stopEpochAndCheckPrices(2, initialApr, _expectedFundsEndEpoch());

    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    // BUG: paid req1 + req2 at par; expected req1 * lossRecoveryPriceByEpoch[1]/RECOVERY_FULL + req2
    assertGt(underlying.balanceOf(address(this)) - balPre,
             req1 * strategy.lossRecoveryPriceByEpoch(1) / RECOVERY_FULL + req2);
}
```

Key assertions to include: `strategy.withdrawsRequestsByEpoch(attacker, 1)` remains non-zero after the claim (receipt state never cleared), and the vault's residual underlying is insufficient for remaining claimants. Note: exact helper names (`stopEpochWithDuration` signature, loss plumbing) should be matched against `IdleCDOEpochVariant` during PoC authoring; the state transition above follows directly from `requestWithdraw`/`_claimLossAdjustedWithdrawRequest`/`_claimFundedWithdrawRequest` logic cited.

Confidence caveat: I verified the claim-path logic and the `lastWithdrawRequest` overwrite directly in `IdleCreditVault.sol` (lines 271-350, 411-430, 786-837); I did not get to read `IdleCDOEpochVariant.stopEpochWithDuration`/`requestWithdraw` to confirm there is no CDO-side guard blocking a second request after a loss epoch — the code comments ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch") and the per-epoch mapping design strongly suggest none exists, but this should be confirmed when writing the PoC.
