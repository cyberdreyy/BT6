### Title
Stale confirmations from a deleted multisig member remain counted toward the confirmation threshold, allowing execution below the true live-member quorum - (`multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`delete_member` (multisig2) and the `DeleteKey` action (multisig, v1) only purge requests and confirmation sets for requests that the removed member **created**. They never scrub the removed member's public key/account entry out of the `confirmations` set of *other* still-pending requests that member had merely confirmed. `confirm()` later counts `confirmations.len()` against `num_confirmations` without re-validating that every entry in the set is still a current member, so a stale confirmation from an already-removed member can push a request over the threshold and trigger execution with fewer live approvers than `num_confirmations` requires. This is the same bug class as the reported `GuardianRecoveryValidator.onUninstall` failing to clear `pendingRecoveryData`: a piece of "identity/approval" state tied to a party is not purged when that party's grant is revoked, letting stale state be used after the revocation to bypass an intended check.

### Finding Description
Binding that should hold: `count(confirmations[R]) == count(live members who confirmed R)`.

- `add_request`/`confirm` in `multisig2/src/lib.rs` insert the confirming member's string key into `self.confirmations[request_id]`: [1](#0-0) 
- `delete_member` removes a departing member from `self.members` and deletes only the requests **it authored** (`r.member == member`), along with their confirmation sets; it does **not** scan other pending requests' `confirmations` sets to strip the departing member's stale entry: [2](#0-1) 
- `confirm` simply checks the confirming key hasn't already confirmed and compares `confirmations.len() as u32 + 1 >= self.num_confirmations` to decide whether to execute — it never re-validates that all keys already present in `confirmations` are still members of `self.members`: [3](#0-2) 

The v1 `multisig/src/lib.rs` has the identical pattern: `DeleteKey` only cleans requests where `r.signer_pk == pk` (the requester), leaving that key's confirmations on other pending requests untouched, and `confirm` counts `confirmations.len()` without filtering out keys no longer known to the contract: [4](#0-3) [5](#0-4) 

Because a member's *approval* (confirmation) is a form of authorization state analogous to `pendingRecoveryData` in the external report, and it is not cleared when the granting party (membership) is revoked, an approval collected before removal is still honored after removal — precisely the "trusted state not cleared on revocation" defect.

### Impact Explanation
This crosses the multisig threshold boundary explicitly in scope ("a multisig request executed below threshold"), which is a Critical-severity impact: a `Transfer`, `AddKey`/`AddMember`, `FunctionCall`, or `DeployContract` request can execute with fewer genuinely live/authorized confirmations than `num_confirmations` mandates, because a removed member's stale confirmation is silently counted. This directly weakens the security guarantee the multisig is built to provide (funds moved or privileged actions taken without the required quorum of current signers).

### Likelihood Explanation
Likelihood is realistic in normal contract operation, not a contrived edge case:
1. Member `B` confirms request `R` created by member `A` (confirmations = {A, B}), but the threshold is not yet met.
2. Members later approve removing `B` via a separate `DeleteMember`/`DeleteKey` request. Because `R`'s creator (`r.member`) is `A`, not `B`, `delete_member`/`DeleteKey` does not touch `R`'s stored confirmations, so `B`'s stale approval remains in `confirmations[R]`.
3. Any remaining live member confirms `R`, reaching `confirmations.len() >= num_confirmations` and triggering execution — even though the number of currently valid members who approved `R` is one less than required.
No malicious node, redeploy, or foundation privilege is needed — this is achievable purely through the multisig's own documented `add_request`/`confirm`/`DeleteMember` (or `DeleteKey`) flow with ordinary member actions.

### Recommendation
When removing a member (`delete_member` in `multisig2/src/lib.rs`, `DeleteKey` action in `multisig/src/lib.rs`), iterate over **all** pending requests (not just those the removed member authored) and strip the removed member's entry from each request's `confirmations` set (or, more defensively, revalidate `confirmations` against current `self.members` at the time of counting in `confirm`, treating stale keys as non-counting). Additionally consider recomputing/decrementing progress atomically so a request cannot flip to "confirmed" purely due to a removed member's historical approval.

### Proof of Concept
Using `multisig2::MultiSigContract` (num_confirmations = 3, members = {A, B, C, D}):
1. `A` calls `add_request_and_confirm(R)` → `confirmations[R] = {A}`.
2. `B` calls `confirm(R)` → `confirmations[R] = {A, B}` (2 < 3, not yet executed).
3. Members separately create and confirm a `DeleteMember { member: B }` request (via `add_request_and_confirm` + enough confirmations) — this calls `delete_member(promise, B)`. Because `B` never authored `R` (`r.member == A`), `R`'s confirmation set is left untouched: it still equals `{A, B}` even though `B` has been removed from `self.members`. See [6](#0-5) .
4. `C` (still a live member) calls `confirm(R)`. `confirmations[R].len() + 1 = 3 >= num_confirmations (3)` in [7](#0-6) , so `execute_request(R)` runs — yet only `A` and `C` are still valid members who actually approved; `B`'s stale, revoked approval was decisive in reaching quorum. The request (e.g., a `Transfer`) is executed below the intended live-member threshold.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));

        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );

            let request = self.remove_request(request_id);

        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);

        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
