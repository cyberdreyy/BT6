### Title
Builder-controlled `fee_recipient` in `ExecutionPayloadBid` is never checked against the proposer's committed `SignedProposerPreferences` at the consensus layer, allowing a builder payment to be misdirected - (File: specs/gloas/beacon-chain.md)

### Summary
The Gloas builder-payment flow lets a proposer publish a `SignedProposerPreferences` message declaring the `fee_recipient` that should receive any builder payment for a given slot [1](#0-0) . Builders are supposed to copy that address into `bid.fee_recipient` when constructing a bid [2](#0-1) . However, the state-transition function that actually admits a bid on-chain, `process_execution_payload_bid`, never checks `bid.fee_recipient` against anything — it only validates builder activity/version, balance, blob limits, slot, and hash linkage before unconditionally caching the bid and creating a `BuilderPendingPayment` to `bid.fee_recipient` [3](#0-2) . The only place a `fee_recipient` mismatch is detected is the gossip-validation function `validate_execution_payload_bid_gossip`, and there it is merely an `IGNORE` (drop from relay), not a `REJECT`, and it is not consulted by block processing at all [4](#0-3) . Because the validator spec explicitly allows a proposer to obtain bids "by other off-protocol means" [5](#0-4)  and the bid-acceptance checklist a proposer is told to apply before including a bid also omits any `fee_recipient` comparison [6](#0-5) , nothing in the canonical state-transition function stops a builder from setting `bid.fee_recipient` to an address of its own choosing rather than the one the proposer committed to via `SignedProposerPreferences`.

### Finding Description
This is the structural analog of the reported bug: in the SAM contract, the artist can silently redirect a fee owed to a third party (the affiliate) to itself, because the contract does not enforce that the fee recipient matches what was represented off-chain/at commitment time — an invalid proof simply defaults the money to the artist instead of reverting. Here, the equivalent breaks the equality "a builder payment goes to the fee recipient the proposer committed to receive it at": `SignedProposerPreferences.fee_recipient` is the commitment (signed by the proposer, gossiped, and meant to bind subsequent bids), yet `process_execution_payload_bid` — the only consensus-enforced gate — never re-derives or checks this value [7](#0-6) . Any `BuilderIndex` that can construct a validly signed bid (i.e. any active, funded builder) can set `bid.fee_recipient` to an address it controls. The pending payment created in `state.builder_pending_payments` and later settled via `settle_builder_payment` (which eventually credits the recorded `fee_recipient`) is thus paid out on the strength of the builder's own say-so, not the proposer's preference, with no assertion tying the two together anywhere in `process_execution_payload_bid`, `process_operations`, or the payment-settlement path referenced from `apply_parent_execution_payload`.

### Impact Explanation
This falls under "a builder payment or withdrawal misdirected" (High impact bucket). A proposer who has broadcast `SignedProposerPreferences` naming their intended payout address (e.g., a pool/staking-service contract) can have their builder payment routed to an address the builder chose instead, purely because the state-transition function accepts any `fee_recipient` value in the bid. Unlike a proposer knowingly self-building with `BUILDER_INDEX_SELF_BUILD` (where `value` must be zero and there is no payment to misdirect), this affects the non-self-build path where real Gwei value (`bid.value`) is at stake and is paid to whichever address the *builder* — an unprivileged, non-consensus-critical party relative to that specific payment — decided to write into the bid.

### Likelihood Explanation
The check that would prevent this exists only as an `IGNORE`-level gossip heuristic used by relaying nodes to decide whether to forward a bid on the P2P network [8](#0-7) ; it is not part of block validity. Because bids may legitimately be obtained "by other off-protocol means" [5](#0-4) , and the reference `process_execution_payload_bid` never re-derives the expected `fee_recipient` from the current `SignedProposerPreferences`, a builder using any direct channel to a proposer (private relay, direct RPC, or simply omitting the gossip step) can supply a bid with an arbitrary `fee_recipient` and have it accepted by every spec-following node during block processing, with no coalition, no equivocation, and no client bug required — the spec text itself omits the check.

### Recommendation
Add an explicit assertion inside `process_execution_payload_bid` (specs/gloas/beacon-chain.md) that `bid.fee_recipient` equals the `fee_recipient` from the `SignedProposerPreferences` most recently accepted for `(bid.slot, dependent_root)` for the proposer of `bid.slot` — mirroring the currently gossip-only `[IGNORE] bid's fee recipient matches proposer's preference` check, but promoted to a state-transition-enforced `assert` (i.e., a consensus-level `REJECT`), analogous to how the SAM fix now reverts on a bad affiliate proof rather than silently defaulting the fee elsewhere.

### Proof of Concept
1. Proposer `P` broadcasts a signed `ProposerPreferences{proposal_slot=S, fee_recipient=A}` [9](#0-8) .
2. A builder `B` privately (off the `execution_payload_bid` gossip topic, so the mismatch `IGNORE` rule never fires) sends `P` a validly signed `ExecutionPayloadBid{slot=S, fee_recipient=Z, value=V, builder_index=B, ...}` where `Z != A`.
3. `P` includes this bid in its block per the acceptance checklist in `specs/gloas/validator.md` [6](#0-5) , none of whose conditions reference `fee_recipient` correctness.
4. `process_execution_payload_bid` runs during state transition, passes all its assertions (builder active, version, balance, blob count, slot, hash linkage) with no check on `fee_recipient`, and records `BuilderPendingPayment{withdrawal=BuilderPendingWithdrawal{fee_recipient=Z, amount=V, builder_index=B}}` [10](#0-9) .
5. On settlement, `V` Gwei is eventually paid to `Z`, not `A`, even though every spec-following node accepted the block as valid — the payment was misdirected from the address the proposer committed to.

def get_signed_proposer_preferences(
    store: Store,
    state: BeaconState,
    head_root: Root,
    proposal_slot: Slot,
    validator_index: ValidatorIndex,
    fee_recipient: ExecutionAddress,
    target_gas_limit: Uint64,
    privkey: int,
) -> SignedProposerPreferences:
    proposal_epoch = compute_epoch_at_slot(proposal_slot)
    dependent_root = get_shuffling_dependent_root(store, head_root, proposal_epoch)
    preferences = ProposerPreferences(
        dependent_root=dependent_root,
        proposal_slot=proposal_slot,
        validator_index=validator_index,
        fee_recipient=fee_recipient,
        target_gas_limit=target_gas_limit,
    )
    domain = get_domain(state, DOMAIN_PROPOSER_PREFERENCES, proposal_epoch)
    signing_root = compute_signing_root(preferences, domain)
    signature = bls.Sign(privkey, signing_root)
    return SignedProposerPreferences(message=preferences, signature=signature)

```python
def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid
