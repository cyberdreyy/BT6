### Title
Unbounded per-slot signature scan in `getSignaturesForAddress` allows single-call cost amplification independent of requested `limit` - (File: `ledger/src/blockstore.rs`)

### Summary
`Blockstore::get_confirmed_signatures_for_address2` — the backing implementation of the `getSignaturesForAddress` JSON-RPC method — delegates to `find_address_signatures_for_slot`, which retrieves **every** signature for a given address within a single slot before the caller ever applies the requested `limit`. This mirrors the report's root cause: no per-unit ceiling exists at the point where cost is actually incurred, so a data structure that a caller controls (transactions from/to one address packed into one slot) can be inflated cheaply and later forces disproportionate work on any single query touching that slot, regardless of how small a `limit` the RPC caller requests.

### Finding Description
`get_signatures_for_address` in `rpc/src/rpc.rs` accepts a caller-supplied `limit` and forwards it straight to `Blockstore::get_confirmed_signatures_for_address2`: [1](#0-0) 

Inside the blockstore, the very first step — used both to seed the initial slot and whenever the starting slot needs its own signatures pulled — is `find_address_signatures_for_slot`: [2](#0-1) 

This function has **no `limit` parameter at all**. It iterates the `address_signatures_cf` column family from the start of the given slot forward and only stops when it reaches a different slot or a different address — i.e., it always collects the *entire* set of signatures for `(address, slot)` before returning. The caller (`get_confirmed_signatures_for_address2`) only applies `.take(limit)` afterward, on the already-fully-materialized result: [3](#0-2) 

Because a single slot's transaction inclusion is controlled by whoever submits transactions to the cluster (a completely unprivileged action — anyone can send many small, cheap transactions from/to the same address so they land in the same slot, up to normal block capacity limits), an attacker can inflate the number of `(address, slot, index, signature)` entries for one address in one slot. Any subsequent `getSignaturesForAddress` RPC call that must resolve signatures starting at (or landing on) that slot — even one requesting `limit: 1` — pays the full cost of scanning and collecting every entry for that address in that slot before the result is truncated.

### Impact Explanation
This is analogous to the reported griefing pattern: the attacker's "many minimum-liquidity positions" become "many minimum-cost transactions from one address packed into a single slot," and the victim's "close positions one-by-one" cost becomes the RPC node's forced full-slot signature scan on every subsequent lookup touching that slot, independent of the caller's requested `limit`. The cost scales with attacker-controlled input on a read path (`getSignaturesForAddress`), not with the caller's declared work size, which is the core "unbounded cost for a single low-rate call" pattern called out in scope.

The severity is bounded by the fact that a single slot's total transaction count is itself capped by normal block-processing limits (compute/entry limits), so this is not an unbounded-in-principle DoS, but it is a real amplification: a `limit=1` request can be made to do O(all address signatures in that slot) work instead of O(1) work, imposing unnecessary I/O and CPU on the RPC-serving validator for legitimate, low-declared-cost queries.

### Likelihood Explanation
Reachable via the unprivileged, publicly documented `getSignaturesForAddress` RPC method with only one call needed (no repeated polling), so it falls within scope per the rules (single-call cost amplification). No special account/mint setup or privileged validator/operator role is required — any user who can send ordinary transactions to/from a single address within one slot can create the condition, and subsequent RPC consumers (including the attacker themselves or unrelated third parties who also query that address's history) trigger the expensive path.

### Recommendation
Thread the `limit` (or a hard per-slot cap) into `find_address_signatures_for_slot` so the column-family iterator breaks out as soon as `limit` entries have been collected, rather than always materializing the complete set of an address's signatures for the slot. Apply the same early-exit discipline to the backward `iterator.next()` loop that follows it, which already benefits from a `while address_signatures.len() < limit` bound — `find_address_signatures_for_slot` should receive equivalent treatment so the two code paths behave consistently with respect to the caller-declared limit.

### Proof of Concept
1. From an unprivileged account, submit a large number of low-cost transactions (e.g., minimal system transfers) all referencing the same target address, arranged (via normal transaction submission/retry timing) to land within a single slot, up to the block's transaction capacity.
2. Issue `getSignaturesForAddress` for that target address with `limit: 1` and a `before` signature that resolves to (or falls within) the inflated slot.
3. Observe that `get_confirmed_signatures_for_address2` → `find_address_signatures_for_slot` scans and collects every one of the address's signatures for that slot — proportional to the attacker-inserted count — before the result is truncated to the requested `limit`, even though the caller asked for only 1 result.     // Returns all signatures for an address in a particular slot, regardless of whether that slot
    // has been rooted. The transactions will be ordered by their occurrence in the block
    fn find_address_signatures_for_slot(
        &self,
        pubkey: Pubkey,
        slot: Slot,
    ) -> Result<Vec<(Slot, Signature, u32)>> {
        let (lock, lowest_available_slot) = self.ensure_lowest_cleanup_slot();
        let mut signatures: Vec<(Slot, Signature, u32)> = vec![];
        if slot < lowest_available_slot {
            return Ok(signatures);
        }
        let index_iterator = self.address_signatures_cf.iter(IteratorMode::From(
            (
                pubkey,
                slot.max(lowest_available_slot),
                0,
                Signature::default(),
            ),
            IteratorDirection::Forward,
        ))?;
        for ((address, transaction_slot, transaction_index, signature), _) in index_iterator {
            if transaction_slot > slot || address != pubkey {
                break;
            }
            signatures.push((transaction_slot, signature, transaction_index));
        }
        drop(lock);
        Ok(signatures)
    }
