## Analysis

The `state-manipulation` contract's `replace` and `clean` exports are raw, unauthenticated NEAR entrypoints with **no `predecessor_account_id` check, no owner check, and no key-based gating whatsoever**. [1](#0-0) 

```rust
#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    ...
    let input = input().unwrap();
    let args: ReplaceInput = serde_json::from_slice(&input).unwrap();
    for (key, value) in args.entries {
        storage_write(&base64::decode(key).unwrap(), &base64::decode(value).unwrap());
    }
}

#[cfg(feature = "clean")]
#[no_mangle]
pub fn clean() {
    ...
    for key in args.keys {
        storage_remove(&base64::decode(key).unwrap());
    }
}
```

Neither function reads `env::predecessor_account_id()`, compares it to the account owner, or checks any access key permission — there is simply no gate before `storage_write`/`storage_remove` execute. On NEAR, any account (including a fully unprivileged attacker's own account) can send a `FunctionCall` action to any `receiver_id` and any public method name; calling a change method never requires possessing a key on the receiver account. This is confirmed by the README's own usage description, which shows `replace`/`clean` invoked as ordinary change methods with no special permission model. [2](#0-1) 

### Binding claimed to be broken
`predecessor_account_id_of(replace call) == operator_account_id` — i.e., only the operator driving the legitimate migration should be able to write into the account's storage while this utility contract is deployed. Tracing the code shows this equality is **never checked at all**: any `predecessor_account_id` is accepted.

### Exploit path
1. An operator (e.g., NEAR Foundation, or the lockup account owner) deploys `state-manipulation` (built with `replace`/`clean` features) onto a victim account that currently holds the `lockup` contract's storage layout (e.g., temporarily replacing the lockup contract during a migration).
2. The operator issues a `replace` call intended to fix/migrate specific keys (e.g., `lockup_information`, `vesting_information`, `owner_account_id`, `termination_withdrawn_tokens`).
3. Because `replace`/`clean` have zero authorization, an unprivileged attacker can, in the same block, submit their own `replace` call to the same account with attacker-chosen key/value pairs (e.g., overwriting `owner_account_id` to their own account, or zeroing `termination_withdrawn_tokens`/adjusting `vesting_information` to unlock funds early).
4. Storage writes are last-write-wins within NEAR's per-account state; whichever transaction is applied last in the block (or later, since nothing stops the attacker from simply re-calling `replace` again once they observe the operator's transaction) determines the final state.
5. Once the operator redeploys the real `lockup` contract binary on top of this manipulated state, the lockup logic will operate on attacker-controlled values — e.g., an attacker-controlled owner, or manipulated vesting/termination fields — enabling withdrawal of funds that were never entitled to them.

None of the standard guards (`assert_owner`, `assert_self()`, `is_promise_success()`, `assert_one_yocto()`, key checks) exist in this contract to prevent this, because the contract was written to be a bare storage-editing utility with the (unstated, and here unenforced) assumption that it would only ever be reachable by a trusted operator holding exclusive access. That assumption is not encoded anywhere in the code.

### Impact
Critical — arbitrary, unauthenticated overwrite of any storage key/value on the account hosting this contract, while it is deployed. Against a lockup account mid-migration, this allows an attacker to inject values (owner, vesting/termination fields, staking pool references) that later let them or an accomplice extract or redirect the locked account's NEAR. This is repeatable for any account/migration window where this contract is live, and the blast radius is the full balance of the victim account.

### Likelihood
The only precondition is that an operator deploys this contract to a victim account and that the account is externally observable as running this code with an in-flight legitimate `replace`/`clean` transaction — both are visible on-chain (mempool/block explorer), and the attacker only needs to submit their own ordinary `FunctionCall` transaction, which any unprivileged NEAR account can do at negligible cost.

### Recommendation
Add an explicit owner/authorization check (e.g., require `env::predecessor_account_id() == env::current_account_id()`, restricting calls to a full-access key holder of the account itself, or gate via a stored authorized-caller field set at deploy time) before any `storage_write`/`storage_remove` in `replace`/`clean`.

### Proof of Concept sketch
A `near-workspaces` test deploying `state_manipulation.wasm` to a lockup-shaped account, then issuing two concurrent `replace` transactions in the same block — one from the "operator" account and one from an unrelated "attacker" account — asserting that after both transactions land, the final state reflects the attacker's key/value pairs (proving no ownership gate exists) rather than being rejected. ### Title
Unauthenticated `replace`/`clean` allow any account to overwrite storage during a migration, letting an attacker race and win control of a lockup's state - (File: state-manipulation/src/lib.rs)

### Summary
The `replace` and `clean` exports perform raw `storage_write`/`storage_remove` calls with no `predecessor_account_id` or owner check at all. Any unprivileged account can call these methods on a victim account that has this utility deployed (e.g., mid-migration on a lockup), racing or overriding the operator's own migration writes to seize control of the account's storage.

### Finding Description
The broken binding is `predecessor_account_id_of(replace_call) == operator_account_id`, which the code never enforces — `replace()`/`clean()` blindly decode base64 keys/values from `input()` and write/remove them via `storage_write`/`storage_remove` with no gate. [1](#0-0) 
Because NEAR permits any account to call a public change method on any other account without holding that account's keys, an attacker can submit their own `replace` transaction against the same victim account concurrently with the operator's legitimate migration transaction. Whichever write lands last determines the final storage state, letting the attacker inject arbitrary key/value pairs (e.g., rewriting `owner_account_id`, `vesting_information`, or `termination_withdrawn_tokens` fields) that the subsequently-redeployed `lockup` contract will trust. No existing guard (`assert_owner`, `assert_self`, key checks) is present anywhere in this file to stop it.

### Impact Explanation
Direct, unauthenticated manipulation of an account's persistent storage while this utility is deployed enables rewriting ownership or vesting/termination accounting fields on a lockup account, which the real `lockup` contract will later trust once redeployed — enabling theft or early release of locked NEAR. This is Critical impact and repeatable against any account/migration window using this tool.

### Likelihood Explanation
Only precondition is that the target account currently runs this contract (visible on-chain) and has a pending operator `replace`/`clean` call; the attacker needs nothing but an ordinary funded NEAR account to submit a competing `FunctionCall`, at negligible cost, fully repeatable.

### Recommendation
Add a strict caller check (e.g. `require!(env::predecessor_account_id() == env::current_account_id())` or an authorized-caller allowlist persisted before the utility contract is even deployed) before performing any `storage_write`/`storage_remove` in `replace`/`clean`.

### Proof of Concept
A `near-workspaces` `#[tokio::test]` deploying `res/state_manipulation.wasm` to a test account, then dispatching two `replace` calls from two different signer accounts (`operator` and `attacker`) within the same block/transaction batch, asserting via `contract.view_state` that the attacker's key/value pair is present in final state despite not being the deploying/operator account — demonstrating the missing authorization check equality `predecessor_account_id == operator_account_id` never holds and is never checked.

            .iter()
            .map(|(a, b)| (base64::encode(a), base64::encode(b)))

        // Replace generated keys and values

            .call(&worker, "replace")
            .args_json(&serde_json::json!({ "entries": &b64_bytes }))?

            .transact()

        for (k, v) in bytes {

        contract
            .call(&worker, "clean")
            .args_json(&serde_json::json!({ "keys": &keys }))?
            .max_gas()
            .transact()
            .await?;

        assert!(state_items.is_empty());

        Ok(())

# State Manipulation contract

This contract has been designed to put key value pairs into storage with `replace` and clear key/value pairs with `clean` from an account's storage.

Deploy this contract into the account that already has another contract deployed to it.
This contract on call `clean` will remove any items of the state specified (keys should be specified in base64). When compiled with `replace` feature, `replace` method can be called with an array of key/value tuple pairs to insert into state.

## Parameters

JSON format for `clean`:

```json
{"keys":["<base64 encoded key byte string>", "...", "..."]}
```

JSON format for `replace`:
```json
{"entries":[["<base64 key byte string>", "<base64 value byte string>"], ["...", "..."]]}
```
