### Title
ProgrammableBorrower `onStopEpoch` early-return skips epoch-state reset, double-counting buffered interest and leaving stale reservation/accounting active - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower.onStopEpoch` has an early `return true` when the ERC4626 vault cannot cover the cash shortfall (`shortfall > _currentVaultAssets()`), letting `IdleCDOEpochVariant._stopEpoch` proceed to `transferFrom` and potentially succeed using the borrower's remaining on-hand balance / allowance. This early return bypasses the reset block that clears `bufferedVaultDelta`, `bufferInterest`, `epochPendingWithdraws`, `bufferStartVaultAssets` and `epochAccountingActive`. Analogous to the reference bug (a timestamp not zeroed on refresh so it is re-derived next time), these stale fields are re-consumed at the next epoch boundary instead of being reset, producing double-counted pool interest and a stale withdraw reservation.

### Finding Description
In `onStopEpoch`: [1](#0-0) 

When `shortfall > _currentVaultAssets()` the function returns `true` at line 245 *before* reaching: [2](#0-1) 

`IdleCDOEpochVariant._stopEpoch` treats `true` as success and calls `getFundsFromBorrower`, which can still succeed — the borrower is a normal EOA/managed wallet that may hold un-deposited underlying plus its standing `transferFrom` allowance, so the pull can be funded even though the vault sleeve alone could not: [3](#0-2) 

Consequences of the skipped reset:

1. `bufferInterest` is never cleared. It is only zeroed at line 260 (or in `onDefault`). On the next stop, `totalInterestDueNow()` still includes it: [4](#0-3) 
Since `settleBorrowerInterest` only settles the contractual `borrowerInterestAccrued`, the phantom `bufferInterest` component of `totalInterestDueNow` is minted as strategy tokens to the CDO (minted-interest mode) or demanded again in cash, i.e., the same interest is charged to the borrower/pool twice.
2. `epochPendingWithdraws` keeps its old value, so `availableToBorrow()` continues to subtract a reservation for withdraw requests the CDO has already settled: [5](#0-4) 
3. `epochAccountingActive` stays `true` across the buffer, so `borrow()` remains callable when the epoch is logically over, and repayments during the buffer take the `_depositToVault(totalRepaidAssets, ...)` epoch branch instead of the `bufferInterest` branch, further corrupting the next epoch's baseline.
4. `bufferStartVaultAssets` retains the baseline from the previous successful stop, so `onStartEpoch` recomputes `bufferedVaultDelta` against a stale anchor: [6](#0-5) 

### Impact Explanation
The double-counted `bufferInterest` / stale `bufferedVaultDelta` flow into `totalInterestDueNow()`, which `IdleCDOEpochVariant` uses to mint strategy tokens or pull cash at `stopEpoch`. In minted mode, `_strategy.mintStrategyTokens(_grossInterest)` inflates the CDO's strategy-token balance by interest that was already realized in a prior epoch — unbacked price inflation that is paid out to whoever redeems first and materializes as insolvency for later claimants. Any tranche holder (unprivileged attacker) profits simply by holding/claiming through the following epoch. The stale `epochPendingWithdraws` also lets the pool believe funds are reserved that are no longer earmarked, distorting `expectedEpochInterest`.

### Likelihood Explanation
Preconditions: programmable-borrower mode, the real borrower having drawn principal (normal revolving-credit usage — the borrower need not be malicious), and enough drawn that `amountRequired - onHand > vault assets` while the borrower still holds other approved cash so the CDO's `transferFrom` succeeds. These are all honest-actor conditions reachable in ordinary operation whenever the facility is heavily drawn and the borrower tops up its wallet to cover the stop; no privileged misbehavior or oracle manipulation is needed.

### Recommendation
Move the state-reset block (`bufferedVaultDelta = 0; bufferInterest = 0; bufferStartVaultAssets = _currentVaultAssets(); epochPendingWithdraws = 0; epochAccountingActive = false`) so it executes on every `return true` path in `onStopEpoch` — i.e., reset before the early return at line 245, exactly as the original report recommends zeroing the stale field on each refresh. Alternatively return `false` when the vault cannot cover the shortfall so the default path runs `onDefault()` and clears the state consistently.

### Proof of Concept
Foundry fork sketch:

```solidity
// Setup: IdleCDOEpochVariant with isProgrammableBorrower, minted interest mode,
// an ERC4626 vault, borrower with principal drawn.
function testStaleBufferInterestDoubleCount() public {
    // Epoch 1: borrower borrows most of the facility during the epoch
    vm.prank(manager); cdo.startEpoch();
    vm.prank(borrower); programmableBorrower.borrow(borrowAmount); // leaves vault nearly empty

    // Mid-epoch borrower repays some interest -> lands in epoch accounting
    // Epoch 1 ends; buffer period: borrower repays remaining interest -> bufferInterest > 0
    // Epoch 2 starts (onStartEpoch): bufferInterest stays non-zero
    vm.warp(...); vm.prank(manager); cdo.startEpoch();

    // At stopEpoch 2, onStopEpoch hits `shortfall > _currentVaultAssets()` (borrower drawn),
    // returns true early WITHOUT clearing bufferInterest / epochPendingWithdraws /
    // epochAccountingActive. CDO's transferFrom succeeds from borrower's wallet.
    deal(underlying, borrower, amountRequired);
    vm.warp(cdo.epochEndDate() + 1);
    vm.prank(manager); cdo.stopEpoch(newApr, 0);

    // bufferInterest and epochAccountingActive are still set
    assertGt(programmableBorrower.bufferInterest(), 0);
    assertTrue(programmableBorrower.epochAccountingActive());

    // Next epoch: totalInterestDueNow() re-includes the same bufferInterest,
    // and minted _grossInterest is inflated -> CDO strategy tokens minted unbacked.
    vm.prank(manager); cdo.startEpoch();
    uint256 due = programmableBorrower.totalInterestDueNow();
    assertGt(due, contractualInterestOnly); // includes previously-consumed bufferInterest
}
```

Note: exact quantities depend on vault share price and borrower draw size; the invariant violation (stale `bufferInterest`/`epochAccountingActive`/`epochPendingWithdraws` surviving a successful stop) is deterministic whenever the early-`return true` branch is taken and the CDO pull subsequently succeeds.
