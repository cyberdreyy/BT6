### Title
`resumeServices` starts containers without verifying job/project label ownership - (File: executors/docker/services.go)

### Summary
`executor.resumeServices` inspects and starts any container ID it is given via `e.dockerConn.ContainerInspect` / `e.dockerConn.ContainerStart`, then adds it to `e.services` and `e.temporary`, without ever checking that the container's labels (e.g. `com.gitlab.gitlab-runner.project.id`, job ID) match the currently-running job/executor. This is a genuine missing authorization check inside the function itself.

### Finding Description
Looking at `executors/docker/services.go` lines 106-138, `resumeServices(serviceIDs []string)` loops over the supplied IDs and does: [1](#0-0) 

At no point does it call `e.labeler` or compare `svcInspect.Config.Labels` against the executor's own project/job/runner-token labels the way `createFromServiceDefinition`/`createService` do when creating containers with `e.labeler.Labels(...)`. Every other container-creation path in this file (e.g. `createConfigForServiceHealthCheckContainer` at line 273-285) tags containers with `e.labeler.Labels(...)`, implying the codebase has an established labeling/ownership convention that `resumeServices` simply does not enforce on the *read* side.

Because there is no ownership check, `resumeServices` will happily inspect, start, and register (into `e.services`/`e.temporary`) *any* container ID reachable via the Docker API, regardless of which job or project created it.

However, I was unable to locate in the indexed portion of the repository the exact call site(s) that invoke `resumeServices` with the list of `serviceIDs`, nor how that list is populated (e.g., from a persisted job-resumption state file, a CI-side variable, or purely runner/host-controlled state). My searches turned up only test files (`executors/docker/services_test.go`) and tangential matches (`resume`-related keywords in `executors/internal/autoscaler/executor.go`, `executors/docker/docker_command.go`, `common/build.go`) but the index did not surface the concrete code that builds and passes the `serviceIDs` slice into `resumeServices`. Without confirming that this input is genuinely attacker-controlled (as opposed to being derived from trusted server-side/runner-side state that an unprivileged pipeline author cannot influence), I cannot fully validate the "attacker-controlled input" precondition required by the audit rules.

### Impact Explanation
If (and only if) the caller populates `serviceIDs` from any value that a pipeline author can influence or that is otherwise guessable/enumerable (e.g., short container IDs, sequential naming, or a resumption manifest that isn't cryptographically bound to the specific build), an attacker could get the runner to attach to and expose networking/log/IP information of a container belonging to a different job or project — a cross-tenant container hijack as described. This would be a serious isolation violation matching the stated scoped impact.

### Likelihood Explanation
Not fully determinable from the code paths I could inspect. The missing ownership check in `resumeServices` is confirmed and would need to be fixed regardless (defense-in-depth), but I could not confirm the concrete, currently-reachable Go path by which an unprivileged user supplies or influences `serviceIDs` for a build retry/restore. Confirming exploitability requires tracing the caller in `executors/docker/docker.go`/`docker_command.go` and the persistence/transport mechanism for the "job resumption" feature, which the available index did not surface in enough detail.

### Recommendation
Regardless of how `serviceIDs` are sourced, `resumeServices` should defensively verify container ownership before calling `ContainerStart`: inspect `svcInspect.Config.Labels` and reject/skip any container whose labels don't match the current job's expected labels (project ID, runner token/ID, job ID) as produced by `e.labeler.Labels(...)` elsewhere in the file. This closes the gap even if the ID source is later found to be attacker-influenced.

func (e *executor) resumeServices(serviceIDs []string) error {
	for _, svcID := range serviceIDs {
		svcInspect, err := e.dockerConn.ContainerInspect(e.Context, svcID)
		if err != nil {
			return fmt.Errorf("service container %s not found: %w", svcID, err)
		}
		if err := e.dockerConn.ContainerStart(e.Context, svcInspect.ID, client.ContainerStartOptions{}); err != nil {
			return fmt.Errorf("service container %s failed to start: %w", svcInspect.ID, err)
		}
		ip, ports, err := e.getContainerIPAndExposedPorts(svcInspect.ID)
		if err != nil {
			return fmt.Errorf("getting service container %s IP and ports: %w", svcInspect.ID, err)
		}
		e.services = append(e.services, &serviceInfo{
			ID:    svcInspect.ID,
			Name:  svcInspect.Name,
			IP:    ip,
			Ports: ports,
		})
	}
