Confirmed: there is no bounds check anywhere in the codebase on `operator_fee_scalar`/`operator_fee_constant` when applied from L1 `ConfigUpdate` logs. This matches the FRAX analog closely enough to report.

### Title
L1 SystemConfig owner can set an unbounded operator fee scalar/constant, making L2 transactions unpayable for users - (File: `crates/common/genesis/src/updates/operator_fee.rs`)

### Summary
The OP-stack `SystemConfig` contract owner on L1 (a protocol admin the Base contest scope treats as "RESTRICTED", analogous to the FRAX admin in the referenced report) can emit a `ConfigUpdate(OperatorFee)` log that sets `operator_fee_scalar` to `u32::MAX` and `operator_fee_constant` to `u64::MAX`. Base's derivation pipeline decodes and applies these values with no upper-bound validation, and the value is subsequently used verbatim by every L2 transaction's fee accounting, making per-transaction fees arbitrarily large.

### Finding Description
`OperatorFeeUpdate::apply` copies the decoded `operator_fee_scalar`/`operator_fee_constant` straight into `SystemConfig` with no range check: [1](#0-0) 

The decode step (`TryFrom<&SystemConfigLog>`) only validates ABI-encoding shape (pointer/length), not the numeric magnitude of the scalar/constant: [2](#0-1) 

This is the L2 analog of FRAX's unguarded `setRedemptionFee`: the `SystemConfig` owner is an external, "RESTRICTED" governance actor whose write is trusted by Base's derivation pipeline and applied without any sanity bound, exactly matching the in-scope bug class "derivation of attacker-written L1 deposit and system-config data."

The unbounded value then flows directly into the operator-fee charge formula used for every non-deposit transaction: [3](#0-2) 

`SystemConfig.operator_fee_scalar`/`operator_fee_constant` are raw `u32`/`u64` fields with no documented or enforced ceiling: [4](#0-3) 

Once the epoch advances, the derivation pipeline (`update_with_receipts`, called from `StatefulAttributesBuilder::prepare_payload_attributes`) applies the malicious update from L1 receipts into the working `SystemConfig`, and it is baked into every subsequent L1-info deposit and used by the operator-fee math for every L2 transaction in that epoch: [5](#0-4) [6](#0-5) 

With an extreme scalar/constant, `operator_fee_charge`/`operator_fee_charge_inner` returns a cost so large that essentially no account can pre-pay it, and `ensure_can_pay_fees`/`validate_against_state_and_deduct_caller`-style balance checks will reject virtually every standard transaction: [7](#0-6) 

### Impact Explanation
If the SystemConfig owner sets the operator fee scalar/constant to extreme values, users on Base become unable to submit ordinary transactions because they cannot cover the inflated upfront fee requirement — effectively freezing their ability to move funds or interact with the chain, mirroring the "users unable to withdraw / loss of assets for the victim" impact of the original FRAX finding. Because the value is applied uniformly and immediately at the next epoch boundary with no cap, this is a chain-wide denial of transaction service rather than an isolated user loss, which is arguably more severe than the FRAX analog.

### Likelihood Explanation
This requires only a single legitimately-signed L1 `ConfigUpdate` transaction from the `SystemConfig` owner — no code exploit, race condition, or additional privilege is needed once that admin key is used maliciously or negligently. Per the contest's own framing (admins of integrated/underlying protocols are "RESTRICTED", i.e., issues stemming from their unilateral, unbounded actions are in-scope), this is directly analogous to the FRAX `setRedemptionFee` issue: no additional trust assumption beyond "the L1 governance/owner key is used to push this specific unbounded parameter" is required.

### Recommendation
Enforce a sane upper bound (and possibly a rate-of-change limit) on `operator_fee_scalar` and `operator_fee_constant` when applying `OperatorFeeUpdate`, rejecting or clamping updates that would make the operator fee charge exceed a documented maximum multiple of the L2 base fee. Alternatively/additionally, document this admin-key risk explicitly for node operators and users, and consider adding a protocol-level ceiling in `operator_fee_charge_inner` itself so that no single `SystemConfig` update can render transactions unpayable chain-wide.

### Proof of Concept
1. SystemConfig owner (L1) emits `ConfigUpdate(OperatorFee)` with `operator_fee_scalar = u32::MAX` and `operator_fee_constant = u64::MAX`, using the same encoding validated by `enqueue_operator_fee_update`/`OperatorFeeUpdate::try_from`: [8](#0-7) 
2. At the next L2 epoch boundary, `update_with_receipts` applies the update into the derivation pipeline's `SystemConfig` with no bound check, and it is encoded into the L1-info deposit for every subsequent L2 block, as exercised by the existing propagation test: [9](#0-8) 
3. `operator_fee_charge_inner` computes an astronomically large operator fee per transaction using the unbounded scalar/constant: [10](#0-9) 
4. Every standard (non-deposit) transaction subsequently fails the upfront-fee affordability check, effectively freezing user transactions on Base until a new, sane `OperatorFee` update is posted on L1.

impl TryFrom<&SystemConfigLog> for OperatorFeeUpdate {
    type Error = OperatorFeeUpdateError;

    fn try_from(log: &SystemConfigLog) -> Result<Self, Self::Error> {
        let LogData { data, .. } = &log.log.data;

        let validated = UpdateDataValidator::validate(data).map_err(|e| match e {
            ValidationError::InvalidDataLen(_expected, actual) => {
                OperatorFeeUpdateError::InvalidDataLen(actual)
            }
            ValidationError::PointerDecodingError => OperatorFeeUpdateError::PointerDecodingError,
            ValidationError::InvalidDataPointer(pointer) => {
                OperatorFeeUpdateError::InvalidDataPointer(pointer)
            }
            ValidationError::LengthDecodingError => OperatorFeeUpdateError::LengthDecodingError,
            ValidationError::InvalidDataLength(length) => {
                OperatorFeeUpdateError::InvalidDataLength(length)
            }
        })?;

        // The operator fee scalar and constant are
        // packed into a single u256 as follows:
        //
        // | Bytes    | Actual Size | Variable |
        // |----------|-------------|----------|
        // | 0 .. 24  | uint32      | scalar   |
        // | 24 .. 32 | uint64      | constant |
        // |----------|-------------|----------|

        let payload = validated.payload();
        let mut be_bytes = [0u8; 4];
        be_bytes[0..4].copy_from_slice(&payload[20..24]);
        let operator_fee_scalar = u32::from_be_bytes(be_bytes);

        let mut be_bytes = [0u8; 8];
        be_bytes[0..8].copy_from_slice(&payload[24..32]);
        let operator_fee_constant = u64::from_be_bytes(be_bytes);

        Ok(Self { operator_fee_scalar, operator_fee_constant })
    }

    /// Calculates the operator fee for a given `gas` amount.
    ///
    /// Missing scalars fall back to zero to match the execution path during the
    /// txpool bootstrap window before the first L1 attributes deposit.
    pub fn operator_fee_charge_inner(&self, gas: U256, upgrade: BaseUpgrade) -> U256 {
        let operator_fee_scalar = self.operator_fee_scalar.unwrap_or_default();
        let operator_fee_constant = self.operator_fee_constant.unwrap_or_default();

        let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
            gas.saturating_mul(operator_fee_scalar)
                .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
        } else {
            gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
        };
        product.saturating_add(operator_fee_constant)
    }

    fn ensure_can_pay_fees(
        host: &mut Evm<'_, BaseEvmTypes>,
        envelope: &BaseTxEnvelope,
        caller: Address,
        l1_fee: U256,
        operator_fee: U256,
    ) -> HandlerResult<()> {
        let Some(tx) = envelope.as_standard() else {
            return Ok(());
        };
        if !host.feature(EvmFeatures::FEE_CHARGE) || !host.feature(EvmFeatures::BALANCE_CHECK) {
            return Ok(());
        }
        let required = U256::from(tx.gas_limit())
            .saturating_mul(U256::from(tx.max_fee_per_gas()))
            .saturating_add(tx.value())
            .saturating_add(l1_fee)
            .saturating_add(operator_fee);
        let balance =
            host.state_mut().account(&caller, false).map_err(HandlerError::Fatal)?.balance();
        if balance < required {
            return Err(HandlerError::InsufficientFunds);
        }
        Ok(())
    }

            address: l1_sys_cfg_addr,
            data: LogData::new_unchecked(
                vec![
                    SystemConfigUpdate::TOPIC,
                    SystemConfigUpdate::EVENT_VERSION_0,
                    B256::from(update_type),
                ],

            ),
        });
