### Title
Integer underflow in RLP list-length peek during Merkle-Patricia trie node decoding - ([File: crates/proof/mpt/src/util.rs])

### Summary
The mutt/NeoMutt CVE-2018-14353 bug class is: a length value taken from attacker-influenced input is used in a subtraction without first validating it against the size of the buffer it is measured against, producing an integer underflow. The Base fault-proof MPT decoder contains the same pattern in `rlp_list_element_length`, which computes `buf.len() - header.payload_length` where `header.payload_length` is parsed straight from untrusted trie-node bytes with no prior check that it does not exceed `buf.len()`.

### Finding Description
`rlp_list_element_length` decodes an RLP header and then immediately subtracts the header's `payload_length` from the remaining buffer length to compute a stopping point for iterating list elements: [1](#0-0) 

`payload_length` here comes directly from `Header::decode(buf)`, which only parses the RLP length prefix bytes; it performs no validation that the declared payload fits within the remaining bytes of `buf` (unlike other decoders in the same codebase, e.g. `decode_calls`, which explicitly checks `if buf.len() < header.payload_length { return Err(InputTooShort) }` before proceeding: [2](#0-1) ).

This function is invoked from `TrieNode::decode`, the core RLP decoder for Merkle-Patricia trie nodes used by the fault-proof program to interpret preimage data supplied during trie traversal/proof verification: [3](#0-2) 

If a malicious or malformed trie-node preimage declares a list `payload_length` larger than the actual bytes present, `buf.len() - header.payload_length` underflows. In a debug build this panics (node halt / fault-proof program abort); in a release build (`overflow-checks` disabled, the default release profile) it wraps to a value near `usize::MAX`, causing the `while buf.len() > len_after_consume` loop to terminate immediately and report `list_element_length == 0`. That value is then used in `TrieNode::decode`'s `match list_length { BRANCH_LIST_LENGTH => ..., LEAF_OR_EXTENSION_LIST_LENGTH => ..., _ => Err(UnexpectedLength) }` dispatch, so a crafted preimage can force the decoder to reject a node it should have accepted, or — depending on how callers react to the resulting error/mis-decode — corrupt the trie walk used to compute the state/withdrawal root during dispute resolution.

### Impact Explanation
The fault-proof program's correctness is security-critical: an attacker who can influence the raw preimage bytes fed into `TrieNode::decode` during a dispute-game move can trigger this underflow to make the program panic (halting execution of the proof program, denial of service for that dispute) or to derive a wrong/garbage output for the RLP peek, which feeds into trie proof verification and ultimately the provable output root computed by the fault-proof program. Either outcome falls into the "node halt" / "wrong provable output root" impact categories for this reachable surface.

### Likelihood Explanation
The `TrieNode::decode` path is reached whenever the fault-proof program processes MPT node preimages during dispute-game execution, which is directly influenced by data a dispute-game participant can submit/supply as preimages. No privileged position is required — any participant able to submit preimage data reachable by trie traversal can attempt to encode a header with an inflated `payload_length`.

### Recommendation
Add an explicit bounds check in `rlp_list_element_length` before computing `len_after_consume`, e.g. `if header.payload_length > buf.len() { return Err(alloy_rlp::Error::InputTooShort); }`, mirroring the pattern already used elsewhere in the codebase (e.g. `decode_calls`).

### Proof of Concept
Construct a byte buffer whose first bytes decode via `alloy_rlp::Header::decode` as `{ list: true, payload_length: N }` where `N` exceeds the buffer's remaining length after the header (e.g. an RLP list header claiming a very large payload length followed by only a few payload bytes), then pass it to `TrieNode::decode`. This buffer reaches `rlp_list_element_length`, and `buf.len() - header.payload_length` underflows before any bounds check occurs.

**Uncertainty**: I could not directly inspect the `alloy_rlp::Header::decode` implementation (external dependency) to confirm with full certainty that it never itself validates `payload_length` against the buffer length in all code paths reachable here; the analysis is based on the fact that other in-repo callers add their own explicit `buf.len() < header.payload_length` guard, implying `Header::decode` alone does not enforce this invariant.

pub(crate) fn rlp_list_element_length(buf: &mut &[u8]) -> alloy_rlp::Result<usize> {
    let header = Header::decode(buf)?;
    if !header.list {
        return Err(alloy_rlp::Error::UnexpectedString);
    }
    let len_after_consume = buf.len() - header.payload_length;

    let mut list_element_length = 0;
    while buf.len() > len_after_consume {
        let header = Header::decode(buf)?;
        buf.advance(header.payload_length);
        list_element_length += 1;
    }
    Ok(list_element_length)
}
