### Title
Global JWT replay-protection cache keyed only by `jti` (not scoped to workflow/signer) enables cross-tenant DoS via jti collision - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks `h.jwtCache.isReplay(claims.ID)` and later `h.jwtCache.recordUsage(claims.ID)` using a single global `map[string]time.Time` keyed solely by the JWT's `jti` claim, with no binding to `workflowID` or signer address. Because `VerifyRequestJWT` only requires `jti` to be non-empty (it does not enforce UUID format or freshness beyond the map check), any attacker authorized on any workflow can register an arbitrary `jti` value in the shared cache, causing rejection of any other tenant's subsequent legitimate request that happens to use the same `jti` value, for the duration of the configured replay window.

### Finding Description
The cache is defined and used as follows: [1](#0-0) [2](#0-1) 

`isReplay`/`recordUsage` operate purely on the `jti` string with no workflow or signer dimension: [3](#0-2) 

`VerifyRequestJWT` (called before the replay check) validates the ECDSA signature, digest binding to the request content, `exp`/`iat`, but only requires `jti` be non-empty — it does not require it be a fresh, unpredictable UUID: [4](#0-3) 

The reference client helper `CreateRequestJWT` generates `jti` via `uuid.New().String()` (client-side, before signing): [5](#0-4) 

However, nothing in `VerifyRequestJWT` or `Authorize` enforces that callers must use this helper or a random UUID — an attacker who is authorized for *any* workflow (i.e., possesses a signer key registered in `authorizedKeys` for at least one workflow) can hand-craft a JWT with a `digest` matching their own request and any chosen `jti` string, sign it with their own key, and call `workflows.execute` against the gateway. `Authorize` will succeed and call `recordUsage(claims.ID)`, inserting that `jti` into the single global map shared by all workflows/tenants on that `WorkflowMetadataHandler` instance. Any subsequent request — including one for a completely unrelated workflow and signer — bearing the same `jti` value will be rejected by `isReplay` at line 87, purely because the string matches, with no consideration of `workflowID` or signer.

This breaks the intended isolation of replay-protection state across tenants: the cache is a single shared namespace instead of being scoped per-workflow (or per-workflow+signer). The existing test suite only demonstrates same-workflow, same-signer replay behavior and does not test cross-workflow isolation: [6](#0-5) 

### Impact Explanation
An attacker who is legitimately authorized to submit requests for workflow X can cause denial-of-service against unrelated workflow Y by pre-registering a `jti` value in the shared cache that the victim's client will also use. This is a cross-tenant DoS affecting request availability, matching Chainlink's "Denial of Service" / cross-user interference impact class rather than fund loss or key disclosure. The scoped impact is limited to blocking a specific request per `jti` collision (not sustained node-wide DoS), and requires the colliding value to actually be used by the victim.

### Likelihood Explanation
The precondition is that the attacker is authorized on at least one workflow (a low bar, satisfiable by any legitimate workflow owner) and can craft an arbitrary signed JWT (they control their own private key and JWT payload construction, since nothing restricts payload construction to the `CreateRequestJWT` helper). The remaining precondition — that the victim's JWT for an unrelated workflow shares the same `jti` — is unlikely under the reference implementation because `CreateRequestJWT` generates `jti` as a fresh random UUIDv4 (122 bits of entropy), making blind collision computationally infeasible. The attack becomes practically feasible only if: (a) a client/SDK implementation generates non-random or low-entropy/predictable `jti` values (e.g., counters, fixed IDs, request-ID-derived values), or (b) an attacker can otherwise learn/predict a specific victim's upcoming `jti` and race to register it first. Given the standard SDK path uses random UUIDs, exploitability in practice is low but the underlying architectural flaw (missing per-workflow/signer scoping of the replay cache) is a genuine isolation defect independent of `jti` entropy assumptions made by any particular client.

### Recommendation
Scope the JWT replay cache key by `(workflowID, signerAddress, jti)` or at minimum `(workflowID, jti)` instead of `jti` alone, e.g. by using a composite key such as `workflowID + "|" + signer.Hex() + "|" + claims.ID` in `jwtReplayCache.cache`. This ensures replay protection state cannot be poisoned across workflow/tenant boundaries even if `jti` values collide.

### Proof of Concept
Add a table/unit test in `workflow_metadata_handler_test.go`:
1. Set up `handler.authorizedKeys` with two workflows, `workflowA` authorized for `signerA` and `workflowB` authorized for `signerB` (as in `createTestWorkflowMetadataHandler`).
2. Attacker crafts a JWT for `workflowA` with `req` digest matching their own request and an attacker-chosen `jti = "shared-jti"`, signs with `signerA`'s key, calls `handler.Authorize(workflowA, tokenA, reqA)` — expect success (`require.NoError`).
3. Simulate "victim" building an unrelated JWT for `workflowB` (different request/digest, different signer `signerB`) but using the same `jti = "shared-jti"` (representing the collision precondition), call `handler.Authorize(workflowB, tokenB, reqB)`.
4. Assert this second call fails with `"JWT token has already been used"` even though `workflowID` and signer differ from the first call — demonstrating the cache is global and not tenant/workflow-isolated, in contrast to the expected behavior where step 3 should succeed since it is a distinct workflow/signer context.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
