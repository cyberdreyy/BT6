### Title
Missing fee-vs-amount validation in `createDstEscrow` allows unprotected subtraction underflow (permanent revert) in `EscrowDst._withdraw` - (File: `contracts/BaseEscrowFactory.sol`, `contracts/EscrowDst.sol`)

### Summary
`EscrowDst._withdraw` computes `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` [1](#0-0)  without any prior validation that `integratorFeeAmount + protocolFeeAmount < immutables.amount`. On the source side, the equivalent check exists — `_postInteraction` explicitly reverts with `InvalidFeeAmounts` if `integratorFeeAmount + protocolFeeAmount >= takingAmount` [2](#0-1)  — but `createDstEscrow`, which is called directly and independently by the taker (not derived from the validated source-side computation), performs no equivalent check [3](#0-2) .

### Finding Description
`createDstEscrow` accepts an arbitrary `IBaseEscrow.Immutables calldata dstImmutables` from the caller (the taker/resolver), including the `parameters` blob that encodes `protocolFeeAmount` and `integratorFeeAmount` [3](#0-2) . The contract validates only that `msg.value` matches `safetyDeposit` (+ `amount` for native token) — there is no check tying `protocolFeeAmount + integratorFeeAmount` to `dstImmutables.amount`. This is unlike `_postInteraction` on the source escrow path, which enforces `integratorFeeAmount + protocolFeeAmount >= takingAmount` must revert [4](#0-3) .

Because Solidity 0.8.23 uses checked arithmetic, if `integratorFeeAmount + protocolFeeAmount > immutables.amount` for a deployed `EscrowDst`, every call to `_withdraw` (triggered via `withdraw` or `publicWithdraw`) will revert on `immutables.amount - integratorFeeAmount - protocolFeeAmount` [5](#0-4) . This is the same root cause pattern as the external report: a subtraction between a fee-like value and a base value with no upstream bound-check, causing the affected computation path to be permanently broken/unusable.

Since `withdraw`/`publicWithdraw` are the *only* functions that deliver destination assets to the maker, and they are gated by `onlyValidImmutables` (which recomputes the CREATE2 address from the exact same `Immutables` struct, including the malformed `parameters`) [6](#0-5) , the maker can never retrieve the destination-chain funds from this escrow once fees are configured this way. The only functioning exit is `cancel()`, which — after the `DstCancellation` timelock — returns `immutables.amount` and the safety deposit back to the **taker**, not the maker [7](#0-6) .

### Impact Explanation
This falls under the Medium bucket ("smart contract unable to operate because required token/native balances can be broken by an unprivileged actor") and potentially High ("temporary freezing of funds during the live swap lifecycle"): a taker (unprivileged actor, not owner/governance) can, by supplying malformed but self-consistent fee parameters when calling `createDstEscrow`, deploy a destination escrow that can never pay out to the maker via `withdraw`/`publicWithdraw`, freezing the maker's expected destination assets for the entire withdrawal window and diverting them to the taker via `cancel()` once the cancellation timelock passes. This requires the off-chain relayer/maker verification step to fail to catch the malformed fee parameters before releasing the secret, which is a real risk since `createDstEscrow` performs no on-chain sanity check that would otherwise make this state unreachable.

### Likelihood Explanation
Low-to-medium likelihood: exploiting this to steal maker value from the swap flow depends on external coordination (the maker or relayer must proceed with revealing the secret despite a malformed dst escrow), which is generally expected to be checked off-chain before secret release. However, the on-chain contract itself provides no defense-in-depth check that the source escrow enforces, making the invariant asymmetric and reachable by any unprivileged taker calling `createDstEscrow` directly.

### Recommendation
Add the same guard used in `_postInteraction` to `createDstEscrow`:
```solidity
uint256 protocolFeeAmount = dstImmutables.protocolFeeAmount();
uint256 integratorFeeAmount = dstImmutables.integratorFeeAmount();
if (protocolFeeAmount + integratorFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();
```
before deploying the escrow, so that a taker cannot create a destination escrow whose `_withdraw` fee subtraction is guaranteed to revert.

### Proof of Concept
1. Taker calls `createDstEscrow` with `dstImmutables.amount = X` and `parameters` encoding `protocolFeeAmount + integratorFeeAmount > X`, funding the call with the correct `safetyDeposit` (+`amount` if native) so the balance check passes [3](#0-2) .
2. Escrow deploys successfully; balance/timelock checks pass since they don't inspect fee parameters.
3. During the withdrawal window, taker calls `withdraw(secret, immutables)` (or anyone with an access token calls `publicWithdraw`); `_withdraw` reverts on `immutables.amount - integratorFeeAmount - protocolFeeAmount` due to underflow [8](#0-7) , every time, for any caller, for the life of the withdrawal window.
4. After `DstCancellation` timelock, taker calls `cancel()`, reclaiming `immutables.amount` and the safety deposit for themselves [7](#0-6) , while the maker never received destination funds through this escrow.

*Note: I was unable to fully verify how the off-chain relayer/maker client validates the dst escrow's fee parameters before releasing the secret, since that logic (if any) lives outside this repository's on-chain contracts. This affects the practical likelihood assessment above but not the fact that the on-chain guard is missing.*

```text
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```
