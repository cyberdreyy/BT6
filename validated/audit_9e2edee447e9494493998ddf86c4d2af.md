### Title
`MerkleTree::try_new_with_len` panics via subtraction overflow / out-of-bounds indexing when `len` disagrees with actual iterator length - ([File: ledger/src/shred/merkle_tree.rs])

### Summary
`MerkleTree::try_new_with_len` trusts a caller-supplied `len` to precompute tree capacity and to drive the tree-building loop, but it never checks that `len` matches the number of items actually produced by the `shreds` iterator. If fewer items are yielded than `len` (e.g. because stored shreds for a `fec_set` are missing/corrupted), the internal offset arithmetic underflows and/or indexes out of bounds, panicking the thread.

### Finding Description
In `ledger/src/shred/merkle_tree.rs`, `try_new_with_len` computes `capacity = get_merkle_tree_size(len)` and then pushes leaves from the iterator into `nodes` without checking that the number of leaves pushed equals `len`: [1](#0-0) 

It then builds parent levels using `len` (via `init = (len > 1).then_some(len)`) to compute `size` for each level, and computes `offset = nodes.len() - size`: [2](#0-1) 

If the iterator yields fewer `Hash` items than `len` (e.g., `nodes.len() == actual_count < len` after the leaf-push loop), the first iteration of the `successors` loop sets `size = len`, and `offset = nodes.len() - size` underflows because `nodes.len() < size`. In debug builds this panics immediately on subtraction overflow; in release builds it wraps to a huge `usize`, and the subsequent `nodes[index]` / `nodes[(index+1).min(...)]` accesses panic with an out-of-bounds index. Either way, the function panics instead of returning an `Err`, despite the function's own doc comment describing itself as fallible (`Result<MerkleTree, Error>`).

`try_new` (the safe wrapper) calls `shreds.len()` from `ExactSizeIterator` to derive `len`, so it is self-consistent and not vulnerable. The vulnerability only manifests through the `try_new_with_len` entry point, which is `pub` (not `pub(crate)`) and explicitly designed to accept a caller-provided `len` decoupled from the iterator, per its call sites in `ledger/src/blockstore.rs`, `core/src/repair/serve_repair.rs`, `core/src/repair/block_id_repair_service.rs`, and `turbine/src/broadcast_stage/standard_broadcast_run.rs`. These call sites (e.g., blockstore double-merkle-tree/proof-population logic keyed off stored `fec_set_count` metadata) compute `len` from persisted metadata separately from the shred iterator, which is the classic pattern for this kind of length/iterator mismatch. I was not able to fully re-verify within this session the exact RPC-reachable call path in `ledger/src/blockstore.rs` that supplies a `fec_set_count`-derived `len` while iterating over a shred set that can be short due to missing/corrupted shreds; this should be independently confirmed by tracing `populate_double_merkle_meta_proofs`/`build_double_merkle_tree` before treating the end-to-end RPC scoped impact as certain. The panic condition inside `try_new_with_len` itself, however, is verifiable directly from the code shown above.

### Impact Explanation
A length/iterator mismatch causes an unrecoverable `panic!` (subtraction overflow or out-of-bounds slice/vec index) inside a decoding/tree-building routine that is documented to return `Result` rather than panic. If reached from a blockstore read path serving an RPC/read request over data whose completeness cannot be guaranteed (e.g., partial FEC sets), this is a validator-process crash triggered by a single external request — matching the "decoder panic" / "validator crash from one request" bounty category.

### Likelihood Explanation
Exploitability is contingent on there actually being a reachable call site that (a) computes `len` from stored/attacker-influenced metadata (e.g. `fec_set_count`) and (b) supplies a `shreds` iterator whose length can independently fall short of that metadata (e.g., due to missing/corrupted shreds for that FEC set). This session found `try_new_with_len` callers in `ledger/src/blockstore.rs`, `serve_repair.rs`, `block_id_repair_service.rs`, and `standard_broadcast_run.rs`, but did not have time to confirm which of these is reachable from a single unprivileged RPC call with attacker-controlled input, versus internal/trusted invariants that already guarantee `len` matches the iterator (e.g., counts derived at write time rather than read time). This should be verified before assuming full RPC reachability.

### Recommendation
In `try_new_with_len`, validate the actual number of leaves pushed equals `len` before proceeding to build internal nodes, returning `Error::InvalidMerkleProof` (or a new dedicated error) on mismatch instead of relying on unchecked arithmetic:
```rust
for shred in shreds {
    nodes.push(shred?);
}
if nodes.len() != len {
    return Err(Error::InvalidMerkleProof); // or a dedicated "length mismatch" error
}
```
This converts the panic into a graceful `Err` for any caller (including current and future ones) that might pass a `len` decoupled from the iterator's real length.

        MerkleTree::try_new_with_len(actual_leaves.into_iter(), claimed_len)
    });
    assert!(
        result.is_err() /* panicked */ || matches!(result, Ok(Err(_))),
        "try_new_with_len must not silently succeed on len/iterator mismatch"
    );
}

Expected: on the current code, this test demonstrates a panic (`catch_unwind` returns `Err`), proving the DoS primitive inside `try_new_with_len`. After applying the recommended length check, the function should instead return `Ok(Err(Error::InvalidMerkleProof))`, and the test should be updated to assert that specific `Err` outcome.
