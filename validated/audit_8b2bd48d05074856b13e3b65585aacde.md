The bug-class match here is the same "stale state not fully invalidated on removal, later miscounted toward a threshold" pattern as the Autonomint report — but the NEAR-native equivalent is in the multisig contracts' `DeleteMember`/`DeleteKey` handling, where a removed member's prior confirmations on requests they didn't originate are never purged from the `confirmations` set, letting those phantom confirmations count toward `num_confirmations` for requests executed later.### Title
Removed multisig member's stale confirmations still count toward `num_confirmations`, allowing request execution below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` decides whether a request is ready to execute purely by counting entries in the `confirmations` `HashSet` for that request (`confirmations.len() as u32 + 1 >= self.num_confirmations`). When a member is removed via `DeleteMember`, `delete_member` only purges `requests`/`confirmations` for requests that member *originated*; it never scans other pending requests to strip that member's confirmation entries from them. A stale confirmation from a since-removed member therefore keeps counting toward the K‑of‑N threshold, letting a request execute with fewer confirmations from members who are actually still authorized than `num_confirmations` requires.

### Finding Description
`confirm()` checks only that the calling member is currently valid and that the confirmation count (including historical entries) reaches the threshold: [1](#0-0) 

`delete_member` removes the departing member from `self.members` and cleans up only the subset of requests where that member was the *original signer* (`r.member == member`); it does not touch `self.confirmations` for any other pending request that the member may have already confirmed as a non-originator: [2](#0-1) 

The same gap exists in the earlier `multisig` contract, where `DeleteKey` cleans up requests filtered by `r.signer_pk == pk` (again, only requests the removed key originated) and does not scrub `confirmations` entries the key added to other requests: [3](#0-2) [4](#0-3) 

Binding broken: the protocol's invariant is `confirmations counted == confirmations from currently-live members`. After a `DeleteMember`/`DeleteKey` action, this becomes `confirmations counted > confirmations from currently-live members`, because a stale entry from the removed member persists in the `confirmations` set for any other pending request.

Concretely, with members `{A, B, C, D}` and `num_confirmations = 3`:
1. Member `A` creates request `X` (e.g., `Transfer` to an arbitrary receiver, or `AddKey`/`FunctionCall`). `confirmations[X] = {}` (or `{A}` if `add_request_and_confirm`).
2. Member `D` confirms `X`: `confirmations[X] = {A, D}` (assuming `A` auto-confirmed) — below threshold, request stays pending.
3. The group discovers `D`'s key is compromised and executes a separate, fully-confirmed `DeleteMember{D}` request. `delete_member` only checks/cleans requests where `D` is the *originator* — request `X`, originated by `A`, is untouched, so `confirmations[X]` still contains `D`.
4. Members are now `{A, B, C}`, `num_confirmations` unchanged at 3.
5. Member `B` confirms `X`: `confirmations[X] = {A, D, B}`, length 3 `>= num_confirmations (3)` → `execute_request` fires.

Only two live members (`A`, `B`) actually approved `X`; the third "confirmation" belongs to a member that has since been deleted (e.g., precisely because their key leaked). The 3-of-4 (or effectively 3-of-3 after removal) security guarantee is bypassed using a phantom confirmation.

### Impact Explanation
This breaks the core custody/authorization guarantee of the multisig: a request (which can be an arbitrary `Transfer`, `FunctionCall`, `DeployContract`, `AddKey`, or `AddMember`/`DeleteMember` action) can be executed with fewer than `num_confirmations` confirmations from members who are valid at execution time. This matches the Critical impact category "a multisig request executed below threshold" — funds can be moved, keys added, or contract code deployed by a coalition that no longer meets the configured K-of-N policy, directly undermining the multisig's threat model (this is exactly the scenario removal-of-a-compromised-key is meant to protect against).

### Likelihood Explanation
No attacker privilege beyond normal, expected multisig operation is required: creating a request, having a legitimate member confirm it, and later removing another member (a routine key-rotation/compromise-response action) are all standard, sanctioned multisig workflows. The vulnerable window (a pending request confirmed by a member who is later removed) is a realistic and common operational sequence — key rotation and removal of departing/compromised signers are the primary reasons `DeleteMember`/`DeleteKey` exist. No special timing tricks, redeploys, or out-of-scope actors (foundation, node operators, RPC interception) are needed.

### Recommendation
When executing `DeleteMember` (or `DeleteKey` in the legacy `multisig` contract), iterate over **all** pending requests' `confirmations` sets (not just the ones the removed member originated) and remove any entry belonging to the removed member/key. Alternatively, change `confirm()` to validate, at confirmation-count time, that every entry in `confirmations` still corresponds to a current member (e.g., filter `confirmations` against `self.members` before comparing length to `num_confirmations`), so stale confirmations are never counted toward the threshold.

### Proof of Concept
Not executable from static analysis alone (no test harness run), but the logical trace above is fully supported by the cited code: `confirm()` at `multisig2/src/lib.rs:292-315` counts raw `confirmations.len()`, and `delete_member()` at `multisig2/src/lib.rs:355-379` only clears confirmations for requests where `r.member == member` (the removed member's own originated requests), leaving that member's confirmation entries on other members' pending requests intact. A Devin/test-harness reproduction would: (1) init `MultiSigContract::new(members=[A,B,C,D], num_confirmations=3)`; (2) `A.add_request_and_confirm(request_X)`; (3) `D.confirm(request_X)`; (4) fully confirm and execute a `DeleteMember{D}` request via A, B, C; (5) `B.confirm(request_X)` and observe `execute_request` fires despite only A and B being live-member approvers.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************

            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
