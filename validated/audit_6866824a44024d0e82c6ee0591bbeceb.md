No vulnerability found for this question.

The premise is refuted by the actual validation logic. `validate_deterministic_state_init` computes `derived_id = derive_near_deterministic_account_id(&action.state_init)` and then requires **exact equality** with `receiver_id` as a whole `AccountId` string — not just equality of the 40-hex-char suffix. [1](#0-0) 

Since `derive_near_deterministic_account_id` always formats its output as `"0s" + hex(hash[12..32])` [2](#0-1) , `derived_id` can never equal an `0x...` (EthImplicit) string, regardless of what bytes the attacker searches for in `state_init`. The `'0x'` vs `'0s'` prefixes are part of the compared `AccountId` value itself (via `!=` on the full string), so no hex-suffix collision between an EthImplicit account and a NearDeterministic account can ever cause `derived_id == receiver_id` to hold for a `receiver_id` starting with `0x`.

This is directly confirmed by the existing unit test `test_validate_deterministic_state_init_receiver`, which asserts that any receiver not matching the exact derived `0s...` id — including a NEAR-implicit-looking id — is rejected with `InvalidDeterministicStateInitReceiver` [3](#0-2) .

The `AccountType::get_account_type` priority order (EthImplicit before NearImplicit before NearDeterministic) only affects *how an account id string is classified for other purposes* (e.g., which account-creation branch to run on `Transfer`) [4](#0-3) ; it does not enter into the `DeterministicStateInitAction` receiver check at all, so it cannot be leveraged to make an `0x...` id pass as the derived `0s...` id.

The only real historical bug in this area was the delegate-action receiver mismatch (fixed by `FixDelegatedDeterministicStateInit`), which is unrelated to prefix collisions and is already covered by regression tests [5](#0-4) .

pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}
