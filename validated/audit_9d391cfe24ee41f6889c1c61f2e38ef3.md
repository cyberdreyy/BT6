**Rationale:** The premise of the question misunderstands the accounting model. `stack_charge` is not applied differently depending on runtime path — it is a single, fixed reservation charged exactly once per function *invocation*, unconditionally, before any of the function's actual code executes [1](#0-0) . The corresponding refund via `call_unstack_instrumentation` uses that *same* `charge` value and is inserted at every possible exit point of the function — `Return`, `ReturnCall`, `ReturnCallIndirect`, and the normal fall-through `End` [2](#0-1) .

Since exactly one of these exit paths is taken per invocation, and each refunds the identical constant that was reserved at entry, the debit/credit pair is always balanced by construction — it does not depend on which path was taken or how much of the operand stack was actually live at that point [3](#0-2) . The design intentionally reserves the statically-declared worst-case (`stack_sz + frame_sz` from `SimpleMaxStackCfg`'s analysis) for the whole call, regardless of the actual dynamic path, and releases that exact same reservation on whichever exit is taken. This is a conservative upper-bound reservation scheme, not a live-depth tracker, so an early `Return` before reaching peak stack usage cannot cause an imbalance: the reservation was never sized to the live depth in the first place, it was sized to the declared maximum for the entire function body, and that same maximum is what gets released at exit.

Additionally, `checked_sub_i64`/`checked_add_i64` traps via `STACK_EXHAUSTED_FN` on underflow/overflow [4](#0-3) , so `STACK_GLOBAL` cannot silently go negative or wrap. There is no reachable sequence of nested calls/early returns that produces an under-count relative to the declared per-frame charge, because the charge amount used for both the decrement and increment is always the same compile-time-fixed value for a given function — there is no code path where a smaller "live" charge is credited back while a larger "declared" charge was debited, or vice versa.

fn call_unstack_instrumentation(func: &mut InstructionSink<'_>, charge: NonZeroU64, globals: u32) {
    func.global_get(globals + STACK_GLOBAL)
        .i64_const(0)
        // This cast being able to wrap-around is intentional.
        // The callee must reinterpret this back to unsigned.
        .i64_const(u64::from(charge) as i64)
        .i64_const(0)
        .checked_add_i64(STACK_EXHAUSTED_FN)
        // $stack + $operand_size + $frame_size
        .global_set(globals + STACK_GLOBAL);
}
