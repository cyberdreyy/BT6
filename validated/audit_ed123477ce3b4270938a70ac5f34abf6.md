Confirmed: `h.callbacks` in `httpTriggerHandler` is keyed **only by the client-supplied JSON-RPC `req.ID`**, globally across all workflows and all workflow owners — there is no per-owner or per-workflow namespacing of this key. [1](#0-0) [2](#0-1) 

### Title
Global, unpartitioned request-ID lock in HTTP Trigger Handler allows any authenticated workflow-owner to block execution requests of unrelated workflow owners for up to `MaxTriggerRequestDurationMs` - (File: `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`)

### Summary
`HandleUserTriggerRequest` validates the request, resolves the workflow, authorizes the JWT, checks the rate limit, and then calls `setupCallback`, which inserts an entry into the shared `h.callbacks` map keyed solely by the request's `req.ID` string. If an entry already exists for that ID, the request is rejected with `jsonrpc.ErrConflict` ("in-flight request"). The lock is not scoped by workflow ID or workflow owner, and it persists until a quorum response arrives or `MaxTriggerRequestDurationMs` (default 60s, configurable) elapses.

### Finding Description
Because the in-flight lock key is the bare `req.ID`, any actor holding a valid JWT for **any** workflow they legitimately own can pre-empt a request ID for a **different** workflow owner simply by submitting a `workflows.execute` request with that same ID first. `setupCallback` only checks for key presence in the shared map: [2](#0-1) 

This is architecturally analogous to the GMX `cooldownDuration` bug: a shared, non-user-partitioned piece of state (there: the `_addLiquidity` timestamp on `GlpManager`; here: the `req.ID → callback` map) can be manipulated by an unrelated, unprivileged/low-privilege actor to deny another legitimate user's operation for the duration of a fixed window. In GMX's case the attacker needed no special access to reset another user's cooldown; here, the attacker needs only a valid JWT for some workflow they control (a low bar, since HTTP Trigger authorization is scoped per-workflow, not globally privileged) and knowledge/prediction of the victim's chosen request ID. Many client SDKs generate request IDs deterministically or with low entropy (e.g., sequential counters, workflow-execution-derived IDs), making collision plausible in practice — mirroring the "average stake interval" style probabilistic collision argument in the original report.

### Impact Explanation
A successful collision causes `setupCallback` to reject the legitimate user's request with `jsonrpc.ErrConflict`, meaning their workflow execution never starts and no funds/actions requiring that trigger are processed for that request ID, until the attacker's own callback for that ID completes or times out. Because the map is not scoped by owner, an attacker only needs to be a valid workflow owner (not the victim's owner) to interfere — a cross-tenant denial-of-service of a specific execution trigger, not merely of the attacker's own resources.

### Likelihood Explanation
Exploitation requires: (1) attacker has a JWT-authorized workflow (achievable by any onboarded workflow owner — not a privileged operator), and (2) attacker can guess or predict the victim's `req.ID` ahead of time. Many systems use predictable IDs (sequence numbers, deterministic hashes of workflow/tag/time), so this is plausible but not universal — likelihood is moderate and scenario-dependent, similar to the original report's own probabilistic argument rather than a guaranteed exploit.

### Recommendation
Scope the in-flight callback key by `(workflowOwner, workflowID, req.ID)` or by the caller's authenticated key rather than by the bare client-supplied `req.ID`, so that collisions can only occur within a single workflow owner's own requests, eliminating cross-tenant blocking.

### Proof of Concept
1. Attacker registers/owns Workflow A with a valid signer key and obtains a JWT.
2. Attacker predicts/observes that Victim (owner of Workflow B) is about to submit (or periodically submits) a `workflows.execute` request with request ID `"X"`.
3. Attacker submits their own valid, signed `workflows.execute` request for Workflow A using the same `id: "X"` just before the victim's request arrives; `setupCallback` inserts `h.callbacks["X"]`.
4. Victim's request for Workflow B with the same `id: "X"` arrives and hits the existing-key check in `setupCallback`, receiving `jsonrpc.ErrConflict` ("requestID: X has already been used") — the victim's execution never starts.
5. Attacker can repeat this before each `MaxTriggerRequestDurationMs` window expires to keep blocking the victim's ID indefinitely, analogous to the GMX attacker repeatedly resetting `cooldownDuration` to keep redemption perpetually blocked.

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
