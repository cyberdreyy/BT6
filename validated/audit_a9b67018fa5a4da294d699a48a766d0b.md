### Title
Unprivileged promise-only DeployGlobalContractAction lets attacker bind a victim account's identity to attacker-controlled wasm and drain the victim's balance for storage cost - (File: runtime/runtime/src/global_contracts.rs)

### Finding Description
`action_deploy_global_contract` in `runtime/runtime/src/global_contracts.rs` receives `account_id`/`account` — which are the *receiver* of the receipt being applied, not necessarily its predecessor — and unconditionally deducts `storage_cost` from that account's balance and, for `GlobalContractDeployMode::AccountId`, registers `GlobalContractIdentifier::AccountId(account_id.clone())` bound to the caller-supplied `deploy_contract.code`: [1](#0-0) [2](#0-1) 

The only pre-execution validation performed on `DeployGlobalContractAction` is a contract-size check; it does not verify that the actor (predecessor) equals the receiver: [3](#0-2) 

This is consistent with the documented action model: only `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, and `DeleteAccount` are required to have `predecessor_id == receiver_id`; `DeployGlobalContract` is conspicuously absent from that list: [4](#0-3) 

Because a `FunctionCall` executed on an attacker-owned contract A can create an outgoing action receipt whose `receiver_id` is an arbitrary victim account B (receiver != predecessor is the normal cross-contract-call pattern), and that receipt can carry a `DeployGlobalContractAction` with `deploy_mode = AccountId`, the runtime will apply `action_deploy_global_contract` against B's account when the receipt is processed at B: it deducts `storage_cost` from B's own NEAR balance and durably writes `TrieKey::GlobalContractCode{AccountId(B)}` with attacker-chosen bytes. Any account that later performs `UseGlobalContractAction(AccountId(B))` executes code B never authorized, and B never signed any transaction authorizing the deploy or the fee.

### Impact Explanation
This falls under "stealing or loss of funds" (unauthorized deduction of B's balance for storage the victim never requested) and "contracts execution flows" (permanent binding of an attacker-chosen contract to victim B's global-contract identity, which can be silently referenced by any future `UseGlobalContractByAccountId(B)` caller, corrupting code provenance for B).

### Likelihood Explanation
Preconditions are minimal and fully within reach of an unprivileged attacker: deploy an attacker contract A, have A issue a `Promise::create` / cross-contract `FunctionCall` batch whose action list includes a `DeployGlobalContractAction`, and target `receiver_id = B` for any account B that holds enough balance to cover `storage_usage_config.global_contract_storage_amount_per_byte * len(code)`. No special permissions, keys, or validator access are needed; cost to the attacker is just gas plus contract-deployment tooling, and it is repeatable against any account with sufficient balance.

### Recommendation
Add `DeployGlobalContract` (at least for `GlobalContractDeployMode::AccountId`) to the list of actions requiring `predecessor_id == receiver_id`, enforced in `validate_action_with_mode`/`validate_deploy_global_contract_action` (`runtime/runtime/src/action_validation.rs`) and/or by asserting `account_id == receipt.predecessor_id()` before calling `action_deploy_global_contract` in `runtime/runtime/src/actions.rs`.

### Proof of Concept
1. Runtime/apply integration test with account A (attacker) and B (victim), each funded.
2. A submits a transaction with a `FunctionCall` to itself/another contract that, during execution, issues a promise batch to `receiver_id = B` containing `Action::DeployGlobalContract(DeployGlobalContractAction { code: <A's wasm>, deploy_mode: GlobalContractDeployMode::AccountId })` (or directly construct the resulting `Receipt`/`ActionReceipt` in a `runtime/test-loop` scenario to isolate `apply_action_receipt`).
3. Apply the receipt at B's shard.
4. Assert: `B.amount()` decreased by `global_contract_storage_amount_per_byte * code.len()`; `state_update` contains `TrieKey::GlobalContractCode{ identifier: GlobalContractCodeIdentifier::AccountId(B) }` equal to A's bytes; B never signed any transaction referencing this deploy.
5. Optionally, have a third account C run `UseGlobalContractAction(GlobalContractIdentifier::AccountId(B))` and confirm C now executes A's injected code under B's identity.

```rust
pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;
```

```rust
/// Validates `DeployGlobalContractAction`. Checks that the given contract size doesn't exceed the limit.
fn validate_deploy_global_contract_action(
    limit_config: &LimitConfig,

) -> Result<(), ActionsValidationError> {
    if action.code.len() as u64 > limit_config.max_contract_size {
        return Err(ActionsValidationError::ContractSizeExceeded {
            size: action.code.len() as u64,
            limit: limit_config.max_contract_size,
```
