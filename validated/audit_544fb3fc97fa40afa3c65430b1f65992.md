### Title
Unbounded RLP decode of EIP-8130 `account_changes`/`initial_actors`/`changes` lists allows pre-validation allocation amplification — ([File: crates/common/consensus/src/transaction/eip8130/account_changes.rs])

### Summary
Base's EIP-8130 transaction decoder bounds the number of `calls` phases *during* RLP decoding (`MAX_CALL_PHASES_PER_TX`, enforced inside `decode_calls`) specifically to stop allocation amplification before mempool admission limits run. The same protection is not applied to the sibling `account_changes` list or its nested `initial_actors` / `changes` lists, which are decoded with the generic, unbounded `Vec::<T>::decode`. The corresponding count caps (`MAX_ACCOUNT_CHANGES_PER_TX`, `MAX_ACTORS_PER_ENTRY`, `MAX_ACTOR_CHANGES_PER_CONFIG`) are enforced only *after* decode, in the txpool validator. This is the same bug class as CVE-2023-27530 (Rack): one dimension of a multi-part structure is capped, but a sibling, structurally identical dimension is not, so an attacker can still force unbounded parsing work before any limit is checked.

### Finding Description
`TxEip8130::rlp_decode_fields` decodes fields in this order: [1](#0-0) 

- `calls: Self::decode_calls(buf)?` — bounded inline by `Eip8130Constants::MAX_CALL_PHASES_PER_TX` (1,024) while decoding, exactly to prevent "a sequence of single-byte empty RLP lists from amplifying into unbounded allocations before transaction-pool admission limits run": [2](#0-1) [3](#0-2) 

- `account_changes: Decodable::decode(buf)?` — uses the plain, unbounded `Vec<AccountChange>` RLP decoder with no per-item cap during decode: [4](#0-3) 

Each `AccountChange::Create` and `AccountChange::ConfigChange` variant itself decodes a nested, also-unbounded `Vec<InitialActor>` / `Vec<SignedChange>`: [5](#0-4) 

The only bounds on these three collections (`MAX_ACCOUNT_CHANGES_PER_TX = 3`, `MAX_ACTORS_PER_ENTRY = 32`, `MAX_ACTOR_CHANGES_PER_CONFIG = 5`) are enforced afterward, in the txpool validator's `validate_account_changes` / `validate_account_change_entries` (and `validate_initial_actors` / `validate_actor_changes`, not shown but referenced there): [6](#0-5) [7](#0-6) 

This mirrors the exact structure of CVE-2023-27530: Rack bounded the number of *file* parts in a multipart body but not the total number of parts, so an attacker could still force unbounded parsing work. Here, Base bounds `calls` phases during decode but not `account_changes` (or its nested `initial_actors`/`changes`), so the RLP decoder still walks and heap-allocates a `Vec` entry (and, for `Create`/`ConfigChange`, a further nested `Vec`) per declared item before the pool's `validate_account_changes` cap of 3 total entries is ever reached.

### Impact Explanation
Every `AccountChange` entry decode allocates a `Vec` push (and `ConfigChange`/`Create` entries allocate an additional nested `Vec` for `changes`/`initial_actors`), all driven by attacker-controlled, unauthenticated transaction bytes reachable via `eth_sendRawTransaction` or p2p tx propagation — before signature/authorization or the pool's structural admission caps run. This is a CWE-400/CWE-770 resource-consumption issue: a crafted EIP-8130 transaction can force disproportionate parser-side allocation work relative to its "useful" (post-cap) content, increasing CPU/memory pressure per submitted transaction and degrading node throughput for a validator/sequencer processing many such transactions. This does not itself corrupt consensus state, so it does not rise to unbacked supply or chain split, but it is a legitimate node-availability/DoS concern reachable by any unprivileged transaction sender — the same class and reachability as the original Rack advisory.

### Likelihood Explanation
High likelihood of reachability: any unprivileged party can submit a raw EIP-8130 transaction over the public RPC or p2p tx-gossip paths, and the vulnerable decode path (`TxEip8130::rlp_decode_fields` → `Vec::<AccountChange>::decode` → nested `Vec::<InitialActor>`/`Vec::<SignedChange>::decode`) runs unconditionally on every candidate transaction before any pool-level cap is applied. The amplification is bounded by the overall raw transaction byte size (RLP items require at least a couple of bytes each), so the practical severity depends on whatever maximum transaction size the ingress path enforces; the codebase does not appear to enforce a transaction-size cap directly inside this decode path (no reference was found in `crates/execution/txpool/src/validator.rs`), which increases likelihood that a large-but-otherwise-valid-looking transaction could reach this code before rejection.

### Recommendation
Apply the same decode-time bound already used for `calls` to `account_changes`, `initial_actors`, and `changes`: replace the plain `Decodable::decode` calls for these three `Vec<T>` fields with bounded decoders that reject once the corresponding constant (`MAX_ACCOUNT_CHANGES_PER_TX`, `MAX_ACTORS_PER_ENTRY`, `MAX_ACTOR_CHANGES_PER_CONFIG`) is exceeded, mirroring `TxEip8130::decode_calls`'s inline `phases.len() >= MAX_CALL_PHASES_PER_TX` check. This closes the gap between "one part-type is capped, its sibling is not," consistent with the fix pattern Rack/Rails applied for CVE-2023-27530 (bound the total count, not just one category of parts).

### Proof of Concept
1. Craft a well-formed `TxEip8130` unsigned body RLP-encoding a very large `account_changes` list (e.g., thousands of minimal `AccountChange::Delegation` entries, each a 2-byte RLP list `rlp([0x02, target])`), or a smaller number of `AccountChange::Create`/`ConfigChange` entries each carrying a maximal `initial_actors`/`changes` sub-list, up to the raw transaction's byte-size ceiling.
2. Sign/wrap it as an `Eip8130Signed` envelope and submit it via `eth_sendRawTransaction` (or p2p tx propagation).
3. Observe that `TxEip8130::rlp_decode_fields` fully decodes and heap-allocates every `AccountChange`/`InitialActor`/`SignedChange` entry (each triggering a `Vec` push, and for `Create`/`ConfigChange` a nested `Vec` allocation) before `validate_account_changes` in `crates/execution/txpool/src/validator.rs` rejects the transaction for exceeding `MAX_ACCOUNT_CHANGES_PER_TX` (3). Repeated submission of such transactions forces the node to repeatedly perform this unbounded pre-validation parsing/allocation work, analogous to the Rack multipart "many parts" DoS shape.

    fn decode_calls(buf: &mut &[u8]) -> alloy_rlp::Result<Vec<Vec<Call>>> {
        let header = Header::decode(buf)?;
        if !header.list {
            return Err(alloy_rlp::Error::UnexpectedString);
        }
        if buf.len() < header.payload_length {
            return Err(alloy_rlp::Error::InputTooShort);
        }

        let (mut payload, rest) = buf.split_at(header.payload_length);
        let mut phases = Vec::new();
        while !payload.is_empty() {
            if phases.len() >= Eip8130Constants::MAX_CALL_PHASES_PER_TX {
                return Err(alloy_rlp::Error::Custom("too many EIP-8130 call phases"));
            }
            phases.push(Vec::<Call>::decode(&mut payload)?);
        }
        *buf = rest;
        Ok(phases)

impl Decodable for AccountChange {
    fn decode(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
        let header = Header::decode(buf)?;
        if !header.list {
            return Err(alloy_rlp::Error::UnexpectedString);
        }
        let started_len = buf.len();
        let type_byte = u8::decode(buf)?;
        let this = match type_byte {
            Eip8130Constants::ACCOUNT_CHANGE_TYPE_CREATE => Self::Create(CreateEntry {
                user_salt: B256::decode(buf)?,
                code: Bytes::decode(buf)?,
                initial_actors: Vec::<InitialActor>::decode(buf)?,
            }),
            Eip8130Constants::ACCOUNT_CHANGE_TYPE_CONFIG => {
                let channel_byte = u8::decode(buf)?;
                let channel = AccountChangeChannel::from_byte(channel_byte)
                    .ok_or(alloy_rlp::Error::Custom("invalid SignedAccountChanges channel byte"))?;
                Self::ConfigChange(SignedAccountChanges {
                    channel,
                    sequence: u64::decode(buf)?,
                    changes: Vec::<SignedChange>::decode(buf)?,
                    signature: Bytes::decode(buf)?,
                })
            }
            Eip8130Constants::ACCOUNT_CHANGE_TYPE_DELEGATION => {
                Self::Delegation(Delegation { target: Address::decode(buf)? })
            }
            _ => return Err(alloy_rlp::Error::Custom("invalid AccountChange type byte")),
        };
        let consumed = started_len - buf.len();
        if consumed != header.payload_length {
            return Err(alloy_rlp::Error::ListLengthMismatch {
                expected: header.payload_length,
                got: consumed,
            });
        }
        Ok(this)
    }
}

    fn validate_account_change_entries(
        signed: &Eip8130Signed,
    ) -> Result<(), InvalidPoolTransactionError> {
        let mut create_count = 0usize;
        let mut delegation_count = 0usize;
        let mut config_count = 0usize;
        for (idx, change) in signed.tx().account_changes.iter().enumerate() {
            match change {
                AccountChange::Create(create) => {
                    create_count += 1;
                    if create_count > 1 || idx != 0 {
                        return Err(InvalidTransactionError::TxTypeNotSupported.into());
                    }
                    // Reject at admission the runtime code shapes the enshrined
                    // deploy (`AccountChangeApplier::apply_create`) refuses:
                    // EIP-170 oversize and the EIP-3541 reserved leading `0xEF`
                    // byte (which `CREATE2` would reject with `address(0)`).
                    if create.code.is_empty()
                        || create.code.len() > Eip8130Constants::MAX_CODE_SIZE
                        || create.code.first() == Some(&0xEF)
                        || create.initial_actors.is_empty()
                    {
                        return Err(InvalidTransactionError::TxTypeNotSupported.into());
                    }
                    Self::validate_initial_actors(&create.initial_actors)?;
                }
                AccountChange::ConfigChange(cfg) => {
                    config_count += 1;
                    if config_count > Eip8130Constants::MAX_CONFIG_CHANGES_PER_TX {
                        return Err(InvalidTransactionError::TxTypeNotSupported.into());
                    }
                    // A signed batch must carry at least one op (mirrors the
                    // contract's `EmptyChangeSet` rejection).
                    if cfg.changes.is_empty() {
                        return Err(InvalidTransactionError::TxTypeNotSupported.into());
                    }
                    if cfg.signature.len() < 20 {
                        return Err(InvalidTransactionError::TxTypeNotSupported.into());
                    }
                    let cfg_authenticator = Address::from_slice(&cfg.signature[..20]);
                    if !Self::authenticator_allowed_for_tx_path(&cfg_authenticator)
                        || !Self::authenticator_payload_well_formed(
                            &cfg_authenticator,
                            &cfg.signature[20..],
                        )
                    {
                        return Err(InvalidTransactionError::TxTypeNotSupported.into());
                    }
                    Self::validate_actor_changes(&cfg.changes)?;
                }
                AccountChange::Delegation(_) => {
                    delegation_count += 1;
                    if delegation_count > 1 {
                        return Err(InvalidTransactionError::TxTypeNotSupported.into());
                    }
                    if create_count > 0 {
                        return Err(InvalidTransactionError::TxTypeNotSupported.into());
                    }
                }
            }
        }
        Ok(())
    }
