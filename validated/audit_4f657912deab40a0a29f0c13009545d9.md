### Title
View-role users can read a bridge's plaintext OutgoingToken via unrestricted GET /v2/bridge_types/:BridgeName - ([File: core/web/router.go])

### Summary
The `GET /v2/bridge_types/:BridgeName` route is registered without any role wrapper, unlike its sibling `POST`/`PATCH`/`DELETE` routes which are wrapped with `auth.RequiresEditRole`. Any authenticated user — including one with only `view` role — can call `bt.Show`, which returns a `presenters.BridgeResource` containing the bridge's `OutgoingToken` in plaintext (no `omitempty`, no redaction).

### Finding Description
In `v2Routes` in `core/web/router.go`, the bridge routes are: [1](#0-0) 

`Index` and `Show` are left ungated while `Create`, `Update`, `Destroy` require `auth.RequiresEditRole`. Since `authv2` group only requires generic authentication (`auth.AuthenticateByToken`/`auth.AuthenticateBySession`, no minimum role), a user with `clsessions.UserRoleView` (the lowest role) passes through `Authenticate` and reaches `bt.Show` unimpeded — `RequiresRunRole`/`RequiresEditRole` explicitly reject `UserRoleView`, but `Show` never calls either.

`BridgeTypesController.Show` in `core/web/bridge_types_controller.go` loads the bridge from the ORM and serializes it directly: [2](#0-1) 

`presenters.NewBridgeResource` unconditionally copies `OutgoingToken` from the stored `bridges.BridgeType` into the JSON-serialized resource, and the field has no `omitempty`/redaction: [3](#0-2) 

The `bridge_types` table stores `outgoing_token` in plaintext (unlike `incoming_token_hash`, which is hashed): [4](#0-3) 

Note: the `IncomingToken` field is *not* leaked via `Show` — it is only populated transiently in `Create` from the freshly-generated token (`bta.IncomingToken`) and is never persisted in plaintext (only `IncomingTokenHash` is stored), so the confidential-token-leak risk applies specifically to `OutgoingToken`.

The existing test `TestBridgeController_Show` in `core/web/bridge_types_controller_test.go` only asserts `Name`, `URL`, `Confirmations` match — it does not assert `OutgoingToken` is present/absent, and does not test with a view-role caller, so this gap was not caught: [5](#0-4) 

### Impact Explanation
A view-role user (or any credential holder that only warrants read access) can retrieve the plaintext `OutgoingToken` for any bridge by name. This token is the credential the Chainlink node uses to authenticate its outgoing requests to the external adapter; possession of it enables the attacker to forge/impersonate requests to that external adapter or otherwise abuse the adapter integration — matching the "credential/secret disclosure enabling request forgery" bounty impact class, scoped to the specific bridge's adapter integration (not full node compromise).

### Likelihood Explanation
Preconditions are minimal: only a valid `view`-role session or API token (the lowest privilege tier) and knowledge of an existing bridge name (bridge names are enumerable via the also-ungated `GET /v2/bridge_types` index route, `authv2.GET("/bridge_types", paginatedRequest(bt.Index))`). No special timing or race condition is required; the request is a single deterministic `GET` and is fully repeatable.

### Recommendation
Wrap the `Show` route with a role check consistent with the sensitivity of the returned data, e.g. `authv2.GET("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Show))` (matching the write operations), or, if view-role must retain read access to some bridge metadata, redact `OutgoingToken` (and any other secret) from the presenter for non-edit/admin callers, similar to how `IncomingToken` is only populated conditionally in `Create`.

### Proof of Concept
Go handler-level integration test plan (extend `core/web/bridge_types_controller_test.go`):
1. Create an app via `cltest.NewApplication(t)`, start it, and create a bridge with `app.BridgeORM().CreateBridgeType(ctx, bt)` (which sets a known `OutgoingToken`).
2. Create a user/session with `clsessions.UserRoleView` (use existing test helpers, e.g. `cltest.MustRandomUser`/`cltest.CreateSessionForUser`-style role-scoped session helper used elsewhere in the auth test suite) and obtain an HTTP client authenticated as that view-role user (`app.NewHTTPClient(&cltest.User{Role: clsessions.UserRoleView})` or equivalent).
3. Issue `client.Get("/v2/bridge_types/" + bt.Name.String())`.
4. Assert response status is `200 OK` (proving no role gate blocks it) and parse the JSON body's `data.attributes.outgoingToken` field.
5. Assert `outgoingToken` equals the bridge's actual stored `OutgoingToken` — demonstrating the secret is returned to an unprivileged view-role caller.
6. Expected (fixed) behavior: either the request returns `401`/`403` for a view-role caller, or the JSON response's `outgoingToken` field is empty/omitted.

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

func TestBridgeController_Show(t *testing.T) {
	t.Parallel()

	app := cltest.NewApplication(t)
	require.NoError(t, app.Start(t.Context()))

	client := app.NewHTTPClient(nil)

	bt := &bridges.BridgeType{
		Name:          bridges.MustParseBridgeName(testutils.RandomizeName("showbridge")),
		URL:           cltest.WebURL(t, "https://testing.com/bridges"),
		Confirmations: 0,
	}
	ctx := t.Context()
	require.NoError(t, app.BridgeORM().CreateBridgeType(ctx, bt))

	resp, cleanup := client.Get("/v2/bridge_types/" + bt.Name.String())
	t.Cleanup(cleanup)
	assert.Equal(t, http.StatusOK, resp.StatusCode, "Response should be successful")

	var resource presenters.BridgeResource
	cltest.ParseJSONAPIResponse(t, resp, &resource)
	assert.Equal(t, bt.Name.String(), resource.Name, "should have the same name")
	assert.Equal(t, bt.URL.String(), resource.URL, "should have the same URL")
	assert.Equal(t, bt.Confirmations, resource.Confirmations, "should have the same Confirmations")

	resp, cleanup = client.Get("/v2/bridge_types/nosuchbridge")
	t.Cleanup(cleanup)
	assert.Equal(t, http.StatusNotFound, resp.StatusCode, "Response should be 404")
}
