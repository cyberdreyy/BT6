## Finding confirmed in `staking_contract.move`; `delegation_pool.move` is not affected

`delegation_pool.move` does not use `beneficiary_for_operator` for actual payouts (no `BeneficiaryForOperator`-driven `deposit_coins` calls found there), so the vulnerable path is specific to `aptos_framework::staking_contract`.

### Title
Operator can permanently trap all delegators' unlocked funds in a `staking_contract` pool by setting a beneficiary that rejects direct coin transfers - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::set_beneficiary_for_operator` lets an operator redirect their own commission payouts to an arbitrary `new_beneficiary` address with **no validation** that the address can actually receive `AptosCoin`. By contrast, the sibling function `vesting::set_beneficiary` explicitly requires `assert_account_is_registered_for_apt(new_beneficiary)` specifically "so `distribute()` wouldn't fail and block all other accounts from receiving APT if one beneficiary is not registered" [1](#0-0) . This exact safeguard is missing in `staking_contract::set_beneficiary_for_operator` [2](#0-1) .

### Finding Description
`distribute_internal` iterates over **every** shareholder of the pool's shared `distribution_pool` (stakers + operator) and pays each one out via `aptos_account::deposit_coins`, redirecting the operator's own share to `beneficiary_for_operator(operator)` when the recipient is the operator: [3](#0-2) 

`aptos_account::deposit_coins` will **abort** with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the target account exists, is not yet registered for the coin, and has disabled direct coin transfers via `set_allow_direct_coin_transfers(false)`: [4](#0-3) 

Because the `while` loop in `distribute_internal` pays out all shareholders in a single atomic transaction, one failing deposit aborts the **entire distribution for every staker in that pool**, not just the operator. Since `set_beneficiary_for_operator` performs no registrability check on `new_beneficiary` (unlike `vesting::set_beneficiary`, which explicitly guards against this same scenario), any operator can:
1. Set their beneficiary to an address they control.
2. Call `set_allow_direct_coin_transfers(false)` on that beneficiary address (or simply never register/create it and later disable transfers before deposit is attempted).
3. Every subsequent call to `distribute`, `unlock_stake`, `switch_operator`, or `update_commision` (all of which invoke `distribute_internal`) will abort for the whole pool, since these all run under one atomic transaction.

This blocks all delegating stakers of that `staking_contract` from ever withdrawing their already-unlocked, already-inactive stake through this pool's distribution mechanism, with no code path to bypass the broken beneficiary once it is poisoned this way (the only fix is the operator calling `set_beneficiary_for_operator` again to point to a valid address — a privileged action the operator fully controls, but which they have no incentive to do if griefing).

### Impact Explanation
This breaks the "Accounting across active/pending_active/pending_inactive/inactive/rewards/commission state must preserve value and withdrawal rights" and "Unlock, reactivate, withdraw... paths must not... strand [value] permanently" invariants. An operator (an unprivileged party relative to the staker's principal — the operator does not own the stake) can strand all inactive/unlocked stake belonging to every staker who created a `staking_contract` with that operator, with no timeout or self-recovery path other than the operator's own goodwill. This is a denial of fund-access vulnerability with a permanent, non-recoverable component for the affected epoch's withdrawals, matching the "Permanent lock or non-recoverable loss of claim rights" impact criterion.

### Likelihood Explanation
Requires the operator's own signer to call `set_beneficiary_for_operator` and to control/disable direct transfers on the target beneficiary address — both trivially executable by any operator, with no special privilege beyond being an operator that a staker chose (a normal, unprivileged, permissionless role in the staking ecosystem). No governance or admin permission is needed.

### Recommendation
Add the same guard used in `vesting::set_beneficiary` to `staking_contract::set_beneficiary_for_operator` (and audit any other `beneficiary_for_operator`-consuming payout path in the codebase for the same gap): require `aptos_account::assert_account_is_registered_for_apt(new_beneficiary)` (or an equivalent "can receive direct transfers" check) before allowing the beneficiary change. Additionally, consider making `distribute_internal` resilient to a single failing recipient (e.g., skip/park funds for a failing recipient rather than aborting the whole batch) so no single misconfigured or malicious beneficiary can block payouts to unrelated stakers.

### Proof of Concept
1. Staker `S` creates a staking contract with operator `O` via `staking_contract::create_staking_contract`, contributing principal stake.
2. Delegator/other stakers with pools under `O` accumulate rewards/commission; some stake becomes `inactive`/`pending_inactive`.
3. `O` calls `staking_contract::set_beneficiary_for_operator(O, B)` where `B` is an address `O` controls [2](#0-1) .
4. `O` (or anyone) calls `aptos_account::set_allow_direct_coin_transfers(B_signer, false)` on `B`, and ensures `B` is not registered for `AptosCoin`.
5. Any subsequent call to `staking_contract::distribute(S, O)` (or `unlock_stake`/`switch_operator`/`update_commision`, which invoke `distribute_internal`) reaches the loop at lines 888-901, tries to `aptos_account::deposit_coins` to `B`, and aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`, reverting the whole transaction and blocking distribution of already-unlocked funds to `S` and any other staker sharing this `staking_contract` pool.

Note: I was not able to further trace whether `delegation_pool.move`'s commission-withdrawal path (`withdraw`) uses `beneficiary_for_operator` at all in this codebase snapshot — my searches found no matches for `beneficiary_for_operator` in `delegation_pool.move`'s payout logic, suggesting `delegation_pool` may compute commission via internal share accounting rather than immediate `deposit_coins` to a beneficiary, and thus may not be exposed to this exact issue. This should be verified directly against `delegation_pool.move`'s full withdraw/commission-payment implementation if a complete confirmation is needed.

```text
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
```
