### Title
Unrestricted BlockRevenue/Inflation commission-in-basis-points updates during active reward accrual - (File: programs/vote/src/vote_state/mod.rs)

### Summary
Solana's vote program enforces a well-known anti-"commission rug" rule for the legacy percentage commission field: `update_commission` only allows commission *increases* during the first half of an epoch (`is_commission_update_allowed`), specifically to stop validators from bumping their cut right before rewards are calculated/paid out. The newer `update_commission_bps` path (SIMD-0291/SIMD-0123, used for both `InflationRewards` and `BlockRevenue` commission types) explicitly removes this timing restriction, per its own comment: "No commission update rule, per SIMD-0249 and SIMD-0291." This mirrors the Concur `Shelter.donate` finding: an actor can mutate a value that feeds into a shared, pro-rata payout pool (delegator rewards / block revenue) at any time — including immediately before the pool is computed/distributed — with no analog of a "grace period" cutoff, unfairly shifting the split between the operator and delegators.

### Finding Description
`update_commission` gates commission increases with `is_commission_update_allowed(clock.slot, epoch_schedule)`, which only permits increases in the first half of an epoch: [1](#0-0) [2](#0-1) 

By contrast, `update_commission_bps`, which sets `inflation_rewards_commission_bps` or `block_revenue_commission_bps`, has no such timing check — it only requires the withdrawer's signature: [3](#0-2) 

These commission-bps values directly govern how much of the accumulated, pooled rewards (`pending_delegator_rewards`, block revenue) is kept by the validator versus distributed to delegators when rewards are calculated/paid at the epoch boundary: [4](#0-3) 

The reward pipeline does apply a *separate* mitigation for the legacy commission path — caching vote-account state from a full epoch earlier specifically "to prevent last-minute commission rugs": [5](#0-4) 

However, based on the code reachable here, the `commission_bps` fields are read via `distribution_epoch_vote_accounts`/current vote state in `calculate_block_reward` and `redeem_delegation_rewards`, not via the delayed `snapshot_epoch_vote_accounts` cache reserved for legacy commission. Since I could not fully trace whether `commission_rate_in_basis_points`/`delay_commission_updates` flags force use of the delayed snapshot for bps commission before the reward calculation runs (the relevant `redeem_delegation_rewards` body past line ~700 and the `inflation_rewards/mod.rs` commission-bps consumption code were not fully retrievable in this session), this is presented as the strongest analog reachable from the report but with an important caveat noted below.

### Impact Explanation
If `commission_bps` (either `InflationRewards` or `BlockRevenue` kind) is not subject to the same epoch-boundary-delay/cutoff protection that legacy `commission` receives, an unprivileged-but-authorized vote-account withdrawer can raise their commission arbitrarily (up to 10000 bps) in the same slot/epoch window used for reward calculation and distribution, silently capturing a larger share of already-accrued `pending_delegator_rewards`/block revenue that delegators expected to receive under the previous commission rate — directly analogous to the Concur `donate()` finding where late deposits diluted/skewed already-committed claim shares. This constitutes unfair/incorrect reward (fund) distribution among delegators of that vote account, not a cluster-wide halt or consensus divergence, since all validators apply the same deterministic rule.

### Likelihood Explanation
Likelihood is **conditional and unverified**: since `update_commission_bps` intentionally removes the timing restriction "per SIMD-0249 and SIMD-0291" by design, this may be an intentional protocol design decision (not a bug) if the reward-calculation snapshot mechanism (`get_cached_vote_accounts`) independently delays commission-bps values used in distribution. I was unable to confirm within tool-call limits whether `commission_bps` reads in `redeem_delegation_rewards`/`calculate_block_reward` use the delayed `snapshot_epoch_vote_accounts` (safe) or the live/current vote account state (exploitable). Given the explicit code comment disclaiming any update-timing rule for bps commissions, and that reward computation in `calculate_block_reward` reads directly from `distribution_epoch_vote_accounts` (current epoch, not the epoch-delayed cache), likelihood leans toward exploitable but is not proven with certainty from the retrieved code alone.

### Recommendation
Confirm (or add) that `inflation_rewards_commission_bps` / `block_revenue_commission_bps` values used during reward calculation/distribution are sourced exclusively from the epoch-delayed vote-account snapshot (`snapshot_epoch_vote_accounts` / `rewarded_epoch_vote_accounts`) rather than the live vote account, so that any commission change made during the current epoch cannot affect rewards being computed/paid for that same epoch — restoring the same "no last-minute rug" guarantee that exists for legacy `commission`.

### Proof of Concept
Not constructible with certainty from the retrieved code: exploitation depends on whether `redeem_delegation_rewards`/`calculate_block_reward` consult the live vote account or the epoch-delayed snapshot for `commission_bps`, which this session's tool calls could not conclusively confirm. If confirmed to use live state, the PoC would be: (1) validator submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10000, kind: BlockRevenue }` (or `InflationRewards`) signed by the withdrawer in a slot late in the epoch, immediately before/at the reward-calculation boundary; (2) at epoch rollover, `begin_partitioned_rewards`/`calculate_block_reward` compute payouts using the newly-maxed commission, causing delegators to receive a reduced share of the previously-accrued `pending_delegator_rewards`/block revenue pool that had already accumulated under a lower commission rate.

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Given the current slot and epoch schedule, determine if a commission change
/// is allowed
pub fn is_commission_update_allowed(slot: Slot, epoch_schedule: &EpochSchedule) -> bool {
    // always allowed during warmup epochs
    if let Some(relative_slot) = slot
        .saturating_sub(epoch_schedule.first_normal_slot)
        .checked_rem(epoch_schedule.slots_per_epoch)
    {
        // allowed up to the midpoint of the epoch
        relative_slot.saturating_mul(2) <= epoch_schedule.slots_per_epoch
    } else {
        // no slots per epoch, just allow it, even though this should never happen
        true
    }
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

    /// Get cached vote account state from the past few epochs so that some vote
    /// state configuration changes are delayed before being used in reward
    /// calculation.
    fn get_cached_vote_accounts<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        distribution_epoch_vote_accounts: &'a VoteAccounts,
    ) -> CachedVoteAccounts<'a> {
        // Snapshot of vote account state from the beginning of the epoch prior to
        // the rewarded epoch. This snapshot state is saved a full epoch before
        // being used to prevent last minute commission rugs.
        let snapshot_epoch_vote_accounts = self
            .epoch_stakes(rewarded_epoch)
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        // Vote account state from the beginning of the rewarded epoch.
        let rewarded_epoch_vote_accounts = self
            .epoch_stakes(self.epoch())
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        CachedVoteAccounts {
            snapshot_epoch_vote_accounts,
            rewarded_epoch_vote_accounts,
            distribution_epoch_vote_accounts,
        }
    }
