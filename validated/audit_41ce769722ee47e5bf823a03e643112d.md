### Title
Attacker can permanently block Core BPF migration of a stateless builtin by pre-funding its program address - ([File: runtime/src/bank/builtins/core_bpf_migration/target_builtin.rs])

### Summary
`TargetBuiltin::new_checked` requires that a `CoreBpfMigrationTargetType::Stateless` builtin's program address have no existing account, but any unprivileged System Program transfer to that fixed, publicly known address creates a minimal system-owned account there. Because the migration is invoked exactly once, at the slot the `core_bpf_migration_config.feature_id` newly activates, and failures are only logged (never retried), pre-funding the address before that feature activates permanently prevents that stateless builtin from ever migrating to Core BPF.

### Finding Description
For `CoreBpfMigrationTargetType::Stateless`, `TargetBuiltin::new_checked` requires the program address to have no account: [1](#0-0) 
Stateless builtins (e.g. `zk_elgamal_proof_program`, `feature_gate` interface) have no on-chain account by design prior to migration, so their fixed program-id address is normally empty in the accounts database. Because the address is a hardcoded constant from `solana_sdk_ids`, an unprivileged attacker can submit an ordinary System Program transfer to that address at any time before the migration's feature gate activates, creating a system-owned account with nonzero lamports there.

The migration is triggered exactly once, only on the slot in which `core_bpf_migration_config.feature_id` transitions from inactive to newly-activated, inside `apply_new_builtin_program_feature_transitions`: [2](#0-1) 
If `migrate_builtin_to_core_bpf` returns `Err(CoreBpfMigrationError::AccountExists(..))` because the attacker pre-funded the address, the error is only logged via `warn!` and swallowed — there is no retry path. On the following slot, the feature is already active in `self.feature_set`, so `new_feature_activations` no longer contains `feature_id`, and this code block is never entered again for that builtin. The corresponding on-chain feature account will already show `activated_at = Some(slot)` (feature activation itself is independent of the migration outcome), so operators have no built-in mechanism to force a retry — the only remedy is releasing new validator software with a new feature gate/config.

The existing test suite's own negative-path test confirms this exact behavior/check: `test_target_program_stateless_builtin`'s "Fail if the program account exists" case stores an account at the stateless program address and asserts `CoreBpfMigrationError::AccountExists`: [3](#0-2) 
This test uses a native-loader-owned account, but the check at line 47 in `new_checked` does not discriminate by owner — any account (including a bare system-owned account created by a plain lamport transfer) at that address will trigger the same `AccountExists` failure, since `get_account_with_fixed_root` simply checks for account existence, not ownership, for the Stateless branch.

### Impact Explanation
This permanently prevents a scheduled protocol upgrade (a stateless builtin's one-shot migration to Core BPF) from ever completing on the affected cluster without a subsequent software release defining a new feature gate. This is a validator-wide liveness/upgrade-availability impact: the builtin remains a "native" builtin forever instead of becoming an on-chain, auditable, upgradeable Core BPF program, which was the intended security/maintainability improvement. It fits Solana's "loss of availability" / "protocol-level DoS impacting network-wide functionality" bounty category rather than direct fund theft, since no funds are stolen and no consensus divergence occurs (all validators compute the same `AccountExists` result deterministically from the same account state).

### Likelihood Explanation
Exploitation requires only funding a keypair and submitting one ordinary System Program transfer transaction to a compile-time-constant address (e.g. `solana_sdk_ids::zk_elgamal_proof_program::id()`) before the relevant `core_bpf_migration_config.feature_id` activates. Migration feature-gate activation schedules are known well in advance (feature activation epochs are public), giving the attacker ample opportunity to front-run. This requires no privileged role, no stolen keys, and no non-default configuration — it is fully within the described unprivileged attacker capability, and the outcome is deterministic and repeatable across any future stateless-builtin migration that reuses this same code path.

### Recommendation
For `CoreBpfMigrationTargetType::Stateless`, do not unconditionally fail when an account exists at the target address. Instead, mirror the `allow_prefunded` handling already used for the program-data account: if the existing account is owned by the System Program (i.e., it only received a plain lamport transfer and holds no meaningful state), allow the migration to proceed and account for/burn those lamports, similar to how `program_data_account_lamports` is handled when `allow_prefunded` is true. Only reject with `AccountExists` if the account is owned by a non-system program (indicating genuine, unexpected state). Additionally, consider making `apply_new_builtin_program_feature_transitions` retry the migration on subsequent slots (e.g., by tracking pending-but-failed migrations) rather than permanently giving up after a single failed attempt tied strictly to the feature-activation slot.

### Proof of Concept
```rust
// runtime/src/bank/builtins/core_bpf_migration/target_builtin.rs (add near existing tests)
#[test]
fn test_stateless_builtin_griefed_by_prefunded_system_account() {
    let migration_target = CoreBpfMigrationTargetType::Stateless;
    let bank = create_simple_test_bank(0);

    // Attacker: pick a currently-unoccupied, publicly known stateless
    // builtin address (e.g. zk_elgamal_proof_program) and send it lamports
    // via an ordinary System Program transfer BEFORE the migration feature
    // activates. This is simulated here directly via account store.
    let program_address = solana_sdk_ids::zk_elgamal_proof_program::id();
    assert!(bank.get_account_with_fixed_root(&program_address).is_none());

    let attacker_funded_account = AccountSharedData::new(
        1_000_000, // lamports sent by unprivileged attacker
        0,
        &SYSTEM_PROGRAM_ID, // plain system-owned account, no special state
    );
    bank.store_account_and_update_capitalization(&program_address, &attacker_funded_account);

    // When the feature later activates and migration is attempted:
    let result = TargetBuiltin::new_checked(
        &bank,
        &program_address,
        &migration_target,
        /* allow_prefunded */ true, // even with prefund allowance, still fails
    );

    // This assertion demonstrates the migration is blocked, and because
    // apply_new_builtin_program_feature_transitions only invokes
    // migrate_builtin_to_core_bpf on the single slot the feature transitions
    // to active (see runtime/src/bank.rs), this failure is never retried.
    assert_matches::assert_matches!(
        result.unwrap_err(),
        CoreBpfMigrationError::AccountExists(addr) if addr == program_address
    );
}
```
