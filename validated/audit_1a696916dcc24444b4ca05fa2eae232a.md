### Title
Router discovery cache in `Client.disco` is keyed globally, not per `RunnerConfig`, allowing cross-runner reuse of a stale router `ServerURL`/`TLSData` - ([File: router/client.go])

### Summary
`Client.getRouterDiscovery` caches `common.RouterDiscovery` (containing `ServerURL` and `TLSData`) as fields on the single `*router.Client` instance, gated only by a TTL timer, with no key derived from the `common.RunnerConfig` passed into `RequestJob`. Because `router.NewClient` is instantiated once in `main.go` and shared as the process-wide delegate wrapper for all registered runner configs, a discovery result fetched for one `RunnerConfig` is transparently served to `RequestJob` calls for a different `RunnerConfig` for up to `discoveryTTL` (1 hour).

### Finding Description
`getRouterDiscovery` checks only `c.discoExpiresAt` before returning `c.disco`: [1](#0-0) 

The `config common.RunnerConfig` argument is used solely to perform the *miss* path lookup (`c.delegate.GetRouterDiscovery(ctx, config)`); it plays no role in cache validation on a *hit*. `RequestJob` then dials using the cached discovery's `ServerURL`/TLS material combined with the *current* call's `config.Token`: [2](#0-1) 

and the response's `TLSData` is overwritten from the (possibly stale/foreign) `disco`: [3](#0-2) 

The `Client` struct holds `disco`/`discoExpiresAt` directly as instance fields with a single mutex, not a map keyed by config identity (URL, token, or runner ID): [4](#0-3) 

In a multi-runner process (a single `gitlab-runner` process polling several `[[runners]]` entries from `config.toml`), this same `*router.Client` instance backs `RequestJob` calls for every configured runner. If runner A's poll populates `c.disco` with router discovery scoped to A's GitLab instance/project, a subsequent poll for runner B within the 1-hour TTL will reuse A's `ServerURL` and `TLSData` while sending B's `config.Token`. This produces a request dialed against a router endpoint that was never discovered for B, and a `TLSData` payload attached to B's job response that actually belongs to A's session. No existing check (breaker, TLS validation, auth check) revalidates that the cached discovery corresponds to the calling `RunnerConfig`; the breaker only tracks router health, not identity.

### Impact Explanation
Concretely: B's job response is stamped with A's `TLSData` (used for subsequent artifact/cache/API calls in that job), and B's `GetJob` RPC is routed to a router endpoint discovered under A's runner registration. Depending on router-side authorization semantics, this can misroute a job request or attach the wrong TLS trust material to a different tenant/runner's job — a cross-runner/cross-project confusion of session routing that violates the stated invariant that discovery must be scoped per runner config.

### Likelihood Explanation
Requires only the common, supported deployment pattern of one `gitlab-runner` process serving multiple `[[runners]]` (multi-runner config), with `FF_USE_JOB_ROUTER` enabled for at least one runner and discovery being reused inside the 1-hour TTL window — no attacker privilege beyond normal multi-runner operation is needed to trigger the mixing; it's a straightforward consequence of the polling loop interleaving configs against a shared `Client`.

### Recommendation
Key the discovery cache by an identity derived from `RunnerConfig` (e.g., a hash of `config.URL`+`config.Token`/`config.ID`) using a `map[string]*discoEntry{disco, expiresAt}` protected by the existing mutex, so each runner config gets its own cached discovery, TTL, and invalidation instead of sharing global `Client.disco`/`discoExpiresAt` fields.

### Proof of Concept
Go unit test in `router/client_test.go`:
1. Construct one `*router.Client` with a mock `Delegate` whose `GetRouterDiscovery` returns `{ServerURL: "router-a", TLSData: tlsA}` for `RunnerConfig{Token: "tokenA"}` and `{ServerURL: "router-b", TLSData: tlsB}` for `RunnerConfig{Token: "tokenB"}`.
2. Call `c.RequestJob(ctx, configA, nil)` first (populates cache with router-a/tlsA).
3. Immediately call `c.RequestJob(ctx, configB, nil)` (still within TTL) and assert via a mock `ClientConnFactory.Dial` spy that the `DialTarget.URL` used equals `"router-a"` (not `"router-b"`) even though `Token` is `"tokenB"`, and that the returned job's `TLSData` equals `tlsA` instead of `tlsB` — proving cross-config data mixing.

func (c *Client) getRouterDiscovery(ctx context.Context, config common.RunnerConfig) *common.RouterDiscovery {
	c.mu.Lock()
	defer c.mu.Unlock()
	if c.discoExpiresAt.After(time.Now()) {
		c.metrics.recordCacheEvent(cacheHit)
		return c.disco
	}
	c.metrics.recordCacheEvent(cacheMiss)
	c.disco = c.delegate.GetRouterDiscovery(ctx, config)
	c.discoExpiresAt = time.Now().Add(discoveryTTL)
	if c.disco != nil {
		config.Log().Info("Using job router at " + c.disco.ServerURL)
	}
	return c.disco
}
