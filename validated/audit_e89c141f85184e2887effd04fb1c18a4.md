### Title
Signer skips tenure-extend legitimacy re-check at pre-commit/signing time, allowing a signature on a stale/non-canonical tenure-extend block - (File: `stacks-signer/src/chainstate/v2.rs`, `stacks-signer/src/v0/signer.rs`)

### Summary
The report's root cause — a check performed once against a live, mutable reference value (pool ratio / price) but never re-verified at the moment the action actually executes — has a direct analog here. `GlobalStateView::check_proposal` validates a tenure-extend block's `burn_view_consensus_hash`/idle-timeout legitimacy against the **live** tenure tip fetched at proposal-arrival time only. The equivalent "settlement" check that runs immediately before a signer casts its actual signature, `check_block_against_signer_db_state`, never re-verifies this condition. A single miner can exploit the timing gap between these two points to get a signature on a tenure-extend block whose burn-view justification is stale relative to the canonical chain at signing time.

### Finding Description
In `stacks-signer/src/chainstate/v2.rs`, `GlobalStateView::check_proposal` fetches the tenure tip live from the node (`client.get_tenure_tip(tenure_id)`) to compute `current_burn_view`, then compares it against the block's `tenure_extend.burn_view_consensus_hash` for both the full-extend and read-count-extend cases: [1](#0-0) [2](#0-1) 

This check only runs once, when the proposal first arrives and is evaluated in `handle_block_proposal` via `check_block_against_state`, before the block is submitted to the node for static/tx validation: [3](#0-2) 

The signature is not produced at that point, however. It is produced later, either at the "validate-ok" recheck or at the moment enough pre-commits (≥70% weight) accumulate — and the only recheck performed immediately before signing is `check_block_against_signer_db_state`, which handles solely the tenure-change-confirms-parent check and `check_latest_block_in_tenure`: [4](#0-3) 

Nowhere in that recheck are the tenure-extend `changed_burn_view` / `enough_time_passed` conditions re-evaluated. The project's own documentation confirms this is a deliberate scope limitation of the recheck, not an oversight elsewhere covered: [5](#0-4) 

So the equality being relied upon — "this tenure-extend's declared burn view matches (or legitimately supersedes) the canonical tip's burn view" — is checked against a live value at time T0 (proposal arrival) but the signature is committed at time T1 (pre-commit threshold crossing), with no re-verification in between. If a new sortition/burn block arrives in that window, the canonical burn view moves, and the signer's earlier "OK" from `check_proposal` at T0 is silently treated as still valid at T1.

### Impact Explanation
This breaks the "signed vs validated" / "approved-parent vs canonical" equality: a signer can cast its actual block signature on a tenure-extend block whose burn-view assumption no longer reflects the canonical chain at the moment of signing, without ever re-checking it. Because signatures accumulate asynchronously across signers (pre-commit threshold is met by whichever peers report in first), a slow signer can cross the 70% pre-commit threshold and sign strictly on the strength of peer pre-commits plus the narrower `check_block_against_signer_db_state` recheck — never re-confirming the tenure-extend legitimacy condition that was the actual basis for the original proposal-time acceptance. This is a "Critical" class outcome per the scope rules: a signer signing a non-canonical/stale block, achievable by the actions of the single sitting miner (who controls block content/timing) plus ordinary gossip propagation delay — no majority of colluding signers is required.

### Likelihood Explanation
The trigger condition (a new Bitcoin block/sortition landing between proposal broadcast and pre-commit-threshold signing) is a naturally occurring network event, not a contrived one; it is also something the current miner can deliberately court by delaying broadcast of its tenure-extend proposal until just before an anticipated burn block, or by exploiting normal signer response-latency variance. No secondary signer collusion, key compromise, or auth-token access is needed — only the ordinary gossip/pre-commit machinery already in the signer set's critical path.

### Recommendation
Extend `check_block_against_signer_db_state` (or add an equivalent gate immediately before `mark_pre_committed`/`mark_locally_accepted`) to re-run the tenure-extend-specific checks (`changed_burn_view`, `enough_time_passed`, replay-set state) against the *current* tenure tip at the moment the pre-commit threshold is crossed, mirroring how `check_latest_block_in_tenure` is already re-verified at that point. Alternatively, bind the tenure-extend legitimacy check to a value that cannot silently go stale (e.g., re-derive it from signer-local state that is updated on every burn-block arrival rather than a point-in-time RPC snapshot).

### Proof of Concept
1. Miner M is the active miner for tenure `T`. At burn view `X`, `T` becomes idle-eligible for a read-count extend, but not yet past `enough_time_passed`.
2. M constructs a tenure-extend block asserting `burn_view_consensus_hash = X` (i.e., `changed_burn_view = false`) and broadcasts it right as burn view is about to move to `X+1` (new sortition imminent).
3. Fast signers evaluate `check_proposal` while the tip is still `X`: `changed_burn_view=false`, but `enough_time_passed` was just barely satisfied → block accepted, submitted for node validation, and pre-committed.
4. Before a slower signer's pre-commit tally crosses 70%, burn view advances to `X+1` locally for that signer (new sortition observed) — meaning the tenure-extend's `burn_view_consensus_hash = X` no longer reflects the canonical tip it should confirm against.
5. When the slower signer's pre-commit weight crosses threshold, `check_block_against_signer_db_state` runs — but it only checks `check_tenure_change_confirms_parent`/`check_latest_block_in_tenure`, not the extend's burn-view legitimacy — so the signer signs anyway, per `stacks-signer/src/v0/signer.rs` lines 1803-1840 and the pre-commit flow in `docs/signer-flows.md` lines 425-433.         stacks_client: &StacksClient,
        proposed_block: &NakamotoBlock,

        let signer_signature_hash = proposed_block.header.signer_signature_hash();
        // If this is a tenure change block, ensure that it confirms the correct number of blocks from the parent tenure.
        if let Some(tenure_change) = proposed_block.get_tenure_change_tx_payload() {
            // Ensure that the tenure change block confirms the expected parent block
            match SortitionData::check_tenure_change_confirms_parent(
                tenure_change,
                proposed_block,
                &mut self.signer_db,
                stacks_client,

                self.proposal_config.reorg_attempts_activity_timeout,

Two things belong to the proposal path only and are **not** re-run at validate-ok
or at signing:

- `validate_tenure_change_payload` rejects with `DuplicateBlockFound` when we
  have already accepted a block in the tenure a tenure-change block is starting.
  v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1
  counts only globally accepted ones (`get_last_globally_accepted_block`).
- the v2 `check_proposal` wrapper checks miner pubkey hash, consensus hash, the
  pox bitvec, and tenure-extend rules before delegating here.
