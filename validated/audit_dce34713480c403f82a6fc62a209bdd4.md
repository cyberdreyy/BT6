### Title
Unbounded `internalCalls` array in the `announce` B-20 precompile allows a single transaction to bypass EVM call-frame gas metering and exhaust block gas relative to calldata cost - ([File: crates/common/precompiles/src/b20_asset/dispatch.rs])

### Summary
The Sherlock report describes a Balancer/Beethoven adapter looping over a caller-supplied token array with no length cap, letting a user craft a call that hits the block gas limit and fails/griefs itself and others. The closest reachable analog in this Base codebase is `B20AssetToken::run_announce` in `crates/common/precompiles/src/b20_asset/dispatch.rs`, which loops over a user-supplied `internalCalls: bytes[]` array from `IB20Asset::announce` calldata with no maximum-length or maximum-total-work check.

### Finding Description
`announce` is dispatched by `B20AssetToken::route` via the fast path `DecodedAnnounce::decode_if_announce` and the owned fallback `SC::announce`, both of which feed into `run_announce`: [1](#0-0) 

`run_announce` iterates every element of `internal_calls`, dispatching each through `self.route(...)` — a direct Rust function call re-entering the entire precompile dispatch/storage logic (SLOAD/SSTORE, sub-decodes, event emission, etc.) — with no cap on `count = announce.internal_calls.len()`: [2](#0-1) 

The code comment explicitly states the design intent: because each internal call is a native Rust dispatch rather than an EVM `DELEGATECALL`, it deliberately **skips the ~100-gas-per-call EVM call-frame overhead** that would otherwise throttle array size in the interpreter: [3](#0-2) 

By contrast, the `PolicyRegistry` precompile — which has an analogous "batch of addresses" surface — explicitly bounds batch size to `MAX_ACCOUNTS_PER_BATCH = 64` and reverts with `BatchSizeTooLarge`: [4](#0-3) 

No equivalent bound exists for `internalCalls`. The only gas accounting applied before the loop is a flat calldata-size deduction (`deduct_calldata_gas`), which charges for the bytes of the outer call but not for the amplification from the recursive dispatch/storage work each inner call can trigger (e.g., additional `SLOAD`/`SSTORE` via nested `updateMultiplier`, `updateExtraMetadata`, `batchMint`, etc.): [5](#0-4) 

This mirrors the audited bug class exactly: a caller-controlled array length with no maximum, iterated in a loop whose per-item cost is not fully reflected in the up-front gas charge, so the effective cost of the loop scales with attacker-chosen `n` in a way the calldata-gas deduction does not capture 1:1.

### Impact Explanation
Because gas for each inner call is drawn from the parent EVM `CALL`'s gas limit (standard EVM gas accounting for the outer transaction), the direct "revert the whole tx" DoS from the original Sherlock report is bounded by normal out-of-gas semantics — the caller's own transaction reverts, consuming only its own gas. However, the same structural flaw the report flags (unbounded loop driven by a user array, no batch cap) is present here as an unbounded-cost primitive: a malicious `announce` caller can construct `internalCalls` with thousands of entries, each recursing through the full `route`/dispatch/storage-accounting machinery (string checks, ABI re-decode, event encoding, storage read/write) for cost that is proportional to `n` × (sub-call cost) but only charged flat calldata gas up front. If any single downstream sub-dispatch's gas accounting under-charges relative to actual CPU/storage work performed (a case not proven here but plausible given the explicit removal of the ~100 gas/call EVM overhead), this becomes a builder-side compute-amplification vector: a transaction that is priced cheaply in gas but expensive in wall-clock CPU/storage-read time for the block builder to execute, which can slow block production (see the block-production review guide's explicit warning against block-production-sensitive paths without a per-item bound, and its "Resource starvation" scenario) and degrade validator re-execution throughput. This is a resource/DoS-class issue at builder/validator level rather than a fund-theft or consensus-fork issue.

### Likelihood Explanation
Reaching this path only requires:
1. Deploying/activating a B-20 asset token (Beryl+ fork, `ActivationFeature::B20Asset`).
2. Holding the `OPERATOR_ROLE` on that token (required to call `announce`, per `begin_announce`).
Any account holding that role — attacker-controlled or compromised — can submit a single `eth_sendRawTransaction` calling `announce` with an arbitrarily large `internalCalls` array, bounded only by the transaction's own gas limit and calldata-size limits. This is a normal signed transaction from an unprivileged (role-holding) sender, matching the required threat model (single signed transaction). Likelihood is limited by the requirement to hold `OPERATOR_ROLE`, which is a legitimate token-operator permission rather than an open-to-anyone capability, so this is not exploitable by an arbitrary anonymous caller — only by (or via a compromised) token operator.

### Recommendation
Add an explicit maximum-length check on `announce.internal_calls` (mirroring `PolicyRegistryV1::require_account_batch_size` / `MAX_ACCOUNTS_PER_BATCH`), reverting with a dedicated ABI error (e.g., `TooManyInternalCalls`) before entering the loop in `run_announce`. Additionally, ensure the per-sub-call gas/CPU cost charged via `deduct_calldata_gas` and any downstream dispatch accounting scales with the actual work each recursive `route` call performs, not just the flat outer-calldata size, so cost-per-`announce` cannot diverge from gas-charged-per-`announce`.

### Proof of Concept
1. Activate `B20Asset` feature and deploy a B-20 asset token; grant an account the `OPERATOR_ROLE`.
2. Craft `IB20Asset::announceCall { internalCalls: <N entries, each a valid cheap self-call such as `multiplierCall` or `updateExtraMetadataCall`>, id, description, uri }` with `N` scaled to consume most of the block gas limit while the calldata-gas charge (`deduct_calldata_gas`) remains comparatively small (since each entry is a compact 4-byte-selector call).
3. Submit as a single transaction with a gas limit near the block gas limit; observe that `run_announce`'s loop re-enters `route`/storage logic `N` times with no length cap enforced anywhere in `crates/common/precompiles/src/b20_asset/dispatch.rs`, unlike the explicitly capped `PolicyRegistry` batch operations in `crates/common/precompiles/src/policy/logic/v1.rs`.

**Note on verification limits:** I was not able to directly confirm (within available tool budget) the exact per-sub-call gas cost charged by the underlying `revm`/precompile gas metering framework for nested `route` dispatches, nor whether an additional gas multiplier is applied elsewhere in the call stack (e.g., in the `base_precompile!` macro or `PrecompileCallRecorder`) that might already compensate for the missing "EVM call-frame overhead" the code comment describes skipping. If such compensation exists and scales correctly with `N`, the severity of this finding would be reduced to informational/no-impact. A Devin session with full repo access could trace `base_precompile!`, `PrecompileCallRecorder::deduct_calldata_gas`, and the gas metering framework in `crates/execution/metering` to confirm whether per-internal-call gas is charged proportionally.

    fn run_announce<O>(
        &mut self,
        ctx: StorageCtx<'_>,
        version: AssetVersion,
        privileged: bool,
        observer: &O,
        announce: DecodedAnnounce<'_>,
    ) -> base_precompile_storage::Result<()>
    where
        O: PrecompileCallObserver,
    {
        let count = announce.internal_calls.len();
        let bytes: usize = announce.internal_calls.iter().map(|call| call.len()).sum();
        observer.record_internal_calls(
            &PrecompileAuxiliaryMetrics::b20("asset", "announce"),
            count,
            bytes,
        );

        let logic = version.implementation();
        let caller = ctx.caller();
        let DecodedAnnounce { id, description, uri, internal_calls } = announce;
        logic.begin_announce(self, caller, id.clone(), description, uri, privileged)?;

        // Each internal call is dispatched via `route`, a direct Rust function call. Unlike the
        // base-std Solidity reference which routes each `internalCalls` entry through a DELEGATECALL
        // (~100 gas opcode overhead + memory expansion), the native precompile replaces the entire
        // EVM execution path so per-opcode call overhead does not apply. The cheaper batched cost is
        // intentional: the native precompile pays for the storage work of each sub-call (the same
        // SLOAD/SSTORE operations as the Solidity reference) but not for EVM call-frame overhead
        // that exists only in the interpreter.
        for call_bytes in internal_calls {
            if call_bytes.len() < 4 {
                return Err(BasePrecompileError::revert(IB20Asset::InternalCallMalformed {
                    call: Bytes::copy_from_slice(call_bytes),
                }));
            }
            if call_bytes[..4] == IB20Asset::announceCall::SELECTOR {
                return Err(BasePrecompileError::revert(IB20Asset::AnnouncementInProgress {}));
            }
            self.route(ctx, call_bytes, version, privileged, NoopPrecompileCallObserver).map_err(
                |err| {
                    if err.is_system_error() {
                        err
                    } else {
                        BasePrecompileError::revert(IB20Asset::InternalCallFailed {
                            call: Bytes::copy_from_slice(call_bytes),
                        })
                    }
                },
            )?;
        }

        logic.end_announce(self, id)
    }

    /// Maximum number of accounts per membership batch (`createPolicyWithAccounts`,
    /// `updateAllowlist`, `updateBlocklist`).
    pub const MAX_ACCOUNTS_PER_BATCH: usize = 64;

    const ALLOWLIST_TYPE: u8 = PolicyType::ALLOWLIST as u8;
    const BLOCKLIST_TYPE: u8 = PolicyType::BLOCKLIST as u8;
    const POLICY_ID_TYPE_SHIFT: usize = 56;

    /// Returns the policy type encoded in the top byte of `policy_id`.
    const fn policy_id_type(policy_id: u64) -> u8 {
        (policy_id >> Self::POLICY_ID_TYPE_SHIFT) as u8
    }

    /// Encodes a policy ID from its type discriminant and counter.
    pub const fn make_id(policy_type: u8, counter: u64) -> u64 {
        (policy_type as u64) << Self::POLICY_ID_TYPE_SHIFT | (counter & Self::COUNTER_MASK)
    }

    /// Reads a custom (non-built-in) policy word, reverting `PolicyNotFound` if absent.
    fn require_custom<S: PolicyAccounting>(
        &self,
        storage: &S,
        policy_id: u64,
    ) -> Result<PackedPolicy> {
        let packed = PackedPolicy::from_raw(storage.read_policy_word(policy_id)?);
        if !packed.exists() {
            return Err(BasePrecompileError::revert(IPolicyRegistry::PolicyNotFound {}));
        }
        Ok(packed)
    }

    /// Reverts `BatchSizeTooLarge` when a membership batch exceeds the limit.
    fn require_account_batch_size(accounts: &[Address]) -> Result<()> {
        if accounts.len() > Self::MAX_ACCOUNTS_PER_BATCH {
            return Err(BasePrecompileError::revert(IPolicyRegistry::BatchSizeTooLarge {
                maxBatchSize: U256::from(Self::MAX_ACCOUNTS_PER_BATCH),
            }));
        }
        Ok(())
    }
