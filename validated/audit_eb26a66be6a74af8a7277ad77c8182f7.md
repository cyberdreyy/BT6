### Title
Pending BB withdrawals escape the first-loss waterfall through pro-rata receipt accounting - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
A KYC-passing BB holder can request a withdrawal before `stopEpochWithDuration` processes a loss, converting first-loss BB exposure into an untyped pending receipt. [1](#0-0)  `previewLossAdjustedWithdrawFunds` then assigns the pending receipt bucket only `loss * pendingBasis / (activeBasis + pendingBasis)`, regardless of whether the receipt came from AA or BB. [2](#0-1) 

### Finding Description
`requestWithdraw` does not require the epoch to still be running and is gated only by the withdrawal flags and `isWalletAllowed`. [3](#0-2)  For a normal request, the CDO calls `IdleCreditVault.requestWithdraw` with the claim amount and principal, then burns the user's tranche tokens and removes the principal from that tranche's NAV. [1](#0-0)  The strategy burns the CDO's principal-backed strategy tokens, mints a receipt for the claim amount, and adds that amount to the aggregate `pendingWithdraws` bucket. [4](#0-3) 

When the honest owner or manager later calls `stopEpochWithDuration`, the code explicitly discards the receipt's original tranche identity and gives all pending receipts the same pro-rata loss treatment. [5](#0-4)  Only the remaining `activeLoss` is then burned from CDO strategy tokens and passed through the normal BB-first waterfall. [6](#0-5)  The CDO waterfall assigns an active loss to BB before spilling any remainder into AA. [7](#0-6) 

For example, with zero interest and fees, 90 AA NAV, and 10 BB NAV, a 10-unit loss should wipe out BB while AA retains 90. If the sole BB holder first requests a withdrawal, `activeBasis` becomes 90 and `pendingBasis` becomes 10, so the pending bucket loses only `10 * 10 / 100 = 1`. [8](#0-7)  The attacker subsequently claims 9 units through the epoch's common `lossRecoveryPrice`, while the remaining 9-unit active loss is borne entirely by AA because active BB NAV is now zero. [9](#0-8) 

### Impact Explanation
This breaks the tranche loss waterfall and allows a BB holder to escape first-loss exposure by changing the position into an untyped pending receipt. [4](#0-3)  In the 90 AA / 10 BB example, the attacker receives 9 instead of 0 and AA holders lose 9 units that should have been absorbed by BB. [2](#0-1)  The loss is directly transferred to senior lenders and becomes permanent once the receipt is claimed. [10](#0-9) 

### Likelihood Explanation
The attack only requires an allowed wallet holding BB tranche tokens and an epoch in which a loss will be realized through `stopEpochWithDuration`. [3](#0-2)  Withdrawal requests are enabled by default for both tranches and can still be made after `epochEndDate` but before the epoch is stopped because `requestWithdraw` does not check `isEpochRunning` or `block.timestamp < epochEndDate`. [11](#0-10)  The attacker can monitor the manager's pending `stopEpochWithDuration` transaction and submit `requestWithdraw` first, without relying on a malicious privileged role. [12](#0-11) 

### Recommendation
Persist the tranche class and principal basis for each pending withdrawal, such as separate AA and BB receipt buckets per epoch. [13](#0-12)  Apply `stopEpochWithDuration` losses globally in seniority order: first to all pending and active BB basis pro rata, then to all pending and active AA basis pro rata. [14](#0-13)  Replace the single `lossRecoveryPriceByEpoch` with per-epoch, per-tranche recovery prices so pending BB receipts cannot receive the same protection as AA claims. [15](#0-14)  Alternatively, prevent new withdrawal requests after `epochEndDate`, although this only reduces mempool ordering risk and does not preserve BB seniority for earlier pending requests. [3](#0-2) 

### Proof of Concept
Add this regression test to the existing `test/foundry/IdleCreditVault.t.sol` fixture; it uses the same `cdoEpoch`, `strategy`, tranche, borrower, manager, and helper names used by the current suite. [16](#0-15) 

```solidity
function testPendingBBEscapesFirstLossWaterfall() external {
    uint256 aaAmount = 90_000 * ONE_SCALE;
    uint256 bbAmount = 10_000 * ONE_SCALE;
    uint256 lossAmount = 10_000 * ONE_SCALE;
    address junior = makeAddr("junior-loss-escape");

    vm.startPrank(owner);
    cdoEpoch.setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0);
    cdoEpoch.setIsAYSActive(false);
    vm.stopPrank();

    idleCDO.depositAA(aaAmount);
    _transferBurnedTrancheTokens(address(this), true);
    _depositWithUser(junior, bbAmount, false);

    // Remove interest from the example.
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);
    _startEpochAndCheckPrices(0);

    uint256 duration = cdoEpoch.epochDuration();
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Requests remain allowed after epochEndDate and before stopEpochWithDuration.
    vm.prank(junior);
    uint256 pendingBasis = cdoEpoch.requestWithdraw(0, address(BBtranche));
    assertEq(pendingBasis, bbAmount, "BB receipt basis mismatch");

    // activeBasis = 90k AA; pendingBasis = 10k ex-BB.
    // pendingLoss = 10k * 10k / 100k = 1k.
    // The borrower therefore funds 9k for the pending receipt.
    deal(defaultUnderlying, borrower, 9_000 * ONE_SCALE);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, duration, lossAmount);

    uint256 juniorBalanceBefore = underlying.balanceOf(junior);
    vm.prank(junior);
    cdoEpoch.claimWithdrawRequest();

    assertEq(
        underlying.balanceOf(junior) - juniorBalanceBefore,
        9_000 * ONE_SCALE,
        "pending BB did not escape first-loss treatment"
    );
    assertEq(cdoEpoch.lastNAVBB(), 0, "BB NAV should have been fully withdrawn");
    assertEq(cdoEpoch.lastNAVAA(), 81_000 * ONE_SCALE, "AA absorbed the escaped loss");
}
```

```text
  /// @notice Preview how a realized stop-epoch loss is split between active LPs and pending receipts.
  /// @dev Without pending receipts, a loss cannot exceed its active basis. When pending receipts
  /// exist, all pending receipts share their aggregate portion of the loss pro rata because the
  /// pending bucket does not retain tranche identity. The remaining active loss is later applied
  /// by the CDO through its ordinary BB-first waterfall.
  /// @param _lossAmount realized loss amount
  /// @return pendingToFund amount of pending withdrawals that should be funded by the borrower
  /// @return activeLoss amount of loss that remains assigned to active LPs
  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;
```
