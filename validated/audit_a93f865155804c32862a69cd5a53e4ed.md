### Title
Missing Per-Client Rate Limiting on the JSON-RPC HTTP Endpoint Enables Resource Exhaustion - (File: rpc/src/rpc_service.rs)

### Summary
The validator's JSON-RPC HTTP server, configured in `JsonRpcService::new` in [1](#0-0) , applies only a maximum request body size and CORS policy to incoming requests. There is no per-IP or per-client request-rate throttling anywhere in the RPC HTTP request path, unlike the QUIC/TPU ingest path which implements multiple layers of rate limiting.

### Finding Description
`JsonRpcService::new` builds the HTTP JSON-RPC server using `jsonrpc_http_server::ServerBuilder`, configuring only `.cors(...)`, `.cors_max_age(86400)`, `.request_middleware(request_middleware)`, and `.max_request_body_size(max_request_body_size)` before calling `.start_http(&rpc_addr)` [2](#0-1) . `RpcRequestMiddleware` only handles static file/snapshot download routing (`is_file_get_path`, `redirect`, `not_found`, `internal_server_error`) [3](#0-2)  and performs no per-source throttling of RPC method invocations.

By contrast, the QUIC/TPU transaction ingest path implements defense-in-depth rate limiting: a global `TokenBucket` capping total new connections per second, a per-IP `ConnectionRateLimiter` capping connections per minute, and stake-weighted per-connection stream throttling via `SwQos`/`throttle_stream` [4](#0-3) [5](#0-4) . No analogous mechanism protects the RPC HTTP surface: a client can open unlimited concurrent HTTP connections and issue requests at arbitrary rates limited only by body size, `rpc_threads`, and `rpc_blocking_threads` [6](#0-5) .

Some individual costly RPC methods (e.g. `getProgramAccounts` via secondary index) have byte-size limits on the *result* of a single scan (`scan_results_limit_bytes` / `byte_limit_for_scan`) [7](#0-6) , but this bounds only the size of one response, not the aggregate rate or concurrency of such calls a single client (or many spoofable HTTP clients) can issue against the shared `rpc_blocking_threads` pool and `accounts_db` scan machinery.

### Impact Explanation
An attacker can flood the RPC HTTP endpoint with cheap or moderately expensive JSON-RPC calls (or unindexed `getProgramAccounts` scans) at a rate bounded only by network throughput, exhausting `rpc_blocking_threads`/`rpc_threads` and CPU, and starving legitimate RPC clients — a direct availability impact for any node exposing `--full-rpc-api` or the base JSON-RPC surface. Because CORS is `AllowOnly(Any)` [8](#0-7) , any web-based attacker can also drive load from browsers. This matches the report's core class (unthrottled API request volume causing resource exhaustion/unavailability), scoped here to unprivileged RPC request handling.

### Likelihood Explanation
High for any validator/RPC node with an RPC port reachable by ordinary clients (i.e., not solely `--private-rpc`). No special privileges, keys, or protocol-level trust are required — this is directly reachable from an ordinary user's RPC call, consistent with the "RPC request handling" scope in this analysis. Operators typically front nodes with reverse proxies/Cloudflare, but the validator binary itself provides no built-in throttling as a defense-in-depth layer, unlike the QUIC ingest path.

### Recommendation
Add a per-IP (and optionally per-API-key) token-bucket/rate limiter to the JSON-RPC HTTP request path analogous to `ConnectionRateLimiter`/`TokenBucket` already used for QUIC in [9](#0-8) , enforced inside `RpcRequestMiddleware` or as an additional `jsonrpc_http_server` middleware layer before request execution. Return HTTP 429 with a `Retry-After` header (already consumed by the client in `http_sender.rs` [10](#0-9) , showing the client already expects this signal) when limits are exceeded, and expose the limiter thresholds as validator CLI arguments similar to `rpc_max_request_body_size`.

### Proof of Concept
1. Start a validator with `--full-rpc-api` and default RPC config (no external reverse proxy/WAF).
2. From a single or spoofed set of source IPs, send JSON-RPC requests (e.g., repeated `getProgramAccounts` without filters, or high-frequency `getAccountInfo`) at a rate far exceeding legitimate traffic (analogous to the 300 req/min PoC in the original report, but unbounded here since no throttling exists).
3. Observe `rpc_blocking_threads`/`rpc_threads` saturation and increased latency/failure for concurrent legitimate RPC clients, confirming the JSON-RPC HTTP endpoint has no built-in rate limiting to mitigate the flood, unlike the QUIC/TPU path.

pub fn service_runtime(
    rpc_threads: usize,
    rpc_blocking_threads: usize,
    rpc_niceness_adj: i8,
) -> Arc<TokioRuntime> {
    // The jsonrpc_http_server crate supports two execution models:
    //
    // - By default, it spawns a number of threads - configured with .threads(N) - and runs a
    //   single-threaded futures executor in each thread.
    // - Alternatively when configured with .event_loop_executor(executor) and .threads(1),
    //   it executes all the tasks on the given executor, not spawning any extra internal threads.
    //
    // We use the latter configuration, using a multi threaded tokio runtime as the executor. We
    // do this so we can configure the number of worker threads, the number of blocking threads
    // and then use tokio::task::spawn_blocking() to avoid blocking the worker threads on CPU
    // bound operations like getMultipleAccounts. This results in reduced latency, since fast
    // rpc calls (the majority) are not blocked by slow CPU bound ones.
    //
    // NB: `rpc_blocking_threads` shouldn't be set too high (defaults to num_cpus / 2). Too many
    // (busy) blocking threads could compete with CPU time with other validator threads and
    // negatively impact performance.
    let rpc_threads = 1.max(rpc_threads);
    let rpc_blocking_threads = 1.max(rpc_blocking_threads);
    Arc::new(
        TokioBuilder::new_multi_thread()
            .worker_threads(rpc_threads)
            .max_blocking_threads(rpc_blocking_threads)
            .on_thread_start(move || renice_this_thread(rpc_niceness_adj).unwrap())
            .thread_name("solRpcEl")
            .enable_all()
            .build()
            .expect("Runtime"),
    )

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
}

/// Limits the rate of connections per IP address.
pub struct ConnectionRateLimiter {
    limiter: KeyedRateLimiter<IpAddr>,
}

/// The threshold of the size of the connection rate limiter map. When
/// the map size is above this, we will trigger a cleanup of older
/// entries used by past requests.
const CONNECTION_RATE_LIMITER_CLEANUP_SIZE_THRESHOLD: usize = 100_000;

impl ConnectionRateLimiter {
    /// Create a new rate limiter per IpAddr. The rate is specified as the count per minute to allow for
    /// less frequent connections. Higher limit also allows higher bursts.
    /// num_shards controls how many shards are used in the underlying dashmap,
    /// should be set >= number of contending threads.
    pub fn new(limit_per_minute: u64, max_burst: u64, num_shards: usize) -> Self {
        Self {
            limiter: KeyedRateLimiter::new(
                CONNECTION_RATE_LIMITER_CLEANUP_SIZE_THRESHOLD,
                TokenBucket::new(limit_per_minute, max_burst, limit_per_minute as f64 / 60.0),
                num_shards,
            ),
        }
    }

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }

    pub fn register_connection(&self, ip: &IpAddr) -> bool {
        if self.limiter.consume_tokens(*ip, 1).is_ok() {
            debug!("Request from IP {ip:?} allowed");
            true // Request allowed
        } else {
            debug!("Request from IP {ip:?} blocked");
            false // Request blocked
        }
    }
}
