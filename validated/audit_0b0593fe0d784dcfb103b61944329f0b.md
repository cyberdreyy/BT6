Based on my investigation, the closest analog to the "recording phase" bug in this codebase is the **tenure-supersession permit mechanism** used for reorg validation, which records a blanket exemption once and later trusts it without re-checking the conditions it was granted under.

### Title
Reorg-permit recording under-counts signer-consensus blocks, letting a single miner permanently exempt an already-signed tenure from the double-sign guard - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_parent_tenure_choice` decides whether a new tenure may legitimately reorg a previous one, and — once it decides "yes" — calls `SignerDb::mark_tenure_superseded` to *record* a permanent exemption (`superseded_tenures` table) for that prior tenure. From then on, `Signer::reorg_permit_stands` only re-checks that the *permitting* sortition is still canonical; it never re-derives whether the exemption itself was safe. The initial "recording" decision is gated on `get_globally_accepted_block_count_in_tenure` (blocks the *node* has confirmed), while the conflict system elsewhere treats a block that merely reached the signer supermajority (`signed_group`, a "bearer instrument") as equally blocking, even before the node ever sees it. This mismatch lets a miner engineer a tenure that reaches full 70% signer sign-off on more than one block (satisfying the real double-sign guard's own definition of "conflict") while keeping the node's confirmed count at 0 or 1, then mine a following tenure whose first block is timed to qualify as a "reorg", permanently voiding the earlier tenure's already-fully-signed blocks as conflicts.

### Finding Description
The double-sign guard treats any block that reached `signed_self` or `signed_group` as a live conflict regardless of node confirmation: [1](#0-0) 
and the design doc explicitly states this is intentional — "*A conflict is any block a signature was ever put over — ours, or a group threshold we observed — whatever its state now.*" [2](#0-1) 

However, `check_parent_tenure_choice` decides whether to *permanently exempt* a whole tenure from ever counting as a conflict (via `mark_tenure_superseded`) using a strictly weaker signal — the count of **globally accepted** (node-confirmed) blocks, not signer-consensus (`signed_group`) blocks: [3](#0-2) 

and only the *first* block's proposal-to-sortition timing is checked before the whole tenure is queued for supersession: [4](#0-3) 

Once superseded, the record is durable (until `MAX_FORK_DEPTH` = 100 burn blocks pass) and the only re-validation performed at signing time is whether the *permitting* tenure's sortition is still canonical — not whether the superseded tenure's actual block/signature state still justifies the exemption: [5](#0-4) [6](#0-5) 

The pre-commit path applies this permit as an unconditional exclusion before any freshness/liveness check runs: [7](#0-6) 

So the "recording" happens once, based on the *node's* confirmed view (which a miner can keep at 0/1 by withholding/delaying broadcast of an already-fully-signed block), and the recorded permit is trusted forever afterward, exactly like the SphereX report's pattern of an under-scrutinized initial recording being blindly relied upon once "TVL" (here, tenure supersession) is exploited.

### Impact Explanation
This lets a signer place a signature on a block in a new tenure that reorgs a prior tenure whose blocks the signer set had *already reached full 70% signature consensus on* (a bearer instrument by the code's own definition) but which never reached the node — the exact double-sign the guard exists to prevent. That is a **Critical** impact per the rules: a signer producing a signature over a conflicting/non-canonical block, i.e. breaking the "at most one signed tip per height" equality the pre-commit conflict guard is meant to enforce.

### Likelihood Explanation
Triggerable by a single winning miner (one slot) plus ordinary signer gossip: the miner needs only (a) to produce more than one block in a tenure that individually reach the 70% signer threshold while preventing/delaying node confirmation of them (e.g., by racing/dropping the `NewBlock` announcement, or exploiting normal network latency), and (b) mine the very next tenure's first block quickly enough to satisfy `first_proposal_burn_block_timing`. No majority-signer collusion, extra keys, or `auth_token`/local access is required — this is exactly the "reachable path" scope specified.

### Recommendation
Gate `check_parent_tenure_choice`'s supersession decision on the same signal the conflict guard itself treats as blocking — i.e., use a count/check based on `signed_self`/`signed_group` (any block a signature was ever placed over), not solely `get_globally_accepted_block_count_in_tenure`. Alternatively, re-derive the permit's safety per-evaluation (as is already done for ordinary conflicts via `conflict_still_blocks`) instead of durably recording a blanket exemption based on a stale, incomplete snapshot.

### Proof of Concept
1. Miner M1 wins tenure T1's sortition and proposes block B1a. Signers validate and each broadcast a pre-commit/signature; the signer set reaches 70% signed weight on B1a (`signed_group` set), but the resulting aggregate signature is not yet delivered to/processed by the stacks-node (e.g., M1 or a partitioned relay delays `handle_post_block`).
2. M1 proposes a second block B1b in the same tenure T1 timed close to (or after) the point where the node would still show 0 or 1 globally-accepted blocks for T1; if needed, B1a can even be the sole "first" block that timed close to the sortition boundary.
3. M1 wins the next sortition (tenure T2) whose first block's proposal-to-sortition timing satisfies `first_proposal_burn_block_timing` in `check_parent_tenure_choice` (stacks-signer/src/chainstate/mod.rs:247-274). Since `get_globally_accepted_block_count_in_tenure(T1) <= 1` (node never confirmed B1a/B1b), the check passes and `mark_tenure_superseded(T1, ..., T2, ...)` permanently records the exemption.
4. Any subsequent pre-commit evaluation for a T2 block sees T1's blocks (including B1a/B1b, which already reached full signer-set signature) filtered out as conflicts via `reorg_permit_stands`, which only checks that T2's sortition is canonical (stacks-signer/src/v0/signer.rs:1222-1247) — it never re-examines that B1a genuinely reached signer consensus.
5. Signers now sign T2's conflicting blocks even though a fully-signed, un-recalled B1a from T1 exists, producing two independently-signed, conflicting blocks at overlapping heights — the equivocation the guard was built to prevent.
