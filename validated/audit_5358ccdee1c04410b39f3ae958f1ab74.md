### Title
Windows job-object assignment TOCTOU allows a CI script to spawn a grandchild process that escapes job containment - ([File: helpers/process/job_windows.go])

### Summary
`osCmd.Start()` starts the job's process with `c.internal.Start()` and only afterwards calls `AssignPidToJobObject` to place it into the Windows job object. In the window between these two calls the freshly-started process is not yet a job member, so any child process it spawns during that window is never associated with the job and is not retroactively added when the parent later joins. That grandchild survives `Wait()`/`closeJobObject()` (and `ForceKill`/`taskkill`) and continues running on the host after the job is supposed to be finished/killed.

### Finding Description
In `helpers/process/job_windows.go`: [1](#0-0) 

The sequence is:
1. `CreateJobObject()` creates the job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`.
2. `c.internal.Start()` launches the process (the attacker's shell/PowerShell script for the shell executor) — the process begins executing immediately, it is not started suspended.
3. Only afterwards is `AssignPidToJobObject(c.internal.Process.Pid, c.jobObject)` called to add the running process to the job.

Windows job object semantics require a process to already be a member of a job *at the moment it creates a child* for that child to automatically inherit membership. `AssignProcessToJobObject` only adds the specified PID — it does not retroactively enroll any children the process already spawned before the assignment. Since the script (attacker-controlled CI job content, reached via the shell executor at `executors/shell/shell.go`'s `Run` which builds the `Commander` with `UseWindowsJobObject` when that feature flag is enabled) starts executing before step 3 completes, a script that forks/spawns a child process immediately at startup can create a process that is never part of the job. This grandchild is unaffected by `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, so it is not killed by `closeJobObject()` in `Wait()`, nor by `ForceKill`/`taskkill /T` paths in `helpers/process/killer_windows.go` that rely on job/process-tree termination: [2](#0-1) 

There is no mitigation such as starting the process suspended (`CREATE_SUSPENDED`) and assigning it to the job before resuming its main thread, which is the standard fix for this class of TOCTOU on Windows.

### Impact Explanation
Under the `UseWindowsJobObject` feature flag (opt-in, default false) used by the shell/custom executors on Windows, a CI job author can cause a subprocess to escape the job object that Runner relies on to guarantee cleanup/termination of all job descendants. This subprocess keeps running on the host after the job is cancelled/completed and after the job object is closed, i.e., attacker-controlled code execution that outlives the job and is not subject to Runner's forced-kill/cleanup logic — a containment/resource-persistence violation on the runner host.

### Likelihood Explanation
Requires `UseWindowsJobObject` to be enabled (opt-in feature flag) and the shell/custom executor on Windows. Given that, the race window between `c.internal.Start()` returning and `AssignPidToJobObject` executing is real and attacker-triggerable deterministically: a script that forks a background/detached child process as its very first statement has a high chance of finishing that spawn before the runner's Go code executes `AssignPidToJobObject` (a syscall-based `OpenProcess`+`AssignProcessToJobObject`), especially under CPU contention. Repeating the fork attempt (e.g., spawning N children in a tight loop at start) makes at least one escape essentially certain.

### Recommendation
Avoid the race by creating the process suspended and assigning it to the job object before resuming its main thread, e.g. set `CREATE_SUSPENDED` in `SysProcAttr.CreationFlags`, call `c.internal.Start()`, immediately call `AssignPidToJobObject`, and only then call `ResumeThread` on the primary thread (via `NtResumeProcess`/`ResumeThread` on the main thread handle). This closes the window entirely so no child of the target process can ever be created before job membership is established.

func (c *osCmd) Start() error {
	setProcessGroup(c.internal, c.options.UseWindowsLegacyProcessStrategy)

	if c.options.UseWindowsJobObject {
		jobObj, err := CreateJobObject()
		if err != nil {
			return fmt.Errorf("starting OS command: %w", err)
		}
		c.jobObject = jobObj
	}

	err := c.internal.Start()
	if err != nil {
		return fmt.Errorf("starting OS command: %w", err)
	}

	if c.options.UseWindowsJobObject {
		// Any failures here are ignored, since we've already started the process running.
		if err := AssignPidToJobObject(c.internal.Process.Pid, c.jobObject); err != nil {
			c.options.Logger.Warn("assigning process to job object:", err)
		}
	}
	return nil
}

func (pk *windowsKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := taskKill(pk.cmd.Process().Pid)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}

	pk.cmd.closeJobObject()
}
