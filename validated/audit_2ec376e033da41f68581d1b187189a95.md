### Title
Cross-user response hijacking via `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores the caller's `handlers.Callback` in `h.savedCallbacks` keyed solely by the attacker-supplied `msg.Body.MessageId`, with no check for an existing/pending entry and no binding to the sender's identity. Because `MessageId` is a fully client-chosen field validated only for length and null-suffix, a second signed message using the same `MessageId` as a pending legitimate request silently overwrites the first caller's callback, so the DON's later response is delivered to the second (attacker) caller instead of the first (victim).

### Finding Description
`HandleLegacyUserMessage` unconditionally writes to the shared map without checking for a pre-existing key: [1](#0-0) 

The map is later read/deleted by whichever `MessageId` a DON node echoes back in `handleWebAPITriggerMessage`: [2](#0-1) 

`MessageId` is entirely attacker-controlled input from the signed message body — `Message.Validate()` only checks length bounds (`1..MessageIdMaxLen`) and that it doesn't end in a null byte; it performs no uniqueness or per-sender namespacing: [3](#0-2) 

Critically, the signature only proves who signed the message (`m.Body.Sender`), it does not bind `MessageId` ownership to a sender in the `savedCallbacks` map — the map key is the raw string `MessageId`, shared across all callers of the same DON handler instance. Any unauthenticated (but validly-signed, e.g. by any known EOA/API-token capable of hitting the gateway's legacy trigger route) attacker can submit `HandleLegacyUserMessage` with a `MessageId` equal to a value the victim is concurrently using. Because line 412 does a plain map assignment rather than a compare-and-swap or "reject if exists" check, the attacker's `Callback` replaces the victim's `Callback` in the map. When the DON later responds with that same `MessageId` (originally addressed to the victim's request, since the underlying JSON-RPC request/response correlation is also keyed by the same ID via `ValidatedRequestFromMessage`/`ValidatedMessageFromResp`), `handleWebAPITriggerMessage` looks up the map by ID and invokes `savedCb.SendResponse(...)` — which now resolves to the attacker's callback, delivering the victim's response to the attacker.

### Impact Explanation
This breaks per-user isolation of gateway responses (cross-user response hijack / request-response confusion), matching Chainlink's "unauthorized access to another user's data/response" impact class. In the worst case an attacker can capture the DON's execution result intended for a victim's HTTP trigger request, potentially exposing sensitive computed data or execution results the attacker was never authorized to see, and simultaneously deny the victim any response.

### Likelihood Explanation
Exploitability depends entirely on the attacker's ability to predict or brute-force a victim's `MessageId`. If client-side implementations generate high-entropy, unpredictable IDs (e.g., UUIDv4), an attacker practically cannot guess the exact ID within the request's narrow in-flight window (order of seconds), making exploitation infeasible in practice. However, nothing in this handler enforces uniqueness, sender ownership, or ID unpredictability — the vulnerability is a missing invariant in the code itself (no "reject on collision" or "namespace by sender" logic), so any deployment/client that uses short, sequential, timestamp-based, or otherwise predictable/short `MessageId`s (explicitly called out as a stated precondition) is immediately and repeatably exploitable by any unprivileged, validly-signed sender.

### Recommendation
- In `HandleLegacyUserMessage`, before inserting into `savedCallbacks`, check whether an entry for `msg.Body.MessageId` already exists; if so, reject the new request (e.g., return a `HandlerError`/conflict response) instead of silently overwriting.
- Namespace the `savedCallbacks` map key by `(sender, MessageId)` or `(DonId, sender, MessageId)` rather than by `MessageId` alone, so no unrelated sender can ever collide with another sender's pending callback.
- Additionally validate/enforce a minimum entropy or gateway-generated component for `MessageId` server-side rather than trusting a purely client-chosen value for correlation.

### Proof of Concept
Go handler-level integration test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler with a fake `handlers.DON` mock and two `handlers.Callback` mocks: `victimCallback` and `attackerCallback` (each recording the `UserCallbackPayload` it receives).
2. Call `h.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)` where `victimMsg` is validly signed by "victim" key with `MessageId = "M1"`.
3. Immediately call `h.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)` where `attackerMsg` is validly signed by a different "attacker" key but reuses `MessageId = "M1"`.
4. Assert `h.savedCallbacks["M1"].Callback == attackerCallback` (confirms overwrite).
5. Simulate the DON's response via `h.HandleNodeMessage(ctx, respWithID_M1, nodeAddr)` (routes to `handleWebAPITriggerMessage`).
6. Assert `attackerCallback.SendResponse` was invoked with the DON's response payload, and `victimCallback.SendResponse` was never called — demonstrating the victim's response was hijacked by the attacker's callback.
7. Expected fix behavior: step 3 should either fail/return an error (duplicate `MessageId` rejected) or `savedCallbacks["M1"]` should remain bound to `victimCallback`, and step 6 should invoke `victimCallback.SendResponse`, not the attacker's.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
