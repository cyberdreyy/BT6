### Title
Loss-adjusted withdrawal haircut is keyed to `lastWithdrawRequest`, so stale-epoch receipts escape the haircut and claim at par, draining funds owed to haircutted claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The CVE-2024-49882 analog is a stale-pointer/double-release bug: `ext4_ext_try_to_merge_up()` released `path[1].p_bh` without clearing the slot, so a later cleanup released it again. In `IdleCreditVault`, `collectWithdrawFunds` applies a shortfall haircut to the *aggregate* `pendingWithdraws` bucket but stores the recovery price under only the current `epochNumber`, while `_claimLossAdjustedWithdrawRequest` looks the price up via the per-user pointer `lastWithdrawRequest[_user]`. Any user whose last request epoch differs from the funding epoch never sees the haircut and is paid at par through `_claimFundedWithdrawRequest`, i.e. the same debt is "released" (paid) at full value although it was only partially funded.

### Finding Description
`requestWithdraw` records requests in the aggregate `withdrawsRequests[_user]` and per-epoch `withdrawsRequestsByEpoch[_user][currentEpoch]`, bumps `pendingWithdraws`, and stores `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) . The contract's own comments confirm a user may stack unclaimed receipts across epochs: "if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests" [2](#0-1) .

When the borrower under-funds a stop (`stopEpochWithDuration` with `_lossAmount`), `collectWithdrawFunds` sets `pendingWithdraws = 0` and writes the haircut to `lossRecoveryPriceByEpoch[epochNumber]` — one epoch key for the whole multi-epoch bucket [3](#0-2) . `previewLossAdjustedWithdrawFunds` explicitly prices the haircut pro rata over the entire `pendingBasis`, which includes receipts from prior epochs [4](#0-3) .

The claim path, however, only finds the haircut through `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` [5](#0-4) . A holder whose last request was made in an earlier epoch `E` (still pending inside `pendingWithdraws` when the loss was taken in epoch `F`) has `lossRecoveryPriceByEpoch[E] == 0`, skips `_claimLossAdjustedWithdrawRequest`, and falls into `_claimFundedWithdrawRequest`. Once `epochNumber > E` the epoch gate passes and the full `withdrawsRequests[_user]` is paid at par via `_transferFundedClaim` [6](#0-5) . The guard in `requestWithdraw` that forces claiming a loss-adjusted receipt before a new request only protects users whose `lastWithdrawRequest` already equals the loss epoch; it cannot catch receipts stranded on older epochs [7](#0-6) .

### Impact Explanation
Broken invariant: one receipt, one (haircutted) payout. Under-funded `pendingWithdraws` is paid out as if fully funded for every user whose `lastWithdrawRequest` is not the funding epoch. With a partial recovery price `p < 1`, the strategy holds only `pendingBasis * p` for the whole bucket; each stale-epoch claimer withdraws 100 cents on the dollar. This is direct insolvency: earlier/stale-epoch claimants over-draw, and the remaining claimants' `_transferFundedClaim` calls revert on insufficient balance — permanent freezing of the residual haircutted claims up to the aggregate overpayment. Quantified loss for the haircutted cohort: `sum(staleEpochReceipts) * (1 - p)`, which can be the entire funded remainder.

### Likelihood Explanation
Requires only unprivileged lenders who request withdrawals in two consecutive epochs without claiming between them — normal, documented usage. Trigger conditions: (1) a user leaves an unclaimed request from epoch `F-1` pending; (2) epoch `F` ends via `stopEpochWithDuration` with `0 < _lossAmount < totalBasis` (borrower partial repayment / realized loss), so `lossRecoveryPriceByEpoch[F]` is written; (3) the stale-epoch user calls `claimWithdrawRequest` and is paid at par. An attacker can also deliberately engineer this by requesting a small withdrawal in an early epoch, keeping it unclaimed, requesting again, then racing to claim first after a lossy stop to drain the haircutted bucket. No privileged misbehavior needed; `manager`/`borrower` calls follow their honest paths. The existing `_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve`, not the funded-claims pool [8](#0-7) .

### Recommendation
Make the loss claim reachable for every receipt covered by the haircutted `pendingWithdraws`, not just those whose `lastWithdrawRequest` equals the funding epoch. Options: (a) at `collectWithdrawFunds` partial-funding time, write `lossRecoveryPriceByEpoch` for every outstanding request epoch or store a single global `pendingLossRecoveryPrice` consumed by `_claimLossAdjustedWithdrawRequest` regardless of epoch; (b) iterate/clear `withdrawsRequestsByEpoch` for all epochs ≤ funding epoch inside the claim; (c) enforce at `requestWithdraw` that any unclaimed receipt (not only loss-epoch ones) is claimed first once a loss can occur, e.g. revert whenever `withdrawsRequests[_user] != 0` — noting this changes the documented "wait another epoch to claim both" UX. After the fix, add a test where a user holds receipts from two epochs, a lossy `stopEpochWithDuration` runs, and both receipts are paid at the same `lossRecoveryPrice`.

### Proof of Concept
Foundry fork-style sequence (extend `test/foundry/IdleCreditVault.t.sol` setup):

```solidity
// epoch N: user1 requests withdraw, never claims
_requestWithdrawWithUser(user1, 100e6);
_stopCurrentEpoch();                    // epoch N ends, receipt funded -> withdrawsRequests[user1] set, lastWithdrawRequest[user1] = N

// epoch N+1: user1 requests again (allowed: no lossRecoveryPrice yet)
vm.prank(manager); cdoEpoch.startEpoch();
_requestWithdrawWithUser(user1, 100e6); // lastWithdrawRequest[user1] = N+1, pendingWithdraws = 200e6 (+user2's)

// user2 also has 200e6 pending in epoch N+1
_requestWithdrawWithUser(user2, 200e6);

// borrower underpays: stopEpochWithDuration with lossAmount so pendingToFund < pendingBasis
uint256 pendingBasis = strategy.pendingWithdraws();
uint256 loss = pendingBasis / 2;
(uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(loss);
// fund borrower, then:
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(apr, 0, duration, loss);
// collectWithdrawFunds writes lossRecoveryPriceByEpoch[epochNumber==N+1] ~ 0.5e18, pendingWithdraws=0

// BUG: user1's lastWithdrawRequest is N+1? -> haircut applies only to epoch N+1 piece;
// if user1's last request had been in epoch N (i.e. second request made by another user),
// lossRecoveryPriceByEpoch[N] == 0 and _claimLossAdjustedWithdrawRequest returns 0.
// Arrange user1 with lastWithdrawRequest = N only (request once in N, a second user drives N+1):
vm.prank(user1); cdoEpoch.claimWithdrawRequest();
// _claimFundedWithdrawRequest pays full withdrawsRequests[user1] at par
// assert: user1 received 100% although lossRecoveryPrice ~ 50%
// assert: strategy balance now < remaining haircutted claims -> user2 claim reverts NotAllowed/transfer fail
```

Concrete minimal variant: user1 requests in epoch N only; user2 requests in epoch N+1; a lossy stop in epoch N+1 writes `lossRecoveryPriceByEpoch[N+1]`. `user1` (`lastWithdrawRequest = N`) skips the loss branch entirely and is paid at par; `user2` gets `claimBasis * p`, and the strategy's funded balance is exhausted before all claims settle — the deficit equals `user1Basis * (1 - p)`.

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
```
