### Title
Global (non-scoped) `requestID` keyspace in `setupCallback` allows any authorized workflow caller to pre-squat another user's request ID and trigger a targeted `ErrConflict` denial-of-service - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`httpTriggerHandler.setupCallback` deduplicates in-flight requests using a single global map keyed only by the client-supplied `requestID` string, with no scoping to `workflowID` or the caller's `AuthorizedKey`. Because `authorizeRequest` only validates that the caller is authorized for *some* workflow (not that the `requestID` belongs to them), any unprivileged-but-authorized caller can pre-register (or race) a `requestID` that a victim is expected to use, causing the victim's legitimate request to be rejected with `jsonrpc.ErrConflict`.

### Finding Description
In `HandleUserTriggerRequest` [1](#0-0) , the flow is: `validatedTriggerRequest` → `resolveWorkflowID` → `authorizeRequest` (JWT/key check scoped to the resolved `workflowID`) → `checkRateLimit` → `setupCallback`. `authorizeRequest` only confirms the caller holds an `AuthorizedKey` for the workflow they claim in their own request; it performs no check tying the client-supplied `req.ID` to any particular caller or workflow [2](#0-1) .

The actual conflict check lives in `setupCallback`, which stores callbacks in `h.callbacks map[string]savedCallback // requestID -> savedCallback` — a single map for the entire gateway, keyed purely by the string `requestID`, with no `workflowID` or key component in the key [3](#0-2) . The dedup logic is:

```go
if _, found := h.callbacks[requestID]; found {
    h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, ...)
    return nil, fmt.Errorf("in-flight request ID: %s", requestID)
}
``` [4](#0-3) 

Because the map key has no per-caller/per-workflow namespace, any caller who is validly authorized for *any* workflow (their own, low-quota workflow included) can submit a request whose `requestID` collides with an ID a victim is expected to use (e.g., a predictable/sequential/session-based ID generated by the victim's client). Whichever request is stored second is rejected with `ErrConflict`. If the attacker's request lands first, the victim's subsequent legitimate submission is denied service — without the attacker ever needing the victim's `AuthorizedKey` or access to the victim's workflow.

This is not actually about the ordering of `authorizeRequest` vs. `checkRateLimit`/`setupCallback` per se — reordering those checks would not close the gap, since the collision surface is a shared, unscoped map. The root cause is that `setupCallback`'s uniqueness check has no relationship to caller identity or workflow, so authorization succeeding for the attacker's own (unrelated) workflow is sufficient to squat any `requestID` value gateway-wide.

### Impact Explanation
The impact is confined to denial of service: a losing party receives `jsonrpc.ErrConflict` and their request is never dispatched to the DON via `sendWithRetries`/`sendToShard`. There is no cross-user data leakage — `HandleNodeTriggerResponse` routes aggregated responses strictly by the stored `savedCallback` for that exact `requestID`, and only one of the two colliding submissions ever gets a `savedCallback` entry [5](#0-4) . This matches a griefing/availability-impact class (targeted request denial) rather than an authentication bypass, key disclosure, or cross-user response confusion.

### Likelihood Explanation
- Attacker needs only valid `AuthorizedKey`/JWT credentials for *any* workflow they control — not the victim's key or workflow membership — satisfying the "unprivileged attacker" model.
- Exploitability depends entirely on the attacker's ability to predict or guess the victim's `requestID` ahead of time and win the race to submit first; the gateway does not enforce ID unpredictability or randomness on behalf of clients.
- If client `requestID` generation is sequential, timestamp-based, or otherwise guessable (a workflow/client design choice outside this handler's control), the race is trivially winnable and repeatable for each targeted ID.
- If IDs are cryptographically random/high-entropy (e.g., UUIDv4), the attack becomes infeasible in practice, so real-world likelihood is contingent on victim client-side ID generation, which this codebase does not standardize or document.

### Recommendation
Scope the in-flight-request dedup key to something that ties uniqueness to the request owner and workflow, not just the raw client-supplied string, e.g., key `h.callbacks` by a composite of `(workflowID, AuthorizedKey, requestID)` or by the already-computed `executionIDWithTriggerIndex` (which incorporates `workflowID`). This prevents a caller authorized for workflow A from ever colliding with a request against workflow B, and — if paired with binding the key’s identity into the composite — prevents same-workflow callers from squatting each other's IDs.

### Proof of Concept
Go handler-level integration test (extending `http_trigger_handler_test.go` patterns):
1. Build a `httpTriggerHandler` via `createTestTriggerHandler`, register workflow `W1` and authorize two distinct keys/JWTs (`victimKey`, `attackerKey`) for `W1` (or separately register `attacker` for an unrelated workflow `W2` to show cross-workflow squatting is also possible).
2. Attacker sends `HandleUserTriggerRequest` with `req.ID = "shared-id"` and `req.Auth` signed by `attackerKey`; mock DON `SendToNode` to hang (block) so the callback stays in `h.callbacks["shared-id"]`.
3. Victim then sends `HandleUserTriggerRequest` with the same `req.ID = "shared-id"` and `req.Auth` signed by `victimKey`.
4. Assert victim's call returns an error containing `"in-flight request ID"`, and `callback.Wait` on the victim's callback yields `requireUserErrorSent(t, r, jsonrpc.ErrConflict)`.
5. Assert no data from the attacker's request/response is present in the victim's callback payload (only the conflict error), confirming impact is confined to DoS and not data exposure.
6. Additionally repeat with attacker authorized only for a different, unrelated workflow `W2` to demonstrate the collision is not scoped to shared-workflow membership, since `h.callbacks` is keyed solely by `requestID` [3](#0-2) .

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
