### Title
Stale confirmations from removed multisig members count toward execution threshold, allowing requests to execute below the live-member confirmation threshold - (File: multisig2/src/lib.rs)

### Summary
The `MultiSigContract::confirm` function counts entries in the `confirmations` set for a request without verifying those confirming identities are still active members. `delete_member` only removes pending requests *authored* by the removed member, not confirmations that member previously cast on requests authored by others. This allows a request to reach the `num_confirmations` threshold using confirmations from accounts/keys that have since been removed from the multisig.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` decides whether to execute a request purely by count: [1](#0-0) 

`delete_member()` removes the departing member and cleans up only the requests that member itself created (`r.member == member`), plus their `num_requests_pk` entry — it does not touch `self.confirmations` entries where the removed member confirmed someone else's still-open request: [2](#0-1) 

Consequently: if member `A` confirms a request created by `B` (adding `A` to that request's `confirmations` set), and `A` is later removed from `members` via a separate `DeleteMember` request, `A`'s stale confirmation remains stored against `B`'s pending request. A subsequent live member's confirmation can push `confirmations.len() + 1 >= num_confirmations` and trigger `execute_request`, even though only one fewer *live* member actually approved it than the configured threshold requires.

### Impact Explanation
This breaks the core multisig custody guarantee that a request (e.g. `Transfer`, `AddKey`, `FunctionCall`) is only executed once `num_confirmations` *current* members have approved it. An attacker (or colluding subset of members) can arrange for a soon-to-be-removed member to pre-confirm a malicious request, then get that member removed, and complete execution with fewer live approvals than configured — e.g., transferring NEAR out of the multisig account or adding an unauthorized access key with fewer than `k` live signers. This is a "multisig request executed below threshold" condition, which the rules classify as Critical impact.

### Likelihood Explanation
Reaching this requires only actions members can already perform: creating requests, confirming them, and later removing a member via the standard `AddMember`/`DeleteMember`/`confirm` workflow — no privileged foundation access, no redeploy, and no key compromise beyond normal member operation. A malicious or compromised member (or a set of members orchestrating membership churn) can trigger it deterministically once they know a fellow member is scheduled for removal, or by timing their own pending requests around a removal they control.

### Recommendation
When removing a member in `delete_member`, iterate all pending `requests`/`confirmations` (not just those authored by the removed member) and strip the removed member's entry from every `confirmations` set; alternatively, have `confirm()` re-validate on each call that every entry in the stored `confirmations` set is still a current member (filtering stale entries) before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy multisig2 with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `B` calls `add_request` with a `Transfer` action.
3. `A` calls `confirm(request_id)` → confirmations = `{A}` (1/3).
4. `C` calls `confirm(request_id)` → confirmations = `{A, C}` (2/3, not yet executed).
5. Members separately confirm and execute a `DeleteMember { member: A }` request (allowed since `members.len()-1 = 3 >= num_confirmations = 3`); `A` is removed. Per `delete_member`, only requests created *by* `A` are purged — `B`'s transfer request and its stored confirmation set `{A, C}` are untouched.
6. `D` calls `confirm(request_id)` → `confirmations.len() as u32 + 1 = 2 + 1 = 3 >= num_confirmations (3)` → `execute_request` fires the `Transfer`, even though the request was really approved by only two still-live members (`C`, `D`) plus one confirmation from an already-removed member (`A`).
