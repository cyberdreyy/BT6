### Title
`getMultipleAccounts` fails entire batch response when any single account's data cannot be base58-encoded - (File: rpc/src/rpc.rs)

### Summary
A single oversized account in a `getMultipleAccounts` (or `getMultipleUiAccounts`) request using `base58`/`binary` encoding causes the entire multi-account query to error out, denying results for all other valid accounts in the same request.

### Finding Description
`encode_account` explicitly returns an `Err(...)` (`InvalidRequest`) when the base58/binary-encoded account data would exceed `MAX_BASE58_BYTES` (128 bytes) [1](#0-0) . `get_multiple_accounts` builds its response by iterating over every requested pubkey and calling `get_encoded_account` (which internally calls `encode_account`) inside a loop, propagating any error with `?` immediately: `self.runtime.spawn_blocking(...).await.expect("rpc: get_encoded_account panicked")?` [2](#0-1) . Because the `?` short-circuits the whole function on the first failing account, one oversized/misconfigured account among many valid ones aborts the entire batched RPC call, unlike `getAccountInfo` for a single pubkey where the same error only affects that one lookup. This mirrors the reported bug class: a single problematic member of an aggregate collection (there: a paused strategy; here: one account whose data is too large to encode) makes the entire batched operation unusable, even though the other elements are perfectly servable.

### Impact Explanation
Any unprivileged RPC client can make a single `getMultipleAccounts` request mixing normal pubkeys with any account holding more than 128 bytes of data (extremely common — most program accounts exceed 128 bytes) while requesting `base58`/`binary` encoding, and the entire response fails with an `InvalidRequest` error instead of returning data for the other pubkeys. This degrades RPC availability/usability for legitimate multi-account queries: a client cannot fetch the healthy majority of accounts if even one target account is "problematic" in this narrow sense, forcing them to fall back to per-account calls (which is exactly the workaround the underlying report highlights: excluding the "paused"/problematic member is not possible within the batched call).

### Likelihood Explanation
High likelihood of accidental triggering: a client using `getMultipleAccounts` with default/binary or base58 encoding and any real-world account (most non-trivial data accounts exceed 128 bytes) will hit this on a single call, no special conditions or multiple requests needed, and it is fully reachable by any unprivileged JSON-RPC caller.

### Recommendation
In `get_multiple_accounts`, catch the per-account encoding error and map it to `None`/an inline error entry for that specific slot in the results vector instead of propagating it with `?`, so a single unencodable account does not abort responses for the rest of the batch — consistent with how `getMultipleAccounts` already tolerates missing accounts (`None`) at `rpc/src/rpc.rs:5816-5862`.

### Proof of Concept
1. Store an account with a `data` field of, e.g., 200 bytes for pubkey `A`, and a normal small account for pubkey `B`.
2. Send `getMultipleAccounts([A, B], {"encoding": "base58"})`.
3. Observe the RPC call returns a top-level JSON-RPC error ("Encoded binary (base 58) data should be less than 128 bytes...") instead of a response array containing an error/null for `A` and the correctly-encoded data for `B`, matching the `encode_account` error path shown by the existing unit test `test_encode_account_throws_when_data_too_large_to_base58_encode` [3](#0-2)  combined with the batch loop in `get_multiple_accounts` [4](#0-3) .

    pub async fn get_multiple_accounts(
        &self,
        pubkeys: Vec<Pubkey>,
        config: Option<RpcAccountInfoConfig>,
    ) -> Result<RpcResponse<Vec<Option<UiAccount>>>> {
        let RpcAccountInfoConfig {
            encoding,
            data_slice,
            commitment,
            min_context_slot,
        } = config.unwrap_or_default();
        let bank = self.get_bank_with_config(RpcContextConfig {
            commitment,
            min_context_slot,
        })?;
        let encoding = encoding.unwrap_or(UiAccountEncoding::Base64);

        let mut accounts = Vec::with_capacity(pubkeys.len());
        for pubkey in pubkeys {
            let bank = Arc::clone(&bank);
            accounts.push(
                self.runtime
                    .spawn_blocking(move || {
                        get_encoded_account(&bank, &pubkey, encoding, data_slice, None)
                    })
                    .await
                    .expect("rpc: get_encoded_account panicked")?,
            );
        }
        Ok(new_response(&bank, accounts))
    }

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
