### Title
`dummyHandler` unconditionally overwrites `savedCallbacks[MessageId]`, allowing cross-user response hijacking on duplicate MessageId - ([File: core/services/gateway/handlers/handler.dummy.go])

### Summary
`dummyHandler.HandleLegacyUserMessage` and `HandleJSONRPCUserMessage` store each caller's `Callback` in `d.savedCallbacks[msg.Body.MessageId]` without checking for an existing entry, and `msg.Body.MessageId` is fully attacker-controlled (either taken directly from the JSON-RPC request `ID` or from the user-supplied message body). If two different users submit requests with the same `MessageId`, the second overwrites the first's callback, so the first user's DON response is silently dropped and the node's response tied to that `MessageId` is instead delivered to the second user's callback.

### Finding Description
`HandleJSONRPCUserMessage` sets `msg.Body.MessageId = jsonRequest.ID` [1](#0-0) , and `HandleLegacyUserMessage` stores the callback keyed only by this attacker-supplied ID with no existence check before overwrite: [2](#0-1) 
When `HandleNodeMessage` later receives a response with a matching `MessageId`, it looks up and deletes whichever callback is currently stored under that key and delivers the response to it: [3](#0-2) 
There is no per-user/session namespacing of `MessageId`, and the handler's own doc comment states it "forwards each request/response without doing any checks" [4](#0-3) .

This is the same overwrite pattern noted for the capabilities handler's v1 `HandleLegacyUserMessage`, which also writes `h.savedCallbacks[msg.Body.MessageId]` unconditionally [5](#0-4) , in contrast to the newer v2 `http_trigger_handler.go`, which explicitly rejects duplicate in-flight request IDs with `jsonrpc.ErrConflict` before saving a callback [6](#0-5) .

However, `dummyHandler` is registered as a selectable production handler type (`DummyHandlerType = "dummy"`) in the gateway's handler factory [7](#0-6) , so a DON operator can wire a real DON to it. But by its own explicit design/comment it performs "no checks" at all — no authentication, no signature verification gate before storing the callback, no rate limiting, no allowlist. This is a deliberately minimal/pass-through handler rather than a hardened production handler; its lack of MessageId isolation is a direct, documented consequence of its stated design intent, not an incidental oversight in an otherwise-secured path.

### Impact Explanation
If a `DummyHandlerType` DON is deployed in production, an unauthenticated caller who can predict or collide another user's `MessageId` (e.g., by submitting a request with the same ID immediately after observing/guessing it) can cause that user's DON response to be delivered to the attacker's callback instead — a cross-user response confusion (information disclosure of another user's gateway response) matching the "cross-user response confusion" impact class in the prompt's scope.

### Likelihood Explanation
Exploitability requires: (1) a DON actually configured to use `DummyHandlerType`, and (2) the attacker being able to submit a request with a `MessageId` matching another concurrent legitimate request. `dummyHandler` has no authentication or signature check on the inbound message body's `MessageId` in `HandleLegacyUserMessage`/`HandleJSONRPCUserMessage`, so any unauthenticated caller of the gateway API could submit a colliding ID. However, `dummyHandler` is explicitly a "does no checks" pass-through handler intended for testing/demo use (`sample_config.toml`, `gateway_test.go`, `handler.dummy_test.go` are the only non-factory references found), not the hardened production handler path (capabilities/vault/confidential-relay/v2 handlers). Whether any production DON is actually configured with `DummyHandlerType` could not be confirmed from the code alone; this is a configuration-dependent precondition.

### Recommendation
In `dummyHandler.HandleLegacyUserMessage`, check for an existing entry under `msg.Body.MessageId` before storing (as done in `http_trigger_handler.setupCallback`) and reject/return an error for duplicates rather than silently overwriting. If `DummyHandlerType` is intended only for testing, consider gating its selection behind a non-production build flag or explicit warning in `handler_factory.go`.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/handler.dummy_test.go`:
1. Construct a `dummyHandler` with a stub `DON`.
2. Call `HandleLegacyUserMessage(ctx, msg1WithId("dup"), cb1)`.
3. Call `HandleLegacyUserMessage(ctx, msg2WithId("dup"), cb2)` before any node response arrives.
4. Assert `len(handler.savedCallbacks) == 1` and that the stored callback is `cb2`, i.e., `cb1` was silently discarded with no error returned from either call.
5. Simulate `HandleNodeMessage` with `MessageId = "dup"` matching msg1's intended response and assert it is delivered to `cb2` (via `cb2.Wait`) instead of `cb1`, while `cb1.Wait` never resolves — demonstrating cross-user response delivery.

func (d *dummyHandler) HandleJSONRPCUserMessage(ctx context.Context, jsonRequest jsonrpc.Request[json.RawMessage], callback Callback) error {
	var msg api.Message
	if jsonRequest.Params != nil {
		if err := json.Unmarshal(*jsonRequest.Params, &msg); err != nil {

func (d *dummyHandler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	var msg api.Message
	err := json.Unmarshal(*resp.Result, &msg)
	if err != nil {
		return err
	}
	msg.Body.MessageId = resp.ID
	err = msg.Validate()
	if err != nil {
		return err
	}
	if nodeAddr != msg.Body.Sender {
		return fmt.Errorf("node address %s does not match message sender %s", nodeAddr, msg.Body.Sender)
	}
	d.mu.Lock()
	savedCb, found := d.savedCallbacks[msg.Body.MessageId]
	delete(d.savedCallbacks, msg.Body.MessageId)
	d.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(&msg), ErrorCode: api.NoError})
	}
	return nil
