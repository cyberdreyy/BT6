### Title
Front-runnable lockup address squatting via unrestricted `owner_account_id` in `create` - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` is a public, unrestricted `#[payable]` method that anyone can call with an arbitrary `owner_account_id`, `whitelist_account_id`, `vesting_schedule`, and other terms. Because the lockup contract's account ID is fully deterministic — `hex::encode(&env::sha256(owner_account_id.as_bytes())[..20])` concatenated with the factory account — an attacker can pre-create the lockup for any victim owner before the legitimate grantor does, permanently squatting that address with attacker-chosen terms, including a hostile `staking_pool_whitelist_account_id`.

### Finding Description
The invariant the codebase depends on is: `lockup_account(owner_account_id) terms == terms chosen by owner_account_id's rightful grantor`. This binding is broken because `create` derives the lockup account address solely from `owner_account_id` [1](#0-0) , and nothing in `create` restricts the caller (predecessor) or validates that the caller is authorized to create a lockup for that `owner_account_id`. The only guard is a minimum attached deposit check [2](#0-1) ; there is no `assert_called_by_foundation` or any predecessor/owner relationship check anywhere in `create` or `on_lockup_create` [3](#0-2) .

`whitelist_account_id` is also fully attacker-controlled and, if provided, is used directly as `staking_pool_whitelist_account_id` passed to the newly deployed lockup contract [4](#0-3) . The `on_lockup_create` callback only checks promise success/failure and refunds on failure; it performs no authorization check either [5](#0-4) .

Exploit flow:
1. Attacker deploys/controls a "whitelist" contract that will approve any staking pool the attacker later wants funds routed to (or is otherwise malicious).
2. Attacker observes (or predicts) that account `owner_account_id` is a future lockup grant recipient (e.g., an employee, investor, or foundation grantee) whose real lockup has not yet been created.
3. Attacker calls `create(owner_account_id, lockup_duration, lockup_timestamp, vesting_schedule, release_duration, Some(attacker_whitelist))` with `MIN_ATTACHED_BALANCE` attached NEAR (3.5 NEAR).
4. NEAR's `create_account` for `hex(sha256(owner)[..20]).factory` succeeds because the account does not yet exist; the lockup contract is deployed there with the attacker's chosen `staking_pool_whitelist_account_id`, `vesting_schedule`/hash, and durations.
5. When the legitimate grantor (foundation or lockup admin) later attempts to call `create` for the same `owner_account_id` with the correct terms, `create_account()` in the Promise fails since the account already exists, `is_promise_success()` in `on_lockup_create` returns false, and the deposit is refunded to the legitimate caller — the real grant can never be deployed at that address. Because the derived address is purely a function of `owner_account_id`, the attacker's contract permanently occupies the slot the protocol and any off-chain tooling treat as "the" lockup for that owner.
6. Once the owner is later granted access (e.g., full access key or being told this is their lockup) and deposits/receives funds, or once transfers are enabled, the owner's stake/withdraw actions on the lockup are routed through the whitelist the attacker chose (any staking pool the attacker whitelisted is considered "trusted" by that lockup instance), and vesting/termination behavior is whatever the attacker configured.

None of the existing guards prevent this: `assert_self` only gates the internal callback to the factory itself [6](#0-5) , and there is no owner-signature or foundation-only check on `create`.

### Impact Explanation
This matches the Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." Funds intended for the victim owner (vesting schedule, staking whitelist, release schedule) end up permanently locked in a contract instance parameterized entirely by the attacker, including which staking pools are considered whitelisted/trusted by that lockup. This blocks the legitimate grant from ever being deployed at the canonical address and can route the owner's future staking/withdrawal operations through an attacker-controlled "trusted" pool. The attack is repeatable against every not-yet-created owner account and costs only `MIN_ATTACHED_BALANCE` (3.5 NEAR) per squatted address.

### Likelihood Explanation
The attacker needs no privileges beyond a funded NEAR account and knowledge (or prediction) of an `owner_account_id` that will eventually receive a lockup grant — this is often public knowledge (e.g., known team/investor account names). The cost is fixed and small (3.5 NEAR, refundable if the attacker instead lets legitimate creation happen — but the attack itself is to front-run, so the attacker pays this once per victim address and it is not refunded to them since their creation succeeds). This is fully feasible on-chain with the exact call signature shown, requiring no timing precision beyond "before the real grantor calls `create`."

### Recommendation
Restrict `create` to be callable only by `self.foundation_account_id` (or another explicitly authorized admin set at `new`), analogous to `assert_called_by_foundation` patterns used elsewhere in this codebase, so an unprivileged account cannot pre-create a lockup for an arbitrary `owner_account_id`. Alternatively/additionally, incorporate a value only the legitimate grantor knows (e.g., a per-owner authorization token or salt agreed out of band) into the derived account ID, or require a signed pre-registration step so the deterministic address cannot be squatted by an outsider.

```rust
// lockup-factory/src/lib.rs tests module (near-sdk testing_env!)
#[test]
fn test_attacker_can_squat_victim_lockup_address() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker (not the foundation, not the owner) calls create() naming the victim owner
    // and their own hostile whitelist contract.
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(),      // victim owner_account_id, real grant not yet created
        lockup_duration,
        None,
        None,
        None,
        Some(custom_whitelist_account_id()), // attacker-controlled whitelist
    );

    // Simulate successful account creation at the deterministic address.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    assert!(contract.on_lockup_create(
        lockup_account(),
        ntoy(30).into(),
        String::from("attacker.near"),
    ));

    // The legitimate grantor (foundation) now attempts to create the real lockup
    // for the same owner_account_id -- create_account fails because the account
    // already exists at that deterministic address.
    context.predecessor_account_id = foundation_account_id().to_string();
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, None, None, None);

    // Simulate the promise failing because create_account() on an existing account fails.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let res = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        foundation_account_id().to_string(),
    );

    // Assert the equality is broken: the address for account_tokens_owner() now
    // permanently carries the attacker's whitelist, not the foundation's intended terms,
    // and the legitimate creation attempt fails/refunds.
    assert_eq!(res, false, "Legitimate creation must fail: address already squatted by attacker");
}
```
This demonstrates the broken binding `lockup_account(owner) terms == grantor-chosen terms`: the attacker's call succeeds and permanently occupies the address with `custom_whitelist_account_id()` as the trusted whitelist, while the legitimate foundation creation for the same owner fails.

```rust
    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )
            .then(ext_self::on_lockup_create(
                lockup_account_id,
                env::attached_deposit().into(),
                env::predecessor_account_id(),
                &env::current_account_id(),
                NO_DEPOSIT,
                gas::CALLBACK,
            ))
    }

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
}
```
