### Title
Stale confirmations from a deleted member remain counted toward `num_confirmations`, allowing a request to execute below the live-member confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` (multisig2/src/lib.rs:356-379) only purges requests whose *requester* field (`r.member`) equals the member being removed; it never scans the `confirmations` map to strip the removed member's entries from requests they merely *confirmed*. Because `confirm` (multisig2/src/lib.rs:294-315) counts raw `confirmations.len()` without checking that each confirming key/account is still in `self.members`, a request can be executed with confirmations from fewer currently-live members than `num_confirmations`.

### Finding Description
The binding that must hold is: `distinct current members in self.members who confirmed request R == num_confirmations` at the moment `confirm` schedules execution.

Trace:
1. Member `A` creates `R1 = Transfer{amount}` via `add_request` (multisig2/src/lib.rs:170-200); `request_with_signer.member = A` (the requester field used later for cleanup and `num_requests_pk` bookkeeping).
2. Member `B` (`other_member`), who did *not* create R1, calls `confirm(R1)` (multisig2/src/lib.rs:294-315). Since `confirmations.len()+1 < num_confirmations`, `B`'s key is inserted into `confirmations[R1] = {B}` and R1 stays pending.
3. Separately, another request `R2 = DeleteMember{B}` is created and confirmed to threshold, invoking `delete_member(promise, B)` (multisig2/src/lib.rs:356-379). This function:
   - Filters `self.requests` for `r.member == B` (line 365) — matches only requests *B originated*, not requests `B` confirmed. R1 was originated by `A`, so it is skipped entirely.
   - Removes `B` from `self.members` (line 374) and deletes `B`'s access key if applicable.
   - Never touches `self.confirmations[R1]`, which still contains `B`'s string key.
4. Remaining live members keep confirming R1. `confirm`'s threshold check (`confirmations.len() as u32 + 1 >= self.num_confirmations`, line 304) counts the stale `B` entry as if it were a live confirmation. Once the raw set size reaches `num_confirmations`, `remove_request`/`execute_request` runs the `Transfer`, even though the number of *currently live* members who actually confirmed is `num_confirmations - 1` (or fewer if multiple members were deleted this way).

Root cause: confirmation cleanup in `delete_member` is scoped only to the requester field, not to the `confirmations: LookupMap<RequestId, HashSet<String>>` entries recording who *confirmed* each pending request. No existing guard (`assert_valid_request`, `assert_self_request`, `current_member()`) re-validates historical confirmers against `self.members` at confirm-time or at deletion-time.

### Impact Explanation
A `Transfer`, `AddKey`, `FunctionCall`, or any other multi-sig action can be pushed through and executed by a coalition of fewer live members than `num_confirmations` mandates, because a removed member's stale confirmation silently persists and counts toward the threshold. This directly moves NEAR (or triggers arbitrary contract calls/key additions) out of the multisig account with fewer authorizing live signers than the contract's own security policy requires — matching the Critical category "a multisig request executed below `num_confirmations` live members." It is repeatable any time a confirming (non-requesting) member is later removed while they have outstanding confirmations on other pending requests.

### Likelihood Explanation
Preconditions are simple and require no special privilege beyond being an existing multisig member (in-scope actor set includes members who can legitimately confirm/create requests): a request must be confirmed by a member other than its creator, and that confirming member must subsequently be removed via `DeleteMember` before the original request reaches its confirmation threshold. This is a normal, non-adversarial-looking sequence of multisig operations (member turnover is a realistic operational event), making it highly feasible and reproducible across accounts/epochs.

### Recommendation
When executing `DeleteMember`, iterate over `self.confirmations` for all pending request IDs and remove the deleted member's key from each `HashSet<String>` (not just requests they authored), or alternatively re-validate at confirm-time that every string in `confirmations.get(&request_id)` still corresponds to a member in `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
```rust
// cargo test in multisig2/src/lib.rs tests module
#[test]
fn test_stale_confirmation_after_member_deletion() {
    // members: A, B, C, D ; num_confirmations = 3
    // (use existing test helpers: context_with_account/context_with_key as appropriate)
    let mut c = MultiSigContract::new(members_4(), 3);

    // Step 1: A creates R1 = Transfer(amount) — requester field = A
    testing_env!(context_with_account(a(), amount));
    let r1 = c.add_request(transfer_request(bob_receiver(), amount));

    // Step 2: B confirms R1 (B did not create it)
    testing_env!(context_with_account(b(), amount));
    c.confirm(r1);
    assert_eq!(c.confirmations.get(&r1).unwrap().len(), 1); // {B}

    // Step 3: C creates+self-confirms R2 = DeleteMember{B}; A and D confirm to reach threshold 3
    testing_env!(context_with_account(c_member(), amount));
    let r2 = c.add_request_and_confirm(delete_member_request(member_b()));
    testing_env!(context_with_account(a(), amount));
    c.confirm(r2);
    testing_env!(context_with_account(d(), amount));
    c.confirm(r2); // executes DeleteMember{B}

    // Assert B removed from members but R1's confirmations still contain B's stale entry
    assert!(!c.get_members().contains(&member_b()));
    assert!(c.confirmations.get(&r1).unwrap().contains(&member_b().to_string()));

    // Step 4: remaining live members C and A confirm R1
    testing_env!(context_with_account(c_member(), amount));
    c.confirm(r1); // confirmations={B,C}, len 2 < 3, not yet executed
    testing_env!(context_with_account(a(), amount));
    let result = c.confirm(r1); // len 2+1=3 >= 3 -> executes Transfer

    // Binding check: live confirmers who actually confirmed R1 = {A, C} = 2
    // but num_confirmations = 3, and R1 executed anyway because B's stale
    // confirmation was counted.
    assert_eq!(c.get_members().len(), 3); // A, C, D remain
    assert!(c.requests.get(&r1).is_none()); // R1 executed/removed
    // live_confirmers (2) != num_confirmations (3) -> binding broken, Transfer executed early
}
```
