## Finding

### Title
Missing beneficiary-receivability check in `staking_contract::set_beneficiary_for_operator` permanently blocks stake/commission distribution and operator switching - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
The external report's root cause is a missing "can the recipient actually receive/hold this asset" check before an unprivileged-triggerable state change permanently traps value belonging to other parties. The Aptos framework contains a self-documented instance of exactly this defect: `vesting.move::set_beneficiary` explicitly validates the new beneficiary is registered to receive APT — specifically to prevent `distribute()` from reverting and blocking all other shareholders — but the equivalent `staking_contract.move::set_beneficiary_for_operator` has no such guard.

### Finding Description
`vesting::set_beneficiary` contains this guard and comment: [1](#0-0) 

```
public entry fun set_beneficiary(...) {
    // Verify that the beneficiary account is set up to receive APT. This is a requirement so distribute() wouldn't
    // fail and block all other accounts from receiving APT if one beneficiary is not registered.
    assert_account_is_registered_for_apt(new_beneficiary);
    ...
```

This is the framework's own acknowledgment of the bug class described in the report (an unsafe recipient can brick a shared distribution flow). However, the sibling function that lets an **operator** (not the staker, i.e. an unprivileged party relative to the staker's funds) redirect their commission payouts has no such check: [2](#0-1) 

`set_beneficiary_for_operator` simply writes `new_beneficiary` into `BeneficiaryForOperator` with no call to `assert_account_is_registered_for_apt` or any receivability check.

The payout path this feeds into, `distribute`/`distribute_internal`, deposits funds to each shareholder (including the operator's beneficiary) using `aptos_account::deposit_coins`, which **aborts** if the recipient is neither registered for the coin nor has opted into direct coin transfers: [3](#0-2) 

Because `distribute_internal` iterates over *all* shareholders of the shared `distribution_pool` in a single transaction, a single unpayable beneficiary aborts the entire transaction, blocking payout to everyone else sharing that pool (the staker's principal withdrawal included). `distribute` is explicitly permissionless ("Allow anyone to distribute already unlocked funds"): [4](#0-3) 

Worse, `switch_operator` — the staker's own escape hatch for removing a misbehaving operator — calls `distribute_internal` first, before doing anything else: [5](#0-4) 

If that forced distribution aborts because the operator's beneficiary can't receive coins, `switch_operator` itself cannot complete, so the staker cannot even escape by replacing the operator.

### Impact Explanation
Once an operator calls `set_beneficiary_for_operator` with an address that (a) does not exist, (b) is not registered for `AptosCoin`, and (c) has not called `set_allow_direct_coin_transfers(true)`, every subsequent call to `distribute()` for that staking contract's pool reverts. Since `switch_operator` also invokes `distribute_internal` before it can proceed, the staker cannot unlock/withdraw their own stake nor switch away from the operator through the normal path. This traps the staker's principal and any accrued rewards/commission inside the staking contract — a permanent, non-recoverable loss of claim/withdrawal rights, and it credits/traps value tied to the wrong (unpayable) beneficiary account, matching the "share-accounting corruption... traps value" and "permanent lock of claim rights in stake... commission... flows" impact categories.

### Likelihood Explanation
This requires no privileged access beyond being the operator of an existing staking contract — a role obtainable simply by being chosen as operator by any staker, or by griefing one's own contract. Setting a beneficiary to a not-yet-initialized/unregistered address is a single permissionless entry-function call (`set_beneficiary_for_operator`), gated only by the `operator_beneficiary_change_enabled` feature flag. No coordination with the staker or any elevated privilege is needed to trigger the freeze.

### Recommendation
Add the same guard used in `vesting::set_beneficiary` to `staking_contract::set_beneficiary_for_operator`:
```move
assert_account_is_registered_for_apt(new_beneficiary);
```
before writing the new beneficiary into `BeneficiaryForOperator`. Additionally, harden `distribute_internal` so that a single shareholder's failed deposit does not abort payouts to all other shareholders (e.g., skip/queue a failed deposit rather than reverting the whole loop), removing the shared-fate blast radius entirely.

### Proof of Concept
1. Staker creates a staking contract with `operator` via `staking_contract::create_staking_contract`, and the pool accrues rewards.
2. `operator` calls `staking_contract::set_beneficiary_for_operator(operator, addr_X)`, where `addr_X` has never been created on-chain (or exists but never registered for `AptosCoin` and never called `aptos_account::set_allow_direct_coin_transfers(true)`).
3. Time passes; stake becomes unlockable. Anyone calls `staking_contract::distribute(staker_address, operator_address)`.
4. `distribute_internal` reaches the loop entry that deposits the operator's commission share to `addr_X` via `aptos_account::deposit_coins`; because `addr_X` is unregistered/non-accepting, this call aborts per `aptos_account.move` (line 121-130 logic), reverting the entire `distribute` transaction.
5. The staker attempts `staking_contract::switch_operator` to escape; it also calls `distribute_internal` first (staking_contract.move lines 781-789) and aborts identically.
6. All future `distribute`/`switch_operator`/`unlock_stake`-driven distributions for this staker/operator pair permanently fail, freezing both the staker's principal and the operator's own commission in the pool.

            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;

            move_to(
                operator,

            );
        };

            SetBeneficiaryForOperator {
                operator: operator_addr,
