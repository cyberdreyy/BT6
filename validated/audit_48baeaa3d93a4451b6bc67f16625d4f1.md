### Title
Funded instant-withdraw receipt is upgraded into a claim over all (including unfunded) instant requests — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The copyparty bug is a scope-confusion flaw: a credential valid for one file (filekey) can be reinterpreted as a credential for the whole directory (dirkey). The analog in `IdleCreditVault` is the instant-withdraw claim path: `claimInstantWithdrawRequest` treats one funded receipt as authorization to pay out the *entire* aggregated `instantWithdrawsRequests[_user]` balance — including later requests whose underlyings were never collected from the borrower — because funding status is tracked only globally (`pendingInstantWithdraws` / `allowInstantWithdraw`), never per receipt.

### Finding Description
`requestInstantWithdraw` mints receipt strategy tokens 1:1 and adds `_amount` to both `instantWithdrawsRequests[_user]` and the global `pendingInstantWithdraws` counter [1](#0-0) . Funding is only delivered via `collectInstantWithdrawFunds`, which the CDO calls at `startEpoch` (capped by available underlying) or in `getInstantWithdrawFunds` after the deadline [2](#0-1) [3](#0-2) .

The claim path pays `instantWithdrawsRequests[_user]` in full and only burns that same amount of receipt tokens — there is no check that the specific amount being claimed was actually funded [4](#0-3) . The gate is solely the CDO's global `allowInstantWithdraw` flag [5](#0-4) , and `_transferFundedClaim` only protects the post-default `defaultRecoveryReserve`, not other users' funded receipts [6](#0-5) .

Attack (running-epoch phase, standard non-programmable mode):

1. Epoch N starts with pending instant requests smaller than idle liquidity, so `startEpoch` collects them and sets `allowInstantWithdraw = true`; surplus is sent to the borrower [7](#0-6) .
2. While the epoch is still running and the flag remains set, the attacker (a KYC'd tranche holder) calls `requestWithdraw`, which routes into `requestInstantWithdraw`, minting them a receipt and increasing `instantWithdrawsRequests[attacker]` and `pendingInstantWithdraws` — but no underlying is pulled from the borrower, because `collectInstantWithdrawFunds` only runs at `startEpoch`/`getInstantWithdrawFunds` [1](#0-0) .
3. The attacker calls `claimInstantWithdrawRequest`. Because `allowInstantWithdraw` is already true and the claim pays the aggregate ledger entry at par, the strategy transfers underlying for an unfunded receipt [5](#0-4) .

The underlying paid out comes from the strategy's balance, which holds funds earmarked for other users' funded instant receipts and normal-withdraw funding collected via `collectWithdrawFunds` [8](#0-7) .

### Impact Explanation
Direct theft: the attacker converts tranche tokens into an unfunded receipt and immediately redeems it for underlying that belongs to other claimants. Loss is bounded by the strategy's held underlying (funded instant + funded normal withdrawals), and each stolen unit leaves an honest user's `claimWithdrawRequest`/`claimInstantWithdrawRequest` underfunded — i.e., theft plus freezing of remaining claims.

### Likelihood Explanation
Requires an epoch running with `allowInstantWithdraw == true` and strategy-held underlying — a routine state. The attacker only needs to hold tranche tokens (KYC'd lender) and make one `requestWithdraw` + one `claimInstantWithdrawRequest`. Uncertainty: I could not fully confirm whether `requestWithdraw` during a running epoch always routes to the instant path; if new instant requests are gated to the buffer phase, the same confusion still applies when `getInstantWithdrawFunds` partially fails silently or when `claimInstantWithdrawRequest` is reached after a defaulted epoch where `allowInstantWithdraw` was left true (the funded/instant boundary in `_claimDefaultedInstantWithdrawRequest` only fires once `defaultInstantWithdrawsFinalized` is set) [9](#0-8) .

### Recommendation
Track funded vs. unfunded instant receipts per user/epoch (the `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` ledgers already exist) and in `claimInstantWithdrawRequest` pay only the funded portion, or gate the claim on `pendingInstantWithdraws == 0` / per-claim funding checks rather than the global `allowInstantWithdraw` flag.

### Proof of Concept
Foundry fork PoC sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// setup: deposits AA/BB, startEpoch(0), stopEpoch(0)
// user requests instant withdraw in buffer
uint256 r1 = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));
// startEpoch(1): pendingInstant <= idle underlying -> allowInstantWithdraw = true,
// surplus sent to borrower
_startEpochAndCheckPrices(1);
// attacker creates a NEW instant request while epoch running and flag still true
uint256 r2 = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));
// pendingInstantWithdraws now > 0, no collectInstantWithdrawFunds happened
assertGt(strategy.pendingInstantWithdraws(), 0);
// claim pays r1 + r2 from strategy balance, stealing funds reserved for
// other users' funded receipts
cdoEpoch.claimInstantWithdrawRequest();
assertEq(underlying gained, r1 + r2); // r2 was never funded
```

  function collectWithdrawFunds(uint256 _amount) external {

      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();

      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);

  function getInstantWithdrawFunds() external {
    _checkOnlyOwnerOrManager();
    // Check that programmable mode is disabled, the epoch is running and the deadline passed.
    _checkNotAllowed(isProgrammableBorrower || !isEpochRunning || block.timestamp < instantWithdrawDeadline);
