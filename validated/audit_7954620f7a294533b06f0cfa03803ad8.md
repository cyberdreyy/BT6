### Title
Unprivileged ERC4626 vault user can permanently block `stopEpoch` by draining vault liquidity, freezing all lender withdraws - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower.onStopEpoch` performs an external `vault.withdraw` inside the `stopEpoch` transaction and reverts with `StopEpochVaultLiquidityUnavailable` whenever that withdrawal fails, even though the vault shares still economically cover the shortfall. Any unprivileged user of the configured ERC4626 vault (e.g. a borrower on a Morpho/Aave-style vault) can pull all underlying liquidity out of the vault, making every `stopEpoch` call revert indefinitely. The epoch can never stop, `epochAccountingActive` stays true, and all pending withdraw requests and new deposits' funds are frozen. This mirrors the external bug class (a lock/resource acquired inside a transaction causing global exhaustion/deadlock): the stop path unconditionally contends on the vault's shared liquidity "lock" inside the same atomic flow that guards epoch settlement.

### Finding Description
In `onStopEpoch`, when the required amount exceeds on-hand balance, the contract checks `shortfall > _currentVaultAssets()` and only then attempts `vault.withdraw(shortfall, ...)` inside a `try/catch` that reverts on failure [1](#0-0) . The coverage check uses `convertToAssets` (share valuation), not the vault's actual `asset().balanceOf(vault)` liquidity. For lending-market-backed ERC4626 vaults, these diverge: shares can be fully "worth" the shortfall while redeemable liquidity is zero because all underlying is lent out. In that state `vault.withdraw` reverts, the catch block reverts, and the whole `stopEpoch` reverts.

There is no fallback: the hook has no asynchronous/queued path and no partial success, so the revert propagates and `IdleCDOEpochVariant.stopEpoch` can never complete. The same illiquidity defeats the privileged escape hatch `emergencyExitVault`, which calls `vault.redeem` and would revert identically [2](#0-1) . `onDefault` deliberately avoids `convertToAssets` exactly because vault views can fail under stress [3](#0-2) , but the normal stop path has no equivalent protection against vault *liquidity* (not valuation) failure.

Attack sequence (running epoch, programmable mode):
1. Attacker, an unprivileged user of the ERC4626 vault, borrows/withdraws essentially all vault liquidity (or holds a pre-existing borrow).
2. Manager calls `stopEpoch` (or it is triggered on schedule). `onStopEpoch` computes `shortfall <= _currentVaultAssets()` (shares are worth enough), calls `vault.withdraw`, which reverts on insufficient cash → `StopEpochVaultLiquidityUnavailable` → `stopEpoch` reverts.
3. Every retry reverts as long as the attacker keeps liquidity drained. The attacker can renew/extend the lending-market borrow indefinitely; the honest borrower's repayment also cannot land because `_repay` only helps once `stopEpoch` succeeds, and `epochPendingWithdraws` reservation means repaid funds get redeposited into the illiquid vault anyway [4](#0-3) .

Broken invariant: epoch state machine liveness — `stopEpoch` must be able to transition the pool to `stopped` regardless of third-party vault liquidity conditions. All `withdrawsRequestsByEpoch` payouts for the epoch and all tranche funds remain locked.

### Impact Explanation
Temporary freezing of all pool funds: every lender's principal and yield in the epoch stays locked while the vault is illiquid, with the duration controlled by the attacker (as long as they service their vault-side borrow). The honest roles cannot unfreeze it: `emergencyExitVault` hits the same liquidity wall, `setVault` is blocked while shares are held and accounting may be active [5](#0-4) , and `rescueTokens` can only sweep on-hand underlying, not vault shares. Loss magnitude is the full epoch TVL for the freeze duration; for lenders this is a real denial of access to funds that would otherwise be payable at `stopEpoch`.

### Likelihood Explanation
Requires the configured vault to be a lending-market-style ERC4626 where liquidity can be fully utilized — a standard deployment choice for a yield sleeve — and an attacker willing to hold a large borrow position, paying borrow interest as the only cost. No privileged role, no malicious vault, and no oracle manipulation is needed; vault liquidity exhaustion is an explicitly in-scope surface. The revert-vs-`return true` branch boundary (`shortfall > _currentVaultAssets()`) makes the freeze trigger exactly when the position is solvent on paper.

### Recommendation
Decouple epoch stopping from vault liquidity, analogous to avoiding a lock inside the transaction:
- On `vault.withdraw` failure inside `onStopEpoch`, return `true` and proceed with settlement using on-hand funds, recording the uncalled shortfall so `IdleCDO`'s `transferFrom` shortfall flows into the existing default/loss path rather than reverting; or
- Catch the withdrawal failure and continue without reverting, leaving shares to be unwound later via `emergencyExitVault`/`settleBorrowerInterest`; or
- Gate on actual vault liquidity (`vault.maxWithdraw(address(this))` / `asset().balanceOf(vault)`) instead of `convertToAssets`, so a solvent-but-illiquid position takes the non-reverting path.

### Proof of Concept
I was unable to run further tool iterations to pull the exact `stopEpoch` call site in `IdleCDOEpochVariant.sol`, so the PoC below is sketched against `ProgrammableBorrower` semantics; the Foundry fork harness should instantiate the real deployment.

```solidity
// test/foundry/StopEpochVaultLiquidityFreeze.t.sol
// Fork setup: real IdleCDOEpochVariant + ProgrammableBorrower + Morpho-style ERC4626 vault.
function test_stopEpochFrozenByVaultIlliquidity() public {
    // 1. Lenders deposit, startEpoch runs; PB deposits idle funds into vault.
    // 2. Attacker (vault user) borrows ~all underlying from the vault market.
    vm.prank(attacker);
    market.borrow(vaultAssets - dust);  // liquidity -> ~0, shares still priced fully

    // 3. Honest manager tries to stop the epoch.
    vm.prank(manager);
    vm.expectRevert();  // wraps StopEpochVaultLiquidityUnavailable
    cdo.stopEpochWithDuration(duration, 0);

    // 4. Repeating reverts while attacker holds the borrow.
    vm.warp(block.timestamp + 30 days);
    vm.prank(manager);
    vm.expectRevert();
    cdo.stopEpochWithDuration(duration, 0);

    // 5. Privileged escape also fails: redeem hits the same liquidity wall.
    vm.prank(manager);
    vm.expectRevert();
    pb.emergencyExitVault(0);

    // 6. Withdraw requests for the epoch remain unclaimable => funds frozen.
    assertEq(pb.epochAccountingActive(), true);
}
```
