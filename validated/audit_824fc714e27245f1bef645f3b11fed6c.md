### Title
V1 signer's `validate_tenure_change_payload` duplicate-block guard checks only globally-accepted blocks, missing locally-accepted prior blocks in the same tenure - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` in the v1 chainstate module guards against signing a second tenure-change (tenure-start) block for a tenure the signer has already signed a block in, but it only queries `get_last_globally_accepted_block` [1](#0-0)  instead of `get_last_signed_block`, which the v2 implementation deliberately uses to also cover locally-accepted blocks [2](#0-1) . This lets a v1-configured signer sign a second, competing tenure-start block for a tenure where it has only locally accepted (but not yet globally accepted) a prior block.

### Finding Description
The intended equality is: "at most one tenure-change block accepted per tenure" should mean "the signer already holds any signed block (local or global) in that tenure," as v2's comment states explicitly: *"Only blocks we have signed (locally or globally accepted) count here: a block we have merely pre-committed to carries no signature from us..."* [3](#0-2) .

The v1 implementation breaks this equality by calling `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` [4](#0-3)  rather than `get_last_signed_block`. If the signer has locally accepted (signed) a first tenure-change block B1 for tenure T but B1 has not yet reached global (threshold) acceptance, `get_last_globally_accepted_block(T)` returns `None`, and the `if let Some(...)` duplicate check at line 510 never fires, so `Ok(())` is returned [5](#0-4) .

Exploit flow: an attacker who wins a single miner slot for sortition/tenure T can craft two different tenure-change ("BlockFound") block proposals B1 and B2 for the same tenure T and gossip them in sequence to a v1-configured signer (i.e., one running signer protocol version below `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`, selecting `SortitionStateVersion::V1` per `SortitionStateVersion::from_protocol_version` [6](#0-5) ). The signer processes B1 through `check_proposal` → `validate_tenure_change_payload`, no prior block exists, so it locally accepts/signs B1 (state becomes LocallyAccepted, not yet GloballyAccepted). The attacker then proposes B2 for the same tenure T. Because `get_last_globally_accepted_block(T)` still returns `None` (B1 is only locally accepted), the duplicate-block guard is bypassed and B2 also passes `validate_tenure_change_payload`, allowing the signer to sign a second, conflicting tenure-start block for the same tenure.

None of the other checks in `check_proposal`/`validate_tenure_change_payload` catch this: `check_tenure_change_confirms_parent` and `check_parent_tenure_choice` evaluate the *parent* tenure's blocks, not duplicate blocks within the *current* tenure T being proposed [7](#0-6) . The only guard specific to "have I already signed a block in this same tenure" is the one at line 505, and it uses the wrong (globally-accepted-only) predicate in v1.

### Impact Explanation
This breaks chain safety (uniqueness/canonicity): a v1-configured signer can end up applying its one signature to two different, conflicting tenure-start blocks for the same tenure. If enough signers are similarly running the legacy v1 protocol version (a plausible fleet configuration during/after a protocol upgrade rollout, not a privileged condition), this can contribute signatures toward two competing blocks at the same tenure/height, which is exactly the "signer signing a conflicting block" Critical impact category. It is repeatable per tenure that a v1 signer has only locally, not globally, accepted a block in.

### Likelihood Explanation
Preconditions: the signer must be running protocol version `< GLOBAL_SIGNER_STATE_ACTIVATION_VERSION` (v1 chainstate path) [6](#0-5) , and the attacker's own tenure-start block must reach only local (not yet global) acceptance before the attacker gossips a second competing tenure-change proposal for the same tenure. This requires only a single miner slot (to be the proposer for the sortition) and the ability to gossip two distinct block proposals — well within the stated unprivileged attacker capability (one signer's weight, no auth_token, no majority). It is fully attacker-controlled and repeatable across tenures where the attacker wins the miner slot and the network hasn't yet reached global acceptance of the first proposal (a normal, not artificially delayed, condition given consensus latency).

### Recommendation
Change `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, matching the v2 semantics, so that any locally- or globally-accepted prior block in the same tenure triggers `RejectReason::DuplicateBlockFound`.

### Proof of Concept
In `stacks-signer/src/chainstate/tests/v1.rs`, add a test that:
1. Builds a `SignerDb` and inserts a `BlockInfo` for tenure `T` with `state = BlockState::LocallyAccepted` (signed_self set, signed_group/global acceptance unset) — i.e., not marked globally accepted.
2. Constructs a second `NakamotoBlock` `B2` with a `TenureChangePayload` for the same tenure `T` (same `consensus_hash`), with a valid parent-tenure match and passing `check_tenure_change_confirms_parent`/`check_parent_tenure_choice`.
3. Calls `SortitionsView::validate_tenure_change_payload` (v1) on `B2` and asserts it returns `Ok(())` — demonstrating the guard is bypassed.
4. As a comparison, run the equivalent v2 `GlobalStateView::validate_tenure_change_payload` with the same locally-accepted `BlockInfo` present and assert it returns `Err(RejectReason::DuplicateBlockFound)`, proving the v1/v2 divergence and that v2's `get_last_signed_block` correctly catches what v1's `get_last_globally_accepted_block` misses.
