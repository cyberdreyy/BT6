### Title
Funded instant-withdraw receipts are never cleared from `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, enabling a double payout from the default-recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Linux bug is a missing `of_node_put()` — an acquired reference whose count is never decremented, leaking the resource. The direct analog in `IdleCreditVault` is the funded instant-withdraw claim path: `requestInstantWithdraw` increments three counters (`instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]`, plus `pendingInstantWithdraws`), but `claimInstantWithdrawRequest` decrements only the aggregate `instantWithdrawsRequests[_user]` and leaves both per-epoch counters populated forever. If the borrower defaults while that epoch is still `defaultRecoveryEpoch`, the stale per-epoch basis is paid out a second time from `defaultRecoveryReserve`.

### Finding Description
`requestInstantWithdraw` records the receipt per epoch:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:366-374
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

The funded claim path clears only the aggregate:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:387-392
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

There is no `instantWithdrawsRequestsByEpoch[_user][currentEpoch] = 0` and no `instantWithdrawClaimsByEpoch[currentEpoch] -= amount`. Compare with `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which *does* clear both — confirming these fields are meant to track outstanding (not yet paid) basis.

Two downstream consumers then over-count:

1. `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis, and `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstantWithdraws` as "already held" reserve. Already-claimed basis inflates both, so `recoveryPrice` is computed against claims that were already paid at par, while the corresponding tokens already left the contract. The reserve is under-collateralized relative to `defaultRecoveryPrice` — honest recovery claimants are diluted and the last claimers are underpaid (insolvency in the recovery waterfall).

2. `_claimDefaultedInstantWithdrawRequest(_user)` pays `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch] * defaultRecoveryPrice`. Because `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` (line 693) and `epochNumber` only increments on a successful `stopEpoch`/`deposit`, a user whose instant request was funded and claimed during the defaulting epoch still has a nonzero per-epoch entry and receives a second payout from `defaultRecoveryReserve`.

### Impact Explanation
Direct theft of the default-recovery reserve: an attacker (any unprivileged user making an instant-withdraw request) is paid at par via `claimInstantWithdrawRequest` and then paid again at `defaultRecoveryPrice` via the defaulted-claim path in the same call sequence. Each duplicated basis unit both pays the attacker twice and shrinks the share available to all other defaulted-epoch receipt holders and active tranche holders, since `recoveryPrice` was inflated by counting claimed basis as prefunded reserve. Loss is bounded by the attacker's instant-withdraw amount (up to `pendingInstantWithdraws`-funded size), i.e. up to the full prefunded instant bucket.

### Likelihood Explanation
Requires: (a) instant withdrawals enabled, (b) the attacker requests an instant withdraw in epoch E and it is funded via `collectInstantWithdrawFunds`, (c) the borrower defaults such that `finalizeDefaultRecovery` runs while `epochNumber == E` and `pendingInstantWithdraws != 0` (i.e., some instant receipts remain unfunded — the exact scenario `defaultInstantWithdrawsFinalized` was built for). All attacker steps are unprivileged user calls; default/finalization are executed by honest privileged roles, consistent with the threat model. No existing guard stops it: `requestWithdraw`'s post-default checks gate *new* requests, not claims, and `_onlyIdleCDO`/`_checkNotAllowed` paths never validate per-epoch instant entries on the funded-claim path.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch accounting alongside the aggregate:

```solidity
uint256 reqEpoch = lastInstantEpochOrTrackedEpoch; // e.g., iterate or store request epoch
instantWithdrawsRequestsByEpoch[_user][reqEpoch] = 0;
instantWithdrawClaimsByEpoch[reqEpoch] -= amount;
```

If requests can span epochs, track each user's instant-request epoch (mirroring `lastWithdrawRequest`) or decrement `instantWithdrawClaimsByEpoch` proportionally at claim time. Additionally, `_defaultPrefundedInstantReserve` and `defaultPendingClaimBasis` should only see still-outstanding basis; add an invariant test asserting `sum(instantWithdrawsRequestsByEpoch[..][e]) == instantWithdrawClaimsByEpoch[e]` after every funded claim.

### Proof of Concept
Foundry fork PoC sketch (pattern follows `testProcessWithdrawalClaimsInstantEpoch` in `test/foundry/IdleCDOEpochQueue.t.sol`):

```solidity
function testInstantClaimDoublePaysRecovery() external {
  _useStandardEpochVariant();
  _stopCurrentEpochWithApr(10e18);          // enter epoch 1
  cdoEpoch.setInstantWithdrawParams(100, 1e18, false); // manager, honest

  // attacker deposits and requests instant withdraw in epoch 1
  uint256 tranches = _depositWithUser(attacker, 100e6);
  _requestInstantWithdraw(attacker, tranches);         // sets per-epoch ledgers

  // honest user2 also requests instant withdraw (stays unfunded)
  _depositWithUser(user2, 100e6);
  _requestInstantWithdraw(user2, tranches2);

  // borrower partially funds instant queue -> attacker claims at par
  _fundInstantWithdraws(tranches);                     // collectInstantWithdrawFunds
  cdoEpoch.claimInstantWithdrawRequest();              // attacker paid
  // BUG: instantWithdrawsRequestsByEpoch[attacker][1] still == tranches

  // borrower defaults; manager finalizes recovery while epochNumber still 1
  _defaultAndFinalize(recovered);                      // defaultRecoveryEpoch = 1

  uint256 balPre = underlying.balanceOf(attacker);
  cdoEpoch.claimInstantWithdrawRequest();              // pays again from reserve
  assertGt(underlying.balanceOf(attacker) - balPre, 0); // second payout
  // user2's recovery claim is correspondingly diluted / reserve underfunded
}
```

Note: the exact default-finalization sequencing (whether `epochNumber` stays equal to the request epoch through `_handleBorrowerDefault`/`finalizeDefaultRecovery`) should be confirmed against `IdleCDOEpochVariant`'s default flow when writing the runnable PoC; the stale-ledger defect itself is unconditional in `claimInstantWithdrawRequest`.
