### Title
Sentinel-value collision in `PrioritizationFee::get_min_compute_unit_price` causes `getRecentPrioritizationFees` to misreport the minimum fee when a landed transaction sets `compute_unit_price == u64::MAX` - (File: runtime/src/prioritization_fee.rs)

### Summary
`PrioritizationFee` uses `u64::MAX` both as the "no prioritized transaction seen yet" sentinel and as a legitimate value that `ComputeBudgetInstruction::set_compute_unit_price` can carry. Because `update()` only overwrites the stored minimum on a strict `<` comparison and the default is `u64::MAX`, a transaction landing with `compute_unit_price == u64::MAX` never actually mutates the field, and `get_min_compute_unit_price()` subsequently reports "unset" instead of the true value.

### Finding Description
`PrioritizationFee` is initialized with `min_compute_unit_price: u64::MAX` as the default/"unset" marker: [1](#0-0) 

`update()` only lowers `min_compute_unit_price` when the incoming `compute_unit_price` is strictly less than the current stored value: [2](#0-1) 

If a landed (finalized) transaction in the block sets `compute_unit_price == u64::MAX`, the check `compute_unit_price < self.min_compute_unit_price` evaluates `u64::MAX < u64::MAX` = `false`, so the field is left at its default `u64::MAX` — indistinguishable from the "no prioritized transactions in this block" state.

`get_min_compute_unit_price()` treats `u64::MAX` as unset and returns `None`: [3](#0-2) 

This value is surfaced through `PrioritizationFeeCache::get_prioritization_fees`, which is consumed by the `getRecentPrioritizationFees` RPC handler in `rpc/src/rpc.rs`. When this collision occurs, the RPC will report the slot as having no minimum prioritization fee (or fall back to 0) even though a real transaction landed with the maximal possible `compute_unit_price`, producing a wrong-value response for that slot.

### Impact Explanation
This is a data-representation/misreporting bug: `getRecentPrioritizationFees` returns a value (`None`/absence of fee data for the slot) that does not faithfully reflect the on-chain fee paid by a finalized transaction. No consensus state, ledger data, or validator stability is affected — it is confined to the RPC value returned for prioritization-fee queries. It matches the "decoder panic and misreporting" category referenced in scope, specifically as an incorrect-value response from a single RPC call rather than a crash or DoS.

### Likelihood Explanation
Feasibility depends on getting a transaction landed and finalized with `compute_unit_price` exactly `u64::MAX`, set via a normal `ComputeBudgetInstruction::set_compute_unit_price(u64::MAX)`. Nothing in the reviewed compute-budget instruction parsing path caps this value below `u64::MAX`; the fee-payer must be able to cover the resulting (very large, likely saturating) prioritization fee for the transaction to actually be admitted and processed, which raises the practical bar but does not require any privileged access, gossip, or leader control — it is a normal unprivileged transaction-submission plus a single `getRecentPrioritizationFees` call, both within the stated attacker capability.

### Recommendation
Use a dedicated `Option<u64>` (or a distinct out-of-band sentinel not reachable by a legitimate `compute_unit_price`) for `min_compute_unit_price` instead of overloading `u64::MAX`, and change `update()`'s comparison logic to `Option`-aware `min` semantics, e.g. store `Option<u64>` and use `.map_or(cu_price, |cur| cur.min(cu_price))` analogous to `PrioritizationFeeMetrics::update_compute_unit_price`, so any real value including `u64::MAX` is preserved and distinguishable from "no data."

### Proof of Concept
```rust
#[test]
fn test_min_compute_unit_price_u64_max_collision() {
    let mut prioritization_fee = PrioritizationFee::default();
    assert!(prioritization_fee.get_min_compute_unit_price().is_none());

    // Attacker's transaction lands with compute_unit_price == u64::MAX
    prioritization_fee.update(u64::MAX, 10, vec![]);

    // BUG: this currently returns None because u64::MAX collides with the
    // "unset" sentinel, even though a real transaction set this exact value.
    // Expected (correct) behavior:
    assert_eq!(
        Some(u64::MAX),
        prioritization_fee.get_min_compute_unit_price()
    );
}
```
Differential check: compare the raw transaction's `compute_unit_price` (`u64::MAX`) against the value returned by `PrioritizationFeeCache::get_prioritization_fees` / the `getRecentPrioritizationFees` RPC response for the slot containing that transaction — the RPC value will be missing/0 instead of `u64::MAX`, confirming the misreport.

    pub fn update(
        &mut self,
        compute_unit_price: u64,
        prioritization_fee: u64,
        writable_accounts: Vec<Pubkey>,
    ) {
        let (_, update_us) = measure_us!({
            if !self.is_finalized {
                if compute_unit_price < self.min_compute_unit_price {
                    self.min_compute_unit_price = compute_unit_price;
                }

                for write_account in writable_accounts {
                    self.min_writable_account_fees
                        .entry(write_account)
                        .and_modify(|write_lock_fee| {
                            *write_lock_fee = std::cmp::min(*write_lock_fee, compute_unit_price)
                        })
                        .or_insert(compute_unit_price);
                }

                self.metrics
                    .accumulate_total_prioritization_fee(prioritization_fee);
                self.metrics.update_compute_unit_price(compute_unit_price);
            } else {
                self.metrics
                    .increment_attempted_update_on_finalized_fee_count(1);
            }
        });

        self.metrics.accumulate_total_update_elapsed_us(update_us);
    }
