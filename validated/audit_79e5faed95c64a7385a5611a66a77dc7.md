### Title
Unsafe silent truncation of the deposit `mint` value from `uint256` to `u128` in `Deposits::unmarshal_v0` - (File: crates/consensus/protocol/src/deposits.rs)

### Summary
`Deposits::unmarshal_v0` parses the L1 deposit event's `opaqueData`, which per the documented encoding contains a `uint256 mint` field (`abi.encodePacked(uint256 mint, uint256 value, uint64 gasLimit, uint8 isCreation, bytes data)`) [1](#0-0) . Instead of reading and validating the full 32-byte `mint` word, the code only extracts the last 16 bytes (`data[offset+16..offset+32]`) and silently discards the first 16 bytes without checking they are zero, directly analogous to the reported `_executeClaim` unsafe downcast pattern (`uint256` → `uint120`/`uint128` without a safe-cast check) [2](#0-1) .

### Finding Description
The struct field `TxDeposit.mint` is a `u128` by design [3](#0-2) , but the source data is a full `uint256` on L1. Every other length-sensitive value decoded in this same file (`opaque_content_len`) is decoded with an explicit `try_into()` that returns `DepositDecodeError::OpaqueContentOverflow` if the value cannot fit in the target type [4](#0-3) . The `mint` field, however, has no equivalent overflow check: it is decoded purely by slicing off the low 16 bytes of the 32-byte word, which is an unchecked, unsafe downcast, exactly the bug class described in the report (`uint120(_totalAmount)` truncation without `SafeCast`).

### Impact Explanation
If an L1 depositor (unprivileged, permissionless caller of the deposit contract) submits a deposit whose `mint` value has any of its high 16 bytes set to a non-zero value (e.g. `mint = 2^128 + X`), this implementation silently truncates it to `X` and continues processing the deposit as valid, rather than rejecting the malformed/overflowing deposit log as an error. This is a derivation-correctness bug in a reachable, attacker-influenced input path (the "derivation of attacker-written L1 deposit… data" class explicitly in scope): a divergent client that instead validates and rejects (or otherwise handles) an out-of-range `mint` would derive a different L2 chain/transaction set than this implementation, which silently accepts a truncated value — a canonical source of state/derivation divergence (wrong provable output root / potential chain split) between conforming implementations, since the derivation must be byte-for-byte deterministic and validated identically across all clients that process L1 deposit logs.

### Likelihood Explanation
Likelihood is low-to-moderate: on the standard ETH gas-token bridge, `mint` is bound to `msg.value`, which cannot realistically exceed `u128::MAX` (~3.4×10^38 wei ≫ total ETH supply), so accidental triggering is not possible. However, for custom gas token deployments (where the deposited/mint amount is driven by an arbitrary ERC-20 amount parameter rather than native ETH balance) an attacker can freely choose a `_mint` argument up to `type(uint256).max` when depositing a token they control, making this directly attacker-reachable without needing any privileged role.

### Recommendation
Decode the full 32-byte `mint` word and explicitly validate/reject (mirroring the pattern already used for `opaque_content_len`) values that do not fit in `u128`, returning a `DepositDecodeError` (e.g. add a `MintOverflow` variant) instead of silently discarding the upper 16 bytes:
```rust
let mint_u256 = U256::from_be_slice(&data[offset..offset + 32]);
tx.mint = mint_u256.try_into().map_err(|_| DepositDecodeError::MintOverflow(...))?;
```

### Proof of Concept
1. Construct/emit a `TransactionDeposited` log whose `opaqueData` word for `mint` (`data[0..32]`) is `0x00000000000000000000000000000001_00000000000000000000000000000005` — i.e. high 16 bytes = `1`, low 16 bytes = `5`.
2. Call `Deposits::unmarshal_v0` (or `Deposits::decode`) on this log.
3. Observe `tx.mint == 5` is produced with no error, even though the true encoded `uint256` value was `2^128 + 5` — demonstrating the silent, unchecked truncation, matching the "unsafely downcasted from `uint256`" pattern in the referenced report. [5](#0-4)
