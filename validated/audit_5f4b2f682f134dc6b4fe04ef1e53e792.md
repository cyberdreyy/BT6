### Title
Unauthenticated attacker can trigger disclosure of internal error details via jsonAPIError when FindExternalInitiator fails with a non-`sql.ErrNoRows` DB error - ([File: core/web/auth/auth.go], [File: core/web/auth/helpers.go])

### Summary
`AuthenticateExternalInitiator` in `core/web/auth/auth.go` only maps `sql.ErrNoRows` from `FindExternalInitiator` to the generic `auth.ErrorAuthFailed`; any other error (e.g. a database/driver error) is wrapped with `pkgerrors.Wrap(err, "finding external initiator")` and propagated up to the `Authenticate` middleware, which passes it directly to `jsonAPIError`. `jsonAPIError` in `core/web/auth/helpers.go` serializes `err.Error()` (raw, unredacted) into the JSON response body sent to the unauthenticated caller.

### Finding Description
The authentication chain is: `Authenticate(store, methods...)` (core/web/auth/auth.go:157-175) iterates auth methods including `AuthenticateExternalInitiator` (auth.go:119-151). That function calls `store.FindExternalInitiator(ctx, eia)` (bridges ORM, core/bridges/orm.go:263-267), which executes `SELECT * FROM external_initiators WHERE access_key = $1` via `sqlx`/`database/sql`. If this query fails for any reason other than "no rows" (e.g., a malformed access key causing a type/scan error, connection error, or other driver-level failure), the code path is: [1](#0-0) 
This returns `errors.Wrap(err, "finding external initiator")`, preserving the underlying error text (which can include raw SQL/driver error strings) inside the wrapped error's message.

Back in `Authenticate`, since this returned error is not `auth.ErrorAuthFailed`, the loop breaks immediately and the error is passed straight to `jsonAPIError`: [2](#0-1) 

`jsonAPIError` then puts `err.Error()` into the JSON response body without any redaction, sanitization, or generic replacement: [3](#0-2) 

There is no logic anywhere in this chain that replaces non-`ErrNoRows` errors with a generic "Authentication failed" message — that generic mapping only happens for `sql.ErrNoRows`. Any other DB-layer error (malformed input causing a scan/type error, DB connectivity issue, etc.) is returned verbatim (wrapped) to the unauthenticated caller in the HTTP response body.

### Impact Explanation
This is an information-disclosure issue: an unauthenticated attacker sending crafted External-Initiator-Access-Key headers can potentially receive internal implementation details (SQL query text fragments, driver error strings, or Go type/scan error messages) inside the JSON error body of a 401 response. This does not by itself grant authentication bypass, privilege escalation, or credential/secret exposure of a specific secret value (access_key/secret values themselves are not echoed back); it is a lower-severity internal-error/information-leak weakness that could aid an attacker in further reconnaissance (e.g., DB engine/version fingerprinting, confirming input validation behavior). It does not satisfy the "Secrets never leave" bounty class in a concrete way, since no actual node secret (private key, session token, external initiator hashed secret) is shown to be disclosed — only generic error text potentially containing schema/driver details.

### Likelihood Explanation
Reaching this path requires an unauthenticated HTTP request to any route protected by `Authenticate(..., auth.AuthenticateExternalInitiator)` with a crafted `X-Chainlink-EA-AccessKey` header value designed to trigger a non-`ErrNoRows` failure in the underlying `GetContext` query (e.g., value causing a scan/type mismatch, extremely long value causing driver-level errors, or a transient DB error). In practice, `SELECT * FROM external_initiators WHERE access_key = $1` with a string parameter is unlikely to produce anything other than `sql.ErrNoRows` for an unmatched string, since Postgres treats `access_key` as a text/varchar column — there's no obvious SQL-injectable or type-confusion vector demonstrated in the code to reliably trigger a distinct DB error from ordinary unauthenticated input. The question's own proof idea does not identify a concrete reachable defect that forces a different-than-ErrNoRows error given the current query definition; triggering this in practice would generally require an actual DB malfunction (connectivity fault) rather than attacker-controlled input, which falls outside "unprivileged attacker exploitable" reproducibility standards.

### Recommendation
In `AuthenticateExternalInitiator` (and similarly `AuthenticateByToken`), do not propagate the raw wrapped DB error to the HTTP layer. Log internally (e.g., via a logger) and return `auth.ErrorAuthFailed` for any error from `FindExternalInitiator`, not just `sql.ErrNoRows`. Alternatively, in `jsonAPIError`, when the calling context is unauthenticated, replace all non-`auth.ErrorAuthFailed`/non-typed-API errors with a fixed generic message and log the details server-side instead of serializing `err.Error()` into the client-visible body.

### Proof of Concept
Handler-level Go test plan (not proven to be triggerable with pure attacker-controlled HTTP input against the current query, so provided as a defensive regression test):
1. Implement a mock `Authenticator` (see `core/sessions/mocks/authentication_provider.go` pattern) whose `FindExternalInitiator` returns a non-`sql.ErrNoRows` error, e.g. `errors.New("pq: connection reset by peer")`.
2. Wire it into a `gin` test router protected by `auth.Authenticate(mockStore, auth.AuthenticateExternalInitiator)`.
3. Send an HTTP request with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers set to any value.
4. Assert the response status is 401 and, critically, assert the JSON body's `errors[0].detail` (or equivalent field produced by `models.NewJSONAPIErrorsWith`) equals a generic message (e.g., "Authentication failed") rather than containing the substring `"pq:"`, `"connection reset"`, or `"finding external initiator"`.
5. This test will currently FAIL against the code as written, since `jsonAPIError` will emit `"finding external initiator: pq: connection reset by peer"` in the body — demonstrating the leak in the code path, though exploitability depends on finding a real-world input that provokes a non-`ErrNoRows` DB error, which was not established with certainty in this analysis.

```go
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
```

```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```
