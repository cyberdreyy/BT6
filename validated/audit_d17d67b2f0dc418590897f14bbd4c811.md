### Title
Authenticated view-role user can read all External Initiator AccessKey/OutgoingToken credentials via GET /v2/external_initiators - ([File: core/web/router.go])

### Summary
The `GET /v2/external_initiators` route is registered with only the generic `authv2` authentication group (session or token auth) and `paginatedRequest`, with no `RequiresEditRole`/`RequiresAdminRole` wrapper, unlike the sibling `POST`/`DELETE` routes on the same resource. `ExternalInitiatorsController.Index` returns `presenters.ExternalInitiatorResource`, which includes the raw `AccessKey` and `OutgoingToken` fields for every external initiator in the system, so any authenticated user regardless of role — including `UserRoleView` — can retrieve these credentials.

### Finding Description
In `core/web/router.go`, the External Initiator routes are set up as: [1](#0-0) 
`Create` and `Destroy` are wrapped with `auth.RequiresEditRole`, but `Index` is only wrapped with `paginatedRequest`, which does not perform any role check — it merely parses pagination parameters, e.g. `paginatedRequest(eia.Index)`. The enclosing `authv2` group only requires `auth.Authenticate` with `AuthenticateByToken`/`AuthenticateBySession`, which succeeds for any valid user session regardless of role: [2](#0-1) 

`ExternalInitiatorsController.Index` calls `App.BridgeORM().ExternalInitiators` and maps every record with `presenters.NewExternalInitiatorResource`, with no redaction: [3](#0-2) 

The presenter that is serialized to JSON includes the raw secret material: [4](#0-3) 

`RequiresEditRole`/`RequiresAdminRole` middleware in `core/web/auth/auth.go` demonstrate that the codebase's intended authorization model distinguishes `UserRoleView`, `UserRoleRun`, `UserRoleEdit`/`UserRoleAdmin`, and blocks view-role users from edit-scoped actions: [5](#0-4) 
Since `Index` has no such wrapper, a `UserRoleView` session that successfully authenticates via `AuthenticateBySession` (setting `SessionUserKey` to a view-role `User`) reaches the handler unblocked and receives `AccessKey`/`OutgoingToken` for every configured external initiator.

### Impact Explanation
`AccessKey`/`OutgoingToken` are the credentials an external initiator uses to authenticate to the node (via `AuthenticateExternalInitiator`, which grants `UserRoleRun`-equivalent capability to trigger job runs at `/v2/jobs/:ID/runs`). A view-role user retrieving these values can impersonate the external initiator and trigger job runs — an unauthorized-action/credential-disclosure impact, exceeding the privileges intended for the `view` role, matching Chainlink's "key/secret disclosure leading to unauthorized action" bounty class.

### Likelihood Explanation
Preconditions are minimal: only a valid `view`-role session or API token, which is a legitimately provisioned low-privilege credential in Chainlink Node's RBAC model. No admin/edit access, no host access, and no special timing is needed — a single unauthenticated-by-role `GET /v2/external_initiators` request suffices and is fully repeatable, exposing all external initiators in the node.

### Recommendation
Wrap `Index` with `auth.RequiresEditRole` (or `RequiresAdminRole`), consistent with `Create`/`Destroy`:
```go
authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))
```
Additionally, consider not returning `AccessKey`/`OutgoingToken` in list responses at all (only return them once, at creation time, as is already done via `ExternalInitiatorAuthentication` for `Create`), reducing exposure even to edit/admin roles that don't need repeated access to raw secrets.

### Proof of Concept
Go handler-level integration test (extending `core/web/external_initiators_controller_test.go`):
1. As an admin/edit session, `POST /v2/external_initiators` to create an EI named `"test-ei"`; capture returned `AccessKey`/`OutgoingToken`.
2. Create a second session/user with `Role: clsessions.UserRoleView` (using existing test helpers such as `cltest.CreateUserWithRole` or similar, seen used across `core/sessions/*_test.go`).
3. Using the view-role session cookie, send `GET /v2/external_initiators`.
4. Assert: HTTP status 200 (not 401/403), and response body's `data[].attributes.accessKey` / `outgoingToken` for `"test-ei"` are non-empty and match the values captured in step 1.
5. Compare against `POST`/`DELETE` on the same resource with the view-role session, expecting 401/403 (confirming the inconsistency is specific to `Index`).

```go
func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
```

```go
// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
