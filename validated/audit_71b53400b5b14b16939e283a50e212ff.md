### Title
Gateway forwards unauthenticated `web_api_trigger` messages to all DON members without sender allowlist checks, enabling resource-exhaustion / broadcast amplification - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` accepts any structurally-valid, signed `MethodWebAPITrigger` message, registers it in `h.savedCallbacks`, and unconditionally fans it out via `don.SendToNode` to every member of `h.donConfig.Members` — with a `// TODO: apply allowlist and rate-limiting here` comment sitting directly above the dispatch code. The real per-workflow `allowedSenders` check only happens later, inside each DON node's capability (`processTrigger` in `core/capabilities/webapi/trigger/trigger.go`), meaning every unauthenticated request is fully processed and broadcast to the whole DON before any sender-based authorization is applied.

### Finding Description
`ProcessRequest` in `core/services/gateway/gateway.go` (lines 218-291) decodes the raw HTTP body, calls `msg.Validate()` (structural/signature-format validation), and for legacy requests invokes `h.HandleLegacyUserMessage(ctx, msg, callback)` directly — there is no sender-allowlist or per-sender quota check at this ingress layer.

In `core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage` (lines 341-421) performs only: payload decoding, timestamp/staleness checks, and method-type checks. Immediately after the `// TODO: apply allowlist and rate-limiting here` comment (line 384), it:
1. Builds a JSON-RPC request from the message via `common.ValidatedRequestFromMessage`.
2. Registers the message under `h.savedCallbacks[msg.Body.MessageId]` (lines 411-414).
3. Loops over **all** `h.donConfig.Members` and calls `don.SendToNode(ctx, member.Address, req)` for each (lines 417-419), with no filtering based on `msg.Body.Sender`.

The only sender-based authorization in this flow lives in `core/capabilities/webapi/trigger/trigger.go`, `processTrigger` (lines 80-149): each DON node independently checks `trigger.allowedSenders[sender.String()]` per registered workflow trigger before dispatching a `TriggerResponse`, and rejects unauthorized senders with "unauthorized Sender" errors. This check happens *after* the message has already been broadcast by the gateway to every node in the DON — i.e., after the resource cost of validation, callback bookkeeping, per-node dispatch, and per-node signature/JSON-RPC processing has already been paid.

This means: for a message from a sender not present in any trigger's `allowedSenders`, the gateway still (a) stores the message in its `savedCallbacks` map, and (b) fires `SendToNode` calls for every DON member. Only the node-side `processTrigger` ultimately blocks execution of the actual capability. No workflow gets triggered for an unauthorized sender (the on-node check does prevent unauthorized capability execution), but the gateway-level fan-out and bookkeeping happen regardless.

### Impact Explanation
This matches a resource-exhaustion / allowlist-bypass-at-the-gateway-layer issue: an unauthenticated attacker with any ECDSA key can force the gateway to store entries in `h.savedCallbacks` and to invoke `don.SendToNode` against every DON member for a request that has no legitimate destination, consuming gateway memory/bookkeeping and DON node bandwidth/CPU (each node must decode, verify, and run `processTrigger` before rejecting). At scale this allows amplification: one HTTP POST to the gateway becomes N `SendToNode` calls to N DON nodes. It does **not**, however, result in unauthorized workflow/capability execution, since `processTrigger`'s `allowedSenders` check on each node blocks the trigger from actually firing — so this is a DoS/resource-exhaustion class issue rather than a full authorization bypass leading to fund movement or unauthorized job execution.

### Likelihood Explanation
Low barrier to entry: any attacker who can sign a `MessageBody` with an arbitrary ECDSA key (no registration or allowlist membership required) and knows a valid DON ID can trigger this repeatedly. The gateway's own rate limiting (`nodeRateLimiter`) only applies to node→client (`handleWebAPIOutgoingMessage`) traffic, not user→gateway ingress in `HandleLegacyUserMessage`, and `MaxSavedCallbacks`/`CallbackMaxAgeSec` pruning is the only backstop against unbounded growth of `savedCallbacks`. This is fully reproducible with a handler-level unit test.

### Recommendation
Implement the allowlist/rate-limiting check that the TODO comment references before registering the callback and broadcasting to `don.SendToNode`: either (a) have the gateway maintain awareness of per-workflow `allowedSenders`/topics so it can reject unauthorized senders before fan-out, or (b) at minimum apply a per-sender rate limiter (similar to `nodeRateLimiter`) at the ingress of `HandleLegacyUserMessage` to cap the fan-out cost imposed by any single unauthenticated sender.

### Proof of Concept
Handler-level Go test in `core/services/gateway/handlers/capabilities/handler_test.go` style:
1. Construct a `handler` with a `donConfig` containing N mock DON members and a mock `handlers.DON` (`don.On("SendToNode", ...)`).
2. Build an `api.Message` with `Method: MethodWebAPITrigger`, a valid timestamp, and `Body.Sender` set to an address never referenced anywhere in test fixtures/allowedSenders (simulating "not present in any trigger's allowedSenders").
3. Call `h.HandleLegacyUserMessage(ctx, msg, callback)`.
4. Assert: `don.AssertNumberOfCalls(t, "SendToNode", N)` — i.e., `SendToNode` fires for every DON member despite the sender never being allowlisted anywhere.
5. Assert `h.savedCallbacks` contains an entry keyed by `msg.Body.MessageId` after the call.

This demonstrates that authorization is not enforced before the gateway commits resources and broadcasts to the DON, confirming the gap identified by the `TODO: apply allowlist and rate-limiting here` comment. [1](#0-0) [2](#0-1) [3](#0-2)
