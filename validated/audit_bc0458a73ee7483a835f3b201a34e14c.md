### Title
`BlockRejection::hash()` excludes `reason_code`/`response_data` from the signed preimage, making the signer's signature cross-context-valid across different rejection reasons for the same block - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection::hash()` computes the message-level signature preimage from only `self.signer_signature_hash` (plus `chain_id` in the domain tuple), never touching `reason`, `reason_code`, or `response_data` (which itself carries `reject_reason`, `failed_txid`, and tenure-extend timestamps). This is the same class of bug as the external report: a signature is supposed to authenticate a full logical object, but the hash/preimage construction silently drops fields that downstream consumers still trust as if they were signed.

### Finding Description
`BlockRejection::hash()`:
```rust
pub fn hash(&self) -> Sha256Sum {
    let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
    let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
    structured_data_message_hash(data, domain_tuple)
}
``` [1](#0-0) 

`sign()`, `verify()`, and `recover_public_key()` all operate on this same truncated hash: [2](#0-1) 

The `BlockRejection` struct carries `reason: String`, `reason_code: RejectCode`, and `response_data: BlockResponseData` (which embeds `reject_reason: RejectReason`, `failed_txid: Option<Txid>`, and tenure-extend timestamps) alongside `signer_signature_hash`: [3](#0-2) 

None of those fields are part of the signed hash. Consequently, any two `BlockRejection` values that share the same `signer_signature_hash` and `chain_id` but differ in `reason`, `reason_code`, or `response_data` (including `reject_reason` and `failed_txid`) will produce an identical `hash()`, so a signature originally produced over one variant verifies successfully for any other variant with those fields swapped.

Consumers treat the recovered public key from this signature as authenticating the *entire* rejection content, not just the block hash:
- Signer-side: `handle_block_rejection` recovers the pubkey via `rejection.recover_public_key()`, authenticates the sender, and then feeds `rejection.response_data.reject_reason` into `store_and_process_block_rejection`, which tallies `RejectReasonPrefix::ReorgNotAllowed` weight to decide whether to mark the current miner invalid: [4](#0-3) [5](#0-4) 
- Node-side: `stackerdb_listener.rs` recovers/validates the rejecting signer's pubkey and then uses `rejected_data.reason_code` and `rejected_data.response_data.failed_txid` to accumulate per-txid weight (`total_weight`, `problematic_weight`) that later determines which txids get temporarily or permanently excluded from block templates: [6](#0-5) [7](#0-6) 

Because none of `reason_code`/`response_data`/`reason` is bound by the signature, whichever component ends up trusting `rejection.signature` as proof of *what a signer actually decided* (reject reason, failed txid) is trusting an assertion the signature never made. This is the direct analog of the Solidity `getNamespace` bug: the signature commits to less data than the code implicitly assumes it commits to, enabling a value substitution that changes the meaning of an authenticated message while keeping it "valid."

### Impact Explanation
If this per-message signature is ever consumed independent of, or with a weaker guarantee than, the transport-level authentication (e.g. any code path that re-serializes/relays/persists a `BlockRejection` and re-derives sender identity purely from `rejection.recover_public_key()`/`rejection.verify()` rather than from the original StackerDB chunk signature), an attacker who can substitute `reason_code`/`response_data`/`reason` while keeping the original `signature` and `signer_signature_hash` bytes produces a `BlockRejection` that still verifies as authored by the original signer, but asserts a different rejection reason or failed txid than the signer ever actually signed. Depending on which reason is substituted, this can:
- Falsely inflate `ReorgNotAllowed` rejection weight and cause `sortition_state.cur_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock` to fire without the reward-weighted quorum of signers ever actually voting `ReorgNotAllowed` — a liveness/censorship wedge against a legitimate miner.
- Falsely attribute `ProblematicTransaction`/`BadTransaction` weight to an arbitrary `failed_txid`, causing the coordinator to permanently or temporarily exclude a transaction from block templates that no signer actually flagged.

This matches the "cross-context-valid signature" impact category: the same signature is valid across multiple distinct logical messages because the hash omits fields the protocol treats as signed.

### Likelihood Explanation
The exploitability of this bug hinges entirely on whether any code path uses `BlockRejection.signature`/`hash()`/`verify()`/`recover_public_key()` as the *sole* authentication for the mutable fields (`reason_code`, `response_data`), independent of the outer StackerDB-chunk-level signature that already covers the full serialized message bytes. Within the code reachable in this review, every consumer of `BlockRejection` (`handle_block_rejection` in `signer.rs`, and the `SignerMessageV0::BlockResponse` handling in `stackerdb_listener.rs`) receives the struct already fully authenticated end-to-end by the StackerDB chunk signature over the entire serialized `SignerMessage`, which does cover `reason_code` and `response_data`. I was not able to find, within the time available, a concrete code path where the narrower message-level `hash()`/`verify()` is used as the sole trust boundary for `reason_code`/`response_data` without that outer chunk-level protection also covering the same bytes — this would require either an alternate transport that only forwards the `BlockRejection` struct and its embedded signature, or a persistence/replay path that re-validates via `recover_public_key()` alone and swaps in different `reason_code`/`response_data` while reusing the stored `signature`. That would fall outside "transport/StackerDB sync mechanics," which is explicitly out of scope, so I flag this finding as **structurally confirmed** (a real signing-scope defect, matching the report's bug class precisely) but **could not fully confirm a currently-reachable exploit path that satisfies the "no majority, no other signer's key, no transport mechanics" scoping constraints** given the tools and time available. This is a genuine gap in the codebase's defense-in-depth (the message-level signature should bind everything it purports to authenticate), but I am not certain it is independently exploitable outside of the StackerDB transport layer in the current code.

### Recommendation
Include `reason_code` and the full `response_data` (or at minimum `response_data.reject_reason` and `response_data.failed_txid`) in the `BlockRejection::hash()` preimage, e.g. by hashing a tuple of `{signer_signature_hash, reason_code, reject_reason, failed_txid}` (analogous to how `signer_signature_hash_inner` in `NakamotoBlockHeader` binds every field it claims to sign) rather than only `signer_signature_hash`. This removes the latent cross-context signature ambiguity regardless of which transport eventually carries the message, and brings the message-level signature's guarantees in line with what every downstream consumer of `reason_code`/`response_data` already assumes.

### Proof of Concept
```rust
// Two BlockRejection values sharing the same signer_signature_hash and chain_id,
// but asserting different reject reasons / failed txids, hash identically and
// therefore share a valid signature under BlockRejection::hash():
let base = BlockRejection::new(
    signer_signature_hash.clone(),
    RejectReason::ValidationFailed(ValidateRejectCode::BadTransaction),
    &signer_privkey,
    mainnet,
    ts1, ts2,
);

// Attacker-crafted variant: same signer_signature_hash/chain_id, different
// reason_code/response_data (e.g. ReorgNotAllowed instead of BadTransaction),
// but reusing base.signature verbatim.
let mut forged = base.clone();
forged.reason_code = RejectCode::ValidationFailed(ValidateRejectCode::ReorgNotAllowed); // illustrative
forged.response_data.reject_reason = RejectReason::ReorgNotAllowed;
forged.signature = base.signature; // signature is still valid, because hash() ignores these fields

assert_eq!(base.hash(), forged.hash()); // hash() only depends on signer_signature_hash + chain_id
// forged.verify(&signer_pubkey) succeeds identically to base.verify(&signer_pubkey)
```

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {

            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
