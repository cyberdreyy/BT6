### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing a request to execute below the intended live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`confirm()` decides whether to execute a pending request purely by comparing the size of the `confirmations` set to `num_confirmations`, without ever re-validating that the accounts/keys already present in that set are still current members. `delete_member()` only purges requests that were *originated* by the removed member; it never scans other pending requests to strip that member's stale confirmation out of their `confirmations` sets. This is the same class of bug as the `BlockhashRegistry.recreateBlockheaders` issue: a piece of state (the empty `_blockheaders` array / here, the stale confirmation entry) is trusted at face value and a boundary check (`calculatedHash != 0` / here, `confirmations.len()+1 >= num_confirmations`) passes trivially even though nothing of substance backs it, letting privileged state mutate (execute the request) without the required real-world validation.

### Finding Description
`confirm()`: [1](#0-0) 

`delete_member()`: [2](#0-1) 

`delete_member` removes stale requests/confirmations only for `request_ids` whose `r.member == member` (i.e., requests *created* by the removed member): [3](#0-2) 

It never inspects `self.confirmations` entries belonging to *other* still-pending requests that the removed member had previously confirmed. Those confirmation sets (`HashSet<String>`, keyed by member identity string) are left untouched.

`confirm()` then trusts `confirmations.len()` as if every entry represents a currently-live, authorized member: [4](#0-3) 

The equivalent flaw exists in the legacy `multisig/src/lib.rs`, where `DeleteKey` purges only requests originated by the removed key, not confirmations recorded by that key on other requests: [5](#0-4) [6](#0-5) 

The binding that should hold is:
`confirmations counted for request R == number of confirmations from accounts that are members of the multisig at the time R is finally confirmed/executed`

This binding is broken: a confirmation recorded by member A while A was a member remains counted after A is removed, so:
`confirmations counted (includes stale A) > confirmations from currently-live members`

### Impact Explanation
This crosses the "multisig request executed below threshold" boundary explicitly called out as Critical impact. Concretely:
- Members: A, B, C; `num_confirmations = 2`.
- B creates request R (e.g. `Transfer` funds to an attacker/self-controlled account, or `AddKey`/`AddMember` to seize the multisig).
- A confirms R: `confirmations = {A}` (1 < 2, request stays pending).
- Later, A is removed as a member via a separate, properly-authorized `DeleteMember` request (a routine operational action, e.g. offboarding or reacting to a suspected key compromise) — this does **not** touch R's confirmation set.
- Now only B and C remain as members. C confirms R: `confirmations.len() (1, stale A) + 1 (C) = 2 >= num_confirmations (2)` → R executes.
- R has executed with only **one** confirmation from a currently-live member (C), even though the contract's own accounting believes 2-of-N approved it. If R was a `Transfer` or `AddKey`/`AddMember` action, NEAR funds move or the multisig's access set is altered on the authority of a single live signer instead of the intended threshold of two.

This is Critical: NEAR is moved, or the trust set (members/keys) is altered, by fewer real authorizers than the deployed threshold requires.

### Likelihood Explanation
Any multisig that ever removes a member/key while that member/key has outstanding, unconfirmed-but-partially-confirmed requests is affected — this is a normal, expected multisig operational pattern (e.g. offboarding a signer or reacting to key compromise), not an edge case requiring an attacker-controlled deployment or ignored initialization. No malicious insider action is required beyond ordinary governance; the flaw is purely in the accounting logic of `confirm()`/`delete_member()`/`DeleteKey` failing to revalidate confirmer identity against the live member/key set.

### Recommendation
When counting confirmations in `confirm()`, filter `confirmations` to only those entries that are still present in `self.members` (or, for the legacy contract, still a valid access key on the account) before comparing against `num_confirmations`. Additionally, `delete_member`/`DeleteKey` should scrub the removed member's identity from every request's confirmation set, not just purge requests that member originated.

### Proof of Concept
```rust

let mut c = MultiSigContract::new(vec![member_a(), member_b(), member_c()], 2);

// B creates a Transfer request
testing_env!(context_with_account(member_b_id(), amount));
let request_id = c.add_request(MultiSigRequest {
    receiver_id: attacker(),
    actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
});

// A confirms (1 of 2)
testing_env!(context_with_account(member_a_id(), amount));
c.confirm(request_id);
assert_eq!(c.confirmations.get(&request_id).unwrap().len(), 1);

// Multisig legitimately removes A via a separate, fully-confirmed DeleteMember request
// (using B + C confirmations on that separate request) -- omitted for brevity,
// but note delete_member() does NOT touch `request_id`'s confirmations set:
// self.requests.iter().filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
// only matches requests *created* by A, not ones A merely confirmed.

// C confirms the still-pending Transfer request; A's stale confirmation still counts
testing_env!(context_with_account(member_c_id(), amount));
c.confirm(request_id);
// confirmations.len() (1, stale A) + 1 (C) = 2 >= num_confirmations(2) -> executes
// Only ONE live member (C) actually authorized this transfer.
```

```rust
    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
```

```rust
    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
```
