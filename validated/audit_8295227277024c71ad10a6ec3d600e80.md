## Title
Deposit front-running lets an attacker permanently hijack a validator's withdrawal address before the legitimate depositor's deposit is finalized - (File: `specs/electra/beacon-chain.md`, also present in `specs/fulu/beacon-chain.md` and `specs/gloas/beacon-chain.md`)

### Summary
This is a valid analog of the reported "reorg-vulnerable `create`-address" bug class. In the reported contract bug, ownership of an address derived only from a mutable counter (the factory nonce) is awarded to whoever's transaction lands first, so a reorg/race lets an attacker seize an address the victim expected to control. In consensus-specs, ownership of a not-yet-registered validator's `withdrawal_credentials` is likewise awarded to whichever `PendingDeposit` for that pubkey is processed *first* — a purely order-dependent, unprivileged race with no signature check tying the winning claim to the intended owner beyond a BLS signature that a rogue key-generating party (e.g. a staking-pool node operator who legitimately holds the pubkey's privkey before the pool's withdrawal-credentials binding is submitted) can freely produce.

### Finding Description
When a deposit for a pubkey that is not yet in `state.validators` is applied, `apply_pending_deposit` blindly calls `add_validator_to_registry` using the `withdrawal_credentials` of *that* pending deposit — whichever one happens to be first in the processed order: [1](#0-0) 

All later deposits for the same pubkey are then treated purely as balance top-ups to the validator that was created by the winning deposit, with no verification that the depositor is the intended owner: [2](#0-1) [3](#0-2) 

The deposit-request path (`process_deposit_request`) simply enqueues whatever `PendingDeposit` arrives from the execution layer, with no binding between a pubkey and a specific `withdrawal_credentials` value: [4](#0-3) 

The equivalent "first pending deposit for a pubkey wins" ordering is directly demonstrated by the test suite: [5](#0-4) 

This is the exact class of bug the `QuestFactory` report describes: a piece of state ("who owns pubkey P") is derived by a race on ordering rather than an explicit, unforgeable authorization, and whoever's message lands first captures control of all future value directed at that identifier. Just as CREATE-address ownership on Polygon/Optimism/Arbitrum can be flipped by a ~1.5-minute reorg, deposit-processing order for a given pubkey can be flipped by mempool front-running of the execution-layer deposit transaction, or by an EL reorg that reorders which deposit transaction for the same pubkey is included first, since deposits are applied to `pending_deposits` in fixed FIFO order once finalized (`specs/electra/beacon-chain.md:1116-1193`) and the position in that queue is entirely a function of inclusion order, not authorization.

Critically, the beacon chain's own maintainers have already recognized and are fixing exactly this bug class: EIP-8205 introduces a `PreregistrationRequest`/`ValidatorPreregistrations` mechanism whose explicit stated purpose is "protecting delegated staking deployments against deposit front-running," by binding a pubkey to specific `withdrawal_credentials` *before* the first deposit is processed, and discarding any deposit that doesn't match the bound credentials: [6](#0-5) [7](#0-6) 

Because this mitigation only exists in the not-yet-adopted `eip8205` feature branch, mainline forks (Electra, Fulu, Gloas) that are in current production scope remain exposed to the underlying race.

### Impact Explanation
This breaks the "Gwei paid to a non-owner" invariant: any depositor whose deposit for a not-yet-registered pubkey is processed after an attacker's competing deposit for the same pubkey has all future top-ups (and, when the validator eventually exits, its entire stake) directed to the attacker's `withdrawal_credentials`, not the intended owner's. This is especially damaging for delegated/pooled-staking setups where a pubkey is generated by an operator and a separate, larger deposit funding the validator's stake is expected to follow with the pool's withdrawal address — the operator (or anyone who learns the pubkey and can produce a signature, e.g. because they hold the initial privkey before handing over control) can win the race and redirect the entire validator's future balance to themselves. Per the report's severity mapping, this is a Critical-class impact (Gwei paid to a non-owner).

### Likelihood Explanation
Exploitation requires only observing a pending deposit transaction (public in the EL mempool, or discoverable via a short reorg reordering two already-broadcast deposit transactions) and submitting a competing, validly-signed deposit for the same pubkey before it is finalized — no coalition, client bug, or majority stake is needed, matching the unprivileged nature of the reported reorg-race bug. The primary constraint is that the front-runner must be able to produce a valid BLS signature for the pubkey, which is realistic in the delegated-staking scenario EIP-8205 itself calls out (a party holding the pubkey's privkey before the withdrawal-credentials binding is finalized).

### Recommendation
Adopt the EIP-8205-style preregistration/binding mechanism (or an equivalent) in the mainline specs so that a pubkey's `withdrawal_credentials` are committed to and verified *before* the first deposit for that pubkey can register a validator, analogous to using `create2` with a `salt` that binds `msg.sender` in the original contract report — i.e., make the binding an explicit, authenticated commitment rather than "first deposit processed wins."

### Proof of Concept
1. Alice (or a staking-pool coordinator) generates keypair `(sk, pubkey)` and prepares `DepositData(pubkey, withdrawal_credentials=W_alice, amount, sig)`, broadcasting the EL transaction.
2. Before Alice's transaction is included/finalized, an attacker who has observed `pubkey`/`sig` (or who holds `sk`, e.g. a rogue node operator in a delegated-staking flow) submits a deposit request/transaction with `DepositData(pubkey, withdrawal_credentials=W_attacker, amount', sig')`, signed correctly per `is_valid_deposit_signature`, and gets it included first (via faster propagation or a short EL reorg).
3. On the beacon chain, `process_pending_deposits`/`apply_pending_deposit` processes the attacker's `PendingDeposit` first (see `specs/electra/beacon-chain.md:1097-1114`), so `add_validator_to_registry` creates the validator with `withdrawal_credentials=W_attacker`.
4. Alice's subsequent deposit for the same `pubkey` is now treated as a top-up (`apply_pending_deposit` else-branch), increasing the balance of the validator whose withdrawal address is `W_attacker`.
5. When the validator exits/is fully withdrawn, all funds — Alice's stake included — are paid to `W_attacker`, confirmed by the `assert_process_deposit_request`/`run_pending_deposit_applying` test helpers showing balance is credited strictly by pubkey match regardless of who deposited it (`tests/core/pyspec/eth_consensus_specs/test/helpers/deposits.py:454-566`).

def apply_pending_deposit(state: BeaconState, deposit: PendingDeposit) -> None:
    """
    Applies ``deposit`` to the ``state``.

    validator_pubkeys = [v.pubkey for v in state.validators]

## Introduction

This upgrade adds withdrawal credentials preregistration to the beacon chain as
part of the EIP-8205 upgrade. A preregistration binds a validator pubkey to
withdrawal credentials before the validator's first deposit is processed,
protecting delegated staking deployments against deposit front-running.

This document specifies the beacon chain changes required to support these
preregistrations. The upgrade introduces a new request type within the execution
payload, triggered by execution layer transactions, which stores a
pubkey-to-withdrawal-credentials binding in the beacon state. While a binding is
active, a deposit request for the bound pubkey is discarded unless its
withdrawal credentials match the binding and its signature is valid.

def process_deposit_request(state: BeaconState, deposit_request: DepositRequest) -> None:
    # [New in EIP8205]
    preregistration = get_active_preregistration(state, deposit_request.pubkey)
    if preregistration is not None:
        if deposit_request.withdrawal_credentials != preregistration.withdrawal_credentials:
            return

        if not is_valid_deposit_signature(
            deposit_request.pubkey,
            deposit_request.withdrawal_credentials,
            deposit_request.amount,
            deposit_request.signature,
        ):
            return

        remove_stored_preregistration(state, deposit_request.pubkey)

    state.pending_deposits.append(

            pubkey=deposit_request.pubkey,
            withdrawal_credentials=deposit_request.withdrawal_credentials,
            amount=deposit_request.amount,
            signature=deposit_request.signature,
            slot=state.slot,
        )
    )
