## Analysis

The external report's core invariant is: **an operator-controlled configuration change can be applied without checking for outstanding user claims, permanently freezing already-committed value while other paths (liquidation) continue to operate.**

The closest Aptos-native analog is in the stake lockup renewal mechanism shared by `stake.move`, `staking_contract.move`, and `vesting.move`.

### Title
Admin/staker can indefinitely extend stake-pool lockup via repeated `reset_lockup`/`increase_lockup` calls, permanently trapping already-unlocked shareholder/delegator funds in `pending_inactive` - (File: `aptos-move/framework/aptos-framework/sources/stake.move`, `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Finding Description
`stake::increase_lockup_with_cap` only requires that the new lockup expiration strictly exceed the old one: [1](#0-0) 

Because `new_locked_until_secs = now + recurring_lockup_duration_secs` and time always advances, this check is satisfiable on essentially every call as long as enough time passes between calls — there is no upper bound and no check on whether stake is currently sitting in `pending_inactive` waiting to unlock.

The `pending_inactive → inactive` transition (which is a prerequisite for `withdraw`/`withdraw_with_cap` and, in `vesting.move`, for `distribute`/`admin_withdraw`) only happens when the *current* lockup has actually expired: [2](#0-1) 

`staking_contract::reset_lockup` and `vesting::update_operator`/`reset_lockup`-style admin entry points expose `increase_lockup_with_cap` to the staker/admin at will: [3](#0-2) 

In `vesting.move`, shareholders call `unlock_rewards`/`vest` to move accumulated rewards/vested grant into `pending_inactive`, expecting that once the *current* lockup cycle ends they can `distribute()` those funds: [4](#0-3) 

If the admin (or staker, for direct `staking_contract`) calls `reset_lockup` again before the outstanding `pending_inactive` balance's lockup expires, the check `old_locked_until_secs < new_locked_until_secs` (stake.move:1052-1055) passes trivially, and the lockup clock is reset. This can be repeated indefinitely, so the `pending_inactive` stake set aside for shareholders/delegators never converts to `inactive`, and `distribute()`/`admin_withdraw()`/`withdraw()` therefore can never pay it out — even though the funds were already "unlocked" from the shareholder's perspective.

This mirrors the external report's pattern exactly: a legitimate, unprivileged-facing administrative action (`reset_lockup`, analogous to `updateSettlementConfiguration`) is not gated on the existence of outstanding claims (`pending_inactive` balances, analogous to open positions), so it can be exercised in a way that permanently stalls users' ability to realize funds they are otherwise entitled to.

### Impact Explanation
Shareholders in a `vesting.move` contract (and delegators/stakers under `staking_contract.move`) who have already called `unlock_rewards`/`vest`/`unlock` have no protocol-level cap preventing the admin/staker from perpetually re-extending the lockup via `reset_lockup`. Since `distribute`, `admin_withdraw`, and `withdraw` all gate on the `pending_inactive → inactive` transition inside `stake.move`, this can result in **non-recoverable freezing of already-earned rewards and vested principal** for unprivileged shareholders/delegators — falling squarely under the "Permanent lock or non-recoverable loss of claim rights in stake ... vesting flows" impact category.

### Likelihood Explanation
This requires only repeated, unprivileged-facing calls to an existing entry function (`reset_lockup`) by whoever already holds the staker/admin role for that specific pool — no special exploit path, race condition, or privilege escalation is needed. However, I was not able to fully verify within the tool budget whether `vesting::reset_lockup`'s exact implementation (I saw its call sites and the underlying `staking_contract`/`stake` primitives, but not its full body) or `staking_config`'s recurring lockup duration configuration imposes any additional cooldown that would mitigate this in practice on mainnet (e.g., the actual `recurring_lockup_duration_secs` value governs how "cheap" it is to grief; if it is very long, the admin would need to remember to call it well before each expiration, which lowers but does not eliminate real-world likelihood).

### Recommendation
- Track the amount of `pending_inactive` stake and its expected unlock time separately from the "next round" lockup extension, so that extending `locked_until_secs` cannot retroactively delay stake that was already moved to `pending_inactive` before the extension was requested.
- Alternatively, disallow `reset_lockup`/`increase_lockup_with_cap` from extending the lockup if there is currently non-zero `pending_inactive` balance whose existing lockup has not yet been reached, or partition `pending_inactive` by "lockup cohort" (similar to how `delegation_pool.move`'s Observed Lockup Cycle mechanism already isolates `pending_inactive` shares per lockup cycle) so a new lockup extension cannot affect stake unlocked under a prior cycle.

### Proof of Concept
Conceptual (not run against the repo, since this requires a live Move test harness):
1. Admin creates a vesting contract for shareholder S with a staking pool lockup duration `D`.
2. S calls `unlock_rewards(contract_address)` — this moves accumulated rewards into `pending_inactive` (`vesting.move:635-640`).
3. Before `D` elapses, admin calls `staking_contract::reset_lockup` (as exposed via `vesting::update_operator`/`reset_lockup`), which invokes `stake::increase_lockup_with_cap` (`stake.move:1042-1061`). Since `now + D` is strictly greater than the previous `locked_until_secs` (which is now closer), the assert passes and lockup is reset.
4. Admin repeats step 3 every `< D` interval indefinitely.
5. `update_stake_pool`'s pending_inactive→inactive condition (`stake.move:1952-1959`) never triggers because `locked_until_secs` is perpetually pushed into the future.
6. S can never successfully call `distribute()` to receive the rewards unlocked in step 2 — the funds are permanently stuck in `pending_inactive`.

Note: This candidate is reported with the caveat noted in the Likelihood section — full verification of `vesting::reset_lockup`'s exact source and of `staking_config`'s current `recurring_lockup_duration_secs` was not completed due to tool-call limits, so the practical griefing cost (how often the admin must act) is not fully confirmed.

    public fun increase_lockup_with_cap(owner_cap: &OwnerCapability) acquires StakePool {
        let pool_address = owner_cap.pool_address;
        assert_stake_pool_exists(pool_address);
        let config = staking_config::get();

        let stake_pool = borrow_global_mut<StakePool>(pool_address);
        let old_locked_until_secs = stake_pool.locked_until_secs;
        let new_locked_until_secs =
            timestamp::now_seconds()
                + staking_config::get_recurring_lockup_duration(&config);
        assert!(
            old_locked_until_secs < new_locked_until_secs,
            error::invalid_argument(EINVALID_LOCKUP)
        );
        stake_pool.locked_until_secs = new_locked_until_secs;

        event::emit(
            IncreaseLockup { pool_address, old_locked_until_secs, new_locked_until_secs }
        );
    }

    /// Convenient function to allow the staker to reset their stake pool's lockup period to start now.
    public entry fun reset_lockup(staker: &signer, operator: address) acquires Store {
        let staker_address = signer::address_of(staker);
        assert_staking_contract_exists(staker_address, operator);

        let store = borrow_global_mut<Store>(staker_address);
        let staking_contract = store.staking_contracts.borrow_mut(&operator);
        let pool_address = staking_contract.pool_address;
        stake::increase_lockup_with_cap(&staking_contract.owner_cap);

        emit(ResetLockup { operator, pool_address });
    }
