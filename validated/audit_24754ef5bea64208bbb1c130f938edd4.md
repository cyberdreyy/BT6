The external bug is a failure-path resource leak (memory not freed on `execve` failure → repeated failures exhaust resources → DoS). The strongest analog is a failure path in the vault/epoch flow where state is consumed before an external call that can fail, letting repeated attempts drain or lock funds. Let me check the CDO's stopEpoch/claim paths and the programmable borrower hooks.### Title
Retryable `onStopEpoch` vault-liquidity failure permanently blocks `stopEpoch` and freezes all LP funds - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
Analogous to CVE-2016-6831 (resources leaked/exhausted on every failed `execve`, so repeated failures produce a persistent denial of service), `ProgrammableBorrower.onStopEpoch` turns an external ERC4626 `vault.withdraw` failure into a *retryable* revert (`StopEpochVaultLiquidityUnavailable`) whenever the borrower's shares still economically cover the shortfall. Because the failure path never releases the epoch into the default branch, an unprivileged user of the borrower's ERC4626 vault who keeps the vault's underlying liquidity drained makes every `stopEpoch` call revert, so the epoch can never end and all tranche holders' withdraw requests remain unfunded indefinitely.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch` (contracts/IdleCDOEpochVariant.sol:395-404), when `isProgrammableBorrower` is set, the CDO calls `IProgrammableBorrower.onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)` and only takes the default path if the hook returns `false`; a revert bubbles up and aborts the whole stop.

In `onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:239-253):

```solidity
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;   // -> let transferFrom fail -> default
  try vault.withdraw(shortfall, address(this), address(this)) { ... }
  catch { revert StopEpochVaultLiquidityUnavailable(); } // -> retryable revert
}
```

The decision between "default" and "retryable revert" is based on `_currentVaultAssets()` (share-price valuation via `convertToAssets`), not on *withdrawable* liquidity (`maxWithdraw`). For lending-market ERC4626 vaults (e.g., Morpho-style), shares can be fully valuable while `withdraw` reverts because the underlying markets have no liquidity. An attacker who is a permissionless participant in that vault can borrow out / withdraw the underlying liquidity so that:

- `convertToAssets(shares) >= shortfall` (share value intact — the loans are still owed to the vault),
- `vault.withdraw(shortfall, ...)` reverts (liquidity exhausted).

Every subsequent `stopEpoch` then reverts at the hook. This is exactly the failure-path leak pattern: the failed operation is repeated, each attempt consumes the revert path, and nothing is ever released — the epoch stays `isEpochRunning`, `epochAccountingActive` stays true, `pendingWithdraws` in `IdleCreditVault` is never collected, and `epochNumber` never advances.

Because `IdleCreditVault.claimWithdrawRequest` requires `epochNumber > lastWithdrawRequest[_user]` (contracts/strategies/idle/IdleCreditVault.sol:326-328), no pending receipt can ever be claimed, and new `startEpoch` calls are gated on the epoch being stopped. The attack is maintained at the cost of interest on the borrowed liquidity, which can be rolled indefinitely; there is no protocol-side timeout that converts the retryable revert into a default.

### Impact Explanation
Temporary (potentially indefinite) freezing of all funds in the CDO: every tranche holder with a pending `requestWithdraw` receipt cannot claim, and the pool cannot transition to a new epoch, cannot default (so `_handleBorrowerDefault` / `DefaultDistributor` recovery never starts), and cannot close. The quantified exposure is the full pool NAV plus all pending withdraw receipts for the duration the attacker keeps the ERC4626 vault illiquid. The escape hatches do not help: `onDefault` is only reachable through `_handleBorrowerDefault`, which this path never reaches, and `_emergencyShutdown` requires the honest owner to intervene — the unprivileged attacker alone freezes the funds.

### Likelihood Explanation
Requires the pool to be in programmable-borrower mode with `isProgrammableBorrower = true` and an epoch running with either pending withdraws or interest to pull (i.e., `_amountRequired > onHand`). The attacker only needs to be a user of the configured external ERC4626 vault — explicitly an allowed unprivileged role. For vaults backed by lendable markets, draining liquidity is a standard borrow action with a known carry cost; no privileged collusion is needed. Likelihood is moderate: it needs a programmable deployment and a liquidity-drainable vault, but once those hold, the attack is deterministic and repeatable every time the manager retries `stopEpoch`.

### Recommendation
Base the retryable-vs-default decision on actual withdrawable liquidity rather than share valuation: compare `shortfall` against `vault.maxWithdraw(address(this))` (or call `withdraw` first and only treat genuine shortfall as default). Alternatively, bound the retry window — e.g., record a failed-stop timestamp and let a subsequent `stopEpoch` (or a permissionless fallback after a grace period) convert a persistently failing recall into `_handleBorrowerDefault` so LP funds are released through the recovery flow instead of frozen behind an always-reverting external call.
