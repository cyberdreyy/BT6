### Title
Secondary buyers of IdleCreditVault receipt tokens are scammed: claim rights stay bound to the requester, so purchased receipts are unclaimable and the funded underlyings are permanently locked - ([File: contracts/strategies/idle/IdleCreditVault.sol](https://github.com/Noahgrantyt/idle-tranches--010/blob/main/contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.requestWithdraw` and `requestInstantWithdraw` mint the strategy ERC20 to the requesting user as a withdraw "receipt" (IdleCreditVault.sol:275, 363). That receipt token is an ordinary transferable ERC20, but the *right to claim* is stored in per-user mappings (`withdrawsRequests[_user]`, `instantWithdrawsRequests[_user]`, `lastWithdrawRequest[_user]`) and `claimWithdrawRequest(_user)`/`claimInstantWithdrawRequest(_user)` can only be executed for that same `_user` by the CDO. A lender can therefore sell their receipt tokens on a secondary market, while the buyer receives tokens that can never be redeemed and the underlying stays locked in the vault forever. This is the same bug class as the Footium escrow report: a transferable wrapper is sold while the value it appears to carry does not travel with it.

### Finding Description
When a tranche holder requests a withdrawal via `IdleCDOEpochVariant.requestWithdraw`, the CDO calls `IdleCreditVault.requestWithdraw(_underlyings, msg.sender, principal)`, which burns the CDO's strategy tokens and mints the receipt amount to the user:

- `IdleCreditVault.sol:274-275`: `_burn(msg.sender, _principal); _mint(_user, _amount);`
- `IdleCreditVault.sol:292-293`: `withdrawsRequests[_user] += _amount; withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;`
- `IdleCreditVault.sol:362-366`: same mint + `instantWithdrawsRequests[_user] += _amount` for instant receipts.

Claims then burn the recorded user's *own* balance and pay the recorded mapping amounts:

- `IdleCreditVault.sol:338-349`: `amount = withdrawsRequests[_user] + apr0...; _burn(_user, normalAmount + apr0PrincipalAmount); ... _transferFundedClaim(_user, amount);`
- `IdleCreditVault.sol:387-392`: `amount = instantWithdrawsRequests[_user]; _burn(_user, amount); _transferFundedClaim(_user, amount);`

There is no `_beforeTokenTransfer` hook or transfer guard in `IdleCreditVault` that moves the mapping entries along with the tokens — claim eligibility is keyed only to the original requester address. So:

1. Attacker deposits into a tranche, calls `cdoEpoch.requestWithdraw(...)` during the buffer phase, and receives `_amount` strategy-token receipts plus a `withdrawsRequests[attacker]` entry.
2. After `stopEpoch` funds the requests (`collectWithdrawFunds` moves underlyings into the vault), the attacker lists the receipt tokens on a secondary marketplace/DEX at a small discount to their apparent claimable underlying value.
3. A buyer purchases the tokens expecting redeemable claims, exactly as the Footium buyer expected the club NFT to include its escrowed players.
4. `withdrawsRequests[buyer] == 0`, so the buyer can never claim anything. The attacker cannot claim either after selling (`_burn(attacker, amount)` reverts on insufficient balance), so the funded underlyings remain locked in `IdleCreditVault` permanently — the attacker is paid the sale price in exchange for tokens backed by nothing.

Equivalently, the seller can front-run the marketplace fill with a token transfer to a fresh address, mirroring the mempool front-run in the original report: the buyer's purchase settles against a "claim" that has already been detached from any redemption rights.

### Impact Explanation
Direct theft plus permanent freezing. The buyer loses the full purchase price for tokens whose redemption right can never be exercised, and the corresponding funded underlyings (sourced from borrower repayments at `stopEpoch` via `collectWithdrawFunds`, IdleCreditVault.sol:411-430) are stranded in the vault forever since neither buyer nor seller can satisfy both `_burn` and the mapping checks. The attack is repeatable, exactly as in the original report, damaging protocol reputation. Quantified loss = sale proceeds + permanently locked claim amount.

### Likelihood Explanation
High feasibility in any running/stopped epoch with funded pending requests: receipts are plain ERC20 balances visible to marketplaces, and no guard prevents or invalidates their transfer. Requires only that a secondary market exists for the receipt tokens and that buyers assume the token carries the claim. No privileged role misbehavior is needed; all guards (`_onlyIdleCDO`, epoch gating, KYC via `isWalletAllowed`) operate normally.

### Recommendation
Make the claim right travel with the receipt token, or make the receipt non-transferable:

- Override `_beforeTokenTransfer`/`_update` in `IdleCreditVault` to either (a) block transfers of receipt balances entirely, or (b) atomically migrate `withdrawsRequests`, `withdrawsRequestsByEpoch`, `instantWithdrawsRequests`, `apr0Users`, and `lastWithdrawRequest` bookkeeping from sender to recipient (mirroring the Footium fix of locking the escrow whenever the asset moves). Option (a) is simpler; option (b) is needed if secondary receipt liquidity is a product requirement.
- Alternatively, burn-to-claim semantics could be driven purely by token balance rather than per-user mappings, so whoever holds the receipt holds the claim.

### Proof of Concept
Foundry fork scenario (mode: fixed-APR, standard `IdleCDOEpochVariant`, epoch running):

```solidity
// 1. Attacker deposits into AA tranche during buffer, epoch starts.
uint256 minted = idleCDO.depositAA(DEPOSIT);

// 2. Buffer period: attacker requests withdrawal of the full position.
cdoEpoch.requestWithdraw(0, address(AATranche));
uint256 receipt = strategyToken.balanceOf(attacker); // minted at IdleCreditVault.sol:275
assertGt(receipt, 0);
assertEq(strategy.withdrawsRequests(attacker), receipt); // claim right recorded on attacker

// 3. Manager stops epoch; borrower repays -> collectWithdrawFunds funds receipts.
//    Underlyings now sit in IdleCreditVault earmarked for the attacker.
//    (vm.prank(manager) cdoEpoch.stopEpoch(0, 0); borrower funds sent;)

// 4. Attacker "sells" receipts: buyer sends payment, attacker transfers receipt tokens.
vm.prank(attacker);
strategyToken.transfer(buyer, receipt); // plain ERC20 transfer, no hook moves the claim

// 5. Buyer tries to redeem through the CDO — withdrawsRequests[buyer] == 0.
vm.prank(buyer);
cdoEpoch.claimWithdrawRequest(); // claims nothing; buyer holds unbacked tokens
assertEq(underlying.balanceOf(buyer), payment * 0); // buyer received no underlyings

// 6. Seller also can no longer claim: _burn(attacker, amount) reverts (balance now 0).
vm.prank(attacker);
vm.expectRevert(); // ERC20: burn amount exceeds balance
cdoEpoch.claimWithdrawRequest();

// Result: attacker keeps buyer's payment; funded underlyings are locked in the vault forever.
```

Key assertion chain: `withdrawsRequests` is keyed to the requester at `IdleCreditVault.sol:292-293`, the payout targets `_user` at `IdleCreditVault.sol:343-349`, and no transfer hook re-maps the entries — so the transferable receipt and the redemption right are detached, reproducing the "empty escrow sold to buyer" scam.
