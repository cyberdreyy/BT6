### Title
Unbounded recursive `TrieNode` decoding allows stack-overflow DoS of the fault-proof program via a single attacker-crafted preimage - ([File: crates/proof/mpt/src/node.rs])

### Summary
`TrieNode::decode` in the Base fault-proof MPT crate recursively decodes nested trie nodes with no depth limit, directly analogous to the Wireshark dissection-recursion bug in CVE-2019-12295 ("the dissection engine could crash... addressed by restricting the number of layers and consequently limiting recursion"). A dispute-game participant that supplies a preimage for a keccak256-addressed trie node can nest `Extension`/`Leaf`/`Branch` sub-structures arbitrarily deep inside a single RLP blob, because sub-32-byte children are inlined (not separately hashed/blinded) rather than referenced by a fresh oracle lookup. Decoding that single blob drives unbounded native-stack recursion in the fault-proof program.

### Finding Description
`TrieNode::decode` peeks the RLP header and, for extension nodes, calls `Self::decode` again on the inline child without any recursion-depth accounting: [1](#0-0) 

The same file's `Decodable` implementation dispatches into this recursive helper for any node whose outer RLP header declares a 2-element list: [2](#0-1) 

The reason arbitrarily deep nesting can be packed into a *single* preimage blob (rather than requiring N separate, individually-hashed preimages) is that only nodes whose RLP encoding is ≥32 bytes get "blinded" (replaced by a keccak256 commitment fetched separately); nodes below that size are embedded inline in the parent's encoding: [3](#0-2) [4](#0-3) 

This `TrieNode::decode` path is reached whenever the fault-proof program (or the ZK proof program built on the same `base-proof-mpt`/`base-proof` crates) resolves state or account/storage trie nodes fetched through the preimage oracle, e.g. in `OracleL1ChainProvider::trie_node_by_hash`: [5](#0-4) 

and in the on-disk/L2 trie providers used by the executor: [6](#0-5) 

Because the preimage oracle only validates that `keccak256(preimage) == requested_key` (it does not validate or bound the internal RLP structure), a dispute-game participant that controls the preimage for one node hash can construct a single blob containing thousands of nested inline `Extension`/`Leaf` layers (each only a few bytes of RLP overhead) that still hashes to the expected commitment as long as the outer bytes match. Passing this crafted blob through `TrieNode::decode` (invoked by `open`/`unblind` while the fault-proof program walks the state trie during block execution/derivation) drives one native stack frame per nesting layer with no depth cap, exhausting the constrained stack of the fault-proof execution environment (Cannon MIPS thread, RISC-V FPVM, or a zkVM guest such as SP1/RISC0 referenced in `crates/proof/zk`).

### Impact Explanation
A stack overflow inside the fault-proof program is a crash of the very component responsible for computing/verifying the L2 output root during a dispute. This maps to "node halt" / "wrong provable output root" impact classes: an honest challenger or defender who is forced to replay a maliciously-populated preimage during a dispute game can have their prover/FPVM instance crash instead of producing a valid output root, which can prevent timely, correct resolution of the fault dispute game and is a High severity denial-of-service on core proof infrastructure.

### Likelihood Explanation
Reachability requires only that the attacker control (or influence) the byte contents of one trie-node preimage supplied to the dispute game/preimage oracle for a hash they can produce — a standard capability of any dispute-game participant supplying preimages, no privileged access or key compromise needed. The construction (many few-byte inline `Extension` layers) is straightforward RLP crafting and requires no cryptographic forgery, only satisfying `keccak256(blob) == claimed_hash`, which is trivially satisfiable because the attacker chooses the blob and its resulting hash together. This is a realistic, low-effort trigger for anyone acting as a fault-proof participant.

### Recommendation
Add an explicit maximum recursion/nesting depth to `TrieNode::decode` (and to `try_decode_leaf_or_extension_payload`), returning a decode error once the depth exceeds the maximum plausible Merkle-Patricia-Trie depth (bounded by the fixed 64-nibble key length for Ethereum-style state/storage tries, plus a small safety margin). Alternatively, convert the decoding routine to an iterative/explicit-stack algorithm so a malicious blob cannot exhaust the native call stack regardless of nesting depth.

### Proof of Concept
Conceptually: recursively build `N` `TrieNode::Extension` values in memory where each child is the tiny previous extension node (well under the 32-byte blinding threshold, e.g. an extension whose child is `TrieNode::Empty` after the first level), RLP-encode the outermost one to a single `Vec<u8>` blob, and register that blob as the preimage for `keccak256(blob)` in a mock `TrieProvider`. Then call `TrieNode::decode(&mut blob.as_slice())` (or `TrieNode::unblind`/`open` against the mock provider) as done in the existing test harness pattern: [7](#0-6) 
With `N` in the low thousands, the process running the fault-proof program overflows its stack and crashes instead of returning a decode error, demonstrating the unbounded-recursion DoS.
