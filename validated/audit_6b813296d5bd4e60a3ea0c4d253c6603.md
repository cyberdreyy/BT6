### Title
Off-by-one in `parse_confidential_transfer_instruction` Withdraw account-offset walk causes a proof-context account to be mislabeled as `owner` - (File: transaction-status/src/parse_token/extension/confidential_transfer.rs)

### Summary
In the `ConfidentialTransferInstruction::Withdraw` arm, the boundary guard `offset < account_indexes.len().saturating_sub(1)` is checked independently for each of the two optional context-account insertions (`equalityProofContextStateAccount`, `rangeProofContextStateAccount`), reserving only one slot for `parse_signers`. When both `equality_proof_instruction_offset` and `range_proof_instruction_offset` are `0` (i.e. both proofs are provided via context-state accounts, requiring 5 accounts total) but the attacker supplies only 4 `account_indexes`, the second context-account field is silently dropped and `parse_signers` mislabels the actual `rangeProofContextStateAccount` pubkey as the `owner`.

### Finding Description
The relevant code is: [1](#0-0) 

`offset` starts at 2. With `equality_proof_instruction_offset == 0` and `range_proof_instruction_offset == 0`, `has_sysvar` is `false`, so the sysvar branch is skipped. If `account_indexes.len() == 4` (the minimum enforced by `check_num_token_accounts(account_indexes, 4)` at line 178), then:
- Equality branch: `offset(2) < len.saturating_sub(1)(3)` → true → inserts `equalityProofContextStateAccount` at index 2, `offset` becomes 3.
- Range branch: `offset(3) < 3` → false → **skipped**, `rangeProofContextStateAccount` is never inserted even though `range_proof_instruction_offset == 0` indicates it should be present.
- `parse_signers(map, offset=3, ...)` is then called: since `account_indexes.len() (4) > last_nonsigner_index+1 (4)` is false, it takes the else branch and labels `account_keys[account_indexes[3]]` as `"owner"`.

Per the SPL Token-2022 interface, when both proofs use `ContextStateAccount` (offset 0/0), the real account layout is `[account, mint, equality_ctx, range_ctx, authority]` (5 accounts) — index 3 is the `rangeProofContextStateAccount`, not the authority. Because the parser only enforces a minimum of 4 accounts via `check_num_token_accounts`, and does not verify that the account count matches what the specific offset combination actually requires, an attacker can submit a Withdraw instruction with exactly 4 accounts and offsets `(0,0)`, causing the parser to mislabel the `rangeProofContextStateAccount` as `owner` in the `jsonParsed` output.

`check_num_token_accounts` only checks a minimum count, not the exact count implied by the offset fields: [2](#0-1) [3](#0-2) 

The transaction need not succeed on-chain for this to be exploitable — a transaction can be included in a block and fail execution (e.g., due to a missing/incorrect authority account for the token program's own checks), yet it is still retrievable via `getTransaction` with `encoding=jsonParsed`, which reaches this code path via `parse_token` → `parse_confidential_transfer_instruction`.

The existing unit tests in this file only construct instructions via the legitimate `inner_withdraw` SPL builder, which always emits the account count matching the chosen offsets, so this account-count/offset mismatch path is never exercised by current tests.

### Impact Explanation
This is a decoder misreporting bug in the `jsonParsed` transaction-status decoding path (transaction-status crate), not a consensus or execution-path bug. A client relying on the parsed `owner` field of a `withdrawConfidentialTransfer` instruction (e.g., a block explorer, wallet, or compliance/monitoring tool) can be shown an incorrect account as the withdrawal authority/owner, while the real `rangeProofContextStateAccount` is omitted from the output. This falls under "wrong ... data returned" by RPC decoding logic.

### Likelihood Explanation
Fully attacker-controlled and requires no privileges: the attacker crafts and submits a single Withdraw confidential-transfer instruction with `equality_proof_instruction_offset = 0`, `range_proof_instruction_offset = 0`, and exactly 4 accounts (omitting the range-proof context account slot), then reads it back via a single `getTransaction(..., {encoding: "jsonParsed"})` call. No fork, staking, or leader control needed; the transaction only needs to land on-chain (it can fail execution and still be queryable).

### Recommendation
Compute the exact expected account count from the decoded offset fields before doing the offset walk (mirroring the SPL Token-2022 interface's own account-layout logic), and validate `account_indexes.len()` against that exact count (not just a floor of 4) before inserting fields, similarly reserving room for `parse_signers`'s multisig tail in all branches consistently, or track remaining required slots explicitly instead of a single shared `saturating_sub(1)` bound applied to each conditional insertion independently.

```rust
// transaction-status/src/parse_token/extension/confidential_transfer.rs (test module)
#[test]
fn test_withdraw_short_accounts_mislabels_range_ctx_as_owner() {
    let account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let equality_ctx = Pubkey::new_unique();
    let range_ctx_actually_used_as_owner = Pubkey::new_unique();

    // Craft raw instruction data: Withdraw discriminant + WithdrawInstructionData
    // with equality_proof_instruction_offset = 0, range_proof_instruction_offset = 0.
    let withdraw_data = WithdrawInstructionData {
        amount: 42.into(),
        decimals: 9,
        new_decryptable_available_balance: PodAeCiphertext::default(),
        equality_proof_instruction_offset: 0,
        range_proof_instruction_offset: 0,
    };
    let mut data = vec![/* ConfidentialTransferExtension */ 27, /* Withdraw */ 3];
    data.extend_from_slice(bytemuck::bytes_of(&withdraw_data));

    // Only 4 accounts, even though offsets (0,0) require 5 per the SPL spec
    // (account, mint, equality_ctx, range_ctx, authority).
    let account_keys = vec![account, mint, equality_ctx, range_ctx_actually_used_as_owner];
    let account_indexes: Vec<u8> = vec![0, 1, 2, 3];

    let parsed = parse_confidential_transfer_instruction(
        &data[1..],
        &account_indexes,
        &AccountKeys::new(&account_keys, None),
    )
    .unwrap();

    // BUG: rangeProofContextStateAccount is missing entirely...
    assert!(parsed.info.get("rangeProofContextStateAccount").is_none());
    // ...and the actual range-proof context account is mislabeled as "owner".
    assert_eq!(
        parsed.info["owner"],
        json!(range_ctx_actually_used_as_owner.to_string())
    );
}
```
Expected result on the current code: both assertions pass, confirming the misattribution (a correct implementation should either reject this account layout or correctly report `rangeProofContextStateAccount` and fail to find a valid `owner`/error out instead of silently mislabeling).

```rust
fn parse_signers(
    map: &mut Map<String, Value>,
    last_nonsigner_index: usize,
    account_keys: &AccountKeys,
    accounts: &[u8],
    owner_field_name: &str,
    multisig_field_name: &str,
) {
    if accounts.len() > last_nonsigner_index + 1 {
        let mut signers: Vec<String> = vec![];
        for i in accounts[last_nonsigner_index + 1..].iter() {
            signers.push(account_keys[*i as usize].to_string());
        }
        map.insert(
            multisig_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
        map.insert("signers".to_string(), json!(signers));
    } else {
        map.insert(
            owner_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
    }
}
```
