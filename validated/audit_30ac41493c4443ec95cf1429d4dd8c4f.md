### Title
Global RequestCache lacks per-sender quota, allowing one low-privilege sender to exhaust `maxCacheSize` and deny service to other tenants - ([File: core/services/gateway/handlers/common/requestcache.go])

### Summary
`requestCache.NewRequest` enforces only a single global size bound (`len(c.cache) >= int(c.maxCacheSize)`) shared across all senders keyed by `globalId{sender, id}`, with no per-sender/per-tenant limit. Any single sender able to submit enough distinct `(sender, id)` pairs before their timeout expires can fill the shared cache and cause `NewRequest` to return `"request cache is full"` for all other senders using the same handler instance.

### Finding Description
`NewRequest` at [1](#0-0)  computes `key := globalId{request.Body.Sender, request.Body.MessageId}` and checks capacity against the entire cache's total size (`len(c.cache) >= int(c.maxCacheSize)`), not against any per-sender count. The `globalId` struct [2](#0-1)  only distinguishes entries, it does not enforce isolation of capacity between senders. As long as an attacker can generate `maxCacheSize` distinct `MessageId` values under their own sender identity and get them accepted into the cache before their timeouts elapse, every subsequent `NewRequest` call — from any sender — will hit the `len(c.cache) >= int(c.maxCacheSize)` branch and be rejected with `"request cache is full"` until entries expire via `c.timeout`.

Whether this is practically exploitable depends on upstream request-admission checks (authentication, rate limiting, allowlisting) performed by whichever handler constructs and calls into a given `requestCache` instance before invoking `NewRequest`. I was unable to fully confirm all call sites in this codebase — searches located `RequestCache` usage only in `core/services/gateway/handlers/capabilities/v2/http_handler.go` and `requestcache_test.go`, and I was not able to conclusively verify whether http_handler.go applies per-sender rate limiting or quota checks prior to calling `NewRequest` (or whether it uses this generic cache at all in the production message-handling path) within the available tool budget. Other gateway handlers examined (e.g. `confidentialrelay/handler.go`, `vault/handler.go`) implement their own separate `activeRequests` maps rather than this shared `RequestCache`, and those also lack visible per-sender caps in the code reviewed.

### Impact Explanation
If a handler instantiates a single shared `RequestCache` and calls `NewRequest` without an independent per-sender/per-tenant admission control (rate limit or quota) in front of it, then any credentialed sender — including a low-privilege one — can deny the run/callback service to all other tenants sharing that handler instance by filling the cache with their own pending requests. This matches a Denial-of-Service impact class (node-wide degradation of pipeline-run/transfer callback processing for other users), scoped to the gateway handler process.

### Likelihood Explanation
Exploitability is conditional and not confirmed as reachable within the code paths verified: it requires (a) a handler that uses this shared generic `RequestCache` without additional per-sender request-rate limiting ahead of `NewRequest`, and (b) the attacker being able to submit `maxCacheSize` distinct message IDs within the cache's `timeout` window. I could not verify from the available index whether the actual production caller of this cache applies such a per-sender guard beforehand, so I cannot confirm the precondition is unmet in the live code path.

### Recommendation
Add a per-sender (or per-tenant) entry limit inside `requestCache`, independent of the global `maxCacheSize`, e.g. maintain a `map[sender]int` count and reject/evict when an individual sender exceeds their allotted share, or partition the cache by sender with a fair-share algorithm. Alternatively/additionally, ensure every caller of `NewRequest` enforces a per-sender rate limiter (as already done for other handlers, e.g. `httpTriggerHandler.checkRateLimit` via `userRateLimiter.AllowErr` at [3](#0-2) ) before requests reach this shared cache.

### Proof of Concept
Table-driven Go test in `core/services/gateway/handlers/common/requestcache_test.go`:
1. Create `cache := common.NewRequestCache[requestState](time.Hour, maxCacheSize)` with a small `maxCacheSize` (e.g. 2, as in existing `TestRequestCache_MaxSize` at [4](#0-3) ).
2. Loop `maxCacheSize` times, calling `cache.NewRequest(lggr, req, callback, initialState)` with a fixed `Sender: "attacker"` and unique `MessageId` values each iteration — assert all succeed.
3. Attempt `cache.NewRequest(lggr, req, callback, initialState)` with a different `Sender: "victim"` and a fresh `MessageId` — assert the call fails with `"request cache is full"`, demonstrating that the victim's legitimate, unrelated request is blocked solely due to the attacker's fill of the shared cache.
4. Expected assertion: this call should ideally succeed (isolation preserved) but currently fails, confirming the missing per-sender isolation invariant.
