### Title
Stale per-epoch instant-withdraw basis underflows `instantWithdrawsRequests`, permanently freezing a user's defaulted-epoch instant claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` resets the aggregate `instantWithdrawsRequests[_user]` to 0 but never clears the per-epoch map `instantWithdrawsRequestsByEpoch[_user][epoch]`. If a user claims a funded instant receipt and then opens a new instant withdraw request within the same strategy epoch, the stale basis is double-counted in `instantWithdrawsRequestsByEpoch`. If the borrower defaults at that epoch's `stopEpoch` and `finalizeDefault` sets `defaultRecoveryEpoch` to that epoch, `_claimDefaultedInstantWithdrawRequest` subtracts the inflated `claimBasis` from the smaller live aggregate, reverting with an arithmetic underflow on every subsequent `claimInstantWithdrawRequest` call. This is the on-chain analog of CVE-2025-23166: a user-controlled input sequence poisons shared state so that a later trusted path (default-recovery claim) crashes deterministically.

### Finding Description
- `requestInstantWithdraw` increments both `instantWithdrawsRequests[_user]` and `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` [1](#0-0) .
- `claimInstantWithdrawRequest` burns and zeroes only the aggregate; `instantWithdrawsRequestsByEpoch` is left untouched [2](#0-1) .
- After `finalizeDefault`, `_claimDefaultedInstantWithdrawRequest` reads `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and executes `instantWithdrawsRequests[_user] -= claimBasis`, which underflows whenever the stale per-epoch basis exceeds the live aggregate [3](#0-2) .

Sequence (single epoch `N`, APR decreased so `_isInstantWithdrawEnabled()` routes `requestWithdraw` to `requestInstantWithdraw`):
1. User calls `cdoEpoch.requestWithdraw(x, AA)` → instant receipt `x` recorded at epoch `N` in both counters.
2. Manager calls `getInstantWithdrawFunds` → `allowInstantWithdraw = true`; user calls `claimInstantWithdrawRequest` → paid `x`, `instantWithdrawsRequests[user] = 0`, but `instantWithdrawsRequestsByEpoch[user][N] = x` remains.
3. User calls `requestWithdraw(y, AA)` again in the same epoch → `instantWithdrawsRequests[user] = y`, `instantWithdrawsRequestsByEpoch[user][N] = x + y`.
4. Borrower fails to repay at `stopEpoch` → `_handleBorrowerDefault`; manager calls `finalizeDefault` → `defaultRecoveryEpoch = N`.
5. User calls `claimInstantWithdrawRequest` → `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = x + y` and executes `instantWithdrawsRequests[user] -= (x + y)` where the aggregate is only `y` → panic underflow. Every retry reverts identically.

The same stale-basis pattern exists for normal receipts: `_claimFundedWithdrawRequest` zeroes `withdrawsRequests[_user]` and `lastWithdrawRequest[_user]` without clearing `withdrawsRequestsByEpoch[_user][epoch]` [4](#0-3) , so `_clearWithdrawClaimForEpoch` can hit `withdrawsRequests[_user] -= normalAmount` underflow on a defaulted-epoch claim after a same-epoch claim-and-re-request [5](#0-4) .

### Impact Explanation
Permanent freezing of unclaimed yield/principal: the user's defaulted-epoch instant receipt (and any other funded receipt paid through the same `claimInstantWithdrawRequest`/`claimWithdrawRequest` path) can never be recovered because the claim function reverts before reaching `_transferFundedClaim`/`_transferDefaultRecovery`. The loss equals the full value `y` of the live receipt plus any recovery-priced amount owed. No privileged misbehavior is required — only an honest borrower default finalization.

### Likelihood Explanation
Requires: instant withdraws enabled with an APR drop (triggering `_isInstantWithdrawEnabled`), the user claiming and re-requesting inside one strategy epoch, and a borrower default finalized on that epoch. APR decreases and defaults are normal protocol events; the trigger is fully in the attacker's control except the default, which is the scenario this codepath exists to serve.

### Recommendation
In `claimInstantWithdrawRequest` and `_claimFundedWithdrawRequest`, delete the per-epoch accounting entries (`instantWithdrawsRequestsByEpoch[_user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]`, `withdrawsRequestsByEpoch[_user][epoch]`) when clearing the aggregate, or make `_claimDefaultedInstantWithdrawRequest`/`_clearWithdrawClaimForEpoch` cap `claimBasis`/`normalAmount` at the live aggregate instead of subtracting unconditionally.

function testStaleInstantEpochBasisUnderflowsOnDefaultClaim() external {
    uint256 amount = 10000 * ONE_SCALE;
    idleCDO.depositAA(amount);

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // drop APR so requestWithdraw routes to requestInstantWithdraw (epochNumber = N)
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);
    uint256 x = cdoEpoch.requestWithdraw(mintedAA / 4, address(AAtranche));

    // epoch N runs; manager funds instant withdrawals
    _startEpochAndCheckPrices(1); // epochNumber incremented; use same N where applicable
    _getInstantFunds();
    cdoEpoch.claimInstantWithdrawRequest(); // aggregate cleared, by-epoch[N] stale

    uint256 y = cdoEpoch.requestWithdraw(mintedAA / 4, address(AAtranche)); // by-epoch[N] = x + y

    // borrower defaults at stopEpoch; manager finalizes recovery
    _stopEpochAndCheckPrices(1, initialProvidedApr, 0);
    _checkDefault();
    // ... finalizeDefault(recovered, manager) ...

    vm.expectRevert(); // arithmetic underflow: instantWithdrawsRequests -= (x + y)
    cdoEpoch.claimInstantWithdrawRequest();
}

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
