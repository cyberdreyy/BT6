### Title
Loss-adjusted withdraw receipts can be claimed at par by placing a second withdraw request in a later epoch — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.claimWithdrawRequest` routes a user's claim through `_claimLossAdjustedWithdrawRequest` using **only** `lastWithdrawRequest[_user]` as the epoch key for `lossRecoveryPriceByEpoch`. A user who makes a new withdraw request in any later epoch overwrites `lastWithdrawRequest`, permanently skipping the haircut path. The un-cleared receipt basis remains in `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][lossEpoch]`, so `_claimFundedWithdrawRequest` pays it at par, while `collectWithdrawFunds` only funded the reduced (post-loss) amount. This is the credit-vault analog of the signal-handler race in ALPINE-CVE-2024-6387: a subsequent request "re-arms" the stale state marker, letting a defaulted/loss-adjusted receipt be handled in an unsafe (unhaircutted) context.

### Finding Description
When `stopEpochWithDuration(..., _lossAmount)` runs, `previewLossAdjustedWithdrawFunds` assigns part of the loss to pending receipts and `collectWithdrawFunds` clears `pendingWithdraws`, funding only `_amount < pendingBasis` and storing `lossRecoveryPriceByEpoch[epoch]` (IdleCreditVault.sol:411-420). Users are then expected to redeem that epoch's receipts through `_claimLossAdjustedWithdrawRequest`, which applies `claimBasis * lossRecoveryPrice / RECOVERY_FULL` (IdleCreditVault.sol:789-800).

The lookup uses `uint256 lossEpoch = lastWithdrawRequest[_user]` (IdleCreditVault.sol:790). `requestWithdraw` sets `lastWithdrawRequest[_user] = currentEpoch` on every request (IdleCreditVault.sol:282). So:

1. Epoch N: attacker calls `requestWithdraw` → receipt basis `B` recorded in `withdrawsRequestsByEpoch[attacker][N]` and `withdrawsRequests[attacker]`, `lastWithdrawRequest = N`.
2. `stopEpochWithDuration` applies a loss: strategy funds `r * B` (r < 1), stores `lossRecoveryPriceByEpoch[N] = r`, `pendingWithdraws = 0`.
3. Epoch N+1 (buffer period, `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are re-enabled in `_stopEpoch`, IdleCDOEpochVariant.sol:481-482): attacker calls `requestWithdraw` again with any amount (or full balance). `lastWithdrawRequest` is overwritten to N+1; `withdrawsRequests[attacker]` now holds `B + B'`, and crucially `withdrawsRequestsByEpoch[attacker][N]` still holds `B` — `_clearWithdrawClaimForEpoch` is never invoked for epoch N.
4. After epoch N+1 ends (`epochNumber > N+1`), attacker calls `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = N+1`, `lossRecoveryPriceByEpoch[N+1] == 0` → returns 0 without clearing epoch-N basis (IdleCreditVault.sol:791-792).
   - `_claimFundedWithdrawRequest` pays `withdrawsRequests[attacker] = B + B'` **at par** via `_transferFundedClaim` (IdleCreditVault.sol:338-349).

The strategy only ever received `r*B` for the epoch-N receipts. The `(1 - r) * B` shortfall is paid from strategy underlyings that fund other users' claims, other funded receipts, or the `defaultRecoveryReserve`.

### Impact Explanation
Direct theft / insolvency: an unprivileged tranche holder (or queue user, since the queue calls the same `claimWithdrawRequest`) escapes the pro-rata loss haircut assigned by `stopEpochWithDuration`. The attacker recovers `B` instead of `r*B`; the excess `(1-r)*B` is drained from the strategy's funded-claim pool, so later legitimate claimants' transfers revert or are underpaid — a loss-socialization/waterfall break ("one receipt, one payout" and loss-adjustment invariants violated). Loss scales with the size of the loss-adjusted epoch's receipts and can be repeated across multiple loss epochs, since `lossRecoveryPriceByEpoch` entries for older epochs become unreachable once `lastWithdrawRequest` moves past them.

### Likelihood Explanation
- Attacker requirements: hold tranche tokens, pass `isWalletAllowed` KYC, place two `requestWithdraw` calls in different epochs — all normal user actions, no privileged role needed.
- Precondition: an epoch ended via `stopEpochWithDuration` with `_lossAmount > 0` that hits pending receipts, i.e. `lossRecoveryPriceByEpoch[N]` set < `RECOVERY_FULL`. This is a supported manager flow (per the NatSpec at IdleCDOEpochVariant.sol:510-519), not an exotic state.
- No existing guard blocks it: `requestWithdraw` does not check for an outstanding haircutted receipt; `_claimLossAdjustedWithdrawRequest` does not scan other epochs; nothing prevents `lastWithdrawRequest` from being overwritten while a loss-adjusted epoch claim is pending.
- Note: the strategy is written deliberately to distinguish per-epoch receipts (`withdrawsRequestsByEpoch`, `_clearWithdrawClaimForEpoch`), so the single-epoch-key lookup is an accounting hole rather than intended behavior. Confidence: high that the accounting path is wrong; the PoC below still needs fork-run confirmation of the exact funding balances at claim time.

### Recommendation
- In `claimWithdrawRequest`, iterate (or track) all epochs with non-zero `lossRecoveryPriceByEpoch` for which the user has an outstanding `withdrawsRequestsByEpoch`/`apr0Users` basis, instead of keying only on `lastWithdrawRequest[_user]`. E.g., store the earliest unsettled loss epoch per user, or check `withdrawsRequestsByEpoch[_user][e]` for each loss epoch.
- Alternatively, revert `requestWithdraw` when the user has an unclaimed receipt in an epoch with `lossRecoveryPriceByEpoch != 0`, forcing the haircutted claim to clear before re-requesting.
- Add a regression test: loss-adjusted epoch N → second request in N+1 → claim; assert payout equals `r*B + B'` and that remaining claimants are fully funded.

### Proof of Concept
```solidity
// Foundry fork test sketch (extend test/foundry/IdleCreditVault.t.sol helpers)
function testLossAdjustedReceiptClaimedAtPar() external {
    // Setup: attacker + victim deposit AA, run epoch 0
    uint256 amount = 100_000 * ONE_SCALE;
    _depositWithUser(attacker, amount, true);
    _depositWithUser(victim,   amount, true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Epoch 1 (buffer): both request withdraw
    vm.prank(attacker); uint256 reqA = cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.prank(victim);   uint256 reqV = cdoEpoch.requestWithdraw(0, address(BBtranche));

    // stopEpochWithDuration applies a loss that haircuts pending receipts
    // -> strategy.collectWithdrawFunds(r * pendingBasis), lossRecoveryPriceByEpoch[1] = r < 1e18
    _startEpochAndCheckPrices(1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(newApr, interest, duration, lossAmount);

    // Epoch 2 buffer: attacker requests again -> lastWithdrawRequest[attacker] = 2,
    // withdrawsRequestsByEpoch[attacker][1] untouched (still = reqA basis)
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(smallAmount, address(AAtranche));

    // Run epoch 2 to completion so the funded-claim gate epochNumber > lastWithdrawRequest passes
    _startEpochAndCheckPrices(2);
    _stopEpochAndCheckPrices(2, newApr, _expectedFundsEndEpoch());

    IdleCreditVault strat = IdleCreditVault(address(strategy));
    uint256 stratBal = defaultUnderlying.balanceOf(address(strat));

    // Attacker claims: loss path skipped (lossRecoveryPriceByEpoch[2] == 0),
    // funded path pays withdrawsRequests[attacker] at par => reqA at FULL value
    uint256 balPre = defaultUnderlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = defaultUnderlying.balanceOf(attacker) - balPre;

    // Attacker received more than r * reqA (the haircutted entitlement for epoch 1)
    uint256 r = strat.lossRecoveryPriceByEpoch(1);
    assertGt(got, reqA * r / 1e18, 'loss haircut bypassed');

    // Victim's claim now underfunded / reverts: insolvency in the funded-claim pool
    vm.prank(victim);
    vm.expectRevert(); // or assertLt(victimGot, expected)
    cdoEpoch.claimWithdrawRequest();
}
```
