### Title
Dust APR0 withdraw request permanently bricks `stopEpoch` once APR is raised above zero, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`prepareStopEpochWithApr0` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0` [1](#0-0) . Any KYC'd lender can leave a 1-wei APR0 withdraw receipt open; once the protocol sets a nonzero APR for a subsequent epoch, every `stopEpoch` call reverts, so the epoch can never close and all pool funds (borrower repayment plus pending withdraw reserves) are frozen.

### Finding Description
When the vault's `unscaledApr == 0`, `requestWithdraw` routes the receipt into the APR0 bucket instead of `withdrawsRequests`, incrementing the global `apr0TotalPrincipal` by the (possibly dust) amount [2](#0-1) . `_requestWithdrawApr0` adds `_amount` to `apr0TotalPrincipal` with no minimum-size check [3](#0-2) , and the `_amount == 0` early return at line 246 only blocks a literal zero, not 1 wei [4](#0-3) .

At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which first checks `apr0TotalPrincipal != 0` and then unconditionally reverts if `unscaledApr != 0` [5](#0-4) . The guard intends to prevent APR0 receipts from accruing under a nonzero APR, but because it reverts instead of settling or clearing the bucket, the entire epoch state machine wedges: `stopEpoch` cannot complete while the dust bucket exists and APR is nonzero.

`apr0TotalPrincipal` is only zeroed inside `prepareStopEpochWithApr0` itself (line 540) — which is unreachable while it reverts — or inside `_clearWithdrawClaimForEpoch` when the APR0 claim is cleared, which requires the epoch to have ended and is itself only reachable via `claimWithdrawRequest` paths that don't clear an *unsettled* APR0 bucket (the `_settleApr0` early-return keeps `principalEpoch` set while `_reqEpoch >= epochNumber`) [6](#0-5) . So the attacker alone cannot unbrick it, and neither can users.

### Impact Explanation
Permanent freezing of funds (or at minimum freezing for the entire duration the vault runs at nonzero APR). With a 1-wei receipt, every subsequent `stopEpoch` reverts while `unscaledApr != 0`, so:
- borrower repayments collected at epoch end cannot be pulled and distributed,
- all pending withdraw receipts (`pendingWithdraws`, instant queue) can never be funded,
- `startEpoch`/deposit flows that depend on the epoch boundary are blocked.

The attacker cost is one dust `requestWithdraw` (1 wei of underlying). The frozen value is the full pool TVL plus `pendingWithdraws`. Recovery requires the honest manager to call `setAprs(0, 0)` to bring `unscaledApr` back to zero so a `stopEpoch` can pass — but that forces the pool to run a whole epoch at zero interest and only un-bricks the vault if the attacker does not repeat the dust request in the intervening APR0 window, which they can do again for another 1 wei, indefinitely.

### Likelihood Explanation
Requirements: the attacker is a KYC-passing lender holding tranche tokens (explicitly in-scope); the vault must go through a phase where `unscaledApr == 0` (a supported configuration — `setAprs(0,0)` is exercised in tests and the APR0 flow is a first-class mode [7](#0-6) ); APR is later raised — a routine manager/CDO action. No privileged misbehavior, timing edge, or large capital is needed; the attack is a single cheap transaction and is re-armable. Likelihood is bounded by pools that actually use the APR0 mode, but where it is used the grief is reliable.

### Recommendation
Do not couple liveness of `stopEpoch` to the APR0 bucket. Concretely, in `prepareStopEpochWithApr0`, when `unscaledApr != 0` and `apr0TotalPrincipal != 0`, settle the APR0 bucket at zero interest (set `apr0RateByEpoch[epochNumber] = 0` and `apr0TotalPrincipal = 0`) rather than reverting, letting `_settleApr0` pay out principal-only claims afterward. Alternatively enforce a minimum receipt size in `_requestWithdrawApr0` so a dust bucket cannot be created — though the revert-based guard should still be removed since a nonzero-but-legitimate bucket would brick the vault identically.

### Proof of Concept
Foundry fork PoC sketch (against the repo's existing `IdleCreditVault.t.sol` harness):

```solidity
function testApr0DustRequestBricksStopEpoch() external {
    // configure APR0 mode
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    // attacker: KYC'd lender deposits dust and requests withdraw while apr == 0
    address attacker = makeAddr('apr0Griefer');
    _depositWithUser(attacker, 1, true); // 1 wei deposit
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // apr0 bucket += ~1 wei
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // honest manager raises APR for the next epoch (normal ops)
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(initialProvidedApr, initialProvidedApr);

    // run epoch and try to stop it: every stopEpoch now reverts
    _startEpochAndCheckPrices(0);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // pending withdraws of other users are unfunded and unclaimable;
    // attacker can repeat the dust request each time APR returns to 0.
}
```

Uncertainty note: I verified the revert condition and the APR0 accounting path in `IdleCreditVault.sol`, but was not able to read `IdleCDOEpochVariant.stopEpoch` in this session to confirm the exact call ordering into `prepareStopEpochWithApr0` and whether any alternate epoch-close path (e.g., default handling or emergency shutdown) bypasses the revert. If a bypass exists, the impact degrades to temporary freezing rather than permanent; the PoC above settles this directly.

  function _settleApr0(address _user) internal {
    Apr0UserData storage _apr0User = apr0Users[_user];
    uint256 _principal = _apr0User.principal;
    if (_principal == 0) {
      return;
    }
    uint256 _reqEpoch = _apr0User.principalEpoch;
    // Settle only after stopEpoch bumped epochNumber (ie after one full wait epoch).
    if (_reqEpoch >= epochNumber) {
      return;
    }
    // Move principal from "open APR0 bucket" to "settled bucket" (same principal, not duplicated).
    _apr0User.settledPrincipal += _principal;
    uint256 _rate = apr0RateByEpoch[_reqEpoch];
    if (_rate != 0) {
      // Convert per-epoch rate to claimable underlying interest.
      _apr0User.settledInterest += (_principal * _rate) / 1e18;
    }
    _apr0User.principal = 0;
    _apr0User.principalEpoch = 0;
  }

  function _requestWithdrawApr0(uint256 _amount, address _user) internal {
    // Settle any previous APR0 request first, then start/update current epoch bucket.
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    if (_apr0User.principal == 0) {
      _apr0User.principalEpoch = epochNumber;
    }
    _apr0User.principal += _amount;
