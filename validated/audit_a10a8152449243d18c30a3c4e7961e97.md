### Title
Client-controlled authentication-mode selection in Vault gateway request authorization - (File: core/capabilities/vault/authorizer.go)

### Summary
The `authorizer.authorizeRequest` function in the Vault gateway node-side authorization path merges two structurally different authentication mechanisms — allowlist-based (on-chain digest allowlisting) and JWT-based (Auth0-issued bearer token) — into a single dispatch function whose branch is selected purely by a field (`req.Auth`) that originates from the untrusted client request itself.

### Finding Description
`authorizeRequest` decides which authorization mechanism validates an incoming Vault gateway request solely based on whether the caller-supplied `req.Auth` string is empty: [1](#0-0) 

This is architecturally the same pattern as the report's bug class: one function silently changes its entire security behavior depending on an argument supplied by the caller, rather than exposing two independent, purpose-specific entry points. The two branches (`authorizeAllowListBasedAuth` and `authorizeJWTBasedAuth`) wrap fundamentally different trust models — one relies on an on-chain workflow-registry allowlist digest match [2](#0-1) , the other relies on validating a signed JWT and its claims [3](#0-2) . Both feed into a single downstream `AuthResult` that is then used uniformly for replay protection and owner binding: [4](#0-3) .

Because the mode selector (`req.Auth == ""`) is part of the same message the client submits through the internet-facing gateway (`GatewayHandler.HandleGatewayMessage` / `GatewayVaultRequestProcessor`), an unprivileged submitter effectively chooses which of the two independently-implemented, independently-maintained authorization code paths will validate their own request. This is precisely the "convoluted implementation" pattern flagged in the reference report: exercising two very different features (allowlist authorization vs. JWT authorization) through one function based on which arguments are populated increases the chance that one path is inadvertently weaker, incompletely validated, or diverges in enforced invariants (e.g., tenant/org claim checks, owner binding, expiry semantics) from the other, since both must be reasoned about together instead of being enforced by a single, uniform mechanism.

### Impact Explanation
If the two branches diverge in strictness (e.g., a future change tightens JWT validation but leaves the legacy allowlist path with weaker invariants, or vice versa), a client can deliberately omit `req.Auth` to fall back to the "backwards compatibility" allowlist branch and dodge the newer JWT-based validation/claims, or attempt to trigger the other path to exploit an inconsistency. This falls into the "authentication method downgrade / mode confusion" category rather than a simple readability issue, because unprivileged Vault gateway clients directly control the discriminator field.

### Likelihood Explanation
Exploitability depends entirely on whether the two authorization implementations are kept in perfect lockstep for every current and future invariant (owner binding, replay protection, expiry, org/tenant scoping). The codebase currently attempts to unify post-authorization checks (owner-match, replay guard) at the `AuthorizeRequest` wrapper level [5](#0-4) , which mitigates but does not eliminate the risk, since pre-authorization decisions (e.g., what counts as a valid allowlisted vs. valid JWT request) are made independently in each branch. I could not find a concrete, currently-exploitable divergence between the two paths in the available code (e.g., both call into distinct authorizer implementations with their own internal invariants that appeared self-consistent in the code reviewed) — this is a structural/architectural risk (mode confusion via caller-controlled dispatch) rather than a demonstrated bypass with a working exploit chain in the code as read.

### Recommendation
Split the dispatch into two explicit, independently-invoked authorization entry points (e.g., `AuthorizeAllowListRequest` and `AuthorizeJWTRequest`) that are selected by the caller of the gateway handler based on transport-level context (e.g., which endpoint/connector delivered the request) rather than by a client-controlled field embedded in the message itself. If both mechanisms must coexist on the same endpoint, enforce a strict, centrally-owned invariant table validated by shared test suites so that both paths are provably equivalent in what they guarantee (replay protection, owner binding, expiry, tenant scoping) — do not rely on branch code alone. Additionally, log/alert when the "legacy" (`req.Auth == ""`) fallback path is used, so any unexpected reliance on the weaker/older path is detectable in production.

### Proof of Concept
Not constructed — no concrete divergence between `authorizeAllowListBasedAuth` and `authorizeJWTBasedAuth` was located in the reviewed code that would currently allow a bypass; the finding documents the mode-confusion structural risk (client-controlled security-mechanism selection) rather than a demonstrated working exploit.

func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}

	return authResult, nil
}

func (a *authorizer) authorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	// Requests without req.Auth continue using the allowlist-based path for backwards compatibility.
	// Existing clients do not populate the auth field yet, so treating an empty value as JWT would break them.
	if req.Auth == "" {
		return a.authorizeAllowListBasedAuth(ctx, req)
	}
	return a.authorizeJWTBasedAuth(ctx, req)
}

// AuthorizeRequest authorizes a request using AllowListBasedAuth.
// It does NOT check if the request method is allowed.
func (r *allowListBasedAuth) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	r.lggr.Debugw("AllowListBasedAuth authorizing request", "method", req.Method, "requestID", req.ID)
	requestDigest, err := req.Digest()
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to create digest", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, err
	}
	requestDigestBytes, err := hex.DecodeString(requestDigest)
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to decode digest", "method", req.Method, "requestID", req.ID, "requestDigest", requestDigest, "error", err)
		return nil, err
	}
	requestDigestBytes32 := [32]byte(requestDigestBytes)
	if r.workflowRegistrySyncer == nil {
		r.lggr.Errorw("AllowListBasedAuth workflowRegistrySyncer is nil", "method", req.Method, "requestID", req.ID)
		return nil, errors.New("internal error: workflowRegistrySyncer is nil")
	}
	allowlistedRequest, allowedRequestsStrs, err := r.findAllowlistedItemWithRetry(ctx, req, requestDigest, requestDigestBytes32)
	if err != nil {
		return nil, err
	}
	if allowlistedRequest == nil {
		r.lggr.Debugw("AllowListBasedAuth request digest not allowlisted",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"allowedRequestsStrs", allowedRequestsStrs)
		return nil, errors.New("request not allowlisted")
	}
