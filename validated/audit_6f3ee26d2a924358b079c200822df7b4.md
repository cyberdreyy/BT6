### Title
Symlink target validation gap in tar+zstd extractor allows path escape via pre-positioned symlink across sequential extractions into the same working directory - (File: commands/helpers/archive/tarzstd/tarzstd_extractor.go)

### Summary
`Extract` validates only the *placement path* of each tar entry against `e.dir` using a lexical `strings.HasPrefix` check; it never validates or resolves `hdr.Linkname` for symlink entries, nor does it detect pre-existing symlinks already present on disk when computing paths for later entries. Because `cache-extractor` (and other archive-extraction call sites) can be invoked repeatedly into the same working directory (`wd`) across job/pipeline stages, a symlink written to disk by one extraction can be silently traversed by a later, unrelated extraction, causing writes to land outside `e.dir`.

### Finding Description
The containment check at [1](#0-0)  only verifies that the *string* form of the target path begins with `e.dir`; it never calls `os.Lstat`/`filepath.EvalSymlinks` on intermediate path components, and it never inspects `hdr.Linkname` at all. Symlink entries are deferred and later created with a completely unchecked target: [2](#0-1)  shows `os.Symlink(hdr.Linkname, path)` executed with no validation that `hdr.Linkname` stays inside `e.dir`.

This means:
1. A single (or first-stage) archive can legitimately place a symlink, e.g. `link -> /tmp/evil` or `link -> ../../outside`, at a path that itself lexically satisfies the chroot check (only the *placement* of `link` is checked, not its target).
2. That symlink persists on disk after extraction completes (there is no cleanup of symlinks between invocations).
3. `cache-extractor`'s `Execute` calls `extractor.Extract(context.Background())` with `wd` (the current working directory, i.e. the job's build directory) as `e.dir` at [3](#0-2) . This command can run multiple times across a job's lifecycle (e.g., separate cache-restore invocations per job stage/cache key), each time reusing the same `wd`.
4. A subsequent extraction (a different archive, e.g. a second cache entry or artifact) whose entry name is `link/payload` produces `path = filepath.Join(e.dir, "link/payload")`, which lexically still has the `e.dir` prefix and thus passes the check at line 62. However, `os.MkdirAll(filepath.Dir(path), 0777)` and `os.Create(path)` at lines 66 and 88 resolve `link` through the filesystem, following the symlink placed by the earlier stage and writing the file to `/tmp/evil/payload` (or wherever the symlink points) — outside `e.dir`.

Existing protections are insufficient: the check is purely lexical/string-based and is evaluated once per entry without accounting for the actual filesystem state (including symlinks placed by earlier, independent extractions into the same directory). No `O_NOFOLLOW`-style open, no `Lstat`-based path-walk validation, and no restriction on `hdr.Linkname` exist anywhere in this function.

This matches the scoped question's core concern — cumulative multi-archive/multi-stage extraction into the same workspace can produce an eventual path escape that each individual extraction call's chroot check does not catch — though the simplest concrete exploit requires only a single symlink hop (stage 1 places the symlink; stage 2's entry path walks through it), rather than the two-hop dangling-symlink chain hypothesized in the question. The two-hop variant is also possible (stage 1 creates `A -> B` where `B` doesn't yet exist; stage 2 later creates `B -> outside`; then any subsequent write to `A` resolves through `B` to outside `e.dir`), but it is not required to achieve the underlying escape — the vulnerability exists as soon as any two archive extractions target the same directory.

### Impact Explanation
A later extraction call into the same job workspace (subsequent cache restore, or any other archive extraction reusing `wd`) can be made to write attacker-controlled file content outside the job root, into any location the earlier-planted symlink points to (subject to OS file permissions of the runner process). Concretely, this enables writing/overwriting files outside the intended build/cache root, which — per the scoped impact — can inject content into files later read or executed by runner-generated scripts, or otherwise corrupt state outside the sandboxed workspace.

### Likelihood Explanation
Preconditions: two archive-extraction operations must target the same directory across time (true for `cache-extractor`, which is invoked separately at various pipeline stages with `wd` as the target), and the attacker must control the contents of at least two archives extracted into that directory (feasible via job-defined cache keys/paths or artifacts an attacker-controlled pipeline can shape). The mechanism is fully deterministic and repeatable — no race condition is required beyond ordinary sequential job-stage execution.

### Recommendation
- Validate `hdr.Linkname` itself: resolve it relative to the symlink's directory and reject (or rewrite) any target that would escape `e.dir`, mirroring the existing chroot check applied to entry names.
- When computing containment for every entry (not just symlinks), resolve the path via `filepath.EvalSymlinks` on the existing portion of the path (or open parent directories with `O_NOFOLLOW`/`openat`-style semantics) so that pre-existing symlinks from prior extractions cannot redirect writes outside `e.dir`.
- Before extracting into a directory, treat any pre-existing symlinks within the target tree as untrusted and refuse to traverse through them for entries defined in a different/subsequent archive.

### Proof of Concept
Go test plan (place in `commands/helpers/archive/tarzstd`):
```go
func TestExtract_CrossStageSymlinkEscape(t *testing.T) {
    dir := t.TempDir()

    // Stage 1 archive: create a symlink "link" inside dir pointing to an
    // absolute location outside dir.
    outside := t.TempDir() // simulates location outside job root
    archive1 := buildTarZstd(t, []tarEntry{
        {name: "link", typeflag: tar.TypeSymlink, linkname: outside},
    })
    ext1, _ := NewExtractor(bytes.NewReader(archive1), int64(len(archive1)), dir)
    require.NoError(t, ext1.Extract(context.Background()))

    // Stage 2 archive (different, attacker-controlled): writes a file
    // through "link/payload".
    archive2 := buildTarZstd(t, []tarEntry{
        {name: "link/payload", typeflag: tar.TypeReg, content: []byte("evil")},
    })
    ext2, _ := NewExtractor(bytes.NewReader(archive2), int64(len(archive2)), dir)
    err := ext2.Extract(context.Background())

    // Expected (fixed) behavior: err should be non-nil (escape rejected),
    // and the file must NOT exist outside dir.
    _, statErr := os.Stat(filepath.Join(outside, "payload"))
    assert.True(t, os.IsNotExist(statErr), "file must not be written outside e.dir")
    _ = err
}
```
Current (buggy) behavior: `ext2.Extract` succeeds with no error, and `outside/payload` is created containing `"evil"`, proving the escape.
