Signer permanently stuck rejecting a legitimately canonical block once `SortitionViewMismatch` is issued, because the rejection is never re-evaluated - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`check_latest_block_in_tenure` (the function backing `check_block_against_signer_db_state`) is explicitly designed to be a *transient*, time-and-node-state-dependent check: its answer depends on freshness windows (`tenure_last_block_proposal_timeout`), whether a competing pre-commit/signature has gone stale, and the live tenure tip fetched from the node. Yet the rejection reason it produces, `RejectReason::SortitionViewMismatch`, is classified in `should_reevaluate_reject_reason` as **not** worth re-validating. A single miner can therefore engineer a situation where a signer issues a `SortitionViewMismatch` rejection for a block that is, or will shortly become, the legitimately canonical block, and that signer will keep resending the same stale rejection forever on reproposal — it never re-runs the chainstate check again. This mirrors the analog bug class: a check function (`_vestingCheck`) that should re-evaluate a category of caller/state over time instead returns a fixed, terminal answer, permanently wedging that actor.

### Finding Description
`check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:376-478`) decides whether a proposed block confirms enough of a tenure's chain by consulting:
- the last **signed** block in that tenure and whether its signature has gone stale (`tenure_last_block_proposal_timeout`),
- a fresh pre-commit at or above the proposed height, and
- the node's live tenure tip (`get_tenure_tip`).

All three inputs are time-varying by design: a signature that currently blocks a competing proposal will stop blocking once it times out, and the node's tenure tip can advance. When this check fails, `check_block_against_signer_db_state` (`stacks-signer/src/v0/signer.rs:1803-1880`) returns a rejection with `RejectReason::SortitionViewMismatch`.

`should_reevaluate_reject_reason` (`stacks-signer/src/v0/signer.rs:2706-2739`) explicitly places `SortitionViewMismatch` in the "No need to re-validate these types of rejections" bucket, alongside genuinely terminal decisions like `DuplicateBlockFound` or `InvalidParentBlock`. Consequently, in `should_reevaluate_block` (`stacks-signer/src/v0/signer.rs:1481-1572`), when a block previously rejected with `SortitionViewMismatch` is reproposed:
- `should_reevaluate_reject_reason` returns `false`,
- the block is not `PreCommitted` (it was locally rejected), so the pre-commit re-evaluation path is skipped,
- `determine_response(block_info)` simply resends the **stored** prior rejection response, without invoking `check_latest_block_in_tenure` (or any chainstate check) again.

Because the underlying condition that produced `SortitionViewMismatch` is inherently transient (freshness timers expiring, node tip advancing, a competing pre-commit going stale), a single miner can trigger the rejection once — e.g. by momentarily creating a race between two competing proposals/pre-commits at the same height/tenure, or by proposing while the signer's view of the tenure tip is briefly behind — and then repropose the exact same, now-legitimately-canonical block. The signer will never re-check reality; it just keeps echoing the original (now-incorrect) rejection. This is a liveness wedge specific to one signer, triggerable by a single miner/proposer without needing a majority or another signer's key, matching the report's core defect pattern: a check that should re-derive its answer against current state instead returns a value that is treated as permanent for that class of input.

### Impact Explanation
This is a **High** severity liveness wedge: a signer can be made to never sign a valid, canonical block that it previously and transiently mis-rejected as `SortitionViewMismatch`, permanently degrading that signer's participation for that block (and, if reproposed unchanged, indefinitely). While one signer alone cannot block consensus (70% threshold), this weakens the signer set's effective participation and, combined with normal operational conditions (e.g., a signer that is briefly behind the node, or races during a competing pre-commit that later goes stale), can silently and permanently remove valid signers from voting on an otherwise-good block, directly matching the "signer wedged into never signing valid blocks" High-impact category.

### Likelihood Explanation
Likelihood is moderate: it requires a single miner (or the natural timing/network jitter of pre-commits) to produce a transient chainstate-check failure (`SortitionViewMismatch`) for a block that later becomes canonical, and then have that exact block reproposed unchanged. This does not require a majority of signers, another signer's key, or any secret material — only crafted timing of proposals/pre-commits by one miner, which is squarely within a "one-slot miner" threat model.

### Recommendation
Move `RejectReason::SortitionViewMismatch` (and any other reject reason whose root check is time/node-state dependent, e.g. via `check_latest_block_in_tenure`) out of the "terminal" branch of `should_reevaluate_reject_reason`, so that a reproposal of the same block re-runs `check_block_against_signer_db_state` rather than resending a cached rejection. Alternatively, ensure `should_reevaluate_block` re-runs the underlying chainstate check specifically for `SortitionViewMismatch` before falling back to `determine_response`.

### Proof of Concept
1. Miner proposes block `B` referencing tenure `T` at a moment when the signer's `check_latest_block_in_tenure` sees a fresher signed/pre-committed sibling at or above `B`'s height (e.g., due to a race with a competing pre-commit) — `check_block_against_signer_db_state` returns `SortitionViewMismatch`, and `handle_block_validate_reject`/proposal-time rejection stores this on `block_info.reject_reason`.
2. The condition that caused the mismatch resolves normally (the competing pre-commit exceeds `tenure_last_block_proposal_timeout` and goes stale, or the node's tenure tip catches up) — `B` is now, or would now be, a legitimately confirmable block.
3. Miner reproposes the identical `B`. In `should_reevaluate_block`, `should_reevaluate_reject_reason(block_info)` returns `false` for `SortitionViewMismatch`; since `block_info.state != PreCommitted`, the code calls `determine_response(block_info)` which resends the original stored rejection — `check_latest_block_in_tenure` is never invoked again for this proposal.
4. The signer never signs `B`, even though the underlying condition that justified the original rejection no longer holds, wedging that signer's participation on this (and any identically-hashed) block indefinitely.
