### Title
Single-slot block-validation gate lets a one-slot miner starve a signer's ability to validate/sign a legitimate block, mirroring the LPP "clock-starvation" freeloader pattern - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
The signer only allows **one** in-flight node-validation request at a time (`self.submitted_block_proposal`). Any additional proposal that arrives while a prior proposal is "occupying" that slot is not submitted for validation at all — it is merely parked in a pending table until the slot frees up, either because the node answers or because a fixed `block_proposal_validation_timeout` elapses. A single miner (the "one-slot" leader) can therefore repeatedly occupy this slot with proposals that are not provably invalid up front but are deliberately expensive/slow to validate, preventing the signer from ever spending its limited validation bandwidth on a subsequent legitimate proposal before that proposal goes stale. This is directly analogous to the reported LPP bug: a resource with a fixed, too-short window (there: chess-clock time vs. `CHALLENGE_PERIOD`; here: the validation timeout vs. the single-slot queue) is starved by an adversary to prevent an honest party from responding in time, causing loss of liveness/incentive rather than requiring a signer majority or key compromise.

### Finding Description
When a `BlockProposal` is received and cannot be immediately rejected by `check_block_against_state`, the signer checks whether it already has a submission in flight: [1](#0-0) 

If `self.submitted_block_proposal` is `Some(..)` (i.e., a prior proposal is still awaiting a node validation response), the new proposal is **not submitted for validation**; it is only stored locally and inserted into a pending-validation queue (`insert_pending_block_validation`). The signer will not vote on it until the in-flight slot is freed.

The slot is freed only by `check_submitted_block_proposal`, which is driven purely by a fixed wall-clock timeout (`block_proposal_validation_timeout`, default 120s): [2](#0-1) 

Because the node-side validation timeout for a single proposal can itself run close to this same window (`block_proposal_validation_timeout_secs` / `block_proposal_max_tx_execution_time_secs`, referenced from `postblock_proposal.rs`'s `spawn_validation_thread`): [3](#0-2) 

a single miner can craft a sequence of structurally-valid-looking proposals (passing the cheap `check_block_against_state` pre-check) whose actual chainstate validation (transaction execution) is deliberately made slow, so each occupies the one available validation slot for up to the full timeout. Any legitimate proposal that shows up during this window is queued, not validated, and the signer issues no vote (accept or reject) for it until the queue drains — by which point the proposal may exceed `block_proposal_max_age_secs` (default 600s) and be dropped with `ProposalTooOld`, or the tenure/sortition window may have already closed.

This is the same structural bug class as the reported issue: a fixed, too-short resource window (`CLOCK_EXTENSION` vs. `CHALLENGE_PERIOD` in the original; `block_proposal_validation_timeout` vs. the single in-flight slot here) can be exhausted by an adversary who controls the timing/content of proposals (there, the disputer of a claim; here, the one-slot miner), preventing the honest party (challenger / signer) from acting on a legitimate item in time. It does not require a signer majority, a stolen key, or transport-layer flooding — a single miner leveraging its normal one-proposal-per-slot privilege suffices.

### Impact Explanation
This maps to the "signer wedged into never signing valid blocks" High-impact class: repeated occupation of the single validation slot can cause a signer to never validate/sign a legitimate, in-window block proposal, purely due to timing starvation rather than any consensus disagreement. In aggregate across the signer set (if the same miner sends near-simultaneous decoy proposals to all signers), this can delay or entirely prevent the network from reaching the approval threshold for a valid block within its liveness window, causing spurious "malicious miner" markings, wasted tenure cycles, or loss of block-production liveness — a purely timing-based wedge, not a cryptographic or majority-based one.

### Likelihood Explanation
Likelihood is moderate: it requires only the current sortition winner (a single, un-trusted party) to craft proposals whose chainstate validation is intentionally slow (e.g., transactions near the execution-cost/time ceiling) while still passing the signer's cheap pre-validation (`check_block_against_state`). No signer collusion, private key access, or majority control is needed — only normal, permitted proposal-crafting ability of the current miner.

### Recommendation
- Allow more than one concurrent in-flight validation submission (or a small bounded pool) instead of a hard single-slot gate, so a slow/decoy proposal cannot fully block validation of a subsequent proposal.
- Decouple the pending-validation queue's dequeue trigger from a fixed wall-clock timeout tied 1:1 to the slowest possible validation; instead, prioritize/dequeue newer or higher-priority proposals (e.g., by tenure/height freshness) ahead of a stale in-flight one.
- Ensure `block_proposal_max_age_secs` and `block_proposal_validation_timeout` are dimensioned so that a full round-trip through the pending queue cannot cause a legitimate proposal to go stale while a single slow decoy occupies the slot (analogous to widening `CLOCK_EXTENSION` to cover `CHALLENGE_PERIOD` in the original report).

### Proof of Concept
1. Attacker (current sortition winner) sends `BlockProposal` A with transactions crafted to make node-side execution/validation take close to `block_proposal_validation_timeout` (e.g., near `block_proposal_max_tx_execution_time_secs`), but which is not provably invalid by `check_block_against_state`. Signer stores A and calls `submit_block_for_validation`, setting `submitted_block_proposal = Some(A)` (`stacks-signer/src/v0/signer.rs:1696-1700`).
2. While A is in flight, a legitimate proposal B (e.g., a corrected/valid re-proposal, or a competing but valid block) arrives. Because `self.submitted_block_proposal.is_some()`, B is not submitted for validation; it is only stored and queued via `insert_pending_block_validation` (`stacks-signer/src/v0/signer.rs:1701-1714`).
3. The signer will not consider B until `check_submitted_block_proposal` times out A (up to `block_proposal_validation_timeout`, default 120s) or the node responds (`stacks-signer/src/v0/signer.rs:2114-2168`).
4. Attacker repeats this by sending A2 immediately after A resolves, keeping the slot perpetually busy. B, and any subsequent legitimate proposals, remain queued and unvalidated. If this persists past `block_proposal_max_age_secs` (default 600s), B is eventually rejected outright with `ProposalTooOld` without ever being validated or voted on, achieving a liveness wedge against the signer's ability to sign a valid block in time.

    /// Check the current tracked submitted block proposal to see if it has timed out.
    /// Broadcasts a rejection and marks the block locally rejected if it has.
    fn check_submitted_block_proposal(&mut self) {
        let Some((proposal_signer_sighash, block_submission)) =
            self.submitted_block_proposal.take()
        else {
            // Nothing to check.
            return;
        };
        if block_submission.elapsed() < self.block_proposal_validation_timeout {
            // Not expired yet. Put it back!
            self.submitted_block_proposal = Some((proposal_signer_sighash, block_submission));
            return;
        }
        // For mutability reasons, we need to take the block_info out of the map and add it back after processing
        let mut block_info = match self.signer_db.block_lookup(&proposal_signer_sighash) {
            Ok(Some(block_info)) => {
                if block_info.has_reached_consensus() {
                    // The block has already reached consensus.
                    return;
                }
                block_info
            }
            Ok(None) => {
                // This is weird. If this is reached, its probably an error in code logic or the db was flushed.
                // Why are we tracking a block submission for a block we have never seen / stored before.
                error!("{self}: tracking an unknown block validation submission.";
                    "signer_signature_hash" => %proposal_signer_sighash,
                );
                return;
            }
            Err(e) => {
                error!("{self}: Failed to lookup block in signer db: {e:?}",);
                return;
            }
        };
        // We cannot determine the validity of the block, but we have not reached consensus on it yet.
        // Reject it so we aren't holding up the network because of our inaction.
        warn!(
            "{self}: Failed to receive block validation response within {} ms. Rejecting block.", self.block_proposal_validation_timeout.as_millis();
            "signer_signature_hash" => %proposal_signer_sighash,
        );
        let rejection = self.create_block_rejection(
            RejectReason::ConnectivityIssues(
                "failed to receive block validation response in time".to_string(),
            ),
            &block_info.block,
        );
        block_info.reject_reason = Some(rejection.response_data.reject_reason.clone());
        if let Err(e) = block_info.mark_locally_rejected() {
            if !block_info.has_reached_consensus() {
                warn!("{self}: Failed to mark block as locally rejected: {e:?}");
            }
        };
        self.send_block_response(&block_info.block, rejection.into());
