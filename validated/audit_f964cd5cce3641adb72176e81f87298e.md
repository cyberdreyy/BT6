### Title
Replay-guard digest consumption before owner validation allows cross-owner denial-of-service against predictable Vault requests - ([File: core/capabilities/vault/authorizer.go])

### Finding Description
`authorizer.AuthorizeRequest` performs `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())` **before** `validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner())`. [1](#0-0) 

The `Digest()` used as the replay key is computed purely from request content (method, id, params) and is **independent of the authorized identity/owner**. Both authorization backends compute it the same way before deriving the owner: [2](#0-1) [3](#0-2) 

The `RequestReplayGuard` is a single shared instance used by both the allowlist-based and JWT-based flows and keys its `seen` map only by digest, with no owner/identity component: [4](#0-3) 

Because the digest is content-only, two requests submitted by different owners with identical `method`/`id`/`params` (e.g. an attacker crafting a `vault.secrets.list` request with the victim's public `owner`/`namespace`/`request_id` fields but authorizing under their own JWT or allowlist entry) produce the same digest. `CheckAndRecord` runs first and unconditionally records that digest as "seen" with the attacker-controlled `expiresAt`. Only afterward does `validateSecretOwnersMatchAuthorized` reject the attacker's request because the `owner` field inside `req.Params` (e.g. `listReq.Owner`) does not match the attacker's `AuthorizedOwner()`: [5](#0-4) 

The attacker's request is denied, but the digest remains marked as "seen" in the shared replay guard until the recorded `expiresAt` elapses. When the victim later submits the identical, legitimate request (same digest, correct owner-matching auth), `CheckAndRecord` finds the digest already present and returns `ErrRequestAlreadySeen`, permanently (until expiry) blocking the victim's valid request.

The existing test suite only exercises replay from the *same* owner reusing a digest twice (`TestAuthorizer_RejectsAllowListBasedAuthReplay`, `TestAuthorizer_RejectsJWTReplay`), never the cross-owner collision case, so this ordering defect is untested. [6](#0-5) 

### Impact Explanation
This is a scoped, targeted denial-of-service: an attacker who is authorized only for their own workflow owner can permanently block (for the duration of the attacker-chosen/token-derived expiry) a victim's specific, predictable Vault request (e.g., `vault.secrets.list`, `vault.secrets.get`) from ever succeeding, without needing the victim's auth token or credentials. This matches "denial of service against a specific user/job" style impact rather than node-wide compromise.

### Likelihood Explanation
Exploitation requires the attacker to reproduce the victim's exact upcoming request content (method, id/request_id, and params such as owner/namespace) — feasible for deterministic, low-entropy read requests with public parameters (e.g., a fixed or predictable `request_id` convention plus a public owner address), as stated in the precondition. The attacker needs only their own valid authorization (a legitimate JWT for their own org, or ability to register/obtain an allowlist entry for their own owner) — no elevated privileges, no victim credentials. The attack is repeatable each time the guard entry expires and the victim's request pattern remains predictable.

### Recommendation
Perform owner/identity validation (`validateSecretOwnersMatchAuthorized`) before consuming the replay-guard slot (`CheckAndRecord`), or incorporate the authorized owner/orgID into the replay-guard key so that digests are scoped per-identity rather than globally shared across owners. Reordering the two checks in `authorizer.AuthorizeRequest` (validate owner match first, then record replay) closes the window without weakening real replay protection.

### Proof of Concept
Go unit test plan (in `core/capabilities/vault/authorizer_test.go` style):
1. Construct `vaultcommon.ListSecretIdentifiersRequest{Owner: "0xvictim", Namespace: "main"}` with a fixed/known `request_id`; marshal into `req.Params`, `req.Method = vaulttypes.MethodSecretsList`.
2. Compute `digest, _ := req.Digest()`.
3. Mock `allowListBasedAuth` (or `jwtBasedAuth`) to return `vault.NewAuthResult(orgAttacker, "0xattacker", digest, futureExpiry)` for this exact `req` (simulating attacker's own valid auth bound to the same digest/content).
4. Call `a.AuthorizeRequest(ctx, req)`; assert it returns an error from `validateSecretOwnersMatchAuthorized` (owner mismatch: `"0xvictim" != "0xattacker"`).
5. Re-mock the authorizer to return `vault.NewAuthResult(orgVictim, "0xvictim", digest, futureExpiry)` for the same `req` (simulating the victim's legitimate subsequent request with identical content and correct owner).
6. Call `a.AuthorizeRequest(ctx, req)` again; **expected (vulnerable) behavior**: returns `vault.ErrRequestAlreadySeen` even though this is the victim's first, legitimate, correctly-owned request — proving the attacker's failed request permanently consumed the victim's digest slot.
7. Assert this demonstrates the invariant violation: replay protection is not scoped per-authorized-identity, allowing cross-owner digest griefing.

```go
// RequestReplayGuard prevents replay of already-processed requests by tracking
// request digests with expiry timestamps. It is safe for concurrent use.
//
// Used by both the AllowListBasedAuth flow and the JWTBasedAuth flow to ensure
// that a given request digest is only accepted once.
type RequestReplayGuard struct {
	mu      sync.Mutex
	seen    map[string]int64 // digest → unix expiry timestamp
	nowFunc func() time.Time // injectable for testing
}

// NewRequestReplayGuard creates a replay guard for authorized Vault requests.
func NewRequestReplayGuard() *RequestReplayGuard {
	return &RequestReplayGuard{
		seen:    make(map[string]int64),
		nowFunc: time.Now,
	}
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```

```go
func TestAuthorizer_RejectsJWTReplay(t *testing.T) {
	req := jsonrpc.Request[json.RawMessage]{
		ID:     "1",
		Method: vaulttypes.MethodPublicKeyGet,
		Auth:   "jwt-token",
	}
	digest, err := req.Digest()
	require.NoError(t, err)

	jwtBasedAuth := vaultmocks.NewAuthorizer(t)
	jwtBasedAuth.EXPECT().AuthorizeRequest(mock.Anything, req).Return(vault.NewAuthResult("org-1", "", digest, time.Now().Add(time.Minute).Unix()), nil).Twice()

	a := vault.NewAuthorizer(nil, jwtBasedAuth, logger.TestLogger(t))

	authResult, err := a.AuthorizeRequest(t.Context(), req)
	require.NoError(t, err)
	require.Empty(t, authResult.AuthorizedOwner())

	authResult, err = a.AuthorizeRequest(t.Context(), req)
	require.Nil(t, authResult)
	require.ErrorIs(t, err, vault.ErrRequestAlreadySeen)
}

func TestAuthorizer_RejectsAllowListBasedAuthReplay(t *testing.T) {
	allowListBasedAuth := vaultmocks.NewAuthorizer(t)
	// Use a method without secret identifiers so the owner-binding check is a no-op.
	req := jsonrpc.Request[json.RawMessage]{ID: "1", Method: vaulttypes.MethodPublicKeyGet}
	allowListBasedAuth.EXPECT().AuthorizeRequest(mock.Anything, req).Return(vault.NewAuthResult("", "0xabc", "digest-1", time.Now().Add(time.Minute).Unix()), nil).Twice()

	authResult, err := a.AuthorizeRequest(t.Context(), req)

	require.Empty(t, authResult.OrgID())

	require.Equal(t, "0xabc", authResult.AuthorizedOwner())

	authResult, err = a.AuthorizeRequest(t.Context(), req)
	require.Nil(t, authResult)
	require.ErrorIs(t, err, vault.ErrRequestAlreadySeen)
}
```
