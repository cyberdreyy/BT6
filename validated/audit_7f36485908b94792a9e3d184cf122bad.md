### Title
Global-contract storage burn (`result.tokens_burnt`) survives receipt rollback, decoupling `total_supply` burn accounting from the actual (rolled-back) account balance change - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
`action_deploy_global_contract` deducts `storage_cost` from the in-memory `Account` and unconditionally adds it to `result.tokens_burnt` via `checked_add`, but that account mutation is only persisted to the trie via `set_account` if the *whole receipt* ends up successful. If a later action in the same receipt (e.g. a second `DeployGlobalContract`) fails, the receipt fails and `TrieUpdate::rollback()` discards all state writes — including the never-committed balance deduction — yet the already-accumulated `result.tokens_burnt` is not rolled back and still flows into `tx_burnt_amount`, which is subtracted from `total_supply` at the block level.

### Finding Description
`action_deploy_global_contract` (`runtime/runtime/src/global_contracts.rs:24-62`) computes `storage_cost`, checks the account can afford it, and on success does: [1](#0-0) 

This mutates the local `Account` object and bumps the receipt-level `ActionResult.tokens_burnt` via `checked_add`, but does **not** write anything to `state_update` itself for the balance change.

In `apply_action_receipt` (`runtime/runtime/src/lib.rs:892-951`), actions in a receipt execute in a loop, and each per-action `ActionResult` is folded into the receipt-level `result` via `result.merge(new_result)?`: [2](#0-1) 

`validate_number_of_deploy_actions` permits up to `max_deploy_actions_per_receipt` `DeployGlobalContract`/`DeployContract` actions inside a single action list (confirmed by `test_validate_actions_num_deploy_actions`): [3](#0-2) [4](#0-3) 

An attacker can therefore submit `[DeployGlobalContract(small_code), DeployGlobalContract(oversized_code)]` in one transaction/receipt to an account funded just enough for the first deploy's `storage_cost` but not the second's. The first action succeeds: `account.set_amount(updated_balance)` mutates the local `account`, and `result.tokens_burnt += storage_cost`. The second action fails with `LackBalanceForState` (the `checked_sub` on `account.amount()` returns `None`), setting `result.result = Err(...)`, breaking the loop.

Because `result.result` is now `Err`, the `set_account(state_update, ...)` write at `runtime/runtime/src/lib.rs:955-960` (gated on `result.result.is_ok()`) is **never reached**, so the balance deduction from action 0 was never written into `state_update` in the first place; and any other partial writes from `initiate_distribution` are discarded by `state_update.rollback()` on the failure path (per the failure-commit branching described at `runtime/runtime/src/lib.rs:961-970` in `runtime-execution.md:70`). However, `result.tokens_burnt` is a plain in-memory field on `ActionReceiptResult`, not a trie write — it is untouched by `TrieUpdate::rollback()` and is unconditionally folded into `tx_burnt_amount` (`runtime/runtime/src/lib.rs:975-984`, documented at `protocol-model/spec/economics.md:66-71`), which reduces `stats.balance.tx_burnt_amount` and ultimately `total_supply` at the block level (`core/primitives/src/block.rs:193`).

Net effect: the account's actual balance is unchanged (rolled back / never persisted), but the chain's recorded `total_supply` is permanently reduced by the phantom `storage_cost` burn from the first, "successful-but-discarded" deploy action.

### Impact Explanation
This breaks the `new_total_supply = prev.total_supply + minted − balance_burnt` invariant's intended backing: `balance_burnt` should only reflect tokens actually removed from an account's persisted balance, but here it counts a burn whose corresponding account-side deduction was rolled back. Repeated, this causes `total_supply` to drift below the true sum of all account balances — a supply/loss-accounting bug (token "loss" category), not a mechanism for an attacker to steal other users' funds (the attacker's own balance is unaffected, since the deduction was rolled back).

### Likelihood Explanation
Trivially reachable by any unprivileged account: send one transaction with two `DeployGlobalContract` actions, sized so the account can afford the first's storage deposit but not the second's, causing `LackBalanceForState` on the second. Cost is only the gas for a failed receipt; repeatable at will and cheaply.

### Recommendation
Do not accumulate `result.tokens_burnt` (or any token-burn bookkeeping used for `total_supply` accounting) speculatively per-action before the whole receipt's success/failure is known. Either only fold `tokens_burnt` from `action_deploy_global_contract` into the receipt-level `ActionResult` after the receipt is confirmed successful, or clear/roll back the accumulated `tokens_burnt` contributions from actions that belong to a receipt whose overall `result.result` becomes `Err`, mirroring the same gating that already protects the `set_account` write.

### Proof of Concept
Runtime apply-path integration test (test-loop or `runtime/runtime` unit test):
1. Create account `alice` with balance exactly covering the storage cost of a small global contract (`code_a`, e.g. 1 byte) plus base fees, but insufficient for a second, larger global contract (`code_b`).
2. Submit one transaction/receipt to `alice` containing actions `[DeployGlobalContract(code_a), DeployGlobalContract(code_b)]`.
3. Apply the chunk; assert the receipt's outcome status is `Failure(LackBalanceForState)`.
4. Assert `alice`'s final balance equals her balance *before* the receipt (i.e. the `code_a` storage cost was fully refunded/never persisted).
5. Assert the outcome's `tokens_burnt` is nonzero (equal to `code_a`'s `storage_cost`) and that this amount is folded into the chunk's `stats.balance.tx_burnt_amount` / `balance_burnt`, causing `total_supply` to decrease by that amount even though no account's persisted balance decreased — demonstrating the mismatch between `balance_burnt` and actual balance changes.

fn validate_number_of_deploy_actions(
    actions: &[Action],
    max_deploy_actions_per_receipt: u64,
) -> Result<(), ActionsValidationError> {
    let deploy_actions_count = actions
        .iter()
        .filter(|a| matches!(a, Action::DeployContract(_) | Action::DeployGlobalContract(_)))
        .count() as u64;
    if deploy_actions_count > max_deploy_actions_per_receipt {
        Err(ActionsValidationError::TotalNumberOfDeployActionsExceeded {
            number_of_deploy_actions: deploy_actions_count,
            limit: max_deploy_actions_per_receipt,
        })
    } else {
        Ok(())
    }
}
