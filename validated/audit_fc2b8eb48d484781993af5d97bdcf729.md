### Title
Unbounded zstd compression cost in `encode_ui_account` (Base64Zstd) allows single-request CPU/memory cost proportional to attacker-chosen account size - (File: account-decoder/src/lib.rs)

### Summary
`encode_ui_account` for `UiAccountEncoding::Base64Zstd` runs `zstd::stream::write::Encoder::new(...).write_all(...)` over the full (or data-sliced) account data with no size cap, unlike the `Base58`/`Binary` path which enforces `MAX_BASE58_BYTES`. An attacker can create an account with data up to the runtime's maximum permitted account size and then have any client (including themselves) request it via `getAccountInfo`/`getMultipleAccounts`/account-subscribe with `encoding=base64+zstd`, forcing one RPC call to spend CPU/memory proportional to the attacker-controlled account size.

### Finding Description
`encode_ui_account` in `account-decoder/src/lib.rs` dispatches on `encoding` and, for `Base64Zstd`, does: [1](#0-0) 
There is no size check analogous to `encode_bs58`'s `MAX_BASE58_BYTES` gate: [2](#0-1) 

The RPC entrypoint `get_account_info` / `get_multiple_accounts` in `rpc/src/rpc.rs` accepts a client-supplied `encoding` and calls `get_encoded_account` → `encode_account`, which only enforces `MAX_BASE58_BYTES` for `Binary`/`Base58` encodings; for `Base64Zstd` it calls `encode_ui_account` directly with no length guard: [3](#0-2) [4](#0-3) 

The same unguarded path is reachable from `account_subscribe`/pubsub notifications (`filter_program_results` in `rpc/src/rpc_subscriptions.rs`), which also calls `encode_ui_account` with the client-selected encoding and no data-size limit before the zstd branch: [5](#0-4) 

An attacker (unprivileged) can submit an on-chain transaction that allocates account data up to the runtime-permitted maximum size (`MAX_PERMITTED_DATA_LENGTH`, referenced in `program-runtime/src/serialization.rs` and enforced in `programs/system/src/system_processor.rs`/`programs/bpf_loader/src/lib.rs`), filled with compressible content (e.g., all zeros), which is inexpensive to write since it's a normal `createAccount`/`allocate`/`extend` instruction sequence subject to normal compute-unit and rent costs, not an RPC call. Once stored, any single subsequent `getAccountInfo` call with `encoding=base64+zstd` triggers `zstd::stream::write::Encoder::write_all` over the entire account buffer, which the validator's RPC thread pool must fully compress synchronously before returning a response — with CPU/allocation cost scaling with the attacker-chosen data size rather than being bounded by a fixed per-request cap, unlike the `Base58` path's explicit length check.

### Impact Explanation
This matches the "unbounded cost for a single low-rate call" scoped-impact category: because `encode_ui_account`'s Base64Zstd branch has no size cap (unlike the analogous Base58 path), a single `getAccountInfo`/`getMultipleAccounts`/`accountSubscribe` request against a large, attacker-authored account forces the validator's RPC-serving thread to perform CPU/memory work proportional to the account's full on-chain size (up to the maximum permitted account data length) for one request, violating the bounded-cost-of-one-request invariant that all sibling encodings (`Base58`) enforce.

### Likelihood Explanation
Feasible for an unprivileged attacker: creating a large on-chain account (e.g., via `createAccount`/`allocate`/`extend` with zero-filled or compressible data up to the max permitted size) requires only standard, rent/compute-budget-bounded transactions available to any user, and querying it via `getAccountInfo` with `encoding=base64+zstd` is a single RPC call satisfying the "no more than one call per `CLUSTER_SLOT_TIME_TARGET / 2`" constraint. No special privileges, mocked paths, or multiple concurrent clients are required; the vulnerability is fully repeatable against the same account by any client that later queries it.

### Recommendation
Add a size/limit check before entering the zstd encode branch in `encode_ui_account`, symmetric to `encode_bs58`'s `MAX_BASE58_BYTES` gate — e.g., cap the account/data-slice length that may be zstd-encoded per request, or reject/require a `dataSlice` when the slice exceeds a fixed threshold, returning an `InvalidRequest` error (as done for oversized Base58 in `encode_account`) instead of unconditionally compressing arbitrarily large buffers.

```rust
#[test]
fn test_base64_zstd_cost_scales_with_account_size() {
    use std::time::Instant;

    let small = AccountSharedData::from(Account {
        data: vec![0u8; 1024],
        ..Account::default()
    });
    let large = AccountSharedData::from(Account {
        data: vec![0u8; 10 * 1024 * 1024], // approaches max permitted account size
        ..Account::default()
    });

    let start = Instant::now();
    let _ = encode_ui_account(&Pubkey::default(), &small, UiAccountEncoding::Base64Zstd, None, None);
    let small_elapsed = start.elapsed();

    let start = Instant::now();
    let _ = encode_ui_account(&Pubkey::default(), &large, UiAccountEncoding::Base64Zstd, None, None);
    let large_elapsed = start.elapsed();

    // Expectation for a bounded-cost implementation: elapsed time for one
    // request should be capped regardless of account size (e.g., via a
    // MAX_BASE64ZSTD_BYTES gate). This assertion currently FAILS because
    // large_elapsed scales roughly linearly with account size, unlike the
    // Base58 path which rejects oversized data outright.
    assert!(
        large_elapsed < small_elapsed * 10,
        "zstd encoding cost scaled with attacker-controlled account size: small={:?} large={:?}",
        small_elapsed, large_elapsed
    );
}
```
Expected result: the assertion fails on current code, demonstrating that a single request's CPU cost is proportional to attacker-chosen account size with no fixed bound, whereas after adding a `MAX_BASE64ZSTD_BYTES`-style guard (mirroring `MAX_BASE58_BYTES`), oversized requests would be rejected in O(1) time instead of performing full compression.

```rust
fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
```
