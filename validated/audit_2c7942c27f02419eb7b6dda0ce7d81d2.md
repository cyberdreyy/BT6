### Title
Dust instant-withdraw receipt accepted at request time unconditionally blocks `stopEpoch` and can force borrower default — (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The bug class of the external report is *check-order inconsistency*: a transaction passes the permissive first-stage validation (mempool) but fails the stricter/differently-ordered second-stage validation (block), letting an attacker enqueue objects that can never be settled, at no cost, forever. The analog in idle-tranches is the instant-withdraw receipt pipeline. `requestWithdraw` accepts and mints an instant-withdraw receipt based only on an APR-delta check at request time, while `stopEpoch` performs the settlement-side check in the opposite "order": it reverts unconditionally whenever `pendingInstantWithdraws != 0`. The only escape is `getInstantWithdrawFunds`, which either pulls extra cash from the borrower or defaults the entire pool. An unprivileged tranche holder (KYC-passing lender) can therefore, for the cost of a dust amount of tranche tokens, halt every epoch or force a borrower default even when the borrower is honest and fully funded for the agreed interest.

### Finding Description
Two validation paths order their checks inconsistently:

1. **Request path** (`contracts/IdleCDOEpochVariant.sol:739-791`). `requestWithdraw` checks only `allowAA/BBWithdrawRequest` and `isWalletAllowed`, then, if `lastEpochApr > unscaledApr + instantWithdrawAprDelta` (a routine state after any APR decrease at `stopEpoch`), calls `creditVault.requestInstantWithdraw(_underlyings, msg.sender)` and burns the tranche tokens. There is no check that the borrower can or will fund this amount, no minimum size, and no opt-in from the manager. A request of 1 wei of tranche tokens is valid.

2. **Settlement path** (`contracts/IdleCDOEpochVariant.sol:338-351`). `_stopEpoch` reverts via `_checkNotAllowed(... || _pendingInstant() != 0 || ...)` — the epoch cannot be stopped while any instant receipt exists, regardless of size. The only way to clear it is `getInstantWithdrawFunds` (`:558-574`), which pulls `_instantWithdraws` from the borrower via `getFundsFromBorrower`; on transfer failure it calls `_handleBorrowerDefault`, which sets `defaulted = true`, pauses the contract, stops the epoch, and disables all withdraw requests (`:577-599`).

So the ordering is inverted exactly like the Monad bug: the cheap check (APR delta) is done at submission and the expensive/terminal check (borrower must cover an extra arbitrary amount, or default) is done at finalization. The borrower — who is honest — typically only holds/approves enough underlying for `expectedEpochInterest + pendingWithdraws`. Any instant receipt in excess of that cannot be funded, and the pull failing triggers a hard default, not a revert.

### Impact Explanation
- **Temporary/permanent freezing:** while `pendingInstantWithdraws != 0`, `stopEpoch` always reverts, so the epoch can never roll until the manager calls `getInstantWithdrawFunds`. If the borrower cannot cover the extra amount, `_handleBorrowerDefault` fires: `defaulted = true`, contract paused, `isEpochRunning = false`, `allowAA/BBWithdrawRequest = false`. All lenders' funds are frozen pending owner recovery/finalization — a full-pool DoS triggered by ~1 wei of tranche tokens.
- **Repeatability:** even if the borrower does fund the instant amount, the attacker resubmits a dust instant request each epoch (tranche tokens are cheap to acquire as a KYC'd lender), forcing the manager into an extra pull every cycle and re-exposing the default path each time — the direct analog of the attacker's re-submittable never-executing transaction.
- Quantified loss: freezing of 100% of pool NAV for the duration of default resolution; in the funded case, theft-adjacent griefing where the borrower must over-fund relative to the agreed `expectedEpochInterest`.

### Likelihood Explanation
The precondition `lastEpochApr > unscaledApr + instantWithdrawAprDelta` occurs on any APR decrease, which is a normal manager action at `stopEpoch` (the test suite exercises this exact state, e.g. `testRequestWithdrawNormal`/instant-withdraw tests in `test/foundry/IdleCreditVault.t.sol`). The attacker only needs a tranche-token balance (KYC-passing lender is in-scope) and loses only the dust principal burned in `_withdrawOps`. No privileged role misbehavior is required — the honest borrower's bounded allowance is what converts the unfunded pull into a default.

### Recommendation
Mirror the mitigation of the external report: perform the settlement-side check at submission time. Concretely, in `requestWithdraw`'s instant branch, require that the instant amount be reservable/fundable — e.g. cap instant requests, enforce a minimum economic size, or have the manager pre-approve an instant-withdraw budget per epoch — and do not let `stopEpoch` be blocked by receipts the borrower cannot cover. Alternatively, treat unfundable instant receipts as a loss-adjusted claim against vault liquidity rather than routing them through `getFundsFromBorrower`→`_handleBorrowerDefault`, so a dust receipt cannot convert a funded borrower into a defaulter.

### Proof of Concept
Foundry fork-style PoC (against the existing `IdleCreditVault.t.sol` harness conventions):

```solidity
// Setup: pool with deposits, epoch 0 started and stopped with a lower APR,
// so lastEpochApr > unscaledApr + instantWithdrawAprDelta (instant mode armed).
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());
_startEpochAndCheckPrices(1); // new epoch running at reduced APR

// Attacker: KYC'd lender with a dust tranche balance
address attacker = makeAddr("attacker");
_depositWithUser(attacker, 1e6, true); // minimal AA deposit
uint256 dust = IERC20(AAtranche).balanceOf(attacker) / 1e6;

vm.prank(attacker);
cdoEpoch.requestWithdraw(dust, address(AAtranche)); // accepted: creates instant receipt
assertGt(strategy.pendingInstantWithdraws(), 0);

// Honest borrower funded only expectedEpochInterest + pendingWithdraws
vm.warp(cdoEpoch.epochEndDate() + 1);
uint256 due = cdoEpoch.expectedEpochInterest() + strategy.pendingWithdraws();
deal(defaultUnderlying, borrower, due);

// stopEpoch can never proceed while instant receipts are pending
vm.prank(manager);
vm.expectRevert(); // _pendingInstant() != 0
cdoEpoch.stopEpoch(0, 0);

// The only remediation pulls extra cash the borrower doesn't have -> full default
vm.prank(manager);
cdoEpoch.getInstantWithdrawFunds(); // try/catch -> _handleBorrowerDefault
assertTrue(cdoEpoch.defaulted());   // whole pool frozen for a dust receipt
```

Caveat: I could not fully read `IdleCreditVault.requestInstantWithdraw`/`collectInstantWithdrawFunds` bodies (index excerpt limits), so the exact bookkeeping of `pendingInstantWithdraws` should be verified in a live session, but the revert ordering at `IdleCDOEpochVariant.sol:345` and the default escalation at `:571-573` are confirmed in source.
