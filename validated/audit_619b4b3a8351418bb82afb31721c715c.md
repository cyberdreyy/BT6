### Title
`check_parent_tenure_choice` treats "no local approval record" as "poorly-timed proposal", letting a signer waive the reorg-timing guard on a tenure it never approved - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a miner is allowed to reorg an already-mined tenure. The only real safeguard against reorging a mature tenure is a timing check: `proposal_to_sortition = sortition_state_received_time - local_block_info.approved_time`, which must be smaller than `first_proposal_burn_block_timing` for the reorg to be sanctioned. When this signer's own `approved_time` for the reorged tenure's first block is `None`, the code silently substitutes `0` for `proposal_to_sortition` [1](#0-0) . Since `0` is always `< first_proposal_burn_block_timing` (unless the operator sets that timeout to `0`), this branch unconditionally treats the tenure as "poorly timed" and pushes it into `superseded_tenures`, permitting the reorg regardless of the tenure's true age [2](#0-1) .

### Finding Description
`check_parent_tenure_choice` is reached whenever a proposed block's sortition does not build on the prior sortition, i.e., the miner is attempting to reorg one or more tenures [3](#0-2) . For each reorged tenure that already has exactly one globally accepted block (more than one is unconditionally refused) [4](#0-3) , the signer looks up its own locally recorded approval for that tenure's first block via `get_first_approved_block_in_tenure`. If it has **no** record at all, it correctly refuses the reorg (`return Ok(false)`) [5](#0-4) . But if it *does* have a `BlockInfo` record for that tenure whose `approved_time` field happens to be `None` (i.e., this signer tracked/received the proposal but never itself pre-committed to or locally accepted it — for example because it rejected the block for an unrelated reason, or the validation never completed before the reorg proposal arrived), the code does not refuse or fall back to a conservative default. Instead it substitutes `proposal_to_sortition = 0` and logs "We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal" [6](#0-5) .

Because `Duration::from_secs(0) < first_proposal_burn_block_timing` is true for any nonzero configured timeout, this signer will *always* conclude the tenure was "poorly timed" and allow the reorg for this tenure, no matter how long the tenure had actually been live on the canonical chain relative to the rest of the network's view. This breaks the equality the timing guard is supposed to enforce: "only tenures whose first block was signed shortly before the next sortition may be reorged." A signer whose own bookkeeping for that tenure happens to lack an `approved_time` (through rejection, a race between validation and proposal arrival, or restart/state loss) effectively has the guard disabled for that tenure and will sanction (and record as `superseded`, via `mark_tenure_superseded`) a reorg of a tenure that other, fully-informed signers would correctly refuse.

This is directly analogous to the reported bug class: a decision-critical value (`proposal_to_sortition`, the analog of the manipulable price) is derived from state that is cheap and easy for the local evaluation path to end up in a degenerate/absent condition (analogous to a flash-crashed price), and the code's fallback silently resolves that degenerate case in the direction that favors approval instead of treating it as "unknown" (which the sibling branch two lines above correctly does by returning `Ok(false)`).

### Impact Explanation
This lets an individual signer sanction (record as superseded) and subsequently sign a tenure-change block that reorgs an established, globally-accepted tenure that it should have refused — i.e., a signer can end up signing a conflicting/non-canonical replacement of a tenure the rest of the network still considers live, purely because of a gap in its own local bookkeeping rather than the actual proposal timing. Per the review rules this maps to the Critical category: "a signer signing an invalid, non-canonical, or conflicting block." It also permanently marks the honestly-mined tenure as `superseded` in this signer's DB (`mark_tenure_superseded`), which subsequently voids its own prior signature over that tenure as a conflict guard, compounding the effect for any later evaluation cycle by this signer [7](#0-6) .

### Likelihood Explanation
No majority of signers, no other signer's key, and no auth token are required — a single signer independently evaluates this function and can independently reach the flawed conclusion. The triggering condition (a `BlockInfo` present but `approved_time` unset) is reachable whenever this signer rejected the tenure's first block, or its block-validation response for that proposal had not yet completed/settled before the conflicting reorg proposal was evaluated — both are states any one-slot miner (or ordinary asynchronous message ordering) can bring about without collusion, by simply timing its reorging block proposal to race a given signer's validation of the prior tenure's first block, or by submitting a transaction/block that a specific signer will reject (e.g., via `problematic_txs` or replay-set differences) while the rest of the network accepts it.

### Recommendation
Do not default `proposal_to_sortition` to `0` when `approved_time` is `None`. An absent `approved_time` on an existing `BlockInfo` record means "this signer has no reliable timing information for this block," not "the block arrived late." Treat this case the same as the "no local knowledge" case a few lines above — return `Ok(false)` (refuse the reorg) or explicitly re-fetch/derive the timing from the node (e.g., via `proposed_time`/burn-block records) rather than substituting a value that always satisfies the "poorly timed" branch.

### Proof of Concept
1. A miner proposes tenure T's first block B. Signer S receives and evaluates B but rejects it (for a reason unrelated to timing, e.g. a transaction it considers problematic), so its `BlockInfo` for B is stored with `approved_time = None`. The rest of the signer set accepts B, and it becomes the tenure's single globally accepted block.
2. Before the next sortition, the same or a colluding miner proposes a new tenure-change block whose sortition does not build on T (i.e., it reorgs T).
3. Signer S runs `check_parent_tenure_choice`. `get_globally_accepted_block_count_in_tenure(T) == 1`, so it passes the ">1" guard. `get_first_approved_block_in_tenure(T)` returns S's own `BlockInfo` for B (it exists, since S evaluated and stored it), with `approved_time == None`.
4. The code takes the `else` branch at `stacks-signer/src/chainstate/mod.rs:255-257`, setting `proposal_to_sortition = 0`, which is always `< first_proposal_burn_block_timing`, so the reorg is sanctioned for T on signer S — even though T was in fact mined and accepted by the network well before the timeout window, and other signers (who have `approved_time` set for B) would correctly refuse the same reorg.
5. Signer S records T as superseded and is now willing to sign the reorging tenure-change block, diverging from the timing-based consensus the rest of the signer set is applying.
