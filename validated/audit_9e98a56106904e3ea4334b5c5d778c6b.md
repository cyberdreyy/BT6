### Title
Unbounded, unvalidated peer-reported `tenure_extend_timestamp` / `tenure_extend_read_count_timestamp` values are aggregated without staleness or sanity checks - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The oracle report's core defect is: a value received from an external/remote source is trusted and acted on without checking that it is fresh, bounded, or sane (staleness/zero checks missing). The analogous pattern exists in `StackerDBListener::update_idle_timestamp` / `update_read_count_timestamp`, which ingest the `tenure_extend_timestamp` and `tenure_extend_read_count_timestamp` fields carried inside every signer's `BlockResponse` (`Accepted` or `Rejected`) and fold them into a weighted-threshold computation (`find_weighted_timestamp_by_threshold`) that determines when the coordinator will accept a miner's tenure-extend request.

### Finding Description
Each signer's `BlockResponse` message carries a self-reported `tenure_extend_timestamp` / `tenure_extend_read_count_timestamp` (`BlockResponseData`, defined in `libsigner/src/v0/messages.rs:1543-1557`). When the node's `StackerDBListener` processes an `Accepted` or `Rejected` response, it unconditionally records this timestamp: [1](#0-0) 

The only "validation" performed is `if timestamp <= existing_info.timestamp { return; }` — i.e., monotonic-increase per signer. There is no check that:
- the timestamp is not implausibly far in the future (e.g., `u64::MAX`, as literally exercised in a test at `stacks-node/src/tests/signer/v0/mod.rs:9058-9063`, `get_epoch_time_secs().saturating_add(u64::MAX)`),
- the timestamp is not stale/zero, or
- the timestamp bears any relation to the current wall-clock time or to the block/tenure it claims to be about.

These per-signer timestamps are then fed into the weighted aggregate: [2](#0-1) 

`find_weighted_timestamp_by_threshold` sorts all reported timestamps ascending and returns the first one whose cumulative signer weight crosses `weight_threshold` (70%). This value directly drives `get_tenure_extend_timestamp`/`get_read_count_extend_timestamp`, which gate whether the coordinator will honor a miner's tenure-extend attempt (see `signer_coordinator.rs` usages and `docs/signer-flows.md` description of `tenure_idle_timeout`/`read_count_idle_timeout` semantics). Exactly like the oracle bug — where a stale or zero price is blindly trusted — this code blindly trusts a gossip-delivered numeric field from a remote party with no upper/lower bound, freshness, or plausibility check before using it in a security/liveness-relevant threshold computation.

### Impact Explanation
A single misbehaving or buggy signer instance (one slot, delivered purely via ordinary StackerDB gossip - no majority collusion, no key/access requirement beyond being a registered signer for that reward cycle) can inject an out-of-range timestamp (e.g., `u64::MAX`, or a timestamp far in the past) into its own `BlockResponse.response_data.tenure_extend_timestamp`. That value is stored verbatim per-signer keyed by that signer's public key, with no clamp. While a single signer's own reported value cannot unilaterally cross the 70% weight threshold, the complete absence of a sanity/staleness bound means:
- the field can carry arbitrary attacker-chosen data that is only ever checked for "monotonic increase," not plausibility, so a corrupted/faulty signer's timestamp poisons the aggregate computation for its own weight-share indefinitely (a stale/garbage value can never be corrected downward per signer, since only strictly-increasing updates are accepted),
- this matches the "acting on a stale/unvalidated threshold" pattern that is explicitly called out as a High-impact class in this repo's model, since the tenure-extend gating logic acts on an aggregate built from unvalidated inputs.

### Likelihood Explanation
The trigger requires no privileged access: any single registered signer's StackerDB relay for `BlockResponse` accepts and forwards these fields to the node, and the node accepts and stores them without validation as shown above. It is directly reachable via the standard signer→StackerDB→node gossip path used for every signed/rejected block, and the test suite itself demonstrates that fields such as `tenure_extend_timestamp` can be set to `get_epoch_time_secs().saturating_add(u64::MAX)` and successfully accepted by the node-side listener (`stacks-node/src/tests/signer/v0/mod.rs:9058-9063`), confirming no bound is enforced.

### Recommendation
Bound and sanity-check `tenure_extend_timestamp` and `tenure_extend_read_count_timestamp` in `update_idle_timestamp`/`update_read_count_timestamp` (or earlier, at message ingestion) before folding them into the weighted-threshold computation — e.g., reject/clamp values that are more than a configured multiple of `tenure_idle_timeout`/`read_count_idle_timeout` beyond "now," and reject values that are zero or clearly stale relative to the block/tenure they accompany.

### Proof of Concept
1. A registered signer (or a compromised/buggy one) sends a normal `BlockResponse::Accepted` (or `Rejected`) message over its StackerDB slot with `response_data.tenure_extend_timestamp = get_epoch_time_secs().saturating_add(u64::MAX)` (saturates to `u64::MAX`), exactly as constructed in the existing test helper at `stacks-node/src/tests/signer/v0/mod.rs:9058-9063`.
2. `StackerDBListener::run` receives this message, and for slot `slot_id`, calls `self.update_idle_timestamp(signer_pubkey, tenure_extend_timestamp, signer_entry.weight)` at `stacks-node/src/nakamoto_node/stackerdb_listener.rs:472-477` (or the analogous rejection path at lines 576-581), with no validation of the value.
3. `update_idle_timestamp` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:614-631`) accepts the value unconditionally (only checking it's larger than the previous recorded value for that signer) and stores it in `signer_idle_timestamps`.
4. This corrupted, unbounded entry then participates in `find_weighted_timestamp_by_threshold` (lines 794-816), permanently skewing that signer's contribution to the tenure-extend threshold computation with no mechanism to detect or discard the implausible value.

            .lock()
            .expect("FATAL: failed to lock idle timestamps");

        // Check the current timestamp for the given signer_pubkey

            }
