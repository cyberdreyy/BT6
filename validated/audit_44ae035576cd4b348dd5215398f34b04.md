## Title
Stale confirmations from deleted multisig keys count toward `num_confirmations`, allowing request execution below the live threshold - (`multisig/src/lib.rs`)

### Summary
The `confirm` function in `multisig/src/lib.rs` counts confirmations stored per `request_id` against `num_confirmations` without verifying that every confirming public key is still an active access key on the account. When a key is removed via `DeleteKey`, only requests *originally added* by that key (`signer_pk == pk`) have their confirmations wiped; confirmations that key placed on *other* pending requests (added by a different signer) are left untouched. This lets a request execute with a confirmation count that includes a key no longer authorized to act for the account.

### Finding Description
`confirm()` decides whether to execute a request purely by comparing the size of the stored `confirmations` set to `self.num_confirmations`: [1](#0-0) 

The only cleanup of stale confirmations happens in `execute_request`'s `DeleteKey` branch, and it is scoped to requests whose **`signer_pk`** (the account that originally called `add_request`) equals the deleted key — not to requests the deleted key merely *confirmed*: [2](#0-1) 

`MultiSigRequestWithSigner` only stores the adder's `signer_pk`; the set of confirmers for a request is tracked separately in `self.confirmations`, and this map is never scanned/pruned for entries belonging to a just-deleted key: [3](#0-2) 

The binding this breaks is: `confirmations counted for a request == confirmations from currently authorized (live) keys`. After a `DeleteKey` execution, this equality no longer holds for any pending request that the removed key confirmed but did not add — its stale confirmation still counts.

### Impact Explanation
Consider a 2-of-3 multisig. Key C confirms a pending transfer request R (added by key A, so `R.signer_pk == A`), bringing confirmations to {A, C} (2 of 3, one short of an already-satisfied threshold if `num_confirmations=2` — adjust to a 3-of-N example below for clarity):

Take `num_confirmations = 2`, members {A, B, C}. Key C confirms request R that key A added → `confirmations(R) = {C}` (A didn't confirm, only added). The account then legitimately removes key C via a `DeleteKey` request (a separate, properly-confirmed request), because C is compromised or an ex-employee. `DeleteKey`'s cleanup only removes requests where `signer_pk == C`; R's `signer_pk` is A, so `confirmations(R) = {C}` is left in storage. Key B now calls `confirm(R)`: `confirmations.len() + 1 = 2 >= num_confirmations(2)` → **executes**, even though the current live signer set is {A, B} and C's confirmation should have been invalidated the moment C was removed. The executed request is authorized by only one currently-valid key (B) plus a phantom confirmation from a removed key — i.e., the request is executed below the real live-member threshold, matching the report's core class of "claims counted vs. reality no longer matching, and a party settles/executes on it."

This can move funds (`Transfer`, `FunctionCall` with deposit, `DeployContract`) out of the multisig account with insufficient live authorization, which maps to the Critical impact bucket ("a multisig request executed below threshold").

### Likelihood Explanation
Requires only ordinary, expected multisig operation: (1) a key confirms a request without being its adder, (2) that same key is later removed for any routine reason (rotation, compromise response, offboarding), (3) the original request remains pending past the key's removal, and (4) any remaining live signer(s) later confirm it. No malicious deployment, redeploy, or foundation/victim-key compromise is needed beyond the normal multisig membership churn the contract is designed to support — this is a realistic operational sequence, not a contrived edge case.

### Recommendation
When executing `DeleteKey` (and analogously in `multisig2`'s `DeleteMember`), iterate `self.confirmations` for **all** pending requests and remove the deleted key/member from each confirmation set (not just requests it authored), decrementing any cached counts accordingly. Alternatively, validate at `confirm()` time that every public key in the stored confirmation set is still present among the account's current access keys before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy multisig with `num_confirmations = 2` and keys `{A, B, C}`.
2. As A: `add_request(transfer_request)` → `request_id = R` (added, unconfirmed).
3. As C: `confirm(R)` → `confirmations(R) = {C}` (1 of 2, not yet executed).
4. As A and B (2-of-2 threshold on this separate action): submit and confirm a `DeleteKey{public_key: C}` request → executes; `execute_request`'s `DeleteKey` branch only clears confirmations/requests where `signer_pk == C`; since `R.signer_pk == A`, `confirmations(R)` remains `{C}`.
5. As B: `confirm(R)` → `confirmations.len() (1) + 1 = 2 >= num_confirmations (2)` → `execute_request(R)` runs, transferring funds, even though only B (a single live key) and a now-deleted key C actually authorized it. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
