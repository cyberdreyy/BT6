### Title
Stale confirmations from removed members counted toward `num_confirmations` threshold, allowing execution with fewer live-member approvals - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` compares `confirmations.len() as u32 + 1 >= self.num_confirmations` against the raw size of a stored `HashSet<String>` of member identifiers, never re-validating that each stored entry still belongs to a current member. When a member who already confirmed a pending request is later removed via `DeleteMember`, their stale confirmation string remains inside that other request's `confirmations` set and still counts toward the quorum, allowing the request (e.g. a `Transfer`) to execute with fewer *live* confirmations than `num_confirmations` requires.

### Finding Description
The invariant that should hold is:
`|{ c ∈ confirmations(request_id) : c ∈ members }| + 1 ≥ num_confirmations`
i.e., only confirmations from accounts/keys that are *still* members should count. What the code actually checks in [1](#0-0)  is `confirmations.len() as u32 + 1 >= self.num_confirmations`, which counts every string ever inserted into the stored `HashSet`, regardless of whether that member is still in `self.members`.

`delete_member`, invoked from `execute_request`'s `DeleteMember` branch, only purges confirmations for requests that the removed member themself originally authored: [2](#0-1)  It filters `self.requests` by `r.member == member` (the request's *author*) and clears confirmations only for those requests. It performs no scan of `confirmations` maps for *other* pending requests where the removed member had merely cast a confirmation (not authored). Those stale entries survive unaffected.

`current_member()` (used by `assert_valid_request`/`confirm`) only validates the *caller* of the current `confirm` invocation against the live member set [3](#0-2) ; it never re-validates the previously stored confirmations already sitting in the `HashSet`.

Exploit flow (num_confirmations = 3, members = {A, B, C, D}):
1. A creates and self-confirms request R2 = `Transfer{amount, receiver_id=attacker}` (targets an external/attacker-controlled account). `confirmations(R2) = {A}`.
2. C confirms R2. `confirmations(R2) = {A, C}` (size 2, still below threshold of 3).
3. Separately, D creates request R1 = `DeleteMember{C}` (self-targeted, receiver_id = current_account_id). A and B confirm R1, reaching 3 confirmations (D, A, B) and executing `delete_member(C)`. This removes C from `self.members`, but only purges requests *authored* by C — R2 was authored by A, so R2's confirmation set `{A, C}` is left untouched even though C is no longer a member.
4. B now confirms R2. `confirmations(R2).len() (=2) + 1 = 3 >= num_confirmations (3)` → the request executes and `Transfer` fires to the attacker-controlled `receiver_id`.

At execution time the *live* confirmers were only A and B (2 of 3 required); C's confirmation is stale from a deleted member yet still counted as valid. None of the existing guards catch this: `assert_valid_request` only checks the calling member is live, `current_member()` is only evaluated for the current caller, and `delete_member` does not sweep stale confirmations out of unrelated requests.

### Impact Explanation
NEAR is moved out of the multisig account via a `Transfer` action that was approved by only 2 live members although `num_confirmations = 3`, i.e. the exact Critical scenario "a multisig request executed below `num_confirmations` live members." This lets funds be moved to an account never authorized by the required live quorum. The pattern is repeatable for any pending, under-threshold request whenever a confirming member is subsequently removed before the quorum is met, and generalizes to other value-affecting actions (e.g. `FunctionCall` with a deposit, `AddKey`/`AddFullAccessKey` to receiver, `DeployContract`) bundled in the stale request.

### Likelihood Explanation
This requires no attacker privilege beyond being the intended `receiver_id` of a pending request that legitimate members are in the process of confirming, combined with an ordinary, foreseeable operational event: removing a member (e.g. key rotation, offboarding) while other requests are still pending confirmation. No special timing precision beyond normal multisig operations is needed — it's a state-management bug that will trigger under realistic multisig maintenance workflows, not a contrived edge case.

### Recommendation
When counting confirmations in `confirm`, filter the stored `HashSet` against `self.members` before comparing to `num_confirmations` (i.e., compute `confirmations.iter().filter(|c| self.members contains parsed member).count()`), or proactively purge any member's confirmation entries from *all* pending requests (not just requests they authored) inside `delete_member`.

### Proof of Concept
```rust
// multisig2/src/lib.rs, inside #[cfg(test)] mod tests
#[test]
fn test_stale_confirmation_after_member_removal_executes_below_threshold() {
    let amount = 1_000;
    let a = AccountId::new_unchecked("a".to_string());
    let b = AccountId::new_unchecked("b".to_string());
    let c = AccountId::new_unchecked("c".to_string());
    let d = AccountId::new_unchecked("d".to_string());
    let attacker = AccountId::new_unchecked("attacker".to_string());

    let members = vec![
        MultisigMember::Account { account_id: a.clone() },
        MultisigMember::Account { account_id: b.clone() },
        MultisigMember::Account { account_id: c.clone() },
        MultisigMember::Account { account_id: d.clone() },
    ];

    testing_env!(context_with_account(a.clone(), amount));
    let mut ms = MultiSigContract::new(members, 3);

    // Step 1: A creates R2 = Transfer to attacker, self-confirms.
    let r2 = MultiSigRequest {
        receiver_id: attacker.clone(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    };
    let r2_id = ms.add_request_and_confirm(r2);
    assert_eq!(ms.confirmations.get(&r2_id).unwrap().len(), 1);

    // Step 2: C confirms R2 -> stored count = 2, below threshold(3).
    testing_env!(context_with_account(c.clone(), amount));
    ms.confirm(r2_id);
    assert_eq!(ms.confirmations.get(&r2_id).unwrap().len(), 2);

    // Step 3: D creates + A, B confirm R1 = DeleteMember{C} -> executes, removes C.
    testing_env!(context_with_account(d.clone(), amount));
    let r1 = MultiSigRequest {
        receiver_id: a.clone(), // current_account_id in test harness is `alice()`/current account,
        // adjust receiver_id to env::current_account_id() per context_with_account setup
        actions: vec![MultiSigRequestAction::DeleteMember {
            member: MultisigMember::Account { account_id: c.clone() },
        }],
    };
    let r1_id = ms.add_request_and_confirm(r1);
    testing_env!(context_with_account(a.clone(), amount));
    ms.confirm(r1_id);
    testing_env!(context_with_account(b.clone(), amount));
    ms.confirm(r1_id); // 3rd confirmation -> executes, C removed from members

    assert!(!ms.get_members().contains(&MultisigMember::Account { account_id: c.clone() }));
    // Stale confirmation from C is still present in R2's confirmation set:
    assert!(ms.confirmations.get(&r2_id).unwrap().contains(&MultisigMember::Account { account_id: c.clone() }.to_string()));

    // Step 4: B confirms R2 -> stored len(2)+1 = 3 >= num_confirmations(3) -> EXECUTES,
    // even though only A and B are live confirmers (2 < 3 required live confirmations).
    ms.confirm(r2_id);
    assert_eq!(ms.requests.len(), 0); // request executed/removed despite only 2 live confirmations
}
```
This demonstrates the binding `live_confirmations + 1 ≥ num_confirmations` is false (2 ≥ 3 fails) while the code's actual check `stored_confirmations.len() + 1 ≥ num_confirmations` is true (3 ≥ 3), causing unauthorized execution of the fund-moving `Transfer`. [4](#0-3) [5](#0-4)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);

            .unwrap_or_else(|| env::panic_str("Must be validated above"));

            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
