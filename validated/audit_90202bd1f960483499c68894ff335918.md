### Title
Bridge deletion uses raw `c.Param` name instead of normalized `taskType`, bypassing the jobs-in-use conflict check on case mismatch - ([File: core/web/bridge_types_controller.go])

### Summary
`BridgeTypesController.Destroy` normalizes the requested bridge name via `bridges.ParseBridgeName`, which lowercases it, and correctly uses `taskType` to look up and delete the bridge row. However, the "is this bridge still used by jobs" check calls `btc.App.JobORM().FindJobIDsWithBridge(ctx, name)` with the raw, un-normalized `c.Param("BridgeName")` instead of `taskType`. Since bridge names are always persisted/referenced in lowercase form (`BridgeName` is normalized by `ParseBridgeName` everywhere a bridge name is parsed from user input, including in job/pipeline task specs), a request whose case differs from the stored/normalized form causes the in-use lookup to silently return no results, letting the bridge be deleted even though jobs reference it.

### Finding Description
In `Destroy` (core/web/bridge_types_controller.go:195-232):
- `taskType, err := bridges.ParseBridgeName(name)` lowercases the input (core/bridges/bridge_type.go:154-161).
- `orm.FindBridge(ctx, taskType)` correctly looks up the bridge with the normalized (lowercase) name.
- But the jobs-in-use check is: `jobsUsingBridge, err := btc.App.JobORM().FindJobIDsWithBridge(ctx, name)` — using the raw `name` variable (the unmodified `c.Param`) rather than `taskType.String()`.

Because bridge task types referenced from job/pipeline specs are always stored/compared in their normalized (lowercased) form (the same `ParseBridgeName` normalization is applied when bridge task specs are parsed), a job that references a bridge as e.g. `mybridge` will not be found by a query using the literal, differently-cased string the caller passed in the URL (e.g. `MyBridge` or `MYBRIDGE`). If `FindJobIDsWithBridge` performs an exact-match (case-sensitive) query against the stored, normalized bridge name column, then supplying a differently-cased `BridgeName` path parameter causes the lookup to return an empty job list, even though the identically-referenced bridge (matched by `FindBridge` via `taskType`) is actively used by a job. The `>0` gate at line 220 is then bypassed and the bridge row is deleted via `orm.DeleteBridgeType(ctx, &bt)` at line 224.

This is a REQUEST_BINDING inconsistency: two different representations of "the same" bridge name are used within the same handler — the normalized `taskType` for existence/deletion, and the raw, attacker-supplied `name` for the safety check that is supposed to prevent deleting a bridge still in use.

### Impact Explanation
Successful exploitation lets an authorized bridge-management (edit-role) caller delete a bridge that is still bound to one or more active jobs, without triggering the intended HTTP 409 conflict/protection. Once deleted, any job spec that references that bridge task will fail at execution time (breaking the isolation/guarantee that the delete-time check is meant to enforce), causing job/pipeline runs to error out unexpectedly. This is a logic/availability defect rather than a cross-tenant/privilege-escalation bug, since the caller must already hold bridge-management permissions; the scoped impact is unintended breakage of job execution reliability for anyone depending on the affected bridge.

### Likelihood Explanation
Requires only an authenticated caller with sufficient role to hit the bridge `DELETE` endpoint (edit role) — no additional privilege is needed. The exploit is trivial and fully repeatable: create/observe a bridge whose canonical (lowercased) name is used by a job, then send the delete request using a different letter-casing in the URL path parameter. No timing or race condition is required.

### Recommendation
Use the normalized `taskType.String()` (or `taskType` directly if the ORM method accepts `bridges.BridgeName`) instead of the raw `name` when calling `FindJobIDsWithBridge`, so the in-use check is performed against the same normalized identity used for `FindBridge`/`DeleteBridgeType`:
```go
jobsUsingBridge, err := btc.App.JobORM().FindJobIDsWithBridge(ctx, taskType.String())
```

3. Call `BridgeTypesController.Destroy` with `c.Param("BridgeName") = "MyBridge"` (mixed case, different from the lowercase form used internally by the job's stored task spec/query key).

```go
// Destroy removes a specific Bridge.
func (btc *BridgeTypesController) Destroy(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	orm := btc.App.BridgeORM()
	bt, err := orm.FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, fmt.Errorf("error searching for bridge: %w", err))
		return
	}
	jobsUsingBridge, err := btc.App.JobORM().FindJobIDsWithBridge(ctx, name)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, fmt.Errorf("error searching for associated v2 jobs: %w", err))
		return
	}
	if len(jobsUsingBridge) > 0 {
		jsonAPIError(c, http.StatusConflict, fmt.Errorf("can't remove the bridge because jobs %v are associated with it", jobsUsingBridge))
		return
	}
```

```go
// ParseBridgeName returns a formatted Task type.
func ParseBridgeName(val string) (BridgeName, error) {
	if !bridgeNameRegex.MatchString(val) {
		return "", fmt.Errorf("task type validation: name %v contains invalid characters", val)
	}

	return BridgeName(strings.ToLower(val)), nil
}
```
