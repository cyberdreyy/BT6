### Title
Type Confusion via Unchecked Enum Transmute in `loader_v4_get_state()` — ([File: svm/src/program_loader.rs])

### Summary
`svm/src/program_loader.rs` contains a `loader_v4_get_state()` helper that reinterprets raw, attacker-controlled account bytes as a `&LoaderV4State` reference via `std::mem::transmute`, with no validation of the `status` field's enum discriminant before it is read/matched. This mirrors the root cause of CVE-2026-22796 (`PKCS7_digest_from_attributes()`): a tagged-union/enum value is consumed straight out of untrusted bytes without checking that the tag is one of the legal variants, producing type confusion / undefined behavior instead of a controlled DoS.

### Finding Description
`loader_v4_get_state()` takes an account's raw data slice and blindly transmutes it into `&LoaderV4State`: [1](#0-0) 

Unlike the neighboring Loader-V3 path, which uses `bincode::deserialize(...)` to parse `UpgradeableLoaderState` (bincode's derived deserializer validates enum discriminants and returns an `Err` for out-of-range tags): [2](#0-1) 

the Loader-V4 path does a raw `transmute` of the byte buffer into a Rust struct containing the `LoaderV4Status` enum field, and immediately reads that field: [3](#0-2) [4](#0-3) 

`LoaderV4Status` is a plain fieldless Rust enum (`Retracted`/`Deployed`/`Finalized`) with a small set of valid bit-pattern discriminants. Per Rust's language rules, constructing (even just holding) an enum value whose underlying bits do not correspond to a declared variant is instant undefined behavior — this is a stronger and more dangerous class of bug than the OpenSSL analog, because `matches!(state.status, LoaderV4Status::Retracted)` gives the optimizer license to generate branchless/jump-table code assuming the discriminant is always valid; an out-of-range value can cause an out-of-bounds jump, a validator panic, or divergent behavior depending on compiler version/target.

**Reachability**: This code is invoked whenever the SVM loads/refreshes any account whose `owner` equals the `loader_v4` program id, via `load_program_accounts()` and `get_program_deployment_slot()`: [5](#0-4) [6](#0-5) 

both of which are reached from `filter_executable_program_accounts()`, which is invoked for every account key referenced by any submitted transaction (not gated behind privileged/operator access): [7](#0-6) 

An unprivileged sender can populate an account with arbitrary attacker-chosen bytes while it is owned by *their own* program, then reassign the account's `owner` field to `loader_v4::id()` (Solana's account model allows the current owning program to freely rewrite the `owner` field via `AccountInfo::assign()`/direct owner mutation without requiring the new owner to be a live/functional program). The account's previously-written data persists across the ownership change, so the attacker fully controls the bytes that later get transmuted into `LoaderV4State`, including an out-of-range `status` discriminant.

### Impact Explanation
Because the malformed `status` value is read deterministically by every validator processing the same transaction (this is on the hot SVM account-loading path used during normal execution, not a peer-only or mock-only code path), the resulting undefined behavior is consensus-relevant:
- Best case: an immediate validator crash/panic when loading the corrupted account (`filter_executable_program_accounts` / `load_program_with_pubkey` are called during normal transaction processing), causing a transaction-triggered denial of service across the fleet.
- Worse case: compiler-dependent UB (e.g. reading an out-of-range value used in `matches!`/pattern matching) could yield different observable behavior on different validator builds/architectures, risking state/consensus divergence between validators — one of the accepted "concrete" outcomes for this class of report.

### Likelihood Explanation
High feasibility for an unprivileged attacker:
1. No signature/permission beyond normal instruction submission is required.
2. Constructing an account with attacker-controlled bytes then reassigning its owner to an arbitrary pubkey (including `loader_v4::id()`) is a standard, well-understood Solana account-model capability available to any deployed program the attacker controls.
3. Simply having any transaction reference that account (as a writable account, or attempted CPI target) is sufficient to route through `filter_executable_program_accounts` → `load_program_accounts`/`get_program_deployment_slot` → `loader_v4_get_state`.

### Recommendation
Replace the raw `transmute` in `loader_v4_get_state()` with a validating parse: read the `status` field as a raw integer first, and explicitly check/convert it into `LoaderV4Status` via `TryFrom`/an exhaustive `match` over the legal numeric range before constructing/returning any typed `LoaderV4State` reference (or use a checked deserialization approach consistent with the Loader-V3 `bincode::deserialize` path), rejecting the account as `InvalidAccountData` on an out-of-range discriminant, just as is already done for the `UpgradeableLoaderState` (V3) path.

### Proof of Concept
1. Attacker deploys/uses a program `P` they control.
2. `P` creates and owns an account `A` and writes bytes into `A.data` such that the first `LoaderV4State::program_data_offset()` bytes decode as a `LoaderV4State` layout with an out-of-range value in the `status` field's bit position (any value other than the enum's valid discriminants, e.g. all `0xFF`).
3. `P` reassigns `A`'s owner to `loader_v4::id()` (owner mutation by the current owning program), preserving `A`'s attacker-written data.
4. Attacker submits a subsequent transaction referencing `A` (e.g., listing it among the transaction's account keys, or as an invoke target), triggering `filter_executable_program_accounts()` → `load_program_accounts()`/`get_program_deployment_slot()` → `loader_v4_get_state(A.data())`, which transmutes the corrupted bytes into `&LoaderV4State` and reads `state.status` without validation.
5. This is executed by every validator processing the transaction, exercising Rust UB on an invalid enum discriminant.

Note: I could not fetch the exact upstream `LoaderV4State`/`LoaderV4Status` struct/enum definitions (they live in the `solana-loader-v4-interface` crate, which was outside what the index returned), so the exact byte offsets/discriminant values for a working exploit payload are not verified here; the vulnerable transmute-without-validation pattern itself is confirmed directly in `svm/src/program_loader.rs`.

pub(crate) fn get_program_deployment_slot<CB: TransactionProcessingCallback>(
    callbacks: &CB,
    program: &AccountSharedData,
    loader: ProgramCacheEntryOwner,
) -> TransactionResult<Slot> {
    match loader {
        ProgramCacheEntryOwner::LoaderV1 | ProgramCacheEntryOwner::LoaderV2 => Ok(0),
        ProgramCacheEntryOwner::LoaderV3 => {
            if let Ok(UpgradeableLoaderState::Program {
                programdata_address,
            }) = bincode::deserialize(program.data())
            {
                let (programdata, _slot) = callbacks
                    .get_account_shared_data(&programdata_address)
                    .ok_or(TransactionError::ProgramAccountNotFound)?;
                if let Ok(UpgradeableLoaderState::ProgramData {
                    slot,
                    upgrade_authority_address: _,
                }) = bincode::deserialize(programdata.data())
                {
                    return Ok(slot);
                }
            }
            Err(TransactionError::ProgramAccountNotFound)
        }
        ProgramCacheEntryOwner::LoaderV4 => {
            let state = loader_v4_get_state(program.data())
                .map_err(|_| TransactionError::ProgramAccountNotFound)?;
            Ok(state.slot)
        }
        ProgramCacheEntryOwner::NativeLoader => unreachable!(),
    }

pub fn filter_executable_program_accounts<'a, CB: TransactionProcessingCallback>(
    callbacks: &CB,
    program_cache_for_tx_batch: &ProgramCacheForTxBatch,
    keys: impl Iterator<Item = &'a Pubkey>,
    check_program_deployment_slot: bool,
) -> Vec<ProgramToLoad<'a>> {
    let mut result = Vec::new();
    for account_key in keys {
        if let Some(cache_entry) = program_cache_for_tx_batch.find(account_key) {
            cache_entry.stats.uses.fetch_add(1, Ordering::Relaxed);
        } else if let Some((account, last_modification_slot)) =
            callbacks.get_account_shared_data(account_key)
        {
            let loader = if loader_v4::check_id(account.owner()) {
                ProgramCacheEntryOwner::LoaderV4
            } else if bpf_loader_upgradeable::check_id(account.owner()) {
                ProgramCacheEntryOwner::LoaderV3
            } else if bpf_loader::check_id(account.owner()) {
                ProgramCacheEntryOwner::LoaderV2
            } else if bpf_loader_deprecated::check_id(account.owner()) {
                ProgramCacheEntryOwner::LoaderV1
            } else {
                continue;
            };
            let match_criteria = if check_program_deployment_slot {
                get_program_deployment_slot(callbacks, &account, loader)
                    .map_or(ProgramCacheMatchCriteria::Tombstone, |slot| {
                        ProgramCacheMatchCriteria::DeployedOnOrAfterSlot(slot)
                    })
            } else {
                ProgramCacheMatchCriteria::NoCriteria
            };
            result.push(ProgramToLoad {
                program_id: account_key,
                loader,
                match_criteria,
                last_modification_slot,
            });
        }
    }
    result
}

// Plucked from the now-removed Loader V4 program library.
fn loader_v4_get_state(data: &[u8]) -> Result<&LoaderV4State, InstructionError> {
    unsafe {
        let data = data
            .get(0..LoaderV4State::program_data_offset())
            .ok_or(InstructionError::AccountDataTooSmall)?
            .try_into()
            .unwrap();
        Ok(std::mem::transmute::<
            &[u8; LoaderV4State::program_data_offset()],
            &LoaderV4State,
        >(data))
    }
}
