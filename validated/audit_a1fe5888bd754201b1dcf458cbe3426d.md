Confirmed analog: renaming a bridge leaves a stale cache entry under the old name in `core/bridges/cache.go`.

### Title
Stale bridge cache entry under old name persists after bridge rename, causing old bridge credentials/URL to remain resolvable - (File: core/bridges/cache.go)

### Summary
`Cache.UpdateBridgeType` in `core/bridges/cache.go` stores the updated `BridgeType` in `bridgeTypesCache` keyed by `bt.Name` (the *new* name) but never removes the stale entry keyed by the bridge's *old* name when a rename occurs, analogous to `ReferralStorage.setCodeOwner` failing to update the reverse `userCode` mapping when ownership/identity changes.

### Finding Description
`BridgeTypeRequest` allows a bridge to be renamed via its `Name` field [1](#0-0) , and `UpdateBridge`/`Update` controller endpoints accept the old name as the lookup key while applying a new name from the request body [2](#0-1) . The underlying `orm.UpdateBridgeType` (not fully shown here, but referenced in `orm.go`) rewrites the row, changing its primary key `name` in the `bridge_types` table.

The `Cache` wrapper, however, maintains an in-memory `sync.Map` (`bridgeTypesCache`) keyed by `BridgeName` to avoid DB round trips [3](#0-2) . On update it only stores the new entry:
```go
func (c *Cache) UpdateBridgeType(ctx context.Context, bt *BridgeType, btr *BridgeTypeRequest) error {
	if err := c.ORM.UpdateBridgeType(ctx, bt, btr); err != nil {
		return err
	}
	c.bridgeTypesCache.Store(bt.Name, *bt)
	return nil
}
``` [4](#0-3) 

Unlike `DeleteBridgeType`, which explicitly evicts the cache entry by name [5](#0-4) , `UpdateBridgeType` performs no eviction of the pre-rename key. Since `bt` is mutated in place by the ORM call (its `Name` field is overwritten to the new name before the cache `.Store` call), the cache is left holding the **old name → old `BridgeType` struct** entry indefinitely, alongside the new **new name → new `BridgeType`** entry. This is the same root-cause pattern as the referral-storage bug: a forward mapping is updated but a related/previous mapping key is not cleaned up, leaving the system in an inconsistent state.

### Impact Explanation
Any subsequent `FindBridge`/`FindBridges` call for the bridge's old name (used by `BridgeTask.Run` pipeline execution and other job-spec references to the old bridge name, e.g. jobs that haven't been repointed) will be served from the stale cache entry containing the old URL, `IncomingTokenHash`, `Salt`, and `OutgoingToken` rather than an error or the updated record [6](#0-5) . This can cause job pipeline runs to keep sending requests to an external adapter that has since been deprecated/renamed/repointed, using stale credentials, until the node process restarts and the in-memory cache is rebuilt from the DB. It does not directly enable session/token forgery by an unprivileged external party, but it is a concrete data-integrity/stale-state bug reachable by any operator with bridge-management edit privileges, and could confuse pipeline routing or leak stale authentication tokens tied to a name that should no longer be valid.

### Likelihood Explanation
Likelihood is moderate: it requires a privileged/admin-role user (bridge management requires edit access, enforced via `authenticateUserCanEdit` in the resolver [7](#0-6) ) to rename an existing bridge while it is still referenced by job specs under the old name, and for the node process not to be restarted afterward.

### Recommendation
In `Cache.UpdateBridgeType`, delete the stale cache entry for the pre-update name before/along with storing the new entry, mirroring the eviction logic already used in `DeleteBridgeType`:
```go
func (c *Cache) UpdateBridgeType(ctx context.Context, bt *BridgeType, btr *BridgeTypeRequest) error {
	oldName := bt.Name
	if err := c.ORM.UpdateBridgeType(ctx, bt, btr); err != nil {
		return err
	}
	if oldName != bt.Name {
		c.bridgeTypesCache.Delete(oldName)
	}
	c.bridgeTypesCache.Store(bt.Name, *bt)
	return nil
}
```

### Proof of Concept
1. Create bridge `bridge-a` (populates cache with key `bridge-a`).
2. Call `FindBridge(ctx, "bridge-a")` once to ensure it is cached [6](#0-5) .
3. Call `UpdateBridgeType` with a `BridgeTypeRequest{Name: "bridge-b", ...}` to rename the bridge; the ORM row is updated to name `bridge-b`, and the cache now stores an entry keyed `bridge-b` [4](#0-3) .
4. Call `FindBridge(ctx, "bridge-a")` again — because the old cache entry under key `bridge-a` was never deleted, this call returns the stale, pre-rename `BridgeType` (line 61-63 hits cache) instead of a not-found/DB-driven result, even though the DB row named `bridge-a` no longer exists.

func (c *Cache) FindBridge(ctx context.Context, name BridgeName) (BridgeType, error) {
	if bridgeType, ok := c.bridgeTypesCache.Load(name); ok {
		return bridgeType.(BridgeType), nil
	}

	ormResult, err := c.ORM.FindBridge(ctx, name)
	if err == nil {
		c.bridgeTypesCache.Store(ormResult.Name, ormResult)
	}

	return ormResult, err
}
