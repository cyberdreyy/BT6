### Title
Missing predecessor/owner check in `replace`/`clean` exports allows any account to race and overwrite migration state - ([File: state-manipulation/src/lib.rs])

### Summary
The `state-manipulation` contract's `replace` and `clean` `#[no_mangle]` exports write/remove arbitrary storage keys with no caller authorization check whatsoever. Because this contract is meant to be temporarily deployed on top of a live contract during an operator-driven migration, any unprivileged account can call `replace` (or `clean`) in the same block as the legitimate operator's migration call, and whichever transaction executes last determines the final on-chain state.

### Finding Description
The binding the design implicitly assumes is: `state_after_migration == operator_intended_state`. In reality the code enforces no such thing — `replace()` and `clean()` never check `predecessor_account_id`, never compare against an owner, and never validate the caller at all: [1](#0-0) [2](#0-1) 

Both functions simply deserialize the raw call input (base64 keys/values, or base64 keys to remove) and perform `storage_write`/`storage_remove` unconditionally: [3](#0-2) 

The README confirms the intended use: this WASM is deployed "into the account that already has another contract deployed to it" specifically to let an operator patch state during a migration, then presumably the real contract is redeployed afterward. There is no `assert_predecessor`, `assert_owner`, or any allow-list of the calling account in the entire file. Since the contract exposes `replace`/`clean` as ordinary public change methods, *any* account (not just the account's owner or the migration operator) can invoke them for as long as this WASM is the deployed code on that account. If an unprivileged attacker submits a `replace` transaction with attacker-chosen empty or malicious values for the same keys the operator is migrating, and it lands in the same block (or simply executes after the operator's legitimate write), the attacker's write silently wins and becomes the final state — directly corrupting whatever underlying contract state (e.g., balances, owner fields) this tool was patching.

No existing guard in the codebase (`assert_self()`, `assert_owner`, `is_promise_success()`, etc.) applies here because this contract has none of those checks implemented at all.

### Impact Explanation
Because this state-manipulation tool is deployed directly onto an account that holds real user/contract state (e.g., a lockup, staking pool, or multisig mid-migration), an attacker who successfully races the operator's write can overwrite storage keys with empty or attacker-chosen values. This can zero out balance fields, corrupt vesting/lockup accounting, or otherwise directly manipulate contract state in a way that leads to loss or misappropriation of funds recorded in that account's storage — matching the "Critical: direct manipulation of contract state, enabling theft of the account's funds" category. The attack is repeatable against any account on which this migration helper is deployed, for the entire window it remains deployed.

### Likelihood Explanation
The only precondition is that this `state-manipulation` WASM is the currently deployed code on the target account (a temporary, operator-chosen migration window) — no owner privileges, deposit, or special key are required by the attacker; a normal NEAR transaction calling `replace` or `clean` with attacker-supplied JSON suffices. Attacker cost is a single NEAR function call with base64-encoded key/value arguments, and the race only requires submitting the transaction so it is included in or near the same block as the operator's migration transaction — well within normal network conditions and repeatable for every account subjected to this migration procedure.

### Recommendation
Add an explicit caller authorization check at the top of both `replace` and `clean` (e.g., `assert_eq!(predecessor_account_id(), current_account_id())` or an explicit allow-listed owner/operator account read from state) so that only the account's own full-access-key holder or an authorized migration principal can invoke these exports, and consider requiring `assert_one_yocto()`-style signed intent plus removing the tool from state as soon as migration completes to shrink the exposure window.

### Proof of Concept
```rust
// cargo test (near-workspaces) plan, added to state-manipulation/src/lib.rs test mod
#[tokio::test]
async fn race_replace_overwrites_operator_migration() -> anyhow::Result<()> {
    let wasm = fs::read("res/state_manipulation.wasm").await?;
    let worker = workspaces::sandbox().await?;
    let contract = worker.dev_deploy(&wasm).await?;

    let attacker = worker.dev_create_account().await?;
    // create a distinct funded account acting as "operator" via a second full-access-signed call
    let operator = worker.root_account();

    let key = base64::encode(b"STATE");
    let legit_value = base64::encode(b"populated-value");
    let empty_value = base64::encode(b"");

    // Operator's legitimate migration write
    let op_call = operator
        .call(&worker, contract.id(), "replace")
        .args_json(&serde_json::json!({ "entries": [[key.clone(), legit_value.clone()]] }))?
        .max_gas();

    // Attacker's unprivileged call racing in the same block, overwriting with empty value
    let atk_call = attacker
        .call(&worker, contract.id(), "replace")
        .args_json(&serde_json::json!({ "entries": [[key.clone(), empty_value.clone()]] }))?
        .max_gas();

    // Fire both, attacker's lands after operator's within same/adjacent block
    let _ = op_call.transact().await?;
    let _ = atk_call.transact().await?;

    let state_items = contract.view_state(&worker, None).await?;
    let stored = state_items.get(&b"STATE".to_vec()).unwrap();

    // Binding under test: stored == operator_intended_value ("populated-value")
    // Actual: stored == attacker_value ("") — invariant broken, attacker's unprivileged
    // call overwrote the operator's legitimate migration write with no owner check.
    assert_eq!(stored, b""); // demonstrates the broken binding
    Ok(())
}
```
This demonstrates that an unprivileged account (no owner rights, no key on the target account) can call the unguarded `replace` export and have its write silently supersede the operator's legitimate migration write, directly corrupting the target account's contract state.

fn storage_write(key: &[u8], value: &[u8]) {

        near_sys::storage_write(

#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    #[derive(serde::Deserialize)]
    struct ReplaceInput<'a> {
        #[serde(borrow)]
        entries: Vec<(&'a str, &'a str)>,
    }

    let input = input().unwrap();
    let args: ReplaceInput = serde_json::from_slice(&input).unwrap();
    for (key, value) in args.entries {
        storage_write(
            &base64::decode(key).unwrap(),
            &base64::decode(value).unwrap(),
        );
    }
}
