## Title
Deleted multisig members' stale confirmations on other pending requests still count toward `num_confirmations` threshold - (File: `multisig2/src/lib.rs`)

### Summary
`confirm()` checks membership only at the moment a member signs a request, and adds that member's identity into a `confirmations` set stored per-request. When a member is later removed via `DeleteMember`, only the requests *created by* that member are purged; confirmations that member left on *other, still-open* requests (created by someone else) are never scrapped. Those stale confirmations continue to count toward `num_confirmations` when the request is eventually confirmed by others, effectively letting a request execute with fewer live/authorized confirmers than the current threshold requires.

### Finding Description
`confirm()` validates that the caller is a live member at call time via `current_member()`, then inserts the member's identity string into the `confirmations` set for that `request_id`, and later just checks `confirmations.len() + 1 >= num_confirmations` to decide whether to execute: [1](#0-0) 

`delete_member()` is only invoked from `execute_request` for the `DeleteMember` action, and its cleanup logic filters and removes *requests* whose `signer`/`member` field equals the removed member (i.e., requests that member itself created), and clears `num_requests_pk` for that member — but it never scans the `confirmations` LookupMap to strip that member's confirmation from other pending requests they had merely confirmed (not created): [2](#0-1) 

Because `confirmations` is a `LookupMap<RequestId, HashSet<String>>` keyed independently of membership, and the assert in `confirm()` only prevents the *same* key from confirming twice — not from a confirmation surviving membership revocation — a member that confirmed request A, then got removed via a separate request B, leaves their vote intact in A's confirmation set. Any subsequent live member confirming A merely needs `confirmations.len() + 1 >= num_confirmations`, which is satisfied using the stale, now-unauthorized vote.

### Impact Explanation
This breaks the intended equality: `confirmations recorded == confirmations from currently authorized members`. A multisig configured for `K` confirmations can execute an action (`Transfer`, `AddKey`, `FunctionCall`, `DeployContract`, `AddMember`/`DeleteMember`, etc.) with fewer than `K` *live* members' consent, because a removed member's earlier confirmation is still tallied. This matches the "multisig request executed below threshold" critical-impact category — funds can be transferred or keys/members changed by a set of currently-authorized signers smaller than the configured `num_confirmations`, i.e., an unauthorized move of NEAR or control of the account.

### Likelihood Explanation
This requires no special privilege beyond being (or having been) a legitimate multisig member at some point, and does not depend on any misconfiguration or the foundation. Any request with outstanding confirmations from a member who is subsequently removed (a routine multisig operation, e.g., rotating a compromised key or offboarding a member) will retain that stale vote automatically — no exploit-crafting needed beyond ordinary sequencing of `confirm` and `DeleteMember` requests. The bug is triggered by normal multisig lifecycle operations, so likelihood is significant given a multisig with rotating membership.

### Recommendation
When executing `DeleteMember`, iterate over all entries in `self.confirmations` and remove the deleted member's identity string from every request's confirmation set (not just requests created by that member). Alternatively, re-validate at `confirm()`/execution time that every entry in a request's `confirmations` set still corresponds to a current member of `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Multisig initialized with members `{A, B, C, D}` and `num_confirmations = 3`.
2. Member `A` creates Request `R1` (e.g., `Transfer` to some receiver) via `add_request_and_confirm`, giving `R1` one confirmation (from `A`). [3](#0-2) 
3. Member `B` confirms `R1` via `confirm(R1)`. Now `confirmations[R1] = {A, B}` (2 of 3 needed). [4](#0-3) 
4. Separately, members `C` and `D` execute a `DeleteMember { member: B }` request (`R2`), reaching threshold and calling `delete_member`. This removes `B` from `self.members` and deletes any requests `B` itself created, but does not touch `confirmations[R1]`, which still contains `B`. [2](#0-1) 
5. Member `C` (now one of only 3 remaining live members `A, C, D`) calls `confirm(R1)`. `confirmations[R1].len() (=2, still containing removed member B) + 1 = 3 >= num_confirmations (3)`, so `R1` executes — using `A`'s and the now-removed `B`'s stale vote plus `C`'s, when only 2 of the 3 currently-live members (`A`, `C`, `D`) actually authorized it. [5](#0-4) 

This demonstrates a request executing with confirmations from fewer live, currently-authorized members than `num_confirmations` requires — an unauthorized action against the equality "confirmations counted == live member authorizations."

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
