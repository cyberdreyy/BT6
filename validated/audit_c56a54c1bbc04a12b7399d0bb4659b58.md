## Title
Stale confirmations from a deleted/revoked multisig key still count toward the confirmation threshold, allowing execution of a request with fewer than `num_confirmations` live keys - (File: `multisig/src/lib.rs`)

### Summary
The reported bug class is "the code calls the wrong thing, so a critical accounting value used to gate an action is wrong." The direct analog in `multisig/src/lib.rs` (and the same pattern in `multisig2/src/lib.rs`) is that `MultiSigRequestAction::DeleteKey` only purges *requests originated by* the deleted public key, but never scans and removes that key's entries from the `confirmations` set of *other* still-pending requests it had confirmed. As a result, `confirm()`'s threshold check `confirmations.len() as u32 + 1 >= self.num_confirmations` can count a confirmation from a key that has already been revoked, letting a request execute with fewer than `num_confirmations` currently-valid keys.

### Finding Description
`confirm()` bases its execution decision purely on the stored `confirmations` `HashSet<PublicKey>` size: [1](#0-0) 

The invariant the contract is supposed to maintain is: `confirmations.len() == number of currently-valid (live) member keys that approved this request`. That invariant is only enforced at `DeleteKey` execution time for requests *authored by* the removed key: [2](#0-1) 

The filter is `r.signer_pk == pk` — i.e., it removes requests the deleted key *itself created*, and clears `num_requests_pk` for that key. It never iterates `self.confirmations` to strip `pk` out of the confirmation sets belonging to requests *created by other keys* that the now-deleted key had previously confirmed. Those stale entries remain in storage and are still summed by `confirm()`'s `confirmations.len()` check.

Equality broken: `confirmations recorded == live members who actually confirmed`. After a `DeleteKey` action executes, this becomes `confirmations recorded > live members`, because a revoked key's earlier confirmation is never retracted from requests it did not author.

The same structural gap exists in `multisig2/src/lib.rs`'s `delete_member`, which likewise only removes requests where `r.member == member`: [3](#0-2) 

### Impact Explanation
This directly falls under "a multisig request executed below threshold" (Critical). A request can reach `num_confirmations` and be executed (including `Transfer`, `FunctionCall`, `AddKey`, etc.) even though one of the counted confirmers' keys has since been deleted/revoked — meaning fewer than the configured number of live, currently-authorized keys actually agreed to the action at execution time. This undermines the entire security guarantee of a K-of-N multisig (e.g., a 3-of-3 or 3-of-5 setup can be satisfied by only 2 live signers plus one stale/revoked signature).

### Likelihood Explanation
No foundation/owner/redeploy/social-engineering assumption is required beyond the normal, documented multisig workflow: any member key can call `confirm`, and revoking a compromised or departing member's key via `DeleteKey` is the exact documented remediation path. The bug is triggered by ordinary usage — confirm a pending request with key K, later revoke K via a separate `DeleteKey` request — with no special conditions, making it readily reachable in production key-rotation/incident-response scenarios.

### Recommendation
When executing `DeleteKey` (or `delete_member` in `multisig2`), also iterate over all entries of `self.confirmations` and remove the deleted key/member from every confirmation set, not just from requests it authored. Alternatively, re-validate at `confirm()`/execution time that every public key in a request's confirmation set is still a currently valid key.

### Proof of Concept
1. Deploy `multisig` with keys `K1, K2, K3` and `num_confirmations = 3`.
2. `K1` calls `add_request(Transfer{...})` → `request_id = A` (no confirmation yet).
3. `K3` calls `confirm(A)` → `confirmations[A] = {K3}` (since `1 < 3`, it just records the confirmation).
4. The team detects `K3` is compromised and revokes it: `K1`/`K2` create and confirm a separate `DeleteKey{K3}` request (self-request), reaching quorum and executing. Per `multisig/src/lib.rs:198-216`, this removes `K3`'s own authored requests and `num_requests_pk[K3]`, but request `A` (authored by `K1`) is untouched — `confirmations[A]` still contains `K3`.
5. `K1` calls `confirm(A)` → `confirmations[A].len() = 1`, `+1 = 2 < 3`, recorded.
6. `K2` calls `confirm(A)` → `confirmations[A].len() = 2`, `+1 = 3 >= 3` → `execute_request(A)` fires the `Transfer`, even though `K3` has been deleted and only `K1` and `K2` are currently valid, live-confirming keys — a "3-of-3" request executed with 2 live confirmations plus one stale/revoked one.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
