### Title
Process-group kill in `unixKiller.getPID()` can be bypassed by a job script that detaches its workload via `setsid`/`nohup`/`disown` - ([File: helpers/process/killer.go])

### Summary
`unixKiller.getPID()` always kills `-Pid` of the tracked Commander process, relying on `setProcessGroup()` having set `Setpgid: true` only on that single direct child [1](#0-0) [2](#0-1) . Any process a job script spawns with `setsid`, `nohup ... &` plus `disown`, or a double-fork re-parents into a new session/process group and is no longer a member of that PGID, so `KillAndWait`'s SIGTERM/SIGKILL to `-Pid` never reaches it. I confirmed the runner's own generated bash wrapper (`scriptwriter.buildBashScript`) does not itself apply `setsid`/`nohup`, so this is purely a job-author-controlled behavior, not something Runner forces on every job.

### Finding Description
- `setProcessGroup(c *exec.Cmd)` sets `Setpgid: true` on the single top-level `exec.Cmd` that runs the generated build script [3](#0-2)  — actually the call site is `osCmd.Start()` [4](#0-3) .
- `unixKiller.Terminate()`/`ForceKill()` send signals to `-pid` (negative PID = process group) based solely on the tracked `Commander.Process().Pid` [5](#0-4) .
- If a job's script content (fully attacker/user controlled — it's the `.gitlab-ci.yml` `script:` block) invokes `setsid cmd &`, `nohup cmd & disown`, or performs its own double-fork, the child process calls `setsid(2)` internally, creating a brand-new session and process group ID different from the one Runner recorded. The new PGID is never tracked anywhere in `unixKiller`/`Commander`.
- When `KillAndWait` fires (job cancellation, timeout, graceful/force kill), `syscall.Kill(-originalPid, SIGTERM/SIGKILL)` only reaches processes still in the original group; the detached process is unaffected and continues running after the parent shell and Runner have exited/reported the job as finished.
- I verified the shell script generator (`functions/concrete/run/stages/internal/scriptwriter`) does not wrap the job body in `setsid`/`nohup` itself [6](#0-5) , and no occurrence of `setsid`/`nohup`/`disown` exists anywhere in the shells/script-generation code paths — the only hit in the whole repo is in an unrelated packaging Mage script. This confirms the detachment must be introduced by the job script itself, not by Runner-generated wrapper code.

### Impact Explanation
This is scoped to executors where the job process tree runs directly on a shared OS (primarily the **shell executor**, and similarly SSH/custom/parallels-virtualbox executors that exec commands via this same `Commander`/`killer` machinery, i.e. wherever `job_unix.go`'s `osCmd` is used — confirmed callers include `executors/shell/shell.go` and `executors/custom/command/command.go`). In these cases, a normal (unprivileged) pipeline author can cause a background process to survive job cancellation/timeout indefinitely, since the runner's only cleanup mechanism (group-kill via negative PID) cannot reach it. This is a resource-exhaustion / persistence issue on the shared host: repeated pipeline runs can leave an accumulating population of orphaned, un-killable processes consuming CPU/memory/disk/network on the runner host, degrading or denying service to other jobs sharing that host, and outliving the job's declared timeout controls. It does not by itself grant sandbox escape into another project's workload or leak secrets, so it is scoped to a persistent-resource/DoS impact rather than a full isolation break.

For container-based executors (docker, kubernetes), this is not exploitable in the same way because the whole container is torn down/removed on cancellation regardless of process group membership, so the vulnerability is effectively limited to non-containerized executors.

### Likelihood Explanation
Highly feasible and trivially reproducible by any pipeline author with shell-executor access: a single `script:` line such as `setsid sh -c 'while true; do sleep 1; done' & disown` (or `nohup ... & disown`) is standard shell syntax requiring no special privileges beyond running a job. It requires no exploitation of parsing bugs, image/service manipulation, or auth bypass — it is a direct consequence of relying purely on Unix process-group semantics for cleanup, which any detaching call defeats.

### Recommendation
- Do not rely solely on process-group signaling for job cleanup on Linux. Use a cgroup (cgroup v1/v2 freezer or `cgroup.kill`) per job, so all descendants — including those that call `setsid`/re-parent to PID 1 — are terminated regardless of PGID/session changes.
- As a defense-in-depth alternative, walk `/proc` for the process tree rooted at the tracked PID (via PPID or a Runner-injected marker environment variable) before/after kill and forcibly kill any surviving matches, rather than trusting only `-Pid`.
- Document explicitly that shell-executor jobs are not "escapable-detachment-proof" until cgroup-based cleanup lands, and consider blocking/warning about `setsid`/`nohup`+`disown` patterns in job policy where the shell executor is exposed to untrusted pipeline authors.

### Proof of Concept
```go
// helpers/process/killer_unix_detach_test.go (new integration-style test)
func TestKillAndWait_DoesNotKillSetsidDetachedChild(t *testing.T) {
    // 1. Start a Commander running: sh -c "setsid sh -c 'sleep 100' & disown; sleep 100"
    //    (setProcessGroup applied only to this top-level exec.Cmd, per job_unix.go)
    cmd := newTestCommander(t, "sh", "-c",
        `setsid sh -c 'echo $$ > /tmp/detached.pid; sleep 100' & disown; sleep 100`)
    require.NoError(t, cmd.Start())

    waitCh := make(chan error, 1)
    go func() { waitCh <- cmd.Wait() }()

    kw := NewOSKillWait(logger, 200*time.Millisecond, 200*time.Millisecond)
    _ = kw.KillAndWait(cmd, waitCh)

    // 2. Read the detached child's PID from /tmp/detached.pid
    detachedPID := readPID(t, "/tmp/detached.pid")

    // 3. Assert the top-level process group is dead...
    assert.Error(t, syscall.Kill(cmd.Process().Pid, 0)) // ESRCH

    // 4. ...but the setsid-detached process is still alive, proving the
    //    negative-PID kill in unixKiller.getPID() never reached it.
    assert.NoError(t, syscall.Kill(detachedPID, 0), "detached process should have survived, demonstrating the isolation gap")

    // cleanup
    _ = syscall.Kill(detachedPID, syscall.SIGKILL)
}
```
This differential test directly demonstrates the invariant violation: case (a) inline command dies with the group kill, case (b) `setsid`-detached command survives `KillAndWait`, confirming a guaranteed runaway process for any pipeline author who uses this pattern on shell/custom executors.

```go
func (pk *unixKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGTERM)
	if err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}

func (pk *unixKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGKILL)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}
}
```
