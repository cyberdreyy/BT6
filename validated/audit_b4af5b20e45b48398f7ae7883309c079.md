### Title
Dust-Transfer Griefing of `SystemInstruction::CreateAccount` Permanently Blocks Legitimate Account/PDA Initialization - (File: programs/system/src/system_processor.rs)

### Summary
The System Program's `create_account` handler unconditionally rejects account creation if the target address already holds any lamports, even a single lamport. Any unprivileged user can pre-fund a target address (e.g. a to-be-created PDA, associated token account, stake account, or vault) with a dust amount before the legitimate creator's transaction lands, permanently forcing that transaction to fail with `SystemError::AccountAlreadyInUse`.

### Finding Description
In `create_account`, the very first check is:

```rust
if to.get_lamports() > 0 {
    ic_msg!(invoke_context, "Create Account: account {:?} already in use", to_address);
    return Err(SystemError::AccountAlreadyInUse.into());
}
``` [1](#0-0) 

This is the exact same bug class as the referenced Tempus `depositAndFix` finding: a state-invariant check (`balance == 0` / `lamports == 0`) is asserted as a precondition for a legitimate operation, but the invariant can be broken by *any* third party sending a trivial amount to the target address before the legitimate transaction executes — a classic front-running/griefing vector. On Solana, deriving a PDA or vanity address ahead of time and sending it 1 lamport is trivial and cheap for an attacker who observes the target address in mempool/QUIC-ingested transactions or knows the deterministic derivation (e.g. associated token accounts, `create_with_seed` accounts, PDA vault accounts a protocol intends to initialize via CPI to `system_instruction::create_account`).

The codebase itself acknowledges this exact griefing class: it added a companion instruction, `create_account_allow_prefund`, whose doc comment states it creates "a new account without checking for 0 lamports... Intended for use where account has already had rent paid in whole or in part before creation" [2](#0-1) , gated behind `feature_set.create_account_allow_prefund` [3](#0-2) . This confirms the balance-based rejection in the original `create_account` path is a recognized DoS/griefing surface, but the fix is opt-in per-instruction and does not retroactively protect the ubiquitous legacy `CreateAccount`/`CreateAccountWithSeed` paths that most on-chain programs and clients (including SPL Associated Token Account creation, stake account creation, and countless custom program PDA-initialization CPIs) still rely on.

### Impact Explanation
Any user-facing on-chain program or client flow that creates a new system-owned or program-owned account at a predictable address (PDA, `create_with_seed` address, associated token account, vanity/deterministic vault) via `system_instruction::create_account` can be permanently denial-of-serviced by an attacker sending 1 lamport to that address beforehand. This blocks the legitimate initialization transaction from ever succeeding as written, breaking user deposits, account bootstrapping, or protocol initialization flows that assume they are the first writer to that address — mirroring the "function becomes unusable" impact described in the Tempus report.

### Likelihood Explanation
The attack is extremely cheap (a single lamport transfer, well under typical minimum balance/rent-exemption requirements since the target account has no data yet) and requires no special privilege — any ordinary `SystemInstruction::Transfer` transaction submitted by any user account suffices. The main requirement is that the attacker can predict the target address in advance, which is true for all PDA/`create_with_seed`/associated-token-account style flows that are extremely common on Solana.

### Recommendation
For any user-reachable flow, prefer `SystemInstruction::CreateAccountAllowPrefund` (once its feature is active) or restructure initialization logic to use `allocate_and_assign` plus an idempotent balance check (top-up rather than exact-zero requirement), similar to how `create_account_allow_prefund` already handles this. Programs/clients that build `CreateAccount` CPIs for deterministic addresses should be audited and migrated to the prefund-tolerant path, and documentation should flag `CreateAccount`'s "already in use" check as a known griefing vector for predictable addresses.

### Proof of Concept
1. Attacker observes/derives a PDA or `create_with_seed` address `X` that a victim protocol intends to initialize via `system_instruction::create_account(payer, X, lamports, space, owner)`.
2. Attacker submits `system_instruction::transfer(attacker, X, 1)` and it lands before the victim's transaction (trivial given deterministic address derivation and no special timing needed beyond ordinary transaction submission).
3. Victim's transaction invokes `create_account`, which now sees `to.get_lamports() == 1 > 0` at line 164 and returns `SystemError::AccountAlreadyInUse`, permanently failing that specific instruction shape unless the victim's program is rewritten to tolerate prefunding. [4](#0-3)

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
