### Title
APR0 dust withdraw request permanently bricks `stopEpoch` after any APR increase - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0`. Any KYC-passing lender can create a non-zero `apr0TotalPrincipal` with a dust `requestWithdraw` during an APR0 period. If the honest manager subsequently raises the APR via `setAprs`/`setAprsWithBuffer` (a legitimate, privileged-but-honest operation), every `stopEpoch` call reverts, freezing the vault and all tranche-holder funds until the APR is forced back to 0.

### Finding Description
The bug class of CVE-2018-16852 is dereferencing state that is only valid under a specific configuration — here, the global APR0 bucket (`apr0TotalPrincipal`) is treated as invalid to settle unless `unscaledApr == 0`:

- `requestWithdraw` routes to `_requestWithdrawApr0` whenever `unscaledApr == 0 && !isClosed`, incrementing `apr0TotalPrincipal` by `_amount` with no minimum ( [1](#0-0) , [2](#0-1) ).
- `prepareStopEpochWithApr0` reverts if `apr0TotalPrincipal != 0 && unscaledApr != 0` ( [3](#0-2) ).
- It is called unconditionally inside `_stopEpoch` before any borrower pull ( [4](#0-3) ).
- `setAprs`/`setAprsWithBuffer` are callable by the manager and update `unscaledApr` directly ( [5](#0-4) ), and `requestWithdraw` remains permissionless for any allowed wallet between epochs (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` stay open in buffer, [6](#0-5) ).

The attacker's dust request survives `prepareStopEpochWithApr0` only if the APR stays 0 through the stop; once `unscaledApr` is non-zero the settle path can never run, `apr0TotalPrincipal` can never be cleared, and every subsequent `stopEpoch` reverts — a self-referential deadlock.

### Impact Explanation
All epoch operations halt: `isEpochRunning` stays true, deposits/withdraw requests stay disabled, borrower repayment cannot be pulled, and all AA/BB tranche funds plus pending withdraw receipts are frozen. Recovery requires the manager to set the APR back to 0 and run `stopEpoch(0, …)`, forfeiting the negotiated APR for at least the current epoch cycle and delaying claims by a full epoch+buffer; with `skipDefaultCheck`/emergency interactions or a manager unaware of the root cause, the freeze is effectively permanent. Loss is quantified as the accrued interest difference (e.g., TVL × (newAPR − 0) × epochDuration) plus the freeze duration of the entire pool NAV.

### Likelihood Explanation
Low cost, no privilege: a KYC-passing lender needs only a dust withdraw request at the right moment (APR0 phase — which is the normal mode for programmable-borrower vaults that always run APR=0). The trigger condition (manager raising APR while an APR0 receipt is open) is an ordinary operational action, so sequencing is realistic. No existing guard prevents mixing: `requestWithdraw` does not check pending APR changes, and `setAprs` does not check `apr0TotalPrincipal`.

### Recommendation
In `setApr`/`setAprs`/`setAprsWithBuffer`, revert (or first settle/close the APR0 bucket) when `apr0TotalPrincipal != 0` and the new `unscaledApr` is non-zero; alternatively, let `prepareStopEpochWithApr0` settle the bucket at a zero rate instead of reverting when the APR changed. A minimum request amount would only raise the griefing cost, not remove the deadlock.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
// contracts: IdleCDOEpochVariant cdo, IdleCreditVault vault, underlying ERC20
// setup: owner/manager configured, lender is Keyring-allowed

// 1. APR = 0 epoch (programmable-borrower style or manager-set)
vm.prank(manager);
vault.setAprs(0, 0);

// 2. lender deposits AA, epoch starts and stops normally, buffer opens
depositAA(lender, 100e18);
startAndStopEpoch();

// 3. ATTACKER: dust APR0 withdraw request during buffer while unscaledApr == 0
vm.prank(lender);
cdo.requestWithdraw(1, AATranche);          // apr0TotalPrincipal = 1 wei
assertEq(vault.apr0TotalPrincipal(), 1);

// 4. manager legitimately raises APR for the next epoch
vm.prank(manager);
vault.setAprsWithBuffer(10e18, epochDuration, bufferPeriod);

// 5. next epoch runs; at stopEpoch the APR0 check reverts forever
warpPastEpochEnd();
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdo.stopEpoch(newApr, 0);                    // bricked: apr0TotalPrincipal!=0 && unscaledApr!=0

// 6. repeat: still bricked; lender funds + NAV frozen until APR forced back to 0
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdo.stopEpoch(newApr, 0);
```
