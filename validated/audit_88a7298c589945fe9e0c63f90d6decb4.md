### Title
Authentication rate limiter on `POST /sessions` is keyed solely by client IP, allowing unlimited per-account password/MFA brute-forcing via IP rotation - ([File: core/web/router.go])

### Summary
The unauthenticated `/sessions` login endpoint is protected only by an IP-keyed rate limiter (`rl.Unauthenticated`/`rl.UnauthenticatedPeriod`, default 5 requests / 20s), with `engine.RemoteIPHeaders = nil` ensuring the key is the genuine socket IP rather than a spoofable header. Because the limiter and the `SessionsController.Create` handler apply no per-account (per-email) throttle, lockout, or backoff, an attacker who can originate requests from many distinct source IPs can issue unlimited password/MFA-challenge guesses against one fixed target email.

### Finding Description
In `core/web/router.go`, `NewRouter` sets `engine.RemoteIPHeaders = nil` so `gin`'s `c.ClientIP()` resolves to the real TCP peer address rather than trusting `X-Forwarded-For`/`X-Real-IP` [1](#0-0) . `sessionRoutes` wraps `unauth.POST("/sessions", sc.Create)` with a `rateLimiter(rl.UnauthenticatedPeriod(), rl.Unauthenticated())` group [2](#0-1) . `rateLimiter` builds an in-memory `ulule/limiter` store and wraps it via `mgin.NewMiddleware`, which keys rate-limit buckets by the request's client IP (via gin's `ClientIP()`) with no additional dimension (e.g., request body email) [3](#0-2) . The default config values are `Unauthenticated = 5` requests per `UnauthenticatedPeriod = '20s'` [4](#0-3) .

`SessionsController.Create` performs no per-account lockout, failed-attempt counter, or exponential backoff keyed by `sr.Email`; it simply loads WebAuthn tokens for the target email and calls `CreateSession`, returning `401` on failure with no additional state tracked against the email [5](#0-4) . Because the only throttle dimension is the caller's IP, and the rate limiter deliberately does not trust any forwarding headers, an attacker who legitimately controls or rotates across many real source IPs (e.g., botnet, cloud NAT pool, proxy farm, mobile carrier CGNAT rotation) is not"restricted" by this limiter at all with respect to a single target email — each new IP gets its own fresh 5-request/20s allowance against the same account. The existing `TestSessions_RateLimited` test only validates single-IP throttling behavior and does not assert any per-account protection [6](#0-5) .

### Impact Explanation
This allows unlimited password and MFA-challenge probing against a specific target admin/operator account as long as the attacker can vary source IP, defeating the intended brute-force resistance of the login endpoint (CWE-307: Improper Restriction of Excessive Authentication Attempts). If a weak or guessable password is in use, this materially increases the odds of full authentication bypass and node compromise (admin session issuance), which enables fund movement, job manipulation, and key-management access downstream.

### Likelihood Explanation
Precondition is only unauthenticated network access to the node's HTTP API, matching the allowed unprivileged threat model. Distributing requests across many source IPs (cloud VMs, proxy pools, botnets, mobile CGNAT) is a well-established, low-cost, and fully repeatable technique; it does not require header spoofing or trusting the reverse proxy (the code explicitly avoids trusting forwarded headers), so it works uniformly whether or not the node sits behind a proxy. Because the rate limiter resets for each new "identity" (IP) rather than the targeted account, exploitation scales linearly with the number of controlled/rotated IPs.

### Recommendation
Add a secondary, per-account (email-based) throttle/lockout independent of source IP — e.g., track failed attempts and cumulative attempt counts keyed by `sr.Email` (or a hash thereof) with escalating backoff or temporary account lockout, in addition to the existing IP-based limiter. Consider also rate-limiting by a combination of IP and email, and enforcing a global cap on failed attempts per account within a rolling window regardless of source IP.

### Proof of Concept
Handler-level integration test plan:
1. Start the router as in `TestSessions_RateLimited` (`core/web/router_test.go`).
2. Issue `rl.Unauthenticated()+1` (e.g., 6) `POST /sessions` requests for `email: "victim@node.com"` with wrong passwords, but assign each request a distinct simulated client IP (e.g., by using `httptest` with different `RemoteAddr` values per request, since `engine.RemoteIPHeaders = nil` means the test must vary the actual socket-level `RemoteAddr`, not headers).
3. Assert that none of the 6+ requests return `429 Too Many Requests` (all return `401 Unauthorized`), demonstrating the per-IP limiter never engages because each request is a "new" IP.
4. Repeat for 50+ iterations to confirm no per-account counter ever triggers a lockout/`429`/backoff for the fixed `email`, proving the absence of identity-bound brute-force protection.

func rateLimiter(period time.Duration, limit int64) gin.HandlerFunc {
	store := memory.NewStore()
	rate := limiter.Rate{
		Period: period,
		Limit:  limit,
	}
	return mgin.NewMiddleware(limiter.New(store, rate))
}

func sessionRoutes(app chainlink.Application, r *gin.RouterGroup) {
	config := app.GetConfig()
	rl := config.WebServer().RateLimit()
	unauth := r.Group("/", rateLimiter(
		rl.UnauthenticatedPeriod(),
		rl.Unauthenticated(),
	))
	sc := NewSessionsController(app)
	unauth.POST("/sessions", sc.Create)
	auth := r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	auth.DELETE("/sessions", sc.Destroy)
}

func (sc *SessionsController) Create(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()
	sc.App.GetLogger().Debugf("TRACE: Starting Session Creation")

	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)
	if err != nil {
		sc.App.GetLogger().Errorf("Error loading user WebAuthn data: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}

	if err := saveSessionID(session, sid); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, errors.Join(errors.New("unable to save session id"), err))
		return
	}

	jsonAPIResponse(c, Session{Authenticated: true}, "session")
}

func TestSessions_RateLimited(t *testing.T) {
	t.Parallel()

	ctx := t.Context()
	app := cltest.NewApplicationEVMDisabled(t)
	require.NoError(t, app.Start(ctx))

	router := web.Router(t, app, nil)
	ts := httptest.NewServer(router)
	defer ts.Close()

	client := clhttptest.NewTestLocalOnlyHTTPClient()
	input := `{"email":"brute@force.com", "password": "wrongpassword"}`

	for range 5 {
		request, err := http.NewRequestWithContext(ctx, http.MethodPost, ts.URL+"/sessions", bytes.NewBufferString(input))
		require.NoError(t, err)

		resp, err := client.Do(request)
		require.NoError(t, err)
		assert.Equal(t, http.StatusUnauthorized, resp.StatusCode)
	}

	request, err := http.NewRequestWithContext(ctx, http.MethodPost, ts.URL+"/sessions", bytes.NewBufferString(input))
	require.NoError(t, err)

	resp, err := client.Do(request)
	require.NoError(t, err)
	assert.Equal(t, 429, resp.StatusCode)
}
