### Title
`epochEndDate == 0` sentinel lets post-close withdrawal receipts bypass `pendingWithdraws` funding and the one-epoch claim delay, draining the strategy's funded reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external bug class is "an uninitialized/terminal sentinel value funnels a state machine into its second stage." The analog lives in `IdleCreditVault.requestWithdraw` and `_claimFundedWithdrawRequest`: `IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0` is treated as "pool successfully closed," which (a) skips `pendingWithdraws += _amount` so no future `stopEpoch` will ever fund the receipt, and (b) disables the `epochNumber <= lastWithdrawRequest` wait so the receipt is claimable in the same transaction. After close-pool (`stopEpoch`/`stopEpochWithDuration` with `_interest == 1`), `IdleCDOEpochVariant` re-enables `allowAAWithdrawRequest`/`allowBBWithdrawRequest` while setting `epochEndDate = 0` and `epochDuration = 0`, so a lender can still call `requestWithdraw` and then `claimWithdrawRequest` immediately, getting paid at par from underlying the strategy is holding for other users' matured-but-unclaimed receipts.

### Finding Description
In `IdleCreditVault.requestWithdraw`, the `isClosed` flag is computed purely from `epochEndDate() == 0`, and when true the function still burns `_principal` from the CDO and mints `_amount` of strategy-token receipts to the user but deliberately does not increment `pendingWithdraws` — "A successfully closed pool already recalled all funds and has no later stopEpoch." [1](#0-0)  The claim path mirrors this: `_claimFundedWithdrawRequest` only enforces the "wait one epoch" rule when `epochEndDate() != 0`, so a zero `epochEndDate` funnels the claim straight through to `_transferFundedClaim`, which pays underlying held by the strategy (including the `defaultRecoveryReserve`-protected funded claims of other users). [2](#0-1)  The close-pool path in `IdleCDOEpochVariant` re-arms the exact preconditions the attacker needs — it sets `epochEndDate = 0`, `epochDuration = 0`, and `allowAAWithdrawRequest = allowBBWithdrawRequest = true` in the same state transition, so `requestWithdraw` remains callable. [3](#0-2)  The analogous "first step skipped" guard — some marker distinguishing "closed and fully settled" from "new requests should be refused" — is missing: `requestWithdraw` checks only the allow flags and wallet KYC, not whether the pool is closed. [4](#0-3) 

### Impact Explanation
After a close-pool `stopEpoch(0, 1)`, all borrower principal is recalled to the strategy and sits there to satisfy previously funded `withdrawsRequests`/`apr0Users` receipts that honest users have not yet claimed (`_transferFundedClaim` pays from the strategy balance / `defaultRecoveryReserve`). [5](#0-4)  An attacker who still holds tranche tokens (or acquires them) calls `requestWithdraw(amount, AATranche)` — `pendingWithdraws` is not incremented, no interest accrues, and `_calcInterestWithdrawRequest` returns zero anyway because `epochDuration == 0` — then calls `claimWithdrawRequest()` in the next block (or same block) and receives underlying at par. [6](#0-5)  Each such claim is a direct transfer of funds reserved for earlier receipt holders: the honest users' funded receipts then revert or underpay when they claim because the reserve was drained by receipts that were never funded. Loss is bounded by the strategy's residual funded-claim balance and is direct theft of unclaimed withdrawals.

### Likelihood Explanation
Requires the pool to be closed via `_interest == 1` (honest manager action) while tranche-token supply still exists and while the strategy still holds unclaimed funded balances — a common state right after close, since users claim lazily. The attacker needs only a KYC-passed wallet holding tranche tokens; no privileged role is involved. One caveat: if `isInterestMinted` minted-mode or other flags leave no underlying in the strategy after close, the window shrinks, but the standard fixed-APR close path recalls all principal into the strategy, creating exactly this pool of claimable funds.

### Recommendation
Treat `epochEndDate == 0` as a terminal state for new requests: in `IdleCDOEpochVariant.requestWithdraw`, revert when `epochDuration == 0` (closed pool), or in `IdleCreditVault.requestWithdraw` revert when `epochEndDate() == 0` instead of routing around `pendingWithdraws`. Equivalently, set `allowAAWithdrawRequest = allowBBWithdrawRequest = false` in the close-pool branch so the sentinel cannot funnel fresh receipts into the instant-claim path.

function testPostCloseRequestDrainsFundedClaims() external {

    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 1); // close pool: epochEndDate = 0, principal recalled

    uint256 stratBal = underlying.balanceOf(address(strategy));

    cdoEpoch.claimWithdrawRequest();                 // epoch-wait skipped, paid at par
    assertGt(underlying.balanceOf(address(this)), 0);
    // honest funded receipt now competes for a drained reserve
}

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }
