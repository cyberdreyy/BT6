## Title
Drift-integrated bank collateral becomes permanently frozen for depositors once admin reward deposits accumulate past index 3, with no user-side recovery path - ([File: programs/drift-mocks/src/state.rs])

### Summary
The Frankencoin `deny` bug traps an innocent, uninvolved user's own collateral in a durable, non-recoverable state (cooldown until `expiration`) triggered by a condition outside the user's control, with no path for the user themselves to unwind. The closest analog on marginfi that fits an unprivileged-user path with real financial effect is the Drift integration's "bricked account" state: once a Drift `MinimalUser`'s spot positions accumulate more than 3 active deposits (1 main + up to 2 reward positions, populated by Drift-side admin reward deposits at market indices 2-7), `validate_not_bricked_by_admin_deposits` starts failing and `DriftWithdraw` unconditionally reverts with `DriftBrickedAccount` for every marginfi user whose funds sit in that bank's underlying Drift `MinimalUser` account.

### Finding Description
`DriftWithdraw`'s account validation enforces: [1](#0-0) 

The constraint calls `validate_not_bricked_by_admin_deposits`, which counts active deposit positions in the shared Drift `MinimalUser` account (owned by the bank's `liquidity_vault_authority`, shared across all marginfi depositors into that bank) and fails once more than 3 exist: [2](#0-1) 

This mirrors the Frankencoin pattern precisely: an event unrelated to the individual user's own choices (Drift admin adding reward deposits, analogous to `deny` being called by qualified helpers) puts the account into a state where the owner cannot withdraw their own legitimate collateral. The in-code comment even states the situation is unresolved by the user themselves ("SOLUTION: Fee admin wallet needs to harvest these rewards ASAP!"), and a dedicated `harvest_reward` instruction exists specifically to relieve this condition: [3](#0-2) 

The test suite explicitly confirms the "bricked" outcome causes `withdraw_all` to hard-fail with `DriftBrickedAccount` even with reward accounts supplied for two rewards, once a fourth active deposit position exists: [4](#0-3) 

Unlike marginfi's `ACCOUNT_FROZEN` (an intentional, documented, admin-toggle-only compliance tool) or `ACCOUNT_IN_RECEIVERSHIP`/`ACCOUNT_IN_DELEVERAGE` (which are provably bounded to a single atomic transaction via instruction introspection, so they cannot persist across blocks), the Drift-bricked state is a durable, cross-transaction condition affecting *every* depositor sharing that bank's Drift user account, and there is no ordinary user-facing instruction to resolve it — remediation depends entirely on the `harvest_reward` instruction being run (by whichever authorized party can call it) to reduce the active-position count back to 3 or fewer.

### Impact Explanation
While funds are not stolen, ordinary marginfi depositors in a Drift-integrated bank can find their withdrawal blocked indefinitely purely because of the shared, pooled Drift user account accumulating admin-side reward deposits — a condition entirely outside any individual depositor's control, and one they cannot resolve themselves via any standard marginfi instruction. This is a durable freeze with real financial effect (temporary loss of liquidity access) closely paralleling the confirmed Frankencoin finding, where severity was assessed as Medium ("funds aren't lost but are locked for some period of time").

### Likelihood Explanation
This requires no attacker action against a legitimate depositor — it is a naturally reachable state whenever Drift-side admin/reward deposits (which the marginfi program does not control) push the shared `MinimalUser` account past 3 active deposit positions. Since the account is shared across all depositors in that bank, a single external event can simultaneously brick withdrawals for many unrelated, unprivileged users at once.

### Recommendation
Ensure a permissionless (or at least non-discretionary, guaranteed) path exists to unbrick the account before depositors are blocked — e.g., allow `withdraw` itself to trigger harvesting inline when the bricked condition is detected, or make `harvest_reward` callable by any party (not gated behind a privileged "fee admin" workflow) so affected depositors are not solely dependent on an external operator to restore their withdrawal access.

### Proof of Concept
1. A marginfi bank is configured with the Drift integration, using a shared Drift `MinimalUser` account as `integration_acc_2`.
2. The Drift program (or its admin) deposits reward assets into spot positions at market indices 2 and 3 for that `MinimalUser` account, in addition to the main deposit — 4 total active deposit positions.
3. Any depositor into that marginfi bank calls `DriftWithdraw`; the `integration_acc_2` constraint calling `validate_not_bricked_by_admin_deposits` returns `Err(DriftMocksError::TooManyActiveDeposits)`, surfaced to the caller as `MarginfiError::DriftBrickedAccount`, confirmed by the test in `tests/specs/drift/d12_driftHarvestReward.spec.ts:1232-1335` where `withdrawAll` fails with error code `0x18ae` (`DriftBrickedAccount`) despite both reward-account slots being supplied.
4. No standard user-facing marginfi instruction lets the depositor resolve this themselves; it remains blocked until a `harvest_reward` call reduces active positions back to ≤3.

    /// Check if Drift has bricked this account with excessive admin deposits
    /// We support 1 main asset + up to 2 reward assets (3 total active deposits)
    /// If Drift admin deposited more reward assets, the account cannot withdraw
    pub fn validate_not_bricked_by_admin_deposits(&self) -> Result<()> {
        let active_deposits = self.count_active_deposits();

        if active_deposits > 3 {
            msg!(
                "ERROR: Drift has {} active deposit positions",
                active_deposits
            );
            msg!(
                "Active market indexes: {:?}",
                self.get_active_deposit_markets()
            );
            msg!("This account has been bricked by Drift admin deposits!");
            msg!("Cannot withdraw when more than 3 assets have active balances");
            msg!("We support 1 main asset + up to 2 reward assets");
            msg!("SOLUTION: Fee admin wallet needs to harvest these rewards ASAP!");
            return Err(DriftMocksError::TooManyActiveDeposits.into());
        }

        Ok(())
    }
