### Title
Unchecked subtraction underflow in `rlp_list_element_length` can panic the fault-proof program when parsing an attacker-influenced MPT node - (File: crates/proof/mpt/src/util.rs)

### Summary
`base-proof-mpt`'s `rlp_list_element_length` computes `buf.len() - header.payload_length` without checking that `header.payload_length` does not exceed the remaining buffer, mirroring the CVE-2017-18233 bug class (unchecked length field taken directly from untrusted chunk/RLP data and used in arithmetic that drives a parsing loop).

### Finding Description
`rlp_list_element_length` decodes an RLP list header and then computes the buffer length "after consuming the list" as: [1](#0-0) 

```rust
let header = Header::decode(buf)?;
if !header.list {
    return Err(alloy_rlp::Error::UnexpectedString);
}
let len_after_consume = buf.len() - header.payload_length;
```

`Header::decode` only validates that the *encoding* of the length field is syntactically well-formed; `alloy_rlp` does not guarantee `header.payload_length <= buf.len()` for a list header whose declared payload length exceeds the actual remaining bytes (a truncated/malformed encoding). If `header.payload_length > buf.len()`, the subtraction `buf.len() - header.payload_length` underflows the `usize`. In a debug/overflow-checked build this panics; the fault-proof / FPVM crates in this workspace are built for a `no_std` bare-metal target (`riscv32imac-unknown-none-elf`) with no default `catch_unwind` handling, so a panic there halts/aborts the program rather than degrading gracefully.

This function is reachable from `TrieNode::decode` at: [2](#0-1) 

which is the MPT node decoder used throughout the fault-proof program to walk L1/L2 Merkle-Patricia-Trie preimages supplied via the untrusted preimage oracle (an adversarial/dishonest server can supply arbitrary trie-node preimage bytes for a hash the honest prover requested), e.g. via `OracleL1ChainProvider::trie_node_by_hash`: [3](#0-2) 

This mirrors the CVE's bug class exactly: a length value taken from untrusted, attacker-controlled input is used directly in unchecked arithmetic that governs a parsing/loop construct, without first validating the length against the buffer bounds.

### Impact Explanation
If reachable with `header.payload_length > buf.len()`, the subtraction underflows. In `no_std`/embedded FPVM builds compiled without disabling overflow checks (or any zkVM guest target that keeps overflow checks on, which is common for reproducibility/safety in guest programs), this triggers an integer-overflow panic, aborting the fault-proof program mid-execution. Because the MPT decoder is on the critical path for computing the output root during dispute-game resolution, a program abort/halt during proof generation would prevent the honest party from producing a valid execution trace/proof for a dispute game move, potentially freezing withdrawal challenges or forcing an incorrect resolution (fault-proof program failure -> node/prover halt, one of the listed acceptable impacts). If overflow checks are disabled (typical release-mode wrapping), `len_after_consume` wraps to a huge value near `usize::MAX`, causing the subsequent `while buf.len() > len_after_consume` loop to be skipped entirely, silently returning `list_element_length == 0` for a node that is not actually empty — corrupting the classification of branch/leaf/extension nodes in `TrieNode::decode` and potentially producing an incorrect trie traversal result (wrong provable output root).

### Likelihood Explanation
The MPT node preimages come from the FPVM's preimage oracle, which in the fault-proof context is the counter-party/host-supplied data during a dispute game — i.e., attacker-influenced input reachable by a dispute-game participant supplying a malicious host or crafted preimage responses that the client trusts before verifying the resulting hash matches the requested key. Triggering the underflow requires supplying a syntactically valid RLP list header (parseable by `Header::decode`) whose declared `payload_length` exceeds the bytes actually present in the slice passed to `rlp_list_element_length` — plausible for a truncated node fetched via preimage but not fully bounds-validated before this call.

### Recommendation
Replace the direct subtraction with a checked/saturating computation and reject malformed headers outright:
```rust
let len_after_consume = buf
    .len()
    .checked_sub(header.payload_length)
    .ok_or(alloy_rlp::Error::InputTooShort)?;
```
Apply the same audit to any other RLP/length-driven arithmetic in `base-proof-mpt` and `base-proof-executor` that assumes `payload_length <= buf.len()` without an explicit check, consistent with the bounds checks already present elsewhere in the codebase (e.g., `crates/proof/tee/registrar/src/cbor.rs`'s `checked_add`/bounds checks on CBOR item lengths).

### Proof of Concept
1. Construct raw bytes representing an RLP list header claiming a payload length larger than the remaining buffer, e.g. `[0xf8, 0xff]` (long-form list header claiming ~255 bytes of payload) followed by fewer than 255 bytes of actual data.
2. Call `TrieNode::decode(&mut these_bytes.as_ref())`, which invokes `rlp_list_element_length` on the malformed buffer.
3. In an overflow-checked build, `buf.len() - header.payload_length` panics (`attempt to subtract with overflow`), aborting the fault-proof client. In a wrapping build, the loop silently exits with `list_element_length == 0`, so `TrieNode::decode`'s subsequent branch/leaf-vs-extension classification produces an incorrect result for a non-empty node.

**Note on confidence**: I was unable to verify from the index whether the production FPVM/zkVM guest builds actually run with Rust overflow checks enabled or disabled (no `overflow-checks` setting was found in the indexed `Cargo.toml`/workspace files, and `check-no-std-proof.sh` builds `base-proof-mpt` for `riscv32imac-unknown-none-elf` without specifying a profile). This determines whether the primary impact is a program panic/halt or silent miscomputation of `list_element_length`; either outcome is a valid, in-scope finding for the fault-proof program/MPT path, but I could not confirm which one applies without building the crate, which is outside the scope of static indexing. A Devin session with full repository/build access could confirm the exact profile settings used for the FPVM/zkVM targets.

impl Decodable for TrieNode {
    /// Attempts to decode the [`TrieNode`].
    fn decode(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
        // Peek at the header to determine the type of Trie node we're currently decoding.
        let header = Header::decode(&mut (**buf).as_ref())?;

        if header.list {
            // Peek at the RLP stream to determine the number of elements in the list.
            let list_length = rlp_list_element_length(&mut (**buf).as_ref())?;

            match list_length {
                BRANCH_LIST_LENGTH => {
                    let list = Vec::<Self>::decode(buf)?;
                    Ok(Self::Branch { stack: list })
                }
                LEAF_OR_EXTENSION_LIST_LENGTH => {
                    // Advance the buffer to the start of the list payload.
                    buf.advance(header.length());
                    // Decode the leaf or extension node's raw payload.
                    Self::try_decode_leaf_or_extension_payload(buf)
                        .map_err(|_| alloy_rlp::Error::UnexpectedList)
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }
