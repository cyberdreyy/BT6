### Title
Reject-then-Accept ordering lets a single signer's weight be double-booked into both `total_weight_approved` and `total_weight_rejected` in the node's StackerDB listener - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The node-side `StackerDBListener` tallies signer weight for a proposed block using two separate guards: `gathered_signatures.contains_key(slot_id)` for the approve path and `responded_signers.insert(slot_id)` for the reject path. Because `responded_signers` is marked by *both* the accept and reject handlers but `gathered_signatures` is marked only by the accept handler, a signer that rejects first and later accepts the same block gets counted into `total_weight_rejected` *and* `total_weight_approved`, corrupting the weight bookkeeping the coordinator relies on to decide consensus/liveness on a block.

### Finding Description
In the `Rejected` branch, weight is only added if `responded_signers.insert(slot_id)` returns `true` (i.e., this slot hasn't been recorded as "responded" yet): [1](#0-0) 

In the `Accepted` branch, weight is only added if `gathered_signatures.contains_key(&slot_id)` is `false` — i.e., this slot hasn't produced a signature yet — and only then is `responded_signers.insert(slot_id)` also called: [2](#0-1) 

The two guards track different sets (`gathered_signatures` vs `responded_signers`), and `responded_signers` is shared/written by both branches. Consider a single signer (one StackerDB slot) that:
1. Sends `BlockResponse::Rejected` for block `B` first → `responded_signers.insert(slot_id)` returns `true` → `total_weight_rejected += weight`. `gathered_signatures` is untouched.
2. Later sends `BlockResponse::Accepted` (a valid signature) for the same `B` → the guard checked is `gathered_signatures.contains_key(&slot_id)`, which is still `false` (no signature was ever recorded for this slot) → `total_weight_approved += weight` is executed, even though this same signer's weight is *already* counted in `total_weight_rejected` from step 1.

The result: the same signer's weight is now present in both `total_weight_approved` and `total_weight_rejected` simultaneously — violating the equality that each signer's weight should be attributed to exactly one bucket at a time (accepted vs rejected). Note the reverse order (accept-then-reject) is correctly guarded, because the reject branch's guard (`responded_signers.insert`) is already `false` after an accept — this asymmetry confirms the bug is in the ordering/guard mismatch, not intentional design.

A single signer (one StackerDB slot, no majority needed) fully controls the content and order of its own StackerDB messages and can trivially produce this reject-then-accept sequence (e.g., signing then quickly reverting a rejection, or benign implementation races where a delayed local rejection message arrives after an accept was already recorded upstream then a genuine later accept follows) — this is exactly the "one-slot miner/signer plus gossip" trigger class called out in scope.

### Impact Explanation
`total_weight_rejected` is used directly to decide the block has been globally rejected/failed: [3](#0-2) 

Because the reject weight is stale/phantom (attributable to a signer that has since accepted), the coordinator can wake up believing the block has crossed the "cannot reach approval" threshold and abandon a block proposal that in fact still has (or will have) enough real approving weight — a liveness impact on the mining/coordinator loop (the coordinator gives up on a valid, still-signable block). Conversely the double-booked weight leaves the internal state inconsistent (`total_weight_approved + total_weight_rejected` can exceed a signer's true single contribution across the two buckets), undermining the invariant the coordinator uses to reason about "aggregated weight vs verified accepts/rejects" for this block.

### Likelihood Explanation
Triggerable by a single, single-slot signer with no cooperation from a majority — only ordinary StackerDB message posting under the signer's own control. It requires only two of that signer's own messages (reject then accept) for the same block to arrive at the node in that order, which is plausible in normal operation (e.g., an initial local rejection followed by a later successful validation/accept, or replay/reordering over StackerDB gossip).

### Recommendation
Unify the "already responded / already counted for a bucket" check so both branches consult a per-outcome record keyed by `slot_id`. Concretely:
- Track a single `HashMap<u32, Decision>` (Accepted/Rejected) per block instead of two independently-guarded structures, or
- Ensure the accept-path check also inspects whether `slot_id` is already recorded as rejected and, if so, atomically remove/decrement the previously-added rejection weight before adding acceptance weight (and vice versa) — treating a switched vote as a state transition rather than an independent tally.

### Proof of Concept
1. Node instantiates `StackerDBListener` for a reward set including signer S at `slot_id = k` with weight `w`, and calls `insert_block(&header)` for block `B` (fresh `BlockStatus` with empty `responded_signers`/`gathered_signatures`).
2. Signer S publishes a `BlockResponse::Rejected` message for `B` to its StackerDB slot.
   - Listener processes it: `responded_signers.insert(k)` → `true` → `total_weight_rejected += w`.
3. Signer S then publishes `BlockResponse::Accepted` (with a validly-recovered signature) for the same `B` to the same slot (e.g., it reconsidered, or a delayed accept overwrote the slot).
   - Listener processes it: `gathered_signatures.contains_key(&k)` → `false` (never set) → `total_weight_approved += w` executes.
4. Result: `block.total_weight_approved == w` and `block.total_weight_rejected == w` simultaneously for the same signer's weight `w`, even though only one true, current opinion (`Accepted`) exists — confirmable by inspecting `BlockStatus` via `StackerDBListenerComms`/`wait_for_block_status` after the two messages are delivered.
