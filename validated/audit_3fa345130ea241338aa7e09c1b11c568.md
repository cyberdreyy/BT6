### Title
Attacker can permanently block `processDeposits()` for an epoch by saturating the guarded TVL limit, breaking the queue's aggregate deposit processing - ([File: contracts/IdleCDOEpochQueue.sol](contracts/IdleCDOEpochQueue.sol))

### Summary
`IdleCDOEpochQueue.requestDeposit()` accepts underlying during the running epoch with no cap check (lines 103-127), while `processDeposits()` (lines 222-246) settles the *entire* `epochPendingDeposits[_epoch]` in one atomic `_cdo.depositAA(_pending)` call during the buffer period. The bug-class analog: a state change between request time and processing time (here, an attacker filling the guarded deposit limit via a direct deposit) makes the single aggregate call revert forever, so the whole queued-deposit epoch can never be processed — exactly like the Carousel report where a `relayerFee` increase made every `queue[i].assets < relayerFee` iteration revert.

### Finding Description
- `requestDeposit()` at `contracts/IdleCDOEpochQueue.sol:103-127` pulls underlying and increments `epochPendingDeposits[nextEpoch]` with no `_guarded`/limit validation (the only cap check is `checkPrefunding`, and only for the prefunded AA queue path at lines 111-118).
- During the buffer period the CDO is unpaused (`_unpause()` in `_stopEpoch`, `contracts/IdleCDOEpochVariant.sol:480`), so direct `depositAA`/`depositBB` are open to any KYC-passing lender, and `_deposit` enforces the guarded launch limit (`_guarded(_amount)`, e.g. `contracts/IdleCDOEpochVariant.sol:681`).
- A KYC'd attacker deposits directly until the pool's TVL limit is saturated, so `depositAA(_pending)` inside `processDeposits()` reverts on `_guarded`. Because `processDeposits()` is atomic and aggregate — mirroring the "non-atomic loop that actually reverts atomically" bug — every retry reverts regardless of call order. There is no skip/partial path: `epochPendingDeposits[_epoch]` is never cleared and `epochPrice[_epoch]` stays 0, so `claimDepositRequest` reverts (`_checkNotAllowed(epochPrice[_epoch] == 0 ...)`, lines 374-379).
- Honest owner/manager cannot fix it: lowering the limit further makes it worse, raising it only helps if the attacker stops topping up; the attacker can keep the cap saturated across the whole buffer window with capital that remains recoverable via a later withdraw request.
- The same atomicity failure applies symmetrically to `processWithdrawRequests()` (lines 298-329): if the owner toggles `allowAAWithdrawRequest`/`allowBBWithdrawRequest` off between request and processing (or `Is0` is hit at line 320), the single `_cdo.requestWithdraw(_pending, tranche)` call reverts and all queued withdrawals for the epoch are unprocessable — users can only self-rescue via `deleteWithdrawRequest`.

### Impact Explanation
Temporary freezing / DoS of the deposit queue for an entire epoch: all `epochPendingDeposits[_epoch]` become unprocessable and `claimDepositRequest` is unreachable. Users recover funds only by each individually calling `deleteRequest` (lines 184-199); the epoch misses its deposit window entirely and the queue's intended settlement path is down, matching the Medium severity of the source report. Uncertainty: exact `_guarded` revert semantics live in `IdleCDOCreditVault`/`GuardedLaunchUpgradable` (index excerpted); the finding assumes the standard limit-exceeded revert used elsewhere in this contract (`depositDuringEpoch` line 681).

### Likelihood Explanation
Requires only a KYC-passing lender (in-scope attacker) plus a pool with an active guarded limit — a normal post-launch configuration. The attacker griefs the epoch at the cost of parking funds until the next withdrawal window; no privileged cooperation needed.

### Recommendation
Check the guarded limit (or the free capacity) inside `requestDeposit()`/`processDeposits()` and allow partial/batched processing: e.g. split `processDeposits()` so the aggregate is deposited up to available capacity and the remainder stays deletable, or add a `processDeposits(uint256 amount)` variant so manager can process a subset rather than the all-or-nothing `depositAA(_pending)`.

### Proof of Concept
```solidity
// test/foundry/IdleCDOEpochQueue.t.sol harness assumed
function testProcessDepositsDosViaLimitSaturation() external {
    uint256 amount = 1e6;
    address victim = makeAddr('victim');
    _requestDepositWithUser(victim, amount);            // queued while epoch runs

    _stopCurrentEpoch();                                // buffer period, pool unpaused

    // Attacker (KYC'd lender) directly deposits to saturate the guarded limit
    address attacker = makeAddr('attacker');
    uint256 cap = cdoEpoch.limit() - cdoEpoch.getContractValue();
    deal(address(underlying), attacker, cap);
    vm.startPrank(attacker);
    underlying.approve(address(cdoEpoch), cap);
    cdoEpoch.depositAA(cap);                            // fills remaining capacity
    vm.stopPrank();

    // Aggregate queue processing now reverts forever
    vm.prank(manager);
    vm.expectRevert();                                  // _guarded inside depositAA
    queue.processDeposits();

    assertEq(queue.epochPrice(strategy.epochNumber()), 0);  // epoch never priced
    // victim's only recovery is deleteRequest(); the epoch deposit is lost
}
```
