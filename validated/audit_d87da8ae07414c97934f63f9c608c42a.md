### Title
Unprivileged vault deployment can configure an unbounded borrower APR - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower.borrowerApr` has no protocol-wide maximum and is not validated during initialization or updates. The public factory accepts an arbitrary `borrowerApr` in `deployRevolvingCreditVault` and writes it directly during initialization. An unprivileged deployer can therefore create a revolving credit vault with a far-above-advertised borrower rate, causing borrower debt and pool-facing interest to inflate disproportionately.

### Finding Description
`deployRevolvingCreditVault` is externally callable and forwards `programmableBorrowerParams.borrowerApr` to `ProgrammableBorrower.initialize` without validation. [1](#0-0) [2](#0-1)  The initializer stores that value directly and performs no APR-bound check. [3](#0-2) 

The strategy's `DEFAULT_MAX_APR` and `maxApr` checks protect `IdleCreditVault.setApr`, but they do not constrain the separate `ProgrammableBorrower.borrowerApr`. [4](#0-3) [5](#0-4)  Borrower interest accrues linearly from `borrowerApr`, and `totalInterestDueNow` includes that accrued debt when pricing the epoch. [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker can deploy a vault with an excessive contractual borrower APR and deposit as a KYC-passing lender while the borrower and manager remain honest. Once the borrower draws principal, interest accrues at the abnormal rate and is included in `totalInterestDueNow`. [6](#0-5)  At epoch settlement, that amount increases pool yield and tranche value, allowing the attacker to capture yield that exceeds the pool's intended rate commitment.

If the borrower cannot cover the inflated debt, the epoch can instead transition into default through the programmable-borrower stop path. [8](#0-7)  Thus, the issue can produce either direct extraction of excess borrower payments or protocol insolvency/default accounting caused by unsupported contractual interest.

### Likelihood Explanation
The vault deployment function is public and accepts `borrowerApr` as caller-controlled configuration. [9](#0-8)  No deployment allowlist, APR ceiling, or post-deployment governance approval prevents an arbitrary value. The attack does not require the attacker to become owner, manager, borrower, guardian, feeReceiver, queue, or Keyring admin.

The impact requires an honest borrower to draw funds and either pay or default on the inflated contractual obligation. Since normal `borrow` calls accrue interest automatically at the configured `borrowerApr`, no additional attacker privilege or malformed external-vault behavior is required. [10](#0-9) 

### Recommendation
Apply the same bounded-rate invariant used by `IdleCreditVault` to programmable borrower APR:

```solidity
// ProgrammableBorrower.sol
uint256 public constant MAX_BORROWER_APR = 20e18;

function setBorrowerApr(uint256 _apr) external {
    _checkOnlyOwnerOrManager();
    if (_apr > MAX_BORROWER_APR) revert NotAllowed();
    _accrueBorrowerInterest();
    borrowerApr = _apr;
    emit BorrowerAprSet(_apr);
}
```

Also validate `_borrowerApr` in `initialize` or validate `programmableBorrowerParams.borrowerApr` in `IdleCreditVaultFactory.deployRevolvingCreditVault`, so deployment cannot install a value that later cannot be set through the guarded setter. [11](#0-10) [2](#0-1) 

### Proof of Concept
A Foundry PoC can reproduce this on the production factory path:

```solidity
function testDeployRevolvingVaultWithExcessiveBorrowerApr() public {
    uint256 excessiveApr = 10_000e18; // 10,000% APR

    IdleCreditVaultFactory.ProgrammableBorrowerParams memory pb =
        _baseProgrammableBorrowerParams();
    pb.borrowerApr = excessiveApr;
    pb.borrower = honestBorrower;

    IdleCreditVaultFactory.StrategyData memory strategyData =
        _baseStrategyData();
    strategyData.manager = honestManager;
    strategyData.borrower = makeAddr("unusedFixedBorrower");

    factory.deployRevolvingCreditVault(
        _baseCreditVaultParams(),
        strategyData,
        pb,
        _baseAncillaryParams()
    );

    ProgrammableBorrower borrowerAdapter =
        ProgrammableBorrower(factory.lastProgrammableBorrower());

    assertEq(borrowerAdapter.borrowerApr(), excessiveApr);

    // Attacker participates only as an ordinary KYC-passing lender.
    _whitelistAndDepositAA(attacker, 100_000e6);

    vm.prank(honestManager);
    cdo.startEpoch();

    uint256 draw = 50_000e6;
    vm.prank(honestBorrower);
    borrowerAdapter.borrow(draw);

    vm.warp(block.timestamp + 365 days);

    uint256 expectedAt100Percent = draw;
    uint256 accruedAtExcessiveRate =
        borrowerAdapter.borrowerInterestAccruedNow();

    assertGt(accruedAtExcessiveRate, expectedAt100Percent * 99);
}
```

The key reproducible assertion is that deployment succeeds with `borrowerApr > IdleCreditVault.DEFAULT_MAX_APR`, after which ordinary borrower activity automatically accrues the excessive debt. [12](#0-11) [13](#0-12)

  function _borrow(uint256 assets) internal returns (uint256 withdrawnShares) {
    if (!epochAccountingActive) revert NotAllowed();
    // `0` is treated as "draw the full currently borrowable amount" after reserving epoch-end obligations.
    uint256 borrowable = availableToBorrow();
    if (assets == 0) {
      if (borrowable == 0) revert InvalidAmount();
      assets = borrowable;
    }

    // Borrows are capped by the live "reserved vs free" view so epoch-end obligations always stay covered.
    if (assets > borrowable) revert InsufficientBorrowable();

    _accrueBorrowerInterest();

    uint256 onHand = underlyingToken.balanceOf(address(this));
    if (onHand < assets) {
      uint256 shortfall = assets - onHand;
      withdrawnShares = vault.withdraw(shortfall, address(this), address(this));
      if (epochAccountingActive) {
        epochWithdrawnFromVault += shortfall;
      }
      emit WithdrawnFromVault(shortfall, withdrawnShares, address(this));
    }

    // Executors can trigger the draw, but proceeds are always delivered to the borrower wallet.
    borrowerPrincipal += assets;
    underlyingToken.safeTransfer(borrower, assets);

  /// @notice Checkpoint borrower interest up to `block.timestamp`.
  /// @dev The first call only seeds the accrual clock. When principal or APR is zero we still
  /// move the timestamp forward so interest starts accruing cleanly from the next state change.
  function _accrueBorrowerInterest() internal {
    uint256 last = lastBorrowerAccrual;
    uint256 principal = borrowerPrincipal;
    if (last == 0 || principal == 0 || borrowerApr == 0) {
      lastBorrowerAccrual = block.timestamp;
      return;
    }
    uint256 elapsed = block.timestamp - last;
    if (elapsed == 0) return;
    borrowerInterestAccrued += _calcInterest(principal, elapsed);
    lastBorrowerAccrual = block.timestamp;
