### Title
Unclaimed dust instant-withdrawal permanently bricks lazy default-recovery initialization, blocking all withdrawal requests and loss-adjusted epoch stops - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault._ensureDefaultRecoveryInitialized()` reverts whenever `pendingInstantWithdraws != 0` (or when legacy `pendingWithdraws != 0` while the epoch is still running). An unprivileged attacker can open a minimal `requestInstantWithdraw` — a dust-sized receipt that the protocol itself can never force-settle — and leave it unclaimed forever. Every subsequent call into `_ensureDefaultRecoveryInitialized` reverts, which DoSes `requestWithdraw` and `requestInstantWithdraw` for all users, and (together with a second dust `requestWithdraw` receipt) permanently blocks `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` in the loss branch, preventing `stopEpochWithDuration(_lossAmount)` from ever closing an epoch under loss. This is the direct analog of "unregisterVault can be DoSed by 1 wei": a cleanup/accounting gate that requires a zero-dust invariant the attacker can cheaply violate, with no admin dust-sweep available.

### Finding Description
On upgraded `IdleCreditVault` strategies (deployed before `defaultRecoveryInitialized` existed), the flag starts `false` and is lazily initialized on the first call that touches recovery accounting. Fresh deployments set it to `true` in `initialize`, so the bug targets upgrade deployments. [1](#0-0) 

```solidity
function _ensureDefaultRecoveryInitialized() internal {
    if (defaultRecoveryInitialized) return;
    if (pendingInstantWithdraws != 0) revert NotAllowed();
    if (pendingWithdraws != 0) {
      IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
      if (cdo.epochEndDate() != 0 || cdo.defaulted()) revert NotAllowed();
      pendingWithdraws = 0;
      apr0TotalPrincipal = 0;
    }
    defaultRecoveryInitialized = true;
    canTransfer = false;
}
```

`pendingInstantWithdraws` is only decremented by `collectInstantWithdrawFunds`, which the IdleCDO calls during `getInstantWithdrawFunds` when a *requester* claims — there is no owner/manager path to force-fund or clear an unclaimed instant receipt: [2](#0-1) [3](#0-2) 

Attack sequence on an upgraded vault (epoch running or in buffer):

1. Attacker deposits 1 unit, calls `IdleCDOEpochVariant.requestInstantWithdraw` (KYC-passing lender, so allowed) for 1 wei of basis. `instantWithdrawsRequests[attacker] = 1`, `pendingInstantWithdraws = 1`. `_ensureDefaultRecoveryInitialized` reverts here — but the revert happens *inside* the same call before the mint/increment? No — order in `requestInstantWithdraw`: `_ensureDefaultRecoveryInitialized()` is called *before* mutating. So pre-upgrade the attacker must instead create the pending instant withdrawal *before* the upgrade (legacy flow had no such gate), or create it on a vault where init already passed. The viable attacker path: have an unclaimed instant receipt pending at upgrade time (any honest or malicious pending request qualifies — attackers can simply never claim). Post-upgrade, every `requestWithdraw` and `requestInstantWithdraw` hits the `pendingInstantWithdraws != 0` revert.

2. Since the attacker never calls `claimInstantWithdrawRequest`, `pendingInstantWithdraws` can never reach zero through the only existing path — `collectInstantWithdrawFunds` is `_onlyIdleCDO` and is only invoked inside the claim flow. There is no `transferToken`-style rescue that decrements the counter, and no admin dust-sweep.

3. Second-order DoS: suppose a legacy `pendingWithdraws != 0` also exists at upgrade and the pool is mid-epoch (`epochEndDate != 0`). The `cdo.epochEndDate() != 0` branch reverts unconditionally. Even after a clean pool close normalizes `pendingWithdraws`, a single dust instant receipt keeps initialization blocked.

4. Because initialization is blocked, `collectWithdrawFunds` reverts in the partial-funding branch (`if (!defaultRecoveryInitialized) revert NotAllowed()`) and `previewLossAdjustedWithdrawFunds` reverts for any `_lossAmount > 0` when pending receipts exist — so `stopEpochWithDuration` with a realized loss can never execute, permanently freezing an epoch that requires loss realization to close. [4](#0-3) [5](#0-4) 

### Impact Explanation
- All user-initiated withdrawals are frozen: `requestWithdraw` and `requestInstantWithdraw` revert for every user while the dust instant receipt is open — a permanent freeze of the withdrawal queue (fund impact: entire TVL unable to exit, quantified as full pool NAV for the duration; effectively permanent since the attacker controls the only settle path).
- Loss-mode epoch closure (`stopEpochWithDuration` with `_lossAmount`) is permanently blocked while `!defaultRecoveryInitialized` and pending receipts exist, leaving the vault stuck in `isEpochRunning` — the CDO cannot realize losses, socialize them, or move toward recovery/finalization.
- No privileged escape: `transferToken` (owner rescue) moves tokens but cannot decrement `pendingInstantWithdraws`; only the requester's claim triggers `collectInstantWithdrawFunds`, and the attacker simply never claims. Honest users are equally affected — one forgotten instant receipt at upgrade time bricks the same surface.

### Likelihood Explanation
Medium-high on any upgrade deployment. The trigger requires a single unclaimed instant withdrawal (even 1 wei) present at the moment `_ensureDefaultRecoveryInitialized` first runs — an everyday state, not an exotic one — or a malicious lender who spends ~1 wei to keep it permanently open. Berachain-style sequencing isn't needed; persistence suffices. Fresh vaults initialize `defaultRecoveryInitialized = true` and are unaffected, which is why severity is bounded to upgrade targets rather than universal.

### Recommendation
- Make `_ensureDefaultRecoveryInitialized` tolerant of dust: either initialize unconditionally and leave `pendingInstantWithdraws`/`pendingWithdraws` as claimable legacy buckets, or add an owner/manager function that force-settles (funds and clears) sub-dust pending counters, mirroring the report's "admin dust-sweep" mitigation.
- Alternatively, allow `collectInstantWithdrawFunds` to be invoked by manager/owner for arbitrary users so stuck receipts can be funded and cleared without requester cooperation.
- If initialization must gate on clean state, emit a measurable threshold (e.g., only revert above a dust floor) so a 1-wei attacker receipt cannot block it.

```solidity
    // 2) Every subsequent withdrawal request reverts in _ensureDefaultRecoveryInitialized
    address victim = makeAddr("victim");
    _depositWithUser(victim, 10_000 * ONE_SCALE, true);

    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));

    // 4) Consequence: a loss-stop via stopEpochWithDuration also reverts through
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
```

```text
  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();
```
