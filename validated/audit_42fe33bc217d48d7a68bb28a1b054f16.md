### Title
Unverified `Metadata.WorkflowDonID` (when `workflowDONBindingGate` is disabled) bypasses vault zone-b owner allowlist restriction - ([File: core/capabilities/vault/capability.go])

### Summary
When `workflowDONBindingGate.Limit(ctx)` returns `false` (gate disabled), `executeCapabilityRequest` skips the check that binds `capabilityRequest.Metadata.WorkflowDonID` to the authenticated `callingDonID`, and the unmodified, attacker-controlled `WorkflowDonID` is passed straight through `capability.Execute` into `Capability.Execute` in `core/capabilities/vault/capability.go`. That value is then used as the sole input to `zoneBRestrictor.enforce`, which decides whether zone-b's owner allowlist restriction applies to a `GetSecrets` call.

### Finding Description
`executeCapabilityRequest` unmarshals the request, checks the gate, and only enforces the DON-binding when `enabled` is true: [1](#0-0) 
The test suite explicitly documents that with the gate disabled, a request whose `Metadata.WorkflowDonID` differs from the authenticated `callingDonID` still executes successfully: [2](#0-1) 
The unverified `capabilityRequest` (including its `Metadata.WorkflowDonID`) is passed unchanged into `capability.Execute(ctx, capabilityRequest)`: [3](#0-2) 
For the vault capability, `Execute` uses `request.Metadata.WorkflowDonID` directly as the authoritative DON ID to decide whether the zone-b owner allowlist restriction is enforced: [4](#0-3) 
`zoneBRestrictor.enforce` then resolves that DON ID against the registry to decide zone-b membership and, if zone-b, requires the caller's `WorkflowOwner` to be allowlisted: [5](#0-4) 
The comment on `isZoneBWorkflowDON` claims "This does not trust any caller-supplied zone data," but that claim only holds for the DON's *family membership* lookup — the `workflowDonID` used as the lookup key itself is caller-supplied and, when the binding gate is disabled, is never cross-checked against the authenticated calling DON: [6](#0-5) 
This means an attacker whose real DON is zone-b (restricted, non-allowlisted owner) can forge `Metadata.WorkflowDonID` to any non-zone-b DON ID to have `isZoneBWorkflowDON` return `false`, skipping the `ownerAllowed.AllowErr` check entirely and bypassing the zone-b owner allowlist for `GetSecrets` reads.

Notably, the sibling code path in `core/services/workflows/v2/secrets.go` (`vaultGetSecretsMetadata`) explicitly documents and relies on the binding gate to make `WorkflowDonID` trustworthy on the server side, confirming the field is expected to be authoritative for downstream authorization once bound: [7](#0-6) 

### Impact Explanation
If `RemoteExecutableWorkflowDONBindingEnabled` / `workflowDONBindingGate` defaults to or is rolled out in the disabled state, a workflow running on a restricted zone-b DON (or, more generally, any workflow DON) can spoof `Metadata.WorkflowDonID` to bypass the `VaultZoneBWorkflowGetSecretsRestrictEnabled` + `PerOwner.VaultZoneBGetSecretsAllowed` allowlist gate in `zoneBRestrictor.enforce`, and obtain `GetSecrets` responses that should have been restricted to allowlisted owners. This is an authorization/allowlist bypass — a distinct capability-layer control being silently defeated by trusting attacker-controlled metadata, matching the "allowlist bypass" bounty impact class. Confidentiality impact is capped by the fact that the secrets themselves are still gated by `owner` matching against `request.Metadata.WorkflowOwner` (`vaultutils.NormalizeOwner` checks at capability.go:130-133), so the primary exploitable effect here is bypassing the *zone-b restriction gate itself*, not arbitrary secret exfiltration for other owners' data.

### Likelihood Explanation
Exploitability depends entirely on the default/rollout state of `workflowDONBindingGate` (backed by `cresettings.Default.RemoteExecutableWorkflowDONBindingEnabled`). If disabled by default (as implied by the question and the "gate disabled" test case being a first-class, intentionally-tested behavior), any workflow author on any DON can forge this field with no special privileges — they already control the `RequestMetadata` sent as part of their own workflow's capability calls. No operator/host access is required; only the ability to run a workflow that issues a vault `GetSecrets` request with an attacker-chosen `WorkflowDonID`.

### Recommendation
Do not gate the DON-binding check behind a rollout-controlled `GateLimiter` for security-relevant metadata. Either enforce `WorkflowDonID == callingDonID` unconditionally in `executeCapabilityRequest`, or have `zoneBRestrictor.enforce` (and any other consumer of `Metadata.WorkflowDonID` for authorization) independently verify the field against the authenticated calling DON ID rather than trusting it directly, regardless of the gate's state.

### Proof of Concept
1. In `core/capabilities/vault/zone_b_restriction_test.go`, construct a `zoneBRestrictor` with `restrictEnabled=true` and an owner allowlist that excludes a given owner, and a fake `CapabilitiesRegistry` where DON ID `1` is `zone-b` and DON ID `2` is not.
2. Call `enforce(ctx, 1)` with a non-allowlisted owner in context — assert it returns an error (baseline, confirms restriction works).
3. Simulate the end-to-end path: build a `commoncap.CapabilityRequest` with `Metadata.WorkflowOwner` = non-allowlisted owner but `Metadata.WorkflowDonID = 2` (a non-zone-b DON), while the actual `callingDonID` used to authenticate the request is `1` (zone-b).
4. Drive this through `request.NewServerRequest` / `OnMessage` with `workflowDONBindingGate = limits.NewGateLimiter(false)` (disabled), matching the pattern in `Test_ServerRequest_WorkflowDONBinding`'s "gate disabled" subtest.
5. Assert that `executeCapabilityRequest` succeeds (no DON-mismatch error) and that `capability.Execute` (vault) receives `Metadata.WorkflowDonID = 2`, causing `zoneBRestrictor.enforce` to treat the request as non-zone-b and skip the `ownerAllowed.AllowErr` check — i.e., the `GetSecrets` request proceeds despite the owner not being allowlisted and the real calling DON (1) being zone-b. Contrast with the same scenario when the gate is enabled (`limits.NewGateLimiter(true)`), where the request is rejected before reaching the vault capability at all.

```go
func (z *zoneBRestrictor) enforce(ctx context.Context, workflowDonID uint32) error {
	enabled, err := z.restrictEnabled.Limit(ctx)
	if err != nil {
		return fmt.Errorf("could not evaluate zone-b vault read restriction gate: %w", err)
	}
	if !enabled {
		return nil
	}

	isZoneB, err := z.isZoneBWorkflowDON(ctx, workflowDonID)
	if err != nil {
		// Fail closed: if we cannot authoritatively resolve the caller's zone, do
		// not proceed. The registry is in-process, so this only fires for an
		// unknown/unregistered WorkflowDonID.
		return err
	}
	if !isZoneB {
		return nil
	}

	if err := z.ownerAllowed.AllowErr(ctx); err != nil {
		return fmt.Errorf("zone-b workflow DON may only read vault secrets for allowlisted workflow owners: %w", err)
	}
	return nil
```
