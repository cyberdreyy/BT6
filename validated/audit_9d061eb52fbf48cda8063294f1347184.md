### Title
No vulnerability found — ext_costs is always resolved deterministically at apply time, not cached from receipt creation - (File: runtime/near-vm-runner/src/imports.rs / core/parameters/src/config_store.rs)

### Summary
The premise of the question is factually incorrect for this codebase: `Config`/`ExtCostsConfig` is never snapshotted at receipt-creation time and carried forward on the `Receipt`. It is looked up fresh, once per chunk, from the `RuntimeConfigStore` keyed by the **epoch's protocol version at the moment the chunk is being applied**, and that single `Arc<RuntimeConfig>` is threaded through `ApplyState` into every receipt processed in that chunk, including the `VMLogic`/`WasmtimeVM` construction. Since all honest nodes apply the same chunk under the same epoch/protocol version, they resolve identical `ext_costs`.

### Finding Description
`RuntimeAdapter::apply_chunk` resolves the protocol version from the epoch of the block being applied and fetches the config via `self.runtime_config_store.get_config(protocol_version)` [1](#0-0) , then builds `ApplyState` carrying that single `config: Arc<RuntimeConfig>` for the whole chunk [2](#0-1) . `RuntimeConfigStore::get_config` performs a floor lookup on protocol version, not on receipt-creation time or any timestamp carried in the receipt [3](#0-2) . The `Receipt` data structure itself carries actions, gas price, deposits, etc., but never a config/fee snapshot — there is no field for it, and nothing in `Runtime::process_receipt`/`apply_action` reads a config from the receipt; the config always comes from the currently-active `ApplyState.config`, which is passed down into `WasmtimeVM::run`/`VMLogic` construction (`Ctx::new` clones `Arc<Config>` from `result_state.config`, itself built at apply time) [4](#0-3) .

Config changes in `RuntimeConfigStore` are keyed strictly by `ProtocolVersion`, and protocol version changes only take effect at epoch boundaries via the validator-vote/tally mechanism (not mid-epoch, not per-chunk, not attacker-triggerable) [3](#0-2) . There is no "congestion-scaled `ext_costs` surcharge" feature in this codebase: congestion control affects gas price via `pessimistic_gas_price_inflation` and receipt admission/throttling (delaying execution), and separately tracks `receipt_congestion_gas` for buffer/queue accounting [5](#0-4)  — it does not rewrite `ExtCostsConfig` values consumed by the VM. Consequently, a receipt delayed by congestion into a later chunk is charged according to whatever `ExtCostsConfig` is active for that chunk's epoch at apply time — deterministically, identically, by every honest node applying that same chunk, because the config selection depends only on consensus-visible epoch/protocol-version state, never on receipt-local or node-local state.

### Impact Explanation
No impact: the described divergence path does not exist. Both honest nodes applying receipt R at the same chunk height necessarily use `epoch_manager.get_epoch_protocol_version(&epoch_id)` for that exact chunk's epoch and therefore the identical `Arc<RuntimeConfig>` / `ExtCostsConfig`, since epoch/protocol version is itself a consensus-agreed value, not something that could differ between "creation-time" and "apply-time" caches on different nodes.

### Likelihood Explanation
Not applicable — there is no reachable code path where the runtime reads or caches `ext_costs` from a receipt-creation-time snapshot; the described precondition ("mid-epoch config parameter change reachable e.g. congestion-based dynamic fee multiplier") does not exist in this codebase's design, since `RuntimeConfigStore` changes are keyed only by protocol version and protocol version only changes at epoch boundaries under validator vote, which is outside the unprivileged attacker's control.

### Recommendation
N/A — no fix needed. If reviewers want documentation reinforcement, `docs/architecture/gas/parameter_definition.md` already states the rule explicitly: config "should not be cached. It should be read from the store once per chunk and then passed down to all functions that need it," matching the actual implementation [6](#0-5) .

### Proof of Concept
N/A — the premised attack precondition (mid-epoch `ext_costs` change reachable by an unprivileged actor, and receipt-creation-time config caching) does not exist in the code, so no test can construct the divergent scenario described.

    config: &RuntimeConfig,

    match receipt.versioned_receipt() {
        VersionedReceiptEnum::Action(action_receipt) => {
            // account for gas guaranteed to be used for executing the receipts
            action_receipt_congestion_gas(receipt, config, action_receipt.into())
        }
        VersionedReceiptEnum::Data(_data_receipt) => {
            // Data receipts themselves don't cost gas to execute, their cost is
            // burnt at creation. What we should count, is the gas of the
            // postponed action receipt. But looking that up would require
            // reading the postponed receipt from the trie.
            // Thus, the congestion control MVP does not account for data
            // receipts or postponed receipts.
            Ok(Gas::ZERO)
        }
