### Title
`get_inflation_reward` can panic via `.expect("...populated block_height")` on the epoch-boundary block when `block_height_cf` has not yet been asynchronously written - ([File: rpc/src/rpc.rs])

### Finding Description
In `JsonRpcRequestProcessor::get_inflation_reward` (`rpc/src/rpc.rs`), when the target epoch has partitioned rewards enabled and the requested address's partition has not yet been distributed, the code computes the "rewards complete" block height from `epoch_boundary_block.block_height`: [1](#0-0) 

The `.expect("every block after partitioned_epoch_reward_enabled should have a populated block_height")` assumes `block_height` is always `Some` for any block once partitioned rewards are active. However, `Blockstore::build_versioned_confirmed_block` explicitly documents that `block_height` (and `block_time`) are populated **asynchronously** and may legitimately be `None` right after a block becomes available: [2](#0-1) 

`get_block` (used to fetch `epoch_boundary_block`) only back-fills `block_time`/`block_height` from the live bank state when it goes through the **confirmed, non-rooted** code path (`commitment.is_confirmed()` branch that calls `blockstore.get_complete_block`): [3](#0-2) 

But when the slot is at or below the highest super-majority root, `get_block` takes the rooted path, calling `blockstore.get_rooted_block(slot, true)` directly and returning whatever `block_height`/`block_time` blockstore currently holds, with **no back-fill fallback**: [4](#0-3) 

The epoch-boundary block queried in `get_inflation_reward` is exactly the first block of an epoch whose partitioned-rewards distribution is still in progress (that's the only way the `.get(partition_index)` lookup at line 835 can miss and fall into the `.ok_or_else` closure). This means the epoch-boundary block is very recent — potentially rooted only moments before the RPC call — so there is a real timing window where `block_height_cf` has not yet been written by the asynchronous writer (`transaction_status_service.rs`) even though the block itself is already rooted/confirmed and returned by `get_blocks_with_limit`/`get_block`. In that window, `epoch_boundary_block.block_height` is `None`, and the `.expect()` panics.

### Impact Explanation
A single unprivileged `getInflationReward` call, issued at the right moment relative to the epoch boundary (querying the previous epoch when the current epoch's partitioned-rewards distribution is still active and the queried address's partition hasn't been distributed yet), can hit an `.expect()` panic inside a live JSON-RPC handler path. This is a decoder/handler panic reachable from a single client request, matching the "decoder panic and misreporting" / crash-from-one-request bounty category. Depending on how the RPC dispatch task is scheduled (spawned tokio task vs. inline future), this either aborts only the offending request or, if unwind boundaries are missing, can propagate and destabilize the serving runtime — the code was not written defensively for this legitimately-documented `None` case, which is a genuine logic bug regardless of blast radius.

### Likelihood Explanation
The precondition is narrow but real and not attacker-controlled data forgery: it only requires timing — issuing the request while (a) partitioned rewards are enabled for the queried epoch, (b) the target address's reward partition has not yet been distributed, and (c) the epoch-boundary block was rooted/confirmed just recently enough that the asynchronous `block_height_cf` write (performed by `transaction_status_service`) has not yet completed. Because block/entry writes and the async block-height cache population are decoupled, this window is real on every partitioned-rewards epoch transition, and is more likely to be hit under I/O backpressure or heavy validator load, which widens the async-write lag. No special privileges, multiple calls, or malformed data are required — a single well-timed `getInflationReward` call suffices.

### Recommendation
In `get_inflation_reward`, do not `.expect()` on `epoch_boundary_block.block_height`. Instead, treat `None` the same as "rewards complete height unknown" by falling back to live bank state (as already done in the confirmed-commitment branch of `get_block`) or by returning `RpcCustomError::EpochRewardsPeriodActive` with a best-effort/omitted `rewards_complete_block_height`, or by re-querying the block/bank until block_height is available, instead of panicking.

### Proof of Concept
Rust integration test sketch (in `rpc/src/rpc.rs` test module or an integration harness):
1. Construct a `JsonRpcRequestProcessor` backed by a real `Blockstore` and `BankForks`, with partitioned rewards enabled for the epoch under test (using existing partitioned-rewards test helpers, e.g. `create_reward_bank` from `runtime/src/bank/partitioned_epoch_rewards/mod.rs` tests).
2. Advance to the epoch boundary block, root it via `set_roots`, but intercept/delay the call to `Blockstore::set_block_height` for that slot (simulate the async-writer lag by simply not calling `set_block_height` yet, mirroring real async timing).
3. Call `processor.get_inflation_reward(addresses, Some(RpcEpochConfig{epoch: Some(rewarded_epoch), ..}))` for an address whose reward partition has not yet been produced (i.e., `block_list.len() < partition_index`).
4. Expected (buggy) result: the call panics inside `.expect("every block after partitioned_epoch_reward_enabled should have a populated block_height")`.
5. After the fix, assert instead that the call returns `Err(RpcCustomError::EpochRewardsPeriodActive { .. })` (or equivalent) without panicking.
