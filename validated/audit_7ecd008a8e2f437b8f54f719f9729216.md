### Title
Dust withdraw request permanently bricks `processWithdrawRequests`, freezing all queued withdrawals - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
`IdleCDOEpochQueue.processWithdrawRequests()` reverts with `Is0()` whenever the implied epoch withdraw price rounds to zero: `epochPrice = _underlyingsRequested * ONE_TRANCHE / _pending`. Because tranche tokens use 18 decimals while underlyings (e.g. USDC) use 6, a single dust-sized `requestWithdraw(1)` makes `_cdo.requestWithdraw(_pending, tranche)` return 0 underlyings, so the division yields 0 and the transaction reverts. The revert happens **after** `_cdo.requestWithdraw` burned the queue's tranches and minted strategy-token receipts inside the same transaction, so the whole call rolls back and `epochPendingWithdrawals[_epoch]` stays non-zero forever. Every later call hits the same revert, and the manager has no privileged path to remove a single user's request (`deleteWithdrawRequest` is per-`msg.sender` only). The queue's entire withdrawal pipeline is deadlocked for that epoch: no claims are opened (`pendingClaims` can't be set), and `pendingClaims == false` also blocks nothing else — but every user who queued a withdrawal in that epoch permanently loses access until the dust-requester voluntarily deletes their request.

### Finding Description
Bug class analog: like CVE-2021-4147 (a malicious guest repeatedly forcing a state that deadlocks the host), here an unprivileged KYC'd user forces a permanently reverting state that deadlocks the privileged epoch-processing function.

Attack sequence (running epoch, fixed-APR mode, 6-decimal underlying):

1. Attacker (any KYC-passing lender / tranche holder) deposits a minimal amount, receives ≥1 wei of tranche tokens.
2. Attacker calls `queue.requestWithdraw(1)` during the running epoch. This pulls 1 wei of tranche into the queue and sets `epochPendingWithdrawals[nextEpoch] = 1`. Honest users may add their own requests; pending becomes `1 + honestAmount` — the attacker can instead grief an epoch where only dust+small requests exist, or more reliably: the attacker requests `1` wei and if honest users' requests push `_underlyingsRequested` above 0 the revert no longer triggers, so the cleanest grief is being the only/majority requester, or requesting an amount `P` such that `P * tranchePrice < ONE_TRANCHE` (any request below ~1e12 wei of tranche at a ~1 USDC price). For `pending = 1` wei, `_underlyingsRequested = floor(1 * price / 1e18) = 0`.
3. In the buffer period, manager calls `processWithdrawRequests()`. `_cdo.requestWithdraw(1, tranche)` returns 0 underlyings, `_epochPrice = 0 * 1e18 / 1 = 0`, revert `Is0()`.
4. Repeat forever: the call always reverts, `epochPendingWithdrawals` is never cleared, `pendingClaims` never set, `epochPendingClaims` never populated → no user's withdrawal for that epoch can ever be claimed. There is no admin function to prune individual requests; the only escape is the attacker calling `deleteWithdrawRequest`, which they won't.

Even if honest users add large requests, the attacker can sandwich: request dust in epoch N where they are the sole requester (common for BB queues or low-activity epochs), guaranteeing the block.

### Impact Explanation
Permanent freezing of funds: all tranche tokens queued for withdrawal in the poisoned epoch are locked in the queue contract indefinitely (users already transferred them in `requestWithdraw`, and `deleteWithdrawRequest` only returns the caller's own). The DoS requires no privileged action, no timing race, and costs the attacker ~1 wei of tranche plus gas. Funds at risk = total `epochPendingWithdrawals` of the epoch plus the blocked processing of subsequent epochs while `pendingClaims` bookkeeping desyncs.

### Likelihood Explanation
Requires only an unprivileged KYC-passing lender with a dust tranche balance and an epoch in which their dust dominates `epochPendingWithdrawals`. On a BB tranche queue or any low-activity epoch this is trivially satisfiable. The `Is0()` guard itself confirms the zero-price case is reachable but treats it as fatal instead of skipping/refunding the dust request.

### Recommendation
In `processWithdrawRequests`, do not revert on `_epochPrice == 0`. Options:
- Enforce a minimum request amount in `requestWithdraw` (e.g. require `amount * virtualPrice(tranche) / ONE_TRANCHE >= 1` underlying wei), or
- When `_underlyingsRequested == 0`, mark the epoch via the existing `isEpochWithdrawZero` path (as `processWithdrawalClaims` already does for rounded-to-zero recoveries) so users can clear their receipts, or
- Refund dust requests inline by transferring the tranche tokens back instead of forwarding them to the CDO.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry/IdleCDOEpochQueue.t.sol` harness, 6-decimal USDC underlying):

```solidity
function testDustWithdrawBlocksEpoch() external {
    _stopCurrentEpoch();              // buffer of epoch 0 -> epoch 1
    _depositWithUser(FASA, 1e6);      // FASA gets ~1e18 tranche
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // dust request only
    vm.prank(FASA);
    queue.requestWithdraw(1);         // 1 wei of tranche

    _stopCurrentEpoch();              // epoch 2 buffer

    vm.prank(manager);
    vm.expectRevert(Is0.selector);
    queue.processWithdrawRequests();  // reverts: epochPrice == 0

    // repeat: still reverts, pending never cleared
    vm.expectRevert(Is0.selector);
    queue.processWithdrawRequests();
    assertGt(queue.epochPendingWithdrawals(2), 0);
    // any other user's queued withdrawal in epoch 2 is permanently stuck
}
```

Caveat: I could not fully read `IdleCDOEpochVariant.requestWithdraw`'s dust return path within the iteration budget; the PoC assumes it returns 0 underlyings for a 1-wei tranche burn rather than reverting — if it reverts internally on zero output the same liveness failure holds (the call still always reverts and `epochPendingWithdrawals` is never cleared).
