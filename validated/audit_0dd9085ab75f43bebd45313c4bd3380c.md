Both `multisig/src/lib.rs` and `multisig2/src/lib.rs` share the exact same DeleteKey/DeleteMember flaw: when a signer/member is removed, only confirmations belonging to requests **they created** are purged; confirmations they cast on **other, still-pending** requests remain in the `confirmations` set and continue to count toward `num_confirmations` even after that key/member is no longer live.### Title
Stale confirmations from removed multisig signer allow request execution below live threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
This is the same bug class as the Althea report: a running counter/collection used to gate an action (`nextWithdrawal` vs `ManagedNFTs.length`) is not kept in sync with removals from the underlying set (NFTs released), letting stale state authorize/mis-gate an operation. In `multisig2` and `multisig` the analog is the `confirmations` set for a pending `MultiSigRequest` versus the live `members`/key set: when a member/key is deleted, only confirmations on requests **that member created** are purged, not confirmations that member had already cast on **other still-pending requests**. Those stale confirmations keep counting toward `num_confirmations`, so a request can execute with fewer live confirmers than the configured threshold — an authorization boundary bypass, not merely a DoS.

### Finding Description
The custody/authorization binding that must hold is:

`confirmations counted toward execution == confirmations cast by currently-live members`

In `multisig2/src/lib.rs`, `confirm()` decides to execute purely by counting entries already stored in `self.confirmations.get(&request_id)`: [1](#0-0) 

`delete_member()` only cleans up requests **created by** the removed member (`r.member == member`); it never scans `self.confirmations` values to strip that member's `confirm()` votes from other pending requests: [2](#0-1) 

So if member `M` confirmed request `X` (created by someone else) before `M` was removed via a `DeleteMember` governance action, `M`'s entry stays inside `self.confirmations[X]` forever. `assert_valid_request()` only checks that the *caller* confirming now is a current member; it never re-validates the pre-existing entries in the confirmations set: [3](#0-2) 

`multisig/src/lib.rs` (v1, key-based) has the identical pattern: `DeleteKey` only removes confirmations for requests whose creator (`signer_pk`) is the removed key, not confirmations that key cast on other requests, and `confirm()` counts the raw set size the same way: [4](#0-3) [5](#0-4) 

### Impact Explanation
This crosses the "confirmations counted versus live members" threshold boundary explicitly called out as in-scope: a request can be executed (arbitrary `Transfer`, `AddKey`/`AddMember` with full access, `FunctionCall`, `DeployContract`, etc.) with the count made up partly of a former member's stale vote, meaning fewer *actually authorized, currently live* parties approved it than `num_confirmations` requires. This is a Critical-class finding per the given impact set: "a multisig request executed below threshold." It can enable unauthorized fund transfers or unauthorized key/member additions out of the multisig account.

### Likelihood Explanation
No privileged actor, redeploy, or victim key is required beyond the normal multisig workflow: any unprivileged member (or attacker who becomes a member and is later legitimately/maliciously removed) can pre-confirm a pending request, then have themselves (or collude to have another member) removed via the standard `DeleteMember`/`DeleteKey` governance action, after which any remaining live member's confirmation completes the count and triggers execution — with one fewer live approver than the threshold intends. This only requires ordinary use of `add_request`, `confirm`, and `DeleteMember`/`DeleteKey`, all reachable by existing members without any code deployment or foundation privilege.

### Recommendation
When removing a member/key, iterate all entries in `self.confirmations` (not just requests they created) and remove the departing member's/key's vote from every set; alternatively, re-validate at `confirm()`-time that every already-recorded confirmer is still present in `self.members` (or has a live key) before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(requestX)` → `confirmations[X] = {A}`.
3. `B` calls `confirm(requestX)` → `confirmations[X] = {A, B}` (still `<3`, not executed).
4. Members create and confirm a separate request `Y = DeleteMember{B}` with 3 live confirmations (`A, C, D`) → executes `delete_member(B)`. This removes `B`'s access key and entry from `members`, and deletes confirmations only for requests `B` had *created* (none here) — `confirmations[X]` is untouched, still `{A, B}`.
5. Live members are now `{A, C, D}` (3 members), `num_confirmations` is still 3.
6. `C` calls `confirm(requestX)` → `confirmations[X].len() + 1 == 3 >= num_confirmations` → `execute_request` fires.
7. `requestX` executes even though only `A` and `C` are currently live members who approved it — one fewer live confirmation than the required threshold of 3, because `B`'s stale vote was counted after removal. [1](#0-0) [2](#0-1)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************

            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
