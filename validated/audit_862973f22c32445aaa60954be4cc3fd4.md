### Title
Missing per-instance authorization in `VaultController.ExportDKGResult` allows any authenticated caller to read another party's DKG result package - ([File: core/web/vault_controller.go])

### Finding Description
`ExportDKGResult` accepts an arbitrary, caller-supplied `InstanceID` in the request body and passes it directly to `vault.NewVaultORM(vc.App.GetDB()).ReadResultPackage(ctx, dkgocrtypes.InstanceID(req.InstanceID))` with no check that the InstanceID belongs to the requesting party or session: [1](#0-0) 

The only validation performed is that `InstanceID` is non-empty; there is no lookup of "who owns this DKG ceremony" and no comparison against the caller's identity, key material, or role scope. If the lookup succeeds, the handler unconditionally returns `hexPackage := hex.EncodeToString(v.ReportWithResultPackage)` to the caller via `presenters.NewExportDKGResultResource`, which is the raw serialized DKG result/report containing the node's encrypted share material for that ceremony. Because the route is gated only by session/role middleware at the router layer (standard authenticated-route wrapper in `core/web/router.go`) and not by any resource-level ACL tied to `InstanceID`, any caller who can reach this endpoint (i.e., any authenticated node-API user) can exfiltrate the result package for any DKG instance ID they can obtain or guess, regardless of which party's ceremony it belongs to. This is a resource-level authorization gap independent of the role tier enforced on the route — the vulnerability is that the endpoint does not scope data access by tenant/party ownership at all.

Note: I was unable to fully confirm from the tool output the exact minimum session role (view vs. edit) required by the route wrapper for `/v2/vault/dkg_results/export` due to truncated search results on `core/web/router.go`; however, this does not change the core finding, since the handler itself performs zero ownership checks once past the role gate.

### Impact Explanation
This is a direct cross-tenant secret disclosure: the exported `ReportWithResultPackage` contains DKG ceremony result data (including the node's encrypted key share for that instance), which is meant to be confined to the participants of that specific DKG ceremony. Disclosure to an unrelated authenticated user violates secret confinement and could expose key-share material used to reconstruct or attack the vault's threshold key, corresponding to Chainlink's "key/secret material disclosure" bounty impact class.

### Likelihood Explanation
Exploitation only requires: (1) an authenticated session/API token capable of hitting the vault export route (view-level access, since no elevated role check exists in the handler itself), and (2) knowledge or guessability of a foreign `InstanceID`. `InstanceID` values are not secrets by design in DKG protocols (they are ceremony identifiers, often predictable/sequential or discoverable via logs/other API responses), making this trivially repeatable at zero cost once a valid session exists.

### Recommendation
Add an ownership/authorization check in `ExportDKGResult` (and `VerifyDKGResult`) that verifies the requesting session/party is a legitimate participant of the specified `InstanceID`'s DKG ceremony before calling `ReadResultPackage`, e.g., by cross-referencing instance-to-party mapping in the vault ORM, or by scoping the query to instances owned by the authenticated node/party. Return 404 for any InstanceID not owned by the caller, matching the behavior described in the proof idea.

### Proof of Concept
1. Seed two DKG result rows in the vault ORM with distinct `InstanceID`s (`instanceA` owned by "tenant A", `instanceB` owned by "tenant B"), each with distinct `ReportWithResultPackage` bytes.
2. Using `core/web/vault_controller_test.go` test harness, authenticate an HTTP client with a session/token associated with tenant A (or simply any valid authenticated session, since no ownership binding exists).
3. POST `/v2/vault/dkg_results/export` with `{"instanceId": "instanceB"}`.
4. Assert current (vulnerable) behavior: HTTP 200 with `exportDKGResultResource.dkgResult` (hex) equal to `hex.EncodeToString(instanceB's ReportWithResultPackage)` — i.e., tenant A's session retrieves tenant B's result package.
5. Expected fixed behavior: HTTP 404 (or 403) when the InstanceID does not belong to the authenticated caller's ceremony.

func (vc *VaultController) ExportDKGResult(c *gin.Context) {
	var req ExportDKGResultRequest
	err := json.NewDecoder(c.Request.Body).Decode(&req)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("could not parse request body"))
		return
	}

	if req.InstanceID == "" {
		jsonAPIError(c, http.StatusBadRequest, errors.New("instanceId is required"))
		return
	}

	orm := vault.NewVaultORM(vc.App.GetDB())
	v, err := orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	if v == nil {
		jsonAPIError(c, http.StatusNotFound, errors.New("DKG result not found"))
		return
	}

	hexPackage := hex.EncodeToString(v.ReportWithResultPackage)
	sha := sha256.Sum256(v.ReportWithResultPackage)
	shaStr := hex.EncodeToString(sha[:])
	jsonAPIResponse(c, presenters.NewExportDKGResultResource(hexPackage, shaStr), "exportDKGResult")
