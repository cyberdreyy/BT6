### Title
Epoch-keyed loss/APR0 rates are written under the post-increment `epochNumber` but read under the pre-increment request epoch — loss-adjusted and APR0 receipts pay at par or lose interest - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.deposit()` increments `epochNumber` when called while the epoch is running (i.e., during `stopEpoch`/`stopEpochWithDuration`). Two later bookkeeping writes — `lossRecoveryPriceByEpoch[epochNumber]` in `collectWithdrawFunds` and `apr0RateByEpoch[epochNumber]` in `prepareStopEpochWithApr0` — can therefore index the *next* epoch, while all reads key on the *request* epoch stored in `lastWithdrawRequest`/`principalEpoch`. This is the direct analog of an out-of-bounds/stale-index read: data is stored at index N+1 but queried at index N, silently returning 0.

### Finding Description
- Requests record the pre-stop epoch: `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch]` (`requestWithdraw`, IdleCreditVault.sol:260-294); APR0 uses `principalEpoch = epochNumber` (`_requestWithdrawApr0`, L571-573).
- During `stopEpoch`, `deposit()` is invoked while `isEpochRunning()` is still true and does `epochNumber += 1` (L607-610).
- `collectWithdrawFunds` then writes the haircut under the bumped index: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (L421), and `prepareStopEpochWithApr0` writes `apr0RateByEpoch[epochNumber] = ...` (L537).
- Reads use the old index: `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (L790-791) and `_settleApr0` looks up `apr0RateByEpoch[_reqEpoch]` (L558).

Consequences if the increment precedes the writes:
1. `lossRecoveryPriceByEpoch[reqEpoch]` reads 0 → `_claimLossAdjustedWithdrawRequest` returns early, and `_claimFundedWithdrawRequest` pays the full un-haircutted `withdrawsRequests[_user]` at par (the `epochNumber <= lastWithdrawRequest` gate passes because epochNumber is now higher). The pool only received the reduced `_amount`, so claimants are overpaid — early claimers drain underlying owed to later receipt holders and LPs.
2. The protective revert in `requestWithdraw` (L263-271), which is supposed to force claiming a loss-adjusted receipt before re-requesting, never triggers for the same reason.
3. `apr0RateByEpoch[reqEpoch]` reads 0 → `_settleApr0` settles principal with zero interest: APR0 requesters permanently lose their accrued interest even though `pendingWithdraws` was increased by `_apr0NetInterest` (the extra funds remain trapped in the strategy).

### Impact Explanation
Direct theft/insolvency: loss-adjusted receipts redeem at par against a pool funded only for the haircut amount, so the shortfall is socialized onto other claimants and active LPs. Separately, APR0 users' earned interest is permanently unclaimable and stranded in the vault. Both break the "one receipt one payout" and loss-waterfall invariants.

### Likelihood Explanation
The bug fires on any `stopEpochWithDuration`/`collectWithdrawFunds` with a realized loss, or any `stopEpoch` with APR0 pending principal, provided the CDO calls `deposit()` (incrementing `epochNumber`) before these functions — which is the natural funding order in `IdleCDOEpochVariant`. If the CDO instead collects funds before the deposit that bumps the epoch, the indices coincide and the issue does not trigger; the PoC must confirm the actual call order in `stopEpoch`. Attackers need only be ordinary withdraw requesters (KYC'd tranche holders) — no privileged action required.

### Recommendation
Write the per-epoch records under the request epoch, not the live counter: capture `uint256 reqEpoch = epochNumber` *before* any increment (or use `epochNumber - 1` semantics consistent with `lastWithdrawRequest`), or move the `epochNumber += 1` in `deposit()` after `collectWithdrawFunds`/`prepareStopEpochWithApr0` complete. Add an invariant test asserting `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0` after a lossy stop for every user with a pending receipt.

### Proof of Concept
Foundry fork sketch (ordering dependent on `IdleCDOEpochVariant.stopEpoch` calling `strategy.deposit` before `strategy.collectWithdrawFunds` — verify in PoC):

```solidity
// setup: running epoch, APR=0 pool or normal pool
// 1. user requests withdraw during buffer -> lastWithdrawRequest[user] = N
// 2. manager calls stopEpochWithDuration(loss) via CDO
//    - deposit() bumps epochNumber to N+1
//    - collectWithdrawFunds(lossAdjustedAmount) writes lossRecoveryPriceByEpoch[N+1]
// 3. assert lossRecoveryPriceByEpoch(N) == 0 && lossRecoveryPriceByEpoch(N+1) > 0
// 4. cdo.claimWithdrawRequest(user) succeeds at par (no haircut applied)
//    -> user receives claimBasis instead of claimBasis * lossRecoveryPrice
// 5. remaining claimants' claims underflow/are unpaid => insolvency
```

Note: I was unable to confirm the exact `stopEpoch`/`stopEpochWithDuration` call order inside `IdleCDOEpochVariant.sol` within this analysis; the finding is valid only if the epoch increment happens before the rate writes. If the code already orders them correctly, this reduces to a no-issue result.
