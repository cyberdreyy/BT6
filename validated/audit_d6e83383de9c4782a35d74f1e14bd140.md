### Title
Mismatched account-count/proof-flag combinations cause `ConfidentialBurn` parser to mislabel proof-context accounts as `permissionedBurnAuthority` - ([File: transaction-status/src/parse_token/extension/permissioned_burn.rs])

### Summary
`parse_permissioned_burn_instruction`'s `PermissionedBurnInstruction::ConfidentialBurn` arm derives optional JSON fields (`instructionsSysvar`, `equalityProofContextStateAccount`, `ciphertextValidityProofContextStateAccount`, `rangeProofContextStateAccount`) by walking `account_indexes` with a hardcoded `saturating_sub(2)`/`saturating_sub(1)` reservation for the trailing authority/owner accounts. Because `check_num_token_accounts` only enforces a minimum of 4 accounts and does not tie the total account count to the proof-offset flags carried in the instruction data, an attacker who crafts a syntactically valid but non-canonical account list (fewer accounts than the flags imply) can cause the walker to prematurely "run out of room," skip a legitimate optional slot, and instead label that account slot as `permissionedBurnAuthority` (and shift the owner/authority parsing accordingly).

### Finding Description
The relevant logic is at [1](#0-0) , which walks the following account slots conditionally: [2](#0-1) 

then equality/validity/range context checks each guarded the same way, and finally: [3](#0-2) 

`check_num_token_accounts(account_indexes, 4)` only guarantees a minimum of 4 accounts [4](#0-3) ; it does not verify that `account_indexes.len()` matches the number of accounts implied by `equality_proof_instruction_offset`, `ciphertext_validity_proof_instruction_offset`, and `range_proof_instruction_offset` (all attacker-controlled fields decoded straight from instruction data with no cross-validation, since `decode_instruction_data` only checks byte-layout, not semantic consistency).

Concretely: with `has_sysvar = true` (any offset != 0) and `equality_proof_instruction_offset == 0` (context-account mode) and `ciphertext_validity_proof_instruction_offset == 0` (context-account mode) and `range_proof_instruction_offset != 0` (offset mode), the "well-formed" real-program layout is: `account, mint, instructionsSysvar, equalityCtx, validityCtx, permissionedBurnAuthority, owner` (7 accounts). If the attacker instead supplies only 6 account indices, the walker computes:
- offset=2, `has_sysvar`→ assign `instructionsSysvar` = idx[2], offset=3 (guard `2 < 6-2=4` passes)
- `equality_offset==0` → assign `equalityProofContextStateAccount` = idx[3], offset=4 (guard `3 < 4` passes)
- `validity_offset==0` → guard `4 < 4` **fails**, so `ciphertextValidityProofContextStateAccount` is *not* emitted
- final authority check: guard `4 < 6-1=5` passes → `permissionedBurnAuthority` = idx[4]

The account at index 4 — which in the canonical layout implied by the flags would be the `ciphertextValidityProofContextStateAccount` — is instead labeled `permissionedBurnAuthority`, and the subsequent `parse_signers` call also shifts by one slot. This violates the stated invariant that "parsed output faithfully represents raw instruction" and produces a decoder misreporting of account roles that a client would see via `getTransaction` with `jsonParsed` encoding.

The attacker fully controls both the instruction data (the three proof offsets) and the account index list of their own transaction, so they can freely construct this mismatched combination and have it land in a block (whether or not the instruction succeeds at runtime, `transaction-status` parsing runs on committed instruction bytes regardless of execution outcome).

### Impact Explanation
This is a decoder misreporting bug in the RPC `jsonParsed` transaction display path (`transaction-status` crate), not a consensus, execution, or account-state bug. It falls under the "decoder panic and misreporting" bounty category: a client relying on `getTransaction`'s parsed JSON for a `permissionedConfidentialBurn` instruction can be shown an incorrect `permissionedBurnAuthority` field (actually a proof-context account) and a missing/incorrect `ciphertextValidityProofContextStateAccount` field, for a transaction the attacker themselves crafted.

### Likelihood Explanation
Fully attacker-controlled and requires only submitting one non-canonical `ConfidentialBurn` instruction (with mismatched account count vs. its own proof-offset flags) and later a single `getTransaction` RPC call — no validator/leader/peer control needed. Only precondition is that such an instruction is accepted into a block (it does not need to execute successfully on-chain for the parser to run against the raw instruction data), which is straightforward for an attacker submitting their own transaction.

### Recommendation
Validate that `account_indexes.len()` matches the exact number of accounts implied by the three proof-offset flags before deriving any optional field, and return a parse error (`ParseInstructionError::InstructionNotParsable`) rather than silently truncating/mislabeling when the count does not match the expected layout for the given flag combination.

### Proof of Concept
Extend the existing test module with a table-driven test that constructs `ConfidentialBurnInstructionData` combinations of `(eq_offset, val_offset, range_offset)` ∈ {0,≠0}³, computes the canonical expected account count for each, then feeds a `Message`/`CompiledInstruction` with one account short of that canonical count (still ≥4, satisfying `check_num_token_accounts`) through `parse_permissioned_burn_instruction`. Assert that either:
1. the function returns a `ParseInstructionError` (desired fixed behavior), or
2. currently, `parsed.info["permissionedBurnAuthority"]` equals the account key that should have been labeled as a proof-context account (e.g., `ciphertextValidityProofContextStateAccount`), demonstrating the mislabeling described above — reusing the pattern of `test_parse_permissioned_confidential_burn_instruction` at [5](#0-4)  but with deliberately shortened `account_indexes`/`instruction.accounts` rather than the well-formed builder output.
