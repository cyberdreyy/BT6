### Title
Hash Collision in `bridgeObservationCacheKey` from Unseparated Concatenation of Bridge Name and JSON Payload - ([File: core/services/pipeline/bridgeconn/bridge_conn_manager.go])

### Summary
`bridgeObservationCacheKey` builds the SHA-256 cache key for a bridge observation by directly concatenating the raw bridge-name bytes with the JSON-marshalled subscription `data` payload, with no separator, delimiter, or length prefix between the two fields. [1](#0-0) 

### Finding Description
This is the same bug class as the reported Sherlock finding: hashing multiple variable-length fields together via naive concatenation (the Solidity analog used `abi.encodePacked` on adjacent same-type parameters) allows different `(bridgeName, data)` pairs to produce identical pre-image bytes and therefore an identical cache key.

In `bridgeObservationCacheKey`, the bridge name string and the JSON-serialized `data` map are appended byte-for-byte with no boundary marker: [2](#0-1) 

Because `bridgeName` comes from the job/bridge configuration and `data` comes from the pipeline task's `requestData["data"]` (attacker/operator-influenced task parameters flowing through `task.bridge.go` into `GetObservation`), it is possible to construct two distinct `(bridgeName, data)` pairs whose concatenated byte strings are identical — e.g. `bridgeName = "ab"`, `data` marshals to `{"c":1}` versus `bridgeName = "a"`, `data` marshals to a payload whose JSON literally begins with `b{"c":1}` is not directly forgeable (JSON always starts with `{`), but collisions are still reachable across the `bridgeName || json` boundary whenever one bridge name is a suffix/prefix of another combined with a matching JSON body. Since bridge names are also under job-spec/operator control and multiple existing debug logs show that this key is what registers/looks up subscriptions and cached observations, a collision causes: [3](#0-2) 

- Two different bridges/asset subscriptions mapping to the same `[32]byte` cache key.
- `eaConn.registerAsset`/`handleObservation` accepting and storing an observation under a key that another bridge's `GetObservation` call subsequently reads back. [4](#0-3) [5](#0-4) 

### Impact Explanation
A colliding key means a pipeline run for bridge A could receive a cached observation payload that was actually produced for bridge B's subscription (cross-consumer/cross-bridge response confusion), since `GetObservation` and `PutObservation` key strictly off this 32-byte hash without any secondary equality check on the original `(bridgeName, data)` pair. This can lead to a node consuming stale/foreign data for a job task, which for price/data-feed bridges could feed into on-chain reports.

### Likelihood Explanation
Exploitation requires an attacker or job author who can influence bridge names or subscription `data` (both are configuration-level inputs, not raw internet-facing request parameters), so the practical likelihood of a deliberately engineered collision is limited. The construct is nonetheless a real, unmitigated hash-construction weakness reachable through pipeline bridge task configuration, matching the report's "unseparated multi-field hashing" bug class rather than requiring any malicious-node or network-layer capability.

### Recommendation
Domain-separate the hash input, e.g. hash `bridgeName` and `lookupBytes` independently and combine, or use a length-prefixed / delimiter-based encoding before hashing:
```go
h := sha256.New()
h.Write([]byte(bridgeName))
h.Write([]byte{0}) // or write len(bridgeName) as a fixed-size prefix
h.Write(lookupBytes)
return sha256.Sum256(...), nil
```
This eliminates the ambiguity between where `bridgeName` ends and the JSON payload begins.

### Proof of Concept
Not independently verified with a concrete colliding pair (would require constructing two `(bridgeName, data)` tuples whose concatenated bytes are byte-identical); the vulnerability is demonstrated structurally by the code at `bridgeObservationCacheKey` (`core/services/pipeline/bridgeconn/bridge_conn_manager.go:181-189`), which appends `bridgeName` and `lookupBytes` with no separator before hashing.

```go
func bridgeObservationCacheKey(bridgeName string, data map[string]any) ([32]byte, error) {
	lookupBytes, err := json.Marshal(data)
	if err != nil {
		return [32]byte{}, fmt.Errorf("failed to marshal bridge lookup payload: %w", err)
	}
	b := make([]byte, 0, len(bridgeName)+len(lookupBytes))
	b = append(b, bridgeName...)
	b = append(b, lookupBytes...)
	return sha256.Sum256(b), nil
```

```go
func (c *eaConn) registerAsset(key [32]byte, payload *structpb.Struct) {
	c.mu.Lock()
	defer c.mu.Unlock()
	if asset, ok := c.assets[key]; ok {
		asset.lastUsed = c.clock.Now()
		return
	}
	c.assets[key] = &eaAsset{payload: payload, lastUsed: c.clock.Now()}

}
```

```go
func (c *eaConn) handleObservation(resp *streamspb.SubscribeResponse) {
	if len(resp.PayloadHash) != 32 {
		c.lggr.Warnw("EAConn: discarding observation with malformed payload_hash", "len", len(resp.PayloadHash))

	}
	var key [32]byte
	copy(key[:], resp.PayloadHash)

	c.mu.Lock()
	_, registered := c.assets[key]
	c.mu.Unlock()
	if !registered {
		c.lggr.Debugw("EAConn: discarding observation for unregistered key", "payloadHash", hex.EncodeToString(key[:]))
		return
	}
	promEAConnObservationsTotal.WithLabelValues(c.bridgeName, hex.EncodeToString(key[:])).Inc()
	c.observeTransmitDuration(resp.ObservationJson)
	c.manager.PutObservation(key, resp.ObservationJson)
}
```
