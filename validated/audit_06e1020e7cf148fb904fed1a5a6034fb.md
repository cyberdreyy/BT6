### Title
Gateway HTTP-action response cache key omits WorkflowID, causing cross-workflow cached response confusion - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
The `responseCache` used by the gateway's HTTP Action handler caches `OutboundHTTPResponse` values keyed by `OutboundHTTPRequest.Hash()`. Despite the component's documentation and comments stating cache entries are "workflow-scoped" / keyed by "workflow ID and request hash" to prevent "cross-workflow data leakage," the actual `Hash()` implementation does not incorporate `WorkflowID` at all, only `WorkflowOwner`.

### Finding Description
`newResponseCache` stores cached responses in `map[string]*cachedResponse` keyed by `req.Hash()` [1](#0-0) . The `Fetch` and `Set` methods both use `req.Hash()` as the sole lookup/store key [2](#0-1) [3](#0-2) .

The package's own test suite proves `Hash()` ignores `WorkflowID`: two requests differing only in `WorkflowID` produce the *same* hash [4](#0-3) , while requests differing in `WorkflowOwner` produce different hashes [5](#0-4) . This directly contradicts the module's README, which explicitly documents "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [6](#0-5) .

This is the same class of bug as the Ajna report: a component's committed/reported state (here, the cache key/lookup used to serve data back to a caller) does not match what the documentation/design promises should distinguish separate principals — leading the gateway to return a response entry to the wrong party. Concretely, `makeOutgoingRequest` in the HTTP handler calls `h.responseCache.Fetch`/`Set` keyed only by `req.Hash()` when handling outbound HTTP action requests from workflow DON nodes [7](#0-6) .

### Impact Explanation
Two distinct workflows (even with different `WorkflowID`s, and potentially different owners in future auth models that don't tie `WorkflowOwner` uniquely) that issue outbound HTTP action requests with the same method, URL, headers, and body will share a single cache entry. A response fetched/cached on behalf of one workflow's request (which may embed workflow-specific request data or trigger workflow-specific side effects downstream) can be transparently returned to a different workflow. Given this is an internet-facing gateway cache serving CRE workflows' HTTP Action capability, this constitutes cross-workflow response confusion, potentially leaking response data intended for one workflow's HTTP call into another's execution context.

### Likelihood Explanation
The condition is trivially reachable: any two workflows that make an outbound HTTP request with identical method/URL/headers/body (e.g., calling the same public API endpoint) and enable caching (`CacheSettings.Store`/`MaxAgeMs`) will collide in the cache, regardless of `WorkflowID`. No malicious actor is required — this occurs under normal, unprivileged workflow usage of the HTTP Action capability.

### Recommendation
Include `WorkflowID` (and confirm `WorkflowOwner`, if intended as an isolation dimension) in the `Hash()` computation used as the cache key, so that cache entries are truly workflow-scoped as documented. Add/restore a test asserting that different `WorkflowID` values produce different hashes, and audit `Set`/`Fetch` call sites to ensure the correct request context object is always passed.

### Proof of Concept
1. Workflow A issues an HTTP Action request: `{Method: "GET", URL: "https://api.example.com/data", WorkflowID: "wf-A", CacheSettings: {Store: true}}`. The gateway forwards it, gets a 200 response, and calls `responseCache.Set(reqA, respA)`, storing it under `reqA.Hash()`.
2. Workflow B (different `WorkflowID: "wf-B"`, otherwise identical method/URL/headers/body) issues the same HTTP Action request with `CacheSettings.MaxAgeMs > 0`.
3. `makeOutgoingRequest` calls `responseCache.Fetch(ctx, reqB, callback, ...)` [8](#0-7) ; since `reqB.Hash() == reqA.Hash()` (per `TestRequestHash`'s "different workflowID results in same Hash" case), the cache returns `respA` — Workflow A's cached response — to Workflow B without ever contacting the external endpoint, and without either workflow's knowledge of the collision.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
