### Title
Attacker-controlled growth of `SecondaryIndex` (SPL-token-owner / program-id index) causes unbounded `RwLockSecondaryIndexEntry` sets that RPC scans and internal accounts-db scans must enumerate in full - ([File: accounts-db/src/accounts_index/secondary.rs])

### Summary
This is analogous to the `dMute.sol` bug: an attacker can cause arbitrary growth of a data structure keyed by a *victim's* pubkey (owner/program id) that they do not control, by simply creating many token accounts (or program-owned accounts) that reference that key. Later, any legitimate operation that must iterate "all accounts for this key" - the `SecondaryIndex::get`/`get_index_key_pubkeys` path used by `index_scan_accounts` and the RPC `getProgramAccounts`/`getTokenAccountsByOwner` handlers - is forced to enumerate and load every entry the attacker inserted, with no cap on the number of entries per key.

### Finding Description
`AccountsIndex` maintains three `SecondaryIndex<RwLockSecondaryIndexEntry>` maps (`program_id_index`, `spl_token_mint_index`, `spl_token_owner_index`) that any account creator can insert into simply by creating accounts owned by the SPL Token program with a given `owner`/`mint` field, or by deploying/creating accounts owned by a given `program_id`. [1](#0-0) 
Insertion into a key's bucket is unconditional and unbounded - `insert_if_not_exists` simply grows a `HashSet<Pubkey>` with no maximum size check: [2](#0-1) 
`update_spl_token_secondary_indexes` inserts into `spl_token_owner_index`/`spl_token_mint_index` for every SPL token account observed whose owner/mint matches the indexed key, with no per-key limit: [3](#0-2) 

When any consumer later needs "all pubkeys for key K" (the "victim's array"), `SecondaryIndex::get` clones the *entire* `HashSet` into a `Vec<Pubkey>`: [4](#0-3) 

This is used by `AccountsIndex::get_index_key_pubkeys`, which backs `index_scan_accounts` in `accounts_db.rs`, iterating and `do_load`-ing every returned pubkey before any filter or byte-limit is applied: [5](#0-4) [6](#0-5) 

The RPC surface directly exposes this to unprivileged callers via `getTokenAccountsByOwner` / `getProgramAccounts`, which route into `get_filtered_spl_token_accounts_by_owner` / `get_filtered_program_accounts`, which call the index-backed scan whenever the corresponding secondary index is enabled: [7](#0-6) [8](#0-7) 

Just as in the `dMute` report, none of `insert`, `get`, or the scan-driving code impose an upper bound on the number of "lock items" (here, pubkeys) that an unrelated third party can push under a target owner/program key. The `byte_limit_for_scan` mechanism referenced in `Bank::get_filtered_indexed_accounts`/`accounts.rs` only trims the *result set* being accumulated during the scan - it does not bound the initial `HashSet`→`Vec<Pubkey>` clone performed by `SecondaryIndex::get`, nor the cost of iterating over every entry before the limit check can apply per-item.

### Impact Explanation
An attacker who creates a very large number of SPL token accounts owned by a single `owner` pubkey (or by deploying data accounts under a shared `program_id`) permanently inflates that key's bucket in the in-memory `DashMap`. Any node operator running with `--account-index spl-token-owner` (or `program-id`) then pays an unbounded, attacker-dictated cost every time:
- `getTokenAccountsByOwner`/`getProgramAccounts` RPC calls for that key are served (RPC thread stalls/increased memory from cloning/loading a huge `Vec<Pubkey>` and subsequently `do_load`-ing each account),
- internal `index_scan_accounts` consumers (e.g., snapshot/verification or admin tooling) touch that key.

This does not permit fund theft, but it degrades or effectively denies RPC service for the targeted key, mirroring the "High" `RedeemTo`-style DoS impact described in the report (the operation becomes unusably slow/expensive), without the attacker gaining anything beyond negligible rent/fee costs.

### Likelihood Explanation
Likelihood is bounded by two factors: (1) the secondary index is opt-in (`--account-index`), so it only affects RPC nodes that enabled it, and (2) creating enough accounts requires paying rent for each, similar to the negligible-token-cost caveat in the original report. However, for any RPC operator who has enabled the SPL-token-owner or program-id index (a common configuration for indexing services), any unprivileged user can trigger this by creating token accounts, making the likelihood moderate-to-high for that deployment class.

### Recommendation
- Cap the number of inner keys tracked per outer key in `SecondaryIndex` (e.g., reject/ignore inserts beyond a configurable maximum per key, with metrics/alerts), rather than leaving `insert_if_not_exists` unbounded.
- Apply the existing `byte_limit_for_scan`/result-size limiting *before* fully materializing `SecondaryIndex::get`'s `Vec<Pubkey>`, e.g., stream/iterate the underlying `HashSet` and abort early once the limit is hit rather than cloning all entries up front.
- Consider rate-limiting or requiring pagination for `getTokenAccountsByOwner`/`getProgramAccounts` scans keyed on secondary indexes, independent of the per-key size.

### Proof of Concept
1. Start a node/RPC service with `--account-index spl-token-owner` enabled.
2. As an attacker, generate a large number (e.g., tens of thousands) of SPL Token accounts whose `owner` field is set to a chosen victim pubkey `V` (creating and initializing token accounts is permissionless and does not require `V`'s signature to set it as owner in account data - as validated by `update_spl_token_secondary_indexes`, which requires no authorization check other than that the account is owned by the token program).
3. Each such account insertion grows `spl_token_owner_index`'s bucket for `V` (`accounts-db/src/accounts_index/secondary.rs:83-94`), with no cap.
4. Any client subsequently calling `getTokenAccountsByOwner(V, ...)` triggers `get_filtered_spl_token_accounts_by_owner` → `get_filtered_indexed_accounts` → `index_scan_accounts`, which calls `SecondaryIndex::get` to clone the full, attacker-inflated `Vec<Pubkey>` and then `do_load`s every entry (`accounts_db.rs:3398-3409`), causing excessive latency/memory usage on the serving node for any query involving `V`.

impl SecondaryIndexEntry for RwLockSecondaryIndexEntry {
    fn insert_if_not_exists(&self, key: &Pubkey, inner_keys_count: &AtomicU64) {
        if self.account_keys.read().unwrap().contains(key) {
            // the key already exists, so nothing to do here
            return;

    pub(crate) fn index_scan_accounts<F>(
        &self,
        ancestors: &Ancestors,
        bank_id: BankId,
        index_key: IndexKey,
        mut scan_func: F,
        config: &ScanConfig,
    ) -> ScanResult<bool>
    where
        F: FnMut(Option<(&Pubkey, AccountSharedData, Slot)>),
    {
        let key = match &index_key {
            IndexKey::ProgramId(key) => key,
            IndexKey::SplTokenMint(key) => key,
            IndexKey::SplTokenOwner(key) => key,
        };
        if !self.account_indexes.include_key(key) {
            // the requested key was not indexed in the secondary index, so do a normal scan
            let used_index = false;
            self.scan_accounts(ancestors, bank_id, scan_func, config)?;
            return Ok(used_index);
        }

        // Register this scan so that slots needed by the scan are not cleaned out from under us.
        let scan_guard = ScanGuard::try_new(&self.scan_tracker, bank_id, || self.max_root())
            .ok_or(ScanError::SlotRemoved {
                slot: ancestors.max_slot(),
                bank_id,
            })?;

        // If the scan's ancestors are all rooted, drop them and scan roots only
        // Scan Guard max root must be used as the scan guard guarantees that
        // the account state as of max root is persisted in the database
        let max_root_ancestors = Ancestors::from(vec![scan_guard.max_root()]);
        let ancestors = if scan_guard.should_use_ancestors(ancestors) {
            ancestors
        } else {
            &max_root_ancestors
        };

        for pubkey in self.accounts_index.get_index_key_pubkeys(&index_key) {
            if config.is_aborted() {
                break;
            }
            if let Some((account, slot)) = self.do_load(
                ancestors,
                &pubkey,
                LoadHint::Unspecified,
                PopulateReadCache::False,
            ) {
                scan_func(Some((&pubkey, account, slot)));
            }
        }

    /// Use a set of filters to get an iterator of keyed program accounts from a bank
    #[allow(clippy::result_large_err)]
    async fn get_filtered_program_accounts(
        &self,
        bank: Arc<Bank>,
        program_id: Pubkey,
        mut filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> RpcCustomResult<Vec<(Pubkey, AccountSharedData)>> {
        optimize_filters(&mut filters);
        if self
            .config
            .account_indexes
            .contains(&AccountIndex::ProgramId)
        {
            if !self.config.account_indexes.include_key(&program_id) {
                return Err(RpcCustomError::KeyExcludedFromSecondaryIndex {
                    index_key: program_id.to_string(),
                });
            }
            self.get_filtered_indexed_accounts(
                &bank,
                &IndexKey::ProgramId(program_id),
                &program_id,
                filters,
                sort_results,
            )
            .await
            .map_err(|e| RpcCustomError::ScanError {
                message: e.to_string(),
            })
        } else {
            // this path does not need to provide a mb limit because we only want to support secondary indexes
            let mut accounts = self
                .runtime
                .spawn_blocking(move || {
                    bank.get_filtered_program_accounts(
                        &program_id,
                        |account: &AccountSharedData| {
                            filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                        },
                    )
                    .map_err(|e| RpcCustomError::ScanError {
                        message: e.to_string(),
                    })
                })
                .await
                .expect("Failed to spawn blocking task")?;
            if sort_results {
                // Avoid copying pubkeys (using Ord::cmp(a, b) silences clippy::unnecessary_sort_by).
                accounts.sort_unstable_by(|(addr_a, _), (addr_b, _)| Ord::cmp(addr_a, addr_b));
            }
            Ok(accounts)
        }
    }

    /// Get an iterator of spl-token accounts by owner address
    async fn get_filtered_spl_token_accounts_by_owner(
        &self,
        bank: Arc<Bank>,
        program_id: Pubkey,
        owner_key: Pubkey,
        mut filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> RpcCustomResult<Vec<(Pubkey, AccountSharedData)>> {
        // The by-owner accounts index checks for Token Account state and Owner address on
        // inclusion. However, due to the current AccountsDb implementation, an account may remain
        // in storage as a zero-lamport AccountSharedData::Default() after being wiped and reinitialized in
        // later updates. We include the redundant filters here to avoid returning these accounts.
        //
        // Filter on Token Account state
        filters.push(RpcFilterType::TokenAccountState);
        // Filter on Owner address
        filters.push(RpcFilterType::Memcmp(Memcmp::new_raw_bytes(
            SPL_TOKEN_ACCOUNT_OWNER_OFFSET,
            owner_key.to_bytes().into(),
        )));

        if self
            .config
            .account_indexes
            .contains(&AccountIndex::SplTokenOwner)
        {
            if !self.config.account_indexes.include_key(&owner_key) {
                return Err(RpcCustomError::KeyExcludedFromSecondaryIndex {
                    index_key: owner_key.to_string(),
                });
            }
            self.get_filtered_indexed_accounts(
                &bank,
                &IndexKey::SplTokenOwner(owner_key),
                &program_id,
                filters,
                sort_results,
            )
            .await
            .map_err(|e| RpcCustomError::ScanError {
                message: e.to_string(),
            })
        } else {
            self.get_filtered_program_accounts(bank, program_id, filters, sort_results)
                .await
        }
    }
