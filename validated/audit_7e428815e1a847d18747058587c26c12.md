## Finding

This external report describes a class of bug where a "seen"/dedup record is written optimistically before final verification completes, and is not rolled back when that verification later fails on one specific path — letting an attacker permanently "poison" the record and block the legitimate counterpart. The Chainlink codebase has a directly analogous pattern in the Vault gateway authorization pipeline.

### Title
Vault request replay guard records a digest before owner-binding verification, allowing an authenticated but unauthorized sender to poison another user's legitimate request digest - (File: core/capabilities/vault/authorizer.go)

### Summary
`authorizer.AuthorizeRequest` records a request's replay-protection digest in `RequestReplayGuard` immediately after authentication succeeds, but *before* it checks that the request's payload actually belongs to the authenticated caller (`validateSecretOwnersMatchAuthorized`). If that later ownership check fails, the digest entry is never removed, so it stays "seen" for the lifetime of the guard's expiry window.

### Finding Description
The authorization sequence in `authorizer.AuthorizeRequest` is: [1](#0-0) 

1. `authorizeRequest` runs JWT or allowlist authentication and returns an `AuthResult` containing a content-derived `digest` and `expiresAt`.
2. `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())` is called and **records the digest immediately** if it hasn't been seen before.
3. Only afterward does `validateSecretOwnersMatchAuthorized` verify that the payload's claimed owner matches the authenticated caller's authorized workflow owner.

`RequestReplayGuard.CheckAndRecord` records the digest unconditionally on first sight and only clears it on TTL expiry — there is no removal path for a request that is recorded but later rejected: [2](#0-1) 

The digest is computed over the full request body (`id`, `method`, `params`) via `req.Digest()`, independent of who is authenticated: [3](#0-2) 

Because JWT issuance binds a `request_digest` claim to caller-chosen request content (any authenticated org/tenant can mint a JWT authorizing any `id`/`params` they submit), an attacker who is a legitimately authenticated Vault client for *their own* tenant can:
1. Craft a JSON-RPC request body whose `params` (e.g. `owner` in `ListSecretIdentifiersRequest`, or secret IDs' `owner` in create/update/delete) contains a **victim's** workflow-owner value and a request `id` the attacker expects the victim to use (e.g. a well-known/deterministic/retried request ID).
2. Mint (or obtain) a JWT for themselves whose `request_digest` claim matches this crafted body — this succeeds because JWT validation only checks the attacker's own signature/claims/digest self-consistency, not who the payload claims to belong to.
3. Submit the request. `AuthorizeRequest` authenticates it, calls `CheckAndRecord`, which **succeeds and stores the digest** — then `validateSecretOwnersMatchAuthorized` rejects it because the payload owner doesn't match the attacker's own authorized owner: [4](#0-3) 

The digest is now poisoned in the guard. If the real victim later submits the exact same `id`/`params` (a very plausible scenario for idempotent retries — the codebase's own test helpers document that Vault clients retry requests with the same body/ID after timeouts, and this "just hits the vault replay guard"): [5](#0-4) 

...the victim's genuine, first-ever attempt is rejected with `ErrRequestAlreadySeen` ("request was already authorized previously"), even though it was never actually processed, until the poisoned entry's `expiresAt` (derived from the attacker's own JWT expiry + leeway) elapses.

This mirrors the reported bug class precisely: an optimistic "seen" record is written before terminal verification, and one rejection path (`validateSecretOwnersMatchAuthorized`, analogous to `Request::KnownBlock`) fails to drain/undo that record, unlike record creation being tied only to success in a fully-synchronous design.

### Impact Explanation
An authenticated-but-unrelated Vault user can deny another org/workflow owner's legitimate Vault request (secrets list/create/update/delete) for the duration of the poisoned entry's TTL, without needing any privileges over the victim's account or secrets. This is a request-blocking/DoS primitive scoped to the Vault gateway's replay protection, reachable purely from the unprivileged client-facing JSON-RPC path (JWT-based auth).

### Likelihood Explanation
Exploitation requires the attacker to predict or observe the exact `id` and `params` bytes the victim will use — most practical when clients use deterministic or retried request IDs (which the codebase's own tests confirm is a supported/expected pattern), making this a realistic though not universal attack surface.

### Recommendation
Move `replayGuard.CheckAndRecord` to occur only after all authorization checks (including `validateSecretOwnersMatchAuthorized`) have passed, or add a compensating removal of the digest from `RequestReplayGuard` when any later step in `AuthorizeRequest` fails after the digest has been recorded.

### Proof of Concept
1. Attacker (authenticated for org A) crafts `params = {"owner": "<victimOwnerAddr>", "namespace": "main"}` with `id = "req-1"` for `vault.secrets.list`.
2. Attacker computes `digest = req.Digest()` over this exact body and obtains a JWT for their own org with `request_digest` claim set to `digest`.
3. Attacker submits the request; `JWTBasedAuth.AuthorizeRequest` succeeds (attacker's own JWT is valid); `replayGuard.CheckAndRecord(digest, expiresAt)` succeeds and stores `digest`.
4. `validateSecretOwnersMatchAuthorized` rejects the request (`list secrets owner ... does not match authorized workflow owner ...`), but the digest remains recorded.
5. Victim later submits the identical `id`/`params` (e.g., via an idempotent retry) with a correctly minted JWT for their own owner; `replayGuard.CheckAndRecord` returns `ErrRequestAlreadySeen`, and the victim's legitimate request is rejected with "request was already authorized previously" until the attacker's original JWT-derived `expiresAt` passes.

func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
