### Title
Programmable-borrower `onStopEpoch` returning false permanently defaults the pool and freezes all lender funds - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant._stopEpoch` treats a `false` return from `IProgrammableBorrower.onStopEpoch` as an irrevocable borrower default. Because the programmable borrower sources epoch liquidity from an external ERC-4626 vault, any unprivileged user of that vault can withdraw liquidity so the recall fails, `onStopEpoch` returns `false`, and `_handleBorrowerDefault` permanently marks the pool `defaulted`, pauses it, and blocks all withdrawals until owner/manager manually runs `finalizeDefault` with a loss haircut.

### Finding Description
In `_stopEpoch` (contracts/IdleCDOEpochVariant.sol:395-404), when `isProgrammableBorrower` is set, the CDO asks the borrower hook to recall ERC-4626 liquidity before pulling funds:

```solidity
if (!IProgrammableBorrower(_borrower()).onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)) {
  _handleBorrowerDefault(_amountToPullFromBorrower + _pendingWithdraws);
  return;
}
```

The comment intends hook *reverts* to be retryable, but a `false` return is not: it unconditionally calls `_handleBorrowerDefault`, which (lines 577-599) sets `defaulted = true`, calls `onDefault()`, `_pause()`s the contract, stops the epoch, and disables `allowAAWithdrawRequest`/`allowBBWithdrawRequest`. Once `defaulted` is set:

- `_beforeUnpause` reverts on `defaulted` (line 636), so the pool can never be unpaused via `restoreOperations`/`unpause`.
- `startEpoch` reverts on `defaulted` (line 239), so no new epoch can ever start.
- `requestWithdraw` is blocked (`allow*WithdrawRequest = false`) and `_deposit` reverts via `whenNotPaused`.
- The only exit is the permissioned `finalizeDefault`, which applies a single aggregate recovery multiplier to all tranches — i.e., a haircut on every LP even when the borrower is solvent and the failure was a transient liquidity shortfall in its ERC-4626 vault.

An ERC-4626 vault's redeemable liquidity is reduced by *any* depositor redeeming or borrowing against it. Since the hook result is binary, a third-party vault user draining available liquidity at the moment `stopEpoch` is called converts a transient cash shortage into a permanent default state and a forced loss distribution.

### Impact Explanation
All lender principal and accrued interest in AA and BB tranches becomes permanently frozen: no deposits, no withdrawal requests, no claims reopening, no new epochs. Recovery requires the owner/manager to run `finalizeDefault`, which crystallizes a recovery multiplier (`defaultRecoveryPrice`) onto tranche prices — turning what could have been a momentary liquidity gap into a realized loss socialized across all LPs. Quantified loss: 100% of pool NAV is frozen until finalization, and any shortfall between `defaultRecoveryReserve` and owed NAV is permanently crystallized.

### Likelihood Explanation
Requires a pool configured with `isProgrammableBorrower` and a borrower whose ERC-4626 vault liquidity can be moved by third parties. The attacker needs no role in idle-tranches — only the ability to withdraw or borrow from the shared ERC-4626 vault, and to time it around the permissioned `stopEpoch` call. The trigger transaction itself (a vault redeem) is unprivileged; no malicious owner, manager, guardian, or borrower is needed. Mitigated only to the extent the programmable borrower's vault is isolated from other users.

### Recommendation
Make the false-return path retryable rather than terminal: e.g., revert the stopEpoch (or leave `isEpochRunning` true and retryable via a re-callable `getInstantWithdrawFunds`-style pull) when `onStopEpoch` returns false, and reserve `_handleBorrowerDefault` for an explicit, confirmed insolvency signal. Alternatively, have `onStopEpoch` revert on transient liquidity failure (matching the documented "reverts bubble" behavior) and only return false for genuine default.

### Proof of Concept
```solidity
// Foundry fork test sketch (contracts/test against ProgrammableBorrower wiring)
function testVaultUserLiquidityDrainForcesDefault() external {
    // 1. Lender deposits into AA tranche; manager starts an epoch.
    idleCDO.depositAA(10_000 * ONE_SCALE);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // 2. Epoch ends. Attacker (unprivileged ERC4626 vault user) redeems /
    //    borrows the vault's free liquidity just before manager's stopEpoch,
    //    so the borrower's liquidity recall cannot be satisfied.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(attacker);
    borrowerVault.redeem(borrowerVault.maxRedeem(attackerVaultShares), attacker, attacker);

    // 3. onStopEpoch returns false -> _handleBorrowerDefault.
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    assertTrue(cdoEpoch.defaulted());

    // 4. Lender funds are frozen: no unpause, no restart, no requests.
    vm.prank(owner);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.unpause();
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.startEpoch();
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.requestWithdraw(1, address(AAtranche));

    // 5. Only exit is finalizeDefault with a recovery haircut on all LPs.
}
```

Note: the PoC depends on `ProgrammableBorrower.onStopEpoch` returning `false` (rather than reverting) when ERC-4626 liquidity is insufficient — index size limits prevented confirming that exact return-false branch in `contracts/strategies/idle/ProgrammableBorrower.sol`; if it reverts instead, the failure is retryable and this analog does not hold.
