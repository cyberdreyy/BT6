## Title
Stale confirmations from removed multisig members still count toward the approval threshold, allowing execution below threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` counts entries in the `confirmations` set for a request without verifying that each confirming member is still a current member of the multisig at execution time. `delete_member` only purges confirmations/requests that a removed member itself *created*, not confirmations that member previously cast on requests created by other members. As a result, a request can execute once `confirmations.len() + 1 >= num_confirmations` even though one or more of the counted confirmations came from a member who has since been removed, letting a request execute with fewer than `num_confirmations` *live* approvals. This mirrors the reported `bypassSignatoryApproval` pattern of an approval-gating boolean/count that is not re-validated against the current authorization state before an early "valid, proceed to execute" decision.

### Finding Description
`confirm()` performs no re-validation of the stored confirmer identities against the live membership set: [1](#0-0) 

The only membership check happens for the *current* caller via `assert_valid_request` / `current_member()`: [2](#0-1) 

When a member is removed, `delete_member` only cleans up requests originally *created* by that member — it filters on `r.member == member` (the request's creator), not on membership within any request's `confirmations` set: [3](#0-2) 

So if member `M` had already confirmed a request `R` created by a *different* member, and `M` is later removed via a separate `DeleteMember` request, `R`'s stored `confirmations` set still contains `M`'s entry. That entry keeps counting toward `num_confirmations` in the next `confirm()` call, even though `M` is no longer an authorized signer.

**Equality that should hold:** `confirmations counted for R` == `approvals from currently-live members`. This invariant is broken because `confirmations` is never intersected with the live `members` set before comparing against `num_confirmations`.

The same flaw architecturally exists in `multisig/src/lib.rs` (v1): `DeleteKey` only purges requests whose `signer_pk == pk` (the deleted key's own requests), not that key's confirmations on other members' requests: [4](#0-3) 

### Impact Explanation
This crosses the exact authorization/threshold boundary called out as Critical impact: "a multisig request executed below threshold." A pending, not-yet-confirmed-enough request created before a member removal can later be pushed to execution by fewer live members than `num_confirmations` requires, because a stale confirmation from an ousted member is silently counted. Depending on the request's actions (`Transfer`, `AddKey`/`AddMember`, `FunctionCall`), this can move NEAR out of the multisig account, grant new access, or make privileged calls with an insufficient live quorum — a genuine custody/authorization boundary violation, not merely a griefing or DoS issue.

### Likelihood Explanation
Exploitation requires only ordinary multisig operation, no protocol bug elsewhere and no external prerequisites:
1. A pending request `R` (created by member `B`) receives confirmations from members `A` and `C` (below threshold).
2. Separately, the multisig legitimately removes member `A` (e.g., because `A`'s key was compromised or `A` left), which succeeds because `delete_member` never checks `R`'s confirmations.
3. Any remaining live member (e.g., `D`) confirms `R`, and `confirmations.len()+1 >= num_confirmations` is satisfied purely by count, including `A`'s stale entry — `R` executes despite only 2 of `num_confirmations`=3 approvals coming from currently-live members.
This is a realistic sequence (member rotation is an expected multisig operation) rather than a contrived edge case, making likelihood high once a member removal happens while requests are pending.

### Recommendation
Before counting confirmations toward the threshold in `confirm()` (and ideally on every `delete_member`/`DeleteKey`), filter/re-validate the `confirmations` set against the current `members` set (or current set of valid access keys in v1), removing/discounting entries from members no longer authorized. Alternatively, on member removal, iterate all pending requests' confirmation sets (not just requests created by that member) and strip the removed member's confirmation, decrementing effective counts accordingly.

### Proof of Concept
1. Deploy `MultiSigContract` (`multisig2`) with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `B` calls `add_request` to create request `R` (e.g., `Transfer` to attacker-controlled account).
3. `A` calls `confirm(R)` → confirmations = `{A}`.
4. `C` calls `confirm(R)` → confirmations = `{A, C}` (2 < 3, not yet executed).
5. Multisig separately creates and confirms (via `B`, `C`, `D`) a `DeleteMember { member: A }` request, which succeeds via `delete_member` (see `multisig2/src/lib.rs:356-374`) since it only checks `self.members.len() - 1 >= num_confirmations` and purges only requests created by `A` — `R`'s confirmations set (`{A, C}`) is untouched.
6. `D` calls `confirm(R)` → `confirmations.len() as u32 + 1 == 3 >= num_confirmations` → `execute_request(R)` runs the `Transfer`, even though only `C` and `D` (2 of the 3 currently-live members) actually approved `R`. [1](#0-0)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
