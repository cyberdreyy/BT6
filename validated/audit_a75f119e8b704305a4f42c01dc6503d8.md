### Title
Masking store (masking.db) and its encryption key material are created with world-readable/writable permissions (0666/0644) - (File: `commands/helpers/internal/store/store_unix.go`, `commands/helpers/internal/store/store.go`)

### Summary
`gitlab-runner`'s `proxy-exec` helper command uses an on-disk encrypted store (`masking.db`) to persist masked secret phrases used for output masking during job execution. On Unix, both the store file and its derived encryption key file are created with overly permissive modes (`0666` and `0644` respectively), and the store file's permissive mode is explicitly enforced regardless of the process umask.

### Finding Description
`store.Open` in `commands/helpers/internal/store/store.go` creates two files that together protect secret material:
1. A key file (`keyPath`) written via `os.WriteFile(keyPath, generateKey(), 0o644)` [1](#0-0) 
2. The `masking.db` store file itself, opened via the platform-specific `openFile()` function.

On Unix, `openFile` (`commands/helpers/internal/store/store_unix.go`) explicitly forces the mode to `0666` on file creation, overriding whatever the umask would normally produce: [2](#0-1) 

This is confirmed as intentional/tested behavior by `TestOpenFilePermissions`, which explicitly asserts the new file gets `0666` "regardless of umask": [3](#0-2) 

The store holds decryption-relevant material: the encrypted secret store (`masking.db`) is derived from XOR-ing two 32-byte keys — one stored inline in `masking.db` itself and one in the separate `keyPath` file [4](#0-3) . Because both files are world-readable (and the store file is even world-writable), any local user or process on the same host that shares the runner's build directory can read (or corrupt) both halves of the key material and decrypt the masked-phrase log ("secrets") that this store is meant to protect from disclosure.

This store is wired up from `commands/helpers/proxy_exec.go`, where `NewProxy` opens the store under the job's temp/project directory and feeds it to `addmask.New` for stdout/stderr masking during `proxy-exec` [5](#0-4) .

### Impact Explanation
If a local, non-privileged user (or a compromised sibling process running under a different UID) has filesystem access to the runner's build/project directory (e.g., shared shell-executor host, shared cache/build volumes, or a shared machine with multiple concurrently-scheduled jobs), the `0666`/`0644` permissions allow that user to read the encryption key material and the encrypted phrase list, and potentially decrypt secret phrases intended to be masked from build logs. The store file being world-writable (`0666`) additionally allows tampering/corruption of the masking database by any local user, which could disable or corrupt masking for that job's log output.

### Likelihood Explanation
This requires local filesystem access to the runner's working directory by another user on the same host — this is realistic on hosts where the shell executor is used with a shared, multi-tenant machine, or where multiple runner jobs/processes run as different local users on the same box. It does not require any privileged/trusted role compromise; it only requires the attacker to be another unprivileged local user able to read files in the job's temp directory, which is a plausible deployment scenario for self-managed shell-executor runners.

### Recommendation
Change `openFile` in `commands/helpers/internal/store/store_unix.go` to create the file (and set its mode when newly created) with `0600` instead of `0666`, and change the key-file write in `store.go` from `os.WriteFile(keyPath, generateKey(), 0o644)` to `0o600`, consistent with the restrictive permissions already used elsewhere in the codebase for sensitive material (e.g., `commands/internal/configfile/system_id_state.go` uses `0o600` for its config file, and `common/config.go`'s `defaultConfigSaver.Save` also uses `0o600`). Avoid explicitly re-`chmod`-ing to a permissive mode on file creation, since that actively defeats a restrictive process umask.

### Proof of Concept
1. On a Unix host, set `umask 0077`.
2. Invoke `gitlab-runner-helper proxy-exec --temp-dir <dir> -- <cmd>` (or otherwise trigger `store.Open(dir)`).
3. Inspect the resulting files: `stat -c '%a' <dir>/masking.db` returns `666`, and `stat -c '%a' <dir>/runner<hash>` (the key file) returns `644`, both ignoring the restrictive umask.
4. Any other local user can then `cat` both files to reconstruct the XOR key and decrypt the base64/AEAD-encrypted secret phrases stored in `masking.db`, or overwrite `masking.db` due to world write access. [3](#0-2)

```go
func deriveEncryptionKey(f *os.File, keyPath string) ([]byte, error) {
	var key1 [32]byte
	if _, err := io.ReadFull(f, key1[:]); err != nil {
		return nil, err
	}

	key2, err := os.ReadFile(keyPath)
	if err != nil {
		return nil, err
	}

	if len(key2) < len(key1) {
		return nil, fmt.Errorf("key1 and key2 not the same size")
	}

	for i := 0; i < len(key1); i++ {
		key1[i] ^= key2[i]
	}

	return key1[:], nil
}
```

```go
func openFile(pathname string) (*os.File, error) {
	// Check if file exists before opening
	_, err := os.Stat(pathname)
	isNewFile := os.IsNotExist(err)

	f, err := os.OpenFile(pathname, os.O_APPEND|os.O_RDWR|os.O_CREATE, 0666)
	if err != nil {
		return nil, err
	}

	// Only chmod if we just created the file
	if isNewFile {
		if err := os.Chmod(pathname, 0666); err != nil {
			f.Close()
			return nil, err
		}
	}

	return f, nil
}
```

```go
func TestOpenFilePermissions(t *testing.T) {
	t.Run("new file gets 0666 regardless of umask", func(t *testing.T) {
		oldUmask := syscall.Umask(0077)
		defer syscall.Umask(oldUmask)

		dir := t.TempDir()

		db, err := Open(dir)
		require.NoError(t, err)
		defer db.Close()

		info, err := os.Stat(filepath.Join(dir, "masking.db"))
		require.NoError(t, err)
		require.Equal(t, os.FileMode(0666), info.Mode().Perm())
	})
```
