### Title
Stale in-memory `BlockInfo` snapshot clobbers persisted pre-commit/signature state in `process_pending_responses_for_block` - (File: stacks-signer/src/v0/signer.rs)

### Summary
`handle_block_proposal` drains early ("pending") pre-commits, rejections, and signatures that arrived before the proposal itself, then replays them via `process_pending_responses_for_block`. That function threads a single `&mut BlockInfo` snapshot through all three replay loops, but pre-commit replay (`handle_block_pre_commit`) does **not** use that shared snapshot — it re-fetches its own independent copy of `BlockInfo` from `signer_db`, mutates it, and persists it. When rejections/signatures are subsequently replayed using the original (now stale) snapshot, `store_and_process_block_rejection`/`store_and_process_block_signature` call `self.signer_db.insert_block(block_info)`, overwriting the freshly-persisted pre-commit state with the older in-memory copy. This is the classic "memory copy vs. storage reference" defect from the referenced report, translated to Rust: two independently-fetched copies of the same logical record are mutated and the write-back of the stale one wins, silently discarding the other's persisted state.

### Finding Description
In `handle_block_proposal` (stacks-signer/src/v0/signer.rs:1574-1727), for a genuinely new block the signer drains pending responses via `drain_pending_block_responses` [1](#0-0) , builds a fresh `BlockInfo` from the proposal, stores it, and calls `process_pending_responses_for_block(..., &mut block_info, pending_responses)` [2](#0-1) .

Inside `process_pending_responses_for_block` (stacks-signer/src/v0/signer.rs:1730-1780), pre-commits are replayed first through `handle_block_pre_commit(stacks_client, sortition_state, &stacker_address, &signer_signature_hash)` — note this call takes only the hash, not `block_info` [3](#0-2) . Then rejections and signatures are replayed by passing the *same, unchanged* `&mut block_info` reference into `store_and_process_block_rejection` and `store_and_process_block_signature` [4](#0-3) .

Both `store_and_process_block_rejection` and `store_and_process_block_signature` end by writing this reference back to the DB with `self.signer_db.insert_block(block_info)` [5](#0-4) [6](#0-5) .

Because `handle_block_pre_commit`'s own internal fetch-mutate-save cycle (a separate, freshly-loaded `BlockInfo`, e.g. via `block_lookup_by_reward_cycle`) is not reflected back into the local `block_info` variable owned by `process_pending_responses_for_block`, any state the pre-commit path just persisted (state → `PreCommitted`, `approved_time` stamped, per `docs/signer-flows.md`'s description of `mark_pre_committed`) [7](#0-6)  is overwritten the moment a pending rejection or pending signature for the same block is replayed afterward, since that replay writes back the original pre-proposal snapshot (state still `Unprocessed`, no `approved_time`).

`insert_block` performs a full overwrite of the persisted `BlockInfo` row; it is not shown to compare against the current DB state before writing, so there is no guard preventing an older in-memory snapshot from clobbering newer persisted fields.

### Impact Explanation
This lets a genuinely benign sequence of gossip (a peer's pre-commit, rejection, and signature for the same not-yet-seen block, parked as pending responses and then replayed together when the proposal finally arrives) silently revert this signer's own persisted `BlockInfo.state`/`approved_time`/`signed_self`/`signed_group` fields back to their pre-pre-commit values, even though the signer already broadcast a pre-commit (or later a signature) reflecting the advanced state. Because later re-evaluation logic (`should_reevaluate_block`, `check_block_against_signer_db_state`, `has_reached_consensus`, the `block_info.valid.is_some()` "already answered" gate) all read from this now-regressed persisted record, the signer can be tricked into re-evaluating a block it already committed to, potentially producing a conflicting signature/response at the same height, or losing the "already responded" idempotency guard — the same category of consequence as "losing the equivocation guard" called out as High impact in the rules.

### Likelihood Explanation
This does not require a majority of signers or any signing key. It requires ordinary network conditions: a signer receiving pre-commit/rejection/signature messages for a block from peers before receiving the block proposal itself from the miner — an ordinary and expected race given `docs/signer-flows.md`'s own description that "Early votes: acceptances, rejections, and pre-commits that arrived before the proposal itself are parked in pending tables and replayed once the proposal is known" [8](#0-7) . It is plausibly triggerable even by a single slow/delayed miner combined with normal StackerDB message propagation timing, without any attacker action.

### Recommendation
`process_pending_responses_for_block` should re-fetch (or otherwise keep in sync) the `BlockInfo` from `signer_db` between each replayed pending response — especially after `handle_block_pre_commit` — instead of threading a single pre-proposal snapshot through the rejection/signature replay calls, so that `insert_block` writes never overwrite state advanced by an intervening pre-commit (or, alternatively, have `insert_block` merge/guard against regressing already-persisted `state`/timestamps rather than performing a blind overwrite).

### Proof of Concept
1. A miner proposes block `B`. Before this signer's `handle_block_proposal` observes the proposal, it receives (and parks as pending, per `drain_pending_block_responses`) a pre-commit from signer `A`, a rejection from signer `C`, and a signature from signer `D`, all for `B`.
2. `handle_block_proposal` builds and stores a fresh `BlockInfo` for `B` (state `Unprocessed`), then calls `process_pending_responses_for_block`.
3. The pre-commit from `A` is replayed via `handle_block_pre_commit`, which independently fetches, mutates (`mark_pre_committed`, stamping `approved_time`), and persists its own `BlockInfo` copy for `B`.
4. The rejection from `C` is then replayed via `store_and_process_block_rejection(&mut block_info, ...)`, using the original stale `block_info` snapshot (still `Unprocessed`, no `approved_time`); this mutates that stale copy and calls `self.signer_db.insert_block(block_info)`, overwriting the DB row and discarding the `PreCommitted` state/`approved_time` just written in step 3.
5. This signer's local, persisted record for `B` no longer reflects the pre-commit it (or peer `A`) had already advertised, opening the door to inconsistent re-evaluation on a subsequent proposal retry for the same block.
