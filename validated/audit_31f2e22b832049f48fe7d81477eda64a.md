### Title
v1 signer's tenure-change duplicate-block check misses locally-accepted/pre-committed blocks, allowing a signer to sign two conflicting tenure-start blocks - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
The v1 chainstate path's `validate_tenure_change_payload` uses `get_last_globally_accepted_block` to decide whether a tenure already has an accepted block, whereas the v2 path was fixed to use `get_last_signed_block` (which also catches `LocallyAccepted` blocks). This asymmetry is the same bug class as the Vyper report: a safety check was tightened in one place (v2) after a real regression, but the analogous check in a parallel code path (v1) was left using the narrower, already-proven-unsafe predicate.

### Finding Description
`validate_tenure_change_payload` in v1 rejects a tenure-change proposal with `RejectReason::DuplicateBlockFound` only if `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` returns a block [1](#0-0) . This query only matches blocks in `BlockState::GloballyAccepted`, per its `get_last_globally_accepted_block` documentation and semantics, and it explicitly does **not** match `LocallyAccepted` blocks — i.e., blocks this very signer has already put a personal signature over (`signed_self`) but that have not yet reached the 70% group threshold.

The v2 implementation was already patched to close exactly this hole, replacing the check with `get_last_signed_block`, which matches both `GloballyAccepted` and `LocallyAccepted` states [2](#0-1) . The project's own regression test documents this exact defect and its intended fix: "previously, the check used `get_last_globally_accepted_block`, which would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change" [3](#0-2) . The docs explicitly call out the asymmetry: "v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1 counts only globally accepted ones (`get_last_globally_accepted_block`)" [4](#0-3) .

This check runs only at proposal-arrival time and is never re-run at validate-ok or at signing time [5](#0-4) . The documented backstop for this gap is the pre-commit-time own-tenure conflict guard, driven by `get_signed_conflicts`, which does use the broader "signed" predicate (`signed_self OR signed_group`, i.e. it does include `LocallyAccepted`) [6](#0-5) . So a v1 signer following this specific instance's protocol has two chances to catch this: proposal-time (broken for v1) and pre-commit-threshold-time (correct, `get_signed_conflicts` catches `LocallyAccepted`).

Given the pre-commit-time backstop appears intact for v1 signers running this instance's `get_signed_conflicts`/`reorg_permit_stands`/`conflict_still_blocks` logic (section 5 of the docs), the proposal-time gap in v1 by itself does not obviously let a signer *sign* two conflicting blocks — it would instead let a duplicate tenure-change proposal proceed further than it should (through node validation, wasting a validation slot, and reaching pre-commit) before eventually being caught by the height-check backstop. I was not able to fully verify, within the remaining budget, whether `get_signed_conflicts`'s "OWN tenure" branch and `conflict_still_blocks` freshness/staleness logic (section 5) covers every timing window that `DuplicateBlockFound` was meant to cover for v1 tenure-change blocks specifically (e.g., whether a stale `LocallyAccepted` block's conflict could go stale and let a duplicate BlockFound-cause tenure-change reach the `SIGN` branch). That gap in verification is a limitation of this analysis, not a claim of safety.

### Impact Explanation
If the pre-commit-time backstop (`get_signed_conflicts` OWN-tenure branch) has any timing gap not covered by this analysis (e.g. once the original `LocallyAccepted` block's conflict is judged "stale" per `conflict_still_blocks`, or if the current miner is on v1 chainstate specifically), a v1 signer could sign a second, conflicting tenure-start block in a tenure where it already holds a personal signature over a different tenure-start block. That would be a Critical-class outcome per the stated impact classes (a signer signing a conflicting block, breaking the "signed vs validated" / one-tenure-start-block-per-tenure equality). Absent full confirmation of a live signing path, the concretely provable defect is a proposal-time equality break: v1's duplicate-detection predicate is weaker than the already-recognized-correct v2 predicate for the same check, unnecessarily letting an already-signed tenure be re-challenged past the point the protocol intends to reject it outright.

### Likelihood Explanation
No majority collusion or forged signer key is required — a single miner (the block proposer) can trigger this by re-proposing a competing tenure-change ("BlockFound") block for a tenure where a signer has already locally accepted (signed) a prior tenure-start block but that block has not yet reached the 70% global-acceptance threshold. This is a realistic race (competing miners, tenure-change retries, or a miner switch) rather than a contrived edge case, and the project's own tests confirm the identical scenario was previously exploitable and had to be patched for v2.

### Recommendation
Align `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` with the v2 fix: replace the `get_last_globally_accepted_block` lookup with `get_last_signed_block` (or equivalent), so that a tenure with a `LocallyAccepted` block is also protected against a duplicate tenure-change proposal. Add a v1-specific regression test mirroring `check_tenure_change_rejects_when_locally_accepted_block_exists` in `stacks-signer/src/chainstate/tests/v2.rs` to prevent this asymmetry from recurring, and audit `get_signed_conflicts`/`conflict_still_blocks`/`reorg_permit_stands` to confirm they fully cover the v1 proposal-time gap in every freshness/staleness window before relying on them as the sole backstop.

### Proof of Concept
1. Signer runs v1 chainstate checks. Miner proposes tenure-start block `A` for tenure `T` (cause `BlockFound`). Signer validates it and locally accepts/signs it (`mark_locally_accepted`), storing `BlockState::LocallyAccepted` — `signed_self` is set, but the group threshold (70%) has not yet been reached, so it is not `GloballyAccepted`.
2. The same or a colluding miner proposes a second, different tenure-start block `B` for the same tenure `T` (also cause `BlockFound`, e.g. with different transactions/coinbase).
3. `check_proposal` → `validate_tenure_change_payload` (v1) calls `signer_db.get_last_globally_accepted_block(&T)`, which returns `None` because `A` is only `LocallyAccepted`, not `GloballyAccepted` [1](#0-0) .
4. The `DuplicateBlockFound` rejection that should fire (and does fire under the equivalent v2 test, `check_tenure_change_rejects_when_locally_accepted_block_exists`, at `stacks-signer/src/chainstate/tests/v2.rs:756-850`) does not fire for v1, and `B` passes proposal-time validation, is submitted to the node, and proceeds toward pre-commit — a state the protocol intends to prevent outright at proposal time for a tenure that already has a locally-accepted (signed) block.
