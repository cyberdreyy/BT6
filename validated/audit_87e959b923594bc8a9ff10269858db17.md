### Title
Silent signer-list truncation on `Pubkey::default()` multisig entries causes `signers.len() != num_valid_signers` misreport - (File: account-decoder/src/parse_token.rs)

### Summary
`parse_token_v3`'s Multisig branch filters the raw `Multisig.signers` array with `filter_map(|pubkey| pubkey != &Pubkey::default())` before returning `UiMultisig.signers`, but it copies `multisig.n` verbatim into `num_valid_signers` without adjusting for filtered entries. Because `Pubkey::default()` is the well-known all-zero System Program address (a legitimate, referenceable pubkey), an attacker can initialize a real SPL-Token/Token-2022 Multisig account whose first `n` signer slots include that address, causing the parsed RPC response to silently drop a "valid" signer while `num_valid_signers` still reports the original count.

### Finding Description
The vulnerable code is in `account-decoder/src/parse_token.rs`:
```rust
Ok(TokenAccountType::Multisig(UiMultisig {
    num_required_signers: multisig.m,
    num_valid_signers: multisig.n,
    is_initialized: multisig.is_initialized,
    signers: multisig
        .signers
        .iter()
        .filter_map(|pubkey| {
            if pubkey != &Pubkey::default() {
                Some(pubkey.to_string())
            } else {
                None
            }
        })
        .collect(),
}))
``` [1](#0-0) 

The SPL Token `Multisig` account layout always stores a fixed 11-entry `signers` array; only the first `n` entries are meant to be "real" signers, while `n..11` are unused padding that is left `Pubkey::default()`-initialized. The `filter_map` was written under the assumption that only padding slots would ever equal `Pubkey::default()`, so filtering them out and leaving `num_valid_signers = multisig.n` unchanged would keep `signers.len() == num_valid_signers` in sync.

That assumption is false: `Pubkey::default()` is the all-zero pubkey, which is the actual address of the System Program (`11111111111111111111111111111111111111111`). The `InitializeMultisig`/`InitializeMultisig2` instruction processor in the SPL Token program copies whichever account pubkeys are passed as the `m..n` signer accounts directly into the `signers` array without rejecting the all-zero/System-Program address. An unprivileged attacker can therefore submit a completely valid `InitializeMultisig` transaction listing the System Program account (or any other means of injecting the all-zero key) as one of the first `n` signer slots.

When such an account is later queried via `getAccountInfo?encoding=jsonParsed` (or any other jsonParsed-based RPC/account-subscription path that routes into `parse_token_v3`), the decoder:
1. Correctly returns `num_valid_signers = n` (e.g., 3) reflecting the raw byte count.
2. Silently drops the attacker-configured default-pubkey slot from `signers`, returning only 2 entries.

No existing guard (parameter limits, commitment checks, length checks) addresses this, since the flaw is purely in the decode/transform logic, not in RPC request validation.

### Impact Explanation
Downstream integrators (wallets, block explorers, exchanges, multisig-management tooling) that trust the parsed `jsonParsed` response will see an inconsistent, incomplete signer list that does not match the reported `numValidSigners`, and will fail to realize the multisig genuinely lists the System Program address as an authorized signer key. This is a decoder misreporting bug ("parsed output faithfully represents raw authority data" invariant violation) affecting the `account-decoder` crate used by JSON-RPC `getAccountInfo`/`getProgramAccounts` and related jsonParsed encodings. It falls under the "misreported authority/signer set to downstream integrators" bounty category — a decoding-fidelity/misreporting bug reachable via a single RPC call on attacker-controlled on-chain data.

### Likelihood Explanation
Exploitation only requires an unprivileged actor to send one on-chain `InitializeMultisig` transaction placing the System Program's pubkey as one of the `m..n` signer accounts (a legal, permissionless operation — no leader/gossip/validator privileges needed), then issue a single `getAccountInfo?encoding=jsonParsed` call. This is fully repeatable and deterministic, and does not depend on timing, contention, or rate limits.

### Recommendation
In the Multisig branch of `parse_token_v3`, do not treat `Pubkey::default()` as an implicit "unused" marker for the first `n` signer slots. Either:
- Filter only the padding range `signers[n as usize..]` rather than all entries, preserving whatever pubkey (including all-zero) is stored within `signers[..n]`, or
- Report `num_valid_signers` as the length of the actually-returned `signers` vector after filtering, so the two fields stay consistent with each other, even if that diverges from raw `multisig.n`.
Either approach restores parity between `signers.len()` and `num_valid_signers`, eliminating the silent information loss.

### Proof of Concept
Extend `account-decoder/src/parse_token.rs`'s existing `test_parse_token` test with a crafted buffer that places a default pubkey inside the "valid" range:
```rust
#[test]
fn test_parse_token_multisig_default_signer_in_valid_range() {
    let signer1 = Pubkey::new_from_array([1; 32]);
    let signer2 = Pubkey::new_from_array([2; 32]);
    let mut multisig_data = vec![0; Multisig::get_packed_len()];
    let mut signers = [Pubkey::default(); 11];
    // slot 0 deliberately left as Pubkey::default() (== System Program id)
    signers[1] = signer1;
    signers[2] = signer2;
    let mut multisig = Multisig::unpack_unchecked(&multisig_data).unwrap();
    multisig.m = 2;
    multisig.n = 3; // three "valid" signer slots, one of which is default
    multisig.is_initialized = true;
    multisig.signers = signers;
    Multisig::pack(multisig, &mut multisig_data).unwrap();

    let TokenAccountType::Multisig(ui) = parse_token_v3(&multisig_data, None).unwrap() else {
        panic!("expected multisig");
    };
    assert_eq!(ui.num_valid_signers, 3);
    // BUG: signers list only has 2 entries, inconsistent with num_valid_signers == 3
    assert_eq!(ui.signers.len(), 2);
    assert_ne!(ui.signers.len() as u8, ui.num_valid_signers);
}
```
This demonstrates that `UiMultisig.signers.len()` (2) diverges from `num_valid_signers` (3), proving information loss relative to the raw 3-signer configuration. [2](#0-1)
