### Title
Loss-haircutted withdraw receipts are keyed to `lastWithdrawRequest`, letting a fresh dust request reclassify them as funded par claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault` assigns a haircut to pending withdraw receipts when `stopEpochWithDuration` realizes a loss: `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = fundedAmount * 1e18 / pendingBasis` and zeroes `pendingWithdraws`, so only the funded (haircutted) amount of underlying is held by the strategy. Claim routing, however, locates a user's loss-adjusted receipt via `lastWithdrawRequest[_user]` — a mutable per-user marker that `requestWithdraw` overwrites on every new request. An unprivileged lender whose receipt was haircutted in epoch E can issue a minimal `requestWithdraw` during the next buffer period, shifting `lastWithdrawRequest` to epoch E+1. Their epoch-E receipt is then invisible to `_claimLossAdjustedWithdrawRequest` (since `lossRecoveryPriceByEpoch[E+1] == 0`) and is paid at par through `_claimFundedWithdrawRequest`, which reads the aggregate `withdrawsRequests[_user]` that was never reduced by the haircut. The strategy only holds the funded (haircutted) balance, so the attacker withdraws more than was funded for them, directly stealing underlyings owed to other receipt holders.

### Finding Description
Analog of CVE-2017-12452 (out-of-bounds read via a crafted index in `bfd_mach_o_i386_canonicalize_one_reloc`): the credit-vault equivalent is an index/key confusion where an attacker-shifted per-user key (`lastWithdrawRequest`) makes the claim dispatcher read the wrong per-epoch accounting record, upgrading a haircutted receipt to a par payout.

Relevant code:

- `requestWithdraw` (lines ~281-294) sets `lastWithdrawRequest[_user] = currentEpoch` on every new request and accumulates `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` without requiring the previous receipt to be claimed (the code comments explicitly allow stacking requests).
- `collectWithdrawFunds` (lines 411-430): when the borrower underfunds (`_amount < pendingBasis`), it stores `lossRecoveryPriceByEpoch[epochNumber]` and sets `pendingWithdraws = 0`, then pulls only `_amount` underlying. Critically, per-user `withdrawsRequests`/`withdrawsRequestsByEpoch` entries still record the full pre-haircut basis.
- `_claimLossAdjustedWithdrawRequest` (lines 789-801) reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. If that mapping entry is 0 it returns 0 without clearing anything — the haircutted receipt is silently skipped rather than claimed.
- `_claimFundedWithdrawRequest` (lines 319-349) then pays `withdrawsRequests[_user] + settled APR0 buckets` at par via `_transferFundedClaim`, gated only by `epochNumber > lastWithdrawRequest[_user]` and the `defaultRecoveryReserve` guard (lines 897-907), which does not bind the payout to what was actually funded for that epoch.
- `_clearWithdrawClaimForEpoch` (lines 811-837) only clears receipts for the epoch passed in; because the dispatcher only ever looks up `lastWithdrawRequest`, the epoch-E entry in `withdrawsRequestsByEpoch` is never consulted and never cleared before the par payout.

Sequence (normal fixed-APR mode, `isInterestMinted` irrelevant, pool not defaulted):

1. Epoch E buffer: attacker deposits AA, epoch starts, attacker calls `requestWithdraw` → receipt recorded at epoch E, `lastWithdrawRequest = E`, minted receipt strategy tokens equal to principal.
2. Epoch E ends; borrower partially repays (a real loss, e.g., credit loss). Honest manager calls `stopEpochWithDuration(_lossAmount)`; `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` fund only `pendingToFund < pendingBasis` and store `lossRecoveryPriceByEpoch[E] < 1e18`.
3. Epoch E+1 buffer (or during the running epoch, whichever mode allows requests — `allowAAWithdrawRequest` is re-enabled after the stop): attacker calls `requestWithdraw` with a dust tranche amount. `lastWithdrawRequest` becomes E+1 and `withdrawsRequests[attacker]` now contains `fullBasis_E + dust`.
4. Epoch E+1 is stopped and fully funded by the honest borrower.
5. Attacker calls `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` checks `lossRecoveryPriceByEpoch[E+1] == 0`, skips; `_claimFundedWithdrawRequest` pays `fullBasis_E + dust` at par.

The strategy holds only `price * basis_E + dust_funded`, so the attacker extracts `basis_E * (1 - lossRecoveryPrice)` of underlying belonging to other claimants — the "out-of-bounds" payout made possible by the attacker-controlled index.

### Impact Explanation
Direct theft of other users' funded withdraw liquidity, quantified as `haircutBasis * (1 - lossRecoveryPriceByEpoch[E])` per exploiting user. Every claimant who had a receipt in the loss epoch can perform this, so the entire haircut amount is extractable by the first claimants, after which remaining claimants' `claimWithdrawRequest` reverts on `safeTransfer` (underfunded strategy) — permanent freezing of honest users' claims. The solvency invariant "one receipt, one funded payout" is broken: receipts are paid at a price that was never funded.

### Likelihood Explanation
Requires only an unprivileged tranche holder (KYC-passed lender) plus a realized `stopEpochWithDuration` loss — an event the protocol explicitly supports and accounts for (borrower partial repayment, which is not a full default and does not require any privileged collusion; the owner/manager merely sequence the epochs honestly). The attacker then performs two ordinary calls (`requestWithdraw` dust + `claimWithdrawRequest`) across two epochs. No guard stops it: `_skimDonatedAssets` is irrelevant here, `defaulted` is false so the default-claim paths don't apply, `isWalletAllowed` passes for any KYC'd lender, and `_transferFundedClaim`'s reserve guard only protects `defaultRecoveryReserve`, not unfunded haircut portions. No existing test covers claim ordering where a user adds a new request after a loss epoch before claiming.

### Recommendation
Route loss-adjusted claims by the actual receipt epochs, not by `lastWithdrawRequest`. Concretely:

- In `_claimLossAdjustedWithdrawRequest`/`_claimFundedWithdrawRequest`, iterate or check `withdrawsRequestsByEpoch[_user][e]` for each epoch `e` that has a nonzero `lossRecoveryPriceByEpoch` entry and a nonzero user basis, rather than keying solely on `lastWithdrawRequest`. A simple fix: record a per-user set of "loss epochs" (e.g., `mapping(address => uint256) lastLossEpoch`/`userLossEpochs`) written at claim time by scanning `lossRecoveryPriceByEpoch` for the epochs in which the user has a nonzero `withdrawsRequestsByEpoch`, or
- Disallow `requestWithdraw` (or new requests via the queue) while the user has any uncleared receipt in an epoch with `lossRecoveryPriceByEpoch != 0`, or
- At `collectWithdrawFunds` loss time, proportionally reduce each user's recorded basis — not feasible per-user, so instead store the haircut and, in `_claimFundedWithdrawRequest`, compute `claimable = Σ basis_e * price_e` over all nonzero `withdrawsRequestsByEpoch` entries before paying, reverting/paying the haircut for any epoch with a recorded loss price.

The key invariant to enforce: a receipt's payout must be `basis * min(1e18, lossRecoveryPriceByEpoch[requestEpoch])` regardless of later requests.

### Proof of Concept
Reproducible in the existing `test/foundry/IdleCreditVault.t.sol` harness:

```solidity
// Test: attacker evades loss haircut via a dust re-request
function testLossHaircutEvasionViaNewRequest() external {
    uint256 amount = 100e6; // attacker deposit
    // epoch E: deposit and start
    _depositWithUser(attacker, amount, false);      // KYC'd lender
    _depositWithUser(victim, amount, false);        // second claimant
    _startEpochAndCheckPrices(0);

    // both request withdraw during epoch E
    _requestWithdrawWithUser(attacker, attackerAABal);
    _requestWithdrawWithUser(victim, victimAABal);

    // epoch E ends with a realized loss: borrower funds only 50%
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = strategy.pendingWithdraws();
    uint256 loss = pending / 2;
    deal(defaultUnderlying, borrower, pending - loss + interestDue);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(loss); // sets lossRecoveryPriceByEpoch[E] ~= 0.5e18
    assertGt(strategy.lossRecoveryPriceByEpoch(strategy.epochNumber()), 0);

    // epoch E+1 buffer: attacker re-requests with dust to shift lastWithdrawRequest
    // (deposit small amount first if needed for a tranche balance)
    _depositWithUser(attacker, 1e6, false);
    _startEpochAndCheckPrices(1);
    _requestWithdrawWithUser(attacker, 1); // dust tranche amount
    uint256 attackerReqEpoch = strategy.epochNumber();
    assertEq(strategy.lastWithdrawRequest(attacker), attackerReqEpoch); // == E+1, not E

    // epoch E+1 fully funded and stopped
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, strategy.pendingWithdraws() + interestDue);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // attacker claims: loss-adjusted path skipped (price[E+1]==0), funded path pays par
    uint256 balPre = underlying.balanceOf(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - balPre;

    uint256 fullBasis = strategyWithdrawBasis(attacker); // pre-haircut basis
    // attacker received ~2x what the loss haircut funded for epoch E
    assertGt(got, fullBasis * strategy.lossRecoveryPriceByEpoch(E) / 1e18 + 1);

    // victim's claim now reverts / underflows the strategy balance
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest(); // victim unpaid: insolvency
}
```

Key assertion: `claimWithdrawRequest` → `claimWithdrawRequest(user)` → `_claimLossAdjustedWithdrawRequest` returns 0 because `lossRecoveryPriceByEpoch[lastWithdrawRequest] == 0`, then `_claimFundedWithdrawRequest` transfers the full `withdrawsRequests[user]` (lines 338-349), paying the epoch-E receipt at par although `collectWithdrawFunds` only pulled `price * basis` underlying (lines 411-429). Uncertain detail to confirm when executing: the exact allow-flag/window in which a post-loss `requestWithdraw` is permitted in each mode (buffer vs. running epoch); if requests are disabled in a given configuration, the dust re-request can instead be performed through `IdleCDOEpochQueue.requestWithdraw`, which has no loss-epoch check either (`contracts/IdleCDOEpochQueue.sol:131-143`).
