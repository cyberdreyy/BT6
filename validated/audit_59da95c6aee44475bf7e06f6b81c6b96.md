### Title
Pending block-response replay ignores arrival order across categories, letting a stale acceptance override a newer rejection (or vice-versa) once a delayed proposal arrives - (File: stacks-signer/src/signerdb.rs)

### Summary
Early votes (pre-commits, acceptances, rejections) that arrive before a signer has seen the corresponding `BlockProposal` are parked in three separate pending tables and replayed once the proposal shows up. The replay path drains all three tables and processes them in a fixed category order (pre-commits, then rejections, then signatures) rather than in the chronological order the messages actually arrived in, even though the underlying tables record a `received_time` for exactly that purpose.

### Finding Description
`drain_pending_block_responses` deletes and returns rows from `signer_pending_pre_commit_responses`, `signer_pending_signature_responses`, and `signer_pending_rejection_responses` with plain `DELETE ... RETURNING` statements that carry no `ORDER BY received_time`: [1](#0-0) 

Contrast this with `get_pending_rejection_responses`, which the codebase itself demonstrates knows how to order by `received_time DESC` when order matters: [2](#0-1) 

Each pending table's primary key is `(signer_signature_hash, signer_addr)` with `INSERT OR REPLACE`, so within one category (e.g. rejections) only the latest message from a given peer survives. But nothing enforces ordering **across** categories: a peer can legitimately emit a signature (acceptance) and later a rejection for the same block-hash before the proposal is locally known (e.g., first pre-commit/sign, then change its vote after re-evaluating chainstate), leaving one stale row in `signer_pending_signature_responses` and one fresher row in `signer_pending_rejection_responses` simultaneously — both tables can hold an entry for the same `(hash, addr)` pair at once since the uniqueness constraint is per-table.

When the proposal finally arrives, `handle_block_proposal` drains all pending responses and replays them via `process_pending_responses_for_block` in a hard-coded order — pre-commits, then rejections, then signatures: [3](#0-2) 

This fixed order is independent of each row's actual `received_time`. If a peer's true sequence was "sign → later reject" (the newer, authoritative state is the rejection), the replay still applies the rejection first and the (older, now-superseded) signature last, so the signer's local view ends by counting the stale acceptance toward the 70% signing weight — the opposite of the peer's most recent, intended vote. The signature is treated as a bearer instrument once counted (per `get_signed_conflicts`'s doc comment noting "rejection... does not clear a conflict... a signature is a bearer instrument"), so a stale acceptance that should have been superseded still counts toward crossing the acceptance threshold in `store_and_process_block_signature`: [4](#0-3) 

This is the direct analog of the reported bug class: just as the multisig transactions lacked a nonce/sequence field so an owner could reorder approved calls for benefit, the signer's pending-response tables lack (and discard) the sequence information (`received_time`) needed to correctly replay a peer's votes in the order they actually happened, allowing a stale "accepted" vote to be counted after a fresher "rejected" vote for the same peer/block — i.e., a rejection recounted, in effect, as an acceptance in the local tally.

### Impact Explanation
This breaks the equality between "a peer's most recent, authoritative vote" and "the vote this signer counts toward the 70% signing weight." If enough proposals are delayed relative to gossip so that several peers' pending rows straddle a sign→reject transition, a signer could end up crediting acceptance weight from peers who have actually moved to rejecting, pushing this signer's local acceptance tally over threshold and producing a signature over a block that should not have reached consensus from this signer's perspective — a rejection recounted as an accept, which is explicitly one of the qualifying Critical impact classes.

### Likelihood Explanation
This requires only a one-slot miner (or any peer signer) plus ordinary StackerDB gossip timing: a peer emits an acceptance then a rejection for the same block (a normal event during pre-commit re-evaluation, chainstate re-checks, or conflict resolution), and the local signer's proposal-arrival for that specific block-hash happens to be delayed past both messages, which is a realistic condition given `handle_block_proposal`'s existing "collect early votes" design explicitly anticipates messages arriving before proposals. No majority collusion, no other signer's key, and no auth-token access is required — only natural message reordering/delay, which the pending-response mechanism was built to handle but handles incorrectly due to the missing cross-table ordering.

### Recommendation
Have `drain_pending_block_responses` return all three categories merged and ordered by `received_time` (ascending), and have `process_pending_responses_for_block` replay them in that single chronological order rather than in a fixed per-category order, so a later rejection always supersedes an earlier acceptance from the same peer (and vice versa) exactly as it would have if the proposal had arrived first.

### Proof of Concept
1. Signer S has not yet received `BlockProposal` for hash `H`.
2. Peer P sends `BlockResponse::Accepted(H)` (e.g., after evaluating a different, older cached proposal state) — stored in `signer_pending_signature_responses` with `received_time = t1`.
3. Peer P subsequently reconsiders (e.g., a chainstate re-check) and sends `BlockResponse::Rejected(H)` — stored in `signer_pending_rejection_responses` with `received_time = t2 > t1`. Both rows now coexist because they live in different tables.
4. S finally receives the `BlockProposal` for `H`; `handle_block_proposal` calls `drain_pending_block_responses(H)`, which returns both entries with no arrival-order information preserved.
5. `process_pending_responses_for_block` processes rejections first, then signatures — applying P's acceptance last regardless of `t1 < t2`, so S's local tally counts P as having accepted `H`, even though P's real final vote (at `t2`) was a rejection. [5](#0-4) [6](#0-5)

    /// Retrieve and clear all pending block response entries matching the given block signer_signature_hash
    /// Returns PendingBlockResponses containing all matching pre-commits, approval signatures, and rejections
    pub fn drain_pending_block_responses(
        &self,
        block_sighash: &Sha512Trunc256Sum,
    ) -> Result<PendingBlockResponses, DBError> {
        let hash_str = block_sighash.to_string();

        // Delete and return pre-commits in one operation
        let pre_commits_qry = "DELETE FROM signer_pending_pre_commit_responses WHERE signer_signature_hash = ?1 RETURNING signer_addr";
        let mut stmt = self.db.prepare(pre_commits_qry)?;
        let pre_commits_rows = stmt.query_map(params![&hash_str], |row| {
            let addr_str: String = row.get(0)?;
            let addr = StacksAddress::from_string(&addr_str).ok_or(
                SqliteError::InvalidColumnType(0, addr_str.clone(), rusqlite::types::Type::Text),
            )?;
            Ok(addr)
        })?;
        let pre_commits: Vec<_> = pre_commits_rows.collect::<Result<Vec<_>, _>>()?;

        // Delete and return signatures in one operation
        let signatures_qry = "DELETE FROM signer_pending_signature_responses WHERE signer_signature_hash = ?1 RETURNING signer_addr, signature";
        let mut stmt = self.db.prepare(signatures_qry)?;
        let signatures_rows = stmt.query_map(params![&hash_str], |row| {
            let addr_str: String = row.get(0)?;
            let sig_str: String = row.get(1)?;
            let addr = StacksAddress::from_string(&addr_str).ok_or(
                SqliteError::InvalidColumnType(0, addr_str.clone(), rusqlite::types::Type::Text),
            )?;
            let signature: MessageSignature = serde_json::from_str(&sig_str).map_err(|_| {
                SqliteError::InvalidColumnType(1, sig_str.clone(), rusqlite::types::Type::Text)
            })?;
            Ok((addr, signature))
        })?;
        let signatures: Vec<_> = signatures_rows.collect::<Result<Vec<_>, _>>()?;

        // Delete and return rejections in one operation
        let rejections_qry = "DELETE FROM signer_pending_rejection_responses WHERE signer_signature_hash = ?1 RETURNING signer_addr, reject_code";
        let mut stmt = self.db.prepare(rejections_qry)?;
        let rejections_rows = stmt.query_map(params![&hash_str], |row| {
            let addr_str: String = row.get(0)?;
            let reject_code: u8 = row.get(1)?;
            let addr = StacksAddress::from_string(&addr_str).ok_or(
                SqliteError::InvalidColumnType(0, addr_str.clone(), rusqlite::types::Type::Text),
            )?;
            let reject_reason = RejectReasonPrefix::from(reject_code);
            Ok((addr, reject_reason))
        })?;
        let rejections: Vec<_> = rejections_rows.collect::<Result<Vec<_>, _>>()?;

        let pending_block_responses = PendingBlockResponses {
            pre_commits,
            signatures,
            rejections,
        };
        if !pending_block_responses.is_empty() {
            debug!("Drained pending block responses for block {block_sighash}";
                "pre_commits_count" => pending_block_responses.pre_commits.len(),
                "signatures_count" => pending_block_responses.signatures.len(),
                "rejections_count" => pending_block_responses.rejections.len());
        }
        Ok(pending_block_responses)
    }

    fn process_pending_responses_for_block(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &mut BlockInfo,
        pending_responses: PendingBlockResponses,
    ) {
        let signer_signature_hash = block_info.block.header.signer_signature_hash();
        for stacker_address in pending_responses.pre_commits {
            debug!("{self}: Processing pending pre-commit.";
                "stacker_address" => %stacker_address,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_info.block.block_id(),
            );
            self.handle_block_pre_commit(
                stacks_client,
                sortition_state,
                &stacker_address,
                &signer_signature_hash,
            );
        }
        for (stacker_address, reject_reason) in pending_responses.rejections {
            debug!("{self}: Processing pending rejection.";
                "stacker_address" => %stacker_address,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_info.block.block_id(),
                "reject_reason" => ?reject_reason,
            );
            self.store_and_process_block_rejection(
                sortition_state,
                block_info,
                &stacker_address,
                reject_reason,
            );
        }
        let block_id = block_info.block.block_id();
        for (stackers_address, signature) in pending_responses.signatures {

                "stacker_address" => %stackers_address,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_id,
            );
            self.store_and_process_block_signature(
                stacks_client,
                sortition_state,
                block_info,
                &stackers_address,
