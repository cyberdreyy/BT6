### Title
Admin can change bank configuration (including risk-critical parameters) while the protocol is panic-paused - (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`)

### Summary
The Compound `_setCreditLimit` bug is a case where a privileged parameter-setting function is not gated by the pause/guardian check, allowing critical risk parameters to change during an incident when the protocol is supposed to be frozen. The strongest reachable analog in marginfi-v2 is the bank-configuration family of instructions, which — despite operator documentation claiming otherwise — are not gated behind `is_protocol_paused()`.

### Finding Description
`LendingPoolConfigureBank`, the primary admin bank-configuration instruction, only checks `has_one = admin` and has no `is_protocol_paused()` constraint in its `Accounts` struct: [1](#0-0) 

Compare this to sibling instructions in the same file/module that explicitly add the pause guard, e.g. `LendingPoolEmissionsDeposit`: [2](#0-1) 

and `LendingPoolAccrueBankInterest`: [3](#0-2) 

and `LendingPoolHandleBankruptcy`, which even makes an explicit admin/risk_admin exception rather than omitting the check entirely: [4](#0-3) 

The scoped delegate variants share the same gap — `LendingPoolConfigureBankInterestOnly` (curve admin) and `LendingPoolConfigureBankLimitsOnly` (limit admin) also have no pause constraint: [5](#0-4) [6](#0-5) 

The `configure()` function invoked by `lending_pool_configure_bank` can change `asset_weight_init/maint`, `liability_weight_init/maint`, `operational_state`, `risk_tier`, `oracle_max_confidence`/`oracle_max_age`, and deposit/borrow limits — the exact risk parameters that determine account health and liquidation thresholds: [7](#0-6) 

Notably, the project's own documentation asserts this is supposed to be blocked: `guides/ADMIN/PERMISSIONS_AND_ROLES.md` explicitly lists "Admin bank configuration changes that route through `LendingPoolConfigureBank`" under "Blocked while paused": [8](#0-7) 

I searched the pause-related test suite (`programs/marginfi/tests/admin_actions/actions_during_pause.rs`) for a test that exercises `configure_bank` during pause and found none — the file only covers deleverage, accrue-interest, liquidation, and bankruptcy flows. This is consistent with the code gap: the check documented as present is absent from the actual `Accounts` struct.

### Impact Explanation
While the panic-pause is designed to be a defensive freeze during an active incident (e.g. oracle manipulation, a discovered exploit, a depeg), an admin (or, in the delegate-scoped case, a curve/limit admin whose key may be less protected than the multisig-controlled `global_fee_admin`) can still push new weights, risk tier, oracle confidence tolerance, or limits into a bank while the rest of the protocol is deliberately silenced. This breaks the "freeze correctly and consistently while triaging" guarantee that a pause is supposed to give: if the admin key is compromised concurrently with, or as the cause of, the incident that triggered the pause, the same actor can degrade a bank's collateral/liability weights or widen the oracle confidence tolerance, worsening the very state the pause was invoked to contain, and users have no ability to react (their deposit/withdraw/repay instructions are blocked) while this config change lands. This is a state-consistency/authority-scope defect with direct financial-safety implications for the pause mechanism, though it requires the config-changing key itself to be used (not a bypass of who can sign) — so its practical severity is bounded by how well the admin/curve/limit keys are protected.

### Likelihood Explanation
Reaching this requires only a valid signature from `admin` (or `delegate_curve_admin` / `delegate_limit_admin`) while the protocol happens to be in a panic-paused window — no cryptographic or logic bypass is needed, it is simply an omitted `constraint`. This makes it trivially reachable by any party holding one of these keys, and specifically dangerous in the admin-key-compromise scenario, which is a primary reason panic-pause exists in the first place.

### Recommendation
Add the same `is_protocol_paused()` guard used elsewhere (`accrue_bank_interest.rs`, `collect_bank_fees.rs`, `configure_bank.rs`'s own `LendingPoolEmissionsDeposit`) to the `group` account constraints of `LendingPoolConfigureBank`, `LendingPoolConfigureBankInterestOnly`, and `LendingPoolConfigureBankLimitsOnly`, consistent with the documented intended behavior in `PERMISSIONS_AND_ROLES.md`. If certain config paths (e.g. risk-tightening-only changes) are intended to remain available during a pause as an admin exception (mirroring the `HandleBankruptcy` pattern), that exception should be explicit and scoped, not an unconditional omission.

### Proof of Concept
1. `global_fee_admin` calls `panic_pause`, setting `panic_state.is_paused_flag()` true and propagating via `propagate_fee_state` to the group's `panic_state_cache`.
2. While paused, `admin` submits `LendingPoolConfigureBank` with a `BankConfigOpt` changing `liability_weight_init/maint` (or `asset_weight_init/maint`, `oracle_max_confidence`, `risk_tier`) on any bank.
3. The instruction succeeds because `LendingPoolConfigureBank`'s `Accounts` struct has no `is_protocol_paused()` check — only `has_one = admin`.
4. Contrast with attempting `lending_pool_accrue_bank_interest` or `lending_pool_emissions_deposit` on the same paused group, which fail with `MarginfiError::ProtocolPaused` per their explicit constraints, confirming the inconsistency is a missing check rather than intended behavior.

        set_if_some!(self.config.asset_weight_init, config.asset_weight_init);
        set_if_some!(self.config.asset_weight_maint, config.asset_weight_maint);
        set_if_some!(
            self.config.liability_weight_init,
            config.liability_weight_init
        );
        set_if_some!(
            self.config.liability_weight_maint,
            config.liability_weight_maint
        );
        set_if_some!(self.config.deposit_limit, config.deposit_limit);

        set_if_some!(self.config.borrow_limit, config.borrow_limit);

        if let Some(new_state) = config.operational_state {
            // JupLend banks must be activated exactly once through `juplend_init_position`.
            check!(
                !(self.config.asset_tag == ASSET_TAG_JUPLEND
                    && self.config.operational_state == BankOperationalState::Uninitialized),
                MarginfiError::Unauthorized
            );
            // These states are unreachable by configuration
            check!(
                new_state != BankOperationalState::KilledByBankruptcy
                    && new_state != BankOperationalState::Uninitialized,
                MarginfiError::Unauthorized
            );
            // Log operational state change
            let old_state = self.config.operational_state;
            self.config.operational_state = new_state;
            msg!(
                "Operational state changed from {:?} to {:?}",
                old_state,
                new_state
            );
        }

        if let Some(ir_config) = &config.interest_rate_config {
            self.config.interest_rate_config.update(ir_config);
        }

        // Log risk tier change
        if let Some(new_risk_tier) = config.risk_tier {
            let old_risk_tier = self.config.risk_tier;
            self.config.risk_tier = new_risk_tier;
            msg!(
                "Risk tier changed from {:?} to {:?}",
                old_risk_tier,
                new_risk_tier
            );
        }
