### Title
Instant-withdraw receipts can be claimed before they are funded, draining other users' deposits while `pendingInstantWithdraws` is still collected in full - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The Keycloak bug (CVE-2018-14637) is an expiry/replay flaw: a consumer endpoint accepts SAML assertions without checking their validity window, so an attacker reuses a stale/expired credential. The strongest analog in this codebase is `IdleCreditVault.claimInstantWithdrawRequest`: it pays out a request receipt without checking the receipt's validity condition — that the request has actually been funded at `startEpoch` via `collectInstantWithdrawFunds`. A normal withdraw receipt is gated by a maturity check (`epochNumber > lastWithdrawRequest` in `_claimFundedWithdrawRequest`, `IdleCreditVault.sol:326-328`), but the instant receipt has no equivalent maturity/funding gate and, critically, the claim does **not** decrement `pendingInstantWithdraws`, so the same receipt is funded a second time at the next `startEpoch`.

### Finding Description
The flow:

1. During the buffer phase (epoch stopped, `isEpochRunning() == false`), the attacker — any KYC-passed AA/BB tranche holder — calls `IdleCDOEpochVariant.requestInstantWithdraw`, which routes to `IdleCreditVault.requestInstantWithdraw` (`IdleCreditVault.sol:356-375`). The strategy burns the CDO's strategy tokens, mints a receipt to the user, and increments `instantWithdrawsRequests[user]` and `pendingInstantWithdraws`. No underlying has been moved to the strategy for this request yet — funding only happens later, at `startEpoch`, when the CDO calls `collectInstantWithdrawFunds` (`IdleCreditVault.sol:398-403`), which pulls `pendingInstantWithdraws` from the CDO/borrower.

2. The attacker immediately calls `IdleCDOEpochVariant.claimInstantWithdrawRequest()` → `IdleCreditVault.claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`). The function only calls `_burn(_user, amount)` and `_transferFundedClaim(_user, amount)` — it never verifies that the receipt's funding was collected (no `epochNumber` comparison, no `instantWithdrawClaimsByEpoch`-vs-funded check). During the buffer the strategy holds underlying from `deposit()` calls (`IdleCreditVault.sol:596-617`) — funds belonging to the epoch depositors awaiting `startEpoch`. `_transferFundedClaim` (`IdleCreditVault.sol:897-907`) pays out any balance above `defaultRecoveryReserve`, so the attacker is paid from these deposits.

3. The claim never decrements `pendingInstantWithdraws` (contrast `collectInstantWithdrawFunds`, `IdleCreditVault.sol:401`, which is the only decreaser). At the next `startEpoch`, the honest manager's call still causes the CDO to fund the full `pendingInstantWithdraws` again — the same receipt is funded twice: once paid early from depositors' cash, once pulled from the CDO/borrower to back the (now already-claimed) pending bucket.

The guard that exists for normal withdraws — the per-epoch maturity check `epochNumber <= lastWithdrawRequest[_user]` revert — has no counterpart for instant receipts; `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` are recorded but only consumed for default accounting (`IdleCreditVault.sol:842-856`), never to gate the funded claim.

### Impact Explanation
Direct theft and insolvency, quantified as the attacker's instant-withdraw amount. Each cycle: attacker withdraws X of pooled deposit cash during the buffer, then `collectInstantWithdrawFunds` pulls another X from the CDO at `startEpoch` for a receipt that is already burned. The excess funded underlying sits in the strategy and is claimable by other instant receipt holders — or, if the attacker is the only instant withdrawer, becomes unbacked surplus — while the depositors whose cash was taken early have their deposits double-spent. Repeating over multiple epochs compounds the drain up to the pool's liquid balance. Broken invariants: one-receipt-one-payout and fair burn/funding.

### Likelihood Explanation
Requires only a KYC-passed wallet holding tranche tokens, `allowInstantWithdraw` enabled, and a buffer-phase window where the strategy holds deposits — all routine conditions. No privileged role involvement, no price manipulation, no borrower misbehavior. The only mitigation is whether a sufficient deposit balance sits in the strategy during the buffer, which is the normal state between `deposit()` and `startEpoch`.

### Recommendation
In `IdleCreditVault.claimInstantWithdrawRequest`, enforce the funding condition before paying: either require that the request epoch's funds were collected (e.g., track a funded-per-epoch flag set in `collectInstantWithdrawFunds` and compare `instantWithdrawsRequestsByEpoch[_user][fundedEpoch]`), and decrement `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` when a claim is paid so a receipt cannot be both claimed early and re-funded at `startEpoch`. Align the gating with the normal path's `epochNumber > requestEpoch` maturity rule.

### Proof of Concept
Foundry fork PoC outline (mirroring `test/foundry/IdleCreditVault.t.sol` setup):

```solidity
// Setup: pool with instant withdraws enabled, between epochs (buffer phase).
// victim deposits via cdoEpoch.depositAA(amount); strategy holds `amount` underlying
// (deposit() at IdleCreditVault.sol:596 pulls underlying into the strategy).

// 1. Attacker (KYC'd tranche holder) requests instant withdraw during buffer.
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(shares, address(AAtranche));
// pendingInstantWithdraws == X; strategy holds victim deposits, not yet funded for X.

// 2. Attacker claims immediately — no funding/maturity gate exists.
uint256 balBefore = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest(); // only checks allowInstantWithdraw
assertGt(underlying.balanceOf(attacker) - balBefore, 0); // paid from victim deposits

// 3. Manager starts epoch; CDO funds pendingInstantWithdraws AGAIN via
//    collectInstantWithdrawFunds (pendingInstantWithdraws was never decremented).
vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() + 1);
vm.prank(manager);
cdoEpoch.startEpoch();
// Strategy balance now contains X funded for an already-burned receipt ->
// pool insolvency / double payout of one receipt.
```

One caveat I could not fully verify within the available iterations: the exact `IdleCDOEpochVariant.requestInstantWithdraw`/`claimInstantWithdrawRequest` gating beyond `allowInstantWithdraw` (e.g., whether `requestInstantWithdraw` is restricted to the buffer and whether any epoch-running check exists on the claim path). The visible code shows no funding check in either contract on the claim path, but a full review of `IdleCDOEpochVariant.sol`'s request/claim wrappers is warranted before finalizing the PoC.
