### Title
Single shareholder can permanently brick `vesting::distribute` and block reward/grant withdrawal for all other shareholders — ([File: aptos-move/framework/aptos-framework/sources/vesting.move])

### Summary
`vesting::distribute()` iterates over every shareholder in a vesting contract and unconditionally calls `aptos_account::deposit_coins()` to pay out each one's share from a single, already-extracted `Coin<AptosCoin>` [3](#0-2) . Any single shareholder (or their beneficiary) can make their own deposit permanently fail — e.g. by never registering a `CoinStore<AptosCoin>` for that address and calling `aptos_account::set_allow_direct_coin_transfers(false)` on it — which causes `aptos_account::deposit_coins` to abort with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` [4](#0-3) . Because the coins for the whole distribution round are pulled out of the stake pool and split inside one atomic Move transaction with no per-recipient error isolation, this single failure reverts the entire `distribute()` call — trapping the rewards/vested tokens of every other shareholder in the same vesting contract, indefinitely. This is the direct structural analog of the ERC20 "arbitrary token in erc20TokensToIncludeInQuit blocks rage-quit for everyone" bug class: one uncooperative party can block the exit/claim path for an entire cohort.

### Finding Description
`distribute()` withdraws all currently-inactive stake as a single `Coin<AptosCoin>` and then loops `shareholders.for_each_ref` to `coin::extract` and `aptos_account::deposit_coins` a slice to each shareholder's beneficiary address [5](#0-4) . `get_beneficiary` returns the shareholder's own address unless an admin has explicitly set a different beneficiary [1](#0-0) , so by default the recipient is the shareholder address itself, which the shareholder fully controls.

`aptos_account::deposit_coins` only auto-registers the recipient's `CoinStore` if the recipient is not yet registered *and* still opts in to direct transfers; if the recipient has disabled `allow_arbitrary_coin_transfers` via `set_allow_direct_coin_transfers(false)` (a completely permissionless, unprivileged call any account holder can make on their own account) while unregistered for `AptosCoin`, the call hits `assert!(can_receive_direct_coin_transfers(to), ...)` and aborts [4](#0-3) .

Nothing in `create_vesting_contract` requires the shareholder to already have a registered `AptosCoin` `CoinStore` — the caller (admin) can supply the buy-in coins from any source on the shareholder's behalf, so a shareholder can be added to a vesting contract without ever having interacted with `AptosCoin` themselves. That shareholder can then permissionlessly configure their own account (or an address they nominate before any beneficiary override is applied) to reject un-registered direct transfers, guaranteeing every future `distribute()` call for that contract aborts.

`distribute()` is `public entry` and callable by anyone (no signer check) [6](#0-5) , and critically, `terminate_vesting_contract()` — the admin's designated escape hatch — calls `distribute()` as its very first step before checking any admin authorization or clearing state [7](#0-6) . So the same griefing shareholder also blocks the admin from ever terminating the contract and reclaiming/finalizing the remaining grant through the normal path.

### Impact Explanation
This breaks the core "shareholders can withdraw rewards/vested funds anytime" invariant documented at the top of the module [8](#0-7) . A single unprivileged shareholder (added to the pool like any other, no special role required) can permanently strand the accumulated rewards and vested APT of every other shareholder in the same contract, since `distribute()`, and by extension `terminate_vesting_contract()`, can never succeed again once the malicious account is configured this way. This is a permanent, non-recoverable loss of claim rights for co-shareholders in stake/vesting flows, matching the "Permanent lock or non-recoverable loss of claim rights ... in ... vesting flows" impact category.

### Likelihood Explanation
Likelihood is high: the attack requires no special privilege, only being one of the shareholders in a shared vesting contract (a common real-world setup, e.g., team/investor grants with multiple beneficiaries pooled under one contract) and a single permissionless call (`set_allow_direct_coin_transfers(false)`) made before ever registering for `AptosCoin`. No governance, admin cooperation, or race condition is needed.

### Recommendation
Do not perform per-shareholder payouts inside a single atomic loop where one failure reverts all others. Options:
- Wrap each recipient's `deposit_coins` in a way that isolates failures (e.g., route failed deposits to a per-shareholder claimable/pull-based ledger instead of push-based `for_each_ref` distribution), or
- Skip (and log/queue) any shareholder whose deposit would fail rather than aborting the whole transaction, or
- Require and enforce that all shareholders/beneficiaries are registered and accepting of direct transfers at vesting-contract creation time, and re-validate on any beneficiary change, rejecting configurations that would let a single party block bulk distribution.

### Proof of Concept
1. Admin creates a vesting contract with shareholders `[A, B]`, funding both buy-ins from the admin's own coins (per `create_vesting_contract`, coins are supplied via `buy_ins: SimpleMap<address, Coin<AptosCoin>>` keyed by shareholder address, not withdrawn from the shareholder) [9](#0-8) , so shareholder `A`'s address has no `AptosCoin` `CoinStore` yet.
2. `A` calls `aptos_framework::aptos_account::create_account(A)` (if needed) then `aptos_account::set_allow_direct_coin_transfers(A_signer, false)` — a fully permissionless self-service call.
3. Time passes, stake accrues rewards, lockup expires; anyone calls `vesting::distribute(contract_address)`.
4. Inside the loop, when it reaches shareholder `A`, `aptos_account::deposit_coins(A, share_of_coins)` hits `!coin::is_account_registered<AptosCoin>(A)` (true) and `can_receive_direct_coin_transfers(A)` (false), aborting with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` [10](#0-9) .
5. The entire `distribute()` transaction reverts, so shareholder `B` never receives any of their rewards; this repeats for every future epoch/vest cycle. `terminate_vesting_contract()` likewise reverts at its initial `distribute(contract_address)` call, so the admin cannot even terminate and fall back to `admin_withdraw` for the remaining grant.

    public entry fun distribute(contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        let coins = withdraw_stake(vesting_contract, contract_address);
        let total_distribution_amount = coin::value(&coins);
        if (total_distribution_amount == 0) {
            coin::destroy_zero(coins);
            return
        };

        // Distribute coins to all shareholders in the vesting contract.
        let grant_pool = &vesting_contract.grant_pool;
        let shareholders = &grant_pool.shareholders();
        shareholders.for_each_ref(|shareholder| {
            let shareholder = *shareholder;
            let shares = pool_u64::shares(grant_pool, shareholder);
            let amount = pool_u64::shares_to_amount_with_total_coins(grant_pool, shares, total_distribution_amount);
            let share_of_coins = coin::extract(&mut coins, amount);
            let recipient_address = get_beneficiary(vesting_contract, shareholder);
            aptos_account::deposit_coins(recipient_address, share_of_coins);
        });
