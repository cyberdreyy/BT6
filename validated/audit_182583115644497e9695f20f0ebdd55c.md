### Title
Sequential unbounded fan-out to DON nodes in vault gateway handler can stall or fail unprivileged client requests - (File: core/services/gateway/handlers/vault/handler.go)

### Summary
`fanOutToVaultNodes` in `core/services/gateway/handlers/vault/handler.go` iterates synchronously over all DON members and issues a blocking `SendToNode` call for each one, using only the overall request context as a bound. Unlike the sibling `confidentialrelay` handler, which explicitly fixed this exact failure mode by fanning out in parallel with a dedicated per-send timeout, the vault handler still performs the send loop sequentially with no per-node timeout, mirroring the unbounded-loop-with-external-calls class of bug described in the report (a single slow/blocked iteration in the loop can hold up or break the whole batch operation for a legitimate caller).

### Finding Description
`fanOutToVaultNodes` is the terminal step of every vault request path reachable by an unprivileged client (`handleSecretsCreate`, `handleSecretsUpdate`, `handleSecretsDelete`, `handleSecretsList`, `handlePublicKeyGet`): [1](#0-0) 

It loops over `h.donConfig.Members` and calls `h.don.SendToNode(ctx, node.Address, &ar.req)` for each node **in sequence**, with no per-node timeout — only the caller-supplied `ctx` bounds each call: [2](#0-1) 

`SendToNode` ultimately funnels into `wsConnectionWrapper.Write`, which pushes the write onto a single-threaded `writeCh` consumed by `writePump`, and blocks until either the write completes or `ctx` is cancelled: [3](#0-2) 

Because the writePump processes writes to a given connection one at a time and `Write` blocks the caller until it is serviced, a slow, congested, or momentarily unresponsive websocket to *any single node* stalls the entire `fanOutToVaultNodes` loop before subsequent nodes are even attempted. This is functionally the same bug class as the report: an in-loop external call (network I/O to a node) with no independent bound per iteration, so one bad iteration degrades or blocks the whole operation.

This is explicitly the failure mode the `confidentialrelay` handler was hardened against — its `fanOutToNodes` fans out in parallel goroutines under a dedicated `nodeSendTimeout`, with an inline comment describing exactly this risk ("a node whose websocket accepts no writes blocks... an unbounded send would hold the request open"): [4](#0-3) 

The vault handler has no equivalent parallelization or per-node timeout, so it retains the vulnerability that was fixed elsewhere in the same gateway package.

### Impact Explanation
Every unprivileged vault request (`vault_secretsCreate`, `vault_secretsUpdate`, `vault_secretsDelete`, `vault_secretsList`, and cache-miss `vault_publicKeyGet`) triggers this sequential, unbounded fan-out. If one DON member's connection is degraded (write buffer saturated, slow TCP path, or the write pump busy with a prior stuck message), that single node delays or blocks delivery to all subsequent nodes in the list for that request, and by extension delays/denies the response to the legitimate calling client. In the worst case, only the overall request context timeout terminates the stall, at which point the entire request — including nodes never even reached — fails, denying service to a legitimate user for reasons unrelated to their own request.

### Likelihood Explanation
Any single slow or backed-up node connection (not necessarily malicious — e.g. a node under load, restarting, or with a temporarily full TCP send buffer) is sufficient to trigger the degraded path. Because fan-out is purely sequential and not parallelized, the effect compounds with DON size (more members = higher chance one is currently slow, and higher cumulative delay). This is reachable directly from any unprivileged client's ordinary vault write/read call.

### Recommendation
Mirror the `confidentialrelay` handler's fix: fan out to nodes in parallel (e.g., via `errgroup`) and bound each individual send with its own short-lived context derived from, but independent of, the overall request deadline, so a single slow node cannot block delivery to (or degrade response time for) the rest of the DON.

### Proof of Concept
1. An unprivileged client sends a `vault_secretsList` (or create/update/delete) request to the gateway, which is dispatched to `handleSecretsList`/`handleSecretsCreate`/etc., all of which call `fanOutToVaultNodes`. [5](#0-4) 
2. `fanOutToVaultNodes` iterates `h.donConfig.Members` sequentially and calls `h.don.SendToNode` for each, with no per-node timeout — only the shared request `ctx`. [2](#0-1) 
3. If the first node's `wsConnectionWrapper.Write` call takes a long time to be serviced by `writePump` (e.g., prior write in flight, TCP send buffer full), the loop blocks on that call before ever reaching subsequent nodes. [3](#0-2) 
4. The legitimate client's request is delayed or times out entirely, even though most DON members were otherwise healthy and reachable — contrasted with the parallel, per-node-timeout-bounded approach already used in `confidentialrelay.fanOutToNodes` for the same class of problem.

func (h *handler) fanOutToVaultNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var nodeErrors []error
	for _, node := range h.donConfig.Members {
		err := h.don.SendToNode(ctx, node.Address, &ar.req)
		if err != nil {
			nodeErrors = append(nodeErrors, err)
			l.Errorw("error sending request to node", "node", node.Address, "error", err)
		}
	}

	if len(nodeErrors) == len(h.donConfig.Members) && len(nodeErrors) > 0 {
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.FatalError, errors.New("failed to forward user request to nodes"), nil))
	}

	l.Debugw("successfully forwarded request to Vault nodes")
	return nil
}

func (c *wsConnectionWrapper) Write(ctx context.Context, msgType int, data []byte) error {
	errCh := make(chan error, 1)
	// push to write channel
	select {
	case c.writeCh <- writeItem{msgType, data, errCh}:
		break
	case <-c.shutdownCh:
		return ErrWrapperShutdown
	case <-ctx.Done():
		return ctx.Err()
	}
	// wait for write result
	select {
	case err := <-errCh:
		return err
	case <-c.shutdownCh:
		return ErrWrapperShutdown
	case <-ctx.Done():
		return ctx.Err()
	}
}
