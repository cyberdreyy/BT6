[1](#0-0) ### Title
Gearbox strategy misvalues ERC-4626 vaults whose share decimals differ from their asset - (`contracts/strategies/gearbox/GearboxStrategy.sol`)

### Summary
`GearboxStrategy` tokenizes external ERC-4626 shares by scaling them with the underlying token’s decimals rather than the vault share decimals. For a standards-compliant ERC-4626 vault with a nonzero decimal offset, the strategy mints the wrong number of 18-decimal strategy tokens while `price()` still values one vault-share unit. This overstates or understates CDO NAV and lets an ordinary tranche depositor withdraw assets belonging to other tranche holders.

### Finding Description
`GearboxStrategy._initialize()` sets `oneToken` from `underlyingToken.decimals()`, not from `strategyToken.decimals()` [2](#0-1) .

On deposit, `depositWithReferral()` returns shares denominated in the external ERC-4626 vault’s decimals, but the strategy converts them to its own 18-decimal receipt using `shares * 1e18 / oneToken` [1](#0-0) . The same incorrect denominator is used when burning the receipt during redemption [3](#0-2) .

This is only correct when `vault.decimals() == asset.decimals()`. ERC-4626 permits share decimals to differ. The inherited `price()` correctly samples `convertToAssets(10 ** vault.decimals())`, so the stored price remains denominated per vault-share unit [4](#0-3) . Consequently, when vault decimals exceed asset decimals, both the minted receipt balance and the CDO’s measured position are multiplied by `10 ** (vaultDecimals - assetDecimals)`.

The CDO calculates NAV from `getContractValue()` during `_updateAccounting()` [5](#0-4) , while tranches are minted from the actual underlying amount received [6](#0-5) . The deposit therefore records real principal but exposes a scaled-up strategy-token balance to subsequent NAV accounting.

### Impact Explanation
For example, with a 6-decimal asset and an 18-decimal ERC-4626 share token, depositing `1e6` assets initially mints `1e18` vault shares. `GearboxStrategy` converts those shares to `1e30` strategy tokens because it divides by `oneToken = 1e6` instead of `1e18`.

If the CDO values the position as `strategyTokenBalance * price() / 1e18`, the reported NAV becomes `1e18` underlying units although the vault position is worth only `1e6` units. With existing liquidity of `100e6`, an attacker can deposit enough assets to obtain a meaningful tranche share, trigger accounting, and then redeem a small fraction of their tranches for all real assets held by the vault. The remaining tranche holders are left with claims exceeding the vault’s redeemable assets.

`_checkDefault()` does not prevent this because the external vault’s `price()` remains correct; the accounting error comes from the incorrectly scaled internal strategy-token balance rather than a lower share price [7](#0-6) .

### Likelihood Explanation
The issue requires the configured ERC-4626/Gearbox-compatible vault to use share decimals different from the underlying asset, such as a vault implementing a positive ERC-4626 decimals offset. The initializer does not enforce matching decimals, so this is a supported input under the ERC-4626 interface rather than a malicious privileged action [8](#0-7) . Exploitation only requires an allowed lender to deposit and withdraw after the inflated strategy position is recognized.

### Recommendation
Read `vaultDecimals = IERC4626(strategyToken).decimals()` during initialization and normalize external vault shares using `10 ** vaultDecimals`, not `oneToken`:

```solidity
uint256 vaultDecimals = IERC4626(_strategyToken).decimals();
mintedStrategyShares = shares * 1e18 / 10 ** vaultDecimals;
```

Apply the same vault-share denominator in `_redeem()`. Alternatively, explicitly require `IERC20Detailed(_strategyToken).decimals() == tokenDecimals` during initialization if only equal-decimal Gearbox vaults are intended.

### Proof of Concept
A Foundry regression can use a standards-compliant ERC-4626 vault with a 6-decimal asset and 18-decimal shares:

```solidity
function testVaultDecimalsOffsetOverstatesStrategyPosition() public {
    // asset.decimals() == 6
    // vault.decimals() == 18
    // vault.convertToShares(1e6) == 1e18

    uint256 assets = 1e6;
    deal(address(asset), cdo, assets);

    vm.prank(cdo);
    asset.approve(address(strategy), assets);

    vm.prank(cdo);
    uint256 vaultShares = strategy.deposit(assets);

    assertEq(vaultShares, 1e18);
    assertEq(vault.balanceOf(address(strategy)), 1e18);

    // Bug: the strategy receipt is scaled by 1e6 instead of 1e18.
    assertEq(strategy.balanceOf(cdo), 1e30);

    assertEq(strategy.price(), 1e6);
    assertEq(vault.convertToAssets(1e18), 1e6);

    // The NAV calculation overstates the position by 1e12.
    uint256 reportedValue = strategy.balanceOf(cdo) * strategy.price() / 1e18;
    assertEq(reportedValue, 1e18);
    assertGt(reportedValue, assets);
}
```

The correct internal mint should be `1e18`, not `1e30`; after the fix, `reportedValue` equals `assets`.
