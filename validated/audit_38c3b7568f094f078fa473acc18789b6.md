## Analysis

The reported bug class — a fee parameter that can be changed to an arbitrary/unbounded value and applied against an already-pending user transaction, with no validation cap — maps onto Base's Isthmus **operator fee scalar** handling.

### Root cause

`OperatorFeeUpdate::try_from` decodes `operator_fee_scalar` (a raw `u32`) and `operator_fee_constant` (a raw `u64`) straight out of the L1 `SystemConfig` `ConfigUpdate` log payload and applies them to `SystemConfig` with **no range/sanity check** at all: [1](#0-0) 

This is inconsistent with the neighboring `GasConfigUpdate`, which explicitly validates the decoded L1 fee scalar via `RollupConfig::check_ecotone_l1_system_config_scalar` and silently discards (keeps the old value) an invalid one: [2](#0-1) 

The unchecked `operator_fee_scalar` is then fed directly into the fee-charging math with no cap, `gas * operator_fee_scalar[/ or *]` depending on upgrade: [3](#0-2) 

The resulting operator fee is deducted from the transaction sender's balance and credited to the `OPERATOR_FEE_VAULT` in every execution path — the legacy handler, EIP-8130, and EVM2: [4](#0-3) [5](#0-4) [6](#0-5) 

### Why this is the same bug class

Just as `royaltiesBps` in the reported NFTCollection contract can be set up to 100% at any time with no cap flag, front-running a buyer's already-submitted purchase, `operator_fee_scalar` here can be set to `u32::MAX` (or any value) with **no protocol-level cap enforced in the node's derivation code**, and applied retroactively to any transaction already signed/broadcast by an unprivileged user before that L1 `ConfigUpdate` log lands. Because the fee math multiplies `gas_limit`/`gas_used` directly by the scalar (with only a `saturating_mul`/`wrapping_div`, not a bound check), a scalar change can extract an arbitrarily large fee from the sender's prepaid balance straight to `Predeploys::OPERATOR_FEE_VAULT` — a direct value-extraction path analogous to the royalty front-run, and worse than the txpool's own admission check, which merely re-derives cost from the *same* unbounded parameter rather than capping it: [7](#0-6) 

### Title
Unbounded `operator_fee_scalar` update lets a fee-parameter change front-run and drain value from already-signed user transactions - (`crates/common/genesis/src/updates/operator_fee.rs`)

### Summary
`OperatorFeeUpdate::try_from` decodes the Isthmus operator-fee scalar/constant from an L1 `SystemConfig` log without any bound, sanity, or cap check, unlike the sibling `GasConfigUpdate` which validates its scalar. The unchecked value is applied verbatim to `SystemConfig.operator_fee_scalar` and later multiplied directly into every transaction's fee charge.

### Finding Description
`OperatorFeeUpdate` extracts a raw `u32` scalar and `u64` constant from the update log payload and returns them unconditionally (`crates/common/genesis/src/updates/operator_fee.rs:56-66`), then applies them to the live `SystemConfig` (`operator_fee.rs:19-24`). By contrast, `GasConfigUpdate` performs an explicit validity check on its analogous scalar and discards invalid values rather than applying them (`crates/common/genesis/src/updates/gas_config.rs:60-65`). No equivalent guard exists for the operator fee scalar anywhere in the update/derivation pipeline (`crates/common/genesis/src/system/log.rs`, `crates/common/genesis/src/system/update.rs`).

The unbounded scalar then flows straight into `L1FeeParams::operator_fee_charge_inner`, which computes `gas * operator_fee_scalar [/ OPERATOR_FEE_SCALAR_DECIMAL or * OPERATOR_FEE_JOVIAN_MULTIPLIER] + operator_fee_constant` with only saturating arithmetic — there is no ceiling on the resulting fee (`crates/common/l1-fees/src/params.rs:184-199`). Every execution path (legacy handler `reward_beneficiary`, the EIP-8130 pre-charge/settlement, and EVM2's `TxHandlerHooks`) charges this value from the sender's account balance directly to `Predeploys::OPERATOR_FEE_VAULT`.

### Impact Explanation
Because the scalar is applied to whichever block a pending, already-signed transaction lands in, a scalar change that takes effect between broadcast and inclusion can multiply the operator-fee component of a transaction's cost by orders of magnitude with no protocol-enforced cap, extracting funds from the sender to the operator fee vault beyond what the sender consented to when signing/funding the transaction, or causing balance-based rejection (`InsufficientFunds`/`LackOfFundForMaxFee`) of previously-valid, fully-funded transactions. This is a direct analog of the reported royalty front-running class: an update to a fee-multiplying parameter, without any bound, that is retroactively applied against a value already committed to by an unprivileged party.

### Likelihood Explanation
Triggering requires only a single `ConfigUpdate(OperatorFee)` L1 log with an out-of-range scalar being derived and applied — there is no additional privileged access needed within this codebase's derivation/execution logic itself (the guard that upstream chains rely on for such parameters is exactly the kind of cap the sibling `GasConfigUpdate` implements but this update omits). Any legitimate or malicious update to this L1 log field is applied without any local validation.

### Recommendation
Add a bound/sanity check for `operator_fee_scalar` (and `operator_fee_constant`) in `OperatorFeeUpdate::try_from`, mirroring `GasConfigUpdate`'s use of `RollupConfig::check_ecotone_l1_system_config_scalar` — reject or ignore values outside an agreed maximum (e.g., matching the `OPERATOR_FEE_SCALAR_DECIMAL` fixed-point range) rather than applying arbitrary `u32`/`u64` values straight into the fee-charging math.

### Proof of Concept
1. Post an L1 `ConfigUpdate` log of kind `OperatorFee` (`SystemConfigUpdateKind::OperatorFee = 5`) with `operator_fee_scalar = 0xFFFFFFFF`.
2. `SystemConfigLog::build` dispatches to `OperatorFeeUpdate::try_from`, which decodes and returns the value unchecked (`operator_fee.rs:56-65`); `SystemConfigUpdate::apply` sets it on `SystemConfig` (`system/update.rs:50`).
3. `L1BlockInfo`/`L1FeeParams` picks up the new scalar; any pending or newly-included transaction now has its operator fee computed as `gas_used * 0xFFFFFFFF / 1_000_000` (or `* 100` post-Jovian) (`params.rs:188-199`), charged from the sender's balance to `OPERATOR_FEE_VAULT` in `reward_beneficiary`/`settle_fees`/`settle_transaction`, with no cap anywhere in the path.

    /// Applies the update to the [`SystemConfig`].

        config.operator_fee_constant = Some(self.operator_fee_constant);
    }

impl TryFrom<&SystemConfigLog> for OperatorFeeUpdate {
    type Error = OperatorFeeUpdateError;

    fn try_from(log: &SystemConfigLog) -> Result<Self, Self::Error> {
        let LogData { data, .. } = &log.log.data;

        let validated = UpdateDataValidator::validate(data).map_err(|e| match e {
            ValidationError::InvalidDataLen(_expected, actual) => {
                OperatorFeeUpdateError::InvalidDataLen(actual)
            }
            ValidationError::PointerDecodingError => OperatorFeeUpdateError::PointerDecodingError,
            ValidationError::InvalidDataPointer(pointer) => {
                OperatorFeeUpdateError::InvalidDataPointer(pointer)
            }
            ValidationError::LengthDecodingError => OperatorFeeUpdateError::LengthDecodingError,
            ValidationError::InvalidDataLength(length) => {
                OperatorFeeUpdateError::InvalidDataLength(length)
            }
        })?;

        // The operator fee scalar and constant are
        // packed into a single u256 as follows:
        //
        // | Bytes    | Actual Size | Variable |
        // |----------|-------------|----------|
        // | 0 .. 24  | uint32      | scalar   |
        // | 24 .. 32 | uint64      | constant |
        // |----------|-------------|----------|

        let payload = validated.payload();
        let mut be_bytes = [0u8; 4];
        be_bytes[0..4].copy_from_slice(&payload[20..24]);
        let operator_fee_scalar = u32::from_be_bytes(be_bytes);

        let mut be_bytes = [0u8; 8];
        be_bytes[0..8].copy_from_slice(&payload[24..32]);
        let operator_fee_constant = u64::from_be_bytes(be_bytes);

        Ok(Self { operator_fee_scalar, operator_fee_constant })
    }

    /// Calculates the operator fee for a given `gas` amount.
    ///
    /// Missing scalars fall back to zero to match the execution path during the
    /// txpool bootstrap window before the first L1 attributes deposit.
    pub fn operator_fee_charge_inner(&self, gas: U256, upgrade: BaseUpgrade) -> U256 {
        let operator_fee_scalar = self.operator_fee_scalar.unwrap_or_default();
        let operator_fee_constant = self.operator_fee_constant.unwrap_or_default();

        let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
            gas.saturating_mul(operator_fee_scalar)
                .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
        } else {
            gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
        };
        product.saturating_add(operator_fee_constant)
    }
