### Title
Funded instant-withdraw claims never clear `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, inflating the default-recovery basis and permanently freezing part of the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug (CVE-2016-9106) is a resource leak: QEMU's `v9fs_write` fails to free an IO vector, so the resource is never released back for reuse. The on-chain analog is a *receipt-basis leak*: `claimInstantWithdrawRequest` pays a funded instant withdrawal but never deletes the per-epoch accounting entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. If the same epoch later defaults, `defaultPendingClaimBasis` counts the already-paid receipt a second time, the recovery price is diluted for all claimants, and the stale basis makes the user's defaulted-claim path revert on underflow — permanently locking the corresponding slice of `defaultRecoveryReserve` inside the strategy.

### Finding Description
In `requestInstantWithdraw`, the vault records both an aggregate and per-epoch basis for the receipt (IdleCreditVault.sol:366-374):

```solidity
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

The normal funded-claim path only clears the aggregate (IdleCreditVault.sol:387-392):

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` are left stale. They are only ever decremented inside `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which runs exclusively after default finalization.

This leaked basis is then consumed by default accounting:

- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (lines 644-649), so `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` over a basis that includes receipts already paid at par (line 688).
- `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` (line 696), so the defaulted-epoch instant claim path is enabled.
- On claim, `_claimDefaultedInstantWithdrawRequest` reads `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — which still includes the already-paid amount — then executes `instantWithdrawsRequests[_user] -= claimBasis` (line 848). Since the funded claim already zeroed the aggregate (or the aggregate only covers a newer, smaller request), this underflows and the entire `claimInstantWithdrawRequest` call reverts forever.

The leaked resource is therefore never released: stale basis permanently enlarges `totalBasis`, reducing `defaultRecoveryPrice` for every other legitimate claimant, and the reserve portion earmarked for the stale receipt (`staleBasis * recoveryPrice`) can never be claimed because the claiming call always reverts — nor can it be paid via the funded path (`_transferFundedClaim` treats it as untouchable reserve, line 904). `epochNumber` does not save the day: requests, collection and default finalization can all occur within the same epoch number, and `requestInstantWithdraw` has no guard against a second request in the same epoch.

### Impact Explanation
Direct, quantified loss in a borrower-default scenario:

1. Every other defaulted-epoch receipt holder (normal + instant) receives `basis * reserveAmount / totalBasis`. Inflating `totalBasis` by the stale amount `S` reduces each claimant's payout proportionally by `S / totalBasis`.
2. The reserve share `S * recoveryPrice` earmarked for the stale receipt is permanently frozen in `IdleCreditVault` — the owner's `transferToken` rescue would violate the reserve invariant, so the funds are effectively burned.
3. The affected user also loses their *legitimate* newer instant receipt: since `_claimDefaultedInstantWithdrawRequest` runs before the funded path (line 385) and reverts, the entire claim entrypoint is bricked — permanent freezing of their unclaimed recovery yield.

### Likelihood Explanation
Requires a borrower default in the same epoch where at least one instant withdrawal was funded and claimed at par, plus at least one still-unfunded instant request (so `pendingInstantWithdraws != 0` at finalization). Defaults are an expected lifecycle event the code explicitly handles (`_handleBorrowerDefault`, `finalizeDefaultRecovery`, `defaultPendingClaimBasis`), and instant withdrawals are processed lazily with a delay (`instantDelay`), so a partially-funded instant queue overlapping a default is a realistic sequence. No privileged misbehavior is needed — any tranche holder can create the stale basis simply by claiming a funded instant withdrawal, which is normal user behavior, not an attack setup.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch entries alongside the aggregate:

```solidity
uint256 currentEpoch = epochNumber; // or track request epoch per user
instantWithdrawsRequestsByEpoch[_user][reqEpoch] = 0; // or subtract claimed amount
instantWithdrawClaimsByEpoch[reqEpoch] -= amount;     // only the funded portion
```

Because instant receipts requested in different epochs share the aggregate `instantWithdrawsRequests`, the clean fix is to record each request's epoch (e.g., a `lastInstantWithdrawRequest` mapping or per-epoch FIFO) and decrement `instantWithdrawClaimsByEpoch` by exactly the amount paid, so `defaultPendingClaimBasis` only ever counts still-unpaid receipts.

### Proof of Concept
Foundry fork sketch (setup mirrors `test/foundry/IdleCreditVault.t.sol`):

```solidity
// epoch N running; instantDelay elapsed path assumed
// 1) user1 deposits via queue, requests instant withdraw of X
cdoEpoch.requestInstantWithdraw(x, address(AAtranche));
uint256 epoch = strategy.epochNumber();

// 2) borrower/manager funds instant claims; CDO collects
vm.prank(manager); cdoEpoch.getInstantWithdrawFunds(); // collectInstantWithdrawFunds(x)

// 3) user1 claims at par -- BUG: per-epoch basis NOT cleared
cdoEpoch.claimInstantWithdrawRequest();
assertEq(strategy.instantWithdrawsRequests(user1), 0);
assertEq(strategy.instantWithdrawsRequestsByEpoch(user1, epoch), x); // leaked

// 4) attacker (or same user1) requests a second instant withdraw of Y,
//    left unfunded so pendingInstantWithdraws != 0
cdoEpoch.requestInstantWithdraw(y, address(AAtranche));

// 5) borrower defaults in the same epoch; owner finalizes recovery
vm.prank(manager); cdoEpoch.emergencyShutdown();        // _handleBorrowerDefault path
strategy.finalizeDefaultRecovery(recovered, recoverySource);

// basis double-counts x: recoveryPrice is diluted
assertEq(strategy.defaultInstantWithdrawsFinalized(), true);

// 6) user1's claim now reverts forever on underflow at
//    instantWithdrawsRequests[user1] -= claimBasis  (y < x + y)
vm.expectRevert(); // arithmetic underflow
cdoEpoch.claimInstantWithdrawRequest();

// 7) reserve slice == x * defaultRecoveryPrice is locked in the strategy permanently
assertGt(strategy.defaultRecoveryReserve(), claimableByOthers);
```

Note: I could not fully trace `IdleCDOEpochVariant`'s exact default/claim wiring (e.g., whether `epochNumber` is bumped between funding and finalization in the default path); if `epochNumber` is guaranteed to change, the stale basis is keyed to a different epoch and the impact collapses — this should be confirmed in a live PoC against `IdleCDOEpochVariant._handleBorrowerDefault`/`stopEpoch`.
