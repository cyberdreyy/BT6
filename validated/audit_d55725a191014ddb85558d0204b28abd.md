### Title
Blocklist/seize-exempt policy updates can be front-run to strip funds before enforcement takes effect - (File: `crates/common/precompiles/src/policy/logic/v1.rs` / `v2.rs`, `crates/common/precompiles/src/common/ops/guards.rs`)

### Summary
Base's native `PolicyRegistry` precompile lets a policy admin add addresses to a `BLOCKLIST` policy via `updateBlocklist`, which B-20 tokens wire to `TransferSender`/`SeizeExempt` policy scopes to deny transfers or make an account seizable. Because `updateBlocklist` is a normal, mempool-visible transaction with no commit/reveal or atomic bundling with the intended enforcement action (freeze/seize), the targeted address can observe the pending admin transaction and front-run it by moving its balance to a fresh, unlisted address before the block containing `updateBlocklist` lands — exactly the front-runnable-denylist pattern described in the reference report for `setConvictionless()`.

### Finding Description
`IPolicyRegistry::updateBlocklist(policyId, blocked, accounts)` is dispatched through `PolicyRegistryLogic::update_blocklist`, which calls `update_membership` to flip the membership bit for the listed accounts and emits `BlocklistUpdated`: [1](#0-0) 

B-20 tokens consult this registry synchronously on every transfer/mint/seize path via `B20Guards::ensure_policy`, which reads the *current* policy membership at call time — there is no historical or delayed-effect check: [2](#0-1) 

The system/integration tests confirm the intended admin workflow is exactly two sequential transactions: (1) admin calls `updateBlocklist` to add the target account, (2) only afterwards do sender-side checks (`transfer`) or privileged seize/burn ops (`seizeWithMemo`, `burnBlocked`) start rejecting/acting on that account: [3](#0-2) 

Because the L2 mempool and block-building pipeline processes transactions in an order the block builder chooses (and is publicly observable pre-inclusion the same way a mempool transaction is), a target address that anticipates or observes the admin's `updateBlocklist` transaction can submit its own `transfer` in the same or an earlier block/position to move funds to a new, unlisted address before the blocklist update is applied. Once moved, `is_authorized` for the new address returns `true` (empty/absent membership) via the same fast-path/membership read used in `is_authorized`: [4](#0-3) 

This mirrors the FairSide `setConvictionless` bug class 1:1: a privileged denylist-style action (`updateBlocklist`) targets a specific address, but the address itself can escape the effect by transferring value away before the transaction that adds it to the denylist is finalized, because there is no atomicity or commit/reveal binding the target address to the enforcement action.

### Impact Explanation
Any B-20 token issuer relying on `updateBlocklist` (wired to `TransferSender`, `MintReceiver`, or `SeizeExempt` policy scopes) as a sanctions/compliance or asset-recovery control can be defeated by the very account it targets. This directly undermines the enforcement guarantee the seize/burn-blocked privileged operations depend on: `seizeWithMemo` and `burnBlocked` require the target to already be authorized-as-blocked/seizable by policy (`ensure_blocked`/`ensure_seizable`), so if the target moves funds out before the blocklist update lands, the subsequent seize/burn-blocked transaction against the original address recovers nothing and the malicious actor retains full custody and continues operating under a fresh, unlisted address. For a stablecoin/security-token deployment where blocklisting is the sole mechanism to halt an account before an issuer executes a seize, this is a Medium-severity bypass of an intended fund-freezing/seizure control — the funds the issuer intended to freeze or seize are never actually frozen or recoverable.

### Likelihood Explanation
Likelihood is high whenever a token issuer treats `updateBlocklist` (or the equivalent allowlist-removal) as a targeted enforcement action against a specific known/suspected bad actor rather than a purely static configuration (e.g., burn address). Any target with mempool/pending-block visibility and enough balance to pay gas can trivially execute the front-run with a standard `transfer` call; no privileged access or unusual capability is required, matching the "unprivileged transaction sender" reachability the task requires.

### Recommendation
Do not treat `updateBlocklist`/policy membership changes as sufficient enforcement by themselves. For freeze/seize workflows, either: (1) provide an atomic "block-and-seize" precompile entry point that adds the account to the blocklist and immediately seizes/burns its balance within the same transaction so no front-run window exists, or (2) support a commit/reveal or time-delayed activation scheme so the address being blocklisted cannot be identified from calldata before the block finalizes. At minimum, document clearly that `updateBlocklist` alone provides no atomic freeze guarantee and must be combined with an in-same-transaction seize call by issuers who need front-run-resistant enforcement.

### Proof of Concept
1. Admin holds `Seize`/`BurnBlocked` role and policy admin rights over a `BLOCKLIST` policy wired to `SeizeExempt`/`TransferSender` for token `T`.
2. Admin submits `updateBlocklist(policyId, true, [Alice])` intending to freeze/seize Alice's balance in a follow-up transaction.
3. Alice observes the pending transaction (or anticipates the action) and submits `transfer(newAddr, balance)` which lands in the same or an earlier block position.
4. `updateBlocklist` executes, adding the original Alice address to the blocklist — but her balance is now `0`.
5. Admin's subsequent `seizeWithMemo(Alice, treasury, amount, memo)` or `burnBlocked(Alice, amount)` either reverts (insufficient balance) or seizes nothing of value, matching the observed test flow order in [5](#0-4) , while Alice continues operating freely from `newAddr`, which starts with default `ALWAYS_ALLOW`/unlisted membership per [4](#0-3) .

        &self,
        storage: &mut S,
        policy_id: u64,
        blocked: bool,
        accounts: Vec<Address>,
    ) -> Result<()> {
        let caller =
            self.update_membership(storage, policy_id, Self::BLOCKLIST_TYPE, blocked, &accounts)?;
        storage.emit_event(
            IPolicyRegistry::BlocklistUpdated {
                policyId: policy_id,
                updater: caller,
                blocked,
                accounts,
            }
            .encode_log_data(),
        )
    }

    fn is_authorized(&self, storage: &S, policy_id: u64, account: Address) -> Result<bool> {
        // Malformed IDs (type byte > 1) are treated as unauthorized rather than reverting.
        if Self::policy_id_type(policy_id) > PolicyType::ALLOWLIST as u8 {
            return Ok(false);
        }
        // Fast-paths for built-in IDs: ALWAYS_ALLOW_ID = 0 is the EVM default for any
        // uninitialized policy field, so this must work before initialization has run.
        if policy_id == Self::ALWAYS_ALLOW_ID {
            return Ok(true);
        }
        if policy_id == Self::ALWAYS_BLOCK_ID {
            return Ok(false);
        }
        // Read membership directly without requiring the policy slot to be written first.
        // An unwritten slot returns false, which naturally gives:
        //   ALLOWLIST  => false  (no members => not authorized)
        //   BLOCKLIST  => !false (no members blocked => authorized)
        let member = storage.read_member(policy_id, account)?;
        match Self::policy_id_type(policy_id) {
            Self::ALLOWLIST_TYPE => Ok(member),
            Self::BLOCKLIST_TYPE => Ok(!member),
            _ => unreachable!("type byte > 1 was rejected by the malformed-ID guard above"),
        }

    pub fn ensure_policy<T: Token + ?Sized>(
        token: &T,
        policy_scope: B256,
        account: Address,
    ) -> Result<()> {
        let policy_id = token.accounting().policy_id(policy_scope)?;
        if token.policy().is_authorized(token.policy_storage(), policy_id, account)? {
            Ok(())
        } else {
            Err(BasePrecompileError::revert(IB20::PolicyForbids {
                policyScope: policy_scope,
                policyId: policy_id,
            }))
        }

#[tokio::test]
async fn b20_blocklist_sender_policy_blocks_listed_accounts() {
    let mut scenario = B20PolicyScenario::new().await;

    let seed_bob =
        scenario.token_tx(IB20::transferCall { to: BerylTestEnv::bob(), amount: SEED_AMOUNT });
    let block = scenario.build_block(vec![seed_bob]).await;
    assert!(scenario.env.user_tx_succeeded(&block, 0), "seeding bob must succeed");
    scenario.assert_balance(BerylTestEnv::alice(), BerylTestEnv::B20_INITIAL_SUPPLY - 100_000);
    scenario.assert_balance(BerylTestEnv::bob(), 100_000);

    let blocklist_id = BerylTestEnv::policy_id(IPolicyRegistry::PolicyType::BLOCKLIST, 2);
    let create_policy = scenario.policy_tx(IPolicyRegistry::createPolicyCall {
        admin: BerylTestEnv::alice(),
        policyType: IPolicyRegistry::PolicyType::BLOCKLIST,
    });
    let block = scenario.build_block(vec![create_policy]).await;
    assert!(scenario.env.user_tx_succeeded(&block, 0), "createPolicy(BLOCKLIST) must succeed");

    let wire = scenario.token_tx(IB20::updatePolicyCall {
        policyScope: B20PolicyType::TransferSender.id(),
        newPolicyId: blocklist_id,
    });
    let block = scenario.build_block(vec![wire]).await;
    assert!(scenario.env.user_tx_succeeded(&block, 0), "updatePolicy must succeed");

    let first_transfer = scenario
        .bob_token_tx(IB20::transferCall { to: BerylTestEnv::carol(), amount: TRANSFER_AMOUNT });
    let block = scenario.build_block(vec![first_transfer]).await;
    assert!(
        scenario.env.user_tx_succeeded(&block, 0),
        "transfer from non-blocked account must succeed"
    );
    scenario.assert_balance(BerylTestEnv::bob(), 99_999);
    scenario.assert_balance(BerylTestEnv::carol(), 1);

    let block_bob = scenario.policy_tx(IPolicyRegistry::updateBlocklistCall {
        policyId: blocklist_id,
        blocked: true,
        accounts: vec![BerylTestEnv::bob()],
    });
    let block = scenario.build_block(vec![block_bob]).await;
    assert!(scenario.env.user_tx_succeeded(&block, 0), "updateBlocklist must succeed");

    let blocked = scenario
        .bob_token_tx(IB20::transferCall { to: BerylTestEnv::carol(), amount: TRANSFER_AMOUNT });
    let block = scenario.build_block(vec![blocked]).await;
    assert!(
        !scenario.env.user_tx_succeeded(&block, 0),
        "transfer from blocked account must revert"
    );
    scenario.assert_balance(BerylTestEnv::bob(), 99_999);
    scenario.assert_balance(BerylTestEnv::carol(), 1);
