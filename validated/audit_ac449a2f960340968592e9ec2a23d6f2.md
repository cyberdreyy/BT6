### Title
Stale-timestamp bypass of the cross-tenure conflict guard in `handle_block_pre_commit` allows signing a genuinely canonical sibling block - ([File: stacks-signer/src/v0/signer.rs])

### Summary
In `handle_block_pre_commit`, the guard that prevents double-signing a sibling block at the same height silently drops any conflict whose `last_endorsed` timestamp has crossed `freshness_cutoff`, without ever asking the node (`conflict_still_blocks`/`get_tenure_tip`) whether that conflicting block is still live, *unless* the conflict happens to share the proposed block's own `consensus_hash`. A conflicting sibling in a third, unrelated tenure that is still fully canonical on the node is therefore cleared purely by clock elapse, letting the signer sign a second, conflicting block (equivocation) at the same height.

### Finding Description
The equality that should hold is: *"a conflict may only stop blocking once it is proven stale-and-dead by both a local timestamp check and a node-derived liveness check (`conflict_still_blocks`), OR by an explicit same-tenure `get_tenure_tip` re-check."* The code breaks this for cross-tenure siblings.

`handle_block_pre_commit` computes:
```
freshness_cutoff = get_epoch_time_secs().saturating_sub(tenure_last_block_proposal_timeout)
```
and the primary guard is:
```rust
if let Some(conflict) = conflicts.iter().find(|conflict| {
    conflict.last_endorsed > freshness_cutoff
        && !self.reorg_permit_stands(stacks_client, conflict)
        && self.conflict_still_blocks(stacks_client, conflict, block_info.block.header.chain_length)
}) { ... return; }
``` [1](#0-0) 

Because `&&` short-circuits, as soon as `conflict.last_endorsed <= freshness_cutoff`, `conflict_still_blocks` (the only code that queries the node's `get_tenure_tip`/`get_sortition_by_burn_hash` to determine if the conflict is truly dead) is **never called** for that conflict. The only remaining check afterward is scoped to conflicts sharing the *same* `consensus_hash` as the block being signed:
```rust
if conflicts.iter().any(|conflict| {
    conflict.consensus_hash == block_info.block.header.consensus_hash && ...
}) {
    match stacks_client.get_tenure_tip(&block_info.block.header.consensus_hash) { ... }
}
``` [2](#0-1) 

This only re-derives liveness for a conflict *in the block's own tenure* - it never re-derives liveness for a conflict in a genuinely different ("third") tenure. The earlier chainstate re-check (`check_block_against_signer_db_state` → `check_latest_block_in_tenure`) is documented as covering only the proposed block's own tenure (or, for a tenure-change block, its parent tenure) - never a third, unrelated sibling tenure: [3](#0-2) [4](#0-3) 

So for a sibling A that lives in a tenure unrelated to B's own/parent tenure (e.g., two competing tenure-change blocks both built on the same grandparent tenure after a mining-slot race), once A's `last_endorsed` crosses `freshness_cutoff`, nothing in `handle_block_pre_commit` ever asks the node again whether A is still canonical. The comment block explicitly (and incorrectly, for this case) asserts this is safe: "A stale conflict in another tenure ... no longer speaks for us: whether this block may replace what another tenure built is settled by the chainstate checks above" - but the chainstate checks (as documented two paragraphs earlier in the same file) are blind to exactly this third-tenure case.

Exploit flow:
1. Miner (attacker, one slot) or an honest miner produces block A in tenure T_A, height h, parent tenure P. Enough signer weight pre-commits/signs A (a "bearer instrument" per the code's own doc), but A is not yet posted/confirmed on the node (delayed relay, congestion, or the attacker - now holding the next mining slot - simply withholds posting it).
2. Attacker crafts and proposes competing sibling B in tenure T_B, same height h, same parent tenure P (a legitimate tenure-change race), which passes proposal-time and validate-ok checks because those only look at P (parent) or T_B (own), never at T_A.
3. Attacker (or simply the passage of time) waits until `tenure_last_block_proposal_timeout` elapses since each signer's `last_endorsed` timestamp for A.
4. Attacker submits/replays B's pre-commits across signers to cross the 70% threshold at/after that instant. Each signer's `handle_block_pre_commit` finds A's `last_endorsed <= freshness_cutoff`, skips `conflict_still_blocks` entirely, finds no same-tenure conflict, logs "none of those conflicts still blocks it," and signs B - even if A subsequently becomes (or already is) the canonical tip.

### Impact Explanation
This breaks UNIQUENESS/safety: a signer can be made to sign a block B that conflicts with A at the same height, while A is confirmably canonical, purely because a wall-clock timeout elapsed with no re-verification of A's actual chain status. If this reasoning replicates across enough signers (which it will, since they all use the same local `tenure_last_block_proposal_timeout` and comparable `last_endorsed` timestamps), both A and B can independently accumulate 70% signatures, producing a true equivocation - two validly signed, conflicting blocks at the same height. This matches the Critical category: "a signer signing an invalid, non-canonical, or conflicting block (chain safety)." It is repeatable any time a sibling relationship spans tenures outside the single-tenure scope that `check_block_against_signer_db_state` re-checks, and needs no majority-signer compromise - only ordinary miner-slot possession plus gossip of B's proposal/pre-commits, and the natural or attacker-assisted delay of A's block delivery to the node.

### Likelihood Explanation
Preconditions: (a) two sibling blocks at the same height in different, non-parent-related tenures (a realistic outcome of a mining-slot/tenure-change race); (b) A signed/pre-committed by enough weight but not yet posted/confirmed on the node within `tenure_last_block_proposal_timeout`; (c) attacker holds one mining slot to produce B and gossips its proposal and (as an "outdated peer" fallback or by re-broadcasting real signer pre-commits) drives the pre-commit tally past 70%. Nothing here requires majority signer weight, the auth token, or local host access - only a single miner slot plus ordinary StackerDB gossip that any signer already accepts. The timing window is bounded by `tenure_last_block_proposal_timeout` (a known, configured constant), making the race schedulable rather than probabilistic. It is repeatable at every tenure-change race where the previous block's confirmation is delayed past the timeout.

### Recommendation
Do not let a purely local timestamp comparison clear a cross-tenure conflict. Either (a) always call `conflict_still_blocks` for every non-permitted conflict regardless of `last_endorsed`, gating only the round-trip cost (not correctness) on freshness, or (b) when a conflict goes stale, still perform an explicit `get_tenure_tip` liveness re-check against *the conflict's own tenure* (not just the proposed block's own tenure) before allowing the sign, mirroring what `conflict_still_blocks`'s "question 2" already does for fresh conflicts.

### Proof of Concept
Rust test plan (in `stacks-signer/src/v0/tests.rs`, extending the `run_cross_tenure_scenario`/`run_sibling_scenario` harness):
1. Set up two tenures T_A and T_B sharing parent tenure P, both proposing a block at height h.
2. Have the signer under test pre-commit/sign A; record `last_endorsed`.
3. Configure the mock `StacksClient` so that `get_tenure_tip(T_A)` returns a tip at height ≥ h (A is genuinely canonical/live) for the entire test - i.e., assert `conflict_still_blocks` would return `true` if invoked.
4. Advance the test clock by `tenure_last_block_proposal_timeout` so `last_endorsed <= freshness_cutoff`.
5. Deliver B's proposal, drive its pre-commits to the 70% threshold, and call `handle_block_pre_commit` for B.
6. Assertion "before" (documents intended safety): assert `conflict_still_blocks(stacks_client, &conflict_a, h)` is `true` (node says A is still reachable/live) - i.e., the node-derived liveness fact says A should still block.
7. Assertion "after" (demonstrates the break): assert that `handle_block_pre_commit` nonetheless signs B (`info_b.state == BlockState::LocallyAccepted` and `info_b.signed_self.is_some()`), proving the guard let B through despite A being node-confirmed canonical, because `conflict_still_blocks` was never invoked once `last_endorsed` fell below `freshness_cutoff`.

Unresolved/uncertain: I could not directly inspect the `last_endorsed` field's write sites in `stacks-signer/src/signerdb.rs` (grep found matches but content wasn't retrieved) to confirm exactly which events refresh it (only initial sign/pre-commit vs. every re-observation); this affects how tight the exploit timing window is, but does not change the core finding that the freshness check bypasses `conflict_still_blocks` on staleness alone for cross-tenure conflicts.

```markdown
Order matters here: the chainstate re-check runs first and produces an explicit
(sticky) rejection when the block now conflicts with a signed one. The conflict
guard behind it is the silent backstop for what that re-check cannot see, and
silence keeps the door open to sign later once the conflict goes stale. Two
blind spots make the guard necessary:

- the re-check only ever looks at _one_ tenure (a tenure-change block's parent,
  or any other block's own), so a signed sibling at the same height in a third
  tenure is invisible to it;
- the `DuplicateBlockFound` check that would catch a second block in the same
  tenure lives in `check_proposal` and runs only at proposal arrival, never
  again. A block that crosses the pre-commit threshold minutes later has no
  other guard, which is what the own-tenure branch above covers.
