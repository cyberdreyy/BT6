### Title
Zero-signature ed25519 precompile instruction bypasses signature verification and returns `Ok(())` - ([File: precompiles/src/ed25519.rs])

### Summary
The `verify` function in `precompiles/src/ed25519.rs` only rejects `num_signatures == 0` when `data.len() > SIGNATURE_OFFSETS_START`, so an instruction with `num_signatures == 0` and `data.len() == SIGNATURE_OFFSETS_START` (2 bytes) passes verification trivially with zero signatures checked. This differs from the sibling `secp256r1.rs` precompile, which unconditionally rejects `num_signatures == 0` [1](#0-0) , confirming the ed25519 check is inconsistent/incomplete.

### Finding Description
`verify` first checks `data.len() < SIGNATURE_OFFSETS_START` and errors if so [2](#0-1) . It then reads `num_signatures = data[0]` and only errors on zero signatures when there are trailing bytes past the offsets-start marker [3](#0-2) . For `data = [0u8, 0u8]` (length exactly `SIGNATURE_OFFSETS_START == 2`), this branch is false, so no error is raised. The subsequent `expected_data_size` computation with `num_signatures = 0` reduces to `SIGNATURE_OFFSETS_START`, which equals `data.len()`, so the size check at line 27 also passes [4](#0-3) . The `for i in 0..num_signatures` loop then never executes since `num_signatures == 0` [5](#0-4) , and the function returns `Ok(())` at line 78 without verifying any signature.

This `verify` function is invoked via `verify_if_precompile` in `precompiles/src/lib.rs`, which is the entry point called during transaction sanitization/precompile verification for any instruction addressed to the ed25519 program id [6](#0-5) . An unprivileged attacker fully controls the instruction data of their own transaction, so they can construct a 2-byte ed25519 instruction `[0, 0]` that will pass `verify_if_precompile` with `Ok(())`.

### Impact Explanation
This falls under the precompile-trust bypass category: any on-chain program that follows the documented pattern of checking "was the ed25519/secp256r1 program invoked in this transaction" (via the Instructions sysvar) without separately validating `num_signatures > 0` in the observed instruction data can be tricked into believing a signature was verified when zero signatures were actually checked. Depending on the victim program's logic (e.g., using this as an authorization gate for withdrawing funds, minting, or session authentication), this could lead to authorization/funds theft without any actual valid signature — a complete bypass of the intended "no action without a verified signature" invariant.

### Likelihood Explanation
Exploitation requires no privileged access: the attacker only needs to submit a transaction containing a 2-byte `ed25519_program` instruction (`[0, 0]`) alongside a call to a victim program that follows the vulnerable "presence-only" pattern (checks precompile invocation but not `num_signatures`). This is fully reproducible by any unprivileged transaction sender. The severity is entirely contingent on whether any deployed victim program actually implements this flawed "presence-only" check pattern — the core `agave` bug is real and directly demonstrable, but the scoped "theft of funds" impact depends on a victim program with this specific flaw, which the audit question stipulates as the precondition.

### Recommendation
Change the check in `precompiles/src/ed25519.rs` to unconditionally reject `num_signatures == 0`, matching the pattern already used in `secp256r1.rs`:
```rust
if num_signatures == 0 {
    return Err(PrecompileError::InvalidInstructionDataSize);
}
```
removing the `&& data.len() > SIGNATURE_OFFSETS_START` condition entirely.
