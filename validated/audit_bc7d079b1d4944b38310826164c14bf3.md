### Title
Malicious authorized voter can front-run withdrawer's replacement to lock the target epoch's voter slot to a colluding key - (File: `programs/vote/src/vote_state/handler.rs`)

### Summary
The vote program's `Authorize`/`AuthorizeChecked` instruction lets the *current authorized voter* (not only the authorized withdrawer) submit a self-service voter rotation for the next `leader_schedule_epoch`. Because the target-epoch slot check (`v4.authorized_voters.contains(target_epoch)`) is unconditional and independent of *who* signed, a malicious current voter can pre-emptively claim that slot for a colluding pubkey before the legitimate authorized withdrawer's replacement transaction lands, causing the withdrawer's transaction to fail with `TooSoonToReauthorize`. This mirrors the reported Allo.sol bug class: an actor who already holds a role (pool manager / vote authority) can front-run the admin's attempt to remove them by re-asserting control of the same slot first.

Notice `authorized_withdrawer_signer` short-circuits the `verify` closure to `Ok(())` when the withdrawer signs, but the *current-epoch voter* is also independently allowed to authorize a new voter when the withdrawer doesn't sign — this is intended so a validator's hot key can rotate itself without withdrawer involvement each epoch.

The actual state mutation happens in `set_new_authorized_voter` in `programs/vote/src/vote_state/handler.rs`: [2](#0-1) 

Crucially, the `verify` callback (which distinguishes withdrawer-signed vs. voter-signed calls) is invoked *before* the `target_epoch` occupancy check, and the occupancy check itself (`v4.authorized_voters.contains(target_epoch)`) is unconditional — it does not care whether the withdrawer or the voter is the one calling. `target_epoch` is deterministically derivable by any observer from the `Clock` sysvar (`clock.leader_schedule_epoch + 1`), because both the withdrawer's replacement transaction and the malicious voter's self-authorization transaction target the exact same future epoch.

Therefore, a compromised/malicious current voter, upon detecting (in the mempool/gossip) that the withdrawer is submitting a transaction to replace them, can submit their own `Authorize(Voter, colluding_pubkey)` transaction targeting the same `target_epoch`. If it lands first, `v4.authorized_voters.insert(target_epoch, ..)` occupies the slot, and the withdrawer's subsequent (even signed, even valid) replacement transaction for that same epoch fails with `VoteError::TooSoonToReauthorize`, exactly as in the malicious `addPoolManager` front-run in the Allo.sol report.

### Impact Explanation
This allows a malicious/compromised authorized voter to indefinitely delay or defeat a withdrawer's legitimate attempt to revoke their voting authority for the vote account, by repeatedly re-claiming/handing off the upcoming epoch's voter slot to a colluding key one step ahead of the withdrawer. Because the authorized voter of a vote account can sign votes that affect that validator's stake-weighted participation in consensus (fork choice, vote credits/rewards accrual), retaining unauthorized control past the point the legitimate owner intended to revoke it can affect vote-credit/reward accounting for the account and prolong a compromised key's ability to vote, which is a security-relevant griefing/control-retention primitive directly analogous to the reported bug class (role holder blocking their own removal via front-running).

### Likelihood Explanation
Both parties' target instructions are fully deterministic and computable from public on-chain state (`Clock::leader_schedule_epoch`), and a malicious current voter has every incentive to watch for/anticipate a withdrawer's removal attempt and beat it to the mempool. No special privilege beyond already holding the (soon to be revoked) voter authority is required — a single signed transaction, submitted before the withdrawer's, is sufficient. This is straightforward to execute by any party who is currently the authorized voter.

### Recommendation
When the authorized withdrawer signs an `Authorize`/`AuthorizeChecked` (Voter) instruction, the `target_epoch` occupancy check should not simply reject with `TooSoonToReauthorize`; instead, withdrawer-signed authorizations should be allowed to overwrite/override an already-set future-epoch entry (since the withdrawer is the ultimate authority), or the program should track and prefer the most-recently-withdrawer-signed intent regardless of a prior voter-signed claim on that slot. Alternatively, disallow the "voter can self-authorize without withdrawer" path entirely and require the withdrawer to explicitly co-sign or pre-approve voter rotations, closing off the same-role front-running vector analogous to removing self-administered role escalation in the Allo.sol pattern.

### Proof of Concept
1. Vote account has withdrawer `W` and current authorized voter `V` (for `current_epoch`).
2. `V` is compromised/malicious. `W` detects this and submits `Authorize(Voter, honest_new_voter)` targeting `target_epoch = leader_schedule_epoch + 1` (withdrawer-signed, so the `verify` closure trivially passes per `programs/vote/src/vote_state/mod.rs:706-725`).
3. Before `W`'s transaction lands, `V` (still the current authorized voter) submits their own `Authorize(Voter, colluder_pubkey)` transaction for the same `target_epoch` (voter-signed path, also passes `verify` since `V` is still the current-epoch voter per `get_and_update_authorized_voter`).
4. If `V`'s transaction is processed first, `set_new_authorized_voter` (`programs/vote/src/vote_state/handler.rs:98-103`) inserts `colluder_pubkey` at `target_epoch`.
5. `W`'s transaction, when processed afterward, hits `v4.authorized_voters.contains(target_epoch)` → `true`, and fails with `InstructionError` wrapping `VoteError::TooSoonToReauthorize` (`programs/vote/src/vote_state/handler.rs:98-100`), leaving `colluder_pubkey` (controlled by `V`) as the authorized voter for the upcoming epoch despite `W`'s attempt to remove `V`'s influence.

    pub(crate) fn set_new_authorized_voter<F>(
        &mut self,
        authorized_pubkey: &Pubkey,
        current_epoch: Epoch,
        target_epoch: Epoch,
        bls_pubkey: Option<&[u8; BLS_PUBLIC_KEY_COMPRESSED_SIZE]>,
        verify: F,
    ) -> Result<(), InstructionError>
    where
        F: Fn(Pubkey) -> Result<(), InstructionError>,
    {
        let epoch_authorized_voter = self.get_and_update_authorized_voter(current_epoch)?;
        verify(epoch_authorized_voter)?;

        match &mut self.target_state {
            TargetVoteState::V4(v4) => {
                // The offset in slots `n` on which the target_epoch
                // (default value `DEFAULT_LEADER_SCHEDULE_SLOT_OFFSET`) is
                // calculated is the number of slots available from the
                // first slot `S` of an epoch in which to set a new voter for
                // the epoch at `S` + `n`
                if v4.authorized_voters.contains(target_epoch) {
                    return Err(VoteError::TooSoonToReauthorize.into());
                }

                v4.authorized_voters
                    .insert(target_epoch, *authorized_pubkey);

                if bls_pubkey.is_some() {
                    v4.bls_pubkey_compressed = bls_pubkey.copied();
                }

                Ok(())
            }
        }
    }
