### Title
Symlink target (Linkname) is embedded verbatim in cache/artifact tar archives without validation, leaking host path information - (File: commands/helpers/archive/tarzstd/tarzstd_archiver.go)

### Summary
`archiver.Archive` validates that the *symlink file itself* resides inside `a.dir` via `filepath.Abs`/`strings.HasPrefix`, but it never validates or sanitizes the symlink's *target* obtained via `os.Readlink`. An attacker who creates a symlink in their own job workspace pointing to an arbitrary absolute path (e.g. `/etc/passwd` or a sibling job/build directory) can have that absolute path embedded verbatim as `hdr.Linkname` in the produced tar archive.

### Finding Description
In `commands/helpers/archive/tarzstd/tarzstd_archiver.go`, the chroot check only applies to the symlink's own path: [1](#0-0) 

The symlink target itself is read with `os.Readlink(path)` and passed straight into `tar.FileInfoHeader(fi, link)`, becoming `hdr.Linkname`, with no path validation, no `filepath.Abs`/prefix check, and no rejection of absolute or `..`-escaping targets: [2](#0-1) 

Since a normal, unprivileged job can create arbitrary symlinks within its own workspace (`ln -s /etc/passwd link`, or `ln -s /builds/other-project/... link`) before a `cache: paths:` or `artifacts: paths:` entry causes that symlink to be archived, the resulting Linkname faithfully records that absolute host path inside the archive. This archive is then persisted in the cache/artifact store and downloaded/extracted by other jobs (including other projects sharing the runner/cache, or the same project's later pipelines). The archive itself — independent of extraction behavior — already discloses the literal host path that the symlink pointed to (e.g., `/etc/passwd`, `/builds/<other-namespace>/<other-project>`, `/home/<user>/...`), which is information about the host filesystem layout that should not be embedded per the stated invariant ("archived content ... must not encode information about paths outside a.dir").

Note: on the *extraction* side, `tarzstd_extractor.go` does perform a chroot check on the symlink's `path` (destination) via `filepath.Abs`/`HasPrefix` (lines 57-64), but it writes `os.Symlink(hdr.Linkname, path)` unconditionally without validating `Linkname` (lines 113-117). This means a dangling symlink pointing at an absolute host path is faithfully recreated in the *extracting* job's workspace. Whether this constitutes a full readable disclosure depends on the extracting job's own filesystem/container access to that absolute path, but the archive itself already discloses the *path string* (host layout information) to any consumer, satisfying the scoped impact of "leaking host filesystem layout."

### Impact Explanation
Any job that includes a symlink pointing outside its build directory in a `cache:` or `artifacts: paths:` entry causes that absolute target path to be stored verbatim in the tar/zip archive's link field. Anyone with access to download that cache/artifact (including, depending on GitLab cache/artifact scoping configuration, other jobs/branches/projects sharing a cache key or fork-based artifact access) can read the embedded absolute path, disclosing host directory structure (usernames, other project paths, build IDs, etc.), and — if extracted on a host/container with the same absolute path accessible — potentially the dangling symlink resolves to real content there.

### Likelihood Explanation
Preconditions are trivial and fully attacker-controlled: any pipeline author can create a symlink in their own job workspace before `cache-push`/`artifacts` upload (e.g. `ln -s /etc/passwd leak; ` then declare `paths: [leak]`). No special executor privileges are required — only ordinary shell access inside the job. The bug is deterministic and 100% reproducible.

### Recommendation
When encountering a symlink during `Archive`, resolve/validate the link target the same way the direct file path is validated: reject (or rewrite) `Linkname` values that are absolute or that resolve outside `a.dir` (e.g., compute `filepath.Join(filepath.Dir(path), link)` if relative, or reject if `filepath.IsAbs(link)`, and always verify the resolved target still lies under `a.dir` with the same `strings.HasPrefix` check used for `path`). Apply the analogous validation on extraction to `hdr.Linkname` before calling `os.Symlink`.

### Proof of Concept
Go unit test in `tarzstd` package:
1. Create temp dir `a.dir`; inside it create `os.Symlink("/etc/passwd", filepath.Join(dir, "leak"))`.
2. Call `archiver.Archive` with `files` map containing the symlink's `os.Lstat` info.
3. Decompress/read back the tar stream and assert that the tar header for `leak` either has `Linkname` rejected (archiving fails) or does **not** equal `/etc/passwd` verbatim — expected: `err != nil` from `Archive`, or `hdr.Linkname` sanitized to a relative-safe value.
4. Currently: assert (to prove the bug) that `hdr.Linkname == "/etc/passwd"` succeeds with no error, demonstrating the absolute host path is stored unvalidated.
