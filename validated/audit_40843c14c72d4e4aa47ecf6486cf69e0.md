### Title
Stale `total_weight_rejected` after a signer's reject→accept flip lets the coordinator misreport a legitimately-approved block as rejected - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` maintains two independent running counters per block, `BlockStatus.total_weight_approved` and `BlockStatus.total_weight_rejected` [1](#0-0) , which are incremented (never decremented) as `BlockResponse` messages arrive. The `Rejected` handler is careful not to double-count a signer that has already been recorded in `responded_signers` (covers accept-then-reject), but the `Accepted` handler only guards against a signer that already appears in `gathered_signatures` — it never checks or clears `total_weight_rejected` for a signer who previously rejected the same block and now accepts it. This is structurally the same class of bug as the reported ERC20 `mint`/`burn` issue: a derived aggregate (`total_weight_rejected`/`totalSupply`) is not kept in sync with the underlying per-account state after it changes, so calculations built on that aggregate become wrong.

### Finding Description
In the `Rejected` branch, weight is added to `total_weight_rejected` only the first time a given `slot_id` is inserted into `responded_signers`: [2](#0-1) 

In the `Accepted` branch, weight is added to `total_weight_approved` guarded only by `gathered_signatures.contains_key(&slot_id)`, and `responded_signers` is inserted unconditionally afterward, with no check of, or subtraction from, `total_weight_rejected`: [3](#0-2) 

Consequence: if signer S first sends `Rejected` for a block (adds `S.weight` to `total_weight_rejected` and marks S in `responded_signers`), and later legitimately sends `Accepted` for the *same* `signer_signature_hash` (a supported, expected flow — the codebase even has a dedicated test, `signer_can_accept_rejected_block`, for a signer accepting a block it previously rejected), then:
- `total_weight_approved` gains `S.weight` (the `gathered_signatures` guard passes since S never accepted before).
- `total_weight_rejected` is never reduced by `S.weight`, since the reject-side guard (`responded_signers`) was already tripped by the earlier rejection and the accept path never touches `total_weight_rejected`.

The result is that `S.weight` is counted in *both* aggregates simultaneously, breaking the invariant that `total_weight_approved + total_weight_rejected` should never double-count a signer's weight ("aggregated-weight vs verified-accepts" equality). This is exactly the asymmetry the project's own changelog says it fixed for the opposite ordering ("Do not count both a block acceptance and a block rejection for the same signer/block") [4](#0-3)  — but the fix only covers accept-then-reject, not reject-then-accept.

This stale `total_weight_rejected` value then feeds directly into the coordinator's finalization decision, which checks the rejection condition first: [5](#0-4) 

Because the reject branch is evaluated before the approval branch, a stale/inflated `total_weight_rejected` (carrying weight from a signer who has since switched to accept) can push `total_weight_rejected.saturating_add(weight_threshold) > total_weight` even though the *current*, true state of votes has already reached (or would reach) the 70% approval threshold with unique, validly verified signatures. The coordinator then returns `Err(NakamotoNodeError::SignersRejected)` and the miner discards a block that in fact has legitimate signer approval.

### Impact Explanation
This falls under the "aggregated-weight vs verified-accepts" equality class called out in scope: the aggregated rejection weight tracked by the node no longer matches the verified, current set of signer votes once a signer switches from reject to accept. The practical effect is a liveness wedge on block finalization — a block that has legitimately collected enough valid signatures can be misreported by the node's own coordinator as globally rejected, forcing miner-side abandonment/reproposal, purely because of a stale, non-decremented counter rather than any actual conflict among signers. This can recur block after block whenever any single signer's initial rejection (e.g., transient "parent not yet processed" reasons, which the codebase explicitly supports reconsidering) is later replaced by a legitimate acceptance.

### Likelihood Explanation
No majority or malicious coordination is required. Reconsidering a rejection and later accepting the same block proposal is a normal, supported signer behavior in this codebase (illustrated by the `signer_can_accept_rejected_block` test scenario) [6](#0-5) . Any single signer naturally reconsidering its vote on a still-open block proposal is enough to leave the counters permanently out of sync for that block, so this can be triggered incidentally during normal operation, or deliberately by a single signer choosing to reject first and accept afterward.

### Recommendation
Track weight per-signer as a single state (e.g., a map from `slot_id` to `Accepted`/`Rejected`) rather than two independently-incremented totals, or explicitly subtract `signer_entry.weight` from `total_weight_rejected` when a previously-rejecting signer later accepts (mirroring the guard already present for the opposite transition). Recomputing both aggregates fresh from the current per-signer vote map before every threshold check, rather than incrementally accumulating them, would remove this class of bug entirely — consistent with how `stacks-signer/src/v0/signer.rs`'s `compute_signature_signing_weight`/`compute_reject_code_signing_weight` recompute weight from the stored per-signer records each time instead of maintaining a running counter [7](#0-6) .

### Proof of Concept
1. Miner proposes block B (`signer_signature_hash = H`), tracked by `StackerDBListener` as `BlockStatus` with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer S (weight `w_S`) sends `BlockResponse::Rejected(H, ...)` (e.g., because its node hadn't processed B's parent yet). `responded_signers.insert(S)` succeeds → `total_weight_rejected += w_S`.
3. Other signers accumulate `total_weight_approved` close to, but below, `weight_threshold` (e.g., `weight_threshold - w_S ≤ total_weight_approved < weight_threshold`), and `total_weight_rejected + weight_threshold ≤ total_weight` so far (not yet globally rejected).
4. B is reproposed/re-evaluated; S's earlier objection no longer applies and S legitimately signs and sends `BlockResponse::Accepted(H, valid_signature)`.
5. In the `Accepted` handler, `gathered_signatures` does not yet contain S's slot, so `total_weight_approved += w_S`, reaching/crossing `weight_threshold`. `total_weight_rejected` is left untouched at its stale value from step 2.
6. `signer_coordinator.rs`'s wait loop now sees `total_weight_rejected.saturating_add(weight_threshold) > total_weight` (using the stale rejected weight that still includes S) evaluated *before* the approval branch, and returns `NakamotoNodeError::SignersRejected`, even though `total_weight_approved` has independently reached/exceeded `weight_threshold` with S's valid signature included — the miner wrongly abandons a block with sufficient legitimate signer approval.

    /// Compute the signing weight, given a list of signatures
    fn compute_signature_signing_weight<'a>(
        &self,
        addrs: impl Iterator<Item = &'a StacksAddress>,
    ) -> u32 {
        addrs.fold(0u32, |signing_weight, stacker_address| {
            let stacker_weight = self.signer_weights.get(stacker_address).unwrap_or(&0);
            signing_weight.saturating_add(*stacker_weight)
        })
    }
