### Title
Withdrawal amount committed to the EL payload can exceed the validator's balance at the deduction slot, causing `decrease_balance` to saturate and mint Gwei with no backing CL deduction - ([File: specs/gloas/beacon-chain.md])

### Summary
In the Gloas fork, `get_expected_withdrawals` computes a validator's full/partial withdrawal `amount` at *bid-production* time and commits it into `state.payload_expected_withdrawals`, but the corresponding balance deduction is deferred to `apply_withdrawals` in the *next* block via `decrease_balance`, which silently saturates at zero rather than reverting or re-capping the committed amount. If an epoch boundary occurs between commitment and deduction, `process_pending_consolidations` can drain the same validator's balance to a different target validator in the interim. The execution layer still mints the full amount originally committed in the withdrawal, while the consensus layer only removes what remains (possibly nothing), so Gwei is created without a matching CL-side reduction — the same "loss/gain asymmetry from a saturating subtraction" bug class as the Flatcoin `stableCollateralTotal` clamp.

### Finding Description
`decrease_balance` in `specs/phase0/beacon-chain.md` clamps to zero instead of underflowing: [1](#0-0) 

`get_expected_withdrawals` (Gloas) computes the withdrawal `amount` for a fully/partially withdrawable validator from the validator's balance **at the time the block is produced** (bid-computation slot), and this committed list becomes binding as part of the execution payload bid: [2](#0-1) 

The actual balance deduction is deferred to the *next* block via `apply_withdrawals`, which for validators simply calls `decrease_balance(state, withdrawal.validator_index, withdrawal.amount)` with no re-check against the validator's current balance (unlike the builder branch, which explicitly does `min(withdrawal.amount, builder_balance)`): [3](#0-2) 

The spec authors themselves document the consequence explicitly: [4](#0-3) 

Meanwhile, `process_pending_consolidations` (inherited from Electra) can, at any epoch boundary, move a validator's active balance to a different target validator via `decrease_balance`/`increase_balance`, and this runs as ordinary epoch processing between the slot where the withdrawal was committed and the slot where `apply_withdrawals` runs: [5](#0-4) 

`process_pending_consolidations` only excludes a source validator if it is `slashed` or its `withdrawable_epoch > next_epoch`; it does not exclude validators that are simultaneously eligible for a full sweep withdrawal (`is_fully_withdrawable_validator` only requires `withdrawable_epoch <= epoch` and `balance > 0`), so a validator can legitimately satisfy both conditions in the same window.

Putting this together: a validator `V` with `withdrawable_epoch` already reached (i.e., fully withdrawable) and also queued as the `source_index` of a `PendingConsolidation` can have its full balance (say 32 ETH) committed as a withdrawal amount in block `N`'s bid. If block `N` is the last slot of an epoch, `process_pending_consolidations` runs during the `N → N+1` epoch transition and moves `V`'s balance to a target validator `T` (via `decrease_balance`/`increase_balance`), leaving `V.balances == 0`. In block `N+1`, `apply_withdrawals` calls `decrease_balance(state, V, 32 ETH)`, which saturates to a no-op since `V`'s balance is already 0. However, the execution layer still executes the already-committed withdrawal of 32 ETH to `V`'s withdrawal address, since EL payment is driven by the committed `Withdrawal` object, not by the CL balance at execution time. The net result: 32 ETH is credited to `T` via consolidation **and** 32 ETH is paid out on the EL side via the withdrawal — 32 ETH of Gwei materialized without a corresponding single CL-side deduction, breaking the equality that the sum of validator balance decreases must equal the sum of EL-side payments.

### Impact Explanation
This breaks the "Gwei created... paid to a non-owner" invariant described as Critical impact: EL executes a withdrawal payment for an amount that the CL state can no longer back, because the underlying balance was already consumed by a separate, standard protocol event (`process_pending_consolidations`) in the intervening epoch transition. This is a genuine supply-inflation bug, not merely an accounting display issue for off-chain consumers, since the amount minted to the withdrawal address is unconditionally honored by the execution layer regardless of what the saturated `decrease_balance` call does on the CL side.

### Likelihood Explanation
No malicious peer, coalition, or client bug is required — this is triggerable by any validator/staking pool operator through entirely ordinary and spec-compliant sequencing: (1) request a consolidation as source once `withdrawable_epoch` conditions permit, (2) ensure the validator is also swept into a full withdrawal in a block at the last slot of an epoch. Both `is_fully_withdrawable_validator` and the consolidation source eligibility check use the same `withdrawable_epoch` gate, so both paths naturally overlap once a validator reaches `withdrawable_epoch`. The requirement is purely about scheduling/timing at epoch boundaries, not about extreme market conditions, large stake, or coalition control — this makes it substantially more likely to occur than the analogous Flatcoin scenario (which needed a 5x price move).

### Recommendation
Either (a) re-validate/re-cap the committed withdrawal `amount` against the validator's *current* balance at `apply_withdrawals` time and update `payload_expected_withdrawals`/EL commitment consistently (mirroring the `min(amount, balance)` pattern already used for builders), or (b) prevent a validator from being both a pending-consolidation source and eligible for a competing full/partial withdrawal in the same commitment window, e.g., by excluding validators with a pending consolidation entry from `is_fully_withdrawable_validator`/`is_partially_withdrawable_validator`, or by disallowing `process_pending_consolidations` from acting on a source validator whose balance is already committed to an unresolved withdrawal.

### Proof of Concept
1. Validator `V` uses an ETH1/compounding withdrawal credential, reaches `exit_epoch`/`withdrawable_epoch` such that `is_fully_withdrawable_validator(V)` is true, and has balance `B` (e.g. 32 ETH).
2. Separately, submit a `ConsolidationRequest` for `V` (as source) and target `T`, which gets queued into `state.pending_consolidations` with `withdrawable_epoch` compatible with the next epoch boundary (`source_validator.withdrawable_epoch <= next_epoch`), per `process_pending_consolidations`: [6](#0-5) 
3. Produce block `N` (the last block of the current epoch). During bid production, `get_expected_withdrawals` includes a full withdrawal of `V`'s balance `B` in `payload_expected_withdrawals`, bound into the signed execution payload bid: [7](#0-6) 
4. State transition to block `N+1` triggers epoch processing first; `process_pending_consolidations` executes and moves `V`'s balance `B` to `T`, leaving `state.balances[V] == 0`: [8](#0-7) 
5. Block `N+1` is processed; `process_withdrawals` → `apply_withdrawals` runs `decrease_balance(state, V, B)`, which saturates to a no-op since `state.balances[V]` is already `0`: [9](#0-8) 
6. The execution layer, driven by the already-committed `Withdrawal(validator_index=V, amount=B, ...)` from step 3, unconditionally credits `B` to `V`'s withdrawal address.
7. Net effect: `T.balance` increased by `B` (from consolidation) and `V`'s withdrawal address received `B` (from EL), for a total of `2B` credited from an original single balance of `B` — `B` Gwei created without any owner losing it.

```python
def decrease_balance(state: BeaconState, index: ValidatorIndex, delta: Gwei) -> None:
    """
    Decrease the validator balance at index ``index`` by ``delta``, with underflow protection.
    """
    if delta > state.balances[index]:
        state.balances[index] = Gwei(0)
    else:
        state.balances[index] -= delta

def apply_withdrawals(state: BeaconState, withdrawals: Sequence[Withdrawal]) -> None:
    for withdrawal in withdrawals:
        # [Modified in Gloas:EIP7732]

            builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)

            state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
        else:
            decrease_balance(state, withdrawal.validator_index, withdrawal.amount)

##### Modified `process_withdrawals`

*Note*: This is modified to only take the `state` as parameter. Withdrawals are
deterministic given the beacon state, any execution payload that has the
corresponding block as parent beacon block is required to honor these
withdrawals in the execution layer. `process_withdrawals` must be called after
`process_parent_execution_payload` (which updates `state.latest_block_hash`) and
before `process_execution_payload_bid` as the latter function affects validator
balances.

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.

```python
def process_pending_consolidations(state: BeaconState) -> None:
    next_epoch = get_current_epoch(state) + 1
    next_pending_consolidation = 0
    for pending_consolidation in state.pending_consolidations:
        source_validator = state.validators[pending_consolidation.source_index]
        if source_validator.slashed:
            next_pending_consolidation += 1
            continue
        if source_validator.withdrawable_epoch > next_epoch:
            break

        # Calculate the consolidated balance
        source_effective_balance = min(
            state.balances[pending_consolidation.source_index], source_validator.effective_balance
        )

        # Move active balance to target. Excess balance is withdrawable.
        decrease_balance(state, pending_consolidation.source_index, source_effective_balance)
        increase_balance(state, pending_consolidation.target_index, source_effective_balance)
        next_pending_consolidation += 1

    state.pending_consolidations = state.pending_consolidations[next_pending_consolidation:]
