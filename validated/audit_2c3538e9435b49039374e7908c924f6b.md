### Title
Double-counting of a signer's weight in both `total_weight_approved` and `total_weight_rejected` when a Reject is followed by an Accept - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` tallies per-signer weight into two independent running counters, `total_weight_approved` and `total_weight_rejected`, that the mining coordinator uses to decide when a block has reached the 70% approval threshold or the >30% blocking-minority rejection threshold. [1](#0-0)  These two counters are meant to be mutually exclusive per signer (a signer's weight should count toward at most one bucket, reflecting its latest vote), but the code uses two different membership sets to decide whether to add weight, so a signer who rejects and later accepts the same block has its weight added to both buckets — exactly the same class of accounting error as the reported `tokensRepurchased`/`getAmountRepurchasable` bug, where a state-mutating action (repurchase, here: a vote) is not reflected in a subsequently used tally.

### Finding Description
On `Accepted`, weight is added to `total_weight_approved` only if the slot is not already present in `block.gathered_signatures` (a signature map), and `block.responded_signers` is inserted unconditionally afterward: [2](#0-1) 

On `Rejected`, weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` succeeds (i.e., the slot was not already present in `responded_signers`): [3](#0-2) 

Because the `Accepted` branch gates on `gathered_signatures` while the `Rejected` branch gates on the shared `responded_signers` set, the two directions are asymmetric:
- Accept-then-Reject: the accept path inserts the slot into `responded_signers` (line 465). When the later reject arrives, `responded_signers.insert(slot_id)` returns `false`, so `total_weight_rejected` is correctly *not* incremented.
- Reject-then-Accept: the reject path inserts the slot into `responded_signers` (line 515) but never touches `gathered_signatures`. When the later accept arrives, `gathered_signatures.contains_key(&slot_id)` is `false` (it's a distinct map), so the accept path *does* add the signer's weight to `total_weight_approved` — on top of the weight already added to `total_weight_rejected` earlier.

The signature itself is validly checked against the block hash before being counted, so this is not a forgery — it's a bookkeeping equality violation: the same signer's weight is simultaneously present in both the approval and blocking-minority tallies used by `NakamotoSigningCoordinator::wait_for_signatures` to decide the fate of the block. [4](#0-3) 

### Impact Explanation
`total_weight_rejected` is used both to reset rejection timeouts and, more importantly, to decide when the blocking-minority (>30%) threshold is reached, at which point the coordinator gives up on the block and permanently/temporarily excludes transactions. [5](#0-4)  Because a signer that changed its mind (rejected, then legitimately accepted after re-validation) still contributes to `total_weight_rejected`, the tally never "returns" that weight when the vote is superseded. This inflates the rejection bucket and can wedge the coordinator into treating a block as rejected (or artificially delay reaching the 70% approval threshold because both buckets grow independently and inconsistently), producing a liveness/decision wedge on the miner side that does not correspond to the real, current weighted opinion of the signer set — analogous to `getAmountRepurchasable` never deducting `tokensRepurchased` and thus reporting a stale, inflated figure.

### Likelihood Explanation
This requires only a single signer to send a `Rejected` message followed later by an `Accepted` message for the same `signer_signature_hash` — both are ordinary, protocol-legal signer outputs (e.g., a signer rejects on a stale view and then re-validates and accepts after a chain-state re-check, which is exactly the re-check pattern documented for `handle_block_pre_commit`/`store_and_process_block_signature`). [6](#0-5)  No majority collusion, node access, or key compromise is required — it is triggerable by any one signer's normal message stream reaching the coordinator in reject-then-accept order.

### Recommendation
Use a single, unified per-signer vote map keyed by `slot_id` (storing the signer's current decision: Accepted or Rejected) instead of two independent flags/sets. When a new message arrives for a slot that already has a recorded vote of the opposite kind, subtract that signer's weight from the previous bucket before adding it to the new one, so `total_weight_approved` and `total_weight_rejected` always reflect only the latest vote of each signer.

### Proof of Concept
1. Coordinator opens `block` status for `block_sighash` with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer S (weight `w`) sends `BlockResponse::Rejected` for `block_sighash`. `responded_signers.insert(S)` succeeds → `total_weight_rejected += w`.
3. Signer S later sends `BlockResponse::Accepted` for the same `block_sighash` (e.g., after a state re-check flips its decision). `gathered_signatures.contains_key(S)` is `false` (S was never added there) → `total_weight_approved += w`.
4. Now both `total_weight_approved` and `total_weight_rejected` include S's weight `w`, even though S's current, final vote is Accept — violating the intended invariant that each signer's weight counts toward exactly one bucket at a time.
