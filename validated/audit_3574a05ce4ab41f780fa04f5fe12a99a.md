Confirmed: `Message.Validate()` derives `Sender` from `ExtractSigner()` — any valid ECDSA signature over the attacker's own chosen fields (including any `MessageId`) recovers to the attacker's own address, with no binding or uniqueness check tying `MessageId` to a specific sender or to whether that `MessageId` is already in-flight. So any unprivileged gateway client can sign a `web_api_trigger` message with an arbitrary attacker-chosen `MessageId` that collides with a victim's still-pending request.

### Title
Cross-user response hijack via unauthenticated MessageId collision in savedCallbacks map - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.HandleLegacyUserMessage` stores the caller's `Callback` in `h.savedCallbacks` keyed solely by the attacker-controlled `msg.Body.MessageId`, with no check for an existing in-flight entry before overwriting it, and no allowlist/rate-limiting is applied before this point (explicitly flagged by the `TODO: apply allowlist and rate-limiting here` comment). Any unprivileged client can sign and submit a `web_api_trigger` request with the same `MessageId` as a victim's pending request, overwrite the victim's saved callback, and receive the victim's response when the DON replies.

### Finding Description
The gateway's `ProcessRequest` in `core/services/gateway/gateway.go:218-292` decodes an incoming JSON-RPC request, validates the message signature via `msg.Validate()` (`core/services/gateway/api/message.go:54-88`), and dispatches to `h.HandleLegacyUserMessage(ctx, msg, callback)`. Validation only checks that the signature is well-formed and recovers to *some* signer address (`ExtractSigner`); it never verifies that the `MessageId` is unique to that signer or unused.

In `core/services/gateway/handlers/capabilities/handler.go:341-421` (`HandleLegacyUserMessage`), after payload decoding/timestamp checks, the code unconditionally does:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [1](#0-0) 

There is no `if _, found := h.savedCallbacks[msg.Body.MessageId]; found { reject }` guard — unlike the sibling v2 implementation, `httpTriggerHandler.setupCallback`, which explicitly checks for an existing in-flight `requestID` and rejects with `jsonrpc.ErrConflict` before storing: [2](#0-1) 

When the DON responds, `handleWebAPITriggerMessage` looks up and deletes by `MessageId` and delivers the payload to whichever `Callback` is currently stored: [3](#0-2) 

Exploit flow:
1. Victim B submits a `web_api_trigger` request with `MessageId="X"`, signed with B's key; `h.savedCallbacks["X"]` is set to B's `Callback`, and the request is forwarded to all DON members.
2. Before the DON replies, attacker A submits their own `web_api_trigger` request also using `MessageId="X"`, signed with A's own key (self-signed — `Validate()` does not check whether `X` was already used or by whom). This overwrites `h.savedCallbacks["X"]` with A's `Callback`, and duplicate messages are also forwarded to the DON.
3. When a DON node responds to message `X`, `handleWebAPITriggerMessage` looks up `h.savedCallbacks["X"]`, finds A's callback (having overwritten B's), deletes the entry, and calls `savedCb.SendResponse(...)` — delivering B's capability execution result to A.
4. A's `callback.Wait(ctx)` in `gateway.ProcessRequest` (`core/services/gateway/gateway.go:278`) returns B's response, which A then reads.

Because `MethodWebAPITrigger` allows arbitrary attacker-chosen `MessageId` up to 128 bytes (`api.MessageIdMaxLen`, `core/services/gateway/api/message.go:22,61-63`) and the only length/format constraints are enforced in `Message.Validate()`, this is trivially exploitable by any unauthenticated/unprivileged party capable of producing a valid signature over their own chosen message body — no special credentials beyond the ability to sign a request (an EOA keypair) are needed.

### Impact Explanation
This is a direct cross-user response/data confusion vulnerability: an attacker can redirect and read the capability execution result intended for another user's `web_api_trigger` request, matching the target scope's "cross-user capability execution result theft/redirection" impact class. Depending on payload sensitivity (trigger response data, headers, computed values), this constitutes unauthorized disclosure of another user's request/response data through the gateway.

### Likelihood Explanation
Feasibility is high and requires no special privileges: the attacker only needs the ability to send a signed `web_api_trigger` gateway request (any EOA keypair works, since `ExtractSigner` accepts the signer as sender without an allowlist at this stage) and knowledge/guessing of the victim's in-flight `MessageId`. In practice this typically requires colluding with, timing against, or predicting/observing a victim's `MessageId` (e.g., via a shared/predictable ID scheme, or a race window while the DON has not yet responded), but no authentication bypass or node compromise is needed — it is fully repeatable and can be automated by racing requests with the same `MessageId`.

### Recommendation
In `core/services/gateway/handlers/capabilities/handler.go`, before storing into `h.savedCallbacks`, check for an existing non-expired entry keyed by `msg.Body.MessageId` and reject the new request (e.g., with a `Conflict`/`already in-flight` error) instead of silently overwriting it, mirroring the guard already present in `httpTriggerHandler.setupCallback` (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:402-405`). Additionally, consider scoping `MessageId` uniqueness to `(Sender, MessageId)` rather than `MessageId` alone, and implement the allowlist/rate-limiting noted by the `TODO` comment at `handler.go:384`.
