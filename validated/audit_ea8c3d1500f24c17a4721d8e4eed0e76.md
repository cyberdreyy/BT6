### Title
Stale confirmations from deleted members are counted toward quorum, allowing request execution below `num_confirmations` live members - (multisig2/src/lib.rs)

### Summary
`confirm()` computes whether quorum is reached using `confirmations.len() as u32 + 1 >= self.num_confirmations` without checking that every entry in the `confirmations` `HashSet<String>` still corresponds to a current member of `self.members`. `delete_member()` only purges requests/confirmations that were *created* by the removed member (`r.member == member`), not confirmations the removed member left on *other* pending requests, so a removed member's stale confirmation string persists and can be counted toward quorum on an unrelated request, letting it execute with fewer than `num_confirmations` live confirmers.

### Finding Description
The broken binding is: `live_confirmers(request_id) := |{m ∈ confirmations(request_id) : m ∈ self.members}|` should equal the value actually compared against `num_confirmations` inside `confirm()`. Instead, `confirm()` at [1](#0-0)  checks `confirmations.len() as u32 + 1 >= self.num_confirmations` using the *raw stored set size*, never filtering it against the current `self.members`.

`delete_member()` at [2](#0-1)  only removes requests whose *creator* (`r.member`) equals the member being deleted:
```
let request_ids: Vec<u32> = self.requests.iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
```
It never scans `self.confirmations` for entries where the deleted member appears as a *confirmer* on a request created by someone else. Those stale confirmation strings remain in the `confirmations: LookupMap<RequestId, HashSet<String>>` map forever, unvalidated against `self.members`.

Exploit flow (all steps performable only by existing multisig members, matching the impact category "a multisig request executed below `num_confirmations` live members"):
1. Multisig has members `{A,B,C,D}`, `num_confirmations = 3`.
2. `A` creates request `R` (a `Transfer`) via `add_request` — `r.member = A`.
3. `D` calls `confirm(R)` → `confirmations(R) = {D}` (1 < 3, not executed).
4. `A` calls `confirm(R)` → `confirmations(R) = {D, A}` (2 < 3, not executed).
5. Separately, a `DeleteMember{member: D}` request `R2` (creator `B`) is confirmed by `B`, `C`, and `A` in sequence; the 3rd confirmation triggers `execute_request`, which calls `delete_member`. `delete_member` asserts `members.len()-1 (=3) >= num_confirmations (=3)` — passes — and removes `D` from `self.members`. Since `R` was created by `A`, not `D`, it is untouched; `confirmations(R)` still contains `{D, A}`.
6. `C` calls `confirm(R)`. In `confirm()`, `confirmations.len() (=2) + 1 = 3 >= num_confirmations (=3)` → `remove_request` + `execute_request` fire, transferring funds.
7. At execution time, current members are `{A,B,C}`. The actually-live confirmers of `R` are only `A` and `C` (2), since `D` is no longer a member — below the required 3 live confirmations — yet the transfer executes.

No existing guard (`assert_valid_request`, `assert_self_request`, `current_member`) re-validates the stored confirmation set against `self.members` at execution time; `current_member()` only validates the *caller* of the current call, not historical confirmers.

### Impact Explanation
NEAR held by the multisig account can be transferred out (or any other multisig action executed, including further `AddKey`/`DeleteMember`/`FunctionCall` actions) with fewer than `num_confirmations` currently-live members having actually approved it, directly matching the Critical impact "a multisig request executed below `num_confirmations` live members." This breaks the core security guarantee of the multisig — that a quorum of *current* signers must approve fund movement — and is repeatable for every pending request that collects a confirmation from a member later removed via a separate `DeleteMember` action.

### Likelihood Explanation
The only precondition is ordinary multisig operation: a member confirms a pending request, and later that same member is removed via a properly-quorate `DeleteMember` request while the first request is still pending and was created by a different member. No special account balances or external contracts are needed, and the sequence is entirely achievable through normal `add_request`/`confirm` calls available to any current member. This is a logic defect in `delete_member`/`confirm`, not a race condition requiring precise timing beyond ordinary transaction ordering within the same contract.

### Recommendation
In `confirm()`, before comparing against `num_confirmations`, filter `confirmations` to only those entries still present in `self.members` (or, in `delete_member`, iterate all entries of `self.confirmations` and strip the deleted member's string from every set, not just requests it created).

### Proof of Concept
```rust
#[test]
fn test_stale_confirmation_below_quorum_executes() {
    // members: A, B, C, D ; num_confirmations = 3
    let mut c = MultiSigContract::new(members_abcd(), 3);

    // Step 1: A creates transfer request R
    testing_env!(context_with_account(a(), amount));
    let r_id = c.add_request(transfer_request(bob(), amount));

    // Step 2: D confirms R
    testing_env!(context_with_account(d(), amount));
    c.confirm(r_id);
    assert_eq!(c.confirmations.get(&r_id).unwrap().len(), 1);

    // Step 3: A confirms R (2/3, not executed yet)
    testing_env!(context_with_account(a(), amount));
    c.confirm(r_id);
    assert_eq!(c.requests.get(&r_id).is_some(), true);
    assert_eq!(c.confirmations.get(&r_id).unwrap().len(), 2);

    // Step 4: B creates + B,C,A confirm DeleteMember{D} request R2 -> executes, removes D
    testing_env!(context_with_account(b(), amount));
    let r2_id = c.add_request(delete_member_request(d()));
    c.confirm(r2_id);
    testing_env!(context_with_account(c_(), amount));
    c.confirm(r2_id);
    testing_env!(context_with_account(a(), amount));
    c.confirm(r2_id); // 3rd confirmation -> executes delete_member(D)
    assert_eq!(c.get_members().contains(&member_account(d())), false);
    assert_eq!(c.get_members().len(), 3); // {A,B,C}

    // R's confirmations still contain stale D
    assert!(c.confirmations.get(&r_id).unwrap().contains(&member_account(d()).to_string()));

    // Step 5: C confirms R -> should NOT execute (only A,C are live confirmers = 2 < 3)
    testing_env!(context_with_account(c_(), amount));
    c.confirm(r_id);

    // BUG: request executed and was removed despite only 2 live-member confirmations
    assert_eq!(c.requests.get(&r_id).is_some(), false, "request executed with stale confirmation counted");
}
```
Both sides of the binding to assert: `live_confirmers(R) = |{A, C}| = 2` versus `num_confirmations = 3`; the test shows `R` executes (removed from `c.requests`) despite `2 < 3`, confirming the vulnerability. [3](#0-2) [4](#0-3) [5](#0-4)

        self.assert_valid_request(request_id);

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .unwrap_or_else(|| env::panic_str("Failed to remove existing element"));
        // decrement num_requests for original request signer
        let original_member = request_with_signer.member;
        let mut num_requests = self
            .num_requests_pk
            .get(&original_member.to_string())
            .unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_member.to_string(), &num_requests);
        // return request
        request_with_signer.request
    }
