### Title
Native EIP-8130 account abstraction sets `tx.origin == msg.sender` for a non-EOA "configured actor," breaking the ubiquitous `require(msg.sender == tx.origin)` EOA-check idiom relied on by deployed contracts - ([File: crates/common/evm/src/eip8130.rs])

### Summary
The external report flags that `msg.sender == tx.origin` checks used by contracts (e.g. Rio's `rebalance()`) to force an EOA caller and block same-block flash-loan sandwich attacks will stop holding once Ethereum ships native account abstraction (EIP-3074/EIP-7702-style). Base already ships exactly this class of native account abstraction as EIP-8130, and its EVM integration deliberately sets the `ORIGIN` opcode (`tx.origin`) to the resolved "sender," which — on the configured-actor path — need not be a raw secp256k1-controlled EOA at all.

### Finding Description
`TxEip8130` supports two sender paths: an EOA path (`sender: None`, recovered via ECDSA) and a "configured-actor" path (`sender: Some(account)`) where the account is authenticated by an arbitrary registered authenticator [1](#0-0) . Authorization explicitly allows "any canonical authenticator (secp256k1, P-256, WebAuthn, or a delegate contract)" to control the sender/config-mutating operations — i.e. the account's authorization logic can be governed by an arbitrary delegate contract rather than a single private key [2](#0-1) , and the same `verify_sender` resolves the sender for either path uniformly, granting it whatever operation scope it has been configured with [3](#0-2) .

When the EVM executes such a transaction, the resolved sender is written into the `TxEnv` caller field specifically so that "`tx.origin` (the `ORIGIN` opcode) reads correctly during `calls`" [4](#0-3) . Every top-level call dispatched by the transaction's phases is then run with `outcome.sender` as both the frame's caller and the transaction's origin: `Self::run_call(evm, outcome.sender, call.to, call.data.clone(), remaining)` [5](#0-4) . The estimation/simulation path repeats the same caller overwrite for the identical reason [6](#0-5) .

Consequently, for any first-level call made by an EIP-8130 "configured-actor" sender, `msg.sender == tx.origin` holds exactly as it would for a genuine EOA, even though the sender account is not a private-key-controlled EOA: it can be a policy-gated account, a multisig, or an account whose authorization is delegated to arbitrary contract logic. In addition, a single EIP-8130 transaction can atomically dispatch multiple phases, each containing multiple calls (`calls: Vec<Vec<Call>>`) [7](#0-6) , giving the "configured actor" the same multi-step, single-transaction composability (flash-loan-style deposit → distribute → withdraw sequencing) that the original report's `msg.sender != tx.origin` check was specifically designed to block.

### Impact Explanation
Any application deployed on Base that uses the standard `require(msg.sender == tx.origin)` / `if (msg.sender != tx.origin) revert` pattern to prevent contract-orchestrated, same-transaction attacks (flash-loan sandwich attacks on reward/price distribution, MEV-sensitive rebalancing, anti-flash-loan governance snapshots, etc.) can be silently bypassed by an EIP-8130 configured-actor transaction. The attacker submits a single EIP-8130 transaction whose "sender" is a policy/delegate-contract-controlled account; every downstream contract sees `tx.origin == msg.sender`, believes it is dealing with an EOA, and the attacker's grouped `calls` phases can still perform the flash-loan-esque compose-in-one-transaction attack the check exists to prevent (theft of protocol rewards / unbacked value extraction). This is a protocol-level (not just an individual dApp bug) erosion of a widely relied-upon security invariant on Base.

### Likelihood Explanation
EIP-8130 is a core, always-available transaction type on Base — no special privilege is required, and the configured-actor path is a first-class, documented feature of the transaction format (not an edge case). Any unprivileged user can submit such a transaction and any dApp deployed on Base that uses the `tx.origin == msg.sender` pattern (a very common idiom, as evidenced by the referenced Sherlock report) is automatically exposed the moment it receives a call originating from a configured-actor sender.

### Recommendation
Document prominently, and consider mitigating at the protocol/tooling level, that on Base `tx.origin == msg.sender` no longer implies the caller is a non-programmable, single-key EOA once the configured-actor path of EIP-8130 is used. Where feasible, expose a reliable on-chain signal distinguishing EOA-path senders (`TxEip8130::sender == None`) from configured-actor senders (e.g. via a precompile/opcode extension) so contracts that depend on the EOA invariant for flash-loan/MEV protection can be updated to use it instead of `tx.origin`. Absent that, ecosystem guidance should steer dApp developers away from `tx.origin`-based EOA checks toward reentrancy guards or explicit timelocks between state-changing operations, consistent with the original report's recommendation.

### Proof of Concept
1. Deploy (or target an existing) contract on Base that gates a sensitive function with `require(msg.sender == tx.origin)` to block flash-loan sandwich attacks (mirroring `RioLRTCoordinator.rebalance()`'s `CALLER_MUST_BE_EOA` check).
2. Construct an EIP-8130 `TxEip8130` with `sender = Some(attackerControlledAccount)` (configured-actor path), where `attackerControlledAccount` is authorized via a delegate-contract authenticator implementing arbitrary attack logic [2](#0-1) .
3. Populate `calls` with multiple phases replicating the flash-loan-driven deposit → reward-sweep → withdrawal-request sequence from the original report, all addressed as top-level calls (`call.to`) from the configured actor.
4. Submit the transaction. Because `evm.ctx_mut().tx.base.caller = outcome.sender` and each call is dispatched via `run_call(evm, outcome.sender, call.to, ...)` [8](#0-7) [9](#0-8) , the target contract's `msg.sender == tx.origin` check passes even though `attackerControlledAccount` is governed by attacker-supplied contract logic, allowing the atomic multi-step attack the check was meant to prevent.
