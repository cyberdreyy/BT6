## Title
Stale confirmations from removed multisig members remain counted toward the confirmation threshold, allowing requests to execute below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
The multisig contract tracks per-request confirmations in a `confirmations: LookupMap<RequestId, HashSet<String>>` map [1](#0-0) . When a member is removed via `DeleteMember`, the contract only purges requests that the removed member itself created — it never scrubs that member's confirmations from requests created by other members [2](#0-1) . Those stale confirmations remain in the `HashSet` and continue to count toward `num_confirmations` in `confirm`, so a request can execute with fewer *live* member approvals than the configured threshold. This is the same bug class as the ZetaChain gas-price median issue: an entry from a party that is no longer part of the "current" set (there: an inactive observer, here: a removed multisig member) is not filtered out of the aggregate that a security threshold is calculated over.

### Finding Description
`confirm` gates execution purely on the size of the `confirmations` set for a request:
```rust
let mut confirmations = self.confirmations.get(&request_id).unwrap();
...
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
} ...
``` [3](#0-2) 

New confirmations can only be added by a `current_member()`, i.e., an account still present in `self.members` [4](#0-3) . However, `delete_member` — invoked from `execute_request`'s `DeleteMember` action — removes:
- the member from `self.members`
- their access key (if any)
- `num_requests_pk` entry
- only the *requests they themselves created* (and those requests' confirmation sets)

```rust
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    ...
    self.members.remove(&member);
    ...
}
``` [2](#0-1) 

It never iterates `self.confirmations` to strip the removed member's identifier (`member.to_string()`) from confirmation sets of requests *created by other members*. Any request that the removed member already confirmed before being kicked out keeps that confirmation entry indefinitely. The binding that should hold — `live confirmations on a request == count used to authorize it` — is broken: the count used includes confirmations from members who are no longer part of `self.members`.

### Impact Explanation
This directly maps to the Critical category "a multisig request executed below threshold." Example with `num_confirmations = 2`, members `{A, B, C}`:
1. `A` calls `add_request_and_confirm` on a `Transfer`/`DeployContract`/`AddKey` request → confirmations = `{A}` (1/2).
2. `A` is removed (e.g., compromised key, offboarded) via a separate `DeleteMember` request executed by `B`+`C`. `delete_member` only deletes requests *added by* `A`; the Transfer request added by `A`... 

Actually since the request itself was added by `A`, use a variant where the confirmer differs from the creator:
1. `B` calls `add_request` on a `Transfer` request (created by `B`).
2. `A` calls `confirm` on that request → confirmations = `{B, A}`... 

To keep it below threshold, use `num_confirmations = 2`, members `{A, B, C}`:
1. `B` creates request `R` (`add_request`), no confirmation yet. `confirmations[R] = {}`.
2. `A` confirms `R` → `confirmations[R] = {A}` (1/2, not yet executed).
3. Multisig removes `A` (e.g., legitimately, key compromised) via a separate, properly-confirmed `DeleteMember` request. `delete_member` scans `self.requests` for requests where `r.member == A` — request `R` was created by `B`, not `A`, so it is untouched; `confirmations[R]` still contains `A`.
4. `B` now confirms `R` → `confirmations[R].len() + 1 == 2 >= num_confirmations` → `R` executes, even though only one *current* member (`B`) ever validly approved it after `A`'s removal.

The severity depends on what `R`'s actions are — with `MultiSigRequestAction::Transfer`, `AddKey`, or `DeployContract`, funds can move or access can be granted with effectively a single live approver instead of the intended 2-of-3 threshold.

### Likelihood Explanation
This requires no special privilege beyond being (at some point) a legitimate multisig member who confirmed a request and was later removed — a routine operational event (key rotation, offboarding, compromise response). No malicious collusion or attacker-controlled deployment is needed; the flaw is triggered by the normal `DeleteMember` maintenance flow combined with any pre-existing partial confirmation. It only takes one other live member confirming to complete the (now understaffed) approval.

### Recommendation
When executing `DeleteMember`, iterate all active `requests`/`confirmations` entries and remove the deleted member's string identifier from every confirmation `HashSet`, not just from requests they created. Alternatively, at `confirm`-time recompute the effective confirmation count by intersecting the stored `HashSet` with the current `self.members` set before comparing against `num_confirmations`.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
