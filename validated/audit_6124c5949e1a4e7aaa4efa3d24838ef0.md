### Title
APR0 dust withdraw request permanently reverts `stopEpoch` once manager raises APR, freezing all pool funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` hard-reverts whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. An unprivileged KYC'd lender can open a dust-size `requestWithdraw` during an APR=0 epoch/buffer; the vault accepts it and records APR0 principal. If the honest manager ever raises the APR before or at the next `stopEpoch`, every `stopEpoch`/`stopEpochWithDuration` call — including the `_interest == 1` "recall all principal" close path — reverts with `NotAllowed`, bricking the epoch state machine while borrower funds are outstanding.

### Finding Description
The analog to the PFCP bug (a malformed-but-accepted setup request that leaves the node in an inconsistent state where a later valid request cascades into failure) is `IdleCreditVault.requestWithdraw` accepting an APR0 request that becomes toxic to the epoch lifecycle:

1. During a buffer period while `unscaledApr == 0`, a lender calls `IdleCDOEpochVariant.requestWithdraw`. The CDO routes to `IdleCreditVault.requestWithdraw`, which mints the user a receipt and calls `_requestWithdrawApr0`, setting `apr0Users[user].principal`, `principalEpoch`, and increasing `apr0TotalPrincipal` (`IdleCreditVault.sol:285-294`, `:567-577`). The request is valid at acceptance time — nothing about it is malformed.
2. `setAprs`/`setApr` (`IdleCreditVault.sol:206-235`) lets the CDO or manager change `unscaledApr` at any time with no check on `apr0TotalPrincipal`. A legitimate operational APR change after the request leaves the strategy in an inconsistent state: pending APR0 receipts exist but APR is no longer zero.
3. `IdleCDOEpochVariant._stopEpoch` unconditionally calls `_strategy.prepareStopEpochWithApr0(_interest)` (`IdleCDOEpochVariant.sol:362`). That function reverts `NotAllowed` when `apr0TotalPrincipal != 0 && unscaledApr != 0` (`IdleCreditVault.sol:505-508`), before any borrower pull, accounting update, or epoch-number bump.

Because the revert happens on every subsequent `stopEpoch` invocation while APR is non-zero, the protocol cannot close the epoch, cannot pull borrower funds, cannot fund pending receipts, and cannot even execute the close-pool `_interest == 1` path (the sentinel still reaches `prepareStopEpochWithApr0`). The only recovery is the manager setting `unscaledApr` back to 0, then stopping with `_newApr` constrained so the post-stop state also keeps `apr0TotalPrincipal` consistent — but `apr0TotalPrincipal` is only cleared inside the same reverting function (`:540`), so the freeze persists for the duration of the non-zero APR.

### Impact Explanation
Temporary freezing of the entire pool: while APR is non-zero and any APR0 principal is pending, `stopEpoch` always reverts, so `epochNumber` never increments, `claimWithdrawRequest` stays gated by `epochNumber <= lastWithdrawRequest[user]` (`IdleCreditVault.sol:326-328`), borrowers' repayment window can lapse, and LP funds are locked for the whole non-zero-APR period. Loss is quantified as denial of the fixed-APR yield the pool was supposed to accrue plus the operational risk of missing the borrower repayment deadline; if the inconsistency is not noticed and corrected before `epochEndDate`, the epoch rollover (and all dependent queue processing) is frozen indefinitely until a privileged APR rollback.

### Likelihood Explanation
Low-to-moderate. It requires (a) an epoch configured with `unscaledApr == 0`, which is a supported mode (dedicated `apr0Users` bucket exists), (b) any lender — including a dust request of minimal size — calling `requestWithdraw` during the buffer, and (c) an honest manager raising the APR (a routine operation via `setAprs`/`setAprsWithBuffer`/`stopEpoch` with `_newApr > 0` once APR propagates) while the request is pending. No malicious privileged action is needed; the attacker only needs a KYC-allowed wallet and a tranche balance to burn.

### Recommendation
Do not revert in `prepareStopEpochWithApr0` when APR changed; instead, settle the APR0 bucket at the rate applicable at request time (or zero interest) and clear `apr0TotalPrincipal` regardless of current `unscaledApr`. Additionally, consider gating `setApr`/`setAprs` to reject a non-zero APR while `apr0TotalPrincipal != 0`, so the inconsistency cannot be created.

### Proof of Concept
```solidity
// Foundry fork-style PoC sketch against IdleCDOEpochVariant + IdleCreditVault
// Phase: buffer period, epoch N running with unscaledApr == 0.

// 1. Attacker (KYC'd lender with tranche tokens) opens a dust APR0 withdraw request
vm.prank(attacker);
idleCDO.requestWithdraw(1, AATranche); // amount=1 wei of tranche
assertGt(strategy.apr0TotalPrincipal(), 0);

// 2. Epoch starts normally; funds sent to borrower
vm.prank(manager);
cdoEpoch.startEpoch();

// 3. Honest operational action: manager raises APR mid-epoch
vm.prank(manager);
strategy.setAprs(5e18, 5e18); // unscaledApr != 0 while apr0TotalPrincipal != 0

// 4. Epoch ends; borrower repays; every stopEpoch reverts
deal(underlying, borrower, expectedFundsEndEpoch);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(0, 0);

// Even the recall-all-principal close path reverts identically
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(0, 1);

// Result: epochNumber frozen, pending receipts unclaimable,
// contract value locked until manager restores unscaledApr == 0.
```

Note on uncertainty: this analog yields temporary rather than permanent freezing (recovery requires the manager to return `unscaledApr` to 0). If the strict bar is permanent loss only, this should be downgraded; no direct theft path was confirmed within the reviewed functions, and the per-epoch receipt guards (`lossRecoveryPriceByEpoch`, `postDefaultRequests`, `defaultRecoveryFinalized`) at `IdleCreditVault.sol:247-271` appear to close the double-claim variants.
