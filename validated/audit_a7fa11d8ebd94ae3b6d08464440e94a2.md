### Title
JSON-RPC `bank()` commitment resolver silently falls back to the root bank when the commitment-cache slot is stale, serving wrong-slot data - ([File: rpc/src/rpc.rs])

### Summary
The bug report describes a stale-reference migration bug: `PirexRewards`' `producer` still points to the old `PirexGmx` contract after `completeMigration()`/`migrateReward()`, so calls routed through the stale reference silently return zero instead of failing, causing quiet loss of value. The structural bug class — a cache/reference that is updated non-atomically relative to a companion state, so a caller consults the stale value and silently receives wrong (but plausible-looking) data instead of an error — reproduces in `JsonRpcRequestProcessor::bank()` in `rpc/src/rpc.rs`, where `BlockCommitmentCache`'s cached slot and `BankForks`' live bank set can fall out of sync, causing the RPC layer to silently substitute an unrelated bank for the one the client asked for.

### Finding Description
`JsonRpcRequestProcessor::bank()` resolves the `Bank` to use for a JSON-RPC query based on the requested `CommitmentConfig`. For `processed`/`finalized` commitment it looks up a slot from `self.block_commitment_cache` and then fetches that slot's bank from `self.bank_forks`: [1](#0-0) 

If the bank for that slot is no longer present in `BankForks` (already pruned by `ReplayStage`/`BankForks::set_root` via `prune_non_rooted`), the code does **not** return an error to the client. Instead it logs a `warn!` and silently substitutes `bank_forks.root_bank()` — a bank for a completely different (older) slot: [2](#0-1) 

The comment in the code itself acknowledges the underlying race: `BlockCommitmentCache` is updated by a separate thread/mechanism than `BankForks` pruning, so "an old bank has been purged from BankForks and a new BlockCommitmentCache has not yet arrived" (referencing solana-labs/solana#11078), which is structurally identical to the report's root cause — two dependent pieces of state (`producer`/`pirexRewards` vs. migration completion; `BlockCommitmentCache` slot vs. `BankForks` bank set) are updated in separate, non-atomic steps, and a caller consulting the stale one gets silently wrong data rather than an explicit failure.

A related test acknowledges the same race at the `AccountsDb` layer: [3](#0-2) 
(the accounts layer now excludes non-ancestor rooted data during load, but the `rpc.rs` `bank()` fallback still exists at the `BankForks`/`BlockCommitmentCache` layer and is unaddressed).

### Impact Explanation
Any unprivileged JSON-RPC caller using `processed` or `finalized` commitment (the default `getBalance`, `getAccountInfo`, `getBlock`, `getSlot`, etc. paths all route through `bank()`) can, during the ordinary window where `ReplayStage` prunes a non-rooted/old bank slightly ahead of `BlockCommitmentCache` catching up, receive a response computed against an unrelated (older) root bank instead of an error. This satisfies the "wrong-slot/fork/account data returned" impact category: the client receives data (balances, account state, block info) for the wrong bank state without any indication in the RPC response that a fallback occurred (only a server-side `warn!` log, generally not visible to the caller).

### Likelihood Explanation
This path is reachable purely from ordinary read-only, unprivileged RPC traffic (no special permissions needed) and is triggered by the validator's normal internal timing between bank pruning and commitment-cache updates — the same race the in-repo comment and linked upstream issue #11078 already describe as a "known bug." It does not require multiple RPC calls, a specific client, or malicious input; a single well-timed `getBalance`/`getAccountInfo` request during normal root advancement can trigger it.

### Recommendation
Do not silently substitute `root_bank()` when the commitment-cache-selected slot's bank is missing. Instead:
1. Make `BlockCommitmentCache` hold an `Arc<Bank>` (as the code comment itself suggests) instead of a bare `Slot`, so the referenced bank cannot be pruned out from under it, or
2. Return an explicit RPC error (e.g. "unable to resolve bank for the given commitment") when the target slot's bank is absent from `BankForks`, rather than returning data from a different bank.

### Proof of Concept
1. A client issues `getAccountInfo`/`getBalance` with `commitment: "finalized"` (or default `processed`).
2. `bank()` reads a slot `S` from `self.block_commitment_cache` at `rpc/src/rpc.rs:365-369`.
3. Concurrently, `ReplayStage`/`BankForks::set_root` prunes bank `S` from `BankForks` before `BlockCommitmentCache` is updated to reflect the new root (the race explicitly noted in the code comment at lines 383-393).
4. `r_bank_forks.get(slot)` at line 382 returns `None`.
5. The closure at lines 382-399 logs a warning and returns `r_bank_forks.root_bank()` instead of erroring, so the RPC response is computed against an unrelated bank/slot with no error surfaced to the caller.

        let slot = self
            .block_commitment_cache
            .read()
            .unwrap()
            .slot_with_commitment(commitment.commitment);

        match commitment.commitment {
            CommitmentLevel::Processed => {
                debug!("RPC using the heaviest slot: {slot:?}");
            }
            CommitmentLevel::Finalized => {
                debug!("RPC using block: {slot:?}");
            }
            CommitmentLevel::Confirmed => unreachable!(), // SingleGossip variant is deprecated
        };

        let r_bank_forks = self.bank_forks.read().unwrap();
        r_bank_forks.get(slot).unwrap_or_else(|| {
            // We log a warning instead of returning an error, because all known error cases
            // are due to known bugs that should be fixed instead.
            //
            // The slot may not be found as a result of a known bug in snapshot creation, where
            // the bank at the given slot was not included in the snapshot.
            // Also, it may occur after an old bank has been purged from BankForks and a new
            // BlockCommitmentCache has not yet arrived. To make this case impossible,
            // BlockCommitmentCache should hold an `Arc<Bank>` everywhere it currently holds
            // a slot.
            //
            // For more information, see https://github.com/solana-labs/solana/issues/11078
            warn!(
                "Bank with {:?} not found at slot: {:?}",
                commitment.commitment, slot
            );
            r_bank_forks.root_bank()
        })
