### Title
APR0 withdraw receipts permanently brick `stopEpoch` once APR is raised above zero - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`prepareStopEpochWithApr0` unconditionally reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` and the vault APR is non-zero. Any KYC-passing lender can create APR0 principal via `requestWithdraw` while `unscaledApr == 0`. If the (honest) manager then restores a positive APR — a normal operational action — before those requests settle, every subsequent `stopEpoch` reverts, freezing the whole pool: new epochs cannot start, interest cannot settle, and the affected users cannot clear their receipts.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` routes to `_requestWithdrawApr0` whenever `unscaledApr == 0`, which increments the global `apr0TotalPrincipal` and stores `apr0Users[_user].principal/principalEpoch` (lines 285-286, 567-577).
- `apr0TotalPrincipal` is only cleared in two places: `prepareStopEpochWithApr0` (line 540) and per-user claims via `_clearWithdrawClaimForEpoch` (line 827).
- `prepareStopEpochWithApr0` — called by the CDO during `stopEpoch` — reverts when `_principal = apr0TotalPrincipal != 0` and `unscaledApr != 0`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

- The users holding the open APR0 receipts cannot settle them: `_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest[_user]` (line 326), and `epochNumber` only increments inside `stopEpoch` — the very call that now reverts. `_settleApr0` also returns early while `_reqEpoch >= epochNumber` (lines 551-555).

This creates a deadlock: pending APR0 receipts need a `stopEpoch` to settle, and `stopEpoch` reverts because pending APR0 receipts exist under a non-zero APR.

### Impact Explanation
While APR is non-zero, the vault is stuck mid-buffer: `stopEpoch` always reverts, `startEpoch` cannot run, borrower repayment/settlement halts, and all lenders' tranche withdrawals (which depend on epoch progression or full redemption) are frozen. The freeze lasts until the manager manually drops `unscaledApr` back to 0 — a forced protocol configuration change — so this is a temporary freezing of all vault funds, plus it forces the pool to run an unwanted zero-interest epoch, quantifiably costing every LP the interest of at least one full epoch duration on the entire TVL. There is no user-side escape hatch.

### Likelihood Explanation
Triggering requires only an unprivileged, whitelisted lender calling `requestWithdraw` during a legitimately configured APR=0 phase — the intended flow — followed by the honest manager raising the APR via `setAprs` before the request settles. APR changes between epochs are routine; no malicious privileged action is needed. The attacker only needs one dust-sized request to hold the whole pool hostage.

### Recommendation
Decouple APR0 bookkeeping from the liveness of `stopEpoch`. Options: (a) in `prepareStopEpochWithApr0`, treat a non-zero `unscaledApr` as a signal to settle the APR0 bucket at a zero or realized rate instead of reverting; (b) store `apr0RateByEpoch[epochNumber] = 0` and zero out `apr0TotalPrincipal` when APR changed, letting users claim principal at par; or (c) allow permissionless settlement of stale APR0 principal when `unscaledApr != 0`.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (against test/foundry/IdleCreditVault.t.sol harness)
function testApr0ReceiptBlocksStopEpochAfterAprRaise() external {
  // 1. Manager legitimately sets APR to 0.
  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(0, 0);

  // 2. Attacker (KYC'd lender) deposits and requests a withdraw in the APR0 phase.
  uint256 minted = idleCDO.depositAA(100 * ONE_SCALE);
  cdoEpoch.requestWithdraw(minted, address(AAtranche));
  assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

  // 3. Honest manager raises APR for the next epoch (routine operation).
  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(500, 0); // 5%

  // 4. Every stopEpoch now reverts -> epoch can never advance.
  vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() + 1);
  vm.prank(manager);
  vm.expectRevert(NotAllowed.selector);
  cdoEpoch.stopEpoch(0, 0);

  // 5. Attacker cannot self-clear: epochNumber never exceeds lastWithdrawRequest.
  vm.expectRevert(NotAllowed.selector);
  cdoEpoch.claimWithdrawRequest();
}
```

Caveat: I could not fully trace the `stopEpoch` → `prepareStopEpochWithApr0` call site inside `IdleCDOEpochVariant.sol` within the available context; the finding assumes it is invoked unconditionally when `apr0TotalPrincipal != 0`, consistent with its `_onlyIdleCDO` guard and the test usage at `test/foundry/IdleCreditVault.t.sol:3129`. If `stopEpoch` skips the call when APR is non-zero, the freeze resolves into a different accounting path and this finding should be downgraded.
