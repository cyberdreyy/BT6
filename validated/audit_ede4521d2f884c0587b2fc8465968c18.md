### Title
Unauthenticated per-request map flooding via missing sender quota in confidential relay handler enables DoS against concurrent legitimate callers - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`HandleJSONRPCUserMessage` in the confidential relay handler admits any JSON-RPC request with a unique, non-empty ID into the `activeRequests` map with no per-sender identity check, authentication, or per-sender rate limit, relying solely on `removeExpiredRequests` sweeping entries older than `RequestTimeoutSec` (default 30s). An attacker can continuously submit fresh, distinct request IDs to keep the map saturated and consume fan-out/bundling resources shared by the handler instance, unlike the vault handler which enforces a `NodeRateLimiter`/per-sender configuration on user requests.

### Finding Description
`HandleJSONRPCUserMessage` only validates that `req.ID` is non-empty and ≤200 characters before calling `h.newActiveRequest(req, callback)` and then `h.fanOutToNodes` [1](#0-0) . `newActiveRequest` only rejects a request if the exact same `req.ID` already exists in `h.activeRequests`; it performs no per-sender bookkeeping or quota check before inserting into the shared map under `h.mu.Lock()` [2](#0-1) .

The only rate limiting present in this handler (`globalNodeRateLimiter`, `perNodeRateLimiters`) is applied in `HandleNodeMessage`, which throttles *node* responses coming back from DON members — not incoming *user* requests [3](#0-2) . There is no `userRateLimiter`, `PerSenderRPS`, or authentication/authorization step analogous to the vault handler's `NodeRateLimiter` config (`PerSenderRPS`/`PerSenderBurst`) or the HTTP trigger handler's `authorizeRequest`/`checkRateLimit` pipeline [4](#0-3) [5](#0-4) .

The gateway's dispatch path (`gateway.ProcessRequest`) decodes the JSON-RPC request and routes it straight to `h.HandleJSONRPCUserMessage` with no gateway-level authentication or per-sender throttling applied uniformly across handlers — each handler is individually responsible for its own auth/rate-limiting [6](#0-5) . Since the confidential relay handler does not implement any such check, any caller reaching this JSON-RPC endpoint can insert entries into `activeRequests` merely by supplying unique IDs.

Expired entries are only pruned once per second by `removeExpiredRequests`, and only once they exceed `RequestTimeoutSec` (default 30s) [7](#0-6) . An attacker can therefore keep issuing a continuous stream of unique-ID requests, each alive for up to ~30 seconds, to keep the map populated indefinitely, forcing `fanOutToNodes` to run (fanning every request out to all DON members with `errgroup`) for each of the attacker's entries, and contending the single `h.mu` mutex used by every legitimate caller's `newActiveRequest`/`getActiveRequest`/`sendResponseAndClearRequest` calls.

### Impact Explanation
This is a resource-exhaustion / availability issue: a single unprivileged caller can cause unbounded growth of the `activeRequests` map and unbounded fan-out traffic to DON members bound only by wall-clock request lifetime, degrading service (lock contention, increased fan-out load, and node-side rate-limit saturation via `perNodeRateLimiters`) for other legitimate callers sharing the same DON's handler instance. This falls under the DoS / resource exhaustion class of the bounty program rather than authentication bypass or fund loss, since no secrets, keys, or unauthorized job execution are directly obtained.

### Likelihood Explanation
No credential beyond ability to reach the gateway's confidential relay JSON-RPC endpoint is required — the handler applies no authentication or authorization to distinguish or throttle senders, only a request-ID uniqueness check. The attack is trivially repeatable: an attacker simply needs to generate unique IDs at a rate that outpaces the `defaultCleanUpPeriod` sweep (1s) and stay under `RequestTimeoutSec` (default 30s) to sustain steady-state map saturation. This makes the precondition low (any client that can send `MethodCapabilityExec`/`MethodSecretsGet` JSON-RPC messages) and the exploit reproducible via simple looped calls to `HandleJSONRPCUserMessage`.

### Recommendation
Add a per-sender quota/rate limiter (mirroring the vault handler's `NodeRateLimiter`/`PerSenderRPS` pattern, or the HTTP trigger handler's `checkRateLimit`) to `HandleJSONRPCUserMessage` before inserting a new entry into `activeRequests`, keyed by an authenticated sender identity (e.g., signer address from `req.Auth` if such a field is added) rather than trusting the caller-supplied request ID alone. Additionally, consider bounding the total size of `activeRequests` (global capacity limit) and rejecting new requests once the cap is reached, returning a rate-limit error rather than silently accepting unlimited concurrent in-flight requests.

### Proof of Concept
Go handler-level integration test plan in `core/services/gateway/handlers/confidentialrelay/handler_test.go`:
1. Construct a `handler` via `NewHandler` with a small `RequestTimeoutSec` (e.g., 5s) and a fake clock (`clockwork.NewFakeClock()`), a mocked `DON` that returns success for `SendToNode`.
2. In a loop (e.g., 10,000 iterations), call `h.HandleJSONRPCUserMessage(ctx, req, callback)` with a unique `req.ID` each time (no per-sender label available) and without advancing the fake clock so entries never expire; assert every call succeeds (no error, no rejection) — demonstrating unlimited map growth.
3. Inspect `len(h.activeRequests)` directly (or via a package-internal test) to confirm it grows unbounded with the loop count, with no plateau or rejection at any point, showing there is no per-sender/global capacity cap enforced at `newActiveRequest`.
4. As a control, submit a "legitimate victim" request between attacker bursts and measure its `newActiveRequest`/`fanOutToNodes` latency (e.g., via wall-clock timing under `sync.RWMutex` contention with many concurrent goroutines hammering the map) to show increased contention/delay scales with attacker request volume — contrasting with the vault handler test (`TestVaultHandler_HandleJSONRPCUserMessage`) where `PerSenderRPS`/`PerSenderBurst` config exists and could be asserted to reject excess requests from a single sender.

func (h *handler) removeExpiredRequests(ctx context.Context) {
	h.mu.RLock()
	var expiredRequests []*activeRequest
	now := h.clock.Now()
	for _, userRequest := range h.activeRequests {
		if now.Sub(userRequest.createdAt) > h.requestTimeout {
			expiredRequests = append(expiredRequests, userRequest)
		}
	}
	h.mu.RUnlock()

	for _, er := range expiredRequests {
		responses := er.copiedResponses()
		l := logger.With(h.lggr, "method", er.req.Method, "requestID", er.req.ID)
		l.Debugw("request expired, evaluating collected relay responses",
			"collected", len(responses),
			"nodes", len(h.donConfig.Members),
			"unanswered", len(h.donConfig.Members)-len(responses),
		)
		summary, err := h.bundler.Bundle(er.req, responses, l)
		if err != nil {
			l.Errorw("failed to build relay response bundle", "error", err)
			if sendErr := h.sendResponseAndClearRequest(ctx, er, h.constructErrorResponse(er.req, api.FatalError, err)); sendErr != nil {
				l.Errorw("error returning bundle failure on expiry", "error", sendErr)
			}
			continue
		}
		// Expiry makes further responses unavailable to this request. The common
		// readiness path forwards a viable partial bundle or returns a timeout.
		if err := h.forwardBundleOrTerminateIfReady(ctx, l, er, summary, 0, true); err != nil {
			l.Errorw("error forwarding bundle on expiry", "error", err)
		}
	}
}

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	l := logger.With(h.lggr, "method", resp.Method, "requestID", resp.ID, "nodeAddr", nodeAddr)
	l.Debugw("handling node response")

	nodeRateLimiter, ok := h.perNodeRateLimiters[nodeAddr]
	if !ok {
		return fmt.Errorf("received message from unexpected node %s", nodeAddr)
	}
	if !nodeRateLimiter.Allow(ctx) {
		l.Debugw("node is rate limited", "nodeAddr", nodeAddr)
		return nil
	}
	if !h.globalNodeRateLimiter.Allow(ctx) {
		l.Debug("global relay rate limit exceeded")
		return nil
	}
