### Title
Stale block-rejection weight is never retracted when a signer later accepts the same block, allowing double-counted weight to wedge the miner's block-finalization coordinator - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The node-side `StackerDBListener` tallies signer votes on a proposed block into two independent counters, `total_weight_approved` and `total_weight_rejected`. The rejection counter is incremented only once per signer via a guard on `responded_signers`, but the acceptance counter is guarded by a *different* set (`gathered_signatures`). A signer that first rejects and later accepts the very same block (`signer_signature_hash`) — a state transition the signer-side code explicitly supports for a "reconsidered" rejection — ends up counted in *both* buckets, since `responded_signers.insert(slot_id)` for the reject path was already consumed, but the accept path's `gathered_signatures` guard is still open.

### Finding Description
In the rejection branch, weight is added only once per signer: [1](#0-0) 

In the acceptance branch, the guard is a *separate* map (`gathered_signatures`), not `responded_signers`: [2](#0-1) 

Since `responded_signers.insert(slot_id)` at line 465 is unconditional and does not gate the `total_weight_approved` addition, a signer who previously rejected the block (already present in `responded_signers`, contributing to `total_weight_rejected`) and later sends an `Accepted` response for the same `block_sighash` will also be added to `total_weight_approved`. Nothing in this code path subtracts the signer's earlier contribution from `total_weight_rejected`. The result is that `total_weight_approved + total_weight_rejected` can exceed `self.total_weight` — an invariant the coordinator's threshold logic implicitly assumes holds.

The coordinator in `signer_coordinator.rs` evaluates the reject condition before the accept condition each loop iteration: [3](#0-2) 

Because stale rejection weight from a signer who has since accepted is never retracted, the `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` (blocking-minority reject) condition can be satisfied using weight that no longer reflects the signer's live vote, even while the *same* signers' current accept-votes have concurrently crossed `weight_threshold` in `total_weight_approved`. The reject branch is checked first, so the miner can be forced into `NakamotoNodeError::SignersRejected` even though a legitimate approval quorum currently exists from the actual up-to-date votes.

### Impact Explanation
This is a liveness wedge on the node/miner's block-finalization coordinator: a block that has genuinely reached signer approval threshold can be reported as rejected due to leftover, stale rejection weight that was never retracted when the responsible signers changed their vote to accept. This prevents legitimate blocks from being finalized/pushed, stalling tenure progress — directly analogous to the external report's core defect (a quantity that should be "recovered"/retracted on state change is never adjusted, corrupting a downstream accounting check and blocking finalization).

### Likelihood Explanation
Signer-side code explicitly permits reconsidering a previously-rejected block upon a qualifying new event (`reprocess_block_proposals.rs`, `signers_consider_consensus_blocks.rs` reference this "reconsider" flow), so a reject→accept sequence for the same `signer_signature_hash` is a real, reachable code path, not purely theoretical. However, I was not able to fully trace, within tool budget, every exact precondition under which the signer-side flips its vote to `Accepted` for the identical `signer_signature_hash` after a prior `Rejected` for that same hash (as opposed to a distinct proposal for the same height with a different hash) — this specific transition needs confirmation via a live Devin session inspecting `stacks-signer/src/v0/signer.rs`'s reconsideration logic (`handle_block_validate_ok`/rejection handling around "reject reason allows us to reconsider") in full, and `reprocess_block_proposals.rs` test scenarios, to determine whether it triggers same-hash re-acceptance or only re-proposal with a new hash. If it turns out reconsideration always produces a *new* `signer_signature_hash` (e.g., due to a new proposal), then `blocks.get_mut(&block_sighash)` would key on a different `BlockStatus` entirely and this double-counting could not occur for a single `BlockStatus` object.

### Recommendation
Use a single authoritative "current vote" map keyed by `slot_id` (holding either Accept or Reject) rather than two independently-guarded weight accumulators. When a signer's vote transitions from Reject to Accept (or vice versa) for the same block, retract the previous contribution from the old bucket before adding it to the new one, so `total_weight_approved + total_weight_rejected` never double-counts a signer's weight for a given block.

### Proof of Concept
Conceptual sequence (requires confirmation that reject→accept for the identical `signer_signature_hash` is reachable):
1. Miner proposes block B (hash H). Signer S (weight w) evaluates and rejects: `stackerdb_listener` records `responded_signers.insert(S)` = true, `total_weight_rejected += w` [1](#0-0) .
2. A later event causes signer S to reconsider and accept the *same* hash H. `stackerdb_listener` checks `!gathered_signatures.contains_key(S)` (true, first acceptance) and adds `total_weight_approved += w` [2](#0-1) . `total_weight_rejected` is never decremented.
3. With enough such signers, `total_weight_approved` can reach `weight_threshold` (true quorum) while `total_weight_rejected` also independently satisfies the blocking-minority condition using stale weight, causing `signer_coordinator.rs`'s loop to return `SignersRejected` before ever reaching the accept check [3](#0-2) , wedging finalization of an otherwise validly-signed block.
