### Title
Cross-user callback hijack via attacker-controlled MessageId collision in HandleLegacyUserMessage - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` stores each user's `Callback` in `h.savedCallbacks` keyed solely by the client-supplied `msg.Body.MessageId`, with no uniqueness check. An unauthenticated (self-signed) attacker can submit a request using a `MessageId` equal to a concurrently in-flight request from another user, overwriting the map entry so the victim's `Callback` reference is replaced by the attacker's, causing the DON's response to be delivered to the attacker instead of the legitimate requester.

### Finding Description
`gateway.ProcessRequest` decodes the incoming JSON-RPC request into an `api.Message`, calls `msg.Validate()`, and then invokes `h.HandleLegacyUserMessage(ctx, msg, callback)` with a freshly created per-request `Callback` object [2](#0-1) . `msg.Validate()` only checks signature format/length, field lengths, and null-byte suffixes, and recovers `Sender` from the signature — it does not require the signer to be a pre-registered/allowlisted address, and does not enforce any uniqueness of `MessageId` [1](#0-0) . Any client can generate its own ECDSA keypair, `Sign` an arbitrary `MessageId` value, and post it to the gateway HTTP endpoint.

Inside `HandleLegacyUserMessage`, after payload/timestamp/method validation, the handler unconditionally does:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [3](#0-2) 
There is no check for an existing entry under the same key before overwrite, and the `TODO: apply allowlist and rate-limiting here` comment a few lines above confirms no allowlisting is currently enforced [4](#0-3) .

Exploit flow: Victim A sends request A with `MessageId = "X"` (signed with A's own key), and the handler forwards A's request to all DON members and stores A's `Callback` under key `"X"`. Before the DON responds, Attacker B sends request B with the *same* `MessageId = "X"` (signed with B's own, unrelated key — allowed since `Validate()` does not require the sender to match any prior registration), which overwrites `h.savedCallbacks["X"]` with B's `Callback`. When a DON node subsequently replies referencing `MessageId = "X"` (from A's original request), `handleWebAPITriggerMessage` looks up `h.savedCallbacks["X"]`, finds B's saved callback, deletes the entry, and calls `savedCb.SendResponse(...)`, delivering A's response payload to B [5](#0-4) . Meanwhile A's HTTP request from `gateway.ProcessRequest` blocks on `callback.Wait(ctx)` and eventually times out with no response, so A never receives its own answer, and B fraudulently receives A's response instead.

The existing test `savedCallbacks stored only when message is valid` only verifies that *invalid* messages don't leave stale entries; it does not test the collision/overwrite scenario for two *valid* messages sharing a `MessageId` [6](#0-5) .

### Impact Explanation
This is a cross-user response confusion/information-disclosure bug: an attacker can intercept another legitimate user's DON response (which may contain sensitive workflow trigger data or execution results intended only for that user) simply by racing a request with a colliding `MessageId`, while denying the victim their own response (denial of service for the victim). This matches the "cross-user response confusion / unauthorized access to another user's response data" impact class relevant to gateway API consumers.

### Likelihood Explanation
Preconditions are minimal: the attacker needs no credentials beyond the ability to reach the gateway's public HTTP endpoint and generate an ECDSA keypair to self-sign a message (trivial, no registration/allowlist check is performed at this layer). The attacker must guess or otherwise learn the victim's `MessageId` and win a race to submit before the DON responds, which is a timing constraint but not a cryptographic barrier — `MessageId` values are often predictable/sequential or observable in client-side flows, and the attack is fully repeatable per targeted request.

### Recommendation
In `HandleLegacyUserMessage`, before inserting into `h.savedCallbacks`, check whether an entry already exists for `msg.Body.MessageId` and reject (or scope the key by `(Sender, MessageId)` tuple, or by a server-generated unique correlation ID) rather than trusting the client-controlled `MessageId` alone as a global map key. Consider using `LoadOrStore`-style atomic insert semantics and returning an error/`DuplicateMessageId` response to the second caller instead of silently overwriting.

### Proof of Concept
Go test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build handler via existing `setupHandler(t)` helper.
2. Create message A with `MessageId = "collide-1"` signed with `nodes[0].PrivateKey` (or any independent test key), and callback `cbA`.
3. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)` — assert it enqueues the callback (`don.SendToNode` invoked, no error).
4. Create message B with the same `MessageId = "collide-1"` but a different signer key and different payload, callback `cbB`.
5. Call `handler.HandleLegacyUserMessage(ctx, msgB, cbB)`.
6. Assert `handler.savedCallbacks["collide-1"].Callback == cbB` (i.e., A's callback reference has been overwritten).
7. Simulate a DON node response referencing `MessageId = "collide-1"` (as if answering A's original request) via `handler.HandleNodeMessage(...)`.
8. Assert that `cbB.Wait(ctx)` returns successfully with the response payload, while `cbA.Wait(ctx)` times out/never receives a response — demonstrating the cross-user callback hijack.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}

		return errors.New("invalid DON ID length")
