I found a concrete analog. It's a node-side (not per-signer) stale-vote accounting bug in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, exactly matching the report's root cause pattern: a value computed from a *prior* state (an already-superseded vote) is applied on top of a *new* state (a later, contradictory vote) without invalidating the earlier one — breaking the invariant that `total_weight_approved` and `total_weight_rejected` are mutually exclusive per-signer weight tallies.

### Title
Stale rejection weight is never cleared when a signer later accepts, letting `total_weight_approved` and `total_weight_rejected` double-count the same signer's weight and cause a validly-signed block to be reported as `SignersRejected` — (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` maintains two independent weight tallies per proposed block: `total_weight_approved` (from `BlockResponse::Accepted`) and `total_weight_rejected` (from `BlockResponse::Rejected`). The guard used to prevent double-counting differs between the two branches, so a signer that rejects a block and later legitimately reconsiders and accepts it (a state transition the signer explicitly supports, `LocallyRejected --> LocallyAccepted : re-evaluated`) ends up permanently counted in *both* tallies simultaneously.

### Finding Description
In the accept branch, weight is only added if the signer's slot isn't already present in `gathered_signatures`: [1](#0-0) 

In the reject branch, weight is added only if the signer's slot is being seen for the very first time across *either* message type, tracked by a shared `responded_signers` set: [2](#0-1) 

Both branches call `block.responded_signers.insert(slot_id)` after processing (line 465 for accept, implicitly via the `if` in the reject branch at line 515). Walking the two possible orderings:

- **Reject arrives first, then Accept**: `responded_signers.insert` succeeds on the reject, adding the signer's weight to `total_weight_rejected` (lines 515-518). When the accept later arrives, the accept branch checks `!block.gathered_signatures.contains_key(&slot_id)` — not `responded_signers` — so it is true, and the signer's weight is *also* added to `total_weight_approved` (lines 443-446). The earlier `total_weight_rejected` increment is never reverted; there is no code path that subtracts from `total_weight_rejected` when a later accept for the same slot arrives.
- **Accept arrives first, then Reject**: the reject branch's `responded_signers.insert(slot_id)` returns `false` (already present), so the late reject is correctly dropped without inflating `total_weight_rejected`.

This asymmetry means only the "flip from reject to accept" direction is unguarded. This is a signer behavior the protocol explicitly allows (see `docs/signer-flows.md`'s `BlockState` transition `LocallyRejected --> LocallyAccepted : re-evaluated`, and the CHANGELOG entry "For some rejection reasons, a signer will reconsider a block proposal that it previously rejected"), so it is reachable by a single honest signer under normal network conditions (e.g., first evaluation fails a transient/re-evaluable check, then a fresh proposal or updated chain view causes the signer to accept) — no majority or malicious signer needed, matching the scope constraint that only a one-slot participant (or ordinary gossip timing) is required.

`NakamotoNodeMinerThread`'s coordinator consumes these two tallies and checks rejection *before* approval: [3](#0-2) 

Because `total_weight_rejected` retains stale weight from signers who have since switched to accepting, the blocking-minority condition (`total_weight_rejected + weight_threshold > total_weight`) can become true even while `total_weight_approved >= weight_threshold` is also true for the *same* block — an outcome that should be impossible if each signer's current, single vote were counted once. The coordinator evaluates the reject branch first, so it returns `NakamotoNodeError::SignersRejected` and proceeds to (temporarily or permanently) exclude transactions based on `failed_txids` weight computed from the same stale-inclusive rejected tally, even though the block in fact reached legitimate 70% signature weight under the signers' current opinions.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality: the node's view of "how much weight currently rejects this block" can include weight from signers who no longer reject it. The practical consequence is a liveness wedge — a block that legitimately reached the 70% signing threshold can be reported to the miner as globally rejected, causing the miner to abandon a validly, sufficiently-signed block and to enact transaction exclusions (`temporarily_excluded_txids`/`permanently_excluded_txids`) driven by stale rejection reasons that no longer reflect the signer set's actual state. This matches the "liveness wedge" and "aggregated-weight vs verified-accepts" categories called out in scope.

### Likelihood Explanation
Reachable by a single ordinary signer under normal, allowed reconsideration behavior (no majority, no malicious key, no auth bypass required) — it only requires message ordering where a signer's rejection for a block is observed by the node before that same signer's later acceptance for the same block, which is a documented, supported flow in the v0 signer state machine.

### Recommendation
Track a single current vote per `slot_id` per block (e.g., an enum `Option<Vote>` instead of two independently-incremented counters gated by different sets), and when a later vote for the same slot supersedes an earlier one, subtract the previous weight from its tally before adding the new weight to the other tally. Use one shared "last known vote" map to gate both `total_weight_approved` and `total_weight_rejected` updates so a signer's weight can only ever be counted toward its most recent, current vote.

### Proof of Concept
1. Node's `StackerDBListener` proposes block `B` to signer set with signer `S` (weight `w`) among others.
2. `S` sends `BlockResponse::Rejected` for `B` (e.g., transient/re-evaluable reason). The listener processes this via the reject branch at [4](#0-3) , adding `w` to `total_weight_rejected` and inserting `S`'s slot into `responded_signers`.
3. `S` re-evaluates (per the supported `LocallyRejected -> LocallyAccepted` transition) and sends `BlockResponse::Accepted` for `B`.
4. The listener processes this via the accept branch at [1](#0-0) ; since `gathered_signatures` does not yet contain `S`'s slot, `w` is added to `total_weight_approved` too. `total_weight_rejected` still includes `w` from step 2, permanently.
5. If enough other signers' weight independently reaches `total_weight_approved >= weight_threshold` while the leftover stale rejection weight (including `S`'s `w`) pushes `total_weight_rejected + weight_threshold > total_weight`, `wait_for_signer_signatures_or_timeout` in `signer_coordinator.rs` (checked in that order) returns `SignersRejected` [5](#0-4)  instead of `Ok`, even though the block currently has ≥70% approving weight under signers' present opinions.
