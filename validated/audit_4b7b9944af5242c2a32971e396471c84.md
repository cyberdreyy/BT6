## Analysis

Investigating the bug class — missing zero-address validation on an owner-restricted transfer function that permanently "burns"/locks the underlying asset — the closest reachable analog in marginfi-v2 is the `new_authority` parameter of `TransferToNewAccount` / `TransferToNewAccountPda`.

### Title
Missing zero-pubkey validation on `new_authority` in `transfer_to_new_account`/`transfer_to_new_account_pda` permanently locks migrated `MarginfiAccount` — ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
The account-migration instructions let the current, authorized signer of a `MarginfiAccount` move all of its lending state (deposits/borrows) to a brand-new account under an arbitrary `new_authority`. The `new_authority` account is explicitly documented as unchecked and no code path rejects `Pubkey::default()` (the system zero address) as the new authority, unlike the equivalent CLI helper which does perform this check client-side.

### Finding Description
`TransferToNewAccount` and `TransferToNewAccountPda` accept `new_authority` as a raw `UncheckedAccount`: [1](#0-0) [2](#0-1) 

That value is copied straight into the new account's authority field with no validation: [3](#0-2) 

`transfer_to_new_account` moves the old account's entire `lending_account` (positions) into the new account, disables the old account, and marks it migrated — an irreversible, one-way operation (`AccountAlreadyMigrated` guard prevents retry): [4](#0-3) 

If `new_authority == Pubkey::default()`, the resulting `MarginfiAccount` is permanently unauthorizable: no signer can ever match `Pubkey::default()`, so no future withdraw/repay/close instruction gated by `authority` signer checks can succeed for that account (the equivalent of transferring an NFT to `address(0)` in the referenced report). This is the same bug class as the CryptoPunksHelper finding: an owner-gated transfer/migration function lacking a zero-address check on the destination/new-authority parameter, enabling the value to be permanently stranded.

Notably, the off-chain CLI wrapper for the same instruction *does* guard against this: [5](#0-4) 
confirming the team recognizes zero-pubkey transfer as a hazard worth blocking, but the on-chain program itself — the only real security boundary — has no such check.

### Impact Explanation
Any position (deposits and/or borrows) held in a `MarginfiAccount` can be made permanently unmanageable by its own authorized signer (owner or authorized delegate per `is_signer_authorized`) setting `new_authority = Pubkey::default()`. Collateral in bank vaults tied to that account can no longer be withdrawn, repaid, or otherwise administered through the frozen account (outside of protocol-level flows like liquidation of unhealthy positions, which do not require the account authority's signature). For a healthy position, this constitutes a durable, self-triggered freeze of user funds with real financial effect, and — because the instruction is only gated by "is this account's current authorized signer," not by any check that prevents targeting the zero pubkey — it also opens the possibility of social-engineering/UI-bug scenarios (a malicious frontend or a delegate abusing scoped signing rights) tricking a legitimate signer into submitting a `new_authority = 0x0` transfer that looks like an ordinary migration.

### Likelihood Explanation
The instruction is a normal, permissionless (to the account's own authority) user-facing feature with no additional gating beyond the existing `is_signer_authorized`/`account_not_frozen_for_authority` checks; reaching the vulnerable code path requires only a single standard `TransferToNewAccount`/`TransferToNewAccountPda` call with `new_authority = Pubkey::default()`, no privileged role required.

### Recommendation
Add an explicit check in `transfer_to_new_account` and `transfer_to_new_account_pda` rejecting `new_authority == Pubkey::default()` (mirroring the check already present in the CLI at `p0-cli/src/processor/account.rs:1179-1181`), returning a dedicated error (e.g. `InvalidNewAuthority`) before any state mutation occurs.

### Proof of Concept
1. User creates `MarginfiAccount` A with `authority = alice`, deposits collateral, optionally borrows.
2. Alice (or an authorized delegate) calls `transfer_to_new_account` (or `_pda`) with `new_authority = Pubkey::default()`.
3. On-chain: `old_account.migrated_to` is set to the new account, `ACCOUNT_DISABLED` flag set on the old account, and `new_account.authority = Pubkey::default()` per `initialize_migrated_account`.
4. Any subsequent instruction requiring `authority` to sign for the new account (withdraw, repay, close balance, place/cancel orders, further transfer) fails permanently since no keypair can produce a valid signature for `Pubkey::default()`.
5. Collateral/borrow position in the new account is now unmanageable through any user-initiated instruction, replicating the "burn to zero address" impact described in the referenced report.
