### Title
Reentrancy window via Token-2022 transfer hooks in `drift_deposit` due to CPI-before-state-update ordering - (File: `programs/marginfi/src/instructions/drift/deposit.rs`)

### Summary
The AbraNFT finding describes an external call (`collateral.transferFrom`) executed before the contract updates its internal state in `_requestLoan`, allowing a malicious ERC721 `afterTokenTransfer` hook to reenter and manipulate state before the original call resumes. The equivalent bug-class root cause — performing external calls/CPIs before persisting internal accounting state, combined with a hook mechanism that can call back into the same program — is reachable in marginfi's `drift_deposit` instruction, which uses Token-2022-compatible transfer primitives (`transfer_checked`) and defers all `bank`/`marginfi_account` state updates until after the CPIs complete.

### Finding Description
In `drift_deposit` ( [1](#0-0) ), the flow is:
1. `bank` and `marginfi_account` are loaded immutably in a scoped block for validation only, then the `Ref` is dropped at the end of the block.
2. `cpi_update_spot_market_cumulative_interest`, `cpi_transfer_user_to_liquidity_vault` (a `transfer_checked` CPI using `TokenInterface`, i.e. Token-2022 compatible), and `cpi_drift_deposit` are executed — all **external calls** — while `bank` and `marginfi_account` are **not** held under a mutable `RefCell` borrow.
3. Only afterward does the code `load_mut()` the `bank` and `marginfi_account` and apply the actual accounting effects: `bank_account.deposit_no_repay(...)`, `record_deposit_inflow(...)`, `bank.update_bank_cache(...)`, and `marginfi_account.last_update`/`sync_indexer_flags()`.

Because `drift/deposit.rs` uses `anchor_spl::token_interface::{transfer_checked, TokenInterface}` (Token-2022 compatible types), a bank mint with an active Token-2022 `TransferHook` extension can specify an arbitrary hook program that is CPI'd into during the `transfer_checked` call. Since the `bank` and `marginfi_account` accounts are not held in a live mutable borrow at that point (the earlier scoped block already released them), a hook program that calls back into the marginfi program with the same `bank`/`marginfi_account` accounts would not be blocked by Anchor's `RefCell` re-borrow protection — unlike the standard `lending_account_deposit` path, which keeps `bank` and `marginfi_account` mutably borrowed for the entire duration of the SPL transfer CPI ( [2](#0-1) ), and unlike `lending_pool_emissions_deposit`, which explicitly rejects mints with active transfer hooks before transferring ( [3](#0-2) ).

I was unable to confirm from the index whether `drift_deposit`'s account validation (`validate_asset_tags`) or bank creation for Drift-tagged banks rejects Token-2022 mints with the `TransferHook` extension the way `lending_pool_emissions_deposit` does with `has_transfer_hook`/`nonzero_fee` checks — I could not retrieve the full account-validation struct for `DriftDeposit` due to a tool error in the final iteration, so this cannot be fully confirmed against production configuration.

### Impact Explanation
If a Drift-integration bank mint can be configured with (or upgraded to have) a Token-2022 transfer hook, and the hook program reenters the marginfi program mid-CPI (before the deposit accounting is committed), the attacker could execute a second instruction against the same `bank`/`marginfi_account` while the deposit's asset-share credit has not yet been recorded, potentially reading stale state or, depending on what else is reachable in that reentrant call, causing an inconsistent internal accounting state between the bank vault's actual token balance (already increased by the transfer) and the user's recorded share balance (not yet increased). This is a durable state-inconsistency risk with financial effect between the Drift bank's real value and marginfi's internal ledger.

### Likelihood Explanation
Exploitability depends entirely on whether a Drift-tagged bank's mint can be a Token-2022 mint with an enabled `TransferHook` extension, and whether the extra hook program is attacker-controlled (typically only possible for banks the admin permits/creates). If Drift-integration banks are restricted (e.g. via `validate_asset_tags`/bank creation checks) to hookless mints, likelihood is low to none. Given I could not verify this restriction in the available index, likelihood is uncertain but the code pattern itself (CPI-before-effects with no active RefCell lock) is a genuine deviation from the safer pattern used elsewhere in the codebase (`lending_account_deposit`, `lending_pool_emissions_deposit`).

### Recommendation
- Explicitly reject Token-2022 mints with an active `TransferHook` extension (and nonzero transfer fee) for all deposit/borrow/withdraw paths that perform CPI-based transfers before internal accounting is finalized, mirroring the `has_transfer_hook`/`nonzero_fee` checks already used in `lending_pool_emissions_deposit`.
- Alternatively, restructure `drift_deposit` (and equivalent Kamino integration flows) to record internal accounting state (or at least acquire and hold the `bank`/`marginfi_account` mutable borrows) before issuing the CPI transfer/deposit calls, consistent with the pattern already used in `lending_account_deposit`.

### Proof of Concept
Not independently reproduced; conceptual PoC based on code-path analysis:
1. Admin/attacker configures (or an existing) Drift-integration bank with a Token-2022 mint that has an active `TransferHook` extension pointing to an attacker-controlled hook program.
2. Attacker calls `drift_deposit`; `cpi_transfer_user_to_liquidity_vault` triggers `transfer_checked`, which CPIs into the attacker's hook program mid-transfer.
3. At this point, `bank`/`marginfi_account` are not held under any Anchor `RefCell` mutable borrow (both were released via block-scoping earlier in the function), so the hook program can construct and invoke a second marginfi instruction against the same `bank`/`marginfi_account` before `drift_deposit`'s own state-update block executes.
4. `drift_deposit` resumes and applies its own state update afterward, potentially compounding with the reentrant call's changes into an inconsistent state.

This PoC is unverified against a live devnet/test harness and depends on confirming that Drift-integration banks are not restricted from using transfer-hook mints — a restriction I could not conclusively find or rule out in the available index.

pub fn drift_deposit(ctx: Context<DriftDeposit>, amount: u64) -> MarginfiResult {
    let authority_bump: u8;
    let market_index: u16;
    {
        let marginfi_account = ctx.accounts.marginfi_account.load()?;
        let bank = ctx.accounts.bank.load()?;
        authority_bump = bank.liquidity_vault_authority_bump;

        validate_asset_tags(&bank, &marginfi_account)?;
        validate_bank_state(&bank, InstructionKind::FailsIfPausedOrReduceState)?;

        let integration_acc_1 = ctx.accounts.integration_acc_1.load()?;
        market_index = integration_acc_1.market_index;
    }

    ctx.accounts.cpi_update_spot_market_cumulative_interest()?;
    let expected_scaled_balance_change = ctx
        .accounts
        .integration_acc_1
        .load()?
        .get_scaled_balance_increment(amount)?;

    let initial_scaled_balance = {
        let integration_acc_2 = ctx.accounts.integration_acc_2.load()?;
        integration_acc_2.get_scaled_balance(market_index)
    };

    ctx.accounts.cpi_transfer_user_to_liquidity_vault(amount)?;
    ctx.accounts
        .cpi_drift_deposit(market_index, amount, authority_bump)?;

    let final_scaled_balance = {
        let integration_acc_2 = ctx.accounts.integration_acc_2.load()?;
        integration_acc_2.get_scaled_balance(market_index)
    };
    let scaled_balance_change = final_scaled_balance - initial_scaled_balance;
    require_eq!(
        scaled_balance_change,
        expected_scaled_balance_change,
        MarginfiError::DriftScaledBalanceMismatch
    );
