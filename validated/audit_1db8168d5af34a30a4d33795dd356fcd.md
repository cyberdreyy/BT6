### Title
ProgrammableBorrower `onStopEpoch` uses `convertToAssets` as liquidity coverage, so an illiquid ERC4626 vault permanently reverts `stopEpoch` instead of taking the default path - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
Analogous to CVE-2019-15297 (a declined response to a re-invite crashes on a NULL object), `onStopEpoch` assumes that an ERC4626 "accept" signal — `shortfall <= convertToAssets(shares)` — guarantees the follow-up `vault.withdraw` will succeed. In MetaMorpho-style vaults, `convertToAssets` counts lent-out (non-idle) assets, so `vault.withdraw` reverts, and the `catch` reverts `stopEpoch` with `StopEpochVaultLiquidityUnavailable` rather than letting the default path run. The epoch can never stop while the vault has no idle liquidity.

### Finding Description
In `ProgrammableBorrower.onStopEpoch`:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol:240-253
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
    uint256 shortfall = _amountRequired - onHand;
    // If the vault shares do not economically cover the shortfall, let IdleCDO's later
    // transferFrom fail and use the existing default path.
    if (shortfall > _currentVaultAssets()) return true;
    try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
        ...
    } catch {
        revert StopEpochVaultLiquidityUnavailable();
    }
}
```

`_currentVaultAssets()` is `vault.convertToAssets(shares)` (accounting value), not `vault.maxWithdraw(address(this))` (withdrawable liquidity). For Morpho MetaMorpho vaults, `totalAssets` includes assets supplied to markets whose liquidity is fully borrowed; `withdraw` then reverts (or is capped by withdrawal-queue/supply-cap logic) even though `convertToAssets` covers the shortfall. `IdleCDOEpochVariant._stopEpoch` deliberately lets this hook's revert bubble up ("Hook reverts bubble so transient ERC4626 liquidity failures can be retried", `contracts/IdleCDOEpochVariant.sol:395-404`), so `stopEpoch` reverts wholesale: `isEpochRunning` stays true, `epochEndDate` stays in the past, and no default is triggered. The mismatch is that the guard designed to route "economically uncovered" cases to the default path (`return true` → `transferFrom` fails → `_handleBorrowerDefault`) can never fire, because `convertToAssets` always reports coverage while `withdraw` always fails.

### Impact Explanation
A third-party user of the same ERC4626 vault (e.g., a borrower in the underlying Morpho markets) drains idle liquidity, which is normal market behavior, not malicious privileged access. From that point every `stopEpoch`/`stopEpochWithDuration` call reverts, so the epoch state machine is frozen: pending withdraw requests cannot be funded, interest cannot be settled, and close-pool recalls cannot execute. All LP funds are temporarily frozen for the entire duration of vault illiquidity — on a Morpho vault this can persist until borrowers repay, and curators may keep utilization near 100% indefinitely. Quantified loss: the full pool NAV (strategy-token balance + pending withdraws) is unrecoverable for the freeze duration, versus the intended behavior of falling into the borrower-default path which at least begins recovery accounting.

### Likelihood Explanation
Requires only that the configured ERC4626 vault's accounting value exceed its idle liquidity at `epochEndDate`, which is routine for high-utilization MetaMorpho vaults; no attacker transaction is even strictly needed, though any unprivileged vault depositor/borrower can induce it. The code itself acknowledges this branch exists (`StopEpochVaultLiquidityUnavailable`), but the coverage check defeats the designed escape hatch. The invariant harness (`test/foundry/ProgrammableBorrowerEpochInvariant.t.sol:318-323`) treats the revert as "retryable" — it is retryable only if liquidity returns, which is outside the protocol's control.

### Recommendation
Use `vault.maxWithdraw(address(this))` (or `maxRedeem` converted via `previewRedeem`) instead of `_currentVaultAssets()` when deciding coverage in `onStopEpoch`. If `shortfall > maxWithdraw`, return `true` so IdleCDO's `transferFrom` fails and `_handleBorrowerDefault` runs, rather than reverting. Alternatively, cap the attempted `withdraw` at `maxWithdraw` and let the shortfall trigger the default path.

### Proof of Concept
Foundry fork (e.g., `test/foundry/ProgrammableBorrowerCreditVault.t.sol` setup with `STEAKHOUSE_USDC` MetaMorpho vault):

```solidity
function testStopEpochStuckWhenVaultIlliquid() external {
    uint256 amount = 10_000 * oneScale;
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);          // idle cash parked into morphoVault

    // Attacker/unprivileged vault user: borrow or withdraw all idle liquidity
    // in the underlying Morpho markets (or deal/mock withdrawLimit on a mock vault).
    // Effect: convertToAssets(shares) still ~amount, but withdraw(shortfall) reverts.
    vault.setWithdrawLimit(0);             // mock equivalent: maxWithdraw = 0

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Epoch is frozen: retries revert identically, no default is triggered,
    // pending withdraw requests stay unfunded.
    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
}
```

With the real MetaMorpho vault, the same state is reached by a market borrower draining idle liquidity; `convertToAssets` still covers `shortfall`, `vault.withdraw` reverts inside the try, and the default path at `ProgrammableBorrower.sol:245` is never reached.
