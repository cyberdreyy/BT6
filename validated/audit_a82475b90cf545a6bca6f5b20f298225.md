### Title
Stale `order_execution_max_fee` allows keeper to extract more profit from a limit order than the user intended when placing it - ([File: programs/marginfi/src/instructions/marginfi_account/order.rs])

### Summary
Limit orders (`place_order`) let an unprivileged user lock in a take-profit/stop-loss trigger and a `max_slippage`, but they do **not** snapshot the global `order_execution_max_fee` parameter at order-creation time. When the order is later executed via `end_execute_order`, the program reads whatever the **current** value of `fee_state.order_execution_max_fee` is and uses it to compute the maximum amount of value a keeper may extract as profit. Because the global fee admin can change this parameter at any time between order placement and order execution, the user's actual outcome depends on a value they never agreed to and could not have known when they placed the order — the exact same "pre-fee vs. post-fee" staleness bug class as the referenced Backed Protocol finding.

### Finding Description
`place_order` creates an `Order` with a `trigger` (stop-loss/take-profit threshold) and `max_slippage`, but the order struct stores no fee snapshot: [1](#0-0) 

Later, `end_execute_order` loads the **current** global `FeeState` and derives `max_fee_frac` from `fee_state.order_execution_max_fee`: [2](#0-1) 

This `max_fee_frac` directly gates how much of the account's take-profit "start health" a keeper is allowed to withdraw as profit: [3](#0-2) 

The `order_execution_max_fee` field itself is mutable by the `global_fee_admin` at any time via `edit_global_fee_state` / `edit_fee_state`, independent of when any given order was placed: [4](#0-3) [5](#0-4) 

A user places a take-profit order believing that, at worst, a keeper can claim up to `order_execution_max_fee` (as it stood at placement time) of their unrealized profit. If the admin subsequently raises `order_execution_max_fee`, the constraint enforced at execution (`net >= allowed_diff` where `allowed_diff = start_health * (1 - max_fee)`) becomes looser, permitting the keeper to withdraw a larger share of the user's profit than the user could have anticipated or consented to — mirroring the referenced bug where a borrower's `minLoanAmount` was computed against a fee rate that could change before the loan was actually funded.

### Impact Explanation
This is a genuine value-redirection issue with financial effect: an unprivileged order-placer's realized proceeds on take-profit execution are determined by a parameter they cannot control and which is not fixed at the time they committed to the order. A raised `order_execution_max_fee` directly increases the amount a keeper (a permissionless, non-privileged executor) can extract from the user's position, reducing what the user actually receives relative to what was true — and what the user could reasonably have modeled — at order-placement time. This is the same medium-severity value-mismatch class as the referenced finding, just in the limit-order keeper-fee constraint rather than an origination fee on a loan.

### Likelihood Explanation
Requires the global fee admin to change `order_execution_max_fee` while orders are outstanding, which is a normal, expected admin action (fee parameters are documented as adjustable) rather than an attack requiring privilege escalation. Any user with a standing take-profit order is exposed for the entire time between placement and execution, and keepers have a natural incentive to maximize the executed profit share allowed by the current fee ceiling.

### Recommendation
Snapshot `order_execution_max_fee` (and/or `max_slippage`-relevant fee inputs) into the `Order` or `ExecuteOrderRecord` at `place_order` time, and use that stored value in `end_execute_order` rather than re-reading the live `FeeState`. This guarantees a user's realized outcome matches the fee terms they accepted when the order was created, consistent with the recommended mitigation in the referenced report (fixing the rate at action-initiation time rather than resolving it later).

### Proof of Concept
1. User deposits collateral, borrows against it, and calls `place_order` with a take-profit trigger and `max_slippage`, while `fee_state.order_execution_max_fee` = 1%.
2. Global fee admin calls `edit_global_fee_state` to raise `order_execution_max_fee` to, e.g., 10%.
3. A keeper triggers the order via `start_execute_order` / `end_execute_order`; `max_fee_frac` is computed from the now-10% fee, loosening the `allowed_diff` bound in the take-profit branch. [6](#0-5) 
4. The keeper withdraws up to the new, looser bound, leaving the user with materially less residual equity than they would have received under the fee rate in effect when they placed the order — with no recourse, since the order never recorded the fee rate the user relied on.

pub fn end_execute_order<'info>(ctx: Context<'info, EndExecuteOrder<'info>>) -> MarginfiResult {
    let EndExecuteOrder {
        marginfi_account: marginfi_account_loader,
        order: order_loader,
        execute_record: execute_record_loader,
        fee_state: fee_state_loader,
        ..
    } = &ctx.accounts;

    validate_not_cpi_by_stack_height()?;

    let mut marginfi_account = marginfi_account_loader.load_mut()?;
    let order = order_loader.load()?;
    let execute_record = execute_record_loader.load()?;
    let fee_state = fee_state_loader.load()?;

    let mut health_cache = HealthCache::zeroed();

    let (
        (order_assets_in_equity, _order_liabs_in_equity, _order_asset_count, order_liab_count),
        is_healthy,
    ) = {
        let (assets, liabs) = get_health_components(
            &marginfi_account,
            ctx.remaining_accounts,
            RequirementType::Maintenance,
            &mut Some(&mut health_cache),
            HealthPriceMode::Live { liq_cache: None },
        )?;

        let account_health = assets.checked_sub(liabs).ok_or_else(math_error!())?;

        let is_healthy = account_health >= I80F48::ZERO;

        health_cache.set_healthy(is_healthy);

        (
            get_tagged_account_health_components(
                &marginfi_account,
                ctx.remaining_accounts,
                &order.tags,
            )?,
            is_healthy,
        )
    };

    marginfi_account.health_cache = health_cache;

    check!(
        order_liab_count.eq(&0), // All order liabilities should be closed
        MarginfiError::OrderLiabilityNotClosed
    );

    let net = order_assets_in_equity;

    // The user slippage constraint we want to enforce is:
    // net >= (1 - slippage) * (tp or sl)
    // where slippage is encoded as a u32 percent (0..100% mapped to 0..u32::MAX).

    // For the TP case another constraint(the max fee constraint) we want to enforce is:
    // net >= (1 - max_fee) * (start health)
    // It may be possible that the value (1 - max_fee) * (start health) is less than the
    // min allowed value based on the user's slippage constraint alone, in that case
    // we clamp it to the slippage, allowing for that much.
    // In the case where the value was greater we use (1 - max_fee) * (start health) instead.

    // Check that the liquidator did not over-withdraw.

    let slippage_frac = {
        let slippage = marginfi_type_crate::types::u32_to_centi(order.max_slippage);
        I80F48::ONE
            .checked_sub(slippage)
            .ok_or_else(math_error!())?
    };

    let max_fee_frac = {
        let max_fee: I80F48 = fee_state.order_execution_max_fee.into();
        I80F48::ONE.checked_sub(max_fee).ok_or_else(math_error!())?
    };

    let start_health = || -> I80F48 { execute_record.order_start_health.into() };

    match order.trigger {
        OrderTriggerType::StopLoss => {
            let sl: I80F48 = order.stop_loss.into();
            let allowed_sl = sl.checked_mul(slippage_frac).ok_or_else(math_error!())?;

            check!(
                net >= allowed_sl,
                MarginfiError::OrderExecutionOverWithdrawal
            );
        }
        OrderTriggerType::TakeProfit => {
            let tp: I80F48 = order.take_profit.into();
            let allowed_tp = tp.checked_mul(slippage_frac).ok_or_else(math_error!())?;

            let allowed_diff = (start_health)()
                .checked_mul(max_fee_frac)
                .ok_or_else(math_error!())?;

            check!(
                net >= allowed_diff && net >= allowed_tp,
                MarginfiError::OrderExecutionOverWithdrawal
            );
        }
