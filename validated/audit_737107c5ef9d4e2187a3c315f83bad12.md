### Title
Contract-held withdrawal receipts can be permanently frozen because claims are bound to `msg.sender` - (File: `contracts/IdleCDOEpochVariant.sol`)

### Summary
`IdleCDOEpochVariant.claimWithdrawRequest()` and `claimInstantWithdrawRequest()` can only be executed by the receipt beneficiary itself because the beneficiary is always `msg.sender`. A smart-contract lender that supports deposits or withdrawal requests but does not expose the corresponding claim call cannot collect its funded underlyings. The receipt cannot be transferred to another account, and no relayer can claim on the contract’s behalf.

### Finding Description
A lender creates a receipt through `requestWithdraw()`, which forwards `msg.sender` as the receipt owner to `IdleCreditVault.requestWithdraw()` [1](#0-0) . After the receipt is funded, the lender must call `claimWithdrawRequest()` itself; the function has no beneficiary parameter and passes `msg.sender` to the vault [2](#0-1) . Instant withdrawals have the same caller-bound design [3](#0-2) .

The vault clears and pays only the supplied `_user`, while direct vault calls are restricted to the configured CDO [4](#0-3) . The funded claim is transferred to that same beneficiary address [5](#0-4) . Strategy-token receipts are also address-bound: their ERC20 transfer implementation permits transfers only when `msg.sender == idleCDO` [6](#0-5) .

Consequently, an immutable lender contract that exposes `depositAA()`/`depositBB()` and `requestWithdraw()` but omits a claim forwarding function becomes unable to obtain the underlying after funding. Any external relayer calling `claimWithdrawRequest()` is treated as the relayer, not as the beneficiary, and cannot trigger the victim’s payout.

### Impact Explanation
The full amount represented by the contract-owned receipt can remain locked indefinitely. This affects both funded normal withdrawals and funded instant withdrawals, including balances isolated after default recovery. For example, if an immutable lender requests `1,000,000` underlying tokens and the request later becomes fully funded, the entire `1,000,000` remains in `IdleCreditVault` because no transaction can make the CDO’s `msg.sender` equal the lender contract unless the lender already exposes that call.

Administrative `transferToken()` rescue may recover funds if an owner chooses to intervene, but there is no permissionless or beneficiary-controlled recovery path [7](#0-6) .

### Likelihood Explanation
The issue requires a contract-based lender or account abstraction wallet to possess withdrawal receipts while lacking a forwarding method for the relevant claim function. Such contracts are plausible beneficiaries because tranche positions can be held by smart contracts, while the receipt design prevents them from transferring the claim to an EOA or another operational contract. No malicious privileged action, market condition, oracle failure, or borrower default is required after the receipt has been funded.

### Recommendation
Add beneficiary-preserving claim functions to `IdleCDOEpochVariant`, for example:

```solidity
function claimWithdrawRequestFor(address _user) external {
    IdleCreditVault(strategy).claimWithdrawRequest(_user);
}

function claimInstantWithdrawRequestFor(address _user) external {
    _checkNotAllowed(!allowInstantWithdraw);
    IdleCreditVault(strategy).claimInstantWithdrawRequest(_user);
}
```

These functions should continue paying only `_user`; they merely allow anyone to execute the payout. Alternatively, make withdrawal receipts transferable so an incapable contract can delegate the claim, although that would be a broader accounting change.

### Proof of Concept
A Foundry fork test can reproduce the freeze using an immutable lender that exposes deposit and request functions but no claim function:

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";

contract ImmutableLender {
    function request(address cdo, uint256 amount, address tranche) external {
        IdleCDOEpochVariant(cdo).requestWithdraw(amount, tranche);
    }
}

contract ContractBeneficiaryClaimFreezeTest is Test {
    function test_contractReceiptCannotBeClaimedByRelayer() public {
        // Fork a deployment containing:
        // - IdleCDOEpochVariant cdo
        // - underlying token
        // - an approved/KYC-passing ImmutableLender with tranche tokens
        IdleCDOEpochVariant cdo = IdleCDOEpochVariant(address(0)); // fork deployment
        address aa = address(0);                                   // cdo.AATranche()
        IERC20 underlying = IERC20(address(0));                    // cdo.token()
        ImmutableLender lender = new ImmutableLender();
        address relayer = makeAddr("relayer");

        // 1. Give the immutable lender tranche tokens during deployment setup.
        // 2. The lender creates a withdrawal receipt.
        lender.request(address(cdo), 0, aa);

        // 3. Advance/settle the epoch through the normal honest manager flow
        // so lender's receipt is fully funded in IdleCreditVault.

        uint256 lenderBefore = underlying.balanceOf(address(lender));
        uint256 relayerBefore = underlying.balanceOf(relayer);

        // 4. A relayer cannot claim for the contract: the CDO uses msg.sender
        // as the receipt owner, so this only attempts relayer's own claim.
        vm.prank(relayer);
        cdo.claimWithdrawRequest();

        assertEq(underlying.balanceOf(address(lender)), lenderBefore);
        assertEq(underlying.balanceOf(relayer), relayerBefore);

        // 5. The funded claim remains assigned to ImmutableLender, but no
        // transaction can originate from that immutable contract because it
        // does not implement a claimWithdrawRequest() forwarding function.
        // Its strategy-token receipt also cannot be transferred to a helper.
    }
}
```

The invariant violated is “one funded receipt, one beneficiary-payable payout”: the payout accounting exists and is funded, but the protocol makes its execution impossible unless the beneficiary contract happened to implement the exact claim call.

  /// @notice Transfer a funded claim without spending default recovery reserve.
  /// @param _user claim receiver
  /// @param _amount amount to transfer
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
