### Title
Lockup Factory Lets the Future Lockup Owner Supply Their Own Staking-Pool Whitelist, Allowing Early Release of Locked/Unvested Tokens - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` accepts an optional, caller-supplied `whitelist_account_id` that is written directly into the deployed lockup contract's `staking_pool_whitelist_account_id` field, with no check that it matches the factory's foundation-approved whitelist. Because the lockup contract's entire "safe staking" guarantee rests on that whitelist being trustworthy, an owner can point their own lockup at a whitelist contract they control, get an attacker-owned account "approved" as a staking pool, and then use `deposit_to_staking_pool` / `deposit_and_stake` to move locked/unvested NEAR out of lockup custody to that account — releasing tokens the lockup and vesting schedule are supposed to keep frozen.

### Finding Description
The lockup contract documents and enforces a specific trust boundary: the owner may delegate locked/unvested tokens to a staking pool, but only if that pool has been vetted through the whitelist contract, because "the staking pool contract and the account have to be approved by the whitelisting contract to prevent tokens from being lost, locked, or stolen" [1](#0-0) .

`select_staking_pool` enforces this by querying `self.staking_pool_whitelist_account_id` before accepting a pool: [2](#0-1) 

`staking_pool_whitelist_account_id` is not fixed by the foundation-controlled factory config; instead `create()` lets the caller override it via the `whitelist_account_id` parameter, defaulting only when omitted: [3](#0-2) 

There is no assertion that the supplied `whitelist_account_id` equals `self.whitelist_account_id` (the one set at factory `new()`) or is itself whitelisted/approved in any way — any syntactically valid account ID is accepted and baked into the new lockup's `LockupArgs`. The test suite even documents this as intended behavior (`test_create_lockup_with_custom_whitelist_success`): [4](#0-3) 

Once the lockup is live with an attacker-controlled whitelist, `select_staking_pool` will faithfully call `is_whitelisted` on that contract, get `true` for any account the attacker names, and store it as the trusted staking pool: [5](#0-4) 

The owner can then call `deposit_to_staking_pool`/`deposit_and_stake`, which transfer real NEAR (including locked/unvested balance, per design) out of the lockup account to the "staking pool" account, bounded only by the lockup's total account balance, not by the unlocked/vested portion: [6](#0-5) [7](#0-6) 

Because the "staking pool" destination is an ordinary account fully controlled by the attacker (not a real staking-pool contract bound by the pool spec), the funds are simply gone from the lockup's custody — there is no obligation or mechanism forcing them back. This breaks the custody equality the whitelist is meant to guarantee: `NEAR sent to staking_pool_account_id == NEAR recoverable by the lockup owner through legitimate unstake/withdraw flows`. With a self-supplied whitelist, the right-hand side collapses to "whatever the attacker chooses," which for locked/unvested balance should have been 0 until the schedule allowed it.

### Impact Explanation
This is a Critical finding: locked or unvested tokens are released early. The lockup contract's own stated guarantee — "The owner can not withdraw tokens locked due to lockup period, disabled transfers, or vesting schedule" [8](#0-7)  — is voided whenever the owner is allowed to pick their own staking-pool whitelist, because staking is explicitly permitted to move locked/unvested tokens under the assumption the whitelist enforces safe return.

### Likelihood Explanation
`create()` is a public, permissionless, `#[payable]` method; any caller can invoke it and supply `whitelist_account_id`. Deploying a trivial whitelist contract (`is_whitelisted` returning `true` unconditionally) and a plain destination account requires no special privilege, foundation key, or social engineering — only the minimum attached deposit already required to create a lockup. This is directly exploitable by any user who wants to create a lockup for themselves (e.g., to make locked/vesting tokens appear compliant while retaining full access).

### Recommendation
`LockupFactory::create` should not accept an arbitrary `whitelist_account_id` from the caller. Either remove the parameter entirely and always use `self.whitelist_account_id` set at factory initialization, or, if flexibility is required, restrict acceptable values to a foundation-maintained allow-list (mirroring the factory-whitelist pattern already used in `whitelist/src/lib.rs`) so a lockup can never be deployed with a whitelist the owner controls.

### Proof of Concept
1. Attacker deploys a minimal contract `fake_whitelist.<attacker>` exposing `is_whitelisted(staking_pool_account_id: AccountId) -> bool { true }`.
2. Attacker calls `lockup_factory.create(owner_account_id: attacker, lockup_duration/vesting_schedule: <long lock>, whitelist_account_id: Some("fake_whitelist.<attacker>"), ...)` with the required attached deposit (large amount, e.g., all NEAR intended to be locked/vested) — see `lockup-factory/src/lib.rs` lines 107-133.
3. The deployed lockup's `staking_pool_whitelist_account_id` is now `fake_whitelist.<attacker>`.
4. Attacker (as owner) calls `select_staking_pool("drain.<attacker>")` where `drain.<attacker>` is a plain account attacker controls. `is_whitelisted` returns `true`, and `on_whitelist_is_whitelisted` stores it as the trusted staking pool — `lockup/src/owner.rs` lines 12-41, `lockup/src/owner_callbacks.rs` lines 6-25.
5. Attacker calls `deposit_and_stake(amount)` (or `deposit_to_staking_pool`) with `amount` up to `get_account_balance()`, transferring locked/unvested NEAR directly to `drain.<attacker>` — `lockup/src/owner.rs` lines 81-166.
6. Attacker now holds the NEAR in `drain.<attacker>`, a normal account under their sole control, fully bypassing the lockup duration/vesting schedule that was supposed to keep those tokens frozen.

    pub fn deposit_to_staking_pool(&mut self, amount: WrappedBalance) -> Promise {
        self.assert_owner();
        assert!(amount.0 > 0, "Amount should be positive");
        self.assert_staking_pool_is_idle();
        self.assert_no_termination();
        assert!(
            self.get_account_balance().0 >= amount.0,
            "The balance that can be deposited to the staking pool is lower than the extra amount"
        );

        env::log(
            format!(
                "Depositing {} to the staking pool @{}",
                amount.0,
                self.staking_information
                    .as_ref()
                    .unwrap()
                    .staking_pool_account_id
            )
            .as_bytes(),
        );

        self.set_staking_pool_status(TransactionStatus::Busy);

        ext_staking_pool::deposit(
            &self
                .staking_information
                .as_ref()
                .unwrap()
                .staking_pool_account_id,
            amount.0,
            gas::staking_pool::DEPOSIT,
        )
        .then(ext_self_owner::on_staking_pool_deposit(
            amount,
            &env::current_account_id(),
            NO_DEPOSIT,
            gas::owner_callbacks::ON_STAKING_POOL_DEPOSIT,
        ))
    }

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

    /// Called after a given `staking_pool_account_id` was checked in the whitelist.
    pub fn on_whitelist_is_whitelisted(
        &mut self,
        #[callback] is_whitelisted: bool,
        staking_pool_account_id: AccountId,
    ) -> bool {
        assert_self();
        assert!(
            is_whitelisted,
            "The given staking pool account ID is not whitelisted"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();
        self.staking_information = Some(StakingInformation {
            staking_pool_account_id,
            status: TransactionStatus::Idle,
            deposit_amount: 0.into(),
        });
        true
    }
