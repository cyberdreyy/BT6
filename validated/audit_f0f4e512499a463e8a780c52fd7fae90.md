### Title
Loss-adjusted withdrawal haircut stored under the wrong epoch index lets pending receipts claim at par — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`collectWithdrawFunds` records a realized stop-epoch loss as `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` is a mutable counter that is incremented inside `deposit()` whenever a deposit lands while `isEpochRunning()` is true. If the borrower's repayment deposit during `stopEpoch`/`stopEpochWithDuration` executes before `collectWithdrawFunds`, the haircut is written to the *next* epoch slot while every affected receipt's `lastWithdrawRequest` still points at the pre-stop epoch. The guard and the loss-adjusted claim path then read a zero price and the receipts are paid in full from a pot that was sized for the haircut — a multi-write/aliasing flaw directly analogous to the CVE's repeated same-slot buffer attachments producing an out-of-bounds write.

### Finding Description
The bug-class analog is "multiple writes to a slot keyed by an index that moved between the write and the read":

- `requestWithdraw` tags each receipt with `currentEpoch = epochNumber` (`lastWithdrawRequest[_user] = currentEpoch`) and rejects new requests only when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` is non-zero (`IdleCreditVault.sol:259-271`).
- `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and applies the haircut (`IdleCreditVault.sol:789-800`).
- `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber]` — the *live* counter — and zeroes `pendingWithdraws` (`IdleCreditVault.sol:411-430`).
- `deposit()` increments `epochNumber` when called while `IIdleCDOEpochVariant(idleCDO).isEpochRunning()` is still true, i.e., inside `stopEpoch` (`IdleCreditVault.sol:607-610`).

If the epoch-flow calls `deposit` (borrower repayment / `_depositToVault`) before `collectWithdrawFunds`, the haircut lands under `epochNumber+1` while receipts carry `lastWithdrawRequest = epochNumber`. Two consequences:

1. The re-request guard at line 263-271 reads `lossRecoveryPriceByEpoch[N] == 0`, so an attacker holding a haircutted receipt can open a new request immediately, moving `lastWithdrawRequest` forward and permanently orphaning the haircut.
2. More importantly, `_claimLossAdjustedWithdrawRequest` returns 0 and execution falls through to `_claimFundedWithdrawRequest`, which only requires `epochNumber > lastWithdrawRequest[_user]` — true right after the stop — and pays `withdrawsRequests[_user]` at par (`IdleCreditVault.sol:326-349`). `pendingWithdraws` was already zeroed in `collectWithdrawFunds`, so the vault pays out more underlyings than it collected: the difference is taken from other users' funded claims / the strategy's skimmed balance.

Caveat: the exploit requires `collectWithdrawFunds` to run after the epoch-bumping `deposit` within `stopEpochWithDuration`. I was unable to read the call ordering inside `IdleCDOEpochVariant.stopEpoch`/`_afterStopEpochWithDuration` (grep returned match counts only, not contents), so that ordering is the unverified precondition.

### Impact Explanation
Direct theft / insolvency: pending receipts escape a realized loss haircut and are paid at par from under-funded vault reserves, leaving a shortfall borne by the last claimers (permanent freezing of their claims) and breaking the loss-waterfall invariant that pending receipts share `stopEpochWithDuration` losses pro rata (`previewLossAdjustedWithdrawFunds`). Loss equals `pendingBasis - fundedAmount` of the defaulted epoch.

### Likelihood Explanation
Trigger requires a `stopEpochWithDuration` with a loss and non-zero `pendingWithdraws`, plus the deposit-before-collect ordering — both reachable by honest manager/borrower calls; the attacker is any unprivileged tranche holder with a pending receipt. No privileged misbehavior needed.

### Recommendation
Freeze the epoch index used for the haircut: in `collectWithdrawFunds`, write `lossRecoveryPriceByEpoch` under the epoch the receipts were requested in (e.g., capture the epoch before `deposit` increments it, or pass the request epoch explicitly from the CDO). Alternatively, have `requestWithdraw`/`_claimLossAdjustedWithdrawRequest` consult both `lastWithdrawRequest` and `epochNumber` slots, or set a dedicated `pendingLossEpoch` during `stopEpoch` before any accounting call can bump the counter.

### Proof of Concept
```solidity
// Foundry fork PoC (sketch — assumes collectWithdrawFunds runs after the
// epoch-bumping deposit inside stopEpochWithDuration)
function testLossReceiptClaimsAtPar() public {
    // 1. Attacker deposits into AA, epoch starts (epochNumber = N).
    cdoEpoch.depositAA(100_000e6);
    _startEpoch();

    // 2. During epoch N, attacker requests withdraw of 50_000e6.
    //    lastWithdrawRequest[attacker] = N, pendingWithdraws = 50_000e6.
    cdoEpoch.requestWithdraw(50_000e6, AAtranche);

    // 3. Epoch ends with a realized loss: borrower funds only half the
    //    pending basis. Inside stopEpochWithDuration the repayment deposit
    //    increments epochNumber to N+1 BEFORE collectWithdrawFunds runs.
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, loss); // partial funding
    // => lossRecoveryPriceByEpoch[N+1] = 0.5e18 ; slot N stays 0.

    // 4. Attacker claims immediately: _claimLossAdjustedWithdrawRequest
    //    reads price 0 for epoch N and skips; _claimFundedWithdrawRequest
    //    passes since epochNumber (N+1) > lastWithdrawRequest (N).
    uint256 balBefore = underlying.balanceOf(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 claimed = underlying.balanceOf(attacker) - balBefore;

    // 5. Attacker received full 50_000e6 although only ~25_000e6 was funded.
    assertEq(claimed, 50_000e6);
    // Vault is now short ~25_000e6 vs remaining claimers.
}
```
