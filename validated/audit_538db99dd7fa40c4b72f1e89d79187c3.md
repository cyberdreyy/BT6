### Title
Kubernetes terminal `Close()` is a no-op, so job cancellation does not terminate the live terminal websocket - ([File: executors/kubernetes/terminal.go])

### Summary
The kubernetes `terminalConn.Close()` in `executors/kubernetes/terminal.go` does nothing, unlike the docker executor's equivalent which cancels the exec context. Combined with `TerminalSettings.MaxSessionTime` being hardcoded to `0`, the job-cancellation path (`ctx.Done()` in `waitForTerminal`) has no mechanism to actually sever the running `kube exec` websocket, leaving the pod's terminal session open after the job's declared lifecycle should have ended.

### Finding Description
`common.Build.waitForTerminal` (common/build.go:1371-1411) enforces terminal lifetime via three paths: [1](#0-0) 
- `ctx.Done()` → calls `b.Session.Kill()` only.
- `time.After(timeout)` → sends error to `b.Session.TimeoutCh`.
- `b.SystemInterrupt` → calls `b.Session.Kill()`.

`Session.Kill()` (session/session.go:263-275) only calls `s.terminalConn.Close()`: [2](#0-1) 

For the kubernetes executor, `terminalConn.Close()` is a stub that returns `nil` and performs no action: [3](#0-2) 

Compare this to the docker executor, where `Close()` actually calls `t.cancelFn()` to cancel the exec's context and terminate the underlying stream: [4](#0-3) 

The only other way to stop an in-flight terminal proxy is via `TimeoutCh` or `DisconnectCh`, which feed into `ProxyTerminal`'s `proxyStopCh`: [5](#0-4) 

But `ctx.Done()` (build cancellation/timeout via context) never writes to `TimeoutCh` — only the separate `time.After(timeout)` branch does. So when a job is cancelled through its context (not through the terminal-specific timer), `waitForTerminal` returns immediately after calling the no-op `Kill()`, while the actual HTTP handler goroutine running `terminalConn.Start` → `ProxyTerminal` → `terminal.ProxyWebSocket(w, r, t.settings, wsProxy)` keeps running untouched, continuing to relay bytes between the client and the pod's `kube exec` (`bash || sh`) session in the `build` container. Since `MaxSessionTime` is hardcoded to `0`, the third-party `gitlab-terminal` library also imposes no independent cutoff.

Existing protections (session token auth in `withAuthorization`, exec-only-if-websocket-upgrade checks) only gate the initial connection; none of them re-validate or terminate an already-established, in-progress exec stream when the job's context is cancelled.

### Impact Explanation
A pipeline author who opens the interactive web terminal for a Kubernetes-executor job (this is a supported, user-triggerable GitLab feature) and whose job is then cancelled or times out via its `ctx` can continue to hold and use the open `kube exec` websocket against the still-running `build` container. During this window they can read/exfiltrate CI/CD variables, masked secrets present in the container's environment or filesystem, or otherwise continue arbitrary command execution in a container that should have been torn down when the job ended — directly contradicting the "confined to its own session" invariant. The exposure window's real-world size depends on how quickly the kubernetes executor's own pod-cleanup logic deletes the pod (which would eventually cause the apiserver connection to fail), but there is no explicit, deterministic enforcement of "the terminal must die when the job's context is cancelled" for this executor, unlike for docker.

### Likelihood Explanation
Preconditions are low-privilege and easily reachable: any pipeline author who can open a web terminal on a Kubernetes-executor job (a standard, documented feature) can trigger this by opening the terminal and then letting/forcing the job to be cancelled or hit its script/job timeout while the terminal stays connected. No cluster-admin or privileged container settings are required. The bug is deterministic given the code path (`ctx.Done()` → `Kill()` → no-op `Close()`), reproducible in a unit test using the existing `TestWaitForTerminal` harness pattern with a kubernetes-style mock `Conn`.

### Recommendation
Make `executors/kubernetes/terminal.go`'s `terminalConn.Close()` actually terminate the exec session — e.g., store the `context.CancelFunc` for the exec request (mirroring the docker executor's pattern) and cancel it in `Close()`, and/or set `TerminalSettings.MaxSessionTime` from `common.Config.SessionServer.SessionTimeout` so the underlying `gitlab-terminal` library enforces an upper bound independent of the outer session wiring. Additionally, ensure `waitForTerminal`'s `ctx.Done()` branch also feeds `TimeoutCh`/`proxyStopCh` so all executors' `ProxyTerminal` invocations are forced to stop, not just rely on each executor's `Close()` implementation.

func (s *Session) Kill() error {
	s.lock.Lock()
	defer s.lock.Unlock()

	if s.terminalConn == nil {
		return nil
	}

	err := s.terminalConn.Close()
	s.terminalConn = nil

	return err
}

func ProxyTerminal(timeoutCh, disconnectCh, proxyStopCh chan error, proxyFunc func()) {
	disconnected := make(chan bool, 1)
	// terminal exit handler
	go func() {
		// wait for either session timeout or disconnection from the client
		select {
		case err := <-timeoutCh:
			proxyStopCh <- err
		case <-disconnected:
			// forward the disconnection event if there is any waiting receiver
			nonBlockingSend(
				disconnectCh,
				errors.New("finished proxying (client disconnected?)"),
			)
		}
	}()

	proxyFunc()
	disconnected <- true
}
