### Title
Gateway HTTP-action response cache is not workflow-scoped despite being documented and named as such - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's `responseCache` for outbound HTTP Action capability requests is documented and named as providing "workflow-scoped caching" and "workflow isolation to prevent cross-workflow data leakage," but its cache key (`OutboundHTTPRequest.Hash()`) does not actually incorporate the `WorkflowID`. This is the same class of bug as the external report: a "safe"-named mechanism (`safeTransferMany`) that skips the safety property (`_safeTransfer`) its name promises. Here, a "workflow-isolated" cache skips the isolation property (including `WorkflowID` in the key) its name and docs promise.

### Finding Description
`core/services/gateway/handlers/capabilities/v2/README.md` explicitly states the caching contract: [1](#0-0) 

And the `responseCache` type itself is documented as being keyed on `(method, URL, headers, body, workflowOwner)`: [2](#0-1) 

The cache's `Fetch` and `Set` operations both key strictly on `req.Hash()`: [3](#0-2) [4](#0-3) 

The unit tests for `Hash()` confirm that the `WorkflowID` field is explicitly excluded from the hash, while only `WorkflowOwner` (not per-workflow) differentiates cache entries: [5](#0-4) [6](#0-5) 

So, despite the interface comment ("Caches HTTP responses to avoid redundant outbound requests... Workflow-scoped caching") and README claim ("Cache Key: Generated from workflow ID and request hash" / "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage"), the actual implementation only isolates by `WorkflowOwner`, not by individual `WorkflowID`.

### Impact Explanation
Any two different workflows belonging to the same `WorkflowOwner` (a legitimate, unprivileged scenario — a single owner can deploy multiple distinct workflows) that issue an outbound HTTP Action to the same URL/method/headers/body will share one cache entry. If Workflow A stores a cacheable response (2xx/4xx, `CacheSettings.Store=true`), a subsequent request from a completely different Workflow B (same owner, different code/purpose/trust boundary) can receive Workflow A's cached response via `CacheSettings.MaxAgeMs` reads — this is exactly the "cross-user response confusion" class called out as in-scope, except here the confusion crosses distinct workflows rather than distinct users. This can leak data intended for one workflow into another, or cause a workflow to act on stale/foreign response data it never requested, undermining the "Workflow Isolation" guarantee the code claims to enforce.

### Likelihood Explanation
This does not require a malicious node or network-layer attacker — it is reachable purely through the normal, unprivileged HTTP Action capability flow: any workflow (owned by the same address as another) making an outbound HTTP call with `CacheSettings.Store=true`/`MaxAgeMs>0` triggers this behavior. Multi-workflow-per-owner deployments are a standard, expected usage pattern (the CRE model), making collision realistic rather than a hypothetical edge case.

### Recommendation
Include `WorkflowID` (not just `WorkflowOwner`) in the `OutboundHTTPRequest.Hash()` computation used as the cache key, so that cache entries are truly workflow-scoped as documented. Update `response_cache.go`'s doc comment and the README to accurately reflect the corrected isolation boundary, and add a regression test asserting that different `WorkflowID`s (even under the same owner) produce different hashes/cache keys.

### Proof of Concept
Using the existing test harness in `response_cache_test.go`:
1. Build `req1` with `WorkflowOwner = "0xOwner"`, `WorkflowID = "workflow-A"`, method/URL/body identical to `req2`.
2. Build `req2` with `WorkflowOwner = "0xOwner"`, `WorkflowID = "workflow-B"` (different workflow, same owner), same method/URL/body.
3. Call `cache.Set(req1, respA)` where `respA` contains data specific to workflow A.
4. Call `cache.Fetch(ctx, req2, fetchFnForB, true)` with `req2.CacheSettings.MaxAgeMs > 0`.
5. Observe that `Fetch` returns `respA` (workflow A's cached response) to workflow B's request instead of invoking `fetchFnForB`, because `req1.Hash() == req2.Hash()` per the existing `TestRequestHash` test at [5](#0-4) .

```go
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
```

```go
// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
```
