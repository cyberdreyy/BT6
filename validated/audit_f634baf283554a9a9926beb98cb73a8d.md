### Title
Unbounded disk consumption during tar+zstd cache/artifact extraction with only inter-header cancellation checks - (File: commands/helpers/archive/tarzstd/tarzstd_extractor.go)

### Summary
`extractor.Extract` decompresses attacker-supplied zstd+tar content and writes each regular file with a single unbounded `io.Copy(f, tr)` call, with no cap on decompressed size and no context check during the copy itself. `ctx.Err()` is only checked once per tar header before the file body is written, so a single tar entry with a huge/zip-bomb payload can consume arbitrary disk space before cancellation is ever observed.

### Finding Description
In `Extract` [1](#0-0) , a zstd reader is created with only `zstd.WithDecoderLowmem(true)`, which bounds decoder memory, not output size, and the tar stream is read entry-by-entry. The only cancellation check is a one-shot `ctx.Err()` test performed before each entry's contents are written [2](#0-1) . For regular files, the body is written with a single blocking `io.Copy(f, tr)` that has no `io.LimitReader`, no byte cap, and does not observe `ctx` at all [3](#0-2) . A crafted zstd stream can therefore expand into an effectively unbounded number of bytes for one tar entry (a classic decompression bomb), and neither the tar header's declared `Size` nor any disk-quota check is validated before or during the copy — there's no equivalent of `archive.MaxUploadedArchiveSize` for the extraction path.

Notably, in the only production caller found, `commands/helpers/cache_extractor.go`, extraction is invoked as `extractor.Extract(context.Background())` [4](#0-3) , a context that is never cancelled, so the `ctx.Err()` check is dead code in this path regardless of the io.Copy issue — cancellation isn't wired to job timeout/abort signals here at all. I was not able to fully trace whether any other caller (e.g., artifacts extraction with a job-scoped cancellable context) passes a real cancellable context into this extractor; that would need further verification in a Devin session with full-repo access, since the index only exposes the `cache_extractor.go` call site.

### Impact Explanation
An attacker who controls a cache/artifact archive (any pipeline author supplying a `tarzstd`-compressed cache, since `CACHE_COMPRESSION_FORMAT=tarzstd` is a user-settable job variable per `docs/configuration/advanced-configuration.md`) can submit a small compressed file that decompresses into a very large regular file, filling the shared runner's disk (`e.dir`, the build/cache directory) before extraction can be aborted. On a shared runner host, this can exhaust disk space used by other concurrently running jobs/caches, causing job failures for unrelated tenants — a real cross-job denial-of-service via disk exhaustion, not just self-inflicted job failure.

### Likelihood Explanation
Feasibility is moderate-to-high in principle: an unprivileged pipeline author can set `CACHE_COMPRESSION_FORMAT: tarzstd` and control the cache content that is later uploaded and downloaded by the runner's `cache-extractor` helper. However, the concrete severity is reduced in the traced call path because `cache_extractor.go` extracts with `context.Background()`, meaning there is no cancellation mechanism to bypass at all in that specific flow — the bug (no size cap) is real, but the "ctx cancellation is defeated" framing only matters if a cancellable context is used elsewhere, which I could not confirm from available context.

### Recommendation
- Enforce a maximum decompressed/extracted size (e.g., via `io.LimitReader` sized from a configurable quota, or track cumulative bytes across all entries and abort when exceeded) before/while calling `io.Copy` at line 93.
- Replace the plain `io.Copy(f, tr)` with a context-aware copy (e.g., wrap `tr` with a reader that checks `ctx.Done()` periodically, or use `io.CopyN` in bounded chunks with an `ctx.Err()` check between chunks) so a single large entry can be interrupted promptly.
- Wire a real cancellable/timeout context into `cache_extractor.go`'s `extractor.Extract(...)` call instead of `context.Background()`.

### Proof of Concept
Go test plan (`tarzstd_extractor_test.go`):
1. Build a crafted archive: a zstd stream (constructed with `zstd.NewWriter`) whose tar entry declares `Size` large (e.g., several GB of highly compressible zeros) but whose compressed size is a few KB.
2. Call `NewExtractor(r, size, tmpDir).Extract(ctx)` with `ctx` cancelled shortly after start (`context.WithTimeout(context.Background(), 100*time.Millisecond)`).
3. Assert: (a) `Extract` returns `ctx.Err()` (or a quota-exceeded error) well before the full decompressed payload is written, and (b) `du`/`os.Stat` on the extracted file shows bytes written are bounded (e.g., under a configured limit), not the full multi-GB payload — currently this assertion fails, demonstrating unbounded disk writes prior to any fix.
