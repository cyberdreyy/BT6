Let me confirm the exact semantics of `get_globally_accepted_block_count_in_tenure` and how `mark_globally_accepted`/`mark_locally_accepted` differ, to nail down the gap precisely.## Finding: The reorg-permit check that suppresses the double-sign guard trusts node-processed tenure state, not signed state — a single miner can force a signer to sign two conflicting blocks

### Summary

`SortitionData::check_parent_tenure_choice` decides whether a miner is allowed to reorg a prior tenure, and — critically — if it approves the reorg it calls `record_superseded_tenure`/`mark_tenure_superseded`, which later causes `reorg_permit_stands` to **exclude** any of this signer's own prior signatures over that tenure from the double-sign conflict guard in `handle_block_pre_commit`. The veto that is supposed to prevent this override ("disallow reorg if more than one block has already been signed") is implemented using `get_globally_accepted_block_count_in_tenure` and the node-reported `first_block_mined`/`nakamoto_blocks` field — both of which reflect only what the local **stacks-node** has already processed into its own chainstate, not what the **signer** has actually put a signature over.

### Finding Description

`check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs:170-295`) is invoked from `validate_tenure_change_payload` (v1: `stacks-signer/src/chainstate/v1.rs:497-504`, v2: analogous code path) whenever a miner's tenure-change block does not build off the last-known sortition — i.e., a reorg attempt.

The veto against reorging a tenure that already produced signed blocks is:
```rust
// disallow reorg if more than one block has already been signed
let globally_accepted_blocks =
    signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)?;
if globally_accepted_blocks > 1 {
    ...
    return Ok(false);
}
``` [1](#0-0) 

`get_globally_accepted_block_count_in_tenure` counts only rows whose `BlockState == GloballyAccepted`. The `has_signed_block()` and `check_globally_signed_block_count()` unit tests explicitly confirm a `LocallyAccepted` (signed, 70%-threshold-reached, self- or group-signed) block does **not** count here: [2](#0-1) 

`GloballyAccepted` is only reached "IFF we receive a new block event confirming it OR see the chain tip of the node advance to it" — a purely local, asynchronous event driven by this signer's own node catching up on block processing: [3](#0-2) 

The subsequent branch for the (now common, since the ">1" check undercounts) case of ≤1 globally-accepted block relies on the node-reported `first_block_mined` from `get_tenure_forking_info`, which is populated straight from the node's own on-disk chainstate (`NakamotoChainState::get_nakamoto_tenure_start_block_header`), not from anything the signer set has cryptographically signed: [4](#0-3) 

If that field is `None` (the node has not yet processed/stored any block for that tenure), the code takes the fast-path and unconditionally supersedes the tenure:
```rust
let Some(first_block_mined) = &tenure.first_block_mined else {
    // The node saw no blocks in this tenure, so the reorg takes nothing away from
    // the canonical chain. We may still hold a signature over a block in it that
    // the node has never seen...
    superseded_tenures.push(tenure);
    continue;
};
``` [5](#0-4) 

The comment right there acknowledges the exact gap: "We may still hold a signature over a block in it that the node has never seen." The code nonetheless proceeds to permit the reorg and record the permit via `record_superseded_tenure` → `mark_tenure_superseded`.

Once recorded, `get_signed_conflicts` still returns this signer's earlier signed block(s) as conflicts (it keys off `signed_self`/`signed_group`, not node state), but `reorg_permit_stands` is consulted first in `handle_block_pre_commit` and, while the permitting sortition remains canonical, **excludes the conflict outright**, bypassing the whole conflict-freshness/liveness machinery documented as the "silent backstop" against double-signing: [6](#0-5) [7](#0-6) 

This mirrors the CVE's bug shape exactly: two independently-reasonable mechanisms (a node-state-based reorg veto, and a node-processing-triggered "globally accepted" marker) are combined in a way that silently disables a security check (the equivocation/conflict guard) whenever the node's local processing lags behind what the signer has already committed to via signature — something a single miner (who fully controls tenure/sortition timing and block propagation to the network) can reliably induce, e.g., by proposing and getting 70%+ pre-commit/signature weight for one or more blocks in a tenure and then immediately abandoning that tenure with a new sortition/tenure-change before this signer's own node has finished processing/broadcasting/adopting those blocks.

### Impact Explanation

If this race is won, the signer records a spurious "superseded" permit for a tenure it actually signed (possibly more than one block, or the reward-set threshold's worth of blocks) into. When the replacement tenure's block(s) reach the pre-commit/signature threshold at the same height(s), `reorg_permit_stands` unconditionally clears the conflict and the signer proceeds to `SIGN`, producing a second, conflicting signature at a height it already signed for — the exact "signer signing a conflicting block" scenario the whole conflict-guard machinery (section 5 of `docs/signer-flows.md`, and the `get_signed_conflicts`/`conflict_still_blocks` design) exists to prevent. This is a **Critical** impact per the stated criteria (a signer signing a conflicting block), achievable by a single miner without needing a majority of signers, another signer's key, or the auth token — only ordinary control over tenure timing/proposal broadcast and the ability to induce its own node's block-processing to lag behind the signer network's tally (a normal, frequent condition under load, and one the code's own comments acknowledge as a known blind spot: "We may still hold a signature over a block in it that the node has never seen").

### Likelihood Explanation

The trigger conditions are mundane rather than exotic:
- A signer's own node lagging its own block-processing behind the signer set's pre-commit/signature tally is a routine timing gap (documented elsewhere in this same codebase as the reason `mark_locally_accepted`/`mark_globally_accepted` are separate states, and why `get_tenure_last_block_info`/`get_signed_conflicts` deliberately do NOT depend on node-confirmed state for the general case).
- A miner abandoning its own tenure via a new sortition win, or racing a block commit, is ordinary miner behavior already exercised by many tests in this repo (`forked_tenure_testing`, `partial_tenure_fork`, etc.), just not combined with this specific counting gap.
- The `first_proposal_burn_block_timing` "poorly timed" branch (line 259-274) provides an *additional*, independently reachable path to the same outcome even when `first_block_mined` is `Some`, if the local `approved_time` (pre-commit time, not signature time) happens to fall close enough to the sortition boundary — again decoupled from how many blocks were actually *signed*.

### Recommendation

Gate the reorg-permit veto in `check_parent_tenure_choice` on the signer's own record of what it has **signed** (e.g. `has_signed_block_in_tenure` / `get_last_signed_block` / a count of `signed_self`/`signed_group` blocks in the tenure), not on `get_globally_accepted_block_count_in_tenure` or the node's `first_block_mined`. If the signer has signed (locally or as part of the observed group) any block in the tenure being reorged, the tenure must never be marked superseded, regardless of whether the local node has finished processing/adopting it.

### Proof of Concept

1. Signer S is part of a 5-signer set; a single miner controls block proposals for tenure T1 at consensus hash `CH1`.
2. Miner proposes block B1 in T1. S validates it, pre-commits, and (because ≥70% weight pre-commits arrive quickly over StackerDB) crosses the signature threshold and calls `mark_locally_accepted`/`handle_block_signature` — B1 is now `LocallyAccepted` in S's `signerdb`, with `signed_self`/`signed_group` set. S's own node has not yet ingested/confirmed B1 as its canonical tip (e.g., it is momentarily busy, or the `NewBlock` event has not yet fired).
3. Miner immediately triggers a new sortition (or otherwise starts tenure T2 that does not build on `CH1`), and proposes a tenure-change block B2 in T2 that reorgs T1 at the same height as B1.
4. S's `handle_block_proposal` for B2 → `validate_tenure_change_payload` → `check_parent_tenure_choice`:
   - `get_globally_accepted_block_count_in_tenure(CH1)` returns 0 (B1 is only `LocallyAccepted`), so the `>1` veto does not fire.
   - `client.get_tenure_forking_info` reports `first_block_mined = None` for `CH1` (S's own node has not yet stored a tenure-start header for it), so `check_parent_tenure_choice` takes the "no blocks seen" branch and pushes `CH1` into `superseded_tenures`, returning `Ok(true)`.
   - `mark_tenure_superseded(CH1, ..., superseded_by=CH2, ...)` is recorded.
5. B2 (or a sibling at B1's height in T2) reaches the pre-commit threshold. In `handle_block_pre_commit`, `get_signed_conflicts` still returns B1 as a conflict (S signed it), but `reorg_permit_stands` sees the recorded permit and, while `CH2`'s sortition remains canonical, returns `true`, excluding the conflict entirely.
6. S proceeds to `mark_locally_accepted`/sign B2 — S has now signed two conflicting blocks at the same height, in different tenures, without ever needing another signer's key, a majority takeover, or the auth token.

Note: I was not able to execute this scenario in a live/integration test harness (no filesystem/terminal access in this mode); the trace above is derived directly from the cited source and the existing unit tests (`check_globally_signed_block_count`, `has_signed_block`, `check_parent_tenure_choice_reorg_timing_ok`/`refused_reorg_supersedes_nothing`) that already establish each individual fact (undercounting of `LocallyAccepted` blocks, and that a standing permit clears the conflict guard). A background Devin session with repo/test access could construct a concrete `stacks-signer` unit test analogous to `run_cross_tenure_scenario`/`standing_reorg_permit_clears_conflict` in `stacks-signer/src/v0/tests.rs`, but seeding `get_globally_accepted_block_count_in_tenure` to 0 while `signed_self`/`signed_group` is set on a `LocallyAccepted` block, to confirm the permit is granted and the double-sign occurs, to remove any remaining doubt.
