### Title
Stale confirmations from removed multisig members still count toward the execution threshold, allowing requests to execute below the configured `num_confirmations` - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` decides whether to execute a pending request purely by comparing the size of the `confirmations` `HashSet<String>` against `num_confirmations` [1](#0-0) . `delete_member`, invoked whenever a `DeleteMember` request executes, only removes confirmation records for requests that member itself *originally proposed* — it does not scan `self.confirmations` to strip that member's confirmations from requests proposed by *other* members [2](#0-1) . This breaks the intended equality: `confirmations.len()` (confirmations counted toward the threshold) must equal the number of confirmations from members who are still in `self.members` (live members) at execution time.

### Finding Description
A `MultiSigRequest` can carry multiple `MultiSigRequestAction`s executed sequentially by `execute_request` [3](#0-2) . `AddMember`/`DeleteMember` require `assert_self_request` (receiver must be the multisig account itself) but nothing prevents a `DeleteMember` action from being bundled or requested independently while other, unrelated pending requests already hold confirmations from the member about to be deleted.

Concretely:
1. Members A, B, C, D exist, `num_confirmations = 3`.
2. Request R1 (e.g. `Transfer` of the account's NEAR balance) is proposed and confirmed by A and B. `confirmations[R1] = {A, B}` (2 of 3 needed).
3. Separately, a `DeleteMember { member: B }` request is proposed and reaches 3 confirmations from A, C, D, and executes via `delete_member` [2](#0-1) . This only removes B from `self.members`, deletes requests *proposed by* B, and removes B's `num_requests_pk` entry — it does not touch `confirmations[R1]`, which still contains `"B"`.
4. C now confirms R1. `confirm()` computes `confirmations.len() as u32 + 1 = 2 + 1 = 3 >= num_confirmations (3)`, so R1 executes [4](#0-3) .
5. R1 executes with only two currently-live members (A and C) having actually approved it after B's removal — B's stale confirmation is still counted as if B were a live authorizer, even though B has been removed from `self.members`.

The same non-cleanup pattern exists in `remove_request`, which is only called for the request being executed or explicitly deleted — it never audits *other* requests' confirmation sets for members no longer in `self.members` [5](#0-4) .

### Impact Explanation
This directly breaks the equality "confirmations counted versus live members." A request (e.g., a `Transfer` moving the multisig-controlled NEAR out to an arbitrary `receiver_id`) can be executed with fewer live, currently-authorized members approving it than the contract's configured `num_confirmations` threshold. This matches the Critical impact category "a multisig request executed below threshold" — NEAR held by the multisig account can be moved by a party set that no longer satisfies the K-of-N security guarantee the contract is supposed to enforce.

### Likelihood Explanation
Exploitation requires no attacker privilege beyond being a normal multisig member (or the ordinary operational flow of the multisig removing a member for routine key rotation/security reasons) combined with an already-pending, not-yet-fully-confirmed request from before the removal. Because member removal (e.g., after a suspected key compromise, employee offboarding, or routine rotation) is an expected, non-malicious multisig operation, and pending unconfirmed requests with partial confirmations are a normal state (the contract explicitly supports up to `active_requests_limit` outstanding requests per member with no forced settlement before a `DeleteMember` action), this can be triggered unintentionally, and can also be engineered by any member who front-loads confirmations on multiple pending requests before proposing/confirming the removal of a co-signer.

### Recommendation
When executing `DeleteMember`, iterate over all entries in `self.confirmations` (not just requests proposed by the removed member) and remove the deleted member's key from every confirmation set; alternatively, at confirmation time, re-validate each entry in the `confirmations` set against current `self.members` before counting it toward the threshold, e.g. `confirmations.iter().filter(|m| self.members.contains(...)).count()`.

c.confirm(r1); // confirmations[r1].len() (2) + 1 == num_confirmations (3) -> executes

// even though only A and C are live members that actually confirmed after B's removal.

        let mut promise = Promise::new(request.receiver_id.clone());
        let receiver_id = request.receiver_id.clone();
        let num_actions = request.actions.len();
        for action in request.actions {
            promise = match action {
                MultiSigRequestAction::Transfer { amount } => promise.transfer(amount.into()),
                MultiSigRequestAction::CreateAccount => promise.create_account(),
                MultiSigRequestAction::DeployContract { code } => {
                    promise.deploy_contract(code.into())
                }
                MultiSigRequestAction::AddMember { member } => {
                    self.assert_self_request(receiver_id.clone());
                    self.add_member(promise, member)
                }
                MultiSigRequestAction::DeleteMember { member } => {
                    self.assert_self_request(receiver_id.clone());
                    self.delete_member(promise, member)

                MultiSigRequestAction::AddKey {

                    permission,

                    self.assert_self_request(receiver_id.clone());

                    self.active_requests_limit = active_requests_limit;
                    return PromiseOrValue::Value(true);
                }

        }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    /// Removes request, removes confirmations and reduces num_requests_pk - used in delete, delete_key, and confirm
    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .unwrap_or_else(|| env::panic_str("Failed to remove existing element"));
        // decrement num_requests for original request signer
        let original_member = request_with_signer.member;
        let mut num_requests = self
            .num_requests_pk
            .get(&original_member.to_string())
            .unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_member.to_string(), &num_requests);
        // return request
        request_with_signer.request
    }
