### Title
Unchecked subtraction in Span Batch `decode_tx_tos` allows attacker-controlled underflow/panic during L1 batch derivation - ([File: crates/consensus/protocol/src/batch/transactions.rs])

### Summary
`SpanBatchTransactions::decode_tx_tos` computes the number of non-contract-creation transactions as `self.total_block_tx_count - contract_creation_count()`, where both operands are derived from attacker-controlled span-batch fields decoded from L1 batcher data. [1](#0-0)  `contract_creation_count()` sums set bits from `contract_creation_bits`, a bitfield whose length/content is fully controlled by the entity submitting the span batch, and is not validated against `total_block_tx_count` before this subtraction occurs. [2](#0-1) 

### Finding Description
`total_block_tx_count` is set from decoded batch data and `contract_creation_bits` is decoded independently as a raw bitfield sized to `total_block_tx_count` bits, but nothing enforces that the population count of `contract_creation_bits` (i.e., `contract_creation_count()`) cannot exceed `total_block_tx_count` itself — the bits are attacker-supplied raw bytes, so a malicious batcher can freely set extra bits beyond what any legitimate encoding would produce, or supply a count of set bits larger than the transaction count if the bit vector's trailing padding bits are set. [2](#0-1)  When `decode_tx_tos` runs `self.total_block_tx_count - contract_creation_count()` with `contract_creation_count() > total_block_tx_count`, this is an unsigned (`u64`) subtraction that underflows. [1](#0-0)  In a debug/overflow-checked build this panics; in a release build (the default `overflow-checks` setting was not found configured to `true` anywhere in the repo, so release builds use wrapping arithmetic by default) the subtraction wraps to a value near `u64::MAX`, which is then used to drive the decode loop `for _ in 0..(self.total_block_tx_count - contract_creation_count)`, attempting to read a huge number of 20-byte `to` addresses from the remaining buffer. This is analogous to the reported Thrift class of bug: an unchecked/overflowing integer operation derived directly from untrusted wire input drives subsequent memory access decisions, exactly the "Integer Overflow or Wraparound" class flagged in the Apache Thrift Compact Protocol advisory, but here applied to op-stack span-batch decoding of L1-derived data rather than Thrift's compact protocol varints.

This code path is reachable by any L1 party who can post batch data (calldata/blob) that Base's derivation pipeline consumes, i.e., the "derivation of attacker-written L1 deposit/batch data" class explicitly listed as in-scope.

### Impact Explanation
If this underflow is not otherwise caught (e.g., by a prior sanity check bounding `contract_creation_count()` against `total_block_tx_count`, or by `r.len() < 20` short-circuiting quickly), a malicious batch can cause the derivation pipeline (used by both sequencer and verifier nodes) to panic on unsigned-subtraction overflow, or — in a release build without overflow checks — enter a loop attempting billions of iterations reading from a short buffer, which will itself immediately trip the `r.len() < 20` bounds check and return `Err(InvalidTransactionData)` after a very large number of iterations (potentially a resource-exhaustion condition per iteration, though each iteration is cheap). The most consensus-relevant risk is a **panic-based node halt** in the derivation pipeline shared by all Base nodes processing the same L1 batch, which would be a node-halt/potential-chain-split issue if only some node builds have overflow-checks enabled and others don't, causing a derivation-result mismatch between node instances.

### Likelihood Explanation
I could not fully verify, due to tool/session limitations in this final pass, (1) whether `contract_creation_bits` is bounds-checked elsewhere before `decode_tx_tos` is called in the actual decode sequence, (2) whether the repository's build profile enables `overflow-checks = true` for release builds (grep for `overflow-checks` in the repo found no matches, suggesting it is not explicitly enabled, meaning default Cargo release behavior — wrapping, not panicking — would apply), and (3) the exact call order of `decode_contract_creation_bits` relative to `decode_tx_tos` in the top-level span-batch decode routine. These are the same class of truncation/underflow bug that the test suite in this file already treats as a known regression category (see `test_decode_tx_sigs_truncated_input` and `test_decode_tx_tos_truncated_input`, which guard against out-of-bounds slicing but do not appear to test the `contract_creation_count > total_block_tx_count` underflow case specifically). [3](#0-2) 

### Recommendation
Add an explicit checked-subtraction (`checked_sub`) or an upfront validation that `contract_creation_count() <= total_block_tx_count` before computing the non-contract-creation transaction count in `decode_tx_tos`, returning `SpanBatchError::Decoding(SpanDecodingError::InvalidTransactionData)` on failure, mirroring the existing truncation guards already present in this file.

### Proof of Concept
Due to session limits I was unable to fully trace the exact top-level call sequence (`decode_prefix` → `decode_contract_creation_bits` → `decode_tx_tos`) to construct a byte-exact PoC batch payload in this pass. Conceptually: craft a span batch where `total_block_tx_count = 1` and `contract_creation_bits` is encoded with trailing padding bits set such that `contract_creation_count()` returns `> 1` (e.g., 8 for a single padded byte with all bits set), then feed it to `SpanBatchTransactions::decode_tx_tos`; this triggers `1u64 - 8u64`, which panics under debug/overflow-checked builds or wraps to `u64::MAX - 6` under release builds, as shown directly in the subtraction at line 223 of `crates/consensus/protocol/src/batch/transactions.rs`.     /// Decode the `to` addresses of the transactions from a reader.
    pub fn decode_tx_tos(&mut self, r: &mut &[u8]) -> Result<(), SpanBatchError> {
        let mut tos = Vec::with_capacity(self.total_block_tx_count as usize);
        let contract_creation_count = self.contract_creation_count();
        for _ in 0..(self.total_block_tx_count - contract_creation_count) {
            if r.len() < 20 {
                return Err(SpanBatchError::Decoding(SpanDecodingError::InvalidTransactionData));
            }
            let to = Address::from_slice(&r[..20]);
            tos.push(to);
            r.advance(20);
        }
        self.tx_tos = tos;
        Ok(())
    }
