### Title
Multisig request can execute below the live-member threshold because stale confirmations from removed members are never purged - (File: multisig2/src/lib.rs)

### Summary
In `MultiSigContract::confirm`, the number of confirmations required to execute a request is computed purely from a stored `HashSet<String>` of confirming member identifiers, without re-checking that those confirmers are still current members at execution time. [1](#0-0)  When a member is removed via `MultiSigRequestAction::DeleteMember`, `delete_member` only purges requests and confirmations for requests *authored by* the removed member; it does not scan and strip confirmations the removed member *cast* on other, still-pending requests. [2](#0-1)  This is analogous to the reported bug class: a value (the recorded confirmation count) is trusted and used to authorize execution without being verified against the live, ground-truth state (the current member set) it is supposed to represent — i.e., "confirmations counted" diverges from "live members."

### Finding Description
The contract stores confirmations per request as a `LookupMap<RequestId, HashSet<String>>`, keyed by the string form of `MultisigMember` (`confirmations`). [3](#0-2) 

`confirm()` checks the caller is currently a member (`assert_valid_request` → `current_member()`), but the threshold check only counts set membership of previously recorded confirmer strings plus the current confirmer, comparing against `self.num_confirmations`:
```rust
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
}
``` [4](#0-3) 

Nothing here re-validates that the members whose identifiers are already present in `confirmations` (added in a prior call) are still current members of `self.members` at the time the threshold is reached.

`delete_member()` is the only place that scrubs `confirmations`, and it filters requests by `r.member == member` — i.e., only requests the removed member *created* (`add_request`'s `member` field), not requests they merely confirmed:
```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
``` [5](#0-4) 

Consequently, if member `C` confirmed a pending request `R` created by member `A`, and `C` is subsequently removed via a separate `DeleteMember` request, `R`'s confirmation set still contains `C`'s entry. A later confirmation by any remaining live member can push `confirmations.len() + 1 >= num_confirmations` and execute `R`, even though only `num_confirmations - 1` (or fewer) *currently live* members actually approved it. The equality that should hold — `count(confirmations from members ∈ current self.members) >= num_confirmations` — is broken into `count(confirmations recorded historically, including from now-removed members) >= num_confirmations`.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." An attacker who is (or colludes with) a subset of members smaller than `num_confirmations` can get a high-value request (e.g., `Transfer`, `AddKey`, `FunctionCall`) executed by combining live confirmations with a stale confirmation left behind by a member removed after confirming but before the request completes. This can move NEAR or add unauthorized keys/permissions to the contract account without the documented number of currently-authorized signers actually approving.

### Likelihood Explanation
This requires no privileged access beyond being a multisig member (an "unprivileged" party relative to the multisig's security guarantee that `num_confirmations` *live* signers approve every action) — it only needs: (1) a pending request with at least one confirmation, (2) a separate, properly-threshold-confirmed `DeleteMember` action removing the confirmer, and (3) one more live confirmation pushing the stale count over the threshold. All of these are ordinary, permitted multisig operations; no bug in downstream contracts or victim keys are needed. The main constraint is timing/ordering of `add_request`/`confirm`/`DeleteMember` calls, which colluding or opportunistic members fully control.

### Recommendation
When checking whether a request has reached `num_confirmations`, filter `confirmations` to only those entries still present in `self.members` before comparing to the threshold, and/or have `delete_member` iterate all pending requests' confirmation sets (not just requests authored by the removed member) and strip the removed member's entry from each.

### Proof of Concept
1. Initialize `MultiSigContract::new([A, B, C, D], 3)`.
2. `A` calls `add_request(R)` (Transfer to attacker-controlled account) → `R`'s `confirmations = {}`.
3. `B` calls `confirm(R)` → `confirmations = {B}` (1 < 3, not executed).
4. `C` calls `confirm(R)` → `confirmations = {B, C}` (2 < 3, not executed).
5. Separately, `A`, `B`, `D` create and confirm a `DeleteMember{C}` request reaching threshold 3 → `C` is removed from `self.members`; because `R`'s `member` field is `A` (not `C`), `delete_member` does not touch `R`'s confirmations, so `R.confirmations` still contains `C`.
6. `A` calls `confirm(R)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request(R)` runs the `Transfer`, even though only `A` and `B` are currently live members who approved it (2 live confirmations, not 3). [6](#0-5) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
