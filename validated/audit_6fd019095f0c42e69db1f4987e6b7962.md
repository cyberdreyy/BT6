### Title
Deposits remain open after the pool is permanently closed (`epochDuration == 0`), permanently freezing new depositor funds in withdraw receipts that can never mature - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol), [File: contracts/IdleCDOCreditVault.sol](contracts/IdleCDOCreditVault.sol))

### Summary
The external bug is a state-flag (`isDepositAllowed`) enforced on the normal deposit path but skipped on an alternative path that credits a user balance. The same pattern exists in `IdleCDOEpochVariant`: the epoch state machine treats `epochDuration == 0` as "pool permanently closed" — `startEpoch` reverts when `epochDuration == 0` (line 239), and `setEpochParams` reverts once `epochDuration == 0` (line 122), so no new epoch can ever begin. Yet the deposit entry points (`depositAA`/`depositBB` → `IdleCDOCreditVault._deposit` → `IdleCDOEpochVariant._deposit`) never check the closed-pool flag; they only require `whenNotPaused` and `isWalletAllowed` (lines 644–650). After a close-pool `stopEpoch(0, 1)`, the contract is unpaused and `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are re-enabled (lines 478–483, 488–493), so deposits succeed into a vault that will never run another epoch.

### Finding Description
When the borrower repays everything, `stopEpoch` with `_interest == 1` sets `epochDuration = 0`, `epochEndDate = 0`, `disableInstantWithdraw = true`, and unpauses the contract (lines 486–493). From that point:

1. Any KYC'd wallet calls `depositAA(amount)` / `depositBB(amount)`. `_deposit` only checks `whenNotPaused` and `isWalletAllowed` (lines 644–650) plus `_guarded` in the parent (IdleCDOCreditVault.sol:196) — there is no `epochDuration == 0` / closed-pool check, even though `depositDuringEpoch` and the epoch functions treat that state as terminal.
2. The underlyings are moved into `IdleCreditVault` via `IIdleCDOStrategy(strategy).deposit(_amount)` (IdleCDOCreditVault.sol:211) and tranche tokens are minted at the post-close price.
3. To exit, the depositor must call `requestWithdraw`, which is allowed (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` are true). `_calcInterestWithdrawRequest` returns zero interest because `epochDuration == 0` (lines 857–860), and `creditVault.requestWithdraw` books a receipt that matures only after the next epoch settles.
4. `startEpoch` can never be called again (`epochDuration == 0` check, line 239), and `setEpochParams` cannot resurrect it (line 122). The receipt is therefore parked against an epoch boundary that never occurs — the same class of failure as the JUSD report: a balance credited on a path that skipped the "is this state allowed" gate, leaving the user with a claim that the state machine will never service.

The depositor's tranche tokens are burned by `_withdrawOps` (line 790), so they cannot reverse the deposit either; their principal is locked in the strategy's pending-withdraw bucket permanently.

### Impact Explanation
Permanent freezing of funds. Any deposit made after pool close is converted into a withdraw receipt that can never be claimed, since claim maturity is driven by epoch transitions and `epochDuration == 0` makes future epochs impossible. The entire deposit amount is lost to the depositor (it remains stranded as strategy balance). The invariant broken is that a terminal/closed pool state must reject new principal on every crediting path — enforced for `startEpoch`, `depositDuringEpoch` (via `isEpochRunning`), and `setEpochParams`, but not for the ordinary `depositAA`/`depositBB` path.

### Likelihood Explanation
Likelihood hinges on the deployment owner choosing to close the pool (`stopEpoch` with `_interest == 1`), which is a supported, non-malicious operation explicitly built for borrower full repayment. After that, no privileged action is needed — the contract is unpaused and unflagged for deposits, and any allowlisted user (or any user if `keyring == address(0)`) can deposit and lose the funds. Note the residual uncertainty: the exact claim-maturity check lives in `IdleCreditVault.claimWithdrawRequest`/`withdrawsRequestsByEpoch`, which I could not fully trace in this pass; the finding assumes receipts require a future epoch boundary to mature, consistent with the documented "claimable after at least 1 epoch" semantics (lines 965–971). If claims instead pay immediately from available strategy balance, the impact downgrades to depositors receiving zero yield on a permanently closed pool — still incorrect, but lower severity.

### Recommendation
Mirror the closed-pool guard onto the deposit path, exactly as the JUSD fix adds the missing flag check to the internal deposit:

```solidity
function _deposit(uint256 _amount, address _tranche) internal override whenNotPaused returns (uint256) {
    // A closed pool (epochDuration == 0) can never start a new epoch, so new
    // principal would only ever become an unmaturable withdraw receipt.
    _checkNotAllowed(epochDuration == 0);
    _checkNotAllowed(!isWalletAllowed(msg.sender));
    _skimDonatedAssets();
    return super._deposit(_amount, _tranche);
}
```

Alternatively, keep the contract paused permanently on the close-pool stop (skip the `_unpause()` at line 480 when `_isRequestingAllFunds`), which blocks deposits while still letting `requestWithdraw`/`claimWithdrawRequest` function for existing holders.

### Proof of Concept
Foundry fork sketch (attacker = ordinary allowlisted LP; owner/manager calls are honest setup):

```solidity
function test_DepositAfterPoolClose_LocksFunds() public {
    // --- setup: normal epoch lifecycle ---
    deal(underlying, alice, 1_000_000e6);
    vm.prank(alice); // KYC-passing lender
    cdo.depositAA(500_000e6);

    vm.prank(manager);
    cdo.startEpoch();
    vm.warp(block.timestamp + cdo.epochDuration() + 1);

    // --- honest close: borrower repaid and approved, stopEpoch(0, 1) ---
    vm.prank(manager);
    cdo.stopEpoch(0, 1);
    assertEq(cdo.epochDuration(), 0);          // pool permanently closed
    assertFalse(cdo.paused());                 // but deposits are unpaused

    // --- victim deposit on a closed pool succeeds ---
    deal(underlying, bob, 100_000e6);
    vm.startPrank(bob);
    IERC20(underlying).approve(address(cdo), 100_000e6);
    uint256 minted = cdo.depositAA(100_000e6); // should revert, does not
    assertGt(minted, 0);

    // --- exit path: request is accepted but burns shares for an unmaturable receipt ---
    cdo.requestWithdraw(0, cdo.AATranche());
    vm.stopPrank();

    // No future epoch can ever start to mature the receipt:
    vm.warp(block.timestamp + 365 days);
    vm.prank(manager);
    vm.expectRevert(); // epochDuration == 0
    cdo.startEpoch();

    vm.prank(bob);
    vm.expectRevert(); // receipt not matured / no claimable epoch
    cdo.claimWithdrawRequest();

    // bob's 100_000e6 is permanently stranded in the strategy.
}
```

Key PoC preconditions: borrower has repaid and approved the pull for the close-pool stop; `keyring` unset or `bob` credentialed. If step 3's claim unexpectedly succeeds (immediate payment from strategy balance), the PoC still demonstrates principal entering a dead pool with zero interest — re-scope impact accordingly after confirming `IdleCreditVault` receipt maturity.
