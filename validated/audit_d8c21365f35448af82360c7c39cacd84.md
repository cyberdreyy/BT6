### Title
Late-window prefunded-queue deposit permanently bricks `stopEpochWithDuration`, freezing all pool funds - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The external report (CVE-2022-47516) is a denial of service: a single crafted unprivileged message trips an assertion and crashes the daemon. The analog in this codebase is a single crafted unprivileged transaction that trips a permanent revert condition in the prefunded epoch-stop path: a KYC-passed lender calls `IdleCDOEpochQueue.requestDeposit` in the last possible second before the prefunded deposit cutoff, creating an `epochPendingDeposits[nextEpoch] != 0` state that can never be cleared. From then on, every `stopEpochWithDuration` call on `IdleCDOEpochVariantPrefunded` reverts inside `prefundedDepositsToProcess()`, permanently freezing the entire pool.

### Finding Description
In the prefunded flow, `requestDeposit` accepts deposits only while `block.timestamp + prefundedDepositWindow < epochEndDate` (strict inequality) and only before `epochPrefundedDeposits[nextEpoch]` is set [1](#0-0) . `processDepositsToBorrower` — the only function that can move `epochPendingDeposits` into `epochPrefundedDeposits` — enforces the *same* strict inequality [2](#0-1) . The legacy `processDeposits` path is explicitly disabled for prefunded queues [3](#0-2) , and `deleteRequest` can only be called by the depositor themselves [4](#0-3) .

Meanwhile, the prefunded stop path unconditionally calls `_epochQueue.prefundedDepositsToProcess()` whenever the queue is configured [5](#0-4) , and `prefundedDepositsToProcess` reverts whenever `epochPendingDeposits[_epoch] != 0` [6](#0-5) . Since the direct `stopEpoch` selector is blocked when a queue is configured [7](#0-6) , `stopEpochWithDuration` is the only stop path — and it reverts atomically forever.

An attacker deposits at `block.timestamp == epochEndDate - prefundedDepositWindow - 1` (the last valid second). One block later the cutoff has passed, `processDepositsToBorrower` reverts, the queued deposit is neither prefundable nor cancellable by anyone but the attacker, and `stopEpochWithDuration` reverts for all eternity.

### Impact Explanation
Permanent freezing of funds: the epoch can never be stopped, so borrower repayments can never be pulled in, `isEpochRunning` stays true, deposits/withdraw requests stay paused (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` are false while running), and every LP's principal and yield is locked. The broken invariant is liveness of the epoch state machine — analogous to the daemon crash in the CVE. Cost to the attacker is one dust deposit plus gas; frozen value is the entire pool TVL. Existing guards do not help: the skim, `_guarded`, `checkPrefunding` (which only blocks on default/zero-price/TVL, not on timing) all pass for a legitimate dust deposit [8](#0-7) .

### Likelihood Explanation
Requires only a KYC-passing lender (in-scope attacker) and a prefunded queue configuration with `prefundedDepositWindow > 0`. The attacker must time a transaction into the final second before the cutoff — trivially achievable via a private relay or by observing the manager's `processDepositsToBorrower` in the mempool and front-running/`requestDeposit`ing in an earlier block of the same cutoff boundary (any pending deposit added after the manager's last opportunity to prefund is sufficient; the window need not be the literal last second if the manager simply hasn't prefunded yet and the cutoff lapses). The manager cannot preemptively prevent it because deposits are permissionless for whitelisted wallets and there is no separate, earlier deposit cutoff than the prefund cutoff — both use the identical timestamp check, which is the root flaw.

### Recommendation
Decouple the two cutoffs: require `requestDeposit` to close strictly earlier than `processDepositsToBorrower` (e.g., deposit cutoff at `epochEndDate - window`, prefund allowed until `epochEndDate`), or allow `processDepositsToBorrower` / a permissionless refund path up to `epochEndDate`. Alternatively, let the queue sweep leftover `epochPendingDeposits` back to depositors (or treat them as non-prefunded and settle them at the post-stop price) so `prefundedDepositsToProcess` never permanently reverts on unprocessable dust.

### Proof of Concept
Foundry fork test (prefunded variant + AA queue configured):

```solidity
function testLateDepositFreezesStopEpoch() external {
    // setup: prefunded CDO, queue set, window = 5 days, epoch running, TVL deposited
    vm.prank(manager);
    cdoEpoch.setEpochQueue(address(queue));
    vm.prank(manager);
    queue.setPrefundedDepositWindow(5 days);

    // attacker is a KYC'd lender; deposit lands in last valid second of the window
    uint256 t = cdoEpoch.epochEndDate() - 5 days - 1;
    vm.warp(t);
    deal(address(underlying), attacker, 1);
    vm.startPrank(attacker);
    underlying.approve(address(queue), 1);
    queue.requestDeposit(1); // succeeds: t + window < epochEndDate
    vm.stopPrank();

    // cutoff passes; manager can no longer prefund the stuck deposit
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.expectRevert(NotAllowed.selector);
    vm.prank(manager);
    queue.processDepositsToBorrower();

    // borrower fully repays; epoch still cannot be stopped — permanent freeze
    deal(address(underlying), borrower, expectedRepay);
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), expectedRepay);
    vm.expectRevert(NotAllowed.selector);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, interest, cdoEpoch.epochDuration(), 0);

    assertTrue(cdoEpoch.isEpochRunning()); // epoch stuck forever; all LP funds frozen
}
```
