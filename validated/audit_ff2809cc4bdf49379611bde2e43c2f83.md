### Title
Signature-as-pre-commit fallback silently drops the acceptance-threshold re-tally once a signer has already self-signed - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`store_and_process_block_signature` redirects a `BlockAccepted` message from a signer it has not seen pre-commit from into `handle_block_pre_commit` and returns immediately, skipping its own threshold tally. `handle_block_pre_commit`, however, bails out as a no-op whenever the local signer has already signed the block (`signed_self` is set). When both conditions coincide, the freshly stored signature is persisted to `block_signatures` but the signer never re-evaluates whether the group acceptance threshold has now been crossed, exactly mirroring the CreamFi bug where a balance existed (`CToken > 0`) but the accounting step (`registerCollateral`) that would make it count was never invoked.

### Finding Description
`store_and_process_block_signature` first stores the incoming signature unconditionally: [1](#0-0) 

It then special-cases a signer we have not seen pre-commit from, treating the acceptance message as an implicit pre-commit and returning before running the tally logic below (`get_block_signatures`, weight computation, `mark_locally_accepted`, `broadcast_signed_block`): [2](#0-1) 

The redirected call lands in `handle_block_pre_commit`, which records the pre-commit table entry but exits as soon as it sees the local signer has already signed: [3](#0-2) 

Because `signed_self.is_some()` short-circuits before the pre-commit weight tally (`get_block_pre_committers` / `compute_signature_signing_weight`) and before the "SIGN" branch that eventually re-invokes `handle_block_signature`/`store_and_process_block_signature` for our own acceptance, the just-stored remote signature is never counted against `min_weight` by either code path. Nothing else in the module re-triggers this check for that block unless another *new* signature or pre-commit arrives from a signer that has neither pre-committed nor already been tallied.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality: the DB genuinely holds enough valid `block_signatures` rows to reach `compute_voting_weight_threshold`, but the signer's local state (`signed_group`, and therefore `broadcast_signed_block` → `handle_post_block`) is never updated to reflect it. A signer that has already self-signed is permanently wedged with respect to *that specific block* — it will never recognize group consensus or push the assembled signature set to the node from this event, unless some other, unrelated event happens to re-run the tally. In a scenario where late/duplicate acceptance messages arrive after every signer's own `signed_self` is already set (e.g. restarted signers replaying only their final `BlockAccepted` without re-emitting the earlier `BlockPreCommit`, which is exactly the "outdated version" case this fallback was written for), the block can be starved of a threshold-triggering re-tally across the whole signer set, stalling confirmation of an otherwise fully-signed block. This matches the "High — signer wedged into never signing/confirming valid blocks" impact bucket.

### Likelihood Explanation
This requires no majority collusion and no key compromise — only ordinary message reordering/replay that a single relaying party (miner or any gossiping signer/node) can cause: deliver a `BlockAccepted` for a signer before/without its corresponding `BlockPreCommit` having been locally recorded (`has_committed` false), while the receiving signer has already reached `signed_self`. The code comment itself ("in case the caller is running an outdated version") acknowledges this is an expected, reachable condition, not a hypothetical one.

### Recommendation
After delegating to `handle_block_pre_commit` in the fallback branch, still fall through to (or explicitly invoke) the acceptance-threshold tally in `store_and_process_block_signature` regardless of whether `handle_block_pre_commit` decided the pre-commit path was "already signed / nothing to do." Concretely, remove the early `return` at `stacks-signer/src/v0/signer.rs:2462-2466`, or have `handle_block_pre_commit`'s `signed_self.is_some()` branch still recompute and act on the signature-based threshold before returning, so a stored signature is never left uncounted.

### Proof of Concept
1. Signer S has already reached `signed_self` for block B (e.g. as the threshold-triggering signer via its own pre-commit path).
2. Remaining honest signer R never had its `BlockPreCommit` for B delivered to/recorded by S (dropped chunk, restart, or version skew), but R's `BlockAccepted` signature for B is delivered to S.
3. S's `store_and_process_block_signature` stores R's signature (`add_block_signature` succeeds), then takes the `signer_address != self.stacks_address && !has_committed(...)` branch and calls `handle_block_pre_commit`.
4. `handle_block_pre_commit` records R in `block_pre_commits` but immediately returns at `signed_self.is_some()` — no weight recount happens.
5. `store_and_process_block_signature` has already returned before reaching its own `get_block_signatures`/weight-threshold code, so even though DB weight now meets/exceeds `min_weight`, S never calls `mark_locally_accepted`/`broadcast_signed_block` for B in response to this event, and no other event is guaranteed to re-trigger it.
