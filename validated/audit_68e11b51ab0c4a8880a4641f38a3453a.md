### Title
Reorg permission (`check_parent_tenure_choice`) forks on each signer's local wall-clock timestamps, letting a timed miner broadcast split the signer set between the old and reorging tenures - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_parent_tenure_choice` decides whether a reorging tenure is a valid parent by comparing `sortition_state_received_time` (this signer's own `get_burn_block_receive_time`) against `local_block_info.approved_time` (this signer's own approval timestamp for the reorged tenure's first block), then checking if the gap is below `first_proposal_burn_block_timing`. Both timestamps are purely local to each signer's own SignerDB, so identical canonical tenure history can legitimately produce `Ok(true)` on some signers and `Ok(false)` on others, purely as a function of when each signer individually received the burn block and approved the earlier proposal.

### Finding Description
The equality that should hold is: for the same tenure history (`self.parent_tenure_id`, `self.prior_sortition`, and the same `tenures_reorged` returned by the node), the reorg-permit decision returned by `check_parent_tenure_choice` should be identical for every honest signer. Instead, the decisive computation is: [1](#0-0) 

`sortition_state_received_time` comes from `signer_db.get_burn_block_receive_time(&self.burn_block_hash)` [2](#0-1)  - a purely local wall-clock timestamp recorded when *that signer's own node* delivered the burn-block event. `local_block_info.approved_time` comes from `signer_db.get_first_approved_block_in_tenure`, i.e. the local time *that same signer* pre-committed to the reorged tenure's first block. Neither value is derived from consensus data or a value shared/verified across the signer set; both depend entirely on each signer's individual network path and processing latency for two independent events (miner proposal receipt and burn-block receipt).

Because the miner (an attacker who only needs to win one sortition slot) fully controls when it broadcasts the reorging tenure's first block relative to when the new sortition's burn block will be delivered, it can deliberately choose a broadcast time such that `proposal_to_sortition` sits near the `first_proposal_burn_block_timing` boundary. Given normal variance in signer-to-signer/network latency, some signers will compute a value below the threshold (get `Ok(true)`, treating the reorg as permitted and calling `record_superseded_tenure`/marking the old tenure superseded) while others compute a value above it (get `Ok(false)`, returning `RejectReason::ReorgNotAllowed` and keeping the old tenure canonical from their point of view). No aggregation, node-side consensus check, or cross-signer coordination reconciles this: `check_proposal` in `v1.rs` (and the v2 equivalent) acts unilaterally on this locally-computed boolean and immediately sets `SortitionMinerStatus::InvalidatedBeforeFirstBlock` (rejecting side) or continues to accept/sign the tenure-change block (permitting side), per [3](#0-2) .

### Impact Explanation
Signers that reject the reorg keep signing for the pre-reorg tenure (via `last_sortition`), while signers that permit the reorg sign the new tenure's blocks at overlapping heights - a chain-safety violation (conflicting signed blocks at the same height under the same canonical history), matching the "Critical" category for a signer signing a non-canonical/conflicting block. This is repeatable on every tenure change where the attacker controls proposal broadcast timing, since the mechanism is identical each time and depends only on the attacker choosing timing near the boundary and natural signer-to-signer network jitter to do the splitting.

### Likelihood Explanation
The attacker needs only one miner slot (to produce the reorging tenure's block and control its broadcast time) and standard network gossip capability - no signer key, no majority weight, no local host access. The precondition is a burn block that arrives close enough in time to the earlier tenure's first proposal that `first_proposal_burn_block_timing` (a node-configurable duration, typically small, e.g. seconds) is comparable to natural inter-signer latency variance; this is realistic during normal chain operation without any exotic network manipulation - the attacker simply needs to broadcast near the threshold and rely on existing signer latency heterogeneity to do the actual splitting, making it feasible and repeatable across tenure changes.

### Recommendation
Do not base the reorg-permit decision on any purely local signer timestamp. Instead, derive the timing decision from data that is verifiably consistent across signers (e.g., the burn block's own timestamp/height as reported by the burnchain, or a value attested to and agreed upon during the signer's shared state machine, or eliminate the fine-grained "quick fork" timing allowance entirely in favor of a deterministic rule such as strict tenure/block-count based comparison). At minimum, require the timing check to use the earliest known consensus-derived timestamp for the burn block rather than each signer's individual `get_burn_block_receive_time`, and add a coordination step (e.g., peer info exchange or aggregator confirmation) before any signer relies on this branch to permit a reorg.

### Proof of Concept
```rust
// stacks-signer/src/chainstate/tests/mod.rs (or v1.rs test module)
// Two independent SignerDb instances simulate two honest signers observing
// the same canonical tenure history but with different local timestamps.

#[test]
fn check_parent_tenure_choice_diverges_across_signers() {
    let sortition_data = make_test_sortition_data(); // parent_tenure_id != prior_sortition
    let client = mock_client_with_tenure_forking_info(/* single reorged tenure,
        first_block_mined = Some(block_id), globally_accepted_blocks = 1 */);
    let first_proposal_burn_block_timing = Duration::from_secs(5);

    // Signer A: fast burn-block receipt relative to its own approval time -> small gap
    let mut db_a = SignerDb::new_test();
    db_a.insert_burn_block_receive_time(&burn_block_hash, approved_at + 2); // gap = 2s < 5s
    db_a.insert_approved_block(&tenure_ch, approved_time = approved_at);

    // Signer B: slow burn-block receipt (further network hop) -> large gap
    let mut db_b = SignerDb::new_test();
    db_b.insert_burn_block_receive_time(&burn_block_hash, approved_at + 8); // gap = 8s > 5s
    db_b.insert_approved_block(&tenure_ch, approved_time = approved_at);

    let result_a = sortition_data
        .check_parent_tenure_choice(&mut db_a, &client, &first_proposal_burn_block_timing)
        .unwrap();
    let result_b = sortition_data
        .check_parent_tenure_choice(&mut db_b, &client, &first_proposal_burn_block_timing)
        .unwrap();

    // For the identical tenure history, honest signers disagree:
    assert_eq!(result_a, true);   // Signer A permits the reorg
    assert_eq!(result_b, false);  // Signer B refuses the reorg
    assert_ne!(result_a, result_b);
}
```
This demonstrates that with the exact same canonical tenure sequence and node-reported `tenures_reorged` data, two honest signers' `check_parent_tenure_choice` calls return different booleans solely due to differing locally-recorded timestamps, confirming the equality break described.
