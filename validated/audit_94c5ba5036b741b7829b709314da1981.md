### Title
Multisig executes below threshold because `delete_member` doesn't purge a departed member's confirmations recorded on other members' requests - (File: multisig2/src/lib.rs)

### Summary
`delete_member` in `multisig2/src/lib.rs` only removes confirmations for requests that the departing member *itself created* (`r.member == member`), but leaves that member's confirmation entries intact inside the `confirmations` set of every *other* request they had confirmed. `confirm()` later counts `confirmations.len()` against `self.num_confirmations` without checking that each recorded confirmer is still a current member, so a stale confirmation from a removed member is counted toward the K-of-N threshold, letting a request execute with fewer live, currently-authorized confirmers than `num_confirmations` requires.

### Finding Description
The binding the multisig is supposed to enforce is:
```
confirmations.len() (for a request) == number of CURRENT members who confirmed it
```
and execution is only permitted when that value reaches `num_confirmations`.

`confirm()` enforces this only at the moment each individual confirmation is added — it checks `self.current_member()` and requires the confirmer to be a member at confirm-time [1](#0-0) . However, once a confirmation is recorded, nothing re-validates it later. `delete_member` cleans up only requests originated by the deleted member:

```rust
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    assert(...);
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    ...
    self.members.remove(&member);
``` [2](#0-1) 

This filter only matches requests where `r.member == member` — i.e., requests the departing member *added*. It does not scan `self.confirmations` for entries where the departing member appears as a *confirmer* on requests added by someone else. Those stale entries remain in the `HashSet<String>` for those other requests.

Then in `confirm()`:
```rust
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
} else {
    confirmations.insert(member.to_string());
    ...
}
``` [1](#0-0) 

The count `confirmations.len()` includes the stale, now-invalid member's confirmation string. As a result the threshold can be satisfied with fewer *currently valid* members than `num_confirmations` mandates.

### Impact Explanation
This is a Critical-tier authorization boundary break: "a multisig request executed below threshold." Example: `num_confirmations = 3`, members {A, B, C, D}. Member B adds a `Transfer` request and confirms it (1/3). Member C confirms (2/3). Before a third confirmation, the group removes B via a `DeleteMember` action (e.g., because B's key was compromised or B left). `delete_member` does not strip B's stale confirmation from the transfer request created by... in this scenario the request was added by B itself, so it *would* be cleaned. To hit the bug precisely: member A creates the transfer request; B and C (both still members) confirm it (2/3); then the group deletes member B via `DeleteMember` (perhaps unrelated to this request). `delete_member` only purges requests where `r.member == B` — i.e. requests B *created* — not requests B merely *confirmed*. Since A created this request, it is untouched, and B's stale confirmation stays in the set. Now with 3 members remaining (A, C, D) and `num_confirmations` still 3, D confirms: `confirmations.len()==2 (B,C) + 1 (D) = 3 >= 3` → executes, even though B is no longer an authorized member. The request executes with only 2 of 3 confirmations coming from currently valid members, i.e., below the intended live threshold.

### Likelihood Explanation
This requires no privileged action beyond the normal multisig workflow that is expected to happen regularly (membership rotation via `DeleteMember`, which any k confirmers can trigger through the normal request/confirm flow) combined with a pending unconfirmed/partially-confirmed request from a different member. Membership changes and pending requests coexisting is a routine, likely production scenario, not a contrived edge case, and it does not require ignoring documented initialization or foundation/owner misbehavior.

### Recommendation
When deleting a member, iterate `self.confirmations` and strip the departing member's entry from every request's confirmation set (not only from requests they created), or alternatively re-validate on `confirm()`/execution that every entry in the confirmations set still corresponds to a `self.members.contains(...)` member, filtering out stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy multisig2 with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A.add_request(Transfer{...})` → `request_id = 0`.
3. `B.confirm(0)` → confirmations = `{B}` (1/3).
4. `C.confirm(0)` → confirmations = `{B, C}` (2/3).
5. Members confirm a `DeleteMember{member: B}` request through the normal add_request/confirm flow (requires 3 confirmations on that separate request) — this succeeds and calls `delete_member` for `B`, per [2](#0-1) . Because request `0` was created by `A`, not `B`, its confirmations set `{B, C}` is left untouched.
6. `D.confirm(0)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request` runs the `Transfer`, per [3](#0-2) , despite only `C` and `D` being currently valid members who confirmed (B was removed) — one confirmation short of the intended live-member threshold.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
