### Title
File-variable `Key` is embedded into generated bash via Go `%q` (not shell-escaped), enabling command substitution injection - (File: shells/bash.go)

### Summary
`BashWriter.Variable` builds the on-disk path for `File`-type variables directly from the attacker-controlled `variable.Key` and writes that path into the generated script using Go's `fmt` `%q` verb, not the shell-aware escaping used everywhere else in the file. Because Go's `%q` does not escape `$` or backtick, a `Key` containing `$(...)` or `` `...` `` survives into a double-quoted context in the emitted bash script, where bash performs command substitution.

### Finding Description
`Variable` at `shells/bash.go:229-241` handles the `File` branch as: [1](#0-0) 

```go
func (b *BashWriter) Variable(variable spec.Variable) {
	if variable.File {
		variableFile := b.TmpFile(variable.Key)
		b.Linef("mkdir -p %q", helpers.ToSlash(b.TemporaryPath))
		b.Linef("printf '%%s' %s > %q", b.escape(variable.Value), variableFile)
		b.Linef("export %s=%q", b.escape(variable.Key), variableFile)
	...
```

`b.TmpFile(variable.Key)` performs a plain `path.Join(b.TemporaryPath, name)` with no escaping of `name` (see `TmpFile`/`cleanPath`/`Absolute` at `shells/bash.go:211-217,361-366`). The resulting `variableFile` string — which contains the raw, attacker-controlled `variable.Key` bytes — is then interpolated into the emitted script via `%q`. This `%q` is Go's `fmt` verb (Go-syntax quoting via `strconv.Quote` semantics), not `helpers.ShellEscape`/`helpers.PosixShellEscape` (the two functions actually used elsewhere in this file, at `helpers/shell_escape.go:53-126`, which correctly backslash-escape or ANSI-C-quote `$` and backtick).

Go's `%q` only escapes control characters, backslashes, and double quotes — it leaves `$` and `` ` `` untouched. Once wrapped in the resulting `"..."` in the generated bash script, those characters are shell metacharacters: bash performs command substitution inside double-quoted strings for `$(...)` and `` `...` ``. So a `Key` such as:

```
FOO$(touch /tmp/pwned)BAR
```

produces a generated line like:

```
printf '%s' 'secret' > "/builds/.../tmp/FOO$(touch /tmp/pwned)BAR"
```

which, when the generated script is later executed (via `eval` in `Finish`, `shells/bash.go:436-440`), runs `touch /tmp/pwned` as a command, not as inert path text — violating the stated invariant that runner-generated shell text must treat attacker data as literal, not executable syntax.

Note that `export %s=%q` on the same line uses `b.escape(variable.Key)` for the *env var name* position (correctly shell-escaped), but the *path* embedded via `%q` is not run through `b.escape`/`PosixShellEscape` at all — this is the inconsistency that breaks the invariant.

### Impact Explanation
This yields command execution inside the job's generated bash script at variable-setup time, before/around the user's own `script:` stage. On its own, within a single job whose own script the attacker already fully controls, this is not privilege escalation. The scoped, concrete impact arises when the `Key` is not chosen by the same actor who controls the target job's script — e.g., a `File`-type or dotenv-report-derived variable whose *name* originates from an upstream/less-trusted pipeline (via `artifacts:reports:dotenv`, `needs:`/pipeline variable propagation, or trigger inputs) and is consumed by a downstream job running with elevated trust (protected branch/environment secrets, a different/more privileged runner). In that cross-job scenario, injecting shell syntax through the variable *name* lets an unprivileged upstream pipeline author execute commands in the stronger downstream job's shell context, exfiltrating that job's secrets/tokens — matching the "stronger-context command execution" impact class in scope.

### Likelihood Explanation
Feasibility depends on whether variable *keys* reaching this code path can contain `$`/backtick characters. GitLab's UI-defined CI/CD variables are typically restricted to identifier-safe names, but this restriction is enforced server-side (GitLab Rails), not inside `shells/bash.go`; the Runner code itself performs no such validation for `spec.Variable.Key` before calling `Variable`. Dotenv-produced variable names are also not validated by `helpers.DotEnvEscape`'s `isValidDotEnvKey` filter at this layer — that filter only guards `DotEnvVariables`, not `Variable`/`TmpFile`. Because the exact upstream validation chain from job payload to `spec.Variable.Key` could not be fully traced in the indexed code, this should be confirmed by a background agent tracing where `File`-type variables and dotenv-report variable keys are constructed before being handed to `Variable`.

### Recommendation
- In `TmpFile`/`Variable`, do not embed raw `variable.Key` bytes into the path and then rely on Go's `%q`. Either shell-escape the whole `variableFile` string with `b.escape(...)` (consistent with `variable.Value` handling), or restrict/validate `variable.Key` to a safe identifier pattern (e.g. `^[A-Za-z_][A-Za-z0-9_]*$`) before it is used to construct any file path or export statement, rejecting/sanitizing otherwise.
- Audit all other `%q` usages in `shells/bash.go` (`IfDirectory`, `IfFile`, `MkDir`, `RmFilesRecursive`, `RmDirsRecursive`, etc.) for the same class of issue whenever the interpolated string can contain attacker-controlled bytes rather than a runner-generated path.

### Proof of Concept
Go unit test target: `TestBashWriter_Variable_FileKeyInjection` in `shells/bash_test.go`.

```go
func TestBashWriter_Variable_FileKeyInjection(t *testing.T) {
    w := NewBashWriter(&common.Build{...}, "bash")
    w.Variable(spec.Variable{
        Key:   `FOO$(touch /tmp/pwned)BAR`,
        Value: "secret",
        File:  true,
    })
    script := w.String()

    // Assert the generated script does NOT contain a literal, unescaped
    // command-substitution sequence in a double-quoted context.
    assert.NotContains(t, script, `$(touch /tmp/pwned)`)
}
```

Expected (current, buggy) result: the assertion fails — the generated script literally contains `$(touch /tmp/pwned)` inside a `"..."` path argument, confirming the fix is needed. As an end-to-end PoC, run a job whose `File`-type variable key/dotenv-derived key contains `$(id > /tmp/pwned)` and confirm `/tmp/pwned` is created by the generated bash script even when the job's own `script:` never references that variable.
