### Title
Missing zero-amount validation in `createWriteOffRequest` lets a fulfiller seize escrowed tranche tokens for free - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` validates only that `amount != 0`; it never validates `underlyingsRequested`. A lender whose request records `underlyings == 0` exposes their escrowed tranche tokens to any unprivileged fulfiller: `fullfillWriteOffRequest` only enforces `_underlyings < currentRequest.underlyings`, so a zero-underlying request can be satisfied with a 0-token payment while the fulfiller receives the full tranche balance.

### Finding Description
The escrow is the credit-vault surface where lenders park tranche tokens pending a write-off deal with the borrower or any buyer:

- `createWriteOffRequest` pulls `amount` tranche tokens into escrow and stores `underlyings: currentRequest.underlyings + underlyingsRequested`, but only rejects `amount == 0` — `underlyingsRequested == 0` is accepted.
- `fullfillWriteOffRequest` is explicitly callable "by any wallet". Its price check is `currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings` → for a request with `underlyings == 0`, passing `_underlyings = 0` and `_tranches = currentRequest.tranches` succeeds. The fulfiller then receives `IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches)` while paying nothing.

This is the same bug class as the reported `setRedeemableSoftCap` missing `softCap == 0` check: a critical economic parameter (the ask price of escrowed tranche debt) is stored without a zero bound, and the zero value produces an absurd outcome — a free transfer of the escrowed asset.

### Impact Explanation
Any EOA can monitor `userRequests`/`pendingUnderlyings` and instantly fulfill a zero-priced request, receiving the victim's escrowed tranche tokens for 0 underlying (the 0-transfer and 0-fee paths execute fine). Tranche tokens represent a claim on credit-vault NAV redeemable via `requestWithdraw`/write-off flows, so this is direct theft of an interest-bearing position. Loss = the full escrowed tranche amount and its underlying value.

### Likelihood Explanation
Requires a lender to create (or top up) a request with `underlyingsRequested == 0` — e.g., a UI/integration that posts the tranche leg first and the price leg never lands, a partial-fill intent, or simple misconfiguration. Since fulfillment is permissionless and atomic, there is no window to cancel once broadcast; `deleteWriteOffRequest` cannot beat an attacker watching the mempool in the same block or later. The victim action is plausible but not guaranteed, hence medium.

### Recommendation
Add a lower bound on the ask in `createWriteOffRequest`:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol
if (amount == 0 || underlyingsRequested == 0) revert NotAllowed();
```

Optionally also require a minimum implied price (e.g., `underlyingsRequested` scaled by tranche decimals) to prevent dust-priced requests that round the exit fee to zero.

### Proof of Concept
Foundry test extending the existing harness in `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol` (same setup: `underlying`, `tranche`, `LP`, running epoch):

```solidity
function testFulfillZeroPriceRequestStealsTranches() external {
    uint256 requestedTranches = 10_000e18;

    // Victim lender creates a request while the epoch is running,
    // but with underlyingsRequested = 0 (no zero check exists).
    vm.startPrank(LP);
    tranche.approve(address(escrow), requestedTranches);
    escrow.createWriteOffRequest(requestedTranches, 0);
    vm.stopPrank();

    (uint256 tranchesStored, uint256 underlyingsStored) = escrow.userRequests(LP);
    assertEq(tranchesStored, requestedTranches);
    assertEq(underlyingsStored, 0);

    // Unprivileged attacker fulfills with 0 underlyings, 0 allowance needed.
    address attacker = makeAddr("attacker");
    uint256 balPre = tranche.balanceOf(attacker);

    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, requestedTranches, 0);

    // Attacker received all escrowed tranche tokens for free.
    assertEq(tranche.balanceOf(attacker) - balPre, requestedTranches);
    // LP received nothing; request cleared.
    (uint256 t2, uint256 u2) = escrow.userRequests(LP);
    assertEq(t2, 0);
    assertEq(u2, 0);
}
```

Key lines: `createWriteOffRequest` only checks `amount == 0` at `contracts/IdleCreditVaultWriteOffEscrow.sol:86-90`, while the fulfillment guard at lines 123-151 lets `_underlyings = 0` satisfy a `underlyings == 0` request and pay out the tranche tokens to `msg.sender`.
