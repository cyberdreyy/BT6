### Title
Loss-adjusted withdraw receipts are keyed by the post-increment epoch while claims look them up by the request epoch, letting withdrawers escape the `stopEpochWithDuration` haircut and over-claim funded underlyings - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`collectWithdrawFunds` stores the realized loss ratio under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` is already incremented inside `deposit()` during the same `stopEpoch` call (line 607-610). Claims and the request guard instead resolve the loss epoch through `lastWithdrawRequest[_user]`, which stores the epoch in which the request was made (one less). The haircut is therefore written under epoch N+1 and read under epoch N, so it is never applied — the closest analog to a use-after-free: a stale epoch pointer dereferences the wrong (empty) recovery slot.

### Finding Description
- `requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` where `currentEpoch = epochNumber` at request time (line 282). A request made during epoch 0 stores `0`.
- During `stopEpoch`/`stopEpochWithDuration`, the CDO calls `deposit()`, which runs while `isEpochRunning()` is still true and executes `epochNumber += 1` (lines 607-610). Only after that does `collectWithdrawFunds` run, and on a partial funding it writes `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (line 421) — i.e., under the *new* epoch N+1.
- On claim, `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` (the request epoch N) and looks up `lossRecoveryPriceByEpoch[N]`, which is `0`, so it returns 0 (lines 789-795).
- Execution then falls into `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` *at par* (lines 338-349). The gating check `epochNumber <= lastWithdrawRequest[_user]` passes because epochNumber was already bumped.
- The same stale-key mismatch exists in the "must claim before requesting again" guard (lines 261-270), which also reads `lossRecoveryPriceByEpoch[lastWithdrawRequest]` = 0, so nothing stops a follow-up request either.

Net effect: the loss haircut that `previewLossAdjustedWithdrawFunds`/`stopEpochWithDuration` intends to socialize across pending receipts is silently skipped, and every pending receipt claims 100%.

### Impact Explanation
Invariant broken: loss waterfall / fair burn. When the borrower funds less than `pendingWithdraws` (a `stopEpochWithDuration` loss), each withdrawer still receives the full `_amount`. The strategy only collected `pendingToFund < pendingBasis` underlying, so paying claims at par makes the strategy insolvent for the deficit: early claimants drain the strategy's funded underlyings (including, once `defaultRecoveryReserve != 0`, everything up to the reserve guard), and later claimants' receipts revert or are left unpaid — direct theft plus permanent freezing of the shortfall, quantified as `pendingBasis - pendingToFund` per loss epoch.

### Likelihood Explanation
Requires only an unprivileged tranche holder with a pending `requestWithdraw` in the epoch where the manager calls `stopEpochWithDuration(_lossAmount > 0)` — an honest manager action during any partial-loss epoch. No privileged misbehavior needed; the bug triggers deterministically on the key mismatch. The only caveat is that I could not trace `IdleCDOEpochVariant.stopEpoch` line-by-line to confirm `deposit()` precedes `collectWithdrawFunds`, but the code comments (lines 605-610: "deposit done on stopEpoch ... epochNumber += 1") and the `_onlyIdleCDO` ordering strongly indicate this sequence.

### Recommendation
Store the loss under the epoch the receipts actually belong to. In `collectWithdrawFunds`, write `lossRecoveryPriceByEpoch[epochNumber - 1]` (the epoch whose requests are being funded), or alternatively have `requestWithdraw`/claim paths consistently use `lastWithdrawRequest + 1`. Add a regression test: request in epoch N, `stopEpochWithDuration` with a loss, then claim — payout must equal `amount * lossRecoveryPrice / 1e18`.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVaultLossKey.t.sol — fork setup mirrors IdleCreditVault.t.sol
function testLossHaircutEscape() external {
    // 1. Deposit AA, start epoch 0, request withdraw of half.
    uint256 mintedAA = idleCDO.depositAA(10_000 * ONE_SCALE);
    _startEpoch();
    cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche)); // lastWithdrawRequest = 0

    // 2. Manager stops epoch with a 50% loss on the pending basis.
    //    deposit() bumps epochNumber to 1; collectWithdrawFunds writes
    //    lossRecoveryPriceByEpoch[1] = 0.5e18 — under the WRONG key.
    _stopEpochWithDurationLoss(lossAmount);

    assertEq(strategy.lastWithdrawRequest(address(this)), 0);
    assertEq(strategy.lossRecoveryPriceByEpoch(0), 0);   // lookup key is empty
    assertGt(strategy.lossRecoveryPriceByEpoch(1), 0);   // haircut stored one epoch too high

    // 3. Claim: _claimLossAdjustedWithdrawRequest finds price 0 at epoch 0,
    //    falls through to _claimFundedWithdrawRequest which pays at par.
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;

    // paid == full requested basis instead of basis * 0.5e18 / 1e18
    assertEq(paid, requestedBasis);          // haircut skipped
    // subsequent claimants of the same epoch now face an underfunded strategy
}
```
