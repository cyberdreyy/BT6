### Title
Unbounded zstd compression cost in `encode_account`/`encode_ui_account` for `Base64Zstd`-encoded large accounts - ([File: rpc/src/rpc.rs, account-decoder/src/lib.rs])

### Summary
`encode_account` in `rpc/src/rpc.rs` only enforces a size guard (`MAX_BASE58_BYTES`) for `Binary`/`Base58` encodings, but performs no size check before dispatching to `Base64Zstd`. `encode_ui_account` in `account-decoder/src/lib.rs` then unconditionally runs a full `zstd::stream::write::Encoder` pass over the entire account data (up to the runtime's max account size) on every `Base64Zstd`-encoded `getAccountInfo`/`getMultipleAccounts`/`getProgramAccounts` call.

### Finding Description
In `rpc/src/rpc.rs`, `encode_account` gates on data size only for `Binary`/`Base58`: [1](#0-0) 
For any other encoding, including `Base64Zstd`, it falls straight through to `encode_ui_account` with no length check.

In `account-decoder/src/lib.rs`, the `Base64Zstd` branch of `encode_ui_account` compresses the full (post-slice) account bytes unconditionally: [2](#0-1) 
There is no cap analogous to `MAX_BASE58_BYTES` (defined at `pub const MAX_BASE58_BYTES: usize = 128;`) for the zstd path. [3](#0-2) 

An attacker who controls an on-chain program can legitimately grow an account's data via CPI-based `realloc` up to the runtime's maximum permitted account size, filling it with high-entropy (incompressible) bytes. A single `getAccountInfo` (or `getMultipleAccounts`/`getProgramAccounts`) call with `encoding=base64+zstd` against that account will cause the RPC node to run `zstd::stream::write::Encoder::write_all` over the entire buffer and buffer the compressed output in a `Vec<u8>`, then base64-encode and JSON-serialize the result — all within a single low-rate request, with the cost scaling with the attacker-controlled account size rather than any RPC-imposed constant.

### Impact Explanation
This is a compute/memory amplification issue reachable via a single unprivileged JSON-RPC call (`getAccountInfo` with `Base64Zstd`), matching the "RPC sent to a validator can cause a large CPU/memory usage" style single-request DoS category. The cost is bounded by the maximum account size the runtime allows accounts to grow to, and — unlike the Base58 path — there is no explicit RPC-side limit preventing a full compression pass over that entire buffer. This can degrade RPC responsiveness for a single low-rate request, consistent with the "bounded by explicit limits, not size of attacker-authored data" invariant being violated. Impact is scoped to CPU/memory spike on the handling thread for a single request; it does not by itself imply a crash, consensus impact, or wrong data being returned.

### Likelihood Explanation
Feasible with only the described preconditions: an attacker-owned program capable of `realloc`-based account growth to the maximum size with random bytes, and a single `getAccountInfo` call with `encoding=base64+zstd`. This requires no validator/staked/gossip control, no multiple calls, and only standard system-program/BPF loader CPI realloc primitives available to any developer. Repeatability is unlimited (attacker can re-issue the read-only RPC call once per rate-limit window against the same account, no re-write needed).

### Recommendation
Add an explicit size guard for `Base64Zstd` (and consider one uniformly for all binary encodings) analogous to the `MAX_BASE58_BYTES` check in `encode_account`, e.g., reject or fall back to plain `Base64` (without compression) when the sliced account data exceeds a defined cap, or impose a maximum output-size / CPU-time budget on the zstd encoder invocation in `encode_ui_account`.

fn test_base64_zstd_incompressible_large_account_cost() {

        &account,
        UiAccountEncoding::Base64Zstd,
        None,
        None,
    );
    let elapsed = start.elapsed();

    // Assert there is no explicit bound stopping full compression of
    // a maximally-sized account, i.e. this succeeds and takes
    // non-trivial, size-proportional time/memory instead of being
    // rejected the way encode_account rejects oversized Base58 requests.
    match encoded.data {
        UiAccountData::Binary(_, UiAccountEncoding::Base64Zstd) => {
            // No size-based rejection occurred, confirming the missing bound.
        }
        _ => panic!("expected zstd-encoded output"),
    }
    println!("compression of 10MB incompressible data took {:?}", elapsed);
}

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
