### Title
Front-runnable, unsigned `InitializeNonceAccount` allows authority hijack of a durable-nonce account - (File: `programs/system/src/system_instruction.rs`)

### Summary
The System Program's `InitializeNonceAccount` instruction transitions a nonce account from `State::Uninitialized` to `State::Initialized`, permanently fixing the account's `authority` field. Unlike every other privileged nonce operation in the same file (`withdraw_nonce_account`, `advance_nonce_account`, `authorize_nonce_account`), `initialize_nonce_account` performs **no signer check whatsoever** on the account or on any other party — it only verifies the account is writable, currently `Uninitialized`, and rent-exempt. This is the direct analog of the reported `setReserve()` issue: a state-defining setter with no access control that can be front-run by any unprivileged transaction sender before the legitimate initializer lands.

### Finding Description
`initialize_nonce_account` in [1](#0-0)  only checks `account.is_writable()`, `State::Uninitialized`, and sufficient lamports for rent — it never calls `check_signer` on the account key or any other pubkey, and never validates that the caller is the account's creator.

Contrast this with the other three nonce operations in the same module, which all explicitly require a signature tied to the account or its current authority:
- `withdraw_nonce_account` calls `check_signer(from.get_key())` (uninitialized case) or `check_signer(&data.authority)` (initialized case) — [2](#0-1) 
- `authorize_nonce_account` requires the current authority to be in `signers` via `Versions::authorize` — [3](#0-2) 

The dispatch site in `system_processor.rs` confirms this asymmetry: `InitializeNonceAccount` is routed straight to `initialize_nonce_account(&mut me, &authorized, &rent, invoke_context)` with no signer argument passed or checked, while `AdvanceNonceAccount`/`WithdrawNonceAccount` explicitly pass the `signers` set derived from `instruction_context.get_signers()` [4](#0-3) .

Because Solana clients typically create a nonce account and initialize it in **two separate instructions/transactions** (`CreateAccount` funds+assigns the account to the System Program; `InitializeNonceAccount` sets the authority afterward), the account exists on-chain in `State::Uninitialized` between the two calls. Since `InitializeNonceAccount` requires no signature at all — the account only needs to be listed as `writable` in the attacker's transaction — any unprivileged sender who observes or predicts the newly-created, not-yet-initialized nonce account address can submit their own `InitializeNonceAccount` instruction naming themselves (or any pubkey) as `nonce_authority`. If this attacker transaction lands (e.g., by being included in the same or an earlier slot due to normal transaction race conditions) before the legitimate initializer transaction, the account state moves to `Initialized` with the attacker's chosen authority. The legitimate initializer's subsequent `InitializeNonceAccount` call then fails with `InstructionError::InvalidAccountData` (already `Initialized`), permanently locking out the rightful owner [5](#0-4) .

### Impact Explanation
Once the attacker becomes the account's `authority`, they gain exclusive rights (per `check_signer(&data.authority)` in `withdraw_nonce_account`) to withdraw all lamports funded into the account by the legitimate creator via `WithdrawNonceAccount`, and exclusive rights to advance/reassign the durable nonce via `AdvanceNonceAccount`/`AuthorizeNonceAccount`. This constitutes a concrete unsigned fund-movement primitive: the rightful funder deposited rent-exempt lamports expecting to control the account, but an unprivileged attacker — without ever signing with the account's own key or any authorized key — can seize permanent authority and later drain the account's lamports to an address of their choosing.

### Likelihood Explanation
This is reachable from any single unprivileged transaction: the attacker only needs to know the (soon-to-be) nonce account's public key (predictable if derived deterministically, or observable once the funding `CreateAccount` transaction is visible/pending) and submit an `InitializeNonceAccount` instruction referencing it as writable — no signature over that account is required by the program logic. The race is a standard transaction-ordering/front-run scenario analogous to the reported `setReserve()` issue, not a hypothetical: it requires no special leader/validator behavior, only that the account remains in `Uninitialized` state momentarily, which is the normal window between a client's `CreateAccount` and `InitializeNonceAccount` calls when they are not atomically bundled.

### Recommendation
Require `initialize_nonce_account` to check that a designated party has signed — most commonly, that the account being initialized (or a specified authority hint) is itself a signer, mirroring the pattern used by `authorize_nonce_account`/`withdraw_nonce_account`. Alternatively/additionally, document and enforce (at the client/tooling level and ideally at the protocol level) that `CreateAccount` and `InitializeNonceAccount` must be submitted atomically within a single transaction so no externally-observable `Uninitialized` window exists on-chain for an attacker to race.

### Proof of Concept
1. Legitimate user submits `CreateAccount` (System Program) creating account `N`, funded with rent-exempt lamports, owned by the System Program, in `State::Uninitialized` (default nonce state per `State::default() == State::Uninitialized`, see test at [6](#0-5) ).
2. Before the user's follow-up `InitializeNonceAccount(user_authority)` transaction is processed, an attacker submits their own transaction containing `SystemInstruction::InitializeNonceAccount(attacker_authority)` with account `N` listed as writable (no signature over `N` needed).
3. `initialize_nonce_account` proceeds because it only checks `is_writable`, `State::Uninitialized`, and rent — see [7](#0-6) . Account `N` becomes `State::Initialized(Data { authority: attacker_authority, .. })`.
4. The legitimate user's `InitializeNonceAccount` now fails with `InstructionError::InvalidAccountData` since the state is already `Initialized` — [5](#0-4) .
5. Attacker later submits `WithdrawNonceAccount` signed by `attacker_authority` and drains all lamports from `N` to any destination they choose, since `check_signer(&data.authority)` is satisfied by the attacker's own signature — [8](#0-7) .

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}
