### Title
Timeout-induced `LocallyRejected(ConnectivityIssues)` permanently discards a later legitimate `BlockValidateOk` for the same block, wedging a signer from ever signing a block its own node just validated - (File: `stacks-signer/src/v0/signer.rs::check_submitted_block_proposal` / `handle_block_validate_ok`)

### Summary
`check_submitted_block_proposal` marks a block `LocallyRejected` with `RejectReason::ConnectivityIssues` purely because the node's validation response did not arrive within `block_proposal_validation_timeout`, and immediately broadcasts a rejection and persists this as the block's decided state. `BlockInfo`'s state machine treats `LocallyRejected`/`LocallyAccepted` as terminal, one-way transitions (evidenced by `mark_locally_rejected()` returning an `Err` once a decision already exists), so a subsequent, late-arriving `BlockValidateResponse::Ok` for the identical `signer_signature_hash` is not applied on top of the stale timeout rejection.

### Finding Description
The relevant code confirmed in `stacks-signer/src/v0/signer.rs`: [1](#0-0) 

shows that on timeout the signer builds a rejection with `RejectReason::ConnectivityIssues`, calls `block_info.mark_locally_rejected()`, sends the rejection response, and persists the block state — all without any confirmation from the node that the block content is actually invalid; the rejection reason is explicitly about failing to receive a validation response in time, not about block content: [2](#0-1) 

The response dispatch path shows that a later `BlockValidateResponse::Ok` for the same block is routed through `handle_block_validate_ok`: [3](#0-2) 

`BlockInfo`'s decision fields (`LocallyRejected`/`LocallyAccepted`) are modeled as terminal: the timeout path itself only tolerates an `Err` from `mark_locally_rejected()` when the block has *already* reached global consensus, implying that once local state is set it is not meant to be overwritten by a later call from the opposite direction. Given this one-way state design, `handle_block_validate_ok`'s decision guard (skip-if-already-decided) treats any pre-existing local decision — including a timeout-manufactured `LocallyRejected(ConnectivityIssues)` — as final, so the arriving proof of validity from the trusted node is discarded rather than reconciled.

The root cause is a category conflation: `ConnectivityIssues` is a "we don't know" outcome (a fail-closed placeholder for a missing answer), not a "we know it's invalid" outcome, yet it is stored using the same terminal `LocallyRejected` state as a genuine content-based rejection, and the guard in `handle_block_validate_ok` cannot distinguish the two when the real answer shows up late.

Attacker capability required: the attacker only needs to be the block proposer (win a miner slot) and craft a block whose validation is slow enough on at least one victim signer's node to exceed `block_proposal_validation_timeout` (e.g., by stuffing it with many/expensive transactions), then let the node's real validation complete afterward. No majority-signer collusion, no node-operator access, and no auth token are needed — this matches the permitted unprivileged, single-miner-slot threat model.

### Impact Explanation
This breaks the bounded-liveness guarantee: a signer becomes permanently unable to sign a specific proposal instance it has already been proven valid for by its own trusted node, purely due to a self-inflicted, transient timing artifact. This is a tenure-scoped, single-signer liveness loss (a signer "wedged into never signing valid blocks"), matching the High-severity liveness category in the rubric. It does not break validity/uniqueness/canonicity and is not shared across signers deterministically (each signer's own timeout/response race is independent), so it is not a chain-safety break, but it can repeatably degrade a signer's participation whenever this race occurs, and an attacker can deliberately try to trigger it via block construction that stresses node validation latency.

### Likelihood Explanation
Preconditions: the signer must have already submitted the block for validation (`submit_block_for_validation`), the node's response must not arrive before `block_proposal_validation_timeout`, and the true `BlockValidateResponse::Ok` must arrive afterward for the same `signer_signature_hash`. This can occur naturally under node/database load, and can plausibly be induced deliberately by an attacker who controls block contents (as a miner) and crafts transactions/state accesses that slow down validation just past the configured timeout. It requires only the attacker's own miner slot and normal gossip of the (unmodified) proposal — no privileged role. It is repeatable per proposal instance whenever the race condition is hit, though it affects one signer instance at a time rather than the network at large.

### Recommendation
Do not conflate a timeout-based "unknown" outcome with a decided rejection. Options:
1. Introduce a distinct non-terminal state (e.g., `LocallyRejectedPendingReval` or a dedicated flag alongside `ConnectivityIssues`) that still broadcasts a rejection for liveness reasons but permits `handle_block_validate_ok` to override it with `mark_locally_accepted` if the true validation response later arrives for the same hash and no global consensus has been reached.
2. Alternatively, have `handle_block_validate_ok` explicitly check the stored `reject_reason`; if it is `ConnectivityIssues` (a "we don't know" reason) and consensus hasn't been reached, allow the local decision to be overwritten by the fresh validation result.
3. At minimum, allow a resubmission/re-validation path that clears the stale `ConnectivityIssues` state once a definitive answer is available.

### Proof of Concept
Rust test plan (stacks-signer, using the `v0::signer::Signer` test harness / `BlockInfo` + `SignerDb`):
1. Construct a `NakamotoBlock` and corresponding `BlockInfo`, insert into `SignerDb`, and set `submitted_block_proposal = Some((signer_signature_hash, Instant::now() - block_proposal_validation_timeout - Duration::from_secs(1)))` to simulate an already-elapsed timeout.
2. Call `check_submitted_block_proposal()`. Assert:
   - `block_info.reject_reason` is `Some(RejectReason::ConnectivityIssues(_))`.
   - `block_info` state is `LocallyRejected`.
   - A `BlockResponse::Rejected` was sent/recorded.
3. Construct a `BlockValidateOk` for the same block/`signer_signature_hash` and call `handle_block_validate_response` → `handle_block_validate_ok`.
4. Assert (the wedge):
   - `signer_db.block_lookup(&signer_signature_hash)` still reports `LocallyRejected` (not `LocallyAccepted`).
   - No `BlockResponse::Accepted` was ever sent for this hash after step 3.
   - Contrast case: repeat steps with no prior timeout (send `BlockValidateOk` directly) and assert the block *does* transition to `LocallyAccepted` and an `Accepted` response is sent — proving the discrepancy is caused specifically by the pre-existing stale `ConnectivityIssues` rejection.

    /// Check the current tracked submitted block proposal to see if it has timed out.
    /// Broadcasts a rejection and marks the block locally rejected if it has.
    fn check_submitted_block_proposal(&mut self) {
        let Some((proposal_signer_sighash, block_submission)) =
            self.submitted_block_proposal.take()
        else {
            // Nothing to check.
            return;
        };
        if block_submission.elapsed() < self.block_proposal_validation_timeout {
            // Not expired yet. Put it back!
            self.submitted_block_proposal = Some((proposal_signer_sighash, block_submission));
            return;
        }
        // For mutability reasons, we need to take the block_info out of the map and add it back after processing
        let mut block_info = match self.signer_db.block_lookup(&proposal_signer_sighash) {
            Ok(Some(block_info)) => {
                if block_info.has_reached_consensus() {
                    // The block has already reached consensus.
                    return;
                }
                block_info
            }
            Ok(None) => {
                // This is weird. If this is reached, its probably an error in code logic or the db was flushed.
                // Why are we tracking a block submission for a block we have never seen / stored before.
                error!("{self}: tracking an unknown block validation submission.";
                    "signer_signature_hash" => %proposal_signer_sighash,
                );
                return;
            }
            Err(e) => {
                error!("{self}: Failed to lookup block in signer db: {e:?}",);
                return;
            }
        };
        // We cannot determine the validity of the block, but we have not reached consensus on it yet.
        // Reject it so we aren't holding up the network because of our inaction.
        warn!(
            "{self}: Failed to receive block validation response within {} ms. Rejecting block.", self.block_proposal_validation_timeout.as_millis();
            "signer_signature_hash" => %proposal_signer_sighash,
        );
        let rejection = self.create_block_rejection(
            RejectReason::ConnectivityIssues(
                "failed to receive block validation response in time".to_string(),
            ),
            &block_info.block,
        );
        block_info.reject_reason = Some(rejection.response_data.reject_reason.clone());
        if let Err(e) = block_info.mark_locally_rejected() {
            if !block_info.has_reached_consensus() {
                warn!("{self}: Failed to mark block as locally rejected: {e:?}");
            }
        };
        self.send_block_response(&block_info.block, rejection.into());

        self.signer_db
            .insert_block(&block_info)
            .unwrap_or_else(|e| self.handle_insert_block_error(e));
    }
