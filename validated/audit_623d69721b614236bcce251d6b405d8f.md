## Analog Found

### Title
Unchecked integer addition in L1 deposit opaque-data length decoding can overflow/panic - (File: `crates/consensus/protocol/src/deposits.rs`)

### Summary
The CVE describes an "incorrect integer overflow protection mechanism" in a size/length calculation used to slice a buffer before rendering — one arithmetic path had overflow protection while a sibling, similarly-shaped calculation did not. The same asymmetric-protection pattern exists in `Deposits::decode`, the function that turns an L1 `TransactionDeposited` log into an L2 deposit transaction during derivation.

### Finding Description
`Deposits::decode` reads an attacker-controlled 32-byte length field from L1 log data and treats it as `opaque_content_len: u64` [1](#0-0) . Immediately after, the code computes a *padding* bound using overflow-safe arithmetic:

```
let opaque_data_ceil_32: u64 = (opaque_content_len.saturating_add(31) / 32).saturating_mul(32);
let Some(padding_end): Option<u64> = 64_u64.checked_add(opaque_data_ceil_32) else { ... };
``` [2](#0-1) 

But the *content* slice bound just below it uses plain, unchecked addition instead of the same `checked_add`/`saturating_add` pattern:

```
let Some(opaque_data) = &log.data.data.get(64..64 + opaque_content_len as usize) else { ... };
``` [3](#0-2) 

`opaque_content_len` is only bounded by `u64` (via the `try_into` at line 96-100) — it does not have to correspond to the actual number of bytes present in `log.data.data`. Because any L1 contract can emit an arbitrary log with the `TransactionDeposited` topic/selector (the derivation pipeline only checks the topic hash, not who emitted it), an attacker fully controls the 32-byte "length" word and can set it to a value near `u64::MAX`. The expression `64 + opaque_content_len as usize` is then computed with plain `+`, which overflows: this panics in any build with arithmetic-overflow checks enabled (the standard Rust default in debug builds, and in test/dev profiles), and silently wraps in release builds without `overflow-checks = true`. I could not confirm from the visible portion of the workspace root `Cargo.toml` whether a `[profile.release]` section explicitly enables `overflow-checks`; the file contains `[profile.*]` sections I was unable to fully inspect within this session, so this should be verified directly.

### Impact Explanation
- If overflow checks are enabled in the build used for derivation/verification (debug, and potentially any hardened release profile), a single malicious L1 log — emittable by any L1 contract deployer/depositor mimicking the deposit event shape — causes a deterministic panic inside the L1→L2 derivation pipeline. Because every rollup node (sequencer, verifier, and the fault-proof program that replays derivation) executes this same code path deterministically over L1 data, this is a reachable **node halt** for the class of "derivation of attacker-written L1 deposit ... data" explicitly listed as in-scope.
- If overflow checks are disabled, the wrapped value silently produces a different (attacker-influenced) `opaque_data` slice than the length nominally declared, which is inconsistent with the intent of the length-validation logic that immediately follows (`is_multiple_of(32)` / padding-zero check) — the same "incorrect integer overflow protection" bug class as the CVE, where one of the length checks is bypassed by integer wraparound.

### Likelihood Explanation
The `TransactionDeposited`-shaped log can be emitted by any L1 address (EOA-deployed contract) with fully attacker-chosen `data`, without needing any special privilege, deposit funds, or coordination — this matches the "depositor" reachable path called out explicitly in scope. Triggering the bug requires only setting the 32-byte length word near `u64::MAX` (e.g. `u64::MAX - 63`), well within the `try_into::<u64>()` bound already validated at line 96-100.

### Recommendation
Replace the unchecked `64 + opaque_content_len as usize` computation with `64_u64.checked_add(opaque_content_len)` (or `saturating_add`) mirroring the protection already applied to `padding_end`, and reject the log with `DepositDecodeError::InvalidOpaqueDataLength`/a new overflow-specific error before performing any slicing arithmetic, exactly matching the pattern used for `opaque_data_ceil_32`/`padding_end`.

### Proof of Concept
1. Craft an L1 log with `topics[0] == Deposits::EVENT_ABI_HASH`, valid `from`/`to` topics, `topics[3]` (version) `== B256::ZERO`.
2. Set `log.data.data[0..32]` to the offset word `32` (required check at line 87-92).
3. Set `log.data.data[32..64]` to a `u64` value close to `u64::MAX` (e.g. `0xFFFF_FFFF_FFFF_FFC0`), which passes the `try_into::<u64>()` check at line 96-100.
4. Provide only a short `log.data.data` buffer (e.g. 64 bytes total, satisfying the `% 32 == 0` alignment check at line 49-51).
5. Call `Deposits::decode(block_hash, index, &log)`. The expression `64 + opaque_content_len as usize` at line 113 overflows `usize`, panicking in any overflow-checked build (or producing a wrapped/incorrect bound otherwise) instead of hitting the intended `InvalidOpaqueDataLength` error path.
