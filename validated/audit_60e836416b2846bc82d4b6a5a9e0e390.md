### Title
Missing interest accrual before interest-rate reconfiguration causes retroactive misapplication of new rates to elapsed time - (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`, `programs/marginfi/src/instructions/marginfi_group/configure_bank_lite.rs`)

### Summary
The Sherlock H-3 finding shows that a global, time-integrated reward/rate parameter (`lumPerSecond`/pool weight) was changed via `setTopPoolIdsWithWeights` without first "closing out" the accrual window (`updateAll`), so the *new* weight was later applied retroactively across the *entire* stale interval, including periods where it should not have applied. marginfi-v2 has a structurally identical pattern in its interest-accrual system: `Bank.last_update` marks the last time interest was accrued, and `accrue_interest` applies the bank's *current* `interest_rate_config` across the whole `time_delta = current_timestamp - last_update` in one shot [1](#0-0) . Both `lending_pool_configure_bank` and `lending_pool_configure_bank_interest_only` mutate `bank.config.interest_rate_config` (or other rate-affecting config) but neither calls `accrue_interest` first to snapshot/settle the pending interest at the old rate before installing the new rate.

### Finding Description
`accrue_interest` computes one lump-sum interest update using the interest-rate curve found in `self.config.interest_rate_config` at the time it is called, applied over the *entire* elapsed time since `self.last_update`: [2](#0-1) [3](#0-2) 

`self.last_update` is only advanced inside `accrue_interest` (and `update_bank_cache`), not inside the config-mutation path [4](#0-3) .

`lending_pool_configure_bank` (the general admin config instruction) directly calls `bank.configure(&bank_config)`, which updates `self.config.interest_rate_config` in place, with **no preceding call to `bank.accrue_interest(...)`**: [5](#0-4) [6](#0-5) 

Likewise, `lending_pool_configure_bank_interest_only` updates `interest_rate_config` directly and validates it, again with no accrual step beforehand: [7](#0-6) 

By contrast, other instructions in the same codebase that mutate bank economic state *do* correctly call `bank.accrue_interest(...)` first to close out the stale window before applying a state change, e.g. `lending_pool_emissions_deposit` in the very same file: [8](#0-7) 

This shows the protocol is aware that pending accrual must be settled before changing state that affects the accrual calculation — the config-mutation paths omit this step.

As a result, if `last_update` is stale (any bank not accrued recently, or between the config change and the next interaction) when the admin reconfigures the interest curve, the very next `accrue_interest` call (triggered permissionlessly by `lending_pool_accrue_bank_interest`, or automatically inside `deposit`/`borrow`/`withdraw`/`repay`/`liquidate`) will compound the *entire* elapsed interval — spanning time both before and after the config change — using only the **new** rate curve. The period that should have accrued under the old curve is silently repriced under the new curve.

### Impact Explanation
This causes an exploitable misvaluation of accrued interest/fees shared among all depositors and borrowers in the bank:
- If the admin lowers rates (e.g., to reduce borrow cost), any borrower can trigger accrual immediately afterward and have the *entire* stale interval — including time when the higher old rate should have applied — retroactively priced at the new, lower rate, underpaying interest owed to depositors and underpaying protocol/insurance fees.
- If the admin raises rates, the reverse happens: depositors extract windfall interest for a period during which the lower rate should have applied, at the expense of borrowers or the protocol fee split.
- Because `accrue_interest` is reachable via the permissionless `lending_pool_accrue_bank_interest` instruction (no signer restriction beyond a paused-protocol check) as well as automatically during any deposit/withdraw/borrow/repay/liquidation, an unprivileged user can choose the timing of the accrual trigger relative to a known/observed admin config change to maximize the benefit of this misapplied-rate window, directly redirecting value between depositors, borrowers, and the protocol/insurance fee recipients.

### Likelihood Explanation
Requires two ingredients that are both realistic in production: (1) `last_update` not fully fresh at the moment the admin submits `lending_pool_configure_bank` / `lending_pool_configure_bank_interest_only` (there is no requirement or CPI-level enforcement to accrue immediately beforehand — any accrual gap, even a few blocks, is enough), and (2) an unprivileged actor calling/triggering the next accrual (trivial, since accrual is either permissionless or automatically bundled into ordinary user actions like deposit/withdraw/borrow). No special permissions are needed to trigger the mispriced accrual once the stale window exists.

### Recommendation
Have `lending_pool_configure_bank` and `lending_pool_configure_bank_interest_only` call `bank.accrue_interest(current_timestamp, &group, ...)` (and `update_bank_cache`) **before** mutating `interest_rate_config` (and any other accrual-relevant fields), mirroring the pattern already used in `lending_pool_emissions_deposit`. This ensures `last_update` is advanced and all pending interest is settled under the *old* curve prior to the new curve taking effect, so no interval is ever priced under the wrong rate.

### Proof of Concept
Conceptual sequence (mirrors the H-3 PoC structure):
1. Bank B has `interest_rate_config` R1 and `last_update = T0`. Time advances so utilization has accrued interest but no `deposit/borrow/withdraw/repay/accrue_bank_interest` call has happened since `T0` (elapsed `T1 - T0`, e.g. several hours/days).
2. Admin calls `lending_pool_configure_bank`/`lending_pool_configure_bank_interest_only` at time `T1`, changing `interest_rate_config` to R2 (e.g., lowering the borrow rate curve). Per `configure`/`update`, `bank.config.interest_rate_config` becomes R2 immediately; `bank.last_update` remains `T0` [6](#0-5) .
3. Any user calls the permissionless `lending_pool_accrue_bank_interest` (or performs a deposit/borrow/withdraw) at time `T1` (or slightly after). `accrue_interest` computes `time_delta = T1 - T0` and applies R2's rate curve over the *entire* `T1 - T0` window [2](#0-1) , even though R1 was in effect for all of `[T0, T1)`.
4. Depositors/borrowers end up with interest and fees computed as if R2 had applied since `T0`, rather than R1 applying `[T0, T1)` and R2 applying from `T1` onward — an outcome directly analogous to the H-3 PoC where pool weights set at `T1` were incorrectly backdated across `[0, T1)`.

pub fn lending_pool_configure_bank(
    ctx: Context<LendingPoolConfigureBank>,
    bank_config: BankConfigOpt,
) -> MarginfiResult {
    let mut bank = ctx.accounts.bank.load_mut()?;

    // If settings are frozen, you can only update the deposit and borrow limits, everything else is ignored.
    if bank.get_flag(FREEZE_SETTINGS) {
        bank.configure_unfrozen_fields_only(&bank_config)?;

        msg!("WARN: Only deposit+borrow limits updated. Other settings IGNORED for frozen banks!");

        emit!(LendingPoolBankConfigureFrozenEvent {
            header: GroupEventHeader {
                marginfi_group: ctx.accounts.group.key(),
                signer: Some(*ctx.accounts.admin.key)
            },
            bank: ctx.accounts.bank.key(),
            mint: bank.mint,
            deposit_limit: bank.config.deposit_limit,
            borrow_limit: bank.config.borrow_limit,
        });
    } else {
        // Settings are not frozen, everything updates
        bank.configure(&bank_config)?;
        msg!("Bank configured!");

        let group = ctx.accounts.group.load()?;
        bank.emode.validate_entries_with_liability_weights(
            &bank.config,
            group.emode_max_init_leverage,
            group.emode_max_maint_leverage,
        )?;

        emit!(LendingPoolBankConfigureEvent {
            header: GroupEventHeader {
                marginfi_group: ctx.accounts.group.key(),
                signer: Some(*ctx.accounts.admin.key)
            },
            bank: ctx.accounts.bank.key(),
            mint: bank.mint,
            config: bank_config,
        });
    }

    Ok(())
}

pub fn lending_pool_configure_bank_interest_only(
    ctx: Context<LendingPoolConfigureBankInterestOnly>,
    interest_rate_config: InterestRateConfigOpt,
) -> MarginfiResult {
    let mut bank = ctx.accounts.bank.load_mut()?;
    msg!(
        "Configuring bank: {:?} mint: {:?}",
        ctx.accounts.bank.key(),
        bank.mint
    );

    // If settings are frozen, interest rates can't update.
    if bank.get_flag(FREEZE_SETTINGS) {
        msg!("WARN: Bank settings frozen, did nothing.");
    } else {
        bank.config
            .interest_rate_config
            .update(&interest_rate_config);
        bank.config.interest_rate_config.validate()?;
        msg!("Bank configured!");
    }

    Ok(())
}
