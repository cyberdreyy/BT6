Confirmed: `readLoop` at [1](#0-0)  processes each incoming Gateway websocket message **synchronously in a single goroutine per gateway connection**, calling `handler.HandleGatewayMessage(ctx, ...)` directly in the read loop and only proceeding to the next message after it returns. This makes the unconditional, non-`select` channel send in `OutgoingConnectorHandler.HandleGatewayMessage` a real deadlock hazard.

### Title
Unbounded blocking send in `HandleGatewayMessage` rate-limit path can permanently stall a node's Gateway message loop - (File: core/capabilities/webapi/outgoing_connector_handler.go)

### Summary
`HandleGatewayMessage` routes incoming Gateway responses to a per-request, buffer-1 channel obtained from `responses.get()`. The rate-limited error path writes to that channel with a bare, unselectable send (`ch <- &errMsg`), unlike the normal-response path, which is wrapped in a `select` with a `ctx.Done()` escape. If two responses for the same `messageID` are delivered before the sole reader in `handleSingleNodeRequest` drains the channel, the second writer can block forever, and because `HandleGatewayMessage` is invoked synchronously inside the connector's single-goroutine `readLoop`, that goroutine — and therefore all subsequent message processing for that Gateway connection — hangs indefinitely, mirroring the "gossiper shutdown deadlock" bug class (unbuffered/undrained error channel receiving a second send with no reader).

### Finding Description
`OutgoingConnectorHandler` creates a `chan *api.Message` with capacity 1 per outstanding request via `responses.new()` [2](#0-1) . The single reader is in `handleSingleNodeRequest`, which reads at most once via `select { case resp := <-ch: ...; case <-ctx.Done(): ... }` and then returns, after which `defer c.responses.cleanup(messageID)` removes the channel from the map [3](#0-2) [4](#0-3) .

`HandleGatewayMessage` looks up this channel by `messageID` and, if the incoming sender/global rate limit is exceeded, sends an error message with a bare, non-`select` statement:
```go
ch <- &errMsg
return nil
``` [5](#0-4) 

In contrast, the legitimate-response branch is guarded:
```go
select {
case ch <- msg:
    return nil
case <-ctx.Done():
    return nil
}
``` [6](#0-5) 

If two `HandleGatewayMessage` invocations occur for the same `messageID` before the reader drains the buffer-1 channel (e.g., the Gateway delivers a duplicate/retransmitted response, or a legitimate response and a rate-limited response race), the first send fills the buffer and is consumed once by `handleSingleNodeRequest`, which then returns and stops reading forever (the channel is removed from `responses.chs` in `cleanup`, but the already-obtained local `ch` reference used by the blocked sender is unaffected — it is simply never read again). The second writer, if it takes the rate-limit branch, blocks on `ch <- &errMsg` with no `select`/`ctx.Done()` escape and hangs permanently.

Because `HandleGatewayMessage` is invoked synchronously from `gatewayConnector.readLoop` — a single goroutine per gateway that processes messages one at a time (`err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)` inside the `for { select { ... } }` loop) [7](#0-6)  — a single blocked call freezes that entire read loop. No further messages from that Gateway (for any method/handler sharing the connection) will ever be processed again, and the goroutine leaks even across `Close()`, since `Close()` only closes `shutdownCh` and waits via `closeWait.Wait()` [8](#0-7)  — the blocked `readLoop` goroutine will never observe `<-c.shutdownCh` because it is stuck mid-iteration on the channel send, causing `Close()`/shutdown to hang, directly analogous to the reported "gossiper shutdown deadlock."

### Impact Explanation
A stuck `readLoop` goroutine means the affected node stops processing **all** Gateway-originated responses/requests on that connection — a denial of service for that node's HTTP/WebAPI/Compute/WorkflowSyncer capability traffic routed through the Gateway. It can also make graceful node shutdown hang (`GatewayConnector.Close()` blocks on `closeWait.Wait()`), requiring a forced kill/restart. This is a service-availability impact rather than fund loss or key disclosure, so severity is moderate.

### Likelihood Explanation
Triggering requires timing such that two responses for the same `messageID` arrive before the single reader drains the buffer — this can plausibly happen when Gateway retransmits a message (e.g., following a reconnect or resend-on-timeout logic) or when a rate-limited response races with a legitimate one for the same outstanding request. This is reachable via normal externally-triggered request/response flow through the Gateway (unprivileged client → Gateway → node), not requiring a malicious node/peer, satisfying the "unprivileged-actor" scope, but exact reproduction depends on Gateway-side retry/timing behavior which I could not fully verify from the indexed files (Gateway-side resend logic was not inspected in this pass).

### Recommendation
Wrap the rate-limit error send in the same non-blocking/`select`-guarded pattern used for the legitimate-response branch, e.g.:
```go
select {
case ch <- &errMsg:
case <-ctx.Done():
}
return nil
```
Additionally, consider increasing the channel buffer to tolerate a second in-flight send (mirroring the LND fix's "buffer up to two messages" approach) and/or having `responses.get()` return `false` once a response has already been delivered/consumed to eliminate the race outright.

### Proof of Concept
1. Node establishes a `HandleSingleNodeRequest` call, registering a channel for `messageID = "X"` via `responses.new`.
2. Gateway (or a compromised/duplicating path) delivers two `jsonrpc.Request` frames referencing `messageID = "X"` in quick succession over the same websocket connection.
3. `readLoop` processes the first frame synchronously, calling `HandleGatewayMessage`, which either writes a valid `msg` or `errMsg` into the buffer-1 channel — succeeding immediately.
4. `handleSingleNodeRequest`'s `select` reads that single message and returns, triggering `responses.cleanup("X")`.
5. `readLoop` processes the second frame for the same (stale) `messageID`; `responses.get("X")` still returns the local channel reference held from before cleanup runs concurrently, or a genuine race window exists between concurrent deliveries prior to the first read — the second `HandleGatewayMessage` call reaches the rate-limit branch and executes `ch <- &errMsg`, which now blocks forever because nothing will ever read `ch` again.
6. `readLoop` for that gateway is now permanently stuck; all further messages from that Gateway are never processed, and `GatewayConnector.Close()` hangs on `closeWait.Wait()`.

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}
```

func (c *gatewayConnector) Close() error {
	return c.StopOnce("GatewayConnector", func() (err error) {
		c.lggr.Info("closing gateway connector")
		close(c.shutdownCh)
		var errs error
		for _, gatewayState := range c.gateways {
			errs = errors.Join(errs, gatewayState.conn.Close())
		}
		c.closeWait.Wait()
		return errs
	})
}

func (r *responses) new(id string) (chan *api.Message, error) {
	r.mu.Lock()
	defer r.mu.Unlock()

	_, ok := r.chs[id]
	if ok {
		return nil, fmt.Errorf("already have response for id: %s", id)
	}

	// Buffered so we don't wait if sending
	ch := make(chan *api.Message, 1)
	r.chs[id] = ch
	return ch, nil
}
