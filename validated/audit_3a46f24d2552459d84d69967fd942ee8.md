## Analysis Summary

The wKeyDAO report describes an **unprotected function** — missing access control that let an unprivileged caller trigger privileged logic. Searching the chainlink node's HTTP API layer for the closest concrete analog (per the allowed scope: node API auth/roles, session/token/external-initiator handling), I found a genuine access-control gap in the External Initiator management routes.

### Title
Missing role check on External Initiator listing endpoint - (File: `core/web/router.go`)

### Summary
The `GET /v2/external_initiators` route is registered without any `RequiresEditRole`/`RequiresAdminRole`/`RequiresRunRole` wrapper, unlike every other mutating or listing route for the same resource and unlike comparable sensitive-resource index routes.

### Finding Description
In `v2Routes`, the external initiator routes are defined as: [1](#0-0) 

Note that `Create` and `Destroy` are wrapped in `auth.RequiresEditRole(...)`, but `Index` is registered bare: `authv2.GET("/external_initiators", paginatedRequest(eia.Index))`. Because the enclosing `authv2` group only requires *any* successfully authenticated user (via `AuthenticateByToken` or `AuthenticateBySession`, see `core/web/router.go:245-248`), a user authenticated with the lowest privilege role (`view`, or even the auto-assigned `run` role granted to any External Initiator caller per `AuthenticateExternalInitiator`) can call this endpoint: [2](#0-1) 

The role hierarchy is explicit and intentionally tiered elsewhere in the same file group — `RequiresEditRole` blocks `view`/`run` roles, `RequiresAdminRole` blocks everything but `admin`: [3](#0-2) 

The `ExternalInitiator` model stores not just the public `AccessKey`, but also `OutgoingSecret` and `OutgoingToken` — plaintext credentials the node uses when calling back out to the initiator's URL: [4](#0-3) 

`Index` returns these records wrapped in a presenter: [5](#0-4) 

I was unable to locate/read the presenter file (`core/web/presenters/external_initiators.go`) to confirm exactly which fields are serialized in the response (the index tool did not return its contents, and the file may be excluded due to index size limits — I could not verify this with certainty). This is the one piece of the chain I could not fully confirm; if the presenter includes `OutgoingSecret`/`OutgoingToken`/`AccessKey`, this becomes a concrete secret-disclosure bug reachable by any low-privilege authenticated user, not just editors/admins.

### Impact Explanation
If the presenter leaks `AccessKey`, `OutgoingToken`, or `OutgoingSecret`, any authenticated low-privilege user (`view` role, or a `run`-role identity obtained via external-initiator auth) can enumerate all configured external initiators and harvest credentials used for outbound authenticated calls or (via `AccessKey`) partially compromise the initiator identity used to trigger job runs — a cross-privilege/role-bypass information disclosure. Even absent secret fields, this is still a role-check omission inconsistent with the rest of the same route group's design intent (Create/Destroy require Edit role), which is itself a maintainability/security-hygiene defect that should be fixed defensively.

### Likelihood Explanation
High reachability: the route requires only a valid session or API token (any role), no special network position, and is reachable directly from the internet-facing node API by any registered user account, including `view`-role and `run`-role (external-initiator) principals that should not have access to bridge/initiator management data.

### Recommendation
Wrap the `Index` handler with `auth.RequiresEditRole(...)` to match `Create`/`Destroy`, and audit `presenters.NewExternalInitiatorResource` to ensure `OutgoingSecret`/`OutgoingToken`/`Salt`/`HashedSecret` are never serialized in list/show responses regardless of caller role.

### Proof of Concept
1. Create a user with `view` role (or authenticate as an external initiator, which is auto-granted `UserRoleRun`).
2. Send `GET /v2/external_initiators` with that low-privilege session/token.
3. Observe the request succeeds (no `403 Forbidden`), unlike the equivalent `POST`/`DELETE` calls on the same resource, which correctly return `401`/`403` for the same principal. [6](#0-5)

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
