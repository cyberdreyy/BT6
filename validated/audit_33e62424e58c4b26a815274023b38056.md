### Title
BridgeTypesController.Show discloses the bridge's OutgoingToken credential to view-role users - ([File: core/web/bridge_types_controller.go])

### Summary
`BridgeTypesController.Show` (and also `Index`, `Create`, `Update`, `Destroy`) builds its response via `presenters.NewBridgeResource`, which unconditionally copies the bridge's `OutgoingToken` into the JSON response with no `omitempty` or role gating, unlike `IncomingToken` which is redacted by default. Any authenticated user with only view/run role (or a restricted API token) hitting `GET /v2/bridge_types/:BridgeName` receives the bridge's outgoing credential in plaintext.

### Finding Description
`BridgeTypesController.Show` looks up the bridge by name and serializes it directly: [1](#0-0) 

The presenter used for this serialization always populates `OutgoingToken` from the stored `bridges.BridgeType`, with a JSON tag that has no `omitempty`, in contrast to `IncomingToken` which is `omitempty` and only explicitly set on `Create`: [2](#0-1) 

`OutgoingToken` is the credential the node itself sends (as `Authorization: Bearer <OutgoingToken>`) when calling out to the external bridge adapter — it is a real secret used to authenticate the node's callback/task requests to the bridge, not a public identifier. Because `Show`/`Index` do not redact this field, any request that reaches the controller (regardless of whether it required edit role) discloses this secret in the response body. The distinction between `IncomingToken` (properly redacted for reads) and `OutgoingToken` (never redacted) indicates the redaction was applied inconsistently.

### Impact Explanation
Exposure of `OutgoingToken` lets an attacker with only read/view access to the node API impersonate the Chainlink node when authenticating to the external bridge adapter, matching Chainlink's bounty class of "credential/key disclosure enabling request impersonation." An attacker who can call the bridge's HTTP endpoint with the leaked token could potentially trigger unauthorized bridge task executions or interfere with job pipeline results depending on how the bridge server validates that token.

### Likelihood Explanation
The only precondition is a valid authenticated session or API token with at least view/run role privilege (the minimal role the node grants for read-only operations), and knowledge of an existing bridge name (enumerable via `Index`). This is trivially repeatable: any `GET /v2/bridge_types/<name>` or `GET /v2/bridge_types` call returns the token in the JSON body.

### Recommendation
Redact `OutgoingToken` from `presenters.BridgeResource` for read operations (`Index`/`Show`), mirroring the `IncomingToken` treatment (`omitempty`, and only populate on create/rotate flows or for edit-role callers). If operators need to retrieve the outgoing token later, gate it behind an explicit edit-role-only endpoint or admin action, and audit-log its retrieval.

### Proof of Concept
1. In `core/web/bridge_types_controller_test.go`, create a bridge with `bridges.BridgeType{OutgoingToken: "supersecret", ...}` via the ORM/factory.
2. Build a Gin test context/router authenticated with a view-role (non-edit) session or API token (as used elsewhere in `core/web/auth/auth_test.go` for role-based tests).
3. Call `GET /v2/bridge_types/<name>` through the router (or directly invoke `BridgeTypesController.Show`).
4. Assert the JSON response's `data.attributes.outgoingToken` field equals `"supersecret"` — proving the secret is returned to a view-role caller.
5. Compare against `incomingToken`, which should be absent (`omitempty`), to highlight the inconsistent redaction.

}

// GetName implements the api2go EntityNamer interface
func (r BridgeResource) GetName() string {
	return "bridges"
}
