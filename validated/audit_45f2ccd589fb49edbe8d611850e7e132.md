This confirms the analog: `init_global_fee_state` and `init_global_fee_state_v2` are permissionless, singleton-PDA initializers with no admin/upgrade-authority gating on the caller — the exact same bug class as the Gnosis Safe deployment issue (deterministic address, permissionless creation, first-caller-wins, front-runnable).

### Title
Front-runnable permissionless initialization of the global `FeeState`/`FeeStateV2` singleton allows an attacker to seize the `global_fee_admin` role - (File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs)

### Summary
`init_global_fee_state` (and its sibling `init_global_fee_state_v2`) create a program-wide singleton PDA derived from a fixed, public seed (`FEE_STATE_SEED` / `FEE_STATE_V2_SEED`) with no relation to any specific caller. The instruction's account context only requires an arbitrary `payer: Signer<'info>` — there is no check that the caller is the intended protocol admin or the program's upgrade authority [1](#0-0) . This mirrors the Gnosis Safe report's root cause: a deterministic, permissionless deployment/creation call whose target address does not depend on the legitimate caller's identity, making it exploitable by any observer who front-runs the intended initialization transaction.

### Finding Description
`init_global_fee_state` takes `admin_key` and `fee_wallet` as plain instruction arguments and writes them directly into the newly created `FeeState` PDA, with the `payer` needing only to be a signer, not the intended admin [2](#0-1) . The PDA is derived from the single fixed seed `FEE_STATE_SEED`, identical for every caller [3](#0-2) , so the target address is known ahead of time by anyone watching the mempool/RPC, exactly like the Gnosis Safe `createProxyWithNonce` deployment whose deterministic address was derivable from public information. Because `init_global_fee_state` uses Anchor's `init` constraint, the account can only be created once; whoever's transaction lands first permanently claims it. `init_global_fee_state_v2` has the identical structure and lack of caller gating [4](#0-3) .

Once initialized, the `FeeState.global_fee_admin` field is the sole authority permitted to later call `edit_global_fee_state` (gated by `has_one = global_fee_admin`) [5](#0-4)  and `config_group_fee` [6](#0-5) . Per the permissions guide, the `global_fee_admin` can edit protocol-wide fee parameters, change the global fee wallet, set/clear the pause delegate admin, and panic-pause the entire protocol [7](#0-6) . If an attacker front-runs the legitimate deployment transaction with their own `init_global_fee_state` call (setting themselves as `admin_key`/`fee_wallet`), they permanently seize this role for the life of the deployment (until the legitimate `global_fee_admin`, who never gets a chance, could reassign it — but they can't, since they never controlled it in the first place).

### Impact Explanation
Because there is no ability to retry with a different address (the PDA is a program-wide singleton derived from a fixed seed), a successful front-run is not merely a temporary denial-of-service like the original Gnosis Safe report — it is a permanent authority-bypass/hijack of the `global_fee_admin` role. The attacker-held role can redirect the `global_fee_wallet` (siphoning protocol fees), disable pause protection, or grant themselves indefinite pause capability, causing a durable, protocol-wide financial and governance compromise.

### Likelihood Explanation
This instruction runs exactly once per program deployment/upgrade cycle ("Runs once per program to init the global fee state") [8](#0-7) , so it is a narrow, one-time window rather than an ongoing threat — the operational deploy guides do not document any special precaution (e.g., atomic bundling with program deploy, or using the upgrade-authority as gate) beyond the standard multisig deploy flow [9](#0-8) . On a public mempool network (or any RPC-visible submission), any bot monitoring for this specific instruction discriminator can front-run it with higher priority fees, since the required accounts (payer, fee_state PDA, system_program) are fully derivable/observable without any secret. Likelihood is therefore tied to whether the deploy process happens on a public/monitored network before the FeeState is initialized, and is not mitigated by any current code gating.

### Recommendation
Gate `InitFeeState`/`InitFeeStateV2` so that only the program's upgrade authority (checked via the `bpf_loader_upgradeable`'s `ProgramData` account) or a hardcoded genesis admin pubkey can call it, rather than allowing an arbitrary signer/payer. Alternatively, bundle the fee-state initialization atomically in the same transaction as the program deployment/upgrade so there is no observable window for front-running, and treat any pre-existing (unexpectedly initialized) `FeeState` account as a signal to abort deployment and re-key.

### Proof of Concept
1. Deployer prepares to deploy the marginfi program and plans to call `init_global_fee_state(admin_key=MULTISIG, fee_wallet=MULTISIG, ...)`.
2. Attacker monitors the mempool/RPC for the `init_global_fee_state` instruction discriminator against the newly deployed `marginfi::ID`, or simply submits their own call as soon as the program is live, since the `fee_state` PDA address (`find_program_address(&[FEE_STATE_SEED], program_id)`) is fully computable from public information [3](#0-2) .
3. Attacker submits `init_global_fee_state(admin_key=ATTACKER, fee_wallet=ATTACKER, ...)` with a higher priority fee, landing first and claiming the singleton PDA.
4. The legitimate deployer's subsequent `init_global_fee_state` call fails (`init` constraint: account already in use); the protocol is now stuck with `global_fee_admin = ATTACKER`.
5. Attacker calls `edit_global_fee_state` (authorized via `has_one = global_fee_admin`) to redirect `fee_wallet` to their own address and/or disable pause protections [10](#0-9) .

## Global Fee Admin

The `global_fee_admin` is separate from the group-level admin roles. It is stored on the `FeeState`

- Set or clear the dedicated pause delegate admin
