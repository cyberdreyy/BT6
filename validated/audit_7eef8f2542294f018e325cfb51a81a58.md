### Title
JWT replay protection in `WorkflowMetadataHandler.Authorize` is scoped to a single process, allowing cross-node replay of a single-use signed JWT across independent gateway node instances - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` verifies a request JWT via `utils.VerifyRequestJWT` and rejects re-use of the same `jti` only by checking `h.jwtCache`, an in-process, in-memory map with no persistence or cross-instance synchronization. Because each Gateway node (each `WorkflowMetadataHandler` instance) maintains its own independent `jwtReplayCache`, a single validly-signed JWT can be independently "consumed" once per node but effectively replayed once per each Gateway node in the fleet.

### Finding Description
`Authorize` at core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go:80-108 performs: signature/digest verification via `utils.VerifyRequestJWT`, then a replay check `h.jwtCache.isReplay(claims.ID)`, then authorized-key lookup, then `h.jwtCache.recordUsage(claims.ID)`. The `jwtReplayCache` (lines 29-34, `newJWTReplayCache` at 392-397, `isReplay`/`recordUsage` at 399-412) is a plain `map[string]time.Time` guarded by a local `sync.RWMutex`, held as a field on the `WorkflowMetadataHandler` struct (line 51) — one instance is constructed per Gateway node process via `NewWorkflowMetadataHandler` (line 58). There is no shared backing store (no DB, no distributed cache/Redis) referenced anywhere in this cache implementation.

The reachable path is: an external client submits an HTTP trigger request to `httpTriggerHandler.HandleUserTriggerRequest` (core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:88), which calls `h.authorizeRequest` → `h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)` (line 363). Each Gateway node in the operator's fleet runs its own `gatewayHandler`/`httpTriggerHandler`/`WorkflowMetadataHandler` (core/services/gateway/handlers/capabilities/v2/http_handler.go:45-63), each with its own independently-constructed `jwtCache`. If the same signed JWT+request is sent to N different Gateway node endpoints, each node's local `isReplay` check returns `false` on first sight (since none of them have seen the `jti` before), so all N nodes accept it, each forwarding the trigger to the DON and consuming HTTP-trigger execution/rate-limit resources.

This is confirmed by the existing test `TestWorkflowMetadataHandler_Authorize/JWT_replay_protection` (workflow_metadata_handler_test.go:1193-1217), which demonstrates that replay detection only works *within a single handler instance* — it never tests or claims cross-instance dedup.

### Impact Explanation
Scoped impact is repeated/duplicated execution of a nominally single-use, signed workflow-trigger authorization across a multi-node Gateway deployment: N-times triggering of what the JWT scheme intends to be a one-time authorized action (each Gateway node independently forwards a legitimate `WorkflowExecute` trigger to the DON). This corresponds to an "unauthorized/duplicate job run" class impact — non-idempotent trigger side effects (e.g., billed executions, downstream state changes) can be multiplied by the number of Gateway node endpoints the attacker submits to, and per-node rate limiting/dedup (`checkRateLimit`, `setupCallback`'s per-`requestID` in-flight check) does not close this gap since those structures are also maintained independently per node.

### Likelihood Explanation
Preconditions: attacker needs one validly-signed JWT for a workflow they are authorized on (normal capability of any authorized workflow caller — no privilege escalation needed to obtain it) plus network access to more than one Gateway node's public HTTP endpoint, which is a standard multi-node Gateway/HA deployment topology already reflected in the code (independent `WorkflowMetadataHandler`/`gatewayHandler` per node, independent per-node rate limiters `perNodeRateLimiters`). The action is trivially repeatable — the same token+request payload can be POSTed to every known Gateway endpoint before `cleanupOldEntries` runs (bounded by `JWTReplayPeriodMs`), each yielding a fresh acceptance.

### Recommendation
Back the JWT replay cache with a store shared across all Gateway node instances (e.g., a shared database, distributed cache such as Redis, or a common OCR/consensus-backed dedup ledger keyed by `jti`) so that `isReplay`/`recordUsage` reflect cluster-wide state rather than per-process memory. Alternatively, require Gateway nodes to reach consensus (already used for metadata aggregation, e.g. `WorkflowMetadataAggregator`) before honoring a trigger request across the fleet, or route/require idempotency de-duplication (e.g., dedup by `jti`) at a component that is inherently singular per deployment (such as the DON node's execution engine keyed by `jti`) rather than relying solely on gateway-tier per-instance replay caches.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler_test.go`:
1. Create two independent `WorkflowMetadataHandler` instances (`handlerNode1`, `handlerNode2`) via `createTestWorkflowMetadataHandler`, each simulating a distinct Gateway node, both seeded with the same `authorizedKeys` map for `workflowID` (mirroring synced metadata across the fleet).
2. Generate one EC private key, build one `jsonrpc.Request[json.RawMessage]`, create one JWT via `utils.CreateRequestJWT` and sign it once with `token.SignedString(privateKey)` to get a single `tokenString`.
3. Call `handlerNode1.Authorize(workflowID, tokenString, req)` and assert `err == nil` and a non-nil key (first "use").
4. Call `handlerNode2.Authorize(workflowID, tokenString, req)` with the identical `tokenString`/`req` and assert `err == nil` and a non-nil key returned — demonstrating the same `jti` is accepted a second time simply because it hits a different process-local `jwtCache`.
5. Contrast with re-calling `handlerNode1.Authorize` a second time with the same token, which correctly returns the existing "JWT token has already been used" error, proving replay protection only holds intra-instance, not cluster-wide.
