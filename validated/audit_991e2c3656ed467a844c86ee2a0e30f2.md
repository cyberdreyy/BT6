### Title
Unprivileged shareholder can permanently DoS `staking_contract::distribute` (and the `vesting` module built on top of it) by opting out of direct coin transfers, freezing stake/commission withdrawals for every other staker/operator sharing the pool - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`distribute_internal` in `staking_contract.move` pays out every recipient in a `StakingContract`'s `distribution_pool` (the staker and the operator/beneficiary) in a single atomic loop, using `aptos_account::deposit_coins` for each recipient. `aptos_account::deposit_coins`/`transfer_coins` will abort if the destination account is unregistered for `AptosCoin` **and** has opted out of direct coin transfers via `set_allow_direct_coin_transfers(false)` (a permissionless, self-service setting any account holder can call, per `aptos_account.move` and its own spec: "Account opted out of receiving coins that they did not register to receive"). Since the whole distribution loop runs inside one Move transaction, a single reverting recipient reverts the entire `distribute()` call, including the share redemptions for every other party.

### Finding Description
`distribute_internal` ( [1](#0-0) ) iterates over `distribution_pool.shareholders()`, redeems each recipient's shares, and then calls `aptos_account::deposit_coins(recipient, coin::extract(&mut coins, amount_to_distribute))` to pay them. `aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` when the target account is not yet registered for the coin type and `can_receive_direct_coin_transfers` returns false, i.e. after the account owner has called `aptos_account::set_allow_direct_coin_transfers(false)` (documented in `aptos_account.move` lines around 20-37 and its formal spec at [2](#0-1) ).

Any of the two parties eligible to be a `distribution_pool` shareholder — the staker (via `unlock_stake`, see [3](#0-2) ) or the operator/beneficiary (via `request_commission`, see [4](#0-3) ) — can unilaterally place themselves (or, for a beneficiary, the operator can point commission to an address they also control) into this state before ever registering for `AptosCoin`, and then call `set_allow_direct_coin_transfers(false)`. Because `distribute` ( [5](#0-4) ) is meant to be permissionlessly callable by anyone ("not need to be restricted to just the staker or operator"), *anyone* can trigger `distribute()`, but the transaction will always abort once the loop reaches the griefing recipient, since Move aborts roll back all state changes made earlier in the same transaction (including the share redemptions of the other, honest shareholder).

This same `distribute_internal`/`distribute` machinery is reused directly by the `vesting` module (`vesting::withdraw_stake` calls `staking_contract::distribute`, see [6](#0-5) ), so the same griefing vector blocks vesting `distribute()`/`admin_withdraw` flows for every shareholder of a vesting contract if any one shareholder or the operator's beneficiary opts out of direct transfers while unregistered.

### Impact Explanation
This breaks the "Accounting across active, pending_active, pending_inactive, inactive, rewards, and commission state must preserve value and withdrawal rights" and "Unlock, reactivate, withdraw, synchronize, and beneficiary-update paths must not redirect value or strand it permanently" invariants: funds that have already been unlocked/inactivated in the underlying stake pool (already redeemed from `stake::withdraw_with_cap`) can never actually reach any of the pool's shareholders once one shareholder is in this abort state, because every future `distribute()` call keeps re-adding that shareholder to the pool (via `update_distribution_pool`) and keeps hitting the same abort. The staker's principal-based stake withdrawal and the operator's commission become permanently non-withdrawable — a value-stranding/non-recoverable loss of claim rights for parties who did nothing wrong, triggered by an unprivileged action of a single co-participant. This qualifies as "Permanent lock or non-recoverable loss of claim rights in stake ... commission ... flows," a High/Critical-tier impact under the stated gate.

### Likelihood Explanation
The precondition is entirely unprivileged and cheap: any account can call `aptos_account::set_allow_direct_coin_transfers(false)` before ever registering for `AptosCoin`, and any staker/operator relationship is naturally two-party, so it takes only one malicious or compromised participant (staker, operator, or an operator-chosen beneficiary address) to induce this state. No admin or governance privilege is required, and the trigger persists across epochs since `distribution_pool` re-adds the same address every time new inactive stake appears.

### Recommendation
Do not let a single failing recipient abort the entire distribution loop. Options:
1. Wrap each `aptos_account::deposit_coins` call so failures for one recipient don't revert distributions to others — e.g., detect an unregistered+opted-out recipient ahead of time and redirect/queue their share into a separate claimable balance instead of trying to push funds, or
2. Use `coin::deposit`-based semantics that always succeed once an account is registered, and require/force registration (`coin::register`) transparently, bypassing the opt-out check for internal protocol distributions, or
3. Process each recipient's payment in its own isolated sub-transaction/resource so a revert for one recipient doesn't unwind share redemptions already committed for others.

### Proof of Concept
Not independently executed in this environment (no code execution access), but the trace is fully supported by the cited code:
1. Attacker account `A` (chosen as staker, or as `beneficiary_for_operator`) never registers for `AptosCoin` and calls `aptos_account::set_allow_direct_coin_transfers(A_signer, false)`.
2. `A` becomes staker/operator/beneficiary in a `StakingContract` with another honest counterpart `B` (e.g., via `create_staking_contract`, `unlock_stake`, or `set_beneficiary_for_operator`).
3. Stake pool accrues rewards/unlocks; someone calls `staking_contract::distribute(staker, operator)`.
4. `distribute_internal` redeems shares for `B` and `A` inside the same loop; when it reaches `A`, `aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. The abort reverts the entire transaction, including `B`'s already-redeemed shares, leaving both `A` and `B` permanently unable to withdraw via `distribute()` as long as `A` keeps this configuration and remains a shareholder — which the protocol itself re-establishes every distribution cycle via `update_distribution_pool`.

**Note on verification limits**: I was not able to locate the exact source lines of `aptos_account::can_receive_direct_coin_transfers`/`set_allow_direct_coin_transfers`/`deposit_coins` bodies via search (only usage sites, tests, and specs were indexed for me); the behavior described is derived from the module's documented semantics, error constants, and formal specification comments, which is consistent evidence but I recommend a Devin session with full file access to confirm the exact abort conditions line-by-line before treating this as final.
