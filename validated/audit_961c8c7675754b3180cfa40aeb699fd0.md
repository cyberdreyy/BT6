### Title
Global, tenant-unscoped `requestID` keyspace in `setupCallback` allows cross-tenant request-ID collision DoS and in-flight existence leak - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`httpTriggerHandler.callbacks` is keyed only by the raw, client-supplied JSON-RPC `req.ID` with no namespacing by workflow, workflow owner, or connection/session. Any authenticated caller (holding a valid auth key for *any* workflow) can pick a `requestID` colliding with another tenant's in-flight request and cause the loser's `setupCallback` call to fail with `jsonrpc.ErrConflict`, denying that tenant's execution and revealing that a request with that ID is currently in-flight.

### Finding Description
`HandleUserTriggerRequest` (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:88-140`) validates and authorizes the request only against the workflow specified in the request itself (`h.authorizeRequest`, line 361-369) — it never checks whether the `req.ID` is already reserved by a different workflow/tenant. It then calls `setupCallback` (line 398-435): [1](#0-0) 

The map `h.callbacks map[string]savedCallback` (line 60) is keyed purely by `requestID`, with no workflow/owner component mixed in, even though elsewhere (`legacyExecutionID`, `executionIDWithTriggerIndex`) the code *does* combine `workflowID` with `req.ID` for logging/aggregation purposes but not for the actual dedup key. Because auth is validated per-workflow and not tied to the global ID namespace, two unrelated tenants — each authorized only for their own workflow — share the same collision-prone keyspace. If tenant B submits a request with the same `requestID` as tenant A's still in-flight request, `setupCallback` returns `jsonrpc.ErrConflict` and the losing caller is told "requestID: X has already been used" (line 403), which is both a denial of the legitimate request and a positive existence oracle for an in-flight request under that ID, without B needing any authorization/knowledge of A's workflow.

### Impact Explanation
Impact is denial of service against a targeted in-flight workflow execution: whichever caller's `setupCallback` call arrives second is rejected outright and its trigger request never reaches `sendWithRetries`/the DON. This maps to a "Denial of Service" bounty class — a low-privilege caller (any user with a valid auth key for an arbitrary workflow) can grief another tenant's execution by racing a colliding, guessable/predictable `requestID` (e.g. sequential counters, timestamps, or well-known constants used by client SDKs). Secondarily, the conflict error is a minimal informational leak confirming the existence of another tenant's in-flight request under that ID, though it discloses no content, workflow ID, or owner.

### Likelihood Explanation
Exploitability requires only a valid JWT/auth key for the attacker's own (or any) workflow — no privilege over the victim's workflow is needed. The attack is fully repeatable and only requires the attacker to guess or predict a `requestID` value the victim's client is likely to use and race the request. Feasibility depends on how unpredictable client-chosen request IDs are in practice; if clients use monotonic/sequential or low-entropy IDs, the collision is trivial to win.

### Recommendation
Scope the callback keyspace by tenant, e.g. key `h.callbacks` by a composite of `(workflowID, requestID)` or `(workflowOwner, requestID)` instead of `requestID` alone, mirroring how `legacyExecutionID`/`executionIDWithTriggerIndex` already combine `workflowID` with `req.ID`. This ensures collisions can only occur within a single workflow's own request stream, eliminating cross-tenant interference and the existence-leak oracle.

### Proof of Concept
Go handler-level test in `http_trigger_handler_test.go`:
1. Set up two distinct workflows/owners (A and B), both authorized via `workflowMetadataHandler`.
2. Goroutine 1: call `h.HandleUserTriggerRequest` for workflow A with `req.ID = "X"`, using a callback whose `SendResponse` blocks/delays (simulate slow shard) so the callback stays registered in `h.callbacks`.
3. Immediately (goroutine 2): call `h.HandleUserTriggerRequest` for workflow B (different owner) with the same `req.ID = "X"`.
4. Assert goroutine 2 receives a `jsonrpc.ErrConflict` response via its callback's `SendResponse`, proving cross-tenant collision blocks an unrelated workflow's execution purely based on `requestID` equality.
5. Assert that no response intended for workflow A ever reaches workflow B's callback (confirming no direct data leak, only DoS/existence leak), and that A's execution proceeds normally once B's colliding attempt is rejected.

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
