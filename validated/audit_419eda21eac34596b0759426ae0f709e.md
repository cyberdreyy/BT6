### Title
Missing `VestingSchedule::assert_valid()` call at lockup creation allows an unprivileged caller to deploy a wrongly-parameterised lockup contract - (File: lockup/src/lib.rs, lockup-factory/src/lib.rs)

### Summary
`VestingSchedule` defines a self-check `assert_valid()` that enforces `start_timestamp <= cliff_timestamp <= end_timestamp` and `start_timestamp < end_timestamp` [1](#0-0) , but this function is never invoked anywhere in the codebase (it exists only in its own definition file) — in particular it is not called from `LockupContract::new`, the `#[init]` constructor that accepts an explicit `VestingScheduleOrHash::VestingSchedule` [2](#0-1) .

### Finding Description
`LockupContract::new` validates the owner account id, whitelist account id, and the foundation-account/vesting-schedule pairing, but performs no validation on the internal consistency of an explicitly supplied `VestingSchedule` (`start_timestamp`, `cliff_timestamp`, `end_timestamp`) [3](#0-2) .

Crucially, `lockup-factory`'s `create` method is callable by **any unprivileged account** and forwards an attacker-supplied `vesting_schedule` argument verbatim into the deployed lockup contract's `new` call, with no additional validation performed in the factory either [4](#0-3) . Since the resulting lockup contract is created with the caller as `owner_account_id`, the caller fully controls the vesting-schedule triple and can pick invalid combinations, e.g. `end_timestamp < start_timestamp`, `cliff_timestamp < start_timestamp`, or `end_timestamp == start_timestamp`.

This breaks the accounting binding relied on by `get_unvested_amount`, which assumes `assert_valid()` was already enforced ("The total time is positive. Checked at the contract initialization.") [5](#0-4) :
```
let total_time = U256::from(vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0);
```
If `end_timestamp < start_timestamp`, this subtraction underflows a `u64`. Combined with `get_locked_amount`, which calls `get_unvested_amount` to compute the maximum of "unreleased" and "unvested" locked balance [6](#0-5) , an invalid schedule can either panic the contract's core accounting method (freezing the deployed funds permanently, since `get_locked_amount` underlies `get_owners_balance`/`get_liquid_owners_balance` used for any transfer) or, depending on the specific malformed values chosen, produce an `unvested_amount` that diverges from the documented pro-rata vesting formula, causing tokens to be reported as released/vested earlier or later than the schedule's semantics intend.

### Impact Explanation
This maps to two of the listed Critical/High impact categories:
- "A wrongly parameterised deployment" — any unprivileged account can, through `lockup-factory::create`, deploy a lockup contract whose vesting/lockup accounting invariant is broken from inception, with no admin or foundation involvement required.
- "Funds permanently frozen" — a malformed schedule (e.g., `end_timestamp < start_timestamp`) causes the u64 subtraction in `get_unvested_amount` to underflow/panic, which is reachable from `get_locked_amount` and thus from every owner balance/transfer computation, permanently bricking the contract's ability to compute a liquid balance.

### Likelihood Explanation
High: no privileged role is required. Any account calling `lockup-factory`'s `create` with `MIN_ATTACHED_BALANCE` and a crafted `vesting_schedule` (or a directly-deployed lockup `new` call, if the caller can deploy code themselves) triggers the missing check immediately at initialization.

### Recommendation
Call `vesting_schedule.assert_valid()` in `LockupContract::new` whenever an explicit `VestingScheduleOrHash::VestingSchedule` is provided (mirroring the identical, already-defined and already-unused `assert_valid()` helper), before storing it as `VestingInformation::VestingSchedule`. Additionally, `lockup-factory::create` should reject internally-inconsistent vesting schedules before attempting to deploy the child contract, to fail fast and refund the deposit rather than let a bricked lockup contract be created.

### Proof of Concept
1. Call `lockup-factory::create` (or directly `lockup::new`) as any unprivileged account with:
   - `vesting_schedule = VestingScheduleOrHash::VestingSchedule(VestingSchedule { start_timestamp: T, cliff_timestamp: T, end_timestamp: T - 1 })`
2. The lockup contract initializes successfully because `assert_valid()` is never invoked in `lockup/src/lib.rs::new` [7](#0-6) .
3. Once `block_timestamp` passes `cliff_timestamp` (T) but is still below the (now nonsensical) `end_timestamp` (T-1, already in the past relative to cliff), any call that reaches `get_unvested_amount` — e.g. `get_locked_amount`, `get_owners_balance`, `get_liquid_owners_balance` — executes `vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0` [8](#0-7) , underflowing the `u64` subtraction and panicking, permanently freezing all balance-dependent operations on the deployed contract.

impl VestingSchedule {
    pub fn assert_valid(&self) {
        assert!(
            self.start_timestamp.0 <= self.cliff_timestamp.0,
            "Cliff timestamp can't be earlier than vesting start timestamp"
        );
        assert!(
            self.cliff_timestamp.0 <= self.end_timestamp.0,
            "Cliff timestamp can't be later than vesting end timestamp"
        );
        assert!(
            self.start_timestamp.0 < self.end_timestamp.0,
            "The total vesting time should be positive"
        );
    }
