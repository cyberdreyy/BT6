## Title
Deleted multisig member's stale confirmation still counts toward execution threshold, allowing a request to execute below the live-member quorum - (`multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges pending requests that were *originated* by the removed member, but never scans the `confirmations` map to strip that member's confirmation from *other* pending requests they had merely confirmed. As a result, a confirmation cast by a member who is later removed from the multisig keeps counting toward `num_confirmations`, letting a request execute with fewer live, authorized confirmations than the configured threshold requires.

### Finding Description
The multisig contract's core guarantee is the equality: `confirmations from currently-valid members >= num_confirmations` before any request executes (`multisig2/src/lib.rs` `confirm()`): [1](#0-0) 

`assert_valid_request` only checks that the *caller* confirming right now is a current member; it does not re-validate the members already recorded in the `confirmations` set for that request: [2](#0-1) 

When a member is removed via `DeleteMember`, `delete_member` deletes outstanding requests that member *added* (`r.member == member`), and clears their `num_requests_pk` entry, but does nothing to the `confirmations` sets of *other* pending requests that this member had confirmed as a co-signer: [3](#0-2) 

Because `MultisigMember` values are stored in `confirmations` by their string representation (`member.to_string()`), and that string is never removed from unrelated requests' confirmation sets on member deletion, a stale confirmation from a now-removed member remains valid indefinitely for any request that was pending before the removal took effect.

Concretely: with `num_confirmations = 3` and members `{A, B, C, D}`, suppose `A` adds a `Transfer` request and `B` confirms it (2/3 confirmations, request still pending). The remaining members then remove `B` from the multisig (e.g. because `B`'s key was compromised) via a separate `DeleteMember` request. `delete_member` does not touch the pending transfer request's confirmation set because that request was not "owned" by `B`. `B`'s confirmation therefore still counts. Any one more live member (e.g. `C`) confirming the transfer now satisfies `2 (stale B + live A) + 1 (C) >= 3`, executing the transfer with only two confirmations from members who are still authorized (`A`, `C`) — one below the intended live-member threshold.

### Impact Explanation
This breaks the binding "confirmations counted versus live members" explicitly protected by the multisig's threshold design, and directly matches the "a multisig request executed below threshold" Critical impact category: funds can be transferred, keys added/removed, or contract code deployed via `execute_request` (`multisig2/src/lib.rs` lines 224-290) with effectively fewer authorized confirmations than `num_confirmations`, i.e., NEAR moved or privileged actions executed by a party (or set of parties) not entitled to do so under the configured quorum.

### Likelihood Explanation
This requires no external attacker at all beyond the normal, expected multisig operational flow: pending requests routinely exist while confirmations accumulate, and removing a member (e.g. due to key rotation, compromise, or a departing signer) is a documented, expected multisig operation. Any overlap between a member's departure and a still-pending request they had confirmed triggers the bug — this is a realistic and likely operational sequence, not a contrived edge case.

### Recommendation
In `delete_member`, iterate over all `self.requests` (not just those with `r.member == member`) and remove the deleted member's entry from every corresponding `self.confirmations` set (using `member.to_string()`), so that any pending request loses that stale confirmation. Alternatively, revalidate every confirming member's current membership status inside `confirm()` before counting confirmations toward `num_confirmations`, and prune stale ones lazily.

### Proof of Concept
1. Deploy `multisig2` with 4 members `A, B, C, D` and `num_confirmations = 3`.
2. `A` calls `add_request` with a `Transfer` action to `attacker`.
3. `B` calls `confirm(request_id)` — confirmations = `{A, B}` (2/3), request stays pending.
4. Members `C`/`D`/etc. submit and confirm a separate `DeleteMember { member: B }` request (reaching its own 3 confirmations), executing `delete_member`, which removes `B` as a member/access key but leaves the pending transfer's confirmation set `{A, B}` untouched (`multisig2/src/lib.rs` lines 356-379).
5. `C` (a live member) calls `confirm(request_id)` on the original transfer request. `confirmations.len() as u32 + 1 = 3 >= num_confirmations`, so `execute_request` runs and transfers funds — even though only `A` and `C`, i.e., 2 live members, ever validly authorized it.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
