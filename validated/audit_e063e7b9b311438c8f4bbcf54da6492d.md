### Title
Rejected signer weight is never retracted when the same signer later accepts, letting a single signer's weight double-count across both `total_weight_rejected` and `total_weight_approved` tallies - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The node-side `StackerDBListener` maintains two independent weight tallies per proposed block — `total_weight_approved` and `total_weight_rejected` — that are supposed to be mutually exclusive per signer (a signer's weight should count on only one side at a time). The dedup guards used to prevent double counting are keyed on two *different* collections (`gathered_signatures` for accepts, `responded_signers` for rejects), so a signer that first rejects and later accepts the same block gets its weight added to `total_weight_rejected` *and* `total_weight_approved`, with the stale rejected weight never retracted.

### Finding Description
In the `BlockResponse::Rejected` branch, the reject tally is guarded only by insertion into `responded_signers`: [1](#0-0) 

In the `BlockResponse::Accepted` branch, the accept tally is guarded by a check against a *different* set, `gathered_signatures`: [2](#0-1) 

Because these two dedup sets are distinct, the following legitimate signer flow is exploitable by a single signer (one slot) via ordinary StackerDB gossip:

1. Signer S sends `BlockResponse::Rejected` for block `B`. `responded_signers.insert(slot_id)` returns `true` (first time), so `total_weight_rejected += weight(S)`.
2. Signer S later sends `BlockResponse::Accepted` for the same block `B` (this is a legitimate, expected flow — the signer's own re-evaluation logic explicitly allows flipping from reject to accept for several `RejectReason`s, see `should_reevaluate_reject_reason`, which returns `true` for reasons like `NotFoundError`, `ConnectivityIssues`, `NoSignerConsensus`, etc.): [3](#0-2) 
3. The accept-path check `!block.gathered_signatures.contains_key(&slot_id)` is still `true` because `gathered_signatures` was never touched by the reject path, so `total_weight_approved += weight(S)` runs a second time for the same signer weight.
4. `total_weight_rejected` is never decremented — there is no code path anywhere in this file that removes or corrects a stale rejection when a signer's vote flips.

The result: the same signer's weight is now counted in *both* `total_weight_approved` and `total_weight_rejected` simultaneously, breaking the implicit invariant that `total_weight_approved + total_weight_rejected <= total_weight` (each signer contributes to at most one side). This is the direct analog of the external report's flaw: two independently-bounded counters (validator MEV rewards % and protocol fees %) that individually respect their own limit but, combined, violate the higher-level invariant (sum ≤ 100%). Here the two "percentages" are `total_weight_approved` and `total_weight_rejected` of `self.total_weight`.

### Impact Explanation
The decision logic in the coordinator checks the reject-blocking condition *before* the approval condition: [4](#0-3) 

Because `total_weight_rejected` is stale/inflated by a signer that has since switched to accept, the miner can incorrectly conclude a blocking minority (>30%) rejected the block and abandon it (returning `Err(NakamotoNodeError::SignersRejected)`) even though the block may in fact have already reached, or would soon reach, the real 70% approval weight from distinct signers. This is a liveness wedge: a single signer's ordinary reconsideration flow (reject → later accept, which the signer's own code explicitly supports) can cause the coordinator/miner to spuriously discard a block that has legitimate signer support, stalling tenure/block production. It requires no majority of signers and no access to another signer's key — only one signer's own two StackerDB messages (gossip) for the same block hash, matching the reachable-by-one-slot-plus-gossip criterion.

### Likelihood Explanation
This is trivially reachable in normal operation, not just via malice: `should_reevaluate_reject_reason` is designed to let a signer legitimately switch from `Rejected` to `Accepted` for the exact same block hash under multiple reject reasons (`NotFoundError`, `ConnectivityIssues`, `NoSignerConsensus`, `NoSortitionView`, etc.), and the signer test suite even exercises "reprocess the block after reproposed" scenarios. Any signer whose environment/connectivity flaps, or a re-proposal that resolves a `NotFoundError`, can produce this sequence organically. A malicious single signer can trigger it deterministically at will by sending Reject then Accept for the same `signer_signature_hash`.

### Recommendation
Track a single per-signer response state (e.g., a `HashMap<slot_id, Vote>` instead of two independent sets), and when a signer's vote changes, retract the previous tally contribution before applying the new one:
```rust
if let Some(prev) = block.votes.insert(slot_id, Vote::Rejected) {
    match prev {
        Vote::Approved => block.total_weight_approved = block.total_weight_approved.saturating_sub(signer_entry.weight),
        Vote::Rejected => { /* no-op, already counted */ }
    }
}
block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
```
and symmetrically for the accept path, ensuring `total_weight_approved + total_weight_rejected <= total_weight` holds as an invariant at all times.

### Proof of Concept
1. Configure a StackerDB listener tracking a block `B` with `total_weight` = 100, `weight_threshold` = 70, and a single signer S with `weight(S)` = 40 among other signers.
2. Signer S broadcasts `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for `B` → `responded_signers.insert(slot_id)` succeeds → `total_weight_rejected = 40`.
3. Signer S broadcasts `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same `B` (representable as a legitimate re-evaluation, e.g. after `NotFoundError`/`ConnectivityIssues` clears) → `gathered_signatures.contains_key(&slot_id)` is `false` (untouched by the reject path) → `total_weight_approved = 40`.
4. Now `total_weight_approved + total_weight_rejected = 80 > total_weight = 100`'s per-signer share is double-counted (S contributes 40 to both sides), and `total_weight_rejected` (40) remains stale forever unless further rejects/accepts occur from other signers — a value the coordinator uses to decide whether to abandon the block: [5](#0-4) 
With enough other signers' rejects on top of this phantom 40, the blocking-minority condition can be reached even though 40 of that weight actually now supports the block, causing the miner to discard a block it should have accepted.
