### Title
Unprivileged ERC4626 vault user can force `stopEpoch` to revert or force an honest borrower into default by manipulating the programmable borrower's external vault - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`IdleCDOEpochVariant` delegates epoch pricing and settlement to the programmable borrower's hook surface (`totalInterestDueNow`, `onStopEpoch`), which in turn prices everything off an externally shared ERC4626 `vault`. That vault is an untrusted-input boundary in the same sense as the project-local `.env` in the reference bug: any unprivileged ERC4626 depositor of the shared vault can alter the inputs (vault liquidity and share valuation) that drive the CDO's privileged stop-epoch execution path. There is no trust boundary — the borrower's own share value and the vault's liquidity are fully controllable by third-party vault users during a live epoch.

### Finding Description
In `onStopEpoch`, when `IdleCDOEpochVariant` asks for `_amountRequired`, the programmable borrower must withdraw the shortfall from the shared ERC4626 vault:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol:239-253
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

Two attacker-controllable outcomes exist, both reachable by "a user of the programmable borrower's ERC4626 vault" (an explicitly in-scope unprivileged actor):

1. **Stop-epoch freeze.** If the vault has insufficient liquid underlying for `vault.withdraw(shortfall)` — e.g., a large vault depositor redeems/queues withdrawals or the vault's liquidity is simply deployed — the `try/catch` reverts with `StopEpochVaultLiquidityUnavailable`. `stopEpoch`/`stopEpochWithDuration`/`stopEpochWithLoss` in `IdleCDOEpochVariant` therefore revert. Since the epoch-end pull goes through this hook on every path, the pool's epoch cannot be closed while the vault stays illiquid: all pending `withdrawsRequestsByEpoch` receipts, tranche withdrawals, and borrower settlement are frozen. The only unlock is the honest borrower fronting the full `_amountRequired` on-hand, i.e., freezing persists as long as vault liquidity is withheld.

2. **Forced default of an honest borrower.** If `_currentVaultAssets()` covers the shortfall in share terms but `vault.withdraw` keeps reverting selectively (ERC4626 vaults with per-request liquidity caps, withdrawal queues, or gated `withdraw` — exactly how MetaMorpho-style vaults used in tests behave), the revert blocks settlement without ever entering the `shortfall > _currentVaultAssets()` early-return. Conversely, where the borrower's on-hand is made to look insufficient while share value covers it, `onStopEpoch` returns `true` and the CDO's subsequent `transferFrom` of the full `totalInterestDueNow + principal` fails on balance, routing into the default path — socializing a manufactured "default" loss to BB then AA tranche holders (`_updateAccounting` BB-first loss + `_handleBorrowerDefault`) even though the borrower performed correctly.

The broken invariant is settlement solvency/fair epoch closure: the epoch state machine's exit is gated entirely on an external contract whose liquidity and valuation are set by unprivileged third parties during the `running` epoch phase, in both minted-interest and pulled-interest programmable modes.

### Impact Explanation
- Temporary-to-permanent freezing of all LP funds: pending withdraw receipts cannot be claimed and tranches cannot exit until the vault regains liquidity — no in-protocol escape exists (guardian/owner cannot bypass the hook in programmable mode; `onDefault` is only reachable through a `stopEpoch` flow that itself requires the hook to return).
- Alternatively, an honest-borrower default crystallizes BB-first losses onto tranche holders via `_updateAccounting`/`_handleBorrowerDefault`, i.e., direct insolvency/false-loss socialization quantified by the shortfall up to the full epoch NAV.

### Likelihood Explanation
Any ERC4626 vault depositor can time liquidity withdrawal around `epochEndDate` (public timestamp). Epochs are long-duration (test config uses ~30+ days), giving a wide, predictable window. The cost to the attacker is only temporarily withholding their own vault liquidity — no capital is lost. No privileged call, no KYC, and no cooperation from borrower/manager is needed; all flagged guards (`nonReentrant`, `_checkOnlyIdleCDO`, `try/catch`) protect the borrower, not the pool.

### Recommendation
Do not let a single `vault.withdraw` result decide epoch settlement. Options: make `stopEpoch` settle for `min(_amountRequired, onHand + withdrawable)` and account the remainder as borrower debt rather than reverting or defaulting; add a guard/keeper path that can force `onDefault`/default handling without requiring the hook to succeed; and treat "vault reports coverage but cannot pay" distinctly from "borrower insolvent" so vault illiquidity never books a borrower default loss onto tranche holders.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";

/// @notice Repro on the programmable-borrower fork setup used in
/// test/foundry/ProgrammableBorrowerCreditVault.t.sol (MetaMorpho-style ERC4626 vault).
contract StopEpochVaultLiquidityPoC is Test {
    // ... reuse setUp from ProgrammableBorrowerCreditVault.t.sol ...

    function testVaultUserBlocksStopEpoch() external {
        uint256 amount = 10_000 * oneScale;
        idleCDO.depositAA(amount);
        _startEpochAndCheckPrices(0);          // all funds parked in shared vault

        // Attacker: an unprivileged large depositor of the SAME ERC4626 vault
        // drains/locks vault liquidity so PB's withdraw(shortfall) reverts.
        address vaultWhale = makeAddr("vaultWhale");
        deal(USDC, vaultWhale, 50_000_000 * oneScale, true);
        vm.startPrank(vaultWhale);
        underlying.approve(vaultAddress, type(uint256).max);
        uint256 whaleShares = morphoVault.deposit(50_000_000 * oneScale, vaultWhale);
        // make the vault illiquid right at epoch end
        morphoVault.redeem(whaleShares, vaultWhale, vaultWhale);
        vm.stopPrank();
        // (for a queue/capped vault: exhaust available liquidity so withdraw reverts)

        vm.warp(cdoEpoch.epochEndDate() + 1);

        // Manager (honest) tries to close the epoch: reverts.
        vm.prank(manager);
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        cdoEpoch.stopEpoch(0, 0);

        // Epoch stays running, all LP withdraw receipts frozen while liquidity withheld.
        assertTrue(cdoEpoch.isEpochRunning());
    }
}
```
