### Title
`getSignatureStatuses` reports a `confirmationStatus` computed from a bank that is newer/inconsistent with the `context.slot` returned to the client - ([File: rpc/src/rpc.rs])

### Summary
`JsonRpcRequestProcessor::get_signature_statuses` fixes a single `bank` snapshot at `CommitmentConfig::processed()` up front and uses it as the response `context.slot`, but the actual `confirmationStatus` field for every signature is computed by `get_transaction_status`, which independently re-fetches the *confirmed* bank and the block-commitment cache on every call/iteration. Because these are separate, non-atomic reads taken at different points in time (and, for a list of signatures, on separate loop iterations), the derived `confirmationStatus` can reflect a different, later chain state than the `context.slot` the client is told the answer corresponds to. This is the same bug class as the FloatCapital finding: a view-only function composes multiple pieces of state captured at different "update indices" (there, `marketUpdateIndex`; here, bank/commitment-cache snapshots) and reports a result that doesn't correspond to any single consistent state, which can mislead a caller making decisions (e.g. believing a transaction is merely "processed" when it is already "finalized", or vice versa) in a fast-moving cluster.

### Finding Description
`get_signature_statuses` takes one snapshot of the bank at `processed` commitment: [1](#0-0) 
It then loops over the requested signatures and, for each one, calls `get_transaction_status(signature, &bank)`: [2](#0-1) 

Inside `get_transaction_status`, the status/slot comes from the fixed `bank` argument, but the "confirmed" reference and the finality/confirmation-count computation come from two additional, freshly-read pieces of shared state that are not read atomically with the outer `bank` snapshot: [3](#0-2) 

Specifically:
- `optimistically_confirmed_bank` is re-fetched via `self.bank(Some(CommitmentConfig::confirmed()))` independently for each signature processed in the loop.
- `block_commitment_cache` is separately locked and read to decide `is_finalized`.

Between the moment the outer `bank` (context.slot) was captured and the moment each per-signature `optimistically_confirmed_bank`/`block_commitment_cache` snapshot is taken, background threads (ReplayStage / commitment-cache updates) can advance the confirmed bank or root, exactly analogous to the oracle updating `marketUpdateIndex` between the user's transaction and the later `getUsersConfirmedButNotSettledSynthBalance` read in the FloatCapital report. The final `new_response(&bank, statuses)` reports `context.slot = bank.slot()`, but the per-item `confirmation_status` values were computed against later/inconsistent state.

### Impact Explanation
This is a view-only, unprivileged JSON-RPC method (`getSignatureStatuses`) reachable with a single request. The impact is a misreported/inconsistent `confirmationStatus` relative to the reported `context.slot`, which can cause a caller (wallet, exchange, bot) to believe a transaction is at a different finality level than the state the response context claims. As the original finding's judge noted, incorrectly reporting position/confirmation status to a UI can cause a user to make decisions (e.g., treat funds as settled/hedged) that lead to real financial loss during a fast-moving/forking period, even though the validator's core consensus state is unaffected.

### Likelihood Explanation
This requires no privileged role and can be triggered by any RPC client simply calling `getSignatureStatuses` with `searchTransactionHistory` unset, during periods where the network is actively rooting/confirming new slots (i.e., essentially all the time). The race window is small per call but is continuously present, and larger signature lists increase the number of independent re-reads (once per signature) inside the same RPC call, increasing the chance that at least one entry is computed against a bank state that has since diverged from the reported `context.slot`.

### Recommendation
Snapshot `optimistically_confirmed_bank` and `block_commitment_cache` once, together with the `bank` used for `context.slot`, before the loop, and pass them into `get_transaction_status` so all signatures in a single request are evaluated against one consistent point-in-time view. If per-signature freshness is desired, then `context.slot` should be recomputed/labeled to match the actual snapshot used for the confirmation computation.

### Proof of Concept
Not independently reproducible without a live multi-threaded validator under load (the race depends on ReplayStage advancing `optimistically_confirmed_bank`/`block_commitment_cache` concurrently with an in-flight `getSignatureStatuses` call), so this is inferred from the code structure rather than an executed repro:
1. Call `getSignatureStatuses` with a list of N signatures.
2. `bank` is snapshotted once at `processed` commitment (`rpc/src/rpc.rs:1684`).
3. For each signature, `get_transaction_status` independently re-reads `self.bank(Some(CommitmentConfig::confirmed()))` and `self.block_commitment_cache.read()` (`rpc/src/rpc.rs:1738-1751`).
4. If a slot becomes confirmed/rooted between the read at step 2 and one of the reads in step 3 (a realistic timing window under active cluster ticking), the returned `confirmation_status` for that signature reflects state newer than the `context.slot` reported to the client in the same response, producing an inconsistent/misleading result — the RPC analog of the FloatCapital `getUsersConfirmedButNotSettledSynthBalance` stale-index bug.
