### Title
CORS wildcard origin allowlist bypass via missing subdomain boundary check in `isAllowedOrigin` - ([File: core/services/gateway/network/httpserver.go])

### Summary
`httpServer.isAllowedOrigin` implements wildcard host matching (`*.example.com`) using `strings.HasSuffix(originHost, allowedHost)` after stripping the `*.` prefix, without verifying that the match is preceded by a `.` separator. This lets an attacker register or control any domain that merely ends with the allowed suffix as a raw string (e.g. `evilexample.com` matching an allowlist entry `*.example.com`), causing the gateway to treat an unrelated, attacker-controlled origin as trusted.

### Finding Description
In `isAllowedOrigin` [1](#0-0) , once the `*.` prefix is stripped from a configured wildcard entry (e.g. `*.example.com` → `example.com`), the code checks `strings.HasSuffix(originHost, allowedHost)`. This is a pure string suffix test, not a domain-label boundary check. Consequently, an `Origin` header such as `https://evilexample.com` (no dot before `example.com`) satisfies `HasSuffix("evilexample.com", "example.com") == true`, even though `evilexample.com` is a completely different, attacker-owned domain and not a subdomain of `example.com`.

The check is invoked from `handleRequest` [2](#0-1) : when `isAllowedOrigin` returns true, the server reflects the attacker's `Origin` value verbatim into `Access-Control-Allow-Origin` and also sets `Access-Control-Allow-Headers: Content-Type` plus allows `GET, POST, OPTIONS`. Because the reflected `Access-Control-Allow-Origin` exactly matches the request's `Origin`, browsers will permit the attacker's page to read the cross-origin response — bypassing the operator's intended origin allowlist restriction for any wildcard entry configured (`*.<domain>`).

No additional validation exists upstream to close this gap; `splitURL` only lower-cases and parses scheme/host/port [3](#0-2) , it does not reject or normalize malformed suffix collisions.

### Impact Explanation
An unauthenticated, unprivileged attacker who controls a domain that textually ends with a wildcard-allowed suffix (e.g. registers `evil-victim-allowed.com` when the operator's config lists `*.victim-allowed.com`) can host a webpage that issues cross-origin `fetch`/`XHR` requests to the gateway HTTP endpoint and successfully read the JSON responses, and set the `Authorization` header (allowed via `Access-Control-Allow-Headers: Content-Type` note — Authorization itself isn't in the allow-list, limiting credentialed request scenarios, but any browser-driven signed-message workflow that relies on Origin-based trust for read access is bypassed). This falls into the "allowlist/quota bypass" and "cross-user response confusion" impact classes: any user visiting the attacker's lookalike site while their client-side signing tool/extension is active could have gateway responses exfiltrated to the attacker page cross-origin, defeating the operator's CORS allowlist.

### Likelihood Explanation
Exploitability requires: (1) the operator configures at least one wildcard entry in `CORSAllowedOrigins` (a normal, documented usage pattern of this feature, not a misconfiguration — the code explicitly supports `*.` wildcards), and (2) the attacker registers/controls a domain matching the vulnerable suffix pattern, which is trivial and cheap (domain registration). No credentials, authentication, or special network position are required — any browser visiting the attacker's page triggers the bypass. This is fully reproducible and deterministic.

### Recommendation
Fix the wildcard suffix check to require a proper label boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".example.com" (keep the leading dot)
    if originHost == allowedHost[2:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
This ensures `originHost` must either equal the base domain or end with `.example.com` (dot-prefixed), preventing `evilexample.com` from matching `*.example.com`.

### Proof of Concept
Go unit test to add to `core/services/gateway/network/httpserver_test.go`:
```go
func TestIsAllowedOrigin_WildcardSuffixBypass(t *testing.T) {
    s := &httpServer{
        config: &HTTPServerConfig{
            CORSAllowedOrigins: []string{"https://*.example.com"},
        },
        lggr: logger.Test(t),
    }
    // Legitimate subdomain should be allowed
    require.True(t, s.isAllowedOrigin("https://sub.example.com"))
    // Attacker-controlled lookalike domain should NOT be allowed but currently is
    require.False(t, s.isAllowedOrigin("https://evilexample.com"))
}
```
Expected current (vulnerable) behavior: the second assertion fails because `isAllowedOrigin` returns `true` for `https://evilexample.com`, confirming the suffix-matching bypass. After applying the recommended dot-boundary fix, the test should pass with `false` for the attacker domain.

func (s *httpServer) splitURL(rawURL string) (string, string, string, error) {
	// lowercase the URL to avoid case sensitivity issues
	parsedURL, err := url.Parse(strings.ToLower((rawURL)))
	if err != nil {
		return "", "", "", fmt.Errorf("error parsing URL: %w", err)
	}

	host, port, err := net.SplitHostPort(parsedURL.Host)
	if err != nil {
		// if there's no port, the host itself is returned
		if parsedURL.Host != "" {
			return parsedURL.Scheme, parsedURL.Host, "", nil
		}
		return "", "", "", fmt.Errorf("error splitting host and port: %w", err)
	}

	return parsedURL.Scheme, host, port, nil
}
