### Title
Stale rejection weight is never retracted when a signer later accepts, corrupting the `total_weight_rejected` vs verified-accepts equality used to abandon block proposals - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The FTC bug rewarded a "position increase" action (mint) with no symmetric "position decrease" action (burn), letting an attacker accrue stake weight that no longer reflects real risk. The stacks-node `StackerDBListener` has the same asymmetry in its block-response tally: a `BlockResponse::Rejected` message permanently adds a signer's weight to `total_weight_rejected`, but a later `BlockResponse::Accepted` from that same signer for the same block never removes it. The two counters (`total_weight_approved`, `total_weight_rejected`) are each guarded independently (by `gathered_signatures` and `responded_signers` respectively) instead of being mutually exclusive, so one signer's weight can sit in both tallies at once, exactly the "aggregated-weight vs verified-accepts" equality break called out in the validation rules.

### Finding Description
In `handle_signer_message` (stackerdb_listener.rs), the `Accepted` arm only checks `!block.gathered_signatures.contains_key(&slot_id)` before adding `signer_entry.weight` to `total_weight_approved`: [2](#0-1) 

The `Rejected` arm only checks `block.responded_signers.insert(slot_id)` before adding weight to `total_weight_rejected`: [3](#0-2) 

Critically, the `Accepted` arm calls `block.responded_signers.insert(slot_id)` unconditionally *after* crediting weight [4](#0-3) , but it never checks `responded_signers` (or subtracts from `total_weight_rejected`) *before* crediting `total_weight_approved`. So the sequence Reject → Accept from the same signer for the same `block_sighash` results in:
- `total_weight_rejected += weight` (from the Reject, `responded_signers` now contains `slot_id`)
- `total_weight_approved += weight` (from the later Accept — unguarded by `responded_signers`, since the check is only against `gathered_signatures`, which the Reject never touched)

The signer's weight is now counted in both tallies simultaneously and permanently; `total_weight_rejected` is never decremented. Note the reverse ordering (Accept → Reject) is protected, since the `Rejected` arm's `responded_signers.insert` returns `false` once `Accepted` has already inserted the slot — this makes the asymmetry deliberate-looking but incomplete, mirroring `FTCHook::onIncreasePosition` minting with no corresponding `onDecreasePosition` burn.

This is a legitimate, reachable sequence in normal protocol operation, not merely theoretical: the signer explicitly supports "repeat my earlier answer (unless the reason I rejected has since gone away)," i.e. a signer that initially rejects for a transient reason (e.g., a temporarily failing validation, or a rejection filed before a competing sibling went stale) can later validate and sign the very same block once the condition clears, per the signer flow documented in `docs/signer-flows.md`.

### Impact Explanation
`total_weight_rejected` feeds directly into the miner's decision to abandon a block proposal in `SignerCoordinator::wait_for_signer_responses` in `signer_coordinator.rs`, at the check `block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight`, which returns `NakamotoNodeError::SignersRejected` and computes `temporarily_excluded_txids`/`permanently_excluded_txids` from the phantom rejecting weight: [5](#0-4) 

Because the stale rejection weight is never retracted, a signer who legitimately changes their mind (which the protocol explicitly anticipates) causes their weight to be double-booked: it inflates `total_weight_rejected` forever for that block hash while also correctly counting toward `total_weight_approved`. This can push the aggregate rejected weight past the 30% blocking-minority threshold even though the true, current set of rejecting signers is below it, causing the miner-coordinator to treat a proposal as globally rejected and to permanently exclude transactions (`permanently_excluded_txids`) based on a threshold computed from weight that a verifying signer has since retracted by accepting. This wedges the miner's per-tenure block-building loop away from a proposal (and associated transactions) that in reality has, or could still reach, the real 70% signature quorum, a liveness degradation directly caused by the aggregated-weight-vs-verified-accepts equality being broken.

### Likelihood Explanation
This requires only a single signer (which could be the attacking/analyzing entity's own signer, or one it can induce via network delay/reordering to send a late Reject and then an Accept for the same block, or vice versa in a scenario the code doesn't guard) — no majority collusion is needed. The Reject→Accept-for-same-block pattern is an expected part of normal operation per the documented "repeat my earlier answer unless the reason has gone away" behavior, so it can occur without any malicious intent, purely from timing/ordering of routine validation retries and StackerDB message delivery order.

### Recommendation
Make `total_weight_approved` and `total_weight_rejected` mutually exclusive and revocable for the same signer/block: before crediting `total_weight_approved` in the `Accepted` arm, check `responded_signers` for prior rejection and subtract the signer's weight from `total_weight_rejected` (and analogously guard the `Rejected` arm against a prior acceptance, deciding which response should win). At minimum, gate weight crediting on a single per-signer "current vote" map (slot_id → Accept/Reject) rather than two independently-guarded accumulators, so a signer's weight only ever appears in exactly one tally at a time, restoring the equality between `total_weight_rejected` and the real, up-to-date set of signers who currently reject the block.

### Proof of Concept
1. Set up a signer set with a `weight_threshold` such that a single signer's weight is enough to move `total_weight_rejected` across the `> self.total_weight - weight_threshold` blocking-minority boundary when combined with other genuine rejecting signers just under that boundary.
2. Have signer S send `BlockResponse::Rejected` for block hash `H` — this drives `blocks[H].total_weight_rejected` to just over the blocking-minority boundary and, combined with other signers' rejections already tallied, is read by `SignerCoordinator::wait_for_signer_responses` and returns `NakamotoNodeError::SignersRejected`.
3. Independently (e.g., because S's local `check_block_against_signer_db_state` recheck subsequently passed, per section 5 of `docs/signer-flows.md`), S now sends `BlockResponse::Accepted` for the same `H`.
4. Observe in `stackerdb_listener.rs` that `blocks[H].total_weight_approved` is incremented by S's weight via the `Accepted` arm (guarded only by `gathered_signatures`), while `blocks[H].total_weight_rejected` still retains S's earlier contribution (no code path decrements it) — S's weight is now counted in both `total_weight_approved` and `total_weight_rejected` for the same block, and any coordinator poll that read the block status before this final Accept already returned `SignersRejected`/excluded transactions based on the inflated total that included S's since-retracted rejection.
