### Title
Stale confirmations from removed multisig members are never purged from unrelated pending requests, allowing execution below `num_confirmations` live members - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` (`multisig2/src/lib.rs:356-379`) only purges confirmations for requests whose *original submitter* (`r.member`) equals the removed member; it never scans other pending requests' `confirmations: HashSet<String>` for an entry matching the removed member's `to_string()`. As a result, a confirmation cast by member `M` on request `R` (submitted by someone else) survives `M`'s removal indefinitely, and `confirm` (`multisig2/src/lib.rs:294-315`) later counts that stale entry toward `num_confirmations`, executing `R` with fewer genuinely-current confirming members than required.

### Finding Description
The binding that must hold is: `|{ members m : m.to_string() ∈ confirmations[R] ∧ m ∈ self.members }| >= num_confirmations` at the moment `R` executes. The actual code only checks `confirmations.get(&request_id).unwrap().len() as u32 + 1 >= self.num_confirmations` in `confirm` (`multisig2/src/lib.rs:304`), with no re-validation that every string already stored in the `HashSet<String>` still corresponds to a current member of `self.members`.

`delete_member` (`multisig2/src/lib.rs:356-379`) removes `member` from `self.members` and deletes requests/confirmations only for requests that `member` itself submitted:
```
let request_ids: Vec<u32> = self.requests.iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
``` [1](#0-0) 

This filter is keyed on `r.member` (the request's submitter), not on membership in each request's `confirmations` set. So if `M` had merely *confirmed* (not submitted) some other pending request `R`, `R`'s confirmation set retains the entry `M.to_string()` forever, even after `M` is deleted from `self.members` at line 374 [2](#0-1) .

Exploit flow (no re-add even required, though re-add as described in the question also works identically since the string returned by `MultisigMember::to_string()` is deterministic and reused):
1. Member `A` calls `add_request` creating `R` (e.g. `Transfer`). `confirmations[R] = {}`.
2. Member `M` calls `confirm(R)` — stored, `confirmations[R] = {M}` (below threshold, not executed) — `multisig2/src/lib.rs:311-312`.
3. A separate self-request `DeleteMember{member: M}` reaches quorum and executes `delete_member`, removing `M` from `self.members`. `R`'s confirmation set is untouched because `R.member == A ≠ M`.
4. Any other live member confirms `R`. `confirmations.len() (1, from M) + 1 (new confirmer) >= num_confirmations (2)` is true, so `execute_request(R)` runs — `multisig2/src/lib.rs:304-309`.

At execution time only one truly current member confirmed `R`; `M`'s confirmation predates its removal and was never invalidated. `assert_valid_request` only checks the *caller* of `confirm` is a current member (`multisig2/src/lib.rs:407-423`); it never re-validates the pre-existing entries in the `HashSet<String>`. No other guard (`assert_self_request`, `assert_one_action_only`, `current_member`) touches this stored set.

### Impact Explanation
Any request type—including `Transfer`, `AddKey`/`FunctionCall`, or further `AddMember`/`DeleteMember` actions—can execute with fewer than `num_confirmations` currently-live members having actually approved it at execution time. If `R` is a `Transfer`, NEAR leaves the multisig account authorized by a confirmation from an account that is no longer entitled to approve anything. This matches the explicitly listed Critical impact category "a multisig request executed below `num_confirmations` live members." The blast radius covers any multisig deployed via the public multisig factory where membership ever changes while requests are pending — a very common operational pattern (member key rotation, offboarding).

### Likelihood Explanation
No special privilege beyond normal multisig operation is required: the sequence relies only on ordinary `add_request`/`confirm`/member-management calls that any multisig deployed through the public factory can perform. It requires: (a) a pending request with fewer confirmations than `num_confirmations`, and (b) a member-removal event (rotation, offboarding, key replacement) occurring afterward without the removed member's stale confirmations being purged. Since delete/add-member operations are routine multisig maintenance, this is highly likely to occur in practice, and is repeatable for every pending request and every membership change, in any multisig instance.

### Recommendation
In `delete_member`, iterate over *all* pending requests' confirmation sets (not just those submitted by the removed member) and remove any entry equal to `member.to_string()`. Alternatively, in `confirm`, re-derive the quorum count by intersecting the stored `HashSet<String>` with the current `self.members` set (converted to strings) before comparing against `num_confirmations`, so stale/removed identities never count toward quorum.

### Proof of Concept
```rust
#[test]
fn test_stale_confirmation_survives_member_deletion() {
    // members: alice, bob, M(access key); num_confirmations = 2
    testing_env!(context_with_account(alice(), 1_000));
    let mut c = MultiSigContract::new(
        vec![
            MultisigMember::Account { account_id: alice() },
            MultisigMember::Account { account_id: bob() },
            MultisigMember::AccessKey { public_key: test_key() },
        ],
        2,
    );

    // Step 1: alice submits R (transfer), no confirm.
    let r = MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: 100.into() }],
    };
    let request_id = c.add_request(r.clone());

    // Step 2: M confirms R -> confirmations[R] = { M }, below threshold.
    testing_env!(context_with_key(test_key(), 1_000));
    c.confirm(request_id);
    assert_eq!(c.get_confirmations(request_id).len(), 1);

    // Step 3: separate self-request deletes M, executed by alice+bob (quorum=2).
    testing_env!(context_with_account(alice(), 1_000));
    let del_req = MultiSigRequest {
        receiver_id: alice(),
        actions: vec![MultiSigRequestAction::DeleteMember {
            member: MultisigMember::AccessKey { public_key: test_key() },
        }],
    };
    let del_id = c.add_request(del_req);
    testing_env!(context_with_account(bob(), 1_000));
    c.confirm(del_id); // 2nd confirm -> executes delete_member(M)

    // BINDING CHECK #1: M must no longer be a current member.
    assert!(!c.get_members().contains(&MultisigMember::AccessKey { public_key: test_key() }));

    // BINDING CHECK #2: R's confirmations must NOT still contain M's stale entry
    // (this assertion FAILS, proving the bug: M's confirmation was never purged)
    assert!(c.get_confirmations(request_id).is_empty(), "stale confirmation from removed member M still present");

    // Step 4: bob confirms R -> executes with only 1 truly-live confirmer (bob),
    // even though num_confirmations = 2.
    testing_env!(context_with_account(bob(), 1_000));
    c.confirm(request_id);
    // request executed (removed from map) despite only 1 live member ever confirming it.
    assert!(c.get_request(request_id).receiver_id == bob()); // panics: "No such request" proves R executed
}
```
The test demonstrates that `R` executes via `confirm` at `multisig2/src/lib.rs:304-309` while the set of *current* members whose confirmation strings are present in `confirmations[R]` is only `{bob}` (size 1), not meeting `num_confirmations = 2`, because `M`'s stale entry from before deletion was never removed by `delete_member` (`multisig2/src/lib.rs:361-371`).
