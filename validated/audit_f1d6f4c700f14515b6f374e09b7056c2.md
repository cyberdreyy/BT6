### Title
`RecentLeaderSlots::estimate_current_slot` integer overflow/panic on a single near-`u64::MAX` slot value - ([File: tpu-client-next/src/node_address_service/recent_leader_slots.rs])

### Summary
`RecentLeaderSlots::estimate_current_slot` computes `median_recent_slot + (max_index - median_index) as u64` and `expected_current_slot + MAX_SLOT_SKIP_DISTANCE` without overflow protection. A single `SlotEvent::Start(slot)` with `slot` close to `u64::MAX` (e.g. `u64::MAX - 10`) causes this addition to overflow `u64`, and even where wraparound doesn't panic outright, the subsequent `rposition(...).expect("no reasonable slot")` panics because no element satisfies the wrapped-around threshold.

### Finding Description
`SlotUpdateService::run`'s `main_loop` (`tpu-client-next/src/node_address_service/slot_update_service.rs:38-48`) calls `recent_slots.record(slot_event)` followed unconditionally by `recent_slots.estimate_current_slot()` for every single item received from `slot_update_stream`. `slot_update_stream` is fed directly from `websocket_slot_event_stream`, which maps `SlotUpdate::FirstShredReceived { slot, .. }` from the pubsub subscription straight into `SlotEvent::Start(slot)` with no bounds/sanity check (`tpu-client-next/src/websocket_node_address_service.rs:138-143`).

In `estimate_current_slot` (`recent_leader_slots.rs:34-65`), with only one recorded event, `max_index == median_index == 0`, so:
- `median_recent_slot = slot_event.slot()` (attacker-controlled, e.g. `u64::MAX - 10`)
- `expected_current_slot = median_recent_slot + 0`
- `max_reasonable_current_slot = expected_current_slot + MAX_SLOT_SKIP_DISTANCE` (`+48`)

Since `48 > 10`, `expected_current_slot + 48` overflows `u64::MAX`. The function is annotated with `#[allow(clippy::arithmetic_side_effects)]`, which only suppresses the clippy lint and does not add checked/wrapping arithmetic — in a debug/overflow-checked build this `+` panics directly. In a release build (wrapping arithmetic), `max_reasonable_current_slot` wraps to a small value (e.g. `37`), and the subsequent `recent_slots.iter().rposition(|e| e.slot() <= max_reasonable_current_slot)` finds no matching element (the only element's slot is `u64::MAX - 10`, far larger than `37`), so `.expect("no reasonable slot")` at line 57 panics regardless of build profile.

This is reachable with a single crafted `SlotUpdate::FirstShredReceived` message on one `slot_updates_subscribe` websocket subscription, satisfying the stated single-message/single-subscription precondition.

### Impact Explanation
The panic occurs inside the `tokio::spawn`'d `main_loop` future in `SlotUpdateService::run`. A panicking async task aborts that task; `JoinHandle::await` (in `shutdown`) then returns `Err`, and the `watch::channel`-backed `SlotReceiver` is left permanently on the last-sent (stale) slot with no further updates, degrading TPU-client leader/slot tracking indefinitely from a single malicious/MITM'd websocket message. This matches a validator/client-process crash-or-deadlock category triggered by one request.

### Likelihood Explanation
Requires only: one active `slot_updates_subscribe` websocket subscription and the ability to inject or MITM a single `SlotUpdate::FirstShredReceived{slot}` notification with `slot` in the range `[u64::MAX - 47, u64::MAX)` (so that `median_recent_slot + MAX_SLOT_SKIP_DISTANCE` overflows or wraps below the recorded slot). No authentication, staking, or repeated calls are needed — fully deterministic and repeatable on the very first received update.

### Recommendation
Use checked/saturating arithmetic in `estimate_current_slot`:
- Replace `median_recent_slot + (max_index - median_index) as u64` with `median_recent_slot.saturating_add((max_index - median_index) as u64)`.
- Replace `expected_current_slot + MAX_SLOT_SKIP_DISTANCE` with `expected_current_slot.saturating_add(MAX_SLOT_SKIP_DISTANCE)`.
- Remove the `#[allow(clippy::arithmetic_side_effects)]` suppression once fixed, so future regressions are caught by clippy.
- Additionally, guard against the `rposition(...).expect(...)` panic by falling back to a safe default (e.g. the largest recorded slot, or `cached_estimated_slot`) instead of `.expect`.
