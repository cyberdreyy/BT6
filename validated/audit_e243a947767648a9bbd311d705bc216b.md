### Title
Post-default instant withdraw requests corrupt `defaultRecoveryEpoch` accounting — clamping `pendingInstantWithdraws` to zero permanently freezes funded claims and drains the recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
An "out-of-bounds write" analog: `requestInstantWithdraw` keeps recording receipts into the same epoch bucket used by the finalized default (`epochNumber` never advances after default finalization), so post-default receipt basis is silently merged into `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`. When such a user claims, `_claimDefaultedInstantWithdrawRequest` treats the whole mixed basis as defaulted-epoch basis: it pays the post-default portion from `defaultRecoveryReserve` at the recovery haircut and clamps `pendingInstantWithdraws` to `0`, after which `collectInstantWithdrawFunds` underflows on any subsequent funding attempt, permanently freezing other users' instant-withdraw claims.

### Finding Description
After a borrower default is finalized (`defaultRecoveryFinalized == true`), `epochNumber` stops advancing and `defaultRecoveryEpoch` equals `epochNumber` forever (`IdleCreditVault.sol:693`). `requestInstantWithdraw` has no post-default branch — it still does `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount`, `instantWithdrawClaimsByEpoch[epochNumber] += _amount`, and `pendingInstantWithdraws += _amount` (`IdleCreditVault.sol:367-374`). A post-default request therefore lands in the exact same per-epoch slot as genuinely defaulted receipts.

On claim, `claimInstantWithdrawRequest` invokes `_claimDefaultedInstantWithdrawRequest` whenever `defaultInstantWithdrawsFinalized` is true (`IdleCreditVault.sol:382-385`). That function reads `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (`:844`) — now polluted with post-default basis — then:

1. `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` and `pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis` (`:847-853`). Because `claimBasis` includes post-default principal, it can exceed the true unfunded remainder, clamping `pendingInstantWithdraws` to `0` while other users still hold unfunded instant receipts.
2. `_transferDefaultRecovery(_user, claimBasis * defaultRecoveryPrice / 1e18)` (`:855`) debits `defaultRecoveryReserve` (`:915`) for post-default basis that was never included in `totalBasis` at `finalizeDefaultRecovery` (`:679-688`), diluting/stealing recovery funds reserved for pre-default claimants.

Any later borrower funding via `collectInstantWithdrawFunds(_amount)` executes `pendingInstantWithdraws -= _amount` (`:401`), which underflows and reverts once the counter was clamped to `0`, so the CDO can never collect funds to pay remaining instant claimants.

### Impact Explanation
Two direct impacts, both reachable by an unprivileged tranche-token holder:

- **Permanent freezing of funds**: once `pendingInstantWithdraws` is clamped to `0` while real unfunded receipts remain, `collectInstantWithdrawFunds` reverts on every subsequent funding call, permanently blocking repayment of other users' instant-withdraw receipts (amount: up to the full remaining instant queue for that pool).
- **Recovery-reserve drainage**: post-default basis is paid out of `defaultRecoveryReserve` at `defaultRecoveryPrice` although it was excluded from the `totalBasis` used to size that reserve, reducing the reserve available to legitimate defaulted-epoch claimants below their entitled `defaultRecoveryPrice` share.

### Likelihood Explanation
Requires a default finalized with `pendingInstantWithdraws != 0` (partially funded instant queue — realistic, since `startEpoch` can leave the instant queue partially covered) and a CDO path that still permits `requestInstantWithdraw` post-default. The vault code contains no guard blocking it, and the symmetric `requestWithdraw` explicitly supports post-default requests (`IdleCreditVault.sol:247-257`), indicating post-default withdrawals are an intended flow. The attacker pays a griefing cost of `(1 - defaultRecoveryPrice) * amount`, so the theft-of-reserve component is bounded, but the permanent-freeze component costs the attacker only the haircut on an arbitrarily small request while freezing an arbitrarily large victim queue — a strong asymmetric griefing/insolvency primitive.

### Recommendation
- In `requestInstantWithdraw`, when `defaultRecoveryFinalized`, either revert or track post-default instant receipts under a separate bucket (e.g., a `postDefaultInstantRequests` mapping keyed by a monotonically increasing post-default epoch id) instead of `instantWithdrawsRequestsByEpoch[user][epochNumber]`.
- In `_claimDefaultedInstantWithdrawRequest`, cap `claimBasis` at the basis recorded at finalization time (snapshot `instantWithdrawClaimsByEpoch` at `defaultRecoveryEpoch` before post-default mutations), or decrement `pendingInstantWithdraws` only by the pre-default component.
- Consider bumping `epochNumber` once at `finalizeDefaultRecovery` so post-default receipts can never alias the defaulted epoch.

### Proof of Concept
Foundry fork test sketch (pool already in "partially funded instant queue" state):

```solidity
function testPostDefaultInstantCorruptsPending() external {
    // 1) Epoch E running; userA calls requestInstantWithdraw(100).
    //    startEpoch funds only 30 -> pendingInstantWithdraws == 70,
    //    instantWithdrawClaimsByEpoch[E] == 100.
    // 2) Borrower defaults; owner calls finalizeDefault / finalizeDefaultRecovery
    //    -> defaultRecoveryFinalized = true, defaultInstantWithdrawsFinalized = true,
    //    defaultRecoveryEpoch = E, defaultRecoveryPrice = p < 1e18,
    //    defaultRecoveryReserve sized for basis that includes A's 100.
    // 3) Attacker B (any tranche holder) calls:
    cdoEpoch.requestInstantWithdraw(50);              // IdleCDOEpochVariant
    //    -> instantWithdrawsRequestsByEpoch[B][E] = 50,
    //       pendingInstantWithdraws = 70 + 50 = 120  (B's receipt mixed into epoch E)
    // 4) B claims:
    cdoEpoch.claimInstantWithdrawRequest();
    //    _claimDefaultedInstantWithdrawRequest(B):
    //      claimBasis = 50  (includes only post-default basis for B)
    //      B receives 50 * p from defaultRecoveryReserve  <- reserve drained for
    //      basis never counted in totalBasis
    //    If instead claimBasis >= pendingInstantWithdraws:
    //      pendingInstantWithdraws == 0 while A still has 70 unfunded.
    // 5) Borrower tries to fund the remaining queue:
    vm.expectRevert(); // arithmetic underflow: pendingInstantWithdraws - amount
    strategy.collectInstantWithdrawFunds(remaining); // called via CDO stopEpoch path
    // 6) A's funded claim is now unreachable: pendingInstantWithdraws can never
    //    be collected again -> permanent freeze of A's 100 * p recovery/funded payout.
}
```

Key lines: `requestInstantWithdraw` writes into `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (`IdleCreditVault.sol:367-374`); `_claimDefaultedInstantWithdrawRequest` reads the same slot keyed by `defaultRecoveryEpoch` and clamps `pendingInstantWithdraws` (`:842-856`); `collectInstantWithdrawFunds` underflows once the counter is zeroed (`:398-403`).
