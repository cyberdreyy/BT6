### Title
Stale epoch-keyed read in `defaultPendingClaimBasis` inflates `defaultRecoveryPrice` and drains the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`defaultPendingClaimBasis()` computes the defaulted-epoch instant-withdraw claim basis by reading only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch key. Instant-withdraw receipts requested in earlier epochs that remain unfunded (`pendingInstantWithdraws != 0`) are silently excluded from the recovery basis, even though the same receipts still exist in `instantWithdrawsRequests[user]` and remain claimable. This is the direct analog of the npmconf uninitialized-read bug (GHSA-57cf-349j-352g): an uninitialized/stale slot is read instead of the data actually owed, producing a wrong result that is then acted on. The under-counted basis makes `finalizeDefaultRecovery` compute an inflated `defaultRecoveryPrice`, so default-epoch claimants are overpaid out of `defaultRecoveryReserve` until the strategy's underlying balance is exhausted, permanently freezing older receipt holders' claims.

### Finding Description

`defaultPendingClaimBasis` adds instant claims only for the epoch in which default is finalized:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
``` [1](#0-0) 

`instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` are keyed by the epoch in which `requestInstantWithdraw` ran, while `pendingInstantWithdraws` is a *global* aggregate that is decremented only by `collectInstantWithdrawFunds` and by claims [2](#0-1) . If instant receipts from epoch N-1 were only partially funded (borrower returned less than requested via `getInstantWithdrawFunds`/`collectInstantWithdrawFunds`), the unfunded remainder survives in `pendingInstantWithdraws` while its per-epoch basis sits under key N-1. When a default is later finalized in epoch N, `defaultPendingClaimBasis` contributes only `instantWithdrawClaimsByEpoch[N]` — the N-1 basis reads as 0 (the "uninitialized" slot) even though those users still hold live claims.

`finalizeDefaultRecovery` then computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` over the shrunken `totalBasis`, so every defaulted-epoch and post-default claimant is paid at an inflated ratio via `_transferDefaultRecovery`, which debits `defaultRecoveryReserve` and transfers real underlying [3](#0-2) . `_defaultPrefundedInstantReserve` has the same single-epoch read (`instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws`), so prefunded cash backing older receipts is also misattributed [4](#0-3) .

### Impact Explanation

Invariant broken: loss waterfall / fair distribution of recovered funds. Recovery price is computed over an incomplete basis, so early claimants with default-epoch receipts receive more than their pro-rata share (recoveryPrice can exceed the true fair ratio, and even exceed `RECOVERY_FULL` since only `recoveryPrice == 0` is guarded elsewhere). Once the strategy balance is drained, older instant-withdraw receipt holders — whose claims remain recorded in `instantWithdrawsRequests` — can no longer be paid: `_transferFundedClaim` reverts whenever `balance - defaultRecoveryReserve < amount`, and after the reserve is consumed the balance itself is gone [5](#0-4) . Result: direct theft of recovery assets by earlier claimants and permanent freezing of the rest, quantified as `instantWithdrawClaimsByEpoch[oldEpochs] * (inflatedPrice - fairPrice)` plus the unpaid funded remainder.

### Likelihood Explanation

Requirements are all unprivileged-attacker reachable: (1) an instant-withdraw requester (any KYC'd lender or tranche holder) requests in epoch N-1; (2) the borrower only partially funds instant claims that epoch, leaving `pendingInstantWithdraws > 0` — a normal outcome whenever liquidity is short; (3) the borrower defaults in a later epoch (a base protocol scenario, not attacker-caused). No privileged misbehavior is needed; owner/manager calls (`stopEpoch`, `collectInstantWithdrawFunds`, `finalizeDefault`) are simply sequenced around. The guard `_ensureDefaultRecoveryInitialized` only blocks the *uninitialized-upgrade* path, not this stale-epoch-key read.

### Recommendation

In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, use the aggregate instant-claim basis (e.g., a running total of unfunded instant claims across all epochs, or iterate/track total `instantWithdrawClaims` rather than only `instantWithdrawClaimsByEpoch[epochNumber]`) so that receipts from any epoch with an unfunded remainder are included in the recovery basis. Similarly, `_claimDefaultedInstantWithdrawRequest` should clear the user's full outstanding unfunded basis, not only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`.

### Proof of Concept

A Foundry fork PoC would:

1. Deploy/fork `IdleCDOEpochVariant` + `IdleCreditVault`; deposit as LP, `startEpoch`.
2. Attacker (KYC'd user) calls `requestInstantWithdraw` in epoch N-1; borrower funds only part via `collectInstantWithdrawFunds`, leaving `pendingInstantWithdraws > 0`.
3. `stopEpoch`/`startEpoch` into epoch N; a second instant request is recorded under `instantWithdrawClaimsByEpoch[N]`.
4. Borrower defaults; manager runs `finalizeDefault`/`finalizeDefaultRecovery`.
5. Assert `defaultPendingClaimBasis()` excludes the epoch N-1 instant basis while `instantWithdrawsRequests[attacker]` is still nonzero; assert `defaultRecoveryPrice` exceeds the fair `reserve / trueBasis`.
6. Claim default-epoch receipts at the inflated price, then show the epoch N-1 instant claim now reverts in `_transferFundedClaim` / transfers fewer tokens than owed — permanent loss. [6](#0-5)

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;

      prefundedReserve = instantBasis - pendingInstant;

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
