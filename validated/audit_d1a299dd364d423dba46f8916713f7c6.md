### Title
Withdraw instruction offset-walk mislabels accounts when insufficient accounts are supplied for the given proof offset flags - ([File: transaction-status/src/parse_token/extension/confidential_transfer.rs])

### Summary
In `parse_confidential_transfer_instruction`'s `Withdraw` branch, the sequential `offset` bookkeeping used to conditionally label `instructionsSysvar`, `equalityProofContextStateAccount`, and `rangeProofContextStateAccount` assumes the number of supplied accounts always matches what the real on-chain instruction layout requires for the given offset flags. Because `check_num_token_accounts` only enforces a floor of 4 accounts (not the 5 accounts actually needed for several flag combinations), an attacker can submit a `Withdraw` instruction with exactly 4 accounts and offset flags requiring 5, causing the parser to skip a legitimate `*ProofContextStateAccount` label and instead mislabel that same account slot as `owner` via `parse_signers`.

### Finding Description
The relevant code is: [1](#0-0) 

`check_num_token_accounts(account_indexes, 4)` only guarantees `account_indexes.len() >= 4`. The subsequent logic walks `offset` starting at 2, guarded by `offset < account_indexes.len().saturating_sub(1)`. With `account_indexes.len() == 4`, `saturating_sub(1) == 3`, so only a single conditional insert (`offset == 2`) can execute before the guard blocks any further inserts — the remaining logic falls through to `parse_signers(map, offset, ...)`, which then labels whatever account sits at the current `offset` as `owner`.

For example, with `equality_proof_instruction_offset = 1` (proof bundled via instruction offset ⇒ `has_sysvar = true`) and `range_proof_instruction_offset = 0` (proof expected to live in a `rangeProofContextStateAccount`), the real/expected account layout needs 5 accounts: `account, mint, instructionsSysvar, rangeProofContextStateAccount, owner`. If the attacker supplies only 4 accounts (`account, mint, X, Y`), the code:
1. Inserts `instructionsSysvar = account_keys[account_indexes[2]]` (offset 2→3).
2. Skips the `rangeProofContextStateAccount` insert because `range_proof_instruction_offset == 0` but `offset(3) < len-1(3)` is false.
3. Calls `parse_signers(map, 3, ...)`, labeling `account_keys[account_indexes[3]]` as `owner`.

The account at index 3, which per the flags should be `rangeProofContextStateAccount`, is instead reported as `owner`. This is a straightforward decoder misreporting: the JSON-RPC consumer (e.g., `getTransaction` with `jsonParsed` encoding) receives an incorrectly labeled account for a transaction that is fully attacker-controlled (both instruction data bytes and account list), regardless of whether the instruction would succeed at runtime — failed transactions are still stored and parsed on request.

### Impact Explanation
This is a decoder/parse-fidelity bug: the JSON-parsed representation of a `withdrawConfidentialTransfer` instruction can mislabel a proof-context account as the transaction's `owner`/authority field. Any off-chain consumer (wallet, explorer, indexer) relying on `jsonParsed` output for this instruction type would display an incorrect authority/account role. This matches the explicitly in-scope category "decoder panic and misreporting."

### Likelihood Explanation
Fully attacker-controlled and requires no privileges beyond submitting one ordinary transaction (or even one that reverts, since failed transactions are still retrievable via `getTransaction`). The attacker only needs to invoke the SPL Token-2022 program's `Withdraw` instruction with a crafted `account_indexes` list of length exactly 4 and `equality_proof_instruction_offset`/`range_proof_instruction_offset` combination that implies 5 real accounts are needed (e.g., one offset zero, the other nonzero). This is deterministic and 100% reproducible.

### Recommendation
Replace the `account_indexes.len().saturating_sub(1)` heuristic with an explicit, flag-aware minimum-account-count check (computed from `has_sysvar`, whether each proof offset is zero) performed once via `check_num_token_accounts` before entering the sequential insert logic, so that insufficient-account instructions are rejected via `ParseInstructionError` rather than silently mislabeled. Alternatively, track remaining accounts precisely per expected field and bail out (return an error) instead of falling through to `parse_signers` when the account list is shorter than the flags require.

Broader fuzz/enumeration plan: for each of the 4 `(eq_offset==0?, range_offset==0?)` combinations, construct instructions with `account_indexes.len()` fixed at 4 (the `check_num_token_accounts` floor) and assert that every field the parser emits (`instructionsSysvar`, `equalityProofContextStateAccount`, `rangeProofContextStateAccount`, `owner`) is only ever populated from an account index that is structurally guaranteed to hold that role for the given flag combination — the assertion fails for the `has_sysvar=true, range_offset==0` and `has_sysvar=true, eq_offset==0` cases as shown above.
