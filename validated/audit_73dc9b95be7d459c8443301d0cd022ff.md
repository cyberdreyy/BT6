### Title
Stale rejection weight is never revoked when a signer later accepts, corrupting the miner's aggregated reject/accept tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::run` (in `stackerdb_listener.rs`) maintains two independent, monotonically-increasing counters, `total_weight_approved` and `total_weight_rejected`, per proposed block. The `Accepted` branch gates its weight increment on `block.gathered_signatures.contains_key(&slot_id)` [1](#0-0) , while the `Rejected` branch gates its increment on a *separate* set, `block.responded_signers.insert(slot_id)` [2](#0-1) . Because these are two different membership tests, a signer who first sends a `Rejected` response (weight added to `total_weight_rejected`, slot recorded in `responded_signers`) and later — per the documented, expected re-evaluation flow ("LocallyRejected --> LocallyAccepted : re-evaluated") — sends an `Accepted` response for the same block, has their weight added to `total_weight_approved` as well, without ever subtracting the earlier weight from `total_weight_rejected`.

### Finding Description
The signer state machine explicitly allows a local rejection to be superseded by a later local acceptance for the same block, and signer-side documentation states that "Rejection, even global rejection, does NOT clear the commitment... A rejection is a revocable opinion; a signature is a bearer instrument" [3](#0-2) . This makes clear that a signer's *rejection* opinion is meant to be revocable when the signer subsequently signs. The node-side coordinator, however, tracks acceptance and rejection weight using two disjoint sets (`gathered_signatures` vs `responded_signers`) rather than a single per-signer "current verdict" record: 
- Accept path: [1](#0-0) 
- Reject path: [2](#0-1) 

A signer that rejects and later accepts is counted in *both* `total_weight_approved` and `total_weight_rejected` simultaneously; `total_weight_rejected` is never decremented to reflect the signer's revocation. This breaks the equality the coordinator relies on: "aggregated rejected weight" should reflect signers currently opposing the block, but it instead accumulates stale, superseded opinions forever for that block hash.

### Impact Explanation
`signer_coordinator.rs` uses `total_weight_rejected` to decide whether to abort the in-flight block entirely: once `total_weight_rejected + weight_threshold > total_weight` (i.e., a blocking minority, ~30%, appears to have rejected), the miner gives up on the block and returns `SignersRejected`, discarding transaction inclusion progress for that proposal [4](#0-3) . Because stale rejection weight from signers who have since accepted is never purged, the aggregated reject tally can cross the blocking-minority threshold even though the *true, current* set of rejecting signers is below 30%. This wedges/aborts a specific block proposal round that could otherwise have reached the real 70% signature threshold, a liveness impact consistent with the "aggregated-weight vs verified-accepts" equality break called out for this class of bug.

### Likelihood Explanation
No majority or privileged access is required: any single signer that legitimately re-evaluates a block (rejects it, then subsequently determines it is acceptable and signs, a flow the signer client itself documents and implements: `LocallyRejected --> LocallyAccepted` re-evaluation) will trigger the stale counting. The bug is purely in the miner/node-side StackerDB listener tally and requires nothing beyond ordinary message gossip from one signer's own key.

### Recommendation
Track a single "current verdict + weight" per slot id (e.g., an enum `{Accepted(sig), Rejected}` map keyed by `slot_id`), and recompute `total_weight_approved`/`total_weight_rejected` by summing over the current verdicts rather than by two independently-incrementing, never-decrementing counters. When a slot's verdict changes from Rejected to Accepted (or vice versa), subtract the old contribution before adding the new one.

### Proof of Concept
1. Miner proposes block B; signer S (weight w) receives it, decides to reject (e.g., transient chainstate check failure), broadcasts `BlockResponse::Rejected`. Coordinator: `total_weight_rejected += w`, `responded_signers.insert(S)`.
2. S receives a pre-commit/re-proposal and, per the documented re-evaluation path, now signs and broadcasts `BlockResponse::Accepted`.
3. Coordinator's Accept handler checks `gathered_signatures.contains_key(S)` → false → `total_weight_approved += w`; it does not check/clear `responded_signers` or subtract `w` from `total_weight_rejected`.
4. `total_weight_rejected` now permanently includes `w` for this block hash, even though S has since accepted. Combined with other signers who independently and currently reject at just under the 30% blocking minority, the addition of this phantom `w` can push `total_weight_rejected + weight_threshold > total_weight`, causing `signer_coordinator.rs` to abort the block via `SignersRejected` even though the real, current rejecting weight is below the blocking minority.
