## Finding: Malicious operator can permanently block a staker's stake unlock/withdrawal via a poisoned beneficiary in `staking_contract::distribute_internal`

### Title
Operator-controlled beneficiary can permanently DoS `staking_contract` unlock/withdraw/switch-operator flows via `aptos_account::deposit_coins` revert - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`distribute_internal` iterates over every shareholder of a single, shared `distribution_pool` (which holds both the staker's pending withdrawal and the operator/beneficiary's pending commission) and unconditionally calls `aptos_account::deposit_coins` for each one in the same transaction, exactly the pattern flagged in the external report (a single failing "receiver" call reverting the whole distribution). Because the operator fully controls their own `beneficiary_for_operator` address, they can engineer that address to make `deposit_coins` abort every time, and since `distribute_internal` is called unconditionally as the first step of `unlock_stake`, `switch_operator`, `update_commision`, and `request_commission`, this traps the staker's own principal/rewards as well.

### Finding Description
`distribute_internal` pays out all shareholders of `staking_contract.distribution_pool` in one loop: [1](#0-0) 

Both the staker and the operator (redirected to `beneficiary_for_operator`) are added as shareholders of this same pool via `add_distribution`, called from `unlock_stake` (staker entry) and `request_commission_internal` (operator entry): [2](#0-1) [3](#0-2) 

`distribute_internal` is unconditionally invoked as a prerequisite step before the "real" logic in every user-facing mutator: `update_commision`, `request_commission`, `unlock_stake`, and `switch_operator`: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

The actual payout uses `aptos_account::deposit_coins`, which reverts if the recipient account already exists, is not registered for the coin, and has opted out of direct coin transfers: [8](#0-7) 

`set_allow_direct_coin_transfers` lets any signer opt an *existing* account out of unregistered-coin deposits, and it is off by default only when explicitly toggled: [9](#0-8) [10](#0-9) 

An operator fully controls `beneficiary_for_operator`, which can be set to *any* address including a resource account the operator itself created (which has an `Account` resource but has never received APT, so it is not registered for `AptosCoin`). The operator can then call `set_allow_direct_coin_transfers(false)` for that resource account's signer. From that point on, every `deposit_coins(beneficiary, ...)` call in `distribute_internal` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.

Because the same shared distribution loop pays out the staker's entry too, the revert kills the *entire* transaction — including `unlock_stake`, `switch_operator`, and `update_commision`, all of which force a `distribute_internal` call first. This mirrors the report's core bug class exactly: one uncooperative payout recipient breaks a shared distribution routine for everyone.

### Impact Explanation
Once the operator poisons its beneficiary, the staker permanently loses the ability to:
- Unlock or withdraw already-unlocked principal/rewards via `unlock_stake` (reverts before executing the withdrawal logic).
- Switch away from the malicious operator via `switch_operator` (reverts before the operator/commission update).
- Update commission terms via `update_commision`.
- Call the permissionless `distribute` entry function at all.

This is a durable, non-recoverable lock of stake claim rights that an unprivileged operator can impose on a staker who has delegated stake to them through `staking_contract`, satisfying the "Permanent lock or non-recoverable loss of claim rights in stake ... flows" impact bucket. There is no recovery path in the module: the staker cannot remove the poisoned distribution entry or force-skip it.

### Likelihood Explanation
The operator role is inherently less trusted than the staker in this design (the staker delegates funds and manages an operator relationship), and setting a hostile beneficiary plus disabling direct transfers requires only two entry-function calls the operator can execute unilaterally (`staking_contract::set_beneficiary_for_operator` and `aptos_account::set_allow_direct_coin_transfers` on an address they control), with no special privilege beyond being an operator. This is realistically triggerable on mainnet whenever a staker has an active `staking_contract` with a non-cooperative operator.

### Recommendation
Do not let a single recipient failure abort the whole distribution loop. Mirror the report's suggested fix pattern: attempt payout per-recipient defensively (e.g., wrap the deposit so a failed/opt-out recipient's share is retained/queued rather than aborting the transaction), or separate the staker's and operator's distribution pools so one party's misbehavior cannot block the other's withdrawal. At minimum, `unlock_stake`/`switch_operator`/`update_commision` should not force a `distribute_internal` step for the *other* party's shares before performing the requested operation.

### Proof of Concept
1. Staker creates a `staking_contract` with `operator` O, commission > 0.
2. O calls `staking_contract::set_beneficiary_for_operator(O, R)` where R is a resource account O created but never funded with APT (so `Account` exists at R but no `AptosCoin` `CoinStore`/primary-store registration exists).
3. O uses R's `SignerCapability` to call `aptos_account::set_allow_direct_coin_transfers(&R_signer, false)`.
4. O calls `staking_contract::request_commission` at least once so R has a nonzero shares entry in `distribution_pool` once commission becomes available (or simply wait until commission accrues and gets unlocked).
5. Staker calls `staking_contract::unlock_stake` (or O calls `switch_operator`/`update_commision`) once there is any unlocked/inactive stake to flush; `distribute_internal` iterates shareholders, reaches R, calls `aptos_account::deposit_coins(R, ...)`, which aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
6. The entire transaction (including the staker's intended unlock/withdraw) reverts, and remains permanently unreversible as long as O keeps R in this poisoned state.

Note: I was not able to fully verify, within available tool calls, whether Aptos's fungible-asset migration for `AptosCoin` (`coin::is_account_registered<AptosCoin>` / primary fungible store semantics) changes this precondition for freshly-created vs. legacy accounts; the PoC assumes the classic `CoinStore`-based registration check shown in `aptos_account::deposit_coins` still applies to an unfunded resource account as described in the source above. This should be independently confirmed against the currently deployed coin/FA migration state before relying on the exact reproduction steps.

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

        // Request to unlock the commission from the stake pool.
        // This won't become fully unlocked until the stake pool's lockup expires.
        stake::unlock_with_cap(commission_amount, &staking_contract.owner_cap);

        let pool_address = staking_contract.pool_address;
        emit(
            RequestCommission {
                operator,
                pool_address,
                accumulated_rewards,
                commission_amount
            }
        );

        commission_amount
    }
