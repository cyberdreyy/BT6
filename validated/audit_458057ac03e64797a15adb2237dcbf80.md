### Title
Epoch-keying mismatch lets unfunded instant-withdraw receipts escape the default haircut and be paid at par (or permanently frozen) - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Mako bug is a *two-interpreters* flaw: the traversal check validates the URI under `os.path`/`ntpath` semantics while the lookup normalizes it under `posixpath` semantics, so an input that is "in-bounds" for one interpreter escapes under the other. `IdleCreditVault` has the same structure for instant-withdraw receipts: eligibility for the default-recovery haircut is keyed by `epochNumber` **at finalization time** (`instantWithdrawClaimsByEpoch[epochNumber]` in `defaultPendingClaimBasis`, `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` in `_claimDefaultedInstantWithdrawRequest`), while the actual payout path `claimInstantWithdrawRequest` resolves the **aggregate, epoch-agnostic** `instantWithdrawsRequests[_user]` at par through `_transferFundedClaim`. When `epochNumber` drifts between request recording and default finalization, the receipt is invisible to both the recovery basis and the defaulted-claim path, yet still fully claimable.

### Finding Description
1. `requestInstantWithdraw` records receipts under the *request-time* epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount`, and bumps `pendingInstantWithdraws` [1](#0-0) .
2. `epochNumber` is incremented inside `deposit()` whenever it is called while `isEpochRunning()` is still true — i.e., during `stopEpoch` borrower repayment [2](#0-1) . So an unfunded instant receipt recorded under epoch N can face finalization under epoch N+1.
3. `defaultPendingClaimBasis` only adds `instantWithdrawClaimsByEpoch[epochNumber]` — the *finalization* epoch — so a receipt recorded under N contributes **zero** basis when finalized under N+1, inflating `recoveryPrice` for everyone else [3](#0-2) .
4. `_defaultPrefundedInstantReserve` uses the same drifted key: `instantBasis = instantWithdrawClaimsByEpoch[epochNumber]` returns 0, so already-collected instant funds are not counted as reserve [4](#0-3) .
5. `defaultInstantWithdrawsFinalized` is still set from `pendingInstantWithdraws != 0`, so `claimInstantWithdrawRequest` enters the defaulted branch, but `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (= 0 under the drifted key) and returns without clearing anything [5](#0-4) [6](#0-5) .
6. The function then pays the full aggregate `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim`, which deliberately avoids spending `defaultRecoveryReserve` [7](#0-6) [8](#0-7) .

### Impact Explanation
Two broken outcomes, both direct fund impact:

- **Theft / over-payment at par**: if the strategy holds underlying outside the reserve (e.g., borrower-send funds that failed at epoch start, or partially collected instant funds), the drifted receipt is paid 1:1 with **no haircut**, while every other claimant — active LPs and normal pending receipts — absorbs the default loss. Simultaneously `recoveryPrice` was computed on a basis that excluded this claim, so remaining recovery claimants are also overpaid relative to true recovered value. This is unilateral loss socialization away from the attacker.
- **Permanent freezing**: if the strategy's non-reserve balance is insufficient, `_transferFundedClaim` reverts and the user's (honest) instant receipt is permanently unclaimable — the defaulted path clears nothing and the funded path cannot pay.

The broken invariant is "one receipt, one recovery haircut": a receipt that should share the default loss instead bypasses it entirely through an aggregate bucket the epoch-keyed guards never see.

### Likelihood Explanation
Requires: (a) instant withdrawals enabled, (b) an instant request left partially unfunded through a `stopEpoch` in which `deposit()` bumps `epochNumber` (borrower repayment while running), and (c) borrower default finalized afterward — a documented, reachable state per the contract's own comments about partially funded instant queues [9](#0-8) . The attacker is an ordinary KYC'd lender requesting an instant withdrawal; all sequencing is done by honest manager/owner calls. Likelihood is medium: it needs the specific epoch drift plus an unfunded remainder, but no privileged misbehavior.

### Recommendation
Make basis, clearing, and payout use one consistent epoch key — the same fix pattern as Mako's "normalize early, before any path operations":

- In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, aggregate instant claims across all epochs with pending receipts (or track a dedicated `defaultInstantClaimsEpoch` snapshot at `_handleBorrowerDefault` time) rather than indexing by the finalization-time `epochNumber`.
- Alternatively, record `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` under a stable "pending instant bucket" identifier that is only rolled when receipts are actually funded, so `epochNumber` drift cannot orphan them.

### Proof of Concept
Foundry fork PoC sketch (against the `IdleCreditVault.t.sol` harness):

1. Enable instant withdrawals: `cdoEpoch.setInstantWithdrawParams(delay, min, true)` (manager).
2. During buffer of epoch N: user deposits AA, then `requestInstantWithdraw(amount, user)` via the CDO — receipt recorded under `instantWithdrawsRequestsByEpoch[user][N]`.
3. `startEpoch()` (manager). At `stopEpoch`, have the borrower repay only part of `pendingInstantWithdraws` so `collectInstantWithdrawFunds` leaves `pendingInstantWithdraws > 0`, and ensure `strategy.deposit()` executes while `isEpochRunning()` → `epochNumber` becomes N+1.
4. Trigger default (`_handleBorrowerDefault` path) and call `finalizeDefaultRecovery(recovered, source)` → `defaultRecoveryEpoch = N+1`, basis excludes the user's claim, `defaultInstantWithdrawsFinalized = true`.
5. `claimInstantWithdrawRequest(user)`: `_claimDefaultedInstantWithdrawRequest` no-ops (key N+1 empty); the aggregate is paid at par via `_transferFundedClaim`.
6. Assert: `underlying` received == full `amount` (no haircut) while `defaultRecoveryPrice < RECOVERY_FULL`; or, with zero non-reserve strategy balance, assert the claim reverts permanently.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
