## Confirmed vulnerability

`LockupContract::new` at `lockup/src/lib.rs:180-243` is missing the `assert!(!env::state_exists(), ...)` guard that every other `#[init]` constructor in this codebase includes — compare `whitelist/src/lib.rs:34`, `multisig/src/lib.rs:104`, `staking-pool/src/lib.rs:179`, `staking-pool-factory/src/lib.rs:106`, and `lockup-factory/src/lib.rs:80`, all of which explicitly reject re-initialization. `LockupContract::new` has no such check, and `#[near_bindgen]`/`#[init]` in near-sdk 3.1.0 (per `lockup/Cargo.toml:12`) does not enforce this automatically — it's the contract author's responsibility, which every sibling contract fulfills except this one. [1](#0-0) 

**Broken invariant (equality)**: `state_written_once(account) == true` should hold for every lockup account after deploy. Because `new` unconditionally does `Self { owner_account_id, lockup_information, vesting_information, staking_information: None, ... }` and writes it via Borsh state overwrite with no existence check, a second call re-executes this write, so `state_written_once(account)` can be `> 1`.

Since `new` is a plain public `pub fn`, any unprivileged account can send a `FunctionCall("new", ...)` transaction directly to an *already-initialized* lockup account (no `create_account`, no factory involvement needed for the second call — the factory is only how the account was first bootstrapped). This bypasses:
- `assert_owner` / `assert_self` — `new` calls neither.
- `assert!(env::is_valid_account_id(...))` on `owner_account_id`, `staking_pool_whitelist_account_id`, `foundation_account_id`, `transfer_poll_account_id` — these only validate format, not the caller's authority to set these fields.
- `VestingSchedule::assert_valid` / `VestingScheduleWithSalt::hash` — irrelevant to authorization, only sanity-check the schedule shape.

**Exploit and impact**: The attacker re-invokes `new` on a victim's already-funded lockup account with `owner_account_id` set to an account the attacker controls, `vesting_schedule = None`, `foundation_account_id = None`, and `lockup_timestamp`/`release_duration` unset. This resets `lockup_information.lockup_amount` to `env::account_balance()` (the account's *current* balance, including all the victim's original + rewarded funds), sets `staking_information: None` (wiping any linked staking pool record — even mid-flight, so a pool `TransactionStatus::Busy` state tracked in the old struct is discarded and any callback like `on_staking_pool_withdraw`/`on_get_account_total_balance` that fires afterward operates on `self.staking_information == None`, panicking or being silently ignored depending on the code path in `owner_callbacks.rs`), and replaces `owner_account_id`/`vesting_information`/`foundation_account_id` entirely. Once the attacker's new state takes over the account, they call the owner-only methods (e.g. `transfer`) as the new `owner_account_id` to withdraw the account's NEAR balance — an account they were never entitled to (Critical impact category: "locked/unvested lockup tokens released to a party not entitled to them" / "an account ... deployed with parameters its rightful creator never chose").

I could not fully trace every callback interaction in `owner_callbacks.rs`/`foundation_callbacks.rs` after `staking_information` is nulled mid-flight (index size limits truncated deeper inspection of those files), but the core defect — a fully public, guard-less re-invocable `#[init]` `new` — is confirmed directly in the code shown above and is sufficient on its own to prove account takeover.

### Title
Missing re-initialization guard allows account takeover via repeated `new` calls - (File: lockup/src/lib.rs)

### Summary
`LockupContract::new` lacks the `assert!(!env::state_exists())` check present in every sibling contract's `#[init]` constructor, so any unprivileged account can call `new` again on an already-initialized lockup contract account and overwrite `owner_account_id`, `vesting_information`, `foundation_account_id`, and `staking_information`.

### Finding Description
Binding that should hold: `state_written_once(lockup_account) == true`. `lockup/src/lib.rs:180-243` defines `#[init] pub fn new(...)` with no `env::state_exists()` guard, unlike `whitelist/src/lib.rs:34`, `multisig/src/lib.rs:104`, `staking-pool/src/lib.rs:179`, `staking-pool-factory/src/lib.rs:106`, `lockup-factory/src/lib.rs:80`. Since `new` is a plain public method with no `assert_self`/`assert_owner`, any attacker can send a `FunctionCall("new", attacker_args)` transaction directly to a live lockup account, which overwrites the whole `LockupContract` struct, including `owner_account_id` (attacker-controlled), `vesting_information` (can be dropped to `None`), `foundation_account_id` (can be dropped), and `staking_information: None` (unconditionally reset regardless of any in-flight staking-pool `TransactionStatus::Busy` state). None of the existing guards (`assert_owner`, `assert_called_by_foundation`, `assert_self`, `is_promise_success`, `assert_one_yocto`, `assert_transfers_enabled`) apply because `new` doesn't call any of them.

### Impact Explanation
The attacker becomes the new `owner_account_id` of a victim's already-funded lockup contract and can then call owner-only methods (e.g. `transfer`) to move the account's NEAR balance — funds the victim deposited and never authorized moving to this new owner. Vesting/termination protections and any foundation oversight are also wiped, so the NEAR Foundation's ability to terminate unvested tokens is destroyed. This matches the Critical category: NEAR moved out of a lockup by a party never entitled to it. Repeatable against any lockup account and any number of times.

### Likelihood Explanation
Trivial precondition: attacker only needs to know a target lockup account ID (deterministic, `sha256(owner_id) + factory`, or discoverable on-chain) and pay standard transaction gas — no deposit, ownership, key, or foundation privilege required. Fully repeatable.

### Recommendation
Add `assert!(!env::state_exists(), "The contract is already initialized");` as the first line of `LockupContract::new` in `lockup/src/lib.rs`, matching the pattern used in every other contract's constructor in this repo.

### Proof of Concept
```rust
#[test]
#[should_panic(expected = "already initialized")]
fn test_reinit_blocked() {
    let context = basic_context();
    testing_env!(context.clone());
    let _contract = new_contract(true, None, None, false); // first init succeeds, state exists
    // Attacker calls new() again with attacker-controlled owner_account_id
    let _attacker_contract = LockupContract::new(
        "attacker".to_string(),
        0.into(),
        None,
        TransfersInformation::TransfersEnabled { transfers_timestamp: to_ts(GENESIS_TIME_IN_DAYS).into() },
        None,
        None,
        "whitelist".to_string(),
        None,
    );
    // Without the fix, this call succeeds silently and overwrites owner_account_id to "attacker",
    // demonstrating the missing env::state_exists() guard.
}
```
Run with `cargo test -p lockup-contract test_reinit_blocked`: on the current code this test fails (no panic occurs, proving the state was overwritten); after adding the `env::state_exists()` check it panics as expected.

            lockup_timestamp: lockup_timestamp.map(|d| d.0),
