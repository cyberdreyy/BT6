### Title
External-initiator credential for one job can trigger runs on any other job via `POST /v2/jobs/:ID/runs` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` grants a generic `UserRoleRun` "user" identity to any request bearing a valid EI access key/secret, without recording which job/bridge that EI is bound to in a way that `PipelineRunsController.Create` checks. Because the `POST /v2/jobs/:ID/runs` route accepts EI, token, or session auth interchangeably via the same `userOrEI` middleware chain and `RequiresRunRole` wrapper, an EI credential valid for one integration can be used to trigger a run on an arbitrary, unrelated job ID.

### Finding Description
The route is registered as: [1](#0-0) 

`auth.AuthenticateExternalInitiator` is tried first; for any valid EI accesskey/secret pair, it unconditionally sets: [2](#0-1) 

This creates a synthetic `*clsessions.User{Role: UserRoleRun}` in the same `SessionUserKey` context slot used for real authenticated users, with no reference to which job the EI is scoped to. `RequiresRunRole` only checks `user.Role != UserRoleView`, which passes for this synthetic run-role user: [3](#0-2) 

Inside `PipelineRunsController.Create`, the code checks only whether *some* authenticated user object exists (`isUser`) and then parses the job ID directly from the URL path, calling `RunJobV2` with that ID — there is no check correlating the EI identity (`GetAuthenticatedExternalInitiator`) with the target job ID: [4](#0-3) 

The comment "only users are allowed to run jobs using int IDs - EIs not allowed" is misleading/stale: `isUser` is derived from `auth.GetAuthenticatedUser(c)`, which simply reads the `SessionUserKey` context value — the very same key that `AuthenticateExternalInitiator` populates with a synthetic run-role `User`. Therefore EI-authenticated requests satisfy `isUser == true` and reach `RunJobV2` with attacker-supplied job ID, with no per-job scoping validation of the EI's authorization.

### Impact Explanation
Any holder of a single external-initiator's `AccessKey`/`Secret` (e.g. from one bridge/EA integration) can call `POST /v2/jobs/<any-job-ID>/runs` and trigger execution of a completely unrelated job, causing unauthorized job runs, forged run submissions, and potential state/impersonation confusion across jobs on the node. This matches the Chainlink bounty impact class of "unauthorized job run" / authorization bypass via request impersonation.

### Likelihood Explanation
The only precondition is possession of one valid EI accesskey/secret pair — a credential explicitly designed to be handed out to external bridge/EA operators, who are lower-trust than node admins. The exploit requires a single unauthenticated-looking HTTP POST with attacker-chosen job ID; it is fully repeatable and requires no race conditions, timing, or additional privileges.

### Recommendation
In `PipelineRunsController.Create` (or in `AuthenticateExternalInitiator`), validate that the authenticated external initiator is actually associated with the target job ID before invoking `RunJobV2`. Concretely: retrieve the `ExternalInitiator` from context via `auth.GetAuthenticatedExternalInitiator(c)`, look up the job spec's associated external initiator (webhook spec `ExternalInitiatorID`/name), and reject the request with `403` if the EI is not bound to that job ID. Do not treat EI-derived pseudo-users the same as real users for authorization purposes without job-scoping the check.

### Proof of Concept
Handler-level integration test plan:
1. Create two distinct jobs, Job A (webhook spec bound to External Initiator `EI-A`) and Job B (bound to `EI-B`, or edit-role created without any EI binding).
2. Register `EI-A` and obtain its `AccessKey`/`Secret`.
3. Send `POST /v2/jobs/<Job B ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to `EI-A`'s credentials.
4. Assert current (vulnerable) behavior: request succeeds (`200`) and `Application.RunJobV2` is invoked for Job B, i.e., `PipelineRunsController.Create` never rejects due to EI/job mismatch.
5. After fix: assert response is `401`/`403` and `RunJobV2` for Job B is never called, while `POST /v2/jobs/<Job A ID>/runs` with the same EI credentials still succeeds.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
