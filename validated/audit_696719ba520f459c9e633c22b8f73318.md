### Title
Unbounded iteration over all post-anchor dispute-game indexes in `GameScanner::scan` enables challenger starvation - (File: crates/proof/challenge/src/scanner.rs)

### Summary
The `GameScanner::scan` function in the Base fault-proof challenger re-evaluates *every* factory index between the current anchor and the latest game on each tick, with no upper bound on the range size. Because dispute-game creation is a permissionless, anonymously-reachable operation on the `DisputeGameFactory`, an attacker can inflate `game_count` far beyond what one scan tick can process, degrading or starving the challenger's ability to detect and respond to fraudulent/invalid proposals before the dispute window closes — the same "unbounded iteration over all indexes" bug class as the referenced Insure `PoolTemplate.sol` finding, but here it maps onto the fault-proof program's game-scanning path rather than a Solidity loop.

### Finding Description
`GameScanner::scan` computes `scan_start` (one past the cached anchor) and then evaluates the full range `scan_start..game_count` every tick: [1](#0-0) 

The struct's own doc comment acknowledges the design explicitly avoids any lookback cap: [2](#0-1) 

Concurrency is capped by `SCAN_CONCURRENCY = 32`, but the *total number of items* streamed through `buffer_unordered` per tick is unbounded and grows linearly with `game_count - scan_start`: [3](#0-2) 

Because `DisputeGameFactory.create()` is permissionless (bond-gated, but not otherwise access-controlled) and the anchor advances only when the `AnchorStateRegistry` finalizes a game, an attacker who keeps creating new games faster than the anchor advances (or who front-loads a burst of games before the anchor updates) can make `game_count - scan_start` grow without bound. Every scan tick then performs `O(n)` async RPC round-trips (`game_at_index`, `status`, `zk_prover`, `tee_prover`, `countered_index`, plus extra calls for actionable games) against the L1 node, so scan latency grows linearly with the attacker-controlled backlog.

### Impact Explanation
If a single scan tick cannot complete before the next tick is due (or before a fraudulent game's response window elapses), the challenger falls behind identifying `InvalidTeeProposal` / `InvalidZkProposal` / `FraudulentZkChallenge` candidates. A malicious or wrong output root proposed in a dispute game that the scanner has not yet reached in its backlog can resolve unchallenged, which is precisely the "wrong provable output root" impact class for the fault-proof program.

### Likelihood Explanation
Creating dispute games only requires paying the configured bond (`init_bonds`), which is an economically bounded but attacker-controllable cost; a well-resourced attacker (or an attacker exploiting a period of low anchor-registry activity) can create a large number of games in a short window. The scanner has no mechanism to cap or paginate the per-tick range independently of `game_count` growth, so likelihood scales directly with how cheaply an attacker can mint games relative to the anchor-advance rate.

### Recommendation
Bound the amount of work performed per scan tick, e.g., by capping the number of factory indices evaluated per tick (analogous to `ANCHOR_SEARCH_BATCH_SIZE` used for anchor lookup) and carrying over unfinished ranges across ticks, or by tracking a persisted high-water mark so a burst of newly created games cannot force a single tick to process an arbitrarily large backlog.

### Proof of Concept
1. Attacker repeatedly calls `DisputeGameFactory.create(...)` (paying the bond each time) to grow `game_count` by a large amount, e.g. tens of thousands of games, faster than the `AnchorStateRegistry` anchor advances.
2. On the next tick, `GameScanner::scan` computes `scan_start..game_count` spanning the attacker's entire backlog and issues `stream::iter(scan_start..game_count)` over `evaluate_game`, bounded only by `SCAN_CONCURRENCY = 32` in-flight requests at a time — see `crates/proof/challenge/src/scanner.rs:184-190`.
3. Scan duration grows linearly with the backlog size, delaying detection of any genuinely fraudulent game mixed into the flood until after its response window may have passed.

    pub async fn scan(&mut self) -> Result<Vec<CandidateGame>> {
        let game_count = self.factory_client.game_count().await?;

        if game_count == 0 {
            debug!("factory has no games");
            return Ok(vec![]);
        }

        let end = game_count - 1;
        let scan_start = self.scan_start_index(game_count).await;

        let games_to_scan = game_count.saturating_sub(scan_start);

        let scanner = &*self;
        let results: Vec<(u64, Result<Option<CandidateGame>>)> =
            stream::iter(scan_start..game_count)
                .map(|i| async move { (i, scanner.evaluate_game(i).await) })
                .buffer_unordered(Self::SCAN_CONCURRENCY)
                .collect()
                .await;
