## Title
Global unauthenticated requestID collision allows an attacker to block a targeted user's HTTP trigger execution - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The `httpTriggerHandler` in the gateway's HTTP Trigger v2 handler keys all in-flight callbacks by the client-supplied JSON-RPC `req.ID` in a single, handler-wide map, with no scoping to workflow, workflow owner, or authenticated caller. [1](#0-0)  A second request that reuses an ID already present in that map is rejected with a "conflict" error before authentication/authorization of the new request's workflow is even relevant to the rejection decision. [2](#0-1) 

### Finding Description
`HandleUserTriggerRequest` parses the request, validates the request ID (only checking it's non-empty and doesn't contain `/`) [3](#0-2) , resolves the workflow, authorizes the workflow-level key, checks rate limits, and only then calls `h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)` [4](#0-3) . The callback bookkeeping structure `callbacks map[string]savedCallback // requestID -> savedCallback` is a single global map on the handler, not partitioned per-workflow or per-caller. [5](#0-4) 

The existing test `TestHttpTriggerHandler_HandleUserTriggerRequest/"duplicate request ID"` confirms the behavior: a second request reusing an already in-flight `req.ID` fails with `"in-flight request"` and is answered with `jsonrpc.ErrConflict`, even though this is the intended idempotency/duplicate-suppression mechanism. [2](#0-1) 

Because the `id` field of a JSON-RPC request is fully attacker-controlled and there is no requirement that it be tied to the caller's identity, workflow, or an unpredictable/signed value scoped to a specific principal, any unauthenticated party who can reach the gateway's HTTP trigger endpoint can submit a request using a request ID that a victim is expected to use (e.g., a well-known, application-level, or predictable ID scheme used by a specific integration/dApp), occupying the slot in the global `callbacks` map for the duration of `MaxTriggerRequestDurationMs`/until cleanup. Any subsequent legitimate request from the actual owner using that same ID is rejected outright with a conflict error before it is dispatched to the DON, until the attacker's own request times out and is reaped. [6](#0-5) 

This is structurally analogous to the reported `addCandidate` issue: a hash/identifier-keyed resource ("candidate" in the report, "requestID → callback" here) is created on a first-come-first-served basis by any caller without ownership verification, and its mere presence blocks a different caller's later, legitimate attempt to use the same identifier.

### Impact Explanation
An attacker can perform a targeted denial-of-service against specific HTTP-triggered workflow executions by squatting on request IDs before the legitimate caller uses them, causing those calls to fail with a conflict error instead of executing the workflow. Depending on how integrators generate request IDs (e.g., deterministic IDs derived from order numbers, session IDs, or other predictable application data), this could be used to selectively block specific business transactions from reaching the DON. This is a griefing/availability issue rather than a fund-loss or authentication-bypass issue, since it does not grant access to other workflows' data or DON responses (the callback resolution is still gated separately by JWT-based workflow authorization).

### Likelihood Explanation
Exploitability depends on how request IDs are generated by legitimate callers and whether they are guessable ahead of time. Since request ID is a free-form client-supplied string with only two very weak constraints (non-empty, no `/`), and it is used unmodified as the map key, any caller with network access to the gateway's trigger endpoint can attempt this without needing to be a registered node, workflow owner, or authorized key holder — the collision check happens before/independent of workflow authorization. The likelihood of a successful targeted block depends on the attacker's ability to guess or observe the victim's chosen ID in advance.

### Recommendation
- Scope the in-flight callback map key by a composite of `(workflowID, requestID)` or `(authenticated caller/workflow owner, requestID)` rather than a raw global `requestID`, so that one workflow's/owner's callers cannot collide with another's.
- Consider deriving/validating request IDs using data anchored to the authenticated JWT (e.g., signed request ID or including the requester's public key/address as part of the dedup key) so squatting requires the same authorization required to actually trigger the workflow.
- Document that request IDs are not authenticated at admission time and should not be treated as capability tokens; recommend integrators use sufficiently high-entropy, unpredictable IDs.

### Proof of Concept
1. Determine (or predict) the `requestID` that a target integrator will use for `workflows.execute` calls against workflow `W` (e.g., from public documentation, a leaked support message, or from observing correlated on-chain/off-chain activity).
2. Before the victim's transaction, send an unauthenticated (or minimally authenticated, since only the target workflow's key matters after the map check occurs — but note the ID check happens on parse before workflow authorization completes in `HandleUserTriggerRequest`) trigger request to the gateway's HTTP trigger endpoint using that same `requestID`, targeting any workflow (attacker does not need to know the victim's authorization key to occupy the global map slot, only to pass basic request-shape validation up to `setupCallback`).
3. When the legitimate caller submits their real request with the same `requestID`, they receive `jsonrpc.ErrConflict` ("in-flight request") as shown by the existing test `TestHttpTriggerHandler_HandleUserTriggerRequest/"duplicate request ID"` [2](#0-1) , and their workflow execution is blocked until the attacker's occupying request is cleaned up by `reapExpiredCallbacks`. [6](#0-5) 

Note: I was unable to view the body of `setupCallback` itself (search for its definition did not return results within the available context/index), so the precise point at which workflow-authorization vs. ID-collision checks are ordered relative to map insertion could not be fully confirmed from source — this should be verified directly in `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go` before treating this as conclusively exploitable pre-authentication. If `setupCallback` performs the map-insert-and-check only after full JWT/workflow authorization succeeds (i.e., the attacker would need a valid authorized key for *some* workflow, not necessarily the victim's), the severity is lower (an authorized-but-malicious workflow user could block other unrelated executions with colliding IDs) but the core collision flaw (global keyspace, no cross-workflow isolation) still stands.

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func TestHttpTriggerHandler_ReapExpiredCallbacks(t *testing.T) {
	requestID := "test-request-id"
	triggerReq := gateway_common.HTTPTriggerRequest{
		Workflow: gateway_common.WorkflowSelector{
			WorkflowID: workflowID,
		},
		Input: []byte(`{"key": "value"}`),
	}
	reqBytes, err := json.Marshal(triggerReq)
	require.NoError(t, err)

	rawParams := json.RawMessage(reqBytes)
	req := &jsonrpc.Request[json.RawMessage]{
		Version: "2.0",
		ID:      requestID,
		Method:  gateway_common.MethodWorkflowExecute,
		Params:  &rawParams,
	}
	privateKey := createTestPrivateKey(t)
	cfg := ServiceConfig{
		CleanUpPeriodMs:             100,
		MaxTriggerRequestDurationMs: 50,
	}
	handler, mockDon := createTestTriggerHandlerWithConfig(t, cfg)
	registerWorkflow(t, handler, workflowID, privateKey)

	t.Run("reap expired callbacks", func(t *testing.T) {
		req.Auth = createTestJWTToken(t, req, privateKey)
		callback := hc.NewCallback()
		mockDon.EXPECT().SendToNode(mock.Anything, mock.Anything, mock.Anything).Return(nil).Times(3)
		err = handler.HandleUserTriggerRequest(t.Context(), req, callback, time.Now())
		require.NoError(t, err)

		// Manually set the callback's createdAt to the past to simulate expiration
		handler.callbacksMu.Lock()
		if cb, exists := handler.callbacks[requestID]; exists {
			cb.createdAt = time.Now().Add(-time.Duration(cfg.CleanUpPeriodMs+1) * time.Millisecond)
			handler.callbacks[requestID] = cb
		}
		handler.callbacksMu.Unlock()

		// Manually trigger reaping
		handler.reapExpiredCallbacks(t.Context())

		// Verify callback was removed
		handler.callbacksMu.Lock()
		_, exists := handler.callbacks[requestID]
		handler.callbacksMu.Unlock()
		require.False(t, exists)
	})
