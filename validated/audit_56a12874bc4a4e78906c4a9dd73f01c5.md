## Finding

The exploit path is real and confirmed by the code. `createDstEscrow` performs no validation of the `parameters` field beyond length/value checks — it only verifies `msg.value` matches the safety deposit + amount and that the cancellation timing is valid: [1](#0-0) 

The `protocolFeeRecipientCd()`/`integratorFeeRecipientCd()` addresses are decoded straight out of `immutables.parameters`, a byte blob supplied entirely by the caller of `createDstEscrow` (the taker/resolver), with no on-chain check that they match a canonical/whitelisted fee recipient: [2](#0-1) 

`EscrowDst._withdraw` performs the fee transfers to those attacker-supplied addresses *before* transferring to the maker, and since it's a single atomic function, a revert on either fee leg aborts the entire withdrawal, including the maker's payout and the safety-deposit refund: [3](#0-2) 

For the native-token fee/deposit path, `_ethTransfer` uses a raw `call` that reverts on failure, so a fee recipient with a reverting `receive()`/fallback will deterministically break every `withdraw`/`publicWithdraw` call: [4](#0-3) 

This is already validated by the test suite's existence of `NativeTokenSendingFailure` reverts on the withdrawal path when a recipient rejects native tokens: [5](#0-4) 

Impact: because `EscrowDst.cancel()` bypasses fee transfers entirely and sends the full amount back to the taker (not the maker), a malicious taker can (1) fund a dst escrow with a poisoned fee recipient, (2) let the maker/relayer submit the secret in a `withdraw`/`publicWithdraw` call that reverts (the secret nonetheless becomes visible in the failed transaction's calldata), (3) use the now-exposed secret to withdraw the maker's funds from `EscrowSrc`, and (4) later call `cancel()` on the dst escrow to reclaim their own deposit plus the safety deposit — leaving the maker with nothing on the destination side while losing their source funds. This breaks the atomic-swap invariant and results in outright theft of maker funds, not merely a griefing/self-DoS, because the taker who controls the poisoned parameters is a different, adversarial party from the maker whose funds are frozen/stolen.

This matches the Critical bounty class (theft of user funds / permanent freezing caused by production contract logic), entered purely through the unprivileged `createDstEscrow` → `withdraw`/`publicWithdraw`/`cancel` lifecycle, with no admin/governance/privileged-resolver assumption required — any taker who wins order fills can mount this.

### Title
Attacker-controlled fee recipient in `EscrowDst._withdraw` permanently DoSes withdrawal and enables secret-extraction theft of maker funds - (File: contracts/EscrowDst.sol)

### Summary
`createDstEscrow` accepts `immutables.parameters` (encoding `protocolFeeRecipient`/`integratorFeeRecipient`) unchecked from the taker. `EscrowDst._withdraw` unconditionally transfers fees to these addresses before paying the maker, in a single atomic call. A taker can set a reverting recipient (or reverting native-token receiver) to make every `withdraw`/`publicWithdraw` call revert, while `cancel()` (which skips fee legs) still lets the taker reclaim their own deposit after the timelock.

### Impact Explanation
Permanent freezing of the maker's destination funds and safety deposit; combined with secret exposure in reverted-transaction calldata, this allows a malicious taker to steal the maker's source-chain funds via `EscrowSrc.withdraw` while still recovering their own destination deposit via `cancel()`. This is Critical (direct fund theft / permanent freeze) under the bounty gate.

### Likelihood Explanation
High. No privilege is required — any taker calling `createDstEscrow` fully controls the fee-recipient fields, and the revert is deterministic and repeatable for every subsequent withdrawal attempt.

### Recommendation
Validate/whitelist `protocolFeeRecipient`/`integratorFeeRecipient` at `createDstEscrow` time (or bind them to canonical factory-configured addresses as is presumably done in the src `postInteraction` path), and/or make fee transfers non-blocking (e.g., wrap in try/catch or use a pull-payment pattern) so a failing fee leg cannot block the maker's principal transfer.

### Proof of Concept
1. Attacker (taker) deploys a `RevertingReceiver` contract with a `receive()`/fallback that always reverts.
2. Taker calls `createDstEscrow` with `immutables.parameters` encoding `integratorFeeRecipient = RevertingReceiver`, `integratorFeeAmount > 0`, native `token = address(0)`.
3. After `DstWithdrawal` timelock, taker (or anyone with access token) calls `withdraw(secret, immutables)`.
4. `_withdraw` reaches `_uniTransfer(token, integratorFeeRecipientCd, integratorFeeAmount)` → `_ethTransfer` → `call` fails → `NativeTokenSendingFailure()` reverts the entire transaction, per [6](#0-5)  and [7](#0-6) .
5. The revealed `secret` is visible in the failed transaction's calldata; attacker submits it to `EscrowSrc.withdraw` to claim the maker's source funds.
6. After `DstCancellation`, taker calls `cancel()` on the dst escrow, which reaches `_uniTransfer(token, taker, amount)` with no fee leg and succeeds, letting the taker reclaim the deposit and safety deposit, per [8](#0-7) .

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

        internal

        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }

    function _uniTransfer(address token, address to, uint256 amount) internal {
        if (token == address(0)) {
            _ethTransfer(to, amount);
        } else {
            IERC20(token).safeTransfer(to, amount);
        }
    }

    /**
     * @dev Transfers native tokens to the recipient.

    function _ethTransfer(address to, uint256 amount) internal {
        (bool success,) = to.call{ value: amount }("");
        if (!success) revert NativeTokenSendingFailure();
    }
