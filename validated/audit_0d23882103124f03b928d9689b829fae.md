### Title
Revoked LDAP user's session/API token remains valid until background sync purges it, not on next request - ([File: core/sessions/ldapauth/sync.go])

### Summary
`AuthorizedUserWithSession` and `FindUserByAPIToken` in `core/sessions/ldapauth/ldap.go` validate a request purely against the locally cached `ldap_sessions`/`ldap_user_api_tokens` tables (checking only that the row exists and hasn't exceeded `SessionTimeout`/`UserAPITokenDuration`), with no live upstream LDAP group check on the request path. [1](#0-0) [2](#0-1)  Role/membership revocation is only reflected in the local cache by `LDAPServerStateSyncer.Work`, which purges/updates rows for users no longer present in the upstream group query, and `Work` only runs on the configured `UpstreamSyncInterval`/rate-limit ticker (or once at startup) — never on a per-request basis. [3](#0-2) [4](#0-3)  `deleteStaleSessions`/`deleteStaleAPITokens` (invoked from `Work`) purge only rows older than the session/token duration threshold — they have no relation to LDAP-group revocation and do not re-validate roles against upstream state. [5](#0-4) 

### Finding Description
The package-level doc comment in `ldap.go` claims "This sync happens for every auth endpoint hit, and via the defined sync interval," but this is not implemented: neither `AuthorizedUserWithSession` nor `FindUserByAPIToken` calls into `LDAPServerStateSyncer.Work` or performs any live upstream LDAP query for role verification. [6](#0-5) [7](#0-6) 

Concretely:
- `AuthorizedUserWithSession` selects `user_email, user_role, created_at + $2 >= now() as valid FROM ldap_sessions WHERE id = $1` and returns the cached role as long as the session has not timed out — it never checks whether the user is still a member of the LDAP group that granted that role. [8](#0-7) 
- `FindUserByAPIToken` behaves identically for `ldap_user_api_tokens`. [2](#0-1) 
- The only mechanism that removes/downgrades a revoked user's session or token is `LDAPServerStateSyncer.Work`, which queries the upstream LDAP groups, builds `upstreamUserStateMap`, and deletes/updates `ldap_sessions`/`ldap_user_api_tokens` rows for users no longer matching. [9](#0-8) 
- `Work` is driven only by a ticker on `UpstreamSyncInterval` (or a single run at `Start` if the interval is unset/instant) and is additionally throttled by `UpstreamSyncRateLimit`. [10](#0-9) [11](#0-10) 

Attacker flow: a user holding a valid session/API token created while a member of a privileged (or even 'view'-adjacent) LDAP group is removed from that group upstream (revocation). Because the per-request auth path (`AuthenticateBySession`/`AuthenticateByToken` → `AuthorizedUserWithSession`/`FindUserByAPIToken`) trusts the locally cached `user_role` column until the next sync tick, the attacker's old session/token continues to authenticate with the stale (now-revoked) role for any authenticated `/v2` route gated only by that role check (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole` in `core/web/auth/auth.go`). [12](#0-11)  No middleware or presenter layer independently re-checks upstream membership on the request path.

### Impact Explanation
This allows a de-provisioned/demoted user to retain their pre-revocation privilege level for an unbounded window bounded only by `UpstreamSyncInterval`/`UpstreamSyncRateLimit` (which could be configured to hours) or until the session naturally times out via `SessionTimeout`/`UserAPITokenDuration`, whichever is longer. If the revoked user previously held Admin/Edit/Run role, this maps to unauthorized privileged actions (key export, unauthorized transaction submission, job creation) after their access was supposed to be cut off — matching a "node takeover via stale-privilege session" class of impact. Note the question's framing that a "view"-only attacker escalates via this exact bug is not directly supported: `deleteStaleSessions` only purges by age, and the role stored for a view-only user does not change without an actual upstream role change; the real exploitable scenario is a user whose *role* was revoked/downgraded but whose cached session still reflects the old (higher) role until sync runs.

### Likelihood Explanation
Precondition is that the operator has configured LDAP auth with a non-instant `UpstreamSyncInterval` (a supported and likely common configuration, since instant sync is only used as a fallback single run at boot) and that a user's group membership is revoked or downgraded while they hold an active session or API token. No special exploitation techniques are needed beyond continuing to reuse the existing valid session cookie or API token — this is fully reachable by any authenticated user and is deterministic/repeatable across the revocation event window.

### Recommendation
Re-validate the user's LDAP group membership/role against the upstream server (or at minimum re-check against the latest synced state) on every authenticated request, or shorten/eliminate the trust window by having `AuthorizedUserWithSession`/`FindUserByAPIToken` trigger the sync (or a lightweight per-user LDAP check) before returning cached role data, per the intent documented in the `ldapauth` package comment. Alternatively, provide an explicit "force-sync on revoke" webhook/trigger and drastically reduce the default `UpstreamSyncInterval`, and update the misleading doc comment.

### Proof of Concept
Go integration test plan (in `core/sessions/ldapauth`):
1. Set up a test DB and `ldapAuthenticator`/`LDAPServerStateSyncer` with a mock `LDAPClient` returning a user in the Admin group.
2. Call `CreateSession` (or manually insert into `ldap_sessions`) for `user@example.com` with role `UserRoleAdmin`.
3. Assert `AuthorizedUserWithSession(ctx, sessionID)` returns role `UserRoleAdmin`.
4. Reconfigure the mock LDAP client to no longer return the user in any group (simulating revocation), but do NOT call `syncer.Work(ctx)`.
5. Call `AuthorizedUserWithSession(ctx, sessionID)` again immediately (simulating the "next request") and assert it still returns `UserRoleAdmin` (demonstrating the vulnerability — expected/desired behavior would be immediate rejection or role downgrade).
6. Call `syncer.Work(ctx)` and re-call `AuthorizedUserWithSession`; assert it now returns `sessions.ErrUserSessionExpired` (session purged), confirming revocation only takes effect after sync.
7. Handler-level variant: wrap with `auth.Authenticate`/`RequiresAdminRole` middleware and hit an admin-only `/v2` route with the stale session cookie between steps 4 and 6, asserting the request still succeeds (200/403-not-triggered) instead of being rejected.

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}
	if !foundUserToken.Valid { // API Token expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
			l.lggr.Errorf("error purging stale ldap API token session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	return sessions.User{
		Email: foundUserToken.UserEmail,
		Role:  foundUserToken.UserRole,
	}, nil
}

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired, and update session's LastUsed field. The state of the upstream LDAP server
// is polled and synced at the defined interval via a SleeperTask
func (l *ldapAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (sessions.User, error) {
	if len(sessionID) == 0 {
		return sessions.User{}, errors.New("session ID cannot be empty")
	}
	// Query the ldap_sessions table for given session ID, user role and email are cached so
	// no further upstream LDAP query is performed
	var foundSession struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	if err := l.ds.GetContext(ctx, &foundSession,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_sessions WHERE id = $1",
		sessionID, l.config.SessionTimeout().Duration(),
	); err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	if !foundSession.Valid {
		// Sessions expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_sessions WHERE id = $1", sessionID); execErr != nil {
			l.lggr.Errorf("error purging stale ldap session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	return sessions.User{
		Email: foundSession.UserEmail,
		Role:  foundSession.UserRole,
	}, nil
}

	// If enabled, start a background task that calls the Sync/Work function on an
	// interval without needing an auth event to trigger it
	// Use IsInstant to check 0 value to omit functionality.
	if !l.config.UpstreamSyncInterval().IsInstant() {

		go l.run()

		l.Work(ctx)
	}
	return nil

func (l *LDAPServerStateSyncer) run() {
	defer close(l.done)
	ctx, cancel := l.stopCh.NewCtx()
	defer cancel()
	ticker := time.NewTicker(l.config.UpstreamSyncInterval().Duration())
	defer ticker.Stop()

	for {
		select {
		case <-ctx.Done():
			return
		case <-ticker.C:
			l.Work(ctx)
		}
	}
}

func (l *LDAPServerStateSyncer) Work(ctx context.Context) {
	// Purge expired ldap_sessions and ldap_user_api_tokens
	recordCreationStaleThreshold := l.config.SessionTimeout().Before(time.Now())
	err := l.deleteStaleSessions(ctx, recordCreationStaleThreshold)
	if err != nil {
		l.lggr.Error("unable to expire local LDAP sessions: ", err)
	}
	recordCreationStaleThreshold = l.config.UserAPITokenDuration().Before(time.Now())
	err = l.deleteStaleAPITokens(ctx, recordCreationStaleThreshold)
	if err != nil {
		l.lggr.Error("unable to expire user API tokens: ", err)
	}

	// Optional rate limiting check to limit the amount of upstream LDAP server queries performed
	if !l.config.UpstreamSyncRateLimit().IsInstant() {
		if !time.Now().After(l.nextSyncTime) {
			return
		}

		// Enough time has elapsed to sync again, store the time for when next sync is allowed and begin sync
		l.nextSyncTime = time.Now().Add(l.config.UpstreamSyncRateLimit().Duration())
	}

	l.lggr.Info("Begin Upstream LDAP provider state sync after checking time against config UpstreamSyncInterval and UpstreamSyncRateLimit")
