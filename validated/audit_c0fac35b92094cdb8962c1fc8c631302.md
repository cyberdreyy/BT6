### Title
Uncollateralized Gwei minted for builder withdrawals — committed `Withdrawal.amount` is not capped to `builder.balance` in `get_builder_withdrawals`, while `apply_withdrawals` only debits the capped amount - (File: `specs/gloas/beacon-chain.md`)

### Summary
In the Gloas (EIP-7732) withdrawal-sweep logic, the amount that gets committed to the execution layer for a builder's pending withdrawal (`get_builder_withdrawals`) is the raw, unvalidated `amount` field stored in the queue entry, with no check against the builder's current balance and no tracking of cumulative draws across multiple queued entries for the same builder. The corresponding balance deduction (`apply_withdrawals`) is capped with `min(withdrawal.amount, builder_balance)`. Because the *committed* withdrawal (which the execution layer will unconditionally credit to `fee_recipient`, exactly like any other consensus-layer withdrawal) can exceed what is actually collateralized in `state.builders[].balance`, more Gwei can be minted on the execution side than is deducted on the consensus side — an unbacked-supply / accounting-mismatch bug conceptually identical to the reported `burnFrom`/`totalSupply` divergence (an accounting field silently diverges from the externally observable effect).

### Finding Description
`get_builder_withdrawals` builds each `Withdrawal` directly from the queued `builder_pending_withdrawals` entry without ever comparing `withdrawal.amount` to `state.builders[builder_index].balance`, and without decrementing a running/simulated balance as it processes multiple entries for the same builder in one call: [1](#0-0) 

Compare this to the sibling function `get_builders_sweep_withdrawals`, which correctly bounds the amount to the live balance (`amount=builder.balance`): [2](#0-1) 

The actual balance deduction, `apply_withdrawals`, only ever removes `min(withdrawal.amount, builder_balance)` from `state.builders[builder_index].balance`: [3](#0-2) 

Both `get_builder_withdrawals` and `apply_withdrawals` are called from the same `process_withdrawals` within the same slot, using the same `expected.withdrawals` list, so the mismatch is between the amount *committed in the block* (the `Withdrawal` objects, which the block's `payload_expected_withdrawals`/withdrawals-root commits the execution layer to honor) and the amount actually *debited from consensus state*: [4](#0-3) 

Concretely: if `state.builder_pending_withdrawals` contains two entries for the same `builder_index` each requesting `X` Gwei, and `builder.balance == 1.25*X` (i.e., enough to satisfy one request but not two), `get_builder_withdrawals` will emit two `Withdrawal` objects each with `amount = X` (total committed = `2X`) because it never checks balance sufficiency and never subtracts what a prior withdrawal in the same batch already "used". `apply_withdrawals` will then deduct `min(X, 1.25X) = X` for the first, leaving balance `0.25X`, then `min(X, 0.25X) = 0.25X` for the second — total actually debited is only `1.25X`, even though the committed withdrawals (which the execution layer mints unconditionally to `fee_recipient`, mirroring how ordinary validator withdrawals work) total `2X`. The difference, `0.75X` Gwei, is minted on the execution layer with no corresponding consensus-layer backing — Gwei created from nothing and paid to whatever `fee_recipient` addresses were specified in the pending-withdrawal entries.

This is the direct analog of the reported `FERC20.burnFrom` bug: an accounting ledger (`builder.balance`, analogous to `_totalSupply`) is decremented conservatively/capped, while the externally-visible effect (the committed `Withdrawal.amount`, analogous to the `Transfer` event) reflects the uncapped, larger value — breaking the invariant that "Gwei debited on L1 consensus == Gwei credited on the execution layer."

### Impact Explanation
This breaks the core Gwei-conservation equality of the protocol: total Gwei removed from `state.builders[*].balance` must equal total Gwei credited via committed withdrawals on the execution layer. A spec-following block builder/proposer can construct (or simply encounter, if two pending withdrawal requests for the same builder accumulate before the balance can cover both) a state where the committed withdrawals exceed the builder's real balance, causing the execution layer to mint Gwei that has no consensus-layer backing, paid to an address of the requester's choosing (`fee_recipient`). This matches the "Critical" impact bucket: Gwei created and paid to a non-owner, via a payload that is executed exactly as the block committed but which the consensus state does not actually back.

### Likelihood Explanation
Reachability requires only that `state.builder_pending_withdrawals` contain more than one entry for the same builder whose combined requested amounts exceed that builder's balance at processing time — a state reachable through normal builder payment/withdrawal flows without needing a malicious peer, coalition, or client bug (this is a pure spec-level bookkeeping gap in `get_builder_withdrawals`, not an implementation bug). No special stake or validator privilege is required beyond being (or controlling) a registered builder with queued pending withdrawals.

### Recommendation
`get_builder_withdrawals` should track a running/simulated remaining balance per builder as it iterates `state.builder_pending_withdrawals` (mirroring what `apply_withdrawals` actually does), and cap each emitted `Withdrawal.amount` to `min(withdrawal.amount, remaining_balance)` — consistent with how `get_builders_sweep_withdrawals` already caps to `builder.balance`. This ensures the amount committed to the execution layer always equals the amount that `apply_withdrawals` will actually be able to deduct.

### Proof of Concept
Given `state.builders[i].balance = 1.25 * X` and `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=i, amount=X, fee_recipient=A), BuilderPendingWithdrawal(builder_index=i, amount=X, fee_recipient=B)]`:

1. `get_expected_withdrawals(state)` → `get_builder_withdrawals` emits `Withdrawal(validator_index=convert(i), amount=X, address=A)` and `Withdrawal(validator_index=convert(i), amount=X, address=B)` — total committed `2X`, per [5](#0-4) .
2. These are embedded in `state.payload_expected_withdrawals` and thus in the block's withdrawals commitment, which the execution layer is required to honor by crediting `A` and `B` each `X` Gwei — total `2X` minted.
3. `apply_withdrawals(state, expected.withdrawals)` runs: first withdrawal deducts `min(X, 1.25X) = X`, leaving builder balance `0.25X`; second withdrawal deducts `min(X, 0.25X) = 0.25X`, leaving balance `0` — total actually debited `1.25X`, per [6](#0-5) .
4. Net result: `0.75X` Gwei credited on the execution layer to `A`/`B` with no corresponding consensus-layer debit — an unbacked, permanent Gwei mint.

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
