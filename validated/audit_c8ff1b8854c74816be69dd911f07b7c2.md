Let me look closer at the claim paths and epoch transitions in `IdleCreditVault.sol`.### Title
Claimed instant-withdraw receipts leave stale per-epoch basis, inflating default recovery and underflowing later claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays a funded instant-withdraw receipt and zeroes the aggregate `instantWithdrawsRequests[_user]`, but it never clears the per-epoch bookkeeping `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. A lender who claims a funded instant withdrawal and then re-requests inside the same epoch silently double-counts the epoch claim basis. If that epoch subsequently defaults, the phantom basis both dilutes `defaultRecoveryPrice` for all honest claimers and makes `_claimDefaultedInstantWithdrawRequest` revert on arithmetic underflow, freezing the user's and the reserve's accounting. This is the idle-tranches analog of the TickLogic bug class: per-cycle claim accounting that is not reset on exit corrupts subsequent-cycle claims.

### Finding Description
Three pieces of per-epoch bookkeeping are written in `requestInstantWithdraw` but are only ever cleared in the *defaulted* claim path:

- `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` at `contracts/strategies/idle/IdleCreditVault.sol:371-372`.
- The funded claim path `claimInstantWithdrawRequest` at `contracts/strategies/idle/IdleCreditVault.sol:380-393` only resets `instantWithdrawsRequests[_user] = 0` and burns the aggregate receipt; it does **not** decrement `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch`.
- The same asymmetry exists for normal requests: `_claimFundedWithdrawRequest` sets `withdrawsRequests[_user] = 0` at line 344 but leaves `withdrawsRequestsByEpoch[_user][epoch]` untouched. (For normal requests the stale key cannot be revisited while the pool is running because `epochNumber` is monotonic and the `epochNumber <= lastWithdrawRequest` gate at line 326 forces a wait; the instant path has no epoch gate, so the same-epoch re-request is reachable.)

Attack sequence inside one running epoch `E` (instant-withdraw mode enabled):

1. User calls `requestInstantWithdraw(A)` → `instantWithdrawsRequestsByEpoch[user][E] = A`, `instantWithdrawClaimsByEpoch[E] = A`, `pendingInstantWithdraws += A`.
2. Epoch-start funding moves `A` via `collectInstantWithdrawFunds` → `pendingInstantWithdraws` back to 0.
3. User calls `claimInstantWithdrawRequest` → receives `A`, aggregate zeroed, but both per-epoch mappings still hold `A`.
4. User calls `requestInstantWithdraw(B)` → `instantWithdrawsRequestsByEpoch[user][E] = A+B`, `instantWithdrawClaimsByEpoch[E] = A+B`, `pendingInstantWithdraws = B`.
5. Borrower fails to repay epoch `E`; manager finalizes via `finalizeDefaultRecovery`.

At finalization (`contracts/strategies/idle/IdleCreditVault.sol:644-723`):

- `defaultPendingClaimBasis` returns `pendingWithdraws + instantWithdrawClaimsByEpoch[E]` = real basis + phantom `A`, so `defaultRecoveryPrice = reserveAmount / totalBasis` is diluted by `A` that was already paid out.
- `_defaultPrefundedInstantReserve` computes `instantBasis (A+B) - pendingInstant (B) = A` and adds `A` to `reserveAmount` as if that underlying were still held by the strategy — it is not, it was paid to the user in step 3. `defaultRecoveryReserve` is therefore overstated by `A` relative to the actual token balance pulled in via `safeTransferFrom(_recoverySource, ...)`.

At claim time, `_claimDefaultedInstantWithdrawRequest` (`contracts/strategies/idle/IdleCreditVault.sol:842-856`) computes `claimBasis = instantWithdrawsRequestsByEpoch[user][E] = A+B`, then executes `instantWithdrawsRequests[_user] -= claimBasis` where the aggregate is only `B` → arithmetic underflow revert. Because this runs at the top of `claimInstantWithdrawRequest` whenever `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, the user's `B` receipt is permanently unclaimable. Independently, the overstated `defaultRecoveryReserve` means the last honest defaulted-epoch claimer(s) will hit an underflow/transfer failure in `_transferDefaultRecovery` for up to `A` underlying.

### Impact Explanation
Two quantified harms, both bounded by the phantom amount `A` (the attacker's already-paid instant withdrawal):

- Recovery dilution: `defaultRecoveryPrice` is divided by a `totalBasis` inflated by `A`, so every honest defaulted-epoch claimer (normal, APR0, and instant receipts) receives less than the true recovery ratio — a direct loss of recovered funds proportional to `A/totalBasis`.
- Reserve insolvency / permanent freeze: `defaultRecoveryReserve` counts `A` tokens that were already paid out, so the last defaulted claims totaling up to `A` cannot be paid, and the attacker's own `B` receipt permanently reverts on underflow in `instantWithdrawsRequests[_user] -= claimBasis`.

The attacker is an ordinary KYC-passed lender; every step (request, claim, re-request) is unprivileged. The broken invariant is "one receipt, one payout": paid receipts continue to occupy claim basis. No existing guard prevents it — `requestInstantWithdraw` has no equivalent of the `lossRecoveryPriceByEpoch`/`lastWithdrawRequest` guard that `requestWithdraw` carries at lines 263-271, and `_ensureDefaultRecoveryInitialized` does not reconcile stale per-epoch entries.

### Likelihood Explanation
Requires (a) instant-withdraw mode enabled (`allowInstantWithdraw`), (b) the request → fund → claim → re-request sequence inside one epoch number, and (c) that epoch ending in a finalized default. (b) is feasible when `instantDelay` permits a claim and a second request while the epoch is running; the per-epoch mappings are keyed by `epochNumber`, which does not change during the epoch, so no timing luck is needed beyond the default itself. (c) is a normal protocol event handled by honest manager/borrower calls — the bug is in the accounting, not in forcing the default. The normal-request variant (`withdrawsRequestsByEpoch`) is latent rather than currently triggerable, since epoch keys cannot be revisited outside the closed-pool path where loss/default accounting does not run.

### Recommendation
- In `claimInstantWithdrawRequest`, clear the requester's per-epoch basis alongside the aggregate: decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` for the epoch(s) being paid, symmetric to how `_clearWithdrawClaimForEpoch` handles normal receipts.
- Symmetrically, clear `withdrawsRequestsByEpoch[_user][*]` inside `_claimFundedWithdrawRequest` (or at claim time recompute the aggregate strictly from per-epoch entries) so funded claims cannot leave phantom basis for any future epoch-keyed accounting.
- Add a property test: after any successful funded claim, all per-epoch claim basis for that user must be zero; sum over `instantWithdrawClaimsByEpoch` must equal the sum of unclaimed per-user per-epoch receipts.

### Proof of Concept
Foundry-style sketch against the existing `IdleCreditVault.t.sol` harness (instant-withdraw setup as in `testClaimInstantWithdrawRequest`):

```solidity
// epoch E running, instant withdraws enabled (instantDelay large enough for claim + re-request)
uint256 A = 1_000e6;
uint256 B = 500e6;

// attacker = KYC'd AA holder
uint256 trA = _depositWithUser(attacker, A + B);

// step 1: request instant withdraw A
_requestInstantWithdraw(attacker, trA / 2); // amount A of strategy tokens

// step 2: epoch starts, borrower funds instant queue (collectInstantWithdrawFunds)
cdoEpoch.startEpoch(); // pulls pendingInstantWithdraws funding

// step 3: attacker claims funded A
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
assertEq(strategy.instantWithdrawsRequests(attacker), 0);
// stale basis remains:
assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, E), A);
assertEq(strategy.instantWithdrawClaimsByEpoch(E), A);

// step 4: attacker re-requests B in the same epoch E
_requestInstantWithdraw(attacker, B);
assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, E), A + B);

// step 5: borrower defaults; manager finalizes recovery
_handleBorrowerDefaultAndFinalize();

// impact 1: recovery price diluted by phantom A
// defaultPendingClaimBasis() counted A+B instead of B
// _defaultPrefundedInstantReserve() counted A as held reserve

// impact 2: attacker claim underflows; honest last claimer underpaid by ~A
vm.expectRevert(); // instantWithdrawsRequests[attacker] -= A+B with only B present
cdoEpoch.claimInstantWithdrawRequest();
```

Uncertainty to verify in the PoC: whether `instantDelay`/`getInstantWithdrawFunds` timing permits both a funded claim and a second `requestInstantWithdraw` under the same `epochNumber` (the mappings key on `epochNumber`, which is unchanged between `startEpoch` and `stopEpoch`, so same-epoch re-request is the only requirement), and the exact funding path used for the first instant claim in this variant. If the deployment never enables instant withdrawals, the residual issue is the latent `withdrawsRequestsByEpoch` staleness, which currently has no reachable epoch-key collision.
