### Title
Permissionless, front-runnable initialization of the global `FeeState`/`FeeStateV2` singleton allows an attacker to claim global fee-admin authority and redirect protocol fees - ([File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs])

### Summary
The reported issue concerns "implementation" contracts whose `initialize`/`init` functions are left unprotected, letting any actor call them first and claim control (classic uninitialized-proxy phishing risk). The marginfi program does not use a Solidity proxy pattern, but it has a structurally identical analog: the program-wide singleton `FeeState` (and its `FeeStateV2` counterpart) PDA is created via `init_global_fee_state`, an instruction with **no caller/admin restriction**. Whoever submits the transaction first becomes the permanent `global_fee_admin` and sets the `global_fee_wallet`, exactly as an attacker could "claim" an uninitialized implementation contract.

### Finding Description
`init_global_fee_state` is documented as "Runs once per program to init the global fee state" [1](#0-0)  and its `Accounts` struct only requires an arbitrary `payer: Signer`, with the `fee_state` PDA derived from a fixed, group-independent seed (`FEE_STATE_SEED`) and `init` constraint: [2](#0-1) . Critically, the `admin_key` and `fee_wallet` values stored into the account are passed in as **plain instruction arguments controlled entirely by the caller**, not derived from any privileged signer or hardcoded deployer key: [3](#0-2) . The public `lib.rs` entrypoint exposes this the same way, with only a comment noting it "Runs once per program": [4](#0-3) . The same pattern is repeated for the newer `init_global_fee_state_v2` / `InitFeeStateV2` singleton, also gated by nothing but a generic `payer: Signer`: [5](#0-4) .

Because Anchor's `init` constraint simply fails if the PDA already exists, this is a strict "first caller wins" race — functionally identical to an unprotected `initialize()`/`init()` on a proxy implementation that anyone can call before the legitimate deployer does.

### Impact Explanation
Whoever wins the race to call `init_global_fee_state` becomes the permanent `global_fee_admin` and sets `global_fee_wallet` to an address of their choosing. The fee-state cache populated here is later copied into every `MarginfiGroup` at group-creation time [6](#0-5) , meaning the attacker-controlled `global_fee_wallet` becomes the destination for protocol-wide fees (bank init fees, liquidation fees, order fees, program fee rate) across the entire deployment. Since `global_fee_admin` is also the authority checked by fee-editing instructions (`edit_global_fee_state`/`config_group_fee`), the attacker additionally gains the ability to change fee parameters and wallet destinations going forward, a durable, protocol-wide privilege escalation and value-redirection with direct financial effect (protocol fee revenue is diverted to the attacker), plus loss of protocol control that is not recoverable without a governance/redeploy action.

### Likelihood Explanation
Likelihood is tied entirely to deployment ordering/timing: the instruction is permissionless and unauthenticated by design intent ("payer" is not checked against any known deployer key), so any actor observing the mempool/deployment transaction for a new marginfi deployment (or any deployment that has not yet executed this one-time setup instruction) can front-run it. This is a realistic race-condition/front-running scenario on public networks and matches the report's core concern: an unprotected, callable-by-anyone initializer for a critical singleton.

### Recommendation
Restrict `init_global_fee_state` / `init_global_fee_state_v2` to a hardcoded/known deployer key (e.g., require `payer` to equal the program's upgrade authority, or gate the instruction behind a constant "genesis admin" pubkey compiled into the program), analogous to "petrifying" the implementation. At minimum, verify the `admin_key` argument matches an expected value rather than accepting an arbitrary attacker-supplied pubkey, and consider deploying/initializing the fee state within the same atomic transaction as program deployment/upgrade to close the front-running window.

### Proof of Concept
1. Deploy (or observe an about-to-be-configured) marginfi program instance where `FeeState` (seed `FEE_STATE_SEED`) has not yet been created.
2. Before the legitimate operator's setup transaction lands, an attacker submits their own `init_global_fee_state` (or `init_global_fee_state_v2`) transaction with `payer = attacker`, `admin_key = attacker_pubkey`, `fee_wallet = attacker_wallet`, using the same well-known PDA seeds [7](#0-6) .
3. Anchor's `init` constraint succeeds for whichever transaction lands first; the legitimate operator's subsequent identical transaction fails with "account already in use."
4. All subsequently created `MarginfiGroup`s inherit the attacker's `fee_wallet`/fee configuration via `fee_state_cache` at group-init time [6](#0-5) , and the attacker retains standing authority as `global_fee_admin` to edit fees thereafter.
