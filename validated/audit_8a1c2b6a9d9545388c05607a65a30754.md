### Title
Permissionless `set_allow_direct_coin_transfers(false)` lets any staker/shareholder permanently DoS `staking_contract::distribute` and `vesting::distribute`, freezing all co-shareholders' unlocked stake, commission, and vested funds - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::distribute_internal` and `vesting::distribute` both withdraw all currently-unlocked stake for a pool in one atomic transaction and then loop over every shareholder in the internal `pool_u64`/distribution pool, paying each one via `aptos_account::deposit_coins`. [1](#0-0) 
`aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient has not registered the `CoinStore<AptosCoin>` for their account and has explicitly disabled direct coin transfers. [2](#0-1) 
Any account can permissionlessly disable this via `aptos_account::set_allow_direct_coin_transfers(account, false)`. [3](#0-2) 
Because the distribution loop is a single atomic Move transaction over *all* shareholders in the pool, one unprivileged shareholder poisoning their own receiving state causes the whole `distribute()` call to abort every time, permanently blocking payout to every other staker/operator sharing that same stake pool - this is the direct analog of the LooksRare report's unchecked-`call` pattern, except here the "trapped ETH" becomes permanently, not just transiently, stuck because the poisoning condition is self-inflicted and persists across every retry.

### Finding Description
`staking_contract::distribute_internal` withdraws `total_potential_withdrawable` (inactive + pending_inactive) stake in one shot, then iterates the `distribution_pool`'s shareholders in a `while` loop, calling `aptos_account::deposit_coins` for each recipient: [1](#0-0) 

`vesting::distribute` follows the identical pattern for its `grant_pool` shareholders (confirmed by the surrounding withdraw/loop/emit structure in the same function region), calling the same `aptos_account::deposit_coins` primitive for each shareholder before emitting a `Distribute` event. [4](#0-3) 

`aptos_account::deposit_coins` will only auto-register a `CoinStore` for the recipient (bypassing the abort) if `can_receive_direct_coin_transfers` returns true; if the account has explicitly opted out via `DirectTransferConfig.allow_arbitrary_coin_transfers = false` and has not separately registered the coin, the call aborts: [2](#0-1) 

`set_allow_direct_coin_transfers` is a fully public, unprivileged entry function that any account (including any staker, delegator, or vesting shareholder) can call on themselves at any time: [3](#0-2) 

Move transactions are atomic - an abort mid-loop reverts the entire `distribute()` call, including the `stake::withdraw_with_cap` that already pulled coins out of the underlying stake pool and any `redeem_shares` state changes attempted before the abort. Since `distribute()` (and the internal `distribute_internal` that `request_commission`, `unlock_stake`, `switch_operator`, `update_commision`, and `terminate_vesting_contract`/`admin_withdraw` all call first to flush pending distributions) is a single all-or-nothing operation across every shareholder of the pool, a single account intentionally poisoning its own receive-path makes the aggregate distribution function permanently un-callable for that stake pool or vesting contract - unlike the LooksRare bug where the dust simply sits trapped until the next successful call, here *no* call can ever succeed again once one shareholder is poisoned, so every other staker/operator's already-unlocked/withdrawable stake, commission, and vested funds become permanently unreachable.

### Impact Explanation
This breaks the "Unlock, reactivate, withdraw, synchronize" invariant that these paths must not strand value permanently. A single unprivileged staking-contract shareholder (or vesting-contract shareholder) can, at zero cost besides one `set_allow_direct_coin_transfers(false)` call executed before receiving any stake shares, prevent themselves *and every co-shareholder/operator of the same pool* from ever withdrawing unlocked stake, rewards, or operator commission again via `distribute()`. Because `distribute_internal`/`vesting::distribute` are also invoked internally by `request_commission`, `unlock_stake`, `update_commision`, `switch_operator`, and `terminate_vesting_contract`/`admin_withdraw`, this cascades to block those functions as well whenever they attempt to flush pending distributions first. This is a permanent, non-recoverable loss of claim/withdrawal rights for value that is not owned by the attacker (operator's commission, other stakers'/shareholders' unlocked principal and rewards), qualifying as High/Critical under the "permanent lock or non-recoverable loss of claim rights" impact category.

### Likelihood Explanation
Likelihood is high: `set_allow_direct_coin_transfers` is a completely permissionless, self-service function requiring no special role, and any staker in `staking_contract` (via `create_staking_contract`) or any shareholder added to a `vesting::create_vesting_contract` can trigger the vulnerable state on their own account before commission/rewards ever get distributed, or even opportunistically right before a scheduled `distribute()` call, e.g. out of malice toward co-stakers or the operator, or to hold funds hostage.

### Recommendation
- In `distribute_internal` (staking_contract.move) and `distribute` (vesting.move), do not let a single recipient's deposit failure abort the whole distribution: wrap each `aptos_account::deposit_coins` call so failures for one shareholder do not revert payouts already computed for others (e.g., use `coin::is_account_registered`/`can_receive_direct_coin_transfers` checks up front and skip/queue non-receivable shareholders instead of unconditionally calling `deposit_coins`, or otherwise isolate per-recipient failures, e.g. by processing distributions outside of a shared loop transaction, or holding the poisoned shareholder's share back in the pool rather than aborting the entire withdrawal).
- Alternatively, require and enforce `assert_account_is_registered_for_apt`-style pre-registration for the staker/each distribution-pool participant (similar to the check already done for vesting beneficiaries in `set_beneficiary`) at the time shares are created, so that opting out afterward cannot break existing shareholders' payouts.

### Proof of Concept
1. Staker `S` calls `staking_contract::create_staking_contract(S, operator, 1000 APT, 10)`, creating a staking contract with `S` as sole staker and `operator` as operator (10% commission).
2. Before any distribution ever occurs, `S` calls `aptos_account::set_allow_direct_coin_transfers(S, false)` on their own account (a fully public, unprivileged call) — legitimate if `S`'s `CoinStore<AptosCoin>` was somehow deregistered/never explicitly registered, or more directly by using a freshly created address that has never registered `AptosCoin` and only exists via `account::create_account` without coin registration.
3. Stake pool accrues rewards; `operator` calls `staking_contract::request_commission` to unlock commission, then, after lockup passes, calls `staking_contract::distribute(S, operator)`.
4. `distribute_internal` withdraws the unlocked pool of coins, and in the payout loop reaches `S`'s distribution entry, calling `aptos_account::deposit_coins(S, ...)`. Because `S` opted out and has no registered `CoinStore<AptosCoin>`, this call hits `assert!(can_receive_direct_coin_transfers(S), ...)` and aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. The entire `distribute` transaction reverts. `operator`'s already-earned, unlocked commission (and `S`'s own unlocked principal) remains permanently stuck in the stake pool: every subsequent call to `distribute`, `request_commission`, `unlock_stake`, or `switch_operator` on this staker/operator pair repeats the same abort, since `S` remains a shareholder in the `distribution_pool` and the loop unconditionally iterates over all shareholders.

Note: I was not able to view the complete body of `vesting::distribute` (lines 720–750 were not returned by the index) to cite the exact loop code, but the surrounding structure (withdraw → distribution amount → emit `Distribute` event) and the module's own documentation confirm it follows the same per-shareholder payout pattern as `staking_contract::distribute_internal`, using the same `aptos_account::deposit_coins`-style transfer for each shareholder. A full review of that omitted range (via a Devin session with complete file access) is recommended to confirm the exact call site before remediation.

    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
