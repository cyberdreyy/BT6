### Title
Instant-withdraw claims can be paid before funding, double-spending underlyings reserved for funded normal withdraw receipts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The OpenLDAP flaw is a double-free / out-of-bounds read in control-request handling — the same request object is consumed twice, so one allocation satisfies two consumers. The credit-vault analog is a double-spend of funded underlyings: `IdleCreditVault.claimInstantWithdrawRequest` pays out an instant-withdraw receipt from the vault's raw token balance without checking that the borrower-funded transfer for that receipt has actually been collected. During the buffer period between `stopEpoch` and `startEpoch`, the only underlyings sitting in the strategy are funds already collected via `collectWithdrawFunds` for matured, funded normal withdraw requests. An attacker can therefore claim an unfunded instant receipt against other users' funded claims — one pot of tokens paying two receipts.

### Finding Description
`requestWithdraw` in `IdleCDOEpochVariant` routes to `creditVault.requestInstantWithdraw` when the APR dropped by more than `instantWithdrawAprDelta`, minting the user a 1:1 strategy-token receipt and increasing `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`). Those receipts are only backed later, when the CDO collects them from the borrower at the next `startEpoch` via `collectInstantWithdrawFunds` (`IdleCreditVault.sol:398-403`, and the docstring at `IdleCDOEpochVariant.sol:973-974`: "funds will get transferred from borrower when epoch starts").

However `claimInstantWithdrawRequest` has no epoch-phase or funding gate:

- `IdleCDOEpochVariant.sol:975-979` checks only `allowInstantWithdraw`, not `isEpochRunning`.
- `IdleCreditVault.sol:380-393` burns the receipt tokens and calls `_transferFundedClaim(_user, amount)` unconditionally.
- `_transferFundedClaim` (`IdleCreditVault.sol:897-907`) only ring-fences `defaultRecoveryReserve`; there is no per-epoch/per-receipt funding flag for normal claims.

Meanwhile `collectWithdrawFunds` (`IdleCreditVault.sol:411-430`) pulls borrower underlyings into the strategy at `stopEpoch` to back matured normal withdraw receipts, which legitimate users can claim "at any time even if a new epoch started" (`IdleCreditVault.sol:320-325`).

Attack sequence (fixed-APR mode, buffer phase after `stopEpoch`):

1. Attacker (KYC'd lender) deposits AA, waits for `stopEpoch` where `manager` sets a lower APR (`lastEpochApr > unscaledApr + instantWithdrawAprDelta`) so instant mode activates.
2. During the buffer, the strategy balance contains `F` underlyings collected at `stopEpoch` for other users' pending funded withdraw claims.
3. Attacker calls `cdoEpoch.requestWithdraw(0, AAtranche)` → routes to `requestInstantWithdraw`, minting receipt of size `F`.
4. In the same block/epoch phase, attacker calls `cdoEpoch.claimInstantWithdrawRequest()` → `_transferFundedClaim` sends `F` underlyings that were earmarked for the other users' funded claims.
5. At `startEpoch`, `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` and pulls `F` again from the borrower — but the original funded claimants' receipts remain unpaid; the newly collected funds now back the attacker's already-claimed receipt a second time, while the first claimants' `claimWithdrawRequest` reverts on insufficient balance.

The receipt-tokens burned in step 4 are freshly minted receipts, so the burn always succeeds; the failure is that the payout source is the shared vault balance rather than funding specifically collected for instant receipts.

### Impact Explanation
Direct theft / permanent freezing of funds: the attacker extracts underlyings equal to the funded normal-withdraw balance held in the strategy. Legitimate claimants' receipts (`withdrawsRequests`, `withdrawsRequestsByEpoch`) remain recorded but `claimWithdrawRequest` → `_transferFundedClaim` reverts on `safeTransfer` insolvency until/if someone refunds the vault — no automatic recovery path exists since `pendingWithdraws` was already zeroed at `stopEpoch`. Loss is bounded by the unclaimed funded-withdraw balance, which can be the full pool NAV for a closing epoch (`epochEndDate == 0` path collects everything).

### Likelihood Explanation
Requires: instant withdraws enabled (`allowInstantWithdraw`, `disableInstantWithdraw == false`, not programmable mode), a lower APR set at `stopEpoch` (a routine manager action), and unclaimed funded withdraw balances in the strategy — all normal operating conditions during the buffer period. Attacker needs only a KYC-passing lender position. The missing `isEpochRunning`/funding gate on the claim path is verifiable directly in the code.

### Recommendation
Gate `claimInstantWithdrawRequest` on collected funding: track funded instant withdrawals per epoch (e.g., set `instantWithdrawsFundedEpoch[currentEpoch]` in `collectInstantWithdrawFunds`) and only pay receipts whose `instantWithdrawsRequestsByEpoch` epoch has been funded, or snapshot a segregated `instantWithdrawReserve` analogous to `defaultRecoveryReserve` and have `_transferFundedClaim` protect `reserve + instantReserve` so unfunded instant claims can never spend normal funded claims.

### Proof of Concept
Reproducible Foundry fork PoC sketch against `IdleCDOEpochVariant` + `IdleCreditVault`:

```solidity
// setup: victim and attacker deposit AA; manager startEpoch -> borrower funded
// manager stopEpoch(apr, 0) with lowered apr so instantWithdrawAprDelta triggers;
//   stopEpoch collects pendingWithdraws -> strategy.balance == victim's funded claim F
// (victim requested normal withdraw before stopEpoch; receipt now funded)

vm.prank(attacker);
cdoEpoch.requestWithdraw(0, address(AAtranche));          // -> requestInstantWithdraw, mints receipt

vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();                   // pays F from strategy balance NOW
assertEq(underlying.balanceOf(attacker) - pre, F);        // attacker stole victim's funded claim

vm.prank(victim);
vm.expectRevert();                                        // safeTransfer: insufficient balance
cdoEpoch.claimWithdrawRequest();                          // victim's funded claim bricked
```

Key assertion: `strategy.pendingInstantWithdraws()` is still non-zero after the attacker's claim (funding never collected), proving the payout consumed underlyings that belonged to the funded normal-withdraw bucket.
