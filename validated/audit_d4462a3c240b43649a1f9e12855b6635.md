### Title
Unbounded growth of `allowListedRequests` causes O(n) linear scan and node-wide latency/DoS on every Vault gateway request - ([File: core/capabilities/vault/allow_list_based_auth.go])

### Summary
The Vault gateway's node-side authorization path (`allowListBasedAuth.AuthorizeRequest`) fetches the *entire* on-chain allowlisted-requests list and performs a linear scan for every single incoming JSON-RPC request, and this scan is retried (with sleeps) whenever the digest is not yet found. The list can be grown without any practical bound by any linked workflow owner calling `AllowlistRequest` on the `WorkflowRegistry` contract, which is a "user" operation, not a DAO/admin-gated one. This mirrors the reported bug class (unbounded iteration over a registrant list triggered by unprivileged actors, causing critical-path failure/slowdown), just applied to the Vault's request-authorization hot path instead of an on-chain checkpoint loop.

### Finding Description
`allowListBasedAuth.AuthorizeRequest` calls `findAllowlistedItemWithRetry`, which on every attempt fetches the complete, unbounded allowlist via `r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)` and then does a full `O(n)` scan (`fetchAllowlistedItem`) to find a match, with debug-string construction over the *entire* list on every attempt: [1](#0-0) 

The scan/fetch is retried up to `allowListBasedAuthRetryCount` (10) times with a 3-second sleep between each attempt if the digest isn't found yet: [2](#0-1) 

This authorization path is invoked for **every** Vault request routed through the gateway to the node (`MethodSecretsCreate/Update/Delete/List`), via `GatewayHandler.HandleGatewayMessage` → `GatewayVaultRequestProcessor.ProcessRequest` → `Authorizer.AuthorizeRequest`: [3](#0-2) 

The underlying list `w.allowListedRequests` is populated by `getAllowlistedRequests`, which paginates through the on-chain `TotalAllowlistedRequests` count and stores the full result set in memory (no cap, no pruning of expired entries observed in the reviewed sync logic): [4](#0-3) [5](#0-4) 

Crucially, adding to this list is a low-privilege "user" operation on the `WorkflowRegistry` contract — any linked workflow owner can call `AllowlistRequest` with an arbitrary digest and expiry, not gated by DAO/admin allow-listing the way the reported custodians must be: [6](#0-5) [7](#0-6) 

Because any linked owner can repeatedly call `AllowlistRequest` (only paying normal transaction gas), the size of `allowListedRequests` is attacker-influenced and effectively unbounded, exactly analogous to the reported concern about unbounded `registeredCustodians` growth blocking a critical for-loop.

### Impact Explanation
Every Vault gateway request performs a full copy and linear scan of this list, and does so multiple times with retries/sleeps if the digest isn't found (e.g., due to sync lag or a malformed/expired/incorrect request). As the list grows (attacker-driven or organically over time with no observed pruning of expired entries), CPU cost and per-request latency of the node-side Vault handler scale linearly with allowlist size for *every* request from *every* workflow owner — not just the attacker's own requests. This can degrade or effectively stall Vault secret operations DON-wide, a shared-resource availability impact analogous to the reported `evaluateReleaseSchedule`/`checkpoint` blocking scenario, though realized here as an off-chain compute/latency DoS rather than a gas-limit revert.

### Likelihood Explanation
Likelihood is moderate: the action needed (calling `AllowlistRequest`) requires only that the caller be a linked workflow owner — a much lower bar than the DAO-gated custodian allow-listing in the original report — making it plausible for a single malicious or careless workflow owner to grow the list significantly. The severity scales with how large the list must get before impact is noticeable, which was not directly measured here; this is a performance/DoS finding requiring further quantification (e.g., benchmarking at scale) which is not confirmed in the reviewed code.

### Recommendation
- Index allowlisted requests by digest (e.g., a `map[[32]byte]*WorkflowRegistryOwnerAllowlistedRequest`) instead of a slice, to make lookups `O(1)`.
- Cap or rate-limit the number of active (non-expired) allowlisted requests per workflow owner, and/or the `AllowlistRequest` contract call frequency.
- Prune expired entries from the in-memory cache and avoid rebuilding debug log strings for the full list on every request/attempt.
- Consider avoiding the retry-with-sleep loop scanning the full list repeatedly; instead, trigger scan only after confirmed sync updates.

### Proof of Concept
Not independently verified with a live load test; based on static code analysis:
1. As a linked workflow owner, repeatedly call `WorkflowRegistry.AllowlistRequest` with unique random digests and long expiries to grow `TotalAllowlistedRequests` unboundedly (no cap observed in the reviewed user-operation path).
2. Once the node's `workflowRegistrySyncer` picks these up, `allowListedRequests` grows to match.
3. Issue legitimate Vault requests (e.g., `secrets/list`) from any other workflow owner; each call now performs an `O(n)` scan over the inflated list inside `AuthorizeRequest`/`fetchAllowlistedItem`, and unauthorized/mismatched digests trigger the full 10-retry × 3s-sleep loop, each retry re-scanning the whole list — degrading throughput/latency for the entire Vault gateway handler on that node.

func (r *allowListBasedAuth) findAllowlistedItemWithRetry(ctx context.Context, req jsonrpc.Request[json.RawMessage], requestDigest string, requestDigestBytes32 [32]byte) (*workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, []string, error) {
	for attempt := 0; attempt <= r.retryCount; attempt++ {
		allowedRequests := r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)
		allowedRequestsStrs := make([]string, 0, len(allowedRequests))
		for _, rr := range allowedRequests {
			allowedReqStr := fmt.Sprintf("AuthorizedOwner: %s, RequestDigest: %s, ExpiryTimestamp: %d", rr.Owner.Hex(), hex.EncodeToString(rr.RequestDigest[:]), rr.ExpiryTimestamp)
			allowedRequestsStrs = append(allowedRequestsStrs, allowedReqStr)
		}
		r.lggr.Debugw("AllowListBasedAuth loaded allowlisted requests", "method", req.Method, "requestID", req.ID, "attempt", attempt+1, "allowedRequests", allowedRequestsStrs)

		allowlistedRequest := r.fetchAllowlistedItem(allowedRequests, requestDigestBytes32)
		if allowlistedRequest != nil {
			return allowlistedRequest, allowedRequestsStrs, nil
		}
		if attempt == r.retryCount {
			return nil, allowedRequestsStrs, nil
		}

		r.lggr.Debugw("AllowListBasedAuth request digest not yet allowlisted, retrying",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"attempt", attempt+1,
			"maxAttempts", r.retryCount+1,
			"retryInterval", r.retryInterval)
		if err := sleepWithContext(ctx, r.retryInterval); err != nil {
			r.lggr.Debugw("AllowListBasedAuth retry canceled", "method", req.Method, "requestID", req.ID, "error", err)
			return nil, nil, err
		}
	}

	return nil, nil, nil // unreachable: loop always returns
}

func (h *GatewayHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) (err error) {
	reqLggr := h.requestLogger(req, gatewayID)
	reqLggr.Debugw("received message from gateway", "req", req)

	var response *jsonrpc.Response[json.RawMessage]
	var authResult *AuthResult

	switch req.Method {
	case vaulttypes.MethodSecretsCreate, vaulttypes.MethodSecretsUpdate:
		publicKey, pkErr := h.getMasterPublicKey(ctx)
		if pkErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pkErr)
			break
		}
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, publicKey)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodSecretsDelete, vaulttypes.MethodSecretsList:
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, nil)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodPublicKeyGet:
		response = h.handlePublicKeyGet(ctx, gatewayID, req)
	default:
		response = h.errorResponse(ctx, gatewayID, req, api.UnsupportedMethodError, errors.New("unsupported method: "+req.Method))
	}
