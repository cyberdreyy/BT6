### Title
Partially prefunded instant-withdraw claims pay the full receipt basis, letting early claimers drain later claimants' funded share - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` in `IdleCreditVault` burns the user's entire `instantWithdrawsRequests[_user]` receipt and pays it out in full through `_transferFundedClaim`, even when `pendingInstantWithdraws` is still non-zero — i.e., the epoch's instant-withdraw queue was only partially prefunded by `IdleCDOEpochVariant` at `startEpoch`/`getInstantWithdrawFunds`. Analogous to the FFmpeg LCL decoder treating a short zlib inflate as non-fatal and copying a full frame from a partially filled buffer, the strategy treats partial funding as non-fatal and pays the full claim basis, spending underlying that belongs to other pending instant claimants and funded normal withdraw receipts.

### Finding Description
`collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` only by the amount actually collected from the CDO (`IdleCreditVault.sol:398-403`), so a partially prefunded epoch leaves `instantWithdrawsRequests[user]` fully intact while the strategy holds only part of the needed underlying. `claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`) then burns the full `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim(_user, amount)`, which only checks `balance - defaultRecoveryReserve >= amount` (`IdleCreditVault.sol:897-907`). It does not check that the user's receipt was actually funded, nor does it pro-rate by a per-epoch funding ratio the way `collectWithdrawFunds`/`lossRecoveryPriceByEpoch` do for normal withdraws (`IdleCreditVault.sol:411-430`). The result: the first claimants are paid in full out of the commingled strategy balance — including underlying reserved for other instant claimants and for funded normal withdraw receipts — until the balance is exhausted and subsequent `safeTransfer` calls revert.

### Impact Explanation
Direct theft and temporary freezing with quantified loss: if an epoch's instant queue of `Q` is prefunded with only `F < Q`, the earliest claimers withdraw up to the full strategy liquid balance, and the last `Q - F` worth of claimants (instant claimants and/or funded normal receipt holders whose claims route through `_transferFundedClaim`) can never claim — their funds were paid out to earlier claimants. The attacker (any KYC-passing lender holding tranche tokens) simply needs to request an instant withdraw and claim before honest users. Loss is bounded by `pendingInstantWithdraws` plus any other funded-but-unclaimed receipt balance held in the strategy, i.e., potentially the entire funded-withdrawal reserve of the vault.

### Likelihood Explanation
Partial prefunding is an explicitly supported mode: the code comments and tests (e.g., `testFinalizeDefaultClaimsInstantRedeemsWithRecoveryRatio` in `test/foundry/IdleCreditVault.t.sol:4441-4483`) describe "partially prefunded instant requests" where `pendingInstantWithdraws < instantClaimBasis` after `startEpoch`. This occurs whenever the CDO's available liquidity at epoch start covers only part of the instant queue — a routine condition in a running epoch, not an edge case. The attack requires only a tranche-token holder requesting an instant withdraw and racing to claim; no privileged role is involved.

### Recommendation
Track per-epoch instant-withdraw funding and pay claims pro-rata, mirroring the `lossRecoveryPriceByEpoch` mechanism used for normal withdraws: store an `instantFundedPriceByEpoch` set when `collectInstantWithdrawFunds` collects less than the epoch basis, cap each claim at `claimBasis * fundedPrice / RECOVERY_FULL`, or revert claims while `pendingInstantWithdraws` exceeds zero for the user's request epoch. Alternatively gate `claimInstantWithdrawRequest` so a receipt can only be claimed once its epoch's instant queue is fully collected.

### Proof of Concept
Foundry fork PoC (sketch, on the existing `IdleCreditVault.t.sol` harness):

```solidity
function testPartiallyPrefundedInstantDrain() external {
  address early = makeAddr('early-claimer');
  address late  = makeAddr('late-claimer');
  uint256 amount = 10_000 * ONE_SCALE;

  // Both users deposit AA and the epoch runs
  _depositWithUser(early, amount, true);
  _depositWithUser(late,  amount, true);
  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

  // Both request instant withdraws in the buffer
  vm.prank(early); cdoEpoch.requestWithdraw(0, address(AAtranche));
  vm.prank(late);  cdoEpoch.requestWithdraw(0, address(AAtranche));

  // startEpoch prefunds only part of the instant queue
  _startEpochAndCheckPrices(1);
  IdleCreditVault cv = IdleCreditVault(address(strategy));
  assertGt(cv.pendingInstantWithdraws(), 0); // unfunded remainder exists

  vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
  vm.prank(manager); cdoEpoch.getInstantWithdrawFunds();

  // Early claimer receives the FULL receipt despite partial funding
  uint256 pre = underlying.balanceOf(early);
  vm.prank(early); cdoEpoch.claimInstantWithdrawRequest();
  assertGt(underlying.balanceOf(early) - pre, 0);

  // Late claimer reverts: their share was paid to `early`
  vm.prank(late);
  vm.expectRevert(); // ERC20 safeTransfer insufficient balance
  cdoEpoch.claimInstantWithdrawRequest();
}
```

Uncertainty note: I could not fully verify the CDO-side gating in `IdleCDOEpochVariant.claimInstantWithdrawRequest`/`getInstantWithdrawFunds` (whether it blocks user claims while `pendingInstantWithdraws > 0`). If the CDO already reverts claims for unfunded instant receipts, this vector is mitigated at that layer; otherwise the strategy-level full-basis payout described above is reachable as shown.
