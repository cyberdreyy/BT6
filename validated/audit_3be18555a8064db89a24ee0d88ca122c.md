### Title
Stale confirmations from removed multisig members allow request execution below `num_confirmations` live members - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` only purges pending requests and confirmation sets for requests that the deleted member *originated* (`r.member == member`), but never scans other requests' `confirmations: LookupMap<RequestId, HashSet<String>>` to strip out the deleted member's confirmation string from requests they only *confirmed*. As a result, a stale confirmation from a no-longer-valid member remains counted toward `num_confirmations`, letting a request execute even though fewer than `num_confirmations` *current* members actually approved it.

### Finding Description
The broken binding is: `confirmations.len() (at execution) == number of confirmations cast by accounts that are members at execution time`. This should always hold but does not.

In `multisig2/src/lib.rs`:
- `confirm()` computes `if confirmations.len() as u32 + 1 >= self.num_confirmations` and executes the request purely based on the *size* of the stored `HashSet<String>`, with no check that every string in that set still corresponds to a current member [1](#0-0) .
- `delete_member` removes `num_requests_pk` for the deleted member and deletes requests/confirmations only for requests where `r.member == member` (i.e., requests the deleted member *originated*), but does nothing to strip that member's `to_string()` entry from confirmation sets of requests originated by *other* members: [2](#0-1) .

Exploit flow (self-contained, no re-add needed to demonstrate the impact):
1. Multisig with members `alice, bob, carol, dave`, `num_confirmations = 2`.
2. `alice` creates request `R1` (e.g. `Transfer` to some receiver) via `add_request`.
3. `carol` calls `confirm(R1)`. Since `confirmations.len()==0`, `0+1 < 2`, so it just inserts `"carol"` into `R1`'s confirmation set rather than executing [3](#0-2) .
4. `alice` and `bob` create+confirm a second request `R2 = DeleteMember{carol}` reaching threshold 2, which executes `delete_member(carol)`. Since `carol` did not *originate* `R1` (alice did), `R1`'s confirmation set is untouched; only `carol`'s `num_requests_pk` entry and membership are removed.
5. `bob` now calls `confirm(R1)`. `confirmations.len()` is still `1` (`"carol"`), so `1+1 >= 2` and the request executes — driven by one live confirmation (`bob`) plus one stale confirmation from a removed member (`carol`).

No existing guard catches this: `assert_valid_request` only checks the *caller* is a current member, not the members backing prior confirmations [4](#0-3) ; there is no re-validation of the confirmation set's membership before execution.

### Impact Explanation
NEAR (or any action, including `AddKey`/`AddMember`/`Transfer`) can be executed by a multisig with effectively fewer live approving signers than `num_confirmations`, since a departed member's leftover confirmation string still counts. This is squarely the listed Critical category: "a multisig request executed below `num_confirmations` live members." The blast radius is any multisig2 contract instance where membership changes occur while other requests are pending — a common operational pattern (rotating signers) — enabling fund transfers, key additions, or contract deployments to bypass the intended live-threshold guarantee.

### Likelihood Explanation
The precondition is simply "some request is pending confirmation, and one of its confirmers is later removed before the request is executed or deleted" — an entirely ordinary sequence achievable by a legitimate member proposing a removal (e.g., off-boarding a signer) while another request is in flight, with zero special cost to any party and fully reachable with only the permissions of an existing multisig member (no foundation/owner privilege beyond normal multisig membership needed to trigger the missing-cleanup defect). It's repeatable on every membership change against every currently-pending un-originated-by-them confirmed request.

### Recommendation
When deleting a member, iterate all pending requests' confirmation sets and remove the deleted member's `to_string()` entry (not just requests they originated), or re-validate at execution time in `confirm()` that every entry in the confirmation `HashSet` still corresponds to a current member of `self.members` before counting it toward `num_confirmations`.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
