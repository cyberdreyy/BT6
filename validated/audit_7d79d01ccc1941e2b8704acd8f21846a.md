### Title
Vault Gateway `MethodPublicKeyGet` request bypasses the shared authorization/validation pipeline enforced on all other vault methods - ([File: core/capabilities/vault/gw_handler.go])

### Summary
The SYMM-IO report describes a function (`internalTransfer`) that performed the same sensitive action (allocating collateral) as guarded functions but omitted the shared guard (`whenNotAccountingPaused`) that every other allocation path enforced. The `chainlink` node's Vault `GatewayHandler.HandleGatewayMessage` follows the identical pattern: every vault method that manipulates or returns request-scoped data is routed through `h.requestProcessor.ProcessRequest`, except `vaulttypes.MethodPublicKeyGet`, which is dispatched directly to `handlePublicKeyGet` without ever touching the processor.

### Finding Description
In `HandleGatewayMessage`, the method dispatch is: [1](#0-0) 

- `MethodSecretsCreate`/`MethodSecretsUpdate` → `h.requestProcessor.ProcessRequest(ctx, req, publicKey)`
- `MethodSecretsDelete`/`MethodSecretsList` → `h.requestProcessor.ProcessRequest(ctx, req, nil)`
- `MethodPublicKeyGet` → `h.handlePublicKeyGet(ctx, gatewayID, req)` directly, with **no call into `requestProcessor.ProcessRequest`** at all.

`handlePublicKeyGet` itself performs no independent authorization, allowlist check, or request validation — it only unmarshals params and calls `h.secretsService.GetPublicKey`: [2](#0-1) 

The `GatewayHandler` is constructed with an `Authorizer` chain (allowlist-based and optionally JWT-based) and a `NewRequestValidatorFromLimitsFactory`-derived validator, both of which are wired only into `requestProcessor`: [3](#0-2) 

Because `MethodPublicKeyGet` never reaches `requestProcessor.ProcessRequest`, any request-level protections implemented there (allowlist/JWT authorization, and — depending on `NewRequestValidatorFromLimitsFactory`'s implementation — batch-size/quota/rate validation) are skipped for this method, exactly mirroring the reported bug class: a new/alternate code path that performs a privileged or resource-consuming action without the guard applied uniformly to its sibling functions.

I was not able to fully confirm from the index whether `NewRequestValidatorFromLimitsFactory`/`ProcessRequest` enforces per-caller rate limiting or quota (the processor's internals in `gateway_vault_request_processor.go` were not fully retrievable before the tool budget was exhausted), so the precise severity of what is bypassed (pure authorization vs. authorization + quota/rate-limiting) is not fully verified.

### Impact Explanation
If `requestProcessor.ProcessRequest` also enforces caller-based quota/rate-limiting for the gateway-facing Vault API (in addition to allowlist/JWT auth), then an unprivileged client can send unlimited `MethodPublicKeyGet` requests through the gateway, bypassing whatever quota or allowlist gating is applied to every other vault operation — analogous to bypassing a global pause/guard via an alternate function. At minimum this is an inconsistency that lets an unauthenticated/unauthorized caller reach `secretsService.GetPublicKey` without going through the same authorization chain the rest of the API enforces, which is a control bypass even if the returned public key itself is not secret material.

### Likelihood Explanation
High reachability: `MethodPublicKeyGet` is one of the four public `vaulttypes.Methods` exposed by the gateway connector and is directly reachable by any client able to send messages to the gateway (unprivileged client request path), requiring no special conditions.

### Recommendation
Route `MethodPublicKeyGet` through the same `h.requestProcessor.ProcessRequest` pipeline (or an equivalent lightweight validator) used by the other vault methods, so that allowlist/JWT authorization and any rate-limiting/quota checks are applied uniformly across all gateway-exposed vault methods, matching the pattern of `MethodSecretsDelete`/`MethodSecretsList`.

### Proof of Concept
Not applicable as executable PoC given ask-only/read-only access; the control-flow evidence above (lines 187-211 vs. 364-386 of `core/capabilities/vault/gw_handler.go`) demonstrates that `MethodPublicKeyGet` is dispatched without any call to `requestProcessor.ProcessRequest`, unlike every sibling method.

func (h *GatewayHandler) handlePublicKeyGet(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	r := &vaultcommon.GetPublicKeyRequest{}
	if err := json.Unmarshal(*req.Params, r); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}

	resp, err := h.secretsService.GetPublicKey(ctx, r)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.HandlerError, fmt.Errorf("failed to get public key: %w", err))
	}

	b, err := json.Marshal(resp)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.NodeReponseEncodingError, err)
	}

	return &jsonrpc.Response[json.RawMessage]{
		Version: jsonrpc.JsonRpcVersion,
		ID:      req.ID,
		Method:  req.Method,
		Result:  (*json.RawMessage)(&b),
	}
}
