### Title
Stale rejection weight is never retracted when a signer flips to acceptance, corrupting the miner's aggregated vote tally - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` tracks `total_weight_approved` and `total_weight_rejected` as two independent, monotonically-increasing counters keyed off separate dedup sets (`gathered_signatures` for accepts, and a shared `responded_signers` set that is inserted into by both arms). Nothing ever subtracts a signer's previously-counted rejection weight when that same signer later sends an `Accepted` `BlockResponse` for the same block. Since the signer-side state machine explicitly supports `LocallyRejected -> LocallyAccepted` (a documented "re-evaluated" transition), a signer can legitimately reject a block and then, after re-evaluation, sign and broadcast acceptance for the very same block — and the miner's coordinator will now double-count that signer's weight on *both* sides of the tally. This is the same bug class as the Fraxlend report: a partial/derived quantity (`total_weight_rejected`) is left stale after an operation (the flip to acceptance) that should have retracted it, corrupting downstream accounting (`total_weight_approved + total_weight_rejected` can exceed `total_weight`, or the rejected count can remain artificially inflated after the true state has moved to acceptance).

### Finding Description
`BlockStatus` (stacks-node/src/nakamoto_node/stackerdb_listener.rs:70-82) stores: [1](#0-0) 

For an `Accepted` response, weight is added guarded only by `gathered_signatures.contains_key(&slot_id)`: [2](#0-1) 

For a `Rejected` response, weight is added guarded by inserting into the *same* `responded_signers` set: [3](#0-2) 

There is no code path that, upon seeing a valid `Accepted` message from a slot_id already present in `responded_signers` (i.e., a slot that previously rejected), subtracts that signer's weight from `total_weight_rejected`. The `Accepted` arm's only gate against re-processing is `gathered_signatures` (which starts empty for that slot on its first acceptance), so the weight is added to `total_weight_approved` even though it is still sitting in `total_weight_rejected` from the earlier rejection.

This reject→accept flip is not a hypothetical: `docs/signer-flows.md` documents `LocallyRejected --> LocallyAccepted: re-evaluated` as a normal `BlockState` transition, and the same document notes "a rejection is a revocable opinion... if rejecting signers change their minds," confirming the protocol expects signers to legitimately switch sides on the same block. ### Impact Explanation
`signer_coordinator.rs::get_block_status` uses these two counters directly to decide the miner's outcome for a proposed block: it treats `total_weight_rejected + weight_threshold > total_weight` as proof the 70% acceptance is now unreachable (triggering `SignersRejected`, banning/excluding txids), and treats `total_weight_approved >= weight_threshold` as proof of acceptance: [6](#0-5) 

Because a single one-slot signer's weight can be simultaneously "stuck" in `total_weight_rejected` after flipping to accept, the aggregated rejection weight is inflated beyond what currently-standing rejections justify. In a scenario where the true accept/reject split is close to the 70/30 boundary, this stale counted weight can push `total_weight_rejected` over the blocking-minority threshold even though the actual outstanding rejecting weight (after the flip) no longer supports it — causing the miner to wrongly declare the block rejected (`SignersRejected`, `bump_naka_rejected_blocks`, txid exclusion) and abandon a block that in fact reached (or would reach) the real 70% signature threshold. This is a liveness wedge triggerable by a single signer's legitimate protocol-conformant behavior (reject-then-reconsider), not requiring a signing majority, an invalid signature, or another signer's key.

### Likelihood Explanation
The reject→accept flip is an explicitly supported and documented state transition (`LocallyRejected -> LocallyAccepted`), meaning any single honest signer that initially rejects a proposal on stale/preliminary information and later re-evaluates to accept it (e.g., after a chainstate recheck clears the earlier objection) will trigger this. No malicious majority or key compromise is required — one signer's ordinary vote flip is sufficient to leave a residual, uncorrected weight entry.

### Recommendation
When processing an `Accepted` `BlockResponse` for a slot that is already present in `responded_signers` due to a prior `Rejected` message (or vice versa), subtract that signer's weight from the previous bucket before adding it to the new one, so `total_weight_approved` and `total_weight_rejected` always reflect only the signer's most recent vote. Concretely, track a single authoritative `HashMap<slot_id, Vote>` (Accept/Reject + weight) and recompute both totals from it, rather than maintaining independently-incremented running sums.

### Proof of Concept
1. Signer S (weight w) sends `BlockResponse::Rejected` for block B. `stackerdb_listener` inserts S's slot_id into `responded_signers` and adds `w` to `total_weight_rejected`.
2. S's local state machine re-evaluates B (e.g., the earlier chainstate objection becomes stale/resolved) and transitions `LocallyRejected -> LocallyAccepted`, broadcasting `BlockResponse::Accepted` for the same B.
3. `stackerdb_listener` receives this Accepted message; since `gathered_signatures` for S's slot_id is still empty, it adds `w` to `total_weight_approved` as well — `w` is now counted in both totals with no correction to `total_weight_rejected`.
4. If other signers' weights bring `total_weight_rejected` (still inflated by S's stale `w`) past `total_weight - weight_threshold`, `signer_coordinator::get_block_status` returns `Err(NakamotoNodeError::SignersRejected{...})` even though the actual current rejecting weight (excluding S, who now accepts) may be below the blocking-minority threshold, causing the miner to needlessly abandon/rebuild the block.
