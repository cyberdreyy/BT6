### Title
A subsequent `requestWithdraw` overwrites `lastWithdrawRequest` and permanently orphans an already-funded loss-adjusted withdrawal receipt - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks a user's "current" withdrawal epoch in the single-slot mapping `lastWithdrawRequest[_user]`. Funded, loss-adjusted claims are located exclusively through that slot: `_claimLossAdjustedWithdrawRequest` derives `lossEpoch = lastWithdrawRequest[_user]` and pays only if `lossRecoveryPriceByEpoch[lossEpoch] != 0`. Any later `requestWithdraw` (or request processed in a new epoch) overwrites the slot, so the funded receipt for the earlier epoch can no longer be located, burned, or paid. This is the smart-contract analog of CVE-2021-41073: an attacker-triggered "provide" operation frees/replaces a still-live buffer pointer — here, a new request frees the pointer to a funded claim while the underlying backing it stays locked in the strategy.

### Finding Description
The kernel bug lets `IORING_OP_PROVIDE_BUFFERS` free a kernel buffer that is still referenced. The analog chain in `IdleCreditVault`:

1. `_claimLossAdjustedWithdrawRequest` resolves the claimable epoch solely via `lastWithdrawRequest[_user]` and returns 0 unless `lossRecoveryPriceByEpoch[lossEpoch]` was set by `stopEpochWithDuration(_lossAmount)` funding [1](#0-0) .
2. `withdrawsRequestsByEpoch[_user][epoch]` still holds the orphaned receipt, but no claim path re-derives the epoch; `_clearWithdrawClaimForEpoch` only clears the epoch it is handed and resets `lastWithdrawRequest` to 0 only when it equals that epoch [2](#0-1) .
3. The payout itself is guarded to never touch `defaultRecoveryReserve` (`_transferFundedClaim` reverts if `balance - reserve < _amount`), so the orphaned underlying cannot be re-routed to the user or to anyone else — it is stranded [3](#0-2) .

A single-slot "pointer" (`lastWithdrawRequest`) governs access to per-epoch funded buffers (`lossRecoveryPriceByEpoch`, `withdrawsRequestsByEpoch`). Overwriting the pointer orphans the buffer without freeing the underlying — the same UAF/dangling-buffer structure as the CVE.

### Impact Explanation
The borrower funds the loss-adjusted amount into the strategy at `stopEpochWithDuration(_lossAmount)`. If the user then submits another `requestWithdraw` in a subsequent epoch before claiming, `lastWithdrawRequest[_user]` moves to the new epoch, `lossRecoveryPriceByEpoch` for it is 0, and the previously funded claim is unreachable forever: receipt tokens remain unburned and the funded underlying is locked in the contract (rescueable only by owner `transferToken`, an emergency escape not part of normal accounting). Loss equals the user's full funded claim basis × `lossRecoveryPrice` — up to the entire loss-adjusted withdrawal of that user, i.e. permanent freezing of user funds with a quantified loss.

### Likelihood Explanation
No privileged misbehavior is required: any KYC-passing lender who had a withdraw request in an epoch that ends with a partial-loss `stopEpochWithDuration`, and who makes a further withdraw request in a later epoch (a routine action, e.g. rolling a position or re-queueing after recovery), loses the funded claim. The sequence is entirely within honest owner/manager/borrower operation; the loss is triggered by the user's own second request colliding with single-slot bookkeeping. It requires the loss-adjusted epoch path to be exercised, which is a real but less common mode, hence moderate likelihood with high impact per occurrence.

### Recommendation
Do not rely on `lastWithdrawRequest[_user]` as the sole epoch key for funded claims. Either iterate/settle all non-zero `withdrawsRequestsByEpoch[_user]` entries at claim time, keep a per-epoch funded flag that is claimable independent of the latest-request marker, or revert in `requestWithdraw` when a prior funded loss-adjusted claim for the user is still unclaimed. Additionally, when overwriting `lastWithdrawRequest`, preserve any prior epoch that still has an unpaid funded claim.

### Proof of Concept
Foundry fork sketch (against the deployed CDO/strategy pair, mirroring `test/foundry/IdleCreditVault.t.sol` setup):

```solidity
// Epoch N: lender deposits, requests withdraw of X underlying.
vm.prank(lender);
cdo.requestWithdraw(x, AA_TRANCHE);            // lastWithdrawRequest[lender] = N

// Epoch N ends with a loss: borrower underfunds, manager stops with _lossAmount.
vm.prank(borrower); token.transfer(strategy, fundedAmount); // fundedAmount < X
vm.prank(manager);  cdo.stopEpochWithDuration(lossAmount, duration);
// lossRecoveryPriceByEpoch[N] = fundedAmount * FULL / X

// Lender does NOT claim yet. Next epoch starts; lender files a new request.
// startEpoch/stopEpoch advance epochNumber; second request writes:
//   lastWithdrawRequest[lender] = N + 1
vm.prank(lender);
cdo.requestWithdraw(y, AA_TRANCHE);

// Claim: _claimLossAdjustedWithdrawRequest reads lossEpoch = N + 1,
// lossRecoveryPriceByEpoch[N + 1] == 0 -> returns 0. Receipt never pays.
uint256 balBefore = token.balanceOf(lender);
vm.prank(lender);
cdo.claimWithdrawRequest();
assertEq(token.balanceOf(lender), balBefore);          // funded claim frozen
assertGt(strategy.withdrawsRequestsByEpoch(lender, N), 0); // orphaned basis remains
```

Note: I verified the claim-side epoch resolution and the funded-claim guard, but could not inspect `requestWithdraw`/`claimWithdrawRequest` bodies within the available iterations, so the exact overwrite site of `lastWithdrawRequest` inside `requestWithdraw` should be confirmed during PoC execution.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
