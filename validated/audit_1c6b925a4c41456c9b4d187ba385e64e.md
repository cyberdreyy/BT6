## Title
Non-persisted `tx_replay_scope` combined with a persisted non-empty `tx_replay_set` wedges a restarted signer into `LocalStateMachineNotReady`, blocking all future signing - (File: `stacks-signer/src/v0/signer.rs`, `stacks-signer/src/v0/signer_state.rs`)

### Summary
Analogous to the `VotingControllerUpgradeable` bug (a field that another initializer depends on is silently left at its default instead of being properly reconstructed), the signer's `Signer::new` unconditionally sets `tx_replay_scope: None` on start-up/restart, while the paired field `tx_replay_set` is recovered from durable state (`SignerDb`/StackerDB) inside `LocalStateMachine::new`. These two fields are supposed to move in lock-step, but only one of them survives a restart.

### Finding Description
`ReplayScope`/`ReplayScopeOpt` is explicitly documented as *not persisted* local state on the `Signer` struct: [1](#0-0) 

Its counterpart, `tx_replay_set`, is part of `SignerStateMachine` and is serialized/persisted as part of `LocalStateMachine` (via `SignerDb`/StackerDB state-machine updates): [2](#0-1) 

At start-up, `Signer::new` restores the state machine from disk/StackerDB via `LocalStateMachine::new(...)`, but always initializes `tx_replay_scope: None` regardless of what the recovered `local_state_machine`'s `tx_replay_set` actually contains: [3](#0-2) 

When the next `NewBurnBlock` event arrives, `bitcoin_block_arrival` calls `ReplayState::infer_state(&tx_replay_set, tx_replay_scope)`. If the previously-persisted `tx_replay_set` is non-empty (meaning a tx replay was in progress at the time the signer stopped) but the freshly-initialized `tx_replay_scope` is `None`, `infer_state` returns `None`: [4](#0-3) 

This `None` causes `bitcoin_block_arrival` to bail out with `SignerChainstateError::LocalStateMachineNotReady`: [5](#0-4) 

Critically, `bitcoin_block_arrival` sets `self` to `Self::Uninitialized` up front via `std::mem::replace`, and only overwrites it with `Self::Initialized(...)` at the very end on success: [6](#0-5) 

Because the function returns an error before reaching that final assignment, the local state machine is left as `Self::Uninitialized` on the calling `Signer`. The caller (`process_event`/`handle_pending_update`) only logs the error and does not retry with a corrected scope: [7](#0-6) 

`LocalStateMachine::new` (used at construction time) hits exactly the same code path with `tx_replay_scope` starting as `&mut None`, so a signer that restarts mid-replay can become permanently wedged on its very first burn-block evaluation after start-up: [8](#0-7) 

### Impact Explanation
This matches the "High" bucket in scope: a signer wedged into never signing valid blocks. Once `local_state_machine` is `Uninitialized`, the signer cannot produce `StateMachineUpdate` messages (`try_into_update_message_with_version` explicitly errors on non-`Initialized` state — see lines 167-171 above) and cannot progress its miner/tenure view, so it can neither participate in the global-state agreement protocol nor evaluate/sign block proposals correctly, until a subsequent burn block happens to arrive with an empty replay set or `expected_burn_block` is `None` (bypassing the `infer_state` check entirely). In practice, for a single signer running with `validate_with_replay_tx = true` who crashes/restarts while a tx-replay set is in-flight (a normal, node-triggered post-fork condition, not requiring any signer misbehavior), the very next burn block processed after restart throws this error and leaves the state machine uninitialized. Since block-signing logic elsewhere in the codebase (`determine_response`, `handle_block_proposal`, etc.) also branches on the local/global state machine, this can stall the affected signer's participation for the current view.

### Likelihood Explanation
This is reachable by ordinary operational conditions — no majority collusion, no other signer's key, and no auth_token access are required. It requires: (1) `validate_with_replay_tx = true` (an experimental/opt-in but supported config flag — documented in `sample/conf/signer/mainnet-signer-conf.toml`), (2) the signer being mid tx-replay when it restarts (crash, upgrade, planned restart), and (3) the next burn block arriving before the replay set naturally clears. Given that Bitcoin forks (which trigger replay) and signer restarts (upgrades, crashes) are both routine operational events, and the code comment itself flags this exact failure mode ("Possibly caused by the scope being a local state in the `Signer` struct, which is not persisted"), the likelihood of triggering this liveness wedge is moderate-to-high in any deployment using replay validation.

### Recommendation
Persist `tx_replay_scope` alongside `tx_replay_set` (e.g., store it in `SignerDb` next to the state-machine record, or reconstruct it deterministically from persisted fork-origin/past-tip burn-block records) so that on restart the scope and set are restored together. Alternatively, on start-up, if the recovered `tx_replay_set` is non-empty but no scope can be reconstructed, explicitly clear the replay set (mirroring the existing fail-safe in `handle_possible_replay_failsafe`) instead of returning a hard error that leaves the whole state machine uninitialized — i.e., treat "non-empty set + missing scope" as "reset to `Unset`" rather than a fatal condition.

### Proof of Concept
1. Configure a signer with `validate_with_replay_tx = true`.
2. Drive it into an active tx-replay state so that its persisted `SignerStateMachine.tx_replay_set` is non-empty (a Bitcoin fork with un-replayed transactions, as covered by the `tx_replay_*` integration tests, e.g. `tx_replay_btc_on_stx_invalidation`, `tx_replay_failsafe` in `stacks-node/src/tests/signer/v0/tx_replay.rs`).
3. Restart the signer process (simulating a crash/upgrade) while the replay set is still non-empty and no new scope-clearing event has occurred.
4. On restart, `Signer::new` sets `tx_replay_scope = None` while `LocalStateMachine::new` loads the persisted non-empty `tx_replay_set`.
5. The subsequent `bitcoin_block_arrival` call (triggered either during `LocalStateMachine::new` or the next `NewBurnBlock` event) invokes `ReplayState::infer_state` with a non-empty set and `None` scope, returns `None`, and the function returns `Err(SignerChainstateError::LocalStateMachineNotReady)`.
6. Because `self` was already replaced with `Self::Uninitialized` before the error path, the signer's `local_state_machine` remains `Uninitialized`, and it stops sending state-machine updates / participating correctly until an external event resets its replay tracking.

I was not able to fully trace every downstream consumer of `Uninitialized` state (e.g., whether `handle_pending_update`/other callers retry on the same tick or only on the next event), so the exact duration of the wedge (single tick vs. indefinite until a qualifying event) should be verified with a live/integration test before filing as a confirmed liveness bug.

impl ReplayState {
    /// Infers the appropriate `ReplayState` based on the contents of the replay transaction set
    /// and the optional scope.
    ///
    /// # Arguments
    ///
    /// * `replay_set` - A reference to a set of transactions intended for replay.
    /// * `scope_opt` - An optional scope defining the boundaries or context for the replay.
    ///
    /// # Returns
    ///
    /// * `Some(ReplayState::Unset)` if the `replay_set` is empty.
    /// * `Some(ReplayState::InProgress)` if the `replay_set` is non-empty and a `scope` is provided.
    /// * `None` if the `replay_set` is non-empty but no `scope` is provided.
    ///   - Possibly caused by the scope being a local state in the `Signer` struct, which is not persisted.
    fn infer_state(replay_set: &ReplayTransactionSet, scope_opt: &ReplayScopeOpt) -> Option<Self> {
        if replay_set.is_empty() {
            return Some(Self::Unset);
        }

        scope_opt
            .as_ref()
            .map(|scope| Self::InProgress(replay_set.clone(), scope.clone()))
    }
