### Title
Stale `instantWithdrawsRequestsByEpoch` after a funded instant claim permanently bricks defaulted-epoch instant claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Same bug class as the external report: a per-receipt accounting slot is not emptied when the receipt is paid out. `claimInstantWithdrawRequest` zeroes `instantWithdrawsRequests[_user]` but never clears `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (its per-epoch copy). If the borrower defaults and recovery is finalized in that same epoch, `_claimDefaultedInstantWithdrawRequest` re-reads the stale per-epoch basis and subtracts it from the already-zeroed aggregate, which underflows and reverts — permanently freezing every instant receipt that user still has pending in the defaulted epoch and corrupting the recovery distribution.

### Finding Description
`requestInstantWithdraw` records both `instantWithdrawsRequests[_user]` and `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` when minting the receipt tokens (lines 356-375). On a funded claim, `claimInstantWithdrawRequest` burns the receipt, sets `instantWithdrawsRequests[_user] = 0`, and pays out — but leaves `instantWithdrawsRequestsByEpoch` untouched (lines 380-393). The only place that per-epoch entry is cleared is `_claimDefaultedInstantWithdrawRequest` (line 847).

On default finalization (`defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`), `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest(_user)`, which computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (line 844). For a user who already claimed an earlier instant receipt in that epoch, `claimBasis` includes the stale already-paid amount, while `instantWithdrawsRequests[_user]` only holds the still-pending basis. The subtraction `instantWithdrawsRequests[_user] -= claimBasis` (line 848) underflows in checked arithmetic, so the whole `claimInstantWithdrawRequest` call reverts — deterministically and forever, since the stale entry is never cleared and epochs are monotonic.

The invariant broken is "one receipt one payout / consistent dual accounting": the aggregate ledger says the receipt was consumed, the per-epoch ledger says it wasn't.

### Impact Explanation
Any user who (a) claimed an instant withdrawal during epoch N and (b) still has (or later opens) an instant receipt in epoch N when the borrower defaults in that same epoch is permanently unable to call `claimInstantWithdrawRequest`. Their remaining receipt tokens cannot be redeemed against the default recovery reserve — permanent freezing of unclaimed recovery funds proportional to their pending receipt size. The same revert also prevents `instantWithdrawClaimsByEpoch[defaultEpoch]` and `pendingInstantWithdraws` from being decremented for that user (lines 852-853), leaving protocol accounting overstated and potentially blocking orderly wind-down bookkeeping.

### Likelihood Explanation
Requires instant withdrawals enabled, a user claiming an instant receipt and holding/opening another one, then `_handleBorrowerDefault` + `finalizeDefaultRecovery` completing while `epochNumber` is unchanged. Epochs are long-duration by design, defaults are an explicitly supported mid-epoch transition, and an unprivileged lender only needs to hold two instant receipts in the same epoch — a routine pattern. The attacker can also be the victim's counterparty only in the sense that the default is triggered by the honest borrower flow, not by the attacker.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch entry for the epoch(s) the claimed basis belongs to (e.g., `instantWithdrawsRequestsByEpoch[_user][epochNumber] = 0` when `instantWithdrawsRequests[_user]` is fully consumed), mirroring the `withdrawsRequestsByEpoch` cleanup in `_clearWithdrawClaimForEpoch`. Alternatively, make `_claimDefaultedInstantWithdrawRequest` cap `claimBasis` at `instantWithdrawsRequests[_user]` so stale per-epoch dust cannot underflow.

### Proof of Concept
Foundry fork sketch:

```solidity
// Setup: instant withdrawals enabled (setInstantWithdrawParams), KYC'd user deposits AA.
// Epoch N running:
uint256 e = strategy.epochNumber();
cdoEpoch.requestWithdraw(amountA, address(AAtranche));   // instant receipt 1
// fund instant liquidity so it is claimable
cdoEpoch.claimInstantWithdrawRequest();                  // instantWithdrawsRequests[user]=0,
                                                         // instantWithdrawsRequestsByEpoch[user][e] still = amountA
cdoEpoch.requestWithdraw(amountB, address(AAtranche));   // instant receipt 2 (same epoch)

// Borrower defaults in the same epoch; owner/manager flow:
strategy._handleBorrowerDefault();                       // via CDO default path
strategy.finalizeDefaultRecovery();                      // sets defaultRecoveryFinalized,
                                                         // defaultInstantWithdrawsFinalized, defaultRecoveryEpoch = e

// User tries to claim receipt 2 recovery:
vm.expectRevert(); // arithmetic underflow at instantWithdrawsRequests[_user] -= claimBasis
cdoEpoch.claimInstantWithdrawRequest();
// amountB recovery is permanently frozen in the reserve.
```
