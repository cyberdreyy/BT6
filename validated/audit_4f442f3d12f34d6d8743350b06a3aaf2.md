### Title
`get_builder_withdrawals` records requested (uncapped) amount in `Withdrawal.amount`, but `apply_withdrawals` only debits `min(amount, builder.balance)` — EL mints more Gwei than the CL burns - ([File: specs/gloas/beacon-chain.md])

### Summary
In `get_builder_withdrawals`, the `Withdrawal` object appended to `payload_expected_withdrawals` (and thus committed for the execution layer to pay out) always carries the *requested* `withdrawal.amount` taken verbatim from `state.builder_pending_withdrawals[i].amount`, with no cap against the builder's actual balance. [1](#0-0)  Meanwhile `apply_withdrawals`, which performs the consensus-layer balance debit for the same withdrawal, caps the deduction at `min(withdrawal.amount, builder_balance)`. [2](#0-1) 

Since `payload_expected_withdrawals` becomes `state.payload_expected_withdrawals`, which the execution payload's `withdrawals` list must hash-equal (`assert hash_tree_root(payload.withdrawals) == hash_tree_root(state.payload_expected_withdrawals)` per the gloas envelope-verification flow), the EL will credit `withdrawal.amount` (the full, uncapped, requested amount) to `withdrawal.address`. [3](#0-2)  But the CL only ever removes `min(amount, balance)` Gwei from `state.builders[builder_index].balance`. [4](#0-3)  If a builder's pending-withdrawal request exceeds their available balance, the amount actually burned on the CL is strictly less than the amount minted on the EL — this breaks the "Gwei created" invariant.

### Finding Description
`process_withdrawals` -> `get_expected_withdrawals` -> `get_builder_withdrawals` builds the withdrawal that is exposed to the execution layer using the raw `builder_pending_withdrawals[i].amount` field with no `min()` clamp:
```python
withdrawals.append(
    Withdrawal(
        index=withdrawal_index,
        validator_index=convert_builder_index_to_validator_index(builder_index),
        address=withdrawal.fee_recipient,
        amount=withdrawal.amount,   # <-- requested amount, unclamped
    )
)
``` [5](#0-4) 

This list is stored as `state.payload_expected_withdrawals` via `update_payload_expected_withdrawals`, and the corresponding execution payload is required to match it exactly (a spec-following EL debits — no, credits — the exact `withdrawal.amount` to `withdrawal.address`). [6](#0-5) 

Later, when the balance is actually decremented on the consensus side, `apply_withdrawals` clamps the deduction:
```python
if is_builder_index(withdrawal.validator_index):
    builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
    builder_balance = state.builders[builder_index].balance
    state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
``` [7](#0-6) 

So whenever `withdrawal.amount > builder_balance`, the CL only burns `builder_balance` Gwei, while the withdrawal object committed to the EL still says `amount = withdrawal.amount` (the larger, requested figure). This directly mirrors the reported bug class: a "receipt"/committed value (`gasUsed` reported as `gas limit` instead of actual usage) diverges from the true consumed/burned quantity — here, the amount an execution-layer client will mint to `withdrawal.address` diverges from the amount actually debited from the builder's consensus-layer balance.

This exact scenario is acknowledged by the repository's own test helper/spec-report documentation, which states: "Actual = `min(amount, builder.balance)`" for the balance effect, while the withdrawal amount recorded is the "Requested amount." [8](#0-7)  A corresponding test explicitly confirms the mismatch is by design/observed behavior: with `available_balance = 1 ETH` and `withdrawal_amount = 5 ETH` requested, the test asserts `withdrawal.amount: 5 ETH (requested amount)` while `builders[0].balance: 0 (deduction capped to available balance)`. [9](#0-8) 

### Impact Explanation
This breaks the equality "Gwei burned on CL == Gwei minted on EL for a withdrawal," a Critical-severity class per the given impact bar (Gwei created, i.e. paid to a non-owner/beyond what was actually available). A builder (or anyone able to enqueue an entry in `state.builder_pending_withdrawals` for a builder index, e.g. via whatever mechanism populates `BuilderPendingWithdrawal.amount`) that requests a withdrawal larger than their current balance causes the execution layer to mint the full over-stated amount to `fee_recipient`, while the consensus layer only actually removes the builder's real (smaller) balance. This is a genuine supply-inflation bug: value materializes on the EL side that was never backed by a corresponding CL balance decrease.

### Likelihood Explanation
The trigger condition is simple: any `BuilderPendingWithdrawal` entry whose `.amount` exceeds the builder's current `.balance` at the time `get_builder_withdrawals` runs. Because balance can change between the request being queued and being processed (e.g., other withdrawals, slashings, or fee accounting reducing the builder's balance in between), or because nothing in the visible spec text enforces `amount <= builder.balance` at insertion time for `builder_pending_withdrawals`, this is readily reachable without any adversarial coalition — a single builder or the mechanism that enqueues `BuilderPendingWithdrawal` entries suffices.

### Recommendation
Clamp the `amount` field written into the `Withdrawal` object in `get_builder_withdrawals` to `min(withdrawal.amount, state.builders[builder_index].balance)`, matching the clamp already applied in `apply_withdrawals`, so that the amount exposed to (and to be minted by) the execution layer equals the amount actually debited from the builder's consensus-layer balance.

### Proof of Concept
1. Beacon state has `state.builders[0].balance = 1_000_000_000` Gwei (1 ETH).
2. `state.builder_pending_withdrawals` contains one entry: `{builder_index: 0, fee_recipient: <addr>, amount: 5_000_000_000}` (5 ETH requested) — this is exactly the configuration in the repo's own test `test_builder_withdrawal_insufficient_balance`. [10](#0-9) 
3. `process_withdrawals(state)` runs: `get_builder_withdrawals` emits `Withdrawal(index=i, validator_index=<builder 0>, address=<addr>, amount=5_000_000_000)` into `state.payload_expected_withdrawals`. [5](#0-4) 
4. `apply_withdrawals` then executes `state.builders[0].balance -= min(5_000_000_000, 1_000_000_000)` → new balance `0`. [4](#0-3)  The test explicitly confirms this outcome: `builder_balances={builder_index: 0}` while `withdrawal_amounts_builders={builder_index: withdrawal_amount}` (5 ETH). [11](#0-10) 
5. A spec-following execution client, receiving a payload whose `withdrawals` list (matching `state.payload_expected_withdrawals` by hash) contains `amount = 5 ETH` for `address = <addr>`, credits 5 ETH to that address on the execution layer.
6. Net effect: only 1 ETH was actually removed from the consensus-layer builder balance, but 5 ETH was created on the execution layer — 4 ETH of Gwei created out of thin air, paid to `<addr>`.

**Uncertainty**: I could not fully verify from the indexed context how `state.builder_pending_withdrawals` entries are originally inserted/validated (i.e., whether some other part of the spec enforces `amount <= balance` at insertion time, which would reduce likelihood). This is worth confirming in the full repo before treating this as conclusively exploitable end-to-end. I recommend a Devin session with full file access to check all insertion points (e.g. `BuilderPendingWithdrawal` creation code) for any such invariant.
