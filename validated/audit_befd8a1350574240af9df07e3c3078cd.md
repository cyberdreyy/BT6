There is no cgroup-based, PID-namespace-based, or process-tree-walking cleanup in this code path.### Title
Job cleanup fails to terminate detached grandchild processes that call `setpgid(0,0)` - ([File: helpers/process/killer_unix.go])

### Summary
`unixKiller.Terminate`/`ForceKill` only send `SIGTERM`/`SIGKILL` to the negative PID of the original job process (its process group), relying entirely on the single `Setpgid: true` set at spawn time in `job_unix.go`. Any descendant process that calls `setpgid(0,0)` (or otherwise moves itself to a new process group) leaves that group and is no longer reachable by the `-pgid` broadcast, so it survives job cancellation.

### Finding Description
The shell executor spawns the job's top-level shell via `newCommander`/`osCmd.Start`, which calls `setProcessGroup` to set `Setpgid: true` on the `exec.Cmd`, making the shell PID 1 of a new process group (`helpers/process/job_unix.go:16-18,36-40`). On cancellation, `executors/shell/shell.go:128-131` calls `newProcessKillWaiter(...).KillAndWait(c, waitCh)`, which in turn calls `processKiller.Terminate()` / `ForceKill()` (`helpers/process/killer.go:76-90`). Those methods compute `pk.getPID()` as `-Pid` of the original process and call `syscall.Kill(pk.getPID(), syscall.SIGTERM)` / `SIGKILL` (`helpers/process/killer_unix.go:21-44,50-52`). Per `kill(2)` semantics this only reaches processes that are still members of that specific process group. A grandchild forked by the job script that calls `setpgid(0,0)` moves itself into a brand-new process group while remaining a descendant (still reparented under the job's process tree, or even under init once orphaned), so it is excluded from the broadcast and is never signaled by either `Terminate` or `ForceKill`. There is no cgroup-based kill, PID-namespace teardown, or process-tree walk in this code path to catch such stragglers — the only mechanism is the pgid signal broadcast.

### Impact Explanation
On shared shell-executor hosts, a pipeline author can leave behind a long-running daemon/process that outlives job cancellation/timeout, consuming CPU, memory, file descriptors, or network sockets indefinitely. This degrades resource availability for other jobs/tenants scheduled on the same host and is a concrete, host-shared-resource exhaustion/persistence issue rather than a theoretical one.

### Likelihood Explanation
This requires only unprivileged code execution in the job script (available to any pipeline author on the shell/custom executors) and a single `setpgid` syscall, achievable via a small C helper, Python's `os.setpgrp()`, or `setsid`/`daemon()`-style double-fork patterns, all of which are commonly available on shared shell runners. No special preconditions beyond the job being allowed to run arbitrary code are needed, making this highly feasible and reliably repeatable.

### Recommendation
Track descendants beyond the initial process group — e.g., use a PID namespace or cgroup per job (already used by some executors) so cleanup can kill the entire cgroup contents regardless of process-group re-parenting, or recursively enumerate `/proc/<pid>/task/*/children` (or `pgrep -P`) to discover and signal all descendant PIDs/PGIDs before and after the initial `SIGTERM`/`SIGKILL`, not just the original `-pgid`.

### Proof of Concept
Integration test extending `helpers/process/killer_integration_test.go`'s pattern: build a test binary that forks a child, has the child call `syscall.Setpgid(0, 0)`, then sleeps; start it via `process.NewOSCmd` (which sets `Setpgid: true`), call `k.Terminate()` followed by `k.ForceKill()` after the graceful timeout, then assert that `syscall.Kill(childPid, 0)` still returns `nil` (process alive) after `KillAndWait` returns, proving the re-parented child was not signaled while the parent's `waitCh` reported termination. func (pk *unixKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGTERM)
	if err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}

func (pk *unixKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGKILL)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}
}

// getPID will return the negative PID (-PID) which is the process group. The
// negative symbol comes from kill(2) https://linux.die.net/man/2/kill `If pid
// is less than -1, then sig is sent to every process in the process group whose
// ID is -pid.`
func (pk *unixKiller) getPID() int {
	return pk.cmd.Process().Pid * -1
}

// KillAndWait will take the specified process and terminate the process and
// wait util the waitCh returns or the graceful kill timer runs out after which
// a force kill on the process would be triggered.
func (kw *osKillWait) KillAndWait(command Commander, waitCh chan error) error {
	process := command.Process()
	if process == nil {
		return ErrProcessNotStarted
	}

	log := kw.logger.WithFields(logrus.Fields{
		"PID": process.Pid,
	})

	processKiller := newProcessKiller(log, command)
	processKiller.Terminate()

	select {
	case err := <-waitCh:
		return err
	case <-time.After(kw.gracefulKillTimeout):
		processKiller.ForceKill()

		select {
		case err := <-waitCh:
			return err
		case <-time.After(kw.forceKillTimeout):
			return &KillProcessError{pid: process.Pid}
		}
	}
}
