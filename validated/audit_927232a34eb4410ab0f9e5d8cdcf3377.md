### Title
Attacker permanently inflates `pendingUnderlyings` and blocks all write-off request creation via unbounded `underlyingsRequested` - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` accepts a fully user-controlled `underlyingsRequested` value and adds it to the shared `pendingUnderlyings` counter with no upper-bound check. Analogous to the OpenQ tier bug (an unvalidated user-supplied index contaminating a shared, bounded accounting space), an unprivileged user can deposit a single wei of tranche tokens while requesting `type(uint256).max` underlyings, pushing `pendingUnderlyings` to the overflow boundary so that every subsequent honest `createWriteOffRequest` reverts.

### Finding Description
In `createWriteOffRequest` (contracts/IdleCreditVaultWriteOffEscrow.sol:86-102), the function:
- only requires the epoch to be running and `amount != 0` (lines 88-90),
- does **not** check `isWalletAllowed`/Keyring (confirmed by `testNonKeyringUsersCanCreateDeleteAndFulfillRequests`, so any EOA qualifies),
- performs `pendingUnderlyings += underlyingsRequested` (line 101) under Solidity 0.8.10 checked arithmetic.

There is no cap on `underlyingsRequested` — it need not correspond to the tranche tokens deposited, the tranche price, or vault TVL. A dust `amount` (1 wei tranche token, purchasable on the open market since tranche tokens are transferable) paired with `underlyingsRequested = type(uint256).max` sets `pendingUnderlyings` to `type(uint256).max`. From then on, any other user's `createWriteOffRequest` with `underlyingsRequested > 0` overflows at line 101 and reverts.

A secondary effect mirrors the "NFT assigned to an unreachable tier" mechanic: the attacker's request can never be fulfilled because `fullfillWriteOffRequest` requires `_underlyings >= currentRequest.underlyings` (line 129), which no fulfiller can pay. The request can only be cleared by the attacker (or remains forever), keeping `pendingUnderlyings` permanently inflated — the guarded subtraction at lines 112/134 ensures it cannot even be reduced by honest cleanup.

### Impact Explanation
- **Temporary freezing of the write-off market**: all honest lenders are unable to create write-off requests while the attacker's request stands. The escrow exists specifically to let lenders exit distressed credit exposure; blocking it during an active epoch is a direct denial of a user-facing function.
- **Permanent accounting corruption if the attacker never deletes**: `pendingUnderlyings` stays at ~`type(uint256).max` indefinitely, so any consumer (on-chain or keeper) relying on total pending requested underlyings sees garbage.
- Cost to attacker: 1 wei of tranche token plus gas; attack is repeatable after any admin/user cleanup.

### Likelihood Explanation
Requirements are minimal: epoch running (checked via `isEpochRunning`), one wei of tranche tokens, no KYC/Keyring gate on `createWriteOffRequest` (the test suite explicitly verifies non-keyring users can call it). No privileged role, timing, or capital is needed. The only mitigation is that the attacker can revert the block at will via `deleteWriteOffRequest`, which is exactly why it is a *temporary* freeze — but the attacker is the one in control of when it unfreezes.

### Recommendation
Bound `underlyingsRequested` relative to the deposited tranches, e.g. cap it at `amount * virtualPrice(tranche) / ONE_TRANCHE` (queried from `idleCDOEpoch`), or at minimum require `underlyingsRequested <= pendingUnderlyings_SAFE_MAX`. Alternatively drop `pendingUnderlyings` aggregation or make the increment non-reverting (saturating), and consider gating `createWriteOffRequest` behind the same `isWalletAllowed` check used elsewhere.

### Proof of Concept
Foundry fork test following the existing harness in `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol` (mainnet fork block 23032567):

```solidity
function testPendingUnderlyingsOverflowBlocksEscrow() external {
    address attacker = makeAddr("attacker");
    address honestLp = makeAddr("honestLp");

    // give attacker dust tranche tokens and approve escrow
    deal(address(tranche), attacker, 1); // 1 wei
    vm.prank(attacker);
    tranche.approve(address(escrow), type(uint256).max);

    // attacker creates a request asking for max underlyings
    vm.prank(attacker);
    escrow.createWriteOffRequest(1, type(uint256).max);
    assertEq(escrow.pendingUnderlyings(), type(uint256).max);

    // honest lender cannot create any request now: pendingUnderlyings += x overflows
    deal(address(tranche), honestLp, 1000e18);
    vm.startPrank(honestLp);
    tranche.approve(address(escrow), type(uint256).max);
    vm.expectRevert(); // arithmetic overflow in pendingUnderlyings +=
    escrow.createWriteOffRequest(1000e18, 1);
    vm.stopPrank();

    // attacker alone controls unfreeze; request is unfulfillable
    deal(address(underlying), borrower, type(uint128).max);
    vm.startPrank(borrower);
    underlying.approve(address(escrow), type(uint256).max);
    vm.expectRevert(); // cannot pay _underlyings >= uint256.max
    escrow.fullfillWriteOffRequest(attacker, 1, type(uint256).max);
    vm.stopPrank();
}
```
