### Title
Dust APR0 withdraw request permanently bricks `stopEpoch` once APR is non-zero, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0()` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` and the current `unscaledApr != 0` (lines 505-508). Any KYC-passing lender can create a nonzero `apr0TotalPrincipal` with a dust-sized `requestWithdraw` while APR is 0 (lines 285-286 → `_requestWithdrawApr0`, lines 567-577). Because the revert happens before `apr0TotalPrincipal` is cleared (line 540), the bucket survives the failed stop and every subsequent `stopEpoch` reverts as long as APR remains non-zero — freezing all lender principal and matured withdraw receipts held by the CDO/vault until the manager sets APR back to 0 and completes a stop epoch.

### Finding Description
The MySQL CVE-2019-2810 analog is an availability flaw: a crafted input causes a repeatable crash. Here, a crafted state (a dust APR0 pending principal) causes a repeatable revert of the epoch-stop path.

Attack sequence:

1. Pool runs an epoch with `unscaledApr == 0` (APR0 mode, exercised in `test/foundry/IdleCreditVault.t.sol` via `setAprs(0,0)`).
2. Attacker (any KYC'd lender) deposits a dust amount through `depositAA`/`depositBB`, then calls `IdleCDOEpochVariant.requestWithdraw`. Since `unscaledApr == 0` and the pool is not closed, `requestWithdraw` routes to `_requestWithdrawApr0` (IdleCreditVault.sol:285-286), setting `apr0Users[attacker].principal` and incrementing `apr0TotalPrincipal` (lines 571-576).
3. Later, the honest manager sets a non-zero APR via `setAprs`/`setAprsWithBuffer` (lines 206-220) — a routine operation.
4. `stopEpoch` calls `prepareStopEpochWithApr0`. `_principal != 0` passes the fast-path check (line 502), then `unscaledApr != 0` hits `revert NotAllowed()` (lines 506-508). The revert occurs before `apr0TotalPrincipal = 0` (line 540), so state is unchanged.
5. Every subsequent `stopEpoch` reverts identically. The epoch never ends: `epochNumber` never increments, so `_claimFundedWithdrawRequest`'s `epochNumber <= lastWithdrawRequest` gate (lines 326-328) keeps all pending withdrawals unclaimable, active lenders cannot exit (no new request can mature), and borrowed funds plus vault-held funds are locked.

No guard stops this: `requestWithdraw` is permissionless for allowed wallets, the revert is unconditional, and even the attacker cancelling is impossible — `apr0TotalPrincipal` can only be cleared by a successful `stopEpoch` under APR 0. If the manager governance process cannot quickly restore APR 0 (e.g., APR is oracle-driven or the vault is expected to run at non-zero APR permanently), the freeze is effectively permanent.

### Impact Explanation
Temporary-to-permanent freezing of the entire vault TVL and all matured/unmatured withdraw receipts. The cost to the attacker is a dust deposit (which stays recoverable as a receipt) plus gas, while the frozen amount is the full pool NAV plus `pendingWithdraws`. Analogous to the CVE: a cheap input produces a repeatable crash of the core service — here the core service is the epoch state machine that gates all exits.

### Likelihood Explanation
Requires a pool that operates an APR0 period (supported, tested flow) followed by a manager APR increase — a normal operational transition, not an edge case. An attacker can cheaply keep a dust APR0 request open during any APR0 epoch as a dormant trap; the moment APR goes non-zero, the next `stopEpoch` bricks. Manager recovery (set APR to 0, stop, restore APR) is possible but requires diagnosing an undocumented revert cause, so real-world freeze duration is non-trivial.

### Recommendation
Make `prepareStopEpochWithApr0` degrade gracefully instead of reverting: when `unscaledApr != 0` and `apr0TotalPrincipal != 0`, treat the bucket as settled at zero rate (write `apr0RateByEpoch[epochNumber] = 0`, zero `apr0TotalPrincipal`, let `_settleApr0` return principal-only) rather than reverting. Alternatively, sweep stale APR0 principal into `withdrawsRequests` so requesters still receive principal at par.

### Proof of Concept
Foundry fork PoC outline (mirroring `testApr0WithdrawGetsInterestAtStopEpoch` setup in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testApr0DustBricksStopEpoch() external {
    // APR0 mode
    vm.prank(owner); cdoEpoch.setIsAYSActive(false);
    vm.prank(manager); IdleCreditVault(address(strategy)).setAprs(0, 0);

    // Honest liquidity
    idleCDO.depositAA(100_000 * ONE_SCALE);

    // Attacker: dust deposit + APR0 withdraw request
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 1, true);          // 1 wei underlying
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    _startEpochAndCheckPrices(0);

    // Manager legitimately restores a non-zero APR
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(10e18, 10e18);

    // Fund borrower and attempt stopEpoch -> always reverts
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Repeat: still reverts; apr0TotalPrincipal unchanged; all funds frozen
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Existing withdraw requests cannot mature: epochNumber never increments
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();
}
```

Uncertainty note: the exact `stopEpoch` call site for `prepareStopEpochWithApr0` in `IdleCDOEpochVariant.sol` was not fully traced due to iteration limits, but the function is `_onlyIdleCDO`, named for stop-epoch preparation, and tests exercise the APR0 settle path through `stopEpoch`, so it is invoked unconditionally in that flow.
