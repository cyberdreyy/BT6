## Finding: Builder withdrawal double-payment via stale sweep amount (Gloas EIP-7732)

### Title
Concurrent builder pending withdrawal and builder sweep withdrawal can double-count Gwei on the execution layer - (specs/gloas/beacon-chain.md)

### Summary
This is a structural analog of the reported bug: the ERC20 report showed that a value used for a critical downstream computation (total supply → quorum) was computed from a stale/incremental source that didn't reflect a concurrent reallocation of the same underlying balance. In `specs/gloas/beacon-chain.md`, the `get_expected_withdrawals()`/`apply_withdrawals()` pipeline for builders exhibits the same class of bug: the amount credited to the execution layer for a "builder sweep" withdrawal is captured from `builder.balance` at list-construction time, without accounting for a concurrently-processed "builder pending withdrawal" for the *same* builder that will consume part of that same balance in the same block.

### Finding Description
Builder withdrawals are gathered in two independent passes inside `get_expected_withdrawals` (order: builder pending withdrawals, then partial, then builder sweep, then validator sweep) [1](#0-0) .

- `get_builder_withdrawals` copies the *raw, uncapped* `withdrawal.amount` straight from `state.builder_pending_withdrawals` into the `Withdrawal` object that is committed to the execution layer via `payload_expected_withdrawals`: [2](#0-1) 

- The builder-sweep amount (per the withdrawals spec table) is "withdraws full `builder.balance`" — i.e., the value of `state.builders[i].balance` read at list-construction time, before any of the withdrawals gathered in the same list have been applied to state: [3](#0-2) 

- Only afterward, in `apply_withdrawals`, is the *actual* CL-tracked balance decremented, and only there is a `min()` cap applied per-withdrawal against the *live* balance at that point in the sequential loop: [4](#0-3) 

Because the sweep amount is fixed at list-build time using the *pre-deduction* balance, and the pending-withdrawal amount is also fixed independently, if the *same builder* has both (a) a pending withdrawal already queued in `state.builder_pending_withdrawals` and (b) a sweep triggered in the same block (`builder.withdrawable_epoch <= current_epoch` and `balance > 0`), the two `Withdrawal` entries placed into `state.payload_expected_withdrawals` sum to more than the builder's actual balance ever was:

- EL-side total credited = `pending_amount + original_balance`
- CL-side total ever held/deducted = `original_balance`

`apply_withdrawals`'s `min(withdrawal.amount, builder_balance)` only protects the **CL-tracked balance field** from going negative; it does nothing to correct the **already-fixed EL-facing `Withdrawal.amount`** for the sweep entry, which was captured before the pending withdrawal's deduction. The execution layer is required to honor `payload_expected_withdrawals` verbatim (this is exactly the invariant the spec authors call out elsewhere as fragile: "the execution layer mints the full committed amount regardless, any CL-side saturation creates a net supply inflation") [5](#0-4) . That documented risk was reasoned about only for the ordinary validator withdrawal-saturation case; the same mechanism applies to builders when a pending withdrawal and a sweep withdrawal for the same builder land in the same withdrawal batch.

### Impact Explanation
If reachable, this results in Gwei minted on the execution layer that was never backed by the builder's consensus-layer balance — a direct "Gwei created" violation (Critical per the rubric), paid to whichever addresses are named in the two withdrawals (the pending withdrawal's `fee_recipient` and the builder's own `execution_address`).

### Likelihood Explanation
This requires a specific timing: a builder must have an outstanding entry in `state.builder_pending_withdrawals` (from a previously-settled `BuilderPendingPayment`) at the exact block/epoch where its `withdrawable_epoch` sweep condition first becomes true. Builder exit is gated on having no pending balance ("no pending balance to withdraw") at the time the exit request is *submitted* [6](#0-5) , but nothing shown in the retrieved spec text prevents the builder from accepting/being awarded a new bid *after* its exit is queued but before `withdrawable_epoch` is reached, which would create exactly this race. I was not able to fully retrieve the body of `get_builders_sweep_withdrawals` in this session (only the summary table describing its behavior), so I cannot 100% confirm whether it independently excludes builders that already have a pending withdrawal queued in the same batch. This is a genuine limitation of my analysis, not a red herring: if `get_builders_sweep_withdrawals` explicitly skips builders with entries in `builder_pending_withdrawals`, this finding would be moot.

### Recommendation
- Either exclude any builder that has an entry in `state.builder_pending_withdrawals` (or a non-empty pending payment) from `get_builders_sweep_withdrawals` in the same call, or
- Compute the sweep amount from the builder's balance *after* subtracting all pending-withdrawal amounts for that builder already included earlier in the same withdrawal list, so the total credited across the batch can never exceed the builder's actual balance.

### Proof of Concept
Conceptual sequence (pending full verification of `get_builders_sweep_withdrawals`):
1. Builder `B` has `balance = X`. Builder submits/gets a bid; payment settles into `state.builder_pending_withdrawals` with `amount = P` (P < X).
2. Builder `B` initiates exit while it has no pending withdrawal (allowed per the exit-request check), setting `withdrawable_epoch`.
3. Before `withdrawable_epoch`, builder `B` is still "active" and gets another bid awarded that settles into `builder_pending_withdrawals` with amount `P`.
4. At the block where `current_epoch >= withdrawable_epoch`, `get_expected_withdrawals` builds:
   - Builder pending withdrawal: `Withdrawal(address=fee_recipient, amount=P)`
   - Builder sweep withdrawal: `Withdrawal(address=execution_address, amount=X)` (X read before any deduction)
5. `apply_withdrawals` deducts `min(P, X)=P` then `min(X, X-P)=X-P` from `state.builders[B].balance`, correctly zeroing the CL-tracked balance.
6. `payload_expected_withdrawals` sent to the execution layer contains `P + X` total Gwei to mint, while the builder only ever held `X` — `P` extra Gwei is created out of thin air.

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
