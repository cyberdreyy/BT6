### Title
Builder payment `fee_recipient` in `ExecutionPayloadBid` is not verified against the proposer's signed preference at the state-transition level - ([File: specs/gloas/beacon-chain.md])

### Summary
`SignedProposerPreferences` lets a proposer commit, off-chain, to the `fee_recipient` address that should receive a builder's payment for a given slot [1](#0-0) . The gossip layer checks a bid's `fee_recipient` against this signed preference before propagating it [2](#0-1) , but the actual consensus state-transition function that determines block validity, `process_execution_payload_bid`, never performs this check [3](#0-2) . `ProposerPreferences`/`fee_recipient` binding does not appear anywhere in `specs/gloas/beacon-chain.md` at all — only in the validator honest-behavior guide and the p2p gossip-validation rules.

### Finding Description
`process_execution_payload_bid(state, signed_bid)` validates the bid's signature, builder activity/funds, blob-commitment count, slot, parent hash/root, and prev_randao [4](#0-3) , and then unconditionally records a `BuilderPendingPayment`/`BuilderPendingWithdrawal` using `bid.fee_recipient` as the payment destination:

```python
pending_payment = BuilderPendingPayment(
    weight=Gwei(0),
    withdrawal=BuilderPendingWithdrawal(
        fee_recipient=bid.fee_recipient,
        amount=amount,
        builder_index=builder_index,
    ),
    proposer_index=get_beacon_proposer_index(state),
)
``` [5](#0-4) 

There is no assertion anywhere in this function, or anywhere else in `specs/gloas/beacon-chain.md`, that `bid.fee_recipient` equals the `fee_recipient` in the proposer's `SignedProposerPreferences` for that slot. The only place such a check exists is `validate_execution_payload_bid_gossip` in the p2p spec, which is explicitly a network-propagation filter (raises `GossipIgnore`), not a state-transition rule:

```python
# [IGNORE] The bid's fee recipient matches the proposer's preference
if bid.fee_recipient != proposer_preferences.fee_recipient:
    raise GossipIgnore("bid's fee recipient does not match the proposer's preference")
``` [6](#0-5) 

Because gossip validation is a soft, IGNORE-level, off-chain filter (and the builder spec explicitly notes bids "MAY [be obtained] by other off-protocol means" [7](#0-6) ), a block containing a `SignedExecutionPayloadBid` whose `fee_recipient` diverges from the proposer's signed, on-record preference for that slot is fully valid per the state-transition rules. Later, `apply_parent_execution_payload`/`settle_builder_payment` faithfully pays out to whatever `fee_recipient` was cached in `state.latest_execution_payload_bid`, again with no cross-check against the proposer's preference [8](#0-7) .

This is directly analogous to the reported Nextcloud bug: an attacker-controlled destination field (`objectId` in the report, `fee_recipient` here) is checked only by a client/relay-side filter (the mobile app's map-tap handler / the gossip validator) while the authoritative backend (the server's share-processing logic / the beacon state-transition function) applies the value without validating it against the value that was actually intended/committed.

### Impact Explanation
The equality broken is "a builder payment is paid to the fee recipient the proposer committed to for that slot." Since the consensus rules never enforce `bid.fee_recipient == proposer_preferences.fee_recipient`, a builder payment can be paid to an address the proposer never authorized on-chain, i.e. Gwei paid to a non-owner/misdirected recipient — matching the "High" impact category ("a builder payment or withdrawal misdirected"). Since `SignedProposerPreferences` is the only on-protocol mechanism meant to bind payment destination to proposer intent, and it carries no weight in `process_execution_payload_bid`, the guarantee is illusory at the consensus layer.

### Likelihood Explanation
Exploitation requires only that a `SignedExecutionPayloadBid` with a mismatched `fee_recipient` reach block inclusion — either via a bug/omission in an honest validator's bid-selection implementation (which per spec is supposed to enforce this, but the spec itself provides no on-chain backstop), via off-protocol bid delivery (explicitly permitted by `builder.md`), or via any relay/aggregator that does not itself re-derive and check the proposer's preference. No coalition, malicious peer, or client bug outside the spec's own logic is required — this is a pure state-transition validation gap.

### Recommendation
Add an explicit check in `process_execution_payload_bid` (or in `apply_parent_execution_payload`/`settle_builder_payment`) that verifies `bid.fee_recipient` against the block proposer's most recently seen/committed `SignedProposerPreferences` for `bid.slot`, promoting the currently gossip-only "IGNORE" rule to a consensus-level "REJECT" rule so that fee-recipient integrity is enforced by all conforming nodes, not merely by network relays.

### Proof of Concept
1. Proposer `P` for slot `S` broadcasts `SignedProposerPreferences{proposal_slot=S, fee_recipient=A}`.
2. A builder crafts `SignedExecutionPayloadBid{slot=S, fee_recipient=B, value=V, ...}` with `B != A`, satisfying all other assertions in `process_execution_payload_bid` (signature, funds, slot/parent/randao match).
3. This bid is delivered to `P` off-protocol (permitted per `specs/gloas/builder.md`) or slips past a naive relay that does not replicate the gossip fee-recipient check.
4. `P` includes `signed_execution_payload_bid` in the block for slot `S`. `process_execution_payload_bid` accepts it unconditionally with respect to `fee_recipient`, caching `bid` into `state.latest_execution_payload_bid`.
5. On settlement (`apply_parent_execution_payload` → `settle_builder_payment`), the value `V` is queued for withdrawal to `fee_recipient=B`, not `A`, even though the proposer's on-chain-referenced preference committed to `A`. All spec-conformant nodes accept this state transition as valid, since no assertion in `beacon-chain.md` ties `bid.fee_recipient` to `ProposerPreferences.fee_recipient`.

    store: Store,

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid

## Builder activities

Builders have two optional activities: submitting bids and submitting payloads.
Builders can submit bids to produce execution payloads. They can broadcast these
bids in the form of `SignedExecutionPayloadBid` objects. These objects encode a
commitment to reveal an execution payload in exchange for a payment. When their
bids are chosen by the corresponding proposer, builders are expected to
broadcast an accompanying `SignedExecutionPayloadEnvelope` object honoring the
commitment. If a proposer accepts a builder's bid, the builder will pay the
proposer what it promised whether it submits the payload or not.
