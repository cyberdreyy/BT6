### Title
Withdrawal receipt can be haircut more than expected because `requestWithdraw` has no minimum-out parameter - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external finding is the "unbounded owner-set fee" class: `UToken.borrow` computes `fee` from an owner-mutable `originationFee` with no `maxDebt` bound, so a fee increase landing before the user's transaction makes the incurred debt larger than the user agreed to. The direct analog in idle-tranches is `IdleCDOEpochVariant.requestWithdraw`: the withdrawal receipt is reduced by owner-mutable `fee` (performance fee) and `managementFee`, yet the function takes only `_amount` and `_tranche` — no `minUnderlyings`/slippage bound. Once executed, the tranche tokens are burned and the receipt is fixed and irrevocable.

### Finding Description
In `requestWithdraw` (`contracts/IdleCDOEpochVariant.sol:739-791`):

```solidity
uint256 principal = _underlyings;
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;
pendingWithdrawFees += totalFees;
creditVault.requestWithdraw(_underlyings, msg.sender, principal);
_withdrawOps(_amount, principal, _tranche);
```

`_totalWithdrawFees` (`IdleCDOEpochVariant.sol:900-906`) charges `_calculateManagementFee(_principal, _withdrawRequestManagementFeeDuration())` upfront plus performance fee `fee` on net gain via `_netGainAfterFees` (`IdleCDOEpochVariant.sol:889-894`). Both `fee` and `managementFee` are owner/feeReceiver-controlled storage read at execution time, and the management-fee duration itself scales with `epochDuration` and remaining `bufferPeriod` (`IdleCDOEpochVariant.sol:925-930`), parameters the manager also controls via `setEpochParams`. A lender who simulates the call (e.g., via `maxWithdrawable`, `IdleCDOEpochVariant.sol:911-918`) and submits `requestWithdraw` in a public mempool has no way to enforce the quoted amount: if an (honest) owner/manager fee or epoch-duration change is mined first, the user's receipt is minted at the worse terms, tranche tokens are already burned, and `creditVault.requestWithdraw` locks the reduced claim — the same "cost larger than expected, no bound" defect, with the difference that here the loss is realized on exit rather than on debt.

### Impact Explanation
The lender permanently receives `principal + interest - totalFees` computed under the new, higher parameters instead of the quoted ones. The delta is paid out to `feeReceiver` as `pendingWithdrawFees` at the next `stopEpoch`, i.e., a direct, quantified transfer of lender funds to the fee receiver: `loss = (fee' - fee) * netGain / FULL_ALLOC + ΔmanagementFee(principal, duration')`. With a 10,000 USDC position, a performance-fee increase of 10 percentage points on projected interest or a management-fee/duration increase can remove hundreds of USDC from the receipt in a single transaction, and the burned tranche tokens make it irreversible.

### Likelihood Explanation
Requires only ordering: an honest owner/manager fee or `setEpochParams` transaction landing before a pending `requestWithdraw` in the same block. On public mempools (or via builders/backrunning bundles) this is routinely observable; fees are also legitimately changed at epoch boundaries, where withdrawal request volume is highest. No attacker privilege, malformed state, or oracle manipulation is needed — the user simply cannot express a minimum acceptable output. Severity is bounded by fee caps (fees are limited by `FULL_ALLOC`-scaled rates and management-fee rates are protocol-capped), keeping it Medium like the Union finding.

### Recommendation
Add a `minUnderlyings` parameter to `requestWithdraw` (and mirror in `depositDuringEpoch` if fee-sensitive) and revert when `principal + interest - totalFees < minUnderlyings`, analogous to the report's suggested `amount + fee <= maxdebt` check. Alternatively, snapshot the fee/duration parameters at quote time or emit an off-chain-signed fee quote that the request validates.

### Proof of Concept
Foundry fork sketch (pattern follows `test/foundry/IdleCreditVault.t.sol` helpers `_setFeeParams`, `_setManagementFee`, `_transferBurnedTrancheTokens`):

```solidity
function testRequestWithdrawFeeIncreaseSandwich() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // fees quoted: 0% perf, 0% mgmt
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0);
    uint256 trancheAmount = idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    uint256 quoted = cdoEpoch.maxWithdrawable(address(this), address(AAtranche));

    // honest owner's fee update is mined before the user's requestWithdraw
    _setFeeParams(TL_MULTISIG, 10_000, FULL_ALLOC, 0); // 10% perf fee
    _setManagementFee(1_000);                          // 1% mgmt fee

    uint256 requested = cdoEpoch.requestWithdraw(trancheAmount, address(AAtranche));

    assertLt(requested, quoted, "receipt haircut by increased fees, no minOut protection");
    assertGt(cdoEpoch.pendingWithdrawFees(), 0, "delta accrues to feeReceiver");
}
```

The user had no function-level way to bound `requested`; the tranche tokens are burned in `_withdrawOps` and the reduced claim is locked in `IdleCreditVault.requestWithdraw` at `IdleCDOEpochVariant.sol:788-790`.
