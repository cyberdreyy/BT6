### Title
External Initiator credentials allow triggering runs on ANY job ID, not just jobs bound to that initiator - (File: core/web/pipeline_runs_controller.go, core/web/auth/auth.go)

### Summary
`auth.AuthenticateExternalInitiator` (core/web/auth/auth.go) authenticates an External Initiator (EI) using its AccessKey/Secret but then also sets a synthetic `SessionUserKey` with `UserRoleRun`, causing `PipelineRunsController.Create` (core/web/pipeline_runs_controller.go) to treat the EI-authenticated request exactly like a regular user request. The handler never checks that the target job is actually associated with the authenticated EI before calling `RunJobV2`, so any valid EI credential can trigger a run on any job in the node by supplying that job's numeric ID.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered with a combined authenticator chain: [1](#0-0) 

`auth.AuthenticateExternalInitiator` looks up the EI by AccessKey/Secret, verifies the hashed secret, and on success stores the EI under `SessionExternalInitiatorKey`, but crucially **also** stores a fabricated `*clsessions.User{Role: clsessions.UserRoleRun}` under `SessionUserKey`: [2](#0-1) 

`PipelineRunsController.Create` then does the following: [3](#0-2) 

The comment states "only users are allowed to run jobs using int IDs - EIs not allowed," but the actual check is `_, isUser := auth.GetAuthenticatedUser(c)`, which reads whatever object is under `SessionUserKey` — and that key was populated by `AuthenticateExternalInitiator` itself. So an EI-authenticated request satisfies `isUser == true` just as a real user session/token would, and the code proceeds to parse the URL's job ID as `int32` and call `prc.App.RunJobV2(ctx, jobID, nil)` with **no reference at all** to `auth.GetAuthenticatedExternalInitiator(c)` or any check that the job is a webhook job configured with that specific EI's name/ID. There is no ORM lookup that binds the run request to the EI that authenticated it.

As a result, an attacker holding valid AccessKey/Secret for EI A can send `POST /v2/jobs/<any-job-id>/runs` with EI A's headers and successfully trigger `RunJobV2` for a job that belongs to a completely different owner (EI B's job, or any OCR/cron/flux-monitor/direct-request job in the node), because the handler cannot distinguish "authenticated as EI A" from "authenticated as a real run-role user" once past the auth middleware, and it performs zero binding/ownership verification between the credential and the target job ID.

Separately, note that legacy webhook jobs identified by UUID external job ID are explicitly rejected with `job.ErrJobTypeRemoved` (`core/web/pipeline_runs_controller.go:103-107`), which was presumably the mechanism that used to scope EI-triggered runs to a specific webhook spec; its removal, combined with the shared `SessionUserKey` set by `AuthenticateExternalInitiator`, leaves no authorization boundary at all for the surviving int32-ID path.

### Impact Explanation
This is an authorization/request-binding bypass: an unprivileged holder of one EI's low-value webhook credential can force execution of pipeline runs for arbitrary jobs it has no relationship to, potentially triggering on-chain transactions, VRF/OCR/flux-monitor pipeline execution, or other side effects tied to those jobs, and can do so repeatedly for any job ID in the node (a much broader impact than just "EI A hitting EI B's job" — it applies to every job, not only other EIs' webhook jobs). This falls under Chainlink's "unauthorized job run" / role-authorization-bypass bounty class.

### Likelihood Explanation
The only precondition is possessing valid AccessKey/Secret for any single, low-privilege External Initiator registered on the node (these are commonly distributed to third-party services). No admin/edit/run-role user account is needed — the EI's credentials alone satisfy `RequiresRunRole` and the `isUser` check due to the shared `SessionUserKey`. The exploit is a single unauthenticated-relative-to-target-job HTTP POST with a guessed/enumerated integer job ID, fully repeatable, and requires no special conditions.

### Recommendation
- In `PipelineRunsController.Create`, explicitly reject requests authenticated via `AuthenticateExternalInitiator` for the int32-job-ID path (check `auth.GetAuthenticatedExternalInitiator(c)` presence and reject, or check the object type/uniquely tagged flag rather than relying on `GetAuthenticatedUser`).
- Do not have `AuthenticateExternalInitiator` overwrite `SessionUserKey` with a synthetic user; instead give EI-authenticated requests a distinct context key/type so downstream handlers cannot mistake them for genuine user sessions.
- If EI-triggered runs are still a supported feature, reinstate a binding check that verifies the target job's configured external initiator (name/ID) matches the authenticated EI before calling `RunJobV2`.

### Proof of Concept
Handler-level integration test plan (extending `core/web/pipeline_runs_controller_test.go` style):
1. Start an app with two jobs: JobX (any non-webhook job type, e.g., OCR or cron) owned by no EI, and register External Initiator EI-A via `cltest.CreateExternalInitiatorViaWeb`.
2. Build `eia := &auth.Token{AccessKey: eiA.AccessKey, Secret: eiA.Secret}`.
3. Send `POST /v2/jobs/{JobX.ID}/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to EI-A's credentials (using `cltest.UnauthenticatedPost` with those headers, mirroring `TestRunner_WebhookJobRemoved`).
4. Assert current (vulnerable) behavior: response is `201 Created` with a pipeline run resource, and a row appears in `pipeline_runs` for JobX — despite EI-A having no configured relationship to JobX.
5. Expected secure behavior: response should be `401 Unauthorized` or `403 Forbidden`, and `cltest.AssertCountStays(t, app.GetDB(), "pipeline_runs", 0)` should hold.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

func (prc *PipelineRunsController) Create(c *gin.Context) {
	ctx := c.Request.Context()
	respondWithPipelineRun := func(jobRunID int64) {
		pipelineRun, err := prc.App.PipelineORM().FindRun(ctx, jobRunID)
		if err != nil {
			jsonAPIError(c, http.StatusInternalServerError, err)
			return
		}
		res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
		jsonAPIResponse(c, res, "pipelineRun")
	}

	idStr := c.Param("ID")

	// Webhook runs used external job UUIDs; that job type has been removed.
	if _, err := uuid.Parse(idStr); err == nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, fmt.Errorf("cannot run job of type %q: %w", job.Webhook, job.ErrJobTypeRemoved))
		return
	}

	_, isUser := auth.GetAuthenticatedUser(c)
	// only users are allowed to run jobs using int IDs - EIs not allowed
	if isUser {
		// Is it an int32? Then process it regardless of type
		var jobID int32
		jobID64, err := strconv.ParseInt(idStr, 10, 32)
		if err == nil {
			jobID = int32(jobID64)
			jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
			if err != nil {
				jsonAPIError(c, http.StatusInternalServerError, err)
				return
			}
			respondWithPipelineRun(jobRunID)
			return
		}
	}

	jsonAPIError(c, http.StatusUnprocessableEntity, errors.New("bad job ID"))
}
