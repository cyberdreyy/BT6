### Title
Donated underlyings are counted in `getContractValue` then skimmed, booking a phantom loss that is socialized to BB holders - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault.getContractValue()` includes the raw `token` balance held by the vault, while the rest of the credit-vault design (and `_managedContractValue()`) explicitly excludes raw underlyings because unsolicited transfers are meant to be skimmed rather than managed. An unprivileged attacker can send `token` directly to the vault before an accounting interaction, have the donation accounted as real gain (with fees carved out to `unclaimedFees`), and then have those tokens leave the contract via the skim path, so the next `_updateAccounting()` records an equal phantom loss that is absorbed BB-first. This mirrors the sha2 bug class: the NAV computation is correct for the normal input shape (only strategy tokens) but miscomputes for the edge input (unsolicited raw tokens present at accounting time).

### Finding Description
In `IdleCDOCreditVault`:

```solidity
// contracts/IdleCDOCreditVault.sol:125-128
function getContractValue() public override view returns (uint256) {
  return _contractTokenBalance(strategyToken) + _contractTokenBalance(token) - unclaimedFees;
}
```

counts raw `token` balance, whereas `_managedContractValue()` (lines 133-137) and its NatSpec state raw underlyings are "excluded because unsolicited transfers are skimmed on interactions", and `virtualPrice` correctly uses `_managedContractValue()` (lines 172-180).

`_updateAccounting()` (lines 222-249), however, calls `getContractValue()`. So an attacker who transfers `D` tokens directly to the vault just before any deposit/withdraw causes:

1. `nav = lastNAV + D`, so `unclaimedFees += D * fee / FULL_ALLOC` and the remaining `D` is split between AA and BB in `_virtualPriceAux` as a real gain (lines 230-234).
2. The donated tokens are then removed by the skim mechanism (the design assumption at line 131) rather than being credited to `lastNAV`.
3. On the next `_updateAccounting`, `nav = lastNAV - D`, i.e. a phantom loss of `D`, which is routed to `totalBBLoss` up to `lastNAVBB` (lines 330-332). If `D >= lastNAVBB`, `_updateAccounting` reverts `Default()` / triggers `_emergencyShutdown(true)` (lines 240-246).

### Impact Explanation
- BB holders absorb a loss of up to `D` of real NAV that never corresponded to a strategy loss — value is effectively transferred to `unclaimedFees`/skim recipients while BB NAV is written down.
- If `D >= lastNAVBB`, the vault reverts `Default()` on every subsequent deposit/withdraw until the owner/guardian calls `updateAccounting()`, permanently wiping `priceBB` and temporarily freezing all redemptions.

### Likelihood Explanation
Only requires an unprivileged direct token transfer sequenced around any honest deposit/withdraw call; no privileged role, oracle manipulation, or borrower default is needed. The cost is the donated `D`, which is partially recouped through the attacker's own tranche share of the fabricated gain, so the net cost can be low while BB holders bear up to `D` of loss.

### Recommendation
Make `getContractValue()` consistent with `_managedContractValue()` — exclude raw `token` balance (or skim before accounting) so unsolicited transfers cannot enter the gain/loss computation in `_updateAccounting` and `_virtualPriceAux`.

### Proof of Concept
A Foundry fork PoC would: (1) deploy/attach the credit vault with existing AA/BB deposits; (2) `token.transfer(address(vault), D)` from an attacker EOA; (3) trigger a deposit/withdraw so `_updateAccounting` books `D` as gain and increases `unclaimedFees`; (4) let the skim path remove `D`; (5) trigger another interaction and assert `priceBB` dropped (or `Default()` reverts when `D >= lastNAVBB`) while `lastNAVAA` is preserved — demonstrating BB-first absorption of a phantom loss.

*Note: I was unable to fully trace the skim call ordering within deposit/withdraw flows in the available context (the skim logic lives partly in `IdleCDOEpochVariant`), so the exact sequencing in step 3-4 should be confirmed against `IdleCDOEpochVariant`'s entry points; the core inconsistency — `getContractValue` counting raw `token` while the design excludes it — is directly visible in `IdleCDOCreditVault.sol`.*
