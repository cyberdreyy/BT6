### Title
Symlink `Linkname` in tar+zstd extraction is not confined to extraction root - ([File: commands/helpers/archive/tarzstd/tarzstd_extractor.go])

### Summary
`extractor.Extract` validates that the *path of the symlink entry itself* is inside `e.dir` via `filepath.Abs`/`strings.HasPrefix`, but never validates `hdr.Linkname` (the symlink target) before calling `os.Symlink(hdr.Linkname, path)` in the deferred-write loop. A tar entry can therefore create a dangling symlink anywhere in the entry-name namespace whose target points outside the cache/artifact root.

### Finding Description
In `Extract` [1](#0-0) , only `hdr.Name` (joined with `e.dir`) is checked against the `e.dir` prefix. When the header describes a symlink, the code stores it in `deferred[path] = hdr` and later calls `os.Symlink(hdr.Linkname, path)` [2](#0-1) , with `hdr.Linkname` used verbatim — no `filepath.Abs`/prefix check, no traversal (`../`) filtering, no rejection of absolute paths. This confirms the root cause described in the question: the confinement invariant is applied only to the entry's own path, not to the symlink's target.

Comparing to `helpers/archives/zip_extract.go`'s `extractZipSymlinkEntry` [3](#0-2) , that code also does not validate the symlink target, so this is a broader repo pattern, not unique to tarzstd — but the question is scoped to the tarzstd extractor, so the finding stands there.

However, the actual damage is limited to what `os.Symlink` can do: it only creates a dangling symlink; it does **not** write or read through the link. The symlink target (`hdr.Linkname`) is never dereferenced by `Extract` itself. `os.Symlink` does not require the target to exist and performs no writes to the target location. So creating the symlink inside `e.dir` with an out-of-root target does not, by itself, read/write/overwrite any file outside `e.dir` at extraction time.

### Impact Explanation
The concrete impact is limited to planting a dangling symlink under the cache directory whose target (e.g., `/etc/passwd`, `../../secret`) resolves outside the extraction root. This is a real violation of the "File operations must stay within intended build/cache/artifact roots" invariant, but exploitation requires an additional, separate step: some later, unrelated process/job step must open/write to that same path *through* the symlink for the escape to become an actual read/write of an out-of-root file. Whether that composability exists is a separate exploit chain (e.g. via cache re-upload of that same path, or a build step writing to a path under the cache dir) that is not established by this file itself, and the question scope explicitly says "can be exploited by a later write" — i.e., it acknowledges this is a precondition rather than itself the concrete impact.

### Likelihood Explanation
Preconditions are easily met: an unprivileged pipeline author fully controls the tar/zstd cache or artifact contents that Runner's cache-extractor helper consumes on the runner host/container, and can embed arbitrary symlink `Linkname` values. Reaching `Extract` requires no special access beyond normal job execution (cache download flow). The gap is deterministic and not dependent on race conditions.

### Recommendation
Validate `hdr.Linkname` the same way `hdr.Name` is validated: resolve the *effective* target (`filepath.Clean(filepath.Join(filepath.Dir(path), hdr.Linkname))` for relative links, or reject absolute/UNC/drive-letter targets outright) and enforce the `e.dir` prefix check on it before calling `os.Symlink`, failing extraction if the target would resolve outside `e.dir`.

### Proof of Concept
```go
func TestExtract_RejectsSymlinkEscapingRoot(t *testing.T) {
    dir := t.TempDir()
    var buf bytes.Buffer
    zw, _ := zstd.NewWriter(&buf)
    tw := tar.NewWriter(zw)
    _ = tw.WriteHeader(&tar.Header{
        Name:     "evil-link",
        Typeflag: tar.TypeSymlink,
        Linkname: "../../../../etc/passwd", // or absolute path
        Mode:     0777,
    })
    tw.Close()
    zw.Close()

    r := bytes.NewReader(buf.Bytes())
    ext, _ := tarzstd.NewExtractor(r, int64(r.Len()), dir)
    err := ext.Extract(context.Background())

    // Expected (fixed) behavior: extraction fails
    require.Error(t, err)

    // Current (buggy) behavior: no error, and the symlink target
    // resolves outside dir:
    target, _ := os.Readlink(filepath.Join(dir, "evil-link"))
    resolved, _ := filepath.Abs(filepath.Join(dir, target))
    require.False(t, strings.HasPrefix(resolved, dir+string(filepath.Separator)))
}
```
This confirms `hdr.Linkname` is unchecked and the created symlink's target escapes `e.dir`, while `hdr.Name`-based confinement passes.

func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
