Based on my investigation, this is now confirmed: the `RequestDigest` allowlisted on-chain by the workflow owner is derived from the public contents of the vault JSON-RPC request (method, ID, params), and the `RequestReplayGuard` in `authorizer.go` marks that digest as consumed the moment *any* caller submits a matching request to the gateway/DON — before the real submitter's request is authorized.

### Title
Attacker can grief a Vault DON user by front-running their allowlisted request to consume its replay-guard digest - (File: `core/capabilities/vault/authorizer.go`)

### Summary
The `AllowListBasedAuth` flow authorizes a Vault request purely by matching the SHA/keccak-style `req.Digest()` of the *public* JSON-RPC request body against an on-chain allowlist entry created ahead of time by the workflow owner [1](#0-0) . Once authorized, `authorizer.AuthorizeRequest` records that digest in an in-memory `RequestReplayGuard` and rejects any future request with the same digest until it expires [2](#0-1) . Because the digest depends only on public request fields, not on a secret held exclusively by the legitimate submitter, an attacker who observes (or can predict/reconstruct) the exact request contents can submit an identical request to the gateway before the legitimate client does, consuming the digest and permanently rejecting the legitimate client's follow-up as an already-seen replay — directly analogous to the ZeroLend permit-front-running griefing pattern.

### Finding Description
The allowlist auth path treats knowledge of a well-formed request matching a pre-approved digest as sufficient authorization — there is no signature or credential in the request itself binding it to a specific submitter/session; anyone who can send the exact bytes to the gateway can "consume" that authorization [3](#0-2) . The `RequestReplayGuard.CheckAndRecord` call, shared across `AllowListBasedAuth` and `JWTBasedAuth` flows, is a single-shot, first-come-first-served gate keyed only by digest [4](#0-3) , and once a digest is recorded it stays "seen" until its on-chain expiry [4](#0-3) . This is structurally the same root cause as `supplyWithPermit`: a value intended for one-time use by the legitimate actor (the permit signature / the allowlisted digest) can be extracted from a not-yet-finalized submission and "spent" first by an attacker, and the protocol has no fallback/idempotent handling (no equivalent of a try/catch that treats "already authorized" as success for the original submitter) — it just hard-fails with `ErrRequestAlreadySeen`.

### Impact Explanation
An unprivileged attacker who can observe or reconstruct a legitimate user's pending Vault request (e.g., via network visibility into gateway traffic, or because request parameters/IDs are otherwise derivable/predictable) can grief that user by resubmitting the identical request to the gateway/DON first. The legitimate request is then rejected with "request was already authorized previously," denying the user their intended `SecretsCreate`/`SecretsUpdate`/`SecretsDelete`/`SecretsList` operation for the duration of the on-chain allowlist expiry window — a denial-of-service against a specific, targeted user's vault operation, matching the Medium-severity griefing class in the source report.

### Likelihood Explanation
Exploitability depends on the attacker's ability to observe or reconstruct the exact request bytes before the legitimate submission lands (i.e., a front-running/race window on the gateway ingress path). This is plausible if request contents are visible in transit (unencrypted JSON-RPC over the gateway network) or if request IDs/params are predictable, but I could not fully verify from the indexed code whether the gateway transport layer exposes enough timing/visibility for a realistic race in production (e.g., whether gateway-to-DON delivery is single-path and synchronous per request, making a genuine "beat the original to the punch" race feasible). This uncertainty affects confidence in the likelihood, though the code-level lack of any submitter-binding or idempotent conflict handling is confirmed.

### Recommendation
Do not treat "digest already seen" as an unconditional hard failure. At minimum, distinguish between "this digest was already fully processed successfully" (fine to no-op/return success to any caller, since the state change already occurred) and "this digest is currently in-flight" cases, and/or bind authorization to a submitter-specific credential (e.g., include a per-submission nonce/signature check with a legitimate-holder-only secret, similar to recommending try/catch fallback logic in the original ZeroLend fix) so that a race with an attacker's copy of the same public request bytes cannot durably deny the legitimate owner's realized outcome.

### Proof of Concept
Not independently reproduced against a live cluster; derived from static analysis of `allow_list_based_auth.go` and `authorizer.go`/`request_replay_guard.go` showing that `AuthorizeRequest`→`CheckAndRecord` accepts the first caller to present matching request bytes and digest, with no requirement that a caller present a submitter-bound secret uniquely known to the workflow owner. A concrete PoC would require capturing an in-flight legitimate request's JSON-RPC bytes and racing them to the gateway, which I could not execute in this read-only investigation. var ErrRequestAlreadySeen = errors.New("request was already authorized previously")

// RequestReplayGuard prevents replay of already-processed requests by tracking
// request digests with expiry timestamps. It is safe for concurrent use.
//
// Used by both the AllowListBasedAuth flow and the JWTBasedAuth flow to ensure
// that a given request digest is only accepted once.
type RequestReplayGuard struct {
	mu      sync.Mutex
	seen    map[string]int64 // digest → unix expiry timestamp
	nowFunc func() time.Time // injectable for testing
}

// NewRequestReplayGuard creates a replay guard for authorized Vault requests.
func NewRequestReplayGuard() *RequestReplayGuard {
	return &RequestReplayGuard{
		seen:    make(map[string]int64),
		nowFunc: time.Now,
	}
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
