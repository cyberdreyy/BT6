### Title
Unbounded `underlyingsRequested` lets an unprivileged lender inflate `pendingUnderlyings` and expand the borrower's write-off capacity - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` escrows tranche tokens from a lender and adds an arbitrary, caller-chosen `underlyingsRequested` to the global `pendingUnderlyings` counter. The only validations are that the epoch is running and `amount != 0`; there is no bound on `underlyingsRequested` relative to the escrowed tranche amount. The analogous bug class to CVE-2022-26691 is a logic/state-management flaw that lets an unprivileged actor upgrade a request state into an economic privilege: the inflated `pendingUnderlyings` total widens the write-off headroom that `IdleCDOEpochVariant.writeOffDeposit` consults when the borrower extinguishes debt, so the borrower can write off more debt than genuine escrowed demand justifies.

### Finding Description
In `createWriteOffRequest` (contracts/IdleCreditVaultWriteOffEscrow.sol:86-102) the user-supplied `underlyingsRequested` is added verbatim into both `userRequests[msg.sender].underlyings` and the global `pendingUnderlyings` (line 101). A request with `amount = 1 wei` of tranche tokens and `underlyingsRequested = type(uint256).max`-scale value is accepted. Because `deleteWriteOffRequest` (lines 105-116) refunds all escrowed tranches and clamps the `pendingUnderlyings` subtraction (line 112), the inflation is fully reversible and costs the attacker essentially nothing — the tranche tokens are recoverable at any time, even after the borrower acts on the inflated counter.

`fullfillWriteOffRequest` (lines 123-155) itself is safe: a fulfiller must pay `>= currentRequest.underlyings`, so the fake request can never be fulfilled at a loss to anyone inside the escrow. The damage is in the externally visible `pendingUnderlyings` state. `IdleCDOEpochVariant.writeOffDeposit` uses this escrow state as the bound for how much debt the borrower may extinguish by burning tranche tokens; an inflated `pendingUnderlyings` therefore grants the borrower a larger write-off allowance than any lender actually requested — a state-driven elevation of the borrower's write-off privilege, mirroring the "logic issue → elevated privileges" class of the external report.

### Impact Explanation
Broken invariant: loss waterfall / solvency. Debt written off via `writeOffDeposit` reduces the borrower's obligation without a corresponding underlying inflow matched to a real fulfillment; the shortfall is socialized across remaining AA/BB lenders at the next `_updateAccounting`, exactly the bad-debt-escape surface. Loss is bounded by the gap between the inflated `pendingUnderlyings` and the legitimately requested underlyings — attacker-controlled, up to the full outstanding borrower debt given sufficient write-off headroom in `writeOffDeposit`.

### Likelihood Explanation
Attacker requirements are minimal: any KYC-passing lender (or anyone holding a dust amount of tranche tokens during a running epoch — tranche transfers are permissionless ERC20). The sequence is two cheap calls: `createWriteOffRequest(1, X)` then, after the borrower executes `writeOffDeposit` against the inflated `pendingUnderlyings`, `deleteWriteOffRequest()` to recover the tranche. No privileged cooperation is required — the honest borrower simply consumes manipulated state, which is precisely what makes this a logic bug rather than a privileged-role abuse. No existing guard blocks it: `EpochNotRunning` only requires the epoch to be running (normal condition), `NotAllowed` only rejects `amount == 0`, and `pendingUnderlyings` itself has no sanity cap versus escrowed tranche value or vault NAV.

### Recommendation
In `createWriteOffRequest`, bound `underlyingsRequested` by the redemption value of the escrowed tranches — e.g. `underlyingsRequested <= amount * virtualPrice(tranche) / ONE_TRANCHE` — so the request (and hence `pendingUnderlyings`) can never exceed the realizable value of the escrowed collateral. Alternatively, have `writeOffDeposit` account strictly per-fulfillment (tranches actually delivered through `fullfillWriteOffRequest`) rather than against requested-but-unfulfilled `pendingUnderlyings`, and subtract fulfilled requests from the bound immediately.

### Proof of Concept
Foundry fork test (add to `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`):

```solidity
function testInflatePendingUnderlyings() external {
    // setup: epoch running, attacker holds 1 wei of AA tranches
    uint256 dust = 1;
    uint256 hugeAsk = 1_000_000 * ONE_SCALE;

    IERC20Detailed(tranche).approve(address(escrow), dust);

    // attacker inflates the global pending counter at dust cost
    escrow.createWriteOffRequest(dust, hugeAsk);
    assertEq(escrow.pendingUnderlyings(), hugeAsk, "pendingUnderlyings inflated");

    // borrower (honest) now has write-off headroom up to the inflated bound:
    // IdleCDOEpochVariant.writeOffDeposit may extinguish debt up to
    // pendingUnderlyings without any lender ever receiving that underlying.

    // attacker fully recovers the dust after the write-off is executed
    escrow.deleteWriteOffRequest();
    assertEq(IERC20Detailed(tranche).balanceOf(address(this)), dust, "tranches refunded");
}
```

The PoC demonstrates that `pendingUnderlyings` — the state consumed by the debt write-off path — is attacker-controlled at negligible cost, and that the manipulation is fully unwindable afterward, leaving no trace except the excessive write-off the borrower was permitted to perform.

*Uncertainty note:* the precise bounding logic inside `IdleCDOEpochVariant.writeOffDeposit` could not be fully read within this investigation; the finding assumes (consistent with `pendingUnderlyings` being a `public` cross-contract counter whose only external consumer is the CDO's write-off flow) that it bounds borrower write-offs by outstanding escrowed demand. If `writeOffDeposit` instead validates strictly per-fulfilled tranche amounts independent of `pendingUnderlyings`, the impact reduces to a cosmetic accounting inconsistency and this should be downgraded.
