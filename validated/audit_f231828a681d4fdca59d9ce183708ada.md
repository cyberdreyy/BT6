### Title
Unprivileged 'view'-role users can read External Initiator credentials via `/v2/external_initiators` - (File: core/web/router.go)

### Summary
The `GET /v2/external_initiators` endpoint is registered without any role-gating middleware, while the sibling `Create`/`Destroy` endpoints for the same resource require at least the `edit` role. As a result, any authenticated user — including the lowest-privilege `view` role — can enumerate every registered External Initiator's `AccessKey` and `OutgoingToken`, which are authentication credentials, not general-purpose read data.

### Finding Description
In `core/web/router.go`, the External Initiator routes are registered as: [1](#0-0) 

`GET /external_initiators` is wrapped only by `paginatedRequest`, with no `auth.RequiresEditRole`/`auth.RequiresRunRole`/`auth.RequiresAdminRole` wrapper, whereas `POST` (Create) and `DELETE` (Destroy) on the same resource explicitly require `auth.RequiresEditRole`. All three routes still sit inside the `authv2` group, which only enforces that the caller has *some* valid session or token via `auth.Authenticate`, `auth.AuthenticateByToken`, `auth.AuthenticateBySession` — it does not enforce a minimum role: [2](#0-1) 

The role hierarchy is defined in `core/web/auth/auth.go`: `RequiresRunRole`, `RequiresEditRole`, and `RequiresAdminRole` progressively restrict access, with `view` being the lowest role that should be denied any mutating or sensitive read capability: [3](#0-2) 

The `Index` handler for external initiators returns `ExternalInitiatorResource`, which includes `AccessKey` and `OutgoingToken`: [4](#0-3) [5](#0-4) 

`AccessKey` is the identifier used (together with the initiator's secret) in `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers to authenticate as an External Initiator, which `AuthenticateExternalInitiator` maps directly to the `run` role, sufficient to trigger job runs: [6](#0-5) 

This mirrors the reported bug class: a lower-privileged actor (a `view`-role authenticated user, analogous to an "unprivileged registered module") is granted access to data/functions that should be restricted to a higher-privilege tier (`edit`/`admin`), because the access-control check on this endpoint is missing rather than scoped correctly.

### Impact Explanation
A `view`-role user (the least privileged authenticated role in the node, meant only for passive dashboard access) can retrieve the `AccessKey` and `OutgoingToken` for every configured External Initiator on the node. While the incoming secret itself is hashed and not returned by `Index`, disclosure of the `AccessKey` reduces the credential to a single missing secret component, and disclosure of `OutgoingToken` (used to authenticate the node's outbound calls to the initiator) can enable impersonation of the node toward external services relying on that token. This is an authorization/role-model gap causing unintended credential exposure to a low-privilege identity.

### Likelihood Explanation
Likelihood is high for any deployment that has multiple users with differentiated roles (a common operational practice) and has External Initiators configured — any `view`-level API/session user can trivially call `GET /v2/external_initiators` and receive the credential-bearing response with no additional exploitation steps required.

### Recommendation
Wrap the `GET /v2/external_initiators` route with `auth.RequiresEditRole` (or a role at least as restrictive as the `Create`/`Destroy` routes) to match the intended access model, consistent with the report's recommendation of restricting privileged operations to the appropriate caller instead of over-broad access. Additionally, consider excluding `AccessKey`/`OutgoingToken` from list responses entirely and only exposing them once at creation time (as is already done via `ExternalInitiatorAuthentication` in `Create`).

### Proof of Concept
1. Create a user with `view` role (`clsessions.UserRoleView`) and authenticate via session/token.
2. As that user, call `GET /v2/external_initiators?size=50` on the running node.
3. Observe the JSON:API response includes `accessKey` and `outgoingToken` fields for every registered external initiator, as validated by the existing test `TestExternalInitiatorsController_Index`: [7](#0-6) 
4. No role check rejects the `view`-role request, unlike attempting `POST /v2/external_initiators` or `DELETE /v2/external_initiators/:Name`, which return 401/403 for the same user.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
