### Title
External-initiator credentials bypass the "EIs not allowed" restriction and can trigger arbitrary jobs by integer ID - (File: core/web/pipeline_runs_controller.go / core/web/auth/auth.go)

### Finding Description
`PipelineRunsController.Create` gates the integer-ID run path with `isUser` obtained from `auth.GetAuthenticatedUser(c)`: [1](#0-0) . The comment states "only users are allowed to run jobs using int IDs - EIs not allowed," implying `isUser` reliably distinguishes a real dashboard/API user from an external initiator (EI).

That assumption is false. `AuthenticateExternalInitiator` — the auth method used for EI credentials — explicitly stores a synthetic `*clsessions.User{Role: clsessions.UserRoleRun}` under the very same `SessionUserKey` used by real user authentication: [2](#0-1) . Since `GetAuthenticatedUser` simply reads `SessionUserKey` and casts it, [3](#0-2) , an EI-authenticated request also returns `isUser == true`. Consequently the "EIs not allowed" branch is never actually reached for EI callers — they satisfy the `isUser` check exactly like a real user and can supply *any* integer job ID, calling `prc.App.RunJobV2(ctx, jobID, nil)` directly, with no check that the job is a webhook job bound to that EI, or bound to that EI at all: [4](#0-3) .

Note that the specific bypass mechanism suggested in the question (whitespace/zero-padding tricking `uuid.Parse`) is not the actual issue: since `isUser` gates the whole integer-ID block, if `isUser` were truly `false` for EIs, no amount of string manipulation on `idStr` would let execution reach `RunJobV2` — the code falls straight through to the generic "bad job ID" error. [5](#0-4)  The real root cause is upstream: the EI authentication method itself sets `isUser` to `true`, making the "EIs not allowed" gate a no-op for any int-ID request from an EI, with no requirement whatsoever that the job be one the EI is bound to.

### Impact Explanation
An entity holding only external-initiator credentials (not an operator/admin) can trigger execution of arbitrary jobs by integer ID on the node — including jobs that have nothing to do with that EI and were never bound to it. This is an authorization/ownership-binding bypass leading to unauthorized job execution, which can cause unintended on-chain transactions, unwanted external adapter calls, or resource exhaustion depending on job contents — matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Precondition is simply possessing valid EI access-key/secret credentials (`static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`), which is the lowest external-initiator privilege level and does not require any operator/admin access. Any int-ID job on the node is a fully reachable target since no binding check exists on this code path. The exploit is a single HTTP POST and is fully repeatable.

### Recommendation
Do not rely on a shared `SessionUserKey` type between real users and external initiators for authorization decisions. Use `auth.GetAuthenticatedExternalInitiator(c)` (or a dedicated boolean/context flag distinct from the synthetic user role) to positively detect EI-authenticated requests in `PipelineRunsController.Create`, and reject (or properly scope) the integer-ID run path for EIs, consistent with the intended "EIs not allowed" semantics.

### Proof of Concept
Go handler-level integration test plan:
1. Create a node with a non-webhook job (e.g., a Cron or DirectRequest job) with a known int32 ID, not associated with any external initiator.
2. Register an external initiator and obtain its access key/secret.
3. POST to `/v2/jobs/<int-id-of-job>/runs` using only the EI's `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers (no user session/API token).
4. Assert current (vulnerable) behavior: response is `200 OK` with a created pipeline run resource, and `prc.App.RunJobV2` was invoked with the EI's chosen job ID — proving the "EIs not allowed" restriction did not apply.
5. Assert desired/fixed behavior: response should be `401/403` (or `422`) rejecting the EI-authenticated integer-ID request, matching the intended restriction in the code comment.

func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
