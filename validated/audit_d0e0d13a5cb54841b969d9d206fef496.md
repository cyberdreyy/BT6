## Title
Operator/beneficiary that opts out of direct coin transfers can permanently brick `staking_contract` withdrawals for the staker - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`staking_contract::distribute_internal` pays every recipient in the shared `distribution_pool` (staker + operator/beneficiary) via `aptos_account::deposit_coins` inside a single atomic loop. Unlike `vesting::set_beneficiary`, which explicitly requires `assert_account_is_registered_for_apt(new_beneficiary)` before accepting a new beneficiary [1](#0-0) , `staking_contract::set_beneficiary_for_operator` performs no such check [2](#0-1) . If the operator (or the beneficiary it designates) has opted out of unsolicited coin transfers via `aptos_account::set_allow_direct_coin_transfers(false)` and has no registered `CoinStore<AptosCoin>`, every future call that reaches `distribute_internal` will revert, permanently trapping the staker's own unlocked stake.

### Finding Description
`distribute_internal` withdraws all inactive/pending_inactive stake from the pool and then loops through **every** shareholder of the shared `distribution_pool` (which mixes the staker's withdrawal shares and the operator's/beneficiary's commission shares) depositing coins to each recipient in one atomic transaction: [3](#0-2) 

`aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient has no registered `CoinStore` and has disabled direct transfers: [4](#0-3) 

The operator fully controls the recipient of its commission share via `set_beneficiary_for_operator`, which — unlike the vesting module's equivalent `set_beneficiary` — has **no registration check**: [5](#0-4) 

Because `unlock_stake`, `request_commission`, `switch_operator`, `update_commision`, and `distribute` all call `distribute_internal` first to flush any already-inactive stake [6](#0-5) [7](#0-6) [8](#0-7) , once the operator's commission share (non-zero `commission_percentage`) is present in `distribution_pool` and the operator/beneficiary address cannot accept the deposit, **every** one of these entry points aborts — including the staker's own `unlock_stake`/`distribute` calls used to retrieve their own funds. Since Move transactions are atomic, the stake pool state is never actually mutated on abort; the staker's inactive/pending_inactive stake simply becomes permanently unclaimable as long as the operator (or its beneficiary) keeps the direct-transfer opt-out in place with no `CoinStore<AptosCoin>` registered.

Note: this pattern is explicitly acknowledged as a hazard by the framework authors in the `vesting.move` comment ("This is a requirement so distribute() wouldn't fail and block all other accounts from receiving APT if one beneficiary is not registered"), but the equivalent guard was never added to `staking_contract::set_beneficiary_for_operator`.

### Impact Explanation
This produces **permanent lock / non-recoverable loss of claim rights** on the staker's own unlocked/pending_inactive stake — an explicitly listed required impact. The staker chose the operator, but has no control over whether that operator later toggles `set_allow_direct_coin_transfers(false)` on itself or reassigns its beneficiary to an address that refuses direct transfers. Because `distribute_internal` is invoked unconditionally as a side effect of the staker's own withdrawal path, a griefing or extorting operator can permanently freeze the staker's exit from the staking contract, with no admin override or alternate withdrawal path in the module.

### Likelihood Explanation
Reaching this state requires only an operator-controlled action (`aptos_account::set_allow_direct_coin_transfers(false)` on an address with no pre-existing `CoinStore<AptosCoin>`, or routing `set_beneficiary_for_operator` to such an address, gated by the `operator_beneficiary_change_enabled` feature flag). No governance or staker cooperation is needed, and the staker cannot preemptively stop it since the staking-contract flow calls `distribute_internal` on the operator's registered address unconditionally whenever commission is owed. This is realistically triggerable by any operator who is malicious or wants leverage over the staker (e.g., extortion), which is a normal, expected role in this permissionless flow.

### Recommendation
Mirror the `vesting::set_beneficiary` guard in `staking_contract`: require `aptos_account::assert_account_is_registered_for_apt` (or an equivalent "can accept transfer" check) on the operator/beneficiary target inside `set_beneficiary_for_operator`, and/or make `distribute_internal` resilient to a single failing recipient (e.g., skip/queue that recipient's payout instead of aborting the whole distribution), so a stuck operator payout cannot block the staker's own withdrawal.

### Proof of Concept
Conceptual Move test flow (cannot be executed in this environment, but the code paths above support it):
1. Staker creates a staking contract with `commission_percentage > 0` for `operator` via `create_staking_contract`.
2. `operator` calls `aptos_account::set_allow_direct_coin_transfers(operator_signer, false)` while never registering `CoinStore<AptosCoin>` for a chosen beneficiary address (or does so via `set_beneficiary_for_operator` pointing to such an address), gated on `features::operator_beneficiary_change_enabled()`.
3. Stake pool accrues rewards; commission becomes non-zero.
4. Staker calls `unlock_stake` (or `distribute`) to withdraw their own inactive stake.
5. `distribute_internal` reaches the loop over `distribution_pool` shareholders, attempts `aptos_account::deposit_coins` to the operator/beneficiary, hits `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` in `aptos_account.move` L121-130, and the entire transaction — including the staker's own payout — reverts, repeatably, with no recovery path in the module.
