### Title
Unauthenticated `/plugins/:name/debug/pprof/symbol` (and sibling LOOP routes) allow internal plugin-name enumeration via response-code oracle - ([File: core/web/router.go], `loopRoutes`, `core/web/loop_registry.go`, `pluginPPROFPOSTSymbolHandler`)

### Summary
`loopRoutes` is registered directly on the shared `api` router group without any `auth.Authenticate` wrapper, unlike `sessionRoutes` and the `authv2`/`userOrEI` subgroups created inside `v2Routes`. As a result, `POST /plugins/:name/debug/pprof/symbol`, `GET /plugins/:name/metrics`, and `GET /plugins/:name/debug/pprof/*profile` are reachable by any unauthenticated client and return a distinguishable `404` vs proxied `200` depending on whether `:name` matches a registered LOOP plugin.

In `core/web/router.go`, the route setup is: [1](#0-0) 
`debugRoutes`, `sessionRoutes`, and the `authv2`/`userOrEI` groups inside `v2Routes` all wrap their sensitive handlers with `auth.Authenticate(...)` middleware, e.g.: [2](#0-1) [3](#0-2) 

But `loopRoutes` registers its handlers directly on `r` (the same `api` group) with no authentication middleware at all: [4](#0-3) 

The handler `pluginPPROFPOSTSymbolHandler` (in `core/web/loop_registry.go`) looks up `pluginName` in the LOOP registry and returns `404` with the message `plugin "<name>" does not exist` if not found, or proxies the request to the plugin's pprof endpoint and returns `200` with the pprof symbol response if found: [5](#0-4) 

Because there is no authentication gate on this route (compare to `metricRoutes(authv2)` which is deliberately placed behind auth in `v2Routes`, see `core/web/router.go` line 446), an unauthenticated attacker can send `POST /plugins/<guess>/debug/pprof/symbol` requests and observe the `404`/`200`/proxied-response difference to enumerate which LOOP plugin names are registered on the node — internal topology information that should require authentication, matching the pattern the codebase itself applies to `metricRoutes`.

### Impact Explanation
This is an information-disclosure / internal-topology-enumeration issue: an unauthenticated attacker can learn which LOOP plugins (e.g., specific chain adapters/relayers) are running on a node. It does not, by itself, allow authentication bypass, key/secret disclosure, fund movement, or unauthorized job execution — the proxied pprof "symbol" response for an existing plugin only returns generic Go pprof symbol data, not secrets. Scoped impact is limited to plugin-name/topology enumeration via a response-code oracle, a low-severity reconnaissance primitive that could aid a follow-on attack surface mapping exercise.

### Likelihood Explanation
Fully unauthenticated and trivially reproducible: no credentials, tokens, or session are required. The attacker only needs network access to the node's HTTP API and a small dictionary of plugin names to probe. The rate limiter (`rl.Authenticated()`) applies to the whole `api` group but does not prevent the response-code difference from being observed, only throttles request volume.

### Recommendation
Wrap `loopRoutes` registrations with the same `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` middleware used for `authv2` and `metricRoutes`, consistent with how other debug/metrics endpoints (`debugRoutes`, `metricRoutes(authv2)`) are protected, so that plugin existence/topology cannot be probed without valid credentials.

### Proof of Concept
Go handler-level integration test plan (using `web.Router`/`NewRouter` test harness similar to existing `core/web/*_test.go` patterns):
1. Build a test `chainlink.Application` with a `LoopRegistry` containing one registered plugin, e.g. `"median"`.
2. Construct the router via `web.Router(t, app, nil)` without setting any `Authorization`/session cookie.
3. `POST /plugins/median/debug/pprof/symbol` with an empty body — assert response status is `200` (or whatever the proxied/backing pprof call returns, but not `401/403`), proving no auth is required.
4. `POST /plugins/does-not-exist/debug/pprof/symbol` with an empty body — assert response status is `404` and body contains `plugin "does-not-exist" does not exist`.
5. Assert both requests succeeded without any `Authorization` header/session cookie, confirming the distinguishable, unauthenticated oracle described in `pluginPPROFPOSTSymbolHandler` (`core/web/loop_registry.go:168-188`).
6. Repeat for `GET /plugins/:name/metrics` and `GET /plugins/:name/debug/pprof/*profile` to show the same unauthenticated oracle applies to all `loopRoutes` handlers.

func (l *LoopRegistryServer) pluginPPROFPOSTSymbolHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/debug/pprof/symbol", l.loopHostName, p.EnvCfg.PrometheusPort)
	urlVals, timeout := pprofURLVals(gc)
	if s := urlVals.Encode(); s != "" {
		pluginURL += "?" + s
	}
	body, err := io.ReadAll(gc.Request.Body)
	if err != nil {
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "error reading plugin pprof request body: %s", err))
		return
	}
	l.doRequest(gc, "POST", pluginURL, bytes.NewReader(body), timeout, pluginName)
}
