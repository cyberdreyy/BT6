### Title
Missing Slippage/Min-Output Protection in Kamino/Solend/Drift/JupLend Deposit & Withdraw Instructions - ([File: programs/marginfi/src/instructions/kamino/withdraw.rs], [File: programs/marginfi/src/instructions/solend/withdraw.rs], [File: programs/marginfi/src/instructions/kamino/deposit.rs], [File: programs/marginfi/src/instructions/juplend/deposit.rs])

### Summary
The `MultipliVault` finding describes ERC-4626 `deposit()`/`mint()` lacking a user-supplied slippage bound (`minSharesOut` / `maxAssetsIn`), so a direct caller can receive materially fewer shares (or pay more assets) than expected if the exchange rate moves between quote and execution. Marginfi's Kamino, Solend, Drift, and JupLend integration instructions exhibit the same root cause: the on-chain instructions accept only a raw `amount` (in collateral or underlying units) with no caller-supplied minimum-output / maximum-input bound, even though the underlying protocols (e.g. JupLend) natively expose slippage-protected variants (`deposit_with_min_amount_out`) that marginfi does not use.

### Finding Description
`kamino_withdraw` and `solend_withdraw` take `amount` denominated in **collateral tokens**, and the docs explicitly require the caller to pre-compute the corresponding underlying/liquidity amount off-chain using the reserve's *current* exchange rate: [1](#0-0) 

Inside the instruction, the "expected" liquidity amount is computed from the reserve/obligation state read at execution time (not from what the client observed when it built the transaction), and is only checked with a loose tolerance after the CPI: [2](#0-1) [3](#0-2) 

Because the check derives `expected_liquidity_amount`/`collateral_to_liquidity` from the same on-chain state used for the actual conversion, it only guards internal consistency of the CPI, not against the reserve's exchange rate having drifted (via interest accrual, or being pushed by another party) between the time the user/off-chain client computed the `amount` (collateral tokens) they wanted to redeem and the time the transaction actually lands. There is no `min_liquidity_out` parameter the caller can supply to force a revert if the redeemed value falls below their tolerance — exactly the missing control described in the report for `mint()`.

The same gap exists on the deposit side: `kamino_deposit`, `drift_deposit`, and `juplend_deposit` accept only `amount` (underlying) and mint whatever collateral/shares the integration computes, with no `min_shares_out`: [4](#0-3) [5](#0-4) 

Notably, JupLend's own program exposes a slippage-protected `deposit_with_min_amount_out` / `min_amount_out` instruction (visible in the vendored IDL), but marginfi's `juplend_deposit` calls the unprotected `deposit` CPI instead: [6](#0-5) [7](#0-6) 

### Impact Explanation
A user who submits a Kamino/Solend `withdraw` for a given collateral `amount` — after computing the expected underlying payout off-chain using the exchange rate visible at quote time — has no on-chain guarantee about the minimum underlying they will actually receive. If the reserve's exchange rate shifts unfavorably before the transaction lands (interest accrual, oracle/reserve refresh, or any other state change affecting `collateral_to_liquidity`), the withdrawal proceeds and the user receives less value than they intended, with only a "within one token" tolerance check protecting against gross internal inconsistency, not against economically meaningful drift. The same applies in reverse to deposits: shares/collateral minted are whatever the live exchange rate dictates at execution time, with no floor the caller can enforce. This is a direct analog of the `mint()`/`deposit()` slippage issue: value can be lost to the depositor/withdrawer without any way to bound the loss on-chain.

### Likelihood Explanation
Every EOA-driven call to `kamino_withdraw`, `solend_withdraw`, `kamino_deposit`, `drift_deposit`, or `juplend_deposit` is affected, since none of these instructions expose a slippage parameter. The likelihood of the exchange rate moving between off-chain quote and on-chain landing increases with network congestion, high-utilization reserves (fast-accruing interest), or during volatile periods — conditions under which protection is most needed and currently absent.

### Recommendation
Add an optional `min_amount_out` (for withdraws) and `min_shares_out`/`max_amount_in` (for deposits) parameter to each integration instruction (Kamino, Solend, Drift, JupLend), and `require!` that the actual amount transferred/minted meets the caller's bound before finalizing state changes — mirroring the underlying protocols' own slippage-protected entry points (e.g., JupLend's `deposit_with_min_amount_out`). This preserves backward compatibility if the parameter is optional/`None`-default while giving integrators the ability to bound their exposure.

### Proof of Concept
1. Off-chain client reads the Kamino reserve, computes `collateral_amount` needed to redeem `X` USDC using `collateral_to_liquidity`.
2. Client builds and submits `kamino_withdraw(collateral_amount, flags)`.
3. Before the transaction lands, interest accrues (or the reserve is refreshed with a different exchange rate) such that `collateral_to_liquidity(collateral_amount)` at execution time now yields less than `X`.
4. The instruction succeeds, computing a fresh `expected_liquidity_amount` from the *current* (already-drifted) state and validating actual receipts against that drifted value (see `programs/marginfi/src/instructions/kamino/withdraw.rs:192-216`) — the transaction does not fail even though the user receives materially less than the `X` USDC they intended, and there is no parameter available to force a revert on this shortfall.

pub fn kamino_deposit<'info>(
    ctx: Context<'info, KaminoDeposit<'info>>,
    amount: u64,
    refresh_reserve: Option<bool>,
) -> MarginfiResult {
    let refresh_reserve = refresh_reserve.unwrap_or(false);
    let authority_bump: u8;
    {
        let marginfi_account = ctx.accounts.marginfi_account.load()?;
        let bank = ctx.accounts.bank.load()?;
        authority_bump = bank.liquidity_vault_authority_bump;

        validate_asset_tags(&bank, &marginfi_account)?;
        validate_bank_state(&bank, InstructionKind::FailsIfPausedOrReduceState)?;
    }

    // Get initial obligation data to verify deposit amount later
    let initial_obligation_deposited_amount =
        ctx.accounts.integration_acc_2.load()?.deposits[0].deposited_amount;
    let expected_collateral_amount = ctx
        .accounts
        .integration_acc_1
        .load()?
        .liquidity_to_collateral(amount)?;

    if refresh_reserve {
        ctx.accounts.cpi_refresh_reserve()?;
    }

    ctx.accounts.cpi_transfer_user_to_obligation_owner(amount)?;
    ctx.accounts.cpi_kamino_deposit(amount, authority_bump)?;

    let final_obligation_deposited_amount =
        ctx.accounts.integration_acc_2.load()?.deposits[0].deposited_amount;

    // Verifying the deposit was successful by checking obligation balance increased by the correct amount
    let obligation_collateral_change =
        final_obligation_deposited_amount - initial_obligation_deposited_amount;
    assert_within_one_token(
        obligation_collateral_change,
        expected_collateral_amount,
        MarginfiError::KaminoDepositFailed,
    )?;

pub fn juplend_deposit(ctx: Context<JuplendDeposit>, amount: u64) -> MarginfiResult {
    let authority_bump: u8;
    {
        let marginfi_account = ctx.accounts.marginfi_account.load()?;
        let bank = ctx.accounts.bank.load()?;
        authority_bump = bank.liquidity_vault_authority_bump;

        validate_asset_tags(&bank, &marginfi_account)?;
        validate_bank_state(&bank, InstructionKind::FailsIfPausedOrReduceState)?;
    }

    // Refresh the exchange price (interest/rewards) for this slot.
    ctx.accounts.cpi_update_rate()?;

    let expected_shares = {
        let lending = ctx.accounts.integration_acc_1.load()?;
        // Compute expected shares minted (round-down) using the same math as JupLend.
        expected_shares_for_deposit_from_rates(
            amount,
            lending.liquidity_exchange_price,
            lending.token_exchange_price,
        )
        .ok_or_else(|| error!(MarginfiError::MathError))?
    };

    let pre_f_token_balance = accessor::amount(&ctx.accounts.integration_acc_2.to_account_info())?;

    // Move underlying into the vault and deposit into JupLend.
    ctx.accounts.cpi_transfer_user_to_liquidity_vault(amount)?;
    ctx.accounts.cpi_juplend_deposit(amount, authority_bump)?;

    let post_f_token_balance = accessor::amount(&ctx.accounts.integration_acc_2.to_account_info())?;
    let minted_shares = post_f_token_balance
        .checked_sub(pre_f_token_balance)
        .ok_or_else(|| error!(MarginfiError::MathError))?;

    // Exact match required.
    require_eq!(
        minted_shares,
        expected_shares,
        MarginfiError::JuplendDepositFailed
    );
