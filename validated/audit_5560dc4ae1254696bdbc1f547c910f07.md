## Title
`GlobalStateEvaluator::reached_agreement` uses floor division while block-signature consensus uses ceiling, letting a signer accept a global state (protocol version, burn view, tx-replay set) that never actually reached the 70% signing threshold - ([File: libsigner/src/v0/signer_state.rs])

### Summary
The signer's block-signing threshold (`NakamotoBlockHeader::compute_voting_weight_threshold`) rounds the 70% quorum **up** (ceiling), whereas the signer's global-state-machine agreement threshold (`GlobalStateEvaluator::reached_agreement`) rounds the same 70% quorum **down** (floor). These two thresholds are meant to express the same "70% of signer weight" invariant across the codebase, but they diverge by exactly 1 unit of weight whenever `total_weight * 7` is not a multiple of 10 - which is the common case for realistic weight distributions.

### Finding Description
`NakamotoBlockHeader::compute_voting_weight_threshold` computes the minimum weight needed to approve a block using ceiling division: [1](#0-0) 
```
let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
u32::try_from((total_weight * threshold) / 10 + ceil)...
```
This is the value used to gate every actual signature/pre-commit accumulation path in `stacks-signer/src/v0/signer.rs` (`handle_block_pre_commit`, `store_and_process_block_signature`, `store_and_process_block_rejection`) and in block-level consensus verification (`verify_signer_signatures`).

In contrast, `GlobalStateEvaluator::reached_agreement`, which drives `determine_latest_supported_signer_protocol_version`, `determine_global_burn_view`, and `determine_global_state` (including the transaction-replay-set consensus), uses plain floor division: [2](#0-1) 
```
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD) / 10
}
```
There is no `+1`/ceiling adjustment here. For example, with `total_weight = 13` and threshold numerator 7: `compute_voting_weight_threshold` yields `ceil(91/10) = 10`, while `reached_agreement` yields `floor(91/10) = 9`. Any total weight where `total_weight * 7 % 10 != 0` (the vast majority of possible weight totals) produces this same 1-unit gap.

`GlobalStateEvaluator` is not a logging/informational helper - it is the mechanism the signer uses to decide the *global* protocol version, the agreed burn view, and the agreed transaction-replay set that is later used to gate re-validation and re-proposal logic (`handle_pending_update`, `capitulate_viewpoint`, `get_global_tx_replay_set`), as seen at the call sites in `stacks-signer/src/v0/signer.rs`: [3](#0-2) 

Because this threshold silently accepts one weight-unit less than the value that actually corresponds to the intended 70% supermajority, a signer subset that does not truly hold 70% of the signing weight can still cause every honest signer's `GlobalStateEvaluator` to conclude that a specific protocol version, burn view, or transaction-replay set has been "agreed" upon. This mirrors the reported bug class exactly: the intended continuous/consistent 70% threshold is instead implemented as two different step functions that disagree at their boundary.

### Impact Explanation
This falls under the "High" impact category of "acting on a stale reward set/threshold": the signer's local state machine will treat a sub-quorum agreement (as low as `floor(70%)` instead of `ceil(70%)`) as globally binding for protocol version negotiation and, more critically, for the transaction-replay set used to gate which transactions must be replayed after a fork/reorg (`get_global_tx_replay_set`/`tx_replay_scope`). Since the replay set directly constrains which blocks a signer will accept as valid during replay scenarios, an incorrectly "agreed" replay set computed from less-than-actual-quorum weight can cause signers to diverge from the true supermajority's view, weakening the equivocation/consensus guarantees the 70% threshold is supposed to provide.

### Likelihood Explanation
This is deterministic and triggers on essentially every reward cycle whose total signer weight does not divide evenly by 10/7 (i.e., `total_weight * 7 % 10 != 0`), which is the overwhelming majority of real-world weight distributions. It requires no majority collusion to trigger - it is simply present in the arithmetic every time a `GlobalStateUpdate` tally crosses the "floor" boundary but has not yet crossed the "ceiling" boundary that would be required by `compute_voting_weight_threshold`. This makes the divergent-threshold window a a fixed, exploitable gap of exactly one weight unit that recurs constantly, not a rare edge case.

### Recommendation
Change `GlobalStateEvaluator::reached_agreement` (and correspondingly review `reached_disagreement`) to use the same ceiling-rounding formula as `NakamotoBlockHeader::compute_voting_weight_threshold`, ideally by sharing a single canonical threshold function between `stackslib` and `libsigner` so the two can never diverge again.

### Proof of Concept
1. Construct a reward set/signer set with `total_weight = 13` (e.g., weights `[2,2,2,2,2,2,1]`).
2. `NakamotoBlockHeader::compute_voting_weight_threshold(13)` returns `10` (`ceil(91/10)`).
3. Have signers whose combined weight is `9` (< the true block-signing threshold of `10`) submit matching `StateMachineUpdate`s (same protocol version / burn view / tx replay set).
4. `GlobalStateEvaluator::reached_agreement(9)` evaluates `9 >= floor(91/10) = 9` → `true`, so `determine_global_state`/`determine_latest_supported_signer_protocol_version`/`get_global_tx_replay_set` report agreement, even though this weight (`9`) would not be sufficient to actually approve/sign a block (which needs `10`).     pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
