### Title
Frontrunning `lending_pool_emissions_deposit()` Allows Unearned Reward Capture and Dilution of Genuine Depositors - ([File: programs/marginfi/src/instructions/marginfi_group/configure_bank.rs])

### Summary
The original finding describes users frontrunning a permissionless/admin-triggered reward-metadata update (`updateRewardsMetadata()`), depositing/claiming right around the update to capture rewards they should not receive, diluting or double-paying rewards. The closest reachable analog in marginfi-v2 is the permissionless `lending_pool_emissions_deposit` instruction, which instantly and uniformly raises `bank.asset_share_value` for every current depositor the moment it executes. A user can frontrun this call with a large `lending_account_deposit`, capture a pro-rata share of the injected emissions, and withdraw immediately afterward, extracting value from a reward pool intended for durable depositors.

### Finding Description
`lending_pool_emissions_deposit` is a permissionless instruction: any signer can call it to top up a bank's emissions by transferring `amount` of the bank's own mint into the liquidity vault and immediately recalculating `asset_share_value` for **all** current depositors: [1](#0-0) 

The share-value bump is applied instantaneously and uniformly based on `total_asset_shares` at the moment the transaction lands — there is no snapshot, vesting, minimum holding period, or time-weighting of which depositors are entitled to the injected value. Because this is directly analogous to the RewardDistributor case (an externally-triggered update to reward-bearing state that any observer can see coming and race), a user can:
1. Observe (in the mempool) an upcoming `lending_pool_emissions_deposit` call for a bank they don't currently hold a position in (or hold only a small position in).
2. Frontrun it with a large `lending_account_deposit` into that bank.
3. Let the emissions-deposit transaction land, instantly raising `asset_share_value` for their newly-minted shares along with everyone else's.
4. Immediately `lending_account_withdraw` their position, realizing a share of the emissions they contributed nothing to and held for less than one block.

There is no on-chain guard (no flashloan check on this instruction, no minimum deposit duration, no per-depositor snapshotting) preventing this in `LendingPoolEmissionsDeposit`'s account/validation set: [2](#0-1) 

### Impact Explanation
Every existing, genuine depositor's expected share of an emissions deposit is diluted by whatever amount a frontrunner captures via a flash/sandwich deposit-withdraw around the call. This is a direct, exploitable value-redirection: real depositors receive less reward than intended while an opportunistic frontrunner captures reward tokens without providing any genuine liquidity duration. Because `lending_pool_emissions_deposit` is permissionless and its timing/amount is visible on submission, this is reliably repeatable for any bank funded this way, and the loss is durable (share value increase, once applied, is not reversible for the diluted depositors).

### Likelihood Explanation
The instruction is permissionless and callable by anyone funding emissions, so the timing of these deposits is observable on-chain (mempool/simulate), making frontrunning straightforward for a searcher/MEV bot. The attack requires only a deposit + a withdraw around a known/predictable transaction, both of which are simple normal user actions requiring no special privilege — this satisfies the "unprivileged-user analog" requirement of the rules. Likelihood is Medium: it depends on emissions-deposit transactions being both sizeable enough to be worth sandwiching and visible/predictable in advance (similar caveat to the original finding, which the judge also scored as Medium precisely because it depends on external/timing conditions).

### Recommendation
- Consider snapshotting eligible depositor shares (e.g., using `total_asset_shares` and a timestamp anchor) prior to allowing an emissions deposit to affect `asset_share_value`, or applying the increase gradually (streamed) rather than instantaneously, similar to how `bank.emissions_rate` used to accrue emissions over time rather than in a single lump sum.
- Alternatively, require a minimum holding period (e.g., disallow withdrawal in the same slot/transaction as a deposit, or require deposits to season for some duration) before a position becomes eligible for a lump-sum share-value increase from `lending_pool_emissions_deposit`.
- At minimum, document/flag this sandwiching risk for bank admins funding emissions via this instruction so they can mitigate off-chain (e.g., using private relays such as Jito/Flashbots-equivalent to avoid being frontrun, similar to the original report's suggested mitigation).

### Proof of Concept
1. Admin/funder prepares to call `lending_pool_emissions_deposit(bank, amount=X)` for `usdc_bank`, which currently has `total_asset_shares = S` and `asset_share_value = V`.
2. Attacker observes the pending transaction (mempool or predictable schedule) and submits `lending_account_deposit` of a large amount `D` into `usdc_bank` just before it lands, minting `D/V` new shares and increasing `total_asset_shares` to `S' = S + D/V`.
3. `lending_pool_emissions_deposit` executes as shown at [3](#0-2) , computing `updated_total_assets = get_asset_amount(S') + X` and setting `asset_share_value = updated_total_assets / S'`. The attacker's freshly-minted `D/V` shares receive the same proportional bump as long-term depositors.
4. Attacker immediately calls `lending_account_withdraw` to redeem their shares at the new, inflated `asset_share_value`, extracting a portion of `X` proportional to `D`, despite having held the position for effectively zero time and having contributed nothing to earning the emissions.
5. Genuine long-term depositors receive a smaller share of `X` than intended because the attacker's shares diluted the pro-rata split.

**Note:** I was unable to find any test coverage in `programs/marginfi/tests/misc/emissions_deposit.rs` that exercises a deposit-then-immediate-withdraw sandwich around `lending_pool_emissions_deposit`, so I cannot confirm from tests alone whether this exact sequence is explicitly permitted or blocked by some check I did not locate; a Devin session with full repo/test access would be needed to run this exact sequence and confirm the exploit end-to-end.

```rust
pub fn lending_pool_emissions_deposit(
    ctx: Context<LendingPoolEmissionsDeposit>,
    amount: u64,
) -> MarginfiResult {
    if amount == 0 {
        return Ok(());
    }

    let clock = Clock::get()?;
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = ctx.accounts.group.load()?;

    utils::validate_bank_state(&bank, utils::InstructionKind::FailsIfPausedOrReduceState)?;

    // Reject mints with non-zero transfer fees or active transfer hooks.
    let mint_ai = ctx.accounts.mint.to_account_info();
    check!(
        !utils::nonzero_fee(mint_ai.clone(), clock.epoch)?,
        MarginfiError::InvalidTransfer
    );
    check!(
        !utils::has_transfer_hook(mint_ai)?,
        MarginfiError::InvalidTransfer
    );

    let total_asset_shares = I80F48::from(bank.total_asset_shares);
    check!(
        total_asset_shares > I80F48::ZERO,
        MarginfiError::EmissionsUpdateError
    );

    bank.accrue_interest(
        clock.unix_timestamp,
        &group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    transfer_checked(
        CpiContext::new(
            ctx.accounts.token_program.key(),
            TransferChecked {
                from: ctx.accounts.emissions_funding_account.to_account_info(),
                to: ctx.accounts.liquidity_vault.to_account_info(),
                authority: ctx.accounts.depositor.to_account_info(),
                mint: ctx.accounts.mint.to_account_info(),
            },
        ),
        amount,
        ctx.accounts.mint.decimals,
    )?;

    let total_assets = bank.get_asset_amount(total_asset_shares)?;
    let updated_total_assets = total_assets
        .checked_add(I80F48::from_num(amount))
        .ok_or_else(math_error!())?;

    bank.asset_share_value = updated_total_assets
        .checked_div(total_asset_shares)
        .ok_or_else(math_error!())?
        .into();
```

```rust
pub struct LendingPoolEmissionsDeposit<'info> {
    #[account(
        constraint = (
            !group.load()?.is_protocol_paused()
        ) @ MarginfiError::ProtocolPaused
    )]
    pub group: AccountLoader<'info, MarginfiGroup>,

    #[account(
        mut,
        has_one = group @ MarginfiError::InvalidGroup,
        has_one = mint @ MarginfiError::InvalidEmissionsMint,
        has_one = liquidity_vault @ MarginfiError::InvalidLiquidityVault,
        constraint = is_marginfi_asset_tag(bank.load()?.config.asset_tag)
            @ MarginfiError::WrongAssetTagForStandardInstructions,
    )]
    pub bank: AccountLoader<'info, Bank>,

    pub mint: InterfaceAccount<'info, Mint>,

    /// NOTE: This is a TokenAccount, spl transfer will validate it.
    ///
    /// CHECK: Account provided only for funding rewards
    #[account(mut)]
    pub emissions_funding_account: UncheckedAccount<'info>,

    #[account(mut)]
    pub depositor: Signer<'info>,

    #[account(mut)]
    pub liquidity_vault: Box<InterfaceAccount<'info, TokenAccount>>,

    pub token_program: Interface<'info, TokenInterface>,
}
```
