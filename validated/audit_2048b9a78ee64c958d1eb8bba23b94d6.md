### Title
Unbounded JSON-RPC batch requests enable resource-amplification DoS - (File: rpc/src/rpc_service.rs)

### Summary
The validator's public JSON-RPC endpoint is built on `jsonrpc-core`'s `MetaIoHandler`, which natively supports the JSON-RPC 2.0 batch-request feature (a single HTTP POST body containing a JSON array of individually-dispatched calls). Agave configures only a byte-size cap on the HTTP body (`max_request_body_size`) and does not cap the number of calls contained in a batch, the number of distinct expensive methods invoked per batch, or overall per-request compute cost. This is the RPC-layer analog of the reported GraphQL "Alias Overloading" / "Field Duplication" class: an unauthenticated client can pack many expensive, independently-processed operations into one request to multiply server-side work relative to the bytes sent.

### Finding Description
`JsonRpcService::new` builds the handler with `let mut io = MetaIoHandler::default();` and registers the full RPC surface (`rpc_minimal`, `rpc_bank`, `rpc_accounts`, `rpc_accounts_scan`, `rpc_full`) onto it [1](#0-0) . The only guard applied to the HTTP layer is `.max_request_body_size(max_request_body_size)`, where `max_request_body_size` defaults to the `MAX_REQUEST_BODY_SIZE` constant in `rpc/src/rpc.rs` if not overridden by `--rpc-max-request-body-size` [2](#0-1) [3](#0-2) .

`MetaIoHandler` (jsonrpc-core) processes any JSON array top-level payload as a batch: it parses every element as an independent request and dispatches each to its handler within the same HTTP call, all counted against only the byte-size limit, not a request count. Because per-call limits like `MAX_MULTIPLE_ACCOUNTS` are enforced *inside* a single `getMultipleAccounts` call [4](#0-3) , and `getProgramAccounts` has no request-level cap on filters/results (only an optional `scan_results_limit_bytes` for secondary-index scans) [5](#0-4) [6](#0-5) , a client can bypass these per-call ceilings in aggregate by issuing many separate calls (e.g., dozens of `getProgramAccounts`, `getMultipleAccounts`, or `getTokenAccountsByOwner` calls) bundled as one JSON-RPC batch, each running its own bank scan/spawn_blocking task via the shared `rpc_threads`/`rpc_blocking_threads` pool [7](#0-6) .

### Impact Explanation
A single unauthenticated HTTP request can trigger many concurrent expensive bank scans (`get_filtered_program_accounts`, repeated `get_multiple_accounts`, `get_token_accounts_by_owner`, etc.), exhausting the RPC node's blocking-thread pool and consuming disproportionate CPU/memory relative to the small request size — a resource-amplification Denial-of-Service against the RPC surface, directly analogous to GraphQL alias/field-duplication overloading.

### Likelihood Explanation
Low complexity, no privileges required: any client able to reach the JSON-RPC HTTP endpoint (default for RPC-serving validators/full-API nodes) can send a crafted batch payload. Exploitability is bounded only by `max_request_body_size` (bytes), which does not meaningfully limit the number of cheap-to-encode-but-expensive-to-execute calls that fit in a modest payload.

### Recommendation
Add an explicit cap on the number of requests permitted in a single JSON-RPC batch (reject or truncate batches exceeding a configurable maximum, mirroring the `rpc-max-multiple-accounts` pattern), and/or apply per-request-batch cost accounting (e.g., total weight of scan-type calls) before dispatch in `JsonRpcService::new`'s handler construction in `rpc/src/rpc_service.rs`. Consider disabling batch requests entirely on public full-API endpoints if not required by clients.

### Proof of Concept
Send a single HTTP POST to the RPC endpoint with body:
```json
[
  {"jsonrpc":"2.0","id":1,"method":"getProgramAccounts","params":["11111111111111111111111111111111"]},
  {"jsonrpc":"2.0","id":2,"method":"getProgramAccounts","params":["11111111111111111111111111111111"]},
  ... (repeated N times, well within max_request_body_size)
]
```
Each element is independently dispatched by `MetaIoHandler` and executed via `get_filtered_program_accounts`/`spawn_blocking`, multiplying bank-scan load per HTTP request with no batch-count guard in `rpc/src/rpc_service.rs`.

```rust
pub fn service_runtime(
    rpc_threads: usize,
    rpc_blocking_threads: usize,
    rpc_niceness_adj: i8,
) -> Arc<TokioRuntime> {
    // The jsonrpc_http_server crate supports two execution models:
    //
    // - By default, it spawns a number of threads - configured with .threads(N) - and runs a
    //   single-threaded futures executor in each thread.
    // - Alternatively when configured with .event_loop_executor(executor) and .threads(1),
    //   it executes all the tasks on the given executor, not spawning any extra internal threads.
    //
    // We use the latter configuration, using a multi threaded tokio runtime as the executor. We
    // do this so we can configure the number of worker threads, the number of blocking threads
    // and then use tokio::task::spawn_blocking() to avoid blocking the worker threads on CPU
    // bound operations like getMultipleAccounts. This results in reduced latency, since fast
    // rpc calls (the majority) are not blocked by slow CPU bound ones.
    //
    // NB: `rpc_blocking_threads` shouldn't be set too high (defaults to num_cpus / 2). Too many
    // (busy) blocking threads could compete with CPU time with other validator threads and
    // negatively impact performance.
    let rpc_threads = 1.max(rpc_threads);
    let rpc_blocking_threads = 1.max(rpc_blocking_threads);
    Arc::new(
        TokioBuilder::new_multi_thread()
            .worker_threads(rpc_threads)
            .max_blocking_threads(rpc_blocking_threads)
            .on_thread_start(move || renice_this_thread(rpc_niceness_adj).unwrap())
            .thread_name("solRpcEl")
            .enable_all()
            .build()
            .expect("Runtime"),
    )
```
