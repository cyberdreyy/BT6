### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
When a member/key is removed from the multisig (`DeleteMember`/`DeleteKey` action), the contract only purges outstanding *requests that member itself created*. Any confirmation that removed member had already cast on a request created by a different member is left untouched in the `confirmations` set. When later confirmations push the count over `num_confirmations`, the stale confirmation from the now-removed (no-longer-live) member is still counted, so a request can execute with fewer *currently live* member approvals than the configured K-of-N threshold requires.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member` only cleans confirmations for requests where the deleted member was the creator: [1](#0-0) 

It never scans `self.confirmations` to strip that member's confirmation entries from *other* pending requests they had confirmed but did not create. `confirm` then simply counts entries in the stored `HashSet<String>` without re-validating that every entry still corresponds to a current member of `self.members`: [2](#0-1) 

The equivalent code path exists in the legacy `multisig/src/lib.rs`, where `DeleteKey` also filters only requests whose `signer_pk` (the request creator) equals the removed key, leaving stale confirmations by that key on other requests intact: [3](#0-2) [4](#0-3) 

The intended invariant is: `confirmations counted toward threshold == confirmations from members currently in self.members`. Because stale entries are never pruned when membership changes, this equality can be broken — `confirmations counted > confirmations from live members`.

### Impact Explanation
This crosses the threshold-authorization boundary explicitly called out as in-scope ("confirmations counted versus live members"). A pending request can be executed (e.g. a `Transfer` draining funds, or a further `AddKey`/`AddMember` privilege grant) using a mix of live confirmations plus one or more confirmations from members who have since been removed — meaning the request is executed below the *effective, current* threshold of live signers. This is a Critical-tier impact per the rubric: "a multisig request executed below threshold."

### Likelihood Explanation
This requires no attacker-controlled deployment or malicious validator — it's a normal usage sequence available to any unprivileged party who can observe pending requests and confirmations:
1. Request R is created by member A and confirmed by member D (2 confirmations recorded, awaiting 1 more to hit threshold 3).
2. Independently, D is removed from the multisig via a separate, legitimately-approved `DeleteMember` request (e.g., because D's key was compromised, or D left the organization). `delete_member` only removes requests *created* by D — R was created by A, so R and its confirmation set (including D's stale confirmation) survive untouched.
3. A remaining live member (e.g., C) later confirms R. `confirm` sees `confirmations.len() + 1 >= num_confirmations` (A, D-stale, C = 3) and executes R — even though D is no longer a member and did not re-attest after removal.

No special privilege is needed by whoever submits the final confirming transaction; the flaw is purely in state cleanup during `delete_member`/`DeleteKey`.

### Recommendation
When removing a member/key, iterate all pending requests' confirmation sets (not just those created by the removed member) and strip any confirmation entry matching the removed member/key, e.g.:
```rust
for (request_id, mut confirmations) in self.confirmations.iter() {
    if confirmations.remove(&member.to_string()) {
        self.confirmations.insert(&request_id, &confirmations);
    }
}
```
Alternatively, re-validate at `confirm`-time (or at execution time) that every stored confirmation entry still belongs to a current `self.members` entry before counting it toward the threshold, discarding any that don't.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A.add_request(transfer_request)` → creates request `R` (id 0).
3. `A.confirm(0)` → 1 confirmation.
4. `D.confirm(0)` → 2 confirmations (stored: `{A, D}`).
5. Separately, members `A, B, C` create and confirm a `DeleteMember { member: D }` request and it executes — `D` is removed from `self.members`; because `delete_member` only purges requests created by `D` (D created none), request `0`'s confirmations `{A, D}` are untouched.
6. `C.confirm(0)` → `confirmations.len() + 1 == 3 >= num_confirmations`, so `execute_request` runs the `Transfer`, even though only `A` and `C` are live members who actually confirmed after the membership change; `D`'s stale pre-removal confirmation was counted toward a 3-of-4 (now 3-of-3-live) threshold.     fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
