## Finding: Operator beneficiary bypass after `switch_operator` in `staking_contract.move`

### Title
Stale distribution `recipient` bypasses beneficiary redirection after operator switch, misdirecting commission to the old operator's raw address - (`File: aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`distribute_internal` only redirects a distribution-pool payout to an operator's beneficiary when the recorded `recipient` equals the `operator` address passed into the *current* call. `switch_operator`/`switch_operator_with_same_commission` request the old operator's commission (recording `recipient = old_operator` in the shared `distribution_pool`) and then move the `StakingContract` under a new map key (`new_operator`), so any later `distribute` call is invoked with `operator = new_operator`. This breaks the `recipient == operator` equality check for the stale distribution entry, so the payout goes directly to `old_operator`'s own address instead of `beneficiary_for_operator(old_operator)`.

### Finding Description
When commission is requested, `request_commission_internal` records the payout under the operator's own address as the distribution-pool shareholder key, not under the beneficiary: [1](#0-0) 

The beneficiary substitution is deferred to actual payout time, inside `distribute_internal`, and is keyed off the `operator` parameter supplied to that specific call: [2](#0-1) 

`switch_operator` requests commission for the *old* operator (creating/growing a `recipient = old_operator` share in the pool) and then relocates the same `StakingContract` (with its `distribution_pool` still containing that entry) to the `new_operator` key in `store.staking_contracts`: [3](#0-2) 

Any subsequent call to `distribute(staker, new_operator)` invokes `distribute_internal` with `operator = new_operator`. When it iterates the distribution pool and reaches the stale entry whose shareholder key is `old_operator`, the check `if (recipient == operator)` compares `old_operator == new_operator`, which is false, so the beneficiary lookup is skipped entirely and the coins are sent straight to `old_operator`'s own address — even though `old_operator` had explicitly configured `set_beneficiary_for_operator` to route commission elsewhere.

### Impact Explanation
This corrupts operator commission routing: funds intended for the operator's designated beneficiary (often a custodial/compliance address, distinct from the operator's hot key) are instead credited to the operator's own account once the pending commission distribution outlives an operator switch. This matches the "operator commission, beneficiary payout... corruption that credits the wrong account" impact class. The bypass is deterministic and requires no special privileges beyond the staker calling `switch_operator`/`switch_operator_with_same_commission`, an action available to any staking-contract owner.

### Likelihood Explanation
Likelihood is high in practice: any staker who switches operators while the outgoing operator still has a pending (not-yet-lockup-expired) commission distribution — a very normal timing scenario since commission unlocking always needs to wait out the stake pool's lockup — will trigger this. No adversarial coordination is required; it is a straightforward account bookkeeping/timing bug, only requiring that `set_beneficiary_for_operator` was used and a `switch_operator` occurs before the pending commission fully unlocks and is distributed.

### Recommendation
Do not key deferred distributions by the raw operator address. Either:
- Resolve and store the beneficiary at `add_distribution` time (snapshot `beneficiary_for_operator(operator)` as the recipient instead of `operator`), or
- Track distributions per-operator-at-time-of-accrual (e.g., pair `recipient` with the operator identity it was earned under) so `distribute_internal` can correctly redirect to that operator's beneficiary regardless of the `operator` value used in the current call.

### Proof of Concept
1. Staker creates a staking contract with `operator1`, `commission_percentage = 10`.
2. `operator1` calls `set_beneficiary_for_operator(operator1, beneficiary_address)`.
3. Validator earns rewards (`stake::end_epoch()`), generating unpaid commission for `operator1`.
4. Staker calls `switch_operator(staker, operator1, operator2, new_commission_percentage)`. Internally this calls `request_commission_internal(operator1, staking_contract)`, which calls `add_distribution(operator1, staking_contract, operator1, commission_amount)` — recording the pending commission under shareholder key `operator1` — then moves the `StakingContract` to key `operator2` in the map via `stake::set_operator_with_cap` and `staking_contracts.add(new_operator, staking_contract)`.
5. Fast forward past the stake pool's lockup so the requested commission becomes inactive/withdrawable (`stake::fast_forward_to_unlock`).
6. Call `distribute(staker_address, operator2)`. Inside `distribute_internal`, the loop reaches `recipient = operator1`, checks `recipient == operator` where `operator == operator2` — false — so `aptos_account::deposit_coins` sends the commission to `operator1` directly instead of `beneficiary_address`, silently bypassing the beneficiary the operator had configured.

        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );
