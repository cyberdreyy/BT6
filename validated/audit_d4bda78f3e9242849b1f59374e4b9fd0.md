Based on my investigation, I found a genuine analog: workflow names in the gateway's HTTP trigger workflow resolution are identified by only a **10-byte (80-bit) truncated hash**, which is used both for workflow lookup and (per the type's own doc comment) for authorization purposes.

### Title
Workflow identity resolved via a truncated 10-byte name hash allows brute-forceable workflow-name collisions - ([File: core/services/workflows/types/workflow_meta.go])

### Summary
`WorkflowName.Hex()` reduces an arbitrary user-supplied workflow name down to a 10-byte (80-bit) hash via `pkgworkflows.HashTruncateName`, and this truncated value is used as the canonical identifier both when registering workflow metadata onchain/at the gateway and when authorizing/resolving workflow requests from the gateway's public HTTP trigger endpoint. This mirrors the reported Cumulative Merkle Drop bug class: shortening a cryptographic hash for use as an identity/authorization key drastically reduces the collision search space, enabling an attacker who controls their own workflow name to intentionally search for and register a colliding name against a legitimate workflow's owner/tag/name-hash tuple.

### Finding Description
The `WorkflowName` interface's doc comment states explicitly that the hashed name is "used in the metadata we send onchain and for authorizing the workflow with the consumer contract": [1](#0-0) 

The truncation is only 10 bytes (80 bits) as noted by the sibling helper comment `HashedWorkflowName returns first 10 bytes of the sha256(workflow_name)`: [2](#0-1) 

On the internet-facing gateway path, an unprivileged client can trigger a workflow via `WorkflowOwner + WorkflowName + WorkflowTag` instead of a full `WorkflowID`. The gateway resolves the target workflow by re-hashing/truncating the caller-supplied name and looking it up: [3](#0-2) 

The metadata handler also enforces only that the truncated name field has the expected fixed length (`WorkflowNameHashLength`), not that it is a full, uncollided hash: [4](#0-3) 

Because workflow names are user-chosen strings that get compressed into only 80 bits, and the resolution/registration keys off `(owner, nameHash, tag)`, an attacker who wants to target a specific owner/tag pair only needs to brute force an 80-bit space to find an arbitrary string whose `HashTruncateName` output collides with an existing registered workflow's name hash — a search that, while still large, is dramatically weaker than the full 256-bit SHA-256 output, and is analogous in structure to the reported CumulativeMerkleDrop128/160 issue where shortening the hash makes brute-forcing the digest space (rather than the full preimage space) computationally tractable for an adversary with resources.

### Impact Explanation
If an attacker can find/craft a workflow name whose truncated hash collides with a targeted legitimate workflow's name hash (for the same owner and tag, or in scenarios where owner/tag are also attacker-influenced/guessable), the gateway's `resolveWorkflowID` and `WorkflowMetadataHandler.GetWorkflowID`/`Authorize` lookups (keyed by the truncated triple) could resolve to the wrong/attacker-adjacent workflow, or allow an attacker's own maliciously-registered workflow metadata (with attacker-controlled `AuthorizedKeys`) to shadow/collide with a legitimate one in the `workflowRefToID`/`workflowIDToRef` maps, enabling request routing or authorization confusion for HTTP-triggered workflow execution — a cross-user response/authorization confusion class explicitly in scope.

### Likelihood Explanation
Exploitation requires finding a hash collision within an 80-bit space, which is far more expensive than typical online attacks but is meaningfully weaker than the 256-bit collision resistance the rest of the system relies on elsewhere (e.g., `sha256` full-digest usage in `core/services/workflows/artifacts/store.go` `messageID`). This is a design-level shortcut, not a randomly discovered bug, and the same 80-bit truncation is used consistently across gateway workflow registration, HTTP trigger resolution, and onchain consumer-contract authorization, so a successful collision would have broad effect. Practical feasibility depends on available compute (80-bit brute force is still far beyond casual attackers), so likelihood is best characterized as low-to-moderate given today's compute costs, but non-zero and architecturally analogous to the reported issue.

### Recommendation
Do not truncate the workflow name hash for identity/authorization purposes reachable from unprivileged/public interfaces. Use the full-width hash (e.g., full SHA-256, 256 bits) as the canonical workflow-name identifier wherever it participates in authorization decisions (`Authorize`, `GetWorkflowID`, `validateAuthMetadata`), reserving truncation (if required for on-chain storage-size constraints) to purely display/UX purposes, or explicitly document and accept the reduced security margin with additional binding factors (e.g., always requiring exact full `WorkflowID` matches for authorization-sensitive operations rather than owner+name+tag lookups).

### Proof of Concept
Conceptual PoC (not verifiable without executing `pkgworkflows.HashTruncateName`, which lives in the `chainlink-common` dependency, so exact byte-level collision generation could not be confirmed from this repo alone):
1. Attacker registers a workflow under their own owner address with a workflow name `N1`.
2. Attacker computes `HashTruncateName(N1)` and brute-forces alternative strings `N2, N3, ...` until one produces the same 10-byte truncated hash as a target victim's known/guessable workflow name under the same owner/tag scope (feasible due to the reduced 80-bit space compared to full 256-bit hashes used elsewhere in the codebase).
3. Attacker submits an `HTTPTriggerRequest` with `WorkflowOwner`, the colliding `WorkflowName`, and `WorkflowTag` via `resolveWorkflowID` [5](#0-4)  to route to/be authorized against the target's `workflowID` entry.

Note: I could not fully verify the exact collision cost or confirm the underlying `pkgworkflows.HashTruncateName` implementation details (it appears to live outside this repo, in `chainlink-common`), so the practical difficulty of finding a usable 80-bit collision within this specific scheme is not fully confirmed from the indexed code alone.
