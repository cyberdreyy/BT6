## Title
Missing atomic check-and-record in JWT replay-guard allows one-time HTTP-trigger JWT to be used twice via a race condition - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

### Summary
The external report's root cause is a classic check-then-act flaw: `CollateralizedDebt.mint()` performs an external callback before/without atomically finalizing state, letting an attacker re-enter and exploit the gap between the check and the state update. The chainlink analog is `WorkflowMetadataHandler.Authorize`, which is reachable directly from an unprivileged HTTP-trigger client and performs its "already used" replay check and its "mark as used" state update as two separate, non-atomic operations guarded by different locks.

### Finding Description
`Authorize` verifies the caller-supplied JWT, checks whether the JWT's `jti` has already been used via `jwtReplayCache.isReplay`, and only after further authorization checks calls `jwtReplayCache.recordUsage` to mark it as used: [1](#0-0) 

`isReplay` takes an `RLock` and only reads the cache; `recordUsage` takes a separate `Lock` call later: [2](#0-1) 

Because these are two independent critical sections rather than a single atomic "check-and-set," two concurrent `HandleUserTriggerRequest` calls carrying the identical signed JWT (same `jti`, same digest) can both pass `isReplay` (both see "not yet recorded") before either calls `recordUsage`. Both then proceed past `authorizeRequest` in `httpTriggerHandler.HandleUserTriggerRequest`: [3](#0-2) 

This is reachable entirely from an unprivileged workflow-owner client hitting the internet-facing gateway's HTTP trigger endpoint — no node or operator privilege is required, only the ability to send the same signed request twice in a tight race window.

### Impact Explanation
A JWT is meant to be single-use per the code's own comment/tests ("JWT replay protection" / "token has already been used"), which callers rely on as an anti-replay/anti-duplicate-execution guarantee. The race allows a single signed authorization to trigger two independent workflow executions/job runs against the DON shards (`setupCallback`/`sendWithRetries` each proceed independently per request, keyed by the caller-supplied `requestID`, which can differ between the two racing requests while the JWT/digest stays the same only if digest binds to params not requestID — regardless, the authorization gate meant to bound one use of the signed key is bypassed), i.e. an unauthorized/duplicated job run of a workflow execution capability driven purely by client-side timing.

### Likelihood Explanation
Exploitation only requires sending the same previously-obtained signed JWT (which is not secret — it's the very payload transmitted in the client request and readable by anyone observing or replaying it before it's marked used) twice in near-simultaneous requests. This requires no special access, node compromise, or insider position — an ordinary unprivileged workflow client can trigger this by design of the two-step non-atomic pattern, though it does depend on winning a small race window, so it's not deterministic on every attempt.

### Recommendation
Merge the replay-check and record-usage into a single atomic operation under one lock (e.g., a `CheckAndRecord(jti string) error` method on `jwtReplayCache` that takes the write lock once, checks presence, and inserts if absent, returning an error if already present), mirroring the pattern already used in `core/capabilities/vault/authorizer.go`'s `replayGuard.CheckAndRecord`.

### Proof of Concept
1. Register a workflow and authorized signer key as in `TestWorkflowMetadataHandler_Authorize`.
2. Sign a single JWT request (fixed `jti`, digest matching a fixed `params`).
3. Fire two goroutines simultaneously calling `handler.Authorize(workflowID, tokenString, req)` (or two concurrent `HandleUserTriggerRequest` calls with the same token) via `go` + a `sync.WaitGroup`/barrier to force both to pass `isReplay` before either calls `recordUsage`.
4. Observe both calls return success (`err == nil`), demonstrating the same one-time JWT authorized two separate workflow-trigger dispatches instead of the second being rejected with "JWT token has already been used." [1](#0-0) [2](#0-1)

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
```

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
```
