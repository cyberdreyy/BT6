### Title
Fee-on-transfer deposits mint unbacked credit-vault strategy tokens - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCDOCreditVault._deposit` correctly measures the underlying received from the depositor and mints tranche tokens only for the net amount, but it then instructs `IdleCreditVault.deposit` to mint strategy tokens for the original gross amount. For a fee-on-transfer underlying, the strategy receives less than `_amount` yet mints `_amount` strategy tokens and records `_amount` in `totEpochDeposits`, creating unbacked vault shares and potentially preventing `startEpoch` from forwarding the recorded deposit amount. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The CDO snapshots its underlying balance, pulls `_amount` from the depositor, and mints tranche tokens based on the measured balance delta. [4](#0-3)  It subsequently calls `IIdleCDOStrategy(strategy).deposit(_amount)` using the nominal amount rather than the measured received amount. [5](#0-4) 

For the credit-vault strategy, `deposit` pulls `_amount` from the CDO but immediately mints `_amount` strategy tokens without measuring the amount actually received. [6](#0-5)  It also increases `totEpochDeposits` by the gross `_amount`. [7](#0-6) 

For example, if an attacker deposits `100e6` units of a 1% fee-on-transfer token, the CDO mints tranches backed by `99e6`, but the strategy mints `100e6` strategy tokens while holding only `99e6` underlying. [8](#0-7) [9](#0-8)  `startEpoch` then requests `100e6` through `sendInterestAndDeposits`, which the strategy cannot transfer if it holds only the `99e6` received. [10](#0-9) [11](#0-10) 

### Impact Explanation
The invariant that each strategy token is backed one-to-one by underlying principal is broken: `IdleCreditVault.price()` is fixed at `oneToken`, while `deposit` mints one strategy token per nominal deposited unit. [12](#0-11) [13](#0-12) 

The resulting unbacked strategy-token balance inflates `getContractValue`, which directly sums CDO strategy-token and underlying balances. [14](#0-13)  The missing transfer fee is socialized across tranche holders, while `totEpochDeposits` can exceed the strategy’s actual underlying balance and cause `startEpoch` to revert until another party tops up the shortfall. [3](#0-2) [11](#0-10) 

### Likelihood Explanation
The issue requires the vault’s configured underlying token to charge a transfer fee. `token` is an immutable initializer parameter, so this depends on deployment/configuration rather than arbitrary token substitution by the attacker. [15](#0-14)  Once such a vault is configured, any unprivileged depositor can trigger the mismatch through an ordinary `depositAA` call; no privileged or malicious participant is required. [16](#0-15) 

### Recommendation
Do not configure fee-on-transfer assets as vault underlyings unless all deposit layers use received-amount accounting. If support is intended, `IdleCDOCreditVault._deposit` should pass the measured balance delta to `strategy.deposit`, and `IdleCreditVault.deposit` should independently snapshot its underlying balance before and after `safeTransferFrom`, mint strategy tokens and update `totEpochDeposits` only by that received delta. [1](#0-0) [17](#0-16) 

### Proof of Concept
The following Foundry test shape reproduces the accounting mismatch for a configured fee-on-transfer underlying. `FOT_TOKEN`, `CDO`, `STRATEGY`, and `AA_TRANCHE` are taken from the target fork deployment:

```solidity
function testFeeOnTransferMintInflation() public {
    vm.createSelectFork(vm.envString("MAINNET_RPC_URL"));

    IERC20Detailed fot = IERC20Detailed(FOT_TOKEN);
    IdleCDOEpochVariant cdo = IdleCDOEpochVariant(CDO);
    IdleCreditVault strategy = IdleCreditVault(STRATEGY);
    address attacker = makeAddr("attacker");

    uint256 amount = 100e6;
    deal(FOT_TOKEN, attacker, amount);
    vm.prank(attacker);
    fot.approve(CDO, amount);

    uint256 cdoUnderlyingBefore = fot.balanceOf(CDO);
    uint256 strategyUnderlyingBefore = fot.balanceOf(STRATEGY);
    uint256 strategySharesBefore = fot.balanceOf(address(0)); // replace with ERC20(strategy).balanceOf(CDO)

    vm.prank(attacker);
    uint256 trancheShares = cdo.depositAA(amount);

    uint256 cdoReceived = fot.balanceOf(CDO) - cdoUnderlyingBefore;
    uint256 strategyReceived = fot.balanceOf(STRATEGY) - strategyUnderlyingBefore;

    // CDO accounting is net-of-fee.
    assertEq(trancheShares, cdoReceived * 1e18 / cdo.oneToken());

    // Strategy accounting remains gross and is therefore inflated by the transfer fee.
    assertEq(strategy.totEpochDeposits(), amount);
    assertLt(strategyReceived, amount);

    // With no prior buffer, the recorded epoch deposit cannot be forwarded.
    vm.prank(cdo.owner());
    vm.expectRevert();
    cdo.startEpoch();
}
```

The invariant assertions are `strategy.totEpochDeposits() == amount` while `strategyReceived < amount`, and `startEpoch` failing on `sendInterestAndDeposits(amount)` when the strategy has no pre-existing surplus to cover the transfer fee. [17](#0-16) [3](#0-2)

  function deposit(uint256 _amount)
    external
    virtual
    override
    returns (uint256) {
    _onlyIdleCDO();
    if (_amount > 0) {
      underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
      _mint(msg.sender, _amount);
    }

    if (IIdleCDOEpochVariant(idleCDO).isEpochRunning()) {
      // deposit done on stopEpoch (before setting the var to false) so we reset the counter
      totEpochDeposits = 0;
