## Finding: Cross-user callback hijack via unscoped `MessageId` keying in the WebAPI capability handler

### Title
Cross-user response hijack/griefing via attacker-controlled `MessageId` collision in WebAPI trigger callback map - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The Sherlock report describes a VUSD queue griefing bug whose root cause is that a shared, ordered structure (the withdrawal queue) is mutated without any guard tying entries to the correct caller, letting an attacker interleave/overwrite state that belongs to other users. The Chainlink Gateway's `capabilities` handler has an analogous root cause: the `savedCallbacks` map that correlates a node's asynchronous response back to the HTTP caller who submitted it is keyed **only** by the client-supplied `MessageId`, with no per-sender scoping and no collision check, unlike the sibling `RequestCache` implementation which explicitly scopes by `globalId{sender, id}`.

### Finding Description
In `HandleLegacyUserMessage`, the gateway saves the caller's `Callback` under the raw, attacker-chosen `MessageId`: [1](#0-0) 

`MessageId` is populated directly from the untrusted, user-supplied JSON-RPC request `ID` field with no server-side generation and no per-sender namespace: [2](#0-1) 

The only limits enforced are a length cap (200/128 chars); there is no requirement that IDs be unique across different senders/users: [3](#0-2) 

When a node later responds with `MethodWebAPITrigger`, the response is routed purely by `MessageId` lookup, and the entry is deleted and delivered to whichever `Callback` currently occupies that key: [4](#0-3) 

This is the same class of defect as the VUSD bug: a shared mutable structure (the withdrawal queue / here, the `savedCallbacks` map) is updated without any guard binding an entry to the legitimate requester, so a second, attacker-controlled write with the same key clobbers the first. By contrast, the codebase's own `RequestCache` shows the correct pattern by scoping keys with `globalId{sender, id}`: [5](#0-4) 

### Impact Explanation
An unprivileged HTTP client (any caller able to POST to the Gateway's user-facing endpoint) can:
1. Observe or guess a `MessageId` in use by another concurrent, in-flight request (IDs are often short, sequential, or predictable client-generated strings, and there's no uniqueness/collision defense).
2. Submit its own `web_api_trigger` request using that same `MessageId` before the victim's request completes, overwriting `h.savedCallbacks[msg.Body.MessageId]` with the attacker's own `Callback`.
3. When the DON node responds to the (originally victim-initiated) `MessageId`, `handleWebAPITriggerMessage` looks the ID up once, deletes it, and delivers the response to whichever callback is currently stored — the attacker's — resulting in **cross-user response confusion** (the attacker receives a response intended for the victim's triggered workflow) while the victim's original HTTP request silently hangs until the gateway's request timeout fires (`callback.Wait(ctx)`), which is a griefing/DoS of the legitimate caller, directly mirroring the VUSD "lengthen the queue / waste caller resources" impact.

### Likelihood Explanation
Exploitation only requires an ability to call the Gateway's public-facing `web_api_trigger` endpoint with attacker-chosen `id` values and to win a race against another concurrent request with the same or predictable ID — no privileged role or node compromise is required. The lack of per-sender scoping (contrasted with the correctly-scoped `RequestCache`) makes this a straightforward one-line collision, not a complex timing exploit.

### Recommendation
Scope `savedCallbacks` (and the corresponding lookup) by `(sender, MessageId)` instead of `MessageId` alone, mirroring the `globalId{sender, id}` pattern already used in `core/services/gateway/handlers/common/requestcache.go`, and reject/`return error` on ID collision instead of silently overwriting an existing pending callback.

### Proof of Concept
1. Attacker submits `POST /gateway {"id": "X", "method": "web_api_trigger", ...}` — call it request A (victim, real request submitted concurrently by another user with the same client-chosen ID "X").
2. Handler stores victim's callback: `savedCallbacks["X"] = victimCallback`.
3. Before the DON responds to victim's request, attacker submits its own request also with `id: "X"`: `savedCallbacks["X"] = attackerCallback` (overwrites victim entry) — see `HandleLegacyUserMessage`.
4. Node responds for `MessageId "X"` (intended for the victim's original trigger). `handleWebAPITriggerMessage` finds `savedCallbacks["X"] == attackerCallback`, deletes the entry, and delivers the node's response to the attacker.
5. Victim's original HTTP call never receives a response and eventually times out via `RequestTimeoutError` in `gateway.go`'s `ProcessRequest`. [6](#0-5)

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

type globalId struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
