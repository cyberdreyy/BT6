Found a concrete analog: `BlockStatus.responded_signers` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`) uses a single `HashSet<u32>` to gate rejection-weight accumulation, but a separate, independent check (`gathered_signatures.contains_key`) gates acceptance-weight accumulation. A signer can therefore be counted into `total_weight_approved` first and later also counted into `total_weight_rejected` (or vice‑versa) for the same block, since the guard sets are not shared/consistent — this is the same "array/slot not consistently tracked across paths" bug class as the Halborn `user.amount` index-mismatch, just manifesting as a miscounted vote tally instead of a miscomputed reward.

### Title
Signer weight double-counted across acceptance and rejection paths due to inconsistent tracking sets - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` tracks per-block signer responses in `BlockStatus` using two different guard structures: `gathered_signatures` (a `BTreeMap<slot_id, MessageSignature>`) gates whether an *acceptance* adds weight to `total_weight_approved`, while `responded_signers` (a `HashSet<u32>`) gates whether a *rejection* adds weight to `total_weight_rejected`. Because these are separate collections, a single signer slot can have its weight added to `total_weight_approved` via an accept message and later also added to `total_weight_rejected` via a reject message for the *same* block, since `responded_signers` was never touched by the acceptance code path.

### Finding Description
In `handle_signer_messages` (loop starting around line 372) each incoming message for a `slot_id` is processed independently per block: [1](#0-0) 

On `BlockResponse::Accepted`, weight is added to `total_weight_approved` only if `block.gathered_signatures.contains_key(&slot_id)` is false, and then `gathered_signatures` and `responded_signers` are both updated: [2](#0-1) [3](#0-2) 

On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot_id appears in `responded_signers`): [4](#0-3) 

Because the accept path checks `gathered_signatures` (a separate map) rather than `responded_signers`, if a signer first sends an *Accepted* response (adding its weight to `total_weight_approved` and inserting its `slot_id` into both `gathered_signatures` and `responded_signers`) and then sends a *Rejected* response for the same block, the reject path's `responded_signers.insert(slot_id)` returns `false` (already present) — so in that specific order double counting does *not* occur. However, the reverse order is exploitable: if a signer first sends a *Rejected* response (`responded_signers.insert(slot_id)` → `true`, adds to `total_weight_rejected`), then later sends an *Accepted* response for the same block, the accept path only checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` (rejection never touched `gathered_signatures`). This lets the signer's weight be added a second time to `total_weight_approved`, inflating the approved tally beyond what a single signer's honest weight should contribute while its weight also still counts toward `total_weight_rejected`.

This breaks the equality/invariant that `total_weight_approved + total_weight_rejected` should never exceed `total_weight` (the sum of all signer weights) when each signer is counted at most once per side. A single non-cooperating or buggy/malicious signer flipping its vote (reject → accept) for the same block sighash can inflate `total_weight_approved` past the `weight_threshold` using weight that has already been simultaneously attributed to a rejection, i.e. the same slot's weight is present on both sides of the tally used to decide whether the block reaches consensus.

### Impact Explanation
This is a miscounted response: a rejection followed by an "accept" is effectively double counted, letting the coordinator's `total_weight_approved >= self.weight_threshold` check (line 467) fire using inflated weight it should not have accrued, potentially causing the miner/coordinator thread to believe threshold was reached (`cvar.notify_all()`) prematurely or incorrectly relative to the actual number of distinct honest signers who approved. This matches the "rejection recounted as an accept"/miscounted-response class named in scope as a Critical-tier consequence, since it can affect whether the node treats a block as sufficiently signed.

### Likelihood Explanation
Reachable by a single StackerDB participant (one signer slot) sending two ordinary, protocol-valid `BlockResponse` messages (`Rejected` then `Accepted`) for the same `signer_signature_hash` — no majority collusion, no key compromise, and no special access is required beyond normal signer message posting rights, which any registered signer already has.

### Recommendation
Use a single, shared per-slot state machine (or one `HashMap<u32, ResponseKind>`) recording the winning/last response per slot_id, and gate weight additions to both `total_weight_approved` and `total_weight_rejected` off that single structure, removing weight from whichever tally it was previously added to (or disallowing an already-responded slot from flipping) before adding it to the other.

### Proof of Concept
1. Coordinator tracks a `BlockStatus` for a proposed block with `weight_threshold` W and one signer `S` with weight `w`.
2. `S` sends `BlockResponse::Rejected` for the block: `responded_signers.insert(S)` → true, `total_weight_rejected += w`.
3. `S` sends `BlockResponse::Accepted` for the same block: `gathered_signatures.contains_key(&S)` is false (rejection path never touched `gathered_signatures`), so `total_weight_approved += w` is executed, and `S`'s `signature` and slot are added to `gathered_signatures`/`responded_signers`.
4. Now `total_weight_approved` includes `w` from `S` even though `S`'s weight is also counted in `total_weight_rejected`; a single signer's weight has been attributed to both outcomes for the same block, inflating whichever total is checked against `weight_threshold`. [1](#0-0) [4](#0-3)
