## Analysis: griefing `distribute_internal` via a beneficiary that rejects direct coin transfers

I traced the H-8 bug class ("forced settlement/liquidation reverts because a recipient-controlled transfer can be made to abort") to `staking_contract.move`'s shared, atomic distribution flow.

### Root cause chain

`staking_contract::distribute_internal` iterates over **every** shareholder recorded in `staking_contract.distribution_pool` and pays them via `aptos_account::deposit_coins` in a single atomic loop: [1](#0-0) 

`aptos_account::deposit_coins` will **abort** with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient (a) is not yet registered for `AptosCoin` and (b) has explicitly opted out of unsolicited transfers: [2](#0-1) 

The opt-out flag is fully attacker-controlled via `set_allow_direct_coin_transfers`: [3](#0-2) 

Critically, `distribute_internal` is invoked as a mandatory first step of `unlock_stake` and `switch_operator` — the two entry points a **staker** uses to unlock/withdraw or reassign their stake: [4](#0-3) [5](#0-4) 

The **operator**, not the staker, controls who the commission recipient (beneficiary) is via `set_beneficiary_for_operator`, and this beneficiary is credited shares in the very same shared `distribution_pool` used by the staker's unlock/switch/distribute paths: [6](#0-5) [7](#0-6) 

### Why this is analogous to H-8

In H-8, a recipient of a *forced* transfer during settlement could revert, blocking settlement for everyone relying on that transaction. Here, a malicious/negligent **operator** can:
1. Register a fresh, unfunded address `X` and call `set_allow_direct_coin_transfers(X_signer, false)` on it (this requires `X` to exist and sign, but does **not** require `X` to ever hold or register `AptosCoin`).
2. Call `set_beneficiary_for_operator(operator, X)`.
3. Once any commission accrues for the operator (via `request_commission` or automatically inside `add_distribution`/`unlock_stake`), `X` becomes a shareholder with a nonzero balance in `distribution_pool`.
4. From that point on, **every** call to `distribute`, `unlock_stake`, or `switch_operator` for that staker/operator pair will hit `distribute_internal`'s payout loop, attempt to pay `X`, and abort — reverting the entire transaction, including the staker's own unlock/withdraw logic.

Because the staker cannot alter the operator's beneficiary (only the operator can via `set_beneficiary_for_operator`), this can permanently strand the staker's principal in the stake pool: they can no longer call `unlock_stake` (to move active stake to pending_inactive) or `switch_operator` (to move away from the malicious operator), since both unconditionally trigger the poisoned `distribute_internal`.

I was unable to fully verify one boundary condition within this session: whether `coin::is_account_registered<AptosCoin>` under the FA-migrated `coin.move` module could independently return `true` for an account that merely exists (e.g., because primary-store-based gas payment implicitly creates a registered store), which would neutralize the attack by bypassing the `can_receive_direct_coin_transfers` check entirely. The `coin.move` definition of `is_account_registered` was not retrieved before the iteration budget ran out, so this exact precondition — whether an attacker can create a signer-capable account with a `DirectTransferConfig` opt-out *without* also registering it for `AptosCoin` — needs to be confirmed against `coin::is_account_registered` and `primary_fungible_store` semantics before treating this as a fully proven, high-severity finding.

### Title
Operator-controlled beneficiary can permanently DoS a staker's `unlock_stake`/`switch_operator` calls by rejecting direct coin transfers - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`distribute_internal` pays out every shareholder in `staking_contract.distribution_pool`, including the operator's beneficiary, inside the same atomic call used by `unlock_stake` and `switch_operator`. If the operator sets an unregistered beneficiary address that has opted out of direct coin transfers, all future calls to these functions revert, since `aptos_account::deposit_coins` aborts on that recipient.

### Finding Description
`distribute_internal` loops over `distribution_pool.shareholders()` and calls `aptos_account::deposit_coins(recipient, ...)` for each one [1](#0-0) , unconditionally, with no per-recipient error handling — a single failing deposit reverts the whole transaction. `deposit_coins` aborts if the target is unregistered for the coin type and has disabled direct transfers [2](#0-1) , a setting fully controlled by the target account itself [3](#0-2) . Since `set_beneficiary_for_operator` lets the operator route their commission to an arbitrary address [6](#0-5) , and `unlock_stake`/`switch_operator` both call `distribute_internal` before doing anything else [4](#0-3) [5](#0-4) , an operator can weaponize this to block the staker.

### Impact Explanation
If proven, this would allow an operator to strand a staker's principal by making unlock/switch-operator unusable, which falls under "permanent lock or non-recoverable loss of claim rights in stake ... flows." This would be high severity if the precondition (attacker can opt out of direct transfers without ever registering `AptosCoin`) holds.

### Likelihood Explanation
Requires the operator to deliberately misconfigure their beneficiary — an intentional griefing action rather than an accidental one, and is gated on an unverified precondition about the FA-migrated coin registration semantics.

### Recommendation
Verify whether `is_account_registered<AptosCoin>` can be `false` for a signer-capable, `DirectTransferConfig`-holding account under the current FA migration. If so, `distribute_internal` should isolate per-recipient payout failures (e.g., via a resumable/queued withdrawal per shareholder) instead of aborting the entire distribution atomically, so one poisoned beneficiary cannot block unrelated shareholders.

### Proof of Concept
Not executed — this requires confirming the `coin::is_account_registered<AptosCoin>` behavior for a freshly created signer account before a concrete repro can be written; recommend a Devin session with Move test execution to (1) create account `X`, call `set_allow_direct_coin_transfers(X, false)` without registering AptosCoin, (2) set `X` as operator beneficiary, (3) accrue commission, and (4) confirm `unlock_stake`/`switch_operator` abort thereafter.

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }

    /// Return true if `account` can receive direct transfers of coins that they have not explicitly registered to

    /// By default, this returns true if an account has not explicitly set whether the can receive direct transfers.
    public fun can_receive_direct_coin_transfers(
        account: address
    ): bool acquires DirectTransferConfig {
        !exists<DirectTransferConfig>(account)
            || borrow_global<DirectTransferConfig>(account).allow_arbitrary_coin_transfers
