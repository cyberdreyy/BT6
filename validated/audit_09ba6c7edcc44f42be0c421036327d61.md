### Title
Signer protocol v1 permits double-signing two conflicting tenure-change blocks in the same tenure - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`v1.rs::validate_tenure_change_payload` checks for a duplicate tenure-change block using `get_last_globally_accepted_block`, which returns `None` for a block that is only `LocallyAccepted` (i.e., already signed by this signer but not yet observed as processed by the node). This lets a v1 signer sign a second, different tenure-change block for the same tenure while its first signature is still only locally accepted, breaking the "one signed block per tenure/height" invariant.

### Finding Description
The proposal-time duplicate-tenure-change guard exists specifically to stop a signer from signing two different tenure-change blocks for the same tenure. In v2 this check uses `get_last_signed_block`, which matches on any state with a signature (`GloballyAccepted` or `LocallyAccepted`): [1](#0-0) 

The v1 equivalent uses `get_last_globally_accepted_block` instead: [2](#0-1) 

`get_last_signed_block` explicitly matches both `GloballyAccepted` and `LocallyAccepted` states, while `get_last_globally_accepted_block` (used by v1) only matches the fully-globally-accepted state: [3](#0-2) 

The repository itself documents this exact defect as a fixed regression for v2, with a dedicated regression test explaining that the old check (`get_last_globally_accepted_block`) "would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change": [4](#0-3) 

That fix was applied only to v2; v1 still contains the vulnerable pattern.

The only other backstop that could catch this at pre-commit time is the "own-tenure" conflict guard in `handle_block_pre_commit`, which is explicitly documented as blind in exactly this window (before the node has caught up): [5](#0-4) 
This guard only refuses to sign if the node's own `get_tenure_tip` for that consensus hash already shows a height ≥ the new proposal — i.e., if the first (only-locally-accepted) block has not yet been observed by the node, this guard falls through and lets the signer sign the second conflicting block, exactly the gap `docs/signer-flows.md` calls out as covered "only" by this branch, which itself depends on node visibility, not signer-side signed state. [6](#0-5) 

### Impact Explanation
A v1 signer can produce valid signatures over two different, conflicting tenure-change blocks for the same tenure (a genuine equivocation): first over block A (reaching `LocallyAccepted`, i.e., `signed_self` set, but not yet pushed to/observed by the node), then, because the duplicate check at proposal time for block B only looks at global acceptance, over block B as well, provided the node's tenure tip hasn't advanced past A when B reaches the pre-commit threshold. This is a Critical-class break per the stated rubric: "a signer signing an invalid, non-canonical, or conflicting block." If enough signers hit this same window, both blocks could independently accumulate the 70% threshold, producing two competing signed chains built on the same tenure.

### Likelihood Explanation
This requires only a single miner (or gossip of a re-proposed tenure-change block for the same tenure) plus normal network/processing latency between "signed by enough signers to be locally accepted" and "pushed to and observed by the node" — no majority-signer collusion, no other signer's key, and no auth_token access is needed. The repo's own test suite demonstrates the underlying race is realistic enough to have warranted a regression test — just only for the v2 code path, leaving v1 exposed to the same condition.

### Recommendation
Change `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` to use `SignerDb::get_last_signed_block` (as v2 does) instead of `get_last_globally_accepted_block`, so that a locally-signed (not yet globally accepted) tenure-change block also blocks a duplicate tenure-change proposal at proposal time, closing the same window v2 already closes.

### Proof of Concept
1. Miner proposes tenure-change block A for tenure X at height H; enough signers (running v1) sign it, reaching `LocallyAccepted` (`signed_self` set) before the block is pushed to/observed by the node.
2. Before the node processes/reports block A, the miner (or a stale re-proposal) sends tenure-change block B, also for tenure X at height H, with a different `signer_signature_hash`.
3. On a v1 signer: `handle_block_proposal` → `check_block_against_state` → `check_block_against_local_state` → `validate_tenure_change_payload` calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` [7](#0-6)  — returns `None` because A is only `LocallyAccepted`, so B is *not* rejected as `DuplicateBlockFound`.
4. B is submitted for node validation and, if it validates, proceeds to pre-commit. When B reaches the pre-commit threshold, `handle_block_pre_commit`'s own-tenure conflict check queries `get_tenure_tip(X)`; if the node still hasn't observed A (tip height < H), the conflict does not block, and the signer signs B [8](#0-7) .
5. The signer has now put a valid signature over two different, conflicting tenure-change blocks (A and B) for the same tenure X — an equivocation that v2's fix (`check_tenure_change_rejects_when_locally_accepted_block_exists`) specifically prevents but v1 does not.

Two things belong to the proposal path only and are **not** re-run at validate-ok
or at signing:

- `validate_tenure_change_payload` rejects with `DuplicateBlockFound` when we
  have already accepted a block in the tenure a tenure-change block is starting.
  v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1
  counts only globally accepted ones (`get_last_globally_accepted_block`).
- the v2 `check_proposal` wrapper checks miner pubkey hash, consensus hash, the
  pox bitvec, and tenure-extend rules before delegating here.

Because the duplicate check never runs again, a block that crosses the pre-commit
threshold long after it was proposed relies on section 5's own-tenure conflict
guard to cover the same ground.
