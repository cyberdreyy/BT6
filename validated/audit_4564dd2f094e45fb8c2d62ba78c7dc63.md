### Title
Unprivileged front-running/squatting of any `owner_account_id`'s deterministic lockup address via `LockupFactory::create` - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the lockup account id deterministically from `sha256(owner_account_id)[..20]` and lets *any* caller who attaches `MIN_ATTACHED_BALANCE` deploy a `LockupContract` there with attacker-chosen `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration` and `staking_pool_whitelist_account_id`, with no check binding the call to the real grantor or to any prior reservation. Because NEAR account creation is one-shot, whoever calls `create` first for a given `owner_account_id` permanently occupies that address with their own parameters, preventing the legitimate sponsor from ever deploying the intended lockup terms there.

### Finding Description
The broken binding: `LockupArgs` stored at `sha256(owner_account_id)[..20].<factory>` should equal the `LockupArgs` the legitimate/intended creator of `owner_account_id`'s lockup would send. In the current code this equality is not enforced by anything — it depends purely on transaction ordering.

`create` computes the account id solely from the hash of `owner_account_id`: [1](#0-0) 

There is no check that `env::predecessor_account_id()` is related to `owner_account_id`, no check that the vesting/duration parameters were pre-approved by anyone, and no reservation mechanism analogous to the staking-pool-factory's `self.staking_pool_account_ids.insert(...)` guard: [2](#0-1) 

The lockup factory has no equivalent set/registry check before issuing `Promise::new(lockup_account_id).create_account().deploy_contract(CODE.to_vec()).transfer(...).function_call(b"new", LockupArgs{...})`: [3](#0-2) 

Attacker exploit flow:
1. Attacker learns/decides `victim.near` will eventually receive a lockup (grant recipients are typically known/public well before funding).
2. Attacker calls `create(owner_account_id='victim.near', lockup_duration=<attacker-chosen>, vesting_schedule=<attacker-chosen or None>, release_duration=<attacker-chosen>, whitelist_account_id=<attacker-controlled contract>)` attaching exactly `MIN_ATTACHED_BALANCE`.
3. Because the target `lockup_account_id = hex::encode(sha256('victim.near')[..20]).<factory>` does not yet exist, `create_account()` succeeds, `CODE` is deployed, and `new` is invoked with the attacker's `LockupArgs`.
4. `on_lockup_create` sees `is_promise_success() == true` and simply logs success — it performs no comparison against any expected/intended `LockupArgs`: [4](#0-3) 
5. When the real sponsor later calls `create` with the correct, foundation-approved parameters for `victim.near`, `create_account()` on an already-existing account id fails at the protocol level, the whole promise batch fails, and `on_lockup_create` (`is_promise_success() == false`) simply refunds the deposit to the real sponsor — the legitimate lockup is never deployed at the canonical address: [5](#0-4) 

No existing guard (`assert_owner`, `assert_self`, `is_promise_success`, etc.) prevents this because the vulnerability is not a state-corruption bug inside a single call — it's the complete absence of any authorization/reservation binding `owner_account_id` to a specific, approved `LockupArgs` before the one-shot deployment happens.

### Impact Explanation
This directly matches the listed Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." The attacker permanently squats `victim.near`'s canonical lockup address with self-chosen `lockup_duration`, `vesting_schedule`/`release_duration`, and `staking_pool_whitelist_account_id` (which could point to an attacker-controlled "whitelist" contract that would later be used to whitelist an attacker-controlled staking pool for `victim.near`'s funds, though the funds themselves are only those the attacker deposited unless/until the real grantor is misled into topping up the squatted contract, believing it is their legitimate lockup). The real sponsor's subsequent `create` call fails and is refunded, so the intended grant/vesting terms for `victim.near` can never be deployed at the expected address, blocking the whole grant program. This is repeatable across any not-yet-created `owner_account_id`, so any known future grant recipient can be squatted by an attacker paying only ~3.5 NEAR per victim.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controllable: the attacker only needs to know (or guess) a future `owner_account_id` that will receive a lockup — grant recipients are frequently public knowledge or predictable (e.g., known team/employee accounts, sale participants) before the foundation/sponsor actually funds the lockup — and attach `MIN_ATTACHED_BALANCE` (3.5 NEAR) in a normal transaction to the public `create` method. No special role, key, or timing advantage beyond simple transaction ordering is required, making this practically exploitable and repeatable against many victims for a bounded, low per-attempt cost.

### Recommendation
Add an authorization/reservation mechanism to `LockupFactory::create`, e.g.:
- Require `env::predecessor_account_id() == owner_account_id` or restrict `create` to `self.foundation_account_id` for the initial deployment, or
- Maintain a `LookupSet<AccountId>` of reserved `owner_account_id`s (populated by the foundation) analogous to staking-pool-factory's `staking_pool_account_ids`, and assert the reservation/approved parameters before deploying, or
- Require a foundation-signed approval (e.g., a hash of the intended `LockupArgs` signed/whitelisted beforehand) that `create` must match before deployment.

### Proof of Concept
```rust
#[test]
fn test_attacker_squats_owner_lockup_address() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker calls create() first for victim.near with attacker-chosen params
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = MIN_ATTACHED_BALANCE;
    testing_env!(context.clone());
    let attacker_promise = contract.create(
        victim_account_id(),          // owner_account_id = "victim.near"
        WrappedDuration::from(1u64),  // attacker-chosen: near-zero lockup_duration
        None,
        None,                          // no vesting, so victim never gets vesting protection
        None,
        Some(attacker_whitelist_account_id()), // attacker-controlled whitelist
    );

    // Simulate successful deployment
    context.predecessor_account_id = account_factory();
    context.attached_deposit = 0;
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let created = contract.on_lockup_create(
        victim_lockup_account(),
        MIN_ATTACHED_BALANCE.into(),
        String::from("attacker.near"),
    );
    assert!(created);

    // Real sponsor later tries to create the legitimate lockup for victim.near
    context.predecessor_account_id = String::from("real_sponsor.near");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        victim_account_id(),
        real_lockup_duration(),        // real, foundation-approved duration
        None,
        Some(real_vesting_schedule()), // real vesting schedule
        None,
        None,
    );

    // Because the account already exists, promise fails -> refund, real lockup never deployed
    context.predecessor_account_id = account_factory();
    context.attached_deposit = 0;
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let real_created = contract.on_lockup_create(
        victim_lockup_account(),
        ntoy(35).into(),
        String::from("real_sponsor.near"),
    );

    // IDENTITY assertion: the attacker's LockupArgs != real sponsor's intended LockupArgs,
    // yet the attacker's deployment occupies the address, and the legitimate creation fails.
    assert_eq!(real_created, false, "Legitimate lockup deployment must fail because address is squatted");
}
```

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
