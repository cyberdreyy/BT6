### Title
`kamino_init_obligation` only enforces a raw-liquidity minimum (`amount >= 10`) and never checks that the resulting collateral converted via the reserve's live exchange rate is non-zero, allowing the "always kept alive" obligation invariant to be violated - (File: `programs/marginfi/src/instructions/kamino/init_obligation.rs`)

### Summary
`kamino_init_obligation` enforces `require_gte!(amount, 10, ...)` on the raw liquidity amount before depositing into Kamino, but never converts that amount through the reserve's actual `liquidity_to_collateral` exchange rate to confirm the deposit yields non-zero collateral. Because that conversion rounds down (as proven by the repo's own unit tests), a reserve whose exchange rate makes `liquidity_to_collateral(10) == 0` will pass the instruction check yet leave the obligation with zero effective deposited collateral, contradicting the function's own documented invariant.

### Finding Description
The check in `kamino_init_obligation` is: [1](#0-0) 
This only validates the raw liquidity `amount`, never the collateral amount that Kamino will actually credit to the obligation. The conversion function used elsewhere in the codebase, `liquidity_to_collateral`, explicitly floors/truncates: [2](#0-1) 
and the underlying scaled math confirms flooring behavior with no zero-guard beyond division-by-zero: [3](#0-2) 
The repo's own tests demonstrate that small liquidity amounts can round to zero collateral, e.g. `floor(1 * 2/3) = 0`, and generalize this into round-trip tests showing conversions never increase: [4](#0-3) 

Contrast this with the sibling `kamino_deposit` instruction, which *does* compute `expected_collateral_amount` via `liquidity_to_collateral` and asserts the actual obligation collateral delta matches it within tolerance after the CPI: [5](#0-4) 
`kamino_init_obligation` has no equivalent post-CPI verification — it calls `cpi_kamino_deposit(amount)` and returns without checking the obligation's actual deposited collateral balance: [6](#0-5) 

The `KaminoInitObligation` accounts struct has no admin/authority gating beyond a plain `Signer` `fee_payer`, and the bank/reserve/obligation bindings are validated via `has_one` constraints rather than caller privilege: [7](#0-6) 
so any unprivileged party holding the requisite token balance can call this instruction once the bank exists (created by `lending_pool_add_bank_kamino`, which is admin-gated via `has_one = admin`, but the reserve's *exchange rate at call time* is not admin-fixed - it evolves with Kamino market state): [8](#0-7) 

### Impact Explanation
If the exchange rate at the moment of calling causes `liquidity_to_collateral(10) == 0`, the "permanent" bootstrap deposit deposits zero effective collateral into the obligation. This breaks the code's own documented invariant ("Arbitrarily setting minimum deposit to 10 absolute units to always keep the obligation alive... even a single lamport suffices to keep a balance open") and risks Kamino auto-closing the obligation as empty. Downstream instructions (`kamino_deposit`, `kamino_withdraw`, liquidation flows) assume `integration_acc_2` (the obligation) always exists and is non-empty; a closed/auto-reclaimed obligation account would break those account-derivation and CPI assumptions for the entire bank, requiring privileged remediation to recover. This matches the scoped "protocol inconsistency" impact described in the question.

### Likelihood Explanation
Exploitability requires a specific reserve exchange-rate state where `total_col / total_liq` is small enough that `10 * total_col / total_liq` floors to 0 (equivalently, a liquidity:collateral ratio worse than 10:1). This is a real, math-derivable rounding condition rather than a hypothetical one — the repo's own tests confirm rounding-to-zero happens for small inputs at ordinary ratios (e.g., 1 liquidity unit → 0 collateral at a 2:3 ratio). Whether any concrete mainnet Kamino reserve reaches a ≥10:1 ratio depends on that reserve's accumulated interest/exchange-rate history, so likelihood is data-dependent, but the code provides no defense regardless of how extreme the ratio becomes, and the call itself is fully permissionless once a bank exists.

### Recommendation
After (or before) the CPI deposit, convert `amount` through `integration_acc_1.load()?.liquidity_to_collateral(amount)?` and require the result to be strictly greater than zero (or check the obligation's actual `deposited_amount` post-CPI as `kamino_deposit` does), rejecting the instruction with a dedicated error if the conversion would round to zero collateral, rather than only checking the raw liquidity minimum.

### Proof of Concept
Rust unit test plan (mirroring `local_tests.rs` patterns):
1. Construct a `MinimalReserve` (via the existing `generic_reserve` test helper) with `total_liq`/`mint_total_supply` such that `total_col / total_liq <= 1/10`, e.g. `generic_reserve(supply=1000, decimals=6, mint_total_supply=50)` (ratio 1:20).
2. Call `reserve.liquidity_to_collateral(10)` and assert it equals `0`.
3. Add a unit/integration test around `kamino_init_obligation` (or a pure function extracted from it) asserting that calling with `amount = 10` against such a reserve either fails with a new dedicated error, or that the resulting obligation `deposited_amount` is checked to be `> 0` post-CPI — currently no such assertion exists, so the PoC demonstrates the instruction succeeds silently with zero effective collateral, violating the stated invariant.

```rust
/// Convert liquidity tokens to collateral tokens given scaled supplies.
/// Returns None on overflow or divide-by-zero.
#[inline]
pub fn liquidity_to_collateral_from_scaled(
    liquidity: u64,
    total_liq: I80F48,
    total_col: I80F48,
) -> Option<u64> {
    if total_liq == I80F48::ZERO {
        return None;
    }

    I80F48::from_num(liquidity)
        .checked_mul(total_col)?
        .checked_div(total_liq)?
        .checked_to_num::<u64>()
}
```
