### Title
Signer skips protocol-version-consensus and miner-identity re-validation at pre-commit/signing time, relying on an explicitly "incomplete" check — analog of the OAuth2 blacklist-skip SSRF - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
The full block-validity check (`check_block_against_state`) — which enforces signer-protocol-version consensus, static block validity, the "no problematic transactions" rule, and (via `check_proposal`) miner-pubkey/consensus-hash/bitvec/tenure-extend legitimacy — runs exactly once, at fresh proposal arrival [1](#0-0) . Every later re-check before a signature is actually produced — at `handle_block_validate_ok` and at the pre-commit-threshold signing decision — calls a narrower function, `check_block_against_signer_db_state`, whose own doc comment states it is an **incomplete check** and must not be called before the full `check_proposal`/validation has already succeeded once [2](#0-1) . This mirrors the Budibase report's pattern precisely: one canonical, thorough check exists and is used at the "front door," but the paths that matter for the final security-relevant action (fetch / signature) call a weaker, partial substitute.

### Finding Description
`check_block_against_state` is the only place that:
- Re-derives `determine_active_signer_protocol_version()` and rejects with `NoSignerConsensus` if the signer set has lost agreement on protocol version [3](#0-2) .
- Delegates to `check_block_against_local_state`/`check_block_against_global_state`, which run `SortitionsView::check_proposal` / `GlobalStateView::check_proposal` — verifying the block's miner pubkey hash against the *currently active* miner, the consensus hash against the *currently active* tenure, the pox bitvec, and (for tenure-change blocks) `DuplicateBlockFound`/`InvalidParentBlock` [4](#0-3) .

This whole check-set only executes in `handle_block_proposal`, i.e. at the moment the proposal is first seen [5](#0-4) .

By the time the block reaches `handle_block_validate_ok` (after the node's asynchronous `/v3/block_proposal` validation) or the pre-commit-threshold signing branch of `handle_block_pre_commit`, the signer instead calls `check_block_against_signer_db_state`, explicitly documented as:

> "WARNING: This is an incomplete check. Do NOT call this function PRIOR to check_proposal or block_proposal validation succeeds." [6](#0-5) 

That function only re-derives `check_tenure_change_confirms_parent` / `check_latest_block_in_tenure` [7](#0-6) . It does **not** re-check:
- whether the signer set's protocol-version consensus still holds (`NoSignerConsensus`),
- whether the miner that produced the block is still the recognized active miner (pubkey/consensus-hash match against the *current* `GlobalStateView`/`SortitionsView`, or whether the miner has since been marked `SortitionMinerStatus::InvalidatedBeforeFirstBlock`/timed out),
- the pox bitvec / tenure-extend legitimacy conditions, which are themselves time-and-state-dependent (`enough_time_passed`, `changed_burn_view`, replay state) [8](#0-7) .

The gap between proposal arrival and the pre-commit-threshold signing decision is not instantaneous: it spans a round-trip to the node's `/v3/block_proposal` validation endpoint plus the time to accumulate ≥70% pre-commit weight over StackerDB gossip — both attacker-influenceable delays (a slow-validating block, or deliberately staggered gossip of pre-commits). During that window the signer's own view of "who is the current miner" / "is signer-protocol-version consensus still held" can change (a new `StateMachineUpdate` shifts `global_state_evaluator`'s view, or the miner times out), yet none of that is re-asked before `mark_pre_committed`/`mark_locally_accepted` is called — the documentation itself calls the guard used at that point "incomplete," precisely analogous to the OAuth2 code path that skips the blacklist check every other outbound-fetch path uses.

### Impact Explanation
If protocol-version consensus is lost or the recognized active miner/tenure changes between proposal time and signing time, a signer can still sign a block that current-state validation (`check_proposal`) would reject — e.g. a block from a miner already marked invalid, or a block whose miner pubkey/consensus hash no longer matches the freshly-agreed active miner. This is a "signer signing an invalid/non-canonical block" outcome (Critical class per the rules), because the only re-check performed before the signature is produced is explicitly documented as incomplete and does not cover these properties.

### Likelihood Explanation
This requires no majority of signers, no other signer's key, and no access beyond what a single miner (plus normal StackerDB gossip propagation delay) already controls: a miner just needs its block's node-side validation, or the 70% pre-commit accumulation, to straddle a window in which the signer set's protocol-version consensus or active-miner view shifts — both of which occur naturally during normal fork/timeout/version-rollout activity, not via any privileged access.

### Recommendation
Re-run the full `check_block_against_state` (or at minimum re-derive `determine_active_signer_protocol_version`, the current miner's pubkey/consensus-hash, and the sortition-timeout/miner-status check) in `check_block_against_signer_db_state`, instead of relying on it as a narrower stand-in, so the same equality that gated proposal acceptance is also enforced immediately before `mark_pre_committed` and `mark_locally_accepted`.

### Proof of Concept
1. Miner M1 wins a sortition and proposes tenure-start block A; the signer's `handle_block_proposal` runs the full `check_block_against_state`, which passes (M1's pubkey matches the currently active miner, protocol-version consensus holds) [9](#0-8) , and A is submitted to the node for validation.
2. While the node's `/v3/block_proposal` validation is pending (or while pre-commit weight is still accumulating over StackerDB), the signer's active-miner/protocol-consensus view shifts — e.g. `capitulate_miner_view`/`StateMachineUpdate` processing moves the signer's `global_state_evaluator` to a new `current_miner`, or M1's sortition times out per `is_timed_out`.
3. The node's `Ok` validation response for A arrives; `handle_block_validate_ok` re-checks only `check_block_against_signer_db_state`, which does not re-verify the miner pubkey / consensus hash / protocol-version-consensus that changed in step 2, so A is marked pre-committed [10](#0-9) .
4. Once pre-commit weight crosses 70%, `handle_block_pre_commit` again calls only `check_block_against_signer_db_state` before `mark_locally_accepted`, still never re-verifying the now-stale miner/consensus-version facts [11](#0-10) , so the signer produces a signature over a block that a fresh `check_proposal` evaluation would now reject.

                "block_id" => %block_info.block.block_id(),
                "problematic_tx_count" => block_info.block.header.problematic_txs.len(),
            );
            return Some(
                self.create_block_rejection(
                    RejectReason::ProblematicTransactions,
                    &block_info.block,
                ),
            );
        }

        if state_version.uses_global_state() {
            self.check_block_against_global_state(stacks_client, &block_info.block)
        } else {
            self.check_block_against_local_state(stacks_client, sortition_state, &block_info.block)
        }

    fn handle_block_proposal(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_proposal: &BlockProposal,
    ) {
        debug!("{self}: Received a block proposal: {block_proposal:?}");
        if block_proposal.reward_cycle != self.reward_cycle {
            // We are not signing for this reward cycle. Ignore the block.
            debug!(
                "{self}: Received a block proposal for a different reward cycle. Ignore it.";
                "requested_reward_cycle" => block_proposal.reward_cycle
            );
            return;
        }

        let signer_signature_hash = block_proposal.block.header.signer_signature_hash();
        let prior_block_info = self.block_lookup_by_reward_cycle(&signer_signature_hash);
        if let Some(block_info) = &prior_block_info {
            // If we have already decided on this block, resend that decision (or ignore
            // the proposal) rather than evaluating it again.
            if !self.should_reevaluate_block(
                stacks_client,
                sortition_state,
                block_info,
                block_proposal,
            ) {
                return;
            }
        }

        if block_proposal
            .block
            .header
            .timestamp
            .saturating_add(self.block_proposal_max_age_secs)
            < get_epoch_time_secs()
        {
            // Block is too old. Reject it (without validating) rather than silently
            // dropping it: the miner's proposal loop re-sends the same block until it
            // accumulates rejection weight, so a silent drop from the whole signer set
            // would livelock the tenure until the next sortition.
            warn!("{self}: Received a block proposal that is more than {} secs old. Rejecting...", self.block_proposal_max_age_secs;
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_proposal.block.block_id(),
                "block_height" => block_proposal.block.header.chain_length,
                "burn_height" => block_proposal.burn_height,
                "timestamp" => block_proposal.block.header.timestamp,
            );
            let rejection =
                self.create_block_rejection(RejectReason::ProposalTooOld, &block_proposal.block);
            self.send_block_response(&block_proposal.block, rejection.into());
            return;
        }

        let pending_responses = if prior_block_info.is_some() {
            PendingBlockResponses::empty()
        } else {
            info!(
                "{self}: received a block proposal for a new block.";
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_proposal.block.block_id(),
                "block_height" => block_proposal.block.header.chain_length,
                "burn_height" => block_proposal.burn_height,
                "consensus_hash" => %block_proposal.block.header.consensus_hash,
            );
            self.signer_db
                .drain_pending_block_responses(&signer_signature_hash)
                .unwrap_or_else(|e| {
                    warn!(
                        "{self}: Failed to drain pending block responses for block proposal: {e:?}";
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %block_proposal.block.block_id(),
                    );
                    PendingBlockResponses::empty()
                })
        };
        crate::monitoring::actions::increment_block_proposals_received();
        // Creating a new proposal will overwrite any prior proposal info on the block if it exists, e.g. validity, signed_timestamps, etc.
        let mut block_info = BlockInfo::from(block_proposal.clone());

        // Get sortition view if we don't have it
        if sortition_state.is_none() {
            *sortition_state =
                SortitionsView::fetch_view(self.proposal_config.clone(), stacks_client)
                    .inspect_err(|e| {
                        warn!(
                            "{self}: Failed to update sortition view: {e:?}";
                            "signer_signature_hash" => %signer_signature_hash,
                            "block_id" => %block_proposal.block.block_id(),
                        )
                    })
                    .ok();
        }

    /// WARNING: This is an incomplete check. Do NOT call this function PRIOR to check_proposal or block_proposal validation succeeds.
    ///
    /// Re-verify a block's chain length against the last signed block within signerdb.
    /// This is required in case a block has been approved since the initial checks of the block validation endpoint.
    fn check_block_against_signer_db_state(
        &mut self,
        stacks_client: &StacksClient,
        proposed_block: &NakamotoBlock,
    ) -> Option<BlockRejection> {
        let signer_signature_hash = proposed_block.header.signer_signature_hash();
        // If this is a tenure change block, ensure that it confirms the correct number of blocks from the parent tenure.
        if let Some(tenure_change) = proposed_block.get_tenure_change_tx_payload() {
            // Ensure that the tenure change block confirms the expected parent block
            match SortitionData::check_tenure_change_confirms_parent(
                tenure_change,
                proposed_block,
                &mut self.signer_db,
                stacks_client,
                self.proposal_config.tenure_last_block_proposal_timeout,
                self.proposal_config.reorg_attempts_activity_timeout,
            ) {
                Ok(true) => return None,
                Ok(false) => {
                    return Some(self.create_block_rejection(
                        RejectReason::SortitionViewMismatch,
                        proposed_block,
                    ))
                }
                Err(e) => {
                    warn!("{self}: Error checking block proposal: {e}";
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %proposed_block.block_id()
                    );
                    return Some(self.create_block_rejection(
                        RejectReason::ConnectivityIssues(
                            "error checking block proposal".to_string(),
                        ),
                        proposed_block,
                    ));
                }
            }
        }

        // Ensure that the block is the last block in the chain of its current tenure.
        match SortitionData::check_latest_block_in_tenure(
            &proposed_block.header.consensus_hash,
            proposed_block,
            &mut self.signer_db,
            stacks_client,
            self.proposal_config.tenure_last_block_proposal_timeout,
            self.proposal_config.reorg_attempts_activity_timeout,
        ) {
            Ok(is_latest) => {
                if !is_latest {
                    warn!(
                        "Miner's block proposal does not confirm as many blocks as we expect";
                        "proposed_block_consensus_hash" => %proposed_block.header.consensus_hash,
                        "proposed_block_signer_signature_hash" => %signer_signature_hash,
                        "proposed_chain_length" => proposed_block.header.chain_length,
                    );
                    Some(self.create_block_rejection(
                        RejectReason::SortitionViewMismatch,
                        proposed_block,
                    ))
                } else {
                    None
                }
            }
            Err(e) => {
                warn!("{self}: Failed to check block against signer db: {e}";
                    "signer_signature_hash" => %signer_signature_hash,
                    "block_id" => %proposed_block.block_id()
                );
                Some(self.create_block_rejection(
                    RejectReason::ConnectivityIssues(
                        "failed to check block against signer db".to_string(),
                    ),
                    proposed_block,
                ))
            }
        }
    }
