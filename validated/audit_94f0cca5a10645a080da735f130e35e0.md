### Title
Fee recipient change causes old fee recipient to lose already-accrued unclaimed fees to the new recipient - ([File: v3/src/core/FeeVault.sol])

### Summary
`FeeVault.setFeeRecipient()` immediately overwrites the `feeRecipient` address without settling or ring-fencing the fees already accrued to the outgoing recipient. [1](#0-0)  Because `BaseFeeCalculator` tracks accrued fees per-vault (not per-recipient address) in `VaultAccruals.accruedFees`, and `claimFees()` is gated to whichever address is *currently* `feeRecipient`, an owner rotating the fee recipient instantly and irrevocably transfers all unclaimed, already-earned fees to the new recipient. [2](#0-1) [3](#0-2)  This is the same root-cause pattern as the referenced Arrakis report: role change transfers un-withdrawn, already-earned fees to the new holder instead of settling them to the outgoing holder.

### Finding Description
`VaultAccruals` stores `accruedFees` keyed only by `vault` address, representing fees owed to "whoever is `feeRecipient`", not to a specific historical address. [4](#0-3)  Fees accrue over time via `submitSnapshot` / `_accrueFees` in `DelayedFeeCalculator`, incrementing `vaultAccruals.accruedFees` regardless of who the current `feeRecipient` is. [5](#0-4) 

When the vault owner calls `setFeeRecipient(newFeeRecipient)`, the function only performs the zero-address check and overwrites `feeRecipient` — it does **not** call `claimFees()`, `_beforeClaimFees()`, or any equivalent that would settle/pay out the accrued balance to the outgoing recipient first. [1](#0-0) 

`claimFees()` is protected by `onlyFeeRecipient`, which checks `msg.sender == feeRecipient` against the *current* value. [3](#0-2)  As soon as `feeRecipient` is rotated, the outgoing address can no longer call `claimFees()` and permanently loses any right to the `accruedFees` balance that had built up on its behalf; the incoming `feeRecipient` claims the entire `vaultAccruals.accruedFees` bucket, including the portion earned while the old recipient held the role. [2](#0-1) 

This directly mirrors the Arrakis pattern where `setManager()` swapped the manager without settling in-pool accrued fees for the old manager first — except here the "in-flight" state is the fee-calculator's `accruedFees` bucket rather than an AMM position.

Comparing to the older Aera versions confirms this is a regression of a previously-fixed pattern:
- `AeraVaultV1.setGuardian()` explicitly calls `lockGuardianFees()` before swapping `guardian`, and stores the locked balance in a per-address mapping `guardiansFee[guardian]`, so the old guardian keeps its claim. [6](#0-5) 
- `AeraVaultV2.setGuardianAndFeeRecipient()` uses the `reserveFees` modifier to run `_reserveFees()` (crediting `fees[feeRecipient]`, a per-address mapping) before overwriting `feeRecipient`. [7](#0-6) [8](#0-7) 

In v3, `FeeVault.setFeeRecipient()` has no analogous settlement step, and `BaseFeeCalculator`'s accrual bucket is not per-address at all — the safeguard present in both v1 and v2 was dropped in v3.

### Impact Explanation
The outgoing fee recipient permanently loses all already-earned but unclaimed protocol/vault fees the moment `setFeeRecipient` is called, and the new fee recipient receives fees it did not earn. This is a direct loss of legitimately earned yield for a bounty-in-scope, non-privileged-attacker party (the fee recipient role holder), matching the "temporary/permanent freezing/loss of unclaimed yield" severity class.

### Likelihood Explanation
The trigger is a completely ordinary administrative action: the vault owner/authority calling `setFeeRecipient`, which is a normal, expected lifecycle operation (e.g., rotating operators or fixing a compromised recipient address). No malicious collusion, oracle manipulation, or privileged role abuse is required — the loss occurs purely because of the missing settlement step, so it will happen on essentially any legitimate fee-recipient rotation performed while fees are outstanding.

### Recommendation
Before overwriting `feeRecipient` in `FeeVault.setFeeRecipient()`, force settlement of the currently accrued fee balance to the outgoing recipient (e.g., internally invoke the same accrual/claim logic used in `claimFees()`, paying out to the old `feeRecipient` before updating storage), or track `accruedFees` per fee-recipient address (as v1/v2 do) rather than per vault, so that a recipient change cannot reassign already-earned, unclaimed fees to a new address.

### Proof of Concept
1. Deploy `FeeVault` (or a concrete subclass) wired to a `DelayedFeeCalculator`/`BaseFeeCalculator`, `feeRecipient = alice`.
2. Advance time and submit snapshots so that `_vaultAccruals[vault].accruedFees` becomes nonzero (fees earned by `alice`'s tenure), verified via `previewFees`/`accrueFees`.
3. As owner/authority, call `feeVault.setFeeRecipient(bob)`.
4. From `alice`, call `feeVault.claimFees()` — assert it reverts with `Aera__CallerIsNotFeeRecipient()`.
5. From `bob`, call `feeVault.claimFees()` — assert `bob` receives the full `accruedFees` balance that had accrued while `alice` was still the fee recipient, proving `alice`'s earned fees were transferred to `bob` without consent or compensation.

    function claimFees(uint256 feeTokenBalance) external virtual returns (uint256, uint256, address) {
        // Effects: hook called before claiming fees
        _beforeClaimFees();

        VaultAccruals storage vaultAccruals = _vaultAccruals[msg.sender];

        uint256 vaultEarnedFees = vaultAccruals.accruedFees;
        uint256 protocolEarnedFees = vaultAccruals.accruedProtocolFees;
        uint256 claimableProtocolFee = Math.min(feeTokenBalance, protocolEarnedFees);
        uint256 claimableVaultFee;

            vaultAccruals.accruedFees = uint112(vaultEarnedFees - claimableVaultFee);
        }

        return (claimableVaultFee, claimableProtocolFee, protocolFeeRecipient);
    }

    function _accrueFees(
        VaultSnapshot storage vaultSnapshot,
        VaultAccruals storage vaultAccruals,
        uint256 lastFeeAccrualCached
    ) internal returns (uint256 protocolFeesEarned, uint256 vaultFeesEarned) {
        uint256 snapshotTimestamp = vaultSnapshot.timestamp;
        if (lastFeeAccrualCached >= snapshotTimestamp || vaultSnapshot.finalizedAt > block.timestamp) {
            // nothing to accrue
            return (0, 0);
        }

        // pending snapshot has become active, accrue fees
        (uint256 vaultPerformanceFeeEarned, uint256 protocolPerformanceFeeEarned) = _calculatePerformanceFees(
            vaultAccruals.fees.performance, vaultSnapshot.highestProfit, vaultSnapshot.lastHighestProfit
        );

        (uint256 vaultTvlFeeEarned, uint256 protocolTvlFeeEarned) = _calculateTvlFees(
            vaultAccruals.fees.tvl, vaultSnapshot.averageValue, snapshotTimestamp, lastFeeAccrualCached
        );

        // Effects: update the vault's state
        vaultSnapshot.lastHighestProfit = vaultSnapshot.highestProfit;
        vaultSnapshot.lastFeeAccrual = uint32(snapshotTimestamp);
        vaultAccruals.accruedFees += (vaultPerformanceFeeEarned + vaultTvlFeeEarned).toUint112();
        vaultAccruals.accruedProtocolFees += (protocolPerformanceFeeEarned + protocolTvlFeeEarned).toUint112();

        // Effects: delete the pending snapshot
        vaultSnapshot.averageValue = 0;
        vaultSnapshot.highestProfit = 0;
        vaultSnapshot.timestamp = 0;
        vaultSnapshot.finalizedAt = 0;

        protocolFeesEarned = protocolPerformanceFeeEarned + protocolTvlFeeEarned;
        vaultFeesEarned = vaultPerformanceFeeEarned + vaultTvlFeeEarned;
    }
