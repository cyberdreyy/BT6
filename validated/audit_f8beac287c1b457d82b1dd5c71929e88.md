### Title
Stale confirmations from deleted keys still count toward `num_confirmations`, allowing execution below the live-key threshold - (File: multisig/src/lib.rs)

### Summary
`MultiSigContract::confirm` counts confirmations purely by the size of a `HashSet<PublicKey>` recorded per request, with no re-validation that each recorded public key is still a live access key on the account. The `DeleteKey` execution path only purges confirmations for requests that the deleted key *originated*, not requests it merely *confirmed*, so a confirmation from a since-removed key remains valid forever and can be combined with a fresh confirmation to execute a request with fewer than `num_confirmations` currently-live keys.

### Finding Description
The invariant this contract is supposed to maintain is:
`confirmations.get(request_id).len()` (counted keys) `== ` number of those keys that are **currently live access keys** on the account.

In practice the code only maintains:
`confirmations.get(request_id).len() >= num_confirmations` → execute,
with no liveness check [1](#0-0) .

Confirmations are stored as raw `PublicKey`s in a `HashSet` keyed by `request_id` [2](#0-1) , added in `confirm()` whenever a signer confirms a request they haven't confirmed before [1](#0-0) .

When a `DeleteKey` request executes, the cleanup logic only removes requests where `r.signer_pk == pk` (i.e., requests *originated* by the deleted key) and clears `num_requests_pk` for that key — it never scans other pending requests to strip confirmations made by that key as a mere confirmer: [3](#0-2) 

Exploit flow:
1. Request `X` (e.g., `Transfer` of account funds) is created via `add_request` and confirmed by `K-1` distinct keys (`self.confirmations` for `X` now has size `K-1`, one short of `num_confirmations`).
2. One of those `K-1` confirming keys (key `B`) is subsequently removed from the account via a legitimately-executed `DeleteKey` request. The `DeleteKey` handler only cleans up requests *created* by `B`; it does not touch `X`'s confirmation set, so `B`'s stale confirmation remains recorded on `X`.
3. Any remaining valid key `C` calls `confirm(X)`. `confirm` only checks `confirmations.len() as u32 + 1 >= self.num_confirmations` [4](#0-3) , which is satisfied using the phantom confirmation from removed key `B`, and `execute_request` runs the `Transfer`.

The contract has no way to query the account's current access-key set on-chain (acknowledged in the README's "Gotchas" section, which only discusses the opposite failure mode of the account locking itself out), so nothing anywhere in `confirm`, `assert_valid_request`, or `execute_request` can detect or reject a stale confirmation from a removed key. `assert_valid_request` only checks the predecessor equals the current account and that the request/confirmations map entries exist [5](#0-4) ; it does not re-derive liveness of each already-recorded confirming key.

### Impact Explanation
This directly matches the Critical category "a multisig request executed below `num_confirmations` live members." Concretely, an account funds `Transfer`, `FunctionCall`, `AddKey`/`DeleteKey`, or `DeployContract` (code upgrade) can be executed with strictly fewer live-key authorizations than the configured `K` of the K-of-N scheme, defeating the entire security guarantee of the multisig. This is repeatable for any multisig account whenever legitimate key rotation (removing an old confirming key) happens to overlap with an outstanding request that key had already confirmed — it does not require the removed key's holder to be malicious, only that key rotation and pending confirmations coincide, and any single remaining keyholder can then push the stale-backed request to execution.

### Likelihood Explanation
The only preconditions are: (a) a pending request with `num_confirmations - 1` confirmations already recorded, and (b) one of those confirming keys being removed via a subsequent (independently-approved) `DeleteKey` request before the pending request is confirmed the rest of the way. Both are ordinary, low-cost, and highly plausible operational events for any multisig account that rotates keys (a common security practice), making this easy to trigger, either opportunistically by a keyholder timing their own key's removal, or accidentally by normal account administration combined with one carelessly-timed extra confirmation.

### Recommendation
On `DeleteKey` execution, iterate over all pending requests' confirmation sets (not just requests originated by the deleted key) and remove the deleted public key from every `confirmations` entry, re-checking whether any request should no longer be treated as fully confirmed. Alternatively, revalidate at `confirm()`/execution time that every key in a request's confirmation set is still tracked as a valid signer (e.g., by maintaining an explicit registry of currently-authorized keys that is updated on `AddKey`/`DeleteKey`, and filtering confirmations against that registry before counting).

### Proof of Concept
`cargo test` plan (unit test in `multisig/src/lib.rs`'s test module, using `testing_env!`/`context_with_key` helpers already present):
1. Initialize `MultiSigContract::new(3)` (K=3) with signer keys `A`, `B`, `C` all treated as valid by mocking `signer_account_pk` per call.
2. As key `A`: `add_request` a `Transfer` request `X` to some receiver, then `confirm(X)` with key `A` — assert result is `PromiseOrValue::Value(true)` (not yet executed) and `get_confirmations(X).len() == 1`.
3. As key `B`: `confirm(X)` — assert `get_confirmations(X).len() == 2` (`K-1`, one short of threshold).
4. As key `A` (or any confirmed key): `add_request_and_confirm` a `DeleteKey { public_key: B }` request and drive it to execution (simulate reaching `num_confirmations` for that separate request) — assert it executes successfully (deletes `B`'s access key on the account).
5. Assert `get_confirmations(X)` still contains `B`'s public key (`len() == 2`), proving stale confirmation survived key deletion — this is the broken binding: `confirmations.len()` no longer equals the count of *live* keys among them (`2` recorded vs `1` live: only `A`).
6. As key `C` (a distinct, still-valid key that never previously confirmed): `confirm(X)` — assert the request executes (`PromiseOrValue::Promise(_)`/successful execution path) even though only `A` and `C` are live keys among the counted confirmers (`B` is dead), i.e., execution occurred with only 2 live-key confirmations against `K=3`, violating the invariant.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
