## Title
Stale confirmations from deleted multisig members allow a request to execute below the configured confirmation threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

## Summary
`confirm()` in both `multisig/src/lib.rs` and `multisig2/src/lib.rs` decides whether to execute a pending request purely by counting the size of the `confirmations` set stored for that `request_id`. When a member/key is removed via `DeleteKey` (`multisig`) or `DeleteMember` (`multisig2`), the cleanup logic only purges requests/confirmations *created* by the removed key — it never scans other pending requests for confirmations the removed key had already cast. Those stale confirmations keep counting toward `num_confirmations`, letting a request execute with fewer *live* member approvals than the configured K-of-N threshold.

## Finding Description
The binding the multisig is supposed to guarantee is:
`confirmations counted at execution == confirmations from currently-live members`.

In `multisig/src/lib.rs`, the `DeleteKey` branch of `execute_request` only removes requests/confirmations for requests where the deleted key was the *creator*: [1](#0-0) 

Similarly, in `multisig2/src/lib.rs`, `delete_member` only removes requests where `r.member == member` (i.e., requests the removed member created): [2](#0-1) 

Neither function iterates `self.confirmations` for *other* requests that the removed member had confirmed but not created. Those `HashSet<PublicKey>` (or `HashSet<String>` in multisig2) entries for the removed key/member remain in storage.

`confirm()` then trusts the raw size of that set: [3](#0-2) [4](#0-3) 

`assert_valid_request`/`assert_self_request` only check that the *current caller* is a live member — they never re-validate the *other* entries already stored in `confirmations` against the current member set. So a confirmation cast by a member who is later deleted keeps counting forever.

This is the direct analog of the reported bug class: the contract trusts a recorded value (a confirmation entry) without re-verifying that the entity it was recorded against is still "live" (has code / is still a member), exactly as the original report trusted a token address without verifying it was a real deployed contract.

## Impact Explanation
This breaks the core custody guarantee of a K-of-N multisig: a coalition of fewer than `num_confirmations` *currently live* members can execute a request (including `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc.) by combining their live confirmations with a stale confirmation left behind by a member that was removed after confirming but before the request was fully approved. This falls under the Critical category "a multisig request executed below threshold," since NEAR/assets held by the multisig account can be moved, or the multisig's key set altered, without the documented number of live approvers.

## Likelihood Explanation
This does not require any bug in access-key deletion or double-confirmation — it is the normal, documented flow: a member confirms a request, later that member (or another member's key) is removed via a completely separate, legitimate `DeleteKey`/`DeleteMember` request (e.g., because the key was compromised, an employee left, or the member set was rotated), and the original request is still outstanding. Any multisig instance that rotates its member set while requests are pending is exposed. Given that member rotation is an expected, encouraged operational practice (the README's "Gotchas" section already acknowledges related key-count issues but not this specific stale-confirmation issue), the likelihood of encountering pending requests during a member change is realistic.

## Recommendation
When removing a key/member (`DeleteKey` in `multisig/src/lib.rs`, `delete_member` in `multisig2/src/lib.rs`), iterate over **all** entries in `self.confirmations` (not just requests created by that key/member) and remove the deleted key/member's entry from each confirmation set. Alternatively, when counting confirmations in `confirm()`, filter the confirmation set against the current, live member set before comparing against `num_confirmations`, rather than trusting the raw stored set size.

## Proof of Concept
Using `multisig2` with `num_confirmations = 3` and members `K1, K2, K3, K4`:
1. `K1` calls `add_request(R1)` (e.g., a `Transfer`). `confirmations[R1] = {}`.
2. `K2` calls `confirm(R1)`. `len()=0, +1=1 < 3` → stored: `confirmations[R1] = {K2}`.
3. Separately, members submit and confirm a `DeleteMember{K2}` request (3 confirmations, e.g. K1,K3,K4) and it executes via `delete_member`, per [5](#0-4) . Since `K2` created no requests, `request_ids` filtered by `r.member == K2` is empty, so `confirmations[R1] = {K2}` is left untouched even though K2 is now removed from `self.members`.
4. `K1` calls `confirm(R1)`: `len()=1, +1=2 < 3` → stored: `confirmations[R1] = {K2, K1}`.
5. `K3` calls `confirm(R1)`: `len()=2, +1=3 >= 3` → `execute_request(R1)` runs.

R1 executes with confirmations `{K2 (removed), K1, K3}` — only 2 of the 3 currently-live members (`K1`, `K3`, out of live set `K1,K3,K4`) actually approved it, one fewer than the configured `num_confirmations = 3`, violating the multisig's threshold guarantee.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
