### Title
Missing deadline/expiration on `place_order` allows stale Stop-Loss/Take-Profit orders to be executed against outdated user intent - (File: `programs/marginfi/src/instructions/marginfi_account/order.rs`, `type-crate/src/types/order.rs`)

### Summary
The `Order` account used for the Stop-Loss/Take-Profit ("SL/TP") feature has no creation timestamp or expiration/deadline field. Once a user calls `place_order`, the order remains permissionlessly executable by any Keeper indefinitely until it is manually closed, its trigger fires, or its tagged balance is removed. This is the on-chain analog of the reported Rubicon `sellAllAmount()`/`buyAllAmount()` issue: a signed intent (in Rubicon's case a pending mempool tx; here, an on-chain `Order`) can sit unexecuted for an arbitrarily long time and later be triggered by a permissionless third party (a Keeper here, an MEV bot/miner there) at conditions the user never anticipated, while the only safeguard is a bounded slippage tolerance rather than a hard time limit.

### Finding Description
`place_order` creates an `Order` account (`programs/marginfi/src/instructions/marginfi_account/order.rs:38-137`) storing only a `stop_loss`/`take_profit` threshold and a `max_slippage` value [1](#0-0) . The struct definition explicitly flags the gap with `// TODO timestamp creation` directly above the `Order` struct [2](#0-1) , confirming no timestamp/expiry tracking exists anywhere in the type.

`start_execute_order` (permissionless, callable by any Keeper) only checks whether the current tagged-balance net value crosses the stored `stop_loss`/`take_profit` threshold — there is no check on how long the order has been outstanding: [3](#0-2) 

`end_execute_order` then only enforces a slippage bound (`max_slippage`, capped at `MAX_ORDER_SLIPPAGE`) relative to the stored threshold, not relative to when the order was created: [4](#0-3) 

This means a user who places an order (e.g., a take-profit at a price target reflecting today's portfolio composition and market view) has no way to make that order automatically expire. If market conditions or the user's broader position change materially after placement, and the user simply forgets the order or has no reason to actively cancel it, a permissionless Keeper can execute it far in the future the instant the stale trigger condition is met — extracting up to the maximum allowed slippage (bounded by `MAX_ORDER_SLIPPAGE`, ~10%) as profit, exactly as documented in the Keeper economics guide: "Keepers are permitted to keep whatever is leftover after completing the order execution as profit" [5](#0-4) .

### Impact Explanation
This is functionally identical in root cause to the referenced M-05 finding: absence of a deadline turns a "signed intent to trade at current conditions" into a perpetually-live instruction that can be executed under conditions the signer never intended. Here the financial impact is direct and quantifiable: the Keeper's profit is drawn straight from the user's account equity via the withdraw/repay executed inside `start_execute_order`/`end_execute_order`, up to the slippage tolerance the user configured at placement time — a tolerance which may become stale and inappropriate as time passes (e.g., portfolio composition changes via new deposits/borrows on other tagged balances, or market volatility increasing). Since `Order` accounts are cheap to create ($0.25 rent per the fee docs) and easy to forget, and closing them is an explicit user action rather than a default, the durable "always live" state is a real, low-friction attack surface for MEV-style Keepers monitoring on-chain orders for triggers that fire long after the user's original intent was valid.

### Likelihood Explanation
Likelihood is moderate-to-high: placing an order is a normal advertised user feature (guides/USER/ORDERS.md), Keepers are explicitly permissionless and profit-motivated by design, and there is no UI/protocol-level nudge or enforced expiry to prompt users to refresh stale orders. Any user who places an order and does not actively monitor/cancel it is exposed for as long as the order remains on-chain (unbounded).

### Recommendation
Add an optional or mandatory expiration (e.g., a `created_at`/`expires_at` slot or unix timestamp) to the `Order` struct, and enforce it in `start_execute_order`/`end_execute_order` so that Keepers cannot execute orders past their intended validity window. This closes the gap flagged by the existing `// TODO timestamp creation` comment and gives users a mechanism analogous to a swap "deadline" parameter, letting them bound how long their SL/TP intent remains executable under potentially stale conditions.

### Proof of Concept
1. User deposits SOL as collateral and borrows USDC, then calls `place_order` with a `TakeProfit` trigger and `max_slippage` = 9% (near the `MAX_ORDER_SLIPPAGE` cap), intending it to fire only if SOL quickly rallies.
2. Market conditions change over an extended period; the user closes unrelated positions and forgets about the still-active order (there is nothing in `Order` tracking its age, per `type-crate/src/types/order.rs:47`).
3. Much later, price action briefly and momentarily crosses the stored `take_profit` threshold (transient volatility, oracle noise, or a deliberately induced price spike by a sophisticated Keeper/MEV actor).
4. A Keeper immediately submits `start_execute_order` → withdraw/repay → `end_execute_order`, satisfying `net >= tp` and the slippage bound checked in `end_execute_order` (`programs/marginfi/src/instructions/marginfi_account/order.rs:435-446`), extracting up to the maximum permitted slippage as profit even though the order's underlying rationale is long stale.
5. The user has no recourse: the trade executes exactly as coded, since no deadline check exists anywhere in the order lifecycle.

    let net = order_assets_in_equity;

    // The user slippage constraint we want to enforce is:
    // net >= (1 - slippage) * (tp or sl)
    // where slippage is encoded as a u32 percent (0..100% mapped to 0..u32::MAX).

    // For the TP case another constraint(the max fee constraint) we want to enforce is:
    // net >= (1 - max_fee) * (start health)
    // It may be possible that the value (1 - max_fee) * (start health) is less than the
    // min allowed value based on the user's slippage constraint alone, in that case
    // we clamp it to the slippage, allowing for that much.
    // In the case where the value was greater we use (1 - max_fee) * (start health) instead.

    // Check that the liquidator did not over-withdraw.

    let slippage_frac = {
        let slippage = marginfi_type_crate::types::u32_to_centi(order.max_slippage);
        I80F48::ONE
            .checked_sub(slippage)
            .ok_or_else(math_error!())?
    };

    let max_fee_frac = {
        let max_fee: I80F48 = fee_state.order_execution_max_fee.into();
        I80F48::ONE.checked_sub(max_fee).ok_or_else(math_error!())?
    };

    let start_health = || -> I80F48 { execute_record.order_start_health.into() };

    match order.trigger {
        OrderTriggerType::StopLoss => {
            let sl: I80F48 = order.stop_loss.into();
            let allowed_sl = sl.checked_mul(slippage_frac).ok_or_else(math_error!())?;

            check!(
                net >= allowed_sl,
                MarginfiError::OrderExecutionOverWithdrawal
            );
        }
        OrderTriggerType::TakeProfit => {
            let tp: I80F48 = order.take_profit.into();
            let allowed_tp = tp.checked_mul(slippage_frac).ok_or_else(math_error!())?;

            let allowed_diff = (start_health)()
                .checked_mul(max_fee_frac)
                .ok_or_else(math_error!())?;

            check!(
                net >= allowed_diff && net >= allowed_tp,
                MarginfiError::OrderExecutionOverWithdrawal
            );
