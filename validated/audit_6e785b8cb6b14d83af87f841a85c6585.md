### Title
Post-default instant-withdraw receipts are confused with defaulted-epoch receipts, letting a new requester drain the default recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The CVE is a type-confusion bug: an object of one kind is treated as another. The credit-vault analog is a claim-type confusion in `IdleCreditVault`. `requestInstantWithdraw` records every receipt under the *current* `epochNumber` in `instantWithdrawsRequestsByEpoch`, but after `finalizeDefaultRecovery` the epoch number no longer advances (no further `stopEpoch`/`deposit` can run on a defaulted vault), so `epochNumber == defaultRecoveryEpoch` forever. Unlike `requestWithdraw`, which has an explicit post-default path (`postDefaultRequests`, haircut applied at request time, reserve-funded claims), `requestInstantWithdraw` has no `defaultRecoveryFinalized` branch at all. A brand-new instant receipt created after default finalization is therefore stored under `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — indistinguishable from a genuine defaulted-epoch receipt — and `claimInstantWithdrawRequest` pays it out of `defaultRecoveryReserve` at `defaultRecoveryPrice`. ### Finding Description
In `requestWithdraw`, once `defaultRecoveryFinalized` is true, requests are routed to a separate accounting bucket: the CDO passes an already-haircut amount, the receipt is stored in `postDefaultRequests`, and `pendingWithdraws` is untouched [3](#0-2) . `requestInstantWithdraw` has no equivalent branch — it unconditionally does `_burn(cdo, _amount)`, `_mint(user, _amount)`, `instantWithdrawsRequestsByEpoch[user][epochNumber] += _amount`, `instantWithdrawClaimsByEpoch[epochNumber] += _amount`, `pendingInstantWithdraws += _amount`.

On the claim side, `claimInstantWithdrawRequest` checks `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` and calls `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` as claim basis and pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` out of `defaultRecoveryReserve`. Because `epochNumber` is only incremented in `deposit()` (called from `stopEpoch`/`startEpoch` paths that cannot execute on a defaulted vault), `defaultRecoveryEpoch` remains the current epoch forever. Any post-default instant receipt is therefore interpreted ("type-confused") as a defaulted-epoch receipt with a pre-existing claim on the recovery reserve.

Two sub-cases:
- If `defaultInstantWithdrawsFinalized` was true at finalization (`pendingInstantWithdraws != 0`), the new receipt is directly paid at `defaultRecoveryPrice` from the reserve.
- If it was false, the receipt sits in `instantWithdrawsRequests` and `pendingInstantWithdraws` permanently, inflating `defaultPendingClaimBasis()` and blocking clean recovery accounting — a permanent freeze of part of the reserve for legitimate claimants.

### Impact Explanation
Direct theft of the isolated default recovery reserve. An attacker holding tranche tokens (any KYC'd lender) requests an instant withdrawal after default finalization, then immediately claims and receives `amount * defaultRecoveryPrice / 1e18` of underlying that is reserved for pre-default creditors. Every token paid this way is a token not available to genuine defaulted-epoch receipt holders, whose final claims will revert or be underpaid — up to the full `defaultRecoveryReserve`. The guard in `_transferFundedClaim` (balance minus reserve check) does not help because the payout goes through `_transferDefaultRecovery`, which intentionally spends the reserve. [4](#0-3) 

### Likelihood Explanation
Requires only that the vault has defaulted and been finalized with `defaultRecoveryPrice > 0` (a partial recovery, the common case) and that `IdleCDOEpochVariant.requestInstantWithdraw`/`getInstantWithdrawFunds` remain callable while `defaulted()` — normal withdraw claims are explicitly kept alive post-default ("if borrower defaults, old withdraw requests can still be claimed"), and instant claims have the same design. The attacker needs tranche tokens to burn, which any lender holds. No privileged cooperation is required.

### Recommendation
Add a post-default branch to `requestInstantWithdraw` mirroring `requestWithdraw`: after `defaultRecoveryFinalized`, either revert, or route the receipt into a haircut-priced bucket (e.g., reuse `postDefaultRequests` semantics, burning at the already-lowered virtual price) so it is never recorded under `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`. Alternatively, index instant receipts by a post-finalization epoch tag (e.g., `type(uint256).max`) so they can never collide with `defaultRecoveryEpoch`.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// Setup: standard epoch vault, user deposits, epoch runs, borrower defaults.
// finalizeDefaultRecovery(recovered, source) leaves defaultRecoveryPrice = 0.6e18
// and defaultRecoveryReserve = R (partial recovery).

// Attacker holds BB tranche tokens worth `amt` underlying post-haircut price.
vm.startPrank(attacker);
cdoEpoch.requestInstantWithdraw(amt, address(BBtranche)); // routed to IdleCreditVault.requestInstantWithdraw
vm.stopPrank();

// epochNumber is still defaultRecoveryEpoch -> receipt booked under defaulted epoch
IdleCreditVault vault = IdleCreditVault(address(strategy));
assertEq(vault.instantWithdrawsRequestsByEpoch(attacker, vault.defaultRecoveryEpoch()), amt);

// Claim pays amt * 0.6e18 / 1e18 straight from defaultRecoveryReserve
uint256 reserveBefore = vault.defaultRecoveryReserve();
uint256 balBefore = token.balanceOf(attacker);
cdoEpoch.claimInstantWithdrawRequest();
assertEq(token.balanceOf(attacker) - balBefore, amt * vault.defaultRecoveryPrice() / 1e18);
assertEq(vault.defaultRecoveryReserve(), reserveBefore - (amt * vault.defaultRecoveryPrice() / 1e18));
// Legitimate defaulted-epoch claimants now find the reserve short.
```

Caveat: the PoC assumes `IdleCDOEpochVariant.requestInstantWithdraw`/`claimInstantWithdrawRequest` do not revert when `defaulted()` is true; that gating could not be fully verified in the available iterations. If the CDO blocks new instant requests after default, the residual impact is the accounting-pollution variant (`pendingInstantWithdraws`/`defaultPendingClaimBasis` desync) only if the request path remains open while claims are kept alive, which the comments suggest is the intended design.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.

    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
