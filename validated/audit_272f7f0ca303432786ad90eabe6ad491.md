## Title
Coordinator double-counts a signer's weight in both `total_weight_approved` and `total_weight_rejected` when a rejection is followed by an acceptance for the same block — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

## Summary
The Arcadia `StakedStargateAM` bug is a class of "stale accumulator not reset/reconciled when a later, superseding event for the same principal arrives" — `lastRewardGlobal` is never zeroed after a claim, so the next delta computation is wrong. The `StackerDBListener` block-response tally in this repo has the same class of bug: `BlockStatus.total_weight_rejected` is never adjusted when the very same signer later sends an `Accepted` message for the same block, so that signer's weight ends up counted in *both* tallies simultaneously, breaking the invariant that a signer's weight should count toward at most one side of the vote.

## Finding Description
`BlockStatus` tracks two independent weight accumulators plus a single "have we heard from this signer" set: [1](#0-0) 

On `Accepted`, the code only guards against double counting by checking `gathered_signatures` (the accept-side map), never `responded_signers`: [2](#0-1) 

On `Rejected`, the guard is `responded_signers.insert(slot_id)`, which returns `false` (no-op) if that slot already answered — this correctly prevents a reject-after-accept from being double counted: [3](#0-2) 

But the reverse ordering is not symmetric. If a signer's `Rejected` message for a block arrives first, `responded_signers` gets that slot id and `total_weight_rejected` is incremented. If that *same* signer later sends `Accepted` for the *same* block (e.g. after re-evaluating, or a malicious/duplicate gossip message), the accept branch's only check is `!gathered_signatures.contains_key(&slot_id)` — which is still true, because `gathered_signatures` is only populated by the accept path. So `total_weight_approved` is incremented too, on top of the already-counted `total_weight_rejected` for that slot. Neither counter is ever decremented, and nothing subtracts the stale reject weight when the flip to accept happens — exactly analogous to `lastRewardGlobal` never being zeroed after the reward was already accounted for.

This breaks the coordinator-side equality that `total_weight_approved` and `total_weight_rejected` are mutually exclusive partitions of `total_weight` (each signer counted at most once, in one bucket). The coordinator's decision logic in `SignerCoordinator` relies on exactly this exclusivity to decide between "block accepted" and "signers rejected": [4](#0-3) 

## Impact Explanation
Because a single signer's weight can remain permanently "stuck" in `total_weight_rejected` even after that signer flips to `Accepted`, the coordinator can declare `NakamotoNodeError::SignersRejected` (line 536-540 area) for a block that in fact has (or will have) enough real acceptances, using a rejection tally inflated by a signer who no longer holds that position. This wedges the miner into abandoning/rejecting a validly-signable block based on stale, uncorrected weight — a liveness impact on block production driven purely by the actions of a single signer's messages observed via StackerDB/gossip, with no cooperation from any other signer required.

## Likelihood Explanation
Any signer (or an attacker replaying/crafting a duplicate signer message on that signer's slot, though a legitimately re-evaluating signer suffices) can trigger this by sending a `Rejected` message and later a `Accepted` message for the same `signer_signature_hash`. This is fully within the reach of "a one-slot signer plus gossip", requires no majority, and no cross-signer collusion.

## Recommendation
Make the tallies mutually exclusive: when processing `Accepted`, check `responded_signers` for a slot that previously rejected and, if the slot had previously contributed to `total_weight_rejected`, subtract that weight (and correspondingly for a would-be reject-after-accept, though that path is already guarded). Equivalently, key both accumulators off the *same* single-decision map (only allow a signer's weight to move between buckets, never accumulate independently in both), rather than each having its own independent additive counter.

## Proof of Concept
1. Signer `S` (slot `k`, weight `w`) sends `BlockResponse::Rejected` for hash `H`. `stackerdb_listener.rs:515-518` sets `responded_signers.insert(k)` (true) and `total_weight_rejected += w`.
2. Signer `S` later sends `BlockResponse::Accepted` for the same `H` (re-proposal replay, network duplicate, or a signer that changed its mind). `stackerdb_listener.rs:443-446` checks `!gathered_signatures.contains_key(k)` → true (never populated by reject path) → `total_weight_approved += w`.
3. Now `total_weight_approved + total_weight_rejected` includes `w` twice, i.e. exceeds the true partition of `total_weight`. If enough other signers are near the threshold on either side, the coordinator in `signer_coordinator.rs:505-545` can reach a `SignersRejected` (or artificially reach the approval threshold sooner) using this double-counted weight, even though `S`'s final, current position was `Accepted` (or vice versa).
