### Title
A second `requestWithdraw` overwrites `lastWithdrawRequest` and lets a haircut receipt escape `lossRecoveryPriceByEpoch`, paying the full pre-loss basis from other users' funded claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`IdleCreditVault._claimLossAdjustedWithdrawRequest` decides whether a user's pending receipt must be claimed at the loss-adjusted price by looking up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. `lastWithdrawRequest[_user]` is a single-slot "latest request epoch" marker that is unconditionally overwritten on every `requestWithdraw`. An unprivileged user whose receipt was haircut by `stopEpochWithDuration(_lossAmount)` can simply file a new withdraw request in the next buffer period; the marker then points at an epoch with no loss price, the loss-adjusted path returns zero, and the stale full-size basis remains inside `withdrawsRequests[_user]`, which `_claimFundedWithdrawRequest` pays out at par.

### Finding Description

Timeline in a standard fixed-APR deployment:

1. Buffer phase before epoch `E`: attacker calls `IdleCDOEpochVariant.requestWithdraw` (`contracts/IdleCDOEpochVariant.sol:739`). The strategy records `withdrawsRequestsByEpoch[attacker][E] += X`, `withdrawsRequests[attacker] += X`, `lastWithdrawRequest[attacker] = E` and mints `X` receipt strategy tokens (`IdleCreditVault.sol:282-293`).
2. Epoch `E` runs. At `epochEndDate` the manager calls `stopEpochWithDuration(apr, interest, duration, lossAmount)`. `_stopEpoch` splits the loss between pending receipts and active LPs via `previewLossAdjustedWithdrawFunds` and calls `collectWithdrawFunds(pendingToFund)` (`IdleCDOEpochVariant.sol:393,410`). Since the funded amount is below the pending basis, the strategy stores `lossRecoveryPriceByEpoch[E] = funded * 1e18 / pendingBasis` and zeroes `pendingWithdraws` (`IdleCreditVault.sol:414-421`). The strategy only ever received the haircut-funded amount.
3. Buffer phase before epoch `E+1`: `stopEpoch` reopened `allowAAWithdrawRequest`/`allowBBWithdrawRequest` (`IdleCDOEpochVariant.sol:480-482`). The attacker files a second `requestWithdraw` for any dust amount of tranche tokens they kept. The strategy now sets `lastWithdrawRequest[attacker] = E+1` (`IdleCreditVault.sol:282`).
4. Epoch `E+1` runs and stops cleanly; `epochNumber` becomes `E+2`. The attacker calls `claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[attacker] = E+1`, finds `lossRecoveryPriceByEpoch[E+1] == 0`, and returns without clearing the epoch-`E` basis (`IdleCreditVault.sol:789-795`).
5. `_claimFundedWithdrawRequest` then pays `withdrawsRequests[attacker]` — which still contains the full, un-haircutted epoch-`E` basis — at par (`IdleCreditVault.sol:338-349`), burning the attacker's 1:1 receipt tokens.

The broken invariant is "one receipt, haircut-adjusted payout": the per-epoch haircut is bound to a mutable single-slot marker rather than iterated over all epochs that carry a `lossRecoveryPriceByEpoch`. No existing guard stops it — the second request is a legal call during an open buffer, the wait-one-epoch check in `_claimFundedWithdrawRequest` (`epochNumber <= lastWithdrawRequest`) is satisfied because the marker was bumped, and the burn only requires receipt tokens the attacker legitimately holds.

### Impact Explanation

Direct theft of the funded withdraw reserve, i.e. insolvency for honest claimants. The strategy holds only `pendingBasis * lossRecoveryPrice / 1e18` for the epoch-`E` cohort, but the attacker withdraws their full pre-loss basis. Every honest epoch-`E` claimant is then paid the same inflated rate until the reserve is exhausted; the last claimants are left with unpayable receipts (permanent freezing of unclaimed funds). Quantified: with a pending basis of 100,000 and a 10% receipt haircut (`lossRecoveryPrice = 0.9e18`), the strategy received 90,000; an attacker holding 50,000 of that basis who claims at par extracts 50,000, leaving 40,000 for receipts nominally worth 45,000 — a 5,000-unit direct theft plus permanent freeze of the shortfall.

### Likelihood Explanation

Requires only an unprivileged KYC-passed tranche holder, two ordinary `requestWithdraw` calls in two consecutive buffer periods, and patience for one extra epoch. The trigger condition — a manager calling `stopEpochWithDuration` with `_lossAmount > 0` — is a normal, honest privileged action (partial borrower repayment), and the attacker does not control it but merely needs it to occur once. Cheap and fully repeatable; multiple attackers can race to drain the reserve.

### Recommendation

Do not derive the loss-adjusted epoch from `lastWithdrawRequest`. In `_claimLossAdjustedWithdrawRequest` (and `_claimDefaultedWithdrawRequest`), iterate or track all epochs in which the user has `withdrawsRequestsByEpoch[_user][e] != 0` with `lossRecoveryPriceByEpoch[e] != 0`, or store the loss flag per `(user, epoch)` receipt. Alternatively, block or consolidate new `requestWithdraw` calls while the user still has an unsettled loss-adjusted receipt, or always route the claim through `_clearWithdrawClaimForEpoch` for every epoch with a nonzero loss price before falling back to the par-funded path.

### Proof of Concept

Foundry fork PoC sketch (running/buffer phases labelled):

```solidity
// Setup: standard IdleCDOEpochVariant + IdleCreditVault, fixed-APR mode.
// Attacker = KYC'd user (isWalletAllowed true).

// --- Buffer before epoch 0 ---
uint256 minted = cdo.depositAA(50_000e6);            // attacker
otherUser depositAA(50_000e6);
cdo.requestWithdraw(minted - dust, AAtranche);       // receipt X recorded at epoch 0
// manager: startEpoch()

// --- Epoch 0 running ---
// warp past epochEndDate
// manager: stopEpochWithDuration(apr, interest, dur, LOSS > 0)
//   -> collectWithdrawFunds stores lossRecoveryPriceByEpoch[0] < 1e18
//   -> strategy received only haircut-funded amount

// --- Buffer before epoch 1 ---
cdo.requestWithdraw(dust, AAtranche);                // attacker: lastWithdrawRequest -> 1
// manager: startEpoch(); warp; stopEpoch(apr, interest)  // clean stop, epochNumber = 2

// --- Claim ---
cdo.claimWithdrawRequest();
// _claimLossAdjustedWithdrawRequest: lossRecoveryPriceByEpoch[1] == 0 -> skipped
// _claimFundedWithdrawRequest: epochNumber(2) > lastWithdrawRequest(1)
//   pays withdrawsRequests[attacker] = full epoch-0 basis + dust AT PAR
// assert attackerUnderlyingDelta > basis * lossRecoveryPriceByEpoch[0] / 1e18
// assert strategy underlying balance < sum of remaining honest haircut claims
```

Note: I could not fully verify the exact line where `epochNumber` is incremented (grep confirmed 30 references but the increment site wasn't displayed); the PoC assumes the standard ordering where `collectWithdrawFunds` keys `lossRecoveryPriceByEpoch` by the request epoch, consistent with `_claimLossAdjustedWithdrawRequest` reading `lastWithdrawRequest` as the loss epoch — the exploit holds under either ordering as long as a later request can overwrite the marker before the loss epoch is cleared.
