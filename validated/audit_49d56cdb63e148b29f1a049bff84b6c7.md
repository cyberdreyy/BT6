### Title
Revoked-KYC lenders keep fund access through existing withdrawal requests and freely transferable tranche tokens — credential check only at request time, never at claim/transfer time - (contracts/IdleCDOEpochVariant.sol, contracts/IdleCDOEpochQueue.sol)

### Summary
The upstream bug is CWE-613 (insufficient session invalidation): disabling a user is enforced only at token issuance; existing tokens remain valid for all authenticated endpoints. The exact same divergence exists in idle-tranches' credit vault: Keyring credential status is enforced only when a withdrawal request / queued request / deposit is *created*, and never again when the request is *claimed* or when tranche tokens move. A wallet whose Keyring credential (or `KeyringIdleWhitelist` entry) is revoked keeps full, permanent withdrawal and transfer capability — identical to "token exists and is not expired; `users.enabled` is not checked", with tranche tokens / queued request entries playing the role of the session token.

### Finding Description
Credential checks exist only on the entry paths:

- `IdleCDOEpochVariant.requestWithdraw` requires `isWalletAllowed(msg.sender)` (`contracts/IdleCDOEpochVariant.sol:739-744`).
- `IdleCDOEpochQueue.requestDeposit` and `requestWithdraw` call `_checkAllowed`, which reverts unless `cdoEpoch.isWalletAllowed(wallet)` (`contracts/IdleCDOEpochQueue.sol:103-143, 415-421`).
- `isWalletAllowed` itself is a live view into Keyring: `IKeyring(keyring).checkCredential(keyringPolicyId, _user)` (`contracts/IdleCDOEpochVariant.sol:984-987`).

But the value-realization paths perform no credential check at all:

- `IdleCDOEpochVariant.claimWithdrawRequest` and `claimInstantWithdrawRequest` just forward `msg.sender` to `IdleCreditVault` (`contracts/IdleCDOEpochVariant.sol:967-979`); the vault pays out based on the stored request, not on the caller's current KYC status.
- `IdleCDOEpochQueue.claimDepositRequest` and `claimWithdrawRequest` gate only on `epochPrice`/`epochWithdrawPrice` and pending-claim flags, then `safeTransfer` tranche tokens or underlying to `msg.sender` (`contracts/IdleCDOEpochQueue.sol:373-411`).
- `IdleCDOTranche` is a plain ERC20 with no `_beforeTokenTransfer` hook — no allowlist on transfers at all (`contracts/IdleCDOTranche.sol:7-40`).
- `KeyringIdleWhitelist.setWhitelistStatus(false)` flips a bit but revokes nothing already held (`contracts/KeyringIdleWhitelist.sol:102-112`) — the direct analog of `UPDATE users SET enabled = 0` not deleting sessions.

Divergence map to the advisory:

```text
Request/requestDeposit path:  isWalletAllowed must be true   (= users.enabled == 1 at login)
Claim/transfer path:          request/token exists           (= token row exists, not expired)
                              credential never re-checked
```

The repo's own test confirms the split is deliberate-looking but incomplete: `testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw` verifies a non-KYC wallet is blocked at `requestWithdraw` — it never exercises `claimWithdrawRequest` after revocation (`test/foundry/IdleCreditVaultWriteOffEscrow.t.sol:288-291`).

### Impact Explanation
A lender who passes KYC, deposits, and files `requestWithdraw` (or queues via `IdleCDOEpochQueue.requestWithdraw`) and is subsequently de-credentialed — Keyring credential expired/revoked or removed via `setWhitelistStatus(false)` — can still call `claimWithdrawRequest`/`claimInstantWithdrawRequest`/`claimDepositRequest`/`claimWithdrawRequest(queue)` and receive underlying or tranche tokens. Because tranche tokens are unrestricted ERC20, a revoked wallet can also transfer its position to any address (which can then file fresh requests if it passes KYC, or sell into `WriteOffEscrow` fulfills). Since Keyring revocation is the mechanism meant to cut off a lender (sanctions hit, credential lapse, compromised wallet flagged by the Keyring admin), this is a persistent post-revocation access bypass of indefinite duration — mirroring the advisory's `token_expiration: never` severity driver. Loss magnitude: the full value of the revoked wallet's position (principal + accrued interest), paid out from the same NAV pool as compliant lenders.

### Likelihood Explanation
Requires only: (1) an epoch where a lender holds tranche tokens or a pending request, and (2) the Keyring admin (honest per scope) revoking that wallet's credential or whitelist status — a routine operational action. No privileged collusion, no timing race needed: unlike upstream's "until token expiry," here there is no expiry at all. The blocked-user test coverage proves the developers intend revocation to be meaningful, so the gap is not an acknowledged design choice.

### Recommendation
Re-check `isWalletAllowed` at every value-realization point: inside `IdleCDOEpochVariant.claimWithdrawRequest` and `claimInstantWithdrawRequest`, inside `IdleCDOEpochQueue.claimDepositRequest`/`claimWithdrawRequest`, and via a `_beforeTokenTransfer` credential check on `IdleCDOTranche` (at minimum on `transfer`/`transferFrom` recipients). Alternatively/additionally, expose an owner/manager "revoke and settle" function that pays out and zeroes a revoked user's pending requests, paralleling session deletion on user disable.

### Proof of Concept
```solidity
// Foundry fork PoC — revoked user still claims a queued withdrawal
// setup: epoch running, LP deposited AA tranche tokens earlier while KYC'd

address keyring = address(1);
vm.prank(cdoEpoch.owner());
cdoEpoch.setKeyringParams(keyring, 1);

// LP currently passes KYC -> files a withdraw request mid-epoch
vm.mockCall(keyring, abi.encodeWithSelector(IKeyring.checkCredential.selector),
            abi.encode(true));
uint256 trancheBal = AAtranche.balanceOf(LP);
vm.prank(LP);
uint256 requested = cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));

// admin (honest) action: Keyring credential for LP is revoked
vm.mockCall(keyring, abi.encodeWithSelector(IKeyring.checkCredential.selector),
            abi.encode(false));

// sanity: new requests are now blocked for LP
vm.prank(LP);
vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
cdoEpoch.requestWithdraw(1, address(AAtranche));

// epoch progresses: stop + new buffer period makes the request claimable
_stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
_startEpochAndCheckPrices(0);

// BUG: revoked user still receives underlyings for the old request —
// claimWithdrawRequest never re-checks isWalletAllowed
uint256 balPre = underlying.balanceOf(LP);
vm.prank(LP);
cdoEpoch.claimWithdrawRequest();          // succeeds, pays LP in full
assertGt(underlying.balanceOf(LP), balPre);

// Same for the epoch queue variant:
// queue.requestWithdraw() while KYC'd -> revoke -> queue.claimWithdrawRequest(epoch)
// transfers underlying at epochWithdrawPrice with no credential check.
```
