### Title
`apply_delegate_action` computes prepaid send-fee refund-burn over the outer receipt's full action list instead of the delegate's own inner actions, allowing double-burn of a sibling action's send fee - (File: runtime/runtime/src/actions.rs)

### Summary
`apply_delegate_action` burns `total_prepaid_send_fees(&apply_state.config, action_receipt.actions())`, i.e. the send fee of the **entire outer action list** currently being executed, rather than the send fee of just `delegate_action.get_actions()` (the actions actually placed into the newly generated inner `new_receipt`). Because `validate_actions_with_mode`'s `DelegateActionMustBeOnlyOne` check only forbids more than one `Delegate`/`DelegateV2` action in a list — it does not forbid other, non-delegate sibling actions from coexisting with it — an attacker can craft a receipt/transaction whose action list is `[Delegate(...), Transfer{deposit: X}]`, causing the sibling `Transfer`'s send fee to be folded into `result.gas_burnt` twice: once erroneously inside the Delegate action's own bookkeeping, and once already burnt during the original transaction-to-receipt conversion (and effectively "re-executed" a second time when the sibling `Transfer` action itself later runs in the same receipt loop).

### Finding Description
In `runtime/runtime/src/actions.rs`:
```rust
let new_receipt = Receipt::V0(ReceiptV0 { ... receipt: ReceiptEnum::Action(ActionReceipt {
    ... actions: delegate_action.get_actions(), }) });

let prepaid_send_fees = total_prepaid_send_fees(&apply_state.config, action_receipt.actions())?;
``` [1](#0-0) 

The `new_receipt` being costed is built from `delegate_action.get_actions()` (the inner, delegate-only actions), but the send-fee amount that gets burnt via `result.gas_burnt.checked_add_result(prepaid_send_fees.gas)` is computed from `action_receipt.actions()` — the **outer**, currently-executing receipt's full action list. In the canonical, intended case that outer list is `[Delegate(...)]` only, so `total_prepaid_send_fees` re-derives exactly what was reserved for sending the Delegate plus its nested payload (matching the fee-computation pattern seen in `total_send_fees`'s `Delegate` branch, which recurses into `delegate_action.get_actions()`) [2](#0-1) .

However, `validate_actions_with_mode` only tracks `found_delegate_action` to reject a *second* `Delegate`/`DelegateV2`; it does not reject other action kinds appearing alongside the single `Delegate`:
```rust
if let Action::Delegate(_) | Action::DelegateV2(_) = action {
    if found_delegate_action {
        return Err(ActionsValidationError::DelegateActionMustBeOnlyOne);
    }
    found_delegate_action = true;
}
``` [3](#0-2) 

This means a relayer-submitted transaction with `actions = [Action::Delegate(signed_delegate_action_for_alice), Action::Transfer{deposit: X}]` (single shared `receiver_id`) is valid and passes both transaction-admission and receipt validation. When this receipt is executed, the per-action loop first dispatches the `Delegate` action to `apply_delegate_action`, which now sums send fees over `action_receipt.actions()` = `[Delegate, Transfer]`. Because `total_send_fees`/`total_prepaid_send_fees` iterates every action in the given slice and adds each one's own send fee (Transfer's `transfer_send_fee` included) on top of the Delegate branch's own recursive computation, the `Transfer` action's send fee gets folded into `result.gas_burnt` during the Delegate action's processing — fees that were already accounted for once when the original transaction was converted to a receipt (the tx-conversion `total_send_fees` call also iterates the same outer `[Delegate, Transfer]` list and burns the Transfer's send fee at that time). The same `Transfer` action is then executed again later in the loop as its own action, so its send-fee contribution effectively enters the receipt's cumulative gas accounting more than the single time it is legitimately owed.

No existing check catches this: `DelegateActionMustBeOnlyOne` only bounds the count of `Delegate` actions, not their coexistence with other action types, and there is no assertion anywhere that `sum(action-level gas_burnt) == receipt_required_cost(receipt)` computed once.

### Impact Explanation
This breaks the gas/balance-conservation invariant that the sum of gas burnt while executing a receipt's actions equals the amount actually prepaid/purchased for that receipt. The result is either (a) more gas is recorded as `gas_burnt` than was legitimately consumed, reducing the refund owed to the relayer (the signer who pays and receives refunds per the comment "Gas is refunded to the signer, this is Relayer"), with the excess effectively flowing to burnt-fee/validator-reward accounting instead of being refunded, or (b) in more extreme constructions, `gas_used`/`gas_burnt` bookkeeping diverging from the actual amount purchased for the receipt. This falls under "token inflation or loss" via broken gas-fee balance conservation rather than direct fund theft from an arbitrary third party, since the party overcharged is the relayer that constructed the malformed action list — but it is a genuine, reproducible consensus-relevant accounting defect in `apply_delegate_action`.

### Likelihood Explanation
The precondition (`[Delegate, Transfer]` or any `[Delegate, <other action>]` combination in one action list) is fully attacker-controlled and costs nothing extra to construct — it only requires that the same account act as its own relayer or that a relayer's transaction-bundling logic combines a delegate action with another action targeting the same receiver. It is deterministically reproducible on every such transaction, requires no privileged access, and is not blocked by any current validation (`DelegateActionMustBeOnlyOne` only limits the delegate count, not sibling actions).

### Recommendation
Change `apply_delegate_action` to compute the prepaid send fee from `delegate_action.get_actions()` (the same list used to build `new_receipt`) instead of `action_receipt.actions()`:
```rust
let prepaid_send_fees = total_prepaid_send_fees(&apply_state.config, &delegate_action.get_actions())?;
```
and add a regression test asserting that for a receipt containing `[Delegate, Transfer]`, `total_prepaid_send_fees`/`result.gas_burnt` contribution from the Delegate action's own processing matches only the delegate's own nested-action fee, not the sibling `Transfer`'s fee.

### Proof of Concept
Add a runtime/`apply_state`-fixture integration test (e.g. alongside existing tests in `runtime/runtime/src/actions.rs` or the runtime `tests/` integration suite):
1. Build a `SignedDelegateAction` for account `alice` with a trivial inner action (e.g. `CreateAccount` or a small `Transfer`), targeting `receiver_id = bob`.
2. Construct an outer transaction/receipt with `actions = [Action::Delegate(signed_delegate_action), Action::Transfer(TransferAction{deposit: X})]`, `receiver_id = bob`, signed/sent by relayer account.
3. Confirm the action list passes `validate_actions_with_mode` (it should, proving `DelegateActionMustBeOnlyOne` does not block sibling actions).
4. Execute the receipt through the runtime and record, per action index, the `gas_burnt` contributed by `apply_delegate_action` versus the `gas_burnt` contributed later by the sibling `Transfer` action.
5. Independently compute the expected total via `receipt_required_cost` for the whole receipt computed once (as the runtime would have charged at tx-to-receipt conversion), and assert `sum(action-level gas_burnt) == receipt_required_cost(receipt)`. The test should show the sum exceeds the expected total by exactly the sibling `Transfer`'s send fee, demonstrating the double-burn.
