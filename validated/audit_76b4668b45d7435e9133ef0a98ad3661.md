### Title
Post-default withdraw claims drain `defaultRecoveryReserve`, underflowing and permanently freezing default-era recovery claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` creates "post-default" receipt requests (`postDefaultRequests`) that are explicitly excluded from `pendingWithdraws` and are funded only by the underlying already backing the burned CDO strategy tokens, which stays in the vault's token balance but is never added to `defaultRecoveryReserve`. `_claimPostDefaultWithdrawRequest` nonetheless pays them 1:1 via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` — the reserve meant to be spent exclusively by default-era claimants at `defaultRecoveryPrice`. Each post-default claim therefore consumes reserve earmarked for defaulted-epoch claimants; once aggregate post-default claims exceed the reserve's slack, `defaultRecoveryReserve -= _amount` underflows and all remaining default recovery claims revert permanently.

### Finding Description
After `finalizeDefaultRecovery`, `defaultRecoveryReserve` is set once to `reserveAmount = _recoveredAmount + prefundedReserve + priorReserve`, sized to pay `totalBasis * recoveryPrice` across active and pending claims (lines 686–699). Nothing ever increases it afterward — `collectWithdrawFunds` only `safeTransferFrom`s into `balance` (lines 411–430), and `pendingWithdraws` is deliberately not increased for post-default requests ("Preserve request/claim UX after default without increasing borrower-facing pendingWithdraws", lines 252–257). Yet `_claimPostDefaultWithdrawRequest` calls `_transferDefaultRecovery`, which does `defaultRecoveryReserve -= _amount` (lines 760–767, 912–917). The backing for those claims is the un-burned underlying left behind when `_burn(msg.sender, _amount)` destroyed the CDO's strategy tokens at request time — i.e., it lives in `balance`, outside the reserve. The reserve-vs-basis accounting is thus mismatched: the same reserve backs both default-era claims (sized to be fully consumed) and unbounded post-default par claims.

### Impact Explanation
Broken invariant: donation/reserve isolation and "one receipt one payout". An unprivileged user (anyone able to call `requestWithdraw` through the CDO post-default — e.g., a KYC-passed lender) places a post-default withdraw request and claims it, debiting `defaultRecoveryReserve` without its funding ever being credited to the reserve. Aggregate post-default claims are unbounded in size relative to the reserve's rounding slack. Result: `defaultRecoveryReserve -= _amount` underflows (Solidity ≥0.8 revert) when honest default-era claimants call `claimWithdrawRequest`/`_claimDefaultedWithdrawRequest`, permanently freezing the entire remaining recovery reserve — a permanent loss of all unclaimed default recovery funds.

### Likelihood Explanation
Requires only that a borrower default has been finalized with a non-total recovery (so `defaultRecoveryReserve > 0` and `defaultRecoveryPrice < RECOVERY_FULL`) and that post-default withdraw requests are permitted. All attacker steps are unprivileged user calls (`requestWithdraw`, `claimWithdrawRequest` via the CDO) sequenced around honest manager/borrower epoch calls. No privileged misbehavior, oracle manipulation, or timing edge is needed; the miscount is deterministic once any post-default claim is paid from the reserve.

### Recommendation
Either (a) pay post-default requests via `_transferFundedClaim` and ensure their funding increases `defaultRecoveryReserve` or is tracked separately, or (b) on post-default `requestWithdraw`, immediately add the released backing to `defaultRecoveryReserve` (e.g., `defaultRecoveryReserve += _amount` net of the applied haircut) so reserve accounting matches the underlying it must pay. The cleanest fix is to keep the post-default bucket out of `_transferDefaultRecovery` entirely: since the haircut is applied at request time through the lowered `virtualPrice`, these claims are already funded by vault balance and should use `_transferFundedClaim`, with the reserve-guard ordering adjusted so reserve isolation is preserved.
