### Title
`getTokenAccountBalance`/JSON-parsed token RPC endpoints trust attacker-controlled mint address without verifying it is owned by a legitimate SPL Token program - (File: rpc/src/parsed_token_accounts.rs)

### Summary
`get_mint_owner_and_additional_data` fetches an account at an arbitrary "mint" pubkey and unpacks its raw bytes as an SPL `Mint` without ever checking that the fetched account is actually owned by `spl_token` or `spl_token_2022`. Because the "mint" pubkey itself comes from attacker-controlled token-account data, an attacker can point it at any account they fully control (owned by any program, e.g. the System Program) and craft its bytes to pass `Mint::unpack`, forging arbitrary `decimals`/extension data that RPC then reports as truth.

### Finding Description
In `rpc/src/parsed_token_accounts.rs`: [1](#0-0) 

`get_mint_owner_and_additional_data` calls `bank.get_account(mint)` and directly unpacks it via `get_additional_mint_data` → `StateWithExtensions::<Mint>::unpack(data)`, returning `*mint_account.owner()` as if it were a validated "token program id" — but this owner is never compared against `is_known_spl_token_id` or any allow-list before being trusted.

This function is fed a `mint` pubkey that originates from a *user-supplied token account's own data field* via `get_token_account_mint`: [2](#0-1) [3](#0-2) 

`get_token_account_mint` only validates that the token-account's data length/layout is plausible; the `mint` field inside it is fully attacker-controlled. In `rpc/src/rpc.rs`, `get_token_account_balance` checks that the *token account* is owned by a known SPL token program, but the subsequently extracted `mint` field is passed straight to `get_mint_owner_and_additional_data` with no equivalent ownership check on the mint account: [4](#0-3) 

This is the direct analog of the Escher finding: sales trusted `sale.edition` as if it were deployed by the legitimate `Escher721Factory` without verifying it; here, RPC trusts an arbitrary "mint" pubkey as if it were deployed by the legitimate SPL Token program without verifying its owner.

### Impact Explanation
An unprivileged user can create/own any account (e.g. a System-owned account) with attacker-chosen bytes shaped to satisfy `StateWithExtensions::<Mint>::unpack` (setting `is_initialized = true` and any `decimals` value 0–255, plus optional extension data). They then create a normal SPL token account (owned by the real token program, so it passes the existing owner check) whose `mint` field points at that forged account. A single `getTokenAccountBalance` call (or `getTokenAccountsByOwner`/`getProgramAccounts` with `jsonParsed` encoding, which use the same `get_mint_owner_and_additional_data`/`get_parsed_token_accounts` path) will then decode the fake mint and return an attacker-controlled `decimals` field, producing a misleading `uiAmount`/`uiAmountString` for a real, verifiable token account. This is decoder misreporting served directly to wallets/explorers/bots that rely on RPC-reported balances, achievable with a single unprivileged call.

### Likelihood Explanation
Trivial to trigger: no special role, no multiple RPC calls, and no elaborate setup beyond creating two ordinary accounts and issuing one `getTokenAccountBalance` (or `jsonParsed`-encoded `getProgramAccounts`/`getTokenAccountsByOwner`) request.

### Recommendation
Before unpacking an account as a `Mint`, verify `mint_account.owner()` is a known SPL token program id (`is_known_spl_token_id`), matching the check already applied to the token account itself, in `get_mint_owner_and_additional_data` and in `get_parsed_token_account`/`get_parsed_token_accounts`.

### Proof of Concept
1. Create account `F` owned by the System Program whose data bytes are crafted to satisfy `spl_token_2022_interface::state::Mint`'s packed layout with `is_initialized = true` and `decimals = 0` (or any chosen value).
2. Create a normal SPL Token account `T` (owned by the real `spl_token` program) whose `mint` field is set to `F`'s pubkey, with some `amount`.
3. Call `getTokenAccountBalance` for `T` (or `getProgramAccounts`/`getTokenAccountsByOwner` with `encoding: jsonParsed`).
4. Observe that `rpc/src/rpc.rs::get_token_account_balance` → `get_mint_owner_and_additional_data` (`rpc/src/parsed_token_accounts.rs:92-108`) unpacks `F`'s forged bytes as a legitimate `Mint` and returns an attacker-chosen `decimals`, producing a fabricated `uiAmount` for account `T` despite `F` never having been created by any real SPL Token program.

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}
