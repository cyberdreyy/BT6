### Title
ProgrammableBorrower trusts unsanitized ERC4626 `convertToAssets` for minted epoch interest — donation/inflation of the external vault mints unbacked strategy tokens - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
In programmable-borrower mode with `isInterestMinted`, the epoch interest minted into the pool comes entirely from `IProgrammableBorrower.totalInterestDueNow()`, which is computed from the external ERC4626 vault's `convertToAssets` view (`_currentVaultAssets`). That value is returned by a third-party contract and is never sanity-checked: the `maxApr` cap that bounds minted interest in `IdleCDOEpochVariant._stopEpoch` is unreachable in programmable mode because `_resolveStopEpochInterest` reverts for `_interest > 1`. An unprivileged user of the same ERC4626 vault (e.g. a MetaMorpho-style vault whose `totalAssets` counts direct token transfers or whose share price can be moved via deposits/withdrawals into underlying markets) can inflate `convertToAssets`, making `totalInterestDueNow` report phantom interest that is then minted as unbacked strategy tokens and reflected in tranche prices — the same "attacker-controlled attributes injected into the system" pattern as CVE-2024-47076. ### Finding Description
`totalInterestDueNow()` (ProgrammableBorrower.sol:330) returns `vaultInterest + borrowerInterestAccruedNow + bufferInterest - loss`, where `vaultInterest` is derived from `_currentVaultAssets()` — i.e. `vault.convertToAssets(vault.balanceOf(this))` on an externally supplied ERC4626. There is no bound, no cross-check against `borrowerApr`/elapsed time, and no tolerance band.

`_stopEpoch` in `IdleCDOEpochVariant.sol` calls `_resolveStopEpochInterest` which, for programmable borrowers, forces `_interest ∈ {0,1}` (line 1003) and returns `totalInterestDueNow()` verbatim (line 1004). The only sanity bound on minted interest — the `maxApr` check at lines 377–380 — requires `_interest > 1`, so it can never run when the borrower is programmable. In minted mode (`isInterestMinted`, non-close), `mintStrategyTokens(_grossInterest)` (line 430) creates unbacked strategy tokens equal to the reported interest, `_updateAccounting` raises tranche `virtualPrice`, and fee receivers are minted shares at the inflated price.

### Impact Explanation
An attacker who is simultaneously (a) a KYC-passed tranche holder and (b) a user of the configured ERC4626 vault can, during a running epoch, inflate the vault's reported `convertToAssets` for the borrower's shares (donation to a balanceOf-based vault, or price manipulation of the vault's underlying markets — both reachable by any unprivileged vault depositor). At `stopEpoch`, the phantom delta is minted as strategy tokens and distributed across tranche holders via `virtualPrice`, while the attacker recovers most of the donation by redeeming their own vault shares. The attacker then exits at the inflated tranche price (withdrawal request or post-stop claim), draining real underlying and leaving remaining LPs with strategy tokens backed by fewer assets than NAV claims — direct insolvency in proportion to the manipulated delta.

### Likelihood Explanation
Requires: programmable-borrower mode, `isInterestMinted = true` (the tested production configuration), and an ERC4626 vault whose per-share valuation an unprivileged depositor can move (balance-of vaults, or Morpho vaults over markets with manipulable utilization/bad debt). `setVault` is honest-manager-gated but accepts any ERC4626 with matching asset, so no privileged misbehavior is needed. The attack needs capital roughly equal to the intended theft, recouped via vault-share redemption; profit scales with the attacker's share of tranche supply.

### Recommendation
Bound programmatic interest: re-enable the `maxApr` cap for programmable borrowers by comparing `totalInterestDueNow()` against `_calcInterestWithApr(getContractValue(), maxApr) + pendingWithdrawFees` regardless of the `_interest` sentinel, and/or cap vault-reported interest to `elapsed * principal * borrowerApr`-style expectations. Preferably, compute epoch interest from immutable borrower-accounting terms plus a realized-vault delta measured only from actual `withdraw`/`redeem` proceeds (`epochWithdrawnFromVault` deltas), not from a live `convertToAssets` snapshot.

### Proof of Concept
Foundry-fork outline:
1. Configure credit vault with programmable borrower, `isInterestMinted`, vault = ERC4626 whose `totalAssets` includes direct `underlying` balance (test fork already uses MetaMorpho; alternatively deploy a minimal ERC4626 wrapper over a Morpho market).
2. Attacker: `depositAA` (KYC'd), `startEpoch`, then `deposit` into the ERC4626 vault to obtain vault shares and `underlying.transfer(vault, X)` to raise `convertToAssets` for the borrower's position (or manipulate the underlying market so PPS jumps).
3. `warp(epochEndDate + 1)`; `manager.stopEpoch(0, 0)` — `totalInterestDueNow()` includes phantom `X`, `mintStrategyTokens(X)` mints unbacked tokens, `virtualPrice` rises.
4. Attacker `redeem`s vault shares recovering ~X, then `requestWithdraw`/`claimWithdrawRequest` at inflated tranche price; assert `underlying` received > deposited while `getContractValue` no longer covers remaining tranche NAV.

  function totalInterestDueNow() external view returns (uint256) {
    (uint256 vaultInterest, uint256 loss) = _vaultNetInterest();
    uint256 totalGain = vaultInterest + borrowerInterestAccruedNow() + bufferInterest;
    return totalGain > loss ? totalGain - loss : 0;
  }

  /// @notice Compute the net vault delta split into interest and loss (mutually exclusive).
  function _vaultNetInterest() internal view returns (uint256 interest, uint256 loss) {
    if (!epochAccountingActive) return (0, 0);
    uint256 earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault;
    uint256 principalAssets = epochStartVaultAssets + epochDepositedToVault;
    int256 netDelta = bufferedVaultDelta + int256(earnedAssets) - int256(principalAssets);
    if (netDelta > 0) {
      interest = uint256(netDelta);
    } else {
      loss = uint256(-netDelta);
    }
  }
