I have sufficient evidence to identify a clear analog. Let me verify one more detail about whether the node serializes proposal validation (which would turn this into a full wedge) versus per-request threads.### Title
Signer's transaction-replay block-validation path runs proposer-controlled transactions with unbounded execution/analysis budget and no deadline, unlike the main validation loop - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
`NakamotoBlockProposal::validate()` is the node-side handler that signers call (via `submit_block_for_validation`) to decide whether to sign a proposed block [1](#0-0) . When a signer runs with `validate_with_replay_tx = true` [2](#0-1) , `validate()` calls `self.validate_replay(...)` **before** it builds the bounded per-tx resource budgets or the overall `block_deadline` [3](#0-2) . Every call inside `validate_replay` executes transactions — including the block's own proposer-supplied transactions (`self.block.txs`) — using `TransactionResourceBudgets::unlimited()` and with no deadline check at all [4](#0-3) [5](#0-4) . This is the same bug class as the reported issue (a per-message/per-call resource limit that is enforced elsewhere in the system is silently skipped on one code path, allowing an attacker to amplify resource consumption via crafted, expensive computation).

### Finding Description
The main tx-processing loop in `validate()` explicitly constructs bounded budgets, tying transaction execution and analysis time to `block_proposal_max_tx_execution_time_secs` / `block_proposal_max_tx_analysis_time_secs` / `block_proposal_max_tx_mem_bytes`, and additionally enforces a wall-clock `block_deadline` between transactions [6](#0-5) . This machinery was purpose-built to stop a malicious contract from stalling proposal validation, as documented in the signer changelog: *"caps the time a single transaction is allowed to run during block proposal validation"* [7](#0-6) , and reiterated in the resource-limiter design comment: budgets must be limited "during the miner's block construction and the signer node's proposal validation to ensure that a smart contract that triggers excessive memory usage or delays is not included in the chain" [8](#0-7) .

However, `validate_replay()` — invoked earlier in the same `validate()` call, before those bounded budgets/deadline even exist — mines every transaction (both replay-set candidates and the block's actual proposer-supplied transactions) with `TransactionResourceBudgets::unlimited()`:
- the mismatch-check loop skip-probe: [9](#0-8) 
- the "apply the block's transaction" step, run unconditionally for every tx in the proposed block: [4](#0-3) 
- the exhaustion probe over the remaining replay set: [10](#0-9) 

None of these calls check `Instant::now()` against any deadline, unlike the main loop's explicit per-iteration check at line 760 [11](#0-10) . Because the block's own transactions (fully controlled by the proposing miner) are executed here with `unlimited()` budgets, a single block proposer can include one transaction whose Clarity execution is deliberately expensive (deep recursion/heavy iteration bounded only by Clarity's deterministic cost-tracker limits, not by wall-clock/memory), and that transaction will run to completion (or to the Clarity-level cost-exhaustion, which can itself take a long time to reach) with no execution-time or memory ceiling, in a place the changelog/design docs explicitly say must always be bounded on this exact validation path.

### Impact Explanation
This breaks the intended equality "every path that executes proposer-controlled Clarity code during signer block-validation is time/memory bounded" for the subset of signers running `validate_with_replay_tx = true`. The practical outcome is a liveness wedge on the affected signer's node-side validation: a crafted proposal can force the block-validation thread to run far longer (or consume far more memory) than `block_proposal_max_tx_execution_time_secs`/`block_proposal_max_tx_mem_bytes` are supposed to allow, exactly mirroring the reported CWE-400/CWE-770 class ("tx gas limit is not enforced ... combined with recursive calls ... can amplify gas consumption exponentially"). Per the rules, a signer wedged into never signing valid blocks in a timely fashion is a High-impact outcome, since the signer cannot promptly validate/vote on the proposal (or subsequent ones, if the underlying chainstate handle is serialized/locked while the runaway computation executes), degrading its participation in the 70%-threshold signing protocol described in `docs/signer-flows.md` [12](#0-11) .

### Likelihood Explanation
The trigger requires only: (1) a single miner slot to propose a block (no signer majority or key compromise needed), and (2) a signer that has opted into `validate_with_replay_tx = true`, an explicitly supported (if "experimental") configuration option [2](#0-1) . The vulnerable code path (`validate_replay`) is unconditionally reached whenever the proposal handler is given a replay-tx set, which the signer itself attaches on every `submit_block_for_validation` call when that flag is set [13](#0-12) . This makes the analog concretely reachable by a one-slot miner without needing majority collusion.

### Recommendation
Move `validate_replay()`'s invocation after (or make it share) the bounded `TransactionResourceBudgets` and `block_deadline` construction that the main loop uses, and pass those same bounded budgets into all three `try_mine_tx_with_len` calls inside `validate_replay` instead of `TransactionResourceBudgets::unlimited()`. Additionally add a deadline check inside `validate_replay`'s loops, consistent with the main loop's per-iteration `block_deadline` check.

### Proof of Concept
1. Configure a signer with `validate_with_replay_tx = true`.
2. As the current miner (one slot), craft a block whose transaction list includes a transaction that performs deep/expensive Clarity computation (e.g., deeply nested/recursive calls bounded only by the Clarity cost tracker, not wall-clock) that does not match the head of the signer's current replay set.
3. Submit the proposal; on the signer's node, `NakamotoBlockProposal::validate()` calls `validate_replay()` first [14](#0-13) , which executes the block's transaction via `try_mine_tx_with_len(..., &TransactionResourceBudgets::unlimited(), ...)` [15](#0-14)  with no execution-time/memory bound and no deadline check, unlike the identical operation performed later in the bounded main loop [16](#0-15) .
4. Observe that `block_proposal_max_tx_execution_time_secs` has no effect on this phase, and the validation thread's runtime for this proposal is bounded only by the expensiveness of the crafted transaction itself.

Note: I was not able to fully trace within available context whether the node serializes concurrent `/v3/block_proposal` validation requests (e.g., via a shared chainstate lock) in a way that would additionally block *other* proposals while the runaway one runs; that would upgrade this from "delays one proposal past its timeout" to "wedges the node against all proposals." This should be verified directly in the node's HTTP/RPC dispatch and `StacksChainState` locking code before finalizing severity.
