### Title
Loss-adjusted withdraw receipts keyed to a stale `epochNumber` become claimable at par, draining the vault — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.collectWithdrawFunds` records a partial-funding haircut under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` is bumped inside `deposit()` during the same `stopEpoch` flow. If the CDO deposits epoch proceeds to the strategy before it collects withdraw funds (the natural ordering, since the deposit is what supplies the funds to collect), the haircut price is stored under the *new* epoch while every affected receipt still points at the *old* epoch via `lastWithdrawRequest`. The loss-adjusted claim path then finds a zero price, silently falls through to `_claimFundedWithdrawRequest`, and pays the full unhaircutted `withdrawsRequests` — even though only the reduced amount was ever transferred in. This is the on-chain analog of CVE-2016-1966's stale/dangling wrapper pointer: a receipt object keyed to a reclaimed epoch index is dereferenced as if still valid.

### Finding Description [1](#0-0) 
`collectWithdrawFunds(_amount)` computes `lossRecoveryPrice = _amount * 1e18 / pendingBasis` and stores it at `lossRecoveryPriceByEpoch[epochNumber]` when `_amount < pendingBasis` (the `stopEpochWithDuration` loss path). At that point `pendingWithdraws` is zeroed and only `_amount` underlying is pulled into the strategy.

Meanwhile `deposit()` increments `epochNumber` whenever `IIdleCDOEpochVariant(idleCDO).isEpochRunning()` is still true — i.e., during `stopEpoch` before the running flag is cleared: [2](#0-1) 

Users' receipts were recorded with `lastWithdrawRequest[_user] = currentEpoch` at request time (the *pre-stop* epoch): [3](#0-2) 

On claim, `_claimLossAdjustedWithdrawRequest` only looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. If the haircut was stored under `epochNumber+1`, this lookup returns 0 and the function returns without clearing anything: [4](#0-3) 

Execution then reaches `_claimFundedWithdrawRequest`. Since `epochNumber` has already advanced past `lastWithdrawRequest`, the "wait one epoch" gate passes, and the user is paid `withdrawsRequests[_user]` **in full** via `_transferFundedClaim`: [5](#0-4) 

The guard in `requestWithdraw` that forces users to claim a loss-adjusted receipt before re-requesting uses the same stale key (`lossRecoveryPriceByEpoch[lastWithdrawRequest]`), so it also sees 0 and does not block new requests: [6](#0-5) 

### Impact Explanation
Broken invariant: loss waterfall / one-receipt-one-funded-payout. The strategy only received `_amount < pendingBasis` underlying for the defaulted-on receipts, but each receipt pays out its full pre-haircut basis. First claimants withdraw more than their pro-rata share; once the funded balance is exhausted, later claimants' `safeTransfer` reverts — permanent loss for the tail of the queue, i.e., direct fund theft by earlier claimants and insolvency of the receipt pool. Quantified: with `pendingBasis = 1000` and `_amount = 600` (40% loss), the first claimant of a 500 receipt takes 500 instead of 300; the remaining receipts (500 basis) are backed by only 100 underlying. The same stale-key hole lets an attacker keep stacking new requests on top of the unhaircutted balance.

### Likelihood Explanation
Requires an epoch stopped with a realized loss (`stopEpochWithDuration`), an honest privileged action — attacker needs only an ordinary pending withdraw request in that epoch. The trigger condition is the intra-`stopEpoch` ordering: if `deposit()` runs while `isEpochRunning()` is still true (it increments `epochNumber`) before `collectWithdrawFunds`, the miskeying always occurs. Whether this fires depends on the call order inside `IdleCDOEpochVariant.stopEpoch`/`_beforeStopEpoch`, which I was not able to fully verify within the indexed context — if `collectWithdrawFunds` is invoked strictly before any `deposit`, the key is consistent and the bug does not manifest; this ordering must be confirmed in `contracts/IdleCDOEpochVariant.sol` before treating the finding as live.

### Recommendation
Key the loss price by the epoch in which the receipts were requested, not by the mutable global `epochNumber` at collection time — e.g., have the CDO pass the request epoch explicitly, or snapshot `epochNumber` at `stopEpoch` entry and use that snapshot in `collectWithdrawFunds`. Additionally, make `_claimFundedWithdrawRequest` defensively check that no `lossRecoveryPriceByEpoch` entry covers any epoch present in `withdrawsRequestsByEpoch[_user]`, and make `requestWithdraw`'s pending-loss guard iterate or track a per-user loss-epoch pointer rather than relying solely on `lastWithdrawRequest`.

```solidity
// Foundry fork test sketch (IdleCreditVault.t.sol harness)
// Precondition: epoch N running, unscaledApr != 0, user U has 500 pending
// withdraw requested in epoch N (lastWithdrawRequest[U] == N,
// withdrawsRequestsByEpoch[U][N] == 500, pendingWithdraws == 1000 total).

// 1. manager calls cdo.stopEpochWithDuration(loss) so that strategy receives:
//    a) deposit(...) while isEpochRunning() == true  -> epochNumber becomes N+1
//    b) collectWithdrawFunds(600)                    -> lossRecoveryPriceByEpoch[N+1] = 0.6e18
//       pendingWithdraws = 0, strategy balance += 600
assertEq(strategy.lossRecoveryPriceByEpoch(N), 0);        // stale key: receipt epoch has no price
assertGt(strategy.lossRecoveryPriceByEpoch(N + 1), 0);    // haircut stored under wrong epoch

// 2. U claims via cdo.claimWithdrawRequest(U)
//    _claimLossAdjustedWithdrawRequest: price[N] == 0 -> returns 0
//    _claimFundedWithdrawRequest: epochNumber (N+1) > lastWithdrawRequest (N) -> pays 500, not 300
uint256 balBefore = underlying.balanceOf(U);
cdo.claimWithdrawRequest(U);
assertEq(underlying.balanceOf(U) - balBefore, 500);       // full basis paid, loss not applied

// 3. Second claimant W (500 basis) tries to claim: only 100 underlying left -> revert
vm.expectRevert();
cdo.claimWithdrawRequest(W);                               // permanent freeze of remaining receipts
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }
```
