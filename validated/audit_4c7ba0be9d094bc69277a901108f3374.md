### Title
ProgrammableBorrower accepts zero-share ERC4626 deposits, enabling first-depositor vault drainage - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
`ProgrammableBorrower._depositToVault` deposits idle pool funds into an ERC4626 vault but never validates that nonzero or economically sufficient shares were returned. [1](#0-0) 

### Finding Description
During `onStartEpoch`, the contract snapshots the pool’s full on-hand balance as epoch principal and then deposits that entire balance into the configured vault. [2](#0-1) 

An ERC4626 vault without virtual-share protection can be inflation-seeded by an ordinary vault user: deposit `1` asset for `1` share, donate `P` assets, and cause the borrower adapter’s `P`-asset deposit to mint `P * 1 / (P + 1) == 0` shares. [3](#0-2) 

Because `_depositToVault` discards the returned share count and performs no post-deposit coverage check, the adapter retains zero vault shares while the donated assets and deposited pool funds remain claimable by the attacker’s single share. [1](#0-0) 

Subsequent accounting derives the vault position from `vault.balanceOf(address(this))` and `convertToAssets(shares)`, so the stolen deposit is represented as zero remaining assets. [4](#0-3) 

When the pool is closed, `IdleCDOEpochVariant` attempts to pull the full recalled principal from the borrower adapter and enters the borrower-default path when that transfer fails. [5](#0-4) [6](#0-5) 

### Impact Explanation
For an epoch deposit of `P`, an attacker spends `1 + P` assets to seed and inflate the vault, then redeems one share for `1 + P + P`, yielding a net profit of `P` and leaving the facility with no backing for the corresponding principal. [7](#0-6) 

This breaks solvency and the fair mint/burn invariant because the CDO records strategy-token principal while the programmable borrower has already lost the underlying assets through the zero-share deposit. [5](#0-4) 

The eventual close-pool recall fails and marks the vault defaulted, permanently impairing lender principal unless recovery later returns funds. [8](#0-7) 

### Likelihood Explanation
The attack requires the configured ERC4626 vault to have an empty or very small supply and to calculate deposits using a raw asset-balance ratio without inflation protection. [3](#0-2) 

`ProgrammableBorrower` supports operator-configured ERC4626 vaults, validates only the vault’s asset, and does not enforce a minimum share issuance or a post-deposit asset-value invariant. [9](#0-8) [1](#0-0) 

The attacker needs only ordinary permissionless access to the selected vault and can execute the seeding before the honest manager starts the next epoch. [10](#0-9) 

### Recommendation
Require a safe ERC4626 integration invariant before and after every deposit: compute `shares = vault.deposit(...)`, require `shares > 0`, and require `vault.convertToAssets(shares)` to cover the deposited assets within an explicitly bounded rounding tolerance. [1](#0-0) 

After `onStartEpoch` completes, verify that the new vault share position economically covers the snapshotted `epochStartVaultAssets`, and revert the epoch start rather than continuing with stranded principal. [11](#0-10) 

The deployment should also restrict supported vaults to ERC4626 implementations with virtual shares or equivalent first-depositor protection, rather than accepting any asset-matching vault. [12](#0-11)

function testInflatedVaultStealsEpochDeposit() external {
    MockStopEpochLiquidityVault inflatedVault = new MockStopEpochLiquidityVault(USDC);
    _setUpProgrammableBorrowerCreditVault(FORK_BLOCK, address(inflatedVault));

    uint256 amount = 10_000 * oneScale;
    address attacker = makeAddr("vaultAttacker");

    deal(USDC, attacker, amount + 1, true);

    vm.startPrank(attacker);
    underlying.approve(address(inflatedVault), type(uint256).max);
    inflatedVault.deposit(1, attacker);              // 1 share, 1 wei assets
    underlying.transfer(address(inflatedVault), amount); // donation inflates PPS
    vm.stopPrank();

    idleCDO.depositAA(amount);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // ProgrammableBorrower deposited `amount` but received zero shares:
    // shares = amount * 1 / (1 + amount) == 0.
    assertEq(inflatedVault.balanceOf(address(programmableBorrower)), 0);
    assertEq(programmableBorrower.vaultSharesBalance(), 0);
    assertEq(programmableBorrower.totalUnderlying(), 0);

    vm.prank(attacker);
    uint256 redeemed = inflatedVault.redeem(1, attacker, attacker);

    assertEq(redeemed, amount + amount + 1);
    assertEq(underlying.balanceOf(attacker), amount + amount + 1);

    vm.warp(cdoEpoch.epochEndDate());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 1);

    assertTrue(cdoEpoch.defaulted());
    assertEq(programmableBorrower.totalUnderlying(), 0);
}

  /// @notice Handle borrower default
  function _handleBorrowerDefault(uint256 funds) internal {
    defaulted = true;
    // Do not reopen instant claims here. They remain disabled when funding is pending;
    // successful full funding is the only path that enables them before finalization.
