### Title
Signer's cross-tenure equivocation guard bypasses `conflict_still_blocks` once the fixed wall-clock freshness window elapses, letting a signer sign two conflicting blocks at the same height - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
The equivocation guard that stops a signer from double-signing at the pre-commit → signature step (`handle_block_pre_commit`) only consults the node's live chain state (`conflict_still_blocks`) for conflicts whose `last_endorsed` timestamp is still inside a fixed wall-clock window (`tenure_last_block_proposal_timeout`). Once that local timer expires, the conflict is treated as dead without ever asking the node whether the earlier block is still canonical - the exact "stale, infrequently-updated state used to authorize an action that should have been blocked by fresher truth" pattern described in the report (there: a manually/rarely-updated price feed; here: a manually-configured, node-state-independent timeout).

### Finding Description
`handle_block_pre_commit` computes signed conflicts across *all* tenures at or above the proposed height with `get_signed_conflicts`, then filters for one that still blocks: [1](#0-0) 

The filter is: `conflict.last_endorsed > freshness_cutoff && !reorg_permit_stands(...) && conflict_still_blocks(...)`. This means `conflict_still_blocks` - the only place the node is actually asked whether the earlier signed block is still part of the canonical chain - is *never invoked* for a conflict whose `last_endorsed` timestamp falls outside the fixed `tenure_last_block_proposal_timeout` window, regardless of whether the node's canonical chain still reaches that block: [2](#0-1) 

The follow-up check (lines ~1423+) that re-examines "stale" conflicts against the node's tip is explicitly scoped to conflicts in the block's *own* tenure only (per the design doc: "a stale conflict in this block's own tenure still blocks if the node already has that tenure at or above the proposed height"), so a stale conflict living in a *different* tenure at the same height is never re-verified against the node at all: [3](#0-2) 

This directly contradicts the guard's own stated safety principle documented immediately above it - "whenever the node cannot be asked, the conflict keeps blocking... wrongly signing cannot be taken back" - because here the node is deliberately *not asked* once the fixed timer has elapsed, even though asking is cheap and the whole point of `conflict_still_blocks` is to derive liveness from ground truth rather than a local clock: [4](#0-3) 

The equality this breaks is the "one-signature-per-height" invariant that the whole pre-commit conflict machinery exists to enforce (as summarized in the design doc: "signing both would be the double-sign this guard exists for") - the guard's decision to block or allow a second signature is supposed to track "is this block still live in the node's canonical chain", but it silently degrades to "has enough wall-clock time passed since I signed" for any conflict outside the signer's own tenure.

### Impact Explanation
If a miner (or a competing tenure resulting from a Bitcoin fork window) can get a second, conflicting block B accepted to the pre-commit threshold at the same Stacks height h as a previously-signed block A in a different tenure, and this happens after `tenure_last_block_proposal_timeout` seconds have elapsed since A was last endorsed, the signer will sign B without ever checking whether A is still the node's canonical tip at height h. If A is in fact still live (e.g. it has been globally accepted and the node's canonical chain still includes it), the signer ends up placing valid signatures over two conflicting blocks at the same height - a Critical impact per the rules ("a signer signing an invalid, non-canonical, or conflicting block"). This can enable a chain split: two blocks at the same height, each independently reaching threshold signatures from possibly overlapping signer sets.

### Likelihood Explanation
This requires only a single miner controlling block production timing across two tenures (or exploiting an ordinary Bitcoin-fork race that the protocol already tolerates for reorg handling) plus the passage of `tenure_last_block_proposal_timeout` real time - no majority of signers, no other signer's key, and no StackerDB/majority assumptions are needed. `tenure_last_block_proposal_timeout` is a signer-configurable value on the order of tens of seconds, well within normal tenure-change/reorg timing windows already exercised by the codebase's own reorg tests, making the window realistically reachable during ordinary chain operation, especially under any latency or slow block-processing conditions.

### Recommendation
Do not use `last_endorsed > freshness_cutoff` as a gate on whether to even ask the node via `conflict_still_blocks`. Instead, always invoke `conflict_still_blocks` (or an equivalent node-derived liveness check) for every returned conflict regardless of tenure, and only skip the node round-trip once `conflict_still_blocks` itself has established that the conflict's tenure is orphaned or the block is otherwise dead. If a caching/performance optimization is desired, cache negative liveness results (proven-dead conflicts) rather than gating on elapsed wall-clock time, so a still-canonical block is never treated as if it can be safely superseded merely because the local timer expired.

### Proof of Concept
1. Signer set signs block A at height h, tenure X, at time t0 (`signed_self`/`signed_group` recorded).
2. A remains the canonical tip in the node (never reorged away).
3. A miner produces a competing tenure Y (through a Bitcoin fork or subsequent tenure-change flow the network already tolerates for reorg handling) whose proposed block B is also at height h.
4. The miner delays B's proposal (or delays gathering pre-commits for it) until `t0 + tenure_last_block_proposal_timeout` has elapsed.
5. When B reaches the pre-commit threshold, `handle_block_pre_commit`'s `get_signed_conflicts` query returns A as a conflict, but because `A.last_endorsed <= freshness_cutoff` (line 1404 filter fails), `conflict_still_blocks` is never called to check that the node's canonical chain still reaches A.
6. The own-tenure re-check (post line 1423) does not apply because A is in tenure X, not B's own tenure Y, so it is not re-verified either.
7. The signer proceeds to sign B, producing two valid signatures over conflicting blocks A and B at the same height h.

    fn conflict_still_blocks(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
        proposed_height: u64,
    ) -> bool {
        if let Ok(burn_block) = self
            .signer_db
            .get_burn_block_by_ch(&conflict.consensus_hash)
        {
            match stacks_client.get_sortition_by_burn_hash(&burn_block.block_hash) {
                Ok(_) => {
                    // The tenure's sortition is still canonical: the conflict is live at the
                    // burn chain level, so fall through to the block-level questions.
                }
                Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                    // A 404 only proves the sortition was orphaned if the node's burnchain
                    // view actually covers the burn block's height: a node still catching up
                    // 404s canonical burn blocks it hasn't processed yet (and the
                    // endpoint also 404s on internal data misses). Only trust it once the
                    // node's burnchain tip is at or past the stored burn block.
                    match stacks_client.get_peer_info() {
                        Ok(peer_info) if peer_info.burn_block_height >= burn_block.block_height => {
                            info!("{self}: A conflicting block's tenure was orphaned by a burnchain fork. The conflict no longer blocks.";
                                "conflicting_consensus_hash" => %conflict.consensus_hash,
                                "conflicting_block_height" => conflict.stacks_height,
                                "burn_block_hash" => %burn_block.block_hash,
                            );
                            return false;
                        }
                        Ok(peer_info) => {
                            info!("{self}: The node does not know a conflicting block's burn block, but its burnchain tip has not reached that height, so this does not prove the tenure was orphaned. Leaving the conflict in place.";
                                "conflicting_consensus_hash" => %conflict.consensus_hash,
                                "burn_block_hash" => %burn_block.block_hash,
                                "burn_block_height" => burn_block.block_height,
                                "node_burn_block_height" => peer_info.burn_block_height,
                            );
                            return true;
                        }
                        Err(e) => {
                            warn!("{self}: Failed to fetch the node's burnchain tip while checking a conflicting block's tenure: {e:?}. Leaving the conflict in place.";
                                "conflicting_consensus_hash" => %conflict.consensus_hash,
                            );
                            return true;
                        }
                    }
                }
                Err(e) => {
                    warn!("{self}: Failed to check whether a conflicting block's tenure is still canonical: {e:?}. Leaving the conflict in place.";
                        "conflicting_consensus_hash" => %conflict.consensus_hash,
                    );
                    return true;
                }
            }
        }
        let node_reaches_conflict = match stacks_client.get_tenure_tip(&conflict.consensus_hash) {
            Ok(tip) => tip.anchored_header.height() >= conflict.stacks_height,
            // A 404 is an answer, not a failure: the node has no blocks in that tenure at all.
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => false,
            Err(e) => {
                warn!("{self}: Failed to fetch the canonical tip of a conflicting block's tenure: {e:?}. Leaving the conflict in place.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "conflicting_block_height" => conflict.stacks_height,
                );
                return true;
            }
        };
        node_reaches_conflict
            || (!conflict.globally_accepted && conflict.stacks_height <= proposed_height)
    }

Freshness alone is not enough to hold a signature back, because a signature can
outlive the block it covers: a Bitcoin reorg can kill the block, and a dead
