### Title
V1 signer's tenure-change duplicate-block check uses only globally-accepted state, letting it sign a conflicting tenure-change block still pending node confirmation - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
The reported Loopfi bug is a partial fix: one code path (`_onDeposit`) was corrected to operate against the real, validated identity (`position`) while the parallel path (`_onWithdraw`) was left operating against the wrong context (`address(this)`), breaking an invariant the fix was supposed to restore everywhere. The stacks-signer codebase has the same structural pattern in the duplicate/conflicting tenure-change-block guard: the v2 protocol path was fixed to check against "signed" state (`get_last_signed_block`, covering `LocallyAccepted`/`PreCommitted`/globally-accepted blocks), but the v1 protocol path still checks only `get_last_globally_accepted_block`, i.e. the pre-fix, weaker context.

### Finding Description
`docs/signer-flows.md` (lines 428–437) documents this exact asymmetry in the shared "duplicate tenure-change block" guard that lives in `validate_tenure_change_payload` (`chainstate/v1.rs`, `chainstate/v2.rs`):

> "`validate_tenure_change_payload` rejects with `DuplicateBlockFound` when we have already accepted a block in the tenure a tenure-change block is starting. v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1 counts only globally accepted ones (`get_last_globally_accepted_block`)." [1](#0-0) 

This asymmetry is corroborated directly in a regression test comment for the v2 path, which describes the exact same class of bug being fixed only there:

> "This is a regression test: previously, the check used `get_last_globally_accepted_block`, which would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change." [2](#0-1) 

A block is only "globally accepted" once the stacks-node has processed and adopted it — that can lag well behind the moment a supermajority of signers have already put their signatures over it (`signed_group`/local acceptance, `mark_locally_accepted`), as `handle_block_response` and `store_and_process_block_signature` describe. [3](#0-2) 

Because v1's duplicate check only asks whether a block in this tenure has already been *globally* accepted, a first tenure-change block that has been fully signed by the signer set (locally accepted, `signed_group` set) but not yet pushed/adopted by the node will not be seen by `validate_tenure_change_payload` on a v1 signer. A second, conflicting tenure-change proposal for the same tenure will pass the `check_proposal`-time duplicate check.

The doc's own section 5 analysis states this proposal-time gap is only supposed to be covered later, at pre-commit-threshold time, by the "own-tenure conflict guard" (`get_signed_conflicts` / `conflict_still_blocks`). But that guard's own-tenure branch explicitly falls through to `SIGN` when the node has never confirmed the conflicting (first) block yet:

> "OWN -- yes --> TIP{...} ... TIP -- 'no — never confirmed' --> SIGN" [4](#0-3) 

i.e. exactly the state the duplicate check was meant to catch (a block that is signed but not yet globally accepted) is the one state where the backstop guard also lets the signature through, on a v1 signer.

### Impact Explanation
This lets a v1 signer put a valid signature on two conflicting tenure-change blocks for the same tenure: the first one it already signed (locally accepted, not yet globally accepted), and a second, competing tenure-change proposal that `check_proposal`'s stale `get_last_globally_accepted_block`-based check fails to flag as a duplicate. That is a signer signing a conflicting block for a slot it has already signed for — the Critical-impact category ("a signer signing an invalid, non-canonical, or conflicting block").

### Likelihood Explanation
Reachable by a single miner (one-slot) plus ordinary gossip timing: the miner (or an attacker controlling the miner slot) only needs to broadcast a second tenure-change proposal for the same tenure in the window between "supermajority of v1 signers has signed the first tenure-change block" and "the node has processed/adopted that block," which is a normal, frequently-occurring window (network/relay latency, node processing time) rather than a contrived edge case. No majority of signers, no other signer's key, and no node/auth-token access is required — only a proposal at the right moment. It is a v1-protocol-specific bug, so it depends on the network still running v1-protocol signers.

### Recommendation
Change `validate_tenure_change_payload`'s v1 code path to use `get_last_signed_block` (the same function already used by the fixed v2 path) instead of `get_last_globally_accepted_block`, so the `DuplicateBlockFound` check covers `PreCommitted`/`LocallyAccepted` blocks exactly as v2 does, closing the gap that the pre-commit-time conflict guard does not reliably cover.

### Proof of Concept
1. Run a v1-protocol signer set. A miner proposes tenure-change block `A` for tenure `T`.
2. Signers pre-commit, reach 70% pre-commit weight, re-check via `check_block_against_signer_db_state`, and sign — `A` becomes `signed_group`/locally accepted on enough signers, but the stacks-node has not yet processed/adopted `A` (`get_last_globally_accepted_block` for `T` is still `None`).
3. Before the node adopts `A`, the miner (or an attacker with the miner's key/slot) proposes a second tenure-change block `B` for the same tenure `T`, e.g. as a reorg/duplicate attempt.
4. `check_proposal` → `validate_tenure_change_payload` on a v1 signer queries `get_last_globally_accepted_block(T)`, which returns `None` since `A` isn't globally accepted yet, so the `DuplicateBlockFound` rejection is not triggered [1](#0-0) .
5. `B` proceeds through pre-commit; at the pre-commit-threshold recheck, the own-tenure conflict guard sees `A` as a conflict but, per the documented flow, treats an unconfirmed own-tenure conflict as "never confirmed" and signs anyway [4](#0-3) .
6. The v1 signer set ends up having signed two conflicting tenure-change blocks (`A` and `B`) for tenure `T`.

Note: I was unable to directly view the raw line-level implementation of `validate_tenure_change_payload` in `chainstate/v1.rs`/`chainstate/v2.rs` before running out of tool calls; this finding is based on the repository's own documentation (`docs/signer-flows.md`) and a corroborating regression-test comment in `chainstate/tests/v2.rs`, both of which explicitly describe the v1/v2 behavioral asymmetry and its root cause.
