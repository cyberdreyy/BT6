### Title
Aggregate `pendingInstantWithdraws` spans epochs but default recovery only haircuts the current-epoch instant claims, stranding or overpaying old instant receipts - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The analog of CVE-2023-32724 (an exposed/stale pointer enabling direct manipulation of the underlying object) is a bookkeeping pointer mismatch in `IdleCreditVault`: `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch` are keyed per epoch, while `pendingInstantWithdraws` and `instantWithdrawsRequests[user]` are aggregate counters spanning all epochs. `defaultPendingClaimBasis()` treats `instantWithdrawClaimsByEpoch[epochNumber]` — a single-epoch "pointer" — as if it represented the whole unfunded instant bucket. Instant receipts requested in an epoch earlier than the defaulted epoch are therefore silently excluded from the recovery basis, corrupting `defaultRecoveryPrice` and leaving the old receipt either permanently unclaimable or payable at par against the recovery reserve.

### Finding Description
When an instant withdrawal is requested, the vault records it in three places: `instantWithdrawsRequests[_user]` (aggregate), `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (per-epoch), and `instantWithdrawClaimsByEpoch[currentEpoch]` (per-epoch global), plus the aggregate `pendingInstantWithdraws` until the CDO funds it via `collectInstantWithdrawFunds` (`IdleCreditVault.sol:356-403`).

On default finalization, `defaultPendingClaimBasis()` computes the claim basis that should be haircut as:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
    basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```

`pendingInstantWithdraws != 0` is an aggregate over *all* epochs, but `instantWithdrawClaimsByEpoch[epochNumber]` only contains claims recorded in the *current* (defaulted) epoch (`IdleCreditVault.sol:644-649`). Similarly `_defaultPrefundedInstantReserve()` compares `instantWithdrawClaimsByEpoch[epochNumber]` against the aggregate `pendingInstantWithdraws` (`IdleCreditVault.sol:716-723`), and `_claimDefaultedInstantWithdrawRequest()` only clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (`IdleCreditVault.sol:842-856`).

Consequence: an instant receipt created in epoch N that is only partially funded (so `pendingInstantWithdraws` remains non-zero) and carried into a default in epoch N+1 is omitted from `totalBasis` in `finalizeDefaultRecovery` (`IdleCreditVault.sol:679-688`). The recovery price `reserveAmount * RECOVERY_FULL / totalBasis` is therefore overstated — defaulted-epoch claimants and active LPs are paid a recovery ratio computed on a smaller denominator, diluting/draining the reserve — while the old-epoch instant receipt is never haircut: `_claimDefaultedInstantWithdrawRequest` finds `instantWithdrawsRequestsByEpoch[_user][defaultEpoch] == 0` and returns without clearing anything. The stale amount persists in `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws`, which post-finalization can never be funded again. Depending on the CDO-side claim gate, the user either claims the stale amount at par through `_transferFundedClaim` (stealing recovery-reserve-adjacent funds until the `balance - reserve` guard trips) or is permanently blocked because `pendingInstantWithdraws` can never reach zero — a permanent freeze of the user's receipt and reserve dust. Post-default, the same stale `instantWithdrawsRequests[_user] != 0` also forces `requestWithdraw` to revert for that user forever (`IdleCreditVault.sol:249`).

### Impact Explanation
Direct fund impact on unprivileged lenders:
- `defaultRecoveryPrice` is computed over an understated `totalBasis`, so every defaulted claim (normal, instant, and active AA/BB recovery via `defaultBBNav`) is paid at a higher ratio than fair. Early claimants drain `defaultRecoveryReserve`; later claimants and the old-epoch instant receipt holder get nothing or revert.
- The old-epoch instant receipt itself is unclaimable at par once `balance - reserve < amount` in `_transferFundedClaim` (`IdleCreditVault.sol:897-906`), permanently freezing the user's funds as stranded vault balance, or is paid at par pre-guard if surplus exists — theft from the recovery pool.
- The affected user can never open post-default withdraw requests (`requestWithdraw` reverts while `instantWithdrawsRequests[_user] != 0`).

Quantified: the misallocation equals the carried-over instant claim `C_old`; `defaultRecoveryPrice` is inflated by a factor of `totalBasis_real / (totalBasis_real - C_old)`, and up to `C_old` becomes permanently stranded or stolen.

### Likelihood Explanation
Requires only unprivileged actions: a KYC-passing lender requests an instant withdrawal (`requestInstantWithdraw` via the CDO) in epoch N; the borrower/manager partially funds the instant queue (normal operation — `collectInstantWithdrawFunds` decrements only what is funded, `IdleCreditVault.sol:398-403`); the user does not claim; the borrower subsequently defaults in epoch N+1 and the manager calls `finalizeDefault` — all honest privileged actions the attacker merely sequences around. No guard exists to prevent carrying an unfunded instant receipt across an epoch boundary or to include non-current epochs in `instantWithdrawClaimsByEpoch` at finalization. The bug is deterministic once that state is reached; likelihood is moderate since it needs a pending instant remainder to survive into a default epoch, but no attacker-privileged capability is needed.

### Recommendation
Make the recovery basis aggregate-consistent with `pendingInstantWithdraws`: either track a per-user/per-epoch iterable set of unfunded instant claims and sum all epochs in `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, or forbid carrying unfunded instant requests across `stopEpoch` (force-fund or convert them into normal withdraw requests / loss-adjusted receipts at epoch end). In `_claimDefaultedInstantWithdrawRequest`, clear *all* epochs contributing to `instantWithdrawsRequests[_user]`, not just `defaultRecoveryEpoch`, and decrement `pendingInstantWithdraws` to zero at finalization since no further funding can arrive.

### Proof of Concept
Foundry fork/harness outline (solidity, extending `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testOldEpochInstantReceiptCorruptsDefaultRecovery() external {
    // epoch N: user requests instant withdraw
    address user = makeAddr('instant-old-epoch');
    _depositWithUser(user, 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);
    vm.prank(user);
    cdoEpoch.requestWithdraw(halfTrancheBal, address(AAtranche)); // instant path per suite config

    // fund only PART of the instant queue: pendingInstantWithdraws stays > 0
    // and instantWithdrawClaimsByEpoch[0] holds user's claim while
    // instantWithdrawsRequestsByEpoch[user][0] remains set.
    _getInstantFunds(); // borrower funds less than requested (partial)
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // epoch N+1: borrower defaults; pendingInstantWithdraws still > 0
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, 0);
    _checkDefault();

    // finalizeDefault computes basis = pendingWithdraws + instantWithdrawClaimsByEpoch[1]
    // -> user's epoch-0 instant claim is EXCLUDED from totalBasis
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    uint256 basis = vault.defaultPendingClaimBasis();
    assertEq(basis & /* epoch-0 instant part */ 0, 0); // user's claim missing
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // recoveryPrice is inflated: defaulted-epoch claimants overpaid,
    // user's epoch-0 instant receipt is stranded
    vm.prank(user);
    cdoEpoch.claimInstantWithdrawRequest(); // either reverts (balance-reserve guard / pending>0 gate)
    // or pays old receipt at par, consuming reserve meant for haircut claims
    assertGt(vault.pendingInstantWithdraws(), 0); // can never be cleared -> permanent freeze
}
```

The assertion that `defaultPendingClaimBasis()` omits the epoch-0 instant claim while `pendingInstantWithdraws > 0` is the direct demonstration of the stale epoch-keyed pointer being used as an aggregate.
