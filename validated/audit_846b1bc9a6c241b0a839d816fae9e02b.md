### Title
Raw internal error messages (including DB error text) are disclosed to unauthenticated clients via `AuthenticateExternalInitiator` error path - ([File: core/web/auth/auth.go])

### Summary
When `store.FindExternalInitiator` returns any error other than `sql.ErrNoRows`, `AuthenticateExternalInitiator` wraps it with `errors.Wrap(err, "finding external initiator")` and returns it unchanged instead of normalizing it to `auth.ErrorAuthFailed`. The `Authenticate` middleware passes this error directly to `jsonAPIError`, which serializes `err.Error()` into the JSON HTTP response body, leaking the underlying (possibly DB-originated) error string to an unauthenticated caller.

### Finding Description
`AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) calls `store.FindExternalInitiator(ctx, eia)` using attacker-supplied headers (`static.ExternalInitiatorAccessKeyHeader` / `static.ExternalInitiatorSecretHeader`). On error it only special-cases `sql.ErrNoRows`: [1](#0-0) 
Any other error (e.g. a DB connectivity error, context deadline, malformed query result, driver error) is wrapped with `errors.Wrap(err, "finding external initiator")` and returned as-is, rather than being converted to the generic `auth.ErrorAuthFailed`.

In `Authenticate`, this error is only treated specially when it equals `auth.ErrorAuthFailed` (to allow falling through to the next auth method); any other error aborts the chain and is passed straight to `jsonAPIError(c, http.StatusUnauthorized, err)`: [2](#0-1) 

`jsonAPIError` puts `err.Error()` verbatim into the JSON response body sent to the client: [3](#0-2) 

There is no redaction or generic-message translation layer between the store/ORM error and the HTTP response for this non-`ErrNoRows` branch. Any unauthenticated caller who can trigger a non-`ErrNoRows` error from `FindExternalInitiator` (e.g. transient DB failures, unexpected driver errors, or errors from underlying query building) would receive the wrapped internal error text — which could include SQL driver messages, connection info, or internal identifiers — in the HTTP 401 response body.

### Impact Explanation
This matches Chainlink's "information disclosure" bounty class: an unauthenticated external-initiator endpoint caller can potentially learn internal implementation/error details (e.g., database driver error text, internal error wrapping context) that should remain confined server-side. It does not by itself grant authentication bypass, privilege escalation, or fund movement — the impact is limited to information leakage that could aid further attacks (e.g., fingerprinting DB backend, learning about transient infra issues) rather than direct compromise. This is a lower-severity issue than a bypass but is a genuine confinement violation of the kind called out in the question.

### Likelihood Explanation
Exploitability depends entirely on being able to force `FindExternalInitiator` to return a non-`sql.ErrNoRows` error, which normally requires an actual backend malfunction (DB outage, timeout, network partition) rather than attacker-controlled input — the attacker only controls the two auth headers, and a well-formed but non-matching request just yields `sql.ErrNoRows` (converted to `ErrorAuthFailed`, not leaked). Therefore, under normal operating conditions this is not reliably triggerable by an attacker; it manifests during infrastructure incidents/degraded conditions, making standalone attacker-triggered exploitation low likelihood, though the code path is a legitimate, always-latent confinement bug per the question’s framing.

### Recommendation
In `AuthenticateExternalInitiator`, do not return the wrapped store error to the HTTP layer. Log it internally (e.g. via a logger) and return `auth.ErrorAuthFailed` (or another generic error) to the caller, consistent with how `AuthenticateByToken` still leaks similarly for its own non-`ErrNoRows`/non-`ErrUserSessionExpired` branch — both should be fixed to never propagate raw internal errors into `jsonAPIError`.

### Proof of Concept
Handler-level Go test plan:
1. Build a mock `Authenticator` (using the existing mocks, e.g. `core/bridges/mocks` / `core/sessions/mocks`) whose `FindExternalInitiator` returns a distinctive non-`sql.ErrNoRows` error, e.g. `errors.New("dial tcp 10.0.0.5:5432: connect: connection refused")`.
2. Wire up `auth.Authenticate(mockStore, auth.AuthenticateExternalInitiator)` as gin middleware in a test router, matching how `external_initiators_controller.go`/routes register it.
3. Send an HTTP request with arbitrary `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader` values via `httptest`.
4. Assert the response status is 401 and parse the JSON body (`models.JSONAPIErrors`) and assert it contains the substring `"connection refused"` / `"10.0.0.5"` — demonstrating that internal error text reaches the client — then assert this should NOT be the case after the fix (expect a generic message like `"invalid credentials"`).

```go
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
```

```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```
