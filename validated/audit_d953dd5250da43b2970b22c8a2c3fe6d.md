### Title
initCalls executed with `privileged=true` bypass all B-20 role/policy authorization guards during token creation - (File: crates/common/precompiles/src/b20_factory/logic/v1.rs)

### Summary
`FactoryV1::init_asset_token` and `FactoryV1::init_stablecoin` execute every entry of the caller-supplied `init_calls` array against the freshly created token with the `privileged` flag hard-coded to `true`, and with the caller context switched to the factory's own address via `with_caller(B20FactoryStorage::ADDRESS, ...)`. This mirrors the reported `XProvider.onlySelf` pattern: a single boolean/identity check ("is this the trusted self/factory context?") is used to gate an entire dispatch surface, and it ends up granting unrestricted access to *any* selector the caller chooses to include, not just the intended bootstrap operation (granting the initial admin role).

### Finding Description
When a token is created via the B-20 factory (`createB20`), `init_asset_token`/`init_stablecoin` iterate over the attacker/creator-supplied `init_calls: Vec<Bytes>` and route each one through `token.route(storage.storage(), &calldata, version, true, NoopPrecompileCallObserver)`: [1](#0-0) 

The `true` argument is the `privileged` flag, which is threaded straight down into every token operation's authorization gate. Looking at `grant_role`, `update_contract_uri`, and the other logic-layer functions, the guard checks are explicitly skipped whenever `privileged` is `true`: [2](#0-1) [3](#0-2) 

The same `privileged` flag flows through the dispatcher into every dispatchable selector (`mint`, `burnBlocked`, `pause`, `unpause`, `updateSupplyCap`, `updateName`, `updateSymbol`, `updateContractURI`, `grantRole`, `revokeRole`, `setRoleAdmin`, `updatePolicy`), as seen in the match arms that forward `privileged` unconditionally: [4](#0-3) 

The only place `privileged` is intended to be `true` is the single bootstrap operation of granting the `DefaultAdmin` role when no admin exists yet (this is explicitly documented on `grant_role_unchecked`): [5](#0-4) 

However, the factory does not restrict `init_calls` to that one bootstrap call — it runs the *entire* attacker-supplied list of arbitrary calldata blobs with `privileged=true`. This means the token creator (an ordinary depositor/transaction sender calling `createB20`) can smuggle in calls such as `grantRole(role, attacker)`, `updateSupplyCap(...)`, `mint(...)`/`mintWithMemo(...)`, `pause`/`unpause`, or `updatePolicy(...)` inside `init_calls`, and every one of them will skip its normal role-admin/role-holder checks because the dispatcher trusts the factory-as-self context unconditionally, exactly like the `onlySelf` modifier in the referenced report trusted `address(this)` unconditionally for the entire `xReceive` surface instead of the one legitimate self-invocation.

### Impact Explanation
An unprivileged token creator can, at token-creation time, self-grant `DefaultAdmin`/`Minter`/other privileged roles to arbitrary addresses, mint beyond intended caps, or otherwise mutate freshly created B-20 token state without holding any role — because every call routed through the factory's bootstrap loop inherits blanket authorization bypass. Depending on how downstream integrators or other factory-created tokens rely on the assumption that only the declared `initialAdmin` receives privileges at creation, this allows unauthorized privilege escalation and unbacked/altered token state on a Base precompile-backed asset, which is a concrete unauthorized-operation / unbacked-supply class of impact.

### Likelihood Explanation
Reachable directly by any unprivileged account calling the B-20 factory's `createB20` (or equivalent) with a crafted `initCalls` array — no special role or privileged context is required, matching the reachability constraint (any transaction sender / B20 token creator).

### Recommendation
Restrict the factory's bootstrap loop so `privileged=true` is applied only to the single, hard-coded `grant_role_unchecked` bootstrap call for the initial admin (as already done at lines 135-142 / 75-82), and route any additional `init_calls` through the normal, non-privileged `route(..., false, ...)` path so ordinary role/policy authorization checks apply to every operation other than the one legitimate self-bootstrap grant.

### Proof of Concept
1. Call the B-20 factory `createB20` for a new asset token, setting `initialAdmin = address(0)` (or any address) and supplying `initCalls` containing an ABI-encoded `grantRole(DEFAULT_ADMIN_ROLE, attacker)` call.
2. `init_asset_token` executes this call through `token.route(..., true, ...)` inside `with_caller(B20FactoryStorage::ADDRESS, ...)`.
3. `grant_role` sees `privileged == true` and skips `ensure_role_admin_mutations_available`/`B20Guards::ensure_role`, calling `grant_role_unchecked` directly: [6](#0-5) 
4. `attacker` now holds `DEFAULT_ADMIN_ROLE` on the newly created token without ever having been authorized, and can repeat the pattern for `mint`, `updateSupplyCap`, `pause`, etc., inside the same `initCalls` array.
