### Title
`MetaOracle.combine()` Uses Relative Oracle Timestamps Instead of Current Wall-Clock Time for Staleness Filtering — (`crates/sui-oracle/move/oracle/sources/meta_oracle.move`)

### Summary

The `combine()` function in `oracle::meta_oracle` computes its freshness window relative to `max_timestamp` — the timestamp of the most recently added oracle data source — rather than against the current on-chain `Clock` time. If all oracle operators stop submitting updates simultaneously, every data point passes the staleness filter indefinitely, and `median()` returns arbitrarily old prices with no on-chain rejection.

### Finding Description

`MetaOracle<T>` stores a `max_timestamp` field that is updated in `add_simple_oracle()`:

```move

    meta_oracle.max_timestamp = data::timestamp(option::borrow(&oracle_data));
};
``` [1](#0-0)

The same absolute-staleness gap exists in `simple_oracle::get_latest_data()`, which returns stored data with no timestamp comparison at all:

```move
public fun get_latest_data<T: store + copy>(oracle: &SimpleOracle, ticker: String): Option<Data<T>> {

The `Data<T>` struct does carry a `timestamp` field, so the raw material for a freshness check exists — it is simply never compared against the current clock in either the oracle library or the consumer pattern shown in the framework. [5](#0-4) 

### Impact Explanation

Any on-chain protocol that calls `meta_oracle::median()` or `simple_oracle::get_latest_data()` and acts on the returned price (e.g., minting, swapping, collateral valuation) will silently consume arbitrarily old prices if oracle operators stop submitting updates. The `combine()` filter passes all data as long as the oracles are mutually consistent with each other — even if the entire set is hours or days old. This matches the IronBank root cause exactly: consuming oracle data without validating freshness against the current time.

### Likelihood Explanation

Oracle liveness failures (network outages, key rotation, operator downtime) are realistic operational events. Because the staleness check is relative rather than absolute, no on-chain circuit-breaker fires when the entire oracle set goes stale. Any ordinary user can call a consuming function during a stale window and receive mispriced output.

### Recommendation

1. Add a `Clock` parameter to `median()` and `combine()`, and replace the relative floor with an absolute check:
   ```move
   assert!(clock::timestamp_ms(clock) - data::timestamp(&oracle_data) <= max_age_ms, EStalePrice);
   ```
2. Similarly, `get_latest_data()` should either accept a `Clock` and `max_age_ms` and abort on stale data, or callers must be required to perform the check themselves with a documented invariant.
3. The `max_timestamp` field in `MetaOracle` should be removed or renamed to avoid implying it represents "now".

### Proof of Concept

1. Oracle operator submits a price at `T = 1000 ms` via `submit_data()`.
2. No further updates are submitted; the chain advances to `T = 10_000_000 ms`.
3. A consumer calls `meta_oracle::median()` (no `Clock` argument accepted).
4. `add_simple_oracle()` sets `max_timestamp = 1000`.
5. `combine()` computes `min_timestamp = 1000 - 60000` which underflows to a very large `u64` value (Move wraps on subtraction in release builds) or, if `time_window_ms < max_timestamp`, to a small positive number — either way the 9-million-ms-old data point passes `data::timestamp > min_timestamp`.
6. `median()` returns the 9-million-ms-old price as `TrustedData` with no error. [6](#0-5)

        let MetaOracle { mut oracle_data, threshold, time_window_ms, ticker: _, max_timestamp } = meta_oracle;
        let min_timestamp = max_timestamp - time_window_ms;
