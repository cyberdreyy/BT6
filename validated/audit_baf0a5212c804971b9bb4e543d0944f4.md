### Title
Sequencer-forwarding RPC errors leak raw transport error text (including endpoint URL) to any `eth_sendRawTransaction` caller - (File: crates/execution/rpc/src/error.rs)

### Summary
`BaseEthApiError`/`SequencerClientError`'s conversion into a JSON-RPC `ErrorObject` forwards the raw `to_string()` of any non-`ErrorResp` `alloy_transport::RpcError<TransportErrorKind>` variant (transport failures, serialization errors, connection failures) straight back to the calling JSON-RPC client, with no redaction.

### Finding Description
When an unprivileged, anonymous RPC client calls `eth_sendRawTransaction`, `send_pool_transaction` forwards the raw tx to the configured sequencer via `SequencerClient::forward_raw_transaction` [1](#0-0) . That call goes through `SequencerClient::request`, which wraps the underlying `alloy_rpc_client` HTTP/WS transport error as a `SequencerClientError::HttpError(RpcError<TransportErrorKind>)` [2](#0-1) .

The conversion of `SequencerClientError` into the outward-facing `jsonrpsee` `ErrorObject` only special-cases the `RpcError::ErrorResp` variant (a structured server error payload); every other `RpcError` variant (`Transport`, `SerError`, `DeserError`, `NullResp`, `UnsupportedFeature`, `LocalUsageError`) falls through to `err.to_string()` verbatim, with `INTERNAL_ERROR_CODE` and no sanitization:

```rust
impl From<SequencerClientError> for jsonrpsee_types::error::ErrorObject<'static> {
    fn from(err: SequencerClientError) -> Self {
        match err {
            SequencerClientError::HttpError(RpcError::ErrorResp(ErrorPayload { code, message, data })) => ...,
            err => jsonrpsee_types::error::ErrorObject::owned(
                INTERNAL_ERROR_CODE,
                err.to_string(),
                None::<String>,
            ),
        }
    }
}
``` [3](#0-2) 

Transport-level errors from the underlying HTTP client (e.g. reqwest's `RpcError::Transport(TransportErrorKind::Custom(...))`) typically embed the target request URL in their `Display` implementation (e.g. `"error sending request for url (https://...)"`). The sequencer endpoint URL is operator-configured via `--sequencer-http`/`SEQUENCER_HTTP` and, in common deployment patterns for hosted RPC providers, embeds an API key or auth token directly in the URL path/query string. Any transient connectivity failure between the RPC node and its sequencer (timeout, DNS failure, TLS error, connection reset) is therefore capable of surfacing that URL — and any embedded credential — verbatim in the JSON-RPC response returned to the original, completely unauthenticated caller.

This mirrors the CVE-2021-29040 bug class exactly: overly verbose error messages exposing internal system details to a remote, unprivileged caller via a JSON RPC path, but here the disclosed detail can be an infrastructure credential rather than a generic stack trace.

Note by contrast that the codebase elsewhere deliberately redacts equivalent internal details before returning them over RPC — e.g. `sequencer_admin_error` in `crates/consensus/rpc/src/admin.rs` explicitly collapses `RequestError`/`ResponseError` variants into a generic `InternalError` with a unit test asserting redaction [4](#0-3) , and the tx-manager's `RpcErrorClassifier::classify_rpc_error` intentionally replaces non-`ErrorResp` transport messages with a fixed string because "they may expose credentials in RPC URLs" [5](#0-4) . The `eth_sendRawTransaction` → sequencer-forwarding path in `crates/execution/rpc/src/error.rs` was not brought into line with that same discipline.

### Impact Explanation
If the sequencer endpoint URL configured on a production execution RPC node embeds a bearer token/API key (a widely used pattern for managed RPC infra), any transient network hiccup between the public-facing RPC node and its sequencer causes that secret to be echoed back, in full, to the anonymous caller who happened to submit a transaction at that moment. This is a remotely triggerable secret/infrastructure-detail disclosure reachable from a single unauthenticated `eth_sendRawTransaction` call — no privilege, deposit, or special role required. Depending on what the leaked credential authorizes (e.g., write access to the sequencer's admin surface, rate-limited quota, or other services sharing the same key), this can escalate well beyond a generic "verbose error message" issue.

### Likelihood Explanation
The trigger condition (any transport-level failure talking to the sequencer: timeout, TLS handshake failure, connection reset, DNS blip) is common in production networking and is not attacker-controlled in timing, but an attacker can repeatedly submit transactions and simply wait for/force a window of sequencer unavailability (e.g., during sequencer restarts/deploys) to reliably capture the leaked text. The code path is unconditionally reachable by any RPC client with no authentication.

### Recommendation
Sanitize non-`ErrorResp` `SequencerClientError` variants before returning them to the RPC caller, following the same pattern already used in `crates/consensus/rpc/src/admin.rs` and `crates/utilities/tx-manager/src/error.rs`: return a fixed, generic message (e.g. `"failed to forward transaction to sequencer"`) for `RpcError::Transport`/`SerError`/`DeserError`/`NullResp`/other variants, and log the detailed `err.to_string()` only server-side via `tracing`/`warn!` (which the code already does at the call sites in `sequencer.rs`/`transaction.rs`). Only the structured `ErrorResp` (`code`, `message`, `data`) coming from the sequencer's own JSON-RPC error response — which is itself an untrusted upstream payload — should be considered for pass-through, and even that should be reviewed for whether the sequencer's own error text could leak internal details.

### Proof of Concept
1. Configure a production node with `--sequencer-http https://sequencer.example.com/rpc?apikey=SECRET123` (or any URL containing a credential).
2. Trigger (or wait for) a transient network failure between the RPC node and the sequencer endpoint (e.g., sequencer restart, DNS resolution failure, connection timeout).
3. As an anonymous client, call `eth_sendRawTransaction` with any validly-signed transaction.
4. `send_pool_transaction` forwards the raw tx via `SequencerClient::forward_raw_transaction` [6](#0-5) ; the underlying HTTP client failure becomes a non-`ErrorResp` `RpcError`, converted via `From<SequencerClientError>` into an `ErrorObject` whose `message` is `err.to_string()` [7](#0-6) , which typically embeds the full request URL including `apikey=SECRET123`.
5. The JSON-RPC error response returned to the caller contains the sequencer URL and embedded credential.

    pub async fn request<Params: RpcSend, Resp: RpcRecv>(
        &self,
        method: &str,
        params: Params,
    ) -> Result<Resp, SequencerClientError> {
        let resp =
            self.client().request::<Params, Resp>(method.to_string(), params).await.inspect_err(
                |err| {
                    warn!(
                        target: "rpc::sequencer",
                        %err,
                        "HTTP request to sequencer failed",
                    );
                },
            )?;
        Ok(resp)
    }

    /// Forwards a transaction to the sequencer endpoint.
    pub async fn forward_raw_transaction(&self, tx: &[u8]) -> Result<B256, SequencerClientError> {
        let start = Instant::now();
        let rlp_hex = hex::encode_prefixed(tx);
        let tx_hash =
            self.request("eth_sendRawTransaction", (rlp_hex,)).await.inspect_err(|err| {
                warn!(

                    %err,
                    "Failed to forward transaction to sequencer",
                );
            })?;
        SequencerMetrics::record_forward_latency(start.elapsed());
        Ok(tx_hash)
