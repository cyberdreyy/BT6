### Title
User enumeration and MFA-status disclosure via distinguishable error responses and timing in `CreateSession` - ([File: core/sessions/localauth/orm.go])

### Summary
`SessionsController.Create` returns to the unauthenticated caller whatever error string `CreateSession` produces, and `CreateSession` produces materially different, distinguishable outcomes depending on whether the email exists, whether the password is correct, and whether MFA is enabled, with an added timing difference from bcrypt only running for existing accounts. This lets an unauthenticated caller enumerate valid emails and, once a valid password is known, distinguish MFA-enabled accounts.

### Finding Description
`SessionsController.Create` (core/web/sessions_controller.go:56-60) calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` and forwards the returned error verbatim to the client via `jsonAPIError(c, http.StatusUnauthorized, err)` [1](#0-0) , and `jsonAPIError` serializes `err.Error()` directly into the JSON response body [2](#0-1) .

In `CreateSession` (core/sessions/localauth/orm.go:144-199):
- If the email does not exist in the DB, `FindUser` returns a SQL "no rows" error immediately, without ever calling `utils.CheckPasswordHash` (bcrypt), i.e. a fast failure path [3](#0-2) .
- If the email exists but doesn't case-normalize match (a code path that is effectively unreachable in practice since the SQL query already filters `lower(email) = lower($1)`), it returns literally `"Invalid email"` [4](#0-3) .
- If the email exists and password is wrong, it runs bcrypt via `CheckPasswordHash` (a comparatively slow, constant-cost operation) and returns `"Invalid password"` [5](#0-4) .
- If email+password are correct and MFA is enabled, it returns a JSON WebAuthn challenge string as the error body [6](#0-5) .

This gives three (in practice two reachable) distinguishable outcomes returned verbatim to an unauthenticated caller:
1. Unknown email → fast DB-lookup-failure response.
2. Known email, wrong password → slower bcrypt-backed `"Invalid password"` response.
3. Known email, correct password, MFA enabled → distinct JSON WebAuthn-challenge body (this branch is only reachable once the attacker already possesses a valid password, so it does not by itself allow email/MFA enumeration without credentials).

The code comment at line 152-153 ("Do email and password check first to prevent extra database look up for MFA tokens leaking if an account has MFA tokens or not") shows the authors were aware of and specifically mitigated the *MFA-leak-without-a-password* case by ordering the password check before the `GetUserWebAuthn` call. That specific concern (an attacker discovering MFA status without knowing the password) is addressed. However, the broader concern — distinguishing "email does not exist" from "email exists, wrong password" via response content and/or timing — is not addressed: the raw error strings/timing differences are exposed at the HTTP layer with no generic error normalization or artificial delay/timing equalization.

### Impact Explanation
This maps to a user-enumeration / information-disclosure issue rather than authentication bypass. An unauthenticated attacker can determine which email addresses are registered on the node by observing distinct error text (`"Invalid email"`-type outcome vs `"Invalid password"`) and/or response latency (bcrypt vs. immediate DB miss), aiding targeted phishing/credential-stuffing/social-engineering campaigns against confirmed operator accounts. It does not, by itself, disclose MFA status to an attacker without valid credentials, since the WebAuthn-challenge branch requires the correct password first.

### Likelihood Explanation
Fully reachable pre-auth: the attacker only needs network access to `POST /sessions` with arbitrary email/password pairs — no credentials, role, or token required. Repeatable and scriptable at scale (mass email enumeration).

### Recommendation
- Normalize all failure responses from `CreateSession` for unauthenticated login attempts to a single generic message/status (e.g., "invalid email or password") regardless of whether the email exists, mirroring OWASP authentication guidance.
- Ensure a constant-cost operation (e.g., always run a dummy/fixed-cost bcrypt comparison against a fixed hash) even when the email lookup fails, so response timing does not correlate with account existence.
- Avoid propagating internal error strings (`"Invalid email"`, `"Invalid password"`, `"MFA Error"`) directly to the HTTP response; log them server-side and return a single client-facing message/status code.

### Proof of Concept
Go handler-level integration test plan (`core/web/sessions_controller_test.go` or new test):
1. Seed one user with no MFA and one user with a WebAuthn credential (`SaveWebAuthn`).
2. Issue `POST /sessions` three times:
   - random unregistered email + random password
   - registered non-MFA email + wrong password
   - registered MFA email + correct password, no `WebAuthnData`
3. Assert (to demonstrate the flaw) that response bodies/error strings differ (`"Invalid email"`/db-miss vs `"Invalid password"` vs WebAuthn challenge JSON) and that request latency for the "unregistered email" case is measurably lower than for "registered email, wrong password" (bcrypt-backed) across repeated trials — proving the responses/timings are *not* indistinguishable, which is the bug.
4. After applying the fix, re-run the same table test and assert response bodies are identical strings and timings converge within a small tolerance.
