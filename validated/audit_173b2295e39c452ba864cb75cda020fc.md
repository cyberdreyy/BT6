### Title
CI-variable expansion into Docker volume destination allows Docker bind-mode/option injection - (File: executors/docker/internal/volumes/parser/base_parser.go, executors/docker/internal/volumes/parser/volume.go)

### Summary
`baseParser.matchesToVolumeSpecParts` expands job variables into the `destination` field **after** the volume spec regex has already validated the raw string, and the expanded result is never re-validated. Because job-controlled variable content can contain `:` and Docker bind-mode tokens, an attacker who controls a CI variable referenced in an admin-configured `runners.docker.volumes` entry can inject unintended mount options (e.g. `rw`, `z`, propagation flags) into the final `parser.Volume.Definition()` string consumed as a `HostConfig.Binds` entry.

### Finding Description
`Create` → `addHostVolume` → `appendVolumeBind` calls `volume.Definition()` [1](#0-0)  to build the final Docker bind string from a `*parser.Volume` produced by `ParseVolume`.

`ParseVolume` first matches the raw spec against a strict regex (`linuxDir`/`linuxDestination`) that explicitly excludes `:` from path segments [2](#0-1) , so a raw spec with stray colons is rejected before expansion. However, `matchesToVolumeSpecParts` performs variable expansion on the already-matched `destination` group only, and does so **after** the regex validation has already passed: `parts[group] = p.varExpander(content)` [3](#0-2) . The expanded string is never re-checked against the destination regex, so any `:`, `,`, `rw`, `ro`, `z`, or propagation token contained in the variable's value survives untouched into `volume.Destination`.

`Volume.Definition()` then simply joins `Source`, `Destination`, and `Mode/Label/BindPropagation` with `:`/`,` and returns the concatenated string as-is [4](#0-3) , with no re-validation that `Destination` is still a clean single path segment. Docker's own bind-string parser (consuming `HostConfig.Binds`) will then re-split this string on `:`, interpreting the attacker-injected suffix as a mode/option field rather than part of the path.

This is a real, tested code path: `TestExpandingVolumeDestination` explicitly documents that `Docker.Volumes` destinations are expanded using job variables (`/host/${COMBINED_VAR}:/tmp/${COMBINED_VAR}` → `/host/${COMBINED_VAR}:/tmp/1-2-3`) [5](#0-4) , confirming this expansion is an intentional, supported runner feature rather than a hypothetical.

Precondition: a runner administrator must configure a `[runners.docker] volumes` entry whose destination references a job/pipeline variable (e.g. `/host/data:/tmp/${CI_COMMIT_REF_NAME}`). If the referenced variable's value is attacker-controlled (branch name, CI/CD variable set by a pipeline author, or any job variable reachable by an unprivileged pipeline), the attacker can set it to something like `1:rw,z` so the effective destination becomes `/tmp/1:rw,z`. `Definition()` then emits `/host/data:/tmp/1:rw,z`, which Docker will parse as `Source=/host/data, Destination=/tmp/1, Options=rw,z`, silently forcing an SELinux relabel (`z`) or overriding an intended `ro` mount to `rw` on the admin's host path.

Existing checks do not stop this: `absolutePath`/`Path().IsAbs`/`IsRoot` only validate that the string looks like an absolute path, they do not reject embedded colons or option tokens [6](#0-5) , and no re-parse/re-validation of the expanded destination is performed anywhere in `manager.go` or `volume.go`.

### Impact Explanation
The attacker cannot redirect the mount to an arbitrary host path (the `Source` is fixed by the admin and is not expanded), so this does not achieve full BasePath escape. However, it does let a job/pipeline-controlled variable value silently alter the mount's access mode/options (e.g. force `rw` on an intended `ro` bind, or trigger SELinux `z`/`Z` relabeling of a shared host directory), which directly violates the stated invariant that job-controlled input must not gain unintended host mount capabilities beyond what the admin declared.

### Likelihood Explanation
Requires the runner administrator to have opted into using job variables inside a `runners.docker.volumes` destination — a supported and tested feature, not a misconfiguration warning in docs. Given that precondition, exploitation only requires setting an ordinary CI/CD variable or branch/ref name value containing a colon and a recognized Docker bind token, which is trivial for any pipeline author with variable control.

### Recommendation
After expanding variables into the `destination` field, re-validate the resulting string against the same destination-only pattern (or explicitly reject any `:`/`,`-containing expanded value) before constructing `Volume.Definition()`, ensuring expansion cannot introduce additional colon-delimited fields or recognized Docker bind-mode tokens.

### Proof of Concept
Go unit test extending `TestExpandingVolumeDestination` style setup in `executors/docker/docker_test.go`:
1. Configure `Docker.Volumes: []string{"/host/data:/tmp/${INJECT}"}`.
2. Set job variable `INJECT` to `"1:rw,z"`.
3. Call `executor.createVolumes()`.
4. Assert `executor.volumesManager.Binds()` does **not** contain a 3-segment bind string with an unexpected `rw,z` suffix — i.e. assert `len(strings.Split(bind, ":")) <= 2` (source:destination) after variable expansion, or that expansion errors out when the substituted value contains `:`/`,`.

```go
func (v *Volume) Definition() string {
	parts := make([]string, 0)
	builder := strings.Builder{}
	options := make([]string, 0)

	if v.Source != "" {
		parts = append(parts, v.Source)
	}

	parts = append(parts, v.Destination)

	if v.Mode != "" {
		options = append(options, v.Mode)
	}
	if v.Label != "" {
		options = append(options, v.Label)
	}
	if v.BindPropagation != "" {
		options = append(options, v.BindPropagation)
	}

	opts := strings.Join(options, ",")
	if opts != "" {
		parts = append(parts, opts)
	}

	builder.WriteString(strings.Join(parts, ":"))

	return builder.String()
}
```
