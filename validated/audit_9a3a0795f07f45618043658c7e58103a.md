### Title
Incorrect `max_timestamp` Tracking in `MetaOracle` Causes Stale Oracle Data to Bypass Time-Window Filter and Corrupt Median Price — (File: `crates/sui-oracle/move/oracle/sources/meta_oracle.move`)

---

### Summary

`add_simple_oracle` unconditionally overwrites `max_timestamp` with each successive oracle's timestamp instead of tracking the running maximum. When a stale oracle is added after fresher ones, `max_timestamp` is set to the stale value, making `min_timestamp = max_timestamp - time_window_ms` too old, so the time-window filter in `combine` passes stale price data that should have been excluded. The resulting median is computed over a mix of fresh and stale prices, producing an incorrect output.

---

### Finding Description

In `add_simple_oracle`:

```move
public fun add_simple_oracle<T: copy + drop + store>(
    meta_oracle: &mut MetaOracle<T>,
    oracle: &SimpleOracle
) {
    let oracle_data = oracle::simple_oracle::get_latest_data(oracle, meta_oracle.ticker);
    if (option::is_some(&oracle_data)) {
        meta_oracle.max_timestamp = data::timestamp(option::borrow(&oracle_data));
    };
    vector::push_back(&mut meta_oracle.oracle_data, oracle_data);
}
```

`max_timestamp` is assigned the timestamp of each oracle as it is added, not the maximum seen so far. [1](#0-0) 

`combine` then computes the staleness cutoff as:

```move
let min_timestamp = max_timestamp - time_window_ms;
...
if (data::timestamp(&oracle_data) > min_timestamp) {
    vector::push_back(&mut values, *data::value(&oracle_data));
``` [2](#0-1) 

**Concrete broken invariant:** Suppose three oracles are added in this order:

| Call order | Oracle | Timestamp (ms) | `max_timestamp` after call |
|---|---|---|---|
| 1st | oracle1 | 1_000_060_000 (fresh) | 1_000_060_000 |
| 2nd | oracle2 | 1_000_000_000 (fresh) | 1_000_000_000 ← overwritten |
| 3rd | oracle3 | 999_940_000 (stale) | 999_940_000 ← overwritten again |

With `time_window_ms = 60_000`:

```
min_timestamp = 999_940_000 - 60_000 = 999_880_000
```

All three oracles satisfy `timestamp > 999_880_000`, so oracle3's stale price is included. Had `max_timestamp` been correctly tracked as `1_000_060_000`, `min_timestamp` would be `1_000_000_000`, and oracle3 (timestamp `999_940_000`) would be correctly excluded.

The `median` function then picks the middle value of the corrupted set:

```move
public fun median<T: copy + drop>(meta_oracle: MetaOracle<T>): TrustedData<T> {
    let (values, oracles) = combine(meta_oracle);
    let mut sortedData = quick_sort(values);
    let i = vector::length(&sortedData) / 2;
    let value = vector::remove(&mut sortedData, i);
    TrustedData { value, oracles }
}
``` [3](#0-2) 

---

### Impact Explanation

Any contract that calls `meta_oracle::median()` receives a price computed over a set that may include stale readings. The reference consumer `trusted_fx` uses this price directly to mint a `MockUSD` object proportional to `mist_amount * value`:

```move
let trusted_data = meta_oracle::median(meta_oracle);
let value = meta_oracle::value(&trusted_data);
...
let amount = mist_amount * value;
``` [4](#0-3) 

During a sudden price spike, if oracle3 holds the pre-spike price and is added last, the median is pulled toward the old price, causing users to receive incorrect token amounts — either over-minted (stale price above current) or under-minted (stale price below current). This is harmful smart-contract behavior reachable from ordinary public input.

---

### Likelihood Explanation

The bug is triggered whenever the caller adds oracles in an order where a stale oracle appears after fresher ones. Because `add_simple_oracle` is a `public fun` with no ordering constraint, any integrating contract that iterates over an unordered oracle set (e.g., from a `Table` or `vector`) can trigger this silently. During high-volatility periods — exactly when accurate prices matter most — the probability that at least one oracle lags behind and happens to be added last is non-trivial.

---

### Recommendation

Replace the unconditional assignment with a maximum-tracking update:

```move
if (option::is_some(&oracle_data)) {
    let ts = data::timestamp(option::borrow(&oracle_data));
    if (ts > meta_oracle.max_timestamp) {
        meta_oracle.max_timestamp = ts;
    };
};
```

This ensures `max_timestamp` always reflects the most recent data point seen across all added oracles, making the time-window filter in `combine` correctly exclude any oracle whose data falls outside `[max_timestamp - time_window_ms, max_timestamp]`.

---

### Proof of Concept

1. Deploy the `oracle` package.
2. Create three `SimpleOracle` objects (oracle1, oracle2, oracle3).
3. Call `submit_data` on oracle1 at clock time T+120s, oracle2 at T+60s, oracle3 at T (stale).
4. In a PTB, call `add_simple_oracle` in order: oracle1, oracle2, oracle3.
5. Call `meta_oracle::median()`.
6. Observe `max_timestamp = T` (oracle3's stale timestamp), `min_timestamp = T - 60_000`.
7. All three oracles pass the filter; oracle3's stale price is included in the median.
8. Repeat with correct max-tracking: oracle3 is excluded, median differs.

The wrong `max_timestamp` value is the exact corrupted state. The fix is a one-line guard in `add_simple_oracle`. [1](#0-0) [2](#0-1)

    fun combine<T: copy + drop>(meta_oracle: MetaOracle<T>, ): (vector<T>, vector<address>) {
        let MetaOracle { mut oracle_data, threshold, time_window_ms, ticker: _, max_timestamp } = meta_oracle;
        let min_timestamp = max_timestamp - time_window_ms;
        let mut values = vector<T>[];
        let mut oracles = vector<address>[];

            let oracle_data = vector::remove(&mut oracle_data, 0);

                let oracle_data = option::destroy_some(oracle_data);
                if (data::timestamp(&oracle_data) > min_timestamp) {
                    vector::push_back(&mut values, *data::value(&oracle_data));
                    vector::push_back(&mut oracles, *data::oracle_address(&oracle_data));
                };
            };
        };

        (values, oracles)
