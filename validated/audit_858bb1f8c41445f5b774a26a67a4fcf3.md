### Title
Loss-adjusted withdraw receipts escape the haircut when the requester has a newer pending request — `_claimLossAdjustedWithdrawRequest` only indexes `lossRecoveryPriceByEpoch` by `lastWithdrawRequest` ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to CVE-2023-4427's out-of-bounds memory read, this is a stale/out-of-bounds index bug on the epoch dimension: `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` only. If a user's receipt-bearing epoch is *not* the latest request epoch, the loss price is read from the wrong epoch slot (returning 0), the loss-adjusted claim silently no-ops, and the haircutted receipt is then paid out **at par** through the funded-claim path.

### Finding Description
- In `requestWithdraw`, each request records both `withdrawsRequests[_user] += _amount` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, and overwrites `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) .
- On a `stopEpochWithDuration`-style partial funding, `collectWithdrawFunds` stores the haircut under the epoch at collection time: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` and zeroes `pendingWithdraws` [2](#0-1) .
- `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest`, which reads `lossEpoch = lastWithdrawRequest[_user]` and returns early when `lossRecoveryPriceByEpoch[lossEpoch] == 0` [3](#0-2) .
- If the user then made *another* request in a later, fully-funded epoch M (`lastWithdrawRequest = M`), `lossRecoveryPriceByEpoch[M] == 0`, so the loss claim is skipped. Execution falls through to `_claimFundedWithdrawRequest`, which pays the whole aggregate `withdrawsRequests[_user]` (including the haircutted epoch-N basis) at par once `epochNumber > lastWithdrawRequest[_user]` [4](#0-3) .
- `_clearWithdrawClaimForEpoch` already exists and can clear receipts per-epoch (`withdrawsRequestsByEpoch[_user][_claimEpoch]`), but it is only invoked for the single epoch derived from `lastWithdrawRequest`/`defaultRecoveryEpoch`, never iterated over all epochs with a stored recovery price [5](#0-4) .
- The only guard on payout, `_transferFundedClaim`, merely protects `defaultRecoveryReserve`; it cannot distinguish funded vs. haircutted receipts [6](#0-5) . The code comments explicitly support users holding requests across multiple epochs ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests"), so the precondition is a supported flow, not an edge case [7](#0-6) .

### Impact Explanation
Direct overpayment / insolvency. A user whose epoch-N receipt was haircutted to `lossRecoveryPrice < RECOVERY_FULL` can add a small second request in epoch M > N, wait one epoch, and claim both receipts at par. They receive `claimBasis_N * (1 - lossRecoveryPrice/RECOVERY_FULL)` more underlying than funded. The vault only collected `pendingToFund < pendingBasis` for the loss epoch, so the excess is paid out of funds belonging to other claimants/LPs — a quantified loss up to the full haircut portion of every multi-epoch receipt that follows this pattern.

### Likelihood Explanation
Requires (a) a loss-adjusted `stopEpochWithDuration` (partial borrower funding, honest manager call), and (b) the attacker being a KYC'd lender who already had, or adds, a request in a different epoch. Both are unprivileged-attacker-compatible and need no malicious privileged role. The haircut escape is deterministic once (b) holds; every such user is systematically overpaid rather than it being a race.

### Recommendation
- Iterate the user's receipt epochs (or store a per-user list) in `_claimLossAdjustedWithdrawRequest`/claim flow so any epoch with `lossRecoveryPriceByEpoch[e] != 0` is cleared and paid at that epoch's haircut, not only `lastWithdrawRequest[_user]`.
- Alternatively, block new `requestWithdraw` while an unsettled loss-adjusted receipt exists, or fold the haircutted basis into `withdrawsRequestsByEpoch` netting so `_claimFundedWithdrawRequest` can never pay it at par.
- Regression test: request in epoch N → loss-adjusted stop → request in epoch M → claim must equal `basisN * priceN / FULL + basisM`, not `basisN + basisM`.

### Proof of Concept
Foundry fork sketch (against the existing `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testLossHaircutEscapedByNewerRequest() external {
    // epoch N: user deposits and requests withdraw of `tranches`
    _stopCurrentEpochWithApr(10e18);          // enter epoch N
    uint256 amountN = 100e6;
    address user = makeAddr('user');
    uint256 tranches = _depositWithUser(user, amountN);
    vm.prank(manager); cdoEpoch.startEpoch();
    _requestWithdrawWithUser(user, tranches); // request in epoch N

    // stopEpochWithDuration: borrower funds only 50% of pendingWithdraws
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = strategy.pendingWithdraws();
    deal(underlying, borrower, pending / 2);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(pending / 2 /* loss-adjusted funding */, ...);
    // => lossRecoveryPriceByEpoch[N'] = 0.5e18

    // epoch M: attacker makes a tiny new request in a fully-funded epoch
    _startEpochAndCheckPrices();
    uint256 tranches2 = _depositWithUser(user, 1e6);
    _requestWithdrawWithUser(user, tranches2); // lastWithdrawRequest[user] = M
    // fund epoch M fully at stop
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(underlying, borrower, strategy.pendingWithdraws());
    vm.prank(manager); cdoEpoch.stopEpoch(0, 0);

    // claim: loss path reads lossRecoveryPriceByEpoch[M] == 0 and skips,
    // funded path pays full withdrawsRequests[user] at par
    uint256 balPre = underlying.balanceOf(user);
    vm.prank(user); // via cdoEpoch.claimWithdrawRequest()
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(user) - balPre;

    // BUG: paid == amountN + 1e6  instead of amountN/2 + 1e6
    assertGt(paid, amountN / 2 + 1e6, 'haircutted receipt paid at par');
}
```

Expected outcome: `paid` exceeds the funded `lossRecoveryPrice`-adjusted amount by `claimBasis_N * (1 - lossRecoveryPrice)`, draining underlying from the strategy that belongs to other claimants.

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
