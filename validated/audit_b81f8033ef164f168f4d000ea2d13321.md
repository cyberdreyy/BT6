### Title
BB holders escape the junior-first loss waterfall by converting tranche positions into loss-adjusted withdraw receipts before a bad-debt stopEpoch - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCDOEpochVariant._stopEpoch` splits a realized loss via `IdleCreditVault.previewLossAdjustedWithdrawFunds`, which assigns pending withdraw receipts only a *pro-rata* share of `_lossAmount` across `activeBasis + pendingBasis`, because receipts have no tranche identity. The remainder is applied to active tranches BB-first. A junior (BB) holder who calls `requestWithdraw` during the buffer period converts a position that should absorb 100% of the loss into a pending receipt that only takes `loss * pendingBasis / totalBasis`. The escaped portion is pushed onto AA holders, breaking the loss-waterfall invariant and effectively letting junior withdrawers pull out collateral that should have been lost — mirroring the external report's "redeeming non-redeemable collateral under bad debt" bug class.

### Finding Description
`requestWithdraw` burns BB tranche tokens and mints fungible strategy-token receipts (`IdleCreditVault.requestWithdraw`, lines 272-294); the receipt enters `pendingWithdraws` with no record that it originated from the junior tranche. At `stopEpochWithDuration`, `previewLossAdjustedWithdrawFunds` (IdleCreditVault.sol:440-460) computes:

```solidity
uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
pendingToFund = pendingBasis - pendingLoss;
activeLoss = _lossAmount - pendingLoss;
```

`activeBasis` is `_lossActiveBasis` ≈ `getContractValue()` (already net of the burned pending principal). The active remainder is then burned via `_strategy.burnStrategyTokens(_lossAmount)` + `_forceUpdateAccounting()` (IdleCDOEpochVariant.sol:496-499), which applies the ordinary BB-first waterfall.

Example: AA NAV = 900k, BB NAV = 100k. The borrower owes and a realized loss of 100k is expected (manager will pass `_lossAmount = 100k`, an honest input reflecting bad debt). If the BB holder stays put, BB is wiped (loses 100k) and AA loses 0. Instead, during the buffer the BB holder calls `requestWithdraw(0, BBTranche)`, moving ~100k into `pendingWithdraws`. Now `pendingLoss = 100k * 100k / 1M = 10k`; the receipt is funded at 90k, while `activeLoss = 90k` is applied BB-first to a vault with zero remaining BB supply — so all 90k hits AA. The attacker receives 90k instead of 0; AA holders absorb 90k they should never have borne.

### Impact Explanation
Direct theft/loss transfer: junior tranche holders can dodge up to nearly all of their first-loss obligation whenever a loss epoch is anticipated, socializing it onto senior (AA) holders. Quantified: with BB = 10% of TVL and a loss equal to BB NAV, the escaping BB holder recovers ~90% of principal and AA takes ~9% of TVL in illegitimate loss. This also distorts the intended "loss waterfall" invariant the protocol documents (BB-first) and can cascade into premature `_emergencyShutdown`/Default reverts for AA.

### Likelihood Explanation
The attacker needs only to be a BB tranche holder (KYC-passing lender) acting during a buffer period — i.e., between `stopEpoch` and `startEpoch`, when `allowBBWithdrawRequest` is true and `isEpochRunning` is false. Losses in this system are manager-declared at `stopEpochWithDuration`, and borrower distress/shortfall can be observable before the loss is crystallized (e.g., borrower failed to repay, ERC4626 liquidity issues, public credit events), giving the BB holder a window to request withdrawal before the next loss-bearing stop. The only gate is `isWalletAllowed`, which any normal lender satisfies. No privileged role misbehavior is required — the manager honestly passes the true `_lossAmount`.

### Recommendation
Retain tranche identity for pending receipts (e.g., `pendingWithdrawsAA`/`pendingWithdrawsBB` buckets) so a loss is applied BB-first across *both* pending and active positions: exhaust the pending+active BB basis before haircutting AA receipts/positions. Alternatively, when `activeLoss` exceeds the remaining active BB NAV, apply the spillover to BB-originated pending receipts before AA. A simpler partial mitigation is to block `requestWithdraw` on BB (or recompute the haircut at claim time) once a loss is pending, though this does not fix the ordering asymmetry for requests already queued.

### Proof of Concept
Foundry-style sketch (following `IdleCreditVault.t.sol` harness conventions):

```solidity
function testBBEscapesJuniorLossViaPendingReceipt() external {
    uint256 amountAA = 900_000 * ONE_SCALE;
    uint256 amountBB = 100_000 * ONE_SCALE;
    address bbUser = makeAddr('bbUser');

    // attacker is an ordinary KYC'd BB lender
    _depositWithUser(bbUser, amountBB, false); // depositBB
    idleCDO.depositAA(amountAA);

    // run a normal epoch
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // buffer period: bad debt on the borrower position becomes known
    // attacker converts BB tranche into a pending withdraw receipt
    vm.prank(bbUser);
    cdoEpoch.requestWithdraw(0, address(BBtranche));
    uint256 pending = strategy.pendingWithdraws(); // ~100k

    vm.prank(manager);
    cdoEpoch.startEpoch();
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // honest manager realizes the true 100k bad-debt loss
    uint256 lossAmount = amountBB;
    (uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(defaultUnderlying, borrower, repay, true);
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), repay);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), lossAmount);

    // attacker claims ~90k instead of 0: only pro-rata haircut applied
    vm.prank(bbUser);
    cdoEpoch.claimWithdrawRequest();
    uint256 attackerOut = underlying.balanceOf(bbUser);
    assertApproxEqAbs(attackerOut, pending * (pending + activeBasisBeforeLoss - lossAmount) ... , );
    // attackerOut ≈ pending * (1 - loss/total) = 100k * 90% = 90k  (BB would be 0)
    assertGt(attackerOut, 0);

    // AA holders absorbed the ~90k the BB holder escaped
    assertLt(cdoEpoch.virtualPrice(address(AAtranche)), ONE_SCALE);
}
```

Invariant broken: `BB-first loss waterfall` — a junior position must bear losses before seniors regardless of whether it is wrapped in a withdraw receipt.
