### Title
Unstaking any amount resets `unstaked_available_epoch_height` for the entire unstaked balance, refreezing already-matured funds - (File: staking-pool/src/internal.rs)

### Summary
`inner_unstake` unconditionally overwrites `account.unstaked_available_epoch_height` with `env::epoch_height() + NUM_EPOCHS_TO_UNLOCK` whenever any additional amount is unstaked, even if the account already has an `unstaked` balance that had already matured and was withdrawable. This re-locks the previously withdrawable portion for another full unstaking delay, breaking the invariant that a matured unstaked balance remains withdrawable regardless of subsequent unstakes.

### Finding Description
The broken binding: for an account with a previously matured balance, `can_withdraw(account) == (account.unstaked_available_epoch_height <= env::epoch_height())` should remain `true` after any later `unstake` call as long as no withdrawal happened, since the already-matured portion of `account.unstaked` was already unlocked. This binding is violated.

In `StakingContract::inner_unstake` [1](#0-0) , the account's `unstaked` field is a single pooled balance that mixes any previously matured (withdrawable) unstaked tokens with newly unstaked tokens:

```
account.unstaked += receive_amount;
account.unstaked_available_epoch_height = env::epoch_height() + NUM_EPOCHS_TO_UNLOCK;
```

There is no check of the account's current `unstaked_available_epoch_height` versus the current epoch before this overwrite, and no separate accounting of "already-matured" vs "newly-unstaked" balances. As a result, calling `unstake(1)` (a dust amount) or `unstake_all()` at any time after a balance has matured pushes the unlock height for the *entire* `account.unstaked` balance forward by `NUM_EPOCHS_TO_UNLOCK` epochs, even the part that was already free to withdraw via `internal_withdraw` (guarded only by `account.unstaked_available_epoch_height <= env::epoch_height()` at [2](#0-1) ).

Exploit flow:
1. Attacker (any delegator) stakes, then unstakes some amount; waits `NUM_EPOCHS_TO_UNLOCK` epochs so `account.unstaked_available_epoch_height <= env::epoch_height()` (balance now withdrawable).
2. Before withdrawing, attacker calls `unstake(1)` (1 yocto/dust) — this succeeds because `inner_unstake` only requires `account.stake_shares >= num_shares` and `total_staked_balance > 0`, no relation to the already-matured unstaked balance.
3. `inner_unstake` recomputes `account.unstaked_available_epoch_height = env::epoch_height() + NUM_EPOCHS_TO_UNLOCK`, overwriting the previous (already-elapsed) unlock height for the *whole* pooled `unstaked` balance, including the mature portion.
4. `internal_withdraw` now fails its assert (`unstaked_available_epoch_height <= env::epoch_height()`), freezing the entire unstaked balance for another `NUM_EPOCHS_TO_UNLOCK` epochs.

None of the existing guards prevent this: `internal_withdraw`'s assert only checks the single shared `unstaked_available_epoch_height` field, which is exactly what gets clobbered; `inner_unstake` has no assert relating to already-mature balances; `internal_ping` and the U256 rounding logic are unrelated to this state field. This can be repeated by any delegator on any staking pool, against their own account or (since it only affects the caller's own account) can also be used to grief oneself unintentionally, but the primary reported impact is self-inflicted or externally-triggerable temporary freezing depending on whether a third party can force calls on the victim's behalf — however, as scoped, the attacker acts on their own account, and the vulnerability is a genuine invariant break within the contract's own accounting regardless of the "last block of epoch" timing detail (that detail is only relevant to avoid the reward distribution changing total_staked_balance mid-transaction, but the core clock-reset bug is independent of epoch boundary timing).

### Impact Explanation
The affected funds are the delegator's own already-matured unstaked NEAR held by the staking pool contract; a dust unstake call re-locks that balance for at least `NUM_EPOCHS_TO_UNLOCK` (4 epochs per `staking-pool/src/lib.rs` constant) additional epochs, matching the "funds frozen for at least one epoch but recoverable" High severity category. This is repeatable indefinitely by the account holder (each unstake call resets the clock again), and applies uniformly to every account/pool built from this staking-pool contract, so the blast radius is every delegator of every deployed staking pool using this code.

### Likelihood Explanation
No special privileges are required — any delegator who has staked and later unstaked, waited for maturity, and then calls `unstake` again (even for 1 yocto) before withdrawing triggers the bug. The preconditions (having staked and having an already-elapsed unstaking delay) are part of normal contract usage, making this trivially reachable and highly likely to occur even accidentally, not just adversarially.

### Recommendation
Track the "matured" and "pending" unstaked amounts separately, or only update `unstaked_available_epoch_height` when the account's current unstaked balance is zero / not yet matured (e.g., `if account.unstaked_available_epoch_height <= env::epoch_height() { /* start fresh clock only for the newly unstaked portion */ }` combined with splitting the balance), so that maturing funds are withdrawable independent of later unstake calls.

### Proof of Concept
```rust
// cargo test in staking-pool, using testing_env! to control env::epoch_height()
#[test]
fn test_unstake_dust_relocks_matured_balance() {
    let mut context = VMContextBuilder::new().build(); // epoch 0
    testing_env!(context.clone());
    let mut contract = StakingContract::new(..., owner, stake_public_key, reward_fee_fraction);

    // Deposit and stake
    testing_env!(context.clone());
    contract.deposit_and_stake(); // attaches deposit, stakes amount

    // Unstake most balance
    contract.unstake(some_amount.into());
    let acc = contract.get_account(account_id.clone());
    let unlock_epoch = acc.unstaked_available_epoch_height; // e.g. NUM_EPOCHS_TO_UNLOCK

    // Advance epoch_height to unlock_epoch (simulate NUM_EPOCHS_TO_UNLOCK epochs passing)
    context.epoch_height = unlock_epoch;
    testing_env!(context.clone());

    let can_withdraw_before = contract.get_account(account_id.clone()).unstaked_available_epoch_height <= env::epoch_height();
    assert!(can_withdraw_before); // matured, withdrawable

    // Attacker unstakes 1 yocto dust
    contract.unstake(1.into());

    let acc_after = contract.get_account(account_id.clone());
    // BROKEN INVARIANT: unlock height pushed forward again for the whole balance
    assert_eq!(acc_after.unstaked_available_epoch_height, env::epoch_height() + NUM_EPOCHS_TO_UNLOCK);

    // Withdraw now fails even though most of the balance was already matured
    let result = std::panic::catch_unwind(|| contract.withdraw(some_amount.into()));
    assert!(result.is_err(), "withdraw should have succeeded for the matured portion but panics due to clock reset");
}
```
This test demonstrates the binding `can_withdraw` before and after the dust `unstake(1)` call diverges: it is `true` before and `false` after, for tokens that had already matured, confirming the freezing bug in `StakingContract::inner_unstake` at [3](#0-2) .

    pub(crate) fn inner_unstake(&mut self, amount: u128) {
        assert!(amount > 0, "Unstaking amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);

        assert!(
            self.total_staked_balance > 0,
            "The contract doesn't have staked balance"
        );
        // Calculate the number of shares required to unstake the given amount.
        // NOTE: The number of shares the account will pay is rounded up.
        let num_shares = self.num_shares_from_staked_amount_rounded_up(amount);
        assert!(
            num_shares > 0,
            "Invariant violation. The calculated number of \"stake\" shares for unstaking should be positive"
        );
        assert!(
            account.stake_shares >= num_shares,
            "Not enough staked balance to unstake"
        );

        // Calculating the amount of tokens the account will receive by unstaking the corresponding
        // number of "stake" shares, rounding up.
        let receive_amount = self.staked_amount_from_num_shares_rounded_up(num_shares);
        assert!(
            receive_amount > 0,
            "Invariant violation. Calculated staked amount must be positive, because \"stake\" share price should be at least 1"
        );

        account.stake_shares -= num_shares;
        account.unstaked += receive_amount;
        account.unstaked_available_epoch_height = env::epoch_height() + NUM_EPOCHS_TO_UNLOCK;
        self.internal_save_account(&account_id, &account);
