### Title
Multisig executes below-threshold requests because stale confirmations from removed members are never purged - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` in [1](#0-0)  counts the raw size of the `confirmations` `HashSet` for a request and executes it once that size reaches `num_confirmations`. It never re-validates that every entry in that set still corresponds to a current member of `self.members`. `delete_member`, in [2](#0-1) , only purges requests *created by* the removed member (`r.member == member`) and that member's own `num_requests_pk` counter — it does not scrub confirmations the removed member gave on *other, still-pending* requests. As a result a request can be executed with fewer live-member confirmations than `num_confirmations` requires.

### Finding Description
The multisig's core security guarantee is the equality: `confirmations counted == confirmations from current members`. The contract stores confirmations keyed only by `request_id -> HashSet<String>` of member identifiers [3](#0-2) . When a member is removed via `MultiSigRequestAction::DeleteMember`, `delete_member` removes:
- outstanding requests *created by* that member, and
- the member's own `num_requests_pk` entry,

but leaves the member's *confirmations on requests created by other members* untouched: [4](#0-3) 

Meanwhile `confirm` blindly trusts the cardinality of the stored confirmation set: [5](#0-4) 

There is no membership check on the confirmers already stored in the set at the moment the threshold is evaluated. So once a member who previously confirmed a pending request is later removed (through a legitimate `DeleteMember` request approved by other members, or by removing themselves), their stale confirmation permanently occupies a "slot" toward `num_confirmations` for that unrelated pending request. If enough *other, still-current* members confirm afterward, the request executes even though the number of confirmations coming from members that are actually members *at execution time* is below `num_confirmations`.

### Impact Explanation
This breaks the K-of-N custody binding the contract is supposed to enforce: a `Transfer`, `FunctionCall`, `AddKey`, or `DeployContract` request can be executed with fewer than `num_confirmations` live members actually agreeing to it at execution time. This matches the "Critical" impact class explicitly defined for this analysis: a multisig request executed below threshold. Because `MultiSigRequestAction::Transfer` and `AddKey` are among the executable actions [6](#0-5) , this can lead directly to unauthorized movement of NEAR held by the multisig account or unauthorized granting of access keys.

### Likelihood Explanation
The precondition is ordinary multisig lifecycle activity — no compromise of keys or social engineering is required beyond the normal K-of-N governance flow that already exists in the contract (adding a request, confirming it, and later removing a member through the standard `DeleteMember` action). Membership churn (onboarding/offboarding signers) is an expected, routine operation for any long-lived multisig, making the stale-confirmation window realistically reachable.

### Recommendation
When counting/checking confirmations in `confirm`, filter the stored confirmation set to only those entries still present in `self.members` before comparing to `num_confirmations` (or proactively purge confirmations from a member's active requests when that member is deleted in `delete_member`, similar to how request-creation entries are purged).

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)` [7](#0-6) .
2. Member `B` calls `add_request` to create request `R` (e.g. `Transfer { amount }` to an attacker-controlled or colluding account) [8](#0-7) .
3. Member `A` calls `confirm(R)` → `confirmations = {A}` (size 1, below threshold, stored) [1](#0-0) .
4. Member `C` calls `confirm(R)` → `confirmations = {A, C}` (size 2, still below threshold 3).
5. Separately, members create and confirm 3-of-4 a `DeleteMember { member: C }` request, removing `C` from `self.members` via `delete_member` [2](#0-1) . Because `R` was created by `B`, not `C`, `delete_member`'s filter `r.member == member` does not touch `R`'s confirmations — `{A, C}` remains stored for `R`.
6. Members are now `[A, B, D]`; `num_confirmations` is still 3.
7. Member `D` calls `confirm(R)` → `confirmations.len() + 1 == 3 >= num_confirmations (3)` → `R` executes via `execute_request` [9](#0-8) , even though only `A` and `D` are still live members among the confirmers (`C`'s confirmation is stale) — i.e., the transfer executes with only 2 of the required 3 *current* members' approval.

    pub fn add_request(&mut self, request: MultiSigRequest) -> RequestId {
        let current_member = self.current_member().unwrap_or_else(|| {
            env::panic_str(
                "Predecessor must be a member or transaction signed with key of given account",
            )
        });
        // track how many requests this key has made
        let num_requests = self
            .num_requests_pk
            .get(&current_member.to_string())
            .unwrap_or(0)
            + 1;
        assert(
            num_requests <= self.active_requests_limit,
            "Account has too many active requests. Confirm or delete some.",
        );
        self.num_requests_pk
            .insert(&current_member.to_string(), &num_requests);
        // add the request
        let request_added = MultiSigRequestWithSigner {
            member: current_member,
            added_timestamp: env::block_timestamp(),
            request,
        };
        self.requests.insert(&self.request_nonce, &request_added);
        let confirmations = HashSet::new();
        self.confirmations
            .insert(&self.request_nonce, &confirmations);
        self.request_nonce += 1;
        self.request_nonce - 1
    }

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
