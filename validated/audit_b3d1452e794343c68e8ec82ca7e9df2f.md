### Title
Global (unscoped) request-ID keyspace in the HTTP trigger gateway handler allows any authorized caller to grief another user's workflow execution requests - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The gateway's HTTP trigger handler stores in-flight callbacks in a single map keyed only by the client-supplied `requestID` string, with no scoping to the requesting workflow or workflow owner. Because the ID is chosen entirely by the caller and uniqueness is enforced globally rather than per-tenant, any authorized user can pre-claim a `requestID` value that another (unrelated) user's request will use, permanently blocking that legitimate submission with a conflict error — the same "unprivileged actor front-runs a user-chosen unique identifier" bug class described in the external report, transposed from an on-chain `accountId` to the gateway's `requestID`.

### Finding Description
`HandleUserTriggerRequest` validates and authorizes an incoming JSON-RPC trigger request, then calls `setupCallback`, which performs the uniqueness check: [1](#0-0) 

The check is `if _, found := h.callbacks[requestID]; found { ... }` — the map key is the raw `requestID` supplied by the caller with no namespacing by `workflowID` or `workflowOwner`: [2](#0-1) 

`validateRequestID` only rejects empty IDs or IDs containing `/`; it performs no ownership or ID-format checks that would prevent one caller from choosing an ID belonging to another caller's namespace: [3](#0-2) 

Authorization (`authorizeRequest`) only verifies that the caller has a valid key for the `workflowID` embedded in *their own* request — it does not verify or reserve exclusivity over the `requestID` value itself: [4](#0-3) 

As a result, an attacker who is authorized to trigger any workflow (including one they control) can submit a request using a `requestID` that a victim, targeting a completely different workflow, is about to use or has just used. The victim's legitimate request then hits the collision path and is rejected outright: [5](#0-4) 

This mirrors the reported pattern exactly: a unique identifier is chosen by an unprivileged, unauthenticated-with-respect-to-the-victim actor, and the system's "first writer wins" semantics on a single shared namespace let that actor deterministically block another user's operation.

By contrast, the Vault gateway handler in the same codebase avoids this class of bug by scoping the deduplication key to `owner + RequestIDSeparator + requestID` rather than the raw request ID alone, confirming that the correct mitigation pattern (namespacing collision-prone IDs by the authenticated caller identity) is already known in this codebase but not applied here: [6](#0-5) 

### Impact Explanation
This is a griefing/denial-of-service vulnerability with no profit motive required for the attacker, consistent with the reported impact class. A malicious but otherwise unprivileged, authorized caller (holding a valid key for any workflow) can:
- Reserve a `requestID` string ahead of time and cause any other user's genuine trigger request using that same ID to be rejected with `jsonrpc.ErrConflict` ("requestID: %s has already been used...").
- Repeatedly re-claim commonly used or predictable IDs (e.g., idempotency keys derived from deterministic business data) to persistently block legitimate workflow executions across unrelated workflows/owners, since the map is a single global namespace shared by all tenants.

### Likelihood Explanation
Exploitation requires the attacker to (1) hold valid authorization for at least one workflow of their own — a low bar since it is any authenticated/authorized caller, not a privileged role, and (2) know or guess the victim's chosen `requestID` in advance. Because `requestID` is entirely caller-defined and many integrations use deterministic/idempotent IDs (order numbers, timestamps, sequence numbers) rather than high-entropy random UUIDs, guessing collisions is plausible for a targeted victim, making this a realistic griefing vector against the internet-facing gateway rather than a purely theoretical one.

### Recommendation
Scope the in-flight callback/dedup key by the authenticated caller identity in addition to the client-supplied `requestID`, mirroring the `owner + separator + requestID` pattern already used in the Vault gateway handler (e.g., key by `workflowOwner + "/" + requestID` or `workflowID + "/" + requestID`) so that request-ID collisions can only occur within a single tenant's own namespace, not across unrelated callers.

### Proof of Concept
1. Attacker holds a valid authorization key for `workflowA` (their own workflow).
2. Attacker learns/guesses that victim will submit a trigger request for `workflowB` with `requestID = "X"` (e.g., a predictable idempotency key).
3. Attacker sends a JSON-RPC `workflows.execute` request to the gateway with `id: "X"` and `workflow.workflowID = workflowA`. It passes `validateRequestID`, `authorizeRequest`, and `checkRateLimit`, then `setupCallback` inserts `h.callbacks["X"]`.
4. Victim's legitimate request for `workflowB` with `id: "X"` reaches `setupCallback`; `h.callbacks["X"]` is already occupied, so the victim receives `jsonrpc.ErrConflict`: `"requestID: X has already been used. Ensure the requestID is unique for each request."` and their trigger execution never starts — reference: [5](#0-4) .

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
