### Title
Resource-metering opcode/precompile budgets can be bypassed with attacker-controlled `meterBundle` simulation data - ([File: crates/execution/payload/src/resource_metering.rs])

### Summary
The Base builder's resource-metering system enforces per-transaction and per-block "resource unit" budgets on opcode/precompile usage, but those budgets are calculated from a `ResourceSample` whose `operations` (opcode/precompile counts) come entirely from the **caller-supplied `base_meterBundle` RPC response**, not from the node's own execution. Only `gas_used` and post-state `STATE_*` counts are overwritten from real execution; every other simulated opcode/precompile row is trusted as-is when the transaction is actually included and charged against the cumulative block budget.

### Finding Description
`ResourceSample::from_meter` builds the "simulated" sample purely from the attacker/searcher-submitted `MeterBundleResponse.results[i].opcode_gas`, which is produced by the `base_meterBundle` RPC (`crates/execution/metering/src/rpc.rs`, `meter_bundle`) — a method any unprivileged JSON-RPC caller can invoke and, more importantly, whose *result* is fed back into the payload builder's admission/throttling path by the caller (via `MeterBundleResponse` attached to the transaction) rather than recomputed independently by the block builder for every dimension: [1](#0-0) 

When the builder actually executes the transaction, `ResourceSample::from_execution` only replaces the `STATE_*` post-state rows and `gas_used`; every other opcode/precompile row supplied in the simulated sample is retained verbatim: [2](#0-1) 

This "committed" usage — still containing attacker-supplied opcode/precompile counts — is what gets added to the cumulative per-block resource totals (`ResourceThrottlingDecision::committed_usage` → `apply_accounted_usage` → `check`/`check_simulated_usage`/`check_executed_usage` in `crates/execution/payload/src/config.rs`), and is exactly the value checked against `dimension.block_limit`/`dimension.transaction_limit`: [3](#0-2) 

This mirrors the Sherlock M-6 root cause precisely: a rate-limit/cap accounting system (the CircuitBreaker in the referenced report; the resource-metering block/transaction budget here) trusts an externally-supplied or delayed-conversion value instead of ground truth, letting an attacker feed the accounting system a value that understates real consumption. Here, a searcher can call `base_meterBundle` and report artificially low (or zero) `opcode_gas`/precompile counts for expensive operations (e.g. `SSTORE`, `KECCAK256`, precompile calls) in their bundle. Because the schedule's `dry_run`/enforced dimensions rely on this self-reported bag for anything other than `gas_used` and post-state slot/account counts, the transaction is admitted and its committed usage recorded as if it barely used the metered dimension, silently exhausting/circumventing the intended per-block resource cap (e.g., a CPU/opcode-heavy dimension meant to bound sequencer build time), while real execution still consumes the disproportionate resource.

### Impact Explanation
Resource metering exists specifically to bound block-building CPU/time cost per dimension so the sequencer can meet its block-time SLA (see `crates/execution/metering/README.md` and `resource_metering.rs` module docs: "Throttling excludes a transaction when an enforced dimension exceeds a budget"). If the accounted usage for opcode/precompile dimensions is attacker-controlled, an adversary can submit bundles that under-report gas-heavy opcode/precompile usage in `meterBundle`, get them admitted past enforced per-block resource budgets, and repeatedly exceed the intended CPU/time envelope for block building — a resource-exhaustion/block-building-delay vector that can degrade sequencer performance or cause missed block-time targets (chain halt/degraded liveness risk), which is a Medium/High-severity node-halt-adjacent issue, analogous to the acknowledged Sherlock Medium finding.

### Likelihood Explanation
Reachable directly by any unprivileged party who can submit bundles/transactions and call the public `base_meterBundle` RPC — no special privileges are required. Exploitation requires the operator to have `--enable-metering` on with a resource-metering schedule that prices opcode/precompile dimensions (an opt-in, but documented production feature), and for the enforced dimension to rely on opcode/precompile pricing rather than only `gas_used`/`STATE_*`. Given the code explicitly documents "Opcode and precompile counts stay on the simulated `meterBundle` bag" as intended behavior, this is a structural trust gap rather than a rare edge case, making exploitation straightforward once the feature is enabled with such a schedule.

### Recommendation
Do not trust caller-supplied opcode/precompile counts for enforcement. Either (a) have the block builder itself re-instrument execution with the same `MeteringInspector` used by `base_meterBundle`/`base_meterBlockByHash` to derive real opcode/precompile counts at inclusion time (analogous to how `STATE_*` counts are already recomputed from real post-state), or (b) treat the simulated sample only as a soft pre-filter (as already noted for block-scope excludes) and never let unverified simulated opcode/precompile rows be added to the cumulative budget that gates admission of subsequent transactions.

### Proof of Concept
Conceptual PoC (matches code paths cited above):
1. Enable `--enable-metering` with a resource-metering schedule that budgets a dimension via `operations` pricing (e.g. `SSTORE`) rather than only `base_gas_weight`.
2. Attacker calls `base_meterBundle` with a bundle containing a transaction that performs many expensive metered opcodes, but the RPC response processing/attachment path allows the attacker to submit/replay a `MeterBundleResponse` reporting near-zero `opcode_gas` counts for that operation (or the attacker controls a `meterBundle` result path returning minimal counts) via `ResourceSample::from_meter`.
3. Builder calls `check_simulated_usage` — passes because the simulated sample under-reports usage.
4. Builder executes the transaction; `check_executed_usage`/`ResourceSample::from_execution` only overwrites `gas_used` and `STATE_*` rows, keeping the attacker's low opcode-gas rows for the priced operation.
5. `committed_usage` (still low) is added to `cumulative`, so subsequent transactions in the same block, and the attacker's own repeated transactions across blocks, keep passing the enforced dimension's block/transaction limit despite real per-block CPU cost from the metered operation being far higher than budgeted.

    /// Builds an executed-preferred sample.
    ///
    /// Actual gas and `STATE_*` counts from post-state replace simulated
    /// `STATE_*` rows. Other simulated opcode and precompile rows are kept.
    /// Production execution does not attach opcode bags.
    pub fn from_execution(gas_used: u64, state: &EvmState, simulated: Option<&Self>) -> Self {
        let mut operations = simulated.map(|sample| sample.operations.clone()).unwrap_or_default();
        operations.retain(|entry| {
            let name = ResourceMeteringSchedule::normalize_operation_name(&entry.opcode);
            !Self::EXECUTED_STATE_OPERATIONS.iter().any(|operation| name == *operation)
        });
        Self::push_count(
            &mut operations,
            Self::STATE_NEW_STORAGE_SLOT,
            Self::count_new_storage_slots(state),
        );
        Self::push_count(
            &mut operations,
            Self::STATE_CHANGED_STORAGE_SLOT,
            Self::count_changed_storage_slots(state),
        );
        Self::push_count(
            &mut operations,
            Self::STATE_CLEARED_STORAGE_SLOT,
            Self::count_cleared_storage_slots(state),
        );
        Self::push_count(
            &mut operations,
            Self::STATE_TOUCHED_ACCOUNT,

        );
        Self::push_count(

            Self::STATE_CHANGED_ACCOUNT,
            Self::count_changed_accounts(state),

    /// Checks transaction and cumulative block budgets for one transaction.
    ///
    /// Overruns are ranked so a later dimension can still exclude the
    /// transaction: enforced transaction-scope, then enforced block-scope,
    /// then the first dry-run overrun in schedule order. Arithmetic overflow
    /// is returned immediately.
    pub fn check(
        &self,
        usage: &ResourceMeteringUsage,
        cumulative: &[u128],
    ) -> Result<(), ResourceThrottlingCheckError> {
        let mut enforced_transaction = None;
        let mut enforced_block = None;
        let mut dry_run_error = None;

        for (index, dimension) in self.dimensions.iter().enumerate() {
            let transaction_cost = usage.get(index);

            // Check the per-tx budget before adding to the block cumulative so
            // an overflow cannot fail-open a transaction that cannot fit any
            // empty block.
            if transaction_cost > u128::from(dimension.transaction_limit) {
                let error = ResourceThrottlingLimitExceeded {
                    dimension: dimension.name.clone(),
                    scope: ResourceThrottlingLimitScope::Transaction,
                    used: transaction_cost,
                    transaction_cost,
                    limit: dimension.transaction_limit,
                    dry_run: dimension.dry_run,
                };
                if dimension.dry_run {
                    if dry_run_error.is_none() {
                        dry_run_error = Some(error);
                    }
                } else if enforced_transaction.is_none() {
                    enforced_transaction = Some(error);
                }
                continue;
            }

            let used = cumulative
                .get(index)
                .copied()
                .unwrap_or_default()
                .checked_add(transaction_cost)
                .ok_or(ResourceThrottlingCheckError::ArithmeticOverflow)?;
            if used > u128::from(dimension.block_limit) {
                let error = ResourceThrottlingLimitExceeded {
                    dimension: dimension.name.clone(),
                    scope: ResourceThrottlingLimitScope::Block,
                    used,
                    transaction_cost,
                    limit: dimension.block_limit,
                    dry_run: dimension.dry_run,
                };
                if dimension.dry_run {
                    if dry_run_error.is_none() {
                        dry_run_error = Some(error);
                    }
                } else if enforced_block.is_none() {
                    enforced_block = Some(error);
                }
            }
        }
