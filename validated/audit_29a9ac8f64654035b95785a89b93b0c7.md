### Title
Removed multisig members' stale confirmations still count toward the execution threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` only purges requests and confirmations that were **created by** the removed member, but leaves untouched any confirmations that member previously cast on **other** pending requests. Those stale confirmations are still counted in `confirm()` when comparing against `num_confirmations`, so a request can be executed with fewer live, currently-authorized signers than the configured threshold requires.

### Finding Description
The multisig invariant is: a request can only execute once `confirmations.len() >= num_confirmations` **distinct current members** have approved it. `confirm()` enforces this purely by counting entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` map: [1](#0-0) 

When a member is removed via `DeleteMember`, `delete_member` cleans up only requests where `r.member == member` (i.e., requests *originated* by that member) and their confirmations. It never scans the `confirmations` map to strip that member's approval from requests originated by other members: [2](#0-1) 

Because `confirm()` never re-validates that every entry in the stored `HashSet<String>` still corresponds to a current member of `self.members`, a confirmation cast by an account that has since been removed remains permanently counted toward `num_confirmations`.

Binding that should hold: `confirmations_counted(request) == live_member_approvals(request)`. After a `DeleteMember` action targeting a member who had already confirmed some other pending request, this becomes `confirmations_counted(request) > live_member_approvals(request)` — the map still reports N confirmations while only N-1 (or fewer) are from members that currently exist.

### Impact Explanation
This directly matches the "multisig request executed below threshold" critical category: a pending transfer, `AddKey`, `DeployContract`, or any other `MultiSigRequestAction` can be pushed to execution using fewer genuinely-authorized (live) signers than `num_confirmations` mandates, because one "vote" belongs to an account that is no longer a member (e.g., removed for being compromised, leaving the organization, or key rotation). This is an authorization-threshold bypass over an account that can move NEAR, add access keys, or deploy code.

### Likelihood Explanation
This is reachable through entirely ordinary governance flow with no special privilege beyond being (or having recently been) a multisig member: (1) a member adds/confirms a request that isn't yet at threshold, (2) that member is later removed via a normal `DeleteMember` action (e.g., precisely because their key was suspected compromised), (3) the remaining members confirm other, unrelated requests reaching what they believe is the intended `num_confirmations` — but the stale vote from the removed member is silently still being counted on any request it previously touched. No special exploit conditions are needed beyond the normal member-removal lifecycle, which is a routine operational action (e.g., key rotation, offboarding, revoking a suspected-compromised key).

### Recommendation
When deleting a member in `delete_member`, iterate over `self.confirmations` (not just `self.requests` filtered by originator) and remove the deleted member's `to_string()` entry from every request's confirmation `HashSet`. Alternatively, have `confirm()` (and the threshold check) filter the stored confirmation set against `self.members.contains(...)` before comparing its length to `num_confirmations`, so stale entries from removed members never count.

### Proof of Concept
1. Deploy `MultiSigContract::new([A, B, C], 3)` (3-of-3 threshold).
2. `C` calls `add_request_and_confirm` with a `Transfer { amount }` request `R` targeting an attacker-controlled account — `R` now has 1 confirmation (`C`).
3. The organization discovers `C`'s key may be compromised and removes `C` via a separate confirmed `DeleteMember { member: C }` request. `delete_member` only removes requests *created by* `C`; since `R` was created by `C` itself in this scenario it would actually be cleaned — so consider the stronger variant: `A` creates `R`, `C` confirms it (1/3), then `C` is removed. `delete_member`'s cleanup loop filters on `r.member == member`, i.e. only requests where `C` is the **creator**, so `R` (created by `A`) is untouched and its confirmation set still contains `C`.
4. Now only `B` needs to call `confirm(R)`: `confirmations.len() + 1 == 2` — still short of 3, so per current code this specific 3-of-3 example needs one more; but with `num_confirmations = 2` (2-of-3) after removal `members.len() - 1 = 2 >= 2` passes the assert, and `B`'s single confirmation on top of stale `C` immediately satisfies `1 (stale C) + 1 (B) >= 2`, executing `R` with only one live signer (`B`) instead of two.
5. Result: the transfer/`AddKey`/`DeployContract` request executes despite only one currently-valid member having approved it, breaking the `confirmations_counted == live_member_approvals` invariant. [3](#0-2) [4](#0-3)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
