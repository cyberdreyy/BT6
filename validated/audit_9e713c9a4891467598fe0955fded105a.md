### Title
switch_operator's pending commission distribution bypasses old operator's beneficiary redirect after operator key changes - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move)

### Summary
`switch_operator` forces a `request_commission_internal` call keyed to `old_operator` right before the `StakingContract` (and its `distribution_pool`) is re-keyed to `new_operator` in the staker's `Store`. The commission distribution entry created by that call stores `old_operator`'s raw address as the pool shareholder key. When this entry is later paid out via the public `distribute` entrypoint, the payout is performed under the `new_operator` key, so the beneficiary-redirect check in `distribute_internal` (`recipient == operator`) never matches, and the commission is paid directly to `old_operator`'s address instead of `old_operator`'s registered beneficiary.

### Finding Description
In `switch_operator`, the staker's staking contract entry is first removed from the `staking_contracts` map keyed by `old_operator`, then processed, then re-added keyed by `new_operator`: [1](#0-0) 

The forced `distribute_internal` call at line 785 correctly uses `operator = old_operator`, so any already-inactive stake at that point is properly redirected to `beneficiary_for_operator(old_operator)` inside `distribute_internal`: [2](#0-1) 

However, the subsequent `request_commission_internal(old_operator, &mut staking_contract)` call (line 793) does not pay out immediately — it only unlocks the commission and records a new distribution-pool share via `add_distribution`, keyed literally by the `operator` parameter (i.e., `old_operator`'s address), not by `beneficiary_for_operator(old_operator)`: [3](#0-2) [4](#0-3) 

Immediately after that, the entire `StakingContract` struct — including this pending `distribution_pool` entry keyed by `old_operator` — is moved from the `old_operator` slot to the `new_operator` slot in the staker's `Store` (line 803). Once the stake pool's lockup expires, anyone (an unprivileged caller) can invoke the public `distribute(staker, operator)` entrypoint, but the only valid key now is `new_operator`: [5](#0-4) 

This calls `distribute_internal(staker, new_operator, staking_contract)`. When it iterates the pool's shareholders and reaches the entry whose stored key is `old_operator`, the beneficiary-redirect check compares the stored recipient to the *current* `operator` parameter (`new_operator`), not to `old_operator`: [6](#0-5) 

Since `old_operator != new_operator`, the `if (recipient == operator)` check fails, so `beneficiary_for_operator(old_operator)` is never consulted. The funds are deposited directly to `old_operator`'s raw address instead of the beneficiary address `old_operator` had registered via `set_beneficiary_for_operator`.

### Impact Explanation
This changes who receives the final pre-switch commission settlement: instead of `old_operator`'s configured beneficiary (per `set_beneficiary_for_operator`, `BeneficiaryForOperator` resource), the funds land directly in `old_operator`'s own account address. The commission is not stolen by a third party and is not permanently stranded — it still reaches an address controlled by (or nominally belonging to) `old_operator` — but the beneficiary-redirect guarantee documented for `distribute_internal`/`set_beneficiary_for_operator` ("any existing unpaid commission rewards will be paid to the new beneficiary") is silently violated for this specific residual batch. If `old_operator`'s registered beneficiary exists precisely because the operator's own address is not the intended custodian (e.g., a separate custodial/revenue-sharing address, or an operator key that is otherwise not meant to receive funds directly), this pending commission slips through to the wrong destination with no way for the beneficiary to reclaim it via the beneficiary mechanism.

### Likelihood Explanation
The trigger sequence is straightforward and reachable from unprivileged/normal operations: the staker calls `switch_operator` (a normal owner action) while `old_operator` has commission left to unlock and has previously set a beneficiary; commission is unlocked via `request_commission_internal` but sits in `pending_inactive` until lockup expiry; then any unprivileged account calls the permissionless `distribute` entrypoint after lockup expiry. No special privileges beyond being the staker (for `switch_operator`) are needed, and the final `distribute` call is explicitly documented as callable by anyone. This is a deterministic outcome of the re-keying order in `switch_operator`, not a race condition, so it will reproduce every time these preconditions hold.

### Recommendation
Before moving the `StakingContract` from `old_operator`'s key to `new_operator`'s key, ensure the commission recorded by the forced `request_commission_internal` call is either (a) recorded under `beneficiary_for_operator(old_operator)` directly in `add_distribution`, or (b) fully distributed immediately (forcing an unlock-and-wait is not required if paid to beneficiary), or (c) `distribute_internal`'s redirect check should compare the stored recipient against the operator that was in effect when the distribution entry was created, not the pool's current live operator. A pragmatic fix is to record beneficiary-resolved recipients at `add_distribution` time (call `beneficiary_for_operator(operator)` instead of `operator` when adding the operator's commission share), removing the need to reconcile operator identity at payout time.

### Proof of Concept
1. Staker creates a staking contract with `old_operator`, and `old_operator` accrues rewards/commission.
2. `old_operator` calls `set_beneficiary_for_operator(beneficiary_addr)`.
3. Staker calls `switch_operator(staker, old_operator, new_operator, new_commission_percentage)`. Internally this calls `request_commission_internal(old_operator, ...)` → `add_distribution(old_operator, staking_contract, old_operator, commission_amount)`, adding a distribution-pool share keyed by `old_operator`'s address; `stake::unlock_with_cap` moves this amount to `pending_inactive`.
4. Wait for the stake pool's lockup to expire (advance epoch(s) past lockup).
5. Any account calls `distribute(staker_address, new_operator)`. `distribute_internal` runs with `operator = new_operator`; when it processes the shareholder entry keyed `old_operator`, `recipient == operator` (`old_operator == new_operator`) is `false`, so `beneficiary_for_operator(old_operator)` is never applied, and the coins are deposited to `old_operator` directly rather than to `beneficiary_addr`.
6. Assert: recipient of the deposit for that share is `old_operator`, not `beneficiary_addr` — contradicting the beneficiary guarantee for that commission batch.

        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

    /// Add a new distribution for `recipient` and `amount` to the staking contract's distributions list.
    fun add_distribution(
        operator: address,
        staking_contract: &mut StakingContract,
        recipient: address,
        coins_amount: u64,
    ) {
        let distribution_pool = &mut staking_contract.distribution_pool;
        let (_, _, _, total_distribution_amount) =
            stake::get_stake(staking_contract.pool_address);
        update_distribution_pool(
            distribution_pool,
            total_distribution_amount,
            operator,
            staking_contract.commission_percentage
        );

        distribution_pool.buy_in(recipient, coins_amount);
        let pool_address = staking_contract.pool_address;
        emit(AddDistribution { operator, pool_address, amount: coins_amount });
    }
