### Title
`setApr`/`setAprs` are callable by anyone while `idleCDO` is unset, letting an attacker fix the epoch APR at the 2000% cap before the CDO is whitelisted - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Lin CMS hardcoded-JWT bug is an access-control failure: a baked-in credential lets any unauthenticated caller reach privileged backend functions. The strongest analog in idle-tranches is in `IdleCreditVault.setApr`, where the only authorization check is deliberately skipped when `idleCDO == address(0)`. Between `initialize` and `setWhitelistedCDO`, any EOA can call `setAprs`/`setAprsWithBuffer`/`setApr` and pin both `unscaledApr` and `lastApr` to `DEFAULT_MAX_APR` (20e18 ≈ 2000% annualized). Once the CDO is linked, the poisoned APR drives `expectedEpochInterest`, inflating yield owed to depositors and, in fixed-APR mode, the borrower repayment / AA share at `stopEpoch` — an attacker-controllable rate that persists if the deployment script does not re-set APRs after whitelisting.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol:225-235`, `setApr` only enforces `msg.sender == idleCDO || msg.sender == manager` when `idleCDO != address(0)`:

```solidity
function setApr(uint256 _apr) public {
    address _cdo = idleCDO;
    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
}
```

`idleCDO` is only assigned later by `setWhitelistedCDO` (line 954), an owner-gated call that is typically a separate transaction from `initialize`. During that gap the only remaining bound is `maxApr`, which `initialize` sets to `DEFAULT_MAX_APR = 20e18` (lines 89, 143). `setAprs` (line 206) additionally writes `unscaledApr` with no access check of its own — it relies entirely on `setApr`'s guard, which is the guard being skipped. A poisoned `unscaledApr == 0` (attacker calls `setAprs(0, anything)` while passing `_apr` within cap — note `setAprs(0, 0)` sets `unscaledApr = 0`, which activates the APR0 withdrawal accounting path at line 285) can also silently switch the vault into APR0 mode, changing how `requestWithdraw`/`_settleApr0` account for principal vs. interest for all lenders.

### Impact Explanation
Broken invariant: access control on the interest-rate oracle input. If the inflated `lastApr` survives until `startEpoch`, `expectedEpochInterest` in the CDO is computed from it, so at `stopEpoch` the borrower must repay up to ~2000%/yr scaled interest; if borrower funds are insufficient this manufactures a `stopEpochWithDuration` loss / haircut on pending receipts, and if funded it transfers an inflated interest amount to the AA tranche at the borrower's expense (theft of yield / borrower insolvency up to `maxApr * duration * NAV`). Alternatively setting `unscaledApr = 0` reroutes all subsequent withdraw requests through `apr0Users`/`apr0RateByEpoch` accounting (line 285-286), which can mis-price receipts and freeze claims until accounting is corrected — a temporary-to-permanent freezing of unclaimed yield. Direct loss magnitude is bounded by `maxApr`, i.e. up to ~5.5% of NAV per day the poisoned epoch runs.

### Likelihood Explanation
Exploitability hinges on a deployment window: `initialize` and `setWhitelistedCDO` are separate calls and `idleCDO` is not set in `initialize`, so the window always exists unless the deployer batches them in one transaction. The attacker's write persists until someone calls `setApr`/`setAprs` again; `setAprsWithBuffer` at `startEpoch` (called by the CDO, which is allowed once whitelisted) overwrites both values, so the poisoned value only matters if `startEpoch` does not itself set APRs or if deposits/interest accounting read `lastApr`/`unscaledApr` before the first epoch configuration. Likelihood is therefore moderate-to-low: it requires the vault to be used (or an epoch started) without the owner re-setting APRs after whitelisting. Uncertainty: I could not fully trace whether `startEpoch` unconditionally calls `setAprsWithBuffer` on the strategy in this codebase version; if it does, the durable impact reduces to the `unscaledApr = 0` APR0-mode flip and APRs observed during the buffer period.

### Recommendation
Remove the `idleCDO == address(0)` bypass entirely — revert unless `msg.sender == idleCDO || msg.sender == manager`, and set `manager`/`idleCDO` atomically during `initialize` (or in the same deployment transaction) so there is no unauthenticated window. Add a regression test asserting `setApr`, `setAprs`, and `setAprsWithBuffer` revert for non-CDO/non-manager callers immediately after `initialize`.

### Proof of Concept
Foundry fork PoC sketch (run against a fork where the vault impl/proxy exists, or deploy the proxy locally):

```solidity
// contracts/IdleCreditVault.sol proxy deployed, initialize() already mined,
// setWhitelistedCDO() not yet called -> idleCDO == address(0)

IdleCreditVault vault = IdleCreditVault(vaultProxy);
assertEq(vault.idleCDO(), address(0));

address attacker = address(0xdead);
vm.startPrank(attacker);
// 1) Pin APR at the cap — should revert but does not
vault.setAprs(20e18, 20e18);            // unscaledApr = 20e18, lastApr = 20e18
assertEq(vault.lastApr(), 20e18);
assertEq(vault.unscaledApr(), 20e18);

// 2) Or silently force APR0 accounting mode
vault.setAprs(0, 0);
assertEq(vault.unscaledApr(), 0);       // requestWithdraw now uses apr0Users path
vm.stopPrank();

// After owner calls setWhitelistedCDO(cdo) and an epoch starts without
// re-setting APRs, expectedEpochInterest uses the attacker-chosen lastApr,
// inflating AA yield / borrower repayment (or routing all requests into
// APR0 settlement), breaking the fair-mint/loss-waterfall invariant.
```

Note: the fix is one line (delete the `_cdo != address(0)` branch or require `manager` even pre-whitelist). If the deployment flow always calls `setAprsWithBuffer` before any user interaction, residual impact is limited to the APR0-mode flip; that residual should still be treated as a finding because it changes per-user receipt accounting with no authorization.
