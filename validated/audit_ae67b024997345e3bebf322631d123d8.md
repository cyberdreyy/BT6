### Title
Prefunded AA queue deposits made near the epoch-end cutoff permanently brick `stopEpochWithDuration`, freezing all pool funds - ([File: contracts/IdleCDOEpochQueue.sol])

### Summary
The external Symmetrical bug class — a mandatory second step guarded by a `block.timestamp` window whose expiry makes the step impossible forever, freezing counterparty funds — maps directly onto the prefunded deposit flow in `IdleCDOEpochQueue` / `IdleCDOEpochVariantPrefunded`. A KYC-passing lender (unprivileged attacker) can deposit dust into the AA prefunded queue at the last allowed moment, leaving no usable window for `processDepositsToBorrower`. The leftover `epochPendingDeposits` then makes `prefundedDepositsToProcess()` revert inside `_afterStopEpochWithDuration`, so the epoch can never be stopped and every lender's funds are frozen.

### Finding Description
The prefunded deposit pipeline is a two-step process with a hard timestamp cutoff, mirroring `liquidatePartyB` / `liquidatePositionsPartyB`:

1. `requestDeposit` accepts AA queue deposits only while `block.timestamp + prefundedDepositWindow < epochEndDate` (`IdleCDOEpochQueue.sol:111-117`).
2. `processDepositsToBorrower` forwards the queued funds to the borrower, but enforces the **same** cutoff: it reverts once `block.timestamp + prefundedDepositWindow >= epochEndDate` (`IdleCDOEpochQueue.sol:163-164`).

There is no slack between "deposits still accepted" and "prefunding still possible". A deposit landing in the final instants of the window (or any deposit the honest manager doesn't prefund before the boundary, e.g. due to network conditions or a same-block sandwich by the attacker) can never be forwarded.

Once the epoch ends, `stopEpochWithDuration` is the only available stop path — `_beforeStopEpoch` reverts on the direct `stopEpoch` selector whenever a queue is configured (`IdleCDOEpochVariantPrefunded.sol:39-48`). During the stop, `_afterStopEpochWithDuration` calls `prefundedDepositsToProcess()`, which reverts whenever `epochPendingDeposits[_epoch] != 0` (`IdleCDOEpochQueue.sol:280-281`). That revert propagates through `stopEpochWithDuration`, so the epoch can never be stopped.

The only escape is `deleteRequest`, which is per-user and voluntary — a depositor who never calls it (the attacker) keeps `epochPendingDeposits` non-zero forever. There is no privileged "force refund" path.

### Impact Explanation
Permanent freezing of all pool funds. With the epoch never stoppable:
- `startEpoch` can never run again (`isEpochRunning` stays true, and `epochEndDate + bufferPeriod` gating is moot), so the vault is dead.
- `requestWithdraw`/`claimWithdrawRequest` receipts can never mature (epoch number never bumps), tranche redemptions are frozen.
- The only funds recoverable are the attacker's own dust deposit — the loss is the entire pool TVL of queued deposits, prefunded principal, and lender balances.

Broken invariant: liveness of the epoch state machine; an unprivileged user's dust deposit permanently halts a privileged-only, time-critical settlement step.

### Likelihood Explanation
- Attacker capability: any KYC-passing wallet can call `requestDeposit(1)` on the AA queue. Cost is 1 wei of underlying, fully recoverable via `deleteRequest` afterward.
- Trigger: deposit at `epochEndDate - prefundedDepositWindow - epsilon`, or front-run `processDepositsToBorrower` in the same block to add new pending deposits the call won't see (the check `_checkNotAllowed(epochPrefundedDeposits[_epoch] != 0)` means prefunding can only happen once, but `epochPendingDeposits` is snapshotted inside that single call — deposits added afterward in the same block are permanent).
- The honest-manager assumption does not save the design: the manager cannot choose a different stop path (direct `stopEpoch` is blocked), cannot refund other users' queued deposits, and cannot clear `epochPendingDeposits`.
- One caveat: if `prefundedDepositWindow == 0`, `requestDeposit` has no cutoff and `processDepositsToBorrower` reverts on the `_prefundedWindow == 0` condition entirely — the exploit window depends on configuration, but any nonzero window admits the dust-lock attack near the boundary.

### Recommendation
Decouple the two checks, analogous to the Symmetrical fix of replacing `block.timestamp`-relative expiry with a one-sided bound:

- Give `processDepositsToBorrower` a strictly later cutoff than `requestDeposit` (e.g., deposits close at `epochEndDate - window`, prefunding allowed until `epochEndDate`), or drop the cutoff for prefunding entirely — prefunding late only means the borrower holds funds briefly before stop.
- Better: make `_afterStopEpochWithDuration` tolerant of leftover queue deposits — e.g., let `prefundedDepositsToProcess` settle prefunded funds and leave `epochPendingDeposits` claimable/refundable via `deleteRequest` post-stop, or add a privileged `refundPendingDeposits(epoch)` that returns queue-held underlyings to depositors, so a stuck deposit can never block epoch finalization.

### Proof of Concept
Foundry fork sketch against the prefunded variant setup in `test/foundry/IdleCDOEpochQueue.t.sol`:

```solidity
function testPrefundedQueueDustLocksStopEpoch() external {
    // assume: prefunded AA queue enabled, prefundedDepositWindow = 5 days,
    // epoch running with epochEndDate = T_end.
    address attacker = makeAddr('kyc-attacker'); // passes isWalletAllowed
    uint256 dust = 1; // 1 wei underlying

    // attacker deposits at the last moment deposits are accepted
    vm.warp(cdoEpoch.epochEndDate() - queue.prefundedDepositWindow() - 1);
    deal(address(underlying), attacker, dust);
    vm.startPrank(attacker);
    underlying.approve(address(queue), dust);
    queue.requestDeposit(dust); // records epochPendingDeposits[nextEpoch] = 1
    vm.stopPrank();

    // now inside the cutoff: processDepositsToBorrower can never succeed
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    queue.processDepositsToBorrower();

    // epoch ends; borrower repays; manager tries to stop
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _fundBorrowerRepayment(); // approve principal + interest to cdoEpoch

    vm.prank(manager);
    // stopEpoch direct selector is blocked by _beforeStopEpoch
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(apr, interest);

    // stopEpochWithDuration reverts inside _afterStopEpochWithDuration ->
    // prefundedDepositsToProcess() -> epochPendingDeposits != 0
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpochWithDuration(nextDuration, apr, interest);

    // attacker never calls deleteRequest; epochPendingDeposits stays nonzero forever.
    // No further epoch transitions are possible; all lender funds are frozen.
    assertTrue(cdoEpoch.isEpochRunning());
}
```

Key assertions: `requestDeposit` succeeds just inside the boundary; both stop paths revert permanently; the attacker retains the ability to reclaim their dust via `deleteRequest` while all other funds stay locked.
