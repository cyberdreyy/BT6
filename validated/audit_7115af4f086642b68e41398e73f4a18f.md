### Title
Missing re-initialization guard in `LockupContract::new` allows any caller to reinitialize an already-funded lockup account and steal its balance - ([File: lockup/src/lib.rs])

### Summary
Every other contract in this repository (`lockup-factory`, `multisig`, `staking-pool`, `staking-pool-factory`, `voting`, `whitelist`) explicitly guards its `#[init]` constructor with `assert!(!env::state_exists(), "The contract is already initialized")`, but `LockupContract::new` in `lockup/src/lib.rs` has no such check. Because the method is a plain public `#[init]` function with no caller/owner check, any unprivileged account can call `new` a second time on an already-deployed, already-funded lockup account, overwrite `owner_account_id`, `lockup_information`, and `vesting_information` with attacker-chosen values, and immediately unlock the account's full NEAR balance to themselves.

### Finding Description
The broken invariant is: `owner_account_id_after_first_new == owner_account_id_forever` (init happens exactly once). In practice, `LockupContract::new` at [1](#0-0)  performs no `env::state_exists()` check and no caller authorization check before constructing and returning a fresh `Self { owner_account_id, lockup_information, vesting_information, staking_information: None, staking_pool_whitelist_account_id, foundation_account_id }`, which `near_bindgen`/`#[init]` then writes over the existing contract state.

Contrast this with the sibling contracts in the same repo, all of which explicitly guard against double-init, e.g. `LockupFactory::new`: [2](#0-1) 

The lockup contract's `new` lacks the equivalent line. Since `new` sets `lockup_amount: env::account_balance()` at [3](#0-2)  using whatever balance the account currently holds (i.e., the funds deposited during the original, legitimate deployment), and takes `owner_account_id`, `lockup_timestamp`, `transfers_information`, `vesting_schedule`, `release_duration`, and `foundation_account_id` entirely from caller-supplied arguments with only basic `is_valid_account_id` format checks (no ownership/foundation authorization) at [4](#0-3) , an attacker can call `new` directly against any already-deployed lockup account (a NEAR function call, not requiring a key on that account — access-key-less function calls are permitted for contract methods) and set:
- `owner_account_id` = attacker's own account,
- `transfers_information` = `TransfersEnabled { transfers_timestamp: <some past timestamp> }`,
- `lockup_timestamp` = `None`,
- `release_duration` = `None`,
- `vesting_schedule` = `None`,
- `foundation_account_id` = `None`.

After this call, `get_owners_balance`/`get_locked_amount` (in `lockup/src/getters.rs`) compute the locked amount from the *new* `lockup_information`, which now has no future lockup timestamp and transfers already enabled in the past — the entire account balance becomes immediately liquid to the new (attacker) owner, who can then call `transfer` to move the NEAR out.

No existing guard prevents this: there is no `assert_owner`, no `assert_self()`, no `env::state_exists()` check, and the `#[init]` macro attribute alone (as demonstrably used elsewhere in this same codebase with an explicit manual guard) does not enforce single-initialization here.

### Impact Explanation
This is a Critical-severity finding: an unprivileged attacker can seize full ownership of any deployed lockup contract account (created via the public `lockup-factory`) and drain its entire locked/unvested NEAR balance before `lockup_timestamp` or vesting completes, releasing tokens to a party (the attacker) never entitled to them. This is repeatable against every lockup account on the network since the attack requires only knowledge of the target lockup account ID and a function call with no attached deposit or special permissions.

### Likelihood Explanation
Preconditions: the target lockup contract must already be deployed (trivial — anyone can create one via `lockup-factory::create`, or target any existing lockup account) and its `lockup_timestamp`/vesting must not yet have released funds (the common case for freshly created lockups). Attacker cost is a single function call with default gas, no deposit required. This is fully repeatable across every lockup account in existence, making it a very high likelihood, trivially exploitable issue once reachable, contingent on whether `new` is actually externally callable post-deployment (it is a public `#[near_bindgen]` method with no access restriction).

### Recommendation
Add an explicit reinitialization guard at the top of `LockupContract::new`, mirroring the other contracts in this repository:
```rust
assert!(!env::state_exists(), "The contract is already initialized");
```
placed before any other logic in `lockup/src/lib.rs`'s `new` function (before line 191).

### Proof of Concept
```rust
// lockup/src/lib.rs tests module
#[test]
#[should_panic(expected = "The contract is already initialized")]
fn test_reinit_blocked() {
    let context = basic_context();
    testing_env!(context.clone());
    let _contract = new_contract(true, None, None, false);

    // Attacker re-calls `new` on the same (already initialized) account,
    // trying to become the new owner and immediately unlock funds.
    testing_env!(context.clone());
    let _attacker_contract = LockupContract::new(
        AccountId::from("attacker"),           // owner_account_id set to attacker
        0u64.into(),                             // lockup_duration
        None,                                    // lockup_timestamp
        TransfersInformation::TransfersEnabled {
            transfers_timestamp: to_ts(GENESIS_TIME_IN_DAYS - 1).into(), // already in the past
        },
        None,                                    // vesting_schedule
        None,                                     // release_duration
        AccountId::from("whitelist"),
        None,                                     // foundation_account_id
    );
    // Without the fix, this call succeeds and overwrites `owner_account_id`.
    // Binding under test: owner_account_id (before) == owner_account_id (after).
    // assert_eq!(contract.owner_account_id, "owner"); would fail post-attack,
    // proving the invariant "init happens exactly once" is broken.
}
```
Run with `cargo test -p lockup test_reinit_blocked`. Before the fix, the test fails to panic (the second `new` call succeeds), demonstrating the vulnerability; after adding the `env::state_exists()` guard, the test passes as expected.

    pub fn new(
        owner_account_id: AccountId,
