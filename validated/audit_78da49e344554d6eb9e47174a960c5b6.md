### Title
Stale-epoch instant withdraw receipts escape default recovery accounting and become permanently unpayable - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The CVE analog is a use-after-free/dangling-reference: a queued item is consumed from one view (per-epoch accounting) while another view (the aggregate per-user receipt) still references it. In `IdleCreditVault`, instant-withdraw receipt basis is stored per epoch in `instantWithdrawsRequestsByEpoch[_user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]`, but `defaultPendingClaimBasis()` only counts `instantWithdrawClaimsByEpoch[epochNumber]` at finalization time. A receipt created in epoch `E` and still unfunded when `epochNumber` advances to `E+1` is excluded from the default claim basis, yet remains in `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws`. The funded-claim path then tries to pay it at par while `_transferFundedClaim` forbids spending the isolated recovery reserve, so the claim permanently reverts — the user's underlying are frozen forever, and `pendingInstantWithdraws` can never reach zero.

### Finding Description
`requestInstantWithdraw` records the receipt under the *current* `epochNumber`:

```solidity
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
``` [1](#0-0) 

`epochNumber` is incremented inside `deposit()` whenever `isEpochRunning()` is true (i.e., on `stopEpoch` funding), so an unfunded instant receipt survives epoch rollovers while its per-epoch entry stays pinned to the request epoch. [2](#0-1) 

At default finalization, `defaultPendingClaimBasis()` only adds the *finalization* epoch's instant basis:

```solidity
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
``` [3](#0-2) 

After finalization, `claimInstantWithdrawRequest` first clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (the *current* epoch), then pays the full remaining `instantWithdrawsRequests[_user]` through `_transferFundedClaim`, which reverts if the payment would touch `defaultRecoveryReserve`: [4](#0-3) [5](#0-4) 

Since `finalizeDefaultRecovery` reprices/burns the CDO's active tokens to the recovery ratio, the strategy's only underlying after default is the reserve itself. The stale-epoch receipt therefore can never be paid: every `claimInstantWithdrawRequest` call reverts inside the reserve guard.

### Impact Explanation
An unprivileged lender who requests an instant withdraw in epoch `E` that is not fully funded before `stopEpoch` bumps `epochNumber` has their underlying permanently frozen once `finalizeDefaultRecovery` runs in a later epoch. The receipt was never included in `defaultPendingClaimBasis`, never haircut, and can never be claimed — a permanent freezing of user funds quantified as the full unfunded `instantWithdrawsRequests[_user]` amount. The global `pendingInstantWithdraws` also remains nonzero forever, breaking the invariant that the instant queue drains.

### Likelihood Explanation
Requires three conditions: (1) an instant-withdraw request that is under-funded at `stopEpoch` (`pendingInstantWithdraws > 0` after `collectInstantWithdrawFunds`, which the code explicitly supports as a "still-unfunded remainder"), (2) the borrower defaults in a later epoch, and (3) `finalizeDefaultRecovery` executes. None of these require privileged misbehavior; `collectInstantWithdrawFunds` may transfer any `_amount` less than the pending basis. [6](#0-5) 

### Recommendation
In `defaultPendingClaimBasis()` (and `_claimDefaultedInstantWithdrawRequest`), include *all* unfunded instant receipts, not just `instantWithdrawClaimsByEpoch[epochNumber]`. Since `pendingInstantWithdraws != 0` is already the trigger for `defaultInstantWithdrawsFinalized`, the aggregate `pendingInstantWithdraws` (plus the already-funded remainder tracked per user) is the correct basis, or track a global unfunded instant claim total independent of epoch. Alternatively, persist the request-epoch chain per user so claims from epochs `< defaultRecoveryEpoch` are haircut by `defaultRecoveryPrice` rather than routed to the par funded path.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (test/foundry/IdleCreditVault.t.sol harness)
function testStaleEpochInstantReceiptFrozenAfterDefault() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount); // KYC'd lender (this contract)

    _startEpochAndCheckPrices(0);

    // Attacker/victim requests instant withdraw in epoch 0
    cdoEpoch.requestInstantWithdraw(0); // via CDO, AA tranche

    // Epoch 0 stops with only PARTIAL instant funding:
    // borrower supplies less than pendingInstantWithdraws,
    // so collectInstantWithdrawFunds leaves a remainder.
    _stopEpochWithPartialInstantFunding(); // pendingInstantWithdraws > 0

    // Epoch 1 starts and runs; epochNumber is now 1 while the
    // user's instantWithdrawsRequestsByEpoch entry sits at epoch 0.
    _startEpochAndCheckPrices(1);

    // Borrower defaults; owner finalizes recovery at epochNumber == 1
    cdoEpoch._handleBorrowerDefault();
    cdoEpoch.finalizeDefaultRecovery(recovered, recoverySource);

    // defaultPendingClaimBasis only counted instantWithdrawClaimsByEpoch[1] == 0.
    // The epoch-0 receipt was excluded from the haircut AND from the reserve.

    // Claim now permanently reverts: funded path would spend reserve.
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimInstantWithdrawRequest();
    // pendingInstantWithdraws remains > 0 forever; funds frozen.
}
```

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
