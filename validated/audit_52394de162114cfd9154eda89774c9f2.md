I have enough signal on the vault side — checking whether the CDO gates instant withdraw requests after a default.### Title
Post-default instant withdraw receipts are recorded under the wrong epoch and paid at par from other claimants' funded balance - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The S3 Encryption Client CVE is a missing-commitment bug: an attacker with write access stores a substitute artifact (a new EDK in an "instruction file") that is later consumed as if it were the original. The analog in `IdleCreditVault` is epoch commitment for withdraw receipts. Normal `requestWithdraw` explicitly branches on `defaultRecoveryFinalized` so post-default requests are segregated into `postDefaultRequests` and paid only from `defaultRecoveryReserve` [1](#0-0) . `requestInstantWithdraw` performs the same receipt write (`_mint` to user, per-epoch bookkeeping) but never checks `defaultRecoveryFinalized`, so a receipt created after default finalization is recorded under the *current* epoch, not `defaultRecoveryEpoch` [2](#0-1) . On claim, `_claimDefaultedInstantWithdrawRequest` only looks up `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and misses the new receipt [3](#0-2) ; execution then falls through to burning `instantWithdrawsRequests[_user]` and paying face value via `_transferFundedClaim`, which spends any non-reserve balance — i.e., underlying funded for other users' still-unclaimed receipts [4](#0-3) .

### Finding Description
- Epoch phase: `defaulted`/`finalized` (`defaultRecoveryFinalized == true`, `defaultInstantWithdrawsFinalized == true`).
- A tranche holder (unprivileged attacker) calls the CDO's instant-withdraw entry point, which forwards to `IdleCreditVault.requestInstantWithdraw(_amount, _user)`.
- The vault burns the attacker's strategy tokens and mints a 1:1 receipt, recording it in `instantWithdrawsRequestsByEpoch[_user][epochNumber]` — where `epochNumber > defaultRecoveryEpoch` — and increments the aggregate `instantWithdrawsRequests[_user]` [5](#0-4) .
- The attacker then calls `claimInstantWithdrawRequest`. `_claimDefaultedInstantWithdrawRequest` returns 0 because its lookup is keyed to `defaultRecoveryEpoch`, so the haircut path is skipped [6](#0-5) . The function then burns the aggregate `instantWithdrawsRequests[_user]` (which includes the post-default receipt) and calls `_transferFundedClaim(_user, amount)` paying the full face amount from the contract's non-reserve underlying balance [7](#0-6) .
- The receipt is a fungible strategy token with no commitment tying it to `defaultRecoveryEpoch`; the "instruction file" (per-epoch mapping entry) was written to a fresh epoch, so the default-claim consumer reads zero and the funded-claim consumer pays par.

### Impact Explanation
Post-default, the strategy tokens burned by the attacker are economically worth `defaultRecoveryPrice` (the haircut ratio), yet the claim pays face value. The payment source is underlying previously collected via `collectInstantWithdrawFunds`/`collectWithdrawFunds` for *other* users' funded receipts that remain unclaimed, or any residual non-reserve balance [8](#0-7) . This is direct theft: the attacker extracts `amount` underlying while contributing tokens worth only `amount * defaultRecoveryPrice`, and victim claimants' funded receipts become unbacked (permanent loss). Invariant broken: one receipt one payout / default-loss socialization — post-default claims must settle at `defaultRecoveryPrice`, not par.

### Likelihood Explanation
- Requires a finalized borrower default, which is a supported, exercised code path (`finalizeDefault`, `finalizeDefaultRecovery`, `defaultRecoveryReserve`).
- Requires residual funded-but-unclaimed instant/normal withdraw balance, which is normal since claims are lazy and can sit for arbitrary epochs.
- The only gate on the attack path is `idleCDO` forwarding instant-withdraw requests post-default. Caveat: I could not fully verify whether `IdleCDOEpochVariant` blocks instant-withdraw entry after default finalization — if it does not (consistent with `requestWithdraw` deliberately handling the post-default case rather than reverting), the exploit is reachable by any tranche holder.

### Recommendation
Mirror the normal-withdraw handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized` is true, either revert or route the request into a post-default bucket (e.g., `postDefaultRequests` semantics) that is paid only from `defaultRecoveryReserve` at the already-applied haircut. Equivalently, commit each instant receipt to its funding epoch and make `claimInstantWithdrawRequest` reject claims whose basis is not funded — never let the aggregate `instantWithdrawsRequests[_user]` pay face value for a receipt recorded after `defaultRecoveryEpoch`.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// Setup: epoch-based IdleCDO + IdleCreditVault strategy, attacker holds tranche tokens.
// 1) Victim requests instant withdraw in epoch N; manager stops epoch,
//    collectInstantWithdrawFunds pulls funding into the vault. Victim does not claim.
// 2) Borrower defaults; owner calls default flow -> finalizeDefaultRecovery
//    sets defaultRecoveryFinalized, defaultRecoveryEpoch = N+1, defaultRecoveryPrice < 1e18.
// 3) Attacker calls idleCDO instant-withdraw entry ->
//    IdleCreditVault.requestInstantWithdraw(amount, attacker)
//    (goes through: no defaultRecoveryFinalized check).
//    Receipt recorded in instantWithdrawsRequestsByEpoch[attacker][N+2].
// 4) Attacker calls claimInstantWithdrawRequest(attacker) via CDO:
//    - _claimDefaultedInstantWithdrawRequest sees
//      instantWithdrawsRequestsByEpoch[attacker][N+1] == 0 -> skips haircut.
//    - Burns instantWithdrawsRequests[attacker] == amount and pays `amount`
//      underlying at par from the victim's funded balance.
// 5) assert(attackerUnderlyingGain == amount) while attacker's burned tokens
//    were worth amount * defaultRecoveryPrice; victim's claim now reverts/underflows
//    on safeTransfer for lack of balance.
```

If step 3 is blocked at the CDO layer (unverified), the finding reduces to a missing-invariant hardening gap rather than a live exploit; the asymmetric default handling between `requestWithdraw` and `requestInstantWithdraw` remains a defect to fix.

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
