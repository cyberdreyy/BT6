## Analog Found

### Title
Malicious maker can set zero-duration `Timelocks` to force instant public cancellation and steal the resolver's safety deposit - (File: `contracts/BaseEscrowFactory.sol`, `contracts/EscrowSrc.sol`, `contracts/libraries/TimelocksLib.sol`)

### Summary
The `Timelocks` value that governs the entire withdrawal/cancellation lifecycle of an `EscrowSrc`/`EscrowDst` clone is fully attacker-controlled by the order **maker**, embedded in the LOP order extension as `extraDataArgs.timelocks` and passed unmodified (except for `setDeployedAt`) into the created escrow's immutables. Neither `_postInteraction` nor `createDstEscrow` enforces any minimum duration for the `SrcWithdrawal`, `SrcCancellation`, `SrcPublicCancellation`, or the destination equivalents. A malicious maker can therefore set all offsets to `0`, which makes the cancellation window open at the exact same instant as escrow deployment, before the taker even has a chance to redeem with the secret.

### Finding Description
`_postInteraction` builds `immutables.timelocks` directly from `extraDataArgs.timelocks` (the order-signed extension data) and only overwrites the `deployedAt` field: [1](#0-0) 

`createDstEscrow` performs the same pass-through and only checks that `DstCancellation` is not later than `srcCancellationTimestamp` — it never enforces a lower bound: [2](#0-1) 

`TimelocksLib.get` simply adds the (attacker-chosen) per-stage offset to `deployedAt`, with no floor: [3](#0-2) 

`EscrowSrc.withdraw`/`withdrawTo` require `block.timestamp` to be within `[SrcWithdrawal, SrcCancellation)`, while `cancel`/`publicCancel` only require `block.timestamp >= SrcCancellation` / `SrcPublicCancellation`: [4](#0-3) 

If the maker sets `SrcCancellation = SrcPublicCancellation = 0` (and any withdrawal offsets ≥ 0), then at the very block the escrow is deployed, `block.timestamp >= deployedAt + 0` is already true, so:
- `withdraw`/`withdrawTo` permanently revert (`onlyBefore(SrcCancellation)` fails immediately, since `block.timestamp` can never be earlier than `deployedAt`), removing the taker's ability to ever redeem with the secret.
- `publicCancel` becomes callable by **any** access-token holder in the very same block, which returns the maker's tokens to the maker and pays the escrow's `safetyDeposit` (funded by the taker/resolver) to `msg.sender`.

Because `onlyAccessTokenHolder` is the only restriction on `publicCancel`, an unrelated third party (or a maker-controlled alt account) can race the resolver and claim the resolver's own safety deposit before the resolver's private `cancel` transaction lands.

### Impact Explanation
This lets an unprivileged, malicious maker guarantee two outcomes with a single crafted order:
1. The swap never genuinely settles — the maker's tokens are unconditionally returned to the maker via instantly-available `cancel`/`publicCancel`.
2. The resolver's native safety deposit (posted as an incentive for correct execution) can be stolen by whichever access-token holder wins the race for `publicCancel`, at zero cost to the maker.

This matches the Medium-severity bounty category "theft of coins/tokens meant for transaction fees or native refund paths," since the safety deposit is exactly this type of incentive/fee-like value, and it is lost through an unprivileged actor (maker) manipulating parameters within the live fill flow — not through any privileged or resolver-only assumption.

### Likelihood Explanation
Likelihood is moderate: the malicious order's extension (and therefore its timelocks) is visible on-chain/off-chain before a resolver chooses to fill it, so a careful resolver implementation could reject anomalous zero-duration orders. However, nothing in the on-chain contracts enforces this, so any resolver bot that does not independently validate timelock sanity (or any automated/naive filler) is exposed, and the exploit requires no privileged access — only crafting and signing a normal LOP order as the maker. This directly parallels the original Putty finding, where the same "maker sets duration to 0" pattern was accepted despite the taker technically being able to inspect order parameters beforehand.

### Recommendation
Enforce a protocol-level minimum duration between `deployedAt` and each of `SrcWithdrawal`, `SrcCancellation`, `SrcPublicCancellation`, `DstWithdrawal`, `DstCancellation` (and their public counterparts) in `_postInteraction` and `createDstEscrow`, reverting if any window is zero or below the minimum, and ensuring monotonic ordering (`Withdrawal < Cancellation < PublicCancellation`) is validated on-chain rather than trusted from maker-supplied data.

### Proof of Concept
1. Malicious maker creates a Fusion order whose extension `extraDataArgs.timelocks` encodes all stage offsets (`SrcWithdrawal`, `SrcPublicWithdrawal`, `SrcCancellation`, `SrcPublicCancellation`, and the `Dst*` equivalents) as `0`, per `TimelocksSettersLib.init` layout: [5](#0-4) .
2. A resolver fills the order via the Limit Order Protocol; `_postInteraction` deploys `EscrowSrc` with `immutables.timelocks.setDeployedAt(block.timestamp)`, so every stage offset resolves to `block.timestamp` itself: [6](#0-5) .
3. In the same block, `withdraw`/`withdrawTo` revert because `onlyBefore(SrcCancellation)` is already false: [7](#0-6) .
4. Any address holding the access token calls `publicCancel(immutables)` immediately, receiving the resolver's `safetyDeposit` and returning the maker's tokens to the maker: [8](#0-7) .
5. The resolver is left having provided the safety deposit and the maker's tokens transiently, but ends up with neither the secret-based redemption nor guaranteed recovery of its own safety deposit.

    /**
     * @notice Returns the timelock value for the given stage.
     * @param timelocks The timelocks to get the value from.
     * @param stage The stage to get the value for.
     * @return The timelock value for the given stage.
     */
    function get(Timelocks timelocks, Stage stage) internal pure returns (uint256) {
        uint256 data = Timelocks.unwrap(timelocks);
        uint256 bitShift = uint256(stage) * 32;
        // The maximum uint32 value will be reached in 2106.
        return (data >> _DEPLOYED_AT_OFFSET) + uint32(data >> bitShift);
