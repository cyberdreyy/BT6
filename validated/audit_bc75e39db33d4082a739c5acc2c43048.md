### Title
JWT replay TOCTOU race in `jwtReplayCache.isReplay`/`recordUsage` allows one-shot JWT to trigger a workflow twice - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks `h.jwtCache.isReplay(claims.ID)` and later calls `h.jwtCache.recordUsage(claims.ID)` as two separate, non-atomic critical sections guarded independently by `RLock`/`Lock`. Two concurrent `HandleUserTriggerRequest` calls carrying the identical JWT (same `jti`) can both pass the `isReplay` check before either calls `recordUsage`, letting a single authorized JWT authorize and trigger the workflow twice.

### Finding Description
The reachable path is `httpTriggerHandler.HandleUserTriggerRequest` → `httpTriggerHandler.authorizeRequest` → `WorkflowMetadataHandler.Authorize`, invoked once per inbound gateway trigger request with `req.Auth` as the JWT token: [1](#0-0) , [2](#0-1) .

Inside `Authorize`, the JWT is verified, then replay is checked, and only after signer authorization succeeds is `recordUsage` called — with no lock held across the whole sequence: [3](#0-2) 

The underlying cache implements `isReplay` (RLock) and `recordUsage` (Lock) as two independent critical sections rather than a single atomic test-and-set: [4](#0-3) 

If two goroutines call `Authorize` with the same `jti` concurrently, both can execute `isReplay` (each acquiring/releasing the `RLock` independently) before either reaches `recordUsage`. Since both see `exists == false`, both pass the replay guard, both pass signer authorization (same signer/key), and both proceed to record usage and return a valid `*gateway.AuthorizedKey`, causing the caller to dispatch the workflow trigger twice from a single JWT.

There is no additional serialization upstream: `httpTriggerHandler` does not lock per-`jti` or per-request before calling `authorizeRequest`, and `HandleUserTriggerRequest` has no idempotency check keyed on `jti` prior to authorization. [1](#0-0) 

The existing unit test only exercises the sequential (non-concurrent) case and would not catch this race: [5](#0-4) 

### Impact Explanation
This is a quota/allowlist (one-shot JWT) bypass: an attacker holding a single valid, unexpired, unused JWT for a workflow HTTP trigger can cause the workflow to execute twice (or more, depending on race window and number of concurrent requests) instead of once, by firing concurrent identical requests. This defeats the intended single-use guarantee of the JWT and can lead to duplicate/double execution of workflow triggers, which may have downstream effects (e.g., duplicate fund movement or state changes) depending on what the triggered workflow does.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs one valid, unexpired, unused JWT issued for a workflow HTTP trigger — no elevated privileges beyond that of a normal caller. The race window is small but real and highly reproducible under `go test -race` with two goroutines calling `Authorize`/`HandleUserTriggerRequest` concurrently with the same token; production exploitability depends on network-level ability to fire near-simultaneous requests, which is feasible for any client.

### Recommendation
Replace the separate `isReplay`/`recordUsage` calls with a single atomic check-and-set operation under one lock, e.g., a `checkAndRecord(jti string) bool` method that holds `cache.mu.Lock()` once, checks existence, and if absent inserts the timestamp and returns whether it was newly inserted — mirroring the pattern already used in `authorizer.replayGuard.CheckAndRecord` in `core/capabilities/vault/authorizer.go`. Call this atomic method from `Authorize` instead of the current two-step check.

### Proof of Concept
Go test plan (in `workflow_metadata_handler_test.go`):
1. Build a `WorkflowMetadataHandler` via `createTestWorkflowMetadataHandler`, register one authorized signer/key for a workflow ID as in `TestWorkflowMetadataHandler_Authorize`.
2. Create one JWT (`utils.CreateRequestJWT` + `SignedString`) for a fixed request.
3. Launch two goroutines simultaneously (using a `sync.WaitGroup` and a start barrier/channel) that both call `handler.Authorize(workflowID, tokenString, req)` with the identical token.
4. Run with `go test -race -run TestWorkflowMetadataHandler_Authorize_ConcurrentReplay -count=100` to increase the chance of hitting the window.
5. Assert: exactly one call returns `(key, nil)` and the other returns the replay error `"JWT token has already been used..."`. Currently, under race, both may return success, demonstrating the bypass.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
