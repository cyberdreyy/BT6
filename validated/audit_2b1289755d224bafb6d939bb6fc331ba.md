### Title
Unfunded instant-withdraw receipts are claimable at par via stale aggregate accounting, draining funds reserved for other claimants — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The IdleCreditVault tracks instant withdraws in two ledgers that can diverge: per-epoch/per-user basis (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, `pendingInstantWithdraws`) versus the aggregate `instantWithdrawsRequests[user]`. `claimInstantWithdrawRequest` pays out the *aggregate* at par and only clears the aggregate, without verifying that the specific epoch whose receipt is being claimed was actually funded. When the instant queue is only partially funded (a state the code explicitly supports — `_defaultPrefundedInstantReserve` calls `pendingInstantWithdraws` "the still-unfunded remainder"), a user holding an old funded-but-unclaimed receipt can stack a new unfunded request on top and claim both, spending underlying that belongs to other pending claimants. This mirrors the reference bug: shares/amounts are subtracted in one ledger while the parallel ledger's eligibility check is skipped.

### Finding Description
`requestInstantWithdraw` (line 356) mints a receipt to the user and increments three counters: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]`, and `pendingInstantWithdraws`. Funding arrives later via `collectInstantWithdrawFunds` (line 398), which decrements only the *global* `pendingInstantWithdraws` and pulls underlying into the vault — there is no per-user or per-epoch funded marker. The per-epoch mappings are read only during default finalization (`_claimDefaultedInstantWithdrawRequest`, line 842) and by `defaultPendingClaimBasis` (line 644).

`claimInstantWithdrawRequest` (line 380) then does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

It pays the full aggregate balance, first-come-first-served, from whatever underlying the vault happens to hold. There is no check that `instantWithdrawsRequestsByEpoch[_user][e]` was funded for each request epoch `e`, and `requestInstantWithdraw` has no guard forcing a user to claim a previous receipt before opening a new one (unlike `requestWithdraw`, which does guard re-requests via `lastWithdrawRequest`/`lossRecoveryPriceByEpoch` at lines 261–271).

Attack sequence (running epoch, prefunded or normal instant mode):
1. Epoch N: attacker requests instant withdraw of X. The CDO funds the queue; `collectInstantWithdrawFunds(X)` moves X underlying into the vault and `pendingInstantWithdraws` returns to 0. Attacker does not claim.
2. Epoch N+1: attacker requests instant withdraw of X again (unfunded), and victim requests instant withdraw of Y.
3. The CDO collects Y (partial funding — explicitly possible per the comment at lines 638–640: "startEpoch moved the CDO's available cash to the strategy but that cash covered only part of the instant queue").
4. Attacker calls `claimInstantWithdrawRequest`: it pays `instantWithdrawsRequests[attacker] = 2X` at par, burning all receipts. The vault holds X + Y, so the attacker walks away with the funded X earmarked for their old receipt *plus* part of the victim's funded Y.
5. Victim's claim burns `instantWithdrawsRequests[victim] = Y` but the vault's underlying balance is now insufficient → the `safeTransfer` reverts, freezing the victim's already-funded receipt.

The invariant "one funded receipt, one payout" is broken because funding is tracked globally (`pendingInstantWithdraws`) while payout eligibility is tracked only per-user aggregate — the exact asymmetry of the reference bug, where the reserve farm subtracted shares that the per-profile farm had never credited.

### Impact Explanation
Direct theft plus freezing: the attacker receives underlying funded for other users' receipts (up to the vault's instant-claim balance), and the last claimants' funded receipts permanently revert on claim because their receipt tokens are not burned but the backing is gone. Loss is quantified as the attacker's unfunded request amount (bounded by the funded instant balance of other claimants).

### Likelihood Explanation
Requires only a KYC-passing lender with tranche tokens — an unprivileged attacker. Preconditions: instant withdraws enabled on the vault and an epoch transition where the queue is funded while the attacker holds a stale unclaimed receipt. The attacker controls both the non-claiming (there is no expiry on receipts) and the stacking of a second request. The scenario needs the CDO to partially fund the instant queue or for the attacker to front-run other claimants when new funding lands; FCFS aggregate payout guarantees the earliest claimer captures the pool.

Caveat: I could not fully verify the CDO-side path (`getInstantWithdrawFunds`/`claimInstantWithdrawRequest` wrappers in `IdleCDOEpochVariant.sol`) that determines when partial funding of the instant queue occurs in a non-default epoch. If the honest manager always fully funds the queue before any claim window, the exploitable window narrows to claims racing newly funded epochs — the accounting asymmetry still exists but the trigger depends on funding sequencing.

### Recommendation
Track funded instant balances per epoch (or per user) symmetrically with `instantWithdrawsRequestsByEpoch`: either gate `claimInstantWithdrawRequest` to pay only receipts whose epoch was funded (decrement `instantWithdrawClaimsByEpoch[e]` / a per-epoch funded marker), or require users to claim an outstanding instant receipt before `requestInstantWithdraw` can add a new one, matching the `requestWithdraw` guard at lines 261–271.

### Proof of Concept
Foundry fork PoC outline (not executed — read-only mode):

```solidity
// Setup: credit vault CDO with instant withdraws enabled, borrower funded.
// attacker and victim are KYC'd AA tranche holders.

// 1) Epoch N: attacker deposits, requests instant withdraw of X.
idleCDO.requestInstantWithdraw(X); // mints receipt, instantWithdrawsRequests[attacker]=X
// manager/stopEpoch path funds queue: collectInstantWithdrawFunds(X)
// -> vault holds X, pendingInstantWithdraws == 0. Attacker does NOT claim.

// 2) Epoch N+1 (new epoch started):
idleCDO.requestInstantWithdraw(X);   // attacker stacks: instantWithdrawsRequests[attacker]=2X
idleCDO.requestInstantWithdraw(Y);   // victim: instantWithdrawsRequests[victim]=Y
// CDO funds only Y (partial): vault balance == X + Y, pendingInstantWithdraws == 2X+Y - (X+Y) = X

// 3) Attacker claims FIRST:
idleCDO.claimInstantWithdrawRequest(); // pays 2X at par, drains X + part of Y
// assert attacker received 2X while only X of theirs was funded

// 4) Victim claim:
vm.expectRevert(); // vault balance < Y
idleCDO.claimInstantWithdrawRequest(); // victim's funded receipt frozen
```

The key assertions: `instantWithdrawsRequests[attacker]` aggregates funded and unfunded epochs; `_transferFundedClaim` only guards the `defaultRecoveryReserve` (lines 899–905), not per-epoch instant funding, so the over-claim succeeds and the victim's `safeTransfer` underflows on balance.
