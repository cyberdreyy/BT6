### Title
Loss-adjusted withdraw receipt escapes its haircut when the user re-requests withdraw in a later epoch — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault` records a stop-epoch loss as `lossRecoveryPriceByEpoch[epochNumber]` and looks it up through `lastWithdrawRequest[_user]`. Because `requestWithdraw` unconditionally overwrites `lastWithdrawRequest[_user]` with the current epoch, a user who holds a loss-adjusted receipt from epoch N can submit a dust-sized new request in a later epoch M. The claim path then skips `_claimLossAdjustedWithdrawRequest` (price at epoch M is 0) and falls through to `_claimFundedWithdrawRequest`, which pays the full aggregate `withdrawsRequests[_user]` at par — including the haircutted epoch-N basis — even though the borrower only funded `pendingBasis * lossRecoveryPrice`.

### Finding Description
- `requestWithdraw` stores `lastWithdrawRequest[_user] = currentEpoch` (line 282) and accumulates `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` (lines 292-293).
- On a lossy stop, `collectWithdrawFunds` pulls only `_amount < pendingBasis` and stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` (lines 417-421). The contract therefore holds less underlying than the sum of recorded receipt basis.
- `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (lines 789-792). If the marker was overwritten by a later request, `lossRecoveryPrice == 0` and the function returns 0 without clearing `withdrawsRequestsByEpoch[_user][N]` or decrementing `withdrawsRequests[_user]`.
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` (which still contains the epoch-N basis) at par via `_transferFundedClaim` (lines 338-349), gated only by `epochNumber <= lastWithdrawRequest[_user]` (line 326), which passes once epoch M ends.

The analog to the phin redirect bug is that per-epoch sensitive context — the haircut tied to the receipt's origin epoch — is silently dropped when the request is "redirected" into a newer epoch, so the old receipt is forwarded to the funded (full-faith) claim path.

### Impact Explanation
Direct theft / insolvency. Suppose a user's epoch-N receipt basis is `A` and the realized loss gives `lossRecoveryPrice = p < 1`. The vault was funded `A * p` for that receipt. After re-requesting `ε` in epoch M and waiting one epoch, the user claims `A + ε` at par, extracting `A * (1 - p)` more than funded. That excess is paid out of the shared funded-claim balance (or, after a default, is only bounded by the `defaultRecoveryReserve` guard in `_transferFundedClaim`), leaving later claimants undercollateralized — permanent loss equal to `A * (1 - p)` borne by other receipt holders/LPs.

### Likelihood Explanation
Requires only an unprivileged tranche holder: one withdraw request before a lossy `stopEpochWithDuration`, then one dust re-request in a later epoch, then a normal claim. All calls are user-facing and unprivileged; the epoch sequence (lossy stop followed by a normal epoch) is a routine manager flow, not attacker-controlled state. No existing guard blocks it: `_claimLossAdjustedWithdrawRequest` does not iterate `withdrawsRequestsByEpoch` for older epochs, and `_claimFundedWithdrawRequest` does not net out loss-adjusted epochs.

### Recommendation
Do not key the loss-adjusted claim solely on `lastWithdrawRequest[_user]`. Either iterate `withdrawsRequestsByEpoch` for all epochs with `lossRecoveryPriceByEpoch != 0`, or check in `_claimFundedWithdrawRequest` that none of the epochs contributing to `withdrawsRequests[_user]` has a non-zero `lossRecoveryPriceByEpoch` before paying at par (e.g., keep a per-user set/bitmap of request epochs, or refuse `requestWithdraw` while the latest request epoch carries an unclaimed loss price).

### Proof of Concept
```solidity
// Foundry fork test sketch (USDC-like underlying, epoch CDO + IdleCreditVault strategy)
// 1. user deposits `amountWei` into AA during buffer, requests withdraw of all tranches (epoch N).
_depositWithUser(user, amountWei, true);
vm.prank(user);
uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche));

// 2. Epoch N runs and stops with a realized loss L so borrower funds only pendingBasis*(1 - share).
_startEpochAndCheckPrices(0);
uint256 pendingBasis = strategy.pendingWithdraws();
// manager stops with duration/loss: stopEpochWithDuration(_lossAmount) →
// collectWithdrawFunds(pendingToFund < pendingBasis) sets lossRecoveryPriceByEpoch[N] = p < 1
_stopEpochWithLoss(L); // helper wrapping manager call
assertGt(strategy.lossRecoveryPriceByEpoch(strategy.epochNumber() - 1), 0);

// 3. In the next buffer (epoch N+1), user re-requests a dust withdraw, overwriting
//    lastWithdrawRequest[user] = N+1.
vm.prank(user);
cdoEpoch.requestWithdraw(1, address(AAtranche)); // requires ≥1 wei tranche balance

// 4. Epoch N+1 runs and stops normally; user claims.
_startEpochAndCheckPrices(1);
_stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

uint256 balBefore = underlying.balanceOf(user);
vm.prank(user);
cdoEpoch.claimWithdrawRequest();

// BUG: paid ~receipt + 1 at par instead of receipt * p + 1
assertGt(underlying.balanceOf(user) - balBefore,
         receipt * strategy.lossRecoveryPriceByEpoch(N) / 1e18 + 1);
```

Note: step 3 requires the user to retain a small tranche balance for the dust request (request less than the full balance in step 1, or dust-deposit again). The excess paid equals `receipt * (1 - p)`, drained from the vault's funded-claim balance that backs other pending receipts.
