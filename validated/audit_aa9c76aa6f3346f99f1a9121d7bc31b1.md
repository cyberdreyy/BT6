### Title
Unprotected Second-Step Initializer Allows Any Caller to Inject Malicious `BridgeConfig` — (`File: bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig()` is a second-step initializer that must be called in a separate transaction after `initialize()`. It carries no caller-authentication guard — any externally-owned account can race it during the deployment window and point the committee's `config` slot at an attacker-controlled contract.

---

### Finding Description

`BridgeCommittee` is deployed and initialized in two non-atomic steps:

1. `initialize(committee, stake, minStakeRequired)` — protected by OpenZeppelin's `initializer` modifier, sets committee members and stake.
2. `initializeConfig(_config)` — **no access control**, only checks `address(config) == address(0)`. [1](#0-0) 

```solidity
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

Between the moment `BridgeCommittee` is deployed (step 1) and the moment the deployer calls `initializeConfig` (step 2), the `config` slot is `address(0)` and the guard passes for **any caller**. An attacker who monitors the mempool can front-run the deployer's `initializeConfig` call and substitute an attacker-controlled contract that implements `IBridgeConfig`.

The deploy script confirms the two-step, non-atomic pattern: [2](#0-1) 

```solidity
BridgeCommittee(bridgeCommittee).initializeConfig(address(bridgeConfig));
BridgeCommittee committeeImplementation =
    BridgeCommittee(Upgrades.getImplementationAddress(bridgeCommittee));
committeeImplementation.initializeConfig(address(bridgeConfig));
```

The implementation contract itself also receives a separate `initializeConfig` call, creating a second front-runnable window on the raw implementation address.

---

### Impact Explanation

`BridgeCommittee.config` is the authoritative `IBridgeConfig` reference consumed by `SuiBridge` and `BridgeLimiter` to resolve supported token addresses, chain IDs, token prices, and transfer limits. A malicious `IBridgeConfig` can:

- Return attacker-chosen token contract addresses, redirecting unlocked ERC-20 funds to attacker-controlled contracts.
- Return false chain-ID or token-support answers, causing the bridge to accept or reject transfers arbitrarily.
- Return manipulated token prices, bypassing `BridgeLimiter` daily-limit checks and enabling unlimited token extraction.

This constitutes a **bridge governance bypass enabling illegitimate unlock**, matching the Critical impact tier.

---

### Likelihood Explanation

The vulnerability requires front-running a single deployment transaction on Ethereum mainnet. Ethereum's public mempool makes this straightforward for any MEV searcher or attacker watching for `BridgeCommittee` proxy deployments. The window exists every time the bridge is deployed or redeployed. No special privilege is required — any EOA can call `initializeConfig`.

---

### Recommendation

Add an `onlyOwner` (or equivalent deployer-only) modifier to `initializeConfig`, or — preferably — pass `_config` as a parameter to `initialize()` and set it atomically in the same transaction, eliminating the two-step window entirely:

```solidity
function initialize(
    address[] memory committee,
    uint16[] memory stake,
    uint16 minStakeRequired,
    address _config          // ← add this
) external initializer {
    __CommitteeUpgradeable_init(address(this));
    __UUPSUpgradeable_init();
    // ... existing committee setup ...
    config = IBridgeConfig(_config);
}
```

If a two-step flow is unavoidable, restrict `initializeConfig` to the contract owner:

```solidity
function initializeConfig(address _config) external onlyOwner {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

---

### Proof of Concept

1. Deployer broadcasts `BridgeCommittee.initialize(members, stakes, minStake)` — tx A.
2. Deployer broadcasts `BridgeCommittee.initializeConfig(legitimateConfig)` — tx B.
3. Attacker sees tx B in the mempool and submits `BridgeCommittee.initializeConfig(maliciousConfig)` with higher gas — tx B′.
4. Tx B′ is mined before tx B; `config` is now set to `maliciousConfig`; tx B reverts with `"Config already initialized"`.
5. All subsequent calls to `SuiBridge` that read `committee.config()` receive attacker-controlled responses, enabling arbitrary token-address substitution and limit bypass. [3](#0-2)
