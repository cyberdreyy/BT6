### Title
Reject-then-accept from a single signer double-counts weight into both `total_weight_approved` and `total_weight_rejected`, causing a miner-side liveness wedge on a validly-signed block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner-side `StackerDBListener` tallies each signer's `BlockResponse` into a `BlockStatus` (`total_weight_approved`, `total_weight_rejected`, `responded_signers`, `gathered_signatures`). The accept path and the reject path use inconsistent de-duplication guards, so a single signer who first rejects and later accepts the same block gets their weight counted into *both* running totals. `SignerCoordinator::get_block_status` checks the rejection condition before the approval condition, so this can make the miner treat a block that legitimately reached the 70% signing threshold as globally rejected instead, stalling block production.

### Finding Description
`BlockStatus` tracks per-slot state with two independent guards: [1](#0-0) 

On `BlockResponse::Accepted`, weight is added to `total_weight_approved` guarded only by `gathered_signatures.contains_key(&slot_id)`: [2](#0-1) 

On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` guarded by `responded_signers.insert(slot_id)`: [3](#0-2) 

If a signer sends **Rejected** first (weight added to `total_weight_rejected`, `slot_id` added to `responded_signers`, but *not* to `gathered_signatures`) and later sends **Accepted** for the same `signer_signature_hash` (e.g. because the signer's local pre-commit/re-check logic flips it from reject to sign, as documented in `docs/signer-flows.md` sections 5–6), the accept-path guard `gathered_signatures.contains_key(&slot_id)` is still false, so the signer's weight is added to `total_weight_approved` as well. The reject-path guard (`responded_signers.insert`) only prevents double-counting in the opposite order (accept-then-reject); it does nothing to prevent reject-then-accept double counting. The result: `total_weight_approved + total_weight_rejected` can exceed the true `total_weight` of the signer set, breaking the intended one-vote-per-signer equality.

`SignerCoordinator::get_block_status` (the miner-facing consumer of `BlockStatus`) evaluates the rejection condition first: [4](#0-3) 

then only afterwards checks the approval condition: [5](#0-4) 

Because the rejected-weight branch is checked first, a signer with weight exceeding the blocking-minority threshold (`total_weight - weight_threshold`, i.e. >~30% of total weight — plausible for a single large stacker, as shown in the existing whale-signer test `test_single_signature_threshold`) can, by rejecting and then accepting the same proposal, push `total_weight_rejected` past the blocking-minority line *while the block also has genuinely collected ≥70% approving weight from the rest of the honest set*. The miner will then take the `SignersRejected` branch and abandon a block that in fact carries enough real, verifiable signatures to pass `NakamotoBlockHeader::verify_signer_signatures` on-chain.

### Impact Explanation
This is a High-severity liveness issue: a single misbehaving (or merely flip-flopping, non-Byzantine) signer with sufficient weight can wedge the miner into discarding/re-proposing a validly, sufficiently-signed block, without needing collusion from a majority of the signer set. It does not itself let an invalid/non-canonical block get signed (on-chain verification via `verify_signer_signatures` in `stackslib/src/chainstate/nakamoto/mod.rs` is unaffected), but it breaks the intended "aggregated-weight vs verified-accepts" equality relied on by the miner's coordination logic, causing spurious `NakamotoNodeError::SignersRejected` outcomes, wasted block-production cycles, and potential txid exclusion side effects triggered off the inflated rejection tally.

### Likelihood Explanation
Reachable by a single signer sending two ordinary StackerDB messages (`BlockResponse::Rejected` then `BlockResponse::Accepted`) for the same block hash — no majority collusion, no cryptographic breakage, and no special timing is required beyond what the normal reject→re-evaluate→sign flow documented in `docs/signer-flows.md` (sections 4–6) already permits for signers that provisionally reject and later re-accept. The only precondition is that the misbehaving/flip-flopping signer's weight alone exceeds the ~30% blocking-minority share, which is realistic given the existing whale-signer scenarios already tested in this codebase.

### Recommendation
Use a single, symmetric per-slot state guard for both accept and reject paths (e.g. check `responded_signers.insert(slot_id)` before adding weight in the accept branch too, or track one `HashMap<u32, BlockResponseKind>` per slot and only ever add weight once per slot, moving it from one bucket to the other on a legitimate vote change rather than adding to both).

### Proof of Concept
1. Signer S (with weight > `total_weight - weight_threshold`) sends `BlockResponse::Rejected` for block B. `total_weight_rejected += S.weight`; `responded_signers.insert(S.slot_id)` → true.
2. The rest of the signer set (≥70% weight excluding S) sends `BlockResponse::Accepted` for B, genuinely reaching `total_weight_approved ≥ weight_threshold`.
3. Signer S later sends a valid `BlockResponse::Accepted` for the same B (e.g. after re-evaluating per the pre-commit/threshold flow). Since `gathered_signatures` does not yet contain S's slot_id, `total_weight_approved += S.weight` is executed again [6](#0-5) .
4. In `SignerCoordinator::get_block_status`, both `total_weight_rejected.saturating_add(weight_threshold) > total_weight` and `total_weight_approved >= weight_threshold` are now true; because the rejected branch is checked first, the coordinator returns `NakamotoNodeError::SignersRejected` [7](#0-6)  even though the block carries a genuinely sufficient, verifiable signature set.
