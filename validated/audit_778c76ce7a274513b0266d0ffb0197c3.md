### Title
Instant-withdraw claims never decrement `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch`, causing double funding and corrupted default recovery basis - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the reported `vaultRewardsPerWeight` bug (a counter incremented when obligations enter but never decremented when they are paid out), `IdleCreditVault` increments `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch` in `requestInstantWithdraw`, but `claimInstantWithdrawRequest` pays the user without decrementing either counter. Only `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws`, and only the default-claim path decrements the per-epoch mappings. A claim satisfied from underlying already held by the strategy (e.g. deposits waiting in the buffer period before `startEpoch` forwards them to the borrower) therefore leaves a phantom pending obligation that will be funded a second time, and poisons `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` if a default is later finalized in the same epoch.

### Finding Description
In `requestInstantWithdraw` the strategy burns the CDO's strategy tokens, mints a receipt to the user, and increases three counters: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`/`instantWithdrawClaimsByEpoch[currentEpoch]`, and the global `pendingInstantWithdraws` [1](#0-0) .

`claimInstantWithdrawRequest` burns the receipt and pays the user via `_transferFundedClaim`, zeroing only `instantWithdrawsRequests[_user]`. It never touches `pendingInstantWithdraws`, `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch` [2](#0-1) .

`pendingInstantWithdraws` is only reduced when the CDO explicitly funds the queue in `collectInstantWithdrawFunds` [3](#0-2) , and the per-epoch mappings are only cleared inside `_claimDefaultedInstantWithdrawRequest` [4](#0-3) .

Two broken invariants result:

1. **Double funding / stranded value.** `deposit` keeps underlying inside the strategy contract (it is only forwarded to the borrower at epoch start), so during the buffer phase a user can request an instant withdrawal and claim it immediately against strategy-held underlying, without any `collectInstantWithdrawFunds` call. `pendingInstantWithdraws` remains elevated, so the next epoch bookkeeping treats the already-paid claim as still unfunded and pulls the same amount from the CDO again. That second transfer backs no live receipt; the underlying is stranded in the strategy (recoverable only via privileged `transferToken`), a direct NAV loss to AA/BB LPs equal to the claimed amount [5](#0-4) .

2. **Corrupted default recovery.** If a borrower default is finalized while `pendingInstantWithdraws != 0`, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` — which still includes receipts already paid out — into the recovery basis, and `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` as reserve that the contract does not actually hold (the funds were already transferred to the claimant) [6](#0-5) [7](#0-6) . `finalizeDefaultRecovery` then stores an overstated `defaultRecoveryReserve`/`defaultRecoveryPrice` [8](#0-7) , so late recovery claimants revert on underflow in `_transferDefaultRecovery` (permanent freezing) or receive a diluted payout.

### Impact Explanation
An unprivileged user (any KYC-passing lender interacting through the CDO) can leave phantom instant-withdraw obligations on the books by claiming before a matching collection. The protocol either (a) double-funds the claim at the next epoch transition — a quantified loss equal to the claimed amount that is permanently removed from CDO NAV — or (b) inflates the default recovery basis and reserve by the already-paid amount, diluting or freezing recovery funds owed to honest claimants. Loss scales linearly with the instant-withdrawal size; no guard (`_transferFundedClaim`'s reserve check only protects `defaultRecoveryReserve`, which is zero pre-default) prevents it [9](#0-8) .

### Likelihood Explanation
Requires an epoch credit vault with idle underlying in the strategy during the buffer period (the normal state between `deposit` and `startEpoch`'s transfer to the borrower) or partial instant-queue funding. The attacker only needs to sequence `requestInstantWithdraw` + `claimInstantWithdrawRequest` through the CDO, both unprivileged flows. No privileged misbehavior is needed; the accounting drift then triggers automatically at the next `collectInstantWithdrawFunds` or at `finalizeDefaultRecovery`.

### Recommendation
In `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user][epochNumber]`/`instantWithdrawClaimsByEpoch[epochNumber]` for the claimed receipt, and treat `pendingInstantWithdraws` consistently: either decrement it on claim when the payout consumes strategy-held underlying that was never routed through `collectInstantWithdrawFunds`, or require claims to be funded (i.e., only allow claims after the corresponding collection) so the funded/unfunded invariant is preserved. Mirroring the report's fix: every path that pays out an instant receipt must decrement the same counters that were incremented on request.

### Proof of Concept
Foundry fork PoC outline (against `IdleCDOEpochVariant` + `IdleCreditVault`):

```solidity
// Epoch in buffer phase; underlying sits in IdleCreditVault, not yet sent to borrower.
cdo.depositAA(1000e6);                       // strategy.deposit() -> underlying held in vault
vm.prank(cdo-like path via withdrawInstant flow);
// user requests instant withdraw of 100e6 through the CDO
vault.requestInstantWithdraw(100e6, user);   // pendingInstantWithdraws = 100e6
// claim BEFORE any collectInstantWithdrawFunds: paid from vault-held deposits
cdo.claimInstantWithdrawRequest(user);       // user receives 100e6
assert(vault.pendingInstantWithdraws() == 100e6);          // phantom obligation remains
assert(vault.instantWithdrawClaimsByEpoch(vault.epochNumber()) == 100e6);
// next epoch transition pulls another 100e6 from the CDO -> double-funded, stranded
// OR: borrower defaults -> finalizeDefaultRecovery counts the paid claim twice,
// overstating defaultRecoveryReserve so later claims revert/are diluted.
```

Caveat: the exact CDO-side trigger (`getInstantWithdrawFunds`/epoch transition calling `collectInstantWithdrawFunds`) should be confirmed in `IdleCDOEpochVariant`, but the counter asymmetry in `IdleCreditVault.sol` is self-contained: obligations are created in `requestInstantWithdraw` and destroyed only in `collectInstantWithdrawFunds`/`_claimDefaultedInstantWithdrawRequest`, never in the normal payout path.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
