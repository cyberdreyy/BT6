### Title
Exact-boundary APR decrease fails to trigger instant-withdraw path, forcing a full-epoch lock - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`requestWithdraw` uses a strict `>` when comparing `lastEpochApr` against `currentApr + instantWithdrawAprDelta`. When the APR drop equals exactly the configured minimum delta, the request is silently routed to the normal withdrawal path instead of the instant one, contrary to the documented semantics of `instantWithdrawAprDelta` as the *minimum* APR change that triggers instant withdrawals.

### Finding Description
In `requestWithdraw` the contract decides between the instant-withdraw path and the normal (epoch-settled) path:

```solidity
// contracts/IdleCDOEpochVariant.sol:762-770
uint256 currentApr = creditVault.unscaledApr();
if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
    creditVault.requestInstantWithdraw(_underlyings, msg.sender);
    _withdrawOps(_amount, _underlyings, _tranche);
    return _underlyings;
}
```

`instantWithdrawAprDelta` is documented at `contracts/IdleCDOEpochVariant.sol:37-38` and in `setInstantWithdrawParams` (`:128-136`) as the *min* APR change that triggers instant withdraw. A minimum bound means `lastEpochApr >= currentApr + instantWithdrawAprDelta` should activate the instant path. With the current `>` operator, a decrease of exactly `instantWithdrawAprDelta` takes the normal path: `creditVault.requestWithdraw(_underlyings, msg.sender, principal)` is called and the receipt can only be claimed after the next epoch is stopped and funded (`claimWithdrawRequest` at `:967-971`), whereas the instant path is funded at `startEpoch`/`getInstantWithdrawFunds` during the epoch.

This is the same bug class as the AvailBridge report: an inclusive-vs-exclusive comparison at the boundary of a documented limit. Integrators and the manager set `instantWithdrawAprDelta` expecting "decrease of delta or more → instant"; equality is the edge case that falls through.

### Impact Explanation
A lender requesting withdrawal in the buffer phase, when the new epoch APR is exactly `lastEpochApr - instantWithdrawAprDelta`, has their request converted to a normal receipt. Their funds are locked for the entire next epoch (`epochDuration`, default 30 days, `contracts/IdleCDOEpochVariant.sol:72`) instead of being claimable after `instantWithdrawDeadline`. This is a temporary freezing of user funds caused by the boundary error, plus loss of the instant-claim option they were entitled to under the documented "minimum delta" semantics.

### Likelihood Explanation
The trigger requires the manager/owner-set `instantWithdrawAprDelta` and the newly configured epoch APR to coincide exactly at the boundary — e.g., `instantWithdrawAprDelta = 100` (1%) and the manager sets the next epoch APR exactly 1% below `lastEpochApr`. Round-number APR deltas (0.5%, 1%) make equality plausible whenever the APR is lowered in round steps, which is the normal operating pattern. No attacker action beyond a normal `requestWithdraw` in the buffer window is needed.

### Recommendation
```diff
// contracts/IdleCDOEpochVariant.sol:763
- if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
+ if (lastEpochApr >= (currentApr + instantWithdrawAprDelta)) {
```
Alternatively, if the strict inequality is intentional (delta must be *exceeded*), update the NatSpec at `:37-38` and `setInstantWithdrawParams` to say the delta is the largest non-triggering change rather than the minimum triggering one.

### Proof of Concept
Foundry fork PoC outline (reproducible against the repo's `test/foundry` harness, e.g. `IdleCreditVault.t.sol`):

```solidity
function testInstantWithdrawBoundaryDelta() external {
    // Setup: non-programmable borrower, minted/cash mode either works;
    // enable instant withdraws.
    IdleCreditVault cv = IdleCreditVault(address(strategy));
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    vm.startPrank(manager);
    cdoEpoch.setInstantWithdrawParams(3 days, DELTA, false); // disableInstantWithdraw = false
    vm.stopPrank();

    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount); // buffer phase deposit

    // Run one epoch so lastEpochApr is recorded (stopEpoch stores unscaledApr).
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 lastApr = cdoEpoch.lastEpochApr(); // set at stop below
    vm.prank(manager);
    cdoEpoch.stopEpoch(NEW_APR, 0); // sets lastEpochApr to previous apr

    // Now set next-epoch apr so that lastEpochApr == currentApr + instantWithdrawAprDelta
    // i.e. APR decreased by EXACTLY DELTA.
    // (manager calls cv.setAprs / stopEpoch sets scaled apr to lastApr - DELTA)

    // User requests withdraw during buffer.
    uint256 pendingBefore = cv.pendingInstantWithdraws();
    cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)), address(aaTranche));

    // BUG: because lastEpochApr > currentApr + DELTA is false at equality,
    // the request went to the normal path, not the instant one.
    assertEq(cv.pendingInstantWithdraws(), pendingBefore, "exact-delta drop skipped instant path");
    // The receipt now requires a full extra epoch to be claimable:
    // claimWithdrawRequest reverts until next epoch is stopped & funded.
}
```

Caveat: I verified the boundary comparison at `contracts/IdleCDOEpochVariant.sol:762-770` and the surrounding epoch/claim gating, but did not fully trace `IdleCreditVault.requestInstantWithdraw`/`claimWithdrawRequest` internals due to tool-iteration limits; the instant-vs-normal routing difference is nonetheless clear from the code paths shown. Severity is borderline — the loss is a temporary lock (one epoch) of the requester's own funds rather than theft, which may rate Low/Medium depending on the judging standard.
