### Title
Lockup owner can substitute an attacker-controlled "whitelist" contract when creating a lockup, bypassing the Foundation staking-pool whitelist for unvested/lockup funds - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` lets the caller who is creating (and funding) a lockup override the factory's configured `staking_pool_whitelist_account_id` with an arbitrary account of their choosing via the `whitelist_account_id: Option<ValidAccountId>` parameter, with no restriction that ties this override to whether the lockup being created has a `vesting_schedule` (i.e., holds tokens subject to Foundation-controlled termination). This mirrors the reported bug class of "wrong/attacker-controlled address wired into a trust binding that governs which counter-party may receive escrowed assets," breaking the guarantee that lockup contracts can only delegate to Foundation-approved staking pools.

### Finding Description
`create()` builds the `LockupArgs` for the newly deployed lockup contract and explicitly defaults the whitelist only if the caller does not supply one: [1](#0-0) 

There is no check restricting this override based on `vesting_schedule.is_some()` — the same `create` call may simultaneously set a `vesting_schedule` (which triggers Foundation termination rights over unvested tokens) and a custom `whitelist_account_id`: [2](#0-1) 

The resulting `staking_pool_whitelist_account_id` is passed straight into the deployed lockup contract's `new` call and stored as the contract's trusted whitelist source, used later by the lockup owner to select a staking pool: [3](#0-2) 

The whitelist contract's `is_whitelisted` method is a completely generic, permissionless-to-deploy contract — anyone can deploy their own copy and have it always return `true` for any account: [4](#0-3) 

Once the lockup's callback records the whitelist's answer as authoritative, the lockup treats an arbitrary account as a bona fide, Foundation-approved staking pool: [5](#0-4) 

The custody binding this system is meant to enforce is documented explicitly in the whitelist README: only whitelisted staking pools guarantee that "the lockup contract should be able to recover delegated tokens back to the lockup from a staking pool": [6](#0-5) 

By supplying a self-controlled whitelist account at lockup-creation time, an attacker defeats this guarantee for a lockup that also carries a `vesting_schedule` (unvested funds subject to Foundation clawback via termination). The owner can then deposit/stake the lockup's balance — including still-unvested amounts — to a pool contract the same attacker controls, which simply never releases the funds back.

### Impact Explanation
This breaks the equality: **"staking pool the lockup trusts" == "a pool vetted and approved by the NEAR Foundation."** Instead it becomes "staking pool the lockup owner personally deployed/controls." For a lockup holding a `vesting_schedule`, the Foundation is supposed to be able to terminate and reclaim unvested tokens; if those tokens have already been irreversibly moved into an attacker-controlled "staking pool" account, the Foundation's termination rights become unenforceable against tokens that can never be returned to the lockup. This matches the Critical impact category "locked or unvested tokens released early" / "a wrongly whitelisted or wrongly parameterised deployment," since the whitelist parameter, which exists specifically to gate custody of delegated funds, is attacker-controllable at deployment time with no guard tied to the presence of a vesting schedule.

### Likelihood Explanation
Likelihood is high for any lockup created through the factory with a vesting schedule where the creator/owner is also the attacker (or colludes with one): no special privilege beyond calling the public, payable `create` function is required, and the `whitelist_account_id` override and `vesting_schedule` are both ordinary, independent optional parameters of the same call. No foundation action, redeploy, or victim key is needed — the attacker is the party invoking `create` and later `select_staking_pool`.

### Recommendation
Restrict the `whitelist_account_id` override in `LockupFactory::create` so it cannot be combined with `vesting_schedule.is_some()` (i.e., only allow custom whitelist accounts for lockups with no Foundation-controlled unvested balance), or remove the override entirely and always force the factory-configured, Foundation-managed whitelist account for any lockup carrying a vesting schedule.

### Proof of Concept
1. Attacker deploys their own copy of the `whitelist` contract (`evil-whitelist.attacker.near`), initialized with themselves as `foundation_account_id`, so `is_whitelisted` always returns `true` for any pool they choose — see `whitelist/src/lib.rs:33-57`.
2. Attacker calls `LockupFactory::create` with `owner_account_id = attacker`, a `vesting_schedule` (so the lockup is subject to Foundation clawback of unvested tokens), and `whitelist_account_id = Some(evil-whitelist.attacker.near)` — permitted per `lockup-factory/src/lib.rs:107-134`.
3. The new lockup is initialized with `staking_pool_whitelist_account_id = evil-whitelist.attacker.near`.
4. Attacker (as lockup owner) calls `select_staking_pool("evil-pool.attacker.near")`; the lockup asks the attacker's own whitelist, which answers `true` — `lockup/src/owner.rs:12-41`, `lockup/src/owner_callbacks.rs:6-25`.
5. Attacker deposits and stakes the lockup's full balance (including unvested tokens) into `evil-pool.attacker.near`, a contract they fully control and which never returns funds.
6. When the Foundation later attempts to terminate the vesting schedule and reclaim unvested tokens, the tokens are already gone: they were sent to a pool never actually vetted by the Foundation, permanently defeating the recovery guarantee described in `whitelist/README.md:6-9`.
