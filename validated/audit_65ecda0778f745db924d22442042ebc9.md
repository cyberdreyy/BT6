### Title
Missing cross-flag validation between `disableInstantWithdraw` and `isProgrammableBorrower` allows instant-withdraw requests that permanently freeze the epoch — (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant` keeps three interdependent mode flags — `isProgrammableBorrower`, `isInterestMinted`, and `disableInstantWithdraw` — but its setters validate each flag in isolation rather than as a consistent combination, exactly like the reported `pluginConfig` issue. Specifically, `setInstantWithdrawParams` can enable instant withdrawals (`disableInstantWithdraw = false`) while `isProgrammableBorrower` is true, even though the rest of the contract hard-reverts on that combination. An unprivileged KYC-passing lender can then open an instant withdrawal request, making `_pendingInstant() != 0`, which bricks `stopEpoch`/`startEpoch` and simultaneously makes `getInstantWithdrawFunds` unreachable because it reverts in programmable mode.

### Finding Description
The epoch lifecycle enforces the invariant in `_checkProgrammableBorrowerMode`: programmable borrowers require minted interest and zero pending instant withdrawals (`_checkNotAllowed(isProgrammableBorrower && (!isInterestMinted || _pendingInstant() != 0))`) [1](#0-0) . This check runs inside `startEpoch` [2](#0-1)  and `_stopEpoch`, which additionally reverts whenever `_pendingInstant() != 0` [3](#0-2) .

However, the flag setters do not enforce the same consistency:

- `setInstantWithdrawParams` only checks `paused()`; it does not revert when enabling instant withdrawals while `isProgrammableBorrower` is set [4](#0-3) .
- `setIsProgrammableBorrower` only checks `isEpochRunning`; it does not require `isInterestMinted` or that instant withdrawals are disabled [5](#0-4) .
- `getInstantWithdrawFunds`, the only path that drains `_pendingInstant`, explicitly reverts when programmable mode is active [6](#0-5) .

So once an instant request exists under programmable mode: `stopEpoch` reverts (both at `_checkProgrammableBorrowerMode` and at the `_pendingInstant() != 0` check), `startEpoch` reverts, and the remediation path `getInstantWithdrawFunds` also reverts. The pool is frozen in the running/buffer phase until `isProgrammableBorrower` can be toggled off — and `setIsProgrammableBorrower` itself reverts while `isEpochRunning` is true [5](#0-4) , so a mid-epoch freeze cannot be unwound through the flag at all. The only exit becomes the default/emergency path (`_handleBorrowerDefault`, `_emergencyShutdown`), i.e. a forced default flow for an otherwise solvent borrower.

### Impact Explanation
Permanent freezing of user funds. Sequence: the pool is in the buffer phase with `isProgrammableBorrower = true` (deployed per the factory task, which enables `isInterestMinted` and disables instant withdraws but relies on off-chain ordering [7](#0-6) ). The honest owner/manager calls `setInstantWithdrawParams(delay, delta, false)` — a valid standalone call — to offer instant exits. Any KYC-passing lender (`isWalletAllowed`) then submits an instant withdrawal request during the buffer. From that point `stopEpoch` can never succeed: `_pendingInstant() != 0` fails both guards, and `getInstantWithdrawFunds` reverts under programmable mode. All tranche funds and borrower repayments are locked; the epoch cannot stop or restart. Loss equals the entire TVL's availability, forced through default accounting with associated loss socialization.

### Likelihood Explanation
Medium-low. It requires a plausible honest privileged call (enabling instant withdrawals) in a mode the contract does not support, plus one unprivileged instant request. No malicious privileged role is needed — the setter simply lacks the combination validation that `_checkProgrammableBorrowerMode` assumes. The deployment script itself shows the intended flag triple is maintained only by operational convention, not by code.

### Recommendation
Mirror the reported fix: centralize mode-flag validation. In `setInstantWithdrawParams`, revert when `isProgrammableBorrower && !_disable`. In `setIsProgrammableBorrower`, revert unless `isInterestMinted && disableInstantWithdraw` (and no pending instant requests). Alternatively, funnel all mode changes through a single `setModeFlags` function that validates the combination atomically.

### Proof of Concept
A Foundry fork PoC would: (1) deploy `IdleCDOEpochVariant` + `IdleCreditVault` with a ProgrammableBorrower borrower, `isProgrammableBorrower = true`, `isInterestMinted = true`; (2) owner calls `setInstantWithdrawParams(1 days, 0, false)` — succeeds; (3) KYC'd lender deposits AA in buffer and submits an instant withdrawal request; (4) manager calls `startEpoch()` → reverts in `_checkProgrammableBorrowerMode` (`_pendingInstant() != 0`); even if epoch were already running, `stopEpoch` reverts identically and `getInstantWithdrawFunds()` reverts due to programmable mode; (5) assert epoch can never close and lender funds remain locked absent `_emergencyShutdown`. Note: I could not fully read `getInstantWithdrawFunds`'s revert condition or the exact instant-request entry point within the available iterations, so step 3–4 should confirm the precise request function name and revert path when writing the PoC.
