### Title
POST /sessions leaks distinguishable error messages ("Invalid email" vs "Invalid password" vs DB not-found) allowing unauthenticated user enumeration - ([File: core/web/sessions_controller.go], [File: core/sessions/localauth/orm.go])

### Summary
`SessionsController.Create` forwards the raw error returned by `orm.CreateSession` directly to the HTTP response body via `jsonAPIError`, without normalizing it. Because `orm.CreateSession` returns different, human-readable error strings depending on whether the email doesn't exist (`FindUser` returns a DB error, e.g. `sql: no rows in result set`) versus exists but the password is wrong (`"Invalid password"`), an unauthenticated attacker hitting `/sessions` can directly read account existence from the response body — no timing analysis needed.

### Finding Description
`SessionsController.Create` (core/web/sessions_controller.go:56-60) calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` and on error calls `jsonAPIError(c, http.StatusUnauthorized, err)` [1](#0-0) . `jsonAPIError` serializes `err.Error()` verbatim into the JSON response body [2](#0-1) .

In `orm.CreateSession` (core/sessions/localauth/orm.go:144-162):
- `FindUser` looks up the user by case-insensitive email match; if the email does not exist, this returns the database "no rows" error directly, unmodified [3](#0-2) .
- If the email exists (lookup succeeded), the subsequent `constantTimeEmailCompare` check will essentially always pass (since `FindUser`'s SQL already matched on `lower(email)`), so this branch is not reachable for a valid stored user, meaning existing accounts fall through to the password check and return the literal string `"Invalid password"` [4](#0-3) .

This produces two clearly distinguishable outcomes returned in the plaintext HTTP response:
- Unknown email → a DB-driven error (e.g., `sql: no rows in result set`)
- Known email, wrong password → `"Invalid password"`

The constant-time compare on email in `orm.go:154` only prevents a *timing* side-channel on the email comparison step itself — it does nothing to prevent the *message content* difference, since the two code paths diverge before that point (`FindUser` error vs. password-check error) and both messages are returned unmodified to the caller. This is a much stronger oracle than a timing side channel: the attacker doesn't need statistical timing analysis, they can enumerate by literally reading the JSON error body.

Additionally, prior to calling `CreateSession`, the controller also calls `GetUserWebAuthn(ctx, sr.Email)` which returns an empty list (not an error) for nonexistent users [5](#0-4) , so this call alone doesn't leak, but it does not mitigate the issue above.

The route `/sessions` sits in the unauthenticated group with only a rate limiter applied, so no authentication or authorization layer blocks this request from any anonymous client.

### Impact Explanation
This is a concrete user-enumeration vulnerability: an unauthenticated attacker submitting POST /sessions requests can directly determine whether an arbitrary email address is a registered chainlink node user by inspecting the returned error message, without needing timing measurements. This maps to Chainlink's "information disclosure without direct fund/key impact" bounty class — it does not itself grant session access or credentials, but it materially aids follow-on credential-stuffing/password-spraying/targeted-phishing campaigns against confirmed accounts, and is a real, exploitable divergence beyond intended constant-time protections.

### Likelihood Explanation
Fully unauthenticated, requires no credentials, and is trivially repeatable — an attacker simply issues repeated POST /sessions requests with different candidate emails and a fixed wrong password, rate-limited only by `rl.UnauthenticatedPeriod()`/`rl.Unauthenticated()`. No special network position, host access, or misconfiguration is required.

### Recommendation
Normalize the error returned to the HTTP layer for all authentication-failure paths in `orm.CreateSession` (invalid email, invalid password, and any other pre-MFA failure) to a single generic message (e.g., `"invalid credentials"`) with identical HTTP status code and structure, and ensure `SessionsController.Create` does not forward internal/DB-derived error text to the client. Preserve real details (specific reason) only in the audit log, as is already done via `o.auditLogger.Audit(...)`.

### Proof of Concept
Go handler-level integration test plan:
1. Set up a test app with router (`web.Router`) and create one known user (email `known@example.com`, password `pw`) via `orm.CreateUser`.
2. Table test hitting `POST /sessions`:
   - Case A: `{"email": "known@example.com", "password": "wrongpw"}`
   - Case B: `{"email": "unknown@example.com", "password": "wrongpw"}`
3. For both cases assert:
   - HTTP status code is `401` for both (expected, currently true)
   - **Failing assertion demonstrating the bug**: `require.Equal(t, bodyA, bodyB)` — this currently fails because body A contains `"Invalid password"` while body B contains a distinct DB-error-derived string.
4. Also add a direct unit test on `orm.CreateSession` asserting `err.Error()` is identical across the "unknown email" and "wrong password" cases, which will currently fail per the code shown above (existing `TestORM_CreateSession` in core/sessions/localauth/orm_test.go only asserts `require.Error(t, err)`, not message equality — extend it to assert message equality to catch this regression).
