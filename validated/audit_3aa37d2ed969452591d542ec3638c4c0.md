### Title
Signer's rejection message signature does not cover `reason_code`/`response_data`, allowing tampering with rejection metadata that drives txid banning and miner-invalidation logic - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection::hash()` — the payload actually covered by the signer's cryptographic signature — only commits to `signer_signature_hash` and `chain_id`. The security-relevant fields `reason`, `reason_code`, `response_data.reject_reason`, and `response_data.failed_txid` are serialized into the message but never included in the signed digest, so `verify()`/`recover_public_key()` succeed for *any* combination of those fields as long as the referenced block hash and chain id are unchanged.

### Finding Description
`BlockRejection::hash()` in `libsigner/src/v0/messages.rs` computes the signed digest as:
```
let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
structured_data_message_hash(data, domain_tuple)
``` [1](#0-0) 

Only `signer_signature_hash` (which block) and `chain_id` (in the domain) are hashed. The struct itself carries far more information that downstream logic treats as authenticated:
```
pub struct BlockRejection {
    pub reason: String,
    pub reason_code: RejectCode,
    pub signer_signature_hash: Sha512Trunc256Sum,
    pub signature: MessageSignature,
    pub chain_id: u32,
    pub metadata: SignerMessageMetadata,
    pub response_data: BlockResponseData,
}
``` [2](#0-1) 

`verify()` and `recover_public_key()` both simply recompute the same restricted `hash()` and check the signature against it [3](#0-2) , so any entity holding one genuinely signed `BlockRejection` for a given block/chain-id can freely rewrite `reason`, `reason_code`, and every field of `response_data` (`reject_reason`, `failed_txid`, the tenure/read-count extend timestamps) and the signature will still verify as belonging to the original signer.

Both the receiving signer (`handle_block_rejection` in `stacks-signer/src/v0/signer.rs`) and the node-side coordinator (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`) trust these unauthenticated fields for consensus-relevant decisions:

- On the signer side, `store_and_process_block_rejection` reads `reject_reason`/`response_data` off the rejection to tally weight per `RejectReasonPrefix` and, once the >30% rejection threshold is reached and the active protocol is not global-state, checks specifically for `RejectReasonPrefix::ReorgNotAllowed` to mark the current miner invalid: [4](#0-3) 
- On the node side, `stackerdb_listener.rs` accumulates `failed_txid` and the associated `reason_code` per-txid weight, and uses that to decide which transactions are *temporarily* vs *permanently* excluded from future block templates: [5](#0-4)  and [6](#0-5) 

Neither `handle_block_rejection` in the signer runloop dispatch loop [7](#0-6)  nor `store_and_process_block_rejection` re-derive `reason_code`/`response_data` from anything the signature actually covers — they consume the struct fields as-is once `recover_public_key()` matches a known signer address.

This is the direct analog of CVE-2015-7577: just as Rails' nested-attributes `destroy` option was accepted without being covered by the intended access-control check, here a field (`reason_code`/`response_data`) that materially changes the *effect* of a signed action (rejection reason, txid blame, miner-invalidation trigger) is not actually bound by the signature that is supposed to authenticate the whole message.

### Impact Explanation
This breaks the equality "signed payload == effective payload" for block rejections. A relayer that can place a modified copy of an already-observed, validly signed `BlockRejection` onto the wire (e.g., re-broadcasting through its own StackerDB slot, or any transport path that only re-verifies via `recover_public_key()`/`verify()` rather than binding message content to the observed slot) can:
- Forge `RejectReasonPrefix::ReorgNotAllowed` from an unrelated rejection to help push the 30% threshold that flags the current miner `InvalidatedBeforeFirstBlock`, a liveness-relevant miner-invalidation action, even though the original signer never rejected for that reason.
- Rewrite `failed_txid`/`reason_code` to blame an arbitrary transaction and push it toward permanent exclusion from block templates via the node coordinator's per-txid weight tally.

Both are safety/liveness-relevant mutations of consensus-adjacent bookkeeping that should require the specific signer's actual endorsement of that specific reason, but the signature does not enforce it.

### Likelihood Explanation
Exploitation only requires observing one legitimately signed `BlockRejection` for the target block (these are broadcast in the clear over StackerDB to the whole signer set) and being able to place a modified copy where a peer signer or the node's `StackerDBListener` will read and process it as coming from the original signer's key — no majority, no other signer's private key, and no `auth_token`/local access is needed to defeat the field-binding, since the defect is purely in what `hash()` covers.

### Recommendation
Include `reason`, `reason_code`, and all of `response_data` (or at minimum a hash of them) in the structured-data digest signed/verified by `BlockRejection::hash()`, so `verify()`/`recover_public_key()` fail whenever any of these fields are altered post-signing. Apply the same audit to `BlockAccepted`/`response_data` handling to ensure its metadata is similarly bound.

### Proof of Concept
1. Capture a validly signed `BlockRejection` message `m` from signer `S` for block `B`, e.g. with `reason_code = ValidationFailed(BadTransaction)` and `response_data.reject_reason = InvalidParentBlock`.
2. Construct `m'` identical to `m` except `reason_code = ValidationFailed(ProblematicTransaction)` and `response_data.reject_reason = ReorgNotAllowed`, keeping `signer_signature_hash`, `chain_id`, and `signature` unchanged.
3. Call `m'.verify(&S_pubkey)` / `m'.recover_public_key()` — both succeed, because `hash()` only depends on `signer_signature_hash` and `chain_id` (see `libsigner/src/v0/messages.rs:1802-1837`), which are unchanged.
4. Feed `m'` into `handle_block_rejection`/`store_and_process_block_rejection` on another signer, or into `StackerDBListener`'s rejection-handling branch — both accept it as an authentic rejection from `S` with the forged `reason_code`/`reject_reason`, driving the `ReorgNotAllowed`-triggered miner invalidation or txid-exclusion bookkeeping described above.

    /// The signature hash for the block rejection
    pub fn hash(&self) -> Sha256Sum {
        let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
        let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
        structured_data_message_hash(data, domain_tuple)
    }

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }

        &mut self,
        rejection: &BlockRejection,

        // recover public key
        let Ok(public_key) = rejection.recover_public_key() else {
            debug!("{self}: Received block rejection with an unrecovarable signature. Will not store.";
               "signer_signature_hash" => %block_hash,
               "signature" => %signature

            return;
        };

        // authenticate the signature -- it must be signed by one of the stacking set
        let signer_address = StacksAddress::p2pkh(self.mainnet, &public_key);
        if !self.is_valid_signer(&signer_address) {
            debug!("{self}: Received block rejection with an invalid signature. Will not store.";
                "signer_public_key" => ?public_key,
                "signer_address" => %signer_address,
                "signer_signature_hash" => %block_hash,
                "signature" => %signature
            );
            return;
        }

        let Some(mut block_info) = self.block_lookup_by_reward_cycle(block_hash) else {

                warn!("{self}: Failed to add pending block rejection response: {e:?}");
            }
            return;
        };

        info!("{self}: Received block rejection";

            "consensus_hash" => %block_info.block.header.consensus_hash,

            sortition_state,
            &mut block_info,
