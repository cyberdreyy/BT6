### Title
CORS wildcard origin check missing dot-boundary allows suffix-based origin spoofing (e.g. `evilethereum.org` matches `*.ethereum.org`) - ([File: core/services/gateway/network/httpserver.go])

### Summary
`httpServer.isAllowedOrigin` implements wildcard-origin matching for CORS by stripping the `*.` prefix from a configured allowed origin and then checking `strings.HasSuffix(originHost, allowedHost)`. Because this check does not enforce a `.` boundary before the suffix, an attacker-controlled domain that merely ends with the same characters as the allowed suffix (without being an actual subdomain) is treated as an allowed origin.

### Finding Description
In `core/services/gateway/network/httpserver.go`, `isAllowedOrigin` parses the incoming `Origin` header and each configured `CORSAllowedOrigins` entry via `splitURL`, then for wildcard entries strips the leading `*.` and does: [1](#0-0) 
`strings.HasSuffix(originHost, allowedHost)` only checks that `originHost` ends with the literal string `allowedHost` — it does not require the preceding character to be a `.` (i.e., a real subdomain boundary). Thus, for an allowed entry `*.ethereum.org` (stripped to `ethereum.org`), the attacker-controlled origin `https://evilethereum.org` has host `evilethereum.org`, which ends with `ethereum.org` and satisfies `HasSuffix`, causing `isAllowedOrigin` to return `true` even though `evilethereum.org` is not a subdomain of `ethereum.org` at all — it's an entirely different domain.

This function is called directly from the request path in `handleRequest`: [2](#0-1) 
On a match, the server echoes the attacker's `Origin` value back in `Access-Control-Allow-Origin`, effectively certifying an unintended origin as trusted for CORS purposes. There is no authentication or authorization gate before this check — any unauthenticated client can send an HTTP request/preflight with a crafted `Origin` header to the gateway's HTTP path, since `CORSEnabled` and origin evaluation happen before any JWT/auth processing in `handleRequest`.

### Impact Explanation
This breaks the intended CORS origin allow-listing invariant: an operator who explicitly scoped access to `*.ethereum.org` (and its genuine subdomains) unintentionally also grants CORS access to any registrable domain that happens to share that suffix string (e.g., `evilethereum.org`, `fake-ethereum.org`, or any domain an attacker purchases ending in that literal string). This maps to a CORS/allow-list bypass in the gateway's HTTP-facing surface, enabling an attacker-hosted web page to have its JavaScript treated as an allowed cross-origin client, which can lead to cross-origin response exposure for browser-based clients interacting with the gateway (impact class: broken access-control / allow-list bypass on a client-facing endpoint).

### Likelihood Explanation
Preconditions: `CORSEnabled` must be `true` and at least one wildcard entry (`*.<domain>`) must be present in `CORSAllowedOrigins` — this is an operator configuration choice, not attacker-controlled, but wildcard CORS entries are a normal/supported configuration pattern (not a misconfiguration in itself). Given that precondition, exploitation requires zero privileges: the attacker only needs to register/control a domain string ending in the allowed suffix and serve a page with cross-origin JS from it, or directly send a crafted `Origin` header. This is fully repeatable and deterministic — no timing, no race, no additional secrets needed.

### Recommendation
Enforce a proper subdomain boundary check instead of a raw string suffix match, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
This ensures `evilethereum.org` does not match `ethereum.org` while `sub.ethereum.org` still correctly matches.

### Proof of Concept
Add a Go table test for `isAllowedOrigin` in `core/services/gateway/network/httpserver_test.go` (or equivalent) with configured `CORSAllowedOrigins: []string{"*.ethereum.org"}`:
- `isAllowedOrigin("https://evilethereum.org")` — expected `false`, currently returns `true` (bug reproduced).
- `isAllowedOrigin("https://sub.ethereum.org")` — expected `true` (legitimate subdomain still works).
- `isAllowedOrigin("https://ethereum.org")` — expected... (per current code, exact match also `true`, unaffected).

Handler-level integration test: send an HTTP `OPTIONS`/`GET` request to the gateway's configured `Path` with header `Origin: https://evilethereum.org`, `CORSEnabled: true`, `CORSAllowedOrigins: []string{"*.ethereum.org"}`; assert the response contains `Access-Control-Allow-Origin: https://evilethereum.org`, demonstrating the bypass.
