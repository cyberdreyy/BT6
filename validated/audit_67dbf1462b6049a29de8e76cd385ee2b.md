### Title
Post-default instant withdraw receipts drain the fixed `defaultRecoveryReserve` — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`requestWithdraw` in `IdleCreditVault` has an explicit post-default branch (lines 247–258) that routes receipts into `postDefaultRequests` so they can never pollute the finalized recovery basis. `requestInstantWithdraw` (lines 356–375) has **no** such branch: after `defaultRecoveryFinalized` it still burns CDO strategy tokens, mints receipts to the user, and records them under `instantWithdrawsRequestsByEpoch[_user][epochNumber]` — and `epochNumber` is frozen at `defaultRecoveryEpoch` after default, because it is only incremented inside `deposit()` while `isEpochRunning()` (lines 607–614). The result: a post-default instant receipt is registered in exactly the same epoch slot that `finalizeDefaultRecovery` priced at `defaultRecoveryPrice`, so it can be claimed out of the already-sized `defaultRecoveryReserve`.

### Finding Description
The bug class of CVE-2024-23850 is "state readable/usable before (or outside of) the consistency boundary that was supposed to seal it" — a subvolume read before its root item's epoch boundary. The analog here is a withdraw receipt inserted *after* recovery accounting was sealed, but read by the claim path as if it had existed at finalization time:

1. `finalizeDefaultRecovery` (lines 661–710) computes `defaultRecoveryReserve` from a fixed `totalBasis` and stores `defaultRecoveryPrice` and `defaultRecoveryEpoch = epochNumber`. From that point the reserve is a closed pie.
2. `epochNumber` never advances again: `deposit()` only bumps it when `IIdleCDOEpochVariant(idleCDO).isEpochRunning()` is true, i.e., during a `stopEpoch` deposit — impossible after default.
3. `requestInstantWithdraw` performs `_ensureDefaultRecoveryInitialized()` but does not check `defaultRecoveryFinalized`. It writes `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch] += amount`, `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch] += amount`, `instantWithdrawsRequests[user] += amount`, and `pendingInstantWithdraws += amount` (lines 366–374).
4. `claimInstantWithdrawRequest` (lines 380–393): when `defaultInstantWithdrawsFinalized` was true (i.e., `pendingInstantWithdraws != 0` at finalization — a common state, since instant receipts are frequently unfunded at default time), `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` and pays `amount * defaultRecoveryPrice / 1e18` via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` (lines 842–856, 912–917). The attacker's post-default receipt is indistinguishable from a defaulted-epoch receipt.
5. Even when `defaultInstantWithdrawsFinalized` is false, the receipt is still claimable at par through `_transferFundedClaim` if the strategy happens to hold any non-reserve underlyings, and in all cases `pendingInstantWithdraws` is re-inflated, corrupting the "unfunded remainder" invariant that `_defaultPrefundedInstantReserve` relies on.

The reserve pie was sized at finalization; every unit a post-default requester extracts at `defaultRecoveryPrice` is a unit the legitimate defaulted-epoch claimants can no longer receive — the last claimants' `_transferDefaultRecovery` underflows/reverts on `defaultRecoveryReserve -= _amount`.

### Impact Explanation
Direct theft / permanent freezing of defaulted-epoch recovery funds. If `defaultRecoveryPrice` is `p` and the attacker requests an instant withdraw of `A` underlyings post-default (using already-haircut tranche value, so their cost is ~`A·p` worth of tranche tokens), they pull `A·p` from `defaultRecoveryReserve` that was never budgeted for them. Legitimate claimants holding `B` in defaulted receipts lose up to `A·p` of their recovery (permanent freezing once the reserve is exhausted — the subtraction in `_transferDefaultRecovery` reverts). This scales to the entire reserve: an attacker can repeatedly request instant withdrawals and claim until `defaultRecoveryReserve` is drained, converting the whole recovery pool into attacker payout.

### Likelihood Explanation
- Attacker requirements: only a KYC-passed tranche holder — an allowed unprivileged role per the threat model. `requestInstantWithdraw` is reached through `IdleCDOEpochVariant.requestWithdraw` (lines 758–769) when `_isInstantWithdrawEnabled()` and `lastEpochApr > unscaledApr + instantWithdrawAprDelta`. The manager (honest) legitimately lowering APR post-default, or the configured delta being small, satisfies the gate without any malicious privileged action.
- Preconditions: a borrower default finalized via `finalizeDefaultRecovery` with `pendingInstantWithdraws != 0` at that moment (instant receipts routinely pending). `epochNumber` is structurally frozen post-default, so no timing race is needed — every post-default instant request lands in `defaultRecoveryEpoch`.
- No guard blocks it: the only post-default check lives in `requestWithdraw`; `requestInstantWithdraw` and `claimInstantWithdrawRequest` were not updated for the new reserve accounting. `_transferFundedClaim`'s reserve guard doesn't apply because payout goes through `_transferDefaultRecovery`.

Caveat on reachability: the attack requires `IdleCDOEpochVariant.requestWithdraw` to remain callable after `defaulted()` is set. `requestWithdraw` itself has no explicit `defaulted` check (only allow-flags, wallet allowlist, `_skimDonatedAssets`, `_updateAccounting`); whether `_updateAccounting` reverts when defaulted could not be fully confirmed in the lines reviewed. If it reverts unconditionally post-default, the instant path is unreachable and this reduces to a latent accounting inconsistency in `pendingInstantWithdraws`.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:356): after `defaultRecoveryFinalized`, either revert outright, or record the request in a post-default bucket (analogous to `postDefaultRequests`) that is paid at par from newly funded liquidity — never into `instantWithdrawsRequestsByEpoch[_][epochNumber]` while `epochNumber == defaultRecoveryEpoch`. Additionally, in `claimInstantWithdrawRequest`, cap `_claimDefaultedInstantWithdrawRequest` to receipts that existed at finalization (e.g., snapshot `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` at finalize time and never let it grow), and make `requestInstantWithdraw` revert when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` to keep `pendingInstantWithdraws` consistent with the sealed reserve.

### Proof of Concept
Foundry fork PoC (against the same harness used in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testPostDefaultInstantWithdrawDrainsRecoveryReserve() external {
    // --- Setup: deposits, epoch running, instant withdrawals enabled ---
    _useStandardEpochVariant();
    uint256 instantDelay = 100;
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(instantDelay, 1e18, false);

    address victim  = makeAddr("victim");
    address attacker = makeAddr("attacker");
    uint256 victimAmt   = 100e6;
    uint256 attackerAmt = 50e6;
    uint256 vTranches = _depositWithUser(victim, victimAmt);
    uint256 aTranches = _depositWithUser(attacker, attackerAmt);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // victim requests a normal withdraw (pending, unfunded)
    _requestWithdrawWithUser(victim, vTranches);

    // force an instant-withdraw-eligible stop + an instant request so
    // pendingInstantWithdraws != 0 at default time
    _stopCurrentEpochWithApr(1e18);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(victimAmt / 10, address(tranche)); // instant receipt pending

    // --- Borrower defaults; manager finalizes recovery ---
    _handleBorrowerDefault();                                  // CDO defaulted
    uint256 recovered = /* partial recovery, e.g. 60% of basis */;
    _finalizeDefaultRecovery(recovered);                        // sets defaultRecoveryPrice,
                                                              // defaultRecoveryEpoch = epochNumber (frozen)

    // --- Attacker: request an INSTANT withdraw AFTER finalization ---
    // (lower unscaledApr if needed so the instant path is taken)
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(aTranches, address(tranche));      // -> requestInstantWithdraw

    IdleCreditVault vault = IdleCreditVault(address(strategy));
    uint256 epoch = vault.epochNumber();
    assertEq(epoch, vault.defaultRecoveryEpoch(), "epoch frozen at default epoch");
    // receipt registered in the defaulted epoch slot even though finalized
    assertGt(vault.instantWithdrawsRequestsByEpoch(attacker, epoch), 0);

    // --- Attacker claims from the sealed reserve at defaultRecoveryPrice ---
    uint256 reserveBefore = vault.defaultRecoveryReserve();
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest(attacker);             // _claimDefaultedInstantWithdrawRequest
    uint256 paid = reserveBefore - vault.defaultRecoveryReserve();
    assertGt(paid, 0, "attacker drained reserve not budgeted for them");

    // --- Victim's legitimate defaulted claim now reverts / is short ---
    vm.prank(victim);
    vm.expectRevert();                                          // reserve exhausted -> underflow
    cdoEpoch.claimWithdrawRequest(victim);
}
```

Key assertions demonstrating the broken invariant: `instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch] > 0` despite finalization already sealing that epoch, `defaultRecoveryReserve` decreasing by attacker payout, and the victim's recovery claim reverting for lack of reserve — one receipt one payout and solvency of the recovery pie are both violated.
