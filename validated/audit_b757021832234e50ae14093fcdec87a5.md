### Title
Missing pagination bounds validation on GraphQL resolvers allows negative-offset/oversized-limit SQL errors and unbounded data dumps - (File: core/web/resolver/helpers.go, core/web/resolver/query.go)

### Summary
The GraphQL API's pagination helpers `pageOffset`/`pageLimit` in `core/web/resolver/helpers.go` accept any `int32` value from the client (including zero, negative, or extremely large numbers) and pass it straight through to database queries without bounds checking, unlike the REST pagination helper `ParsePaginatedRequest` in `core/web/api.go`, which explicitly rejects `size < 1` and `page < 1`. [1](#0-0) [2](#0-1) 

### Finding Description
`pageOffset` and `pageLimit` simply return the caller-supplied `*int32` cast to `int`, with no lower or upper bound checks, falling back to a default only when the pointer is `nil`: [1](#0-0) 

Multiple GraphQL resolvers (`Bridges`, `Chains`, `Nodes`, `Jobs`, `JobRuns`, `EthTransactions`, `EthTransactionsAttempts`) call `pageOffset`/`pageLimit` and forward the results directly into ORM calls without any further clamping: [3](#0-2) [4](#0-3) [5](#0-4) 

Those ORM implementations interpolate `offset`/`limit` directly into raw SQL `LIMIT $1 OFFSET $2` clauses, e.g. `BridgeTypes`/`ExternalInitiators` in `core/bridges/orm.go`: [6](#0-5) [7](#0-6) 

PostgreSQL rejects negative `LIMIT`/`OFFSET` values with a query error ("LIMIT must not be negative" / "OFFSET must not be negative"), so a negative `offset` or `limit` GraphQL argument produces a server-side database error on every call. Conversely, an oversized `limit` (up to `math.MaxInt32`) is passed unbounded into the query, letting a caller request the entire table in a single response.

Notably, only one resolver — `JobResolver.Runs` — clamps the limit (`min(pageLimit(args.Limit), 100)`), proving the codebase is aware of the need for an upper bound but failed to apply it consistently across all paginated GraphQL queries: [8](#0-7) 

This is the direct analog of the reported bug class: pagination parameters flowing unvalidated into a database `.skip()`/`.limit()`-equivalent call, causing crashes on negative values and bulk-extraction potential on oversized values.

### Impact Explanation
- Any authenticated GraphQL caller (the resolvers only require `authenticateUser(ctx)`, not a specific elevated role) can trigger repeated database errors by submitting negative `offset`/`limit`, causing wasted query/transaction cycles and noisy error logs — a resource-exhaustion / minor DoS vector. [9](#0-8) 
- An authenticated caller can set `limit` to a very large value to force the node to return the entire `bridge_types`, `external_initiators`, `eth_txes`, `jobs`, or node-status tables in a single response, defeating the intended pagination/rate-limiting design and increasing server memory/CPU load. [10](#0-9) 
- This is scoped to already-authenticated node-operator sessions (Chainlink's GraphQL API is not publicly reachable without a session), so it is a lower-severity Medium finding rather than a full compromise, consistent with the "Fixed" status noted for the analogous frontend report.

### Likelihood Explanation
High for any authenticated user of the Operator UI/GraphQL API — no special role or precondition is required beyond a valid session, and the vulnerable code path is reached on nearly every paginated query (`bridges`, `chains`, `nodes`, `jobs`, `jobRuns`, `ethTransactions`, `ethTransactionsAttempts`).

### Recommendation
- Apply the same validation pattern already used by `ParsePaginatedRequest` (`core/web/api.go`) to the GraphQL `pageOffset`/`pageLimit` helpers: reject or clamp `offset < 0` and `limit < 1`.
- Enforce a maximum limit (mirroring the `min(pageLimit(args.Limit), 100)` pattern already used in `JobResolver.Runs`) consistently across all paginated resolvers in `core/web/resolver/query.go`.
- Consider centralizing this validation in `pageOffset`/`pageLimit` themselves so every resolver benefits automatically rather than relying on per-resolver clamping.

### Proof of Concept
```graphql
# Negative offset/limit triggers a Postgres error ("OFFSET must not be negative")
query {
  bridges(offset: -1, limit: -1) {
    results { id }
  }
}

# Oversized limit dumps the entire external_initiators / bridge_types / eth_txes table
query {
  ethTransactions(offset: 0, limit: 2000000000) {
    results { hash }
  }
}
```
Both requests only require a valid authenticated session (any role that can call the GraphQL endpoint); the ORM layer (`core/bridges/orm.go` `BridgeTypes`/`ExternalInitiators`, and analogous transaction/job ORM calls) forwards the values unchecked into `LIMIT $1 OFFSET $2`, producing either a DB error or an unbounded result set.

func ParsePaginatedRequest(sizeParam, pageParam string) (int, int, int, error) {
	var err error
	page := 1
	size := PaginationDefault

	if sizeParam != "" {
		if size, err = strconv.Atoi(sizeParam); err != nil || size < 1 {
			return 0, 0, 0, fmt.Errorf("invalid size param, error: %w", err)
		}
	}

	if pageParam != "" {
		if page, err = strconv.Atoi(pageParam); err != nil || page < 1 {
			return 0, 0, 0, fmt.Errorf("invalid page param, error: %w", err)
		}
	}

	offset := (page - 1) * size
	return size, page, offset, nil
}

	})

	return
}
