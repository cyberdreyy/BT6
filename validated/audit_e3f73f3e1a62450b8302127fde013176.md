Confirmed root cause: `get_builder_withdrawals` in `specs/gloas/beacon-chain.md` creates the `Withdrawal.amount` field directly from the *requested* `builder_pending_withdrawals[i].amount`, uncapped by the builder's actual balance, while `apply_withdrawals` only debits the builder's CL-side balance by `min(withdrawal.amount, builder_balance)`. This breaks the equality between the Gwei the execution layer is instructed to mint to `fee_recipient` (the full uncapped `withdrawal.amount`) and the Gwei actually removed from the builder's stake.

### Title
Uncapped `builder_pending_withdrawals` amount lets the EL mint more Gwei than is deducted from the builder's balance - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` copies the requested withdrawal amount into the `Withdrawal` object without capping it to the builder's actual balance. `apply_withdrawals` later caps the *state* deduction with `min(withdrawal.amount, builder_balance)`, but the execution layer receives and mints the uncapped `withdrawal.amount` to `fee_recipient`. When a builder's requested pending withdrawal exceeds its balance, the CL only removes the available balance while the EL credits the full requested amount — creating Gwei that was never backed by stake.

### Finding Description
`get_builder_withdrawals` (specs/gloas/beacon-chain.md, "New `get_builder_withdrawals`"):
```python
for withdrawal in state.builder_pending_withdrawals:
    ...
    withdrawals.append(
        Withdrawal(
            index=withdrawal_index,
            validator_index=convert_builder_index_to_validator_index(builder_index),
            address=withdrawal.fee_recipient,
            amount=withdrawal.amount,   # <-- requested amount, NOT capped to builder.balance
        )
    )
``` [1](#0-0) 

Compare this to `apply_withdrawals`, which is the only place the builder's on-chain balance is actually reduced:
```python
def apply_withdrawals(state: BeaconState, withdrawals: Sequence[Withdrawal]) -> None:
    for withdrawal in withdrawals:
        if is_builder_index(withdrawal.validator_index):
            builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
            builder_balance = state.builders[builder_index].balance
            state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
        else:
            decrease_balance(state, withdrawal.validator_index, withdrawal.amount)
``` [2](#0-1) 

The `Withdrawal` list produced by `get_expected_withdrawals` is exactly the list the execution layer is required to honor (per `process_withdrawals`'s own note: "any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals in the execution layer"). [3](#0-2) 

So the equality that must hold is:
`Gwei minted to fee_recipient by EL == Gwei removed from builder.balance on CL`

Concretely, before the attacker's action: builder balance = 1 ETH, `builder_pending_withdrawals` entry with `amount = 5 ETH` (this is exactly the scenario codified in the repo's own test `test_builder_withdrawal_insufficient_balance`, which explicitly documents "withdrawal.amount: 5 ETH (requested amount)" and "builders[0].balance: 0 (deduction capped to available balance)"). [4](#0-3) 

After processing: `state.builders[0].balance` goes from 1 ETH to 0 (only 1 ETH removed from CL state), but the emitted `Withdrawal` object still carries `amount = 5 ETH`, and the EL is required to credit `fee_recipient` with 5 ETH. This mints 4 ETH of Gwei that is unbacked by any burned/reduced stake — the exact analog of the reported bug class ("a value already accounted for/available is ignored, so the payout formula produces more than intended").

The intended design ("Requested amount. Actual = min(amount, builder.balance)") is documented in the repo's own AI-generated report table but is not actually implemented in `get_builder_withdrawals` — only `apply_withdrawals` performs the `min()`, and only on the CL-side bookkeeping, not on the amount that gets sent to/executed by the EL. [5](#0-4) 

### Impact Explanation
This is Gwei created and paid to a non-owner (a fee_recipient address controlled by/for the builder), which is a Critical-class impact under the given rubric: the execution layer executes a payment that the consensus layer's own state does not actually back, since the CL debit is capped but the EL credit is not. Any block proposer/builder can set an oversized `amount` in a `BuilderPendingWithdrawal` (this field is protocol-internal state populated by builder withdrawal requests) whose value exceeds the builder's balance, causing net token inflation with each occurrence, split across the EL/CL state boundary that all spec-following clients must accept as valid.

### Likelihood Explanation
`builder_pending_withdrawals` entries and their `.amount` values are attacker/builder-controllable (a builder can request a withdrawal amount larger than its remaining balance, e.g., after prior withdrawals or slashes reduce `builder.balance` below the originally requested amount, or simply by requesting an amount larger than balance directly). No coalition, malicious client, or foreign key is required — this is purely a spec-defined function operating on protocol state a single builder controls. This significantly raises likelihood relative to typical validator-balance bugs, though I could not fully verify from the indexed spec text whether an earlier validity check (e.g., in the builder withdrawal *request* processing function that populates `state.builder_pending_withdrawals`) already restricts `amount <= builder.balance` at insertion time — that request-processing function was not found in my search results and should be checked before finalizing severity.

### Recommendation
Cap the `amount` field written into the `Withdrawal` object in `get_builder_withdrawals` to `min(withdrawal.amount, state.builders[builder_index].balance)` (accounting for any prior builder withdrawals already included in the same block, similar to how `get_balance_after_withdrawals` is used for validator sweeps), so that the amount instructed to the execution layer never exceeds the amount actually deducted from `state.builders[*].balance`.

### Proof of Concept
1. Builder registered with `state.builders[0].balance = 1_000_000_000` Gwei (1 ETH).
2. `state.builder_pending_withdrawals` contains one entry: `builder_index=0, amount=5_000_000_000` (5 ETH), `fee_recipient` = attacker-controlled address.
3. Call `process_withdrawals(state)`:
   - `get_builder_withdrawals` emits `Withdrawal(validator_index=<builder 0>, address=fee_recipient, amount=5_000_000_000)`.
   - `apply_withdrawals` computes `min(5_000_000_000, 1_000_000_000) = 1_000_000_000` and sets `state.builders[0].balance = 0`.
4. The resulting `state.payload_expected_withdrawals` (which the EL is bound to honor per the parent-block-full commitment) still contains `amount = 5_000_000_000` for that withdrawal.
5. The execution layer credits `fee_recipient` with 5 ETH, while only 1 ETH was ever removed from the builder's beacon-state balance — net 4 ETH of Gwei created from nothing. This matches the exact behavior asserted by the repo's existing test `test_builder_withdrawal_insufficient_balance`, which confirms `withdrawal.amount` remains the uncapped 5 ETH request while `builders[0].balance` is capped to 0. [4](#0-3)
