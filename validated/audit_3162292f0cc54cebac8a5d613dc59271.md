### Title
External Initiator credentials can trigger arbitrary integer-ID job runs, bypassing the "EIs not allowed" restriction in PipelineRunsController.Create - ([File: core/web/pipeline_runs_controller.go])

### Summary
The `POST /v2/jobs/:ID/runs` route accepts authentication via `auth.AuthenticateExternalInitiator`, which sets a synthetic `clsessions.User{Role: clsessions.UserRoleRun}` into the session context. `PipelineRunsController.Create` uses `auth.GetAuthenticatedUser(c)` to gate int-ID job runs to "users only," but since the EI's synthetic user satisfies this check (`isUser == true`), an attacker holding only EI credentials can run any job by integer ID that the EI was never bound to.

### Finding Description
The route is registered in `v2Routes` at [1](#0-0) , combining `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, and `auth.AuthenticateBySession` as alternative auth methods, wrapped by `auth.RequiresRunRole(prc.Create)`.

In `AuthenticateExternalInitiator`, after successfully validating EI access-key/secret, the code sets a *user* session key: `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` [2](#0-1) . This means any request authenticated purely via EI headers now has a "user" object stored under `SessionUserKey`.

`RequiresRunRole` only rejects `UserRoleView`; `UserRoleRun` passes through [3](#0-2) .

Inside `PipelineRunsController.Create`, the code explicitly comments "only users are allowed to run jobs using int IDs - EIs not allowed" and gates on `auth.GetAuthenticatedUser(c)`'s boolean `isUser` [4](#0-3) . But `GetAuthenticatedUser` simply checks whether an object exists at `SessionUserKey` and can be cast to `*clsessions.User` [5](#0-4)  — it does not distinguish a "real" user (authenticated by session/token) from the synthetic EI-role user injected by `AuthenticateExternalInitiator`. Consequently `isUser` evaluates to `true` for EI-only-authenticated requests, and the int32 ID branch runs, calling `prc.App.RunJobV2(ctx, jobID, nil)` for the arbitrary job ID supplied in the URL — with no check that the EI is actually associated with that job.

### Impact Explanation
An attacker who possesses only External Initiator credentials (a low-privilege credential intended solely to trigger webhook-bound jobs) can trigger execution of **any** job on the node by supplying its integer job ID, regardless of whether that job is bound to the EI. This corresponds to Chainlink's "unauthorized job run" bounty impact class — it allows cross-job/cross-tenant unauthorized action (e.g., triggering VRF, OCR-associated pipeline runs, or jobs with side effects like on-chain transactions/fund movement) using credentials never intended to control those jobs.

### Likelihood Explanation
The precondition is minimal: possession of valid EI access key/secret is sufficient — no user session, no API token, no edit/admin role required. Job integer IDs are sequential/small and easily enumerable/guessable. The bypass is deterministic and repeatable on every request; no race condition or timing dependency is needed.

### Recommendation
In `PipelineRunsController.Create`, distinguish real authenticated users from EI-derived synthetic users, e.g., by checking `auth.GetAuthenticatedExternalInitiator(c)` is absent (or by not overwriting `SessionUserKey` in `AuthenticateExternalInitiator`, instead exposing a separate identity type/flag). The int-ID execution branch should only be reachable when the request was authenticated via `AuthenticateByToken`/`AuthenticateBySession`, not via `AuthenticateExternalInitiator`.

### Proof of Concept
Handler-level integration test plan:
1. Start app; insert an External Initiator record and a non-webhook job (e.g., OCR job, as in `setupPipelineRunsControllerTests`) not associated with that EI.
2. Build an HTTP client that authenticates using only `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers (per `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`), with no session cookie or API token.
3. `POST /v2/jobs/<jobID>/runs` with that job's int32 ID.
4. Assert the response is `200 OK` with a `pipelineRun` resource returned (i.e., `RunJobV2` was actually invoked), demonstrating the EI triggered a run on a job it was never bound to — contradicting the intended "EIs not allowed" restriction.
5. As a control, assert `auth.GetAuthenticatedUser(c)` inside a test-only middleware/log returns `isUser=true` and `Role=UserRoleRun` for the EI-authenticated request, confirming the root cause.

// GetAuthenticatedUser extracts the authentication user from the context.
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
