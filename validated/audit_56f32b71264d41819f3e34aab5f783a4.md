### Title
Withdraw-to-a-deleted-account causes a failed, unhandled `Promise::new(account_id).transfer(amount)` whose refund is misattributed as pool "reward" instead of restoring the debited `unstaked` balance - (File: staking-pool/src/internal.rs)

### Summary
`StakingContract::internal_withdraw` debits `account.unstaked` and `self.last_total_balance` synchronously and then fires a bare `Promise::new(account_id).transfer(amount)` with no `.then()` callback to verify success. If the receiving account is deleted before the transfer receipt executes, the transfer fails and the NEAR is refunded to the pool's own account balance, but the contract has already permanently debited the withdrawer's `unstaked` balance and `last_total_balance` with no code path to restore it.

### Finding Description
The broken binding: for any withdrawal, `last_total_balance_after = last_total_balance_before - amount` should hold **iff** the transfer actually leaves the contract; when the transfer is refunded, the invariant that should hold instead is `account.unstaked` is restored to its pre-withdraw value and `last_total_balance` is unchanged.

Code path: [1](#0-0) 
`internal_withdraw` asserts sufficient `account.unstaked`, decrements it, saves the account, then unconditionally does `Promise::new(account_id).transfer(amount)` and `self.last_total_balance -= amount` — with **no `.then()` callback** and no `is_promise_success()` check, unlike the analogous lockup-owner pattern which does check success via `on_staking_pool_withdraw` / `is_promise_success()`. [2](#0-1) 

`withdraw` / `withdraw_all` in `lib.rs` call `internal_ping()` then `internal_withdraw`, with no additional safety net. [3](#0-2) 

Exploit flow: the attacker deposits and later unstakes into a pool with `reward_fee_fraction` set to `{numerator: 1, denominator: 1}` (100% owner fee) — a value the pool owner is free to configure and which is explicitly allowed by the contract's own validation logic (fraction can be at most 1). [4](#0-3) 
After the unstaking delay elapses, the attacker calls `withdraw`/`withdraw_all`, targeting an account they control, and in the same block deletes that account (e.g. via a batched `DeleteAccount` action) so that by the time the `Transfer` receipt for the withdrawal executes, the destination account no longer exists. Per NEAR protocol semantics, a `Transfer` action to a non-existent named account fails and the balance is refunded to the predecessor of the failed receipt — the staking pool contract itself. Because `internal_withdraw` attached no callback, the contract has no way to detect this failure or restore `account.unstaked`.

The contract's own README documents this exact scenario for the *owner's* withdrawal path (returned funds become a reward in the next epoch) but the code does not special-case or protect a delegator's own withdrawal the same way — the debit stands regardless of outcome: [5](#0-4) 

On the next `internal_ping`, the contract compares its actual account balance (now silently inflated by the refunded `amount`, since it never left the contract) against `last_total_balance` (which was already decremented by `amount`). The difference is computed and distributed as a "reward" — with `reward_fee_fraction = 1/1`, the *entire* refunded amount is awarded as stake shares to the pool owner, not returned to the attacker/victim account whose `unstaked` balance was debited. Existing guards (`assert_self`, `is_promise_success`, the U256 rounding pair, etc.) do not apply here because no callback exists to invoke them at all.

### Impact Explanation
The withdrawing account permanently loses `amount` of previously-credited `unstaked` balance with no compensating transfer received, while that exact amount of NEAR — which never actually left the contract — is misattributed entirely to the pool owner as staking reward when `reward_fee_fraction` is 1/1. This is a mis-crediting of funds to the wrong party (owner instead of the rightful delegator), matching the High-severity category ("rewards or owner fees attributed to the wrong party"). Repeatability: any delegator can perform this against any pool, deleting a throwaway target account they control each time, so the attack is repeatable across accounts and epochs, though each repetition consumes a fresh disposable account to delete. Whether this also produces a strict *ledger insolvency* (recorded claims permanently exceeding actual held NEAR) is not established from the code alone — the refunded NEAR remains inside the contract's actual balance and is later reconciled back into `last_total_balance` via the next `internal_ping`, so the totals converge; what diverges is *who* the reconciled amount is credited to, not whether total accounting balances.

### Likelihood Explanation
Preconditions: a pool with `reward_fee_fraction` at or near 1/1 (owner-configured, out of the attacker's control, so the attacker cannot force this on an arbitrary pool — they must find or wait for one so configured), an unstaked balance available for withdrawal after the delay, and the ability to delete an account the attacker controls in the same block as the withdrawal receipt's execution. Attacker cost is low (one throwaway account per attempt), but the impact scales only with the attacker's own principal loss (they lose their own `unstaked` amount, transferring it to the owner) — there's no mechanism shown here by which the attacker profits from someone else's balance, so the primary "gain" is that the pool owner (or an owner colluding with an attacker account) receives funds that should have gone to a delegator.

### Recommendation
Attach a `.then()` callback to the withdrawal transfer (mirroring the lockup contract's `on_staking_pool_withdraw` pattern) that checks `is_promise_success()`; on failure, restore `account.unstaked += amount` and `self.last_total_balance += amount` in the callback rather than leaving the debit final and letting the refunded balance be swept into the next epoch's reward distribution.

    pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        assert!(
            account.unstaked >= amount,
            "Not enough unstaked balance to withdraw"
        );
        assert!(
            account.unstaked_available_epoch_height <= env::epoch_height(),
            "The unstaked balance is not yet available due to unstaking delay"
        );
        account.unstaked -= amount;
        self.internal_save_account(&account_id, &account);

        env::log(
            format!(
                "@{} withdrawing {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );

        Promise::new(account_id).transfer(amount);
        self.last_total_balance -= amount;
    }

    /// Withdraws the entire unstaked balance from the predecessor account.
    /// It's only allowed if the `unstake` action was not performed in the four most recent epochs.
    pub fn withdraw_all(&mut self) {
        let need_to_restake = self.internal_ping();

        let account_id = env::predecessor_account_id();
        let account = self.internal_get_account(&account_id);
        self.internal_withdraw(account.unstaked);

        if need_to_restake {
            self.internal_restake();
        }
    }
