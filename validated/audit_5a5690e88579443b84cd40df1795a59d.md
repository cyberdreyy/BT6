### Title
Pre-first-epoch `requestWithdraw` is misrouted as a "closed pool" receipt: zero-encoded `epochEndDate` mints an instantly claimable receipt with unearned interest, draining vault-held deposits - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The CVE analog is an ambiguity of representation: a sentinel value that is supposed to mean one state is satisfied by a different state that merely shares the same encoding. In `IdleCreditVault.requestWithdraw` and `_claimFundedWithdrawRequest`, `epochEndDate == 0` is used as the encoding for "successfully closed pool" (`isClosed`). But `epochEndDate` is also `0` before the very first `startEpoch`, i.e. the initial buffer phase. A withdraw request made in that window is handled by the closed-pool branch — no `pendingWithdraws` debt is registered and no one-epoch wait is enforced — while still minting a receipt that includes projected epoch interest, payable immediately out of underlyings the vault holds for depositors.

### Finding Description
In `requestWithdraw` the pool-closed flag is derived purely from the CDO's `epochEndDate`: [1](#0-0) 

When `isClosed` is true, `pendingWithdraws += _amount` is skipped — correct for a genuinely closed pool, because no future `stopEpoch` exists to source the funds. However the same branch is taken during the initial buffer before epoch 0 starts, when `epochEndDate` has never been set.

On the claim side, the one-epoch waiting check is gated by the same sentinel: [2](#0-1) 

With `epochEndDate == 0`, `epochNumber <= lastWithdrawRequest[_user]` is never evaluated, so a receipt created in the same transaction window is claimable immediately via `_transferFundedClaim`, which only protects `defaultRecoveryReserve` (zero here) and otherwise pays straight from the vault's underlying balance.

Meanwhile the CDO layer prices the receipt with projected epoch interest — `_underlyings = principal + interest - totalFees` — and the strategy mints `_amount` (interest included) as a receipt while only burning `_principal` strategy tokens: [3](#0-2) [4](#0-3) 

Before the first `startEpoch`, deposited underlyings sit in the vault contract (the credit-vault `deposit` pulls funds into the strategy, and `sendInterestAndDeposits`/borrower transfer only happens at epoch start). The attacker therefore exits instantly at a price inflated by a full epoch of projected interest, paid out of other depositors' principal — interest that no epoch ever produced.

### Impact Explanation
Direct theft. A KYC-passed lender deposits during the initial buffer, calls `cdoEpoch.requestWithdraw(...)` in the same buffer (allowed when `allowAAWithdrawRequest`/`allowBBWithdrawRequest` and `isWalletAllowed` hold — no `isEpochRunning` check exists on this path), and immediately calls `claimWithdrawRequest`. The payout is `principal + projectedInterest - fees`, withdrawn from the vault's underlying balance that economically belongs to other depositors whose funds have not yet been lent to the borrower. The unearned interest component is a net transfer from honest LPs; additionally the skip of `pendingWithdraws += _amount` means the receipt never entered borrower-facing debt accounting, so the protocol's own solvency bookkeeping treats the payout as if it were fully collateralized.

### Likelihood Explanation
The trigger requires the deployment-specific pre-first-epoch window (or a genuinely closed pool while the vault still holds residual underlying, where the same path pays instantly). The attacker needs only to pass the wallet allowlist and hold tranche tokens — both attainable by a normal lender. No privileged action, default, or oracle manipulation is required; the guards that stop related flows (`_ensureDefaultRecoveryInitialized`, `defaultRecoveryReserve` check in `_transferFundedClaim`, `lossRecoveryPriceByEpoch` gating) do not apply because no loss or default has occurred. `_skimDonatedAssets` in `IdleCDOEpochVariant.requestWithdraw` sweeps only *unsolicited* underlying donations to `feeReceiver` and does not touch the strategy vault's deposit balance.

### Recommendation
Distinguish the two states that share the `epochEndDate == 0` encoding. Options:
- In `IdleCreditVault.requestWithdraw`, treat `isClosed` as valid only when `epochNumber > 0` (i.e. the pool actually ran and was closed), and revert or take the normal pending path when `epochEndDate == 0 && epochNumber == 0`.
- Equivalently, keep the one-epoch claim delay active whenever the pool was never closed deliberately: change the guard in `_claimFundedWithdrawRequest` so the `epochEndDate == 0` bypass applies only after a finalized close, e.g. keyed to a dedicated `poolClosed` flag set in the close path rather than inferred from the date.
- Optionally cap receipts minted while `epochEndDate == 0` to `_principal` (no projected interest), since no epoch interest can exist before the first epoch.

### Proof of Concept
Foundry fork PoC sketch (build on `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testPreEpochWithdrawDrainsVault() external {
    uint256 amountWei = 10000 * ONE_SCALE;

    // honest LP deposits during the initial buffer (epochEndDate == 0, epochNumber == 0)
    uint256 mintedVictim = idleCDO.depositAA(amountWei);

    // attacker is a second KYC'd lender depositing in the same buffer
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, amountWei, true);

    // epoch has never started: epochEndDate == 0 -> IdleCreditVault treats pool as closed
    assertEq(cdoEpoch.epochEndDate(), 0);

    // attacker requests withdraw of their full balance; receipt includes projected interest
    vm.prank(attacker);
    uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(receipt, amountWei, 'receipt includes unearned epoch interest');

    // same-window claim succeeds because the epoch-wait check is skipped when epochEndDate == 0
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 claimed = underlying.balanceOf(attacker) - balPre;

    // attacker receives principal + interest paid from vault-held deposits
    assertGt(claimed, amountWei, 'attacker claimed unearned interest immediately');
    // strategy bookkeeping never recorded this as pending borrower debt
    assertEq(IdleCreditVault(address(strategy)).pendingWithdraws(), 0, 'receipt never registered as pending');
}
```

Uncertainty: the exact gating inside `IdleCDOEpochVariant.claimWithdrawRequest` (not fully traced here) may add conditions, but the vault-level paths above (`requestWithdraw` skipping `pendingWithdraws`, `_claimFundedWithdrawRequest` skipping the epoch delay, `_transferFundedClaim` paying from vault balance) are sufficient to demonstrate the misrouting; the PoC should be run against the real CDO `requestWithdraw`/`claimWithdrawRequest` entry points as written.
