### Title
APR0 withdraw receipts from epochs earlier than `defaultRecoveryEpoch` escape the default haircut and revert or pay par against non-reserve funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The CVE's class — an error/edge case mishandled so freed-or-stale state is used as if still valid — maps here to `_claimDefaultedWithdrawRequest` resolving claims by a single epoch key (`defaultRecoveryEpoch`) while APR0 receipts are tracked under their own `principalEpoch`. An APR0 withdrawal requested in epoch N that remains unsettled when the borrower defaults in epoch N+k (> N) is counted in `totalBasis`/`defaultRecoveryReserve` by `finalizeDefaultRecovery` (its principal and interest sit in `pendingWithdraws` via `defaultPendingClaimBasis()`), but `_withdrawClaimAmountsForEpoch(user, defaultRecoveryEpoch)` returns zero for it because `apr0User.principalEpoch != defaultRecoveryEpoch` and APR0 requests never write `withdrawsRequestsByEpoch`. The claim then falls through to `_claimFundedWithdrawRequest`, which lazily settles it via `_settleApr0` and attempts a full par payout through `_transferFundedClaim`.

### Finding Description

Relevant flow in `IdleCreditVault.sol`:

1. `requestWithdraw` with `unscaledApr == 0` routes to `_requestWithdrawApr0`, which records `apr0Users[user].principal` and `principalEpoch = epochNumber`, but writes nothing to `withdrawsRequestsByEpoch` (`IdleCreditVault.sol:285-294`, `:567-577`).
2. On default, `finalizeDefaultRecovery` computes `totalBasis = activeBasis + defaultPendingClaimBasis()`, where `defaultPendingClaimBasis` returns `pendingWithdraws` — which already contains the unsettled APR0 principal (`requestWithdraw` added it at `:279`) and APR0 net interest added by `prepareStopEpochWithApr0` (`:535`). The recovery reserve is sized for the haircut on that basis (`:644-649`, `:679-692`).
3. On claim, `claimWithdrawRequest` → `_claimDefaultedWithdrawRequest` → `_clearWithdrawClaimForEpoch(user, defaultRecoveryEpoch, true)` → `_withdrawClaimAmountsForEpoch(user, defaultRecoveryEpoch)`. That function only counts `apr0User.principal` when `principalEpoch == _claimEpoch` (`:865-880`). For an APR0 request opened in an earlier epoch, `claimBasis == 0`, `pendingWithdraws` is never decremented, and the receipt tokens are never burned.
4. Execution continues to `_claimFundedWithdrawRequest`, which calls `_settleApr0` — `reqEpoch < epochNumber` now holds, so the full principal moves to `settledPrincipal` plus `settledInterest` (`:545-564`) — and then pays `settledPrincipal + settledInterest` at par via `_transferFundedClaim`, burning the receipt (`:319-349`).

Two outcomes depending on strategy balance:

- If the strategy's underlying balance equals `defaultRecoveryReserve` (the common case after finalization, since all non-reserve cash was lent out or already claimed), the guard `balance - reserve < _amount` in `_transferFundedClaim` reverts (`:897-906`). The user's claim is permanently frozen: every subsequent call reverts identically, and their basis share is trapped inside `defaultRecoveryReserve` forever (no sweep path exists for it), also shrinking the effective recovery of other defaulted claimants who can still claim.
- If the strategy happens to hold non-reserve underlyings (e.g., previously collected funded-receipt cash via `collectWithdrawFunds`), the APR0 user withdraws 100% par on a receipt that was haircutted inside `totalBasis`, directly spending cash belonging to funded pre-default withdraw claimants — a first-come theft of the funded pool.

The broken invariant is "one receipt, one recovery-priced payout": the same underlying liability is both haircut-provisioned in the reserve and payable at par through the funded path, because the default-claim lookup uses the wrong epoch key for APR0 receipts.

### Impact Explanation

Direct theft or permanent freezing of withdraw receipts. Any lender who requested a withdrawal while `unscaledApr == 0` in an epoch strictly earlier than the default-finalization epoch (a routine occurrence — APR0 withdrawals are designed to wait one full epoch) either permanently loses the entire receipt or drains par value reserved for other claimants. Quantified loss equals the full APR0 principal plus accrued `apr0RateByEpoch` interest for all such users, up to the entire `apr0TotalPrincipal` bucket of prior epochs.

### Likelihood Explanation

Requires the vault to operate in APR0 mode (`unscaledApr == 0`, a supported mode per `prepareStopEpochWithApr0`), at least one APR0 withdraw request surviving into a later epoch without being claimed (normal, since claims are user-initiated), and a borrower default finalized via `finalizeDefaultRecovery`. All actors are unprivileged; the sequence needs only ordinary `requestWithdraw` calls plus the honest borrower-default flow. The bug is deterministic once those conditions hold — no race or privileged misbehavior needed.

### Recommendation

In `_withdrawClaimAmountsForEpoch` / `_clearWithdrawClaimForEpoch`, treat open APR0 principal with `principalEpoch <= _claimEpoch` (any unsettled APR0 receipt predating or equal to the default epoch) as part of the default claim basis, or settle it into the defaulted-epoch bucket before computing `claimBasis`. Equivalently, `_claimDefaultedWithdrawRequest` should iterate all epochs with pending user receipts rather than only `defaultRecoveryEpoch`. Add a regression test: APR0 `requestWithdraw` in epoch N, `stopEpoch`/`startEpoch` advancing to N+1 without claim, then borrower default + `finalizeDefaultRecovery`, then `claimWithdrawRequest` should pay `principal * defaultRecoveryPrice / RECOVERY_FULL` plus haircutted APR0 interest from the reserve instead of reverting or paying par.
