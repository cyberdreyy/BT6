### Title
Timeout-based conflict staleness lets a signer sign a conflicting sibling block at the same height, breaking the one-signature-per-height equivocation guard - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The pre-commit → signature path guards against a signer producing two conflicting signatures at the same Stacks height by consulting `get_signed_conflicts` and treating any conflict whose `last_endorsed` timestamp is still "fresh" (`last_endorsed > freshness_cutoff`) as blocking, subject to node-derived liveness checks (`conflict_still_blocks`, `reorg_permit_stands`). Once a conflict's endorsement timestamp falls behind the wall-clock cutoff (`tenure_last_block_proposal_timeout`, default 30s), it is dropped from consideration entirely — *unless* it is in the same tenure as the new proposal, in which case it is separately re-verified against the node's tenure tip. A sibling conflict in a **third, unrelated tenure** (neither the new proposal's own tenure nor its parent tenure) is invisible to the chainstate re-check (`check_block_against_signer_db_state`) by design, and once it goes stale by wall-clock time it is also invisible to the conflict guard. Nothing then re-verifies with the node whether that sibling block is actually dead. A miner (or slow gossip) can trivially create a >30s gap between endorsing one block and proposing a conflicting sibling at the same height in a different tenure to make the signer emit a second, conflicting signature.

### Finding Description
In `stacks-signer/src/v0/signer.rs`, `handle_block_pre_commit` (~line 1250) computes: [1](#0-0) 
The freshness comparison uses a pure wall-clock cutoff (`get_epoch_time_secs().saturating_sub(tenure_last_block_proposal_timeout)`) against `conflict.last_endorsed`, which is `MAX(signed_self, signed_group)` as computed in `get_signed_conflicts`: [2](#0-1) 

Only if a conflict is judged "fresh" does the code ask the node whether it is provably dead (`conflict_still_blocks`) before continuing to block the signature. Once `last_endorsed` falls behind the cutoff, the conflict is dropped from that check with no node round-trip at all — the code comment even states this is deliberate ("stale conflicts cost no round-trips").

The only remaining guard for stale conflicts is the own-tenure branch: [3](#0-2) 
This branch only fires when `conflict.consensus_hash == block_info.block.header.consensus_hash` — i.e., the stale conflict is in the *same* tenure as the new proposal. It provides no protection when the stale, still-possibly-live conflict is in a **different, unrelated tenure** (a genuine sibling at the same height from a third tenure).

The earlier chainstate re-check (`check_block_against_signer_db_state`, backed by `check_latest_block_in_tenure`) is documented as covering only one tenure per block — the new proposal's own tenure, or its parent tenure for tenure-change blocks — never a third, unrelated tenure: [4](#0-3) [5](#0-4) 

So a sibling conflict at the same height, in a tenure that is neither the proposal's own nor its parent, is:
1. Not caught by `check_block_against_signer_db_state` (blind spot acknowledged in the docs).
2. Not caught by the fresh-conflict guard once its `last_endorsed` timestamp ages past `tenure_last_block_proposal_timeout` (default 30 s) — no node liveness check is performed.
3. Not caught by the own-tenure recheck (different `consensus_hash`).

The result: the signer signs the new proposal even though the earlier, conflicting, already-signed sibling block may still be entirely live and could still be adopted by the network — this is exactly the SNX bug pattern of "the wall-clock gap silently exceeds what the safety accounting assumes," except here the "erroneous output" is an extra, conflicting signature instead of an extra reward.

### Impact Explanation
This breaks the one-per-height / no-conflicting-signature invariant that the pre-commit→signature flow is explicitly built to guarantee (see `docs/signer-flows.md` sections 0 and 5: "have I already signed a rival block at this height?"). A signer producing signatures over two conflicting blocks at the same height is the "signing a conflicting block" impact category explicitly called Critical in the rules: it can contribute weight toward two different blocks reaching the 70% signature threshold, which is the core equivocation the pre-commit protocol exists to prevent.

### Likelihood Explanation
This requires no majority of signers, no other signer's key, and no auth token — it only requires ordinary network/gossip delay or a slow/malicious miner spacing two conflicting proposals by more than `tenure_last_block_proposal_timeout` (default 30 seconds, entirely miner/timing controlled) while ensuring the second proposal's tenure lineage isn't the first block's own or parent tenure. This is easily reachable by a single miner producing a sibling tenure-change/fork scenario with ordinary timing, matching the "one-slot miner (plus gossip)" threat model in scope.

### Recommendation
Do not let the "freshness" wall-clock check alone gate whether a node-liveness re-verification (`conflict_still_blocks`) is performed. Instead, always ask the node whether a stale, cross-tenure conflict is still live before allowing a new conflicting signature — mirroring how the own-tenure branch re-verifies via `get_tenure_tip` regardless of staleness. At minimum, extend the own-tenure re-check to cover all distinct tenures present among `conflicts`, not just the tenure matching the new proposal's `consensus_hash`, so that stale sibling conflicts in any third tenure are still confirmed dead (or alive) by the node before the signer commits its signature.

### Proof of Concept
1. Signer set locally accepts/signs block `A` at height `H` in tenure `T1` (`signed_self`/`signed_group` recorded, `last_endorsed = t0`).
2. Miner (or natural network delay) waits more than `tenure_last_block_proposal_timeout` (default 30s) before proposing.
3. Miner proposes block `B` at height `H` in tenure `T3`, where `T3`'s parent tenure is neither `T1` nor tied to `T1` (e.g., a different tenure lineage/fork), so `check_block_against_signer_db_state` for `B` never inspects `T1`.
4. `handle_block_pre_commit` for `B` calls `get_signed_conflicts(H, B_hash)`, which returns `A` as a conflict, but `A.last_endorsed = t0 < freshness_cutoff` (elapsed > 30s), so the `find` predicate at signer.rs:1403-1411 skips the node liveness check entirely for `A`.
5. The own-tenure branch at signer.rs:1432-1457 does not fire because `A.consensus_hash (T1) != B.consensus_hash (T3)`.
6. The signer proceeds to sign `B` (`mark_locally_accepted`) even though `A` may still be canonical/live on the node — producing conflicting signatures over `A` and `B` at the same height `H`.

Note: I was unable to fully trace every downstream consumer of these conflicting signatures (e.g., whether `stacks-node`'s aggregation in `signer_coordinator.rs`/`stackerdb_listener.rs` would ever combine votes across two different block hashes at the same height into a valid quorum for both); the demonstrated root-cause defect is confined to the signer's own conflict-detection gap in `stacks-signer/src/v0/signer.rs`, which is sufficient to establish the safety violation of the signer emitting a conflicting signature it should have refused.

    pub fn get_signed_conflicts(
        &self,
        height: u64,
        excluded_signer_signature_hash: &Sha512Trunc256Sum,
    ) -> Result<Vec<SignedConflictInfo>, DBError> {
        let query = "SELECT b.consensus_hash, b.signer_signature_hash, b.stacks_height, b.state,
                MAX(COALESCE(b.signed_self, 0), COALESCE(b.signed_group, 0)) AS last_endorsed,
                st.superseded_by_consensus_hash, st.superseded_by_burn_block_hash
            FROM blocks b
            LEFT JOIN superseded_tenures st ON st.consensus_hash = b.consensus_hash
            WHERE (b.signed_self IS NOT NULL OR b.signed_group IS NOT NULL)
                AND b.stacks_height >= ?1
                AND b.signer_signature_hash != ?2
            ORDER BY b.stacks_height DESC";
        let args = params![
            u64_to_sql(height)?,
            excluded_signer_signature_hash.to_string(),
        ];
        query_rows(&self.db, query, args)
    }
