### Title
Stale confirmations from removed multisig keys are not purged, allowing requests to execute below the live confirmation threshold - (File: multisig/src/lib.rs)

### Summary
`MultiSigContract::confirm()` authorizes execution of a pending request once the number of recorded confirmations reaches `num_confirmations`. That count is taken from the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map. When a key is removed via the `DeleteKey` action, `execute_request()` only deletes requests *authored* by that key (`r.signer_pk == pk`) and removes the key from `num_requests_pk`; it never scans `self.confirmations` to strip that public key out of the confirmation sets of *other*, still-pending requests that it had previously confirmed. As a result, a confirmation recorded by a key that has since been deleted from the account continues to count toward the threshold, letting a request execute with fewer currently-valid signers than `num_confirmations` requires. ### Finding Description
The multisig contract's custody/authorization binding is: *number of confirmations from currently-authorized keys ≥ `num_confirmations`*. The contract instead tracks: *number of `PublicKey` entries ever inserted into the confirmation `HashSet` for a request ≥ `num_confirmations`*, with no invalidation when a key's authorization is revoked.

`confirm()` simply checks set membership/size and executes once the threshold is met: [2](#0-1) 

The `DeleteKey` action removes the on-chain access key and cleans up requests *the removed key itself created*, plus its `num_requests_pk` counter, but does nothing to `self.confirmations` for requests created by other keys that the removed key had confirmed: [1](#0-0) 

Because `self.confirmations` entries are never pruned for the deleted key, a confirmation made by that key before its removal remains permanently valid and countable, even though the key can no longer sign anything on the account (its on-chain access key is gone). This breaks the intended equality: `live_signer_confirmations == recorded_confirmations`. After the removal, `recorded_confirmations` can still include the stale entry, so a subsequent legitimate confirmation from a remaining member can push the count to `num_confirmations` while the set of *currently authorized* confirmers is one short of that threshold.

### Impact Explanation
This is a Critical-impact finding: it allows a multisig request (e.g., a `Transfer` draining the account's NEAR, or an `AddKey` granting a full-access key to an attacker) to be executed with fewer live, currently-authorized confirmations than the configured threshold — i.e., a multisig request executed below threshold. This directly matches the "confirmations counted versus live members" custody binding called out as in-scope, and the outcome (funds moved / access granted below the required k-of-n threshold) is explicitly listed as a Critical impact.

### Likelihood Explanation
The scenario requires only routine, expected multisig operations — no attacker privilege escalation beyond having legitimately held a key at some point:
1. Key `K1` (one of the `n` members) confirms a pending request `R` that is not yet fully confirmed.
2. `K1`'s key is later revoked via a normal `DeleteKey` request (e.g., routine key rotation, suspected compromise, or offboarding a member) confirmed by the remaining members.
3. Because `execute_request`'s `DeleteKey` branch never touches `self.confirmations`, `K1`'s confirmation on `R` survives.
4. A remaining member confirms `R`; the stale `K1` entry plus the new confirmation reach `num_confirmations`, and `R` executes even though `K1` is no longer an authorized signer.

This does not depend on any misconfiguration or bypassing initialization — it is a direct consequence of the shipped `DeleteKey` handling, making it readily reachable in normal contract usage/lifecycle (key rotation is a routine multisig operation).

### Recommendation
When executing a `DeleteKey` action, iterate over all entries in `self.confirmations` (not just `self.requests` filtered by `signer_pk`) and remove the deleted public key from every confirmation `HashSet`. Alternatively, validate at `confirm()`-time (or at execution time) that every public key present in a request's confirmation set still corresponds to a live access key on the account before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(3)` with three access keys `A`, `B`, `C` (3-of-3).
2. Using key `A`, call `add_request_and_confirm` for `MultiSigRequest { receiver_id: self, actions: [Transfer { amount }] }` → request `R` now has 1 confirmation (`A`).
3. Using keys `B` and `C` (2 confirmations reaching the current 3-of-3... to demonstrate the bug precisely, first reduce members): submit and confirm a `DeleteKey { public_key: A }` request with `B` and `C` (2-of-3 not yet met unless threshold changes accordingly, but assume `A` is being revoked because it's suspected compromised and the remaining `B`,`C` execute the deletion using a separately already-confirmed 3-of-3 flow, or the org lowers `num_confirmations` to 2 via `SetNumConfirmations` beforehand). `A`'s on-chain access key is deleted; `execute_request`'s `DeleteKey` branch removes only requests where `signer_pk == A` — request `R` (authored/confirmed, but not created, in this variant, by `A`) is untouched, retaining `A` in `confirmations[R]`.
4. With `num_confirmations` now effectively 2 (or originally 2-of-3 with `A` being one of the two initial confirmers on an unrelated pre-existing request), key `B` calls `confirm(R)`. `confirmations[R].len() + 1 >= num_confirmations` evaluates true using the stale `A` entry, and `execute_request(R)` fires the `Transfer`, moving funds despite only one currently-authorized key (`B`) having actually approved it.
5. Inspect state before/after: `get_confirmations(R)` still lists the now-deleted key `A` even after step 3, proving the stale entry persists and is countable — confirming the root cause at `multisig/src/lib.rs` lines 198-216 and the execution path at lines 248-266. [1](#0-0) [2](#0-1)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
