### Title
Instant-withdraw claims are not bound to funded receipts, letting an attacker steal reserves funded for normal withdraw requests - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays a user their full `instantWithdrawsRequests` balance out of the strategy's underlying balance without checking that the borrower's funding for that request was actually collected via `collectInstantWithdrawFunds`, and without decrementing `pendingInstantWithdraws`. The payout goes through `_transferFundedClaim`, which only guards the `defaultRecoveryReserve` — so an instant claimant can consume underlyings that were pulled into the strategy by `collectWithdrawFunds` to back *other* users' normal withdraw receipts. One funded reserve backs two claimable entitlements: the analog of the race/object-corruption class in CVE-2026-2319, where a state mutation (funding) is consumed by a claim it was never meant to satisfy.

### Finding Description
- `requestInstantWithdraw` burns the CDO's strategy tokens, mints a receipt to the user, and bumps `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch` and `pendingInstantWithdraws` (lines 356–375). No funding check happens there.
- Funding is delivered lazily: `collectInstantWithdrawFunds(_amount)` only decrements `pendingInstantWithdraws` and pulls tokens from the CDO (lines 398–403).
- `claimInstantWithdrawRequest` then burns the receipt and pays `instantWithdrawsRequests[_user]` via `_transferFundedClaim`, which requires only that `balance - defaultRecoveryReserve >= amount` (lines 380–393, 897–907). Crucially it does **not** require the user's request to have been funded, and it does **not** reduce `pendingInstantWithdraws`.
- Normal withdraw funding is also pooled in the same contract balance: `collectWithdrawFunds` transfers `pendingWithdraws` basis into the strategy (lines 411–430). Those tokens are earmarked for `withdrawsRequests` claimants but are indistinguishable to `_transferFundedClaim`.

Attack sequence (running epoch, instant mode enabled):
1. Other users' normal withdraw requests have been funded — the strategy holds `pendingWithdraws`-basis underlyings after a `stopEpoch`/`collectWithdrawFunds` call.
2. Attacker (KYC'd lender) calls `requestInstantWithdraw` on the CDO for amount `X` up to the strategy's excess balance.
3. Before the CDO/manager calls `collectInstantWithdrawFunds(X)` (i.e., before the borrower's funds arrive), the attacker calls `claimInstantWithdrawRequest`. `_transferFundedClaim` sees balance ≥ `X` and pays the attacker out of the reserve funded for normal receipts.
4. When `collectInstantWithdrawFunds` later pulls `X` more, the strategy is double-funded but `pendingInstantWithdraws` was only decremented once; the funded normal claimants' `withdrawsRequests` can no longer be fully paid, or the double count permanently freezes residual claims.

The broken invariant is "one funded unit, one payout": receipt issuance, funding, and payout are decoupled, and the claim path trusts `instantWithdrawsRequests` instead of the funded accounting in `pendingInstantWithdraws`. Existing guards don't stop it: `_onlyIdleCDO` is satisfied since the CDO forwards user calls, `_transferFundedClaim`'s reserve guard only protects `defaultRecoveryReserve` (0 pre-default), and there is no epoch/maturity check on instant claims comparable to `epochNumber <= lastWithdrawRequest` in `_claimFundedWithdrawRequest`.

### Impact Explanation
Direct theft / permanent freezing of other users' funded withdraw reserves, up to the attacker's instant-request size (bounded by their deposit and the strategy's funded balance). Funded normal withdraw receipts become unclaimable (revert on insufficient balance or `NotAllowed` from the reserve check), i.e., a quantified loss equal to the drained amount and a permanent freeze of the residual entitlement. A second-order effect: `pendingInstantWithdraws` is never decremented on claim, so a `collectInstantWithdrawFunds` call made later for the already-paid request pulls fresh borrower funds that no receipt maps to — recoverable only via `transferToken` (privileged).

### Likelihood Explanation
Requires instant-withdraw mode enabled and a sequencing window between the user's `requestInstantWithdraw` and the funding `collectInstantWithdrawFunds` (or simply any period where funded reserves sit in the strategy while an attacker's instant request is unfunded). Both calls are permissionless for the lender; the funding call is made by the honest CDO/manager, and the attacker sequences around it, which is in scope. Uncertainty: I could not fully verify whether `IdleCDOEpochVariant.claimInstantWithdrawRequest` enforces a funding or delay precondition on the CDO side (the grep returned matches but the surrounding logic was not readable in the available iterations). If the CDO atomically collects funds before enabling claims, exploitability hinges on claiming in a later epoch using stale `instantWithdrawsRequests` funded basis — the accounting gap remains either way because `pendingInstantWithdraws` is not consumed by the claim.

### Recommendation
Bind instant claims to actual funding: track funded vs. unfunded instant receipts per user/epoch (e.g., decrement `pendingInstantWithdraws` and a `instantWithdrawsRequestsByEpoch` entry inside `claimInstantWithdrawRequest`, or require `pendingInstantWithdraws` coverage only from *segregated* instant liquidity). Alternatively, make `requestInstantWithdraw` revert unless the CDO collects funds atomically in the same call, and reserve-tag the funded normal-withdraw balance so `_transferFundedClaim` for instant claims can only spend an instant-specific sub-reserve. Add a test asserting `pendingInstantWithdraws` consistency after a claim.

### Proof of Concept
Reproducible Foundry fork outline (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):
1. Deploy standard epoch variant; deposit as `victim` (AA) and `attacker` (AA, KYC'd).
2. `cdoEpoch.requestWithdraw` for victim; run `stopEpoch` with borrower funding so `collectWithdrawFunds` moves `pendingWithdraws` basis into `IdleCreditVault` (strategy balance now holds `B`).
3. Enable instant withdraws via `cdoEpoch.setInstantWithdrawParams(...)`.
4. Attacker calls `cdoEpoch.requestInstantWithdraw(X)` where `X <= B` — `instantWithdrawsRequests[attacker] == X`, `pendingInstantWithdraws == X`, no new funds collected.
5. Attacker calls `cdoEpoch.claimInstantWithdrawRequest()` → receives `X` underlying from the victim's funded reserve; assert `underlying.balanceOf(attacker)` increased and `pendingInstantWithdraws` still `== X`.
6. Victim calls `claimWithdrawRequest()` → `_transferFundedClaim` reverts or pays short, demonstrating theft/freeze; alternatively call `collectInstantWithdrawFunds(X)` afterward and show the strategy is now over-funded relative to remaining receipts.
