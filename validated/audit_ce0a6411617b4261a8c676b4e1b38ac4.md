### Title
Write-Only Party Member Can Steal Object Ownership via Missing TRANSFER Permission Check in `party_transfer_internal` — (`sui-execution/latest/sui-move-natives/src/transfer.rs`)

### Summary
A sender holding only `WRITE` permission on a `Owner::Party` object can call `sui::transfer::public_party_transfer` to unconditionally reassign the object's owner to themselves. The native function `party_transfer_internal` contains an explicit `// TODO check permissions for transfer` comment where the sender's TRANSFER permission should be validated but is not. No other layer in the execution pipeline enforces this invariant.

### Finding Description
The `party.move` module defines four permission bits: READ (0x01), WRITE (0x02), DELETE (0x04), and TRANSFER (0x08). The WRITE permission is documented to allow mutation but explicitly not ownership change; TRANSFER is the required bit for that. Both are stated to be enforced "at the end of transaction execution" in the Rust adapter.

The enforcement chain for `public_party_transfer` is:

1. **Move layer** (`transfer.move:91-94`): `assert!(party.is_single_owner())` — validates the *destination* party structure, not the caller's permissions.
2. **Native layer** (`party_transfer_internal`, line 230): validates that the new party has ALL permissions — again about the destination, not the caller.
3. **Line 251**: `// TODO check permissions for transfer` — the caller's TRANSFER permission check is absent.
4. **Post-execution** (`invariants.rs:624-633`): `can_use_mutably()` returns true for WRITE, so a WRITE-only sender is admitted as a mutable user with no further per-operation permission gating.

### Impact Explanation
A WRITE-only party member can transfer any `key + store` party-owned object to themselves, gaining full ownership. This is unauthorized object ownership transfer — a Critical-class state corruption impact under the active bounty scope.

### Likelihood Explanation
Any party member with WRITE permission (including default-permission holders if the party's default includes WRITE) can exploit this against any party-owned object with `store`. No special setup, leaked keys, or privileged access is required — a standard PTB suffices.

### Recommendation
In `party_transfer_internal`, before calling `object_runtime_transfer`, resolve the sender's permissions on the input object and assert that the TRANSFER bit is set. Remove the `// TODO` and implement the check analogously to how `can_use_mutably()` is used in `check_ownership_invariants`, but specifically gating on `can_internal_transfer()` or `can_public_transfer()`.

### Proof of Concept

sui::transfer::public_party_transfer(party_obj, new_party);
// Result: party_obj.owner == ConsensusAddressOwner { owner: sender_address }
// The sender now has full ownership despite holding only WRITE permission.
