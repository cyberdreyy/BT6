## Title
Coordinator's per-block rejection tally is never cleared when a signer flips from reject to accept, allowing a stale/retracted rejection to wedge the miner out of a valid block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` aggregates `total_weight_approved` and `total_weight_rejected` per block proposal from `BlockResponse` messages gossiped by signers. The bookkeeping is asymmetric: the accept path gates on `gathered_signatures`, while the reject path gates on the shared `responded_signers` set, and neither path ever removes a signer's weight from `total_weight_rejected` once counted. A signer that legitimately reconsiders — rejects a proposal and later signs the same proposal (a supported, documented flow in the v0 signer's re-evaluation logic) — ends up with its weight counted in *both* buckets permanently. The stale rejection weight can combine with other signers' rejections to cross the >30% blocking-minority threshold and cause the miner/coordinator to declare the block rejected (`NakamotoNodeError::SignersRejected`), even though the signer in question currently supports the block and enough live weight may exist to reach 70% approval.

### Finding Description
`handle_message` in `stackerdb_listener.rs` processes `BlockResponse::Accepted` and `BlockResponse::Rejected` messages for a given `block_sighash`/`BlockStatus`:

- On `Accepted`, weight is added to `total_weight_approved` only the first time this slot's signature is *not yet* in `gathered_signatures`: [1](#0-0) 
followed unconditionally by `gathered_signatures.insert(slot_id, signature)` and `responded_signers.insert(slot_id)`.

- On `Rejected`, weight is added to `total_weight_rejected` only if `responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot has responded at all, in either direction): [2](#0-1) 

Because the two paths gate on different sets (`gathered_signatures` vs. `responded_signers`) and neither decrements the other bucket, a signer that first rejects and later accepts the *same* block proposal will:
1. On reject: `responded_signers.insert(slot_id)` returns `true` → `total_weight_rejected` incremented.
2. On accept: `gathered_signatures.contains_key(&slot_id)` is still `false` (never touched by the reject path) → `total_weight_approved` is also incremented.

The signer's weight is now counted in both `total_weight_approved` and `total_weight_rejected` simultaneously, and `total_weight_rejected` is never reduced back down. This breaks the intended equality that `total_weight_rejected` reflects the currently-standing rejecting weight (aggregated-weight vs. verified-accepts).

The rejection check in the coordinator's polling loop is evaluated using this stale, monotonically-non-decreasing `total_weight_rejected`: [3](#0-2) 
so a block can be declared globally rejected due to a rejection contributed by a signer who has since retracted it by signing.

This is directly analogous to the CreditLine.liquidate report: a value (weight, analogous to the borrowed ETH) that should be reassigned/"transferred" out of the rejection pool when the signer's decision changes is instead left stuck in the stale bucket, requiring no attacker action — just an ordinary signer re-evaluation, which the v0 signer state machine explicitly supports (`should_reevaluate_reject_reason`, documented in `docs/signer-flows.md` section 3/6).

### Impact Explanation
This is a liveness wedge on the node/coordinator side: a well-supported, valid block can be reported as `SignersRejected` and abandoned by the miner even though the opposing weight that triggered the threshold includes phantom/stale rejection weight from a signer that has already signed. This matches the "wedge" impact category — an aggregated-weight tally diverging from the verified/current set of accepts and rejects, causing the coordinator to give up on a legitimate block and forcing a retry/fork of mining activity. It requires no majority collusion and no key compromise — only a single signer changing its vote, which is expected and supported signer behavior.

### Likelihood Explanation
Signers legitimately flip from reject to accept on re-proposal or re-evaluation of the same block (e.g., after a reject reason becomes stale, per `should_reevaluate_reject_reason`/`should_reevaluate_block` in `stacks-signer/src/v0/signer.rs`), and this flip is gossiped as ordinary `BlockResponse` traffic observed by any node's `StackerDBListener`. No adversarial coordination is needed; the condition can occur in normal operation whenever timing causes a signer to reject once (e.g., transient chainstate mismatch) and subsequently accept the very same block.

### Recommendation
Make the two counters consistent and reversible:
- Gate `total_weight_approved` increments on membership in `responded_signers` at the time of the *first* response for that slot, or otherwise track whether the slot has previously counted toward `total_weight_rejected`, and if so subtract that weight (or transfer it) rather than only adding to `total_weight_approved`.
- Symmetrically, ensure that once a slot's weight has been moved into `total_weight_approved`, it can never simultaneously remain counted in `total_weight_rejected`.
- Consider tracking each slot's *current* verdict (accept/reject) explicitly and recomputing `total_weight_approved`/`total_weight_rejected` as sums over current verdicts, rather than incrementally with one-way increments.

### Proof of Concept
1. Node receives `BlockResponse::Rejected` from signer S (slot `k`, weight `w`) for block `H`. `responded_signers.insert(k)` → `true`; `total_weight_rejected += w`. [4](#0-3) 
2. Signer S later re-evaluates and gossips `BlockResponse::Accepted` for the same block `H` (e.g., following the re-evaluation flow described for `should_reevaluate_reject_reason`).
3. Node processes it: `gathered_signatures.contains_key(&k)` is `false` (untouched by the reject branch) → `total_weight_approved += w`, `gathered_signatures.insert(k, sig)`, `responded_signers.insert(k)` (no-op since already present). [1](#0-0) 
4. Now S's weight `w` is counted in both `total_weight_approved` and `total_weight_rejected`. If other signers' genuine rejections plus this stale `w` push `total_weight_rejected.saturating_add(weight_threshold) > total_weight`, the coordinator's poll loop returns `Err(SignersRejected{...})`: [5](#0-4) 
even though S currently supports the block and true rejecting weight (excluding S) may not clear the blocking-minority threshold.
