This confirms the vulnerability. The pattern in this codebase is well established: both `lockup-factory` and `staking-pool-factory` attach a `.then()` callback (`on_lockup_create`, `on_staking_pool_create`) that calls `is_promise_success()` and issues `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` when the deployment promise chain fails. `multisig-factory::create` has no such `.then()` at all — the `Promise` chain (`create_account().deploy_contract(...).transfer(...).function_call(...)`) is returned directly with nothing to detect or handle failure.### Title
No refund path in `MultisigFactory::create` — failed deployment silently keeps the attacker's/payer's deposit - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` builds a promise chain (`create_account → deploy_contract → transfer → function_call`) and returns it directly with no `.then()` callback to itself, unlike `LockupFactory::create` and `StakingPoolFactory::create_staking_pool` in the same repo, which both attach an `on_..._create` callback that checks `is_promise_success()` and refunds the deposit via `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` on failure. Because `multisig-factory` has no callback and no validation of `name`, any deployment that fails (e.g. because the derived `account_id` is malformed, already exists, or is an implicit/unusable account form) permanently strands the attached NEAR deposit on the factory contract instead of refunding the payer.

### Finding Description
The invariant under test: `balance_before_create(predecessor) - attached_deposit == balance_after_failed_create(predecessor)` should hold when a call to `create` fails to produce a usable multisig account — i.e. a failed deployment must refund the payer. In `MultisigFactory::create`:

```rust
let account_id = format!("{}.{}", name, env::current_account_id());
Promise::new(account_id)
    .create_account()
    .deploy_contract(CODE.to_vec())
    .transfer(env::attached_deposit())
    .function_call(...)
``` [1](#0-0) 

there is no `is_valid_account_id` check on `name`/`account_id`, no length/character validation, and — critically — no `.then(ext_self::on_create(...))` callback at all. The function simply returns the raw `Promise` chain to the runtime.

Compare with `LockupFactory::create`, which validates and attaches `.then(ext_self::on_lockup_create(...))`, and whose callback refunds on failure: [2](#0-1) 

and `StakingPoolFactory::create_staking_pool`, which similarly validates `staking_pool_account_id` with `env::is_valid_account_id` and attaches `.then(ext_self::on_staking_pool_create(...))` which refunds on failure: [3](#0-2) 

Since `multisig-factory` has neither the validation nor the callback, an attacker calls `create(name, members, num_confirmations)` with an attached deposit and a `name` chosen so that the derived `account_id = format!("{}.{}", name, current_account_id())` is invalid or otherwise causes the `create_account`/`deploy_contract`/`function_call` chain to fail on-chain (e.g., a `name` containing characters that make the resulting subaccount ID malformed, or a name colliding with an existing account). The `Promise::new(account_id).create_account()...transfer(deposit)` action still executes as a receipt targeting that (invalid/failing) account; when the receipt fails, NEAR's runtime returns any unused gas but the transferred deposit that was part of the failed receipt's actions is not returned to the original predecessor because the multisig-factory contract never scheduled any transfer-back logic — there is no callback to detect the failure and issue a refund `Promise`. The deposit is consumed/stranded rather than automatically returned to the caller by protocol design in this codebase's pattern (as proven by the sibling factories needing an explicit refund callback to make this correct).

No existing guard (`assert_self`, `is_promise_success`, `assert_valid_request`, `is_valid_account_id`, etc.) is present anywhere in `multisig-factory/src/lib.rs` to prevent this, confirmed by the absence of any such calls in the file.

### Impact Explanation
The predecessor's attached NEAR deposit is lost with no path to recovery — the factory contract account absorbs value that does not belong to it, and the entitled payer's balance is not restored. This matches "an accounting value diverging from reality where another party settles on it" (here, the factory/network state settles on a deposit that was supposed to be returned). Every unprivileged caller of `create` who triggers a failing deployment (bad `name`, colliding account, or oversized/undergassed call) loses their deposit permanently; the flaw is repeatable across accounts and calls with no privilege required.

### Likelihood Explanation
Any unprivileged account can call `create` with an arbitrary `name`, attach any deposit, and choose a `name` that is trivially able to make the account creation/deployment fail (e.g., invalid characters in `name`, a `name` producing an account ID exceeding 64 bytes, or reusing an already-existing sub-account name to force `create_account` to fail). This requires no special preconditions beyond having some NEAR to attach, making it fully attacker-controlled and cheap to trigger repeatedly.

### Recommendation
Mirror the pattern used by `lockup-factory` and `staking-pool-factory`: validate `name`/derived `account_id` with `env::is_valid_account_id` before creating the promise, and attach a `.then(ext_self::on_create(account_id, attached_deposit, predecessor_account_id, ...))` callback that calls `assert_self()`, checks `is_promise_success()`, and on failure issues `Promise::new(predecessor_account_id).transfer(attached_deposit)` to refund the caller.

### Proof of Concept
Using `near-sdk`'s `testing_env!`/`PromiseResult::Failed` pattern (as done in `lockup-factory`'s `test_create_lockup_rollback` and `staking-pool-factory`'s `test_create_staking_pool_rollback`):
1. Set up `MultisigFactory::default()` with `predecessor_account_id = attacker`, `attached_deposit = D`.
2. Call `contract.create(name, members, num_confirmations)` — observe it returns a bare `Promise` with no subsequent callback method exposed on `MultisigFactory` (grep confirms no `on_create`/`on_multisig_create` method exists in the contract's `impl` block, unlike the sibling factories).
3. Simulate the promise chain failing (`testing_env_with_promise_results(context, PromiseResult::Failed)`), then assert that no method on `MultisigFactory` refunds `D` to `attacker` — because none exists, `assert!(contract` has no `on_create` method`)` demonstrates the missing refund path structurally; a full `near-workspaces` integration test would additionally deploy `multisig-factory`, call `create` with a deliberately malformed `name` (e.g. containing `.` or exceeding account-id length limits) to force the `create_account` receipt to fail, and confirm the attacker's balance decreases by `D` while the factory account's balance increases by `D` with no compensating transfer, in contrast to `lockup-factory`/`staking-pool-factory` where `on_lockup_create`/`on_staking_pool_create` restore the predecessor's balance under identical failure conditions.

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
