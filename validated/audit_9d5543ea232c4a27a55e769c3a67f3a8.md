near-sdk 3.1.0's `#[init]` macro does **not** by itself forbid re-initialization — it is purely a marker; the check must be added explicitly by the contract author. This is confirmed by every sibling contract in this same repo doing it manually: `WhitelistContract::new` [1](#0-0) , `MultiSigContract::new` [2](#0-1) , `StakingContract::new` [3](#0-2) , and `LockupFactory::new` [4](#0-3)  all explicitly `assert!(!env::state_exists(), ...)`. `LockupContract::new` in `lockup/src/lib.rs` has **no such assertion** anywhere in its body [5](#0-4) .

### Title
Missing `state_exists` re-initialization guard in `LockupContract::new` allows full lockup takeover - (File: lockup/src/lib.rs)

### Summary
`LockupContract::new` unconditionally overwrites the entire contract state (`owner_account_id`, `lockup_information`, `vesting_information`, `staking_information`, `foundation_account_id`) and, unlike every sibling contract in this repository, never checks `env::state_exists()` before doing so. Because `new` is a plain public method with no predecessor/owner check, any unprivileged account can call `new` a second time on an already-deployed, funded lockup account and reset it with attacker-chosen parameters, including making themselves the owner.

### Finding Description
The broken binding: `owner_account_id_after_deploy == owner_account_id_forever` is claimed to hold once a lockup account is created, but the code makes `owner_account_id_after_call(new) == whatever the caller of new supplies`, with no restriction on who may call it or how many times.

`LockupContract::new` is annotated `#[init]` [6](#0-5) , but near-sdk 3.1.0 (declared in `lockup/Cargo.toml` [7](#0-6) ) treats `#[init]` only as a marker that lets the method be called without a pre-existing `Default` state; it does not itself forbid calling the method again on state that already exists. Enforcement of "only once" is left entirely to the contract author, and every other contract in this repository (`whitelist`, `multisig`, `staking-pool`, `lockup-factory`) does add `assert!(!env::state_exists(), ...)` inside their own `new`. `LockupContract::new` omits this assert:

```
Self {
    owner_account_id,
    lockup_information,
    vesting_information,
    staking_information: None,
    staking_pool_whitelist_account_id,
    foundation_account_id,
}
``` [8](#0-7) 

`new` itself only validates account-ID validity and that a foundation account accompanies a vesting schedule [9](#0-8) ; it never checks `env::predecessor_account_id()` against the existing `owner_account_id`, and there is no `#[private]`/`assert_self()` guard. `new` is a normal `pub fn`, callable by any account via a `FunctionCall` action targeted at the lockup account — the caller needs only their own signing key, not any key on the victim account.

Exploit flow:
1. Victim's lockup account already exists (deployed by the lockup factory `lockup-factory/src/lib.rs`'s `create` [10](#0-9) ), holding real NEAR, possibly with `staking_information: None` (before `select_staking_pool` was ever called, or after the owner unstaked and withdrew but before reselecting a pool).
2. Attacker (unprivileged, not owner, not foundation) sends a plain `FunctionCall` transaction to the victim's lockup account, method `new`, with attacker-chosen args: `owner_account_id = attacker`, `vesting_schedule = None`, `foundation_account_id = None`, `transfers_information = TransfersEnabled { transfers_timestamp: 0 }`, `lockup_timestamp = None`, `release_duration = None`.
3. Because there is no re-init guard, this call succeeds and completely replaces the struct: `lockup_information.lockup_amount` is recomputed from `env::account_balance()` at that moment [11](#0-10) , `staking_information` is forced back to `None` regardless of whatever was previously staked, and the attacker is now `owner_account_id`.
4. With transfers already enabled (timestamp 0) and no lockup/vesting, the attacker (now "owner") can immediately call owner methods (e.g., transfer) and drain the account balance.

Existing guards that were checked and do not prevent this: `assert_valid_request`, `assert_self`, `is_promise_success`, `assert_one_yocto`, `assert_transfers_enabled` are all in `owner.rs`/`foundation.rs`, not in `new`; none of them gate `new`. `env::is_valid_account_id` only validates syntax, not authorization.

### Impact Explanation
NEAR held in any already-deployed lockup contract can be moved to a party never entitled to it (the attacker becomes owner and can withdraw/transfer freely), and any locked/unvested/staked amount recorded via `vesting_information`/`staking_information` is discarded from tracking. This is repeatable against every lockup account in existence system-wide (any factory-deployed lockup, at any point after deployment) as long as the attacker can front-run/observe it and issue the `new` call, satisfying the Critical category: "NEAR ... moved out of a ... lockup ... by a party not entitled to it" and "locked or unvested tokens released early."

### Likelihood Explanation
Preconditions: a deployed lockup contract account exists (all of them, since the factory's `create` deploys code then calls `new` in the same batch of actions, and nothing thereafter blocks a further `new` call). Attacker cost: one function call transaction with no deposit requirement (no `#[payable]` on `new`, and no minimum balance check against caller). Feasibility: trivial — this is a single unauthenticated RPC call reachable by anyone at any time after the target account's `new` has already run once. Repeatable across every lockup account and every epoch.

### Recommendation
Add `assert!(!env::state_exists(), "The contract has already been initialized");` at the top of `LockupContract::new` in `lockup/src/lib.rs`, mirroring the guard already present in `whitelist/src/lib.rs`, `multisig/src/lib.rs`, `staking-pool/src/lib.rs`, and `lockup-factory/src/lib.rs`.

### Proof of Concept
```rust
// lockup/src/lib.rs tests module
#[test]
#[should_panic] // after fix; currently SUCCEEDS which is the bug
fn test_reinit_overwrites_state() {
    let mut context = basic_context();
    testing_env!(context.clone());
    let mut contract = new_contract(true, None, None, false); // first `new`, owner = account_owner()

    // Assert binding before: owner_account_id == account_owner()
    assert_eq!(contract.owner_account_id, account_owner());

    // Attacker calls `new` again on the same account, with themselves as owner
    context.predecessor_account_id = non_owner();
    context.signer_account_id = non_owner();
    testing_env!(context.clone());

    contract = LockupContract::new(
        non_owner(),          // attacker sets themselves as owner
        0.into(),
        None,
        TransfersInformation::TransfersEnabled { transfers_timestamp: 0.into() },
        None,
        None,
        AccountId::from("whitelist"),
        None,
    );

    // Assert binding after: owner_account_id is now the attacker, not account_owner()
    assert_eq!(contract.owner_account_id, non_owner());
    assert_eq!(contract.staking_information, None);
}
```
Run with `cargo test -p lockup-contract test_reinit_overwrites_state`. On the current code the second `LockupContract::new` call succeeds without panicking and silently reassigns `owner_account_id` to the attacker, proving the missing re-init guard.

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
