### Title
Unbounded busy-loop on repeated `Temporary` pipeline errors in `DriverPipeline::produce_payload` can hang the fault-proof program - ([File: crates/proof/driver/src/pipeline.rs])

### Summary
`DriverPipeline::produce_payload`, the default trait method used by the ZK/fault-proof derivation driver, treats *every* `PipelineErrorKind::Temporary(_)` variant returned from a pipeline step as transient and immediately retries with `continue`, with no retry counter, no backoff, and no distinction between progress-making temporary errors (e.g. `NotEnoughData`) and errors that leave pipeline state completely unchanged (e.g. `MissingL1Data`/`Eof` when the oracle-backed L1 data source is exhausted). This mirrors the CVE-2023-52726 bug class: "infinite repetition of the processing of an error" in a step/subscribe-style function.

### Finding Description
`DriverPipeline::produce_payload` loops on `self.step(...)`: [1](#0-0) 

Any `PipelineErrorKind::Temporary(_)` — not just the progress-safe `NotEnoughData`/`ChannelReaderEmpty` cases — causes an unconditional `continue`. This method is the *default* implementation of the `DriverPipeline` trait, and `OraclePipeline` (used by the fault-proof program / ZK client) does not override it: [2](#0-1) 

It is invoked from the proof driver's block-advancing loop: [3](#0-2) [4](#0-3) 

Inside the derivation pipeline, when the L1 retrieval stage's oracle-backed `next_l1_block()` returns `None` (i.e. there is no more L1 block data available for the oracle to serve — the boot-claimed L1 head has been fully consumed), it maps to a `Temporary` error rather than a critical one: [5](#0-4) 

Because this condition does not change any pipeline state and is classified as `Temporary`, `produce_payload`'s `continue` will call `self.step(...)` again, which will hit the exact same code path and return the exact same `Temporary` error, forever — with no sleep, no backoff, and no iteration limit. This is a hot, CPU-bound busy loop that never returns to the caller.

This is materially different from how the equivalent situation is handled elsewhere in the codebase, both of which explicitly bound or redirect handling of such errors:
- The online derivation-service actor treats only `NotEnoughData` as loop-worthy and yields for every other `Temporary` variant (including `Eof`): [6](#0-5) 
- The test harness explicitly caps consecutive no-progress `Temporary` retries at 1000 and treats it as a hard pipeline error beyond that: [7](#0-6) 

`DriverPipeline::produce_payload` has neither safeguard.

### Impact Explanation
The fault-proof program is the trusted derivation/execution path used to compute an L2 output root for dispute-game resolution and to verify claims made by challengers/defenders. If the L1 data the oracle can serve (bounded by the boot claim's L1 head and preimage set) is exhausted before the pipeline reaches the claimed L2 block number in a way that repeatedly surfaces as a `Temporary` (non-progressing) error — e.g. a mismatched/adversarial claim combining an L2 block number with insufficient/incomplete L1 data — the fault-proof program's derivation loop spins indefinitely instead of returning `PipelineErrorKind::Critical`/`EndOfSource` to the caller. This halts the prover/verifier process (resource exhaustion / DoS on the node running the fault-proof program), preventing it from ever producing a provable output root for that dispute game and potentially stalling dispute resolution, which matches the "node halt" impact category.

### Likelihood Explanation
Reaching the buggy path requires the derivation pipeline to repeatedly surface a non-advancing `Temporary` error from a stage (e.g., `MissingL1Data` from `L1Retrieval::next_data` when the oracle's bounded L1 block set is exhausted) in a way that never reclassifies to `Critical`/`EndOfSource`. This can plausibly occur for a dispute-game participant who submits/derives a claim referencing an L2 block number that requires more L1 data than is boot-committed/available to the program, or via other stage-level `Temporary` errors that don't change internal state between retries. Because the exact conditions under which every stage in the pipeline maps "no more data" errors to `Critical` vs `Temporary` were not fully re-verified for every stage (only `L1Retrieval` and `BlobSource`/`BatchQueue::try_derive_empty_batch` were inspected), there is some uncertainty about how easily an attacker can force this specific non-progressing `Temporary` cycle versus the more common `Eof`→`AdvancedOrigin` progressing cycle. This should be validated with a background Devin session that can trace all `PipelineErrorKind::Temporary` producers reachable from `produce_payload` and construct a concrete oracle/L1-data scenario that triggers the spin.

### Recommendation
In `DriverPipeline::produce_payload` (crates/proof/driver/src/pipeline.rs), only `continue` on `Temporary` variants that are known to make progress (e.g., `NotEnoughData`/`ChannelReaderEmpty`, mirroring the actor's and test harness's handling), and treat non-progressing `Temporary` errors (e.g., `Eof`/`MissingL1Data` when `advance_origin` does not change state) as terminal, returning an error to the caller after a bounded number of consecutive no-progress iterations — analogous to the 1000-iteration cap in `act_l2_pipeline_until`.

### Proof of Concept
Not independently reproduced in this pass; the control-flow argument is code-based (see citations above). A concrete PoC would require constructing an oracle-backed `OraclePipeline` instance whose L1 data source is exhausted (e.g., boot info claiming an L2 block number that requires L1 blocks beyond the oracle's committed preimage set) and observing that `advance_to_target`/`produce_payload` never returns, spinning on repeated `Temporary` errors from `L1Retrieval::next_data`.
