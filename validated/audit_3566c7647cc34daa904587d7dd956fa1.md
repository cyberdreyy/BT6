### Title
Confirmations from revoked multisig keys still count toward execution threshold, allowing requests to execute below the required live-key threshold - (File: multisig/src/lib.rs)

### Summary
The multisig contract removes a public key's own pending *requests* when that key is deleted via `DeleteKey`, but it never scrubs that key's *confirmations* left on other members' still-pending requests. Because `confirm()` only counts the size of the stored `confirmations` set against `num_confirmations`, a confirmation cast by a key that has since been revoked continues to count, allowing a request to be executed with fewer currently-valid signers than the configured K-of-N threshold.

### Finding Description
`confirm()` decides whether to execute a request purely by comparing the size of the persisted `confirmations: HashSet<PublicKey>` for that `request_id` against `self.num_confirmations`: [1](#0-0) 

When a key is removed via the `DeleteKey` action, the contract deletes the access key from the account, but only purges *requests created by* that key (`r.signer_pk == pk`) and clears its `num_requests_pk` entry. It does **not** iterate over `self.confirmations` to strip that key's public key from confirmation sets of *other* pending requests it had confirmed but did not create: [2](#0-1) 

As a result, a request created by member A and confirmed by member B keeps B's public key in its `confirmations` set even after B's key is revoked via a separate, properly-executed `DeleteKey` request. Any subsequent confirmation from a live member simply adds to that stale count: [3](#0-2) 

so the request can execute (`confirmations.len() + 1 >= num_confirmations`) while the actual number of *currently authorized* signers who approved it is below `num_confirmations`. The equality the contract is supposed to preserve — `confirmations counted == confirmations by live/current members` — is broken; instead `confirmations counted >= confirmations by live members` can hold with a strict inequality.

The same pattern exists in the v2 contract's `delete_member`, which likewise only purges requests created by the removed member and never scrubs that member's confirmations from other pending requests: [4](#0-3) 

### Impact Explanation
This breaks the core K-of-N guarantee the multisig contract is supposed to provide: "a multisig request executed below threshold" is explicitly a Critical-severity outcome. A key that is revoked (e.g., a lost device, an offboarded signer, or a compromised key that prompted the `DeleteKey` action in the first place) retains permanent influence over any request it confirmed before revocation. This can let an attacker who controls a revoked key's prior confirmation, plus fewer live signers than intended, push through fund transfers, `AddKey`/`DeleteKey` actions, or contract deployments that should have required more currently-trusted approvals.

### Likelihood Explanation
This requires no privileged bypass — it is a direct consequence of the intended, documented workflow (creating a request, having it partially confirmed, then legitimately revoking one of the confirming keys via `DeleteKey`). Any multisig account that revokes a key after that key has confirmed but not fully executed some other request is affected; no malicious cooperation from a still-active member is needed beyond normal key-rotation practice.

### Recommendation
When executing `DeleteKey` (and `DeleteMember` in multisig2), iterate over all entries in `self.confirmations` and remove the deleted public key/member from every confirmation set, not just from requests that key itself created. Alternatively, re-validate at `confirm()` time that confirmations only count keys currently present as valid access keys/members on the account.

### Proof of Concept
1. Deploy the multisig with 3 keys `A`, `B`, `C` and `num_confirmations = 2`.
2. `A` calls `add_request` to create request `X` (e.g., `Transfer`). `confirmations[X] = {}`.
3. `B` calls `confirm(X)` → `confirmations[X] = {B}` (1 < 2, not executed).
4. `A` and `C` create and confirm a separate request `Y` = `DeleteKey { public_key: B }` with 2 confirmations, which executes: `B`'s access key is removed from the account, and `B`'s `num_requests_pk` entry is cleared — but `confirmations[X]` still equals `{B}` because request `X` was created by `A`, not `B` (see `execute_request`'s `DeleteKey` handling at [2](#0-1) ).
5. Later, `C` calls `confirm(X)`. `confirmations[X].len() + 1 == 2 >= num_confirmations`, so request `X` executes — even though the only currently-live signer that actually approved it after `B`'s revocation is `C`, one short of the required 2 current confirmations.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
