### Title
Timing Side-Channel in WebSocket-Proxy API Key Authentication Enables Key Enumeration - (File: crates/infra/websocket-proxy/src/auth.rs)

### Summary
The `websocket-proxy`'s API-key authentication check (`Authentication::get_application_for_key`) resolves the caller-supplied API key directly through `HashMap::get`, and the calling handlers branch on `Some`/`None` before doing any further work (issuing/incrementing per-app metrics, subscribing to the registry) [1](#0-0) [2](#0-1) . Like the Flow `PersistedUsernamePasswordProvider` advisory (hashing/comparison only performed when the account exists), the presence check here is not constant-time with respect to the submitted key and the amount of work done diverges based on whether/how far the key matches a stored entry, giving an anonymous WebSocket client a timing oracle to infer valid API keys.

### Finding Description
`Authentication::get_application_for_key` is a thin wrapper over `HashMap<String, String>::get`, keyed directly by the raw, attacker-controlled path segment `{api_key}` [1](#0-0) . This is reached unauthenticated, straight off the public HTTP/WebSocket upgrade path, for every request to `/ws/{api_key}` or `/ws/{api_key}/filter`, before any rate limiting or connection admission occurs [3](#0-2) .

Standard `HashMap`/`String` equality is not constant-time: hashing depends on key length, and once a bucket is located, `str`/`[u8]` comparison short-circuits on the first mismatched byte. When a key partially matches a real stored key (correct prefix, correct length, same hash bucket), more comparison work is performed than for a key that is wrong from the first byte or hashes to an empty bucket. This mirrors the bug class in the Flow advisory: work performed by the authentication routine leaks whether/how closely the submitted credential matches a stored one, allowing an attacker to iteratively refine guesses using response-time measurements rather than brute-forcing the full keyspace at once.

The two handler entry points, `authenticated_websocket_handler` and `authenticated_filter_websocket_handler`, both perform this lookup as their very first authentication step and immediately return `401 Unauthorized` on `None` with no constant-time padding or artificial delay [4](#0-3) .

### Impact Explanation
A successful timing-based key-recovery attack lets an anonymous network client obtain a valid application's API key without authorization. Because the proxy attributes connections/metrics per application and (per the code comments) treats registered applications as the trust boundary for accessing the flashblocks/pending-state broadcast stream, key theft is unauthorized access to a gated real-time data feed (`websocket_handler` → `state.registry.subscribe`) [5](#0-4) , and also lets the attacker exhaust or misattribute another tenant's rate-limit/connection allotment (`Metrics::connections_by_app`) [6](#0-5) . This is a Medium-severity information-disclosure / unauthorized-access issue consistent with the reported advisory's classification.

### Likelihood Explanation
Exploitation requires many timed requests per guessed byte and is sensitive to network jitter, so it is harder to exploit than a purely local timing attack, but it is fully remotely reachable by any anonymous client with no prerequisites (no signed transaction, no privileged role) since the vulnerable code sits directly on the public WebSocket upgrade path [7](#0-6) .

### Recommendation
Compare the submitted API key against all configured keys using a constant-time comparison (e.g., `subtle::ConstantTimeEq`) instead of a length/prefix-dependent `HashMap` lookup, or hash the incoming key with a fixed-time KDF/HMAC and compare digests, ensuring the same amount of work is performed regardless of match length or hash-bucket occupancy in `Authentication::get_application_for_key` [1](#0-0) .

### Proof of Concept
1. Deploy the `websocket-proxy` with authentication enabled (`authentication: Some(...)`), exposing `/ws/{api_key}` [8](#0-7) .
2. From an anonymous client, repeatedly issue upgrade requests to `/ws/<guess>` where `<guess>` varies one byte at a time, measuring response latency to `authenticated_websocket_handler`'s `401` rejection [4](#0-3) .
3. Statistically distinguish guesses whose prefix matches a real stored key (longer comparison time in the `HashMap`/`String` equality check) from those that mismatch immediately, and iterate to reconstruct a valid key byte-by-byte.

async fn authenticated_websocket_handler(
    State(state): State<ServerState>,
    ws: WebSocketUpgrade,
    ConnectInfo(addr): ConnectInfo<SocketAddr>,
    headers: HeaderMap,
    Path(api_key): Path<String>,
) -> impl IntoResponse {
    let application = state.auth.get_application_for_key(&api_key).cloned();

    application.map_or_else(
        || {
            Metrics::unauthorized_requests().increment(1);

            Response::builder()
                .status(StatusCode::UNAUTHORIZED)
                .body(Body::from(json!({"message": "Invalid API key"}).to_string()))
                .unwrap()
        },
        |app| {
            Metrics::connections_by_app(app).increment(1);
            websocket_handler(state, ws, addr, headers, FilterType::None)
        },
    )
}

    Path(api_key): Path<String>,

) -> impl IntoResponse {
    let application = state.auth.get_application_for_key(&api_key).cloned();

    application.map_or_else(

        },
    )
}
