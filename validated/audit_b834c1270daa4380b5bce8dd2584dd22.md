Confirmed: `Authentication::get_application_for_key` does a plain `HashMap::get` lookup with no rate limiting or timing-safe comparison, and the caller (`authenticated_websocket_handler`/`authenticated_filter_websocket_handler`) rejects invalid keys before the `RateLimit`/`InMemoryRateLimit` connection-limiter is ever invoked.

### Title
Unrestricted API-key guessing on websocket-proxy `/ws/{api_key}` route allows enumeration of valid API keys - ([File: crates/infra/websocket-proxy/src/server.rs])

### Summary
The `base-websocket-proxy` binary's authenticated WebSocket route accepts the API key as a URL path segment and performs a plain HashMap lookup with no throttling before the per-IP/global rate limiter is applied, letting an anonymous client brute-force valid API keys.

### Finding Description
`authenticated_websocket_handler` and `authenticated_filter_websocket_handler` extract the caller-supplied `api_key` from the path and immediately check it against the configured key map via `state.auth.get_application_for_key(&api_key)` [1](#0-0) . Only *after* a key is found valid does the code call `websocket_handler`, which is the function that actually invokes `state.rate_limiter.try_acquire(client_addr)` [2](#0-1) . This means the `InMemoryRateLimit`/`RateLimit` trait, whose only job is bounding per-IP and global connection counts, is never consulted on the invalid-key path — every rejected guess only bumps a metrics counter (`Metrics::unauthorized_requests().increment(1)`) and returns `401` immediately [3](#0-2) .

The lookup itself is a simple, non-constant-time `HashMap::get` over `key_to_application` [4](#0-3) , with no failed-attempt counter, backoff, or per-IP cap on the number of distinct keys that can be tried. Since the route is reachable by any anonymous WebSocket client hitting `/ws/{api_key}` or `/ws/{api_key}/filter`, and HTTP connection setup/teardown is comparatively cheap, an attacker can pipeline a very large number of guesses per second against a public deployment to brute-force or enumerate live API keys, directly mirroring the Richdocuments OCS token-enumeration bug class (unauthenticated, un-throttled credential-guessing endpoint) described in CVE-2021-37629.

### Impact Explanation
A successful guess grants the attacker an authenticated WebSocket session under someone else's `app` identity, letting them consume that application's flashblocks/eth data feed, exhaust the per-app connection allotment (denying legitimate use of that key), and pollute `connections_by_app` metrics attributed to the victim application. Because keys map 1:1 to paying/whitelisted applications, this is a legitimate access-control failure/theft-of-service and is rated Medium, consistent with the CVE-2021-37629 analog (CVSS 5.3).

### Likelihood Explanation
No special privileges are needed — only network access to the deployed `websocket-proxy` HTTP listener is required (`bin/websocket-proxy`) [5](#0-4) . The absence of any failed-auth throttle makes brute forcing bounded only by connection setup cost and key-space size (operator-chosen key length/entropy, not enforced by the code).

### Recommendation
Apply the existing `RateLimit`/`IpRateLimiter` (or a dedicated failed-auth limiter) to invalid-API-key attempts *before* returning the `401`, independent of the successful-connection limiter, and use a constant-time comparison (e.g. `subtle::ConstantTimeEq`) for `get_application_for_key` instead of `HashMap::get` on raw strings, to remove both the throttling gap and any timing side channel.

### Proof of Concept
1. Deploy `websocket-proxy` with `--api-keys app1:secretkey1`.
2. From an unauthenticated client, issue a rapid sequence of WebSocket upgrade requests to `GET /ws/<guess>` for many candidate `<guess>` values.
3. Observe that each invalid guess returns `401` immediately with no `429`/backoff, since `state.rate_limiter.try_acquire` is only invoked once a key matches [6](#0-5) ; repeating this at high volume against a real deployment allows exhaustive/brute-force discovery of `secretkey1`.

async fn authenticated_websocket_handler(
    State(state): State<ServerState>,
    ws: WebSocketUpgrade,
    ConnectInfo(addr): ConnectInfo<SocketAddr>,
    headers: HeaderMap,
    Path(api_key): Path<String>,
) -> impl IntoResponse {
    let application = state.auth.get_application_for_key(&api_key).cloned();

    application.map_or_else(
        || {
            Metrics::unauthorized_requests().increment(1);

            Response::builder()
                .status(StatusCode::UNAUTHORIZED)
                .body(Body::from(json!({"message": "Invalid API key"}).to_string()))
                .unwrap()
        },
        |app| {
            Metrics::connections_by_app(app).increment(1);
            websocket_handler(state, ws, addr, headers, FilterType::None)
        },
    )

    addr: SocketAddr,
    headers: HeaderMap,
    filter: FilterType,
) -> Response {
    let connect_addr = addr.ip();
    let client_addr = state.trusted_proxy_config.client_ip(connect_addr, &headers);

    let ticket = match state.rate_limiter.try_acquire(client_addr) {

        Err(RateLimitError::Limit { reason, limit_type }) => {
            match limit_type {

                        client_ip = client_addr.to_string(),
                        reason = reason
