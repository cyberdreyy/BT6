### Title
Unauthenticated `public_key_get` requests bypass rate limiting and can trigger unbounded fan-out to all Vault DON nodes on cache miss - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
`HandleJSONRPCUserMessage` explicitly skips `requestProcessor.ProcessRequest` authorization for `vaulttypes.MethodPublicKeyGet`, and when `h.cachedPublicKeyGetResponse` is empty/stale, every such request independently calls `h.fanOutToVaultNodes`, which sends a message to every node in `h.donConfig.Members` via `h.don.SendToNode`. There is no per-sender or global rate limit gating this specific unauthenticated code path before the cache is warm.

### Finding Description
In `core/services/gateway/handlers/vault/handler.go`, `HandleJSONRPCUserMessage` (lines 413-429) intentionally exempts `MethodPublicKeyGet` from `requestProcessor.ProcessRequest`. When `h.getCachedPublicKey()` returns `nil` (cache empty, e.g., right after startup, or if `tryCachePublicKeyResponse` never succeeds), each request calls `h.newActiveRequest(req, callback)` and `h.handlePublicKeyGet(ctx, ar)`, which in turn calls `h.fanOutToVaultNodes(ctx, l, ar)` (line 697). `fanOutToVaultNodes` (lines 726-742) loops over `h.donConfig.Members` and calls `h.don.SendToNode` for every DON node, once per incoming request.

The only per-request gating mechanisms present are:
- `newActiveRequest`'s dedupe map keyed by `req.ID` (line 469), which only rejects requests reusing the exact same ID — trivially bypassed by using distinct IDs.
- `nodeRateLimiter` (`h.nodeRateLimiter.Allow(nodeAddr)`), which is applied only in `HandleNodeMessage` for inbound node *responses* (line 493), not for outbound fan-out triggered from the public path.

At the transport layer (`core/services/gateway/network/httpserver.go`), the only protection is `MaxRequestBytesLimiter` for payload size; there is no per-IP/per-sender rate limiter in `handleRequest` or in `gateway.go`'s `ProcessRequest`. `donConnectionManager.SendToNode` (`core/services/gateway/connectionmanager.go`) performs an unthrottled websocket write to the target node for every call. Consequently, an attacker who floods `public_key_get` requests with distinct IDs concurrently, before/while the cache is unwarmed, can cause the gateway to fan out one message per node per request with no bound tied to attacker identity.

### Impact Explanation
This matches a DoS/resource-exhaustion class impact against the Vault DON: an unauthenticated actor can amplify traffic toward all DON member nodes proportional to the number of concurrent/distinct requests they send, with no per-sender quota. Since the cache TTL is only refreshed periodically (`tickerVaultPublicKeyRefresh` every minute in `Start`, comment claims aggressive caching but relies on a background successful `fetchVaultPublicKey`), any period where the cache is unset/stale (startup, node failures preventing `tryCachePublicKeyResponse` from succeeding, or intentionally exhausting it) widens the exploitable window. This does not by itself compromise keys or funds — the public key is intended to be public — but it can degrade DON node availability/latency for legitimate vault operations (secrets create/update/list), which is a service-availability impact rather than a confidentiality/integrity bypass.

### Likelihood Explanation
No credentials are required (`public_key_get` is explicitly unauthenticated by design). The attack only requires the cache to be empty or not yet populated — a state that naturally occurs at gateway startup and could persist if `fetchVaultPublicKey`/`tryCachePublicKeyResponse` fails to complete (e.g., nodes slow/unavailable, response fails to decode). The request is trivial to construct and repeat concurrently with distinct JSON-RPC IDs, defeating the only existing dedupe check. This is realistically exploitable during any cache-cold window, though its severity is bounded by cache lifetime and does not persist once the cache is successfully populated (which occurs on the first successful round trip).

### Recommendation
- Add a lightweight per-sender/IP or global rate limiter specifically guarding the cache-miss branch of `MethodPublicKeyGet` in `handler.go` (e.g., reuse `limits.GateLimiter`/`ratelimit.RateLimiter` similar to `nodeRateLimiter`/`writeMethodsEnabled`) before calling `fanOutToVaultNodes`.
- Coalesce concurrent cache-miss requests into a single in-flight fan-out (singleflight pattern) so that only one fan-out request is issued to nodes while multiple callers await the same in-flight lookup.
- Consider pre-warming the cache synchronously on `Start()` (blocking until first successful fetch or a short timeout) rather than relying purely on the 1-minute ticker, to shrink the cache-empty window.

### Proof of Concept
Go handler-level test plan (extending `core/services/gateway/handlers/vault/handler_test.go`):
1. Construct `handler` via `newHandlerWithAuthorizer` with an empty `cachedPublicKeyGetResponse`/`cachedPublicKeyObject` (default zero state) and a `donConfig.Members` with N nodes, using a mock `DON` (`mocks.NewDON(t)`).
2. Set `don.On("SendToNode", mock.Anything, mock.Anything, mock.Anything).Return(nil)` and use an atomic counter in the `Run` callback to track invocation count.
3. Launch M goroutines, each calling `h.HandleJSONRPCUserMessage(ctx, jsonrpc.Request[json.RawMessage]{ID: uuid.New().String(), Method: vaulttypes.MethodPublicKeyGet}, common.NewCallback())` concurrently, without ever populating the cache (skip calling `tryCachePublicKeyResponse`).
4. Assert `SendToNode` call count == M * N (linear in unauthenticated request count with no caps), and confirm no rate-limit error/rejection occurs for any of the M callers.
5. Optionally repeat with `nodeRateLimiter`/no analogous outbound limiter configured to show absence of protection on the outbound fan-out path, distinguishing it from `HandleNodeMessage`'s inbound `nodeRateLimiter.Allow` check which does not apply here.
