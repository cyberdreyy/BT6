### Title
Unbounded zip entry decompression in `extractZipFileEntry` enables disk-exhaustion via cache/artifact zip bomb - (File: `helpers/archives/zip_extract.go`)

### Summary
`extractZipFileEntry` in `helpers/archives/zip_extract.go` copies a zip entry's decompressed stream to disk via `io.Copy(out, in)` with no size ceiling and no cross-check against the entry's declared `UncompressedSize64`. A pipeline author who controls the cache/artifact zip content pushed through the normal cache-download path (`commands/helpers/cache_extractor.go` -> `archive.NewExtractor` -> `ziplegacy.extractor.Extract` -> `archives.ExtractZipArchive`) can supply a highly compressed entry that expands to an arbitrarily large size on extraction.

### Finding Description
`extractZipFileEntry` opens the per-entry reader (`file.Open()`, which is a `flate.Reader` wrapping the compressed bytes) and streams it directly to the destination file with `io.Copy(out, in)`: [1](#0-0) 
There is no check of `file.UncompressedSize64`, no `io.LimitReader`, and no running-total budget across all entries in `ExtractZipArchive`: [2](#0-1) 
The decompression stream returned by `zip.File.Open()` will simply keep producing bytes according to the actual DEFLATE-encoded payload, independent of what the entry header claims — a classic "zip bomb" pattern (e.g., a KB-scale zip file expanding to GB/TB of output). Since a job controls the cache key/paths and the resulting cache archive content that is later uploaded and re-downloaded (or shared as an artifact), this file is fully attacker-influenced. The download path in `cache_extractor.go` only bounds the network transfer size (via HTTP `Content-Length`/meter), not the decompressed output size, and then calls `extractor.Extract(context.Background())` which reaches `ExtractZipArchive` with no additional guard: [3](#0-2) [4](#0-3) 

### Impact Explanation
Extraction writes unbounded decompressed bytes into the job's working directory tree (`file.Name`), which can exhaust the host filesystem hosting the job workspace. On shared-host executors (shell, or docker executors where the runner's cache/build volumes reside on the same host disk as other concurrently-running jobs), filling the disk causes write failures / OOM-adjacent disk-pressure for other jobs sharing that filesystem — a denial-of-service impact scoped to disk exhaustion, not code execution or cross-tenant data read. The impact is concrete: no size ceiling exists anywhere in this code path to stop it.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged pipeline author's control: they only need to produce a cache/artifact zip with a highly-compressed large payload (trivial with standard tools, e.g. a file of repeated bytes compresses at ratios of 1000:1+) and have Runner extract it via the normal `cache-extractor` flow. This is deterministic and repeatable on every job run using that cache.

### Recommendation
Enforce a decompression size ceiling in `extractZipFileEntry` (and in the archive-wide extraction loop): wrap `in` with `io.LimitReader(in, maxAllowed+1)` before `io.Copy`, and fail extraction if the copied byte count reaches the limit (indicating truncated legitimate content or a bomb). Additionally validate/accumulate `file.UncompressedSize64` across all `archive.File` entries against a configurable total budget before starting extraction, and compare actual bytes written against the declared `UncompressedSize64` to detect mismatches.

### Proof of Concept
Go unit test in `helpers/archives/zip_extract_test.go`:
1. Build an in-memory `zip.Writer` with one entry whose header declares a tiny `UncompressedSize64` (or omit it, since it's computed on Close) but whose backing writer emits a highly compressible large payload (e.g., 500MB of zeros) written through the `flate` writer so the compressed size on disk stays small (e.g., <1MB).
2. Call `archives.ExtractZipArchive(zr)` against a `t.TempDir()`.
3. Assert that either extraction returns an error before completing (expected fix behavior) or, with current code, assert the extracted file size (`os.Stat(path).Size()`) equals the full uncompressed payload size, demonstrating no size ceiling is enforced — proving the bug exists prior to a fix.

func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}
