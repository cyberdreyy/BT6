### Title
Post-finalization instant withdraw requests are booked into the defaulted epoch and drain `defaultRecoveryReserve` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a use-after-free: an entry deleted synchronously while a deferred/cursor-based walk still references it; the fix defers teardown so the stale cursor never dereferences freed state. The credit-vault analog is in `IdleCreditVault`: a "closed" epoch bucket (`instantWithdrawsRequestsByEpoch[epochNumber]` / `instantWithdrawClaimsByEpoch[epochNumber]`) is still written to after default finalization because `epochNumber` never advances post-default, so the deferred defaulted-claim path (`_claimDefaultedInstantWithdrawRequest`) consumes receipts that were created *after* the recovery snapshot, paying them out of the isolated `defaultRecoveryReserve` that belongs to pre-default claimants.

### Finding Description
`requestInstantWithdraw` (lines 356-375) has no `defaultRecoveryFinalized` branch, unlike `requestWithdraw` which routes post-default requests into `postDefaultRequests` (lines 247-257). It records the new receipt under `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and increments `instantWithdrawClaimsByEpoch[epochNumber]` (lines 371-372). After `finalizeDefault`, `epochNumber` is frozen — `defaultRecoveryEpoch == epochNumber` is set at line 693 and no further `stopEpoch`/`deposit` bump occurs on a defaulted pool.

In `claimInstantWithdrawRequest` (lines 380-393), when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (line 844) — which now also contains the post-finalization request — and pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` via `_transferDefaultRecovery`, decrementing `defaultRecoveryReserve` (line 915). There is no per-epoch timestamp or request-generation check distinguishing pre-default receipts from post-default ones; the recovery bucket is iterated by a stale epoch cursor exactly like the invalidated `list_for_each_entry_safe` cursor in the kernel patch.

### Impact Explanation
Broken invariant: isolation of the default recovery reserve ("one receipt one payout" against a fixed recovery pie). The reserve was sized at finalization as `reserveAmount = basis * recoveryPrice` for the claim basis that existed at that block (lines 686-688). Every post-finalization instant request creates claim basis that was never in `totalBasis`, so its payout `X * defaultRecoveryPrice` is taken from honest defaulted claimants' share. Once enough post-default claims execute, `defaultRecoveryReserve -= _amount` underflows (line 915) or the reserve guard in `_transferFundedClaim` (line 904) reverts, permanently freezing the remaining recovery owed to legitimate defaulted-epoch receipt holders. The attacker also gains immediate liquidity (no epoch wait is enforced anywhere in `claimInstantWithdrawRequest`) on tranche tokens that would otherwise be subject to the normal post-default request path.

### Likelihood Explanation
Requires `defaultInstantWithdrawsFinalized == true`, i.e. `pendingInstantWithdraws != 0` at finalization (line 696) — reachable whenever instant withdraws were only partially funded at the default epoch boundary. The attacker needs tranche tokens (any KYC-passing holder, including a post-default buyer of active tranches) to call `requestInstantWithdraw` via the CDO, then `claimInstantWithdrawRequest`. Attacker cost is tokens worth roughly `X * recoveryPrice`; the theft is the pro-rata share of honest claimants' recovery. One residual uncertainty: `IdleCDOEpochVariant.requestInstantWithdraw` may impose a caller-side delay/epoch gate (`instantWithdrawDelay`) that could rate-limit but does not eliminate the misclassification, since the vault-side bucket key is the frozen `epochNumber` regardless of when the request arrives.

### Recommendation
Mirror `requestWithdraw`'s post-default handling: in `requestInstantWithdraw`, when `defaultRecoveryFinalized`, either revert or record the request under a dedicated post-default instant bucket (or `postDefaultRequests`-style slot) keyed separately from `instantWithdrawsRequestsByEpoch[defaultEpoch]`. Alternatively key instant claims by a monotonically increasing request index or record `block.timestamp`/finalization flag per receipt so `_claimDefaultedInstantWithdrawRequest` only pays receipts created before `defaultRecoveryEpoch` was sealed — the same "don't let new entries reach the deferred teardown path" fix as `l2cap_chan_timeout`.

### Proof of Concept
Foundry fork PoC (against `IdleCreditVault.t.sol` harness conventions):

```solidity
function testPostDefaultInstantRequestDrainsRecovery() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // Victim deposits and files an instant withdraw during the default epoch.
    address victim = makeAddr("victim");
    _depositWithUser(victim, amount, true);
    vm.prank(victim);
    cdoEpoch.requestInstantWithdraw(0, address(AAtranche)); // instant receipt, epoch N

    _startEpochAndCheckPrices(0);
    // leave pendingInstantWithdraws != 0 at stop (partial funding)
    _stopEpochAndCheckPrices(0, initialProvidedApr, 0);
    _checkDefault();

    uint256 recovered = /* partial recovery, e.g. 70% of basis */;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();
    // defaultRecoveryFinalized = true, defaultInstantWithdrawsFinalized = true,
    // epochNumber == defaultRecoveryEpoch (frozen)

    // Attacker (post-default tranche holder) files a NEW instant request.
    // requestInstantWithdraw has no defaultRecoveryFinalized branch:
    // it writes into instantWithdrawsRequestsByEpoch[attacker][defaultEpoch].
    address attacker = makeAddr("attacker");
    _depositWithUser(attacker, amount, true); // or buys tranches post-default
    uint256 reservePre = IdleCreditVault(address(strategy)).defaultRecoveryReserve();
    vm.startPrank(attacker);
    cdoEpoch.requestInstantWithdraw(0, address(AAtranche));
    cdoEpoch.claimInstantWithdrawRequest(); // paid from recovery reserve at defaultRecoveryPrice
    vm.stopPrank();

    assertLt(
        IdleCreditVault(address(strategy)).defaultRecoveryReserve(),
        reservePre,
        'post-default instant request consumed default recovery reserve'
    );

    // Victim's legitimate defaulted claim now reverts or is underpaid.
    vm.prank(victim);
    vm.expectRevert(); // reserve underflow / NotAllowed guard
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Note: exact helper names (`_depositWithUser`, `_stopEpochAndCheckPrices`, `requestInstantWithdraw` signature on the CDO) follow the existing harness in `test/foundry/IdleCreditVault.t.sol`; the CDO-side instant request entrypoint and any `instantWithdrawDelay` gating in `IdleCDOEpochVariant.sol` should be confirmed when writing the runnable PoC, since the delay may only throttle — not prevent — the reserve drain.
