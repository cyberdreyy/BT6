## Finding

The staking_contract commission accounting in [1](#0-0)  computes commission using floored integer division on the *incremental* rewards since the last commission event, and this computation is triggered by `request_commission`, which any of staker/operator/beneficiary can call at will [2](#0-1) . Because commission is `floor(accumulated_rewards * commission_percentage / 100)` computed against `staking_contract.principal` (which is reset to `total_active_stake - commission_amount` every time) [3](#0-2) , splitting reward accrual into many small increments (via repeated calls once per epoch) systematically floors commission toward zero on each call, letting the staker retain reward dust that should have accrued to the operator as commission — this differs from computing commission once on the cumulative reward total.

### Title
Staker can grief operator commission via repeated small `request_commission`/`unlock_stake` calls exploiting floor rounding - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move)

### Summary
`get_staking_contract_amounts_internal` computes `commission_amount = accumulated_rewards * commission_percentage / 100` using integer (floor) division [4](#0-3) . This function is invoked by `request_commission_internal`, itself reachable via the public entry `request_commission`, which is permissioned to staker, operator, or beneficiary [5](#0-4) . Each call resets `staking_contract.principal` to the current total active stake minus the (floored) commission just charged [6](#0-5) , so all future commission is computed only on rewards accrued *after* this reset point.

### Finding Description
Because `commission_amount` is floored on each call rather than accumulated with fractional carry, calling `request_commission` (or `unlock_stake`, which internally forces `request_commission_internal` first [7](#0-6) ) once per epoch on small per-epoch reward increments causes `accumulated_rewards * commission_percentage / 100` to floor to 0 or near-0 far more often than if the same total rewards had accrued over a longer interval before a single commission computation. Since `principal` is advanced to the full `total_active_stake` after each call regardless of whether commission rounded to 0, the staker permanently retains the rounding remainder that "should" have been part of the operator's commission base under a coarser accrual schedule — this is a rounding/accounting drift the staker (an unprivileged, non-operator party with respect to the operator's commission rights) can unilaterally trigger and amplify through timing/call frequency, analogous to the Balancer `_calcInGivenOut` dust-accumulation bug where repeatedly interacting through a rounding boundary siphons value from the counterparty.

### Impact Explanation
Each triggered epoch loses at most `floor` remainder (up to `commission_percentage/100` fraction of one epoch's rewards) to the operator, and the staker can force this every epoch indefinitely by calling `request_commission` themselves (no cost beyond gas), which qualifies under "Operator commission ... share-accounting corruption that credits the wrong account or traps value." The per-call loss is small (sub-unit dust), matching Trail-of-Bits' own classification of the analogous Balancer issue as medium severity due to the small size of extractable value per operation, though it compounds over the life of a staking_contract.

### Likelihood Explanation
The precondition is only that the staker calls a permissionless, staker-callable public entry function (`request_commission`) frequently, which requires no special privilege beyond being a party to the staking_contract — a scenario a staker already legitimately controls and has direct financial incentive to exploit repeatedly against its own operator.

### Recommendation
Do not floor commission independently at each call; instead track a running fractional remainder (or round commission the same way `pool_u64` does with `MIN_COINS_ON_SHARES_POOL`-style dust protections) so that commission computed piecewise over many small calls sums to the same value as commission computed once over the cumulative rewards. Alternatively, throttle/rate-limit commission-triggering entry points or accumulate a persisted remainder field across calls so rounding dust is never structurally lost to one side.

### Proof of Concept
1. Staker and operator set up a staking_contract with e.g. 10% commission.
2. Instead of allowing rewards to accrue over many epochs before calling `request_commission` once, the staker calls `request_commission` (or performs a tiny `unlock_stake`) every single epoch.
3. If each epoch's incremental `accumulated_rewards` is small enough that `accumulated_rewards * 10 / 100` floors to 0 (e.g., reward increment of 9 units per epoch → `9*10/100 = 0`), the operator receives zero commission for that epoch even though non-zero rewards accrued.
4. Repeating this every epoch versus letting rewards compound before a single `request_commission` call demonstrably yields the operator strictly less cumulative commission over the same total reward amount — the existing test at [8](#0-7)  already documents "some small rounding error" being absorbed on the operator/staker split, showing the mechanism is real; a malicious staker can deliberately maximize call frequency to compound this loss against the operator.

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

    /// Calculate accumulated rewards and commissions since last update.
    fun get_staking_contract_amounts_internal(
        staking_contract: &StakingContract
    ): (u64, u64, u64) {
        // Pending_inactive is not included in the calculation because pending_inactive can only come from:
        // 1. Outgoing commissions. This means commission has already been extracted.
        // 2. Stake withdrawals from stakers. This also means commission has already been extracted as
        // request_commission_internal is called in unlock_stake
        let (active, _, pending_active, _) =
            stake::get_stake(staking_contract.pool_address);
        let total_active_stake = active + pending_active;
        let accumulated_rewards = total_active_stake - staking_contract.principal;
        let commission_amount =
            accumulated_rewards * staking_contract.commission_percentage / 100;

        (total_active_stake, accumulated_rewards, commission_amount)
    }
