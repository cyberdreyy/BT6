### Title
APR0 withdraw receipts brick `stopEpoch` after an APR update for the upcoming epoch, forcing a default or freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Ethash bug was a stale-data-for-the-upcoming-epoch flaw: the DAG was generated with parameters of the wrong epoch, so work computed for the *next* epoch was invalid even though everything looked correct in the current one. The analog in idle-tranches is the APR0 withdraw bucket: `requestWithdraw` records receipts into `apr0TotalPrincipal` keyed to the epoch in which they were made, but `prepareStopEpochWithApr0` hard-reverts if `unscaledApr` is non-zero at settlement time. An unprivileged lender can open an APR0 receipt in epoch N; when the honest manager later sets a non-zero APR for the upcoming epoch N+1 (a routine, legitimate action), every subsequent `stopEpoch` reverts, so the epoch can never close normally.

### Finding Description
- `IdleCreditVault.requestWithdraw` routes requests to `_requestWithdrawApr0` whenever `unscaledApr == 0`, incrementing `apr0TotalPrincipal` and stamping `apr0Users[user].principalEpoch = epochNumber` (IdleCreditVault.sol:285-286, 567-577).
- `prepareStopEpochWithApr0`, called by the CDO during `stopEpoch`, reverts with `NotAllowed` if `apr0TotalPrincipal != 0 && unscaledApr != 0` (IdleCreditVault.sol:502-508). There is no fallback path: the bucket is only closed inside this same function (`apr0TotalPrincipal = 0`, line 540), which is unreachable once it reverts.
- Nothing clears `apr0TotalPrincipal` on the user side either: `_settleApr0` only moves per-user principal into `settledPrincipal` (lines 545-565), and `_clearWithdrawClaimForEpoch` decrements the global bucket only during default-claim clearing (lines 822-828). A user cannot claim mid-epoch (`_claimFundedWithdrawRequest` reverts while `epochNumber <= lastWithdrawRequest`, line 326), so the poisoned state cannot be self-healed.
- Sequence: pool runs an epoch with `unscaledApr == 0` → lender calls `IdleCDOEpochVariant.requestWithdraw` → receipt lands in the APR0 bucket → manager/borrower flow sets a new APR via `setAprs`/`setAprsWithBuffer` for the upcoming epoch (lines 206-220, callable by the honest manager) → borrower repays, manager calls `stopEpoch` → `prepareStopEpochWithApr0` reverts → `stopEpoch` can never succeed while `unscaledApr != 0`.

### Impact Explanation
Temporary freezing of the entire vault's funds with a possible forced-default cascade. While `stopEpoch` reverts, the epoch cannot close past `epochEndDate`, so borrower repaid funds cannot be distributed and all pending receipts and active NAV are stuck. If the stall extends past the default deadline, honest default-handling (`_handleBorrowerDefault` / instant-withdraw funding paths) can be triggered even though the borrower repaid, crystallizing a spurious default and invoking recovery accounting for all LPs. Recovery exists (the manager can call `setAprs(0, …)` to restore `unscaledApr == 0`, let one `stopEpoch` drain the bucket, then re-apply the intended APR), so the freeze is temporary rather than permanent — matching the "temporary freezing with quantified loss" acceptance criterion. Quantified loss: all yield and withdrawals for every depositor are frozen for the stall duration, and if the stall crosses the default window the pool suffers a wrongful default finalization (loss of full principal recovery price for all receipt holders).

### Likelihood Explanation
Medium. The attacker is any unprivileged KYC'd lender: one `requestWithdraw` while APR is 0 plants the blocker. The trigger requires only the honest manager changing the APR for the next epoch — a routine operation, and precisely the "data prepared for the upcoming epoch" transition that mirrors the Ethash epoch-boundary bug. No malicious privileged action, timing precision, or capital is required beyond a deposit. The main mitigant is that the manager can eventually restore `unscaledApr == 0` to unbrick settlement, which is why the impact is temporary freezing rather than permanent loss.

### Recommendation
In `prepareStopEpochWithApr0`, do not revert when `unscaledApr != 0`. Either settle the outstanding APR0 bucket at a zero rate (close `apr0TotalPrincipal` and let `_settleApr0` pay principal with `apr0RateByEpoch` unset), or move the revert earlier by rejecting new APR0 `requestWithdraw` calls once a non-zero APR is scheduled. Alternatively, key APR0 requests to their request epoch and settle them regardless of the current APR, so an APR change for the next epoch can never invalidate receipts recorded under the previous one.

### Proof of Concept
```solidity
// Foundry fork PoC (test/foundry/IdleCreditVault.t.sol harness style)
// Precondition: pool ran its last epoch with unscaledApr == 0 (APR0 mode),
// attacker holds AA tranches, epochEndDate passed, borrower funded.

function testApr0ReceiptBricksStopEpochAfterAprChange() external {
    // --- epoch N ends with APR = 0; attacker requests withdraw ---
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);                 // epoch N settles fine at APR 0

    _forceLastEpochAprToZero();               // keep unscaledApr == 0
    uint256 trancheBal = IERC20(AAtranche).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(trancheBal / 2, address(AAtranche)); // lands in apr0 bucket
    assertGt(strategy.apr0TotalPrincipal(), 0);

    // --- honest manager schedules a non-zero APR for the upcoming epoch ---
    vm.prank(manager);
    strategy.setAprsWithBuffer(5e18, cdoEpoch.epochDuration(), cdoEpoch.bufferPeriod());
    assertGt(strategy.unscaledApr(), 0);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // --- borrower repays in full; stopEpoch is now permanently bricked ---
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest()
        + strategy.pendingWithdraws());
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);                 // reverts: apr0TotalPrincipal != 0 && unscaledApr != 0

    // every retry reverts; if the stall crosses the default deadline the pool
    // can be forced into _handleBorrowerDefault despite full repayment.
    vm.warp(block.timestamp + cdoEpoch.epochDuration());
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);
}
```

Caveat: I was unable to fully trace `IdleCDOEpochVariant.stopEpoch` to confirm it calls `prepareStopEpochWithApr0` unconditionally before the tool budget ended; the revert path in `IdleCreditVault` itself is verified, but if `stopEpoch` skips `prepareStopEpochWithApr0` when `apr0TotalPrincipal == 0` only (not the case here — it is non-zero), the finding stands as described.
