### Title
`depositDuringEpoch` prices minted tranche shares and interest share using pre-deposit AA/BB weights, ignoring the new deposit's size — large or reshaping deposits capture the interest split they should dilute - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The bug class is "the quote/pricing function uses only the pre-trade state and never the incoming order size, so economic protection that depends on position size can be bypassed." In `IdleCDOEpochVariant.depositDuringEpoch`, both the existing holders' expected interest (`trancheExpected`) and the new deposit's own interest (`trancheInterest`) are computed with `_calcTrancheInterestShare` on the **pre-deposit** tranche NAVs (`lastNAVAA`/`lastNAVBB`). The minted share count is then derived from `expectedFinal = lastTrancheNAV + trancheExpected` (IdleCDOEpochVariant.sol L705-L724). The deposit's own amount — which can radically change the AA/BB NAV ratio and therefore the tranche's actual share of `expectedEpochInterest` — is never reflected in either quantity. This is the same defect as OracleMaker quoting spread off the pre-trade maker position only.

### Finding Description
`depositDuringEpoch` (L656-L733) runs during a running epoch (between `startEpoch`/`stopEpoch`, i.e., not buffer/closed/defaulted) in fixed-APR mode (`isProgrammableBorrower == false`, `isAYSActive == false`).

Flow:
1. `_updateAccounting()` crystallizes accrued interest (L682).
2. `interest` is computed on `_amount` alone (L693-L697).
3. `trancheExpected` = existing holders' expected share of net epoch interest, split via `_calcTrancheInterestShare` using **pre-deposit** NAVs (L705-L709).
4. `trancheInterest` = this deposit's prorated interest, again split with **pre-deposit** weights (L711-L714).
5. `_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal` (L724), where `expectedFinal` is the pre-deposit tranche NAV plus `trancheExpected`.

The flaw: `_calcTrancheInterestShare` attributes epoch interest between AA and BB proportionally to their NAV weights. A deposit that materially shifts the ratio (e.g., a whale deposit into the minority tranche) is nevertheless quoted a mint price and an interest entitlement as if the old ratio persisted — exactly the "position crosses the size threshold but the quote sees the old position" defect. Concretely:

- Suppose AA NAV is large and BB NAV is small (BB is the minority tranche). Per the senior/junior design, the minority BB tranche commands a leveraged share of interest.
- Alice deposits a huge amount into BB mid-epoch. `trancheInterest` is computed as though BB still has the minority weight, but after the deposit BB dominates NAV — and `expectedEpochInterest += interest` (L728) accrues to a tranche whose actual share at `stopEpoch` accounting will be far larger than the pre-deposit ratio implied.
- Symmetrically, `trancheExpected` for existing BB holders was computed at the old minority ratio while the deposit dilutes per-share claims; conversely for the AA side the quote never re-weights. The minted amount is priced off `expectedFinal` that does not include the deposit's own NAV contribution or its effect on the split ratio, so the share price paid differs systematically from the fair price.

Analogous to the reported attack, the trader controls the "size" dimension that the quote ignores: by choosing a deposit that crosses ratio thresholds (or splitting one large deposit into a sequence — each call re-reads `lastNAVAA`/`lastNAVBB` but still prices interest share at whatever the then-current, attacker-influenced ratio is), Alice captures interest allocation the design intended to reserve proportionally, forcing the other tranche (or existing same-tranche holders) to fund a worse-than-designed distribution.

### Impact Explanation
Direct loss to tranche holders: the deposit mints shares priced on a stale interest split, so at `stopEpoch`/`claimWithdrawRequest` the actual NAV per share of the counterparty tranche (and of pre-existing same-tranche holders) is lower than what the `expectedFinal`-based price implied. The attacker withdraws principal plus an interest share that pre-deposit holders effectively subsidize. Loss magnitude scales with deposit size and the pre/post ratio distortion — bounded by the epoch's expected interest for the affected tranche, minus fees.

### Likelihood Explanation
- Attacker needs only `isWalletAllowed` (KYC lender) — an in-scope unprivileged role.
- Conditions: epoch running, `isDepositDuringEpochDisabled == false`, fixed-APR non-programmable mode, target tranche supply nonzero, and `_guarded` limit permitting a size-significant deposit. All are normal operating states.
- No privileged action, oracle manipulation, or timing dependence beyond depositing mid-epoch; the entire sequence is atomic within the attacker's own call(s).

### Recommendation
Compute `trancheExpected` and `trancheInterest` using the **post-deposit** AA/BB NAV weights (i.e., pass `lastNAVXX + _amount` for the deposited tranche into `_calcTrancheInterestShare`), and include the deposit's own contribution in `expectedFinal` — mirroring the Synthetix SIP-279 style fix of averaging the relevant weight before and after the trade rather than only before. Alternatively, disallow `depositDuringEpoch` when `_amount` would move the AA/BB ratio by more than a bounded threshold.

Foundry fork PoC sketch (concrete reproduction):

```solidity
// Setup: deploy/init IdleCDOEpochVariant with fixed APR, isAYSActive=false,
// isProgrammableBorrower=false, bufferPeriod>0, non-zero AA and BB seeded
// such that NAV_AA >> NAV_BB (BB is minority tranche).

// 1. owner: startEpoch(...) -> isEpochRunning = true
// 2. Advance block.timestamp to mid-epoch (< epochEndDate).
// 3. Bob (KYC'd): existing BB holder with navBB0; Alice is KYC'd attacker.

// 4. Record BB virtualPrice / expected per-share payoff:
uint256 bbSupply0 = BBTranche.totalSupply();
uint256 bbNav0    = cdo.lastNAVBB();

// 5. Alice depositDuringEpoch(huge, BBTranche) where huge >> bbNav0
//    -> trancheInterest computed with pre-deposit AA/BB ratio
//    -> minted = (huge + trancheInterest) * bbSupply0 / (bbNav0 + trancheExpected_bb)

// 6. Warp to epochEndDate + bufferPeriod; borrower repays; owner calls stopEpoch*.
// 7. Bob requestWithdraw + claimWithdrawRequest; Alice claims likewise.

// Assertions:
uint256 alicePayoff = aliceUnderlying - huge;         // captured interest
uint256 bobPayoff   = bobUnderlying - bobPrincipal;   // diluted interest
// alicePayoff / huge > bobPayoff / bobNav0: Alice earns a disproportionate
// share of epoch interest because her mint price and interest share were
// quoted at the pre-deposit ratio; Bob's realized NAV/share is below the
// expectedFinal-based expectation used when minting Alice's shares.
// Equivalent control run: when Alice's deposit is split to keep the ratio
// constant (or priced with post-deposit weights), the per-unit payoff
// differential disappears.
```

Key instrumentation: compare `_minted` shares against a recomputed fair mint `(huge + trancheInterestPost) * bbSupply / expectedFinalPost` where the interest share uses post-deposit NAVs; the difference quantifies the subsidy extracted from existing holders.
