## Title
Missing Fee-Amount Bounds Check in Destination Escrow Enables Permanent Withdrawal Denial-of-Service - (File: `contracts/BaseEscrowFactory.sol` / `contracts/EscrowDst.sol`)

### Summary
The `createDstEscrow` function accepts caller-supplied `dstImmutables.parameters` (encoding `protocolFeeAmount` and `integratorFeeAmount`) without validating that their sum does not exceed `dstImmutables.amount`. This omission mirrors the root cause described in the external report: a downstream subtraction (`immutables.amount - integratorFeeAmount - protocolFeeAmount` in `EscrowDst._withdraw`) is performed with no upstream guard against the fee values exceeding the escrowed amount.

### Finding Description
On the source side, `_postInteraction` explicitly guards against this exact condition: [1](#0-0) 

```
(uint256 integratorFeeAmount, uint256 protocolFeeAmount, bytes calldata tail) = FeeTaker._getFeeAmounts(...);
if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();
```

However, `createDstEscrow` — a separate, independently callable entry point reachable directly by any unprivileged taker/resolver — has no equivalent check: [2](#0-1) 

The `protocolFeeAmount`/`integratorFeeAmount` values embedded in `dstImmutables.parameters` are fully attacker-controlled at this call site (the caller assembles `Immutables` themselves), and the factory does not cross-check them against `dstImmutables.amount` before deploying the destination escrow clone and pulling in funds.

Later, `EscrowDst._withdraw` performs the unchecked-in-intent subtraction: [3](#0-2) 

Because the contracts are compiled with Solidity `0.8.23` (no `unchecked` block here — confirmed no `unchecked` usage in `EscrowDst.sol`/`BaseEscrowFactory.sol`), `immutables.amount - integratorFeeAmount - protocolFeeAmount` does not silently wrap like the Go `int64` in the analog report; instead it reverts with a arithmetic-underflow panic whenever `integratorFeeAmount + protocolFeeAmount > immutables.amount`. Since this check is missing at escrow-creation time, an escrow can be deployed and funded in a state where `withdraw()` and `publicWithdraw()` will unconditionally revert forever, regardless of who calls them or when.

### Impact Explanation
Once such a malformed destination escrow is created, both `withdraw` (taker-only) and `publicWithdraw` (public path) permanently revert due to the underflow panic, so the maker can never receive `immutables.amount` on the destination chain through the intended withdrawal path. The only remaining path is `cancel()`, which returns funds to the taker/resolver after the cancellation timelock — meaning the maker's expected destination-side payout is temporarily/durably frozen and the atomic swap cannot complete as designed for that leg. This falls under "temporary freezing of funds during the live swap lifecycle" / the contract becoming unable to operate its core withdrawal function due to attacker-supplied parameters, reachable purely through the `createDstEscrow` public entry point described explicitly in the audit's Destination path pivot.

### Likelihood Explanation
`createDstEscrow` is a `public payable` function with no fee-sanity validation, callable by any address; a resolver constructing `dstImmutables` in bad faith (or due to an off-chain computation bug that isn't independently verified on-chain) can trivially set `protocolFeeAmount + integratorFeeAmount > amount` and get the escrow deployed and funded, since the only checks performed are on `msg.value`/timelock ordering, not on fee-sum bounds.

### Recommendation
Add an explicit bounds check in `createDstEscrow` (or in `EscrowDst._withdraw`) analogous to the existing `InvalidFeeAmounts` guard in `_postInteraction`:
```solidity
if (dstImmutables.integratorFeeAmount() + dstImmutables.protocolFeeAmount() >= dstImmutables.amount) revert InvalidFeeAmounts();
```
This prevents deployment/funding of an escrow whose committed fee parameters make normal withdrawal permanently unreachable.

### Proof of Concept
1. A resolver calls `createDstEscrow(dstImmutables, srcCancellationTimestamp)` where `dstImmutables.parameters` encodes `protocolFeeAmount + integratorFeeAmount > dstImmutables.amount`, supplying the correct `msg.value`/token amount as required by the current (unchecked) logic.
2. The escrow clone deploys successfully; funds are transferred in per [4](#0-3) .
3. After the withdrawal timelock, any call to `withdraw`/`publicWithdraw` executes fee transfers, then hits `immutables.amount - integratorFeeAmount - protocolFeeAmount` in [5](#0-4) , which reverts with an arithmetic panic — permanently, for any caller, at any future time (short of `cancel()` after the cancellation stage).

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```
