### Title
Loss-adjusted withdraw receipts escape their haircut when a later request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` keys the loss lookup only on `lastWithdrawRequest[_user]`, i.e. the *most recent* request epoch. A user whose epoch-N receipt was funded at a loss haircut (`lossRecoveryPriceByEpoch[N] < 1e18`) can submit a second `requestWithdraw` in a later epoch M. This overwrites `lastWithdrawRequest[_user]` to M, so the loss lookup returns 0, the old receipt is never cleared through `_clearWithdrawClaimForEpoch`, and `_claimFundedWithdrawRequest` pays the *aggregate* `withdrawsRequests[_user]` at full par — the haircut is silently bypassed.

### Finding Description
Path traversal analog: an epoch-scoped receipt "traverses" out of its own epoch's loss boundary into a later clean epoch.

- `collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]` when the borrower underfunds `pendingWithdraws` (lines 411-421).
- `requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` (line 282), losing the reference to the loss epoch.
- `_claimLossAdjustedWithdrawRequest` only inspects `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (lines 789-792). With `lastWithdrawRequest` = M (clean), it returns 0 and never calls `_clearWithdrawClaimForEpoch` for epoch N.
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — which still contains epoch N's full `claimBasis` — 1:1 via `_transferFundedClaim` (lines 338-349), and clears `withdrawsRequestsByEpoch` is never consulted on the funded path.

The code comments even acknowledge multiple concurrent requests are legal ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch", lines 323-324), so the overwrite is reachable, not an edge case. `_transferFundedClaim`'s reserve guard only protects `defaultRecoveryReserve`, not the general underfunding this creates.

### Impact Explanation
The strategy received only `claimBasis_N * lossRecoveryPrice` of underlying for the epoch-N receipt, but pays out `claimBasis_N`. The attacker steals `claimBasis_N * (1 - lossRecoveryPrice / 1e18)` — funded by other users' claims/reserves, breaking solvency and the loss-socialization invariant that `stopEpochWithDuration(_lossAmount)` is supposed to enforce on pending receipts. Last claimants in the epoch absorb the shortfall (revert on insufficient balance → freezing of unclaimed funds).

### Likelihood Explanation
Requires only a normal (unprivileged) user with a pending receipt in a `stopEpochWithDuration` loss epoch plus one extra `requestWithdraw` in a subsequent epoch — no privileged collusion. The loss epoch must be realized by the honest manager, which is a normal operating mode (`_lossAmount` path). Once `epochNumber > lastWithdrawRequest[_user]` (one more epoch), the par claim succeeds.

### Recommendation
Track loss-adjusted receipts per epoch instead of a single `lastWithdrawRequest` key: iterate/`pop` all epochs with non-zero `withdrawsRequestsByEpoch[_user][e]` that have a `lossRecoveryPriceByEpoch[e]` entry, or store a per-user list of request epochs. Alternatively, keep a `firstPendingLossEpoch[_user]` pointer, or pro-rate the haircut into `withdrawsRequests[_user]` at `collectWithdrawFunds` time so the funded path is already haircut-aware.

### Proof of Concept
Foundry fork scenario (attacker = KYC'd lender `user1`):

```solidity
// 1. user1 deposits and requests withdraw in epoch 0
_depositWithUser(user1, 10_000 * ONE_SCALE, true);
vm.prank(user1);
uint256 basis = cdoEpoch.requestWithdraw(0, address(AAtranche)); // epoch 0 receipt

// 2. epoch 0 runs; stopEpochWithDuration realizes a loss so pending receipts
//    are underfunded -> lossRecoveryPriceByEpoch[1] = e.g. 0.5e18
_startEpochAndCheckPrices(0);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), lossAmount);
// strategy now holds only basis * lossRecoveryPrice for user1's receipt

// 3. user1 makes a NEW request in the next epoch (needs tranche tokens;
//    deposit again first). This sets lastWithdrawRequest[user1] = epoch 2.
idleCDO.depositAA(...); // as user1
vm.prank(user1);
cdoEpoch.requestWithdraw(0, address(AAtranche));

// 4. run one more epoch so the gate epochNumber > lastWithdrawRequest passes
_startEpochAndCheckPrices(2);
_stopEpochAndCheckPrices(2, apr, funds);

// 5. claim: _claimLossAdjustedWithdrawRequest looks up
//    lossRecoveryPriceByEpoch[2] == 0 -> skipped;
//    _claimFundedWithdrawRequest pays withdrawsRequests[user1] at PAR,
//    including the epoch-0 receipt that was funded at 50%.
vm.prank(user1);
cdoEpoch.claimWithdrawRequest();
// assert user1 received basis (full) + epoch-2 amount, i.e.
// stole basis * (1 - lossRecoveryPrice) from the pool
```
