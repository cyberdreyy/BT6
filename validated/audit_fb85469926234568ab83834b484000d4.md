This confirms the key finding: `select_staking_pool` requires `assert_owner()`, so the owner (whoever `owner_account_id` was set to) is the only one who can pick a staking pool, and it must pass through `staking_pool_whitelist_account_id`. If an attacker front-runs lockup creation and sets a malicious `staking_pool_whitelist_account_id`, the owner will unknowingly be restricted to (or fooled into trusting) an attacker-controlled whitelist rather than the legitimate foundation whitelist.

### Title
Unauthenticated `create()` lets anyone pre-deploy a victim's lockup with attacker-chosen `release_duration`, `vesting_schedule` and whitelist - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the lockup's account ID solely from `sha256(owner_account_id)` and accepts `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, and `whitelist_account_id` directly from the caller, with no check that the caller is the intended grantor/foundation. Because NEAR account creation is a first-come, first-served namespace, any unprivileged attacker can front-run the legitimate grantor and permanently claim the deterministic lockup address for a given `owner_account_id`, populating it with terms and a whitelist contract of their own choosing.

### Finding Description
The intended binding is: `lockup_terms(owner_account_id) == terms_chosen_by_grantor(owner_account_id)`, i.e., the vesting/release schedule and the staking-pool whitelist bound to an employee's lockup account should always reflect what the foundation/grantor configured for that grant.

In `create` [1](#0-0) , the lockup account name is computed purely from `owner_account_id`:
```
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id = format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
```
There is no dependency on `env::predecessor_account_id()` or any grantor-signed data, and the function is `#[payable]` with the only gate being `attached_deposit() >= MIN_ATTACHED_BALANCE` [2](#0-1) . All of `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, and `whitelist_account_id` are taken verbatim from the caller and passed into the `LockupArgs` sent to the freshly created contract [3](#0-2) .

Because the target account name is deterministic and depends only on `owner_account_id`, an attacker can call `create(owner_account_id = victim, lockup_duration = <attacker's choice>, vesting_schedule = <attacker's choice, e.g. none or a schedule that fully unlocks immediately>, release_duration = <attacker's choice>, whitelist_account_id = <attacker-deployed fake whitelist>)` before the real grantor does, paying only `MIN_ATTACHED_BALANCE` (3.5 NEAR). NEAR's `create_account` action fails if the account already exists, so once the attacker's lockup is deployed at that address, the legitimate grantor's later `create()` call for the same `owner_account_id` will fail at `create_account`, causing `on_lockup_create` to detect failure via `is_promise_success()` and refund the grantor's deposit [4](#0-3) . The victim (`owner_account_id`) is left owning a contract whose schedule and staking-pool whitelist were chosen by the attacker rather than the grantor.

The downstream impact is amplified because `select_staking_pool` in the lockup contract is gated only by `assert_owner()` and checks whitelisting against whatever `staking_pool_whitelist_account_id` was baked in at creation time [5](#0-4) . If the attacker substitutes their own whitelist contract, the owner's later staking actions are validated against a contract the protocol never vetted, defeating the "only foundation-approved pools" invariant, and any `release_duration`/`vesting_schedule` chosen by the attacker can cause funds to unlock far earlier (or never) than the grant intended.

No guard in `create` or `on_lockup_create` checks `predecessor_account_id` against a foundation allowlist for the non-vesting path (foundation is only injected when `vesting_schedule.is_some()` at line 124-126), and there is no reservation/claim mechanism preventing account-name squatting.

### Impact Explanation
This is Critical under "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." The attacker permanently seizes the deterministic account name for an intended grant recipient, dictating that recipient's `release_duration`, `vesting_schedule`, `lockup_timestamp`, and `staking_pool_whitelist_account_id`. This can cause tokens to be released early/never as chosen by the attacker and can route the owner's staking interactions through an attacker-controlled "whitelist" contract instead of the foundation's, undermining the pool-vetting invariant across the whole staking flow. The attack is repeatable against any `owner_account_id` the attacker anticipates the foundation will grant to, for the cost of `MIN_ATTACHED_BALANCE` per victim.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only `MIN_ATTACHED_BALANCE` (3.5 NEAR) and knowledge/guess of an `owner_account_id` that will later receive a legitimate grant (e.g., a publicly known employee/investor account, or an account name pattern used by the foundation). No privileged role, key, or contract ownership is required. `create` is `pub` and callable by any account [6](#0-5) .

### Recommendation
Restrict lockup creation for a given `owner_account_id` so that schedule-defining parameters can only originate from an authorized grantor: e.g., require `env::predecessor_account_id() == foundation_account_id` (or a dedicated grantor allowlist) whenever `vesting_schedule`/`release_duration`/custom `whitelist_account_id` are supplied, and/or incorporate `predecessor_account_id` into the derived lockup account name so a random third party cannot pre-claim the address reserved for a specific owner/grantor pair. At minimum, before creating a non-foundation-vested lockup, check that no account exists yet at the target address is insufficient (that's already implicit); the real fix is authenticating who may set the terms for a target owner.
