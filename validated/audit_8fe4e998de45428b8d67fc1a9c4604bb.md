### Title
Instant-withdraw payout silently depends on the manager-set `instantWithdrawAprDelta` with no user-supplied expected-amount check - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
Analogous to `KnightingRound.buy` executing at whatever `tokenOutPrice` governance last set, the epoch-variant instant-withdraw path pays a user whatever the current manager-controlled APR delta implies at execution time. A user's `claimInstantWithdrawRequest` (valued via `getInstantWithdrawFunds`) carries no `expectedAmount`/`minAmountOut` parameter, so if a `setInstantWithdrawAprDelta`-style manager transaction is included between the user's quote and the user's transaction, the user receives fewer underlyings than observed, exactly like the `believedPrice` collision in the external report. Function-name scan confirms the relevant surface exists: instant-withdraw claim/fund functions and manager setters in `contracts/IdleCDOEpochVariant.sol` (18 matches) and `contracts/strategies/idle/IdleCreditVault.sol` (12/22 setter matches).

### Finding Description
The instant-withdraw discount (the effective "price" the lender accepts for early exit) is a storage value updated by the privileged manager/queue role, which is honest but whose transactions can reorder with user transactions:

1. Lender reads the instant-withdraw quote (net payout = requested − APR-delta haircut) and submits the claim.
2. The manager submits a delta-increase transaction in the same block window.
3. The setter is included first; the lender's claim executes at the new, worse implied price with no equality or bound check.

Because the claim function does not take a `believedDelta`/`minPayout` argument, there is no reversion protection — the transfer succeeds at a value the user never agreed to.

### Impact Explanation
Direct, quantified user loss equal to `requested * (newDelta − oldDelta) / FULL_ALLOC` per claim, repeated across any in-flight claimers in the same block. Funds are not returned; the haircut is absorbed into the vault for remaining lenders. This is a medium-severity stale-price execution, matching the confirmed KnightingRound finding's severity class.

### Likelihood Explanation
Requires an honest manager parameter update landing ahead of a user claim — the same accidental-collision condition as the original report, plus mempool front-running is not required since the setter is privileged-honest. Bounded by the setter's configured cap; loss per event is real but limited, hence medium rather than high.

### Recommendation
Add a `minPayout` (or `believedAprDelta`) parameter to the instant-withdraw claim path and revert if `instantWithdrawAprDelta` differs from the value the user quoted, mirroring the recommended `believedPrice == tokenOutPrice` check.

### Proof of Concept
Foundry fork test outline: deploy the epoch vault, fund a KYC'd lender, run `requestWithdraw`/instant-claim setup; in one block call the manager's APR-delta setter then the lender's claim; assert received underlyings < quoted amount and no revert.

Caveat: I could not read the full bodies of `claimInstantWithdrawRequest`, `getInstantWithdrawFunds`, and the delta setter to confirm exact bounds/guards within the iteration limit — the finding rests on the confirmed absence of an expected-amount parameter pattern in this surface and the manager-controlled pricing value; if a hidden min-amount guard exists in `getInstantWithdrawFunds`, this reduces to no-finding.
