### Title
Multisig executes requests below the effective live-member threshold because confirmations from removed (deleted) members are not purged from in-flight requests they did not author - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` in [1](#0-0)  decides whether to execute a request purely by counting entries already stored in the `confirmations: LookupMap<RequestId, HashSet<String>>` map, without re-validating that every stored confirming identity is still a current member of `self.members`. `delete_member` only cleans up requests that were *authored* by the removed member, not confirmations the removed member cast on requests authored by someone else, so a stale confirmation from an already-removed member remains counted toward `num_confirmations` for any still-pending request.

### Finding Description
- `add_request` records the request together with the caller as `member` [2](#0-1) , and creates an empty confirmation `HashSet<String>` for it.
- `confirm` inserts the confirming member's stringified identity into that set, and once `confirmations.len() + 1 >= self.num_confirmations` it executes the underlying request [3](#0-2) .
- `delete_member` (invoked through `execute_request`'s `DeleteMember` action) removes the member from `self.members`, but the cleanup of outstanding requests is scoped only to requests where `r.member == member`, i.e. requests the removed member *created* [4](#0-3) . It never scans `self.confirmations` to strip the removed member's votes from requests authored by *other* members.
- As a result, `confirm`'s threshold check in [5](#0-4)  treats a vote cast by a since-removed member as equivalent to a vote from a current member, even though `current_member()` at line [6](#0-5)  is used only to gate *new* confirmations, not to re-validate ones already stored.

The equality the multisig is supposed to enforce is:
`number of confirmations from CURRENT members >= num_confirmations` before execution.

What is actually enforced is:
`|confirmations set recorded at any point, possibly containing removed members| + 1 (current caller) >= num_confirmations`.

These two diverge whenever a confirming member is later removed from the multisig while their earlier vote is still attached to a pending, unrelated request.

### Impact Explanation
This lets a multisig request execute while fewer than `num_confirmations` *live* members actually approved it — i.e., a multisig request is executed below threshold. Since `execute_request` can move funds (`Transfer`), add/delete keys or members, deploy new contract code, or make arbitrary `FunctionCall`s on behalf of the multisig account [7](#0-6) , an attacker who once held a legitimate confirming key/account (later revoked, e.g. as part of routine key rotation or after being suspected compromised) still gets partial "credit" toward executing any request that was pending against them at the time of removal, undermining the security guarantee that k-of-n *current* signers must approve every multisig action.

### Likelihood Explanation
This does not require any attacker privilege beyond having been a member at some point and having confirmed a request before being removed — a routine key-rotation/membership-change workflow. Any multisig that (a) has pending, not-yet-fully-confirmed requests and (b) removes one of the members who already confirmed one of those requests (very plausible operational sequence: rotate out a key, then later finish approving pre-existing requests) will silently execute requests with fewer live-member approvals than configured.

### Recommendation
When removing a member in `delete_member`, iterate all entries of `self.confirmations` (not just requests authored by the removed member) and strip the removed member's identity from every confirmation set. Alternatively, have `confirm`/threshold-check re-validate, at confirmation time, that every entry in the stored confirmation set still corresponds to a current member of `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize a `multisig2` contract with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request` to create request `R` (e.g., `Transfer` to an attacker-controlled account) — `R.member == A`, `confirmations[R] = {}`.
3. `B` calls `confirm(R)` → `confirmations[R] = {B}` (1 < 3, not executed yet).
4. Members `A, C, D` submit and confirm a separate request `DeleteMember{member: B}` (3-of-4, reaching threshold) — `B` is removed from `self.members`. Per `delete_member`'s cleanup logic, only requests where `r.member == B` are purged; since `R.member == A`, `R`'s confirmation set `{B}` is left untouched.
5. `C` calls `confirm(R)` → `confirmations[R].len() (1) + 1 = 2 < 3`, not yet executed.
6. `D` calls `confirm(R)` → `confirmations[R].len() (2) + 1 = 3 >= 3` → `execute_request(R)` runs and the transfer is sent.

Only `C` and `D` were live members who actually confirmed `R`; `B`'s vote was cast before removal and should no longer count. The request executed on 2 live-member approvals despite `num_confirmations = 3`, breaking the k-of-n threshold guarantee.

    fn execute_request(&mut self, request: MultiSigRequest) -> PromiseOrValue<bool> {
        let mut promise = Promise::new(request.receiver_id.clone());
        let receiver_id = request.receiver_id.clone();
        let num_actions = request.actions.len();
        for action in request.actions {
            promise = match action {
                MultiSigRequestAction::Transfer { amount } => promise.transfer(amount.into()),
                MultiSigRequestAction::CreateAccount => promise.create_account(),
                MultiSigRequestAction::DeployContract { code } => {
                    promise.deploy_contract(code.into())
                }
                MultiSigRequestAction::AddMember { member } => {
                    self.assert_self_request(receiver_id.clone());
                    self.add_member(promise, member)
                }
                MultiSigRequestAction::DeleteMember { member } => {
                    self.assert_self_request(receiver_id.clone());
                    self.delete_member(promise, member)
                }
                MultiSigRequestAction::AddKey {
                    public_key,
                    permission,
                } => {
                    self.assert_self_request(receiver_id.clone());
                    if let Some(permission) = permission {
                        promise.add_access_key(
                            public_key.into(),
                            permission
                                .allowance
                                .map(|x| x.into())
                                .unwrap_or(DEFAULT_ALLOWANCE),
                            permission.receiver_id,
                            permission.method_names.join(","),
                        )
                    } else {
                        // wallet UI should warn user if receiver_id == env::current_account_id(), adding FAK will render multisig useless
                        promise.add_full_access_key(public_key.into())
                    }
                }
                MultiSigRequestAction::FunctionCall {
                    method_name,
                    args,
                    deposit,
                    gas,
                } => promise.function_call(
                    method_name,
                    args.into(),
                    deposit.into(),
                    Gas::from(gas.0),
                ),
                // the following methods must be a single action
                MultiSigRequestAction::SetNumConfirmations { num_confirmations } => {
                    self.assert_one_action_only(receiver_id, num_actions);
                    self.num_confirmations = num_confirmations;
                    return PromiseOrValue::Value(true);
                }
                MultiSigRequestAction::SetActiveRequestsLimit {
                    active_requests_limit,
                } => {
                    self.assert_one_action_only(receiver_id, num_actions);
                    self.active_requests_limit = active_requests_limit;
                    return PromiseOrValue::Value(true);
                }
            };
        }
        promise.into()
    }

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
