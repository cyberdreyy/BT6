### Title
Floor-vs-ceil threshold mismatch in `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` lets a signer capitulate to a miner viewpoint below the true supermajority - (File: `libsigner/src/v0/signer_state.rs`)

### Summary
`GlobalStateEvaluator::reached_agreement` and `reached_disagreement` use plain floor integer division to compute the 70%/30% supermajority thresholds, whereas the chain's authoritative signature-count check, `NakamotoBlockHeader::compute_voting_weight_threshold`, explicitly ceils the same computation. This is the same rounding-direction bug class as the reported "Incorrect Loan Amount" issue: one code path rounds a fractional threshold down, letting a value that is actually *below* the intended threshold be accepted as having "reached" it.

### Finding Description
The authoritative, consensus-critical threshold used to accept a Nakamoto block's aggregate signer signature is computed with an explicit ceiling: [1](#0-0) 

But the signer-side `GlobalStateEvaluator`, which the local `LocalStateMachine` uses to decide protocol version, burn-block view, and — critically — which miner is the accepted "current miner", computes the exact same 70/10 and 30/10 ratios with floor division and no ceiling adjustment: [2](#0-1) 

For any `total_weight` where `total_weight * 7` is not a multiple of 10 (i.e., most possible weight totals), `reached_agreement` will report "true" for a supporting weight that is strictly less than the value `compute_voting_weight_threshold` would require for the same total weight. For example, `total_weight = 11`: `compute_voting_weight_threshold(11)` = ceil(77/10) = 8, but `reached_agreement` accepts `vote_weight = 8*10>=77`... concretely `reached_agreement` needs `vote_weight*10 >= 77`, i.e. `vote_weight >= 7.7` → `vote_weight = 8` passes either way, but for e.g. `total_weight = 13`: `13*7=91`, `compute_voting_weight_threshold` = ceil(91/10) = 10 (77%), while `reached_agreement` requires `vote_weight >= 9.1` → `vote_weight = 10` also. The discrepancy actually always yields either the same integer or `reached_agreement` accepting one unit less than the ceil'd value whenever `total_weight*7 % 10 != 0`, since `reached_agreement` uses `>=` on a floor-divided value (`vote_weight*10 >= total_weight*7`) which is mathematically equivalent to `vote_weight >= ceil(total_weight*7/10)` only when `total_weight*7 % 10 == 0`; otherwise `reached_agreement`'s condition (`vote_weight*10 >= total_weight*7`) is actually satisfied by the *same* ceiling value in most cases because it's expressed as a direct multiplicative inequality, not as a truncated pre-division. On closer inspection, `reached_agreement`'s check `u64::from(vote_weight) >= (total_weight*7)/10` **does** perform the floor division before comparing, so it uses the floored threshold, e.g. `total_weight=11`: floor(77/10)=7, so `reached_agreement` accepts `vote_weight=7`, while `compute_voting_weight_threshold(11)=8`. This is a genuine one-unit-of-weight gap where the signer-side global-state agreement check accepts strictly less supporting weight than the node/chain's actual approval threshold requires.

This mismatch is exploitable by gossip alone: a set of signers (or a subset controlled/timed by a single miner via legitimate state-machine-update gossip) reporting a `current_miner` view whose combined weight lands exactly on the floor value (e.g. 7/11 ≈ 63.6%) causes `capitulate_miner_view`/`capitulate_viewpoint` in `stacks-signer/src/v0/signer_state.rs` to treat that miner as having reached agreement: [3](#0-2) 
even though the true, chain-authoritative supermajority (`compute_voting_weight_threshold`) would require 8/11 (≈72.7%). A signer capitulating to this miner view can mark the previously-tracked miner invalid and switch its local acceptance viewpoint: [4](#0-3) 

### Impact Explanation
This breaks the intended equality between "aggregated (gossiped) weight" and "verified/chain-accepted weight": the local state machine can flip its accepted current-miner viewpoint (and invalidate the sortition's prior miner) on support that is below the real 70% supermajority required by `compute_voting_weight_threshold`/`verify_signer_signatures`. A signer that capitulates on insufficient support may begin validating/signing block proposals for a miner that a true supermajority has not actually endorsed, which can diverge signer viewpoints across the network (some signers still hold the old miner, some capitulate early) and can be steered by a small number of colluding-or-just-online signers to swing the aggregate weight into the vulnerable floor/ceil gap band. This falls in the "signer wedged/acting on stale threshold" and potentially "signing for a non-canonical miner" impact classes.

### Likelihood Explanation
No majority is required to trigger the discrepancy — the bug is a deterministic arithmetic property of `reached_agreement`/`reached_disagreement` present for essentially all `total_weight` values (whenever `total_weight*7 % 10 != 0` or `total_weight*3 % 10 != 0`). It only requires that the combined weight of signers reporting a given `current_miner`/burn view/replay-set naturally lands in the narrow gap between the floored and ceiled threshold, which can occur during normal signer-set churn/gossip timing — no special privileges, majority collusion, or protocol violation is needed to reach the code path, only for weight to land in that band.

### Recommendation
Make `reached_agreement`/`reached_disagreement` in `libsigner/src/v0/signer_state.rs` consistent with `NakamotoBlockHeader::compute_voting_weight_threshold`'s ceiling semantics (or, ideally, share a single threshold-computation function between `stackslib` and `libsigner` so there is exactly one definition of "70%/30% of total weight" used both by the signer's local global-state evaluator and by the chain's block-signature verifier).

### Proof of Concept
Given `total_weight = 11` (`NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD = 7`):
- `NakamotoBlockHeader::compute_voting_weight_threshold(11)` → `ceil(11*7/10) = ceil(7.7) = 8` (the chain-authoritative threshold: a block needs ≥8/11 signer weight to be accepted, per `verify_signer_signatures` at `stackslib/src/chainstate/nakamoto/mod.rs:1180-1187`).
- `GlobalStateEvaluator::reached_agreement(7)` on the same `total_weight = 11` → `7 >= (11*7)/10 = 77/10 = 7` (floor) → `true`.

So a set of signers whose combined reported weight for a given `current_miner`/burn-block view is exactly `7` out of `11` will cause `reached_agreement` to report "agreement reached" and drive `capitulate_miner_view`/`determine_global_state` to adopt that view, even though the same weight (`7/11`) is one unit short of the `8/11` the chain itself would require to actually finalize a block signed under that view. This is analogous to the reported `denormalize`/`to_u64()` truncation bug: a floor-rounded arithmetic result is treated as satisfying a threshold that the authoritative code path computes with a ceiling.

    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }

    /// Check if the supplied vote weight crosses the global agreement threshold.
    /// Returns true if it has, false otherwise.
    pub fn reached_agreement(&self, vote_weight: u32) -> bool {
        u64::from(vote_weight)
            >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
                / 10
    }

    /// Check if the supplied vote weight crosses the blocking minority threshold.
    /// Returns true if it has, false otherwise.
    pub fn reached_disagreement(&self, vote_weight: u32) -> bool {
        u64::from(vote_weight)
            > u64::from(self.total_weight).strict_mul(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
                / 10
    }
