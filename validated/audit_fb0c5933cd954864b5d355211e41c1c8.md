### Title
Stale confirmations from removed multisig members still count toward the execution threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges pending requests and confirmation records for requests that the removed member originally *created*; it does not scan and strip that member's confirmations from requests created by other members. Because `confirm()` decides whether to execute a request purely by comparing the size of the stored `confirmations` set against `num_confirmations` — without re-validating that every recorded confirmer is still a current member — a request can execute even though fewer than `num_confirmations` *live* members actually approved it.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` adds the calling member's id to a `HashSet<String>` of confirmations for a request, and executes the request once `confirmations.len() + 1 >= self.num_confirmations`: [1](#0-0) 

Membership removal is handled by `delete_member()`, which only removes *requests originated by* the deleted member (`r.member == member`) along with their confirmations. It never inspects the `confirmations` sets of *other* pending requests to strip out the deleted member's prior confirmation: [2](#0-1) 

`current_member()` / membership checks (`self.members.contains(&member)`) are only applied to the entity actively calling `confirm()` at that moment; the historical confirmations already recorded in the `confirmations` map are never revalidated against the current `members` set: [3](#0-2) 

The intended custody binding is: `confirmations.len() >= num_confirmations` should equal "at least `num_confirmations` **currently live** members approved this request." Once a confirming member is removed via `DeleteMember`, that equality breaks — the stale confirmation remains counted, so the request can be pushed over the threshold with fewer live approvers than `num_confirmations` requires. The equivalent unchecked-cleanup pattern exists in the legacy `multisig/src/lib.rs` for `DeleteKey`, which likewise only purges requests originated by the deleted key, not confirmations that key gave on other members' requests: [4](#0-3) 

### Impact Explanation
This is a Critical-class issue per the custody boundary being broken: a multisig request (e.g. `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, `DeployContract`) can be executed by the contract with an effective live-confirmation count below the configured `num_confirmations` threshold, because a stale confirmation from a now-removed member is still counted. This directly undermines the K-of-N security guarantee the multisig is supposed to enforce and can allow value transfers or privileged account modifications to occur with insufficient current authorization.

### Likelihood Explanation
Likelihood is realistic in any multisig with member churn: any time a member who has already confirmed a still-pending request is later removed (a routine operational action, e.g. key rotation, offboarding a member, replacing a compromised key), that member's stale confirmation remains valid on that pending request. No malicious cooperation beyond ordinary governance actions (create request, confirm, later remove a member) is required, and confirming members act within their normal permissions the whole time — the flaw is state-cleanup logic, not privilege escalation.

### Recommendation
When a member is deleted, iterate over all pending requests' `confirmations` sets (not just those the member originated) and remove that member's confirmation entry, decrementing effectively toward the threshold. Alternatively, revalidate at execution time that every entry in `confirmations` for a request still belongs to `self.members` before counting it toward `num_confirmations`, e.g. by filtering `confirmations` against `self.members` before comparing lengths in `confirm()`.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = {A, B, C, D}, num_confirmations = 3)`.
2. `A` calls `add_request(R1)` (e.g. a `Transfer` to an attacker-controlled account).
3. `B` calls `confirm(R1)` → `confirmations = {B}` (len 1 < 3, not executed).
4. `C` calls `confirm(R1)` → `confirmations = {B, C}` (len 2 < 3, not executed).
5. Separately, members submit and confirm a `DeleteMember(C)` request (`R2`) which executes, removing `C` from `self.members`. `delete_member()` only purges requests *created by* `C`; `R1`'s confirmation set `{B, C}` is left untouched.
6. `D` calls `confirm(R1)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `R1` executes, even though only `B` and `D` are actually live, current members who confirmed — one fewer live confirmation than the configured threshold requires.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
