### Title
Instant-withdraw path bypasses the upfront fee/interest accounting enforced on normal withdraw requests - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external bug (CVE-2025-5025) is a verification routine (`wssl_verify_pinned()`) that is invoked on the standard code path but was never wired into an alternative transport path (QUIC/HTTP3), silently disabling a security check for that mode. The analog in idle-tranches is `IdleCDOEpochVariant.requestWithdraw`: the normal (queued) path invokes `_calcInterestWithdrawRequest` and `_totalWithdrawFees` to deduct the upfront management fee and net performance fee from the receipt, but the instant-withdraw branch — taken whenever `lastEpochApr > unscaledApr + instantWithdrawAprDelta` — burns tranche tokens and mints a full-price strategy-token receipt without ever running that fee/interest adjustment. [1](#0-0) 

### Finding Description
In `requestWithdraw` (contracts/IdleCDOEpochVariant.sol:739-791), a tranche holder requesting withdrawal during the buffer phase gets two different treatments depending on APR conditions:

- **Normal path** (lines 772-790): `_underlyings = principal + interest - totalFees`, where `totalFees = _totalWithdrawFees(principal, interest)` charges the upfront management fee for `epochDuration + remaining buffer` plus the performance fee on projected interest (`_totalWithdrawFees`, lines 900-906; `_withdrawRequestManagementFeeDuration`, lines 925-930). The discounted amount is recorded in `pendingWithdrawFees` and the receipt is booked in `IdleCreditVault.requestWithdraw`.
- **Instant path** (lines 761-769): when `_isInstantWithdrawEnabled()` (not disabled, not programmable) and the new unscaled APR dropped by more than `instantWithdrawAprDelta`, the code calls `creditVault.requestInstantWithdraw(_underlyings, msg.sender)` with `_underlyings = _trancheToUnderlyings(_amount, _tranche)` — the raw principal at current `virtualPrice` — and returns early. `_calcInterestWithdrawRequest`, `_totalWithdrawFees`, and `pendingWithdrawFees` are never applied. [2](#0-1) 

The instant receipt is then funded at `startEpoch` from the pooled underlyings sitting in the CDO (including other users' buffer-period deposits) via `collectInstantWithdrawFunds` (lines 279-294), and claimed at par through `IdleCreditVault.claimInstantWithdrawRequest` / `_transferFundedClaim` (IdleCreditVault.sol:380-393). Nothing in the instant path compensates for the skipped fee deduction: the requester exits at full `virtualPrice` while a queued requester on the same tranche, same amount, same timestamp locks a receipt discounted by `totalFees`.

Whenever the upfront management fee (plus performance fee on projected interest) exceeds the projected epoch interest the queued request would add — i.e. whenever `_totalWithdrawFees(principal, interest) > interest`, which occurs for small principals, high `managementFee`, or low APR — the instant receipt pays strictly more than the economically equivalent queued receipt. The excess is paid from common pool liquidity reserved by `startEpoch`, diluting remaining tranche holders and reducing `pendingWithdrawFees` owed to `feeReceiver`.

### Impact Explanation
- **Fee evasion / holder dilution**: an attacker holding tranche tokens when the APR drops past `instantWithdrawAprDelta` receives `principal` instead of `principal + interest − totalFees`. The skipped fee (management fee over `epochDuration + buffer`, plus performance fee) is borne by the pool: instant claims are funded from `totUnderlyings` at `startEpoch` ahead of borrower forwarding, so remaining depositors' liquidity backs the overpayment and `feeReceiver`/`owner` never accrue the fee that a normal request books into `pendingWithdrawFees`.
- **Quantified loss**: for a request of `P` underlying, evaded value ≈ `managementFee% × P × (epochDuration + remainingBuffer) / YEAR` plus `fee% × max(interest − mgmtFee, 0)`. With a 10% management fee, 30-day epoch + 5-day buffer, a 1M USDC instant request bypasses ≈ 9.6k USDC of fees relative to the queued path.
- Broken invariant: fair burn — two receipt types for the same position should be priced by the same fee policy; the instant path silently skips the "verification" step, mirroring the CVE where pinning was skipped on the QUIC backend.

### Likelihood Explanation
Requires (a) instant withdrawals enabled (`disableInstantWithdraw == false`, settable by manager; default true in `_additionalInit` but enabled on deployments that support instant mode), (b) non-prefunded, non-programmable variant, and (c) a `stopEpoch` where `newApr < lastEpochApr − instantWithdrawAprDelta`. Condition (c) is an ordinary market event (APR reductions happen at every `stopEpoch` where demand falls) and needs no privileged misbehavior — the manager legitimately lowers APR and any unprivileged tranche holder can then call `requestWithdraw` during the buffer window. The exploit is repeatable each time the APR drops. The per-event loss is bounded by the fee schedule, keeping this at medium/low severity rather than high.

### Recommendation
Apply the same deduction discipline on the instant branch: compute `(interest, diff) = _calcInterestWithdrawRequest(_underlyings, _tranche)` and `totalFees = _totalWithdrawFees(principal, interest)` before calling `requestInstantWithdraw`, and pass `principal + interest − totalFees` (or an explicitly justified instant-specific fee such as `instantWithdrawDelay`-scaled management fee) as the receipt amount, while crediting `pendingWithdrawFees` accordingly. If the intent is that instant withdrawals forgo epoch interest, still charge the fee on the funded principal so both receipt types share the same fee invariant; document and test parity between the two branches.

### Proof of Concept
Foundry fork-style PoC (to be placed under `test/foundry/`, modeled on `testClaimInstantWithdrawRequest*` cases in `test/foundry/IdleCreditVault.t.sol:4822-4892`):

```solidity
function testInstantWithdrawBypassesWithdrawFees() external {
    _setFeeParams(TL_MULTISIG, 10000, FULL_ALLOC, 20000); // 10% perf fee, 20% mgmt fee
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(3 days, 1e15, true); // enable instant, small delta

    uint256 amount = 1_000_000 * ONE_SCALE;
    idleCDO.depositAA(amount);                 // attacker position
    _depositWithUser(makeAddr("victim"), amount, true); // pool liquidity

    _startEpochAndCheckPrices(0);
    // stop epoch with a sharply lower next APR so instant mode triggers
    _stopEpochAndCheckPrices(0, initialProvidedApr / 4, _expectedFundsEndEpoch());

    uint256 trancheBal = IERC20(AAtranche).balanceOf(address(this));
    // What the queued path WOULD pay: principal + interest - totalFees
    uint256 underlyings = cdoEpoch.virtualPrice(AAtranche) * trancheBal / ONE_SCALE;
    (uint256 interest, ) = _calcInterestForTranche(AAtranche, underlyings);
    uint256 fees = /* replicate _totalWithdrawFees(principal, interest) */;
    uint256 queuedReceipt = underlyings + interest - fees;

    // Attacker takes the instant path: verification (fee deduction) is skipped
    uint256 instantReceipt = cdoEpoch.requestWithdraw(0, AAtranche);

    assertEq(instantReceipt, underlyings);              // full price, no fee
    assertGt(instantReceipt, queuedReceipt);            // strictly better than queued
    assertEq(cdoEpoch.pendingWithdrawFees(), 0);        // no fee booked to feeReceiver

    // Funded from pooled liquidity at startEpoch and claimed at par
    _startEpochAndCheckPrices(1);
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    _getInstantFunds();
    cdoEpoch.claimInstantWithdrawRequest();
    // Attacker received `instantReceipt` underlyings while `pendingWithdrawFees`
    // never accrued the `fees` amount -> pool/feeReceiver shortfall = `fees`.
}
```

The key assertion is that the instant branch returns the un-discounted `_trancheToUnderlyings` amount while the normal branch on identical inputs returns `principal + interest − totalFees`, and `pendingWithdrawFees` is never incremented — the missing "pinning check" of this codebase.

Caveat: this finding assumes the fee discount on queued receipts is intended to apply to all exits; if instant withdrawals are deliberately priced at par as a protocol policy, the issue reduces to a design/fee-consistency concern rather than a strict bypass. Whether deployments enable `disableInstantWithdraw = false` in production could not be confirmed from the repo alone.
