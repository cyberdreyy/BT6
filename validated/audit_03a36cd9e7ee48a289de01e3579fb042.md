### Title
Vault gateway leaks raw authorizer error text distinguishing "invalid signature" from "unauthorized sender", enabling sender enumeration - ([File: core/services/gateway/handlers/vault/handler.go])

### Finding Description
`HandleJSONRPCUserMessage` calls `h.requestProcessor.ProcessRequest(ctx, &req, cachedPublicKey)` to authenticate/authorize an incoming vault request. When this fails for any reason other than `vaultcap.IsInvalidVaultParamsError`, the handler does: [1](#0-0) 
This wraps and returns the *raw* underlying authorizer error (`"request not authorized: " + err.Error()`) as a plain Go `error`, bypassing the handler's own `errorResponse` sanitation path entirely (that path is only used for responses sent via `sendResponse`/`sendImmediateUserResponse`, not for this early return). The returned error propagates to `gateway.ProcessRequest`, which converts any handler error into a generic `api.HandlerError` but preserves the original message verbatim: [2](#0-1) 
`ToHttpErrorCode` maps both `UserMessageParseError` and `HandlerError` to HTTP 400, so the status code alone does not distinguish cases: [3](#0-2) 
However, the JSON-RPC error `Message` field is populated directly from `err.Error()` with no generalization step, unlike other error paths in the same file that explicitly redact detail (e.g. `NodeReponseEncodingError` — "Intentionally hide the error from the user"): [4](#0-3) 
If the underlying authorizer (`vaultcap.Authorizer` / `NewAllowListBasedAuth` / `NewJWTBasedAuth`) produces distinguishable error strings for "signature verification failed" versus "sender not in allowlist"/"unknown sender", an attacker can submit well-formed but arbitrarily-signed requests with varying sender keys and correlate the returned message text to determine which senders are recognized/allowlisted for a DON/method before attempting impersonation. I was not able to fully verify the exact error message strings produced inside the `vaultcap` authorizer package (not retrieved in this session), so the degree of distinguishability of the underlying messages is not fully confirmed, but the code path that forwards the raw, unredacted authorizer error to the unauthenticated caller is concretely present and confirmed.

### Impact Explanation
If the authorizer's error strings differ between "malformed/invalid signature" and "sender unrecognized/not allowlisted", this handler discloses that distinction directly in the HTTP response body to an unauthenticated caller. This falls under an information-disclosure / minimal-disclosure violation that could aid a sender-enumeration attack, a precursor to attempted request impersonation against a discovered valid subscriber address — matching a "request impersonation reconnaissance" / information disclosure bounty class rather than a direct authentication bypass.

### Likelihood Explanation
The precondition is only an unauthenticated HTTP client able to send signed JSON-RPC gateway requests with varying throwaway keys — no credentials or elevated role are required. The exploit is fully automatable (varying sender key per request, same payload/don_id/method) and repeatable at will since there is no rate limiting or generalized error path visible in `HandleJSONRPCUserMessage`'s authorization-failure branch itself. However, actual exploitability depends on whether the underlying `vaultcap` authorizer error messages are in fact distinguishable per failure mode, which could not be confirmed in this session.

### Recommendation
In `handler.go`'s `HandleJSONRPCUserMessage` (around line 436-443), do not propagate the raw authorizer error message to the caller. Return a single generic, constant message/error code (e.g., always `"unauthorized"` with `api.HandlerError` or a dedicated `UnauthorizedError` code) regardless of whether the failure was signature verification, sender-not-found, or allowlist rejection, and log the detailed reason server-side only (as is already done for `NodeReponseEncodingError`). Route this failure through the same `errorResponse` sanitization path used elsewhere in the file instead of returning a bare `error` that bypasses it.

### Proof of Concept
Go handler-level integration test plan (in `core/services/gateway/handlers/vault/handler_test.go`):
1. Construct two `jsonrpc.Request` messages with identical `don_id`/method/params:
   - Request A: signed with a garbage/malformed signature (triggers signature verification failure).
   - Request B: signed correctly by a throwaway key not present in the DON's allowlist/workflow registry (triggers "unknown sender" rejection).
2. Call `handler.HandleJSONRPCUserMessage` for both (or drive through `gateway.ProcessRequest` end-to-end) and capture the returned `RawResponse`/error text and `ErrorCode`.
3. Assert (to prove the vulnerability) that the two responses currently contain distinguishable substrings from the underlying authorizer errors (e.g., one contains "signature" and the other contains "not authorized"/"unknown sender"), demonstrating the enumeration side channel.
4. After the fix, assert both responses are byte-identical in error code and message (generic "unauthorized"), verifying the side channel is closed.

func ToHttpErrorCode(errorCode ErrorCode) int {
	gatewayErrorToHTTPError := map[ErrorCode]int{
		NoError:                  200, // OK
		UserMessageParseError:    400, // Bad Request
		UnsupportedDONIdError:    400, // Bad Request
		UnsupportedMethodError:   400, // Bad Request
		HandlerError:             400, // Bad Request
		InvalidParamsError:       400, // Bad Request
		RequestTimeoutError:      504, // Gateway Timeout
		NodeReponseEncodingError: 500, // Internal Server Error
		FatalError:               500, // Internal Server Error
		StaleNodeResponseError:   500, // Internal Server Error
		ConflictError:            409, // Conflict
		LimitExceededError:       429, // Too Many Requests
	}

	code, ok := gatewayErrorToHTTPError[errorCode]
	if !ok {
		return 500
	}
	return code
}
