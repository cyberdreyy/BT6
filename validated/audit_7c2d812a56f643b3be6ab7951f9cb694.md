### Title
Legacy gateway path routes to any DON handler by DonId without Sender-to-DON membership check, allowing unauthorized cross-DON request injection - ([File: core/services/gateway/gateway.go])

### Summary
`gateway.ProcessRequest`'s legacy branch selects the handler purely by `msg.Body.DonId` and calls `msg.Validate()`, which only checks field lengths/format and signature validity — it never checks that the recovered `Sender` is a member/subscriber of the target DON. The routed capabilities handler (`core/services/gateway/handlers/capabilities/handler.go`) forwards the request to every DON node without any allowlist check either, confirmed by an explicit `TODO: apply allowlist and rate-limiting here` in the handler and a matching `TODO: Validate Senders and rate limit check` in its test file.

### Finding Description
In `gateway.ProcessRequest`, the legacy branch computes `handlerKey := msg.Body.DonId` and looks up `h, ok = g.handlers[handlerKey]` immediately after `msg.Validate()` [1](#0-0) . `Message.Validate()` only checks field-length/format constraints and recovers the signer into `m.Body.Sender` via `ExtractSigner`; it performs no DON-membership or allowlist check against the target `DonId` [2](#0-1) . The request is then dispatched to `h.HandleLegacyUserMessage(ctx, msg, callback)` [3](#0-2) .

For the capabilities handler (a real registered legacy handler type), `HandleLegacyUserMessage` decodes the payload, checks timestamp staleness and method name, but has an explicit unresolved TODO for authorization: `// TODO: apply allowlist and rate-limiting here` right before forwarding, with no Sender/DON-membership check anywhere in the function [4](#0-3) . It then forwards the request to every node in the target DON via `don.SendToNode` for `member := range h.donConfig.Members` [5](#0-4) . The handler's own test suite documents this gap explicitly: `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated` [6](#0-5) .

This confirms the exploit chain described: an attacker with any private key can self-sign a `Message` with a guessed/enumerated `DonId` and `MethodWebAPITrigger`, submit it to `ProcessRequest`, pass `Validate()` (format-only), get routed via `g.handlers[handlerKey]` to the capabilities handler for that DON, and have the message forwarded to all real nodes of that DON — with no check anywhere in this path that the Sender is an authorized subscriber of that DON.

### Impact Explanation
This is unauthorized cross-DON request injection: any holder of an Ethereum keypair can send arbitrary `MethodWebAPITrigger` requests into any DON whose `don_id` they can guess/enumerate, without being a subscriber/member of that DON. Downstream node-side processing may apply its own authorization (not verifiable from this file/handler alone), but at the gateway/handler layer documented here, there is no allowlist enforcement — matching the "allowlist/quota bypass" and "request impersonation" bounty impact classes.

### Likelihood Explanation
Feasible with minimal privilege: attacker only needs to generate an ECDSA keypair (no registration required) and know or brute-force a valid `don_id` string, which per the finding's stated precondition may be low-entropy/enumerable. `Message.Validate()` imposes no rate limiting or allowlisting on `DonId`, and the capabilities handler explicitly defers this check via TODO, making the attack repeatable and requiring no elevated credentials.

### Recommendation
Add DON-membership/allowlist enforcement at either `gateway.ProcessRequest` (validate `msg.Body.Sender` against a known subscriber/allowlist for `msg.Body.DonId` before dispatch) or, at minimum, inside `capabilities.handler.HandleLegacyUserMessage` before forwarding to `don.SendToNode`, resolving the outstanding TODO at `core/services/gateway/handlers/capabilities/handler.go:384`.

### Proof of Concept
Handler-level integration test plan:
1. Construct a `capabilities.handler` instance configured for DON `"testDON"` with a known member set, using a mocked `don.SendToNode`.
2. Self-sign a legacy `api.Message` with `Body.DonId = "testDON"`, `Body.Method = MethodWebAPITrigger`, using a private key never registered as an allowed sender/subscriber for that DON.
3. Call `handler.HandleLegacyUserMessage(ctx, msg, callback)` directly (bypassing gateway-level routing, mirroring `ProcessRequest`'s legacy path).
4. Assert that `don.SendToNode` is still invoked for all DON members despite the sender not being an authorized subscriber — demonstrating the missing check documented by the `TODO` comment.
5. Compare against expected behavior: the call should instead return an authorization error (e.g., `api.HandlerError` for "sender not authorized for DON") before any `don.SendToNode` call occurs.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
