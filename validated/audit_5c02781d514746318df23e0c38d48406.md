### Title
Permanent epoch freeze when `unscaledApr` is raised while an APR0 withdraw bucket is open — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
CVE-2018-3200 is a hang/crash (availability) bug. The closest credit-vault analog is an unprivileged-driven permanent freeze of the epoch state machine: `prepareStopEpochWithApr0` reverts unconditionally whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. Since `apr0TotalPrincipal` can only be cleared inside that same function (or via default-finalization paths that are themselves unreachable while `stopEpoch` reverts), any lender can create a state in which a routine manager APR update bricks `stopEpoch` forever.

### Finding Description
`IdleCreditVault.requestWithdraw` routes requests into the APR0 bucket whenever `unscaledApr == 0` at request time: it calls `_requestWithdrawApr0`, which sets `apr0Users[_user].principal`/`principalEpoch` and increments `apr0TotalPrincipal` (lines 285–286, 567–577). At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which contains this guard (lines 502–508):

```solidity
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

There is no escape hatch: `apr0TotalPrincipal` is only reset to 0 at line 540 inside the same function that reverts, or decremented in `_clearWithdrawClaimForEpoch`/`_ensureDefaultRecoveryInitialized`, which are reachable only through claim/default paths that all require an epoch to have ended. `_settleApr0` cannot run either, because settlement requires `_reqEpoch < epochNumber`, and `epochNumber` only advances via `stopEpoch`/`deposit` during the stop flow (lines 551–554, 607–610).

Sequence:

1. Pool operates in APR0 mode (`unscaledApr == 0`, e.g. between rate renegotiations or a zero-rate epoch; tests show `setAprs(0,0)` is a supported manager operation, `test/foundry/IdleCreditVault.t.sol:2986`).
2. Attacker (any KYC-passed AA/BB holder) calls `requestWithdraw` → `apr0TotalPrincipal > 0`. This is a legitimate, unprivileged action.
3. Manager performs a routine `setAprs(newApr, scaledApr)` to set a nonzero rate for the next epoch — an honest privileged action the rules allow sequencing around.
4. Every subsequent `stopEpoch` reverts with `NotAllowed`. The borrower cannot repay, the epoch can never end, withdraws cannot be claimed, deposits are frozen, and the default path is also unreachable (default handling is triggered from `stopEpoch`/`getInstantWithdrawFunds` funding failures, which are gated behind the same reverting call).

### Impact Explanation
Permanent freezing of all vault funds: lenders' tranche value, pending withdraw receipts, and borrower repayment all depend on `stopEpoch` succeeding. Broken invariant: epoch liveness. Loss is the entire NAV until funds are rescued (strategy `transferToken` can recover underlying, but tranche/receipt accounting is permanently corrupted and holders cannot exit at value).

### Likelihood Explanation
Requires the combination APR0 epoch + open APR0 withdraw request + an APR change. The attacker controls the request; the APR change is a normal management operation the manager is expected to perform when renegotiating borrower rates. No malicious privileged role, no oracle, no loop/gas speculation is involved — a single external call by an unprivileged lender creates the armed state.

### Recommendation
Do not hard-revert in `prepareStopEpochWithApr0` when `unscaledApr != 0` and `apr0TotalPrincipal != 0`. Instead, settle the APR0 bucket at a zero rate (skip interest allocation, close the bucket) or provide a manager escape to force-close `apr0TotalPrincipal`, so `stopEpoch` always remains callable.

### Proof of Concept
Foundry fork test (extends the existing `IdleCreditVault.t.sol` harness, e.g. `testApr0WithdrawGetsInterestAtStopEpoch` setup):

```solidity
function testApr0AprChangeBricksStopEpoch() external {
  _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(0, 0); // APR0 mode

  idleCDO.depositAA(10_000 * ONE_SCALE);
  _transferBurnedTrancheTokens(address(this), true);
  _startEpochAndCheckPrices(0);
  vm.warp(cdoEpoch.epochEndDate() + 1);
  deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);

  // attacker (any lender) opens an APR0 withdraw request
  cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 2, address(AAtranche));
  assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

  _startEpochAndCheckPrices(1);

  // honest manager raises APR for next epoch mid-epoch
  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(5e18, 5e18);

  vm.warp(cdoEpoch.epochEndDate() + 1);
  deal(defaultUnderlying, borrower, type(uint256).max / 2);
  vm.prank(manager);
  vm.expectRevert(NotAllowed.selector);
  cdoEpoch.stopEpoch(0, 0); // reverts forever: epoch can never stop
}
```

One caveat I could not fully verify within the tool budget: the exact `stopEpoch` body in `IdleCDOEpochVariant.sol` was not read end-to-end, so this rests on `prepareStopEpochWithApr0` being invoked unconditionally in the stop flow (consistent with `IdleCreditVault.t.sol:2979+` driving APR0 settlement through `stopEpoch`). If `stopEpoch` wraps that call in a `try`, the impact downgrades to APR0 claims only; the revert guard itself is confirmed at `contracts/strategies/idle/IdleCreditVault.sol:505-508`.
