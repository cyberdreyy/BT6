### Title
Loss haircut applied only to the latest request epoch lets earlier unclaimed receipts exit at par, underfunding the funded-claim pool - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` records a stop-epoch loss as `lossRecoveryPriceByEpoch[epochNumber]` against the *entire* aggregate `pendingWithdraws` basis, but `_claimLossAdjustedWithdrawRequest` only haircuts receipts stored under `lastWithdrawRequest[user]` — the user's most recent request epoch. A user who stacked withdraw receipts across multiple epochs before the loss escapes the haircut on all earlier-epoch receipts, draining the underfunded pool and leaving later claimers unpayable.

### Finding Description
- `pendingWithdraws` is a single aggregate counter incremented on every `requestWithdraw` (`pendingWithdraws += _amount`, line 279) and never attributed per epoch.
- A user can hold unfunded receipts in multiple epochs: `requestWithdraw` only reverts when a *loss-priced* receipt exists under `lastWithdrawRequest` (lines 261–271). If epoch N had no loss, a second request in epoch N+1 simply adds `withdrawsRequestsByEpoch[user][N+1]` and moves `lastWithdrawRequest` to N+1 while `withdrawsRequestsByEpoch[user][N]` remains outstanding.
- When the manager calls `stopEpochWithDuration(_lossAmount)`, `previewLossAdjustedWithdrawFunds` computes `pendingLoss = _lossAmount * pendingBasis / totalBasis` over the *full* pending basis — including the older-epoch receipt (lines 454–459). `collectWithdrawFunds` then funds only `pendingBasis - pendingLoss` and stores the haircut under the current `epochNumber` (lines 414–421).
- On claim, `_claimLossAdjustedWithdrawRequest` clears only `withdrawsRequestsByEpoch[user][lastWithdrawRequest]` at the reduced price (lines 789–800); the epoch-N remainder stays in `withdrawsRequests[user]` and is paid **at par** by `_claimFundedWithdrawRequest` once `epochNumber > lastWithdrawRequest` (lines 319–349).
- The funded pool is short by exactly the haircut the older receipt dodged: `pendingLoss * (olderBasis / pendingBasis)`.

### Impact Explanation
Direct insolvency of the funded-claim reserve. An attacker (any KYC'd tranche holder) requests a small withdraw in epoch N, does not claim, requests again in epoch N+1, and a realized borrower loss is applied at stopEpoch. The attacker's epoch-N receipt is redeemed at 100% while the pool was funded assuming it took `lossRecoveryPrice`. The shortfall is socialized onto other pending withdrawers: the last claimers' `claimWithdrawRequest` reverts on insufficient underlying (permanent freezing of unclaimed funds until new money arrives, or theft of their share by early claimers). Quantified loss: `pendingLoss × olderEpochBasis / pendingBasis`, bounded only by the attacker's position size.

### Likelihood Explanation
Requires a `stopEpochWithDuration` loss event (borrower underfunds at stop) plus a user holding receipts across two request epochs — both ordinary, non-privileged conditions. The attacker only needs to keep one stale unclaimed receipt before re-requesting; no privileged role or timing precision is needed. Likelihood is moderate: it triggers whenever a partial loss lands while mixed-epoch receipts exist.

### Recommendation
Track the loss haircut per pending-receipt basis, not per latest request epoch. Either:
- store the loss price against every epoch with outstanding receipts (e.g., iterate/mark `lossRecoveryPriceByEpoch` for all epochs contributing to `pendingWithdraws`, or maintain a global `pendingLossRecoveryPrice` applied to `withdrawsRequests[user]` as a whole), or
- on `requestWithdraw`, force settlement/claim of any older-epoch receipt regardless of loss status so `pendingWithdraws` never spans epochs, and make `_claimLossAdjustedWithdrawRequest` clear all epochs up to `lastWithdrawRequest`.

### Proof of Concept
Foundry fork sketch (setup mirrors `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// Epoch 1 running: attacker deposits, requests withdraw W1 (small).
cdoEpoch.requestWithdraw(W1, address(AAtranche));
// stopEpoch (no loss), epoch 2 starts.
cdoEpoch.stopEpoch(0, 0);
cdoEpoch.startEpoch();
// Attacker requests again W2 (allowed: no lossRecoveryPrice on epoch 1).
cdoEpoch.requestWithdraw(W2, address(AAtranche));
// Honest user requests W3 in epoch 2.
// stopEpochWithDuration with loss L: borrower funds pendingBasis - pendingLoss.
cdoEpoch.stopEpochWithDuration(lossArgs); // lossRecoveryPriceByEpoch[2] = funded/basis
// epoch 3:
// Attacker claims: epoch-2 receipt haircut, epoch-1 receipt W1 paid AT PAR.
cdoEpoch.claimWithdrawRequest();
// Honest user's claim reverts/underpays: pool short by W1 * (1 - lossRecoveryPrice).
vm.expectRevert();
cdoEpoch.claimWithdrawRequest(); // other user
```

Assert `underlying.balanceOf(strategy) < withdrawsRequests[honestUser]` after the attacker's claim.
