### Title
Cross-user response hijacking via attacker-chosen `MessageId` collision in `handler.savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The gateway capabilities handler keys pending user callbacks solely by the client-supplied `MessageId`, and unconditionally overwrites any existing entry for that key without checking if it is already in use. Since `MessageId` is fully attacker-chosen (only length/charset validated, never checked for uniqueness or bound to the request signer beyond the signature over the attacker's own message), an unprivileged gateway client can submit a request using the same `MessageId` as another user's still-pending request and hijack that victim's DON response.

### Finding Description
`HandleLegacyUserMessage` stores the caller's `Callback` in the shared map keyed only by `msg.Body.MessageId`, without checking for an existing entry: [1](#0-0) 

`MessageId` originates directly from the untrusted, client-controlled value. For legacy requests it comes straight from the signed `api.Message.Body.MessageId` field set by the caller; for the JSON-RPC path, `ValidatedMessageFromReq` copies `req.ID` (also attacker-controlled) directly into `m.Body.MessageId`: [2](#0-1) 

`Message.Validate()` only checks length and null-byte constraints on `MessageId`, and derives `Sender` from the signature — but nothing ties `MessageId` uniqueness to `Sender`, and the signature only proves *the sender authored their own message*, not that the `MessageId` is exclusive to them: [3](#0-2) 

When the DON later responds, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageId` from the node response, with no cross-check against the original sender's identity, and delivers the response to whatever callback is currently registered under that key: [4](#0-3) 

Exploit flow:
1. Victim (User B) submits a `web_api_trigger` legacy request with `MessageId = "X"`. The gateway registers `savedCallbacks["X"] = B's callback` and forwards the signed request to DON nodes.
2. Before the DON responds, Attacker (User A) — an unrelated, unprivileged gateway client — submits their own independently-signed request also using `MessageId = "X"` (attacker picks this ID themselves; no server-side uniqueness enforcement exists). The gateway overwrites `savedCallbacks["X"]` with A's callback.
3. When the DON responds to B's original triggered request (the response also carries `MessageId = "X"`, since the gateway forwarded that value to nodes and nodes echo it back), `handleWebAPITriggerMessage` finds A's callback under key `"X"`, deletes it, and delivers **B's DON response payload to A**.
4. B's original callback is orphaned and never receives a response (eventually times out at `callback.Wait` in `gateway.go`).

This is a concrete cross-user response confusion: A receives data intended for B (e.g., HTTP action/target response payloads potentially containing another workflow's data), violating per-request isolation. Nothing in the existing checks (signature verification, `Validate()`, rate limiting, `MaxAllowedMessageAgeSec` staleness check) prevents this, because they all validate the *attacker's own* message is well-formed and signed by the attacker — none of them enforce `MessageId` uniqueness across concurrent users.

### Impact Explanation
An unprivileged gateway user can hijack another user's in-flight capability response (`web_api_trigger`/target/action results), causing data intended for one user's workflow execution to be delivered to an attacker-controlled callback. This matches Chainlink's "unauthorized access to another user's data/response" bounty impact class (cross-user isolation violation within the gateway).

### Likelihood Explanation
Exploitation requires only: (1) network access to the gateway HTTP endpoint (unprivileged client), (2) the ability to sign one's own valid message (any keypair works — no special credential needed), and (3) knowledge/prediction of a colliding `MessageId` used concurrently by another user. Since `MessageId` values in practice can be short, sequential, timestamp-derived, or otherwise guessable/observable (and the field caps at only 128 chars with no server-enforced entropy/uniqueness), collision is practically achievable, especially by racing many candidate IDs against a busy gateway. The bug is deterministic once a collision occurs (`map` overwrite is unconditional), making it reliably repeatable.

### Recommendation
- Reject registration in `savedCallbacks` if a `MessageId` is already active (return an error to the second submitter instead of silently overwriting).
- Scope the callback map key to `(Sender, MessageId)` rather than `MessageId` alone, so collisions across different senders cannot occur.
- When resolving a DON response in `handleWebAPITriggerMessage`, verify the response's sender/DON context matches the original request context stored alongside the callback before delivering the payload.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Create handler via `setupHandler(t)`.
2. Build `msgA` and `msgB`, both legacy `web_api_trigger` messages with identical `MessageId = "collide"`, signed by two different node/test keys (`nodes[0]` and a second distinct key), each with distinct payload content (e.g., different `TriggerEventId`).
3. Call `handler.HandleLegacyUserMessage(ctx, msgB, cbB)` (victim B registers first).
4. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)` (attacker A registers second, same `MessageId`), assert it overwrites `savedCallbacks["collide"]` (no error returned).
5. Simulate the DON responding to B's original request: build the node response derived from `msgB` (same `MessageId`), call `handler.HandleNodeMessage(ctx, respFromMsgB, nodeAddr)`.
6. Assert: `cbA.Wait(ctx)` receives the response payload derived from `msgB` (i.e., attacker gets victim's data) — proving cross-user response confusion — while `cbB.Wait(ctx)` times out/never resolves.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
