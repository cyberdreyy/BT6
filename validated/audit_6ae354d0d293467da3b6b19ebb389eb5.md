### Title
Operator can set delegation pool commission beneficiary to `0x0`, permanently locking accrued commission stake - ([File: aptos-move/framework/aptos-framework/sources/delegation_pool.move])

### Summary
`delegation_pool::set_beneficiary_for_operator` lets an operator set an arbitrary `new_beneficiary` address with no validation, and `beneficiary_for_operator` is read directly whenever commission is credited during pool synchronization. Because delegation-pool commission is not paid via `aptos_account::deposit_coins` (which safeguards against reserved addresses) but instead credited as internal pool shares via `buy_in_active_shares`/`buy_in_pending_inactive_shares`, setting the beneficiary to `0x0` causes commission shares to be permanently and irrecoverably locked inside the pool, since no signer can ever be produced for the reserved `0x0` address to call `unlock`/`withdraw`/`reactivate_stake`.

### Finding Description
`set_beneficiary_for_operator` performs no checks on `new_beneficiary`: [1](#0-0) 

`beneficiary_for_operator` simply returns whatever address is stored, defaulting to the operator itself only if the resource doesn't exist: [2](#0-1) 

During `synchronize_delegation_pool` (called on essentially every user-facing entry point: `add_stake`, `unlock`, `withdraw`, `vote`, `set_operator`, etc.), the operator's commission is minted as internal pool shares directly to `beneficiary_for_operator(operator)`, with no existence or validity check on that address: [3](#0-2) 

Unlike `staking_contract.move`'s `distribute_internal`, which pays commission via `aptos_account::deposit_coins` — a real coin transfer that would actually abort for `0x0`, since `aptos_account::create_account` → `account::create_account` explicitly rejects `@vm_reserved` (`0x0`): [4](#0-3) [5](#0-4) 

...the delegation-pool path never calls `deposit_coins`. It only manipulates an internal `pool_u64::Pool` share ledger keyed by address, so there is no such reserved-address guard. Once shares are minted to `0x0`, any subsequent `unlock`, `reactivate_stake`, or `withdraw` call requires a `&signer` whose address matches the shareholder — but no signer for `0x0` can ever be produced in a user transaction (it is the VM-reserved address). This permanently traps the commission stake with no recovery path (not even the admin/governance can redeem another account's shares in this module).

### Impact Explanation
This satisfies the "Permanent lock or non-recoverable loss of claim rights in stake, delegation, commission, beneficiary, or vesting flows" impact category. Every future commission accrual for that operator (as long as the beneficiary remains `0x0`) is minted as unclaimable shares, permanently removing that value from circulation within the delegation pool's accounting — a real accounting/share-ownership corruption, not merely an event-log or cosmetic issue.

### Likelihood Explanation
`set_beneficiary_for_operator` is a permissionless entry function callable directly by the operator signer with no privileged role required, and no validation is present anywhere in the call path to reject `0x0` (or other unspendable/reserved addresses). Any operator — maliciously or by mistake — can trigger this on the very next `synchronize_delegation_pool` call (which fires automatically on `add_stake`/`unlock`/`vote`/etc.).

### Recommendation
Add a validation in `delegation_pool::set_beneficiary_for_operator` (and the analogous `staking_contract::set_beneficiary_for_operator`, for defense-in-depth even though it currently reverts rather than burns) rejecting `new_beneficiary == @0x0` and other reserved addresses (`@vm_reserved`, `@aptos_framework`, `@aptos_token`), e.g. mirroring the checks already present in `account::create_account`.

### Proof of Concept
1. Operator calls `delegation_pool::initialize_delegation_pool` and becomes the pool operator (`beneficiary_for_operator(operator) == operator` by default per `delegation_pool.move:899-907`).
2. Operator calls `delegation_pool::set_beneficiary_for_operator(operator, @0x0)` — succeeds, no validation (`delegation_pool.move:1272-1291`).
3. Any delegator calls `add_stake`/`unlock`/`vote`, which triggers `synchronize_delegation_pool` → `update_active_shares`-style commission crediting, minting commission shares to `@0x0` via `buy_in_active_shares`/`buy_in_pending_inactive_shares` (`delegation_pool.move:1949-1956`).
4. No transaction can ever produce a `&signer` for `@0x0` to call `unlock`/`withdraw`/`reactivate_stake` on those shares — the commission is permanently locked in the pool.

Note: I could not fully trace `pool_u64::Pool`'s `buy_in_active_shares`/`redeem_active_shares` internals or the exact numeric value/definition of `NULL_SHAREHOLDER` within the tool budget available; if `NULL_SHAREHOLDER` happens to equal a specially-handled sentinel address distinct from `0x0`, that would not change this finding, since it concerns operator-controlled `beneficiary_for_operator`, not the fee-shares mechanism.

```text
    public entry fun set_beneficiary_for_operator(
        operator: &signer,
        new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
        } else {
            move_to(operator, BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary });
        };

        emit(SetBeneficiaryForOperator {
            operator: operator_addr,
            old_beneficiary,
            new_beneficiary,
        });
    }
```
