### Title
Stale confirmations from a removed-then-re-added member still count toward `num_confirmations`, allowing request execution below the true live-confirmer threshold - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` only purges requests that the removed member itself originally created (`r.member == member`), never scrubbing that member's confirmation entries from `confirmations` sets belonging to requests created by *other* members. Because `confirm()` counts raw `HashSet<String>` length against `self.num_confirmations` without checking that every entry still reflects continuous live membership, a member who confirms, gets removed, and is later re-added has their old confirmation silently resurrected and counted, letting a request execute with fewer truly-live re-confirmations than the configured threshold.

### Finding Description
The invariant the contract must maintain is: `confirmations.get(request_id).len() == |{m ∈ self.members : m confirmed request_id while continuously a member}|`, and this value must be `>= self.num_confirmations` before `execute_request` runs.

In `delete_member` [1](#0-0) , the cleanup only targets requests keyed by `r.member == member` (requests the removed member *created*), and only calls `self.num_requests_pk.remove(&member.to_string())`. It never scans `confirmations` maps of requests created by other members to strip `member.to_string()` out of them.

`confirm()` [2](#0-1)  simply checks `confirmations.len() as u32 + 1 >= self.num_confirmations` and, if true, calls `remove_request` and executes — with no re-validation that every string already in `confirmations` still belongs to a member who has been continuously live since confirming.

Exploit flow (2-of-3 multisig with members A, B, C):
1. C creates `request1` (a `Transfer` to an attacker-controlled account), so `request1.member == C`.
2. A confirms `request1` → `confirmations = {A}`.
3. B and C jointly confirm a self-request `DeleteMember{A}` (2-of-3), executing `delete_member(A)`. Since `request1.member == C ≠ A`, `request1`'s confirmations set is untouched and still contains `"A"`.
4. B and C (now the only 2 members, threshold still 2) jointly confirm `AddMember{A}`, re-adding A to `self.members`.
5. B confirms `request1`. `confirms.contains("B")` is false, so it proceeds; `confirmations.len() + 1 == 2 >= num_confirmations(2)` → `remove_request` + `execute_request` fire, moving funds out.

Only B actually confirmed while continuously live around this window; A's counted confirmation is stale from before a live→removed→live gap during which A never re-confirmed. No existing guard (`assert_valid_request`, `assert_self_request`, `current_member()`) checks historical continuity of confirmers already present in the set — `current_member()` [3](#0-2)  only validates the *caller* of the current call, not the other entries already accumulated in `confirmations`.

### Impact Explanation
NEAR can leave the multisig contract account via `Transfer` (or any other action, e.g. `AddKey`/`DeployContract`) with the real threshold of live re-confirmations never reached — one fewer independent, continuously-live confirmation than `num_confirmations` requires. This matches the Critical category "a multisig request executed below `num_confirmations` live members." The bug is repeatable for any request whose creator differs from a member subsequently removed-and-readded, and applies to every multisig instance deployed from this contract.

### Likelihood Explanation
The only precondition is the ordinary governance sequence available to any multisig's own members: confirm a request, then execute a `DeleteMember`+`AddMember` cycle for the confirming member (a legitimate operational pattern, e.g. key rotation). No attacker outside the multisig membership is needed to trigger it — it is a latent correctness bug in the confirmation bookkeeping that surfaces whenever member rotation intersects with a still-pending request, which is a realistic operational scenario (rotating a compromised or lost key while other requests are in flight).

### Recommendation
When removing a member in `delete_member`, iterate over all entries in `confirmations` (not just requests the member created) and remove `member.to_string()` from each set, or alternatively re-validate at `confirm()`-time that every account in `confirmations.get(request_id)` is still (and has been continuously) present in `self.members`, discarding stale entries before counting toward `num_confirmations`.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

            None
