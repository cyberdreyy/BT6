### Title
Withdraw confidential-transfer parser silently reassigns `rangeProofContextStateAccount` (or `equalityProofContextStateAccount`) to `owner`/`multisigOwner` at minimum account-count boundary - (transaction-status/src/parse_token/extension/confidential_transfer.rs)

### Summary
`parse_confidential_transfer_instruction`'s `Withdraw` arm only requires 4 accounts via `check_num_token_accounts(account_indexes, 4)`, but the real per-role layout for the "both proofs use context-state accounts" case needs 5 accounts (`account`, `mint`, `equalityProofContextStateAccount`, `rangeProofContextStateAccount`, `owner`). When exactly 4 accounts are supplied with `equality_proof_instruction_offset == 0` and `range_proof_instruction_offset == 0`, the bounds guard `offset < account_indexes.len().saturating_sub(1)` silently skips inserting `rangeProofContextStateAccount` and the account that should hold that role instead falls through into `parse_signers` and gets labeled `owner`/`multisigOwner`.

### Finding Description
The Withdraw handling walks a shared `offset` cursor through `account_indexes` and conditionally inserts `instructionsSysvar`, `equalityProofContextStateAccount`, and `rangeProofContextStateAccount`, guarded by `offset < account_indexes.len().saturating_sub(1)` to keep the very last account reserved for `parse_signers` (owner/multisig fallback) [1](#0-0) .

With `account_indexes.len() == 4` (the minimum enforced by `check_num_token_accounts(account_indexes, 4)` at line 178) and both `equality_proof_instruction_offset == 0` and `range_proof_instruction_offset == 0` (i.e. attacker chooses both proofs as context-state accounts, `has_sysvar == false`):
- `offset` starts at 2.
- `has_sysvar` is false, so the sysvar branch is skipped.
- Equality branch: `offset(2) < len-1(3)` is true, so `equalityProofContextStateAccount` = `account_keys[account_indexes[2]]`, `offset` becomes 3.
- Range branch: `offset(3) < len-1(3)` is false, so the range-context insertion is skipped entirely — no `rangeProofContextStateAccount` field is produced.
- `parse_signers(map, 3, ...)` then runs with `last_nonsigner_index = 3`; since `account_indexes.len() (4) > last_nonsigner_index+1 (4)` is false, it inserts `owner = account_keys[account_indexes[3]]` [2](#0-1) .

The account at `account_indexes[3]`, which in this offset combination should represent the range-proof context-state account per the real instruction semantics tested in `test_withdraw`'s "All Contexts" case (5-account layout) [3](#0-2) , is instead reported under the `owner` field, and the true role (`rangeProofContextStateAccount`) is dropped from the JSON entirely. The check `check_num_token_accounts(account_indexes, 4)` at line 178 does not scale the minimum account requirement based on the actual offsets decoded from `instruction_data`, so this malformed-but-minimally-valid account count is accepted by the parser [4](#0-3) .

The parser operates purely syntactically on attacker-supplied `instruction_data`/`account_indexes` from a `CompiledInstruction`, with no cross-check against whether the instruction would actually execute successfully on-chain; `getTransaction`/`getConfirmedTransaction` with `jsonParsed` encoding parse instructions regardless of the transaction's execution outcome. An attacker can craft (and land, even if it fails execution due to `NotEnoughAccountKeys` in the real Token-2022 processor) a transaction targeting the real Token-2022 program ID with a `Withdraw` instruction carrying exactly 4 accounts and both proof offsets `== 0`.

### Impact Explanation
This is a decoder misreporting bug: querying such a transaction via `getTransaction`/`getConfirmedTransaction` (jsonParsed) returns a `rangeProofContextStateAccount`-omitting, `owner`-mislabeled JSON payload, where the account genuinely intended (by the offset semantics) to be a range-proof context-state account is reported as the withdrawal `owner`. This falls under Agave's "decoder panic and misreporting" bounty category. Impact is confined to how this specific attacker-crafted transaction is displayed to any RPC client (explorers, indexers, wallets) that requests it; it does not cause consensus-state mutation, crash, or unbounded cost, and no other user's real transaction is affected.

### Likelihood Explanation
Fully reachable by an unprivileged single client: submit one `sendTransaction` call constructing the raw `CompiledInstruction` bytes directly (bypassing the SDK's `inner_withdraw` builder, which would never itself produce this malformed 4-account/both-context-offset combination) and later retrieve it via one `getTransaction` call. The transaction will likely fail execution on-chain (insufficient accounts for the real program logic), but a failed transaction is still recorded in a block and its instructions are still parsed identically by RPC. No parameter-limit/commitment guard prevents this since `check_num_token_accounts` only enforces a flat minimum of 4, independent of the derived proof-offset combination. This is deterministic and repeatable for anyone who understands the offset semantics.

### Recommendation
Compute the minimum required account count for `Withdraw` (and similarly `Transfer`/`TransferWithFee`) dynamically based on `has_sysvar` plus the number of proof offsets equal to `0` (each needing its own context-state account) plus 1 for the owner, and call `check_num_token_accounts` with that computed minimum instead of the flat constant `4`. Alternatively, make each conditional insertion in the offset walk unconditionally required for its role (returning `ParseInstructionError::InstructionNotParsable` if the bound would be violated) rather than silently falling through to `parse_signers`.

### Proof of Concept
```rust
// transaction-status/src/parse_token/extension/confidential_transfer.rs (add to `mod test`)
#[test]
fn test_withdraw_min_accounts_role_confusion() {
    use spl_token_2022_interface::extension::confidential_transfer::instruction::WithdrawInstructionData;

    // Manually build a Withdraw instruction with exactly 4 accounts and both
    // equality/range proof offsets == 0 (both "context state account" mode),
    // which per real semantics (see test_withdraw's "All Contexts" case)
    // requires 5 accounts: account, mint, eq_ctx, range_ctx, owner.
    let account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let range_ctx_masquerading_as_owner = Pubkey::new_unique(); // attacker-chosen 4th account

    let withdrawal_data = WithdrawInstructionData {
        amount: 42.into(),
        decimals: 9,
        new_decryptable_available_balance: Default::default(),
        equality_proof_instruction_offset: 0,
        range_proof_instruction_offset: 0,
    };
    let mut data = vec![ConfidentialTransferInstruction::Withdraw as u8];
    data.extend_from_slice(bytemuck::bytes_of(&withdrawal_data));

    let instruction = Instruction {
        program_id: spl_token_2022_interface::id(),
        accounts: vec![
            AccountMeta::new(account, false),
            AccountMeta::new_readonly(mint, false),
            AccountMeta::new_readonly(Pubkey::new_unique(), false), // pretend eq ctx
            AccountMeta::new_readonly(range_ctx_masquerading_as_owner, false), // should be range ctx
        ],
        data,
    };

    let message = Message::new(&[instruction], None);
    let parsed = parse_token(
        &message.instructions[0],
        &AccountKeys::new(&message.account_keys, None),
    )
    .unwrap();

    // Bug: rangeProofContextStateAccount is missing entirely...
    assert!(parsed.info.get("rangeProofContextStateAccount").is_none());
    // ...and the account is mislabeled as "owner" instead.
    assert_eq!(
        parsed.info["owner"],
        json!(range_ctx_masquerading_as_owner.to_string())
    );
}
```
Expected result: the assertions pass, demonstrating that the account intended (by offset semantics) as `rangeProofContextStateAccount` is misreported under the `owner` field and the true role field is silently omitted, confirming the parse-fidelity violation at the 4-account boundary.

```rust
fn parse_signers(
    map: &mut Map<String, Value>,
    last_nonsigner_index: usize,
    account_keys: &AccountKeys,
    accounts: &[u8],
    owner_field_name: &str,
    multisig_field_name: &str,
) {
    if accounts.len() > last_nonsigner_index + 1 {
        let mut signers: Vec<String> = vec![];
        for i in accounts[last_nonsigner_index + 1..].iter() {
            signers.push(account_keys[*i as usize].to_string());
        }
        map.insert(
            multisig_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
        map.insert("signers".to_string(), json!(signers));
    } else {
        map.insert(
            owner_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
    }
}
```
