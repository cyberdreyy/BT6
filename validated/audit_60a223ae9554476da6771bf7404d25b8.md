### Title
No refund path in `MultisigFactory::create` — failed multisig deployment silently consumes attached deposit - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` schedules a single promise batch (`create_account` → `deploy_contract` → `transfer` → `function_call("new", ...)`) and returns it directly with no `.then()` callback to itself. Unlike the sibling `lockup-factory` and `staking-pool-factory` crates, which both attach an `on_..._create` callback that checks `is_promise_success()` and refunds the predecessor on failure, the multisig factory has no such mechanism, so if the `new` call on the freshly created sub-account fails (e.g., invalid `members`, invalid `num_confirmations`, or insufficient gas for `new`), the attached deposit remains stranded on the (potentially half-initialized) new account and is never returned to the caller.

### Finding Description
The invariant under test is: `predecessor_balance_after_failed_create == predecessor_balance_before_create` (net of gas), i.e., a failed deployment must refund the attached deposit to the caller. In `MultisigFactory::create`: [1](#0-0) 

the promise chain does `create_account()`, `deploy_contract(CODE)`, `transfer(env::attached_deposit())`, then `function_call(b"new", ...)`, and the whole chain is returned as-is with no `.then(ext_self::on_..._create(...))`. Contrast this with `staking-pool-factory/src/lib.rs`'s `create_staking_pool`, which does the equivalent chain but adds: [2](#0-1) 

and its callback `on_staking_pool_create` which calls `is_promise_success()` and, on failure, executes `Promise::new(predecessor_account_id).transfer(attached_deposit.0)`: [3](#0-2) 

`lockup-factory/src/lib.rs` follows the identical pattern with `on_lockup_create`: [4](#0-3) 

The multisig factory has no such callback anywhere in the crate — there is no `is_promise_success` or `assert_self` usage in `multisig-factory/src/`, confirmed by search. Any unprivileged attacker (or even an honest caller who makes a mistake) calling `create` with a `new`-call-failing configuration (e.g., empty `members`, a `num_confirmations` value that fails multisig2's internal validation in its `new` constructor, or a `name` that collides with an existing account) will have the account created, funded via `transfer`, and then have `new` fail — with the deposit permanently stuck on that account with no owner/keys able to move it out (since `new` never completed to set up any access), or at minimum diverging from the caller's expectation with no automatic recovery.

None of the standard guards (`assert_self`, `is_promise_success`, `assert_one_yocto`, etc.) are present in this file to intervene, because there is no callback function at all to run them in.

### Impact Explanation
The attached NEAR deposit that the caller intended to fund a new multisig account with is consumed/stranded when `new` fails, with no automatic path back to the caller. This matches the "accounting value diverges from reality and another party settles on it" / funds-frozen-or-lost High impact category: the caller's balance decreases by the deposit amount while no corresponding multisig account with usable access exists to compensate, and there is no owner or privileged actor who can trigger a refund since the factory contract itself has no refund logic. This is repeatable by any caller across any number of `name` values.

### Likelihood Explanation
The attacker (or an ordinary user) needs only to call `create` with a deposit and any input that causes `new` to fail on the deployed multisig2 contract, or ensure `new`'s prepaid gas (`env::prepaid_gas() - CREATE_CALL_GAS`) is insufficient. This requires no special privileges — it's directly reachable by the public, payable `create` entrypoint, and is easy to trigger unintentionally as well as deliberately.

### Recommendation
Add an `ext_self` callback analogous to `on_lockup_create` / `on_staking_pool_create`: chain `.then(ext_self::on_multisig_create(predecessor_account_id, attached_deposit, &env::current_account_id(), NO_DEPOSIT, CALLBACK_GAS))` after the `function_call`, and implement the callback with `assert_self()` + `is_promise_success()` check that refunds `attached_deposit` to `predecessor_account_id` via `Promise::new(...).transfer(...)` when the `new` call failed.

### Proof of Concept
Using `near-sdk`'s `testing_env!`/`PromiseResult` pattern as done in `lockup-factory`'s `test_create_lockup_rollback` and `staking-pool-factory`'s `test_create_staking_pool_rollback`:
1. Set up `VMContextBuilder` with `predecessor_account_id = attacker`, `attached_deposit = X`.
2. Call `MultisigFactory::create(name, members, num_confirmations)`, capturing the returned `Promise`.
3. Simulate the promise result as `PromiseResult::Failed` for the `new` call (i.e., what `staking-pool-factory` does before calling its callback).
4. Assert: there is no callback method available to invoke on `MultisigFactory` to trigger a refund (attempt to call any `on_*` method — none exists), and thus `attacker`'s balance is never restored — contrasted directly against `lockup-factory::on_lockup_create`/`staking-pool-factory::on_staking_pool_create` which explicitly `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` on `PromiseResult::Failed`.
5. This demonstrates the binding `predecessor_balance_after == predecessor_balance_before - gas_fees_only` is violated: after a failed `new` call, the predecessor's balance is `predecessor_balance_before - deposit - gas_fees`, with no compensating transfer, unlike its sibling factories.
