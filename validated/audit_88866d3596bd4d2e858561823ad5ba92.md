### Title
Loss-adjusted withdraw receipts in a non-latest epoch are paid again at par by `_claimFundedWithdrawRequest` — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary

The null_blk bug is a request processed by two competing paths: `null_poll()` detaches the request outside the lock, so `null_timeout_rq()` processes the same request again because completion was never marked atomically. The fix marks the request `MQ_RQ_COMPLETE` under `poll_lock` so the second path sees it and returns early.

The same pattern exists in `IdleCreditVault.claimWithdrawRequest` (`IdleCreditVault.sol:301-314`): one receipt can be consumed by multiple claim paths, and the loss-adjusted path only marks the receipt complete when the receipt's epoch equals `lastWithdrawRequest[_user]`. A loss-adjusted receipt from an *earlier* epoch is never marked, stays inside the `withdrawsRequests` aggregate, and is paid a second time at par by `_claimFundedWithdrawRequest`.

### Finding Description

When a `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` (`IdleCreditVault.sol:411-430`) funds only `_amount < pendingBasis`, zeroes `pendingWithdraws`, and stores the haircut in `lossRecoveryPriceByEpoch[epochNumber]`. Users later recover the reduced amount via `_claimLossAdjustedWithdrawRequest` (`IdleCreditVault.sol:789-801`), which:

1. Reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — i.e., only the epoch of the **latest** request.
2. Calls `_clearWithdrawClaimForEpoch` (`IdleCreditVault.sol:811-837`), which subtracts that epoch's piece from `withdrawsRequests[_user]` — this is the "complete" marker.

Now sequence a user with requests in two epochs:

- Epoch N: user calls `requestWithdraw` → `withdrawsRequests[user] += X`, `withdrawsRequestsByEpoch[user][N] += X`, `lastWithdrawRequest[user] = N`.
- `stopEpochWithDuration` realizes a loss → `lossRecoveryPriceByEpoch[N] = price < RECOVERY_FULL`, only `X * price` underlying is collected.
- Epoch N+1: user deposits again and calls `requestWithdraw` → `withdrawsRequestsByEpoch[user][N+1] += Y`, `lastWithdrawRequest[user] = N+1`.
- Epoch N+1 ends fully funded.
- User calls `claimWithdrawRequest`:
  - `_claimLossAdjustedWithdrawRequest`: looks up `lossRecoveryPriceByEpoch[N+1] == 0` → **returns early, never clears epoch N**.
  - `_claimFundedWithdrawRequest`: the only gate is `epochNumber <= lastWithdrawRequest[user]` (now satisfied), and it pays `amount = withdrawsRequests[user]` — the **aggregate including the epoch-N receipt X at par** — via `_transferFundedClaim`.

The epoch-N receipt was only ever funded at `X * price`, but is paid `X`. Analogous to the kernel fix, the "completed" flag (`withdrawsRequestsByEpoch`/`withdrawsRequests` decremented) is only set on the loss path keyed to the latest request; the stale receipt is double-processed by the funded path.

### Impact Explanation

Direct theft / insolvency. The attacker over-claims `(1 - lossRecoveryPrice) * X` underlying from the strategy's funded pool, which is backed by *other* users' funded withdrawal receipts. `_transferFundedClaim` (`IdleCreditVault.sol:897-907`) explicitly guards `defaultRecoveryReserve`, but there is no guard isolating other users' funded claims, so the over-payment succeeds and later honest claimants' `claimWithdrawRequest` calls revert on insufficient balance — permanent loss up to the haircut size. With a 50% loss haircut and a large epoch-N request, the attacker steals half the request value in a single transaction.

### Likelihood Explanation

- Attacker is an ordinary KYC-passing lender (in scope); no privileged role misbehaves.
- Requires a `stopEpochWithDuration` loss — a legitimate, honest-manager path for realized borrower losses, reachable whenever the borrower underpays at stop.
- Requires the attacker to hold or deposit tranche tokens to submit a second request in a later epoch — routine.
- No existing guard stops it: `withdrawsRequestsByEpoch` clearing is epoch-scoped to `lastWithdrawRequest`, `_transferFundedClaim` only protects `defaultRecoveryReserve`, and `lastWithdrawRequest = 0` clearing in `_clearWithdrawClaimForEpoch` never runs for the stale epoch.
- Uncertainty: epoch numbering alignment between `lastWithdrawRequest` (set at request time) and the key used by `collectWithdrawFunds` (`epochNumber` at funding time) should be verified in the PoC; if they diverge the single-request loss path would itself be broken, which tests suggest is not the case.

### Recommendation

Track loss-adjusted receipts so they cannot be re-claimed at par. Concretely:

- In `_claimLossAdjustedWithdrawRequest`, iterate/check all epochs with `withdrawsRequestsByEpoch[_user][e] != 0` that have a non-zero `lossRecoveryPriceByEpoch[e]`, not only `lastWithdrawRequest[_user]`; or
- When `collectWithdrawFunds` applies a haircut, move the affected per-epoch basis out of `withdrawsRequests`/`withdrawsRequestsByEpoch` into a dedicated `lossAdjustedClaimsByEpoch[user][epoch]` bucket, so `_claimFundedWithdrawRequest` can never include it; and
- Revert in `requestWithdraw` (or force-claim) if the user still has an uncleared loss-adjusted receipt, the same way `null_timeout_rq` early-returns on `MQ_RQ_COMPLETE`.

### Proof of Concept

Foundry fork PoC (against a mainnet fork with the deployed `IdleCDOEpochVariant` + `IdleCreditVault`, mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testLossEpochReceiptDoublePaidAtPar() external {
    // Setup: attacker is a KYC'd lender with AA tranches
    uint256 depositAmount = 1_000_000 * ONE_SCALE;
    idleCDO.depositAA(depositAmount); // attacker tranches

    // Epoch 0 -> 1 transition; attacker requests withdraw of half position
    _startEpochAndCheckPrices(0);
    uint256 tranches = IERC20(AAtranche).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(tranches / 2, address(AAtranche));
    // withdrawsRequestsByEpoch[attacker][1] = X ; lastWithdrawRequest = 1

    // stopEpochWithDuration: borrower underfunds -> realized loss
    // e.g. pendingBasis = X, borrower funds only X/2
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _fundBorrowerPartial(pendingBasis / 2);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(loss, ...); // lossRecoveryPriceByEpoch[1] = RECOVERY_FULL/2

    // New epoch: attacker deposits fresh underlying and requests again
    _startEpochAndCheckPrices(1);
    idleCDO.depositAA(depositAmount); // attacker deposits again
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(newTranches, address(AAtranche));
    // lastWithdrawRequest = 2 ; withdrawsRequests aggregates X + Y

    // Epoch 2 ends fully funded
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _fundBorrowerFully();
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Claim: loss path early-returns (lossRecoveryPriceByEpoch[2] == 0),
    // funded path pays withdrawsRequests[attacker] = X + Y at par,
    // but only (X * price + Y) was ever funded.
    uint256 balBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balBefore;

    uint256 funded = X * strategy.lossRecoveryPriceByEpoch(1) / RECOVERY_FULL + Y;
    assertGt(paid, funded); // over-claim == theft
    // Subsequent honest claimant reverts: vault underfunded.
}
```

Expected result: `paid > funded` by `(1 - lossRecoveryPriceByEpoch[1]) * X`, and a second user's claim on the same funding pool reverts with insufficient underlying, confirming insolvency/theft of other claimants' funds.
