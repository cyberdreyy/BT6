### Title
Underlying ERC4626 vault withdrawal revert blocks all tranche withdrawals and locks lender funds - (File: contracts/strategies/ERC4626Strategy.sol)

### Summary
`ERC4626Strategy._redeem` issues a raw `IERC4626(strategyToken).redeem(...)` call with no liquidity check, no partial-withdrawal handling, and no try/catch. This is the idle-tranches analog of the Derby/Yearn `maxLoss` finding: when the wrapped ERC4626 vault (MetaMorpho, Morpho supply vault, Gearbox, Ethena sUSDe, Amphor, Instadapp Lite — all subclasses of `ERC4626Strategy`) cannot satisfy the redemption, the call reverts and propagates through `IdleCDO._liquidate` → `IdleCDO._withdraw`, reverting the entire `withdrawAA`/`withdrawBB` transaction. Any withdrawal that exceeds the unlent buffer is then impossible until external liquidity returns, with no user-side escape path (burn would have happened inside the same reverting call, so nothing is lost permanently, but funds are frozen).

### Finding Description
The withdrawal path is:

- `IdleCDO._withdraw` computes `toRedeem` and, when the unlent balance is insufficient, calls `_liquidate(toRedeem - balanceUnderlying, revertIfTooLow)` at `contracts/IdleCDO.sol:495-499`. [1](#0-0) 
- `_liquidate` calls `IIdleCDOStrategy(strategy).redeemUnderlying(_amount)` and only tolerates a *shortfall* when `_revertIfNeeded == false` — it does nothing about a *reverting* downstream call. [2](#0-1) 
- `ERC4626Strategy.redeemUnderlying` converts the underlying amount to shares via `convertToShares` and calls `_redeem`, which transfers shares in and calls `IERC4626(strategyToken).redeem(_shares, msg.sender, address(this))` directly. [3](#0-2) 

Per the ERC4626 spec itself, `redeem`/`withdraw` **MUST revert** if the requested assets exceed the vault's withdrawal limit (`maxWithdraw`/`maxRedeem`). MetaMorpho vaults built on Morpho Blue can have all liquid assets borrowed; Gearbox dTokens, sUSDe cooldown mechanics, and credit-line vaults can likewise impose withdrawal constraints. There is no `maxWithdraw`/`maxRedeem` pre-check and no try/catch anywhere in this path, so a single vault with exhausted liquidity freezes every tranche withdrawal larger than the IdleCDO's unlent buffer.

Notably, the codebase already treats this exact failure mode as real elsewhere: `ProgrammableBorrower.onStopEpoch` wraps `vault.withdraw` in try/catch and reverts with a retryable `StopEpochVaultLiquidityUnavailable` precisely because "only an otherwise-covered ERC4626 withdrawal failure should make stopEpoch retryable." [4](#0-3)  The same protection is missing on the user-facing redemption path in `ERC4626Strategy`.

### Impact Explanation
All `withdrawAA`/`withdrawBB` calls whose amount exceeds the contract's unlent token balance revert while the underlying ERC4626 vault is illiquid or capped. Tranche holders' funds (the portion lent into the vault, i.e., ~100% minus `unlentPerc`) are frozen — a temporary freeze of user funds that can persist as long as the underlying vault remains illiquid, and resolves only when external liquidity returns or owner governance action (strategy replacement) is taken. For Morpho-backed vaults, an unprivileged borrower draining the last Morpho market liquidity makes the freeze externally triggerable.

### Likelihood Explanation
Medium. It requires the wrapped vault to hit a withdrawal limit — e.g., a MetaMorpho vault whose Morpho markets are fully borrowed, or a vault under redemption caps. This is a normal market state for lending vaults (high utilization) and needs no privileged action; any third-party borrower on the underlying market can induce it. Historical Morpho utilization spikes make this a realistic condition.

### Recommendation
In `ERC4626Strategy._redeem` / `redeemUnderlying`, clamp the share amount to `IERC4626(strategyToken).maxRedeem(address(this))` (and/or `maxWithdraw`) before calling `redeem`, so a partial redemption returns what is available and lets `_liquidate`'s existing tolerance logic decide whether to revert. Optionally wrap the external `redeem` in try/catch and return `0`/partial on failure so the CDO can still pay out from unlent balance rather than bricking the entire withdrawal.

### Proof of Concept
A reproducible Foundry fork test would: (1) deploy/use an existing `MetaMorphoStrategy` + `IdleCDO` on a mainnet fork; (2) deposit AA tranche funds and harvest so underlying is lent into the MetaMorpho vault; (3) from an unprivileged address, borrow all available liquidity from the Morpho Blue markets backing the vault (or simulate `maxWithdraw(idleCDO) == 0` via a mock ERC4626 with a `withdrawLimit` knob, mirroring `MockStopEpochLiquidityVault` in `test/foundry/ProgrammableBorrowerCreditVault.t.sol:372-399`); (4) call `idleCDO.withdrawAA(0)` with an amount exceeding the unlent buffer and observe the revert inside `ERC4626Strategy._redeem`, even with `revertIfTooLow == false`; (5) show the withdrawal succeeds again only after liquidity is repaid — demonstrating temporary freezing of lender funds caused by an external withdrawal revert.

Uncertainty note: I verified the call chain and the absence of guards in `ERC4626Strategy`, but I did not confirm which specific deployed strategies are currently considered non-legacy/in-scope; if `MetaMorphoStrategy`/`MorphoSupplyVaultStrategy` deployments are classified as legacy, the in-scope impact narrows to the other `ERC4626Strategy` subclasses (Gearbox, Ethena, Amphor, Instadapp Lite, Truefi credit line) that share the identical unguarded `_redeem` path.
