### Title
`PosixShellEscape` fails to quote several shell metacharacters, enabling command injection via job variables when `FF_POSIXLY_CORRECT_ESCAPES` is active - (File: `helpers/shell_escape.go`)

### Summary
`PosixShellEscape` (`helpers/shell_escape.go:98-126`) only treats a subset of shell metacharacters as quote-triggering, unlike `ShellEscape`'s `modeTable`. Characters such as `;`, `:`, `+`, `]`, `^`, `{`, `}`, `~`, and `'` are absent from `posixModeTable` (`helpers/shell_escape.go:90-95`), so a string composed only of "safe" alphanumerics plus these unlisted metacharacters is emitted completely unquoted by `PosixShellEscape`. When `BashWriter.escape` (`shells/bash.go:447-453`) routes through this path (controlled by the `usePosixEscape`/`FF_POSIXLY_CORRECT_ESCAPES` feature flag set in `NewBashWriter`, `shells/bash.go:115-128`), attacker-controlled CI/CD variable values containing a lone `;` can break out of their intended single-token context (e.g. `export KEY=VALUE`) and inject additional shell statements into the generated bash script.

### Finding Description
`ShellEscape`'s `modeTable` (`helpers/shell_escape.go:26-48`) marks `;`, `:`, `+`, `]`, `^`, `{`, `}`, `~` as `quo` (quote-triggering), ensuring any string containing them is wrapped in `$'...'`. `PosixShellEscape`'s `posixModeTable` (`helpers/shell_escape.go:90-95`) omits all of these characters from both its `quo` list and its backslash-escape list. In the escaping loop (`helpers/shell_escape.go:107-119`), any byte whose table entry is the empty string (`""`, i.e. not present in the table at all) is written through literally via `case "": sb.WriteByte(c)`, and critically does **not** set `escape = true`. The function only wraps the output in double quotes if `escape` was set (`helpers/shell_escape.go:121-123`).

Consequently, a value such as `;id;` — consisting solely of letters and semicolons, neither of which appear in `posixModeTable` — produces the literal output `;id;` with **no surrounding quotes at all**, whereas `ShellEscape` on the same input correctly returns `$';id;'`.

This function is reached through `BashWriter.escape` (`shells/bash.go:447-453`), which is used pervasively, including in `BashWriter.Variable` (`shells/bash.go:229-241`) to emit `export %s=%s` lines from job/pipeline CI/CD variable values. `usePosixEscape` is set once per build from the `FF_POSIXLY_CORRECT_ESCAPES` feature flag (`shells/bash.go:121`), so once that flag is enabled (e.g., via a `.gitlab-ci.yml` `variables:` entry naming the flag, a common mechanism for `FF_*` runner feature flags), every `Variable()` call in the script uses the vulnerable code path consistently — the inconsistency is not within one script but between builds run with the flag on vs. off, and the "on" path is unsafe.

Given a job variable value of `;touch/tmp/pwned;` (no spaces or other quo-triggering characters), the generated line becomes:
```
export KEY=;touch/tmp/pwned;
```
which bash parses as three statements: `export KEY=` (empty), `touch/tmp/pwned` (a no-argument-looking but actually a single word — for a true multi-argument injection an attacker is limited to metacharacters not in either escape table, but a semicolon alone is sufficient to inject a second no-space command, e.g. `;env;` to dump the process environment, including secrets, into the job trace).

No other layer (masking, path validation, image checks) mitigates this: masking only redacts known secret literal values in trace output, not attacker-crafted commands, and there is no other validation of variable values before they are embedded into the generated shell script.

### Impact Explanation
An unprivileged pipeline author who can set a CI/CD variable value (a job variable is fully attacker-controlled input) can inject additional shell statements into the generated build script whenever the runner/build has `FF_POSIXLY_CORRECT_ESCAPES` enabled. This breaks the invariant that job variable values are treated as opaque data rather than executable script fragments, and can be used to exfiltrate other job's exported environment (via `env`), tamper with build state, or chain further no-argument commands available on `PATH`. While the character set usable without triggering quoting is limited (no spaces, `$`, `<`, `>`, quotes, parens), a bare `;` is enough to terminate the `export` statement and start injecting the next command name.

### Likelihood Explanation
This bug is only reachable when the `PosixlyCorrectEscapes` feature flag is turned on for the build (`shells/bash.go:121`, `helpers/featureflags/flags.go`). I could not verify within the available context whether this flag defaults to on/off or whether it is settable per-job via a `.gitlab-ci.yml` `variables:` block (as many `FF_*` runner flags are) versus being restricted to `config.toml`. If it is user-settable per-pipeline, the exploit is trivially and repeatably triggerable by any pipeline author with no other privileges. If it is a runner-operator-only setting, exploitability requires that setting to already be enabled, making it a latent bug rather than an attacker-triggerable one on default configurations.

### Recommendation
Add the missing metacharacters (`;`, `:`, `+`, `]`, `^`, `{`, `}`, `~`, `'`) to `posixModeTable` as `quo` entries (or equivalent backslash-escaped entries) so any string containing them is always quoted/escaped, matching the safety guarantees of `ShellEscape`. Add a fuzz/property test asserting that `PosixShellEscape(s)` never returns `s` unmodified/unquoted when `s` contains any ASCII punctuation character.

### Proof of Concept
```go
package helpers

import "testing"

func TestPosixShellEscape_SemicolonInjection(t *testing.T) {
    input := ";id;"
    out := PosixShellEscape(input)
    // BUG: currently returns ";id;" unquoted (identical to input),
    // which when embedded as `export KEY=` + out produces a shell
    // script that executes `id` as a separate statement.
    if out == input {
        t.Fatalf("PosixShellEscape failed to quote metacharacter ';': got unquoted output %q", out)
    }
}
```
Integration-level PoC: create a build with `FF_POSIXLY_CORRECT_ESCAPES=true` (or the flag enabled at runner config), define a job variable `INJECT=";touch /tmp/pwned;"`, and inspect the generated script from `BashShell.GenerateScript` — assert that the resulting `export INJECT=...` line does not contain an unquoted, unescaped `;` that would be parsed as a statement separator by bash.
