### Title
Front-runnable one-time global FeeState initialization allows attacker to seize `global_fee_admin` and pause/fee authority - ([File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs])

### Summary
`init_global_fee_state` (handler `initialize_fee_state`) creates the singleton `FeeState` PDA and sets `global_fee_admin`/`global_fee_wallet` from caller-supplied arguments, with no check restricting who may call it. Because this is a "runs once per program" instruction using `init` on a PDA derived only from a constant seed, whoever's transaction lands first permanently claims the `global_fee_admin` role. This exactly matches the reported bug class: an initializer for a critical, singleton system component that can be front-run in its own (separate) transaction, silently handing control to an attacker.

### Finding Description
The instruction accounts struct only requires an arbitrary `payer: Signer`, with no `has_one`, hardcoded pubkey, or upgrade-authority check tying the call to the legitimate deployer: [1](#0-0) 

The handler sets `fee_state.global_fee_admin = admin_key` and `fee_state.global_fee_wallet = fee_wallet` directly from caller-controlled instruction arguments: [2](#0-1) 

The `FEE_STATE_SEED` PDA is deterministic and public (used everywhere, e.g. bank creation and group init reference `seeds = [FEE_STATE_SEED.as_bytes()]`), so any observer can compute its address ahead of time and race to submit an `init_global_fee_state` transaction with their own pubkey as `admin_key` before the legitimate deployer's transaction lands: [3](#0-2) 

Since the account is created via Anchor's `init` constraint, once claimed it can never be re-initialized by the real deployer — the legitimate `init_global_fee_state` call will simply fail with an "account already in use" error, permanently locking the attacker in as `global_fee_admin`.

### Impact Explanation
Owning `global_fee_admin` grants durable, high-value protocol control, as documented in the permissions guide: [4](#0-3) 

Concretely, the attacker-controlled `global_fee_admin` can:
- Redirect all protocol fees to an attacker wallet and set arbitrary fee rates via `edit_fee_state` (`has_one = global_fee_admin`): [5](#0-4) 
- Invoke `panic_pause`/`panic_unpause` to freeze the entire protocol at will (subject to rate limits), since these also gate on `has_one = global_fee_admin`: [6](#0-5) 
- Set/clear the `pause_delegate_admin`, extending pause-triggering control to another attacker-controlled key.

This is a genuine, durable authorization bypass with direct financial effect (fee redirection) and a durable freeze/DoS capability (unauthorized pause control) over the whole protocol, not merely a reputational or "no impact" issue.

### Likelihood Explanation
The likelihood depends entirely on operational discipline: if the deployer bundles `init_global_fee_state` in the same atomic transaction as program deployment/verification (as the test fixtures in this repo do, batching `init_fee_state_ix` with group init instructions in one transaction), front-running is not possible. However, the instruction itself provides no on-chain enforcement of this discipline — there is no `#[account(address = HARDCODED_DEPLOYER)]`, environment/network gate, or similar guard. If deployment tooling or a manual multi-step rollout ever calls this instruction in isolation (as the external report shows happened historically with comparable "runs once" initializers in other codebases), any observer watching the mempool/leader schedule for the marginfi program ID can win the race by submitting a competing transaction with a higher priority fee.

### Recommendation
Add an explicit authorization check to `InitFeeState`/`initialize_fee_state` so it cannot be claimed by an arbitrary signer:
- Require the `payer`/caller to match a hardcoded, compile-time deployer pubkey (or the program's upgrade authority, checked via the `BPFLoaderUpgradeable` program data account), similar to patterns used elsewhere in the codebase for privileged one-time setup.
- Alternatively, restrict this instruction to only be callable in the same transaction as program initial deployment (not generally enforceable on Solana), or require an existing trusted PDA/config (e.g., verify against `id_crate::ID`'s known upgrade authority) before allowing `global_fee_admin` to be set.
- As defense in depth, emit a clear post-deploy verification step that checks `FeeState.global_fee_admin` matches the intended admin immediately after deployment, and treat any mismatch as a critical incident requiring a fresh program deployment.

### Proof of Concept
1. Attacker monitors mempool / precomputes `FEE_STATE_SEED` PDA address for the marginfi program (deterministic, derivable by anyone from `marginfi::ID` and the public constant seed).
2. Immediately after (or in anticipation of) the marginfi program's deployment/upgrade, before the legitimate deployer submits their `init_global_fee_state` transaction, attacker submits their own transaction calling `init_global_fee_state` with:
   - `admin = attacker_pubkey`
   - `fee_wallet = attacker_wallet`
   - arbitrary fee parameters.
3. Because `fee_state` uses `init` with a deterministic PDA and no caller-restriction, the attacker's transaction succeeds first, and the `FeeState` account is now owned by the attacker.
4. The legitimate deployer's subsequent `init_global_fee_state` transaction fails (`already in use`), permanently locking the attacker in.
5. Attacker calls `edit_fee_state` to redirect `global_fee_wallet` to their own wallet and/or calls `panic_pause` to freeze the entire protocol, using the now-legitimate `has_one = global_fee_admin` checks in their favor.

## Global Fee Admin

The `global_fee_admin` is separate from the group-level admin roles. It is stored on the `FeeState`
account (a global singleton).

**Can do:**
- Edit global fee parameters (program fee rates, origination fee shares, init fees)
- Change the global fee wallet
- Set or clear the dedicated pause delegate admin
- Panic-pause the entire protocol (with rate limiting: max 4 consecutive pauses, max 3 per day,
  each lasting 6 hours)

This role is intended for the protocol operator (e.g. the foundation) and controls protocol-level
economics and emergency pause functionality.
