## Confirmed via `apply_withdrawals` (specs/gloas/beacon-chain.md:1920-1932)

`apply_withdrawals` resolves a `Withdrawal.validator_index` back to a *builder slot* by `is_builder_index`/`convert_validator_index_to_builder_index` and mutates whatever `Builder` currently sits at that slot — it never checks that the builder occupying the slot is still the one the withdrawal was created for:

```python
def apply_withdrawals(state: BeaconState, withdrawals: Sequence[Withdrawal]) -> None:
    for withdrawal in withdrawals:
        if is_builder_index(withdrawal.validator_index):
            builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
            builder_balance = state.builders[builder_index].balance
            state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
``` [1](#0-0) 

### Title
Reused `builder_index` slot lets a stale `builder_pending_withdrawals` entry drain a *new* builder's balance and pay it to the exited builder's `fee_recipient` - ([File: specs/gloas/beacon-chain.md])

### Summary
`state.builder_pending_withdrawals` entries are keyed only by a positional `builder_index` (analogous to the `_marketWeightsByToken[token][market]` mapping in the referenced report). `get_index_for_new_builder` allows that same index to be reassigned to a brand‑new builder once the previous occupant's `balance == 0` and `withdrawable_epoch <= current_epoch`, but nothing purges or re-validates queued `BuilderPendingWithdrawal`/`BuilderPendingPayment` entries that still reference that index. When such a stale entry is later processed, `apply_withdrawals` blindly decreases `state.builders[builder_index].balance` — now the *new* builder's balance — and pays the withdrawal amount to the old builder's `fee_recipient`.

### Finding Description
`get_index_for_new_builder` only checks the `Builder` record itself:
```python
def get_index_for_new_builder(state: BeaconState) -> BuilderIndex:
    for index, builder in enumerate(state.builders):
        if builder.withdrawable_epoch <= get_current_epoch(state) and builder.balance == 0:
            return BuilderIndex(index)
    return BuilderIndex(len(state.builders))
``` [2](#0-1) 

It does not check whether `state.builder_pending_withdrawals` (or unsettled `builder_pending_payments`) still contains an entry whose `builder_index` equals this slot. The spec's own note acknowledges index reuse as an intended pattern but only warns about *pubkey* caching, not about outstanding withdrawal entries:
"Builder indices are reusable. When a builder exits, its index may later be reassigned to a different builder with a new public key. Any deposit sent to an exited builder will be withdrawn to the builder's execution address... Implementations that rely on caching should account for this behavior." [3](#0-2) 

A builder can reach `balance == 0` while a pending withdrawal for it is still queued and unprocessed, because:
1. `get_builders_sweep_withdrawals` withdraws the builder's *full* balance to zero as soon as `withdrawable_epoch <= epoch` (independent of the separate `builder_pending_withdrawals` queue) — [4](#0-3) .
2. `builder_pending_withdrawals` is a FIFO capped at `MAX_WITHDRAWALS_PER_PAYLOAD - 1` processed per block [5](#0-4) , so an entry referencing that builder's index can sit unprocessed for many blocks/epochs while other unrelated pending withdrawals are drained ahead of it.
3. Once `balance == 0` and `withdrawable_epoch <= current_epoch`, `process_builder_deposit_request`/`add_builder_to_registry` can immediately place a brand-new builder (new pubkey, fresh balance) at that same index via `set_or_append_list` [6](#0-5) .
4. When the stale `builder_pending_withdrawals` entry (or a late-settling `builder_pending_payments` entry — see `settle_builder_payment` appending to the same queue, [7](#0-6) ) is finally processed, `apply_withdrawals` decreases the *new* builder's balance and the withdrawal is paid to `fee_recipient`, which was fixed at creation time to the **old** builder's payee.

This breaks the invariant that a builder's Gwei can only be withdrawn as a result of that specific builder's own committed payments — Gwei is destroyed from the new builder's stake and paid to an address the new builder never authorized.

### Impact Explanation
This is a builder-payment misdirection: Gwei is removed from one builder's balance and paid to an unrelated address, exactly the "builder payment or withdrawal misdirected" High-impact category. It requires no majority stake or coalition — any single deposit racing against a slow-draining pending-withdrawal queue for a swept slot can trigger it.

### Likelihood Explanation
Requires a specific timing window: a builder must be swept to zero balance (satisfying reuse eligibility) while an older `builder_pending_withdrawals`/settled-payment entry for that same index is still unprocessed in the queue, and a new builder deposit must land before that entry drains. Given `builder_pending_withdrawals` is a large (`2^20`), block-rate-limited FIFO and slot reuse only requires `balance == 0` with no cross-check against the pending queues, this is plausible under normal network conditions with many builders, not merely a theoretical edge case — but it does need the specific ordering described above, so likelihood is Low-to-Medium rather than trivially always triggerable.

### Recommendation
`get_index_for_new_builder` (or `add_builder_to_registry`) should additionally verify that no outstanding `builder_pending_withdrawals` entries (and no unsettled `builder_pending_payments` entries) reference the candidate index before it is considered reusable — mirroring the fix pattern from the referenced report (clear/validate the stale index-keyed reference before allowing reassignment). Alternatively, `BuilderPendingWithdrawal`/`BuilderPendingPayment` could bind to a stable builder identity (e.g. pubkey or a monotonically incrementing generation counter per slot) instead of the raw, reusable `builder_index`.

### Proof of Concept
1. Builder B is at index `i`; a large bid payment settles, appending `BuilderPendingWithdrawal{builder_index=i, amount=X, fee_recipient=B_addr}` to `state.builder_pending_withdrawals`, behind many other entries so it is not processed for several blocks.
2. Builder B's `withdrawable_epoch` is reached (via `initiate_builder_exit` earlier) and `get_builders_sweep_withdrawals` sweeps B's remaining balance to `0` before the queued entry for `i` is reached (sweep withdrawals and the pending-withdrawal queue are processed independently, per `get_expected_withdrawals`) [8](#0-7) .
3. `get_index_for_new_builder` now returns `i` since `withdrawable_epoch <= current_epoch and balance == 0`.
4. A new builder C submits `BuilderDepositRequest`; `process_builder_deposit_request`/`add_builder_to_registry` places C at index `i` with a fresh balance `Y`.
5. In a later block, the still-queued `BuilderPendingWithdrawal{builder_index=i, amount=X, fee_recipient=B_addr}` is finally processed by `get_builder_withdrawals`/`apply_withdrawals`, decreasing `state.builders[i].balance` (now C's balance) by `min(X, Y)` and creating an EL `Withdrawal` paid to `B_addr` — Gwei taken from C, paid to B.

def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

##### New `get_builders_sweep_withdrawals`

```python
def get_builders_sweep_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    epoch = get_current_epoch(state)
    builders_limit = min(len(state.builders), MAX_BUILDERS_PER_WITHDRAWALS_SWEEP)
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    builder_index = state.next_withdrawal_builder_index
    for _ in range(builders_limit):
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder = state.builders[builder_index]
        if builder.withdrawable_epoch <= epoch and builder.balance > 0:
            withdrawals.append(
                Withdrawal(
                    index=withdrawal_index,
                    validator_index=convert_builder_index_to_validator_index(builder_index),
                    address=builder.execution_address,
                    amount=builder.balance,
                )
            )
