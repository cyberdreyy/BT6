### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing execution of a request with fewer live approvals than the required threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` (and the analogous `DeleteKey` handling in the legacy `multisig` contract) only purges *requests authored by* the removed member/key. It never scrubs that member's *confirmations already cast on other still-open requests*. Since `confirm()` counts confirmations purely by set size (`confirmations.len() as u32 + 1 >= self.num_confirmations`) without re-validating that every entry in the stored `confirmations` set still corresponds to a current member, a confirmation cast by a member before removal keeps counting after removal. This lets a request execute with strictly fewer *live* member approvals than `num_confirmations`, breaking the K‑of‑N threshold guarantee that is the entire security model of the multisig.

### Finding Description
`confirm()` in `multisig2/src/lib.rs`: [1](#0-0) 
increments/checks the confirmations `HashSet<String>` size against `self.num_confirmations` and executes the request once the count is reached. It never re-checks that the strings already stored in that set are still members of `self.members`.

`delete_member()` in the same file only cleans up requests where the *creator* matches the removed member, and removes the member's `num_requests_pk` entry - it does **not** iterate over `self.confirmations` to strip the removed member's entry from confirmation sets of requests authored by *other* members: [2](#0-1) 

The identical gap exists in the legacy `multisig` contract's `DeleteKey` action, which filters requests by `r.signer_pk == pk` (i.e., only requests the key *authored*) before wiping confirmations, leaving that key's confirmations on requests authored by other keys untouched: [3](#0-2) 
and the same count-only check in `confirm()`: [4](#0-3) 

This is structurally the same bug class as the reported issue: an authorization check is bound to the wrong entity (here, a *historical* confirmation count instead of the *live* member set), analogous to `onlyAuth()` checking `msg.sender` instead of the actual `receiver`/`controller` whose custody position is being changed. The binding that should hold is:

`confirmations recorded for request X == confirmations from accounts that are members of the multisig at the time of execution`

After a member is removed, this equality is silently broken for any request that member had previously confirmed but did not author.

### Impact Explanation
This falls under the explicitly Critical impact category: "a multisig request executed below threshold." A request (e.g., `Transfer`, `AddKey`/full-access-key grant, `FunctionCall`, `DeployContract`) can be pushed to execution with one fewer *live* approving member than `num_confirmations` mandates, because a stale confirmation from a since-removed member is still counted. This weakens the K-of-N security guarantee the contract advertises and can be used to move funds or change the multisig's own keys/members with less real consensus than configured.

### Likelihood Explanation
Exploitation only requires normal, in-protocol multisig operations (creating requests, confirming, and removing a member) — no foundation privilege, no redeploy, no external key compromise. Any sequence where a member confirms a pending request and is later removed (for any legitimate reason — resignation, rotation, suspected compromise) leaves that stale confirmation live on-chain indefinitely, because nothing ever revisits or invalidates already-cast confirmations tied to non-authored requests. Given multisig membership changes are a normal lifecycle event for these contracts, the precondition is realistic rather than contrived.

### Recommendation
When executing `confirm()`, validate that every account/public key present in the stored confirmation set is still a current member before counting it toward `num_confirmations` (or, when removing a member in `delete_member`/`DeleteKey`, iterate all open requests' confirmation sets and remove the departing member's entry, not just requests they authored).

### Proof of Concept
1. Deploy `MultiSigContract::new([M1, M2, M3, M4], num_confirmations = 3)`.
2. `M1.add_request(maliciousRequest)` → `request_id = X` (e.g., `Transfer` of the account's balance to an attacker-controlled account, or `AddKey` with a full-access key).
3. `M2.confirm(X)` → confirmations for `X` = `{M2}` (count 1 < 3, not yet executed).
4. Separately, via a normal, fully-confirmed multisig flow, the group executes `DeleteMember { member: M2 }` (`delete_member` in `multisig2/src/lib.rs:355-379`). This only removes requests *authored* by `M2`; request `X` (authored by `M1`) is untouched, and `X`'s confirmation set still contains `M2`.
5. `M3.confirm(X)` → confirmations = `{M2, M3}`, count 2 < 3.
6. `M4.confirm(X)` → count = 3 → `confirm()` (`multisig2/src/lib.rs:292-315`) sees `confirmations.len() + 1 >= num_confirmations` and executes `X`.
7. Result: request `X` executed with confirmations from `M2` (no longer a member), `M3`, `M4` — i.e., only 2 *live* members actually approved a request that was supposed to require 3-of-N live approvals. [2](#0-1) [1](#0-0)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);

            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
