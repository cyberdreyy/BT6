### Title
EI-authenticated requests can trigger integer-ID job runs via `PipelineRunsController.Create`, bypassing the intended EI restriction - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates integer-ID job runs behind an `isUser` check that is supposed to exclude external-initiator (EI) callers. However, `auth.AuthenticateExternalInitiator` sets the very same `SessionUserKey` context value that `auth.GetAuthenticatedUser` checks, so EI-authenticated requests are indistinguishable from real user sessions and `isUser` evaluates to `true`. This allows EI credential holders to trigger arbitrary integer job IDs via `RunJobV2`, defeating the intended authorization boundary.

### Finding Description
In `core/web/pipeline_runs_controller.go`, `Create` computes the guard as: [1](#0-0) 

`isUser` comes from `auth.GetAuthenticatedUser(c)`, which merely checks whether the `SessionUserKey` context value exists: [2](#0-1) 

The root cause is in `AuthenticateExternalInitiator`: after validating the EI's access key/secret, it sets `SessionExternalInitiatorKey` **and also** sets `SessionUserKey` to a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}`: [3](#0-2) 

Because `GetAuthenticatedUser` only checks for presence of `SessionUserKey` (not whether the caller authenticated via `AuthenticateBySession`/`AuthenticateByToken` vs. `AuthenticateExternalInitiator`), an EI-authenticated request passing through the standard `Authenticate(...)` + `RequiresRunRole(...)` middleware chain will have `isUser == true` in `Create`. This directly contradicts the code comment "only users are allowed to run jobs using int IDs - EIs not allowed" — the check is broken by construction, not merely bypassable via a crafted forgery. Any EI credential holder sending `POST /v2/jobs/<int-id>/runs` will have `strconv.ParseInt` succeed and reach `prc.App.RunJobV2(ctx, jobID, nil)`, executing the job.

### Impact Explanation
This is an authorization/role-boundary bypass: a credential holder scoped only to external-initiator webhook-triggering (intended to be restricted to UUID-based webhook job triggering) can instead trigger job runs for jobs identified by integer ID, which is explicitly documented as user-only functionality. This corresponds to Chainlink's "unauthorized job run" impact class — an attacker with only EI credentials can cause execution of pipeline runs for jobs they were not meant to control, potentially triggering unwanted on-chain transactions or resource consumption depending on job configuration.

### Likelihood Explanation
The precondition is simply possession of valid external-initiator credentials (access key/secret), which is a much lower privilege than a full user session or API token. No forgery of session state is even required — the normal EI authentication flow itself produces a session context that flips `isUser` to `true`. This is deterministic and repeatable for any EI credential and any known integer job ID.

### Recommendation
Distinguish "real user" sessions from EI-derived pseudo-user sessions. Do not have `AuthenticateExternalInitiator` set `SessionUserKey`; instead, have `RequiresRunRole` (and any downstream logic) rely solely on `SessionExternalInitiatorKey` for EI identity, or introduce a distinct context key (e.g., a boolean flag) that positively marks "authenticated via real user credentials" vs. "authenticated via EI". Then update `PipelineRunsController.Create`'s `isUser` check to test that dedicated flag rather than mere presence of `SessionUserKey`.

### Proof of Concept
Go handler-level integration test plan (extending `core/web/pipeline_runs_controller_test.go`):
1. Set up an application with a registered `ExternalInitiator` (access key/secret) and a job created with an integer ID (non-webhook type, e.g., direct request/OCR spec).
2. Build an HTTP client that sets `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers (the EI headers) instead of a session cookie or API token.
3. `POST /v2/jobs/<intJobID>/runs` with the EI client.
4. Assert (current expected/broken behavior) that the response is `200 OK` with a `pipelineRun` resource, i.e., `isUser` was `true` and `RunJobV2` was invoked — demonstrating the bypass.
5. As a regression assertion for the fix, add a unit test directly calling `auth.GetAuthenticatedUser` on a `gin.Context` populated only via `auth.AuthenticateExternalInitiator`, asserting it should return `ok=false` (or that a new dedicated "is real user" helper returns `false`), and that `Create` responds `422 "bad job ID"` for EI-authenticated requests targeting integer job IDs.
