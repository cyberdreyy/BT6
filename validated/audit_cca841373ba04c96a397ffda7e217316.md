### Title
`getSignaturesForAddress` can silently return fewer signatures than requested, dropping otherwise-matching entries instead of backfilling to `limit` - (File: ledger/src/blockstore.rs)

### Summary
`Blockstore::get_confirmed_signatures_for_address2()` collects address signatures into a bounded buffer up to `limit` entries *before* applying the `until`-exclusion filter, then only afterwards filters and takes `limit`. Just like the reported Babburuzu `deposit()` bug — which caps a value at a threshold and drops (rather than carrying forward) the excess instead of continuing to fill the next bucket — this code stops pulling from the RocksDB iterator once it has accumulated `limit` raw candidates, then discards some of them due to the `until` filter, without going back to the iterator to backfill the shortfall. The net effect is that `getSignaturesForAddress` can return fewer results than `limit` even though more valid, matching signatures exist in the blockstore.

### Finding Description
In [1](#0-0)  the collection loop is:

```rust
while address_signatures.len() < limit {
    if let Some(((key_address, slot, transaction_index, signature), _)) = iterator.next() {
        if slot < lowest_slot { break; }
        if key_address == address {
            if self.is_root(slot) || confirmed_unrooted_slots.contains(&slot) {
                address_signatures.push((slot, signature, transaction_index));
            }
            continue;
        }
    }
    break;
}
...
let address_signatures_iter = address_signatures
    .into_iter()
    .filter(|(_, signature, _)| !until_excluded_signatures.contains(signature))
    .take(limit);
```

The `while` loop stops as soon as `address_signatures.len()` reaches `limit`, *without* accounting for the `until_excluded_signatures` set (computed earlier from the `until` signature's slot, see [2](#0-1) ). Only after the loop terminates is `until_excluded_signatures` applied via `.filter(...)`, discarding any of the already-capped `limit` entries that fall on the excluded side of `until`. Because the loop already stopped at `limit`, there is no attempt to pull additional entries from `iterator` to compensate for the ones removed by the late filter — exactly the "cap at threshold, drop the excess instead of carrying it forward" pattern described in the external report.

### Impact Explanation
This is reachable by any unprivileged caller of the `getSignaturesForAddress` JSON-RPC method (`RpcHandler::get_signatures_for_address` → `Blockstore::get_confirmed_signatures_for_address2`, see [3](#0-2) ). It causes the RPC handler to return a wrong/incomplete result set (fewer signatures than actually exist for the given `address`/`before`/`until`/`limit` window) with no indication of truncation. Clients that paginate signature history using `before`/`until` cursors rely on getting a full page (`limit` items) unless the true end of history has been reached; under-filling silently can make clients believe they've reached the end of an address's history when more transactions actually exist, producing wrong-data-returned behavior for a read-only query — matching the "wrong ... data returned" acceptance criterion.

### Likelihood Explanation
Triggering requires only a single `getSignaturesForAddress` call with a `until` signature whose containing slot has a mix of address-matching signatures that straddle the `until` boundary within the same `limit`-sized fetch window — a normal, unprivileged usage pattern (no special account/state manipulation, no elevated permissions, one JSON-RPC call).

### Recommendation
Move the `until_excluded_signatures` filtering inside the collection loop (or otherwise continue pulling from `iterator` after filtering) so that the loop keeps fetching until either `limit` *valid* (non-excluded) entries have been collected or the iterator/slot range is exhausted, mirroring the report's recommendation to carry the excess forward rather than truncating and discarding it.

### Proof of Concept
Conceptually (mirrors the Babburuzu PoC structure):
1. Populate the blockstore with address signatures across a slot range where the `address`-matching signatures for one slot are ordered `[s1, s2, ..., sN]` in reverse chronological order.
2. Choose `until = sK` for some `K` in the middle of that slot's signature list, so `until_excluded_signatures` contains `s_K..sN` (the older ones).
3. Call `get_confirmed_signatures_for_address2(address, highest_slot, before=None, until=Some(sK), limit=N)` where `N` equals exactly the count collected by the `while` loop before the `until` filter is applied (i.e., the loop stops having already included some of the `s_K..sN` entries that will subsequently be excluded).
4. Observe the returned `infos.len() < limit`, even though there exist additional address-matching, non-excluded signatures earlier in `iterator` that were never visited because the loop already reached `limit` unfiltered entries and stopped. [4](#0-3) [5](#0-4)
