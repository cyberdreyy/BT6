### Title
Reject-then-Accept from the same signer double-counts weight into both `total_weight_rejected` and `total_weight_approved` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
In the miner-side signing coordinator's `BlockStatus` tally, a single signer's weight can be counted on *both* sides of the accept/reject equality if that signer first rejects a block proposal and later accepts the same proposal (e.g. after reconsidering, or via a crafted/duplicate `BlockResponse`). This mirrors the Ajna bug class: state that logically should be superseded/removed when a new, mutually-exclusive event occurs (rejected reserves being retained as a liability after the auction ends) is instead left stale and gets double-counted against the pool's true accounting, skewing an equality that downstream logic depends on.

### Finding Description
`BlockStatus` tracks two independent guard structures for the same signer slot: `gathered_signatures` (a map keyed by `slot_id`, populated only in the `Accepted` branch) and `responded_signers` (a set, inserted into by *both* branches) [1](#0-0) .

- On `Accepted`, the weight-add guard checks `!block.gathered_signatures.contains_key(&slot_id)` before adding the signer's weight to `total_weight_approved`, then unconditionally inserts into both `gathered_signatures` and `responded_signers`: [2](#0-1) 
- On `Rejected`, the weight-add guard checks `block.responded_signers.insert(slot_id)` (true only the first time this slot is inserted into that shared set) before adding weight to `total_weight_rejected`: [3](#0-2) 

Because the two branches guard on *different* collections, the protection is asymmetric:
- Accept-then-Reject is protected: after an `Accepted` message, `responded_signers` already contains the slot, so a later `Rejected` message from the same signer fails the `insert` check and its weight is not added again.
- Reject-then-Accept is **not** protected: after a `Rejected` message, only `responded_signers` contains the slot — `gathered_signatures` is still empty for that slot. When the same signer later sends an `Accepted` message, the `Accepted` branch's guard (`!gathered_signatures.contains_key(&slot_id)`) passes, so the signer's weight is added to `total_weight_approved` *in addition to* the weight already counted in `total_weight_rejected`.

This is confirmed by contrast with the signer-side accounting in `stacks-signer/src/signerdb.rs`, which explicitly guards against this class of double-counting at the DB layer (`add_block_rejection_signer_addr` refuses to record a rejection if a signature already exists, and inserting a signature clears any prior rejection row) — behavior validated by the `reject_then_accept` and `accept_then_reject` unit tests [4](#0-3) [5](#0-4) . The node-side coordinator (`stackerdb_listener.rs`) has no equivalent cross-branch check, so the same invariant ("do not count both a block acceptance and a block rejection for the same signer/block", as stated in the CHANGELOG for the signer-side fix [6](#0-5) ) is not enforced here.

### Impact Explanation
The coordinator (`SignerCoordinator::begin_sign_v0`/wait loop in `signer_coordinator.rs`) uses `block_status.total_weight_approved` and `block_status.total_weight_rejected` to decide, respectively, whether to treat the block as signed (≥70% threshold) or as globally rejected (blocking minority >30%) [7](#0-6) . With the double-count, a single malicious or merely inconsistent signer (reject then accept) inflates *both* tallies simultaneously using the same underlying weight. This can let the coordinator reach the acceptance threshold with less genuinely-distinct approving weight than required (effectively recording the same weight as both a rejection and an acceptance), i.e. a rejection is recounted toward acceptance — exactly the kind of miscounted-response outcome called out as a Critical impact category in the rules. It can also inflate `total_weight_rejected` beyond what distinct signers actually rejected, moving the "blocking minority" determination (and the txid exclusion/ban logic keyed off it) away from the true weight distribution.

### Likelihood Explanation
This requires only a single signer (one StackerDB slot) sending two ordinary, individually-valid signed messages for the same block in the order Reject → Accept, which is well within a one-slot actor's normal message space (no majority collusion, no key compromise, no auth-token access needed). Genuine cause: a signer that rejects a proposal and later reconsiders/accepts it (a supported flow noted in the CHANGELOG: "a signer will reconsider a block proposal that it previously rejected" [8](#0-7) ) will legitimately produce this exact message ordering, making the trigger not even adversarial in the common case.

### Recommendation
Make the `Accepted` branch's weight-add guard consistent with the `Rejected` branch by gating on the same `responded_signers` set (or an explicit per-slot "already counted" check spanning both accept and reject), e.g. change the condition at `stacks-node/src/nakamoto_node/stackerdb_listener.rs:443` from `!block.gathered_signatures.contains_key(&slot_id)` to `!block.responded_signers.contains(&slot_id)`, evaluated and inserted atomically before either weight total is mutated.

### Proof of Concept
1. Coordinator proposes block `B` with `signer_signature_hash = H`; `BlockStatus` for `H` is initialized with empty `gathered_signatures`/`responded_signers` and zero weight totals.
2. Signer `S` (weight `w`) sends `BlockResponse::Rejected` for `H`. In the `Rejected` branch, `responded_signers.insert(slot_S)` returns `true` (first time), so `total_weight_rejected += w` [3](#0-2) .
3. Signer `S` later sends `BlockResponse::Accepted` for the same `H` (e.g. reconsidering, or the same message re-sent after a state change). In the `Accepted` branch, the guard checks `gathered_signatures.contains_key(slot_S)`, which is `false` (never set), so it passes and `total_weight_approved += w` [2](#0-1) .
4. Result: `S`'s weight `w` is now present in both `total_weight_rejected` and `total_weight_approved` for the same block `H`, even though only one distinct signer responded. If other signers push either total near the threshold, this single signer's duplicated weight can be the deciding margin for a threshold decision on either side, effectively counting one signer's rejection as (also) an acceptance.

        let sig_args = params![block_sighash, addr.to_string()];
        let exists = self.db.query_row(sig_qry, sig_args, |row| row.get(0))?;

                "signer_signature_hash" => %block_sighash,
                "signer_address" => %addr,
                "reject_reason" => ?reject_reason
            );
            return Ok(false);
