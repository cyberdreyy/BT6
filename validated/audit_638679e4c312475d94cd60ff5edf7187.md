### Title
`ExternalInitiatorsEnabled` toggle does not retroactively revoke existing External Initiator credentials, allowing continued unauthorized job-run triggering after the feature is disabled - (File: `core/web/auth/auth.go`)

### Summary
Chainlink gates *creation* of External Initiators (EIs) behind the `JobPipeline.ExternalInitiatorsEnabled` config flag, but the authentication middleware that lets an EI trigger job runs does not check this flag at all. This is the same class of bug as the Rubicon `matchingEnabled` finding: a boolean feature toggle is checked in one code path (creation) but silently ignored by another code path that consumes state created under the old setting (authentication/execution), leaving previously-created objects in a state inconsistent with administrator intent.

### Finding Description
`ExternalInitiatorsController.Create` refuses to create a new `ExternalInitiator` when the feature is disabled: [1](#0-0) 

However, the runtime authentication path, `AuthenticateExternalInitiator` in `core/web/auth/auth.go`, which validates the `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers and grants the caller the `run` role (able to trigger job runs), never queries `JobPipeline().ExternalInitiatorsEnabled()`: [2](#0-1) 

A grep across the codebase confirms `ExternalInitiatorsEnabled` is referenced only in the controller/config layers (`core/web/external_initiators_controller.go`, config docs/tests) — not in `core/web/auth/auth.go`, `core/bridges/external_initiator.go`, or the router wiring that installs `AuthenticateExternalInitiator` as an auth method.

This mirrors the Rubicon `matchingEnabled` bug: an operator toggles a boolean gate expecting it to change the behavior/availability of a feature for all associated state (open offers in Rubicon; existing EI credentials here), but a separate code path that operates on previously-created state (`_unsort`/`_hide` in Rubicon; `AuthenticateExternalInitiator` here) doesn't consult the flag, causing inconsistent enforcement.

### Impact Explanation
If an operator disables `ExternalInitiatorsEnabled` — e.g., because a specific EI's key material was suspected of being leaked, or because the feature is being deprecated for security/compliance reasons — any EI credentials created while the feature was enabled remain fully functional. An unprivileged holder of a valid (or previously-leaked) `AccessKey`/`Secret` pair can still call the EI-authenticated endpoints and trigger job runs with the `run` role, even though the administrator believes the entire EI authentication surface has been shut off. This is a request-impersonation / access-control-bypass condition: the disabled feature flag does not disable the credential, contrary to operator expectation and to the explicit enable/disable check enforced at creation time.

### Likelihood Explanation
Any node operator relying on `ExternalInitiatorsEnabled = false` to shut down the external-initiator attack surface (a documented, existing config knob) is affected as soon as at least one EI was created prior to disabling the flag. No special privileges beyond possessing a valid EI access key/secret are required to exploit the inconsistency, and the code path (`AuthenticateExternalInitiator`) is reachable directly by external, unprivileged HTTP clients hitting EI-authenticated routes.

### Recommendation
Add a check for `JobPipeline().ExternalInitiatorsEnabled()` inside `AuthenticateExternalInitiator` (and/or in the route registration in `core/web/router.go`) so that disabling the flag also rejects authentication attempts from previously-created External Initiators, consistent with the create-time enforcement.

### Proof of Concept
1. Enable `JobPipeline.ExternalInitiatorsEnabled = true` and create an External Initiator via `POST /v2/external_initiators`, recording `AccessKey`/`Secret`.
2. Confirm the EI can authenticate and trigger a job run using `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers.
3. Set `JobPipeline.ExternalInitiatorsEnabled = false` and restart/reload the node.
4. Repeat step 2: the request still succeeds through `AuthenticateExternalInitiator` because it performs no check of `ExternalInitiatorsEnabled`, whereas a call to `POST /v2/external_initiators` to create a *new* initiator now correctly fails with "The External Initiator feature is disabled by configuration." // AuthenticateExternalInitiator authenticates an external initiator request.

// Implements authMethod
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
