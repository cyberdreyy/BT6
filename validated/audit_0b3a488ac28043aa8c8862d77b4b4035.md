## Analysis

The reported bug class is: a state-tracking mapping meant to gate/authorize an action is updated (or checked) on only one of two code paths that can produce the same effect, so the second path silently bypasses the intended invariant.

I found a structurally identical gap in the EIP‑8205 "validator preregistration" feature.

`EIP-8205` introduces `validator_preregistrations`, which binds a pubkey to specific `withdrawal_credentials` *before* the validator's first deposit lands, explicitly "protecting delegated staking deployments against deposit front-running" [1](#0-0) . The only enforcement point specified is `process_deposit_request` (the execution-layer `DepositRequest` path), which checks `get_active_preregistration` and discards the request if the withdrawal credentials don't match the binding [2](#0-1) .

However, the legacy in-block `Deposit` operation path (`process_deposit` → `apply_deposit`, present since phase0 and still active through at least Electra/Fulu/Gloas per the codebase's `process_deposit` references) creates or tops up validators purely by checking whether the pubkey already exists in `state.validators` and verifying the deposit signature — it never consults `validator_preregistrations`: [3](#0-2) . EIP‑8205's table of contents only lists a "Modified `process_deposit_request`" section; there is no corresponding modification to `process_deposit`/`apply_deposit` [4](#0-3) .

### Title
Preregistration withdrawal-credential lock is bypassable via the legacy `Deposit` path - ([File: specs/_features/eip8205/beacon-chain.md])

### Summary
EIP-8205 stores a pubkey → withdrawal-credentials binding (`validator_preregistrations`) that is meant to stop a deposit from ever landing with the "wrong" withdrawal credentials for a given pubkey. This binding is enforced only inside `process_deposit_request` (EL `DepositRequest` operations). The pre-existing `process_deposit`/`apply_deposit` code path, which still processes legacy `Deposit` operations included directly in `BeaconBlockBody.deposits`, is untouched by EIP-8205 and never checks `get_active_preregistration`.

### Finding Description
`process_preregistration_request` only refuses to (re)bind a pubkey if it is already an existing validator or has a pending deposit already queued for it [5](#0-4) . The binding it creates is subsequently enforced solely by `process_deposit_request`, which requires the incoming `DepositRequest.withdrawal_credentials` to equal `preregistration.withdrawal_credentials`, or the deposit is silently discarded [6](#0-5) .

`apply_deposit` (unmodified base function, still reachable via legacy `Deposit` operations included in block bodies) instead does:
```
if pubkey not in validator_pubkeys:
    if is_valid_deposit_signature(...):
        add_validator_to_registry(state, pubkey, withdrawal_credentials, amount)
``` [3](#0-2) 

There is no check here for an active preregistration. Any party who can produce a validly-signed `Deposit` for a given pubkey (e.g., a staking-pool operator or signer who holds the validator signing key but is not the intended withdrawal-credential owner — precisely the "delegated staking" actor this feature is meant to defend against) can set `withdrawal_credentials` to any value of their choosing by using the legacy `Deposit` path instead of the `DepositRequest` path, completely ignoring an active `validator_preregistrations` lock for that pubkey.

### Impact Explanation
This breaks the equality the feature is designed to guarantee: "a pubkey with an active preregistration can only be activated with the pre-committed withdrawal credentials." Bypassing it lets the entity submitting the deposit redirect the validator's exit/withdrawal destination to credentials the depositor never authorized — i.e., stake (Gwei) is bound to a withdrawal address chosen by a non-owner instead of the address the depositor locked in via preregistration. This matches the "Gwei ... paid to a non-owner" / "validator mutated without its authority" impact class.

### Likelihood Explanation
The legacy `Deposit`/`process_deposit` path is not removed by EIP-8205 and is exercised on every fork up through Gloas (and, as far as could be determined from the fork sequence, is not stated to be retired before Heze, the fork EIP-8205 is built on). Any depositor with a valid deposit signature for the target pubkey (which, in the delegated-staking model this feature targets, is exactly the untrusted signer/operator role) can trigger this at will with no coordination, special timing, or coalition required.

### Recommendation
Enforce `get_active_preregistration` in `apply_deposit` (or `process_deposit`) identically to how it is enforced in `process_deposit_request`, so both validator-creation paths honor an active `validator_preregistrations` binding, or explicitly retire the legacy `Deposit` operation before EIP-8205 activates so only the enforced `DepositRequest` path remains reachable.

### Proof of Concept
1. Depositor `D` submits a `PreregistrationRequest` binding `pubkey P` to `withdrawal_credentials W_D`; it is validly signed and stored in `state.validator_preregistrations` via `process_preregistration_request` [7](#0-6) .
2. Before `D`'s intended `DepositRequest` (with `W_D`) lands, an operator/signer `M` who holds the BLS signing key for `P` (e.g., a delegated staking operator) crafts a legacy `Deposit` for `pubkey P` with `withdrawal_credentials W_M` and a valid `DepositMessage` signature.
3. `M` includes this `Deposit` in `BeaconBlockBody.deposits`. `process_deposit` → `apply_deposit` runs: `P` is not yet in `state.validators`, the signature verifies, so `add_validator_to_registry(state, P, W_M, amount)` executes — with no reference to `state.validator_preregistrations` [3](#0-2) .
4. The validator for `P` is created with `W_M` instead of the pre-committed `W_D`, even though an active preregistration for `P` exists — the exact scenario `process_deposit_request` was built to prevent, achieved instead through the parallel, unguarded code path.

def process_preregistration_request(state: BeaconState, request: PreregistrationRequest) -> None:
    pubkey = request.pubkey

    # An active binding for this pubkey makes the new request a no-op,
    # whether the duplicate is exact or conflicting
    if get_active_preregistration(state, pubkey) is not None:
        return

    # A pubkey with an existing validator cannot be preregistered
    if pubkey in [validator.pubkey for validator in state.validators]:
        return

    # A pubkey with a valid pending deposit cannot be preregistered
    if is_pending_validator(state.pending_deposits, pubkey):
        return

def process_deposit_request(state: BeaconState, deposit_request: DepositRequest) -> None:
    # [New in EIP8205]
    preregistration = get_active_preregistration(state, deposit_request.pubkey)
    if preregistration is not None:
        if deposit_request.withdrawal_credentials != preregistration.withdrawal_credentials:
            return

        if not is_valid_deposit_signature(
            deposit_request.pubkey,
            deposit_request.withdrawal_credentials,
            deposit_request.amount,
            deposit_request.signature,
        ):
            return

        remove_stored_preregistration(state, deposit_request.pubkey)

    state.pending_deposits.append(
        PendingDeposit(
            pubkey=deposit_request.pubkey,
            withdrawal_credentials=deposit_request.withdrawal_credentials,
            amount=deposit_request.amount,
            signature=deposit_request.signature,
            slot=state.slot,
        )
    )
