### Title
`getSupply` RPC handler performs unchecked subtraction that can underflow/misreport - ([File: rpc/src/rpc.rs])

### Summary
The `getSupply` JSON-RPC method computes `circulating` supply with a raw, unchecked `u64` subtraction, `total_supply - non_circulating_supply.lamports`, whereas the functionally-identical `/v0/circulating-supply` REST handler performs the same computation with `saturating_sub`. This mismatch mirrors the reported `Goldilend` bug class: two code paths derive the same value from independently-computed quantities, and only one of them guards the subtraction, so if the two quantities become inconsistent, the unguarded path underflows.

### Finding Description
`JsonRpcRequestProcessor::get_supply` computes: [1](#0-0) 

```
let non_circulating_supply = self.calculate_non_circulating_supply(&bank).await...;
let total_supply = bank.capitalization();
...
circulating: total_supply - non_circulating_supply.lamports,
```

`non_circulating_supply.lamports` is computed by `calculate_non_circulating_supply`, which performs a full scan of stake-program accounts and sums live `bank.get_balance(pubkey)` reads: [2](#0-1) 

`total_supply` is read afterward as `bank.capitalization()`, a running counter maintained independently of the account-balance scan. These two reads are not atomic with respect to one another: the account scan iterates over (potentially many) individual account balances while the bank is used at whatever commitment level is requested (including `processed`, i.e. a bank that is not yet frozen and can still be actively mutated by transaction processing/rewards/rent burn in the same slot). Consequently `non_circulating_supply.lamports` and `bank.capitalization()` are two separately-derived, potentially skewed views of "supply," directly analogous to `interest`/`outstandingDebt` being derived independently in the reported bug.

By contrast, the REST equivalent explicitly guards the same subtraction: [3](#0-2) 

```
Ok(total_supply.saturating_sub(non_circulating_supply.lamports))
```

The existence of a `saturating_sub` fix in the sibling handler, but not in the JSON-RPC `getSupply` handler, indicates the raw subtraction in `rpc.rs` is the unguarded analog of the reported rounding/inconsistency bug.

### Impact Explanation
If `non_circulating_supply.lamports` ends up greater than `total_supply` (due to the scan/capitalization read skew described above), the raw `u64` subtraction at `rpc.rs:1148` will either wrap to a huge, incorrect `circulating` value (misreported data returned to any unprivileged RPC caller) or panic on overflow if the build has overflow checks enabled. This is reachable by any unprivileged client via a single `getSupply` RPC call with no special privileges, matching the "decoder panic and misreporting" / wrong-data-returned class of impact called out as acceptable.

### Likelihood Explanation
I could not directly confirm from the codebase whether the workspace enables `overflow-checks` in the release profile (no matches found), so I cannot conclusively prove this triggers a hard panic in a production build versus a silent wraparound. Likewise, actually causing `non_circulating_supply.lamports > total_supply` requires a specific timing race between the account scan and the capitalization read against a non-frozen ("processed") bank, which I was not able to fully verify is achievable in practice (capitalization changes are driven by burns/rewards, not ordinary transfers, so it is unclear how easily the two figures can diverge in the wrong direction). Given these unresolved uncertainties, likelihood should be treated as low/unconfirmed rather than proven.

### Recommendation
Change `rpc/src/rpc.rs`'s `get_supply` to mirror the `saturating_sub` guard already used in `rpc_service.rs`:
```rust
circulating: total_supply.saturating_sub(non_circulating_supply.lamports),
```

### Proof of Concept
Not established with certainty — I was unable to confirm a concrete, reproducible sequence (via a single `getSupply` call) that forces `non_circulating_supply.lamports` above `bank.capitalization()`, nor confirm whether release builds panic-on-overflow. This is flagged as a structural code inconsistency (unchecked vs. checked subtraction of the same derived quantities) rather than a fully proven, reproducible crash.

pub fn calculate_non_circulating_supply(bank: &Bank) -> ScanResult<NonCirculatingSupply> {
    debug!("Updating Bank supply, epoch: {}", bank.epoch());
    let mut non_circulating_accounts_set: HashSet<Pubkey> = HashSet::new();

    for key in non_circulating_accounts() {
        non_circulating_accounts_set.insert(key);
    }
    let withdraw_authority_list = withdraw_authority();

    let clock = bank.clock();
    let stake_accounts = if bank
        .rc
        .accounts
        .accounts_db
        .account_indexes
        .contains(&AccountIndex::ProgramId)
    {
        bank.get_filtered_indexed_accounts(
            &IndexKey::ProgramId(stake::program::id()),
            // The program-id account index checks for Account owner on inclusion. However, due to
            // the current AccountsDb implementation, an account may remain in storage as a
            // zero-lamport Account::Default() after being wiped and reinitialized in later
            // updates. We include the redundant filter here to avoid returning these accounts.
            |account| account.owner() == &stake::program::id(),
            None,
        )?
    } else {
        bank.get_program_accounts(&stake::program::id())?
    };

    for (pubkey, account) in stake_accounts.iter() {
        let stake_account = account
            .deserialize_data::<StakeStateV2>()
            .unwrap_or_default();
        match stake_account {
            StakeStateV2::Initialized(meta)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            StakeStateV2::Stake(meta, _stake, _stake_flags)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            _ => {}
        }
    }

    let lamports = non_circulating_accounts_set
        .iter()
        .map(|pubkey| bank.get_balance(pubkey))
        .sum();

    Ok(NonCirculatingSupply {
        lamports,
        accounts: non_circulating_accounts_set.into_iter().collect(),
    })
}

async fn calculate_circulating_supply_async(bank: &Arc<Bank>) -> Result<u64, SupplyCalcError> {
    let total_supply = bank.capitalization();
    let bank = Arc::clone(bank);
    let non_circulating_supply =
        tokio::task::spawn_blocking(move || calculate_non_circulating_supply(&bank))
            .await
            .expect("Failed to spawn blocking task")
            .map_err(|e| SupplyCalcError::Scan(e.to_string()))?;

    Ok(total_supply.saturating_sub(non_circulating_supply.lamports))
}
