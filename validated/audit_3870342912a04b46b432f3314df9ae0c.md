### Title
Response cache key omits WorkflowID, causing cross-workflow HTTP response leakage despite documented "workflow isolation" - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
The gateway's HTTP Action response cache is documented to be "workflow-scoped" and to prevent "cross-workflow data leakage," but the actual cache key computed by `gateway.OutboundHTTPRequest.Hash()` does not include the `WorkflowID` field at all — it is keyed only by method/URL/headers/body/`WorkflowOwner`. This is the same class of root-cause defect as the audited Sherlock report: a value/identifier that should be scoped to a specific sub-entity (a withdraw request's partial vaultShares, here a specific `WorkflowID`) is instead computed/scoped against a broader aggregate (the total withdrawal value, here the `WorkflowOwner`), producing an overly permissive result that violates an explicit isolation guarantee.

### Finding Description
`responseCache` stores cached HTTP responses in `rc.cache[cacheKey]`, where `cacheKey := req.Hash()` [1](#0-0) . The documentation for this component explicitly states the cache key is "Generated from workflow ID and request hash" and that entries are "scoped by workflow ID to prevent cross-workflow data leakage" [2](#0-1) .

However, the test suite for `Hash()` demonstrates the opposite behavior: two requests that differ only in `WorkflowID` produce the *same* hash, while `WorkflowOwner` is the field that actually differentiates entries: [3](#0-2) 

Because `Set`/`Fetch` key exclusively off `req.Hash()` [4](#0-3) , any two distinct workflows belonging to the same `WorkflowOwner` that issue an outbound HTTP Action with identical method/URL/headers/body will collide on the same cache entry — one workflow's cached response is served to a different workflow, regardless of `WorkflowID`.

This mirrors the audited root cause: `_calculateValueOfWithdrawRequest` was documented/expected to reflect the value attributable to a specific (possibly split) request, but instead used the whole/aggregate withdrawal value — the correct narrower scoping key was silently dropped in the actual computation while the surrounding logic/documentation assumed it was present.

### Impact Explanation
The HTTP Action gateway handler is reachable by any unprivileged workflow (CRE workflow) that can issue outbound HTTP requests with caching enabled (`CacheSettings.Store = true`). If a `WorkflowOwner` deploys or is otherwise associated with multiple distinct workflows (e.g., multi-tenant CRE Node Operator setups, or workflow templates managed on behalf of multiple end customers under one owner key), a response computed within the trust/data boundary of one workflow can be transparently served into the execution of a different workflow that happens to hit the same URL/method/headers/body. This breaks the explicitly documented workflow isolation guarantee and can lead to stale/cross-workflow data being consumed by a workflow that never made that request — a form of cross-user/cross-workflow response confusion.

### Likelihood Explanation
Exploitation only requires two workflows under the same owner to make outbound HTTP Action requests with identical request signatures (method, URL, headers, body) and `CacheSettings.Store=true` — a common scenario for workflows that fetch from shared/public endpoints (e.g., price feeds). No special privileges beyond normal workflow authoring are needed, and the mismatch is deterministic (not timing-dependent), making it straightforward to trigger.

### Recommendation
Include `WorkflowID` (or restore full per-workflow scoping consistent with the documented design) in `OutboundHTTPRequest.Hash()`'s input, so that cache entries are correctly isolated per workflow rather than per owner. Add a regression test asserting that requests differing only in `WorkflowID` produce different hashes, and update/verify the existing test asserting "different workflowID results in same Hash" reflects intended behavior — as written, it directly certifies the isolation bypass.

### Proof of Concept
1. Workflow A (owner `O`) issues an `OutboundHTTPRequest{Method:"GET", URL:"https://api.example.com/data", WorkflowID:"wfA", WorkflowOwner:"O", CacheSettings:{Store:true}}` and gets a response cached under `req.Hash()`.
2. Workflow B (owner `O`, different `WorkflowID:"wfB"`) issues an outbound request with identical Method/URL/Headers/Body and `WorkflowOwner:"O"`.
3. Per `TestRequestHash`'s "having different workflowID results in same Hash" case [5](#0-4) , `req1.Hash() == req2.Hash()` despite `WorkflowID` differing.
4. `responseCache.Fetch` for Workflow B's request looks up the same `cacheKey` and returns Workflow A's cached response [6](#0-5) , violating the documented per-workflow isolation.

**Note on verification limits**: I was unable to locate the source file defining `gateway.OutboundHTTPRequest.Hash()` itself (likely in the `chainlink-common` module, outside this repo's index), so I could not directly inspect which fields are hashed; this conclusion is inferred from the `response_cache_test.go` behavioral assertions, which are strong but indirect evidence. A Devin session with full repository/dependency access would be needed to confirm the exact `Hash()` implementation.

```go
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
```

```go
// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
```

```go
		hash1 := req1.Hash()
		hash2 := req2.Hash()
```
