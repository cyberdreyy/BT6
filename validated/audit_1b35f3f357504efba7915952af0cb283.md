### Title
Aggregated peer-signature threshold in `store_and_process_block_signature` bypasses the chainstate/conflict re-check that `handle_block_pre_commit` performs, letting a signer locally accept and push a conflicting block - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`store_and_process_block_signature`, which fires when a `BlockResponse::Accepted` from a peer pushes the aggregated signature weight over the 70% threshold, marks the block `LocallyAccepted` and pushes it to the node without ever calling `check_block_against_signer_db_state` or `get_signed_conflicts` — the exact checkpoint that the analogous "we are about to sign" path, `handle_block_pre_commit`, always re-runs immediately before it calls `mark_locally_accepted`. This mirrors the referenced bug class: one state-transition function (`withdraw`/`handle_block_pre_commit`) re-syncs a checkpoint before mutating consensus-relevant state, while the sibling function (`redeem`/`store_and_process_block_signature`) reaches the same terminal state without it.

### Finding Description
Two independent code paths reach the terminal effect "mark this block accepted in signerdb + broadcast/push it to the node":

1. Our own signing decision, `handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs:1345-1480`): before calling `mark_locally_accepted(false)`, it always re-runs `check_block_against_signer_db_state` (chainstate re-check) [1](#0-0)  and then `get_signed_conflicts` plus freshness/liveness questions (`conflict_still_blocks`, `reorg_permit_stands`) before it is willing to sign [2](#0-1) , only then calling `mark_locally_accepted(false)` [3](#0-2) .

2. Aggregating *other* signers' already-existing signatures, `store_and_process_block_signature` (`stacks-signer/src/v0/signer.rs:2442-2538`): it verifies the cryptographic signature, tallies weight, and once the 70% threshold is met calls `mark_locally_accepted(true)` and `broadcast_signed_block` directly — with **no** call to `check_block_against_signer_db_state` or `get_signed_conflicts` anywhere in the function [4](#0-3) .

The docs confirm this asymmetry is by design for the *tally* itself ("reaching 70% signatures still only marks the block locally accepted"), but the missing checkpoint matters because `mark_locally_accepted` (with `group_signed=true`) sets `signed_group`, and `signed_group`/`signed_self` are exactly the timestamps that `get_tenure_last_block_info` and `get_signed_conflicts` use to determine this signer's own view of "the tenure's signed tip" and "conflicting signed blocks at/above a height, in ANY tenure" [5](#0-4) . Because `store_and_process_block_signature` writes this checkpoint without ever consulting it, a signer's own signerdb can end up recording two mutually-conflicting blocks (siblings at the same height, across tenures) as locally accepted:

- Block X, height h, tenure A: signed by *this* signer through the normal `handle_block_pre_commit` path (own decision, conflict-checked).
- Block Y, height h, tenure B: a sibling this signer never proposed/pre-committed to, or already rejected — but for which ≥70% of the other signers' weight of `Accepted` responses arrives. `store_and_process_block_signature` will mark Y `LocallyAccepted` (with `signed_group`) on this signer's own record and immediately `broadcast_signed_block` → `handle_post_block`, pushing Y to this signer's node, without checking that Y conflicts with the already-signed X.

This breaks the "one-per-height" / "aggregated-weight vs verified-accepts" equality the report's rules explicitly call out: the signer treats an aggregated peer-signature count as equivalent to a verified accept, exactly as `takeManagementAndPerformanceFees` treated a stale `highWaterMark` as an up-to-date checkpoint.

### Impact Explanation
This lets a signer push a block to its node, and record it in its own signerdb as accepted/signed, without the signer ever independently validating it against its own conflict-aware chainstate view — the same category of harm the report's rules classify as Critical ("a signer signing an invalid/non-canonical/conflicting block", here effectively acting on a block as if it verified it when it only counted others' weight). At minimum it corrupts this signer's own `signerdb` bookkeeping (two locally-accepted siblings at the same height), which subsequently feeds `get_tenure_last_block_info`/`get_signed_conflicts`/`check_latest_block_in_tenure` with an inconsistent picture, degrading the guarantees those checks are meant to give for every future proposal this signer evaluates.

### Likelihood Explanation
Reachable by a single miner (plus normal gossip) proposing two conflicting blocks at the same height in different tenures and getting each block signed by a different, possibly disjoint but individually-sufficient (≥70%) subset of the other signers — no majority key compromise or auth-token access is required, only normal `BlockResponse` gossip that already occurs in the protocol.

### Recommendation
Have `store_and_process_block_signature` run the same `check_block_against_signer_db_state` + `get_signed_conflicts` (with freshness/liveness/reorg-permit logic) checkpoint that `handle_block_pre_commit` runs, before calling `mark_locally_accepted(true)` and `broadcast_signed_block`, so that a threshold reached purely from peers' signatures cannot cause this signer to record/push a block that conflicts with something it has already signed.

### Proof of Concept
1. Miner proposes conflicting blocks X (tenure A, height h) and Y (tenure B, height h).
2. Signer S goes through `handle_block_pre_commit` for X, passes the chainstate/conflict checks, and calls `mark_locally_accepted(false)` — `signed_self` is set for X [6](#0-5) .
3. A different, sufficiently-weighted subset of signers independently signs Y (S may never have pre-committed to Y, or rejected it).
4. S receives their `BlockResponse::Accepted` messages for Y; `store_and_process_block_signature` tallies the weight to ≥70% and, without any call to `check_block_against_signer_db_state`/`get_signed_conflicts`, calls `mark_locally_accepted(true)` on Y and `broadcast_signed_block` [7](#0-6) .
5. S's signerdb now holds both X and Y as accepted/signed at the same height in different tenures, and S has pushed Y to its node without ever verifying it against its own signed conflicts.
