### Title
`parse_associated_token` misreports `tokenProgram` for `Create`/`CreateIdempotent`/`RecoverNested` by blindly echoing an attacker-controlled account with no identity validation - ([File: transaction-status/src/parse_associated_token.rs])

### Summary
`parse_associated_token` only performs a bounds check via `check_num_associated_token_accounts` (`check_num_accounts`) before echoing `account_keys[instruction.accounts[5]]` (or index 6 for `RecoverNested`) into the `"tokenProgram"` field of the parsed JSON. There is no verification that this account is actually `spl_token::id()`, `spl_token_2022::id()`, or any real token program, so an attacker can place an arbitrary pubkey at that instruction-account slot and have it surfaced as `"tokenProgram"` in `getTransaction` with `jsonParsed` encoding.

### Finding Description
In `parse_associated_token` (`transaction-status/src/parse_associated_token.rs:34-78`), for `AssociatedTokenAccountInstruction::Create` and `CreateIdempotent`, the code calls `check_num_associated_token_accounts(&instruction.accounts, 6)` which only checks that there are at least 6 account indices present (`transaction-status/src/parse_associated_token.rs:36,50,81-86`, delegating to `check_num_accounts`). It then unconditionally builds the JSON info object using `account_keys[instruction.accounts[5] as usize].to_string()` as `"tokenProgram"` (`transaction-status/src/parse_associated_token.rs:45,59`), and for `RecoverNested`, `account_keys[instruction.accounts[6] as usize]` (`transaction-status/src/parse_associated_token.rs:74`). No comparison is made against the real `spl_token`/`spl_token_2022` program IDs or against the ATA program's own validation logic. Because transaction history parsing (used by `getTransaction`/`getConfirmedTransaction` with `jsonParsed` encoding) occurs independently of on-chain execution success, an attacker can submit any transaction containing an `AssociatedTokenAccountInstruction::Create`-shaped instruction (even data-less, since empty data defaults to `Create` at line 24-26) with account index 5 set to an arbitrary pubkey of the attacker's choosing. The instruction may fail on-chain (the real ATA program will reject a bogus token program at runtime), but the transaction is still recorded and its instructions are still parsed for `getTransaction`, so the RPC response's `meta.innerInstructions`/`transaction.message.instructions` will report the fabricated `tokenProgram` value as if it were validated truth.

### Impact Explanation
This is an RPC misreporting bug (decoder/parser misreporting a program identity field) rather than a consensus or crash issue. Downstream integrators (explorers, indexers, wallets) that trust `info.tokenProgram` from `jsonParsed` transaction data without independently verifying account ownership/program IDs on-chain will display or act on incorrect program identity for that instruction. This matches the "decoder panic and misreporting" accepted impact category, scoped strictly to the transaction-status parsing layer.

### Likelihood Explanation
Trivial and fully reproducible by any unprivileged client: construct and submit a single transaction with a `Create`-shaped instruction where `accounts[5]` is an arbitrary pubkey, then call `getTransaction` with `jsonParsed` encoding once. No special privileges, staking, or multiple calls are required, and the instruction need not succeed on-chain for the parse layer to report the fabricated value.

### Recommendation
In `parse_associated_token`, validate that `account_keys[instruction.accounts[5]]` (and index 6 for `RecoverNested`) equals a known token program ID (`spl_token::id()` or `spl_token_2022::id()`) before labeling it `"tokenProgram"`, or otherwise clearly document/flag in the parsed output that this field is a positional echo and not a verified program identity, consistent with how other parsers in this crate should treat unvalidated account roles.

### Proof of Concept
```rust
// transaction-status/src/parse_associated_token.rs (test module)
#[test]
fn test_parse_create_reports_arbitrary_token_program() {
    let funder = Pubkey::new_unique();
    let wallet_address = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let attacker_pubkey = Pubkey::new_unique(); // not spl_token / spl_token_2022 id
    let create_ix =
        create_associated_token_account(&funder, &wallet_address, &mint, &attacker_pubkey);
    let mut message = Message::new(&[create_ix], None);
    let compiled_instruction = &mut message.instructions[0];

    let parsed = parse_associated_token(
        compiled_instruction,
        &AccountKeys::new(&message.account_keys, None),
    )
    .unwrap();

    // Demonstrates the parser echoes the attacker-chosen pubkey verbatim
    // with no validation that it is a real token program.
    assert_eq!(
        parsed.info["tokenProgram"],
        json!(attacker_pubkey.to_string())
    );
    assert_ne!(attacker_pubkey, spl_token_interface::id());
    assert_ne!(attacker_pubkey, spl_token_2022_interface::id());
}
