This confirms the vulnerability. The `delete_member` function only purges confirmations for requests **authored by** the deleted member (`filter_map(|(k, r)| if r.member == member`), but does not scan and remove that member's **confirmation entries on other requests they merely confirmed but did not author**. This is a genuine stale-confirmation bug.

## Title
Stale confirmation from a deleted member lets `AddKey{permission: None}` reach `num_confirmations` with fewer live signers - (File: multisig2/src/lib.rs)

## Summary
`MultiSigContract::confirm` counts every entry in a request's `confirmations` `HashSet<String>` toward `num_confirmations`, but `delete_member` never scrubs a departing member's confirmation entries from requests they merely confirmed (only from requests they authored). This lets an `AddKey{public_key: attacker_pk, permission: None}` request on `receiver_id = current_account_id()` execute `promise.add_full_access_key(attacker_pk)` using a stale confirmation from a member who is no longer live, i.e. below the intended live-signer threshold.

## Finding Description
Binding: `confirmations.len() as u32 + 1 >= self.num_confirmations` should equal "number of **live, distinct** `self.members` that confirmed R" `>= num_confirmations`, at the moment `execute_request` is invoked in [1](#0-0) .

Root cause: confirmations are stored keyed only by `request_id` → `HashSet<String>` of `member.to_string()`, independent of `self.members`. When a member M is removed via a `DeleteMember` request, `delete_member` at [2](#0-1)  only deletes requests where `r.member == member` (i.e., requests M *authored*), and only cleans `num_requests_pk`. It performs no scan/cleanup of `self.confirmations` entries containing `member.to_string()` for other outstanding requests M had *confirmed* but not authored. `self.members.remove(&member)` removes M from the live-member set, but the stale confirmation string for M remains inside another request R's `confirmations` set forever.

Exploit flow:
1. Members `A`, `B`, `M` (num_confirmations = 3, members.len() = 3).
2. Attacker (or any member) creates request `R = {receiver_id: current_account_id(), actions: [AddKey{public_key: attacker_pk, permission: None}]}` via `add_request`.
3. `M` confirms `R` (`confirm(R)` → `confirmations = {A}` say, then `{A, M}`), leaving `confirmations.len() == 2 < 3`, so it's stored, not yet executed.
4. Separately, a `DeleteMember{member: M}` request reaches quorum and executes, calling `delete_member`, which removes `M` from `self.members` and deletes `M`-authored requests, but does **not** touch `R`'s confirmations set (`{A, M}` stays intact) since `R` wasn't authored by `M`.
5. Now only `A` and `B` are live members (2 members), yet `num_confirmations` was left at 3 (or could have been lowered separately). `B` (a live member) confirms `R`: `confirmations.len() as u32 + 1 == 2 + 1 == 3 >= self.num_confirmations (3)` — quorum reached, but the actual live-member confirmers are `{A, B}` = 2, not 3; `M`'s stale entry silently padded the count.
6. `execute_request` runs `MultiSigRequestAction::AddKey` with `permission: None` → `promise.add_full_access_key(attacker_pk)` scheduled on `current_account_id()` per [3](#0-2) .
7. `attacker_pk` is now a full-access key on the multisig account — not tracked in `self.members` at all — and can directly sign transfers, bypassing `confirm`/`execute_request` and the member/threshold model entirely.

Existing guards that fail to catch this: `assert_valid_request` only checks the *caller* is currently a member [4](#0-3) ; it never re-validates that *previously stored* confirmations still belong to live members. `confirm`'s only duplicate-check is `!confirmations.contains(&member.to_string())` [5](#0-4) , which does not filter stale entries. `assert_self_request` only checks `receiver_id == current_account_id()`, irrelevant to member liveness.

## Impact Explanation
Critical: a full-access key controlled by the attacker is installed on the multisig account with fewer live confirming signers than `num_confirmations` requires, i.e., "a multisig request executed below `num_confirmations` live members." Once `attacker_pk` holds a full-access key, the attacker can transfer out all NEAR held by the multisig account directly via that key, completely bypassing the `confirm`/`execute_request` state machine — total loss of custody for that multisig's funds. This is repeatable against any multisig2-based contract that mixes member deletion with concurrently pending confirmed-but-not-yet-executed requests.

## Likelihood Explanation
Preconditions: the multisig must have at least one pending request `R` that a soon-to-be-deleted member has confirmed but that hasn't reached quorum yet, and a `DeleteMember` action must subsequently execute for that member while `R` remains outstanding. This requires either collusion/timing among members, or an attacker-controlled member proposing/confirming `R` then engineering (or waiting for) that member's own removal, or simply race-like ordering of two independently-progressing requests. No special privileges beyond being able to observe pending requests are needed by the ultimate beneficiary (`attacker_pk` can be chosen by whoever authored `R`); it does require at least one member to act maliciously or be replaced through the normal governance flow while `R` is pending — a realistic multisig lifecycle event (member rotation) that isn't currently guarded against.

## Recommendation
When removing a member in `delete_member`, iterate over **all** outstanding `self.requests` (not just those authored by the member) and remove `member.to_string()` from each request's `confirmations` set, re-checking whether the remaining set size still satisfies invariants. Alternatively, validate confirmation liveness at `confirm`-time by filtering `confirmations` to only entries where `self.members.contains(...)` before comparing against `num_confirmations`, and persist the filtered set.
