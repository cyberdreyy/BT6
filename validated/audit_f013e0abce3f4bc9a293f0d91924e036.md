The external report's bug class — implementation silently diverging from documented behavior around **checks that gate state/isolation** — has a direct analog in the CRE HTTP Gateway response cache.

### Finding

The `README.md` for the HTTP Handlers V2 gateway explicitly documents:
> **Cache Key**: Generated from workflow ID and request hash
> **Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage [1](#0-0) 

But the actual cache implementation keys entries using `req.Hash()`, and the struct comment states the hash covers `(method, URL, headers, body, workflowOwner)` — **not** `workflowID`: [2](#0-1) 

This is confirmed by the test suite for `OutboundHTTPRequest.Hash()`, which explicitly asserts that requests with **different `WorkflowID`** but identical method/URL/body produce the **same hash**, while different `WorkflowOwner` values produce different hashes: [3](#0-2) 

The cache is consulted/populated for every outbound HTTP action from `makeOutgoingRequest`, using the same shared `responseCache` instance across all workflows/DONs served by the gateway handler: [4](#0-3) 

### Why this matches the report's bug class

Just as `TokTokNft.sol`'s implementation deviated from its documented checks (no funds check in `_mintCheck()`, no balance check in `withdraw()`, no cleanup in `removeBonusToken()`), the gateway's response cache deviates from its documented "workflow ID" isolation guarantee — it is actually only owner-scoped. Two distinct workflows deployed by the same `workflowOwner` that issue outbound HTTP actions with identical method/URL/headers/body (a very plausible scenario, e.g., both calling the same third-party API with default parameters) will **share a cached response**, even though they are logically distinct workflow executions. This is a cross-workflow response confusion within the gateway's cache, contradicting the documented isolation model.

### Caveats

- The `Hash()` method itself lives in the `chainlink-common` package (`gateway_common.OutboundHTTPRequest`), which is not part of this repo's index, so I could not inspect its exact source — this conclusion is based on the struct doc-comment and the passing test assertions in this repo, which together are strong evidence but not a full view of the hash implementation.
- Whether this constitutes meaningful "impact" depends on whether same-owner workflows are expected to have independent caches (per the README, yes) and whether cached data could leak sensitive per-workflow information (e.g., workflow-specific auth tokens embedded in headers/body that aren't part of the hash but do vary — not confirmed here).

### Title
Response cache isolation is scoped by workflow owner, not workflow ID, contradicting documented workflow-level isolation - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
The CRE HTTP Gateway documents that cached outbound HTTP action responses are isolated per workflow ID, but the actual cache key (`OutboundHTTPRequest.Hash()`) only incorporates `workflowOwner`, not `workflowID`, method/URL/headers/body. Two different workflows owned by the same address that issue equivalent outbound HTTP requests will collide in the shared response cache.

### Finding Description
`README.md` states the cache is keyed by "workflow ID and request hash" and that entries are "scoped by workflow ID to prevent cross-workflow data leakage." The `responseCache` struct comment and the `TestRequestHash` test, however, show the hash is computed from method/URL/headers/body/workflowOwner — explicitly confirming that varying `WorkflowID` alone does not change the hash while varying `WorkflowOwner` does. The single shared `responseCache` instance in `gatewayHandler` is used by `makeOutgoingRequest` for all outbound HTTP actions across all workflows served by the gateway.

### Impact Explanation
Any two workflows belonging to the same `workflowOwner` that make outbound HTTP action requests with identical method/URL/headers/body will read/write the same cache entry, even though the documentation guarantees per-workflow isolation. This can cause one workflow to receive a cached response actually produced for, or intended for, a different workflow's execution context, undermining the confidentiality/isolation model the gateway advertises for multi-workflow tenants sharing an owner.

### Likelihood Explanation
This requires no privileged access — it is triggered purely by normal multi-workflow usage from a single unprivileged workflow owner operating more than one workflow that happens to call the same external endpoint with the same parameters (a common pattern, e.g., default API calls with `CacheSettings.Store=true`).

### Recommendation
Include `WorkflowID` (or another workflow-execution-scoped identifier) in `OutboundHTTPRequest.Hash()` so the cache key matches the documented isolation guarantee, or update the documentation to accurately state that isolation is enforced at the `workflowOwner` level rather than the `workflowID` level.

### Proof of Concept [5](#0-4) 
This existing test demonstrates the collision directly: constructing two requests with identical method/URL but different `WorkflowID` values yields identical hashes, meaning a cache write from workflow A's outbound request is readable by workflow B's identical outbound request as long as both share the same owner.
