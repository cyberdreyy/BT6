### Title
Unfunded instant-withdraw receipts can be stacked on funded ones and drained early — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`claimInstantWithdrawRequest` pays out the full `instantWithdrawsRequests[_user]` balance with no epoch gating, while `requestInstantWithdraw` keeps adding receipts that are only funded later via `collectInstantWithdrawFunds`. A user who holds an already-funded instant receipt can open a second, unfunded instant request and immediately claim the combined balance, consuming underlyings that belong to other funded claimants.

### Finding Description
The bug class of the external report is a lifetime race: a resource (a tty) is freed by one operation while a concurrent operation still uses it. The on-chain analog is a receipt whose backing is "freed" (never funded) while the claim path still treats it as payable.

- `requestInstantWithdraw` mints a strategy-token receipt and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `pendingInstantWithdraws`, with no check that the user already has an open receipt. [1](#0-0) 
- Funding only happens when the CDO calls `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and pulls exactly `_amount` underlyings from the CDO. Receipts requested after that call are unfunded until a later collect. [2](#0-1) 
- `claimInstantWithdrawRequest` burns and pays the entire `instantWithdrawsRequests[_user]` in one shot. Unlike the normal path `_claimFundedWithdrawRequest`, which enforces `epochNumber > lastWithdrawRequest[_user]` so a receipt cannot be claimed before its epoch is funded, there is no epoch/funding check here and no per-epoch split of funded vs. unfunded instant receipts. [3](#0-2) [4](#0-3) 
- The only reserve protection is `_transferFundedClaim`, which guards `defaultRecoveryReserve` but happily spends underlyings earmarked for other users' funded claims. [5](#0-4) 

Attack sequence (running epoch, instant-withdraw mode enabled):

1. Epoch N: attacker calls `requestInstantWithdraw(100)`. At `stopEpoch`, `collectInstantWithdrawFunds(100)` funds the strategy; attacker's receipt is backed.
2. Epoch N+1 begins. Attacker calls `requestInstantWithdraw(100)` again. The new receipt is pending and unfunded (collect only runs at the next stop).
3. Attacker calls `claimInstantWithdrawRequest`. It burns 200 receipt tokens and transfers 200 underlying, although only 100 was ever funded for them. The extra 100 is paid out of funds collected for other users' instant receipts (or reverts if the balance is insufficient, freezing those users).

Invariant broken: one receipt one payout / solvency — a claim is paid before its corresponding `collectInstantWithdrawFunds` has run.

### Impact Explanation
Direct theft: each stacked unfunded receipt steals up to its full amount from underlyings reserved for other claimants. Repeated stacking before each collect drains the funded pool. If other funded claimants' money is insufficient, the claim reverts and their withdrawals are frozen instead.

### Likelihood Explanation
Requires instant withdrawals to be enabled by the manager (`setInstantWithdrawParams`) and at least one funded epoch boundary. Attacker is an ordinary KYC'd lender; no privileged or borrower cooperation needed. Caveat: whether the CDO-side wrapper (`IdleCDOEpochVariant.claimInstantWithdrawRequest`/`requestInstantWithdraw`) imposes additional per-user gating (e.g., `instantDelay` or blocking a second open request) was not fully verified; if it already prevents a second request while one is unclaimed, this path is unreachable and the issue reduces to a defense-in-depth gap in the strategy.

### Recommendation
Mirror the normal-request protection for instant receipts: track a `lastInstantWithdrawRequestEpoch[_user]`, and in `claimInstantWithdrawRequest` only pay receipts whose epoch was already funded (i.e., exclude `instantWithdrawsRequestsByEpoch[_user][epochNumber]` unless a collect has run for it), or revert while `pendingInstantWithdraws` includes the user's newest receipt. Alternatively reject `requestInstantWithdraw` when `instantWithdrawsRequests[_user] != 0`, matching the post-default guard in `requestWithdraw`. [6](#0-5) 

### Proof of Concept
Foundry fork sketch (standard epoch variant, instant mode):

```solidity
// epoch N: user1 requests 100 instant, user2 requests 100 instant
cdoEpoch.requestInstantWithdraw(100, address(AAtranche)); // user1
cdoEpoch.requestInstantWithdraw(100, address(AAtranche)); // user2
// stopEpoch N -> collectInstantWithdrawFunds(200) funds strategy
_stopCurrentEpochWithApr(lowApr); // triggers instant path
// epoch N+1: user1 requests 100 more (pendingInstantWithdraws = 100, unfunded)
cdoEpoch.requestInstantWithdraw(100, address(AAtranche)); // user1 again
// user1 claims immediately: burns 300 receipt, receives 300 underlying
// strategy only holds 200 funded -> user2's claim now underfunded/reverts
uint256 balPre = underlying.balanceOf(user1);
cdoEpoch.claimInstantWithdrawRequest(); // via IdleCDO for user1
assertEq(underlying.balanceOf(user1) - balPre, 300);
vm.expectRevert(); // user2 claim now fails or is short-paid
cdoEpoch.claimInstantWithdrawRequest();
```

Note: the PoC validity depends on the CDO wrapper permitting a second instant request while one is unclaimed and permitting a claim before the newest receipt's collect; confirm both in `IdleCDOEpochVariant` before finalizing.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
