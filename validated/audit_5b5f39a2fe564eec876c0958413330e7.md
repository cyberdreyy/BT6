Analysis of `multisig2/src/lib.rs`:

- `confirm()` at line 294-315 checks `confirmations.len() as u32 + 1 >= self.num_confirmations` — it counts raw confirmation entries in the `HashSet<String>` for a request, without re-validating that each recorded confirmer is still a current member of `self.members` [1](#0-0) .
- `delete_member()` at line 356-379 only purges requests where `r.member == member`, i.e., requests *originated* by the removed member. It does **not** scan `self.confirmations` for entries where the removed member had merely *confirmed* someone else's pending request [2](#0-1) .

Exploit path: Member A creates a `Transfer` (or `FunctionCall`/`DeployContract`) request (`add_request`, recorded with `member: A`). Member B, who is about to be removed, confirms it (`confirm`, count=1, added to that request's `confirmations` set as B's identity string). Members then pass a separate `DeleteMember{member: B}` request to threshold and execute it — this only cleans up requests where `r.member == B` (i.e., requests B personally created), leaving B's stale confirmation on A's request untouched. Any remaining live member(s) can now confirm A's request; since `confirmations.len()` still includes B's (now-invalid) confirmation, the counted total reaches `num_confirmations` with fewer actually-live confirming members than K, and `execute_request` fires the transfer/deploy/function-call.

This breaks the equality "confirmations counted == confirmations from currently live members," letting NEAR move (or a contract be deployed/upgraded, or a function called with attacker-chosen args/deposit) from the multisig account with fewer than K live-member confirmations — a threshold-bypass on custody of the multisig's NEAR balance.

### Title
Stale confirmations from removed multisig members are not purged, allowing request execution below the live-member confirmation threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` counts raw entries in a request's confirmation `HashSet<String>` against `num_confirmations` without checking whether each recorded confirmer is still a current member of `self.members`. `delete_member` only removes requests that a departing member *originated* (`r.member == member`), but never scans and strips that member's confirmations from requests *originated by someone else*. A stale confirmation from a removed member therefore still counts toward the K-of-N threshold on any other pending request, letting a request execute (transfer NEAR, deploy/upgrade contract, add a full-access key, or call an arbitrary function with attached deposit) with confirmations from fewer than K currently-live members.

### Finding Description
`confirm()` computes eligibility purely from set size: `confirmations.len() as u32 + 1 >= self.num_confirmations` [4](#0-3) . The `confirmations` map is populated by member identity strings (`MultisigMember::to_string()`), and nothing in `confirm()` re-checks that those strings still correspond to entries in `self.members` at the time the threshold is evaluated.

`delete_member()` is invoked from `execute_request` for a `DeleteMember` action and is the single place membership changes are propagated into request/confirmation cleanup:
```
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
``` [5](#0-4) 

This filter only matches on `r.member`, the *creator* of the request (set once in `add_request` at line 189-190 [6](#0-5) ). It never inspects the contents of `self.confirmations`, so a confirmation contributed by the member being deleted, on a request created by a *different* member, survives untouched in storage. That stale confirmation remains counted the next time anyone calls `confirm()` on that request.

Binding broken: confirmations counted (`confirmations.len() + 1 >= num_confirmations`) should equal confirmations obtained from members that are live at the moment of execution. After a `DeleteMember` executes, this equality can diverge — the counted total includes a phantom confirmation from an account/key that no longer has any authority over the multisig.

### Impact Explanation
This allows a `MultiSigRequestAction::Transfer`, `DeployContract`, `AddKey` (full access key), or `FunctionCall` (with attached deposit and arbitrary args) to execute against the multisig's own NEAR balance and control surface with effectively K-1 (or fewer) live-member approvals instead of the configured K. That is a multisig request executed below threshold — NEAR held in the multisig account can be moved, or the account's control can be handed to an unauthorized key, by less than the required quorum of currently-trusted members. This matches the Critical custody-binding class: "a multisig request executed below threshold."

### Likelihood Explanation
The scenario requires no privileged actor beyond ordinary multisig usage: any member (A) creates a request, any second member (B) confirms it, and the group later removes B via a normal `DeleteMember` request (a routine operational action, e.g., offboarding a departed member or rotating a compromised key) before A's request is otherwise confirmed/executed or deleted. Because pending requests can persist for the `active_requests_limit` count per member and have no forced expiry beyond the 15-minute `delete_request` cooldown, the window for this sequence to occur in normal operation is realistic, and no attacker-side compute/cost is required beyond timing an existing pending request against a member-removal request.

### Recommendation
In `delete_member`, iterate all entries in `self.confirmations` (not just requests where `r.member == member`) and strip the removed member's identity string from every confirmation set; alternatively, revalidate every confirmer's current membership inside `confirm()` before comparing the count against `num_confirmations` (e.g., filter `confirmations` to only strings present in `self.members` before counting).

### Proof of Concept
1. Deploy multisig with members `{A, B, C}` and `num_confirmations = 2`.
2. A calls `add_request` with `MultiSigRequest { receiver_id: multisig_account, actions: [Transfer { amount: X }] }` → `request_id = 0`, `r.member = A`.
3. B calls `confirm(0)` → `confirmations.len() == 1 < 2`, so it's just recorded; `confirmations[0] = {B}`.
4. A separate request is created and confirmed to threshold to `DeleteMember{ member: B }` (e.g., A creates it, C confirms, reaching 2/2) → executes `delete_member`, which only removes requests with `r.member == B` (none here), so `confirmations[0]` still contains `{B}` and `members` is now `{A, C}`.
5. C (the only other live member) calls `confirm(0)` → `confirmations.len() (1) + 1 >= num_confirmations (2)` is true, so `execute_request` fires the `Transfer` — despite only A (creator, uncounted in the set) and C ever confirming while being live members at execution time, with B's stale confirmation making up the count instead of a second live confirmer having confirmed independently. In effect, the request is authorized on paper by "2 confirmations" while only 1 confirmation came from someone who was a live member of the reduced 2-member/2-confirmation set at execution time, and B (no longer a member) still influenced execution of a transfer from the account.
