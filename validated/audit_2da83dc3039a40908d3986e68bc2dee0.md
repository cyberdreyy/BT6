### Title
Stale rejection weight is never retracted when a signer flips to acceptance, letting a non-canonical/aborted-early tally wedge block production - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` maintains two independent, monotonically-increasing weight counters per proposed block — `total_weight_approved` and `total_weight_rejected` — gated by two different dedup sets (`gathered_signatures` for accepts, `responded_signers` for rejects). Nothing in the accept path removes a signer's weight from `total_weight_rejected` after that signer later accepts the same block, and nothing prevents the reject path from having already counted it. This is the same bug class as the RSK/TOB report: an event's effect (weight) is applied once into a running tally and never retracted/reconciled when superseded, so a later, contradictory event still leaves the stale contribution counted forever.

### Finding Description
On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` guarded only by `responded_signers.insert(slot_id)`: [1](#0-0) 

On `BlockResponse::Accepted`, weight is added to `total_weight_approved` guarded only by `gathered_signatures.contains_key(&slot_id)`: [2](#0-1) 

These two guards are independent maps/sets. If the same signer's slot first sends `Rejected` (weight is added to `total_weight_rejected`, `responded_signers` marks the slot as responded) and later sends `Accepted` for the *same* block (e.g. because whatever condition caused the rejection resolved — the signer-side flow explicitly allows re-evaluating and eventually signing a previously-rejected block, per `docs/signer-flows.md` section 4/6: "repeat my earlier answer (unless the reason I rejected has since gone away)"), the accept branch's guard (`gathered_signatures.contains_key`) is empty for that slot, so the weight is added a second time — into `total_weight_approved` — while the earlier contribution to `total_weight_rejected` is never removed.

The consequence: after a reject→accept flip, the signer's weight is counted in *both* running totals simultaneously, and `total_weight_rejected` keeps counting weight from signers who no longer currently reject. The coordinator loop checks the rejected tally first: [3](#0-2) 
and only afterward checks the approved tally: [4](#0-3) 

Because the stale rejection contribution is never retracted, `total_weight_rejected` can cross the `>30%` blocking-minority line (`total_weight_rejected + weight_threshold > total_weight`) purely from decisions that are no longer current, even while enough *currently accepting* weight exists to legitimately reach the 70% threshold. The miner will declare `NakamotoNodeError::SignersRejected` and permanently/temporarily exclude transactions based on a tally that misrepresents the live state of signer opinion.

### Impact Explanation
This breaks the equality between "aggregated weight" and "verified/current accepts," per the rules' definition of in-scope impact ("acting on a stale reward set/threshold"). A single signer's legitimate reject→accept transition (no majority collusion required) permanently inflates the rejected-weight tally, which can push the miner into wrongly aborting a block that would otherwise have reached the 70% signing threshold — a liveness wedge on block production for that tenure attempt, and it can also cause transactions to be wrongly marked "problematic"/excluded (`permanently_excluded_txids`/`temporarily_excluded_txids`) based on stale rejection data, degrading future block templates.

### Likelihood Explanation
Any one signer that rejects a proposal for a transient reason (a validation race, a temporarily-stale sortition/tenure view, a reorg-permit timing issue — all scenarios the signer-side code explicitly re-checks and can resolve into a later signature, per `handle_block_pre_commit`/`store_and_process_block_signature` in `stacks-signer/src/v0/signer.rs`) and then legitimately signs the same block triggers this. No majority, no malicious key, and no protocol violation is needed — only ordinary Accept-after-Reject message sequencing from a single well-behaved signer, which the signer-side state machine is explicitly designed to allow.

### Recommendation
When processing a `BlockResponse::Accepted` for a slot that is already present in `responded_signers` due to a prior rejection, retract that slot's weight from `total_weight_rejected` (and vice versa if a rejection ever arrives after an acceptance, though that path is already blocked signer-side). Alternatively, replace the two independent weight counters with a single per-slot "current vote" map (slot_id → Accept/Reject) and recompute `total_weight_approved`/`total_weight_rejected` by summing over that map on each update, so a flip always correctly moves weight from one bucket to the other instead of accumulating in both.

### Proof of Concept
1. Node proposes block `B` to signer set with weights `{S1: 35, S2: 35, S3: 30}` (`weight_threshold` = 70 out of 100).
2. `S1` sends `BlockResponse::Rejected(B)` (transient reason, e.g. it hasn't yet seen the parent tenure's tip). `StackerDBListener` sets `total_weight_rejected = 35`, `responded_signers = {S1}`.
3. `S1`'s local state resolves (per `check_block_against_signer_db_state`) and it later sends `BlockResponse::Accepted(B)` with a valid signature. `gathered_signatures` does not contain `S1`'s slot, so `total_weight_approved = 35`.
4. `S2` and `S3` also accept: `total_weight_approved` reaches `35+35+30 = 100 ≥ 70`, but `total_weight_rejected` is still stuck at `35` from step 2 (never retracted).
5. Now suppose instead only `S1` and `S2` accept (`total_weight_approved = 70`) while `S3` genuinely rejects (`total_weight_rejected = 30` from `S3`, plus the stale `35` from `S1` = `65`). `signer_coordinator.rs` checks `total_weight_rejected.saturating_add(weight_threshold) > total_weight` → `65 + 70 = 135 > 100` → true → the coordinator returns `Err(NakamotoNodeError::SignersRejected)` even though `total_weight_approved` already reached the 70% threshold and the block should have been accepted; the rejected-check runs first in the `if/else if` chain, per `stacks-node/src/nakamoto_node/signer_coordinator.rs:509-541`.
