### Title
Instant-withdraw claims pay the unscoped aggregate receipt balance, letting unfunded current-epoch receipts spend other users' funded claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays out `instantWithdrawsRequests[_user]` — the aggregate of a user's instant-withdraw receipts across *all* epochs — without checking whether the current-epoch portion has actually been funded by the borrower. This mirrors the reported bug class (unscoped/unvalidated identifier keys granting cross-boundary access): the claim path uses an unscoped aggregate key instead of the epoch-scoped, funding-scoped value, so a receipt that is still inside `pendingInstantWithdraws` (i.e., borrower has not yet sent the underlying) is paid out of underlying held by the strategy that is earmarked for *other* users' already-funded claims.

### Finding Description
`requestInstantWithdraw` (`IdleCreditVault.sol:356-375`) records receipts both in the aggregate `instantWithdrawsRequests[_user]` and in the epoch-scoped `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` / `instantWithdrawClaimsByEpoch[currentEpoch]`, and increments the unfunded counter `pendingInstantWithdraws`.

Funding arrives only via `collectInstantWithdrawFunds` (`IdleCreditVault.sol:398-403`), which the CDO calls around epoch boundaries and which decrements `pendingInstantWithdraws` while pulling underlying into the strategy.

`claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`) then does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

Two scope violations follow:

1. **Funded vs unfunded scope.** The aggregate `instantWithdrawsRequests[_user]` mixes receipts whose funds were collected with receipts still sitting in `pendingInstantWithdraws`. `_transferFundedClaim` (`IdleCreditVault.sol:897-907`) pays any non-zero amount from `underlyingToken.balanceOf(address(this))` (less `defaultRecoveryReserve`), i.e., from underlying the strategy is holding for other users' funded normal/instant claims placed there by `collectWithdrawFunds`. An attacker who requests an instant withdraw mid-epoch and claims before the borrower-funded collection receives underlying that belongs to earlier claimants. Because `pendingInstantWithdraws` is not decremented on this path, the borrower's later funding refills the strategy — meaning the attacker simply front-ran other claimants; if the borrower defaults before that funding lands (or funds less via a loss-adjusted stop), the earlier claimants' balances were already spent.

2. **Epoch scope for default accounting.** The claim path never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. If a default is later finalized for that epoch, `defaultPendingClaimBasis()` (`IdleCreditVault.sol:644-649`) still counts the attacker's already-claimed basis, inflating `totalBasis` in `finalizeDefaultRecovery` (`IdleCreditVault.sol:679-688`) and diluting `defaultRecoveryPrice` for every other defaulted-epoch claimant — a cross-tenant transfer of recovery value caused by an unscoped identifier.

### Impact Explanation
Direct theft / insolvency of unclaimed withdrawal funds: an unprivileged tranche holder can withdraw underlying that is reserved for other users' matured, funded claims, and permanently dilutes the default-recovery reserve because the spent basis is never removed from `instantWithdrawClaimsByEpoch`. The loss equals the attacker's instant-withdraw amount (up to the strategy's spendable underlying balance) plus the pro-rata dilution of `defaultRecoveryPrice` on every other claimant.

### Likelihood Explanation
The path is reachable by any KYC-passing lender whenever `allowInstantWithdraw` is enabled and the strategy holds a non-zero underlying balance (funded claims awaiting collection). It requires no privileged role: `requestInstantWithdraw` and `claimInstantWithdrawRequest` are both callable through `IdleCDOEpochVariant.claimInstantWithdrawRequest` (`IdleCDOEpochVariant.sol:975-979`), which only checks `allowInstantWithdraw`. The residual uncertainty is whether the CDO gates user instant-claim timing to a post-funding window elsewhere; the strategy itself enforces no funded-status check and no epoch scoping, so any gap in CDO timing or any epoch where collection lags a claim leaves the funded pool spendable by unfunded receipts.

### Recommendation
In `claimInstantWithdrawRequest`, pay only the funded portion: track per-epoch funded status (e.g., cap the claim to `instantWithdrawsRequestsByEpoch` entries for epochs whose funds were collected, or subtract the user's share of `pendingInstantWithdraws`), decrement `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` consistently when a claim consumes unfunded basis, and clear `instantWithdrawsRequestsByEpoch[_user][epoch]` on claim so `defaultPendingClaimBasis` cannot double-count spent receipts. Alternatively, have the CDO pass a validated funded amount rather than letting the strategy trust the aggregate.

### Proof of Concept
Foundry fork outline (cannot be fully verified without re-running the CDO funding flow):

```solidity
// Setup: pool running, epoch N; victim V has a matured normal withdraw
// already funded via collectWithdrawFunds => strategy holds underlying for V.
uint256 v = strategy.withdrawsRequests(V);
assertGt(underlying.balanceOf(address(strategy)), 0);

// Attacker A (KYC'd, holds tranche tokens) requests an instant withdraw mid-epoch.
vm.startPrank(A);
cdo.requestInstantWithdraw(amount, tranche); // burns tranches, mints receipt tokens
vm.stopPrank();

// A's receipt is unfunded: pendingInstantWithdraws includes `amount`, borrower sent nothing.
assertEq(strategy.pendingInstantWithdraws(), amount);

// A claims immediately; strategy pays from funded pool earmarked for V.
uint256 balPre = underlying.balanceOf(A);
vm.prank(A);
cdo.claimInstantWithdrawRequest();
assertEq(underlying.balanceOf(A) - balPre, amount);

// Invariant broken: pendingInstantWithdraws still `amount` but underlying left the vault.
// When borrower funds at next startEpoch, the strategy is made whole only if funding succeeds;
// if default/finalizeDefaultRecovery happens first, A's basis is still inside
// instantWithdrawClaimsByEpoch[epochNumber], inflating defaultPendingClaimBasis and
// diluting defaultRecoveryPrice for all other claimants.
```

Expected result: `instantWithdrawsRequestsByEpoch[A][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` remain non-zero after the claim, so `strategy.defaultPendingClaimBasis()` overstates the defaulted claim basis by `amount`, and `V`'s funded claim reverts or is underpaid.
