### Title
Legacy trigger callback map silently overwritten on duplicate `MessageId`, allowing cross-user response confusion - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores a per-request callback in `h.savedCallbacks` keyed only by the attacker-controllable JSON-RPC `id` (`msg.Body.MessageId`), with no check for an already in-flight entry with the same key, unlike the newer v2 trigger handler which explicitly rejects duplicate in-flight IDs. An attacker who submits a second signed request reusing the same `MessageId` as a victim's still-pending request silently replaces the victim's saved callback, so the next node response keyed by that `MessageId` (which could be the response to the victim's original trigger) is delivered to the attacker's callback via `savedCb.SendResponse` in `handleWebAPITriggerMessage`, while the victim's request hangs until timeout.

### Finding Description
`MessageId` for legacy gateway requests comes directly from the untrusted, caller-chosen JSON-RPC `id` field: `common.ValidatedMessageFromReq` sets `m.Body.MessageId = req.ID` [1](#0-0)  before `Message.Validate()` only checks length/format, not uniqueness [2](#0-1) . The only "authentication" required is that the message is signed by some ECDSA key the attacker controls (`ExtractSigner`), which does not tie identity to any privilege — anyone can generate a keypair and sign an arbitrary `MessageId`.

In `HandleLegacyUserMessage`, the handler stores the new callback unconditionally:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [3](#0-2) 
There is no lookup/rejection of an existing in-flight entry for the same `MessageId`, in contrast to the newer v2 handler which explicitly detects and rejects duplicate in-flight request IDs with a `jsonrpc.ErrConflict`/"in-flight request" error [4](#0-3) .

When a node later responds with that `MessageId`, `handleWebAPITriggerMessage` looks the callback up, deletes it, and forwards whatever response arrived to that saved callback — without any binding to which original request produced it:
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
h.mu.Unlock()
if found {
    return savedCb.SendResponse(...)
}
``` [5](#0-4) 

Exploit flow: victim submits request A with `MessageId=X`, which stores callback A and fans the request out to all DON members [6](#0-5) . Before any node replies, attacker submits request B with a colliding `MessageId=X` (signed with attacker's own key), which overwrites `h.savedCallbacks[X]` with callback B and also fans B's request to DON members. Whichever node response for `MessageId=X` arrives first (it could be a node's response to victim's request A, since correlation is purely by `MessageId`) is delivered to whichever callback currently occupies the map slot — the attacker's callback B — because the map has no per-request/sender binding. Victim's original callback A is orphaned and will time out (`gateway.ProcessRequest`'s `callback.Wait(ctx)` returns "handler timeout") [7](#0-6) .

### Impact Explanation
This is a cross-user response confusion / request-smuggling bug: an unprivileged attacker who can predict or coordinate to collide a `MessageId` with a victim's in-flight legacy trigger request can receive the node's response payload intended for the victim (potentially containing data derived from the victim's workflow/trigger execution), while the victim's request silently fails via timeout — a denial-of-service side effect. This matches the "cross-user response confusion" bounty impact class for the gateway's legacy handler path.

### Likelihood Explanation
Exploitation requires no special privilege: the attacker only needs the ability to send signed gateway JSON-RPC requests (any self-generated ECDSA keypair, per the trust model already assumed by unauthenticated senders of legacy messages) and the ability to choose the `id`/`MessageId` field. The attacker must win a race — sending the colliding request before the victim's request's DON responses arrive back — which is plausible given typical multi-hundred-millisecond DON round-trip times and repeatable via automated retries. There is no rate limiting or uniqueness check preventing the collision at the legacy handler level (`h.nodeRateLimiter` only limits node->gateway traffic, not user->gateway).

### Recommendation
In `HandleLegacyUserMessage`, before storing a new entry, check whether `h.savedCallbacks[msg.Body.MessageId]` already exists and is not expired; if so, reject the new request with a conflict error (mirroring the v2 `httpTriggerHandler`'s duplicate in-flight ID rejection) instead of silently overwriting. Additionally consider binding responses to the original request/sender (e.g., verifying `msg.Body.Sender` consistency) rather than relying solely on `MessageId` for correlation.

### Proof of Concept
Add a table/unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct two valid, signed legacy `api.Message` requests A and B, both with method `MethodWebAPITrigger` and identical `MessageId = "X"`, signed by two different private keys (simulating victim and attacker).
2. Call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)`; assert `h.savedCallbacks["X"]` is set to callback A.
3. Call `h.HandleLegacyUserMessage(ctx, msgB, callbackB)`; **current (vulnerable) behavior**: assert `h.savedCallbacks["X"]` now equals callback B with no error returned to the caller and no error/notification sent to `callbackA`.
4. Simulate a node response for `MessageId="X"` via `h.HandleNodeMessage`/`handleWebAPITriggerMessage`; assert the response is delivered to `callbackB.Wait()` even though it correlates to victim's original request A, and that `callbackA.Wait(ctx)` times out/never receives a response.
5. After the fix, step 3 should instead return an error (e.g. `errors.New("message ID already in use for in-flight request")`) and leave `h.savedCallbacks["X"]` pointing at callback A, and `callbackB.Wait()` should receive a conflict error rather than the victim's response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
