## Analysis

The Hats Protocol bug (H‑9) is a case where an invariant check recomputes its "correct" value from the *same* mutated state that the transaction just changed, instead of comparing against a value snapshotted before the mutation — letting the attacker change both the raw state and the derived check value together and still pass. The consensus-specs analog is the builder-payment quorum mechanism introduced for Gloas (ePBS), specifically `get_builder_payment_quorum_threshold` and `process_builder_pending_payments`.

### Root cause

`payment.weight` is accumulated incrementally, slot by slot, during `process_attestation` over the course of an epoch, using each attester's *effective balance at the moment their attestation is processed*: [1](#0-0) 

At the epoch boundary, `process_builder_pending_payments` compares that accumulated weight against a quorum computed from `get_total_active_balance(state)` — but this is the *current*, already-mutated state at epoch-processing time, not a value pinned to when the weight was accumulated: [2](#0-1) [3](#0-2) 

`process_epoch` runs `process_registry_updates`, `process_slashings`, and `process_effective_balance_updates` (which can shrink the active validator set and validators' effective balances) in the *same* epoch-transition call that later invokes the new Gloas step that settles builder payments (this ordering pattern is visible in the analogous `process_epoch` definition for Fulu): [4](#0-3) 

Because `get_builder_payment_quorum_threshold` divides `get_total_active_balance(state)` by `SLOTS_PER_EPOCH` *after* registry/slashing changes for that same epoch transition have already been applied, the quorum bar used to judge `payment.weight` is not the same "total active balance" that existed while attesters were actually contributing weight throughout the epoch. This is exactly the H‑9 pattern: the "correct" threshold is derived from post-mutation state rather than a pre-mutation snapshot, so the equality `weight >= quorum` no longer reflects a consistent point in time.

### Title
Builder-payment quorum threshold recomputed from post-mutation active balance instead of the balance in effect while weight was accumulated - (File: `specs/gloas/beacon-chain.md`)

### Summary
`process_builder_pending_payments` checks `payment.weight >= get_builder_payment_quorum_threshold(state)` at the epoch boundary, but `get_total_active_balance(state)` used inside the threshold function is evaluated *after* `process_registry_updates`/`process_slashings`/`process_effective_balance_updates` have already run for that same epoch transition, while `payment.weight` was accumulated slot-by-slot during the epoch using effective balances as of attestation-processing time. The check compares two quantities from different points in the state's mutation timeline rather than pinning the divisor to a stable pre-epoch-processing snapshot.

### Finding Description
`get_builder_payment_quorum_threshold` derives its quorum purely from the live `get_total_active_balance(state)`: [2](#0-1) 

`payment.weight`, however, is built up incrementally across the preceding epoch by `process_attestation`, adding each attester's effective balance at the time their attestation lands: [1](#0-0) 

`process_builder_pending_payments` then evaluates the accumulated weight against the *current* quorum at the moment epoch processing rotates the payment queue: [5](#0-4) 

Standard `process_epoch` ordering (illustrated by the equivalent Fulu definition, since epoch-processing steps such as `process_registry_updates`, `process_slashings`, and `process_effective_balance_updates` are shared machinery that Gloas' new steps are appended after) means the active-validator set and effective balances used by `get_total_active_balance` in the quorum calculation are the *post*-registry-update, *post*-slashing values for that very epoch transition: [4](#0-3) 

This is structurally identical to H‑9: the "correct" comparison value (`_getCorrectThreshold()` in Hats, `get_builder_payment_quorum_threshold` here) is derived from state that can be mutated in the same unit of execution as the thing being checked (owner/threshold changes in Hats; validator exits/slashing/effective-balance changes in the same epoch transition here), so the equality no longer certifies what it is meant to certify — that the payment weight represents the intended fraction of stake.

### Impact Explanation
If validators represented in `payment.weight` are removed from the active set or have their effective balance reduced by `process_registry_updates`/`process_slashings`/`process_effective_balance_updates` within the same epoch-boundary transition that runs `process_builder_pending_payments`, `get_total_active_balance(state)` shrinks and the quorum threshold is lowered *after* the weight was already accumulated under the larger, pre-mutation active balance. A payment that would not legitimately have reached quorum under the active balance that existed while attestations were being counted can be pushed over the (now lower) threshold, causing `state.builder_pending_withdrawals` to be credited with a builder payment that the actual attesting weight, relative to the honest active-balance denominator, did not satisfy. This falls under "a builder payment or withdrawal misdirected, doubled or escaped" (High impact), since it can release (or, symmetrically, block) an ETH-denominated builder payment inconsistent with the quorum invariant the mechanism is supposed to enforce.

### Likelihood Explanation
This requires no adversarial coalition of stake beyond the ordinary validator exit/slashing churn that occurs every epoch as part of normal protocol operation — the divisor moves purely as a side effect of `process_epoch`'s own internal ordering, not because of any single malicious actor forging a message. The magnitude of the effect scales with how many validators exit/are slashed in a given epoch relative to `SLOTS_PER_EPOCH`, so on mainnet-scale validator sets the per-epoch swing in `get_total_active_balance` is normally small, making a decisive over/under-quorum flip a low-probability but non-zero event; it becomes deterministic in adversarially-crafted scenarios (e.g., an entity controlling a coordinated block of validators intentionally timing exits/slashings) or in smaller (testnet/minimal-preset) validator sets.

### Recommendation
Snapshot the value used as the quorum divisor (or the full `get_builder_payment_quorum_threshold` result) at the point weight accumulation begins for the corresponding payment slot — e.g., store it alongside `BuilderPendingPayment` when the payment entry is first created in `process_execution_payload_bid` — instead of recomputing `get_total_active_balance(state)` from the post-registry-update/post-slashing state at rotation time in `process_builder_pending_payments`. This mirrors the H‑9 fix of pinning the comparison value before the state-mutating operations rather than re-deriving it from the already-mutated state.

### Proof of Concept
Conceptual state trace (not client-executable, since this requires interleaving epoch-processing sub-steps that are otherwise atomic within `process_epoch`):
1. At epoch `N`, `get_total_active_balance(state)` = `B0`, so quorum = `Q0 = (B0 // SLOTS_PER_EPOCH) * NUM/DEN`.
2. Throughout epoch `N`, attesters accumulate `payment.weight` for a given slot's `BuilderPendingPayment`, reaching `W`, where `Q0 <= W` is false only marginally (`W` just below `Q0`), because it reflects balances that existed under `B0`.
3. During the epoch-`N`→`N+1` boundary's `process_epoch` call, `process_registry_updates`/`process_slashings`/`process_effective_balance_updates` reduce the active validator set/effective balances such that `get_total_active_balance` becomes `B1 < B0` — purely from validators processed earlier in the *same* `process_epoch` invocation, before `process_builder_pending_payments` runs.
4. `process_builder_pending_payments` computes quorum `Q1 = (B1 // SLOTS_PER_EPOCH) * NUM/DEN < Q0`, and now `W >= Q1` holds even though `W` never reflected `B1`-relative stake — the builder's payment is released into `state.builder_pending_withdrawals` on a quorum check that mixes pre-mutation weight with post-mutation threshold. [5](#0-4)

def get_builder_payment_quorum_threshold(state: BeaconState) -> Uint64:
    """
    Calculate the quorum threshold for builder payments.
    """
    per_slot_balance = get_total_active_balance(state) // Uint64(SLOTS_PER_EPOCH)
    quorum = per_slot_balance * BUILDER_PAYMENT_THRESHOLD_NUMERATOR
    return Uint64(quorum // BUILDER_PAYMENT_THRESHOLD_DENOMINATOR)

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
