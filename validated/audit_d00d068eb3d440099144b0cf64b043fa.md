### Title
Missing `receive` function in Escrow implementation preventing native safety deposit funding - (`contracts/EscrowSrc.sol`, `contracts/EscrowDst.sol`)

### Summary
The `EscrowSrc` and `EscrowDst` contracts (and their zkSync variants) lack a `receive` or `payable fallback` function. This prevents them from accepting the native token (ETH) safety deposits required for their operation when deployed via `BaseEscrowFactory`. While `EscrowDst` is funded during deployment via `CREATE2` value, `EscrowSrc` is designed to be funded *before* the factory's `postInteraction` call to a pre-computed address. Because the contract bytecode lacks a way to accept native transfers, these transfers revert, preventing the protocol from functioning as intended for source-chain escrows.

### Finding Description
The 1inch Cross-chain Swap protocol utilizes deterministic deployment (Clones/CREATE2) for escrow contracts. 
1.  **Source Chain Flow**: In `BaseEscrowFactory._postInteraction`, the factory computes the address of a source escrow and then attempts to deploy it using `implementation.cloneDeterministic(salt, 0)` [1](#0-0) . Before this call, the protocol expects the `safetyDeposit` (native ETH) to have been pre-sent to the deterministic address [2](#0-1) .
2.  **The Root Cause**: The implementation contracts `EscrowSrc` [3](#0-2)  and `EscrowDst` [4](#0-3)  inherit from `BaseEscrow` [5](#0-4) . None of these contracts implement a `receive()` or `fallback()` function. 
3.  **The Failure**: When a resolver or user attempts to fund the pre-computed `EscrowSrc` address with the required `safetyDeposit` via a standard native transfer (e.g., `address.call{value: amt}("")`), the transaction will revert because the contract does not have a payable receiving function. This is explicitly demonstrated in the protocol's own test suite where a manual check for `success` is required [6](#0-5) .

While `EscrowDst` is funded at the moment of deployment with `msg.value` [7](#0-6) , the `EscrowSrc` logic relies on the address being funded *prior* to the factory transaction. Without a `receive` function, the `EscrowSrc` can never be funded, and the factory will revert with `InsufficientEscrowBalance()` [8](#0-7) .

### Impact Explanation
**Medium**: The smart contract is unable to operate because the required native balance cannot be established by an unprivileged actor (the resolver/taker). Any attempt to fulfill a cross-chain swap on the source chain will fail at the `postInteraction` stage because the safety deposit cannot be deposited into the escrow's pre-computed address. This effectively breaks the core "Source path" of the protocol for any swap requiring a safety deposit.

### Likelihood Explanation
**High**: This is a fundamental architectural requirement of the protocol's source-chain flow. Every standard swap using the `EscrowFactory` requires a safety deposit to be sent to the deterministic address before deployment. Since the code is compiled with Solidity 0.8.23, which reverts on native transfers to contracts without a `receive` function, this failure is guaranteed for every attempt to use the protocol.

### Recommendation
Add a `receive()` function to `BaseEscrow.sol` to allow the escrow clones to accept native token deposits.

```solidity
// contracts/BaseEscrow.sol
receive() external payable {}
```

### Proof of Concept
1.  Compute the deterministic address of a source escrow using `addressOfEscrowSrc`.
2.  Attempt to send ETH (the `safetyDeposit`) to that address: `(bool success, ) = computedAddress.call{value: 1 ether}("");`.
3.  The call returns `success = false` and reverts.
4.  Call `EscrowFactory.postInteraction` (via the Limit Order Protocol).
5.  The function execution reaches the balance check:
    `if (escrow.balance < immutables.safetyDeposit ... ) revert InsufficientEscrowBalance();`
6.  The transaction reverts, preventing the swap from being initiated. [8](#0-7)
