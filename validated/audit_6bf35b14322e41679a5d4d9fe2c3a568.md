### Title
Settled APR0 receipts bypass the loss-adjusted claim guard, letting a lender claim a haircutted epoch's receipt at full value - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a single `notifier_block` node shared between two bus types, so a handler registered for one class of object fires on the other. The analog in `IdleCreditVault` is the shared per-user epoch marker `lastWithdrawRequest` plus the APR0 bookkeeping in `apr0Users`: the guard in `requestWithdraw` that forces a user to claim a loss-haircutted receipt before opening a new request only checks the *open* APR0 bucket (`apr0Users[_user].principal`), not the *settled* bucket (`settledPrincipal`/`settledInterest`). A lender whose APR0 receipt belongs to a `stopEpochWithDuration` loss epoch can call `_settleApr0` (via a first `claimWithdrawRequest` attempt path), then open a new request. The new request overwrites `lastWithdrawRequest`, so `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch` for the wrong epoch and pays the haircutted receipt at par from the funded pool.

### Finding Description
- `collectWithdrawFunds` stores a haircut per request epoch when the borrower under-funds pending receipts: `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` (`IdleCreditVault.sol:411-430`).
- `requestWithdraw` tries to prevent `lastWithdrawRequest` from being overwritten while a loss receipt is pending: it reverts only if `withdrawsRequestsByEpoch[_user][lossEpoch] != 0` **or** `apr0Users[_user].principal != 0 && principalEpoch == lossEpoch` (`IdleCreditVault.sol:261-271`).
- `_settleApr0` moves `principal` into `settledPrincipal` and zeroes `principal`/`principalEpoch` once `epochNumber` has advanced past the request epoch (`IdleCreditVault.sol:545-565`). After that, the guard condition is false even though the user still holds an unclaimed claim on the loss epoch (`settledPrincipal + settledInterest`, settled at `apr0RateByEpoch[lossEpoch]`).
- The user then calls `requestWithdraw` again; `lastWithdrawRequest[_user]` is overwritten to the new `currentEpoch` (`IdleCreditVault.sol:282`).
- On `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` (now the *new* epoch), finds `lossRecoveryPriceByEpoch[newEpoch] == 0`, returns 0, and `_claimFundedWithdrawRequest` pays `settledPrincipal + settledInterest` (plus the new normal amount) at full value via `_transferFundedClaim` (`IdleCreditVault.sol:319-350`, `789-801`).

The "two buses sharing one node" is literal here: one scalar epoch marker is multiplexed across normal, APR0-settled, and loss-adjusted receipt classes, so registering a new request silently rebinds which epoch's haircut applies to the old receipt.

### Impact Explanation
The funded pool only contains `claimBasis * lossRecoveryPrice` for that epoch's receipts (the borrower funded the haircutted amount). Paying the settled-APR0 claimant at par overpays by `claimBasis * (1 - lossRecoveryPrice)`, directly draining underlyings reserved for other pending claimants — the last claimants' `_transferFundedClaim` either reverts or pays less than entitled. Broken invariant: one receipt, one (haircutted) payout. Loss is quantified by `claimBasis * (1 - lossRecoveryPriceByEpoch[lossEpoch])`, i.e. proportional to the realized `stopEpochWithDuration` loss share assigned to pending receipts.

### Likelihood Explanation
Requires: a manager-called `stopEpochWithDuration` with `_lossAmount` that haircuts pending receipts (an honest-but-lossy epoch stop, in scope since the manager is honest and the attacker only sequences around it); the attacker is a KYC-passed lender holding an APR0 (`unscaledApr == 0`) withdraw request in that epoch; after `epochNumber` advances they trigger `_settleApr0` then a small second `requestWithdraw`, and claim. No privileged cooperation needed. This is a medium-likelihood path gated on the APR0 mode and a loss epoch both being used.

### Recommendation
- In `requestWithdraw`'s loss-receipt guard, also treat `apr0Users[_user].settledPrincipal`/`settledInterest` belonging to the loss epoch as an unclaimed receipt. Store the settled bucket's epoch (e.g. a `settledEpoch` field) or clear the whole `Apr0UserData` only at claim time.
- Alternatively, key `_claimLossAdjustedWithdrawRequest` off a dedicated per-epoch scan (check `lossRecoveryPriceByEpoch` for every epoch recorded in `withdrawsRequestsByEpoch`/APR0 data) instead of the single `lastWithdrawRequest` pointer, so no single marker can be rebound across receipt classes.

### Proof of Concept
A Foundry fork test (mirroring `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`):

```solidity
// setup: setAprs(0,0) (APR0 mode), attacker deposits AA, epoch starts
cdoEpoch.requestWithdraw(0, address(AAtranche));      // APR0 request in epoch N
// manager stops epoch N with a loss haircutting pendingWithdraws:
//   previewLossAdjustedWithdrawFunds -> pendingToFund < pendingBasis
//   collectWithdrawFunds -> lossRecoveryPriceByEpoch[N] = e.g. 0.5e18
// next startEpoch bumps epochNumber to N+1
cdoEpoch.claimWithdrawRequest();                      // settles APR0 (may partially pay or just settle)
cdoEpoch.requestWithdraw(dust, address(AAtranche));   // guard passes: apr0Users.principal == 0
// lastWithdrawRequest[attacker] is now N+1
// warp, stop epoch N+1 normally (no loss)
cdoEpoch.claimWithdrawRequest();                      // pays settledPrincipal+settledInterest at PAR
// assert attacker received > claimBasis * lossRecoveryPriceByEpoch[N]
// assert strategy underlying balance < remaining claimants' entitlement
```

Note: I could not fully verify within this session whether the first `claimWithdrawRequest` call pays out the settled amounts immediately (which would remove the exploit) or leaves them pending while `principal` is zeroed — `_claimFundedWithdrawRequest` pays `settledPrincipal` in the same call that settles, so the bypass likely requires ordering where settlement happens but the loss receipt is recorded under epoch `N` while `lastWithdrawRequest` still points at `N` *before* a full claim. If settlement and payment are always atomic, the residual risk narrows to the case where `apr0RateByEpoch`/`settledInterest` survives into a second request cycle; the fix above (tracking settled-bucket epochs) covers both cases.
