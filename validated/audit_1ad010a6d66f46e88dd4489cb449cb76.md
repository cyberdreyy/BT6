### Title
Raising `unscaledApr` while APR0 withdraw requests are open makes `stopEpoch` revert and freezes all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` burns the CDO's strategy tokens and records an APR0 principal bucket when `unscaledApr == 0`. At epoch end, `IdleCDOEpochVariant.stopEpoch` invokes `prepareStopEpochWithApr0`, which unconditionally reverts with `NotAllowed` if `apr0TotalPrincipal != 0` while `unscaledApr != 0`. There is no guard preventing the manager from calling `setAprs` to raise the APR between the user's request and `stopEpoch`. Once that happens, every `stopEpoch` call reverts, the epoch can never end, `epochNumber` never advances, and all pending withdraw receipts (and all other deposits) are frozen in the vault until the APR is manually restored to 0.

### Finding Description
The analogous bug class is: a user commits funds under one configuration, then a later configuration flip makes the fulfillment path revert, freezing the committed funds.

Concretely, in `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` mints the user a receipt and calls `_requestWithdrawApr0` when `unscaledApr == 0` (lines 285-286), which increments `apr0TotalPrincipal`.
- `prepareStopEpochWithApr0` (lines 490-541), called from `IdleCDOEpochVariant.stopEpoch`, contains:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

- `setAprs` (manager-callable, as exercised at `test/foundry/IdleCreditVault.t.sol:2986`) has no check that `apr0TotalPrincipal == 0` before changing `unscaledApr`.

Because `apr0TotalPrincipal` is only zeroed inside `prepareStopEpochWithApr0` (line 540), a nonzero bucket plus a nonzero APR creates an unbreakable revert loop at every `stopEpoch`. Claims are blocked transitively: `_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest[_user]`, which requires a successful `stopEpoch`.

### Impact Explanation
All funds in the credit vault — pending withdraw receipts, APR0 principal, instant-withdraw requests, and ordinary tranche deposits — are frozen for as long as the inconsistency persists. Borrower repayment cannot be processed because `stopEpoch` reverts before collecting funds. This matches the external report's "tokens locked on the origin side cannot be released because a destination-side flag was flipped" pattern: the receipt is already minted/burned, and the settlement path reverts due to a later flag change.

### Likelihood Explanation
Requires only normal honest-manager sequencing: (1) APR is 0, a KYC'd lender requests withdraw; (2) manager sets a nonzero APR for the next epoch (a routine operation shown in tests); (3) `stopEpoch` now always reverts. Funds remain frozen until the manager sets APR back to 0 and calls `stopEpoch` again — i.e., temporary freezing of all vault funds, plus forced continuation of the epoch beyond `epochEndDate`. No attacker privilege is needed beyond being an ordinary withdraw requester.

### Recommendation
Enforce the invariant at the flag-mutation site rather than at the settlement site, mirroring the report's "cache/check the flag before committing" recommendation:

- Revert in `setAprs` when `apr0TotalPrincipal != 0` and the new APR is nonzero, or
- Settle/close the open APR0 bucket inside `setAprs` (apply the current-epoch rate and move `apr0Users[*].principal` to `settledPrincipal` semantics) before allowing `unscaledApr` to change, or
- Make `prepareStopEpochWithApr0` gracefully settle the open APR0 bucket at a zero/last-known rate instead of reverting, so `stopEpoch` can never be bricked by the APR flag.

### Proof of Concept
Foundry fork test sketch (pattern follows `testApr0WithdrawGetsInterestAtStopEpoch` in `test/foundry/IdleCreditVault.t.sol:2979`):

```solidity
function testPocAprFlipFreezesStopEpoch() external {
  _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
  vm.prank(owner);
  cdoEpoch.setIsAYSActive(false);
  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(0, 0); // APR0 mode

  uint256 amountWei = 10000 * ONE_SCALE;
  idleCDO.depositAA(amountWei);
  _transferBurnedTrancheTokens(address(this), true);

  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, 0, _expectedFundsEndEpoch());

  // user commits funds: APR0 withdraw request during buffer
  uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));
  assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

  // honest manager raises APR for next epoch — no guard stops this
  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(10e18, 10e18);

  _startEpochAndCheckPrices(1);

  // every subsequent stopEpoch reverts inside prepareStopEpochWithApr0
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  cdoEpoch.stopEpoch(0, initialProvidedApr);

  // epochNumber cannot advance -> claimWithdrawRequest reverts forever
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  cdoEpoch.claimWithdrawRequest();
}
```

Caveat: this relies on `IdleCDOEpochVariant.stopEpoch` unconditionally calling `prepareStopEpochWithApr0` (the grep confirms the call exists in that contract but I could not re-verify it runs on the non-prefunded path); if it is invoked only under a mode flag, the freeze is gated to that mode but the revert path and its consequences are unchanged.
