### Title
`check_parent_tenure_choice` under-counts already-signed blocks when sanctioning a tenure reorg - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a miner is allowed to reorg away a prior tenure. It uses `signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)` to check "disallow reorg if more than one block has already been signed" [1](#0-0)  but this counter only reflects **globally accepted** blocks (blocks that reached the 70% signature threshold and were adopted by the node), not blocks this signer itself already **signed** but that have not yet reached global acceptance. Since a signature is documented elsewhere in the codebase as "a bearer instrument" that binds the signer regardless of state [2](#0-1) , this creates a gap between "signed" and "counted as signed for reorg-permission purposes."

### Finding Description
The reorg-permission rule is supposed to protect against sanctioning a reorg that would discard tenure history the signer has already committed to via signature. The code comment states the intent explicitly: "disallow reorg if more than one block has already been signed" [3](#0-2) , yet the implementation checks `get_globally_accepted_block_count_in_tenure`, which is a strictly narrower predicate than "signed." A block can be `LocallyAccepted` (i.e. `signed_self` is set — this signer put its own signature over it) for a long time without ever reaching `GloballyAccepted`, particularly if the rest of the signer set is slow, offline, or split. In that state, `get_globally_accepted_block_count_in_tenure(&tenure)` returns 0 or 1 even though this signer (and potentially other signers) already hold live signatures over 2+ blocks in that tenure.

This is directly analogous to the reported CWE-918/SSRF class of bug: the check trusts a narrower/wrong signal (only the fully-adopted / "public" state) as a stand-in for the real security-relevant fact (whether a signature already exists), the same way the Batik bug let attacker-supplied data reach a sensitive sink because the code checked the wrong/incomplete gate. Here a single one-slot miner can drive the tenure into a state — several locally-accepted-but-not-globally-accepted blocks, by controlling pacing of proposals/validation and normal network jitter — where the guard is blind to the pre-existing exposure.

If `check_parent_tenure_choice` returns `true` incorrectly, `record_superseded_tenure`/`mark_tenure_superseded` is invoked for every tenure in the reorg [4](#0-3) . This is the same permit mechanism used later in `reorg_permit_stands` and `handle_block_pre_commit`'s conflict-exclusion path: once a tenure is marked superseded, this signer's own prior signature over that tenure's blocks "stops counting as a conflict while `self`'s sortition remains canonical" [5](#0-4)  and is explicitly excluded from the conflict list checked before signing a new, competing block [6](#0-5) .

### Impact Explanation
This breaks the "one signature per height / no double-endorsement of conflicting histories" invariant that the whole pre-commit + conflict-guard machinery exists to protect (see the extensive commentary on why a signed block must never be silently superseded: docs/signer-flows.md §5). If the reorg-permission check under-counts already-signed blocks and wrongly sanctions the reorg, the signer will (a) have already signed 2+ blocks in the "reorged" tenure that are still live signatures, and (b) simultaneously exclude those signatures from blocking a new, competing tenure's blocks at the same or lower heights, because the tenure is now recorded as `superseded`. This is the "a signer signing an invalid, non-canonical, or conflicting block" class of Critical impact called out in the rules: the signer can end up having placed live signatures on two mutually exclusive chain histories at the same height, one of which it also actively helps advance by removing the conflict-guard that would otherwise refuse to sign the replacement.

### Likelihood Explanation
This requires only the actions a single miner (plus ordinary signer-to-signer gossip) can already produce: a miner proposes multiple blocks in one tenure that gather enough weight to be individually `LocallyAccepted`/signed by a majority of individual signers but not enough to cross into `GloballyAccepted` (e.g. due to natural network asynchrony, brief signer downtime, or a split vote that later resolves) before the miner pivots to a new tenure with a different parent. No majority collusion or key compromise is needed — this is the same "signed but not yet globally accepted" window that the rest of the codebase (e.g. `get_signed_conflicts`, `conflict_still_blocks`) treats as an important, protected state precisely because it can persist for the `tenure_last_block_proposal_timeout` window or longer.

### Recommendation
Change the "disallow reorg if more than one block has already been signed" check in `check_parent_tenure_choice` to count blocks by signed state (i.e., `signed_self.is_some() || signed_group.is_some()`, matching `get_last_signed_block`/`get_signed_conflicts` semantics) rather than only `GloballyAccepted` state, so the guard actually reflects what its own comment promises.

### Proof of Concept
1. Miner starts tenure T1 and proposes block A; the signer set individually validates and each signer marks A `LocallyAccepted` (signs it), but slow signer gossip/StackerDB propagation means global-acceptance weight is not yet reached and A is not marked `GloballyAccepted`.
2. Miner proposes a second block B in T1 (still parented on A); it likewise reaches `LocallyAccepted`/signed state for a majority of signers without reaching `GloballyAccepted`.
3. `get_globally_accepted_block_count_in_tenure(T1)` returns 0 (or 1, depending on timing), even though 2 signed-but-not-yet-globally-accepted blocks exist in T1 — this can be reproduced by inspecting the existing test harness pattern in `stacks-signer/src/chainstate/tests/v2.rs` (`check_tenure_change_rejects_when_locally_accepted_block_exists`, lines 755-850) which already demonstrates the signer's local DB holding a `LocallyAccepted` block that a naive "globally accepted only" query would miss [7](#0-6) .
4. Miner abandons T1 and starts tenure T2 with a different `parent_tenure_id`. `check_parent_tenure_choice` is invoked; because `get_globally_accepted_block_count_in_tenure(T1) <= 1`, the reorg check does not hit the `Ok(false)` branch at [1](#0-0)  and instead falls through to the timing-based branch, potentially sanctioning the reorg and calling `record_superseded_tenure` on T1.
5. T1 is now marked superseded (`mark_tenure_superseded`) even though the signer holds live signatures over 2 conflicting blocks in it. Subsequent pre-commit evaluation for a new T2 block will use `reorg_permit_stands`/the superseded annotation to exclude A/B as conflicts [8](#0-7) , letting the signer add its signature to T2's block while its earlier signatures over A and B in T1 remain outstanding and public — a concrete equivocation across two mutually exclusive tenures.
