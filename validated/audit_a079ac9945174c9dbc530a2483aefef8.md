### Title
Gateway `HandleLegacyUserMessage` skips allowlist authorization, permitting unauthenticated actors to trigger DON workflows - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The reported PEG-IN bug is a "missing verification" class of flaw: the bridge server never checks that a Bitcoin transaction was actually sent to the address it generated, so the owner can mint against any qualifying transaction, not just the user's own. The closest analog in the Chainlink Gateway's capabilities handler is that the legacy user-message path forwards a caller-supplied `web_api_trigger` request to every node in the DON without ever checking the message sender against any allowlist — a verification step that is explicitly left as an unfinished `TODO`, even though the signature-derived sender is available.

### Finding Description
Incoming JSON-RPC "legacy" gateway requests are parsed and validated in `core/services/gateway/api/message.go`'s `Message.Validate()`, which recovers the `Sender` from the ECDSA signature but does not check the sender against any authorization list [1](#0-0) .

The gateway's dispatcher, `gateway.ProcessRequest`, routes any request carrying a `DonId` down the "legacy" path, calling `msg.Validate()` and then `h.HandleLegacyUserMessage(ctx, msg, callback)` on the DON's registered handler [2](#0-1) .

In the capabilities handler, `HandleLegacyUserMessage` performs payload decoding, a timestamp/staleness check, and a method check, but the authorization step is explicitly stubbed out with a comment and never implemented:
```
// TODO: apply allowlist and rate-limiting here
if msg.Body.Method != MethodWebAPITrigger {
```
Immediately after this point, the handler builds a request from the (unauthorized) message and broadcasts it to every member of the DON: `for _, member := range h.donConfig.Members { err = errors.Join(err, don.SendToNode(ctx, member.Address, req)) }` [3](#0-2) .

This is different from the newer Vault gateway handler, which explicitly wires an `Authorizer`/allowlist chain (`NewAllowListBasedAuth`, `NewAuthorizer`) before processing any request [4](#0-3) , showing that allowlisting is the intended security control for gateway user-message paths that this legacy handler omits.

### Impact Explanation
Because the sender allowlist check is not implemented on the legacy `web_api_trigger` path, any unprivileged client capable of reaching the gateway's user-facing endpoint and producing a validly-signed (but otherwise arbitrary) `Message` can have its trigger payload relayed to all nodes of a DON. This is analogous to the referenced bug class: a critical authorization/verification step ("does this request legitimately originate from/target the expected party") is missing on a path that results in privileged downstream action (workflow trigger execution across an entire DON), just as the missing Bitcoin-destination check let the bridge owner mint against arbitrary transactions.

### Likelihood Explanation
The `TODO` is unconditional and unguarded by any feature flag in the code reviewed; every request routed to `HandleLegacyUserMessage` reaches the node-broadcast step as long as it passes format/staleness/method checks, none of which restrict the sender identity. Reachability requires only that the gateway's external-facing "legacy" JSON-RPC endpoint accept requests from arbitrary or semi-trusted clients (this framework component exists specifically to bridge un-privileged workflow requests to DONs), so likelihood is high assuming this code path is exposed to non-operator callers as designed.

### Recommendation
Implement the allowlist (and rate-limiting) check called out in the `TODO` before forwarding any message to DON members in `HandleLegacyUserMessage` — mirroring the `Authorizer`/`AllowListBasedAuth` pattern already used in `core/capabilities/vault/gw_handler.go`, verifying `msg.Body.Sender` (populated by `Message.Validate()`) against a workflow/owner allowlist prior to calling `don.SendToNode`.

### Proof of Concept
Not independently executable from static review alone; the concrete exploit path would be: craft a JSON-RPC request with `DonId` set and a payload for `MethodWebAPITrigger`, sign it with an arbitrary (non-allowlisted) private key so `Message.Validate()` succeeds, and submit it to the gateway's external endpoint. Because `HandleLegacyUserMessage` never validates `msg.Body.Sender` against an allowlist before the `for _, member := range h.donConfig.Members { don.SendToNode(...) }` loop, the message would be forwarded to the DON nodes despite originating from an unauthorized party. Full exploitability could not be confirmed within the index because the HTTP-layer authentication/exposure of the gateway's legacy `/user` endpoint (in `core/services/gateway/network/httpserver.go`) could not be fully traced in this session — a Devin session with full repo/browser access would be needed to confirm whether any upstream layer (e.g., TLS client cert pinning, connector-level allowlist) mitigates this before reaching `HandleLegacyUserMessage`.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
