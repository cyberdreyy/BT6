Confirmed: `FindExternalInitiator` in `core/sessions/localauth/orm.go` performs a plain DB lookup by access key with no check of `ExternalInitiatorsEnabled()`, and the run-trigger route wiring confirms the gap.

### Title
Disabling `JobPipeline.ExternalInitiatorsEnabled` does not revoke existing EI credentials, allowing continued job-run triggering via stale EI auth - ([File: core/web/auth/auth.go], [File: core/web/router.go], [File: core/web/pipeline_runs_controller.go])

### Summary
`ExternalInitiatorsController.Create` is the only place that checks `JobPipeline().ExternalInitiatorsEnabled()`. The `AuthenticateExternalInitiator` middleware and the `POST /v2/jobs/:ID/runs` handler chain never check this flag, so an already-issued EI credential continues to authenticate and trigger job runs even after an administrator disables the External Initiator feature.

### Finding Description
The `/v2/jobs/:ID/runs` route is registered with `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` followed by `auth.RequiresRunRole(prc.Create)` [1](#0-0) .

`AuthenticateExternalInitiator` authenticates by looking up the EI record via `store.FindExternalInitiator(ctx, eia)` and comparing hashed secrets — it contains no call to `ExternalInitiatorsEnabled()` anywhere in the function [2](#0-1) . On success it injects a synthetic `User{Role: clsessions.UserRoleRun}` into the Gin context, which is exactly the role `RequiresRunRole` requires to proceed [3](#0-2) [4](#0-3) .

The backing datastore lookup, `orm.FindExternalInitiator` in `core/sessions/localauth/orm.go`, is a raw SQL query (`SELECT * FROM external_initiators WHERE access_key = $1`) with no feature-flag gating [5](#0-4) .

In `PipelineRunsController.Create`, the handler calls `auth.GetAuthenticatedUser(c)` to decide whether to run the job — since the EI middleware sets `SessionUserKey` to a synthetic run-role user, `isUser` evaluates true for EI-authenticated requests too, and the job is run via `prc.App.RunJobV2(ctx, jobID, nil)` [6](#0-5) . (Note the inline comment "EIs not allowed" is inconsistent with the actual behavior, since the EI-set context user satisfies `isUser`.)

By contrast, `ExternalInitiatorsController.Create` explicitly checks the flag before doing any DB work and returns HTTP 405 if disabled [7](#0-6) . This inconsistency means the administrative "kill switch" for the EI feature only stops *new* EI registration; it does not revoke already-existing credentials from authenticating or triggering runs.

### Impact Explanation
An administrator who disables `JobPipeline.ExternalInitiatorsEnabled` (e.g., in response to a security incident, a leaked EI credential, or to fully turn off the EI attack surface) will not actually cut off holders of previously issued EI access-key/secret pairs. Such a holder can continue to authenticate as an EI and trigger arbitrary job runs on jobs they know the integer ID of, via `RunJobV2`, which can move funds, consume node resources, or otherwise activate node behavior the operator believed was disabled. This falls under unauthorized job run triggering / authorization bypass of an administratively revoked feature state.

### Likelihood Explanation
The precondition is narrow but realistic: the attacker must already hold a valid EI access key/secret pair (previously issued, e.g., a compromised or since-untrusted integration) and know a target job's integer ID. No elevated node access, admin credentials, or other privilege is required once the credential is held — this fully fits the "unprivileged EI-credential holder" attacker model in the rules. The bypass is deterministic and repeatable: as long as the EI row remains in the `external_initiators` table (deletion, not the config flag, is what actually revokes it via `Destroy`), the credential keeps working regardless of the `ExternalInitiatorsEnabled` setting.

### Recommendation
Add an `ExternalInitiatorsEnabled()` check in `AuthenticateExternalInitiator` (core/web/auth/auth.go) so it immediately fails with `auth.ErrorAuthFailed` when the feature is disabled, rather than relying solely on the `Create` endpoint's gate. Alternatively/additionally, have the feature-disable action (or a scheduled job) purge or invalidate all `external_initiators` records, and document that disabling the flag does not retroactively revoke issued credentials unless they are also deleted via `Destroy`.

### Proof of Concept
Go handler-level integration test plan (in `core/web/external_initiators_controller_test.go` or a new `pipeline_runs_controller_test.go` test):
1. Start a test app with `JobPipeline.ExternalInitiatorsEnabled = true`; create an EI via `POST /v2/external_initiators` and capture the returned `AccessKey`/`Secret`.
2. Create a job (webhook or any job runnable via `RunJobV2`) and note its integer job ID.
3. Reconfigure/rebuild the app config with `ExternalInitiatorsEnabled = false` (without deleting the EI record).
4. Issue `POST /v2/jobs/{jobID}/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to the previously issued credential.
5. Assert (current buggy behavior) that the response is `200 OK` with a created pipeline run — proving the stale EI credential still triggers a run despite the feature being disabled.
6. After applying the fix (adding the `ExternalInitiatorsEnabled()` check to `AuthenticateExternalInitiator`), assert the same request now returns `401 Unauthorized`.

// AuthenticateExternalInitiator authenticates an external initiator request.

// Implements authMethod
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
