### Title
Reorg-permit exclusion is not scoped to the permitted tenure, letting a signer sign two conflicting blocks at the same height - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
The CVE describes a whitelist that authorizes an action ("this specific method call is safe") but is enforced too broadly, letting an attacker invoke *any* method under cover of the whitelist entry. The stacks-signer has a structurally identical construct: a "reorg permit" that is supposed to authorize exactly one specific tenure (`Y`) to replace exactly one specific superseded tenure (`X`). The enforcement check, `reorg_permit_stands`, only re-validates that the *permitting sortition* is still canonical — it never checks that the block currently being signed is the one the permit was actually granted for. As a result, once a permit for `X → Y` is recorded and `Y`'s sortition stays canonical, `X`'s signed block stops vetoing *any* future conflicting proposal at that height, not just proposals descending from `Y`.

### Finding Description
`check_parent_tenure_choice` sanctions a reorg by recording, per superseded tenure, only the permitting tenure's identity (`mark_tenure_superseded`) — [1](#0-0) . The record is keyed by the *superseded* tenure's consensus hash and carries the permitting tenure's sortition/burn-block hash [2](#0-1) .

When a new block reaches the pre-commit signing threshold, `handle_block_pre_commit` asks `get_signed_conflicts` for every previously *signed* block at or above the proposed height, joined against `superseded_tenures` [3](#0-2) . For each conflict, if it is fresh and `reorg_permit_stands` returns true, the conflict is excluded from blocking the *current* signature — regardless of what tenure the current candidate block actually belongs to: [4](#0-3) 

`reorg_permit_stands` itself only checks that the sortition recorded as `superseded_by` is still resolvable/canonical on the node — it never compares that sortition (or its consensus hash) to `block_info.block.header.consensus_hash` (the block actually being evaluated for signature): [5](#0-4) 

So the permit's scope ("tenure `Y` may replace tenure `X`") is not enforced at use time: it degenerates into "as long as *some* still-canonical tenure was once granted permission to replace `X`, `X`'s signature no longer counts as a conflict for *anyone*." Any other proposal `Z` (a different tenure than `Y`, also built on `X`'s parent state, e.g. from a genuine Bitcoin-fork race between two sortitions at the same burn height) benefits from the same exclusion the instant it queries `get_signed_conflicts`, because the query and the permit check are keyed only by the conflicting *tenure* (`X`), never by the tenure of the block currently being signed.

The other independent guard, the same-tenure/tip check right below, is scoped to `conflict.consensus_hash == block_info...consensus_hash`, i.e. it only protects the proposal's *own* tenure, not cross-tenure siblings [6](#0-5) . Cross-tenure sibling protection is *entirely* the responsibility of the `get_signed_conflicts` + `reorg_permit_stands` pair quoted above, so the scope leak removes the only guard against equivocating across two "children" of the same superseded parent tenure once a permit for either of them has ever been recorded.

### Impact Explanation
This breaks the equivocation guard (the "one signed block per height" equality) that the whole pre-commit/conflict-check design exists to defend, as documented directly in the codebase: "two blocks at the same height are siblings ... conflicts" and "a signature is a bearer instrument" that must never be given to two mutually exclusive blocks [7](#0-6) . If a signer can be induced to sign both the legitimately permitted replacement `Y` and a different, non-canonical/conflicting block `Z` at the same height (because `X`'s conflict record was cleared for everyone, not just `Y`), that signer contributes a signature to two globally-conflicting blocks. Under the "Critical" impact bucket in this analysis, this is exactly "a signer signing an invalid, non-canonical, or conflicting block" — an authorization-scope bug (CWE-863-class) in the exact sense of the source CVE: a mechanism intended to authorize one specific action is checked in a way that authorizes a broader class of actions.

### Likelihood Explanation
This requires no majority collusion and no key/auth-token access — only ordinary miner-controlled forking:
1. A legitimate reorg permit gets recorded (already a normal path: `check_parent_tenure_choice` sanctions a reorg when the reorged tenure produced ≤1 block and was proposed close to the sortition transition — a naturally occurring, not attacker-crafted, condition).
2. Two competing sortitions at/near the same burn height both build on the superseded tenure's parent (a routine burnchain-fork race that this codebase already extensively tests for, e.g. `reorg.rs`, `capitulate_parent_tenure_view.rs`).
3. The signer signs the first (`Y`), recording `signed_self`. Because the exclusion in `handle_block_pre_commit` is keyed only to whether *some* permit for `X` still stands — not to whether the second candidate (`Z`) is `Y` — the signer's later evaluation of `Z` also sees `X`'s conflict excluded, and (absent some other still-live signed conflict) proceeds to sign `Z` too.

This is a logic/scoping defect rather than a timing coincidence, so it is deterministically reachable whenever the permit and the fork race overlap; I was not able to fully trace whether some other check elsewhere (outside the files inspected) additionally re-derives tenure ancestry before this code path is reached, so there is some residual uncertainty about whether an additional implicit guard exists further upstream — but nothing in `chainstate/mod.rs`, `signerdb.rs`, or `v0/signer.rs` ties the exclusion to the specific permitted tenure.

### Recommendation
Scope the reorg-permit exclusion to the specific permitted relationship instead of the mere existence/canonicity of *a* permit:
- In `reorg_permit_stands`, additionally verify that the block currently being signed (`block_info.block.header.consensus_hash`, or its tenure ancestry) actually corresponds to `conflict.superseded_by.consensus_hash` (the tenure the permit was granted to), not merely that the permitting sortition is still resolvable.
- Alternatively, when recording the permit in `mark_tenure_superseded`, encode the check as "only tenure `Y` (and blocks provably descending from it) may bypass conflict `X`", and require `handle_block_pre_commit` to pass the candidate's own tenure/consensus hash into `reorg_permit_stands` for that comparison.
- Add a regression test analogous to `standing_reorg_permit_clears_conflict` / `orphaned_reorg_permit_restores_conflict` in `stacks-signer/src/v0/tests.rs`, but with a *third*, unrelated tenure `Z` (not the permitted `Y`) proposed at the same height as `X`, asserting that `Z` is still refused even though `X`'s permit to `Y` stands.

### Proof of Concept
1. Set up a signer that has signed block `A` in tenure `X` (height `h`).
2. Trigger `check_parent_tenure_choice` to sanction tenure `Y` reorging `X` (e.g. via the existing `reorg_timing_testing`/`check_parent_tenure_choice_reorg_timing_ok` fixture), which calls `mark_tenure_superseded(X, ..., Y, ...)`.
3. Have the signer sign block `B` in tenure `Y` at height `h+1`, as in `standing_reorg_permit_clears_conflict` [8](#0-7) .
4. Before/independently, propose block `C` in a third tenure `Z` (also built on `X`'s parent, at height `h+1`) that never received any permit relative to `X`.
5. Drive `C` through `handle_block_pre_commit`. `get_signed_conflicts` returns `A` (superseded_by = `Y`, still canonical → `reorg_permit_stands` = true → excluded from the fresh/live check) and, if `B`'s signature has not yet been persisted at evaluation time (a realistic race given asynchronous pre-commit tallying), no conflict blocks `C`. `check_block_against_signer_db_state` also does not see `Y`'s sibling, since it only checks `Z`'s own/parent tenure tip via `get_tenure_last_block_info`, which is unrelated to the permit tracking. The signer signs `C`, producing two mutually conflicting signed blocks (`B` and `C`) at height `h+1`.

I was unable to execute this end-to-end in an actual running signer/test harness (no execution environment here), so the PoC above is a code-path trace grounded in the cited functions rather than an observed test failure; the exact race window on step 5 (whether `B`'s signature is already persisted) would need to be confirmed empirically in a Devin session with the integration test harness.
