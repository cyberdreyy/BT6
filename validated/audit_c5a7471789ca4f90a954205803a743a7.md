Based on my investigation of the chainlink node codebase, I found the analog you're describing: an intentionally unauthenticated endpoint whose only protection against unauthorized task/run mutation is possession of an unguessable UUID (`taskID`), with **no ownership, ACL, or replay-window check** at the handler or route level.

### Title
Unauthenticated resume endpoint allows any client to complete/fail arbitrary pipeline task runs by UUID guess/leak - (File: `core/web/pipeline_runs_controller.go`)

### Summary
The `/v2/resume/:runID` route is explicitly mounted on the **unauthenticated** router group, and its handler, `PipelineRunsController.Resume`, performs no additional authorization, ownership, or state check before mutating pipeline run state via `App.ResumeJobV2`.

### Finding Description
In `core/web/router.go`, the route is registered on `unauthedv2` rather than the session/token-authenticated `authv2` group used for essentially every other mutating endpoint (jobs, bridges, external initiators, keys, etc.): [1](#0-0) 

The handler itself, `Resume`, only validates that `runID` parses as a UUID and that the JSON body decodes into a `pipeline.ResumeRequest`; it performs no caller identity check, no verification that the resume token/run is still pending, and no rate limiting before calling `prc.App.ResumeJobV2`: [2](#0-1) 

This is the same bug class as the report's `updateFairLaunchProperties()` — a state-mutating entry point reachable by any unprivileged caller with no access-control gate — except here the "secret" gating access is only the UUID value itself, which is generated per task and can be leaked via logs, external HTTP callback URLs, browser history, proxies, or third-party bridge/adapter systems that receive it as a callback URL parameter.

### Impact Explanation
Any external, unauthenticated party who obtains or guesses a pending task's `runID` can:
- Complete or fail a bridge/task callback out of band, resuming an in-flight pipeline run with attacker-supplied `pipeline.ResumeRequest` result data.
- Interfere with the correctness of job pipeline results feeding on-chain reports if bridge adapters route callback URLs through infrastructure (proxies, logs, browser referrers) where the UUID could be disclosed.
This does not reach the severity of the referenced report's fund/market manipulation, since it is scoped to per-task resume and the node treats it as an intentionally unauthenticated bridge-callback surface (see `audit.UnauthedRunResumed` naming), but it is a genuine unauthenticated-mutation surface reachable from an unprivileged HTTP client.

### Likelihood Explanation
Low-to-moderate: the code already names the audit event `UnauthedRunResumed`, indicating the maintainers are aware this endpoint is intentionally unauthenticated by design (it exists specifically so external bridge adapters, which cannot hold node session/API credentials, can resume a task via a per-run secret URL). Exploitation requires leakage of the specific `runID`, not blanket guessing (UUIDv4 space), so the realistic risk is confined to `runID` disclosure scenarios rather than brute force.

### Recommendation
Given this is an intentional design (webhook/bridge callback resumption), the actual security control is supposed to be a **combination of the run ID's unguessability plus one-time-use invalidation**. Confirm/verify:
1. That `ResumeJobV2` enforces the task can only be resumed once and rejects resumption of an already-completed/non-pending task (removes replay-based abuse even if the ID leaks).
2. Whether `runID` values are ever exposed in caller-visible logs, redirect URLs, or third-party bridge configs where they could leak to unrelated parties, and redact them at logging boundaries (`core/logger` redaction utilities) if so.
3. Consider adding a short-lived expiry to resume tokens on top of the one-time-use property, consistent with how `AllowListBasedAuth` in the vault gateway enforces `ExpiryTimestamp`: [3](#0-2) 

### Proof of Concept
1. Create any job with a task supporting external task resumption, obtain the generated `taskID` (UUID) for a pending task.
2. Without any session cookie or API token, send:
```
PATCH /v2/resume/<taskID>
Content-Type: application/json

{"data": "attacker-controlled-value"}
```
3. Observe `prc.App.ResumeJobV2` executes and the pipeline run completes with attacker-supplied data — no `Authorization` header, session cookie, or `X-Chainlink-EA-*` external-initiator headers are required, unlike every other mutating `/v2/*` route in `core/web/router.go`. [2](#0-1) [1](#0-0)

```go
// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
```
