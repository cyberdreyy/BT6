## Finding

### Title
Unprivileged/self-inflicted receiver revert in `distribute_internal` permanently DoSes payout of stake, rewards, and commission for *all* co-shareholders of a `StakingContract` distribution pool - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
This is the closest local analog of the external report's "unsafe external call inside a payout path controlled by a receiver" bug class. In the external report, gas griefing was possible because a `payable().call` blindly trusted the callee's return behavior inside a value-transfer path invoked by a third-party relayer. In `staking_contract::distribute_internal`, the framework performs an equivalent trust mistake: it iterates over *every* shareholder of a shared `distribution_pool` and calls `aptos_account::deposit_coins` for each one inside a single atomic `while` loop, with no isolation between recipients. [1](#0-0) 

### Finding Description
`distribute` is explicitly documented as callable by *anyone* ("not need to be restricted to just the staker or operator"), similar to a relayer-invoked function in the original report. [2](#0-1) 

`distribute_internal` withdraws the entire withdrawable balance from the stake pool once, then loops over `distribution_pool.shareholders()` and pays out each one via `aptos_account::deposit_coins`:
```
while (distribution_pool.shareholders_count() > 0) {
    ...
    aptos_account::deposit_coins(recipient, coin::extract(&mut coins, amount_to_distribute));
    ...
};
``` [1](#0-0) 

`aptos_account::deposit_coins` aborts if the recipient's `CoinStore` is frozen, or — more importantly for an unprivileged actor — if the recipient has never registered a `CoinStore<CoinType>` **and** has disabled direct coin transfers via `set_allow_direct_coin_transfers(false)`:
```
if (!coin::is_account_registered<CoinType>(to)) {
    assert!(can_receive_direct_coin_transfers(to), error::permission_denied(EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS));
    coin::register<CoinType>(&create_signer(to));
};
coin::deposit<CoinType>(to, coins)
``` [3](#0-2) 

There is no per-recipient try/skip logic, no way to remove or bypass an uncooperative shareholder, and no fallback deposit path (e.g., to a claimable escrow) if `deposit_coins` aborts. Because the withdrawal from the stake pool (`stake::withdraw_with_cap`) and the entire payout loop happen in one atomic transaction, a single reverting recipient aborts the whole `distribute()` call — blocking payout to every *other*, non-malicious shareholder (other stakers who switched operators into this pool, and the operator/beneficiary) whose funds are sitting withdrawable in the same `distribution_pool`. This directly parallels the external bug's core lesson: trusting an externally-influenced payout target inside a shared, atomic disbursement loop lets one actor grief value owed to unrelated parties. The developers were clearly aware of a similar DoS vector for *pool size* (bounding `MAXIMUM_PENDING_DISTRIBUTIONS` to prevent out-of-gas griefing via too many recipients), but did not defend against a single recipient causing a hard abort via `deposit_coins`. [4](#0-3) 

### Impact Explanation
Any shareholder that ends up in a shared `distribution_pool` — which can include multiple past stakers (added via `add_distribution` on operator switches) and the operator/its beneficiary — can strand withdrawable stake/rewards/commission belonging to every *other* shareholder of that same pool by making their own account revert on deposit (opting out of direct transfers while unregistered for `AptosCoin`, e.g. a freshly created address never funded before, such as one set via `set_beneficiary_for_operator`). This traps otherwise-withdrawable value and blocks legitimate claim rights for unrelated stakers/operators sharing the pool, matching the "permanent lock/non-recoverable loss of claim rights" and "share-accounting... traps value" impact categories.

### Likelihood Explanation
Exploitability depends on at least one shareholder in the shared distribution pool being an account that both (a) has never registered `CoinStore<AptosCoin>` and (b) has called `set_allow_direct_coin_transfers(false)`. This is plausible for accounts created specifically to serve as an operator's beneficiary or for freshly-created resource/treasury accounts that have not yet interacted with AptosCoin, but it is not universally true for ordinary funded accounts (most user wallets already hold registered `CoinStore<AptosCoin>` because it is commonly used to pay gas, which would bypass the guarded abort path). I was not able to fully confirm within available tooling whether `CoinStore<AptosCoin>`/primary fungible store registration is unconditionally auto-created for every account at genesis-level account creation in this codebase version (the FA-migration code paths suggest this can vary), so the precondition should be treated as conditional rather than guaranteed. Given this uncertainty about universal preconditions, I rate confidence in real-world triggerability as moderate rather than certain.

### Recommendation
Make `distribute_internal`'s per-recipient payout resilient to a single failing deposit: wrap each `aptos_account::deposit_coins` call so a revert for one recipient does not abort the whole transaction (e.g., attempt registration/deposit defensively, and on failure route that recipient's share to a claimable/escrow resource instead of the shared atomic loop), so that one uncooperative or misconfigured shareholder cannot block payouts owed to all other shareholders of the same distribution pool.

### Proof of Concept
1. Staker A creates a staking contract with operator O (`create_staking_contract`), and later switches operators (or the operator sets `set_beneficiary_for_operator` to a brand-new address B that has never registered `CoinStore<AptosCoin>`), leaving B or A as a shareholder entry in the pool's `distribution_pool` alongside other legitimate stakers. [5](#0-4) 
2. Shareholder B calls `aptos_account::set_allow_direct_coin_transfers(false)` on their own account, and never registers `CoinStore<AptosCoin>`. [3](#0-2) 
3. Time passes, stake becomes withdrawable, and anyone calls `staking_contract::distribute(staker, operator)`. [6](#0-5) 
4. In the payout loop, when the iterator reaches B, `aptos_account::deposit_coins(B, ...)` hits `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` and aborts, reverting the entire `distribute()` transaction — including payouts already computed for all other shareholders in the same call. [1](#0-0) 
5. Every subsequent call to `distribute()` for this staker/operator pair fails the same way, permanently blocking withdrawal of stake/rewards/commission for all other shareholders until B is manually removed from the shares model (no such mechanism exists in the code shown).
