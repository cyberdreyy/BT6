### Title
Unbounded flood of legacy `web_api_trigger` requests lets an attacker evict a victim's valid, unexpired callback via `pruneCallbacks`'s creation-time-only eviction - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.pruneCallbacks` evicts callbacks purely by oldest-`createdAt` ordering once `len(savedCallbacks) > MaxSavedCallbacks`, with no notion of per-sender fairness or quota. `HandleLegacyUserMessage` inserts every accepted trigger request into the shared `savedCallbacks` map with an explicit `// TODO: apply allowlist and rate-limiting here` comment confirming no per-user throttling exists at this layer, so an attacker can flood the map to force eviction of another tenant's still-valid callback.

### Finding Description
`HandleLegacyUserMessage` validates message shape/freshness/method but explicitly defers allowlisting and rate limiting (`// TODO: apply allowlist and rate-limiting here`), then unconditionally stores the callback: [1](#0-0) 

`pruneCallbacks`, run periodically, first removes truly expired entries, then — if the map is still over `MaxSavedCallbacks` — sorts *all remaining* entries by `createdAt` and deletes the oldest half, with zero consideration of sender/tenant identity or remaining time-to-live: [2](#0-1) 

Because eviction is purely a function of insertion order, an attacker who submits `MaxSavedCallbacks` (default 20000, `defaultMaxSavedCallbacks`) or more cheap `web_api_trigger` requests in a burst — with at least one request submitted immediately after a victim's legitimate request — guarantees the victim's callback lands in the "older half" once the flood pushes total count above the threshold, and it gets silently `delete()`d before the corresponding node response (`handleWebAPITriggerMessage`) ever arrives: [3](#0-2) 

When the legitimate node response for the victim's request eventually arrives, `savedCb, found := h.savedCallbacks[msg.Body.MessageId]` returns `found == false`, so `SendResponse` is never invoked and the caller's HTTP/gateway request simply times out with no explicit error — a silent cross-tenant denial of response.

### Impact Explanation
This breaks tenant isolation for the gateway's web API trigger path: an unprivileged attacker can cause legitimate, in-flight, non-expired pipeline/workflow trigger responses belonging to other users/workflows to be dropped, denying them their expected response without any signal that the eviction (rather than the target service) caused the failure. This matches Chainlink's "Denial of Service" / cross-user response confusion impact class since attacker-initiated activity directly and repeatably suppresses another user's expected callback delivery.

### Likelihood Explanation
The only precondition is the ability to submit many well-formed, appropriately-signed `web_api_trigger` requests to the same DON/gateway handler — something any client permitted to call the gateway's legacy webAPI trigger endpoint can already do, since the code path itself notes no allowlist/rate-limit is enforced before the callback is stored. This requires no special credentials beyond whatever is minimally needed to submit a trigger request, is fully attacker-controlled/timed (attacker just interleaves its flood immediately after observing/guessing the victim's request), and is repeatable on demand every prune cycle (`CallbackPruneIntervalSec`, default 30s).

### Recommendation
Change `pruneCallbacks` eviction policy to never evict callbacks that have not exceeded `CallbackMaxAgeSec`; instead, when over `MaxSavedCallbacks`, apply per-sender/tenant quotas (e.g., cap concurrent in-flight callbacks per sender address) or reject new insertions with a rate limit/backpressure signal at `HandleLegacyUserMessage` before the map grows unbounded, rather than trimming purely by global creation order. Implement the currently-missing "apply allowlist and rate-limiting here" TODO.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with `MaxSavedCallbacks = N` (e.g., 10) and a mock `Callback` for each entry.
2. Insert one "victim" callback with `createdAt = now` via direct map manipulation (mirroring `HandleLegacyUserMessage`'s insertion at [4](#0-3) ).
3. Insert `N` "attacker" callbacks with `createdAt = now.Add(1*time.Millisecond)` (i.e., strictly newer than the victim), simulating a flood submitted right after the victim's request.
4. Call `h.pruneCallbacks()`.
5. Assert: victim's `messageId` is no longer present in `h.savedCallbacks` (evicted) despite `now.Sub(victim.createdAt) < maxAge` (not expired), while newer attacker entries survive — demonstrating the fairness/isolation gap at [5](#0-4) .
6. Optionally simulate the subsequent node response for the victim via `handleWebAPITriggerMessage` and assert the victim's `SendResponse` mock is never invoked, confirming silent response loss.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
