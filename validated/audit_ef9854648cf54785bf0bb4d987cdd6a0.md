### Title
Global contract code committed to state and marked "existing" for `use_global_contract` regardless of `precompile_contract_with_warming` (module-validation) failure - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
`apply_distribution_current_shard` writes the global contract's raw bytes to `state_update` and commits the state change *before* calling `precompile_contract_with_warming`, and the compile/precompile result is completely discarded (`let _ = precompile_contract(...)` in `runtime/runtime/src/cache_warming.rs:77`). Because `use_global_contract`'s only existence check is `state_update.contains_key(&key, ...)` against `TrieKey::GlobalContractCode`, wasm that passes only the `ContractSizeExceeded` check but fails module validation/instantiation is still treated as "existing," letting third parties pay `use_global_contract_base`/`use_global_contract_byte` fees to opt into permanently non-functional code.

### Finding Description
`action_deploy_global_contract` (`runtime/runtime/src/global_contracts.rs:24-61`) only enforces a storage-balance check and calls `initiate_distribution`, which produces a `GlobalContractDistribution` receipt carrying the raw code. There is no wasm module/validation check at deploy time in `runtime/runtime/src/action_validation.rs`'s `validate_deploy_global_contract_action`-style path beyond the `ContractSizeExceeded` size check (per `docs/RuntimeSpec/Actions.md:462`, the only listed `DeployGlobalContractAction` validation error is `ContractSizeExceeded`).

When the distribution receipt lands on a shard, `apply_distribution_current_shard` (`runtime/runtime/src/global_contracts.rs:190-234`) does:
```
state_update.set(trie_key, global_contract_data.code().to_vec());
state_update.commit(...);
...
precompile_contract_with_warming(&ContractCode::new(...), config, ..., apply_state.cache.as_deref());
```
The state write and commit happen unconditionally, before compilation is even attempted. `precompile_contract_with_warming` (`runtime/runtime/src/cache_warming.rs:66-78`) explicitly drops the result: `let _ = precompile_contract(code, ..., cache);` — a `CompilationError` (module validation failure) is silently ignored, and the caller (`apply_distribution_current_shard`) has no branch checking it; execution proceeds to compute fees and returns `Ok(compute)` unconditionally.

Later, `use_global_contract` (`runtime/runtime/src/global_contracts.rs:75-107`) checks only:
```
if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
    result.result = Err(ActionErrorKind::GlobalContractDoesNotExist{..}.into());
    return Ok(());
}
```
This checks presence of the `TrieKey::GlobalContractCode` entry, which was written regardless of module validity. It does not consult the compiled-contract cache or its stored `CompileModuleError`/`CompilationError` state (`runtime/near-vm-runner/src/wasmtime_runner/mod.rs:663-678`, `CompiledContract::CompileModuleError`). Consequently `use_global_contract` succeeds, the caller pays `use_global_contract_base`/`use_global_contract_byte` fees (`runtime/near-vm-runner/src/logic/logic.rs:2789-2809`), and the account's `AccountContract::Global`/`GlobalByAccount` is set. Every subsequent `FunctionCall` receipt against that account will hit the cached `CompileModuleError` in `with_compiled_and_loaded` (`runtime/near-vm-runner/src/wasmtime_runner/mod.rs:686-730`) and fail deterministically — the contract can never execute.

### Impact Explanation
This is a fee-payment/metering-totality violation: a third party (V) pays non-refundable `action_use_global_contract_base`/`byte` fees (and separately consumed gas for the enclosing FunctionCall/promise-batch action) to "opt in" to a global contract that is unconditionally and permanently non-executable, in exchange for zero delivered functionality. It does not cause fund loss beyond the fee itself, is not a consensus divergence, and is not a shard-halting panic — every downstream FunctionCall against the account fails gracefully as a normal execution outcome (a `FunctionCallError`/`CompilationError`), not a node crash. It maps most closely to a "fee bypass without deliverable outcome" / broken invariant class rather than direct fund theft, and its scoped monetary impact is bounded to the wasted per-use fee amount, which is attacker-controlled but victim-paid only if the victim chooses to call `use_global_contract` on that specific identifier.

### Likelihood Explanation
Trivial and fully attacker-controlled and repeatable: deploying invalid-but-size-compliant wasm via `DeployGlobalContractAction` requires no privilege beyond an ordinary funded account and passes today's only deploy-time check (`ContractSizeExceeded`). However, actual exploitation requires an independent third party (V) to voluntarily choose to call `use_global_contract` against the attacker's specific (unverified) contract identifier — the attacker cannot force V to opt in. This significantly lowers real-world likelihood: it is a self-harm risk for any account that blindly trusts an unverified global-contract identifier, not something the attacker can inflict on an unwilling victim without a social-engineering-style lure (which is out of scope per the rules).

### Recommendation
Before (or in addition to) writing the code to `TrieKey::GlobalContractCode` and committing state in `apply_distribution_current_shard`, validate the module (or at minimum, propagate the `precompile_contract_with_warming`/`precompile_contract` compilation result) and only mark the contract "available" (or store a validity flag alongside it) if compilation succeeds; alternatively, have `use_global_contract`'s existence check also consult the compiled-cache validity (i.e., reject `CompileModuleError` entries), and consider preventing `DeployGlobalContractAction` from ever finalizing (or refunding storage cost) for code that fails module validation.

### Proof of Concept
1. Unit test in `runtime/runtime/src/global_contracts.rs` tests (or `test-loop-tests/src/tests/global_contracts.rs`): construct wasm bytes that pass the `max_contract_size` check but fail wasmtime module validation (e.g., malformed section). Submit `DeployGlobalContractAction` with `CodeHash` mode; assert the distribution receipt applies successfully and `state_update.contains_key(TrieKey::GlobalContractCode{..})` is `true`.
2. From a second account V, submit `UseGlobalContractAction` referencing that identifier; assert the outcome is `FinalExecutionStatus::SuccessValue` (i.e., NOT `ActionErrorKind::GlobalContractDoesNotExist`), and assert V's account balance decreased by exactly the metered `use_global_contract_base + use_global_contract_byte*len` fee.
3. From V, submit a `FunctionCall` receipt to any method on the now-"linked" contract; assert every such call fails (e.g., `FunctionCallError`/compilation-related abort) for repeated attempts, quantifying that the fee paid in step 2 bought permanently zero functionality.
