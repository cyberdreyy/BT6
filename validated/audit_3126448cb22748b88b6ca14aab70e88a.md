### Title
Bridge `OutgoingToken` secret disclosed to view-role users via unrestricted `GET /v2/bridge_types/:BridgeName` - (File: `core/web/bridge_types_controller.go`)

### Summary
`BridgeTypesController.Show` (and `Index`) are registered without `auth.RequiresEditRole`, so any authenticated user regardless of role (including `UserRoleView`) can retrieve a bridge's `OutgoingToken`, which is included unconditionally (no `omitempty`, no redaction) in `presenters.BridgeResource`.

### Finding Description
The router wires `bridge_types` routes as: [1](#0-0) 
Only `Create`, `Update`, and `Destroy` are wrapped with `auth.RequiresEditRole`; `Index` and `Show` are reachable by any authenticated session/token regardless of role, gated only by the outer `authv2` group's `auth.Authenticate` middleware (session or API token), not by `RequiresEditRole`.

`Show` looks up the bridge and serializes it with `presenters.NewBridgeResource`: [2](#0-1) 

The presenter builds the response with `OutgoingToken` populated directly from the DB model, with no `omitempty` and no role-based redaction: [3](#0-2) 

`IncomingToken` is (by design, per the code comment) only ever populated at bridge-creation time in-memory and never reloaded from storage, so it is effectively redacted for `Show`/`Index`. `OutgoingToken`, however, is always populated when the bridge is fetched from the ORM, meaning it is returned on every `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` call. This is confirmed by the presenter unit test, which asserts `outgoingToken` is always present in the marshaled JSON while `incomingToken` only appears once manually set: [4](#0-3) 

The existing RBAC route map explicitly documents/expects `viewOnlyAllowed: true` for these GET routes: [5](#0-4) 
but that test suite (`TestRBAC_Routemap_ViewOnly`, etc.) only asserts HTTP status codes are not `401`/`403`; it never inspects response bodies for secret redaction, so it does not catch the `OutgoingToken` leak.

### Impact Explanation
`OutgoingToken` is a credential the node uses to authenticate itself when it calls out to the external bridge adapter. A user granted only `UserRoleView` (or an API token scoped to view-only) — an unprivileged, non-edit/non-admin role — can read this outbound authentication secret for any configured bridge via a simple authenticated GET, without any edit/admin privilege. This matches the "credential/secret disclosure" bounty impact class: an attacker holding a low-privilege but valid session/token can obtain a secret intended to be edit/admin-restricted, which could be replayed to impersonate the node to the external adapter or pivot toward further compromise of bridge integrations.

### Likelihood Explanation
Precondition: attacker needs any valid authenticated session or API token with `UserRoleView` (or `UserRoleRun`, since `RequiresEditRole` explicitly blocks only `View`/`Run`, but the `Show`/`Index` routes have no role check at all, so even `Run` role works) — no edit or admin privilege is required. This is a normal, low-privilege node user credential (e.g., a read-only dashboard integration or monitoring token), and the request is a simple, repeatable `GET /v2/bridge_types/:BridgeName` call with no rate limiting or additional checks blocking it.

### Recommendation
Wrap `bt.Index` and `bt.Show` with `auth.RequiresEditRole` (or introduce a distinct redacted presenter for view-role responses that omits `OutgoingToken`), and add `omitempty`/explicit redaction logic to `presenters.BridgeResource.OutgoingToken` for non-edit/admin callers, mirroring how `IncomingToken` is already handled. Extend `TestRBAC_Routemap_*` to also assert on response body field presence for confidential fields, not just status codes.

### Proof of Concept
1. Go handler-level integration test in `core/web/bridge_types_controller_test.go`:
   - Create an application via `cltest.NewApplication(t)`, create a bridge with `OutgoingToken` set via `app.BridgeORM().CreateBridgeType`.
   - Create an HTTP client authenticated as `cltest.User{Role: sessions.UserRoleView}` (as done in `TestRBAC_Routemap_ViewOnly` in `core/web/auth/auth_test.go`).
   - Call `client.Get("/v2/bridge_types/" + bridgeName)`.
   - Assert `resp.StatusCode == http.StatusOK` (view role is not blocked).
   - Parse response body into `presenters.BridgeResource` and assert `resource.OutgoingToken != ""` and equals the created bridge's `OutgoingToken`, demonstrating disclosure to a view-role session.
   - Cross-check: repeat with a `UserRoleRun` client to show the same leak occurs for run-role too, since neither `Index` nor `Show` enforces `RequiresEditRole`.

```go
// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
```

```go
// GetName implements the api2go EntityNamer interface
```
