### Title
Signer duplicate-tenure-change guard checks only global acceptance, allowing equivocated re-signing within the same tenure - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` blocks a second tenure-change proposal for a tenure only if `SignerDb::get_last_globally_accepted_block` finds a block that has already crossed the 70% global-acceptance threshold. A block this same signer has already locally accepted/signed for that tenure — but which never reached global acceptance — leaves the lookup returning `None`, so the guard silently passes and the signer can be walked into signing a second, conflicting tenure-start block for the identical tenure.

### Finding Description
`check_proposal` dispatches tenure-change blocks to `validate_tenure_change_payload`: [1](#0-0) 

The only anti-duplicate check inside that function is: [2](#0-1) 

`get_last_globally_accepted_block` only returns a block once it has crossed the global signer-weight threshold; it says nothing about whether *this* signer already locally signed a different block for the same tenure. Elsewhere in the same file, the code explicitly acknowledges that local/pre-commit acceptance is a distinct, weaker state than global signing: [3](#0-2) 
(`has_signed_block_in_tenure` is used only for the inactivity-timeout logic, not for duplicate detection in `validate_tenure_change_payload`.)

For a second (non-tenure-change) block in the same tenure, `check_proposal` instead calls `SortitionData::confirms_latest_block_in_same_tenure`, which forces the new block to chain off the previously signed block, indirectly preventing forks mid-tenure. That protection does not exist for the *first* block of a tenure: the tenure-change path relies solely on the global-acceptance lookup.

Because the proposal's `miner_pkh` must match the sortition winner's pubkey hash (checked earlier in `check_proposal`), only the actual winning miner for that sortition can produce a validly-signed tenure-change block header for that `consensus_hash`. That miner is exactly the attacker's own single winning BTC-slot miner under the stated threat model. This miner can craft two distinct tenure-change blocks (`B1`, `B2`) for the same tenure and gossip them to the same signer (or different signers) via StackerDB block-proposal messages. If `B1` is only locally accepted by a given signer — never crossing the 70% global threshold (e.g., the attacker withholds broadcast to enough signers, or timing/latency prevents quorum) — `get_last_globally_accepted_block` for that tenure still returns `None` when `B2` is subsequently evaluated by that same signer, so `validate_tenure_change_payload` returns `Ok(())` for `B2` as well.

### Impact Explanation
This breaks the uniqueness/equivocation-guard property: a single signer can be led to sign two different, conflicting tenure-start blocks for the same tenure. That is exactly the chain-safety "conflicting block" scenario the DuplicateBlockFound check exists to prevent, matching the Critical impact category. If enough signers repeat this pattern (each independently satisfies the same broken equality), two mutually exclusive blocks can accumulate signer weight for the same tenure, creating a genuine equivocation/fork risk rather than merely a rejected proposal being miscounted as accepted.

### Likelihood Explanation
Preconditions: the attacker must win a single sortition (their own BTC, as permitted by the threat model) so their key satisfies the `miner_pkh` check, and must be able to get one signer to locally accept `B1` without it reaching global 70% acceptance before `B2` is proposed and evaluated by that same signer. This is fully achievable with only miner-level control plus normal StackerDB gossip of block proposals — no majority-signer collusion, no compromised keys, and no local host access are required. It is repeatable every time the attacker wins a slot and can stagger/withhold propagation of their two competing tenure-change blocks.

### Recommendation
In `validate_tenure_change_payload`, extend the duplicate check to also consult this signer's own local acceptance/signing record for the tenure (e.g., any block this signer has locally accepted or signed, not just globally-accepted ones), rejecting a second tenure-change proposal whenever a different `signer_signature_hash` for the same tenure has already been locally accepted/signed by this signer, regardless of whether it reached global consensus.
